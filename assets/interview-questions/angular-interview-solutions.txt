ANGULAR FRAMEWORK — SOLUTIONS TO 200 TECHNICAL INTERVIEW QUESTIONS
==================================================================

Companion to angular-interview-questions.txt. Numbering matches the question
file. Answers reflect the modern Angular API surface (standalone, signals,
built-in control flow, zoneless) while noting the older APIs you will still
meet in existing codebases.


------------------------------------------------------------------
SECTION 1: FUNDAMENTALS & ARCHITECTURE (1–15)
------------------------------------------------------------------

1. What is Angular, and how does it differ from AngularJS?

Angular is a TypeScript-based, component-driven framework from Google for building single-page and server-rendered web applications. It ships an integrated toolset: a compiler, router, forms, HTTP client, dependency injection, testing utilities, and the CLI. AngularJS (1.x) was a separate JavaScript framework built around controllers, $scope, and two-way binding driven by a digest loop.

Angular (2+) was a complete rewrite rather than an upgrade. It replaced controllers and $scope with components, uses a hierarchical DI system, compiles templates ahead of time, and detects changes through Zone.js or signals instead of dirty-checking watchers. AngularJS reached end of life in January 2022, so new work and migrations all target Angular.


2. Describe the overall architecture of an Angular application. What are its main building blocks?

An Angular app is a tree of components. Each component pairs a TypeScript class with an HTML template and styles. Directives add behavior to DOM elements, and pipes transform values for display. Services hold business logic and shared state and reach components through dependency injection.

The router maps URLs to components, and HttpClient handles server communication. The application is bootstrapped from a root component with a set of application-level providers. Features are usually organized into folders of standalone components, routes, and services, and are often lazy loaded. The compiler turns templates into efficient JavaScript instructions that create and update the DOM.


3. What are standalone components, and why did Angular move away from NgModules as the default?

A standalone component declares its own template dependencies in its imports array, so no NgModule is needed to compile it. Standalone became the default in recent versions; you no longer write standalone: true explicitly.

The motivation was to reduce boilerplate and confusion. With NgModules a component's dependencies lived in a different file, the declarations, imports, and exports rules were hard to learn, and SharedModule patterns hid unused code. Standalone makes dependencies local and explicit, improves tree-shaking, makes lazy loading individual components trivial (loadComponent), and simplifies testing.


4. What is the purpose of an NgModule, and in what situations might you still use one today?

An NgModule groups declarations (components, directives, pipes), imports other modules, exports a public API, and registers providers. It defines a compilation context and, historically, an injector scope for lazy-loaded features.

You still meet NgModules in legacy applications, in third-party libraries that have not migrated, and in some module-based APIs such as RouterModule.forRoot or older Material versions. They can also be convenient for bundling a related set of standalone directives under one import. You can import an NgModule directly into a standalone component's imports array, so the two styles interoperate.


5. Walk through the bootstrapping process of a standalone app using bootstrapApplication().

main.ts calls bootstrapApplication(AppComponent, appConfig). Angular creates the platform and an environment (root) injector from the providers in appConfig, such as provideRouter, provideHttpClient, and change detection providers. It then runs app initializers.

Next, Angular finds the root component's selector in index.html, creates the component, and attaches it to the application's change detection. The returned promise resolves to an ApplicationRef. For SSR there is a parallel server bootstrap that reuses the same config merged with server-specific providers.


6. What is the role of app.config.ts and the application-level providers array?

app.config.ts exports an ApplicationConfig object whose providers array configures the root environment injector. It replaces what the root AppModule's imports and providers used to do.

Typical entries are provideRouter(routes, ...features), provideHttpClient(withInterceptors(...)), provideAnimationsAsync(), provideZonelessChangeDetection() or provideZoneChangeDetection(), provideClientHydration(), and your own app-wide tokens. Keeping this in its own file lets the browser and server configurations share and merge it, and keeps main.ts minimal.


7. What is the Angular CLI, and which commands do you use most often?

The Angular CLI (@angular/cli, invoked as ng) scaffolds, builds, serves, tests, and updates Angular workspaces. It wraps the build system and applies schematics for code generation and migrations.

Common commands include ng new to create a workspace, ng serve to run the dev server, and ng build to produce a production bundle. ng generate (ng g) creates components, services, guards, pipes, and similar files. You will also use ng test, ng e2e, ng lint (once configured), ng add to install a package with its setup schematic, ng update to upgrade with migrations, and ng extract-i18n for translations.


8. What is the difference between JIT (Just-in-Time) and AOT (Ahead-of-Time) compilation?

With JIT, the browser downloads the Angular compiler and compiles templates at runtime. This means larger bundles, slower startup, and template errors that only appear at runtime.

With AOT, templates are compiled to JavaScript during the build. You get smaller bundles (no compiler shipped), faster rendering, template type-checking at build time, and better security, because templates are not evaluated from strings. AOT has been the default for development and production builds since Ivy, and JIT is now mostly limited to special cases such as some test setups.


9. What is the Ivy rendering engine, and what benefits did it bring over View Engine?

Ivy is Angular's compiler and runtime, the default since version 9; View Engine was removed in version 13. Ivy compiles each component into instructions stored as static properties on the class (for example ɵcmp). It follows a locality principle: each file compiles independently.

The benefits include better tree-shaking and smaller bundles, faster incremental builds, and improved template type checking. Error messages and debugging improved, and runtime APIs such as ng.getComponent became available in the console. Ivy also enabled later features, including standalone components, dynamic component creation without entryComponents, and the groundwork for signals and zoneless change detection.


10. What does angular.json control, and how do build configurations (development, production) work?

angular.json is the workspace configuration file. It lists each project and its architect targets (build, serve, test, extract-i18n), together with the builder each target uses and that builder's options: entry points, assets, styles, polyfills, tsconfig, output path, and so on.

Each target can define named configurations, such as production and development, that override the base options. Typical overrides are optimization, sourceMap, outputHashing, budgets, and fileReplacements. defaultConfiguration selects which configuration applies when none is given, and you can choose one explicitly with ng build --configuration=staging.


11. Why is TypeScript central to Angular, and how do decorators fit into the framework?

Angular is written in TypeScript and uses its static types throughout: DI tokens are resolved from types, templates are type-checked against component classes, and APIs such as typed forms and signals depend on generics. This catches errors at compile time and enables strong IDE tooling.

Decorators such as @Component, @Injectable, and @Input attach metadata to classes and members. The Angular compiler reads that metadata at build time to generate component definitions, injector configuration, and input/output maps. Because the compiler processes them during the build, they cost little at runtime.


12. Name the key Angular decorators and explain what each one does.

@Component marks a class as a component and supplies its selector, template, styles, imports, change detection strategy, and providers. @Directive defines a directive with a selector and no template. @Pipe defines a named template transformation and whether it is pure. @Injectable marks a class as a DI provider and can set providedIn. @NgModule declares a module's declarations, imports, exports, and providers.

@Input and @Output declare a component's or directive's public inputs and event outputs; the signal-based input() and output() functions are now preferred. @HostListener subscribes to events on the host element or on global targets (window, document), and @HostBinding binds a class property to a host property, attribute, class, or style. The style guide now recommends the host metadata property instead of these two decorators. @ViewChild and @ContentChild and their plural forms query the view or the projected content.


13. How does Angular's release cadence and versioning policy work, and how do you upgrade a project with ng update?

Angular follows semantic versioning. It releases a major version roughly every six months, with minor and patch releases in between. Each major gets about six months of active support followed by twelve months of long-term support (security and critical fixes only). Deprecated APIs normally remain for at least two major versions before removal.

To upgrade, move one major version at a time with ng update @angular/core@X @angular/cli@X, plus companion packages such as @angular/material. The command updates package.json and runs automated migration schematics that rewrite code. The official update guide at angular.dev/update lists manual steps for your version path. Commit before each step and run tests between majors.


14. What are schematics, and when would you write a custom one?

Schematics are code generators and transformers that run against a virtual file tree. They can create, modify, or delete files and are applied atomically. The CLI uses them for ng generate, ng add setup routines, and ng update migrations.

You would write a custom schematic (with @angular-devkit/schematics) to enforce team conventions. Examples include generating a feature with a predefined folder structure, a store, and tests, adding licence headers, or shipping ng add and ng update support for a library you publish. Large organizations often use them to scaffold consistent micro-frontends.


15. In an Angular workspace, what is the difference between an application project and a library project?

An application project is deployable. It has an index.html and a bootstrap entry point, and builds into a browser bundle (and optionally a server bundle). A library project is a reusable package with no bootstrap. It is built with ng-packagr into the Angular Package Format so other apps can import it, either from npm or by path.

Libraries define a public API in public-api.ts, declare peerDependencies on Angular, and are generated with ng generate library. In monorepos, libraries are the main tool for sharing UI components, data-access services, and utilities across applications while keeping boundaries clear.

SECTION 2: COMPONENTS & TEMPLATES (16–35)
------------------------------------------------------------------

16. What is a component, and what metadata does the @Component decorator require?

A component is a directive with a template. It is a class that controls a region of the UI, together with its HTML, styles, and the dependencies it uses. Components are the main building block of an Angular app.

In practice you need a selector to place the component in a template, plus either template or templateUrl. Common optional metadata includes styles or styleUrl(s), imports (the components, directives, and pipes the template uses), changeDetection, providers and viewProviders, encapsulation, host bindings, and hostDirectives. A routed component can omit the selector.


17. List the component lifecycle hooks and explain the order in which they run.

The order is: constructor (not technically a hook), ngOnChanges (when inputs are set, before ngOnInit), ngOnInit (once), and ngDoCheck (every change detection run). These are followed by ngAfterContentInit (once) and ngAfterContentChecked, then ngAfterViewInit (once) and ngAfterViewChecked. ngOnDestroy runs when the component is removed.

ngOnChanges, ngDoCheck, and the two *Checked hooks repeat on later change detection cycles. Content hooks run before view hooks because projected content is checked before the component's own view. Besides these, afterNextRender and afterEveryRender register callbacks that run after the DOM has been rendered, and DestroyRef.onDestroy is a composable alternative to ngOnDestroy.


18. What is the difference between the constructor and ngOnInit? What belongs in each?

The constructor is a TypeScript and JavaScript feature. It runs when the class is instantiated, before Angular has set any decorator-based inputs, and its main job is receiving dependencies and initializing simple fields. ngOnInit runs once after the first ngOnChanges, so decorator inputs are available.

Put dependency injection (or inject() field initializers) and trivial assignments in the constructor or field initializers. Put logic that depends on inputs, such as fetching data based on an id input, in ngOnInit. With signal inputs, many cases are better expressed as computed() or resource() values that react to input changes automatically.


19. When is ngOnChanges called, and what information does SimpleChanges provide?

ngOnChanges is called before ngOnInit when the component has decorator-based @Input properties. It is called again whenever a parent binding changes an input's reference. It is not called when inputs are set programmatically on the class, and it does not see deep mutations inside an object whose reference stays the same.

SimpleChanges is an object keyed by input name. Each entry is a SimpleChange with previousValue, currentValue, firstChange(), and isFirstChange semantics. Signal inputs do not need ngOnChanges, because you can derive values with computed() or react with effect().


20. What is the difference between ngAfterContentInit and ngAfterViewInit?

ngAfterContentInit runs once after Angular projects external content (from ng-content) into the component and initializes @ContentChild and @ContentChildren queries. ngAfterViewInit runs once after the component's own view and its child components are initialized, at which point @ViewChild and @ViewChildren queries are resolved.

Use the content hook to work with projected children (for example, a tabs component reading its tab children). Use the view hook to work with elements in your own template (for example, measuring a canvas). Changing bound state inside ngAfterViewInit can trigger ExpressionChangedAfterItHasBeenCheckedError. DOM work that does not change bindings fits better in afterNextRender.


21. What are afterNextRender and afterEveryRender (afterRender), and when should you use them instead of lifecycle hooks?

These functions register callbacks that run after Angular has rendered the DOM across the whole application. afterNextRender runs once, after the next render. afterEveryRender, called afterRender in earlier versions, runs after every render. They must be called in an injection context and they never run on the server, which makes them the right place for browser-only code.

Use them for direct DOM manipulation or measurement, for initializing third-party libraries (charts, editors), and for code that touches window or document. You can split work into phases (earlyRead, write, mixedReadWrite, read) to avoid layout thrashing. Lifecycle hooks remain the right tool for component-specific logic tied to inputs and queries.


22. Explain view encapsulation. What are the differences between Emulated, ShadowDom, and None?

View encapsulation controls whether a component's styles leak in or out. Emulated is the default: Angular rewrites component CSS selectors with generated attributes (such as _ngcontent-abc), so styles apply only to that component's template, while global styles can still reach in.

ShadowDom uses the browser's native Shadow DOM, which gives true isolation: global styles do not penetrate, and you use ::part or CSS custom properties to theme. None disables encapsulation, so the component's styles become global. That is sometimes useful for theming third-party content, but it risks collisions. A fourth legacy option, Native, has been removed.


23. What is content projection? Explain single-slot, multi-slot (select), and conditional projection.

Content projection lets a parent pass markup into a child component's template through the <ng-content> placeholder, much like slots in Web Components. Single-slot projection uses one <ng-content> that receives everything. Multi-slot projection uses several <ng-content select="..."> elements with CSS selectors (element, attribute, or class) to route content to specific places, plus a default slot for the rest. ngProjectAs can make content match a selector it would not otherwise match.

ng-content is always initialized, even if it sits inside an @if, so it is not truly conditional. For conditional or repeated projection, the parent passes an <ng-template> that the child queries with contentChild(TemplateRef) and renders with ngTemplateOutlet only when needed. ng-content also supports fallback content written between its tags.


24. What is the difference between @ViewChild and @ContentChild? What does the static option do?

@ViewChild queries elements, directives, or components declared in the component's own template. @ContentChild queries elements that were projected into the component from its parent via ng-content. View queries resolve before ngAfterViewInit, and content queries resolve before ngAfterContentInit.

static: true resolves the query before change detection runs, making it available in ngOnInit. This works only if the target is not inside a structural directive or control-flow block such as @if. The default, static: false, resolves after change detection and updates if the result changes. The read option lets you retrieve a different token from the matched node, such as ElementRef or ViewContainerRef.


25. How do the signal-based queries differ from their decorator equivalents?

viewChild(), viewChildren(), contentChild(), and contentChildren() return signals instead of assigning class properties. viewChild returns Signal<T | undefined>, viewChild.required throws if the result is missing when you read it, and the plural forms return Signal<ReadonlyArray<T>>.

Because they are signals, you can derive state with computed() and react with effect() without timing guesswork in ngAfterViewInit. They work naturally with OnPush and zoneless change detection, are fully typed, and support the read option. There is no static flag; the signal simply updates whenever the query result changes.


26. What is a QueryList, and how do you react to changes in it?

QueryList is the live, iterable collection that @ViewChildren and @ContentChildren populate. It exposes array-like methods (map, filter, forEach, toArray, first, last, length) and updates when matching elements are added or removed, for example by @for or @if.

To react to changes, subscribe to queryList.changes, an observable that emits the QueryList on each update, and remember to unsubscribe. With signal queries you get a signal of an array instead, so computed() or effect() replaces the changes subscription.


27. Explain the differences between ng-template, ng-container, and ng-content.

<ng-template> defines a chunk of template that is not rendered by default. Code renders it through structural directives, ngTemplateOutlet, or ViewContainerRef.createEmbeddedView, and it can accept a context. <ng-container> is a logical grouping element that renders no DOM node of its own. Use it to apply a directive, or to group siblings, without adding an extra wrapper element.

<ng-content> is a projection slot inside a component's template. It marks where content passed from the parent should appear. In short: ng-template is a deferred blueprint, ng-container is an invisible wrapper, and ng-content is a slot for parent-supplied content.


28. What are template reference variables, and what can they refer to?

A template reference variable is declared with a hash, such as #name. It gives you a handle to something in the template that you can use elsewhere in the same template.

On a plain element it refers to the DOM element. On a component it refers to the component instance. On an <ng-template> it refers to a TemplateRef. With exportAs syntax (#f="ngForm", #m="matMenu") it refers to that directive instance. Variables are scoped to their template, and those declared inside structural blocks are not visible outside them. They are also the selectors used by @ViewChild('name') and viewChild('name').


29. How do you create components dynamically?

The most common approach is to inject or query a ViewContainerRef and call createComponent(MyComponent). This returns a ComponentRef, on which you can call setInput('name', value), subscribe to outputs through instance, and call destroy(). Newer versions also accept bindings such as inputBinding() and outputBinding() and extra directives directly in createComponent options. Because Ivy no longer needs entryComponents, any standalone component can be created this way.

Declaratively, NgComponentOutlet renders a component type from the template: <ng-container *ngComponentOutlet="cmp; inputs: data" />. To create a component outside any view, for example to attach it to document.body, use the standalone createComponent() function with an EnvironmentInjector and then attach its hostView to ApplicationRef. CDK Portals and Overlay are higher-level abstractions over the same ideas.


30. List every way a parent and child component can communicate, and when you would choose each.

Parent-to-child communication uses inputs: input(), model(), or @Input. Child-to-parent communication uses outputs: output() or @Output with EventEmitter. model() provides two-way binding. These cover most direct parent–child cases.

A parent can also access a child directly with viewChild or a template reference variable and call its methods. That is useful for imperative APIs such as focus() or open(), but it creates tight coupling. A child can inject an ancestor component or directive through DI, which is the pattern behind compound components such as tabs and accordions.

For distant or sibling components, use a shared service holding signals or Subjects, ideally scoped to the nearest common provider. You can also use router state and URL params, or a state management library. Prefer inputs and outputs for presentation components and services for cross-cutting state.


31. What is the host element? How do :host and :host-context selectors work in component styles?

The host element is the DOM element that matches the component's selector, such as <app-card>. The component's template renders inside it. By default it is an inline element with no styles.

In component CSS, :host targets the host element itself, and :host(.active) applies only when the host has that class. :host-context(.dark-theme) applies styles when any ancestor of the host matches the selector, which is useful for themes. Host classes and attributes can be set with the host metadata property, for example host: { class: 'card', '[class.active]': 'isActive()' }.


32. What is ::ng-deep, why is it discouraged, and what are the alternatives?

::ng-deep disables style encapsulation for the rest of a selector, so a component can style elements inside child components. :host ::ng-deep .mat-x is a common example. It has been deprecated for years, though no replacement exists and it still works.

It is discouraged because it couples your styles to another component's internal DOM structure. Without :host in front it leaks globally, and it breaks easily when libraries change their markup. Alternatives include CSS custom properties exposed by the child, a component's theming API (such as Material's Sass mixins and design tokens), global stylesheets with specific selectors, ::part() with Shadow DOM, or ViewEncapsulation.None on a small wrapper.


33. What is the built-in control flow syntax, and how does it improve on *ngIf, *ngFor, and ngSwitch?

Built-in control flow uses @if / @else if / @else, @for with @empty, and @switch / @case / @default blocks directly in the template, compiled by Angular itself. You do not import anything to use them.

The improvements are clearer syntax (real else-if chains, no ng-template for else), better type narrowing in templates, and a mandatory track expression for loops, which prevents a common performance bug. @for also provides an @empty block and implicit variables such as $index, $first, $last, $even, $odd, and $count. Performance improves too, especially in loops, along with smaller bundles and a smooth path to zoneless. A migration schematic (ng generate @angular/core:control-flow) converts the old directives.


34. Why does @for require a track expression, and how does it compare to the old trackBy function?

When a list changes, Angular has to decide which existing DOM nodes to keep, move, or destroy. The track expression supplies a stable identity for each item, such as track item.id, so Angular can reuse DOM and component state instead of recreating rows. Making it mandatory stops developers from accidentally causing full re-renders and losing focus, scroll, or component state.

trackBy did the same job in *ngFor, but it was optional, required writing a separate function in the class, and was frequently forgotten. track is a simple inline expression. Use a unique id when you have one. track $index is acceptable for static lists, and tracking by the object itself (track item) works only if references stay stable.


35. What is @defer? Describe its triggers and its sub-blocks.

@defer lazily loads the components, directives, and pipes used inside it. The compiler splits their code into a separate chunk that is fetched only when a trigger fires. Dependencies must be standalone and not referenced elsewhere in the same file for the split to happen.

The triggers are on idle (the default, via requestIdleCallback), on viewport (the element enters the viewport), on interaction (click or keydown), on hover, on immediate, on timer(500ms), and when someCondition (a boolean expression). prefetch on ... loads the code earlier than it renders. Several triggers can be combined.

The sub-blocks are @placeholder, shown before loading and optionally with minimum, @loading, shown while fetching and optionally with after and minimum to avoid flicker, and @error, shown if loading fails. With SSR and incremental hydration, hydrate on ... triggers control when server-rendered deferred content becomes interactive.

SECTION 3: DATA BINDING & DIRECTIVES (36–50)
------------------------------------------------------------------

36. Explain the four forms of data binding in Angular with examples.

Interpolation, {{ user.name }}, renders a value as text. Property binding, [disabled]="isSaving", sets a DOM or component property from an expression. Event binding, (click)="save()", calls a handler when an event fires and can access $event.

Two-way binding, [(ngModel)]="name" or [(value)]="count" with model(), combines a property binding and an event binding so values flow in both directions. The first two flow from the component to the view, event binding flows from the view to the component, and two-way binding does both.


37. What is the difference between property binding and attribute binding ([attr.x])?

Property binding sets a DOM element property, such as [value] or [hidden], or a component input. Many HTML attributes have matching DOM properties, but not all do, and some behave differently. An attribute only initializes a value, while the property holds the current value.

Attribute binding, [attr.aria-label]="label" or [attr.colspan]="2", sets an HTML attribute directly. Use it for attributes with no corresponding property, such as ARIA attributes, colspan, data-* attributes, and SVG attributes. Binding null or undefined removes the attribute.


38. How does two-way binding work under the hood ("banana in a box" [( )])?

[(x)]="value" is syntactic sugar for [x]="value" (xChange)="value = $event". The child exposes an input named x and an output named xChange, and when the child emits, the parent's expression is assigned the new value.

model() creates this input-and-output pair for you as a writable signal. Setting it in the child emits the change. In the parent you can bind a plain property or a writable signal, and Angular writes back to the signal. ngModel follows the same pattern through its ngModelChange event.


39. How do class and style bindings work, including binding to multiple classes at once?

Single bindings look like [class.active]="isActive" and [style.width.px]="width"; the second form appends the unit. For multiple classes, [class]="expr" accepts a string ("a b"), an array, or an object ({ active: isActive, disabled: !enabled }). [style]="{ 'font-size.px': 14, color: c }" accepts a string or an object.

Angular merges these bindings with static classes and host bindings using defined precedence rules: template bindings beat host bindings, and specific bindings beat map bindings. These native bindings cover nearly everything NgClass and NgStyle did, without importing a directive.


40. What is the @let template syntax, and what problems does it solve?

@let declares a read-only local variable in a template, for example @let user = user$ | async; or @let total = price() * qty();. The variable is scoped to the current view and its children and is re-evaluated on each change detection.

It removes awkward workarounds. Before @let, developers used *ngIf="obs$ | async as x" just to alias a value, which broke on falsy values. It also avoids repeating a long expression or async pipe several times. It improves readability, but complex logic still belongs in computed signals in the class.


41. What is a directive? Name the three types of directives in Angular.

A directive is a class that adds behavior to elements in a template. Angular matches it by selector, and it can have inputs, outputs, host bindings, lifecycle hooks, and injected dependencies.

The three types are components (directives with a template), attribute directives (which change the appearance or behavior of an existing element, such as NgClass or a custom highlight directive), and structural directives (which change the DOM layout by adding or removing elements through templates, such as *ngIf, *ngFor, and custom ones).


42. What is the difference between structural and attribute directives?

Structural directives shape the DOM. They inject TemplateRef and ViewContainerRef and decide whether and how many times to render a template, and they are applied with the * prefix. Only one structural directive can sit on an element, so you wrap with ng-container when you need two.

Attribute directives modify the element they are placed on, for example by changing classes, styles, attributes, or event handling. They typically inject ElementRef or use host bindings. Any number can be combined on one element. Since built-in control flow arrived, most structural use cases are written as @if and @for blocks rather than directives.


43. Write a custom attribute directive that highlights an element on hover.

Example:
@Directive({ selector: '[appHighlight]', host: { '(mouseenter)': 'active.set(true)', '(mouseleave)': 'active.set(false)', '[style.backgroundColor]': 'active() ? color() : null' } })
export class HighlightDirective { color = input('yellow', { alias: 'appHighlight' }); active = signal(false); }

Usage: <p appHighlight="lightblue">Hover me</p>. It uses the host metadata for listeners and bindings instead of touching ElementRef directly, which keeps it SSR-safe. An equivalent older version would use @HostListener and Renderer2.setStyle.


44. How do you write a custom structural directive? What is the microsyntax?

Inject TemplateRef (the content to render) and ViewContainerRef (where to render it), then call viewContainer.createEmbeddedView(templateRef, context) or viewContainer.clear() as inputs change. An *appUnless directive, for example, renders the template when the condition is false. Add static ngTemplateContextGuard to get type-checked context variables.

Microsyntax is the mini-language inside a * attribute. For example, *appRepeat="let item of items; index as i; trackBy: fn" maps to inputs named after the directive prefix (appRepeatOf, appRepeatTrackBy) and to let-variables that read context properties ($implicit, index). Understanding it lets you design directives with ngFor-style syntax.


45. What does the asterisk (*) prefix desugar to in a template?

The asterisk wraps the host element in an <ng-template> and moves the directive binding onto that template. <div *ngIf="show">Hi</div> becomes <ng-template [ngIf]="show"><div>Hi</div></ng-template>.

Microsyntax expressions expand into more inputs and template variables. *ngFor="let x of list; let i = index" becomes <ng-template ngFor let-x [ngForOf]="list" let-i="index">. This is why only one structural directive is allowed per element: each one needs its own template wrapper.


46. Compare @HostListener/@HostBinding with the host property in component or directive metadata. Which is recommended now and why?

@HostListener('click', ['$event']) on a method and @HostBinding('class.active') on a property declare host interactions next to the code they affect. The host metadata property declares the same things in one object: host: { '(click)': 'onClick($event)', '[class.active]': 'isActive()', role: 'button' }.

The current style guide recommends the host property. It keeps all host interactions in one place, supports static attributes, works naturally with signals because expressions are evaluated like template bindings, and is checked by the template compiler. The decorators still work and remain common in existing code.


47. What is the directive composition API (hostDirectives), and when is it useful?

hostDirectives lets a component or directive apply other standalone directives to its own host element, as in hostDirectives: [{ directive: CdkDrag, inputs: ['cdkDragData'], outputs: ['cdkDragEnded'] }]. The listed directives are instantiated with the host and can share DI.

It is useful for composing reusable behaviors (focus management, tooltips, ARIA patterns, drag) into components without inheritance or making consumers add several attributes. You choose explicitly which inputs and outputs to expose, optionally with aliases. Host directives must be standalone, and they are applied statically at compile time.


48. What does ngTemplateOutlet do, and how do you pass a context object to it?

ngTemplateOutlet renders a TemplateRef at a given location. This is how you reuse a template fragment or let a parent supply a template for a child to render, a pattern called templates as inputs.

You pass a context with <ng-container *ngTemplateOutlet="rowTpl; context: { $implicit: row, index: i }" />. In the template, let-row receives $implicit and let-i="index" receives the named property. ngTemplateOutletInjector can supply a custom injector. This is the basis of customizable list, table, and dropdown components.


49. When would you use ngClass/ngStyle versus native [class] and [style] bindings?

Native [class] and [style] bindings now accept strings, arrays, and objects, need no import, are a little faster, and are recommended for new code. They cover essentially every NgClass and NgStyle use case.

NgClass and NgStyle remain fine in existing code and can be slightly more convenient in rare cases, such as keys that contain several space-separated class names. Prefer the native bindings for new standalone components and leave the directive versions in older code unless you are already refactoring it.


50. What is strict template type checking (strictTemplates), and why should you enable it?

strictTemplates, set in angularCompilerOptions, makes the compiler type-check templates as rigorously as TypeScript code. It checks input binding types, $event types, the types of template variables from @for and @if, null-safety, and DOM event types.

Enable it because it catches whole classes of bugs at build time, such as passing a string to a number input, misspelled properties, and unsafe null access. It also improves IDE autocompletion. New CLI projects enable it by default. Related flags such as strictInputAccessModifiers and extendedDiagnostics add further checks.

SECTION 4: PIPES (51–58)
------------------------------------------------------------------

51. What is a pipe? Name several built-in pipes.

A pipe is a class decorated with @Pipe whose transform() method converts a value for display in a template, using the | operator: {{ price | currency:'EUR' }}. Pipes keep formatting logic out of components and out of templates.

Built-in pipes include DatePipe, UpperCasePipe, LowerCasePipe, TitleCasePipe, CurrencyPipe, DecimalPipe (number), PercentPipe, JsonPipe, SlicePipe, AsyncPipe, KeyValuePipe, I18nPluralPipe, and I18nSelectPipe. In standalone components you import each pipe you use, such as DatePipe, or CommonModule.


52. What is the difference between pure and impure pipes? What are the performance implications?

A pure pipe, the default, is re-executed only when its input value or arguments change by reference (or for primitives, by value). Angular caches the result, so a pure pipe is very cheap. Mutating an array in place does not re-run a pure pipe.

An impure pipe (pure: false) runs on every change detection cycle, which can be expensive if the transform does real work. Impure pipes are needed when the output depends on mutable or external state; AsyncPipe and JsonPipe are impure for that reason. Prefer pure pipes with immutable data, and keep impure transforms lightweight or memoized.


53. Walk through creating a custom pipe, including parameters.

Example:
@Pipe({ name: 'truncate' })
export class TruncatePipe implements PipeTransform { transform(value: string, limit = 20, suffix = '…'): string { return value.length > limit ? value.slice(0, limit) + suffix : value; } }

Import it into a component's imports array and use it as {{ text | truncate:50:'...' }}. Each argument after the colon maps to a transform parameter in order. Pipes can use inject() for services such as a translation service or LOCALE_ID. Generate the skeleton with ng g pipe truncate.


54. How does the async pipe work, and what are its advantages over manual subscription?

The async pipe subscribes to an Observable or Promise, returns the latest emitted value, and calls markForCheck() on each emission so OnPush components update. When the component is destroyed or the expression switches to a new source, it unsubscribes automatically.

It removes subscription boilerplate and memory leaks and works with OnPush out of the box. It keeps templates declarative, for example @if (user$ | async; as user). Each use of the pipe creates its own subscription, so alias the value with @let or as, or share the stream, to avoid duplicate HTTP calls. In signal-first code, toSignal() serves a similar role.


55. How do you chain pipes and pass multiple arguments to a pipe?

Chain pipes left to right: {{ birthday | date:'longDate' | uppercase }}. The output of each pipe becomes the input of the next. The pipe operator has higher precedence than the ternary operator, so use parentheses when combining them.

Pass several arguments separated by colons: {{ value | slice:1:5 }} or {{ amount | currency:'USD':'symbol':'1.0-0' }}. Arguments can be any template expression, including signal reads and component properties.


56. Why is using a pipe usually better than calling a method in a template?

A method call in a template such as {{ formatName(user) }} runs on every change detection cycle, because Angular cannot know whether its result changed. For costly logic that hurts performance, especially inside large @for lists.

A pure pipe re-runs only when its inputs change, so its result is effectively memoized per binding. Pipes are also reusable across components and easy to unit test. Computed signals offer the same memoization in the class (formattedName = computed(...)), and reading a signal in a template is cheap.


57. How can you use a pipe inside TypeScript code rather than a template?

You can provide the pipe and inject it, for example providers: [DatePipe] followed by private datePipe = inject(DatePipe), and then call this.datePipe.transform(date, 'short'). You can also instantiate a pipe with new when it has no dependencies.

For built-in formatting, Angular exports standalone functions, formatDate, formatNumber, formatCurrency, and formatPercent from @angular/common, which take a locale argument. These are usually cleaner than injecting the pipe. If you need the same logic in both a pipe and a service, extract it into a plain function both can call.


58. How do locale-sensitive pipes use LOCALE_ID?

DatePipe, CurrencyPipe, DecimalPipe, and PercentPipe format according to the LOCALE_ID injection token, which defaults to en-US. They use locale data for separators, month names, and currency symbol position, and each pipe accepts an optional locale argument for a single call.

To change the default, provide { provide: LOCALE_ID, useValue: 'de-DE' } and register the locale data with registerLocaleData(localeDe) for runtime use. With @angular/localize builds, the locale is set per build automatically. DEFAULT_CURRENCY_CODE sets the default currency, and DATE_PIPE_DEFAULT_OPTIONS sets the date pipe's default format and timezone.

SECTION 5: DEPENDENCY INJECTION & SERVICES (59–78)
------------------------------------------------------------------

59. What is dependency injection, and why does Angular rely on it?

Dependency injection is a design pattern in which a class receives its dependencies from an external injector instead of creating them. Angular has a built-in hierarchical DI system that resolves dependencies from tokens (class types or InjectionTokens) and provider configuration.

Angular relies on DI because it decouples classes from concrete implementations. It makes testing easy, since you swap real services for mocks, controls the lifetime and sharing of instances (singletons or per-component instances), and allows configuration through tokens. Much of the framework itself is delivered and configured through DI, including Router, HttpClient, and interceptors.


60. What is a service, and what does @Injectable({ providedIn: 'root' }) do?

A service is a class that holds logic or state not tied to a single view, such as data access, business rules, logging, or shared state. It is usually decorated with @Injectable so Angular can inject it and its own dependencies.

providedIn: 'root' registers the service with the application's root environment injector. You get one shared singleton for the whole app, created lazily the first time it is injected. Because the registration lives on the service itself, the service is tree-shakable: if nothing injects it, it is removed from the bundle.


61. Compare providedIn: 'root', 'platform', 'any', and providing a service at the component level.

'root' gives one instance per application, which is the usual choice. 'platform' gives one instance shared by every Angular application on the page through the platform injector, which matters only in rare multi-app or micro-frontend scenarios. 'any' gave one instance per lazy-loaded environment injector. It is deprecated because it was confusing; use route-level providers instead.

Listing a service in a component's providers array creates a new instance for each component instance, shared by that component's children. Use this for state that should live and die with a piece of UI, such as a form wizard's state or per-row editing state. That instance is destroyed with the component.


62. Explain the injector hierarchy: environment injectors versus element (node) injectors.

Environment injectors form one tree. The platform injector sits at the top, then the root environment injector, configured by bootstrapApplication providers and providedIn: 'root', and then child environment injectors created by lazy-loaded routes with providers or by createEnvironmentInjector. They hold application-level services.

Element injectors form a second tree that parallels the component and DOM tree. Each element with a component or directive that has providers or viewProviders gets one. During resolution Angular first walks up the element injector tree from the requesting node. If the token is not found there, it continues into the environment injector tree, starting from the injector associated with that view. This two-phase lookup explains scoping behavior and most "No provider for X" errors.


63. How does Angular resolve a dependency? Explain the resolution modifiers @Optional, @Self, @SkipSelf, and @Host.

By default Angular looks for the token on the current element's injector, walks up through ancestor element injectors, and then searches the environment injectors up to root and platform. If nothing provides the token, it throws NullInjectorError.

@Optional (inject(X, { optional: true })) returns null instead of throwing. @Self (self: true) looks only on the current element injector. @SkipSelf (skipSelf: true) starts the search at the parent, which is useful for a nested component that wants its parent's instance, as in recursive menus. @Host (host: true) stops the search at the host component boundary, so a directive cannot reach beyond its host's view. These modifiers can be combined, for example optional with skipSelf.


64. What is the inject() function, how does it differ from constructor injection, and what is an injection context?

inject(Token) returns the dependency for a token, as in private http = inject(HttpClient). Constructor injection declares the same dependencies as constructor parameters. inject() works without parameter decorators, plays better with class inheritance (no super(...) chains), allows field-initializer style, and can be used in plain functions such as functional guards, interceptors, and resolvers.

An injection context is a period during which an injector is available. That includes class construction (field initializers and the constructor) for anything DI creates, factory functions for providers, router guard and resolver functions, and code inside runInInjectionContext. Calling inject() outside one, for example in ngOnInit or a setTimeout callback, throws an error. assertInInjectionContext() lets your own helpers enforce the rule.


65. What is an InjectionToken, and when should you use one?

An InjectionToken<T> is a unique DI key for something that is not a class, such as a configuration object, a primitive, a function, or an interface type, since interfaces do not exist at runtime. Create one with export const API_URL = new InjectionToken<string>('API_URL').

Provide it with { provide: API_URL, useValue: 'https://api.example.com' } and inject it with inject(API_URL). The token can also declare a default through a factory: new InjectionToken('X', { providedIn: 'root', factory: () => ... }), which makes it tree-shakable. Use tokens for configuration, abstractions, and plugin points created with multi providers.


66. Explain the provider recipes useClass, useValue, useFactory, and useExisting.

useClass, as in { provide: Logger, useClass: ConsoleLogger }, creates an instance of the given class for the token, letting you substitute an implementation. useValue, as in { provide: CONFIG, useValue: { retries: 3 } }, supplies a ready-made value such as a constant, configuration, or mock object.

useFactory, as in { provide: Storage, useFactory: () => isBrowser() ? localStorage : memoryStorage() }, calls a function to build the value. The function can call inject() (older code used a deps array) and suits conditional or computed dependencies. useExisting, as in { provide: OldLogger, useExisting: NewLogger }, aliases one token to another so both resolve to the same instance. It is commonly used for exposing abstract tokens such as NG_VALUE_ACCESSOR.


67. What do multi: true providers do? Give a real-world example.

With multi: true, several providers for the same token are collected into an array instead of the last one replacing the others. Injecting the token returns all registered values.

Angular itself uses this for NG_VALIDATORS, NG_VALUE_ACCESSOR, HTTP_INTERCEPTORS (class-based interceptors), and ENVIRONMENT_INITIALIZER. A real-world example is a plugin system: each feature registers { provide: DASHBOARD_WIDGETS, useValue: WeatherWidget, multi: true }, and the dashboard injects DASHBOARD_WIDGETS to render all of them without knowing about each feature.


68. What is the difference between providers and viewProviders?

Services in a component's providers array are visible to the component, to the children in its own template, and to content projected into it from a parent. Services in viewProviders are visible only to the component and its view children, not to projected content.

Use viewProviders when a component's internal services should stay private, so that content projected by consumers cannot inject them or accidentally receive them. This matters mostly for reusable library components that both project content and keep internal state services.


69. How do you guarantee a service is a singleton, and what pitfalls arise with lazy-loaded routes?

Use @Injectable({ providedIn: 'root' }) and do not list the service in any other providers array. Angular then creates exactly one instance in the root injector.

The pitfalls come from providing the service again elsewhere. If a lazy-loaded route's providers, a lazy NgModule's providers, or a component's providers include the service, a second instance is created in that child injector, and the lazy feature silently sees different state. Libraries can cause the same problem when importing their module calls forRoot-style providers more than once. The fix is to provide singletons only at root, use forRoot()/forChild() conventions for modules, and keep route-level providers for services that are meant to be scoped to the feature.


70. What is runInInjectionContext, and when do you need it?

runInInjectionContext(injector, fn) runs fn with the given injector as the current injection context, so inject(), toSignal(), effect(), and takeUntilDestroyed() work inside it.

You need it when you must create injection-dependent things outside construction time. Examples include creating an effect or toSignal in ngOnInit or in response to an event, and calling a helper that uses inject() from a callback. You usually get the injector from inject(Injector) or EnvironmentInjector, and TestBed.runInInjectionContext offers the same in tests. Many APIs, such as effect and toSignal, also accept an { injector } option directly.


71. What is forwardRef, and when is it required?

forwardRef(() => SomeClass) wraps a reference in a function so it is resolved lazily. Angular calls the function when it needs the value.

It is needed when a class is referenced before it is defined in the same file. The classic case is a component that provides itself, as in providers: [{ provide: NG_VALUE_ACCESSOR, useExisting: forwardRef(() => MyInputComponent), multi: true }], because the decorator is evaluated before the class body is assigned. It is also used for circular references between classes. It cannot fix true circular DI dependencies, where A needs B at construction and B needs A.


72. What are tree-shakable providers, and why do they matter for bundle size?

A tree-shakable provider declares its own registration, either @Injectable({ providedIn: 'root' }) or an InjectionToken with providedIn and a factory. Nothing else needs to reference the service for it to be available.

Because the only references to the service are its injection sites, the bundler can remove it completely if nothing injects it. With the older approach of listing services in an NgModule's providers array, the module referenced every service and kept them all in the bundle whether or not they were used. This matters most for large libraries and shared code.


73. How do you swap a service implementation for testing or for different environments?

In tests, override the provider with TestBed.configureTestingModule({ providers: [{ provide: UserService, useValue: mockUserService }] }) or with useClass: FakeUserService. You can also use TestBed.overrideProvider or overrideComponent for component-level providers.

For environments, provide based on configuration: { provide: Analytics, useClass: environment.production ? GoogleAnalytics : NoopAnalytics }. A useFactory can read a runtime config token, and an abstract class or InjectionToken can serve as the contract. Depending on abstractions rather than concrete classes makes these swaps clean.


74. What is provideAppInitializer (formerly APP_INITIALIZER), and what is it used for?

provideAppInitializer(() => { ... }) registers a function that runs during application bootstrap, before the root component is rendered. If it returns a Promise or Observable, bootstrap waits for it to finish. inject() works inside it. It replaces the older multi provider { provide: APP_INITIALIZER, useFactory, multi: true }, which is now deprecated.

Typical uses are loading runtime configuration (for example config.json for a build-once, deploy-anywhere setup), restoring an auth session, loading translations, or initializing feature flags. Keep initializers fast, because they delay first render. provideEnvironmentInitializer and providePlatformInitializer cover the equivalent hooks for environment and platform injectors.


75. What is DestroyRef, and how does takeUntilDestroyed() use it?

DestroyRef is an injectable that represents the lifetime of the current context, such as a component, directive, service, or environment injector. destroyRef.onDestroy(callback) registers cleanup and returns a function that unregisters it. It is a composable alternative to implementing ngOnDestroy.

takeUntilDestroyed(), from @angular/core/rxjs-interop, is an RxJS operator that completes the stream when the associated DestroyRef is destroyed. Called in an injection context, as in obs$.pipe(takeUntilDestroyed()).subscribe(...) in a field initializer or constructor, it picks up DestroyRef automatically. Elsewhere you pass a DestroyRef explicitly: takeUntilDestroyed(this.destroyRef). It replaces the old destroy$ Subject pattern.


76. How do you manage environment-specific configuration?

The traditional approach uses src/environments/environment.ts and environment.prod.ts (create them with ng generate environments) and fileReplacements in angular.json, which swaps the file at build time per configuration. This is simple, but you need a separate build for each environment.

For build-once, deploy-anywhere, load configuration at runtime. Fetch /config.json in provideAppInitializer, store it in a service or InjectionToken, and have the deployment pipeline write that file for each environment. Never put secrets in either kind of configuration, because everything shipped to the browser is public. Use build-time environments only for values that are truly fixed per build.


77. How do route-level providers work, and what scope do they have?

Adding providers: [...] to a Route makes the router create a child EnvironmentInjector for that route. It is created when the route is first activated, or when it is loaded, for lazy routes. The route's component and all its child routes resolve services from that injector before falling back to root.

The scope is the route subtree. Services there are shared by that feature's components and are instantiated only when the feature is used. That makes route-level providers ideal for feature state, feature-specific NgRx feature stores, or overriding a configuration token for one section of the app. These injectors currently live as long as the application rather than being destroyed on navigation away, so state in them persists between visits.


78. How would you build a library-style provideX() function using makeEnvironmentProviders?

Export a function that returns makeEnvironmentProviders([...]). For example:
export function provideAnalytics(config: AnalyticsConfig) { return makeEnvironmentProviders([{ provide: ANALYTICS_CONFIG, useValue: config }, AnalyticsService, provideEnvironmentInitializer(() => inject(AnalyticsService).init())]); }

Consumers add provideAnalytics({ key: '...' }) to app.config or to route providers. The EnvironmentProviders type cannot be placed in a component's providers array, so the compiler prevents misuse. Optional features can follow Angular's own pattern, provideX(withFeatureA(), withFeatureB()), where each with* function returns a typed feature object.

SECTION 6: SIGNALS & REACTIVITY (79–98)
------------------------------------------------------------------

79. What are signals, and what problems do they solve in Angular?

A signal is a reactive wrapper around a value that notifies its consumers when the value changes. You read it by calling it, count(), and when a template or computed reads it, Angular automatically records the dependency.

Signals solve the coarse-grained nature of Zone.js-based change detection, which re-checked whole component trees after any async event without knowing what changed. Because signals know exactly which views depend on which state, Angular can update only those views. That enables zoneless applications, simpler OnPush usage, and less RxJS boilerplate for synchronous state. They also give glitch-free, synchronous derived state through computed().


80. Explain the differences between signal(), computed(), and effect().

signal(initial) creates a WritableSignal that you change with set() or update(). computed(() => a() + b()) creates a read-only derived signal. It is evaluated lazily, recalculates only when one of the signals it read changes, and memoizes its result.

effect(() => { ... }) registers a side effect that runs whenever the signals it read change, for example syncing to localStorage, logging, or calling a non-reactive API. Effects run asynchronously as part of Angular's scheduling, must be created in an injection context, and are cleaned up with their owner. The rule of thumb is that state goes in signals, derived values in computed, and side effects reaching outside the reactive graph in effects.


81. How does a computed signal track its dependencies and memoize its value?

When a computed's function runs, Angular records every signal read during that execution as a dependency. Dependencies are dynamic: if a branch is not taken, the signals in it are not tracked on that run.

When a dependency changes, the computed is marked stale but not recalculated. It recalculates only when someone reads it, which makes it lazy. After recalculating, if the new value is equal to the old one according to the equality function, its own consumers are not notified, which prunes unnecessary updates. Results are cached between reads, so reading a computed many times is cheap.


82. When are effects appropriate, and when are they an anti-pattern?

Effects are appropriate for synchronizing signal state with the outside world. Examples include writing to localStorage, logging or analytics, imperatively updating a third-party chart or canvas, and keeping a non-signal API in sync.

They are an anti-pattern when used to propagate state from one signal to another, as in effect(() => this.b.set(this.a() * 2)). That creates extra change detection cycles, ordering surprises, and possible loops. Use computed() for derived values, linkedSignal() for state that resets when a source changes, and resource() for async derivations. If you find yourself writing to signals in an effect, reconsider the design.


83. What is the difference between set() and update() on a WritableSignal? Why should you avoid mutating objects held in a signal?

set(value) replaces the value outright. update(fn) computes the new value from the current one, as in count.update(c => c + 1), which is convenient and avoids reading and then writing separately.

Signals use Object.is equality by default. If you mutate an object or array in place, for example items().push(x), the reference does not change. Consumers are not notified, and computeds and OnPush views show stale data. Always produce a new reference instead: items.update(list => [...list, x]) or user.update(u => ({ ...u, name })). The older mutate() method was removed for exactly this reason.


84. How and why would you provide a custom equality function to a signal?

Pass it in the options: signal(initial, { equal: (a, b) => a.id === b.id }). The same option works for computed(). The function decides whether a new value counts as a change. If it returns true, dependents are not notified.

This is useful to avoid needless downstream recomputation and re-rendering when a new object is structurally the same. A common case is an API that returns a fresh object with identical data on every poll, which you can compare with a deep-equal or id/version check. Keep the comparison cheap, because it runs on every write. You can also deliberately notify on every set by using equal: () => false.


85. What does untracked() do, and give a scenario where you need it.

untracked(() => expr) reads signals without registering them as dependencies of the current reactive context. Inside an effect or computed, the code it wraps can read values without causing re-runs when they change.

A typical scenario is an effect that should run when userId() changes and needs the current filter value, but should not re-run when the filter changes: effect(() => { const id = userId(); untracked(() => this.load(id, this.filter())); }). It also matters when calling service methods from an effect that internally read signals you do not want to subscribe to by accident.


86. How do signal inputs differ from @Input()?

name = input<string>() declares an optional input that returns a read-only Signal<string | undefined>. input('default') supplies a default value, and input.required<User>() requires the parent to bind it, which the compiler checks. Options include alias and transform, for example input(false, { transform: booleanAttribute }).

Compared with @Input, signal inputs are reactive by default, so you derive state with computed instead of using ngOnChanges or setters. Their types are more precise, required inputs are checked at compile time, and they are read-only inside the component, which prevents accidental mutation. They also integrate with OnPush and zoneless change detection. If the child needs to write back, use model().


87. How does the output() function differ from @Output() with EventEmitter?

saved = output<User>() returns an OutputEmitterRef. You call saved.emit(user), and parents bind (saved)="onSave($event)" exactly as before. Options include alias.

Unlike EventEmitter, which extends RxJS Subject, output() has no RxJS dependency and is not an Observable. It exposes a simple subscribe() for programmatic listeners and completes when the directive is destroyed. outputFromObservable(stream$) declares an output driven by an existing Observable, and outputToObservable(ref) converts back. It is lighter, more type-safe, and consistent with the signal-based APIs.


88. What is model(), and how does it enable two-way binding with signals?

value = model<number>(0) declares a writable signal that is also an input, with an automatically created output named valueChange. Inside the child you call value.set(5) or value.update(v => v + 1), and the change is emitted to the parent.

The parent can bind [(value)]="count", where count is a plain property or a WritableSignal; with a signal, Angular writes the new value back into it. model.required() makes the binding mandatory. It replaces the hand-written pair of @Input value plus @Output valueChange and is ideal for custom controls such as toggles, sliders, and pickers.


89. What is linkedSignal, and what use case does it address?

linkedSignal creates a writable signal whose value is derived from a source but can also be set locally. When the source changes, the linked signal resets to a recomputed value. For example: selected = linkedSignal(() => this.options()[0]). The longer form, linkedSignal({ source, computation: (src, prev) => ... }), gives access to the previous value.

It addresses "derived but overridable" state. Examples include a default selection that the user can change but that resets when the option list changes, or pagination that returns to page 1 when filters change. Without it, developers wrote effects that set signals, which is the anti-pattern described in question 82.


90. What are resource(), rxResource(), and httpResource(), and how do they handle async data?

resource({ params: () => ({ id: this.id() }), loader: ({ params, abortSignal }) => fetch(...) }) turns async loading into signals. In earlier versions the params option was called request. Whenever params change, it calls the loader, aborts the previous request, and exposes value(), status(), isLoading(), error(), hasValue(), and reload(). You can also set its value locally.

rxResource is the same but takes an Observable-returning stream function, which suits HttpClient and RxJS pipelines. httpResource(() => `/api/users/${this.id()}`) is a thin wrapper over HttpClient that builds the request from a reactive function, so interceptors still apply. Some of these APIs were introduced as experimental or developer preview, so check your version's stability notes. They cover the common "load data when inputs change" case without hand-written switchMap or effect code.


91. How do toSignal() and toObservable() work, and what caveats should you know?

toSignal(obs$) subscribes immediately and returns a signal holding the latest value, and it unsubscribes when the injection context is destroyed. Before the first emission its value is undefined unless you pass { initialValue }, or { requireSync: true } for streams that emit synchronously, such as BehaviorSubject. Errors thrown by the Observable are rethrown when the signal is read.

toObservable(sig) creates an Observable that emits the signal's value. Internally it uses an effect, so emissions are asynchronous and intermediate synchronous values are coalesced. Both functions require an injection context unless you pass { injector }. Do not call toSignal repeatedly, for example in a getter or template method, because each call creates a new subscription.


92. When would you choose signals over RxJS, and vice versa?

Use signals for synchronous state and derived values: UI state, form-ish state, store state, anything templates read. They are simpler, glitch-free, need no subscription management, and drive change detection directly.

Use RxJS for events over time and complex async orchestration. Examples include debouncing user input, cancelling with switchMap, retry and backoff, websockets, combining multiple streams, and race conditions. A common architecture uses RxJS at the edges (HTTP, events) and signals for state and views, bridged with toSignal, rxResource, or rxMethod. They complement each other rather than compete.


93. How do signals enable finer-grained change detection and zoneless applications?

When a template reads a signal, Angular records that view as a consumer. When the signal changes, Angular marks only that view (and its ancestors, for traversal) as needing a refresh and schedules change detection. Unaffected OnPush subtrees are skipped. In newer versions Angular can refresh just the affected view without re-checking its ancestors' bindings.

Since signals themselves tell Angular when something changed, there is no need for Zone.js to guess by patching every async API. Combined with other notification sources (markForCheck, the async pipe, template event handlers, setInput), this lets Angular run without Zone.js entirely, which gives smaller bundles, more predictable timing, and better performance.


94. How would you implement a simple state store using signals in a service?

Example:
@Injectable({ providedIn: 'root' }) export class CartStore { private readonly _items = signal<Item[]>([]); readonly items = this._items.asReadonly(); readonly total = computed(() => this._items().reduce((s, i) => s + i.price * i.qty, 0)); add(item: Item) { this._items.update(list => [...list, item]); } remove(id: string) { this._items.update(list => list.filter(i => i.id !== id)); } }

Keep the writable signal private, expose read-only signals and computeds, and change state only through methods that perform immutable updates. Async operations can call HttpClient and set state on completion, or use resource(). Scope the store with route or component providers if it should not be global.


95. What is NgRx SignalStore, and how does it compare with the classic NgRx Store?

SignalStore (@ngrx/signals) is a lightweight, functional store built on signals. You compose it with signalStore(withState(...), withComputed(...), withMethods(...), withHooks(...)) and add features such as withEntities. State changes go through patchState(), and rxMethod handles RxJS-based side effects. Each store is an injectable service that can be global or scoped locally.

Classic NgRx Store is a Redux-style global store with actions, reducers, selectors, and effects. Its strict unidirectional flow and DevTools time-travel suit large apps that need auditability, but it carries much more boilerplate. SignalStore is simpler and more local, works with signals out of the box, and is often preferred for feature or component state. Teams may use both in the same app.


96. How does reading a signal in a template register it as a dependency of that view?

Each component view has a reactive consumer node in Angular's signal graph. During template execution, Angular sets this consumer as the active consumer. Any signal read during that time records the view as a dependent, the same mechanism a computed uses.

When one of those signals changes, it notifies its consumers. The view consumer marks the view dirty for refresh, marks ancestors for traversal, and notifies the change detection scheduler. That is why signals update OnPush components automatically, and why reading signals is the most efficient way to drive templates.


97. When do effects run, and how do you perform cleanup inside an effect?

Effects never run synchronously when a signal is set. They are scheduled and run as part of Angular's change detection process. Effects created in components run during view refresh, in tree order and before the component's own template is checked. Root-level effects created in services run as part of the application-wide flush. Each effect runs at least once initially, then again whenever its tracked signals change, with multiple changes batched into one run.

For cleanup, the effect function receives an onCleanup callback: effect((onCleanup) => { const t = setInterval(...); onCleanup(() => clearInterval(t)); }). Cleanup runs before the next execution and when the effect is destroyed. Effects are destroyed with their owning component or injector, or manually through the EffectRef returned by effect(), using effectRef.destroy().


98. What is the idea behind signal-based forms, and how do they differ from reactive forms?

Signal forms, an experimental API under @angular/forms/signals in recent versions, build a form from a signal holding your data model. A function such as form(modelSignal, schema) creates a tree of fields, each exposing value, validity, errors, touched, and dirty as signals. Validation rules are declared in a schema function, and a template directive binds a field to an input.

Reactive forms instead create a separate tree of FormControl objects that mirror your model, expose changes through Observables (valueChanges), and require syncing back to your data. Signal forms keep the model as the single source of truth, give fully typed, synchronous reactive state, and fit zoneless apps naturally. The API is still stabilizing, so most production code still uses reactive forms.

SECTION 7: RXJS & OBSERVABLES (99–118)
------------------------------------------------------------------

99. What is an Observable, and how does it differ from a Promise?

An Observable represents a stream of zero or more values over time, delivered to subscribers through next, error, and complete notifications. It is lazy: nothing happens until someone subscribes. It is also composable with operators.

A Promise represents a single future value. It is eager (the work starts immediately) and cannot be cancelled. Observables can emit many values, can be cancelled by unsubscribing (which can abort an HTTP request), and are lazy and re-executable per subscriber. They offer a rich operator library for retry, debounce, and combination. Angular uses Observables for HttpClient, router events, and reactive forms.


100. What is the difference between cold and hot observables?

A cold observable creates its data producer inside the subscription, so each subscriber gets its own independent execution from the beginning. HttpClient requests, of(), and interval() are cold, which means subscribing twice to http.get makes two requests.

A hot observable shares one producer that exists independently of subscribers, and late subscribers miss earlier values. DOM events (fromEvent), Subjects, and websockets are hot. You can turn a cold source into a shared one with share() or shareReplay(), which is how you avoid duplicate HTTP calls.


101. Compare Subject, BehaviorSubject, ReplaySubject, and AsyncSubject.

A Subject is both an Observable and an Observer. It multicasts to its current subscribers and has no memory, so late subscribers miss past values. A BehaviorSubject requires an initial value, always holds the current value (accessible synchronously through getValue()), and emits it immediately to new subscribers. It is the classic choice for state in services.

A ReplaySubject buffers a configurable number of past values (and optionally a time window) and replays them to new subscribers. An AsyncSubject emits only its last value, and only when it completes, much like a Promise. In signal-era code, many BehaviorSubject state holders are better expressed as signals.


102. Explain switchMap, mergeMap, concatMap, and exhaustMap, with a use case for each.

All four map each source value to an inner observable and flatten the results; they differ in how they handle overlap. switchMap cancels the previous inner observable when a new value arrives, which suits search-as-you-type or loading details for the latest selected item. mergeMap runs all inner observables concurrently (with an optional concurrency limit), which suits independent parallel operations such as uploading several files or deleting multiple items.

concatMap queues inner observables and runs them one at a time in order, which suits save operations that must happen in sequence. exhaustMap ignores new values while an inner observable is active, which suits a submit or login button where repeated clicks should not trigger duplicate requests. Choosing the wrong one is a common source of race conditions.


103. How do you prevent memory leaks from subscriptions in components?

Avoid manual subscriptions where possible. Use the async pipe or toSignal(), which unsubscribe automatically, or express the data as computed signals and resources.

When you must subscribe, use takeUntilDestroyed() in an injection context, or pass a DestroyRef to it. Older options are a destroy$ Subject with takeUntil (placed last in the pipe) or storing a Subscription and unsubscribing in ngOnDestroy. Streams that complete on their own, such as HttpClient calls, do not leak, but long-lived ones do: router events, valueChanges, interval, store selections, and websockets.


104. Compare combineLatest, forkJoin, zip, and withLatestFrom.

combineLatest emits an array of the latest values from all sources whenever any of them emits, once each has emitted at least once. It suits combining filters, pagination, and data that all change over time. forkJoin waits for all sources to complete and then emits their last values once, much like Promise.all. It suits parallel HTTP calls.

zip pairs values by index: the first with the first, the second with the second. withLatestFrom is used in a pipe: when the source emits, it attaches the latest value from other streams without letting those streams trigger emissions themselves. A typical example is a save click that grabs the current form state.


105. What does shareReplay do, and what are the pitfalls around its refCount option?

shareReplay(n) multicasts a source to all subscribers through an internal ReplaySubject and replays the last n values to late subscribers. It is commonly used to cache an HTTP response or share an expensive stream among several async pipes.

The pitfall is refCount. With the plain shareReplay(1) form, refCount is false, so the inner subscription to the source stays alive even after every subscriber leaves. For long-lived sources such as interval or websockets this leaks resources. Use shareReplay({ bufferSize: 1, refCount: true }) so the source is torn down when subscribers drop to zero, but remember that the cache is lost at that point and the source re-executes on the next subscription.


106. How do you handle errors in streams?

catchError(err => fallback$) intercepts an error and replaces the stream with another Observable, such as of([]) for a default value, or rethrows with throwError(() => mapped). An error terminates the stream, so in long-lived streams catchError should go inside the inner observable of a switchMap. Otherwise one failed request kills the whole search stream.

retry(3) resubscribes immediately on error. retry({ count: 3, delay: (error, attempt) => timer(2 ** attempt * 1000) }) implements exponential backoff and can conditionally rethrow, for example not retrying 4xx responses. Combine retries with an interceptor or global ErrorHandler for user-facing messages, and log errors centrally.


107. Implement a typeahead search using debounceTime, distinctUntilChanged, and switchMap.

Example:
results$ = this.searchControl.valueChanges.pipe(map(v => v.trim()), debounceTime(300), distinctUntilChanged(), filter(q => q.length >= 2), switchMap(q => this.api.search(q).pipe(catchError(() => of([])))));

debounceTime waits for typing to pause, and distinctUntilChanged skips repeated queries. switchMap cancels outdated requests, so stale responses never overwrite newer ones. The inner catchError keeps the stream alive after a failure. Render it with @if (results$ | async; as results) or convert it with toSignal(results$, { initialValue: [] }).


108. What is a higher-order observable, and how do flattening operators deal with it?

A higher-order observable is an Observable that emits Observables, for example map(id => http.get(...)) produces an Observable<Observable<User>>. Subscribing to the outer stream gives you inner observables instead of data.

Flattening operators subscribe to the inner observables and merge their values into a single output stream. mergeAll, switchAll, concatAll, and exhaustAll each apply a different concurrency strategy, and the *Map operators combine map with the matching flattening step. Understanding this explains why nested subscribe calls are unnecessary.


109. What is the difference between unicasting and multicasting?

With unicasting, each subscriber gets its own independent execution of the observable. Plain cold observables work this way, so two subscribers to an HTTP observable trigger two requests.

With multicasting, one execution is shared among many subscribers, all of whom receive the same values. Subjects are multicast, and the share() and shareReplay() operators turn a cold, unicast source into a multicast one. Multicasting avoids duplicate side effects and network calls when several parts of the UI need the same data.


110. What is tap() for, and why should side effects be isolated there?

tap() runs a function for each notification (next, error, complete, subscribe, unsubscribe, and finalize through its observer form) without changing the values passing through. It is meant for side effects such as logging, debugging, setting a loading flag, or updating a cache.

Isolating side effects in tap keeps the other operators pure transformations. That makes pipelines easier to reason about and test, and avoids hidden mutations inside map. Do not subscribe to other observables inside tap; that is a nested subscription, so use a flattening operator instead.


111. How do you write a custom RxJS operator?

The simplest way is to compose existing operators with pipe(): export const filterNil = <T>() => pipe(filter((v: T | null | undefined): v is T => v != null));. You use it like any built-in operator, obs$.pipe(filterNil()).

For full control, return a function from Observable to Observable that creates a new Observable, subscribes to the source, and emits transformed values. You must handle error and complete and return teardown logic. Most needs are covered by composition, which preserves correct unsubscription semantics. Custom operators are also good places for domain logic such as retryWithBackoff or handleHttpErrors.


112. What are firstValueFrom and lastValueFrom, and why did they replace toPromise()?

firstValueFrom(obs$) returns a Promise that resolves with the first emitted value and then unsubscribes. lastValueFrom(obs$) resolves with the last value once the observable completes. Both reject if the stream errors or completes without emitting, unless you supply a defaultValue.

toPromise() was deprecated because its semantics were ambiguous. It resolved with the last value, and with undefined if the stream completed without emitting, which hid bugs. It also would never resolve for streams that do not complete. The new functions make the intent explicit. They are useful with async/await, for example in a provideAppInitializer function.


113. What is the difference between take(1), first(), and takeUntil()?

take(1) emits the first value and completes. If the source completes without emitting, it simply completes silently. first() also emits the first value, optionally the first value matching a predicate, but it throws an EmptyError if the source completes without a match, unless you provide a default value.

takeUntil(notifier$) mirrors the source until the notifier emits and then completes. It is used to tie a stream's lifetime to an event such as component destruction. It should normally be the last operator in the pipe so that later operators do not keep subscriptions alive. takeUntilDestroyed() is Angular's convenience version.


114. What are RxJS schedulers, and when might you use one?

Schedulers control when and in what execution context notifications are delivered. asyncScheduler uses setTimeout-style timers and is the default for time-based operators. asapScheduler uses microtasks, queueScheduler runs synchronous work trampolined, and animationFrameScheduler aligns work with requestAnimationFrame.

Application code rarely needs them. Typical uses are observeOn(animationFrameScheduler) for smooth animations or scroll handling, and controlling timing in tests. Testing usually goes through TestScheduler, which virtualizes time so that debounceTime(300) can be tested instantly.


115. How do you test observables with marble testing?

Marble testing describes streams as ASCII diagrams in which each character is a frame. '-' means time passes, 'a' is an emission, '|' is completion, and '#' is an error. With TestScheduler you write: testScheduler.run(({ cold, expectObservable }) => { const src = cold('-a-b-|'); expectObservable(src.pipe(map(x => x.toUpperCase()))).toBe('-A-B-|'); });.

Inside run(), time-based operators use virtual time, so debounce and delay tests are instant and deterministic. hot() creates hot sources, and expectSubscriptions verifies subscribe and unsubscribe timing. Marble tests are especially valuable for complex operator chains in effects or services. They need care with Angular-specific async such as HttpClient, which is better tested with HttpTestingController.


116. How would you implement polling with RxJS that stops on a condition?

Example:
status$ = timer(0, 5000).pipe(switchMap(() => this.api.getJobStatus(id)), takeWhile(s => s.state !== 'done', true), shareReplay({ bufferSize: 1, refCount: true }));

timer(0, 5000) fires immediately and then every five seconds. switchMap issues a request and drops one that is still pending when the next tick arrives; use exhaustMap instead to skip ticks while a request is running. takeWhile with inclusive set to true emits the final "done" value and then stops. Add retry with backoff for transient errors and takeUntilDestroyed() to stop polling when the component is destroyed.


117. Why are nested subscriptions an anti-pattern, and how do you refactor them?

A subscribe inside another subscribe creates inner subscriptions that are not automatically cancelled when the outer value changes or the component is destroyed. That causes race conditions (stale responses arriving out of order), memory leaks, and error handling that is split up and easy to miss. It also makes code hard to read and test.

Refactor by moving the dependency into a flattening operator: this.route.paramMap.pipe(map(p => p.get('id')!), switchMap(id => this.api.getUser(id)), switchMap(user => this.api.getOrders(user.id))). Then subscribe once, or better, use the async pipe or toSignal. Choose switchMap, concatMap, mergeMap, or exhaustMap based on the concurrency you need, and use forkJoin or combineLatest for parallel combinations.


118. What does EventEmitter extend, and why shouldn't you use it as a general-purpose event bus in services?

EventEmitter extends RxJS Subject and adds an optional async delivery mode. It was designed for @Output() properties, where Angular subscribes to it on behalf of event bindings.

Using it in services is discouraged. Its semantics are tied to component outputs, Angular may change its implementation (as happened with the move to output(), which is not RxJS-based), and it gives no clearer intent than a Subject. In services, use a private Subject or BehaviorSubject exposed through asObservable(), or a signal. For outputs, prefer output() in modern code.

SECTION 8: CHANGE DETECTION & ZONES (119–130)
------------------------------------------------------------------

119. How does change detection work in Angular, from event to DOM update?

Something async happens: a DOM event, an HTTP response, a timer, or a signal change. Angular is notified, either because Zone.js intercepted the async callback or, in zoneless mode, because a signal, markForCheck, or event handler scheduled a check. Angular then schedules application-wide change detection through ApplicationRef.tick().

During the tick, Angular walks the component tree from the root, top-down. For each view that needs checking, it runs the compiled update instructions: it evaluates template bindings, compares them with previous values, and updates only the DOM nodes or child inputs whose values changed. OnPush and non-dirty views are skipped. Lifecycle hooks and after-render callbacks run at defined points. In development mode a second verification pass checks that nothing changed during the check.


120. What is Zone.js, and what browser APIs does it patch?

Zone.js is a library that creates execution contexts called zones, which persist across async operations. It monkey-patches browser async APIs so it can tell when async work starts and finishes. Angular runs the app inside NgZone, and when the zone becomes stable after a task completes, Angular triggers change detection.

It patches setTimeout and setInterval, Promise and microtasks, addEventListener and DOM events, XMLHttpRequest and fetch, requestAnimationFrame, MutationObserver, WebSocket, and more. This makes change detection automatic but coarse, because every patched callback triggers a check. It adds bundle size, does not support native async/await without downleveling, and complicates stack traces, which is why Angular is moving to zoneless.


121. What is the difference between the Default and OnPush change detection strategies?

With Default (ChangeDetectionStrategy.Default, now also called Eager in some docs), a component is checked on every change detection cycle, whenever anything in the application triggers one. That is simple, but large trees do redundant work.

With OnPush, Angular checks the component, and lets it check its subtree, only when it has been marked dirty. That happens when an input reference changes, when an event originates in the component or its children, when a signal it reads changes, or when markForCheck() is called (which the async pipe does). OnPush encourages immutable data and explicit reactivity and is strongly recommended for every component in modern apps.


122. What events trigger change detection for an OnPush component?

An OnPush component is checked in these cases. The parent passes a new reference to one of its inputs through a template binding, or setInput() is called. An event bound in its template (or a child's template) fires, such as (click). A signal read in its template changes. The async pipe in its template receives a new value, because it calls markForCheck.

It is also checked when code explicitly calls ChangeDetectorRef.markForCheck() or detectChanges(). It is not checked when an object it received is mutated in place, when a setTimeout or HTTP callback changes a plain class property without one of the above, or when an unrelated part of the app changes.


123. Explain ChangeDetectorRef methods: markForCheck(), detectChanges(), detach(), and reattach().

markForCheck() marks the current view and all its ancestors as dirty, so they are checked during the next scheduled change detection. Use it after updating a plain property in an OnPush component from an async callback. detectChanges() runs change detection synchronously and immediately for this view and its children, which is useful when you need the DOM updated right now or in detached components.

detach() removes the view from the change detection tree, so it is not checked until you reattach it or call detectChanges() manually. It is useful for very high-frequency widgets that you update on your own schedule. reattach() puts the view back into normal checking. checkNoChanges() also exists for verification in development mode. With signals, you rarely need any of these.


124. What does NgZone.runOutsideAngular() do, and when would you use it?

runOutsideAngular(fn) executes fn in the parent zone, outside Angular's zone. Async work started inside it, such as timers, event listeners, and animation frames, does not trigger change detection when it fires.

Use it for high-frequency events that do not need to update bindings on every tick: mousemove and scroll handlers, requestAnimationFrame loops, canvas or WebGL rendering, polling third-party libraries, and websockets that you batch. When you do need to update the UI, call ngZone.run(() => ...) to re-enter, or update a signal, which schedules its own check. In zoneless apps this API becomes largely unnecessary.


125. What is zoneless Angular? How do you enable it, and what must change in an app to migrate?

Zoneless Angular runs without Zone.js. Change detection is scheduled only by explicit notifications: signal changes read in templates, template event handlers, markForCheck() (including from the async pipe), ComponentRef.setInput(), and attaching or removing views. You enable it with provideZonelessChangeDetection() in app.config and remove zone.js from the polyfills in angular.json. Newer versions make zoneless the default for new projects.

To migrate, make every component work correctly under OnPush. Remove reliance on code that changes plain properties inside setTimeout, Promise.then, or subscribe callbacks without notifying Angular; use signals or markForCheck there. Replace NgZone.onStable or onMicrotaskEmpty usage with afterNextRender or afterEveryRender. Check third-party libraries for zone assumptions, and update tests to use fixture.whenStable() or autoDetect rather than fakeAsync where it depends on the zone. The payoff is a smaller bundle, better performance, clearer stack traces, and native async/await.


126. What causes ExpressionChangedAfterItHasBeenCheckedError, and how do you fix it?

In development mode Angular runs a second check after each change detection pass and throws this error if a binding's value changed between the two passes. That means the template's state was modified during change detection, which violates unidirectional data flow and would leave the UI inconsistent.

Common causes are changing a parent's bound property from a child's ngAfterViewInit or ngOnChanges, getters that return a new object or a random or time-based value on every call, and services that update state synchronously while a view is being rendered. Fixes include moving the logic earlier (ngOnInit or a computed), deriving state with signals or computed so it is consistent, and using afterNextRender for DOM-dependent work. As a last resort, defer the update (queueMicrotask or setTimeout) and then trigger a check. Do not simply call detectChanges() to hide the error.


127. Why does immutability matter when using OnPush?

OnPush, signals, and pure pipes all detect changes by comparing references. If you mutate an object or array in place, as in this.user.name = 'x' or items.push(i), the reference passed to the child is unchanged, so Angular sees no change and the OnPush child keeps showing old data.

Immutable updates, such as this.user = { ...this.user, name: 'x' } or items.update(l => [...l, i]), create new references, so change detection is both correct and cheap. Reference checks are O(1), compared with costly deep comparisons. Immutability also makes state changes predictable and debuggable, which is why stores like NgRx enforce it.


128. How do signals interact with OnPush components?

When an OnPush component's template reads a signal and the signal changes, Angular marks that component's view as needing a refresh, much like an automatic markForCheck, and schedules change detection. The component updates without inputs changing and without you injecting ChangeDetectorRef.

This makes OnPush plus signals the recommended default. Change detection is precise, you need no async pipe or manual markForCheck for signal-driven state, and the same code works unchanged under zoneless. Reading signals only in class code, for example in a method called from a timer, does not on its own refresh the view unless the template also reads them or a computed the template uses.


129. How do you profile and debug change detection performance?

The Angular DevTools browser extension has a Profiler tab that records change detection cycles. It shows which components were checked, how long each took, and what triggered the cycle, and lets you inspect the component tree, inputs, signals, and injectors. Look for components checked far more often than necessary and slow bindings.

You can also use the Chrome Performance panel, where Angular adds custom timing tracks in newer versions. In development mode, ng.profiler.timeChangeDetection() in the console measures tick time. Common fixes include adopting OnPush and signals, adding track expressions, replacing template method calls with pipes or computed values, using @defer and virtual scrolling for heavy content, and running noisy third-party code outside the zone.


130. What is Angular's unidirectional data flow rule, and why does it exist?

During change detection, data flows one way, from parent to child, top-down through the tree. A child must not change state that its parent's already-checked bindings depend on while the check is running. Upward communication happens through events (outputs), which trigger a new change detection cycle rather than modifying the current one.

The rule exists because it guarantees that a single top-down pass produces a consistent view. Without it Angular would have to loop until values stabilize, as AngularJS's digest cycle did, which was slow and could loop forever. The development-mode ExpressionChangedAfterItHasBeenChecked check enforces the rule.

SECTION 9: ROUTING (131–148)
------------------------------------------------------------------

131. How do you configure routing in a standalone application with provideRouter()?

Define an array of Route objects, typically in app.routes.ts, for example [{ path: '', component: HomeComponent }, { path: 'users/:id', loadComponent: () => import('./user/user.component') }, { path: '**', component: NotFoundComponent }]. Then add provideRouter(routes, ...features) to app.config providers.

Features configure behavior: withComponentInputBinding(), withViewTransitions(), withPreloading(PreloadAllModules), withInMemoryScrolling(...), withHashLocation(), withRouterConfig(...), and withDebugTracing(). Place <router-outlet /> in the root template and import RouterOutlet, RouterLink, and RouterLinkActive into components that use them.


132. Compare routerLink, routerLinkActive, Router.navigate(), and Router.navigateByUrl().

routerLink is a template directive for declarative navigation, as in <a routerLink="/users">, [routerLink]="['/users', id]", and [queryParams]="{ page: 2 }". It renders a real href, which helps accessibility and SEO, and supports relative paths. routerLinkActive adds CSS classes when its link's route is active. Options such as { exact: true } and ariaCurrentWhenActive refine its behavior.

Router.navigate(['users', id], { relativeTo: this.route, queryParams }) navigates from code using an array of commands that the router resolves, possibly relative to a route. Router.navigateByUrl('/users/5?tab=info') navigates to an absolute URL string or a UrlTree and ignores relativeTo. Both return a Promise<boolean> for success. Use the template directive for links, navigate for programmatic relative navigation, and navigateByUrl when you already have a full URL.


133. How do you read route params, query params, and fragments? What does withComponentInputBinding() do?

Inject ActivatedRoute. Observable APIs, which react when the same component is reused with different params, include route.paramMap, queryParamMap, fragment, and data. Snapshot APIs include route.snapshot.paramMap.get('id'). Convert the Observables with toSignal() for signal-based code, and inject the Router for global URL state.

withComponentInputBinding() makes the router bind path params, query params, resolver data, and static route data directly to component inputs with matching names. id = input<string>() then receives the :id param automatically, and it updates on navigation. This removes most ActivatedRoute boilerplate and makes routed components easier to reuse and test.


134. How do you lazy load routes with loadComponent and loadChildren?

loadComponent: () => import('./admin/admin.component').then(m => m.AdminComponent) lazy loads a single standalone component. If the file uses a default export, => import('./admin/admin.component') is enough. loadChildren: () => import('./admin/admin.routes').then(m => m.ADMIN_ROUTES) lazy loads an entire child route configuration, which can contain its own providers and further lazy routes.

The bundler splits each dynamic import into its own chunk, which the router fetches the first time the route matches. This reduces initial bundle size. loadChildren can still point to an NgModule in legacy apps. Combine lazy loading with preloading strategies to soften the delay on first navigation.


135. What preloading strategies exist, and how would you write a custom one?

The built-in strategies are NoPreloading (the default), where lazy chunks load only on navigation, and PreloadAllModules, which loads every lazy route in the background after the app starts. Configure one with provideRouter(routes, withPreloading(PreloadAllModules)). Community options such as quicklink preload routes whose links are visible in the viewport.

For a custom strategy, implement PreloadingStrategy: preload(route: Route, load: () => Observable<any>) { return route.data?.['preload'] ? load() : of(null); }. Then mark routes with data: { preload: true }. You can refine it further by checking network conditions (navigator.connection.saveData or effectiveType), user roles, or delays, so that heavy features are preloaded only for likely users on fast connections.


136. Explain functional guards: CanActivate, CanActivateChild, CanDeactivate, and CanMatch.

Functional guards are plain functions that can use inject(). They return boolean, UrlTree, or RedirectCommand, synchronously or as a Promise or Observable. For example: export const authGuard: CanActivateFn = () => inject(AuthService).isLoggedIn() || inject(Router).createUrlTree(['/login']);. Attach one with canActivate: [authGuard].

canActivate decides whether a route can be entered. canActivateChild runs before activating any child route, which is useful to protect a whole section. canDeactivate decides whether the user may leave, typically to warn about unsaved changes, and receives the component instance. canMatch decides whether a route configuration may be matched at all. Class-based guards are deprecated in favor of these functions, though they can be wrapped with mapToCanActivate.


137. What is the difference between CanMatch and CanActivate, and why might CanMatch be preferred?

canActivate runs after the router has matched a route. If it fails, navigation is cancelled or redirected, but the route's lazy code has already been downloaded during matching. canMatch runs during matching. If it returns false, the router behaves as if the route did not exist and keeps trying the next route configuration.

CanMatch is preferred for permission-based routing because a lazy chunk is not downloaded for unauthorized users. It also lets you define two routes with the same path for different roles (an admin dashboard and a user dashboard at /dashboard) or feature flags, and the router picks whichever one matches. CanActivate remains useful when the route should match but access depends on additional runtime checks.


138. What are resolvers, and what are the UX trade-offs of using them?

A resolver is a function on a route, resolve: { user: userResolver }, that fetches data before the route activates. The router waits for it, and the data appears in route.data or, with input binding, as a component input. ResolveFn<User> = (route) => inject(UserService).get(route.paramMap.get('id')!).

The advantage is that the component renders with its data ready, without empty states, and routing errors can redirect early. The trade-off is that navigation feels frozen while the data loads. You need a global loading indicator, a slow API delays the whole page, and the user cannot see partial content. Many teams prefer navigating immediately and loading data in the component with resource() or httpResource() and skeleton UI. Resolvers are kept for small, critical data or when a missing item should redirect.


139. How do nested (child) routes and named router outlets work?

Child routes are declared in a route's children array. The parent component's template contains its own <router-outlet>, where the active child renders, so a URL like /settings/profile renders SettingsComponent with ProfileComponent inside it. Children can use relative paths, guards, resolvers, and lazy loading.

Named outlets, such as <router-outlet name="sidebar" />, let several routes render at once in different places. Routes target them with outlet: 'sidebar', and URLs encode them as /inbox(sidebar:chat). You navigate with commands like [{ outlets: { sidebar: ['chat'] } }]. They are useful for independently navigable panels and popups, but they make URLs complex, so use them sparingly.


140. How do redirects, wildcard routes, and pathMatch: 'full' vs 'prefix' work?

A redirect route, { path: '', redirectTo: 'home', pathMatch: 'full' }, replaces the matched URL segment and continues matching. A wildcard route, { path: '**', component: NotFoundComponent }, matches anything. It must come last because the router uses the first match in configuration order.

pathMatch: 'prefix', the default, matches when the URL starts with the route path. pathMatch: 'full' requires the remaining URL to equal the path exactly. An empty-path redirect needs 'full', because every URL has an empty prefix, and with 'prefix' the redirect would always fire.


141. How do redirectTo functions work, and when are they useful?

redirectTo can be a function instead of a string: redirectTo: ({ queryParams, params }) => { ... return 'new-path' or a UrlTree; }. It runs in an injection context, so it can use inject(), for example to read a user's preferences or a feature-flag service.

This is useful for dynamic redirects. Examples include sending users to their last-visited section or their role's default page, migrating legacy URL formats while mapping query parameters, and choosing a locale-specific route. It avoids writing a dummy component or a guard purely to perform a redirect.


142. What router events exist, and how would you use them to show a global loading indicator?

Router.events emits, in sequence, NavigationStart, RoutesRecognized, GuardsCheckStart and GuardsCheckEnd, ResolveStart and ResolveEnd, and then NavigationEnd, NavigationCancel, NavigationError, or NavigationSkipped. Lazy loading adds RouteConfigLoadStart and RouteConfigLoadEnd, and ActivationStart, ActivationEnd, and Scroll events also appear.

For a loading bar: loading = toSignal(inject(Router).events.pipe(filter(e => e instanceof NavigationStart || e instanceof NavigationEnd || e instanceof NavigationCancel || e instanceof NavigationError), map(e => e instanceof NavigationStart)), { initialValue: false });. Then show the bar with @if (loading()). Adding a small delay before showing it avoids a flicker on fast navigations. Router events are also used for analytics page views and for focus management to improve accessibility.


143. What is RouteReuseStrategy, and when would you implement a custom one?

RouteReuseStrategy decides whether the router reuses a component when navigating, and whether it detaches and stores a route's component tree for later reattachment instead of destroying it. The default reuses the component only when the route config is the same (for example, when only params change) and never stores detached routes.

A custom strategy implements shouldDetach, store, shouldAttach, retrieve, and shouldReuseRoute. It keeps expensive pages alive, preserving scroll position, form state, and data, when users go back and forth, as in list-to-detail flows or tab-like apps. The risks are memory growth and stale data, and stored components miss lifecycle hooks, so implement eviction rules and refresh logic.


144. Compare HashLocationStrategy and PathLocationStrategy. What server configuration do deep links require?

PathLocationStrategy, the default, uses the HTML5 History API and produces clean URLs such as /users/5. HashLocationStrategy (withHashLocation()) puts the route after a #, as in /#/users/5. Browsers never send the fragment to the server, so any static host works without configuration.

With path-based URLs, a deep link or refresh on /users/5 asks the server for that path. The server must be configured to fall back to index.html for all non-file routes. Examples include try_files in nginx, rewrite rules in Apache or IIS, and SPA fallback settings on Netlify, Firebase, or S3 and CloudFront. Otherwise users get 404s. Set the correct base href when the app is not served from the domain root.


145. How do you set page titles with the route title property or a custom TitleStrategy?

Add title to a route: { path: 'about', title: 'About Us', component: AboutComponent }. The router's default TitleStrategy sets document.title after successful navigation. title can also be a ResolveFn for dynamic titles, for example a product name fetched from the API.

For consistent formatting, such as appending " | MySite", extend TitleStrategy and override updateTitle(snapshot), using buildTitle(snapshot) and the Title service. Provide it with { provide: TitleStrategy, useClass: AppTitleStrategy }. This centralizes titles, which helps SEO and screen-reader users, and avoids setting the title manually in every component.


146. How do you enable view transitions in the router?

Add withViewTransitions() to provideRouter(). The router then wraps each navigation's DOM update in the browser's document.startViewTransition() API, which by default produces a cross-fade between the old and new page. Browsers without support fall back to an instant switch.

You customize the animations with CSS: the ::view-transition-old(root) and ::view-transition-new(root) pseudo-elements, and view-transition-name on elements that should morph between pages, such as a thumbnail growing into a hero image. Options include skipInitialTransition and an onViewTransitionCreated callback, which lets you skip or adjust transitions per navigation, for example to respect prefers-reduced-motion.


147. How do you configure scroll position restoration and anchor scrolling?

Use provideRouter(routes, withInMemoryScrolling({ scrollPositionRestoration: 'enabled', anchorScrolling: 'enabled' })). With 'enabled', the router scrolls to the top on forward navigation and restores the previous position on back and forward navigation. 'top' always scrolls to the top, and 'disabled' is the default. anchorScrolling scrolls to the element whose id matches the URL fragment.

Restoration happens after navigation, so asynchronously loaded content may not exist yet. For those cases, listen for the router's Scroll event and use ViewportScroller.scrollToPosition after data loads. ViewportScroller.setOffset() accounts for sticky headers.


148. What are the options for passing data or state between routes?

The URL options are route params (/users/:id) and query params (?tab=orders), which are shareable, bookmarkable, and survive refresh, and so are best for anything that defines what the page shows. Static route data, data: { breadcrumb: 'Users' }, and resolvers provide configuration or prefetched data.

For non-URL state, router.navigate(['/next'], { state: { from: 'cart' } }) attaches a history state object, readable through router.getCurrentNavigation()?.extras.state during navigation or history.state afterwards. It survives back and forward navigation but is not in the URL. For larger or shared state, use a service or store holding signals. In general, put identifiers in the URL and keep heavier data in services or caches.

SECTION 10: FORMS (149–163)
------------------------------------------------------------------

149. Compare template-driven forms and reactive forms. When would you choose each?

Template-driven forms (FormsModule) build the form model implicitly from directives in the template, ngModel, ngModelGroup, and ngForm, with validation through attributes such as required. They are quick for simple forms, but the logic lives in the template, the model is created asynchronously, and they are harder to unit test and compose dynamically.

Reactive forms (ReactiveFormsModule) build an explicit, synchronous model in the class with FormControl, FormGroup, and FormArray. The template binds to it with [formGroup] and formControlName. They are fully typed, easy to test, support dynamic forms and complex validation, and expose Observables for changes. Choose reactive forms for most non-trivial applications, and keep template-driven forms for small, simple forms. Signal forms are the emerging third option.


150. Explain FormControl, FormGroup, FormArray, and FormBuilder.

A FormControl tracks the value, validation status, and interaction state of a single input. A FormGroup groups named controls into an object; its value is an object, and it is valid only if all its children are valid. A FormArray holds an ordered, dynamic list of controls or groups, which suits repeating fields such as phone numbers or line items.

FormBuilder (inject(FormBuilder)) is a helper that builds these with less code: fb.group({ name: ['', Validators.required], tags: fb.array([]) }). All of them inherit from AbstractControl, which provides value, status, errors, valueChanges, setValue, patchValue, reset, enable and disable, and the touched and dirty flags.


151. What are typed reactive forms, and what does NonNullableFormBuilder change?

Since Angular 14, reactive forms are strongly typed. new FormControl('') is a FormControl<string | null>, and form.value and get('name') carry proper types, so the compiler catches typos and wrong value types. The null comes from reset(), which by default sets a control back to null.

NonNullableFormBuilder (fb.nonNullable, or inject(NonNullableFormBuilder)) creates controls with nonNullable: true. Their type excludes null, and reset() restores the initial value instead of null. That gives cleaner types (FormControl<string>) and more predictable reset behavior. FormRecord covers dynamic keys, and UntypedFormControl and similar types remain available for gradual migration of old code.


152. Write a custom synchronous validator.

Example:
export function forbiddenWord(word: string): ValidatorFn { return (control: AbstractControl): ValidationErrors | null => { const v = (control.value ?? '').toString().toLowerCase(); return v.includes(word) ? { forbiddenWord: { word } } : null; }; }

Use it as new FormControl('', [Validators.required, forbiddenWord('admin')]). A validator returns null when the value is valid, or an errors object whose keys appear in control.errors. To use it with template-driven forms, wrap it in a directive that provides NG_VALIDATORS (multi: true) and implements Validator.


153. Write an async validator, such as checking whether a username is available.

Example:
export function usernameAvailable(api: UserApi): AsyncValidatorFn { return (control) => timer(300).pipe(switchMap(() => api.isAvailable(control.value)), map(ok => ok ? null : { usernameTaken: true }), catchError(() => of(null))); }

Attach it with new FormControl('', { validators: [Validators.required], asyncValidators: [usernameAvailable(inject(UserApi))], updateOn: 'blur' }). Async validators run only after the synchronous validators pass. While they run, the control's status is PENDING. Angular unsubscribes from the previous run when the value changes, which, together with timer, acts as a debounce. The Observable must complete, because Angular waits for completion.


154. How do you implement cross-field validation (e.g., password confirmation)?

Put the validator on the parent FormGroup so it can see several controls: const matchPasswords: ValidatorFn = (group) => group.get('password')?.value === group.get('confirm')?.value ? null : { passwordMismatch: true };. Attach it with fb.group({ password: [''], confirm: [''] }, { validators: matchPasswords }).

The error appears on the group (form.hasError('passwordMismatch')), so display it near the confirm field and check whether that field has been touched. Some teams also call setErrors on the child control, but that must be done carefully to avoid wiping the child's other errors. Group validators re-run whenever any child changes.


155. Explain the control states: pristine/dirty, touched/untouched, valid/invalid/pending/disabled.

pristine means the user has not changed the value through the UI; dirty means they have. Programmatic setValue does not mark a control dirty. untouched means the control has never been blurred; touched means it has. These interaction flags exist mainly to decide when to show errors, for example invalid && (touched || submitted).

status is one of VALID, INVALID, PENDING (an async validator is running), or DISABLED. Disabled controls are excluded from the parent's validity and value. Angular also adds CSS classes (ng-valid, ng-invalid, ng-pending, ng-pristine, ng-dirty, ng-touched, ng-untouched) to bound elements for styling, and markAsTouched, markAllAsTouched, and markAsPristine let you set the flags from code.


156. What is ControlValueAccessor, and how do you implement a custom form control?

ControlValueAccessor is the bridge between the Forms API and a UI element. Implementing it lets your component work with formControlName, [formControl], and ngModel like a native input. It has four methods: writeValue(value), when the form sets the value; registerOnChange(fn), where you call fn(newValue) when the user changes the value; registerOnTouched(fn), where you call fn() on blur; and the optional setDisabledState(isDisabled).

Register it with providers: [{ provide: NG_VALUE_ACCESSOR, useExisting: forwardRef(() => RatingComponent), multi: true }]. Keep the internal state in a signal, call the stored callbacks on user interaction, and avoid calling onChange inside writeValue, which would cause loops. To contribute validation as well, also provide NG_VALIDATORS and implement Validator.


157. What is the difference between setValue() and patchValue()?

On a FormGroup or FormArray, setValue() requires a value for every control in the structure and throws if a key is missing or unknown. That strictness catches mistakes when you intend to replace the whole value. patchValue() updates only the keys you provide and ignores missing or extra ones, which suits partial updates such as applying an API response with fewer fields.

Both accept options such as { emitEvent: false } to suppress valueChanges and { onlySelf: true } to avoid updating ancestors' validity. On a single FormControl the two behave the same.


158. How do you build a dynamic form with FormArray (add/remove rows)?

Define items = fb.array<FormGroup<ItemForm>>([]) inside a group. Write helpers addItem() { this.items.push(fb.group({ name: ['', Validators.required], qty: [1] })); } and removeItem(i: number) { this.items.removeAt(i); }. In the template, use formArrayName="items" with @for (row of items.controls; track row; let i = $index) and [formGroupName]="i" on each row.

FormArray also provides insert, at, setControl, clear, and move-style operations, built with removeAt plus insert. Typed forms keep the row type consistent. For metadata-driven forms, such as fields defined by a server schema, generate the controls from configuration in a loop and render them with a field component that switches on the field type.


159. What do the updateOn options ('change', 'blur', 'submit') do?

updateOn controls when a control's value and validity update from the UI. 'change', the default, updates on every input event. 'blur' updates only when the control loses focus, which is useful for expensive validators and async validators that call APIs. 'submit' updates only when the parent form is submitted.

Set it per control, new FormControl('', { updateOn: 'blur' }), per group (child controls inherit it), or through ngModelOptions in template-driven forms. It reduces validation churn and valueChanges emissions, though it makes immediate feedback, such as live character counts, impossible for that control.


160. How do valueChanges, statusChanges, and the unified control events observable work?

valueChanges is an Observable that emits the control's new value after each change, whether from the UI, setValue, or patchValue, unless emitEvent is false. statusChanges emits VALID, INVALID, PENDING, or DISABLED when the status is recalculated. Both are hot and long-lived, so unsubscribe with takeUntilDestroyed or convert with toSignal.

control.events, added in newer versions, is a single Observable of typed event objects: ValueChangeEvent, StatusChangeEvent, PristineChangeEvent, TouchedChangeEvent, and, on forms, FormSubmittedEvent and FormResetEvent. It lets you react to touched and pristine changes, which previously had no Observable at all, and to filter by event type in one stream. Each event carries a source property identifying which control triggered it.


161. How do disabled controls affect form.value, and what does getRawValue() return?

When a control is disabled, its value is excluded from its parent group's value. It is also ignored for validity, so the group can be valid while it holds an invalid disabled child. This surprises developers who submit form.value and find fields missing.

getRawValue() returns the full value including disabled controls. Use it when you need every field, for example read-only fields displayed as disabled. Disable controls with control.disable() rather than a [disabled] attribute binding, which reactive forms warn about. If you only want an input to be non-editable but still part of the submitted value, consider readonly instead.


162. What is a clean, reusable approach to displaying validation error messages?

Avoid repeating @if (ctrl.hasError('required') && ctrl.touched) blocks everywhere. Create a reusable error component, <app-field-error [control]="form.controls.email" />, or a directive that maps error keys to messages using a central dictionary (required: 'This field is required', minlength: (e) => `Min ${e.requiredLength} characters`). Show errors only after the user interacts (touched) or after a submit attempt.

Provide the messages map through an InjectionToken so it can be translated and overridden per app. Wrap inputs in a form-field component that includes the label, the error display, and aria-describedby wiring for accessibility. Angular Material's mat-form-field with mat-error follows this pattern, with an ErrorStateMatcher controlling when errors appear.


163. How does ngModel work, and what is its relationship to FormsModule?

ngModel is a directive from FormsModule. [(ngModel)]="name" creates a FormControl behind the scenes, binds the value to the element through the element's ControlValueAccessor (DefaultValueAccessor for text inputs, CheckboxControlValueAccessor, and so on), and emits ngModelChange on user input. That gives two-way binding. Inside a <form>, it registers with the parent NgForm and requires a name attribute.

You must import FormsModule, or the standalone directives it exports, into the component to use it. It supports validators as attributes, ngModelOptions for updateOn and standalone settings, and exposes state through #model="ngModel". It does not belong in reactive forms: mixing ngModel with formControl is deprecated.

SECTION 11: HTTP & DATA ACCESS (164–173)
------------------------------------------------------------------

164. How do you set up HttpClient with provideHttpClient(), and what do features like withInterceptors() and withFetch() do?

Add provideHttpClient(...features) to app.config providers, then call inject(HttpClient) in services. The older HttpClientModule is deprecated in favor of this function.

withInterceptors([authInterceptor, loggingInterceptor]) registers functional interceptors. withInterceptorsFromDi() enables legacy class-based HTTP_INTERCEPTORS. withFetch() uses the browser Fetch API instead of XMLHttpRequest, which is recommended for SSR and improves performance; upload progress events are limited with fetch. Other features include withXsrfConfiguration(), withNoXsrfProtection(), withJsonpSupport(), and withRequestsMadeViaParent() for nested injectors.


165. What are functional interceptors, and what are typical use cases (auth, logging, error handling)?

A functional interceptor is a function (req, next) => Observable<HttpEvent>, typed HttpInterceptorFn, that can use inject(). It can modify the request, pass it on with next(req), and transform or react to the response stream. For example: export const authInterceptor: HttpInterceptorFn = (req, next) => { const token = inject(AuthService).token(); return next(token ? req.clone({ setHeaders: { Authorization: `Bearer ${token}` } }) : req); };.

Typical uses are adding auth headers, setting base URLs or API versions, logging and timing requests, global error handling (redirect to login on 401, toast on 500), retries, caching GET responses, showing a global loading indicator, and mocking APIs in development. They are simpler than class interceptors and are the recommended form.


166. In what order do interceptors run, and why must you clone() a request to modify it?

Interceptors run on the request in the order they are listed in withInterceptors([a, b, c]): a, then b, then c, then the backend. Responses flow back in reverse order: c, then b, then a. Order matters. An auth interceptor should run before a logging interceptor that records headers, and a retry interceptor positioned after auth will retry with the auth header already attached.

HttpRequest and HttpHeaders are immutable, so an interceptor cannot change a request in place. You call req.clone({ setHeaders, url, body, params }) to create a modified copy. Immutability makes requests safe to retry, because the original is unchanged, and prevents one interceptor from mutating a request another interceptor has already seen.


167. How would you implement global HTTP error handling?

Write an error interceptor: (req, next) => next(req).pipe(catchError((err: HttpErrorResponse) => { if (err.status === 401) inject(Router).navigate(['/login']); else if (err.status >= 500) inject(Notifier).error('Server error'); return throwError(() => err); })). Call inject() at the top of the interceptor function, not inside the callback, because the callback runs outside the injection context.

Rethrow the error so individual callers can still handle specific cases. Add retry with backoff for transient network or 503 errors before it. For non-HTTP runtime errors, provide a custom ErrorHandler class that logs to a monitoring service such as Sentry. Use HttpContext tokens so particular requests can opt out of global handling, for example when a 404 is expected.


168. How do you use HttpParams, HttpHeaders, typed responses, and the observe/responseType options?

Pass query parameters as an object, http.get<User[]>('/api/users', { params: { page: 2, q: 'smith' } }), or build them with new HttpParams().set('page', 2). Headers work the same way, through a { headers: { 'X-Trace': id } } object or an HttpHeaders instance. Both classes are immutable, so set() returns a new instance. The generic parameter, get<User[]>, types the parsed JSON body. It is a compile-time assertion only, so validate untrusted data separately.

observe: 'body' is the default and returns just the body. observe: 'response' returns HttpResponse<T> with status and headers, which is useful for reading pagination headers. observe: 'events' with reportProgress: true emits upload and download progress events. responseType can be 'json' (the default), 'text', 'blob' (for file downloads), or 'arraybuffer'.


169. How do you cancel an in-flight HTTP request?

HttpClient Observables are cancellable: unsubscribing aborts the underlying XHR or fetch request. Explicit unsubscribe works, and cancellation also happens automatically through operators. switchMap cancels the previous request when a new value arrives, takeUntil or takeUntilDestroyed cancel on destroy or on a notifier, and the async pipe cancels when the component is destroyed.

With resource(), the loader receives an abortSignal that you pass to fetch. resource, rxResource, and httpResource cancel automatically when their params change. Remember that cancelling only stops the client from waiting. The server may have already processed the request, so for non-idempotent operations, design APIs with idempotency keys.


170. What strategies can you use to cache HTTP responses?

Within a service, you can store a shared Observable with shareReplay({ bufferSize: 1, refCount: false }) so all callers reuse one response, or keep the result in a signal and return it if it is present. A caching interceptor keyed by URL and params can store GET responses in a Map with a TTL, and an HttpContext token lets individual requests opt in or out.

Libraries such as TanStack Query for Angular offer stale-while-revalidate, background refetching, and invalidation. Also lean on HTTP-level caching (Cache-Control and ETag headers, which the browser handles) and on the SSR transfer cache to avoid refetching after hydration. Always define invalidation: clear or update the cache after mutations such as POST, PUT, and DELETE.


171. What is HttpContext, and how do HttpContextTokens let you configure interceptor behavior per request?

HttpContext is a typed, mutable map of metadata attached to an HttpRequest. It is not sent to the server and exists only for interceptors. You define a token with a default, export const SKIP_AUTH = new HttpContextToken<boolean>(() => false), and set it on a call: http.get(url, { context: new HttpContext().set(SKIP_AUTH, true) }).

Interceptors read it with req.context.get(SKIP_AUTH) and adjust their behavior: skip the auth header, skip the global error toast, enable caching, set a retry count, or suppress the loading spinner. This keeps interceptors generic and configurable without hacks such as custom headers or URL patterns.


172. How would you implement a token-refresh flow in an interceptor that handles multiple concurrent 401 responses?

The interceptor catches a 401 (skipping the refresh endpoint itself). If no refresh is in progress, it sets an isRefreshing flag, clears a shared refreshedToken$ subject (a BehaviorSubject set to null), and calls the refresh API. On success it stores the new token, emits it on the subject, and retries the original request with the new header.

Requests that fail with 401 while a refresh is in progress do not trigger another refresh. They wait: refreshedToken$.pipe(filter(t => t !== null), take(1), switchMap(t => next(addToken(req, t)))). If the refresh fails, all waiting requests error, the session is cleared, and the user is redirected to login. Use shareReplay on the refresh Observable, or the flag-plus-subject pattern, so exactly one refresh call happens no matter how many requests fail at once.


173. How do you test HTTP calls with provideHttpClientTesting() and HttpTestingController?

Configure TestBed with providers: [provideHttpClient(), provideHttpClientTesting()], adding withInterceptors if you want interceptors in the test. Inject the service under test and HttpTestingController. Call the service method and subscribe, or read its resource, and the request is captured instead of sent.

Then assert and respond: const req = httpTesting.expectOne('/api/users/1'); expect(req.request.method).toBe('GET'); req.flush({ id: 1, name: 'Ann' });. Simulate errors with req.flush('fail', { status: 500, statusText: 'Server Error' }) or req.error(new ProgressEvent('error')). Call httpTesting.verify() in afterEach to make sure no unexpected requests remain. Use match() for multiple requests and expectNone() to assert that no call was made.

SECTION 12: PERFORMANCE & BUILD (174–183)
------------------------------------------------------------------

174. List the main techniques for optimizing an Angular application's runtime performance.

For change detection, use OnPush everywhere, use signals for state, and go zoneless where possible. Use track in @for loops, avoid method calls and heavy getters in templates (prefer pure pipes or computed), and run noisy third-party work outside Angular's zone. For rendering, use virtual scrolling for long lists, pagination, @defer for below-the-fold or heavy widgets, and NgOptimizedImage for images.

For loading performance, lazy load routes, keep the initial bundle within budget, preload intelligently, and use SSR or prerendering with hydration, including incremental hydration, for faster first paint. Remove unused dependencies and polyfills, enable HTTP caching and compression, and use a CDN. Measure with Angular DevTools, Lighthouse, and Web Vitals rather than guessing.


175. How do you analyze bundle size, and how do build budgets work?

Run ng build --stats-json. With the esbuild-based builder this produces a metafile you can load into an esbuild bundle analyzer; with webpack it works with webpack-bundle-analyzer. source-map-explorer on the production source maps also shows which modules occupy space. The build output also lists the initial and lazy chunk sizes.

Budgets in angular.json, under configurations.production.budgets, set thresholds: { type: 'initial', maximumWarning: '500kB', maximumError: '1MB' } and { type: 'anyComponentStyle', maximumWarning: '4kB' }. Other types include bundle, allScript, and any. Builds warn or fail when they exceed a budget, which catches regressions in CI. Track bundle size over time and investigate every large new dependency.


176. What is tree-shaking, and what code patterns defeat it?

Tree-shaking is dead-code elimination during bundling. Using static ES module imports and exports, the bundler includes only code that is reachable from your entry points, and the optimizer then removes unused exports.

Patterns that defeat it include CommonJS dependencies (require and module.exports), which cannot be statically analyzed; the CLI warns about them. Others are module-level side effects (top-level code that registers something on import) and packages without "sideEffects": false. Importing whole libraries (import * as _ from 'lodash' instead of lodash-es or per-method imports), dynamic property access on namespaces, and eager provider arrays in NgModules instead of providedIn also prevent it. Large barrel files with side effects can pull in more than needed.


177. What is the esbuild/Vite-based application builder, and how does it differ from the older webpack builder?

The application builder (@angular-devkit/build-angular:application, and @angular/build in newer setups) uses esbuild to compile and bundle, and Vite as the development server. It has been the default for new projects for several major versions and also handles SSR and prerendering in the same build.

Compared with the webpack-based browser builder, it is much faster for both cold and incremental builds, produces ESM output with simpler configuration, and integrates SSR with a single output folder. The trade-off is that it does not support custom webpack configuration. Teams that relied on webpack plugins (some Module Federation setups, custom loaders) need alternatives such as esbuild plugins or Native Federation. ng update offers a migration schematic.


178. What is virtual scrolling in the CDK, and when should you use it?

Virtual scrolling, from @angular/cdk/scrolling, renders only the items visible in the viewport plus a small buffer, and recycles DOM nodes as the user scrolls. You use <cdk-virtual-scroll-viewport itemSize="48"> with *cdkVirtualFor in place of a normal loop. Thousands of rows then cost about as much as a few dozen.

Use it for long lists and tables (hundreds to millions of rows) where pagination is undesirable, such as logs, chat histories, and large dropdowns. Fixed item sizes work best, while variable heights need the experimental autosize strategy or a custom one. Drawbacks include harder in-page find (Ctrl+F), accessibility considerations, and complexity with sticky headers. Paginated or infinite-scroll APIs combine well with it.


179. What does NgOptimizedImage do, and what performance problems does it address?

NgOptimizedImage is a directive applied by using ngSrc instead of src on <img>, together with width and height or fill. It enforces image best practices and generates them for you: automatic srcset and sizes for responsive images (with an image CDN loader), loading="lazy" by default, fetchpriority="high" and preload hints for images marked priority, and optional blurred placeholders.

It addresses Largest Contentful Paint (LCP), by prioritizing the hero image and warning in development if the LCP image is not marked priority. Required dimensions prevent Cumulative Layout Shift. It also avoids oversized downloads, cuts wasted bandwidth through lazy loading, and warns about distorted aspect ratios. Built-in loaders exist for Cloudinary, Imgix, ImageKit, Cloudflare, and Netlify, and you can provide custom ones.


180. How do you use Web Workers in an Angular application?

Generate one with ng generate web-worker app. This creates app.worker.ts and a tsconfig.worker.json and configures the build. In a component or service, create it with const worker = new Worker(new URL('./app.worker', import.meta.url), { type: 'module' }), send data with worker.postMessage(data), and receive results through worker.onmessage. The worker file uses addEventListener('message', ...) and postMessage.

Use workers for CPU-heavy work that would block the main thread, such as parsing large files, image processing, complex calculations, and searching or sorting big datasets. Workers cannot access the DOM or Angular services, and data is copied between threads, or transferred for ArrayBuffers. Guard their creation for SSR (typeof Worker !== 'undefined'), and wrap the message API in an Observable or Promise service for ergonomic use.


181. How do @defer blocks and lazy-loaded routes differ as code-splitting tools?

Lazy routes, loadComponent and loadChildren, split code by navigation. A route's chunk loads when the user goes to that URL, which suits whole pages and features. @defer splits code within a template. A part of the current page loads when a trigger fires (viewport, idle, interaction, or a condition), which suits heavy widgets, below-the-fold sections, charts, editors, and dialogs.

They complement each other: lazy routes keep the initial bundle small, and @defer keeps each route's chunk small and improves that page's first render. @defer also offers placeholders, loading and error states, prefetching, and SSR hydration triggers built in, whereas route lazy loading relies on the router's preloading strategies. Both require the deferred code to be standalone and not imported eagerly elsewhere.


182. How do you detect and fix memory leaks in an Angular app?

To detect leaks, use the Chrome DevTools Memory panel. Take heap snapshots before and after repeatedly navigating to and from a page, then look for detached DOM trees and component instances that keep growing. The Performance monitor's JS heap and DOM node counts help too. Leaks show up as memory that never returns to baseline after garbage collection.

Common causes and fixes: subscriptions that never complete (use the async pipe, toSignal, or takeUntilDestroyed); event listeners added manually to window or document without removal (use host listeners, Renderer2.listen, which returns an unlisten function, or DestroyRef); timers and intervals; third-party widgets not destroyed in ngOnDestroy; and global caches or services holding references to components. Also watch shareReplay without refCount on infinite streams and effects created repeatedly without being destroyed.


183. What are Angular Elements, and how do they relate to micro-frontend approaches such as Module Federation or Native Federation?

Angular Elements (@angular/elements) package an Angular component as a standard Custom Element (Web Component) with createCustomElement(MyComponent, { injector }) and customElements.define('my-widget', el). Inputs become attributes and properties, and outputs become DOM CustomEvents. Any HTML page or framework can then use the component.

In micro-frontends, Elements are one integration strategy: each team ships Web Components that a shell page composes, which works across frameworks. Module Federation (webpack) and Native Federation (esbuild and import maps, used with the application builder) load separately built and deployed remote apps or modules at runtime and share dependencies such as Angular itself, so it is not downloaded twice. Federation suits Angular-on-Angular setups with shared routing, and Elements suit framework-agnostic embedding. The approaches can be combined, but each adds operational complexity, so micro-frontends should be justified by team and deployment needs.

SECTION 13: TESTING (184–192)
------------------------------------------------------------------

184. How do you configure TestBed for a standalone component?

Import the component itself, since it is standalone and carries its own dependencies: await TestBed.configureTestingModule({ imports: [UserCardComponent], providers: [{ provide: UserService, useValue: mockUserService }, provideRouter([]), provideHttpClient(), provideHttpClientTesting()] }).compileComponents();. Then create it: fixture = TestBed.createComponent(UserCardComponent).

To replace a child component or directive, use TestBed.overrideComponent(UserCardComponent, { set: { imports: [StubChild] } }) or a remove/add combination. Component-level providers are overridden the same way. Call fixture.detectChanges() or await fixture.whenStable() to render, or enable auto change detection. In zoneless setups, add provideZonelessChangeDetection() to the test providers.


185. How do you unit test a component's inputs and outputs?

For inputs, including signal inputs, use fixture.componentRef.setInput('user', { name: 'Ann' }), then fixture.detectChanges() or await fixture.whenStable(), and assert on the DOM: expect(el.querySelector('h2')?.textContent).toContain('Ann'). setInput marks the component dirty correctly. Assigning to a signal input directly is not possible, which is why setInput is needed.

For outputs, subscribe programmatically: let emitted; component.saved.subscribe(v => emitted = v);. Then trigger the UI action (button.click() and a detectChanges) and assert on emitted. Alternatively, test through a small host component that binds inputs and outputs in a template, which exercises the real binding path. Prefer asserting on rendered output and emitted events over internal state.


186. How do you mock services and dependencies with spies or test doubles?

Use a spy object such as jasmine.createSpyObj('UserService', ['getUser']), or an object of vi.fn() mocks in Jest or Vitest, with a returned value: getUser.and.returnValue(of(user)) or mockResolvedValue. Provide it with { provide: UserService, useValue: mock }. Then assert on interactions: expect(mock.getUser).toHaveBeenCalledWith('1').

For signal-based services, a fake class with writable signals is often clearer: { user: signal(null), load: vi.fn() }. Prefer fakes that mirror the real interface (typed with Partial<UserService> or jasmine.SpyObj<UserService>) to avoid drift from the real service. Mock at boundaries (HTTP, storage, time) rather than mocking everything, so tests still verify real behavior.


187. Explain fakeAsync, tick, flush, and waitForAsync.

fakeAsync(() => { ... }) runs a test in a special zone where timers and Promise microtasks are virtualized, so asynchronous code reads like synchronous code. tick(ms) advances virtual time and runs due timers and pending microtasks. flush() runs all remaining macrotasks until the queue is empty, and flushMicrotasks() drains only microtasks. The test fails if timers remain pending at the end, unless you discard them.

waitForAsync(() => { ... }) runs the test in a zone that waits for all real async operations to finish before completing, often combined with await fixture.whenStable(). Both depend on Zone.js. In zoneless tests, prefer native async/await with fixture.whenStable() and your runner's fake timers (jasmine.clock() or vi.useFakeTimers()).


188. What are CDK component harnesses, and why do they make tests more robust?

Component harnesses (@angular/cdk/testing) are classes that expose a semantic API for interacting with a component, such as await button.click(), await select.open(), and await input.setValue('x'), instead of querying internal DOM structure and CSS classes. Angular Material ships harnesses for all its components, and you can write your own by extending ComponentHarness.

You get them through a loader: const loader = TestbedHarnessEnvironment.loader(fixture); const btn = await loader.getHarness(MatButtonHarness.with({ text: 'Save' }));. Tests become more robust because they do not break when a library changes its internal markup, they read like user interactions, they handle change detection and async stabilization automatically, and the same harness can run in unit tests and in end-to-end environments.


189. How do you test signals, computed values, and effects?

Plain signals and computeds are synchronous, so test them directly: store.add(item); expect(store.total()).toBe(10);. No async handling is needed. For components, set inputs with setInput, trigger change detection, and assert on the DOM or on computed values.

Effects are scheduled rather than synchronous, so after changing state, call TestBed.tick() (which replaced the older TestBed.flushEffects()), or await fixture.whenStable() in component tests, and then assert on the side effect. Create effects in an injection context, through the service or component under test or with TestBed.runInInjectionContext. For resources and httpResource, combine HttpTestingController with whenStable or tick to resolve loading states.


190. How do you test functional guards, resolvers, and interceptors?

Guards and resolvers are functions that need an injection context, so call them with TestBed.runInInjectionContext(() => authGuard(route, state)) after providing mocks, such as an AuthService that returns logged-out, and assert on the result: true, or a UrlTree to /login. Build ActivatedRouteSnapshot and RouterStateSnapshot as simple casted objects, or test through the real router with RouterTestingHarness and its navigateByUrl.

For interceptors, configure provideHttpClient(withInterceptors([authInterceptor])) and provideHttpClientTesting(). Make a request with HttpClient and use HttpTestingController to assert that the outgoing request has the expected header (req.request.headers.get('Authorization')). Flush error responses to test 401 handling and retries. Alternatively, call the interceptor function directly with a fake next handler inside runInInjectionContext.


191. What tools are used for end-to-end testing now that Protractor is deprecated?

Protractor was deprecated and has reached end of life, and new CLI projects no longer include an e2e tool by default. ng e2e prompts you to add one through ng add: Cypress (@cypress/schematic), Playwright (playwright-ng-schematics), WebdriverIO, or Puppeteer.

Playwright is popular for its speed, parallel cross-browser support (Chromium, Firefox, WebKit), auto-waiting, trace viewer, and network mocking. Cypress offers an excellent interactive runner and debugging experience and also supports component testing. Whichever you choose, use stable selectors (data-testid or accessible roles), mock or seed back-end data for determinism, and run the suite in CI against a production build.


192. Compare test runners for Angular: Karma, Jest, Vitest, and Web Test Runner.

Karma, the historical default with Jasmine, runs tests in a real browser. It has been deprecated, and the Angular team has been moving off it. Jest runs in Node with jsdom and is fast, with great mocking and snapshots. It has long been a popular community choice (jest-preset-angular), and the CLI added experimental support at one point.

Vitest is Vite-native and fast, with Jest-compatible APIs, and can run in Node (jsdom or happy-dom) or in a real browser mode. Recent Angular versions provide official Vitest support and make it the default for new projects. Web Test Runner was another experimental option that runs Jasmine-style tests in real browsers. For new projects use the current CLI default, which is Vitest in recent versions. For existing Karma suites, plan a migration, using the CLI's migration tooling where available.

193. Explain server-side rendering, prerendering (SSG), hydration, and incremental hydration in Angular.

SSR renders the application's HTML on a Node or edge server for each request, so users and crawlers get content immediately, which improves first contentful paint, LCP, and SEO. Prerendering (SSG) does the same at build time for routes that can be static. Both are set up with ng add @angular/ssr or ng new --ssr. Server route configuration lets you choose a render mode per route: RenderMode.Server, Prerender, or Client.

Hydration (provideClientHydration()) lets the client-side app reuse the server-rendered DOM instead of destroying and re-creating it. That avoids flicker and layout shifts, and Angular warns about DOM mismatches. withEventReplay() captures user clicks made before hydration finishes and replays them afterwards. Incremental hydration (withIncrementalHydration()) leaves @defer blocks as static server HTML and hydrates them, downloading their code, only when a trigger such as hydrate on viewport or hydrate on interaction fires. That reduces JavaScript on the critical path.


194. How do you safely handle browser-only APIs in an SSR app?

During SSR, objects such as window, document (beyond Angular's server DOM), localStorage, navigator, and IntersectionObserver do not exist, and accessing them crashes rendering. Put DOM and browser code in afterNextRender or afterEveryRender, which run only in the browser. You can also check isPlatformBrowser(inject(PLATFORM_ID)) before using such APIs.

Inject DOCUMENT instead of using the global document, and use Renderer2 or host bindings for DOM manipulation. Wrap storage in a service that falls back to in-memory or no-op behavior on the server. Lazy load browser-only libraries with dynamic import() inside browser-only paths, or with @defer, whose content is not rendered on the server unless hydration triggers are configured. Avoid long-running timers on the server, because they keep the render from becoming stable.


195. What is TransferState, and how does the HTTP transfer cache prevent duplicate requests after hydration?

TransferState is a key-value store that is serialized into the server-rendered HTML in a script tag and read on the client. Data computed on the server can be reused in the browser, using makeStateKey<T>('key'), set() on the server, and get() on the client.

The HTTP transfer cache, enabled by default with provideClientHydration(), uses this mechanism automatically for HttpClient. GET and HEAD responses fetched during SSR are embedded in the page, and identical requests made during client bootstrap are answered from the cache instead of the network. This prevents a double fetch and content flicker. withHttpTransferCacheOptions() configures which requests are cached, for example including POST, filtering by URL, or excluding requests with auth headers, which are excluded by default for safety.


196. What XSS protections does Angular provide by default? What are the risks of DomSanitizer's bypassSecurityTrust* methods?

Angular treats all values as untrusted by default. Interpolation and property bindings escape content. Binding to dangerous contexts, such as [innerHTML], style, href or src URLs, and resource URLs for iframes and scripts, triggers automatic sanitization: Angular strips script tags, event-handler attributes, and javascript: URLs, with a development-mode warning. Templates are compiled ahead of time, so attackers cannot inject template syntax, and Trusted Types are supported for an extra layer.

DomSanitizer's bypassSecurityTrustHtml, Style, Script, Url, and ResourceUrl methods tell Angular to skip sanitization for a value. If that value contains any user-controlled input, you have created an XSS vulnerability. Use them only for content you fully control or have sanitized with a vetted library such as DOMPurify, keep them in one reviewed place, and never pass user data to them. Also avoid direct DOM APIs such as element.innerHTML, which bypass Angular's protections entirely.


197. How does HttpClient support XSRF/CSRF protection, and how do you make Angular work with a strict Content Security Policy?

For XSRF, if the server sets a cookie (default name XSRF-TOKEN), HttpClient reads it and sends it back in a header (default X-XSRF-TOKEN) on mutating requests (POST, PUT, PATCH, DELETE) to relative or same-origin URLs. The server checks that the header matches the cookie, which a cross-site attacker cannot do. You can configure the names with withXsrfConfiguration({ cookieName, headerName }) or disable the behavior with withNoXsrfProtection(). The server-side check is still required, and SameSite cookies add further defense.

For CSP, avoid unsafe-inline and unsafe-eval. AOT means no eval is needed. Angular inlines critical CSS and adds some inline styles, so supply a nonce: put ngCspNonce="..." on the root element, or provide the CSP_NONCE token, and have the server generate a fresh nonce per response and include it in the header. Newer versions offer an autoCsp build option that generates a hash-based CSP for inline scripts. Also enable Trusted Types (require-trusted-types-for 'script'), which Angular supports.


198. How does internationalization work with @angular/localize and $localize? Compare build-time translation with runtime approaches.

The built-in i18n flow marks text with the i18n attribute in templates (<h1 i18n="@@welcome">Welcome</h1>) and with $localize tagged strings in code ($localize`:@@greeting:Hello ${name}`). ng extract-i18n generates a source translation file (XLIFF, XMB, or JSON). Translators produce per-locale files, and the build inlines each locale's translations, producing a separate optimized bundle per locale (ng build --localize). ICU expressions handle plurals and selects.

Build-time translation gives the best runtime performance (no lookups and no translation files to download), type-safe IDs, and AOT-checked templates. The costs are one build and deployment per locale, and switching language means a page reload or a different URL. Runtime libraries such as Transloco or ngx-translate load JSON at runtime and switch languages instantly without a reload, at the cost of runtime lookups and keys that are not type-checked. $localize also supports runtime loading through loadTranslations before bootstrap. Choose build-time i18n for content-heavy public sites with fixed locales, and runtime i18n for apps that need in-app language switching or CMS-driven translations.


199. What state management options exist, and how do you decide when a library is justified?

The options, roughly from simplest to heaviest, are: component state with signals; services holding signals (or BehaviorSubjects) scoped at root, route, or component level; NgRx SignalStore for structured, composable stores; and classic NgRx Store, NGXS, or similar Redux-style global stores with actions, reducers, effects, and DevTools. Server-state libraries such as TanStack Query handle caching and refetching of API data specifically.

Start simple. Signal-based services cover most apps. Introduce a library when you have real pain: many features sharing complex, frequently changing state, a need for strict auditability or time-travel debugging, large teams that benefit from enforced conventions, complex side-effect orchestration, or caching and synchronization logic you are rewriting repeatedly. Separate server state (fetched data) from client state (UI), because they need different tools. Avoid putting everything in a global store by default.


200. Scenario: You are designing a large enterprise Angular application for several teams. How would you structure the codebase?

I would use a monorepo, typically Nx, with one or more apps and many libraries organized by domain (orders, billing, users) and by type: feature libs (smart routed pages), ui libs (presentational components), data-access libs (services, stores, API clients), and util libs (pure functions). Lint rules (Nx module boundaries with tags) enforce dependency direction. For example, a ui lib cannot import data-access, and one domain cannot import another's internals, only its public API. All components are standalone, every feature is lazy loaded through loadChildren, a shell app handles layout, auth, and routing, and a shared design system library provides themed components and tokens.

Conventions would be OnPush plus signals everywhere, aiming for zoneless; typed reactive forms; functional guards and interceptors; SignalStore or signal services per domain, with classic NgRx only where justified; and a generated, typed API client from OpenAPI. Strict TypeScript and strictTemplates are enabled. Custom schematics or Nx generators scaffold features consistently, and code owners map libraries to teams.

For quality and delivery, I would use unit tests with Vitest and harnesses for libraries, Playwright end-to-end tests for critical journeys, affected-only builds and tests in CI with remote caching, bundle budgets, and Lighthouse checks. SSR or prerendering applies where SEO or LCP matters, and runtime configuration keeps a build-once, deploy-anywhere pipeline. Micro-frontends (Native Federation) only make sense if teams truly need independent deployments; otherwise a well-bounded monorepo is simpler. I would document architecture decisions (ADRs) and schedule Angular upgrades every six months so the codebase never falls more than one major version behind.
