SOLUTIONS: 200 JAVA PROGRAMMING TECHNICAL INTERVIEW QUESTIONS
(Companion to java_interview_questions.txt. Each answer is two paragraphs / ten sentences or fewer.
A few coding questions also include a short code sketch.)
=====================================================================


SECTION 1: CORE LANGUAGE & OBJECT-ORIENTED PROGRAMMING (1-25)
---------------------------------------------------------------------

Q1. What is the difference between the JDK, the JRE, and the JVM?
The JVM (Java Virtual Machine) is the runtime engine that loads bytecode, verifies it, executes it through an interpreter and JIT compiler, and manages memory with garbage collection. The JRE (Java Runtime Environment) is the JVM plus the core class libraries needed to run Java programs. The JDK (Java Development Kit) is the JRE plus development tools such as javac, jar, javadoc, jdb, jshell, and jlink.
Since Java 11, Oracle no longer ships a separate JRE download; instead you can build a trimmed custom runtime with jlink. In short: JVM runs code, JRE lets you run applications, and JDK lets you build them.

Q2. Why is Java described as "write once, run anywhere"? What makes it platform independent?
The javac compiler produces platform-neutral bytecode in .class files rather than native machine code for a specific CPU and OS. Any machine with a compatible JVM can execute that bytecode, because the JVM translates it to native instructions at runtime through interpretation and JIT compilation. The bytecode is portable, but the JVM itself is platform specific. Portability can still break through native code (JNI), hard-coded file paths or line separators, or OS-specific behavior.

Q3. Explain the four pillars of OOP and how Java supports each.
Encapsulation hides internal state behind private fields and exposes behavior through methods, reinforced by packages and modules. Inheritance lets a class reuse and specialize another via extends, and implement contracts via implements. Polymorphism allows one reference type to refer to many object types: compile-time polymorphism through overloading and runtime polymorphism through overriding with dynamic dispatch. Abstraction exposes what an object does rather than how, using abstract classes and interfaces.

Q4. What is the difference between an abstract class and an interface? When would you choose one over the other?
An abstract class can have instance fields, constructors, any access modifiers, and both abstract and concrete methods, but a class can extend only one. An interface defines a contract; its fields are implicitly public static final, it can have default, static, and private methods but no instance state, and a class can implement many interfaces.
Choose an abstract class when closely related classes share state or substantial implementation and form a genuine "is-a" hierarchy. Choose an interface to describe a capability that unrelated classes might share (Comparable, Runnable) or when you need multiple inheritance of type. A common pattern combines both: an interface for the type plus a skeletal abstract implementation, such as List and AbstractList.

Q5. Can an interface contain method implementations? Explain default, static, and private interface methods.
Yes, since Java 8. Default methods provide an implementation that implementing classes inherit and may override, which allows interfaces to evolve without breaking existing implementations (for example, Iterable.forEach). Static interface methods belong to the interface itself, are called as InterfaceName.method(), and are not inherited by implementing classes. Private interface methods (Java 9) let default and static methods share helper code without exposing it. Interfaces still cannot have instance fields or constructors.

Q6. What is the difference between method overloading and method overriding?
Overloading means multiple methods with the same name but different parameter lists (number, type, or order) in the same class hierarchy; it is resolved at compile time based on the static types of the arguments, and return type alone cannot distinguish overloads. Overriding means a subclass provides a new implementation of an inherited instance method with the same signature; it is resolved at runtime based on the actual object type. Overriding requires a compatible return type, no weaker access, and no broader checked exceptions. Use @Override so the compiler catches accidental overloads.

Q7. Can you override a static method? What happens if a subclass declares a static method with the same signature?
No. Static methods are bound to the class at compile time, so there is no dynamic dispatch. A subclass static method with the same signature hides the parent's method, and which one runs depends on the declared type of the reference, not the object. For example, with Parent p = new Child(), p.staticMethod() calls Parent's version. Declaring an instance method with the same signature as an inherited static method (or vice versa) is a compile error.

Q8. Can you override a private or final method? Why or why not?
A private method is not visible to subclasses, so it cannot be overridden; a method with the same signature in a subclass is simply a new, unrelated method. A final method explicitly forbids overriding, and attempting it is a compile error. Methods are made final to protect invariants (for example, template methods that must keep a fixed algorithm) and to prevent subclasses from changing critical behavior. Static methods are likewise hidden rather than overridden.

Q9. What is a covariant return type?
Since Java 5, an overriding method may return a subtype of the overridden method's return type. For example, Object.clone() returns Object, but an override in MyClass can return MyClass, which spares callers a cast. The compiler generates a synthetic bridge method with the original return type to preserve binary compatibility. Covariance applies only to reference types; primitive return types must match exactly.

Q10. What are the rules for access modifiers and return types when overriding a method?
The overriding method cannot reduce visibility: a public method must stay public, and a protected method can stay protected or become public. The return type must be the same or a covariant subtype, and primitive return types must match exactly. The override may not declare new or broader checked exceptions, though it may declare fewer, narrower, or any unchecked exceptions. The method name and parameter types (after erasure) must match, and final, static, and private methods cannot be overridden.

Q11. Explain the difference between == and equals().
For primitives, == compares values; for references, it checks identity, meaning whether both references point to the same object. equals() is intended for logical equality, and while Object's default implementation is just ==, classes such as String, Integer, and the collections override it to compare contents. Thus new String("a") == new String("a") is false, but equals() returns true. Use Objects.equals(a, b) for null-safe comparison, and == is fine for enums and other singletons.

Q12. What is the contract between equals() and hashCode()? What breaks if you violate it?
If a.equals(b) is true, then a.hashCode() must equal b.hashCode(); unequal objects may share a hash code, but that should be rare for good performance. hashCode() must be consistent across calls as long as the fields used by equals() do not change. equals() itself must be reflexive, symmetric, transitive, consistent, and return false for null.
If you override equals() without hashCode(), hash-based collections break: you can put an object in a HashMap or HashSet and then fail to find it with an equal key, or end up with "duplicate" elements in a set. Generate both together using Objects.hash, an IDE, or a record.

Q13. What does the final keyword mean when applied to a variable, a method, and a class?
A final variable can be assigned only once; for a reference, the reference cannot change but the object it points to can still be mutated. Final fields must be assigned by the end of the constructor and get special memory-model guarantees for safe publication across threads. A final method cannot be overridden by subclasses. A final class cannot be extended, as with String and Integer.

Q14. What is the difference between final, finally, and finalize()?
final is a modifier that prevents reassignment, overriding, or subclassing. finally is a block attached to try that runs whether or not an exception occurs, used for cleanup. finalize() is a method on Object that the garbage collector could call before reclaiming an object. It was deprecated in Java 9 and deprecated for removal in Java 18 because it is unpredictable, slow, and a security risk; the three share only a similar name.

Q15. Explain the static keyword: static variables, static methods, static blocks, and static nested classes.
A static variable has a single copy per class shared by all instances. A static method belongs to the class, is called without an instance, has no this reference, and cannot directly access instance members. A static block runs once when the class is initialized and is used for complex static setup. A static nested class does not hold a reference to an outer instance and can be instantiated independently. Static imports also let you use static members without qualifying them.

Q16. What is the order of initialization when an object is created?
When a class is first used, superclass static initialization runs first, followed by the class's static field initializers and static blocks in textual order, and this happens only once. On each new, memory is allocated and all fields are set to default values, then the constructor runs and first invokes super() up the hierarchy. After the superclass constructor returns, the class's instance field initializers and instance initializer blocks run in textual order, followed by the rest of the constructor body. A classic pitfall is calling an overridable method from a superclass constructor, because the subclass's fields are not yet initialized when it runs.

Q17. Can a constructor be private? What are the use cases?
Yes, and it prevents code outside the class from instantiating it directly. Use cases include singletons, classes that expose static factory methods (such as valueOf or of), non-instantiable utility classes like Math and Collections, and builder patterns where the nested builder calls the private constructor. Enum constructors are implicitly private. A class with only private constructors also cannot be subclassed from outside its own nest.

Q18. What is constructor chaining? How do this() and super() work, and why must they be the first statement?
Constructor chaining is one constructor calling another: this(...) calls another constructor in the same class to avoid duplication, and super(...) calls a superclass constructor. If neither is written, the compiler inserts an implicit super(). The rule that the call must come first ensures the superclass is fully initialized before the subclass touches its own state, and only one of the two may appear. Java 25 finalized flexible constructor bodies (JEP 513), which allow statements before this() or super() as long as they do not reference the object under construction, such as validating arguments.

Q19. What is the difference between composition and inheritance? Why is composition often preferred?
Inheritance models an "is-a" relationship where a subclass extends a parent and reuses its code, but it couples the subclass tightly to the parent's implementation and suffers from the fragile base class problem. Composition models a "has-a" relationship where a class holds a reference to another object and delegates to it. Composition is usually preferred because behavior can be swapped at runtime, encapsulation is preserved, and deep hierarchies are avoided. A classic example is a subclass of HashSet that counts additions and double-counts because addAll() internally calls add(); a wrapper class that delegates avoids this. Use inheritance only for genuine subtypes in classes designed for extension.

Q20. Why does Java not support multiple inheritance of classes? How does it resolve the diamond problem with default methods?
Java avoids multiple class inheritance to prevent ambiguity about which inherited state and implementation to use (the diamond problem) and to keep the language simpler; multiple inheritance of type is still possible through interfaces. With default methods, Java resolves conflicts with three rules. First, a method declared in a class or superclass always wins over interface defaults. Second, a more specific interface (a subinterface) wins over its parent. Otherwise, if two unrelated interfaces supply the same default, the class must override the method, and it may call a particular one with InterfaceName.super.method().

Q21. What are the different kinds of nested classes? How do they differ?
A static nested class has no reference to an outer instance and can access only the outer class's static members (including private ones). An inner (non-static member) class is tied to an outer instance, can access its fields, is created with outer.new Inner(), and holds a hidden reference to the outer object, which can cause memory leaks. A local class is declared inside a method, is visible only there, and can capture effectively final local variables. An anonymous class is an unnamed local class declared and instantiated in one expression for one-off implementations, now largely replaced by lambdas for functional interfaces. Prefer static nested classes unless you truly need the outer instance.

Q22. Is Java pass-by-value or pass-by-reference? Explain with an example involving objects.
Java is strictly pass-by-value. For primitives the value is copied, and for objects the value of the reference is copied. A method can therefore mutate an object through the copied reference, but reassigning the parameter does not affect the caller's variable. For example, in void m(StringBuilder sb) { sb.append("x"); sb = new StringBuilder("y"); }, the caller sees "x" appended but never sees the new builder. This is also why you cannot write a method that swaps two of the caller's references.

Q23. What is an immutable class? Walk through the steps to design one correctly.
An immutable class is one whose state cannot change after construction. Make the class final (or use private constructors with factories) so subclasses cannot add mutability, declare all fields private and final, provide no setters, and initialize everything in the constructor. Defensively copy mutable inputs in the constructor and mutable outputs in getters (for example, use List.copyOf for lists and clone arrays), and do not let this escape during construction.
Immutable objects are inherently thread-safe, safe to share and cache, and ideal as HashMap keys. Records give you final fields and accessors automatically, but you still need defensive copies for mutable components.

Q24. What is the purpose of the Object class? List its methods and briefly explain each.
Object is the root of every class hierarchy, so every class implicitly extends it and gains common behavior used by collections and threading. equals() and hashCode() support logical equality and hashing, and toString() returns a string representation (by default the class name and a hex hash). getClass() returns the runtime class, and clone() (protected) makes a shallow copy if the class implements Cloneable. wait(), notify(), and notifyAll() coordinate threads using the object's monitor, and finalize() is a deprecated cleanup hook.

Q25. What is the difference between a shallow copy and a deep copy? How does clone() work, and what are its pitfalls?
A shallow copy duplicates field values, so referenced objects are shared between the original and the copy. A deep copy recursively copies referenced objects so that the copy is fully independent. Object.clone() performs a field-by-field shallow copy, requires the class to implement Cloneable or it throws CloneNotSupportedException, and is protected, so you override it as public, call super.clone(), and then deep-copy mutable fields.
Its pitfalls are many: Cloneable is a marker interface with no clone method, the checked exception is awkward, final fields cannot be reassigned during a deep copy, and no constructor runs. Copy constructors or static factories (such as new ArrayList<>(other)) are usually cleaner.


SECTION 2: STRINGS & DATA TYPES (26-40)
---------------------------------------------------------------------

Q26. Why is String immutable in Java?
Immutability provides security, because strings used for file paths, URLs, class names, and credentials cannot be altered after validation. It makes strings thread-safe without synchronization and lets String cache its hash code, which makes strings efficient HashMap keys. It also enables the string pool, where identical literals can safely share one instance. The implementation backs this up with a final class, a private final byte array, and no mutator methods. The downside is that frequent modifications create many temporary objects, and sensitive data such as passwords lingers in memory, which is why char[] is preferred for secrets.

Q27. What is the String constant pool? How does intern() work?
The string pool is a table, stored in the heap since Java 7, where string literals and compile-time constant expressions are stored once and shared, so "abc" == "abc" is true. intern() returns the canonical pooled instance: if the pool already contains an equal string, that instance is returned; otherwise this string is added and returned. This can deduplicate large numbers of repeated strings, though G1 string deduplication or your own map is often a better tool. The pool size can be tuned with -XX:StringTableSize.

Q28. How many objects are created by: String s = new String("hello"); ?
Up to two, ignoring internal arrays. The literal "hello" is placed in the string pool when the class is loaded if it is not already there, and new String creates a separate object on the heap. So the answer is one if the literal was already pooled and two otherwise. As a result, s == "hello" is false, while s.intern() == "hello" is true. There is rarely any reason to write new String with a literal.

Q29. What is the difference between String, StringBuilder, and StringBuffer?
String is immutable, so every "modification" creates a new object. StringBuilder is mutable and not synchronized, which makes it the fastest choice for building strings in a single thread. StringBuffer is also mutable but synchronized, a legacy class from Java 1.0 that is slower because of locking. In practice you should use StringBuilder, because sharing a single builder across threads is rarely a sensible design.

Q30. Why is concatenating strings with + inside a loop inefficient? How does the compiler handle concatenation in modern Java?
Each + in a loop creates a new String and copies all previous content, which gives O(n^2) behavior for n iterations. The compiler optimizes a single concatenation expression, but it cannot reuse one buffer across loop iterations. Since Java 9 (JEP 280), javac emits an invokedynamic call to StringConcatFactory, which picks an efficient concatenation strategy at runtime instead of generating StringBuilder chains. For loops, still use an explicit StringBuilder, String.join, or Collectors.joining.

Q31. What are the eight primitive types, their sizes, and their default values?
byte is 8 bits (-128 to 127), short is 16 bits, int is 32 bits, and long is 64 bits, all signed two's complement. float is 32-bit and double is 64-bit IEEE 754 floating point. char is a 16-bit unsigned UTF-16 code unit, and boolean holds true or false with a JVM-dependent size. Default values for fields and array elements are 0 for integer types, 0.0 for floating types, '\u0000' for char, false for boolean, and null for references. Local variables get no default and must be definitely assigned before use.

Q32. What are autoboxing and unboxing? What pitfalls can they introduce?
Autoboxing automatically converts a primitive to its wrapper (int to Integer), for example when adding to a List<Integer>, and unboxing does the reverse. Unboxing a null throws NullPointerException, as when Map<String, Integer>.get() returns null and is assigned to an int. Boxing in hot loops (such as Long sum += i) allocates many objects and hurts performance. Comparing wrappers with == compares references, which works only inside the cache range. Overload resolution can surprise you too: List<Integer>.remove(1) removes by index, not the value 1.

Q33. Why does "Integer a = 127, b = 127; a == b" return true, while the same code with 128 returns false?
Autoboxing calls Integer.valueOf(), which caches Integer instances from -128 to 127. Two boxed 127 values therefore refer to the same cached object, so == is true. A value of 128 is outside the cache, so two separate objects are created and == is false. The upper bound can be raised with -XX:AutoBoxCacheMax, and Byte, Short, Long, and Character have similar caches. Always compare wrapper values with equals().

Q34. What is the difference between int and Integer? When would you use each?
int is a primitive stored directly, cannot be null, defaults to 0, and is efficient in memory and speed. Integer is an object wrapper that can be null, works with generics and collections, offers utility methods, and costs extra memory for the object header plus a level of indirection. Use int for arithmetic, counters, and performance-sensitive code. Use Integer when null is meaningful (an absent value), in collections and generics, or with APIs that require objects.

Q35. Explain widening and narrowing type conversions. What happens on integer overflow?
Widening converts a smaller type to a larger one automatically (int to long, char to int, int to double), which is safe except for possible precision loss when converting int or long to float or double. Narrowing requires an explicit cast: double to int truncates toward zero, and long to int keeps only the low 32 bits. Integer overflow wraps silently in two's complement, so Integer.MAX_VALUE + 1 equals Integer.MIN_VALUE. Use Math.addExact and multiplyExact to get an ArithmeticException instead, or use long or BigInteger. Compound assignments like b += 1 on a byte include an implicit narrowing cast.

Q36. Why should you avoid float and double for monetary calculations? What should you use instead?
Binary floating point cannot represent many decimal fractions exactly, so values like 0.1 carry tiny errors that accumulate (1.10 - 1.00 is not exactly 0.10). Money requires exact decimal arithmetic and explicit, controlled rounding. Use BigDecimal created from strings (new BigDecimal("0.10"), not new BigDecimal(0.1)) with an explicit RoundingMode, or store amounts as long minor units such as cents. Note that BigDecimal.equals() considers scale (2.0 is not equal to 2.00), so use compareTo() for numeric comparison.

Q37. What does 0.1 + 0.2 == 0.3 evaluate to in Java, and why?
It evaluates to false. Neither 0.1 nor 0.2 has an exact binary representation, so their sum is 0.30000000000000004, while the literal 0.3 rounds to a slightly different double. Compare floating-point values with a tolerance, such as Math.abs(a - b) < 1e-9, or use BigDecimal for exact decimal math. Also remember that NaN is not equal to itself, so use Double.isNaN() or Double.compare().

Q38. How does Java represent characters internally?
A char is a 16-bit UTF-16 code unit. Characters outside the Basic Multilingual Plane, such as many emoji, require two chars called a surrogate pair. As a result, String.length() counts code units, not user-visible characters, so use codePointCount(), codePoints(), and Character.toChars() for full Unicode handling. Since Java 9, compact strings store Latin-1 content as one byte per character internally and switch to UTF-16 otherwise, transparently. Reversing a string char by char can break surrogate pairs, whereas StringBuilder.reverse() handles them.

Q39. How does a switch statement on Strings work under the hood?
Since Java 7, the compiler computes the hashCode of each case label and generates a lookupswitch on s.hashCode(). Within each matching hash bucket, it calls equals() to confirm the match, which handles hash collisions correctly. A second switch on a generated index then jumps to the actual case body. A null string throws NullPointerException unless the switch uses the Java 21 case null label.

Q40. What are text blocks, and what problems do they solve?
Text blocks, finalized in Java 15, are multi-line string literals delimited by triple quotes ("""). They remove the need for \n escapes and concatenation when embedding JSON, SQL, HTML, or other multi-line text. Incidental indentation is stripped based on the least-indented line (including the closing delimiter), and trailing whitespace is removed. A backslash at the end of a line joins it with the next, and \s inserts an explicit space. The result is an ordinary String, and formatted() can be used for simple interpolation.


SECTION 3: EXCEPTION HANDLING (41-55)
---------------------------------------------------------------------

Q41. Describe the Java exception hierarchy.
Throwable is the root and has two main subclasses: Error and Exception. Errors represent serious problems that applications usually should not catch, such as OutOfMemoryError and StackOverflowError. Exception subclasses are checked exceptions, except RuntimeException and its subclasses (NullPointerException, IllegalArgumentException, IndexOutOfBoundsException), which are unchecked. Errors are also unchecked. Every Throwable carries a message, an optional cause, a stack trace, and any suppressed exceptions.

Q42. What is the difference between checked and unchecked exceptions? When should you use each?
Checked exceptions must be caught or declared in a throws clause, and the compiler enforces this; they represent recoverable conditions outside the program's control, such as IOException. Unchecked exceptions (RuntimeException and Error) have no such requirement and usually indicate programming bugs like null dereferences or illegal arguments. Use checked exceptions when a caller can reasonably recover and should be forced to consider the failure. Use unchecked exceptions for precondition violations and bugs. Many modern APIs favor unchecked exceptions because checked ones compose poorly with lambdas and streams, which is why wrappers like UncheckedIOException exist.

Q43. What is the difference between throw and throws?
throw is a statement that actually throws an exception instance, as in throw new IllegalArgumentException("bad id"). throws is a clause in a method signature declaring which exceptions the method may propagate, as in void read() throws IOException. throw raises one exception object at a time, while throws can list several types. A throws declaration is required for checked exceptions that a method does not handle.

Q44. Does a finally block run if the try block contains a return statement? Are there cases where finally does not run?
Yes. The return expression is evaluated first, then finally runs, and then control returns to the caller. Modifying a returned primitive local inside finally does not change the value already being returned, although mutating a returned object does. finally does not run if System.exit() or Runtime.halt() is called, if the JVM crashes or is killed, if the thread is a daemon thread when the JVM exits, or if the try block never completes because of an infinite loop or deadlock.

Q45. What happens if both the try block and the finally block return a value?
The return in finally overrides the try block's return, and the try value is discarded. Worse, if the try block threw an exception, a return in finally silently swallows it. This makes the code misleading and hides errors, so compilers and linters warn about it. Never return from a finally block.

Q46. What is try-with-resources? Which interface must a resource implement?
Introduced in Java 7, try-with-resources declares resources in parentheses after try and closes them automatically at the end of the block, even when exceptions occur. A resource must implement AutoCloseable (Closeable extends it). Multiple resources are separated by semicolons and closed in reverse order of declaration. Since Java 9, you can also use an existing effectively final variable, as in try (reader) { ... }. If the main block throws and close() also throws, the close exception is recorded as suppressed rather than replacing the original.

Q47. What are suppressed exceptions, and how do you access them?
When the body of a try-with-resources block throws and then close() also throws, the second exception is attached to the first as a suppressed exception instead of replacing it. You access them with Throwable.getSuppressed(), which returns an array, and you can add them manually with addSuppressed(). This preserves the original root cause, which was often lost with older manual finally-based cleanup. Stack traces print these under "Suppressed:" sections.

Q48. What is multi-catch, and what restrictions apply to it?
Multi-catch, added in Java 7, lets one catch block handle several exception types, as in catch (IOException | SQLException e), which removes duplicated handling code. The alternatives cannot be related by inheritance; for example, FileNotFoundException | IOException is a compile error because one already covers the other. The catch parameter is implicitly final and cannot be reassigned. Its static type is the closest common supertype of the listed exceptions.

Q49. How do you create a custom exception? Should it be checked or unchecked?
Extend Exception for a checked exception or RuntimeException for an unchecked one, and provide the standard constructors (no-arg, message, message plus cause, and cause) that call super. You can add fields carrying context, such as an error code or the invalid value, and a serialVersionUID because Throwable is Serializable. Make it checked if callers can reasonably recover and should be forced to handle it, and unchecked for programming errors or failures callers cannot act on. End the name with "Exception," and prefer standard exceptions such as IllegalArgumentException when they already fit.

Q50. What are the rules for declared exceptions when overriding a method?
An overriding method may declare the same checked exceptions, narrower subclasses of them, fewer of them, or none at all. It may not declare new or broader checked exceptions, because callers using the parent type would not be prepared to handle them, which would violate substitutability. Unchecked exceptions are unrestricted. Constructors work the other way: a subclass constructor must declare the checked exceptions of the superclass constructor it calls (or broader ones). The same rules apply when implementing interface methods.

Q51. What is exception chaining, and why is it useful?
Exception chaining wraps a low-level exception as the cause of a higher-level one, as in throw new ServiceException("Failed to load user", e). It lets you present an exception at the right level of abstraction to callers (exception translation) while preserving the original stack trace and root cause. The cause is available through getCause(), and stack traces print it under "Caused by:". You set it through a constructor or initCause(). Passing only e.getMessage() to the new exception throws away valuable debugging information.

Q52. Why is catching Exception or Throwable generally considered bad practice?
Catching Exception also catches unchecked programming bugs such as NullPointerException, and catching Throwable additionally catches Errors like OutOfMemoryError that you generally cannot handle. Broad catches hide bugs, lead to indiscriminate handling, and can swallow InterruptedException without restoring the interrupt flag. They are acceptable at top-level boundaries, such as a thread's run loop, a request handler, or main, where you log and fail gracefully. Everywhere else, catch the specific exceptions you can actually handle.

Q53. What is the difference between ClassNotFoundException and NoClassDefFoundError?
ClassNotFoundException is a checked exception thrown when code explicitly loads a class by name (Class.forName or ClassLoader.loadClass) and the class cannot be found. NoClassDefFoundError is an Error thrown when the JVM cannot find or define a class that was present at compile time, typically because a JAR is missing at runtime. It also appears on later uses of a class whose static initializer failed earlier with ExceptionInInitializerError. The first is an anticipated failure of dynamic loading, while the second signals a broken deployment or environment.

Q54. What causes a StackOverflowError versus an OutOfMemoryError?
A StackOverflowError occurs when a thread's stack is exhausted, almost always because of unbounded or very deep recursion; fix the recursion or increase the stack size with -Xss. An OutOfMemoryError occurs when the JVM cannot allocate memory in some area. The message identifies the area: Java heap space, Metaspace, GC overhead limit exceeded, direct buffer memory, or unable to create a native thread. Common causes are memory leaks, an undersized heap, or loading too much data at once.

Q55. What are the performance costs of exceptions, and why should they not be used for control flow?
Creating an exception captures a stack trace by walking the stack, which is expensive, and throwing and unwinding can inhibit JIT optimizations. Using exceptions for control flow, such as calling parseInt inside a try block to test whether input is numeric or ending a loop with ArrayIndexOutOfBoundsException, makes code slow and obscure. Exceptions should be reserved for exceptional conditions. In hot paths, you can reduce the cost by reusing preallocated exceptions or disabling stack trace capture with the writableStackTrace constructor flag. Note that the JVM's OmitStackTraceInFastThrow optimization can drop stack traces for frequently thrown built-in exceptions, which can confuse debugging.


SECTION 4: COLLECTIONS FRAMEWORK (56-80)
---------------------------------------------------------------------

Q56. Describe the hierarchy of the Java Collections Framework.
There are two root hierarchies: Collection (which extends Iterable) and Map, which is separate. Collection's main subinterfaces are List (ordered, indexed, duplicates allowed: ArrayList, LinkedList), Set (unique elements: HashSet, LinkedHashSet, and TreeSet through SortedSet and NavigableSet), and Queue/Deque (ArrayDeque, PriorityQueue, LinkedList). Java 21 added SequencedCollection, which sits above List, Deque, and LinkedHashSet. Map implementations include HashMap, LinkedHashMap, TreeMap (via SortedMap and NavigableMap), and ConcurrentHashMap, with SequencedMap added in Java 21. Skeletal abstract classes such as AbstractList and the utility classes Collections and Arrays complete the framework.

Q57. What is the difference between Collection and Collections?
Collection is the root interface for groups of elements, extended by List, Set, and Queue. Collections is a final utility class containing static helper methods. Those helpers include sort, reverse, shuffle, max, min, frequency, nCopies, emptyList, and the unmodifiable and synchronized wrapper factories.

Q58. Compare ArrayList and LinkedList. What are the time complexities of common operations for each?
ArrayList is backed by a resizable array: get and set are O(1), adding at the end is amortized O(1), and inserting or removing in the middle is O(n) because elements must shift. It is cache-friendly and has low per-element memory overhead.
LinkedList is a doubly linked list: get(i) is O(n), adding or removing at either end is O(1), and inserting at an iterator position is O(1), but reaching that position is O(n). Each node carries two pointers plus an object header and has poor memory locality. In practice ArrayList (or ArrayDeque for queues) is almost always faster, and LinkedList is rarely the right choice.

Q59. How does an ArrayList grow internally when its capacity is exceeded?
A new ArrayList() starts with a shared empty array, and the first add allocates a default capacity of 10. When the array is full, the list grows to about 1.5 times its old capacity (old + old >> 1), allocates a new array, and copies the elements with Arrays.copyOf. This gives amortized O(1) appends. The list never shrinks automatically; trimToSize() reduces capacity, and ensureCapacity() or an initial capacity in the constructor avoids repeated growth when the size is known in advance.

Q60. How does HashMap work internally? Explain hashing, buckets, and collision handling.
HashMap stores entries in an array of buckets (Node<K,V>[] table). On put, it computes the key's hashCode(), spreads the high bits into the low bits (h ^ (h >>> 16)), and computes the index as hash & (n - 1), which works because the capacity is always a power of two. If the bucket is empty, a new node is stored; otherwise the chain is walked, and if a key with the same hash and equals() is found, its value is replaced, else a new node is appended.
get() follows the same hash-and-index steps and then scans the bucket using equals(). Collisions are handled by chaining, with long chains converted to trees in Java 8 and later. HashMap allows one null key (stored in bucket 0) and many null values, and it is not thread-safe.

Q61. What changed in HashMap's collision handling in Java 8?
Before Java 8, colliding entries formed linked lists, giving worst-case O(n) lookups that could be exploited by hash-flooding denial-of-service attacks. In Java 8, when a bucket's chain exceeds 8 entries (TREEIFY_THRESHOLD) and the table has at least 64 buckets, the bucket is converted into a red-black tree, giving O(log n) worst-case lookups. If the table is smaller than 64, the map resizes instead of treeifying. A tree bucket converts back to a list when it shrinks to 6 entries. Tree nodes are ordered by hash and then by compareTo() when keys are Comparable.

Q62. What are the default load factor and initial capacity of a HashMap? What happens during a resize?
The defaults are an initial capacity of 16 and a load factor of 0.75, so the resize threshold is capacity times load factor (12 by default). When the size exceeds the threshold, the table doubles and entries are redistributed. Because capacity is a power of two, each entry either stays at its index or moves to index + oldCapacity, decided by a single hash bit, so no full rehash is needed. Resizing is O(n), so presize maps when you know the expected size; Java 19 added HashMap.newHashMap(n) to do the load-factor math for you. A higher load factor saves memory at the cost of more collisions.

Q63. Why should HashMap keys be immutable, or at least have a stable hashCode()?
The bucket for an entry is chosen from the key's hashCode() at insertion time. If the key is later mutated so that its hash changes, the entry sits in the wrong bucket. Lookups with the same object or an equal key then fail, and the entry is effectively lost while still occupying memory. Changing the fields used by equals() causes similar problems. Use immutable keys such as String, Integer, enums, or records with immutable components.

Q64. Compare HashMap, Hashtable, and ConcurrentHashMap.
Hashtable is a legacy class from Java 1.0 whose methods are all synchronized on the whole table, giving poor concurrency, and it forbids null keys and values. HashMap is unsynchronized, allows one null key and many null values, is the fastest choice for single-threaded use, and has fail-fast iterators. ConcurrentHashMap is thread-safe with fine-grained locking and CAS operations, scales well under contention, forbids nulls to avoid ambiguity with absent keys, and has weakly consistent iterators that never throw ConcurrentModificationException. It also provides atomic compound operations such as putIfAbsent, computeIfAbsent, and merge. For concurrent code, use ConcurrentHashMap rather than Hashtable or Collections.synchronizedMap.

Q65. How does ConcurrentHashMap achieve thread safety? How did its implementation change between Java 7 and Java 8?
In Java 7, the map was divided into segments (16 by default), each a small hash table guarded by its own ReentrantLock, so writes locked only one segment and reads were mostly lock-free through volatile fields. Java 8 removed segments in favor of a single table of nodes. Inserting into an empty bin uses a CAS operation, while updating a non-empty bin synchronizes only on that bin's head node, and reads are lock-free via volatile reads. Java 8 also added tree bins and cooperative resizing, in which multiple threads help transfer entries. The size count uses striped counter cells similar to LongAdder, so concurrency is limited per bin rather than per segment.

Q66. Compare HashMap, LinkedHashMap, and TreeMap. When would you use each?
HashMap provides no ordering guarantees and O(1) average operations. LinkedHashMap adds a doubly linked list that preserves insertion order, or access order if requested in the constructor, at the cost of a little extra memory; it is the basis for simple LRU caches. TreeMap is a red-black tree sorted by the keys' natural order or a Comparator, with O(log n) operations and NavigableMap methods such as floorKey, ceilingEntry, subMap, and headMap. Use HashMap by default, LinkedHashMap when iteration order matters, and TreeMap when you need sorting or range queries. TreeMap does not allow null keys under natural ordering.

Q67. How would you implement an LRU cache using LinkedHashMap?
    class LruCache<K, V> extends LinkedHashMap<K, V> {
        private final int capacity;
        LruCache(int capacity) { super(16, 0.75f, true); this.capacity = capacity; }
        @Override protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
            return size() > capacity;
        }
    }
Passing true as the accessOrder argument makes get() and put() move the accessed entry to the end of the internal list, so the head is always the least recently used entry. removeEldestEntry() is called after every insertion, and returning true evicts that head once the capacity is exceeded. All operations stay O(1). The class is not thread-safe, so wrap it with Collections.synchronizedMap or use a dedicated caching library in concurrent code.

Q68. How does HashSet work internally?
HashSet is backed by a HashMap: each element is stored as a key, and a shared dummy object (PRESENT) is used as every value. add(e) calls map.put(e, PRESENT) and returns true if the previous value was null, so uniqueness comes directly from the map's key uniqueness via hashCode() and equals(). Performance characteristics are the same as HashMap's, and one null element is allowed. LinkedHashSet is backed by a LinkedHashMap, and TreeSet is backed by a TreeMap.

Q69. What is the difference between Comparable and Comparator?
Comparable<T> is implemented by the class itself through compareTo(T) and defines its single natural ordering, as with String and Integer. Comparator<T> is a separate object with compare(T, T), so you can define many orderings, including for classes you cannot modify. Java 8 added fluent combinators such as Comparator.comparing(Person::getAge).thenComparing(Person::getName).reversed() and nullsFirst(). Orderings should be consistent with equals(), because TreeSet and TreeMap use comparison, not equals(), to decide uniqueness. Avoid subtraction-based comparisons, which can overflow, and use Integer.compare instead.

Q70. What are fail-fast and fail-safe iterators? What causes a ConcurrentModificationException?
Fail-fast iterators, used by ArrayList and HashMap, track a modification count, and if the collection is structurally modified other than through the iterator's own remove(), the next call to next() throws ConcurrentModificationException. This is best-effort detection, and it commonly happens in a single thread, for example when removing from a list inside a for-each loop. Fail-safe iterators, more precisely snapshot or weakly consistent iterators, are found in concurrent collections. CopyOnWriteArrayList iterates over a snapshot, while ConcurrentHashMap's iterators may reflect some concurrent changes, and neither throws ConcurrentModificationException.

Q71. How do you safely remove elements from a collection while iterating over it?
Use an explicit Iterator and call iterator.remove(), or more simply use Collection.removeIf(predicate) from Java 8. For lists, you can also iterate backward by index, collect the items to remove and call removeAll() afterward, or build a new filtered collection with a stream. For maps, use map.entrySet().removeIf(...) or map.values().removeIf(...). Concurrent collections allow modification during iteration without throwing.

Q72. What is the difference between Iterator and ListIterator?
Iterator works on any Collection, moves only forward, and offers hasNext(), next(), and remove(). ListIterator is available only for lists and is bidirectional, adding hasPrevious() and previous(). It also provides nextIndex() and previousIndex(), and it can modify the list during iteration with set() and add(). You can start a ListIterator at any position with list.listIterator(index).

Q73. What are WeakHashMap and IdentityHashMap, and when would you use them?
WeakHashMap holds its keys through weak references, so an entry is removed automatically after a key is no longer strongly reachable elsewhere and has been garbage collected. It suits caches of metadata attached to objects whose lifecycle you do not control. Watch out for values that reference their own keys, which keep the keys alive, and for string literal keys, which are never collected.
IdentityHashMap compares keys with == and System.identityHashCode() instead of equals() and hashCode(), deliberately breaking the general Map contract. It is useful for tracking visited objects during graph traversal, serialization, or deep copying, where identity rather than logical equality matters.

Q74. What is the difference between Queue, Deque, and Stack? Why is ArrayDeque preferred over Stack?
Queue typically models FIFO processing with offer(), poll(), and peek() (plus add(), remove(), and element(), which throw on failure). Deque is a double-ended queue that supports insertion and removal at both ends, so it can serve as a queue or as a stack via push(), pop(), and peek(). Stack is a legacy class that extends Vector, so every method is synchronized, and it exposes Vector methods that allow insertion at arbitrary positions, breaking the LIFO abstraction. ArrayDeque is a resizable circular array without synchronization, faster than both Stack and LinkedList for stack and queue use, though it does not allow nulls. The Javadoc itself recommends Deque over Stack.

Q75. How does PriorityQueue work internally?
PriorityQueue is an unbounded queue backed by a binary heap stored in an array, and its head is the smallest element according to natural ordering or a supplied Comparator (a min-heap). offer() adds at the end and sifts up in O(log n), and poll() removes the root, moves the last element to the root, and sifts down in O(log n). peek() is O(1), while remove(Object) and contains() are O(n). Its iterator and toString() do not return elements in priority order. It is not thread-safe (use PriorityBlockingQueue for that), does not allow null, and is useful for top-k problems, Dijkstra's algorithm, and scheduling.

Q76. What is the difference between unmodifiable views and immutable collections?
Collections.unmodifiableList(list) returns a read-only view wrapping the original list: mutator methods throw UnsupportedOperationException, but changes to the underlying list still show through the view. List.of(), Set.of(), and Map.of() (Java 9) create truly immutable collections with no backing collection. They reject null elements, Set.of and Map.of reject duplicates, and Set and Map iteration order is deliberately unspecified. List.copyOf() makes an immutable copy, and Stream.toList() (Java 16) returns an unmodifiable list that does allow nulls. Remember that the elements themselves may still be mutable objects.

Q77. What does Arrays.asList() return, and what are its limitations?
It returns a fixed-size List backed directly by the array, an internal class rather than java.util.ArrayList. set() works and writes through to the array, and changes to the array are visible in the list, but add() and remove() throw UnsupportedOperationException. Passing a primitive array such as int[] produces a List<int[]> with a single element, so use Integer[] or IntStream.boxed() instead. Unlike List.of(), it allows null elements. Wrap it with new ArrayList<>(Arrays.asList(...)) when you need a resizable list.

Q78. What are EnumSet and EnumMap, and why are they so efficient?
They are specialized implementations for enum elements and keys. EnumSet is represented as a bit vector: enums with up to 64 constants use a single long, larger ones use a long array, so set operations are fast bitwise operations with tiny memory use. EnumMap uses an array indexed by each constant's ordinal, with no hashing, and iterates in declaration order. Neither allows null keys or elements, and neither is synchronized. EnumSet.of, noneOf, allOf, and range are the usual factories, and EnumSet is the idiomatic replacement for int bit flags.

Q79. What is CopyOnWriteArrayList, and when is it appropriate?
It is a thread-safe List in which every mutation (add, set, remove) copies the entire underlying array. Reads are lock-free, and iterators work on an immutable snapshot, so they never throw ConcurrentModificationException but also do not see later changes, and iterator.remove() is unsupported. It is appropriate when reads and iterations vastly outnumber writes and the list is small, as with listener lists or configuration data. It performs poorly for frequent writes or large lists because each write costs O(n). CopyOnWriteArraySet offers the same trade-off for sets.

Q80. What are sequenced collections, and what methods do they add?
Java 21 (JEP 431) introduced SequencedCollection, SequencedSet, and SequencedMap to give a uniform API to collections that have a defined encounter order. SequencedCollection adds addFirst, addLast, getFirst, getLast, removeFirst, removeLast, and reversed(), which returns a reverse-ordered view. These interfaces were retrofitted onto List, Deque, LinkedHashSet, and SortedSet. SequencedMap adds firstEntry, lastEntry, pollFirstEntry, pollLastEntry, putFirst, putLast, reversed, and sequenced views of keys, values, and entries, and it is implemented by LinkedHashMap and SortedMap. Previously, getting the last element required type-specific code such as list.get(list.size() - 1), deque.getLast(), or sortedSet.last().


SECTION 5: GENERICS (81-92)
---------------------------------------------------------------------

Q81. What are generics, and what problems do they solve?
Generics, introduced in Java 5, let you parameterize classes, interfaces, and methods with type parameters, as in List<String>. They provide compile-time type safety, turning would-be ClassCastExceptions into compile errors. They eliminate explicit casts and enable reusable, type-safe algorithms and data structures. Before generics, collections held Object, so casts were everywhere and type errors surfaced only at runtime.

Q82. What is type erasure? What are its consequences?
The compiler checks generic types and then erases them: type parameters are replaced by their bounds (Object or the first bound), casts are inserted where needed, and bridge methods are generated to preserve polymorphism. At runtime, objects carry no information about their type arguments, although some generic signatures remain in class metadata for reflection. Erasure was chosen for backward compatibility with pre-generics code.
As a consequence, you cannot write new T(), new T[], obj instanceof List<String>, or T.class, and primitives cannot be type arguments. You also cannot overload methods that differ only by type arguments, static fields are shared across all parameterizations, and generic classes cannot extend Throwable.

Q83. Why can't you create an array of a generic type (new T[])?
Arrays are reified and covariant: they know their component type at runtime and check every store, throwing ArrayStoreException on a mismatch. Because of erasure, T is unknown at runtime, so the JVM could neither create an array with the right component type nor enforce store checks, which would break array type safety. The same reasoning forbids new List<String>[10]. Workarounds include passing a Class<T> and calling Array.newInstance(clazz, n), using an internal (T[]) new Object[n] with @SuppressWarnings as ArrayList does (without exposing it), or accepting an IntFunction<T[]> generator such as String[]::new. Usually a List<T> is the better choice.

Q84. Explain bounded type parameters, such as <T extends Number>.
A bound restricts type arguments to subtypes of a given type, which lets you call that type's methods inside the generic code. For example, <T extends Number> double sum(List<T> list) can call doubleValue() on each element. Multiple bounds are written as <T extends Number & Comparable<T>>, with at most one class listed first, followed by interfaces. Erasure uses the first bound. Recursive bounds such as <T extends Comparable<T>> are common, and type parameters support only upper bounds; super appears only with wildcards.

Q85. What is the difference between <? extends T>, <? super T>, and <?>?
<? extends T> is an unknown subtype of T: you can read elements as T, but you cannot add anything except null because the exact type is unknown, so it acts as a producer. <? super T> is an unknown supertype of T: you can add T or its subtypes, but reads return only Object, so it acts as a consumer. <?> is an unbounded unknown type that can be read as Object but not added to; it fits code that only needs Object methods or size(), and unlike a raw type, it remains type-safe. Wildcards make APIs more flexible, as in addAll(Collection<? extends E>).

Q86. Explain the PECS principle.
PECS, coined by Joshua Bloch, stands for "Producer Extends, Consumer Super." If a parameterized argument produces values that your method reads, use extends; if it consumes values that your method writes, use super; if it does both, use the exact type. Collections.copy(List<? super T> dest, List<? extends T> src) is the canonical example. Comparators are typed as Comparator<? super T> because they consume T values. Following PECS lets your methods accept a much wider range of arguments, but avoid wildcards in return types.

Q87. Why is List<Object> not a supertype of List<String>?
Generics are invariant: if List<String> were a List<Object>, you could add an Integer through the Object-typed reference and corrupt a list that should hold only strings. Arrays are covariant, so String[] is an Object[]. That means Object[] arr = new String[1]; arr[0] = 1; compiles but throws ArrayStoreException at runtime, because arrays check stores dynamically. Generics catch the equivalent error at compile time, which is safer. When you need covariant, read-only access, use List<? extends Object> or List<?>.

Q88. What are raw types, and why should you avoid them?
A raw type is a generic type used without type arguments, such as List list = new ArrayList();, and it exists only for compatibility with pre-Java 5 code. Raw types lose type safety: the compiler issues unchecked warnings, anything can be inserted, and ClassCastExceptions surface later, far from the bug. Using a raw type also erases the generic types of all its members, even unrelated ones. Use List<Object> or List<?> instead. Raw types are acceptable only in class literals (List.class) and instanceof checks.

Q89. What is a generic method, and how does type inference work?
A generic method declares its own type parameters before the return type, as in static <T> List<T> listOf(T... items), independent of any class type parameters, and it may be static. The compiler infers the type arguments from the method arguments and from the target type of the assignment or call context, so Collections.emptyList() assigned to a List<String> infers T as String. Java 7 added the diamond operator, Java 8 greatly improved inference for chained calls and lambdas, and Java 9 allowed the diamond with anonymous classes. When inference fails, you can supply an explicit type witness such as Collections.<String>emptyList().

Q90. Can you overload methods that differ only in their generic type parameters? Why not?
No. After erasure, void print(List<String>) and void print(List<Integer>) both become print(List), so they have the same erased signature, and the compiler reports a name clash. The JVM distinguishes methods by their erased descriptors, so the two cannot coexist. Workarounds are to use different method names or to make the parameter lists differ in some non-generic way.

Q91. What is heap pollution, and what does @SafeVarargs do?
Heap pollution occurs when a variable of a parameterized type refers to an object that is not of that type, typically through raw types or unchecked casts, which leads to ClassCastExceptions in unexpected places. It commonly arises with generic varargs, because a parameter like List<String>... is implemented as an erased List[] array that the method could fill with the wrong elements, and the compiler warns about "possible heap pollution." @SafeVarargs (Java 7) is the author's promise that the method does not store into the varargs array or expose it, and it suppresses the warnings at call sites. It is allowed on static methods, final instance methods, constructors, and (since Java 9) private methods.

Q92. Write a generic method that returns the maximum element from a list of Comparable items.
    public static <T extends Comparable<? super T>> T max(List<? extends T> list) {
        if (list == null || list.isEmpty()) throw new NoSuchElementException("empty list");
        Iterator<? extends T> it = list.iterator();
        T best = it.next();
        while (it.hasNext()) {
            T next = it.next();
            if (next.compareTo(best) > 0) best = next;
        }
        return best;
    }
The bound Comparable<? super T> allows types that inherit compareTo() from a supertype, and List<? extends T> accepts lists of subtypes, following PECS. The method runs in O(n) and fails fast on an empty list. This mirrors the design of Collections.max(), and the same result is available with list.stream().max(Comparator.naturalOrder()).


SECTION 6: CONCURRENCY & MULTITHREADING (93-122)
---------------------------------------------------------------------

Q93. What is the difference between a process and a thread?
A process is an independent running program with its own address space, memory, and file handles; processes are heavyweight, isolated from each other, and communicate via inter-process communication. A thread is a unit of execution within a process: threads share the heap and other resources but each has its own stack and program counter. Threads are cheaper to create and switch between, and they communicate through shared memory, which requires synchronization. A JVM runs as a single process containing many threads, including main, GC, and JIT compiler threads. A fatal failure in one thread can bring down the whole process.

Q94. What are the ways to create a thread? What is the difference between Runnable and Callable?
You can extend Thread and override run(), implement Runnable and pass it to a Thread (preferred, because it separates the task from the execution mechanism and leaves you free to extend another class), or pass a lambda as the Runnable. Java 21 added builders such as Thread.ofPlatform() and Thread.ofVirtual(), plus Thread.startVirtualThread(). Best practice is to submit tasks to an ExecutorService rather than create threads by hand.
Runnable.run() returns nothing and cannot throw checked exceptions. Callable<V>.call() returns a value and can throw Exception, and submitting it to an ExecutorService yields a Future<V> for retrieving the result.

Q95. Describe the states in a thread's lifecycle.
The Thread.State enum defines six states. NEW means created but not started, and RUNNABLE means running or ready to run (including waiting on OS-level I/O). BLOCKED means waiting to acquire a monitor lock to enter a synchronized block. WAITING means waiting indefinitely via wait(), join(), or LockSupport.park(), and TIMED_WAITING covers sleep(), wait(timeout), join(timeout), and parkNanos(). TERMINATED means run() has completed or thrown, and a terminated thread can never be restarted.

Q96. What is the difference between calling start() and run() on a Thread?
start() creates a new thread of execution, which then calls run() concurrently with the caller. Calling run() directly simply executes the method in the current thread like any ordinary method call, with no concurrency at all. start() may be called only once per Thread object; a second call throws IllegalThreadStateException.

Q97. What does synchronized do? Compare synchronized methods with synchronized blocks.
synchronized provides mutual exclusion, meaning only one thread at a time can hold a given monitor. It also guarantees memory visibility, because releasing a lock happens-before any subsequent acquisition of the same lock. A synchronized instance method locks this (a static one locks the Class object) for the entire method. A synchronized block locks a chosen object only for the critical section, which reduces contention and lets you use a private lock object that outside code cannot interfere with. Intrinsic locks are reentrant, so the same thread can acquire them repeatedly, and narrow blocks are generally preferred.

Q98. What is an intrinsic lock (monitor)? Which lock does a static synchronized method acquire versus an instance synchronized method?
Every object has an intrinsic lock, or monitor, used by synchronized and by wait()/notify(). A thread acquires it on entering a synchronized region and releases it on exit, including when an exception is thrown. An instance synchronized method locks the instance (this), while a static synchronized method locks the Class object (MyClass.class). Because these are different locks, a static and an instance synchronized method can run at the same time, which is a common bug when instance-level locking is used to protect static data.

Q99. What does volatile guarantee, and what does it not guarantee?
volatile guarantees visibility: a write to a volatile variable becomes visible to subsequent reads by other threads instead of being cached. It also guarantees ordering, because a volatile write happens-before every subsequent read of that variable, so earlier writes become visible too, and it makes reads and writes of long and double atomic. It does not make compound operations atomic: count++ is a read-modify-write sequence, so concurrent increments can lose updates. It provides no mutual exclusion. Use volatile for flags, safe publication, and double-checked locking, and use atomic classes or locks for compound operations.

Q100. What is the Java Memory Model? Explain the happens-before relationship.
The Java Memory Model (JSR-133, Java 5) defines how threads interact through memory and which values a read may observe, which lets compilers and CPUs reorder and cache operations within defined limits. If action A happens-before action B, then A's effects are visible to B and ordered before it. Key rules: program order within a thread, unlocking a monitor before a later lock of the same monitor, a volatile write before a later read of the same variable, Thread.start() before the started thread's actions, and a thread's actions before another thread's successful join() on it. Happens-before is transitive, final fields are safely visible once the constructor finishes, and concurrent utilities add their own guarantees, such as a put into a concurrent collection happening-before a subsequent get. Without a happens-before edge, two threads accessing the same variable form a data race and may see stale or inconsistent values.

Q101. What is a race condition? Give an example and show how to fix it.
A race condition occurs when a program's correctness depends on the timing or interleaving of threads accessing shared mutable state, with at least one thread writing. For example, in class Counter { int count; void inc() { count++; } }, count++ is a read, an add, and a write, so two threads can both read 5 and both write 6, losing an update. Fixes include making inc() synchronized, using AtomicInteger.incrementAndGet() (which relies on CAS), or using LongAdder for heavily contended counters. You can also avoid shared mutable state entirely through thread confinement or immutability. Check-then-act races, such as if (!map.containsKey(k)) map.put(k, v), are fixed with atomic operations like putIfAbsent() or computeIfAbsent().

Q102. What is a deadlock? What are the four necessary conditions, and how can you prevent or detect one?
A deadlock is when two or more threads each wait forever for a lock held by another. All four Coffman conditions must hold: mutual exclusion, hold and wait, no preemption, and circular wait. Prevention strategies include acquiring locks in a consistent global order (breaking circular wait), using ReentrantLock.tryLock() with a timeout and backing off, minimizing lock scope, and avoiding calls to unknown code while holding a lock. Higher-level concurrency utilities often remove the need for manual locking altogether. To detect deadlocks, take a thread dump with jstack or jcmd Thread.print, which reports "Found one Java-level deadlock," or call ThreadMXBean.findDeadlockedThreads() programmatically.

Q103. What are livelock and starvation?
In a livelock, threads are not blocked but keep reacting to each other and changing state without making progress, like two people repeatedly stepping aside in a hallway; two threads that back off and retry in lockstep behave this way. Randomized backoff usually fixes it. Starvation occurs when a thread is perpetually denied CPU time or locks because others are favored, for example by greedy threads holding locks for long periods or by unfair lock acquisition. Remedies include fair locks (new ReentrantLock(true)), shorter lock hold times, and not relying on thread priorities.

Q104. How do wait(), notify(), and notifyAll() work? Why must they be called inside a synchronized block, and why inside a loop?
wait() releases the object's monitor and suspends the thread until notify(), notifyAll(), an interrupt, or a timeout; notify() wakes one arbitrary waiting thread, and notifyAll() wakes all of them, after which they compete for the lock. The caller must hold the monitor, or IllegalMonitorStateException is thrown. This requirement makes checking the condition and starting to wait atomic with respect to state changes, preventing lost wakeups.
Waiting must happen in a while loop because spurious wakeups can occur and because another thread may change the condition between the notification and reacquiring the lock. The standard pattern is synchronized (lock) { while (!condition) lock.wait(); ... }. Prefer notifyAll() unless you are certain notify() is safe, and in new code prefer java.util.concurrent tools such as Condition and BlockingQueue.

Q105. What is the difference between sleep() and wait()?
sleep() is a static Thread method that pauses the current thread for a given time, does not release any locks it holds, and does not require synchronization. wait() is an Object method that must be called while holding that object's monitor, and it releases the monitor while waiting. A waiting thread resumes on notify(), notifyAll(), a timeout, or an interrupt and must then reacquire the lock. Use sleep() for simple delays and wait() for coordinating threads around a condition. Both throw InterruptedException.

Q106. Explain join(), yield(), and interrupt(). How does thread interruption work?
join() makes the current thread wait until the target thread terminates (optionally with a timeout) and establishes a happens-before relationship with the target's actions. yield() is merely a hint that the current thread is willing to give up the CPU, with no guarantees, and is rarely useful. interrupt() sets the target thread's interrupt flag as a cooperative cancellation request; it does not forcibly stop the thread.
If the target is blocked in sleep(), wait(), join(), or an interruptible channel, it receives InterruptedException and the flag is cleared. Otherwise the thread should periodically check isInterrupted() (which preserves the flag) or Thread.interrupted() (which clears it). When you catch InterruptedException, either propagate it or restore the flag with Thread.currentThread().interrupt(), and never swallow it silently. The old Thread.stop() is unsupported in modern JDKs.

Q107. Compare ReentrantLock with synchronized. What extra features does ReentrantLock offer?
Both provide reentrant mutual exclusion with the same memory-visibility semantics. ReentrantLock adds tryLock() (immediate or timed), lockInterruptibly(), an optional fairness policy, multiple Condition objects for separate wait sets, and query methods such as isLocked() and getQueueLength(). The cost is that you must call unlock() yourself in a finally block, which is verbose and easy to get wrong. synchronized is simpler, released automatically, and well optimized by the JVM, and since Java 24 it no longer pins virtual threads. Use synchronized by default and ReentrantLock when you need its extra features.

Q108. What are ReadWriteLock and StampedLock, and when would you use them?
ReentrantReadWriteLock provides a pair of locks: many readers can hold the read lock at once, while the write lock is exclusive. It suits read-heavy data with infrequent writes, supports reentrancy and downgrading from write to read (but not upgrading), and can add overhead or starve writers under some workloads. StampedLock (Java 8) returns long stamps and supports write, read, and optimistic-read modes. With tryOptimisticRead(), you read fields without locking and then call validate(stamp), falling back to a real read lock if a write intervened. StampedLock can deliver higher read throughput, but it is not reentrant, has no Condition support, and is easier to misuse.

Q109. How do atomic classes such as AtomicInteger work? What is compare-and-swap, and what is the ABA problem?
Atomic classes (AtomicInteger, AtomicLong, AtomicReference, atomic arrays, LongAdder) provide lock-free, thread-safe operations on single variables. They are built on compare-and-swap (CAS), a hardware instruction behind compareAndSet(expected, newValue) that updates the value only if it still equals the expected value; otherwise the caller retries in a loop. Operations never block, which works well under low to moderate contention, but heavy contention causes repeated retries, which LongAdder reduces by spreading updates across cells.
The ABA problem occurs when a value changes from A to B and back to A between a thread's read and its CAS, so the CAS succeeds even though the state changed in between. This matters in lock-free data structures that reuse nodes. AtomicStampedReference and AtomicMarkableReference solve it by pairing the reference with a version stamp or mark.

Q110. What is ThreadLocal? What are its use cases and its memory-leak risks?
ThreadLocal<T> gives each thread its own independent copy of a value, stored in that thread's internal map and usually initialized with ThreadLocal.withInitial(supplier). Typical uses are per-thread instances of non-thread-safe objects and per-request context such as a user ID or trace ID, which avoids passing parameters through every layer. In thread pools, threads live a long time, so values persist across unrelated tasks unless you call remove(). The internal map holds keys weakly but values strongly, so stale entries can accumulate, and in application servers they can even leak whole class loaders. Always call remove() in a finally block, and with large numbers of virtual threads, prefer ScopedValue (final in Java 25).

Q111. What is the Executor framework, and why should you use thread pools?
The Executor framework (java.util.concurrent, Java 5) separates task submission from execution policy through Executor, ExecutorService, ScheduledExecutorService, and the Executors factory class. Thread pools reuse threads, avoiding the cost of creating and destroying one per task. They bound resource consumption by limiting thread counts and queue sizes. They also provide task lifecycle management through Futures, cancellation, and orderly shutdown, along with scheduling. For blocking, I/O-bound tasks, Java 21's newVirtualThreadPerTaskExecutor() makes pooling unnecessary.

Q112. What thread pools does the Executors class provide, and why can some of them be dangerous in production?
newFixedThreadPool(n) uses n threads and an unbounded LinkedBlockingQueue, so the queue can grow until the JVM runs out of memory under overload. newCachedThreadPool() creates threads on demand with a SynchronousQueue and no upper limit, so a load spike can create thousands of threads. newSingleThreadExecutor() runs one thread with an unbounded queue, and newScheduledThreadPool() handles delayed and periodic tasks. newWorkStealingPool() returns a ForkJoinPool, and newVirtualThreadPerTaskExecutor() (Java 21) starts a virtual thread per task. Because the unbounded variants hide back-pressure, production code often builds a ThreadPoolExecutor directly with a bounded queue, a naming thread factory, and an explicit rejection policy.

Q113. Explain the ThreadPoolExecutor parameters.
corePoolSize is the number of threads kept alive even when idle (unless allowCoreThreadTimeOut is set), and maximumPoolSize is the upper limit. On submission, if fewer than core threads are running, a new thread is created; otherwise the task is queued; if the queue is full, a new thread is created up to the maximum; and if that limit is also reached, the task is rejected. This means maximumPoolSize matters only with a bounded queue. keepAliveTime controls how long threads above the core size may sit idle before terminating, and a ThreadFactory sets thread names and daemon status.
The rejection policies are AbortPolicy (the default, which throws RejectedExecutionException), CallerRunsPolicy (the submitting thread runs the task, providing natural back-pressure), DiscardPolicy (drops the task silently), and DiscardOldestPolicy (drops the oldest queued task and retries).

Q114. What is the difference between Future and CompletableFuture?
Future (Java 5) represents a pending result with a blocking get(), isDone(), and cancel(), but it offers no callbacks, no composition, no manual completion, and clumsy error handling. CompletableFuture (Java 8) implements both Future and CompletionStage. It can be completed manually with complete() or completeExceptionally(), and it supports non-blocking callbacks (thenApply, thenAccept), composition (thenCompose, thenCombine, allOf, anyOf), error handling (exceptionally, handle, whenComplete), and timeouts (orTimeout and completeOnTimeout, Java 9). Async variants run on ForkJoinPool.commonPool() by default or on an executor you supply. This enables declarative asynchronous pipelines instead of blocking calls to get().

Q115. How do you chain and combine asynchronous tasks with CompletableFuture?
Start work with supplyAsync(() -> fetchUser(id), executor). thenApply(fn) transforms the result synchronously, like map, while thenCompose(fn) takes a function that returns another CompletableFuture and flattens it, like flatMap, for dependent async calls, avoiding a nested CompletableFuture<CompletableFuture<T>>. thenCombine(other, fn) waits for two independent futures and merges their results. allOf(futures...) returns a CompletableFuture<Void> that completes when all complete, after which you collect the results with join(), as in allOf(a, b).thenApply(v -> List.of(a.join(), b.join())). anyOf() completes with the first result, and errors are handled with exceptionally() or handle(). Supply your own executor for blocking work so you do not starve the shared common pool.

Q116. Explain CountDownLatch, CyclicBarrier, Semaphore, and Phaser.
CountDownLatch starts with a count, and threads calling await() block until other threads have called countDown() enough times to reach zero; it is one-shot and cannot be reset, which suits waiting for N services to start. CyclicBarrier makes a fixed number of threads wait for each other at a barrier point, optionally runs a barrier action when all arrive, and then resets for reuse in iterative phases, throwing BrokenBarrierException if a participant fails. Semaphore maintains a set of permits that threads acquire() and release(), limiting concurrent access to a resource such as a connection pool, and permits are not tied to an owning thread. Phaser is a flexible, reusable barrier that supports dynamic registration and deregistration of parties across multiple phases, generalizing both the latch and the barrier.

Q117. What are the main BlockingQueue implementations? Implement a producer-consumer solution with one.
BlockingQueue adds blocking put() and take() plus timed offer() and poll(). The main implementations are ArrayBlockingQueue (bounded, array-based, one lock), LinkedBlockingQueue (optionally bounded, separate put and take locks), PriorityBlockingQueue (unbounded, priority-ordered), DelayQueue (elements become available after a delay), SynchronousQueue (no capacity, direct handoff), LinkedTransferQueue, and LinkedBlockingDeque.
    BlockingQueue<Integer> q = new ArrayBlockingQueue<>(10);
    Thread producer = new Thread(() -> {
        try { for (int i = 0; i < 100; i++) q.put(i); q.put(-1); }
        catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    });
    Thread consumer = new Thread(() -> {
        try { int v; while ((v = q.take()) != -1) System.out.println(v); }
        catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    });
    producer.start(); consumer.start();
put() blocks when the queue is full, providing back-pressure, and take() blocks when it is empty, so the queue handles all synchronization. The value -1 acts as a "poison pill" that tells the consumer to stop.

Q118. What is the Fork/Join framework, and how does work-stealing function?
Fork/Join (Java 7) supports divide-and-conquer parallelism: a task splits itself into subtasks (fork), computes them, and combines the results (join). You subclass RecursiveTask<V> (which returns a result) or RecursiveAction and implement compute(): if the problem is small enough, solve it directly; otherwise split it, fork one half, compute the other, and join. Tasks run in a ForkJoinPool where each worker thread has its own double-ended queue and takes its own tasks from one end, which gives good cache locality. Idle workers steal tasks from the other end of busy workers' queues, picking older and usually larger tasks, which balances load with little contention. The common pool backs parallel streams and CompletableFuture's default async methods, and it is unsuitable for blocking I/O.

Q119. What is double-checked locking, and why does it require volatile?
Double-checked locking is a lazy-initialization optimization: check whether the instance is null without locking, and only if it is, synchronize and check again before creating it, so the lock is taken only during first creation.
    private static volatile Singleton instance;
    static Singleton getInstance() {
        Singleton r = instance;
        if (r == null) {
            synchronized (Singleton.class) {
                r = instance;
                if (r == null) instance = r = new Singleton();
            }
        }
        return r;
    }
Without volatile, the write of the reference can be reordered with the constructor's field writes, so another thread could see a non-null reference to a partially constructed object. volatile creates a happens-before edge that forbids this reordering, which has been reliable since the Java 5 memory model. The holder idiom or an enum singleton is simpler and avoids the subtlety.

Q120. What are the different ways to implement a thread-safe singleton?
Eager initialization with private static final Singleton INSTANCE = new Singleton() is thread-safe thanks to class initialization, but it is not lazy. A synchronized getInstance() is simple and lazy but takes a lock on every call. Double-checked locking with a volatile field is lazy with low overhead. The initialization-on-demand holder idiom puts the instance in a static nested Holder class, which the JVM loads only on first access, giving laziness and thread safety with no synchronization cost. An enum singleton (enum Singleton { INSTANCE; }) is thread-safe and also resistant to serialization and reflection attacks, and Effective Java recommends it unless you must extend a class. Class-based singletons need readResolve() to survive serialization and can be broken by reflection.

Q121. What is a daemon thread?
A daemon thread is a background service thread, and the JVM exits when only daemon threads remain, without waiting for them to finish. You must call setDaemon(true) before start(), or an IllegalThreadStateException is thrown, and new threads inherit the daemon status of the thread that created them. JVM housekeeping threads such as GC and JIT compiler threads are daemons. Because daemons are terminated abruptly at shutdown, their finally blocks may not run and I/O may be left incomplete, so never use them for critical work. Virtual threads are always daemon threads.

Q122. How do you shut down an ExecutorService gracefully?
Call shutdown() to stop accepting new tasks while letting submitted tasks finish, then wait with awaitTermination(timeout). If the wait times out, call shutdownNow(), which interrupts running tasks and returns the tasks that never started, and wait again briefly. If the waiting thread is itself interrupted, call shutdownNow() and restore the interrupt flag. Tasks must respond to interruption for shutdownNow() to be effective. Since Java 19, ExecutorService implements AutoCloseable, so close() (or try-with-resources) shuts the executor down and waits for its tasks to complete.


SECTION 7: JVM INTERNALS, MEMORY & GARBAGE COLLECTION (123-142)
---------------------------------------------------------------------

Q123. Describe the JVM architecture.
The class loader subsystem loads .class files, links them (verifying bytecode, preparing static fields with default values, and resolving symbolic references), and then initializes them by running static initializers. The runtime data areas include the shared heap and method area (metaspace), plus per-thread JVM stacks, program counter registers, and native method stacks. The execution engine contains the bytecode interpreter, the JIT compilers (C1 and C2), and the garbage collector. The Java Native Interface (JNI) and native method libraries connect Java code to OS and C/C++ code.

Q124. What are the JVM memory areas?
The heap is shared by all threads, holds objects and arrays, is managed by the garbage collector, and is sized with -Xms and -Xmx. Metaspace, the method area, holds class metadata, method bytecode, and runtime constant pools in native memory. Each thread has a JVM stack of frames holding local variables and operand stacks, sized with -Xss, and exhausting it causes StackOverflowError. Each thread also has a PC register pointing at the current bytecode instruction and a native method stack for JNI code. Outside these areas, the JVM also uses a code cache for JIT-compiled code and off-heap memory for direct buffers.

Q125. What replaced PermGen in Java 8, and why?
Metaspace replaced PermGen in Java 8 (JEP 122). PermGen was a fixed-size region that held class metadata, interned strings (until Java 7), and static data, and applications with many classes or class loader leaks frequently hit "OutOfMemoryError: PermGen space," while sizing it correctly was difficult. Metaspace stores class metadata in native memory and grows automatically by default, with an optional cap set by -XX:MaxMetaspaceSize. This simplified tuning and the collection of class metadata, and it aligned HotSpot with the JRockit JVM. Interned strings and static variables now live in the regular heap, and Metaspace exhaustion is still possible with class loader leaks.

Q126. What is stored on the stack versus the heap?
Each thread's stack holds method frames containing primitive local variables, references to objects, parameters, and return addresses; frames are freed automatically when methods return, and stacks are private to their thread. The heap is shared and holds all objects and arrays, including their instance fields, even primitive ones. Static fields and the string pool also live in the heap in modern JVMs. For example, with int x = 5 inside a method, x lives on the stack, while for Person p = new Person(), the reference p is on the stack and the Person object is on the heap. JIT escape analysis can sometimes eliminate heap allocation entirely through scalar replacement.

Q127. How does garbage collection work? When does an object become eligible for collection?
Garbage collection automatically reclaims the memory of objects that are no longer reachable. An object is eligible when no chain of strong references connects it to a GC root. Roots include local variables and operand stacks of active frames, static fields, active threads, JNI references, and objects used as monitors. Because collection is reachability-based, unreachable cycles are collected, unlike with reference counting. Typical algorithms mark live objects starting from the roots and then sweep, compact, or copy to reclaim the rest. You cannot force a collection: System.gc() is only a hint, and timing is nondeterministic.

Q128. Explain generational garbage collection.
Generational GC relies on the weak generational hypothesis that most objects die young. The young generation has an Eden space for new allocations and two survivor spaces, while the old (tenured) generation holds long-lived objects. A minor GC collects the young generation by copying live objects from Eden and one survivor space into the other survivor space, incrementing their age. Objects that survive enough collections (up to an age threshold of 15) are promoted to the old generation, and minor GCs are fast because few objects survive. A major GC collects the old generation, and a full GC collects the entire heap, usually with longer pauses. G1 divides the heap into regions rather than contiguous generations, and very large objects may be allocated directly in old or "humongous" regions.

Q129. Compare the Serial, Parallel, G1, ZGC, and Shenandoah garbage collectors.
Serial is single-threaded and stop-the-world with minimal overhead, suiting small heaps and single-CPU containers. Parallel uses multiple threads for stop-the-world collections and maximizes throughput, which suits batch jobs. G1, the default since Java 9, is region-based, performs concurrent marking, and collects the regions with the most garbage first to meet a pause-time goal (-XX:MaxGCPauseMillis, 200 ms by default), making it a good general-purpose balance.
ZGC is a scalable low-latency collector that compacts concurrently using colored pointers and load barriers, keeping pauses typically under a millisecond regardless of heap size; it became generational in Java 21 and generational-only in Java 24. Shenandoah, developed by Red Hat, also compacts concurrently with pauses independent of heap size. Choose based on your latency, throughput, and memory footprint priorities, and note that the older CMS collector was removed in Java 14.

Q130. What is a stop-the-world pause?
A stop-the-world pause halts all application threads at safepoints while the garbage collector (or another VM operation) does work that requires a consistent view of the heap, such as scanning roots or copying young-generation objects. During the pause the application is unresponsive, which shows up as latency spikes. Pause length depends on the collector, the heap size, and the amount of live data. Concurrent collectors such as G1 (partly), ZGC, and Shenandoah do most work alongside the application to keep pauses short. GC logging with -Xlog:gc* shows pause times, and other VM operations such as deoptimization and thread dumps can also cause pauses.

Q131. What are strong, soft, weak, and phantom references?
A strong reference is a normal reference, and an object is never collected while it is strongly reachable. A SoftReference is cleared only when memory runs low, before an OutOfMemoryError, which makes it usable for memory-sensitive caches, though its behavior is hard to predict. A WeakReference is cleared at the next collection once the object is only weakly reachable, and it underpins WeakHashMap and canonicalizing maps. A PhantomReference's get() always returns null; it is enqueued in a ReferenceQueue after the object becomes unreachable and is used for post-mortem cleanup, as Cleaner does. Reference queues let your code learn when referents have been collected.

Q132. Can memory leaks occur in Java? What are the common causes?
Yes. Java leaks are logical: objects stay reachable even though they are no longer needed, so the GC cannot reclaim them. Common causes include unbounded static collections and caches, listeners or callbacks that are registered and never removed, and ThreadLocal values left in pooled threads. Others are inner classes, anonymous classes, or lambdas that capture an outer instance, unclosed resources holding native memory, and mutable HashMap keys. Class loader leaks in application servers, where a static reference keeps an undeployed application's classes alive, are another classic source. Leaks show up as old-generation usage after full GC trending steadily upward, and heap dumps reveal the culprits.

Q133. How would you diagnose an OutOfMemoryError?
Start with the error message, which tells you the exhausted area: Java heap space, Metaspace, GC overhead limit exceeded, direct buffer memory, unable to create native thread, or requested array size exceeds VM limit. Run with -XX:+HeapDumpOnOutOfMemoryError and -XX:HeapDumpPath, or capture a dump on demand with jcmd <pid> GC.heap_dump or jmap. Analyze the dump in Eclipse MAT or VisualVM using the dominator tree, leak suspects report, and paths to GC roots to find what retains the most memory.
GC logs show whether old-generation occupancy after collections trends upward (a leak) or simply spikes under load (insufficient capacity). Java Flight Recorder adds allocation profiling and old-object sampling, jcmd GC.class_histogram gives a quick per-class view, and Native Memory Tracking helps with off-heap problems. The fix may be eliminating a leak, enlarging the heap, or streaming data instead of loading it all at once.

Q134. What is JIT compilation? Explain the interpreter, the C1 and C2 compilers, and tiered compilation.
The JVM starts by interpreting bytecode while profiling which methods and loops are hot, and it compiles hot code to native machine code at runtime, which is just-in-time compilation. C1, the client compiler, compiles quickly with lighter optimizations. C2, the server compiler, takes longer but applies aggressive, profile-guided optimizations such as inlining, loop unrolling, escape analysis, devirtualization, and intrinsics. Tiered compilation, the default since Java 8, moves code from the interpreter to C1 with profiling and then to C2, combining fast startup with high peak performance. Speculative optimizations are deoptimized back to the interpreter if their assumptions break, for instance when a new subclass is loaded, and on-stack replacement lets long-running loops switch to compiled code mid-execution.

Q135. What is escape analysis, and which optimizations does it enable?
Escape analysis is a JIT analysis that determines whether an object reference escapes the method that created it (by being stored in a field, returned, or passed to code the compiler cannot see) or escapes to other threads. If an object does not escape the method, the JIT can perform scalar replacement, turning the object's fields into local variables or registers and eliminating the allocation entirely, so there is no heap or GC cost. If an object does not escape its thread, locks on it can be elided. HotSpot does not perform true stack allocation, but scalar replacement achieves a similar effect. The analysis depends heavily on inlining and is enabled by default, which makes short-lived objects like iterators and small wrappers very cheap.

Q136. Explain common JVM flags such as -Xms, -Xmx, -Xss, and -XX:+UseG1GC.
-Xms sets the initial heap size and -Xmx the maximum, and servers often set them equal to avoid resizing. -Xss sets each thread's stack size, which affects recursion depth and per-thread memory use. -XX:+UseG1GC, -XX:+UseZGC, -XX:+UseParallelGC, and -XX:+UseSerialGC select the garbage collector, and -XX:MaxGCPauseMillis sets a pause-time goal. -XX:MaxMetaspaceSize caps metaspace, and -XX:MaxRAMPercentage sizes the heap relative to container memory. Other useful flags include -XX:+HeapDumpOnOutOfMemoryError, unified GC logging with -Xlog:gc*, and -XX:+PrintFlagsFinal to list every effective value.

Q137. What is bytecode, and how can you inspect it?
Bytecode is the platform-independent instruction set the JVM executes, stored in .class files along with a constant pool, field and method metadata, and attributes. Its instructions are stack-based, such as iload, iadd, getfield, and invokevirtual, operating on an operand stack and numbered local-variable slots. javac produces it from Java source, and other JVM languages such as Kotlin and Scala produce it too. You can inspect it with javap -c to disassemble methods, -v for verbose output including the constant pool, and -p to include private members. Libraries such as ASM and ByteBuddy, and the Class-File API finalized in Java 24, can read and generate bytecode, which is handy for seeing how lambdas, string concatenation, or autoboxing are actually compiled.

Q138. Why was finalize() deprecated, and what are the alternatives?
finalize() offers no guarantee about when, or whether, it runs. It slows garbage collection because finalizable objects need an extra GC cycle, and a backlog in the finalizer queue can itself cause OutOfMemoryError. It can resurrect objects, silently ignores exceptions, runs on an unspecified thread, and enables finalizer attacks on partially constructed objects. It was deprecated in Java 9 and deprecated for removal in Java 18 (JEP 421). The primary alternative is deterministic cleanup with AutoCloseable and try-with-resources. java.lang.ref.Cleaner (Java 9) can serve as a safety net by registering a cleanup action that runs when an object becomes phantom reachable, as long as the action does not reference the object itself.

Q139. What is string deduplication in the G1 collector?
Many applications hold large numbers of distinct String objects with identical contents, often produced by parsing or I/O. With -XX:+UseStringDeduplication (added for G1 in Java 8u20), the collector finds strings with equal contents and makes them share one underlying byte array, reducing heap usage. The work runs concurrently in the background and targets strings that have survived a certain number of collections. The strings remain distinct objects, so == is still false, and only the backing array is shared, unlike intern(). Since Java 18, the other HotSpot collectors support it too, and it is off by default.

Q140. How does the JVM dispatch method calls?
invokestatic calls static methods, which are resolved at link time with no receiver object. invokespecial calls constructors and super.method() invocations without dynamic dispatch. invokevirtual calls class instance methods and dispatches on the receiver's runtime class, typically through a virtual method table. invokeinterface calls interface methods using an interface table lookup. invokedynamic (Java 7) links a call site at runtime through a bootstrap method, and it is used for lambdas, string concatenation, record equals()/hashCode()/toString(), and pattern-matching switches. The JIT uses profiling to devirtualize and inline call sites that see only one or two receiver types.

Q141. What is a safepoint?
A safepoint is a point in execution where a thread's state is fully known to the JVM, so every object reference it holds can be located. When the VM needs a consistent view, for garbage collection root scanning, deoptimization, class redefinition, or thread dumps, it brings all threads to a safepoint. Compiled code polls for safepoint requests at method returns and loop back-edges, and threads running native code are already considered safe. A thread stuck in a long loop without polls can delay every other thread and stretch pauses, which is why the JVM inserts polls into long loops (loop strip mining). Thread-local handshakes (Java 10) allow some per-thread operations without a global safepoint, and -Xlog:safepoint logs safepoint activity.

Q142. What are Class Data Sharing (CDS) and ahead-of-time compilation, and how do they improve JVM startup?
CDS stores pre-parsed class metadata in an archive file that is memory-mapped at startup, skipping class parsing and verification and letting multiple JVM processes share that memory. A default CDS archive for JDK classes has been enabled since Java 12, AppCDS extends this to application classes, and dynamic archiving with -XX:ArchiveClassesAtExit arrived in Java 13. Project Leyden's AOT cache, introduced in Java 24 (JEP 483), also caches loaded and linked classes, and Java 25 added AOT method profiling to speed warmup.
Full ahead-of-time compilation, such as GraalVM Native Image, compiles an application into a standalone native executable with very fast startup and a small memory footprint. The trade-offs are a closed-world assumption that requires configuration for reflection, longer build times, and often lower peak throughput than a warmed-up JIT. These techniques matter most for serverless functions, command-line tools, and containers that scale up frequently.


SECTION 8: FUNCTIONAL PROGRAMMING, STREAMS & DATE/TIME (143-162)
---------------------------------------------------------------------

Q143. What is a functional interface? What does the @FunctionalInterface annotation do?
A functional interface has exactly one abstract method (a single abstract method, or SAM), though it may also have default and static methods, and public Object methods such as equals() do not count. Functional interfaces are the target types for lambdas and method references. The @FunctionalInterface annotation is optional, but it makes the compiler report an error if the interface does not have exactly one abstract method. This documents intent and prevents someone from accidentally adding a second abstract method later. Runnable, Callable, Comparator, and Function are common examples.

Q144. Describe the core interfaces in java.util.function.
Function<T, R> has R apply(T) for transformations and supports andThen() and compose(). Predicate<T> has boolean test(T) for filtering and supports and(), or(), and negate(). Consumer<T> has void accept(T) for side effects, and Supplier<T> has T get() for lazy creation and factories. BiFunction<T, U, R> takes two inputs, UnaryOperator<T> is a Function<T, T>, and BinaryOperator<T> is a BiFunction<T, T, T> often used with reduce(). Primitive specializations such as IntPredicate, ToIntFunction, and IntUnaryOperator avoid boxing, and BiConsumer and BiPredicate round out the set.

Q145. How do lambdas differ from anonymous classes?
A lambda can implement only a functional interface, whereas an anonymous class can implement any interface or extend a class and can have its own state and multiple methods. Inside a lambda, this refers to the enclosing instance, while inside an anonymous class it refers to the anonymous object itself. A lambda does not introduce a new scope, so it cannot redeclare a local variable from the enclosing method, whereas an anonymous class can shadow such names.
An anonymous class compiles to a separate .class file (Outer$1) and creates a new instance every time the expression is evaluated. A lambda compiles to a private synthetic method plus an invokedynamic call site that LambdaMetafactory links at runtime, and non-capturing lambdas are typically reused as a single instance, which means fewer classes and better startup. Both can capture only effectively final local variables.

Q146. What does "effectively final" mean, and why do lambdas require captured variables to be effectively final?
A variable is effectively final if it is never reassigned after initialization, so it could be declared final without causing an error. Lambdas and inner classes capture a copy of a local variable's value, because the local lives in a stack frame that may be gone when the lambda runs, possibly on another thread. Requiring effectively final variables prevents the confusion of changes that would never be seen, and it avoids data races on captured locals. Fields and array elements can still be modified from a lambda, and workarounds such as a one-element array or an AtomicInteger exist, but needing them usually signals a side effect that a stream reduction would express better.

Q147. What are the four kinds of method references?
A static method reference, such as Integer::parseInt, is equivalent to s -> Integer.parseInt(s). A bound instance method reference uses a particular object, as in System.out::println or myString::concat. An unbound instance method reference names a type, as in String::toUpperCase, and the first lambda parameter becomes the receiver, so it is equivalent to s -> s.toUpperCase(). A constructor reference, such as ArrayList::new or int[]::new, creates new objects or arrays. For bound references, the receiver expression is evaluated once when the reference is created, so a null receiver fails immediately.

Q148. What is a Stream, and how does it differ from a Collection?
A Stream (java.util.stream, Java 8) is a sequence of elements that supports declarative aggregate operations such as filter, map, and reduce, chained into a pipeline. A collection stores data, while a stream does not; it computes elements on demand from a source such as a collection, array, generator, or I/O channel. Streams are lazy, can be consumed only once, and do not modify their source. They use internal iteration, make parallelism easy, and can even be infinite, as with Stream.iterate() and Stream.generate(). In short, collections are about storing and accessing data, while streams are about computing with it.

Q149. What is the difference between intermediate and terminal operations? What does it mean that streams are lazy?
Intermediate operations such as filter, map, flatMap, sorted, distinct, limit, and peek return a new stream and do nothing until a terminal operation runs. Terminal operations such as forEach, collect, reduce, count, findFirst, anyMatch, and toList trigger evaluation, produce a result or side effect, and consume the stream. Laziness lets the pipeline be fused so that each element flows through all stages in a single pass. It also enables short-circuiting, where operations like limit() and findFirst() stop early, avoids building intermediate collections, and makes infinite streams practical. For example, stream.filter(...).map(...).findFirst() processes elements only until the first match.

Q150. What is the difference between map() and flatMap()?
map() applies a function that produces exactly one output per element, turning a Stream<T> into a Stream<R>. flatMap() applies a function that returns a stream for each element and then flattens all those streams into one, which handles one-to-many transformations. For example, flatMap(List::stream) turns a stream of lists into a single stream of their elements. Similarly, lines.flatMap(line -> Arrays.stream(line.split(" "))) turns a stream of lines into a stream of words. Optional offers the same map() and flatMap() distinction, and Java 16 added mapMulti() as an imperative alternative to flatMap().

Q151. What are short-circuiting stream operations? Give examples.
Short-circuiting operations can finish without processing every element, which is what makes infinite streams usable. The intermediate short-circuiting operations are limit(n) and takeWhile() (Java 9), which turn a potentially infinite stream into a finite one. The terminal ones are findFirst(), findAny(), anyMatch(), allMatch(), and noneMatch(). For example, Stream.iterate(1, i -> i * 2).filter(i -> i > 1000).findFirst() terminates even though the source is infinite. allMatch() stops at the first false result, and anyMatch() stops at the first true one.

Q152. What is the difference between reduce() and collect()?
reduce() combines elements into a single immutable result using an associative function, as in stream.reduce(0, Integer::sum), and a three-argument form adds a combiner for parallel execution; its functions should produce new values rather than mutate existing ones. collect() performs a mutable reduction, accumulating elements into a mutable container such as an ArrayList, StringBuilder, or Map through a Collector or a supplier, accumulator, and combiner. Using reduce() to build a collection is inefficient and can be incorrect in parallel. The rule of thumb is reduce() for values like sums and maximums and collect() for containers.

Q153. Explain Collectors.groupingBy, partitioningBy, toMap, and joining.
groupingBy(classifier) produces a Map<K, List<T>>, and downstream collectors refine each group, as in groupingBy(Person::getCity, Collectors.counting()), with an optional map factory such as TreeMap::new. partitioningBy(predicate) produces a Map<Boolean, List<T>> that always contains both the true and false keys. toMap(keyMapper, valueMapper) throws IllegalStateException on duplicate keys unless you supply a merge function such as (a, b) -> a or Integer::sum, and it throws NullPointerException for null values. joining(delimiter, prefix, suffix) concatenates strings, as in names.stream().collect(Collectors.joining(", ", "[", "]")). Other useful collectors include toSet, counting, summingInt, mapping, and teeing (Java 12).

Q154. Can a stream be reused after a terminal operation? Why not?
No. A stream is a one-shot pipeline over its source, and once a terminal operation runs (or another operation has been chained onto it), any further use throws IllegalStateException: "stream has already been operated upon or closed." Some sources, such as I/O channels or iterators, cannot be traversed twice at all, which is part of why the design is one-shot. To reuse a pipeline, create a fresh stream from the source each time, for example with a Supplier<Stream<T>> such as () -> list.stream().

Q155. How do parallel streams work, and when can they hurt performance?
parallelStream() or .parallel() splits the source into chunks with a Spliterator, processes them on ForkJoinPool.commonPool() threads (about one fewer than the number of cores, plus the calling thread), and combines the partial results. They hurt performance for small datasets, where overhead dominates, and for sources that split poorly, such as LinkedList, Stream.iterate(), and I/O-backed streams. Ordering constraints such as findFirst(), forEachOrdered(), and limit() on ordered streams add coordination costs, and boxing adds more. Shared mutable state causes contention or outright race bugs, and blocking I/O inside parallel streams can starve the common pool that the whole JVM shares. Parallel streams shine for large, CPU-bound, stateless work on easily split sources such as arrays, ArrayLists, and IntStream.range(), and you should always measure with a tool like JMH.

Q156. What is the difference between stateful and stateless intermediate operations? Why are side effects in streams dangerous?
Stateless operations such as filter, map, flatMap, and peek process each element independently. Stateful operations such as sorted, distinct, limit, and skip must remember or see other elements; sorted() in particular must consume the entire input before emitting anything, which can buffer a lot of memory and reduce parallel efficiency.
Side effects in stream lambdas, such as adding to an external list or incrementing a counter, are dangerous because they are not thread-safe in parallel streams and cause races. Laziness and short-circuiting mean those side effects may run in an unexpected order or not at all; since Java 9, count() may even skip map() and peek() entirely when the size is known from the source. Behavioral parameters should be stateless and must not modify the stream's source, and collectors should be used in place of side effects.

Q157. What is Optional for? What are correct usages and common anti-patterns?
Optional<T> (Java 8) is a container for a possibly absent value, intended mainly as a return type for methods that may have no result, such as findFirst() or max(). It makes absence explicit and nudges callers to handle it. Correct usage means returning Optional.empty() instead of null, chaining map(), flatMap(), and filter(), and finishing with orElse(), orElseGet(), orElseThrow(), ifPresent(), ifPresentOrElse(), or or().
Common anti-patterns include calling get() without checking, writing isPresent() followed by get() in imperative style, and using Optional for fields (it is not Serializable), method parameters, or collection elements. Returning null from a method declared to return Optional, returning Optional<List<T>> instead of an empty list, and calling Optional.of() on a possibly null value (use ofNullable()) are also mistakes. For primitives, OptionalInt, OptionalLong, and OptionalDouble avoid boxing.

Q158. What is the difference between Optional.orElse() and Optional.orElseGet()?
orElse(value) evaluates its argument eagerly, every time, even when the Optional already contains a value, so orElse(createDefault()) calls createDefault() on every call. orElseGet(supplier) invokes the supplier lazily, only when the Optional is empty. Use orElse() for constants or values already computed, and orElseGet() when the default is expensive or has side effects, such as a database call or object creation. orElseThrow(supplier) is the equivalent for throwing an exception when the value is absent.

Q159. What are primitive streams, and why do they exist?
IntStream, LongStream, and DoubleStream operate directly on primitives, avoiding the boxing overhead and memory cost of a Stream<Integer>. They add numeric operations such as sum(), average(), min(), max(), and summaryStatistics(), plus range() and rangeClosed() for generating sequences. You convert with mapToInt(Person::getAge), boxed(), mapToObj(), and asLongStream(), and their reductions return OptionalInt and OptionalDouble. Only three exist to avoid a combinatorial explosion of specialized types, which is why String.chars() returns an IntStream rather than a char stream.

Q160. Using streams, how would you find the second-highest number in a list, or count character frequencies in a string?
    Optional<Integer> second = list.stream()
        .distinct()
        .sorted(Comparator.reverseOrder())
        .skip(1)
        .findFirst();

    Map<Character, Long> freq = s.chars()
        .mapToObj(c -> (char) c)
        .collect(Collectors.groupingBy(Function.identity(), LinkedHashMap::new, Collectors.counting()));
For the second-highest value, distinct() ensures duplicates of the maximum are not counted as second place, and returning an Optional handles lists with fewer than two distinct values; sorting costs O(n log n), so for huge inputs a single pass tracking the top two values is O(n). For frequencies, chars() yields an IntStream that mapToObj() boxes into Characters, LinkedHashMap preserves first-appearance order, and codePoints() should be used for full Unicode support. A common follow-up is finding the first non-repeating character by filtering for entries with a count of 1 and calling findFirst().

Q161. Why did java.time replace Date and Calendar? Explain LocalDate, LocalDateTime, Instant, ZonedDateTime, Duration, and Period.
Date and Calendar are mutable and not thread-safe, use confusing conventions such as zero-based months and years offset from 1900, mix date and time concepts, and handle time zones poorly, and SimpleDateFormat is not thread-safe either. java.time (JSR-310, Java 8, inspired by Joda-Time) provides immutable, thread-safe, clearly named types and a thread-safe DateTimeFormatter.
LocalDate is a date without time or zone, such as a birthday, and LocalDateTime is a date and time with no zone. Instant is a point on the UTC timeline used for machine timestamps, and ZonedDateTime is a date-time with time-zone rules, including daylight saving transitions (OffsetDateTime uses a fixed offset instead). Duration measures time-based amounts in seconds and nanoseconds, while Period measures date-based amounts in years, months, and days. Across a daylight saving change, adding Period.ofDays(1) keeps the same local clock time, whereas adding Duration.ofHours(24) does not.

Q162. What are Stream Gatherers, and what problem do they solve?
Stream Gatherers, finalized in Java 24 (JEP 485), let you define custom intermediate operations, much as Collectors let you define custom terminal operations. Previously the set of intermediate operations was fixed, so tasks like sliding windows, fixed-size batching, running totals, or deduplication by key were awkward without leaving the stream API. You apply one with stream.gather(gatherer), and a Gatherer is built from an initializer, an integrator, an optional combiner for parallel use, and a finisher, so it can keep state and short-circuit. Built-in gatherers in the Gatherers class include windowFixed(n), windowSliding(n), fold(), scan(), and mapConcurrent(), which runs a mapping function concurrently on virtual threads with bounded concurrency. For example, Stream.of(1, 2, 3, 4, 5, 6, 7).gather(Gatherers.windowFixed(3)) yields [1, 2, 3], [4, 5, 6], and [7].


SECTION 9: MODERN JAVA FEATURES (163-175)
---------------------------------------------------------------------

Q163. What is local variable type inference (var), and what are its limitations?
var (Java 10) lets the compiler infer a local variable's static type from its initializer, as in var list = new ArrayList<String>(); the variable is still statically typed. It works only for local variables, including for-loop variables and try-with-resources, and for lambda parameters since Java 11, not for fields, method parameters, or return types. The variable must be initialized, and the initializer cannot be null, an array initializer such as {1, 2}, or a lambda without a target type. var is a reserved type name rather than a keyword, so it can still be used as a variable name. Use it when the type is obvious from the right-hand side, and beware that var list = new ArrayList<>() infers ArrayList<Object>.

Q164. What are records? What does the compiler generate for them, what are their limitations, and what is a compact constructor?
Records (final in Java 16) are concise, transparent carriers of immutable data, such as record Point(int x, int y) {}. The compiler generates private final fields, a canonical constructor, accessor methods named x() and y() (without a get prefix), and equals(), hashCode(), and toString() based on all components. Records are implicitly final, implicitly extend java.lang.Record and so cannot extend another class, and cannot declare additional instance fields. Their immutability is shallow, so mutable components such as lists need defensive copies, though records can implement interfaces and declare static members, instance methods, nested types, and extra constructors.
A compact constructor omits the parameter list and is used for validation or normalization, as in record Range(int lo, int hi) { Range { if (lo > hi) throw new IllegalArgumentException(); } }, with the fields assigned automatically afterward. Records deserialize through their canonical constructor, which makes them safer to serialize, and they work with record patterns.

Q165. What are sealed classes and interfaces, and why are they useful?
Sealed classes and interfaces (Java 17) restrict which classes may extend or implement them, as in sealed interface Shape permits Circle, Square, Rectangle {}. Each permitted subclass must be declared final, sealed, or non-sealed (which explicitly reopens extension). Permitted subclasses must be in the same module, or in the same package when using the unnamed module, and the permits clause can be omitted when all subclasses are in the same file. Sealed types model closed hierarchies precisely and give API authors control over extension without making everything final. Because the compiler knows every subtype, switch pattern matching over a sealed type can be exhaustive without a default branch, and records make natural permitted subtypes.

Q166. How does pattern matching for instanceof work?
Finalized in Java 16 (JEP 394), it combines the type test and the cast into one step with a binding variable, as in if (obj instanceof String s && !s.isEmpty()) { ... }. This removes the redundant cast that previously followed every instanceof check. The binding is in scope only where the match is definitely true, so after if (!(obj instanceof String s)) return;, s is usable for the rest of the method. It also shortens equals() implementations, as in return o instanceof Point p && x == p.x && y == p.y;. Java 21 extended instanceof to record patterns, as in if (obj instanceof Point(int x, int y)).

Q167. What are switch expressions? Explain the arrow syntax and the yield keyword.
Switch expressions (final in Java 14) let a switch produce a value, as in int days = switch (month) { case FEB -> 28; case APR, JUN, SEP, NOV -> 30; default -> 31; };. Arrow labels never fall through, so no break is needed, and several labels can share one case separated by commas. The right side of an arrow can be an expression, a block, or a throw statement. Inside a block, yield returns the value, as in case X -> { log(); yield 5; }, and yield also works with traditional colon-style cases in a switch expression. Switch expressions must be exhaustive, covering every enum constant or sealed subtype or including a default, and arrow syntax can also be used in ordinary switch statements.

Q168. Explain pattern matching for switch and record patterns. How does exhaustiveness checking work with sealed types?
Java 21 (JEP 441) allows case labels with type patterns, guards, and null, as in switch (shape) { case Circle c -> ...; case Square s when s.side() > 10 -> ...; case Square s -> ...; case null -> ...; }. Record patterns (JEP 440) deconstruct records directly, as in case Point(int x, int y) -> x + y, and they can be nested. Dominance rules require more specific patterns to appear before more general ones, or the code fails to compile.
A switch expression, and any pattern switch statement, must cover every possible value. With a sealed hierarchy, listing all permitted subtypes satisfies this without a default branch, so adding a new subtype later causes compile errors wherever it is not handled, which is a deliberate safety feature. If a new subtype appears through separate compilation anyway, the switch throws MatchException at runtime, and unnamed patterns (_) from Java 22 let you ignore components you do not need.

Q169. What are virtual threads, and how do they differ from platform threads?
Virtual threads (final in Java 21, JEP 444) are lightweight threads managed by the JVM rather than the operating system. Platform threads map one-to-one to OS threads, which are expensive in memory and creation cost and practical only in the thousands. Virtual threads are mounted on a small pool of carrier platform threads, and when one blocks on I/O or a lock, the JVM unmounts it by saving its stack to the heap and frees the carrier to run another, so millions of blocking virtual threads are feasible.
This lets you write simple thread-per-request blocking code with the scalability of asynchronous code. You create them with Thread.ofVirtual().start(task), Thread.startVirtualThread(), or Executors.newVirtualThreadPerTaskExecutor(). They are always daemon threads with a fixed priority, should never be pooled, and should be throttled with semaphores when protecting limited resources. They improve throughput for I/O-bound workloads but do not make CPU-bound code any faster.

Q170. What is thread pinning with virtual threads? How did Java 24 change pinning behavior around synchronized blocks?
Virtual threads do not help CPU-bound work, code that is already non-blocking, or workloads bottlenecked by a downstream resource such as a fixed-size database connection pool. Pinning happens when a virtual thread cannot unmount from its carrier while blocked, so the carrier is blocked too, which reduces scalability and can starve other virtual threads. In Java 21 through 23, blocking inside a synchronized block or method, or in Object.wait(), pinned the carrier, so the advice was to replace synchronized with ReentrantLock in hot paths.
Java 24 (JEP 491) reimplemented monitors so that virtual threads can acquire, hold, release, and wait on monitors independently of their carriers, meaning synchronized no longer pins. Pinning still occurs when blocking inside native code (JNI) or foreign functions. The JFR event jdk.VirtualThreadPinned helps detect it, and heavy ThreadLocal use also deserves care because memory multiplies across millions of threads.

Q171. What are structured concurrency and scoped values, and what problems do they address compared with ThreadLocal?
Structured concurrency (StructuredTaskScope, still a preview API as of Java 25) treats a group of related concurrent subtasks as a single unit of work bounded by a lexical scope. You fork subtasks inside the scope and join them, and if one fails or the scope is cancelled, the remaining subtasks are cancelled automatically, so no threads leak, errors propagate cleanly, and thread dumps show the task hierarchy. This fixes a weakness of unstructured ExecutorService and CompletableFuture code, where one failing subtask can leave its siblings running.
Scoped values (ScopedValue, final in Java 25) share immutable data one way with callees and child threads for the bounded duration of a call, as in ScopedValue.where(USER, user).run(() -> handle()). Compared with ThreadLocal, they cannot be reassigned, they are automatically unbound when the scope ends (so there is nothing to remove() and nothing to leak), and child threads in a structured scope inherit them cheaply without copying. That makes them far more efficient than ThreadLocal when there are millions of virtual threads.

Q172. What is the Java Platform Module System (JPMS)? Explain module-info.java, requires, exports, and opens.
JPMS (Java 9, Project Jigsaw) organizes code into modules, which are named, self-describing groups of packages with explicit dependencies and strong encapsulation. Each module has a module-info.java file at its root, such as module com.example.app { requires java.sql; requires transitive com.example.api; exports com.example.app.service; opens com.example.app.model; }. requires declares a dependency, and missing modules are detected at startup, while requires transitive passes that dependency on to the module's consumers. exports makes a package's public types accessible to other modules, and packages that are not exported stay hidden even if their classes are public. opens permits deep reflection on a package's private members at runtime, which frameworks need, and uses and provides declare service loader relationships. The JDK itself is modularized around java.base, which makes custom runtime images with jlink possible, and classpath code runs in the unnamed module.

Q173. What are helpful NullPointerExceptions?
Introduced in Java 14 (JEP 358) and enabled by default since Java 15, helpful NullPointerExceptions make the JVM describe exactly which reference was null. Before this, an NPE reported only a line number, which was ambiguous for chains like a.getB().getC()[i].d. Now the message says something like: Cannot invoke "String.length()" because the return value of "User.getName()" is null. Local variable names appear in the message when the code is compiled with debug information (-g). The message is computed lazily, only when it is requested, so the runtime cost is negligible.

Q174. Explain Java's six-month release cadence and LTS model. Which releases are LTS versions?
Since Java 9 (2017), a new feature release ships every six months, in March and September, with features delivered when they are ready and refined through preview and incubator stages. Most releases receive only six months of updates, while long-term support (LTS) releases receive years of updates from Oracle and other vendors such as Eclipse Adoptium, Amazon Corretto, Azul, Red Hat, and Microsoft. The LTS releases so far are Java 8, 11, 17, 21, and 25 (September 2025). Since Java 17, an LTS release has come every two years, so the next one is expected to be Java 29 in September 2027. Most enterprises standardize on LTS versions, while teams that want new features sooner track each feature release.

Q175. What are unnamed variables and patterns (_), and where are they useful?
Finalized in Java 22 (JEP 456), the underscore declares a variable or pattern you intend to ignore, which signals intent and avoids unused-variable warnings. Unnamed variables are useful in catch blocks (catch (NumberFormatException _)), enhanced for loops used only for counting, try-with-resources whose resource is never referenced, and lambda parameters you do not need, as in map.forEach((_, value) -> ...). Unnamed patterns ignore record components, as in case Point(int x, _) -> x, and they allow several patterns to share one case, as in case Circle _, Square _ -> .... You cannot read or reference _, and multiple unnamed variables may appear in the same scope.


SECTION 10: I/O, NIO & SERIALIZATION (176-185)
---------------------------------------------------------------------

Q176. What is the difference between byte streams and character streams?
Byte streams (InputStream and OutputStream, such as FileInputStream and BufferedInputStream) read and write raw 8-bit bytes and are meant for binary data like images, archives, and network protocols. Character streams (Reader and Writer, such as BufferedReader and FileWriter) handle text as characters, decoding and encoding bytes with a charset. InputStreamReader and OutputStreamWriter bridge the two using a specified Charset. Always specify the charset explicitly, such as StandardCharsets.UTF_8, although since Java 18 (JEP 400) the default charset is UTF-8. Do not use byte streams to manipulate multibyte text or character streams for binary data.

Q177. Why do buffered streams improve performance?
Unbuffered streams typically perform an operating-system call for every read() or write(), which is very expensive when done byte by byte. Buffered streams such as BufferedInputStream, BufferedReader, and BufferedWriter use an in-memory buffer (8 KB by default), reading large chunks at once and batching writes until the buffer fills or flush() is called. This dramatically reduces the number of system calls and disk or network operations. BufferedReader also adds readLine(), and BufferedWriter adds newLine(). Remember to flush or close output streams, or buffered data can be lost.

Q178. What are the differences between java.io and java.nio?
java.io (Java 1.0) is stream-oriented and blocking: a thread waits until data is read or written, and its File class has poor error reporting and limited metadata and symbolic link support. java.nio (Java 1.4) is buffer-oriented, built on Channels and Buffers, and supports non-blocking I/O multiplexed by Selectors, so one thread can manage many connections, along with memory-mapped files, scatter/gather I/O, and direct buffers. NIO.2 (Java 7, java.nio.file) added Path, Files, FileSystem, WatchService, file attributes, symbolic links, and asynchronous channels. Modern code typically uses java.nio.file for filesystem work, while java.io streams remain common and interoperate through methods like Files.newBufferedReader(). With virtual threads, simple blocking I/O scales well again.

Q179. How do you work with files using the Path and Files APIs?
A Path represents a filesystem location, created with Path.of("data", "in.txt") (Java 11) or Paths.get(), and it supports resolve(), relativize(), normalize(), getParent(), getFileName(), and toAbsolutePath(). Files is a utility class with static methods such as exists(), isDirectory(), createDirectories(), copy(), move() (with options like REPLACE_EXISTING and ATOMIC_MOVE), deleteIfExists(), size(), and readAttributes(). For reading and writing, it offers readString() and writeString() (Java 11), readAllLines(), readAllBytes(), write(), newBufferedReader(), newBufferedWriter(), and lines(), which returns a lazy stream that you must close. For directories, Files.list(), walk(), and find() return streams that must also be closed, and walkFileTree() and newDirectoryStream() with glob patterns provide finer control. Files throws specific, meaningful exceptions such as NoSuchFileException.

Q180. Explain NIO Channels, Buffers, and Selectors. What is the difference between blocking and non-blocking I/O?
A Channel, such as FileChannel, SocketChannel, ServerSocketChannel, or DatagramChannel, is a connection to an I/O entity that reads into and writes from Buffers. A Buffer, such as ByteBuffer, is a fixed-capacity container with position, limit, and capacity: you write into it, call flip() to switch to reading, and call clear() or compact() to reuse it, and direct buffers live off-heap for efficient native I/O. A Selector lets one thread monitor many non-blocking channels for readiness events (OP_ACCEPT, OP_READ, OP_WRITE, OP_CONNECT) and process only the ones that are ready.
With blocking I/O, a call blocks the thread until it completes, which is simple but traditionally needs one thread per connection. With non-blocking I/O, a call returns immediately with whatever is available, possibly nothing, and combined with a Selector this enables event-driven servers that handle thousands of connections with few threads, as Netty does, at the cost of complexity. Virtual threads now offer similar scalability with straightforward blocking code.

Q181. What is serialization? What is the role of Serializable and serialVersionUID?
Serialization converts an object graph into a byte stream (ObjectOutputStream.writeObject()) for storage or transmission, and deserialization rebuilds it (ObjectInputStream.readObject()). Serializable is a marker interface that opts a class in; every non-transient field must also be serializable or NotSerializableException is thrown, and a non-serializable superclass needs an accessible no-arg constructor, which re-initializes its fields. serialVersionUID is a version number written into the stream and checked during deserialization, and a mismatch throws InvalidClassException.
If you do not declare serialVersionUID, it is computed from the class structure, so almost any change, even adding a method, can break compatibility. Declare it explicitly (private static final long serialVersionUID = 1L;) and evolve the class compatibly. You can customize the process with writeObject()/readObject() and writeReplace()/readResolve(), as in the serialization proxy pattern, and records always deserialize through their canonical constructor.

Q182. What does the transient keyword do?
transient marks a field to be skipped during Java serialization, so after deserialization it holds its default value (null, 0, or false) unless it is restored in readObject() or recomputed. Use it for sensitive data such as passwords, for derived or cached values, and for non-serializable resources such as threads, connections, and loggers. Static fields are never serialized, so they do not need it. Other serialization libraries may or may not honor transient; Jackson, for example, relies mainly on its own annotations. A final transient field is awkward because it cannot be easily reassigned after deserialization.

Q183. What security risks does Java deserialization pose? What are Externalizable and serialization filters?
Deserializing untrusted data is dangerous because readObject() can instantiate any serializable class on the classpath and run its readObject(), readResolve(), and related methods. Attackers chain such library classes into "gadget chains" to achieve remote code execution, and deeply nested or enormous object graphs enable denial-of-service attacks; deserialization also bypasses constructors and their invariant checks. Mitigations include never deserializing untrusted input with Java serialization, preferring schema-based formats such as JSON or Protocol Buffers, and validating objects in readObject().
Serialization filters (ObjectInputFilter, Java 9, JEP 290) let you allowlist classes and limit graph depth, array sizes, and reference counts, set globally through jdk.serialFilter or per stream, and Java 17 (JEP 415) added context-specific filter factories. Externalizable is a subinterface of Serializable in which the class fully controls its format through writeExternal() and readExternal(). It requires a public no-arg constructor, which is called during deserialization, and it can be more compact and faster but makes you responsible for everything, including superclass state and versioning.

Q184. How would you read a very large file efficiently without loading it entirely into memory?
Stream the file instead of using readAllLines() or readAllBytes(). For line-based text, use try (BufferedReader r = Files.newBufferedReader(path, UTF_8)) { String line; while ((line = r.readLine()) != null) process(line); }, or try (Stream<String> lines = Files.lines(path)) { ... }, both of which keep only about one line in memory at a time (beware of extremely long single lines). For binary data, read fixed-size chunks with InputStream.read(byte[]) or a FileChannel with a ByteBuffer. For random access to very large files, use memory mapping with FileChannel.map() (each MappedByteBuffer is limited to 2 GB) or, since Java 22, map a MemorySegment through the Foreign Function & Memory API, which has no 2 GB limit. Process records incrementally, keep only aggregates, parallelize carefully by splitting the file into ranges, and always close resources with try-with-resources.

Q185. When try-with-resources declares multiple resources, in what order are they closed?
Resources declared as try (A a = ...; B b = ...) are initialized in declaration order and closed in reverse order, so b closes before a, mirroring nested try blocks. This matters when one resource depends on another, such as a wrapper stream built on top of a file stream. If a later resource's initializer throws, the resources already opened are still closed. Every close() is attempted even if an earlier one throws, and additional exceptions are added as suppressed exceptions on the primary one. All resources are closed before any catch or finally block of the same statement runs.


SECTION 11: REFLECTION, ANNOTATIONS & CLASS LOADING (186-193)
---------------------------------------------------------------------

Q186. What is reflection? What are its use cases and drawbacks?
Reflection (java.lang.reflect together with Class) lets code inspect and manipulate classes, methods, fields, constructors, and annotations at runtime, using calls such as Class.forName(), getDeclaredMethods(), Method.invoke(), Field.set(), and Constructor.newInstance(). It powers dependency-injection containers, ORMs, serialization libraries such as Jackson, test frameworks such as JUnit, plugin loading, debuggers and IDE tooling, and generic utilities. Its drawbacks are slower calls than direct invocation (although Java 18 reimplemented core reflection on method handles), loss of compile-time type safety and refactoring support because names are strings, and broken encapsulation. It is also restricted by the module system and complicates ahead-of-time compilation and native images. Prefer interfaces where possible, and use MethodHandles or VarHandles when performance matters.

Q187. How do you access a private field via reflection, and how does the module system restrict this?
Use Field f = obj.getClass().getDeclaredField("secret"); f.setAccessible(true); Object value = f.get(obj); and f.set(obj, newValue) to change it. getDeclaredField() finds any field declared in that exact class, including private ones, whereas getField() finds only public fields, including inherited ones. setAccessible(true) suppresses the Java language access checks. Under JPMS, setAccessible() succeeds only if the target package is open to the caller's module, through an opens directive in module-info.java, the --add-opens command-line flag, or the more permissive rules for the unnamed module; otherwise it throws InaccessibleObjectException. Since Java 16 (JEP 396) and Java 17 (JEP 403), JDK internals are strongly encapsulated, so reflective hacks into JDK classes fail unless you add explicit --add-opens flags, and fields of records and static final fields cannot be modified this way.

Q188. How do annotations work? Explain retention policies and targets, and show how to create a custom annotation.
Annotations are metadata attached to declarations (and, since Java 8, to type uses), declared with @interface, such as @Retention(RetentionPolicy.RUNTIME) @Target(ElementType.METHOD) public @interface Timed { String value() default ""; int threshold() default 100; }. Annotation elements are declared like methods and may return only primitives, String, Class, enums, other annotations, or arrays of these, with optional defaults. The retention policy SOURCE discards the annotation during compilation (as with @Override, or for use by annotation processors), CLASS (the default) keeps it in the class file but hides it from reflection, and RUNTIME makes it readable via reflection, as in method.getAnnotation(Timed.class).
@Target restricts where the annotation may appear, using values such as TYPE, METHOD, FIELD, PARAMETER, CONSTRUCTOR, TYPE_USE, and RECORD_COMPONENT. Other meta-annotations include @Documented, @Inherited (which lets subclasses inherit class-level annotations), and @Repeatable. Annotations are processed either at compile time by annotation processors that generate code or at runtime through reflection.

Q189. Explain the class loader delegation model and the bootstrap, platform, and application class loaders.
Classes are loaded on demand by a hierarchy of class loaders. Under the delegation model, a loader asked for a class first delegates to its parent and attempts to load the class itself only if the parent cannot. This guarantees that core classes such as java.lang.String always come from the trusted bootstrap loader, prevents duplicate loading, and keeps types consistent. The bootstrap loader is part of the JVM, loads core modules such as java.base, and is represented as null in Java code. The platform class loader (Java 9, replacing the extension class loader) loads the remaining Java SE and JDK platform modules, and the application (system) class loader loads your code and libraries from the class path or module path. A class's runtime identity is its fully qualified name plus its defining loader, and some environments, such as servlet containers, deliberately use child-first delegation instead.

Q190. Can two versions of the same class be loaded in one JVM? How do custom class loaders make this possible?
Yes, as long as they are loaded by different class loaders, because a class's runtime identity is its binary name plus its defining loader. The two versions are distinct types, so casting between them throws ClassCastException even though their names are identical. A custom class loader extends ClassLoader, overrides findClass(name) to locate the class bytes (from a directory, JAR, network, generated code, or decrypted data), and calls defineClass(), while normally keeping parent delegation for core classes. To isolate library versions, you can use separate URLClassLoader instances pointing to different JARs, sometimes with child-first delegation. Application servers use this for per-application isolation and hot redeployment, and plugin systems, OSGi, and build tools rely on it too. The pitfalls are class loader leaks, LinkageErrors from conflicting definitions, and the need for shared interfaces to come from a common parent loader, and JPMS ModuleLayers offer a module-aware alternative.

Q191. What is the difference between Class.forName() and ClassLoader.loadClass()?
Classes referenced directly in code, as with new Foo(), are loaded implicitly when first needed, and a missing class then causes NoClassDefFoundError. Dynamic loading uses a class name known only at runtime and fails with ClassNotFoundException. Class.forName(name) loads and, by default, initializes the class, running its static initializers, using the caller's class loader; the overload forName(name, initialize, loader) controls both choices. This is why old JDBC code used Class.forName() to trigger a driver's static self-registration. ClassLoader.loadClass(name) loads the class through that specific loader's delegation chain but does not initialize it, so initialization happens later on first active use. Class.forName() also accepts array type names such as "[Ljava.lang.String;", which loadClass() does not.

Q192. What are dynamic proxies (java.lang.reflect.Proxy), and how do they work?
Proxy creates, at runtime, a class that implements a given set of interfaces and routes every method call to an InvocationHandler, as in Foo f = (Foo) Proxy.newProxyInstance(loader, new Class<?>[] { Foo.class }, (proxy, method, args) -> { log(method); return method.invoke(target, args); });. The generated proxy class extends Proxy, implements the interfaces, and passes each call's Method object and arguments to the handler's invoke() method. Proxies are used for logging, timing, transactions, caching, remote stubs, mocking, and decorators without hand-writing every method, and they form the basis of aspect-oriented features in many frameworks. Their limitations are that they work only with interfaces (libraries such as ByteBuddy generate subclasses for concrete classes), they add reflection overhead, equals(), hashCode(), and toString() are routed to the handler as well, and exceptions arrive wrapped in InvocationTargetException when the handler calls method.invoke().

Q193. What is the difference between Class.newInstance() and Constructor.newInstance(), and why was the former deprecated?
Class.newInstance(), deprecated in Java 9, can call only the no-arg constructor, and it propagates any exception the constructor throws, including checked exceptions, without wrapping. Because newInstance() does not declare those checked exceptions, this bypasses compile-time exception checking. Constructor.newInstance(args...) works with any constructor, including parameterized and (with setAccessible()) private ones. It wraps constructor exceptions in InvocationTargetException, consistent with Method.invoke(). The recommended replacement is clazz.getDeclaredConstructor().newInstance().


SECTION 12: DESIGN, BEST PRACTICES & CODING PROBLEMS (194-200)
---------------------------------------------------------------------

Q194. How do you implement the Singleton pattern, and why is an enum-based singleton often considered the best approach?
The main implementations are eager initialization, a synchronized accessor, double-checked locking, the holder idiom, and an enum (see Q120). An enum singleton looks like public enum Config { INSTANCE; private final Properties props = load(); public String get(String key) { return props.getProperty(key); } }. The JVM guarantees one instance per enum constant through thread-safe class initialization. Serialization is handled specially, so deserializing returns the same constant without any readResolve(), whereas class-based singletons create a new instance unless readResolve() is written. Reflection cannot instantiate enums, because Constructor.newInstance() refuses to create enum objects, while a private constructor can be invoked reflectively with setAccessible(). The limitations are that an enum cannot extend another class (though it can implement interfaces) and that singletons in general make testing harder because they are global state, so dependency injection is often preferable.

Q195. What is the Builder pattern, and when should you use it in Java?
The Builder pattern separates the construction of a complex object from its representation, typically through a static nested Builder class with fluent setter-like methods that return this and a build() method that calls the target class's private constructor. Use it when a constructor would take many parameters, especially optional or same-typed ones, which leads to the "telescoping constructor" problem, or when you want immutable objects without JavaBeans-style mutable setters. Call sites become readable, as in Pizza p = new Pizza.Builder(Size.LARGE).cheese(true).pepperoni(true).build();, and build() is the natural place to validate invariants. The downsides are extra code and a small overhead. For objects with only a few parameters, records or static factory methods are usually enough.

Q196. Explain the SOLID principles with Java examples.
Single Responsibility says a class should have one reason to change, so InvoiceCalculator, InvoicePrinter, and InvoiceRepository should be separate classes. Open/Closed says code should be open for extension but closed for modification, so you add a new Shape implementation with its own area() method instead of editing a type switch in an AreaCalculator. Liskov Substitution says subtypes must be usable wherever the supertype is expected without breaking behavior, which a Square extending Rectangle violates when setWidth() also changes the height, as does a subclass that throws UnsupportedOperationException.
Interface Segregation favors small, focused interfaces over large ones, so splitting Worker into Workable and Feedable spares a Robot from implementing eat(). Dependency Inversion says high-level modules should depend on abstractions, so OrderService should receive a PaymentGateway interface through its constructor rather than creating a concrete payment client itself, which also makes testing with fakes easy. Together these principles guide maintainable object-oriented design and should be applied pragmatically rather than dogmatically.

Q197. What can enums do beyond defining constants?
Enums are full classes that implicitly extend java.lang.Enum, so they can have fields, constructors (implicitly private), instance and static methods, and can implement interfaces. For example, enum Planet { MERCURY(3.303e23, 2.4397e6), EARTH(5.976e24, 6.37814e6); private final double mass, radius; Planet(double mass, double radius) { this.mass = mass; this.radius = radius; } } can add a surfaceGravity() method. Constant-specific method bodies let each constant override an abstract method, as in enum Operation { PLUS { int apply(int a, int b) { return a + b; } }, MINUS { int apply(int a, int b) { return a - b; } }; abstract int apply(int a, int b); }, or each constant can pass a lambda to the constructor instead.
Enums also come with values(), valueOf(), name(), ordinal(), and compareTo(), work in switch statements, and pair with EnumSet and EnumMap. They are well suited to singletons, state machines, and strategy implementations. Avoid persisting ordinal() values, since reordering constants changes them, and compare enums with ==.

Q198. Implement a thread-safe bounded blocking queue from scratch without using java.util.concurrent.
    public class BoundedBlockingQueue<E> {
        private final Object[] items;
        private int head, tail, count;
        public BoundedBlockingQueue(int capacity) {
            if (capacity <= 0) throw new IllegalArgumentException("capacity must be positive");
            items = new Object[capacity];
        }
        public synchronized void put(E e) throws InterruptedException {
            if (e == null) throw new NullPointerException();
            while (count == items.length) wait();
            items[tail] = e; tail = (tail + 1) % items.length; count++;
            notifyAll();
        }
        @SuppressWarnings("unchecked")
        public synchronized E take() throws InterruptedException {
            while (count == 0) wait();
            E e = (E) items[head]; items[head] = null; head = (head + 1) % items.length; count--;
            notifyAll();
            return e;
        }
        public synchronized int size() { return count; }
    }
The queue is a circular array with head and tail indices, and synchronized provides both mutual exclusion and memory visibility. Waiting in while loops handles spurious wakeups and competing threads, and notifyAll() is required because producers and consumers share a single wait set, so notify() could wake the wrong kind of thread and stall the system. Nulling out the taken slot prevents the queue from retaining references. A more efficient version would use one ReentrantLock with separate notFull and notEmpty Conditions and call signal(), which is how ArrayBlockingQueue works, and you could add timed offer() and poll() methods using wait(timeout).

Q199. Implement a simplified HashMap. Walk through put(), get(), collision handling, and resizing.
    public class SimpleHashMap<K, V> {
        private static final class Node<K, V> {
            final int hash; final K key; V value; Node<K, V> next;
            Node(int hash, K key, V value, Node<K, V> next) {
                this.hash = hash; this.key = key; this.value = value; this.next = next;
            }
        }
        private Node<K, V>[] table = newTable(16);
        private int size;

        @SuppressWarnings("unchecked")
        private static <K, V> Node<K, V>[] newTable(int n) { return (Node<K, V>[]) new Node[n]; }

        private static int hash(Object key) {
            int h = (key == null) ? 0 : key.hashCode();
            return h ^ (h >>> 16);
        }

        public V get(K key) {
            int h = hash(key);
            for (Node<K, V> n = table[h & (table.length - 1)]; n != null; n = n.next)
                if (n.hash == h && Objects.equals(n.key, key)) return n.value;
            return null;
        }

        public V put(K key, V value) {
            int h = hash(key), i = h & (table.length - 1);
            for (Node<K, V> n = table[i]; n != null; n = n.next)
                if (n.hash == h && Objects.equals(n.key, key)) { V old = n.value; n.value = value; return old; }
            table[i] = new Node<>(h, key, value, table[i]);
            if (++size > table.length * 3 / 4) resize();
            return null;
        }

        private void resize() {
            Node<K, V>[] old = table;
            table = newTable(old.length * 2);
            for (Node<K, V> head : old) {
                for (Node<K, V> n = head; n != null; ) {
                    Node<K, V> next = n.next;
                    int i = n.hash & (table.length - 1);
                    n.next = table[i]; table[i] = n;
                    n = next;
                }
            }
        }
    }
put() hashes the key (spreading the high bits), picks a bucket with a bit mask because the capacity is a power of two, and walks the bucket's chain, replacing the value if the key already exists or otherwise prepending a new node, which is separate chaining. get() computes the same index, compares the cached hash first as a cheap filter, and then confirms with equals(). When the size exceeds the 0.75 load factor, resize() doubles the table and moves every node into its new bucket, an O(n) step that keeps put() amortized O(1). Null keys work through hash 0 and Objects.equals(). Natural extensions are remove(), iterators, treeifying long chains, and thread safety, and the map averages O(1) per operation with an O(n) worst case.

Q200. Write a program in which two threads print the numbers 1 to N alternately (one prints odd numbers, the other prints even numbers).
    public class OddEvenPrinter {
        private final int max;
        private int current = 1;
        OddEvenPrinter(int max) { this.max = max; }

        private synchronized void print(boolean odd) throws InterruptedException {
            while (current <= max) {
                while (current <= max && (current % 2 == 1) != odd) wait();
                if (current <= max) {
                    System.out.println(Thread.currentThread().getName() + ": " + current++);
                    notifyAll();
                }
            }
        }

        public static void main(String[] args) {
            OddEvenPrinter p = new OddEvenPrinter(10);
            Runnable odd = () -> { try { p.print(true); } catch (InterruptedException e) { Thread.currentThread().interrupt(); } };
            Runnable even = () -> { try { p.print(false); } catch (InterruptedException e) { Thread.currentThread().interrupt(); } };
            new Thread(odd, "odd").start();
            new Thread(even, "even").start();
        }
    }
A shared counter is guarded by the object's monitor, and each thread waits until the counter's parity matches its role, then prints, increments, and calls notifyAll() to wake the other thread. The inner while loop protects against spurious wakeups and also rechecks the upper bound, so neither thread hangs waiting after the last number is printed, regardless of whether N is odd or even or which thread starts first. Alternative solutions use two Semaphores (the odd semaphore starting with one permit and the even one with zero, each thread acquiring its own and releasing the other's), a ReentrantLock with two Conditions, or a SynchronousQueue handoff. A common follow-up is generalizing to K threads in round-robin order by having thread i print only when current % K == i.
