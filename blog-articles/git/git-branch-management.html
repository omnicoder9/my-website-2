1. Introduction: what a branch is, and what managing one means

A branch is a pointer, not a container. Pro Git defines a branch as "simply a lightweight movable pointer" to a commit, and notes that because a branch is a file holding the 40-character SHA-1 of the commit it points to, branches are "cheap to create and destroy".1 The name main carries no special meaning to Git either: the default branch is "exactly like any other branch", and exists only because git init creates one.1 You can see the pointer directly:

$ cat .git/refs/heads/main
a8a7bdb492b3b71aee2232e5ae794e443cdd3b4d

Every branch management practice follows from that model. Creating a branch costs almost nothing, so the expensive part of branching is never the branch itself. The cost lies in divergence: the longer two pointers move independently, the more commits each side accumulates that the other has not seen, and the more work it takes to bring them back together. Pro Git describes Git's merge as a three-way merge that uses "the two snapshots pointed to by the branch tips and the common ancestor of the two".2 Divergence widens the gap between those tips and that ancestor. The four parts of this guide are four ways of controlling that cost:

  • Lifetimes limit how far a branch can drift before it is merged.
  • Protection guarantees that whatever lands on an important branch has been reviewed and tested.
  • Keeping branches current pays down divergence in small instalments rather than one large one.
  • Cleaning removes pointers whose work is finished, so the branch list stays a true picture of work in progress.

Conventions. Examples assume a repository cloned from GitHub, so the remote is named origin and the default branch is main. Terminal transcripts were produced with Git 2.43.0 against a local bare repository standing in for GitHub, with repository paths replaced by GitHub-style URLs; commit hashes will differ on your machine, and the wording of hints varies between Git versions. Transcript text is observed output, not a cited claim. GitHub-side configuration examples (rulesets, workflows) were not run against a live GitHub repository and are marked as such. Statements that are this guide's own inference, rather than something a cited source says, are labelled as inferences.

2. Branch lifetimes

Pro Git distinguishes two kinds of branch by how long they live. Long-running branches are "always open" and represent stages of a development cycle, with code graduating from one to the next as it becomes more stable; topic branches are short-lived branches created "for a single particular feature or related work".3 Git's own workflow guide, gitworkflows(7), uses the same split between integration branches (in Git's own project: maint, master, next and seen) and topic branches.4

2.1 Short-lived branches

Concept. A short-lived branch exists to deliver one change. Pro Git notes that in Git "it's common to create, work on, merge, and delete branches several times a day", and that isolating each topic makes it "easier to see what has happened during code review".3 GitHub's recommended workflow, GitHub flow, is built entirely on such branches. It is described as "a lightweight, branch-based workflow" with six steps: create a branch, make changes, create a pull request, address review comments, merge, and delete the branch.5

How short is short? Pro Git is permissive: you can keep topic changes "for minutes, days, or months".3 The research programme DORA is much stricter. Its trunk-based development capability reports that higher-performing teams have "three or fewer active branches", "merge branches to trunk at least once a day", and do not have code freezes or integration phases. It adds that branches in trunk-based development "typically last no more than a few hours".6 Martin Fowler gives the reasoning: "Frequent integration increases the frequency of merges but reduces their complexity and risk", and for teams that do use feature branches he argues for "smaller features: days not weeks (and months are right out)".7 DORA also identifies slow code review as a cause of long branches, because when review "takes hours or days, developers avoid working in small batches".6

Worked example: the life of a GitHub flow branch.

$ git switch -c feature/login             # create and switch in one step
Switched to a new branch 'feature/login'
# ...commit work...
$ git push -u origin feature/login         # publish and set upstream
To github.com:acme/shop.git
 * [new branch]      feature/login -> feature/login
branch 'feature/login' set up to track 'origin/feature/login'.
$ gh pr create                              # open the pull request (not run)
# ...review, CI, more commits...
$ gh pr merge --squash --delete-branch      # merge, then delete local and remote branch (not run)

git switch -c creates the branch and switches to it as a single transactional step.8 The -u (--set-upstream) flag on the first push records the remote branch as the local branch's upstream, which argument-less git pull and other commands then use.9 Setting push.autoSetupRemote to true makes Git assume --set-upstream on a default push when no upstream exists yet.9 In the GitHub CLI, gh pr merge --delete-branch deletes "the local and remote branch after merge", and --auto merges "only after necessary requirements are met".10

Practices for short-lived branches.

  • One topic per branch, branched from the right base. gitworkflows gives the rule "Make a side branch for every topic (feature, bugfix, …)" and says to fork it from "the oldest integration branch that you will eventually want to merge it into".4 In GitHub flow that base is the default branch.
  • Descriptive names. GitHub notes that "a short, descriptive branch name enables your collaborators to see ongoing work at a glance".5 A prefix convention such as feature/, fix/ or docs/ is common practice rather than a Git or GitHub requirement, but it pays off later: GitHub's branch rules accept fnmatch patterns,11 so prefixes let you target groups of branches.
  • Small scope. If a feature cannot be finished in a few days, split it. This follows from Fowler's and DORA's guidance above; how to split it (for example behind a feature flag) is a design decision outside this guide.
  • Do not keep reusing a branch after a squash merge. GitHub recommends against squash merging a pull request whose head branch you intend to keep working on, because the squash creates a new commit on the base branch while the head branch's history is unchanged, and this "makes merge conflicts more likely".12 Starting a fresh branch from the updated main avoids this.

2.2 Long-lived branches

Concept. A long-lived branch represents a state of the code (stable, next release, a maintained release line) rather than a piece of work. Pro Git describes projects that keep only stable, released code on master and integrate work on a parallel develop or next branch, which is merged into master when stable. It describes these branches as "work silos, where sets of commits graduate to a more stable silo when they're fully tested", and adds that "having multiple long-running branches isn't necessary, but it's often helpful, especially when you're dealing with very large or complex projects".3

The best-known formal model is Vincent Driessen's 2010 git-flow, which keeps two main branches, master and develop, "with an infinite lifetime", plus supporting feature, release and hotfix branches that "always have a limited life time".13 In a 2020 note on the same page, Driessen wrote that web apps "are typically continuously delivered", and that a team doing continuous delivery should "adopt a much simpler workflow (like GitHub flow)", concluding "Consider your own context."13

When a long-lived branch is justified. The common legitimate case is a release branch, which Fowler defines as "a branch that only accepts commits accepted to stabilize a version of the product ready for release".7 Software that ships versioned releases and supports several of them at once needs somewhere to put fixes for each version. Git's own project does this with maint, which "tracks the commits that should go into the next 'maintenance release'".4

Rules that keep long-lived branches manageable.

  • Merge upwards. gitworkflows: "Always commit your fixes to the oldest supported branch that requires them. Then (periodically) merge the integration branches upwards into each other."4 A fix made on release/1.x and merged up into main reaches every newer line without cherry-picking.
  • Expect divergence to grow. Fowler warns that "as more commits modify mainline, it gets harder to merge the release branch into mainline".7 Merge upwards regularly rather than in one large batch at the end of a release.
  • Throw-away integration branches are never a base. To test several topics together, merge them into a throw-away branch, but "You must never base any work on such a branch!"4
  • Do not squash merge a long-running head branch. GitHub warns that if you keep squash merging pull requests from a long-running head branch, "you will have to resolve the same conflicts repeatedly".12 Use a merge commit for develop → main or release → main promotions.
  • Record conflict resolutions. For long-lived topic branches that need repeated test merges, git rerere records "conflicted automerge results and corresponding hand resolve results" and replays them the next time the same conflict appears. It must be enabled with rerere.enabled.14
$ git config --global rerere.enabled true
# Fix on the oldest supported line, then merge upwards
$ git switch release/1.x
$ git switch -c fix/csv-escaping
# ...commit, open PR against release/1.x, merge...
$ git switch main
$ git pull --ff-only
$ git merge --no-ff origin/release/1.x -m "Merge release/1.x into main"

On a protected main (Section 3) that final merge would itself go through a pull request from release/1.x to main rather than a direct push.

GitHub's branches page helps find branches whose lifetime has quietly run out. Its Stale view lists "all branches that no one has committed to in the last three months, ordered by the branches with the oldest commits first".15

3. Branch protection

Branch protection turns workflow conventions into rules the server enforces. GitHub offers two mechanisms. Branch protection rules target a branch name or an fnmatch pattern, and "only a single branch protection rule can apply at a time" to a given branch.11 Rulesets are "a named list of rules"; they "work alongside" branch protection rules, have no priority among themselves, and where rules overlap "the most restrictive version of the rule applies". Anyone with read access can view a repository's rulesets.16 Rulesets are available in public repositories on GitHub Free and in public and private repositories on GitHub Pro, Team and Enterprise Cloud.16

The security article in this series covers protected branches as an access-control measure (signed commits, bypass, code owners for sensitive paths). This section covers the same settings from the workflow side: what each rule does to day-to-day development and how to configure it so it helps rather than blocks.

3.1 Preventing direct pushes

Why. In GitHub flow, "your changes will not end up on the default branch until you merge your branch".5 That promise only holds if nobody can push to the default branch directly. A direct push skips review and CI, and a force push can rewrite history that others have already built on, which Git's documentation calls "a bad idea" because "anyone downstream of it is forced to manually fix their history".17

The settings involved.

  • Require a pull request. With required reviews enabled, "collaborators can only push changes to a protected branch via a pull request that is approved".11 The ruleset equivalent is "Require a pull request before merging", which requires "all changes to the target branch be associated with a pull request".18 This is the rule that actually stops direct pushes for normal contributors.
  • Block force pushes and deletions. "By default, GitHub blocks force pushes on all protected branches" and "by default, you cannot delete a protected branch".11 In rulesets, "Block force pushes" and "Restrict deletions" are both on by default.18
  • Restrict who can push. Branch protection can limit pushes to named users, teams or apps; this option is available on some organisation plans only.11 The ruleset rule "Restrict updates" allows only users with bypass permission to push.18
  • Lock branch. "Locking a branch will make the branch read-only".11 This suits a release branch whose support has ended.
  • Do not allow bypassing. "By default, the restrictions of a branch protection rule do not apply to people with admin permissions to the repository." The Do not allow bypassing the above settings option applies them to administrators too.11 Rulesets instead use an explicit list of roles, teams or GitHub Apps that may bypass.16

Example: a ruleset for the default branch via the REST API. The endpoint is POST /repos/{owner}/{repo}/rulesets; conditions.ref_name.include accepts ~DEFAULT_BRANCH; the rule types deletion and non_fast_forward block deletion and force pushes; and a pull_request rule requires the five parameters shown.19 The example below was written from that reference and not run against a live repository.

{
  "name": "main-protection",
  "target": "branch",
  "enforcement": "active",
  "conditions": {
    "ref_name": { "include": ["~DEFAULT_BRANCH"], "exclude": [] }
  },
  "rules": [
    { "type": "deletion" },
    { "type": "non_fast_forward" },
    { "type": "pull_request",
      "parameters": {
        "required_approving_review_count": 1,
        "dismiss_stale_reviews_on_push": true,
        "require_code_owner_review": false,
        "require_last_push_approval": true,
        "required_review_thread_resolution": true
      } },
    { "type": "required_status_checks",
      "parameters": {
        "strict_required_status_checks_policy": false,
        "required_status_checks": [ { "context": "test" } ]
      } }
  ]
}
$ gh api --method POST repos/acme/shop/rulesets --input main-protection.json   # not run

Keeping the ruleset in a JSON file under version control makes the policy itself reviewable. Applying the same file to several repositories, or using an organisation ruleset, keeps the policy consistent. Both are inferences about good practice, not GitHub requirements.

What a developer sees. With these rules in place, the only route to main is a pull request. A developer who commits to main by mistake has lost nothing: git switch -c fix/whatever creates a branch at the current commit,8 which can then be pushed and opened as a pull request, after which local main can be reset to origin/main.

3.2 Required reviews

Concept. Pull request reviews have three states: Comment, Approve ("ready to merge") and Request changes. Repository administrators "can require approvals before pull requests are merged".20 Required approvals must come "from people with write permissions in the repository or from a designated code owner".11 If a person with admin permissions requests changes, "that person must approve the pull request before the pull request can be merged".11

The settings and what they do to the workflow.

SettingEffectWorkflow consideration
Required approving reviews (count)Every pull request needs that many approvals before merge.11Each extra approver adds waiting time; DORA identifies slow review as a cause of large batches.6
Dismiss stale approvalsApprovals are dismissed "when commits are pushed that affect the diff".11Without it, an approval can cover code the reviewer never saw. With it, every push after approval needs re-review.
Require approval of the most recent reviewable pushThe latest push must be approved "by someone other than the person who pushed it".11Stops an author adding unreviewed commits after approval and merging their own last change.
Require review from Code OwnersCode owners must approve changes to files they own.21Routes reviews automatically; see below.
Require conversation resolution"Requires all comments on the pull request to be resolved before it can be merged".11Makes unresolved review threads blocking rather than advisory.
Restrict who can dismiss reviewsLimits review dismissal to "specific people or teams".11Prevents an author dismissing a "Request changes" review to get past it.

Code owners. A CODEOWNERS file in .github/, the repository root or docs/ maps paths to people or teams, and "code owners are automatically requested for review when someone opens a pull request that modifies code that they own". GitHub reads the file from the pull request's base branch, and does not automatically request code-owner review on draft pull requests.21 Two workflow consequences follow. Because the base branch's file is used, a pull request cannot change who reviews it by editing CODEOWNERS in the same change. And because drafts do not trigger requests, opening a draft is a way to share early work without pulling in owners; both are inferences from the documented behaviour.

# .github/CODEOWNERS
*                 @acme/maintainers
/docs/            @acme/docs
/src/payments/    @acme/payments
*.sql             @acme/data

Choosing a review baseline. A reasonable default for a small team is one approval, stale approvals dismissed, approval of the most recent push, and conversation resolution, which is what the ruleset example above encodes. Larger teams can add code-owner review for areas with clear ownership. This is a recommendation, not a GitHub default; the trade-off is that every added requirement lengthens the time a branch stays open, which works against the short lifetimes discussed in Section 2.

3.3 Required CI

Concept. "Status checks show whether commits meet the conditions set for a repository." They come in two kinds: checks, created by GitHub Apps including GitHub Actions, and commit statuses, created by external services. "If status checks are required for a protected branch, they must pass before the pull request can be merged."22 A required check passes when it has a successful, skipped or neutral status.11 Fowler's healthy branch pattern describes the goal: "on each commit, perform automated checks, usually building and running tests, to ensure there are no defects on the branch".7

Strict versus loose. The most important workflow choice is the checkbox Require branches to be up to date before merging.11

  • Strict (checked): "The branch must be up to date with the base branch before merging." GitHub notes that "more builds may be required", because every pull request has to be brought up to date whenever someone else merges first.11
  • Loose (unchecked): the branch need not be up to date. Fewer builds run, but checks may fail after merging if the change is incompatible with what has landed on the base branch since.11

For GitHub Actions workflows triggered by pull_request, GITHUB_REF is the pull request's merge branch refs/pull/PULL_REQUEST_NUMBER/merge, and GITHUB_SHA is the last merge commit on that ref.23 In other words, CI tests a trial merge of the pull request into the base branch, not just the branch on its own. Inference: this narrows the gap that loose mode leaves, but does not close it, because the base branch can move after the checks ran, and another pull request merged in the meantime is not part of the tested merge.

Merge queues: strict correctness without strict churn. A merge queue "helps increase velocity by automating pull request merges into a busy branch" while "ensuring the branch is never broken by incompatible changes", and "does not require a pull request author to update their pull request branch".24 It validates changes on temporary branches with the prefix gh-readonly-queue/{base_branch}. CI must be configured for this: "You must use the merge_group event to trigger your GitHub Actions workflow", otherwise required checks are not triggered for queued pull requests.24 Merge queues are available in public repositories owned by organisations, and in private repositories of organisations on GitHub Enterprise Cloud.24 With gh pr merge, a pull request targeting a queue-protected branch is added to the queue if checks have passed, or set to auto-merge if they have not.10

Example: a workflow suitable as a required check. (Not run against a live repository.)

# .github/workflows/ci.yml
name: ci
on:
  pull_request:          # default types: opened, synchronize, reopened
  merge_group:           # needed if main uses a merge queue
  push:
    branches: [main]
permissions:
  contents: read
jobs:
  test:                  # the check name to mark as required
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: make test

By default a pull_request workflow runs only for the activity types opened, synchronize and reopened, and merge_group runs "when a pull request is added to a merge queue".23

Pitfalls that block merging.

  • Skipped workflows. If a required workflow is skipped by path filtering, branch filtering or a commit-message directive, "associated checks stay in a 'Pending' state and block merging". GitHub's advice is to "avoid requiring workflows that can be skipped".25 So do not put a paths: filter on the workflow that provides a required check.
  • Checks must be current. "Required checks must pass on the latest commit SHA. Checks from earlier commits don't satisfy the requirement."25
  • Checks must have run recently. GitHub states that "a required status check must have completed successfully in the chosen repository during the past seven days".25 Inference: add the workflow and let it run on a pull request before marking it as required.
  • Merge conflicts stop CI. "Workflows will not run on pull_request activity if the pull request has a merge conflict."23 A conflicted pull request shows no fresh results until it is brought up to date, which is the subject of the next section.

4. Keeping branches current

Knowing how far behind you are. Remote-tracking branches such as origin/main are "references to the state of remote branches" that Git updates during network operations.26 git fetch downloads new commits "but it will not modify your working directory at all".26 After a fetch, git branch -vv shows each branch's upstream and whether it is ahead, behind or both. These numbers are "only since the last time you fetched", because the command does not contact the server.26

$ git fetch
From github.com:acme/shop
   a8a7bdb..227544a  main       -> origin/main
$ git branch -vv
* feature/login 52ece8f [origin/feature/login] Validate login input
  main          a8a7bdb [origin/main: behind 1] Initial commit

Here a teammate has merged a header change into main on GitHub. feature/login does not yet contain it. There are two ways to bring it in. Both end with the same file contents: Pro Git stresses that the final snapshot of a merge and of a rebase "is the same snapshot — it's only the history that is different".27

When to update. gitworkflows discourages updating "just habitually": its rule is "Do not merge to downstream except with a good reason: upstream API changes affect your branch; your branch no longer merges to upstream cleanly; etc."4 The git rerere documentation makes the same point about clutter, noting that a long-lived topic branch "would end up having many such 'Merge from master' commits on it, which would unnecessarily clutter the development history".14 On GitHub, three concrete triggers apply: the pull request shows a conflict (which also stops CI23); strict status checks require the branch to be up to date11; or you need something that has landed on main.

4.1 Merge from main

Concept. git merge "incorporates changes from the named commits (since the time their histories diverged from the current branch) into the current branch". When histories have diverged, the result is a merge commit "that has both of them as its parents".28 Nothing existing is rewritten. Pro Git describes this view of history as a "record of what actually happened".27

$ git switch feature/login
$ git merge origin/main -m "Merge origin/main into feature/login"
Merge made by the 'ort' strategy.
 header.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 header.txt
$ git log --oneline --graph --decorate --all
*   d4d3f08 (HEAD -> feature/login) Merge origin/main into feature/login
|\
| * 227544a (origin/main) Add site header
* | 52ece8f (origin/feature/login) Validate login input
* | bcbef81 Add login form
|/
* a8a7bdb (main) Initial commit
$ git push
To github.com:acme/shop.git
   52ece8f..d4d3f08  feature/login -> feature/login

The push is an ordinary fast-forward of the remote branch, because the old tip 52ece8f is a parent of the new one. Merging origin/main rather than local main uses what was just fetched without first updating local main.

On GitHub. The Update branch button on a pull request performs this same "traditional merge" from the base branch. It is available "when there are no merge conflicts and the branch is behind the base branch", to people with write access; conflicts must be resolved first.29

Conflicts. When both sides changed the same area, Git "asks you to resolve it by leaving what both sides did to that area" in the file.28 Resolve, git add, and commit; or back out with git merge --abort. The documentation recommends committing or stashing uncommitted changes before merging, because --abort cannot always reconstruct them.28

When to prefer merging.

  • The branch is shared: someone else has pushed to it or based work on it. Merging never invalidates their commits.
  • The commits are signed, or their exact hashes are referenced somewhere (review comments, issue links). Merging preserves them.
  • The branch is long-lived (Section 2.2). gitworkflows recommends merging upwards between integration branches, not rebasing them.4

The cost is merge commits that carry no feature work. If the pull request is squash merged, those commits disappear from main anyway. This is an inference from how squash merging works, since a squash produces a single new commit on the base branch.12

4.2 Rebase onto main

Concept. git rebase transplants "a series of commits onto a different starting point". In outline it lists the branch's commits that are not already in the upstream, checks out the upstream, replays the commits one by one "similar to running git cherry-pick", and moves the branch to the result.17 Pro Git notes the benefit, "rebasing makes for a cleaner history", and the cost: "you're abandoning existing commits and creating new ones that are similar but different".27

Worked example, including a conflict. Here the teammate's change to main and the branch both edited README.md:

$ git fetch
From github.com:acme/shop
   3fc054c..2be0ea1  main       -> origin/main
$ git rebase origin/main
Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
error: could not apply 7f2cde0... Document cart in README
hint: Resolve all conflicts manually, mark them as resolved with
hint: "git add/rm <conflicted_files>", then run "git rebase --continue".
hint: You can instead skip this commit: run "git rebase --skip".
hint: To abort and get back to the state before "git rebase", run "git rebase --abort".
Could not apply 7f2cde0... Document cart in README
$ git status --short
UU README.md
# edit README.md to keep both lines
$ git add README.md
$ git rebase --continue
[detached HEAD 0d353cd] Document cart in README
 1 file changed, 1 insertion(+)
Successfully rebased and updated refs/heads/feature/cart.
$ git log --oneline --graph --decorate --all
* 0d353cd (HEAD -> feature/cart) Document cart in README
* a1124d9 Add cart model
* 2be0ea1 (origin/main) Add license line to README
| * 7f2cde0 (origin/feature/cart) Document cart in README
| * b804e3d Add cart model
|/
* 3fc054c (main) Initial commit

Rebase stops at the first commit that conflicts. You can resolve it and run git rebase --continue, skip that commit with --skip, or return the branch to its original state with --abort.17 The graph shows the important fact: the commits have new hashes (a1124d9 and 0d353cd), and the old ones (b804e3d and 7f2cde0) are still what GitHub has.

Publishing a rebased branch. Because the old remote tip is no longer an ancestor of the local branch, a normal push is refused:

$ git status -sb
## feature/cart...origin/feature/cart [ahead 3, behind 2]
$ git push
To github.com:acme/shop.git
 ! [rejected]        feature/cart -> feature/cart (non-fast-forward)
error: failed to push some refs to 'github.com:acme/shop.git'
hint: Updates were rejected because the tip of your current branch is behind
hint: its remote counterpart. If you want to integrate the remote changes,
hint: use 'git pull' before pushing again.

The hint to git pull is wrong in this situation: pulling would merge the old, pre-rebase commits back in. Replacing the remote branch needs a force push, and the safe form is --force-with-lease. It overrides the fast-forward rule only "if the current value of the remote ref is the expected value", by default the value of your remote-tracking branch. The documentation describes it as taking "a 'lease' on the ref without explicitly locking it", so that if somebody else has pushed since you last fetched, their work is not lost.9 The documentation also warns that a background fetch (for example by an IDE) updates the remote-tracking branch and defeats this protection. --force-if-includes closes that gap by also checking that the remote tip "has been integrated locally", using the local branch's reflog.9

All three outcomes, observed:

# 1. Nobody else pushed: the lease holds and the branch is replaced
$ git push --force-with-lease
To github.com:acme/shop.git
 + 9e61163...7b0bed0 feature/search -> feature/search (forced update)

# 2. A teammate pushed to feature/cart after our last fetch: refused
$ git push --force-with-lease
To github.com:acme/shop.git
 ! [rejected]        feature/cart -> feature/cart (stale info)

# 3. We fetched (so the lease alone would now pass) but never integrated their commit
$ git fetch
From github.com:acme/shop
   7f2cde0..89fe5af  feature/cart -> origin/feature/cart
$ git push --force-with-lease --force-if-includes
To github.com:acme/shop.git
 ! [rejected]        feature/cart -> feature/cart (remote ref updated since checkout)

In case 3, plain --force-with-lease would have succeeded and silently discarded the teammate's commit 89fe5af. That follows from the documented default (the lease compares against the remote-tracking branch, which the fetch had just updated).9 The correct response is to rebase again on top of origin/feature/cart to pick up their commit, then push.

The golden rule. Pro Git's rule is "Do not rebase commits that exist outside your repository and that people may have based work on", summarised as "rebase local changes before pushing to clean up your work, but never rebase anything that you've pushed somewhere".27 A pushed pull request branch is, strictly, "pushed somewhere". In practice many teams treat a single-author pull request branch as private until review starts, and rebase it freely with --force-with-lease. Inference: that is consistent with the rule's intent, which is about other people's work, so long as nobody else has based work on the branch. Once a second person pushes to it, switch to merging.

On GitHub. The Update branch dropdown offers Update with rebase, which "creates a linear history without a merge commit".29 Because GitHub rewrites the branch on the server, anyone with a local copy then has a branch that has diverged from origin. Inference: after using it, update local copies with git fetch and git reset --hard origin/<branch> (after checking there is no unpushed work) rather than git pull, which would merge the old commits back in.

Rebase details worth knowing.

  • --update-refs "automatically force-update[s] any branches that point to commits that are being rebased", which keeps a stack of dependent branches together.17
  • --autostash stashes uncommitted changes before the rebase and reapplies them afterwards, with the warning that the reapplication "might result in non-trivial conflicts".17
  • git rebase --onto main server client moves only the commits that are on client but not on server onto main, which is how you re-base a branch that was started from the wrong place.27

Updating local main itself. git pull runs git fetch and then integrates the upstream branch.30 Current documentation lists four integration modes and describes --ff-only as the default "when no method for reconciling divergent histories is provided".30 Git 2.43 refuses outright when local main has diverged and no preference is configured:

$ git pull
hint: You have divergent branches and need to specify how to reconcile them.
hint: You can do so by running one of the following commands sometime before
hint: your next pull:
hint:
hint:   git config pull.rebase false  # merge
hint:   git config pull.rebase true   # rebase
hint:   git config pull.ff only       # fast-forward only
...
fatal: Need to specify how to reconcile divergent branches.

With protected branches, local main should never contain commits that are not on origin/main, since nothing reaches GitHub's main except through a pull request. Inference: git config --global pull.ff only is therefore a good default. A pull that cannot fast-forward then signals a mistake (a commit made on main by accident) instead of hiding it in a merge.

Choosing between merge and rebase

"Ordinary push" and "Yes" in the merge column follow from merge not rewriting existing commits; they are inferences, as is the per-commit statement about conflicts beyond what the rebase documentation describes for the first conflicting commit.

Recommendation (inference). Rebase a branch only you work on; merge into a branch others share; and use a merge commit, never a rebase, between long-lived branches. If the repository squash merges pull requests, the choice matters only during review, because the branch's own history does not reach main. If Require linear history is enabled, which "prevents collaborators from pushing merge commits to the branch",11 that applies to the protected branch, not to your topic branch; GitHub's squash or rebase merge methods produce the linear result.

5. Cleaning branches

Why clean up. GitHub's flow ends with "After you merge your pull request, delete your branch", because this "indicates that the work on the branch is complete and prevents you or others from accidentally using old branches". It adds: "Don't worry about losing information. Your pull request and commit history will not be deleted."5 A branch is only a pointer,1 so deleting a merged branch loses nothing that main does not already contain.

There are three separate things to clean, and each has its own command:

WhatLives inRemoved by
Local branch, e.g. feature/loginYour clonegit branch -d / -D31
Remote branch, e.g. feature/login on GitHubGitHubgit push origin --delete9, the GitHub UI, or automatic deletion32
Remote-tracking branch, e.g. origin/feature/loginYour clonegit fetch --prune or git remote prune33,34

The scenario used in this section: fix/typo was merged on GitHub with a merge commit, feature/export was squash merged, and GitHub deleted both head branches. spike/graphql was an experiment that is being abandoned.

5.1 Local deletion

Safe deletion with -d. git branch -d deletes a branch only if it is "fully merged in its upstream branch, or in HEAD if no upstream was set". -D is shorthand for --delete --force and deletes "irrespective of its merged status".31 --merged lists branches "whose tips are reachable from" a commit (default HEAD), and --no-merged lists those that are not.31 Pro Git's own examples delete branches with -d as soon as their work has been merged.2

$ git switch main
$ git pull --ff-only                     # bring in the merges done on GitHub first
Updating a155f29..41b66ad
Fast-forward
 feature_export.txt | 2 ++
 fix_typo.txt       | 2 ++
 2 files changed, 4 insertions(+)
$ git branch --merged
  fix/typo
* main
$ git branch -d fix/typo
Deleted branch fix/typo (was 03f5106).
$ git branch -d feature/export
error: the branch 'feature/export' is not fully merged.
If you are sure you want to delete it, run 'git branch -D feature/export'

The squash-merge problem. feature/export's work is in main, but git branch does not list it as merged and -d refuses. The reason is that a squash merge creates a new commit on the base branch containing the changes, while the head branch's own commits are never added to the base branch's history.12 "Merged", for git branch, means the branch tip is reachable from HEAD,31 and the original commits are not. GitHub's rebase and merge method has the same effect, because it creates new commit SHAs.12

Rather than reaching for -D blindly, check that the branch would add nothing. git merge-tree --write-tree performs a merge "but does not make any new commits and does not read from or write to either the working tree or index", and prints the OID of the resulting top-level tree.35 If merging the branch into main would produce exactly main's current tree, everything on the branch is already there:

$ git merge-tree --write-tree main feature/export
0c47fdc2f9a6cd4c0f2dc0f1ad649e700887abf1
$ git rev-parse 'main^{tree}'
0c47fdc2f9a6cd4c0f2dc0f1ad649e700887abf1     # identical: nothing left to merge
$ git branch -D feature/export
Deleted branch feature/export (was e22355e).

Inference: this test is conservative. It can report a difference for a branch that was merged if main later changed the same lines, so a mismatch means "check the pull request", not "unmerged work". git merge-tree --write-tree requires a reasonably recent Git; it worked in 2.43 for this guide.

One more nuance, observed in Git 2.43. Because -d checks the upstream first, a squash-merged branch whose upstream still exists (GitHub has not deleted it, or you have not pruned) is deleted with a warning, not refused:

$ git branch -d feature/export
warning: deleting branch 'feature/export' that has been merged to
         'refs/remotes/origin/feature/export', but not yet merged to HEAD
Deleted branch feature/export (was 56faa08).

That matches the documented rule ("fully merged in its upstream branch"31): the branch was safe to delete because the remote still had it, not because main did.

Recovering a deleted branch. Deleting a branch removes only the pointer. Git prints the tip's hash on deletion (was f20ca65), and you can recreate the branch from it. The branch's own reflog is removed with the branch, as the transcript shows, but HEAD's reflog keeps the commits you had checked out. Reflogs "record when the tips of branches and other references were updated in the local repository", and their entries expire after gc.reflogExpire (90 days by default) or, for entries not reachable from the current tip, gc.reflogExpireUnreachable (30 days).36

$ git branch -D spike/graphql
Deleted branch spike/graphql (was f20ca65).
$ git reflog show spike/graphql
fatal: ambiguous argument 'spike/graphql': unknown revision or path not in the working tree.
$ git branch spike/graphql f20ca65          # recreate from the printed hash
$ git log --oneline -1 spike/graphql
f20ca65 More work on spike/graphql

5.2 Remote deletion

From the command line. git push origin --delete <branch> deletes the branch on the remote; -d/--delete "is the same as prefixing all refs with a colon", so git push origin :dev is the older equivalent.9 Pro Git notes that "all this does is to remove the pointer from the server", and that the server "will generally keep the data there for a while until a garbage collection runs".26

$ git push origin --delete spike/graphql
To github.com:acme/shop.git
 - [deleted]         spike/graphql

A protected branch cannot be deleted this way, because protected branches cannot be deleted by default.11 That is the intended behaviour for main and release branches.

Automatically, on merge. The most reliable approach is to let GitHub do it. A repository administrator can enable Automatically delete head branches under Settings → General → Pull Requests, after which head branches are deleted when their pull requests are merged. Branch protection rules and rulesets can prevent particular branches from being deleted automatically.32 gh pr merge --delete-branch does the same for a single merge, and also deletes the local branch.10

In the GitHub UI. On a merged or closed pull request, a Delete branch button removes the head branch, provided no other open pull request references it. If it was deleted by mistake, the head branch of a closed pull request can be brought back with Restore branch.37 Deleting the branch does not delete the pull request or its commit history.5

Finding branches to delete. GitHub's Stale branch view lists branches with no commits in three months.15 Locally, after a fetch, git branch -r --merged origin/main lists remote branches already contained in main, using the same reachability test as for local branches.31 As with local branches, squash-merged branches will not appear in that list.

5.3 Pruning

Why stale remote-tracking branches exist. Deleting a branch on GitHub does not delete origin/<branch> in anyone's clone. The git fetch documentation explains: "Git has a default disposition of keeping data unless it's explicitly thrown away; this extends to holding onto local references to branches on remotes that have themselves deleted those branches." Left to accumulate, these can slow down "big and busy repos that have a lot of branch churn" and clutter commands such as git branch -a --contains.33

$ git fetch                                   # fetch alone does not remove anything
From github.com:acme/shop
   a155f29..41b66ad  main       -> origin/main
$ git branch -r
  origin/feature/export
  origin/fix/typo
  origin/main
  origin/spike/graphql
$ git remote prune origin --dry-run           # preview
Pruning origin
URL: github.com:acme/shop.git
 * [would prune] origin/feature/export
 * [would prune] origin/fix/typo
$ git fetch --prune
From github.com:acme/shop
 - [deleted]         (none)     -> origin/feature/export
 - [deleted]         (none)     -> origin/fix/typo

git fetch --prune removes, before fetching, "any remote-tracking references that no longer exist on the remote". git remote prune <name> is equivalent "except that no new references will be fetched", and --dry-run reports what would be pruned.33,34 git branch -r -d can delete a single remote-tracking branch, but the documentation notes this only makes sense if the branch no longer exists on the remote, or fetch has been configured not to fetch it again.31

Make it automatic. Set fetch.prune (all remotes) or remote.<name>.prune (one remote), and every fetch, including the fetch inside git pull, will prune.33

$ git config --global fetch.prune true

Be careful with tags. Pruning follows the remote's refspec, not branches as such. --prune-tags (or fetch.pruneTags) also deletes local tags that do not exist on the remote, and the documentation warns this "should be used more carefully" because it removes tags you created locally.33 Plain fetch.prune does not prune tags fetched by the default tag auto-following.33

From pruned remote-tracking branches to local cleanup. Pruning removes origin/fix/typo but not your local fix/typo. The local branch's upstream is then reported as gone:

$ git branch -vv
  feature/export e22355e [origin/feature/export: gone] More work on feature/export
  fix/typo       03f5106 [origin/fix/typo: gone] More work on fix/typo
* main           a155f29 [origin/main: behind 4] Initial commit
  spike/graphql  f20ca65 [origin/spike/graphql] More work on spike/graphql

git for-each-ref's %(upstream:track) field prints "[gone]" "whenever unknown upstream ref is encountered",38 which makes the state scriptable. The following deletes every local branch whose upstream is gone, using -d so that anything Git cannot prove merged is kept back for review:

$ git for-each-ref --format='%(refname:short) %(upstream:track)' refs/heads \
    | awk '$2 == "[gone]" {print $1}' | xargs -r git branch -d
error: the branch 'feature/export' is not fully merged.
If you are sure you want to delete it, run 'git branch -D feature/export'
Deleted branch fix/typo (was 3608332).

The merge-commit branch went; the squash-merged branch was kept for a manual check with the merge-tree test from Section 5.1. Inference: a gone upstream combined with automatic head-branch deletion on GitHub is strong evidence that the pull request was merged, but not proof, because branches can also be deleted after a pull request is closed unmerged.37 That is why the script uses -d and not -D.

A complete cleanup routine.

$ git switch main
$ git pull --ff-only                          # with fetch.prune=true this also prunes
$ git branch --merged main | grep -v '^\*'    # review, then delete with -d
$ git for-each-ref --format='%(refname:short) %(upstream:track)' refs/heads \
    | awk '$2 == "[gone]" {print $1}'            # check each against its PR or with merge-tree

6. Summary checklist

Lifetimes

  • One topic per short-lived branch, from main4,5
  • Aim to merge within hours to days6,7
  • Long-lived branches only for release lines; fix oldest, merge upwards4
  • Merge commits, not squash, for long-lived branches12
  • rerere.enabled for repeated conflicts14

Protection

  • Pull request required; force pushes and deletion blocked11,18
  • Admins included, or an explicit bypass list11,16
  • 1+ approval, dismiss stale, approve latest push11
  • Required CI check that is never path-filtered25
  • Strict checks or a merge queue with merge_group11,24

Currency

  • Update when there is a reason: conflict, strict checks, needed change4
  • Merge into shared branches27
  • Rebase private branches; push with --force-with-lease --force-if-includes9
  • pull.ff only for local main (inference)30

Cleanup

  • Auto-delete head branches on GitHub32
  • fetch.prune true33
  • Delete with -d; check squash merges before -D31,35
  • Recover from the printed hash or HEAD reflog; Restore branch on GitHub36,37
