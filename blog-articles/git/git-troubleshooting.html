Git Troubleshooting

1. Concepts you need first

Almost every Git "disaster" is a pointer pointing somewhere unexpected. Recovery becomes mechanical once the pointers are clear.

Commits, branches and HEAD

A branch in Git is "simply a lightweight movable pointer" to a commit, and is stored as a file containing the hash of the commit it points to [1]. HEAD is a further pointer: normally it refers to the local branch you are currently on [1]. When you commit, Git creates the new commit with the current tip as its parent and moves the branch that HEAD refers to forward to it [2].

The three trees

Git manages three collections of files during normal work: HEAD (the last commit snapshot, and the parent of the next one), the index or staging area (the proposed next commit), and the working directory (the files you edit) [3]. Many undo commands differ only in which of these three they rewrite, which is why git reset --soft, --mixed and --hard behave so differently (section 3).

Naming commits relative to others

  • HEAD~3 is the third first-parent ancestor of HEAD; HEAD^2 is its second parent, which only exists for merge commits [4].
  • main@{1} is the immediately prior value of main, read from the reflog, and HEAD@{2} is where HEAD was two moves ago [4,5].
  • @{-1} is the branch or commit checked out before the current one; git switch - is a synonym for switching to it [4,6].
  • main@{upstream} (short form @{u}) is the remote-tracking branch that main builds on, typically refs/remotes/origin/main [4].
  • ORIG_HEAD is written by commands that move HEAD drastically (git am, git merge, git rebase, git reset) to record where it was before, so you can go back [4].

The reflog: Git's flight recorder

Reference logs ("reflogs") record when the tips of branches and other references were updated in the local repository [5]. Every commit, checkout, reset, merge and rebase therefore leaves a trail. The reflog is local: it records movements in your clone, not on GitHub.

Reachability and garbage collection

A commit that no branch, tag or other reference can reach is not deleted immediately. git gc keeps objects referenced by branches, tags, the index, remote-tracking branches, reflogs and anything else under refs/ [7]. Reflog entries themselves expire: by default after 90 days, or 30 days for entries no longer reachable from the current tip (gc.reflogExpire and gc.reflogExpireUnreachable) [5,7]. Unreachable objects are pruned only after a grace period, which defaults to two weeks (gc.pruneExpire) [7]. This is why the Pro Git book can say that anything committed "can almost always be recovered", whereas changes that were never committed are likely gone for good [8].

The first rule of recovery. Before experimenting, pin the state you might want back with a throwaway branch, for example git branch rescue-$(date +%s). A branch is cheap to create and delete [1], and a commit reachable from a branch is protected from garbage collection [7].

Local versus remote

Cloning names the remote origin automatically [9]. Remote-tracking branches such as origin/main are local references to the state of the remote's branches; Git moves them whenever you communicate with the remote [10]. git fetch only downloads data and updates those references; it does not merge anything into your work [9]. git pull is a fetch followed by an integration step, either a merge or a rebase [11].

An update that moves a ref from commit A to commit B is a fast-forward if and only if B is a descendant of A; a fast-forward loses no history, whereas a non-fast-forward update does, so git push refuses non-fast-forward updates by default [12]. Most push trouble in sections 4 and 7 follows from this rule.

2. Detached HEAD

"Detached HEAD" means simply that HEAD refers to a specific commit rather than to a named branch [2]. Nothing is broken. You can build, test and even commit. The risk is only that new commits are referenced by nothing except HEAD, so they become unreachable the moment you switch away.

2.1 Causes

  • Checking out something that is not a local branch. Detaching is the default behaviour of git checkout <commit> when the argument is not a branch name [2]. That covers a commit hash, a tag (git checkout v2.0), a relative name such as main^^ [2], and a remote-tracking branch such as origin/main, which is a reference to the remote's state rather than a local branch [10].
  • Explicit detachment. git switch requires --detach to move to a commit, for example git switch --detach HEAD~3 [6]. git checkout --detach does the same [2].
  • Submodules. With the default checkout update procedure, git submodule update checks out the commit recorded in the superproject on a detached HEAD inside the submodule [13].
  • Operations in progress. git bisect checks out commits in the middle of the range under test and returns to the original HEAD with git bisect reset [14]. A rebase also works on a detached HEAD while it replays commits: in the transcript in section 7, the commit created mid-rebase is reported as [detached HEAD 83a39d4] (observed). In both cases, finish or abort the operation rather than "fixing" the detached state by hand.

Git announces the state when you enter it:

$ git checkout HEAD~1
Note: switching to 'HEAD~1'.

You are in 'detached HEAD' state. You can look around, make experimental
changes and commit them, and you can discard any commits you make in this
state without impacting any branches by switching back to a branch.

If you want to create a new branch to retain commits you create, you may
do so (now or later) by using -c with the switch command. Example:

  git switch -c <new-branch-name>
...
HEAD is now at 09d7054 Commit 2

2.2 Committing while detached

Committing in this state works normally: the new commit's parent is the detached commit, and HEAD moves to the new commit, but no branch moves with it [2]. You can keep committing; each new commit is reachable only through HEAD. When you then switch to a branch, nothing refers to those commits any more, and they will eventually be removed by garbage collection unless you create a reference first [2]. Git warns you as you leave:

$ git switch main
Warning: you are leaving 1 commit behind, not connected to
any of your branches:

  351d47d Experiment

If you want to keep it by creating a new branch, this may be a good time
to do so with:

 git branch <new-branch-name> 351d47d

Switched to branch 'main'

2.3 Recovery

Still detached, want to keep the work. Create a reference to the current commit. The git-checkout manual lists three equivalent ways [2]:

$ git switch -c experiment     # new branch here, and attach HEAD to it
$ git branch experiment        # new branch here, HEAD stays detached
$ git tag experiment-1         # tag here, HEAD stays detached

To publish the rescued work on GitHub, push the new branch and open a pull request from it: git push -u origin experiment.

Still detached, want to discard the work. Switch back with git switch main, or return to wherever you were before with git switch - [6].

Already switched away. First recover the commit's hash, typically from the reflog, then create a reference to it [2]:

$ git reflog -4
1c966a6 HEAD@{0}: checkout: moving from 351d47d3c035ed1cfd8d93a2fa128d1f2277935e to main
351d47d HEAD@{1}: commit: Experiment
09d7054 HEAD@{2}: checkout: moving from main to HEAD~1
1c966a6 HEAD@{3}: commit: Commit 3
$ git branch rescue HEAD@{1}      # or: git branch rescue 351d47d
$ git log --oneline -2 rescue
351d47d Experiment
09d7054 Commit 2

git log -g shows the same reflog in full log format, which helps when commit messages alone are not enough to identify the right entry [2,15].

3. Accidental reset

git reset <commit> moves the branch that HEAD points to, which is different from checkout, which moves HEAD itself [3]. Its modes decide how much of the three trees follows:

ModeBranch tipIndexWorking treeUncommitted work at risk?
--softmovedunchangedunchangedNo
--mixed (default)movedreset to new tipunchangedNo
--hardmovedreset to new tipoverwrittenYes
--keepmovedresetupdated; aborts if a file to be changed has local editsNo (refuses instead)

Table 1. Effects of git reset modes, summarised from the git-reset manual [16] and Pro Git, "Reset Demystified" [3].

--hard overwrites files in the working tree and may overwrite untracked files [16]; Pro Git calls it the only form that makes reset dangerous, "one of the very few cases where Git will actually destroy data" [3]. That damage, however, is limited to uncommitted changes. Commits that a reset moved the branch away from still exist and are still in the reflog.

3.1 Reflog recovery

Suppose main was reset two commits too far:

$ git reset --hard HEAD~2
HEAD is now at fa39b7f Commit 1
$ git reflog -3
fa39b7f HEAD@{0}: reset: moving to HEAD~2
1c966a6 HEAD@{1}: checkout: moving from 351d47d... to main
351d47d HEAD@{2}: commit: Experiment

The entry before the reset, HEAD@{1}, is where the branch used to be. Reset back to it:

$ git reset --hard HEAD@{1}
HEAD is now at 1c966a6 Commit 3

Three equivalent targets are available:

  • ORIG_HEAD. git reset sets it to the branch tip before the operation [16], so git reset --hard ORIG_HEAD undoes the most recent reset, as long as no later drastic command has overwritten it [4].
  • main@{1}, the branch's own reflog, which is immune to unrelated HEAD movements such as switching branches [4].
  • A commit hash read from git reflog or git log -g.

If you would rather inspect before moving main, create a branch at the old tip (git branch recover HEAD@{1}), compare, and then decide. This is the procedure Pro Git demonstrates for commits lost to a hard reset [15].

When the reflog has nothing. If the reflog is gone (for example, a fresh clone, or a deleted .git/logs/), git fsck --full lists objects that nothing points to; lost commits appear as "dangling commit" lines, and you can recover one by creating a branch at its hash [15].

What cannot be recovered. Uncommitted edits to tracked files that --hard overwrote are not in the reflog, because they were never committed [8]. (Content you had staged with git add is a partial exception: staging creates objects in the repository, which git gc later removes if they become unreachable [7], and git fsck --full lists such leftovers as "dangling blob" entries [15]. Fishing a file out of them is a last resort, not a plan.) The habit that prevents this class of loss is git stash or a commit before any reset --hard, or using --keep, which aborts instead of overwriting local changes [16].

4. Accidental commit

Which tool fits depends almost entirely on one question: has the commit been pushed and possibly fetched by someone else? Amend and reset rewrite history; revert adds history. Rewriting local history is harmless. Rewriting published history forces everyone downstream to repair their clones [17], which is why Pro Git's advice is to amend only commits "that are still local and have not been pushed somewhere" [8].

SituationNot yet pushedAlready pushed
Wrong message, forgotten file, small fix to the last commitgit commit --amendNew fix-up commit, or git revert
Last few commits should not exist, or should be rebuiltgit resetgit revert
Committed to the wrong branchgit branch + git resetgit revert on the wrong branch, cherry-pick or re-push to the right one
Committed a secretAmend or reset, and rotate the secretRotate the secret first; then see section 5.2

Table 2. Choosing a remedy for an unwanted commit. Rationale from the git-commit, git-reset and git-revert manuals [16,18,19] and GitHub Docs [20].

4.1 Amend

git commit --amend replaces the tip of the current branch with a new commit, built from the current index, with the same parents and author as the one it replaces; the old commit message is the starting point unless you supply a new one [18]. Pro Git stresses that you are not fixing the commit so much as replacing it with a new one [8].

# Fix only the message
$ git commit --amend -m "Add login form validation"

# Add a forgotten file, keep the message
$ git add src/validators.js
$ git commit --amend --no-edit

# Remove a file that should never have been committed (it stays on disk)
$ git rm --cached .env
$ echo ".env" >> .gitignore && git add .gitignore
$ git commit --amend --no-edit

--no-edit reuses the existing message without opening an editor [18]. The git-commit manual describes --amend as a rough equivalent of git reset --soft HEAD^ followed by a new commit, and warns that amending a commit that has already been published has the implications of rewriting history [18]. If you amend a commit you already pushed to a branch on GitHub, the next ordinary push is rejected as non-fast-forward, which is the subject of section 5.

If you amend by mistake, the original commit is still in the reflog, so git reset --soft HEAD@{1} moves the branch back to it while keeping the amended content staged (reflog semantics [4], reset modes [16]).

4.2 Reset

Reset is the tool for removing or rebuilding one or more local commits. Pick the mode by what you want to keep [16]:

# Undo the last commit, keep its changes staged (redo it differently)
$ git reset --soft HEAD~1

# Undo the last commit, keep its changes in the working tree but unstaged
$ git reset HEAD~1

# Squash the last five commits into one (with no other staged changes)
$ git reset --soft HEAD~5 && git commit

# Throw away the last three commits entirely
$ git reset --hard HEAD~3

The manual's "undo a commit and redo" example shows the soft form followed by git commit -c ORIG_HEAD, which reopens the old message for editing [16]. Its "undo commits permanently" example carries the warning: do not do this if you have already given these commits to somebody else [16].

Worked example: committed to main instead of a feature branch. You made two commits on local main that belong on a new branch, and have not pushed:

$ git branch feature/login      # 1. pin the commits with a new branch
$ git reset --keep origin/main   # 2. move main back to match GitHub
$ git switch feature/login        # 3. continue the work there
$ git push -u origin feature/login

Step 1 makes the commits reachable from a branch before anything moves. Step 2 uses --keep rather than --hard so that, if a file the reset would change has uncommitted edits, the reset aborts instead of overwriting them [16]; origin/main is the last known state of GitHub's main [10].

4.3 Revert

git revert records new commits that reverse the changes introduced by earlier ones [19]. History is only added to, so it is safe on branches other people have pulled, and pushing a revert is an ordinary fast-forward [12]. It needs a clean working tree [19].

$ git revert HEAD                 # reverse the last commit
$ git revert a28ccef              # reverse any earlier commit
$ git revert -n HEAD~3..HEAD      # reverse a range into one commit
$ git commit -m "Revert login rollout"

-n (--no-commit) applies the reversal to the index and working tree without committing, which lets you combine several reverts into a single commit [19]. If a revert conflicts, resolve as for a merge and run git revert --continue, or git revert --abort to return to the state before the sequence began [19].

Revert is not a way to discard uncommitted changes; the manual points to git reset --hard or git restore for that, and warns that both discard work [19]. Reverting a merge commit has special rules, covered in section 6.

5. Accidental push

Once a commit is on GitHub, assume someone has fetched it: a colleague, a CI job, a fork. You now have two strategies. Revert keeps history intact and needs no coordination. Rewriting removes the commit from the branch but requires a forced push and work by every collaborator.

5.1 Revert

For almost every accidental push of ordinary code, revert is the right answer. It works on protected branches, is a normal fast-forward push, and leaves an audit trail.

$ git switch main && git pull --ff-only
$ git revert --no-edit a28ccef
[main 1fda8fa] Revert "Bad change"
 1 file changed, 1 deletion(-)
$ git push origin main

On a branch where main only changes through pull requests, push the revert to a new branch and open a pull request instead. If the unwanted change arrived through a merged pull request, GitHub can do this for you: the Revert button on a merged pull request creates a new pull request that reverts the original merge commit; it requires write permission, and you may need to revert individual commits on the command line instead if the revert conflicts or the original pull request was not merged on GitHub [21].

Pushed to the wrong branch. If commits meant for feature/login went to GitHub's main, preserve them on the correct branch first, then revert them on main:

$ git branch feature/login main     # or cherry-pick them onto an existing branch
$ git push -u origin feature/login
$ git revert --no-edit HEAD~1..HEAD  # reverse the two commits on main
$ git push origin main

Be aware of one consequence when the feature branch is later merged back: if you reverted a merge, Git treats the merged commits as already present (section 6.3). The same reasoning applies when you reverted ordinary commits whose originals are later merged again, since those commits are already in main's history (an inference from the merge behaviour described in [22]); the clean way to reintroduce them is to revert the revert, or to rebase the feature branch so it carries new copies of the commits [22].

5.2 Coordinated history rewriting

Sometimes the commit must actually leave the branch history: a large binary bloating every clone, or a branch that you, alone, pushed and want to tidy before review. Rewriting published history means replacing the remote branch with commits that are not descendants of its current tip, which git push refuses by default because a non-fast-forward update loses history [12].

Secrets are a special case. If the pushed data is a password, token or other credential, GitHub's first instruction is to revoke or rotate it; that may solve the problem without rewriting history at all [20]. A rewrite does not remove the data from forks or from clones others already have [20].

Force-pushing safely

git push --force disables the fast-forward check and can cause the remote repository to lose commits [12], including commits a colleague pushed after your last fetch. Prefer --force-with-lease, which refuses to overwrite the remote branch unless it still points where your remote-tracking branch says it does [12]:

$ git push --force-with-lease origin feature/login

Here is the lease protecting a teammate's commit. A teammate pushed to main; you then amended and force-pushed without fetching:

$ git commit --amend -m "Revert bad change (amended)"
$ git push --force-with-lease origin main
 ! [rejected]        main -> main (stale info)
error: failed to push some refs to 'github.com:acme/webapp.git'

Two caveats from the git-push manual. First, the lease compares against your remote-tracking branch, so anything that fetches in the background (an IDE, a cron job) silently renews it and defeats the protection; the manual suggests giving an explicit expected value, --force-with-lease=main:<expected-hash>, in that situation [12]. Second, --force-if-includes, used together with --force-with-lease, additionally checks that the remote tip you are about to overwrite is reachable from your branch's reflog, that is, that you actually integrated it locally [12]:

$ git push --force-with-lease --force-if-includes origin feature/login

Also avoid bare --force when several refs are pushed at once: it applies to all of them. Prefix a single refspec with + to force only that ref [12].

GitHub branch protection

By default, GitHub blocks force pushes on all protected branches, and protected branches cannot be deleted [23]. An administrator can enable Allow force pushes for everyone with write access or for specific people or teams; this does not bypass other rules, so a force-pushed merge commit is still rejected if linear history is required [23]. A rewrite of a protected branch therefore usually starts with an administrator temporarily granting the right and ends with revoking it.

A coordination protocol

  1. Announce and freeze. Tell everyone with a clone which branch is being rewritten, and ask them to push pending work and stop pushing to it. GitHub itself calls rebasing already-pushed commits bad practice because changing history "can make things difficult for everyone else using the repository" [24].
  2. Back up. git branch backup/main-before-rewrite origin/main and push that branch, so the old history is recoverable from GitHub.
  3. Rewrite locally. git reset, git commit --amend or git rebase -i for recent commits; for removing a file from all of history, GitHub recommends git-filter-repo [20].
  4. Lift protection if needed, push with a lease, restore protection. git push --force-with-lease origin main [12,23].
  5. Repair every clone. Collaborators must either re-clone or carefully clean their clones, rebasing rather than merging any branches built on the old history; merging would bring the old commits straight back [20]. The git-rebase manual describes this repair from the downstream side. If the rewritten commits have the same content, a plain git rebase origin/main on each topic branch suffices because rebase skips changes already present upstream; otherwise, transplant only your own commits with git rebase --onto origin/main <old-base> <topic> [17].
  6. For sensitive data, contact GitHub Support to remove cached views and references from pull requests, and chase forks separately [20].

A collaborator with no local work on the branch can repair it in one step: git fetch origin then git reset --hard origin/main (section 7.3).

6. Merge problems

When Git cannot reconcile two sets of changes automatically, a merge stops part-way. At that point HEAD is unchanged, MERGE_HEAD points to the other branch's tip, cleanly merged paths are already updated in the index and working tree, and each conflicted path has up to three versions in the index: stage 1 from the common ancestor, stage 2 from HEAD, stage 3 from MERGE_HEAD [25]. GitHub Docs summarises the usual cause: competing changes to the same lines of a file, or one side editing a file the other side deleted [26].

$ git merge feature
Auto-merging app.txt
CONFLICT (content): Merge conflict in app.txt
Automatic merge failed; fix conflicts and then commit the result.
$ git status --short
UU app.txt
$ git ls-files -u
100644 a92d664... 1	app.txt
100644 c304eca... 2	app.txt
100644 a84fb5b... 3	app.txt

Prevention matters here. Git refuses to start a merge if uncommitted changes overlap with files it needs to update, or if anything is staged, and the manual recommends committing or stashing first so your own work cannot be clobbered [25]. Pro Git gives the same advice [22].

6.1 Abort

$ git merge --abort

--abort tries to reconstruct the pre-merge state [25]. It is equivalent to git reset --merge when MERGE_HEAD is present (the exception being an autostash, which --abort reapplies) [25]. If uncommitted changes were present when the merge started, --abort may be unable to reconstruct them, which is one more reason to start merges from a clean tree [25]. Two related escapes: git merge --quit forgets the merge but leaves the index and working tree as they are [25], and if a merge or pull has already completed and you regret it, git reset --hard ORIG_HEAD returns the branch to its pre-merge tip, because merge and pull always record it there [16]. After a merge has been pushed, use a revert instead (section 6.3).

6.2 Conflict resolution

Read the markers. In the default style, the text between <<<<<<< and ======= is your side (HEAD), and the text between ======= and >>>>>>> is the other branch [25,26]:

line 1
<<<<<<< HEAD
line 2 (main)
=======
line 2 (feature)
>>>>>>> feature
line 3

Show the common ancestor. Knowing what the line looked like before either side changed it is often decisive. The diff3 conflict style adds a ||||||| section with the original text; zdiff3 is similar but trims lines that match on both sides from the edges of the conflict [25]. Set it once with git config --global merge.conflictStyle zdiff3, or re-create the markers for one file with git checkout --conflict=diff3 <file> [22]:

line 1
<<<<<<< HEAD
line 2 (main)
||||||| e3d7efb
line 2
=======
line 2 (feature)
>>>>>>> feature
line 3

Inspect each side. Useful commands while the merge is stopped [25]:

  • git diff shows a three-way diff against both HEAD and MERGE_HEAD; git diff AUTO_MERGE shows the resolutions you have made so far.
  • git log --merge -p <path> shows the commits on each side that touched the path.
  • git show :1:<path>, :2: and :3: print the ancestor, ours and theirs versions from the index stages.
  • git mergetool opens a configured graphical merge tool.

Resolve. Edit each file into its final form and delete the markers, or take one whole side with git checkout --ours <file> or --theirs [22]. For a modify/delete conflict, keep the file with git add or accept the deletion with git rm [26]. Then mark the file resolved by staging it, and conclude with git commit or git merge --continue, which first checks that a merge is in progress [25]:

$ $EDITOR app.txt
$ git add app.txt
$ git merge --continue
$ git push origin main

Merge-wide strategies. -Xours or -Xtheirs resolve every conflicting hunk in favour of one side while still merging non-conflicting changes; whitespace-only conflicts can be avoided with -Xignore-space-change or -Xignore-all-space [22]. Do not confuse -Xours with the -s ours strategy, which records a merge but keeps your tree unchanged, discarding the other branch's changes entirely [22].

Repeated conflicts. If you resolve the same conflicts over and over on long-lived branches, enable rerere ("reuse recorded resolution") with git config rerere.enabled true [27].

On GitHub. Merge conflicts block merging a pull request until they are resolved [28]. Simple competing-line conflicts can often be resolved in GitHub's web editor; more complex ones must be resolved in a local clone and pushed back to the pull request's branch [28]. Locally that means: fetch, merge the base branch (for example origin/main) into the pull request's branch, resolve as above, and push the branch.

6.3 Undoing a pushed merge

A merge commit has two parents, so git revert needs to be told which one is the mainline: git revert -m 1 <merge> keeps parent 1, the branch you were on [19,22]. Reverting a merge declares that you will never want the tree changes it brought in; later merges of the same branch only bring in commits that are not ancestors of the reverted merge [19]. To bring the work back later, revert the revert first and then merge again [22].

7. Rebase problems

A rebase replays your commits, one at a time, on top of a new base, producing new commits that are similar to the originals but different [17,29]. Each replayed commit can conflict. When one does, the rebase pauses and you have three ways forward: resolve and continue, skip the commit, or abort [17,30].

$ git switch feature
$ git rebase main
Rebasing (1/2)Auto-merging app.txt
CONFLICT (content): Merge conflict in app.txt
error: could not apply ca715ed... Feature edit
hint: Resolve all conflicts manually, mark them as resolved with
hint: "git add/rm <conflicted_files>", then run "git rebase --continue".
hint: You can instead skip this commit: run "git rebase --skip".
hint: To abort and get back to the state before "git rebase", run "git rebase --abort".
$ git status
interactive rebase in progress; onto 8d2c836
Last command done (1 command done):
   pick ca715ed Feature edit
Next command to do (1 remaining command):
   pick f87bcce Feature second
...

"Ours" and "theirs" are swapped during a rebase. Because rebase replays your branch's commits on top of the upstream, the side reported as ours is the rebased series so far, starting from the upstream, and theirs is your working branch [17]. So during git rebase main, git checkout --theirs file picks your feature branch's version. The commit being replayed is recorded in REBASE_HEAD [4].

7.1 Abort

$ git rebase --abort

Aborts the operation and resets HEAD to the original branch, as it was when the rebase started [17]; GitHub Docs describes this as completely undoing the rebase [30]. A gentler variant, git rebase --quit, stops the rebase but leaves HEAD, the index and the working tree where they are [17].

After a rebase has finished, --abort no longer applies. The previous branch tip is still in the branch's reflog as @{1}; ORIG_HEAD is also set at the start of a rebase, but other commands used during the rebase can overwrite it, so the reflog is the reliable route [17]:

$ git reset --hard feature@{1}    # check with: git log -g feature

7.2 Continue

Resolve the conflict exactly as for a merge, stage the result, and continue [17,30]:

$ $EDITOR app.txt
$ git add app.txt
$ git rebase --continue
[detached HEAD 83a39d4] Feature edit
 1 file changed, 1 insertion(+), 1 deletion(-)
Successfully rebased and updated refs/heads/feature.

--continue restarts the rebasing process after a conflict has been resolved [17]; Git may open an editor for the commit message. The next commit may conflict in turn; repeat until the rebase reports success. If the branch was already on GitHub, the rebased branch has new commits and must be force-pushed, with a lease (section 5.2), which is acceptable on your own feature branch and a problem on a shared one [29].

7.3 Skip

$ git rebase --skip

--skip restarts the rebase by skipping the current patch [17]: none of the changes introduced by the problematic commit are included [30]. That is correct when the commit is redundant, for example when the same change already landed upstream through another route. Rebase normally drops commits whose changes are already present upstream on its own [17], but a change that was edited on the way in no longer matches and shows up as a conflict instead. Skipping a commit whose changes you actually need silently loses work; if you skip by mistake, abort and start over, or recover the old tip from the reflog afterwards. In the reproduction behind this article, skipping the first commit left the branch with only the second (Feature second) replayed onto main (observed).

8. Diverged branches

Your branch and its upstream have diverged when each has commits the other lacks: you committed locally while someone else pushed to the same branch on GitHub [10]. git status reports it after a fetch, and a push is rejected because it would not be a fast-forward [12,31]:

$ git fetch
$ git status
On branch main
Your branch and 'origin/main' have diverged,
and have 1 and 2 different commits each, respectively.
$ git push origin main
 ! [rejected]        main -> main (non-fast-forward)
error: failed to push some refs to 'https://github.com/USERNAME/REPOSITORY.git'

See exactly what differs before choosing a remedy. main...origin/main is the symmetric difference, the commits reachable from either side but not both [4]:

$ git log --oneline --left-right --graph main...origin/main

A plain git pull will not choose for you. Current Git documentation states that --ff-only is the default when no reconciliation method is configured, so the pull fails when local history has diverged [11]. Git 2.43 prints:

$ git pull
hint: You have divergent branches and need to specify how to reconcile them.
hint:   git config pull.rebase false  # merge
hint:   git config pull.rebase true   # rebase
hint:   git config pull.ff only       # fast-forward only
...
fatal: Need to specify how to reconcile divergent branches.

There are three answers, below. Choose per situation, or set pull.rebase or pull.ff to make one of them the default [11].

8.1 Merge

$ git pull --no-rebase origin main    # = git fetch + git merge origin/main
$ git push origin main

--no-rebase makes pull run git merge [11]; GitHub's guidance for a rejected non-fast-forward push is exactly this fetch-and-merge [31]. It never rewrites anything, so it is always safe on shared branches. The cost is a merge commit in history. Conflicts are handled as in section 6.

8.2 Rebase

$ git pull --rebase origin main       # = git fetch + git rebase origin/main
$ git push origin main

--rebase replays your unpushed local commits on top of the fetched upstream [11,29], giving linear history without a merge commit. The push that follows is a fast-forward, because only commits that existed solely in your clone were rewritten. The git-pull manual nevertheless calls this mode potentially dangerous because it rewrites history, and warns against using it on history you have already published [11]. Pro Git's rule is the same: do not rebase commits that exist outside your repository and that people may have based work on [29]. Conflicts are handled as in section 7.

8.3 Reset

When your local commits are not wanted (an experiment, or a branch that someone else deliberately rewrote on GitHub), make your branch identical to GitHub's:

$ git fetch origin
$ git branch backup/main-local        # optional, but cheap
$ git reset --hard origin/main

This discards your divergent commits from the branch and overwrites the working tree [16]. The backup branch, or the reflog entry main@{1}, keeps them recoverable [4]. Make sure to fetch first: origin/main only reflects GitHub as of your last communication with it [10].

The opposite reset, making GitHub match your local branch, is a force push, and belongs in section 5.2.
