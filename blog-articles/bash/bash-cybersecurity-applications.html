Bash for Defensive Cybersecurity: Auditing, Detection, Hardening and Secure Scripting

Published 16 November 2026 · Reading time about 75 minutes · 87 references (Vancouver style)

Abstract

The Bourne-Again Shell (Bash) is installed on almost every Linux server and is the default glue language of system administration. This article shows how defenders can use it to inventory their own hosts, analyse logs, monitor file integrity, audit permissions, accounts, processes, network exposure, SSH and firewall configuration, automate authorised vulnerability scanning, collect incident-response evidence and support static malware triage. The second half turns the lens on Bash itself: handling secrets, temporary files, privilege boundaries, command injection and untrusted input safely. Each of the eighteen topics comes with working source code, an explanation grounded in primary sources (NIST, CIS, MITRE CWE and ATT&CK, OWASP, IETF RFCs and the upstream manuals), and an exercise with a worked solution.

Scope, ethics and test environment

Bash is the GNU Project's shell: a command interpreter compatible with the POSIX shell plus many extensions such as arrays, [[ ]] tests and process substitution [1,2]. The same ubiquity that makes it valuable to administrators makes it attractive to intruders, which is why MITRE ATT&CK tracks the Unix shell as an execution technique in its own right [3]. Everything in this article is written for defenders: the scripts observe and report, they do not exploit. Run them only on systems you own or are explicitly authorised to assess. NIST's guide to security testing stresses that even passive assessment needs documented authorisation and rules of engagement, because scanning and probing can disrupt services and may be unlawful without permission [4].

The examples were written for and checked with Bash 5.2, GNU coreutils, findutils, util-linux, procps and iproute2 on Debian/Ubuntu and RHEL-family systems. Paths differ between families (for example /var/log/auth.log on Debian versus /var/log/secure on RHEL), and the scripts note where. Every listing passes bash -n, the safe listings pass ShellCheck with no warnings [5], and the runnable examples were executed on a test system. Deliberately unsafe "before" examples are outlined in red and labelled; never copy them.

1. Foundations: a defensive script template

A security script runs with elevated privileges, processes hostile data and is trusted to tell the truth. Small shell defaults matter. The template below is used, in whole or in part, throughout the article.

Why each line is there:

  • set -Eeuo pipefail. -e exits when a command fails, -u treats unset variables as errors, -o pipefail makes a pipeline fail if any stage fails, and -E lets the ERR trap fire inside functions. The Bash manual lists important exceptions: -e is ignored in conditions of if/while, in any command of an &&/|| list except the last, and in commands negated with ! [1]. Treat -e as a safety net, not as error handling; audit scripts that must keep going after a failed check deliberately omit -e and check status explicitly.
  • Quoting and IFS. Unquoted expansions undergo word splitting on the characters in IFS and then pathname (glob) expansion [1,2]. A filename containing a space or * can otherwise turn into several arguments. Always write "$var" and "${array[@]}".
  • Absolute interpreter and fixed PATH. #!/usr/bin/env bash is portable, but it resolves bash through the caller's PATH. For scripts run by root or from cron, use #!/bin/bash and reset PATH, otherwise a writable directory early in the search path lets someone substitute their own program (CWE-426, Untrusted Search Path) [6].
  • LC_ALL=C. Bracket ranges such as [a-z] and the sort order of sort depend on the locale's collation sequence [1,7]. Security tooling should give the same answer on every host.
  • ShellCheck. Static analysis catches unquoted expansions, unsafe read, useless cat and dozens of subtler bugs before they reach production [5]. Run shellcheck -x script.sh in CI.

2. System reconnaissance

Attackers run discovery commands (uname, id, ss, package listings) almost immediately after gaining access; ATT&CK catalogues this as System Information Discovery [8]. Defenders benefit from running exactly the same commands first, on a schedule, to build the authoritative inventory and baseline configuration that NIST SP 800-53 requires under controls CM-2 (Baseline Configuration) and CM-8 (System Component Inventory) [9]. A baseline turns "is this normal?" into a diff.

3. Log analysis

NIST SP 800-92 describes log management as the generation, transmission, storage, analysis and disposal of log data, and identifies routine analysis as the step most organisations neglect [12]. Bash, together with grep, awk, sort and uniq, is ideal for quick, repeatable analysis on the host or on exported logs. On systemd hosts, journalctl reads the binary journal and can filter by unit, priority and time window [13].

Silence is itself a signal. 4. File integrity monitoring

File integrity monitoring (FIM) detects unauthorised changes to binaries and configuration by comparing cryptographic hashes and metadata against a trusted baseline. It is required by NIST SP 800-53 control SI-7 (Software, Firmware, and Information Integrity) [9], and CIS Benchmarks for Linux recommend installing a dedicated tool such as AIDE and scheduling regular checks [19,20]. The script below is a compact, transparent FIM that is useful for learning, for minimal containers and for spot checks; production estates should still use a maintained tool.

Design notes:

  • find -print0 with read -r -d '' handles every legal filename, including ones containing spaces, tabs or newlines [1,21]. Paths are stored with printf %q so a newline in a name cannot forge an extra record.
  • The file is hashed through standard input (sha256sum < "$f") because GNU sha256sum escapes names containing backslashes or newlines in its output, which would otherwise corrupt the first field [7].
  • -xdev keeps the walk on one filesystem, avoiding /proc and network mounts.
  • The .sha256 sidecar only detects accidental corruption or a careless attacker. Anyone with root on the host can rewrite both files, so store the baseline off-host or on read-only media, or sign it (section 14). This is the same reason AIDE documentation recommends keeping the database on read-only storage [20].

5. Permission auditing

Overly permissive modes on sensitive files are a weakness class of their own (CWE-732, Incorrect Permission Assignment for Critical Resource) [22]. CIS Benchmarks for Linux contain a section of filesystem checks: no world-writable files, the sticky bit on world-writable directories, no unowned files, a reviewed list of SUID/SGID programs, and specific maximum modes for /etc/passwd, /etc/shadow and friends [19]. All of these are expressible with GNU find predicates such as -perm -0002 ("all of these bits set"), -nouser and -nogroup [21].

The mode test uses Bash arithmetic in base 8 (8#644) and a bit mask: mode & ~max is non-zero exactly when the file has a permission bit that the policy does not allow [1]. Unlike a string comparison, this accepts stricter modes (for example /etc/shadow at 000, the RHEL default) and rejects looser ones. The maxima shown follow the CIS Linux benchmarks; check the benchmark for your distribution because some values differ [19].

6. User and process auditing

Creating a local account (ATT&CK T1136) and appending a public key to authorized_keys (T1098.004) are two of the most common ways intruders keep access [24,25]. Running processes can also betray an intrusion: malware often runs from /tmp or /dev/shm, or deletes its binary after starting. Linux exposes each process's executable as the symbolic link /proc/PID/exe, and when the file has been unlinked the link target ends in " (deleted)" [26].

The second field of /etc/shadow holds the password hash; an empty field means no password is required, while ! or * means password login is locked [27]. Interpret the process check with care: after a package upgrade, long-running daemons legitimately keep running a "(deleted)" copy of the old binary until restarted. That is still worth knowing, because the process is running unpatched code.

7. Network diagnostics

Every listening socket is attack surface. NIST's server security guide recommends removing or disabling unnecessary services and network protocols, and documenting the ones that remain [28]. ss from iproute2 reports sockets with their owning processes (-p) without resolving names (-n) [29]. Comparing the live list with an approved list turns that guidance into an automated control.

The fifth column of ss output is the local address:port; splitting on : and taking the last element works for IPv4 (0.0.0.0:22), IPv6 ([::]:22) and wildcard (*:22) forms. comm requires both inputs to be sorted in the same collation order, which is why the script fixes LC_ALL=C [7]. A "MISSING" line is informational (an approved service is down); an "UNEXPECTED" line makes the script fail so that it can gate a deployment or raise a monitoring alert.

Reachability and TLS checks without extra tools

Bash can open TCP connections itself through the special path /dev/tcp/HOST/PORT in a redirection [1]. Combined with timeout from coreutils [7], that gives a dependency-free port probe for your own services. For TLS endpoints, openssl s_client fetches the certificate and openssl x509 -checkend tests whether it expires within a given number of seconds [30,31].

8. Security configuration checks

Configuration benchmarks such as the CIS Benchmarks express hardening guidance as testable rules with expected values [19], and NIST SP 800-123 recommends that server operating systems be hardened and their configuration verified regularly [28]. Many Linux rules are kernel parameters. Their meanings are defined in the kernel documentation: for example net.ipv4.conf.all.accept_redirects=0 ignores ICMP redirects that could reroute traffic, rp_filter=1 enables strict reverse-path filtering against spoofed source addresses, tcp_syncookies=1 mitigates SYN floods, and fs.suid_dumpable=0 prevents set-user-ID programs from dumping core files that might contain secrets [11,32]. A data-driven checker keeps the policy separate from the code.

Two Bash details are worth noticing. First, ((++pass)) is used rather than ((pass++)): an arithmetic command returns status 1 when its value is zero, and the post-increment's value is the old value, 0, which would abort a script running under set -e [1]. Second, a quoted here-document delimiter (<<'EOF') disables expansion inside the policy table, so a stray $ in a comment cannot execute anything. Routers and container hosts legitimately set ip_forward=1; policies should be per role, not global.

Bash rarely is the scanner, but it is the natural way to schedule scanners, enforce scope, keep history and detect change. NIST SP 800-40 Rev. 4 frames patching as routine preventive maintenance and recommends tracking the remediation status of every asset [33]; SP 800-115 describes network discovery and vulnerability scanning as core assessment techniques that must stay inside an authorised scope [4].

10. Incident response scripts

NIST SP 800-61 Rev. 3 places incident response within the NIST Cybersecurity Framework 2.0 functions, emphasising preparation (having tools and procedures ready before an incident) as well as detection, response and recovery [38]. For evidence collection, SP 800-86 and RFC 3227 both say to collect the most volatile data first (memory, network connections, running processes) before slower, more persistent sources, to minimise changes to the system, and to document every action [39,40]. A pre-written, tested collection script is preparation in concrete form.

Trust caveat. On a compromised host, ps, ss and even the kernel may lie (rootkits). RFC 3227 recommends running collection tools from read-only, trusted media rather than the suspect system's own binaries [40]. Capture memory with a dedicated tool before running anything else if memory forensics may be needed, and follow your organisation's chain-of-custody procedure.

The inline bash -c '...' programs are single-quoted literals with no interpolated data, which is the safe way to use bash -c (contrast section 18). The cron and systemd locations are collected because they are the most common Linux persistence mechanisms in ATT&CK (T1053.003 and T1543.002) [41,42]. Recording the final SHA256SUMS hash in the incident ticket ties the evidence set to a point in time.

11. Malware analysis support

NIST SP 800-83 Rev. 1 recommends that incident handlers be able to identify malware characteristics and indicators in order to contain and eradicate it [43]. Bash is useful for the first, static step: identify, hash, extract indicators and match signatures without ever executing the sample. Do this inside an isolated analysis VM with no route to production, store samples in a directory mounted noexec, and keep them in password-protected archives when moving them.

Notes on the tools: file identifies formats by magic numbers; readelf parses ELF headers and the dynamic section, where an unexpected RPATH/RUNPATH can indicate library hijacking; and strings -a scans the whole file rather than only selected sections [44]. Defanging URLs (hxxp, [.]) prevents accidental clicks when indicators are pasted into tickets. YARA rules describe malware families as textual or binary patterns with boolean conditions; -s prints the matching strings [45]. MD5 and SHA-1 are printed only because threat-intelligence feeds still index them; they are not collision-resistant (see section 14).

Exercise 11: entropy as a packing indicator

12. SSH security automation

NIST IR 7966 observes that SSH keys frequently outnumber user accounts, are rarely rotated and are often unmanaged, and it recommends inventorying keys and authorised access, enforcing configuration and removing unused keys [48]. Two Bash-friendly primitives make this possible: sshd -T, which prints the daemon's effective configuration after all includes and defaults are applied [49], and ssh-keygen -l, which prints the size, fingerprint and type of public keys [23].

The keywords and their meanings come from sshd_config(5) [50]; the target values mirror the SSH section of the CIS Linux benchmarks, which, for instance, recommend MaxAuthTries of 4 or less and LogLevel VERBOSE or INFO [19]. ${have,,} lowercases the value, because sshd -T prints some values in upper case. Note the use of an associative array (declare -A) whose keys are sorted for stable output. If you use Match blocks, run sshd -T -C user=alice,host=...,addr=... to see the settings that apply to a specific connection [49].

Auditing authorized_keys

The thresholds follow two sources: OpenSSH has deprecated and then removed DSA keys (disabled by default in 9.8, support removed in 10.0) [15], and NIST SP 800-57 Part 1 equates 2048-bit RSA with 112-bit security and 3072-bit RSA with 128-bit security, with 112-bit strength acceptable only through 2030 [51]. Options such as from="10.0.0.0/8", command= and restrict limit what a stolen key can do; they are documented in the AUTHORIZED_KEYS FILE FORMAT section of sshd(8) [49].

13. Firewall rule auditing

NIST SP 800-41 Rev. 1 recommends a default-deny policy for inbound traffic, rule sets that permit only what is required, and periodic review of rules to remove those that are no longer needed [54]. On modern Linux the packet filter is nftables, whose nft list ruleset prints the whole active configuration and whose -s (stateless) option omits counters so output is stable enough to compare [55]. Legacy hosts expose the same information through iptables-save [56].

In nftables a base chain without an explicit policy statement defaults to accept [55], which is why the script flags anything other than policy drop. "Review" findings are not necessarily wrong (a public web server must accept port 443 from anyone), but each should map to a documented business need, as SP 800-41 recommends [54].

14. Hashing and checksum verification

A cryptographic hash maps data of any length to a fixed-length digest such that finding two inputs with the same digest (a collision) or an input matching a given digest should be infeasible. The approved functions are the SHA-2 family in FIPS 180-4 and SHA-3 in FIPS 202 [57,58]. MD5 and SHA-1 no longer meet that bar: practical MD5 collisions were published in 2005 and the first full SHA-1 collision in 2017 [59,60], and NIST disallows SHA-1 for generating digital signatures [61]. Use SHA-256 or stronger (sha256sum, sha512sum, or b2sum for BLAKE2 in GNU coreutils) [7].

Equally important: a checksum only proves integrity relative to the checksum you trust. A hash published on the same server as the download protects against corruption, not against an attacker who controls the server. Authenticity requires a signed checksum manifest verified against a key fingerprint obtained independently.

GnuPG's machine-readable --status-fd interface emits a VALIDSIG line whose first argument is the fingerprint of the signing key and whose last argument is the primary key's fingerprint [62]. Checking for that line with the expected fingerprint is more robust than parsing the human-readable "Good signature" text, which is localised and does not say which key signed. The manifest lookup accepts both GNU's text-mode (hash␠␠name) and binary-mode (hash␠*name) entries [7].

15. Secret handling

Scripts need passwords, API tokens and keys, and shell scripts leak them in characteristic ways. The relevant weaknesses are hard-coded credentials (CWE-798), secrets visible in a process's arguments (CWE-214) and secrets written to logs (CWE-532) [63–65]. OWASP's secrets-management guidance is to keep secrets out of source code, deliver them at run time from a dedicated store, scope and rotate them, and audit their use [66].

Finding secrets that have already leaked

16. Secure temporary file management

Predictable names in shared directories such as /tmp are a classic local attack (CWE-377, Insecure Temporary File). If a root script writes to /tmp/report.$$, another user can guess the name (process IDs are predictable) and pre-create it as a symbolic link to /etc/passwd; the script then overwrites the target with root's privileges (CWE-59, Link Following). Checking first with [[ -e ]] does not help, because the attacker can win the race between the check and the use (CWE-367, TOCTOU) [70–72].

mktemp replaces the trailing Xs with random characters and creates the file (mode 0600) or directory (mode 0700) atomically, failing if the name exists [7]. Putting all temporary files inside one private directory means a single rm -rf cleans everything, and nothing inside is reachable by other users. The EXIT trap runs on normal exit and, because the signal traps call exit, after HUP, INT and TERM as well [1]. set -o noclobber makes > fail rather than truncate an existing file [1].

The kernel adds defence in depth: with fs.protected_symlinks=1, symlinks in sticky world-writable directories are followed only if the follower owns the link or the link's owner matches the directory's owner, which defeats the attack above [11]. For services, systemd's PrivateTmp=yes gives each unit its own /tmp and /var/tmp [67]. Use all three layers; do not rely on any one.

Show solution

GNU mktemp creates files with permissions u+rw and directories with u+rwx, minus the umask's restrictions; it never adds group or other bits, so even umask 000 yields 600 and 700 [7]. Files your script later creates inside the directory do follow the umask, which is why the template sets umask 077.

17. Privilege escalation risks

Local privilege escalation usually exploits misconfiguration rather than a kernel bug: a set-user-ID program that can spawn a shell (ATT&CK T1548.001), an over-broad sudo rule (T1548.003), or a writable directory in a privileged process's PATH (T1574.007) [73–75]. The general weakness is running with more privilege than needed (CWE-250) [76]. Defenders should look for these conditions before an attacker does.

How Bash itself behaves around privilege

  • Linux ignores the set-user-ID and set-group-ID bits on interpreted scripts, so chmod u+s script.sh does not make a script run as its owner [77]. Use a narrowly scoped sudo rule instead.
  • If Bash starts with an effective user ID different from its real user ID and without -p, it does not read startup files, ignores SHELLOPTS, BASHOPTS, CDPATH and GLOBIGNORE from the environment, does not import functions, and resets the effective ID to the real ID [1]. Treat any use of bash -p in a privileged context as a red flag.
  • sudo by default resets the environment and can enforce a secure_path; rules containing NOPASSWD, wildcards, or editors and interpreters that can spawn a shell deserve review [78].

File capabilities split root's power into units such as cap_net_bind_service or cap_setuid; a capability like cap_setuid or cap_dac_override on an interpreter is equivalent to root [79]. A SUID file that no package owns was installed by hand, possibly by an intruder, and should be explained. The cron check looks for absolute paths in the command fields of root's system cron entries; for a production tool you would also parse user crontabs and handle @reboot-style schedules.

Exercise 17: hijackable parent directories

A root cron job running /opt/app/bin/rotate.sh is still exploitable if /opt/app is writable by others, because an attacker can rename bin and create their own. Write weak_chain PATH that checks the file and every ancestor directory up to /, printing each weak component.

Show solution

realpath -e resolves symlinks first, so the walk covers the directories that are actually traversed [7]. This mirrors the reasoning behind CWE-426: control over any directory on the lookup chain is control over what gets executed [6].

18. Command injection prevention

OS command injection (CWE-78) occurs when externally influenced data is placed into a command that a shell then parses, so that metacharacters such as ;, |, $( ) and backticks become code [80]. Argument injection (CWE-88) is the related case where data is passed as an argument but starts with - and is interpreted as an option [81]. OWASP's primary defence is to avoid invoking a shell with constructed strings at all, and otherwise to pass data as separate, validated arguments [82]. Bash makes the safe form natural: a quoted expansion is always one argument and is never re-parsed as shell syntax [1].

Notes: -- marks the end of options for utilities that follow the POSIX utility syntax guidelines, so a value such as -rf is treated as an operand [2]. ${var@Q} and printf %q produce a quoted form that Bash can re-read safely [1]; if the remote login shell is not Bash, prefer passing data on standard input instead. In find -exec sh -c '...' sh {}, the first argument after the script becomes $0 and the file name becomes $1, so the name is data, never code.

Two Bash-specific traps

Arithmetic evaluation. Inside (( )), $(( )), let, array subscripts and the numeric operators of [[ ]] (-eq, -lt, ...), Bash evaluates the operands as arithmetic expressions, and a variable whose value is a name is itself evaluated recursively [1]. Because an array subscript in such an expression is expanded, a value like a[$(cmd)] runs cmd. Always validate before doing arithmetic on untrusted input:

Function import and Shellshock. In 2014, CVE-2014-6271 ("Shellshock") showed that Bash executed trailing commands placed after function definitions in environment variables, so any service that copied request data into the environment of a Bash process (CGI scripts, DHCP clients) became remotely exploitable [83]. Patched Bash only imports functions from specially named variables, but the lesson stands: keep Bash patched, and never let untrusted data define the environment of a privileged shell.

Bugs: unquoted $dir splits and globs; parsing ls output breaks on spaces and newlines; the file name is interpolated into sh -c code, so a file called x;rm -rf ~ executes; and a name starting with - becomes an option to file.

19. Unsafe input handling

Improper input validation (CWE-20) underlies most of the weaknesses above [84]. OWASP recommends allow-list ("known good") validation of syntax and semantics, applied as early as possible, with canonicalisation before checking paths [85]. In Bash, "input" includes arguments, environment variables, file contents, file names, command output and network data.

Reading data correctly

Without -r, read interprets backslashes; without IFS= it strips leading and trailing whitespace [1]. Using untrusted data as a printf format lets it inject % directives, and echo's handling of options and escapes differs between shells, which is why POSIX recommends printf for portable output [2].

A small validation library

Each validator encodes a specific lesson:

  • Anchors in [[ =~ ]]. Bash matches against the whole string with POSIX extended regular expressions, where ^ and $ anchor to the start and end of the string [1,2]. grep, by contrast, is line-oriented, so grep -qE '^[0-9]+$' <<<"$v" accepts $'42\nrm -rf /' because one line matches. Validate with [[ =~ ]], not grep.
  • Length limits. {1,9} caps the input so arithmetic cannot overflow and absurd values are rejected early, in line with OWASP's advice to check length as well as characters [85].
  • Leading zeros. Bash arithmetic treats 010 as octal and 08 as an error; 10# forces base 10 [1].
  • Path traversal. A user-supplied name such as ../../etc/shadow must be canonicalised and then checked to remain inside the intended directory (CWE-22) [86]. realpath -m resolves .. and symlinks without requiring the final component to exist [7]. The check is still subject to races if an attacker can change the directory tree between check and use (CWE-367) [72].
  • Log injection. If a user name contains a newline, writing it to a log can forge an extra, convincing entry; ANSI escape sequences can also hide text in terminals. Neutralise control characters before logging (CWE-117) [18,87].

Show solution

The regular expression enforces the syntax, so free-form strings like tomorrow never reach date. GNU date then checks semantics: it rejects 30 February outright, and the round-trip comparison catches any input it would normalise differently [7].
