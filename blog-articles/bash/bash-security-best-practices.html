1. Why shell scripts are a security surface

Shell scripts glue together programs, files and user input, and they often run with more privilege than the people who feed them data: from cron, CI pipelines, web hooks, installers and sudo rules. The shell's own design makes mistakes easy. Unquoted expansions are split into words and treated as glob patterns[1,2], strings can be re-parsed as code by eval[3], and any argument starting with a dash may be read as an option[4]. These behaviours are the shell-level forms of well-catalogued weaknesses: OS command injection (CWE-78)[5], argument injection (CWE-88)[6], eval injection (CWE-95)[7], and the symlink and race-condition attacks on temporary files (CWE-59, CWE-367)[8,9].

Bash itself has also carried serious flaws. The 2014 "Shellshock" bug (CVE-2014-6271) let attackers run commands through crafted environment variables that Bash imported as function definitions[10]. Keeping Bash patched is the first line of defence. The rest of this article covers the second line, which is writing scripts that do not open holes of their own.

Two habits run through every section below. Treat every value that came from outside the script (arguments, environment variables, file contents, filenames, command output, network data) as untrusted until it has been checked, which is the principle behind OWASP's input-validation guidance[11]. And give each process only the access it needs, the "least privilege" principle described by Saltzer and Schroeder[12].

A note on "strict mode"

Many scripts start with set -euo pipefail. The options are useful: -u treats expanding an unset variable as an error, and pipefail makes a pipeline fail if any stage fails rather than only the last[13]. But -e has many documented exceptions. It does not fire inside an if or while condition, in any command of an && or || list except the last, or for a command negated with ![13]. Greg Wooledge's BashFAQ explains why relying on it for correctness leads to surprises[14]. Use these options as a safety net, and still check the exit status of commands that matter.

2. Quote variable expansions

When Bash expands $var, $(cmd) or $((expr)) outside double quotes, it scans the result for word splitting on the characters in IFS[1]. Each resulting word that contains *, ? or [ is then treated as a pattern and replaced with a sorted list of matching filenames[2]. Splitting and globbing happen after the other expansions, in a fixed order[15]. Inside double quotes, every character keeps its literal value except $, `, \ and, when history expansion is on, ![16]. So double quotes keep the expansion working while turning off splitting and globbing.

The same rule applies to command substitution and to lists. Use "$@" to pass all positional parameters through unchanged, and "${arr[@]}" for arrays. Both expand each element to a separate word, and they are the documented exceptions to the "quotes make one word" rule[15,17]. ShellCheck reports unquoted expansions as SC2086 and unquoted array expansions as SC2068[18,19].

There are a few places where quotes are optional because no splitting happens: the right side of a plain assignment (a=$b), and the word after case. Inside [[ … ]] the left side is not split either, but on the right of == or =~ an unquoted expansion is treated as a pattern, while a quoted part is matched literally[20]. When in doubt, quote. The Wooledge wiki's page on quoting is a good general reference[21].

Quoting also protects against a classic catastrophe: a variable that is empty when you expected a path. rm -rf "$dir/"* with an empty $dir becomes rm -rf /*. The ${var:?message} form makes a non-interactive shell print the message and exit when the variable is unset or empty[22], which is what ShellCheck suggests in SC2115[23].

3. Validate external input

Validate input against what you expect (an allow-list) rather than trying to strip out what you fear (a deny-list). OWASP's guidance is to define what the application accepts and reject everything else, instead of trying to recognise every malicious string[11]. In Bash the tools are case patterns and the [[ string =~ regex ]] operator[20]. Anchor the regex with ^ and $ so the whole value must match, and keep the regex in a variable so that its backslashes and brackets are not mangled by quoting.

Arithmetic is code too

In an arithmetic context, Bash evaluates the value of a variable as an arithmetic expression[24], and array subscripts inside that expression are expanded. So an unvalidated value can run commands when it is used in (( … )), $(( … )), let, or the numeric operators of [[ … ]] such as -eq and -gt. The following prints PWNED in Bash 5.2:

4. Avoid unnecessary eval

eval joins its arguments into a single string and runs that string as a shell command[3]. Any data in that string is parsed again as code, with quotes, semicolons, redirections and substitutions all active. This is CWE-95, eval injection[7]. The BashFAQ entry on eval warns that it is a common source of bugs and security holes and that most uses have safer replacements[25].

Most reasons people reach for eval have a direct, safe alternative in modern Bash:

GoalInstead of eval
Run a command stored in a variableStore it in an array and run "${cmd[@]}" (section 13)[26]
Read a variable whose name is in another variableIndirect expansion ${!name}, or a nameref declare -n ref=$name[22,27]
Assign to a variable whose name is dynamicprintf -v "$name" '%s' "$value"[27]
Map keys to valuesAn associative array: declare -A conf; conf[$key]=$value[17]
Build a string that a shell will parse laterQuote each piece with printf '%q'[27]

Even with indirection, check the name first. ${!name} and printf -v accept array subscripts such as a[$(cmd)], which brings back the arithmetic-expansion problem from section 3.

If eval is truly needed, for example to evaluate output that a trusted tool printed in shell syntax, make sure every piece of data inside the string was produced by printf '%q' or ${var@Q}, and the rest is a constant you wrote. ShellCheck flags the common anti-pattern of flattening an array into eval as SC2294[28].

5. Avoid unsafe command construction

Command injection happens whenever untrusted data is pasted into a string that a shell will parse. OWASP's first recommendation is to avoid calling out to a command interpreter with built strings at all, and otherwise to keep data separate from the command structure and validate it[29]. In shell terms, that means passing data as separate arguments, never as part of the command text.

The common places strings get re-parsed are sh -c or bash -c, eval, ssh remote commands, su -c, xargs without -0, and tools like find -exec sh -c.

In the second example the script given to sh -c is a fixed string in single quotes. The filenames arrive as $1, $2, … (the first word after the script, sh, becomes $0), so they are never parsed. The {} + form passes many names per invocation[30].

Remote commands over SSH

ssh does not pass an argument vector to the remote side. It appends any extra arguments to the command, separated by spaces, and sends that single string to the server, where the remote user's shell parses it[31]. Quote each piece for the remote shell with printf '%q' (or ${var@Q}), which produces output that can be reused as shell input[27]:

%q quotes for Bash. If the remote login shell is not Bash-compatible, prefer sending data on standard input or pass a fixed script with ssh host 'sh -s' < script.sh and validated arguments.

xargs

Without -0, xargs splits on blanks and newlines and interprets quotes and backslashes in its input, so filenames with spaces or quotes break or are misread. Pair find -print0 with xargs -0, both of which are now in POSIX.1-2024[32,33].

6. Use -- to terminate option parsing where supported

If a filename or user-supplied value starts with -, many commands read it as an option. A file named -rf in the current directory turns rm * into rm -rf …. This is argument injection, CWE-88[6]. POSIX Utility Syntax Guideline 10 says the first -- argument that is not an option-argument should be accepted as a delimiter marking the end of options[4]. GNU tools follow it: later arguments are treated as operands even if they begin with -[34].

ShellCheck's SC2035 recommends ./*glob* or -- *glob* for exactly this reason[35].

Not every command supports --. The Bash echo builtin prints it literally (echo -- x prints -- x), and echo "$var" prints nothing at all when $var is -n. The POSIX specification notes that echo cannot be used portably for arbitrary data and encourages new applications to use printf instead[36]. Use printf '%s\n' "$var": the format string is fixed and the data is an argument, so it cannot be read as an option or a format. For commands that don't accept --, anchor the path with ./ or make it absolute.

7. Avoid predictable temporary filenames

Shared directories like /tmp are writable by every user. If a script writes to a name another user can guess, such as /tmp/myapp.log or /tmp/myapp.$$ (the PID is easy to guess or brute-force), an attacker can create that name first. A symbolic link there can redirect the script's write to any file the script's user can modify, which is how a root-run script ends up overwriting /etc/shadow. MITRE catalogues the weaknesses involved as CWE-59, improper link resolution before file access, and CWE-367, time-of-check time-of-use race condition[8,9]. BashFAQ 62 covers the shell side of the problem in detail[37].

Checking for the file first does not help, because the attacker can create it between the check and the write (a time-of-check to time-of-use race[9]). The fix is to create the file atomically, with a name nobody can predict, failing if it already exists. That is exactly what mktemp does.

If you must create a file at a fixed path, Bash's noclobber option (set -C) makes > fail when the target exists as a regular file[13,38]. That gives an atomic "create only if absent" for lock files, but it is no replacement for unpredictable names in shared directories.

8. Use mktemp

mktemp creates a file (or, with -d, a directory) with a unique random name built from a template ending in XXX…, and prints the name[39]. GNU mktemp creates files with u+rw and directories with u+rwx, minus umask restrictions, so the result is private to the owner[39]. The underlying C functions mkstemp and mkdtemp, which POSIX specifies, likewise create the file exclusively (as if with O_EXCL) with owner read and write permission, and the directory with owner-only access[40]. mktemp as a command is not in POSIX, but it is available on Linux, the BSDs and macOS.

Some practical points:

  • Prefer one private directory from mktemp -d over many temporary files. Everything inside it is safe to name freely, and one rm -rf removes it all.
  • Respect TMPDIR. GNU mktemp uses it with -t or -p/--tmpdir[39]; the explicit "${TMPDIR:-/tmp}/name.XXXXXXXXXX" template above works on GNU and BSD alike.
  • Use at least six Xs, more for long-lived files. The template's randomness is the only thing protecting the name.
  • Always check that mktemp succeeded. If it fails and you carry on with an empty variable, "$tmpdir/sorted" becomes /sorted.
  • Register cleanup immediately after creation (see section 15).

9. Set restrictive file permissions (umask)

The file mode creation mask, or umask, removes permission bits from every file and directory a process creates[41]. A common default, 022, makes new files world-readable. Setting the umask is supported both as a Bash builtin[3] and as a POSIX utility[42]. Creating a file with the default umask and tightening it with chmod afterwards leaves a window in which other users can open it, and once they hold an open descriptor, a later chmod does not take it back. CWE-732 and CWE-276 describe the result of getting this wrong[43].

The umask only affects newly created files. Overwriting an existing file with > keeps its old permissions, so for sensitive output write to a fresh file in a private directory and mv it into place. A rename within one filesystem replaces the target atomically, and readers never see a half-written file.

10. Protect credentials and secrets

Secrets leak from shell scripts in a handful of predictable ways. CWE-798 covers hard-coded credentials and CWE-214 covers secrets visible in a process's invocation[44,45]. OWASP's Secrets Management Cheat Sheet gives the broader organisational guidance[46].

  • Command-line arguments are public. On Linux, /proc/[pid]/cmdline holds the complete command line of a process[47]. Unless /proc is mounted with the hidepid option, every user may access every process's /proc/[pid] directory[48], which is how ps shows other users' commands. Never pass a password as an argument to an external program.
  • The environment is less exposed but still inherited. /proc/[pid]/environ is protected by a ptrace access check, so normally only the same user or root can read it[49]. But every child process inherits exported variables, and many tools log or dump their environment on errors. Don't export a secret unless the specific child needs it, and pass it only to that command: PGPASSWORD=$pw psql ….
  • Tracing prints everything. set -x prints each command and its arguments after expansion[13], secrets included, often into CI logs. Turn it off around sensitive code.
  • Source code and history. Hard-coded tokens end up in version control and backups. Load them at run time from a file with mode 0600, a secrets manager, or an injected file such as a CI secret.

The final pipeline works because curl -K reads options from a config file, and - means standard input[50]. The general pattern is: secrets travel through files with tight permissions, standard input, or a dedicated file descriptor, never through argv. To prompt for a secret interactively, use read -rs, where -s turns off echo[27].

11. Handle filenames containing whitespace and special characters

On POSIX systems, a filename may contain any byte except / and NUL. That includes spaces, tabs, newlines, glob characters, quotes, leading dashes and invalid UTF-8. David A. Wheeler's essay on Unix filenames documents how much breakage this causes, and why scripts must cope with it[51]. Tools like find separate names with newlines by default, which cannot represent a name containing a newline. find -print0 uses NUL instead, the one byte that cannot appear in a name[30].

Each part matters. IFS= stops read stripping leading and trailing whitespace. -r stops it treating backslashes as escapes[27], the problem ShellCheck reports as SC2162[52]. -d '' makes NUL the delimiter. And process substitution < <(…) keeps the loop in the current shell, so count survives after it, which a pipeline into while would not. BashFAQ 20 discusses these choices in depth[53].

To collect names into an array instead, use mapfile -d '' -t files < <(find … -print0) (Bash 4.4 and later). For files in a single directory, a glob is simpler and fully safe:

Without nullglob, a pattern that matches nothing is left unchanged, so the loop would run once with the literal string ./*.txt. With nullglob the word is removed[2]. Print names you don't control with printf '%q' or ${f@Q}, so that a name containing terminal escape sequences cannot rewrite your screen or your logs.

12. Avoid parsing ls output

ls is designed for people, not programs. Its output is newline-separated, may replace unprintable characters with ?, and its format varies between systems and locales. Parsing it breaks on the filenames described in section 11[54]. It is pitfall number one on the Wooledge BashPitfalls page[55], and ShellCheck flags it as SC2045 (iterating over ls) and SC2012 (use find instead of ls)[56,57].

In a test directory holding four files named a b, -dash, * and one containing a newline, this loop ran eleven times, because the * name was expanded to the contents of the current directory. Use the shell's own tools instead:

13. Prefer arrays for command arguments

A string variable cannot hold a list of arguments safely. If you store opts="--name 'My File'" and run cmd $opts, the quotes are not syntax any more. They are ordinary characters, and the value is split on spaces into --name, 'My and File'. BashFAQ 50 explains this in detail and recommends arrays or functions[26]. An array keeps each argument separate, and "${arr[@]}" expands to exactly those words[17].

The printf ' %q' line shows the exact command in a form you could paste back into a shell, which is far more honest than echoing a string. In POSIX sh, which has no arrays, the positional parameters are the one list you have: build them with set -- "$@" --dry-run and run cmd "$@" (see section 18).

14. Validate external commands and dependencies

A script depends on every program it calls, and on the PATH that finds them. If a script that runs with privilege searches a directory an attacker can write, the attacker can plant a program named ls or tar there. This is CWE-426, untrusted search path[58]. Defend in three ways:

  1. Set PATH explicitly at the top of scripts that run as another user or from cron, using only root-owned system directories. Never include . or an empty entry, which also means the current directory.
  2. Check dependencies up front with command -v, which POSIX specifies and which Bash implements as a builtin[27,59]. Unlike which, it is standard and reports functions, builtins and aliases correctly. Fail with a clear message before doing any work.
  3. Control the environment. In non-interactive mode, Bash reads the file named in BASH_ENV before running a script[60], and Bash can import functions from the environment, the mechanism abused by Shellshock[10]. For privileged helpers, start from a clean environment: env -i PATH=/usr/sbin:/usr/bin:/sbin:/bin /path/to/helper.

Validate the things you download, too. Check a downloaded file's checksum or signature before you execute or install it, and avoid piping a URL straight into a shell.

15. Handle signals and cleanup

Scripts get interrupted by Ctrl-C (SIGINT), by kill (SIGTERM), by a closed terminal (SIGHUP), or by an error under set -e. Without cleanup they leave behind temporary files that may hold sensitive data, stale lock files that block the next run, and half-written output. The trap builtin runs a command when the shell receives a signal, and a trap on EXIT runs when the shell exits[3]. The Wooledge SignalTrap page describes the conventions below[61].

Why the details matter:

  • Cleanup must be safe to run twice and before setup has finished. The signal trap runs cleanup, then the EXIT trap could run it again; and a signal may arrive before mktemp has assigned tmpdir. Initialising the variable first and testing it handles both.
  • Re-raising the signal tells the parent process the truth. A caller that sees a normal exit status may carry on as if the job had succeeded. In testing, sending SIGTERM to this script removed its directory and gave exit status 143 (128 + 15).
  • Traps wait for foreground commands. If Bash is waiting for a foreground command when a trapped signal arrives, the trap does not run until that command completes[62]. Running long work in the background and using wait, which returns as soon as a trapped signal arrives, keeps the script responsive.
  • Single-quote trap strings. The trap's command is evaluated when the signal arrives. With single quotes, trap 'rm -rf -- "$tmpdir"' EXIT expands the variable at that moment and quotes it correctly. With double quotes the value is pasted in when the trap is set and then parsed again as code, which breaks on names with spaces or quotes (ShellCheck SC2064). Calling a function, as on_signal does here, avoids the problem entirely.

To make sure only one copy of a script runs at a time, use flock (util-linux) on a lock file, or mkdir of a lock directory, which is atomic, rather than testing for a file's existence and then creating it.

16. Minimize privilege

The principle of least privilege holds that every program and user should operate with the least set of privileges needed for the job[12]. Running a whole script as root because one line needs it turns every bug in the other lines into a root bug. CWE-250 describes this weakness[63].

  • Elevate only the step that needs it. Run the script as an ordinary user and use sudo for the single command, with a sudoers rule that names the exact program and arguments. Keep env_reset and secure_path on: they give sudo'd commands a minimal environment and a fixed PATH[64].
  • Drop privilege when root is not needed. A root-run maintenance script can do its unprivileged work as a service account: sudo -u appuser -- "$helper" "$arg" or runuser -u appuser -- ….
  • Don't write set-user-ID shell scripts. Linux ignores the set-user-ID and set-group-ID bits on interpreted scripts[65], and on systems that honour them, scripts are notoriously hard to make safe. Bash by default resets the effective user ID to the real one when they differ, unless started with -p, and in privileged mode it skips BASH_ENV, ENV and imported functions[13]. Use a small compiled helper or a sudo rule instead.
  • Check who you are. Fail early if a script is (or isn't) running as root, rather than half-working.
  • Restricted shell is not a sandbox. rbash disables some features, such as changing directory or setting PATH[66], but it is easy to escape through any program that can run commands. Use OS mechanisms such as separate accounts, containers, or systemd sandboxing.

A matching sudoers line, edited with visudo, could be deploy ALL=(root) /usr/bin/install -m 0755 -- ./mytool /usr/local/bin/mytool, which permits that command and nothing else.

17. Use ShellCheck

ShellCheck is a static analysis tool that gives warnings and suggestions for Bash and sh scripts. Its stated goals are to point out beginner's syntax issues, intermediate-level semantic problems, and subtle caveats, corner cases and pitfalls[67]. Options let you follow sourced files (-x), choose the shell dialect (-s) and set a minimum severity (-S)[68]. 18. Follow POSIX portability requirements when needed

If a script will run under /bin/sh (on Debian and Ubuntu that is dash; on Alpine it is BusyBox ash), in a minimal container, or on several Unix systems, write to the POSIX Shell Command Language[71] and declare it with #!/bin/sh. If you rely on Bash features, say so with #!/usr/bin/env bash or #!/bin/bash. A mismatched shebang is a bug that often hides until the script reaches a different system.

Bash featurePOSIX sh alternative
Arrays arr=(…), "${arr[@]}"Positional parameters: set -- a "b c", "$@"[72]
[[ … ]], =~[ … ] with quoted operands; case for patterns
localNot in POSIX (though dash and BusyBox support it); use a subshell function body f() ( … )
echo -e, echo -nprintf[36]
read -d '', mapfilefind … -exec cmd {} + (read -d is in POSIX.1-2024, but older shells lack it)
<(…) process substitutionA named pipe from mkfifo in a mktemp -d directory, or a temporary file
$RANDOM, $EUIDid -u; for random names use mktemp
function f { … }f() { … }

The 2024 edition of POSIX (IEEE Std 1003.1-2024, Issue 8) standardised several features that used to be extensions, including $'…' quoting, find -print0, xargs -0 and read -d, where an empty delimiter means the null byte[32,33,71,73,74]. Older shells still in service may lack them, so check what your target systems actually ship.

Test portable scripts the way they will run: dash script.sh, busybox sh script.sh, and shellcheck -s sh, which reports Bash-only syntax as SC3xxx warnings[72]. Running Bash with --posix or set -o posix changes Bash's behaviour where it differs from the standard[75], but it does not disable Bash extensions, so it is not a portability test on its own.

21. Review checklist

  • Every expansion is double-quoted unless splitting is intended and commented.
  • All external input is validated against an allow-list before use, and before any arithmetic.
  • No eval, sh -c "…$var…", or SSH command built from unquoted data.
  • Option-taking commands get -- before operands; globs start with ./.
  • printf '%s\n' instead of echo for arbitrary data.
  • Temporary files and directories come from mktemp, and the result is checked.
  • umask 077 (or a subshell with it) wherever sensitive files are created.
  • No secrets in argv, source code, set -x output, or needlessly exported variables.
  • Filename loops use globs with nullglob, or find -print0 with read -r -d ''.
  • No parsing of ls output.
  • Argument lists are arrays (or "$@" in sh).
  • PATH set explicitly for privileged or scheduled scripts; dependencies checked with command -v.
  • trap … EXIT cleans up; signal handlers re-raise the signal.
  • The script runs with the least privilege it needs; sudo rules are narrow.
  • ShellCheck runs clean in CI; every directive has a comment.
  • The shebang matches the features used; portable scripts are tested with dash.
