Bash in practice

Testing and Quality Assurance for Bash

A working guide to linting, formatting, testing and reviewing shell scripts, and to running all of it in continuous integration. Every listing in this article was run before publication.

Tool versions used: GNU Bash 5.2.21 (suite also run under Bash 4.4, 5.0, 5.1 and 5.2 containers), ShellCheck 0.11.0, shfmt 3.14.1, Bats 1.13.0, bats-assert 2.2.4, bats-support 0.3.0, actionlint 1.7.12. Citations follow the Vancouver (NLM) style.[1] References accessed 16 November 2026.

1. Why test shell scripts

Shell scripts glue systems together: they deploy software, rotate logs, run backups and bootstrap machines. They are also unusually easy to get subtly wrong. An unquoted expansion is split into words and then expanded as a glob pattern,[2] so a file name with a space or an asterisk can turn one argument into several. The errexit option (set -e) is ignored in several contexts, including the condition of an if and any command in an && or || list except the last,[3] so a script that “stops on error” often does not. These problems rarely show up in a quick manual run, which is exactly why they need automated checks.

A sound quality process for Bash has layers, each catching a different class of defect:

The shape mirrors the familiar test pyramid: many small, fast tests at the bottom and fewer broad, slower tests at the top.[4] The rest of the article builds each layer around one small, realistic project.

2. The running example: logsum

logsum reads log files whose lines look like TIMESTAMP LEVEL message, counts lines per level and prints a sorted summary. With -n URL it also POSTs the summary to a webhook using curl. Its exit status is part of its contract: 0 when no ERROR lines were found, 1 when at least one was, 2 for usage errors and 3 when the notification failed. Having a documented exit-code contract is what makes a CLI testable.

The code is split into a library of pure functions and a thin executable. That split is the single most useful design decision for testability, because the library can be sourced and tested function by function while the executable is tested as a black box.

A few details matter for what follows. count_levels uses an associative array (local -A), a feature introduced in Bash 4.0,[5,6] so the project requires Bash 4 or later. set -euo pipefail is applied only in the executable; the library deliberately does not change the caller’s shell options, because a sourced file that turns on errexit changes the behaviour of every test that loads it. The directive comment # shellcheck source=... tells ShellCheck where the sourced file lives, since it cannot resolve $here statically.[7]

The full project tree, including everything in later sections, is:

logsum/
├── bin/logsum                 executable (black box under test)
├── lib/logsum.sh              library of pure functions
├── test/
│   ├── helpers/common.bash    shared setup, assertion libraries, stub helper
│   ├── fixtures/*.log         static input files
│   ├── unit/                  in-process function tests
│   ├── integration/           whole-program tests
│   └── regression/            one test per fixed bug
├── examples/                  ShellCheck demonstrations
├── exercises/                 solutions to section 15

3. Static analysis

Static analysis examines source code without running it. For shell scripts it comes in three strengths:

ToolWhat it checksExample of a defect it finds
bash -n scriptSyntax only. The -n option reads commands without executing them.[3]A missing fi or an unterminated quote.
shfmtParses the script into a syntax tree and prints it back in a canonical layout; parse errors are reported.[8]Inconsistent indentation; syntax errors.
ShellCheckSemantic analysis: quoting, word splitting, misuse of commands, portability, unused or unassigned variables, and many more patterns, each with a numbered code and a wiki page.[9,10]Unquoted $var, iterating over ls output, cd without error handling.

Static checks are fast enough to run in an editor on every save and in a pre-commit hook on every commit. They do not replace tests: a script can be perfectly lint-clean and still compute the wrong answer. They do remove a whole category of defects so that tests can concentrate on behaviour.

When the target is a POSIX sh rather than Bash, the authoritative definition of the language is the POSIX Shell Command Language chapter.[11] ShellCheck and shfmt both accept a dialect setting (-s sh and -ln posix respectively) so that Bash-only syntax is flagged in portable scripts.[8,12]

4. ShellCheck

4.2 Severities, output formats and exit status

ShellCheck has four severities: error, warning, info and style. -S warning (or --severity=warning) reports only warnings and errors. -f selects the output format: tty (default), gcc, checkstyle, diff, json, json1 or quiet.[12] The gcc format is convenient for editors and CI annotations:

$ shellcheck --norc -f gcc examples/cleanup.sh
examples/cleanup.sh:4:1: warning: Use 'cd ... || exit' or 'cd ... || return' in case cd fails. [SC2164]
examples/cleanup.sh:4:4: note: Double quote to prevent globbing and word splitting. [SC2086]
examples/cleanup.sh:5:10: error: Iterating over ls output is fragile. Use globs. [SC2045]

ShellCheck exits with status 0 when there are no issues and 1 when it reports any, which is what lets it fail a CI step directly.[12]

4.3 Directives and suppressions

A comment of the form # shellcheck key=value is a directive. Placed before a command, it applies to that command; placed after the shebang and before the first command, it applies to the whole file.[7] The common ones are:

  • # shellcheck disable=SC2154 suppresses a check. Always say why on the same line.[19]
  • # shellcheck source=../lib/logsum.sh tells ShellCheck which file a dynamic source refers to.[7]
  • # shellcheck shell=bash sets the dialect when there is no shebang, as in a sourced library.[7]

In the example project every .bats file begins with a file-wide # shellcheck disable=SC2154, because variables such as BATS_TEST_TMPDIR are assigned by Bats at run time and ShellCheck cannot see that assignment. SC2154 is the “referenced but not assigned” warning.[20] Suppressing it per file, with a reason, is better than turning it off for the whole project, where it catches real typos.

5. shfmt

shfmt is the formatter in Daniel Martí’s mvdan/sh project, which also provides a shell parser and interpreter written in Go.[21] It supports the bash, posix, mksh, bats and zsh dialects.[8] A consistent layout matters for review: when formatting is automatic, diffs show only real changes and reviewers stop commenting on indentation.

5.1 The four modes you need

CommandEffect
shfmt filePrint the formatted file to standard output.
shfmt -w fileRewrite the file in place.
shfmt -d filePrint a diff and exit non-zero if the formatting differs. Use this in CI.
shfmt -l dirList files whose formatting differs; a directory is walked for shell files.

Printer flags include -i N (indent with N spaces; 0, the default, means tabs), -ci (indent case branches), -bn (allow binary operators such as && to start a line), -sr (space after redirections) and -s (simplify code).[8] When walking a directory, shfmt picks up files with shell extensions and extensionless files with a shell shebang.[8]

5.2 Configure with EditorConfig, not flags

The [node_modules/**] ignore = true section is also there for a reason. Without it, shfmt -l . walked into the vendored copy of Bats and reported a 200 KB diff of somebody else’s code. 6. Bats (Bash Automated Testing System)

Bats is a TAP-compliant testing framework for Bash; the maintained fork is bats-core.[23,24] A Bats file is a Bash script with a special syntax: each @test "description" { ... } block becomes a function, and a test passes if every command in it succeeds.[25] Bats evaluates a test file once to count the tests and then runs each test case in its own process,[25] which is the foundation of the isolation discussed in section 11.

6.1 Installing

Bats can be installed from a package manager, from source, as a Git submodule or from npm.[26] This project uses npm so that the exact versions of Bats and its helper libraries are pinned in package-lock.json and installed reproducibly with npm ci, which installs exactly what the lockfile records.[27]

Supply-chain note

The npm package named bats-file is not the bats-core helper library; when this article was written it was a security placeholder (version 0.0.1-security). If you want bats-file, install it from the bats-core GitHub organisation, for example as a Git submodule.[28] Always check what a package name resolves to before trusting it in CI.

6.2 The run helper

run executes a command, captures its exit status in $status, its combined standard output and error in $output, and the non-empty lines of output in the $lines array. run itself returns 0, so the test continues and can make assertions.[25] Three options make tests stricter and clearer:

  • run -N cmd fails the test unless the exit status is exactly N; run ! cmd requires a non-zero status.[25]
  • run --separate-stderr cmd puts standard error in $stderr and ${stderr_lines[@]} so that you can assert on each stream separately.[25]
  • bats_require_minimum_version 1.5.0 at the top of a file declares the Bats version that these flags need. Without it, Bats prints warning BW02 when a flag is used on run.[25,29]

The bats documentation explains why run -1 is better than checking [ "$status" -ne 0 ]: a command that is not installed exits 127, which a plain non-zero check would accept as the expected failure.[25]

6.3 Assertion libraries

Plain [ ... ] tests work, but a failure says only which line failed. bats-assert (which depends on bats-support) provides assertions such as assert_success, assert_failure, assert_output (exact, --partial or --regexp) and assert_line, and on failure prints the expected and actual values.[30,31] Libraries are brought in with load, which sources a file relative to the test file’s directory, adding .bash if needed.[25] Here is the shared helper every test loads:

6.5 Two gotchas

First, Bats relies on errexit, so Bash’s rules about when set -e is ignored apply inside tests. A negated command is one of those cases.[3,33] This test passes even though ! true “fails”:

@test "negation does not fail the test" { ! true; echo after; }   # ok
@test "run ! does"                     { run ! true; }            # not ok

Use run !, run -N or an assertion function instead of a bare !. ShellCheck knows about this trap: in a .bats file it reports a bare ! in a test as SC2314.[34] Second, run executes its command in a subshell, so variables it sets are not visible afterwards and it cannot see a pipe written after it; bats_pipe exists for the pipeline case.[25,33]

7. Unit testing

A unit test exercises one function in isolation, with controlled inputs, and checks its outputs and exit status. In Bash, the unit is usually a function, and “controlled inputs” means arguments, standard input, environment variables and files.

7.1 Make the code sourceable

To call a function from a test, the test must source the file that defines it, and sourcing must have no side effects. That is why logsum keeps its functions in lib/logsum.sh. If you prefer a single file, guard the entry point so that it runs only when the file is executed, not when it is sourced. BASH_SOURCE[0] holds the name of the file being read, while $0 is the name of the running script, so the two are equal only when the file is executed directly:[35]

main() { ... }
if [[ ${BASH_SOURCE[0]} == "$0" ]]; then
  main "$@"
fi

The Google Shell Style Guide recommends the same structure: put the program in a main function called at the bottom of the file.[36]

7.2 The unit tests

Points to notice:

  • Each test checks one behaviour, and the name says which. When a test fails, its name should tell you what broke.
  • Edge cases get their own tests: whitespace, a carriage return, an unknown level, an empty file, multiple files.
  • The negative case asserts the exact status (assert_failure 1) and that nothing was printed.
  • assert_output - reads the expected value from standard input, which keeps multi-line expectations readable with a quoted here-document.[30]

8. Integration testing

An integration test runs the real program as a separate process, the way a user or another script would, and checks the observable contract: exit status, standard output, standard error and side effects on files. It catches what unit tests cannot, such as option parsing, the effect of set -euo pipefail, path resolution of the library and the wiring between functions.

9. Mocking external commands

Tests should not depend on the network, the clock, the host name or anything else outside their control. The general name for an object that stands in for a real dependency during a test is a test double; a stub returns canned answers, and a mock or spy also records how it was called so the test can verify the interaction.[37,38]

9.1 How Bash finds a command

Mocking in Bash works by exploiting the command search order. When a command name contains no slash, Bash looks for a shell function of that name first, then a builtin, and only then searches the directories in $PATH.[39] POSIX specifies the same general order.[11] That gives two techniques:

TechniqueHowReaches child processes?Best for
Function overrideDefine curl() { ...; } in the testNo, unless exported with export -f[40]Unit tests of sourced functions
PATH stubWrite an executable curl into a temporary directory placed first in PATHYes, any program that looks up curl by nameIntegration tests of whole scripts

The stub_command helper in test/helpers/common.bash implements the PATH technique and adds spy behaviour: every call appends the command name and its arguments, quoted with printf %q, to $STUB_LOG. The integration tests then assert on three things: that a successful notification calls curl --fail with the right URL, that a failing curl yields exit status 3 with a clear message, and that curl is never called when -n is absent. The last one is a negative interaction test, and it is the kind of check that prevents a script from contacting production by accident.

Exercise 3 shows both techniques side by side for date and hostname.

Lesson from building this example: stubs that read standard input can hang

The first version of the curl stub was cat >/dev/null; exit 0, meant to swallow a request body. The first run of the suite passed. A later run, started in the background with standard input left open, hung indefinitely at test 10, because logsum passes the body as an argument (--data-binary "$summary") and the stub’s cat waited on a standard input that never closed. Two fixes, both applied in the project: stubs do only what the real call needs, and CI runs Bats with </dev/null. A per-test timeout (BATS_TEST_TIMEOUT) is a further safety net.[25]

9.2 What not to mock

Mock the boundaries you do not own or cannot control (network, time, randomness, privileged system commands). Do not mock grep, sort or your own functions in an integration test; at that point the test checks the mock rather than the program. A good rule is that integration tests should fail if the real tool changes behaviour in a way that matters, which is impossible if it has been replaced.

10. Test fixtures

A fixture is the known state a test starts from: input files, directories, environment variables, configuration.[38] Bats supports two kinds.

10.1 Static fixtures

Files checked into test/fixtures/, each designed to exercise something specific:

FilePurpose
mixed.logAll levels plus a malformed line that must be ignored.
clean.logNo ERROR lines; exit status 0 path.
empty.logZero bytes; boundary case.
crlf.logWindows line endings, including a line with no message; see section 12.
no-eol.logLast line has no trailing newline; see section 12.

Static fixtures are easy to read and review, but must never be modified by a test. A test that needs to change a file copies it into its temporary directory first, as the “file names containing spaces” test does.

10.2 Generated fixtures and the lifecycle hooks

Bats runs setup before each test and teardown after each test, and setup_file and teardown_file once per file.[25] Expensive shared fixtures belong in setup_file, written to $BATS_FILE_TMPDIR, a directory shared by all tests in the file.[25] Variables must be exported in setup_file to be visible to the tests, because each test runs in a separate process.[25]

teardown runs even when the test fails; this was confirmed while preparing the article with a test whose body is just false. That makes teardown the place for cleanup that must always happen, such as stopping a background server started in setup.

11. Test isolation

Isolated tests can run in any order, alone or in parallel, and give the same result. Shell tests are especially prone to leaking state through the working directory, the file system and the environment. Bats helps in three ways:

  1. Process per test. Each test runs in its own process,[25] so a variable exported or a directory changed in one test does not affect the next. The last two tests in fixtures_lifecycle.bats demonstrate both.
  2. Private temporary directory. $BATS_TEST_TMPDIR is unique to each test.[25] Write every generated file there and cd into it when the code under test writes relative paths.
  3. Per-test PATH. The stub helper puts its directory under $BATS_TEST_TMPDIR, so a mock defined in one test cannot shadow the real command in another.

Some isolation is your responsibility:

  • Locale. Sorting and character classes depend on the locale. count_levels pins LC_ALL=C for sort so that output is identical on every machine.
  • Time and randomness. Inject them (pass a timestamp as an argument) or stub date.
  • Standard input. As section 9 showed, a test that inherits an open terminal can block. Run suites with </dev/null.
  • Real home directory and network. If the code reads ~/.config, set HOME="$BATS_TEST_TMPDIR" in setup.

Outside Bats, the same pattern is a temporary directory created with mktemp -d and removed by a trap on exit:[41,42]

tmp=$(mktemp -d) || exit 1
trap 'rm -rf -- "$tmp"' EXIT

12. Regression testing

A regression is a bug that comes back. The defence is simple and strict: every fixed bug gets a test that reproduces it, written before the fix so that you have seen it fail. Naming the test after the issue makes the link to the bug report permanent, and tagging lets you run just these tests quickly with bats --filter-tags regression.[32]

The three bugs are real classes of shell defect. Issue #17 is the trailing-newline problem: read returns non-zero when it reaches end of file before a newline,[43] so a plain while read loop silently drops the last line. The fix is || [[ -n $line ]]. Issue #21 guards against glob expansion of unquoted data.[14]

12.1 Test your tests: a small mutation check

A regression test is only useful if it fails when the bug returns. The cheapest way to check is to put the bug back by hand and run the suite. While preparing this article, two such mutations were tried on lib/logsum.sh:

  1. Removing || [[ -n $line ]] made test 14 (issue #17) fail, as intended.
  2. Removing the call to trim in level_of made no test fail.

The second result exposed a weak test. The original crlf.log had only lines with a message after the level, so read put the carriage return into the third field and the level was clean anyway. The bug only shows when the level is the last field. Adding the line 2026-11-01T10:00:02Z WARN\r to the fixture made the mutation fail as it should:

This is mutation testing in miniature. Doing it for each regression test, once, when you write it, costs a minute and tells you the test actually protects you.

13. Code review

Automated checks free reviewers to look at what tools cannot judge. Google’s published review guidelines list design, functionality, complexity, tests, naming, comments, style and documentation as the things to look for, and ask reviewers to check that tests are correct, sensible and useful, and that they would fail when the code is broken.[44] For shell code, a reviewer’s checklist can be concrete:

13.1 A shell review checklist

  • Tools are green. ShellCheck and shfmt pass in CI; every disable= directive has a reason.
  • Error handling is real. set -e is not relied on inside functions that are called from if, &&, || or !, where it is ignored.[3] The demonstration below shows the effect.
  • No masked failures. local v=$(cmd) discards cmd’s exit status because the status of local is returned instead; declare and assign separately.[45]
  • Quoting and globbing. Every expansion quoted unless splitting is intended and commented.[14]
  • Destructive commands are guarded. rm -rf "$dir/" where $dir could be empty; prefer ${dir:?}, which aborts if it is unset or empty.[46]
  • Portability is explicit. The shebang matches the features used (Bash 4 features need Bash 4).[5]
  • Tests come with the change. New behaviour has unit or integration tests; a bug fix has a regression test that was seen failing.
  • Style follows the team’s guide, for example the Google Shell Style Guide, which also recommends that scripts longer than about 100 lines or with complex control flow be rewritten in a more structured language.[36]

13.2 Two demonstrations for reviewers

$ bash examples/masking.sh; echo "rc=$?"
still running, v=''
rc=0

ShellCheck flags line 5 with SC2155.[45] The second demonstration shows set -e being ignored inside a function called as an if condition, but honoured when the same function is called normally:

$ bash examples/sete.sh; echo "rc=$?"
check: kept going after false
if-branch taken
rc=1

A reviewer who knows these two behaviours will catch bugs that no current ShellCheck default check reports. ShellCheck does have an optional check, check-set-e-suppressed, aimed at the second case.[12]

14. CI-based shell testing

Continuous integration runs every check on every push and pull request, on a clean machine, so that “works on my laptop” is not the standard. Three pieces make this reliable: a single local entry point, a pinned toolchain and a CI workflow that calls the entry point.

14.1 One entry point: the Makefile

Developers run make ci locally and CI runs the same targets, so the two cannot drift apart.

14.2 The GitHub Actions workflow

Design notes, each tied to documented behaviour:

  • Least privilege. permissions: contents: read limits the token the workflow receives.[47]
  • Superseded runs are cancelled. The concurrency group with cancel-in-progress stops an older run on the same branch when a new commit arrives.[47]
  • Shell semantics are explicit. On non-Windows runners a run step with no shell uses bash -e {0}; with shell: bash it uses bash --noprofile --norc -eo pipefail {0}, which also fails on errors inside pipelines.[47] The test job sets the default with defaults.run.shell.[48]
  • Pinned tools. ShellCheck, shfmt and Bats are pinned to exact versions. A new ShellCheck release can add checks, and an unpinned upgrade would turn CI red on an unrelated pull request.
  • PATH updates are made by appending to the file named by $GITHUB_PATH, which affects subsequent steps.[49]
  • Reports survive failures. The JUnit report is uploaded with actions/upload-artifact under if: ${{ !cancelled() }}, a status-check expression that is true even when an earlier step failed, so the report is available precisely when tests fail.[50,51]
  • The workflow is linted too. actionlint is a static checker for workflow files and runs ShellCheck on the scripts inside run: blocks.[52] Both workflow files in this article pass it.

Exercise 5: Why does shfmt disagree with the project?

A colleague runs shfmt -i 2 -d bin lib and gets no diff. Another runs shfmt -i 2 -ci -d bin lib and also gets none, yet a third runs shfmt -d -i 4 bin lib and gets a diff of every line. The project’s .editorconfig says indent_size = 2. Explain what is going on and what command everyone should use.

Show solution

Any parser or printer flag on the command line makes shfmt ignore EditorConfig formatting options entirely.[8] Each colleague is therefore checking against the flags they typed, not the project style. The first two happen to agree with the project; the third does not. Everyone, and CI, should run shfmt -d . (or make fmt-check) with no printer flags, so that .editorconfig is the single source of truth.

Exercise 6: Add a Bash version matrix to CI

Write a GitHub Actions job that runs the Bats suite under Bash 4.4, 5.0, 5.1 and 5.2, with each version reported separately and one failing version not cancelling the others.

Show solution

strategy.matrix creates one job per version and fail-fast: false keeps the others running when one fails.[47] Bats is installed on the runner with npm ci, and the project directory, including node_modules, is mounted into the official bash image for each version.[54] The workflow passes actionlint, and the same docker run command was executed locally for all four versions with 22 of 22 tests passing. Adding "3.2" to the matrix would be a useful experiment: local -A needs Bash 4.0,[5] so you should expect failures, which is exactly what a version matrix is for.

Exercise 7: Review this change

A pull request adds the following function to a deployment script. Write review comments as you would on the pull request.

deploy() {
  local release=$(git describe --tags)
  cd $DEPLOY_DIR
  rm -rf $DEPLOY_DIR/current/*
  tar -xzf /tmp/$release.tgz -C current
  echo "deployed $release"
}
Show solution
  1. Masked failure (SC2155). If git describe fails, local still succeeds and release is empty. Declare and assign separately and check the status.[45]
  2. Unchecked cd (SC2164). If $DEPLOY_DIR does not exist, every later command runs in the current directory.[15]
  3. Dangerous rm. If DEPLOY_DIR is unset or empty, the command becomes rm -rf /current/*. Use "${DEPLOY_DIR:?}", which aborts on an empty value.[46] ShellCheck reports this pattern as SC2115.[55]
  4. Unquoted expansions (SC2086) throughout.[14]
  5. Predictable path in /tmp. Another user could plant /tmp/v1.2.tgz. Download to a directory from mktemp -d.[41]
  6. Not atomic. The old release is deleted before the new one is known to extract. Extract into a new directory and switch a symlink.
  7. Tests. Ask for a Bats integration test with a stubbed git and a temporary DEPLOY_DIR, including the case where git describe fails.

A corrected version:

deploy() {
  local release dir
  release=$(git describe --tags) || return 1
  dir=${DEPLOY_DIR:?DEPLOY_DIR must be set}
  cd -- "$dir" || return 1
  mkdir -- "releases/$release" || return 1
  tar -xzf "$ARTIFACT_DIR/$release.tgz" -C "releases/$release" || return 1
  ln -sfn -- "releases/$release" current
  printf 'deployed %s\n' "$release"
}
