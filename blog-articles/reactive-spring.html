01Problem

The scarcity that started it

Every server-side concurrency model is an answer to the same arithmetic. Little’s law states that the average number of items in a stable system equals the arrival rate multiplied by the average time each item spends inside it: L = λW. The result was proved in full generality by John Little in 1961 and holds without any assumption about arrival distribution or service discipline.1 Applied to an HTTP service it says something uncomfortable: the number of requests simultaneously in flight is fixed by throughput and latency, and a server controls neither. A service handling 8,000 requests per second with a mean latency of 200 ms has 1,600 requests in flight at all times, whatever its implementation looks like.

In a classical servlet application each in-flight request owns a platform thread for its entire duration, including the portion spent waiting on a database, a cache or a downstream API. A thread that is parked on a socket read consumes no CPU, but it does consume a thread — a scarce, kernel-scheduled object with a reserved stack. Sixteen hundred of them is not a pool, it is a memory budget and a scheduler problem. The usual mitigation is to cap the pool, which converts a memory problem into a latency problem: requests queue in the acceptor, response times inflate, and by Little’s law the inflation increases the in-flight count further. This is the failure mode that makes blocking services fall over abruptly rather than degrade smoothly.

Non-blocking I/O attacks the same arithmetic from the other side. If a request that is waiting on I/O holds no thread, then in-flight count and thread count are decoupled. A handful of event-loop workers — conventionally one per core — multiplex tens of thousands of connections, doing work only when a socket is actually readable or writable. The Spring team describes the expected benefit precisely, and it is worth quoting the framing rather than the marketing: reactive and non-blocking generally do not make applications run faster, and doing things the non-blocking way requires more work, which can slightly increase processing time. The benefit is the ability to scale with a small, fixed number of threads and less memory, which makes applications more resilient under load because they scale in a more predictable way.2

That last clause is the honest sales pitch for the entire reactive stack. You are not buying throughput. You are buying a system whose resource consumption is flat with respect to concurrency, and whose degradation curve under overload is a queue you can see and control rather than a thread pool you cannot. The price is a programming model in which control flow is expressed as data, exceptions are values, and the call stack no longer tells you where you are.

What non-blocking does not buy you

Per-request latency usually gets marginally worse, not better. CPU-bound work is unaffected. A single blocking call anywhere in the chain reverts the whole service to thread-per-request behaviour, with a pool four times too small. And debugging cost rises sharply. If your service talks to one low-latency database over JDBC and nothing else, the reactive stack will cost you more than it returns.

02History

Lineage: from Rx to Reactive Streams to Spring

The programming model arrived before the specification. Erik Meijer’s Reactive Extensions at Microsoft recast asynchronous event sources as composable, queryable sequences — the dual of the iterator — and the operator vocabulary it established (map, filter, flatMap, merge, zip, window) is still the vocabulary everything else uses.3,4 Netflix ported the ideas to the JVM as RxJava, motivated by a concrete production problem: an API layer that had to fan a single device request out into dozens of concurrent service calls without the thread-safety and nesting pain of chained futures. Ben Christensen and Jafar Husain introduced the library publicly in February 2013.5

Rx solved composition but not flow control. An Observable pushed at whatever rate the source produced, and a fast source with a slow consumer had exactly two outcomes: unbounded buffering or dropped data. The Reactive Streams initiative, a collaboration between engineers from Lightbend, Netflix, Pivotal, Kaazing, Red Hat, Twitter and others, was formed to fix that gap with the smallest possible standard: four interfaces and a set of rules governing asynchronous stream processing with non-blocking back pressure.6 Version 1.0 landed in 2015; the interfaces were adopted verbatim into the JDK as java.util.concurrent.Flow in Java 9, which is why the JDK type and the org.reactivestreams type are structurally identical and trivially adapted.7

In parallel, the Reactive Manifesto argued the architectural case — responsive, resilient, elastic, message-driven — and gave the movement a name that has been both useful and endlessly abused.8 “Reactive” in the manifesto sense is a property of a distributed system; “reactive” in the Spring sense is much narrower. The Spring team ties the word to two things: reacting to change instead of blocking, and non-blocking back pressure, the mechanism that keeps a fast producer from overwhelming its destination when there is no blocking call to serve as a natural brake.2

Project Reactor became Spring’s implementation, developed in close collaboration with the framework team, and Spring WebFlux shipped in Spring Framework 5.0 in 2017 as a peer of Spring MVC rather than a replacement for it.9 The two web stacks live in separate modules, spring-webmvc and spring-webflux, and both are optional; an application can use one, the other, or Spring MVC controllers with the reactive WebClient.9,10 The remaining pieces filled in over the following years: R2DBC gave relational databases a non-blocking SPI in 2018–2022,11 RSocket provided a wire protocol with Reactive Streams semantics built in,12 and Kotlin coroutines gave the whole stack an imperative surface syntax.13

The current generation is Spring Framework 7.0, released in November 2025 on a Jakarta EE 11 baseline, and Spring Boot 4.0 alongside it.14,15 Two changes matter for reactive work specifically. Servlet 6.1 became the container baseline, which removed the Undertow-specific WebSocket and low-level HTTP support from the WebFlux side until Undertow catches up.14 And declarative HTTP service clients were promoted to a first-class, auto-configured feature, giving WebClient an interface-based front end for the common case.16,15

03Specification

The contract: four interfaces and a protocol

Reactive Streams is deliberately unglamorous. It defines a Publisher with a single subscribe method, a Subscriber with four callbacks, a Subscription with request and cancel, and a Processor that is both.6,17 A Publisher is a factory rather than an accessor: subscribe may be called many times, each call starting a new Subscription that serves exactly one Subscriber, and a rejected subscription is reported through onError rather than by throwing.18 Everything else in this article is built on those twelve methods.

org.reactivestreams · the entire specification surface
public interface Publisher<T> {
    void subscribe(Subscriber<? super T> s);
}

public interface Subscriber<T> {
    void onSubscribe(Subscription s);
    void onNext(T t);
    void onError(Throwable t);
    void onComplete();
}

public interface Subscription {
    void request(long n);
    void cancel();
}

public interface Processor<T, R> extends Subscriber<T>, Publisher<R> {}

The interfaces are unremarkable; the rules are the specification. Every method returns void, deliberately, so that all four participants can be implemented fully asynchronously.6 A Subscription represents a one-to-one lifecycle between one Subscriber and one Publisher and can be used only once, which is why subscribe returns nothing and hands the subscription back through onSubscribe instead.19 No data flows until demand is signalled: after onSubscribe, the subscriber receives nothing further until it calls request(n).20

Four rules carry most of the practical weight.

Demand is a bound, and it is additive. A publisher may emit at most n onNext signals for a request(n), and successive requests accumulate.19,6 A cumulative outstanding demand of Long.MAX_VALUE or more may be treated as effectively unbounded, which is the specification’s formal escape hatch for consumers that genuinely do not want flow control.19 This is exactly what a bare subscribe() with no arguments does in Reactor, and it is why so much reactive code silently has no backpressure at all.

Signals to a single subscriber are serial. onNext, onError and onComplete are never invoked concurrently for the same subscriber, which is the property that lets pipeline code manipulate mutable local state without synchronisation.6 The Spring documentation calls this out as a key benefit: a reactive pipeline processes data sequentially in distinct stages, and application code inside the pipeline is never invoked concurrently.2

Terminal signals are final. Once onError or onComplete has been signalled, no further signal may occur, and the subscription is treated as cancelled.6 There is no resumption after failure; recovery means substituting a different sequence, which is why every recovery operator in Reactor takes a replacement publisher rather than a continuation.

Bounds must be knowable. The specification’s design principle is that all buffer sizes are bounded, and that those bounds are known and controlled by subscribers, expressed in element counts.6 Any implementation aiming to support high-rate or infinite streams has to enforce bounds along the entire path or it will run out of memory.6 The rule that a subscriber must call cancel() when a subscription is no longer needed exists for the same reason: it is how resources get reclaimed promptly.6

The specification is an SPI, not an API

Reactive Streams is for interoperability between libraries and infrastructure; it is too low-level to be an application API. Applications need a richer functional vocabulary to compose asynchronous logic, and that is the role reactive libraries play.2 You will almost never implement Subscriber by hand. You will, however, debug through these signals constantly.

The project ships a Technology Compatibility Kit alongside the interfaces so that implementations can be verified against the rules rather than against each other.6 That is why Reactor, RxJava 3, Akka Streams, Vert.x, Mutiny and the JDK Flow types interoperate: they all pass the same TCK. Spring WebFlux exploits this directly — a WebFlux API generally accepts a plain Publisher as input, adapts it internally to a Reactor type, and returns Flux or Mono as output, so you can feed it RxJava and adapt the result back if you want.2,21

04Library

Reactor: Mono, Flux, and the two-phase pipeline

Reactor is the reactive library WebFlux requires as a core dependency. It supplies two publisher types aligned to cardinality: Mono<T> for a sequence of zero or one element, and Flux<T> for zero to N, both with operator sets aligned to the ReactiveX vocabulary and both fully backpressure-aware because they are Reactive Streams implementations.2,22,23

Encoding cardinality in the type is a small decision with large downstream effects. Mono<Order> and Flux<Order> are different contracts, and the compiler enforces the difference at every boundary: a repository lookup by identifier returns Mono, a query returns Flux, an HTTP handler returns Mono<ServerResponse> because there is exactly one response. Mono also composes with Void to express “completion with no value”, which is how the entire WebFlux request pipeline signals that an exchange has been fully handled.

Assembly time and subscription time

The single most important operational fact about Reactor is that building a pipeline does nothing. Operators are declarative: each call wraps the upstream publisher in a new one and returns immediately. No I/O is issued, no thread is used, no lambda is invoked. All of that happens later, when something subscribes, and the subscription walks the chain upward from the terminal subscriber to the source before any signal travels back down.24

Two phases means two places for bugs, and they look completely different. An exception thrown while assembling a chain propagates like an ordinary exception on the calling thread. An exception thrown while executing it arrives as an onError signal on whatever thread the pipeline happens to be running on, long after the assembling method returned. The practical rule that follows is that try/catch around a pipeline declaration catches almost nothing worth catching.

// Assembly: returns instantly, does nothing, touches no network.
Mono<OrderView> view = orderRepository.findById(id)            // no query yet
        .flatMap(order -> pricing.quote(order))                // no HTTP call yet
        .map(OrderView::from)                                  // no mapping yet
        .switchIfEmpty(Mono.error(new OrderNotFound(id)));     // no error yet

// Subscription: the framework subscribes when it writes the response.
// Only now does the query run, and only now can anything fail.

“Nothing happens until you subscribe” is the slogan; the corollary that bites in production is that a publisher you forget to return or subscribe to is a silent no-op. A save() whose Mono is discarded never writes. There is no warning, no log line, and no exception — only a missing row. Static analysis for unused reactive return values is worth enabling on day one.

Cold, hot, and the shape of repetition

Most Reactor sources are cold: each subscriber triggers a fresh execution of the source, so subscribing twice to a WebClient call issues two HTTP requests. Hot sources — typically built with Sinks, or created by share()/cache()/replay() — multicast a single execution to many subscribers, and late subscribers may miss earlier elements.24 Confusing the two produces the two classic bugs of reactive services: duplicated side effects from an accidentally cold pipeline that is subscribed more than once, and missing data from a hot pipeline subscribed too late.

A worked fan-out

// One request, three independent downstream calls, one composed result.
Mono<Quote> quote(String sku, String region) {
    Mono<BigDecimal> base   = pricing.base(sku);           // ~40 ms
    Mono<Integer>    stock  = inventory.available(sku);    // ~25 ms
    Mono<BigDecimal> rating = rating.factorFor(region);    // ~60 ms

    // Subscribed together; wall-clock cost is the slowest, not the sum.
    return Mono.zip(base, stock, rating)
            .map(t -> new Quote(sku, t.getT1(), t.getT2(), t.getT3()))
            .timeout(Duration.ofMillis(250))
            .onErrorResume(TimeoutException.class, e -> cachedQuote(sku, region));
}

This is where reactive composition genuinely pays: 125 ms of serial latency becomes ~60 ms, with a single timeout governing the whole composition and one fallback path. The Spring team makes the same point — the greater the latency per call and the interdependency among calls, the more dramatic the benefit.2

05Flow control

Backpressure in practice

Backpressure is the feature people cite as the reason to go reactive and then never configure. It is worth being precise about what the framework does automatically and what it does not.

Reactor operators propagate demand upstream automatically. When WebFlux writes a Flux to an HTTP response, the response writer subscribes with bounded demand and requests more only as the socket drains, so a slow client genuinely does slow a database cursor behind it — provided every hop in between honours demand. Most operators prefetch in batches (256 by default) rather than requesting one element at a time, because a stop-and-wait protocol where each element costs a round trip of demand signalling is needlessly slow; requesting in batches amortises the cost of acknowledgement.6,24

The gap opens at sources that cannot be slowed. The specification is explicit that its job is only to establish the mechanism and the boundary: if a publisher cannot slow down, it has to decide whether to buffer, drop, or fail.2 That decision is yours, and it is a product decision disguised as an API call.

Naming the policy at the edge, where the unbounded source enters
// A push source you do not control: a message broker, a sensor feed, a websocket.
Flux<Reading> readings = Flux.create(sink ->
        device.onReading(sink::next), FluxSink.OverflowStrategy.LATEST);

// Explicit policy at the boundary, with an escape hatch for what is dropped.
Flux<Reading> governed = readings
        .onBackpressureBuffer(10_000,
                dropped -> meterRegistry.counter("readings.dropped").increment(),
                BufferOverflowStrategy.DROP_OLDEST)
        .limitRate(256);        // shape unbounded downstream demand into batches

Three rules cover most production cases.

Put the policy at the boundary. The place to decide between buffering, dropping and failing is where the uncontrollable source enters your system, not three operators downstream after a queue has already grown.

Bound every buffer explicitly. onBackpressureBuffer() with no argument is unbounded, which converts a flow-control problem into an OutOfMemoryError under exactly the conditions where you least want one. Always supply a capacity and an overflow strategy, and always instrument the drop callback: a silent drop is an outage you find out about from a customer.

Watch for demand-erasing operators. Anything that decouples upstream from downstream on a queue — publishOn, buffer, window, groupBy, parallel — introduces a capacity that must be sized. groupBy in particular deadlocks quietly if you do not consume every group, because an unconsumed group holds demand that the source is waiting on.

Backpressure does not cross an unaware boundary

Demand signalling stops at the first component that does not participate. A JDBC driver, a synchronous cache client, an ExecutorService with an unbounded queue, or an HTTP endpoint that has already buffered the whole response body all erase it. RSocket is notable precisely because it carries Reactive Streams semantics across the network, so demand propagates between processes rather than terminating at the socket.12,25

06Runtime

Threads, schedulers, and the one unbreakable rule

Spring MVC and WebFlux differ less in their programming model than in their default assumptions about blocking. Servlet containers assume applications may block the current thread and therefore use a large thread pool to absorb it; non-blocking servers assume applications do not block, and use a small fixed-size pool of event-loop workers.2 Everything difficult about operating WebFlux follows from that one asymmetry.

On a plain WebFlux server you should expect one thread for the server plus roughly as many request-processing threads as there are CPU cores; a servlet container may start with more, for example ten on Tomcat, because it supports both blocking and non-blocking servlet I/O.2 The reactive WebClient runs in the same event-loop style, and if Reactor Netty is used for both client and server, the two share event loop resources by default — which is efficient and also means a client-side stall can starve server request handling.2,26

publishOn and subscribeOn

Reactor exposes thread control through two operators that are constantly confused because both take a Scheduler and neither says which direction it applies in.27

publishOn affects everything declared after it: signals arriving at that point are re-dispatched onto the given scheduler, and downstream operators run there. subscribeOn affects the source: it determines the thread on which the subscription, and therefore the source’s work, happens, regardless of where in the chain it appears. Multiple publishOn calls each take effect at their position; multiple subscribeOn calls do not stack — the one closest to the source wins.

The escape hatch, and its cost

Both Reactor and RxJava provide publishOn to continue processing on a different thread, so calling a blocking library is possible; the documentation is blunt that blocking APIs are not a good fit for this concurrency model.2 The mechanically correct pattern is to isolate the blocking call on boundedElastic:

Mono<LegacyReport> report(String id) {
    return Mono.fromCallable(() -> legacyJdbcDao.load(id))   // blocking, deferred
            .subscribeOn(Schedulers.boundedElastic())        // moved off the event loop
            .timeout(Duration.ofSeconds(2));                 // the pool is not infinite
}

Two caveats. Mono.fromCallable defers the call correctly; Mono.just(legacyJdbcDao.load(id)) executes it eagerly on the calling thread at assembly time, which is the same bug with a friendlier syntax. And boundedElastic is bounded on purpose: if every request needs it, you have rebuilt a thread-per-request server with extra indirection and a queue that fills silently. Isolating one legacy dependency is sound engineering; isolating your primary data store is a sign that Spring MVC was the right choice.

Finding blocking calls you did not know about

The dangerous blocking calls are the ones nobody wrote deliberately: a logging appender that flushes synchronously, a metrics client, a DNS lookup, a lazily-initialised bean, an InputStream read hidden in a serialisation library. Code review does not find these, because a blocking method and a non-blocking method look identical at the call site.

BlockHound exists for exactly this. It is a Java agent that instruments the JVM’s blocking methods — including native ones, via native method instrumentation — and throws an error when one is invoked from a thread marked as non-blocking, meaning threads implementing Reactor’s NonBlocking marker interface such as those started by Schedulers.parallel().28,29 The error points at the exact call site, which is the part code review cannot give you.30 Reactor has shipped a built-in integration since reactor-core 3.3.0.28

07Architecture

Inside WebFlux: from socket to handler

WebFlux is layered so that the programming models sit on a runtime-neutral foundation. The spring-web module contains that foundation: HTTP abstractions, Reactive Streams adapters for supported servers, codecs, and a core WebHandler API comparable to the Servlet API but with non-blocking contracts.2 31

The lowest application-visible contract is HttpHandler, a single method taking a request and response and returning Mono<Void> that completes when the exchange is finished. Every supported server — Reactor Netty, Tomcat, Jetty, and Servlet containers generally — is adapted to it, which is what lets the higher layers be server-agnostic.31,2 Above that sits the WebHandler API with its filter chain and exception handlers, and above that DispatcherHandler, the reactive analogue of DispatcherServlet, which discovers HandlerMapping, HandlerAdapter and HandlerResultHandler beans from the application context and delegates in the same three-phase pattern.32

Two details of this layering are worth internalising because they explain most surprising behaviour.

The Servlet API is not exposed. Spring MVC relies on Servlet blocking I/O and lets applications use the Servlet API directly; WebFlux relies on Servlet non-blocking I/O behind a low-level adapter and does not expose it. The documentation strongly advises against mapping servlet filters or manipulating the Servlet API in a WebFlux application, because mixing blocking and non-blocking I/O in the same context causes runtime issues.2 Spring Boot defaults the WebFlux starter to Netty because it is more widely used in the async, non-blocking space and lets client and server share resources.2,33 Netty itself is an asynchronous event-driven network framework, and Reactor Netty is the Reactive Streams adapter over it.34,26

Bytes are a resource, not a value. WebFlux abstracts over server buffer implementations with DataBuffer and a DataBufferFactory, and on Netty those wrap pooled, reference-counted ByteBuf instances.35 Codecs (Encoder, Decoder, and the HTTP-specific HttpMessageReader/HttpMessageWriter) convert between buffers and objects incrementally, which is what makes it possible to decode Flux<Order> from a request body without materialising the whole body.35,31 If you ever consume a Flux of raw buffers yourself, you own their release; DataBufferUtils.release exists for that, and leaked buffers surface as slow memory growth rather than an obvious error.

ServerWebExchange is the container carried through the whole chain: request, response, attributes, session and principal in one object.31 It is the right place to stash per-request state that filters and handlers share, and one of the two correct answers to “where did my ThreadLocal go” — the other being the Reactor Context.

Note the shape of the WebFlux stack in Spring Framework 7: Tomcat, Jetty and Servlet containers are supported alongside Netty, but Undertow-specific WebSocket and low-level HTTP support was dropped when Servlet 6.1 became the baseline, since Undertow does not yet implement that specification.14,36 Framework-level infrastructure — codecs, path matching, CORS, view resolution, API versioning — is customised through WebFluxConfigurer rather than through servlet registration.37

08Programming model

Annotated controllers and streaming responses

WebFlux offers two programming models on the same foundation. The first is annotated controllers, consistent with Spring MVC and based on the same annotations from spring-web; both stacks support reactive return types, and one notable difference is that WebFlux also supports reactive @RequestBody arguments, so a handler can begin processing a payload before the client has finished sending it.2,38,39

Annotated WebFlux controllers — the same annotations, different contracts
@RestController
@RequestMapping("/orders")
class OrderController {

    private final OrderRepository orders;
    private final PricingClient pricing;

    OrderController(OrderRepository orders, PricingClient pricing) {
        this.orders = orders;
        this.pricing = pricing;
    }

    @GetMapping("/{id}")
    Mono<OrderView> byId(@PathVariable String id) {
        return orders.findById(id)
                .switchIfEmpty(Mono.error(new OrderNotFound(id)))
                .flatMap(order -> pricing.quote(order)
                        .map(q -> OrderView.of(order, q)));
    }

    // The request body is decoded incrementally: elements are handled as they
    // arrive rather than after the whole payload has been buffered.
    @PostMapping(consumes = MediaType.APPLICATION_NDJSON_VALUE)
    Mono<Void> bulkImport(@RequestBody Flux<OrderDraft> drafts) {
        return drafts.concatMap(orders::insert).then();
    }

    // Server-sent events: an open-ended stream with no Content-Length.
    @GetMapping(value = "/events", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    Flux<OrderEvent> events(@RequestParam(required = false) String customer) {
        return eventStream.forCustomer(customer)
                .takeUntilOther(shutdownSignal);
    }
}

The choice of return type is not cosmetic. Returning Mono<T> or Flux<T> hands the publisher to the framework, which subscribes when it is ready to write and applies demand from the response writer.40 Returning a plain value forces you to have already resolved it, which usually means you blocked.

Flux plus application/json is the trap. It looks like streaming and behaves like buffering, because a JSON array cannot be emitted incrementally in a way general clients can parse. If you want the memory profile of streaming you must choose a streaming media type: text/event-stream or application/x-ndjson. Spring Framework 7 tightened this area — new Gson codecs were added for WebFlux, and because Gson cannot decode JSON non-blockingly, the decoder deliberately does not support decoding to Flux, though the encoder does support NDJSON for streaming output.14

Kotlin users get a third surface. WebFlux supports coroutines, so handler functions can be suspend functions returning ordinary values and Flow<T> for streams, which restores imperative-looking control flow over the same non-blocking runtime.13 For teams who want the concurrency model without the operator vocabulary, this is the shortest path.

    return OrderView.of(order, quote)

09Programming model

Functional endpoints: routing as a value

The second programming model is functional endpoints: a lambda-based, lightweight model that you can think of as a small library for routing and handling requests. The big difference from annotated controllers is that the application is in charge of request handling from start to finish, rather than declaring intent through annotations and being called back.2,41

Two functional interfaces carry the model. A HandlerFunction takes a ServerRequest and returns Mono<ServerResponse>. A RouterFunction takes a ServerRequest and returns Mono<HandlerFunction> — routing is itself an asynchronous lookup, and routes compose with and and andRoute rather than being discovered by classpath scanning.41

                        .GET("", accept(APPLICATION_JSON), handler::list)
                        .GET("/{id}", accept(APPLICATION_JSON), handler::byId)
                        .GET("/events", accept(TEXT_EVENT_STREAM), handler::stream)
                        .POST("", contentType(APPLICATION_JSON), handler::create)
                        .DELETE("/{id}", handler::cancel))
                .filter(audit)                              // wraps every handler above
                .onError(OrderNotFound.class, OrderRoutes::notFound)
                .build();
    }

    private static Mono<ServerResponse> notFound(Throwable ex, ServerRequest request) {
        ProblemDetail body = ProblemDetail.forStatusAndDetail(NOT_FOUND, ex.getMessage());
        body.setType(URI.create("https://errors.example.com/order-not-found"));
        body.setInstance(URI.create(request.path()));
        return ServerResponse.status(NOT_FOUND)
                .contentType(APPLICATION_PROBLEM_JSON)
                .bodyValue(body);
    }
}
Handlers are ordinary methods with an ordinary signature
@Component
class OrderHandler {

    private final OrderRepository orders;

    OrderHandler(OrderRepository orders) { this.orders = orders; }

                .flatMap(saved -> ServerResponse

                        .bodyValue(saved));
    }

        return ServerResponse.ok()
                .contentType(TEXT_EVENT_STREAM)
                .body(orders.watch(), Order.class);      // no Content-Length, no buffer

}

What you gain is transparency. There is no argument resolution, no content negotiation happening implicitly, no @ResponseStatus deciding the status code somewhere else. The handler reads the body, chooses the status, sets the content type, and returns. Every step is visible, which makes the model a good fit for gateways, edge services and anything where the request lifecycle itself is the thing being engineered. Spring Cloud Gateway’s server variant is built on exactly this stack.42

What you lose is the machinery: validation, content negotiation, exception mapping and argument binding are yours to wire. HandlerFilterFunction is the functional analogue of an interceptor and composes with filter, while RouterFunctions.route()’s onError gives you route-scoped error mapping.41 For a large CRUD surface this is more code than annotations; for twelve carefully-designed endpoints it is less indirection.

Both models can coexist

A single application can serve annotated controllers and router functions simultaneously — they are handled by different HandlerMapping implementations under the same DispatcherHandler.32 A common arrangement is annotations for the domain API and router functions for streaming, health and gateway-style endpoints. Note also that the functional model exists in Spring MVC too; the routing DSL is not exclusive to the reactive stack.41

Routers are also unusually easy to test, because a RouterFunction is a value. You can bind one directly to WebTestClient without starting a server or loading an application context, which keeps the feedback loop short:

10Client

WebClient: the reactive REST client

WebClient is the non-blocking, reactive HTTP client built on the same codecs and ClientHttpConnector abstraction as the server side, with Reactor Netty as the default connector.44 It is also the one part of the reactive stack that is worth adopting on its own: the Spring team’s explicit advice for teams with existing Spring MVC applications is to try the reactive WebClient first, returning reactive types directly from MVC controller methods, and to start small and measure the benefits before any broader shift.2

retrieve() and exchange()

retrieve() is the declarative path: it extracts the body and, by default, raises WebClientResponseException for 4xx and 5xx responses, with onStatus available to customise that mapping.45 exchangeToMono() gives you the whole ClientResponse when you need to branch on status, headers or cookies before deciding how to decode — with the obligation that you must always consume the body, or the connection leaks back into the pool in an unusable state.46

retrieve() with explicit status mapping, timeout and jittered backoff 45,47
Mono<Quote> quote(String sku) {
    return client.get()
            .uri("/pricing/{sku}", sku)
            .accept(APPLICATION_JSON)
            .retrieve()
            .onStatus(HttpStatusCode::is4xxClientError,
                    resp -> resp.bodyToMono(ProblemDetail.class)
                            .map(pd -> new PricingRejected(pd.getDetail())))
            .bodyToMono(Quote.class)
            .timeout(Duration.ofMillis(400))
            .retryWhen(Retry.backoff(3, Duration.ofMillis(50))
                    .jitter(0.5)
                    .filter(this::isTransient)
                    .onRetryExhaustedThrow((spec, signal) -> signal.failure()));
}

// Streaming: the response body is consumed as it arrives, never fully buffered.
Flux<Trade> trades(String symbol) {
    return client.get()
            .uri("/feed/{symbol}", symbol)
            .accept(APPLICATION_NDJSON)
            .retrieve()
            .bodyToFlux(Trade.class);
}

Retry.backoff deserves a note. Exponential backoff without jitter synchronises every client that failed at the same instant into a retry stampede that arrives together; the jitter factor randomises the delay and is the difference between a recovery and a second outage.47 The filter predicate matters equally: retrying a 400 is pointless, and retrying a non-idempotent POST is dangerous.

Configuration that is not optional

A default WebClient has no timeout beyond the connector’s defaults and a shared connection pool. Under load, both facts become incidents.

Bounded pool, bounded queue, bounded wait — the three bounds that prevent cascading failure 26,44
@Bean
WebClient pricingClient(WebClient.Builder builder, ObservationRegistry registry) {

    ConnectionProvider pool = ConnectionProvider.builder("pricing")
            .maxConnections(200)                        // hard ceiling per host
            .pendingAcquireMaxCount(500)                // queue depth, then fail fast
            .pendingAcquireTimeout(Duration.ofMillis(100))
            .maxIdleTime(Duration.ofSeconds(20))        // shorter than the peer's idle close
            .evictInBackground(Duration.ofSeconds(30))
            .build();

    HttpClient http = HttpClient.create(pool)
            .responseTimeout(Duration.ofMillis(500))
            .option(ChannelOption.CONNECT_TIMEOUT_MILLIS, 300)
            .compress(true);

    return builder
            .clientConnector(new ReactorClientHttpConnector(http))
            .baseUrl("https://pricing.internal")
            .filter(retryAfterAware())
            .filter(correlationIdPropagation())
            .observationRegistry(registry)              // per-request metrics and traces
            .build();
}

The connection-pool queue is the subtle one. pendingAcquireTimeout converts “wait indefinitely for a connection” into a fast failure you can shed load on, which is the reactive equivalent of a bulkhead. Without it, a slow downstream service silently converts your non-blocking client into an unbounded queue with a memory footprint. Setting maxIdleTime below the peer’s idle-close window avoids the classic intermittent PrematureCloseException caused by racing a server that closed the connection while it sat in your pool.

Blocking on WebClient, deliberately

WebClient can be used synchronously by calling block() on the result, and the documentation covers this case explicitly — but blocking on more than one value or in a WebFlux controller will throw, because Reactor detects the blocking call on a non-blocking thread.50 From a Spring MVC controller running on a servlet thread it is legitimate; from an event loop it is a bug the runtime will catch for you.

11Failure

Error handling as composition

In imperative Java, failure is a control-flow mechanism: an exception unwinds the stack until a handler catches it. In a reactive pipeline there is no stack to unwind by the time the failure occurs — the assembling method returned long ago, and the failure arrives as an onError signal travelling downstream on some other thread. Error handling is therefore composition, and the specification’s terminal-signal rule means recovery is always substitution: you cannot resume a failed sequence, only replace it.6

The error operators, and the honest guidance on each

onErrorContinue deserves its warning. It works by pushing a marker into the context that upstream operators consult, which means it can change the behaviour of operators that were written without knowledge of it. Prefer per-element error handling inside flatMap — where the scope is explicit — over a chain-wide continuation:

Mapping failures to HTTP

Spring’s error-response model is built on RFC 9457, Problem Details for HTTP APIs, which obsoleted RFC 7807 in 2023 and standardises a small JSON object with type, title, status, detail and instance members, extensible with additional fields.51,52 Four framework types implement it: ProblemDetail as the representation, ErrorResponse as the contract that all Spring WebFlux exceptions implement, ErrorResponseException as a convenient base class, and ResponseEntityExceptionHandler as a @ControllerAdvice base that handles every Spring WebFlux exception and renders an RFC 9457 body.53,54

Handler methods return Mono<ResponseEntity<ProblemDetail>> on the reactive stack 53,55
@RestControllerAdvice
class ApiErrors extends ResponseEntityExceptionHandler {

    @ExceptionHandler(OrderNotFound.class)
    Mono<ResponseEntity<ProblemDetail>> notFound(OrderNotFound ex,
                                                 ServerWebExchange exchange) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(NOT_FOUND, ex.getMessage());
        pd.setType(URI.create("https://errors.example.com/order-not-found"));
        pd.setTitle("Order not found");
        pd.setProperty("orderId", ex.orderId());          // non-standard extension field
        return Mono.just(ResponseEntity.of(pd).build());
    }

    @ExceptionHandler(PricingRejected.class)
    Mono<ResponseEntity<ProblemDetail>> upstreamRejected(PricingRejected ex) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(BAD_GATEWAY,
                "Pricing service rejected the request");
        pd.setProperty("upstreamDetail", ex.detail());
        return Mono.just(ResponseEntity.of(pd).build());
    }
}

Three details are easy to get wrong. First, the Jackson message converters use application/problem+json as the producible media type for ProblemDetail, preferring it over application/json and falling back to it when no compatible type is found — so clients that only accept application/json still receive problem documents.53 Second, the instance property is populated from the current URL path if you do not set it, which is usually what you want.53 Third, @ControllerAdvice ordering matters: a broad advice that catches Exception and is ordered ahead of your specific handlers will swallow them silently.56

Below the handler layer sits WebExceptionHandler, and specifically ErrorWebExceptionHandler, which catches what escapes the handler chain entirely — routing failures, filter failures, decoding errors that occur before a handler is selected.31 Any production service needs one, because the default representation is not the one you want to expose. It is also worth customising the problem details for framework exceptions to avoid revealing implementation details.53

Resilience patterns

Timeouts, retries and fallbacks are operators; circuit breakers and bulkheads are not. Resilience4j provides reactive operators that integrate directly into a Reactor chain, which is the idiomatic way to add a breaker without leaving the pipeline.57 The ordering of decorators is significant and frequently wrong:

Decorator order determines what the breaker actually observes 57
return pricing.quote(sku)
        .transformDeferred(RateLimiterOperator.of(rateLimiter))    // shed load first
        .transformDeferred(TimeLimiterOperator.of(timeLimiter))    // bound each attempt
        .transformDeferred(CircuitBreakerOperator.of(breaker))     // record the outcome
        .transformDeferred(RetryOperator.of(retry))                // then retry
        .onErrorResume(CallNotPermittedException.class,
                ex -> cachedQuote(sku));                           // open-circuit path

The rule of thumb for ordering

Retry outermost, circuit breaker inside it, time limiter inside that. If the breaker sits outside the retry, it observes one composite outcome per call rather than each attempt, and its failure-rate window becomes meaningless. If the time limiter sits outside the retry, the budget covers all attempts together, which is sometimes what you want — but decide it deliberately rather than by accident.

12Persistence

Data access without blocking

The Spring documentation offers a one-line test for whether an application is a candidate for the reactive stack: check its dependencies, and if you have blocking persistence APIs such as JPA or JDBC, Spring MVC is the best choice for common architectures.2 This is the constraint that determines most real adoption decisions, because JDBC is a fundamentally blocking API and no amount of wrapping changes that.

R2DBC

R2DBC exists to close the gap. It specifies a service-provider interface implemented by driver vendors and consumed by client libraries, giving reactive programmatic access to relational databases from JVM languages.11 Its drivers implement the database wire protocol on top of a non-blocking I/O layer rather than wrapping JDBC, and the SPI is deliberately minimal, specifying only the parts that differ across databases.58,59 The design goals are explicitly reactive: leave resource scheduling to the runtime, remove assumptions about concurrency from the programming model, and use backpressure for flow control.11 The practical effect is that the classic one-thread-per-connection model is replaced by one where connections are multiplexed like any other socket.59

Spring integrates R2DBC at two levels: DatabaseClient in spring-r2dbc for a fluent, functional API over the SPI, and Spring Data R2DBC for repositories, entity mapping and query derivation.60 61

Spring Data R2DBC repositories and DatabaseClient 61,60

}

R2DBC is genuinely non-blocking, and it is genuinely less capable than JPA. There is no lazy loading, no dirty checking, no first-level cache, no cascading, no @OneToMany graph traversal. Relationships are your problem, resolved with explicit queries and joins. For services with a small aggregate surface this is a feature; for a rich domain model with deep object graphs it is a substantial rewrite, and the honest answer is often that the domain belongs on the servlet stack.

Transactions

Reactive transactions work, but the boundary is different: a transaction is bound to the subscription rather than to a thread, because there is no thread to bind it to. Spring provides @Transactional on methods returning reactive types and a programmatic TransactionalOperator, both driven by ReactiveTransactionManager.60

Reactive transactions are scoped to a subscription, not a thread 60
// Declarative: the reactive transaction is bound to the subscriber context.
@Transactional
public Mono<Order> place(OrderDraft draft) {
    return orders.insert(Order.from(draft))
            .flatMap(saved -> ledger.debit(saved.customerId(), saved.total())
                    .thenReturn(saved));
}

// Programmatic, when the boundary is narrower than the method:
public Mono<Order> place(OrderDraft draft) {
    return transactionalOperator.transactional(
            orders.insert(Order.from(draft))
                    .flatMap(saved -> ledger.debit(saved.customerId(), saved.total())
                            .thenReturn(saved)));
}

The failure mode to watch for is a transaction that spans a call to a component that switches schedulers or is subscribed independently: the transactional context travels in the Reactor Context, so a publisher subscribed outside the transactional chain simply is not in the transaction. This is not detectable at compile time and rarely shows up in tests, which is a good argument for keeping reactive transactional scopes small and explicit.

13Cross-cutting

Context, security and observability

ThreadLocal is the substrate for an enormous amount of Java infrastructure: SLF4J’s MDC, security context holders, transaction synchronisation, tracing spans. None of it survives a reactive pipeline, because a single logical request may touch several threads and a single thread serves many requests. Reactor’s answer is Context: an immutable, subscriber-bound key-value store that propagates upstream from the point of subscription, which is why contextWrite placed at the end of a chain is visible to operators declared before it.24

Reactor Context: the reactive replacement for request-scoped ThreadLocal state
// Written once, at the outermost boundary; readable anywhere upstream of it.
@Component
class TenantContextFilter implements WebFilter {

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, WebFilterChain chain) {
        String tenant = exchange.getRequest().getHeaders().getFirst("X-Tenant");
        return chain.filter(exchange)
                .contextWrite(ctx -> ctx.put(TENANT_KEY, tenant));
    }
}

// Read, deep inside a service, with no parameter threading and no ThreadLocal.
Mono<Order> load(String id) {
    return Mono.deferContextual(ctx ->
            orders.findByIdAndTenant(id, ctx.get(TENANT_KEY)));
}

Spring Security’s reactive stack uses exactly this mechanism: ReactiveSecurityContextHolder reads the authentication from the Reactor context rather than a thread local, and @PreAuthorize works on methods returning reactive types.62,63 The same is true of reactive transaction state.

Making logs and traces work again

Manual context threading is correct but does nothing for the libraries that still read ThreadLocal. The Micrometer context-propagation library bridges the two worlds by defining accessors between context mechanisms — ThreadLocal, Reactor Context and others.64 Reactor Core supports it in two modes: an explicit mode using handle/tap, and an automatic mode enabled by Hooks.enableAutomaticContextPropagation(), which applies only to new subscriptions and should therefore be enabled at application startup.65 The automatic mode arrived in Reactor 3.5.3 and requires matching Micrometer versions; with it, tracing information is present in logs anywhere in a reactive chain without tap or handle gymnastics.66 Spring Boot exposes it as a property rather than requiring the hook call in application code.67

Configuration, not code 67

# and the usual observability wiring

The documentation is candid about the cost: both modes affect performance, accessing ThreadLocal variables can significantly impact a reactive pipeline, and if maximum scalability is the goal, more verbose approaches such as explicit argument passing should be considered instead of relying on ThreadLocal state.65 For most services the trade is worth making; for the hot path of a gateway handling six-figure request rates it may not be.

Beyond context, Spring Framework’s observability support instruments both the WebFlux server and WebClient with Micrometer observations, producing metrics and trace spans with consistent low-cardinality names.68 Adding observationRegistry(…) to a WebClient.Builder, as in the client configuration earlier, is what activates per-request client instrumentation.

14Verification

Testing reactive code

Reactive pipelines are testable in a way blocking code is not, because time and demand are both parameters rather than facts. reactor-test supplies StepVerifier, which subscribes to a publisher and asserts on the exact sequence of signals, and can substitute a virtual clock so that a five-hour retry policy is verified in milliseconds.69

StepVerifier asserts signals, demand and time 69
@Test
void emitsOrdersThenCompletes() {
    StepVerifier.create(service.recent(Duration.ofDays(1)))
            .expectNext(order("a"), order("b"))
            .expectComplete()
            .verify(Duration.ofSeconds(1));
}

@Test
void backpressureIsHonoured() {
    StepVerifier.create(service.feed(), 2)      // subscribe with an initial demand of 2
            .expectNextCount(2)
            .thenRequest(3)                     // then ask for three more
            .expectNextCount(3)
            .thenCancel()
            .verify();
}

@Test
void retriesWithBackoffWithoutWaiting() {
    StepVerifier.withVirtualTime(() -> client.quote("SKU-1"))
            .expectSubscription()
            .thenAwait(Duration.ofMinutes(30))  // virtual: the test takes microseconds
            .expectError(RetryExhaustedException.class)
            .verify();
}

The second test is the one most teams skip and most need: it verifies that a pipeline actually respects bounded demand rather than requesting Long.MAX_VALUE. Given how easily backpressure is erased by an intermediate operator, asserting on it is the only way to know it survived.

TestPublisher lets you drive a source manually, including emitting protocol violations to check that downstream code copes; PublisherProbe asserts whether a fallback branch was actually subscribed, which is otherwise invisible because an unsubscribed publisher looks identical to one that never existed.

What actually changes in production

Migrations to WebFlux disappoint when they are justified by throughput and delivered without changing the failure behaviour that motivated them. It is worth being concrete about which numbers move.

The realistic scorecard for an I/O-bound service

The Spring documentation frames the same point: reactive and non-blocking generally do not make applications run faster; the key expected benefit is scaling with a small, fixed number of threads and less memory, and observing that benefit requires latency in the system — a mix of slow and unpredictable network I/O is where the reactive stack begins to show its strengths.2 A service whose downstream calls all return in two milliseconds has nothing to gain.

Sizing and tuning

There is no thread pool to size, which removes the usual tuning lever and replaces it with three others.

Event loop count. The default is the number of available processors, and the default is almost always right. Increasing it does not help, because the loops are not the bottleneck unless something is blocking them — in which case the fix is removing the blocking call.26 In containers, verify that the JVM sees the correct CPU quota; a container limited to two cores but reporting sixteen will create eight times too many loops.

Connection pools. These are now the real concurrency limit. Every downstream host needs a bounded pool, a bounded pending-acquire queue and a bounded acquire timeout, as shown in the WebClient configuration earlier.26 The same applies to R2DBC: r2dbc-pool sits in front of the driver and its maximum size is the true ceiling on database concurrency.58

Queue capacities. Every publishOn, buffer, window and onBackpressureBuffer introduces a queue. Unbounded queues are a memory-exhaustion mechanism with a friendly name.

Benchmark the failure mode, not the happy path

Load tests that ramp to a target and hold it measure the least interesting property of a reactive service. The behaviour that justifies the architecture appears past saturation and during downstream degradation: inject 2-second latency into one dependency and watch whether the service sheds load, queues unboundedly, or falls over. That experiment tells you whether your bounds are real.

16Judgement

Reactive Spring after virtual threads

The strongest historical argument for WebFlux was thread scarcity. Virtual threads weakened it considerably. JEP 444 finalised virtual threads in JDK 21 with the explicit goal of enabling server applications written in the simple thread-per-request style to scale with near-optimal hardware utilisation, and of letting existing java.lang.Thread code adopt them with minimal change.71,72 A virtual thread that blocks on I/O unmounts from its carrier rather than parking a kernel thread, so the memory arithmetic that made 1,600 concurrent requests expensive largely disappears. JEP 491 later removed the pinning that synchronized blocks used to cause, closing the most common practical gap.73 Spring Boot has supported virtual threads through a single property since 3.2.74

The intellectually honest position is that virtual threads removed one of WebFlux’s two arguments and left the other intact. Thread scarcity is solved. Flow control is not.

Virtual threads restore cheap concurrency; they do not provide backpressure, streaming semantics, or a composition algebra. A virtual thread reading from a fast producer will happily allocate until the heap is exhausted, because there is no mechanism by which the consumer’s rate reaches the producer. Reactive Streams exists precisely to establish that mechanism and its boundary.6,2 Where the workload is request/response with bounded payloads, virtual threads plus Spring MVC is now the simpler and usually the correct answer. Where the workload is a stream — server-sent events, change feeds, message pipelines, gateway proxying, anything where a producer can outrun a consumer — the reactive stack retains a capability the imperative stack does not have.

Spring’s own guidance has been consistent and notably unhyped since well before Loom shipped: if you have a Spring MVC application that works fine, there is no need to change, because imperative programming is the easiest way to write, understand and debug code; if you have a large team, keep in mind the steep learning curve in the shift to non-blocking, functional and declarative programming; a practical way to start without a full switch is to use the reactive WebClient, then start small and measure; and for a wide range of applications the shift is unnecessary.2

Two further considerations tilt specific cases. Kotlin coroutines give the non-blocking runtime an imperative syntax, which removes much of the learning-curve objection for teams already writing Kotlin.13 And RSocket-based systems get backpressure that propagates across process boundaries, which no thread model can provide because the problem is a protocol problem rather than a concurrency problem.12,25

Virtual threads solved thread scarcity. They did not solve flow control, and flow control was always the more interesting half of the argument.

A pull-request checklist

Worth pinning to the repository. Each line corresponds to a row above or a rule from earlier sections.

  1. Every publisher created in this change is returned or explicitly subscribed.
  2. No block(), blockFirst(), blockLast() or toIterable() outside test code.
  3. Every remote call has a timeout(), and every retry has a bounded policy with jitter and an idempotency justification.47
  4. Every flatMap over a bounded resource declares an explicit concurrency limit.
  5. Every buffer, window and backpressure operator has an explicit bound and a metric on what it discards.
  6. Streaming endpoints declare a streaming media type and are tested with an explicit cancellation.
  7. Request-scoped state travels in ServerWebExchange or the Reactor Context, never a ThreadLocal.
  8. Error paths produce ProblemDetail bodies and do not leak internal exception text.53
  9. Significant pipelines carry named checkpoint() calls.
  10. New dependencies have been run against BlockHound.28

Primary sources worth reading in full

The Reactive Streams specification is short enough to read in an afternoon and repays it completely; the rules are stated with their rationale, which is where the design becomes intelligible rather than arbitrary.6 The WebFlux overview chapter in the Spring reference documentation is the most balanced short treatment of when not to use the reactive stack that exists anywhere, written by the people who built it.2 The Reactor reference guide’s chapters on schedulers, context propagation and debugging are the operational manual the framework docs assume you have read.24,65 And the RFC 9457 text is worth reading before designing an error contract, because most hand-rolled error schemas are a worse version of it.51

Closing

Reactive Spring is a coherent answer to a specific problem: services whose cost is dominated by waiting, and whose producers can outrun their consumers. Where that description fits — gateways, streaming APIs, aggregation layers, event pipelines — the model gives you flat resource consumption, explicit flow control, and failure behaviour you can reason about at the boundary rather than discover at three in the morning. Where it does not fit, the complexity is real and unrecovered, and virtual threads have made the alternative genuinely good.

The version of this argument that has aged best is the one in Spring’s own documentation, and it is a question rather than a claim: check the dependencies, look for latency, start with the client, measure, and expand only where the numbers justify it.2 That is unusually restrained advice from a framework team about their own framework, and nine years after WebFlux shipped it remains the right way to approach the decision.
