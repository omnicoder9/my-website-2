Spring Framework Web MVC

REST APIs in Spring

An expert guide to REST constraints, HTTP methods and status codes, content negotiation, JSON and XML conversion, HATEOAS, ResponseEntity, response headers, conditional requests, error bodies, and production API design.

Spring Framework 7.0.8Spring HATEOAS 3.1.1HTTP Semantics: RFC 9110Long-form technical articleVancouver references
Abstract. A Spring controller becomes a sound HTTP API only when its Java types, mappings, status codes, headers, and representations preserve protocol semantics. REST is an architectural style defined by constraints—not a synonym for JSON over HTTP. Spring MVC supplies dispatching, annotated request mappings, argument resolution, validation, content negotiation, message conversion, exception handling, conditional-request support, and response construction. Spring HATEOAS adds link and representation-model infrastructure for hypermedia-driven APIs. This article develops the full stack from REST constraints and HTTP semantics through runnable controller patterns, emphasizing representation boundaries, method safety and idempotency, status/body contracts, JSON/XML parity, cache validators, optimistic concurrency, problem details, and evolvable links.

Spring MVC is the Servlet-based web framework in Spring Framework. Its central DispatcherServlet implements a front-controller workflow and delegates request mapping, controller invocation, message conversion, and exception resolution to configurable components. Spring Framework 7.0.8 and Spring HATEOAS 3.1.1 are the current stable references used for the examples.[1][2][3]

1. REST principles

Representational State Transfer is an architectural style for distributed hypermedia systems. Its constraints are client-server separation, stateless interaction, cacheability, a uniform interface, layered systems, and optional code-on-demand. The uniform interface is further constrained by resource identification, manipulation through representations, self-descriptive messages, and hypermedia as the engine of application state.[4]

Client-serverUser-interface and data-management concerns evolve independently.
StatelessEach request contains the information needed to understand it; server-side application session state is not required.
CacheableResponses identify whether and how they may be reused.
Uniform interfaceResources, representations, methods, metadata, and links use general Web semantics.
Layered systemA client interacts with the immediate layer without requiring knowledge of the full component topology.
Code-on-demandAn optional constraint allowing executable code to extend client functionality.

1.1 Resource is not representation

A resource is the conceptual target identified by a URI: an order, customer, report, or collection. JSON, XML, HAL, and a downloadable document can be different representations of that same resource. The URI identifies the resource; Content-Type identifies the selected representation format; Accept expresses representation preferences.[4][5]

HTTP
GET /api/orders/4d2626fd-6242-4cb7-91bd-258f70875ad8 HTTP/1.1
Host: api.example.net
Accept: application/json
HTTP
GET /api/orders/4d2626fd-6242-4cb7-91bd-258f70875ad8 HTTP/1.1
Host: api.example.net
Accept: application/xml

These requests target one resource and ask for different representation media types. A server may return 406 Not Acceptable when it cannot produce an acceptable representation.[5]

1.2 Uniform interface over RPC-shaped routes

Resource-oriented APIs encode operation semantics primarily in HTTP methods, status codes, headers, and media types. A route such as POST /api/orders/{id}/cancellations creates a cancellation subresource, while POST /cancelOrder hides protocol semantics inside a procedure name. RPC is not inherently invalid, but it should not be mislabeled as REST merely because the payload is JSON.

1.3 Statelessness does not prohibit server state

A stateless interaction constraint does not forbid databases, caches, or durable resources. It means that request interpretation does not depend on hidden conversational state retained from earlier requests. Authentication credentials, conditional headers, pagination cursors, and workflow links can carry the state needed for the current interaction.[4]

1.4 Hypermedia

Hypermedia controls describe available transitions in representations. Instead of constructing every URI from documentation, a client follows typed links such as self, cancel, payment, or next. Spring HATEOAS provides link values, item and collection representation models, assemblers, and controller-aware link builders.[3]

2. HTTP methods

HTTP methods carry standardized semantics. A method is safe when its requested semantics are read-only; a method is idempotent when multiple identical requests have the same intended effect as one. Safety and idempotency concern requested semantics, not incidental logging, metrics, or billing side effects.[5]

MethodSafeIdempotentTypical resource semantics
GETYesYesRetrieve a selected representation
HEADYesYesRetrieve the metadata of a corresponding GET without response content
POSTNoNo guaranteeCreate subordinate state, submit a command, or process content according to target semantics
PUTNoYesCreate or completely replace target resource state with the enclosed representation
PATCHNoNo guaranteeApply a patch document describing partial changes
DELETENoYesRemove the association between target URI and current functionality
OPTIONSYesYesDescribe communication options

2.1 GET and HEAD

GET retrieves a representation and should not be used for state-changing commands. Spring MVC automatically supports HEAD for GET mappings and normally suppresses body transmission while preserving response metadata. It also supplies default OPTIONS handling with an Allow header derived from matching request mappings.[5][6]

2.2 POST

POST semantics are defined by the target resource. For a successful resource creation, 201 Created with a Location header identifying the new resource is the strongest standard contract. If processing is accepted but incomplete, 202 Accepted should identify a status resource or another mechanism for observing completion.[5]

2.3 PUT

PUT requests replacement of the target resource state with the request representation. It is idempotent even if repeated requests produce different audit records or timestamps as incidental effects. A partial DTO named “UpdateRequest” does not automatically make PUT appropriate; if omitted fields retain prior values, the operation is not a complete replacement contract.[5]

2.4 PATCH

PATCH applies a patch document whose media type defines the patch semantics. Unlike PUT, PATCH does not imply complete replacement and is not inherently idempotent. Servers can advertise accepted patch formats with Accept-Patch.[7]

HTTP
PATCH /api/orders/42 HTTP/1.1
Content-Type: application/merge-patch+json
If-Match: "order-42-v7"

{
  "shippingAddress": {
    "city": "Raleigh"
  }
}

2.5 DELETE

DELETE is idempotent at the semantic level: repeated deletion requests converge on the target no longer having its former association. The first response may be 204 and a later one 404; identical status codes are not required for idempotency.[5]

3. Status codes

HTTP status codes describe the result at the protocol layer. The response body can add application-specific details but must not contradict the status. Spring’s HttpStatus enum implements the more general HttpStatusCode abstraction and includes standard and selected extension codes.[5][8]

3.1 Status codes that constrain the body

HEAD responses, 204 No Content, and 304 Not Modified do not carry ordinary response content. Returning a Java object with one of these statuses creates a contradictory API contract; build an empty ResponseEntity instead.[5]

Java
@DeleteMapping("/{id}")
ResponseEntity<Void> delete(
        @PathVariable UUID id) {

    service.delete(id);
    return ResponseEntity.noContent().build();
}

3.2 Status code and body are complementary

A body such as {"success": false} attached to 200 OK forces every intermediary and client to ignore HTTP semantics. Use the correct status code for generic software and a typed response body for domain-specific context.

4. Spring MVC REST processing

Spring MVC maps a request through DispatcherServlet, selects a handler, resolves method arguments, invokes the controller, handles the return value, converts the response body, and resolves exceptions. Annotated controllers are one programming model over that dispatch infrastructure.[2]

4.1 @RestController

@RestController combines @Controller and class-level @ResponseBody. Return values are therefore written to the response through an HttpMessageConverter unless another supported return-value type, such as ResponseEntity, supplies additional response metadata.[9][10]

Java
@RestController
@RequestMapping("/api/orders")
public final class OrderController {

    @GetMapping("/{id}")
    OrderResponse get(
            @PathVariable UUID id) {
        return service.get(id);
    }
}

4.2 Request mappings

@RequestMapping matches by path, method, query parameters, headers, consumed media types, produced media types, and—when configured—API version. Method-specific composed annotations are preferred because an unconstrained @RequestMapping matches every HTTP method.[6]

Java
@PostMapping(
    consumes = {
        MediaType.APPLICATION_JSON_VALUE,
        MediaType.APPLICATION_XML_VALUE
    },
    produces = {
        MediaType.APPLICATION_JSON_VALUE,
        MediaType.APPLICATION_XML_VALUE
    })
ResponseEntity<OrderResponse> create(
        @Valid @RequestBody CreateOrderRequest request) {
    // ...
}

The consumes condition matches request Content-Type; produces participates in negotiation against acceptable response media types. Method-level consumes and produces override rather than extend class-level declarations.[6]

4.3 Request body and validation

@RequestBody asks a message converter to deserialize the request content into the declared Java type. Combined with @Valid, standard Bean Validation is applied; invalid command objects raise MethodArgumentNotValidException by default and are mapped to a 400 response unless customized.[11]

Java
public record CreateOrderRequest(
        @NotBlank String customerReference,
        @NotEmpty List<@Valid LineRequest> lines) {
}

public record LineRequest(
        @NotBlank String sku,
        @Positive int quantity,
        @DecimalMin("0.01") BigDecimal unitPrice) {
}
Use API-specific input modelsDo not deserialize directly into persistence entities. Command DTOs define writable fields, validation, compatibility policy, and security boundaries independently of the database model.

4.4 Response body

A response body is a representation, not a dump of internal state. Return DTOs with stable external names, explicit temporal and numeric formats, documented nullability, and no accidental lazy-loaded associations or secrets. The selected message converter serializes the object according to the negotiated media type.[10][12]

5. Content negotiation

Proactive content negotiation selects a representation using request metadata, most commonly Accept. Spring MVC checks the Accept header by default. Query-parameter negotiation can be configured; path-extension negotiation is discouraged because of ambiguity and reflected-file-download concerns.[13]

5.1 Accept versus Content-Type

HeaderDirectionQuestion answered
Content-TypeRequest or responseWhat media type is this enclosed content?
AcceptRequestWhich response media types can the client accept?
Accept-LanguageRequestWhich natural languages are preferred?
Content-LanguageResponseWhich language is used by this representation?
VaryResponseWhich request headers affected representation selection?

5.2 Quality values and specificity

HTTP
Accept: application/hal+json;q=1.0,
        application/json;q=0.9,
        application/xml;q=0.5

Quality parameters express relative preference. Selection also accounts for specificity, server capabilities, and mapping declarations. An API should not make clients depend on converter registration order when the client sends */*; document a default representation and use explicit produces conditions where representation shape differs.

5.3 Spring MVC configuration

Java
@Configuration(proxyBeanMethods = false)
@EnableWebMvc
class ApiWebConfiguration
        implements WebMvcConfigurer {

    @Override
    public void configureContentNegotiation(
            ContentNegotiationConfigurer configurer) {

        configurer
            .favorParameter(false)
            .defaultContentType(
                MediaType.APPLICATION_JSON);
    }
}

When a response can vary by Accept, send Vary: Accept so shared caches do not reuse a JSON response for an XML request. ResponseEntity provides varyBy() for this purpose.[14]

6. JSON and XML

HttpMessageConverter is the Spring strategy for reading request bodies and writing response bodies. Spring Framework includes converters for byte arrays, strings, resources, forms, JSON, XML, feeds, protocol buffers, and other formats. Server-side converters are used by the request-mapping handler adapter.[12]

6.1 JSON

JSON is a text-based, language-independent structured-data format with objects, arrays, strings, numbers, booleans, and null. Interoperable JSON exchanged outside a closed ecosystem uses UTF-8. The registered media type is application/json.[15]

Spring Framework 7’s JacksonJsonHttpMessageConverter uses Jackson 3’s JsonMapper and supports application/json and structured-syntax-suffix media types such as application/*+json. A custom mapper or builder can be supplied when the API needs specific modules or serialization policy.[16]

JSON
{
  "id": "4d2626fd-6242-4cb7-91bd-258f70875ad8",
  "status": "SUBMITTED",
  "total": 49.90,
  "createdAt": "2026-07-31T18:30:00Z"
}

6.2 XML

XML represents structured documents through elements, attributes, character data, and markup. Spring can read and write XML through Jackson XML, JAXB-based converters, Spring OXM marshalling, or source-oriented converters. The Jackson XML converter defaults to application/xml; the required XML module must be available.[12][17]

XML
<OrderResponse>
  <id>4d2626fd-6242-4cb7-91bd-258f70875ad8</id>
  <status>SUBMITTED</status>
  <total>49.90</total>
  <createdAt>2026-07-31T18:30:00Z</createdAt>
</OrderResponse>

6.4 Parser security and limits

Request parsing is an untrusted-input boundary. Apply request-size limits, nesting limits where supported, numeric constraints, validation, and safe XML parser configuration. Do not enable external entity or network resolution for untrusted XML. Reject unsupported media types before invoking business logic.

7. ResponseEntity

ResponseEntity<T> extends HttpEntity<T> with an HTTP status code. Spring MVC writes its headers and converts its body through the configured message converters. Static builders support common statuses and headers including Location, ETag, Last-Modified, Cache-Control, Allow, and Vary.[10][14]

7.1 Creation response

Java
@PostMapping
ResponseEntity<OrderResponse> create(
        @Valid @RequestBody CreateOrderRequest request,
        UriComponentsBuilder uriBuilder) {

    OrderResponse created =
            service.create(request);

    URI location = uriBuilder
            .path("/api/orders/{id}")
            .buildAndExpand(created.id())
            .toUri();

    return ResponseEntity
            .created(location)
            .eTag(etag(created.version()))
            .body(created);
}

7.2 Optional lookup

Java
@GetMapping("/{id}")
ResponseEntity<OrderResponse> get(
        @PathVariable UUID id) {

    return ResponseEntity.of(
            service.find(id));
}

ResponseEntity.of(Optional) returns 200 with the present body or 404 with an empty body. Use an explicit problem-detail response instead when the API contract requires a typed error representation.[18]

7.3 Custom headers

Java
return ResponseEntity.ok()
    .header("X-Request-Id", requestId)
    .header(
        HttpHeaders.CONTENT_LANGUAGE,
        locale.toLanguageTag())
    .varyBy(
        HttpHeaders.ACCEPT,
        HttpHeaders.ACCEPT_LANGUAGE)
    .body(response);
Headers are protocol metadataDo not move cache policy, concurrency validators, authentication challenges, pagination links, or retry instructions into arbitrary JSON fields when standard HTTP headers already define those semantics.

8. Response headers

8.1 Location

Location identifies another URI associated with the response. Its most common API use is identifying a newly created resource in a 201 response. Generate it from routing configuration or link builders instead of concatenating host and path strings.

8.2 Cache-Control

Cache directives define response reuse. Spring’s CacheControl builder supports common response directives such as max-age, no-store, public/private caching, and revalidation. Efficient cache behavior combines freshness policy with validators such as ETag or Last-Modified.[19]

Java
return ResponseEntity.ok()
    .cacheControl(
        CacheControl
            .maxAge(Duration.ofMinutes(5))
            .cachePrivate())
    .eTag(etag(order.version()))
    .lastModified(order.updatedAt())
    .body(order);

8.3 ETag and conditional requests

An ETag is an opaque validator for a selected representation. If-None-Match supports cache revalidation; If-Match supports lost-update prevention. Strong validators are appropriate when byte-level representation identity or update preconditions require exact equality. Weak validators are sufficient for semantically equivalent cache representations but cannot satisfy every precondition use.[5][20]

Spring MVC can compare application-generated ETags and timestamps against conditional headers through WebRequest.checkNotModified(). For GET and HEAD, a successful check yields 304; for conditional state-changing methods, failed preconditions can yield 412.[21]

Java
@GetMapping("/{id}")
ResponseEntity<OrderResponse> get(
        @PathVariable UUID id,
        WebRequest request) {

    OrderResponse order = service.get(id);
    String tag = etag(order.version());
    long modified =
            order.updatedAt().toEpochMilli();

    if (request.checkNotModified(tag, modified)) {
        return null;
    }

    return ResponseEntity.ok()
        .eTag(tag)
        .lastModified(modified)
        .cacheControl(
            CacheControl.maxAge(
                Duration.ofMinutes(1)))
        .varyBy(HttpHeaders.ACCEPT)
        .body(order);
}

8.4 Conditional update

Java
@PutMapping("/{id}")
ResponseEntity<OrderResponse> replace(
        @PathVariable UUID id,
        @RequestHeader(HttpHeaders.IF_MATCH)
        String ifMatch,
        @Valid @RequestBody ReplaceOrderRequest request) {

    long expectedVersion =
            parseOrderVersion(ifMatch);

    OrderResponse replaced =
            service.replace(
                id,
                expectedVersion,
                request);

    return ResponseEntity.ok()
        .eTag(etag(replaced.version()))
        .body(replaced);
}

A stale validator should map to 412 Precondition Failed, whereas an application conflict not expressed as an HTTP precondition often maps to 409 Conflict.

8.5 Allow, Accept-Patch, and Retry-After

Allow lists supported methods for a target in 405 responses and OPTIONS metadata. Accept-Patch advertises supported patch-document media types. Retry-After can advise clients when to retry after 429 or 503, but clients still need bounded retry and idempotency policy.[5][7]

9. HATEOAS with Spring

Spring HATEOAS defines Link, RepresentationModel, EntityModel, CollectionModel, PagedModel, assemblers, and MVC/WebFlux link builders. EntityModel<T> wraps one payload with links; CollectionModel<T> represents a collection plus collection-level links.[3][22]

9.1 Representation-model assembler

Java
@Component
final class OrderModelAssembler
        implements RepresentationModelAssembler<
            OrderResponse,
            EntityModel<OrderResponse>> {

    @Override
    public EntityModel<OrderResponse> toModel(
            OrderResponse order) {

        EntityModel<OrderResponse> model =
                EntityModel.of(
                    order,
                    linkTo(
                        methodOn(OrderHypermediaController.class)
                            .get(order.id()))
                        .withSelfRel(),
                    linkTo(
                        methodOn(OrderHypermediaController.class)
                            .all())
                        .withRel("orders"));

        if (order.status()
                == OrderStatus.SUBMITTED) {
            model.add(
                linkTo(
                    methodOn(OrderHypermediaController.class)
                        .cancel(order.id()))
                    .withRel("cancel"));
        }

        return model;
    }
}

9.2 Hypermedia controller

Java
@RestController
@RequestMapping(
    path = "/api/hypermedia/orders",
    produces = MediaTypes.HAL_JSON_VALUE)
final class OrderHypermediaController {
    private final OrderService service;
    private final OrderModelAssembler assembler;

    OrderHypermediaController(
            OrderService service,
            OrderModelAssembler assembler) {
        this.service = service;
        this.assembler = assembler;
    }

    @GetMapping("/{id}")
    EntityModel<OrderResponse> get(
            @PathVariable UUID id) {
        return assembler.toModel(
                service.get(id));
    }

    @GetMapping
    CollectionModel<EntityModel<OrderResponse>>
            all() {

        List<EntityModel<OrderResponse>> content =
                service.all().stream()
                    .map(assembler::toModel)
                    .toList();

        return CollectionModel.of(
            content,
            linkTo(
                methodOn(OrderHypermediaController.class)
                    .all())
                .withSelfRel());
    }

    @PostMapping("/{id}/cancellations")
    ResponseEntity<Void> cancel(
            @PathVariable UUID id) {
        service.cancel(id);
        return ResponseEntity.noContent().build();
    }
}

WebMvcLinkBuilder derives links from controller mappings and current request context, reducing duplicated URI strings. Forwarded-header handling must be configured correctly when an application sits behind trusted proxies so generated absolute links use the public scheme, host, and prefix.[3][23]

10. Error response bodies

RFC 9457 defines machine-readable problem details with JSON and XML media types. Standard members include type, status, title, detail, and instance, with extension members permitted. The problem type URI is the primary machine identifier, not the human-readable title.[24]

Spring MVC supports ProblemDetail, ErrorResponse, ErrorResponseException, and ResponseEntityExceptionHandler. Jackson JSON and XML converters favor application/problem+json and application/problem+xml for ProblemDetail responses.[25]

10.1 Controller advice

Java
@RestControllerAdvice
final class ApiExceptionHandler
        extends ResponseEntityExceptionHandler {

    @ExceptionHandler(OrderNotFoundException.class)
    ProblemDetail handleNotFound(
            OrderNotFoundException exception,
            HttpServletRequest request) {

        ProblemDetail problem =
                ProblemDetail.forStatus(
                    HttpStatus.NOT_FOUND);

        problem.setType(
            URI.create(
                "https://api.example.net/problems/"
                + "order-not-found"));
        problem.setTitle("Order not found");
        problem.setDetail(exception.getMessage());
        problem.setInstance(
            URI.create(request.getRequestURI()));
        problem.setProperty(
            "orderId",
            exception.orderId());

        return problem;
    }

    @ExceptionHandler(StaleOrderVersionException.class)
    ProblemDetail handleStale(
            StaleOrderVersionException exception) {

        ProblemDetail problem =
                ProblemDetail.forStatus(
                    HttpStatus.PRECONDITION_FAILED);

        problem.setType(
            URI.create(
                "https://api.example.net/problems/"
                + "stale-order-version"));
        problem.setTitle(
                "The order has changed");
        problem.setDetail(
                "Retrieve the current representation "
                + "and retry with its ETag.");

        return problem;
    }
}

10.2 Validation extensions

Validation failures can extend the problem object with a stable array of field pointers, codes, and messages. Do not expose rejected secrets, database details, stack traces, class names, or internal exception messages. Internationalize human-readable fields independently of machine-readable problem types and codes.[24][25]

JSON
{
  "type": "https://api.example.net/problems/validation",
  "title": "Request validation failed",
  "status": 400,
  "instance": "/api/orders",
  "errors": [
    {
      "pointer": "/lines/0/quantity",
      "code": "Positive",
      "message": "must be greater than zero"
    }
  ]
}

11.2 Controller

Java
@RestController
@RequestMapping(
    path = "/api/orders",
    produces = {
        MediaType.APPLICATION_JSON_VALUE,
        MediaType.APPLICATION_XML_VALUE
    })
public final class OrderController {
    private final OrderService service;

    public OrderController(OrderService service) {
        this.service = service;
    }

    @GetMapping("/{id}")
    public ResponseEntity<OrderResponse> get(
            @PathVariable UUID id,
            WebRequest webRequest) {

        OrderResponse order = service.get(id);
        String tag = etag(order.version());
        long modified =
                order.updatedAt().toEpochMilli();

        if (webRequest.checkNotModified(
                tag,
                modified)) {
            return null;
        }

        return ResponseEntity.ok()
            .eTag(tag)
            .lastModified(modified)
            .cacheControl(
                CacheControl.maxAge(
                    Duration.ofSeconds(30)))
            .varyBy(HttpHeaders.ACCEPT)
            .body(order);
    }

    @PostMapping(consumes = {
        MediaType.APPLICATION_JSON_VALUE,
        MediaType.APPLICATION_XML_VALUE
    })
    public ResponseEntity<OrderResponse> create(
            @Valid @RequestBody
            CreateOrderRequest request,
            UriComponentsBuilder uris) {

        OrderResponse created =
                service.create(request);

        URI location = uris
                .path("/api/orders/{id}")
                .buildAndExpand(created.id())
                .toUri();

        return ResponseEntity.created(location)
            .eTag(etag(created.version()))
            .varyBy(HttpHeaders.ACCEPT)
            .body(created);
    }

    @PutMapping(
        path = "/{id}",
        consumes = {
            MediaType.APPLICATION_JSON_VALUE,
            MediaType.APPLICATION_XML_VALUE
        })
    public ResponseEntity<OrderResponse> replace(
            @PathVariable UUID id,
            @RequestHeader(HttpHeaders.IF_MATCH)
            String ifMatch,
            @Valid @RequestBody
            ReplaceOrderRequest request) {

        OrderResponse replaced =
                service.replace(
                    id,
                    parseOrderVersion(ifMatch),
                    request);

        return ResponseEntity.ok()
            .eTag(etag(replaced.version()))
            .varyBy(HttpHeaders.ACCEPT)
            .body(replaced);
    }

    @DeleteMapping("/{id}")
    public ResponseEntity<Void> delete(
            @PathVariable UUID id,
            @RequestHeader(HttpHeaders.IF_MATCH)
            String ifMatch) {

        service.delete(
            id,
            parseOrderVersion(ifMatch));

        return ResponseEntity.noContent().build();
    }

    private static String etag(long version) {
        return "\"order-v" + version + "\"";
    }
}

The controller delegates business state transitions to the service, performs representation and protocol work, never exposes persistence entities, supports explicit JSON/XML negotiation, uses strong version-based validators for updates, and attaches cache metadata only to safe reads.

12. Testing REST APIs

Spring MVC tests should verify protocol contracts, not only deserialized bodies: method and path mapping, status, Content-Type, Location, ETag, Vary, cache directives, problem media types, validation shape, conditional requests, and JSON/XML representation equivalence. MockMvc exercises Spring MVC request handling through the DispatcherServlet with mock Servlet request and response objects and no running server.[26]

12.1 MockMvc

Java
class OrderControllerTest {
    private OrderService service;
    private MockMvc mvc;

    @BeforeEach
    void setUp() {
        service = mock(OrderService.class);

        mvc = MockMvcBuilders
            .standaloneSetup(
                new OrderController(service))
            .setControllerAdvice(
                new ApiExceptionHandler())
            .build();
    }

    @Test
    void returnsJsonAndValidators() throws Exception {
        OrderResponse order = fixture();

        given(service.get(order.id()))
            .willReturn(order);

        mvc.perform(
            get("/api/orders/{id}", order.id())
                .accept(MediaType.APPLICATION_JSON))
            .andExpect(status().isOk())
            .andExpect(
                content().contentTypeCompatibleWith(
                    MediaType.APPLICATION_JSON))
            .andExpect(
                header().string(
                    HttpHeaders.ETAG,
                    "\"order-v7\""))
            .andExpect(
                header().string(
                    HttpHeaders.VARY,
                    containsString(
                        HttpHeaders.ACCEPT)))
            .andExpect(
                jsonPath("$.status")
                    .value("SUBMITTED"));
    }
}

Java
mvc.perform(

        .header(

Use full server tests for proxy headers, compression, security filters, CORS, container limits, streaming, and deployed serialization configuration. Contract tests should pin public media types and error schemas without overfitting irrelevant field order.

13. Diagnostics

13.1 406 Not Acceptable

Compare the request’s Accept ranges with the handler’s produces condition and converter-supported media types. Confirm that the required Jackson or XML module is present and that the body type is writable.

13.2 415 Unsupported Media Type

Check request Content-Type, handler consumes, converter availability, charset parameters, and whether a body was sent with the expected syntax.

13.3 Body is unreadable

Distinguish malformed JSON/XML from validation failure. Conversion errors occur before Bean Validation. Return a generic, safe problem detail and log parser diagnostics with request correlation rather than echoing sensitive payloads.

13.4 Wrong representation selected

Inspect Accept quality values, mapping specificity, default content type, registered converters, and Vary. Avoid relying on URL filename extensions.

13.5 Concurrent update overwrites state

Require If-Match for mutation, compare it with a strong server validator, perform the version check atomically in the persistence layer, and return 412 when stale.

13.6 HATEOAS links use an internal host

Configure trusted forwarded-header processing at the framework or container boundary. Never trust arbitrary forwarded headers from untrusted direct clients.[3]

14. Expert practices

14.1 Design from HTTP semantics

Choose the resource model, method, preconditions, status, headers, and representation together. Do not begin with controller method names and retrofit HTTP afterward.

14.2 Separate API and persistence models

DTOs prevent accidental fields, cycles, lazy loading, mass assignment, and storage-driven compatibility breaks. Map deliberately at the application boundary.

14.3 Make status/body contracts exact

Document which success and error statuses can occur, whether a body is present, its media type, and required headers. Treat 204, 304, and HEAD body rules as invariants.

14.4 Advertise only tested media types

JSON and XML support are separate public contracts. Verify round trips, validation, errors, dates, decimals, links, and empty collections in every format.

14.5 Use validators and cache policy

Send Cache-Control, ETag or Last-Modified, and Vary where appropriate. Conditional requests reduce bandwidth and can prevent lost updates.

14.6 Make links state-aware

Provide transitions that are valid for the current resource and caller, use registered or documented link relations, and still enforce authorization server-side.

14.7 Standardize problem details

Use stable type URIs and extension codes, localize human text, preserve request correlation, and redact implementation details.

14.8 Design retries explicitly

Idempotent method semantics help, but POST retries often require an idempotency key and durable deduplication. Never retry state-changing requests blindly after ambiguous network failure.

14.9 Observe protocol behavior

Record method, normalized route, status, selected media type, latency, request and response size, validation category, and cache outcome. Avoid high-cardinality raw paths and sensitive bodies.

15. Summary

A robust Spring REST API aligns three systems:

  • REST supplies architectural constraints: stateless messages, cacheability, uniform interfaces, layered systems, and hypermedia.
  • HTTP supplies method semantics, status codes, representation metadata, caching, preconditions, and standard headers.
  • Spring MVC supplies request dispatch, annotated mappings, body conversion, negotiation, validation, exception handling, conditional requests, and response construction.
  • @RestController makes return values response bodies through message conversion.
  • consumes constrains request content; produces participates in response negotiation.
  • JSON and XML are representations of resources, not distinct resources by default.
  • ResponseEntity expresses status, headers, and body as one protocol-level return value.
  • ETag, Last-Modified, Cache-Control, Vary, Location, Allow, and Retry-After carry semantics that do not belong in arbitrary payload fields.
  • Spring HATEOAS adds links and representation models for discoverable application-state transitions.
  • RFC 9457 problem details give errors a standard JSON/XML envelope without redefining HTTP status semantics.

Diagnose API behavior by tracing one request: Which resource is targeted? What semantics does the method declare? What request media type was received? Which response types are acceptable? Which mapping and converter were selected? What status and body contract applies? Which validators, cache directives, and links were emitted? Answering those questions turns a controller endpoint into an explicit HTTP protocol rather than an accidental serialization surface.
