Spring Framework Data Access

JDBC with Spring

An expert guide to the JDBC contract, JdbcTemplate, NamedParameterJdbcTemplate, row mapping, generated keys, exception translation, transaction participation, and high-throughput batch operations.

Target: Spring Framework 7.0.8 Java 17+ baseline Long-form technical article Vancouver references
Abstract. Spring JDBC is a workflow abstraction over the standard JDBC API, not an object-relational mapper and not a replacement SQL language. The application remains responsible for SQL, parameter values, result-shape semantics, transaction boundaries, and domain mapping. Spring takes responsibility for obtaining transaction-aware connections, creating and closing statements and result sets, iterating results, invoking narrow callbacks, and translating checked SQLException instances into a portable unchecked hierarchy. This article develops that model from raw JDBC through JdbcTemplate and NamedParameterJdbcTemplate, then examines row-mapping contracts, single-result semantics, generated keys, exception translation, batching, transaction integration, diagnostics, and production design.

Spring Framework 7.0.x is the current production line, with 7.0.8 the stable reference version used here. Spring 7 retains a Java 17 baseline. The core JDBC APIs remain deliberately close to SQL and JDBC, while newer conveniences such as JdbcClient delegate to the same template infrastructure; this article concentrates on the requested template APIs because they remain the execution foundation and expose the full callback model.[1][2]

1. JDBC and Spring JDBC: control remains explicit

Standard JDBC defines connection acquisition, prepared and callable statements, positional parameters, result sets, update counts, generated keys, warnings, SQL state, vendor error codes, and batch execution. A correct raw JDBC operation must close the ResultSet, statement, and connection along every path, while preserving transaction ownership and translating low-level failures into application semantics. Spring’s JDBC layer centralizes this lifecycle while leaving SQL and data interpretation to the application.[3]

Java 
static Optional<Account> findRaw(
        DataSource dataSource,
        long id) throws SQLException {

    String sql = """
        select id, external_id, email, status,
               balance, created_at
        from account
        where id = ?
        """;

    try (Connection connection =
             dataSource.getConnection();
         PreparedStatement statement =
             connection.prepareStatement(sql)) {

        statement.setLong(1, id);

        try (ResultSet resultSet =
                 statement.executeQuery()) {

            if (!resultSet.next()) {
                return Optional.empty();
            }

            Account account =
                    mapAccount(resultSet);

            if (resultSet.next()) {
                throw new SQLException(
                        "Expected one row for id " + id);
            }

            return Optional.of(account);
        }
    }
}

The raw version is not conceptually wrong. It is repetitive and easy to make transactionally wrong: direct DataSource.getConnection() calls do not automatically participate in a connection already bound by Spring transaction management. Spring’s template code obtains and releases connections through transaction-aware infrastructure, executes a fixed workflow, and delegates only the operation-specific parts to callbacks.[4][5]

1 Obtain the appropriate connection from the configured DataSource.
2 Reuse the thread-bound connection when a Spring transaction is active.
3 Create and configure the JDBC statement.
4 Bind parameters supplied by application code.
5 Execute the operation and invoke mapping or extraction callbacks.
6 Translate SQLException into DataAccessException.
7 Close result-set and statement resources and release the connection according to transaction ownership.

1.1 Division of responsibility

Spring JDBC is therefore a template-method and callback architecture. It removes lifecycle duplication without hiding the database. SQL plans, indexes, lock behavior, isolation anomalies, server-side limits, and driver capabilities remain operational concerns.

2.2 Template and transaction-manager beans

Both templates are thread-safe after configuration and should normally be shared. NamedParameterJdbcTemplate wraps a classic template and delegates execution after converting named parameters to JDBC placeholders. A JdbcTransactionManager manages one DataSource and adds JDBC exception translation to commit and rollback failures.[5][6][7]

Java 
@Configuration(proxyBeanMethods = false)
@EnableTransactionManagement
class JdbcConfiguration {

    // The DataSource bean is environment-specific and is normally
    // supplied by a pool, application server, or Boot auto-configuration.

    @Bean
    JdbcTemplate jdbcTemplate(DataSource dataSource) {
        JdbcTemplate template =
                new JdbcTemplate(dataSource);

        template.setFetchSize(500);
        return template;
    }

    @Bean
    NamedParameterJdbcTemplate namedJdbcTemplate(
            JdbcTemplate jdbcTemplate) {

        return new NamedParameterJdbcTemplate(
                jdbcTemplate);
    }

    @Bean
    JdbcTransactionManager transactionManager(
            DataSource dataSource) {

        return new JdbcTransactionManager(dataSource);
    }
}

Statement settings such as fetch size, maximum rows, and query timeout are applied by the template to created statements. Their effective behavior is ultimately driver- and database-dependent. Avoid global values chosen without measuring every query class; a reporting query, point lookup, and batch update can require different policies.[5]

3. JdbcTemplate

JdbcTemplate is the central delegate in org.springframework.jdbc.core. It supports static statements, prepared statements, callable statements, scalar queries, row mapping, aggregate extraction, updates, generated keys, batch operations, streams, and low-level callbacks. It catches JDBC exceptions and translates them through an SQLExceptionTranslator. Once configured, an instance is reusable and thread-safe.[4][5]

3.1 Inserts, updates, and deletes

Java 
@Repository
final class AccountWriteRepository {
    private final JdbcTemplate jdbc;

    AccountWriteRepository(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    int changeEmail(long accountId, String email) {
        return jdbc.update(
            """
            update account
            set email = ?
            where id = ?
            """,
            email,
            accountId);
    }

    boolean delete(long accountId) {
        int affected = jdbc.update(
                "delete from account where id = ?",
                accountId);

        return affected == 1;
    }
}

The returned update count is a concurrency and integrity signal, not merely a metric. A command intended to change exactly one row should verify that count. Zero can mean a missing row, stale version, unmet guard, or authorization condition; a count greater than one can reveal a defective predicate.

3.2 Scalar queries

Java 
long countActiveAccounts() {
    Long count = jdbc.queryForObject(
            """
            select count(*)
            from account
            where status = ?
            """,
            Long.class,
            AccountStatus.ACTIVE.name());

    return Objects.requireNonNull(count);
}

queryForObject means “exactly one result row” for row queries. Zero rows lead to EmptyResultDataAccessException; more than one produces IncorrectResultSizeDataAccessException. An aggregate such as count(*) normally returns one row even when the count is zero, so its cardinality contract differs from a point lookup.[8][9]

3.3 Optional lookup without exception-driven absence

Java 
Optional<Account> findById(long id) {
    List<Account> rows = jdbc.query(
            """
            select id, external_id, email, status,
                   balance, created_at
            from account
            where id = ?
            """,
            ACCOUNT_MAPPER,
            id);

    Account single =
            DataAccessUtils.singleResult(rows);

    return Optional.ofNullable(single);
}

DataAccessUtils.singleResult() returns null for an empty collection and rejects multiple elements. This makes “zero or one” explicit while preserving detection of a broken uniqueness assumption.[10]

3.4 Generated keys

A GeneratedKeyHolder stores keys returned by an insert. Create a new holder for each operation. The JDBC driver must support generated-key retrieval, and the key-column names should be specified where the API and database require them.[11]

Java 
long insert(AccountDraft draft) {
    String sql = """
        insert into account (
            external_id, email, status,
            balance, created_at
        )
        values (?, ?, ?, ?, ?)
        """;

    KeyHolder keys = new GeneratedKeyHolder();

    int affected = jdbc.update(connection -> {
        PreparedStatement statement =
                connection.prepareStatement(
                    sql,
                    new String[] {"id"});

        statement.setString(
                1,
                draft.externalId().toString());
        statement.setString(2, draft.email());
        statement.setString(
                3,
                draft.status().name());
        statement.setBigDecimal(
                4,
                draft.balance());
        statement.setTimestamp(
                5,
                Timestamp.from(draft.createdAt()));

        return statement;
    }, keys);

    if (affected != 1) {
        throw new IncorrectUpdateSemanticsDataAccessException(
                "Expected one inserted account, got "
                + affected);
    }

    Long id = keys.getKeyAs(Long.class);
    if (id == null) {
        throw new DataRetrievalFailureException(
                "Database returned no account id");
    }

    return id;
}

3.6 Query streams must be closed

queryForStream() returns a closeable stream backed by JDBC resources. It must be used in try-with-resources so that early termination, mapping failure, or short-circuiting does not leak the result set and statement.[5]

Java 
try (Stream<Account> accounts =
         jdbc.queryForStream(
             """
             select id, external_id, email, status,
                    balance, created_at
             from account
             order by id
             """,
             ACCOUNT_MAPPER)) {

    accounts
        .filter(account ->
                account.balance()
                       .signum() > 0)
        .forEach(exporter::write);
}
A Java Stream is not automatically a database cursor policy The driver may buffer rows, require a transaction for cursor-based fetching, or interpret fetch size differently. Verify memory, network, and transaction behavior with the selected driver and database.

4. NamedParameterJdbcTemplate

NamedParameterJdbcTemplate accepts parameters such as :accountId and rewrites them into positional JDBC placeholders at execution time. It delegates actual execution to a wrapped JdbcTemplate, supports collection expansion, and exposes the underlying classic operations for cases outside its dedicated interface. It is thread-safe after configuration.[6]

4.1 Named parameters as executable documentation

Java 
int updateStatus(
        long accountId,
        AccountStatus expected,
        AccountStatus replacement) {

    String sql = """
        update account
        set status = :replacement
        where id = :accountId
          and status = :expected
        """;

    MapSqlParameterSource parameters =
            new MapSqlParameterSource()
                .addValue(
                    "accountId",
                    accountId,
                    Types.BIGINT)
                .addValue(
                    "expected",
                    expected.name(),
                    Types.VARCHAR)
                .addValue(
                    "replacement",
                    replacement.name(),
                    Types.VARCHAR);

    return namedJdbc.update(sql, parameters);
}

Named parameters reduce positional coupling when a statement has repeated values or many columns. They do not change database parsing semantics: the final statement is still a JDBC prepared statement with positional values, and identifiers or SQL fragments cannot be bound as values.

4.2 Parameter-source choices

The named-parameter package provides these sources and utilities specifically for template operations. Use explicit SQL types when a null value leaves the driver unable to infer the intended type or when a vendor type requires a type name.[12]

4.3 Collection expansion

Java 
List<Account> findByIds(Collection<Long> ids) {
    if (ids.isEmpty()) {
        return List.of();
    }

    return namedJdbc.query(
        """
        select id, external_id, email, status,
               balance, created_at
        from account
        where id in (:ids)
        order by id
        """,
        Map.of("ids", ids),
        ACCOUNT_MAPPER);
}

The template expands a list into the required number of ? placeholders. Branch explicitly for an empty collection because an empty SQL IN list is not a portable value-binding construct. Large lists can exceed database parameter limits or produce unstable plans; temporary tables, array parameters, table-valued parameters, or chunked queries may be more appropriate depending on the database.[6]

4.4 Generated keys with named parameters

Java 
long insertNamed(AccountDraft draft) {
    String sql = """
        insert into account (
            external_id, email, status,
            balance, created_at
        )
        values (
            :externalId, :email, :status,
            :balance, :createdAt
        )
        """;

    SqlParameterSource parameters =
            new MapSqlParameterSource()
                .addValue(
                    "externalId",
                    draft.externalId().toString())
                .addValue(
                    "email",
                    draft.email())
                .addValue(
                    "status",
                    draft.status().name())
                .addValue(
                    "balance",
                    draft.balance())
                .addValue(
                    "createdAt",
                    Timestamp.from(
                        draft.createdAt()));

    KeyHolder keys = new GeneratedKeyHolder();

    int affected = namedJdbc.update(
            sql,
            parameters,
            keys,
            new String[] {"id"});

    if (affected != 1) {
        throw new IncorrectUpdateSemanticsDataAccessException(
                "Expected one inserted row");
    }

    Long id = keys.getKeyAs(Long.class);
    return Objects.requireNonNull(id);
}

5. RowMapper

RowMapper<T> maps the current row of a ResultSet to one object. The template advances the cursor and closes the result set; a mapper must not call next() or close it. Mappers are normally stateless and reusable. A checked SQLException can be thrown directly from the callback and will be translated by the template.[13]

5.1 Explicit custom mapping

Java 
private static final RowMapper<Account>
        ACCOUNT_MAPPER = (resultSet, rowNumber) -> {

    Timestamp created =
            resultSet.getTimestamp("created_at");

    return new Account(
        resultSet.getLong("id"),
        UUID.fromString(
            resultSet.getString("external_id")),
        resultSet.getString("email"),
        AccountStatus.valueOf(
            resultSet.getString("status")),
        resultSet.getBigDecimal("balance"),
        created.toInstant());
};

Explicit mapping is verbose but makes column aliases, null semantics, enum conversion, timestamp policy, and type adaptation visible. Reuse one mapper per stable projection, and select columns explicitly rather than coupling the mapping to select *.

5.2 SQL null and primitive getters

Primitive JDBC getters such as getLong() return a primitive default when the database value is SQL NULL; wasNull() must then be checked. For nullable numeric values, getObject(column, Wrapper.class) or an explicit null check is usually clearer. A database NULL should be represented deliberately in the Java model rather than silently becoming zero or false.

Java 
Long managerId =
        resultSet.getObject(
                "manager_id",
                Long.class);

5.3 Automatic mapping implementations

BeanPropertyRowMapper creates a bean using a no-argument constructor and maps columns to setters, including underscore-to-camel-case matching. DataClassRowMapper additionally maps constructor parameters for Java records, Kotlin data classes, and similar constructor-oriented classes. Both prioritize convenience over maximum performance; custom mappers remain the most explicit and efficient choice for hot paths or nontrivial conversions.[14][15]

Java 
public record AccountSummary(
        long id,
        String email,
        BigDecimal balance) {
}

private static final RowMapper<AccountSummary>
        SUMMARY_MAPPER =
        DataClassRowMapper.newInstance(
                AccountSummary.class);

List<AccountSummary> summaries =
        jdbc.query(
            """
            select id, email, balance
            from account
            order by id
            """,
            SUMMARY_MAPPER);

Automatic mapping relies on a naming contract between SQL columns and Java properties or constructor parameters. Use aliases when database names differ, and test migrations that rename columns because a mapper can otherwise fail only at runtime.

5.4 One row per object is not always the right shape

A join that repeats parent columns for each child cannot be faithfully mapped to one aggregate per row without duplication. Use a ResultSetExtractor to consume the complete result set and group rows by parent identity. A ResultSetExtractor owns aggregate construction but not result-set closing.[16]

Java 
List<AccountWithTags> findAccountsWithTags() {
    return jdbc.query(
        """
        select a.id, a.email,
               t.name as tag_name
        from account a
        left join account_tag t
          on t.account_id = a.id
        order by a.id, t.name
        """,
        resultSet -> {
            Map<Long, MutableAccountAggregate> grouped =
                    new LinkedHashMap<>();

            while (resultSet.next()) {
                long id = resultSet.getLong("id");
                String email =
                        resultSet.getString("email");

                MutableAccountAggregate aggregate =
                        grouped.computeIfAbsent(
                            id,
                            ignored ->
                                new MutableAccountAggregate(
                                    id,
                                    email));

                String tag =
                        resultSet.getString("tag_name");

                if (tag != null) {
                    aggregate.tags().add(tag);
                }
            }

            return grouped.values().stream()
                    .map(MutableAccountAggregate::freeze)
                    .toList();
        });
}

JDBC values are extracted before computeIfAbsent() because its mapping function cannot declare SQLException. The outer extractor may throw SQLException directly and relies on the template for translation. MutableAccountAggregate is an application-owned builder that accumulates tags and produces an immutable AccountWithTags.

5.5 RowCallbackHandler

Use a row callback when the result is processed for side effects rather than accumulated into a returned list: writing an export, feeding a digest, or building an external index. The handler is called once per row and should not advance or close the result set.[17]

6. Exception translation

Spring’s DataAccessException is the root of an unchecked hierarchy designed to represent data-access failure categories independently of JDBC, JPA, or another persistence technology. This lets service code react to semantic classes such as integrity violation, transient concurrency failure, resource failure, bad SQL, or incorrect result size without parsing vendor messages.[18]

6.1 SQLExceptionTranslator

SQLExceptionTranslator converts a JDBC SQLException into a Spring exception using the operation description, SQL text when available, SQL state, vendor code, and exception subtype. Since Spring Framework 6.0, the default is SQLExceptionSubclassTranslator, which recognizes JDBC 4 exception subclasses and falls back to SQL-state translation. Vendor-code translation remains available through SQLErrorCodeSQLExceptionTranslator when greater database-specific precision is required.[19][20]

DataIntegrityViolationExceptionConstraint or data-integrity failure.
DuplicateKeyExceptionNarrow unique or primary-key violation; often catch the broader integrity exception.
TransientDataAccessExceptionA retry may succeed without changing the operation itself.
DataAccessResourceFailureExceptionThe database resource or connection failed.
BadSqlGrammarExceptionInvalid SQL or resource usage translated from JDBC details.
IncorrectResultSizeDataAccessExceptionObserved cardinality violated the caller’s contract.

6.2 Handle semantics, not messages

Java 
AccountId register(AccountDraft draft) {
    try {
        return new AccountId(
                repository.insertNamed(draft));
    }
    catch (DuplicateKeyException ex) {
        throw new AccountAlreadyExistsException(
                draft.email(),
                ex);
    }
}

Spring’s own documentation advises considering the broader DataIntegrityViolationException instead of relying only on DuplicateKeyException, because integrity failures have wider causes and translator precision depends on the driver and database. Catch at a boundary where a stable domain meaning exists; otherwise let the translated exception propagate to transaction management and centralized failure handling.[21]

6.3 Translation does not imply retry policy

A transient exception category indicates that retry may be meaningful, not that immediate blind retry is safe. Retrying requires an idempotent unit of work, a new transaction where appropriate, bounded attempts, backoff, observability, and awareness of external side effects. Do not retry syntax errors, integrity violations, or a transaction that has already been marked rollback-only.

6.4 Custom translator

Java 
@Bean
JdbcTemplate jdbcTemplate(DataSource dataSource) {
    JdbcTemplate template =
            new JdbcTemplate(dataSource);

    SQLErrorCodeSQLExceptionTranslator translator =
            new SQLErrorCodeSQLExceptionTranslator(
                    dataSource);

    translator.setCustomTranslator(
        (task, sql, exception) -> {
            if ("45001".equals(
                    exception.getSQLState())) {
                return new DataIntegrityViolationException(
                        task + ": policy violation",
                        exception);
            }
            return null; // Continue normal fallback translation.
        });

    template.setExceptionTranslator(translator);
    return template;
}

Custom translation belongs in shared infrastructure and should use stable vendor codes or SQL states. Message-text matching is fragile across database versions, localization, proxies, and drivers.

7. Batch operations

JDBC batching groups repeated executions—usually of one prepared statement—so the driver can reduce client/server round trips or apply vendor-specific optimizations. Spring exposes callback-based, list-based, named-parameter, and chunked batch APIs. The driver and database determine whether a batch is rewritten, pipelined, or executed command by command.[22][3]

7.1 BatchPreparedStatementSetter

Java 
int[] insertBatch(List<AccountDraft> drafts) {
    String sql = """
        insert into account (
            external_id, email, status,
            balance, created_at
        )
        values (?, ?, ?, ?, ?)
        """;

    return jdbc.batchUpdate(
        sql,
        new BatchPreparedStatementSetter() {
            @Override
            public void setValues(
                    PreparedStatement statement,
                    int index) throws SQLException {

                AccountDraft draft =
                        drafts.get(index);

                statement.setString(
                        1,
                        draft.externalId().toString());
                statement.setString(
                        2,
                        draft.email());
                statement.setString(
                        3,
                        draft.status().name());
                statement.setBigDecimal(
                        4,
                        draft.balance());
                statement.setTimestamp(
                        5,
                        Timestamp.from(
                            draft.createdAt()));
            }

            @Override
            public int getBatchSize() {
                return drafts.size();
            }
        });
}

The return value contains one update-count array per submitted chunk. Batch size should be measured against row width, driver buffers, database parameter limits, transaction-log pressure, lock duration, latency, and failure recovery. The maximum possible batch is rarely the optimum batch.

7.5 Update-count semantics

JDBC batch results are ordered to correspond to submitted commands. A non-negative value is the row count. Statement.SUCCESS_NO_INFO means the command succeeded but the driver does not know the affected-row count. Statement.EXECUTE_FAILED can appear when the driver continues processing after a failure. On BatchUpdateException, a driver may stop at the first failure or continue, so the available update-count array is driver-dependent.[23][24]

Java 
static void verifyBatchCounts(int[] counts) {
    for (int index = 0; index < counts.length; index++) {
        int count = counts[index];

        if (count == Statement.EXECUTE_FAILED) {
            throw new IllegalStateException(
                    "Batch element failed at index "
                    + index);
        }

        if (count != Statement.SUCCESS_NO_INFO
                && count != 1) {
            throw new IllegalStateException(
                    "Unexpected row count "
                    + count
                    + " at index "
                    + index);
        }
    }
}

7.6 Batching and transactions

A batch call is not itself a transaction boundary. When executed inside a Spring transaction and the translated exception escapes, the transaction interceptor can roll back the transaction according to its rules. Outside a transaction, autocommit and driver behavior can leave a successfully executed prefix committed. Even within a transaction, database-specific DDL, autonomous operations, or external side effects may not roll back with the batch.[25]

Never retry a failed batch blindly Determine whether the transaction rolled back, whether the driver continued after failure, whether generated external effects occurred, and whether a unique business key makes replay idempotent.

7.7 Generated keys in batches

Spring provides generated-key batch overloads, including named-parameter support added in Spring 6.1. The driver must support generated keys for the operation, key ordering must be verified, and returned key cardinality can vary by database and driver. When identity mapping is critical, consider database-native returning clauses or client-generated identifiers, while preserving parameter binding and transaction management.[26]

8. Transaction integration

JdbcTemplate obtains connections through DataSourceUtils, which recognizes a connection bound to the current thread by Spring transaction management. All templates participating in one transaction must use the same logical DataSource instance or a transaction-aware arrangement that resolves to it.[27]

Java 
@Service
final class TransferService {
    private final AccountRepository accounts;

    TransferService(AccountRepository accounts) {
        this.accounts = accounts;
    }

    @Transactional
    public void transfer(
            long sourceId,
            long targetId,
            BigDecimal amount) {

        int debited =
                accounts.debitIfSufficient(
                        sourceId,
                        amount);

        if (debited != 1) {
            throw new InsufficientFundsException(
                    sourceId,
                    amount);
        }

        int credited =
                accounts.credit(
                        targetId,
                        amount);

        if (credited != 1) {
            throw new AccountNotFoundException(
                    targetId);
        }
    }
}

The guarded debit embeds the balance predicate in the update, making the row count a concurrency-safe business result under the database’s locking and isolation behavior:

SQL 
update account
set balance = balance - :amount
where id = :accountId
  and balance >= :amount

Transactional method interception normally requires the call to pass through the Spring proxy; self-invocation does not create a new intercepted boundary. Keep transaction boundaries in application services, not scattered across individual repository methods, unless each method is deliberately an independent unit of work.

8.1 Custom JDBC inside a transaction

If a low-level operation cannot use a template callback, obtain and release the connection through DataSourceUtils rather than calling DataSource.getConnection() and Connection.close() directly. The utility translates acquisition failures and preserves ownership of a transaction-bound connection.[27]

Java 
Connection connection =
        DataSourceUtils.getConnection(dataSource);

try {
    DatabaseVendorConnection vendor =
            connection.unwrap(
                    DatabaseVendorConnection.class);

    vendor.performSpecialOperation();
}
finally {
    DataSourceUtils.releaseConnection(
            connection,
            dataSource);
}

9. Worked example: transaction-aware account repository

The following repository combines named parameters for readable application queries, a custom mapper for explicit domain conversion, generated keys, optional lookup, guarded updates, and chunked batch insertion. The schema is illustrative SQL and may require type or identity syntax adjustments for the selected database.

9.1 Schema

SQL 
create table account (
    id bigint generated always as identity primary key,
    external_id varchar(36) not null unique,
    email varchar(320) not null unique,
    status varchar(20) not null,
    balance decimal(19, 2) not null,
    created_at timestamp not null,
    version bigint not null default 0,
    constraint account_balance_nonnegative
        check (balance >= 0)
);

create index account_status_created_idx
    on account (status, created_at);

9.2 Domain types

Java 
public enum AccountStatus {
    ACTIVE,
    SUSPENDED,
    CLOSED
}

public record Account(
        long id,
        UUID externalId,

9.3 Repository implementation

Java 
@Repository
public final class AccountRepository {
    private static final String SELECT_COLUMNS = """
        id, external_id, email, status,
        balance, created_at, version
        """;

    private static final String INSERT_SQL = """
        insert into account (
            external_id, email, status,
            balance, created_at
        )
        values (
            :externalId, :email, :status,
            :balance, :createdAt
        )
        """;

    static final RowMapper<Account> MAPPER =
            (rs, rowNumber) ->
                new Account(
                    rs.getLong("id"),
                    UUID.fromString(
                        rs.getString("external_id")),
                    rs.getString("email"),
                    AccountStatus.valueOf(
                        rs.getString("status")),
                    rs.getBigDecimal("balance"),
                    rs.getTimestamp("created_at")
                      .toInstant(),
                    rs.getLong("version"));

    private final NamedParameterJdbcTemplate named;
    private final JdbcTemplate jdbc;

    public AccountRepository(
            NamedParameterJdbcTemplate named,
            JdbcTemplate jdbc) {
        this.named = named;
        this.jdbc = jdbc;
    }

    public Optional<Account> findById(long id) {
        List<Account> rows = named.query(
            """
            select %s
            from account
            where id = :id
            """.formatted(SELECT_COLUMNS),
            Map.of("id", id),
            MAPPER);

        return Optional.ofNullable(
                DataAccessUtils.singleResult(rows));
    }

    public List<Account> findByStatuses(
            Set<AccountStatus> statuses,
            int limit) {

        if (statuses.isEmpty()) {
            return List.of();
        }

        List<String> names =
                statuses.stream()
                    .map(Enum::name)
                    .toList();

        return named.query(
            """
            select %s
            from account
            where status in (:statuses)
            order by created_at, id
            fetch first :limit rows only
            """.formatted(SELECT_COLUMNS),
            new MapSqlParameterSource()
                .addValue("statuses", names)
                .addValue("limit", limit),
            MAPPER);
    }

    public long insert(AccountDraft draft) {
        KeyHolder keys =
                new GeneratedKeyHolder();

        int affected = named.update(
                INSERT_SQL,
                parameters(draft),
                keys,
                new String[] {"id"});

        if (affected != 1) {
            throw new IncorrectUpdateSemanticsDataAccessException(
                    "Expected one account insert");
        }

        Long id = keys.getKeyAs(Long.class);
        if (id == null) {
            throw new DataRetrievalFailureException(
                    "No generated account id");
        }

        return id;
    }

    public int debitIfSufficient(
            long accountId,
            BigDecimal amount) {

        return named.update(
            """
            update account
            set balance = balance - :amount,
                version = version + 1
            where id = :accountId
              and status = 'ACTIVE'
              and balance >= :amount
            """,
            new MapSqlParameterSource()
                .addValue("accountId", accountId)
                .addValue("amount", amount));
    }

    public int credit(
            long accountId,
            BigDecimal amount) {

        return named.update(
            """
            update account
            set balance = balance + :amount,
                version = version + 1
            where id = :accountId
              and status = 'ACTIVE'
            """,
            new MapSqlParameterSource()
                .addValue("accountId", accountId)
                .addValue("amount", amount));
    }

    public int[][] insertBatch(
            Collection<AccountDraft> drafts,
            int batchSize) {

        return jdbc.batchUpdate(
            """
            insert into account (
                external_id, email, status,
                balance, created_at
            )
            values (?, ?, ?, ?, ?)
            """,
            drafts,
            batchSize,
            (statement, draft) -> {
                statement.setString(
                        1,
                        draft.externalId().toString());
                statement.setString(
                        2,
                        draft.email());
                statement.setString(
                        3,
                        draft.status().name());
                statement.setBigDecimal(
                        4,
                        draft.balance());
                statement.setTimestamp(
                        5,
                        Timestamp.from(
                            draft.createdAt()));
            });
    }

    private static SqlParameterSource parameters(
            AccountDraft draft) {

        return new MapSqlParameterSource()
            .addValue(
                "externalId",
                draft.externalId().toString())
            .addValue(
                "email",
                draft.email())
            .addValue(
                "status",
                draft.status().name())
            .addValue(
                "balance",
                draft.balance())
            .addValue(
                "createdAt",
                Timestamp.from(
                    draft.createdAt()));
    }
}

9.4 Design analysis

  • The repository owns SQL and row-shape conversion; the service owns transaction and business semantics.
  • Point lookup uses zero-or-one semantics without swallowing duplicate-row defects.
  • Named parameters clarify guarded updates and repeated values.
  • Enum and timestamp conversion are explicit instead of delegated to reflection-based mapping.
  • Generated key retrieval is checked for both update cardinality and missing keys.
  • Batch insertion is chunked and does not require materializing an Object[] for every row.
  • Update counts become domain signals for insufficient funds, missing targets, and optimistic state changes.
  • The SQL limit syntax must be adapted if the selected database does not support the shown standard-style FETCH FIRST form or parameter binding in that position.

10. Testing Spring JDBC code

Unit tests can verify mapping with mocked result sets, but database integration tests provide substantially more value for SQL grammar, type conversion, generated keys, constraints, transaction rollback, isolation, and batch behavior. Use the same database engine and materially similar driver version as production when those semantics matter.

A transactional test rollback is useful for isolation, but it can hide commit-time failures and behavior that occurs only after commit. Add non-rollback tests for transaction synchronization, serialization failures at commit, generated events, and database triggers whose behavior is commit-sensitive.

11. Diagnostics

11.1 Bad SQL despite valid syntax

Capture the translated exception type, SQL state, vendor code, task description, and SQL identifier. Do not log sensitive parameter values indiscriminately. Reproduce the prepared statement with representative typed parameters against the same database and schema version.

11.2 Unexpected update count

Check predicates, triggers, cascade behavior, driver count modes, optimistic version clauses, and whether the statement was rewritten. Do not automatically treat every non-one count as success.

11.3 queryForObject throws on absence

The method enforces an exact cardinality contract. Use a list plus DataAccessUtils.singleResult(), an optional-returning higher-level API, or a database-specific scalar expression when zero rows is expected.[8][10]

11.4 Statements use different connections

Confirm that every template uses the same DataSource bean as the transaction manager, that the transactional method is invoked through the proxy, and that custom JDBC obtains connections through templates or DataSourceUtils.[27]

11.5 Batch failed at an unclear row

Retain a stable input index or business key for each batch element, log the chunk boundary, inspect the translated root cause and nested BatchUpdateException where available, and understand whether the driver stopped or continued. Reduce the failing chunk with a deterministic replay in a disposable transaction.

11.6 Connection pool exhaustion during exports

Search for unclosed streams from queryForStream(), long-running transactions, blocking row handlers, and consumers that short-circuit without try-with-resources. Monitor active connection duration, not only pool size.

12. Expert practices

12.1 Treat SQL as source code

Format it, review it, test it against migrations, name projections, avoid select *, and attach performance expectations. Repository methods should reveal the query’s cardinality and update-count contract.

12.2 Reuse explicit mappers

A mapper should be stateless, projection-specific, and tested. Automatic mappers are appropriate for straightforward administrative or low-volume projections; custom mappers are preferable when correctness depends on conversion policy.

12.3 Bind values, never concatenate them

Parameters protect value boundaries and support plan reuse. Table names, column names, sort directions, and SQL operators cannot be bound as values; choose them from an allowlisted set and assemble the SQL structurally.

12.4 Encode cardinality explicitly

Distinguish exactly one, zero or one, any number, and at least one. Do not catch EmptyResultDataAccessException everywhere as a substitute for designing the repository return type.

12.5 Put transactions around business invariants

A repository operation is not necessarily a business transaction. Place the boundary where all required database state changes form one invariant-preserving unit.

12.6 Translate once, interpret later

Let Spring convert JDBC failures to portable categories. Convert those categories to domain failures only where the application can add stable meaning. Preserve the cause.

12.7 Batch by measured constraints

Use bounded chunks, stable business identifiers, idempotency where possible, and explicit validation of update counts. Benchmark with production-like latency, data width, indexes, constraints, and driver settings.

12.8 Choose identifier strategy deliberately

Database-generated numeric keys are compact and efficient but require key-return support. Client-generated UUIDs simplify replay and batch correlation but affect index locality and storage. The repository contract should not assume all databases return generated keys identically.

12.9 Define temporal mapping

Specify whether database timestamps represent instants, local wall-clock values, or offset-aware values. Configure the database session and JDBC driver consistently, and avoid implicit system-default time zones in mapping code.

12.10 Observe database work at the boundary

Record operation names, durations, affected-row counts, batch sizes, translated exception categories, and transaction outcomes. Avoid logging secrets or high-cardinality raw SQL parameter values.

13. Summary

Spring JDBC is best understood as a deterministic resource-management and exception-translation engine around standard JDBC:

  • JdbcTemplate owns the repetitive JDBC lifecycle while application code owns SQL and mapping.
  • NamedParameterJdbcTemplate rewrites named values to positional JDBC parameters and delegates execution to the classic template.
  • RowMapper maps one current row and must not advance or close the result set.
  • ResultSetExtractor is the correct tool for hierarchical results whose object cardinality differs from row cardinality.
  • DataAccessException represents portable failure categories; the default translator uses JDBC exception subclasses with SQL-state fallback.
  • Generated keys are driver capabilities and require explicit cardinality checks.
  • Batch execution reduces round trips but has driver-dependent counts and failure continuation behavior.
  • A batch is not a transaction; transaction boundaries must be defined around application invariants.
  • Templates participate in Spring transactions through transaction-aware connection acquisition.
  • Update counts, result cardinality, null mapping, timestamps, and exceptions are part of the repository contract, not incidental implementation details.

When a Spring JDBC operation behaves unexpectedly, inspect the problem in this order: Which SQL and typed parameters were sent? Which connection and transaction owned the statement? What result cardinality or update count was promised? Which mapper or extractor interpreted the rows? Which JDBC exception details were translated into the observed Spring category? For batches, add: what did the driver report for each element, and did the transaction actually roll back? Those questions turn most database-access failures into a reproducible contract mismatch rather than a template mystery.
