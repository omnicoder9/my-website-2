Spring Distributed Systems

Building Microservices with Spring

A technical guide to service decomposition, API gateways, service discovery, configuration management, inter-service communication, event-driven architecture, transactional outboxes, sagas, CQRS, and event sourcing.

Spring Cloud 2025.1.2 Compatible example baseline: Spring Boot 4.0.7 Gateway 5.0.2 · Stream 5.0.2 · Kafka 4.1.0 Long-form technical article Vancouver references
Abstract. A Spring Boot application becomes a microservice through architecture and operations, not through a dependency. A useful service owns a cohesive business capability, exposes explicit contracts, controls its data, can be changed and deployed independently, and remains operable when networks and dependencies fail. Spring Framework and Boot supply the application foundation; Spring Cloud adds gateway, discovery, load-balancing, configuration, circuit-breaker, contract-testing, and messaging integrations; Spring Security protects service boundaries; Spring Cloud Stream and Spring for Apache Kafka implement message-driven communication; and Spring Modulith helps establish enforceable module boundaries before distribution. This article develops one order-processing system across synchronous HTTP, asynchronous events, transactional outbox publication, choreography and orchestration sagas, CQRS projections, and an event-sourced aggregate. It emphasizes the hard properties: ownership, failure isolation, idempotency, schema evolution, consistency, observability, and compatibility.

The microservice architectural style organizes an application as independently deployable services built around business capabilities, commonly with decentralized data ownership and lightweight communication. These benefits introduce distribution costs: remote calls fail, latency accumulates, data becomes eventually consistent, and operational automation becomes mandatory.[1][2]

1. Microservices are an architectural commitment

Independent ownershipA team owns behavior, data, deployment, and operations for a business capability.
Explicit contractsHTTP, gRPC, and event schemas replace in-process method calls and shared objects.
Failure as normalTimeouts, partial availability, duplicate messages, and stale data are ordinary states.
Operational autonomyEach service needs deployability, telemetry, security, capacity limits, and recovery procedures.

Service boundaries are valuable when they provide independent change and ownership. Splitting one cohesive application into many processes without independent capabilities produces a distributed monolith: deployment and runtime complexity increase while teams remain tightly coordinated. Fowler explicitly cautions that many systems are better served by a monolith and that distribution and eventual consistency are significant microservice costs.[2][3]

Start from modularity, not network topology A well-structured Spring Boot modular monolith is often the safest first implementation. Extract a module when independent deployment, scaling, ownership, security, or technology needs outweigh the cost of a network boundary.

3. Service decomposition

A common decomposition method is to identify business subdomains and bounded contexts, then align service ownership with those boundaries. A bounded context defines the scope within which a domain model and terminology are consistent. The service should own the data required to enforce its aggregate invariants; other services access that capability through a contract rather than reading its tables.[5][6]

3.1 Order-system decomposition

OrderOrder lifecycle and customer intentOrders, lines, saga state, order outboxOrderPlaced, OrderApproved, OrderRejected

3.2 Boundary tests

  • Can the capability be described without implementation terms?
  • Can one team own its API, data, deployment, and production alerts?
  • Does it have a meaningful independent release cadence or scaling profile?
  • Can its invariants be enforced with local transactions?
  • Are cross-boundary calls coarse-grained rather than object-level chatter?
  • Can failure and stale-data behavior be specified explicitly?

3.3 Verify modules before extracting services

Spring Modulith discovers application modules from package structure and can verify that module dependencies contain no cycles, that other modules access only exposed APIs, and that explicitly allowed dependencies are respected. Module-scoped integration tests can bootstrap a module alone or with its declared dependencies.[7][8]

4. Reference architecture

1 Clients call an API gateway using OAuth 2.0 access tokens.
2 The gateway routes coarse-grained APIs to order, catalog, and query services.
3 Services resolve logical names through Kubernetes DNS or a discovery client and use load-balanced HTTP/gRPC clients.
4 Runtime configuration comes from environment-native sources or Spring Cloud Config; secrets use a dedicated secret store.
5 Local commands update one service database and append an outbox record in one transaction.
6 Outbox relays publish integration events to Kafka; consumer groups process independently.
7 Sagas coordinate workflows spanning order, inventory, and payment.
8 CQRS projections build query-optimized views from events.
9 Metrics, logs, and traces correlate gateway requests, commands, events, and saga instances.

5. API Gateway

Spring Cloud Gateway provides a full-featured gateway for WebFlux and Web MVC environments. A route consists of an ID, destination URI, predicates, and filters. Gateways centralize edge concerns such as routing, authentication integration, rate limiting, metrics, header policy, and resilience, while business invariants remain in the owning service.[9][10]

XML 
<dependency>
  <groupId>org.springframework.cloud</groupId>
  <artifactId>
    spring-cloud-starter-gateway-server-webflux
  </artifactId>
</dependency>

<dependency>
  <groupId>org.springframework.cloud</groupId>
  <artifactId>
    spring-cloud-starter-loadbalancer
  </artifactId>
</dependency>
YAML 
spring:
  application:
    name: api-gateway

  cloud:
    gateway:
      server:
        webflux:
          routes:
            - id: order-api
              uri: lb://order-service
              predicates:
                - Path=/orders/**
              filters:
                - StripPrefix=1
                - name: CircuitBreaker
                  args:
                    name: orderGateway
                    fallbackUri: forward:/fallback/orders

            - id: catalog-api
              uri: lb://catalog-service
              predicates:
                - Path=/catalog/**
              filters:
                - StripPrefix=1

management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,prometheus

The lb:// URI delegates instance selection to Spring Cloud LoadBalancer. Gateway filters execute before and after the downstream proxy request. Discovery-based automatic route generation is available, but explicit public routes are generally safer because they prevent every registered service from becoming an accidental external API.[10][11]

5.1 Keep the gateway thin

  • Authenticate and apply broad request policy at the edge, but authorize resource-specific operations inside services.
  • Do not place order, payment, or inventory workflows in gateway filters.
  • Avoid response aggregation that creates long fan-out chains unless the gateway is intentionally a backend-for-frontend.
  • Preserve trace context, request IDs, trusted forwarding metadata, and client deadlines.
  • Set strict request, header, body, connection, and response timeouts.

6. Service discovery

Service discovery maps a logical service name to one or more currently available instances. Spring Cloud Commons defines DiscoveryClient, ReactiveDiscoveryClient, service registration, and load-balancer abstractions independent of Eureka, Consul, Zookeeper, or Kubernetes implementations.[12][13]

6.1 Platform-native discovery

Kubernetes already supplies stable Service names and DNS-based discovery. A client can call http://inventory-service and let cluster networking select an endpoint. Spring Cloud Kubernetes adds a DiscoveryClient when applications need service metadata, endpoint inspection, label filtering, or Spring Cloud LoadBalancer integration beyond native DNS.[14]

Prefer the platform’s simplest stable mechanism On Kubernetes, DNS plus Services is often sufficient. Adding an application-level registry creates another control plane. Use Eureka or a Kubernetes DiscoveryClient when its metadata, zoning, portability, or client-side selection behavior is an actual requirement.

6.2 Eureka

Spring Cloud Netflix Eureka clients register instance metadata and send heartbeats; clients query the registry to discover instances. Adding the Eureka client starter makes a Boot application both a service instance and a discovery client, provided the registry location and application name are configured.[15]

XML 
<dependency>
  <groupId>org.springframework.cloud</groupId>
  <artifactId>
    spring-cloud-starter-netflix-eureka-client
  </artifactId>
</dependency>
YAML 
spring:
  application:
    name: inventory-service

eureka:
  client:
    serviceUrl:
      defaultZone: http://eureka:8761/eureka/
  instance:
    metadataMap:
      zone: zone-a

Registration is eventually consistent: a newly started or failed instance may not appear or disappear instantaneously. Clients still need connection and response timeouts, retries only for safe operations, and circuit breakers even when discovery is healthy.

7.3 Configuration policy

  • Version configuration alongside reviewable change history.
  • Separate non-secret settings from credentials and private keys.
  • Define whether unavailable central configuration blocks startup.
  • Prefer immutable restart-based rollout for structural changes.
  • Use refresh only for properties whose runtime mutation is safe and tested.
  • Protect Config Server independently from its Actuator endpoints and repository credentials.

Config Server supports encryption features, but secret storage and key custody remain security architecture concerns. A dedicated secret manager with workload identity, short-lived credentials, audit, and rotation is generally preferable to committing encrypted secrets that many services can retrieve.[19]

8.1 HTTP Service Client

Spring Framework provides synchronous RestClient, reactive WebClient, and annotated HTTP Service Clients. An HTTP interface can be backed by either client, preserving a typed contract while allowing the calling service to choose an imperative or reactive execution model.[20]

Java 
@HttpExchange(
    url = "/api/inventory",
    accept = MediaType.APPLICATION_JSON_VALUE)
public interface InventoryClient {

    @PostExchange("/reservations")
    ReservationResponse reserve(
        @RequestBody ReservationRequest request,
        @RequestHeader("Idempotency-Key")
        UUID idempotencyKey);

    @DeleteExchange("/reservations/{id}")
    void release(
        @PathVariable UUID id,
        @RequestHeader("Idempotency-Key")
        UUID idempotencyKey);
}
Java 
@Configuration(proxyBeanMethods = false)
public class InventoryClientConfiguration {

    @Bean
    @LoadBalanced
    RestClient.Builder loadBalancedBuilder(
            RestClientBuilderConfigurer configurer) {

        return configurer.configure(
            RestClient.builder());
    }

    @Bean
    InventoryClient inventoryClient(
            @LoadBalanced
            RestClient.Builder builder) {

        RestClient restClient = builder
            .baseUrl("http://inventory-service")
            .build();

        HttpServiceProxyFactory factory =
            HttpServiceProxyFactory.builderFor(
                RestClientAdapter.create(restClient))
            .build();

        return factory.createClient(
            InventoryClient.class);
    }
}

Spring Cloud Commons can make RestClient.Builder, WebClient.Builder, and RestTemplate load-balanced so a logical service ID is resolved through a discovery client and Spring Cloud LoadBalancer. Using Boot’s configured builders also preserves client instrumentation such as trace propagation.[21][22]

8.2 Timeouts, retries, and circuit breakers

Java 
@Service
public final class InventoryGateway {

    private final InventoryClient client;
    private final CircuitBreaker breaker;

    public InventoryGateway(
            InventoryClient client,
            CircuitBreakerFactory<?, ?> factory) {

        this.client = client;
        this.breaker =
            factory.create("inventory");
    }

    public ReservationResponse reserve(
            ReservationRequest request,
            UUID idempotencyKey) {

        return breaker.run(
            () -> client.reserve(
                request,
                idempotencyKey),
            failure ->
                ReservationResponse
                    .temporarilyUnavailable());
    }
}

Spring Cloud Circuit Breaker supplies a common API with Resilience4j, Spring Retry, and Spring Framework Retry implementations. Resilience4j integration supports blocking and reactive circuit breakers and optional bulkheads. A circuit breaker limits repeated calls to a failing dependency; it does not replace client connection/read deadlines or upstream request deadlines.[23]

  • Set connect, response, acquisition, and overall request deadlines.
  • Retry only transient failures and only when the operation is idempotent or carries an idempotency key.
  • Use exponential backoff and jitter; do not align retry storms.
  • Limit concurrent calls with bulkheads and bounded pools.
  • Return a truthful degraded result rather than fabricated success.

8.3 gRPC

Spring gRPC streamlines creation of gRPC clients and servers. Protobuf definitions generate service bases and stubs; Spring applications expose BindableService beans and bind generated clients to channels. gRPC is useful for strongly typed internal APIs, bidirectional streaming, and efficient binary messages, but it does not remove the need for versioning, deadlines, retries, authentication, and load balancing.[24]

9. Event-driven architecture

Spring Cloud Stream is a framework for message-driven microservices. It binds Java Supplier, Function, and Consumer beans to external destinations through broker-specific binders and provides consumer groups, partitioning, content negotiation, error handling, observability, and testing abstractions.[25][26]

Java 
@Configuration(proxyBeanMethods = false)
public class InventoryEvents {

    @Bean
    Consumer<OrderPlaced> reserveInventory(
            InventoryApplicationService inventory,
            IntegrationEventPublisher events) {

        return event -> {
            ReservationOutcome outcome =
                inventory.reserve(
                    event.orderId(),
                    event.lines());

            events.publish(
                outcome.toIntegrationEvent());
        };
    }
}
YAML 
spring:
  cloud:
    function:
      definition: reserveInventory

    stream:
      bindings:
        reserveInventory-in-0:
          destination: commerce.order-events.v1
          group: inventory-service
          content-type: application/json

  • Version contracts additively where possible; never repurpose an existing field.
  • Publish business facts, not ORM entities or internal class graphs.

  • Define retention, replay, compaction, dead-letter, and privacy policies.

9.2 Delivery semantics

Broker and framework “exactly once” claims are scoped. Spring Kafka can use Kafka transactions so a Kafka read-process-write sequence commits produced records and consumed offsets atomically. This does not make an arbitrary database update and Kafka publication one atomic operation, and external side effects still require idempotency.[29]

Design consumers for duplicates A producer can publish twice, a consumer can crash after applying a side effect but before acknowledging, and an outbox relay can send before recording completion. Idempotency is a business property implemented with stable event IDs, unique constraints, state transitions, and deduplication records.

10. Transactional outbox

A service that updates its database and publishes a broker event performs a dual write. If either write succeeds alone, state and notifications diverge. The transactional outbox pattern writes business state and an outbox record in one local database transaction; a separate relay publishes committed outbox records. The relay may publish duplicates, so consumers remain idempotent.[30]

SQL 
CREATE TABLE integration_outbox (
    id UUID PRIMARY KEY,
    aggregate_type VARCHAR(100) NOT NULL,
    aggregate_id UUID NOT NULL,
    event_type VARCHAR(200) NOT NULL,
    payload JSONB NOT NULL,
    occurred_at TIMESTAMPTZ NOT NULL,
    published_at TIMESTAMPTZ,
    attempts INTEGER NOT NULL DEFAULT 0
);

CREATE INDEX integration_outbox_unpublished
    ON integration_outbox (occurred_at)
    WHERE published_at IS NULL;
Java 
@Service
public final class PlaceOrderService {

    private final OrderRepository orders;
    private final OutboxRepository outbox;
    private final ObjectMapper json;

    @Transactional
    public OrderId place(PlaceOrder command) {
        Order order = Order.place(command);
        orders.save(order);

        OrderPlaced event =
            OrderPlaced.from(order);

        outbox.save(
            OutboxMessage.create(
                event.eventId(),
                "Order",
                order.id().value(),
                "commerce.order-placed.v1",
                writeJson(event),
                event.occurredAt()));

        return order.id();
    }
}
Java 
@Component
public final class OutboxRelay {

    private final OutboxRepository outbox;
    private final KafkaTemplate<String, String> kafka;

    @Scheduled(fixedDelayString = "${outbox.delay:250ms}")
    public void publishBatch() {
        List<OutboxMessage> batch =
            outbox.claimNextBatch(100);

        for (OutboxMessage message : batch) {
            try {
                kafka.send(
                    "commerce.events.v1",
                    message.aggregateId().toString(),
                    message.payload())
                .get(5, TimeUnit.SECONDS);

                outbox.markPublished(
                    message.id(),
                    Instant.now());
            }
            catch (Exception failure) {
                outbox.recordFailure(
                    message.id(),
                    failure.getClass().getName());
            }
        }
    }
}

A crash after Kafka acknowledges the send but before published_at is recorded causes a later resend. The relay therefore gives reliable at-least-once publication, not global exactly-once side effects. Claiming rows must also be safe across multiple relay instances, typically with database locking, leases, or change-data capture.

Spring Modulith’s Event Publication Registry records transactional event-listener publications in the original business transaction and tracks completion or failure. It can externalize selected events to brokers and, in current releases, supports dedicated outbox integrations for advanced requirements. Its documentation distinguishes the publication registry from a complete outbox implementation and describes cleanup requirements for completed entries.[31]

Spring Data aggregate roots can also expose domain events through @DomainEvents or AbstractAggregateRoot; repository operations publish those events into the Spring application context. That mechanism is useful for domain-event capture, but durable broker publication still requires a publication registry, outbox, or equivalent reliability boundary.[40]

11. Saga pattern

A saga represents a business transaction as a sequence of local transactions. Each step commits within one service and triggers the next step; failures invoke compensating actions or forward-recovery logic. Sagas provide consistency without one cross-service ACID transaction, but they do not provide automatic rollback or isolation.[32][33]

StyleCoordinationStrengthRisk
ChoreographyParticipants react to eventsLoose coupling and no central workflow componentImplicit flow, cycles, and difficult global timeout/diagnostics
OrchestrationCoordinator sends commands and interprets repliesExplicit state, ordering, timeout, and compensation policyCoordinator complexity and availability become critical

11.1 Choreography example

1 Order commits PENDING and publishes OrderPlaced.
2 Inventory reserves stock and publishes InventoryReserved or InventoryRejected.
3 Payment reacts to InventoryReserved and publishes PaymentAuthorized or PaymentDeclined.
4 Order approves after payment or rejects after either failure.
5 Inventory reacts to payment failure and releases the reservation.
Java 
@Configuration(proxyBeanMethods = false)
public class PaymentSagaHandlers {

    @Bean
    Consumer<InventoryReserved> authorizePayment(
            PaymentApplicationService payments,
            IntegrationEventPublisher events) {

        return event -> {
            PaymentOutcome outcome =
                payments.authorize(
                    event.orderId(),
                    event.amount(),
                    event.currency(),
                    event.eventId());

            events.publish(
                outcome.toIntegrationEvent());
        };
    }
}

Choreography is suitable for a small, stable participant set. As participants grow, event dependencies and compensation paths become difficult to see, test, and operate. AWS guidance calls out dual writes, cyclic dependencies, timeout policy, observability, latency, and compensation complexity as key choreography concerns.[34]

Java 
@Service
public final class OrderSagaOrchestrator {

    private final OrderSagaRepository sagas;
    private final SagaCommandPublisher commands;

    @Transactional
    public void start(OrderPlaced event) {
        OrderSaga saga =
            OrderSaga.start(
                UUID.randomUUID(),
                event.orderId(),
                event.total(),
                event.currency(),
                Instant.now().plusSeconds(30));

        sagas.save(saga);

        commands.reserveInventory(
            saga.sagaId(),
            event.orderId(),
            event.lines());
    }

    @Transactional
    public void on(InventoryReserved reply) {
        OrderSaga saga =
            sagas.require(reply.sagaId());

        saga.inventoryReserved(
            reply.reservationId());

        commands.authorizePayment(
            saga.sagaId(),
            saga.orderId(),
            saga.total(),
            saga.currency());
    }

    @Transactional
    public void on(PaymentDeclined reply) {
        OrderSaga saga =
            sagas.require(reply.sagaId());

        saga.beginInventoryCompensation();

        commands.releaseInventory(
            saga.sagaId(),
            saga.reservationId());
    }
}

Persist saga state before or atomically with outgoing commands so the coordinator can recover after restart. Every command and reply needs a saga ID and message ID. Transitions must be idempotent, optimistic-lock protected, and tolerant of duplicate, late, and out-of-order replies. A production orchestrator also needs deadline scanning, retries, poison-message handling, manual intervention, and audit history.[35]

11.3 Compensation is a business operation

Compensation is not byte-for-byte rollback. Refunding a captured payment, releasing inventory, or issuing store credit can fail and may have fees, legal effects, or irreversible external consequences. Model compensation explicitly with its own authorization, idempotency key, deadlines, and terminal states.

12. CQRS

Command Query Responsibility Segregation uses different models for updating information and reading it. The separation may begin as different classes and repositories over one database; an advanced form uses independently scalable stores and asynchronously maintained projections. CQRS is valuable when command invariants and query shapes differ substantially, but it adds synchronization, consistency, and operational complexity.[36][37]

12.1 Write model

Java 
@RestController
@RequestMapping("/api/orders")
public final class OrderCommandController {

    private final PlaceOrderService orders;

    @PostMapping
    ResponseEntity<OrderAccepted> place(
            @Valid
            @RequestBody PlaceOrderRequest request) {

        OrderId id =
            orders.place(request.toCommand());

        return ResponseEntity.accepted()
            .body(
                new OrderAccepted(
                    id.value(),
                    "/api/order-queries/"
                    + id.value()));
    }
}

A command expresses intent—PlaceOrder, CancelOrder, ApproveRefund—rather than generic field mutation. The write model enforces invariants and emits facts after successful state changes.

12.2 Read projection

Java 
@Component
public final class OrderSummaryProjector {

    private final JdbcClient jdbc;
    private final ProcessedMessageRepository processed;

    @KafkaListener(
        topics = "commerce.events.v1",
        groupId = "order-summary-projection-v1")
    @Transactional
    public void on(OrderApproved event) {
        if (!processed.claim(
                "order-summary-projection-v1",
                event.eventId())) {
            return;
        }

        jdbc.sql("""
            INSERT INTO order_summary(
                order_id,
                customer_id,
                status,
                total,
                currency,
                approved_at
            )
            VALUES (?, ?, ?, ?, ?, ?)
            ON CONFLICT (order_id)
            DO UPDATE SET
                status = EXCLUDED.status,
                approved_at = EXCLUDED.approved_at
            """)
            .params(
                event.orderId(),
                event.customerId(),
                "APPROVED",
                event.total(),
                event.currency(),
                event.occurredAt())
            .update();
    }
}

    }
}

Separate stores make read-after-write consistency asynchronous. A command response can return the new resource ID and status URL, while the query endpoint may temporarily return an older version. Options include polling, version tokens, client notifications, reading the write store for a narrow period, or waiting for a projection checkpoint—each with explicit latency and coupling trade-offs.

12.3 Rebuilding projections

  • Make projectors deterministic and idempotent.
  • Track source offsets or event positions.
  • Build a new projection version beside the current one.
  • Validate counts, checksums, and business invariants.
  • Atomically switch query traffic and retain rollback capability.

13. Event sourcing

Event sourcing stores every state change as an ordered sequence of events. Current aggregate state is derived by replaying that stream, optionally beginning from a snapshot. The event log becomes the authoritative record; projections, search indexes, and relational views are rebuildable models.[38][39]

13.1 Aggregate

Java 
sealed interface OrderEvent
        permits OrderOpened,
                OrderLineAdded,
                OrderConfirmed {
    UUID eventId();
    UUID orderId();
    Instant occurredAt();
}

public final class EventSourcedOrder {

    private UUID id;
    private final List<OrderLine> lines =
        new ArrayList<>();
    private OrderStatus status;
    private long version;

    private final List<OrderEvent> pending =
        new ArrayList<>();

    public static EventSourcedOrder rehydrate(
            List<OrderEvent> history) {

        EventSourcedOrder order =
            new EventSourcedOrder();

        history.forEach(order::apply);
        order.pending.clear();
        return order;
    }

    public void addLine(
            String sku,
            int quantity) {

        if (status != OrderStatus.DRAFT) {
            throw new IllegalStateException(
                "Only draft orders can change");
        }

        raise(
            new OrderLineAdded(
                UUID.randomUUID(),
                id,
                Instant.now(),
                sku,
                quantity));
    }

    public void confirm() {
        if (lines.isEmpty()) {
            throw new IllegalStateException(
                "Order must contain a line");
        }

        raise(
            new OrderConfirmed(
                UUID.randomUUID(),
                id,
                Instant.now()));
    }

    private void raise(OrderEvent event) {
        apply(event);
        pending.add(event);
    }

    private void apply(OrderEvent event) {
        switch (event) {
            case OrderOpened opened -> {
                id = opened.orderId();
                status = OrderStatus.DRAFT;
            }
            case OrderLineAdded added ->
                lines.add(
                    new OrderLine(
                        added.sku(),
                        added.quantity()));
            case OrderConfirmed ignored ->
                status = OrderStatus.CONFIRMED;
        }
        version++;
    }

    public List<OrderEvent> pendingEvents() {
        return List.copyOf(pending);
    }

    public long version() {
        return version;
    }
}

13.2 Event store

SQL 
CREATE TABLE event_stream (
    aggregate_type VARCHAR(100) NOT NULL,
    aggregate_id UUID NOT NULL,
    sequence_number BIGINT NOT NULL,
    event_id UUID NOT NULL UNIQUE,
    event_type VARCHAR(200) NOT NULL,
    schema_version INTEGER NOT NULL,
    payload JSONB NOT NULL,
    metadata JSONB NOT NULL,
    occurred_at TIMESTAMPTZ NOT NULL,

Java 
@Transactional
public void append(
        UUID orderId,
        long expectedVersion,
        List<OrderEvent> events) {

    long current =
        eventStore.currentVersion(
            "Order",
            orderId);

    if (current != expectedVersion) {
        throw new OptimisticLockingFailureException(
            "Order stream changed");
    }

    long sequence = current;

    for (OrderEvent event : events) {
        eventStore.insert(
            "Order",
            orderId,
            ++sequence,
            event);
    }
}

A unique aggregate/sequence key implements optimistic concurrency: two writers cannot both append the same next version. The event append and any same-store publication checkpoint must be atomic. Replaying events must not call current external systems, generate new IDs, or depend on the current clock; event application is deterministic.

13.3 Event evolution and governance

  • Never change the meaning of an existing event type or field.
  • Add schema versions and upcasters for historical payloads.
  • Keep event application deterministic across software versions.
  • Snapshot only as an optimization; events remain authoritative.
  • Plan deletion, redaction, encryption, and key destruction for personal data.
  • Test full replay and projection rebuild before every release.
Event sourcing is not “keep an audit table” The event stream is the source of truth and must support concurrency, replay, schema evolution, backup, retention, privacy, and deterministic aggregate reconstruction. Use it only where temporal history, auditability, complex state transitions, or multiple projections justify those obligations.

A common architecture uses a transactional write model, outbox events, and asynchronous CQRS projections without event sourcing. Another uses event sourcing to make event append the write operation and derives multiple read models. Sagas can coordinate either architecture.

15. Data ownership and consistency

Spring Data’s aggregate model treats an aggregate as the atomic consistency boundary and recommends one repository per aggregate root. References across aggregates may become consistent eventually. In a microservice architecture, the service boundary should not split invariants that require one atomic aggregate change.[6]

15.1 Database per service

  • Another service must not update or join against the owner’s private tables.
  • Cross-service queries use API composition or replicated projections.
  • Schema migrations are deployed by the owning service.
  • Backups and restores account for cross-service event positions and workflow state.
  • Analytics consumes governed exports, streams, or warehouse models rather than production joins.

15.2 Transitional shared database

During extraction, multiple services may temporarily share a database server. Preserve logical ownership with separate schemas, users, migration pipelines, and permissions. A physically shared database is not necessarily a shared-data model; unrestricted cross-schema queries recreate tight coupling.

16. Security

Spring Security supports OAuth 2.0 resource-server validation for JWT and opaque bearer tokens. In a common architecture, an authorization server issues access tokens, the gateway rejects obviously unauthenticated requests, and each resource service validates the token and enforces its own audience, scope, tenant, and resource authorization.[41]

YAML 
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://identity.example.net
          audiences:
            - https://api.example.net/orders
Java 
@Bean
SecurityFilterChain apiSecurity(
        HttpSecurity http) throws Exception {

    return http
        .authorizeHttpRequests(authorize ->
            authorize
                .requestMatchers(
                    HttpMethod.GET,
                    "/actuator/health/**")
                .permitAll()
                .requestMatchers(
                    HttpMethod.POST,
                    "/api/orders")
                .hasAuthority(
                    "SCOPE_orders.write")
                .anyRequest()
                .authenticated())
        .oauth2ResourceServer(
            oauth2 ->
                oauth2.jwt(
                    Customizer.withDefaults()))
        .build();
}
  • Do not trust identity headers from arbitrary clients; only a trusted gateway may create them.
  • Validate token issuer and audience in every resource service.
  • Use client credentials or workload identity for service-to-service calls.
  • Propagate user identity only when downstream authorization truly depends on it.
  • Keep secrets out of Config Server repositories, event payloads, traces, and logs.

17. Observability and operability

Spring Boot defines observability around logs, metrics, and traces and uses Micrometer Observation for metrics and tracing integration. Auto-configured RestClient.Builder, RestTemplateBuilder, and WebClient.Builder participate in trace propagation; directly constructed clients can bypass that instrumentation.[22][42]

  endpoints:
    web:
      exposure:
        include:

      probability: 0.1

  opentelemetry:

        otlp:

17.1 Correlation model

Attach a trace ID to synchronous calls and a stable message/event ID, causation ID, correlation ID, aggregate ID, and saga ID to asynchronous flows. Traces can expire before long-running workflows complete; durable saga and message identifiers provide the historical join.

17.2 Service-level signals

  • Request rate, latency distribution, errors, and saturation.
  • HTTP connection pools, client deadlines, circuit state, and retry counts.
  • Consumer lag, processing duration, retries, dead-letter rate, and duplicate suppression.
  • Outbox age, unpublished count, attempts, and oldest pending event.
  • Saga state counts, deadline violations, compensations, and manual interventions.
  • Projection lag, last applied offset, rebuild status, and query freshness.

18.2 Failure tests

  • Dependency timeout before and after the remote side commits.
  • Duplicate event, duplicate command, and duplicate reply.
  • Out-of-order saga reply and reply after timeout.
  • Broker unavailable after local database commit.
  • Consumer crash after side effect and before acknowledgement.
  • Projection rebuild while live events continue.
  • Old and new event-schema versions processed together.
  • Rolling deployment with old and new service versions communicating.

19. Deployment and evolution

Independently deployable services require independently versioned artifacts, database migrations, capacity policies, rollback procedures, and on-call ownership. “Independent” does not mean uncoordinated: contracts and events must support mixed-version operation during rolling releases.

19.1 Expand and contract

1 Add a new field, endpoint, event version, or database column without removing the old one.
2 Deploy producers that can populate both representations.
3 Migrate consumers and rebuild projections.
4 Observe that old usage has stopped.
5 Remove the old contract in a later deployment.

19.2 Strangler migration

Route one capability at a time from a monolith through the gateway to a new service. Establish data ownership, anti-corruption translation, event synchronization, and rollback before moving the next capability. Do not split database tables and service processes simultaneously without a verified consistency plan.

20. Anti-patterns

20.1 Service per entity or table

Entities are not business capabilities. Fine-grained entity services create chatty transactions and spread invariants over unreliable remote calls.

20.2 Shared domain-model JAR

Sharing DTOs and entities across all services synchronizes releases and leaks one bounded context into another. Share only stable technical libraries; publish contracts as schemas and generated clients where appropriate.

20.3 Shared writable tables

Multiple services updating the same tables bypass APIs, ownership, invariants, and independent migrations. Move toward schema and credential isolation.

20.4 Business workflow in the gateway

A gateway is routing infrastructure, not an order coordinator. Put multi-service business state in a durable saga orchestrator or owning domain service.

20.5 Retrying every failure

Retries can duplicate non-idempotent work and amplify overload. Classify failures, use deadlines and budgets, and require idempotency.

20.6 Events that demand one consumer action

“ReserveInventoryNow” is a command, not a historical fact. Name events in past tense and do not assume exactly one consumer unless the contract is explicitly a queue command.

20.7 Event sourcing every aggregate

Event sourcing imposes replay, evolution, privacy, and event-store obligations. Use ordinary state plus outbox events unless history-as-source-of-truth provides clear value.

20.8 “Eventually consistent” without a bound

Define expected projection lag, timeout behavior, client status, reconciliation, and operator alerts. Eventual consistency is a measurable contract, not an excuse for unexplained stale data.

22. Summary

  • A Spring Boot process is not automatically a microservice; independent business ownership and operations define the boundary.
  • Decompose by business capability and bounded context, not by entity, controller, or table.
  • Use Spring Modulith to verify module boundaries before paying distribution costs.
  • Use a compatible Spring Cloud release train and Boot version rather than independently selecting latest versions.
  • Spring Cloud Gateway centralizes edge routing and cross-cutting filters; business workflows stay in services.
  • Use platform-native discovery where sufficient and Spring Cloud discovery/load balancing when richer client behavior is required.
  • Spring Cloud Config provides versioned external configuration; secrets need stricter dedicated management.
  • HTTP and gRPC provide immediate responses but create temporal coupling and require deadlines, idempotency, and resilience.
  • Spring Cloud Stream and Spring Kafka support event-driven communication, consumer groups, partitioning, transactions, and broker integration.
  • A transactional outbox resolves the local database/broker dual-write problem but still permits duplicate publication.
  • Sagas coordinate local transactions with continuation and compensation; choreography is implicit, orchestration explicit.
  • CQRS separates command and query models and may introduce asynchronous read-model lag.
  • Event sourcing makes the event stream authoritative and requires deterministic replay, concurrency control, schema evolution, and privacy design.
  • Contract tests, failure injection, distributed tracing, durable correlation IDs, and mixed-version testing are essential operational capabilities.

When a microservice design is unclear, trace ownership and failure: Which team owns the business decision? Which database transaction enforces it? Which contract crosses the boundary? What happens when the network times out after the receiver commits? How is a duplicate detected? How stale may a query be? Which compensation restores an acceptable business state? Which metric tells an operator that the workflow is stuck? Answering those questions produces a service architecture; merely splitting packages into deployables does not.
