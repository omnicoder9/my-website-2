Spring Performance Engineering

Performance Optimization in Spring

A measurement-first guide to bean optimization, lazy initialization, JDBC connection pooling, caching, JVM and garbage-collector tuning, profiling, memory optimization, startup acceleration, and production diagnostics.

Spring Framework 7.0.8 Spring Boot 4.1.0 Java 25 HotSpot Long-form technical article Vancouver references
Abstract. Spring application performance is an end-to-end systems property. Bean creation affects startup and first-use latency; thread and connection pools define admission; database transaction duration determines connection occupancy; caches exchange freshness and memory for fewer computations; the JVM balances throughput, pause time, and footprint; and profiling tools identify where CPU, allocation, locks, I/O, and retention actually occur. Optimization therefore begins with a workload, service-level objective, baseline, and resource-saturation model—not with framework folklore or arbitrary JVM flags. This article presents a disciplined optimization workflow and production-oriented configurations for the requested areas, including startup instrumentation, selective laziness, HikariCP sizing, Spring Cache with Caffeine, Flight Recorder, GC logs, heap and native-memory analysis, bounded batch processing, and operational metrics.

Spring Framework 7.0.8 supplies the IoC container, lazy bean semantics, cache abstraction, startup instrumentation, and JVM checkpoint integration. Spring Boot 4.1.0 adds auto-configuration, startup tracking, Actuator diagnostics, datasource and cache integration, metrics, AOT processing, and JVM AOT-cache/CDS packaging support.[1][2]

1. Measurement-first optimization

1 Define a representative workload and explicit latency, throughput, startup, and memory objectives.
2 Establish a reproducible baseline under controlled data volume, concurrency, CPU, memory, and dependency behavior.
3 Observe saturation: executor queues, JDBC waits, CPU, GC, locks, network, database, and cache behavior.
4 Profile the dominant path rather than optimizing code selected by intuition.
5 Change one material variable and compare the complete distribution, not only an average.
6 Verify correctness, failure behavior, and resource use before retaining the change.
LatencyTime for one operation, including queueing and downstream waits. Tail percentiles reveal slow outliers hidden by an average.
ThroughputCompleted work per unit time at a defined correctness and latency target.
SaturationHow close a finite resource is to capacity: CPU, connections, threads, queue, heap, or external quota.
FootprintHeap, metaspace, code cache, thread stacks, direct buffers, JVM native memory, and non-JVM native allocations.

Micrometer timers record at least count and total time and can expose maximums, percentiles, or histograms where the backend supports them. Gauges represent sampled current values such as queue size or active connections; they do not retain every intermediate state.[3][4]

Do not optimize a benchmark artifact Warmup, data cardinality, query plans, cache state, network latency, payload sizes, concurrency, and failure rates must resemble production. A microbenchmark proving one method is faster does not prove the application’s critical request path improved.

1.1 Decompose the latency budget

Text 
end-to-end latency =
    admission queue delay
  + application CPU time
  + lock wait
  + connection-pool wait
  + database execution
  + remote I/O
  + serialization
  + runtime pauses

Optimization is most effective where a large term can be reduced without merely shifting work to another queue. A larger JDBC pool can reduce pool wait while overloading the database; a larger heap can reduce collection frequency while increasing footprint and potentially lengthening some collections; a larger cache can reduce I/O while retaining more live data.

2. Bean optimization

2.1 Measure Spring startup steps

Spring’s ApplicationStartup records named startup steps. Spring Framework provides FlightRecorderApplicationStartup for JFR correlation, while Boot provides BufferingApplicationStartup; Actuator’s startup endpoint exposes buffered startup data when configured.[5][6]

Java 
@SpringBootApplication
public class PerformanceApplication {

    public static void main(String[] arguments) {
        SpringApplication application =
                new SpringApplication(
                    PerformanceApplication.class);

        application.setApplicationStartup(
            new BufferingApplicationStartup(
                4_096));

        application.run(arguments);
    }
}
YAML 
management:
  endpoints:
    web:
      exposure:
        include:
          - health
          - metrics
          - startup
          - threaddump

Actuator endpoints are disabled from remote exposure unless explicitly included according to endpoint configuration. Heap dumps, thread dumps, metrics, and startup details are operationally sensitive and should be protected by authentication, network policy, and least-privilege access.[6]

2.2 Reduce the bean graph before making it lazy

Each dependency, starter, component scan, auto-configuration, proxy, repository, converter, endpoint, listener, and client can add classes and bean definitions. Boot auto-configuration is conditional and backs away when conditions do not match or user beans replace it. Removing unused starters and optional features reduces class loading and configuration processing without deferring failures to runtime.[7]

  • Remove dependencies that are present only through copied starter templates.
  • Keep component scanning rooted at the application package rather than scanning broad shared namespaces.
  • Disable a specific auto-configuration only after confirming it is active and unnecessary.
  • Do not create infrastructure clients for features disabled by configuration.
  • Avoid remote calls, large file reads, or bulk cache population in constructors and initialization callbacks.

2.3 Use lite configuration when inter-bean calls are unnecessary

Full @Configuration mode uses a generated CGLIB subclass to intercept calls between @Bean methods and preserve container semantics. When factory methods are self-contained and express dependencies as parameters, @Configuration(proxyBeanMethods=false) avoids that subclass processing.[8]

Java 
@Configuration(proxyBeanMethods = false)
public class ClientConfiguration {

    @Bean
    CatalogClient catalogClient(
            WebClient.Builder builder,
            CatalogProperties properties) {

        return new CatalogClient(
            builder
                .baseUrl(
                    properties.endpoint()
                        .toString())
                .build(),
            properties.timeout());
    }

    @Bean
    CatalogService catalogService(
            CatalogClient client) {

        return new CatalogService(client);
    }
}

Do not switch modes blindly when a configuration class deliberately calls another @Bean method. In lite mode, direct calls have ordinary Java semantics and can create unmanaged extra objects; use injected method parameters instead.[8]

2.4 Separate construction from runtime warmup

Java 
@Component
public final class ReferenceDataWarmup {

    private final ReferenceDataCache cache;

    public ReferenceDataWarmup(
            ReferenceDataCache cache) {
        this.cache = cache;
    }

    @EventListener(
        ApplicationReadyEvent.class)
    public void warm() {
        cache.loadCriticalEntries();
    }
}

ApplicationReadyEvent occurs after runners complete and Boot marks the application ready immediately afterward in the normal lifecycle. A large synchronous ready listener can therefore extend readiness. Warm only data required before traffic, or expose readiness only after a controlled warmup phase; optional data can warm asynchronously with bounded concurrency.[5]

3. Lazy initialization

Spring application contexts eagerly pre-instantiate singleton beans by default so configuration and environment failures are discovered during startup. A lazy bean is created when first requested. If an eager singleton directly depends on a lazy bean, the lazy bean is still created during startup to satisfy that dependency.[9]

Java 
@Bean
@Lazy
RecommendationModel recommendationModel(
        ResourceLoader resources) {

    return RecommendationModel.load(
        resources.getResource(
            "classpath:/models/recommendation.bin"));
}

3.1 Global Boot lazy initialization

YAML 
spring:
  main:
    lazy-initialization: true

Boot can enable lazy initialization globally. This can reduce startup time, especially for web infrastructure not used before the first request, but it delays misconfiguration failures and can shift latency and allocation to live traffic. Boot therefore leaves it disabled by default and recommends sizing the heap for the eventual complete bean graph before enabling it.[5]

3.2 Prefer selective laziness

Java 
@Service
public final class DocumentService {

    private final ObjectProvider<ArchiveClient>
            archiveClient;

    public DocumentService(
            ObjectProvider<ArchiveClient>
                    archiveClient) {
        this.archiveClient = archiveClient;
    }

    public ArchivedDocument archive(
            Document document) {

        return archiveClient
            .getObject()
            .archive(document);
    }
}

Selective @Lazy or ObjectProvider works well for rarely used integrations, optional administrative features, large models, and expensive factories. Critical request handlers, health infrastructure, security chains, serializers, and database mappings are often better initialized before readiness so startup proves they work.

3.3 Measure first-use latency

MetricWhy it matters
Process start to livenessPlatform can manage the process
Process start to readinessInstance can receive traffic
First request latencyReveals deferred bean creation and JIT/class-loading work
Steady-state latencyRepresents warmed execution
Post-idle latencyReveals connection, cache, or code deconditioning
Startup speed is not readiness quality An instance that opens its port quickly but initializes essential beans on the first customer request has moved startup work into tail latency. Decide what must be proven before readiness and what can be deferred safely.

4. Connection pooling

Boot auto-configures a pooling DataSource for production JDBC connections and prefers HikariCP when it is available. The JDBC and JPA starters include HikariCP by default. Implementation-specific settings use spring.datasource.hikari.*.[10]

YAML 
spring:
  datasource:
    url: jdbc:postgresql://db.internal/orders
    username: orders_app
    password: ${ORDERS_DB_PASSWORD}
    name: orders
    connection-fetch: lazy
    hikari:
      maximum-pool-size: 20
      connection-timeout: 2000
      validation-timeout: 1000
      max-lifetime: 1500000
      keepalive-time: 120000
      auto-commit: false

HikariCP’s maximumPoolSize limits total idle plus in-use connections. When the pool is full, callers wait up to connectionTimeout. Its default maximum is 10. Hikari recommends leaving minimumIdle unset for fixed-size behavior and setting maxLifetime shorter than any database or infrastructure connection limit. keepaliveTime applies to idle connections and must be shorter than maxLifetime.[11]

4.1 Size the pool from database capacity

Text 
average concurrent connections
    ≈ database transactions per second
      × average connection hold time in seconds

This Little’s-Law estimate gives a starting concurrency, not a final pool size. Validate it under representative load while observing database CPU, I/O, locks, query latency, active connections, and application wait time. HikariCP’s sizing guidance emphasizes that a smaller pool can outperform a large pool because excessive database concurrency increases contention and context switching.[12]

Pool size is a concurrency limit, not a throughput knob If the database can efficiently run 30 concurrent transactions, ten application replicas with 30 connections each offer 300 connections. Size the fleet-wide connection budget, reserve capacity for operations and migrations, and account for failover when traffic shifts to fewer database nodes.

4.2 Reduce connection hold time

Java 
@Service
public final class ShipmentService {

    private final CarrierClient carrier;
    private final ShipmentPersistence persistence;

    public ShipmentService(
            CarrierClient carrier,
            ShipmentPersistence persistence) {
        this.carrier = carrier;
        this.persistence = persistence;
    }

    public ShipmentResult ship(
            ShipmentCommand command) {

        CarrierLabel label =
                carrier.purchaseLabel(command);

        return persistence.persist(
            command,
            label);
    }
}

@Service
public final class ShipmentPersistence {

    private final ShipmentRepository shipments;

    public ShipmentPersistence(
            ShipmentRepository shipments) {
        this.shipments = shipments;
    }

    @Transactional
    public ShipmentResult persist(
            ShipmentCommand command,
            CarrierLabel label) {

        return shipments.save(
            Shipment.from(command, label));
    }
}

Slow carrier I/O occurs before the transactional Spring bean is invoked, so a pooled JDBC connection and database locks are not held while waiting on the remote service. Keep transactions no broader than required for consistency; where the remote call and database write form one business obligation, use an outbox, compensation, or another explicit consistency design rather than expanding the JDBC transaction around the network call.

4.3 Lazy connection acquisition

Boot can wrap an auto-configured pool so a transaction obtains a physical JDBC connection only when a statement is first created. With spring.datasource.connection-fetch=lazy, transaction control that performs no JDBC operation can complete without borrowing a connection.[10]

4.4 Observe pool behavior

Boot instruments datasource pools with jdbc.connections gauges for active, idle, maximum, and minimum connections and exposes Hikari-specific meters under the hikaricp prefix. Pool name tags can be controlled through datasource naming.[13]

HTTP 
GET /actuator/metrics/jdbc.connections.active?tag=name:orders
GET /actuator/metrics/jdbc.connections.max?tag=name:orders
GET /actuator/metrics/hikaricp.connections.acquire?tag=pool:orders
  • Persistent active-at-maximum plus rising acquisition latency indicates saturation.
  • Many idle connections across a large fleet indicate an oversized connection budget.
  • Long usage duration points to slow queries, broad transactions, or application work inside transactions.
  • Frequent connection creation can indicate lifetime mismatch, network closure, or an unnecessarily elastic idle policy.

5. Caching

Spring’s cache abstraction applies caching to method invocations and requires a backing CacheManager; it is not itself a cache store. Cacheable methods should return the same logical result for the same key within the chosen freshness policy. Concurrency and multi-process consistency are responsibilities of the selected provider and topology.[14][15]

5.1 Bounded local cache with Caffeine

Java 
@Configuration(proxyBeanMethods = false)
@EnableCaching
public class CacheConfiguration {

    @Bean
    CacheManager cacheManager() {
        CaffeineCacheManager manager =
                new CaffeineCacheManager(
                    "catalogById",
                    "priceBySku");

        manager.setCaffeine(
            Caffeine.newBuilder()
                .maximumSize(20_000)
                .expireAfterWrite(
                    Duration.ofMinutes(10))
                .recordStats());

        return manager;
    }
}

Spring integrates Caffeine through its cache package and cache manager. Caffeine supports bounded size, time-based expiration, loading, refresh, weak or soft references, removal notifications, and statistics. A bound is essential because an ordinary map retains entries until explicitly removed, while a cache is normally configured to evict and constrain memory use.[16][17]

5.2 Cacheable reads and transactional writes

Java 
@Service
@CacheConfig(cacheNames = "catalogById")
public final class CatalogService {

    private final ProductRepository products;

    public CatalogService(
            ProductRepository products) {
        this.products = products;
    }

    @Cacheable(
        key = "#id",
        sync = true,
        unless = "#result == null")
    public ProductView find(UUID id) {
        return products.findViewById(id)
            .orElse(null);
    }

    @Transactional
    @CacheEvict(key = "#command.id")
    public ProductView update(
            UpdateProduct command) {

        return ProductView.from(
            products.update(command));
    }
}

@Cacheable populates a cache, @CachePut updates it while still invoking the method, and @CacheEvict removes entries. sync=true asks the provider to synchronize concurrent loading for a key where supported. Cache advice defaults to proxy interception, so same-class self-invocation bypasses the annotation.[15]

5.3 Key design

  • Include every input that changes the result: tenant, locale, permissions, currency, version, or feature state.
  • Use immutable keys with stable equality and hash behavior.
  • Do not use an entire mutable request object as a key.
  • Avoid high-cardinality, one-use data that creates misses and memory churn.
  • Decide whether “not found” results are cached and for how long.

5.4 Invalidation and consistency

A local cache exists independently in each application process. A write evicting one node’s cache does not automatically invalidate other nodes unless the provider or application distributes invalidations. Select one of these models explicitly:

ModelBenefitTrade-off
Short-lived local cacheLowest latency and no network hopTemporary cross-node staleness
Distributed cacheShared entries and central policyNetwork dependency and serialization
Local cache plus invalidation eventsFast reads with coordinated evictionEvent delivery and race complexity
Versioned keysNo explicit stale-entry mutationOld entries remain until expiration/eviction
Hit rate is not sufficient Measure load latency, eviction rate, cache size/weight, stale-read tolerance, backend reduction, and the cost of misses. A high hit rate can still be harmful if retained objects consume excessive heap or cached values are incorrect.

6. JVM tuning

HotSpot selects collector, heap, and compiler defaults ergonomically. Oracle’s tuning guidance recommends starting with defaults unless the application has explicit throughput or pause requirements, then changing heap and collector settings from measured behavior. G1 is the default collector on most server-class configurations; Parallel GC emphasizes throughput, while ZGC targets low pause time at some throughput cost.[18][19]

6.1 Heap sizing

Heap size affects collection frequency and available space for the live set. -Xms sets the initial heap and -Xmx bounds the maximum. Setting them equal can improve predictability by removing heap growth decisions, but it also prevents the JVM from compensating for a poor fixed choice. The heap must remain below the process memory limit with headroom for metaspace, code cache, direct buffers, thread stacks, GC structures, native libraries, and operating-system needs.[20]

Shell 
JAVA_TOOL_OPTIONS="
  -Xms2g
  -Xmx2g
  -XX:+UseG1GC
  -XX:MaxGCPauseMillis=200
  -Xlog:gc*,safepoint:file=/var/log/app/gc.log:
        time,uptime,level,tags:
        filecount=5,filesize=20m
  -XX:+HeapDumpOnOutOfMemoryError
  -XX:HeapDumpPath=/var/dumps
  -XX:+ExitOnOutOfMemoryError
"

G1 attempts to meet a pause-time goal while retaining throughput, but the goal is not a hard real-time guarantee. Unified JVM logging uses -Xlog; -Xlog:gc* records detailed GC events and -Xlog:safepoint records stop-time information beyond garbage collection.[21][22]

6.2 Collector selection

CollectorPrimary objectiveStarting use case
G1Balanced throughput and pause goalsGeneral server application; default on most server configurations
ParallelHigh aggregate throughputBatch workloads tolerant of longer pauses
ZGCVery low pause timeLatency-sensitive services with sufficient CPU and heap headroom
SerialLow collector complexitySmall heaps or constrained single-processor environments

Collector choice is only a starting hypothesis. Compare throughput, CPU cost, pause distribution, live-set size, allocation rate, and memory footprint under the same workload. Oracle documents ZGC as concurrent and adaptive, with the maximum heap as its main tuning control.[19][23]

6.3 Reduce allocation before tuning generations

A high allocation rate increases young-generation collection work. Profile allocation sites before hand-tuning generation ratios. Common application causes include repeated serialization trees, copying large collections, per-record temporary maps, unbounded buffering, loading complete result sets, and logging that eagerly constructs expensive arguments.

Java 
public void exportCustomers(
        Consumer<CustomerRow> sink) {

    int page = 0;

    while (true) {
        Slice<CustomerRow> batch =
            repository.findExportRows(
                PageRequest.of(
                    page,
                    1_000,
                    Sort.by("id")));

        batch.forEach(sink);

        if (!batch.hasNext()) {
            return;
        }

        page++;
    }
}

Bounded batches constrain the number of retained rows, but offset pagination can become increasingly expensive in some databases. Keyset pagination or database streaming may be preferable; whichever technique is selected should be validated against query plans, transaction lifetime, and driver fetch behavior.

6.4 AOT processing, AOT cache, CDS, and checkpoint/restore

Boot supports running Spring AOT-generated initialization code on the JVM, with restrictions caused by a fixed build-time bean view. Java 25 AOT cache can reduce startup time and memory footprint; earlier supported JDKs can use CDS. Boot recommends AOT cache when available, and the cache must match the application and Java version and be used with the extracted application layout.[24][25]

Shell 
# Extract the Boot application.
java -Djarmode=tools \
  -jar app.jar \
  extract \
  --destination application

cd application

# Train a Java 25 AOT cache.
java \
  -XX:AOTCacheOutput=app.aot \
  -Dspring.context.exit=onRefresh \
  -jar app.jar

# Start with the cache.
java \
  -XX:AOTCache=app.aot \
  -jar app.jar

Spring also integrates with Project CRaC checkpoint/restore. Checkpoint files represent JVM memory and can contain secrets visible to the process; file, socket, thread, and connection lifecycle must be handled across checkpoint and restore.[26]

7. Profiling

7.1 Metrics locate symptoms

Boot auto-configures Micrometer and common JVM, HTTP, datasource, executor, and cache instrumentation when the relevant components are present. Metrics identify rates, latency distributions, utilization, and saturation; they do not by themselves identify the exact line allocating objects or consuming CPU.[13][27]

Java 
@Component
public final class PricingMetrics {

    private final Timer calculation;

    public PricingMetrics(
            MeterRegistry registry) {

        this.calculation = Timer.builder(
                "application.pricing.duration")
            .description(
                "Time spent calculating prices")
            .publishPercentileHistogram()
            .register(registry);
    }

    public <T> T record(
            Supplier<T> operation) {
        return calculation.record(
            operation);
    }
}

Use bounded, low-cardinality tags such as operation, outcome, region, or cache name. User IDs, request IDs, URLs with identifiers, SQL text, and arbitrary exception messages create unbounded time-series cardinality.

7.2 Java Flight Recorder

Java Flight Recorder is integrated into the JDK and collects timestamped JVM and application events, including CPU samples, allocations, locks, threads, I/O, and garbage collection. Oracle describes low-overhead recording configurations as suitable for production diagnosis; the more detailed profiling template adds overhead and should be used intentionally.[28]

Shell 
# Start a five-minute recording in a running JVM.
jcmd <pid> JFR.start \
  name=incident \
  settings=profile \
  duration=5m \
  filename=/var/recordings/incident.jfr

# Inspect or dump an existing continuous recording.
jcmd <pid> JFR.check
jcmd <pid> JFR.dump \
  name=continuous \
  filename=/var/recordings/snapshot.jfr

Analyze recordings with JDK Mission Control or the jfr command. Correlate hot methods with allocation sites, lock contention, socket/file I/O, GC pauses, class loading, and Spring startup events rather than treating one flame graph as the entire system.[28][29]

7.3 Thread dumps

Shell 
jcmd <pid> Thread.dump_to_file \
  -format=json \
  -overwrite \
  /var/dumps/threads.json

Capture several dumps during an incident. A single dump shows one instant; repeated dumps reveal threads consistently blocked on the same lock, pool, socket, future, or database call. Boot also exposes a protected threaddump Actuator endpoint.[6][29]

7.4 Heap dumps and histograms

Shell 
# Class histogram: lower impact first inspection.
jcmd <pid> GC.class_histogram

# Heap dump: potentially large and disruptive.
jcmd <pid> GC.heap_dump \
  /var/dumps/application.hprof

Boot’s heapdump endpoint returns an HPROF dump on HotSpot and can produce a large binary response. Heap dumps can contain credentials, customer data, tokens, and other sensitive objects and require secure storage and restricted access.[30]

Native Memory Tracking reports JVM internal reserved and committed memory by category. Oracle documents a 5–10% performance cost for NMT, so it should be enabled deliberately for diagnosis. Baseline and diff commands help identify native growth after warmup.[31]

Shell

# After warmup:

8.2 Optimize retention, not only allocation

A memory leak in a managed heap is usually unintended reachability: objects remain reachable from a GC root after the application no longer needs them. Common Spring-application retention paths include unbounded caches or maps, executor queues, application-event listeners registered outside normal lifecycle, static references, long HTTP sessions, unbounded message aggregation, class-loader references, and collections held by singleton beans.

Java 
@Component
public final class RecentFailureRegistry {

    private final Cache<UUID, FailureSummary>
            failures = Caffeine.newBuilder()
                .maximumSize(10_000)
                .expireAfterWrite(
                    Duration.ofHours(1))
                .build();

    public void record(
            UUID operationId,
            FailureSummary failure) {
        failures.put(operationId, failure);
    }
}

Every in-memory retention structure needs a maximum count or weight, expiration/cleanup policy, ownership, and metrics. A time-to-live alone may still permit an excessive burst; a maximum alone may retain obsolete data indefinitely. Caffeine supports combining bounded size and expiration policies.[17]

8.3 Scope and lifecycle

Spring singleton scope means one instance per bean definition per application context. Mutable collections held by singleton services therefore live until removal or context shutdown. Prototype beans are created by the container but their full destruction lifecycle is not managed after they are handed to the client; resources retained by prototypes require explicit ownership.[32]

8.4 Bound persistence-context growth

Java 
@Transactional
public int updateStatuses(
        List<OrderId> ids) {

    int updated = 0;

    for (List<OrderId> batch :
            partition(ids, 500)) {

        updated += repository
            .bulkUpdateStatus(
                batch,
                OrderStatus.ARCHIVED);

        entityManager.clear();
    }

    return updated;
}

Bulk update operations avoid materializing every entity when entity-level callbacks and dirty checking are not required. When entities must be loaded, flush and clear in bounded batches so the persistence context does not retain the complete job. Validate semantics carefully because bulk updates bypass ordinary managed-entity synchronization and lifecycle behavior.

8.5 Reduce payload and buffering costs

  • Project only columns required for a read response rather than loading full aggregates.
  • Page or stream large exports instead of constructing one giant list or byte array.
  • Set request, response, multipart, and message-size limits.
  • Use backpressure or bounded queues between producers and consumers.
  • Avoid retaining request/response bodies in logs, traces, or error objects.
  • Close streams, cursors, files, and response bodies through structured resource ownership.

10.2 Record the complete experiment

  • Application, JDK, container image, database, schema, and dependency versions.
  • JVM flags, CPU and memory limits, replica count, pool sizes, and cache configuration.
  • Dataset size and distribution, request mix, payload size, and concurrency model.
  • Latency percentiles, throughput, errors, queue waits, GC, CPU, allocation, and memory.
  • Database plans, locks, I/O, connections, and query latency.
  • Warm versus cold state and the exact time window compared.

11. Performance anti-patterns

11.1 Enable global laziness to hide a large context

Global lazy initialization can improve startup while delaying misconfiguration and first-use cost. Measure and reduce the graph first; make only genuinely optional components lazy.[5]

11.2 Increase every pool after a timeout

Larger pools can increase concurrency against a saturated downstream resource and worsen latency. Tune executor, connection, and dependency limits as one system.

11.3 Cache every read

Low-reuse keys create misses and memory pressure. Mutable results create invalidation complexity. Cache expensive, repeatable work with a clear key, freshness policy, and bounded storage.[14]

11.4 Copy JVM flags from another service

Collector and heap behavior depends on live data, allocation rate, CPUs, memory, and latency objectives. Start with ergonomics and measure before applying detailed controls.[18]

11.5 Optimize average latency

Averages hide queueing and long-tail outliers. Use distributions and correlate tail events with pool waits, GC, locks, and downstream latency.

11.6 Treat RSS growth as a heap leak

Process memory includes non-heap and native regions. Use heap analysis for Java reachability and NMT/OS tools for native growth.[31]

12. Diagnostic playbook

12.1 Startup is slow

Enable BufferingApplicationStartup or FlightRecorderApplicationStartup; inspect bean instantiation, class loading, scans, repositories, migrations, remote initialization, and runners. Compare eager, selective-lazy, Spring AOT, and AOT-cache runs under the same environment.[5][25]

12.2 Latency rises with concurrency

Inspect queue delay, active executor threads, JDBC acquisition, database execution, HTTP client pools, CPU, and GC. The first resource that remains saturated while its wait queue grows is the current bottleneck.

12.3 JDBC acquisition times out

Confirm whether active connections are at the maximum, then inspect transaction duration and database latency. Fix leaked connections, broad transactions, or slow queries before raising the pool; verify the fleet-wide database connection budget.[11][13]

12.4 Heap grows after caching is enabled

Inspect cache entry count, retained size, key cardinality, value size, and eviction. Add maximum size or weight, expiration, and cache statistics; ensure keys do not retain large request graphs.[17]

12.5 GC CPU or pauses rise

Record GC logs and JFR. Determine live-set growth versus allocation growth, humongous allocations, promotion pressure, or insufficient heap. Reduce retention/allocation first; then compare heap and collector changes under the same workload.[20][28]

12.6 RSS grows while heap is stable

Inspect thread count, direct buffers, metaspace, code cache, GC native structures, and native libraries. Use NMT baseline/diff for JVM-managed native memory and operating-system tools for allocations NMT cannot see.[31]

13. Expert practices

  • Optimize against a reproducible workload and explicit service-level objective.
  • Measure queue delay and resource saturation, not only method execution time.
  • Remove unnecessary beans and dependencies before enabling global laziness.
  • Keep expensive initialization out of constructors and verify critical beans before readiness.
  • Size JDBC pools from database capacity, connection hold time, and the fleet-wide budget.
  • Keep transactions short and avoid remote I/O while holding database connections.
  • Bound every cache by size or weight and define freshness and invalidation semantics.
  • Let JVM ergonomics establish a baseline before choosing collector-specific flags.
  • Use JFR, thread dumps, heap dumps, and NMT for different classes of evidence.
  • Reduce object retention and allocation before tuning GC internals.
  • Protect diagnostic endpoints and artifacts because they expose sensitive runtime state.
  • Repeat performance tests after JDK, Spring, database, driver, schema, or infrastructure changes.

14. Summary

  • Spring performance is an end-to-end property involving admission, application code, dependencies, runtime, and memory.
  • ApplicationStartup, Actuator, and JFR expose bean and startup costs.
  • Bean optimization begins by reducing the graph and startup side effects, not merely deferring creation.
  • Lazy initialization trades startup time for delayed failures, first-use latency, and deferred memory allocation.
  • Boot prefers HikariCP and exposes standard and Hikari-specific pool metrics.
  • JDBC pool size must respect database concurrency and fleet-wide connection limits.
  • Spring Cache is an abstraction; eviction, TTL, distribution, locking, and storage belong to the provider.
  • Bounded Caffeine caches can reduce repeated work while controlling heap retention.
  • JVM tuning begins with ergonomics, representative load, heap headroom, GC logs, and allocation evidence.
  • G1 balances throughput and pauses; Parallel favors throughput; ZGC targets very low pauses.
  • JFR profiles CPU, allocation, locks, I/O, GC, and startup with production-capable recording modes.
  • Heap dumps diagnose Java retention; NMT diagnoses JVM-native categories; neither alone explains all process memory.
  • AOT processing, Java 25 AOT cache, CDS, and CRaC address startup with different constraints and operational models.

When a Spring application is slow, follow ownership of time and memory: Which queue admitted the work? Which bean, thread, connection, cache entry, database operation, allocation site, lock, or native region retained the resource? Which metric showed saturation, and which profile proved the cause? That evidence-driven chain is more reliable than any universal tuning checklist.
