Spring Distributed Systems Platform

Spring Cloud

A technical guide to Config Server and distributed configuration, service discovery, Gateway, OpenFeign, Spring HTTP Service Clients, LoadBalancer, CircuitBreaker, Bus, Stream, security, observability, native-image constraints, testing, and production operations.

Spring Cloud release train 2025.1.2 Supported example baseline: Spring Boot 4.0.7 Config 5.0.4 · most train components 5.0.2 Long-form technical article Vancouver references
Abstract. Spring Cloud is a coordinated portfolio for recurring distributed-system concerns rather than a single runtime framework. Spring Cloud Config externalizes and versions configuration; Commons defines discovery, registration, load-balancing, and circuit-breaker abstractions; Eureka, Consul, and Kubernetes implement service discovery; Gateway provides reactive and servlet API-gateway variants; OpenFeign supplies declarative HTTP clients while current guidance favors Spring HTTP Service Clients for new development; LoadBalancer selects service instances; CircuitBreaker integrates Resilience4j and Spring retry implementations; Bus distributes management events over Kafka or AMQP; and Stream binds functional applications to brokers. These components remove framework boilerplate but do not make remote calls reliable, configuration changes safe, retries idempotent, or events exactly once. Correct systems define failure budgets, security boundaries, refresh semantics, contract ownership, observability, and platform responsibilities explicitly.

Spring Cloud’s release documentation describes the portfolio as tools for configuration management, service discovery, circuit breakers, intelligent routing, control buses, service-to-service calls, load balancing, and distributed messaging. Release train 2025.1.2 currently aligns its components with Spring Boot 4.0.7, so applications should import the train BOM rather than choose component versions independently.[1][2]

1. What Spring Cloud is—and is not

AbstractionsCommon interfaces for discovery, registration, load balancing, circuit breaking, functions, and binders.
ImplementationsGateway, Config, Eureka, Consul, Kubernetes, Resilience4j integrations, Kafka and Rabbit binders.
Release coordinationA train BOM aligns dozens of interdependent projects with a supported Boot baseline.
Operational patternsConfiguration APIs, routing filters, management-event broadcast, health, metrics, and contract testing.

Spring Cloud does not replace Spring Boot, a service mesh, Kubernetes, an identity provider, a broker, or an observability backend. It integrates application code with those concerns and provides portable programming models. The simplest platform-native mechanism should remain the default: for example, Kubernetes DNS can be sufficient without an application-level discovery client, and ordinary Boot external configuration can be sufficient without a Config Server.[3][4]

Do not install the portfolio indiscriminately Every control plane, registry, gateway, broker, refresh endpoint, and client interceptor adds runtime and operational behavior. Select a component because a concrete distributed-system requirement justifies it.

4. Spring Cloud Config Server (Configuration Server)

Config Server exposes an HTTP resource API for external configuration and is embedded in a Boot application with @EnableConfigServer. Its EnvironmentRepository resolves resources by application, profile, and label; those map to the client’s spring.application.name, active profiles, and a server-side version label such as a Git branch, tag, or commit.[6][7]

A local filesystem Git repository is useful for tests, but Config’s documentation recommends a hosted repository in production. Large binary files should not be stored in a configuration repository because they slow cloning and can increase Config Server memory use.[6]

Shared application* files apply to clients broadly, while service-named files specialize configuration. Profile-specific resources override non-profile resources according to Spring environment precedence. Labels provide a version dimension and support promotion or rollback to a known configuration revision.[7]

4.3 Composite repositories

YAML 
spring:
  profiles:
    active: composite

  cloud:
    config:
      server:
        fail-on-composite-error: true
        composite:
          - type: vault
            host: vault.internal
            port: 8200
            order: 1

          - type: git
            uri: https://git.example.net/platform/configuration.git
            order: 2

Composite repositories combine several backends. Precedence is set by list order or each repository’s order; lower order values have higher priority. By default, one backend failure fails the complete composite request, although the server can be configured to continue. Repositories in a composite must support the requested labels consistently.[8]

4.4 Security and secrets

Config Server can decrypt values prefixed with {cipher} before returning configuration and exposes encryption/decryption endpoints when cryptographic keys are configured. Those endpoints and the environment API must be strongly authenticated and authorized. Encryption in Git protects values at rest, but key custody, secret rotation, client authorization, audit, and exposure through the server remain separate concerns; dedicated Vault integration is preferable for dynamic or short-lived credentials.[9]

Config Server is a high-value control plane Compromise can reveal credentials or change behavior across an entire fleet. Isolate it from public networks, use TLS, least-privilege repository credentials, workload authentication, audit logs, protected Actuator endpoints, and tested backup and restore.

5.1 Discovery-first lookup

YAML 
spring:
  config:
    import: configserver:

  cloud:
    config:
      discovery:
        enabled: true
        service-id: config-server

Discovery-first Config locates the server through a DiscoveryClient, allowing Config Server coordinates to change. It adds a registry lookup to startup and still requires fixed coordinates for the discovery service itself. Config-first with a stable DNS name is often simpler.[10]

Use @ConfigurationProperties to bind and validate related settings. Central distribution does not eliminate configuration contracts: each service should declare types, defaults, constraints, ownership, and restart or refresh requirements.

6. RefreshScope and configuration changes

@RefreshScope places a bean behind a lazy proxy whose target is cached. A refresh invalidates that cache so the next invocation creates a new target from the updated environment. The refresh endpoint also rebinds configuration properties. Not every bean can be refreshed safely; HikariDataSource is in the default never-refreshable set, deleting a property does not necessarily remove its prior value, and refresh is unsupported for AOT/native-image applications.[11][10]

Java 
@Configuration(proxyBeanMethods = false)
public class PartnerClientConfiguration {

    @Bean
    @RefreshScope
    PartnerClient partnerClient(
            PartnerProperties properties,
            RestClient.Builder builder) {

        return new PartnerClient(
            builder
                .baseUrl(
                    properties.baseUrl()
                        .toString())
                .build(),
            properties.timeout());
    }
}
Prefer immutable rollout for structural changes Changing URLs, credentials, thread pools, serializers, security policy, or data sources in a live process can create mixed old/new state. Runtime refresh is appropriate only for specifically designed settings such as feature parameters or safe thresholds, with tests for concurrent use.

7. Service discovery

Spring Cloud Commons defines DiscoveryClient, ReactiveDiscoveryClient, ServiceInstance, and service-registration abstractions so client code can work with Eureka, Consul, Kubernetes, Zookeeper, or a simple property-based client. Discovery clients usually auto-configure from their starter; @EnableDiscoveryClient is available but not generally required for activation.[5][12]

Java 
@RestController
@RequestMapping("/internal/discovery")
public final class DiscoveryController {

    private final DiscoveryClient discovery;

    public DiscoveryController(
            DiscoveryClient discovery) {
        this.discovery = discovery;
    }

    @GetMapping("/{serviceId}")
    List<ServiceInstanceView> instances(
            @PathVariable String serviceId) {

        return discovery.getInstances(serviceId)
            .stream()
            .map(ServiceInstanceView::from)
            .toList();
    }
}

Application business code should usually call a load-balanced client rather than querying instances directly. Direct discovery access is useful for diagnostics, administrative selection, metadata inspection, or custom instance-supply policies.

Registry state is eventually consistent, so callers still require deadlines, load-balancing policy, and resilience when stale instances are selected.[13]

7.2 Consul

Spring Cloud Consul integrates discovery, configuration, and bus-related patterns with HashiCorp Consul. Discovery registration commonly uses an HTTP health check against the Boot health endpoint; the path and interval must be changed when the management context differs, and registration health checks can be disabled or replaced with TTL heartbeat behavior.[14][15]

YAML 
spring:
  application:
    name: inventory-service

  cloud:
    consul:
      host: consul.internal
      port: 8500
      discovery:
        health-check-path: /actuator/health/readiness
        health-check-interval: 15s
        metadata:
          zone: us-east-1a

7.3 Kubernetes

Kubernetes Services and DNS already provide server-side discovery; Spring Cloud Kubernetes is optional for deploying a Boot application. Its DiscoveryClient implementations query Services and endpoint addresses through the Kubernetes API and can filter namespaces, labels, readiness, metadata, and EndpointSlice use. Broad all-namespace discovery increases API and application load and requires wider RBAC.[3][16]

YAML 
spring:
  cloud:

      discovery:

          - commerce

        include-not-ready-addresses: false
        use-endpoint-slices: true

8. Spring Cloud LoadBalancer

Spring Cloud LoadBalancer is a client-side load-balancer abstraction. It obtains instances through ServiceInstanceListSupplier and supplies round-robin and random algorithms. It integrates with RestClient, RestTemplate, WebClient, Gateway lb:// routes, OpenFeign, and Spring HTTP Service Client groups.[17]

8.1 Load-balanced RestClient

Java 
@Configuration(proxyBeanMethods = false)
public class ClientConfiguration {

    @Bean
    @LoadBalanced
    RestClient.Builder loadBalancedRestClient(
            RestClientBuilderConfigurer configurer) {

        return configurer.configure(
            RestClient.builder());
    }
}

@Service
public final class InventoryClient {

    private final RestClient client;

    public InventoryClient(
            @LoadBalanced
            RestClient.Builder builder) {

        this.client = builder
            .baseUrl(
                "http://inventory-service")
            .build();
    }

    public Reservation reserve(
            ReservationRequest request) {

        return client.post()
            .uri("/api/reservations")
            .body(request)
            .retrieve()
            .body(Reservation.class);
    }
}

The URI host is a service ID, not necessarily a DNS name. The load-balancer interceptor asks the instance supplier for candidates, selects one, and rewrites the request to the instance host and port. Use Boot-configured builders so observation and trace propagation remain active.[12][17]

8.2 Instance suppliers, caching, and health

Suppliers can combine discovery, caching, health checks, zone preference, request hints, subsets, weighted selection, and version filtering. LoadBalancer creates a child context per service ID lazily by default; selected service contexts can be eagerly initialized. When Caffeine is present, a Caffeine-backed instance cache is available. Cache time-to-live must remain short enough to avoid routing to removed instances, and discovery platforms already providing cached watches may not need another caching layer.[17]

Java 
@LoadBalancerClient(
    name = "inventory-service",
    configuration =
        InventoryLoadBalancerConfiguration.class)
@Configuration(proxyBeanMethods = false)
public class InventoryClientMarker {
}

class InventoryLoadBalancerConfiguration {

    @Bean
    ServiceInstanceListSupplier supplier(
            ConfigurableApplicationContext context) {

        return ServiceInstanceListSupplier
            .builder()
            .withDiscoveryClient()
            .withCaching()
            .withZonePreference()
            .build(context);
    }
}
Load balancing is not capacity control Round robin distributes calls but does not prevent every caller from overwhelming every instance. Combine it with per-call deadlines, bounded concurrency, circuit breakers, admission limits, and server-side backpressure.

9. Spring Cloud Gateway as an API Gateway

Spring Cloud Gateway provides a full-featured Server variant and a lighter Proxy Exchange variant. Both support WebFlux and Web MVC; the WebFlux server runs matching requests through route-specific pre-filters, proxies the request, then runs post-filters. Routes contain an ID, destination URI, predicates, filters, order, and optional metadata.[18][19]

9.1 WebFlux gateway routes

XML 
<dependency>
  <groupId>org.springframework.cloud</groupId>
  <artifactId>
    spring-cloud-starter-gateway-server-webflux
  </artifactId>
</dependency>

<dependency>
  <groupId>org.springframework.cloud</groupId>
  <artifactId>
    spring-cloud-starter-loadbalancer
  </artifactId>
</dependency>

<dependency>
  <groupId>org.springframework.cloud</groupId>
  <artifactId>
    spring-cloud-starter-circuitbreaker-reactor-resilience4j
  </artifactId>
</dependency>
YAML 
spring:
  cloud:
    gateway:
      server:
        webflux:
          default-filters:
            - RemoveResponseHeader=Server

          routes:
            - id: order-api
              uri: lb://order-service
              predicates:
                - Path=/orders/**
                - Method=GET,POST,PUT,DELETE
              filters:
                - StripPrefix=1
                - name: CircuitBreaker
                  args:
                    name: orderGateway
                    fallbackUri: forward:/fallback/orders

            - id: inventory-admin
              uri: lb://inventory-service
              predicates:
                - Path=/inventory-admin/**
                - RemoteAddr=10.0.0.0/8
              filters:
                - StripPrefix=1

Route predicates select requests, and GatewayFilter factories transform requests or responses. lb:// delegates target resolution to LoadBalancer. DiscoveryClient route generation is disabled by default and can expose every discovered service under a generated route when enabled; explicit externally visible routes are safer for API governance.[20][21]

9.2 Java route API

Java 
@Bean
RouteLocator routes(
        RouteLocatorBuilder builder) {

    return builder.routes()
        .route(
            "catalog-api",
            route -> route
                .path("/catalog/**")
                .filters(filters -> filters
                    .stripPrefix(1)
                    .addResponseHeader(
                        "X-Edge",
                        "catalog-gateway"))
                .uri("lb://catalog-service"))
        .build();
}

The fluent API supports logical combinations of route predicates and custom filters. Keep routes deterministic, version-controlled, and tested; dynamic route stores require their own consistency and audit model.[22]

9.3 Gateway responsibilities

  • Edge authentication integration and broad authorization.
  • Path, host, method, header, cookie, time, and network predicates.
  • Request-size limits, rate limiting, CORS, header normalization, and trusted forwarding.
  • Timeout, retry, circuit-breaker, and fallback policy at the edge.
  • Gateway metrics and trace propagation.

Resource-level authorization and business invariants must remain in the downstream service. A fallback should represent a truthful degraded outcome; returning stale or empty data as success can corrupt client decisions.

10. Spring Cloud OpenFeign

OpenFeign creates a dynamic implementation of an annotated Java interface and integrates Spring MVC annotations, Boot message converters, Eureka, LoadBalancer, and CircuitBreaker. The project is now feature-complete; the Spring team recommends Spring HTTP Service Clients for new development while continuing bug fixes and small contributions to OpenFeign.[23]

10.1 Declarative client

XML 
<dependency>
  <groupId>org.springframework.cloud</groupId>
  <artifactId>
    spring-cloud-starter-openfeign
  </artifactId>
</dependency>
Java 
@SpringBootApplication
@EnableFeignClients
public class OrderApplication {
}

@FeignClient(
    name = "inventory-service",
    path = "/api/inventory",
    fallbackFactory =
        InventoryFallbackFactory.class)
public interface InventoryFeignClient {

    @PostMapping("/reservations")

        @RequestBody ReservationRequest request,
        @RequestHeader("Idempotency-Key")
        UUID idempotencyKey);
}
Java 
@Component
public final class InventoryFallbackFactory
        implements FallbackFactory<
            InventoryFeignClient> {

    @Override
    public InventoryFeignClient create(
            Throwable cause) {

        return (request, idempotencyKey) ->
            ReservationResponse
                .temporarilyUnavailable(
                    cause.getClass()
                        .getSimpleName());

}
YAML 
spring:
  cloud:
    openfeign:
      circuitbreaker:
        enabled: true

      client:
        config:
          inventory-service:
            connect-timeout: 1000
            read-timeout: 3000

When a Feign client specifies a name without a URL, LoadBalancer resolves that service ID. Circuit-breaker wrapping is opt-in through spring.cloud.openfeign.circuitbreaker.enabled; fallbacks implement the client contract and must be Spring beans. Spring Cloud’s Feign configuration disables Feign’s default automatic retry behavior with Retryer.NEVER_RETRY unless explicitly changed.[23][24]

Fallbacks must not disguise writes A failed reservation or payment call cannot safely return a fabricated success. For commands, prefer a clear unavailable result, asynchronous acceptance with durable processing, or propagation of a typed failure.

10.2 Modern alternative: HTTP Service Clients

Spring Framework’s HTTP Service Client uses annotated interfaces backed by RestClient or WebClient. Spring Cloud LoadBalancer 5.0 adds integration with Boot’s HTTP Service Client groups, allowing a group name or lb: base URL to become the service ID. This is the strategic choice for new declarative clients when OpenFeign-specific features are unnecessary.[17][25]

Java 
@HttpExchange("/api/inventory")
public interface InventoryHttpClient {

    @PostExchange("/reservations")
    ReservationResponse reserve(
        @RequestBody ReservationRequest request,
        @RequestHeader("Idempotency-Key")
        UUID idempotencyKey);
}

11. Spring Cloud CircuitBreaker

CircuitBreaker supplies a common API in Cloud Commons and implementations for Resilience4j, Spring Retry, and Spring Framework Retry. Resilience4j supports blocking and reactive applications and integrates circuit breakers, time limiters, and bulkheads. Framework Retry is lightweight and non-reactive.[26]

11.2 Default and service-specific policy

Java 
@Configuration(proxyBeanMethods = false)
public class ResilienceConfiguration {

    @Bean
    Customizer<Resilience4JCircuitBreakerFactory>
            defaults() {

        return factory ->
            factory.configureDefault(id ->
                new Resilience4JConfigBuilder(id)
                    .timeLimiterConfig(
                        TimeLimiterConfig.custom()
                            .timeoutDuration(
                                Duration.ofSeconds(2))
                            .build())
                    .circuitBreakerConfig(
                        CircuitBreakerConfig.custom()
                            .slidingWindowSize(50)
                            .minimumNumberOfCalls(20)
                            .failureRateThreshold(50)
                            .waitDurationInOpenState(
                                Duration.ofSeconds(10))
                            .build())
                    .build());
    }
}
Java 
@Service
public final class CatalogGateway {

    private final CatalogClient client;
    private final CircuitBreaker breaker;

    public CatalogGateway(
            CatalogClient client,
            CircuitBreakerFactory<?, ?> factory) {

        this.client = client;
        this.breaker =
            factory.create("catalog");
    }

    public ProductView find(String sku) {
        return breaker.run(
            () -> client.find(sku),
            failure ->
                ProductView.unavailable(sku));
    }
}

A circuit breaker observes outcomes and rejects calls while open so a failing dependency is not repeatedly invoked. A time limiter bounds asynchronous execution; a client-level connect/read timeout remains necessary. Bulkheads constrain concurrency and prevent one dependency from consuming every caller thread. CircuitBreaker metrics are auto-configured when Actuator and the Resilience4j Micrometer module are present.[27][28]

11.3 Failure policy

MechanismQuestion answered
Timeout/deadlineHow long may this attempt consume?
RetryShould another attempt be made, and is it safe?
Circuit breakerShould calls be rejected because recent outcomes indicate failure?
BulkheadHow much concurrent capacity may this dependency consume?
FallbackWhat truthful alternative outcome is available?
Load balancerWhich candidate instance receives this attempt?
A retry can multiply load A gateway retry, Feign retry, service retry, client-library retry, and mesh retry can turn one request into many attempts. Assign retry ownership to one layer, enforce an overall deadline, use jitter, and require idempotency for writes.

12. Spring Cloud Bus

Spring Cloud Bus connects application instances through a lightweight broker and acts as a distributed Actuator. Kafka and AMQP starters are provided. Bus can broadcast refresh, environment, shutdown, and custom events to every node, every instance of an application, or a targeted instance.[29][30]

XML 
<dependency>
  <groupId>org.springframework.cloud</groupId>
  <artifactId>
    spring-cloud-starter-bus-kafka
  </artifactId>
</dependency>
YAML 
spring:
  application:
    name: order-service

  kafka:
    bootstrap-servers:
      - kafka-1:9092
      - kafka-2:9092

  cloud:
    bus:
      id: ${spring.application.name}:${INSTANCE_ID:${random.uuid}}

management:
  endpoints:
    web:
      exposure:
        include: health,info,busrefresh
Shell 
# Refresh all bus-connected applications.
curl \
  --request POST \
  --user operator:secret \
  https://order-service.internal/actuator/busrefresh

# Refresh every order-service instance.
curl \
  --request POST \
  --user operator:secret \
  https://order-service.internal/\
actuator/busrefresh/order-service:**

/actuator/busrefresh clears RefreshScope targets and rebinds configuration properties across addressed instances. Bus IDs must be unique because event de-duplication compares sender and receiver IDs. busenv can change environment values and busshutdown can stop applications; exposing those endpoints creates a powerful administrative channel and should be avoided unless there is a tightly controlled operational requirement.[31][32]

12.1 Git webhook to Bus refresh

Adding Config Monitor to a bus-enabled Config Server exposes /monitor. Supported repository webhooks can notify Config Server of changed paths; the server publishes a RefreshRemoteApplicationEvent targeted at matching applications. Both Config Server and clients must participate in Bus for propagation.[33]

1 An operator merges a reviewed configuration change.
2 The Git provider sends a signed webhook to Config Server’s monitor endpoint.
3 Config Monitor maps changed files to affected application names.
4 Bus broadcasts a refresh event to matching instances.
5 Clients reload remote configuration and rebuild explicitly refreshable targets.

This pipeline requires webhook authentication, event audit, refresh-safe properties, a rollback revision, and protection against a fleet-wide restart or reconnection storm.

13. Spring Cloud Stream

Spring Cloud Stream binds functional Supplier, Function, and Consumer beans to middleware through binders. Its current binder catalog includes Kafka, RabbitMQ, Kafka Streams, Pulsar, and partner-maintained systems. Common binding properties define destination, consumer group, content type, and binder selection.[34][35]

            orders.approve(
                event.orderId(),
                event.eventId());
    }
}
YAML 
spring:
  cloud:
    function:
      definition: reserveInventory;approveOrder

    stream:
      bindings:
        reserveInventory-in-0:
          destination: commerce.order-events.v1
          group: inventory-service
          content-type: application/json

        approveOrder-in-0:
          destination: commerce.payment-events.v1
          group: order-service
          content-type: application/json

        approveOrder-out-0:
          destination: commerce.order-events.v1

      kafka:
        binder:
          brokers: kafka:9092

        bindings:
          reserveInventory-in-0:
            consumer:
              enable-dlq: true

Functional binding names use <function>-in-0 and <function>-out-0 by convention. In the Kafka binder, destinations map to topics, groups map to Kafka consumer groups, and partitioning maps to Kafka partitions. A named group provides competing-consumer semantics and durable group offsets; an anonymous group behaves like pub-sub for that instance and is usually unsuitable for durable business processing.[36][37]

13.2 Dynamic production with StreamBridge

Java 
@Service
public final class IntegrationEventPublisher {

    private final StreamBridge stream;

    public IntegrationEventPublisher(
            StreamBridge stream) {
        this.stream = stream;
    }

    public void publish(OrderApproved event) {
        boolean accepted = stream.send(
            "orderEvents-out-0",
            MessageBuilder
                .withPayload(event)
                .setHeader(
                    "eventId",
                    event.eventId())
                .setHeader(
                    "aggregateId",
                    event.orderId())
                .build());

        if (!accepted) {
            throw new EventPublicationException(
                event.eventId());
        }
    }
}

StreamBridge sends data from non-functional entry points or to dynamically selected bindings. A successful handoff to the binding does not by itself make a preceding database change atomic with broker publication; use a transactional outbox, broker transaction where its scope applies, or another explicit consistency design.

13.3 Event and consumer design

  • Use stable event IDs and idempotent consumers.
  • Partition by aggregate ID when ordering per aggregate matters.
  • Version schemas additively and test old/new compatibility.
  • Define retry, dead-letter, poison-message, and replay policy.
  • Track consumer lag, processing latency, error rate, and oldest pending work.
  • Keep personal and secret data out of broadly retained event streams.

14. Worked component topology

1 api-gateway authenticates traffic and routes /orders/** to order-service through lb://.
2 order-service imports versioned configuration from Config Server and discovers inventory-service.
3 An HTTP Service Client or Feign client calls inventory through LoadBalancer and CircuitBreaker.
4 Order writes local state and an outbox entry in one transaction.
5 A relay publishes OrderPlaced; Stream consumers process it in durable groups.
6 Config repository webhooks can trigger Bus refresh for safe runtime properties.
7 Metrics and traces correlate gateway requests, instance selection, circuit state, and event processing.

15. Security boundaries

ComponentPrimary controls
Config ServerTLS, workload identity, application/profile authorization, repository least privilege, protected encryption endpoints
Discovery registryAuthenticated registration and lookup, network isolation, metadata validation
GatewayOAuth 2.0/OIDC integration, request limits, trusted proxies, route authorization, rate policy
Service clientsmTLS or OAuth client credentials, issuer/audience validation, bounded token forwarding
BusBroker ACLs, unique IDs, protected Actuator endpoints, audit of refresh/env/shutdown events
StreamTopic/exchange ACLs, encryption, schema governance, data-retention and privacy controls

A gateway can reject unauthenticated requests, but each service remains a resource server and must enforce resource-specific authorization. Bus and Config administrative endpoints can change fleet behavior and should not be exposed merely because Actuator is installed.

16. Observability

  • Config Server request latency, Git/Vault backend errors, clone duration, revision served, and client startup failures.
  • Registry registration age, heartbeat loss, stale instances, discovery lookup latency, and instance counts.
  • LoadBalancer selected service/instance, no-instance outcomes, retries, and cache age.
  • Gateway route ID, downstream URI class, latency, status, filter failures, and circuit state.
  • Feign/HTTP client latency, timeout type, retry count, and fallback usage.
  • Bus event type, origin, destination, propagation delay, and failed refreshes.
  • Stream consumer lag, processing duration, delivery attempts, DLQ rate, and partition imbalance.

CircuitBreaker exposes Resilience4j metrics when Actuator and the Micrometer integration are present. Gateway, Config Client, LoadBalancer, and other current projects publish observability metadata through their reference documentation and Boot/Micrometer integration. Use low-cardinality tags such as service ID, route ID, client name, result, and exception class; never use arbitrary URLs, configuration values, user IDs, or event payloads as metric tags.[28]

17. Testing

17.1 Configuration tests

  • Resolve every application/profile/label combination expected in production.
  • Verify precedence among shared, service, profile, and composite repositories.
  • Test Config Server outage, authentication failure, stale Git checkout, and rollback label.
  • Test refresh concurrency and prove that non-refreshable infrastructure remains coherent.

17.3 Stream tests

Spring Cloud Stream supplies a test binder for exercising functions and bindings without a real broker. Component tests should additionally use the actual Kafka or Rabbit binder because partitioning, transactions, headers, ACLs, redelivery, and dead-letter behavior are broker-specific.

17.4 Failure tests

  • Discovery returns no instances or a stale instance.
  • Client connects but response exceeds the deadline.
  • Circuit opens under a controlled failure rate and later probes recovery.
  • Gateway receives a slow downstream response while its request is cancelled.
  • Bus refresh reaches only some instances.
  • Consumer crashes after applying a side effect but before acknowledgement.
  • Configuration and service versions roll independently during deployment.

18. AOT and native-image considerations

Config Client and LoadBalancer support AOT and native images with restrictions. Legacy Config bootstrap is unsupported for AOT, RefreshScope is unsupported in native images, and refresh must be disabled. LoadBalancer native support requires service IDs to be known through @LoadBalancerClient declarations or the eager-load client list so AOT can generate the required contexts.[10][17]

YAML 
spring:
  cloud:
    refresh:
      enabled: false

    loadbalancer:
      eager-load:
        clients:
          - inventory-service
          - payment-service

A native application may still read runtime configuration, but build-time bean conditions and dynamically discovered client structures require deliberate AOT compatibility. Native deployment generally favors restart-based configuration rollout over live refresh.

19. Operational design

19.1 Control-plane availability

Dependency unavailableExisting instanceNew instance
Config ServerNormally continues with already loaded valuesStarts or fails according to optional/fail-fast policy
Discovery registryMay use cached instances until staleMay fail registration or lack service candidates
GatewayDirect internal service calls can continueExternal entry point may be unavailable
Bus brokerApplication traffic continuesFleet refresh/management propagation stops
Stream brokerHTTP paths may continueEvent publication/consumption stalls according to buffering policy

19.2 Change policy

  • Pin release-train and Boot versions and upgrade together.
  • Promote configuration revisions through environments with audit and rollback.
  • Use a canary instance before fleet-wide refresh.
  • Assign ownership of retries, circuit breakers, and timeouts to avoid duplicated policies.
  • Run registries, Config Server, brokers, and gateways with independent availability and backup plans.
  • Document which platform feature or Spring Cloud feature owns discovery, routing, TLS, retries, and configuration.

20. Anti-patterns

20.1 Adding every Spring Cloud starter

The release train is a catalog, not a required stack. Unused auto-configuration increases startup work, dependencies, attack surface, and operational ambiguity.

20.2 Running Eureka on Kubernetes without a requirement

Kubernetes Service DNS already provides discovery. Add Eureka only for a concrete metadata, cross-platform, or client-selection need.[3]

20.3 Exposing every discovered service through Gateway

Discovery route generation can publish internal services accidentally. Maintain an explicit external API allowlist.[21]

20.4 Refreshing infrastructure beans fleet-wide

Live replacement can produce mixed connections, credentials, and state. Use immutable deployment for structural changes.

20.5 Returning success from a failed write fallback

Fallbacks must represent a real alternative outcome. A fabricated payment or inventory success corrupts business state.

20.6 Retrying at Gateway, Feign, LoadBalancer, service, and mesh

Layered retries amplify load and violate deadlines. Choose one retry owner per call path.

20.7 Public Bus or Config management endpoints

Refresh, environment mutation, shutdown, encryption, and configuration APIs are administrative control planes, not public application APIs.

20.8 Durable business consumer without a group

Anonymous consumer groups do not provide the durable competing-consumer behavior expected for business processing. Assign a stable group and design idempotency.

22. Summary

  • Spring Cloud is a release-coordinated portfolio for distributed-system patterns, not one framework.
  • Release train 2025.1.2 documents Spring Boot 4.0.7 as its supported baseline.
  • Config Server exposes application/profile/label-based configuration from Git, Vault, JDBC, native, or composite repositories.
  • Config Client uses spring.config.import=configserver:; optionality determines whether startup fails without the server.
  • RefreshScope recreates selected targets but is unsuitable for many infrastructure beans and unsupported in native images.
  • DiscoveryClient abstracts Eureka, Consul, Kubernetes, and other registries; platform-native discovery is often simpler.
  • LoadBalancer selects instances for RestClient, WebClient, Gateway, OpenFeign, and HTTP Service Clients.
  • Gateway supplies WebFlux and Web MVC routing, predicates, filters, resilience, and edge policies.
  • OpenFeign is feature-complete; Spring recommends HTTP Service Clients for new development.
  • CircuitBreaker abstracts Resilience4j and retry-based implementations; it complements deadlines, bulkheads, and idempotent retry policy.
  • Bus distributes management events over Kafka or AMQP and requires strict endpoint and broker security.
  • Stream binds functional applications to brokers with destinations, groups, partitioning, error handling, and test support.
  • Spring Cloud removes integration boilerplate but does not eliminate stale discovery, partial refresh, duplicate messages, retry storms, or control-plane failure.

When selecting or diagnosing a Spring Cloud component, follow the responsibility chain: Which control plane owns the data? How is it discovered and authenticated? Which version and release train define compatibility? What happens when that control plane is unavailable? Which cache or registry can become stale? Which layer owns the timeout, retry, circuit breaker, and fallback? Which event or administrative action is auditable? Those questions determine whether Spring Cloud simplifies the system or merely adds another distributed layer.
