Spring Framework Web MVC

File Uploads in Spring

An expert guide to multipart requests, MultipartFile, secure storage boundaries, metadata and integrity, upload validation, file downloads, content disposition, conditional requests, range support, streaming, and production operations.

Spring Framework 7.0.8 Spring Boot 4.1.0 conventions Servlet multipart and WebFlux notes Long-form technical article Vancouver references
Abstract. File handling is an untrusted-data pipeline, not merely a controller parameter. Spring MVC can resolve multipart/form-data requests through the Servlet Part API and expose uploaded parts as MultipartFile, Part, request parameters, or message-converted @RequestPart values. The temporary upload belongs to the request lifecycle; application code must validate and copy it into a durable store. A production design separates transport parsing, content validation, object storage, metadata persistence, authorization, malware processing, and HTTP download behavior. This article develops that architecture and provides a complete local-filesystem implementation that uses server-generated identifiers, normalized storage roots, bounded streaming, SHA-256 digests, staged publication, typed metadata, Resource-based downloads, safe Content-Disposition, cache validators, and transparent byte-range support.

Spring MVC 7.0.8 is the stable Servlet-stack reference used here. Spring’s standard multipart resolver delegates parsing to the Servlet container; Spring Boot 4.1.0 auto-configures Servlet multipart support when enabled and exposes limits under spring.servlet.multipart.[1][2][3]

1. Architecture and lifecycle

1 Edge infrastructure enforces total request size, authentication, rate limits, and connection timeouts.
2 The Servlet container parses multipart boundaries and stores parts in memory or temporary disk according to its configuration.
3 Spring resolves parts into controller arguments such as MultipartFile and message-converted metadata.
4 Application validation checks authorization, expected size, declared type, detected type, format structure, and policy.
5 Content is streamed to a staging object while a digest and actual byte count are calculated.
6 Malware scanning or content-disarm processing approves, rejects, or quarantines the object.
7 A server-generated object key is published to durable storage and metadata is committed.
8 Downloads re-authorize by object identifier and return controlled headers plus a streaming resource.

Spring’s MultipartFile represents content received in a multipart request. Its bytes may reside in memory or in a temporary file, and that temporary storage is cleared at the end of request processing. The application is responsible for copying accepted content into a longer-lived store before the request completes.[4]

The original filename is data, not a path getOriginalFilename() is supplied by the client, can contain path information or malicious sequences such as .., and must not determine the server-side storage path. Generate an opaque storage key and retain a sanitized display name only as metadata.[4][5]

2. Multipart requests

multipart/form-data encodes a request as a sequence of body parts separated by a boundary declared in the request Content-Type. Each form part carries Content-Disposition: form-data with a field name; a file part normally also includes a client-supplied filename and may include a part-level Content-Type.[6]

HTTP 
POST /api/files HTTP/1.1
Host: files.example.net
Content-Type: multipart/form-data; boundary=example-boundary
Authorization: Bearer …

--example-boundary
Content-Disposition: form-data; name="metadata"
Content-Type: application/json

{"purpose":"INVOICE","retentionDays":365}
--example-boundary
Content-Disposition: form-data; name="file"; filename="invoice.pdf"
Content-Type: application/pdf

...binary PDF bytes...
--example-boundary--

2.1 MultipartResolver

Spring’s MultipartResolver is the strategy used by DispatcherServlet to detect and resolve multipart requests. Spring Framework does not install a default resolver for every dispatcher. The standard implementation, StandardServletMultipartResolver, uses the Servlet Part API and requires multipart configuration on the servlet registration or equivalent container setup.[2][7]

Java 
@Configuration(proxyBeanMethods = false)
class MultipartConfiguration {

    @Bean(name = "multipartResolver")
    StandardServletMultipartResolver multipartResolver() {
        StandardServletMultipartResolver resolver =
                new StandardServletMultipartResolver();

        resolver.setStrictServletCompliance(true);
        resolver.setResolveLazily(false);
        return resolver;
    }
}

Strict Servlet compliance narrows resolver applicability to multipart/form-data. Lazy resolution postpones parsing until multipart files or parameters are accessed, which can move parsing failures later in request handling. Because the standard resolver delegates to the container parser, behavior outside the Servlet specification can differ between containers.[7]

2.3 Spring Boot configuration

Boot’s MultipartProperties configures the Servlet MultipartConfigElement. Current defaults are 1 MB per file, 10 MB per multipart request, a zero-byte disk threshold, and an unspecified temporary location chosen by the environment. Production applications should set explicit limits based on their API contract rather than relying on framework defaults.[3]

YAML 
spring:
  servlet:
    multipart:
      enabled: true
      max-file-size: 20MB
      max-request-size: 24MB
      file-size-threshold: 512KB
      location: /var/tmp/example-uploads
Apply limits at several layers Reverse proxies, load balancers, servlet containers, Spring multipart configuration, application policy, and storage quotas should agree. A controller-level size check occurs only after infrastructure may already have received or spooled the request.

getBytes() is reasonable for a deliberately tiny payload such as a small public key, but is a dangerous default for general uploads. transferTo(File) may move or copy provider-managed temporary content and can delete an existing destination first; use a server-generated, non-existing destination and do not depend on calling the operation repeatedly.[4]

4. Upload validation and security

OWASP recommends a defense-in-depth upload pipeline: allowlist extensions, validate actual file type rather than trusting the Content-Type header, generate server-side filenames, enforce size limits, restrict uploaders, store content outside the web root or on a separate host, apply least-privilege filesystem permissions, scan content, and protect upload forms from CSRF where applicable.[5]

4.1 Filename policy

Preserve an original name only for user-facing metadata. Strip directory components, remove control characters, normalize Unicode according to application policy, impose a length limit, and provide a safe fallback. The sanitized display name must still never be resolved against the storage root.

Java 
static String safeDisplayName(
        String originalFilename) {

    String raw = Objects.requireNonNullElse(
            originalFilename,
            "download");

    String leaf = Paths.get(raw)
            .getFileName()
            .toString();

    String normalized =
            Normalizer.normalize(
                leaf,
                Normalizer.Form.NFC);

    String cleaned = normalized
            .replaceAll("[\\p{Cntrl}\\\\/]+", "_")
            .replaceAll("\\s+", " ")
            .strip();

    if (cleaned.isBlank()
            || cleaned.equals(".")
            || cleaned.equals("..")) {
        return "download";
    }

    return cleaned.length() <= 180
            ? cleaned
            : cleaned.substring(0, 180);
}

4.2 Extension, declared type, and detected type

No single type signal is authoritative. The filename extension and multipart Content-Type are client-controlled. Java’s Files.probeContentType() delegates to installed file-type detectors and can return null; it is useful as one signal but is not a security verdict. High-risk formats require signature inspection and format-aware parsing with bounded resource consumption.[9]

Java 
record UploadTypePolicy(
        Set<String> extensions,
        Set<MediaType> mediaTypes) {

    void validateDeclared(
            String displayName,
            @Nullable String contentType) {

        String extension =
                extensionOf(displayName)
                    .toLowerCase(Locale.ROOT);

        if (!extensions.contains(extension)) {
            throw new UnsupportedUploadTypeException(
                    "Extension is not allowed");
        }

        if (contentType != null) {
            MediaType declared =
                    MediaType.parseMediaType(
                            contentType);

            if (!mediaTypes.contains(declared)) {
                throw new UnsupportedUploadTypeException(
                        "Declared media type is not allowed");
            }
        }
    }
}

4.3 Streaming size enforcement

Check MultipartFile.getSize() for early rejection, but also count bytes while copying. Streaming enforcement protects a storage API that may receive content from sources other than the Servlet multipart parser and verifies the byte count actually persisted.

Java 
static long copyBounded(
        InputStream input,
        OutputStream output,
        long maximumBytes,
        MessageDigest digest)
        throws IOException {

    byte[] buffer = new byte[64 * 1024];
    long count = 0;

    for (int read;
         (read = input.read(buffer)) != -1;) {

        count = Math.addExact(count, read);

        if (count > maximumBytes) {
            throw new UploadTooLargeException(
                    maximumBytes);
        }

        digest.update(buffer, 0, read);
        output.write(buffer, 0, read);
    }

    return count;
}

4.4 Quarantine and content processing

Store newly received content in a non-public staging or quarantine state. Scan or transform it before marking it downloadable. Office documents and PDFs may require content disarm and reconstruction; images can be decoded and re-encoded to discard unexpected ancillary data. Archive extraction requires explicit entry-count, expanded-size, nesting, path, compression-ratio, and timeout limits because a small upload can expand into excessive work.[5]

4.5 Authorization and object identifiers

A random identifier reduces guessability but does not replace authorization. Every upload, metadata lookup, download, and deletion must verify ownership or an explicit access rule. Never expose the storage-relative path as the public resource identifier.

5.3 Local filesystem implementation

Java 
@Component
public final class LocalFileObjectStore
        implements FileObjectStore {

    private final Path root;
    private final Path staging;
    private final Path objects;

    public LocalFileObjectStore(
            @Value("${files.storage.root}")
            Path configuredRoot)
            throws IOException {

        this.root = configuredRoot
                .toAbsolutePath()
                .normalize();

        this.staging = root.resolve("staging");
        this.objects = root.resolve("objects");

        Files.createDirectories(staging);
        Files.createDirectories(objects);
    }

    @Override
    public StoredObject store(
            UploadSource source,
            UploadPolicy policy)
            throws IOException {

        policy.validateNameAndDeclaredType(source);

        ObjectKey key = ObjectKey.random();
        Path target = pathFor(key);
        Files.createDirectories(target.getParent());

        Path temporary =
                Files.createTempFile(
                    staging,
                    "upload-",
                    ".part");

        boolean published = false;

        try {
            MessageDigest digest =
                    MessageDigest.getInstance("SHA-256");

            long size;

            try (InputStream input =
                     new BufferedInputStream(
                         source.content()
                               .getInputStream());
                 OutputStream output =
                     new BufferedOutputStream(
                         Files.newOutputStream(
                             temporary,
                             StandardOpenOption.WRITE,
                             StandardOpenOption
                                 .TRUNCATE_EXISTING))) {

                size = copyBounded(
                        input,
                        output,
                        policy.maximumBytes(),
                        digest);
            }

            MediaType detected =
                    detectMediaType(temporary);

            policy.validateDetected(
                    temporary,
                    detected,
                    size);

            policy.scanOrThrow(temporary);

            publish(temporary, target);
            published = true;

            return new StoredObject(
                    key,
                    size,
                    HexFormat.of().formatHex(
                        digest.digest()),
                    detected,
                    new PathResource(target));
        }
        catch (NoSuchAlgorithmException impossible) {
            throw new IllegalStateException(
                    "SHA-256 is unavailable",
                    impossible);
        }
        finally {
            if (!published) {
                Files.deleteIfExists(temporary);
            }
        }
    }

    @Override
    public StoredContent load(ObjectKey key)
            throws IOException {

        Path target = pathFor(key);

        if (!Files.isRegularFile(
                target,
                LinkOption.NOFOLLOW_LINKS)) {
            throw new StoredObjectNotFoundException(key);
        }

        return new StoredContent(
                key,
                Files.size(target),
                detectMediaType(target),
                new PathResource(target));
    }

    @Override
    public void delete(ObjectKey key)
            throws IOException {
        Files.deleteIfExists(pathFor(key));
    }

    private Path pathFor(ObjectKey key) {
        String value = key.value().toString();

        Path candidate = objects
                .resolve(value.substring(0, 2))
                .resolve(value.substring(2, 4))
                .resolve(value)
                .normalize();

        if (!candidate.startsWith(objects)) {
            throw new IllegalStateException(
                    "Object path escaped storage root");
        }

        return candidate;
    }

    private static void publish(
            Path temporary,
            Path target)
            throws IOException {

        try {
            Files.move(
                temporary,
                target,
                StandardCopyOption.ATOMIC_MOVE);
        }
        catch (AtomicMoveNotSupportedException ex) {
            Files.move(temporary, target);
        }
    }

    private static @Nullable MediaType detectMediaType(
            Path path) throws IOException {

        String value = Files.probeContentType(path);
        return value == null
                ? null
                : MediaType.parseMediaType(value);
    }
}

Files.createTempFile() creates a unique work file. ATOMIC_MOVE either performs one atomic filesystem operation or throws AtomicMoveNotSupportedException; an atomic move usually requires source and target to be on a compatible file store. A non-atomic fallback has weaker crash semantics and should be paired with reconciliation of staging and metadata records.[9]

Filesystem atomicity is not database atomicity Publishing the blob and inserting metadata are separate resource operations. Choose and document a failure model: metadata first with a pending state, blob first with orphan cleanup, or an object store plus database workflow reconciled by a background job. A local database transaction cannot roll back a completed filesystem move.

Persist the actual byte count and digest calculated during storage, not solely values supplied by the client. A cryptographic digest supports integrity checks and deduplication candidates, but identical hashes do not by themselves prove that two users are authorized to share one object.

5.5 Object storage

Cloud object stores replace local path operations with object keys, multipart transfer APIs, checksums, lifecycle policies, replication, and signed retrieval. Preserve the same application boundary: generate server keys, validate before publication, record metadata, authorize by application identity, and treat storage-provider metadata as infrastructure rather than the public domain model.

6. Complete upload API

6.1 Application service

Java 
@Service
public final class FileApplicationService {
    private final FileObjectStore objectStore;
    private final FileRecordRepository records;
    private final UploadPolicy policy;

    public FileApplicationService(
            FileObjectStore objectStore,
            FileRecordRepository records,
            UploadPolicy policy) {

        this.objectStore = objectStore;
        this.records = records;
        this.policy = policy;
    }

    public FileRepresentation upload(
            Principal principal,
            UploadMetadata metadata,
            MultipartFile multipartFile) {

        if (multipartFile.isEmpty()) {
            throw new EmptyUploadException();
        }

        String displayName =
                safeDisplayName(
                    multipartFile
                        .getOriginalFilename());

        MediaType declared =
                parseNullableMediaType(
                    multipartFile.getContentType());

        if (multipartFile.getSize()
                > policy.maximumBytes()) {
            throw new UploadTooLargeException(
                    policy.maximumBytes());
        }

        try {
            StoredObject object =
                    objectStore.store(
                        new UploadSource(
                            displayName,
                            declared,
                            multipartFile),
                        policy);

            FileRecord record =
                    records.insertAvailable(
                        principal.getName(),
                        metadata,
                        displayName,
                        object);

            return FileRepresentation.from(record);
        }
        catch (IOException ex) {
            throw new FileStorageException(
                    "Could not store uploaded content",
                    ex);
        }
    }
}

7. Upload errors

Spring’s MaxUploadSizeExceededException represents multipart-size violations and implements Spring’s error-response contract. ResponseEntityExceptionHandler includes handling for upload-size failures and renders RFC 9457 problem details by default.[10][11]

Java 
@RestControllerAdvice
final class FileApiExceptionHandler
        extends ResponseEntityExceptionHandler {

    @Override
    protected ResponseEntity<Object>
            handleMaxUploadSizeExceededException(
                MaxUploadSizeExceededException ex,
                HttpHeaders headers,
                HttpStatusCode status,
                WebRequest request) {

        ProblemDetail problem =
                ProblemDetail.forStatus(
                    HttpStatus.PAYLOAD_TOO_LARGE);

        problem.setType(
            URI.create(
                "https://api.example.net/problems/"
                + "upload-too-large"));
        problem.setTitle("Upload exceeds size limit");
        problem.setDetail(
            "The multipart request or file exceeded "
            + "the configured maximum.");

        return handleExceptionInternal(
                ex,
                problem,
                headers,
                HttpStatus.PAYLOAD_TOO_LARGE,
                request);
    }

    @ExceptionHandler(
        UnsupportedUploadTypeException.class)
    ProblemDetail unsupported(
            UnsupportedUploadTypeException ex) {

        ProblemDetail problem =
                ProblemDetail.forStatus(
                    HttpStatus.UNSUPPORTED_MEDIA_TYPE);

        problem.setType(
            URI.create(
                "https://api.example.net/problems/"
                + "unsupported-upload-type"));
        problem.setTitle(
                "Unsupported file type");
        problem.setDetail(ex.getMessage());
        return problem;
    }

    @ExceptionHandler(
        MalwareDetectedException.class)
    ProblemDetail malware(
            MalwareDetectedException ex) {

        ProblemDetail problem =
                ProblemDetail.forStatus(
                    HttpStatus.UNPROCESSABLE_CONTENT);

        problem.setType(
            URI.create(
                "https://api.example.net/problems/"
                + "unsafe-upload"));
        problem.setTitle(
                "Uploaded content was rejected");
        problem.setDetail(
                "The file did not pass content policy.");
        return problem;
    }
}

8. Downloading files

8.1 Download response contract

A download response should establish authorization, a trustworthy server-side object lookup, media type, content length when known, content disposition, cache policy, and validators. Spring’s ResourceHttpMessageConverter writes Resource bodies and supports byte-range requests.[12]

Java 
@GetMapping("/api/files/{id}/content")
ResponseEntity<Resource> download(
        @PathVariable UUID id,
        Principal principal) {

    DownloadFile file =
            fileDownloadService.authorizeAndLoad(
                principal,
                id);

    ContentDisposition disposition =
            ContentDisposition.attachment()
                .filename(
                    file.displayName(),
                    StandardCharsets.UTF_8)
                .build();

    return ResponseEntity.ok()
        .contentType(file.mediaType())
        .contentLength(file.size())
        .header(
            HttpHeaders.CONTENT_DISPOSITION,
            disposition.toString())
        .eTag(file.etag())
        .lastModified(file.lastModified())
        .cacheControl(
            CacheControl
                .privateCache()
                .maxAge(Duration.ofMinutes(5)))
        .body(file.resource());
}

Spring’s ContentDisposition models the HTTP header defined by RFC 6266 and supplies attachment and inline builders. The filename is a presentation suggestion to the recipient, not a path that the server should dereference.[13][14]

8.2 Attachment versus inline

attachment
Signals that the representation should normally be downloaded and provides a suggested filename.
inline
Allows user agents to render the representation in their context when supported.

Prefer attachment for untrusted user content. Inline HTML, SVG, PDF, and other active or script-capable formats need a deliberate origin, content-security policy, sandboxing, and content-disposition strategy. Serving user uploads from a separate unprivileged origin reduces the impact of content interpreted by a browser.

8.3 Media type

Store a validated media type at ingestion and use a conservative fallback such as application/octet-stream. Do not recalculate trust from the user-facing filename at download time. Spring’s media-type factory and resource converter can infer types, but an application with a validation pipeline should prefer persisted verified metadata.[12]

8.4 Range requests

Spring MVC transparently processes RFC 9110 range requests when an annotated controller returns a Resource or ResponseEntity<Resource>. The resource must not be an InputStreamResource, and a ResponseEntity<Resource> should initially have status 200. Spring can then produce 206 responses and the required range metadata. Invalid or unsatisfiable ranges use 416 semantics.[15][16]

HTTP 
GET /api/files/3c8cd911-094a-430e-88fb-1af496b3139b/content HTTP/1.1
Range: bytes=1048576-2097151
If-Range: "sha256-3568f75e..."
Use a repeatable resource for range support PathResource or FileSystemResource can reopen the file and report length. InputStreamResource describes an already-open, single-use stream and is specifically excluded from transparent MVC range handling.[15][17][21]

8.5 Conditional downloads

Use a strong ETag based on immutable object identity or a stored digest. If-None-Match permits 304 cache revalidation, while If-Range decides whether a range can be served from the client’s cached representation. Immutable objects can use long-lived cache policy if authorization and URL design make shared reuse safe.[16]

8.6 StreamingResponseBody

StreamingResponseBody writes directly to the Servlet response output stream asynchronously and can be used as a ResponseEntity body. It is useful for remote object-store streams or dynamically generated archives. Configure the Spring MVC async task executor explicitly. Manual streaming does not automatically gain the transparent Resource range behavior shown above.[18]

Java 
@GetMapping("/api/exports/{id}")
ResponseEntity<StreamingResponseBody> export(
        @PathVariable UUID id) {

    ExportHandle export =
            exportService.open(id);

    StreamingResponseBody body =
            output -> {
                try (InputStream input =
                         export.openStream()) {
                    input.transferTo(output);
                }
            };

    return ResponseEntity.ok()
        .contentType(
            MediaType.APPLICATION_OCTET_STREAM)
        .header(
            HttpHeaders.CONTENT_DISPOSITION,
            ContentDisposition.attachment()
                .filename(
                    export.filename(),
                    StandardCharsets.UTF_8)
                .build()
                .toString())
        .body(body);
}

9. WebFlux notes

WebFlux represents uploaded files with FilePart. Its filename is client-supplied and must not be used blindly; transferTo(Path) copies content reactively to a destination. Reactive multipart processing can also expose a stream of part events for sequential processing, which is useful when the application must avoid aggregating a large multipart body.[19][20]

Java 
@PostMapping(
    path = "/reactive/files",
    consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
Mono<FileRepresentation> uploadReactive(
        @RequestPart("file") FilePart part) {

    String displayName =
            safeDisplayName(part.filename());

    ObjectKey key = ObjectKey.random();
    Path destination = storagePath(key);

    return part.transferTo(destination)
        .then(metadataService.register(
            key,
            displayName,
            part.headers().getContentType()));
}

A real reactive storage pipeline should calculate limits and digests over the data-buffer stream, release buffers correctly, and avoid blocking filesystem or scanner calls on event-loop threads. Do not mix Servlet MultipartFile and WebFlux FilePart abstractions in one controller model.

10. Metadata, storage, and consistency

10.1 Database and blob store are two resources

A Spring database transaction does not include a filesystem or ordinary object-store operation. Treat the workflow as a state machine:

  1. Create a metadata row in STAGING, or create the staged blob first.
  2. Transfer and validate content.
  3. Publish the object under its final key.
  4. Mark metadata AVAILABLE.
  5. Reconcile abandoned staging rows and orphaned blobs periodically.

Downloads must expose only AVAILABLE objects. Deletion can similarly use a tombstone state followed by asynchronous physical removal, making retries and audit behavior explicit.

10.2 Deduplication

Content-addressed storage can reduce duplication, but it creates authorization and lifecycle questions. Do not reveal whether another tenant already uploaded matching content. Maintain independent logical records and reference counts or ownership mappings, and verify the complete digest before deduplicating.

10.3 Retention and legal holds

Model retention, deletion eligibility, quarantine, legal holds, and backup policy in metadata. Filesystem timestamps and bucket lifecycle rules are infrastructure signals; they are not a complete application retention model.

12. Operational design

12.1 Capacity and backpressure

Monitor temporary-disk use, durable capacity, inode/object counts, upload concurrency, parser failures, scanner queue depth, staging age, download throughput, and open connections. Reject work before the temporary volume is exhausted and reserve capacity for cleanup and system operation.

12.2 Timeouts

Use connection and request timeouts at the proxy and container, scanner deadlines, object-store timeouts, and asynchronous processing limits. A size limit does not prevent a slow client from holding resources.

12.3 Safe telemetry

Record object ID, owner or tenant, validated media type, actual size, digest prefix when appropriate, policy result, scanner result, duration, and storage outcome. Avoid logging authorization tokens, full paths, original content, or unsanitized filenames.

12.4 Reconciliation

Periodically remove expired staging files, resolve stale metadata states, identify orphaned final objects, enforce retention, and retry deletions. Cleanup jobs need bounded batches, idempotency, and metrics; they are part of the storage system rather than optional housekeeping.

13. Diagnostics

13.1 Missing multipart part

Verify the request Content-Type includes the correct boundary, the field name matches @RequestPart or @RequestParam, the resolver is enabled, and the client did not manually set a multipart header without generating a matching body boundary.

13.2 Controller never sees an oversized upload

The reverse proxy, container, or multipart parser rejected the request before controller invocation. Inspect limits and logs at each layer and standardize the public 413 response where infrastructure permits.

13.3 Temporary file disappears

Application code retained a MultipartFile beyond request processing. Copy content into durable or application-managed staging storage before returning from the request.

13.4 Download has zero or unknown length

Check whether an InputStreamResource or one-shot remote stream is used. A filesystem PathResource reports stable length and supports repeatable access. For remote streams, persist metadata and set Content-Length only when reliable.

13.5 Range request returns 200

Confirm the controller returns a non-InputStreamResource Resource or ResponseEntity<Resource> with initial status 200 and that no custom converter or response wrapper consumes the body first.[15]

13.6 Non-ASCII filename is corrupted

Build Content-Disposition through Spring’s builder with UTF-8 rather than concatenating an unescaped header string.[13]

14. Expert practices

14.1 Use opaque storage keys

Public resource IDs and internal object keys should be server-generated. Store display names as metadata and never let them select directories or final paths.

14.2 Stream and bound

Avoid getBytes() for general files. Count bytes and compute digests during one buffered transfer, with explicit maximums and cleanup on every failure path.

14.3 Verify content in layers

Combine extension allowlists, declared media types, signature checks, strict parsers, decompression limits, malware scanning, and application-specific validation. No single signal is sufficient.

14.4 Publish only approved content

Keep staging content outside public download paths. Model quarantine and rejection states explicitly and make download authorization require an available state.

14.5 Isolate browser-active content

Prefer attachment. When inline rendering is required, use a dedicated origin, restrictive response headers, and media-specific sanitization.

14.6 Return Resource for stored files

A repeatable file resource integrates with Spring’s message converter, content length, and transparent range support. Use manual streaming only when the underlying source cannot expose a repeatable resource.

14.7 Make metadata authoritative

Persist validated media type, actual size, digest, state, owner, display name, retention, and timestamps. Do not reconstruct trust from request headers or filenames during download.

14.8 Reconcile cross-resource workflows

Filesystem or object-store operations and relational metadata are not one local transaction. Use state transitions, idempotent operations, and reconciliation jobs.

14.9 Test adversarial inputs

Include traversal strings, double extensions, polyglot formats, malformed archives, huge declared lengths, zero-byte content, parser bombs, Unicode edge cases, concurrent overwrites, and authorization bypass attempts.

15. Summary

  • multipart/form-data divides one request into named parts separated by a declared boundary.
  • StandardServletMultipartResolver delegates multipart parsing to the Servlet container and requires Servlet multipart configuration.
  • Spring Boot exposes upload location, per-file size, total request size, and memory-to-disk threshold under spring.servlet.multipart.
  • @RequestParam MultipartFile handles form-style files; @RequestPart message-converts typed JSON or XML metadata.
  • A MultipartFile is request-lifecycle content. Copy it before the request ends.
  • The original filename and declared content type are untrusted client metadata.
  • Secure storage uses server-generated keys, an isolated root, bounded streaming, layered content validation, quarantine, and least privilege.
  • Filesystem publication and database metadata require an explicit cross-resource consistency strategy.
  • ResponseEntity<Resource> provides controlled media type, content length, disposition, cache validators, and transparent range support.
  • Use ContentDisposition to encode download filenames safely.
  • InputStreamResource is one-shot and unsuitable for Spring MVC’s transparent range handling.
  • Operational correctness includes capacity limits, scanner queues, cleanup, reconciliation, observability, and adversarial testing.

Diagnose a file workflow as a pipeline: Which component accepted the bytes? Where were they temporarily stored? Which limits executed before and after parsing? Which names and media types came from the client? Which checks were content-based? Which object key and metadata record became authoritative? Was publication atomic within the storage system, and how are cross-resource failures reconciled? Which authorization and response headers governed retrieval? Those questions expose the real security and correctness properties beneath a convenient MultipartFile parameter.
