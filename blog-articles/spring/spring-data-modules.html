Spring Data 2026.0

Spring Data Modules

An expert comparison of MongoDB, Redis, Cassandra, Elasticsearch, Neo4j, JDBC, and R2DBC—covering repositories, templates, mapping, native query models, transactions, reactive execution, and polyglot persistence.

Spring Data release train 2026.0 Spring Framework 7.0.8 baseline Imperative and reactive APIs Long-form technical article Vancouver references
Abstract. Spring Data Commons defines shared repository, mapping, conversion, auditing, pagination, and lifecycle concepts. Store modules adapt those concepts to radically different databases: MongoDB documents and aggregations; Redis keys, hashes, streams, and atomic commands; Cassandra partition-oriented tables and CQL; Elasticsearch indexes and search hits; Neo4j labeled property graphs and Cypher; JDBC aggregate persistence over blocking relational drivers; and R2DBC aggregate persistence over reactive relational drivers. The modules deliberately preserve store-native semantics. A repository method does not make Redis transactional like a relational database, turn Elasticsearch into a system of record, make Cassandra support arbitrary joins, or make JDBC reactive. This article identifies the stable common core, the module-specific boundaries, and the architectural consequences of combining several modules in one application.

Spring Data 2026.0, identified as generation 4.1, became generally available in June 2026. Its release train BOM aligns compatible module versions even though individual modules retain independent version numbers: MongoDB and Cassandra 5.1, Redis and Relational 4.1, Elasticsearch 6.1, and Neo4j 8.1 in the current documentation set.[1][2]

1. The Spring Data common core

Spring Data’s repository abstraction aims to reduce data-access boilerplate while keeping modules free to implement store-specific queries and behavior. Common repository interfaces, query-method parsing, projections, paging types, entity callbacks, auditing, object conversion, and exception translation form a consistent vocabulary. Each store module then supplies a repository factory, mapping context, converter, template or operations API, transaction integration, and native-query support.[3]

1 A domain type declares store mapping through conventions and annotations.
2 A module-specific mapping context builds metadata for that type.
3 A converter translates domain values to the store’s representation.
4 A template or operations API exposes explicit store-native operations.
5 A repository proxy delegates CRUD and query methods to module infrastructure.
6 Spring transaction and exception abstractions integrate where the store supports corresponding semantics.

1.1 Templates versus repositories

RepositoryBest for aggregate-oriented CRUD, concise query methods, paging, projections, and domain-specific collection-like interfaces.
Template/operationsBest for ad hoc queries, partial updates, bulk operations, pipelines, scripts, native options, callbacks, and explicit control.
Native clientBest for capabilities not modeled by the module, with greater coupling and responsibility for mapping and transactions.

Repositories and templates normally share the same mapping converter. Moving from a repository to a template is therefore not abandoning Spring Data; it is selecting a lower-level abstraction for a use case that does not fit a generated interface.

1.3 Multiple repository modules

When several repository factories are present, Spring Data must bind each repository to exactly one module. Module-specific repository interfaces, identifying mapping annotations, and explicitly separated scan packages remove ambiguity. Avoid applying multiple store annotations such as MongoDB and Elasticsearch @Document variants to one domain class merely to reuse it across stores; persistence models usually diverge in shape and lifecycle.[3]

Java 
@Configuration(proxyBeanMethods = false)
@EnableMongoRepositories(
    basePackages = "com.example.catalog.mongo")
@EnableRedisRepositories(
    basePackages = "com.example.session.redis")
@EnableJdbcRepositories(
    basePackages = "com.example.orders.jdbc")
class MultiStoreRepositoryConfiguration {
}
A common interface is not common semantics CrudRepository.save() is implemented according to each store’s model. Query keywords, transactions, generated identifiers, optimistic locking, relationship handling, paging cost, and consistency guarantees remain module-specific.

3. Spring Data MongoDB

Spring Data MongoDB 5.1 provides object mapping, MongoTemplate, repository proxies, criteria and update DSLs, aggregations, geospatial support, sessions and multi-document transactions, change streams, sharding support, search, vector search, encryption, and reactive counterparts.[4][5]

3.1 Document mapping

Java 
@Document("catalog_item")
public class CatalogItem {

    @Id
    private String id;

    @Indexed(unique = true)
    private String sku;

    private String name;

    private Money price;

    private Set<String> tags = new LinkedHashSet<>();

    @Version
    private Long version;

    protected CatalogItem() {
    }

    public CatalogItem(
            String sku,
            String name,
            Money price) {
        this.sku = sku;
        this.name = name;
        this.price = price;
    }
}

MongoDB mapping normally embeds value objects directly in the owning document. This makes aggregate reads efficient but creates document-growth and update-contention trade-offs. References to other aggregates should be represented deliberately rather than assumed to behave like JPA lazy relationships.

3.2 Repository

Java 
public interface CatalogItemRepository
        extends MongoRepository<CatalogItem, String> {

    Optional<CatalogItem> findBySku(String sku);

    Page<CatalogItem>
        findByTagsContainingAndPriceAmountBetween(
            String tag,
            BigDecimal minimum,
            BigDecimal maximum,
            Pageable pageable);
}

MongoDB repository queries derive field criteria from property paths. Page still requires a count query, while Slice avoids exact totals. Derived names are appropriate for simple predicates; aggregation pipelines, array updates, geospatial queries, and partial updates usually belong in MongoTemplate or a custom repository fragment.[6]

3.3 Template and atomic update

Java 
@Repository
final class CatalogInventoryOperations {

    private final MongoTemplate mongo;

    CatalogInventoryOperations(MongoTemplate mongo) {
        this.mongo = mongo;
    }

    UpdateResult decrementIfAvailable(
            String sku,
            int amount) {

        Query query = Query.query(
            Criteria.where("sku").is(sku)
                .and("available").gte(amount));

        Update update = new Update()
                .inc("available", -amount)
                .currentDate("updatedAt");

        return mongo.updateFirst(
                query,
                update,
                CatalogItem.class);
    }
}

A guarded update performs the invariant check and mutation in one server operation. Loading a document, checking a number in Java, and saving later introduces a race unless versioning or a transaction protects the decision.

3.4 Transactions and reactive execution

MongoDB transactions require a client session and an appropriate deployment topology. Spring can manage imperative and reactive MongoDB transactions, but a transaction should not be the default substitute for aggregate design: embedding related state in one document often provides a simpler atomic boundary. Reactive repositories and ReactiveMongoTemplate use reactive driver publishers and Reactor-context transaction participation.[5][7]

4. Spring Data Redis

Spring Data Redis 4.1 integrates Lettuce and Jedis drivers and offers RedisTemplate, ReactiveRedisTemplate, repositories, serialization, transactions, pipelining, cache integration, Pub/Sub, Streams, scripting, and collection-like abstractions.[8][9]

4.1 Template and serialization

Java 
@Bean
RedisTemplate<String, SessionView>
        sessionRedisTemplate(
            RedisConnectionFactory connectionFactory,
            ObjectMapper objectMapper) {

    RedisTemplate<String, SessionView> template =
            new RedisTemplate<>();

    template.setConnectionFactory(
            connectionFactory);
    template.setKeySerializer(
            new StringRedisSerializer());
    template.setValueSerializer(
            new JacksonJsonRedisSerializer<>(
                objectMapper,
                SessionView.class));

    return template;
}

Serialization is part of the persisted data contract. Changing from Java serialization to JSON, renaming fields, or changing type metadata can make existing values unreadable. Configure serializers explicitly and version long-lived key formats.

4.2 Redis repositories

Java 
@RedisHash(
    value = "session",
    timeToLive = 3600)
public class SessionRecord {

    @Id
    private String id;

    @Indexed
    private UUID accountId;

    private Instant authenticatedAt;

    private Set<String> authorities;
}

public interface SessionRepository
        extends CrudRepository<SessionRecord, String> {

    List<SessionRecord> findByAccountId(
            UUID accountId);
}

Redis repositories map objects to hashes and maintain secondary index structures for indexed properties. TTL can be part of mapping metadata. They are useful for key-addressed aggregate records, but they are not a general query engine: query methods depend on maintained indexes and referenced objects are persisted separately.[10]

Redis repositories do not participate in Redis transactions The current Redis repository documentation explicitly states that repositories do not work with transaction-enabled RedisTemplate usage. Use template operations, Lua scripts, atomic commands, or explicitly designed transactional command sequences when multiple keys must change together.[10]

4.3 Atomic commands, scripts, and pipelines

Java 
Boolean acquired = redisTemplate
        .opsForValue()
        .setIfAbsent(
            "lock:invoice:" + invoiceId,
            ownerToken,
            Duration.ofSeconds(30));

Prefer one atomic Redis command when it expresses the invariant. Lua scripts execute server-side and can atomically coordinate several keys. Pipelining reduces network round trips but is not atomic. Redis transactions queue commands and execute them together, but their failure and watch semantics differ from relational rollback.

4.4 Reactive Redis

Java 
Mono<Boolean> remember(
        String key,
        SessionView value) {

    return reactiveRedisTemplate
        .opsForValue()
        .set(
            key,
            value,
            Duration.ofMinutes(30));
}

Reactive Redis uses non-blocking driver APIs. Do not invoke blocking repository or template operations on a reactive event loop. Cache access can be reactive while a system-of-record update remains relational, but that combination is not one transaction.

5. Spring Data Cassandra

Spring Data Cassandra 5.1 supplies CQL templates, object-mapping templates, repositories, reactive and asynchronous variants, prepared-statement integration, query/update DSLs, auditing, and vector-search support. The module is built over the DataStax Java Driver.[11][12]

5.1 Model from the query

Cassandra tables are designed around partition keys, clustering columns, and known access paths. Repository method names do not create missing indexes or make unrestricted filtering efficient. Start with the query, choose a partition key that distributes load, and order clustering columns for required range scans.

Java 
@PrimaryKeyClass
public record EventKey(

    @PrimaryKeyColumn(
        name = "tenant_id",
        type = PrimaryKeyType.PARTITIONED,
        ordinal = 0)
    UUID tenantId,

    @PrimaryKeyColumn(
        name = "day",
        type = PrimaryKeyType.PARTITIONED,
        ordinal = 1)
    LocalDate day,

    @PrimaryKeyColumn(
        name = "occurred_at",
        type = PrimaryKeyType.CLUSTERED,
        ordinal = 2,
        ordering = Ordering.DESCENDING)
    Instant occurredAt,

    @PrimaryKeyColumn(
        name = "event_id",
        type = PrimaryKeyType.CLUSTERED,
        ordinal = 3)
    UUID eventId) {
}

@Table("tenant_event")
public class TenantEvent {

    @PrimaryKey
    private EventKey key;

    private String eventType;

    private String payload;
}

5.2 Repository and partition-scoped query

Java 
public interface TenantEventRepository
        extends CassandraRepository<
            TenantEvent,
            EventKey> {

    Slice<TenantEvent>
        findByKeyTenantIdAndKeyDay(
            UUID tenantId,
            LocalDate day,
            Pageable pageable);
}

This query supplies the complete partition key and walks rows in clustering order. Cross-partition scans, joins, and relational-style ad hoc predicates do not become good Cassandra queries because a repository method compiles.

5.3 Template variants

Java 
Query query = Query.query(
        Criteria.where("tenant_id")
            .is(tenantId))
    .and(
        Criteria.where("day")
            .is(day))
    .sort(
        Sort.by(
            Sort.Order.desc("occurred_at")))
    .pageRequest(
        CassandraPageRequest.first(100));

Slice<TenantEvent> events =
        cassandraTemplate.slice(
            query,
            TenantEvent.class);

CqlTemplate, AsyncCqlTemplate, and ReactiveCqlTemplate expose CQL-oriented operations. CassandraTemplate and its asynchronous/reactive variants add object mapping. Template instances are thread-safe after configuration.[12][13]

5.4 Consistency and paging state

Cassandra consistency level, replication, partition scope, lightweight transactions, and driver paging state determine behavior. A Spring Pageable abstraction does not imply offset pagination in Cassandra; native paging uses continuation state. Avoid exposing arbitrary high page numbers for a store whose efficient navigation is cursor-like.

6. Spring Data Elasticsearch

Spring Data Elasticsearch 6.1 targets the 2026.0 release train and documents compatibility with Elasticsearch 9.4.2. It provides imperative and reactive clients, mapping, ElasticsearchOperations, repositories, query DSL integration, search hits, routing, joins, scripted fields, and runtime fields.[14][15]

6.1 Index document

Java 
@Document(
    indexName = "catalog-product-v1",
    createIndex = false)
public class ProductSearchDocument {

    @Id
    private String id;

    @Field(type = FieldType.Keyword)
    private String sku;

    @Field(
        type = FieldType.Text,
        analyzer = "english")
    private String name;

    @Field(type = FieldType.Keyword)
    private Set<String> categories;

    @Field(type = FieldType.Scaled_Float)
    private BigDecimal price;

    @Field(type = FieldType.Date)
    private Instant updatedAt;
}

Index mappings are deployment artifacts. Production systems commonly create versioned indexes through controlled migration and switch aliases after reindexing rather than allowing every application startup to create or mutate mappings.

6.2 Repository

Java 
public interface ProductSearchRepository
        extends ElasticsearchRepository<
            ProductSearchDocument,
            String> {

    Page<ProductSearchDocument>
        findByNameContainingAndCategories(
            String text,
            String category,
            Pageable pageable);
}

Repository derivation is useful for straightforward field queries. Search applications usually need relevance scores, highlights, aggregations, total-hit relations, routing, point-in-time search, or vector queries; these belong in ElasticsearchOperations or a custom fragment.[16]

6.3 Search hits

Java 
Criteria criteria =
        Criteria.where("name")
            .matches(searchText)
            .and("categories")
            .is(category);

CriteriaQuery query =
        new CriteriaQuery(criteria)
            .setPageable(
                PageRequest.of(
                    0,
                    25));

SearchHits<ProductSearchDocument> hits =
        operations.search(
            query,
            ProductSearchDocument.class);

List<ProductResult> results =
        hits.stream()
            .map(hit ->
                new ProductResult(
                    hit.getContent(),
                    hit.getScore(),
                    hit.getHighlightFields()))
            .toList();

SearchHits preserves search metadata that a plain entity list discards. Elasticsearch is normally a derived read model, not the sole authority for payment, inventory, or other strongly consistent transactional state. Near-real-time index visibility and asynchronous projection updates must be part of the API contract.

6.4 No cross-document application transaction

Spring transaction annotations cannot turn Elasticsearch indexing plus a relational update into one atomic commit. Use an outbox or change-data-capture pipeline, assign idempotent event identifiers, and make indexing retryable. Alias-based reindexing and version checks are search-index operational concerns rather than relational transaction semantics.

7. Spring Data Neo4j

Spring Data Neo4j 8.1 maps labeled property graphs and provides imperative and reactive repositories, a mapping-aware template, a low-overhead client over the Neo4j Java Driver, Spring transaction integration, projections, auditing, and custom Cypher queries.[17][18]

7.1 Nodes and relationships

Java 
@Node("Person")
public class PersonNode {

    @Id
    @GeneratedValue
    private Long id;

    @Property("external_id")
    private UUID externalId;

    private String name;

    @Relationship(
        type = "FOLLOWS",
        direction = Relationship.Direction.OUTGOING)
    private Set<PersonNode> follows =
            new LinkedHashSet<>();
}

Graph mapping should reflect traversal ownership and loading requirements. Large, cyclic graphs must not be treated as object graphs to load recursively without bounds. Use projections and explicit Cypher to shape graph reads.

7.2 Repository and Cypher

Java 
public interface PersonGraphRepository
        extends Neo4jRepository<PersonNode, Long> {

    Optional<PersonNode> findByExternalId(
            UUID externalId);

    @Query("""
        MATCH (start:Person {external_id: $personId})
        MATCH path =
            (start)-[:FOLLOWS*1..3]->(candidate:Person)
        WHERE candidate.external_id <> $personId
        RETURN candidate,
               min(length(path)) AS distance
        ORDER BY distance, candidate.name
        LIMIT $limit
        """)
    List<PersonRecommendation> recommend(
            UUID personId,
            long limit);
}

7.3 Client and template layers

Neo4jClient and ReactiveNeo4jClient are mapping-agnostic fluent layers over the driver and integrate with Spring-managed transactions. Neo4jTemplate and ReactiveNeo4jTemplate add domain mapping, and simple repositories delegate to the template. The module advises against mixing imperative and reactive styles in one application.[19][20]

Java 
Collection<Map<String, Object>> counts =
        neo4jClient.query("""
            MATCH (p:Person)-[:FOLLOWS]->(other:Person)
            WHERE p.external_id = $personId
            RETURN other.country AS country,
                   count(*) AS followers
            ORDER BY followers DESC
            """)
        .bind(personId)
        .to("personId")
        .fetch()
        .all();

Direct use of the raw Neo4j driver can bypass Spring transaction synchronization if it is not obtained and used through the configured Spring Data infrastructure. Use the same driver instance for clients and transaction managers.[19]

8. Spring Data JDBC

Spring Data JDBC in Spring Data Relational 4.1 provides aggregate mapping and repositories over JDBC. It intentionally omits a persistence session, lazy loading, dirty tracking, and first-level cache. Loading executes SQL and returns a fully loaded aggregate; saving is explicit.[21][22]

8.1 Aggregate mapping

Java 
@Table("purchase_order")
public class PurchaseOrder {

    @Id
    private UUID id;

    private String externalReference;

    private OrderStatus status;

    @MappedCollection(
        idColumn = "order_id",
        keyColumn = "line_number")
    private List<OrderLine> lines =
            new ArrayList<>();

    private AggregateReference<
        Customer,
        UUID> customer;

    @Version
    private Long version;
}

@Table("order_line")
public record OrderLine(
        String sku,
        int quantity,
        BigDecimal unitPrice) {
}

All entities reachable from the aggregate root are treated as part of the aggregate. References to other aggregate roots should be represented as identifiers or AggregateReference. The current implementation can delete and recreate referenced child rows during aggregate updates, making aggregate size and write frequency important design constraints.[23][24]

8.2 Repository and explicit save

Java 
public interface PurchaseOrderRepository
        extends ListCrudRepository<
            PurchaseOrder,
            UUID> {

    Optional<PurchaseOrder>
        findByExternalReference(
            String externalReference);
}

@Service
final class SubmitOrderService {

    private final PurchaseOrderRepository orders;

    @Transactional
    void submit(UUID id) {
        PurchaseOrder order =
                orders.findById(id)
                    .orElseThrow();

        order.submit();

        orders.save(order);
    }
}

Unlike JPA, changing a loaded object does not trigger dirty checking. The aggregate must be saved explicitly. JDBC transaction management remains ordinary Spring JDBC transaction management, so repository and JdbcTemplate operations can share the same thread-bound connection when configured against the same DataSource.

8.3 Aggregate template and custom SQL

JdbcAggregateTemplate exposes mapping-aware aggregate persistence without requiring repository interfaces. For reporting, joins, window functions, and carefully tuned SQL, use JdbcTemplate or a custom repository fragment rather than forcing a relational report into aggregate loading.

Spring Data JDBC is not a small JPA It is a different model: explicit aggregate saves, no transparent lazy loading, and intentionally limited relationships. This simplicity is valuable when the domain fits aggregate replacement and SQL remains visible.

9. Spring Data R2DBC

Spring Data R2DBC 4.1 applies the Spring Data Relational aggregate model to non-blocking R2DBC drivers. R2dbcEntityTemplate is the central mapping-aware API, and reactive repositories expose Mono and Flux return types.[25][26]

9.1 Reactive repository

Java 
public interface CustomerRepository
        extends ReactiveCrudRepository<
            Customer,
            Long> {

    Mono<Customer> findByEmail(String email);

    Flux<Customer> findByStatusOrderById(
            CustomerStatus status);
}

9.2 Entity template

Java 
Flux<CustomerSummary> findActiveCustomers(
        Instant createdAfter) {

    Query query = Query.query(
        Criteria.where("status")
            .is(CustomerStatus.ACTIVE)
            .and("created_at")
            .greaterThanOrEquals(createdAfter))
        .sort(Sort.by("id"));

    return template.select(
            query,
            Customer.class)
        .map(CustomerSummary::from);
}

9.3 Reactive transaction boundary

Java 
TransactionalOperator operator =
        TransactionalOperator.create(
            reactiveTransactionManager);

Mono<TransferReceipt> transfer =
        accounts.debit(sourceId, amount)
            .flatMap(updated -> {
                if (!updated) {
                    return Mono.error(
                        new InsufficientFundsException());
                }
                return accounts.credit(
                    targetId,
                    amount);
            })
            .then(transfers.record(
                sourceId,
                targetId,
                amount));

return operator.transactional(transfer);

Reactive transaction state is carried in Reactor context, not a thread-local. Every participating database operation must remain in the same publisher chain and use the same transaction-aware ConnectionFactory. Calling blocking JDBC inside the chain neither becomes reactive nor joins the R2DBC transaction.

9.4 Relational does not mean JDBC-compatible behavior

R2DBC drivers vary in supported data types, generated-key behavior, batching, isolation, and database dialect support. Spring Data R2DBC lists directly supported databases and requires a dialect provider for others. Validate the chosen driver and database combination rather than assuming that an existing JDBC driver implies equivalent R2DBC support.[26]

10. Polyglot persistence

A mature system can use several modules because each model solves a different access pattern:

  • Spring Data JDBC stores the authoritative order aggregate.
  • Spring Data Elasticsearch stores a denormalized search projection.
  • Spring Data Redis stores short-lived session and rate-limit state.
  • Spring Data Neo4j stores recommendation relationships.
  • Spring Data MongoDB stores flexible product content or event documents.
  • Spring Data Cassandra stores high-volume tenant/time-partitioned events.

10.1 Do not pretend several stores are one transaction

A method annotated @Transactional and calling three repositories does not automatically create one atomic unit across JDBC, Redis, and Elasticsearch. Most polyglot designs use one authoritative transaction plus durable events:

1 Update the system of record and insert an outbox event in one local database transaction.
2 Publish the committed event asynchronously.
3 Update search, cache, graph, or document projections idempotently.
4 Store consumer offsets or event identifiers to make retry safe.
5 Rebuild derived stores from authoritative data when necessary.

10.2 Use separate persistence models

Java 
// Relational write model
@Table("product")
public class ProductAggregate {
    @Id UUID id;
    String sku;
    Money price;
    ProductState state;
    Long version;
}

// Elasticsearch read model
@Document(indexName = "product-search-v1")
public class ProductSearchDocument {
    @Id String id;
    String sku;
    String name;
    Set<String> categories;
    BigDecimal price;
    String availability;
}

// Redis cache model
public record ProductCacheEntry(
        UUID id,
        String name,
        BigDecimal price,
        Instant sourceVersion) {
}

Separate models make duplication explicit and allow each store’s denormalization, indexing, serialization, TTL, and schema-evolution needs to differ. Sharing one annotated class across modules creates accidental coupling and ambiguous repository binding.

12. Testing module integrations

12.1 Test against the real engine

Embedded substitutes often miss native behavior: MongoDB transaction topology, Redis Lua and expiry, Cassandra partitioning and paging state, Elasticsearch analyzers and mappings, Neo4j Cypher plans, relational dialects, and R2DBC driver behavior. Use disposable real services in integration tests and pin server versions compatible with the module documentation.

12.2 Per-module contracts

  • MongoDB: indexes, optimistic versions, aggregation output, transaction topology, and document growth.
  • Redis: serializers, TTL refresh, secondary-index cleanup, scripts, cluster key slots, and eviction.
  • Cassandra: partition distribution, consistency, paging state, clustering order, and tombstones.
  • Elasticsearch: analyzers, mappings, relevance, total-hit behavior, aliases, and reindex compatibility.
  • Neo4j: constraints, Cypher cardinality, bounded graph projections, transaction retry, and database selection.
  • JDBC: aggregate child replacement, constraints, locking, dialect SQL, and transaction boundaries.
  • R2DBC: publisher cancellation, backpressure, transaction context, generated keys, and driver errors.

12.3 Projection and recovery tests

Test duplicate event delivery, out-of-order delivery, consumer restart, unavailable derived stores, stale cache reads, reindexing, and full projection rebuild. A polyglot architecture is correct only if it converges after ordinary failures.

13. Operational concerns

13.1 Observe native operations

Record module-specific signals: MongoDB command latency and pool wait; Redis command and script latency, memory, eviction, and keyspace events; Cassandra coordinator latency, retries, consistency, and tombstones; Elasticsearch query latency, shard failures, refresh and indexing lag; Neo4j query plans and transaction retries; JDBC connection, lock, and SQL metrics; R2DBC connection acquisition, cancellation, and publisher latency.

13.2 Treat schema and indexes as deployment artifacts

Repository startup is not a substitute for controlled schema management. Relational DDL, Cassandra tables, MongoDB indexes and validators, Elasticsearch mappings and aliases, Neo4j constraints, and Redis key-version migrations need reviewed deployment workflows and rollback plans.

13.3 Timeouts and retries

Configure driver timeouts and pool limits explicitly. Retry only errors documented as transient, and retry complete idempotent operations. A retry policy appropriate for a Cassandra timeout can be harmful for an Elasticsearch indexing conflict or a relational serialization failure.

14. Diagnostics

14.1 Repository binds to the wrong module

Separate base packages, use module-specific repository interfaces, and avoid multiple identifying mapping annotations on one type. Inspect repository bootstrap logs when several Spring Data modules are present.

14.2 A derived method works in one module but not another

Query keywords and property traversal have a common grammar, but modules implement only operations their stores can express. Replace the method with a template/native query or redesign the access path.

14.3 @Transactional gives unexpected results

Identify the selected transaction manager and the actual resource. Redis repository operations, Elasticsearch indexing, raw Neo4j driver work, JDBC, and reactive R2DBC do not share one implicit transaction.

14.4 Reactive endpoint stalls under load

Search for blocking repository/template calls, filesystem work, synchronous mapping callbacks, and blocking driver usage on event-loop threads. A Mono wrapper does not make a blocking module non-blocking.

14.5 Search or cache disagrees with the system of record

Measure projection lag, inspect failed events, replay idempotently, and expose freshness semantics. Do not “fix” the discrepancy with an unsafe cross-store dual write.

15. Expert practices

15.1 Start with the native data model

Design documents, keys, partitions, indexes, graphs, and aggregates for the store. Add Spring Data abstractions after the access model is valid.

15.2 Drop to the template early enough

A long derived method name is a signal, not a badge. Use the module template or a custom repository fragment for pipelines, partial updates, scripts, graph traversals, or advanced search.

15.3 Keep one repository per aggregate or projection root

Do not turn repositories into table gateways or expose unrestricted generic CRUD when domain invariants require named operations.

15.4 Separate multi-store models

Duplicate data intentionally and synchronize it through durable events. Let each model use store-specific denormalization, indexing, and lifecycle.

15.5 Choose imperative or reactive end to end

Reactive modules help only when the driver, transaction manager, service composition, and web stack remain non-blocking. Do not mix styles casually within one unit of work.

15.6 Use the release-train BOM

Module version numbers differ. Let Spring Boot or the Spring Data BOM select compatible artifacts, and follow each module’s server/client compatibility matrix.

15.7 Design recovery before dual writes

Use outbox, CDC, idempotent consumers, reconciliation, and rebuildable projections. Cross-store failure is a normal operating condition.

15.8 Measure generated behavior

Repositories generate native commands. Log and trace the query shape, result cardinality, paging strategy, transaction, consistency level, and retry path appropriate to the selected store.

16. Summary

  • Spring Data Commons supplies a shared programming vocabulary, not identical database semantics.
  • The 2026.0 BOM aligns modules whose individual versions range from 4.1 to 8.1.
  • MongoDB centers on mapped documents, MongoTemplate, aggregations, sessions, transactions, and reactive driver support.
  • Redis centers on explicitly serialized keys and data structures; repositories map hashes and indexes but do not work with transaction-enabled template behavior.
  • Cassandra centers on partition-key access paths, clustering order, CQL, consistency, and continuation-based paging.
  • Elasticsearch centers on index mappings, search metadata, relevance, aggregations, and derived read models rather than cross-document application transactions.
  • Neo4j centers on graph mapping, Cypher, a transaction-aware client, a mapping-aware template, and bounded graph projections.
  • Spring Data JDBC provides explicit aggregate persistence without sessions, lazy loading, or dirty tracking.
  • Spring Data R2DBC applies relational aggregate mapping to reactive drivers and Reactor-context transactions.
  • Polyglot persistence requires separate models, one authoritative transaction, durable events, idempotent projection updates, and recovery workflows.

Diagnose a Spring Data system by asking two sets of questions. First, what is common: which repository factory, converter, callback, projection, paging type, and transaction abstraction is involved? Second, what is native: which document update, Redis command, CQL partition, Elasticsearch query, Cypher traversal, SQL statement, consistency level, driver, and failure model actually executed? The first set explains the Spring programming model; the second determines correctness and performance.
