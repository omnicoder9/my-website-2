The Twelve Disciplines of Production Spring

On 30 June 2026 the last open-source branch of Spring Boot 3 stopped receiving security patches. The 3.5 line shipped its final community release five days earlier, and with it the entire 3.x generation — the generation that carried the javax-to-jakarta migration, the first native-image story, and the Observation API — passed out of free maintenance.1,2 Anything still running on it is running on a codebase that will not be fixed. That is the practical backdrop against which any discussion of Spring best practice now takes place: the framework moves, the ground moves under it, and a practice that was correct in 2019 may today be a finding in an audit.

It is worth remembering how thoroughly the framework's own guidance has reversed itself. The Spring 3.0 reference manual stated plainly that the team “generally advocates setter injection,” on the reasoning that large constructor argument lists become unwieldy.3 The current manual says the opposite: constructors for mandatory dependencies, setters or configuration methods only for genuinely optional ones.4 Neither statement was wrong when written. What changed was the surrounding cost structure — immutability became cheap, containers became fast, and the population of Spring applications shifted from long-lived monoliths configured once to fleets of services restarted thousands of times a day. Best practice in Spring is not a fixed doctrine. It is a moving equilibrium between what the container makes easy and what production makes expensive.

This article works through twelve disciplines. Each is treated the same way: what the default behaviour actually is, where that default stops being adequate, what the current framework gives you to replace it, and what evidence should trigger the change. The material is current through Spring Framework 7.0 and Spring Boot 4.1 — the November 2025 and June 2026 releases respectively — which set a Java 17 baseline while targeting Java 25, move to Jakarta EE 11, adopt JSpecify for nullness, split Boot's autoconfiguration into focused modules, and add first-class API versioning and HTTP service clients.5,6,7

Two framing assumptions run through everything below. The first is that a framework's defaults are a political settlement, not a technical optimum: they encode what the maintainers judged safest for the median application, and your application is not the median. The second is that most Spring pathology is not exotic. It is a small set of recurring failures — a dependency discovered at runtime instead of start-up, an entity serialised straight onto the wire, a connection pool sized by superstition, a log line that costs more than the request it describes — repeated across thousands of codebases.

01

Wiring

Constructor injection

Make the dependency set part of the type, so the container can refuse to start rather than the request refuse to complete.

Constructor injection is the most settled recommendation in the Spring world, and also the most commonly misunderstood, because the usual argument for it — “it makes testing easier” — is the weakest one available. Testing is easier, but that is a consequence. The substantive argument is about when errors become visible and what the type system is permitted to know.

What the container can and cannot verify

A bean's dependencies are either part of its type or they are not. With constructor injection they are: the set of collaborators is the constructor signature, the container resolves it during refresh(), and a missing or ambiguous bean aborts start-up with a diagnostic that names the type, the injection point, and the candidates it considered. With field injection the dependency set is invisible to the compiler, reflection populates it after construction, and any gap — a conditional autoconfiguration that did not fire, a profile that was not active, an @Autowired(required = false) that quietly resolved to null — surfaces as a NullPointerException at whatever hour production first exercises that path.

The immutability argument is separate and equally load-bearing. Fields assigned in a constructor can be final; fields populated by reflection cannot. Final fields give you safe publication under the Java memory model without any explicit synchronisation, which matters because Spring singletons are, by construction, shared across every request thread in the application. A non-final field on a singleton is a mutable shared variable that happens to be written only once, by a framework, during a phase you cannot easily reason about.

Two details in that second listing are worth naming. The constructor carries no @Autowired annotation, because since Spring 4.3 a class with exactly one constructor has it applied implicitly — which means the class has no compile-time dependency on Spring at all and can be instantiated directly by a test, a batch job, or a future caller that does not use a container.4 And optionality is expressed with ObjectProvider rather than a nullable field, so the absence of an auditor is a branch in the code rather than a latent null.

Circular dependencies are a design signal, not a configuration problem

Constructor injection cannot express a cycle: to construct A you need B, to construct B you need A, and the container throws BeanCurrentlyInCreationException.4 Historically the escape hatch was to switch one side to setter injection, and the framework documented that escape while advising against it. Spring Boot 2.6 closed it by default — spring.main.allow-circular-references is false, and applications that relied on cycles now fail to start.8 This was correctly received as a breaking change and incorrectly received as an inconvenience. A cycle between two beans almost always means a third concept is missing: some piece of coordination logic that belongs in neither collaborator has been smeared across both. Extracting it removes the cycle and usually removes a test that nobody could write.

The self-invocation trap
Constructor injection interacts badly with one specific pattern: a bean calling its own @Transactional or @Cacheable method. Spring's declarative behaviour is proxy-based, so an internal this.method() call bypasses the proxy entirely and the annotation silently does nothing. 9,10 Injecting the bean into itself “fixes” it and should never survive review; the correct fix is to move the annotated method to a collaborator, which is what the annotation was telling you about your boundaries in the first place.

When the argument list gets long

The standard objection — that constructor injection produces eight-argument constructors — is true and is the point. A class requiring eight collaborators has eight reasons to change, and the constructor is the only place in the codebase where that fact is impossible to overlook. Field injection does not reduce the coupling; it hides it. When the list grows, the useful responses are to extract a cohesive subset into a collaborator of its own, or to notice that several of the arguments are really configuration and belong in a bound @ConfigurationProperties record. Suppressing the symptom with Lombok's @RequiredArgsConstructor is defensible for boilerplate reduction but removes the visual pressure that made the smell legible.

Spring Framework 7 adds a further compile-time dimension. The portfolio has migrated to JSpecify annotations, which give static analysers and the Kotlin compiler a precise nullness contract on parameters, return types, generics and array elements.11,12 Combined with constructor injection, a well-annotated bean now expresses its entire collaborator contract — presence, type, and nullability — in a form that tools can check before the container ever starts.

Review ledger

Hold the line on

  • One constructor, all mandatory dependencies, all fields final.
  • ObjectProvider<T> or Optional<T> for genuinely optional collaborators.
  • A Clock bean injected wherever code reads the current time.
  • Growing argument lists treated as a decomposition prompt.
  • JSpecify annotations on public constructors and factory methods.

Flag in review

  • @Autowired on fields, in any class, including tests.
  • @Autowired(required = false) on a field — it produces a null, not an absence.
  • spring.main.allow-circular-references=true anywhere in the tree.
  • A bean injected into itself, or @Lazy used to break a cycle.
  • this.transactionalMethod() — the proxy is not in that call path.
02

Structure

Layered architecture

Layers are a means, not an end. What matters is the direction of dependency at the persistence boundary, and whether anything checks it.

Almost every Spring application starts with the same three packages: controller, service, repository. It is a reasonable first cut, it matches the framework's stereotype annotations, and it survives roughly until the second bounded context arrives. The failure mode is well documented and predictable: the domain objects become anaemic data carriers, the service classes accumulate procedural scripts, and every feature change touches all three packages because the packages are organised by technical role rather than by reason to change.13,14

The rule that actually matters

Strip away the vocabulary of hexagons, onions and clean architecture and one rule remains: source-code dependencies point toward policy, never toward mechanism.15,14 In Spring terms, the domain package should compile with no import of jakarta.persistence, no import of org.springframework.web, and ideally no import of Spring at all. The repository interface belongs to the domain, because the domain is what decides which questions it needs answered; the Spring Data implementation belongs to infrastructure, because that is an accident of the current database.

The structural benefit of this layout is deletability. When the invoicing capability is retired, one directory disappears and the build still passes. In the layer-first layout the same retirement requires archaeology across three packages, and the archaeology is never complete, which is why dead code accumulates in exactly those codebases.

Making the boundary executable

A boundary that is not checked by the build is a naming convention. Two tools make it executable at different price points. ArchUnit expresses architectural rules as ordinary JUnit tests over the compiled byte code, which costs a few seconds and catches the common violations.16 Spring Modulith goes further: it derives an application-module model from the package structure, verifies that cross-module access goes only through explicitly exposed types, and can generate documentation and integration tests per module.17

Where the transaction boundary goes

Layering arguments usually resolve into a single concrete question: which class carries @Transactional. The answer is the application service — the class that represents one business operation — and neither of its neighbours. On the repository it is too narrow, producing a transaction per statement and losing atomicity across a use case. On the controller it is too wide, holding a database connection open across serialisation and, if the request fans out to another service, across a network call you do not control.10,18

The related trap is spring.jpa.open-in-view, which Spring Boot enables by default and warns about at start-up.19 It keeps the persistence context open for the duration of the request so that lazy associations resolve during view rendering or JSON serialisation. That convenience means queries are issued from the serialisation layer, outside any transaction you declared, invisible to the service that appears to own the data access. Turning it off is a one-line change that converts a category of silent N+1 problems into loud LazyInitializationExceptions during testing, which is precisely the trade you want.

Entities are not wire contracts

The single most consequential boundary decision in a Spring application is whether JPA entities are serialised directly to HTTP clients. Doing so couples the public API to the database schema, so that a column rename becomes a breaking API change; it exposes every field to deserialisation binding, which is the mass-assignment vulnerability class;20 and it makes lazy loading a wire-format concern. Explicit request and response records, mapped by hand or by MapStruct,21 cost some typing and buy independent evolution of two contracts that genuinely change at different rates.

Review ledger

Hold the line on

  • Package by capability; keep a package-private internal subtree.
  • Repository interfaces in the domain, implementations in infrastructure.
  • @Transactional on the application service, sized to one business operation.
  • spring.jpa.open-in-view=false, set deliberately and early.
  • Boundaries asserted by ArchUnit or Spring Modulith in CI.

Flag in review

  • JPA entities returned from controllers or accepted as request bodies.
  • @Transactional on a controller method, or on a repository interface.
  • A util or common package that every module depends on.
  • Cross-module calls into another module's internal package.
  • Architecture documented only in a diagram nobody regenerates.

Failure

Exception handling

One representation, one place that produces it, and a status code chosen by what the caller should do next.

Error handling is where an API's design quality becomes legible to its consumers. A service that returns a 500 with an HTML stack trace for a validation failure, a 200 with {"error": "..."} for a business rejection, and a 403 for a missing record has no error model — it has an accumulation of local decisions. The fix is structural: one representation, one place that produces it, and a deliberate mapping from failure category to status code.

RFC 9457 as the default representation

Since Spring Framework 6 the framework ships ProblemDetail, an implementation of the IETF problem-details format standardised in RFC 9457, which obsoleted RFC 7807.22,23,24 The format defines five members — type, title, status, detail and instance — and allows arbitrary extensions, served under the application/problem+json media type. Its value is not the field names. It is that clients can be written once against a known envelope, and that the type URI gives you a stable, documentable identifier for a failure mode that survives rewording of the human-readable message.

For everything the domain does not model explicitly, a single @RestControllerAdvice extending ResponseEntityExceptionHandler inherits sensible handling of the framework's own exceptions — unreadable bodies, unsupported media types, binding failures — and lets you add the mappings specific to your application.24

Choosing the status code on purpose

RFC 9110 defines the semantics; the recurring mistake is treating the choice as cosmetic when clients make retry decisions from it.25 The operational question is not “what went wrong” but “what should the caller do next.” A 4xx says the caller can fix this by changing the request; a 5xx says the caller can do nothing but retry, and therefore that a retry with backoff is legitimate. Getting this backwards is expensive in both directions: returning 500 for a malformed request invites a retry storm against a request that will never succeed, and returning 400 for a transient downstream failure causes clients to discard work that would have succeeded a second later.

The distinction between 400, 422 and 409 is the one worth being deliberate about. Reserve 400 for requests that fail syntactic or schema validation; 422 for requests that are well-formed and schema-valid but semantically unacceptable; 409 for requests that conflict with current resource state and might succeed later without modification. That third category is exactly where optimistic locking failures and business-rule rejections belong, and it is the category most often mislabelled.

Logging, once, at the boundary

The catch-log-rethrow idiom produces the same failure three or four times in the log at different stack depths, each occurrence looking like a distinct incident to a text-matching alert rule. The discipline is simple: code that can handle an exception handles it and does not log it as an error; code that cannot handle it lets it propagate without comment; the boundary that converts it into a response logs it once, with the correlation identifier attached. Everything else is noise that will be paid for in storage and in the seconds an on-call engineer spends reconstructing which of four entries was the original.

Never leak the internals
Stack traces, SQL fragments, bean names, framework versions and internal hostnames in an error body are reconnaissance for an attacker and are classified under security misconfiguration in the OWASP Top 10. 26 Spring Boot's server.error.include-stacktrace defaults to never; the failure mode is a developer who set it to always during debugging and shipped the profile.
Review ledger

Hold the line on

  • ProblemDetail / application/problem+json for every error response.
  • A stable type URI per failure mode, documented alongside the API.
  • One @RestControllerAdvice, with a Throwable backstop.
  • A correlation id in the body so support and traces can be joined.
  • Status chosen by what the caller should do next, not by what broke.

Flag in review

  • Catch, log, rethrow — the same failure four times in the log.
  • Business failures reported as HTTP 200 with an error field in the payload.
  • catch (Exception e) { }, and its cousin, an empty catch with a TODO.
  • Stack traces, SQL, or bean names in a response body.
  • Exception messages assembled from user input and reflected verbatim.

Input

Validation

Four boundaries with four different jobs; most validation pain comes from asking one of them to do another's work.

Validation looks like a solved problem: annotate the DTO, add @Valid, done. It stays solved for about as long as the rules remain expressible as independent constraints on individual fields. The moment a rule references two fields, or another aggregate, or a different set of requirements for creation than for update, teams start improvising — and the improvisations scatter, so that the same business rule ends up implemented in a controller, a service, a database constraint, and a front-end form, with four subtly different definitions.

The productive way to think about this is that there is no single validation layer. There are four, each structurally incapable of seeing what the next one sees, and the design task is deciding which rule lives where rather than pretending one mechanism can carry all of them.

Jakarta Validation carries shape, not meaning

Jakarta Validation 3.1 — the specification formerly known as Bean Validation, and the Jakarta EE 11 baseline for Spring Framework 7 — is very good at one job: declaring the permissible shape of a value.27,5 Lengths, ranges, patterns, presence, and the composition of those into reusable custom constraints. Hibernate Validator is the reference implementation Spring Boot auto-configures.28,29 Where teams get into difficulty is asking it to carry meaning — availability, entitlement, uniqueness — which requires the validator to reach out to a repository and turn what should be a pure predicate into an I/O operation running inside a binding phase.

Two mechanisms exist for triggering it, and the distinction is not cosmetic. @Valid is the Jakarta annotation and cascades validation into a nested object graph. @Validated is Spring's own, and its distinguishing capability is validation groups — the mechanism for expressing that an identifier must be absent on create and present on update, without inventing two nearly-identical DTOs.29 Since Spring Framework 6.1, controller method parameters are validated by built-in method validation without requiring the class to be annotated at all, which removed one of the more obscure sources of “my constraint is being ignored.”

Rejecting input the framework has already accepted

The most security-relevant validation decision happens before any constraint runs. When a request body is bound to an object with more fields than the client should be permitted to set, the deserialiser will happily populate them: a role, an accountBalance, an id. This is mass assignment, and the durable defence is not a blocklist but a request type whose fields are exactly the fields a client may supply.20,30 Setting spring.jackson.deserialization.fail-on-unknown-properties=true converts an unexpected field from a silent ignore into a 400, which is a strong signal during integration and a reasonable posture in production for internal APIs — though it does make you the party responsible for coordinating client changes, so it is a decision to take with the versioning discipline in mind.

The invariant belongs to the domain

Constraint annotations can only guard the boundary they are attached to. A rule such as “a customer may not hold more than three open accounts” references state the DTO cannot see, and placing it in a ConstraintValidator that consults a repository produces a validator with a database dependency, a transaction question, and a race condition. Such rules belong in the aggregate — enforced in a factory method or constructor, so that an invalid object cannot be constructed at all — with a uniqueness constraint in the database as the backstop against the race.13

Finally, the responses. Binding failures surface as MethodArgumentNotValidException and method-validation failures as HandlerMethodValidationException; both are handled by ResponseEntityExceptionHandler and both should be rendered into the same ProblemDetail envelope as everything else, with the field errors carried in a documented extension member rather than in a prose detail string that clients will be forced to parse.

Review ledger

Hold the line on

  • A dedicated request record per endpoint, with exactly the client-settable fields.
  • Field constraints for shape; type-level assertions for cross-field rules.
  • Validation groups instead of near-duplicate create and update DTOs.
  • Domain invariants enforced in factories and constructors.
  • Field errors returned as a structured extension of the problem detail.

Flag in review

  • Entities bound directly to request bodies.
  • ConstraintValidator implementations that query a repository.
  • Check-then-act uniqueness logic instead of a database constraint.
  • Validation logic duplicated in the controller after @Valid has run.
  • Treating validation as authorisation — a well-formed request is not a permitted one.

Environment

Configuration management

Bind once into a typed, validated object, and let a bad value fail the deployment instead of the request.

Configuration is where the same binary becomes a development environment, a staging environment, and a regulated production deployment. Spring Boot's externalised configuration machinery is unusually capable — sixteen or so property sources arranged in a documented precedence order, relaxed binding across naming conventions, profile-specific documents, and type-safe binding to immutable records.31 The capability is also the hazard: a value can arrive from so many places that “where did this setting come from” becomes a genuine debugging exercise.

Bind once, into a typed object

The single highest-return change most codebases can make is replacing scattered @Value injections with @ConfigurationProperties bound to records.31 @Value resolves a string at injection time in whatever bean happens to need it, so the full configuration surface of the application is discoverable only by grepping; a typo produces either a start-up failure at an unhelpful location or, with a default supplied, silent wrong behaviour. Constructor binding to a record gives you one declaration site, real types, IDE completion, metadata generation, and — combined with @Validated — the ability to refuse to start when the configuration is wrong.

The refusal to start is the point. A service that boots with a missing downstream URL and fails every request is strictly worse than one that never becomes ready, because the first will be routed traffic by a load balancer that only checks liveness. Validated configuration properties turn a class of runtime incidents into deployment failures, which is the direction the arrow should always point.

Profiles are for environments, not for features

Profiles carry an implicit assumption that is easy to violate: that the code path exercised in development is the code path that runs in production.32 Using @Profile to swap a real implementation for a stub is legitimate for local development. Using it to enable or disable a business feature means the feature is tested in one configuration and shipped in another, and the failure is discovered in the environment where it costs most. Feature state belongs in configuration properties evaluated at runtime, or in a feature-flag service, where it can be toggled without a redeploy and observed in both states.

The genuinely dangerous variant is a security-relevant @Profile: a SecurityFilterChain bean annotated @Profile("!dev"), or a @Profile("dev") chain that permits everything. One misconfigured environment variable in a deployment manifest then produces an unauthenticated production service, and nothing in the application logs looks abnormal. Security configuration should be unconditional, with differences expressed as properties — issuer URIs, allowed origins — rather than as the presence or absence of an entire chain.

Secrets are configuration with a different threat model

The twelve-factor principle of strict separation between config and code remains correct, and its usual implementation — environment variables — remains adequate for non-secret values.33 Secrets deserve more: environment variables are inherited by child processes, visible in /proc on many systems, frequently captured by crash handlers, and routinely printed by well-meaning start-up diagnostics. Spring Boot's config-tree support reads each file in a directory as a property, which maps directly onto Kubernetes secrets mounted as volumes and keeps the value out of the process environment entirely.31

For secrets that must live in a repository — and there are legitimate reasons, notably keeping the deployment fully declarative — encrypt them at rest with a tool such as SOPS, which keeps the ciphertext diffable and the decryption key in a KMS.34 For credentials that should be short-lived rather than merely hidden, Spring Cloud Vault issues dynamic database credentials with a lease, which converts credential rotation from a quarterly project into a property of the runtime.35

Configuration that must never be dynamic
Two categories should be fixed at build time, not configured: the database schema version, which belongs to a migration tool such as Flyway or Liquibase running as part of deployment, 36,37 and anything whose incorrect value produces silent data corruption rather than a loud failure. A property that can quietly destroy data is not a property; it is a code path that needs a review.
Review ledger

Hold the line on

  • @ConfigurationProperties records with @Validated, scanned once.
  • Fail-fast on missing or invalid values — refuse to become ready.
  • Config trees or a secret manager for credentials; never application.yml.
  • Schema changes owned by a migration tool, versioned with the code.
  • show-values: never on the actuator env and configprops endpoints.

Flag in review

  • @Value scattered across services for anything but trivial constants.
  • Business features gated by @Profile.
  • A SecurityFilterChain whose existence depends on a profile.
  • Secrets in environment variables when a mounted volume is available.
  • Defaults for production-critical values that make a missing setting invisible.

Posture

Security by default

Spring Security's defaults are good. Most incidents begin with a developer switching one off to make something work.

Spring Security's defaults are, unusually among frameworks, aggressive in the right direction: add the starter and every endpoint requires authentication, CSRF protection is active, a set of security response headers is written, and passwords are hashed with an adaptive function.38,39,40 Most real incidents in Spring applications therefore begin with a developer switching a default off to make something work and never switching it back. The discipline is less about adding security than about understanding precisely what each default buys, so that turning it off is a decision with a stated reason.

Deny by default, and put the rule where the behaviour is

The authorizeHttpRequests block should end in anyRequest().authenticated() or anyRequest().denyAll(). This matters more than it appears: a rule set that ends in permitAll() silently grants access to every endpoint added afterwards by anyone on the team. Spring Security 7 removed the long-deprecated authorizeRequests and the and() chaining style entirely in favour of the lambda DSL, so upgrading applications will be revisiting these blocks anyway.41

Separate chains matched by securityMatcher are what makes the CSRF decision defensible. CSRF protection exists because browsers attach cookies automatically to cross-site requests; it is therefore necessary exactly when the browser holds an ambient credential and unnecessary when every request carries an explicit Authorization header.42 A single chain covering both a cookie-authenticated UI and a token-authenticated API forces a blanket decision, and the blanket decision taken under deadline pressure is always disable(). Spring Security 7 also adds a dedicated single-page-application CSRF mode for the increasingly common case where a JavaScript client holds a session cookie.

Method security is the gate that survives refactoring

URL-based rules protect the paths that exist when they are written. Method-level rules protect the operation regardless of how it is reached — and services acquire new callers constantly: a scheduled job, a message listener, a GraphQL resolver, an admin console, a test that was never meant to be a production code path.43 @EnableMethodSecurity is opt-in, and @PreAuthorize annotations in an application that never enabled it are decorative. That combination — annotations present, enforcement absent — is worth an explicit test.

Credentials, tokens and the current baseline

Password storage has a settled answer: a delegating encoder so that stored hashes carry their algorithm prefix and can be upgraded in place, with bcrypt as the framework default and Argon2id the current OWASP and IETF-documented preference for new systems.40,44,45 NIST SP 800-63B remains the reference for the surrounding policy, and its guidance has been stable and widely ignored for a decade: length over composition rules, screening against known-breached lists, and no mandatory periodic rotation.46

For token-based APIs, the resource-server support validates signature, issuer and expiry by default, but audience validation is opt-in and its absence is a genuine vulnerability: a token minted for a different service by the same authorisation server will otherwise be accepted.47,48 RFC 9700 consolidates the current OAuth 2.0 security guidance and is the document to hand to anyone proposing the implicit or password grant.49

Spring Security 7 finally shipped first-class multi-factor authentication, a feature first proposed in 2013.50 Factors are modelled as authorities — FACTOR_PASSWORD, FACTOR_OTT, FACTOR_WEBAUTHN — so an authorisation rule can require a combination, and the framework redirects the user to whichever factor is missing rather than requiring you to write that state machine.51,52 This is worth adopting for administrative endpoints even in applications where full MFA is not a product requirement: it costs a configuration block and removes the largest single class of account compromise.

The lesson of CVE-2022-22965
Spring4Shell was a remote code execution vulnerability reached through data binding on JDK 9+ under specific deployment conditions. 53 The durable lesson is not about that particular gadget chain. It is that binding untrusted input onto rich object graphs enlarges the attack surface in ways no reviewer can fully enumerate, and that the time between a disclosure and a patched production deployment is a capability you either have or do not — a point the Log4Shell response made at greater cost. 54

Finally, the actuator. Its endpoints expose configuration, environment, thread dumps and heap dumps; /actuator/heapdump alone is a complete disclosure of everything in memory, including credentials. Expose the minimum set, bind management to a separate port unreachable from the internet, and require authentication on anything beyond health.55,56

Review ledger

Hold the line on

  • Rule sets ending in anyRequest().authenticated().
  • Separate SecurityFilterChain beans per posture, matched by path.
  • @EnableMethodSecurity plus a test that proves it is active.
  • Explicit audience validation on JWTs; bounded clock skew.
  • Actuator on a separate port, minimum endpoints, authenticated.

Flag in review

  • csrf().disable() on a chain that authenticates with cookies.
  • permitAll() as the terminal rule.
  • A security chain whose existence depends on an active profile.
  • Custom crypto, custom session tokens, or a hand-rolled authentication filter.
  • /actuator/** reachable from outside the cluster.

Signal

Logging strategy

A log record is a queryable event with a storage bill, not a message to a human who is watching.

Logging is the only observability signal most teams have complete control over and the one they most consistently treat as an afterthought. The symptoms are familiar: a log stream nobody reads because the signal-to-noise ratio makes reading unproductive, a monthly bill that exceeds the compute cost of the service producing it, and — at the moment it matters — an incident where the one field needed to correlate a customer report with a request is the field nobody thought to include.

One facade, one binding, one destination

The structural decisions are unglamorous and cheap. Application code depends on the SLF4J API and nothing else, so that the binding is a deployment concern.57 Spring Boot's default binding is Logback, configured through logback-spring.xml when profile-conditional configuration is needed, since that file is processed by Boot and supports the <springProfile> element.58,59 And the process writes to standard output only. Log rotation, shipping, retention and indexing belong to the platform; an application that also writes files has two sources of truth and a disk-full failure mode it cannot recover from.

Structured by default

Since Spring Boot 3.4, structured logging is built in and requires no extra dependency: setting logging.structured.format.console to ecs, logstash or gelf emits one JSON object per record, with every MDC entry included automatically.59,60 This closes out a decade of fragile ingest-time regular expressions. It also changes what a log line is for: once fields are structured, a log record is a queryable event, and the useful question shifts from “what should this message say” to “what will I want to filter or aggregate by.”

The MDC point deserves emphasis because the failure is silent. Thread pools reuse threads; an MDC entry that is set but not cleared leaks into the next request handled by that thread, attributing one customer's activity to another. With virtual threads the specific mechanism changes but the discipline does not, and Micrometer's context-propagation library exists precisely to carry this context correctly across asynchronous and reactive boundaries where a thread-local cannot.61

Levels as a contract with the on-call engineer

Log levels are only useful if they mean the same thing across the codebase. A workable contract: ERROR means a human must act, and every occurrence should be actionable — if an ERROR fires routinely and is ignored, it is miscategorised and it is training the team to ignore the channel. WARN means degraded but handled: a retry succeeded, a fallback engaged, a deprecated path was used. INFO records business-significant events at a rate proportional to business volume, not to request volume. DEBUG is off in production and reachable at runtime through the actuator loggers endpoint, which lets you raise the level for one package for the duration of an incident without a redeploy.55

What must never be logged
Credentials, tokens, full request or response bodies, and direct personal identifiers. Under the GDPR, log stores are processing systems like any other: they inherit retention limits, access controls, and erasure obligations, and a log aggregation cluster with two years of retention and organisation-wide read access is a compliance finding waiting to be written. 62 Redact at the source. A masking filter in the pipeline is a second line of defence, not a substitute, because it can only remove what it has been taught to recognise.

One performance note. Synchronous appenders make logging part of request latency; a slow or blocked destination becomes an application stall. An AsyncAppender with a bounded queue and an explicit discard policy converts that stall into dropped records, which is almost always the better failure — but only if the queue is bounded and neverBlock is set, since the default behaviour blocks the producing thread when the queue fills, reproducing the problem it was meant to solve.58

Review ledger

Hold the line on

  • SLF4J API only in application code; binding chosen at deployment.
  • Structured output via logging.structured.format.console.
  • MDC set and cleared with try-with-resources, never bare put.
  • A documented meaning for each level, with ERROR reserved for action.
  • Bounded async appender with an explicit discard policy.

Flag in review

  • String concatenation inside a log call.
  • Log-and-rethrow at every stack level.
  • PII, tokens, or full payloads in any record, at any level.
  • Application-managed log files alongside stdout.
  • DEBUG left on in production because someone needed it once.

Confidence

Testing strategy

The context cache, not the annotation vocabulary, is what decides whether a suite stays runnable.

Spring's testing support is comprehensive enough to be a trap. Every annotation is useful, most teams discover @SpringBootTest first, and the result is a suite where every test starts an application context — pleasant at forty tests, a twenty-minute pipeline at four hundred, and an abandoned suite at fifteen hundred. The single most valuable thing to understand about Spring testing is not any individual annotation but the context cache.

The cache key is the cost model

The TestContext framework caches application contexts across test classes, keyed on the full set of configuration attributes: the classes and locations loaded, the active profiles, the property sources, the context initialisers, the web environment, and the set of bean overrides.63 Two test classes with identical keys share one context; change one property in one class and a second context is built and held alongside the first for the rest of the run. Suites that take minutes to start almost always have dozens of distinct keys, usually because @TestPropertySource and bean overrides were applied ad hoc rather than through a small number of shared base configurations.

This is the practical link back to the first discipline. A service with constructor injection can be instantiated with plain new and hand-written fakes, and its business rules tested in microseconds with no container involved at all. Field injection makes that impossible and forces every test up a tier, which is how a codebase ends up with an entirely integration-shaped test suite and no unit tests — not by decision, but by a wiring choice made two years earlier.64

Slices for the layers that need the framework

Where the framework genuinely participates in the behaviour under test — request mapping, content negotiation, validation, security rules, query derivation — the slice annotations load only the relevant part of the context.65 @WebMvcTest loads the web layer with collaborators mocked; @DataJpaTest loads the persistence layer and rolls back each test; @JsonTest covers serialisation contracts. Note that @MockBean was deprecated in Boot 3.4 in favour of @MockitoBean, which is worth a mechanical sweep during any upgrade since the old annotation is one of the more common sources of context-cache fragmentation.66

Test against the database you deploy

The historical compromise — H2 in PostgreSQL compatibility mode — fails in the ways that matter. It differs on isolation behaviour, on JSONB, on array and range types, on window function support, on collation and case sensitivity, on upsert syntax, and on the precise exception thrown for a constraint violation. Every one of those differences is a defect that passes CI and fails in production. Testcontainers removes the compromise by running the real engine, and Spring Boot's @ServiceConnection wires the container's connection details into the context without any manual property plumbing.67,68

Two adjacent categories complete the picture. Outbound HTTP dependencies should be exercised against WireMock rather than mocked at the client interface, because a mocked client cannot catch a serialisation mismatch, a timeout that is never triggered, or an error-response shape you failed to parse.69 And where two teams own the two sides of an interface, consumer-driven contract tests are the mechanism that lets each deploy independently while retaining evidence that the other still works.70

Determinism is a testing feature
Two dependencies account for most flaky Spring suites: the clock and the thread scheduler. Inject a Clock so tests can supply Clock.fixed(...) instead of sleeping; use Awaitility rather than Thread.sleep for asynchronous assertions. A suite that is retried on failure is a suite nobody trusts, and a suite nobody trusts stops blocking merges — which is the moment it stops having any value at all.
Review ledger

Hold the line on

  • Plain JUnit and constructor wiring for anything with no framework behaviour.
  • A small, deliberate set of context configurations, shared through base classes.
  • Slices for framework-mediated behaviour; the real security config imported.
  • Testcontainers running the exact engine and major version deployed.
  • ArchUnit and Modulith verification tests in the same suite.

Flag in review

  • @SpringBootTest as the default annotation for every test.
  • @DirtiesContext used to work around test coupling.
  • H2 standing in for the production database.
  • Thread.sleep in an asynchronous assertion.
  • A different @TestPropertySource in every class.

Cost

Performance optimization

Almost all of it is data access and queueing. Measure first, because intuition consistently indicts the wrong layer.

Performance work in Spring applications divides cleanly into two populations. A small number of problems are genuinely about the framework — reflection at start-up, proxy overhead, serialisation cost. The overwhelming majority are about data access, concurrency limits, and remote calls, and would be present in any framework. Distinguishing between them requires measurement before any change, which is worth stating because the alternative — optimising by intuition — reliably produces effort spent on the wrong layer.

Measure with the right instrument

Three tools cover almost everything. JDK Flight Recorder is always available, has low enough overhead to run continuously in production, and answers questions about allocation, locking, and thread state that sampling profilers miss.71 async-profiler produces accurate CPU and allocation flame graphs without the safepoint bias that distorts traditional JVM profilers.72 JMH is the only defensible way to benchmark a method in isolation, and is worth reaching for precisely because naive micro-benchmarks are systematically wrong: the JIT eliminates dead code, folds constants, and inlines away the thing you were trying to measure.73

The N+1 problem is still the largest single cost

In a typical Spring Data JPA application, the dominant performance defect is not algorithmic but cardinality: a query returning fifty rows, each of which triggers a lazy association load, producing fifty-one round trips where one would do.74,75 It is invisible in development against ten rows of seed data and catastrophic at production volumes. The remedies are well understood — entity graphs, explicit join fetch, @BatchSize — but the more important control is detection: assert the query count in integration tests, so that a regression fails the build rather than the quarter.

Pool sizing is a queueing problem, not a capacity problem

Connection pools are sized upward under pressure, which usually makes things worse. The relationship is described by Little's law — the number of connections needed is the arrival rate multiplied by the mean hold time — and by the Universal Scalability Law, which adds the coherency penalty that makes throughput actively retrograde beyond a certain concurrency.76,77 HikariCP's own guidance reaches the same conclusion from the practitioner side: small pools consistently outperform large ones, because a request queued in the application is visible, bounded and sheddable, while the same request queued inside the database is none of those things.78

The corollary is that hold time, not pool size, is the variable to attack. A transaction that spans a remote HTTP call holds a connection for the duration of somebody else's latency, and no pool size survives that. Keep transactions short, keep remote calls outside them, and set spring.transaction.default-timeout so that a pathological case is bounded rather than indefinite.18

Virtual threads change the shape of the problem

Virtual threads, standard since Java 21, remove the historical reason for reactive programming in I/O-bound services: the platform thread is no longer a scarce resource, so blocking code scales without the loss of stack traces, debuggability and straight-line reasoning that reactive style imposes.79 Spring Boot enables them for the servlet container and for its task executors with a single property.80

Two caveats matter. First, virtual threads help I/O-bound workloads and do nothing for CPU-bound ones — the carrier pool is still sized to the available cores. Second, the pinning problem that made early adoption risky, where a virtual thread inside a synchronized block could not unmount, was resolved in JDK 24; on earlier runtimes, library code using synchronized around blocking I/O could still pin a carrier thread and collapse throughput under load.81 Since Spring Boot 4 targets Java 25 while retaining a Java 17 baseline, this is a live consideration for any team running the older baseline.

Start-up time as a first-class metric

For long-running services, start-up time is an inconvenience. For anything that scales to zero, deploys continuously, or fails over under load, it is a reliability property. Four packaging options trade off differently, and the choice should follow the workload rather than fashion: a plain JVM has the best steady-state throughput; class data sharing archives cut a meaningful fraction of start-up for one extra build step;82 the AOT cache produced by the ahead-of-time class loading and linking work goes further;83,84 and GraalVM native images start in tens of milliseconds with a much smaller footprint, at the cost of a closed-world assumption that requires every reflective access to be registered and a build that takes minutes rather than seconds.85

Caching deserves a closing note, because it is the optimisation most often applied first and understood least. Spring's cache abstraction with Caffeine as the local store is a few lines of configuration,86,87 and it converts a latency problem into a coherency problem: stale reads, a stampede when a popular key expires, and memory pressure that shows up as garbage collection rather than as a cache metric. Set explicit maximum sizes and expiry, instrument hit ratio, and treat any cache without an eviction policy as a memory leak with good intentions.

Review ledger

Hold the line on

  • Profile before optimising: JFR continuously, async-profiler for detail, JMH for micro.
  • Assert query counts in tests to prevent N+1 regressions.
  • Size pools from measured hold time; keep remote calls outside transactions.
  • Choose a runtime by workload shape, not by benchmark headlines.
  • Bounded, instrumented caches with explicit expiry.

Flag in review

  • Enlarging the connection pool as a response to latency.
  • spring.jpa.open-in-view=true in a service that returns JSON.
  • Reactive rewrites for throughput that virtual threads already deliver.
  • Native image adopted before a start-up requirement exists.
  • Caches without eviction, without metrics, or without a stampede strategy.

Evidence

Observability

The ability to answer questions nobody anticipated, decided months earlier by instrumentation choices.

Monitoring answers questions you thought to ask in advance. Observability is the property of being able to answer questions you did not anticipate, from the telemetry the system already emits.88 The distinction is practical rather than philosophical: a dashboard of pre-aggregated counters tells you that error rate rose; it cannot tell you that the rise is confined to one tenant, on one endpoint, against one downstream shard, for requests carrying a particular header. Whether you can answer that during an incident was decided months earlier, by instrumentation choices.

One instrumentation point, three signals

The Spring portfolio's answer is the Micrometer Observation API: a single instrumentation call that produces a timer, a span and the log correlation context simultaneously, so that adding a new signal type does not require touching instrumented code.61 Spring Boot 4 consolidates the previously scattered dependency set behind spring-boot-starter-opentelemetry, bridging Micrometer observations to the OpenTelemetry API and exporting over OTLP to any conformant backend.89,90

The cardinality distinction is not stylistic. A metric's storage cost is the product of the distinct values of every label it carries, so a single userId label on a request timer with four existing labels multiplies the series count by the size of the user base — and the resulting cost lands on the metrics backend, not on the application, which is why it is typically discovered on an invoice.91 Identifiers belong on spans, where each is stored once against the trace that produced it.

Health, readiness, and the difference between them

Actuator's health endpoint is frequently wired straight into an orchestrator's liveness probe, which is wrong in a specific and damaging way: a database outage then makes every replica report unhealthy, the orchestrator restarts them all, and restarts cannot restore a dependency. Liveness should answer only “is this process irrecoverably broken”; readiness answers “can this instance serve traffic right now.” Spring Boot exposes both as separate health groups.92

Trace sampling is the other budget worth setting deliberately. Sampling every request is affordable at low volume and ruinous at high volume; sampling one percent loses precisely the rare failures traces are most useful for. The pragmatic middle is a low head-based rate with tail-based sampling at the collector so that errors and slow requests are retained regardless, plus the ability to raise the rate temporarily during an investigation.

Conventions, so the telemetry composes

Telemetry from twelve services is only useful if the twelve agree on names. OpenTelemetry's semantic conventions give a shared vocabulary for HTTP, database, messaging and RPC attributes, and adopting them means a query written against one service works against all of them.93 The same applies to context propagation: W3C Trace Context defines the traceparent header that lets a trace survive a process boundary, and the failure mode of not propagating it is a set of disconnected single-service traces that look complete and explain nothing.94

Review ledger

Hold the line on

  • The Observation API as the single instrumentation point.
  • Low-cardinality keys on metrics, identifiers on spans.
  • Distinct liveness and readiness groups; dependencies only in readiness.
  • OpenTelemetry semantic conventions and W3C trace context.
  • A stated sampling budget, raisable during an incident.

Flag in review

  • User, request, or tenant identifiers as metric labels.
  • Liveness probes that fail when a downstream dependency fails.
  • Actuator exposed on the traffic port, unauthenticated.
  • Bespoke metric names that no shared dashboard can consume.
  • Traces that stop at the first outbound call.

Contract

API versioning

The cheapest version is the one an additive change made unnecessary; the rest need a resolution strategy and an end date.

API versioning is the discipline with the least consensus and the strongest opinions. Roy Fielding's position — that a properly hypertext-driven API should not need versioning at all, because clients follow links rather than construct URLs — remains theoretically sound and practically unavailable to most teams.95 The Spring team, introducing first-class versioning support in Framework 7, acknowledged this directly: the space has no standard, advice ranges widely, and the framework's role is to provide the building blocks rather than to pick a winner.96

The cheapest version is the one you did not need

Before choosing a versioning scheme, it is worth being precise about what actually forces one. Adding an optional field, adding a new endpoint, adding a new enum value that clients are told to tolerate, relaxing a validation rule — none of these break a client that was written as a tolerant reader.97,98 What breaks clients is removing or renaming a field, tightening validation, changing a type, changing the meaning of an existing value, or altering default behaviour. Discipline about the first list postpones the second list for years, and the practical control is a contract test in CI that fails when a response schema loses a field.

What Spring Framework 7 provides

Versioning is now a first-class concern of the request mapping infrastructure. A version attribute on @RequestMapping and its specialisations declares which version a handler serves; an ApiVersionConfigurer declares how the version is resolved from the request — header, query parameter, media-type parameter or path segment — and which versions are supported; and a SemanticApiVersionParser handles major.minor.patch comparison so that a handler can declare a baseline such as "1.2+" rather than enumerating every later version.96,99,12 Support extends to the test infrastructure, including MockMvc and the new RestTestClient.

The structural rule visible in that listing matters more than the choice of resolver: the version lives in the representation and the mapping, never in the domain model. Two versioned response records mapping from one aggregate is maintainable; two parallel service layers, or a versioned entity, is a fork that will diverge. When a change genuinely requires different behaviour rather than a different shape, the difference belongs in a mapper or a small strategy, not in a duplicated stack.

Dates as versions, and endings as commitments

Two large public APIs have converged independently on date-based versions pinned per client: GitHub uses a dated X-GitHub-Api-Version header,100 and Stripe pins each account to the API version current at first use, upgrading only on explicit action.101 The scheme has a specific virtue for high-churn APIs — it makes the version an immutable snapshot of behaviour rather than a semantic promise, and it removes the argument about whether a given change is “major.” It costs a compatibility layer per dated version, which is affordable only if that layer is generated or thin.

Whatever the scheme, publishing a version is a commitment and retiring one requires a machine-readable countdown. The Deprecation and Sunset response headers give clients a date they can monitor rather than a changelog entry they will not read. Spring ships StandardApiVersionDeprecationHandler for exactly this, emitting Deprecation, Sunset and Link headers per the two relevant RFCs without any per-controller code.102,103,99 Combined with per-version request metrics, they turn deprecation from a negotiation into a measurement: you can see exactly who is still on the old version, and how quickly they are leaving.

Finally, document each live version separately. An OpenAPI description generated per version, published alongside the API and diffed in CI, is the artefact that makes an accidental breaking change visible before release rather than after.104,105

Review ledger

Hold the line on

  • Additive change as the default; a new version only for genuine breaks.
  • One resolution strategy, configured once in ApiVersionConfigurer.
  • Versioned representations mapped from an unversioned domain model.
  • Deprecation and Sunset headers with a real date.
  • Per-version request metrics, and an OpenAPI document diffed in CI.

Flag in review

  • Multiple resolution strategies active at once in the same application.
  • A version number in the domain model or the persistence schema.
  • Parallel service layers per version.
  • A version retired without a published sunset date and usage evidence.
  • Breaking changes shipped inside a patch release because the version is internal.

Supply

Dependency management

Thirty declared, several hundred resolved. The gap is the discipline — and now, partly, the regulation.

A Spring Boot application declares perhaps thirty dependencies and resolves several hundred. That gap is the discipline: almost everything running in production arrived transitively, was chosen by a resolution algorithm rather than a person, and is invisible in the build file. Managing it well is now partly a regulatory matter as well as an engineering one.

The bill of materials is the primary control

Spring Boot's dependency management exists to make the resolved graph coherent: the spring-boot-dependencies BOM pins a set of versions that have been tested together, so that individual starters carry no version and the whole tree moves as a unit.106,107 Overriding a managed version is legitimate — a CVE fix ahead of the next Boot release is the standard case — but it should be done by overriding the documented version property rather than by pinning the artefact, so that the override lifts automatically when Boot catches up and does not silently persist as a downgrade two years later.

The resolution algorithms differ in a way that catches people moving between build tools. Maven uses nearest-definition-wins, and at equal depth the first declaration encountered — so dependency order in the POM can change what is deployed.106 Gradle selects the highest version among conflicting requests, which is more predictable but silently upgrades transitive dependencies. Neither is safe by default; both need constraints. Maven Enforcer's dependencyConvergence and requireUpperBoundDeps rules fail the build on divergence,108 and Gradle's dependency locking writes the resolved graph to a file that is reviewed like any other source change.109,110

Upgrade cadence is a capability, not a chore

The Log4Shell response separated organisations into two groups: those that could identify every affected artefact and ship a patched build within hours, and those that spent a week finding out what they ran.54 The distinguishing factor was not tooling budget but cadence. Teams that upgrade weekly have a small diff, a warm pipeline and a trusted test suite; teams that upgrade annually face a large diff at the worst possible moment. Automated update bots — Renovate or Dependabot — make small, frequent, individually reviewable changes the default,111,112 and their real value is that the test suite is continuously exercised against moving dependencies rather than against a frozen snapshot.

This is exactly the discipline that the Spring 3.x end-of-life makes concrete. Every 3.x branch is now out of open-source support, and the migration to Boot 4 involves the Jakarta EE 11 baseline, Jackson 3, the modularised autoconfiguration jars and JSpecify nullness.1,6,113 That is a substantial diff for anyone who deferred it — and a routine one for teams who had been tracking milestones. OpenRewrite recipes automate a large share of the mechanical portion, which changes the calculus considerably for large codebases.114

From dependency list to attested artefact

Scanning alone is insufficient and increasingly insufficient as a compliance answer. The current expectation is a chain: a software bill of materials describing exactly what shipped, in CycloneDX or SPDX format and meeting the documented minimum elements;115,116,117 a signature proving the artefact has not been altered, which Sigstore makes practical without key management;118 and provenance attesting which pipeline produced it from which source, which is what the SLSA framework formalises.119 For products placed on the EU market, the Cyber Resilience Act converts much of this from good practice into a legal obligation with defined vulnerability-handling and reporting duties.120

Two smaller practices round this out. Prefer fewer starters: each one activates autoconfiguration, and unused autoconfiguration is attack surface, start-up time and upgrade friction acquired for nothing — Boot 4's modularisation into smaller, focused jars is partly a response to exactly this.6 And build layered container images so that the dependency layer, which changes rarely, is cached separately from the application layer, which changes on every commit.121 That single change often halves deployment time and reduces registry cost by more, which is an unusually good return for a build-configuration edit.

Review ledger

Hold the line on

  • A BOM governing the whole graph; overrides expressed as version properties.
  • Convergence enforced or the resolved graph locked and reviewed.
  • Automated update PRs, small and frequent, against a trusted suite.
  • SBOM, signature and provenance produced by the pipeline, not by hand.
  • Layered images with dependencies cached separately from application code.

Flag in review

  • Version numbers hard-coded on managed artefacts.
  • An end-of-life framework branch in production without a dated exit plan.
  • Snapshot or dynamic version ranges in a release build.
  • A starter added to obtain one utility class.
  • Scanner findings suppressed without a recorded rationale and expiry.

Synthesis

What the twelve have in common

Every practice above trades a little convenience now for information earlier. That is the entire method.

Read together, the twelve disciplines share a single mechanism. Each one moves the moment of failure earlier: from production to deployment, from deployment to the build, from the build to the compiler. Constructor injection moves a null pointer from a request to a start-up failure. Validated configuration properties move a bad environment variable from a running service to a refused deployment. Architecture tests move a boundary violation from a future refactor to a red build. Contract diffs move a breaking API change from a customer's integration to a pull request.

Every practice in this list is a trade of convenience now for information earlier. That is the whole of the method; the annotations are implementation detail.

The corollary is a useful test for any practice not covered here. If a proposed convention makes failures visible sooner, it is probably worth its cost. If it only makes code look more like some canonical example, it probably is not.
