Spring Framework Concurrency

Asynchronous Programming in Spring

An expert guide to @Async, TaskExecutor, CompletableFuture, bounded thread pools, executor qualification, context propagation, transactions, cancellation, error handling, virtual threads, testing, and production operations.

Spring Framework 7.0.8 Java 25 concurrency semantics Platform and virtual threads Long-form technical article Vancouver references
Abstract. Spring asynchronous execution is an admission and ownership boundary, not merely a way to “run something later.” @EnableAsync installs advice that intercepts eligible bean method calls, resolves an executor, packages the invocation as a task, and returns immediately. TaskExecutor abstracts execution policy; ThreadPoolTaskExecutor exposes a configurable ThreadPoolExecutor; CompletableFuture represents completion and composes dependent stages. Correctness depends on proxy interception, bounded queueing, explicit rejection, transaction and security-context boundaries, executor selection for continuations, timeout and cancellation semantics, idempotent background work, graceful shutdown, and observability. This article develops those mechanics and provides production-oriented configurations and composition patterns.

Spring Framework 7.0.8 provides the TaskExecutor abstraction, annotation-driven @Async interception, configurable thread-pool and virtual-thread executors, task decoration, and integration with Spring MVC and other framework components. Java’s CompletableFuture, ExecutorService, and ThreadPoolExecutor define the underlying completion and execution semantics.[1][2][3]

1. Mental model

1 A caller invokes a Spring-managed proxy.
2 Async advice resolves a qualified or default executor.
3 The invocation is wrapped as a task and submitted.
4 The caller receives immediately: no value for void, or a future handle.
5 Queue and pool policy decide whether, when, and on which thread the task runs.
6 Completion, failure, timeout, or cancellation updates the returned future or uncaught-exception handler.

Spring’s TaskExecutor has the same single execute(Runnable) shape as Java’s Executor. The name “executor” intentionally does not promise a thread pool: an implementation can execute synchronously, create a thread per task, use platform-managed threads, use virtual threads, or delegate to a bounded pool.[1][4]

Asynchronous does not mean durable A task accepted into an in-memory executor can be lost when the process crashes. Use a durable queue, job table, or broker when work must survive restart, be retried after deployment, or be owned by another service.

1.1 Appropriate uses

  • Parallelizing independent remote calls within a bounded latency budget.
  • Moving nonessential work off a request thread when loss on process failure is acceptable or separately recovered.
  • Performing CPU work on a dedicated pool with explicit parallelism.
  • Integrating callback- or future-based APIs into a compositional pipeline.
  • Separating listener, event, or application components from the caller’s thread.

1.2 Inappropriate uses

  • Fire-and-forget money movement, email obligations, or audit writes without durable handoff.
  • Hiding a slow dependency while still waiting immediately with join().
  • Submitting unbounded work to avoid implementing backpressure.
  • Expecting the caller’s transaction, request, MDC, locale, or security context to appear automatically.
  • Wrapping blocking code in CompletableFuture and calling it “reactive.”

2. Enabling asynchronous method execution

@EnableAsync imports Spring’s async configuration. By default, Spring looks for a unique TaskExecutor bean, then an Executor named taskExecutor. If neither is resolvable, Spring uses a local SimpleAsyncTaskExecutor. Proxy mode is the default.[5][6]

Java 
@Configuration(proxyBeanMethods = false)
@EnableAsync
public class AsyncConfiguration
        implements AsyncConfigurer {

    private final AsyncFailureHandler failureHandler;

    public AsyncConfiguration(
            AsyncFailureHandler failureHandler) {
        this.failureHandler = failureHandler;
    }

    @Bean("applicationExecutor")
    ThreadPoolTaskExecutor applicationExecutor(
            TaskDecorator contextDecorator) {

        ThreadPoolTaskExecutor executor =
                new ThreadPoolTaskExecutor();

        executor.setCorePoolSize(8);
        executor.setMaxPoolSize(32);
        executor.setQueueCapacity(500);
        executor.setKeepAliveSeconds(60);
        executor.setAllowCoreThreadTimeOut(true);
        executor.setThreadNamePrefix("app-async-");
        executor.setTaskDecorator(contextDecorator);
        executor.setRejectedExecutionHandler(
            new ThreadPoolExecutor.AbortPolicy());
        executor.setWaitForTasksToCompleteOnShutdown(
            true);
        executor.setAwaitTerminationSeconds(30);

        return executor;
    }

    @Override
    public Executor getAsyncExecutor() {
        return applicationExecutor(
            contextPropagatingTaskDecorator());
    }

    @Override
    public AsyncUncaughtExceptionHandler
            getAsyncUncaughtExceptionHandler() {
        return failureHandler;
    }

    @Bean
    ContextPropagatingTaskDecorator
            contextPropagatingTaskDecorator() {
        return new ContextPropagatingTaskDecorator();
    }
}

The example returns a managed executor bean from AsyncConfigurer. AsyncConfigurer is initialized early, so dependencies used there should avoid requiring incomplete post-processing; declaring the executor as a regular @Bean gives Spring full lifecycle management.[5][7]

Simpler configuration A single bean named taskExecutor is enough for many applications. Implement AsyncConfigurer when a default executor or AsyncUncaughtExceptionHandler must be selected explicitly.

3. @Async

@Async marks a method or type as a candidate for asynchronous execution. Parameters are unrestricted, but the return type must be void or a Future-compatible type; CompletableFuture is the normal modern choice. The annotation is not supported on methods declared within a @Configuration class.[8]

Java 
@Service
public final class DocumentAnalysisService {

    @Async("analysisExecutor")
    public CompletableFuture<AnalysisResult>
            analyze(
                UUID documentId,
                AnalysisOptions options) {

        AnalysisResult result =
                analyzeSynchronously(
                    documentId,
                    options);

        return CompletableFuture
                .completedFuture(result);
    }
}

The target method returns a temporary completed future because its signature must match the proxy method. The proxy returns the actual asynchronous future that represents executor submission and target completion.[8]

3.1 Executor qualification

Java 
@Async("cpuExecutor")
public CompletableFuture<ImageHash> hash(
        byte[] image) {
    return CompletableFuture.completedFuture(
        perceptualHash(image));
}

@Async("blockingIoExecutor")
public CompletableFuture<PartnerProfile> fetch(
        UUID partnerId) {
    return CompletableFuture.completedFuture(
        partnerClient.fetch(partnerId));
}

The annotation value resolves an executor by bean name or qualifier and can use a property placeholder or SpEL expression. Method-level qualification overrides a class-level qualifier.[8]

3.2 Proxy interception and self-invocation

Default async advice uses Spring AOP proxies. Only calls crossing the proxy are intercepted. A method calling another @Async method through this remains a normal same-thread Java call. AspectJ mode can intercept local calls but requires the Spring aspects module and weaving.[5]

Java 
@Service
final class BrokenImportService {

    void importAll(List<URI> files) {
        for (URI file : files) {
            importOne(file); // Not asynchronous.
        }
    }

    @Async
    void importOne(URI file) {
        importer.importFile(file);
    }
}
Java 
@Service
final class ImportCoordinator {
    private final AsyncFileImporter importer;

    ImportCoordinator(AsyncFileImporter importer) {
        this.importer = importer;
    }

    List<CompletableFuture<ImportResult>> importAll(
            List<URI> files) {
        return files.stream()
            .map(importer::importOne)
            .toList();
    }
}

@Service
final class AsyncFileImporter {

    @Async("blockingIoExecutor")
    CompletableFuture<ImportResult> importOne(
            URI file) {

        return CompletableFuture.completedFuture(
            importer.importFile(file));
    }
}

3.3 void methods

A void async method gives the caller no completion handle. Uncaught exceptions cannot propagate to that caller and are handled by AsyncUncaughtExceptionHandler; the default behavior logs them. Prefer CompletableFuture<Void> when completion matters.[5][9]

Java 
@Component
public final class AsyncFailureHandler
        implements AsyncUncaughtExceptionHandler {

    private static final Logger log =
            LoggerFactory.getLogger(
                AsyncFailureHandler.class);

    @Override
    public void handleUncaughtException(
            Throwable failure,
            Method method,
            Object... arguments) {

        log.error(
            "Uncaught async failure in {} with {} argument(s)",
            method.toGenericString(),
            arguments.length,
            failure);
    }
}

AsyncTaskExecutor extends the execution model with Callable submission and future handles. ThreadPoolTaskExecutor implements Spring’s task interfaces and translates rejection into TaskRejectedException under the Spring contract.[10][11]

5. Thread pools

5.1 ThreadPoolExecutor admission sequence

1 If fewer than corePoolSize workers exist, create a worker.
2 Otherwise, offer the task to the work queue.
3 If the queue rejects because it is full and the pool is below maxPoolSize, create another worker.
4 If both queue and maximum pool are saturated, invoke the rejection policy.

This sequence means maxPoolSize does nothing while an unbounded queue continues accepting work. Spring’s ThreadPoolTaskExecutor defaults to core size 1, unlimited maximum size, and unlimited queue capacity—approximately a single-thread executor. A zero queue capacity behaves like direct handoff and can scale threads immediately, so it must be paired with a finite maximum.[11][12]

An unbounded queue converts overload into latency and memory growth The system appears healthy while the queue grows, but work becomes stale, callers cannot receive timely rejection, shutdown takes longer, and queued payloads consume heap. Bound the queue from a concrete waiting-time and memory budget.

5.2 Production pool configuration

Java 
@Bean("blockingIoExecutor")
ThreadPoolTaskExecutor blockingIoExecutor(
        TaskDecorator taskDecorator) {

    ThreadPoolTaskExecutor executor =
            new ThreadPoolTaskExecutor();

    executor.setCorePoolSize(16);
    executor.setMaxPoolSize(64);
    executor.setQueueCapacity(1_000);
    executor.setKeepAliveSeconds(60);
    executor.setAllowCoreThreadTimeOut(true);
    executor.setThreadNamePrefix("io-async-");
    executor.setTaskDecorator(taskDecorator);
    executor.setRejectedExecutionHandler(
        new ThreadPoolExecutor.AbortPolicy());
    executor.setWaitForTasksToCompleteOnShutdown(
        true);
    executor.setAwaitTerminationSeconds(45);

    return executor;
}

Managed Spring beans are initialized and shut down by the container, so explicit initialize() is unnecessary for a normal @Bean. Register executor metrics after initialization through an observation or metrics binder rather than forcing early pool initialization inside the factory method.

5.3 Rejection policies

PolicyBehaviorRisk
AbortPolicyRejects by throwingCaller must convert overload into a controlled response or retry decision
CallerRunsPolicyCaller executes the taskProvides feedback but can block request or broker-consumer threads unexpectedly
DiscardPolicySilently dropsUsually unacceptable for business work
DiscardOldestPolicyDrops an older queued task and retries submissionBreaks ordering and silently abandons work

AbortPolicy is a good default because overload becomes visible. Map rejection to an HTTP 503/429, message negative acknowledgement, durable retry record, or explicit fallback according to the caller’s protocol. Never retry executor rejection in a tight loop.

5.4 Pool sizing

For CPU-bound work, useful platform-thread parallelism is usually near available processor count, adjusted for other CPU consumers and native libraries. For blocking work, a first estimate can use:

Text 
threads ≈ target throughput × average service time

or

threads ≈ cores × utilization target
          × (1 + wait time / compute time)

These are capacity estimates, not universal constants. Measure dependency limits, connection-pool capacity, response-time distributions, memory per task, and acceptable queue delay. Sixty-four executor threads cannot improve throughput when the JDBC pool has ten connections; they produce fifty-four waiters.

5.5 Queue capacity from latency budget

If an executor sustains 100 tasks per second and queued work may wait at most two seconds, a queue around 200 tasks is the approximate upper latency budget before accounting for bursts and service-time variance. When payloads are large, memory can impose a smaller bound. Admission control should reject before work becomes useless.

6. CompletableFuture

CompletableFuture<T> implements both Future<T> and CompletionStage<T>. It can be completed explicitly and supports dependent stages. Non-async continuations may execute on the thread that completes the prior stage or another thread that invokes completion. Async methods without an explicit executor use the default asynchronous facility, normally the common fork-join pool.[2]

Always know which executor owns a continuation thenApply() can run on a request thread, worker thread, or completion thread. thenApplyAsync() without an executor can escape into the common pool. Supply the intended executor for blocking or capacity-sensitive stages.

6.1 Parallel composition

Java 
@Service
public final class CustomerOverviewService {
    private final CustomerAsyncGateway gateway;
    private final Executor compositionExecutor;

    public CustomerOverviewService(
            CustomerAsyncGateway gateway,
            @Qualifier("compositionExecutor")
            Executor compositionExecutor) {

        this.gateway = gateway;
        this.compositionExecutor =
                compositionExecutor;
    }

    public CompletableFuture<CustomerOverview> load(
            UUID customerId) {

        CompletableFuture<Profile> profile =
                gateway.profile(customerId);

        CompletableFuture<List<OrderSummary>> orders =
                gateway.recentOrders(customerId);

        CompletableFuture<RiskAssessment> risk =
                gateway.risk(customerId);

        return profile
            .thenCombineAsync(
                orders,
                OverviewParts::new,
                compositionExecutor)
            .thenCombineAsync(
                risk,
                (parts, assessment) ->
                    new CustomerOverview(
                        parts.profile(),
                        parts.orders(),
                        assessment),
                compositionExecutor);
    }
}
Java 
@Service
final class CustomerAsyncGateway {

    @Async("blockingIoExecutor")
    CompletableFuture<Profile> profile(
            UUID customerId) {
        return CompletableFuture.completedFuture(
            profileClient.fetch(customerId));
    }

    @Async("blockingIoExecutor")
    CompletableFuture<List<OrderSummary>>
            recentOrders(UUID customerId) {
        return CompletableFuture.completedFuture(
            orderClient.recent(customerId));
    }

    @Async("blockingIoExecutor")
    CompletableFuture<RiskAssessment> risk(
            UUID customerId) {
        return CompletableFuture.completedFuture(
            riskClient.assess(customerId));
    }
}

6.2 Dynamic fan-out

Java 
public static <T> CompletableFuture<List<T>>
        sequence(
            List<CompletableFuture<T>> futures) {

    CompletableFuture<Void> all =
            CompletableFuture.allOf(
                futures.toArray(
                    CompletableFuture[]::new));

    return all.thenApply(ignored ->
        futures.stream()
            .map(CompletableFuture::join)
            .toList());
}

allOf() completes when every stage completes but does not itself collect values. After it completes successfully, joining the constituent futures does not block. Bound fan-out before creating thousands of futures; a list of futures is not backpressure.

6.4 Timeouts

orTimeout() completes the future exceptionally after a deadline; completeOnTimeout() supplies a fallback value. These operations change the future’s completion but do not guarantee that the underlying blocking call stops. Configure native HTTP, database, and lock timeouts as well.

6.5 Cancellation

Executor-service submission establishes Java memory-consistency guarantees between actions before submission, task actions, and successful result retrieval. A general Future may support interruption-based cancellation, but CompletableFuture.cancel(boolean) treats cancellation as exceptional completion and ignores mayInterruptIfRunning; the underlying async operation can continue after the future is cancelled.[2][13]

Java 
CompletableFuture<Report> report =
        reportService.generate(reportId);

boolean futureCancelled =
        report.cancel(true);
// For CompletableFuture, true does not imply
// that the executing thread was interrupted.

Configure native operation timeouts and design explicit cancellation tokens or persistent job state when business cancellation must stop work or survive process boundaries.

7. Context propagation

Thread-local state does not automatically follow work to another thread. Common examples include logging MDC, observation context, locale, request attributes, and Spring Security’s SecurityContext. Spring’s TaskDecorator can wrap the actual execution callback; ContextPropagatingTaskDecorator uses Micrometer context propagation to restore registered context around the task.[14][15]

Java 
@Bean
TaskDecorator contextDecorator() {
    return new CompositeTaskDecorator(
        List.of(
            new ContextPropagatingTaskDecorator(),
            runnable -> {
                Locale locale =
                        LocaleContextHolder
                            .getLocale();

                return () -> {
                    Locale previous =
                            LocaleContextHolder
                                .getLocale();
                    try {
                        LocaleContextHolder
                            .setLocale(locale);
                        runnable.run();
                    }
                    finally {
                        LocaleContextHolder
                            .setLocale(previous);
                    }
                };
            }));
}

Context propagation adds overhead and should be deliberate. Copy immutable identifiers and tracing context; avoid retaining full request objects, mutable thread locals, or security credentials longer than necessary.

7.1 Security context

Spring Security stores authentication in thread-local state in common servlet applications. Its delegating security-context executor and task-executor wrappers capture the submitting context, install it for task execution, and clear it afterward. Alternatively, pass an immutable actor identifier and authorize again in the background operation.[16]

Java 
@Bean("securedExecutor")
AsyncTaskExecutor securedExecutor(
        @Qualifier("applicationExecutor")
        AsyncTaskExecutor delegate) {

    return new DelegatingSecurityContextAsyncTaskExecutor(
            delegate);
}

8. Transactions

Imperative Spring transactions are normally thread-bound. They do not propagate into newly started executor threads. An async method begins without the caller’s transaction unless it opens its own transaction through an intercepted transactional boundary.[17][18]

Java 
@Service
final class OrderService {
    private final InvoiceAsyncService invoices;

    @Transactional
    public void placeOrder(OrderCommand command) {
        Order order = orders.save(
            Order.create(command));

        invoices.createInvoice(order.getId());
        // Async task may start before this transaction commits.
    }
}
Commit-before-consume race The async task can query for an order that is still uncommitted, and the outer transaction can later roll back after work has been submitted. Publish a durable outbox record in the transaction, use an after-commit event for best-effort local work, or make the async operation tolerate visibility delay and absence.
Java 
@Component
final class OrderCommittedListener {

    private final InvoiceAsyncService invoices;

    OrderCommittedListener(
            InvoiceAsyncService invoices) {
        this.invoices = invoices;
    }

    @TransactionalEventListener(
        phase = TransactionPhase.AFTER_COMMIT)
    public void afterCommit(
            OrderPlaced event) {
        invoices.createInvoice(event.orderId());
    }
}

@Service
final class InvoiceAsyncService {

    @Async("blockingIoExecutor")
    @Transactional
    public CompletableFuture<Void> createInvoice(
            UUID orderId) {

        invoiceCreator.create(orderId);
        return CompletableFuture.completedFuture(null);
    }
}

The after-commit listener removes the pre-commit visibility race, but submission remains in-memory and can be lost between database commit and executor acceptance or process completion. Use a durable outbox when the obligation must survive failure.

9. Virtual threads

Spring’s VirtualThreadTaskExecutor starts a new virtual thread per task on JDK 21 or later and exposes only a thread-name prefix. SimpleAsyncTaskExecutor can also use virtual threads and adds concurrency limiting and task decoration. Virtual threads reduce the cost of large numbers of blocking tasks; they do not increase database connections, remote-service quotas, memory bandwidth, or CPU.[19]

Java 
@Bean("virtualBlockingExecutor")
SimpleAsyncTaskExecutor virtualBlockingExecutor(
        TaskDecorator taskDecorator) {

    SimpleAsyncTaskExecutor executor =
            new SimpleAsyncTaskExecutor(
                "virtual-io-");

    executor.setVirtualThreads(true);
    executor.setConcurrencyLimit(200);
    executor.setTaskDecorator(taskDecorator);
    executor.setTaskTerminationTimeout(
        30_000);

    return executor;
}

A concurrency limit remains valuable because external systems are finite. Virtual threads change the cost model of blocked threads, not the correctness requirement for admission control. Monitor connection-pool waits and downstream saturation rather than thread count alone.

10. @Async versus asynchronous HTTP

Spring MVC asynchronous request processing is a different feature. A controller can return Callable, DeferredResult, CompletionStage, or CompletableFuture; Spring releases the servlet request thread and later dispatches to finish the response. Callable work uses MVC’s configured AsyncTaskExecutor. A service returning a future can be returned directly without adding @Async to the controller.[20][21]

Java 
@RestController
@RequestMapping("/reports")
final class ReportController {

    private final ReportAsyncService reports;

    @GetMapping("/{id}")
    CompletableFuture<ResponseEntity<ReportView>> get(
            @PathVariable UUID id) {

        return reports.load(id)
            .thenApply(ResponseEntity::ok);
    }
}

Async servlet processing improves request-thread utilization but does not make blocking dependencies non-blocking. The executor, timeout, client disconnect, and downstream cancellation policy still require configuration.

11. Asynchronous application events

An @EventListener can also be annotated with @Async. Exceptions from an asynchronous listener do not propagate to the publisher, and an asynchronous listener cannot publish follow-up events by returning a value. Use explicit publication inside the listener when required.[22]

Java 
@Component
final class SearchProjectionListener {

    @Async("projectionExecutor")
    @EventListener
    public CompletableFuture<Void> update(
            ProductChanged event) {

        searchProjection.apply(event);
        return CompletableFuture.completedFuture(null);
    }
}

Spring application events are process-local by default. They are useful for modularity, not durable integration. Use a broker or outbox for cross-process delivery and recovery.

12. Lifecycle and graceful shutdown

ThreadPoolTaskExecutor participates in Spring lifecycle management and exposes pool size, active count, and queue size. On context close, policy determines whether queued work is cancelled, existing tasks complete, or submissions are rejected. Waiting for completion must be bounded by the platform’s termination budget.[11]

  • Stop accepting external submissions before draining the executor.
  • Use finite native timeouts so tasks can complete or fail during shutdown.
  • Persist checkpoints for work that must resume later.
  • Do not rely on daemon threads for business obligations.
  • Test process termination with a full queue and slow dependencies.

13. Testing asynchronous code

13.1 Replace the executor with synchronous execution

Java 
@TestConfiguration(proxyBeanMethods = false)
class SynchronousAsyncTestConfiguration {

    @Bean("applicationExecutor")
    @Primary
    TaskExecutor synchronousExecutor() {
        return new SyncTaskExecutor();
    }
}

Synchronous execution makes most service tests deterministic and keeps exceptions on the test thread. Retain separate integration tests that exercise proxy interception, pool rejection, context propagation, and concurrency.

void combinesIndependentCalls() throws Exception {
    CompletableFuture<CustomerOverview> future =

13.3 Test overload

Java 
@Test
void rejectsWhenPoolAndQueueAreFull()
        throws Exception {

    ThreadPoolTaskExecutor executor =
            new ThreadPoolTaskExecutor();

    executor.setCorePoolSize(1);
    executor.setMaxPoolSize(1);
    executor.setQueueCapacity(1);
    executor.initialize();

    CountDownLatch release =
            new CountDownLatch(1);

    executor.execute(
        () -> await(release)); // Running.
    executor.execute(
        () -> await(release)); // Queued.

            () -> {}));

}

13.4 Concurrency tests

Use barriers and latches to force interleavings. Verify that deduplication, optimistic locking, or database claims protect shared state. Repeated timing-based tests that use Thread.sleep() rarely prove the intended race.

14.1 Measuring queue delay

Java 
final class TimedTask implements Runnable {
    private final long submittedNanos =
            System.nanoTime();
    private final Runnable delegate;
    private final Timer queueDelay;
    private final Timer execution;

    TimedTask(
            Runnable delegate,
            Timer queueDelay,
            Timer execution) {
        this.delegate = delegate;
        this.queueDelay = queueDelay;
        this.execution = execution;
    }

    @Override
    public void run() {
        queueDelay.record(
            System.nanoTime() - submittedNanos,
            TimeUnit.NANOSECONDS);

        execution.record(delegate);
    }
}

A task decorator can apply this wrapper consistently, although submitted task wrappers may obscure original exceptions. Future-based methods should also observe completion exceptionally so errors are not hidden inside futures.

15. Diagnostics

15.1 @Async still runs on the caller thread

Check @EnableAsync, component scanning, bean management, public/proxy eligibility, same-class invocation, and whether the selected executor is intentionally synchronous.

15.2 Pool never grows beyond core size

The queue is probably unbounded or not full. ThreadPoolExecutor queues after reaching core size and creates non-core workers only when queueing fails. Bound or remove the queue when controlled expansion is intended.[11][12]

15.3 Future never completes

Inspect dependency timeouts, thread dumps, executor saturation, pool-to-connection-pool mismatch, cyclic waits between executors, and continuations accidentally submitted to the same exhausted pool.

15.4 Exception appears lost

For void, inspect the AsyncUncaughtExceptionHandler. For futures, ensure the caller observes get, join, whenComplete, or another terminal stage. An unobserved exceptional future does not automatically fail the request.

15.5 Async code cannot see uncommitted data

The caller’s thread-bound transaction did not propagate. Move the handoff after commit, create a separate transaction inside the async service, or use a durable outbox.[17]

15.6 Correlation ID disappears

Thread-local logging context was not propagated. Configure a task decorator or pass correlation identifiers explicitly, and clear restored context in a finally block.

15.7 Rejections spike during a dependency outage

Slow tasks occupied workers and filled the queue. Fail fast at the dependency, open a circuit breaker where appropriate, reduce accepted work, return overload to callers, and avoid increasing the queue as the first response.

16. Expert practices

16.1 Bound every scarce resource

Set finite pools, queues, connection pools, request concurrency, dependency timeouts, and fan-out. A bounded executor is one layer in an end-to-end admission design.

16.2 Separate workload classes

CPU work, blocking I/O, low-priority maintenance, message listeners, and request continuations should not compete in one undifferentiated pool.

16.3 Return futures for meaningful work

Use CompletableFuture<T> or CompletableFuture<Void> so callers can observe failure, timeout, cancellation, and completion. Reserve void for truly best-effort tasks with strong operational monitoring.

16.4 Name continuation executors

Supply executors to async completion-stage methods. Avoid accidental use of the common pool for blocking or tenant-sensitive work.

16.5 Propagate only required context

Copy tracing and immutable identity deliberately. Never assume thread locals, transactions, request scope, or persistence contexts cross the executor boundary.

16.6 Distinguish concurrency from durability

Use an executor for local parallel execution. Use a broker, outbox, or durable job store when accepted work must survive process failure.

16.7 Put timeouts at the actual blocking operation

A future timeout is a caller-observation policy. Configure socket, database, lock, and queue timeouts so underlying work releases resources.

16.8 Treat rejection as a designed outcome

Select a rejection policy, expose metrics, and map overload to the caller’s protocol. Silent discard is rarely acceptable.

17. Summary

  • @EnableAsync installs Spring advice that submits intercepted method invocations to an executor.
  • Proxy mode is the default; same-class calls do not trigger @Async.
  • @Async methods return void or a Future-compatible type, normally CompletableFuture.
  • void failures go to AsyncUncaughtExceptionHandler; future failures must be observed through the future.
  • TaskExecutor does not promise a pool; the implementation defines execution policy.
  • ThreadPoolTaskExecutor defaults are effectively single-threaded with an unbounded queue and should be configured explicitly.
  • A bounded queue makes overload visible; an unbounded queue converts overload into waiting time and memory use.
  • CompletableFuture continuations may run on completion threads or the common pool unless an executor is supplied.
  • Future timeout and cancellation do not guarantee termination of the underlying operation.
  • Thread-local security, logging, locale, request, and transaction state do not propagate automatically.
  • Imperative transactions are thread-bound; async work requires its own transaction and a commit-safe handoff.
  • Virtual threads reduce blocked-thread cost but do not remove downstream capacity limits.
  • Durable work needs a durable queue or job store, not only an in-memory executor.

When an async workflow surprises you, trace it through five ownership boundaries: Which proxy intercepted the call? Which executor admitted it? Which queue and worker ran it? Which thread-local and transactional context was available? Which future, rejection path, or durable record owned completion and failure? Those questions turn @Async from apparent background magic into an explicit concurrency architecture.
