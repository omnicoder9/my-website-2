Spring Internationalization

Internationalization in Spring

A technical guide to MessageSource, locale resolution, message bundles, localization, formatting and parsing, validation messages, MVC, WebFlux, testing, and production practices.

Spring Framework 7.0.8 Spring Boot 4.1.0 Servlet and reactive web stacks Long-form technical article Vancouver references
Abstract. Internationalization is the architectural work that makes an application adaptable to different linguistic and regional conventions; localization is the production and selection of locale-specific content and presentation. Spring separates these responsibilities. MessageSource resolves stable message codes to parameterized text. MVC LocaleResolver implementations and WebFlux LocaleContextResolver implementations determine the current locale and, where supported, time zone. The formatting system converts between typed values and locale-sensitive strings through printers, parsers, formatters, annotations, and a FormattingConversionService. Validation and binding errors participate through message codes. Correct systems additionally distinguish language from time zone and currency, keep machine APIs stable, avoid string concatenation, test fallback chains, and propagate locale deliberately across asynchronous boundaries.

Spring’s ApplicationContext extends MessageSource, making internationalized message lookup a core container capability rather than a web-only feature. Spring MVC adds request locale resolution, WebFlux exposes a reactive locale context, and Spring’s formatting SPI adds locale-aware parsing and printing above the general conversion system.[1][2][20]

1. Internationalization and localization

Internationalization (i18n)Designing code, data, templates, and workflows so language and regional behavior are configurable rather than embedded.
Localization (l10n)Supplying translated messages, formats, layouts, policies, and media for a particular audience.
LocaleA language-and-region preference used by locale-sensitive APIs; it is not inherently a time zone, currency, or authorization rule.

Java’s Locale is consumed by locale-sensitive APIs such as number, currency, date, and message formatting. APIs that omit an explicit locale generally use a configured default locale category. Spring carries a current LocaleContext, which can optionally include a time zone through TimeZoneAwareLocaleContext.[8][18]

Do not infer business facts from locale A French locale does not prove that a customer resides in France, uses EUR, or belongs to a French legal entity. Store language, region, time zone, currency, and jurisdiction as separate domain facts when they affect business behavior.

2. MessageSource

MessageSource is the strategy interface for parameterized and internationalized messages. Its lookup methods accept a message code, arguments, an optional default message, and a locale. A lookup without a default can throw NoSuchMessageException. MessageSourceResolvable packages one or more candidate codes, arguments, and a default message for deferred resolution.[2]

Java 
@Service
public final class OrderMessages {

    private final MessageSource messages;

    public OrderMessages(MessageSource messages) {
        this.messages = messages;
    }

    public String created(
            UUID orderId,
            Instant createdAt,
            Locale locale) {

        return messages.getMessage(
            "order.created",
            new Object[] {
                orderId,
                Date.from(createdAt)
            },
            locale);
    }

    public String missing(
            UUID orderId,
            Locale locale) {

        return messages.getMessage(
            "order.not-found",
            new Object[] {orderId},
            "Order not found",
            locale);
    }
}

2.1 MessageSourceAccessor

MessageSourceAccessor is a convenience wrapper with overloaded lookup methods. When no locale is supplied, it can use the locale associated with LocaleContextHolder, depending on how it is constructed. Explicit locale parameters remain preferable in domain services and background work because they make the presentation dependency visible.[17][18]

2.2 Hierarchical message sources

Spring supports hierarchical message resolution through HierarchicalMessageSource. A child application context can resolve local messages first and delegate to a parent source for shared messages. This is useful for modular applications, but duplicate codes require a documented override policy.[1]

3. Message bundles

Resource-bundle naming normally combines a basename with locale suffixes. For basename i18n/messages, files can include a root bundle and progressively specific locale variants:

Text 
src/main/resources/
└── i18n/
    ├── messages.properties
    ├── messages_en.properties
    ├── messages_en_GB.properties
    ├── messages_es.properties
    ├── messages_fr.properties
    └── messages_fr_CA.properties
Properties 
# messages.properties — required default/fallback content
order.created=Order {0} was created at {1,time,short}.
order.not-found=Order {0} does not exist.
cart.items={0,choice,0#No items|1#One item|1<{0,number,integer} items}
article.title=Today''s article
Properties 
# messages_fr.properties
order.created=La commande {0} a été créée à {1,time,short}.
order.not-found=La commande {0} n’existe pas.
cart.items={0,choice,0#Aucun article|1#Un article|1<{0,number,integer} articles}
article.title=L''article du jour

Spring’s resource-bundle message sources follow the locale candidate and fallback model of the JDK ResourceBundle. Message arguments are formatted through MessageFormat; its patterns use indexed placeholders and locale-sensitive subformats. Single quotation marks have escaping semantics in MessageFormat patterns, which is why a literal apostrophe is commonly doubled when the pattern is parsed.[3][7][9]

Never assemble sentences from translated fragments Word order, agreement, plural forms, punctuation, and grammatical roles vary. Give translators one complete message with named meaning documented for every argument.

3.1 Message-code design

Message codes are application contracts. Use stable semantic names such as checkout.payment.declined rather than English text as the key. Organize by capability or domain, avoid exposing internal class names unless the code is specifically a binding error, and document argument positions.

Properties 
# Argument contract:
# {0}: customer display name
# {1}: localized due date
invoice.payment-due=Hello {0}, payment is due on {1,date,long}.

4. Message-source implementations

ImplementationLoading modelUse
ResourceBundleMessageSourceJDK ResourceBundle and MessageFormatClasspath bundles and standard JDK behavior
ReloadableResourceBundleMessageSourceSpring Resource handles and PropertiesConfigurable encodings, basenames, cache intervals, and external resources
StaticMessageSourceProgrammatically registered messagesTests and small programmatic sources

MessageSource documents ResourceBundleMessageSource and ReloadableResourceBundleMessageSource as its production implementations. The reloadable implementation is more configurable and participates in Spring resource loading; actual reloading is most useful with change-detectable external resources rather than immutable resources inside a packaged application.[2][3][4]

4.1 Explicit Framework configuration

Java 
@Configuration(proxyBeanMethods = false)
public class InternationalizationConfiguration {

    @Bean
    MessageSource messageSource() {
        ReloadableResourceBundleMessageSource source =
                new ReloadableResourceBundleMessageSource();

        source.setBasenames(
            "classpath:i18n/messages",
            "classpath:i18n/validation");

        source.setDefaultEncoding(
            StandardCharsets.UTF_8.name());
        source.setFallbackToSystemLocale(false);
        source.setCacheMillis(
            Duration.ofMinutes(5).toMillis());

        return source;
    }
}

The bean name must be messageSource for the application context’s conventional lookup. Disabling fallback to the host system locale prevents a server’s operating-system settings from unexpectedly changing application fallback behavior.

5. Spring Boot internationalization

Spring Boot looks for a messages bundle at the classpath root by default. Auto-configuration requires the default file for a configured basename—for example, messages.properties, not only messages_fr.properties. The spring.messages namespace configures basenames, common messages, encoding, cache duration, system-locale fallback, MessageFormat behavior, and missing-code behavior.[5][6]

YAML 
spring:
  messages:
    basename:
      - i18n/messages
      - i18n/validation
    common-messages:
      - classpath:i18n/common.properties
    encoding: UTF-8
    cache-duration: 10m
    fallback-to-system-locale: false
    always-use-message-format: false
    use-code-as-default-message: false
Do not use message codes as defaults in production Returning an internal code can conceal missing translations and leak implementation details. Fail tests for missing codes, supply a controlled fallback where required, and alert on production lookup failures.

6. Locale resolution in Spring MVC

DispatcherServlet uses a LocaleResolver to determine the locale for a request. The default resolver is AcceptHeaderLocaleResolver, based on the request locale derived from Accept-Language. The extended LocaleContextResolver can also expose time-zone information.[10][11]

ResolverSource of preferenceMutable by server?Use
AcceptHeaderLocaleResolverAccept-LanguageNoStateless content negotiation
CookieLocaleResolverCookie, then configured/request fallbackYesPersistent preference without server session
SessionLocaleResolverHTTP session, then configured/request fallbackYesApplications already using sessions
FixedLocaleResolverConfigured fixed locale/time zoneNoSingle-locale services and deterministic tests

6.1 Accept-Language negotiation

Java 
@Configuration(proxyBeanMethods = false)
public class AcceptLanguageConfiguration {

    @Bean
    LocaleResolver localeResolver() {
        AcceptHeaderLocaleResolver resolver =
                new AcceptHeaderLocaleResolver();

        resolver.setSupportedLocales(
            List.of(
                Locale.US,
                Locale.UK,
                Locale.FRANCE,
                Locale.CANADA_FRENCH,
                Locale.forLanguageTag("es")));

        resolver.setDefaultLocale(Locale.US);
        return resolver;
    }
}

Supported-locale matching is exact on language and country for region-specific entries. If a language-only fallback such as en should match en-GB, include that language-only locale explicitly. AcceptHeaderLocaleResolver cannot change the request header and therefore does not support setting a locale through the resolver.[12]

6.2 Persistent cookie preference

Java 
@Configuration(proxyBeanMethods = false)
public class LocalePreferenceConfiguration
        implements WebMvcConfigurer {

    @Bean
    LocaleResolver localeResolver() {
        CookieLocaleResolver resolver =
                new CookieLocaleResolver(
                    "APP_LOCALE");

        resolver.setDefaultLocale(Locale.US);
        resolver.setDefaultTimeZone(
            TimeZone.getTimeZone("UTC"));
        resolver.setCookieMaxAge(
            Duration.ofDays(365));
        resolver.setCookieSecure(true);
        resolver.setCookieHttpOnly(true);
        resolver.setCookieSameSite("Lax");

        return resolver;
    }

    @Override
    public void addInterceptors(
            InterceptorRegistry registry) {

        LocaleChangeInterceptor interceptor =
                new LocaleChangeInterceptor();

        interceptor.setParamName("lang");
        interceptor.setHttpMethods("POST");
        interceptor.setIgnoreInvalidLocale(false);

        registry.addInterceptor(interceptor)
            .addPathPatterns("/preferences/locale");
    }
}

CookieLocaleResolver stores the selected locale and optionally time zone in a cookie and supports BCP 47 language tags. LocaleChangeInterceptor changes the locale from a configurable request parameter and can restrict the HTTP methods on which changes are accepted.[13][16]

6.3 Session and fixed strategies

SessionLocaleResolver stores locale and optionally time zone in HttpSession; it is most appropriate when the application already needs a session. Its operation is based on servlet session attributes and is not a special integration with Spring Session. FixedLocaleResolver always returns a configured locale and optional time zone and does not allow changing them per request.[14][15]

7. Accessing the current locale

MVC exposes the resolved locale through request context utilities and associates it with LocaleContextHolder for the request-processing thread. Application services can also accept a Locale explicitly, which is safer for background tasks and makes localization a visible input.[10][18]

Java 
@RestController
@RequestMapping("/api/profile")
public final class ProfileController {

    private final MessageSource messages;

    public ProfileController(MessageSource messages) {
        this.messages = messages;
    }

    @GetMapping("/greeting")
    GreetingResponse greeting(Locale locale) {
        String text = messages.getMessage(
            "profile.greeting",
            null,
            locale);

        return new GreetingResponse(
            locale.toLanguageTag(),
            text);
    }
}
Locale context is thread-bound in imperative code Executor threads do not automatically inherit request locale safely. Pass the locale explicitly or use deliberate context propagation. Never retain request-scoped locale state inside a long-running singleton task.

8. Locale resolution in Spring WebFlux

WebFlux uses org.springframework.web.server.i18n.LocaleContextResolver, whose methods resolve or set a LocaleContext from a ServerWebExchange. Spring provides accept-header and fixed implementations. WebFlux infrastructure can auto-detect a resolver bean and exposes the resulting locale context through the exchange.[19][21]

Java 
@Configuration(proxyBeanMethods = false)
public class ReactiveLocaleConfiguration {

    @Bean
    org.springframework.web.server.i18n
            .LocaleContextResolver
            localeContextResolver() {

        AcceptHeaderLocaleContextResolver resolver =
                new AcceptHeaderLocaleContextResolver();

        resolver.setSupportedLocales(
            List.of(
                Locale.US,
                Locale.FRANCE,
                Locale.forLanguageTag("es")));

        resolver.setDefaultLocale(Locale.US);
        return resolver;
    }
}
Java 
Mono<ServerResponse> greeting(
        ServerRequest request) {

    Locale locale = request
        .exchange()
        .getLocaleContext()
        .getLocale();

    String text = messages.getMessage(
        "profile.greeting",
        null,
        locale);

    return ServerResponse.ok()
        .bodyValue(
            new GreetingResponse(
                locale.toLanguageTag(),
                text));
}

Reactive processing can move across threads, so request locale should come from the reactive exchange or explicitly propagated context rather than an assumed thread-local.

9. Spring formatting architecture

Spring’s general ConversionService converts values between types but does not itself express locale-sensitive presentation. The formatting SPI adds Printer<T>, Parser<T>, and Formatter<T>; a formatter combines printing and parsing with a supplied locale. FormattingConversionService combines conversion and formatter registration.[20][22][23]

1 A web request supplies a string and a resolved locale.
2 A data binder identifies the target property or method-parameter type.
3 The formatting conversion service selects an annotation formatter, type formatter, or converter.
4 A parser turns localized text into a typed value.
5 During rendering, a printer turns the typed value back into localized text.

9.1 Default formatters

DefaultFormattingConversionService registers converters and formatters suitable for common applications, including number and Java time formatters and money support when the corresponding API is present. Spring MVC installs common number and date formatting support and allows customization through WebMvcConfigurer.addFormatters.[24][25]

10. Formatting annotations

Java 
public final class InvoiceSearchForm {

    @DateTimeFormat(
        style = "M-")
    private LocalDate issuedAfter;

    @NumberFormat(
        style = NumberFormat.Style.CURRENCY)
    private BigDecimal minimumTotal;

    @DurationFormat(
        style = DurationFormat.Style.ISO8601)
    private Duration overdueBy;

    // getters and setters
}

@DateTimeFormat, @NumberFormat, and @DurationFormat declare field or parameter formatting rules. Number formatting supports general, integer, currency, percent, compact, and custom-pattern styles. Date/time formatting supports styles, ISO forms, and patterns; duration formatting supports selected duration styles and units.[26][27]

10.1 Request parameter binding

Java 
@GetMapping("/api/invoices")
List<InvoiceSummary> search(
        @RequestParam
        @DateTimeFormat(iso = DateTimeFormat.ISO.DATE)
        LocalDate issuedAfter,

        @RequestParam
        @NumberFormat(pattern = "#,##0.00")
        BigDecimal minimumTotal) {

    return invoiceQueries.search(
        issuedAfter,
        minimumTotal);
}
Use stable machine formats for machine APIs Locale-sensitive query parameters are appropriate for human-entered forms. Public machine APIs usually benefit from ISO dates, explicit decimals, and explicit currency codes so the same request means the same thing in every locale.

10.2 HTML date and time inputs

Spring MVC normally considers the request locale when parsing and formatting dates. Native HTML date and time input controls, however, use fixed formats defined by the browser/HTML contract; Spring’s MVC documentation recommends configuring ISO date/time formatters for those controls rather than applying localized text patterns.[25]

Java 
@Configuration(proxyBeanMethods = false)
public class DateTimeFormattingConfiguration
        implements WebMvcConfigurer {

    @Override
    public void addFormatters(
            FormatterRegistry registry) {

        DateTimeFormatterRegistrar registrar =
                new DateTimeFormatterRegistrar();

        registrar.setUseIsoFormat(true);
        registrar.registerFormatters(registry);
    }
}

11. Custom locale-aware formatter

Java 
public record Weight(BigDecimal kilograms) {
}

public final class WeightFormatter
        implements Formatter<Weight> {

    @Override
    public Weight parse(
            String text,
            Locale locale)
            throws ParseException {

        String normalized =
                text.replace("kg", "")
                    .trim();

        NumberFormat format =
                NumberFormat.getNumberInstance(
                    locale);

        if (format instanceof DecimalFormat decimal) {
            decimal.setParseBigDecimal(true);
        }

        Number parsed = format.parse(normalized);

        BigDecimal kilograms =
                parsed instanceof BigDecimal decimal
                    ? decimal
                    : BigDecimal.valueOf(
                        parsed.doubleValue());

        return new Weight(kilograms);
    }

    @Override
    public String print(
            Weight value,
            Locale locale) {

        NumberFormat format =
                NumberFormat.getNumberInstance(
                    locale);

        format.setMaximumFractionDigits(2);

        return format.format(
                value.kilograms())
            + " kg";
    }
}
Java 
@Configuration(proxyBeanMethods = false)
public class DomainFormattingConfiguration
        implements WebMvcConfigurer {

    @Override
    public void addFormatters(
            FormatterRegistry registry) {

        registry.addFormatter(
            new WeightFormatter());
    }
}

Java NumberFormat formats and parses numbers according to locale conventions such as decimal separators and grouping. Java DateTimeFormatter likewise supports localized styles and can be configured with locale, chronology, zone, and decimal style.[28][29]

11.1 FormatterRegistrar

A FormatterRegistrar groups related converters and formatters and registers them against a FormatterRegistry. It is useful for a reusable domain-formatting module or for configuring related date/time policies consistently.[30]

12. Formatting versus JSON serialization

MVC formatting participates primarily in string conversion used by request parameters, path variables, form binding, model rendering, and other DataBinder scenarios. JSON request and response bodies are handled by HTTP message converters and their serialization libraries. An @DateTimeFormat annotation should therefore not be assumed to configure Jackson’s JSON representation.[20][25]

JSON 
{
  "issuedAt": "2026-07-31T18:45:00Z",
  "amount": 1499.95,
  "currency": "USD",
  "messageCode": "invoice.payment-due",
  "localizedDetail": "Payment is due on August 15, 2026."
}

A robust API keeps typed machine fields stable and, when useful, adds a localized display string. Clients should not have to parse localized text to recover an amount or timestamp.

13. Localized validation and binding errors

Spring’s binding and validation system records message codes rather than only final strings. DefaultMessageCodesResolver expands a rejected code into more specific candidates that can include the object name, field name, and field type, allowing specific translations with generic fallbacks.[31]

Properties 
# Most specific:
NotBlank.registrationForm.email=Enter your email address.

# Field-wide fallback:
NotBlank.email=This field cannot be blank.

# Constraint-wide fallback:
NotBlank=A value is required.

typeMismatch.registrationForm.birthDate=Use a valid date.

13.1 Jakarta Bean Validation

Java 
public record RegistrationRequest(

    @NotBlank(
        message = "{registration.email.required}")
    @Email(
        message = "{registration.email.invalid}")
    String email,

    @Size(
        min = 12,
        message = "{registration.password.length}")
    String password) {
}
Java 
@Configuration(proxyBeanMethods = false)
public class ValidationConfiguration
        implements WebMvcConfigurer {

    private final MessageSource messageSource;

    public ValidationConfiguration(
            MessageSource messageSource) {
        this.messageSource = messageSource;
    }

    @Override
    public Validator getValidator() {
        LocalValidatorFactoryBean validator =
                new LocalValidatorFactoryBean();

        validator.setValidationMessageSource(
            messageSource);

        return validator;
    }
}

LocalValidatorFactoryBean is Spring’s central Jakarta Validation bootstrap and can use a Spring MessageSource instead of the default ValidationMessages.properties lookup. When Bean Validation is present, Spring MVC registers a global validator by default; explicit configuration is useful when sharing the application message source or customizing validation behavior.[32][33]

13.2 Localized API errors

Java 
@RestControllerAdvice
public final class LocalizedErrorHandler {

    private final MessageSource messages;

    public LocalizedErrorHandler(
            MessageSource messages) {
        this.messages = messages;
    }

    @ExceptionHandler(OrderNotFoundException.class)
    ResponseEntity<ProblemDetail> notFound(
            OrderNotFoundException exception,
            Locale locale) {

        ProblemDetail problem =
                ProblemDetail.forStatus(
                    HttpStatus.NOT_FOUND);

        problem.setTitle(
            messages.getMessage(
                "problem.order-not-found.title",
                null,
                locale));

        problem.setDetail(
            messages.getMessage(
                "problem.order-not-found.detail",
                new Object[] {
                    exception.orderId()
                },
                locale));

        problem.setProperty(
            "code",
            "ORDER_NOT_FOUND");

        return ResponseEntity
            .status(HttpStatus.NOT_FOUND)
            .body(problem);
    }
}

Keep the stable machine code independent from localized title and detail. Logs and telemetry should record the stable code and structured arguments; localized text can be added for user-facing diagnostics.

14. Localization in views and templates

Spring-integrated view technologies can resolve messages and use the current locale through their Spring support. The core design remains the same: templates reference message codes, and the active MessageSource supplies localized content.

HTML 
<h1 th:text="#{checkout.title}">
  Checkout
</h1>

<p th:text="#{checkout.total(${total})}">
  Total
</p>

<html
  th:lang="${#locale.toLanguageTag()}">

Set the document language and, when needed, text direction in rendered HTML. Keep layout flexible for translated text expansion and avoid embedding sentences in images.

15. Localization practices

15.1 Translate complete units

Use one message with arguments rather than combining a prefix, number, noun, and suffix in code. Translators need control over order and grammar.

15.2 Preserve typed values

Persist timestamps, amounts, currency codes, durations, and identifiers as typed data. Format them at the user boundary with an explicit locale and time zone.

15.3 Define fallback deliberately

Decide whether an unsupported locale falls back to a language-only bundle, a product default, or a controlled English root. Disable host-system fallback when server configuration must not affect customer output.

15.4 Treat bundles as deployable content

Validate duplicate keys, missing keys, argument counts, invalid patterns, and encoding in continuous integration. Make translator comments and screenshots available for context.

15.5 Localize safely

Message arguments remain untrusted data. HTML templates must escape them according to output context. Never use translated text as an authorization decision, database key, protocol command, or control-flow token.

15.6 Vary localized HTTP responses correctly

When representation language is negotiated through Accept-Language, caches need language-aware keys, commonly expressed through an appropriate Vary response header. Cookie- or session-personalized responses require compatible cache policy.

16. Testing internationalization

16.1 Resolve every supported locale

Java 
@SpringJUnitConfig(
    InternationalizationConfiguration.class)
class MessageBundleTest {

    @Autowired
    MessageSource messages;

    @ParameterizedTest
    @MethodSource("supportedLocales")
    void resolvesRequiredMessages(Locale locale) {
        assertDoesNotThrow(() ->
            messages.getMessage(
                "order.created",
                new Object[] {
                    UUID.randomUUID(),
                    new Date()
                },
                locale));
    }

    static Stream<Locale> supportedLocales() {
        return Stream.of(
            Locale.US,
            Locale.FRANCE,
            Locale.CANADA_FRENCH,
            Locale.forLanguageTag("es"));
    }
}

17. Diagnostics

17.1 NoSuchMessageException

Verify basename, classpath location, root bundle presence, code spelling, active locale, file encoding, and fallback settings. In Boot, auto-configuration does not activate when the default file for every configured basename is absent.[5]

17.2 Wrong language selected

Inspect Accept-Language, supported-locale configuration, resolver bean name, default locale, cookie/session state, and language-versus-region matching. Region-specific supported locales do not automatically create a language-only fallback.[12]

17.3 Locale change interceptor fails

AcceptHeaderLocaleResolver cannot mutate the client’s header. Use a cookie or session resolver for an application-controlled preference, and ensure the interceptor path and HTTP method match the request.[12][16]

17.4 Apostrophes or braces render incorrectly

The message is being interpreted as a MessageFormat pattern. Escape literal apostrophes correctly, validate braces, and keep formatting behavior consistent across bundles.[9]

17.5 @DateTimeFormat does not change JSON

The annotation participates in Spring field formatting and data binding, while JSON bodies are handled by an HTTP message converter and serializer. Configure the serializer or DTO contract separately.[20][25]

17.6 Background task uses server locale

The request’s thread-bound locale did not cross the asynchronous boundary. Capture the required locale or language tag in the work item and pass it explicitly.[18]

18. Expert practices

  • Use stable semantic message codes and document argument contracts.
  • Keep a complete root bundle and test all supported locales.
  • Disable system-locale fallback when deployment-host settings must not affect output.
  • Use Accept-Language for stateless negotiation and cookie/session resolvers for an application-managed preference.
  • Represent time zone and currency explicitly rather than deriving them from locale.
  • Use locale-aware formatters for human input and stable ISO/typed forms for machine APIs.
  • Configure validation to use the shared message source where one translation catalog is desired.
  • Pass locale explicitly to asynchronous, scheduled, batch, and messaging work.
  • Return stable machine error codes beside localized human detail.
  • Validate message patterns, argument counts, encoding, missing keys, fallback, and layout expansion in CI.

19. Summary

  • ApplicationContext implements MessageSource, so message resolution is a core Spring capability.
  • MessageSource resolves codes, arguments, defaults, and locales; MessageSourceResolvable supports ordered candidate codes.
  • ResourceBundleMessageSource uses JDK resource bundles; ReloadableResourceBundleMessageSource adds Spring resource and reload configuration.
  • Spring Boot auto-configures message bundles through spring.messages when a default bundle file exists.
  • MVC uses LocaleResolver; the default strategy is request Accept-Language.
  • Cookie and session resolvers support application-managed preferences; accept-header and fixed resolvers are immutable from the server side.
  • WebFlux uses its own exchange-based LocaleContextResolver.
  • LocaleContext can include a locale and, through an extension, a time zone.
  • Spring formatting adds locale-aware printers and parsers above general conversion.
  • @DateTimeFormat, @NumberFormat, and @DurationFormat control field and parameter formatting, not arbitrary JSON serialization.
  • Validation errors resolve through message-code hierarchies, and Jakarta Validation can share Spring’s MessageSource.
  • Correct localization requires complete messages, typed values, explicit fallback, durable translation governance, and locale-aware testing.

When localized output is wrong, trace four independent decisions: Which locale and time zone were resolved? Which message codes and bundle candidates were searched? Which arguments were passed to MessageFormat? Which formatter or serializer produced each typed value? Separating those layers turns internationalization from scattered string handling into a predictable application subsystem.
