Spring Framework Core Technologies

Spring Core Container

A rigorous guide to the Spring IoC container, BeanFactory and ApplicationContext, bean lifecycle and scopes, XML/Java/annotation configuration, component scanning, dependency injection, autowiring resolution, profiles, property injection, and conditional bean registration.

Spring Framework 7.0.9IoC · Beans · DI · WiringJava, XML, annotations, and web scopesLong-form technical articleVancouver references
Abstract. The Spring Core Container is the foundation beneath Spring MVC, transactions, data access, messaging, scheduling, security integration, and most higher-level Spring programming models. It represents application components as BeanDefinition metadata, turns those definitions into object graphs, resolves dependencies, manages scopes and lifecycle callbacks, applies post-processors, and may replace raw instances with proxies. The underlying BeanFactory defines the essential bean-container contract; ApplicationContext extends it with resource loading, events, message resolution, environment access, automatic infrastructure detection, and lifecycle management. This article develops the container from first principles and connects configuration styles, dependency injection, autowiring, qualifiers, primary candidates, properties, profiles, conditions, scopes, lifecycle, and circular dependency behavior into one coherent model.

Spring Framework 7.0.9 identifies the IoC container as one of the framework’s central technologies. Dependency injection is the mechanism by which a bean declares collaborators through constructor or factory arguments, properties, or configuration methods while the container supplies those collaborators instead of the bean locating or constructing them itself.[1][2]

1. Spring IoC Container

Inversion of Control describes a reversal in responsibility. Instead of application objects controlling construction, lookup, configuration, and lifecycle of collaborating objects, the container receives configuration metadata and assembles the object graph. Dependency injection is Spring’s principal IoC mechanism: application classes express requirements, while the container resolves and injects matching values.[2]

1 Configuration sources are read: XML, annotated classes, @Bean methods, scanned components, or programmatic registrations.
2 Those sources become BeanDefinition metadata in a bean-definition registry.
3 Factory post-processors can modify definitions before ordinary beans are created.
4 The factory instantiates beans and recursively resolves dependencies.
5 Dependency injection, awareness callbacks, post-processors, and initialization callbacks run.
6 A post-processor may return a proxy rather than the raw target as the exposed bean reference.
7 At shutdown, destruction-aware post-processors and destroy callbacks run for managed beans whose scopes support destruction.

The key abstraction is metadata rather than annotation syntax. XML <bean> elements, component scanning, and Java @Bean methods all ultimately describe beans to the same container. The core BeanFactory level does not assume a particular configuration representation; readers and post-processors translate different configuration styles into the shared metadata model.[3]

1.2 Bootstrapping the core container

Java
try (AnnotationConfigApplicationContext context =
        new AnnotationConfigApplicationContext()) {

    context.getEnvironment()
        .setActiveProfiles("production");

    context.register(CoreConfiguration.class);
    context.scan("com.example.orders");
    context.refresh();

    OrderService service =
        context.getBean(OrderService.class);

    service.processPendingOrders();
}

AnnotationConfigApplicationContext is a common core-container entry point for annotated classes, scanning, and Java configuration. A context can be built empty, have its environment prepared and components registered, and then be explicitly refreshed. Spring recommends ApplicationContext rather than a bare BeanFactory for ordinary application bootstrapping.[3][4]

2. BeanFactory

BeanFactory is the root interface for accessing a Spring bean container. It defines lookup by name and type, singleton/prototype queries, type checks, aliases, and lazy ObjectProvider access. Its implementations hold bean definitions identified by names and can return shared or independent object instances according to the definition’s scope.[5]

Java
BeanFactory factory = context;

PaymentGateway gateway =
    factory.getBean(PaymentGateway.class);

ObjectProvider<AuditSink> provider =
    factory.getBeanProvider(AuditSink.class);

provider.ifAvailable(
    sink -> sink.record("context-ready"));

Application code should normally receive dependencies through injection rather than call getBean(). Pulling dependencies from the factory creates a service-locator dependency on the container and hides required collaborators from the class API. Provider-style access is appropriate when the requirement itself is optional, lazy, multiple, or per-use.[5]

2.1 DefaultListableBeanFactory

DefaultListableBeanFactory is a central configurable implementation used inside higher-level contexts. It combines bean creation with listable registry semantics and serves as the internal bean-factory delegate for GenericApplicationContext. Container extensions frequently operate against this level even when application code sees only ApplicationContext.[3]

3. ApplicationContext

ApplicationContext extends BeanFactory and adds higher-level container services. It exposes the application Environment, publishes events, resolves messages, loads resources, supports parent contexts, and automatically detects many infrastructure beans such as post-processors and listeners. Normal applications should treat the context as the complete container abstraction.[6]

Practical rule. Use ApplicationContext for application bootstrapping and application-level integration. Work directly with BeanFactory APIs when implementing framework extensions, container infrastructure, or specialized low-level code.

4. Bean lifecycle

Bean creation is a pipeline rather than a constructor call. The exact callbacks depend on the bean and context, but Spring’s lifecycle includes awareness interfaces, bean post-processors, initialization callbacks, and destruction callbacks. Post-processors are also the mechanism behind annotation injection and AOP proxy creation.[5][7]

1 Resolve bean definition, scope, constructor or factory method, and dependencies.
2 Instantiate the raw bean.
3 Populate fields, properties, and annotated injection points.
4 Invoke relevant *Aware callbacks.
5 Invoke BeanPostProcessor.postProcessBeforeInitialization.
6 Run @PostConstruct, InitializingBean.afterPropertiesSet(), and configured init methods.
7 Invoke postProcessAfterInitialization; this stage may expose a proxy.
8 On destruction, run destruction-aware processors and applicable destroy callbacks.

4.1 Lifecycle callback example

Java
public final class PricingCatalog {

    private final PricingRepository repository;
    private Map<String, Price> cache;

    public PricingCatalog(PricingRepository repository) {
        this.repository = repository;
    }

    @PostConstruct
    void initialize() {
        cache = repository.loadCurrentPrices();
    }

    @PreDestroy
    void clear() {
        cache = Map.of();
    }
}
Java
@Configuration(proxyBeanMethods = false)
public class PricingConfiguration {

    @Bean(
        initMethod = "initialize",
        destroyMethod = "close")
    LegacyPricingClient pricingClient() {
        return new LegacyPricingClient();
    }
}

Spring supports jakarta.annotation.PostConstruct/PreDestroy, Spring-specific InitializingBean/DisposableBean, and bean-definition init/destroy methods. Modern application code commonly favors annotations or explicit bean metadata rather than lifecycle callback interfaces because that avoids coupling the class to Spring interfaces.[8][9]

4.2 BeanPostProcessor

Java
@Component
public final class TimedComponentPostProcessor
        implements BeanPostProcessor {

    @Override
    public Object postProcessAfterInitialization(
            Object bean,
            String beanName) {

        if (bean.getClass()
                .isAnnotationPresent(TimedComponent.class)) {
            return createTimingProxy(bean);
        }

        return bean;
    }
}

A post-processor sees applicable beans before and after initialization and may replace the exposed object, commonly with a proxy. AutowiredAnnotationBeanPostProcessor performs annotation-based injection; Spring AOP infrastructure likewise uses post-processors for proxy wrapping.[7]

5. Bean scopes

Scope defines lifecycle and lookup semantics for a bean definition. The default singleton scope yields one shared instance per bean definition per Spring IoC container—not one object per JVM. prototype creates independent instances. Request, session, application, and WebSocket scopes are available in appropriate web-aware contexts.[10]

ScopeIdentity boundaryTypical use
singletonOne instance per bean definition per containerStateless services, repositories, clients
prototypeNew instance per request for the beanStateful short-lived helpers
requestOne instance per HTTP requestRequest-local metadata/state
sessionOne instance per HTTP sessionSession web state
applicationOne instance per ServletContextServlet-application-wide state
websocketOne instance per WebSocket sessionSTOMP/WebSocket conversation state

5.1 Singleton

Java
@Service
@Scope(ConfigurableBeanFactory.SCOPE_SINGLETON)
public final class ExchangeRateService {

    private final ExchangeRateClient client;

    public ExchangeRateService(ExchangeRateClient client) {
        this.client = client;
    }
}

Singleton is the default and fits stateless collaborators. Mutable singleton state is shared by every caller and therefore needs correct concurrency semantics. Spring’s singleton differs from the GoF Singleton pattern because the container owns instance identity and can hold several singleton definitions of the same Java class under different bean names.[5][10]

5.2 Prototype

Java
@Component
@Scope(ConfigurableBeanFactory.SCOPE_PROTOTYPE)
public final class CsvExportJob {
    private final StringBuilder buffer = new StringBuilder();
    public void append(String row) {
        buffer.append(row).append('\n');
    }
}

Injecting a prototype directly into a singleton resolves the prototype while the singleton is created, so the singleton retains that one instance. Use ObjectProvider, method injection, or another factory abstraction when the singleton needs a new prototype repeatedly. Spring initializes prototypes but does not retain them to invoke ordinary destruction callbacks later; client code owns cleanup after handoff.[10]

Java
@Service
public final class ExportService {

    private final ObjectProvider<CsvExportJob> jobs;

    public ExportService(ObjectProvider<CsvExportJob> jobs) {
        this.jobs = jobs;
    }

    public byte[] export(List<String> rows) {
        CsvExportJob job = jobs.getObject();
        rows.forEach(job::append);
        return job.toBytes();
    }
}

5.3 Request

Java
@Component
@RequestScope
public final class RequestContext {
    private final UUID requestId = UUID.randomUUID();
    public UUID requestId() { return requestId; }
}

Request scope creates one target for one HTTP request. A scoped proxy makes a request-scoped dependency injectable into a longer-lived singleton; the proxy resolves the real target associated with the active request.[10]

5.4 Session

Java
@Component
@SessionScope
public class ShoppingSession {
    private final List<UUID> viewed = new ArrayList<>();
    public void viewed(UUID productId) { viewed.add(productId); }
}

Session scope associates the bean with an HTTP session. In distributed systems, session replication, affinity, serialization, persistence, and invalidation become operational concerns, so server-side session state should be kept deliberately small.

5.5 Application

Java
@Component
@ApplicationScope
public final class ServletApplicationStatistics {
    private final LongAdder requests = new LongAdder();
    public void started() { requests.increment(); }
}

Application scope is tied to the Servlet ServletContext. It is not simply another spelling for the ordinary Spring singleton scope, even though lifetimes can appear similar in a single web application.[10]

5.6 WebSocket

Java
@Component
@Scope(
    scopeName = "websocket",
    proxyMode = ScopedProxyMode.TARGET_CLASS)
public class ConversationState {
    private final Instant connectedAt = Instant.now();
    public Instant connectedAt() { return connectedAt; }
}

WebSocket scope is associated with a WebSocket session in Spring’s STOMP-over-WebSocket support. Like other short-lived web scopes, it normally requires proxy or provider semantics when referenced from a longer-lived bean.[10]

6. Bean Configuration

Spring supports several configuration sources because all of them produce the same underlying bean-definition model. XML remains supported; Java configuration supplies definitions with @Configuration and @Bean; component scanning registers stereotype-annotated classes; annotation post-processors then interpret injection and lifecycle metadata.[4][11]

7. XML configuration

XML
<?xml version="1.0" encoding="UTF-8"?>
<beans
  xmlns="http://www.springframework.org/schema/beans"
  xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
  xmlns:context="http://www.springframework.org/schema/context"
  xsi:schemaLocation="
    http://www.springframework.org/schema/beans
    https://www.springframework.org/schema/beans/spring-beans.xsd
    http://www.springframework.org/schema/context
    https://www.springframework.org/schema/context/spring-context.xsd">

  <context:annotation-config/>

  <bean id="clock"
        class="java.time.Clock"
        factory-method="systemUTC"/>

  <bean id="auditRepository"
        class="com.example.audit.JdbcAuditRepository">
    <constructor-arg ref="dataSource"/>
  </bean>

  <bean id="auditService"
        class="com.example.audit.AuditService"
        init-method="initialize"
        destroy-method="close">
    <constructor-arg ref="auditRepository"/>
    <constructor-arg ref="clock"/>
    <property name="batchSize" value="500"/>
  </bean>
</beans>

XML can express constructor arguments, properties, values, references, collections, scopes, lazy initialization, primary candidates, lifecycle callbacks, profiles, and legacy autowiring modes. <context:annotation-config/> registers annotation-processing infrastructure for already defined beans; <context:component-scan> also scans and implicitly enables the normal annotation processors.[11][12]

8. Java configuration

Java configuration uses @Configuration classes as definition sources and @Bean methods as factory definitions. Method parameters are dependency injection points and use the same candidate resolution semantics as constructor injection.[13][14]

Java
@Configuration(proxyBeanMethods = false)
public class ApplicationConfiguration {

    @Bean
    Clock clock() {
        return Clock.systemUTC();
    }

    @Bean
    AuditRepository auditRepository(DataSource dataSource) {
        return new JdbcAuditRepository(dataSource);
    }

    @Bean(initMethod = "initialize", destroyMethod = "close")
    AuditService auditService(
            AuditRepository repository,
            Clock clock) {

        AuditService service = new AuditService(repository, clock);
        service.setBatchSize(500);
        return service;
    }
}

8.1 @Configuration

@Configuration marks a class whose primary purpose is bean definition. With full configuration processing, direct calls from one @Bean method to another are intercepted so they obey container scope and lifecycle. With proxyBeanMethods=false, or when @Bean methods live on ordinary components, they operate in “lite” mode: direct Java calls are not intercepted and behave like normal method calls.[13][15]

Java
@Configuration(proxyBeanMethods = false)
public class LiteConfiguration {

    @Bean
    Repository repository() {
        return new Repository();
    }

    @Bean
    Service service(Repository repository) {
        // Dependency is explicit; no direct @Bean call required.
        return new Service(repository);
    }
}

8.2 @Bean

@Bean is the Java analog of XML <bean>. The returned object becomes a managed bean, the method name is normally its bean name, and attributes can define names/aliases, initialization and destruction methods, and autowire-candidate behavior. Spring 7 also supports custom default name generation for configuration methods.[14]

Java
@Bean({"exchangeRateClient", "fxClient"})
@Primary
ExchangeRateClient rates(HttpClient http) {
    return new RemoteExchangeRateClient(http);
}

9. Annotation-based configuration

Annotation configuration overlays metadata on classes, methods, fields, and parameters. Processing is not inherent in the Java annotation itself; post-processors such as AutowiredAnnotationBeanPostProcessor inspect and apply it during bean creation.[11][7]

9.1 @Component

Java
@Component
public final class OrderNumberGenerator {
    private final AtomicLong sequence = new AtomicLong();
    public String next() {
        return "ORD-" + sequence.incrementAndGet();
    }
}

@Component is Spring’s generic stereotype. @Repository, @Service, @Controller, and custom meta-annotated stereotypes build on it. Component scanning can register these types without an explicit XML or @Bean definition.[12]

10. Component scanning

Java
@Configuration
@ComponentScan(
    basePackages = {
        "com.example.order",
        "com.example.payment"
    },
    excludeFilters = @ComponentScan.Filter(
        type = FilterType.ANNOTATION,
        classes = Experimental.class))
public class ComponentConfiguration {
}

Default scan filters detect @Component, common stereotypes, @Configuration, and custom annotations meta-annotated with @Component. Include and exclude filters can select by annotation, assignable type, AspectJ expression, regular expression, or custom TypeFilter.[12]

Scanning defines architectural reach. Narrow package roots reduce accidental registration, name collisions, startup work, and hidden dependencies. Avoid scanning an organization-wide root merely because it is convenient.

11. Dependency Injection

Dependency injection removes construction and lookup responsibility from application classes. A bean declares collaborators through constructors, factory-method parameters, setters, or other injection points; the container identifies matching beans or values and supplies them. This also improves testability because a class can be constructed directly with test doubles without booting Spring.[2]

12. Constructor injection

Java
@Service
public final class TransferService {

    private final AccountRepository accounts;
    private final FraudPolicy fraudPolicy;
    private final DomainEventPublisher events;

    public TransferService(
            AccountRepository accounts,
            FraudPolicy fraudPolicy,
            DomainEventPublisher events) {

        this.accounts = Objects.requireNonNull(accounts);
        this.fraudPolicy = Objects.requireNonNull(fraudPolicy);
        this.events = Objects.requireNonNull(events);
    }
}

If a managed class has only one constructor, @Autowired is unnecessary. Spring’s DI guidance advocates constructor injection for mandatory collaborators because required dependencies can be final, objects can be immutable, and callers do not observe partially initialized instances.[16][2]

A large constructor is useful design feedback that the type may have too many responsibilities. Field injection hides that signal rather than resolving it.

13. Setter injection

Java
@Component
public final class ReportRenderer {

    private WatermarkRenderer watermark = WatermarkRenderer.noop();

    @Autowired(required = false)
    public void setWatermark(WatermarkRenderer watermark) {
        this.watermark = watermark;
    }
}

Setter or configuration-method injection is appropriate for optional dependencies that have sensible defaults and for intentionally reconfigurable objects. Spring recommends constructors for mandatory dependencies and setters/configuration methods primarily for optional ones.[2]

14. Field injection

Java
@Component
public class LegacySettlementService {

    @Autowired
    private SettlementRepository repository;

    // Supported, but not a preferred default design.
}

Spring supports field injection through annotation post-processing. It is concise, but required dependencies are hidden from the constructor contract, fields cannot normally be final, and plain unit tests require reflection or a Spring context to populate them. Constructor injection gives better encapsulation for ordinary application code.[16]

15. Dependency-injection best practices

  • Use constructor injection for required collaborators.
  • Use interfaces where substitution represents a real architectural boundary; do not create interfaces only to satisfy the container.
  • Use setter/configuration injection when optionality or reconfiguration is intrinsic to the type.
  • Keep configuration values distinct from service dependencies; group cohesive settings when the surrounding application framework supports typed configuration objects.
  • Prefer explicit dependencies to static access, service locators, and arbitrary context lookup.
  • Treat large constructors and dense dependency graphs as design signals.
  • Use ObjectProvider for genuinely optional, lazy, multiple, or per-use retrieval—not as a universal escape hatch.

16. Circular dependencies

Java
@Component
final class BillingService {
    BillingService(InvoiceService invoices) { }
}

@Component
final class InvoiceService {
    InvoiceService(BillingService billing) { }
}

Pure constructor cycles are unresolvable: neither object can be created first, so the container throws BeanCurrentlyInCreationException. Setter-based singleton cycles can sometimes be resolved through early references, but one bean can be injected before full initialization. Spring documents that mechanism as possible but not recommended.[2]

16.1 Architectural resolution

The preferred solution is to remove the cycle: move shared behavior to a third component, invert one dependency behind an abstraction, publish an event, or place coordination in a higher-level service. @Lazy or provider lookup can defer resolution but does not remove conceptual coupling.

17. Bean Wiring

Autowiring starts with the required type, finds candidate bean definitions, narrows candidates by qualifiers and candidate flags, applies single-value preference rules such as @Primary, and fails rather than guessing if ambiguity remains. Collections and maps intentionally receive multiple matching beans.[17][18]

1 Determine injection-point type and generic information.
2 Find candidate bean definitions whose predicted types match.
3 Apply autowire-candidate flags and qualifier restrictions.
4 For one value, apply primary/fallback/default-candidate and name tie-breaking rules.
5 For collections, arrays, maps, or providers, retain all qualifying candidates.
6 Resolve scope/laziness and instantiate selected dependencies as needed.

18. @Autowired

@Autowired can annotate constructors, fields, setters, arbitrary configuration methods, and parameters. A one-constructor class does not need the annotation. Arrays, typed collections, and maps can receive all matching beans; map keys are bean names.[16]

Java
@Component
public final class NotificationRouter {

    private final List<NotificationChannel> channels;
    private final Map<String, NotificationChannel> byName;

    public NotificationRouter(
            List<NotificationChannel> channels,
            Map<String, NotificationChannel> byName) {
        this.channels = channels;
        this.byName = byName;
    }
}

18.1 Optional dependencies

Java
@Component
public final class AuditFacade {

    private final Optional<AuditSink> audit;
    private final ObjectProvider<ExpensiveDiagnostics> diagnostics;

    public AuditFacade(
            Optional<AuditSink> audit,
            ObjectProvider<ExpensiveDiagnostics> diagnostics) {
        this.audit = audit;
        this.diagnostics = diagnostics;
    }
}

Optional<T> represents optionality explicitly. ObjectProvider<T> adds lazy lookup, availability and uniqueness queries, iteration, and streams.[5][16]

19. @Qualifier

@Qualifier narrows type-matching candidates with semantic metadata. Its value is not fundamentally a unique bean-name lookup; it describes a characteristic within the candidate set. Multiple beans may share the same qualifier and be injected as a qualified collection.[19]

Java
@Bean
@Qualifier("persistent")
AuditSink databaseAuditSink() {
    return new DatabaseAuditSink();
}

@Bean
@Qualifier("ephemeral")
AuditSink consoleAuditSink() {
    return new ConsoleAuditSink();
}

@Service
public final class ComplianceService {
    public ComplianceService(
            @Qualifier("persistent") AuditSink audit) {
    }
}

19.1 Custom qualifier

Java
@Target({
    ElementType.FIELD,
    ElementType.PARAMETER,
    ElementType.METHOD,
    ElementType.TYPE
})
@Retention(RetentionPolicy.RUNTIME)
@Qualifier
public @interface Region {
    String value();
}

@Bean
@Region("eu")
TaxPolicy euTaxPolicy() {
    return new EuTaxPolicy();
}

@Service
public final class CheckoutService {
    public CheckoutService(@Region("eu") TaxPolicy policy) { }
}

Custom qualifiers make selection semantics type-safe and reusable. CustomAutowireConfigurer can also register third-party annotations as qualifier types.[20]

20. @Primary

@Primary gives one candidate preference when several beans match a single-valued injection point. It does not remove non-primary beans from list, array, map, or provider injection.[18]

Java
@Bean
@Primary
ExchangeRateProvider liveRates() {
    return new LiveExchangeRates();
}

@Bean
ExchangeRateProvider fixedRates() {
    return new FixedExchangeRates(BigDecimal.ONE);
}

@Service
public final class PriceService {
    // Receives liveRates.
    public PriceService(ExchangeRateProvider rates) { }
}
Primary is a default; qualifier is a requirement. Use @Primary when one implementation is genuinely the normal choice. Use @Qualifier when an injection point requires a particular semantic variant.

21. @Value

@Value injects property placeholders and Spring Expression Language expressions into fields, methods, and constructor or method parameters. Placeholder syntax uses ${...}; SpEL uses #{...}. Type-conversion infrastructure converts strings to supported target types.[21]

Properties
payments.base-url=https://payments.internal
payments.timeout=2s
payments.max-attempts=3
Java
@Component
public final class PaymentClient {

    public PaymentClient(
            @Value("${payments.base-url}") URI baseUrl,
            @Value("${payments.timeout:3s}") Duration timeout,
            @Value("${payments.max-attempts:2}") int maxAttempts) {
        // ...
    }
}
Java
@Value("#{systemProperties['user.timezone'] ?: 'UTC'}")
String timezone;

At the core-container level, Environment, property sources, placeholder resolution, and type conversion underpin value injection. Cohesive configuration should generally be modeled explicitly rather than spread across many unrelated fields.[21][22]

22. Profiles

The Environment models profiles and properties. A profile is a named logical group of bean definitions eligible for registration when active. @Profile may annotate components, configuration classes, and @Bean methods and supports expressions with !, &, |, and parentheses.[22]

Java
@Configuration(proxyBeanMethods = false)
public class StorageConfiguration {

    @Bean("documentStore")
    @Profile("development")
    DocumentStore localStore() {
        return new LocalDocumentStore(Path.of("./var/documents"));
    }

    @Bean("documentStore")
    @Profile("production & !disaster-recovery")
    DocumentStore productionStore() {
        return new RemoteDocumentStore();
    }

    @Bean("documentStore")
    @Profile("disaster-recovery")
    DocumentStore recoveryStore() {
        return new RecoveryDocumentStore();
    }
}
Shell
java -Dspring.profiles.active=production -jar application.jar

Profiles can also be activated programmatically through the Environment. The default profile is named default and applies only when no other profile is active; it can be renamed.[22]

Use profiles for coarse structural variants. Ordinary values should remain properties. Excessive profiles create a combinatorial bean graph that is hard to reason about and test.

23. Conditional beans

@Conditional makes a component or @Bean eligible for registration only when every supplied Condition matches. A condition runs before the bean definition is registered and may inspect the environment, registry, resource loader, class loader, and annotated metadata, but it must not interact with bean instances.[23][24]

Java
public final class FeatureEnabledCondition
        implements Condition {

    @Override
    public boolean matches(
            ConditionContext context,
            AnnotatedTypeMetadata metadata) {

        return context.getEnvironment()
            .getProperty(
                "features.audit.enabled",
                Boolean.class,
                false);
    }
}

@Configuration(proxyBeanMethods = false)
public class FeatureConfiguration {

    @Bean
    @Conditional(FeatureEnabledCondition.class)
    AuditPublisher auditPublisher() {
        return new AuditPublisher();
    }
}

@Conditional can be placed on components, configuration classes, @Bean methods, or composed meta-annotations. If a configuration class is conditional, associated bean methods, imports, and component scans are subject to the condition.[23]

24. Autowiring resolution in detail

24.1 Ambiguous candidates

Java
@Bean
@Qualifier("fast")
Serializer jsonSerializer() {
    return new JsonSerializer();
}

@Bean
@Qualifier("compact")
Serializer binarySerializer() {
    return new BinarySerializer();
}

@Component
public final class Transport {
    public Transport(
            @Qualifier("compact") Serializer serializer) {
    }
}

A single-valued, unqualified dependency fails when several candidates remain and none can be uniquely preferred. Spring does not arbitrarily choose a same-type bean. Explicit wiring, qualifiers, @Primary, candidate flags, fallback/default-candidate semantics, and bean-name fallback are available to disambiguate.[17][18][19]

24.2 Collections and ordering

Java
@Component
@Order(10)
final class EmailValidator implements OrderValidator { }

@Component
@Order(20)
final class FraudValidator implements OrderValidator { }

@Service
final class ValidationPipeline {
    ValidationPipeline(List<OrderValidator> validators) {
        // Receives all matching validators in ordered form.
    }
}

Multi-element dependencies collect all qualifying beans. Ordering can be supplied through Ordered, @Order, or priority metadata. @Primary does not filter the collection because it only selects a preferred single value.[16][18]

25. Hidden initialization dependencies

Ordinary object dependencies belong in constructor or property references. When a bean depends on a side effect rather than a reference—such as registration performed by another bean—@DependsOn or XML depends-on can force initialization order. For singleton beans, it also influences destruction order.[25]

Java
@Bean
DriverRegistry driverRegistry() {
    return new DriverRegistry();
}

@Bean
@DependsOn("driverRegistry")
LegacyEngine legacyEngine() {
    return new LegacyEngine();
}

@DependsOn is not dependency injection and should not replace an explicit object dependency when one exists.

26. Programmatic registration in Spring 7

Spring Framework 7 adds first-class BeanRegistrar support for programmatic registration through BeanRegistry and Environment. It complements XML, component scanning, and @Bean methods and is useful when definitions arise from loops, metadata, environment choices, or extension libraries.[26]

Java
public final class RegionalClientRegistrar
        implements BeanRegistrar {

    @Override
    public void register(
            BeanRegistry registry,
            Environment environment) {

        String[] regions = environment.getProperty(
            "regions",
            String[].class,
            new String[] {"us-east"});

        for (String region : regions) {
            registry.registerBean(
                region + "Client",
                RegionalClient.class,
                spec -> spec.supplier(
                    context -> new RegionalClient(region)));
        }
    }
}

@Configuration
@Import(RegionalClientRegistrar.class)
class RegionalConfiguration { }

BeanCurrentlyInCreationExceptionConstructor cycle or re-entrant creationTrace graph and remove cycle
Injected field is nullObject created with new, unsupported/static targetEnsure the object itself is container-managed
Prototype appears reusedPrototype injected once into singletonUse provider/factory retrieval
Request scope failureNo active request or non-web contextUse web-aware context and scoped proxy
Duplicate object from @BeanDirect method call in lite configurationInject factory-method parameter
Conditional bean missingCondition evaluated false before registrationTest/log environment, classpath, resource, metadata inputs

The core container exposes startup instrumentation for bean instantiation, component scanning, configuration-class parsing and enhancement, factory post-processing, and context refresh. These step names are implementation diagnostics rather than a permanent public contract, but they can identify startup cost.[27]

28. Testing container configuration

Java
@Test
void productionGraphResolves() {
    try (AnnotationConfigApplicationContext context =
            new AnnotationConfigApplicationContext()) {

        context.getEnvironment()
            .setActiveProfiles("production");

        context.register(ApplicationConfiguration.class);
        context.refresh();

        assertThat(context.getBean(OrderService.class))
            .isNotNull();

        assertThat(context.getBeansOfType(PaymentGateway.class))
            .hasSize(1);
    }
}

Configuration tests should exercise supported profile and condition combinations, intentionally verify ambiguous candidates, and close the context so destruction callbacks run. Unit tests for ordinary services should usually construct the service directly rather than use Spring only to satisfy constructors.

29. Core-container anti-patterns

29.1 Context lookup in domain code

Calling ApplicationContext.getBean() from services hides dependencies and couples business logic to the container. Inject collaborators.

29.2 Field injection everywhere

It hides required collaborators and removes constructor-level invariants. Prefer constructor injection.

29.3 Bean names as architecture

A qualifier such as billingRepositoryImpl2 exposes incidental implementation naming. Prefer semantic qualifiers.

29.4 Profile for every value

Profiles alter bean eligibility. Ordinary configuration values belong in properties.

29.5 Conditions that instantiate beans

Conditions run during definition registration and must not interact with bean instances; use environment, classpath, resources, or metadata instead.[24]

29.6 Shorter scope directly captured by longer scope

Use a scoped proxy or provider so the longer-lived bean resolves the correct request/session target.

29.7 Hiding cycles with lazy injection

Deferral can let startup proceed but preserves conceptual coupling. Remove the cycle unless lazy retrieval has independent value.

30. Worked configuration

Java
@Configuration(proxyBeanMethods = false)
@ComponentScan("com.example.checkout")
@PropertySource("classpath:checkout.properties")
public class CheckoutConfiguration {

    @Bean
    Clock clock() {
        return Clock.systemUTC();
    }

    @Bean
    @Primary
    @Profile("production")
    PaymentGateway liveGateway(
            @Value("${payments.base-url}") URI baseUrl,
            @Value("${payments.timeout:2s}") Duration timeout) {
        return new HttpPaymentGateway(baseUrl, timeout);
    }

    @Bean
    @Profile("development")
    PaymentGateway fakeGateway() {
        return new FakePaymentGateway();
    }

    @Bean
    @Conditional(FeatureEnabledCondition.class)
    AuditSink auditSink(DataSource dataSource) {
        return new JdbcAuditSink(dataSource);
    }

    @Bean
    CheckoutPolicy policy(
            @Qualifier("standard") DiscountPolicy discount,
            ObjectProvider<AuditSink> audit,
            Clock clock) {
        return new CheckoutPolicy(
            discount,
            audit.getIfAvailable(AuditSink::noop),
            clock);
    }
}

@Component("standard")
@Qualifier("standard")
final class StandardDiscountPolicy implements DiscountPolicy { }

@Service
final class CheckoutService {

    private final PaymentGateway payments;
    private final CheckoutPolicy policy;
    private final RequestContext request;

    CheckoutService(
            PaymentGateway payments,
            CheckoutPolicy policy,
            RequestContext request) {
        this.payments = payments;
        this.policy = policy;
        this.request = request;
    }
}

This configuration connects the requested mechanisms: scanning registers application components; @Configuration supplies explicit infrastructure definitions; constructor and @Bean parameters are injection points; @Primary establishes a default single candidate; @Qualifier requests a semantic variant; @Profile selects structural alternatives; @Conditional controls eligibility; ObjectProvider expresses optionality; @Value injects external values; and the request-scoped dependency is represented through scoped-proxy behavior.

31. Expert practices

  • Design classes so they can be instantiated without Spring; let the container assemble them.
  • Use ApplicationContext at application boundaries and avoid context lookup inside domain logic.
  • Prefer constructor injection and immutable required dependencies.
  • Keep component-scan roots narrow and package architecture intentional.
  • Use Java configuration for explicit integration wiring and stereotypes for obvious application components.
  • Use semantic qualifiers and a genuine default @Primary.
  • Use profiles for coarse environment variants and conditions for registration-time capabilities.
  • Avoid dependency cycles rather than relying on early references.
  • Use providers or scoped proxies when injecting shorter-lived beans into longer-lived beans.
  • Keep lifecycle callbacks small, deterministic, and free of hidden long-running remote work.
  • Test each supported container graph, including profiles and conditions.

32. Summary

  • The Spring IoC container converts configuration metadata into managed object graphs.
  • BeanFactory is the root bean-container contract; ApplicationContext is the normal application-level container.
  • XML, Java configuration, component scanning, and programmatic registration all feed the same bean-definition model.
  • Bean creation passes through dependency resolution, injection, awareness callbacks, post-processors, lifecycle callbacks, and potentially proxy creation.
  • Singleton scope is per bean definition per container, not JVM-global.
  • Prototype creates new instances on bean requests but does not provide automatic destruction ownership after handoff.
  • Request, session, application, and WebSocket scopes require a web-aware context and often scoped proxies.
  • @Configuration and @Bean provide explicit Java bean definitions; lite mode requires normal Java-call discipline.
  • @Component and component scanning provide implicit registration of stereotypes.
  • Constructor injection is the recommended default for mandatory dependencies; setter/configuration injection fits optional dependencies.
  • Constructor dependency cycles are unresolvable and usually indicate a design problem.
  • @Autowired resolves by type, while qualifiers, primary status, candidate flags, and names refine selection.
  • @Qualifier expresses semantic narrowing; @Primary expresses a default preference.
  • @Value injects placeholders and SpEL; Environment underpins properties and profiles.
  • @Profile selects environment-specific bean graphs; @Conditional generalizes registration-time predicates.
  • Spring 7 adds first-class BeanRegistrar support for flexible programmatic definitions.

A useful mental model is to follow one dependency from metadata to runtime: Which configuration source registered the bean definition? Which scope owns its identity? Which injection point requested it? Which candidates matched? Which qualifier or primary rule selected it? Which lifecycle callbacks ran? Did a post-processor replace it with a proxy? Which context will destroy it? Once those questions are explicit, even large Spring applications become predictable rather than “annotation magic.”
