Observability in Spring

A technical guide to logging with SLF4J, Logback, and Log4j2; structured JSON logs; Micrometer metrics; Prometheus scraping and PromQL; Grafana dashboards and alerts; distributed tracing; OpenTelemetry; correlation; context propagation; testing; security; and telemetry cost control.

Spring Boot 4.1.0 Micrometer 1.17.0 SLF4J 2.0.x · OpenTelemetry Java stable signals Long-form technical article Vancouver references
Abstract. Observability is the ability to infer a running system’s internal state from externally available telemetry. In Spring Boot, logs are produced through a logging facade and implementation, metrics through Micrometer, and traces through Micrometer Observation and Micrometer Tracing backed by OpenTelemetry or Brave. Prometheus scrapes dimensional metrics, Grafana queries and visualizes telemetry, and the OpenTelemetry Collector receives, processes, and exports traces, metrics, or logs. A sound design does not merely “turn on Actuator.” It defines stable event schemas, low-cardinality metric dimensions, bounded trace sampling, correlation across asynchronous boundaries, trustworthy service-level indicators, secure diagnostic endpoints, retention and privacy controls, and a cost model. This article builds that design from application code through collectors, dashboards, alerts, and incident investigation.

Spring Boot defines observability around three pillars—logging, metrics, and traces—and uses Micrometer Observation for metrics and tracing integration. Micrometer is the Spring portfolio’s preferred vendor-neutral metrics facade, while OpenTelemetry provides stable Java APIs and SDKs for traces, metrics, and logs and the OTLP protocol for exporting telemetry.[1][2][3]

3. Logging architecture

1 Application code calls the SLF4J API.
2 Exactly one SLF4J provider routes events to Logback, Log4j2, or another implementation.
3 Logger configuration filters by name, level, marker, and policy.
4 Layouts or encoders transform events into text or JSON.
5 Appenders write to console, file, socket, or asynchronous queues.
6 A platform log agent collects standard output and ships it to a backend.

SLF4J is a facade: application source depends on its API while deployment selects a provider. SLF4J 2.x discovers providers through Java’s ServiceLoader. Logback-classic implements SLF4J directly; Log4j2 uses its SLF4J binding and Core runtime. Multiple providers cause ambiguous behavior and should be removed from the runtime classpath.[8][9][10]

4. SLF4J

4.1 Parameterized logging

Java 
private static final Logger log =
        LoggerFactory.getLogger(
            CheckoutService.class);

public CheckoutResult checkout(
        CheckoutCommand command) {

    log.info(
        "Starting checkout for order {} with {} lines",
        command.orderId(),
        command.lines().size());

    try {
        return process(command);
    }
    catch (PaymentException failure) {
        log.warn(
            "Payment authorization failed for order {}",
            command.orderId(),
            failure);
        throw failure;
    }
}

Parameterized messages avoid eagerly concatenating strings when a level is disabled and keep the message template separate from values. Pass an exception as the final argument to retain the stack trace; logging only failure.getMessage() discards type, cause chain, and location.

4.2 Fluent key-value logging

Java 
log.atInfo()
    .addKeyValue(
        "order.id",
        command.orderId())
    .addKeyValue(
        "customer.id",
        command.customerId())
    .addKeyValue(
        "line.count",
        command.lines().size())
    .addKeyValue(
        "currency",
        command.currency())
    .log("Order accepted");

SLF4J 2.0’s fluent API supports key-value pairs, arguments, markers, and suppliers. Spring Boot’s built-in structured formats include MDC entries and fluent key-value pairs in JSON, allowing search and aggregation without parsing prose.[8][11]

4.3 MDC and scope

Java 
public void handle(
        String tenantId,
        Runnable operation) {

    String previous =
            MDC.get("tenant.id");

    try {
        MDC.put(
            "tenant.id",
            tenantId);
        operation.run();
    }
    finally {
        if (previous == null) {
            MDC.remove("tenant.id");
        }
        else {
            MDC.put(
                "tenant.id",
                previous);
        }
    }
}

MDC is commonly backed by thread-local state, so values must be cleared and propagated deliberately across executors and reactive pipelines. Micrometer Tracing places trace and span IDs into MDC while a span is in scope, and Boot includes a correlation identifier in logs by default when tracing is active.[12]

Do not use MDC as a data store MDC exists to enrich the current log event. Large objects, high-cardinality business payloads, credentials, or values that are not reliably cleared cause memory, privacy, and correlation defects.

5. Logback

Spring Boot’s starters use spring-boot-starter-logging, and Logback is Boot’s first-choice logging system when it is present. Basic levels and output locations can be configured with logging.* properties; advanced behavior uses logback-spring.xml, which supports Boot’s Logback extensions.[13]

XML 
<configuration>
  <include resource=
    "org/springframework/boot/logging/logback/defaults.xml"/>

  <springProperty
    scope="context"
    name="applicationName"
    source="spring.application.name"
    defaultValue="application"/>

  <appender
    name="CONSOLE"
    class="ch.qos.logback.core.ConsoleAppender">
    <encoder>
      <pattern>
        %d{ISO8601} %-5level
        service=${applicationName}
        trace=%X{traceId:-}
        span=%X{spanId:-}
        logger=%logger{36}
        - %msg%n%wEx
      </pattern>
    </encoder>
  </appender>

  <appender
    name="ASYNC"
    class="ch.qos.logback.classic.AsyncAppender">
    <queueSize>4096</queueSize>
    <neverBlock>false</neverBlock>
    <appender-ref ref="CONSOLE"/>
  </appender>

  <root level="INFO">
    <appender-ref ref="ASYNC"/>
  </root>
</configuration>

Logback’s architecture separates loggers, appenders, and layouts or encoders. Asynchronous appenders move destination I/O to a worker thread but add a queue whose overflow policy must be explicit. If losing an audit or security event is unacceptable, do not configure a drop-on-overflow policy merely to preserve request throughput.[9][14]

Modern Logback also includes a JSON encoder that writes one JSON object per line. Spring Boot’s built-in structured logging often removes the need for a custom encoder, while native Logback configuration remains useful for multiple appenders, filters, rolling files, or bespoke schemas.[15]

Log4j2 layouts encode a LogEvent for its destination. The project recommends JSON Template Layout for structured production logging; the older JSON Layout is deprecated. Caller location requires stack walking and is expensive, especially for asynchronous logging, so it should be disabled unless operationally necessary.[16][17]

Asynchronous loggers and appenders move logging I/O off application threads and can absorb bursts. Log4j2 recommends benchmarking the actual application and retaining synchronous logging when asynchronous logging does not produce a material benefit, because queueing introduces complexity and failure policy.[18]

7. Structured logging

Structured logging represents events in a stable machine-readable schema rather than relying on regular-expression parsing of free text. Spring Boot supports ECS, GELF, and Logstash JSON formats for console or file output with either supported logging implementation. MDC and SLF4J fluent key-value pairs become JSON fields.[11]

YAML 
logging:
  structured:
    format:
      console: ecs

    ecs:
      service:
        name: ${spring.application.name}
        version: ${spring.application.version}
        environment: production

    json:
      exclude:
        - process.command_line
      rename:
        process.id: process.pid
      add:
        organization.name: example
      stacktrace:
        root: first
        max-length: 8192
        max-throwable-depth: 64
        include-common-frames: false
        include-hashes: true

7.1 Event schema

  • Use stable event names such as order.accepted rather than embedding the action only in prose.
  • Use typed fields for counts, amounts, durations, booleans, and timestamps.
  • Use one canonical field for trace ID, span ID, service, deployment environment, and version.
  • Keep human text concise; queries should use fields rather than message parsing.
  • Do not log access tokens, passwords, payment data, session cookies, raw personal records, or complete request bodies.
  • Bound stack-trace length and repeated exception volume.

7.2 Operational logs versus audit records

Operational logs are optimized for diagnosis and may be sampled, rotated, or dropped under pressure. Audit records require durable integrity, authorization, retention, and non-repudiation controls. A console appender is not automatically an audit system; publish audit events to a dedicated append-only store or durable broker with an explicit availability policy.

8.1 Custom meters

Java 
@Component
public final class CheckoutMetrics {

    private final Counter accepted;
    private final Counter rejected;
    private final Timer duration;
    private final DistributionSummary lineCount;

    public CheckoutMetrics(
            MeterRegistry registry) {

        accepted = Counter.builder(
                "orders.checkout.accepted")
            .description(
                "Accepted checkout commands")
            .register(registry);

        rejected = Counter.builder(
                "orders.checkout.rejected")
            .description(
                "Rejected checkout commands")
            .register(registry);

        duration = Timer.builder(
                "orders.checkout.duration")
            .description(
                "Checkout processing duration")
            .publishPercentileHistogram()
            .serviceLevelObjectives(
                Duration.ofMillis(100),
                Duration.ofMillis(250),
                Duration.ofSeconds(1))
            .register(registry);

        lineCount = DistributionSummary.builder(
                "orders.checkout.lines")
            .description(
                "Line count per checkout")
            .baseUnit("lines")
            .serviceLevelObjectives(
                1.0,
                5.0,
                20.0,
                100.0)
            .register(registry);
    }

    public <T> T record(
            CheckoutCommand command,
            Supplier<T> operation) {

        lineCount.record(
            command.lines().size());

        return duration.record(
            operation);
    }

    public void accepted() {
        accepted.increment();
    }

    public void rejected() {
        rejected.increment();
    }
}

8.2 Tags and cardinality

Java 
Counter.builder("orders.checkout.outcomes")
    .tag("outcome", "accepted")
    .tag("channel", "web")
    .register(registry)
    .increment();

Tags create a separate time series for every unique label combination. Safe dimensions have a small controlled value set: method, outcome, region, queue, route template, or product category. User IDs, order IDs, request IDs, exception messages, full URLs, SQL, and arbitrary tenant IDs are unbounded and should be logs or trace attributes rather than metric labels. Prometheus recommends investigating metrics whose cardinality can exceed roughly one hundred and emphasizes that label cardinality is a dominant performance risk.[19][20]

A tag multiplies storage Ten methods × ten status values × fifty tenants × fifty instances creates 250,000 series for one meter before histogram buckets. Establish a label budget during instrumentation review.

9. Micrometer Observation

An Observation represents an operation and provides one lifecycle from which handlers can create metrics, traces, logs, or custom behavior. Low-cardinality key values can become metric tags and span attributes; high-cardinality key values can enrich traces but are intentionally excluded from meters to avoid cardinality explosions.[21][22]

Java 
@Service
public final class PaymentAuthorizer {

    private final ObservationRegistry observations;
    private final PaymentClient client;

    public PaymentAuthorizer(
            ObservationRegistry observations,
            PaymentClient client) {
        this.observations = observations;
        this.client = client;
    }

    public Authorization authorize(
            PaymentCommand command) {

        return Observation
            .createNotStarted(
                "payment.authorize",
                observations)
            .contextualName(
                "authorize payment")
            .lowCardinalityKeyValue(
                "payment.provider",
                command.provider())
            .lowCardinalityKeyValue(
                "payment.currency",
                command.currency())
            .highCardinalityKeyValue(
                "order.id",
                command.orderId()
                    .toString())
            .observe(
                () ->
                    client.authorize(command));
    }
}

Boot registers a meter observation handler and, when tracing is configured, a tracing-aware handler. One completed observation can therefore generate both a timer and a span. Use an ObservationConvention when names and key values must be standardized across several implementations or overridden by application policy.[1][23]

10. Prometheus

Adding micrometer-registry-prometheus causes Boot to create a Prometheus registry and Actuator scrape endpoint. Micrometer’s current registry uses the Prometheus Java client 1.x; the legacy simpleclient registry is available separately. The endpoint emits Prometheus text by default and can negotiate OpenMetrics.[24]

10.2 Recording and alerting rules

YAML 
groups:
  - name: order-service
    interval: 30s
    rules:
      - record:
          job:http_requests:error_ratio_5m
        expr: |
          sum by (job) (
            rate(
              http_server_requests_seconds_count{
                status=~"5.."
              }[5m]
            )
          )
          /
          sum by (job) (
            rate(
              http_server_requests_seconds_count[5m]
            )
          )

      - alert: OrderServiceHighErrorRatio
        expr: |
          job:http_requests:error_ratio_5m
            > 0.02
        for: 10m
        labels:
          severity: page
          service: order-service
        annotations:
          summary: >-
            Order service error ratio exceeds 2%
          runbook_url: >-
            https://runbooks.example.net/order/high-errors

Recording rules precompute expensive or frequently reused expressions. Alerts should identify sustained user-visible symptoms or imminent capacity exhaustion, include ownership and a runbook, and avoid paging on a single instance when the service remains healthy.[27][28]

10.3 Exemplars

Exemplars attach a trace identifier to selected counter or histogram observations, providing a direct jump from a latency bucket to an example trace. Prometheus exposition supports exemplars, and Micrometer’s Prometheus registry can obtain trace context from a tracing integration. Exemplars must remain sampled and bounded; they do not replace the aggregate time series.[24][26]

11. Grafana

Grafana dashboards query a data source such as Prometheus and render panels, tables, heatmaps, annotations, links, and variables. Variables allow one dashboard to switch application, environment, region, instance, or interval without duplicating the dashboard. 12. Distributed tracing

A trace represents one end-to-end operation and contains spans for individual operations. A span has a name, trace and span context, parent, kind, timestamps, attributes, events, links, and status. Span names should describe a low-cardinality class of work—such as GET /orders/{id} or payment authorize—rather than include an individual order ID.[34]

12.1 OpenTelemetry with OTLP

YAML 
management:
  tracing:
    sampling:
      probability: 0.10
    propagation:
      type:
        - w3c

  opentelemetry:
    resource-attributes:
      service.namespace: commerce
      deployment.environment.name: production

    tracing:
      sampler: parent-based-trace-id-ratio
      limits:
        max-attributes: 64
        max-attribute-value-length: 256
        max-events: 64
        max-links: 32

        max-queue-size: 2048
        max-batch-size: 512
        schedule-delay: 5s
        timeout: 10s
        otlp:
          endpoint: http://otel-collector:4318/v1/traces

Boot’s OpenTelemetry starter configures OTLP tracing and uses a parent-based trace-ID-ratio sampler by default. The default Boot trace sampling probability is ten percent. Span limits bound attributes, events, links, and value length before telemetry reaches a backend.[12][35]

12.2 Custom observation and trace

Java 
@Component
public final class PricingObservation {

    private final ObservationRegistry registry;
    private final PricingEngine engine;

    public Price calculate(
            PricingRequest request) {

        return Observation
            .createNotStarted(
                "pricing.calculate",
                registry)
            .contextualName(
                "calculate price")
            .lowCardinalityKeyValue(
                "pricing.channel",
                request.channel())
            .lowCardinalityKeyValue(
                "pricing.currency",
                request.currency())
            .highCardinalityKeyValue(
                "product.id",
                request.productId())
            .observe(
                () ->
                    engine.calculate(request));
    }
}

Boot registers tracing and metric handlers on the Observation registry, so the operation produces a metric and a span. Use Micrometer’s lower-level Tracer API when a span without a metric is required. For framework-integrated application code, Boot recommends Micrometer Observation or Tracing rather than calling the OpenTelemetry API directly.[1][12][36]

12.3 Propagation

Java 
@Service
public final class InventoryClient {

    private final RestClient client;

    public InventoryClient(
            RestClient.Builder builder) {

        this.client = builder
            .baseUrl(
                "http://inventory-service")
            .build();
    }

    Reservation reserve(
            ReservationRequest request) {

        return client.post()
            .uri("/api/reservations")
            .body(request)
            .retrieve()
            .body(Reservation.class);
    }
}

Construct RestClient, RestTemplate, and WebClient from Boot’s auto-configured builders so observation interceptors inject and extract trace context. Directly creating clients bypasses that automatic propagation. OpenTelemetry propagators serialize span context and baggage across process boundaries, commonly using W3C Trace Context.[12][37]

12.4 Asynchronous context

Thread-local trace and MDC state does not automatically cross every executor, callback, reactive publisher, virtual thread, or message boundary. Use Spring-managed instrumented clients and executors, Reactor context, and Micrometer context propagation rather than copying MDC maps manually. In messaging, propagate trace headers through the framework’s observation integration and use span links when work has multiple parents or is processed in batches.[38][39]

12.5 Baggage

Baggage is propagated application metadata, not a general payload channel. It increases every downstream request or message and may appear in telemetry or logs. Use a tiny allowlist of non-sensitive values such as a workflow class or tenant tier; do not propagate credentials, personal data, or arbitrary customer identifiers.[37]

13. OpenTelemetry Collector

The OpenTelemetry Collector is a vendor-neutral service that receives, processes, and exports telemetry. A pipeline explicitly enables receivers, processors, and exporters for traces, metrics, or logs; merely declaring a component does not enable it.[40][41]

      insecure: false

  debug:
    verbosity: basic

service:
  pipelines:
    traces:
      receivers:
        - otlp
      processors:
        - memory_limiter
        - attributes/redact
        - batch
      exporters:
        - otlp/traces

The Collector decouples applications from backend credentials and protocols and can batch, retry, filter, redact, route, tail-sample, or fan out telemetry. It is also another production dependency: size queues, bound memory, monitor dropped spans and exporter failures, use TLS and authentication, and deploy enough capacity to avoid making observability a request-path bottleneck.

14. OpenTelemetry logs

Spring Boot can configure OpenTelemetry’s SdkLoggerProvider and OTLP log exporters, but Boot does not bridge Logback or Log4j2 events into that provider out of the box. A third-party logging bridge is required for direct OTel log export. In container platforms, structured logs to standard output plus a node or sidecar collector remains a simple and failure-isolated model.[1]

Do not duplicate every log Sending the same event through stdout collection and an in-process OTLP bridge doubles volume and can produce inconsistent delivery. Choose one authoritative log export path and test failure behavior.

15. Correlating signals

1 A Prometheus alert identifies a service, route, and time window with elevated errors.
2 A Grafana panel displays latency histograms, dependencies, and deployment annotations.
3 An exemplar opens a representative trace for a slow histogram observation.
4 The trace identifies the slow span and downstream service.
5 Trace and span IDs find structured logs containing error details and business context.
6 A runbook or deployment event explains the change and guides remediation.
YAML 
logging:
  pattern:
    correlation: >-
      [${spring.application.name:},
      %X{traceId:-},
      %X{spanId:-}]
  include-application-name: false

Boot automatically includes trace and span IDs in logs when Micrometer Tracing is configured. Structured formats include MDC fields, making correlation queryable. Preserve the same service name, environment, and deployment version across logs, metrics, traces, dashboards, and alerts.[12][11]

16. Service-level objectives

Telemetry should measure user outcomes rather than only infrastructure. For a synchronous API, useful indicators include successful request ratio, latency distribution, and availability of critical dependencies. For asynchronous systems, include enqueue success, processing delay, oldest message age, completion ratio, and dead-letter volume.

PromQL 
# 99.9% availability objective over 30 days:
# Allowed error budget = 0.1%.

# Fast burn: 14.4x budget over one hour.
(
  sum(rate(
    http_server_requests_seconds_count{
      status=~"5.."
    }[5m]
  ))
  /
  sum(rate(
    http_server_requests_seconds_count[5m]
  ))
) > (14.4 * 0.001)

Multi-window burn-rate alerts are preferable to static CPU or one-minute error thresholds because they relate directly to error-budget consumption. Page on fast user-impacting burn; create tickets for slow burn and capacity trends.

17. Security, privacy, and cost

RiskControls
Actuator exposureNetwork isolation, authentication, endpoint allowlist, separate management port only when health semantics are understood
Log injectionStructured encoders, newline handling, schema validation, untrusted-value escaping
Secrets in telemetryAllowlist fields, request-body exclusion, header redaction, collector processors, automated scanning
Metric cardinalityTag review, meter filters, cardinality dashboards, hard budgets
Trace costHead/tail sampling, span limits, route exclusions, short retention for high-volume data
Backend accessRBAC, tenant isolation, audit, TLS, short-lived credentials
Telemetry outageBounded queues, non-blocking exporters, drop metrics, application independence

Runtime log-level changes can accidentally generate enormous DEBUG or TRACE volume and expose payloads. Apply time-bounded change procedures and reset levels. Heap dumps, environment endpoints, log files, and traces can be more sensitive than the application database because they aggregate data across requests.

18.2 Observation tests

Java 
@Test
void emitsPricingObservation() {
    TestObservationRegistry registry =
            TestObservationRegistry.create();

    PricingObservation component =
            new PricingObservation(
                registry,

    TestObservationRegistryAssert

Micrometer provides observation and tracing test modules for asserting names, tags, spans, and scope behavior. Unit tests should verify metric and span contracts without requiring a backend; integration tests should additionally verify Prometheus scraping, OTLP export, context propagation, and collector failure behavior.[42][43]

18.3 Log contract tests

  • Capture structured output and parse every line as JSON.
  • Assert required fields: timestamp, level, service, event action, trace ID where applicable.
  • Assert credentials, authorization headers, and prohibited fields are absent.
  • Test exception truncation and multi-line payload escaping.
  • Test async-appender overflow behavior under load.

19. Diagnostic playbook

19.1 Meter exists in code but not Prometheus

Confirm the Prometheus registry dependency, endpoint exposure, meter creation path, meter filters, scrape target, endpoint authentication, and the Prometheus target status. Query /actuator/metrics/<name> using the Micrometer name, not its Prometheus-normalized snake-case name.[4]

19.2 Client call lacks a child span

Ensure the client was constructed from Boot’s auto-configured builder, tracing dependencies are present, the request was sampled, propagation headers were not removed, and asynchronous context was preserved.[12]

19.3 Prometheus memory or storage grows rapidly

Inspect series count by metric and label. Remove IDs, paths with values, exception messages, and arbitrary tenant/user dimensions. Histograms multiply every label combination by bucket count.

19.4 Trace IDs disappear in asynchronous logs

The task crossed a context boundary without propagation or logged outside span scope. Use instrumented executors, Reactor context, and Micrometer context propagation; do not rely on inherited thread-local state.

19.5 Traces disappear during load

Inspect SDK exporter queue limits, Collector receiver errors, memory limiter actions, dropped spans, batch size, exporter retries, backend throttling, and network timeouts. Telemetry export must remain bounded and must not block application requests indefinitely.

20. Anti-patterns

20.1 Logging every request body

This creates privacy, cost, performance, and security risk. Log stable event fields and sample or explicitly capture payloads only in controlled diagnostics.

20.2 IDs as metric tags

A time series per order, user, trace, URL, or exception message destroys aggregation efficiency. Put identifiers in logs or sampled traces.

20.3 Publishing client-side percentiles everywhere

Client-computed quantiles generally cannot be aggregated across instances. Prefer histogram buckets when fleet-wide quantiles are required.[20]

20.4 Sampling every production trace indefinitely

Full sampling can overwhelm application exporters, collectors, networks, and storage. Use a measured rate or tail policy and preserve complete coverage only for low-volume critical workflows.

20.5 Dashboards without alert ownership

A dashboard helps only when someone is looking. Define SLO-based alerts, notification routing, severity, runbooks, and escalation.

20.6 Alerts on metrics with no response

Every page should imply a user impact or imminent risk and a specific operator action. Informational trends belong in dashboards or tickets.

20.7 Instrumenting the same operation twice

Combining a Java agent, Spring observations, manual spans, and library instrumentation can produce duplicate nested spans. Establish one instrumentation owner for each operation.

21. Reference architecture

1 Spring Boot writes ECS JSON logs to standard output through Logback or Log4j2.
2 A platform log agent enriches container metadata and forwards logs to a searchable log backend.
3 Micrometer records JVM, HTTP, database, executor, cache, and business metrics.
4 Prometheus scrapes /actuator/prometheus, evaluates recording and alert rules, and stores time series.
5 Micrometer Observation creates metrics and OpenTelemetry spans for application operations.
6 Boot exports spans via OTLP to an OpenTelemetry Collector, which batches, redacts, and exports to a trace backend.
7 Grafana dashboards query Prometheus and link exemplars to traces and trace IDs to logs.
8 Grafana or Alertmanager routes SLO and capacity alerts to the owning team and runbook.

22. Expert practices

  • Define telemetry schemas and ownership as part of API and domain design.
  • Use SLF4J in application code and exactly one runtime provider.
  • Prefer structured JSON logging in production and concise text locally.
  • Use stable event names and typed key-value fields rather than parsing messages.
  • Keep secrets, personal data, and high-volume payloads out of telemetry.
  • Use Micrometer for Spring application metrics and Observation for operations that need both metrics and traces.
  • Establish a metric-label cardinality budget and review every new dimension.
  • Use Prometheus histograms for aggregatable latency distributions.
  • Build Grafana dashboards around user impact, saturation, dependencies, and recent changes.
  • Use Boot-configured HTTP clients and executors so context propagation remains intact.
  • Sample traces intentionally and monitor exporter/collector drops.
  • Correlate logs, metrics, and traces through consistent service, environment, version, trace, and workflow fields.
  • Provision dashboards, rules, and collectors as version-controlled code.
  • Test observability contracts and failure modes before production incidents require them.

23. Summary

  • Spring observability combines logs, Micrometer metrics, and Micrometer/OpenTelemetry traces.
  • SLF4J is the facade; Logback and Log4j2 are runtime implementations.
  • Spring Boot uses Logback by default and can switch to Log4j2 through its starter.
  • Boot supports ECS, GELF, and Logstash structured JSON logging with MDC and SLF4J key-value fields.
  • Micrometer supplies dimensional counters, gauges, timers, summaries, and observations.
  • Low-cardinality values can become metric tags; high-cardinality identifiers belong in traces or logs.
  • Prometheus scrapes the Actuator Prometheus endpoint and computes rates, ratios, and histogram quantiles with PromQL.
  • Grafana builds dashboards, variables, links, annotations, and alerts over telemetry backends.
  • Micrometer Observation can produce both metrics and spans from one operation lifecycle.
  • Boot’s OpenTelemetry starter exports traces through OTLP and includes trace/span correlation in logs.
  • Auto-configured RestClient, RestTemplate, and WebClient builders preserve trace propagation.
  • The OpenTelemetry Collector decouples reception, processing, redaction, batching, and export.
  • Telemetry must be bounded, secured, tested, and tied to service-level objectives.

During an incident, begin with the user-visible symptom, quantify it with metrics, locate representative operations with traces, and explain those operations with structured logs. When that workflow fails, inspect the telemetry pipeline itself: instrumentation names, label cardinality, sampling, context propagation, exporter queues, collector processors, backend ingestion, dashboard queries, and alert rules. Observability is not a collection of agents; it is a designed chain of evidence.
