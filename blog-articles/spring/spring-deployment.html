Spring Boot Operations

Spring Deployment

A technical guide to embedded Tomcat and Jetty, Undertow compatibility, traditional WAR deployment, executable JARs, Docker and OCI images, Kubernetes workloads, probes, rolling updates, external configuration, and graceful shutdown.

Spring Boot 4.1.0 Servlet 6.1 / Jakarta EE 11 baseline Tomcat, Jetty, Docker, Kubernetes Long-form technical article Vancouver references
Abstract. Spring deployment is a set of ownership decisions. With an executable JAR, the application owns the HTTP server and its lifecycle. With a traditional WAR, an external Servlet container owns connectors, deployment, class loading, and process lifecycle. A Docker or OCI image adds an immutable filesystem and container process boundary; Kubernetes adds reconciliation, Pods, Services, probes, rolling updates, resource scheduling, and termination semantics. Spring Boot supports embedded Tomcat and Jetty in its current 4.x generation. Undertow was supported through the Boot 3.5 line but was removed from Boot 4 because the latter requires Servlet 6.1. Correct deployment therefore depends on choosing a compatible packaging model, keeping configuration and secrets external, forwarding proxy metadata safely, aligning graceful-shutdown timeouts, exposing low-cost availability probes, setting resource requests and limits, and validating the exact packaged artifact under production-like conditions.

Spring Boot applications can be packaged as executable JARs or WARs, run with embedded servers, deployed to compatible standalone Servlet containers, or converted to Docker-compatible images with Dockerfiles or Cloud Native Buildpacks. Spring Boot 4.1’s Servlet stack supports embedded Tomcat and Jetty; Tomcat is the default server brought in by the Spring MVC starter.[1][2][3]

2.1 Externalized configuration

Shell

export SPRING_DATASOURCE_URL=\
jdbc:postgresql://database.internal/orders
export SPRING_DATASOURCE_USERNAME=orders_app

java -jar orders.jar

Spring Boot’s environment supports property files, environment variables, system properties, command-line arguments, configuration trees, and imported configuration. Deployment systems should supply secrets outside source control and avoid printing resolved credentials in logs or diagnostic endpoints.[6]

3. Embedded Servlet containers

In an embedded deployment, ServletWebServerApplicationContext discovers a ServletWebServerFactory, creates the server, applies Servlet initializers, refreshes the application context, and starts the HTTP server. Boot provides server starters and common configuration properties so application packaging, server version, and server lifecycle can be managed together.[2][3]

3.1 Benefits

  • One process and versioned artifact contains the application and tested server libraries.
  • Local, test, container, and production startup use the same entry point.
  • Server configuration can be externalized through Boot properties and customizers.
  • Rolling replacement is usually simpler than mutating applications inside a shared container.
  • Application and server metrics, lifecycle, and graceful shutdown share one context.

3.2 Costs

  • Each application process carries its own server and connection/thread infrastructure.
  • Server patching requires rebuilding and redeploying the application artifact.
  • Operations teams cannot rely on one centrally configured container instance for all applications.
  • JSP support is constrained for executable archives and is not available from executable JAR packaging.[2]

4. Embedded Tomcat

Spring Boot’s current Spring MVC starter uses Tomcat by default. Tomcat is therefore the lowest-friction Servlet deployment choice for Boot 4.1. The managed Tomcat generation implements the Servlet baseline required by Boot; applications should let Boot manage the tested server version rather than overriding Tomcat artifacts independently.[3][7]

XML 
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>
    spring-boot-starter-webmvc
  </artifactId>
</dependency>
YAML 
server:
  port: 8080
  max-http-request-header-size: 16KB
  tomcat:
    max-connections: 8192
    accept-count: 100
    connection-timeout: 5s
    keep-alive-timeout: 30s
    max-keep-alive-requests: 100
    threads:
      max: 200
      min-spare: 20
      max-queue-capacity: 500
    accesslog:
      enabled: false

Tomcat connector, worker-thread, request-limit, resource-cache, and access-log settings are exposed through Boot’s application properties. These limits are an admission policy: raising threads and connections can increase pressure on JDBC pools and downstream services rather than increase sustainable throughput. Virtual-thread mode changes which traditional thread-pool properties are effective.[4]

4.1 Programmatic customization

Java 
@Configuration(proxyBeanMethods = false)
public class TomcatConfiguration {

    @Bean
    WebServerFactoryCustomizer<
            TomcatServletWebServerFactory>
            tomcatCustomizer() {

        return factory ->
            factory.addConnectorCustomizers(
                connector -> {
                    connector.setProperty(
                        "maxParameterCount",
                        "1000");
                    connector.setProperty(
                        "maxPartCount",
                        "50");
                });
    }
}

Prefer Boot properties first. Use a server-factory customizer for a server capability that has no property or when configuration must be generated programmatically. Auto-configured customizers still apply to a user-supplied factory, so replacing the factory itself requires careful integration testing.[3]

5. Embedded Jetty

Jetty is the supported alternative embedded Servlet server in Spring Boot 4.1. Switching servers means excluding the default Tomcat starter and adding the Jetty starter. The rest of the Spring MVC programming model is unchanged, although connector, threading, HTTP protocol, and deployment details remain server-specific.[3]

XML 
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>
    spring-boot-starter-webmvc
  </artifactId>
  <exclusions>
    <exclusion>
      <groupId>org.springframework.boot</groupId>
      <artifactId>
        spring-boot-starter-tomcat
      </artifactId>
    </exclusion>
  </exclusions>
</dependency>

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>
    spring-boot-starter-jetty
  </artifactId>
</dependency>
YAML 
server:
  port: 8080
  jetty:
    max-http-form-post-size: 2MB
    max-http-response-header-size: 16KB
    threads:
      min: 8
      max: 200
      idle-timeout: 60s
      max-queue-capacity: 500

Boot exposes Jetty acceptor, selector, queue, and worker-thread configuration. Standalone Jetty 12.1 separates JETTY_HOME from JETTY_BASE and supports deployment environments including Jakarta EE 11. Embedded Boot applications use Jetty libraries programmatically rather than the standalone server’s deploy scanner and module layout.[4][8][9]

6. Undertow

Spring Boot 4 does not support embedded Undertow Boot 4 requires Servlet 6.1. Undertow was not compatible with that baseline when Boot 4 was released, so Boot removed the Undertow starter and embedded-server integration. Do not force a Boot 3 Undertow starter into Boot 4.

Spring Boot 3.5 still supports embedded Tomcat, Jetty, and Undertow and remains a separately supported release line. Existing Undertow applications can remain on a supported Boot 3.5 patch while planning migration, subject to the organization’s support policy. New Boot 4 deployments should use Tomcat or Jetty unless Undertow is integrated independently outside Boot’s supported embedded-server model.[10][11]

XML 
<!-- Spring Boot 3.5.x only -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
  <exclusions>
    <exclusion>
      <groupId>org.springframework.boot</groupId>
      <artifactId>
        spring-boot-starter-tomcat
      </artifactId>
    </exclusion>
  </exclusions>
</dependency>

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>
    spring-boot-starter-undertow
  </artifactId>
</dependency>

Undertow itself provides low-level handler and Servlet deployment APIs. A direct Undertow deployment uses DeploymentInfo, a DeploymentManager, and an Undertow handler chain; that is a custom integration and is not equivalent to Boot 4 auto-configuration. Boot 3.5’s Undertow integration also documented that Undertow does not support JSPs.[11][12]

7. Executable JARs

The Spring Boot Maven and Gradle plugins repackage an application JAR so it can be launched with java -jar. Application classes are stored under BOOT-INF/classes, dependencies under BOOT-INF/lib, and Boot loader classes provide nested-JAR loading. The plugin manages the manifest’s launcher and application start-class entries.[13][14]

Text 
orders.jar
├── META-INF/
│   └── MANIFEST.MF
├── org/springframework/boot/loader/
└── BOOT-INF/
    ├── classes/
    │   └── com/example/orders/...
    ├── lib/
    │   ├── spring-*.jar
    │   ├── jackson-*.jar
    │   └── ...
    └── classpath.idx
Shell 
./mvnw clean package

java \
  -Duser.timezone=UTC \
  -XX:+ExitOnOutOfMemoryError \
  -jar target/orders-1.0.0.jar \
  --spring.profiles.active=production

7.1 Extracted production layout

Loading classes from nested JARs has a small startup cost. Boot’s tools JAR mode can extract an executable archive into an efficient layout, leaving an application JAR whose manifest references libraries in a separate directory. Boot recommends the extracted layout for efficient production startup and compatibility with AOT cache or CDS workflows.[15]

Shell 
java \
  -Djarmode=tools \
  -jar orders.jar \
  extract \
  --destination /opt/orders

java -jar /opt/orders/orders.jar

7.2 Process supervision

The Java process should be managed by the deployment platform: systemd, a container runtime, Kubernetes, or another supervisor. The supervisor should restart crashed processes according to policy, capture standard output and error, deliver SIGTERM, impose resource limits, and avoid wrapping Java in a shell that fails to forward signals.

8. Traditional WAR deployment

WAR deployment is appropriate when an external Servlet container must own ports, connectors, TLS, JNDI, shared operational policy, and application deployment. A Spring Boot WAR uses SpringBootServletInitializer so the external container can create the application context through the Servlet initialization contract.[16]

Java 
@SpringBootApplication
public class OrdersApplication
        extends SpringBootServletInitializer {

    @Override
    protected SpringApplicationBuilder configure(
            SpringApplicationBuilder application) {

        return application.sources(
            OrdersApplication.class);
    }

    public static void main(String[] arguments) {
        SpringApplication.run(
            OrdersApplication.class,
            arguments);
    }
}
XML 
<packaging>war</packaging>

<dependencies>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>
      spring-boot-starter-webmvc
    </artifactId>
  </dependency>

  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>
      spring-boot-starter-tomcat
    </artifactId>
    <scope>provided</scope>
  </dependency>
</dependencies>

<build>
  <plugins>
    <plugin>
      <groupId>org.springframework.boot</groupId>
      <artifactId>
        spring-boot-maven-plugin
      </artifactId>
    </plugin>
  </plugins>
</build>

Marking the embedded container as provided prevents its runtime libraries from conflicting with the external container. Boot’s executable WAR format places provided dependencies under WEB-INF/lib-provided, so the same WAR can normally be deployed to a container or run with java -jar.[16][13][14]

8.1 Container compatibility

Spring Boot 4 uses a Jakarta EE 11 and Servlet 6.1 baseline and recommends deployment only to a compatible Servlet 6.1 container. Tomcat 11 and the appropriate Jetty 12.1 Jakarta EE 11 environment are examples of current compatible container generations. Older javax.servlet-based containers are not binary-compatible with Boot 4’s jakarta.servlet APIs.[10][7][8]

8.2 Context path and container ownership

Standalone containers usually derive a context path from the WAR name—for example, orders.war becomes /orders and ROOT.war becomes /—unless server-specific deployment configuration overrides it. Jetty and Tomcat provide their own deployment descriptors, virtual-host, JNDI, hot-deployment, and security controls.[9][17]

Do not apply embedded-server assumptions to a WAR In external deployment, the container—not Boot—owns connector ports, server thread pools, deployment scanning, TLS listeners, and some logging behavior. Test the WAR in the exact target container version and configuration.

9. Docker and OCI images

Spring Boot supports Docker-compatible images through Dockerfiles and Cloud Native Buildpacks. A container image should contain the application and runtime, not environment secrets or mutable operational state. Containers should run one foreground Java process, write logs to standard streams, and persist durable data outside the container filesystem.[18]

9.1 Minimal Dockerfile

Dockerfile 
FROM eclipse-temurin:25-jre

WORKDIR /application

COPY target/orders-1.0.0.jar application.jar

USER 10001:10001

EXPOSE 8080

ENTRYPOINT ["java", "-XX:+ExitOnOutOfMemoryError", "-jar", "application.jar"]

The JSON-form ENTRYPOINT launches Java as the container’s main process instead of introducing an unnecessary shell, which helps the runtime deliver termination signals correctly. A numeric non-root user reduces privileges, but the selected base image and writable directories must be tested.

9.2 Layered optimized Dockerfile

Copying one large executable JAR into one image layer invalidates that layer whenever application code changes. Boot’s layer index separates released dependencies, Boot loader classes, snapshot dependencies, and application content according to expected change frequency. The tools JAR mode extracts those layers into an efficient runtime layout.[19][20]

Dockerfile 
FROM bellsoft/liberica-openjre-debian:25-cds AS builder

WORKDIR /builder

ARG JAR_FILE=target/*.jar
COPY ${JAR_FILE} application.jar

RUN java \
    -Djarmode=tools \
    -jar application.jar \
    extract \
    --layers \
    --destination extracted

FROM bellsoft/liberica-openjre-debian:25-cds

WORKDIR /application

COPY --from=builder \
  /builder/extracted/dependencies/ ./
COPY --from=builder \
  /builder/extracted/spring-boot-loader/ ./
COPY --from=builder \
  /builder/extracted/snapshot-dependencies/ ./
COPY --from=builder \
  /builder/extracted/application/ ./

USER 10001:10001

EXPOSE 8080

ENTRYPOINT ["java", "-XX:+ExitOnOutOfMemoryError", "-jar", "application.jar"]

Boot’s Maven and Gradle plugins create OCI images through Cloud Native Buildpacks. Buildpack images use application layer metadata, build and run as non-root users, and require access to a Docker-compatible daemon for the plugin workflows. Buildpacks reduce custom Dockerfile maintenance while retaining configurable builders, run images, environment, platform, cache, tags, and publication settings.[21][22][23]

9.5 Image security

  • Pin and regularly rebuild base images to receive OS and JRE security updates.
  • Run as a non-root user and drop Linux capabilities unless required.
  • Use a read-only root filesystem where compatible; mount bounded writable volumes for /tmp or generated files.
  • Do not copy Maven settings, source-control credentials, cloud credentials, or private keys into image layers.
  • Generate and retain an SBOM, scan dependencies and final layers, and sign or attest promoted images.
  • Promote an immutable digest between environments rather than rebuilding from a mutable tag.

10. Kubernetes deployment

Kubernetes runs containers inside Pods, while higher-level workload resources manage replacement and desired replica counts. A Deployment is the usual controller for a stateless application whose replicas are interchangeable. A Service supplies a stable network endpoint over a changing set of ready Pods.[24][25]

10.1 Spring availability endpoints

With Actuator, Boot exposes liveness and readiness health groups at /actuator/health/liveness and /actuator/health/readiness. Setting management.endpoint.health.probes.add-additional-paths=true also exposes /livez and /readyz on the main application port, avoiding a false-positive probe when a separately managed port remains healthy but the main connector cannot serve traffic.[26]

YAML 
management:
  endpoint:
    health:
      probes:
        enabled: true
        add-additional-paths: true

spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s

A Deployment’s rolling update gradually scales old ReplicaSets down and new ones up; maxUnavailable and maxSurge bound that transition. The example Secret is not production secret management Kubernetes Secrets are intended for sensitive data, but their values are not automatically encrypted in etcd by default. Use encryption at rest, strict RBAC, namespace isolation, external secret-management integration, rotation, and avoid committing secret manifests.[29]

11. Liveness, readiness, and startup probes

ProbeQuestionFailure action
StartupHas this process completed startup?Kubelet restarts the container after threshold; liveness/readiness wait until startup succeeds
LivenessIs the process irrecoverably broken?Kubelet restarts the container
ReadinessShould this instance receive traffic now?Pod remains running but is removed from matching Service endpoints

Kubernetes explicitly warns that incorrect liveness checks can create cascading failures by restarting healthy-but-overloaded instances and shifting more traffic to the remaining replicas. Boot therefore keeps liveness centered on internal application state and does not automatically add external dependencies to readiness. A shared database outage should not cause every Pod to fail liveness and restart simultaneously.[30][26]

11.1 Probe design rules

  • Use a startup probe when startup can exceed the liveness failure window.
  • Keep liveness inexpensive and independent of shared external systems.
  • Add external checks to readiness only when inability to reach that system truly makes the replica unable to serve useful traffic.
  • Set timeouts and thresholds from observed startup and failure behavior, not copied defaults.
  • Probe the main application connector or expose additional probe paths there.
  • Do not require authentication, remote calls, or expensive database queries for kubelet probes.

12. Graceful shutdown

Graceful shutdown is enabled by default in current Boot for embedded Tomcat, Jetty, and Reactor Netty. During application-context closure, the server stops accepting new requests and allows in-flight requests to complete within spring.lifecycle.timeout-per-shutdown-phase. The exact network behavior is server-specific.[31]

1 Kubernetes marks the Pod for termination and terminating endpoints become not ready for normal Service traffic.
2 The container runtime delivers the stop signal—normally SIGTERM—to the main process.
3 Spring changes readiness to refusing traffic and begins graceful server shutdown.
4 In-flight HTTP requests and lifecycle components receive their configured shutdown window.
5 If the Pod still runs when the Kubernetes grace period expires, the runtime sends SIGKILL.

Kubernetes gives Pods a termination grace period, 30 seconds by default, and executes a configured preStop hook before sending the stop signal. Boot’s shutdown timeout must fit inside the Pod grace period with margin for any hook, endpoint propagation, and process exit. A shell-form container entry point can prevent Java from receiving the signal correctly.[32]

YAML 
spec:
  template:
    spec:
      terminationGracePeriodSeconds: 45
      containers:
        - name: orders
          lifecycle:
            preStop:
              exec:
                command:
                  - /bin/sh
                  - -c
                  - sleep 5

A short preStop delay can accommodate infrastructure that takes time to observe endpoint removal, but it consumes the same grace period and requires a shell in the image. Modern Kubernetes marks terminating endpoints not ready, so a blind sleep is not universally required. Prefer platform-specific traffic-drain mechanisms and verify behavior with the actual load balancer.[32]

13. Networking, proxies, and TLS

Kubernetes Services expose a changing set of Pods through a stable endpoint. For public HTTP routing, a Gateway API implementation or Ingress controller terminates or forwards traffic to a Service. The Kubernetes project recommends Gateway over the frozen Ingress API for new capabilities, although Ingress remains stable and supported.[25][33]

13.1 Forwarded headers

When TLS terminates at a reverse proxy, the application may see internal HTTP, host, and port values unless the proxy supplies Forwarded or X-Forwarded-* metadata and Boot is configured to process it. Trust only headers inserted by controlled infrastructure; an internet client must not be allowed to forge its apparent scheme, host, or source address.[5][34]

13.2 TLS ownership

PatternTLS terminates atUse
Embedded TLSTomcat or Jetty inside the applicationDirect exposure or end-to-end encryption
Gateway/load balancer terminationCluster edgeCentral certificate management and routing
Re-encryptionEdge and applicationEncrypted cluster traffic with separate certificates
Service mesh mTLSSidecar or node data planeWorkload identity and transparent service encryption

Certificate storage, rotation, client authentication, cipher policy, and forwarded-header trust must match the chosen boundary. Do not configure both edge and application redirects without testing for loops.

14. Kubernetes resource and JVM sizing

Kubernetes schedules from resource requests and enforces resource limits. The Java process also consumes heap, metaspace, code cache, thread stacks, direct buffers, GC structures, and native-library memory. Therefore -Xmx must remain below the Pod memory limit with native headroom; allocating the entire limit to heap invites an operating-system-level out-of-memory kill.[28]

Text 
container memory limit
  = Java heap
  + metaspace
  + code cache
  + thread stacks
  + direct/native buffers
  + GC and JVM native structures
  + safety margin

CPU limits can throttle a process even when node CPU is available. Requests should reflect sustained scheduling need; limits and JVM processor detection should be tested under realistic concurrency. Autoscaling signals should be based on a resource that tracks load before latency collapses, such as CPU, queue depth, or application-specific concurrency—not only a late-stage error rate.

15. Rolling updates and release safety

Any change to a Deployment’s Pod template triggers a rollout. Kubernetes creates a new ReplicaSet and replaces old Pods according to the update strategy. Readiness prevents traffic from reaching a new Pod until it can serve requests, while graceful termination drains old Pods.[27][35]

Shell 
kubectl apply -f k8s/orders.yaml

kubectl rollout status \
  deployment/orders \
  --timeout=10m

kubectl rollout history deployment/orders

kubectl rollout undo deployment/orders

15.1 Backward-compatible deployments

  • Apply database migrations that remain compatible with both old and new application replicas.
  • Use expand-and-contract schema changes rather than dropping a column before old Pods stop using it.
  • Version external message and API contracts or make consumers tolerant of additive changes.
  • Do not reuse an image tag for different bytes; deploy immutable digests.
  • Set rollout deadlines and alert on stalled, crash-looping, or never-ready replicas.
  • Use a PodDisruptionBudget for voluntary disruptions when application availability requires a minimum replica count.

17. Deployment testing

17.1 Test the packaged archive

Shell 
./mvnw clean verify

java -jar target/orders.jar &
PID=$!

for i in $(seq 1 60); do
  curl --fail \
    http://localhost:8080/actuator/health \
    && break
  sleep 1
done

kill -TERM "$PID"
wait "$PID"

17.3 Test termination under load

Send long and short requests while issuing SIGTERM or deleting a Pod. Verify that readiness changes, new traffic stops, in-flight requests finish within the configured grace period, executors and consumers stop accepting work, and the process exits before SIGKILL.

New independent Spring serviceExecutable JAR with embedded Tomcat, packaged as an OCI image
Jetty-specific operational standardEmbedded Jetty or compatible external Jetty WAR
Existing Undertow serviceSupported Boot 3.5 patch while migrating; Boot 4 uses Tomcat or Jetty
Shared enterprise Servlet containerExecutable WAR deployed to a Servlet 6.1-compatible container
Docker without custom image maintenanceSpring Boot Cloud Native Buildpacks
Fine-grained image controlLayered multi-stage Dockerfile
Replicated stateless workloadKubernetes Deployment plus ClusterIP Service and Gateway/Ingress
Stateful identity or stable storageEvaluate StatefulSet and persistent-volume semantics rather than forcing Deployment

19. Deployment anti-patterns

19.1 Copying changed files into a running container

Containers and Kubernetes Pods are replaceable deployment units. Build and promote a new image rather than mutating live files.

19.2 Deploying latest

Mutable tags make rollback, provenance, and incident analysis ambiguous. Use a version or commit tag and promote by digest.

19.3 Putting the shared database in liveness

A database outage can restart every application replica and amplify the incident. Keep liveness internal; evaluate database availability separately for readiness or request-level resilience.[26]

19.4 Deploying Boot 4 to an old Servlet container

Boot 4 requires the Jakarta Servlet 6.1 generation. A javax.servlet container or earlier Jakarta baseline is incompatible.[10]

19.5 Forcing Undertow dependencies into Boot 4

Boot removed its Undertow starter and integration. Use a supported server or remain temporarily on the supported Boot 3.5 line while migrating.[10][11]

19.6 Baking secrets into the image

Deleted Dockerfile lines and later layers do not reliably remove secrets from prior image layers. Supply credentials at runtime and rotate them independently.

19.7 Giving Spring longer than Kubernetes

When Spring’s shutdown phase exceeds the Pod termination grace period, Kubernetes kills the process before draining completes. Budget the complete termination path.

20. Summary

  • Executable JARs let the Spring Boot application own its tested embedded-server version and lifecycle.
  • Spring Boot 4.1 supports embedded Tomcat and Jetty; Tomcat is the default Spring MVC server.
  • Undertow support remains in Boot 3.5 but was removed from Boot 4 because Boot 4 requires Servlet 6.1.
  • Traditional WAR deployment requires SpringBootServletInitializer, WAR packaging, and a provided embedded-container dependency.
  • Boot 4 WARs require a compatible Servlet 6.1/Jakarta EE 11 container.
  • Executable JARs store application classes and nested dependencies under BOOT-INF; executable WARs use WEB-INF and lib-provided.
  • Boot’s tools mode can extract archives into a faster, layer-friendly production layout.
  • Docker images should use immutable artifacts, non-root execution, explicit signals, external configuration, and layered caching.
  • Cloud Native Buildpacks create non-root OCI images directly through Boot’s Maven and Gradle plugins.
  • Kubernetes Deployments reconcile stateless replicas, Services provide stable endpoints, and rolling updates gradually replace Pods.
  • Startup, liveness, and readiness probes answer different questions and must not be conflated.
  • Boot exposes Kubernetes availability groups and can place /livez and /readyz on the main server port.
  • Graceful shutdown requires signal delivery, readiness removal, bounded Spring shutdown, and a longer Kubernetes termination grace period.
  • Resource requests guide scheduling; limits constrain runtime usage; JVM heap must leave native-memory headroom.

When a deployment fails, identify which layer owns the failing contract: Did the archive contain the correct server and launcher? Did the external container satisfy the Servlet baseline? Did the image run Java as PID 1 with the required files and user permissions? Did Kubernetes schedule the requested resources, expose the correct port, and receive a successful readiness response? Did termination deliver SIGTERM and provide enough drain time? Following ownership across those boundaries turns deployment from environment-specific guesswork into a testable system.
