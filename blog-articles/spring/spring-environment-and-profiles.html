Spring Framework Core Container

Spring Environment and Profiles

An expert guide to the Environment abstraction, property-source precedence, properties and YAML files, active and default profiles, externalized configuration, typed binding, programmatic customization, testing, and operational diagnostics.

Core target: Spring Framework 7.0.8 Boot supplement: current 4.x conventions Long-form technical article Vancouver references
Abstract. Spring’s environment model has two orthogonal responsibilities: property resolution and profile evaluation. Properties are not stored in one map; they are resolved through an ordered chain of named PropertySource objects. Profiles are not arbitrary runtime flags; they are predicates evaluated during container bootstrap to decide whether bean definitions and configuration documents are eligible. Spring Framework supplies the core abstractions, mutable source chain, placeholder resolution, profile expressions, properties-file integration, and YAML factories. Spring Boot adds an opinionated configuration-data pipeline that discovers application.properties and YAML files, processes profile variants and imports, normalizes environment variables, exposes structured binding, and defines a detailed override order. This article develops both layers and shows how to make configuration deterministic, typed, testable, observable, and secure.

Spring Framework 7.0.8 is the current stable framework API used for the core examples. Spring Boot 4.1.0 is the current project release as of 31 July 2026; Boot 4 requires Java 17 or later and builds on Spring Framework 7.x. The Boot-specific sections describe the current externalized-configuration model while keeping the core Environment concepts independent of Boot.[1][2][3]

1. Mental model: one environment, two axes

The Environment interface models the context in which an application runs. It exposes two distinct concerns: named profiles and property resolution. A profile is a logical grouping condition for bean definitions. A property is a value resolved by name from one or more underlying sources. Conflating the two leads to profile proliferation—using profiles for every feature flag or scalar setting—and to configuration logic hidden in bean-registration conditions.[4]

Profiles answerShould this definition or configuration document participate in this deployment?
Properties answerWhat value should this application use for a named setting?
Property sources answerWhich location supplied the winning value, and what can override it?
Binding answersHow are external scalar values converted into a validated application configuration model?

The key implementation model is an ordered search:

1 A caller requests a key, such as client.timeout.
2 The property resolver visits PropertySource objects in precedence order.
3 The first source containing the key wins.
4 The resolver converts the raw value to the requested target type when possible.
5 Placeholders inside values may be resolved recursively according to resolver policy.
6 Bean definitions and profile conditions see the environment during container bootstrap.
Configuration is a precedence graph, not a bag of values A setting is fully understood only when its key, winning value, source identity, override rules, target type, validation rules, and bootstrap phase are known.

2. Core API structure

2.1 Environment and PropertyResolver

Environment extends PropertyResolver. Its property methods include presence checks, nullable and defaulted lookup, typed lookup, required-property lookup, and placeholder resolution. Its profile methods expose active and default profile names and evaluate profile predicates. Application beans can inject the environment directly, although Spring recommends that ordinary application beans usually receive resolved values rather than becoming coupled to the environment API.[4]

Java 
@Configuration(proxyBeanMethods = false)
class ClientConfiguration {

    @Bean
    RemoteClient remoteClient(Environment environment) {
        String endpointText =
                environment.getRequiredProperty(
                        "client.endpoint");

        int timeoutMillis = environment.getProperty(
                "client.timeout-ms",
                Integer.class,
                5_000);

        return new RemoteClient(
                URI.create(endpointText),
                Duration.ofMillis(timeoutMillis));
    }
}

Direct environment access is useful when configuration is dynamic in shape, when a framework component must inspect profiles, or when factory logic needs conditional property access. For stable application configuration, constructor-injected typed objects generally provide a clearer contract than string keys distributed throughout the codebase.

2.2 ConfigurableEnvironment

ConfigurableEnvironment adds mutation: setting active and default profiles, adding an active profile, manipulating the ordered property-source chain, setting required properties, customizing conversion, and merging a parent environment. When an environment belongs to an application context, mutations that must influence bean registration or placeholder resolution need to occur before refresh().[5]

Java 
try (AnnotationConfigApplicationContext context =
         new AnnotationConfigApplicationContext()) {

    ConfigurableEnvironment environment =
            context.getEnvironment();

    environment.setActiveProfiles("production");
    environment.setDefaultProfiles("local");

    environment.getPropertySources().addFirst(
            new MapPropertySource(
                    "bootstrapOverrides",
                    Map.of(
                        "client.timeout-ms", "2000",
                        "feature.audit", "true")));

    environment.setRequiredProperties(
            "client.endpoint",
            "client.timeout-ms");

    context.register(ApplicationConfiguration.class);
    context.refresh();
}

Required properties are validated when the configurable environment’s required-property validation is invoked during context preparation. Programmatic setup before refresh is deterministic and appropriate for launchers, tests, embedded containers, and framework integration.[5]

2.3 PropertySource<T>

A PropertySource wraps any underlying object capable of supplying name/value pairs, such as a Map, Properties, servlet context, servlet configuration, or JNDI source. Sources are aggregated in PropertySources and searched by a property resolver. A source’s identity is its name, not the content of the wrapped object; source names therefore matter for replacement, relative insertion, diagnostics, and duplicate suppression.[6]

ImplementationBacking dataTypical use
MapPropertySourceMap<String,Object>Programmatic overrides and test fixtures
PropertiesPropertySourcePropertiesTraditional properties resources
SystemEnvironmentPropertySourceProcess environment mapEnvironment variables with shell-friendly name variants
ResourcePropertySourceProperties loaded from a Spring ResourceProgrammatic file-backed sources
CompositePropertySourceMultiple nested sourcesLogical aggregation while preserving internal precedence

2.4 MutablePropertySources and precedence

MutablePropertySources is the default ordered container. addFirst() gives a source highest precedence, addLast() gives it lowest precedence, and addBefore()/addAfter() position a source relative to another named source. Resolution stops at the first source that contains the requested key.[7]

Java 
ConfigurableEnvironment environment =
        new StandardEnvironment();

MutablePropertySources sources =
        environment.getPropertySources();

sources.addFirst(new MapPropertySource(
        "commandLikeOverrides",
        Map.of("service.mode", "safe")));

sources.addAfter(
        StandardEnvironment.SYSTEM_PROPERTIES_PROPERTY_SOURCE_NAME,
        new ResourcePropertySource(
                "operatorFile",
                "file:/etc/example/operator.properties"));

String mode = environment.getProperty("service.mode");
// "safe" because the first source wins.
Null does not mean “delete a lower value” Property-source semantics are lookup-oriented. Model deliberate removal or disablement with an explicit domain value, a dedicated enable flag, or source-chain manipulation rather than assuming a null value will erase a lower-precedence setting.

3. Standard environment implementations

3.1 StandardEnvironment

A non-web StandardEnvironment starts with two property sources in this order: JVM system properties, followed by process environment variables. A system property therefore overrides an environment variable with the same logical key. Both sources can be removed, replaced, or repositioned through the mutable source chain.[8]

Shell 
export CLIENT_TIMEOUT_MS=10000
java -Dclient.timeout-ms=2000 -jar application.jar

In a plain Spring Framework StandardEnvironment, the system property wins because systemProperties precedes systemEnvironment.[8]

3.2 Environment-variable name translation

SystemEnvironmentPropertySource compensates for shells that do not permit dots or hyphens in variable names. A lookup such as foo.bar can match forms including foo_bar and FOO_BAR, with analogous handling for hyphens. This is why spring.profiles.active can be supplied conventionally as SPRING_PROFILES_ACTIVE.[9]

3.3 StandardServletEnvironment

Servlet-based application contexts use StandardServletEnvironment. In addition to the standard JVM and OS sources, it contributes servlet configuration parameters, servlet context parameters, and JNDI-backed sources. Their participation is still governed by the same ordered PropertySources model.[10]

3.4 Parent and child environments

A child configurable environment can merge a parent’s active profiles, default profiles, and property sources. Child sources with the same name are retained and identically named parent sources are discarded; duplicate profile names are filtered. The merge is a snapshot—later parent changes are not automatically reflected in the child.[5]

4. Properties files

Traditional Java properties files are a flat key/value format. Hierarchy is represented conventionally with dotted names and list indexes. Spring can load these resources declaratively with @PropertySource, programmatically as a ResourcePropertySource, through placeholder configurers, or—under Spring Boot—as configuration data.[11]

Properties 
client.endpoint=https://api.example.net
client.timeout-ms=3000
client.pool.max-size=32
client.pool.validation-query=SELECT 1
features.audit=true
regions[0]=us-east
regions[1]=eu-central

4.1 @PropertySource

@PropertySource adds one or more resource-backed property sources to the enclosing application environment. It is repeatable, supports resource-location placeholders, can ignore missing resources when explicitly configured, and can delegate parsing to a custom PropertySourceFactory. Since Spring Framework 6.1, resource-location wildcards are supported. Ordering among annotations discovered through component scanning can be difficult to predict, so programmatic insertion is preferable when precise override semantics are essential.[11]

Java 
@Configuration(proxyBeanMethods = false)
@PropertySource(
    name = "applicationDefaults",
    value = "classpath:config/application.properties")
@PropertySource(
    name = "operatorOverrides",
    value = "file:${example.config.dir:"
          + "./config}/override.properties",
    ignoreResourceNotFound = true)
class PropertiesConfiguration {
}

In a Boot application, @PropertySource is added during application-context refresh. It is therefore too late for settings consumed before refresh, including some logging.* and spring.main.* settings. Boot configuration data is the appropriate mechanism for those early settings.[12]

4.2 Reading properties through Environment

Java 
@Component
final class EnvironmentBackedClientFactory {
    private final Environment environment;

    EnvironmentBackedClientFactory(
            Environment environment) {
        this.environment = environment;
    }

    RemoteClient create() {
        String endpointText =
                environment.getRequiredProperty(
                        "client.endpoint");

        int timeoutMillis = environment.getProperty(
                "client.timeout-ms",
                Integer.class,
                5_000);

        return new RemoteClient(
                URI.create(endpointText),
                Duration.ofMillis(timeoutMillis));
    }
}

Typed lookups use the environment’s conversion service. A required lookup fails immediately when the key is absent; a defaulted lookup distinguishes intentional fallback from an accidentally unresolved key.

4.3 @Value and placeholders

@Value supports property placeholders such as ${client.timeout-ms} and SpEL expressions such as #{systemProperties['user.timezone']}. It is processed by a bean post-processor and therefore cannot configure the post-processors responsible for interpreting it. Constructor-parameter use is preferable to field injection because the resolved value becomes part of the Java object’s construction contract.[13]

Java 
@Component
final class RetryPolicy {
    private final int attempts;
    private final Duration delay;

    RetryPolicy(
            @Value("${retry.attempts:3}")
            int attempts,

            @Value("${retry.delay-ms:250}")
            int delayMillis) {

        this.attempts = attempts;
        this.delay = Duration.ofMillis(delayMillis);
    }
}

4.4 Strict placeholder resolution

When no explicit embedded-value configurer is registered, Spring can provide a lenient environment-backed resolver. A static PropertySourcesPlaceholderConfigurer gives explicit placeholder-processing policy and can be configured to fail on unresolved placeholders. The class resolves placeholders in bean-definition values and @Value annotations against the environment and its property sources; local properties are lower precedence by default unless localOverride is enabled.[14][15]

Java 
@Configuration(proxyBeanMethods = false)
class PlaceholderConfiguration {

    @Bean
    static PropertySourcesPlaceholderConfigurer
            propertyPlaceholders() {

        PropertySourcesPlaceholderConfigurer configurer =
                new PropertySourcesPlaceholderConfigurer();

        configurer.setIgnoreUnresolvablePlaceholders(false);
        configurer.setTrimValues(true);
        return configurer;
    }
}
Fail early on mandatory configuration A literal unresolved placeholder that survives startup is almost always worse than a startup failure. Use explicit defaults only where the default is valid for every supported deployment.

5. YAML configuration

YAML offers hierarchical maps, sequences, typed scalar values, anchors, and multi-document files. Spring Framework and Spring Boot use YAML differently. Core Spring supplies YAML-to-Properties and YAML-to-Map factories but does not make YAML an automatic application configuration format. Spring Boot’s configuration-data subsystem natively discovers and flattens application.yaml/application.yml documents into the environment.[16][17][12]

YAML 
client:
  endpoint: "https://api.example.net"
  timeout: 3s
  pool:
    max-size: 32
    validation-query: "SELECT 1"

features:
  audit: true

regions:
  - us-east
  - eu-central

In the property-resolution model, the document is flattened to keys such as client.endpoint, client.pool.max-size, and regions[0].[16][12]

5.1 YamlPropertiesFactoryBean

YamlPropertiesFactoryBean converts YAML into a flat Properties structure and exposes all values as strings. Nested mappings become dotted keys and lists become indexed keys. It requires SnakeYAML 2.0 or later.[16]

Java 
YamlPropertiesFactoryBean factory =
        new YamlPropertiesFactoryBean();

factory.setResources(
        new ClassPathResource("config/application.yaml"));
factory.afterPropertiesSet();

Properties properties =
        Objects.requireNonNull(factory.getObject());

String timeout =
        properties.getProperty("client.timeout");

5.2 YamlMapFactoryBean

YamlMapFactoryBean preserves nested structure and YAML-declared value types in a Map<String,Object>. When multiple YAML resources are supplied, later resources override matching scalar entries while nested maps are merged hierarchically rather than replacing the entire parent map.[17]

Java 
YamlMapFactoryBean factory =
        new YamlMapFactoryBean();

factory.setResources(
        new ClassPathResource("config/base.yaml"),
        new FileSystemResource("config/override.yaml"));
factory.afterPropertiesSet();

Map<String, Object> configuration =
        Objects.requireNonNull(factory.getObject());

5.3 YAML with @PropertySource

The default @PropertySource factory handles traditional and XML properties formats, not YAML. A custom PropertySourceFactory can bridge a YAML document into a PropertiesPropertySource.[11]

Java 
public final class YamlPropertySourceFactory
        implements PropertySourceFactory {

    @Override
    public PropertySource<?> createPropertySource(
            String name,
            EncodedResource encodedResource)
            throws IOException {

        YamlPropertiesFactoryBean yaml =
                new YamlPropertiesFactoryBean();

        yaml.setResources(
                encodedResource.getResource());
        yaml.afterPropertiesSet();

        Properties properties =
                Objects.requireNonNull(yaml.getObject());

        String sourceName =
                (name != null && !name.isBlank())
                ? name
                : encodedResource.getResource()
                        .getDescription();

        return new PropertiesPropertySource(
                sourceName,
                properties);
    }
}

@Configuration(proxyBeanMethods = false)
@PropertySource(
    value = "classpath:config/application.yaml",
    factory = YamlPropertySourceFactory.class)
class CoreYamlConfiguration {
}
Do not recreate Spring Boot’s config-data engine casually A custom YAML property-source factory does not automatically provide Boot’s default locations, profile-specific variants, imports, origin metadata, profile activation documents, or complete precedence model.

6. Active and default profiles

Profiles determine which bean definitions are registered during container bootstrap. They can be activated through spring.profiles.active, supplied as a system property or environment variable, or set programmatically on ConfigurableEnvironment. If no explicit profiles are active, the default profile set applies; the reserved default name is default unless changed.[18]

6.1 @Profile

@Profile may annotate a component or configuration class, or an individual @Bean method. A class-level condition suppresses processing of the complete configuration class. Method-level conditions are useful for alternative bean variants within one configuration module.[19]

Java 
@Configuration(proxyBeanMethods = false)
class StorageConfiguration {

    @Bean
    @Profile("production & !offline")
    ObjectStore productionStore(
            ProductionStorageProperties properties) {
        return new RemoteObjectStore(properties.endpoint());
    }

    @Bean
    @Profile("development | test")
    ObjectStore localStore() {
        return new InMemoryObjectStore();
    }
}

6.2 Profile expressions

Profile expressions support negation, conjunction, and disjunction. Parentheses should be used whenever conjunction and disjunction are combined. Programmatic evaluation uses a Profiles predicate against the environment’s active profiles, or against default profiles when none are explicitly active.[20]

Java 
Profiles cloudProduction =
        Profiles.of(
            "production & (aws | azure)");

if (environment.matchesProfiles(
        cloudProduction)) {
    enableCloudDiagnostics();
}

6.3 Activation mechanisms

Shell 
# JVM system property
java -Dspring.profiles.active=production,metrics \
     -jar application.jar

# Environment variable
export SPRING_PROFILES_ACTIVE=production,metrics
java -jar application.jar
Java 
AnnotationConfigApplicationContext context =
        new AnnotationConfigApplicationContext();

context.getEnvironment()
       .setActiveProfiles(
           "production",
           "metrics");

context.register(ApplicationConfiguration.class);
context.refresh();

Programmatic activation must occur before refresh because profile evaluation controls definition registration. Calling setActiveProfiles() replaces the active set; addActiveProfile() preserves existing entries and adds one.[5]

6.4 Profiles are coarse-grained

Use profiles for deployment modes or large configuration groupings: production versus development, online versus offline, or cloud-provider modules. Use properties for scalar values and fine-grained feature decisions. A design with dozens of independently combinable profiles creates a configuration matrix that is difficult to reason about and test.

Good split A profile can select the implementation of a messaging subsystem. Properties should configure its endpoint, retry policy, concurrency, credentials reference, and observability settings.

7. Spring Boot externalized configuration

Spring Framework supplies the environment abstraction; Spring Boot supplies a configuration-data pipeline around it. Boot can externalize values through properties and YAML files, environment variables, system properties, command-line arguments, JSON, servlet/JNDI sources, test-specific sources, and imported configuration. Values can be read through Environment, injected with @Value, or bound to @ConfigurationProperties objects.[12]

7.1 Global property-source precedence

Boot defines an ordered list in which later items override earlier items. The current reference order begins with default properties and @PropertySource, then configuration data, random values, OS environment variables, JVM system properties, JNDI and servlet sources, SPRING_APPLICATION_JSON, command-line arguments, test-specific overrides, and development-tool settings. The exact order is part of Boot’s public configuration contract and should be consulted when diagnosing a winning value.[12]

Broad tier, low to high precedenceExamples
Application defaultsSpringApplication.setDefaultProperties()
Configuration annotations and data@PropertySource, application.properties, YAML, imports
Deployment environmentOS environment variables, JVM system properties, JNDI, servlet parameters
Launch overridesSPRING_APPLICATION_JSON, command-line arguments
Test and development overrides@DynamicPropertySource, @TestPropertySource, devtools settings

Do not memorize only a simplified slogan such as “environment variables always win.” The result depends on Boot’s complete ordered chain and any custom sources added by the application or extensions.

7.2 Configuration-data file precedence

Within Boot configuration data, packaged non-profile files have lower precedence than packaged profile-specific files; external non-profile files override packaged files; external profile-specific files have the highest precedence among these four categories. If both properties and YAML files exist in the same location, Boot recommends using one format and gives .properties precedence.[12]

  1. Packaged application.properties or YAML.
  2. Packaged application-{profile} files.
  3. External application.properties or YAML.
  4. External application-{profile} files.

7.3 Names and locations

Boot searches standard classpath and filesystem locations for the base name application. spring.config.name changes the basename. spring.config.location replaces the default search locations, while additional locations can augment them. Location order and grouping affect precedence, and wildcard locations are supported for external directories rather than classpath locations.[12]

Shell 
java -jar application.jar \
  --spring.config.name=service \
  --spring.config.location=\
optional:classpath:/defaults/,\
optional:file:./config/

7.4 Profile-specific files

If profile production is active, Boot considers both the base document and application-production.properties or YAML. Profile-specific values override non-profile values from the same location tier. When multiple profiles are active, the later profile in the active-profile list can override values from earlier profiles.[12]

YAML 
# application.yaml
client:
  endpoint: "https://sandbox.example.net"
  timeout: 5s
YAML 
# application-production.yaml
client:
  endpoint: "https://api.example.net"
  timeout: 2s

7.5 Multi-document files and activation

Boot supports multiple logical documents in one YAML or properties file. A document with spring.config.activate.on-profile participates only when its profile expression matches. Documents are processed in encounter order, and later values override earlier values within that file’s effective merge.[21]

YAML 
client:
  timeout: 5s

---
spring:
  config:
    activate:
      on-profile: "development"

client:
  timeout: 15s

---
spring:
  config:
    activate:
      on-profile: "production & !offline"

client:
  timeout: 2s

spring.profiles.active and spring.profiles.default may be declared only in non-profile-specific documents; they cannot be set inside a document that is itself activated by a profile expression.[22]

7.6 Included profiles and profile groups

Boot’s spring.profiles.include adds profiles to those activated normally. Profile groups map a logical profile to several fine-grained profiles, allowing production to activate, for example, proddb and prodmq. Include and group declarations belong in non-profile-specific documents.[22]

YAML 
spring:
  profiles:
    group:
      production:
        - proddb
        - prodmq
        - observability

7.7 spring.config.import

Configuration data can import additional documents. Imported values take precedence over the document that declares the import; multiple imports are processed in declaration order, with later imports taking precedence. Relative imports resolve against the importing document. The optional: prefix makes absence non-fatal, and profile-specific variants of imported files are considered where appropriate.[12]

Properties 
spring.config.import=\
optional:file:./config/operator.properties,\
optional:classpath:config/common.yaml

7.8 Configuration trees

Boot’s configtree: import maps files in a directory tree to property names. This is designed for mounted configuration and secret volumes, where each key is stored in a separate file. File and directory names form the property name, and values can bind as strings or byte arrays.[12]

Properties 
spring.config.import=\
optional:configtree:/run/secrets/example/
The environment is not a secret vault Once a secret becomes a property, it can be exposed through diagnostics, exception messages, heap dumps, or overly permissive actuator endpoints. Use origin and value diagnostics carefully, redact sensitive keys, and prefer short-lived credentials where the platform supports them.

8. Typed externalized configuration

Environment and @Value are scalar lookup tools. Spring Boot’s @ConfigurationProperties is designed for cohesive, structured, type-safe configuration and supports relaxed binding from properties, YAML, and environment-variable naming conventions. This is generally the correct boundary for application-owned configuration domains.[12]

Java 
@ConfigurationProperties(prefix = "client")
public record ClientProperties(
        URI endpoint,
        Duration timeout,
        Pool pool,
        List<String> regions) {

    public ClientProperties {
        timeout = Objects.requireNonNullElse(
                timeout,
                Duration.ofSeconds(5));

        regions = List.copyOf(regions);
    }

    public record Pool(
            int maxSize,
            String validationQuery) {
    }
}

@SpringBootApplication
@ConfigurationPropertiesScan
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(
                Application.class,
                args);
    }
}
YAML 
client:
  endpoint: "https://api.example.net"
  timeout: 3s
  pool:
    max-size: 32
    validation-query: "SELECT 1"
  regions:
    - us-east
    - eu-central

External environment variables can use canonical uppercase underscore forms such as CLIENT_ENDPOINT and CLIENT_POOL_MAXSIZE under Boot’s relaxed-binding rules. Keep the canonical configuration-property name in kebab case in source and documentation.

9. Programmatic property sources

9.1 Adding a map source

Java 
static void addTenantDefaults(
        ConfigurableEnvironment environment,
        String tenantId) {

    Map<String, Object> values = Map.of(
            "tenant.id", tenantId,
            "tenant.rate-limit", "1000",
            "tenant.audit-enabled", "true");

    environment.getPropertySources().addLast(
            new MapPropertySource(
                    "tenantDefaults",
                    values));
}

Source names should be stable and meaningful because name determines identity in the source collection. Use one name per conceptual source, not a description containing timestamps or random IDs, unless multiple independent instances are intentionally required.[6]

9.2 Remote source design

A custom property source may retrieve values from a database, control plane, or secrets service, but property lookup can occur frequently and during fragile bootstrap phases. Avoid performing a network request on every getProperty() call. Load a bounded snapshot before refresh, give it a clear precedence tier, define failure behavior, and expose refresh as an explicit lifecycle operation.

9.3 Application-context initializer

Java 
public final class DeploymentEnvironmentInitializer
        implements
        ApplicationContextInitializer<
                ConfigurableApplicationContext> {

    @Override
    public void initialize(
            ConfigurableApplicationContext context) {

        ConfigurableEnvironment environment =
                context.getEnvironment();

        String deployment =
                System.getenv()
                      .getOrDefault(
                          "DEPLOYMENT_NAME",
                          "local");

        environment.getPropertySources().addFirst(
                new MapPropertySource(
                    "deploymentIdentity",
                    Map.of(
                        "deployment.name",
                        deployment)));
    }
}

An initializer runs early enough to affect bootstrap and is preferable to adding high-priority sources from an ordinary bean after definitions have already been processed.

10. Security and configuration integrity

10.1 Configuration is executable influence

Property values can select endpoints, class names, SQL fragments, file locations, profile sets, logging behavior, and conditional beans. Treat writable configuration sources as privileged deployment inputs. Constrain who can modify files, environment variables, command lines, config maps, and secret mounts.

10.2 Do not dump the environment indiscriminately

Property sources may contain credentials, tokens, private keys, database URLs, proxy settings, and cloud metadata. Diagnostic tools should show source names and selected safe keys, not arbitrary complete source contents. Spring’s property-source names are useful for provenance without revealing every value.[6]

10.3 Validate values after resolution

Placeholder resolution answers “what string wins,” not “is this value safe.” Validate URIs against allowed schemes and hosts, normalize filesystem paths, constrain durations and pool sizes, and reject unknown enum values. Typed binding is a transport mechanism, not a replacement for domain validation.

10.4 Profiles are not authorization

An active profile is deployment metadata, not a user identity or security decision. Do not use environment.matchesProfiles() to authorize requests or protect privileged operations. Profile activation can often be changed by launch configuration.

11. Testing environments and profiles

11.1 Unit tests with MockEnvironment

Spring provides a simple configurable mock environment for tests. It supports direct property insertion and profile configuration without creating an application context.[23]

Java 
@Test
void createsClientFromEnvironment() {
    MockEnvironment environment =
            new MockEnvironment()
                .withProperty(
                    "client.endpoint",
                    "https://test.example.net")
                .withProperty(
                    "client.timeout-ms",
                    "100");

    EnvironmentBackedClientFactory factory =
            new EnvironmentBackedClientFactory(
                    environment);

    RemoteClient client = factory.create();

    assertEquals(
            Duration.ofMillis(100),
            client.timeout());
}

11.2 Integration tests with @ActiveProfiles

@ActiveProfiles declares the profiles used when the Spring TestContext Framework loads an application context. It supports inheritance and composed annotations. By default, a spring.profiles.active system property or environment variable does not override profiles explicitly declared by the annotation.[24]

Java 
@SpringJUnitConfig(ApplicationConfiguration.class)
@ActiveProfiles({"test", "offline"})
class OfflineStorageIntegrationTest {

    @Autowired
    ObjectStore objectStore;

    @Test
    void usesInMemoryStore() {
        assertInstanceOf(
                InMemoryObjectStore.class,
                objectStore);
    }
}

12. Worked example: typed, profile-aware delivery service

The example below uses Boot configuration data for external values, @ConfigurationProperties for typed binding, a profile for selecting transport infrastructure, and a programmatic property source for immutable deployment identity.

12.1 Configuration model

Java 
package com.example.delivery;

import org.springframework.boot.context.properties
        .ConfigurationProperties;

import java.net.URI;
import java.time.Duration;
import java.util.List;

@ConfigurationProperties(prefix = "delivery")
public record DeliveryProperties(
        URI endpoint,
        Duration connectTimeout,
        Duration requestTimeout,
        List<String> regions) {

    public DeliveryProperties {
        regions = List.copyOf(regions);
    }
}

12.3 Profile-selected transports

Java 
package com.example.delivery;

import org.springframework.context.annotation.*;

@Configuration(proxyBeanMethods = false)
class DeliveryTransportConfiguration {

    @Bean
    @Profile("remote-delivery")
    DeliveryTransport remoteTransport(
            DeliveryProperties properties) {

        return new HttpDeliveryTransport(
                properties.endpoint(),
                properties.connectTimeout(),
                properties.requestTimeout());
    }

    @Bean
    @Profile("!remote-delivery")
    DeliveryTransport localTransport() {
        return new RecordingDeliveryTransport();
    }
}

12.4 Service consuming typed configuration

Java 
package com.example.delivery;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Service;

@Service
final class DeliveryService {
    private final DeliveryTransport transport;
    private final DeliveryProperties properties;
    private final String deploymentName;

    DeliveryService(
            DeliveryTransport transport,
            DeliveryProperties properties,
            @Value("${deployment.name:local}")
            String deploymentName) {

        this.transport = transport;
        this.properties = properties;
        this.deploymentName = deploymentName;
    }

    DeliveryReceipt deliver(Message message) {
        DeliveryRequest request =
                new DeliveryRequest(
                    message,
                    properties.regions(),
                    deploymentName);

        return transport.deliver(request);
    }
}

The production profile group activates the remote transport and observability module. The environment variable overrides the YAML request timeout. The service receives one structured configuration object plus one isolated scalar value; it does not perform runtime key lookup.

13. Diagnostics

13.1 A property has the wrong value

Identify the canonical key, enumerate property-source names in precedence order, and inspect only that key in each enumerable source. In Boot, enable trace logging for org.springframework.boot.context.config to diagnose loaded configuration documents.[21]

Java 
static void traceProperty(
        ConfigurableEnvironment environment,
        String key) {

    System.out.println(
            "resolved " + key + " = "
            + environment.getProperty(key));

    for (PropertySource<?> source :
            environment.getPropertySources()) {

        Object value = source.getProperty(key);

        System.out.printf(
                "%-40s %s%n",
                source.getName(),
                value != null
                    ? "[contains key]"
                    : "");
    }
}

Do not print the value for keys that may contain secrets. Source presence is often sufficient to identify the override.

13.2 A profiled bean is missing

Log active and default profile arrays, check the exact profile expression, confirm that activation occurred before refresh, and determine whether a Boot profile group or include changed the effective set. Remember that a class-level @Profile can suppress every bean method and import in that configuration class.

13.3 YAML was not loaded

In plain Spring Framework, YAML is not automatically treated as an environment source; configure a YAML factory or custom property-source factory. In Boot, verify the name, extension, standard location or explicit config location, profile suffix, import syntax, and SnakeYAML availability.

13.4 Logging or bootstrap setting ignores @PropertySource

The annotation is processed during refresh, after some Boot settings have already been consumed. Move early settings into Boot configuration data, environment variables, system properties, or command-line arguments.[12]

13.5 Environment variable does not bind

Distinguish core Environment lookup from Boot relaxed binding. Check uppercase underscore naming, list/index encoding, canonical property names, container-orchestrator substitutions, and whether the target is @Value or @ConfigurationProperties.

13.6 A placeholder remains literal

Confirm that an embedded value resolver or PropertySourcesPlaceholderConfigurer is registered, the property source was added before placeholder processing, and unresolved placeholders are not intentionally ignored. Static factory-post-processor @Bean methods avoid premature instantiation of the containing configuration class.

14. Expert practices

14.1 Define canonical keys

Use stable lowercase kebab-case names for external configuration and document the environment-variable form. Do not rename keys casually; they are deployment APIs.

14.2 Publish the override model

State which values belong in packaged defaults, external files, secret mounts, environment variables, system properties, and command-line arguments. An undocumented precedence model becomes tribal knowledge.

14.3 Bind cohesive domains

Prefer one validated configuration object per subsystem. Keep raw Environment access at framework and bootstrap boundaries.

14.4 Keep profiles few and meaningful

Profiles should describe deployment topology or broad modes. Use properties for tunables and feature decisions. Test every supported profile combination explicitly.

14.5 Make defaults safe

A default should be valid in every environment where the key may be absent. Never default a production credential, unrestricted endpoint, destructive mode, or permissive security setting merely to make startup succeed.

14.6 Mutate before refresh

Property sources and profiles that affect bean registration or placeholder resolution must be present before the application context refresh pipeline processes definitions.[5]

14.7 Preserve origin and redact values

Give custom sources meaningful names, retain document and line origin where the framework supports it, and expose provenance without leaking sensitive values.

14.8 Treat effective configuration as immutable

Runtime mutation of the environment does not automatically rebuild beans or rebind configuration objects. If dynamic refresh is a requirement, design an explicit refresh protocol with atomic snapshots, validation, rollback, observability, and concurrency semantics.

14.9 Test precedence, not only values

A test that asserts the resolved value under one source is insufficient. Test representative collisions: packaged versus external, base versus profile-specific, environment variable versus system property, and command line versus configuration data.

15. Summary

Spring’s environment system is most coherent when viewed as a bootstrap-time composition of ordered inputs:

  • Environment combines profile evaluation with property resolution.
  • PropertySource adapts heterogeneous sources to a common lookup contract.
  • MutablePropertySources makes precedence explicit: the first matching source wins.
  • StandardEnvironment starts with system properties ahead of environment variables; servlet environments add web-specific sources.
  • @PropertySource contributes properties during context refresh and is unsuitable for Boot settings read earlier.
  • Core Spring supports YAML through YAML factories or custom property-source factories; Boot supplies automatic YAML configuration data.
  • Profiles decide definition eligibility; properties configure the selected definitions.
  • Boot externalized configuration adds default locations, profile variants, document activation, imports, configuration trees, test sources, and a detailed override order.
  • @ConfigurationProperties is the preferred application boundary for cohesive typed settings; @Value remains useful for isolated scalars.
  • Configuration must be validated, redacted, traced to its source, and treated as a privileged deployment interface.

When configuration behaves unexpectedly, ask four questions in order: Which profiles were effective before refresh? Which property sources were installed, and in what order? Which source contained the winning key? How was that raw value converted, bound, and validated? Those questions reduce most environment problems to a deterministic bootstrap trace rather than an annotation mystery.
