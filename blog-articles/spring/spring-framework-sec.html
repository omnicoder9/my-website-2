Spring Security is unusual among application security libraries in how much it does before you write a line of configuration: CSRF tokens, seven response headers, session fixation protection, adaptive password hashing, and a deny-by-default authorization model all arrive with the dependency. It is equally unusual in how sharply that guarantee stops. Output encoding, query construction, data binding, secret storage, and the Actuator surface are yours. This is a working map of both halves — what the framework holds, where it hands the problem back, and what the CVE record says about the seams between them.

01What the framework guarantees, and what it merely offers

A Spring Boot application that has never had a security requirement written down is nonetheless enforcing a security policy. Adding spring-boot-starter-security to a build file changes the behaviour of every endpoint in the application: requests are authenticated, state-changing requests require a CSRF token, seven response headers appear, sessions are rotated on login, and any request not explicitly permitted is refused. Nobody asked for this. It happens because the framework's designers concluded, correctly, that the default configuration of a web framework is its most widely deployed configuration.

That decision shapes what it means to secure a Spring application. The work is rarely a matter of switching protections on. It is a matter of understanding precisely where the framework's guarantee ends — because the guarantee is real, and its boundary is sharp, and most production incidents in Spring applications occur a few centimetres past that boundary.

Three categories are worth separating before anything else.

Enforced by default. Authentication of every request, CSRF protection on unsafe HTTP methods, a fixed set of response headers, session fixation protection, a request firewall that rejects malformed URLs, and adaptive one-way password hashing when you use the framework's own user store. You have to write code to turn these off, and the configuration DSL makes turning them off conspicuous.

Offered but not applied. Content Security Policy, Referrer-Policy, Permissions-Policy, method-level authorization, OAuth 2.0 resource-server validation, allow-list data binding, encrypted configuration properties, and breached-password screening. Every one of these is a first-class, documented feature; none of them does anything until you ask.

Outside the framework entirely. Whether your templates escape the values they render, whether your repository concatenates a sort column into a query string, whether your entity class is bound directly to request parameters, whether your Actuator endpoints are reachable from the internet, and whether a credential is sitting in a properties file in version control. Spring Security has no opinion on any of these, and no mechanism by which it could.

The shape of the argument

Almost every section that follows is a variation on the same theme: the framework has already solved the version of the problem that was solvable at the framework layer, and the residue — which is where the incidents are — is a design question in your application. The most useful thing an experienced engineer brings to a Spring codebase is an accurate map of that residue.

The current baseline for that map is Spring Framework 7.0, generally available since November 2025, which raised the portfolio to Jakarta EE 11 and a JDK 17 minimum while targeting JDK 25.1 It is paired with Spring Security 7.0, released four days later, and with Spring Boot 4.0.2 3 At the time of writing the stable Spring Security line is 7.1, with 7.0.6 and 6.5.11 maintained alongside it,4 and Spring Boot has moved on to 4.1.5 The substance of what follows applies from Spring Security 6.0 onward; where 7.x changed something materially, it is called out.

02From Acegi to Spring Security 7

In late 2003 someone asked on the Spring developers' mailing list whether anyone had considered a Spring-based security implementation. The answer was that it seemed worthwhile but nobody had time. Ben Alex built one anyway, did not release it, and then handed it to the next person who asked. By January 2004 roughly twenty people were using the code, and in March 2004 it was published on SourceForge under the Apache License.6

The name came from a naming collision. Alex had proposed calling it "Spring Security"; Rod Johnson and Juergen Hoeller had not had time to review it properly and suggested he ship it as "something Security System for Spring" instead. He prefixed the name of his consultancy, Acegi — the first, third, fifth, seventh and ninth letters of the alphabet, chosen years earlier for a bulletin board because every name he liked was taken.7 Acegi Security became an official Spring portfolio project at the end of 2007 and was renamed; the first release under the new name, Spring Security 2.0.0, shipped in April 2008.68 Alex went on to found Spring Roo and Spring Shell.9

The historical detail matters for one reason: it explains the framework's characteristic shape. Acegi was written for a world in which J2EE container-managed security was the alternative — a model where the deployment descriptor owned the policy, the container enforced it, and the application could not extend it without leaving the standard. Acegi's answer was to move the entire policy into the application context as ordinary beans, enforced by an ordinary servlet filter and ordinary AOP proxies. Everything since has been an elaboration on that: policy as configuration, enforcement as interception, extension as bean replacement.

Spring Security's peculiar density — a dozen filters, five authorization models, four password encoders — is the accumulated residue of twenty-three years of refusing to remove a working mechanism from under somebody's production system.

That elaboration has run in one direction: each generation folded a class of attack into default behaviour. Version 3.2 added the header writers. Version 4 added CSRF protection by default. Version 5 introduced DelegatingPasswordEncoder, which made password-hash migration a non-event, and made OAuth 2.0 and OpenID Connect first-class. Version 6 moved to Jakarta EE, replaced the WebSecurityConfigurerAdapter inheritance model with SecurityFilterChain beans and a lambda DSL, and made CSRF tokens randomised per request. Version 7 brought passkeys, declarative multi-factor authentication, one-time-token login and DPoP-bound access tokens into the core.410

The cost of that trajectory is a large API surface with several overlapping ways to express the same policy, and a long tail of deprecated-but-alive mechanisms. The benefit is that an application built on defaults in 2026 gets protections that in 2008 required a specialist.

03The filter chain is the security model

Every security decision Spring Security makes for a servlet application happens in a chain of filters, and understanding that chain is the difference between configuring the framework and guessing at it.

The servlet container knows about exactly one filter: a DelegatingFilterProxy registered under the name springSecurityFilterChain. It holds no logic. It looks up a Spring bean — FilterChainProxy — and delegates to it. This indirection is what allows security filters to be full participants in the application context: they can be injected, proxied, and configured like any other bean, despite living in a container that was built before any of that existed.11

FilterChainProxy then matches the request against an ordered list of SecurityFilterChain beans and dispatches to the first one that matches. Not every matching one. The first.

The single most common configuration bug

Because only the first matching chain runs, chain order is policy. A chain declared with @Order(1) whose matcher is broad will silently shadow every chain after it. If an API chain that permits anonymous access is ordered ahead of the chain that protects the admin console, the admin console is unprotected — and nothing logs an error, because the configuration is perfectly valid. Spring Boot prints the resolved filter chains and their matchers at DEBUG on org.springframework.security; reading that output once, on a real application, is worth more than any amount of configuration review.

A modern configuration is a set of beans. There is no adapter class to extend, and since Spring Security 7 the request matchers are built from PathPatternRequestMatcher rather than the older Ant-style matching.12

java
@Configuration
@EnableWebSecurity
@EnableMethodSecurity                                  // opt-in: @PreAuthorize etc.
public class SecurityConfig {

    @Bean
    @Order(1)
    SecurityFilterChain apiChain(HttpSecurity http) throws Exception {
        http
            .securityMatcher("/api/**")                 // narrow: this chain owns only /api
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/public/**").permitAll()
                .anyRequest().authenticated())
            .oauth2ResourceServer(oauth -> oauth.jwt(Customizer.withDefaults()))
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .csrf(csrf -> csrf.disable());              // justified: no cookie auth on this chain
        return http.build();
    }

    @Bean
    @Order(2)
    SecurityFilterChain webChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/", "/login", "/css/**").permitAll()
                .requestMatchers("/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated())         // deny-by-default backstop
            .formLogin(Customizer.withDefaults())
            .logout(logout -> logout.logoutSuccessUrl("/"))
            .headers(h -> h
                .contentSecurityPolicy(csp -> csp.policyDirectives(
                    "default-src 'self'; object-src 'none'; base-uri 'none'"))
                .referrerPolicy(r -> r.policy(ReferrerPolicy.STRICT_ORIGIN_WHEN_CROSS_ORIGIN)));
        return http.build();
    }
}

Three details in that configuration carry disproportionate weight.

anyRequest().authenticated() is the backstop. Spring Security's authorization model is first-match-wins within a chain, top to bottom, so a terminal catch-all rule is what converts the list from an allow-list of protections into a deny-by-default policy. Without it, a new controller added six months later is public.

csrf.disable() on the API chain is defensible only because that chain authenticates with a bearer token rather than a cookie. CSRF exists because browsers attach ambient credentials automatically; a token deliberately placed in an Authorization header by client code is not ambient. Disabling CSRF on a chain that still accepts session cookies re-opens the hole completely.13

SessionCreationPolicy.STATELESS is not merely an optimisation. It prevents the API chain from creating an HttpSession as a side effect of authentication, which is how token-authenticated APIs quietly acquire session cookies and, with them, CSRF exposure they were assumed not to have.

The request firewall

Before any of this, FilterChainProxy passes the request through an HttpFirewall. The default implementation, StrictHttpFirewall, rejects requests whose URLs contain encoded slashes, encoded percent signs, semicolons (path parameters), backslashes, non-printable ASCII, or paths that are not normalised.14 These rejections look pedantic and occasionally break a legitimate integration. They exist because the entire family of path-based authorization bypasses depends on the security layer and the dispatch layer disagreeing about what a URL means. The firewall's job is to refuse any request about which such a disagreement is possible. Loosening it — and there is a documented, sanctioned way to loosen it — should be a deliberate, reviewed decision with a specific integration named in the commit message.

04Authorization: two enforcement points, both required

Broken access control has been the top entry in the OWASP Top 10 for four consecutive editions, and in the 2025 data it was found in some form in every application tested.1516 The 2025 revision expanded the category to absorb server-side request forgery and to name the API authorization patterns — broken object-level and function-level authorization — explicitly.1718 Spring gives you two enforcement points for this, and using only one of them is the usual failure.

Request-level authorization

The AuthorizationFilter sits near the end of the chain and evaluates a list of matcher-to-rule pairs against the request URL and method.12 It is fast, centralised, and easy to audit, and it knows nothing about your domain. It can tell you that /api/invoices/** requires the ACCOUNTING authority. It cannot tell you that invoice 4471 belongs to a different tenant.

Method-level authorization

@EnableMethodSecurity activates AOP-based enforcement using @PreAuthorize, @PostAuthorize, @PreFilter and @PostFilter, evaluated as Spring Expression Language against the method's arguments and return value.19 This is where object-level decisions belong, because this is the only layer that can see the object.

java
@Service
public class InvoiceService {

    @PreAuthorize("hasAuthority('ACCOUNTING')")
    public List<Invoice> findForCurrentTenant() { ... }

    // Object-level: the decision needs the entity, so it happens after loading.
    @PostAuthorize("returnObject.tenantId == authentication.principal.tenantId")
    public Invoice findById(long id) { ... }

    // Argument-level: cheaper, and it never loads what it will not return.
    @PreAuthorize("@tenantGuard.owns(#id, authentication)")
    public void voidInvoice(long id) { ... }
}
CVE-2025-41248 · CVE-2025-41249

In September 2025 Spring disclosed a pair of related flaws in annotation resolution. Where a secured method is declared on a generic superclass or interface with an unbounded type parameter, the annotation detection mechanism could fail to resolve @PreAuthorize and its siblings on the overriding method — with the result that Spring Security enforced nothing and reported nothing. Applications using @EnableMethodSecurity with generic service hierarchies were affected; fixed in Spring Security 6.4.10 and 6.5.4, with the documented workaround being to redeclare the secured methods in their concrete target class.2021

The lesson generalises beyond the patch. Annotation-driven authorization is invisible when it fails. A request-level rule that stops matching produces a 403 that somebody notices; a method annotation that is not discovered produces a successful response. Defence in depth here means keeping a coarse request-level rule in place even where method security carries the precise decision.

Authorities, roles, and the prefix that eats afternoons

hasRole("ADMIN") and hasAuthority("ADMIN") are not the same test. The former prepends ROLE_ before comparing; the latter compares literally. A user loaded with the authority ADMIN fails hasRole("ADMIN"), and a user loaded with ROLE_ADMIN fails hasAuthority("ADMIN"). Pick one convention per codebase and enforce it in the GrantedAuthority mapping rather than at each call site — for JWT resource servers, in a JwtAuthenticationConverter.22

Spring Security 7.1 added ConditionalAuthorizationManager and an InetAddressMatcher, which make it practical to express rules like "this endpoint requires a second factor unless the request originates from the management network" without hand-rolling an AuthorizationManager.423

05Cross-site request forgery

Cross-site request forgery exploits the fact that browsers attach cookies to requests based on the destination, not the origin. A form on an attacker's page that posts to your application will carry your user's session cookie. The synchroniser token pattern defeats this by requiring a value the attacker cannot read: the server issues a token, stores it server-side, and requires it back on every state-changing request.24

Spring Security applies this by default to every unsafe HTTP method — anything that is not GET, HEAD, OPTIONS or TRACE. No code is required.25 It also, deliberately, requires a CSRF token for login and logout. Forged login requests are a real attack (they let an attacker authenticate a victim's browser as the attacker's own account and then read what the victim does), and forced logout is a denial of service; Spring's LogoutFilter therefore only processes POST when CSRF protection is on.25

What changed in Spring Security 6, and why single-page applications broke

Two changes landed together. First, loading of the token became deferred, so the HttpSession is no longer read on every request. Second, and more consequentially, the token value is now randomised on every render by XorCsrfTokenRequestAttributeHandler, which masks the persisted token with fresh randomness before it reaches the response.25

The reason is BREACH — a compression side-channel attack that recovers secrets embedded in compressed HTTPS responses by observing how response length varies with attacker-controlled input. A CSRF token that is byte-identical across renders is exactly the kind of secret BREACH extracts.26 Masking it makes each rendered value unique, so response length carries no signal. The filter unmasks the submitted value and compares the recovered raw token against the persisted one.25

This is what broke JavaScript clients. With CookieCsrfTokenRepository, the cookie contains the raw token; the value the server expects in the header is a masked encoding of it. A client that reads the cookie and echoes it back is submitting an unmasked value, and the default handler rejects it. The situation is compounded by the fact that CsrfAuthenticationStrategy and CsrfLogoutHandler clear the token on login and logout success, so a fresh one must be obtained at both points.25

Spring Security now ships a single-call answer to the whole problem:

java
@Bean
SecurityFilterChain spa(HttpSecurity http) throws Exception {
    http.csrf(csrf -> csrf.spa());   // cookie repository + SPA-aware token resolution
    return http.build();
}

For a server-rendered application none of this is visible: Thymeleaf and Spring's form tag library integrate with RequestDataValueProcessor and inject the hidden _csrf input into every non-GET form automatically.25 For a native mobile client that also serves browser traffic, the documented pattern is a small /csrf endpoint returning the current token on demand, which keeps deferred loading intact.25

When disabling CSRF is correct — and when it is cargo cult

The rule is about how the request is authenticated, not about what it returns. If a chain authenticates only via a bearer token, mutual TLS, or an API key that client code must place in a header, CSRF protection is redundant, and csrf.disable() plus SessionCreationPolicy.STATELESS is right. If the chain accepts a session cookie for any route — including a login endpoint that sets one — disabling CSRF is a vulnerability. "It's a REST API" is not the test. "Nothing here is authenticated by an ambient credential" is.

Two adjacent controls

The SameSite cookie attribute is a genuine second layer, and SameSite=Lax is now the browser default for cookies that do not specify it. It is not a replacement: Lax permits top-level GET navigation, older clients ignore the attribute entirely, and same-site does not mean same-origin — a subdomain compromise defeats it.24 Set it, and keep the token.

CORS is the other. It is frequently mistaken for a CSRF control and is close to the opposite: it governs whether JavaScript may read a cross-origin response, not whether the request is sent. A permissive CORS configuration that reflects arbitrary origins and allows credentials converts a read-protected API into a readable one. Configure it through Spring's CorsConfigurationSource so that Spring Security's CorsFilter sees it, and never reflect the Origin header with allowCredentials enabled.27 CVE-2020-5397 is a reminder that the interaction between CORS preflight and CSRF has produced real vulnerabilities in Spring itself.28

06Cross-site scripting and the escaping contract

Cross-site scripting is the major class in which Spring Security does almost nothing for you, and this surprises people. The framework has no output encoder, no template awareness, and no sanitiser. Its sole contribution is the ability to emit a Content Security Policy header — which it will not do unless you write the policy.29

The defence lives in the template engine, and for the overwhelming majority of Spring applications that means Thymeleaf, which escapes by default. th:text applies HTML escaping to everything it renders. th:utext — the "u" is for unescaped — does not.3031

html
<!-- Safe: escaped. &lt;script&gt; arrives as visible text. -->
<p th:text="${comment.body}">placeholder</p>

<!-- Unsafe unless comment.body is already sanitised markup you produced. -->
<p th:utext="${comment.body}">placeholder</p>

<!-- Attribute context is still escaped, but the URL scheme is not validated. -->
<a th:href="${user.website}">profile</a>   <!-- javascript: still executes -->

Three practical consequences follow.

Grep for th:utext and justify every hit. It is a two-character difference from the safe form, it is the idiomatic way to render internationalised messages that contain markup, and it is the single highest-yield search in a Thymeleaf security review. Where it is genuinely needed — user-authored rich text — the value must pass through a real HTML sanitiser such as the OWASP Java HTML Sanitizer before it reaches the model, not through a hand-written blocklist of tag names.

Escaping is contextual, and template engines only know one context. HTML escaping neutralises <script> but does nothing to a URL whose scheme is javascript:, and nothing at all to a value interpolated into an inline <script> block, where the correct encoding is JavaScript string escaping. Thymeleaf's th:inline="javascript" handles the latter properly; string concatenation into a script block does not. Validate URL schemes against an allow-list of http and https before rendering them into an href.

Escape on output, never on input. The recurring anti-pattern is a servlet filter that HTML-escapes every request parameter on the way in. It corrupts data for every non-HTML consumer — the JSON API, the CSV export, the search index, the email templates — while failing to protect the contexts that need a different encoding. Store what the user typed. Encode when and where you render it.

Template injection is the escalated form

Where a template name or fragment expression is built from user input, the exposure is not cross-site scripting but server-side template injection: Thymeleaf evaluates SpEL, and SpEL can reach T(java.lang.Runtime). Public proof-of-concept chains for Spring applications reach remote code execution through exactly this path.32 Template names must come from a fixed set in code. This is the same rule that governs SpEL and query fragments, and it appears three more times in this article.

On the framework's own contribution: Spring Security's default X-XSS-Protection: 0 is not an oversight. The legacy browser XSS auditors that the header enabled were themselves the source of vulnerabilities and information leaks, and every major engine has removed them; 0 explicitly disables the remaining implementations rather than leaving behaviour to the client.33 The modern replacement is a real Content Security Policy, which is the subject of the next section.

07Content Security Policy

Content Security Policy is the browser-side control that assumes your escaping will eventually fail. It declares, per response, which origins may supply scripts, styles, images, frames and connections, and what inline content is permitted.34 Where escaping is a per-value guarantee that has to hold everywhere, CSP is a per-page guarantee that holds even where escaping did not.

Spring Security will not emit one by default, and the documentation explains why plainly: a reasonable default is impossible to know without knowing the application. The author must declare the policy.29

java
http.headers(headers -> headers
    .contentSecurityPolicy(csp -> csp.policyDirectives(
        "default-src 'self'; " +
        "script-src 'self' 'nonce-{NONCE}'; " +
        "object-src 'none'; " +
        "base-uri 'none'; " +
        "frame-ancestors 'none'; " +
        "form-action 'self'; " +
        "report-uri /csp-report"))
    .frameOptions(f -> f.deny()));

Four directives deserve specific attention because they are the ones most often omitted.

object-src 'none' blocks plugin content, which is a long-standing script-execution bypass that a script-src directive alone does not cover. base-uri 'none' prevents an injected <base> tag from re-pointing every relative script URL in the document at an attacker's host — a bypass that defeats an otherwise correct allow-list. frame-ancestors is the modern replacement for X-Frame-Options and, unlike it, supports a list of origins. form-action 'self' stops an injected form from posting credentials off-site.

Nonces, and why the naive policy fails

The reason CSP adoption stalls is almost always inline script. A policy of script-src 'self' blocks every <script> block and every onclick attribute in the application, and the path of least resistance — adding 'unsafe-inline' — nullifies the protection completely, because injected script is inline script.

The correct mechanism is a per-response nonce: a cryptographically random value emitted in both the header and the nonce attribute of each legitimate script tag. Injected script has no nonce and does not execute. Spring Security does not generate the nonce for you, but the pieces are small: a filter that puts a fresh value on the request and a HeaderWriter that substitutes it into the policy string, with the template reading the same request attribute.

java
public class CspNonceFilter extends OncePerRequestFilter {
    public static final String ATTR = "cspNonce";
    private final SecureRandom random = new SecureRandom();

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
                                    FilterChain chain) throws ServletException, IOException {
        byte[] bytes = new byte[16];
        random.nextBytes(bytes);
        req.setAttribute(ATTR, Base64.getUrlEncoder().withoutPadding().encodeToString(bytes));
        chain.doFilter(req, res);
    }
}

// Registered before the header writer so the value exists when the policy is rendered:
http.addFilterBefore(new CspNonceFilter(), HeaderWriterFilter.class)
    .headers(h -> h.addHeaderWriter((req, res) ->
        res.setHeader("Content-Security-Policy",
            "default-src 'self'; script-src 'self' 'nonce-" + req.getAttribute(CspNonceFilter.ATTR) + "'")));
Deploy in report-only first

csp.reportOnly() emits Content-Security-Policy-Report-Only, which reports violations without blocking anything.29 Run it for a full release cycle against real traffic, collect the reports, and only then switch to enforcement. A CSP rolled out enforcing on day one will break a marketing tag, an analytics snippet or a third-party widget that nobody remembered, and the resulting incident tends to end with 'unsafe-inline' permanently in the policy.

08Secure response headers

Spring Security writes seven response headers on every response without being asked, and the exact set is worth committing to memory because it determines what you still have to add.33 35

Each has a rationale. The three cache headers exist so that a page rendered for an authenticated user cannot be recovered from the browser's back-forward cache after logout — a real and frequently demonstrated exposure on shared machines. nosniff stops content-type sniffing, which is how a user-uploaded file served as text/plain gets executed as HTML. HSTS instructs the browser never to speak plaintext HTTP to this host again for a year. X-Frame-Options: DENY is anti-clickjacking. X-XSS-Protection: 0 explicitly disables the legacy browser auditors.33

Customisation is per-header, and defaultsDisabled() exists for the case where you want explicit control over the whole set.29 The commonly needed adjustments are frameOptions().sameOrigin() for applications that embed themselves, and HSTS with includeSubDomains and preload — the latter being a one-way door, since removal from the browser preload list takes months.

java
http.headers(h -> h
    .httpStrictTransportSecurity(hsts -> hsts
        .includeSubDomains(true)
        .preload(true)
        .maxAgeInSeconds(31536000))
    .referrerPolicy(r -> r.policy(ReferrerPolicy.STRICT_ORIGIN_WHEN_CROSS_ORIGIN))
    .permissionsPolicy(p -> p.policy("geolocation=(), camera=(), microphone=()"))
    .crossOriginOpenerPolicy(c -> c.policy(SAME_ORIGIN))
    .crossOriginEmbedderPolicy(c -> c.policy(REQUIRE_CORP)));

One header is worth adding at logout rather than on every response. ClearSiteDataHeaderWriter, wired through a HeaderWriterLogoutHandler, instructs the browser to discard cookies, cache and storage for the origin — which is the only reliable way to remove client-side state that the application put there and no longer controls.29

In March 2026 Spring disclosed that under some conditions, servlet applications using the default lazy header-writing mode would not write configured HTTP response headers at all. Every actively maintained branch was affected — 5.7.0 to 5.7.21, 5.8.0 to 5.8.23, 6.3.0 to 6.3.14, 6.4.0 to 6.4.14, 6.5.0 to 6.5.8, and 7.0.0 to 7.0.3 — with fixes in 6.5.9 and 7.0.4 and a workaround of setting HeaderWriterFilter.shouldWriteHeadersEagerly to true. The advisory names cache-related exposure specifically: responses that should never have been stored could be.3637 It was disclosed alongside two Actuator authentication bypasses in the same batch.38

Nothing about the affected applications' configuration was wrong. They had asked for the headers; the headers were not written; no error was raised. This is the clearest available argument for verifying security headers from outside the application — an integration test that asserts on the actual response, or a synthetic check in production — rather than trusting that configuration implies behaviour.

09SQL injection and the query surface

SQL injection is, in the ordinary case, a solved problem in Spring. JdbcTemplate with ? placeholders, NamedParameterJdbcTemplate with :name parameters, derived query methods on a Spring Data repository, and @Query with @Param bindings all compile to JDBC PreparedStatement parameters, where the value can never be reinterpreted as syntax.3940 An application that stays inside those idioms is not injectable through them.

The interesting question is where applications leave those idioms, and there are exactly two places — both structural, both invisible to a scanner that only looks for string concatenation adjacent to a WHERE clause.

Structural interpolation

Parameters bind values. They cannot bind a column name, a table name, a sort direction, or a schema. So the moment a requirement says "let the user choose the sort column", the parameter mechanism stops applying and the code goes back to string building:

java
// Vulnerable: sortBy and direction arrive from the query string.
String sql = "SELECT * FROM invoice WHERE tenant_id = :tenant ORDER BY " + sortBy + " " + direction;

// Correct: the untrusted value selects from a fixed set; it never reaches the SQL text.
private static final Map<String, String> SORTABLE = Map.of(
        "date",   "issued_on",
        "amount", "total_cents",
        "status", "status");

String column = SORTABLE.get(sortBy);
if (column == null) throw new IllegalArgumentException("unsortable field");
String dir = "desc".equalsIgnoreCase(direction) ? "DESC" : "ASC";

String sql = "SELECT * FROM invoice WHERE tenant_id = :tenant ORDER BY " + column + " " + dir;

The same hazard arrives less visibly through Spring Data's Pageable. Binding a Sort directly from request parameters means the property names in the sort order come from the client. For derived queries the property path is validated against the entity metamodel, but for native queries with a string-interpolated ORDER BY it is not. Map incoming sort keys onto a fixed set of allowed properties in the controller, and never pass a client-supplied Sort into a native query.

Expression evaluation

The second exit is more dangerous, because the payload is not SQL. Spring's expression language appears in query annotations — @Query("... ?#{...} ...") in Spring Data JPA, SpEL-backed @Query and @Aggregation in Spring Data MongoDB. Where untrusted input is interpolated into the expression rather than bound as a parameter, the attacker is not writing SQL; they are writing Java.

Two CVEs make the shape concrete. CVE-2018-1273 was a property-binder flaw in Spring Data Commons: MapDataBinder evaluated a user-supplied property path as a SpEL expression using a StandardEvaluationContext, which permits type references. A crafted parameter name containing T(...) reached arbitrary class references and, from there, remote code execution against Spring Data REST endpoints and projection-based request binding. The fix replaced the evaluation context with the restricted SimpleEvaluationContext.41 42 CVE-2022-22980 was the same category in Spring Data MongoDB: SpEL injection through @Query and @Aggregation expressions containing parameter placeholders where the input was not sanitised.43

The rule that covers template names, expression fragments and query structure is one rule: untrusted input may select among alternatives you wrote, and may be bound as a value. It may never become part of an expression that something else will parse.

What actually protects the ordinary case

Prefer the Criteria API or Spring Data Specification for genuinely dynamic queries: the structure is assembled from typed objects rather than concatenated text, which removes the string manipulation entirely.40 Validate at the boundary with Bean Validation so that a field expected to be numeric is numeric before it reaches the persistence layer. And apply least privilege at the database: an application account that cannot DROP, cannot read other schemas, and cannot execute the file-write functions the DBMS exposes converts many successful injections into failed ones.

10Mass assignment and the data binder

Mass assignment is the vulnerability where a request parameter binds to a field the developer never intended to expose — classically isAdmin=true in a profile-update form. Spring MVC's data binder maps request parameters to object properties by name, recursively, following nested property paths. That is the feature. The vulnerability is the same feature pointed at an object with more properties than the form has fields.44

Spring offers three controls, and their history is instructive.

java
@Controller
public class ProfileController {

    // 1. Deny-list: which fields must not bind. Case-insensitive matching.
    @InitBinder
    void denyList(WebDataBinder binder) {
        binder.setDisallowedFields("role", "enabled", "accountBalance");
    }

    // 2. Allow-list: which fields may bind. Case-sensitive. Preferred.
    @InitBinder
    void allowList(WebDataBinder binder) {
        binder.setAllowedFields("firstName", "lastName", "*Address");
    }

    // 3. Declarative binding: constructor binding always; setter binding only
    //    for explicitly allowed fields.
    @InitBinder
    void declarative(WebDataBinder binder) {
        binder.setDeclarativeBinding(true);
    }
}

The framework documentation is unambiguous about the ranking: an allow-list is safer than a deny-list, and setAllowedFields() should be favoured over setDisallowedFields(). It also notes an asymmetry that matters — allowed patterns match case-sensitively, disallowed patterns case-insensitively.45 The recommended design goes further: prefer immutable objects, because a constructor naturally constrains binding to its declared parameters, and set declarativeBinding so that setter binding does not happen at all unless allowedFields is configured.46

Why the deny-list keeps failing

The CVE record for Spring's data binder is a fifteen-year demonstration that enumerating forbidden property names does not work.

It begins with CVE-2010-1622, after which Spring added a check to ignore the class.classLoader and class.protectionDomain property descriptors — a blocklist. In March 2022 that blocklist was walked around. Class.getModule(), introduced in JDK 9, gave attackers class.module.classLoader: a different path to the same object.47 The result, CVE-2022-22965 or "Spring4Shell", was an unauthenticated remote code execution scored 9.8, affecting Spring Framework 5.3.0–5.3.17 and 5.2.0–5.2.19 on JDK 9 or later. The published exploit chain bound properties of Tomcat's AccessLogValve — pattern, directory, prefix, suffix — to write a JSP web shell into the web root, then invoked it.484947 It reached CISA's Known Exploited Vulnerabilities catalogue. The patch, in 5.3.18 and 5.2.20, restricted child property access on class to name variants and stopped permitting ClassLoader and ProtectionDomain types to bind at all.5048

The instructive part is what came after. CVE-2022-22968 made disallowedFields patterns case-insensitive, closing a bypass where Admin evaded a rule written for admin. CVE-2024-38820 then observed that the fix relied on String.toLowerCase(), which has locale-dependent behaviour, so some fields were still not protected as intended.51 CVE-2025-22233, disclosed in May 2025, reported that even after locale-independent lowercasing, cases remained where the disallowedFields checks could be bypassed. Spring's own guidance in that advisory is the conclusion of the whole arc: use a dedicated model object with properties only for data binding, or use constructor binding with declarativeBinding turned on, and prefer allowedFields over disallowedFields.52

The design that ends the problem

Do not bind requests to entities. Bind them to purpose-built records that contain exactly the fields the operation accepts, validate those, and map explicitly.

java
// The request object cannot express a privilege change, because it has nowhere to put one.
public record UpdateProfileRequest(
        @NotBlank @Size(max = 80)  String firstName,
        @NotBlank @Size(max = 80)  String lastName,
        @Email                     String email) {}

@PostMapping("/profile")
String update(@Valid @ModelAttribute UpdateProfileRequest form, Principal principal) {
    User user = users.findByUsername(principal.getName());
    user.setFirstName(form.firstName());
    user.setLastName(form.lastName());
    user.setEmail(form.email());
    users.save(user);
    return "redirect:/profile";
}

The three lines of manual mapping are the point, not an overhead. They are the place where a future developer who adds a role field to User has to make a deliberate decision, rather than exposing it by omission. Every one of the five CVEs above is a failure of a mechanism that tried to make that decision automatic.

11Password hashing and credential storage

Spring Security's password storage design solves a problem most frameworks do not attempt: how an application changes its hashing algorithm without asking users to reset their passwords, and without a migration window in which both algorithms are half-deployed.

The answer is DelegatingPasswordEncoder, and the whole mechanism is a prefix. Each stored hash carries its algorithm identifier in braces at the front, and the encoder reads that identifier to decide which delegate verifies the password.53

java
@Bean
PasswordEncoder passwordEncoder() {
    // bcrypt for new hashes; every historical format still verifies.
    return PasswordEncoderFactories.createDelegatingPasswordEncoder();
}

Because the algorithm travels with the hash, a password table can hold six generations of hashing simultaneously. When a user with a legacy {sha256} hash logs in successfully, the application re-encodes their password with the current default and stores it. Over a few months the old format disappears without a single user noticing. Spring Security's documentation is explicit that this design exists because the best practice for password storage will change again, and applications with old encodings cannot easily migrate.53

The prefix being visible to an attacker is not a weakness. Password storage does not rely on the algorithm being secret, and most formats are trivially identifiable from their structure anyway.53

Rate limiting is the companion control, not an optional extra.

Screening against breached passwords

NIST's Digital Identity Guidelines, finalised as SP 800-63B Revision 4 in 2025, reorganised password policy around three ideas: length over composition, no mandatory periodic rotation absent evidence of compromise, and mandatory screening of proposed passwords against lists of known-compromised values.5657 The third is the one that requires implementation work, and Spring Security 6.3 added the API for it.

java
@Bean
CompromisedPasswordChecker compromisedPasswordChecker() {
    return new HaveIBeenPwnedRestApiPasswordChecker();
}

The implementation uses Have I Been Pwned's range search: it sends the first five characters of the password's SHA-1 hash and receives back every matching suffix, comparing locally. The password never leaves the process, and the service learns almost nothing about what was checked.5859

Handle the failure properly

Wiring the bean and stopping there produces a bad experience: a user with a correct-but-breached password gets a 401 or a redirect to /login?error, indistinguishable from a wrong password.53 Catch CompromisedPasswordException in an AuthenticationFailureHandler and route the user into a forced password change that explains what happened. Better still, run the check at registration and password-change time, where the user is already in a flow that expects to be told their password is unacceptable.

12Beyond passwords: passkeys, MFA and bound tokens

The most consequential recent additions to Spring Security are not hardening of the password flow. They are the mechanisms that reduce how much the password matters.

Passkeys

Spring Security ships first-class WebAuthn support, with registration and authentication flows, credential storage abstractions and — as of 7.1 — published authentication events for the WebAuthn path.604 A passkey is a device-bound or synced public-key credential: the server stores a public key, the private key never leaves the authenticator, and the signature is scoped to the origin. That last property is what makes passkeys phishing-resistant in a way no password policy achieves — a credential presented to evil-bank.example simply does not verify against bank.example, regardless of how convincing the page was.

Declarative multi-factor authentication

Spring Security 7 introduced @EnableMultiFactorAuthentication and an authorization model built on required authentication factors. Version 7.1 extended it with AllRequiredFactorsAuthorizationManager.anyOf and with conditions — including MultiFactorCondition.WEBAUTHN_REGISTERED, which requires a second factor only for users who have registered a WebAuthn credential.614 Before this, step-up authentication in Spring applications was a hand-rolled affair involving custom Authentication implementations and a lot of care. It is now configuration.

One-time tokens

One-time-token login — the "magic link" pattern — is built in, with a token repository, a generation endpoint and a submission filter.62 It is most valuable not as a primary authentication method but as a replacement for the password-reset flow, which in most applications is a second, less-scrutinised authentication path with weaker controls than the login it can bypass.

Bearer tokens and the resource server

For APIs, oauth2ResourceServer().jwt() validates signature, issuer, audience and expiry against a JWK set, with the key set fetched and cached from the authorization server.22 Two configuration points are worth stating explicitly because their absence is a common finding.

java
@Bean
JwtDecoder jwtDecoder(OAuth2ResourceServerProperties props) {
    NimbusJwtDecoder decoder = NimbusJwtDecoder
            .withJwkSetUri(props.getJwt().getJwkSetUri()).build();
    decoder.setJwtValidator(JwtValidators.createDefaultWithValidators(
            new JwtIssuerValidator(props.getJwt().getIssuerUri()),
            new JwtClaimValidator<List<String>>("aud",
                    aud -> aud != null && aud.contains("invoices-api"))));
    return decoder;
}

Audience validation is the control that stops a token issued for the marketing site from being replayed against the payments API. Scope-to-authority mapping is the other: by default Spring maps the scope claim to authorities prefixed SCOPE_, which interacts badly with hasRole() if that convention is not understood.22

Spring Security 7 also supports DPoP-bound access tokens, which cryptographically bind a token to a client-held key so that a stolen bearer token cannot be replayed by a different client.63 For high-value APIs this closes the structural weakness of bearer tokens — that possession is the entire authorisation.

Sessions, where they remain

Session fixation protection is on by default: Spring Security changes the session identifier on authentication, so a session id planted by an attacker before login is not the one that ends up authenticated.64 Concurrent-session control, session timeouts and a logoutSuccessHandler that invalidates server-side state complete the picture. For distributed deployments, Spring Session moves the store into Redis or a database so that logout is effective across instances rather than only on the node that handled it.

13Encrypted credentials and secrets management

Spring Boot's externalised configuration model is excellent at getting values into an application and entirely agnostic about where those values came from. A database password can arrive from application.yml, an environment variable, a command-line argument, a config server, a Kubernetes secret mounted as a file, or Vault, and the injecting code cannot tell the difference. That neutrality is a feature; it also means the framework will not stop you putting a production credential in a file that gets committed.

Two mechanisms deserve detailed treatment, because they solve different problems and are frequently confused.

Encrypted configuration properties

Spring Cloud Config Server supports encryption of individual property values. The server exposes /encrypt and /decrypt endpoints; you POST a plaintext value, receive ciphertext, and store it in the configuration repository prefixed with {cipher}.65 Clients receive the decrypted value transparently.

shell
$ curl localhost:8888/encrypt -s -d 'the-real-database-password'
682bc583f4641835fa2db009355293665d2647dade3375c0ee201de2a49f7bda

# application.yml, safe to commit to a git repository:
spring:
  datasource:
    password: '{cipher}682bc583f4641835fa2db009355293665d2647dade3375c0ee201de2a49f7bda'

The key can be symmetric — a single encrypt.key property, conventionally supplied through the ENCRYPT_KEY environment variable to keep it out of plaintext configuration files — or asymmetric, using an RSA key pair in a keystore configured through encrypt.keyStore.*. The asymmetric option is stronger: the public key encrypts, and only the config server holds the private key needed to decrypt.66 For applications outside the Spring Cloud stack, jasypt-spring-boot provides the equivalent with an ENC(...) wrapper resolved by a property-source post-processor.67

What encrypted properties do and do not buy you

They make a configuration repository safe to read. They do not rotate, do not expire, do not audit, and do not revoke. The plaintext still exists in the running JVM's memory and in the Environment. And the whole scheme collapses to a single question: where does the decryption key live? If ENCRYPT_KEY is in the same deployment manifest as the ciphertext, you have re-implemented base64 with extra steps.

External secret stores

The stronger model moves the secret out of configuration entirely. Spring Cloud Vault integrates HashiCorp Vault as a property source through Spring Boot's Config Data API — the modern mechanism, which replaced the older bootstrap context in Spring Cloud Vault 3.0 and Spring Boot 2.4. A single spring.config.import entry mounts Vault's enabled secret backends as properties.68

yaml
spring:
  application:
    name: invoices
  config:
    import: 'vault://'
  cloud:
    vault:
      uri: https://vault.internal:8200
      authentication: KUBERNETES        # not a static token
      kubernetes:
        role: invoices
      kv:
        enabled: true
        backend: secret
      database:                          # dynamic, short-lived credentials
        enabled: true
        role: invoices-readwrite

Three capabilities distinguish this from encrypted properties. Authentication is workload identity — Vault supports token, AppRole, client certificate, Cubbyhole, AWS-EC2, AWS-IAM and Kubernetes authentication, so the application proves who it is rather than presenting a shared secret. Access is audited centrally, so "which service read this credential, and when" is an answerable question. And the database backend generates credentials on demand with a lease: the application receives a username and password created for it, valid for hours, revoked automatically.6869 A credential that expires before it can be traded is a different class of asset from one that has sat in a properties file since 2021.

The same shape applies to AWS Secrets Manager, Azure Key Vault and Google Secret Manager through their respective Spring Cloud integrations, and to Kubernetes Secrets mounted as files and imported via spring.config.import=configtree:/etc/secrets/. Spring Vault also exposes Vault's transit engine, which performs encryption as a service so that application-level field encryption never requires the application to hold a key.69

The operational hygiene that matters more than the mechanism

  • Scan history, not just the working tree. A secret removed in a later commit is still in the repository. Rotate anything that was ever committed; deletion is not remediation.
  • Treat environment variables as semi-public. They appear in process listings, in container inspection output, in crash dumps, and in any log line that dumps the environment on startup. They are a large improvement on committed files and a long way short of a secret store.
  • Mask them in Actuator. /actuator/env and /actuator/configprops sanitise values matching known key patterns by default, and management.endpoint.env.show-values controls the rest. Confirm that a custom property named something like partnerApiToken is actually being masked, rather than assuming the default pattern caught it.
  • Rotate on personnel change, not on a calendar. The event that should trigger rotation is a change in who could have read the secret.

14The operational surface: Actuator and heap dumps

Spring Boot Actuator is the operational surface of a Spring application: health, metrics, environment, thread dumps, heap dumps, loggers, mappings, caches, and — if enabled — shutdown. It is genuinely valuable and it is the single most reliable way to turn a well-written Spring application into a serious breach.

The defaults are conservative. Only /health is exposed over HTTP; the rest require explicit inclusion through management.endpoints.web.exposure.include. If Spring Security is on the classpath and no custom SecurityFilterChain bean is defined, Spring Boot's auto-configuration secures every actuator other than /health. If you define your own chain, that auto-configuration backs off entirely and the access rules become yours.70

The interaction that produces incidents

Those two sentences combine badly. A team adds a custom SecurityFilterChain for ordinary application concerns. Spring Boot's actuator protection silently steps aside. Somebody later sets management.endpoints.web.exposure.include=* to debug a staging problem, and the property survives into production. There is now an unauthenticated /actuator/heapdump on the internet. No single change was obviously wrong.

The Volkswagen case

In December 2024, researchers presenting at the Chaos Computer Club described a data exposure at Cariad, Volkswagen Group's software subsidiary. Terabytes of data on roughly 800,000 electric Audi, Seat, Skoda and Volkswagen vehicles had been reachable from the internet for months, including precise location coordinates for around 460,000 of them — in some cases accurate to within centimetres.71

The entry point is the part that concerns this article. The researcher found an unprotected heap dump from an internal JVM — the kind of artefact an application produces for performance introspection. Inside it, in plaintext, were active AWS credentials. Those credentials led to the storage holding the vehicle data.72 Secondary analyses of the incident trace the exposure specifically to an unsecured Spring Boot Actuator endpoint on a discoverable subdomain.73

A heap dump is a serialisation of everything the process is holding. Every credential the application has read, every token it has cached, every password that passed through a request parameter, sitting in a file that a single unauthenticated GET will hand over.

This is not a Spring vulnerability. Every component behaved as documented. It is the canonical example of the third category from the opening section: the framework had no opinion, the decision was the application's, and the decision was made by nobody in particular.

A defensible Actuator configuration

yaml
management:
  server:
    port: 9090                        # separate port; do not route it from the internet
  endpoints:
    web:
      base-path: /internal/actuator
      exposure:
        include: health,info,prometheus   # enumerate. never '*'
  endpoint:
    health:
      show-details: when-authorized
      probes:
        enabled: true
    shutdown:
      enabled: false
  info:
    env:
      enabled: false                  # do not echo the environment into /info
java
@Bean
@Order(0)
SecurityFilterChain actuatorChain(HttpSecurity http) throws Exception {
    http
        .securityMatcher(EndpointRequest.toAnyEndpoint())
        .authorizeHttpRequests(auth -> auth
            .requestMatchers(EndpointRequest.to(HealthEndpoint.class)).permitAll()
            .anyRequest().hasRole("OPS"))
        .httpBasic(Customizer.withDefaults())
        .csrf(csrf -> csrf.disable());
    return http.build();
}

One caveat on EndpointRequest: the March 2026 advisory batch included CVE-2026-22731, an authentication bypass under Actuator health group paths, and CVE-2026-22733, a bypass affecting Actuator CloudFoundry endpoints.38 The matcher machinery is itself security-relevant code and has had bugs. Network-level isolation — binding the management port to an internal interface — is the control that does not depend on getting the matcher right.

Endpoints to treat as never-exposed: heapdump, threaddump, env, configprops, beans, loggers (it accepts POST and can change log levels at runtime), mappings, and shutdown.

15The dependency surface

A typical Spring Boot application contains a few thousand lines written by its team and several hundred megabytes written by other people. OWASP's 2025 revision recognised this by promoting the former "Vulnerable and Outdated Components" category into Software Supply Chain Failures at A03, broadening it from known-vulnerable dependencies to the whole ecosystem — build systems, distribution infrastructure and the trust relationships between them. It carries the highest incidence rate in the contributed data.1517

What Spring gives you

The dependency-management BOM is an underrated security feature. spring-boot-dependencies pins a coherent, tested set of versions for several hundred libraries, so upgrading Spring Boot's patch version upgrades Tomcat, Jackson, Hibernate, Logback and the rest as a set. Applications that override individual versions to work around a build issue give up that property, usually permanently.

Since Spring Boot 3.3, SBOM generation is built in. Adding the CycloneDX Maven or Gradle plugin is enough — Boot detects it, configures it, embeds the resulting document in the jar, and can expose it at /actuator/sbom.7475 The jar manifest advertises the SBOM's location and format so downstream tooling can find it.74

xml
<plugin>
  <groupId>org.cyclonedx</groupId>
  <artifactId>cyclonedx-maven-plugin</artifactId>
</plugin>

An SBOM is a manifest, not a control. Its value is realised when it is fed to something that compares it against advisory data continuously — OWASP Dependency-Track for a running inventory, OWASP Dependency-Check or a commercial scanner in the pipeline.767778 The question an SBOM answers is the one that mattered during Log4Shell and Spring4Shell: which of our four hundred services contain this library, at which version, right now.

Patch cadence as a security control

The Spring portfolio's advisory volume is not static. In 2025 Spring Security published two CVEs. In the first four months of 2026, one vendor tracking the ecosystem counted roughly thirty across the portfolio in two months — including batched, multi-CVE advisories where eight Spring Boot issues were disclosed on a single day and seven Spring Security issues two days earlier — attributing the increase in part to improved, partly AI-assisted vulnerability research against mature Java frameworks.79 The March 2026 batch discussed earlier is one instance of that pattern.38

Whether or not that rate persists, the operational implication is straightforward. A patch cadence that assumed two or three relevant advisories a year does not survive a monthly batch. Practically:

  • Subscribe to the source. Spring publishes advisories at spring.io/security with affected ranges and fix versions.80 This is the authoritative feed; aggregators lag it.
  • Track the support window, not just the version. Open-source patches stop at end-of-life; Spring Boot 3.2 reached OSS EOL at the end of 2024 and 3.x support is winding down.5 Running an EOL branch means the fix for the next critical CVE will exist only behind a commercial agreement.
  • Automate the small upgrades. Dependabot or Renovate on the Boot version, with a test suite you trust, converts patching from a project into a merge.
  • Fail the build on known-exploited vulnerabilities rather than on CVSS score. Severity alone produces alert fatigue; exploitation status produces a short list.

16Testing the security configuration

Security controls that are not tested are configuration opinions. Spring Security's testing support exists precisely so that authorization rules can be asserted the way business logic is. It supplies request post-processors for mocked principals and for supplying — or deliberately withholding — a valid CSRF token, and it is thin enough that there is no excuse for skipping it.8182

java
@WebMvcTest(InvoiceController.class)
@Import(SecurityConfig.class)              // the real configuration, not a stub
class InvoiceControllerSecurityTest {

    @Autowired MockMvc mvc;

    @Test
    void anonymousIsRedirectedToLogin() throws Exception {
        mvc.perform(get("/invoices"))
           .andExpect(status().is3xxRedirection());
    }

    @Test
    @WithMockUser(roles = "USER")
    void userCannotReachAdminConsole() throws Exception {
        mvc.perform(get("/admin/users"))
           .andExpect(status().isForbidden());
    }

    @Test
    @WithMockUser(roles = "USER")
    void postWithoutCsrfTokenIsRejected() throws Exception {
        mvc.perform(post("/invoices").param("amount", "100"))
           .andExpect(status().isForbidden());
    }

    @Test
    @WithMockUser(roles = "USER")
    void postWithCsrfTokenSucceeds() throws Exception {
        mvc.perform(post("/invoices").param("amount", "100").with(csrf()))
           .andExpect(status().is3xxRedirection());
    }

    @Test
    @WithMockUser(roles = "USER")
    void securityHeadersArePresent() throws Exception {           // see CVE-2026-22732
        mvc.perform(get("/invoices").with(user("u")))
           .andExpect(header().string("X-Content-Type-Options", "nosniff"))
           .andExpect(header().exists("Content-Security-Policy"));
    }
}

Four points about writing these well.

Import the real security configuration. A test that runs against a permissive test profile proves nothing about production. @WebMvcTest plus an explicit @Import of the actual SecurityConfig is the combination that tests the thing you deploy.

Assert the negative. The valuable test is the one that fails when a rule is deleted. "A user without the role gets 403" catches regressions; "a user with the role gets 200" does not.

Test method security separately. @WithMockUser works with @PreAuthorize in a service-layer test, and given CVE-2025-41248 — where annotations on generic hierarchies were silently not discovered — a direct test that an unauthorised principal is rejected at the service boundary is worth having independently of the controller test.8120

Assert on headers. The March 2026 header omission is the argument. Configuration that requests a header is not evidence that the header is written.

Beyond unit tests

Static analysis catches the patterns that reviews miss at scale. Find Security Bugs, a SpotBugs plugin, carries Java-specific detectors including the SpEL-injection pattern that originally surfaced CVE-2018-1273 during a scan of Spring components.8342 Semgrep's rule sets cover Spring idioms such as th:utext on unsanitised values and concatenated SQL in JdbcTemplate calls.84 OWASP ZAP provides dynamic scanning in a pipeline and is the practical way to verify headers, cookie flags and CSP against a deployed instance rather than against a configuration file.85

18What holds up in practice

Spring Security's defaults are among the best in any web framework, which produces a specific and recurring failure mode: teams inherit a strong baseline, never examine it, and then weaken it in three or four small, individually reasonable steps. Nothing in this article is exotic. The whole of it reduces to knowing which layer owns which decision, and checking that the layer is actually doing what the configuration says.

The review

Points that have caught real problems, roughly in the order they are cheapest to check.

  • Read the resolved filter chains. Turn on DEBUG for org.springframework.security once and read what Spring Boot prints. Confirm chain order and that no broad matcher shadows a narrower one.
  • Confirm the deny-by-default backstop. Every chain ends with anyRequest().authenticated() or denyAll().
  • Justify every csrf.disable(). The test is whether the chain accepts an ambient credential, not whether it returns JSON.
  • Grep for th:utext. Each occurrence either renders trusted markup your code produced or passes through a real HTML sanitiser.
  • Confirm a Content Security Policy exists and that it does not contain 'unsafe-inline' in script-src. Check object-src and base-uri are set.34
  • Assert security headers in a test. CVE-2026-22732 is the reason this is not paranoia.36
  • Search for entities bound to requests. Any @ModelAttribute or @RequestBody whose type is a JPA entity is a finding; the fix is a purpose-built record and explicit mapping.46
  • Search for concatenation into query strings. Focus on ORDER BY, dynamic table names and anything built from a Pageable.
  • Search for SpEL built from input — in @Query, in @PreAuthorize, in template names.41
  • Check the password encoder is delegating and that the work factor has been tuned on production-class hardware rather than left at the decade-old default.53
  • Enumerate Actuator exposure. Confirm include is a list, not *; confirm the management port is not internet-routable; confirm a chain exists for EndpointRequest.toAnyEndpoint() if any custom chain exists.70
  • Trace one production secret from source to use. Whatever the answer is, it is the real secrets policy.
  • Check the Spring Boot version against the support window and confirm somebody receives the advisory feed.805

What the CVE record actually teaches

Three patterns recur across every advisory cited here, and they are more durable than any specific configuration.

Blocklists erode; allow-lists do not. Fifteen years of data-binder CVEs — 2010, 2022, 2022 again, 2024, 2025 — are five attempts to enumerate what must not bind, each defeated by a path the enumerators had not thought of: a new JDK method, a case variation, a locale-dependent lowercasing.485152 Not one of them touched setAllowedFields or constructor binding. The same asymmetry governs sort columns, template names and CORS origins.

Silent failures are the expensive ones. CVE-2025-41248 caused method security annotations not to be discovered; CVE-2026-22732 caused configured headers not to be written. Both produced successful responses and no errors. Controls whose failure mode is invisible need external verification — which is the entire argument for asserting on the response rather than trusting the configuration.2036

The framework's boundary is where the incidents are. Spring did nothing wrong at Cariad. Every component behaved exactly as documented. An endpoint that ships disabled was enabled, a port that should have been internal was not, and a file containing everything the process was holding was served to anyone who asked.7273 The defaults were never the problem. The problem was that nobody owned the decision to change them.

Twenty-three years of accumulated defaults will carry an application a long way. They will not carry it past the first place where somebody had to decide something and did not notice they were deciding.
