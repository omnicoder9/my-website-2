Spring MVC is often described as "the annotation-driven web layer of Spring," which is true and almost entirely uninformative. What it actually is: a single servlet that owns the request, plus six or seven pluggable contracts that the servlet consults in a fixed order. Every feature in the programming model — path variables, JSON binding, validation, exception translation, template rendering — is an implementation of one of those contracts. Once you can name them, the framework stops being a bag of annotations and becomes a small, legible state machine. This article works through that machine at implementation depth, current as of the Spring Framework 7 generation.

/mvc/why-a-front-controller01

A front controller, and why this one outlived its cohort

The vocabulary comes from Trygve Reenskaug's 1979 Xerox PARC note describing Models, Views and Controllers as a way of separating a user's mental model of a domain from its on-screen representation and from the input handling that mediates between them.1 Web frameworks borrowed the three words and changed almost all of the mechanics: there are no observers pushing updates to views, and the "controller" is not a long-lived object tracking input devices but a method invoked once per HTTP exchange. What web MVC actually inherits is the classification, not the collaboration pattern.2

The structural idea that matters more is Front Controller: route every request through one handler that centralizes the concerns nobody wants duplicated — locale resolution, security gating, error handling, view selection — and dispatch from there to per-request logic.3,4 Rod Johnson's 2002 critique of contemporary J2EE practice argued that the servlet API was a reasonable foundation being badly used, and shipped an interface-driven web layer as part of the argument; that layer became Spring MVC when the framework was extracted from the book's codebase.5

Three design commitments from that period explain why the same architecture is still in the box more than twenty years later.

Contracts, not classes. HandlerMapping, HandlerAdapter, ViewResolver, HandlerExceptionResolver and View are interfaces the dispatcher discovers from the application context by type.6 The annotated-controller programming model is not privileged machinery; it is one HandlerMapping and one HandlerAdapter pair (RequestMappingHandlerMapping and RequestMappingHandlerAdapter) registered by default.7 That is why the programming model could change radically — from Controller interfaces, to @RequestMapping, to ResponseEntity, to ProblemDetail — without ever changing the dispatcher.

No required base class. A handler is any object; the adapter's job is to know how to call it. Testability follows: a controller method that takes a domain command object and returns a domain result is a plain method with plain arguments.

Deference to the servlet contract. Spring MVC never tried to replace the container. It targets Jakarta Servlet, so it runs on Tomcat, Jetty, or anything else that implements the specification.8,9 The cost is that the model is thread-per-request and blocking by construction; the benefit is thirty years of accumulated container engineering, and an escape hatch to raw HttpServletRequest whenever abstraction fails you.

Where the 7.x generation sits

Spring Framework 7.0 went GA on 13 November 2025 as the foundation for Spring Boot 4.0.10,11 It retains a JDK 17 baseline while recommending JDK 25, and raises the Jakarta EE floor to EE 11: Servlet 6.1, JPA 3.2, Bean Validation 3.1.12,13 Several changes in that release are directly relevant to everything below:

  • The legacy AntPathMatcher variant for matching HTTP request mappings is deprecated, completing a migration to parsed PathPattern that began in 5.0; the last blocking gap — matching many leading segments, as in /**/pages/index.html — is now closed.12
  • Path-extension content negotiation and suffix pattern matching, deprecated since 6.0, are removed outright.12
  • Jackson 3 (package tools.jackson) is the default JSON stack, with Jackson 2 support deprecated and slated for removal.14,15
  • API versioning becomes a first-class request-mapping condition on both the server and client sides.16,17
  • The <mvc:*> XML configuration namespace is deprecated in favour of the Java configuration model, and RestTemplate is deprecated in the reference documentation ahead of an @Deprecated marking in 7.1.12,18
Terminology

"Spring MVC" names the servlet stack in spring-webmvc. Spring WebFlux is a separate, reactive stack in spring-web/spring-webflux that reuses the annotation programming model on a non-blocking runtime.19 The two share annotations but not a dispatcher; almost nothing in this article about DispatcherServlet internals transfers to DispatcherHandler.

/mvc/lifecycle02

The lifecycle, in the order the dispatcher executes it

Everything else in this article is a zoom on one of the stages below. It is worth reading the sequence once as a whole, because most confusing Spring MVC behaviour is a stage-ordering question in disguise: why did my interceptor not see the header I set? why is my exception handler returning HTML? why did a 406 come back before my method ran?

In source terms, DispatcherServlet.doDispatch is a readable ninety-line method, and reading it is the single highest-leverage hour you can spend on this framework.20 Its shape:21

  1. Multipart check. If the request is multipart/form-data, it is wrapped in a MultipartHttpServletRequest so parts are available as parameters and files.22,23
  2. Handler lookup. Each HandlerMapping is consulted in order until one returns a HandlerExecutionChain — the handler plus the interceptors that apply to it. No chain means no handler, which surfaces as a 404.
  3. Adapter lookup. Each HandlerAdapter is asked whether it supports the handler object. For an annotated controller this is RequestMappingHandlerAdapter.
  4. Conditional GET short-circuit. For GET and HEAD, Last-Modified handling can end the exchange with a 304 before invocation.24
  5. preHandle. Interceptors run in registration order. Any of them returning false ends the dispatch; the framework assumes that interceptor has written the response.25
  6. Invocation. The adapter resolves arguments, calls the method reflectively, and processes the return value, producing a ModelAndView or nothing at all if the response was already written.
  7. Default view name. If the method returned a model without a view name, a RequestToViewNameTranslator derives one from the path.
  8. postHandle. Interceptors run in reverse order, before rendering.
  9. Render. The view name is resolved through the ViewResolver chain and View.render writes the body.26
  10. Exception path. Anything thrown between steps 5 and 9 goes to the HandlerExceptionResolver chain, whose output is itself rendered as a view or a body.27
  11. afterCompletion. Interceptors run in reverse order with the exception, if any — the reliable place for cleanup.

Two consequences deserve emphasis up front. First, the @ResponseBody path short-circuits steps 7–9 entirely: the return value handler writes the body inside the adapter, so by the time postHandle runs the response is typically already committed.28 That is why adding a header in postHandle silently does nothing for REST endpoints, and why ResponseBodyAdvice exists as the supported alternative.25 Second, mapping conditions are evaluated before your method exists in the picture at all — a 415 or 406 is a statement about the mapping table, not about your code.

/mvc/dispatcher-servlet03

Bootstrapping, three ways

The classic deployment declares the servlet in web.xml. The Servlet 3.0+ programmatic route replaces that with a WebApplicationInitializer discovered through the container's ServletContainerInitializer mechanism, and Spring provides a base class that wires both contexts:8,29

javaClassic WAR bootstrap with a parent/child context split
public class AppInitializer extends AbstractAnnotationConfigDispatcherServletInitializer {

    @Override
    protected Class<?>[] getRootConfigClasses() {
        return new Class<?>[] { PersistenceConfig.class, ServiceConfig.class };
    }

    @Override
    protected Class<?>[] getServletConfigClasses() {
        return new Class<?>[] { WebConfig.class };   // controllers, resolvers, converters
    }

    @Override
    protected String[] getServletMappings() {
        return new String[] { "/" };                 // default servlet mapping, not /*
    }

    @Override
    protected Filter[] getServletFilters() {
        return new Filter[] { new CharacterEncodingFilter("UTF-8", true) };
    }
}

The mapping matters. "/" is the default servlet mapping: it wins only where no more specific mapping applies, so the container's own default servlet no longer serves static content and Spring's resource handling takes over. "/*" is a path mapping that swallows forwards to JSPs and will break view rendering.

Spring Boot removes the ceremony: DispatcherServletAutoConfiguration registers the servlet against / in a single application context, and configuration moves to properties and WebMvcConfigurer beans.30 Note the distinction that trips up every Boot user once: adding @EnableWebMvc to a Boot application switches off WebMvcAutoConfiguration and you inherit the framework defaults instead of Boot's — losing static resource handling, the configured message converters, and error page wiring.31,30

The two-context hierarchy is still worth understanding even though Boot flattens it. Child contexts see parent beans; parents cannot see children. That asymmetry is what lets several dispatchers (one for an admin UI, one for a public API, each with its own converters and resolvers) share a single set of services and a single DataSource. It is also why a @Bean defined in the servlet context is invisible to a ContextLoaderListener-loaded security configuration in the root context — the historical source of "my @Transactional proxy is not being applied to my controller" bug reports.29

Practice

Prefer WebMvcConfigurer callbacks over redefining RequestMappingHandlerAdapter or the converter list from scratch. Custom argument resolvers and return value handlers registered through the configurer are appended after the built-ins, which means a built-in resolver that also claims your parameter type will win. When you need to pre-empt one, wrap or reorder the list on the adapter directly via WebMvcRegistrations.

/mvc/handler-mapping04

Handler mapping: a conjunction of typed conditions

RequestMappingHandlerMapping builds its registry at startup by scanning every @Controller bean for methods carrying @RequestMapping metadata and converting each into a RequestMappingInfo. That object is not a string. It is a composite of independent conditions, each of which knows how to test itself against a request, how to produce a narrower version of itself, and how to compare itself with a competing condition.32

At request time the mapping computes all matching infos, sorts them with the composite comparator, and takes the best. If the top two compare as equal, the framework throws rather than choose arbitrarily — a startup-adjacent failure surfacing at request time, and always a sign of an ambiguous mapping table.

Path patterns

Paths are parsed once into a PathPattern tree and matched against a parsed RequestPath, rather than re-parsed per request as string matching. This is faster, and it removes an entire family of encoding and traversal ambiguities that dogged AntPathMatcher. As of 7.0 the string matcher is deprecated for request mapping.12 The syntax:32,33

Removed behaviour

Suffix pattern matching (/orders also matching /orders.json), registered-suffix matching, trailing-slash matching, and path-extension content negotiation are all removed in 7.0 after deprecation in 6.0.12 Applications that relied on /api/orders/ and /api/orders both resolving must now either declare both patterns or normalise in a filter. This is a behavioural break with real migration cost, and it was made deliberately: implicit path variants are a well-known source of security-filter bypasses, because the authorization layer and the mapping layer can disagree about what a URL means.34

Beyond patterns

The remaining conditions are what turn a mapping table into a genuine dispatch language. consumes constrains Content-Type; produces participates in content negotiation and pre-filters on Accept; params and headers allow presence, absence (!draft) and equality (version=2) predicates. Because these are mapping conditions rather than method logic, a mismatch produces a 415, 406 or 404 without invoking your code, and it does so consistently across every controller in the application.32

/mvc/handler-adapter05

Handler adaptation: where HTTP becomes a method call

The HandlerAdapter contract is three methods — supports(Object), handle(request, response, handler), and a legacy getLastModified — and it is the reason Spring MVC could keep its dispatcher while replacing its programming model twice. SimpleControllerHandlerAdapter still supports the original Controller interface; HttpRequestHandlerAdapter supports raw HttpRequestHandler objects, which is how static resources are served; HandlerFunctionAdapter supports functional routes.7,35 The one that matters for annotated controllers is RequestMappingHandlerAdapter.

Its inner loop is a pair of ordered strategy lists. Argument resolution asks each HandlerMethodArgumentResolver whether it supports a MethodParameter, and the first one that says yes owns it. Return handling does the same with HandlerMethodReturnValueHandler. Both lists are cached per parameter and per return type after first use.36,37

Two objects thread through the invocation and explain most of the surprising behaviour:

  • ModelAndViewContainer holds the model, the view (name or instance), a response status, and a requestHandled flag. When RequestResponseBodyMethodProcessor writes a body it sets that flag, which is precisely how the dispatcher learns to skip view resolution.
  • WebDataBinderFactory creates a WebDataBinder per bound argument, applying the controller's @InitBinder methods (local first, then those from @ControllerAdvice) before binding starts.38

Adding your own resolver

Custom argument resolvers are the cleanest way to lift a cross-cutting concern out of every signature in an application — a tenant identifier, a resolved caller, a pagination cursor parsed from three parameters. The contract is two methods:

    @Override
    public boolean supportsParameter(MethodParameter parameter) {
        return parameter.getParameterType().equals(TenantId.class)
                && parameter.hasParameterAnnotation(CurrentTenant.class);

                                  ModelAndViewContainer mavContainer,

/mvc/interception06

Filters and interceptors are not interchangeable

Both wrap request handling; they wrap different things, at different times, with different information available.

A Filter is a servlet contract. It sees the request before any Spring code does, can wrap or replace the request and response objects, applies to every dispatch type it is registered for (including FORWARD, INCLUDE, ERROR and ASYNC), and runs whether or not a handler is ever found. Spring Security is implemented as a filter chain for exactly this reason: authorization decisions must not depend on Spring MVC having successfully mapped the request.34,8

A HandlerInterceptor is a Spring MVC contract, invoked only when a handler has been matched, and given the handler object itself. That access is the reason to prefer it: preHandle can read annotations on the target method and decide accordingly, which a filter cannot do without duplicating the mapping logic.25

javaAn interceptor that reads metadata from the matched handler
public class RateLimitInterceptor implements HandlerInterceptor {

    private final RateLimiter limiter;

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response,
                             Object handler) throws Exception {

        if (!(handler instanceof HandlerMethod hm)) {
            return true;                       // static resource or router function
        }
        RateLimited annotation = hm.getMethodAnnotation(RateLimited.class);
        if (annotation == null) {
            annotation = hm.getBeanType().getAnnotation(RateLimited.class);
        }
        if (annotation == null) {
            return true;
        }
        if (!limiter.tryAcquire(key(request), annotation.permitsPerMinute())) {
            response.setStatus(HttpStatus.TOO_MANY_REQUESTS.value());
            response.setHeader("Retry-After", "60");
            return false;                      // dispatch ends here; nothing else runs
        }
        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response,
                                Object handler, Exception ex) {
        // Runs even when the handler threw. The right place for cleanup and metrics.
    }
}

Two framework filters deserve explicit mention because they solve problems people otherwise solve badly. ShallowEtagHeaderFilter buffers the rendered response, hashes it, and answers conditional requests with a 304 — it saves bandwidth, never computation.24 ForwardedHeaderFilter applies Forwarded / X-Forwarded-* headers to the request so that generated links are correct behind a proxy; without it, UriComponentsBuilder will happily build http://localhost:8080 links in production.39

/mvc/controllers07

@Controller and @RestController

@Controller is a @Component stereotype. Its only mechanical effect is to make the bean eligible for component scanning and to mark it as a candidate for RequestMappingHandlerMapping's detection pass. Everything else — the mappings, the argument binding, the return handling — comes from the method-level metadata. There is no base class, no lifecycle interface, and no required constructor.42

@RestController is a composed annotation: @Controller plus @ResponseBody at type level.28 That single difference changes the return-value contract for every method in the class — a returned String stops being a view name and becomes a response body written by StringHttpMessageConverter. The most common Spring MVC bug in mixed applications is precisely this: a @RestController that returns "redirect:/login" and produces a 200 response whose body is the literal text redirect:/login.

Statelessness and threading

Controllers are singletons by default and are invoked concurrently on container threads. Mutable instance state is a data race; the framework offers no protection and will not warn you. Per-request state belongs in method arguments and locals, per-conversation state in the session (declared with @SessionAttributes, and mutated under the SessionStatus contract), and per-user state in the security context.43 The alternative — @Scope("request") beans injected into a singleton controller — works via scoped proxies but pays a proxy indirection on every access and hides the request dependency from the signature.

Constructor injection is the right default: it makes the collaborators explicit, allows final fields, and produces a class that can be instantiated in a unit test with new.

javaA complete, idiomatic REST controller
@RestController
@RequestMapping(path = "/api/orders", produces = MediaType.APPLICATION_JSON_VALUE)
@Validated                                     // enables method-level constraint validation
class OrderController {

    private final OrderService orders;

    OrderController(OrderService orders) {     // constructor injection, no @Autowired needed
        this.orders = orders;
    }

    @GetMapping("/{id}")
    OrderView byId(@PathVariable UUID id) {
        return orders.find(id)
                .map(OrderView::of)
                .orElseThrow(() -> new OrderNotFoundException(id));
    }

    @GetMapping
    PagedView<OrderView> search(
            @RequestParam(defaultValue = "") String customer,
            @RequestParam(defaultValue = "0") @Min(0) int page,
            @RequestParam(defaultValue = "20") @Min(1) @Max(200) int size,
            @RequestParam(required = false) @DateTimeFormat(iso = ISO.DATE) LocalDate placedAfter) {

        return PagedView.of(orders.search(customer, placedAfter, PageRequest.of(page, size)));
    }

    @PostMapping(consumes = MediaType.APPLICATION_JSON_VALUE)
    ResponseEntity<OrderView> create(@RequestBody @Valid CreateOrder command,
                                     UriComponentsBuilder uri) {

        Order created = orders.place(command);
        URI location = uri.path("/api/orders/{id}").buildAndExpand(created.id()).toUri();
        return ResponseEntity.created(location).body(OrderView.of(created));
    }

    @PatchMapping(path = "/{id}", consumes = "application/merge-patch+json")
    OrderView patch(@PathVariable UUID id, @RequestBody JsonNode patch) {
        return OrderView.of(orders.merge(id, patch));
    }

    @DeleteMapping("/{id}")
    @ResponseStatus(HttpStatus.NO_CONTENT)
    void cancel(@PathVariable UUID id, @RequestHeader(name = "If-Match", required = false) String etag) {
        orders.cancel(id, etag);
    }
}

Three details in that listing are deliberate. ResponseEntity.created(location) sets both the status and the Location header, which RFC 9110 requires of a 201 response identifying a new resource.44 The @PatchMapping declares a specific patch media type as a consumes condition, so a client sending the wrong patch dialect gets a 415 rather than silent misbehaviour. And @Validated at class level turns the constraints on page and size into enforced method validation — without it, those annotations on simple parameters are inert decoration.45

/mvc/request-inputs08

Path variables, parameters, bodies and negotiation

Path variables

URI template variables are extracted during matching and stored as a request attribute, so @PathVariable resolution is a map lookup rather than a re-parse. Values are converted through the ConversionService, which means a UUID, LocalDate or custom identifier type binds directly and a malformed value raises MethodArgumentTypeMismatchException — a 400, not a 500.36,46

Request parameters and multipart

@RequestParam reads the servlet parameter map, which merges the query string with a form-encoded body. Two consequences follow. A POST with an application/x-www-form-urlencoded body binds to @RequestParam without any Spring-specific machinery, because the container already parsed it. And for any other body type, reading parameters after reading the body may yield nothing — the stream is consumed once.

Multipart requests are handled by StandardServletMultipartResolver, delegating to the container's own Servlet 3.0+ part parsing.22,23 Files bind to MultipartFile; a JSON part binds through the message converters with @RequestPart:

javaMixed multipart upload: metadata as JSON, payload as a file
@PostMapping(path = "/documents", consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
ResponseEntity<DocumentView> upload(
        @RequestPart("metadata") @Valid DocumentMetadata metadata,   // converted from JSON
        @RequestPart("file") MultipartFile file,                     // raw part
        @RequestParam(defaultValue = "false") boolean overwrite) throws IOException {

    if (file.isEmpty()) {
        throw new EmptyUploadException(file.getOriginalFilename());
    }
    try (InputStream in = file.getInputStream()) {                   // never getBytes() on large files
        return ResponseEntity.ok(DocumentView.of(store.save(metadata, in, overwrite)));
    }
}
Caution

MultipartFile.getOriginalFilename() is attacker-controlled. Treat it as an untrusted string: never concatenate it into a filesystem path, and never echo it into HTML without escaping.47 Container-level limits (spring.servlet.multipart.max-file-size and its request-level sibling) are your first defence against upload-based resource exhaustion, and exceeding them raises MaxUploadSizeExceededException before your method runs.30

Negotiation and the shape of the response

Since 7.0 removed path-extension strategies, negotiation is driven by the Accept header by default, optionally supplemented by a query parameter strategy that you opt into explicitly.12,31 The resolved media types are intersected with the produces condition and with what the converters can actually write; the first match wins.

On the writing side, prefer ResponseEntity when status or headers vary, and a bare object when they do not. ResponseEntity composes cleanly with conditional requests:

javaConditional GET handled explicitly
@GetMapping("/{id}")

    Order order = orders.require(id);
    return ResponseEntity.ok()
            .eTag("\"" + order.version() + "\"")
            .lastModified(order.updatedAt())
            .cacheControl(CacheControl.maxAge(Duration.ofMinutes(5)).cachePrivate())
            .body(OrderView.of(order));
}

// Or let the framework decide, short-circuiting before the body is built:
@GetMapping("/{id}/summary")

    long updated = orders.lastModified(id);
    if (request.checkNotModified(updated)) {
        return null;                    // 304 already written; no body produced
    }
    return ResponseEntity.ok(orders.summary(id));
}

The model, data binding, and the objects that carry state

The Model in Spring MVC is a Map<String, Object> with an opinion about naming. Attributes placed in it are visible to the view during rendering, and — for the HTML case — to the form-binding tags that redisplay user input. Three annotations populate it, and the interaction between them is where the model gets interesting.43

@ModelAttribute in its two roles

On a method, @ModelAttribute declares a contributor that runs before every handler method in the controller (or, on a @ControllerAdvice, in every controller it applies to). On a parameter, it declares an object that should be constructed and populated from request parameters.43

javaBoth roles, and the lookup order for the parameter case
@Controller
@RequestMapping("/orders")
@SessionAttributes("draft")                       // keep "draft" across requests of a wizard
class OrderFormController {

    // Contributor: runs before each handler, result lands in the model under "warehouses".
    @ModelAttribute("warehouses")
    List<Warehouse> warehouses() {
        return catalogue.warehouses();
    }

    @GetMapping("/new")
    String form(Model model) {
        model.addAttribute("draft", new OrderDraft());
        return "orders/form";
    }

    // Parameter: resolved by looking in (1) the model, (2) the session via @SessionAttributes,
    // (3) a URI variable or request parameter matching the name, (4) a new instance.
    @PostMapping("/new")
    String submit(@ModelAttribute("draft") @Valid OrderDraft draft,
                  BindingResult binding,          // MUST be the next parameter
                  SessionStatus status,
                  RedirectAttributes redirect) {

        if (binding.hasErrors()) {
            return "orders/form";                 // redisplay with errors and rejected values
        }
        UUID id = orders.place(draft);
        status.setComplete();                     // clears the session attribute
        redirect.addFlashAttribute("message", "Order " + id + " placed");
        return "redirect:/orders/" + id;
    }
}

The adjacency rule for BindingResult is not a style preference. The adapter resolves arguments left to right and associates an Errors argument with the immediately preceding model attribute; insert anything between them and you get an IllegalStateException at invocation time.45

Flash attributes

A redirect is a new request, so the model does not survive it. Flash attributes are stored by the FlashMapManager before the redirect and merged into the model of the subsequent request, then removed — the standard solution to the post/redirect/get pattern's message problem.6 Note the distinction between RedirectAttributes.addAttribute (becomes a query parameter, visible and bookmarkable) and addFlashAttribute (survives once, invisibly, via the session).

WebDataBinder: conversion, allow-lists and formatting

Binding a flat set of string request parameters onto a typed object graph is the job of WebDataBinder, which combines a ConversionService, a set of PropertyEditors for legacy cases, and a policy for which fields may be bound.50,46

The security-relevant knob is the allow-list. By default a binder will set any writable property matching a submitted parameter name, which is mass assignment by another name.49 @InitBinder is where you constrain it:38

javaConstraining and customising a binder
@InitBinder("draft")
void initDraftBinder(WebDataBinder binder) {

    // Allow-list beats deny-list: unknown future fields are refused by default.
    binder.setAllowedFields("customerReference", "requestedDelivery", "lines*", "note");

    // Fail loudly if a parameter targets a field outside the list.
    binder.setDisallowedFields("id", "status", "createdBy");

    // Reject empty strings as null rather than binding "" into a String field.
    binder.registerCustomEditor(String.class, new StringTrimmerEditor(true));

    // A per-controller formatter, without touching global configuration.
    binder.addCustomFormatter(new DateFormatter("dd/MM/yyyy"), "requestedDelivery");
}

Constructor binding deserves a note: when the target type has a single non-default constructor — as records do — the binder resolves each constructor argument by name and instantiates directly, rather than instantiating and then setting properties. Immutable command objects therefore bind correctly, and the "value must be settable" constraint that historically forced mutable form beans is gone.50

Validation: Bean Validation, Spring Validators, and where each fires

Spring MVC does not implement validation. It integrates two independent systems and gives them a common error model.45

  • Jakarta Validation (formerly Bean Validation, JSR 303 in 2009 and JSR 380 in 2017, now Jakarta Validation 3.1 in the EE 11 platform) — declarative constraint annotations, evaluated by a provider, almost always Hibernate Validator.52,53,54,55 Spring Framework 7 requires Jakarta Validation 3.1 and Hibernate Validator 9.12

Both write into the same Errors/BindingResult object, so a view or an error handler does not need to know which produced a given message.

What happens when validation fails

This is the single most consequential branch in the programming model, and it is decided by your method signature.45

  • BindingResult present immediately after the validated argument: the method is invoked with the errors attached. Correct for HTML forms, where you want to redisplay the form. Dangerous for JSON APIs: forget to call hasErrors() and you have shipped an endpoint that accepts invalid input with a 200.
  • Absent: the framework throws. MethodArgumentNotValidException for @RequestBody and @ModelAttribute arguments, HandlerMethodValidationException for constraints on simple parameters, both translated to 400 by DefaultHandlerExceptionResolver.40

Spring Framework 6.1 unified the second case: constraints declared directly on controller method parameters are now validated by the framework itself, with violations reported per-parameter through HandlerMethodValidationException rather than surfacing as a raw ConstraintViolationException with no HTTP meaning.57,45 That is why @Min(0) int page in the earlier controller listing produces a clean 400 rather than a 500.

@Documented
@Constraint(validatedBy = SkuExistsValidator.class)
@Target({ElementType.FIELD, ElementType.PARAMETER, ElementType.RECORD_COMPONENT})
@Retention(RetentionPolicy.RUNTIME)
public @interface SkuExists {
    String message() default "{catalogue.sku.unknown}";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

@Component
public class SkuExistsValidator implements ConstraintValidator<SkuExists, String> {

    private final CatalogueRepository catalogue;

    public SkuExistsValidator(CatalogueRepository catalogue) {   // injected by Spring
        this.catalogue = catalogue;
    }

    @Override
    public boolean isValid(String sku, ConstraintValidatorContext context) {

            return true;               // null-handling belongs to @NotNull, not here
        }
        if (catalogue.exists(sku)) {
            return true;
        }
        context.disableDefaultConstraintViolation();
        context.buildConstraintViolationWithTemplate("{catalogue.sku.unknown}")
               .addConstraintViolation();
        return false;
    }

Cross-field rules go at class level, because a field validator cannot see its siblings. Attach the violation to a specific property node so the message renders next to the right input rather than as a global error:

@Documented
@Constraint(validatedBy = DateRangeValidator.class)
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
public @interface ValidDateRange {
    String message() default "End date must be on or after the start date";
    String start() default "start";
    String end() default "end";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

public class DateRangeValidator implements ConstraintValidator<ValidDateRange, Object> {

    private String startField, endField, message;

    @Override
    public void initialize(ValidDateRange annotation) {
        this.startField = annotation.start();
        this.endField = annotation.end();
        this.message = annotation.message();
    }

    @Override
    public boolean isValid(Object bean, ConstraintValidatorContext context) {
        BeanWrapper wrapper = new BeanWrapperImpl(bean);
        LocalDate start = (LocalDate) wrapper.getPropertyValue(startField);
        LocalDate end = (LocalDate) wrapper.getPropertyValue(endField);
        if (start == null || end == null || !end.isBefore(start)) {
            return true;
        }
        context.disableDefaultConstraintViolation();
        context.buildConstraintViolationWithTemplate(message)
               .addPropertyNode(endField)            // reported as a field error on "end"
               .addConstraintViolation();
        return false;
    }
}

@Component

    private final PricingService pricing;

    OrderDraftValidator(PricingService pricing) { this.pricing = pricing; }

    @Override
    public boolean supports(Class<?> clazz) {
        return OrderDraft.class.isAssignableFrom(clazz);

        // Field error: attached to a property, rendered next to the input.
        if (draft.getDiscountCode() != null && !pricing.isRedeemable(draft.getDiscountCode())) {

        }
        // Global error: a statement about the object as a whole.
        if (pricing.total(draft).compareTo(draft.getCreditLimit()) > 0) {
            errors.reject("order.overCreditLimit", "Order exceeds the available credit limit");
        }
    }
}

Practice

Keep the two systems in their lanes. Bean Validation is for statements about the shape of a value that hold everywhere the type appears — length, nullability, format, range. Spring Validators and domain services are for statements about a business situation, which depend on collaborators and change with policy. /mvc/exception-handling11

Exception handling: five mechanisms, one chain

Spring MVC offers what looks like an embarrassment of overlapping error-handling options: @ResponseStatus, ResponseStatusException, @ExceptionHandler, @ControllerAdvice, ResponseEntityExceptionHandler, plus the container's error page and Spring Boot's /error endpoint. They are not alternatives competing for the same job. They are layers of one chain, and the chain has a strict order.27

The resolver chain

When a handler, an interceptor's postHandle, an argument resolver or a message converter throws, DispatcherServlet walks its ordered HandlerExceptionResolver list and takes the first non-null result:27,7

  1. ExceptionHandlerExceptionResolver — looks for an @ExceptionHandler method, first on the controller that produced the exception, then across @ControllerAdvice beans in @Order.
  2. ResponseStatusExceptionResolver — handles ResponseStatusException and any exception class annotated @ResponseStatus.
  3. DefaultHandlerExceptionResolver — translates the framework's own exception vocabulary to standard statuses: HttpRequestMethodNotSupportedException to 405, HttpMediaTypeNotSupportedException to 415, MethodArgumentNotValidException to 400, NoResourceFoundException to 404, and so on.

If nothing resolves it, the exception propagates out of the servlet, the container performs an ERROR dispatch, and in a Boot application that lands on BasicErrorController at /error, which renders either a JSON body or an error view depending on the request's Accept header.30

@ExceptionHandler mechanics

An @ExceptionHandler method is a handler method in almost every respect: it accepts the same argument types, returns the same return types, and its return value goes through the same return value handlers. The differences worth internalising:

  • The exception types it handles come from the annotation or, if omitted, from the method's own parameter list.
  • Matching prefers the most specific type. Within one class, a handler for IllegalArgumentException beats one for RuntimeException.
  • Cause traversal is supported: if no handler matches the thrown exception directly, its causes are examined, which is what makes handlers work through UndeclaredThrowableException and similar proxy wrappers.59
  • A controller-local handler always wins over an advice, regardless of @Order.
  • The exception itself, plus HttpServletRequest, WebRequest, HandlerMethod, and Locale, are all injectable arguments.
javaController-local handling, for exceptions that are local in meaning
@RestController
@RequestMapping("/api/orders")
class OrderController {

    @ExceptionHandler(OptimisticLockingFailureException.class)
    ProblemDetail conflict(OptimisticLockingFailureException ex, HttpServletRequest request) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT,
                "The order was modified by someone else. Reload and try again.");
        problem.setTitle("Concurrent modification");

Ordering trap

Advice beans are consulted in @Order sequence, and the first advice containing a matching handler wins — the search is not "most specific handler across all advices". A catch-all @ExceptionHandler(Exception.class) in an advice with high precedence will therefore shadow the precise handlers in a lower-precedence advice. Put catch-alls in the lowest-precedence advice, always.41

ProblemDetail and RFC 9457

Spring Framework 6.0 added first-class support for the problem-details format: a JSON object carrying type, title, status, detail and instance, served as application/problem+json, plus arbitrary extension members.60,40 The format was originally RFC 7807 and is now RFC 9457, which added the ability to reference several problems and clarified extension semantics.61 Spring's HttpStatus vocabulary was realigned with RFC 9110 in the 7.0 generation.12,44

ResponseEntityExceptionHandler

ResponseEntityExceptionHandler is an abstract @ControllerAdvice base class with a single @ExceptionHandler covering the framework's whole standard exception set, dispatching internally to one protected method per exception type, and rendering ProblemDetail bodies throughout.40 Extending it gives an API a consistent, specification-conformant error surface with very little code, and lets you override exactly the cases you care about.

javaA complete API error advice
@RestControllerAdvice(basePackages = "com.example.api")
@Order(Ordered.LOWEST_PRECEDENCE)
class ApiExceptionAdvice extends ResponseEntityExceptionHandler {

    private static final Logger log = LoggerFactory.getLogger(ApiExceptionAdvice.class);

    /** Override one framework case: expand field errors into an extension member. */
    @Override
    protected ResponseEntity<Object> handleMethodArgumentNotValid(
            MethodArgumentNotValidException ex, HttpHeaders headers,
            HttpStatusCode status, WebRequest request) {

        ProblemDetail problem = ProblemDetail.forStatusAndDetail(
                HttpStatus.BAD_REQUEST, "The request body failed validation");
        problem.setTitle("Invalid request");
        problem.setType(URI.create("https://errors.example.com/validation"));
        problem.setProperty("errors", ex.getBindingResult().getFieldErrors().stream()
                .map(fe -> Map.of(
                        "field", fe.getField(),
                        "rejected", String.valueOf(fe.getRejectedValue()),
                        "message", Optional.ofNullable(fe.getDefaultMessage()).orElse("invalid")))
                .toList());
        return handleExceptionInternal(ex, problem, headers, status, request);
    }

    /** Domain exceptions that already describe themselves need no work here. */

    /** Application-specific translation. */
    @ExceptionHandler(InsufficientStockException.class)
    ProblemDetail stock(InsufficientStockException ex) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(
                HttpStatus.UNPROCESSABLE_ENTITY, ex.getMessage());
        problem.setTitle("Insufficient stock");
        problem.setProperty("sku", ex.sku());
        problem.setProperty("available", ex.available());
        return problem;
    }

    /** The catch-all: log with the stack trace, return without it. */
    @ExceptionHandler(Exception.class)
    ProblemDetail unexpected(Exception ex, HttpServletRequest request) {
        String reference = UUID.randomUUID().toString();
        log.error("Unhandled exception [{}] on {} {}", reference,
                request.getMethod(), request.getRequestURI(), ex);

        ProblemDetail problem = ProblemDetail.forStatusAndDetail(
                HttpStatus.INTERNAL_SERVER_ERROR,
                "The request could not be completed. Quote reference " + reference + ".");
        problem.setTitle("Internal error");
        problem.setProperty("reference", reference);
        return problem;
    }
}
Security

Never let exception text reach the client unfiltered. Stack traces, SQL fragments, class names and file paths in a 500 body are reconnaissance material, and ex.getMessage() on a persistence exception frequently contains all four. The correlation-reference pattern above — log everything, return an opaque identifier — keeps operability without disclosure. Boot's server.error.include-stacktrace defaults to never for the same reason.30

The lightweight options

Not every error needs a handler. @ResponseStatus on an exception class is a declarative status mapping resolved by the second resolver in the chain, appropriate when the status is a permanent property of the exception type. ResponseStatusException is its imperative twin, thrown at the point of failure with a status and a reason, and it is the right tool when the same condition means different things at different call sites:27

A note on the exception path and interceptors

When a resolver handles an exception, postHandle is skipped but afterCompletion still runs, with the exception passed only if it went unresolved. Interceptor code that assumes it always sees failures will miss every handled one; metrics and tracing belong in an Observation or a filter, not in afterCompletion.25,62

    SseEmitter emitter = new SseEmitter(Duration.ofMinutes(30).toMillis());
    Subscription subscription = bus.subscribe(id, event -> {
        try {
            emitter.send(SseEmitter.event()
                    .id(event.sequence())
                    .name(event.type())
                    .reconnectTime(3_000)
                    .data(event, MediaType.APPLICATION_JSON));
        }
        catch (IOException ex) {
            emitter.completeWithError(ex);
        }
    });

    emitter.onTimeout(emitter::complete);
    emitter.onCompletion(subscription::cancel);    // ALWAYS release resources here
    emitter.onError(ex -> subscription.cancel());
    return emitter;
}

Async processing has semantics that catch people out. Interceptors run on the container thread only: preHandle fires, then afterConcurrentHandlingStarted instead of postHandle; when the result arrives a second, ASYNC dispatch runs the full chain again for rendering. Anything stored in a ThreadLocal — security context, transaction, MDC, request-scoped bean — does not follow the work to another thread unless it is explicitly propagated. A default timeout applies to the async request, and exceeding it triggers an AsyncRequestTimeoutException that your exception advice should handle rather than leaving to the container's error page.51

Virtual threads reset the trade-off

The original argument for async return types was thread economy: a blocked platform thread is an expensive idle resource. With JEP 444 virtual threads finalised in Java 21 and Boot able to run request handling on them, blocking a request thread costs a few hundred bytes rather than a megabyte of stack.64,30 That removes the scalability rationale for wrapping ordinary blocking work in Callable, while leaving the other rationales intact: streaming, incremental delivery, long-lived subscriptions, and results produced by a thread you do not control. Pinning caveats apply to synchronized-heavy libraries and native frames, so measure before assuming.

/mvc/view-technologies13

View technologies: the contract, the chain, and four engines

Everything on the rendering side reduces to two interfaces. View has render(Map model, HttpServletRequest, HttpServletResponse) and a content type; ViewResolver has resolveViewName(String, Locale). The controller returns a logical name, which is the decoupling point: the controller never names a file, a template engine or a content type.26,65

The resolution chain

All ViewResolver beans are detected and sorted; the first to return a non-null View wins. That ordering is how mixed applications work — a BeanNameViewResolver for a handful of programmatic views such as a PDF or a redirect, then a template resolver as the general case. Two resolvers deserve specific comment:26

  • ContentNegotiatingViewResolver does not resolve views itself; it delegates to the others and then selects among the candidates using the same ContentNegotiationManager the annotation model uses. It is the mechanism for serving an HTML page and a JSON representation from one controller method.
  • UrlBasedViewResolver and its subclasses recognise the redirect: and forward: prefixes, which is why those work at all. A returned "redirect:/orders/42" becomes a RedirectView; a returned "forward:/legacy" performs a servlet forward, re-entering the dispatcher.

During rendering, the model is exposed as request attributes and a RequestContext is placed in scope. That object gives templates access to the locale, the theme-free message source, and — critically — the BindingResult for each command object, which is how every form-binding tag library can render field values and error messages without the controller passing them explicitly.65

Thymeleaf

Thymeleaf is the default recommendation for server-rendered HTML in the Spring ecosystem, and the reason is its "natural templates" property: a template is a valid HTML document that renders correctly when opened directly in a browser, because the dynamic behaviour lives in th:* attributes that a browser ignores.66 Designers can work on files that developers also use, without a build step in between.

Integration is provided by the Thymeleaf project rather than by Spring, through a thymeleaf-spring<N> module matched to the framework generation. It supplies a SpringTemplateEngine, the ThymeleafViewResolver, and the SpringStandardDialect that adds th:field, SpEL expression evaluation, and form-binding support; in a Boot application spring-boot-starter-thymeleaf selects and configures the right one for you.67,68

htmlA form bound to a command object, with validation feedback
&lt;form th:action="@{/orders/new}" th:object="${draft}" method="post"&gt;

    &lt;p class="error" th:if="${#fields.hasErrors('customerReference')}"
       th:errors="*{customerReference}"&gt;placeholder shown only in the browser&lt;/p&gt;
  &lt;/div&gt;

  &lt;select th:field="*{warehouseId}"&gt;

FreeMarker is a mature, general-purpose template engine with a real template language — macros, functions, namespaces, sequence and hash built-ins, and a configurable escaping policy.69 Spring integrates it through FreeMarkerConfigurer and FreeMarkerViewResolver, and ships a spring.ftl macro library providing the same form-binding capabilities as the JSP tag library.70

Mustache

Mustache is defined by what it refuses to do: there is no expression language, no conditionals beyond section presence, no loops beyond section iteration over a list, and no arithmetic.71 Spring integrates the JMustache implementation through MustacheViewResolver.72,73 The consequence is that all presentation logic must be resolved in the controller or in a view-model type before rendering, which some teams consider the entire point and others find intolerable.

/mvc/functional-and-edges14

The functional alternative, CORS, and link building

Annotated controllers are not the only programming model on the servlet stack. Functional endpoints express routes as data: a RouterFunction maps a RequestPredicate to a HandlerFunction, and both are ordinary values that can be composed, nested, and returned from methods.35 The dispatcher support is a separate HandlerMapping/HandlerAdapter pair, so both models coexist in one application without interference.

javaThe same resource, expressed functionally
@Configuration(proxyBeanMethods = false)
class OrderRoutes {

    @Bean
    RouterFunction<ServerResponse> orderRoutes(OrderHandler handler) {
        return RouterFunctions.route()
                .path("/api/orders", builder -> builder
                        .GET("/{id}", accept(APPLICATION_JSON), handler::byId)
                        .GET("", handler::search)
                        .POST("", contentType(APPLICATION_JSON), handler::create)
                        .DELETE("/{id}", handler::cancel))
                .filter((request, next) -> {                 // scoped to this router only
                    request.attributes().put("tenant", request.headers().firstHeader("X-Tenant"));
                    return next.handle(request);
                })
                .onError(OrderNotFoundException.class,
                        (ex, request) -> ServerResponse.notFound().build())
                .build();
    }
}

@Component
class OrderHandler {

    ServerResponse byId(ServerRequest request) throws ServletException {
        UUID id = UUID.fromString(request.pathVariable("id"));
        return orders.find(id)
                .map(order -> ServerResponse.ok().body(OrderView.of(order)))
                .orElseGet(() -> ServerResponse.notFound().build());
    }

    ServerResponse create(ServerRequest request) throws ServletException, IOException {
        CreateOrder command = request.body(CreateOrder.class);
        Order created = orders.place(command);
        return ServerResponse.created(request.uriBuilder()
                        .path("/{id}").build(created.id()))
                .body(OrderView.of(created));
    }
}

The trade is explicitness for convenience. Routing is visible in one place and testable without a container; there is no reflection and no annotation scanning, which helps AOT compilation and native images. But you give up automatic validation triggering, automatic argument conversion, @ControllerAdvice participation, and the generated documentation that tools derive from annotations. Most teams use annotations as the default and functional routes for narrow cases: dynamically generated routes, a gateway-like proxy, or a handful of endpoints that must be registered conditionally.

CORS

Cross-origin configuration is a mapping concern, handled before the handler runs. Pre-flight OPTIONS requests are dispatched to a dedicated handler that consults the CorsConfiguration associated with the mapping that would have matched the actual request.77 That is why @CrossOrigin on a method works: the annotation feeds the mapping registry, not a filter.

javaGlobal rules, plus a per-endpoint override
@Configuration(proxyBeanMethods = false)
class CorsConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
                .allowedOrigins("https://app.example.com")   // never "*" with credentials
                .allowedMethods("GET", "POST", "PUT", "DELETE")
                .allowedHeaders("Authorization", "Content-Type", "X-API-Version")
                .exposedHeaders("Location", "ETag")
                .allowCredentials(true)
                .maxAge(1800);
    }
}

@CrossOrigin(origins = "https://partner.example.net", maxAge = 300)
@GetMapping("/public-feed")
FeedView feed() { ... }

When Spring Security is present, its filter chain runs before the dispatcher, so CORS pre-flight requests must be permitted there as well or they will be rejected before MVC's configuration is ever consulted — the standard remedy being Security's own cors() integration, which reads the MVC configuration source.77,34 Note also a 7.0 behaviour change: pre-flight requests are no longer rejected when the CORS configuration is empty.12

Testing the web layer without a network

The Spring MVC Test framework builds a real DispatcherServlet over mock servlet objects, so requests traverse mappings, interceptors, argument resolvers, converters, validation and exception resolution exactly as they would in a container — without a socket, a port, or a running server.78 It is the only web-layer test that verifies your configuration rather than just your code.

javaA slice test: one controller, mocked collaborators
@WebMvcTest(OrderController.class)
class OrderControllerTests {

    @Autowired MockMvcTester mvc;          // fluent AssertJ front end, Spring Framework 6.2+
    @MockitoBean OrderService orders;

    @Test
    void returnsProblemDetailWhenBodyIsInvalid() {
        assertThat(mvc.post().uri("/api/orders")
                        .contentType(MediaType.APPLICATION_JSON)
                        .content("""
                                {"customerReference": "", "lines": []}
                                """))
                .hasStatus(HttpStatus.BAD_REQUEST)
                .hasContentTypeCompatibleWith(MediaType.APPLICATION_PROBLEM_JSON)
                .bodyJson()
                .extractingPath("$.errors[*].field")
                .asArray().contains("customerReference", "lines");
    }

    @Test
    void setsLocationHeaderOnCreate() {
        given(orders.place(any())).willReturn(new Order(UUID.fromString(ID), ...));

        assertThat(mvc.post().uri("/api/orders")
                        .contentType(MediaType.APPLICATION_JSON)
                        .content(VALID_BODY))
                .hasStatus(HttpStatus.CREATED)
                .hasHeader("Location", "http://localhost/api/orders/" + ID);
    }
}

Scope

@WebMvcTest loads only the web slice: controllers, advice, converters, WebMvcConfigurer beans and security configuration, with everything else mocked. If your test needs a repository it is no longer a slice test; use @SpringBootTest(webEnvironment = RANDOM_PORT) and accept the slower context. Mixing the two — a slice test with five @MockitoBean declarations reconstructing a service graph — is the worst of both.30

Observability

Spring Framework instruments server request handling with Micrometer's Observation API, producing metrics and trace spans from a single instrumentation point, with the matched mapping pattern — not the raw URI — as the low-cardinality tag.62 That distinction is what keeps a metrics backend from exploding when your paths contain identifiers. Custom ObservationConvention implementations let you add tags such as tenant or API version without touching controller code.

Startup, AOT and native images

Annotated controllers are discovered by scanning bytecode for annotations at startup. For Java 24 and later, Spring Framework 7 reads that metadata through the JDK's own Class-File API rather than a bundled ASM fork.82,12 Ahead-of-time processing goes further, computing bean definitions and reflection hints at build time; for GraalVM native images, 7.0 switched to the unified reachability-metadata format, with the practical consequence that resource-hint globs and reflection registrations written for earlier versions need review.12

What to read next

Spring MVC rewards a specific kind of study: not memorising annotations, but learning the half-dozen contracts and the order in which the dispatcher consults them. Every annotation in the programming model is a leaf on one of those branches, and once the branches are clear the leaves are looked up rather than remembered. The framework's longevity is a consequence of that structure — the dispatcher of 2003 is recognisably the dispatcher of 2026, while the programming model above it has been rewritten twice.

For going deeper, in rough order of return on effort:

  • The reference documentation's web chapter, read end to end once rather than consulted piecemeal. It is unusually good, and the sections on request mapping, method arguments and error responses answer most day-to-day questions.83,40
  • DispatcherServlet.doDispatch and RequestMappingHandlerAdapter.invokeHandlerMethod in the source. Roughly three hundred lines between them, and they make the rest of the framework legible.20
  • The release notes for 6.0, 6.1, 6.2 and 7.0, which are the only complete record of what changed in the Jakarta migration, method validation, testing APIs and the current generation.60,57,79,12
  • The specifications underneath: Jakarta Servlet for the runtime contract, Jakarta Validation for constraint semantics, RFC 9110 for what the statuses actually mean, and RFC 9457 for error bodies.8,54,44,61
  • Rod Johnson's original argument, for why the design took the shape it did — much of it now reads as obvious, which is the highest compliment available to an architectural critique.5
