Spring Data JPA

Repositories, Queries, and Pagination

An expert guide to the repository abstraction, CrudRepository, PagingAndSortingRepository, JpaRepository, derived queries, JPQL, native SQL, Specifications, Querydsl, Pageable, Sort, Slice, and Page.

Spring Data JPA 4.1.0 Spring Data Commons 4.1.0 Jakarta Persistence Long-form technical article Vancouver references
Abstract. Spring Data JPA generates repository implementations over a Jakarta Persistence EntityManager. Its value is not that SQL and persistence semantics disappear; rather, repetitive repository plumbing is replaced by composable interfaces, query-method parsing, declared JPQL or SQL, Criteria-based Specifications, Querydsl predicates, projections, and common pagination abstractions. Correct use requires understanding the current repository-fragment hierarchy, JPA entity state behind save(), how method signatures drive query execution, which result types trigger count queries, why native SQL narrows portability, and how offset pagination and dynamic sorting affect database plans. This article develops those mechanics and provides a complete order-search repository using every requested approach.

Spring Data JPA 4.1.0 provides repository support for Jakarta Persistence and is built on Spring Data Commons 4.1.0. Repository proxies delegate persistence work to JPA and therefore retain the provider’s persistence-context, flush, transaction, lazy-loading, locking, and generated-SQL behavior.[1][2]

1. Mental model

1 The repository interface declares an aggregate type, identifier type, fragments, and query methods.
2 Repository scanning creates a proxy and selects a store-specific base implementation.
3 CRUD methods delegate to SimpleJpaRepository and the current EntityManager.
4 Query methods are derived, resolved to named queries, or implemented by declared JPQL/native SQL.
5 Specifications and Querydsl build predicates programmatically.
6 Return types select execution behavior: one, collection, stream, slice, page, projection, count, or existence.
7 JPA generates SQL, manages entity state, and synchronizes changes at flush.

The repository abstraction is intended to reduce boilerplate in data-access layers through a consistent programming model. It is not a universal persistence language: store modules support different query keywords, features, and execution strategies, and JPA-specific operations remain tied to Jakarta Persistence.[1][3]

2. Repository pattern

A domain repository represents collection-like access to aggregate roots. It should express domain retrieval and persistence operations rather than expose every table or arbitrary query as generic CRUD. Spring Data’s marker interface Repository<T, ID> captures the domain and identifier types; extending repository fragments opts into selected capabilities.[3]

Java 
public interface OrderRepository
        extends JpaRepository<PurchaseOrder, UUID> {

    Optional<PurchaseOrder> findByExternalReference(
            String externalReference);
}
Expose only intentional operations An interface may extend Repository directly and copy only the method signatures it wants. This is useful when unrestricted deleteAll(), findAll(), or generic saves would violate an aggregate boundary.
Java 
@NoRepositoryBean
public interface AggregateRepository<T, ID>
        extends Repository<T, ID> {

    Optional<T> findById(ID id);

    <S extends T> S save(S aggregate);
}

public interface PaymentRepository
        extends AggregateRepository<Payment, UUID> {

    Optional<Payment> findByProviderReference(
            String providerReference);
}

@NoRepositoryBean prevents an intermediate generic interface from being instantiated as a repository bean. Domain-specific repositories can then inherit the curated fragment.[3]

3. Repository interface hierarchy

3.1 CrudRepository

CrudRepository<T, ID> defines generic save, lookup, existence, count, and delete operations. Its multi-entity methods use Iterable. Implementations may optimize modules and events differently, so callers should rely on the documented contract rather than assuming that every bulk method is one SQL statement.[4]

Method familyContractJPA concern
save, saveAllPersist or update entitiesNew-state detection chooses persist or merge
findByIdZero or one by identifierReturns Optional
findAll, findAllByIdAll or selected identifiersPotentially unbounded result
existsById, countExistence or cardinalitySeparate query execution
delete*Delete entities or identifiersLifecycle and cascade semantics depend on the method

3.2 PagingAndSortingRepository

In current Spring Data, PagingAndSortingRepository<T, ID> is a separate repository fragment that extends Repository, not CrudRepository. It declares findAll(Sort) and findAll(Pageable). A manually composed repository that needs both CRUD and paging must extend both fragments, or use a higher-level interface such as JpaRepository.[5]

Java 
public interface MinimalOrderRepository
        extends CrudRepository<PurchaseOrder, UUID>,
                PagingAndSortingRepository<
                    PurchaseOrder,
                    UUID> {
}

ListPagingAndSortingRepository refines sorted retrieval to return a List, while the page-returning method remains Page<T>.[3]

3.3 JpaRepository

JpaRepository<T, ID> is the JPA-specific convenience interface. It extends list-returning CRUD and paging fragments plus QueryByExampleExecutor. It adds explicit flushing, save-and-flush operations, reference retrieval, and batch-delete methods.[6]

flush()Synchronizes pending persistence-context changes with the database; it does not commit the transaction.
saveAndFlush()Saves and immediately flushes; useful when a constraint must be observed before later work.
getReferenceById()Returns a JPA reference that can fail when first resolved if the row does not exist.
Batch deletesExecute direct delete queries and can leave managed state stale.

JPA batch-delete methods do not honor ordinary per-entity cascade semantics or lifecycle events and can leave the first-level cache out of sync with the database. Flush and clear or otherwise reconcile the persistence context before continuing with affected entities.[6]

3.4 What save() means

Spring Data JPA determines whether an entity is new. New entities are passed to EntityManager.persist(); others are passed to EntityManager.merge(). The default strategy examines a nullable version property first and then the identifier. Entities with manually assigned identifiers can implement Persistable.isNew() or use a custom entity-information strategy.[7]

Do not save managed entities after every mutation Inside a transaction, a managed entity is already dirty-checked. Calling save() again usually adds no persistence semantics and obscures whether the instance is new, managed, or detached.

Repository scanning registers proxies for eligible interfaces. Query lookup can create a query from a method name, require a declared query, or use a declared query when available and derive one otherwise. The create-if-not-found strategy is the usual default; declared-query-only mode can make large systems fail fast when a query was not explicitly reviewed.[8]

5. Query methods

A repository query method combines a subject, predicate, optional static ordering or limiting keywords, parameters, and a return type. Spring Data parses the method name, validates property paths against the domain model, and creates a JPA query when query derivation is selected.[8][9]

5.1 Derived queries

Java 
public interface OrderRepository
        extends JpaRepository<PurchaseOrder, UUID> {

    Optional<PurchaseOrder>
        findByExternalReferenceIgnoreCase(
            String externalReference);

    List<PurchaseOrder>
        findTop20ByStatusOrderByCreatedAtDescIdDesc(
            OrderStatus status);

    boolean existsByCustomerIdAndStatusIn(
            UUID customerId,
            Collection<OrderStatus> statuses);

    long countByStatusAndCreatedAtBefore(
            OrderStatus status,
            Instant cutoff);

    long deleteByStatusAndCreatedAtBefore(
            OrderStatus status,
            Instant cutoff);
}

Subject keywords include find/read/get/query/search/stream, count, exists, delete/remove, distinct, and top/first limiting. Predicates include equality, null checks, comparison, ranges, collection membership, string containment, empty collections, Boolean values, conjunction, disjunction, and case modifiers. Support remains store-specific.[10]

5.2 Property traversal and ambiguity

Derived queries can traverse nested properties, for example findByCustomer_Address_City. An underscore can make the intended traversal boundary explicit when compound property names would otherwise be ambiguous. Renaming entity properties therefore changes repository method validity and should be covered by application startup and integration tests.[8]

5.3 Reserved method names

Certain inherited signatures such as findById, existsById, and deleteById are reserved CRUD operations and target the repository identifier property even if an entity also has a non-identifier field named id. Use a descriptive token such as findOrderById when deriving against a separate property.[10]

6. Declared JPQL

JPQL queries operate over entity names, attributes, and relationships rather than tables and columns. @Query colocates a declared query with the repository method and takes precedence over named queries. Named parameters reduce positional-refactoring errors.[9][11]

Java 
public interface OrderRepository
        extends JpaRepository<PurchaseOrder, UUID> {

    @Query("""
        select o
        from PurchaseOrder o
        where o.customer.id = :customerId
          and o.status in :statuses
          and o.total >= :minimum
        order by o.createdAt desc, o.id desc
        """)
    List<PurchaseOrder> findQualified(
            @Param("customerId") UUID customerId,
            @Param("statuses")
            Collection<OrderStatus> statuses,
            @Param("minimum") BigDecimal minimum);
}

6.2 Fetch planning

Java 
@EntityGraph(attributePaths = {
    "customer",
    "lines"
})
Optional<PurchaseOrder> findDetailedById(
        UUID id);

Repository abstraction does not eliminate N+1 queries. Use an entity graph, fetch join, batch-fetch policy, or projection according to the use case. Avoid pageable collection fetch joins because row multiplication complicates both page boundaries and count queries.

6.3 Modifying queries

Java 
@Modifying(
    flushAutomatically = true,
    clearAutomatically = true)
@Query("""
    update PurchaseOrder o
    set o.status = :replacement
    where o.status = :expected
      and o.createdAt < :cutoff
    """)
int transitionOldOrders(
        @Param("expected")
        OrderStatus expected,
        @Param("replacement")
        OrderStatus replacement,
        @Param("cutoff")
        Instant cutoff);

JPQL bulk updates and deletes bypass ordinary managed-entity synchronization. Clearing the persistence context prevents stale entities from being reused, but also detaches unrelated managed objects; place bulk operations at deliberate transaction boundaries.[9]

7. Native SQL

@NativeQuery is a composed form of @Query(nativeQuery = true) with native-query-specific attributes such as SQL result-set mapping. Native SQL enables database functions, common table expressions, window functions, optimizer hints, vendor operators, and hand-tuned projections, at the cost of portability and tighter schema coupling.[9][12]

Java 
public interface OrderSummaryView {
    UUID getId();
    String getExternalReference();
    String getStatus();
    BigDecimal getTotal();
    Instant getCreatedAt();
}

@NativeQuery(
    value = """
        select
            o.id,
            o.external_reference,
            o.status,
            o.total,
            o.created_at
        from purchase_order o
        where o.customer_id = :customerId
          and o.status = :status
        order by o.created_at desc, o.id desc
        """,
    countQuery = """
        select count(*)
        from purchase_order o
        where o.customer_id = :customerId
          and o.status = :status
        """)
Page<OrderSummaryView> findNativeSummaries(
        @Param("customerId") UUID customerId,
        @Param("status") String status,
        Pageable pageable);

Spring Data can rewrite simple native queries for pagination and sorting. More complex SQL requires a capable parser such as JSqlParser on the classpath or an explicit countQuery. The count query is part of the repository contract and should be tested independently for joins, duplicate rows, grouping, and filters.[9]

Never bind identifiers through value parameters Table names, column names, operators, and SQL fragments cannot be safely supplied as ordinary query values. Choose them from an application allowlist or use separate declared queries. Do not concatenate arbitrary web sorting input into native SQL.

7.1 Native result mapping

Entity returns require selected columns to satisfy the entity mapping. Interface projections can map aliases to accessor names. Complex DTOs can use JPA @SqlResultSetMapping. Raw tuple-to-map native results are provider-sensitive; current Spring Data documentation notes that string-based tuple queries are supported by Hibernate while EclipseLink supports Criteria-based tuple queries.[9]

8. Specifications

JPA’s Criteria API builds queries programmatically. Spring Data JPA Specifications package reusable predicates and expose composition through JpaSpecificationExecutor. Spring Data JPA 4.x also provides PredicateSpecification, a query-type-agnostic predicate abstraction, plus select/update/delete specification variants and a fluent query API.[13]

Java 
public interface OrderRepository
        extends JpaRepository<PurchaseOrder, UUID>,
                JpaSpecificationExecutor<PurchaseOrder> {
}

public final class OrderSpecifications {

    public static Specification<PurchaseOrder>
            hasStatus(
                @Nullable OrderStatus status) {

        return (root, query, builder) ->
            status == null
                ? builder.conjunction()
                : builder.equal(
                    root.get("status"),
                    status);
    }

    public static Specification<PurchaseOrder>
            createdBetween(
                @Nullable Instant from,
                @Nullable Instant to) {

        return (root, query, builder) -> {
            List<Predicate> predicates =
                    new ArrayList<>();

            if (from != null) {
                predicates.add(
                    builder.greaterThanOrEqualTo(
                        root.get("createdAt"),
                        from));
            }

            if (to != null) {
                predicates.add(
                    builder.lessThan(
                        root.get("createdAt"),
                        to));
            }

            return builder.and(
                    predicates.toArray(
                        Predicate[]::new));
        };
    }

    private OrderSpecifications() {
    }
}
Java 
Specification<PurchaseOrder> specification =
        Specification.allOf(
            OrderSpecifications.hasStatus(
                filter.status()),
            OrderSpecifications.createdBetween(
                filter.from(),
                filter.to()));

Page<OrderSummary> result =
        repository.findBy(
            specification,
            query -> query
                .as(OrderSummary.class)
                .page(pageable));

The fluent specification API can apply sorting, limits, projections, pages, slices, scrolling, streams, counts, and existence checks. Specifications are most valuable when they represent reusable domain predicates; a single giant specification builder full of presentation flags becomes another untyped query language.[13]

8.1 Separate count specifications

JpaSpecificationExecutor supports page methods that accept a distinct count specification. This allows the content query to contain fetches or joins that the total-count query does not require. Ensure the simplified count preserves exactly the same filtering cardinality.[13]

9.2 Custom Querydsl repository fragment

Java 
public interface OrderSearchRepository {
    Slice<OrderSummary> search(
            OrderFilter filter,
            Pageable pageable);
}

public final class OrderSearchRepositoryImpl
        implements OrderSearchRepository {

    private final JPAQueryFactory queries;

    public OrderSearchRepositoryImpl(
            EntityManager entityManager) {
        this.queries =
                new JPAQueryFactory(entityManager);
    }

    @Override
    public Slice<OrderSummary> search(
            OrderFilter filter,
            Pageable pageable) {

        QPurchaseOrder order =
                QPurchaseOrder.purchaseOrder;

        BooleanBuilder where =
                new BooleanBuilder();

        if (filter.status() != null) {
            where.and(
                order.status.eq(filter.status()));
        }

        if (filter.minimumTotal() != null) {
            where.and(
                order.total.goe(
                    filter.minimumTotal()));
        }

        List<OrderSummary> rows = queries
            .select(Projections.constructor(
                OrderSummary.class,
                order.id,
                order.externalReference,
                order.status,
                order.total,
                order.createdAt))
            .from(order)
            .where(where)
            .orderBy(
                order.createdAt.desc(),
                order.id.desc())
            .offset(pageable.getOffset())
            .limit(pageable.getPageSize() + 1L)
            .fetch();

        boolean hasNext =
                rows.size() > pageable.getPageSize();

        if (hasNext) {
            rows = rows.subList(
                0,
                pageable.getPageSize());
        }

        return new SliceImpl<>(
                rows,
                pageable,
                hasNext);
    }
}

Spring Data’s JPA Querydsl helper can apply a Pageable or Sort to a Querydsl JPQL query. A custom fragment retains full control over projection and count behavior while still composing with the generated repository proxy.[16]

9.3 Web predicate binding

Spring Data can bind HTTP request parameters to Querydsl predicates. Default generic binding can expose more of the entity model than intended; customize allowed paths, aliases, collection behavior, and string matching through a binder and never treat predicate construction as authorization.[17]

10. Sorting

Sort is an immutable sequence of orders. Each order contains a property, direction, optional case handling, and a null-handling hint. JPA sorting properties generally need to resolve to entity paths or selected aliases. Function expressions are rejected by default; JpaSort.unsafe() explicitly opts into expressions that are appended or translated into the query.[18][9]

Java 
Sort stableSort = Sort.by(
    Sort.Order.desc("createdAt"),
    Sort.Order.desc("id"));

List<PurchaseOrder> orders =
        repository.findByStatus(
            OrderStatus.SUBMITTED,
            stableSort);
Always define a deterministic tie-breaker Sorting only by a non-unique timestamp or status does not create a stable total order. Offset pages can duplicate or omit records when ties are reordered. Append a unique immutable key such as the primary key.

10.1 Sort allowlisting

Java 
private static final Map<String, String>
        API_SORTS = Map.of(
            "created", "createdAt",
            "total", "total",
            "status", "status");

static Sort toDomainSort(
        List<ApiSort> requested) {

    List<Sort.Order> orders =
            requested.stream()
                .map(item -> {
                    String property =
                            Optional.ofNullable(
                                API_SORTS.get(
                                    item.field()))
                            .orElseThrow(
                                InvalidSortException::new);

                    return new Sort.Order(
                        item.direction(),
                        property);
                })
                .collect(
                    Collectors.toCollection(
                        ArrayList::new));

    orders.add(Sort.Order.desc("id"));
    return Sort.by(orders);
}

Public sort names should be mapped to internal paths. This prevents persistence-property leakage, invalid paths, unindexed orders, and unsafe expression injection.

11. Pagination

11.1 Pageable

Pageable describes a zero-based page number, positive page size, offset, and sort. PageRequest is the standard implementation. APIs accept Pageable.unpaged() rather than null when no restriction is intended.[19][20]

Java 
Pageable pageable =
        PageRequest.of(
            0,
            50,
            Sort.by(
                Sort.Order.desc("createdAt"),
                Sort.Order.desc("id")));

11.2 Slice

Slice<T> contains the current content, paging metadata, and whether next or previous slices exist. A slice query commonly fetches pageSize + 1 rows to determine whether another slice exists and does not need the total result count.[8][21]

Java 
Slice<OrderSummary> findByStatus(
        OrderStatus status,
        Pageable pageable);

11.3 Page

Page<T> extends Slice<T> with total elements and total pages. Producing those totals can require an additional count query. For large or complex joins, the count may cost more than the content query.[8][22]

Java 
Page<OrderSummary> page =
        repository.findSummaries(
            OrderStatus.SUBMITTED,
            pageable);

Page<OrderResponse> response =
        page.map(OrderResponse::from);

11.4 Offset cost and consistency

Offset pagination becomes increasingly expensive because the database must locate and discard preceding rows. Concurrent inserts and deletes can shift later pages between requests. For deep, continuously changing data sets, keyset scrolling or a cursor built from the last stable sort key is usually more scalable than a high page number. Spring Data also exposes scrolling and window abstractions beyond the requested page model.[8][9]

11.5 Web-bound pagination

12.1 Service boundary

Java 
@Service
public final class OrderQueryService {

        this.orders = orders;
    }

Repository methods describe persistence operations; the application service owns transaction boundaries and business invariants. Read-only transaction metadata can help providers optimize, but it does not replace query design or database authorization.[23]

13.1 Plan and count tests

  • Verify generated SQL and the presence of required joins.
  • Test count queries independently from content queries.
  • Assert stable ordering for equal primary sort values.
  • Measure late offset pages with production-like volume.
  • Test N+1 behavior using query-count instrumentation.
  • Exercise empty IN collections and null filters explicitly.
  • Test specification combinations rather than only individual predicates.
  • Compile generated Querydsl Q-types in continuous integration.

14. Diagnostics

14.1 Repository fails during startup

A derived method likely references an invalid or ambiguous property path. Compare the parsed method segments with entity attributes, use explicit traversal underscores, or replace an unwieldy name with a declared query.

14.2 Single-result query returns several rows

The return type declared zero-or-one semantics while the database allowed duplicates. Enforce the invariant with a unique constraint or return a collection when multiplicity is valid.

14.3 Page content is fast but the endpoint is slow

Inspect the generated count query. Use a Slice, provide a simpler count query/specification, maintain a separate aggregate, or switch the navigation contract when exact totals do not justify their cost.

14.4 Dynamic sort throws a property exception

The sort property does not resolve to an entity path or selected alias. Map public sort fields to valid internal paths. Use JpaSort.unsafe only for trusted application-defined expressions, never raw client input.[9]

14.5 Entities remain after a batch delete

Direct batch deletion bypassed normal per-entity synchronization. Flush before the operation and clear or refresh affected managed state afterward.[6]

14.6 Native page has incorrect totals

The content and count SQL differ in joins, filters, duplicate elimination, grouping, or tenant conditions. Supply and test an explicit count query rather than depending on automatic rewriting for complex SQL.[9]

15. Expert practices

15.1 Choose the smallest repository surface

Use JpaRepository for broad application repositories; use curated base interfaces when unrestricted CRUD conflicts with aggregate rules.

15.2 Escalate query style deliberately

Use derived queries for short, obvious predicates; JPQL for readable entity-oriented queries; Specifications for composable dynamic filters; Querydsl for type-safe complex construction; native SQL for database-specific capability.

15.3 Prefer projections for reads

Avoid loading mutable entities for list screens and reports. Select the required shape and separate read contracts from transactional aggregate mutation.

15.4 Do not pay for totals accidentally

Use Page only when exact totals are a requirement. Use Slice, scrolling, or cursor navigation for feed-style and high-volume traversal.

15.5 Require deterministic order

Add a unique tie-breaker, align order with an index, and allowlist public sort fields. Without stable ordering, pagination is not reproducible.

15.6 Isolate native SQL

Keep vendor-specific queries in clearly named methods or custom fragments, use explicit projections and count queries, and run them against the actual production database.

15.7 Put transactions in services

Repository operations are implementation primitives. Application services should define the unit of work across repositories and managed-entity mutations.

15.8 Observe generated behavior

Record SQL count, duration, rows, count-query duration, page depth, selected sort, and cache behavior. A repository method is executable database behavior, not merely an interface signature.

16. Summary

  • Spring Data JPA creates repository proxies over an EntityManager; JPA persistence semantics remain in force.
  • CrudRepository supplies generic CRUD operations.
  • PagingAndSortingRepository is a separate fragment in current Spring Data and does not itself supply CRUD.
  • JpaRepository combines list-based CRUD and paging with JPA-specific flush, reference, and batch operations.
  • save() selects persist or merge through new-state detection.
  • Derived query names are appropriate when the predicate remains short and readable.
  • JPQL targets entities and relationships; native SQL targets schema and database-specific capability.
  • Specifications compose Criteria predicates and now support fluent projection, page, slice, count, and scroll execution.
  • Querydsl provides generated type-safe paths and integrates through predicate executors and custom fragments.
  • Sort must resolve to safe, valid paths or trusted aliases, and pagination requires a deterministic unique tie-breaker.
  • Slice avoids exact totals; Page can require a costly count query.
  • Offset pagination degrades at depth and is unstable under concurrent changes; cursor or keyset navigation is often better for large feeds.

When a repository operation surprises you, trace it from the signature inward: Which repository fragment supplied the method? Was the query derived, named, JPQL, native, Specification-based, or Querydsl-based? Which return type selected the execution strategy? Did pagination add a count query? Which sort paths and joins were generated? Did the operation return managed entities, projections, or stale state after a bulk query? That sequence turns Spring Data JPA from proxy magic into an explicit persistence execution model.
