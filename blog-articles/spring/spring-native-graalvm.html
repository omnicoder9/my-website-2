Spring AOT and GraalVM Native Image

Spring Native and GraalVM

A technical guide to the Spring Native transition, Spring ahead-of-time processing, GraalVM native executables, closed-world analysis, reflection and reachability hints, native build tooling, tests, diagnostics, and performance trade-offs.

Spring Framework 7.0.8 Spring Boot 4.1.0 GraalVM Native Image 25.1 documentation Long-form technical article Vancouver references
Abstract. Spring Native was the experimental Spring Boot 2.x project that incubated native-image support. It was archived after its AOT engine and native integrations became first-class, generally available capabilities in Spring Framework 6 and Spring Boot 3. Modern applications therefore do not add a “Spring Native” dependency: the Spring Boot build plugins invoke Spring AOT processing and GraalVM Native Build Tools. Spring AOT creates a build-time view of the application context, evaluates conditions, generates bean-registration code, and emits runtime hints. GraalVM Native Image then performs closed-world reachability analysis and compiles reachable Java code, resources, metadata, and runtime components into an operating-system- and architecture-specific executable. The result often starts faster and uses less memory than the corresponding HotSpot process, but imposes longer and more resource-intensive builds, a fixed build-time application shape, metadata requirements for dynamic Java features, and a different peak-throughput and diagnostics model. This article explains those mechanisms and provides production-oriented build, hint, testing, and optimization examples.

Spring Boot describes GraalVM native images as standalone executables generated by ahead-of-time processing of compiled Java applications and notes their typical startup-time and memory-footprint advantages. GraalVM’s builder performs static reachability analysis and compiles reachable classes, methods, resources, metadata, and runtime support into a binary for a specific operating system and architecture.[1][2]

1. From Spring Native to built-in native support

Spring Native began as an experimental project for Spring Boot 2.x. The Spring team used it to develop AOT transformations, hints, build-plugin integration, portfolio compatibility, and native test infrastructure. In 2023 the project was archived in spring-attic; no further Spring Native releases were planned, and users were directed to Spring Boot 3’s official native-image support. Spring Boot 3.0 was the first GA Boot generation with built-in GraalVM native support, superseding the experimental project.[3][4]

Current terminology “Spring Native” is historically important but no longer the artifact to add. In current Spring, use Spring Framework AOT, Spring Boot’s AOT and native-image plugin integration, GraalVM Native Build Tools, and runtime hints.

Spring AOT and native compilation are related but not synonymous. Spring AOT-generated initialization can run on the JVM to improve startup, while the same generated assets also make Spring’s dynamic programming model understandable to the native-image compiler. Boot documents building an AOT-processed JAR with the native profile and running it on the JVM with -Dspring.aot.enabled=true.[5]

Shell 
# Maven: generate Spring AOT assets in the packaged JAR.
./mvnw -Pnative package

# Run the AOT-prepared application on HotSpot.
java \
  -Dspring.aot.enabled=true \
  -jar target/application.jar
Benchmark all three when startup matters A native image is not the only startup option. Compare ordinary JVM, JVM plus Spring AOT, JVM AOT cache/CDS where available, CRaC where operationally suitable, and a native executable against the same workload and deployment constraints.

3. Spring ahead-of-time processing

Spring AOT processes an application’s BeanFactory at build time. Boot’s Gradle plugin documentation describes processAot as creating a persistent view of the beans that will be contributed at runtime, generating code that makes bean instantiation more direct, and producing metadata such as reflection configuration required by GraalVM. Conditions are evaluated during that processing phase.[6]

1 The build launches the application’s AOT processing entry point with a build-time classpath and environment.
2 Configuration classes and auto-configurations are discovered and conditions are evaluated.
3 The bean factory is prepared and bean definitions are analyzed.
4 Spring projects contribute generated initialization code and runtime hints.
5 Generated Java/classes, resources, and native-image metadata are added to the build output.
6 The native plugin passes the AOT output to GraalVM Native Image.

3.1 Fixed build-time application shape

Boot warns that AOT processing fixes the classpath and application bean model at build time. Profiles and property-driven conditions that change which beans exist have limitations because those decisions were already evaluated. Build-time environment variables, system properties, and arguments can be supplied to the AOT task when they legitimately determine the deployed application shape.[5][6]

Kotlin DSL 
tasks.named<JavaExec>("processAot") {
    systemProperty(
        "spring.profiles.active",
        "production")
    environment(
        "FEATURE_SEARCH_ENABLED",
        "true")
}

A native binary can still read ordinary runtime settings such as endpoints, credentials, timeouts, pool sizes, and feature parameters. The restriction concerns settings that alter the generated bean graph or reachability assumptions. Separate deployment configuration from build-time structural variants and build distinct binaries only where the structural difference is intentional.

3.2 Inspect generated output

Generated AOT code is designed to be inspectable Java rather than opaque compiler state. Inspecting it helps diagnose why a bean, proxy, resource, or hint was—or was not—generated. Build directories vary by tool, but Gradle’s processAot and Maven’s AOT goal generate source, class, and resource outputs that feed the native compilation.[6][7]

4. GraalVM Native Image

Native Image consumes Java bytecode. It analyzes which program elements are reachable, compiles them ahead of time, constructs an initial image heap, links required runtime components and native libraries, and emits a platform-specific executable or shared library. The build depends on a local C toolchain when invoked directly; Spring Boot Buildpacks can instead provide a containerized native build environment.[2][8]

4.1 Closed-world assumption

The builder assumes that all code that can execute is known at image build time. Static analysis can understand direct calls and some dynamic operations with constant arguments, but it cannot exhaustively infer arbitrary reflection, JNI, dynamic proxies, runtime class definition, serialization, resource lookup, or resource-bundle access. Those uses require reachability metadata.[2][9]

A successful build does not prove complete metadata A missing reflective constructor or resource can remain invisible until a rare runtime path executes. Native compatibility requires exercising representative behavior and testing metadata, not only compiling the executable.

4.2 What the executable contains

  • Ahead-of-time compiled machine code for reachable Java methods.
  • Native Image runtime services, including memory management and threads.
  • An image heap containing selected build-time objects and metadata.
  • Registered resources, resource bundles, reflection metadata, and proxy definitions.
  • Linked native libraries and platform-specific executable structures.

Build output reports code area, image heap, embedded resources, debug information, and resource usage. Build reports can further explain package, class, method, resource, metadata, and software-bill-of-material contents, depending on the GraalVM distribution and feature availability.[10][11]

6. Runtime and reachability hints

Spring’s RuntimeHints API records reflection, resource, resource-bundle, proxy, and Java-serialization requirements. Spring Framework and portfolio projects generate hints for supported programming models; application code and unsupported libraries must supply missing metadata. The preferred location for reusable third-party metadata is the library itself or the GraalVM Reachability Metadata Repository rather than Spring Boot carrying hints for arbitrary libraries.[14][15]

6.1 Reflection for binding

Java 
@Configuration(proxyBeanMethods = false)
@RegisterReflectionForBinding({
    PartnerRequest.class,
    PartnerResponse.class,
    PartnerError.class
})
public class PartnerClientConfiguration {
}

Spring can infer JSON-binding hints for common controller signatures. Explicit @RegisterReflectionForBinding is useful when types are only visible through programmatic clients or generic abstractions, such as a WebClient, RestClient, or RestTemplate call whose target type is not otherwise discoverable by the AOT engine.[15][16]

Java 
@Service
public final class PartnerClient {

    private final RestClient client;

    public PartnerClient(RestClient.Builder builder) {
        this.client = builder
            .baseUrl(
                "https://partner.example.net")
            .build();
    }

    public PartnerResponse create(
            PartnerRequest request) {

        return client.post()
            .uri("/v1/partners")
            .body(request)
            .retrieve()
            .body(PartnerResponse.class);
    }
}

6.2 Programmatic RuntimeHintsRegistrar

Java 
public final class ApplicationRuntimeHints
        implements RuntimeHintsRegistrar {

    @Override
    public void registerHints(
            RuntimeHints hints,
            ClassLoader classLoader) {

        hints.reflection().registerType(
            LegacyPlugin.class,
            MemberCategory
                .INVOKE_DECLARED_CONSTRUCTORS,
            MemberCategory
                .INVOKE_PUBLIC_METHODS);

        hints.resources().registerPattern(
            "rules/*.json");

        hints.resources().registerResourceBundle(
            "i18n.messages");

        hints.proxies().registerJdkProxy(
            PaymentGateway.class);

        hints.reflection()
            .registerJavaSerialization(
                AuditEnvelope.class);
    }
}

@SpringBootApplication
@ImportRuntimeHints(
    ApplicationRuntimeHints.class)
public class NativeApplication {
    public static void main(String[] arguments) {
        SpringApplication.run(
            NativeApplication.class,
            arguments);
    }
}

RuntimeHintsRegistrar can be activated conditionally through @ImportRuntimeHints or registered statically for library use through META-INF/spring/aot.factories. Register the minimum access that the application requires; broad “all members” reflection metadata increases executable metadata and can conceal an imprecise integration contract.[17][14]

6.3 Introspection versus invocation

Native reflection metadata distinguishes discovering a member from invoking it. Spring’s reflection hint APIs expose executable modes and member categories so code that merely inspects annotations does not automatically receive invocation rights. Prefer targeted constructor, method, field, and type registrations based on the actual library behavior.[18]

6.4 Resources and resource bundles

Classpath resources are not automatically copied merely because a string names them. Register files or patterns that are dynamically loaded, and register localization bundles as bundles rather than ordinary files when they are resolved through ResourceBundle. GraalVM reachability metadata treats resources and resource bundles as explicit metadata categories.[9][14]

6.5 Dynamic proxies

Spring AOT generates metadata for framework-managed proxy scenarios it understands. Direct use of Proxy.newProxyInstance or a third-party library that builds JDK proxies from runtime interface lists can require a proxy hint. The ordered interface set is part of the proxy identity in native metadata.[9]

6.6 Static JSON metadata

JSON 
{
  "reflection": [
    {
      "type": "com.example.LegacyPlugin",
      "allDeclaredConstructors": true,
      "methods": [
        {
          "name": "execute",
          "parameterTypes": [
            "java.lang.String"
          ]
        }
      ]
    }
  ],
  "resources": [
    {
      "glob": "rules/*.json"
    }
  ]
}

GraalVM accepts reachability metadata files under META-INF/native-image/<groupId>/<artifactId>/. Spring recommends putting manually supplied files in a separate artifact-specific subdirectory so they do not clash with AOT-generated files. Prefer Spring’s typed hints for application code and static metadata when integrating an external library whose configuration is naturally distributed as GraalVM metadata.[9][15]

7. Testing runtime hints

Java 
class ApplicationRuntimeHintsTest {

    @Test
    void registersRequiredMetadata() {
        RuntimeHints hints =
                new RuntimeHints();

        new ApplicationRuntimeHints()
            .registerHints(
                hints,
                getClass().getClassLoader());

        assertThat(
            RuntimeHintsPredicates
                .resource()
                .forResource("rules/default.json"))
            .accepts(hints);

        assertThat(
            RuntimeHintsPredicates
                .reflection()
                .onType(LegacyPlugin.class))
            .accepts(hints);
    }
}

RuntimeHintsPredicates lets tests assert that an expected resource, reflection member, proxy, or other hint is present before paying the cost of a native compilation. These unit tests verify declarations; they do not prove that the complete application requires no additional metadata.[15][19]

8. Tracing agent

GraalVM’s tracing agent observes dynamic-feature use while the application runs on a regular JVM and writes metadata files. Because it records only exercised code, representative test and application paths are required, and generated output should be reviewed. Spring recommends the agent mainly to identify missing entries when a library or pattern is not recognized by the AOT engine.[20][15]

Shell 
java \
  -Dspring.aot.enabled=true \
  -agentlib:native-image-agent=\
config-output-dir=target/native-agent \
  -jar target/application.jar

Exercise startup, serialization, scheduled paths, messaging listeners, error handlers, administrative endpoints, optional integrations, and shutdown behavior. A test-suite run can generate repeatable coverage but may also record test-framework metadata; agent access filters can exclude irrelevant callers.[15][20]

Agent output is evidence, not an ideal final design The agent can over-register metadata from broad tests and under-register untested behavior. Convert important application metadata into reviewed typed hints and contribute reusable library metadata upstream.

9. Native tests

Spring’s TestContext AOT support discovers application contexts required by tests, generates AOT assets for each context, builds a native test executable containing the JUnit test engine and discovered tests, and executes that binary. Standard @SpringBootTest and test-slice patterns can participate.[21]

Shell 
# Maven
./mvnw -PnativeTest test

# Gradle
./gradlew nativeTest

Native tests are slower to build than JVM tests, so keep the fast JVM suite as the primary feedback loop and run a focused but representative native suite in continuous integration. Include error paths and dynamic integrations, not merely a context-start smoke test.[21]

10. Diagnosing native-image failures

10.1 Build-time failure

  • Read the first meaningful exception rather than only the final native-image failure summary.
  • Inspect generated AOT sources and resources.
  • Confirm the build-time profile, properties, environment, classpath, JDK, and plugin versions.
  • Inspect Native Image’s reachable-type, code-area, resource, and image-heap summaries.
  • Check whether an unsupported third-party dependency has reachability metadata.

10.2 Runtime missing registration

Current GraalVM documentation provides an exact reachability-metadata mode that reports missing registrations more directly. The runtime reporting mode can warn or exit when a missing-registration path is encountered, making it useful in native integration tests. Exact mode is evolving toward the default behavior, so applications should adopt it deliberately and fix genuine metadata gaps rather than depending on permissive behavior.[9]

Gradle 
graalvmNative {
    binaries {
        named("main") {
            buildArgs.add(
                "--exact-reachability-metadata="
                + "com.example")
        }
    }
}
Shell 
./application \
  -XX:MissingRegistrationReportingMode=Exit

10.3 Class initialization problems

Native Image may initialize eligible classes during the image build and store their state in the executable, while other classes initialize at runtime. Build-time initialization can improve startup, but static state that depends on clocks, random data, environment, files, threads, sockets, or secrets can become incorrect or unsafe if captured in the image. GraalVM provides class-initialization controls, but library and framework defaults should be preferred over broad application flags.[22]

10.4 Unsupported library

Spring Boot’s documentation notes that not every library provides native support. Determine whether the problem is missing metadata, runtime bytecode generation, unsupported native/JNI integration, class-loader behavior, or a genuinely unsupported JDK feature. Metadata can fix reachability; it cannot make every runtime code-generation model compatible.[15][2]

11. Performance considerations

11.1 Startup and memory

Native executables generally start faster and have a lower runtime memory footprint than their JVM counterparts because code and framework initialization have been moved to build time and the executable includes only reachable elements. The exact difference depends on application size, framework features, traffic, allocator behavior, native libraries, GC, and measurement method.[1][9]

11.2 Peak throughput

HotSpot observes live application behavior and JIT-compiles hot paths using runtime profiles. A native executable is compiled ahead of time and does not obtain the same ordinary HotSpot profiling and recompilation cycle. GraalVM provides profile-guided optimization to supply representative runtime profiles to the AOT compiler and improve performance and size; PGO availability depends on the GraalVM distribution.[23][24]

Shell 
# 1. Ask the builder invoked by Gradle to
#    create an instrumented executable.
NATIVE_IMAGE_OPTIONS="--pgo-instrument" \
  ./gradlew clean nativeCompile

# 2. Exercise a representative workload.
./build/native/nativeCompile/application
# A profile such as default.iprof is written
# when the instrumented process exits.

# 3. Rebuild using that profile.
NATIVE_IMAGE_OPTIONS="--pgo=$PWD/default.iprof" \
  ./gradlew clean nativeCompile
Measure the workload that matters Native often wins decisively for scale-to-zero services, command-line applications, short batch tasks, function workloads, and dense container fleets. A long-running CPU-heavy service can favor a warmed JVM. There is no universal winner across startup, footprint, peak throughput, latency, and build cost.

11.3 Build time and build memory

Native compilation performs whole-program analysis and optimization and can take minutes for a nontrivial application. Build output reports the number of threads, memory limits, peak RSS, reachable types and methods, and compilation stages. Reducing build parallelism can reduce resource pressure at the cost of a slower build; development quick-build optimization levels can shorten feedback loops but should not be confused with production output.[10][25]

11.4 Binary size

Executable size includes compiled code, image-heap objects, resources, reflection metadata, and runtime support. Overly broad reflection registrations, resource globs, character sets, localization bundles, security providers, and optional dependencies increase reachability and size. Use build output and reports to identify dominant packages, code, and embedded resources.[10][11]

11.5 Native runtime memory

Native Image has its own runtime memory management rather than HotSpot’s collectors. Serial GC is the default and emphasizes low footprint; other collectors, including G1 on supported platforms and distributions, address different latency and throughput requirements. The native Java heap is not the process’s complete memory footprint because stacks and runtime-native structures exist outside it.[26]

Shell 
# Runtime heap cap for a native executable.
./application -Xmx256m

# Build-time default heap cap for produced binaries.
native-image \
  -R:MaxHeapSize=256m \
  -jar application.jar

11.6 Optimization level

Native Image uses -O2 by default as a balance among execution performance, image size, and build time. Quick-build, size-oriented, debug, and higher optimization modes serve different development and production goals. Keep production build options version-controlled and compare output and runtime behavior after GraalVM upgrades.[25]

13. Native-friendly application design

13.1 Keep dynamic types explicit

Prefer typed DTOs, concrete configuration properties, explicit serialization targets, and discoverable repository/controller signatures. Type erasure and opaque generic wrappers can hide binding types from AOT analysis even when ordinary JVM execution succeeds.

13.2 Prefer build-time code generation over runtime bytecode generation

Runtime-generated classes are difficult under closed-world analysis. Select libraries with native support, build-time generators, static proxies, or supplied reachability metadata. Do not assume a tracing-agent JSON file can repair a library whose central behavior requires arbitrary runtime class definition.

13.3 Make resources intentional

Use narrow resource locations and patterns. A broad **/* registration can embed test fixtures, schemas, templates, localization bundles, and other unused data. Keep secrets outside the binary; build-time resources become part of the distributable executable.

13.4 Minimize environment-dependent static initialization

Static state that captures the build machine’s locale, time zone, hostname, filesystem, random seed, environment, or credentials can violate runtime expectations if initialized into the image heap. Construct environment-dependent state through Spring beans at runtime unless a framework-supported build-time initialization policy proves it safe.

13.5 Retain a JVM deployment path

The same application can usually produce a JAR and a native executable. Maintaining JVM tests and an operational JVM fallback reduces migration risk, supports libraries that remain incompatible, and provides richer HotSpot diagnostics for difficult production investigations.

14. Security and supply chain

  • A native executable is platform-specific and must be rebuilt for JDK, GraalVM, compiler, C library, dependency, and application security updates.
  • Build-time resources and image-heap objects become part of the artifact; never capture credentials or environment secrets.
  • Use reproducible, pinned builder images and verify the generated software bill of materials where available.
  • Scan both application dependencies and the final native container or executable.
  • Protect agent-generated metadata and test recordings if they reveal class names, resource paths, or proprietary integration behavior.

Native Image build reports can include an SBOM section, and the executable still incorporates third-party runtime and native components whose provenance and patch status must be tracked.[11]

          trap 'kill $PID || true' EXIT

            sleep 1
          done
          exit 1

A production pipeline should also exercise representative JSON binding, database access, security, messaging, resource bundles, scheduled tasks, optional feature paths, and failure handlers. Build native artifacts on the target architecture or create separate architecture-specific jobs because ordinary Native Image builds are not cross-compilation builds.[8][21]

16. Anti-patterns

16.1 Adding the archived Spring Native dependency

Current Boot applications should use built-in AOT and native integration. Spring Native was archived after its capabilities graduated into Framework and Boot.[3]

16.2 Registering every class for all reflection

Broad registrations increase metadata and image size, hide the actual dynamic contract, and can unnecessarily expose members. Register specific types and access modes.

16.3 Treating one tracing-agent run as complete

Agent output covers executed paths only. Use representative tests, manual review, typed hint tests, and native tests.[20]

16.4 Assuming native is always faster

Startup and footprint often improve, but warmed JVM throughput can be stronger and native builds are more expensive. Measure the complete operational objective.

16.5 Supplying production secrets to AOT processing

Build-time conditions may require structural settings, not live credentials. Keep secrets runtime-injected and prevent static initialization or resource generation from capturing them.

16.6 Designing a runtime plugin system and expecting closed-world compilation

Arbitrary classes introduced after the binary is built violate the native-image reachability model. Use a fixed plugin set at build time, separate processes, or a JVM deployment for genuinely dynamic extensions.

18. Summary

  • Spring Native was the experimental Boot 2.x predecessor; current native support is built into Spring Framework and Spring Boot.
  • Spring AOT can run on the JVM and also prepares applications for GraalVM Native Image.
  • AOT processing builds a persistent view of the bean factory and evaluates structural conditions at build time.
  • GraalVM Native Image performs closed-world reachability analysis and emits a platform-specific executable.
  • Reflection, resources, bundles, proxies, serialization, JNI, and similar dynamic features may require reachability metadata.
  • Spring generates hints for supported programming models; application-specific dynamic behavior uses typed runtime hints or static metadata.
  • @RegisterReflectionForBinding is useful for DTOs hidden behind programmatic clients or generic abstractions.
  • RuntimeHintsRegistrar registers precise reflection, resource, bundle, proxy, and serialization requirements.
  • The tracing agent discovers observed dynamic access but must be reviewed and supplemented by tests.
  • Maven, Gradle, and Cloud Native Buildpacks provide supported build paths.
  • Native tests build and execute a native JUnit test binary from AOT-processed test contexts.
  • Native images often improve startup and memory, while build time, build memory, fixed application shape, diagnostics, and peak throughput require measurement.
  • PGO can improve native throughput and size using a representative execution profile, subject to distribution support.
  • Native-friendly design favors explicit types, build-time generation, narrow resources, controlled static initialization, and supported libraries.

When a native application fails, trace the build-time and runtime contracts separately: Which beans and conditions existed during AOT processing? Which code and data were reachable to Native Image? Which dynamic operation required metadata? Which native test exercised it? Which performance objective justified the target? That discipline turns native compilation from a packaging trick into a controlled application architecture.
