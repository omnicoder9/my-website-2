Spring Validation

Bean Validation in Spring

A technical guide to Jakarta Validation, built-in and custom constraints, validation groups and sequences, constraint validators, cascaded validation, MVC, WebFlux, method validation, error localization, and testing.

Jakarta Validation 3.1 Spring Framework 7.0.8 Spring Boot 4.1.0 Long-form technical article Vancouver references
Abstract. Jakarta Validation defines a provider-neutral metadata model and runtime API for declaring constraints on object state, container elements, constructor and method parameters, and return values. Spring integrates that model through LocalValidatorFactoryBean, data binding, MVC and WebFlux request handling, method-validation proxies, message resolution, and Spring-created ConstraintValidator instances. The simple case is an annotation such as @NotBlank on a request field. The difficult cases involve object-graph boundaries, null semantics, cross-field invariants, remote checks, validation groups, group ordering and conversion, controller exception models, proxy interception, localization, and the separation between structural validation and domain policy. This article develops those mechanics and provides production-oriented implementations.

Jakarta Validation 3.1 is the Jakarta EE 11 validation specification and requires Java 17 or later. It defines constraint declaration, validation, executable validation, group selection, metadata inspection, message interpolation, value extraction, and provider bootstrapping. Spring Framework 7.0.8 adapts a Jakarta provider to Spring’s Validator, binding, web, and AOP infrastructure.[1][2][12]

1. Validation model

1 Constraints are declared as runtime annotations on types, fields, accessors, parameters, return values, or type uses.
2 A validation call selects one or more groups; the Default group is used when none is supplied.
3 The provider reads metadata and selects a compatible ConstraintValidator for each constrained value.
4 Cascaded and container-element declarations expand validation through the selected object graph.
5 Failed checks produce immutable ConstraintViolation reports with paths, templates, interpolated messages, invalid values, and descriptors.
6 Spring adapts violations to binding errors, web exceptions, or method-validation errors according to the invocation boundary.

The central Jakarta interfaces are ValidatorFactory, Validator, ExecutableValidator, ConstraintViolation, and the metadata API. Validator implementations must be thread-safe and are intended to be obtained from a factory rather than bootstrapped for every request.[3][4]

Validation is not sanitization or authorization A valid DTO can still contain dangerous content for a particular output context, and a syntactically valid operation can still be unauthorized. Escape output, parameterize queries, enforce access control, and apply domain invariants separately.

2. Dependencies and Spring setup

XML 
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-validation</artifactId>
</dependency>

In Spring Boot, the validation starter supplies the Jakarta API and a provider, normally Hibernate Validator. Boot auto-configures validation infrastructure when the executable-validation API and a provider service declaration are available. It also enables proxy-based method validation for eligible @Validated beans.[22][23]

2.1 Explicit LocalValidatorFactoryBean

Java 
@Configuration(proxyBeanMethods = false)
public class ValidationConfiguration {

    @Bean
    LocalValidatorFactoryBean validator(
            MessageSource messageSource) {

        LocalValidatorFactoryBean validator =
                new LocalValidatorFactoryBean();

        validator.setValidationMessageSource(
            messageSource);

        return validator;
    }
}

LocalValidatorFactoryBean is Spring’s central Jakarta Validation bootstrap. It implements jakarta.validation.ValidatorFactory, jakarta.validation.Validator, and Spring’s org.springframework.validation.Validator. When used through Spring’s interface, violations are adapted to FieldError and ObjectError instances.[12][13]

Boot versus explicit configuration Boot applications usually rely on auto-configuration and add a customization only when message interpolation, mappings, clock, parameter names, or provider properties must change. Defining duplicate validator or method-validation infrastructure can create confusing selection and double interception.

3. Built-in constraints

The specification defines the built-in constraints and the supported Java types for each. Applying a constraint to an unsupported type can cause UnexpectedTypeException. Most value constraints treat null as valid so presence can be expressed independently with @NotNull; the specification recommends this separation as a general practice.[5][2]

Java 
public record CreateCustomerRequest(

    @NotBlank
    @Size(max = 120)
    String displayName,

    @NotBlank
    @Email
    String email,

    @Past
    LocalDate birthDate,

    @NotNull
    @Positive
    BigDecimal creditLimit) {
}

3.1 Null semantics

A custom constraint should normally return true for null and let @NotNull express required presence. Combining the two concerns makes the custom annotation harder to reuse for optional values and can duplicate error messages.[2]

4. Constraint placement

Constraints can target fields, JavaBean accessors, record components through their propagated targets, constructor and method parameters, method return values, types, and TYPE_USE locations. Select one consistent access strategy for a model; placing the same logical constraint on both a field and getter can validate it twice.[2][6]

Java 
public final class AccountForm {

    private String username;

    @NotBlank
    @Size(min = 4, max = 40)
    public String getUsername() {
        return username;
    }

    public void setUsername(String username) {
        this.username = username;
    }
}

Property constraints invoke the accessor; field constraints access the field according to provider rules. Avoid constrained getters with remote calls, state changes, or other side effects because validation can invoke them repeatedly.

5. Cascaded and container-element validation

@Valid marks an association, method parameter, return value, or container element for cascaded validation. It is not itself a constraint and does not reject null. Container-element constraints use type-use annotations and value extractors to validate collection elements, map keys and values, optionals, and nested containers.[9][2]

Java 
public record CreateOrderRequest(

    @NotNull
    @Valid
    CustomerInput customer,

    @NotEmpty
    List<@NotNull @Valid OrderLineInput> lines,

    Map<
        @NotBlank String,
        @Positive Integer> quantities,

    Optional<@Email String> notificationEmail) {
}

public record OrderLineInput(
    @NotBlank String sku,
    @Positive int quantity) {
}

When a container element is constrained, a value extractor retrieves the contained values before validation. The specification defines extractors for common JDK containers and allows custom extractors for application-specific wrappers. Deep object graphs can be expensive and can expose unintended data; cascade only across the intended validation boundary.[2]

Persistence relationships are not automatic validation boundaries Adding @Valid across a large bidirectional entity graph can traverse much more state than an API operation intends. Validate command objects or aggregate boundaries rather than recursively validating an entire persistence model by habit.

6. Spring MVC request validation

Spring MVC has two validation paths. An individual @ModelAttribute, @RequestBody, or @RequestPart command object annotated with @Valid or @Validated is validated during binding and can raise MethodArgumentNotValidException. Direct constraints on controller method parameters or the return value trigger built-in method validation and can raise HandlerMethodValidationException.[17]

Java 
@RestController
@RequestMapping("/api/orders")
public final class OrderController {

    @PostMapping
    ResponseEntity<OrderResponse> create(
            @Valid
            @RequestBody
            CreateOrderRequest request) {

        OrderResponse response =
                orderService.create(request);

        return ResponseEntity
            .status(HttpStatus.CREATED)
            .body(response);
    }

    @GetMapping("/{id}")
    OrderResponse get(
            @PathVariable
            @Positive
            long id) {

        return orderService.require(id);
    }
}

The first method uses argument-level object validation. The direct @Positive constraint on the second method parameter invokes controller method validation. @Valid alone only requests cascading and does not itself force method validation.[17]

6.1 Handling errors in the controller

Java 
@PostMapping("/forms")
String submit(
        @Valid
        @ModelAttribute("order")
        OrderForm form,
        BindingResult errors) {

    if (errors.hasErrors()) {
        return "orders/edit";
    }

    orderService.create(form);
    return "redirect:/orders";
}

A BindingResult or Errors parameter must immediately follow the validated command object it represents. For method validation across several parameters, the controller is invoked only when all validation failures are associated with parameters that have a following errors argument; otherwise Spring raises HandlerMethodValidationException.[17]

6.2 Avoid class-level @Validated on modern controllers

Spring MVC has built-in method validation. A controller class annotated with @Validated instead uses AOP proxy-based validation. Spring’s current documentation recommends removing class-level @Validated from controllers to use the built-in MVC path and its web-specific error model.[17]

7. WebFlux validation

WebFlux mirrors the two validation levels. Individual command-object validation raises WebExchangeBindException; direct constraints on handler parameters or return values use method validation and raise HandlerMethodValidationException. The validation engine is synchronous even when the controller returns reactive types, so a validator must not perform blocking network or database work on an event-loop thread.[20][21]

Java 
@RestController
@RequestMapping("/api/reactive/orders")
public final class ReactiveOrderController {

    @PostMapping
    Mono<OrderResponse> create(
            @Valid
            @RequestBody
            Mono<CreateOrderRequest> request) {

        return request.flatMap(orderService::create);
    }
}
Keep request validation local and deterministic Database uniqueness and remote policy checks are business operations, not ideal event-loop validation work. Perform them in a service workflow using the correct scheduler, transaction, timeout, and error model.

8. Defining a custom constraint

A constraint definition combines a runtime annotation marked with @Constraint and one or more compatible ConstraintValidator implementations. Every constraint annotation defines message, groups, and payload elements using the standard signatures.[2][6]

Java 
@Target({
    ElementType.FIELD,
    ElementType.PARAMETER,
    ElementType.RECORD_COMPONENT,
    ElementType.TYPE_USE,
    ElementType.ANNOTATION_TYPE
})
@Retention(RetentionPolicy.RUNTIME)
@Documented
@Constraint(
    validatedBy = AllowedCountryValidator.class)
public @interface AllowedCountry {

    String message() default
            "{customer.country.unsupported}";

    Class<?>[] groups() default {};

    Class<? extends Payload>[]
            payload() default {};
}

8.1 Constraint validator with Spring injection

Java 
public final class AllowedCountryValidator
        implements ConstraintValidator<
            AllowedCountry,
            String> {

    private final CountryPolicy policy;

    public AllowedCountryValidator(
            CountryPolicy policy) {
        this.policy = policy;
    }

    @Override
    public boolean isValid(
            String value,
            ConstraintValidatorContext context) {

        return value == null
                || policy.isSupported(
                    value.toUpperCase(
                        Locale.ROOT));
    }
}

LocalValidatorFactoryBean uses SpringConstraintValidatorFactory by default, so Spring creates custom validators and can inject their dependencies. A validator does not need to be annotated as a component for this creation path.[12][14]

8.2 Validator lifecycle and thread safety

The provider may cache ConstraintValidator instances, their lifecycle is otherwise undefined, and isValid() implementations must be thread-safe. Store immutable annotation configuration initialized once; do not store the current value, request, or mutable per-invocation state in validator fields.[2][7]

Dependency injection does not make remote validation a good idea Spring can inject a repository or HTTP client into a validator, but validation APIs do not provide a natural async contract, transaction model, retry policy, or durable result. Use injected services for local policy/catalog lookups; keep expensive or state-changing checks in the application service.

9. Class-level cross-field constraints

A type-level constraint evaluates an invariant involving several properties. The validator can replace the default object-level path with a property path so web clients receive an actionable field error.[2][8]

Java 
@Target({
    ElementType.TYPE,
    ElementType.ANNOTATION_TYPE
})
@Retention(RetentionPolicy.RUNTIME)
@Documented
@Constraint(
    validatedBy =
        ChronologicalRangeValidator.class)
public @interface ChronologicalRange {

    String message() default
            "{date-range.invalid}";

    Class<?>[] groups() default {};

    Class<? extends Payload>[]
            payload() default {};
}
Java 
@ChronologicalRange
public record CampaignRequest(
    @NotNull Instant startsAt,
    @NotNull Instant endsAt) {
}
Java 
public final class ChronologicalRangeValidator
        implements ConstraintValidator<
            ChronologicalRange,
            CampaignRequest> {

    @Override
    public boolean isValid(
            CampaignRequest value,
            ConstraintValidatorContext context) {

        if (value == null
                || value.startsAt() == null
                || value.endsAt() == null) {
            return true;
        }

        if (value.endsAt()
                .isAfter(value.startsAt())) {
            return true;
        }

        context
            .disableDefaultConstraintViolation();

        context
            .buildConstraintViolationWithTemplate(
                context
                    .getDefaultConstraintMessageTemplate())
            .addPropertyNode("endsAt")
            .addConstraintViolation();

        return false;
    }
}

The validator is intentionally typed to CampaignRequest. A reflection-based reusable variant can expose property names as annotation attributes, but it should cache access metadata safely and fail clearly when configured properties do not exist.

10. Cross-parameter constraints

Executable constraints can validate the relationship among all arguments of a method or constructor. A cross-parameter validator targets ValidationTarget.PARAMETERS and receives the argument array. Use it only for invocation invariants that cannot be represented by a command object; a request or command type with a class-level constraint is usually easier to test and document.[2][30]

Java 
@Target({
    ElementType.METHOD,
    ElementType.CONSTRUCTOR
})
@Retention(RetentionPolicy.RUNTIME)
@Constraint(
    validatedBy =
        DifferentAccountsValidator.class)
public @interface DifferentAccounts {

    String message() default
            "{transfer.accounts.must-differ}";

    Class<?>[] groups() default {};

    Class<? extends Payload>[]
            payload() default {};
}

@SupportedValidationTarget(
    ValidationTarget.PARAMETERS)
public final class DifferentAccountsValidator
        implements ConstraintValidator<
            DifferentAccounts,
            Object[]> {

    @Override
    public boolean isValid(
            Object[] values,
            ConstraintValidatorContext context) {

        if (values == null
                || values.length < 2) {
            return true;
        }

        return !Objects.equals(
            values[0],
            values[1]);
    }
}

11. Composed constraints

A custom annotation can compose existing constraints by placing them on the annotation type. Without @ReportAsSingleViolation, each failing composing constraint can produce its own report. With it, the composed constraint reports one violation when any composing constraint fails.[3]

Java 
@Target({
    ElementType.FIELD,
    ElementType.PARAMETER,
    ElementType.TYPE_USE
})
@Retention(RetentionPolicy.RUNTIME)
@Documented
@NotBlank
@Size(min = 12, max = 128)
@Pattern(
    regexp =
        "^(?=.*[A-Z])(?=.*[a-z])(?=.*\\d).+$")
@ReportAsSingleViolation
@Constraint(validatedBy = {})
public @interface StrongPassword {

    String message() default
            "{password.weak}";

    Class<?>[] groups() default {};

    Class<? extends Payload>[]
            payload() default {};
}

A password strength rule based only on character composition can still be weak against breached-password or context-specific attacks. Validation annotations should reflect the actual security policy rather than create the appearance of strength.

12. Validation groups

A group is a marker interface identifying a subset of constraints. Constraints with no explicit group belong to jakarta.validation.groups.Default. Group inheritance includes constraints from parent group interfaces. When several ordinary groups are requested together, their evaluation order is unspecified unless a group sequence defines one.[2][10]

Java 
public interface CreateChecks {
}

public interface UpdateChecks {
}

public record CustomerCommand(

    @Null(groups = CreateChecks.class)
    @NotNull(groups = UpdateChecks.class)
    UUID id,

    @NotBlank(
        groups = {
            CreateChecks.class,
            UpdateChecks.class
        })
    String name,

    @NotBlank(
        groups = {
            CreateChecks.class,
            UpdateChecks.class
        })
    @Email(
        groups = {
            CreateChecks.class,
            UpdateChecks.class
        })
    String email) {
}
Java 
@PostMapping
void create(
        @Validated(CreateChecks.class)
        @RequestBody
        CustomerCommand command) {
}

@PutMapping("/{id}")
void update(
        @Validated(UpdateChecks.class)
        @RequestBody
        CustomerCommand command) {
}
Groups can couple DTOs to workflows When create and update payloads diverge significantly, separate command types are often clearer than a single object covered in lifecycle groups. Use groups when the model is genuinely shared and the constraint subsets remain comprehensible.

13. Group sequences

@GroupSequence creates ordered validation. Groups are processed sequentially, and evaluation stops before later groups when an earlier group produces a violation. This is useful for delaying expensive checks until cheap structural checks pass. Cyclic sequences are invalid and raise GroupDefinitionException.[2][10]

Java 
public interface StructuralChecks {
}

public interface ExternalPolicyChecks {
}

@GroupSequence({
    StructuralChecks.class,
    ExternalPolicyChecks.class
})
public interface RegistrationChecks {
}

public record RegistrationRequest(

    @NotBlank(groups = StructuralChecks.class)
    @Email(groups = StructuralChecks.class)
    String email,

    @NotBlank(groups = StructuralChecks.class)
    @AllowedCountry(
        groups = ExternalPolicyChecks.class)
    String country) {
}

@PostMapping("/registrations")
void register(
        @Validated(RegistrationChecks.class)
        @RequestBody
        RegistrationRequest request) {
}

13.1 Redefining a class default sequence

A class can redefine its Default group sequence by placing @GroupSequence on the class. The class itself represents its default constraints and must appear in that sequence. This behavior is local to the class and should be used sparingly because callers may not expect ordinary default validation to be ordered or to include additional groups.[2]

Java 
@GroupSequence({
    PurchaseOrder.class,
    CoherenceChecks.class
})
public final class PurchaseOrder {

    @NotNull
    private CustomerId customerId;

    @ValidOrderTotals(
        groups = CoherenceChecks.class)
    private List<OrderLine> lines;
}

14. Group conversion

During cascaded validation, @ConvertGroup maps a requested group on the parent to a different group for the associated object. Conversions apply at the cascade boundary and are not recursively chained. They let a parent workflow reuse a nested type whose group taxonomy differs.[2][11]

Java 
public interface CheckoutChecks {
}

public interface PostalAddressChecks {
}

public record CheckoutCommand(

    @NotNull(groups = CheckoutChecks.class)
    @Valid
    @ConvertGroup(
        from = CheckoutChecks.class,
        to = PostalAddressChecks.class)
    Address shippingAddress) {
}

public record Address(
    @NotBlank(groups = PostalAddressChecks.class)
    String street,
    @NotBlank(groups = PostalAddressChecks.class)
    String postalCode) {
}

15. Service method validation

Outside MVC and WebFlux controller infrastructure, Spring-driven method validation uses MethodValidationPostProcessor and AOP proxies. The target class is annotated with @Validated, optionally naming the default groups for its methods. Parameter and return-value constraints are evaluated around intercepted invocations.[12][15][16]

Java 
@Service
@Validated
public class TransferService {

    @DifferentAccounts
    @NotNull
    public TransferReceipt transfer(
            @NotNull AccountId source,
            @NotNull AccountId target,
            @Positive BigDecimal amount) {

        return performTransfer(
            source,
            target,
            amount);
    }
}
Java 
@Bean
static MethodValidationPostProcessor
        methodValidationPostProcessor() {

    MethodValidationPostProcessor processor =
            new MethodValidationPostProcessor();

    processor.setAdaptConstraintViolations(true);
    return processor;
}

By default, proxy-based method validation raises ConstraintViolationException. With adapted violations enabled, Spring raises MethodValidationException containing parameter-oriented Spring error objects. Method validation inherits ordinary proxy limitations: self-invocation does not cross the proxy, and callers must use the Spring-managed bean reference.[12][15]

16. Programmatic validation

Java 
@Service
public final class ImportValidationService {

    private final Validator validator;

    public ImportValidationService(
            Validator validator) {
        this.validator = validator;
    }

    public void validateRow(CustomerCommand row) {
        Set<ConstraintViolation<CustomerCommand>>
                violations =
            validator.validate(
                row,
                CreateChecks.class);

        if (!violations.isEmpty()) {
            throw new InvalidImportRowException(
                violations);
        }
    }
}

Validator.validate() validates an object for the requested groups and returns a set of violations. validateProperty() and validateValue() target one property; forExecutables() exposes constructor and method parameter/return validation. The metadata API can inspect constraints without validating an instance.[4][30][31]

16.1 Violation information

Java 
for (ConstraintViolation<CustomerCommand>
        violation : violations) {

    log.info(
        "path={}, template={}, message={}, invalid={}",
        violation.getPropertyPath(),
        violation.getMessageTemplate(),
        violation.getMessage(),
        safeValue(
            violation.getInvalidValue()));
}

A violation also exposes root and leaf beans, the constraint descriptor, and executable parameters or return values where relevant. Do not log secrets, passwords, authentication tokens, or full rejected payloads merely because getInvalidValue() makes them available.[29]

A constraint’s message is a message template. A value such as {customer.country.unsupported} is resolved through message interpolation; annotation attributes can be referenced by interpolation rules. LocalValidatorFactoryBean.setValidationMessageSource() integrates a Spring MessageSource instead of relying only on the provider’s default ValidationMessages bundle lookup.[2][13][24]

17.1 Spring error-code adaptation

Spring expands binding and adapted validation errors into code hierarchies such as a constraint code qualified by object, field, and Java type, followed by a generic code. This supports precise localized messages with broad fallbacks. Method validation can similarly adapt violations to MessageSourceResolvable errors.[12][25]

18. HTTP error responses

Java 
@RestControllerAdvice
public final class ValidationErrorHandler {

    @ExceptionHandler(
        MethodArgumentNotValidException.class)
    ResponseEntity<ProblemDetail> invalidBody(
            MethodArgumentNotValidException exception) {

        List<Map<String, Object>> fields =
            exception.getBindingResult()
                .getFieldErrors()
                .stream()
                .map(error -> Map.of(
                    "field", error.getField(),
                    "code", Objects.requireNonNullElse(
                        error.getCode(),
                        "Invalid"),
                    "message",
                        Objects.requireNonNullElse(
                            error.getDefaultMessage(),
                            "Invalid value")))
                .toList();

        ProblemDetail problem =
                ProblemDetail.forStatus(
                    HttpStatus.BAD_REQUEST);

        problem.setTitle("Validation failed");
        problem.setProperty(
            "code",
            "VALIDATION_FAILED");
        problem.setProperty(
            "errors",
            fields);

        return ResponseEntity.badRequest()
            .body(problem);
    }
}

Production APIs should also handle HandlerMethodValidationException for direct parameter and return-value constraints. Keep stable machine codes and paths separate from localized human messages. Do not expose implementation class names, regular expressions, database details, or rejected secrets.[17][18][19]

19. Configuration-property validation

Spring Boot can apply Spring and Jakarta validators while binding configuration properties and raises a bind-validation exception when configured values violate constraints. This is startup configuration validation, not HTTP request validation, and is valuable for failing deployment before invalid endpoints, durations, or capacity limits are used.[26]

Java 
@ConfigurationProperties("partner")
@Validated
public record PartnerProperties(

    @NotNull
    URI endpoint,

    @NotNull
    @DurationMin(seconds = 1)
    @DurationMax(seconds = 30)
    Duration timeout,

    @Min(1)
    @Max(20)
    int retries) {
}

The duration annotations shown are provider or application-specific rather than Jakarta built-ins. When portability is required, define a custom duration constraint using the standard @Constraint contract.

20.3 What to test

  • Null, empty, boundary, and just-outside-boundary values for every custom constraint.
  • Every supported target type and the expected UnexpectedTypeException for unsupported declarations.
  • Thread safety when validators contain caches or injected shared collaborators.
  • Group selection, inheritance, sequence short-circuiting, and group conversion.
  • Cascaded paths and collection/map indices or keys.
  • Localized message interpolation and argument substitution.
  • MVC’s two exception models and WebFlux binding errors.
  • Proxy behavior for service method validation, including self-invocation tests.

MockMvc tests annotated MVC controllers through the DispatcherServlet infrastructure without requiring an HTTP server. WebTestClient provides analogous reactive-stack testing and can also run against a live server.[27][28]

21. Performance and design

21.1 Put cheap checks first

Use group sequences to prevent expensive policy checks when basic shape constraints already fail. A sequence controls evaluation order but does not make an I/O-bound validator asynchronous.

21.2 Reuse validators

Validator and factory implementations are thread-safe, and providers cache parsed metadata and may cache constraint-validator instances. Inject the configured validator rather than rebuilding a factory for each request.[2][4]

21.3 Validate commands, not arbitrary state

Request and application-command types provide explicit validation boundaries. Reusing persistence entities for every input can expose fields, trigger oversized cascades, and mix storage constraints with use-case-specific requirements.

21.4 Keep domain invariants authoritative

Validation improves feedback before execution, but the domain model and transaction must still enforce critical invariants. Concurrent requests can invalidate a uniqueness or balance check after validation but before commit.

22. Diagnostics

22.1 Constraints do not run

Verify that a provider is on the classpath, the object is reached through a validation boundary, @Valid is present for cascading, the intended groups are requested, and method calls cross a Spring proxy where proxy-based validation is used.[12][17]

22.2 UnexpectedTypeException

No unique compatible validator exists for the constraint and declared value type. Check generic validator signatures, primitive versus wrapper types, container-element placement, and conflicting validators.[3]

22.3 Injected validator dependency is null

The validator factory was bootstrapped outside Spring or a non-Spring ConstraintValidatorFactory is configured. Use the application’s LocalValidatorFactoryBean and avoid manually calling Validation.buildDefaultValidatorFactory() inside Spring services.[13][14]

22.4 Expected constraint does not execute

A constraint belongs only to the groups declared on it. Requesting a custom group does not implicitly include Default unless group inheritance or a sequence includes it. Inspect group conversion at cascade boundaries.[2]

22.5 Constraint appears twice

The same logical constraint may be declared on both field and getter, or validation may be invoked through both controller binding and an additional proxy layer. Standardize placement and avoid class-level @Validated on controllers using MVC built-in method validation.[17]

22.6 Validation blocks or times out

A custom validator is performing remote or database I/O. Move the check into an application workflow with explicit timeout, transaction, retry, concurrency, and error semantics.

23. Expert practices

  • Use Jakarta built-ins before creating a custom annotation.
  • Separate nullability from value validity unless the constraint inherently defines presence.
  • Keep ConstraintValidator implementations stateless and thread-safe.
  • Use class-level constraints for cross-field state and command objects for cross-parameter workflows.
  • Use groups sparingly; prefer separate command types when workflows have substantially different shapes.
  • Use group sequences for ordered cheap-to-expensive checks, not as a substitute for a workflow engine.
  • Cascade only across intentional object-graph boundaries.
  • Keep database and remote checks out of request validators where blocking, races, or side effects matter.
  • Use MVC/WebFlux built-in controller method validation and proxy-based validation for service beans.
  • Return stable error codes and paths alongside localized messages.
  • Enforce critical invariants again in the domain and transactional storage layer.
  • Test boundary values, groups, paths, localization, proxy interception, and concurrent execution.

24. Summary

  • Jakarta Validation defines a provider-neutral constraint and metadata model; Spring integrates it with the container, binding, web stacks, and AOP.
  • LocalValidatorFactoryBean exposes one configured engine through Jakarta and Spring validation interfaces.
  • Built-in constraints cover presence, size, numeric bounds, patterns, email syntax, and temporal comparisons.
  • @Valid enables cascaded validation but is not itself a constraint.
  • Container-element constraints validate collection elements, map keys and values, optionals, and nested containers.
  • A custom constraint consists of a @Constraint annotation and compatible ConstraintValidator logic.
  • Spring’s validator factory supports dependency injection into constraint validators.
  • Validator instances may be cached; isValid() must be thread-safe.
  • Class-level and cross-parameter constraints express multi-value invariants.
  • Groups select subsets; group sequences order them and short-circuit later groups after failure.
  • Group conversion changes the group used at a cascade boundary.
  • MVC and WebFlux distinguish command-object binding validation from full handler-method validation.
  • Service method validation is proxy-based and uses @Validated.
  • Stable APIs separate machine error codes from localized validation messages.

When a validation result is surprising, trace the complete declaration: Which element carries the constraint? Which groups were requested? Which validator implementation matched the declared type? Was the value reached through cascading or a value extractor? Which Spring boundary invoked validation? Which exception adapter and message source transformed the violation? That sequence exposes the runtime model beneath concise annotations.
