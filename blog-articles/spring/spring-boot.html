Who Decided That?

Spring Boot’s fundamentals, its configuration model and Actuator, read as one question: for every value a running application uses, who got to decide it, who can still change it, and can the application tell you afterwards?

A Spring Boot application in production is a verdict. Its port, its connection-pool size, its log level, the servlet container it runs in, the endpoints it exposes and the latency buckets it reports were each settled by someone: the framework’s authors, whoever chose the dependencies, the developer, the packaged configuration, the active profile, or the operator who launched it. Boot’s central design move is to let each of these parties override the ones before it without editing their work 1,2. That is why a Boot service can be built once and run anywhere, and it is also why the most common production question about one is not “how does this work?” but “who decided that?”

This article works through the fundamentals (auto-configuration, starters, embedded servers, SpringApplication and the two configuration file formats), the configuration model (profiles, typed properties, environment variables, command-line arguments and external configuration) and Actuator (health, metrics, info, logging, monitoring and Prometheus). Each topic is a numbered plate placed on a six-rung decision ladder, and each carries a small gauge showing who decides it, who can override it, and how well the running application can testify about it. The versions are current as of this writing: Spring Boot 4.1.1, released on 20 August 2026 as a maintenance release of the 4.1 line that arrived on 10 June 3,4, on Spring Framework 7 and a Java 17 baseline 5.

1The question, and the ladder that answers it

Spring Boot did not invent dependency injection or externalised configuration. Both belong to the Spring Framework, whose container grew out of Rod Johnson’s 2002 argument that enterprise Java needed lighter infrastructure 6, and whose inversion-of-control style Martin Fowler named and catalogued in 2004 7. The Framework’s Environment abstraction already held an ordered list of property sources and a set of active profiles 8. What Boot added, from its 1.0 release in April 2014 onward 9, was a fixed policy for that order and a large library of conditional configuration that consults it. The effect is that every decision in a Boot application has a place in a hierarchy, and the hierarchy is documented.

The ladder below compresses that hierarchy into six rungs, ordered by when a decision is fixed and by who fixes it. D0 is the framework default: a value written by Boot’s authors into an auto-configuration class or a properties class. D1 is the classpath, fixed by whoever edits the build. D2 is code: an @Bean method, a SpringApplication setter, a default in a typed properties class. D3 is a packaged file, application.properties or application.yml inside the jar. D4 is a profile-specific file. D5 is deploy time: operating-system environment variables, Java system properties, command-line arguments and files mounted beside the jar. The reference documentation’s own ordering of property sources and config-data files is the backbone of rungs D2 to D5 1.

Two further quantities sit beside the rung. The first is reach: which later layers can still change a decision once it is made. A framework default can usually be overridden from almost anywhere; a command-line argument can be overridden from nowhere outside tests. The second is witness: the best evidence a running application can give about who decided. Grade W3 means a value with its origin, down to a file, line and column, as the env and configprops endpoints report for property sources 10,11. W2 means an outcome with its reason, as the conditions report gives for auto-configuration and the loggers endpoint gives for inherited levels 12,13. W1 means the value alone. No plate in this article sits at W0, but several reach W1 only because an endpoint happens to report the result.

Every plate has the same five fields: what it decides, who decides it by default, who can override it, what witnesses it at runtime, and how it typically fails. The gauge on each plate, which this article calls a shadow strip, shows the same information graphically: the deciding rung as a solid cell, the rungs that can still override it hatched, and three brass pips for the witness grade. A small runtime tag marks the two plates whose decision can be changed after the application has started. The plates are collected into a ledger at the end, where the lab computes what the ladder shows.

2Fundamentals: SpringApplication, starters, auto-configuration and the embedded server

A Boot application starts from an ordinary main method. The @SpringBootApplication annotation combines three things: @SpringBootConfiguration (a @Configuration marker), @EnableAutoConfiguration, and @ComponentScan rooted at the annotated class’s package 14. SpringApplication.run creates an Environment, prepares an application context of the right type (servlet, reactive or none), refreshes it, and starts the embedded web server if there is one 15.

The startup sequence is observable as application events, published in a documented order: ApplicationStartingEvent, ApplicationEnvironmentPreparedEvent, ApplicationContextInitializedEvent, ApplicationPreparedEvent, ApplicationStartedEvent, an AvailabilityChangeEvent reporting LivenessState.CORRECT, ApplicationReadyEvent, and finally an AvailabilityChangeEvent reporting ReadinessState.ACCEPTING_TRAFFIC 15. That last pair matters later, because Actuator’s liveness and readiness probes are built on exactly these availability states 16. When startup fails, registered failure analysers turn common exceptions (a port already in use, a missing bean) into a readable description and a suggested action rather than a stack trace 15.

Starter dependencies

A starter is a dependency descriptor with no code of its own: a curated set of transitive dependencies for one capability, with versions managed by Boot’s dependency-management bill of materials 17. Spring Boot 4.0 reorganised the codebase into smaller, focused modules, and the starters followed: the web starter for Spring MVC is now spring-boot-starter-webmvc, and most technologies have a companion test starter 5. So-called classic starters that bundle every auto-configuration, as Boot 3 did, remain available for quick migrations but are deprecated 5. Boot 4 also moved JSON support to Jackson 3, whose packages begin tools.jackson, while keeping a separate Jackson 2 module 16,18.

Auto-configuration

Auto-configuration is ordinary @Configuration guarded by conditions. Candidate classes are listed in META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports inside each auto-configuration jar and are annotated @AutoConfiguration; each one declares conditions such as @ConditionalOnClass, @ConditionalOnMissingBean and @ConditionalOnProperty 21. The design rule is non-invasiveness: auto-configuration backs away as soon as you define your own bean of the same kind 2. That works because user configuration is registered before auto-configuration is evaluated, so a @ConditionalOnMissingBean condition can see what you declared 21. Two tools make auto-configuration legible. Starting with --debug prints a conditions evaluation report to the log, and the conditions endpoint serves the same report at runtime: positive matches, negative matches, and the reason for each 2,12. Exclusions can be made in code with @SpringBootApplication(exclude = …) or from any property source with spring.autoconfigure.exclude 2.

The embedded server

A Boot web application carries its server inside the jar. Tomcat is the default for servlet applications; Jetty is the supported alternative; reactive applications use Reactor Netty by default 22,23. Spring Boot 4 is based on Jakarta EE 11 with a Servlet 6.1 baseline, and because Undertow was not compatible with Servlet 6.1, Boot 4.0 removed Undertow support entirely, including its starter 5,24. Switching to Jetty is a build change.

Most server tuning is exposed as server.* properties, and anything the properties do not cover can be reached with a WebServerFactoryCustomizer bean 23. Graceful shutdown, which lets in-flight requests finish before the context closes, is controlled by server.shutdown and bounded by spring.lifecycle.timeout-per-shutdown-phase 25. The executable jar that holds all of this uses Boot’s nested-jar format and launches with plain java -jar; Boot 4.0 removed the Unix launch scripts that once made such jars “fully executable” 5,26.

3The packaged answer: application.properties and application.yml

Whatever ships inside the jar is the application’s own answer to every configuration question. Boot looks for application.properties and application.yaml first on the classpath (its root, then a /config package) and then in the current directory (the directory, then its config/ subdirectory, then that subdirectory’s immediate children), each location overriding the ones before it 1. Within the jar, these files are rung D3.

A properties file is a flat list of keys in the java.util.Properties format 27. Files are read as ISO-8859-1 by default; Boot 4.1 added an encoding attribute to spring.config.import so an imported file can be read as UTF-8 instead 1,28. Placeholders such as ${app.name} and ${username:Unknown} resolve against the whole Environment when the value is used, and the reference documentation recommends always writing placeholder names in canonical kebab-case form 1. The next section shows why that advice is not stylistic.

YAML expresses the same keys as a hierarchy, and Boot flattens it into the same key space: nested maps become dotted names and lists become [index] suffixes 1. A YAML file can also hold several logical documents separated by ---, and properties files can do the same with a #--- comment line; each document can carry activation conditions such as spring.config.activate.on-profile or on-cloud-platform 1.

Two YAML hazards recur. Boot reads YAML through SnakeYAML 1, which resolves plain scalars under YAML 1.1 rules, so unquoted yes, no, on and off become booleans and a number with a leading zero is read as octal; the YAML 1.2 specification narrowed these rules, but a 1.1 parser does not follow it 29. And * has a special meaning in YAML, which is why the Actuator documentation tells you to quote it when exposing every endpoint 16. If a .properties and a .yaml file sit at the same location, the .properties file wins, and the documentation recommends picking one format per application 1.

4Configuration I: profiles and typed properties

Profiles

A profile names an environment or a mode. Beans annotated @Profile("prod") register only when prod is active, and files named application-prod.properties or application-prod.yaml load alongside the base file and override it 1,30. When no profile is set, the default profile applies, so application-default.* is loaded 1. Profiles are activated with spring.profiles.active, which is usually supplied at D5 through SPRING_PROFILES_ACTIVE or a command-line argument, and a profile group lets one name expand into several 30.

The lab implements the documented rules. Activating production with the group above yields production, proddb, prodmq. Profile-specific files apply last-wins in the order the profiles were activated 1, so the same two files give two different answers depending only on the order of the active list: with prod,live the pool size is 50, with live,prod it is 20. Nothing fails and nothing is logged as a conflict.

Profile expressions allow !, & and |, and Spring Framework rejects an expression that mixes & and | without parentheses 31. The lab’s parser follows the same rule and rejects “prod & cloud | staging”; with parentheses, (prod & cloud) | staging is true for 3 of the 5 profile sets it was evaluated against.

@ConfigurationProperties

@Value("${…}") injects one value at a time. @ConfigurationProperties binds a whole prefix to a typed object, validates it, and generates metadata that IDEs use for completion 1,32. Records are bound through their constructor, @DefaultValue supplies defaults for missing properties, Duration and DataSize values accept units such as 250ms or 10MB, and @Validated with Jakarta Bean Validation constraints turns a bad value into a startup failure rather than a runtime surprise 1.

The typed class is registered with @ConfigurationPropertiesScan or @EnableConfigurationProperties, and constructor binding requires compilation with -parameters, which Boot’s Maven parent and Gradle plugin configure for you 1. Boot 4.1 changed one behaviour here: an Optional constructor parameter with no value now binds as Optional.empty() rather than null 28.

The plate below records a subtle point from the reference documentation. Defaults declared in a properties class are not reflected in the Environment 1. If a class says enabled defaults to false and no source sets it, the Environment has no such property, so a @Value placeholder or a custom condition that reads it sees nothing. The configprops endpoint does show the bound value, and where a value came from a property source it shows the origin too 11; a code-level default has no origin to show.

5Configuration II: the operator’s layers

Everything so far travels inside the artifact. The configuration model’s purpose, stated in the Twelve-Factor App’s third factor, is the opposite: configuration that varies between deploys should live outside the code, and environment variables are the canonical carrier 33. Boot orders its property sources so that deploy-time sources outrank packaged ones. In increasing precedence the list runs: default properties set on SpringApplication, @PropertySource annotations, config data files, random values, operating-system environment variables, Java system properties, JNDI, servlet context and config parameters, SPRING_APPLICATION_JSON, command-line arguments, and then test-only sources 1. Config data files have their own inner order: packaged base file, packaged profile file, external base file, external profile file 1.

The lab replays one realistic launch through that order: a jar with a base and a prod file, an external config directory with two files, three environment variables, one system property and one command-line argument. The result is 20 definitions of 9 keys, of which 11 (55.0%) are shadowed. Only 3 of the 9 running values come from the jar’s files, 5 come from deploy-time sources, and 4 keys run with a value different from the one the artifact itself would give.

Environment variables

Most platforms forbid dots and dashes in variable names, so Boot maps them: replace dots with underscores, remove dashes, convert to upper case, and write list indices as numbers surrounded by underscores 1. server.servlet.context-path becomes SERVER_SERVLET_CONTEXTPATH. The mapping throws information away. Of the 25 real Boot property names the lab converts, 11 (44.0%) contain a dash that the environment form cannot carry, and one, a map key containing dots under management.metrics.distribution, cannot be told apart from a longer path at all. The binder copes by comparing names in a uniform form rather than reconstructing them.

That comparison is also why the canonical-name advice for placeholders matters. The table reproduces, from the lab’s model of the documented rules 1, which stored names each placeholder picks up.

External configuration

The files and directories outside the jar are the operator’s configuration surface. spring.config.location replaces the default search locations, spring.config.additional-location adds to them, and spring.config.import pulls in further files from any document; imports are loaded once, rank above the file that imported them, and must be marked optional: if their absence should not stop startup 1. Because these three properties are read before any file is loaded, they must themselves come from an environment variable, a system property or an argument 1.

Kubernetes ConfigMaps and Secrets can be mounted as files 34, and Boot’s configtree: prefix reads such a directory tree as properties, one file per key, which keeps secrets out of the process environment 1. Boot does not encrypt property values itself; it provides EnvironmentPostProcessor as the hook, and the documentation points to Spring Cloud Vault for secret storage 1.

6Actuator I: health, info and logging

Actuator adds production-ready endpoints: health, info, metrics, loggers, env, conditions and about twenty others 16. Two defaults govern all of them. Access to every endpoint except shutdown and heapdump is unrestricted, and only health is exposed, over HTTP and over JMX 16. Everything else must be exposed deliberately, and if Spring Security is present with no SecurityFilterChain of your own, every endpoint but health is secured by default 16.

Health endpoints

Health is a tree of contributors. Each HealthIndicator returns a Status; composites group them; a StatusAggregator sorts the statuses by an ordered list and reports the first 16. The order is configurable with management.endpoint.health.status.order, and by default DOWN and OUT_OF_SERVICE map to HTTP 503 while everything else maps to 200 16. The lab uses the default order in Boot’s SimpleStatusAggregator source, DOWN, OUT_OF_SERVICE, UP, UNKNOWN; the 503 count below does not depend on how UP and UNKNOWN are ranked. Enumerating three indicators over four statuses, the lab finds 56 of 64 combinations return 503: one bad dependency is enough. With five indicators whose individual failure rates are between 0 and 1% per check, the composite reports DOWN on 1.642% of checks, more than any indicator alone.

Health groups let different consumers see different trees. Boot configures two by default, liveness and readiness, backed by the application availability states published at startup, and serves them at /actuator/health/liveness and /actuator/health/readiness; management.endpoint.health.probes.add-additional-paths also serves them on the main port as /livez and /readyz 16. Kubernetes restarts a container whose liveness probe fails and stops routing to one whose readiness probe fails 35. The documentation is explicit that liveness should not depend on external systems, because a shared dependency’s failure would restart every instance at once 16.

The lab puts a number on that warning. With liveness wired to a shared database, a probe period of 10 seconds and a failure threshold of 3, any outage of 30 seconds or more fails every pod together. If outage durations are exponential with a mean of 45 seconds, 51.3% of outages restart the whole fleet of 40 pods, an expectation of 20.5 restarts per outage delivered all at once; the simulated rate over 20,000 outages is 51.6%. At a 90-second mean the expectation rises to 28.7. Wired into readiness instead, the same check drains traffic and restarts nothing.

Logging

Boot uses Commons Logging internally and defaults to Logback through the starters, logging at INFO to the console 37,38. Levels are set per logger with logging.level.*, and log groups such as the predefined web and sql groups change several loggers at once 37. Structured logging in the Elastic Common Schema, Graylog Extended Log Format or Logstash format can be switched on for the console or file with logging.structured.format.* 37. Custom Logback configuration goes in logback-spring.xml, which, unlike logback.xml, can use Boot’s <springProfile> and <springProperty> extensions 37.

Logging is one of the two plates whose decision can change after startup. The loggers endpoint lists every logger with its configured and effective level, and a POST sets a new level on a running instance 13. That is useful during an incident and hazardous afterwards: the change lives only in memory, is visible only to whoever looks, and vanishes on the next restart.

7Actuator II: metrics, monitoring and Prometheus

Metrics

Boot’s metrics are Micrometer’s. Micrometer is a vendor-neutral facade with timers, counters, gauges and distribution summaries, and Boot auto-configures a MeterRegistry and instruments the JVM, the web layer, data sources and more 39,40. The request timer http.server.requests is recorded for every Spring MVC and WebFlux request, tagged by method, URI template, status, outcome and exception 39. Custom meters are one injection away.

Tags are where metrics go wrong. Each distinct combination of tag values is a separate time series, and the Prometheus project’s own guidance is to keep label cardinality low and never to use unbounded values such as user identifiers 41. Boot’s URI tag uses the route template rather than the raw path for this reason 39, and a MeterFilter can deny, rename or cap tags 40.

Monitoring: exposure, ports and security

Monitoring means deciding who can see which endpoint over which transport. Exposure is controlled with management.endpoints.web.exposure.include and exclude (exclude wins), access with management.endpoint.<id>.access and the application-wide ceiling management.endpoints.access.max-permitted 16. Actuator can run on a separate port with management.server.port, which keeps it off a public listener, and the discovery page at /actuator lists whatever is exposed 16,42. A separate port has a cost the documentation spells out: a probe on the management port can succeed while the main connector is failing, which is why the probe groups can be mirrored onto the main port 16.

Prometheus integration

Adding micrometer-registry-prometheus is the whole integration on the application side: Boot configures a PrometheusMeterRegistry and a prometheus endpoint that serves the registry in the Prometheus text exposition format (or OpenMetrics when asked) at /actuator/prometheus, once it is exposed 16,43–45. Boot 4.1 manages Prometheus Client 1.5.1 and Micrometer 1.17.0 28. Prometheus then scrapes the endpoint on an interval 46.

Latency needs a decision about distribution. Micrometer can publish client-side percentiles, computed inside each instance, or a percentiles histogram, which publishes bucket counters that Prometheus aggregates and interpolates with histogram_quantile() 40,47,48. The Prometheus documentation explains the trade: summaries are accurate for one instance but cannot be aggregated; histograms can be aggregated, and their error depends on the bucket layout 47.

The lab measures both halves. Against 200,000 simulated requests with a true median of 121.0 ms and a true p99 of 883.0 ms, the common default client buckets estimate the median +20.7% high, because the whole of the 100–250 ms range is one bucket; hand-picked SLO buckets cut that to +10.2%; a fine geometric layout gets within 0.1% at the cost of 112 series per label set instead of 14. The p99 is estimated well by all three here only because a bucket boundary happens to sit near it.

The other half is aggregation. Four instances with different latency profiles serve one fleet whose true p99 is 616.9 ms. Averaging the four per-instance p99s gives 431.5 ms (-30.1%), weighting by traffic makes it worse (-49.3%), and taking the maximum overshoots (+53.9%). Summing the instances’ histogram buckets and interpolating once gives 620.6 ms (+0.6%). A percentile is not additive; a bucket count is.

This is the concrete reason to publish histograms for anything that will be read across instances, and to reserve client-side percentiles for a single process. Tail latency is where the fleet-level view matters most, since in a fan-out system the slowest component sets the response time 49, and it is the latency signal that Google’s monitoring guidance puts first among its four golden signals 50.

The division is not statistical; it is structural, and the lab’s split shows it exactly. The practical consequence is a design rule. When a decision may need to be explained in production, route it through the Environment: bind it with @ConfigurationProperties rather than a constant, guard optional infrastructure with @ConditionalOnProperty rather than classpath accident alone, and publish build and Git information so the info endpoint can say which artifact is running. class Expr:
    """Tiny parser for Spring profile expressions: ! & | ( ). Mixing & and |
    without parentheses is rejected, as in Spring Framework's Profiles.of."""
    def __init__(self, s):
        self.t = [c for c in s.replace("(", " ( ").replace(")", " ) ").replace("!", " ! ").replace("&", " & ").replace("|", " | ").split()]
        self.i = 0
    def peek(self):
        return self.t[self.i] if self.i < len(self.t) else None
    def take(self):
        tok = self.t[self.i]; self.i += 1; return tok
    def parse(self):
        e = self.seq()
        if self.peek() is not None:
            raise ValueError("trailing")
        return e
    def seq(self):
        terms = [self.unary()]; op = None
        while self.peek() in ("&", "|"):
            o = self.take()
            if op and o != op:
                raise ValueError("mixed & and | need parentheses")
            op = o; terms.append(self.unary())
        if op is None:
            return terms[0]
        return (op, terms)
    def unary(self):
        tok = self.take()
        if tok == "!":
            return ("!", self.unary())
        if tok == "(":
            e = self.seq(); assert self.take() == ")"; return e
        return tok

def ev(e, act):
    if isinstance(e, str):
        return e in act
    if e[0] == "!":
        return not ev(e[1], act)
    if e[0] == "&":
        return all(ev(x, act) for x in e[1])
    return any(ev(x, act) for x in e[1])

def lat_sample(rnd, median, sigma, tail_p, tail_median):
    if rnd.random() < tail_p:
        return tail_median * math.exp(rnd.gauss(0, 0.5))
    return median * math.exp(rnd.gauss(0, sigma))

def true_q(sorted_x, q):
    i = q * (len(sorted_x) - 1)
    lo = int(math.floor(i)); hi = min(lo + 1, len(sorted_x) - 1)
    return sorted_x[lo] + (sorted_x[hi] - sorted_x[lo]) * (i - lo)

def hist_counts(xs, bounds):
    cnt = [0] * (len(bounds) + 1)
    import bisect
    for x in xs:
        cnt[bisect.bisect_left(bounds, x)] += 1
    return cnt

def hist_quantile(q, bounds, counts):
    """histogram_quantile semantics: linear interpolation inside the bucket; the
    lowest bucket's lower bound is 0; a rank in the +Inf bucket returns the
    highest finite bound."""
    total = sum(counts)
    rank = q * total
    cum = 0
    for i, c in enumerate(counts):
        if cum + c >= rank and c > 0:
            if i == len(bounds):
                return bounds[-1]
            lo = 0.0 if i == 0 else bounds[i - 1]
            hi = bounds[i]
            return lo + (hi - lo) * (rank - cum) / c
        cum += c
    return bounds[-1]

def evaluate(classpath, user_beans, props, exposed):
    beans = set(user_beans)            # user configuration is registered first
    report = []
    for name, conds, provides in AUTOS:
        ok = True; why = []
        for c in conds:
            kind = c[0]
            if kind == "class":
                r = c[1] in classpath; why.append(f"@ConditionalOnClass {c[1]} {'found' if r else 'absent'}")
            elif kind == "missing":
                r = c[1] not in beans; why.append(f"@ConditionalOnMissingBean {c[1]} {'none' if r else 'PRESENT'}")
            elif kind == "bean":
                r = c[1] in beans; why.append(f"@ConditionalOnBean {c[1]} {'present' if r else 'none'}")
            elif kind == "prop":
                v = props.get(c[1], "true" if c[2] else None)
                r = v == "true"; why.append(f"@ConditionalOnProperty {c[1]}={v}")
            elif kind == "exposed":
                r = c[1] in exposed; why.append(f"endpoint {c[1]} {'exposed' if r else 'not exposed'}")
            ok = ok and r
            if not r:
                break
        if ok:
            beans.update(provides)
        report.append((name, ok, why))
    return report, beans

def rankdata(v):
    s = sorted(range(len(v)), key=lambda i: v[i])
    r = [0.0] * len(v); i = 0
    while i < len(v):
        j = i
        while j + 1 < len(v) and v[s[j + 1]] == v[s[i]]:
            j += 1
        for k in range(i, j + 1):
            r[s[k]] = (i + j) / 2 + 1
        i = j + 1
    return r

def pearson(a, b):
    ma = sum(a)/len(a); mb = sum(b)/len(b)
    num = sum((x-ma)*(y-mb) for x, y in zip(a, b))
    den = math.sqrt(sum((x-ma)**2 for x in a) * sum((y-mb)**2 for y in b))
    return num / den
