Spring Framework Data Access

Transactions in Spring

An expert guide to ACID semantics, Spring’s transaction abstraction, declarative and programmatic demarcation, @Transactional, propagation, isolation, rollback rules, reactive transactions, synchronization, and testing.

Target: Spring Framework 7.0.8 Imperative and reactive models Long-form technical article Vancouver references
Abstract. Spring transaction management is a policy and resource-coordination abstraction over concrete transaction systems such as JDBC, JPA, Hibernate, JTA, JMS, and R2DBC. It does not create atomicity or isolation by annotation; those guarantees are delivered by the underlying resource manager within the scope that Spring begins, joins, suspends, commits, or rolls back. Declarative transactions apply metadata through AOP interception, while programmatic APIs expose the same transaction-definition model through callbacks or direct manager operations. Correct use requires understanding the difference between logical and physical transactions, which propagation modes start independent work, when isolation settings apply, how rollback-only state propagates, and why remote calls or multiple non-XA resources do not become atomic merely because they execute inside one Java method.

Spring Framework 7.0.8 is the stable reference version used here. Spring provides a consistent transaction model across JDBC, JPA, Hibernate, JTA, and reactive resource managers, while preserving the semantics and limitations of each underlying transaction system.[1][2]

1. ACID principles

ACID abbreviates atomicity, consistency, isolation, and durability. These properties describe the intended behavior of database transactions under concurrency, errors, crashes, and partial execution.[3]

AtomicityThe transaction’s durable database effect is all-or-nothing: every operation commits, or the transaction is rolled back.
ConsistencyA successful transaction moves the database from one valid state to another under declared constraints and correct application logic.
IsolationConcurrent transactions are prevented from observing or producing specified classes of anomalies.
DurabilityOnce commit succeeds, the resource manager preserves the committed state according to its durability configuration.

1.1 Atomicity is bounded by participating resources

A local JDBC or JPA transaction normally controls one database resource. Updating a database and then calling an HTTP service does not make the remote call part of that atomic transaction. Spring explicitly does not propagate transaction contexts across ordinary remote calls. Coordinating multiple independent resources atomically requires an appropriate distributed transaction protocol and compatible resources, or an application-level pattern such as an outbox, saga, or compensating action.[4]

1.2 Consistency is not supplied by rollback alone

Transactions preserve database constraints only when those constraints exist and the transaction’s logic is correct. Primary keys, foreign keys, uniqueness, checks, and version predicates enforce invariants under concurrency. An application can commit inconsistent business state if the invariant is neither encoded in the database nor enforced correctly at the chosen isolation level.

1.3 Isolation is a concurrency contract

SQL isolation levels are described through prohibited anomalies: dirty reads, non-repeatable reads, phantom reads, and serialization anomalies. A database may provide stronger behavior than the minimum associated with a named level. PostgreSQL, for example, treats READ_UNCOMMITTED as READ_COMMITTED, and its repeatable-read implementation prevents phantom reads even though the standard permits them at that level.[5]

1.4 Durability begins at successful commit

Durability is a property of the database, storage stack, replication policy, and commit configuration. A Spring interceptor can request commit and report a transaction-system exception; it cannot make unsafe database settings durable. Commit can also fail after application work has completed, which is why side effects performed before commit require careful coordination.

A transaction is not a distributed lock around a method It has a concrete resource scope, isolation policy, lifecycle, and failure model. CPU work, in-memory changes, filesystem writes, emails, and arbitrary network calls are not automatically rolled back.

2. Spring’s transaction abstraction

TransactionManager is the common marker for imperative and reactive managers. PlatformTransactionManager is the central imperative strategy; ReactiveTransactionManager is its reactive counterpart. Application code usually uses declarative interception or a template rather than invoking the imperative manager directly.[6][7]

1 Transaction metadata supplies propagation, isolation, timeout, read-only status, labels, and rollback policy.
2 The selected manager determines whether to join, create, suspend, or reject a transaction.
3 Resource infrastructure binds the current connection, session, or entity manager to the execution context.
4 Application data access resolves the bound resource.
5 Normal completion requests commit; configured failure conditions request rollback.
6 Synchronizations run at defined lifecycle phases and resources are released.

2.1 TransactionDefinition

TransactionDefinition describes propagation, isolation, timeout, read-only status, and an optional name. Its defaults are REQUIRED, datastore-default isolation, datastore-default timeout, and read-write. Isolation and timeout apply only when a new physical transaction starts; they do not redefine an existing transaction that the method merely joins.[8]

2.2 TransactionStatus

TransactionStatus represents an imperative transaction execution. It exposes whether the transaction is new, rollback-only, completed, or savepoint-backed; permits programmatic rollback-only marking; and provides savepoint operations when supported by the transaction manager.[9]

2.4 JDBC configuration

Java 
@Configuration(proxyBeanMethods = false)
@EnableTransactionManagement(
    rollbackOn = RollbackOn.ALL_EXCEPTIONS)
class JdbcTransactionConfiguration {

    @Bean
    JdbcTransactionManager transactionManager(
            DataSource dataSource) {

        JdbcTransactionManager manager =
                new JdbcTransactionManager(dataSource);

        manager.setValidateExistingTransaction(true);
        return manager;
    }
}

Since Spring Framework 6.2, annotation-driven transaction management can globally choose rollback for all exceptions rather than retaining the historical unchecked-exception default. Per-method rollback rules still take precedence over the global default.[10][13]

3. Declarative transactions

Declarative transaction management is implemented through Spring AOP. Transaction metadata is read from annotations or XML and applied by a TransactionInterceptor using the selected transaction manager. The target method remains focused on business logic, while the proxy performs begin/join, commit, and rollback behavior around the invocation.[4]

Java 
@Service
public final class FundsTransferService {
    private final AccountRepository accounts;

    public FundsTransferService(
            AccountRepository accounts) {
        this.accounts = accounts;
    }

    @Transactional
    public void transfer(
            long sourceId,
            long targetId,
            BigDecimal amount) {

        int debited =
                accounts.debitIfSufficient(
                        sourceId,
                        amount);

        if (debited != 1) {
            throw new InsufficientFundsException(
                    sourceId,
                    amount);
        }

        int credited =
                accounts.credit(targetId, amount);

        if (credited != 1) {
            throw new AccountNotFoundException(
                    targetId);
        }
    }
}

3.1 Proxy interception boundary

In the default proxy mode, only calls entering through the proxy are intercepted. A method on the target object calling another method on the same target—self-invocation—does not pass through the proxy, so the inner method’s transaction annotation is not independently applied. Transactional behavior should be placed on externally invoked service methods, moved to another collaborator, invoked through programmatic APIs, or implemented with AspectJ weaving when self-invocation interception is truly required.[12]

Java 
@Service
class ImportService {

    public void importAll(List<Record> records) {
        for (Record record : records) {
            importOne(record); // Direct self-call: no proxy hop.
        }
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void importOne(Record record) {
        // The REQUIRES_NEW metadata is not applied
        // when called directly from importAll().
    }
}

The same proxy limitation means transaction annotations should not be relied upon from constructors or @PostConstruct methods, before the proxy is fully available.

3.2 Thread-bound versus reactive context

Imperative transactions are normally bound to the current thread. Starting a new thread, using an executor, or crossing an asynchronous boundary does not carry the transaction with it. Reactive transactions use Reactor context instead of thread-local state and require all participating operations to remain in the same reactive pipeline.[11]

3.3 Annotation placement and precedence

@Transactional may be declared on a class or method. A class-level annotation supplies defaults for methods of that class; method-level metadata can override it. Put transaction semantics on concrete implementation classes and public service methods for the clearest proxy behavior. Annotation metadata is converted into Spring transaction attributes before interception.[11]

Isolation, timeout, and most resource-level characteristics matter only when the invocation starts a new physical transaction. When a REQUIRED method joins an existing transaction, the outer transaction’s characteristics apply. Enabling validateExistingTransaction causes incompatible inner isolation and read-only declarations to be rejected rather than silently ignored.[8][14]

3.5 Multiple managers

Java 
@Transactional(
    transactionManager = "ordersTransactionManager")
public void changeOrder(...) {
}

@Transactional(
    transactionManager = "auditTransactionManager")
public void writeAudit(...) {
}

Selecting two local managers for two method calls does not create atomic coordination between their resources. One can commit while the other rolls back. Use JTA/XA or an explicitly eventual-consistency design when a cross-resource invariant is required.

4. Propagation

Propagation describes how a transactional method behaves relative to an existing transaction. It distinguishes logical method scopes from physical resource transactions. Every intercepted method has a logical scope; several logical scopes may map to one physical transaction.[15]

ModeExisting transactionNo existing transaction
REQUIREDJoin itCreate one
REQUIRES_NEWSuspend it and create an independent transactionCreate one
NESTEDCreate a savepoint-backed nested scope when supportedCreate a normal transaction
SUPPORTSJoin itRun without a physical transaction
MANDATORYJoin itThrow an exception
NOT_SUPPORTEDSuspend it and run non-transactionallyRun non-transactionally
NEVERThrow an exceptionRun non-transactionally

4.1 REQUIRED: shared physical transaction

REQUIRED is the default. If a transaction exists, an inner method participates in the same physical transaction while retaining a logical scope that can mark rollback-only. If an inner scope marks the shared transaction rollback-only and the outer scope later attempts to commit, Spring throws UnexpectedRollbackException so the caller is not told that a commit succeeded when the transaction actually rolled back.[15][16]

Java 
@Transactional
public void placeOrder(OrderCommand command) {
    inventory.reserve(command); // REQUIRED
    payments.authorize(command); // REQUIRED
    orders.persist(command);     // REQUIRED
}

Catching an exception from a participating method does not necessarily make the transaction committable. The inner infrastructure or persistence provider may already have marked the physical transaction rollback-only.

4.2 REQUIRES_NEW: independent physical transaction

REQUIRES_NEW suspends the outer transaction and starts an independent physical transaction. It can commit or roll back independently and can use its own isolation, timeout, and read-only settings. The suspended outer transaction retains its resource while the inner transaction acquires another resource—commonly another connection. A pool sized only to the number of worker threads can therefore deadlock or exhaust under nested REQUIRES_NEW use.[15]

Java 
@Service
class AuditService {

    @Transactional(
        propagation = Propagation.REQUIRES_NEW)
    public void record(AuditRecord record) {
        auditRepository.insert(record);
    }
}

Independent audit commits can be useful, but they can also create a durable statement about outer work that eventually rolls back. Record the attempted state accurately, or use a transaction-bound outbox when the audit or message must correspond only to committed business state.

4.3 NESTED: savepoint within one physical transaction

NESTED normally uses a savepoint inside the existing physical transaction. Rolling back the nested scope returns the shared transaction to that savepoint; the outer transaction may continue. The nested work is not independently committed: an outer rollback still undoes it. Out of the box, nested propagation is primarily supported by JDBC transaction managers with savepoint-capable drivers; it is not a portable JPA subtransaction facility.[17][18]

4.4 SUPPORTS

SUPPORTS joins an existing transaction but otherwise runs without a physical transaction. With transaction synchronization enabled, this scope can still share resources across its execution, so it is not necessarily equivalent to an entirely unmanaged method call.[17]

4.5 Contract-enforcing modes

MANDATORY declares that the method is invalid outside an existing transaction. NEVER declares the inverse. These modes are useful for enforcing architectural assumptions in low-level components but should not substitute for clear service boundaries.

5. Isolation levels

Spring’s isolation constants correspond to JDBC isolation levels. DEFAULT delegates to the datastore. A custom isolation setting applies only when the method starts a new transaction; joining an existing transaction does not alter that physical transaction’s isolation.[8]

Spring levelDirty readNon-repeatable readPhantom read
READ_UNCOMMITTEDPermittedPermittedPermitted
READ_COMMITTEDPreventedPermittedPermitted
REPEATABLE_READPreventedPreventedPermitted by the standard model
SERIALIZABLEPreventedPreventedPrevented

5.1 Anomalies

Dirty read
Reading data written by another transaction that has not committed.
Non-repeatable read
Reading the same row twice and observing a committed modification between reads.
Phantom read
Repeating a predicate query and observing a changed set of matching rows.
Serialization anomaly
A committed concurrent outcome that cannot be explained by any serial ordering of the transactions.

The named isolation level is only a portable request. Databases implement concurrency through locks, multiversion concurrency control, predicate locking, or hybrids, and may reject unsupported levels or provide stronger guarantees. Validate behavior on the production database.[5]

5.2 READ_COMMITTED

Read committed prevents dirty reads but can expose a new committed snapshot to each statement. It is often the database default and provides high concurrency, but a read-modify-write invariant may need a guarded update, explicit lock, version column, or stronger isolation.

5.3 REPEATABLE_READ

Repeatable read stabilizes previously read row values under the standard model. Database-specific snapshot implementations can still permit serialization anomalies. Do not infer full serial behavior from a stable snapshot.

5.4 SERIALIZABLE

Serializable aims to make committed concurrent execution equivalent to some serial order. Systems can enforce this through blocking, conflict detection, or both. Applications must be prepared to retry complete transactions after serialization failure; retrying only the last statement can violate the original decision logic.[5]

Java 
@Transactional(
    isolation = Isolation.SERIALIZABLE,
    timeoutString = "${billing.close-timeout-seconds:30}")
public void closeBillingPeriod(
        YearMonth period) {
    // Read decision state, validate invariants,
    // and write the complete period close atomically.
}

5.5 Choose isolation from the invariant

Start with the datastore default, identify the anomalies that can break the use case, and use the least expensive mechanism that prevents them. Sometimes an atomic conditional statement is better than a broader isolation level:

SQL 
update account
set balance = balance - :amount
where id = :accountId
  and balance >= :amount

The affected-row count then expresses the concurrency-safe outcome without a separate vulnerable read.

6. Rollback behavior

6.1 Historical default

Without custom rollback rules, Spring rolls back declarative transactions for RuntimeException and Error, but not for checked exceptions. This historical behavior follows the EJB-style distinction between unexpected system failures and declared business exceptions.[11]

Java 
@Transactional(
    rollbackFor = PaymentGatewayException.class,
    noRollbackFor = DuplicateNotificationException.class)
public void settle(...) throws PaymentGatewayException {
    // Checked PaymentGatewayException now triggers rollback.
}

6.2 Global rollback on all exceptions

Spring Framework 6.2 introduced RollbackOn.ALL_EXCEPTIONS for annotation-driven management. It gives checked and unchecked exceptions consistent rollback semantics unless a transaction-specific rule overrides the default. This is especially useful in codebases where checked exceptions are not used to signal commit-worthy business outcomes.[10]

6.3 Type rules versus name patterns

Type-based rules match an exception class and its subclasses and are the safest form. Pattern rules match substrings of fully qualified exception class names and do not support wildcards; broad names can unintentionally match similarly named or nested exception classes. Prefer rollbackFor = SomeException.class to rollbackForClassName whenever the type is available.[11]

6.4 Caught exceptions

Declarative rollback decisions are normally made when an exception escapes the intercepted method. If the method catches the exception and returns normally, the interceptor has no thrown exception to evaluate. Rethrow, translate and rethrow, or explicitly mark the transaction rollback-only when returning normally is unavoidable.

Java 
@Transactional
public TransferResult transfer(...) {
    try {
        performTransfer();
        return TransferResult.success();
    }
    catch (DataAccessException ex) {
        TransactionAspectSupport
            .currentTransactionStatus()
            .setRollbackOnly();

        return TransferResult.failed(ex.getMessage());
    }
}

Programmatic rollback-only marking couples business code to Spring transaction APIs. Throwing an exception is usually clearer. Also remember that a provider can mark a transaction rollback-only before the application catches its exception.

6.5 UnexpectedRollbackException

An outer REQUIRED scope can catch an inner exception and continue, yet still receive UnexpectedRollbackException at commit because the shared physical transaction was already marked rollback-only. The exception protects the caller from believing that a commit occurred.[16]

6.6 Commit and rollback can fail

Constraint checks, optimistic conflicts, serialization detection, storage failures, and distributed transaction outcomes can surface during flush or commit rather than at the line that changed state. Keep non-transactional side effects out of the pre-commit window unless their failure and compensation semantics are explicit.

7. Programmatic transactions

Spring recommends TransactionTemplate for imperative programmatic demarcation and TransactionalOperator for reactive code. Programmatic management is appropriate when transaction boundaries depend on runtime control flow, when only a small block should be transactional, or when the application must inspect status or use savepoints.[19]

7.1 TransactionTemplate

Java 
@Service
public final class ImportCoordinator {
    private final TransactionTemplate required;
    private final TransactionTemplate requiresNew;
    private final ImportRepository imports;

    public ImportCoordinator(
            PlatformTransactionManager manager,
            ImportRepository imports) {

        this.imports = imports;

        this.required =
                new TransactionTemplate(manager);
        this.required.setIsolationLevel(
                TransactionDefinition
                    .ISOLATION_READ_COMMITTED);

        this.requiresNew =
                new TransactionTemplate(manager);
        this.requiresNew.setPropagationBehavior(
                TransactionDefinition
                    .PROPAGATION_REQUIRES_NEW);
        this.requiresNew.setTimeout(10);
    }

    public ImportSummary importRecords(
            List<ImportRecord> records) {

        ImportId id = required.execute(
            status ->
                imports.createImport(records.size()));

        for (ImportRecord record : records) {
            requiresNew.executeWithoutResult(
                status -> {
                    try {
                        imports.insert(id, record);
                    }
                    catch (RecoverableRecordException ex) {
                        status.setRollbackOnly();
                    }
                });
        }

        return imports.summarize(id);
    }
}

TransactionTemplate is thread-safe after its configuration is fixed, but different transaction settings should use distinct template instances rather than mutating one shared template per invocation.[20]

7.2 Direct PlatformTransactionManager

Java 
DefaultTransactionDefinition definition =
        new DefaultTransactionDefinition();

definition.setName("inventory-reconciliation");
definition.setPropagationBehavior(
        TransactionDefinition.PROPAGATION_REQUIRED);
definition.setIsolationLevel(
        TransactionDefinition.ISOLATION_REPEATABLE_READ);
definition.setTimeout(20);

TransactionStatus status =
        manager.getTransaction(definition);

try {
    reconcileInventory();
    manager.commit(status);
}
catch (RuntimeException | Error failure) {
    if (!status.isCompleted()) {
        manager.rollback(status);
    }
    throw failure;
}

Direct manager use is lower-level and easier to get wrong around commit failures, rollback failures, and callback composition. Prefer the template unless explicit lifecycle control is essential.[7]

7.3 Programmatic savepoints

Java 
transactionTemplate.executeWithoutResult(status -> {
    persistHeader();

    Object savepoint = status.createSavepoint();
    try {
        persistOptionalDetails();
        status.releaseSavepoint(savepoint);
    }
    catch (DataAccessException ex) {
        status.rollbackToSavepoint(savepoint);
        status.releaseSavepoint(savepoint);
    }

    persistCompletionMarker();
});

Savepoints require an active transaction and manager support. For standard nested semantics, PROPAGATION_NESTED is generally clearer than hand-managed savepoints.[18]

8. Reactive transactions

Reactive transaction state is stored in Reactor context rather than a thread-local. A method using @Transactional with a reactive manager must return a reactive type, and the data-access operations must remain in the same reactive pipeline. Blocking JDBC and reactive R2DBC resources do not become one transaction through annotation alone.[13]

Java 
TransactionalOperator operator =
        TransactionalOperator.create(
                reactiveTransactionManager);

Mono<Receipt> operation =
        inventory.reserve(command)
            .then(payments.record(command))
            .then(orders.create(command));

return operator.transactional(operation);

Operator-style demarcation applies to the upstream publisher. Callback-style use can narrow transaction participation when several reactive flows are assembled and only selected publishers should share the transaction.

9. Read-only transactions, timeouts, and labels

9.1 Read-only is a hint

readOnly = true communicates intent to the transaction manager and managed resources. A provider can reduce dirty checking or choose a read-only resource mode, but the flag is not a universal authorization mechanism and may be ignored if the underlying system has no matching capability.[7][8]

9.2 Transaction timeout

A transaction timeout limits the transaction according to manager and resource support. It is not necessarily a hard wall-clock interruption of arbitrary Java code. For JDBC, Spring can apply remaining transaction time to statements created through transaction-aware infrastructure. Network clients and CPU work need their own deadlines.

9.3 Labels

Transaction labels are descriptive strings that a transaction manager may interpret as implementation-specific options. They do not have universal semantics; use them only with documented manager support.[11]

10. Transaction synchronization and events

10.1 Synchronization callbacks

TransactionSynchronization exposes callbacks around commit, completion, suspension, resume, flush, and savepoints. Infrastructure integrations use these callbacks to coordinate resource cleanup and post-transaction work. Callback ordering can be controlled through Spring’s ordering contract.[21]

10.2 @TransactionalEventListener

A transactional event listener runs according to a transaction phase, commonly after commit. If no transaction is active, the event is discarded unless fallback execution is enabled. After-commit listeners run after the resource transaction has completed; data access invoked there can still see bound resources in some implementations, but new changes are not committed as part of the completed transaction. Start a new transaction for durable follow-up database work.[22]

Java 
@Component
class OrderCommittedListener {

    private final NotificationService notifications;

    OrderCommittedListener(
            NotificationService notifications) {
        this.notifications = notifications;
    }

    @TransactionalEventListener(
        phase = TransactionPhase.AFTER_COMMIT)
    public void onOrderCommitted(
            OrderPlaced event) {

        notifications.enqueue(event.orderId());
    }
}

An in-process after-commit event is not a durable message. A process crash after commit but before listener execution can lose the side effect. Use a transactional outbox when guaranteed eventual delivery is required.

11. Worked example: funds transfer with audit and outbox

11.1 Schema

SQL 
create table account (
    id bigint primary key,
    balance decimal(19, 2) not null,
    version bigint not null,
    constraint balance_nonnegative
        check (balance >= 0)
);

create table transfer (
    id varchar(36) primary key,
    source_account bigint not null,
    target_account bigint not null,
    amount decimal(19, 2) not null,
    created_at timestamp not null
);

create table outbox_event (
    id varchar(36) primary key,
    aggregate_type varchar(64) not null,
    aggregate_id varchar(64) not null,
    event_type varchar(128) not null,
    payload text not null,
    created_at timestamp not null,
    published_at timestamp null
);

11.2 Repository

Java 
@Repository
final class TransferRepository {
    private final NamedParameterJdbcTemplate jdbc;

    TransferRepository(
            NamedParameterJdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    int debit(
            long accountId,
            BigDecimal amount) {

        return jdbc.update(
            """
            update account
            set balance = balance - :amount,
                version = version + 1
            where id = :accountId
              and balance >= :amount
            """,
            Map.of(
                "accountId", accountId,
                "amount", amount));
    }

    int credit(
            long accountId,
            BigDecimal amount) {

        return jdbc.update(
            """
            update account
            set balance = balance + :amount,
                version = version + 1
            where id = :accountId
            """,
            Map.of(
                "accountId", accountId,
                "amount", amount));
    }

    void insertTransfer(
            Transfer transfer) {

        jdbc.update(
            """
            insert into transfer (
                id, source_account, target_account,
                amount, created_at
            )
            values (
                :id, :source, :target,
                :amount, :createdAt
            )
            """,
            new MapSqlParameterSource()
                .addValue(
                    "id",
                    transfer.id().toString())
                .addValue(
                    "source",
                    transfer.sourceAccount())
                .addValue(
                    "target",
                    transfer.targetAccount())
                .addValue(
                    "amount",
                    transfer.amount())
                .addValue(
                    "createdAt",
                    Timestamp.from(
                        transfer.createdAt())));
    }

    void insertOutbox(OutboxEvent event) {
        // Insert into outbox_event using the same DataSource.
    }
}

11.3 Transactional application service

Java 
@Service
public final class TransferApplicationService {
    private final TransferRepository repository;
    private final ApplicationEventPublisher events;

    public TransferApplicationService(
            TransferRepository repository,
            ApplicationEventPublisher events) {

        this.repository = repository;
        this.events = events;
    }

    @Transactional(
        isolation = Isolation.READ_COMMITTED,
        timeout = 10)
    public TransferId transfer(
            TransferCommand command) {

        if (command.sourceAccount()
                == command.targetAccount()) {
            throw new IllegalArgumentException(
                    "Accounts must differ");
        }

        int debited =
                repository.debit(
                    command.sourceAccount(),
                    command.amount());

        if (debited != 1) {
            throw new InsufficientFundsException(
                    command.sourceAccount(),
                    command.amount());
        }

        int credited =
                repository.credit(
                    command.targetAccount(),
                    command.amount());

        if (credited != 1) {
            throw new AccountNotFoundException(
                    command.targetAccount());
        }

        Transfer transfer =
                Transfer.create(command);

        repository.insertTransfer(transfer);

        OutboxEvent outbox =
                OutboxEvent.forTransfer(transfer);

        repository.insertOutbox(outbox);

        events.publishEvent(
                new TransferRecorded(
                    transfer.id()));

        return new TransferId(transfer.id());
    }
}

11.4 Why the design is atomic

  • Debit, credit, transfer record, and outbox event use the same transaction-aware DataSource.
  • The debit is a guarded atomic update; no vulnerable balance read precedes it.
  • Every failure escapes the method and triggers rollback under the configured rollback policy.
  • The outbox record commits with the business state and can be published asynchronously and idempotently.
  • The application event is useful for local best-effort reactions but is not the durable delivery mechanism.
  • No remote call is made while the database transaction holds locks.

12. Testing transactions

Spring’s TestContext Framework can run a test method inside a test-managed transaction and roll it back afterward. This is useful for isolation but can hide commit-time behavior, asynchronous work, and code that depends on a real commit. Test both rollback-isolated repository behavior and explicit commit scenarios.[23]

Java 
@SpringJUnitConfig(TestConfiguration.class)
@Transactional
class TransferIntegrationTest {

    @Autowired
    TransferApplicationService transfers;

    @Autowired
    JdbcTemplate jdbc;

    @Test
    void rollsBackCompleteTransferOnFailure() {
        assertThrows(
            AccountNotFoundException.class,
            () -> transfers.transfer(
                new TransferCommand(
                    1L,
                    999L,
                    new BigDecimal("10.00"))));

        BigDecimal balance =
                jdbc.queryForObject(
                    """
                    select balance
                    from account
                    where id = 1
                    """,
                    BigDecimal.class);

        assertEquals(
                new BigDecimal("100.00"),
                balance);
    }
}

12.1 Testing after-commit behavior

A test that is automatically rolled back never executes normal after-commit semantics. Use TestTransaction, a non-transactional test, or a deliberately committed test transaction when verifying outbox polling, transactional listeners, database triggers, or deferred constraints.[23]

13. Diagnostics

13.1 @Transactional appears ignored

Check whether transaction management is enabled, whether the object is Spring-managed, whether the invocation entered through the proxy, whether the method is called during initialization, whether the correct manager was selected, and whether the transaction was already active with different attributes.

13.2 Unexpected rollback at method exit

A participating inner scope or provider marked the shared transaction rollback-only. Inspect earlier exceptions, including those caught by application code. Use REQUIRES_NEW only when genuinely independent commit semantics are desired, not merely to suppress the symptom.[16]

13.3 Isolation annotation has no effect

The method likely joined an existing transaction. Isolation applies to newly created transactions. Enable existing-transaction validation to reject incompatible assumptions, or place the isolation boundary at the outermost transaction.[14]

13.4 Connection pool exhausts under load

Inspect long transaction duration, leaked streams, remote calls inside transactions, and nested REQUIRES_NEW usage. An outer transaction can hold one connection while the inner scope waits for another.

13.5 Checked exception committed the transaction

That is the historical default unless rollbackFor or the global all-exceptions policy is configured. Make the rollback contract explicit and test it.[10][11]

13.6 Timeout did not stop Java work

Transaction timeout support is resource-manager-specific. Add explicit deadlines to network calls, locks, and computation. Do not assume transaction timeout interrupts arbitrary code.

14. Expert practices

14.1 Align boundaries with invariants

A transaction should enclose the reads and writes required to preserve one application invariant. Repository methods are operations; service methods usually define the unit of work.

14.2 Keep transactions short

Validate inexpensive input before beginning the transaction. Avoid remote calls, file transfer, user interaction, and unbounded loops while holding database resources and locks.

14.3 Treat propagation as architecture

Use REQUIRED by default. Introduce REQUIRES_NEW only for independently durable work, and NESTED only when partial rollback within one database transaction is the intended semantics.

14.4 Standardize rollback policy

Decide whether checked exceptions commit or roll back. Prefer type-safe rules, document intentional no-rollback exceptions, and preserve original causes when translating failures.

14.5 Test concurrency, not just annotations

Build concurrent integration tests for lost updates, duplicate allocation, overselling, write skew, and serialization retries using the production database.

14.6 Use an outbox for durable external effects

Write the business change and outbox record in one database transaction. Publish later with idempotency and retry. An after-commit listener alone is not durable delivery.

14.7 Retry complete idempotent units

Deadlock and serialization retries must restart the complete transaction from fresh state. Apply bounded backoff and ensure external effects are idempotent or deferred.

14.8 Observe transaction behavior

Record transaction names, duration, propagation, isolation, rollback category, timeout, lock waits, and connection usage. Declarative transactions are runtime infrastructure and need operational visibility.

14.9 Do not mix context models casually

Imperative transactions use thread-bound resources; reactive transactions use Reactor context. Crossing between blocking and reactive APIs requires explicit architecture, not merely another annotation.

15. Summary

Spring transaction management is predictable when the physical resource boundary and logical method scopes are kept distinct:

  • ACID properties are delivered by the underlying transaction resource within the scope Spring controls.
  • PlatformTransactionManager is the imperative strategy; declarative AOP and TransactionTemplate are the usual application-facing APIs.
  • @Transactional is metadata applied by interception, not an intrinsic behavior of the Java method.
  • Proxy-based self-invocation does not apply inner transactional metadata.
  • REQUIRED shares a physical transaction; REQUIRES_NEW creates an independent one; NESTED typically uses a savepoint.
  • Isolation and timeout apply only when a new physical transaction starts.
  • The historical rollback default covers unchecked exceptions and errors; Spring 6.2+ can globally roll back on all exceptions.
  • Rollback-only state in a participating inner scope can produce UnexpectedRollbackException for the outer caller.
  • Read-only is a hint, transaction timeout is resource-dependent, and transaction context does not cross arbitrary threads or remote calls.
  • Reactive transactions use Reactor context and require a continuous reactive pipeline.
  • Durable integration with external systems usually requires an outbox or distributed transaction—not an after-commit callback alone.

When a transaction surprises you, trace it mechanically: Which manager was selected? Did the invocation enter through an interceptor? Was there already a physical transaction? Which propagation decision was made? Which isolation and timeout actually applied? Which resource was bound? Who marked rollback-only? Did an exception escape? Did commit itself fail? Answering those questions turns transactional behavior from annotation folklore into an explicit execution model.
