Spring IoC and Web Programming Model

Core Annotations in Spring

A technical guide to component stereotypes, Java-based bean definitions, dependency injection, candidate selection, external values, profiles, scopes, lazy resolution, and initialization ordering.

Spring Framework 7.0.8 IoC container and Spring MVC Long-form technical article Vancouver references
Abstract. Spring annotations are metadata consumed by several distinct subsystems. Component stereotypes make classes discoverable as bean definitions and communicate architectural roles. @Configuration and @Bean define objects through Java factory methods. @Autowired, @Qualifier, and @Primary control dependency resolution. @Value resolves placeholders and expressions. @Profile conditionally registers bean definitions. @Scope changes instance lifetime, while @Lazy changes creation or resolution timing. @DependsOn imposes initialization and destruction ordering without injecting a reference. Web stereotypes add handler semantics on top of the core container. This article explains the processing model, interactions, edge cases, and design implications of every requested annotation.

Spring’s annotation model is implemented by component scanning, configuration-class processing, bean-definition metadata, post-processors, autowire-candidate resolution, and web handler discovery. An annotation has no effect on an object created outside the Spring container unless another framework explicitly processes it.[1][2]

1. Processing model

1 Component scanning or explicit registration discovers configuration and component classes.
2 Configuration processing turns scanned classes and @Bean methods into bean definitions.
3 Profile and conditional metadata determine which definitions are registered.
4 Scope, lazy, primary, qualifier, and dependency-order metadata are attached to definitions.
5 The bean factory instantiates objects and resolves constructor or factory-method arguments.
6 Bean post-processors perform annotation-driven injection, lifecycle callbacks, proxying, and exception translation.
7 Web infrastructure detects controller beans and maps handler methods.

Annotation-based configuration is container metadata. @Autowired and @Value, for example, are processed by bean post-processors, while @Configuration, @Bean, profiles, and component scanning are primarily processed while bean definitions are being registered.[2][3]

Annotations do not make arbitrary objects Spring beans Calling new PaymentService(...) bypasses component scanning, dependency injection, scope proxies, lazy resolution, AOP advice, and container lifecycle. Register the object as a bean or keep it deliberately outside the container.

3. @Component

@Component marks a class as a candidate for auto-detection during classpath scanning. It is the generic stereotype from which @Service, @Repository, and @Controller are composed. Any custom annotation meta-annotated with @Component is also a stereotype and can be discovered by scanning.[4][5]

Java 
@Component
public final class SystemClockProvider {

    private final Clock clock =
            Clock.systemUTC();

    public Instant now() {
        return clock.instant();
    }
}

3.1 Bean naming

A component can suggest a logical bean name through @Component("systemClock"). Without an explicit name, the configured BeanNameGenerator derives one, normally from the short class name. Referencing bean names directly creates stronger container coupling than type-and-qualifier injection and should be reserved for infrastructure that genuinely addresses beans by name.[4][5]

3.2 Custom stereotypes

Java 
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Documented
@Component
public @interface DomainPolicy {

    @AliasFor(annotation = Component.class)
    String value() default "";
}

@DomainPolicy
final class CreditLimitPolicy {
}

Modern custom stereotype annotations should explicitly alias their naming attribute to Component.value() with @AliasFor. Convention-based aliasing through an unrelated String value() is deprecated.[4]

4. @Service

@Service is a specialization of @Component that communicates a service role—typically an application service, domain service, or business-operation boundary. Current core container behavior is primarily the same as @Component, but the stereotype provides architectural meaning and a stable pointcut or tooling target.[6][7]

Java 
@Service
public final class PlaceOrderService {

    private final OrderRepository orders;
    private final PricingPolicy pricing;

    public PlaceOrderService(
            OrderRepository orders,
            PricingPolicy pricing) {
        this.orders = orders;
        this.pricing = pricing;
    }

    @Transactional
    public OrderId place(PlaceOrder command) {
        Order order =
                Order.create(
                    command,
                    pricing.quote(command));

        orders.save(order);
        return order.id();
    }
}
Use stereotypes to communicate architecture Marking every class @Component works mechanically but discards useful role information. Prefer the narrowest accurate stereotype and custom stereotypes for important domain roles.

5. @Repository

@Repository identifies a persistence repository or DAO and is meta-annotated with @Component. When a PersistenceExceptionTranslationPostProcessor is present, eligible repository beans can have native persistence exceptions translated into Spring’s DataAccessException hierarchy.[8]

Java 
@Repository
public final class JdbcOrderRepository
        implements OrderRepository {

    private final NamedParameterJdbcTemplate jdbc;

    public JdbcOrderRepository(
            NamedParameterJdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    @Override
    public Optional<Order> findById(OrderId id) {
        return jdbc.query(
                """
                select id, status, total
                from purchase_order
                where id = :id
                """,
                Map.of("id", id.value()),
                orderRowMapper)
            .stream()
            .findFirst();
    }
}

Exception translation depends on the relevant post-processor and supported persistence technology; the annotation alone does not rewrite exceptions. Spring Data-generated repositories integrate with the same broader data-access exception model but do not require a handwritten implementation class to carry this stereotype.[8]

6. @Controller

@Controller is a component stereotype for web controllers. Spring MVC and WebFlux handler mappings detect controller beans and inspect mapping annotations on their methods. In MVC, a method can populate a model and return a logical view name; it can also write a response body when annotated appropriately.[9][10]

Java 
@Controller
@RequestMapping("/orders")
public final class OrderPageController {

    private final OrderQueries orders;

    public OrderPageController(OrderQueries orders) {
        this.orders = orders;
    }

    @GetMapping("/{id}")
    String show(
            @PathVariable UUID id,
            Model model) {

        model.addAttribute(
            "order",
            orders.require(id));

        return "orders/detail";
    }
}

@Controller does not imply that every returned object is serialized. Return-value semantics depend on the method signature, annotations, configured resolvers, and message converters or view resolvers.[10]

7. @RestController

@RestController is a composed annotation combining @Controller and @ResponseBody. Handler return values are therefore processed through response-body handling—typically HTTP message conversion—unless another return-value contract applies.[11][12]

Java 
@RestController
@RequestMapping("/api/orders")
public final class OrderApiController {

    private final OrderQueries orders;

    public OrderApiController(OrderQueries orders) {
        this.orders = orders;
    }

    @GetMapping("/{id}")
    ResponseEntity<OrderResponse> get(
            @PathVariable UUID id) {

        return ResponseEntity.of(
            orders.find(id)
                .map(OrderResponse::from));
    }
}
@RestController is not a REST guarantee It selects response-body controller semantics. Resource design, HTTP method semantics, status codes, caching, content negotiation, idempotency, and hypermedia remain application responsibilities.

8. @Configuration

@Configuration marks a class as a source of one or more bean definitions, normally declared through @Bean methods. It is itself meta-annotated with @Component, so it can be discovered through component scanning and participate in dependency injection.[13]

Java 
@Configuration(proxyBeanMethods = false)
public class PaymentConfiguration {

    @Bean
    PaymentGateway paymentGateway(
            PaymentProperties properties,
            WebClient.Builder webClient) {

        return new HttpPaymentGateway(
            webClient
                .baseUrl(properties.baseUrl())
                .build(),
            properties.timeout());
    }

    @Bean
    PaymentService paymentService(
            PaymentGateway gateway,
            PaymentRepository payments) {

        return new PaymentService(
            gateway,
            payments);
    }
}

8.1 Full and lite configuration

With the default proxyBeanMethods=true, Spring can subclass a configuration class so direct calls between its @Bean methods are intercepted and return container-managed instances. With proxyBeanMethods=false, methods use ordinary Java semantics; dependencies should be expressed as method parameters rather than by calling another factory method. A @Bean method declared on a non-@Configuration component also operates in “lite” mode and is not intercepted for inter-bean calls.[13][14]

Java 
// Preferred in proxyBeanMethods = false configuration:
@Bean
BillingService billingService(
        BillingRepository repository,
        Clock applicationClock) {

    return new BillingService(
        repository,
        applicationClock);
}

// Avoid relying on direct @Bean method calls in lite mode:
@Bean
BillingService billingService() {
    return new BillingService(
        billingRepository(),
        applicationClock());
}

Disabling proxy methods avoids configuration-class subclassing and is appropriate when factory methods are self-contained and obtain collaborators through parameters. Full mode remains useful when preserving inter-bean method-call semantics is intentional.[13]

9. @Bean

@Bean marks a factory method whose return value is managed as a Spring bean. By default, the method name becomes the bean name; the annotation can supply one or more names, plus lifecycle metadata such as an initialization or destruction method. Factory-method parameters are resolved through the container using dependency-injection rules.[15][14]

Java 
@Bean(
    name = {
        "applicationClock",
        "clock"
    })
Clock applicationClock() {
    return Clock.systemUTC();
}

@Bean(
    initMethod = "start",
    destroyMethod = "close")
PartnerClient partnerClient(
        PartnerProperties properties,
        Clock applicationClock) {

    return new PartnerClient(
        properties.endpoint(),
        properties.timeout(),
        applicationClock);
}

9.1 Third-party classes

@Bean is the normal way to register classes that cannot or should not be annotated, including third-party clients, JDK types, generated objects, and infrastructure assembled from configuration values.

9.2 Complementary annotations

@Bean deliberately does not duplicate profile, scope, lazy, dependency-order, primary, or order attributes. Apply @Profile, @Scope, @Lazy, @DependsOn, @Primary, @Qualifier, and ordering annotations directly to the factory method.[15]

10. @Autowired

@Autowired requests dependency resolution by type, refined by qualifiers, primary/default-candidate rules, generic type information, priority, and dependency name where applicable. It can annotate constructors, methods, fields, and parameters. Injection is performed by AutowiredAnnotationBeanPostProcessor.[16][17]

10.1 Constructor injection

Java 
@Service
public final class RefundService {

    private final PaymentRepository payments;
    private final RefundGateway gateway;

    // @Autowired is optional because this is
    // the only constructor.
    public RefundService(
            PaymentRepository payments,
            RefundGateway gateway) {

        this.payments = payments;
        this.gateway = gateway;
    }
}

A bean class with exactly one constructor does not need @Autowired; Spring uses that constructor. With several constructors, Spring selects annotated candidates according to satisfiable dependencies and required flags, or uses a primary/default constructor where applicable.[17][18]

Prefer constructor injection for required collaborators Constructor injection makes dependencies explicit, permits immutable fields, supports ordinary unit construction, and prevents a bean from existing in a partially injected state.

10.2 Optional and deferred dependencies

Java 
@Component
public final class OptionalAuditSupport {

    private final Optional<AuditSink> sink;
    private final ObjectProvider<DiagnosticsClient>
            diagnostics;

    public OptionalAuditSupport(
            Optional<AuditSink> sink,
            ObjectProvider<DiagnosticsClient>
                    diagnostics) {

        this.sink = sink;
        this.diagnostics = diagnostics;
    }
}

Optionality can be represented with Optional, nullable parameters under the configured nullability model, ObjectProvider, or @Autowired(required=false). ObjectProvider additionally supports lazy lookup, availability checks, ordered streams, and prototype retrieval without injecting a scoped proxy.[18]

10.3 Collections and maps

Java 
@Service
public final class ExportService {

    private final List<ExportFormatter> formatters;
    private final Map<String, ExportValidator>
            validators;

    public ExportService(
            List<ExportFormatter> formatters,
            Map<String, ExportValidator>
                    validators) {

        this.formatters = List.copyOf(formatters);
        this.validators = Map.copyOf(validators);
    }
}

Arrays and typed collections receive all matching beans. A typed map uses bean names as keys and matching bean instances as values. @Order, Ordered, or standard priority metadata can sort injected lists, but @Primary does not remove non-primary beans from multi-valued injection.[18][19]

10.4 Field injection

Java 
@Component
final class FieldInjectedExample {

    @Autowired
    private PaymentGateway gateway;
}

Field injection is supported but hides required dependencies from constructors, requires container or reflective support for ordinary tests, and prevents straightforward use of final fields. It is often acceptable in test fixtures and framework glue but is usually a weaker default for application code.

11. @Qualifier

@Qualifier narrows the set of type-matching autowire candidates. A qualifier is semantic filtering within the candidate set, not necessarily a unique bean identifier. Several beans can share a qualifier, especially when injecting a collection.[20][21]

Java 
@Bean
@Qualifier("external")
PaymentGateway stripeGateway() {
    return new StripePaymentGateway();
}

@Bean
@Qualifier("external")
PaymentGateway bankGateway() {
    return new BankPaymentGateway();
}

@Service
final class ExternalPaymentRouter {

    ExternalPaymentRouter(
            @Qualifier("external")
            List<PaymentGateway> gateways) {
        // Receives both qualified gateways.
    }
}

11.1 Custom qualifier annotations

Java 
@Target({
    ElementType.FIELD,
    ElementType.PARAMETER,
    ElementType.METHOD,
    ElementType.TYPE
})
@Retention(RetentionPolicy.RUNTIME)
@Qualifier
public @interface Region {
    String value();
}

@Bean
@Region("us-east")
InventoryClient eastInventory() {
    return new HttpInventoryClient(
        URI.create("https://east.example.net"));
}

@Service
final class CheckoutService {

    CheckoutService(
            @Region("us-east")
            InventoryClient inventory) {
    }
}

Custom qualifiers provide compile-time discoverability and domain meaning while avoiding scattered string literals. Qualifier attributes participate in matching.[20][21]

11.2 Generics as qualifiers

Java 
interface Store<T> {
    void save(T value);
}

@Bean
Store<Invoice> invoiceStore() {
    return new JdbcInvoiceStore();
}

@Bean
Store<Customer> customerStore() {
    return new JdbcCustomerStore();
}

@Service
final class InvoiceService {

    InvoiceService(Store<Invoice> store) {
        // Generic type narrows the candidate.
    }
}

Spring can use generic type arguments as implicit qualifiers, reducing the need for explicit names when beans implement the same generic contract for different domain types.[22]

12. @Primary

@Primary gives one bean preference when several candidates match a single-valued dependency. It can appear on a component class or an @Bean method. It has no filtering effect on arrays, collections, maps, or ObjectProvider streams; all matching beans remain available.[19]

Java 
@Bean
@Primary
ExchangeRateProvider cachedRates(
        RemoteExchangeRateProvider remote) {
    return new CachedExchangeRateProvider(
        remote,
        Duration.ofMinutes(5));
}

@Bean
ExchangeRateProvider directRates() {
    return new RemoteExchangeRateProvider();
}

@Service
final class PriceConversionService {

    PriceConversionService(
            ExchangeRateProvider rates) {
        // Receives cachedRates.
    }
}

12.1 Primary versus qualifier

MechanismPurposeBest use
@PrimaryDefault preference among matching candidatesOne implementation is the normal default
@QualifierExplicit semantic narrowing at injection pointThe caller requires a particular role, region, mode, or format
Bean name fallbackMay disambiguate by dependency nameIncidental fallback, not preferred domain modeling

An explicit qualifier communicates intent more strongly than relying on a primary default. If two primary candidates remain after filtering, single-valued injection is still ambiguous.[19][21]

13. @Value

@Value injects the result of an embedded value expression. Common forms are property placeholders such as ${catalog.timeout:5s} and Spring Expression Language expressions such as #{systemProperties['user.timezone']}. The resolved string can be converted to the target parameter or field type through Spring’s conversion infrastructure.[23][24]

Java 
@Component
public final class CatalogClient {

    private final URI endpoint;
    private final Duration timeout;
    private final int maximumAttempts;

    public CatalogClient(
            @Value("${catalog.endpoint}")
            URI endpoint,

            @Value("${catalog.timeout:3s}")
            Duration timeout,

            @Value("${catalog.max-attempts:3}")
            int maximumAttempts) {

        this.endpoint = endpoint;
        this.timeout = timeout;
        this.maximumAttempts = maximumAttempts;
    }
}

13.1 SpEL

Java 
@Value(
    "#{systemProperties['user.timezone']"
    + " ?: 'UTC'}")
private String defaultZone;

SpEL is powerful but can obscure configuration provenance and move logic into strings. Use it for concise infrastructure expressions, not as a substitute for typed application configuration or domain code.

13.2 Processing limitations

Because @Value is processed by a bean post-processor, it cannot be relied on inside bean post-processors or bean-factory post-processors in the ordinary way. Static fields are also not a normal dependency-injection target. For groups of related settings, immutable typed configuration objects are generally easier to validate and test than many scattered @Value declarations.[23]

14. @Profile

@Profile is a specialization of @Conditional that registers a component or @Bean method only when its profile expression matches the active environment profiles. Profiles can be activated through the Environment and external configuration.[25][26]

Java 
@Configuration(proxyBeanMethods = false)
@Profile("production")
class ProductionMailConfiguration {

    @Bean
    MailGateway smtpMailGateway(
            MailProperties properties) {
        return new SmtpMailGateway(properties);
    }
}

@Configuration(proxyBeanMethods = false)
@Profile("!production")
class LocalMailConfiguration {

    @Bean
    MailGateway loggingMailGateway() {
        return new LoggingMailGateway();
    }
}

14.1 Profile expressions

Java 
@Bean
@Profile("production & (us-east | us-west)")
TaxProvider regionalProductionTaxProvider() {
    return new RegionalTaxProvider();
}

Profile expressions support profile names, negation, conjunction, and disjunction with parentheses where needed. Avoid making profiles an uncontrolled matrix of feature flags. Profiles are strongest for coherent environment or deployment variants; runtime feature rollout usually needs a dedicated feature-management mechanism.[25][26]

14.2 Factory-method caution

Do not use different @Profile conditions on overloaded @Bean methods that share one Java method name and expect profile selection to choose among signatures. Use distinct method names and, when the public bean name must remain the same, assign it explicitly with @Bean(name="...").[26]

15. @Scope

@Scope sets the lifecycle scope for a component or @Bean definition. Core scopes include singleton and prototype. A web-aware application context additionally supports request, session, application, and WebSocket scopes. The default is singleton: one instance per bean definition per Spring container, not one instance per JVM or class loader.[27][28]

ScopeLifetimeTypical use
singletonOne instance per bean definition per containerStateless services and shared infrastructure
prototypeNew instance for each retrieval/injection resolutionStateful short-lived objects created by the container
requestOne instance per HTTP requestRequest-local state
sessionOne instance per HTTP sessionSession-local conversational state
applicationOne instance per servlet applicationServlet-context-scoped state
websocketOne instance per WebSocket sessionWebSocket-session state
Java 
@Component
@Scope(
    value = WebApplicationContext.SCOPE_REQUEST,
    proxyMode = ScopedProxyMode.TARGET_CLASS)
public class RequestAuditContext {

    private final UUID requestId =
            UUID.randomUUID();

    public UUID requestId() {
        return requestId;
    }
}

15.1 Injecting a shorter-lived bean

Injecting a request- or session-scoped object directly into a singleton would otherwise resolve it while the singleton is created. A scoped proxy is injected instead and looks up the current target instance when a method is invoked. Built-in composed annotations such as @RequestScope and @SessionScope provide convenient web-scope declarations with proxy behavior.[28]

Scope changes state ownership A session-scoped bean consumes per-session memory and requires serialization or compatible external storage in distributed deployments. A request-scoped bean cannot safely escape to work that runs after the request ends.

15.2 Prototype lifecycle

For prototype beans, the container creates, configures, and returns each instance but does not manage the complete destruction lifecycle afterward. The consumer that retains a prototype object must release its resources, or a custom post-processor must track and clean them.[28]

16. @Lazy

On a component or @Bean method, @Lazy requests creation when the bean is first needed instead of during normal eager singleton initialization. On a @Configuration class, it establishes lazy defaults for its bean methods; @Lazy(false) can override that default on an individual bean.[29][30]

Java 
@Bean
@Lazy
LargeReferenceModel referenceModel(
        ResourceLoader resources) {

    return LargeReferenceModel.load(
        resources.getResource(
            "classpath:/model.bin"));
}

A lazy bean is still instantiated at startup when an eager singleton requires it directly, because the dependency must be satisfied. Lazy creation delays cost and failure; it does not remove them.[29]

16.1 Lazy injection proxy

Java 
@Service
public final class RecommendationService {

    private final ExperimentalModel model;

    public RecommendationService(
            @Lazy ExperimentalModel model) {
        this.model = model;
    }

    Recommendation recommend(Customer customer) {
        return model.recommend(customer);
    }
}

@Lazy on an injection point creates a lazy-resolution proxy. The target is resolved when the proxy is first used. For genuinely optional or programmatic resolution, ObjectProvider is often clearer because a lazy proxy can still fail on first invocation when no target bean exists.[30]

16.2 Trade-offs

  • Faster startup can become slower first-request latency.
  • Configuration or connectivity failures move from startup to runtime.
  • Memory is saved only if the bean is never requested.
  • Lazy proxies can obscure dependency timing in debugging and tests.

17. @DependsOn

@DependsOn declares that named beans must be initialized before the annotated bean. For singleton beans, it also establishes corresponding destruction order: dependent beans are destroyed before the beans they depend on. The annotation addresses lifecycle ordering, including indirect dependencies not represented by a Java reference.[31][32]

Java 
@Bean
DatabaseDriverRegistry driverRegistry() {
    DatabaseDriverRegistry registry =
            new DatabaseDriverRegistry();

    registry.registerDefaults();
    return registry;
}

@Bean
@DependsOn("driverRegistry")
LegacyReportingEngine reportingEngine() {
    return new LegacyReportingEngine();
}

17.1 Ordering is not injection

If bean A receives bean B as a constructor parameter, the dependency already forces B to be created first; adding @DependsOn("b") is redundant. Use @DependsOn for hidden side effects such as static driver registration, shared resource initialization, or infrastructure whose dependency cannot be represented as an object reference.[32]

Hidden ordering is a design smell Prefer explicit object dependencies, lifecycle interfaces, events, or a dedicated coordinator. @DependsOn is useful for legacy and infrastructure constraints but should not become an invisible workflow language.

18. Dependency resolution sequence

A practical single-valued autowiring model is:

  1. Find beans assignable to the dependency type, including generic type constraints.
  2. Apply qualifier annotations and candidate metadata.
  3. Apply primary and priority/default-candidate rules.
  4. Use dependency-name fallback where supported and still necessary.
  5. Fail when no required candidate or no unique candidate remains.

The exact resolver contains additional rules and extension points, but this sequence explains most application-level results. Multi-valued dependencies intentionally retain all matching candidates and apply ordering rather than primary selection.[18][19][21]

19. Worked configuration

Java 
@Configuration(proxyBeanMethods = false)
public class NotificationConfiguration {

    @Bean
    @Primary
    @Profile("production")
    NotificationGateway productionGateway(
            @Value("${notification.endpoint}")
            URI endpoint,
            @Value("${notification.timeout:3s}")
            Duration timeout) {

        return new HttpNotificationGateway(
            endpoint,
            timeout);
    }

    @Bean
    @Profile("!production")
    NotificationGateway loggingGateway() {
        return new LoggingNotificationGateway();
    }

    @Bean
    @Qualifier("audit")
    NotificationGateway auditGateway() {
        return new AuditNotificationGateway();
    }

    @Bean
    @Scope(
        value =
            WebApplicationContext.SCOPE_REQUEST,
        proxyMode =
            ScopedProxyMode.TARGET_CLASS)
    RequestNotificationContext
            requestNotificationContext() {

        return new RequestNotificationContext(
            UUID.randomUUID());
    }

    @Bean
    @Lazy
    TemplateCatalog templateCatalog(
            ResourceLoader resources) {

        return TemplateCatalog.load(
            resources.getResource(
                "classpath:/templates/"));
    }

    @Bean
    @DependsOn("templateCatalog")
    NotificationFormatter formatter(
            @Lazy TemplateCatalog templates) {

        return new NotificationFormatter(
            templates);
    }
}
Java 
@Service
public final class NotificationService {

    private final NotificationGateway defaultGateway;
    private final NotificationGateway auditGateway;
    private final List<NotificationEnricher>
            enrichers;
    private final RequestNotificationContext context;
    private final ObjectProvider<TemplateCatalog>
            templates;

    public NotificationService(
            NotificationGateway defaultGateway,

            @Qualifier("audit")
            NotificationGateway auditGateway,

            List<NotificationEnricher> enrichers,

            RequestNotificationContext context,

            ObjectProvider<TemplateCatalog>
                    templates) {

        this.defaultGateway = defaultGateway;
        this.auditGateway = auditGateway;
        this.enrichers = List.copyOf(enrichers);
        this.context = context;
        this.templates = templates;
    }

    public void send(Notification command) {
        Notification enriched =
                enrichers.stream()
                    .reduce(
                        command,
                        (current, enricher) ->
                            enricher.enrich(
                                current,
                                context.requestId()),
                        (left, right) -> right);

        defaultGateway.send(enriched);
        auditGateway.send(enriched);
    }
}

19.1 What the container does

  • The active profile determines which default gateway definition is registered.
  • @Primary selects the production gateway for the unqualified single-valued dependency when production is active.
  • @Qualifier("audit") explicitly selects the audit gateway.
  • Every matching enricher is injected and ordered by ordering metadata.
  • The request context is a scoped proxy whose target is request-local.
  • The template catalog is created only when requested, although @DependsOn on the formatter can force earlier initialization if the formatter is eagerly created.
  • ObjectProvider allows programmatic and delayed access without making the service itself lazy.
Metadata interactions can defeat intent Marking a bean lazy and then making an eager bean depend on it—through constructor injection or @DependsOn—causes it to be created eagerly. Evaluate the complete bean graph, not annotations in isolation.

Java 
new AnnotationConfigApplicationContext() {{
    getEnvironment()
        .setActiveProfiles("production");

        ProductionMailConfiguration.class,

Test the effective bean graph: active profiles, candidate ambiguity, qualifiers, scopes, lazy creation, lifecycle order, and web handler detection. Tests that instantiate a component directly are valuable unit tests but do not verify annotation processing.

21. Diagnostics

21.1 Component is not discovered

Verify scan-package boundaries, stereotype metadata, conditional/profile matches, exclusions, and that the class is concrete and visible. In a Boot application, the main application class normally establishes the default scan root.

21.2 “Expected single matching bean but found multiple”

Add a semantic qualifier, identify one default with @Primary, inject a collection, or narrow the abstraction. Renaming the parameter to match a bean name may work as fallback but is a weaker design than explicit qualification.

21.3 An autowired field is null

The object was likely constructed outside the container, injection has not yet occurred, or the field is being accessed during construction. Prefer constructor injection and ensure callers obtain the bean from the application context.

21.4 Calling an @Bean method creates a second object

The configuration is in lite mode—such as proxyBeanMethods=false or an ordinary component with a @Bean method—so direct calls use normal Java semantics. Inject factory-method dependencies as parameters.[13][14]

21.5 Lazy bean is created at startup

An eager singleton depends on it directly, a @DependsOn relationship forces it, or startup code requests it. Use a lazy injection proxy or ObjectProvider only when deferred resolution is genuinely desired.[29]

21.6 Profile-specific bean is missing

Inspect active and default profiles, profile-expression syntax, configuration precedence, and whether the profile annotation is attached to the bean definition source actually being registered.[25][26]

21.7 Request-scoped bean fails outside a request

The current thread has no active request scope, commonly because work escaped to an asynchronous executor or background listener. Pass immutable request data explicitly instead of retaining the request-scoped object.

22. Expert practices

22.1 Use precise stereotypes

Prefer @Service, @Repository, @Controller, and custom stereotypes over generic @Component when the architectural role is meaningful.

22.2 Use constructor injection by default

Required dependencies should be immutable and explicit. Use setters or optional providers for genuinely optional, reconfigurable, or circularly constrained infrastructure.

22.3 Qualify by meaning

Qualifiers such as region, protocol, storage tier, or document format communicate intent better than implementation-class names or incidental bean names.

22.4 Reserve primary for a real default

A primary bean should represent the normal implementation. Injection points with special requirements should still use explicit qualifiers.

22.5 Keep configuration declarative

Use @Bean methods to assemble collaborators, not to perform business workflows, remote calls, or hidden startup side effects. Put runtime behavior in ordinary beans.

22.6 Prefer typed configuration for cohesive settings

Use @Value for small isolated values. Use validated immutable configuration objects when several properties form one concept.

22.7 Keep profiles coarse

Profiles should describe coherent deployment modes. Avoid combinatorial profile sets that act as an undocumented conditional-programming language.

22.8 Minimize mutable broad scopes

Singleton services should normally be stateless or internally thread-safe. Request and session state should be small, explicit, and prevented from escaping its lifecycle.

22.9 Prefer explicit dependencies to @DependsOn

Constructor and factory-method parameters make ordering visible and type-safe. Use @DependsOn only where the dependency is truly non-object-based.

23. Summary

  • @Component is the generic scanned stereotype; custom stereotypes can be meta-annotated with it.
  • @Service, @Repository, and @Controller communicate architectural roles.
  • @Repository can participate in persistence exception translation when supporting infrastructure is present.
  • @RestController combines @Controller and class-level response-body semantics.
  • @Configuration declares Java configuration; proxyBeanMethods controls inter-bean method-call interception.
  • @Bean registers a factory-method result and accepts injected method parameters.
  • @Autowired resolves dependencies by type and candidate metadata; a sole constructor needs no annotation.
  • @Qualifier semantically narrows candidates; generic types can also qualify.
  • @Primary selects a preferred single-valued candidate but does not filter collections.
  • @Value injects placeholders or SpEL results through post-processing and conversion.
  • @Profile conditionally registers definitions based on active profile expressions.
  • @Scope controls instance lifetime; scoped proxies bridge shorter-lived beans into longer-lived collaborators.
  • @Lazy defers creation or resolution but can be defeated by eager dependencies.
  • @DependsOn controls lifecycle order and does not inject a collaborator.

When annotation behavior is surprising, trace the bean definition rather than reading one annotation in isolation: How was the class discovered? Which profiles and conditions registered it? What name, type, scope, qualifiers, primary flag, lazy flag, and dependencies were attached? Which post-processors injected or proxied it? Which web infrastructure later detected it? That sequence reveals the container model beneath Spring’s concise annotation syntax.
