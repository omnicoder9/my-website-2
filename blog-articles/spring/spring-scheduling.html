Spring Framework Scheduling

Spring Scheduling

An expert guide to @Scheduled, cron expressions, fixed delay, fixed rate, scheduler pools, reactive tasks, dynamic triggers, concurrency, clustered deployments, error handling, testing, and production operations.

Spring Framework 7.0.8Java scheduled-executor semanticsImperative and reactive tasksLong-form technical articleVancouver references
Abstract. Spring scheduling separates two questions that are frequently conflated: when a task becomes eligible to run, and where that task executes. TaskScheduler abstracts one-time, fixed-rate, fixed-delay, and trigger-based scheduling. @EnableScheduling registers infrastructure that discovers @Scheduled methods and submits them to a scheduler. Fixed delay measures from completion to the next start; fixed rate measures successive planned start times; cron selects wall-clock instants through a six-field expression and time zone. Correct production use additionally requires explicit pool sizing, deterministic job semantics, idempotency, timeout and retry policy, clustered-instance coordination, graceful shutdown, observability, and tests that do not depend on sleeping.

Spring Framework 7.0.8 provides the TaskScheduler service-provider interface, trigger types, scheduler implementations, declarative @Scheduled processing, reactive scheduling, Quartz integration, and observation metadata for scheduled executions.[1][2]

1. Scheduling mental model

1A trigger calculates an eligible execution time.
2The scheduler waits and makes the task runnable.
3Pool capacity determines when execution actually begins.
4The task performs one bounded unit of work.
5Completion, failure, or cancellation influences the next calculation.
6Lifecycle policy determines shutdown and draining.

TaskScheduler schedules a Runnable at an Instant, according to a Trigger, at a fixed rate, or with a fixed delay. It exposes a Clock so trigger calculations can use the scheduler’s time source. Spring’s traditional local implementation is ThreadPoolTaskScheduler, a wrapper around ScheduledThreadPoolExecutor.[2][3]

Eligibility is not executionA cron instant or fixed-rate tick means that a task is due. A saturated pool, CPU pause, database outage, garbage-collection pause, or previous long-running work can make the actual start late. Correctness must not depend on millisecond-perfect dispatch.

2. Enabling and configuring scheduling

@EnableScheduling imports configuration that registers a ScheduledAnnotationBeanPostProcessor. The post-processor discovers @Scheduled methods and registers them with a scheduler.[4][5]

Java
@Configuration(proxyBeanMethods = false)
@EnableScheduling
public class SchedulingConfiguration {

    @Bean("cpuScheduler")
    ThreadPoolTaskScheduler cpuScheduler(
            ScheduledJobErrorHandler errors) {

        ThreadPoolTaskScheduler scheduler =
                new ThreadPoolTaskScheduler();

        scheduler.setPoolSize(4);
        scheduler.setThreadNamePrefix("schedule-cpu-");
        scheduler.setRemoveOnCancelPolicy(true);
        scheduler.setWaitForTasksToCompleteOnShutdown(true);
        scheduler.setAwaitTerminationSeconds(30);
        scheduler.setErrorHandler(errors);
        return scheduler;
    }

    @Bean("ioScheduler")
    ThreadPoolTaskScheduler ioScheduler(
            ScheduledJobErrorHandler errors) {

        ThreadPoolTaskScheduler scheduler =
                new ThreadPoolTaskScheduler();

        scheduler.setPoolSize(12);
        scheduler.setThreadNamePrefix("schedule-io-");
        scheduler.setRemoveOnCancelPolicy(true);
        scheduler.setWaitForTasksToCompleteOnShutdown(true);
        scheduler.setAwaitTerminationSeconds(60);
        scheduler.setErrorHandler(errors);
        return scheduler;
    }
}

ThreadPoolTaskScheduler defaults to one scheduler thread. Tasks execute on its scheduler threads rather than on an automatically separate worker pool, so pool size directly limits simultaneous scheduled work.[3]

2.1 Scheduler selection

The scheduler attribute on @Scheduled names or qualifies a TaskScheduler or ScheduledExecutorService. Separate pools keep blocking jobs from starving short, latency-sensitive tasks.[6]

Java
@Scheduled(
    fixedDelayString = "${jobs.cleanup.delay:PT5M}",
    initialDelayString = "${jobs.cleanup.initial-delay:PT30S}",
    scheduler = "ioScheduler")
public void removeExpiredUploads() {
    cleanupService.removeExpiredUploads();
}

@Scheduled(
    fixedRateString = "${jobs.metrics.period:PT10S}",
    scheduler = "cpuScheduler")
public void calculateLocalMetrics() {
    metricsSnapshotService.refresh();
}

2.2 Virtual-thread-aligned scheduling

SimpleAsyncTaskScheduler uses one scheduler thread and starts a separate thread for each execution, aligning with JDK virtual threads when enabled. Fixed-delay tasks are the exception: they run on the single scheduler thread, so Spring recommends fixed-rate or cron triggers for virtual-thread concurrency.[1][7]

Java
@Bean("virtualScheduler")
SimpleAsyncTaskScheduler virtualScheduler() {
    SimpleAsyncTaskScheduler scheduler =
            new SimpleAsyncTaskScheduler();
    scheduler.setVirtualThreads(true);
    scheduler.setThreadNamePrefix("schedule-vt-");
    return scheduler;
}

3. @Scheduled

For a periodic task, exactly one of cron, fixedDelay, or fixedRate is specified, with an optional initial delay for fixed schedules. A one-time task can specify only an initial delay. Scheduled methods accept no arguments. Ordinary return values are ignored; reactive return types receive special handling.[6]

Java
@Component
public final class ScheduledJobs {
    private final ReconciliationService reconciliation;

    public ScheduledJobs(ReconciliationService reconciliation) {
        this.reconciliation = reconciliation;
    }

    @Scheduled(
        cron = "${jobs.reconciliation.cron:0 15 2 * * *}",
        zone = "${jobs.reconciliation.zone:UTC}",
        scheduler = "ioScheduler")
    public void reconcile() {
        reconciliation.runOnce();
    }
}

3.1 Numeric and string attributes

Numeric delays and rates use milliseconds by default; timeUnit changes that interpretation. String variants accept placeholders, expressions, plain numbers, ISO-8601 durations, and Spring simple-duration syntax. An explicit unit inside a duration string takes precedence over timeUnit.[1][6]

Java
@Scheduled(
    fixedDelay = 30,
    initialDelay = 5,
    timeUnit = TimeUnit.SECONDS)
void pollNumerically() {
    poller.poll();
}

@Scheduled(
    fixedDelayString = "30s",
    initialDelayString = "PT5S")
void pollWithDurations() {
    poller.poll();
}

3.2 Repeatable schedules

@Scheduled is repeatable. Each declaration creates an independent trigger, so schedules on one method can overlap or run in immediate succession. Multiple instances of a scheduled bean likewise register multiple callbacks.[6][8]

Java
@Scheduled(
    cron = "0 0 8 * * MON-FRI",
    zone = "Europe/London")
@Scheduled(
    cron = "0 0 8 * * MON-FRI",
    zone = "America/New_York")
void openRegionalBusinessDay() {
    businessDayService.openDueRegions();
}

4. Fixed delay

Fixed delay measures the configured delay between completion of one execution and start of the next. If work takes 40 seconds and the delay is 20 seconds, starts are roughly 60 seconds apart, plus scheduler latency.[1][9]

Java
@Scheduled(
    fixedDelayString = "${jobs.inbox-poller.delay:PT20S}",
    initialDelayString = "${jobs.inbox-poller.initial-delay:PT5S}",
    scheduler = "ioScheduler")
public void pollInbox() {
    int processed = inboxService.claimAndProcessBatch(100);
    pollMetrics.recordBatch(processed);
}

Fixed delay fits polling and batch loops where the remote system should rest after each request and a slow run should push the next run later. It is not a wall-clock schedule: process restart resets the local sequence, and execution duration shifts every later invocation.

5. Fixed rate

Fixed rate measures successive planned start times. A ten-second period creates a nominal sequence at 0, 10, 20, and 30 seconds from the initial start. If work is slow, later executions start late. Under ScheduledThreadPoolExecutor, successive executions of the same periodic task do not overlap; effects of one execution happen-before the next.[9]

Java
@Scheduled(
    fixedRateString = "${jobs.heartbeat.period:PT10S}",
    initialDelayString = "PT2S",
    scheduler = "cpuScheduler")
public void publishHeartbeat() {
    heartbeatPublisher.publish(
        Heartbeat.at(clock.instant()));
}
@Scheduled plus @Async changes the modelThe scheduled invocation can return immediately after submitting asynchronous work, allowing later ticks to submit more work while prior work remains active. Concurrency then belongs to the async executor rather than the scheduler.

6. Cron expressions

Spring cron expressions contain six fields: second, minute, hour, day of month, month, and day of week. This differs from five-field Unix crontab syntax because Spring includes seconds. Day of week uses normal cron numbering, with 0 or 7 for Sunday, even with optional Quartz-style L and # constructs.[1][10]

6.1 Validation and next execution

Java
public record CronSchedule(
        String expression,
        ZoneId zone) {

    public CronSchedule {
        CronExpression.parse(expression);
    }

    public Optional<ZonedDateTime> nextAfter(
            ZonedDateTime time) {

        CronExpression cron =
                CronExpression.parse(expression);

        return Optional.ofNullable(
            cron.next(time.withZoneSameInstant(zone)));
    }
}

CronExpression.parse() validates syntax and next(Temporal) calculates the next match. Validate externally supplied expressions when configuration is loaded rather than during the first production run.[10]

6.2 Zones and daylight-saving time

Java
@Scheduled(
    cron = "0 30 2 * * *",
    zone = "America/New_York")
public void runAtLocalTwoThirty() {
    reportingService.createDailyReport();
}

Cron is resolved in the configured zone. Civil time contains gaps when clocks move forward and overlaps when clocks move backward, so a local time can be absent or occur twice. Absolute operational cadences often use UTC; local-business schedules need an explicit daylight-saving policy and tests around transitions.

6.3 Property-driven disabling

The special cron value -, exposed as Scheduled.CRON_DISABLED, disables the trigger and is designed for external configuration.[6]

Java
@Scheduled(
    cron = "${jobs.month-end.cron:-}",
    zone = "${jobs.month-end.zone:UTC}")
public void closeMonth() {
    monthEndService.closeEligiblePeriod();
}

6.4 Lenient and fixed cron execution

A normal CronTrigger is lenient: it calculates from completion and can skip original firings when a task runs too long. CronTrigger.forFixedExecution() calculates from the last scheduled time and preserves every original firing, possibly running follow-up tasks late. Resume factories continue either policy from a known timestamp.[11]

Java
CronTrigger lenient =
        CronTrigger.forLenientExecution(
            "0 */5 * * * *");

CronTrigger catchUpEveryFiring =
        CronTrigger.forFixedExecution(
            "0 */5 * * * *");

ScheduledFuture<?> handle =
        taskScheduler.schedule(
            settlementJob::runOnce,
            catchUpEveryFiring);
Catch-up can create a stormMaking up every missed five-minute run after a two-hour outage creates twenty-four due executions. Prefer a persisted watermark and one reconciliation run when individual ticks have no independent business meaning.

7. Programmatic and dynamic scheduling

SchedulingConfigurer selects a scheduler and registers tasks programmatically. It is the entry point for arbitrary Trigger logic that cannot be expressed by @Scheduled.[12]

Java
@Configuration(proxyBeanMethods = false)
@EnableScheduling
public class DynamicScheduleConfiguration
        implements SchedulingConfigurer {

    private final TaskScheduler scheduler;
    private final ScheduleRepository schedules;
    private final ExportJob exportJob;

    public DynamicScheduleConfiguration(
            @Qualifier("ioScheduler") TaskScheduler scheduler,
            ScheduleRepository schedules,
            ExportJob exportJob) {
        this.scheduler = scheduler;
        this.schedules = schedules;
        this.exportJob = exportJob;
    }

    @Override
    public void configureTasks(ScheduledTaskRegistrar registrar) {
        registrar.setTaskScheduler(scheduler);
        registrar.addTriggerTask(
            exportJob::runOnce,
            context -> schedules.nextExecution(
                "customer-export",
                context.lastCompletion(),
                context.getClock()));
    }
}

A custom trigger receives last scheduled time, actual start, completion time, and the scheduler clock. It can implement adaptive backoff, database-configured next runs, holiday calendars, or outcome-sensitive timing.[1][13]

7.1 Registration and cancellation

Java
@Component
public final class RuntimeScheduleRegistry {
    private final TaskScheduler scheduler;
    private final ConcurrentMap<UUID, ScheduledFuture<?>> tasks =
            new ConcurrentHashMap<>();

    RuntimeScheduleRegistry(
            @Qualifier("ioScheduler") TaskScheduler scheduler) {
        this.scheduler = scheduler;
    }

    public void start(UUID id, Duration period, Runnable task) {
        ScheduledFuture<?> future =
                scheduler.scheduleAtFixedRate(task, period);
        ScheduledFuture<?> old = tasks.put(id, future);
        if (old != null) old.cancel(false);
    }

    public boolean stop(UUID id) {
        ScheduledFuture<?> future = tasks.remove(id);
        return future != null && future.cancel(false);
    }
}

Runtime registries must restore schedules after restart, cancel replaced futures, and define interruption policy. For durable business schedules, persistent triggers, cluster ownership, and operator-controlled misfire handling, Quartz or an external scheduler is usually a better fit than an in-memory map.[14]

8. Reactive scheduled methods

Spring supports no-argument methods returning a Reactive Streams Publisher or a type adaptable to a deferred publisher. The framework obtains the publisher once and schedules repeated subscriptions. Emitted values are ignored, and the publisher must support multiple subscriptions.[1][6]

Java
@Scheduled(
    fixedRateString = "PT30S",
    scheduler = "ioScheduler")
public Mono<Void> refreshReactiveCache() {
    return Mono.defer(() ->
        remoteCatalog.fetchChanges()
            .flatMap(cache::apply)
            .then());
}

Mono.defer creates fresh work for each subscription even though the scheduled method is called once to obtain the publisher. Reactive onError signals are logged at WARN and recovered so later subscriptions continue; they do not pass through the scheduler ErrorHandler. With fixed delay, Spring blocks the subscription to preserve completion-plus-delay semantics. Context shutdown cancels the next subscription and an active subscription.[1][6]

A periodic publisher must finishAn infinite publisher prevents fixed-delay progression and can create repeated long-lived subscriptions under fixed rate. Model one finite unit of work per subscription.

9. Transactions and bounded work

The scheduler supplies a thread and invocation; it does not automatically create a database transaction. Put the business unit of work behind a transactional service boundary so each invocation receives a fresh local transaction under normal Spring semantics.[15]

Java
@Component
final class SettlementSchedule {
    private final SettlementBatchService batches;

    SettlementSchedule(SettlementBatchService batches) {
        this.batches = batches;
    }

    @Scheduled(
        fixedDelayString = "PT15S",
        scheduler = "ioScheduler")
    void settleNextBatch() {
        while (batches.settleOneBatch(100) == 100) {
            // Drain backlog in bounded transactions.
        }
    }
}

@Service
final class SettlementBatchService {

    @Transactional
    public int settleOneBatch(int maximum) {
        List<Payment> claimed =
                payments.claimPending(maximum);
        claimed.forEach(Payment::settle);
        return claimed.size();
    }
}

A single transaction spanning millions of rows increases lock duration, rollback cost, persistence-context growth, and shutdown latency. Claim a bounded batch, commit, and continue.

10. Multi-instance scheduling

@Scheduled is local application-context infrastructure. Five identical replicas each discover and register the same methods, producing up to five executions per trigger unless the work is intentionally parallel or coordinated externally.[4][5]

10.1 Database lease

SQL
create table scheduled_job_lock (
    job_name varchar(120) primary key,
    locked_until timestamp not null,
    locked_by varchar(160) not null,
    last_success timestamp null
);

update scheduled_job_lock
set locked_until = current_timestamp + interval '5 minutes',
    locked_by = :instance_id
where job_name = :job_name
  and locked_until < current_timestamp;

The instance runs only when the conditional update affects one row. The lease must exceed ordinary runtime or be renewed, and the job must remain idempotent because pauses, partitions, and lease expiry can still produce duplicates. Use the database clock consistently.

10.2 Watermark over exact ticks

Java
@Transactional
public void reconcileDueIntervals() {
    JobCheckpoint checkpoint =
            checkpoints.lock("daily-reconciliation");

    Instant upperBound =
            clock.instant().truncatedTo(ChronoUnit.DAYS);

    while (checkpoint.nextStart().isBefore(upperBound)) {
        Instant start = checkpoint.nextStart();
        Instant end = start.plus(1, ChronoUnit.DAYS);
        reconciliation.reconcile(start, end);
        checkpoint.advanceTo(end);
    }
}

A persisted watermark makes downtime recoverable without replaying empty trigger ticks. The scheduler becomes a prompt to check due work; durable state determines what remains.

10.3 Quartz or external orchestration

Spring integrates Quartz through SchedulerFactoryBean and job/trigger adapters. Use a persistent scheduler or platform orchestrator when schedules are durable business data, cluster ownership is required, misfire policy must be explicit, calendars and one-off jobs are extensive, or operators need pause/resume and history independent of one application process.[14][16]

11. Errors, retries, and timeouts

Java’s raw scheduled executor suppresses later periodic executions when an exception escapes. Spring decorates repeating tasks with a default handler that logs and suppresses errors so future executions continue; one-shot tasks use a propagating default. A custom handler can change this behavior.[9][17]

Java
@Component
public final class ScheduledJobErrorHandler
        implements ErrorHandler {

    private final Counter failures;
    private final Logger logger =
            LoggerFactory.getLogger(getClass());

    ScheduledJobErrorHandler(MeterRegistry registry) {
        this.failures = Counter.builder(
                "application.scheduled.failures")
            .register(registry);
    }

    @Override
    public void handleError(Throwable error) {
        failures.increment();
        logger.error("Scheduled task failed", error);
        // Rethrowing normally stops later executions.
    }
}

Retry only failures classified as transient, bound the attempts and total duration, and ensure the operation is idempotent. Configure network, database, and lock timeouts at their native clients; thread interruption is not a universal cancellation mechanism.

12. Lifecycle and shutdown

ThreadPoolTaskScheduler participates in Spring lifecycle management and supports pause/resume and graceful shutdown. Shutdown policies control delayed and periodic work. Waiting for current tasks can preserve consistency, but the platform termination budget must exceed the configured wait.[1][3]

  • Stop accepting new work before draining long jobs.
  • Keep jobs interruptible at batch boundaries.
  • Checkpoint progress before shutdown.
  • Do not configure an unbounded termination wait.
  • Test termination while a task holds a transaction or lease.

13. Testing

13.1 Separate trigger from logic

Java
@Component
final class ExpirySchedule {
    private final ExpiryJob job;

    ExpirySchedule(ExpiryJob job) {
        this.job = job;
    }

    @Scheduled(cron = "${jobs.expiry.cron:-}", zone = "UTC")
    void trigger() {
        job.runOnce();
    }
}

@Service
final class ExpiryJob {
    private final Clock clock;

    ExpiryJob(Clock clock) {
        this.clock = clock;
    }

    ExpiryResult runOnce() {
        Instant cutoff =
                clock.instant().minus(Duration.ofDays(30));
        return repository.expireBefore(cutoff);
    }
}

Test runOnce() directly with a fixed Clock. The annotation needs only a small context test; this avoids sleeping and hoping a background thread runs within an arbitrary window.

13.2 Test cron calculations

Java
@Test
void nextBusinessRunIsMondayMorning() {
    CronExpression expression =
            CronExpression.parse("0 0 9 * * MON-FRI");

    ZonedDateTime fridayAfterRun =
            ZonedDateTime.parse(
                "2026-07-31T10:00:00-04:00"
                + "[America/New_York]");

    ZonedDateTime next = expression.next(fridayAfterRun);

    assertEquals(
        ZonedDateTime.parse(
            "2026-08-03T09:00:00-04:00"
            + "[America/New_York]"),
        next);
}

13.3 Disable background scheduling

Property-driven cron schedules can use - in tests. Spring also supplies NoOpTaskScheduler, which accepts scheduling requests without executing them, specifically for disabled or test setups.[18]

Java
@TestConfiguration(proxyBeanMethods = false)
class SchedulingTestConfiguration {

    @Bean
    @Primary
    TaskScheduler noOpTaskScheduler() {
        return new NoOpTaskScheduler();
    }
}

14. Observability

Spring defines observations for scheduled executions with low-cardinality dimensions including code namespace, function, outcome, and exception. Spring Boot’s scheduledtasks Actuator endpoint lists cron, fixed-rate, fixed-delay, custom, and one-time tasks with execution metadata where available.[19][20]

HTTP
GET /actuator/scheduledtasks HTTP/1.1
Host: service.example.net
Authorization: Bearer ...

Measure execution duration and outcome, scheduled-to-actual start lag, age of last success, records claimed and processed, lease acquisition, backlog distance, active threads, and queue size. A task that returns successfully while processing zero records for hours can still signal an upstream failure.

15. Diagnostics

15.1 Method never runs

Verify @EnableScheduling, component scanning, bean creation, a valid trigger, a non-disabled cron property, scheduler availability, and startup logs. An object constructed with new is not processed by Spring.

15.2 Job runs twice

Check repeatable annotations, overlapping expressions, duplicate bean instances, parent and child contexts, multiple replicas, and dual registration mechanisms.[1][6]

15.3 Job starts late

Inspect runtime versus period, pool saturation, blocked threads, long transactions, CPU pauses, and competing tasks. Separate workloads and measure execution lag.

15.4 Programmatic schedule stops after an error

A raw ScheduledExecutorService suppresses later runs after an exception. Decorate the task with the intended policy or use Spring’s repeating-task error handling.[9][17]

15.5 Cron runs at the wrong time

Confirm six fields, the zone, day-of-week numbering, system clock, and daylight-saving transition. Calculate future instants with CronExpression in a deterministic test.[10]

15.6 Duplicates appear only in production

Production probably has several replicas. Add a lease, partition work deliberately, or move ownership to a clustered scheduler. Keep the job idempotent.

17. Summary

  • TaskScheduler abstracts one-time, trigger-based, fixed-rate, and fixed-delay execution.
  • @EnableScheduling registers infrastructure that discovers @Scheduled methods.
  • Fixed delay measures from completion to the next start.
  • Fixed rate follows planned start times; slow executions become late but do not self-overlap on ScheduledThreadPoolExecutor.
  • Spring cron uses six fields, includes seconds, supports macros and selected L/# extensions, and resolves in a zone.
  • Normal cron triggering is lenient; fixed-execution triggers preserve every firing and can create catch-up pressure.
  • ThreadPoolTaskScheduler defaults to one thread, so explicit pool design matters.
  • Reactive scheduled methods return one reusable deferred publisher that Spring subscribes to repeatedly.
  • Every application replica registers local schedules unless coordination is added.
  • Transactions, retries, leases, watermarks, and idempotency belong to job design, not the annotation.
  • Production readiness requires graceful shutdown, execution-lag metrics, stale-success alerts, schedule inspection, and deterministic tests.

When a job behaves unexpectedly, trace one execution from trigger to effect: Which clock and zone calculated the due instant? Which scheduler and pool owned it? When did it actually start? Was prior work active? Which transaction or lease protected the work? What progress persisted before failure? Which error policy determined whether future executions continued? That sequence turns a convenient annotation into an explicit scheduling system.
