Spring Expression Language (SpEL)

A rigorous guide to SpEL syntax, literals and operators, object-graph navigation, property and method access, collections, conditional expressions, templating, evaluation contexts, variables, functions, Spring bean integration, compilation, and security.

Spring Framework 7.0.9 Parser · Evaluation · Object graphs Collections · Templates · Security Long-form technical article Vancouver references
Abstract. Spring Expression Language (SpEL) is Spring Framework’s expression language for querying and manipulating object graphs at runtime. It supports literals, arithmetic and logical operations, regular-expression matching, property and index access, method and constructor invocation, Java type references, variables, functions, bean references, assignment, null-safe navigation, ternary and Elvis conditionals, collection selection and projection, and expression templates. SpEL can be used programmatically through ExpressionParser and EvaluationContext, or indirectly through Spring features such as @Value and bean-definition expressions. The same flexibility also creates a security boundary: full SpEL evaluation can invoke arbitrary reachable methods and constructors, so untrusted expression strings must not be evaluated as though SpEL were a sandbox. This article explains the language and its runtime model, then shows how to use it precisely and safely.

Spring Framework 7.0.9 defines SpEL as a runtime language for querying and manipulating object graphs. Its language is independent of the Spring container, although Spring uses it extensively in configuration and other portfolio projects. Expressions are parsed into reusable Expression objects and evaluated against a root object plus an optional EvaluationContext.[1][2]

1. Runtime model

1 An ExpressionParser parses a source string.
2 Parsing produces a reusable Expression.
3 An evaluation supplies a root object and optionally an EvaluationContext.
4 The context resolves properties, methods, types, constructors, variables, functions, beans, operators, and conversions.
5 The expression returns a value or, for writable expressions, can assign a value.
Java 
ExpressionParser parser =
    new SpelExpressionParser();

Expression expression =
    parser.parseExpression(
        "'Hello'.concat(' SpEL')");

String result =
    expression.getValue(
        String.class);

System.out.println(result);
// Hello SpEL

ExpressionParser parses raw expression strings and template expressions. Expression encapsulates the already parsed form and exposes typed and untyped getValue(), setValue(), writability, and type-inspection operations. A parse failure produces a ParseException; a runtime evaluation failure produces an EvaluationException.[2][3][4]

2. Evaluation contexts

ContextPurposeCapabilities
StandardEvaluationContextFull SpELProperties, methods, constructors, types, bean references, functions, custom resolvers/accessors
SimpleEvaluationContextRestricted data-binding and condition-style evaluationExplicitly selected property/method support, custom accessors, optional assignment and conversion
Java 
Customer customer =
    new Customer(
        "Ada",
        new Address(
            "Raleigh",
            "NC"));

ExpressionParser parser =
    new SpelExpressionParser();

StandardEvaluationContext context =
    new StandardEvaluationContext(
        customer);

String city =
    parser.parseExpression(
        "address.city")
    .getValue(
        context,
        String.class);

StandardEvaluationContext exposes the full language and is highly configurable. SimpleEvaluationContext deliberately excludes features such as Java type references, constructors, and bean references and requires explicit property and method access policy. Spring documents that this restriction is not a security guarantee; reachable objects and methods still determine what an expression can do.[2][5]

Java 
SimpleEvaluationContext readOnly =
    SimpleEvaluationContext
        .forReadOnlyDataBinding()
        .build();

String city =
    parser.parseExpression(
        "address.city")
    .getValue(
        readOnly,
        customer,
        String.class);
Do not evaluate untrusted SpEL Spring explicitly warns that evaluating expressions obtained from end users or external systems is inherently dangerous. StandardEvaluationContext must never be used for untrusted expressions; SimpleEvaluationContext is restrictive but is not a general sandbox.[2]

3. Syntax

SpEL source is token-based. Tokens include literals, identifiers, property references, indexers, method calls, operators, variables, type references, and collection operators. Spaces, tabs, carriage returns, and newlines can separate tokens and are ignored outside string literals.[6]

3.1 Literal expressions

LiteralExamples
String'hello', "hello", 'can''t'
Integer42, -42, hexadecimal values
Real3.14159, 1.2e3, float/double suffix forms
Booleantrue, false
Nullnull

Strings may use single or double quotes; the matching quote is escaped by doubling it. Numeric literals support negative signs, exponent notation, hexadecimal integers, and decimal real values. Booleans use true/false, and null is a literal value.[7]

Java 
String message =
    parser.parseExpression(
        "'SpEL ''quotes'' work'")
    .getValue(String.class);

Double scientific =
    parser.parseExpression(
        "1.25e3")
    .getValue(Double.class);

Boolean flag =
    parser.parseExpression(
        "true")
    .getValue(Boolean.class);

3.2 Inline lists and maps

SpEL 
{'READ', 'WRITE', 'DELETE'}

{
  'timeout': 2500,
  'retries': 3,
  'enabled': true
}

SpEL supports inline collection literals. Constant inline collections may be represented internally as constant structures and reused by the expression implementation when every element is itself a constant literal.[8][9]

3.3 Array construction

SpEL 
new int[4]

new int[]{1, 2, 3, 5, 8}

new String[2][3]

SpEL supports Java-like array construction syntax, including dimensions and initializers where permitted by the language grammar.[10]

4. Operators

SpEL supplies relational, logical, string, mathematical, assignment, and overloadable operators. Relational operations work with numbers and comparable values, while equality follows SpEL’s comparison semantics rather than Java reference equality syntax alone.[11]

Java 
boolean expensive =
    parser.parseExpression(
        "total >= 100 "
        + "and active")
    .getValue(
        context,
        Boolean.class);

boolean validSku =
    parser.parseExpression(
        "sku matches "
        + "'[A-Z]{3}-[0-9]{6}'")
    .getValue(
        context,

BigDecimal gross =
    parser.parseExpression(
        "unitPrice * quantity")
    .getValue(
        context,

4.1 String operators

SpEL supports string concatenation with +. Current Spring 7 language support also includes string repetition with * and subtraction semantics documented by the operator reference for supported operands. Keep application expressions simple enough that their intent remains obvious; move complex transformations into ordinary Java methods.[11]

4.2 Operator overloading

StandardEvaluationContext can be configured with an OperatorOverloader for selected mathematical operations on custom operand types. Operator overloading is an extension mechanism, not automatic Java method dispatch, and compiled SpEL does not support expressions that rely on overloaded operators.[2]

5. Property access

Property navigation uses a period and is resolved through property accessors. The standard context uses reflective access capable of reading JavaBean-style properties and fields. Indexers operate on arrays, collections, maps, strings, objects, and configured custom index accessors. Numeric indexes are zero-based.[12]

Java 
record Address(
    String city,
    String state) {
}

record Customer(
    String name,
    Address address,
    List<String> roles,
    Map<String, Object> attributes) {
}

Customer customer =
    new Customer(
        "Ada",
        new Address(
            "Raleigh",
            "NC"),
        List.of(
            "USER",
            "ADMIN"),
        Map.of(
            "tier",
            "gold"));

StandardEvaluationContext context =
    new StandardEvaluationContext(
        customer);

String city =
    parser.parseExpression(
        "address.city")
    .getValue(
        context,
        String.class);

String firstRole =
    parser.parseExpression(
        "roles[0]")
    .getValue(
        context,
        String.class);

String tier =
    parser.parseExpression(
        "attributes['tier']")
    .getValue(
        context,
        String.class);

5.1 Writing properties

Java 
class Preferences {
    private boolean notifications;

    public boolean isNotifications() {
        return notifications;
    }

    public void setNotifications(
            boolean notifications) {
        this.notifications =
            notifications;
    }
}

Preferences preferences =
    new Preferences();

SimpleEvaluationContext writeContext =
    SimpleEvaluationContext
        .forReadWriteDataBinding()
        .build();

Expression property =
    parser.parseExpression(
        "notifications");

property.setValue(
    writeContext,
    preferences,
    "true");

assert preferences.isNotifications();

SpEL uses Spring’s conversion service for assignment and typed results. Conversion is generics-aware; for example, assigning a string into an indexed List<Boolean> can convert it to a Boolean if the configured conversion service supports that conversion.[2]

5.2 Safe navigation

SpEL 
customer?.address?.city

members?.[0]?.name

orders?.?[status == 'OPEN']

orders?.![id]

The safe-navigation operator ?. returns null for the particular null-safe operation instead of throwing a null dereference. Since Spring Framework 6.2, null-safe index access uses ?.[], and safe variants also exist for collection selection and projection. In a compound expression, a null result from one null-safe operation does not automatically stop every later subexpression from being evaluated, so compound expressions must still be designed carefully.[13]

6. Method invocation

Methods use Java-like invocation syntax. A call can target the root object, a nested object, or even a literal. Varargs methods are supported. Method resolution is context-dependent and normally reflection-based in StandardEvaluationContext.[14]

Java 
String upper =
    parser.parseExpression(
        "'spring'.toUpperCase()")
    .getValue(String.class);

Boolean eligible =
    parser.parseExpression(
        "isEligible(100, 'USD')")
    .getValue(
        pricingContext,
        Boolean.class);

String segment =
    parser.parseExpression(
        "customer.segment().trim()")
    .getValue(
        orderContext,
        String.class);

6.1 Method resolution policy

SimpleEvaluationContext can be built without method invocation or can opt into data-binding methods. StandardEvaluationContext can install custom MethodResolver implementations or filters. A restricted method surface is especially important when an expression is not fully controlled by application developers.[2][5]

7. Types and constructors

The T(...) operator returns a Java Class and enables static member access. java.lang types can be referenced by simple name; other packages normally require the fully qualified class name. Constructor syntax uses new.[15][16]

SpEL 
T(java.time.Duration).ofSeconds(5)

T(Math).max(10, 25)

new java.math.BigDecimal('19.95')

Type and constructor access are powerful reflective features and are excluded from SimpleEvaluationContext. Do not expose them to expression text that is not fully trusted.[2]

8. Variables

Variables use the #name form and are stored in the evaluation context. The special #root variable always refers to the root evaluation object. #this refers to the current evaluation object and changes while operators such as selection and projection iterate over elements.[17]

Java 
StandardEvaluationContext context =
    new StandardEvaluationContext(
        order);

context.setVariable(
    "minimum",
    new BigDecimal("100.00"));

Boolean qualifies =
    parser.parseExpression(
        "total >= #minimum")
    .getValue(
        context,
        Boolean.class);

8.1 #root and #this

SpEL 
lineItems.?[
  #this.quantity > 1
  and #root.currency == 'USD'
]

9. User-defined functions

A function is registered in the evaluation context and invoked with #functionName(...). StandardEvaluationContext supports registration via reflected Method or MethodHandle. Variables and functions share the same namespace, so names must not collide.[18]

Java 
public final class TextFunctions {

    public static String normalizeSku(
            String value) {
        return value
            .trim()
            .toUpperCase(Locale.ROOT);
    }
}

Method normalize =
    TextFunctions.class.getMethod(
        "normalizeSku",
        String.class);

StandardEvaluationContext context =
    new StandardEvaluationContext();

context.registerFunction(
    "normalizeSku",
    normalize);

String sku =
    parser.parseExpression(
        "#normalizeSku(' abc-123 ')")
    .getValue(
        context,
        String.class);

10. Bean references

If an evaluation context has a BeanResolver, @beanName resolves a bean and &beanName accesses a FactoryBean itself. Bean names containing special characters can be quoted. Spring’s application-context expression infrastructure configures this capability for expressions used in bean definitions.[19]

SpEL 
@pricingService.currentPrice(#sku)

@'regional.tax-policy'.rateFor(#state)

&messageConverterFactory
Bean references increase coupling An expression that reaches arbitrary Spring beans has access to application behavior, not merely data. Prefer explicit variables or dedicated root objects when evaluating expressions programmatically.

11. Collection manipulation

11.1 Selection

Selection filters arrays, Iterable values, or maps using .?[predicate]. Map predicates evaluate against Map.Entry, exposing key and value. .^[predicate] selects the first match, and .$[predicate] selects the last match.[20]

SpEL 
# All expensive lines.
lines.?[unitPrice * quantity > 100]

# First open line.
lines.^[status == 'OPEN']

# Last failed line.
lines.$[status == 'FAILED']

# Map entries with high values.
attributes.?[value > 10]
Java 
@SuppressWarnings("unchecked")
List<LineItem> expensive =
    parser.parseExpression(
        "lines.?[unitPrice "
        + "* quantity > 100]")
    .getValue(
        orderContext,
        List.class);

11.2 Projection

Projection evaluates a subexpression for every element and returns a new collection. The syntax is .![expression]. Projection works with arrays, Iterable types, and maps; projecting a map evaluates the expression against each Map.Entry and returns a list of results.[21]

SpEL 
lines.![sku]

lines.![unitPrice * quantity]

customers.![address?.city]

attributes.![key + '=' + value]

11.3 Selection plus projection

SpEL 
lines
  .?[status == 'OPEN']
  .![sku]

This expression selects open lines and then projects their SKU values. While concise, deeply nested expression pipelines become difficult to debug and maintain; move complex business transformations into ordinary Java methods and call a small method from SpEL when necessary.

12. Conditional expressions

12.1 Ternary operator

SpEL 
total >= 100
  ? 'HIGH_VALUE'
  : 'STANDARD'

The ternary operator has ordinary condition ? ifTrue : ifFalse semantics and returns one branch based on the Boolean condition.[22]

12.2 Elvis operator

SpEL 
displayName ?: 'Unknown'

customer?.nickname ?: customer.name

preferredLocale ?: 'en-US'

SpEL’s Elvis operator ?: provides a default when the left side is null or an empty string. As of Spring Framework 7.0 it also transparently unwraps Optional: an empty Optional falls back to the right side, while a non-empty Optional yields its contained object.[23]

12.3 Null-safe conditional composition

SpEL 
customer?.address?.state == 'NC'
  ? 'DOMESTIC'
  : 'OTHER'

customer?.nickname?.trim()
  ?: 'Anonymous'

13. Template expressions

Template expressions combine literal text with one or more expression blocks. Parsing requires a ParserContext; TemplateParserContext uses #{ and } as its default delimiters. The parser evaluates each block and concatenates the result with literal segments.[24][3]

Java 
Expression template =
    parser.parseExpression(
        "Order #{id} totals "
        + "#{total} #{currency}",
        new TemplateParserContext());

String rendered =
    template.getValue(
        order,
        String.class);

13.1 Custom delimiters

Java 
ParserContext custom =
    new ParserContext() {
        @Override
        public boolean isTemplate() {
            return true;
        }

        @Override
        public String getExpressionPrefix() {
            return "${{";
        }

        @Override
        public String getExpressionSuffix() {
            return "}}";
        }
    };

Expression expression =
    parser.parseExpression(
        "Customer: ${{name}}",
        custom);

Template expressions are useful for compact display strings and framework configuration. They should not replace a real template engine for large documents, escaping-sensitive HTML, localization, or complex presentation logic.

14. SpEL in Spring bean definitions

In Spring bean configuration, expression blocks use the #{...} form. The application context expression resolver exposes context beans and standard objects including environment, systemProperties, and systemEnvironment. @Value can inject SpEL results into fields and method or constructor parameters.[25]

Java 
@Component
public final class RuntimeInfo {

    private final String region;
    private final int processors;
    private final Duration timeout;

    public RuntimeInfo(
            @Value(
                "#{systemEnvironment"
                + "['APP_REGION'] "
                + "?: 'local'}")
            String region,

            @Value(
                "#{T(java.lang.Runtime)"
                + ".getRuntime()"
                + ".availableProcessors()}")
            int processors,

            @Value(
                "#{@timeoutPolicy"
                + ".requestTimeout()}")
            Duration timeout) {

        this.region = region;
        this.processors = processors;
        this.timeout = timeout;
    }
}
XML 
<bean
  id="reportService"
  class="com.example.ReportService">

  <property
    name="workerCount"
    value=
      "#{T(java.lang.Runtime)
        .getRuntime()
        .availableProcessors()}"/>

  <property
    name="region"
    value=
      "#{systemEnvironment['APP_REGION']
        ?: 'local'}"/>

</bean>

14.1 ${...} versus #{...}

SyntaxMeaningExample
${...}Property placeholder resolved from property sources${payments.timeout:2s}
#{...}SpEL evaluation#{@clock.instant()}

A property placeholder retrieves external configuration; SpEL evaluates an expression. They can be combined in configuration scenarios, but excessive nesting obscures configuration intent. Prefer typed configuration properties for cohesive external settings and reserve SpEL for genuinely computed values.

15. Parser configuration

SpelParserConfiguration controls parser and evaluation behavior including auto-growing null references and collections, compiler mode, maximum expression length, operation limits, and large power-operation limits. Spring 7.0.9 documents default limits of 10,000 expression characters and 10,000 evaluation operations; BigInteger/BigDecimal exponentiation is also bounded by a configurable maximum bit size.[2]

Java 
SpelParserConfiguration config =
    new SpelParserConfiguration(
        false,  // autoGrowNullReferences
        false,  // autoGrowCollections
        1_000   // maximum auto-grow size
    );

SpelExpressionParser parser =
    new SpelExpressionParser(
        config);

15.1 Auto-growing object graphs

Auto-grow can instantiate null intermediate elements and enlarge collections when an indexed write exceeds current size. This is convenient for data binding but creates implicit mutation, so it should be enabled only where that behavior is intentional and bounded.[2]

16. SpEL compilation

SpEL is normally interpreted. Its optional compiler generates a Java class implementing the observed expression behavior and can substantially reduce repeated evaluation cost. Compilation depends on runtime type information learned during interpreted executions, so it is best suited to stable expression shapes whose referenced types do not change.[2]

ModeBehavior
OFFAlways interpreted; default
IMMEDIATECompile as soon as practical; compiled failure propagates
MIXEDSwitch between interpreted and compiled modes; compiled failures can fall back to interpretation
Java 
SpelParserConfiguration config =
    new SpelParserConfiguration(
        SpelCompilerMode.MIXED,
        Thread.currentThread()
            .getContextClassLoader());

SpelExpressionParser compiledParser =
    new SpelExpressionParser(
        config);

Expression hotExpression =
    compiledParser.parseExpression(
        "customer.address.city");

Not every expression can be compiled. Current documented limitations include assignment, conversion-service-dependent expressions, custom resolvers, overloaded operators, Optional-based null-safe/Elvis forms, array construction, collection selection/projection, and bean references. Compilation is therefore an optimization for a subset of frequently repeated expressions, not a different language mode.[2]

18. Security design

18.1 Trusted expressions

Expressions committed with application source, authored by trusted administrators, or generated from fixed templates are the natural SpEL use case. They can safely use powerful features when the application deliberately grants that capability.

18.2 Untrusted expressions

Never take an arbitrary query parameter, header, form field, database string controlled by an untrusted party, or external message and evaluate it as full SpEL. Reflection-backed property and method access can expose filesystem, process, network, framework, or data-access operations reachable from the context. Restricting syntax alone does not automatically make the reachable object graph safe.[2]

Java 
// Dangerous design:
String expressionText =
    request.getParameter("filter");

StandardEvaluationContext context =
    new StandardEvaluationContext(
        domainEntity);

Object result =
    parser.parseExpression(
        expressionText)
    .getValue(context);

// Never use this pattern for untrusted input.

18.3 Safer alternative

Java 
record OrderFilterView(
    String status,
    BigDecimal total,
    String region) {
}

SimpleEvaluationContext context =
    SimpleEvaluationContext
        .forReadOnlyDataBinding()
        .withAssignmentDisabled()
        .build();

// Even here, expression text from an
// untrusted source requires a deliberate,
// reviewed policy. Prefer a real query DSL.

For end-user filtering, prefer a purpose-built grammar or structured query object whose allowed operators and fields are explicit. If SpEL is retained in a constrained administrative feature, expose dedicated safe DTOs rather than JPA entities, files, connections, application contexts, or infrastructure clients.[2]

19. Performance

  • Parse an expression once and reuse the resulting Expression object.
  • Reuse evaluation configuration where appropriate; avoid rebuilding resolvers for every call.
  • Prefer ordinary Java for hot loops when the expression is fixed at compile time.
  • Consider compilation only after profiling identifies repeated interpretation as material.
  • Keep selection/projection over large collections out of latency-critical expression paths.
  • Bound expression length and operation count, especially for configurable administrative expressions.
Java 
public final class CompiledRule {

    private final Expression expression;

    public CompiledRule(
            ExpressionParser parser,
            String source) {

        this.expression =
            parser.parseExpression(source);
    }

    public boolean test(
            EvaluationContext context,
            Object root) {

        return Boolean.TRUE.equals(
            expression.getValue(
                context,
                root,
                Boolean.class));
    }
}

20. Testing expressions

20.1 Treat expressions as code

Java 
class DiscountRuleTest {

    private final ExpressionParser parser =
        new SpelExpressionParser();

    private final Expression rule =
        parser.parseExpression(
            "customer.tier == 'GOLD' "
            + "and total >= 100");

    @Test
    void goldCustomerQualifies() {
        OrderView order =
            fixture(
                "GOLD",
                "125.00");

        Boolean result =
            rule.getValue(
                order,
                Boolean.class);

        assertThat(result)
            .isTrue();
    }

    @Test
    void lowerValueDoesNotQualify() {
        OrderView order =
            fixture(
                "GOLD",
                "25.00");

        assertThat(
            rule.getValue(
                order,

            .isFalse();
    }
}

20.2 Boundary cases

  • Null intermediate properties and safe-navigation behavior.
  • Empty collections, first/last selection with no match, and map projections.
  • Numeric coercion, decimal precision, and conversion-service behavior.
  • Empty strings and Optional values with Elvis.
  • Unexpected runtime types under compiled expressions.
  • Maximum expression length and operation limits.
  • Attempts to access disallowed properties or methods in restricted contexts.

22. Anti-patterns

22.1 Turning SpEL into the primary business language

Complex pricing, authorization, tax, and workflow logic becomes difficult to refactor, debug, statically analyze, and version when encoded mainly as strings. Use SpEL for concise configuration and rule predicates; use Java or a dedicated rules/DSL system for large domain logic.

22.2 Evaluating arbitrary user expressions

Full SpEL is a reflective execution language, not an end-user sandbox. Use a purpose-built query grammar for untrusted input.[2]

22.3 Parsing on every request

Parsing is reusable work. Parse stable expressions once and cache the Expression.

22.4 Exposing infrastructure objects as root values

A root object such as DataSource, File, Spring context, repository, or cloud client dramatically expands reachable behavior. Expose a narrow purpose-built view.

22.5 Using SpEL templates for HTML documents

SpEL templating is basic expression interpolation. It does not provide a full presentation engine’s escaping, layout, fragment, localization, and rendering features.

22.6 Deep expression chains

Expressions that combine property traversal, several selections, projections, method calls, and conditionals become opaque. Extract a Java method with a meaningful name and invoke that method instead.

23. Worked rule engine

Java 
public record OrderRuleView(
    String status,
    BigDecimal total,
    String currency,
    CustomerRuleView customer,
    List<LineRuleView> lines) {
}

public record CustomerRuleView(
    String tier,
    String region) {
}

public record LineRuleView(
    String sku,
    int quantity,
    BigDecimal unitPrice) {
}

public final class TrustedOrderRule {

    private final Expression expression;

    private static final SimpleEvaluationContext
            EVALUATION_CONTEXT =
        SimpleEvaluationContext
            .forReadOnlyDataBinding()
            .withAssignmentDisabled()
            .build();

    public TrustedOrderRule(
            SpelExpressionParser parser,
            String source) {

        this.expression =
            parser.parseExpression(source);
    }

    public boolean matches(
            OrderRuleView order) {

        return Boolean.TRUE.equals(
            expression.getValue(
                EVALUATION_CONTEXT,
                order,
                Boolean.class));
    }
}
SpEL 
status == 'READY'
and currency == 'USD'
and customer.tier == 'GOLD'

  quantity >= 2

This design deliberately exposes a read-only DTO rather than an entity or service. The expression is authored by trusted application administrators, parsed once, evaluated with read-only data-binding access, and limited to properties and the methods reachable through the restricted context. If expressions were supplied by untrusted users, a custom query parser with an explicit grammar would be preferable even with this reduced context.[2]

24. Expert practices

  • Use SpEL when runtime configurability provides real value; use Java when behavior is fixed.
  • Parse once and reuse Expression instances.
  • Choose SimpleEvaluationContext for deliberately restricted data-binding scenarios and StandardEvaluationContext only when full language capabilities are required.
  • Never treat either context as a universal sandbox for arbitrary untrusted text.
  • Expose narrow root DTOs and explicitly registered variables/functions.
  • Keep property paths, collection expressions, and conditionals short enough to review.
  • Use low-complexity template expressions; use a template engine for real documents.
  • Distinguish property placeholders ${...} from SpEL blocks #{...}.
  • Use safe navigation and Elvis for expected absence, not to suppress programming errors indiscriminately.
  • Enable compilation only for measured hot expressions with stable runtime types.
  • Test nulls, collections, conversions, expression limits, and security boundaries.
  • Version trusted business rules as code or reviewed configuration and retain rollback history.

25. Summary

  • SpEL is Spring’s runtime language for querying and manipulating object graphs.
  • SpelExpressionParser parses source into reusable Expression objects.
  • StandardEvaluationContext exposes full language features; SimpleEvaluationContext exposes a configurable subset.
  • Syntax includes string, numeric, Boolean, null, list, map, and array expressions.
  • Operators cover comparison, logic, regex matching, arithmetic, assignment, and conditionals.
  • Property and index access navigate object graphs, collections, maps, strings, and configured custom structures.
  • Method invocation supports normal and varargs calls; T(...) exposes Java types and static members.
  • Variables use #name; #root and #this have special evaluation semantics.
  • Functions are registered methods or method handles invoked through the variable namespace.
  • Selection filters collections; projection transforms each element into a new result collection.
  • Ternary, Elvis, and safe-navigation operators support compact conditional and null-aware expressions.
  • Template parsing combines literal text with expression blocks.
  • Spring bean definitions use #{...} for SpEL and ${...} for property placeholders.
  • SpEL can be compiled for selected stable hot expressions, but many dynamic features remain interpreted.
  • Untrusted SpEL evaluation is dangerous; use a dedicated query language or tightly controlled object model instead.

A disciplined way to reason about any expression is to ask five questions: What is the root object? Which evaluation context is used? Which properties, methods, types, variables, functions, and beans are reachable? Can the expression mutate state? Who controls the expression string? Those questions determine both correctness and security more reliably than the surface syntax alone.
