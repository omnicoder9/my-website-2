01 The integration problem has not moved

Every non-trivial system eventually stops being a program and becomes a negotiation. Two runtimes that were written by different teams, deployed on different schedules, and funded by different cost centres have to agree on what a message means and what happens when one of them is not there. The Spring portfolio is, more than anything else, an accumulated set of answers to that negotiation — and the answers have specific, non-interchangeable failure modes.

It is tempting to read the six subjects of this article — REST, SOAP, GraphQL, gRPC, messaging, and batch — as a chronology, with SOAP as the embarrassing ancestor and gRPC as the destination. That reading is wrong in a way that produces bad architectures. They are not generations of one idea. They are answers to different questions about coupling, and a large enterprise usually needs four or five of them at once, in the same JVM, wired to the same domain model. The interesting engineering is not choosing a winner; it is deciding which coupling you are willing to accept at each seam, and then making that decision legible in code.

What has changed, and changed sharply in the last eighteen months, is the substrate. Spring Boot 4.0 and Spring Framework 7.0 shipped in November 2025 as a coordinated release across the whole portfolio, moving Spring AMQP to 4.0, Spring Batch to 6.0, Spring for GraphQL to 2.0, Spring Integration to 7.0, Spring for Apache Kafka to 4.0 and Spring Web Services to 5.0 in one go.1 That release drew a line under a decade of accumulated compromises: retry moved from an add-on library into the core framework, API versioning became a first-class concern of the request-mapping infrastructure, JSpecify annotations replaced the old bespoke nullability markers across the portfolio, and Jakarta EE 11 and Jackson 3 became the baseline.1,2,3 Spring Data's ahead-of-time query generation moved work from runtime to build time, with correspondingly large reductions in startup cost.4 Spring Boot 4.1 followed on 10 June 2026, folding gRPC support into Boot's own starters and modules.5,6

This article is a practitioner's map of that terrain as it stands in mid-2026. It assumes you know what a bean is, what a broker does, and why distributed transactions went out of fashion. It is organised by integration style rather than by project, because the project boundaries in Spring are increasingly an implementation detail: spring-retry is now core framework code, gRPC autoconfiguration migrated from a satellite project into Boot, and Spring Batch 6 borrows Spring Integration channels to dispatch step executions.7,8,9

What "integration pattern" is supposed to mean

The vocabulary in this article is not invented. Gregor Hohpe and Bobby Woolf's Enterprise Integration Patterns, published in 2003, catalogued sixty-five messaging patterns and, crucially, opened with a taxonomy of four integration styles: file transfer, shared database, remote procedure invocation, and messaging.10 Spring Integration was built explicitly as an implementation of that catalogue — its documentation has described itself in those terms since the 2.0 line, when Message History and Control Bus were added specifically to close gaps against the book.11 The value of that lineage is not nostalgia. It is that "aggregator", "splitter", "claim check" and "dead letter channel" are shared nouns. A reviewer reading .aggregate(a -> a.correlationExpression(...)) knows immediately what invariant is at stake — correlation, completeness, and expiry — without reverse-engineering it from a nest of conditionals.

The four styles have not aged. What has changed is their relative cost. File transfer used to be the cheap option and is now the expensive one, because it externalises schema drift into a nightly failure. Shared database used to be the pragmatic option and is now understood as coupling with extra steps: two services that share tables share a deployment schedule whether they admit it or not. RPC became cheap enough to be the default, which is precisely the problem — the default is a synchronous, temporally coupled call graph whose availability is the product of its members' availabilities. Messaging is the only style in the taxonomy that decouples in time, and everything else in this article is, at some level, an argument about when that decoupling is worth the loss of a stack trace.

02 A working taxonomy for choosing

Before the protocols, a frame. Three questions decide almost every integration choice, and they are not the questions teams usually argue about.

Who owns the schema, and how often can it change?

SOAP's answer is a WSDL and an XML Schema under change control, negotiated before code exists.12,13 gRPC's answer is a .proto file with numbered fields and explicit reserved declarations, checked into a repository that both sides build against.14 GraphQL's answer inverts the question: the server publishes a type system and the client declares, per request, which subset it wants.15 REST, at least as practised, usually has no answer at all — which is why API versioning has been an unsolved argument for fifteen years and why Spring Framework 7 finally shipped an opinionated mechanism for it.16 Messaging can adopt any of these answers, and the decision of which one is the single highest-leverage choice in an event-driven architecture.

Whose thread waits?

In a synchronous call, the caller's thread is held hostage by the callee's latency. That is tolerable at one hop and pathological at five. Every technique for managing it — timeouts, bulkheads, circuit breakers, deadlines, virtual threads — is an attempt to bound the damage rather than remove it. In asynchronous messaging, nobody waits: the broker absorbs the availability difference between producer and consumer, and in exchange you give up the ability to answer "did it work?" in the same request. Spring Framework 7 makes the synchronous side cheaper to defend, with @Retryable and @ConcurrencyLimit available without any extra dependency and with @Retryable extending to reactive return types by decorating the Reactor pipeline.17,7 It does not make the coupling go away.

What is the unit of failure?

A REST call fails one request. A batch job fails one chunk — and, if the JobRepository is doing its work, resumes from that chunk rather than from the beginning.18 A message consumer fails one delivery, and then fails it again, and then again, until something removes it from the retry loop. The unit of failure determines what "retry" means, and getting it wrong is how you end up with a partition stalled behind one poison record or a nightly job that reprocesses eleven million rows because someone made the commit interval equal to the file size.

The portfolio, briefly

Spring's projects have accumulated over two decades in response to whichever protocol had become load-bearing for ordinary enterprises. Spring Web Services arrived for the WS-* era and still exists because regulated interfaces do not get rewritten; Spring Integration arrived to make Hohpe and Woolf's patterns into beans; Spring Batch arrived because the mainframe workload never actually went away; Spring for Apache Kafka arrived when the log displaced the queue; Spring for GraphQL and Spring gRPC arrived last, after their protocols had crossed from novelty into infrastructure.

03 REST: the default, and its unfinished business

REST is what you get when nobody makes a decision, which is both its greatest strength and the source of most of its pathologies. Roy Fielding's dissertation described an architectural style defined by constraints — client–server, statelessness, cacheability, a uniform interface, layered systems — whose purpose was to make network-based systems evolvable at internet scale.19 The wire semantics those constraints assume — methods, status codes, conditional requests, caching directives — are specified in RFC 9110, and most REST arguments are really arguments about which parts of it a team has read.20 What the industry adopted was the URL-and-JSON subset, and it adopted it because a person can curl it. That is not a small property. Debuggability by a human with a terminal is a genuine architectural advantage, and it is the reason REST remains correct for public APIs, for edges facing browsers and mobile clients, and for any interface whose consumers you do not control.

The server side is largely settled

Annotated controllers, content negotiation via HttpMessageConverter, validation via Jakarta Bean Validation, and exception translation have been stable for a decade. The one genuinely important recent addition is standardised error bodies. Spring implements RFC 9457 problem details as a first-class type: ProblemDetail can be returned from any @ExceptionHandler or handler method, the status property drives the HTTP status, the instance property is populated from the current path, and the Jackson codecs advertise application/problem+json so content negotiation favours it.21,22 Extending ResponseEntityExceptionHandler in an @ControllerAdvice turns every built-in Spring MVC exception into the same shape.21,23

This matters more than it sounds. An error contract is part of your API contract, and a hand-rolled {"error": "..."} envelope means every client writes bespoke parsing for every service. A stable type URI is something a client can branch on without string-matching an English sentence that a well-meaning developer will eventually rephrase.

OrderController.javaJava
@RestController
@RequestMapping("/orders")
class OrderController {

    private final OrderService orders;

    OrderController(OrderService orders) {
        this.orders = orders;
    }

    // Two generations of the same resource, selected by the configured version strategy.
    @GetMapping(path = "/{id}", version = "1")
    OrderV1 getV1(@PathVariable String id) {
        return OrderV1.from(orders.require(id));
    }

    @GetMapping(path = "/{id}", version = "1.1+")   // 1.1 and every later version
    OrderV2 getV2(@PathVariable String id) {
        return OrderV2.from(orders.require(id));
    }

    @PostMapping
    ResponseEntity<Void> place(@Valid @RequestBody PlaceOrder cmd,
                               UriComponentsBuilder uri) {
        Order created = orders.place(cmd);
        return ResponseEntity
                .created(uri.path("/orders/{id}").build(created.id()))
                .build();
    }

    // RFC 9457 body, machine-readable, with a stable type URI the client can branch on.
    @ExceptionHandler(InsufficientCredit.class)
    ProblemDetail handle(InsufficientCredit ex) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(
                HttpStatus.UNPROCESSABLE_ENTITY, ex.getMessage());
        pd.setType(URI.create("https://errors.example.com/insufficient-credit"));
        pd.setTitle("Insufficient credit");
        pd.setProperty("shortfallMinor", ex.shortfallMinor());
        return pd;
    }
}

API versioning finally has an opinion

Fielding argued against versioning; the industry does it anyway, and until recently Spring made you build the mechanism yourself.16 Framework 7 adds a version attribute to @RequestMapping and its specialisations, with the extraction strategy — path segment, request header, query parameter, or media type parameter — configured centrally rather than baked into each mapping.16,24 Spring Boot deliberately does not impose a default strategy, because the right choice depends on your proxies, your caches and your clients.24

ApiVersionConfig.javaJava
@Configuration
class ApiVersionConfig implements WebMvcConfigurer {

    @Override
    public void configureApiVersioning(ApiVersionConfigurer configurer) {
        configurer.useRequestHeader("API-Version")          // header strategy
                  .addSupportedVersions("1", "1.1", "2")    // anything else -> 400
                  .setVersionRequired(false)
                  .setDefaultVersion("1");
    }
}

Two details are worth internalising. First, versions are compared semantically, not as strings, so "1.1+" means "this version and all later ones" and a mapping can declare a floor rather than an exact match. Second, versioning is symmetric: the same concept exists on the client through an ApiVersionInserter, on @HttpExchange methods via a version attribute, and in tests through RestTestClient and WebTestClient.16 A versioning scheme you cannot exercise in a test is a versioning scheme you will break.

The client side has been rebuilt, and RestTemplate is on notice

The client story is where the last two years of change concentrate. RestTemplate arrived in Spring 3.0 and has carried an enormous amount of production traffic, but its template-style API cannot express what a modern client needs, and in September 2025 the Spring team published an explicit plan: announce the intent to deprecate in 7.0, apply @Deprecated in 7.1 (provisionally November 2026), and remove it in 8.0 — leaving open-source support in place until at least 2029.25 That is a decade-long runway, not an emergency, but new code should not be starting there.

The replacement is two-layered. RestClient, introduced in 6.1, is a fluent synchronous client with WebClient's ergonomics and considerably more flexibility around error handling: where RestTemplate throws HttpClientErrorException uniformly for 4xx responses, RestClient allows custom status handlers.26,27 Its builder also signals the direction of travel: the old messageConverters setters are deprecated for removal in favour of a configureMessageConverters consumer that composes across multiple contributors.28 Above it sits the HTTP interface client: you declare a Java interface with @HttpExchange methods, and HttpServiceProxyFactory generates a proxy backed by RestClient, WebClient or RestTemplate through an adapter.29 The same interface can be implemented by an @Controller on the server side, which makes the contract a shared artifact rather than two drifting copies.26

PricingClient.javaJava
// 1. The contract: an interface, not an implementation.
@HttpExchange("/pricing")
interface PricingClient {

    @GetExchange("/quote/{sku}")
    Quote quote(@PathVariable String sku, @RequestParam int qty);

    @PostExchange(url = "/reserve", version = "1.1")
    Reservation reserve(@RequestBody ReserveRequest request);
}

// 2. The proxy: one factory call, transport chosen here and only here.
@Configuration
class PricingClientConfig {

    @Bean
    PricingClient pricingClient(RestClient.Builder builder) {
        RestClient client = builder
                .baseUrl("https://pricing.internal")
                .defaultHeader("User-Agent", "checkout/4.2")
                .build();
        return HttpServiceProxyFactory
                .builderFor(RestClientAdapter.create(client))
                .build()
                .createClient(PricingClient.class);
    }
}

Framework 7 pushes this further with grouped, autoconfigured registration via @ImportHttpServices, so client interfaces no longer need a hand-written factory bean each, and Spring Security 7 adds OAuth 2.0 support for HTTP service groups by detecting a @ClientRegistrationId annotation on @HttpExchange methods.30 For teams who adopted Spring Cloud OpenFeign, the migration is close to mechanical: the annotations and method signatures are near-identical, and the result is one fewer external dependency with first-class support for versioning and Boot configuration.

The one place RestClient does not yet displace WebClient is streaming. The Spring team has been explicit that streaming support in RestClient is unresolved, because there is no clean path in the Java platform today that composes well with virtual threads and structured concurrency.25 If you are consuming server-sent events or long-lived response bodies, stay reactive.

Defending a synchronous call

A REST client that has no timeout is a distributed-systems bug waiting for a bad day. Framework 7 puts the standard defences in the core framework, removing the spring-retry dependency that most projects previously carried — that project is now in maintenance mode.7,31 Annotate a configuration class with @EnableResilientMethods and @Retryable and @ConcurrencyLimit become active; a bare @Retryable retries any exception up to three times with a one-second delay.32 RetryTemplate covers the programmatic case, and @ConcurrencyLimit provides a bulkhead that is particularly relevant under virtual threads, where there is no pool size to act as an accidental limit.7,33

ShippingGateway.javaJava
@Configuration
@EnableResilientMethods          // activates @Retryable and @ConcurrencyLimit processing
class ResilienceConfig { }

@Service
class ShippingGateway {

    private final ShippingClient client;

    ShippingGateway(ShippingClient client) {
        this.client = client;
    }

    // Retry only what is plausibly transient. Retrying a 400 just multiplies the error.
    @Retryable(includes = { ResourceAccessException.class, HttpServerErrorException.class },
               maxAttempts = 4,
               delay = 200,
               multiplier = 2.0,
               jitter = 100,
               maxDelay = 3000)
    Label buy(Shipment shipment) {
        return client.purchaseLabel(shipment);
    }

    // Bulkhead: at most eight threads may be inside this method at once.
    @ConcurrencyLimit(8)
    List<Rate> rates(Shipment shipment) {
        return client.quoteAll(shipment);
    }

    // Reactive return types are decorated with Reactor's retry spec instead.
    @Retryable(maxAttempts = 3, delay = 100)
    Mono<Void> notifyAsync(String orderId) {
        return client.notifyShipped(orderId);
    }
}

The failure mode to watch is retrying non-idempotent operations. A retried POST that timed out after the server committed produces a duplicate. Either make the operation idempotent with a client-supplied key, or restrict includes to exceptions that prove the request never reached the handler. Blanket @Retryable on a payment capture is a way to charge a customer four times with excellent test coverage.

Testing

RestTestClient, new in 7.0, is a genuine client rather than a mock dispatcher wrapper, and it configures both the client-side version inserter and the server-side ApiVersionStrategy, so version negotiation itself becomes testable.16,34 Combined with problem-detail assertions, the test below covers the entire error contract — status, media type, and body shape — which is exactly the surface that clients depend on and that refactoring silently breaks.

04 SOAP: the contract you cannot renegotiate

Nothing dates an architecture discussion faster than dismissing SOAP. Spring Web Services 5.0.0 shipped on 18 November 2025 alongside the rest of the Boot 4 wave.35,1 It is maintained because the interfaces it serves — payment schemes, insurance clearing houses, government filing systems, telecom OSS/BSS — are not going to be rewritten in your lifetime, and because their operators are frequently required by regulation to publish a machine-readable contract with signed, encrypted, non-repudiable messages.

Spring-WS makes one strong claim that distinguishes it from the JAX-WS lineage: it supports contract-first development only, and it argues the case rather than merely asserting it.36 A contract generated from Java classes has two defects. It leaks refactorings into the wire format, so renaming a field breaks a partner. And it cannot express what XML Schema can: object graphs with cyclic references marshal into structures that no XML validator can check, and the standard RPC/encoded workaround was deprecated in favour of document/literal by the WS-I Basic Profile.36 The schema comes first because the schema is the only thing both parties can agree on without agreeing on a programming language.

The programming model

Spring-WS mirrors the DispatcherServlet design: a MessageDispatcherServlet front controller, endpoint mappings, endpoint adapters and an interceptor chain.36 Given an XSD and a set of naming conventions, Spring-WS will generate the WSDL for you rather than requiring it to be written by hand — which is how most contract-first projects should start.37 Dispatch is on the qualified name of the payload root element rather than on a URL, which is the correct granularity for a protocol where the URL carries no semantics. Incoming XML can be handled through DOM, SAX or StAX, through JDOM, dom4j or XOM, or through a marshalling technology — the Object/XML Mapping module supports JAXB, Castor, XMLBeans, JiBX and XStream and is usable outside web-service code entirely.38

Note what the schema is doing: CurrencyCode is constrained by a pattern and MandateId by a maximum length. Those constraints are enforced at the edge by a PayloadValidatingInterceptor before a single application bean runs. In a JSON-over-HTTP service the equivalent checks live in Bean Validation annotations inside your domain objects, which means each client discovers them by trial and error at runtime. This is the fundamental trade: SOAP moves validation into a published, machine-readable artifact, and pays for it with ceremony.

SettlementEndpoint.javaJava
@Endpoint
class SettlementEndpoint {

    private static final String NS = "http://example.com/payments/schemas";

    private final SettlementService service;

    SettlementEndpoint(SettlementService service) {
        this.service = service;
    }

    // Dispatch is on the qualified name of the payload root element,
    // not on a URL and not on a method name.
    @PayloadRoot(namespace = NS, localPart = "SettlementRequest")
    @ResponsePayload
    public SettlementResponse settle(@RequestPayload SettlementRequest request) {
        Receipt receipt = service.settle(
                request.getMandateId(),
                Money.of(request.getAmountMinor(), request.getCurrency()),
                request.getValueDate());

        SettlementResponse response = new SettlementResponse();
        response.setReceiptId(receipt.id());
        response.setStatus(receipt.status().name());
        return response;
    }
}

@EnableWs
@Configuration
class WebServiceConfig extends WsConfigurerAdapter {

    @Bean
    ServletRegistrationBean<MessageDispatcherServlet> messageDispatcher(ApplicationContext ctx) {
        MessageDispatcherServlet servlet = new MessageDispatcherServlet();
        servlet.setApplicationContext(ctx);
        servlet.setTransformWsdlLocations(true);
        return new ServletRegistrationBean<>(servlet, "/ws/*");
    }

    // The WSDL is derived from the schema; the schema is the artifact under change control.
    @Bean(name = "payments")
    DefaultWsdl11Definition wsdl(XsdSchema schema) {
        DefaultWsdl11Definition wsdl = new DefaultWsdl11Definition();
        wsdl.setPortTypeName("PaymentsPort");
        wsdl.setLocationUri("/ws");
        wsdl.setTargetNamespace("http://example.com/payments/definitions");
        wsdl.setSchema(schema);
        return wsdl;
    }

    @Bean
    XsdSchema paymentsSchema() {
        return new SimpleXsdSchema(new ClassPathResource("payments.xsd"));
    }

    // Reject malformed payloads at the edge, with a SOAP Fault, before any bean runs.
    @Override
    public void addInterceptors(List<EndpointInterceptor> interceptors) {
        PayloadValidatingInterceptor validating = new PayloadValidatingInterceptor();
        validating.setXsdSchema(paymentsSchema());
        validating.setValidateRequest(true);
        validating.setValidateResponse(true);
        interceptors.add(validating);
    }
}

The client, and WS-Security

WebServiceTemplate handles the client side, usually through WebServiceGatewaySupport so that the marshaller and interceptors are wired in one place. Where SOAP still has no real competitor is message-level security: Spring-WS supports SOAP Message Security 1.1 with the Username Token, X.509 Certificate, SAML and Kerberos token profiles.36 That distinction — security applied to the message rather than to the transport — is what allows a signed payload to traverse three intermediaries and remain verifiable at the destination. TLS terminating at a load balancer gives you nothing comparable.

How to live with it

The practical failure mode of a SOAP integration in a modern codebase is contamination: generated JAXB types with 40-character namespaces leaking into service interfaces, domain logic branching on SOAPFaultException, and a partner's optional-everything schema forcing null checks through six layers. Treat the generated types as a boundary dialect. Map them at the endpoint, keep the domain free of them, and put the WSDL and XSD under the same review discipline as a database migration — because that is what they are.

The 5.0 release is mostly a modernisation: Jakarta alignment, JSpecify nullability, and removal of long-deprecated support such as XMLUnit 1 in the test module.39 Do not expect new capability here. Expect it to keep working, which for this class of integration is the entire requirement.

05 GraphQL: moving the shape decision to the client

GraphQL is best understood not as "a better REST" but as a specific trade: the server gives up control over response shape in exchange for eliminating the round-trip negotiation that REST forces on aggregating clients.15 A mobile client that needs an order, its customer, its lines and the product on each line makes one request and receives exactly those fields. In REST, it makes four requests, or the server grows a bespoke /orders/{id}?expand=customer,lines.product parameter that is GraphQL with worse tooling.

The cost is that you have moved query planning to the network edge, and query planning is a thing that can be done badly. Every serious GraphQL production incident is a variant of the same story: a client sent a legal query whose execution plan was quadratic.

Spring for GraphQL 2.0

Spring for GraphQL is a joint project between the Spring and GraphQL Java teams, released as 1.0 in 2022 alongside Spring Boot 2.7.40 The 1.4 line, released in May 2025, moved the baseline to GraphQL Java 24 and was explicitly the last before the Framework 7 generation.41 Version 2.0 went GA on 18 November 2025, built on Spring Framework 7.0 and GraphQL Java 25.42,43 The 2.0 line adopted Jackson 3 as its default with Jackson 2 as a fallback, applied JSpecify annotations across the entire public API, and switched to GraphQL Java 25's official implementation of request cancellation, so that a client disconnect stops further data fetching rather than leaving resolvers running.44,45 Maintenance now runs on the same monthly cadence as Boot itself, with 1.3.x, 1.4.x and 2.0.x lines patched in step with the Boot releases they ship in.46

The most interesting 2.0 feature is unglamorous: schema mapping inspection now understands nullability. A GraphQL schema distinguishes Book from Book!; a Kotlin type or a JSpecify-annotated Java type carries the same information. Spring can now verify that the two agree, for both field return types and field arguments, and report the mismatch at startup rather than as a runtime error.45 This is the sort of feature that seems minor until you have debugged a production NullValueInNonNullableField at 3 a.m.

The controller model

Spring's annotated controllers map handler methods onto schema coordinates: @QueryMapping, @MutationMapping and @SubscriptionMapping for root fields, @SchemaMapping for fields on any type, with the type name inferred from the source argument's class when it matches the schema type.47 Arguments bind through @Argument, and Bean Validation applies to those parameters the same way it applies to a controller method.47 Because these are ordinary Spring beans, method security composes: @PreAuthorize on a field resolver gives you field-level authorisation without a separate policy engine.

@Controller
class OrderGraphQlController {

    private final OrderService orders;

        return orders.stream().collect(toMap(o -> o, o -> byId.get(o.customerId())));
    }

    @SchemaMapping(typeName = "Order", field = "shipment")

    Shipment shipment(Order order) {
        return orders.shipmentOf(order);
    }

    PlaceOrderPayload placeOrder(@Argument @Valid PlaceOrderInput input) {
        return PlaceOrderPayload.of(orders.place(input.toCommand()));
    }

    @SubscriptionMapping
    Flux<Order> orderStatusChanged(@Argument String id) {
        return orders.statusStream(id);
    }

    @GraphQlExceptionHandler
    GraphQLError handle(OrderNotFound ex) {
        return GraphQLError.newError()
                .errorType(ErrorType.NOT_FOUND)
                .message("No order with id %s".formatted(ex.id()))

The N+1 problem is the whole game

Given { orders { customer { name } } } and a naive per-parent resolver, a page of 50 orders issues one query for orders and 50 for customers. This is not a GraphQL defect; it is the direct consequence of resolving a graph field-by-field. The remedy is batching: an org.dataloader.DataLoader defers individual loads so they can be issued together, and Spring exposes a BatchLoaderRegistry bean that registers each batch-loading function as a DataLoader in the per-request DataLoaderRegistry.48,47 When you register by type pair, the loader's name is derived automatically and @SchemaMapping methods can locate and inject a DataLoader<T> argument by generic type.48

@BatchMapping is the ergonomic form: declare a method taking a List of parents and returning a Map from parent to value, and the registration is done for you. Two properties of the DataLoader deserve attention. Its cache is scoped to a single request, so batching cannot leak entities across users. And its dispatch is tied to the execution's field-resolution phases, which means a batch function that blocks synchronously inside a resolver can defeat the entire mechanism — return a CompletableFuture or a reactive type and let the engine dispatch.

The operational surface you must add

A GraphQL endpoint without limits is an open invitation. Four controls are not optional in production:

  • Query depth and complexity limits. GraphQL Java provides MaxQueryDepthInstrumentation and MaxQueryComplexityInstrumentation; register them as Instrumentation beans. Without them, a recursive schema relationship lets a 200-byte query request a million rows.
  • Persisted queries. For first-party clients, ship a query allow-list keyed by hash. This converts an arbitrary-query endpoint into a fixed-operation endpoint while keeping the client-shaped-response benefit.
  • Field-level authorisation. Authorising the request tells you nothing about whether this user may traverse order.customer.taxId. Resolve authorisation where the field is resolved.
  • Per-field observability. Aggregate request latency hides the one resolver that is doing a table scan. Instrument at the data-fetcher level.

06 gRPC: typed calls, and the discipline they require

gRPC is the answer to a narrower question than the others: how do I make a strongly-typed, low-overhead call between services I control? It is a poor fit for public APIs and browser clients, and an excellent fit for east–west traffic inside a cluster, for polyglot fleets, and for anything involving streams.

Two design decisions define it. Interface definition lives in a .proto file compiled to native stubs in each language, with fields identified by number rather than name and with explicit reserved declarations preventing accidental reuse of retired tags.14 And the transport is HTTP/2, so every call is a stream multiplexed onto one connection, with header compression and no head-of-line blocking at the HTTP layer.50 The result is that the marginal cost of an additional concurrent call is dramatically lower than an HTTP/1.1 connection pool — and that a badly behaved stream can starve its neighbours on the same connection, a failure mode that surprises teams migrating from REST.

The Spring story, and its recent consolidation

gRPC support in Spring was community-owned for years. The grpc-spring family of starters — net.devh, later grpc-ecosystem/grpc-spring — provided @GrpcService and @GrpcClient annotations, actuator health indicators and discovery-client integration well before Spring shipped anything official.51 Spring gRPC became the official project, with a core library for using gRPC with dependency injection and a Boot starter providing autoconfiguration and configuration properties.52 The project then split the coarse spring-grpc-spring-boot-starter into fine-grained spring-grpc-client, spring-grpc-server and spring-grpc-server-web starters, and introduced @EnableGrpcClients with nested @GrpcClient declarations that can enumerate stub types explicitly or scan a base package for them.53

The plan had been to move that autoconfiguration into Spring Boot 4.0. It slipped: Spring gRPC 1.0 released against Boot 4.0 as a dependent project instead, with the merge deferred to an early Boot 4.1 milestone.54 That merge landed. Spring Boot 4.1, released 10 June 2026, ships spring-boot-grpc-server, spring-boot-grpc-client and spring-boot-grpc-test modules with corresponding starters, backed by Spring gRPC 1.1.0 and grpc-java 1.80.0.6,55,8 The modules had been available to early adopters since the 4.1.0-M3 milestone, ahead of their documentation.56 You can run a standalone Netty-backed server or use Servlet integration to expose gRPC over HTTP/2 on the same port as your REST endpoints — which matters a great deal in environments where opening a second port means a conversation with the platform team.6,55

The 4.1 release also added @GrpcAdvice for centralised exception handling, an auto-configured reflection service so that grpcurl and similar tools can discover services at runtime, a health indicator bridged into Boot's health model, SSL bundle support for both server and client channels, Spring Security integration for both Netty and Servlet modes, and an ObservationGrpcServerInterceptor wired into the Micrometer observation model.8,55,57

InventoryGrpcService.javaJava
@GrpcService
class InventoryGrpcService extends InventoryGrpc.InventoryImplBase {

    private final StockRepository stock;

    InventoryGrpcService(StockRepository stock) {
        this.stock = stock;
    }

    @Override
    public void getStock(GetStockRequest request, StreamObserver<StockLevel> observer) {
        stock.find(request.getSku(), request.getWarehouse())
             .ifPresentOrElse(
                 level -> { observer.onNext(toProto(level)); observer.onCompleted(); },
                 () -> observer.onError(Status.NOT_FOUND
                         .withDescription("unknown sku " + request.getSku())
                         .asRuntimeException()));
    }

    @Override
    public void watchStock(WatchStockRequest request, StreamObserver<StockLevel> observer) {
        // Honour cancellation: a client that walks away must not leave a producer running.
        ServerCallStreamObserver<StockLevel> downstream =
                (ServerCallStreamObserver<StockLevel>) observer;
        Disposable subscription = stock.stream(request.getSkusList())
                .map(this::toProto)
                .subscribe(observer::onNext, observer::onError, observer::onCompleted);
        downstream.setOnCancelHandler(subscription::dispose);
    }
}

The disciplines that are not optional

gRPC punishes casual use in ways REST does not, because the framework will happily let you build something that works in staging and collapses under load.

  • Set a deadline on every call. gRPC deadlines propagate: a service that receives a call with 300 ms remaining and makes a downstream call inherits that budget. A call with no deadline has an infinite one, and infinite deadlines are how a slow dependency turns into an exhausted thread pool three services away.
  • Treat field numbers as permanent. Removing a field without reserved lets a future developer reuse the tag, at which point old clients silently deserialise a string into an enum. The schema is a database migration with worse error messages.
  • Map errors deliberately. The status code space is small and its semantics are specified: NOT_FOUND, ABORTED and FAILED_PRECONDITION mean different things to a retrying client. Use @GrpcAdvice to make the mapping a single reviewable artifact instead of scattered onError calls.
  • Handle cancellation on streams. A server-streaming RPC whose client disconnects will keep producing unless you register a cancel handler. This is the gRPC equivalent of a leaked subscription, and it is the most common cause of gRPC services that degrade over days rather than seconds.
  • Do not expose it to browsers directly. Browsers cannot speak gRPC's framing without gRPC-Web and a proxy. If a browser is the client, put REST or GraphQL at the edge and use gRPC behind it.

When gRPC is the wrong answer

If the caller and callee are deployed together and versioned together, the protocol buffer contract is ceremony without benefit. If the consumer is a third party you cannot coordinate with, the code-generation requirement becomes a support burden. And if what you actually want is decoupling in time rather than efficiency in space, gRPC gives you the opposite: it makes the synchronous call cheaper, which encourages more of them, which is how a service mesh turns into a distributed monolith with excellent p50 latency and catastrophic tail behaviour.

07 Messaging: the only style that decouples in time

Everything so far has assumed the callee is available. Messaging is what you use when that assumption is unacceptable — when the consumer may be down for maintenance, when the producer must not be slowed by the consumer's database, when three teams need the same event and you refuse to maintain three outbound calls. In exchange you give up the stack trace, the immediate answer, and the illusion that "it worked" is a binary knowable at request time.

Spring's messaging story has three layers that are easy to confuse. At the bottom is org.springframework.messaging: Message<T> with a payload and headers, MessageChannel, MessageHandler. Above it sit the broker-specific projects — Spring for Apache Kafka, Spring AMQP, Spring JMS, Spring for Apache Pulsar — each providing a template for sending and an annotation-driven listener container for receiving. Alongside them sits Spring Integration, which is not a broker client at all but an implementation of the EIP catalogue that composes those clients into flows. And beside that is Spring Cloud Stream, which hides the broker behind a binder so that a java.util.function.Function bean becomes a stream processor.

Spring Integration: the pattern language as code

Spring Integration 7.0.0 shipped on 19 November 2025.62 The release is a structural cleanup as much as a feature drop: all modules moved to a standard package layout with components sorted into input or output packages by purpose, the message-store column MESSAGE_BYTES was renamed to MESSAGE_CONTENT because serialisation is not always a byte array, the ScatterGatherHandler gained full async support emitting a Mono for reply processing, and a DistributedLock abstraction arrived.62 The Java DSL, which was a separate project until it merged into core in 5.0, is now the default way to express flows.63,64,65 The 7.1 line continues the tidying: TestUtils.getPropertyValue() moved to generic type inference, and the MQTT v5 adapters had their MessageConverter direction corrected after years of inverted toMessage/fromMessage usage.66

The DSL's value is that it names patterns. A flow reads as a sequence of EIP nouns, and IntegrationFlowBuilder wires the endpoints implicitly through DirectChannel instances unless you say otherwise — while still allowing you to send a message directly to any component whose input channel you have named.64

@Configuration
class SettlementFlow {

    @Bean
    IntegrationFlow settlementIngest(SettlementValidator validator,
                                     SettlementRepository repository) {
        return IntegrationFlow
                // Inbound channel adapter: poll a landing directory for partner files.
                .from(Files.inboundAdapter(new File("/var/spool/settlement"))
                                .patternFilter("*.csv")
                                .preventDuplicates(true),
                      poller -> poller.poller(p -> p.fixedDelay(5_000).maxMessagesPerPoll(4)))
                // Enricher: attach provenance before anything downstream can lose it.
                .enrichHeaders(h -> h.headerExpression("sourceFile", "payload.name")
                                     .header("ingestedAt", Instant.now()))
                // Splitter: one message per line, sequence headers applied automatically.
                .split(Files.splitter().charset(StandardCharsets.UTF_8))
                // Filter: drop the header row rather than teaching every consumer about it.
                .filter(String.class, line -> !line.startsWith("mandate_id,"))
                // Transformer: text to domain object.
                .transform(String.class, SettlementLine::parse)
                // Router: content-based dispatch, the branch made explicit.
                .<SettlementLine, Boolean>route(validator::isValid,
                        mapping -> mapping
                                .subFlowMapping(true, ok -> ok
                                        .handle(repository::save)
                                        .channel("settlement.accepted"))
                                .subFlowMapping(false, bad -> bad
                                        .handle(Files.outboundAdapter("/var/spool/rejected"))))
                .get();
    }

    // Aggregator: re-form per-file batches so downstream sees one event per file.
    @Bean
    IntegrationFlow settlementSummary(MessageChannel accepted) {
        return IntegrationFlow.from("settlement.accepted")
                .aggregate(a -> a.correlationExpression("headers['sourceFile']")
                                 .releaseExpression("size() == headers['sequenceSize']")
                                 .expireGroupsUponCompletion(true)
                                 .groupTimeout(60_000)
                                 .sendPartialResultOnExpiry(true)
                                 .messageStore(new SimpleMessageStore()))
                .transform(SettlementBatch::summarise)
                .handle(Kafka.outboundChannelAdapter(kafkaTemplate())
                                .topic("settlement.batches"))
                .get();
    }
}

The most consequential line in that configuration is the one you cannot see: the channel type between each pair of endpoints. A DirectChannel invokes the handler on the sender's thread, so the whole flow shares one transaction and one stack trace and is not actually asynchronous. A QueueChannel hands off to a polling consumer, which ends the transaction at the queue — and an in-memory queue discards its contents on crash unless you supply a persistent MessageStore. Teams adopt Spring Integration for asynchrony, get DirectChannel by default, and then discover during an incident that their "async" pipeline was synchronous all along. Read your channels.

The aggregator deserves the same scrutiny. Correlation strategy, release strategy, group timeout, expiry behaviour and message-store choice are five independent decisions, and the defaults are chosen for demos rather than for a service that must not lose a partial batch across a restart. If groups must survive redeployment, the store must be JDBC, MongoDB or Redis-backed, not SimpleMessageStore.

Kafka: the log as integration substrate

Spring for Apache Kafka 4.0 went GA in November 2025 after an eight-month cycle, integrated into Boot 4.0.67 The first 4.0 milestone had already migrated every org.springframework.lang nullability annotation to JSpecify, a change that rippled through the whole portfolio.68 The 4.x line tracks a substantially changed broker: ZooKeeper support is gone because Apache Kafka 4.0 removed it in favour of KRaft, the EmbeddedKafkaBroker test utility now speaks KRaft only, and the next-generation consumer rebalance protocol from KIP-848 is supported.69 Jackson 3 support was added across serialisation and messaging components with automatic detection, and — the change with the widest blast radius — the spring-retry dependency was replaced by Spring Framework 7's core retry support, a breaking change requiring configuration updates.70

Kafka 4.0 also introduced queue semantics through KIP-932 share groups, and Spring for Apache Kafka supports them.67 The 4.1 line, released 9 June 2026 alongside Boot 4.1, extends this: ShareAcknowledgment gained renew(), exposing Kafka's AcknowledgeType.RENEW from KIP-1222 so a consumer whose processing exceeds group.share.record.lock.duration.ms can extend the acquisition lock without completing the record.71,72 @KafkaListener also gained an ackMode attribute so individual listeners can override the container factory's acknowledgment mode without a separate factory bean, and the default sameIntervalTopicReuseStrategy changed from MULTIPLE_TOPICS to SINGLE_TOPIC to align with @RetryableTopic.72 The 4.1 GA also shipped fixes for a cluster of CVEs in header handling — an unbounded delegate cache keyed on a user-controlled selector header, forged retry-topic headers subverting retry routing, and overly broad trusted-package matching in header mappers — which is a useful reminder that message headers are attacker-influenced input.73

OrderEventsListener.javaJava
@Component
class OrderEventsListener {

    private final ProcessedEvents processed;
    private final FulfilmentService fulfilment;

    OrderEventsListener(ProcessedEvents processed, FulfilmentService fulfilment) {
        this.processed = processed;
        this.fulfilment = fulfilment;
    }

    // Non-blocking retries: failures are republished to timed retry topics,
    // then to a dead-letter topic, instead of stalling the partition.
    @RetryableTopic(attempts = "4",
                    backoff = @Backoff(delay = 1_000, multiplier = 3.0),
                    dltTopicSuffix = "-dlt",
                    exclude = { PermanentValidationException.class })
    @KafkaListener(topics = "orders.placed", groupId = "fulfilment",
                   concurrency = "3", ackMode = "RECORD")
    void onOrderPlaced(@Payload OrderPlaced event,
                       @Header(KafkaHeaders.RECEIVED_KEY) String key,
                       @Header(KafkaHeaders.OFFSET) long offset) {

        // At-least-once delivery means this method WILL be called twice at some point.
        if (!processed.claim(event.eventId())) {
            return;                                   // idempotence, enforced by a unique index
        }
        fulfilment.begin(event);
    }

    @DltHandler
    void dead(OrderPlaced event,
              @Header(KafkaHeaders.EXCEPTION_MESSAGE) String reason) {
        // The DLT is an operational queue, not a bin. Something has to read it.
        fulfilment.quarantine(event, reason);
    }
}

@RetryableTopic is the single most useful thing in the project for people who have been burned. Blocking retry inside a listener stalls the partition: while you sleep and retry, every subsequent record behind that offset waits. Non-blocking retry republishes the failed record to a timed retry topic and moves on, then to a dead-letter topic when the attempt budget is exhausted.72 It trades ordering for liveness, which is the right trade for most workloads and exactly the wrong trade for a few — know which one you have.

AMQP: routing as a first-class concern

Spring AMQP 4.0.0 shipped 19 November 2025, adding a spring-rabbitmq-client module for the AMQP 1.0 protocol with RabbitMQ and migrating to Spring's core retry support.74 The mental model is different from Kafka in a way that matters: RabbitMQ routes, Kafka logs. An exchange with bindings performs content-based routing at the broker, so a consumer subscribes to a semantic subset rather than filtering client-side. Kafka gives you replay, retention and consumer-group offset control; Rabbit gives you routing topologies, per-message TTL, priority queues, and delayed delivery. Choosing between them on throughput benchmarks misses the point almost entirely.

Spring Cloud Stream builds on Boot and uses Spring Integration for broker connectivity, adding the concepts of persistent publish-subscribe semantics, consumer groups and partitions across vendors.77 Since 3.x the recommended programming model is functional: beans of type Supplier, Function or Consumer are treated as message sources and handlers, with input and output bindings generated by the <function-name>-<in|out>-<index> convention.78,79 The older @EnableBinding and @StreamListener annotations are gone.

The outbox, and why dual writes keep coming back

The most common correctness bug in event-driven Spring applications is the dual write: save an entity, then publish an event. Four outcomes exist and two of them are wrong. If the publish fails after the commit, the event is lost. If the publish succeeds and the transaction later rolls back, downstream consumers act on something that never happened.80

Spring Modulith's event publication registry implements the transactional outbox directly against Spring's own event mechanism. On publication it identifies the transactional event listeners that will receive the event and writes a row per listener into an event publication log inside the original business transaction; a listener is marked complete only when it succeeds, so a failed broker interaction leaves the entry in place for later resubmission.81,82 An EventPublicationRepository SPI has implementations for JPA, JDBC and MongoDB.81 Marking an event type @Externalized with a routing target and key is enough to have it published to Kafka, RabbitMQ or another supported broker.82,83

OrderPlacedExternalization.javaJava
// 1. Mark the domain event for externalization and name its routing target.
@Externalized("orders.placed::#{#this.orderId()}")   // topic :: routing key
record OrderPlaced(String orderId, String customerId, long totalMinor) { }

// 2. Publish it as an ordinary application event inside the business transaction.
@Service
class OrderService {

    private final OrderRepository repository;
    private final ApplicationEventPublisher events;

    OrderService(OrderRepository repository, ApplicationEventPublisher events) {
        this.repository = repository;
        this.events = events;
    }

    @Transactional
    public Order place(PlaceOrder command) {
        Order order = repository.save(Order.from(command));
        events.publishEvent(new OrderPlaced(order.id(), order.customerId(), order.totalMinor()));
        return order;                 // one commit: the row and the publication log entry
    }
}
application.yamlYAML
spring:
  modulith:
    events:
      externalization:
        enabled: true

      jdbc:

      republish-outstanding-events-on-restart: true

Because externalization runs as a transactional event listener, multiple threads can interact with the broker simultaneously, and resubmissions can overtake later events; setting serialize-externalization to true forces one interaction at a time.81 Even then, ordering across resubmissions is not guaranteed — if strict ordering is a requirement, change data capture with Debezium reading the transaction log is the more honest tool.84

Delivery semantics, stated plainly

At-most-once loses messages. At-least-once duplicates them. Exactly-once is a property of an end-to-end system, not of a broker, and it is achieved by making at-least-once delivery meet an idempotent consumer. There is no configuration flag for this. The mechanism is a deduplication key with a uniqueness constraint, claimed in the same transaction as the side effect.

processed_events.sqlSQL
-- The cheapest idempotency mechanism that actually works: let the database say no.
CREATE TABLE processed_event (
    event_id     UUID        NOT NULL,
    consumer     VARCHAR(64) NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (event_id, consumer)
);

-- Claim inside the same transaction as the side effect.
-- If the insert conflicts, this delivery is a duplicate and the handler returns.
INSERT INTO processed_event (event_id, consumer)
VALUES (?, ?)
ON CONFLICT DO NOTHING;

Everything else — consumer groups, acknowledgment modes, transaction managers — is about narrowing the duplicate window. The unique index is what makes duplication harmless. Design for it from the first event you publish, because retrofitting idempotence onto a consumer that has been running for a year means reconciling the damage first.

08 Batch: the integration style that never left

Batch processing is unfashionable and irreplaceable. Nightly reconciliation, regulatory extracts, month-end close, bulk imports from partners who will send you a fixed-width file until the heat death of the universe: these are integration problems, and they have properties no request/response protocol handles well. The work is windowed rather than continuous, the failure unit is a chunk rather than a request, and the operational requirement is not low latency but exact, restartable, auditable completion.

Spring Batch 6.0 went GA on 19 November 2025, built on Spring Framework 7.0 and delivered through Spring Boot 4.0, with Spring Data 4.0, Spring Integration 7.0, Spring AMQP 4.0 and Spring Kafka 4.0 as its dependency baseline.85,86,87 The programming model it refined predates and outlasted the JSR-352 standardisation attempt, and its operational semantics are documented in depth outside the reference manual.88,89 It is the most substantial release the project has had in years, and most of the substance is in the execution engine rather than the API surface.

The chunk is the transaction

Chunk-oriented processing reads items one at a time, accumulates them into a chunk, and writes the whole chunk inside a transaction boundary; when the number of items read equals the commit interval, the ItemWriter writes and the transaction commits.18 That single sentence contains the entire operational model. The commit interval is your failure granularity: a crash rolls back at most one chunk, and a restart resumes from the last committed one because the JobRepository persisted the step execution context in the same transaction.

Spring Batch 6 re-implemented this model from scratch. The previous implementation suffered from inadequate transaction synchronisation, complex state management and concurrency defects; the new ChunkOrientedStep class replaces the ChunkOrientedTasklet and TaskletStep pair and had been available experimentally since 5.1.86,90,91 The infrastructure was simplified at the same time: JobRepository now extends JobExplorer and JobOperator extends JobLauncher, so the separate beans are no longer required, and the JobRegistry registers jobs automatically.86 APIs across the project carry JSpecify annotations.86

SettlementJobConfig.javaJava
@Configuration
class SettlementJobConfig {

    @Bean
    Job settlementJob(JobRepository jobRepository, Step loadStep, Step reconcileStep) {
        return new JobBuilder("settlementJob", jobRepository)
                .incrementer(new RunIdIncrementer())
                .start(loadStep)
                .next(reconcileStep)
                .build();
    }

    @Bean
    Step loadStep(JobRepository jobRepository,
                  PlatformTransactionManager tx,
                  ItemReader<RawSettlement> reader,
                  ItemProcessor<RawSettlement, LedgerEntry> processor,
                  ItemWriter<LedgerEntry> writer) {

        return new StepBuilder("loadStep", jobRepository)
                .<RawSettlement, LedgerEntry>chunk(500, tx)   // commit interval
                .reader(reader)
                .processor(processor)
                .writer(writer)
                .faultTolerant()
                .skip(MalformedRecordException.class)
                .skipLimit(100)          // a budget, not an amnesty
                .retry(TransientDataAccessException.class)
                .retryLimit(3)
                .listener(new SkipAuditListener())
                .build();
    }

    // A restartable reader: position is saved in the step's execution context.
    @Bean
    @StepScope
    FlatFileItemReader<RawSettlement> reader(
            @Value("#{jobParameters['input']}") Resource input) {
        return new FlatFileItemReaderBuilder<RawSettlement>()
                .name("settlementReader")     // the name is what makes state restartable
                .resource(input)
                .linesToSkip(1)
                .delimited().names("mandateId", "amountMinor", "currency", "valueDate")
                .targetType(RawSettlement.class)
                .build();
    }
}

Three details in that configuration are load-bearing. The reader's name is what makes its position restartable, because the execution context key is derived from it — two unnamed readers in one step is a silent restart bug. skipLimit is a budget rather than an amnesty: unbounded skipping turns a data-quality incident into a silent partial run. And @StepScope with a #{jobParameters['input']} expression is how late binding works; without it the resource is resolved once at context startup and every run reads the same file.

Scaling, in the order you should attempt it

Spring Batch offers a ladder of parallelism, and the discipline is to climb only as far as the measured bottleneck requires. Spring Batch 6 added two rungs. Local chunking processes chunks in parallel within one JVM using multiple threads without requiring partitioning: a bounded internal queue sits between a producer thread and consumer threads, items enter the queue as they become ready, and the producer pauses while a chunk is written before resuming.86,91 This replaces the SEDA-style BlockingQueueItemReader/Writer approach introduced in 5.2 with a simpler producer–consumer model, and 6.0 additionally supports SEDA-style processing at scale using Spring Integration message channels.86,92 Remote step execution, also new, dispatches whole steps to remote machines through the RemoteStep class, again using Spring Integration channels for communication.9

Above the single-JVM rungs sit the two distributed patterns, and they are frequently confused. In remote chunking the manager does all the reading and sends items over messaging to workers that process and write; because the actual data crosses the wire it is I/O intensive, and it only pays off when processing is materially more expensive than reading. In remote partitioning the manager sends partition metadata only — an ID range, a file name — and each worker performs its own I/O; workers are fully defined Spring Batch steps and therefore need JobRepository access.9,93 Spring Batch Integration supplies a MessageChannelPartitionHandler that abstracts the transport, so the same configuration works over JMS, AMQP or Kafka.94

RemotePartitionConfig.javaJava
@Configuration
class RemotePartitionConfig {

    // Manager: computes partitions and sends *metadata* over a message channel.
    @Bean
    Step managerStep(JobRepository jobRepository,
                     PartitionHandler partitionHandler,
                     Step workerStep) {
        return new StepBuilder("managerStep", jobRepository)
                .partitioner("workerStep", new ColumnRangePartitioner("id"))
                .partitionHandler(partitionHandler)
                .build();
    }

    @Bean
    MessageChannelPartitionHandler partitionHandler(MessagingTemplate template,
                                                    JobRepository jobRepository) {
        MessageChannelPartitionHandler handler = new MessageChannelPartitionHandler();
        handler.setStepName("workerStep");
        handler.setGridSize(12);
        handler.setMessagingOperations(template);
        handler.setJobRepository(jobRepository);   // poll the repository for completion
        return handler;
    }

    // Worker: an ordinary chunk step that reads only its own slice.
    @Bean
    @StepScope
    JdbcPagingItemReader<RawSettlement> partitionedReader(
            DataSource dataSource,
            @Value("#{stepExecutionContext['minId']}") Long minId,
            @Value("#{stepExecutionContext['maxId']}") Long maxId) {
        return new JdbcPagingItemReaderBuilder<RawSettlement>()
                .name("partitionedReader")
                .dataSource(dataSource)
                .selectClause("SELECT id, mandate_id, amount_minor, currency")
                .fromClause("FROM raw_settlement")
                .whereClause("WHERE id BETWEEN :minId AND :maxId")
                .parameterValues(Map.of("minId", minId, "maxId", maxId))
                .sortKeys(Map.of("id", Order.ASCENDING))
                .pageSize(1000)
                .rowMapper(new RawSettlementRowMapper())
                .build();
    }
}

Batch as an endpoint in a message flow

The integration between Spring Batch and Spring Integration runs in both directions. A job can be launched by a message through JobLaunchingMessageHandler, with the JobExecution returned as a reply; and a step can use Spring Integration channels as its remoting fabric.94 This is how you build the pattern most enterprises actually need: an event announces that a file has landed, a job runs against it, and the job's completion is itself an event that downstream systems consume.

JobLaunchFlow.javaJava
// Batch as an endpoint inside a message flow: a broker event launches the job,
// and the JobExecution comes back as a reply message.
@Configuration
class JobLaunchFlow {

    @Bean
    IntegrationFlow launchOnFileArrival(JobOperator jobOperator, Job settlementJob) {
        return IntegrationFlow
                .from(Kafka.messageDrivenChannelAdapter(consumerFactory(), "settlement.files"))
                .transform(String.class, path -> new JobLaunchRequest(
                        settlementJob,
                        new JobParametersBuilder()
                                .addString("input", path)
                                .addLocalDateTime("requestedAt", LocalDateTime.now())
                                .toJobParameters()))
                .handle(new JobLaunchingMessageHandler(jobOperator))
                .transform(JobExecution.class, execution ->
                        Map.of("jobId", execution.getId(),
                               "status", execution.getStatus().name()))
                .handle(Kafka.outboundChannelAdapter(kafkaTemplate()).topic("settlement.jobs"))
                .get();
    }
}

Spring Batch 6 also replaced the long-serving CommandLineJobRunner, which had accumulated problems around static initialisation and non-standard option handling, with a new command-line operator, and added the ability to recover failed job executions.86 For containerised deployments the practical launcher is usually a Boot application invoked as a Kubernetes Job, with job parameters supplied as arguments — but the improved runner matters for the large installed base still scheduling through Control-M, Autosys or cron.

The batch failure modes worth naming

  • Non-restartable readers. A cursor-based reader that cannot be repositioned, or a queue-based reader with no durable position, converts restart into duplication. Verify restart behaviour in a test that kills the job mid-run.
  • Commit interval chosen by vibes. Too small and you pay a transaction per handful of rows; too large and a failure at 95% repeats hours of work and holds locks long enough to affect online traffic.
  • Job parameter identity. Spring Batch identifies a job instance by its identifying parameters. A job whose only parameter is a timestamp can never be restarted, only re-run — which is sometimes what you want and usually an accident.
  • Partition skew. Range partitioning over a monotonically increasing key concentrates recent, denser data into the last partition. Measure the distribution before choosing the partitioner.
  • Silent skip accumulation. A SkipListener that only logs produces runs that succeed while quietly discarding thousands of records. Skips belong on a dashboard with a threshold alert.

09 The concerns that cut across all six

Observability is one model, not six

The portfolio has converged on Micrometer's Observation API as the single instrumentation seam: one call site produces metrics, traces and context propagation depending on the registered handlers. Boot 4.0 moved to Micrometer 1.16 and Micrometer Tracing 1.6 and added a spring-boot-starter-opentelemetry;1 4.1 delivered the most comprehensive OpenTelemetry update since the integration was introduced, touching SDK lifecycle, exporter configuration, sampling, limits and environment-variable interoperability, and fixed context propagation across @Async boundaries.55,8 Redis autoconfiguration switched to MicrometerTracing rather than the older latency recorder precisely because the former operates on the Observation API and yields both metrics and spans.1

The practical payoff is a trace that survives protocol changes: an HTTP request enters, a gRPC interceptor continues the trace, a Kafka producer writes trace context into record headers, a consumer picks it up, and a batch job launched from that consumer reports under the same trace id. Every hop must propagate rather than re-create context, which is why the observation-enabled flags on Kafka listeners and templates and the ObservationPropagationChannelInterceptor on Spring Integration channels are not decorative.

ObservabilityConfig.javaJava
@Configuration
class ObservabilityConfig {

    // One registry; protocol-specific instrumentation registers against it.
    @Bean

            @Value("${spring.application.name}") String app) {
        return registry -> registry.observationConfig()
                .observationFilter(context -> context.addLowCardinalityKeyValue(
                        KeyValue.of("service.name", app)));
    }

    // Spring Integration flows become spans when the channel carries the context.
    @Bean
    IntegrationFlow observedFlow() {
        return IntegrationFlow.from("orders.inbound")
                .channel(c -> c.direct().interceptor(new ObservationPropagationChannelInterceptor(
                        observationRegistry())))
                .get();
    }
}

Security does not compose automatically

Each protocol has its own authentication surface, and the mistake is assuming a filter chain covers all of them. Spring Security 7.0 shipped with Boot 4.0 and provides OAuth 2.0 support for HTTP service groups by detecting @ClientRegistrationId on @HttpExchange methods.30 Boot 4.1 added Spring Security integration for gRPC in both Netty and Servlet modes, and Spring gRPC provides an autoconfigured OAuth2 client for gRPC channels that works like any other Boot OAuth2 client.55,61 SOAP's security lives at the message layer through WS-Security rather than in a servlet filter.36 GraphQL needs field-level authorisation because a single authorised request can traverse into data the caller must not see. And messaging has no request context at all — identity must be carried in headers and re-established by the consumer, which is the step teams most often skip.

Boot 4.1 also added SSRF mitigation for HTTP clients via an InetAddressFilter, which is a direct answer to the class of vulnerability where a URL supplied by a caller becomes an outbound request from inside your network.5,8 If any part of your integration layer fetches user-supplied URLs, this is worth enabling deliberately rather than inheriting.

Testing strategy per style

The portfolio now supplies a first-class test client for every style, and the strategy should mirror the contract's shape. For REST, RestTestClient exercises status, media type and problem-detail body.34 For SOAP, the Spring-WS test module drives real XML payloads against real endpoints. For GraphQL, GraphQlTester executes documents and asserts on JSON paths, and schema mapping inspection catches resolver/schema drift at startup.45 For gRPC, in-process transports and @AutoConfigureTestGrpcTransport remove the network without removing the protocol.61,60 For Spring Integration, the test framework's @SpringIntegrationTest and MockIntegration factory let you substitute endpoints inside a flow.63 For batch, the essential test is not a happy-path run but a killed run followed by a restart.

Above all of them sits Testcontainers, and the rule of thumb is simple: mock the protocol boundary in unit tests, but run the real broker, the real database and the real schema in at least one integration test per flow. Every serious messaging bug lives in the gap between how you think a broker behaves and how it behaves.

Anti-patterns

  • The distributed monolith. Synchronous calls everywhere because gRPC made them cheap. Availability multiplies down the chain; a 99.9% dependency five hops deep is a 99.5% service. If two components must both be up for either to work, they are one component with network latency between them.
  • Events as RPC. Publishing CalculateTaxRequest to a topic and waiting for CalculateTaxResponse is a synchronous call with a broker in the middle: you have kept the temporal coupling and added latency, ordering hazards and a second failure domain. Events should describe things that happened, not things you want.
  • The shared canonical model. One schema to which all services conform becomes a change-coordination bottleneck within eighteen months. Prefer consumer-driven contracts and per-consumer projections.
  • Exactly-once as a checkbox. No broker setting substitutes for an idempotent consumer. Teams that believe otherwise discover the truth during their first rebalance under load.
  • Retry without a budget. Retries amplify load precisely when the system is least able to absorb it. Bound attempts, add jitter, and pair retry with a concurrency limit so the retry storm cannot consume the thread pool it is retrying into.
  • Batch as a fallback for a broken stream. A nightly job that "fixes up" what the event pipeline dropped is a permanent tax and a permanent excuse. Reconciliation is legitimate; compensating for known-broken delivery is not.
  • Versioning by branch. Maintaining v1 and v2 of a service as separate deployments doubles the operational surface. Framework 7's mapping versions let one deployment serve both, and the transformation between them lives in one reviewable place.16

One planning note that is easy to miss: Spring Boot follows a twelve-month open-source support window per minor release, after which free patches stop.2 Spring Boot 3.5 received its last free maintenance release in June 2026, and continued support on the 3.x line is commercial.2,95 Because Boot 4.0 kept Java 17 as the minimum while supporting Java 25, most 3.x applications can migrate without a JDK upgrade;2 the real migration cost is elsewhere — Jackson 3, Jakarta EE 11, Hibernate, the removal of Undertow support, and any custom autoconfiguration that leaned on internal Spring APIs.2 Modularisation of the autoconfigure jar is the compensating benefit: fewer classpath checks at startup and smaller uber jars.24

12 What the 2025–26 releases actually tell you

Read the release notes of the last two waves together and a direction emerges. Retry and concurrency limiting moved from an add-on library into the core framework. gRPC autoconfiguration moved from a satellite project into Boot's own modules. API versioning moved from an argument on Stack Overflow into the request-mapping infrastructure. Nullability moved from framework-specific annotations to JSpecify, checked at build time across the portfolio. Observability converged on a single Observation abstraction with OpenTelemetry as a first-class exporter.

The pattern is consolidation of things that every distributed Spring application was already doing badly by hand. That is a mature ecosystem behaving correctly: the framework absorbs the boilerplate once the industry has agreed what the boilerplate should be. It also raises the bar for what counts as an interesting architectural decision. Wiring a gRPC client is no longer interesting. Deciding whether that call should be gRPC at all — whether the two services should be temporally coupled, whether the failure of one should be the failure of the other — is as interesting as it ever was, and no release note will answer it.

The patterns Hohpe and Woolf catalogued in 2003 have outlived three generations of transport technology because they describe the negotiation, not the wire format.10 A splitter is a splitter whether the messages arrive over JMS or a Kafka topic or an HTTP/2 stream. The most durable thing you can do for a system that will outlive its current protocols is to make the pattern visible in the code — so that the next engineer can see the aggregator and ask the right question about its expiry policy, rather than finding a HashMap, a ScheduledExecutorService, and a comment that says // TODO: handle timeout.
