Spring Messaging

JMS, STOMP, WebSockets, RabbitMQ, and Apache Kafka

An expert guide to Spring’s message model, broker ownership, delivery guarantees, listener containers, acknowledgements, transactions, retries, dead-lettering, ordering, schemas, security, and production operations.

Spring Framework 7.0.8 Spring AMQP 4.1.0 Spring for Apache Kafka 4.1.0 Long-form technical article Vancouver references
Abstract. Spring’s core messaging package represents a message as a payload plus headers and routes it through channels and handlers. Protocol integrations adapt that model to different transports and brokers. Jakarta Messaging defines a Java API for queue and topic providers; STOMP supplies frame and destination semantics over WebSocket; Spring AMQP maps messages to RabbitMQ exchanges, routing keys, queues, acknowledgements, and publisher confirms; Spring for Apache Kafka maps them to durable partitioned logs, keys, offsets, consumer groups, and producer transactions. The APIs look deliberately similar—templates, listener annotations, converters, headers, error handlers—but their failure models are not interchangeable. This article develops each stack from the broker’s native semantics outward and shows how to design idempotent consumers, reliable publication, dead-letter workflows, schema evolution, observability, and cross-resource consistency.

Spring Framework 7.0.8 contains the generic messaging abstractions, JMS integration, and STOMP-over-WebSocket support. Spring AMQP 4.1.0 supplies RabbitMQ-oriented AMQP abstractions, while Spring for Apache Kafka 4.1.0 supplies Kafka templates and message-driven listener containers.[1][2][3]

1. Spring’s messaging model

org.springframework.messaging.Message<T> is a generic message representation containing a payload and immutable message headers. MessageChannel defines sending, MessageHandler defines handling, SubscribableChannel dispatches to registered subscribers, and PollableChannel exposes active receive operations. MessagingException is the root Spring exception for messaging failures.[4][5]

Java 
OrderPlaced event =
        new OrderPlaced(
            eventId,
            orderId,
            customerId,
            total,
            Instant.now());

Message<OrderPlaced> message =
        MessageBuilder
            .withPayload(event)
            .setHeader("eventType", "OrderPlaced")
            .setHeader("schemaVersion", 3)
            .setHeader(
                "correlationId",
                correlationId)
            .setHeader(
                MessageHeaders.CONTENT_TYPE,
                MimeTypeUtils.APPLICATION_JSON)
            .build();

boolean accepted =
        outboundChannel.send(
            message,
            2_000);

1.1 Payload and headers

The payload carries application data; headers carry routing, content type, correlation, identity, tracing, delivery, and protocol metadata. Protocol adapters map a subset of Spring headers to native JMS properties, STOMP headers, AMQP properties, or Kafka record headers. Header mapping is not lossless by default: supported types, reserved names, serialization, size limits, and trust rules differ between transports.

Do not serialize arbitrary Java classes as a public contract Prefer explicit JSON, Avro, Protobuf, or another versioned format with a stable event name and schema version. Java-native serialization tightly couples consumers to class names, classpaths, and deserialization trust.

1.2 A channel is not necessarily a broker

An in-process MessageChannel can be synchronous and ephemeral. A broker-backed channel can persist and redeliver. A WebSocket outbound channel targets live sessions. A Kafka topic retains an ordered log by partition. The Spring interface normalizes invocation style, not persistence, fan-out, replay, ordering, or transactional behavior.

2. Delivery guarantees and ownership transfer

At-most-onceA message is delivered zero or one time. Loss is possible, but duplicates are avoided.
At-least-onceA message is retried until acknowledged or recovered. Duplicates are possible and consumers must be idempotent.
Exactly-once scopeA particular broker workflow commits output and progress atomically. External side effects may still duplicate.

Acknowledgement is an ownership boundary. A consumer should acknowledge only after the durable effects it owns are complete. RabbitMQ automatically requeues unacknowledged deliveries when a channel or connection closes, so redelivery is expected. Kafka consumer progress is represented by committed offsets; processing that succeeds before an offset commit can be repeated. JMS transacted sessions similarly roll back message receipt on failure.[6][7][8]

2.1 Idempotent consumer

SQL 
create table processed_message (
    consumer_name varchar(120) not null,
    message_id uuid not null,
    processed_at timestamp not null,
    primary key (consumer_name, message_id)
);
Java 
@Transactional
public void process(OrderPlaced event) {
    int inserted = jdbc.update(
        """
        insert into processed_message (
            consumer_name,
            message_id,
            processed_at
        )
        values (?, ?, ?)
        on conflict do nothing
        """,
        "invoice-projector",
        event.eventId(),
        Timestamp.from(Instant.now()));

    if (inserted == 0) {
        return; // Already applied.
    }

    invoiceProjection.apply(event);
}

The deduplication marker and business projection must commit in the same local transaction. An in-memory set cannot survive restart, and acknowledging before the transaction commits creates loss.

2.2 Poison messages

Infinite redelivery of deterministic conversion or validation failures consumes capacity without making progress. Classify errors into transient and permanent categories, bound retries, preserve diagnostic metadata, and move exhausted messages to a dead-letter destination or explicit quarantine. A dead-letter destination is a recovery queue, not a trash can; it needs ownership, retention, alerts, replay controls, and schema-aware tooling.

3. JMS with Spring

Jakarta Messaging 3.1 defines a common Java API for enterprise messaging providers. A JMS message has standard headers, optional properties, and a body; the API supports point-to-point queues and publish-subscribe topics. Spring’s JMS support manages connection, session, producer, and consumer resources and supplies templates, converters, listener containers, annotations, transactions, and exception translation.[9][10]

3.1 Template and listener configuration

Java 
@Configuration(proxyBeanMethods = false)
@EnableJms
class JmsConfiguration {

    @Bean
    MappingJackson2MessageConverter
            jmsMessageConverter(
                ObjectMapper objectMapper) {

        MappingJackson2MessageConverter converter =
                new MappingJackson2MessageConverter();

        converter.setObjectMapper(objectMapper);
        converter.setTargetType(
                MessageType.TEXT);
        converter.setTypeIdPropertyName(
                "_event_type");

        return converter;
    }

    @Bean
    JmsTemplate jmsTemplate(
            ConnectionFactory connectionFactory,
            MappingJackson2MessageConverter converter) {

        JmsTemplate template =
                new JmsTemplate(connectionFactory);

        template.setMessageConverter(converter);
        template.setExplicitQosEnabled(true);
        template.setTimeToLive(86_400_000);
        return template;
    }

    @Bean
    DefaultJmsListenerContainerFactory
            jmsListenerContainerFactory(
                ConnectionFactory connectionFactory,
                MappingJackson2MessageConverter converter) {

        DefaultJmsListenerContainerFactory factory =
                new DefaultJmsListenerContainerFactory();

        factory.setConnectionFactory(
                connectionFactory);
        factory.setMessageConverter(converter);
        factory.setConcurrency("3-12");
        factory.setSessionTransacted(true);
        return factory;
    }
}

JmsTemplate is Spring’s central JMS core class and manages low-level resources. Spring Framework 7 also provides the fluent JmsClient, built on JmsTemplate, for generic Spring Message conversion and per-operation customization. Annotated @JmsListener methods are backed by listener containers.[10][11]

Java

A transacted JMS listener session makes message receipt and JMS sends performed on that session part of one local JMS transaction. Database work is a separate resource unless XA/JTA coordinates both. If the database commits but JMS acknowledgement fails, the message can be redelivered; duplicate detection is therefore still required. XA supplies unified commit semantics at the cost of distributed transaction coordination and logging overhead.[11]

4. WebSockets

RFC 6455 defines a full-duplex, two-way communication channel over one TCP connection after an HTTP opening handshake. WebSocket frames carry text or binary data but do not define application routing or message semantics; applications either invent a protocol or negotiate a subprotocol such as STOMP.[12][13]

4.1 Raw WebSocket handler

Java 
public final class MetricsWebSocketHandler
        extends TextWebSocketHandler {

    @Override
    protected void handleTextMessage(
            WebSocketSession session,
            TextMessage message)
            throws Exception {

        ClientCommand command =
                decode(message.getPayload());

        ClientReply reply =
                metricsService.execute(command);

        session.sendMessage(
            new TextMessage(encode(reply)));
    }
}

Raw handlers are appropriate for a compact custom protocol, binary streaming, or integration with non-STOMP peers. They also make the application responsible for routing, validation, correlation, subscriptions, acknowledgements, heartbeats, protocol errors, and authorization conventions.[13]

4.2 Operational implications

  • A connection is long-lived and consumes server, proxy, and load-balancer state.
  • Idle timeouts and heartbeats must agree across clients, proxies, and servers.
  • Slow clients require bounded outbound buffers and disconnect policy.
  • Horizontal scaling requires session affinity, shared broker state, or both.
  • Authentication starts at the HTTP handshake, but authorization applies to every application message.

Spring’s guidance recommends WebSocket primarily where low latency combines with high message frequency or volume; ordinary polling or streaming can be simpler for low-rate updates. Restrictive proxies and long-lived connection handling also affect public deployments.[13]

5. STOMP over WebSocket

STOMP is a frame-based messaging protocol with commands such as CONNECT, SEND, SUBSCRIBE, ACK, and DISCONNECT. Frames contain headers, an optional body, and a frame terminator. Spring maps decoded STOMP frames to Spring Message objects and routes them through inbound, broker, and outbound channels.[14][15]

5.1 Message broker configuration

Java 
@Configuration(proxyBeanMethods = false)
@EnableWebSocketMessageBroker
class StompWebSocketConfiguration
        implements WebSocketMessageBrokerConfigurer {

    @Override
    public void registerStompEndpoints(
            StompEndpointRegistry registry) {

        registry.addEndpoint("/ws")
            .setAllowedOriginPatterns(
                "https://app.example.net")
            .withSockJS();
    }

    @Override
    public void configureMessageBroker(
            MessageBrokerRegistry registry) {

        registry.setApplicationDestinationPrefixes(
                "/app");
        registry.setUserDestinationPrefix(
                "/user");

        registry.enableSimpleBroker(
                "/topic",
                "/queue");
    }

    @Override
    public void configureWebSocketTransport(
            WebSocketTransportRegistration registry) {

        registry
            .setMessageSizeLimit(128 * 1024)
            .setSendBufferSizeLimit(
                512 * 1024)
            .setSendTimeLimit(15_000);
    }
}

Destinations under the application prefix are routed to @MessageMapping methods; broker destinations are routed to the simple broker or external relay. The in-memory simple broker tracks subscriptions and broadcasts, but supports only a subset of STOMP and is not suitable for clustered broker state, acknowledgements, or receipts. A broker relay connects Spring to a full STOMP broker such as RabbitMQ or ActiveMQ.[15][16]

5.3 User destinations

Java 
notificationTemplate

Spring resolves /user/ destinations into session-unique destinations, preventing collisions between users and supporting one or several sessions per principal. User destinations remain a routing convenience, not an authorization control.[18]

5.4 Authentication and authorization

In the common browser model, authentication occurs during the HTTP handshake and Spring associates the resulting principal with the WebSocket session and subsequent messages. Spring ignores STOMP login and passcode headers by default for WebSocket sessions. Spring Security authorizes message types and destinations through channel interception.[19][20]

Never trust the destination alone A client can construct any STOMP frame. Authorize subscriptions and sends, validate ownership in application handlers, constrain origins, limit message sizes, and reject user-supplied headers that impersonate server identity.

The relay maintains TCP connections to the broker, forwards application broker messages, and relays broker deliveries to connected WebSocket clients. Broker topology, heartbeats, destination cleanup, credentials, reconnect behavior, and cross-node user destinations must be operated explicitly.[16]

6. RabbitMQ with Spring AMQP

RabbitMQ publishers publish to exchanges. Exchanges route messages through bindings to queues or streams. Direct exchanges match routing keys exactly, topic exchanges match patterns, fanout exchanges broadcast to every bound destination, and headers exchanges route by header arguments. Consumers normally receive from queues.[21][22]

6.1 Declarative topology

Java 
@Configuration(proxyBeanMethods = false)
class RabbitTopology {

    static final String EXCHANGE =
            "orders.events.v1";
    static final String QUEUE =
            "billing.order-placed.v1";
    static final String DLX =
            "orders.events.dlx";
    static final String DLQ =
            "billing.order-placed.dlq";

    @Bean
    TopicExchange orderExchange() {
        return ExchangeBuilder
            .topicExchange(EXCHANGE)
            .durable(true)
            .build();
    }

    @Bean
    DirectExchange deadLetterExchange() {
        return ExchangeBuilder
            .directExchange(DLX)
            .durable(true)
            .build();
    }

    @Bean
    Queue billingQueue() {
        return QueueBuilder
            .durable(QUEUE)
            .deadLetterExchange(DLX)
            .deadLetterRoutingKey(DLQ)
            .build();
    }

    @Bean
    Queue billingDeadLetterQueue() {
        return QueueBuilder
            .durable(DLQ)
            .build();
    }

    @Bean
    Binding billingBinding(
            Queue billingQueue,
            TopicExchange orderExchange) {

        return BindingBuilder
            .bind(billingQueue)
            .to(orderExchange)
            .with("order.placed.*");
    }

    @Bean
    Binding deadLetterBinding(
            Queue billingDeadLetterQueue,
            DirectExchange deadLetterExchange) {

        return BindingBuilder
            .bind(billingDeadLetterQueue)
            .to(deadLetterExchange)
            .with(DLQ);
    }
}

Durable topology survives broker restart subject to queue type and broker policy. Durable queues and persistent messages are only part of data safety; publisher confirms, replicated queue types where required, and consumer acknowledgements remain necessary. Dead-lettering can occur after rejection without requeue, expiration, queue-length overflow, or delivery-limit exhaustion for quorum queues.[22][23]

Prefetch bounds the number of unacknowledged deliveries in flight. Higher prefetch can improve throughput but increases memory use and duplicate work after failure. With manual acknowledgements, a connection or channel close requeues unacknowledged deliveries. Consumers must therefore tolerate redelivery.[25]

6.4 Error classification

Spring AMQP wraps listener failures in ListenerExecutionFailedException. By default, a rejected listener delivery is normally requeued unless configured otherwise; defaultRequeueRejected=false rejects without requeue, allowing dead-letter routing. Conversion and other fatal pre-listener failures are classified by ConditionalRejectingErrorHandler to avoid endless redelivery.[26]

Retry topology must be bounded A TTL-based retry queue that dead-letters back to the source can loop forever unless delivery attempts or x-death history are examined. Keep the original message ID and diagnostic headers, and ensure replay tools do not create uncontrolled loops.

7. Apache Kafka with Spring Kafka

Kafka stores records in ordered topic partitions. Records with the same key are normally assigned to the same partition, enabling per-key ordering. Consumer groups divide partitions among consumer instances, so parallelism is bounded by partition count and total ordering exists only within a partition.[27]

7.1 Producer and listener infrastructure

Java 
@Bean
ProducerFactory<String, OrderEvent>
        producerFactory(
            KafkaProperties properties) {

    Map<String, Object> configuration =
            new HashMap<>(
                properties.buildProducerProperties());

    configuration.put(
        ProducerConfig.ACKS_CONFIG,
        "all");
    configuration.put(
        ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG,
        true);

    return new DefaultKafkaProducerFactory<>(
            configuration);
}

@Bean
KafkaTemplate<String, OrderEvent> kafkaTemplate(
        ProducerFactory<String, OrderEvent> factory) {

    return new KafkaTemplate<>(factory);
}

KafkaTemplate wraps a Kafka producer and provides asynchronous send methods returning CompletableFuture<SendResult<K,V>>. When backed by DefaultKafkaProducerFactory, the template is thread-safe. The record key, topic, partition, timestamp, payload, and headers form the native publication contract.[28][29]

7.2 Keyed publication

Java 
CompletableFuture<
        SendResult<String, OrderEvent>> future =
    kafkaTemplate.send(
        "orders.events.v1",
        event.orderId().toString(),
        event);

future.whenComplete((result, failure) -> {
    if (failure != null) {
        publicationMonitor.failed(
            event.eventId(),
            failure);
        return;
    }

    RecordMetadata metadata =
            result.getRecordMetadata();

    publicationMonitor.acknowledged(
        event.eventId(),
        metadata.topic(),
        metadata.partition(),
        metadata.offset());
});

Completion of the send future reports the producer result. Blocking on every send destroys batching and throughput; if synchronous confirmation is required, use a timeout and understand that the caller is now coupled to broker latency. Kafka producer idempotence prevents certain duplicate appends caused by producer retries, but it does not make an application-level command globally idempotent.

Increasing listener concurrency beyond the available assigned partitions does not create useful parallel record consumption for that topic.[27][30]

7.4 Retries and dead-letter topics

Java 
@Bean
DefaultErrorHandler kafkaErrorHandler(
        KafkaTemplate<Object, Object> template) {

    DeadLetterPublishingRecoverer recoverer =
            new DeadLetterPublishingRecoverer(
                template,
                (record, exception) ->
                    new TopicPartition(
                        record.topic() + ".DLT",
                        record.partition()));

    ExponentialBackOffWithMaxRetries backOff =
            new ExponentialBackOffWithMaxRetries(4);

    backOff.setInitialInterval(500);
    backOff.setMultiplier(2.0);
    backOff.setMaxInterval(8_000);

    DefaultErrorHandler handler =
            new DefaultErrorHandler(
                recoverer,
                backOff);

    handler.addNotRetryableExceptions(
        InvalidEventSchemaException.class,
        IllegalArgumentException.class);

    return handler;
}

DefaultErrorHandler can retry records with backoff and invoke a recoverer after exhaustion. DeadLetterPublishingRecoverer publishes failed records to a dead-letter topic, by default retaining the original partition when the target has enough partitions. Deserialization and conversion failures require an error-handling deserializer or equivalent strategy because they can occur before the listener receives a typed value.[31]

7.5 Serialization, conversion, and headers

Kafka serializers and deserializers convert keys and values at the client boundary. Spring’s messaging converter can additionally adapt between ConsumerRecord/ProducerRecord and Spring Message. Kafka headers map to Spring MessageHeaders; JSON header mapping restricts trusted packages by default and should not deserialize arbitrary application classes from untrusted producers.[32][33]

7.6 Transactions and exactly-once processing scope

A transaction-capable producer factory enables KafkaTransactionManager, transactional listener containers, and local KafkaTemplate.executeInTransaction() operations. For a Kafka read-process-write flow, the listener container can start a transaction, include output records and consumed offsets, and commit them together. Spring describes this as exactly-once semantics for the read-process-write sequence; the read and application processing may still execute more than once before a successful commit.[34][35]

Java 
@KafkaListener(
    topics = "orders.events.v1",
    groupId = "fulfillment-router-v1")
public void route(OrderPlaced event) {

    FulfillmentRequested output =
            fulfillmentPlanner.plan(event);

    kafkaTemplate.send(
        "fulfillment.commands.v1",
        event.orderId().toString(),
        output);
}

With a transactional listener container, a successful listener sends output records and offsets in one Kafka transaction; failure aborts the transaction and the input is fetched again. This guarantee does not atomically include an ordinary database, HTTP call, RabbitMQ publish, or email. Spring can synchronize Kafka and database transactions with a defined commit order, but a second commit can still fail after the first has committed, requiring compensation. A transactional outbox is often easier to recover.[34]

9. Cross-cutting messaging patterns

9.1 Transactional outbox

1 Commit domain state and an outbox row in one database transaction.
2 A relay reads committed outbox rows.
3 Publish to JMS, RabbitMQ, or Kafka with the outbox ID as message ID.
4 Mark publication or retain retry state after broker confirmation.
5 Consumers deduplicate by event ID.

The outbox avoids a database-plus-broker dual write without requiring distributed commit. Publication remains at-least-once, so the producer relay and consumers must be idempotent.

Event type and version should be stable machine identifiers. Additive evolution is easier than changing meaning. Preserve unknown fields where intermediaries republish events, and test old producers against new consumers and new producers against supported old consumers.

9.3 Commands versus events

Command
A request for one responsible consumer to perform work; may be rejected.
Event
A fact that has already occurred; any number of independent consumers may react.

Naming every message “event” while expecting one consumer to decide whether it may happen creates ambiguous ownership. Destination topology, retry policy, and response expectations should follow the semantic type.

9.4 Request/reply

JMS, RabbitMQ, STOMP, and Kafka integrations can implement correlation-based request/reply, but synchronous RPC over a broker inherits timeout, duplicate, late-reply, and cancellation complexity. Use it when broker mediation is a real requirement, not as a slower replacement for a direct service call.

10. Security

  • Use TLS and broker authentication; rotate credentials without redeploying message payload schemas.
  • Apply least-privilege permissions to JMS destinations, RabbitMQ virtual hosts/exchanges/queues, and Kafka topics/groups.
  • Authorize STOMP CONNECT, SEND, and SUBSCRIBE frames by message type and destination.
  • Do not trust type headers to select arbitrary classes for deserialization.
  • Limit message and header sizes, decompression ratios, nesting, and batch sizes.
  • Redact credentials, personal data, and payloads from logs and dead-letter diagnostics.

Message-level authorization is required even when the connection is authenticated. A compromised producer credential can send syntactically valid but unauthorized commands, and a broad consumer credential can expose data across tenants.

11. Testing

11.1 Unit tests

Unit-test converters, listener business logic, event compatibility, routing-key construction, partition-key selection, error classification, and deduplication independently of broker infrastructure.

11.2 Real broker integration

  • JMS: selectors, transacted sessions, redelivery flags, durable subscriptions, and provider failover.
  • STOMP: handshake authentication, destination authorization, user destinations, broker relay reconnect, ordering, and slow-client limits.
  • RabbitMQ: exchange bindings, mandatory returns, confirms, requeue/DLQ behavior, prefetch, quorum queues, and broker restart.
  • Kafka: partition assignment, key ordering, offset commits, rebalance, deserialization failures, DLT publication, transaction abort, and replay.

Integration tests should use the actual broker family and production-relevant topology. In-memory substitutes do not reproduce RabbitMQ acknowledgements, Kafka rebalances, STOMP broker relays, or JMS provider transactions.

Spring’s STOMP infrastructure exposes runtime statistics; Spring AMQP and Spring Kafka integrate listener and template metrics and observations. Keep metric dimensions bounded: topic, queue, listener ID, and outcome are useful, while raw message IDs and destinations containing user identifiers create unbounded cardinality.[36][28]

12.1 Capacity relationships

  • RabbitMQ prefetch × consumer count bounds in-flight deliveries and potential duplicate work.
  • Kafka partition count bounds useful consumer-group concurrency.
  • STOMP inbound and outbound executor queues bound application work and slow-client pressure.
  • JMS listener concurrency and provider prefetch jointly determine work in flight.

Tune from measured processing time, message size, downstream capacity, broker latency, and recovery objectives. Increasing concurrency without database, CPU, or partition capacity merely moves the bottleneck.

13. Diagnostics

13.1 RabbitMQ publish succeeds but no consumer receives

Confirm the exchange exists, binding pattern matches the routing key, target queue is declared, mandatory publishing is enabled, return callbacks are observed, and the consumer listens to the expected virtual host and queue.

13.2 Kafka event processed twice

Inspect offset commit timing, listener exceptions, rebalances, transaction aborts, retry handlers, and whether the side effect is idempotent. Duplicate processing is valid under at-least-once behavior even when producer idempotence is enabled.

13.3 JMS database row duplicates after rollback

The database committed independently from the transacted JMS session, then message receipt rolled back. Add durable deduplication or use XA when unified commit is justified.[11]

13.4 STOMP subscription receives nothing

Verify application and broker prefixes, subscription destination, broker relay state, user-destination translation, authorization, message conversion, and outbound executor pressure.

13.5 Message loops forever

Separate transient from permanent exceptions, cap attempts, reject without requeue or recover to DLT, and inspect dead-letter history. Conversion failures often occur before listener code can catch them.

14. Expert practices

14.1 Design from native broker semantics

Start with JMS destination and session behavior, RabbitMQ exchange/queue ownership, Kafka partitions and retention, or STOMP session routing. Add Spring abstractions after the failure model is understood.

14.2 Give every business message a stable ID

Broker-assigned IDs are useful diagnostics but may change when republishing. Carry an application event ID through retries, DLTs, and bridges.

14.3 Acknowledge after durable effects

Ack or commit progress only after the consumer-owned transaction commits. Make duplicate application safe before optimizing acknowledgement timing.

14.4 Avoid database-plus-broker dual writes

Use an outbox or CDC unless XA is a deliberate operational choice. Broker transactions do not automatically include unrelated resources.

14.5 Choose routing and partition keys from invariants

Rabbit routing keys determine topology; Kafka keys determine partition locality and ordering. Changing key strategy changes scale and consistency behavior.

14.6 Bound and classify retries

Retry transient infrastructure failures with backoff and jitter. Route deterministic schema, authorization, and validation failures directly to recovery.

14.7 Treat schemas as deployed contracts

Version message types, test compatibility, retain consumers during migration, and avoid class-name-based polymorphism across trust boundaries.

14.8 Operate the recovery path

Alert on lag, queue age, failed confirms, dead-letter growth, listener restarts, and WebSocket buffer pressure. Provide safe replay with authorization and rate limits.

15. Summary

  • Spring Message, headers, channels, handlers, templates, and listener methods provide a common programming model.
  • JMS is a standard Java messaging API with queues, topics, selectors, sessions, and provider-defined implementations.
  • WebSocket is a full-duplex transport, not an application messaging protocol.
  • STOMP adds destinations, frames, subscriptions, acknowledgements, and an annotated Spring controller model over WebSocket.
  • The simple STOMP broker is useful for basic broadcasting; a broker relay is required for full broker features and clustering.
  • RabbitMQ routes publications through exchanges and bindings to queues; publisher confirms and consumer acknowledgements protect different transfer boundaries.
  • RabbitMQ redelivery is expected, prefetch controls in-flight work, and DLQ workflows need bounded retry and ownership.
  • Kafka stores ordered records by partition, distributes partitions across consumer groups, and tracks progress through offsets.
  • Kafka exactly-once semantics applies to transactional read-process-write flows inside Kafka; external effects still require idempotency or coordination.
  • Across every broker, durable IDs, schema evolution, idempotent consumers, outbox publication, bounded retries, security, and operational recovery are more important than annotation choice.

When messaging behavior surprises you, trace the ownership transitions: Did the producer receive broker confirmation? Which exchange, destination, topic, or partition received the message? Which consumer instance obtained it? When was it acknowledged or its offset committed? Which local effects committed first? What caused retry or redelivery? Which recovery destination now owns the failure? Those questions reveal the true distributed protocol beneath Spring’s deliberately uniform APIs.
