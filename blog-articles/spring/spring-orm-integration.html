Spring Framework Data Access

ORM Integration with Spring

An expert guide to Jakarta Persistence, Hibernate, EclipseLink, Spring-managed EntityManager instances, transaction integration, exception translation, and Spring Data JPA repositories.

Spring Framework 7.0.8 Jakarta Persistence 3.2 Spring Data JPA 4.1.0 Long-form technical article Vancouver references
Abstract. Spring ORM integration is infrastructure around a persistence provider, not a replacement for one. Jakarta Persistence defines the portable mapping and persistence-context contract; Hibernate and EclipseLink implement that contract and add provider-specific capabilities. Spring creates and manages the EntityManagerFactory, exposes transaction-scoped EntityManager proxies, coordinates local or JTA transactions, adapts provider behavior through vendor adapters and dialects, and translates persistence exceptions into Spring’s data-access hierarchy. Spring Data JPA adds repository composition and query derivation on top of the same EntityManager. This article develops those layers, emphasizing entity state, persistence-context scope, flush behavior, transaction boundaries, lazy loading, provider portability, repository semantics, and performance.

Spring Framework 7.0.8 is the stable framework reference used here. Jakarta Persistence 3.2 is the current final specification, and Spring Data JPA 4.1.0 is the current stable repository generation. EclipseLink 5.0.x implements Jakarta Persistence 3.2, while Hibernate supplies both a native Session API and a Jakarta Persistence implementation.[1][2][3][4]

ORM maps a Java object model to relational state, but it does not remove the database. Query count, join shape, index coverage, lock duration, transaction isolation, constraint timing, and generated SQL remain observable parts of application behavior. Spring’s recommended ORM style is to write data-access code against the native JPA or provider API and let Spring supply resource and transaction management around it.[5]

2. Jakarta Persistence fundamentals

2.1 Persistence unit, factory, manager, and context

A persistence unit defines related managed types mapped to one database configuration. An EntityManagerFactory creates entity managers for that unit and is thread-safe. An EntityManager owns one persistence context and must not be shared between concurrently executing threads. A persistence context guarantees one managed Java object instance for a given persistent identity within that context.[2]

ConceptScopeThread safety
EntityManagerFactoryPersistence-unit/application lifetimeThread-safe
EntityManagerPersistence context, usually one transactionNot thread-safe
Managed entityIdentity-scoped within one contextOrdinary mutable object; do not share as concurrent state

2.2 Entity states

New/transient
Not associated with a persistence context and without persistent database identity.
Managed
Associated with the current context; state changes are tracked and may be flushed.
Detached
Has persistent identity but is no longer associated with the current context.
Removed
Associated with the context and scheduled for deletion.

persist() makes a new entity managed. merge() copies state into a managed instance and returns that instance; the argument itself does not become managed merely because it was passed to merge(). This distinction is central to detached-object handling and to Spring Data JPA’s save() behavior.[2][6]

Java 
@Transactional
public Customer updateDetached(Customer detached) {
    Customer managed =
            entityManager.merge(detached);

    // Continue with the returned managed instance.
    managed.recordAuditEvent();

    return managed;
}

2.3 Entity class constraints

Jakarta Persistence 3.2 requires an entity to be a top-level class or static inner class with a public or protected no-argument constructor. An entity cannot be an enum, record, or interface. The entity class and persistent members must not be final under the portable contract. These rules permit provider instantiation, proxying, enhancement, and lifecycle management.[2]

Java 
@Entity
@Table(name = "customer")
public class Customer {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Version
    private long version;

    @Column(nullable = false, unique = true, length = 320)
    private String email;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 24)
    private CustomerStatus status;

    protected Customer() {
        // Required by the persistence provider.
    }

    public Customer(String email) {
        this.email = Objects.requireNonNull(email);
        this.status = CustomerStatus.ACTIVE;
    }

    public Long getId() {
        return id;
    }

    public void changeEmail(String replacement) {
        this.email = Objects.requireNonNull(replacement);
    }

    public void suspend() {
        if (status == CustomerStatus.CLOSED) {
            throw new IllegalStateException(
                    "Closed customers cannot be suspended");
        }
        status = CustomerStatus.SUSPENDED;
    }
}

2.4 Dirty checking and flushing

Providers track changes to managed entities and synchronize them with the database during flush. Flush is not commit: it sends pending SQL to the database within the current transaction, allowing constraints to fail before commit, but transaction durability still depends on commit. Hibernate describes the persistence context as a transactional write-behind cache; JPA defines AUTO and COMMIT flush modes, while providers may expose additional modes.[2][7]

Java 
@Transactional
public void changeEmail(long id, String replacement) {
    Customer customer =
            entityManager.find(Customer.class, id);

    if (customer == null) {
        throw new CustomerNotFoundException(id);
    }

    customer.changeEmail(replacement);

    // No explicit update call is required.
    // Flush may occur before a relevant query or at commit.
}
Rollback does not rewind ordinary Java objects After a persistence exception, roll back and discard the failed persistence context. Objects already mutated in memory are not automatically restored to their pre-transaction state.[7]

3. What Spring adds

Spring manages ORM resources in the application context, binds the current persistence context to the transaction, applies declarative transaction semantics, adapts provider-specific behavior, and translates provider exceptions into the common DataAccessException hierarchy. JPA and JDBC code can participate in a consistent transaction model when configured against the same underlying resource.[5][8]

3.1 Factory bootstrap options

Spring supports three broad factory arrangements: standalone JPA bootstrap through LocalEntityManagerFactoryBean, an EntityManagerFactory obtained from JNDI in a Jakarta EE environment, and full container-style bootstrap through LocalContainerEntityManagerFactoryBean. The container factory is the usual choice for standalone Spring applications because it accepts Spring-managed data sources, package scanning, vendor adapters, load-time weaving, persistence-unit customization, and local or global transaction integration.[8][9]

3.2 Provider-neutral Spring configuration

Java 
@Configuration(proxyBeanMethods = false)
@EnableTransactionManagement
class PersistenceConfiguration {

    @Bean
    LocalContainerEntityManagerFactoryBean
            entityManagerFactory(
                    DataSource dataSource,
                    JpaVendorAdapter vendorAdapter) {

        LocalContainerEntityManagerFactoryBean factory =
                new LocalContainerEntityManagerFactoryBean();

        factory.setDataSource(dataSource);
        factory.setPackagesToScan(
                "com.example.customer");
        factory.setJpaVendorAdapter(vendorAdapter);
        factory.setPersistenceUnitName(
                "customer-unit");

        return factory;
    }

    @Bean
    JpaTransactionManager transactionManager(
            EntityManagerFactory factory) {

        return new JpaTransactionManager(factory);
    }
}

LocalContainerEntityManagerFactoryBean uses JPA’s container bootstrap contract and manages the resulting factory lifecycle. In Spring Framework 7, its common superclass also exposes a shared EntityManager for dependency injection, while traditional @PersistenceContext injection remains portable and explicit.[9][10]

3.3 JpaVendorAdapter and JpaDialect

A vendor adapter configures provider defaults and exposes a provider-specific dialect. A JpaDialect can apply provider transaction semantics, expose an underlying JDBC connection, and perform advanced exception translation. Spring provides adapters for Hibernate and EclipseLink; they are designed primarily for Spring-managed transactions through JpaTransactionManager.[8]

4. Hibernate integration

Hibernate provides a native API centered on SessionFactory and Session and implements Jakarta Persistence through EntityManagerFactory and EntityManager. Spring recommends JPA-style Hibernate setup for new applications, while allowing provider-specific unwrapping when a Hibernate capability is intentionally required.[4][8]

4.1 Hibernate provider configuration

Java 
@Configuration(proxyBeanMethods = false)
@Profile("hibernate")
class HibernateProviderConfiguration {

    @Bean
    JpaVendorAdapter jpaVendorAdapter() {
        HibernateJpaVendorAdapter adapter =
                new HibernateJpaVendorAdapter();

        adapter.setGenerateDdl(false);
        adapter.setShowSql(false);
        return adapter;
    }

    @Bean
    static BeanPostProcessor hibernateProperties() {
        return new BeanPostProcessor() {
            @Override
            public Object postProcessBeforeInitialization(
                    Object bean,
                    String beanName) {

                if (bean instanceof
                        LocalContainerEntityManagerFactoryBean factory) {

                    factory.setJpaPropertyMap(Map.of(
                        "hibernate.hbm2ddl.auto", "validate",
                        "hibernate.jdbc.batch_size", "50",
                        "hibernate.order_inserts", "true",
                        "hibernate.order_updates", "true"
                    ));
                }
                return bean;
            }
        };
    }
}

The example separates provider-neutral factory configuration from provider settings. In production code, a dedicated factory method or configuration-properties object is usually clearer than a general post-processor. Schema generation should normally be handled by a migration tool; provider schema validation can verify that mappings and the migrated schema agree.

4.2 Controlled native access

Java 
@Transactional(readOnly = true)
public void streamCustomers(
        Consumer<Customer> consumer) {

    Session session =
            entityManager.unwrap(Session.class);

    try (Stream<Customer> stream =
         session.createSelectionQuery(
                "from Customer c order by c.id",
                Customer.class)
             .setFetchSize(500)
             .getResultStream()) {

        stream.forEach(consumer);
    }
}

Unwrapping makes the method Hibernate-specific and should be isolated behind an explicit adapter or repository fragment. The returned stream must be closed. Provider fetch-size behavior and cursor requirements still depend on the JDBC driver and database.

4.3 Persistence-context growth during bulk ingestion

Hibernate retains managed entities in the first-level cache and checks them for dirty state. Large insert loops can therefore consume memory even when JDBC batching is enabled. Periodic flush() and clear() bound the persistence-context size, but clearing detaches every managed entity and changes subsequent identity and cascade behavior.[7]

Java 
@Transactional
public void importCustomers(
        List<CustomerDraft> drafts,
        int chunkSize) {

    for (int index = 0; index < drafts.size(); index++) {
        entityManager.persist(
                Customer.from(drafts.get(index)));

        if ((index + 1) % chunkSize == 0) {
            entityManager.flush();
            entityManager.clear();
        }
    }
}

5. EclipseLink integration

EclipseLink is an Eclipse Foundation persistence implementation. EclipseLink 5.0.x targets Jakarta EE 11 and implements Jakarta Persistence 3.2. Spring’s EclipseLinkJpaVendorAdapter configures EclipseLink as the JPA provider and supplies an EclipseLink-specific dialect for Spring transaction integration.[3][11]

5.1 EclipseLink provider configuration

Java 
@Configuration(proxyBeanMethods = false)
@Profile("eclipselink")
class EclipseLinkProviderConfiguration {

    @Bean
    JpaVendorAdapter jpaVendorAdapter() {
        EclipseLinkJpaVendorAdapter adapter =
                new EclipseLinkJpaVendorAdapter();

        adapter.setGenerateDdl(false);
        adapter.setShowSql(false);
        return adapter;
    }

    @Bean
    static BeanPostProcessor eclipseLinkProperties() {
        return new BeanPostProcessor() {
            @Override
            public Object postProcessBeforeInitialization(
                    Object bean,
                    String beanName) {

                if (bean instanceof
                        LocalContainerEntityManagerFactoryBean factory) {

                    factory.setJpaPropertyMap(Map.of(
                        "eclipselink.ddl-generation", "none",
                        "eclipselink.logging.level", "WARNING"
                    ));
                }
                return bean;
            }
        };
    }
}

EclipseLink offers provider-specific annotations and configuration extensions beyond the JPA standard. Use them only behind a deliberate portability boundary. Provider switching is realistic for ordinary mappings and JPQL, but not cost-free once an application depends on provider query hints, cache coordination, weaving strategy, proprietary mappings, or SQL extensions.[12]

5.2 Weaving and enhancement

JPA providers may transform entity bytecode to support lazy loading, change tracking, and other optimizations. LocalContainerEntityManagerFactoryBean accepts a Spring LoadTimeWeaver and applies provider transformers through the host class loader. Hibernate does not require a JVM agent for ordinary JPA operation, while EclipseLink deployments should select dynamic, static, or disabled weaving deliberately according to runtime capabilities and desired features.[8]

6. Spring-managed EntityManager

6.1 Transaction-scoped proxy

A JPA EntityManager is not thread-safe, but Spring’s injected transaction-scoped reference is a shared proxy. It delegates to the actual entity manager bound to the current transaction. Outside a transaction, it can create an entity manager for an individual operation. This makes the proxy safe to inject into a singleton repository without making any underlying entity manager concurrently shared.[8]

Java 
@Repository
public class CustomerJpaRepository {
    @PersistenceContext
    private EntityManager entityManager;

    public Optional<Customer> find(long id) {
        return Optional.ofNullable(
                entityManager.find(
                        Customer.class,
                        id));
    }
}

6.2 Constructor injection

@PersistenceContext applies to fields and methods, not constructors. Spring Framework 7 can expose a shared manager from the factory infrastructure, or an application can declare one explicitly with SharedEntityManagerCreator, making ordinary constructor injection possible.[8][13]

Java 
@Bean
EntityManager sharedEntityManager(
        EntityManagerFactory factory) {

    return SharedEntityManagerCreator
            .createSharedEntityManager(factory);
}

@Repository
final class CustomerQueryRepository {
    private final EntityManager entityManager;

    CustomerQueryRepository(
            EntityManager entityManager) {
        this.entityManager = entityManager;
    }
}

6.3 Extended persistence context

An extended persistence context survives transaction boundaries and keeps entities managed between transactions. It is not thread-safe and must not be injected into an ordinary singleton serving concurrent requests. Extended contexts belong in explicitly stateful components with controlled lifecycle and concurrency; most Spring applications should use transaction-scoped contexts.[2][8]

7. Transactions and locking

JpaTransactionManager manages local transactions for one EntityManagerFactory. It binds an entity manager to the thread and can expose the underlying JDBC connection to JDBC code using the same DataSource when the configured dialect supports it. Multi-resource atomic coordination requires JTA and XA-capable resources rather than a local JPA transaction manager.[8][14]

Java 
@Service
public final class CustomerService {
    private final CustomerRepository customers;

    public CustomerService(
            CustomerRepository customers) {
        this.customers = customers;
    }

    @Transactional
    public void suspend(long customerId) {
        Customer customer =
                customers.findById(customerId)
                    .orElseThrow(
                        () ->
                            new CustomerNotFoundException(
                                customerId));

        customer.suspend();
        // Dirty checking persists the state at flush.
    }
}

7.1 Operations requiring transactions

With a transaction-scoped persistence context, persist, merge, remove, and refresh require a transaction. Lock modes other than NONE also require an active transaction. Read operations can execute without one, but returned entities may be detached immediately and lazy navigation becomes unsafe.[2]

7.2 Optimistic locking

A version attribute lets the provider detect that another transaction changed a row since it was read. The provider includes version state in update or delete coordination and raises an optimistic-lock failure when the expected version no longer matches. Spring translates JPA optimistic locking failures to its portable concurrency hierarchy.[2][15]

7.3 Pessimistic locking

Java 
@Transactional
public Customer lockForUpdate(long id) {
    Customer customer =
            entityManager.find(
                Customer.class,
                id,
                LockModeType.PESSIMISTIC_WRITE);

    if (customer == null) {
        throw new CustomerNotFoundException(id);
    }

    return customer;
}

Pessimistic locks can serialize conflicting work but increase contention and deadlock risk. Keep the transaction short, access rows in a consistent order, configure lock timeouts where portable or provider-specific support exists, and do not hold database locks across user interaction or remote calls.

7.4 Read-only transactions

Spring’s read-only flag is a transaction hint that providers and transaction managers may use for optimizations. It is not a universal database-enforced prohibition against writes. Treat it as intent and optimization, not a security boundary.[8][14]

8. Fetching, lazy loading, and query shape

Association mappings define a default fetch policy, but the use case should define the actual query graph. Lazy loading outside an active persistence context can fail or produce hidden database access during serialization. Keeping a persistence context open through view rendering can mask query-shape defects and make transaction boundaries ambiguous.[2][7]

8.1 N+1 query failure

Java 
// One query loads customers.
// Accessing orders may issue one query per customer.
List<Customer> customers =
        entityManager.createQuery(
            "select c from Customer c",
            Customer.class)
        .getResultList();

for (Customer customer : customers) {
    consume(customer.getOrders().size());
}

8.2 Fetch join

Java 
List<Customer> customers =
        entityManager.createQuery(
            """
            select distinct c
            from Customer c
            left join fetch c.orders
            where c.status = :status
            """,
            Customer.class)
        .setParameter(
            "status",
            CustomerStatus.ACTIVE)
        .getResultList();

Fetch joins are useful for bounded graphs but can multiply rows, complicate pagination, and load more state than required. DTO projections are often better for read-only screens and reports.

8.3 Entity graphs

JPA entity graphs specify which parts of an object graph should be fetched for a find or query, allowing query-specific fetch plans without permanently changing mapping defaults.[2]

Java 
EntityGraph<Customer> graph =
        entityManager.createEntityGraph(
                Customer.class);

graph.addAttributeNodes("orders");

Map<String, Object> hints = Map.of(
        "jakarta.persistence.fetchgraph",
        graph);

Customer customer =
        entityManager.find(
                Customer.class,
                id,
                hints);

9. Exception translation

JPA and providers throw unchecked persistence exceptions. Spring ORM factory beans implement PersistenceExceptionTranslator. A PersistenceExceptionTranslationPostProcessor advises beans marked with @Repository and converts eligible native exceptions to Spring’s DataAccessException hierarchy.[16][17]

Java 
@Configuration(proxyBeanMethods = false)
class ExceptionTranslationConfiguration {

    @Bean
    static PersistenceExceptionTranslationPostProcessor
            persistenceExceptionTranslation() {

        return new PersistenceExceptionTranslationPostProcessor();
    }
}

Common translated categories include data-integrity violations, optimistic-locking failures, object-retrieval failures, resource failures, and uncategorized JPA system errors. Catch translated exceptions only where the application can assign a stable domain meaning; otherwise let them propagate so transaction rollback and centralized error handling remain intact.

Java 
public CustomerId register(
        RegistrationCommand command) {

    try {
        Customer customer =
                repository.save(
                    new Customer(command.email()));

        return new CustomerId(customer.getId());
    }
    catch (DataIntegrityViolationException ex) {
        throw new EmailAlreadyRegisteredException(
                command.email(),
                ex);
    }
}

10. Spring Data JPA repositories

Spring Data’s repository abstraction reduces repetitive data-access code by generating implementations for repository interfaces. Repository<T,ID> captures the domain and identifier types; technology-specific interfaces such as JpaRepository add JPA capabilities. The generated implementation still executes through an EntityManager and therefore obeys JPA entity-state, transaction, flush, and fetch semantics.[18][19]

10.1 Repository definition

Java 
public interface CustomerRepository
        extends JpaRepository<Customer, Long> {

    Optional<Customer> findByEmailIgnoreCase(
            String email);

    Page<Customer> findByStatus(
            CustomerStatus status,
            Pageable pageable);

    boolean existsByEmailIgnoreCase(
            String email);
}

Method names can derive queries from domain-property paths. For complex SQL shape, performance-sensitive fetching, provider hints, or business terminology that does not map cleanly to a long method name, use a declared query or a custom repository fragment rather than forcing query derivation.[20]

10.2 save(): persist or merge

Spring Data JPA determines whether an entity is new. New entities are passed to EntityManager.persist(); existing entities are passed to merge(). The default strategy inspects a nullable version property first and then the identifier. Entities with manually assigned identifiers may need Persistable.isNew() or an equivalent state strategy.[6]

Do not call save() after every mutation A managed entity is already tracked. Inside a transaction, changing its state is sufficient; an extra repository save() call often adds no persistence value and can obscure whether the object is managed or detached.

10.3 Declared JPQL query

Java 
public interface CustomerRepository
        extends JpaRepository<Customer, Long> {

    @Query("""
        select c
        from Customer c
        where c.status = :status
          and exists (
              select o.id

10.4 Bulk modifying query

Java 
@Modifying(
    flushAutomatically = true,
    clearAutomatically = true)
@Query("""
    update Customer c
    set c.status = :replacement
    where c.status = :expected
      and c.id in :ids
    """)
int transitionStatus(
        @Param("ids") Collection<Long> ids,
        @Param("expected") CustomerStatus expected,
        @Param("replacement") CustomerStatus replacement);

JPQL bulk updates and deletes operate directly in the database and bypass the normal synchronized state of managed entity instances. Clear or otherwise reconcile the persistence context so stale entities are not reused.[20]

10.5 Projections

Repository queries can return interface or class-based projections. Spring Data JPA generally uses tuple queries for interface projections and JPA constructor expressions for DTO projections. Nested projection paths can introduce joins and may materialize more state than a superficial property list suggests.[21]

Java 
public record CustomerSummary(
        Long id,
        String email,
        CustomerStatus status) {
}

@Query("""
    select new com.example.customer.CustomerSummary(
        c.id, c.email, c.status)
    from Customer c
    where c.status = :status
    order by c.id
    """)
List<CustomerSummary> findSummaries(
        @Param("status")
        CustomerStatus status);

10.6 Specifications

Specifications compose predicates through JPA Criteria. They are useful for dynamic filters with reusable conditions, but they do not automatically solve fetch planning, count-query cost, or projection design.[19]

Java 
public interface CustomerRepository
        extends JpaRepository<Customer, Long>,
                JpaSpecificationExecutor<Customer> {
}

static Specification<Customer> emailContains(
        String fragment) {

    return (root, query, builder) ->
        builder.like(
            builder.lower(root.get("email")),
            "%" + fragment.toLowerCase(Locale.ROOT) + "%");
}

10.7 Custom repository fragment

Repository fragments are the appropriate escape hatch for query logic that needs direct EntityManager access, provider APIs, complex result assembly, or a method whose semantics do not fit derivation. The custom implementation is a normal Spring bean and participates in the surrounding transaction.[22]

Java 
public interface CustomerRepositoryCustom {
    List<CustomerRiskView> findRiskViews(
            RiskFilter filter);
}

public final class CustomerRepositoryCustomImpl
        implements CustomerRepositoryCustom {

    private final EntityManager entityManager;

    public CustomerRepositoryCustomImpl(
            EntityManager entityManager) {
        this.entityManager = entityManager;
    }

    @Override
    public List<CustomerRiskView> findRiskViews(
            RiskFilter filter) {

        return entityManager.createQuery(
            """
            select new com.example.customer.CustomerRiskView(
                c.id, c.email, count(o), sum(o.total))
            from Customer c
            join c.orders o
            where o.createdAt >= :since
            group by c.id, c.email
            having sum(o.total) >= :minimum
            """,
            CustomerRiskView.class)
        .setParameter("since", filter.since())
        .setParameter("minimum", filter.minimum())
        .getResultList();
    }
}

public interface CustomerRepository
        extends JpaRepository<Customer, Long>,
                CustomerRepositoryCustom {
}

10.8 Transaction boundaries

Repository CRUD methods receive default transaction metadata from their implementation, but declared query methods do not all imply the business transaction an application needs. Place cross-repository and invariant-preserving transactions on service methods. A repository method is an implementation operation; a service transaction is an application unit of work.[23]

11. Multiple persistence units

Multiple factories require explicit naming and qualification for the factory, transaction manager, entity manager, and repository scan. Do not rely on type-only autowiring when two persistence units manage distinct databases or domains.[8][19]

Java 
@Configuration(proxyBeanMethods = false)
@EnableJpaRepositories(
    basePackages = "com.example.audit",
    entityManagerFactoryRef = "auditEntityManagerFactory",
    transactionManagerRef = "auditTransactionManager")
class AuditPersistenceConfiguration {

    @Bean
    LocalContainerEntityManagerFactoryBean
            auditEntityManagerFactory(
                    @Qualifier("auditDataSource")
                    DataSource dataSource,
                    JpaVendorAdapter vendorAdapter) {

        LocalContainerEntityManagerFactoryBean factory =
                new LocalContainerEntityManagerFactoryBean();

        factory.setDataSource(dataSource);
        factory.setPackagesToScan("com.example.audit");
        factory.setPersistenceUnitName("audit-unit");
        factory.setJpaVendorAdapter(vendorAdapter);
        return factory;
    }

    @Bean
    JpaTransactionManager auditTransactionManager(
            @Qualifier("auditEntityManagerFactory")
            EntityManagerFactory factory) {

        return new JpaTransactionManager(factory);
    }
}

One local transaction manager cannot atomically commit two independent databases. Use an outbox, saga, idempotent compensation, or JTA/XA according to the required consistency model.

12. Worked example: order aggregate

12.1 Aggregate mapping

Java 
@Entity
@Table(name = "purchase_order")
public class PurchaseOrder {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Version
    private long version;

    @Column(nullable = false, unique = true, length = 36)
    private String externalId;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 24)
    private OrderStatus status;

    @Column(nullable = false, precision = 19, scale = 2)
    private BigDecimal total;

    @OneToMany(
        mappedBy = "order",
        cascade = CascadeType.ALL,
        orphanRemoval = true)
    private List<OrderLine> lines =
            new ArrayList<>();

    protected PurchaseOrder() {
    }

    public PurchaseOrder(UUID externalId) {
        this.externalId = externalId.toString();
        this.status = OrderStatus.DRAFT;
        this.total = BigDecimal.ZERO;
    }

    public Long getId() {
        return id;
    }

    public List<OrderLine> getLines() {
        return Collections.unmodifiableList(lines);
    }

    public BigDecimal getTotal() {
        return total;
    }

    public void addLine(
            String sku,
            int quantity,
            BigDecimal unitPrice) {

        if (status != OrderStatus.DRAFT) {
            throw new IllegalStateException(
                    "Only draft orders can change");
        }

        OrderLine line =
                new OrderLine(
                    this,
                    sku,
                    quantity,
                    unitPrice);

        lines.add(line);
        recalculateTotal();
    }

    public void submit() {
        if (lines.isEmpty()) {
            throw new IllegalStateException(
                    "Cannot submit an empty order");
        }
        status = OrderStatus.SUBMITTED;
    }

    private void recalculateTotal() {
        total = lines.stream()
            .map(OrderLine::lineTotal)
            .reduce(
                BigDecimal.ZERO,
                BigDecimal::add);
    }
}
Java 
@Entity
@Table(name = "order_line")
public class OrderLine {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "order_id", nullable = false)
    private PurchaseOrder order;

    @Column(nullable = false, length = 64)
    private String sku;

    @Column(nullable = false)
    private int quantity;

    @Column(nullable = false, precision = 19, scale = 2)
    private BigDecimal unitPrice;

    protected OrderLine() {
    }

    OrderLine(
            PurchaseOrder order,
            String sku,
            int quantity,
            BigDecimal unitPrice) {

        this.order = Objects.requireNonNull(order);
        this.sku = Objects.requireNonNull(sku);
        this.quantity = quantity;
        this.unitPrice = unitPrice;
    }

    BigDecimal lineTotal() {
        return unitPrice.multiply(
                BigDecimal.valueOf(quantity));
    }
}

12.3 Application service

Java 
@Service
public final class OrderService {
    private final PurchaseOrderRepository orders;

    public OrderService(
            PurchaseOrderRepository orders) {
        this.orders = orders;
    }

    @Transactional
    public OrderId create(CreateOrder command) {
        PurchaseOrder order =
                new PurchaseOrder(
                    command.externalId());

        for (CreateOrderLine line :
                command.lines()) {

            order.addLine(
                line.sku(),
                line.quantity(),
                line.unitPrice());
        }

        PurchaseOrder persisted =
                orders.save(order);

        return new OrderId(persisted.getId());
    }

    @Transactional
    public void submit(long id) {
        PurchaseOrder order =
                orders.findDetailedById(id)
                    .orElseThrow(
                        () ->
                            new OrderNotFoundException(id));

        order.submit();
        // No save call: the entity is managed.
    }

    @Transactional(readOnly = true)
    public OrderDetails details(long id) {
        PurchaseOrder order =
                orders.findDetailedById(id)
                    .orElseThrow(
                        () ->
                            new OrderNotFoundException(id));

        return OrderDetails.from(order);
    }
}

12.4 Design analysis

  • The aggregate root owns line mutation and total calculation.
  • Cascade and orphan removal are limited to the aggregate-owned child collection.
  • A version field detects conflicting updates.
  • Detailed reads declare a fetch graph; summary reads return DTOs.
  • The service transaction encloses entity loading and mutation.
  • Managed-state changes rely on dirty checking instead of repeated save() calls.
  • Database constraints and migrations must reinforce uniqueness, nullability, precision, and foreign-key rules.

13. Testing ORM integration

Mapping tests should use the production database engine when SQL dialect, generated identifiers, locking, constraint timing, JSON types, sequences, or batch behavior matter. An in-memory substitute can verify basic JPA wiring but may conceal migration and query defects.

Java 
@SpringJUnitConfig(PersistenceTestConfiguration.class)
@Transactional
class PurchaseOrderRepositoryTest {

    @Autowired
    PurchaseOrderRepository orders;

    @PersistenceContext
    EntityManager entityManager;

    @Test
    void persistsAggregateAndLines() {
        PurchaseOrder order =
                new PurchaseOrder(UUID.randomUUID());

        order.addLine(
                "SKU-1",
                2,
                new BigDecimal("12.50"));

        PurchaseOrder saved =
                orders.saveAndFlush(order);

        entityManager.clear();

        PurchaseOrder reloaded =
                orders.findDetailedById(saved.getId())
                    .orElseThrow();

        assertEquals(1, reloaded.getLines().size());
        assertEquals(
                new BigDecimal("25.00"),
                reloaded.getTotal());
    }
}

flush() in tests surfaces SQL generation and database constraints before assertions. clear() prevents the test from passing only because the same managed instance remains in the first-level cache. Add non-rollback tests for failures that occur only during commit.[2]

14. Performance and production behavior

14.1 Observe SQL and plans

Count queries per use case, record durations and row counts, inspect generated SQL, and analyze plans with production-like data. ORM abstractions make query generation convenient, not automatically efficient.

14.2 Pagination

Offset pagination requires the database to locate and often discard preceding rows. For deep navigation, keyset pagination based on a stable ordered key may be more efficient. Collection fetch joins and pageable queries are a dangerous combination because row multiplication makes count and page boundaries difficult.

14.3 Cache layers

The persistence context is always a first-level identity map. A provider second-level cache is optional and factory-scoped. Query caches, collection caches, and external caches introduce invalidation and consistency policy; enable them only for measured, well-bounded access patterns.[2][7]

14.4 Write batching

Provider batching depends on identifier strategy, statement ordering, JDBC driver support, and flush boundaries. Measure actual network round trips and statement execution rather than assuming a configured batch size guarantees batching.[7]

15. Diagnostics

15.1 Lazy initialization failure

The code accessed an unloaded association after its persistence context was unavailable. Fix the query or mapping boundary: fetch the required graph, return a projection, or perform DTO conversion inside the transaction. Do not make every association eager.

15.2 Detached entity passed to persist

A relationship or explicit operation cascaded persist() to an object that already has persistent identity. Review aggregate ownership, cascade settings, new-state detection, and whether the object should be loaded and mutated instead of reconstructed.

15.3 Optimistic lock failure

Another transaction changed the same versioned row. Roll back and discard the failed persistence context. Retry only a complete idempotent application operation using freshly loaded state, or surface a conflict to the caller.

15.4 SQL issued unexpectedly

Inspect flush mode, query overlap with dirty entities, cascades, collection ownership, automatic dirty checking, and lifecycle callbacks. A read query can trigger an automatic flush before it runs.

15.5 Too many selects

Trace query count by endpoint, identify lazy traversal, inspect repository projection shape, and distinguish N+1 behavior from legitimate separate queries. Apply a fetch join, entity graph, batch-fetch setting, or DTO query according to cardinality.

15.6 Provider-specific behavior differs

Confirm the actual persistence provider, vendor adapter, dialect, property namespace, bytecode enhancement mode, and database dialect. Test provider switches; the JPA API standardizes contracts, not generated SQL or every performance characteristic.

16. Expert practices

16.1 Model aggregate ownership

Apply cascade and orphan removal only where the parent truly owns the child lifecycle. Broad cascades across shared references can create accidental inserts and deletes.

16.2 Put transactions around use cases

Load, validate, mutate, and flush within one explicit application transaction. Avoid remote calls and user interaction while database locks or a large persistence context are retained.

16.3 Separate write models from read shapes

Return entities when the caller needs aggregate behavior in the transaction. Return DTOs or projections for reports, APIs, and list screens. Do not serialize persistence proxies as an accidental API contract.

16.4 Isolate provider extensions

Keep native Hibernate or EclipseLink calls in small adapters or custom repository fragments. Document the portability trade-off and add provider-specific integration tests.

16.5 Let the database enforce invariants

Use primary keys, foreign keys, unique constraints, checks, precision, nullability, and indexes. Java validation improves feedback but does not replace concurrency-safe database enforcement.

16.6 Design entity equality cautiously

Generated identifiers are unavailable before persistence, mutable business fields are unsafe hash keys, and proxies can complicate class comparisons. Define equality according to aggregate lifecycle and test transient, managed, detached, and proxied instances.

16.7 Discard failed contexts

After a provider exception, roll back and end the unit of work. Do not catch an exception and continue making persistence calls in the same transaction.

16.8 Keep repositories persistence-oriented

Repository interfaces should express aggregate retrieval and persistence. Cross-aggregate workflows, authorization, retries, and orchestration belong in application services.

16.9 Measure generated behavior

Review SQL, query counts, plans, lock waits, batch effectiveness, cache hit rates, and persistence-context size. An ORM mapping is executable database behavior.

17. Summary

Spring ORM integration is a layered composition:

  • Jakarta Persistence defines entities, persistence units, entity managers, persistence contexts, lifecycle, querying, flushing, and locking.
  • Hibernate and EclipseLink implement that contract and provide different SQL generation, enhancement, caching, batching, and extension facilities.
  • Spring’s LocalContainerEntityManagerFactoryBean performs container-style bootstrap with Spring-managed resources.
  • JpaTransactionManager binds the current persistence context to a local transaction and can coordinate JDBC access to the same resource.
  • The injected transaction-scoped EntityManager is a shared proxy; the underlying manager remains transaction-bound and non-thread-safe.
  • Dirty checking persists changes to managed entities; merge() returns a managed copy and does not attach the argument itself.
  • Spring exception translation turns provider failures into portable data-access categories for repositories and DAOs.
  • Spring Data JPA repositories generate persistence adapters, but they do not change JPA entity-state, fetch, transaction, or flush semantics.
  • Fetch plans, projections, transaction boundaries, database constraints, and generated SQL determine correctness and performance.

Diagnose ORM problems by tracing the unit of work: Which persistence context owns the entity? Is the entity new, managed, detached, or removed? Which transaction is active? When will flush occur? Which associations are initialized? Which SQL was generated? Which database constraint, version predicate, or lock determined the result? Which provider-specific behavior or repository abstraction participated? Those questions expose the real mechanics beneath the annotations.
