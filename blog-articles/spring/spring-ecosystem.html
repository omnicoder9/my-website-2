1The question

Every project in the Spring portfolio makes the same offer. You write a small thing: a constructor, an annotation, an interface, a property, sometimes nothing but a dependency. Spring writes the rest. The seventeen projects on this list differ mostly in how small the thing you write is allowed to be, in what Spring reads to work out the rest, and in who notices when the inference is wrong.

That is the organising question of this article: who writes the rest, and who checks it? It is a better question than the usual one, which asks what each project does. What each project does is on its home page. What it is worth knowing before adopting one is how much of the behaviour you will not have written, what it was inferred from, and where the mistakes in that inference surface.

The idea is older than most of the projects. Rod Johnson's 2002 book on J2EE design shipped with the framework code that became Spring 1, and the 1.0 release of March 2004 led with a lightweight container supporting setter and constructor injection 2. Martin Fowler's essay of the same year gave the pattern the name that stuck, dependency injection, and described its central move: an assembler, not the object, decides which implementation a dependency receives 3. Twenty-two years on, the assembler writes far more than wiring. It writes HTTP dispatch, SQL, broker topologies, OAuth endpoints and the loop that feeds a language model its tool results.

One correction to the brief before the survey. The list names VMware Spring Boot, and that attribution is out of date. Broadcom completed its acquisition of VMware on 22 November 2023 4, and the Spring projects' own pages now carry a Broadcom copyright line 5. The projects remain open source; the commercial support offering is sold under the Tanzu name.

The versions the article describes are current as of September 2026. Spring Framework 7.0 went GA on 13 November 2025 as the start of a new generation, and its maintainers name 7.1 in November 2026 as the next feature branch; the 6.2 line's open-source support ended in June 2026 6,7. Spring Boot 4.0 followed on 20 November 2025 and 4.1 on 10 June 2026 8,9. Framework 7 keeps the JDK 17 baseline while recommending JDK 25 for production, and moves to Jakarta EE 11 7.

The survey is built from three pieces. Each project gets a plate with the same five fields. Each plate is placed on two scales, one for how much Spring writes and one for what it reads. And eleven small experiments, run at build time with their output embedded, put numbers on the failure mode each plate names. The ledger in section 14 collects the placements; its headline is that the unchecked projects are not the most magical ones. They are the ones where Spring infers least.

2How to read a plate

The first scale is the delegation ladder. It asks what kind of artefact the developer supplies for a project's canonical use, and it has six rungs, from writing the whole interaction to writing nothing but a dependency.

At D0, procedure, you write the interaction and the framework supplies types. At D1, callback, you write the varying step and the framework owns the loop, the resources and the transaction: a batch item processor, an assembler that adds hypermedia links, a prompt passed to a chat client. At D2, annotated method, you write a method whose signature and annotations say how to bind it: an HTTP handler, a message listener, a GraphQL field mapping. At D3, interface, you write a type with no body and the framework generates the implementation. At D4, policy, you write rules in a DSL or properties and the framework builds the machinery that enforces them. At D5, presence, the declaration is a dependency, a property or a package layout.

The coding rule is the canonical use named in each project's own documentation, not its most advanced mode. Spring MVC can be driven through functional routes, and Spring Data repositories can include hand-written fragments; each plate records the default path a new user is shown, and the escape hatches appear in its breaks when field.

The second scale is the inference source: what Spring reads in order to write the rest. There are five values. X, explicit: nothing is inferred; the framework executes the rules you wrote. T, types: constructor parameters, method signatures and the annotations on them. N, names: method names, schema field names, package names. E, environment: the classpath, properties, and remote state such as a configuration server or a service registry. R, runtime content: the bodies and headers of messages, or the output of a model.

The two scales are independent. Spring Data and Spring Modulith sit on different rungs but both infer from names; Spring MVC and Spring AMQP sit on the same rung but one reads types and the other reads message content.

Each plate then records who checks the inference, in five classes. K0: only your own tests. K1: the type system. K2: the framework fails fast at bootstrap. K3: the framework ships a dedicated diagnostic or verification. K4: the framework contains failures at run time, message by message. The gauge on every plate, a split rule, shows all three: the six rungs with the delegated ones filled, a chip for the inference source, and a glyph for the check. An open magenta circle means nothing but your tests stands between a wrong declaration and production.

3Twenty-two years of hand-offs

The portfolio did not arrive as a design. It accreted, and the order of accretion explains a good deal about where each project sits.

The first wave, 2004 to 2008, is the container and the things enterprise Java needed around it. Framework 1.0 shipped with its web MVC framework, transaction management and AOP in March 2004 2. The security project that began as Acegi Security was relaunched as Spring Security 2.0 in April 2008, with configuration its authors described as substantially simplified; Rod Johnson reported the Acegi line at more than 250,000 downloads 10,11. Spring Batch reached its production release in 2008 as a joint effort with Accenture, which contributed batch frameworks it had built for earlier platforms 12,13. Spring Integration was unveiled in December 2007 around the vocabulary of Hohpe and Woolf's Enterprise Integration Patterns, and its 1.0 GA was announced at SpringOne Americas late in 2008 14–16.

The second wave, 2011 to 2017, is data and messaging beyond the relational database, and then the move from configuring a container to having one configured for you. Spring Data JPA 1.0 shipped in July 2011 after merging the Hades repository library 17,18. Spring AMQP 1.0 followed in August 2011 19. Spring Boot 1.0 arrived on 1 April 2014, eighteen months after the request for better containerless web applications that started it, with 1,720 commits from 54 contributors 20. Spring Session 1.0 came in January 2015 21, Spring Cloud's first release train, Angel, in 2015 22, and Spring for Apache Kafka's 1.0 line in 2016 23,24. Spring Framework 5.0 added WebFlux in September 2017 25.

The third wave is recent and responds to new pressures rather than old gaps. Spring HATEOAS, begun as a small extension to Spring MVC around 2012, reached 1.0 in September 2019 after renaming its core types to make clear it builds representations rather than resources 26,27. Spring for GraphQL reached 1.0 in May 2022 as a joint effort with the GraphQL Java team 28,29. Spring Authorization Server reached 1.0 in November 2022 and has since moved into Spring Security 7.0 30. Spring Modulith left experimental status in August 2023 31, and Spring AI reached 1.0 in May 2025 and 2.0 in June 2026 5,32.

The colours in the timeline carry a pattern. The early projects cluster at D1 and D2, where you write methods and callbacks. The projects that sit highest on the ladder, D4 and D5, arrive after Boot made presence a legitimate form of declaration. Spring AI is the exception, landing at D1. When the thing being called is a model, the developer's prompt is the varying step and cannot be inferred away.

4The container and the presence

Everything else in the portfolio is built on the container, so it is the right place to start. Its documentation describes inversion of control as the process by which objects declare their dependencies and the container supplies them at creation 33.

Plate 1

Spring Framework

You write
Plain classes whose constructors name what they need, registered as components or returned from @Bean methods.
Spring writes
The object graph: instantiation order, injection, lifecycle callbacks and the proxies that add transactions or aspects around your methods 33.
Reads
Types. Constructor and method signatures, and the annotations on them.
Checked by
The container itself, at refresh: it validates each bean's configuration as the context is created, so an unsatisfiable dependency stops startup rather than a request 34.
Breaks when
Two candidates satisfy one type, or two constructors need each other; the documented remedies are qualifiers and restructuring, not configuration 34.

The container reads types. That choice is why its check is strong. A constructor's parameter types are checked by the compiler before the container ever sees them, and the container validates each bean's configuration as the context is created, so a missing collaborator stops the application at startup rather than failing on first use 34. Framework 7 pushes the same idea one step further: the codebase is now annotated with JSpecify nullability, and Spring Boot 4 documents how applications can adopt the annotations so that tooling catches null misuse at build time 35. Framework 7 also moved resilience into the core, with concurrency throttling and retry annotations 36, and added first-class API versioning for web endpoints 37.

Spring Boot is the project that turned presence into a declaration.

Plate 2

Spring Boot

You write
A dependency on a starter and, where the default is wrong, a property.
Spring writes
Whole configuration classes, each applied only when its conditions hold: a class on the classpath, a bean missing from the context, a property set 38,39.
Reads
The environment: classpath, the beans you already declared, properties.
Checked by
A dedicated diagnostic. Starting with --debug logs a conditions report of every auto-configuration and the reason it did or did not apply 38.
Breaks when
The classpath says something you did not mean. Boot 4 split auto-configuration into per-technology modules, so the Kafka client alone no longer switches Kafka on; the starter does 40,41.

Boot reads the environment, and the environment is a weaker source than types in one precise way: the compiler cannot see it. Boot's response is a mechanism and a report. The mechanism is back-off. Auto-configuration classes are guarded by conditions, typically on a class being present and a bean being absent, so a bean you define replaces the default rather than competing with it 39. The guide notes that bean conditions are only reliable on auto-configuration classes, because those are processed after user-defined bean definitions have been added 42. The report is the conditions report, which lists every auto-configuration with the reason it matched or did not 38.

The lab's second experiment implements that evaluation in miniature: ten auto-configurations, a small classpath, one property and two user beans. It then runs them twice, once in Boot's order and once with auto-configuration first.

Run in Boot's order, the evaluator produces 4 positive and 6 negative matches and no duplicates, because the user's DataSource is already registered when the auto-configured one asks whether one exists. Boot 4 changed what presence means. The 4.0 line began by modularising the code base 40, so auto-configuration now lives in per-technology modules; the documented example imports DataSourceAutoConfiguration from a JDBC-specific package 38. One consequence surfaced as a user report against Spring for Apache Kafka: adding the Kafka library alone no longer activates Kafka auto-configuration under Boot 4, and the starter is required 41. The declaration moved from a library is present to a starter is present. It is a small change with a large lesson. At D5 the dependency list is the source code, and it deserves the same review as source code.

5The web layer: one model, two runtimes

Spring MVC and Spring WebFlux share a programming model and differ in what happens underneath it. The pairing is the clearest case in the portfolio of two projects on the same rung, reading the same source, that fail in entirely different ways.

Plate 3

Spring MVC

You write
Controller methods whose annotations give the path and verb, and whose parameters say what to extract from the request.
Spring writes
Dispatch through one front-controller servlet, argument resolution, content negotiation and message conversion 43.
Reads
Types and annotations on the handler method's signature.
Checked by
The compiler for the method's types; everything else is exercised when a request arrives.
Breaks when
Waiting, not computing, fills the thread pool. Each request holds a Tomcat worker thread for its whole duration, and the connector's default ceiling is 200 44.
Plate 4

Spring WebFlux

You write
The same annotated handlers, or functional routes, returning reactive types.
Spring writes
A non-blocking pipeline on an event loop, with back-pressure carried by the Reactive Streams contract 45,46.
Reads
Types, as in MVC; the return type now also says the result arrives later.
Checked by
The compiler for signatures. Nothing in the programming model detects a blocking call made on the loop.
Breaks when
Anything on the event loop blocks. A small fixed set of loop threads is the whole capacity, so one blocking call starves every connection they serve.

WebFlux arrived with Spring Framework 5.0 as a dedicated reactive web framework beside a revised MVC 25. The framework's own FAQ states the rationale: blocking threads consume resources, and for workloads with many concurrent, latency-sensitive requests a non-blocking event loop is more efficient 45. Java 21 then changed the comparison. Virtual threads make a thread per request cheap again 47, and Spring Boot exposes them through a single property, a switch whose one-line simplicity prompted a request to document where it does not help 48.

The fourth experiment puts one number on each option. It uses Little's law, which says concurrency equals throughput times time in system 49, with 8 cores and 2 ms of CPU per request, a CPU ceiling of 4,000 requests per second.

Three results follow. First, the default pool of 200 platform threads stops being the bottleneck only while blocking wait stays below 48.0 ms; beyond that, throughput falls as 200 divided by time in system, to 1,960.8 requests per second at 100 ms. A discrete-event simulation of the same pool at 100 ms wait delivered 1,951.5 requests per second, within 0.48% of the formula. Second, virtual threads remove the thread ceiling but not the resource behind it. With 50 permits to the downstream resource, a figure chosen to stand for a connection pool, throughput follows 50 divided by time in system: a quarter of the platform figure wherever both are limited by waiting, and 490.2 requests per second at 100 ms. Third, the event loop wins everywhere when its I/O is truly non-blocking and loses badly when it is not. One blocking call at 50 ms of wait delivers 153.8 requests per second, 25.0 times less than the 200-thread pool at the same wait.

The engineering choice follows the plates' breaks when fields. MVC fails by queueing, visibly and gradually. WebFlux fails by starvation, and nothing in the type system shows that a method called on the loop is secretly blocking. With virtual threads, MVC's failure mode moves from the thread pool to whatever pool sits behind it. That is usually where it belonged.

6Data access: the method name as a program

Spring Data is the purest case of D3. The developer writes an interface and the framework writes its implementation, including queries it derives from nothing but method names.

Plate 5

Spring Data

You write
An interface extending a repository base type, with query methods named after what they should find.
Spring writes
The implementation, including queries derived by parsing the method name against the domain type's properties 50,51.
Reads
Names. The subject and predicate keywords in the method name, resolved against property names.
Checked by
Bootstrap: derived queries undergo a property check when repositories are created, and declared queries have been validated at startup since the first milestones 51,52.
Breaks when
A name grows into a sentence. Past two or three predicates the method name is harder to read than the query it replaces, and a declared query is the escape 50.

The reference documentation defines the grammar. A subject such as find…By, count…By or exists…By, optionally with Distinct or a Top limit, is followed by predicates over properties joined with And and Or. Keywords such as Between, LessThan and IgnoreCase choose the operator 50,51. The grammar also defines how nested properties are found. The documentation describes the traversal: try the whole expression as a property, then split the camel-case parts from the right into a head and a tail and recurse into the head 50.

The third experiment implements a subset of that grammar and the traversal against a small Person type with a nested Address.

The parser derives 12 of 14 names. The two failures are the interesting part. findByNickname names a property that does not exist, and findByAddressCountry names a nested property that does not exist. Both are the kind of error a type checker would catch in ordinary code, and here a string parser catches it instead. That is why Spring Data puts the check at bootstrap. It property-checks derived queries when repositories are created 51, and it has validated declared queries at startup since before 1.0 52. A name-inferred declaration gets a framework-owned check to replace the one the compiler cannot give it.

The growth series shows the other limit. One predicate costs a 14-character name; six cost 99. Past three or four predicates the method name is harder to read than the query it replaces. The declared-query escape exists for exactly that case, and it sits one rung down: you write the query, and Spring still writes the execution.

The current release line moved in the direction this article's thesis predicts, towards earlier checks. The 2025.1 generation derives JPA queries as JPQL rather than through the Criteria API, which lets Hibernate cache query structure. The same release announced work on ahead-of-time repositories, which move derivation from startup to build 53. The next train, 2026.1, is scheduled for GA in November 2026 54.

7Identity and state: where Spring infers least

Three projects handle who the caller is and what the server remembers about them. Two of them sit at D4 and read only what you wrote. They are also two of the four projects in this survey whose mistakes nothing but your tests will find.

Plate 6

Spring Security

You write
A filter-chain policy in a configuration DSL: which requests need which authorities, and how users authenticate.
Spring writes
The filter chain, authentication flows, session fixation and CSRF handling, and method-level authorization 10,55.
Reads
Nothing inferred. The rules are what you wrote, matched in the order you wrote them.
Checked by
Only your own tests. The framework cannot know that a rule you wrote is broader than you meant.
Breaks when
A matcher is too wide or sits above a narrower one. The failure is an endpoint that works for the wrong caller, which no exception reports.

Spring Security has spent five years modernising its authorization API, which paved the way for authorized objects, value masking and multi-factor authentication. As of 7.0 the legacy access-decision API moves to a separate artefact 55. None of that changes the plate's central property. A filter-chain policy is explicit, so the framework enforces what it is told. A rule that is broader than intended produces an endpoint that works, and no exception names the mistake. Spring Security ships test support for exactly this reason. The check is available, but it is yours to write.

Plate 7

Spring Authorization Server

You write
Registered clients, their grant types, redirect URIs, scopes and token settings.
Spring writes
The OAuth 2 and OpenID Connect protocol endpoints, token issuance and signing-key publication 30,56,57.
Reads
The client registrations and token settings you declared.
Checked by
The protocol reports errors to clients, but whether a client should have that grant is a policy only your tests can check.
Breaks when
Token lifetime and revocation pull against each other. A self-contained token cannot be recalled before it expires; an opaque one costs a call to check 58,59.

Spring Authorization Server started as a separate project so it could iterate quickly. Its team judged it mature enough to fold into Spring Security 7.0, keeping the same Maven coordinates except the version 30. It implements the OAuth 2 framework and OpenID Connect 56,57, and the protocol's own security guidance has accumulated around it. PKCE was defined for public clients 60, and the 2025 best-current-practice document collects the attacks the original framework did not anticipate 61.

The design decision with the most operational weight is the access token's form. A token can be self-contained, a signed JWT that any resource server can validate locally 58. Or it can be opaque, meaningful only to the authorization server, which answers introspection requests 59. The ninth experiment prices the choice for 10,000 active tokens.

For opaque tokens with a response cache, the product of introspection rate and mean revocation exposure is fixed at 5,000, half the number of active tokens. A 5-second cache costs 2,000 calls per second for 2.5 seconds of mean exposure; a 300-second cache costs 33.3 calls per second for 150 seconds. The simulation reproduces the exposure within 1% at every point. Self-contained tokens make no calls, and a revoked token remains usable for half its lifetime on average: 150 seconds for a five-minute token, 1,800 for an hour. The invariant is the useful part. No setting reduces both costs, and a team arguing for both is arguing with arithmetic.

Plate 8

Spring Session

You write
A dependency on a store module and its connection settings. Application code keeps calling the ordinary session API.
Spring writes
A replacement for the servlet container's session, backed by Redis, a relational database or Hazelcast, without tying the application to one container 21,62.
Reads
The environment: which store module is present and how to reach it.
Checked by
Only your tests, and the store's own availability.
Breaks when
What an application puts in the session must now travel to a store and back, on requests that never noticed the session was remote.

Spring Session sits at D5 for the application's code, which keeps calling the ordinary session API while a filter swaps in a store-backed implementation 62. Its 1.0 release named the use cases that still define it: clustered sessions without container-specific configuration, several accounts in one browser, and session identifiers in headers for REST clients 21. What it infers is where the store is, and what it cannot infer is whether the objects the application puts in a session belong in a remote store at all.

8Messaging: listeners that read the world

The three messaging projects all move the inference source to runtime content. What arrives on a queue or a topic decides what happens, and no startup check can see it. All three answer the same way, with containment that handles failures one message at a time.

Plate 9

Spring Integration

You write
Flows: channels, filters, transformers, routers and adapters, composed in a Java DSL or annotations.
Spring writes
The messaging plumbing behind the Enterprise Integration Patterns vocabulary, plus adapters to files, brokers, HTTP and more 14,16.
Reads
The topology you declared; routing decisions then read message headers at run time.
Checked by
The type system for the DSL; a flow's behaviour shows itself message by message.
Breaks when
The topology is right but the routing data is not, and messages arrive at an error channel rather than a stack trace.

Spring Integration was announced as the portfolio's integration layer, built on the pattern catalogue of Hohpe and Woolf and on Spring's existing JMS, remoting and scheduling support 14,16. Its current generation, 7.0, adds channel adapters for AMQP 1.0 built on Spring AMQP 4.0 and moves retry onto the core framework's retry support 63. It sits at D4 because its characteristic artefact is the flow, a declared topology. The routing that topology performs then reads message headers, which is why failures arrive on error channels rather than in stack traces.

Plate 10

Spring AMQP

You write
Listener methods annotated with the queue they consume, and template calls to send.
Spring writes
Listener containers, message conversion, and automatic declaration of queues, exchanges and bindings 64.
Reads
Runtime content: message properties and bodies decide how each delivery is converted.
Checked by
Runtime containment. Failed deliveries go to error handling and dead-lettering, and since 4.1 the JSON converters trust no packages unless told to 63.
Breaks when
A body cannot be converted into the listener's parameter type. It fails one message at a time, not at startup.

Spring AMQP describes itself in two parts: a template for sending and receiving, and a listener container for message-driven objects 64. Version 4.0 added a client module for RabbitMQ's AMQP 1.0 support, usable only with RabbitMQ 65,66. The 4.1 release of June 2026 added generic AMQP 1.0 support on the ProtonJ 2 library. It also changed the JSON converters to trust no packages by default, so the previous trust-everything behaviour now needs an explicit wildcard 63. That default is a runtime-containment check in the plainest form: a message body can no longer choose its own Java type. AMQP 1.0 itself is an OASIS standard from 2012 67.

Plate 11

Spring for Apache Kafka

You write
Listener methods annotated with topics, a template to send, and a container concurrency.
Spring writes
Consumer threads, polling, offset commits, retries and, since 4.0, share-group consumers 23,68.
Reads
Runtime content: records, their headers and the partitions the broker assigns.
Checked by
Runtime containment in the listener container's error handling; nothing checks that the concurrency you asked for can be used.
Breaks when
Concurrency exceeds what the partitions allow. In the reference guide's own example, 15 threads over three five-partition topics leave ten idle 69.

Kafka changes one thing the other two do not: the unit of parallelism is fixed by the topic, not the consumer. Kafka was designed around partitioned logs 70. Within a partition, Spring's concurrent container processes records sequentially 71, so a container can use at most as many threads as it has partitions. The reference guide gives an example with a twist: three topics of five partitions each, a concurrency of 15, and only five active consumers, because the default range assignor divides each topic separately 69. The fifth experiment implements both assignors and reproduces the example.

Under the range assignor, consumers 1 to 5 each take partition n of every topic, and ten threads sit idle. Round-robin keeps all fifteen busy. On a single 12-partition topic, the sweep shows active consumers rising with concurrency up to 12 and then staying at 12 whether 16, 20 or 24 are requested. Share groups change this ceiling for the first time. Kafka's queues feature, production-ready in 4.2, lets consumers in a share group process records from the same partitions with per-record acknowledgement, without the one-partition-one-consumer rule 72. Spring for Apache Kafka 4.0 added share consumers as a preview. A later change gave the share container its own concurrency, reasoning that work distribution now happens at the broker rather than in Spring 68,73.

The same experiment measures the at-least-once window. If offsets are committed after each poll batch of B records and a consumer crashes mid-batch, the records already processed in that batch are delivered again. Across 20,000 simulated crashes, a batch of 500 records, the consumer's default maximum per poll 74, replays 250.12 records per crash on average. A batch of 10 replays 4.55. Committing after every record replays none, at 10,000 commits per 10,000 records. The trade-off is linear and unavoidable, so the question is whether the listener is idempotent, which no Spring setting can answer.

9Batch: the commit interval and the memory of a job

Spring Batch is the portfolio's oldest D1 project and the clearest example of a callback rung. You write the reader, processor and writer for one item. The framework writes the loop that calls them in chunks, commits each chunk in a transaction, and records enough metadata to resume.

Plate 12

Spring Batch

You write
A reader, an optional processor and a writer for one kind of item, and a step that names a commit interval.
Spring writes
The chunk loop, transaction boundaries, skip and retry policy, and the job metadata that makes a restart resume rather than repeat 75,76.
Reads
The job and step definitions you declared.
Checked by
The type system; restart behaviour depends on which job repository you chose.
Breaks when
Nobody chose one. Since 6.0 the default infrastructure is resourceless, so unless a JDBC or MongoDB repository is enabled there is no metadata to resume from 76,77.

Version 6.0, released in November 2025, rewrote the chunk-oriented processing model with a new concurrency model, local chunking across threads, remote step execution and graceful shutdown with recovery of failed executions 75. It also changed a default with real consequences. Before 6, enabling batch processing implied a JDBC job repository. From 6 onward the default infrastructure is resourceless, and a JDBC or MongoDB repository is opted into with a dedicated annotation 76. A Spring Boot issue records the practical effect: by default nothing is stored, so schema initialisation for batch tables no longer applies unless a JDBC repository is enabled 77.

The sixth experiment prices both decisions a batch author makes. The first is the commit interval. With a commit costing C item-times and a failure probability q per item that discards the uncommitted part of a chunk, the work per item is about 1 + C/n + q(n−1)/2. It is minimised at n* = √(2C/q), the same shape as Young's classic result for checkpoint intervals 78.

For C = 50 and q = 10−4 the optimum is 1,000 items per chunk at 1.0999 item-times per item, and the simulation's minimum on the grid lands on the same 1,000. A chunk of 10 costs 6.0 times the useful work; a chunk of 10,000 costs 1.84 times in simulation. The approximation says 1.505, and drifts once qn nears one, as first-order checkpoint formulas do. The curve is flat near its minimum, so the commit interval needs to be right to within a factor of two, not tuned to the item.

The second decision is whether the job remembers anything. For a million-item job, the experiment compares restartable chunked processing with a job that must start again from the first item after any failure. That is the situation the resourceless default creates if nobody enables a persistent repository. At q = 10−7 the difference is invisible, 1.052 against 1.050 times the useful work. At 10−6 the job without memory does 1.718 times the work, at 3×10−6 6.362 times, and at 10−5 2,202.5 times, while the restartable job stays at about 1.05. The expected cost of starting over grows exponentially in job length times failure rate, and the default is safe only for jobs short enough that nobody minds.

10Cloud: resilience that composes badly

Spring Cloud is less a project than a release train of projects that share one concern: the environment an application runs in is other services. Its first train, Angel, established the convention of naming trains alphabetically after London Underground stations so the sub-projects could keep their own versions 22. The current train, 2025.1 (Oakwood), moved every project to version 5.0 on Spring Framework 7 and Boot 4. It moved gateway retries onto the framework's own retry support and put the Spring Retry circuit-breaker module into maintenance 79. Trains are supported for as long as the Boot versions they target, and roughly three months beyond 80.

Plate 13

Spring Cloud

You write
Properties and small policy beans: gateway routes, discovery, externalised configuration, circuit-breaker and retry settings.
Spring writes
Client-side load balancing, a gateway, a configuration server and client, circuit breakers and binders for streams, versioned as one release train 22,79.

The plate's inference source is the environment in its most remote form: configuration served from elsewhere, a registry of peers, the health of those peers. Its check is K0. Each service's resilience settings are individually reasonable, and nothing inspects the stack of them. The seventh experiment shows why that matters.

When each of L layers makes three attempts, a failure at the bottom sees 3L times the edge traffic: 3, 9, 27, 81. For a 60-second outage at 100 requests per second through three layers, 162,000 calls reach the failed dependency. Retrying at one layer only cuts that to 18,000, 11.1% of the layered total. A breaker on the lowest client that opens after 100 failures lets through exactly 100, and it opens within the first second. Google's site reliability guidance names retry amplification as a cause of cascading failure and recommends retrying at a single layer 81. Amazon's builders' guidance makes the same argument and adds jitter so that retries do not synchronise 82. Neither recommendation can be expressed as a property on one service. Here the missing check is architectural, and it has to be written by whoever can see all the layers.

11API shape: two answers to the nested view

Spring HATEOAS and Spring for GraphQL both answer one question: how does a client obtain a nested view of related data? They answer it in opposite places, and their plates sit on different rungs and read different sources.

Fielding later insisted that an API which does not use it is not RESTful in his sense, however it uses HTTP 84. Spring HATEOAS supplies the machinery. Spring for GraphQL replaced an earlier, minimal integration and grew through joint work with Spring Boot, Data and Security 28. The eighth experiment counts the cost of a nested view both ways, for a tree with fan-out f and depth d.

Resolving each field for each parent costs one call per node: 111 calls for fan-out 10 at depth 2, 1,111 at depth 3, 8,421 for fan-out 20 at depth 3. Batch loading, the DataLoader technique that collects keys across parents before fetching 86, costs one call per level, 3 and 4. A hypermedia client that follows links without embedding pays the per-node count too, but in HTTP round trips rather than database calls. At 50 ms per sequential round trip, fan-out 10 at depth 2 is 5.55 seconds of latency against 0.05 for one GraphQL request. The two projects place the N+1 problem differently. GraphQL moves it to the server, where Spring's batch mapping can remove it. Hypermedia leaves it on the network, where only embedding or client-side concurrency can reduce it. Neither is wrong. They suit different clients, and the plates' breaks when fields say which.

12Architecture inside one deployable

Spring Modulith applies the portfolio's move one level up, from wiring objects to arranging modules. Its announcement put the parallel directly: Boot has an opinion on an application's technical arrangement, and Modulith has one on how to structure it functionally and how its logical parts should interact 31.

Plate 16

Spring Modulith

You write
Packages. Each direct sub-package of the application's main package is a module.
Spring writes
A model of those modules, verification of their dependencies, module-scoped integration tests, documentation, and a registry that keeps application events until listeners complete 88,89.
Reads
Names: package structure decides what is a module and what is internal to one.
Checked by
A dedicated verification: a test calls verify() and fails on cycles or on references into another module's internals; the Spring Tools now flag the second in the editor 88,90.

The declaration is the package layout. Each direct sub-package of the main package is an application module 88. That is a name-based inference, and like every name-based inference in this survey it comes with a framework-owned check. A test builds the module model and calls verify(), which fails on dependency cycles and on references into another module's internals, and the implementation uses ArchUnit to detect violations 88,89. As of September 2026 the Spring Tools raise the second kind of violation in the editor, as an error on the offending reference 90. The criterion being enforced is fifty years old. Parnas argued in 1972 that modules should hide design decisions likely to change, not steps in a flowchart 91.

The tenth experiment runs the verification on a six-module shop: catalog, customer, inventory, order, payment and shipping. It uses Tarjan's strongly-connected-components algorithm to find cycles 92.

The model finds one cycle, inventory and order depending on each other, and one internal reference, from payment into a sub-package of customer. The cycle is removed without deleting a feature. Order stops calling inventory and publishes an OrderCompleted event, and inventory listens. The listener now depends on the publisher's event type, the direction the dependency already ran, so the cycle disappears and the graph is acyclic. Modulith's event publication registry exists to make that refactoring safe. It persists events until listeners complete, so a crash between publishing and handling does not lose the event 89.

13AI: a callback whose other side is a model

Spring AI is the newest project and the only one whose inference source is the output of another program that is itself probabilistic. It reached 1.0 in May 2025 with a portable chat client, advisors, vector-store abstractions, tool calling, chat memory and support for the Model Context Protocol 32.

Plate 17

Spring AI

You write
A prompt and a call through a fluent client, plus tool methods and a target type for structured output.
Spring writes
Portable model clients, an ordered chain of advisors, the tool-calling loop, conversion of model output into your type, vector stores and MCP servers and clients 5,32.
Reads
Runtime content: what the model returns decides which tools run and whether the output parses.
Checked by

Version 2.0, released on 12 June 2026, is the release that fits this article's thesis most exactly. Its team wrote that in 1.x each chat model contained its own private tool-calling loop, with no way to hook into it. In 2.0 the loop is a component of the advisor chain, which can re-enter the downstream chain 5. The same mechanism drives structured-output retries: a validation advisor asks the model again when its JSON does not conform, even with native structured output enabled. A tool-search advisor exposes tools on demand rather than sending every definition with every request. The release also narrowed the core to a set of providers built on vendor SDKs, adopted Jackson 3 and JSpecify, and brought the MCP integration into the core, on MCP Java SDK 2.0 compliant with the 2025-11-25 specification 5,93. The team also noted that most incoming pull requests now involve coding agents, and rewrote its contributing guide for human and agent readers alike 5.

The eleventh experiment measures what a tool loop costs in context, with a 2,000-token base prompt and 800 tokens per tool call and result.

Each round resends the conversation, so cumulative input grows quadratically in the number of rounds. Three rounds cost 12,800 input tokens over four model calls, eight rounds 46,800 over nine, twelve rounds 88,400 over thirteen. If only the base prompt were sent each time, twelve rounds would cost 26,000. Tool definitions multiply the same way. Anthropic reported a five-server setup at 58 tools and about 55,000 tokens of definitions, with the handful of tools actually discovered for a task at about 3,000 94. Sending the full set on every call adds 495,000 tokens to an eight-round request, against 27,000 with discovery. Lifting the loop into the advisor chain is what lets a Spring application see and limit those costs. The plate's check is runtime containment, because the source is runtime content, and 2.0 is where the containment became something an application can compose.

14The ledger

With all seventeen plates placed, the census can be read as a whole. The first experiment computes it from the placements.

The rung distribution is lopsided. No project sits at D0, three at D1, six at D2, one at D3, four at D4 and three at D5, for a mean rung of 2.88. The annotated method is the portfolio's dominant idiom, as it has been since annotations replaced XML. The two scales together are a good description. Rung alone separates 80.1% of the 136 project pairs, inference source 84.6%, and rung with source 94.1%. Adding the check class raises that to 97.8%. Eleven of the thirty rung-by-source cells are occupied.

The finding is in the columns. Every project that infers from names ships a framework-owned check. Data property-checks at bootstrap, GraphQL inspects its schema at startup, and Modulith verifies its module graph. Every project that infers from runtime content ships runtime containment: AMQP, Kafka and AI. That is six of six. The framework's authors knew that a string or a message could be wrong in ways the compiler cannot see, and built the check the compiler would have been. Projects that infer from types lean on the compiler. Only the container adds a bootstrap failure on top.

The unchecked projects are elsewhere. Four plates carry K0: Security, Authorization Server, Session and Cloud. Two of them read explicit policy, and none of the four explicit-policy projects has a framework-owned check at all. The other two read the environment, where only Boot among three projects ships a report. The mean rung of the K0 group is 4.25, the highest of any check class. The pattern is this: the less Spring infers, the less Spring checks. When you write the rule yourself, Spring has nothing to validate it against, and the failures are policies that work but are wrong. An endpoint open to the wrong caller, a session that should not have left the server, a retry setting that multiplies across services: none of them throws.

That runs against the usual worry about frameworks, which is that magic is dangerous. On this evidence the magic is the best-checked part of the portfolio. Derived queries, schema mappings and package conventions fail loudly at startup, and Boot's conditions report explains itself on request. The quiet failures sit in the explicit, low-inference configuration that developers assume is safe because they wrote it.

15Using the ledger, and its limits

Three practical rules follow from the placements.

First, treat D5 declarations as source code. A dependency list or a package layout is a program when the framework reads it, and Boot 4's move from library presence to starter presence shows the program can change meaning between major versions 41. Review dependency changes as behaviour changes, and keep the conditions report within reach 38.

Second, write the missing checks where the ledger shows a K0. For Security and Authorization Server that means tests that assert who is refused, not only who is admitted. For Session it means a test that round-trips the session through the real store. For Cloud it means a document, owned by someone who sees every layer, that states which layer retries.

Third, let the name-inferred projects check at the earliest point they offer. Enable Spring for GraphQL's schema inspection. Keep a Modulith verification test in the build. Watch Spring Data's move of repository derivation towards build time 53. Framework-owned checks exist in this portfolio exactly where inference is weakest, and they only help when they run.

Method. Each project was coded by the canonical use its own documentation shows first. The rung is what the developer supplies, the source is what the framework reads to complete it, and the check is the strongest mechanism the project provides, not one a user could add. Several codings are arguable. Spring Integration could be read as D1, since its endpoints are callbacks. Spring AI could be read as D3, since a target type declares the shape of the output. Neither change moves a project between check classes, and the headline depends only on the source and check columns. The lab is eleven stdlib-only Python experiments with seed 20260923, run at build time. Its output is byte-identical under three values of PYTHONHASHSEED, and its source and full output are reproduced below. Every number quoted from it is the output of a model, not a benchmark of Spring, and the models are chosen to be simple enough to check by hand. The throughput experiment is validated against a discrete-event simulation, and the Kafka assignment against the reference guide's own example. The batch approximation is compared with simulation and its drift reported.

The survey is a snapshot of September 2026, and the portfolio is moving in the direction its ledger suggests. The newest releases add checks that run earlier: null-safety annotations across the portfolio 35, ahead-of-time repositories 53, editor-time module verification 90, and a validation loop around model output 5. The plates most likely to look different in a year are the ones marked with an open circle.

def camel_split(s):

def lcfirst(s): return s[:1].lower()+s[1:]
def resolve(expr, dom):
    """Spring Data property-expression traversal: try the whole expression, then split the
    camel-case parts from the right into head and tail and recurse (documented algorithm)."""
    trace = []
    def go(e, d, prefix):
        cand = lcfirst(e); trace.append(prefix+cand)
        if cand in d: return prefix+cand, d[cand]
        parts = camel_split(e)
        for cut in range(len(parts)-1, 0, -1):
            head = lcfirst("".join(parts[:cut])); tail = "".join(parts[cut:])
            trace.append(prefix+head+"."+lcfirst(tail))
            if head in d and isinstance(d[head], dict):
                r = go(tail, d[head], prefix+head+".")
                if r: return r
        return None
    r = go(expr, dom, "")
    seen = []
    for x in trace:
        if x not in seen: seen.append(x)
    return r, seen
def derive(name):
    import re
    m = re.match(r"^(find|read|get|query|count|exists|delete)(.*?)By(.*)$", name)
    if not m: return None, "no subject"
    verb, subj, crit = m.groups()
    order = None
    if "OrderBy" in crit:
        crit, order = crit.split("OrderBy", 1)
    distinct = "Distinct" in subj
    limit = None
    mm = re.search(r"(Top|First)(\d*)", subj)
    if mm: limit = int(mm.group(2) or 1)
    ors = crit.split("Or") if crit else []
    clauses, idx, props_used = [], 1, 0
    for o in ors:
        ands = o.split("And"); sub = []
        for a in ands:
            kw = next(((k,n,t) for k,n,t in KW if a.endswith(k) and len(a)>len(k)), None)
            prop = a[:-len(kw[0])] if kw else a
            ( r, trace ) = resolve(prop, DOMAIN)
            if r is None:
                return None, f"No property '{lcfirst(prop)}' found for type 'Person' (tried {len(trace)} paths)"
            path = "x."+r[0]; props_used += 1
            if kw is None: kw = ("",1,"{p} = ?{i}")
            sub.append(kw[2].format(p=path, i=idx, j=idx+1)); idx += kw[1]
        clauses.append(" and ".join(sub))
    q = ("select count(x)" if verb=="count" else "select distinct x" if distinct else "select x") + " from Person x"
    if clauses: q += " where " + " or ".join(clauses)
    if order:

        q += " order by " + ", ".join(f"x.{resolve(p, DOMAIN)[0][0]} {d.lower()}" for p,d in segs)
    if limit: q += f"  [limit {limit}]"
    return q, props_used

def range_assign(consumers, topics):
    a = {c: [] for c in consumers}
    for t, n in topics:
        cs = sorted(consumers); per, extra = divmod(n, len(cs)); p = 0
        for i, c in enumerate(cs):

            a[c] += [(t, j) for j in range(p, p+k)]; p += k
    return a
def rr_assign(consumers, topics):
    a = {c: [] for c in consumers}
    tps = sorted((t, j) for t, n in topics for j in range(n))

    for i, tp in enumerate(tps): a[cs[i % len(cs)]].append(tp)
    return a

def tarjan(nodes, edges):
    idx = {}; low = {}; st = []; on = set(); out = []; c = [0]
    adj = {n: [b for a,b in edges if a == n] for n in nodes}
    def sc(v):
        idx[v] = low[v] = c[0]; c[0] += 1; st.append(v); on.add(v)
        for w in adj[v]:
            if w not in idx: sc(w); low[v] = min(low[v], low[w])
            elif w in on: low[v] = min(low[v], idx[w])
        if low[v] == idx[v]:
            comp = []
            while True:
                w = st.pop(); on.discard(w); comp.append(w)
                if w == v: break
            out.append(sorted(comp))
    for n in nodes:
        if n not in idx: sc(n)
    return out
