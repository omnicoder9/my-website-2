Encryption hides what a message says; it does not, by itself, stop anyone from changing it. Flip one bit of an AES-CTR or ChaCha20 ciphertext and the same bit flips in the decrypted plaintext, with no error raised. The tools in this article supply what encryption lacks. A message authentication code (MAC) lets the holder of a secret key prove that data came from another key holder and has not been altered.[1,2] Behind every MAC sits a pseudorandom function (PRF), the most useful abstraction in symmetric cryptography, which also powers key derivation functions (KDFs) that stretch one secret into many independent keys.[3,4] And all of them consume keys that must come from a random number generator nobody can predict, which is where real systems most often fail.[5,6]

The four parts depend on each other. A TLS 1.3 connection shows how: an ephemeral Diffie–Hellman key share is generated from the operating system's CSPRNG, the shared secret is turned into traffic keys by HKDF (a KDF built from the HMAC PRF), and every record is protected by an AEAD whose integrity half is a universal-hash MAC (GMAC inside AES-GCM, or Poly1305).[7–9]

Companion articles. Hash functions, length extension and password hashing are covered in Cryptographic Hash Functions; AES, GCM and ChaCha20 in Symmetric-Key Cryptography; security games, EUF-CMA and reductions in Cryptographic Security Theory; finite fields, min-entropy and the birthday paradox in Mathematical Foundations.
Notation. K is a secret key, M a message, T a tag; ‖ is concatenation and ⊕ XOR; {0,1}n is the set of n-bit strings; x ←$ S means x is drawn uniformly from S; [i]32 is the integer i as a 32-bit big-endian string; q counts an adversary's queries and Adv is its advantage.

1. Message authentication codes

1.1 MAC fundamentals

A MAC scheme is a pair of efficient algorithms that share a key K drawn from a key space:[1,10]

  • MacK(M) → T, the tagging algorithm (possibly randomized or nonce-based);
  • VrfyK(M, T) → accept / reject, the verification algorithm, with correctness: VrfyK(M, MacK(M)) always accepts.

For a deterministic MAC, verification is canonical: recompute MacK(M) and compare with the received tag. The sender transmits (M, T); the receiver accepts the message only if the tag verifies. A MAC provides data-origin authentication and integrity, but not confidentiality (the message travels in the clear unless also encrypted) and not non-repudiation: both parties hold the same key, so either could have made the tag, and a third party cannot tell which. Non-repudiation needs digital signatures.[1,2]

MACs are everywhere: the HMAC in a JSON Web Token or an AWS API signature, the CMAC protecting payment-card messages, the GMAC tag on every AES-GCM packet, the Poly1305 tag on every WireGuard packet, IPsec's integrity transforms, and the authentication tag of every AEAD.[8,11–13] The history goes back further: the ANSI X9.9 and FIPS 113 “data authentication algorithm”, a CBC-MAC over DES, protected banking messages from the 1980s.[2,14]

1.2 Authentication tags

The tag (or MAC value, or “MIC” in some IEEE standards) is a short fixed-length string, typically 64 to 256 bits. Its length t sets a hard ceiling on security: an adversary who guesses a tag uniformly at random succeeds with probability 2−t per verification attempt, so a system that allows v attempts can be forged with probability about v·2−t, independent of how strong the key is.[8,15]

1.3 MAC security requirements

The standard definition is existential unforgeability under adaptive chosen-message attack (EUF-CMA), adapted from Goldwasser, Micali and Rivest's notion for signatures.[20,21] The game (Figure 2): a key is chosen at random; the adversary may ask a tagging oracle for the tag of any messages it likes, adaptively; it wins if it outputs a pair (M*, T*) that verifies and where M* was never queried. The MAC is secure if every efficient adversary wins with only negligible probability. “Existential” means the adversary picks the message: even forging a tag for gibberish counts as a break.[1,10]

Several refinements matter in practice:

  • Strong unforgeability (SUF-CMA): producing a new tag for a previously queried message also counts as a forgery. Deterministic MACs with canonical verification are automatically strong; randomized ones need not be. Strong unforgeability is what Encrypt-then-MAC needs to give a CCA-secure AEAD.[22]
  • Replay is outside the definition. A MAC accepts a perfect copy of an old (M, T). Protocols add sequence numbers, timestamps or nonces inside the authenticated data (TLS uses an implicit 64-bit record sequence number).[1,7]
  • Every bit that matters must be authenticated: headers, lengths, algorithm identifiers and the associated data of an AEAD. Anything left out can be changed without detection.[11]
  • PRF security is stronger and often assumed. Any secure PRF with a long enough output is a secure MAC (§2.6), and HKDF and TLS rely on HMAC being a PRF, not just unforgeable.[4,23]
  • Key independence. The MAC key must not be reused for encryption or any other purpose; SP 800-57 requires a key to have a single purpose (see §3.6).[24]

1.4 HMAC

The naive keyed hash H(K ‖ M) is insecure for Merkle–Damgård hashes such as SHA-256: from H(K ‖ M) and the length of K ‖ M, anyone can compute H(K ‖ M ‖ pad ‖ M′) by continuing the hash from its output state. This length-extension attack broke Flickr's API signatures in 2009.[25] (See the hash functions article for a worked example.) HMAC, designed by Bellare, Canetti and Krawczyk in 1996, avoids the problem with two nested hash passes:[16,26,27]

K₀ = K padded with zeros to the block size B (if |K| > B, first K := H(K)) HMAC(K, M) = H( (K₀ ⊕ opad) ‖ H( (K₀ ⊕ ipad) ‖ M ) ) ipad = 0x36 repeated B times, opad = 0x5c repeated B times

Security. The original proof assumed the compression function is a PRF and the iterated hash is weakly collision-resistant. Bellare's 2006 proof removed the collision-resistance requirement: HMAC is a PRF if the compression function is a PRF under a mild related-key assumption.[23,26] This is why HMAC-MD5 and HMAC-SHA-1 were never broken in practice even after collisions were found for MD5 and SHA-1, though new designs should use SHA-2 or SHA-3.[17,23]

Keys. The key should be at least as long as the hash output (32 bytes for HMAC-SHA-256) and random. Keys longer than B are hashed first, which creates a quirk: the long key K and the short key H(K) give identical HMACs. The ASCII string plnlrtfpijpuhqylxbgqiiyipieyxvfsavzgxbbcfusqkozwpngsyejqlmjsytrmd has a SHA-1 hash that happens to be printable, eBkXQTfuBqp'cTcar&g*, so these two “passwords” are equivalent in HMAC-SHA-1 and PBKDF2-HMAC-SHA-1 (verified in §5.3). It is harmless for random keys, but it shows that HMAC is not injective in its key.[16,28]

Worked example (RFC 4231, test case 2). Key "Jefe", message "what do ya want for nothing?", HMAC-SHA-256 = 5bdcc146bf60754e6a042426089575c7 5a003f089d2739839dec58b964ec3843.[29] Section 5 reproduces it with the standard library and from scratch.

NMAC and HMAC in protocols. HMAC is the PRF of HKDF, TLS 1.2's PRF, PBKDF2, IKEv2, HMAC_DRBG, JWT's HS256, the TOTP/HOTP one-time-password algorithms and AWS Signature Version 4.[11,12,30–32]

1.5 CBC-MAC

CBC-MAC runs a block cipher in CBC mode with a zero IV and outputs only the last ciphertext block:[21,33]

T₀ = 0ⁿ, Tᵢ = E_K(Tᵢ₋₁ ⊕ Mᵢ) for i = 1..ℓ, CBC-MAC_K(M) = T_ℓ

Bellare, Kilian and Rogaway proved it a secure PRF for messages of one fixed length (more generally for any prefix-free message set), with advantage roughly q2ℓ2/2n for q queries of ℓ blocks.[21] With variable-length messages it is trivially forgeable. Given the tag T of a one-block message M, the two-block message M ‖ (M ⊕ T) has tag EK(T ⊕ M ⊕ T) = EK(M) = T.[1,10]

Fixes include prepending the message length (provably secure but needs the length up front), EMAC/ECBC (encrypt the CBC-MAC output under a second key), Black and Rogaway's three-key XCBC, and Iwata and Kurosawa's one-key OMAC, which NIST standardised as CMAC.[33–35] CBC-MAC with a random or non-zero IV is also insecure, because the IV can be modified to change the first block. The CCM mode uses CBC-MAC safely because it encodes the length and nonce into the first block.[10]

1.6 CMAC

CMAC (NIST SP 800-38B, RFC 4493 for AES) is OMAC1: CBC-MAC with a final-block tweak that makes it secure for arbitrary lengths using a single key.[15,35,36] Two subkeys are derived by “doubling” in GF(2128):

L = E_K(0¹²⁸) K1 = L·x = (L ≪ 1) ⊕ (msb(L) ? 0x87 : 0) (0x87 encodes x⁷+x²+x+1) K2 = K1·x = (K1 ≪ 1) ⊕ (msb(K1) ? 0x87 : 0)

If the final block is complete it is XORed with K1; otherwise it is padded with 10…0 and XORed with K2. Then plain CBC-MAC runs. The different masks keep a padded message and an unpadded one from colliding, and the secret mask on the final block defeats the splicing forgery.[15,35]

Worked example (RFC 4493). With AES-128 key 2b7e1516 28aed2a6 abf71588 09cf4f3c: K1 = fbeed618 35713366 7c85e08f 7236a8de, K2 = f7ddac30 6ae266cc f90bc11e e46d513b; the tag of the empty message is bb1d6929 e9593728 7fa37d12 9b756746 and the tag of the block 6bc1bee2 2e409f96 e93d7e11 7393172a is 070a16b4 6b4d4144 f79bdd9d d04a287c.[36] CMAC is used in IPsec (AES-CMAC-96), in banking key-check values, in NFC/MIFARE DESFire, and as the PRF in SP 800-108 KDFs.[36,37] Its security bound degrades as about q2ℓ2/2128, so SP 800-38B suggests limiting AES-CMAC to about 248 messages per key.[15]

1.7 Universal hashing and Carter–Wegman MACs

A family of hash functions {hk} is ε-almost universal (ε-AU) if for all distinct M ≠ M′, Prk[hk(M) = hk(M′)] ≤ ε; it is ε-almost XOR-universal (ε-AXU) if Prk[hk(M) ⊕ hk(M′) = Δ] ≤ ε for every Δ (and ε-AΔU with subtraction in place of XOR).[38,39] These are combinatorial properties: they hold information-theoretically and need no computational assumption, and such hashes can be very fast.

Wegman and Carter (1981) built a MAC from a universal hash and a one-time pad: T = hk(M) ⊕ r with fresh random r per message.[40] Replace the pad with a PRF of a nonce and you get the Carter–Wegman MAC used in practice:[10,41]

T = h_k(M) ⊕ F_K'(N) (N a nonce, never repeated under K') Pr[forgery per attempt] ≤ ε + Adv_PRF(F)

The classic example is polynomial evaluation: split M into field elements m1, …, mℓ and compute hk(M) = Σ mikℓ−i+1. Two different messages give two different polynomials whose difference, of degree ≤ ℓ, has at most ℓ roots, so ε ≤ ℓ/|F|.[10,41] GMAC evaluates this polynomial in GF(2128); Poly1305 in the prime field modulo 2130−5. Other members of the family include UMAC/VMAC (built on NH hashing) and Krawczyk's LFSR-based Toeplitz hashing.[39,42]

The nonce is load-bearing. If two messages are tagged with the same nonce, the attacker can XOR the tags to cancel the pad and obtain hk(M) ⊕ hk(M′), an equation in the hash key. For polynomial hashes that equation can be solved for k, after which universal forgery is possible. This is Joux's “forbidden attack” on GCM, and it was found in practice on the public internet.[43,44]

1.8 GMAC

GMAC is the authentication-only specialisation of Galois/Counter Mode: GCM with an empty plaintext, so all data is “additional authenticated data”.[8,45] The hash key is H = EK(0128), and GHASH evaluates a polynomial in H over GF(2128) defined by x128 + x7 + x2 + x + 1:

S = GHASH_H(A ‖ pad ‖ [len(A)]₆₄ ‖ [0]₆₄) with Yᵢ = (Yᵢ₋₁ ⊕ Xᵢ) · H T = MSB_t( E_K(J₀) ⊕ S ) J₀ = IV ‖ 0³¹1 for a 96-bit IV

GMAC is very fast on CPUs with carry-less multiplication (PCLMULQDQ, ARMv8 PMULL), and is a standard IPsec integrity transform. Its weaknesses are those of all polynomial Carter–Wegman MACs: IV reuse leaks H, and short tags allow Ferguson-style key recovery.[8,19,43] When nonces cannot be guaranteed unique, use a misuse-resistant mode such as AES-GCM-SIV, whose POLYVAL hash is GHASH with a byte-reversed convention, or a PRF-based MAC such as HMAC or CMAC.[46]

1.9 Poly1305

Poly1305, designed by Bernstein (2005), is a one-time authenticator: a polynomial-evaluation universal hash modulo the prime p = 2130 − 5 plus a one-time pad.[47] RFC 8439 defines it with a 32-byte one-time key (r, s):[9]

r = clamp(key[0:16]) (clear the top 4 bits of bytes 3,7,11,15 and the low 2 bits of bytes 4,8,12) acc = 0 for each 16-byte chunk c (the last may be shorter): n = little-endian(c ‖ 0x01) # the appended 1 makes lengths unambiguous acc = (acc + n) · r mod 2¹³⁰−5 tag = (acc + s) mod 2¹²⁸ # s = key[16:32]

The clamping (22 fixed bits in r, leaving 106 free) makes fast implementations with 26-bit or 64-bit limbs possible without overflow. Bernstein's bound: for messages of at most L bytes, each forgery attempt succeeds with probability at most 8⌈L/16⌉/2106, plus the advantage of distinguishing the pad generator from random.[47]

Worked example (RFC 8439 §2.5.2). Key 85d6be78 57556d33 7f4452fe 42d506a8 0103808a fb0db2fd 4abff6af 4149f51b, message "Cryptographic Forum Research Group" (34 bytes, so three chunks), tag a8061dc1 305136c6 c22b8baf 0c0127a9.[9] The from-scratch implementation in §5.2 is eleven lines of Python.

Never reuse a Poly1305 key. Two messages under the same (r, s) give two equations from which r and s can be recovered by polynomial root-finding. That is why the stand-alone Poly1305 APIs in libsodium and pyca/cryptography say the key must be used for one message only.[48,49]

1.10 Keyed BLAKE2, KMAC and other hash-native MACs

HMAC's double hashing exists to repair Merkle–Damgård. Newer hash designs are not vulnerable to length extension and offer a native keyed mode, which is faster and simpler:[18,50]

  • Keyed BLAKE2. BLAKE2b accepts a key of up to 64 bytes (BLAKE2s: 32). The key length goes into the parameter block, and the key, zero-padded to a full 128-byte block, is processed as the first message block; the finalisation flag on the last block prevents extension. The result is a PRF and MAC in a single pass: hashlib.blake2b(msg, key=k, digest_size=32). The digest size is also in the parameter block, so different-length outputs are unrelated.[18,51] WireGuard uses keyed BLAKE2s for its MAC1/MAC2 cookie fields and HMAC-BLAKE2s inside its HKDF.[13]
  • BLAKE3 has a dedicated keyed_hash mode with a 32-byte key and a separate derive_key mode with a context string.[52]
  • KMAC128 / KMAC256 (NIST SP 800-185) is the SHA-3 family's MAC: cSHAKE with function name "KMAC", a customization string and the encoded key prepended. The output length is encoded too, and KMACXOF variants give arbitrary-length output. Because a sponge's capacity is never output, the simple prefix construction is sound.[50]
  • SipHash is a fast short-input PRF with a 128-bit key, designed for hash-table DoS protection; it is the default string hash in Python, Rust and many other runtimes, but its 64-bit output makes it unsuitable as a general MAC.[53]

1.11 MAC verification

Most real MAC failures happen in verification, not in the primitive.

  1. Compare in constant time. A byte-by-byte comparison that returns at the first mismatch leaks how many leading bytes are correct; an attacker who can time responses can forge a tag byte by byte with about 256·t/8 attempts instead of 2t. Nate Lawson reported exactly this bug in Google's Keyczar library in 2009, and Crosby et al. showed remote timing differences of tens of microseconds are measurable over the internet, and of a few hundred nanoseconds over a LAN.[54,55] Use hmac.compare_digest (Python), crypto/subtle.ConstantTimeCompare (Go), CRYPTO_memcmp (OpenSSL) or sodium_memcmp.[48,56]
  2. Verify before you use. Do not parse, decrypt, decompress or act on data until the tag has verified. For AEADs, release no plaintext from a message whose tag fails, and return a single generic error.[7,57]
  3. Authenticate exactly what you interpret. Compute the MAC over an unambiguous encoding (length-prefixed fields, canonical JSON) and verify the bytes received, not a re-serialisation. Ambiguous concatenation such as "user=ali" ‖ "ce&role=user" versus "user=alice&" ‖ "role=user" lets different field values share a tag.[11]
  4. Never let the message choose the algorithm. JWT libraries that honoured "alg": "none", or accepted an RSA public key as an HMAC secret, let attackers forge tokens; RFC 8725 requires the verifier to fix the allowed algorithms.[11]
  5. Check the tag length. An implementation that compares only min(len(received), len(expected)) bytes accepts a one-byte, or empty, tag.
  6. Limit and monitor failures when tags are short, and reject replays with sequence numbers or a nonce cache.[8]

A belt-and-braces alternative to constant-time comparison is double HMAC verification: compare HMAC(K′, T) with HMAC(K′, Texpected) under a fresh random key K′, so any timing leak concerns values the attacker cannot predict.

2. Pseudorandom generators, functions and permutations

MACs, KDFs, stream ciphers, block-cipher modes and DRBGs are all proved secure by reduction to three idealised objects. Each is defined by indistinguishability: no efficient algorithm can tell the real object from a truly random one with more than negligible advantage.[1,10,58] (The game-based method itself is covered in the security theory article.)

2.1 Pseudorandom generators (PRGs)

A PRG is a deterministic, efficient function G: {0,1}s → {0,1}ℓ with ℓ > s such that G(seed) for a uniform seed is computationally indistinguishable from a uniform ℓ-bit string:[1,59,60]

Adv_PRG(𝒟) = | Pr[𝒟(G(s)) = 1 : s ←$ {0,1}ˢ] − Pr[𝒟(r) = 1 : r ←$ {0,1}^ℓ] |
  • It cannot be statistically random. G has at most 2s outputs among 2ℓ strings, so an unbounded distinguisher wins; security is purely computational.[1]
  • Next-bit unpredictability is equivalent. Yao showed that a generator passes all polynomial-time statistical tests if and only if no efficient algorithm can predict bit i+1 from bits 1…i with probability noticeably better than ½.[59]
  • Existence. Blum and Micali built a PRG from the hardness of discrete logarithms using a hard-core predicate; Blum, Blum and Shub from quadratic residuosity (the BBS generator xi+1 = xi2 mod N, outputting low-order bits); and Håstad, Impagliazzo, Levin and Luby proved that a PRG exists if and only if a one-way function does.[60–62]
  • Expansion is free. A PRG that stretches by one bit can be iterated to stretch by any polynomial amount; this is a classic hybrid argument.[1,58]

In practice, PRGs are stream ciphers (ChaCha20 keyed by the seed) or block ciphers in counter mode, which is exactly how CTR_DRBG and the Linux kernel CSPRNG produce output (§4.4).[32,63]

2.2 Pseudorandom functions (PRFs)

A PRF is a keyed function family F: 𝒦 × {0,1}m → {0,1}n such that an adversary with oracle access cannot tell FK(·), for random secret K, from a function chosen uniformly from all 2n·2m functions.[3,21] A PRF looks like a giant random table: every new input gives an independent-looking uniform output, even to an adversary that picks inputs adaptively. That is far stronger than a PRG, whose output the adversary sees only once.

Goldreich, Goldwasser and Micali (GGM, 1986) showed PRFs exist whenever PRGs do. Take a length-doubling PRG G(s) = G0(s) ‖ G1(s) and walk a binary tree: FK(x1…xm) = Gxm(…Gx2(Gx1(K))…).[3]

The GGM tree is slow but conceptually important: it underlies puncturable and constrained PRFs and every hierarchical key-derivation scheme (§3.9). In practice, PRFs are HMAC, CMAC, keyed BLAKE2, KMAC, and block ciphers used as PRFs via the switching lemma.[23,35,37]

2.3 Pseudorandom permutations (PRPs)

A PRP is a keyed family of permutations EK: {0,1}n → {0,1}n, efficiently invertible given K, that is indistinguishable from a uniformly random permutation. A strong PRP (super-pseudorandom permutation) remains indistinguishable even when the adversary may also query the inverse EK−1. Block ciphers such as AES are conjectured strong PRPs; that is the formal meaning of “AES is secure”.[1,64,65]

Luby and Rackoff (1988) proved that PRPs can be built from PRFs using the Feistel network: three rounds with independent PRF round functions give a PRP, and four rounds give a strong PRP.[64]

2.4 PRF distinguishability

Formally, a distinguisher 𝒟 gets an oracle 𝒪 that is either FK (world 1) or a random function f (world 0), makes q queries in time t, and outputs a bit. Its PRF advantage is[21,66]

Adv_F^prf(𝒟) = | Pr[𝒟^{F_K(·)} = 1] − Pr[𝒟^{f(·)} = 1] |

and F is a (t, q, ε)-secure PRF if every such 𝒟 has advantage at most ε. Two generic attacks bound what is possible for any PRF:[1,10]

  • Key search: try keys and check consistency with the oracle; advantage about t/2k for a k-bit key.
  • Output collisions for PRPs: a block cipher never repeats an output, while a random function does after about 2n/2 queries. This is the reason 64-bit block ciphers are unsafe for bulk data: the Sweet32 attack recovered HTTP cookies from 3DES- and Blowfish-encrypted sessions after about 232 blocks (785 GB in the HTTPS experiment).[67]

The real/random experiment is the right notion for keys too: a key-derivation output is “good” when it is indistinguishable from a uniformly random key of the same length, even given the context and all other derived keys.[4]

2.5 The PRP/PRF switching lemma

Proofs about CTR mode, GCM and CMAC model the block cipher as a random function because independence is easier to reason about, then pay a price for the substitution. The switching lemma states that for any adversary making q queries to an oracle on n-bit strings,[65,68]

| Pr[𝒜^{π} = 1] − Pr[𝒜^{f} = 1] | ≤ q(q − 1) / 2ⁿ⁺¹ (π random permutation, f random function) ⇒ Adv^prf_E(𝒜) ≤ Adv^prp_E(𝒜) + q(q − 1) / 2ⁿ⁺¹

Proof sketch. A random function and a random permutation answer identically until the function produces its first repeated output. The probability of any repeat among q uniform n-bit values is at most C(q,2)/2n by the union bound: the birthday bound. Bellare and Rogaway's code-based game-playing proof makes this rigorous and points out a flaw in a frequently cited earlier proof.[68]

For AES (n = 128) and q = 248 blocks the term is about 2−33, negligible; at q = 264 it is about ½. Concrete-security guidance on how much data to process under one key comes straight from bounds like this one.[8,65]

3. Key derivation functions

3.1 KDF fundamentals

A key derivation function takes some input keying material (IKM) and produces one or more cryptographic keys. Inputs differ wildly in quality, and that decides which KDF to use:[4,37,69]

Uniform key → keys

The input is already a full-entropy secret (a master key, a TLS traffic secret). Only expansion is needed: a PRF keyed with the input, evaluated on labels. NIST SP 800-108 KDFs and HKDF-Expand.[30,37]

High-entropy but non-uniform → keys

A Diffie–Hellman shared secret gxy or a hardware entropy sample: plenty of min-entropy but not uniform bits. First extract a uniform key, then expand. HKDF, SP 800-56C.[4,69]

Low-entropy password → key

A password has perhaps 20–40 bits of entropy; no KDF can add more. A password-based KDF adds a salt and a deliberate work factor so each guess is expensive: PBKDF2, scrypt, Argon2.[31,70]

The security requirement, in Krawczyk's formalisation, is that the output be indistinguishable from uniform even to an adversary who knows the salt and context, has partial knowledge of the input, and has seen the KDF's output on other contexts.[4] A good KDF also gives independence (learning one derived key reveals nothing about another) and one-wayness (a derived key does not reveal the input).

3.2 The extract-and-expand construction

Krawczyk's 2010 paper argued that a KDF should be designed in two stages with different goals, and proved HMAC suitable for both:[4,71]

  1. Extract: condense IKM with min-entropy m into a short pseudorandom key PRK. This is a randomness extractor (§4.7), keyed by a public, ideally random salt. With a random salt, extraction can rely on HMAC as a computational extractor rather than modelling it as a random oracle.
  2. Expand: use PRK as a PRF key and generate as many output bits as needed, bound to an info string that names the purpose and context.

NIST adopted the same two-step structure in SP 800-56C (“two-step key derivation”), allowing HMAC or AES-CMAC for extraction and any SP 800-108 KDF for expansion, alongside a one-step option that hashes the shared secret with a counter and FixedInfo.[69]

3.3 HKDF

HKDF-Extract(salt, IKM) = HMAC-Hash(salt, IKM) = PRK (salt defaults to HashLen zero bytes) HKDF-Expand(PRK, info, L): T(0) = empty; T(i) = HMAC-Hash(PRK, T(i−1) ‖ info ‖ [i]₈) for i = 1..⌈L/HashLen⌉ OKM = first L bytes of T(1) ‖ T(2) ‖ …

Practical notes from RFC 5869 and its users:[4,30]

  • Salt. A random salt strengthens the extraction guarantee and gives independent results for repeated IKM, but it need not be secret, and HKDF remains useful without one. The salt must not be attacker-controlled in a way that depends on the IKM.
  • Info. Put everything that distinguishes this key in info: protocol name and version, key purpose, party identities, transcript hash. Different info values give independent keys from the same PRK.
  • Output length is at most 255 × HashLen bytes (8160 bytes for SHA-256), because the counter is a single byte.
  • Expand-only use is fine when the input is already uniform (TLS 1.3 does this for every secret after the first extraction).

Worked example (RFC 5869 test case 1, SHA-256). IKM = 22 bytes of 0x0b, salt = 000102…0c, info = f0f1…f9, L = 42:[30]

PRK = 077709362c2e32df0ddc3f0dc47bba6390b6c73bb50f9c3122ec844ad7c2b3e5 OKM = 3cb25f25faacd57a90434f64d0362f2a2d2d0a90cf1a5a4c5db02d56ecc4c5bf34007208d5b887185865

HKDF in TLS 1.3. The key schedule alternates HKDF-Extract, which mixes in a new secret (PSK, then the (EC)DHE shared secret, then zero), with Derive-Secret, which is HKDF-Expand-Label(Secret, Label, Transcript-Hash(Messages), Hash.length). Every label is prefixed with "tls13 ", for example "c hs traffic", "s ap traffic", "derived" and "key"/"iv".[7] With no PSK, the early secret is HKDF-Extract(0, 032) = 33ad0a1c…f170f92a for SHA-256, as published in the RFC 8448 example traces and reproduced in §5.5.[72] HKDF is also used in Signal, the Noise framework, WireGuard (with HMAC-BLAKE2s), HPKE, QUIC and MLS.[13,73–75]

3.4 PBKDF2

PBKDF2, from PKCS #5 v2.0 (RFC 2898, 2000) and now RFC 8018, derives keys from passwords by iterating a PRF, normally HMAC, c times per output block:[31,76]

DK = T₁ ‖ T₂ ‖ … (truncated to dkLen) Tᵢ = U₁ ⊕ U₂ ⊕ … ⊕ U_c U₁ = PRF(P, S ‖ [i]₃₂), U_j = PRF(P, U_{j−1})
  • Salt (at least 128 bits per SP 800-132, randomly generated) ensures equal passwords give different keys and defeats precomputed tables.[77]
  • Iteration count c makes each guess cost c HMAC evaluations. SP 800-132 (2010) required at least 1000 and recommended as many as feasible; OWASP's 2025 guidance is 600 000 for PBKDF2-HMAC-SHA-256, 220 000 for SHA-512, and 1 400 000 for legacy SHA-1.[77,78]
  • Weakness. PBKDF2 needs negligible memory, so GPUs and ASICs compute it massively in parallel. Memory-hard functions (scrypt, Argon2id) are preferred for password storage, and OWASP lists Argon2id first; PBKDF2 remains the choice when FIPS-approved algorithms are required.[70,78,79]
  • Multi-block cost asymmetry. Each output block costs a full c iterations, but an attacker only needs to compute the first block to test a guess. Asking PBKDF2-HMAC-SHA-1 for 32 bytes (two blocks) doubles the defender's cost but not the attacker's; derive one block and expand it with HKDF instead.[10]

Test vector (RFC 6070): P = "password", S = "salt", c = 1, dkLen = 20, PBKDF2-HMAC-SHA-1 = 0c60c80f961f0e71f3a9b524af6012062fe037a6; with c = 4096 it is 4b007901b765489abead49d926f721d065a429c1.[80] Password hashing in depth (bcrypt, scrypt, Argon2 parameters, peppers, migration) is in the hash functions article.

3.5 NIST SP 800-108 KDFs

SP 800-108 Rev. 1 specifies key-based KDFs (KBKDFs) for deriving keys from an existing key KIN using HMAC, CMAC or (since Rev. 1) KMAC as the PRF. Each iteration feeds the PRF a counter and/or chaining value plus fixed input data, typically Label ‖ 0x00 ‖ Context ‖ [L]32, where L is the output length in bits.[37]

Points worth knowing:[37]

  • Including [L] in every PRF input ensures that asking for 128 bits and asking for 256 bits do not give one output as a prefix of the other, which matters when one party can choose the length.
  • Rev. 1 added guidance against key-control attacks with CMAC: if an attacker can choose fixed input data, CMAC's linear structure can let it influence the derived key; feeding K0 = PRF(KIN, fixed data) into each block counters this.
  • HKDF-Expand is essentially SP 800-108 feedback mode with HMAC and an 8-bit counter after the info, which is why SP 800-56C accepts it.[30,69]

§5.5 implements counter mode and checks it against pyca/cryptography's KBKDFHMAC.

3.6 Key separation

Key separation is the rule that each key has exactly one purpose: one algorithm, one direction, one role. NIST SP 800-57 states that a key should be used for only one purpose (encryption, integrity, key wrapping, signature, and so on), because reuse can weaken the security of either purpose and enlarges the damage when the key is exposed.[24] Classic failures include:

  • Using the same key for CBC encryption and CBC-MAC: the MAC tag becomes the last ciphertext block, and simple attacks then forge.[1,2]
  • Using one key in both directions of a connection, enabling reflection attacks where a message is sent back to its sender. TLS 1.3 derives separate client and server traffic secrets.[7]
  • Using one RSA key pair for both signing and decryption, so a decryption oracle doubles as a signing oracle.[24]

KDFs make separation cheap: keep one master secret, derive Kenc, Kmac, Kc→s, Ks→c with different labels, and never use the master directly.[30,37]

3.7 Context binding

Context binding means including in the KDF input everything that identifies the session in which the key will be used: the identities of both parties, their roles, the negotiated algorithms, nonces, and ideally a hash of the whole handshake transcript. Two parties then derive the same key only if they agree on that context, which defeats unknown-key-share, cross-protocol and downgrade attacks.[7,37,69]

  • SP 800-56C's FixedInfo and SP 800-108's Context carry party identifiers and nonces.[37,69]
  • TLS 1.3 feeds Transcript-Hash(ClientHello…) into every Derive-Secret; TLS 1.2 added the same idea later as the Extended Master Secret.[7]
  • HPKE binds the KEM output, the KEM's encapsulated key, the recipient public key, the mode and the suite identifiers into its key schedule.[75]
Rule of thumb. If changing a value would change what the key protects or who shares it, put that value in info/Context. Encode it unambiguously, with length prefixes or fixed-width fields.

3.8 Domain separation

Domain separation is the general technique of making the inputs of one function, used for several purposes, provably disjoint, so that one use cannot be mistaken for, or exploited through, another.[81] It is the mechanism behind key separation and context binding, and it applies to hashes as well as KDFs:

  • Distinct labels or prefixes per use: TLS 1.3's "tls13 c hs traffic" vs "tls13 s hs traffic"; Signal's Double Ratchet derives the message key as HMAC(chain key, 0x01) and the next chain key as HMAC(chain key, 0x02).[7,73]
  • Customisation strings built into the primitive: cSHAKE and KMAC take a function name N and customisation S; BLAKE2 has a personalisation field; BLAKE3's derive_key takes a hard-coded context string.[18,50,52]
  • Prefix-free encodings so that no input for one purpose is a prefix or reinterpretation of another, as with the length fields in HkdfLabel and TupleHash.[7,50]

Bellare, Davis and Günther found that several NIST post-quantum KEM submissions derived several random oracles from one hash without proper separation, and showed that such oracle-cloning mistakes can lead to practical attacks.[81] The hash functions article covers hash-level domain separation in detail.

3.9 Hierarchical key derivation

Applying a KDF repeatedly produces a key tree: each node is derived from its parent and a label. Compromise of a node exposes its subtree but nothing above or beside it, and any node can be recomputed from the root on demand, so only the root needs secure storage.[3,37]

Hierarchies in the wild:

  • TLS 1.3 key schedule: early secret → handshake secret → master secret, each branching into traffic secrets, exporter and resumption secrets; traffic keys are later updated by HKDF-Expand-Label(secret, "traffic upd", "", L), giving forward secrecy within a connection.[7]
  • Signal's Double Ratchet: a root chain advanced by each new Diffie–Hellman output, sending and receiving chains advanced per message, and one-time message keys; old keys are deleted, giving forward secrecy and post-compromise security.[73]
  • AWS Signature Version 4: kDate = HMAC("AWS4" ‖ secret, date), kRegion = HMAC(kDate, region), kService = HMAC(kRegion, service), kSigning = HMAC(kService, "aws4_request"). A leaked signing key is valid for one day, one region and one service only.[12]
  • BIP-32 hierarchical deterministic wallets: master key and chain code = HMAC-SHA512("Bitcoin seed", seed); children are derived with an index, where indices ≥ 231 are “hardened” (derived from the private key, so a leaked child private key plus the parent public key cannot reveal the parent private key).[82]
  • DUKPT (ANSI X9.24-3) in payment terminals derives a unique key per transaction from a base derivation key, so capturing one terminal key does not expose past transactions.[83]

4. Random number generation

Every key, nonce, IV, salt and ephemeral Diffie–Hellman exponent in the previous sections must be unpredictable to the adversary. RFC 4086 puts it bluntly: the security of a system that uses predictable “random” numbers is only as good as the effort needed to guess them.[5] Modern systems separate the job into two parts: a physical entropy source that is slow, noisy and hard to analyse, and a deterministic DRBG that is fast, provably sound and seeded by the entropy source. NIST's SP 800-90 series standardises all three pieces: 90A for DRBG mechanisms, 90B for entropy sources and 90C for how they combine into a random bit generator (RBG).[32,84,85]

4.1 True random number generators

A true (physical, or non-deterministic) RNG derives its output from a physical process that is unpredictable in principle or in practice:[5,84,86]

  • Electronic noise: thermal (Johnson–Nyquist) noise in resistors, shot noise and avalanche noise in reverse-biased diodes.
  • Oscillator jitter: free-running ring oscillators sampled by a slower clock; the phase drift accumulates unpredictably. Most on-chip TRNGs in microcontrollers and FPGAs use this.
  • Metastability: Intel's digital RNG resolves a deliberately balanced latch at high speed; the raw bits are conditioned with AES-CBC-MAC and feed an AES CTR_DRBG behind the RDRAND instruction, with RDSEED returning conditioned seed values.[87,88]
  • Quantum processes: photon arrival times, beam-splitter path choice, vacuum fluctuations, radioactive decay.
  • Macroscopic chaos: Cloudflare's LavaRand photographs a wall of about 100 lava lamps in its San Francisco office and mixes the images into its servers' entropy pools.[89]
  • Event timing on general-purpose computers: interrupt and disk timings, keystroke and mouse intervals, CPU cycle-counter jitter. These are “non-physical” sources in SP 800-90B's terms and are harder to model.[63,84]

Raw TRNG output is usually biased and correlated, can degrade with temperature, voltage and ageing, and can be manipulated by fault injection or electromagnetic coupling. That is why the standards require online health tests, a conservative entropy estimate, and conditioning before use, and why the output usually seeds a DRBG rather than being used directly. BSI's AIS 31 classifies physical RNGs (PTG.1–PTG.3) by these properties.[84,86]

4.2 Pseudorandom number generators

A PRNG is a deterministic algorithm that expands a seed into a long sequence that looks statistically random: statei+1 = f(statei), outputi = g(statei). Linear congruential generators, xorshift, PCG and the Mersenne Twister (MT19937) are designed for simulation: speed, long period and good equidistribution.[90,91] MT19937 has period 219937−1 and is 623-dimensionally equidistributed, but its output function is an invertible linear “tempering”, so 624 consecutive 32-bit outputs reveal the entire internal state and every future (and past) output. §5.6 does this in a dozen lines.[90] Python's documentation warns that the random module “should not be used for security purposes” and points to secrets.[92,93]

Statistically random is not unpredictable. MT19937 passes most of TestU01's batteries (it fails only the linear-complexity tests in Crush and BigCrush), yet it is trivially predictable.[90,91] Cryptographic security is about an adversary, not a statistician.

4.3 Cryptographically secure PRNGs

A CSPRNG is a PRNG whose output is a cryptographic PRG (§2.1): no efficient adversary can predict the next bit or distinguish output from random. Practical CSPRNGs add further properties, formalised by Dodis et al. as robustness:[32,94]

  • Backtracking resistance (forward security): compromise of the current state does not reveal earlier outputs. Achieved by updating the state one-way after every request.
  • Prediction resistance (post-compromise security, “recovery”): after a compromise, fresh entropy restores security of future outputs. Achieved by reseeding, ideally from accumulated entropy so that an attacker cannot track small increments (the motivation for Fortuna's pools).[94,95]
  • Resilience against attacker-influenced inputs: adversarially chosen additional input must not reduce security.

Examples: ChaCha20-based designs (Linux getrandom, OpenBSD arc4random), AES-CTR-DRBG (Windows BCryptGenRandom), HMAC_DRBG, Fortuna and Yarrow, and the historical Blum–Blum–Shub generator, which is provably secure under a factoring-type assumption but far too slow for practice.[61,63,96,97]

4.4 Deterministic random bit generators (DRBGs)

SP 800-90A Rev. 1 specifies three DRBG mechanisms, each with the functions Instantiate, Generate, Reseed and Uninstantiate:[32]

Common parameters: security strength up to 256 bits; instantiation needs entropy input of at least the security strength plus a nonce; at most 219 bits per Generate call and at most 248 requests between reseeds. Optional personalization strings at instantiation and additional input on each call provide domain separation and a hedge if entropy is weak.[32] HMAC_DRBG's Update is the heart of the design:

Update(data): K = HMAC(K, V ‖ 0x00 ‖ data); V = HMAC(K, V) if data ≠ empty: K = HMAC(K, V ‖ 0x01 ‖ data); V = HMAC(K, V) Instantiate: K = 0x00…00, V = 0x01…01, Update(entropy ‖ nonce ‖ personalization) Generate(n): repeat V = HMAC(K, V), output V until n bits; Update(additional_input)

Calling Update after every request replaces K and V with values from which the previous ones cannot be computed: that gives backtracking resistance.[32]

Dual_EC_DRBG. SP 800-90 (2006) also included a DRBG based on elliptic-curve points P and Q. Shumow and Ferguson pointed out in 2007 that whoever knows d with P = dQ can recover the internal state from about 30 bytes of output. After the 2013 Snowden disclosures NIST withdrew it, and Rev. 1 (2015) removed it. Checkoway et al. showed the backdoor was practically exploitable against TLS implementations such as RSA BSAFE, and Juniper ScreenOS was found to contain Dual EC with altered constants.[32,99,100]

4.5 Entropy sources

SP 800-90B defines an entropy source as a noise source, an optional conditioning component and health tests, and specifies how to validate each.[84]

  • Noise source: the non-deterministic part. The developer must justify why it is unpredictable (a stochastic model, for physical sources) and give an expected entropy rate.
  • Conditioning: a vetted function (HMAC, CMAC, CBC-MAC, Hash_df, Block_cipher_df) or a non-vetted one, which compresses raw samples into output with higher entropy per bit. Conditioning cannot create entropy; output entropy is bounded by input entropy and output length.
  • Health tests: start-up tests on at least 1024 samples, continuous tests on every sample, and optional on-demand tests. Two continuous tests are mandatory for most sources:
    • Repetition Count Test (RCT): fail if one value repeats C = 1 + ⌈−log2(α)/H⌉ times in a row, where H is the claimed min-entropy per sample and α the false-alarm rate (recommended 2−20). For H = 0.5 bits, C = 41.
    • Adaptive Proportion Test (APT): within a window of 1024 samples (binary) or 512 (non-binary), fail if the first value of the window occurs too often.

These tests detect a source that has failed catastrophically (stuck, or heavily biased), not subtle weaknesses; they are a tripwire, not a proof of quality.[84]

4.6 Entropy estimation

Security depends on min-entropy, not Shannon entropy: H∞(X) = −log2 maxx Pr[X = x], which measures the attacker's best single guess.[1,84] (Definitions and examples are in the mathematical foundations article.) A source that outputs a fixed 128-bit string half the time and a random string otherwise has Shannon entropy about 65 bits but min-entropy only 1 bit: the attacker's first guess succeeds 50% of the time.

SP 800-90B's procedure:[84,101]

  1. Collect at least 1 000 000 consecutive raw samples, plus 1000 restarts of 1000 samples each.
  2. Test whether the samples look IID (independent and identically distributed) with permutation and chi-square tests.
  3. If IID, use the most common value estimate: with p̂ the observed frequency of the most common value, take the 99% upper bound pu = min(1, p̂ + 2.576√(p̂(1−p̂)/(L−1))) and H = −log2 pu.
  4. If not IID, run ten estimators (most common value, collision, Markov, compression, t-tuple, longest repeated substring, and four predictors: MultiMCW, Lag, MultiMMC, LZ78Y) and take the minimum.
  5. Take the minimum of that and the developer's claim, then validate with the restart data.

§5.6 applies the MCV estimator to bits with Pr[1] = 0.75 (true min-entropy 0.415 bits per bit): it reports 0.406, slightly conservative as intended. Estimation from data alone can never prove a source unpredictable (a counter encrypted with a secret key would score perfectly) which is why 90B also demands a design rationale.[84]

4.7 Randomness extraction

An extractor turns a weakly random source with min-entropy m into nearly uniform bits.[102]

  • Von Neumann's trick (1951): read bits in pairs, output 0 for 01, 1 for 10, discard 00 and 11. For independent bits with any fixed bias p the output is exactly unbiased, at a yield of p(1−p) output bits per input bit. It fails for correlated input.[103]
  • Seeded extractors: no single deterministic function extracts from every source of a given min-entropy, so general extractors take a short uniform seed. Nisan and Zuckerman formalised this definition.[102]
  • Leftover hash lemma: a universal hash family with a random public seed extracts about m − 2 log2(1/ε) bits that are ε-close to uniform from any source with min-entropy m.[62] Extracting 128 bits at ε = 2−64 thus needs 256 bits of min-entropy.
  • Computational extractors: HMAC, CBC-MAC and hash functions are used in practice, with proofs under PRF-type assumptions or in idealised models. HKDF-Extract and SP 800-90B's vetted conditioning functions are examples.[4,71,84]

4.8 Entropy pools

An operating system collects many low-quality events. An entropy pool accumulates them, mixing each input into a state with a cryptographic hash, so the state becomes unpredictable once enough entropy has arrived, and then seeds the CSPRNG.[63,95]

Design points and history:

  • Linux. getrandom(2) (added in Linux 3.17) blocks only until the pool has been initialised once, then never again; it is the right interface. Since Linux 5.6, /dev/random no longer blocks after initialisation either, ending a long-standing source of confusion; /dev/urandom never blocked and, on early boot, could return output before initialisation.[63,104,105]
  • Yarrow (1999) used a fast and a slow pool; Fortuna (2003) uses 32 pools, with pool i used in every 2i-th reseed, so that even if an attacker can inject or observe most inputs, some pool eventually accumulates enough entropy to recover from compromise without the designer having to estimate entropy.[95,97]
  • Dodis et al. showed the pre-2016 Linux /dev/random was not “robust” in their model, because its entropy estimator could be fooled into reseeding too early, motivating later redesigns.[94]
  • Never mix with XOR from an untrusted source without hashing. A malicious input that sees the other inputs can cancel them; hashing into the pool prevents this.[5]

4.9 Randomness testing

Statistical test suites compute a statistic from the output and its p-value under the hypothesis “the sequence is uniform and independent”:[91,106]

  • NIST SP 800-22 Rev. 1a: 15 tests (frequency/monobit, block frequency, runs, longest run of ones, binary matrix rank, discrete Fourier transform, non-overlapping and overlapping template matching, Maurer's universal, linear complexity, serial, approximate entropy, cumulative sums, random excursions and its variant), with significance level α = 0.01 by default.[106]
  • TestU01 (L'Ecuyer and Simard): SmallCrush, Crush and BigCrush batteries, the most stringent widely used suite.[91]
  • Dieharder, PractRand and ent for quick checks.[107–109]

The monobit test, for example: map bits to ±1, sum to Sn, compute sobs = |Sn|/√n and p = erfc(sobs/√2); reject if p < 0.01. The alternating sequence 0101… passes monobit perfectly (p = 1) and fails the runs test (p ≈ 0), which is why suites run many tests.[106]

What tests can and cannot do. Tests can only reject. AES in counter mode under a published key passes every test in every suite, and so does MT19937 on most of them, but both are completely predictable to anyone who knows how they work. Statistical testing is useful for catching broken hardware and implementation bugs; it is no substitute for a design argument and SP 800-90B entropy assessment.[84,91,106]

4.10 Seed management

A DRBG is exactly as secure as its seed and state. Rules drawn from SP 800-90A/C, RFC 4086 and incident history:[5,32,85]

  • Enough entropy, once, before first use. Seed with at least the security strength (and 90A's extra nonce) from an approved entropy source; block, rather than return output, until then. Headless devices that generated SSH and TLS keys on first boot, before their pools had entropy, produced the shared primes and repeated keys found by Heninger et al.[6]
  • Never use time, PIDs or counters as seeds. The 2008 Debian OpenSSL bug removed all entropy except the process ID (at most 32 768 values), so every key generated on affected systems for two years came from a tiny enumerable set.[110]
  • Never let state be duplicated. Virtual machine snapshots, cloned images, and fork() copy the DRBG state, so two instances produce identical “random” output. Ristenpart and Yilek demonstrated TLS key compromise from VM resets. Reseed after fork, resume and clone; OS interfaces like getrandom handle this for you.[111]
  • Protect the state and seed file like a key. Persist a seed across reboots (as systemd's random-seed service does) but credit it only if it is known to be fresh and unique to the machine, and replace it at each boot.[63]
  • Reseed periodically for prediction resistance, and use personalization strings (device serial number, instance ID) so that two instances with the same seed still diverge.[32]
  • Hedge. Where a long-term secret is available, mix it into the randomness, as RFC 8937 proposes for TLS, or derive nonces deterministically as in RFC 6979 and EdDSA, so that a weak RNG does not instantly leak a signing key.[98,112]
  • In application code, ask the OS: getrandom/getentropy, BCryptGenRandom, Python secrets/os.urandom, Java SecureRandom, WebCrypto crypto.getRandomValues.[93,96,105,113]

def hmac_sha256(key: bytes, msg: bytes) -> bytes:
    B = 64                                   # SHA-256 block size in bytes
    if len(key) > B:
        key = hashlib.sha256(key).digest()   # long keys are hashed first
    key = key.ljust(B, b"\x00")

    opad = bytes(k ^ 0x5C for k in key)
    inner = hashlib.sha256(ipad + msg).digest()
    return hashlib.sha256(opad + inner).digest()

    assert len(msg) % 16 == 0
    t = bytes(16)
    for i in range(0, len(msg), 16):
        t = aes_block(key, xor(t, msg[i:i+16]))
    return t

def _dbl(b: bytes) -> bytes:                 # multiply by x in GF(2^128)
    n = int.from_bytes(b, "big") << 1
    if n >> 128:
        n = (n ^ 0x87) & ((1 << 128) - 1)    # reduce: R_128 = 0^120 || 10000111
    return n.to_bytes(16, "big")

def cmac_subkeys(key):
    L = aes_block(key, bytes(16))
    K1 = _dbl(L)
    return K1, _dbl(K1)

    else:
        last = xor(last + b"\x80" + bytes(15 - len(last)), K2)   # 10* padding
    return cbc_mac(key, msg[:16*(n-1)] + last)

5.4 PRP/PRF switching, GGM, Luby–Rackoff and PRF-based encryption

prf_prp.py
# PRGs, PRFs and PRPs in miniature.
import os, hmac, hashlib, random

# 1. PRP/PRF switching: on an n-bit domain, a random *permutation* never
#    repeats an output, a random *function* does after about 2^(n/2) queries.
def collision_rate(n_bits, q, trials=20000, rng=random.Random(1)):
    hits = 0
    for _ in range(trials):
        seen = set()
        for _ in range(q):
            y = rng.getrandbits(n_bits)      # fresh query to a random function
            if y in seen:
                hits += 1; break
            seen.add(y)
    return hits / trials

def exact(n_bits, q):                       # 1 - prod (1 - i/2^n)
    p = 1.0
    for i in range(q):
        p *= 1 - i / 2 ** n_bits
    return 1 - p

n = 16
for q in (16, 64, 256, 512):
    bound = min(q * (q - 1) / 2 ** (n + 1), 1)
    print(f"n={n} q={q:3d}: simulated {collision_rate(n, q):.4f}"
          f"  exact {exact(n, q):.4f}  bound {bound:.4f}")

# 2. GGM: a PRF from a length-doubling PRG G(s) = G0(s) || G1(s).
def G(seed: bytes):
    out = hashlib.sha256(b"GGM" + seed).digest() + hashlib.sha256(b"ggm" + seed).digest()
    return out[:32], out[32:]               # (G0, G1): toy PRG, illustration only

def ggm_prf(key: bytes, x_bits: str) -> bytes:
    s = key
    for b in x_bits:                        # walk the binary tree, one PRG call per bit
        s = G(s)[int(b)]
    return s

k = os.urandom(32)
print("GGM F_k(0110) =", ggm_prf(k, "0110").hex()[:32], "...")

# 3. Luby-Rackoff: a 4-round Feistel network over a PRF is a strong PRP.
def F(key, i, half):                        # round function: HMAC as a PRF
    return hmac.new(key, bytes([i]) + half, hashlib.sha256).digest()[:16]

def lr_encrypt(key, block32, rounds=4):
    L, R = block32[:16], block32[16:]
    for i in range(rounds):
        L, R = R, bytes(a ^ b for a, b in zip(L, F(key, i, R)))
    return L + R

def lr_decrypt(key, block32, rounds=4):
    L, R = block32[:16], block32[16:]
    for i in reversed(range(rounds)):
        L, R = bytes(a ^ b for a, b in zip(R, F(key, i, L))), L
    return L + R

blk = b"thirty-two byte block of input!!"
ct = lr_encrypt(k, blk)
assert lr_decrypt(k, ct) == blk
print("Luby-Rackoff round trip OK:", ct.hex()[:32], "...")

# 4. CPA-secure encryption from any PRF: c = (r, F_k(r) XOR m)
def prf_encrypt(key, m16):
    r = os.urandom(16)
    pad = hmac.new(key, r, hashlib.sha256).digest()[:16]
    return r, bytes(a ^ b for a, b in zip(pad, m16))

def prf_decrypt(key, r, c):
    pad = hmac.new(key, r, hashlib.sha256).digest()[:16]
    return bytes(a ^ b for a, b in zip(pad, c))

r, c = prf_encrypt(k, b"sixteen byte msg")
assert prf_decrypt(k, r, c) == b"sixteen byte msg"
print("PRF-based encryption round trip OK")

# Random number generation: HMAC_DRBG, why non-crypto PRNGs fail,
# health tests, entropy estimation, extraction and statistical tests.
import hmac, hashlib, math, os, random, secrets
from collections import Counter

# ---------- 1. HMAC_DRBG (NIST SP 800-90A Rev. 1, section 10.1.2), SHA-256 ----------
class HmacDrbg:
    RESEED_INTERVAL = 2 ** 48
    def __init__(self, entropy: bytes, nonce: bytes, personalization: bytes = b""):
        self.K, self.V = b"\x00" * 32, b"\x01" * 32
        self._update(entropy + nonce + personalization)
        self.reseed_counter = 1
    def _h(self, key, data):
        return hmac.new(key, data, hashlib.sha256).digest()
    def _update(self, provided: bytes = b""):
        self.K = self._h(self.K, self.V + b"\x00" + provided)
        self.V = self._h(self.K, self.V)
        if provided:
            self.K = self._h(self.K, self.V + b"\x01" + provided)
            self.V = self._h(self.K, self.V)
    def reseed(self, entropy: bytes, additional: bytes = b""):
        self._update(entropy + additional)
        self.reseed_counter = 1
    def generate(self, n: int, additional: bytes = b"") -> bytes:
        if self.reseed_counter > self.RESEED_INTERVAL:
            raise RuntimeError("reseed required")
        if additional:
            self._update(additional)
        out = b""
        while len(out) < n:
            self.V = self._h(self.K, self.V)
            out += self.V
        self._update(additional)           # backtracking resistance
        self.reseed_counter += 1
        return out[:n]

8. Exercises

Click an exercise to reveal its solution.

8.1 Tag length. An API accepts HMAC-SHA-256 tags truncated to 32 bits and allows 1000 verification attempts per second per client. How long until a single client forges with probability ½? What tag length makes a year of attempts safe to 2−40?

Each guess succeeds with probability 2−32, so about 231 ≈ 2.1×109 guesses give probability ½: about 2.1×106 s ≈ 25 days. A year is about 3.15×1010 ≈ 235 attempts, so we need 235 − t ≤ 2−40, i.e. t ≥ 75 bits; in practice use 96 or 128. This is why RFC 2104 suggests at least 80 bits, and rate limiting matters for short tags.[16,17]

8.2 Secret-prefix MAC. Explain why T = SHA-256(K ‖ M) is not a secure MAC but T = SHA3-256(K ‖ M) is considered fine, and give one fix that works for SHA-256.

SHA-256 outputs its full internal chaining state, so from T and |K ‖ M| an attacker can continue hashing and compute SHA-256(K ‖ M ‖ pad ‖ M′) without K: a length-extension forgery. SHA3-256 is a sponge that outputs only part of its state and keeps 512 bits of capacity hidden, so the state cannot be resumed; KMAC formalises this prefix-key construction.[50] Fixes for SHA-256: HMAC, or SHA-512/256, whose truncated output also prevents extension.[16,26]

8.3 CBC-MAC forgery. You see the CBC-MAC tags T1 of the one-block message A and T2 of the one-block message B. Construct a forgery on a two-block message.

A ‖ (B ⊕ T1) has tag EK(T1 ⊕ B ⊕ T1) = EK(B) = T2. Any message whose chaining value can be steered to a known state can be extended this way; CMAC's secret final-block mask blocks it.[15,21]

8.4 CMAC subkeys. Given L = EK(0) = 7df76b0c 1ab899b3 3e42f047 b91b546f (RFC 4493), compute K1.

The most significant bit of L is 0 (0x7d = 0111…), so K1 = L ≪ 1 with no reduction: fbeed618 35713366 7c85e08f 7236a8de. The MSB of K1 is 1, so K2 = (K1 ≪ 1) ⊕ 0x87 = f7ddac30 6ae266cc f90bc11e e46d513b, matching §5.2.[36]

8.5 Universal hash bound. A polynomial MAC over GF(2128) authenticates 1 MiB messages. What is ε per forgery attempt, and how many attempts until the forgery probability reaches 2−32?

1 MiB = 216 blocks of 16 bytes, so the polynomial has degree about 216 and ε ≈ 216/2128 = 2−112. Reaching 2−32 takes about 280 attempts: comfortable, but notice the bound degrades linearly with message length, which is why GCM caps a single message at about 64 GiB (239−256 bits).[8,41]

8.6 Nonce reuse in Carter–Wegman. Show what an attacker learns from tags T = hk(M) ⊕ P and T′ = hk(M′) ⊕ P computed with the same pad P, for GHASH.

T ⊕ T′ = hk(M) ⊕ hk(M′), which for GHASH is a known polynomial in H over GF(2128) (the coefficients are the XOR of the message blocks). Its roots include H; factoring (e.g. with Cantor–Zassenhaus) yields a short list of candidates, and one more tag confirms the right one. With H the attacker can forge tags for any message under that nonce. This is Joux's forbidden attack.[43,44]

8.7 Poly1305 by hand. With r = 2, s = 0 and a single one-byte message 0x05, compute the Poly1305 tag (ignore clamping).

The chunk 0x05 with the appended 0x01 is the little-endian integer 0x0105 = 261. acc = (0 + 261) · 2 mod (2130−5) = 522; tag = 522 mod 2128 = 522 = 0x020a, encoded little-endian as 0a 02 00 … 00. The appended 1 is why 0x05 and 0x05 0x00 give different polynomials.[9]

8.8 PRF ⇒ MAC. Prove that if F is a PRF with n-bit output then MacK(M) = FK(M) is EUF-CMA secure for fixed-length messages.

Given a forger 𝒜, build a distinguisher 𝒟 that answers 𝒜's tag queries with its oracle, then queries the oracle on 𝒜's forgery message M* and outputs 1 if the answer equals T*. With the real PRF, 𝒟 outputs 1 exactly when 𝒜 forges. With a random function, f(M*) is uniform and independent of everything 𝒜 saw (since M* is fresh), so Pr = 2−n. Hence Adveuf(𝒜) ≤ Advprf(𝒟) + 2−n.[1,10]

8.9 Switching lemma. AES-CTR encrypts 240 blocks (16 TiB) under one key. Bound the cost of modelling AES as a random function.

q(q−1)/2n+1 ≈ 280/2129 = 2−49. Negligible. For 3DES (n = 64) the same 240 blocks give 280/265 > 1: the bound is vacuous, and Sweet32 shows the attack is real at about 232 blocks.[67,68]

8.10 Luby–Rackoff with too few rounds. Show that a 2-round Feistel network with PRF round functions is not a PRP.

After two rounds, L2 = L0 ⊕ F1(R0). Query (L0, R) and (L0′, R) with the same right half: the outputs' left halves XOR to L0 ⊕ L0′, always for the Feistel network, but only with probability 2−n/2 for a random permutation. One round more fixes this.[1,64]

8.11 HKDF limits. What is the maximum output of HKDF-SHA-256 and why? If you need more, what should you do?

255 × 32 = 8160 bytes, because the block counter is a single octet and must not be 0. For more, expand several independent PRKs with distinct info values, or use the output as a key for a stream cipher or DRBG.[30]

8.12 Extract or not? For each input decide whether to use HKDF-Extract+Expand, Expand only, or a password KDF: (a) X25519 shared secret; (b) a 256-bit key from an HSM; (c) a user's passphrase; (d) 1 KB of raw jitter samples with an estimated 0.3 bits/byte min-entropy.

(a) Extract + Expand: uniform over the curve group's encoding, not over bit strings. (b) Expand only (SP 800-108 or HKDF-Expand): already uniform. (c) Password KDF (Argon2id, scrypt, PBKDF2) with salt. (d) Only about 300 bits of min-entropy: Extract with a vetted conditioner (enough for a 128-bit seed with margin, per the leftover-hash budget of §4.7), then use it to seed a DRBG.[4,69,78,84]

8.13 PBKDF2 cost asymmetry. A system derives a 64-byte key with PBKDF2-HMAC-SHA-256 (32-byte blocks) at 600 000 iterations, and stores the second half as a verifier. What does the attacker need to compute per guess?

Only block T2, so 600 000 iterations, while the defender computes both blocks, 1 200 000. Worse, if the first half were stored the attacker would test guesses against T1 alone. Derive one PRF block and expand it with HKDF, or choose a PRF whose output covers the needed length (HMAC-SHA-512).[10,31]

8.14 Domain separation bug. A service derives both its encryption and MAC keys as HKDF(master, info = user_id), then discovers that for user "enc" its encryption key equals another derived key. Explain and fix.

The two keys share an info and so are identical, violating key separation; and because info is just the attacker-influenced user ID, it can collide with labels used elsewhere. Fix: fixed, distinct purpose labels plus length-prefixed context, e.g. info = "app/v1/enc" ‖ len(user_id) ‖ user_id and "app/v1/mac" ‖ ….[24,37]

8.15 Min-entropy. A 4-bit source outputs 0000 with probability ½ and each of the other 15 values with probability 1/30. Compute its Shannon and min-entropy, and how many samples are needed for a 128-bit seed.

Shannon: ½·1 + 15·(1/30)·log230 ≈ 0.5 + 2.45 = 2.95 bits. Min-entropy: −log2(½) = 1 bit. Budget by min-entropy: at least 128 samples, and in practice at least twice that so an extractor can reach small statistical distance (§4.7).[62,84]

8.16 Von Neumann yield. Bits are independent with Pr[1] = 0.75. What fraction of input bits does the von Neumann extractor output, and why did §5.6 get exactly 18 750 bits from 100 000?

Each pair produces a bit with probability 2pq = 2·0.75·0.25 = 0.375; there are 50 000 pairs, so the expected output is 18 750 bits, or 0.1875 bits per input bit. Hitting the expectation exactly was luck (the standard deviation is about 108).[103]

8.17 Fork safety. A server forks worker processes after seeding a user-space DRBG. What goes wrong, and name two fixes.

Each child inherits an identical DRBG state and produces the same “random” nonces and keys; with ECDSA, two signatures sharing a nonce reveal the private key. Fixes: call the OS RNG (getrandom) directly, reseed in each child after fork (mixing in PID and fresh OS entropy), or use deterministic/hedged nonces (RFC 6979).[98,105,111]

8.18 Verification timing. Estimate how many requests a byte-at-a-time timing attack needs to forge a 16-byte tag if 100 samples per candidate byte value suffice to see the timing difference.

16 positions × 256 candidates × 100 samples ≈ 4.1×105 requests, compared with 2127 on average for blind guessing. Constant-time comparison closes the gap entirely.[54,55]

9. Trivia

What do the HMAC constants 0x36 and 0x5c have in common?

They differ in exactly half their bits (0x36 ⊕ 0x5c = 0x6a = 01101010, four of eight bits), so the inner and outer keys are far apart in Hamming distance.[16,26]

Which two “passwords” give the same HMAC-SHA-1 and PBKDF2-HMAC-SHA-1 results?

plnlrtfpijpuhqylxbgqiiyipieyxvfsavzgxbbcfusqkozwpngsyejqlmjsytrmd and eBkXQTfuBqp'cTcar&g*, because the first is longer than the 64-byte block and is replaced by its SHA-1 hash, which is the second.[28]

Which prime gives Poly1305 its name?

2130 − 5; the “1305” is 130 and 5.[47]

Who invented universal hashing, and for what original purpose?

J. Lawrence Carter and Mark Wegman (1979), for hash tables with guaranteed average performance; their 1981 paper applied it to authentication.[38,40]

What does the “O” in OMAC stand for?

One-key CBC MAC: Iwata and Kurosawa improved XCBC's three keys to one. OMAC1 became NIST's CMAC.[34,35]

Which 1985 US federal standard was a CBC-MAC over DES?

FIPS 113, “Computer Data Authentication”, the federal counterpart of ANSI X9.9 for banking.[14]

What hard-coded HMAC key starts every Bitcoin HD wallet?

The ASCII string “Bitcoin seed” (HMAC-SHA512).[82]

In AWS Signature V4, what is the final string that produces the signing key?

“aws4_request”, after chaining HMACs over the date, region and service.[12]

What six-character prefix appears in every TLS 1.3 key-schedule label?

“tls13 ” (including the space).[7]

How many pools does Fortuna use?

32, with pool i drained every 2i-th reseed.[95]

How many outputs of MT19937 do you need to clone it?

624 32-bit outputs, the size of its state.[90]

What does Cloudflare point a camera at to gather entropy?

A wall of about 100 lava lamps (LavaRand) in its San Francisco office.[89]

Which hash replaced SHA-1 in the Linux kernel RNG, and in which version?

BLAKE2s, in Linux 5.17 (2022).[63]

Which DRBG did NIST remove from SP 800-90A in 2015?

Dual_EC_DRBG, after evidence it contained a backdoor.[32,100]

How many statistical tests are in NIST SP 800-22?

15.[106]

How many possible keys per type and size could the vulnerable Debian OpenSSL generate?

About 32 768: one for each possible process ID.[110]

Which mathematician proposed the “unbiasing” trick for coin flips in 1951, and what did he say about arithmetic random numbers?

John von Neumann. In the same paper he wrote that “anyone who considers arithmetical methods of producing random digits is, of course, in a state of sin.”[103]

What two bytes does Signal's Double Ratchet feed to HMAC to step a chain?

0x01 for the message key and 0x02 for the next chain key.[73]
