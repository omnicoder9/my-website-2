Introduction

Three hospitals want to know whether a rare side effect is more common with drug A than with drug B, but none may disclose patient records to the others. Two banks want to find customers they share without revealing their customer lists. Five executives want any three of them to be able to approve a cryptocurrency transfer, yet no single laptop should ever hold the signing key. Each of these is an instance of secure multiparty computation (MPC, also SMPC or SMC): n parties with private inputs x1, …, xn jointly compute y = f(x1, …, xn) so that each learns y and nothing more, even if some of them collude or cheat.[1,2]

Andrew Yao framed the problem in 1982 with the millionaires' problem: two millionaires want to know who is richer without revealing their wealth.[3] A few years later came the startling general answer: every efficiently computable function can be computed securely, against any number of corrupted parties if one accepts computational assumptions and the possibility of abort,[4,5] or with perfect, unconditional security when fewer than a third of the parties are corrupted.[6,7] Four decades of engineering then turned that feasibility result into practice. Garbled circuits shrank from four ciphertexts per gate to fewer than two,[8,9] oblivious transfers became nearly as cheap as symmetric encryption,[10,11] and dishonest-majority arithmetic protocols such as SPDZ moved the heavy public-key work into an input-independent preprocessing phase.[12,13] MPC now runs auctions, tax statistics, ad conversion measurement and, most visibly, the threshold-signing wallets of custodians and exchanges.[14,15,16,17]

This article covers the building blocks named in its title, in the order a practitioner meets them: secret sharing (additive and Shamir), oblivious transfer, two-party computation with garbled circuits, arithmetic MPC with Beaver triples, the difference between semi-honest and malicious adversaries, and finally threshold signatures with distributed key generation. Every scheme is accompanied by a worked example, and Section 12 contains seven tested Python programs, including a complete garbled-circuit run of the millionaires' problem and a FROST threshold signer whose output is checked by an ordinary Ed25519 verifier.

Notation. n is the number of parties and t the number the adversary may corrupt. ‘[x]’ denotes a secret-shared value, with party Pi holding share [x]i. 𝔽p is the field of integers modulo a prime p, and ⊕ is XOR. κ is the computational security parameter (typically 128) and H a hash function modelled as a random oracle.

1. What MPC promises

1.1 The ideal/real paradigm

Defining “learns nothing more” precisely is subtle, because the output itself leaks information: if two parties compute the sum of their inputs, each can subtract its own input and learn the other's. MPC security is therefore defined relative to an ideal world in which an incorruptible trusted party collects the inputs, computes f and hands back the outputs. A protocol is secure if whatever an adversary can achieve by attacking the real protocol, it could also achieve in the ideal world. Formally, for every real adversary 𝒜 there exists an ideal adversary (a simulator) 𝒮 such that the joint distribution of the honest parties' outputs and the adversary's view is indistinguishable in the two worlds.[18,19,20]

The simulator argument is constructive. To prove a protocol private against a semi-honest party, one writes a program that, given only that party's input and output, produces a transcript distributed like the real one. If such a program exists, the transcript can contain nothing beyond the input and output. Canetti's universal composability (UC) framework strengthens the definition so that a protocol stays secure when run concurrently with arbitrary other protocols, which is the setting real deployments live in.[21]

1.2 Security properties

The ideal world implies a set of properties that are easier to state individually:[1,19]

PropertyMeaningCan it be guaranteed?
PrivacyNo party learns anything beyond its prescribed output.Always (the core goal).
CorrectnessHonest parties receive the correct value of f.Always, possibly together with “abort”.
Independence of inputsCorrupted parties choose inputs without knowing honest inputs (no “bid one more than the highest”).Always.
Guaranteed output deliveryThe adversary cannot prevent honest parties from getting output.Only with an honest majority.[22]
FairnessIf corrupted parties get output, so do honest ones.Not in general with a dishonest majority: Cleve showed even fair coin tossing is impossible.[23]

Protocols for a dishonest majority therefore usually achieve security with abort: the adversary may learn the output and then stop the honest parties from learning it, but it can never learn more or make them accept a wrong value. Stronger variants identify who caused the abort (identifiable abort), which lets a system exclude the cheater and retry.[24]

1.3 Feasibility landscape

Which guarantees are achievable depends on how many parties are corrupt and on what the communication network provides. The classical results are summarised below.[25,2]

2. Secret sharing

2.1 Threshold secret sharing

A (t, n) threshold secret-sharing scheme splits a secret s into n shares such that any t of them determine s, while any t − 1 reveal nothing about it, in the information-theoretic sense: the distribution of any t − 1 shares is the same for every secret.[27,28] (Some MPC papers instead use t for the number of corruptions tolerated, so that t + 1 shares reconstruct; the code in this article states its convention each time.) Secret sharing is used in two quite different ways:

  • Storage. A key is split for backup or dual control, and reconstructed in one place when needed, as in key ceremonies.
  • Computation. Shares are never reassembled. Parties compute on them directly, producing shares of the output. This is how most multiparty protocols represent every intermediate value.[35,25]

Shares in a perfect scheme must each be at least as long as the secret, because the last missing share must be able to “select” any secret. Shamir and additive sharing meet this bound exactly, which is why they are called ideal.[25]

2.2 Additive secret sharing

The simplest scheme is n-out-of-n. To share x ∈ 𝔽p, pick x1, …, xn−1 uniformly at random and set xn = x − Σ xi. Any n − 1 shares are independent uniform values, so they are a one-time pad on x; all n sum to x. The same works over any group: over bit strings with XOR (Boolean or XOR sharing), over ℤ264 to match machine words, or over elliptic-curve points.[2]

[x] = (x₁, x₂, …, xₙ) with x₁ + x₂ + … + xₙ ≡ x (mod p) [x] + [y] = (x₁+y₁, …, xₙ+yₙ) local, no messages c·[x] = (c·x₁, …, c·xₙ) local [x] + c = (x₁+c, x₂, …, xₙ) only one party adds the constant

Additive sharing tolerates t = n − 1 corruptions, the best possible, which is why dishonest-majority protocols such as SPDZ and GMW use it. Its weakness is availability: if one share is lost or one party goes offline, the secret is gone.

2.3 Shamir's secret sharing

Shamir's 1979 scheme fixes the availability problem with polynomials.[27] To share s with threshold t, the dealer picks a random polynomial of degree t − 1 with constant term s,

f(x) = s + a₁x + a₂x² + … + a_{t−1}x^{t−1} (mod p), aᵢ uniform in 𝔽ₚ

and gives party i the point (i, f(i)). Any t points determine a unique polynomial of degree t − 1, so t parties recover s = f(0) by Lagrange interpolation:

s = f(0) = Σ_{i∈S} λᵢ · f(i), λᵢ = Π_{j∈S, j≠i} j / (j − i) (mod p)

With only t − 1 points, for every candidate secret s′ there is exactly one polynomial through those points and (0, s′), so every secret remains equally likely. McEliece and Sarwate observed in 1981 that Shamir shares form a Reed-Solomon codeword, so extra shares allow errors to be detected and corrected, which is what BGW exploits against malicious parties.[36,6]

Worked example

Work in 𝔽17 with secret s = 13 and threshold t = 3. The dealer picks f(x) = 13 + 2x + 10x² and hands out

f(1) = 25 ≡ 8, f(2) = 57 ≡ 6, f(3) = 109 ≡ 7, f(4) = 181 ≡ 11, f(5) = 273 ≡ 1 (mod 17)

Parties 1, 2 and 3 compute Lagrange coefficients λ1 = (2·3)/((2−1)(3−1)) = 3, λ2 = (1·3)/((1−2)(3−2)) = −3 ≡ 14 and λ3 = (1·2)/((1−3)(2−3)) = 1, and recover 3·8 + 14·6 + 1·7 = 115 ≡ 13. Parties 2, 4 and 5 use λ = (9, 12, 14) and also get 9·6 + 12·11 + 14·1 = 200 ≡ 13.

2.4 Homomorphism and its limit

Both schemes are linear: adding shares point-wise gives shares of the sum, because the sum of two degree-(t−1) polynomials is again one, with constant term x + y.[35] Any linear function, such as a sum, a weighted average or a matrix-vector product with a public matrix, can therefore be evaluated with no communication at all. Multiplication is different. The point-wise product of Shamir shares lies on f·g, whose degree is 2(t−1): it still encodes xy, but now needs 2t − 1 shares to open, and the degree grows with every further product. The product of additive shares is not a sharing of anything useful, since x1y1 + x2y2 ≠ (x1 + x2)(y1 + y2). Handling multiplication is the central problem of arithmetic MPC; Sections 6 and 7 give the two standard answers, degree reduction and Beaver triples.

Shamir is not authenticated. Plain secret sharing assumes honest shareholders. A party that submits a modified share during reconstruction shifts the result by a known amount (the share's offset times its Lagrange coefficient), and with exactly t shares the change cannot even be detected. Real deployments add commitments (VSS), MACs, or extra shares for error correction.[37,36]

2.5 Verifiable and proactive sharing

A verifiable secret sharing (VSS) scheme lets shareholders check that the dealer's shares are consistent, that is, that they lie on one polynomial of the right degree.[37] Feldman VSS publishes commitments Ck = ak·G to the polynomial's coefficients in a group where discrete logarithms are hard; party j accepts its share sj if

s_j · G =? Σ_k j^k · C_k (Feldman: hides s only computationally; C₀ = s·G is public)

Pedersen VSS uses commitments akG + bkH with a second random polynomial, making the commitments perfectly hiding.[38,39] Feldman's leak of s·G is harmless when s is a signing key whose public key is published anyway, which is why threshold-signature key generation uses it (Section 10).

Proactive secret sharing defends against an adversary that slowly compromises shareholders over months. In each epoch the holders add a fresh random sharing of zero to their shares. The secret is unchanged, but old shares become useless: t − 1 shares stolen last year cannot be combined with one stolen today.[40] Listing 12.1 demonstrates this refresh, and the same idea lets a group change its membership or threshold without changing the public key.

3. Oblivious transfer

3.1 Flavours of OT

In 1-out-of-2 oblivious transfer (OT), a sender holds two messages m0, m1 and a receiver holds a choice bit b. The receiver learns mb and nothing about m1−b; the sender learns nothing about b. Even, Goldreich and Lempel introduced this form in 1985 to sign contracts.[41] Rabin's original 1981 OT was different: the sender transmits one message, which arrives with probability ½, and the sender does not know whether it arrived.[29] Crépeau proved the two equivalent.[42] Other useful variants include 1-out-of-N OT, random OT (the messages, and possibly the choice, are random and generated by the protocol) and correlated OT (m1 = m0 ⊕ Δ for a fixed Δ), which is exactly what free-XOR garbling and OT-based triple generation need.[43]

3.2 Building OT

OT needs public-key techniques; it cannot be built from symmetric primitives alone in a black-box way. A classic construction in the random-oracle model, due to Bellare and Micali, works in any prime-order group with generator G:[44,45]

  1. The sender publishes a random group element C whose discrete logarithm the receiver does not know.
  2. The receiver picks a random k, sets PKb = k·G and PK1−b = C − PKb, and sends PK0. Because it knows the discrete log of only one key, it can decrypt only one ciphertext. PK0 is uniformly distributed whatever b is, so the sender learns nothing.
  3. The sender computes PK1 = C − PK0 and sends ElGamal-style encryptions (riG, mi ⊕ H(ri·PKi)) for i = 0, 1.
  4. The receiver decrypts entry b with H(k·rbG).

Listing 12.2 implements this on the Ed25519 group. Chou and Orlandi's “simplest OT” is a popular variant that needs only one message in each direction.[46] Protocols this short are easy to get subtly wrong, so production libraries use versions with carefully analysed proofs.

3.3 OT is complete

Kilian proved in 1988 that OT is complete for secure computation: given an OT functionality, any function can be computed securely against malicious adversaries without further assumptions.[26] Ishai, Prabhakaran and Sahai later made this efficient.[47] Practically, OT is the bridge in every two-party protocol: in Yao's protocol it delivers the evaluator's input labels, in GMW it evaluates AND gates on XOR shares, and in OT-based arithmetic protocols (Gilboa's method, MASCOT) it produces multiplication triples.[48,13] Beaver showed OTs can even be precomputed on random inputs and later “derandomised” with one cheap message each, which separates the expensive phase from the input-dependent one.[49]

3.4 OT extension

Public-key operations cost tens of microseconds, and a large garbled circuit or triple generator needs millions of OTs. Beaver first showed that a few “seed” OTs can be stretched into many,[50] and in 2003 Ishai, Kilian, Nissim and Petrank (IKNP) made the extension practical, using only κ = 128 base OTs plus hashing for any number m of OTs.[10]

The trick is a transpose. The receiver's choice vector r is hidden in the columns by pseudorandom pads the sender cannot remove, but in the rows it appears as qi = ti ⊕ ri·s: the sender can mask message 0 with H(qi) and message 1 with H(qi ⊕ s), and the receiver knows exactly one of these, H(ti). IKNP as shown is semi-honest; KOS added malicious security for a small constant overhead.[51] Since 2019, silent OT and VOLE extensions based on pseudorandom correlation generators and LPN-style assumptions produce millions of random OTs with communication sublinear in their number.[11]

4. Secure two-party computation

With two parties there is no honest majority to lean on, so every 2PC protocol is computational and offers security with abort at best.[23,52] The two classical paradigms differ in how they handle the circuit:

Yao: garbled circuits

One party (the garbler) encrypts the whole circuit; the other (the evaluator) evaluates it on encrypted wire values. Constant rounds regardless of circuit depth; communication proportional to circuit size; cheap for Boolean circuits.[4,53]

GMW: secret-shared gates

Both parties hold XOR shares of every wire. XOR gates are local; each AND gate needs an OT (or a Boolean triple). Rounds grow with the circuit's AND-depth, but traffic per gate is small and work is balanced.[5,2]

Both reduce the problem to a circuit: the function is compiled to AND, XOR and NOT gates, or to additions and multiplications over a ring. The cost is driven by the number of non-linear gates (AND or multiplication), not by the number of lines of source code. A 32-bit comparison needs 32 AND gates, a 32-bit adder 31, a 32-bit multiplier about a thousand, and one AES-128 block 6 400 in the best known circuits; this is why MPC compilers work hard on circuit optimisation and why MPC-friendly ciphers exist.[54,2] Fairplay (2004) was the first system to compile a high-level language to a garbled circuit and run it,[31] and in 2009 Pinkas, Schneider, Smart and Williams showed that maliciously secure 2PC of AES was practical.[55]

5. Garbled circuits

5.1 Garbling one gate

The garbler assigns every wire w two random labels (keys) W0w and W1w of κ bits, standing for 0 and 1. The labels look random, so holding one reveals nothing about which bit it encodes. For a gate g with inputs a, b and output c, the garbler encrypts each output label under the matching pair of input labels:[4,53]

for each (u, v) ∈ {0,1}²: E( Wₐᵘ , W_bᵛ ; W_c^{g(u,v)} ) = H(Wₐᵘ, W_bᵛ, gate-id) ⊕ W_c^{g(u,v)}

The four ciphertexts are shuffled to form the garbled table. An evaluator who holds exactly one label for each input wire can decrypt exactly one row, obtaining one output label, and continues gate by gate. At the output wires the garbler supplies a decoding table mapping labels to bits.

5.2 Yao's protocol end to end

For two parties, Alice (garbler) with input x and Bob (evaluator) with input y:[53,2]

  1. Alice garbles the circuit for f and sends Bob the garbled tables, the labels for her own input bits (which look random to Bob) and the output decoding information.
  2. For each of his input bits yi, Bob runs a 1-out-of-2 OT with Alice as sender of (W0, W1) and obtains Wyi without Alice learning yi and without Bob learning the other label.
  3. Bob evaluates gate by gate, decodes the output and sends it to Alice if she is also to learn it.

Yao described the idea in talks around his 1986 paper, but the paper did not spell out the garbling construction; the first full proof of security for the semi-honest protocol appeared only in 2009, by Lindell and Pinkas.[4,53,58]

Free-XOR works because if A1 = A0 ⊕ Δ and B1 = B0 ⊕ Δ, then setting C0 = A0 ⊕ B0 makes Au ⊕ Bv = Cu⊕v for all u, v; the evaluator just XORs the labels it holds.[59] Half-gates decomposes a∧b = (a∧r) ⊕ (a∧(r⊕b)) for a random bit r known to the garbler: in the first half the garbler knows one input, in the second the evaluator does (it learns r⊕b as a colour bit), and each half costs a single ciphertext.[8] Zahur, Rosulek and Evans also proved that two ciphertexts are optimal for “linear” garbling schemes; Rosulek and Roy broke that bound by leaving the model, reaching 1.5κ + 5 bits per AND gate.[8,9] Implementations instantiate H with fixed-key AES, which runs at a few nanoseconds per call on AES-NI hardware.[60]

5.4 Security of garbling

Bellare, Hoang and Rogaway turned garbling into a primitive with its own definitions: privacy (the garbled circuit and one set of input labels reveal only the output), obliviousness (they reveal nothing at all without the decoding information) and authenticity (the evaluator cannot produce a valid label for an output it did not compute).[58] Authenticity is what makes garbling useful beyond 2PC, for example in zero-knowledge proofs and verifiable outsourcing. Note what garbling does not provide: a malicious garbler can garble a different function, which Section 8 addresses.

6. Arithmetic MPC

6.1 Circuits over fields and rings

Many computations, such as statistics, auctions, linear algebra and machine-learning inference, are naturally arithmetic. Expressing a 64-bit multiplication as a Boolean circuit costs thousands of AND gates, while an arithmetic circuit over 𝔽p or ℤ2k does it in one multiplication gate. Arithmetic MPC protocols represent every wire as a secret-shared ring element and evaluate gates as follows:[25,2]

  • Addition, subtraction, multiplication by a public constant: local, thanks to linearity (Section 2.4).
  • Multiplication of two shared values: interactive; costs one round and a few field elements per party.
  • Opening a value: every party broadcasts its share.
  • Non-linear functions such as comparison, division or ReLU: built from multiplications and bit decomposition, or by switching to a Boolean or garbled representation (“mixed-protocol” MPC, as in ABY).[61]

Cost is therefore measured in multiplications and in multiplicative depth, which sets the number of rounds. Fixed-point arithmetic is emulated by scaling reals by 2f and truncating after each product, a technique central to secure machine learning.[62,63]

6.2 BGW: honest-majority multiplication

With Shamir shares of degree t and n ≥ 2t + 1 parties, BGW multiplies as follows.[6,64] Each party multiplies its shares locally, obtaining a point di = f(i)g(i) on a polynomial of degree 2t whose constant term is xy. Since 2t + 1 ≤ n points determine it, xy = Σ λidi with public Lagrange coefficients. Each party then re-shares its di with a fresh degree-t polynomial, and everyone combines the sub-shares they receive with the same coefficients. The result is a fresh degree-t sharing of xy, without anybody having seen di in the clear.[64]

Honest-majority protocols are attractive because they need no public-key cryptography at all; three-party replicated-sharing protocols in the style of Araki et al. evaluate billions of gates per second across a data centre.[65] Damgård and Nielsen's protocol brings the communication per multiplication down to O(n) field elements.[66]

6.3 GMW and Boolean sharing

The GMW protocol is the Boolean analogue with XOR shares and any number of corruptions.[5] For an AND gate with inputs a = a1 ⊕ a2 and b = b1 ⊕ b2, the product expands to a1b1 ⊕ a2b2 ⊕ a1b2 ⊕ a2b1; the first two terms are local and the cross terms are computed with OT (party 1 offers (r, r ⊕ a1) and party 2 chooses with b2). Equivalently, one Boolean Beaver triple per AND gate, which is how modern GMW implementations work.[2,43]

6.4 The preprocessing model

The most consequential idea in practical MPC is to split the work into two phases.[30,12]

  • An offline (preprocessing) phase, independent of the inputs and even of the function beyond its size, produces correlated randomness: multiplication triples, random shared bits, random OTs. This is where the expensive cryptography (OT extension, homomorphic encryption) happens.
  • An online phase consumes that randomness to evaluate the circuit on real inputs using only additions and openings. It is information-theoretically secure and extremely fast.

Beaver triples are the canonical form of this correlated randomness.

7. Beaver triples

7.1 The multiplication trick

Donald Beaver observed in 1991 that a multiplication can be reduced to two openings if the parties already share a random multiplication triple ([a], [b], [c]) with c = ab.[30] To compute [xy]:

ε = open([x] − [a]) δ = open([y] − [b]) (a, b uniformly random: ε, δ reveal nothing) xy = (ε + a)(δ + b) = εδ + ε·b + δ·a + ab [xy] = [c] + ε·[b] + δ·[a] + εδ (εδ added by one party only)

Since a and b are uniform and used once, ε and δ are one-time-padded versions of x and y and leak nothing. Everything else is linear, so the whole multiplication costs one round and two openings. A triple must never be reused: two openings ε = x − a and ε′ = x′ − a reveal x − x′.

Worked example

Two parties in 𝔽97 hold shares of x = 12 as (40, 69) and of y = 7 as (60, 44). The dealer gave them a = 5 as (30, 72), b = 9 as (11, 95) and c = 45 as (20, 25).

  1. Party 1 broadcasts x1 − a1 = 10 and y1 − b1 = 49; party 2 broadcasts 69 − 72 ≡ 94 and 44 − 95 ≡ 46. Hence ε = 10 + 94 ≡ 7 and δ = 49 + 46 = 95 ≡ −2.
  2. Party 1: z1 = 20 + 7·11 + 95·30 + 7·95 ≡ 23. Party 2: z2 = 25 + 7·95 + 95·72 ≡ 61.
  3. Check: 23 + 61 = 84 = 12 · 7. Neither party saw x or y; the opened values 7 and 95 are x − a and y − b for uniformly random a, b.

8. Semi-honest versus malicious adversaries

8.1 Adversary models

The security definition of Section 1.1 is parameterised by what corrupted parties may do:[19,52]

ModelCorrupted parties…Typical toolRelative cost
Semi-honest (passive, honest-but-curious)follow the protocol exactly but try to learn from everything they see, alone or in coalition.Basic Yao, GMW, BGW, Beaver with dealer1×
Covertmay deviate, but are caught with probability at least ε (say ½), which deters rational cheaters.Cut-and-choose with few copies[69]≈2-3×

Orthogonal choices are whether corruptions are static (fixed before the protocol starts) or adaptive (chosen during execution, as an attacker hops between machines), and whether the adversary may corrupt a majority. Semi-honest security is meaningful where parties are audited or run attested software, and it protects against later leaks of transcripts; but it says nothing about a party that modifies its code.[1]

8.2 What a malicious party can do

  • Wrong function. A malicious garbler can garble f′(x, y) = y instead of f, and the evaluator, who sees only random-looking ciphertexts, would happily send back its own input.[70]
  • Selective failure. The garbler offers a correct label for yi = 0 and garbage for yi = 1 in Bob's OT. Whether Bob aborts tells Alice the bit.[71,70]
  • Additive attacks on shares. A party adds an error e to its share before opening; the opened value becomes x + e. In Listing 12.5 a single tampered share silently changes BGW's result, and in Listing 12.4 a cheater shifts SPDZ's ε.
  • Inconsistent inputs. Using different values of the same input in different sub-protocols, or bad shares in key generation (Listing 12.6).
  • Malformed messages in threshold signing. Sending maliciously chosen Paillier moduli or skipping range proofs in threshold ECDSA leaked full keys in several wallets in 2023 (Section 9.5).[72]

8.3 From passive to active security

GMW compiler. Each party commits to its input and randomness and proves in zero knowledge, after every message, that the message was computed correctly. This shows feasibility for any protocol, but generic ZK proofs make it slow.[5,73]

Cut-and-choose for garbled circuits. The garbler sends s garbled copies; the evaluator opens a random subset to check and evaluates the rest, taking the majority output. Lindell and Pinkas made this rigorous and handled selective failure by encoding each input bit as the XOR of several random bits.[70] Early protocols needed well over a hundred copies for a 2−40 cheating probability; later techniques reduced this considerably, and a billion-gate malicious computation was demonstrated in 2012.[74]

Authenticated garbling. Wang, Ranellucci and Katz combine one garbled circuit with information-theoretic MACs on wire values produced in preprocessing, removing cut-and-choose; maliciously secure 2PC of an AES block then takes tens of milliseconds on a fast network.[75]

MAC-based secret sharing. SPDZ and its relatives attach a MAC to every shared value (next subsection). TinyOT is the Boolean counterpart.[12,76]

Honest majority with redundancy. Shamir shares are a Reed-Solomon code: with n ≥ 3t + 1 errors can be corrected (BGW's malicious protocol), and with n ≥ 2t + 1 plus broadcast they can at least be detected and identified by VSS.[6,22]

8.4 SPDZ-style MACs

SPDZ shares a global MAC key α additively, so nobody knows it, and represents every value x by additive shares of x together with additive shares of αx:[12,77]

⟨x⟩ = ( [x], [α·x] ) linear operations act on both components; ⟨x⟩ + c updates the MAC by α·c MAC check for opened value x′: each Pᵢ publishes σᵢ = mᵢ − αᵢ·x′ (via commit-then-open) accept iff Σ σᵢ = 0

If a cheater shifts the opened value by e ≠ 0, it would have to shift the MAC by αe, but α is a uniformly random field element unknown to it; it succeeds with probability 1/p. In practice many opened values are checked together with a random linear combination, and the check is done before any output is revealed, so a cheater gains nothing but an abort.[77] Listing 12.4 shows the honest run passing the check and a party that shifts ε by 1 being caught. SPDZ is secure with abort against n − 1 malicious parties; MASCOT (OT-based) and Overdrive (lattice-based) generate its authenticated triples.[13,68]

Rule of thumb. For a new deployment, assume malicious adversaries unless the threat model genuinely rules them out. The overhead of modern actively secure protocols is a small constant factor, and “semi-honest” components inside systems that hold real keys have been the root of practical attacks.[72,1]

9. Threshold signatures

9.1 Why not just share the key?

A (t, n) threshold signature scheme lets any t of n parties produce a signature under one public key, while fewer than t cannot. Desmedt and Frankel introduced threshold cryptography in 1989.[78,79] Shamir-sharing the private key for backup is not enough: to sign, someone must reconstruct the key, and at that instant one machine holds it. A threshold scheme instead runs an MPC protocol whose output is a signature and whose secret input, the key, stays shared for its whole life. Compared with multisignatures (each signer has its own key, and the verifier checks a set), a threshold signature is indistinguishable from an ordinary one: the verifier sees one public key and one signature, which saves space on blockchains and hides the policy.[79]

9.2 Threshold Schnorr and FROST

Schnorr signatures are linear in the secret, which makes them natural to threshold. With key s, public key Y = sG, nonce k and commitment R = kG, a signature is (R, z) with z = k + c·s and c = H(R, Y, m). If s and k are both Shamir-shared, each signer outputs zi = ki + c·λisi and the sum is a valid z. The difficulty is the nonce: it must be jointly random, fresh, and committed before the challenge is known. Stinson and Strobl's scheme generated it with a full DKG per signature;[80] naive two-round variants that let signers sum individual nonces are vulnerable to concurrent attacks (the Drijvers et al. attack on two-round multisignatures and the polynomial-time ROS attack).[81,82]

FROST (Komlo and Goldberg, 2020; RFC 9591, 2024) solves this with two nonces per signer and a binding factor.[32,33]

  1. Round 1 (can be preprocessed): signer i samples (di, ei) and publishes Di = diG, Ei = eiG.
  2. The coordinator fixes the signer set S, the message and the list of commitments B. Each signer computes binding factors ρj = H1(j, m, B), the group commitment R = Σ (Dj + ρjEj) and the challenge c = H2(R, Y, m).
  3. Round 2: signer i returns zi = di + eiρi + λisic.
  4. The coordinator checks each ziG = Di + ρiEi + cλiYi against the public verification share Yi, identifying any cheater, and outputs (R, Σ zi).

RFC 9591 specifies ciphersuites for Ed25519, Ed448, ristretto255, P-256 and secp256k1, and the Ed25519 suite produces signatures that unmodified RFC 8032 verifiers accept.[33] A signer must never reuse its round-1 nonces: as with ordinary Schnorr and ECDSA, two signatures sharing a nonce reveal the signer's key share.

9.3 Threshold ECDSA

ECDSA is much harder because the signature s = k−1(H(m) + r·x) involves the inverse of the shared nonce and a product of two shared values. Protocols compute [k−1] and the product using multiplicative-to-additive (MtA) share conversion, typically via Paillier encryption with zero-knowledge range proofs, or via OT.[85,86] Milestones include MacKenzie and Reiter's two-party DSA (2001), Lindell's fast two-party ECDSA (2017), Gennaro and Goldfeder's multiparty GG18 and the UC-secure, proactive CGGMP protocol with identifiable aborts and a non-interactive online phase.[85,87,88,89] These protocols underpin the “MPC wallets” used by custodians, because Bitcoin and Ethereum verify ECDSA on secp256k1.

9.4 Threshold RSA and BLS

Shoup's 2000 threshold RSA scheme shares d over the integers and is non-interactive: each party publishes x2Δsi mod N with a proof of correctness, where Δ = n! clears the denominators of Lagrange coefficients that cannot be inverted modulo the unknown φ(N).[90] Its weak point is key generation, which needs either a trusted dealer or an expensive distributed RSA modulus protocol. BLS signatures, σ = s·H(m) in a pairing group, are the easiest of all: partial signatures si·H(m) are combined with Lagrange coefficients in the exponent, the result is deterministic and unique, and each partial signature is verifiable with a pairing; no interaction or nonce is needed.[91] Threshold BLS is used for distributed randomness beacons and in proof-of-stake consensus.

9.5 Deployments and pitfalls

Threshold signing went from research to infrastructure within a decade. In 2023 Fireblocks researchers disclosed “BitForge”, practical key-extraction attacks on implementations of GG18, GG20 and Lindell17 in more than fifteen wallet providers: missing zero-knowledge proofs about Paillier keys let a malicious participant recover the full key from a handful of signatures.[72] The lesson matches Section 8: implementations that verify proofs “optionally” are only semi-honest secure. Coinbase open-sourced its production MPC library, cb-mpc, in March 2025, and the Zcash Foundation maintains a FROST implementation in Rust.[92,93,94] Standardisation is underway: NIST's Multi-Party Threshold Cryptography project published its first call for multi-party threshold schemes, NIST IR 8214C, on 20 January 2026, inviting submissions for signatures, encryption, key generation and related primitives with open-source reference implementations.[34,95,96]

10. Distributed key generation

A threshold signature removes the single point of failure during signing, but if a dealer generated the key and split it, that dealer once held it. Distributed key generation (DKG) lets n parties jointly create a key pair so that the public key is output to everyone, each party gets a Shamir share of the private key, and no coalition below the threshold learns anything about the key, which in fact never exists in one place.[97,98]

Pedersen's DKG (“Joint-Feldman”) has every party act as a dealer of a random secret:[97,38]

  1. Party i picks a random polynomial fi of degree t − 1 and broadcasts Feldman commitments Ci,k = ai,kG.
  2. Party i sends fi(j) privately to each party j, who checks it against the commitments and broadcasts a complaint if it fails. Dealers with valid complaints are disqualified.
  3. Party j's key share is sj = Σi fi(j), a share of s = Σi fi(0). The public key is Y = Σi Ci,0, and anyone can compute each party's public verification share Yj = sjG from the commitments.

Gennaro, Jarecki, Krawczyk and Rabin showed that Joint-Feldman does not produce a uniformly random key: a rushing adversary can see the others' commitments and then cause its own disqualification (or not) to bias the result. Their fix first commits with perfectly hiding Pedersen VSS and only then reveals Feldman values.[98] For Schnorr-type signatures the small bias is known to be harmless, so FROST keeps the simpler protocol but adds a Schnorr proof of knowledge of each dealer's ai,0, preventing a party from choosing its contribution as a function of others' (a rogue-key attack, which could otherwise let it control the group key).[32]

Practical DKGs also need a broadcast channel (or an equivalent consensus mechanism) so that all honest parties agree on the set of qualified dealers, and authenticated encrypted channels for the private shares. After generation, resharing protocols, a proactive refresh as in Section 2.5, change shares, membership or threshold while keeping the public key and every address derived from it.[40,89]

# Additive and Shamir secret sharing over a prime field (educational; not constant time)
import secrets
P = 2**127 - 1                                    # Mersenne prime field modulus

# ---- additive (n-out-of-n) sharing -----------------------------------------
def additive_share(x, n):
    shares = [secrets.randbelow(P) for _ in range(n - 1)]
    return shares + [(x - sum(shares)) % P]

def additive_open(shares):
    return sum(shares) % P

def xor_share(bit_string: bytes, n):              # the same idea over GF(2)^k
    parts = [secrets.token_bytes(len(bit_string)) for _ in range(n - 1)]
    last = bit_string
    for s in parts: last = bytes(a ^ b for a, b in zip(last, s))
    return parts + [last]

# ---- Shamir (t-out-of-n) sharing -------------------------------------------
def shamir_share(x, t, n):
    """Random polynomial f of degree t-1 with f(0) = x; share i is (i, f(i))."""
    coeffs = [x] + [secrets.randbelow(P) for _ in range(t - 1)]
    f = lambda z: sum(c * pow(z, k, P) for k, c in enumerate(coeffs)) % P
    return [(i, f(i)) for i in range(1, n + 1)]

def lagrange_at_zero(xs):
    """lambda_i such that f(0) = sum lambda_i f(x_i) for any f of degree < len(xs)."""
    lam = []
    for i in xs:
        num, den = 1, 1
        for j in xs:
            if j != i: num, den = num * j % P, den * (j - i) % P
        lam.append(num * pow(den, -1, P) % P)
    return lam

def shamir_open(shares):
    xs = [i for i, _ in shares]
    return sum(l * y for l, (_, y) in zip(lagrange_at_zero(xs), shares)) % P

# Minimal Ed25519 group arithmetic (RFC 8032 section 5.1); educational, NOT constant time
p = 2**255 - 19
L = 2**252 + 27742317777372353535851937790883648493           # prime order of the base point
d = -121665 * pow(121666, -1, p) % p
SQRT_M1 = pow(2, (p - 1) // 4, p)

def _recover_x(y, sign):
    x2 = (y * y - 1) * pow(d * y * y + 1, -1, p) % p
    x = pow(x2, (p + 3) // 8, p)
    if (x * x - x2) % p: x = x * SQRT_M1 % p
    if (x * x - x2) % p: return None
    if (x & 1) != sign: x = p - x
    return x

_By = 4 * pow(5, -1, p) % p
_Bx = _recover_x(_By, 0)
B = (_Bx, _By, 1, _Bx * _By % p)                  # extended coordinates (X, Y, Z, T)
O = (0, 1, 1, 0)                                  # neutral element

def add(P, Q):
    A = (P[1] - P[0]) * (Q[1] - Q[0]) % p; Bv = (P[1] + P[0]) * (Q[1] + Q[0]) % p
    C = 2 * P[3] * Q[3] * d % p;           D = 2 * P[2] * Q[2] % p
    E, F, G, H = Bv - A, D - C, D + C, Bv + A
    return (E * F % p, G * H % p, F * G % p, E * H % p)

def neg(P): return ((-P[0]) % p, P[1], P[2], (-P[3]) % p)
def sub(P, Q): return add(P, neg(Q))

def mul(s, P):
    Q = O
    s %= L
    while s:
        if s & 1: Q = add(Q, P)
        P, s = add(P, P), s >> 1
    return Q

def eq(P, Q):
    return (P[0] * Q[2] - Q[0] * P[2]) % p == 0 and (P[1] * Q[2] - Q[1] * P[2]) % p == 0

def enc(P) -> bytes:
    zi = pow(P[2], -1, p); x, y = P[0] * zi % p, P[1] * zi % p
    return (y | ((x & 1) << 255)).to_bytes(32, "little")

    x = _recover_x(y, sign)
    if x is None or y >= p: raise ValueError("not a point")
    return (x, y, 1, x * y % p)

# 1-out-of-2 oblivious transfer (Bellare-Micali style, random-oracle model) and IKNP OT extension
# Educational code: semi-honest IKNP, no constant-time arithmetic.
import hashlib, secrets
import ed25519_group as G

def H(*parts, n=16):
    h = hashlib.shake_256()
    for x in parts: h.update(x if isinstance(x, bytes) else repr(x).encode()); h.update(b"|")
    return h.digest(n)

def xor(a, b): return bytes(x ^ y for x, y in zip(a, b))

# ---- base OT: sender has (m0, m1), receiver has bit b and learns only m_b --------------
class BaseOTSender:
    def __init__(self):
        self.c = secrets.randbelow(G.L); self.C = G.mul(self.c, G.B)
    def first(self): return G.enc(self.C)                            # S -> R : C
    def respond(self, pk0_bytes, m0, m1):                             # R -> S : PK0
        PK0 = G.dec(pk0_bytes); PK = [PK0, G.sub(self.C, PK0)]        # PK1 = C - PK0
        out = []
        for i, m in enumerate((m0, m1)):
            r = secrets.randbelow(G.L)
            out.append((G.enc(G.mul(r, G.B)), xor(m, H(G.enc(G.mul(r, PK[i])), i, n=len(m)))))
        return out                                                    # S -> R : (R_i, e_i)

class BaseOTReceiver:
    def __init__(self, b): self.b = b
    def choose(self, C_bytes):
        C = G.dec(C_bytes); self.k = secrets.randbelow(G.L)
        PKb = G.mul(self.k, G.B)                                      # receiver knows log of PK_b only
        PK0 = PKb if self.b == 0 else G.sub(C, PKb)
        return G.enc(PK0)
    def finish(self, cts):
        R, e = cts[self.b]
        return xor(e, H(G.enc(G.mul(self.k, G.dec(R))), self.b, n=len(e)))

def base_ot(m0, m1, b):
    S, Rv = BaseOTSender(), BaseOTReceiver(b)
    return Rv.finish(S.respond(Rv.choose(S.first()), m0, m1))

# ---- IKNP OT extension: k base OTs -> m OTs using only hashing --------------------------
def prg(seed: bytes, nbits: int) -> int:
    return int.from_bytes(hashlib.shake_256(seed).digest((nbits + 7) // 8), "big") >> (-nbits % 8)

def iknp(pairs, choices, k=128):
    m = len(pairs)
    r = sum(bit << i for i, bit in enumerate(choices))                # choice bits as one integer
    # 1) roles reversed: OT-sender picks s and acts as base-OT *receiver*
    s = [secrets.randbelow(2) for _ in range(k)]
    seeds = [(secrets.token_bytes(16), secrets.token_bytes(16)) for _ in range(k)]
    got = [base_ot(k0, k1, sj) for (k0, k1), sj in zip(seeds, s)]    # k public-key OTs in total
    # 2) receiver: column t^j = G(k_j^0), sends u^j = t^j ^ G(k_j^1) ^ r
    t = [prg(k0, m) for k0, _ in seeds]
    u = [tj ^ prg(k1, m) ^ r for tj, (_, k1) in zip(t, seeds)]
    # 3) sender: q^j = G(k_j^{s_j}) ^ s_j * u^j  =  t^j ^ s_j * r
    q = [prg(g, m) ^ (u[j] if s[j] else 0) for j, g in enumerate(got)]
    row = lambda cols, i: sum(((c >> i) & 1) << j for j, c in enumerate(cols))
    S = sum(sj << j for j, sj in enumerate(s))
    # row i: q_i = t_i ^ r_i * s, so H(q_i) and H(q_i ^ s) mask the two messages
    y = []
    for i, (x0, x1) in enumerate(pairs):
        qi = row(q, i).to_bytes(k // 8, "big")
        qs = (row(q, i) ^ S).to_bytes(k // 8, "big")
        y.append((xor(x0, H(i, qi, n=len(x0))), xor(x1, H(i, qs, n=len(x1)))))
    # 4) receiver unmasks the chosen message with H(t_i)
    return [xor(y[i][c], H(i, row(t, i).to_bytes(k // 8, "big"), n=len(y[i][c])))
            for i, c in enumerate(choices)]

# Ends with a full semi-honest two-party run of Yao's millionaires' problem using OT for Bob's input.
import hashlib, secrets
from oblivious_transfer import base_ot

K = 128
def H(*xs):                                       # random-oracle hash to a 128-bit label
    h = hashlib.sha256(b"|".join(x.to_bytes(32, "big") for x in xs)).digest()
    return int.from_bytes(h[:16], "big")
lsb = lambda w: w & 1

# ---- circuits: gates are (op, a, b, out); op in {"AND", "XOR", "INV"} --------------------
def greater_than(n):
    """Wires 0..n-1 = x (LSB first), n..2n-1 = y. Output wire = [x > y] (unsigned). n ANDs."""
    gates, w = [], 2 * n
    def g(op, a, b=None):
        nonlocal w; gates.append((op, a, b, w)); w += 1; return w - 1
    ny0 = g("INV", n)
    c = g("AND", 0, ny0)                          # c1 = x0 AND NOT y0
    for i in range(1, n):                         # c_{i+1} = x_i XOR ((x_i XOR c_i) AND (y_i XOR c_i))
        c = g("XOR", i, g("AND", g("XOR", i, c), g("XOR", n + i, c)))
    return gates, w, [c]

def plain_eval(circ, inputs):
    gates, nw, outs = circ; v = dict(enumerate(inputs))
    for op, a, b, o in gates:
        v[o] = v[a] & v[b] if op == "AND" else v[a] ^ v[b] if op == "XOR" else 1 - v[a]
    return [v[o] for o in outs]

# ---- 1) textbook Yao with point-and-permute: every gate gets a 4-row table ----------------
def garble_classic(circ, n_in):
    gates, nw, outs = circ
    lab = {}
    for w in range(n_in):
        z = secrets.randbits(K); lab[w] = (z, z ^ secrets.randbits(K - 1) << 1 ^ 1)  # opposite colour bits
    tables = []
    for gid, (op, a, b, o) in enumerate(gates):
        z = secrets.randbits(K); lab[o] = (z, (secrets.randbits(K) & ~1) | (1 - lsb(z)))
        f = {"AND": lambda x, y: x & y, "XOR": lambda x, y: x ^ y, "INV": lambda x, y: 1 - x}[op]
        T = [0] * 4
        for va in (0, 1):
            for vb in ((0, 1) if op != "INV" else (0,)):
                A = lab[a][va]; Bl = lab[b][vb] if op != "INV" else 0
                row = 2 * lsb(A) + (lsb(Bl) if op != "INV" else 0)
                T[row] = H(A, Bl, gid) ^ lab[o][f(va, vb)]
        tables.append(T)
    decode = [lsb(lab[o][0]) for o in outs]
    return lab, tables, decode

def eval_classic(circ, tables, in_labels):
    gates, nw, outs = circ; W = dict(enumerate(in_labels))
    for gid, (op, a, b, o) in enumerate(gates):
        A = W[a]; Bl = W[b] if op != "INV" else 0
        W[o] = tables[gid][2 * lsb(A) + (lsb(Bl) if op != "INV" else 0)] ^ H(A, Bl, gid)
    return [W[o] for o in outs]

# ---- 2) free-XOR (Kolesnikov-Schneider) + half-gates (Zahur-Rosulek-Evans) -----------------
def garble_halfgates(circ, n_in):
    gates, nw, outs = circ
    R = secrets.randbits(K) | 1                   # global offset, lsb(R) = 1
    zero = {w: secrets.randbits(K) for w in range(n_in)}   # label for 0; label for 1 = zero ^ R
    tables, j = [], 0
    for op, a, b, o in gates:
        if op == "XOR": zero[o] = zero[a] ^ zero[b]; continue     # no table, no hashing
        if op == "INV": zero[o] = zero[a] ^ R; continue
        A0, B0 = zero[a], zero[b]; A1, B1 = A0 ^ R, B0 ^ R
        pa, pb = lsb(A0), lsb(B0); j1, j2 = 2 * j, 2 * j + 1; j += 1
        TG = H(A0, j1) ^ H(A1, j1) ^ (R if pb else 0)             # generator half-gate
        WG0 = H(A0, j1) ^ (TG if pa else 0)
        TE = H(B0, j2) ^ H(B1, j2) ^ A0                           # evaluator half-gate
        WE0 = H(B0, j2) ^ ((TE ^ A0) if pb else 0)
        zero[o] = WG0 ^ WE0; tables.append((TG, TE))              # two ciphertexts per AND
    return zero, R, tables, [lsb(zero[o]) for o in outs]

def eval_halfgates(circ, tables, in_labels):
    gates, nw, outs = circ; W = dict(enumerate(in_labels)); t = iter(tables); j = 0
    for op, a, b, o in gates:
        if op == "XOR": W[o] = W[a] ^ W[b]; continue
        if op == "INV": W[o] = W[a]; continue                     # garbler already flipped meaning
        TG, TE = next(t); A, Bl = W[a], W[b]; j1, j2 = 2 * j, 2 * j + 1; j += 1
        WG = H(A, j1) ^ (TG if lsb(A) else 0)
        WE = H(Bl, j2) ^ ((TE ^ A) if lsb(Bl) else 0)
        W[o] = WG ^ WE
    return [W[o] for o in outs]

def bits(v, n): return [(v >> i) & 1 for i in range(n)]

code/beaver_mpc.py
# Arithmetic MPC on additive shares: Beaver triples, OT-based triple generation (Gilboa),
# and SPDZ-style information-theoretic MACs that catch a cheating party. Educational only.
import secrets
from oblivious_transfer import base_ot

P = 2**61 - 1
rnd = lambda: secrets.randbelow(P)
def share(x, n):
    s = [rnd() for _ in range(n - 1)]; return s + [(x - sum(s)) % P]
def open_(sh): return sum(sh) % P

# ---- semi-honest n-party arithmetic with a trusted dealer of triples --------------------
def dealer_triple(n):
    a, b = rnd(), rnd()
    return share(a, n), share(b, n), share(a * b % P, n)

def beaver_mul(xs, ys, triple):
    """Inputs: shares of x and y. Output: shares of x*y. One round, two openings."""
    A, Bt, C = triple; n = len(xs)
    eps = open_([(x - a) % P for x, a in zip(xs, A)])        # x - a is public: a masks x
    dlt = open_([(y - b) % P for y, b in zip(ys, Bt)])
    # x*y = c + eps*b + dlt*a + eps*dlt ; the public constant is added by party 0 only
    return [(C[i] + eps * Bt[i] + dlt * A[i] + (eps * dlt if i == 0 else 0)) % P for i in range(n)]

# ---- two-party triples without a dealer: Gilboa's OT-based multiplication ----------------
def gilboa(a, b, bits=61):
    """Alice holds a, Bob holds b. Returns additive shares (u, v) with u + v = a*b mod P."""
    u = v = 0
    for i in range(bits):
        r = rnd()
        m0, m1 = r, (r + a * (1 << i)) % P                    # Alice is OT sender
        got = base_ot(m0.to_bytes(8, "big"), m1.to_bytes(8, "big"), (b >> i) & 1)
        u = (u - r) % P; v = (v + int.from_bytes(got, "big")) % P
    return u, v

def ot_triple():
    a0, b0, a1, b1 = rnd(), rnd(), rnd(), rnd()               # party 0 has (a0,b0), party 1 (a1,b1)
    u1, v1 = gilboa(a0, b1); u2, v2 = gilboa(a1, b0)          # cross terms a0*b1 and a1*b0
    c0 = (a0 * b0 + u1 + v2) % P; c1 = (a1 * b1 + v1 + u2) % P
    return [a0, a1], [b0, b1], [c0, c1]

# ---- SPDZ-style MACs: every shared x also carries shares of alpha*x -----------------------
class Spdz:
    def __init__(self, n):
        self.n = n; self.alpha = share(rnd(), n)              # nobody knows alpha
        self.a = open_(self.alpha)                            # used only by the "dealer" below
        self.opened = []                                      # (value, mac shares) to check later
    def auth(self, x):                                        # dealer-style authenticated sharing
        return share(x, self.n), share(self.a * x % P, self.n)
    def open(self, v, cheat=0):
        s, m = v; val = (open_(s) + cheat) % P                # a cheater shifts its share by `cheat`
        self.opened.append((val, m)); return val
    def add(self, u, v): return [(x + y) % P for x, y in zip(u[0], v[0])], [(x + y) % P for x, y in zip(u[1], v[1])]
    def sub(self, u, v): return [(x - y) % P for x, y in zip(u[0], v[0])], [(x - y) % P for x, y in zip(u[1], v[1])]
    def scale(self, u, k): return [x * k % P for x in u[0]], [m * k % P for m in u[1]]
    def add_const(self, u, k):
        s = u[0][:]; s[0] = (s[0] + k) % P
        return s, [(m + ai * k) % P for m, ai in zip(u[1], self.alpha)]
    def mul(self, u, v, cheat=0):
        a, b = self.auth(rnd()), self.auth(rnd())          # preprocessing: an authenticated triple
        c = self.auth(open_(a[0]) * open_(b[0]) % P)
        eps = self.open(self.sub(u, a), cheat); dlt = self.open(self.sub(v, b))
        z = self.add(self.add(c, self.scale(b, eps)), self.scale(a, dlt))
        return self.add_const(z, eps * dlt)
    def mac_check(self):
        """Each party i publishes sigma_i = m_i - alpha_i * value; the sigmas must sum to 0."""
        return all(open_([(mi - ai * val) % P for mi, ai in zip(m, self.alpha)]) == 0
                   for val, m in self.opened)

# BGW-style honest-majority MPC on Shamir shares (n = 5, t = 2 corruptions, polynomials of degree t).
# Multiplication: local product (degree 2t) then degree reduction by resharing (Gennaro-Rabin-Rabin).
import secrets
P = 2**61 - 1
N, T = 5, 2                                       # needs N >= 2T + 1
XS = list(range(1, N + 1))

def share(x, t=T):
    c = [x] + [secrets.randbelow(P) for _ in range(t)]
    return [sum(ck * pow(i, k, P) for k, ck in enumerate(c)) % P for i in XS]

def lagrange0(xs):
    out = []
    for i in xs:
        num = den = 1
        for j in xs:
            if j != i: num, den = num * j % P, den * (j - i) % P
        out.append(num * pow(den, -1, P) % P)
    return out
LAM = lagrange0(XS)                               # recombination vector for all N points

def reconstruct(sh, xs=XS): return sum(l * s for l, s in zip(lagrange0(xs), sh)) % P

def mul(xs_, ys_):
    d = [a * b % P for a, b in zip(xs_, ys_)]     # degree-2t sharing of x*y, held locally
    sub = [share(di) for di in d]                 # each party re-shares its point with degree t
    # new share of party j = sum_i LAM_i * sub[i][j]; fresh degree-t sharing of x*y
    return [sum(LAM[i] * sub[i][j] for i in range(N)) % P for j in range(N)]

# Distributed key generation on Ed25519: Pedersen-style DKG with Feldman commitments and a
# Schnorr proof of knowledge per dealer (the FROST KeyGen shape). Nobody ever holds the key.
import hashlib, secrets
import ed25519_group as G

def hq(*parts):                                   # hash to a scalar mod L
    h = hashlib.sha512(b"|".join(x if isinstance(x, bytes) else str(x).encode() for x in parts))
    return int.from_bytes(h.digest(), "little") % G.L

def poly_eval(coeffs, x): return sum(c * pow(x, k, G.L) for k, c in enumerate(coeffs)) % G.L

def lagrange0(xs):                                # Lagrange coefficients at 0, mod L
    out = []
    for i in xs:
        num = den = 1
        for j in xs:
            if j != i: num, den = num * j % G.L, den * (j - i) % G.L
        out.append(num * pow(den, -1, G.L) % G.L)
    return out

def commit_eval(C, j):                            # sum_k j^k C_k  ==  f(j)*B  if commitments are honest
    acc = G.O
    for k, Ck in enumerate(C): acc = G.add(acc, G.mul(pow(j, k, G.L), Ck))
    return acc

class Dealer:
    def __init__(self, i, t, ctx=b"demo-dkg"):
        self.i = i
        self.f = [secrets.randbelow(G.L) for _ in range(t)]          # f_i of degree t-1
        self.C = [G.mul(a, G.B) for a in self.f]                      # Feldman commitments
        k = secrets.randbelow(G.L); R = G.mul(k, G.B)                 # PoK of f_i(0): stops rogue keys
        c = hq(ctx, i, G.enc(self.C[0]), G.enc(R))
        self.pok = (R, (k + self.f[0] * c) % G.L); self.ctx = ctx
    def share_for(self, j): return poly_eval(self.f, j)

def check_pok(d):
    R, mu = d.pok; c = hq(d.ctx, d.i, G.enc(d.C[0]), G.enc(R))
    return G.eq(G.mul(mu, G.B), G.add(R, G.mul(c, d.C[0])))

def run_dkg(n, t, cheater=None):
    dealers = [Dealer(i, t) for i in range(1, n + 1)]
    assert all(check_pok(d) for d in dealers), "bad proof of knowledge"
    complaints, secret_shares = [], {}
    for j in range(1, n + 1):                                        # party j checks every share it got
        total = 0
        for d in dealers:
            s = d.share_for(j)
            if cheater == d.i and j == 2: s = (s + 1) % G.L          # dealer sends one bad share
            if not G.eq(G.mul(s, G.B), commit_eval(d.C, j)): complaints.append((j, d.i)); continue
            total = (total + s) % G.L
        secret_shares[j] = total
    Y = G.O
    for d in dealers: Y = G.add(Y, d.C[0])                           # group public key
    Yj = {j: G.O for j in range(1, n + 1)}                           # public verification shares
    for j in Yj:
        for d in dealers: Yj[j] = G.add(Yj[j], commit_eval(d.C, j))
    return Y, secret_shares, Yj, complaints, dealers

12.7 FROST-style threshold Ed25519 signatures

The aggregated signature is passed to Ed25519PublicKey.verify from pyca/cryptography, which knows nothing about thresholds.[83] This is a simplified version of RFC 9591's FROST(Ed25519, SHA-512) and does not match its test vectors (hash domain separation and encodings are simplified); use the RFC or a vetted library for real systems.[33]

code/frost.py
# Two-round FROST-style threshold Schnorr signing on Ed25519 (after Komlo-Goldberg and RFC 9591,
# simplified: ad-hoc hash domain separation, no serialization rules). The output is an ordinary
# Ed25519 signature, checked here with the standard verifier in pyca/cryptography.
import hashlib, secrets
import ed25519_group as G
from dkg import run_dkg, lagrange0, hq
from cryptography.hazmat.primitives.asymmetric.ed25519 import Ed25519PublicKey
from cryptography.exceptions import InvalidSignature

def round1():                                     # each signer: two nonces, two commitments
    d, e = secrets.randbelow(G.L), secrets.randbelow(G.L)
    return (d, e), (G.mul(d, G.B), G.mul(e, G.B))

def binding(i, msg, comms):                      # rho_i binds every nonce to the message and signer set
    enc = b"".join(str(j).encode() + G.enc(D) + G.enc(E) for j, (D, E) in sorted(comms.items()))
    return hq(b"rho", i, msg, enc)

def group_commitment(msg, comms):
    R = G.O
    for i, (D, E) in comms.items(): R = G.add(R, G.add(D, G.mul(binding(i, msg, comms), E)))
    return R

def ed25519_challenge(R, Y, msg):                # exactly the RFC 8032 challenge SHA-512(R || A || M)
    return int.from_bytes(hashlib.sha512(G.enc(R) + G.enc(Y) + msg).digest(), "little") % G.L

def sign(signers, shares, Y, Yj, msg, cheat=None):
    nonces, comms = {}, {}
    for i in signers: nonces[i], comms[i] = round1()             # round 1 (can be preprocessed)
    R = group_commitment(msg, comms); c = ed25519_challenge(R, Y, msg)
    lam = dict(zip(signers, lagrange0(signers)))
    z = {}
    for i in signers:                                            # round 2: one scalar per signer
        (d, e), rho = nonces[i], binding(i, msg, comms)
        z[i] = (d + e * rho + lam[i] * shares[i] * c) % G.L
        if i == cheat: z[i] = (z[i] + 1) % G.L
    # the aggregator verifies every share, so a bad signer is identified, not just detected
    bad = [i for i in signers if not G.eq(G.mul(z[i], G.B), G.add(G.add(comms[i][0],
           G.mul(binding(i, msg, comms), comms[i][1])), G.mul(c * lam[i] % G.L, Yj[i])))]
    return G.enc(R) + (sum(z.values()) % G.L).to_bytes(32, "little"), bad

def verify(Y, msg, sig):
    try: Ed25519PublicKey.from_public_bytes(G.enc(Y)).verify(sig, msg); return True
    except InvalidSignature: return False

if __name__ == "__main__":
    n, t = 5, 3
    Y, shares, Yj, _, _ = run_dkg(n, t)
    msg = b"transfer 2.5 BTC to bc1q...; nonce 7"
    sig, bad = sign([1, 3, 4], shares, Y, Yj, msg)
    print("3-of-5 signature:", sig.hex()[:32] + "...")

    print("only 2 signers (below threshold) -> valid?", verify(Y, msg, sig3))
    sig4, bad = sign([1, 3, 4], shares, Y, Yj, msg, cheat=3)
    print("signer 3 sends a bad share -> valid?", verify(Y, msg, sig4), "| identified:", bad)

14. Exercises

Solutions are hidden; click an exercise to reveal its solution.

14.1 Additive shares. A value x = 37 is additively shared modulo 100 among three parties. Two shares are 58 and 91. What is the third? What do the first two shares alone reveal about x?

x3 = 37 − 58 − 91 = −112 ≡ 88 (mod 100). The first two shares reveal nothing: for every candidate x′ there is exactly one third share (x′ − 149 mod 100) consistent with them, and in a correct sharing the first two shares are uniform and independent of x.

14.2 Shamir reconstruction. In 𝔽13 with t = 3, three parties hold (1, 6), (2, 2) and (3, 11). Recover the secret and the polynomial.

The Lagrange coefficients for {1, 2, 3} at 0 are λ1 = 3, λ2 = −3 ≡ 10, λ3 = 1. So s = 3·6 + 10·2 + 1·11 = 49 ≡ 10. Solving f(x) = 10 + ax + bx² gives a + b ≡ 9 and 2a + 4b ≡ 5, hence b = 0, a = 9: f(x) = 10 + 9x. (A random top coefficient is zero with probability 1/13; that is still a valid sharing.)

14.3 A 2-of-3 sharing in 𝔽11 gives shares (1, 5) and (2, 9). What is the secret?

The line through the points has slope 9 − 5 = 4, so f(0) = 5 − 4 = 1. With Lagrange: λ1 = 2/(2−1) = 2, λ2 = 1/(1−2) = −1, and 2·5 − 9 = 1.

14.4 Prove that any t − 1 Shamir shares are independent of the secret.

Fix t − 1 evaluation points x1, …, xt−1 (all non-zero and distinct) and any values y1, …, yt−1. For each secret s, the t conditions f(0) = s, f(xi) = yi determine exactly one polynomial of degree ≤ t − 1 (Vandermonde matrix invertible). The dealer's t − 1 random coefficients map bijectively to the t − 1 share values, so the shares are uniform in 𝔽pt−1 for every s.[27]

14.5 Tampering. In Exercise 14.2, party 3 reports 12 instead of 11 at reconstruction. What value is reconstructed, and how could the others notice?

The error e = 1 is multiplied by λ3 = 1, so the result is 11 instead of 10. With only t = 3 shares there is no redundancy and the error is undetectable. With a fourth share (or VSS commitments, or MACs) the honest parties see that the four points do not lie on one quadratic.[36,37]

14.6 Beaver multiplication. In 𝔽23, compute xy for x = 5, y = 8 using the triple a = 3, b = 10, c = 30 mod 23 = 7. Give ε, δ and the result.

ε = 5 − 3 = 2, δ = 8 − 10 ≡ 21. Then c + εb + δa + εδ = 7 + 20 + 63 + 42 = 132 ≡ 17, and indeed 5 · 8 = 40 ≡ 17 (mod 23). In the protocol each term except εδ is computed share-wise.[30]

14.7 Why must a Beaver triple never be reused?

If the same [a] masks x in one multiplication and x′ in another, the opened values are ε = x − a and ε′ = x′ − a, so everyone learns ε − ε′ = x − x′. This is the same failure as reusing a one-time pad.

14.8 Communication of Yao. Using the comparator of Listing 12.3, how many bytes of garbled tables does a 32-bit millionaires' comparison need with half-gates and 128-bit labels? How many OTs?

The circuit has n = 32 AND gates; half-gates sends 2 ciphertexts of 16 bytes each per AND, so 32 × 32 = 1 024 bytes. Alice also sends 32 labels for her input (512 bytes) and one decoding bit. Bob needs one OT per input bit: 32 OTs, which OT extension makes cheap.[8,10]

14.9 Prove that free-XOR evaluation is correct.

With labels Au = A0 ⊕ uΔ, Bv = B0 ⊕ vΔ and C0 := A0 ⊕ B0: Au ⊕ Bv = A0 ⊕ B0 ⊕ (u ⊕ v)Δ = Cu⊕v. Security requires Δ to stay hidden, which needs H to be secure under related keys (circular correlation robustness); this is why free-XOR is not a “standard model” result.[59,8]

14.10 Describe a selective-failure attack against Yao with a malicious garbler, and one countermeasure.

In Bob's OT for bit y1, Alice offers the correct label for 0 and a random string for 1. If Bob's evaluation fails (or he complains), Alice learns y1 = 1. Countermeasure: encode each of Bob's input bits as the XOR of s random bits, so that any abort depends on random bits Bob chose and is nearly independent of y; or obtain labels through committed or authenticated OT and cut-and-choose.[70,71]

14.11 In the Bellare-Micali OT of Section 3.2, why can't the receiver learn both messages? Why must the sender pick C freshly rather than let the receiver choose it?

To decrypt both, the receiver needs the discrete logs of PK0 and PK1, whose sum is the discrete log of C; that would solve the discrete-log problem (in the random-oracle model, Computational Diffie-Hellman suffices). If the receiver chose C = cG itself, it could set PK0 = k0G, PK1 = (c − k0)G and decrypt both.[44,45]

14.12 IKNP. With columns qj = tj ⊕ sj·r, show that row i of Q equals ti ⊕ ri·s. Why can't the receiver unmask both messages?

Bit j of row i is qi,j = ti,j ⊕ sjri; collecting over j gives qi = ti ⊕ ri·s. The receiver knows ti, which equals qi if ri = 0 and qi ⊕ s if ri = 1, so it can compute exactly one of the two masks. The other mask needs s, which was hidden by the base OTs.[10]

14.13 Feldman VSS by hand. In the order-11 subgroup of ℤ23* generated by g = 2, the dealer uses f(x) = 4 + 3x mod 11 and publishes C0 = 24, C1 = 23. Verify party 2's share, and show that a share of 9 would be rejected.

C0 = 16, C1 = 8 and f(2) = 10. Check: g10 = 1024 mod 23 = 12, and C0·C12 = 16 · 64 = 1024 ≡ 12. Accept. For the share 9: 29 = 512 ≡ 6 ≠ 12. Reject and complain.[38]

14.14 Why does BGW multiplication need n ≥ 2t + 1 even against semi-honest parties?

The local products lie on a polynomial of degree 2t, which is determined only by 2t + 1 points. With fewer parties the product polynomial cannot be interpolated, so degree reduction is impossible. More fundamentally, information-theoretic MPC with a dishonest majority is impossible for functions such as AND.[6,25]

14.15 Threshold Schnorr. Show that if each signer in set S outputs zi = ki + cλisi with R = Σ kiG, then (R, Σ zi) verifies. What goes wrong if the signers' ki are chosen after seeing the others' commitments?

Σ ziG = Σ kiG + c(Σ λisi)G = R + cY, which is the Schnorr verification equation. If an attacker opens many concurrent sessions and picks its nonce contributions adaptively, it can steer the challenges and solve a ROS instance, forging a signature on a new message. FROST's binding factors make each R depend on all commitments and the message, blocking this.[81,82,32]

14.16 Nonce reuse. A threshold-Schnorr signer reuses its nonce share ki in two sessions with challenges c ≠ c′ and the same signer set. Recover si.

zi − z′i = λisi(c − c′), so si = (zi − z′i) / (λi(c − c′)) mod L. With t such leaks the whole key falls. Hence RFC 9591 requires fresh nonces for every signing attempt.[33]

14.17 Rogue keys in DKG. Without proofs of knowledge, how can the last party to publish choose the group public key? How does a Schnorr proof of knowledge stop it?

After seeing others' Cj,0, the attacker publishes Ci,0 = X − Σj≠i Cj,0 for a key X = xG it knows, so the group key is X. (It cannot then deal consistent shares of its contribution, but in protocols that only sum public keys this is enough.) A proof of knowledge of the discrete log of Ci,0, bound to the party's index and the session, is impossible to produce for such a contribution.[32,98]

14.18 GMW AND gate. Two parties hold a = a1 ⊕ a2, b = b1 ⊕ b2. Using two 1-out-of-2 OTs, produce XOR shares of ab.

ab = a1b1 ⊕ a2b2 ⊕ a1b2 ⊕ a2b1. For a1b2: party 1 picks random r and sends (r, r ⊕ a1) by OT; party 2 chooses with b2 and receives r ⊕ a1b2. Symmetrically for a2b1 with party 2's random r′. Party 1 outputs a1b1 ⊕ r ⊕ (r′ ⊕ a2b1); party 2 outputs a2b2 ⊕ (r ⊕ a1b2) ⊕ r′. Their XOR is ab.[5,2]

15. Trivia

15.1 Who posed the “millionaires' problem”, and where?

Andrew Chi-Chih Yao, in “Protocols for secure computations” at FOCS 1982.[3]

15.2 Threshold secret sharing was invented twice in the same year. By whom, and how did the two schemes differ?

In 1979 Adi Shamir used polynomial interpolation and G. R. Blakley used the intersection of hyperplanes in a geometric space.[27,28]

15.3 What practical problem was the 1985 paper that introduced 1-out-of-2 OT trying to solve?

Contract signing: its title is “A randomized protocol for signing contracts” (Even, Goldreich and Lempel).[41]

15.4 Rabin's 1981 OT report was not easy to find for decades. Where can it be read today?

As Cryptology ePrint Archive paper 2005/187, a reprint of Harvard Aiken Computation Laboratory technical report TR-81.[29]

15.5 Which agricultural commodity was traded in the first large-scale commercial MPC deployment?

Danish sugar-beet production contracts, auctioned with MPC in January 2008.[14]

15.6 Which 1987 paper title promised to play “any mental game”?

Goldreich, Micali and Wigderson's STOC 1987 paper “How to play any mental game”, the GMW protocol.[5]

15.7 What fraction of corrupted parties can BGW tolerate with perfect security against malicious adversaries?

Fewer than one third (t < n/3), and this bound is optimal.[6]

15.8 How many years passed between Yao's protocol and its first complete security proof?

About 23: Yao's paper appeared in 1986 and Lindell and Pinkas published “A proof of security of Yao's protocol for two-party computation” in the Journal of Cryptology in 2009.[4,53]

15.9 “Two halves make a whole” was answered six years later by which paper title?

“Three halves make a whole? Beating the half-gates lower bound for garbled circuits” by Rosulek and Roy (CRYPTO 2021).[8,9]

15.10 What do the letters of SPDZ stand for?

The surnames of its authors: Smart, Pastro, Damgård and Zakarias.[12]

15.11 Expand FROST.

Flexible Round-Optimized Schnorr Threshold signatures.[32]

15.12 Which RFC standardises FROST, and in what month and year was it published?

RFC 9591, June 2024, from the IRTF's Crypto Forum Research Group.[33]

15.13 Cleve's 1986 result shows that something as simple as which task cannot be done fairly with a dishonest majority?

Tossing a fair coin: with half or more of the parties faulty, an adversary can always bias the outcome noticeably.[23]

15.14 Which primitive did Kilian prove “complete” for secure computation in 1988?

Oblivious transfer: “Founding cryptography on oblivious transfer”.[26]

15.15 Which country used secure computation to link tax and education records in a study of working students?

Estonia, using the Sharemind platform.[15]

15.16 What was “BitForge”?

A set of key-extraction vulnerabilities in threshold-ECDSA implementations of many wallet providers, disclosed by Fireblocks researchers in 2023.[72]

15.17 How many public-key OTs does IKNP need to produce a million OTs at 128-bit security?

About 128 (κ), regardless of the number of extended OTs.[10]

15.18 On what date did NIST publish its first call for multi-party threshold schemes?

20 January 2026, as NIST IR 8214C.[34,95]

16. Practitioner's cheat sheet

Choosing a paradigm

Two parties, Boolean logic, high latency: garbled circuits (half-gates). Many parties or arithmetic: secret sharing with Beaver triples. Three servers you trust not to collude: replicated sharing, fastest of all.[8,65]

Threat model

Default to malicious with abort. Accept semi-honest only with attested code and audit logs. Need liveness? Use an honest-majority protocol with guaranteed output or identifiable abort.[24]

Randomness hygiene

Never reuse a Beaver triple, a signing nonce or a garbled circuit. Seed every party's randomness independently; regenerate preprocessing after a crash.

Threshold signing

Use FROST (RFC 9591) for Schnorr/EdDSA and a recent, audited protocol (CGGMP-class) for ECDSA. Verify every zero-knowledge proof; reject non-canonical inputs; rate-limit signing sessions.[33,89,72]

Key lifecycle

Generate keys by DKG, never by a dealer. Refresh shares periodically and on membership change. Back up shares encrypted to separate holders with their own threshold.[98,40]

What MPC does not hide

The output, input sizes, circuit shape, timing and who participated. If the output itself is sensitive, add differential privacy or restrict queries.
