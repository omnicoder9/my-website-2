Modern cipher design has largely solved the problem it set out to solve. Nobody breaks AES-256 or X25519 by attacking the mathematics. Systems are broken because a key was generated from a predictable seed, copied into a crash dump, committed to a public repository, left unrotated for seven years, or held by one administrator who could be bribed or coerced. Kerckhoffs' principle says a system should stay secure when everything except the key is public; the consequence is that all of the security now sits in the keys, and in the processes that create, move, use and eventually destroy them.[1,2,3]

Key management is the discipline that looks after those keys. NIST defines it as the activities involved in handling cryptographic keys and other security parameters during the entire life cycle of the keys, including their generation, storage, establishment, entry and output, use and destruction.[4] ISO/IEC 11770-1 gives an equivalent framework for the international standards community.[5] It is part cryptography, part systems engineering and part organisational policy. Terminology. Keying material means keys plus associated data such as IVs, salts and domain parameters. A cryptoperiod is the time span during which a specific key is authorised for use. A cryptographic module is the hardware, software or firmware boundary that implements approved security functions and contains keys.[4,7]

1. The key lifecycle

SP 800-57 divides the life of a key into four phases and tracks its condition through six states.[4] The phases describe what the organisation is doing with the key; the states describe what the key may be used for at a given moment. 1.1 Key generation

Every key starts as random bits. For symmetric keys SP 800-133 Rev. 2 requires that the bits come directly or indirectly from an approved random bit generator (RBG) that supports at least the security strength the key needs; for asymmetric keys the RBG output seeds the algorithm-specific generation procedure, such as the prime search for RSA or the scalar choice for elliptic-curve keys.[8,9] SP 800-133 also allows a key to be formed by combining several independently generated keys with XOR or a KDF, which is how many key ceremonies combine contributions from several custodians; the result is at least as strong as the strongest input as long as the inputs are independent.[8] A Revision 3 draft (April 2026) adds methods for deriving asymmetric key pairs.[10]

Three rules dominate practice:

  1. Use a cryptographically secure generator. In Python that means secrets or os.urandom, never random; in browsers crypto.getRandomValues; in hardware, the module's own DRBG seeded from a validated entropy source.[9,11,12]
  2. Generate where the key will live. A private key generated inside an HSM, TPM or secure enclave never has to cross a boundary in plaintext. Keys generated on a laptop and imported later have an unrecorded history.[4,7]
  3. Record metadata at birth. Algorithm, length, owner, purpose, permitted operations, creation date and cryptoperiod should be bound to the key from the start; SP 800-130 calls these the key's metadata and requires a key management system to protect them as carefully as the key.[13]

The best-known failures are generation failures. In 2008 a Debian patch removed almost all entropy from OpenSSL's pool, leaving the process ID (at most 32,768 values) as the only variable input, so every SSH and TLS key generated on affected systems for two years came from a tiny enumerable set.[14] In 2012 Heninger and colleagues scanned the internet and factored the RSA keys of 0.50% of TLS hosts and 0.03% of SSH hosts, because embedded devices generated keys at first boot before their entropy pools were seeded, producing moduli that shared primes.[15] In 2017 the ROCA flaw in an Infineon library generated RSA primes with so much structure that 1024- and 2048-bit keys could be factored in practice; it affected TPMs, smart cards and national identity cards.[16]

Worked example: key check values. When a key is entered into an HSM in components, operators need to confirm the result without displaying it. The usual method is a key check value (KCV): encrypt an all-zero block with the key and publish the first three bytes. With the FIPS-197 example key 000102…0f, AES-128 of the zero block begins c6a13b, so its KCV is C6A13B (checked in listing 5.1).[17,18] Three bytes leak only 24 bits about a 128-bit key, but some vendors now prefer a CMAC-based KCV because an encryption of a known block is itself a usable plaintext/ciphertext pair.

1.2 Key distribution

Distribution moves keying material from where it was generated to where it will be used. SP 800-57 distinguishes manual (out-of-band) distribution, such as couriered key components on paper or smart cards, from automated distribution over a network protected by previously established keys.[4] Manual distribution needs physical controls: tamper-evident envelopes, split components carried by different couriers, and receipts. Automated distribution needs a key-transport or key-agreement protocol (section 1.3) and, for public keys, a way to bind the key to an identity, usually an X.509 certificate.[19]

The classic scaling problem is the reason key distribution centres exist. If n parties each share a separate key with every other party, the system needs n(n−1)/2 keys: about 5 million for 3,200 users. With a trusted centre that shares one long-term key with each user, the number drops to n, and the centre hands out short-lived session keys on demand. This is the design of Needham–Schroeder (1978) and its descendant Kerberos.[20,21] Public-key cryptography solves the same problem differently: each user publishes one public key, and the hard part becomes authenticating that public key rather than keeping it secret.[22]

Public keys need integrity and authenticity, not confidentiality. Secret and private keys need all three. SP 800-57 also requires that the recipient be able to confirm the intended use of the key, which is why wrapped-key formats carry metadata and why X.509 certificates carry key-usage extensions.[4,19]

1.3 Key establishment

Key establishment is the process by which two or more parties end up with a shared secret key. It comes in two forms:[4,23,24]

  • Key transport: one party chooses the key and sends it, encrypted under the other party's key. RSA-OAEP key transport (SP 800-56B) and AES key wrap (SP 800-38F) are examples.[24,25,26]
  • Key agreement: both parties contribute, and neither alone determines the result. Diffie–Hellman and its elliptic-curve forms (ECDH, X25519) are the standard examples.[22,23,27] The raw shared secret is never used directly; it goes through a key-derivation step, specified in SP 800-56C, that binds it to the identities and context.[28,29]

Key-encapsulation mechanisms (KEMs) such as ML-KEM (FIPS 203) sit between the two: the sender runs an encapsulation algorithm against the recipient's public key and gets back a fresh shared secret plus a ciphertext, so the sender does not choose the secret directly but the recipient contributes no fresh randomness.[30] TLS 1.3 now commonly combines X25519 with ML-KEM-768 in a hybrid exchange, standardised in RFC 10024 (August 2026), so that the session key stays secret unless both components are broken.[31,32]

Two properties separate good establishment schemes from weak ones. Forward secrecy means that compromise of long-term keys does not expose session keys from earlier sessions; it requires ephemeral contributions that are deleted after use, which is why TLS 1.3 removed static-RSA key transport entirely.[31] Key confirmation means each party gets evidence that the other really derived the same key, usually by exchanging MAC tags computed under a key derived from the shared secret (SP 800-56A section 5.9).[23]

1.5 Key activation

A key that has been generated and distributed is in the pre-activation state: it exists but must not yet be used to protect data. Activation moves it to active, either on a scheduled date or by an explicit operation.[4] Separating the two lets an organisation distribute a key well ahead of time, for example pushing next quarter's key to every server so that the switch-over is instantaneous, while guaranteeing nobody uses it early. X.509 certificates express the same idea with their notBefore field, and DNSSEC pre-publishes a new key in the DNS before it begins signing so that resolvers have it cached when it is needed.[19,41,42]

Activation is also a natural control point. Many HSMs require a quorum of operator cards before a key can be used at all, and Vault starts sealed: it holds its encrypted data but cannot decrypt anything until enough unseal-key shares are supplied to reconstruct the key that decrypts its root key.[43]

1.6 Key usage

During the active state a key should be used only for its authorised purpose, by authorised entities, with the authorised algorithm. SP 800-57 section 5.2 states that, in general, a single key should be used for only one purpose (encryption, integrity, signature, key wrapping and so on), and section 4.3 returns to why.[4] Usage controls are enforced in three places: in the key's metadata (for example the CKA_SIGN, CKA_DECRYPT and CKA_EXTRACTABLE attributes in PKCS#11), in access policies (IAM policies in a cloud KMS) and in the protocol, which can bind context to the key, as AWS KMS does with its encryption context authenticated data.[39,44]

Usage also has quantitative limits. AES-GCM with random 96-bit nonces should not encrypt more than 232 messages under one key, because the chance of a nonce repeating grows quadratically; TLS 1.3 sets explicit limits on how much data each key may protect before a key update is required.[31] A nonce reused with ECDSA is worse: it reveals the private key, as happened with the PlayStation 3 firmware signing key in 2010.[45]

1.7 Key rotation

Rotation replaces a key with a new one at the end of its cryptoperiod or on demand. The new key should be generated independently; deriving it from the old key is called key update and is permitted only in limited circumstances because a compromise of the old key then exposes the new one.[4] Rotation limits the amount of data protected by any one key, bounds the damage from an undetected compromise, and keeps the procedures exercised so that an emergency rotation after a known compromise is routine rather than a crisis.

SP 800-57 Table 1 suggests cryptoperiods by key type. A few of them, summarised:[4]

Cloud services turn rotation into a configuration setting. AWS KMS rotates a customer-managed symmetric key every 365 days by default, lets the period be set anywhere from 90 to 2,560 days, and allows up to 25 on-demand rotations per key.[46,47] Google Cloud KMS does not re-encrypt existing data when a key rotates, keeps old versions enabled until they are destroyed, and does not support automatic rotation for asymmetric keys, because a new public key must be distributed.[48] Azure Key Vault requires at least seven days between creation and rotation and recommends rotating encryption keys at least every two years.[49] In all three, rotation creates a new key version under the same key identifier: ciphertexts record which version wrapped them, and old versions remain available for decryption. That is the OUP/RUP split of Figure 4 implemented as an API.

Rotation does not re-encrypt data. Rotating a KMS key changes which key version protects new data. Data, or wrapped DEKs, already protected by the old version are still protected only by the old version until they are re-wrapped. If the reason for rotating is a suspected compromise, re-wrapping or re-encrypting is the actual remedy.[48,49]

1.8 Key renewal

Renewal is often confused with rotation, and in the public-key world the difference matters. SP 800-57 distinguishes:[4]

  • Certificate renewal: a new certificate is issued for the same public key, with a new validity period. The key itself is not replaced, so the total time that key is used grows with each renewal and must still respect its cryptoperiod.
  • Rekeying: a new, independently generated key pair replaces the old one and a new certificate is issued for it. This is rotation in the sense of section 1.7.
  • Key update: the new key is derived from the old one by a non-reversible function. It is cheap but provides no recovery from compromise, since anyone who has the old key can compute the new one. The TLS 1.3 KeyUpdate message is a key update of this kind, which still gives forward security (an attacker who learns the new key cannot recover the old one).[31]

In OpenPGP a primary certification key is often long-lived while encryption and signing subkeys are given short expiry dates and renewed or replaced; the expiry date of a key can be extended by re-signing it with the primary key.[35,50] Listing 5.7 creates such a key with a two-year primary and a one-year subkey.

1.9 Key backup

Losing a key that protects stored data is equivalent to destroying the data. A backup is a copy of operational keying material kept so that the key can be restored if the primary copy is lost or damaged; an archive holds keys after their cryptoperiod so that old data can still be processed.[4] Backups need the same protection as the original and are usually stored wrapped under a backup KEK, often split among custodians, and kept in a different location.

Not every key should be backed up. SP 800-57 Table 5 recommends against backing up private signature keys in general, because a copy weakens the claim that only the owner could have produced a signature, and if the key is lost the owner can simply generate a new one and certify it.[4] The same table says ephemeral keys are never backed up, and keys that only protect data in transit, such as session keys, have nothing to recover once the session ends. Data-encryption keys for stored data, and the KEKs that protect them, are exactly the keys that must be backed up. Vault's documentation states the consequence bluntly: if the seal mechanism or its keys are permanently deleted, the cluster cannot be recovered, even from backups.[43]

1.10 Key recovery

Key recovery retrieves a key from backup or archive so that data can be decrypted, for example when an employee leaves, a smart card is lost, or a court orders disclosure.[4] It is different from key escrow, in which a copy is deposited with a third party specifically so that someone other than the key owner can obtain it (section 4.7). A recovery capability is a deliberate weakness, so SP 800-57 asks for a written key recovery policy that states which keys are recoverable, who may request recovery, who must approve it, how requesters are authenticated and how each recovery is audited (section 4.8).[4]

Most enterprise recovery schemes work by wrapping an extra copy of each data-encryption key, or of the key above it, under a recovery key held somewhere else. Full-disk encryption is the everyday example: BitLocker normally unlocks the volume with a TPM protector and treats the device as fully protected only once a recovery key has also been created and backed up, so the disk can still be opened if the TPM refuses (after a firmware change, say) or the motherboard dies.[51]

1.11 Key revocation

Revocation removes a key from use before the end of its planned cryptoperiod, because it has been or may have been compromised, its owner has left, or its use has changed.[4] The hard part is telling everyone who relies on the key. For public keys bound in certificates, the issuing CA publishes a certificate revocation list (CRL) or answers Online Certificate Status Protocol (OCSP) queries, and relying parties are expected to check.[19,52] For OpenPGP keys the owner publishes a revocation signature, which is why GnuPG generates a revocation certificate as soon as a key is created and recommends storing it offline.[35,50] For symmetric keys in a KMS, revocation is a state change: the key version is disabled, and every subsequent decrypt request fails.

A compromise-recovery plan should exist before it is needed. SP 800-57 lists its contents: who is notified, how the compromised key is identified and replaced, how data protected under it is re-protected, and how the cause is investigated.[4] Key compromise itself is discussed in section 4.3.

1.12 Key destruction

When a key is no longer needed, every copy should be destroyed so that it cannot be recovered: the operational copy, backups, archived copies, and plaintext remnants in memory, swap and logs.[4] In a cryptographic module destruction is called zeroisation; FIPS 140-3 requires modules to provide a way to zeroise all unprotected sensitive security parameters.[7] Destroying a key renders everything encrypted under it unreadable, which is the basis of cryptographic erase (crypto-shredding), one of the sanitisation methods in SP 800-88 Rev. 2: instead of overwriting every block of a disk or every replica of a database, destroy the key and the ciphertext becomes noise.[53] Section 4.6 explains why this is often more reliable than overwriting.

Metadata about a destroyed key (its identifier, when and why it was destroyed) is usually kept for audit. SP 800-57 calls this the destroyed state; the key no longer exists but its record does.[4]

2.1 Master keys

A master key is a symmetric key used to derive or protect other keys rather than data. SP 800-57 describes a symmetric master key as one used to derive other symmetric keys, for example data-encryption or key-wrapping keys, using a key-derivation function, and suggests a cryptoperiod of about a year.[4,54] Payment systems are the classic example: under the DUKPT scheme of ANSI X9.24, a base derivation key held only in the acquirer's HSM yields a unique initial key for each PIN pad, and every transaction key is derived from that, so a compromised terminal exposes neither the base key nor its other transactions.[18] In general use the term is loose: some products call the top of their hierarchy the master key, others the root key.

2.2 Root keys

A root key anchors trust: everything else in a hierarchy can be traced back to it, and nothing vouches for it except procedure. A root CA's private key signs the intermediate certificates of a PKI; the root key-signing key (KSK) of the DNS signs the keys that sign the DNS root zone; the root key of a KMS or secrets manager protects every other key it holds.[19,43,55] Root keys are used rarely and guarded heavily. They are typically generated in an HSM in a formal ceremony, kept offline, backed up as shares among several custodians, and activated only when a quorum is present.

Case study: the DNS root KSK. The private half of the DNS root key-signing key is held in HSMs at two key-management facilities in the United States. It is used only at scripted, filmed key signing ceremonies, a few times a year, to sign the zone-signing keys for the coming quarter: KSK Ceremony 63 on 12 November 2026 signed the keys for the first quarter of 2027.[55] The ceremonies depend on volunteers from the internet community: IANA lists 14 cryptographic officers (seven for each facility), a quorum of whose smart cards is needed to activate the HSMs, and seven recovery key share holders, who hold shares of a backup key that could rebuild the system if both facilities were lost.[56] The root KSK was rolled for the first time on 11 October 2018, and IANA's schedule plans the generation of a successor, KSK-2027, for April 2027.[41,55]

2.3 Session keys

A session key protects a single communication session and is discarded when it ends. It is almost always produced by key establishment (section 1.3) and expanded by a KDF into several working keys: in TLS 1.3 each direction gets its own traffic secret, from which the record-protection key and IV are derived.[31] Short-lived session keys limit how much traffic any one key protects, and if they come from ephemeral key agreement they give forward secrecy. Kerberos tickets are a centralised alternative: the key distribution centre generates a fresh session key and delivers it to both parties, encrypted under each one's long-term key.[21]

2.4 Data-encryption keys

A data-encryption key (DEK) encrypts data at rest: a file, a database column, a disk volume, an object in cloud storage. Google's documentation says it directly: the key used to encrypt the data itself is called a data encryption key.[38] DEKs are numerous and local. Best practice is a fresh DEK for every object or every write, kept next to the ciphertext in wrapped form; Google recommends generating a new DEK every time data is written, which removes any need to rotate DEKs.[38] The DEK is used for bulk AEAD encryption and never sent to the KMS in plaintext except to be wrapped.

2.5 Key-encryption keys

A key-encryption key (KEK), also called a key-wrapping key, encrypts other keys. SP 800-57 calls it a symmetric key-wrapping key and gives it the same cryptoperiod guidance as a data-encryption key.[4] The point of a KEK is leverage: one KEK inside an HSM can protect millions of DEKs outside it, so the expensive, well-guarded resource stays small. KEKs should only ever wrap keys, with a dedicated key-wrap algorithm (section 3.4), and never encrypt ordinary data; mixing the two lets an attacker who can get data encrypted under a KEK obtain something that looks like a wrapped key.[25]

2.6 Signing keys

A signing key is the private half of a signature key pair, used to produce digital signatures that anyone with the public verification key can check. Its management differs from that of encryption keys in three ways. First, the private key should have exactly one holder, so it is generally not backed up or escrowed (section 1.9). Second, the public key may need to remain usable for verification long after the private key is retired, so its cryptoperiod is longer.[4] Third, a stolen signing key lets an attacker impersonate the owner indefinitely, not just read old data. The Storm-0558 intrusion in 2023 showed how far that reaches: an attacker with a Microsoft consumer-account signing key, created in 2016, forged authentication tokens accepted by Exchange Online and read the email of US government officials. The Cyber Safety Review Board's report blamed a cascade of failures, including that the key had not been rotated, which it said Microsoft had stopped doing automatically for consumer keys in 2021.[57,58]

2.7 Authentication keys

An authentication key proves identity or message origin. SP 800-57 separates symmetric authentication keys, used with MACs to give integrity and source authentication, from private/public authentication key pairs, used to authenticate an entity in a protocol, such as a TLS client certificate or a FIDO2 credential.[4] An authentication key is used to prove possession at the moment of a transaction, so, unlike a signing key whose signatures may be checked years later, it rarely needs a long verification life. Hardware-bound authentication keys (passkeys in a secure enclave, TPM-held device keys) are now the norm, because a key that cannot be extracted cannot be phished.[36,37]

2.8 Ephemeral keys

An ephemeral key is generated for one execution of a key-establishment process and destroyed immediately afterwards; SP 800-57's cryptoperiod for a private ephemeral key-agreement key is a single transaction.[4,23] Ephemeral keys are what give forward secrecy (Figure 3), and their management is very simple: never store, back up, archive or reuse them. Reuse turns them into static keys and can break protocols that assume freshness.

2.9 Long-term keys

A long-term or static key is used across many sessions or transactions, typically as an identity: a server's certificate key, a user's OpenPGP key, the long-term key a Kerberos KDC shares with each principal.[21,23,35] Because a long-term key accumulates value over time, it gets the strongest storage, the most careful backup decisions and the most planned rotation. A well-designed protocol uses long-term keys only to authenticate ephemeral exchanges, so that their compromise allows future impersonation but not decryption of past traffic.[31,33]

3. Key management architecture

A cryptographic key management system (CKMS) is the set of components, policies and people that carries keys through their lifecycle. SP 800-130 is a framework for designing one: it lists the topics a CKMS design must document, from roles and key metadata to how keys are generated, distributed, stored, recovered and destroyed. SP 800-152 profiles it for US federal systems.[13,59] Architecturally, the choices fall into a few recurring patterns.

3.1 Centralised key management

In a centralised design, one logical service generates, stores and controls keys for many consumers. Applications authenticate to the service and ask it to perform operations (wrap this DEK, sign this hash) or to release keys they are entitled to. Kerberos's key distribution centre, an enterprise key manager reached over KMIP, and every cloud KMS follow this pattern.[21,39,60]

Centralisation gives one place to enforce policy, one audit log, consistent rotation and a single point of revocation. Its costs are availability (if the KMS is down, nothing can decrypt), scale (every operation is a network round trip) and concentration of risk (the KMS is the most valuable target in the organisation). Envelope encryption (section 3.5) and DEK caching address the first two; HSMs, quorum controls and strict separation of administrative roles address the third.[61]

3.2 Distributed key management

In a distributed design there is no single authority. Each party generates and holds its own keys and establishes shared keys pairwise, using authenticated key agreement or, in the OpenPGP web of trust, by vouching for each other's public keys.[22,35] End-to-end encrypted messengers are distributed at the key level even when a central server relays messages: device keys never leave the device, and session keys are agreed between endpoints and ratcheted forward.[62] Threshold schemes (section 4.11) distribute a single key itself, so that no one machine ever holds it.

3.3 Key hierarchies

A key hierarchy organises keys in layers, each protecting the layer below. The usual shape has three or four levels: a root key in an HSM, one or more KEKs (often per tenant, application or region), and DEKs that encrypt data.[4,63] The advantages are concrete. The expensive protections apply only at the top, where there are few keys. Rotating a KEK means re-wrapping a few DEKs rather than re-encrypting terabytes of data. Access control can follow the tree: granting a service access to one KEK grants it exactly the data underneath. And destroying one node crypto-shreds its whole subtree.

Real systems layer the same idea several times. Apple's data protection, for example, gives each file its own key, wraps it under a class key, and protects the class keys with keys derived from the device's hardware UID and the user's passcode inside the Secure Enclave, so erasing the effaceable storage that holds one wrapping key renders the whole device unreadable at once.[36] Vault encrypts its data with keys in a keyring, encrypts the keyring with a root key, and encrypts the root key with the unseal key, which is either split into Shamir shares or held by an external KMS or HSM.[43]

3.4 Key wrapping

Key wrapping encrypts a key under a KEK with an algorithm designed for keys rather than general data. SP 800-38F specifies three: AES Key Wrap (KW), AES Key Wrap with Padding (KWP) and a triple-DES variant (TKW).[25] KW is the algorithm of RFC 3394: it runs six passes over the key in 64-bit halves, calling AES 6n times for an n-block key, and prepends a fixed integrity check value A6A6A6A6A6A6A6A6 that unwrap verifies.[64] KWP (RFC 5649) adds a length indicator so that keys of any length can be wrapped.[65]

Why not just use AES-GCM? You can, and many systems do (listing 5.3 wraps DEKs with AES-GCM). Dedicated key-wrap modes exist because they need no nonce: KW is deterministic, its security rests on the key being wrapped being high-entropy and unique, and it has the property Rogaway and Shrimpton formalised as deterministic authenticated encryption, which is secure without a nonce as long as each input is distinct.[66] That removes the risk of nonce reuse in hardware with poor randomness, and makes wrapping reproducible. The price is that wrapping the same key twice under the same KEK gives the same output, which reveals that it is the same key.

Asymmetric keys are wrapped too. PKCS#8 and the Asymmetric Key Packages of RFC 5958 define containers for private keys, encrypted under a passphrase-derived or symmetric key; PKCS#11 has C_WrapKey and C_UnwrapKey so that keys can move between HSMs without ever being exposed in plaintext; and HPKE (RFC 9180) wraps a key to a recipient's public key.[34,44,67]

3.5 Envelope encryption

Envelope encryption is key wrapping used as an architecture. AWS defines it as the practice of encrypting plaintext data with a data key, and then encrypting the data key under another key.[68] The procedure is:

  1. Generate a fresh DEK locally, or ask the KMS for one (AWS GenerateDataKey returns the DEK both in plaintext and wrapped).
  2. Encrypt the data locally with the DEK using an AEAD such as AES-256-GCM.
  3. Have the KMS wrap the DEK under a KEK that never leaves the KMS, binding context such as the tenant and table as additional authenticated data.
  4. Store the ciphertext together with the wrapped DEK and the KEK version; erase the plaintext DEK from memory.
  5. To decrypt, send the wrapped DEK (and the same context) to the KMS, get the DEK back, decrypt locally.

Kubernetes uses envelope encryption to protect Secrets in etcd: the API server encrypts each resource with a DEK and has an external KMS plugin wrap the DEK, so a stolen etcd backup is useless without access to the KMS.[69] SOPS does the same for configuration files, encrypting the values in a YAML or JSON file with a data key that is wrapped separately for each configured KMS, age or PGP recipient.[70]

3.6 Key derivation trees

Instead of storing many keys, a system can store one and derive the rest on demand with a KDF, using labels that name each key's position and purpose. HKDF (RFC 5869) and the counter-mode KDFs of SP 800-108 are the usual tools.[54,71,72] A tree of derivations gives a hierarchy without storage: Ktenant = KDF(Kroot, "tenant=acme"), then Kpurpose = KDF(Ktenant, "purpose=db-encryption"). Anyone holding a node can compute its subtree but nothing above or beside it, because a KDF is one-way and its outputs for different labels are independent.

Derivation trees appear everywhere once you look. The TLS 1.3 key schedule is a tree rooted in the handshake secret, with labels such as "c hs traffic" and "s ap traffic".[31] TPM 2.0 does not store its primary keys at all: it re-derives them from a hierarchy's primary seed each time, which is why the same template always gives the same storage root key on the same TPM.[40,73] Bitcoin's BIP 32 derives a whole wallet of key pairs from one seed, with "hardened" derivation steps that stop a leaked child private key plus the parent public key from revealing the parent private key.[74] The Signal double ratchet combines a symmetric-key ratchet like Figure 9's with repeated Diffie–Hellman steps, so that keys heal after a compromise as well as protecting the past.[62]

The trade-off is that derived keys cannot be rotated independently: to replace one leaf you change its label (add a version number) or re-key the node above. And because everything is reachable from the root, the root deserves the strongest protection in the system.

3.7 Hardware security modules

A hardware security module (HSM) is a tamper-resistant computer whose job is to generate, store and use keys without ever exposing them. Keys are created inside, marked non-extractable, and used through an API: the application sends data and a key handle, and gets back a ciphertext or signature.[7,44] HSMs come as PCIe cards, network appliances, USB tokens and smart cards, and as the hidden back end of every cloud KMS.[39,63]

The assurance standard is FIPS 140-3, which defines four security levels. Level 1 requires correct, approved algorithms. Level 2 adds tamper evidence and role-based authentication. Level 3 adds tamper resistance with active zeroisation of keys and identity-based operator authentication. Level 4 adds protection against environmental attacks, such as voltage and temperature excursions, and penetration of the enclosure from any direction.[7] FIPS 140-2 validations were moved to the historical list in September 2026, so procurement now asks for FIPS 140-3 certificates.[75] Payment HSMs are additionally evaluated against PCI requirements.[76]

Applications talk to HSMs through standard APIs. PKCS#11 (Cryptoki), maintained by OASIS, is the common C interface: version 3.1 became an OASIS Standard in July 2023 and version 3.2 reached Committee Specification in November 2025.[44,77] KMIP (Key Management Interoperability Protocol, version 2.1 approved December 2020) is the wire protocol for managing keys in a key manager: create, register, locate, activate, revoke and destroy map directly onto the lifecycle of section 1.[60] SoftHSM implements PKCS#11 in software for testing.[78]

3.8 Trusted Platform Modules

A Trusted Platform Module (TPM) is a small, inexpensive security chip (or firmware equivalent) built into PCs and servers, specified by the Trusted Computing Group; version 185 of the TPM 2.0 library specification was published in March 2026.[40] Where an HSM is a shared, high-throughput service, a TPM is a per-device root of trust with modest performance. It provides:[40,73]

  • Hierarchies with primary seeds. TPM 2.0 has platform, storage (owner) and endorsement hierarchies, plus a null hierarchy whose seed changes on every reboot. Primary keys are derived from a seed on demand, as in section 3.6.
  • An endorsement key (EK), unique to the chip and usually certified by the manufacturer, which identifies a genuine TPM.
  • Key storage without storage. Ordinary keys are wrapped under a parent key and stored on disk as blobs that only this TPM can load: a key hierarchy (Figure 11).
  • Sealing. Data can be sealed to the values of platform configuration registers (PCRs), which record measurements of the boot chain, so a disk key is released only if the firmware and boot loader are unmodified. BitLocker and Linux systemd-cryptenroll use this.[51]
  • Attestation: signing PCR values with an attestation key, so a remote verifier can check what booted.

TPMs are not invulnerable. ROCA weakened RSA keys generated by Infineon TPMs, and the TPM-FAIL attacks of 2019 recovered ECDSA keys from Intel's firmware TPM and an STMicroelectronics TPM through timing side channels.[16,79] The tpm2-tools project gives command-line access to TPM functions on Linux.[80]

3.9 Cloud key management services

A cloud KMS (AWS KMS, Google Cloud KMS, Azure Key Vault and others) is a centralised, multi-tenant key manager built on fleets of HSMs and exposed through an authenticated API.[39,49,63] The customer creates logical keys, sets IAM policies on who may use them for which operations, and calls Encrypt, Decrypt, GenerateDataKey or Sign; the key material normally never leaves the provider's HSMs. Common features are:

  • Key versions and automatic rotation, with old versions kept for decryption (section 1.7).[46,48,49]
  • Envelope encryption as the integration pattern for storage services.[38,68]
  • Audit logging of every use of every key, which makes the KMS a detective control as well as a preventive one.
  • Scheduled deletion with a waiting period, so that an accidental or malicious destroy can be cancelled.
  • Customer-managed and external keys (BYOK, HYOK), where the customer imports key material or keeps the KEK in their own HSM outside the cloud, to retain the ability to cut off access.

The trust question is unavoidable: the provider operates the HSMs and the software in front of them. Providers publish detailed descriptions of their designs, such as AWS's cryptographic-details document and Google's KMS deep dive, so that customers can judge the controls, and they hold FIPS 140 validations for the HSMs.[39,63]

3.10 Secrets management systems

Not every secret is a cryptographic key. Database passwords, API tokens, OAuth client secrets and TLS private keys for services are all secrets, and they leak more often than keys because they are handled by more people and copied into more places: configuration files, container images, CI logs and source repositories. A secrets manager (HashiCorp Vault, AWS Secrets Manager, Google Secret Manager, Azure Key Vault secrets, Kubernetes Secrets with KMS encryption) stores them encrypted, releases them to authenticated workloads, rotates them and logs access.[43,69,81]

The OWASP secrets-management guidance stresses centralisation, short lifetimes, least privilege and audit, and treats secret sprawl as the main risk.[81] Mature systems add three capabilities:

  • Dynamic secrets: instead of storing a long-lived database password, the manager creates a fresh credential for each requester with a short lease and revokes it when the lease expires.
  • Encryption as a service: Vault's transit engine encrypts data for applications without ever revealing the key, supports key versions, can archive versions older than a configured min_decryption_version, and offers a rewrap operation that upgrades ciphertext to the newest version without exposing the plaintext; its documentation recommends periodic rotation even in the absence of compromise.[82]
  • Leak detection: secret scanning on code hosts, such as GitHub's, and tools such as Gitleaks look for credentials committed to repositories so they can be revoked.[83,84]

Every secrets manager has a bootstrapping problem, sometimes called secret zero: the workload needs a credential to fetch its other credentials. Platform identity (cloud instance roles, Kubernetes service-account tokens, TPM-attested device identity) is the usual answer, because it lets the platform vouch for the workload without a stored secret.

4. Key security

4.1 Key entropy

A key is only as unpredictable as the process that produced it. The relevant measure is min-entropy, H∞ = −log2(maxx Pr[X = x]), which counts the attacker's chance of guessing the single most likely value. A 128-bit key drawn uniformly at random has 128 bits of min-entropy; a 128-bit key derived from a timestamp has perhaps 20.[11,12] SP 800-90B specifies how entropy sources are designed, tested and assessed, and SP 800-90A specifies the DRBGs that stretch a seed of full entropy into as many key bits as needed.[9,11]

The common entropy mistakes are well documented: seeding from the time or process ID (Debian, 2008), generating keys at first boot before the pool is ready (the 2012 scans), using a non-cryptographic generator such as Mersenne Twister, and confusing length with entropy.[14,15] Human-chosen secrets are the extreme case. A random 8-character lowercase password has 268 ≈ 237.6 possibilities, a random six-word Diceware passphrase about 277.5, and a 32-byte key from secrets.token_bytes 2256; listing 5.1 prints all three. Password-based key derivation (PBKDF2, scrypt, Argon2) multiplies the attacker's cost per guess but adds no entropy: 600,000 PBKDF2 iterations add log2(600,000) ≈ 19 bits of work, nowhere near the 90 bits that separate a typical password from a 128-bit key.

4.2 Key strength

Security strength is the number of bits of work, roughly log2 of the operations, needed to break a cryptographic mechanism with the best known attack. For a good symmetric cipher it equals the key length. For public-key algorithms it is much smaller than the key size, because the attacks exploit mathematical structure. NIST treats 112 bits as the minimum for protecting federal information today and has set out the transitions away from weaker algorithms and key sizes in SP 800-131A; the Rev. 6 draft of SP 800-57 moves the schedule of which strengths are acceptable when entirely into SP 800-131A.[6,85] Germany's BSI publishes its own recommendations in TR-02102-1, updated in January 2026.[86] Two practical rules follow. First, the strength of a system is the strength of its weakest key: an AES-256 DEK wrapped under an RSA-2048 key has 112-bit strength. Second, strength must last as long as the data needs protecting, which for some records is decades. Shor's algorithm on a large quantum computer would break RSA, finite-field DH and elliptic-curve keys at any size, so data that must stay secret long-term should already use post-quantum key establishment such as ML-KEM, often in a hybrid with X25519.[30,32]

4.3 Key compromise

A key is compromised when it has been disclosed to, modified by, substituted by or used by an unauthorised party, or when that is suspected.[4] The damage depends on the key type:

Compromised keyConsequenceResponse

Compromise often goes undetected, which is the deepest reason for cryptoperiods: a key that is replaced regularly limits an unknown compromise to the data of one period. When compromise is detected, speed matters, and the incidents that turn out worst are those where the organisation finds it cannot rotate because the old key is hard-coded, unrecorded, or shared by systems nobody knows about. Storm-0558 is again instructive: the CSRB recommended that cloud providers automate key rotation and be able to rotate signing keys rapidly in an emergency.[57] Heartbleed (2014), which could leak server private keys from memory, forced a mass rotation of TLS keys across the internet; measurement afterwards found that only a fraction of vulnerable sites replaced their certificates and fewer still revoked the old ones.[87]

4.4 Key separation

Key separation means using each key for exactly one purpose with one algorithm. SP 800-57 justifies it in four ways: using a key for two purposes can weaken the security of one or both; it limits the damage if one key is compromised; different purposes have different cryptoperiods, backup and archive rules; and some uses conflict outright.[4] Concrete conflicts are easy to find:

  • An RSA key used for both decryption and signatures lets an attacker who can get anything signed turn the signing operation into a decryption oracle, since textbook RSA signing and decryption are the same computation.[26]
  • Using one AES key for CBC encryption and CBC-MAC breaks the MAC: an attacker can build forgeries from ciphertext blocks.[2]
  • A KEK that also encrypts data lets an attacker who controls the data obtain values indistinguishable from wrapped keys (section 2.5).
  • A private signature key that is backed up for its other role as a decryption key loses its non-repudiation.

When one secret has to serve several purposes, derive independent keys from it with a KDF and distinct labels, as TLS 1.3 does for every key in its schedule and as listing 5.4 does for each tenant and purpose.[31,54,71] PKCS#11 enforces separation in hardware through key attributes: a key created with CKA_WRAP but without CKA_ENCRYPT cannot be used to encrypt ordinary data.[44]

4.5 Secure key storage

Attackers look for keys wherever they rest, even briefly. The places keys leak from include:

  • Source code and configuration: hard-coded keys and committed .env files, which secret-scanning tools exist to find.[83,84]
  • Process memory: read by bugs such as Heartbleed, or by attackers with debugging access.[87]
  • Crash dumps, swap and hibernation files: Microsoft's first account of Storm-0558 said the consumer signing key had been captured in a 2021 crash dump that was moved into a less protected debugging environment; the CSRB later noted that Microsoft could not confirm this.[57,58]
  • DRAM after power-off: cold-boot attacks cool memory chips and read keys that survive seconds to minutes without power, defeating disk encryption whose key is held in RAM.[88]
  • Backups and logs, which are often kept longer and protected less than production systems.

OWASP's guidance opens its storage section with the rule that keys should never be stored in plaintext.[89] The defences are layered: keep the highest-value keys in hardware where they cannot be read at all (HSM, TPM, secure enclave); keep the rest wrapped under such a key and unwrap them only in memory; restrict memory (no core dumps, locked pages, short lifetimes for plaintext keys); and treat every copy, including backups and archives, as needing the same protection as the original.[4,7]

4.6 Secure deletion

Deleting a file removes a directory entry, not the data. Overwriting works on simple magnetic disks, and Gutmann's 1996 paper on recovering overwritten data led to the famous 35-pass scheme, though he later noted most of its passes are pointless on modern drives.[90] On flash storage overwriting is unreliable: Wei and colleagues found in 2011 that the controllers' wear-levelling and remapping meant individual files could not be reliably erased by overwriting, and some drives' built-in sanitise commands were implemented incorrectly.[91]

Two techniques do work. For storage media, cryptographic erase encrypts everything from the start and sanitises by destroying the key, which reduces the problem to securely deleting 32 bytes in a place designed for it, such as an HSM or a self-encrypting drive's controller. SP 800-88 Rev. 2 (September 2025) recognises it as a sanitisation technique within an organisation's media-sanitisation programme.[53] For keys in memory, zeroisation overwrites the buffer as soon as the key is no longer needed. This is harder than it sounds: compilers may remove a memset of a buffer that is never read again, so C code uses explicit_bzero, memset_s or SecureZeroMemory; and in garbage-collected languages immutable byte strings may be copied around the heap and cannot be wiped at all, which is one more reason to keep high-value keys inside a module.[7]

4.7 Key escrow

Key escrow deposits a copy of a key, or enough information to reconstruct it, with one or more trusted third parties, so that someone other than the key's user can recover it under defined conditions.[4] Inside an organisation, escrow of data-encryption keys is a normal recovery mechanism (section 1.10). Escrow for government access is far more contentious.

The Clipper chip. In 1993 the US government proposed the Escrowed Encryption Standard (FIPS 185, February 1994), implemented in the Clipper chip. Each chip's unit key was split into two components held by two government escrow agents, and every encrypted session carried a Law Enforcement Access Field (LEAF) containing the session key encrypted under the unit key.[92] In 1994 Matt Blaze showed that the LEAF was protected by only a 16-bit checksum, so a user could generate fake LEAFs by trial and error and defeat the escrow while still using the chip's encryption.[93] The programme was abandoned.

Two influential reports by leading cryptographers, in 1997 and in 2015 (Keys Under Doormats), argued that escrow for exceptional access adds complexity, creates high-value targets that concentrate risk, and conflicts with forward secrecy, which deliberately destroys keys after use.[94,95] The technical point holds regardless of the policy view: an escrowed key is another copy, and every copy has to be protected for as long as the data matters.

4.8 Key recovery policies

Because recovery deliberately creates a second route to a key, it should be governed by a written key recovery policy. Drawing on SP 800-57's guidance on key recovery and the organisational guidance in Part 2, a policy should state:[4,61]

  1. Which keys may be recovered (typically DEKs and KEKs for stored data; never private signature keys or ephemeral keys).
  2. Who may request recovery, under what circumstances, and how requesters are authenticated.
  3. Who must approve each recovery, usually under dual control.
  4. How recovered keys are delivered and protected, and how long they may be used.
  5. What is logged, who reviews the log, and how the key owner is notified.
  6. How the recovery material itself (backup KEKs, shares) is protected, tested and rotated.

Recovery that has never been tested is a hope rather than a capability, so policies should include regular recovery drills. The DNSSEC root's recovery key share holders exist for exactly this reason, and their shares are checked at ceremonies.[55,56]

4.9 Split knowledge

Split knowledge divides a key into components so that no single person knows, or can determine, any part of the key; only when all the components are combined is the key formed.[4,18] The simplest scheme uses XOR: generate random components C1, …, Cn−1 and set Cn = K ⊕ C1 ⊕ … ⊕ Cn−1. Any n−1 components are uniformly random and independent of K, by the same argument that makes the one-time pad perfectly secret.[96] Each custodian keys in a component and its KCV at the HSM; the HSM combines them internally and displays the KCV of the result for confirmation.

Payment-industry standards make split knowledge mandatory for manual handling of clear-text keys. PCI DSS requires that manual cleartext cryptographic key-management operations be performed using split knowledge and dual control, and the PCI PIN Security Requirements apply the same rules to the keys that protect PINs; ISO 11568 sets out the same principles for retail financial key management internationally.[76,97,98]

4.10 Dual control

Dual control requires two or more separate, authorised people acting together to perform a sensitive operation, so that no one person can do it alone.[4,97] It is a procedural control, where split knowledge is a cryptographic one, and the two are usually combined: two custodians each hold a component (split knowledge), and loading the key requires both to be present and authenticated (dual control). Other common uses are two-person approval for exporting or destroying a key in a KMS, quorum smart cards for HSM administration, and witnessed key ceremonies with scripts, video recording and independent auditors, like the DNS root's.[55] Dual control fails if the two people are not really independent, for instance when one administrator holds both cards, which is why the code in listing 5.6 checks for two distinct authorised officers.

4.11 Threshold key management

XOR splitting needs every component, so losing one custodian loses the key. Threshold schemes fix this: a k-of-n scheme gives shares to n parties such that any k can reconstruct the key and any k−1 learn nothing. Shamir (1979) and Blakley (1979) published the first schemes independently in the same year.[99,100]

Shamir's scheme hides the secret s as the constant term of a random polynomial of degree k−1 over a finite field, f(x) = s + a1x + … + ak−1xk−1, and gives party i the share (i, f(i)). Any k points determine the polynomial, and Lagrange interpolation at x = 0 recovers s:[99]

s = f(0) = Σ_{j∈S} y_j · Π_{m∈S, m≠j} x_m / (x_m − x_j) (|S| = k)

With only k−1 points, every possible secret is consistent with exactly the same number of polynomials, so the shares carry no information about s at all; listing 5.6 checks this by brute force in a small field. Practical implementations work byte by byte in GF(28), as Vault's unseal keys and SLIP-39 mnemonic backups do.[43,101]

Plain secret sharing has limits that later work addresses:

  • Verifiability. A dishonest dealer could hand out inconsistent shares. Feldman's verifiable secret sharing (1987) publishes commitments to the polynomial's coefficients so each party can check its share.[102]
  • Proactive refresh. Shares stolen one at a time over years would eventually reach k. Proactive secret sharing (Herzberg et al., 1995) periodically re-randomises the shares without changing the secret, so old stolen shares become useless.[103]
  • Never reconstructing. Reassembling the key in one place recreates the single point of failure. Threshold cryptography, introduced by Desmedt and Frankel, lets the parties compute with the shared key, producing a decryption or signature jointly, without the key ever existing in one place.[104] FROST (RFC 9591, 2024) is a standardised two-round threshold Schnorr signature scheme, and threshold ECDSA protocols such as Lindell's are used by cryptocurrency custody services and multi-party-computation wallets.[105,106]
Choosing k and n. The threshold trades confidentiality against availability. A 2-of-3 scheme survives the loss of one share but needs only two conspirators; a 5-of-7 scheme resists four colluders but is lost if three shares are. Shares should be held by people with different reporting lines, in different places, and the scheme should be exercised regularly. The DNSSEC root's design, with separate groups of officers for normal operation and for recovery, shows how a threshold scheme fits into a larger set of procedures.[55,56]

5.1 Key generation, strength and check values

Generates symmetric and asymmetric keys from the CSPRNG, combines keys by XOR as SP 800-133 allows, computes AES and CMAC key check values (checked against FIPS-197), prints the comparable-strength table, compares password and key entropy, and simulates a Debian-style weak generator by brute-forcing its 215 seeds.[4,8,14]

keygen.py
"""Key generation, key strength and key check values (KCVs).

Run: python3 keygen.py      (needs: pip install cryptography)
Follows the approaches in NIST SP 800-133r2 and SP 800-57 Part 1.
"""
import math, os, secrets, hashlib
from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes
from cryptography.hazmat.primitives.asymmetric import ec, ed25519, rsa
from cryptography.hazmat.primitives import hashes, serialization
from cryptography.hazmat.primitives.kdf.pbkdf2 import PBKDF2HMAC

# 1. Symmetric keys come straight from the OS CSPRNG (SP 800-133r2, section 6.1).
k_aes = secrets.token_bytes(32)                 # 256-bit AES key
print("AES-256 key       :", k_aes.hex())

# 2. SP 800-133r2 section 6.3 also allows combining independent keys with XOR:
#    the result is at least as strong as the strongest input.
k1, k2 = os.urandom(32), secrets.token_bytes(32)
k_combined = bytes(a ^ b for a, b in zip(k1, k2))
print("XOR-combined key  :", k_combined.hex()[:32], "...")

# 3. Key check value: encrypt an all-zero block and keep the first 3 bytes.
#    Ceremonies and HSM imports use KCVs to confirm a key was entered correctly
#    without revealing it.
def kcv_aes(key: bytes) -> str:
    enc = Cipher(algorithms.AES(key), modes.ECB()).encryptor()
    return (enc.update(bytes(16)) + enc.finalize())[:3].hex().upper()

def kcv_cmac(key: bytes) -> str:          # newer CMAC-based KCV (used by some HSM vendors)
    from cryptography.hazmat.primitives.cmac import CMAC
    c = CMAC(algorithms.AES(key)); c.update(bytes(16)); return c.finalize()[:3].hex().upper()

print("KCV (AES-ECB 0^128):", kcv_aes(k_aes), "  KCV (CMAC):", kcv_cmac(k_aes))
# FIPS-197 Appendix C.1 key 000102..0f: AES_K(0^128) is c6a13b37878f5b826f4f8162a1c8d879
assert kcv_aes(bytes(range(16))) == "C6A13B", kcv_aes(bytes(range(16)))

# 4. Asymmetric key pairs: always generate inside the library / module.
rsa_key = rsa.generate_private_key(public_exponent=65537, key_size=3072)
ec_key = ec.generate_private_key(ec.SECP256R1())
ed_key = ed25519.Ed25519PrivateKey.generate()
print("RSA-3072 modulus bits:", rsa_key.key_size, "| P-256 curve:", ec_key.curve.name,
      "| Ed25519 public:", ed_key.public_key().public_bytes_raw().hex()[:16], "...")

         (128, "AES-128", 3072, "256-383"), (192, "AES-192", 7680, "384-511"),
         (256, "AES-256", 15360, "512+")]
print("\nstrength  symmetric  RSA/DH bits  ECC bits")
for s, sym, ifc, ecc in TABLE:
    print(f"{s:>6}    {sym:<9}  {ifc:>8}     {ecc}")

def entropy_bits(alphabet: int, length: int) -> float:

print("\n8-char random lowercase password :", round(entropy_bits(26, 8), 1), "bits")
print("12-char random from 94 printable :", round(entropy_bits(94, 12), 1), "bits")

# 7. A password-derived key is only as strong as the password: PBKDF2 slows guessing
#    by a constant factor (iterations) but adds no entropy.
salt = os.urandom(16)

pw_key = kdf.derive(b"correct horse battery staple")

# 8. The Debian OpenSSL bug (CVE-2008-0166) left the process ID as the only seed:
#    at most 32,768 possible keys per type/size. Simulate and enumerate.
def weak_keygen(pid: int) -> bytes:

victim = weak_keygen(secrets.randbelow(32768))

5.2 AES Key Wrap from scratch

Implements RFC 3394 wrap and unwrap (Figure 7), checks both against the RFC's 128- and 256-bit test vectors and against the library, shows that tampering and wrong KEKs are detected, and checks KWP against the RFC 5649 20-byte example.[25,64,65]

keywrap.py
"""AES Key Wrap (RFC 3394 / NIST SP 800-38F "KW") from scratch, checked against
the RFC 3394 test vectors and pyca/cryptography; plus KWP (RFC 5649) via the library.

Run: python3 keywrap.py
"""
import os
from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes
from cryptography.hazmat.primitives import keywrap

IV = bytes.fromhex("A6A6A6A6A6A6A6A6")       # RFC 3394 section 2.2.3.1 default IV

def _aes(kek, block, decrypt=False):
    c = Cipher(algorithms.AES(kek), modes.ECB())
    op = c.decryptor() if decrypt else c.encryptor()
    return op.update(block) + op.finalize()

def wrap(kek: bytes, key: bytes) -> bytes:
    if len(key) % 8 or len(key) < 16:
        raise ValueError("KW wraps keys of 16+ bytes in 8-byte multiples (use KWP otherwise)")
    n = len(key) // 8
    a, r = IV, [key[8*i:8*i+8] for i in range(n)]
    for j in range(6):                          # 6 rounds of n AES calls each
        for i in range(n):
            b = _aes(kek, a + r[i])
            t = n * j + i + 1
            a = (int.from_bytes(b[:8], "big") ^ t).to_bytes(8, "big")
            r[i] = b[8:]
    return a + b"".join(r)

def unwrap(kek: bytes, wrapped: bytes) -> bytes:
    n = len(wrapped) // 8 - 1
    a, r = wrapped[:8], [wrapped[8*(i+1):8*(i+2)] for i in range(n)]
    for j in reversed(range(6)):
        for i in reversed(range(n)):
            t = n * j + i + 1
            a_t = (int.from_bytes(a, "big") ^ t).to_bytes(8, "big")
            b = _aes(kek, a_t + r[i], decrypt=True)
            a, r[i] = b[:8], b[8:]
    if a != IV:                                 # integrity check: built-in authentication
        raise ValueError("integrity check failed: wrong KEK or tampered wrapped key")
    return b"".join(r)

5.3 A toy KMS: key states, envelope encryption, rotation and crypto-shredding

Models the SP 800-57 states and transitions of Figure 2, refuses illegal transitions, wraps per-object DEKs with versioned KEKs and an encryption context, rotates by re-wrapping (the bulk ciphertext is unchanged), handles a compromised version, and finally destroys every version so the data becomes unrecoverable.[4,38,68]

envelope_kms.py
"""A toy key management service: SP 800-57 key states, versioned KEKs,
envelope encryption with AES-GCM, rotation by re-wrapping, revocation,
and crypto-shredding.  For teaching only: real KEKs live inside an HSM.

Run: python3 envelope_kms.py
"""
import json, os, time
from dataclasses import dataclass, field
from enum import Enum
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

class State(Enum):                      # SP 800-57 Pt 1 r5, section 7
    PRE_ACTIVATION = "pre-activation"
    ACTIVE = "active"
    SUSPENDED = "suspended"
    DEACTIVATED = "deactivated"
    COMPROMISED = "compromised"
    DESTROYED = "destroyed"

ALLOWED = {                              # permitted transitions (simplified Fig. 4 of SP 800-57)
    State.PRE_ACTIVATION: {State.ACTIVE, State.COMPROMISED, State.DESTROYED},
    State.ACTIVE: {State.SUSPENDED, State.DEACTIVATED, State.COMPROMISED},
    State.SUSPENDED: {State.ACTIVE, State.DEACTIVATED, State.COMPROMISED},
    State.DEACTIVATED: {State.COMPROMISED, State.DESTROYED},
    State.COMPROMISED: {State.DESTROYED},
    State.DESTROYED: set(),
}

class KeyStateError(Exception): pass

@dataclass
class KeyVersion:
    version: int
    material: bytes | None
    state: State = State.PRE_ACTIVATION
    created: float = field(default_factory=time.time)
    history: list = field(default_factory=list)

    def transition(self, new: State, reason: str = ""):
        if new not in ALLOWED[self.state]:
            raise KeyStateError(f"v{self.version}: {self.state.value} -> {new.value} not allowed")
        self.history.append((self.state.value, new.value, reason))
        self.state = new
        if new is State.DESTROYED:
            self.material = None        # in an HSM: zeroise; here: drop the reference

class ToyKMS:
    def __init__(self, name):
        self.name, self.versions, self.primary = name, {}, None
        self.audit = []

    def _log(self, op, **kw):
        self.audit.append({"t": round(time.time(), 3), "key": self.name, "op": op, **kw})

    def create_version(self, activate=True) -> int:
        v = len(self.versions) + 1
        self.versions[v] = KeyVersion(v, AESGCM.generate_key(256))
        self._log("generate", version=v)
        if activate:
            self.versions[v].transition(State.ACTIVE, "activate")
            if self.primary:                          # old primary may still decrypt
                self.versions[self.primary].transition(State.DEACTIVATED, "rotated")
            self.primary = v
            self._log("activate", version=v)
        return v

    # The KMS API: wrap/unwrap DEKs. The KEK never leaves this object.
    def encrypt_dek(self, dek: bytes, context: dict) -> dict:
        kv = self.versions[self.primary]
        if kv.state is not State.ACTIVE:
            raise KeyStateError("primary version not active")
        aad = json.dumps(context, sort_keys=True).encode()   # "encryption context"
        nonce = os.urandom(12)
        self._log("wrap", version=kv.version, context=context)
        return {"v": kv.version, "n": nonce.hex(), "c": AESGCM(kv.material).encrypt(nonce, dek, aad).hex()}

    def decrypt_dek(self, blob: dict, context: dict) -> bytes:
        kv = self.versions[blob["v"]]
        # Deactivated keys may still *process* (decrypt); compromised keys only under review.
        if kv.state not in (State.ACTIVE, State.DEACTIVATED):
            raise KeyStateError(f"v{kv.version} is {kv.state.value}: unwrap refused")
        aad = json.dumps(context, sort_keys=True).encode()
        self._log("unwrap", version=kv.version, context=context)
        return AESGCM(kv.material).decrypt(bytes.fromhex(blob["n"]), bytes.fromhex(blob["c"]), aad)

    def rewrap(self, blob, context):      # rotation without touching the bulk data
        return self.encrypt_dek(self.decrypt_dek(blob, context), context)

def seal(kms, plaintext: bytes, context: dict) -> dict:
    dek = AESGCM.generate_key(256)                     # fresh DEK per object
    nonce = os.urandom(12)
    ct = AESGCM(dek).encrypt(nonce, plaintext, None)
    return {"wrapped_dek": kms.encrypt_dek(dek, context), "nonce": nonce.hex(), "ct": ct.hex()}

def open_(kms, env: dict, context: dict) -> bytes:
    dek = kms.decrypt_dek(env["wrapped_dek"], context)
    return AESGCM(dek).decrypt(bytes.fromhex(env["nonce"]), bytes.fromhex(env["ct"]), None)

5.6 Split knowledge, Shamir sharing and dual control

XOR components, Shamir 3-of-5 over GF(28) with every 3-subset tested, a brute-force proof in GF(13) that two shares of a 3-of-5 sharing leave every secret equally likely, and a dual-control check that requires two distinct officers.[18,99]

shamir.py
"""Split knowledge and threshold key management:
  * XOR key components (n-of-n split knowledge, as in key ceremonies)
  * Shamir secret sharing over GF(2^8), byte by byte (the approach HashiCorp Vault uses)
  * Shamir over a prime field, with a check that k-1 shares reveal nothing

Run: python3 shamir.py
"""
import itertools, os, secrets
from collections import Counter
from functools import reduce

# ---- 1. XOR components: every custodian must be present (split knowledge) ----
def xor_split(key: bytes, n: int):
    parts = [os.urandom(len(key)) for _ in range(n - 1)]
    last = bytes(reduce(lambda a, b: a ^ b, col) for col in zip(key, *parts))
    return parts + [last]

def xor_join(parts):
    return bytes(reduce(lambda a, b: a ^ b, col) for col in zip(*parts))

master = secrets.token_bytes(16)

assert xor_join(comps) == master and xor_join(comps[:2]) != master

EXP, LOG = [0] * 512, [0] * 256
x = 1
for i in range(255):
    EXP[i] = x; LOG[x] = i
    x ^= (x << 1) ^ (0x11B if x & 0x80 else 0)   # multiply by generator 3
    x &= 0xFF
for i in range(255, 512):
    EXP[i] = EXP[i - 255]

def gmul(a, b): return 0 if a == 0 or b == 0 else EXP[LOG[a] + LOG[b]]
def gdiv(a, b):
    if b == 0: raise ZeroDivisionError
    return 0 if a == 0 else EXP[(LOG[a] - LOG[b]) % 255]

def split(secret: bytes, k: int, n: int):
    """Return n shares (x, bytes); any k reconstruct the secret."""
    assert 1 < k <= n < 256
    xs = list(range(1, n + 1))
    shares = {xi: bytearray() for xi in xs}
    for s in secret:
        coeffs = [s] + [secrets.randbelow(256) for _ in range(k - 1)]
        for xi in xs:                                 # Horner evaluation in GF(2^8)
            y = 0
            for c in reversed(coeffs):
                y = gmul(y, xi) ^ c
            shares[xi].append(y)
    return [(xi, bytes(ys)) for xi, ys in shares.items()]

def combine(shares):
    """Lagrange interpolation at x = 0 (addition and subtraction are both XOR)."""
    out = bytearray()
    for idx in range(len(shares[0][1])):
        acc = 0
        for j, (xj, yj) in enumerate(shares):
            num = den = 1
            for m, (xm, _) in enumerate(shares):
                if m != j:
                    num = gmul(num, xm)          # (0 - xm) = xm in characteristic 2
                    den = gmul(den, xj ^ xm)
            acc ^= gmul(yj[idx], gdiv(num, den))
        out.append(acc)
    return bytes(out)

root_key = secrets.token_bytes(32)

6. In-browser lab

These demos run entirely in your browser using the Web Crypto API; nothing is sent anywhere. Keys are generated fresh each time.

6.1 Generate a key and its check value

Generates an AES-256 key with crypto.subtle.generateKey, exports it, and computes the KCV as the first 3 bytes of AES(K, 0128) (one-block AES-CBC with a zero IV equals AES-ECB). Paste a key to check a known KCV; the FIPS-197 key 000102030405060708090a0b0c0d0e0f gives C6A13B.

6.2 AES Key Wrap (RFC 3394)

Wraps a key under a KEK with the browser's native AES-KW. The defaults are RFC 3394 section 4.1; the expected output is 1FA68B0A8112B447AEF34BD8FB5A7B829D3E862371D2CFE5. Flip a hex digit in the wrapped value and unwrap to see the integrity check fail.

6.3 Envelope encryption with rotation

Creates KEK v1, encrypts the message with a fresh AES-256-GCM DEK, wraps the DEK with AES-KW, and shows the stored envelope. "Rotate KEK" adds a new version and re-wraps the DEK; the data ciphertext does not change. "Destroy all KEKs" crypto-shreds the envelope.

6.4 Shamir secret sharing (GF(28))

Splits a hex secret into n shares with threshold k. Then delete lines from the shares box until fewer than k remain and press Combine: the result is garbage, and not even partly right.

8. Exercises

Click an exercise to reveal its solution.

8.1 Pairwise keys. A company of 1,200 people wants every pair to share a symmetric key. How many keys are needed? How many with a KDC? How many key pairs with public-key cryptography?

Pairwise: 1200 × 1199 / 2 = 719,400 keys, each held by two people. With a KDC: 1,200 long-term keys (one per user, shared with the KDC), plus session keys issued on demand. With public keys: 1,200 key pairs, but each public key needs an authenticated binding to its owner, such as a certificate.[20,21,22]

8.2 Weakest link. A database is encrypted with AES-256 DEKs. The DEKs are wrapped under an RSA-2048 key, whose private key is protected by a PKCS#8 file under a 10-character random lowercase passphrase with PBKDF2 at 600,000 iterations. What is the effective security strength?

The AES layer gives 256 bits and RSA-2048 gives 112 bits (Table 2). The passphrase has 10 log2 26 ≈ 47 bits of entropy, plus about 19 bits of work from PBKDF2, so roughly 66 bits, which is the effective strength. An attacker who obtains the PKCS#8 file brute-forces the passphrase, not AES. Fix: keep the RSA key in an HSM or KMS, or use a passphrase of at least six Diceware words.[4]

8.3 OUP and RUP. A symmetric DEK protects backups. Its originator-usage period is 1 year and backups are retained for 7 years. Is this consistent with SP 800-57's suggested cryptoperiods? What would you change?

The suggested RUP for a data-encryption key is at most OUP + 3 years, here 4 years, while the data must be readable for 7 years after the last write: up to 8 years in total. Either re-encrypt (or, with envelope encryption, re-wrap under a newer KEK and re-key the data) before the RUP ends, or document a longer RUP justified by the risk analysis. With per-backup DEKs under a rotating KEK, rotation becomes a re-wrap of small blobs.[4]

8.4 Rotation that does nothing. After a suspected KEK compromise an engineer clicks "rotate" in the cloud KMS and closes the incident. What did that achieve and what is missing?

New DEKs will be wrapped under the new version, but every existing wrapped DEK is still protected only by the compromised version, which remains enabled for decryption. Missing: re-wrap (or re-encrypt) all existing DEKs under the new version, then disable and destroy the old version; and, because an attacker with the old KEK could have unwrapped DEKs already, re-encrypt the data under new DEKs if exposure of the wrapped DEKs is plausible.[48,49]

8.5 Key wrap by hand. In RFC 3394 KW, how many AES block operations are needed to wrap a 256-bit key? How long is the output?

A 256-bit key is n = 4 blocks of 64 bits. KW performs 6n = 24 AES operations, and the output is n + 1 = 5 blocks = 40 bytes, matching the RFC 3394 section 4.6 vector checked in listing 5.2.[64]

8.6 Deterministic wrapping. Why is it acceptable for AES-KW to be deterministic when deterministic encryption of ordinary data is insecure? When does it leak something?

Deterministic encryption leaks equality of plaintexts. Keys are high-entropy and normally unique, so equal inputs essentially never occur, and KW meets the deterministic authenticated-encryption notion of Rogaway and Shrimpton. It leaks when the same key is wrapped twice under the same KEK: the outputs are identical, so an observer learns the two blobs hold the same key.[25,66]

8.7 Shamir by hand. Over GF(13), a 2-of-3 sharing uses f(x) = s + 4x and the shares are (1, 9) and (3, 4). Find s.

Lagrange at 0 with x1 = 1, x2 = 3: s = 9 · 3/(3 − 1) + 4 · 1/(1 − 3) = 9 · 3 · 2−1 + 4 · (−2)−1. In GF(13), 2−1 = 7 and (−2)−1 = 11−1 = 6. So s = 9·3·7 + 4·6 = 189 + 24 = 213 ≡ 5 (mod 13). Check: f(1) = 5 + 4 = 9 and f(3) = 5 + 12 = 17 ≡ 4.[99]

8.8 XOR components. Three custodians hold K = C1 ⊕ C2 ⊕ C3. Custodian 3 retires. Can the key be re-split for a new custodian without anyone learning K?

Yes, if the HSM does it: load all three components into the HSM under dual control, have it generate fresh random C′1, C′2 and compute C′3 = K ⊕ C′1 ⊕ C′2 internally, and print each new component for its custodian with its KCV. Old components are destroyed. No person ever sees K or more than one component. (Simply handing C3 to a newcomer keeps the key but leaves a copy with the retiree.)[18,76]

8.9 Choosing a threshold. You must protect a root key against any three colluding insiders and survive the loss of any two shares. What is the smallest k-of-n scheme?

Collusion resistance against 3 needs k ≥ 4. Surviving the loss of 2 needs n − 2 ≥ k, so n ≥ 6. The smallest scheme is 4-of-6.[99]

8.10 Key separation. A service uses one HMAC key both to authenticate API requests and, via HMAC(K, user_id), to derive per-user encryption keys. Describe an attack and a fix.

If an attacker can get the service to authenticate a request whose body is a victim's user_id, the resulting tag is the victim's encryption key. Fix: derive independent keys with distinct labels, for example Kauth = HKDF(K, "api-auth") and Kuser = HKDF(K, "user-enc|" ‖ user_id), and never expose a raw PRF output that doubles as a key.[4,54,71]

8.11 Forward secrecy. Traffic recorded in 2026 was protected by TLS 1.2 with static RSA key transport. In 2030 the server's private key leaks. What can the attacker read? What if it had used ECDHE, and what if a quantum computer arrives?

Static RSA: every recorded session, because each premaster secret was encrypted to that key. ECDHE: nothing from the leak alone, since the session keys came from ephemeral keys that were deleted; the long-term key only signed the handshake. A cryptographically relevant quantum computer could recover the ephemeral ECDH secrets from the recorded public values (harvest now, decrypt later); only a post-quantum or hybrid exchange such as X25519MLKEM768 protects against that.[31,32]

8.12 Crypto-shredding. A SaaS provider must delete one customer's data within 30 days of contract end, but the data is spread across replicated databases and seven years of backups. Design a key hierarchy that makes this feasible.

Give each customer its own KEK in the KMS (Figure 6). Encrypt each record or object under a DEK wrapped by that customer's KEK, including in backups. At contract end, schedule destruction of the customer's KEK versions (with a waiting period and dual approval). Once destroyed, every replica and every backup becomes unreadable without being touched. Log the destruction for audit; SP 800-88 Rev. 2 treats cryptographic erase as a sanitisation technique.[38,53]

8.13 Backup or not? For each key, decide whether to back it up: (a) TLS 1.3 ephemeral X25519 key; (b) a user's S/MIME decryption key; (c) a code-signing private key in an HSM; (d) a KEK protecting a data lake.

(a) Never: it exists for one handshake. (b) Yes: otherwise old encrypted email is lost; back up or escrow under a recovery policy. (c) Generally no, to preserve exclusive control; if loss is unacceptable, back it up only as HSM-wrapped material under dual control, since a lost code-signing key can be replaced and re-certified. (d) Yes, essential, under split knowledge and in a separate location.[4]

8.14 Entropy at boot. A router generates its SSH host key on first boot, 2 seconds after power-on, using a pool seeded only from the MAC address and the boot time in seconds. Estimate the entropy and describe the 2012-style attack.

The MAC address is public (or narrowly predictable by vendor prefix), and the boot time in seconds since power-on is nearly constant, so the entropy is close to zero, perhaps a few bits. Devices of the same model generate the same or overlapping keys. For RSA, moduli that share one prime are factored by computing pairwise GCDs across a large scan; Heninger et al. did this efficiently across millions of keys.[15]

8.15 Activation and pre-publication. Why does DNSSEC publish a new KSK in the DNS long before it begins signing with it?

Resolvers must trust the new key before signatures made with it appear, or validation fails. Pre-publishing (the key's pre-activation state) lets resolvers learn and cache it, and RFC 5011-style automated trust-anchor updates need a hold-down period before accepting it. The 2018 root rollover published KSK-2017 months before it was used on 11 October 2018.[41]

8.16 Zeroisation in Python. Why can't listing 5.3 truly wipe a key from memory, and what would you do in production?

Python bytes are immutable and may be copied by the interpreter, the library and the garbage collector; dropping the reference does not overwrite the memory. A bytearray can be overwritten, but copies made earlier remain. In production, keep the KEK in an HSM or KMS so it never enters process memory, keep plaintext DEKs short-lived, disable core dumps, and use libraries that zeroise in native code.[7,88]

10. Practitioner's cheat sheet

Generate

CSPRNG only; generate inside the module that will use the key; record metadata (purpose, owner, cryptoperiod) at birth.[8,13]

Establish

Ephemeral (EC)DH or ML-KEM hybrid, authenticated; KDF over the transcript; confirm the key.[23,28,32]

Store

Root keys in HSMs, offline if possible; everything else wrapped; no plaintext keys in code, config, logs or dumps.[7,89]

Structure

Root → KEK → DEK; fresh DEK per object; context-bound wrapping; derive rather than reuse.[38,71]

Use

One key, one purpose; respect usage limits (GCM 232 random nonces); enforce in metadata and policy.[4,31]

Rotate

Automate; keep old versions decrypt-only; re-wrap after compromise; practise emergency rotation.[46,48,57]

Back up & recover

Back up keys protecting stored data, under split knowledge; never ephemeral keys; written recovery policy; drills.[4,61]

Revoke & destroy

Compromise plan ready in advance; destroy every copy; crypto-shred instead of overwrite.[4,53]

People

Split knowledge and dual control for clear-text key handling; k-of-n shares for roots; audit everything.[97,99]
