1. Fundamentals

1.1 What a hash function is

A hash function maps a message of (practically) any length to a short output of fixed length, called the digest, hash value or fingerprint.[1] Written formally, H : {0,1}* → {0,1}n. SHA-256 accepts messages up to 264−1 bits and always returns n = 256 bits; SHA-512 accepts up to 2128−1 bits and returns 512.[2] Two structural facts follow from this definition:

  • Fixed-length digests. The output length does not depend on the input. A one-byte file and a 4 GB disk image both hash to 32 bytes under SHA-256. Because the domain is vastly larger than the range, collisions must exist (pigeonhole principle). Security is about making them infeasible to find, not about making them absent.[3]
  • Deterministic hashing. The same input always yields the same digest, on every machine and at every time. There is no secret and no randomness inside an unkeyed hash. This is what lets two parties compare fingerprints independently, and it is also why an attacker can precompute digests of likely inputs (the reason password hashing adds salts, §5.2).

A cryptographic hash function adds security requirements on top of this: it must be hard to invert, hard to find a second input with the same digest, and hard to find any two colliding inputs. Non-cryptographic hashes used in hash tables (for example FNV or MurmurHash) are fast and well distributed, but make none of these promises.

1.2 Preimage, second-preimage and collision resistance

The three classical security notions were formalised by Merkle and Damgård in 1989 and given precise, comparable definitions by Rogaway and Shrimpton.[3,7,8] For an n-bit hash H:

Definitions

Preimage resistance (one-wayness). Given a digest y, it is infeasible to find any x with H(x) = y. Generic attack: try inputs until one hits, about 2n evaluations.

Second-preimage resistance (weak collision resistance). Given a specific x, it is infeasible to find x′ ≠ x with H(x′) = H(x). Generic attack: about 2n evaluations (less for very long messages in Merkle–Damgård hashes, see §2.3).

Collision resistance (strong collision resistance). It is infeasible to find any pair x ≠ x′ with H(x) = H(x′). Generic attack: the birthday attack, about 2n/2 evaluations.

The notions are related but not equivalent. Collision resistance implies second-preimage resistance (a second preimage is a collision), and for functions that compress sufficiently it also implies preimage resistance in the sense made precise by Rogaway and Shrimpton; the converse implications do not hold.[3] The practical difference matters a great deal: MD5 and SHA-1 have practical collision attacks, yet no practical preimage attack is known on either.[9,10] That is why a forged SHA-1 certificate is a real threat, while recovering a file from its SHA-1 digest is not.

Modern designs are also expected to behave like a random oracle, a function whose outputs look independent and uniformly random. A construction that is indifferentiable from a random oracle can replace one in most security proofs; this is the standard Coron et al. introduced for hash constructions and that the sponge was proven to satisfy.[12,13]

1.3 Avalanche behaviour

Feistel described the avalanche effect for block ciphers: a small change in the input should produce a large, unpredictable change in the output.[14] Webster and Tavares sharpened it into the strict avalanche criterion (SAC): flipping any single input bit should flip each output bit with probability 1/2.[15] For a 256-bit hash, a one-bit change should therefore flip about 128 output bits, with a standard deviation of √(256·¼) = 8 bits.

avalanche.py — "Hello" versus "hello" (one bit apart: 0x48 vs 0x68)
import hashlib

def bit_diff(a: bytes, b: bytes) -> int:
    return sum(bin(x ^ y).count("1") for x, y in zip(a, b))

a = hashlib.sha256(b"Hello").digest()
b = hashlib.sha256(b"hello").digest()
print(a.hex())

Good avalanche is necessary but not sufficient: MD5 has excellent avalanche statistics and is still trivially broken for collisions, because differential attacks exploit carefully chosen multi-bit differences rather than random single-bit flips.[16]

1.4 Security levels and the birthday bound

The security level (or security strength) of a primitive is the base-2 logarithm of the work needed to break it. NIST expresses hash strengths separately for each property.[17,18] The asymmetry comes from the birthday paradox: among q random n-bit values, the probability of at least one collision is roughly

P(collision) ≈ 1 − e−q(q−1) / 2n+1,   so P ≈ ½ when q ≈ 1.1774 · 2n/2

This is why a 256-bit digest offers only 128-bit collision resistance, and why digests are twice as long as the matching symmetric key size.[1]

2. Hash function constructions

Designing a function that takes arbitrarily long input directly is hard. Every widely used hash instead builds the long-input function from a fixed-size primitive, iterated by a mode. Two modes dominate: the Merkle–Damgård iteration of a compression function (MD5, SHA-1, SHA-2, RIPEMD-160) and the sponge iteration of a permutation (SHA-3, SHAKE).

2.1 Merkle–Damgård and compression functions

A compression function f : {0,1}n × {0,1}b → {0,1}n takes an n-bit chaining value and a b-bit message block and returns a new chaining value. SHA-256 uses n = 256 and b = 512.[2] Merkle and Damgård independently showed at CRYPTO '89 that iterating a collision-resistant compression function, with the right padding, yields a collision-resistant hash for messages of any length.[7,8]

  1. Pad the message M: append a single 1 bit, then zeros, then the message length as a fixed-width integer (64 bits in SHA-256, 128 in SHA-512), so the total is a multiple of b. Encoding the length is called MD-strengthening, and it is what makes the security proof work.[1,2]
  2. Split the padded message into blocks m1, …, mL.
  3. Iterate: H0 = IV (a fixed constant), Hi = f(Hi−1, mi).
  4. Output HL, possibly through a finalisation step or truncation (SHA-224 and SHA-384 output only part of the final state).

Worked example: SHA-256 padding of "abc". The message is 3 bytes = 24 bits (61 62 63). Append 80 (the 1 bit plus seven zeros), then zeros until the length is 56 mod 64 bytes, then the 64-bit length 24 = 0x18. The result is exactly one 64-byte block:[2]

61626380 00000000 00000000 00000000 00000000 00000000 00000000 00000000
00000000 00000000 00000000 00000000 00000000 00000000 00000000 00000018

A 55-byte message still fits in one block (55 + 1 + 8 = 64), but a 56-byte message needs two, because the 80 byte and the 8-byte length no longer fit.

2.2 The Davies–Meyer construction

Where does a compression function come from? The classical answer is to build it from a block cipher Ek(x). Preneel, Govaerts and Vandewalle enumerated the 64 ways to combine one cipher call with XORs and identified 12 secure ones; Black, Rogaway and Shrimpton later proved their security in the ideal-cipher model.[19,20] The best known, Davies–Meyer, uses the message block as the cipher key and the chaining value as the plaintext, and then feeds the input forward:

Hi = Emi(Hi−1) ⊕ Hi−1

MD4, MD5, SHA-1 and SHA-2 all have this shape: the compression function is a dedicated block cipher (for SHA-256 it has been studied separately as SHACAL-2) whose output is added word-wise modulo 232 or 264 to the input chaining value, rather than XORed.[2] Two relatives in the PGV family are Matyas–Meyer–Oseas, Eg(H)(m) ⊕ m, and Miyaguchi–Preneel, which also XORs in H.[1,19]

A known quirk: Davies–Meyer has easily computable fixed points. For any block m, setting h = Dm(0) gives Em(h) ⊕ h = 0 ⊕ h = h. Fixed points are harmless on their own but are an ingredient of some second-preimage attacks; MD-strengthening limits their use.[21]

The toy hash below wires everything together: a small Feistel cipher, Davies–Meyer, MD-strengthening and the iteration. It is meant to be read, not used.

toymd.py — a 128-bit toy Merkle–Damgård hash (do not use for anything real)
"""Toy Merkle-Damgard hash with a Davies-Meyer compression function.
The 'block cipher' is a 4-round Feistel network whose round function is
SHA-256, so the file needs only the standard library. Educational only."""
import hashlib, struct

BLOCK = 16                    # message block size in bytes (= cipher key size)
IV = bytes(range(16))         # fixed initial chaining value

def E(key: bytes, x: bytes) -> bytes:
    """Toy 128-bit block cipher: 4 Feistel rounds keyed by `key`."""
    L, R = x[:8], x[8:]
    for r in range(4):
        f = hashlib.sha256(key + bytes([r]) + R).digest()[:8]
        L, R = R, bytes(a ^ b for a, b in zip(L, f))
    return L + R

def davies_meyer(h: bytes, m: bytes) -> bytes:
    """H_i = E_{m_i}(H_{i-1}) XOR H_{i-1}"""
    return bytes(a ^ b for a, b in zip(E(m, h), h))

def md_pad(msg: bytes) -> bytes:
    """MD-strengthening: 0x80, zero bytes, 64-bit big-endian bit length."""
    bitlen = 8 * len(msg)
    msg += b"\x80"
    while (len(msg) + 8) % BLOCK:
        msg += b"\x00"
    return msg + struct.pack(">Q", bitlen)

def toy_hash(msg: bytes) -> bytes:
    h = IV
    padded = md_pad(msg)
    for i in range(0, len(padded), BLOCK):
        h = davies_meyer(h, padded[i:i + BLOCK])
    return h

if __name__ == "__main__":
    for m in [b"", b"abc", b"abd", b"The quick brown fox"]:
        print(f"{m!r:24} {toy_hash(m).hex()}")

2.3 Length extension and other Merkle–Damgård weaknesses

Because the digest of a plain Merkle–Damgård hash is the final chaining value, anyone who knows H(M) and the length of M can continue the iteration and compute H(M ‖ pad ‖ X) for any suffix X, without knowing M. This length-extension property breaks the naive "secret-prefix" MAC H(key ‖ msg). It is the reason HMAC exists, and why SHA-3 and truncated SHA-2 variants advertise resistance to it.[17,18,22]

lengthext.py — forging a secret-prefix MAC against the toy hash
from toymd import md_pad, davies_meyer, BLOCK, toy_hash

def pad_only(n: int) -> bytes:
    """The padding bytes MD-strengthening appends to an n-byte message."""
    return md_pad(b"\x00" * n)[n:]

key = b"supersecretkey!!"                 # unknown to the attacker
msg = b"amount=10"
tag = toy_hash(key + msg)                  # attacker sees msg and tag

key_len = 16                               # attacker knows or guesses this
extra = b"&amount=1000000"
glue = pad_only(key_len + len(msg))        # the padding the server used
forged_msg = msg + glue + extra

# Resume the iteration from the published tag as the chaining value.
tail = extra + pad_only(key_len + len(forged_msg))
h = tag
for i in range(0, len(tail), BLOCK):
    h = davies_meyer(h, tail[i:i + BLOCK])

print("forged tag    :", h.hex())
print("server accepts:", h == toy_hash(key + forged_msg))
forged tag    : ca2c6ae2d546d9f4016b01369b750b5e
server accepts: True

The same attack works against SHA-1, SHA-256 and SHA-512 (tools such as hash_extender automate it). The fix is never to build a MAC by hand: use HMAC, KMAC, or the keyed modes of BLAKE2 and BLAKE3.[5,22–24]

Two further generic results show that iterated hashes are weaker than an ideal n-bit random function in some respects:

  • Joux multicollisions. Finding 2k messages that all collide costs only about k·2n/2, not the far larger cost for a random function. One consequence: concatenating two iterated hashes, H1(M) ‖ H2(M), is barely stronger than the stronger of the two.[25]
  • Long-message second preimages. For a target of about 2k blocks, Kelsey and Schneier find a second preimage in roughly k·2n/2+1 + 2n−k+1 work, using expandable messages built from multicollisions or fixed points. This is the origin of the reduced second-preimage figures in the table in §1.4.[17,21]

Successor designs patch these issues in different ways: wide-pipe designs keep an internal state larger than the output (SHA-512/256), HAIFA-style designs mix a counter into every compression call (BLAKE2), and the sponge keeps part of its state permanently hidden.[2,26,27]

2.4 The sponge construction and the Keccak permutation

The sponge, introduced by Bertoni, Daemen, Peeters and Van Assche, iterates a fixed permutation f on a state of b = r + c bits.[27] The rate r is the part that touches data; the capacity c is never directly read or written by the user and sets the security level.

  1. Absorb. Pad the message to a multiple of r bits. For each r-bit block, XOR it into the first r bits of the state, then apply f.
  2. Squeeze. Output the first r bits of the state; if more output is needed, apply f and output r more bits, and so on.

A sponge with an ideal random permutation is indifferentiable from a random oracle up to about 2c/2 queries.[13] This single number explains the SHA-3 parameters: SHA3-256 sets c = 512 so that the sponge itself is not the weak point at the 256-bit preimage level.[18]

Keccak-f[1600]

SHA-3 instantiates f with Keccak-f[1600], a permutation on a 1600-bit state arranged as a 5×5 array of 64-bit lanes, iterated for 24 rounds.[18,28] Each round applies five step mappings:

χ has algebraic degree 2, which keeps hardware cheap and makes masking against side channels easier; the large number of rounds compensates.[28] FIPS 202 defines the permutation family generally as Keccak-p[b, nr]; reduced-round members such as Keccak-p[1600, 12] are used in non-NIST designs like KangarooTwelve.[18]

2.5 Tree hashing

Both MD and the sponge are inherently sequential: block i cannot be processed until block i−1 is done. Tree hashing splits the input into chunks, hashes the chunks independently (in parallel across cores or SIMD lanes), and then hashes the chunk digests together up a tree. The output is a different function from the sequential hash, so the mode must be specified exactly. Bertoni et al.'s Sakura coding gives sufficient conditions for a tree mode to be as secure as its inner function, chiefly that leaves, inner nodes and the root are unambiguously distinguishable.[29]

Standardised or widely deployed tree modes include NIST's ParallelHash (a two-level tree over cSHAKE), KangarooTwelve, BLAKE2's optional tree mode (BLAKE2bp, BLAKE2sp) and BLAKE3, which is always a tree.[23,24,26] The same tree shape, with leaves holding data records rather than chunks of one file, is the Merkle tree of §4.2.

2.6 Domain separation

Domain separation means making sure that hash inputs produced for different purposes can never be equal, typically by prefixing or suffixing a distinct tag. Without it, a value computed in one context can be replayed in another: a Merkle inner node could be presented as a leaf, or a key-derivation output could double as a signature hash. Examples from the standards:

  • SHA-3 versus SHAKE. Before padding, FIPS 202 appends the bits 01 for SHA3-d and 1111 for SHAKE, so SHA3-256(M) and SHAKE128(M, 256) are unrelated even when parameters overlap.[18]
  • cSHAKE customisation. SP 800-185 adds a function-name string N and a customisation string S, so that KMAC, TupleHash and ParallelHash, and any application-defined variants, are domain-separated by construction.[23]
  • Merkle tree node tags. Certificate Transparency hashes leaves as SHA-256(0x00 ‖ leaf) and interior nodes as SHA-256(0x01 ‖ left ‖ right).[30]
  • BLAKE2 personalisation and BLAKE3 modes. BLAKE2 has a 16-byte (BLAKE2b) or 8-byte (BLAKE2s) personalisation parameter; BLAKE3 has distinct hash, keyed_hash and derive_key modes, the last taking a hard-coded context string.[24,26]
Domain separation with BLAKE2b personalisation
import hashlib
a = hashlib.blake2b(b"msg", person=b"app-v1", digest_size=32).hexdigest()
b = hashlib.blake2b(b"msg", person=b"app-v2", digest_size=32).hexdigest()
print(a != b)   # True: same input, different domains, unrelated digests

A related discipline is unambiguous encoding. Hashing "ab" + "c" and "a" + "bc" gives the same digest, so multi-field inputs need length prefixes or a canonical encoding. TupleHash exists precisely to hash a sequence of strings unambiguously.[23]

2.7 Extendable-output functions (XOFs)

An extendable-output function produces output of any requested length d, and shorter outputs are prefixes of longer ones. The sponge is naturally an XOF: keep squeezing. FIPS 202 standardises two, SHAKE128 and SHAKE256, and SP 800-185 builds cSHAKE, KMAC (including KMACXOF) and others on them.[18,23] BLAKE3 is also an XOF.[24]

xof.py — prefix property of SHAKE128
import hashlib
short = hashlib.shake_128(b"abc").hexdigest(16)
long_ = hashlib.shake_128(b"abc").hexdigest(64)
print(short)
print(long_.startswith(short))   # True
5881092dd818bf5cf8a3ddb793fbcba7
True
Caution

The prefix property means that SHAKE128(M, 32 bytes) and SHAKE128(M, 64 bytes) are related: one is the start of the other. If two uses of an XOF must be independent, separate them by domain (different input tags or cSHAKE customisation strings), not by output length.[18,23] Also, more output does not mean more security: SHAKE128 never exceeds 128-bit security, however long its output.[18]

Typical XOF uses are key derivation and mask generation (filling a buffer of arbitrary length), deterministic random generation in post-quantum schemes, and as a hash with a length chosen by the application, such as the SHAKE256 instances inside SLH-DSA.[31]

3.2 MD4 and MD5

Ron Rivest designed MD4 (RFC 1320) for speed on 32-bit machines: a Merkle–Damgård hash with a 128-bit state of four 32-bit words, processing 512-bit blocks in three rounds of 16 operations each.[32] Its successor MD5 (RFC 1321) added a fourth round, a unique additive constant per step (taken from the integer part of 232·|sin(i)|), and a few other changes; the RFC describes it as slightly slower than MD4 but more "conservative" in design.[4]

Both fell to Xiaoyun Wang's differential techniques, presented at EUROCRYPT 2005: MD4 collisions with fewer than 28 MD4 computations, effectively by hand, and MD5 collisions in about an hour on an IBM P690 cluster.[16,34] Chosen-prefix MD5 collisions followed, which allow two meaningful documents with different prefixes to collide. Stevens et al. used them in 2008 to create a rogue certification authority certificate trusted by browsers.[11] The Flame espionage malware, discovered in 2012, used a previously unknown MD5 chosen-prefix collision to forge a Microsoft code-signing certificate.[35]

Status

RFC 6150 moved MD4 to Historic status, and RFC 6151 states that MD5 must not be used where collision resistance is needed, for example in digital signatures. RFC 6151 also notes that HMAC-MD5 was not immediately broken by these attacks, because HMAC's security does not rest on collision resistance, but discourages it for new protocols.[9,36] MD5 survives only as a non-adversarial checksum, and even there SHA-256 or BLAKE3 is a better default.

3.3 SHA-1

The NSA-designed Secure Hash Algorithm was published as FIPS 180 in 1993 (now called SHA-0) and amended in 1995 as FIPS 180-1 with a single change to the message schedule: a one-bit rotation.[37] SHA-1 produces 160-bit digests from 512-bit blocks in 80 steps.[2]

  • 2005. Wang, Yin and Yu estimated a collision cost of under 269 SHA-1 operations, the first attack below the 280 birthday bound.[37]
  • 2017, SHAttered. Stevens, Bursztein, Karpman, Albertini and Markov published the first full SHA-1 collision: two distinct PDF files with the same digest. It took about 263.1 SHA-1 computations, roughly 6,500 CPU-years and 110 GPU-years.[10]
  • 2020, "SHA-1 is a Shambles". Leurent and Peyrin computed the first practical chosen-prefix SHA-1 collision (about 263.4 work) and used it to forge PGP/GnuPG key certifications.[38]

NIST announced in December 2022 that SHA-1 should be phased out completely by 31 December 2030.[39] Git, which identifies objects by SHA-1, now uses a collision-detecting SHA-1 implementation based on Stevens's counter-cryptanalysis, and supports a SHA-256 object format.[35,40]

3.4 SHA-2: SHA-224, SHA-256, SHA-384, SHA-512

The SHA-2 family, specified in FIPS 180-4, has two cores.[2]

SHA-256 coreEight 32-bit state words, 512-bit blocks, 64 rounds, message length field 64 bits. SHA-224 uses different initial values and outputs 224 of the 256 bits.
SHA-512 coreEight 64-bit state words, 1024-bit blocks, 80 rounds, length field 128 bits. SHA-384, SHA-512/224 and SHA-512/256 use different IVs and truncate.

Each round updates eight working variables a…h using the bitwise functions Ch(x,y,z) = (x ∧ y) ⊕ (¬x ∧ z) and Maj(x,y,z) = (x ∧ y) ⊕ (x ∧ z) ⊕ (y ∧ z), two rotation-based Σ functions, one word of the expanded message schedule Wt and a round constant Kt. The SHA-256 constants are the first 32 bits of the fractional parts of the cube roots of the first 64 primes, and its IV comes from the square roots of the first eight primes. Such "nothing-up-my-sleeve" constants show the designers had no freedom to plant a weakness.[2]

On 64-bit CPUs without hardware SHA extensions, SHA-512 is often faster per byte than SHA-256, because it processes twice as much data per round with 64-bit operations. SHA-512/256 is therefore a good choice when a 256-bit digest is wanted and length-extension resistance helps.[17,41] No attack on full SHA-2 is anywhere near practical, and it remains the default choice for signatures, TLS, certificates and most protocols.

3.6 BLAKE2 and BLAKE3

BLAKE2 (2012) refines BLAKE, a SHA-3 finalist, for software speed. Its compression function is built from the ChaCha quarter-round; BLAKE2b uses 64-bit words and 12 rounds, BLAKE2s 32-bit words and 10 rounds. It has a built-in key input (so a MAC needs no HMAC wrapper), a salt, a personalisation string, and tree-hashing parameters, and the authors reported speeds faster than MD5 on contemporary x86-64 CPUs.[26] RFC 7693 specifies the core hash and keyed mode.[5] Argon2 uses BLAKE2b internally.[43]

BLAKE3 (2020) reduces BLAKE2s to 7 rounds and wraps it in a mandatory binary tree over 1 KiB chunks. The tree gives unlimited parallelism (SIMD across chunks, multithreading across subtrees), verified streaming, and incremental updates; the root can be squeezed as an XOF. It targets 128-bit security for all its goals and exposes three modes: hash, keyed_hash (MAC/PRF) and derive_key (KDF with a context string).[24]

3.7 RIPEMD-160

RIPEMD-160 was designed in 1996 by Dobbertin, Bosselaers and Preneel as a strengthened replacement for the original RIPEMD, after Dobbertin's attacks on reduced versions of RIPEMD and MD4. It runs two independent, differently structured lines of five rounds of 16 steps over each 512-bit block and combines them at the end, producing a 160-bit digest.[33] The original RIPEMD fell to Wang et al. in 2005 together with MD4; no practical collision is known for full RIPEMD-160.[34] Its best-known modern use is Bitcoin's HASH160 = RIPEMD-160(SHA-256(x)), which forms the 20-byte payload of many addresses.[44] With only 80-bit collision security it is not recommended for new designs.

4. Hash-based data structures

Once you trust a hash to be collision resistant, a digest becomes a compact, unforgeable name for data. Linking digests together turns that into structures that can prove facts about large data sets with a few dozen bytes.

4.1 Hash chains

A hash chain is the sequence x, H(x), H2(x), …, Hn(x). Moving forward is easy; moving backward requires a preimage. Lamport used this in 1981 for one-time passwords: the server stores only Hn(x), and the user authenticates with Hn−1(x), then Hn−2(x), and so on. An eavesdropper who sees one password cannot compute the next one.[47] This is the basis of S/KEY and the IETF one-time password system.[48]

chain.py — Lamport one-time passwords
import hashlib, os

def H(x: bytes) -> bytes:
    return hashlib.sha256(x).digest()

seed, n = os.urandom(32), 1000
chain = [seed]
for _ in range(n):
    chain.append(H(chain[-1]))
server_stored = chain[n]              # the server keeps only H^n(seed)

def login(otp: bytes) -> bool:
    global server_stored
    if H(otp) == server_stored:
        server_stored = otp           # step the anchor back by one
        return True
    return False

print(login(chain[n - 1]))   # True
print(login(chain[n - 1]))   # False: a replayed password is rejected
print(login(chain[n - 2]))   # True

Hash chains reappear in many forms: an append-only log where each entry includes the hash of the previous one (so altering any entry changes every later hash), Haber and Stornetta's linked time-stamping, and the block chain of Bitcoin, where each block header contains the hash of its predecessor.[49,50] Hash-based one-time and few-time signatures (Lamport, Winternitz) also use chains; standardised descendants include XMSS, LMS and SLH-DSA.[31]

4.2 Hash trees, Merkle trees and Merkle proofs

A hash tree, or Merkle tree, puts data blocks at the leaves, labels every leaf with the hash of its data and every inner node with the hash of its children's labels, and publishes the root. Merkle introduced the idea in his 1979 thesis to authenticate many one-time signature public keys with a single value.[45,51] Changing any leaf changes the root, so the root commits to the entire data set.

The payoff is the Merkle proof (audit path, inclusion proof). To prove that a leaf belongs under a known root, provide the sibling hash at each level from the leaf to the root. The verifier recomputes the path and compares the result with the root. For N leaves the proof has ⌈log2 N⌉ hashes: 20 hashes (640 bytes with SHA-256) are enough for a million leaves.[30]

merkle.py — Merkle tree, inclusion proof and verification
import hashlib

def H(b: bytes) -> bytes:
    return hashlib.sha256(b).digest()

# Domain separation as in RFC 6962: 0x00 prefix for leaves, 0x01 for interior nodes
def leaf_hash(data: bytes) -> bytes:
    return H(b"\x00" + data)

def node_hash(left: bytes, right: bytes) -> bytes:
    return H(b"\x01" + left + right)

def build_levels(leaves):
    level = [leaf_hash(x) for x in leaves]
    levels = [level]
    while len(level) > 1:
        nxt = []
        for i in range(0, len(level), 2):
            if i + 1 < len(level):
                nxt.append(node_hash(level[i], level[i + 1]))
            else:
                nxt.append(level[i])        # odd node is promoted, never duplicated
        level = nxt
        levels.append(level)
    return levels

def root(levels):
    return levels[-1][0]

def prove(levels, index):
    """Audit path: list of (sibling_hash, sibling_is_left)."""
    path = []
    for level in levels[:-1]:
        sib = index ^ 1
        if sib < len(level):
            path.append((level[sib], sib < index))
        index //= 2
    return path

def verify(data, path, expected_root):
    h = leaf_hash(data)
    for sib, sib_is_left in path:
        h = node_hash(sib, h) if sib_is_left else node_hash(h, sib)
    return h == expected_root

if __name__ == "__main__":
    txs = [b"alice->bob:5", b"bob->carol:2", b"carol->dave:1",
           b"dave->erin:7", b"erin->frank:3"]
    levels = build_levels(txs)
    r = root(levels)
    print("root      :", r.hex())
    proof = prove(levels, 2)
    print("proof size:", len(proof), "hashes")
    for sib, left in proof:
        print("  ", "L" if left else "R", sib.hex()[:16] + "...")
    print("valid     :", verify(b"carol->dave:1", proof, r))
    print("tampered  :", verify(b"carol->dave:9", proof, r))

Two classic pitfalls

No leaf/node separation. If leaves and interior nodes are hashed the same way, the 64-byte concatenation of two child hashes is itself a valid "leaf", so an attacker can prove membership of data that was never inserted. The 0x00/0x01 prefixes prevent this.[30]

Duplicating the odd node. Bitcoin's Merkle tree pairs a lone last node with a copy of itself. That makes the lists [a, b, c] and [a, b, c, c] produce the same root, which enabled a denial-of-service bug (CVE-2012-2459) in which a node could be made to reject a valid block.[52] The code above promotes the odd node instead, as RFC 6962 does.

Beyond inclusion, RFC 6962 also defines consistency proofs, which show that a later tree is an append-only extension of an earlier one, with O(log N) hashes.[30] Variants include sparse Merkle trees (a leaf for every possible key, enabling proofs of non-membership) and Merkle Patricia tries.

4.3 Authenticated data structures

An authenticated data structure (ADS) lets an untrusted server answer queries over a data set on behalf of a trusted source, together with a proof that the answer is correct relative to a short digest the source signed.[53] The three parties are the source (owns the data and publishes a signed digest), the responder (stores the data and answers queries) and the client (checks proofs against the digest). The Merkle tree is the canonical ADS for membership queries; authenticated skip lists, authenticated dictionaries and hash-based search trees extend the idea to ordered queries, range queries and updates.[53]

Certificate TransparencyPublic logs of TLS certificates. Browsers check inclusion proofs; monitors check consistency proofs so a log cannot quietly rewrite history.[30]
Light clientsBitcoin's simplified payment verification lets a client confirm that a transaction is in a block by checking a Merkle branch against a block header, without downloading the block.[50]
Verified file systemsSystems such as Linux dm-verity and fs-verity store a Merkle tree over a read-only partition or file so every block read is checked against a trusted root hash.

4.4 Cryptographic commitments

A commitment scheme is the digital analogue of a sealed envelope: you commit to a value now and open it later. It must be hiding (the commitment reveals nothing about the value) and binding (you cannot later open it to a different value).[54] A hash gives a simple, practical scheme: commit with c = H(r ‖ v) for a fresh random r, and open by revealing (r, v). Binding follows from collision resistance; hiding is heuristic and relies on the hash behaving like a random oracle.

commit.py — a hash commitment
import hashlib, hmac, secrets

TAG = b"commit-v1|"                              # domain separation for this protocol

def commit(value: bytes):
    r = secrets.token_bytes(32)                  # fresh 256-bit randomness for hiding
    return hashlib.sha256(TAG + r + value).digest(), r

def open_commitment(c: bytes, value: bytes, r: bytes) -> bool:
    return hmac.compare_digest(c, hashlib.sha256(TAG + r + value).digest())

c, r = commit(b"rock")
print(open_commitment(c, b"rock", r))    # True
print(open_commitment(c, b"paper", r))   # False

The randomness is not optional. If you commit to H("rock"), an opponent simply hashes "rock", "paper" and "scissors" and compares; low-entropy values need a high-entropy blinding factor. Because r has fixed length and comes first, the encoding is unambiguous. Commit–reveal schemes appear in coin-flipping and sealed-bid protocols, in hash-based signatures, and as building blocks in zero-knowledge proofs.[54]

4.5 Content-addressable storage

In content-addressable storage (CAS), an object's address is the hash of its content. Lookups need no index of names; identical content is stored once (deduplication); and any corruption or tampering is detected on read, because the content no longer matches its address.

Git is the most familiar example. A file is stored as a blob whose identifier is SHA-1 over a short header plus the content; trees list blobs and subtrees by hash, and commits point to a tree and to parent commits. The commit hash therefore authenticates the entire history, which makes a Git repository a Merkle DAG.[55]

The header (blob 3\0, meaning type and length) is itself a form of domain separation: a blob and a tree with the same bytes get different IDs.[55] IPFS generalises the idea to a peer-to-peer network: content identifiers (CIDs) are self-describing "multihashes" that record which hash function was used, so the system can migrate algorithms without breaking old links.[56] Docker and OCI images identify layers by sha256: digests in the same spirit.

4.6 Distributed integrity verification

When data comes from many untrusted peers, hashes let a receiver check each piece independently against a small trusted value:

  • BitTorrent splits a file into pieces and puts the SHA-1 hash of every piece in the .torrent metadata; a client discards any piece that does not match, so a malicious peer can waste bandwidth but cannot corrupt the download.[57] Version 2 of the protocol, added to the specification in 2017, moves to per-file SHA-256 Merkle trees.[58]
  • Subresource Integrity lets a web page pin a script or stylesheet served from a CDN: <script src="…" integrity="sha384-…">. The browser refuses the file if its digest differs.[59]
  • Blockchains combine a hash chain of block headers with a Merkle tree of transactions per block, so any participant can verify the whole ledger from the genesis block.[50]
  • Transparency logs (Certificate Transparency, Go's checksum database, Sigstore's Rekor) publish Merkle tree heads that independent auditors cross-check, turning "trust the server" into "detect a lying server".[30]

5. Password hashing

5.1 Password hashing versus general-purpose hashing

A server should never store passwords in a form it can reverse. It stores a verifier derived by a one-way function and, at login, recomputes it from the submitted password and compares. The threat model is a database breach: the attacker has every verifier and can run unlimited guesses offline, on their own hardware, with no rate limiting.[60,61]

General-purpose hashes are a poor fit for this, for the very reasons they are good elsewhere:

General-purpose hash (SHA-256, BLAKE3)Password hash (Argon2id, scrypt, bcrypt, PBKDF2)

Output formatRaw digestSelf-describing string with algorithm, parameters and salt

Preimage resistance does not help when the input space is small: an attacker does not invert SHA-256, they hash candidate passwords until one matches. The defence is to make each guess expensive and to stop one computation serving many targets.[62]

5.2 Salting and peppers

A salt is a random value, unique per stored password, that is hashed together with the password and stored alongside the result. It has two effects:[61,62]

  • No precomputation. Rainbow tables and lookup tables built for unsalted hashes are useless, since every salt needs its own table.
  • No multi-target batching. Without salts, one guess is checked against every account at once, and users with the same password share a hash. With unique salts the attacker must attack each account separately.

A salt does not slow down guessing against a single account; that is the job of the work factor. NIST SP 800-63B-4 requires the salt to be at least 32 bits and chosen to minimise collisions between stored hashes; SP 800-132 asks for at least 128 random bits, and 16 bytes from a cryptographically secure generator is the usual choice.[60,62]

A pepper is a secret key shared by all hashes and kept outside the database: in a hardware security module, a key-management service, or at least in application configuration. SP 800-63B-4 says verifiers should perform an additional keyed hashing or encryption step with a secret key known only to the verifier, stored separately from the hashed passwords.[60] If an attacker steals only the database, a pepper makes offline guessing impossible. Rotating a pepper is awkward, since you cannot recompute a hash without the password, which is one reason to apply it as a final encryption or HMAC layer that can be re-wrapped.[61]

pepper.py — HMAC pepper before Argon2id
import hmac, hashlib, os
from argon2 import PasswordHasher

# In production load this from a KMS/HSM or secret store; never store it in the DB.
PEPPER = bytes.fromhex(os.environ["PASSWORD_PEPPER_HEX"])
ph = PasswordHasher()

def peppered(password: str) -> str:
    return hmac.new(PEPPER, password.encode(), hashlib.sha256).hexdigest()

stored = ph.hash(peppered("hunter2"))
print(ph.verify(stored, peppered("hunter2")))   # True

Pre-hashing is also a way around bcrypt's 72-byte input limit, but OWASP warns that it is easy to get wrong: raw digests can contain zero bytes that some bcrypt implementations treat as the end of the string, and an unkeyed pre-hash lets an attacker "shuck" the outer layer using hashes leaked from other sites. Its suggested form is bcrypt(base64(HMAC-SHA384(password, pepper))), with the pepper stored outside the database.[61]

5.3 Work factors and key stretching

Key stretching turns a low-entropy secret into a key or verifier by iterating an expensive computation, so that each guess costs the attacker as much as one legitimate login costs the server. If an attacker's search space is 2k passwords and stretching multiplies the cost per guess by 2w, the effective work becomes 2k+w. SP 800-132 frames the iteration count exactly this way.[62]

The work factor (cost parameter) is the knob: an iteration count for PBKDF2, a logarithmic cost for bcrypt, and time, memory and parallelism parameters for scrypt and Argon2. It should be "as high as practical without negatively impacting verifier performance" and raised over time as hardware improves; storing the parameters with each hash is what makes that possible.[60]

Iteration alone has a weakness: GPUs and ASICs run thousands of cheap SHA-256 cores in parallel. Memory-hard functions make each guess require a large amount of RAM, and memory is expensive to replicate in parallel hardware. Percival introduced the concept, with scrypt as its first instance; Argon2 refined it.[43,63]

5.4 PBKDF2

PBKDF2 (Password-Based Key Derivation Function 2) comes from PKCS #5, now RFC 8018, and is the scheme approved in NIST SP 800-132.[62,64] It applies a pseudorandom function, in practice HMAC with SHA-1, SHA-256 or SHA-512, c times and XORs the intermediate results:

U1 = PRF(P, S ‖ INT(i)),  Uj = PRF(P, Uj−1),  Ti = U1 ⊕ U2 ⊕ … ⊕ Uc

The derived key is T1 ‖ T2 ‖ … truncated to the requested length.[64] PBKDF2 is simple, standardised and FIPS-validatable, but it uses almost no memory, so GPUs attack it efficiently. SP 800-132 sets a floor of 1,000 iterations (and suggests 10,000,000 for critical keys); OWASP currently recommends 600,000 iterations for PBKDF2-HMAC-SHA256 and 220,000 for PBKDF2-HMAC-SHA512.[61,62]

5.5 bcrypt

Provos and Mazières designed bcrypt for OpenBSD in 1999 around "Eksblowfish", an expensive variant of the Blowfish key schedule. The cost parameter is logarithmic: cost 12 means 212 iterations of the key setup, and each increment doubles the work, which is what the authors meant by "future-adaptable".[65] Blowfish's constantly modified 4 KiB S-boxes make bcrypt somewhat unfriendly to GPUs, though it is not memory-hard in the modern sense.[61]

5.6 scrypt

Colin Percival introduced scrypt in 2009 together with the notion of a sequential memory-hard function: one that, for a given amount of time, needs close to the maximum possible memory, so that trading memory for time is expensive.[63] It is specified in RFC 7914.[66] scrypt runs PBKDF2-HMAC-SHA256 to expand the password, fills a large array using the Salsa20/8-based BlockMix function (ROMix), reads it back in a data-dependent order, and compresses the result with PBKDF2 again. Its parameters are:

  • N: CPU/memory cost, a power of two. Memory use is about 128·N·r bytes.
  • r: block size (8 is standard).
  • p: parallelisation, the number of independent ROMix instances.

OWASP's minimum recommendation is N = 217, r = 8, p = 1, which uses 128 MiB per hash.[61] Because the memory access pattern depends on the password, scrypt can in principle leak information through cache-timing side channels; Argon2id was designed to address that.[43] scrypt is also the proof-of-work function of Litecoin and several other cryptocurrencies.

5.7 Argon2 and Argon2id

Argon2, by Biryukov, Dinu and Khovratovich, won the Password Hashing Competition in 2015 and is specified in RFC 9106 (2021).[43,46] It fills a memory array of m KiB in 1 KiB blocks using a compression function based on BLAKE2b's round function, makes t passes over it, and splits the work into p lanes that can run on separate threads. There are three variants:[43]

Argon2dData-dependent memory access. Strongest against GPU and time–memory trade-off attacks, but its access pattern can leak through side channels.
Argon2iData-independent memory access. Side-channel resistant, but more exposed to trade-off attacks, so it needs more passes.
Argon2idHybrid: the first half of the first pass is data-independent (like Argon2i), the rest data-dependent (like Argon2d). RFC 9106 makes it the variant that must be supported and recommends it by default.

RFC 9106 gives two recommended Argon2id settings: t = 1, p = 4, m = 2 GiB if that much memory is affordable, otherwise t = 3, p = 4, m = 64 MiB, with a 128-bit salt and 256-bit tag.[43] The argon2-cffi library uses the second, low-memory profile as its default.[67] OWASP lists five configurations it considers equivalent, from m = 46 MiB, t = 1 down to m = 7 MiB, t = 5, all with p = 1; m = 19 MiB, t = 2 is a common choice.[61]

5.9 Offline guessing resistance

The attacker's cost is (number of guesses needed) × (cost per guess). The hash function controls only the second factor. A worked comparison, using round numbers chosen for illustration rather than measured benchmarks:

Worked example

Passwords are 8 random characters from lowercase letters and digits: 368 ≈ 2.82 × 1012 candidates (about 41.4 bits).

Unsalted fast hash. Suppose a GPU rig tests 1010 SHA-256 guesses per second. Exhausting the space takes 2.82 × 1012 / 1010 ≈ 282 seconds, and because there is no salt, that one pass cracks every account in the dump whose password is in the space.

Slow, salted hash. Suppose instead the same rig manages 104 guesses per second against a memory-hard hash. The same search takes 2.82 × 108 s ≈ 8.9 years per account, and the salt means it must be repeated for each account.

A slow hash buys a factor of about a million here. It cannot rescue a password that is in the top few thousand of a cracking wordlist; that is why SP 800-63B-4 also requires checking new passwords against blocklists of common and compromised values.[60]

Real attackers do not search uniformly. Tools like hashcat and John the Ripper combine wordlists, mangling rules, Markov models and masks to try likely passwords first (§6).[68,69] Offline guessing resistance therefore depends on three layers: the per-guess cost (the hash), the per-account separation (the salt), and an additional secret the attacker may not have (the pepper).

5.10 Password hash migration

Because the server never knows the plaintext password, it cannot simply recompute old hashes with a new algorithm. Two standard strategies exist, and they are often combined:[61]

  1. Rehash on login. When a user logs in successfully, you have the plaintext for a moment: verify with the old scheme, then store a new hash. Simple, but accounts that never log in keep the weak hash forever.
  2. Layered (wrapped) hashes. Immediately wrap every existing hash, new = Argon2id(old_hash), so the entire database is protected today. At login, compute the legacy hash of the submitted password, verify it through the wrapper, and replace the record with a direct Argon2id(password).
migrate.py — wrap legacy SHA-1 hashes, then upgrade on login
import hashlib
from argon2 import PasswordHasher, exceptions

ph = PasswordHasher()                         # Argon2id, RFC 9106 low-memory profile

def legacy_sha1(pw: str) -> str:              # what the old system stored
    return hashlib.sha1(pw.encode()).hexdigest()

def wrap(legacy_hex: str) -> str:             # run once, offline, over every row
    return "wrapped$" + ph.hash(legacy_hex)

def verify_and_upgrade(record: str, pw: str):
    if record.startswith("wrapped$"):
        try:
            ph.verify(record[len("wrapped$"):], legacy_sha1(pw))
        except exceptions.VerifyMismatchError:
            return False, record
        return True, ph.hash(pw)              # replace with a direct Argon2id hash
    try:
        ph.verify(record, pw)
    except exceptions.VerifyMismatchError:
        return False, record
    if ph.check_needs_rehash(record):         # parameters were raised since
        record = ph.hash(pw)
    return True, record

rec = wrap(legacy_sha1("Tr0ub4dor&3"))
ok, rec = verify_and_upgrade(rec, "Tr0ub4dor&3")
print(ok, rec[:31] + "...")                   # True $argon2id$v=19$m=65536,t=3,p=4...
print(verify_and_upgrade(rec, "Tr0ub4dor&3")[0])   # True

The prefix tag (wrapped$) and the self-describing PHC string are what make this safe: each record says exactly how to verify it, which is the "reference to the password hashing scheme used, including the cost factor" SP 800-63B-4 asks verifiers to store.[60] The same check_needs_rehash logic handles routine parameter increases. After a deadline, accounts still on a wrapped legacy hash can be forced through a password reset.

7. Exercises

Try each before opening the solution. Exercises marked ⚙ need a computer.

1. Birthday bound. You truncate SHA-256 to 80 bits to save space in a database of identifiers. Roughly how many random entries can you store before the chance of some collision reaches 50%? How much work does an attacker need to find a collision deliberately?

Both answers are on the order of 280/2 = 240 ≈ 1.1 × 1012; more precisely about 1.18 × 240 ≈ 1.3 × 1012 for 50%. 240 hash evaluations take minutes on one GPU, so an 80-bit truncation gives no meaningful collision resistance against an adversary, even though accidental collisions in a database of millions of entries are very unlikely (§1.4).

2. Padding. How many 512-bit blocks does SHA-256 process for messages of 0, 55, 56, 64 and 119 bytes?

Padding adds at least 1 byte (0x80) plus 8 bytes of length, so a message of L bytes needs ⌈(L + 9) / 64⌉ blocks.

0 → 1, 55 → 1, 56 → 2, 64 → 2, 119 → 2 (119 + 9 = 128 exactly). See §2.1 and FIPS 180-4 §5.1.[2]

3. Secret-prefix MAC. A web API authenticates requests as tag = SHA-256(key ‖ params). Explain the attack and give two correct alternatives.

SHA-256 is a Merkle–Damgård hash whose output is its full internal state, so from (params, tag) and the key length an attacker can compute a valid tag for params ‖ padding ‖ &admin=true (length extension, §2.3). Correct alternatives: HMAC-SHA-256 (RFC 2104), KMAC128/256 (SP 800-185), keyed BLAKE2 or BLAKE3 keyed_hash. SHA3-256(key ‖ msg) is also not length-extendable, but a standard MAC is the better engineering choice.[22,23]

4. Merkle proof size. A transparency log contains 230 certificates hashed with SHA-256. How many bytes is an inclusion proof? How does that compare with downloading the log if each entry is 1 KiB?

The tree height is 30, so the proof is 30 hashes × 32 bytes = 960 bytes. The log itself is 230 KiB = 1 TiB, so the proof is about a billion times smaller.[30]

5. Leaf/node confusion. A Merkle tree hashes leaves as H(x) and nodes as H(L ‖ R), with no prefixes. Show how to "prove" that a 64-byte value that was never inserted is in the tree.

Take any interior node N = H(L ‖ R). Claim that the 64-byte string x = L ‖ R is a leaf at N's position. Its "leaf hash" is H(x) = N, and the honest audit path from N to the root verifies. Prefixing leaves with 0x00 and nodes with 0x01 (RFC 6962) makes leaf and node inputs disjoint, so the forgery fails.[30]

6. Sponge arithmetic. How many Keccak-f calls does SHA3-256 make on a 1,000-byte message? How many does SHAKE128 make to produce 500 bytes from a 10-byte message?

SHA3-256 has rate 136 bytes. Padding adds at least one byte, so 1,001 bytes need ⌈1001/136⌉ = 8 blocks, hence 8 permutation calls during absorbing; the 32-byte output fits in the first squeeze.

SHAKE128 has rate 168 bytes. Absorbing the 10-byte message is 1 call. Squeezing 500 bytes needs ⌈500/168⌉ = 3 rate-blocks; the first is available after absorbing, so 2 more calls: 3 in total.[18]

7. Davies–Meyer fixed points. Show that for every message block m there is a chaining value h with f(h, m) = h, and explain why removing the feed-forward would be worse.

Let h = Dm(0), the decryption of the all-zero block under key m. Then f(h, m) = Em(h) ⊕ h = 0 ⊕ h = h. Without the feed-forward, f(h, m) = Em(h) is invertible: given any target output y and any block m, h = Dm(y) is a preimage, so the compression function would not be one-way at all.[20]

8. ⚙ Avalanche statistics. Write a script that flips each of the 8 bits of the first byte of "Hello" in turn and reports the number of SHA-256 output bits that change. What mean and spread do you expect? 
import hashlib
base = bytearray(b"Hello")
ref = hashlib.sha256(base).digest()
for bit in range(8):
    m = bytearray(base); m[0] ^= 1 << bit
    d = hashlib.sha256(m).digest()
    print(bit, sum(bin(a ^ b).count("1") for a, b in zip(ref, d)))

Each count should look like a draw from a binomial distribution with n = 256, p = 1/2: mean 128, standard deviation 8, so almost all values fall between about 112 and 144 (§1.3).[15]

9. Salt or pepper? For each threat, say whether a salt, a pepper, a higher work factor, or none of these helps: (a) a precomputed rainbow table; (b) two users with the same password; (c) an attacker with a full database dump, including the application server's config; (d) a user whose password is "123456".

(a) Salt. (b) Salt: identical passwords get different hashes. (c) Only the work factor; a pepper stored in the same compromised config adds nothing, which is why SP 800-63B-4 asks for the secret key to be stored separately, ideally in an HSM.[60] (d) None of them: it is guessed in the first handful of attempts whatever the cost. Blocklisting common passwords at registration is the fix.[60]

10. Cost doubling. A server uses bcrypt cost 10. Hardware gets twice as fast every two years. What cost should it use in eight years to keep the same per-guess time?

Eight years is four doublings. Each bcrypt cost increment doubles the work, so the cost should rise by 4, to 14.[65] Store the cost in each hash (bcrypt does this automatically) and rehash on login when it is below the current target.

11. Commitment hiding. Alice commits to her vote with c = SHA-256(vote), where the vote is "yes" or "no". Why is this broken, and how do you fix it without losing binding?

Anyone can compute SHA-256("yes") and SHA-256("no") and compare with c, so the commitment does not hide anything. Fix: c = SHA-256(tag ‖ r ‖ vote) with a fresh 256-bit random r, revealed at opening time. Binding still follows from collision resistance (§4.4).[54]

12. ⚙ Migration plan. Your legacy system stores unsalted MD5 password hashes for 2 million users, 30% of whom have not logged in for a year. Outline a migration that protects every account today.
  1. Wrap every row immediately: Argon2id(salt, md5_hex), tagged with a version prefix. All accounts are now protected by a slow, salted hash.
  2. On successful login, verify through the wrapper and replace the record with a direct Argon2id(password) hash.
  3. Delete the original MD5 column and any backups containing it.
  4. After a deadline, force a password reset for accounts still on wrapped hashes, and consider checking all new passwords against breached-password lists.

See §5.10 and the OWASP guidance on upgrading legacy hashes.[61]

8. Trivia

Where do MD5's 64 additive constants come from?

From the sine function: constant T[i] is the integer part of 232 × |sin(i)| for i = 1 … 64, with i in radians.[4]

What do the SHA-256 initial hash values represent?

The first 32 bits of the fractional parts of the square roots of the first eight primes, 2 to 19. The 64 round constants are the same for the cube roots of the first 64 primes.[2]

What is the SHA-256 digest of the empty string, and why do many developers recognise it?

e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855. It turns up whenever a program accidentally hashes an empty file or an empty request body, so spotting "e3b0c442…" in logs is a well-known debugging clue.

Which algorithm won the SHA-3 competition, and when was the winner announced?

Keccak, announced by NIST on 2 October 2012, chosen from 64 initial submissions. The other finalists were BLAKE, Grøstl, JH and Skein.[42]

What did the SHAttered team actually publish in 2017?

Two different PDF files with the same SHA-1 digest, the first full SHA-1 collision, at a cost of about 263.1 SHA-1 computations.[10]

Which piece of malware used a then-unknown MD5 collision attack?

Flame (2012). It forged a Microsoft code-signing certificate with a chosen-prefix MD5 collision using a variant of the attack not previously published; Stevens's counter-cryptanalysis reconstructed it from the certificate.[35]

How many rounds does Keccak-f[1600] have, and how many does BLAKE3 use?

24 rounds for Keccak-f[1600]; 7 rounds for BLAKE3's compression function (down from BLAKE2s's 10).[18,24]

What is the longest password bcrypt actually uses?

72 bytes in most implementations. Anything after that is ignored.[61]

Which competition did Argon2 win, and in what year?

The Password Hashing Competition, in 2015. Catena, Lyra2, Makwa and yescrypt received special recognition.[46]

What bug did Bitcoin's Merkle tree design cause in 2012?

CVE-2012-2459. Because a lone last node is paired with a copy of itself, different transaction lists could give the same Merkle root, and an attacker could get nodes to mark a valid block as invalid.[52]

Why are a Git blob's ID and the plain SHA-1 of the file's bytes different?

Git hashes a header first: "blob " + length + "\0" + content. For "abc" that gives f2ba8f84…, not a9993e36….[55]

In which year did Merkle's thesis introduce hash trees, and what were they for?

1979, at Stanford, to authenticate a large number of one-time signature public keys with a single root value: the ancestor of today's hash-based signatures.[45,51]

By what date does NIST want SHA-1 gone completely?

31 December 2030.[39]
