Symmetric-key cryptography is the workhorse of practical security. Public-key techniques establish who you are talking to and agree on a secret, but nearly every byte that is actually protected on disk or on the wire, from a TLS 1.3 record to a WireGuard packet to a sector of an encrypted laptop drive, is encrypted and authenticated with a symmetric algorithm keyed by that shared secret.[1–3] Symmetric algorithms are fast (modern CPUs encrypt with AES at gigabytes per second using dedicated instructions[4]), well studied, and, unlike today's public-key schemes, they are not broken by a large quantum computer; at worst Grover-style search roughly halves their effective key length, which is why 256-bit keys are recommended for long-term protection.[5]

This article goes deep on the primitives (block and stream ciphers), on the modes that turn a fixed-width block cipher into a usable encryption scheme, and on authenticated encryption, the only form of symmetric encryption you should deploy today. Other articles in this series cover the mathematical foundations (finite fields, probability), classical ciphers, and formal security definitions; here those topics appear only where needed.

Notation. EK(·) and DK(·) are block-cipher encryption and decryption under key K; ⊕ is bitwise XOR; ‖ is concatenation; n is the block length in bits; Pi, Ci are the i-th plaintext and ciphertext blocks; {xy} is a byte written in hexadecimal, as in FIPS 197.[6]

1. Fundamentals

1.1 Shared-secret keys

A symmetric (secret-key) cipher uses the same key K for encryption and decryption, or keys trivially derivable from each other. Formally a symmetric encryption scheme is a triple (Gen, Enc, Dec) with DecK(EncK(M)) = M for every key and message.[7] Following Kerckhoffs's principle, the algorithm is public and all of the security rests in the key, so the key must be:

  • Uniformly random and generated by a cryptographically secure random number generator (or derived from a high-entropy secret with a key-derivation function); a password is not a key.
  • Shared only between the communicating parties, which creates the key-distribution problem: n parties who all want pairwise secrecy need n(n−1)/2 keys. In practice keys are agreed with public-key methods (Diffie–Hellman in TLS 1.3) or distributed by a trusted key-distribution centre (Kerberos).[1,8]
  • Used for one purpose and for a bounded amount of data. NIST's key-management guidance assigns each key a cryptoperiod and forbids reusing one key across different algorithms or purposes.[5]

1.3 Key lengths

For an ideal cipher the best generic attack is exhaustive key search, costing about 2k trial decryptions for a k-bit key (2k−1 on average). The security strength of an algorithm is the base-2 log of the cost of the best known attack; it can be lower than the key length (3DES has a 168-bit key but only 112-bit strength because of meet-in-the-middle).[5,19]

1.4 Block ciphers versus stream ciphers

Block cipher

A family of permutations EK: {0,1}n → {0,1}n. Security goal: indistinguishable from a random permutation (a pseudorandom permutation, PRP). Alone it encrypts exactly one block; a mode is needed for longer or shorter messages.[7,21]

Stream cipher

A generator that expands a key (and nonce) into a long pseudorandom keystream z; encryption is C = P ⊕ z. No padding, minimal latency, but the keystream must never repeat.[8,22]

The line is blurred in practice: CTR, OFB and CFB modes turn a block cipher into a stream cipher, and ChaCha20 internally computes a 512-bit “block function” that it runs in counter mode.[18,21]

1.5 Deterministic versus randomized encryption

A deterministic scheme always maps the same (key, plaintext) to the same ciphertext. That leaks equality: an eavesdropper learns when a message repeats, which is fatal for structured data (“YES”/“NO” votes, database fields, image pixels). The standard notion of security against chosen-plaintext attack, IND-CPA, therefore cannot be met by a deterministic, stateless scheme: the adversary simply asks for the encryption of one of its challenge messages and compares.[7,23]

Secure schemes are therefore randomized (a fresh random IV per message, as in CBC) or stateful / nonce-based (a counter or nonce that never repeats, as in CTR or GCM). Deterministic encryption is acceptable only in narrow settings where equality leakage is intended or inputs are already unique, for example key wrapping with SIV,[24] or the length-preserving sector encryption of XTS (which deliberately trades this property for not expanding the data).[3]

1.7 Initialization vectors and nonce requirements

An initialization vector (IV) is a per-message input that makes encryption randomized or stateful. A nonce (“number used once”) is a value that must never repeat under the same key; it need not be secret or random. 2. Block cipher construction

Practically every block cipher is an iterated cipher: a relatively weak round function is applied many times, each time mixed with a different round key (subkey) derived from the master key by a key schedule.[8,33] Two architectures dominate: substitution–permutation networks and Feistel networks.

2.1 Confusion and diffusion

Claude Shannon identified the two properties a good cipher needs in his 1949 paper.[34]

  • Confusion makes the relationship between key and ciphertext as complex as possible, so that each ciphertext bit depends on the key in a highly non-linear way. In modern ciphers it is provided by S-boxes (or by modular addition in ARX designs).
  • Diffusion spreads the influence of each plaintext bit over many ciphertext bits, hiding statistical structure. It is provided by permutations and linear mixing layers (P-boxes, AES's ShiftRows + MixColumns).

Non-linearity defeats linear cryptanalysis, which looks for linear approximations holding with probability far from ½; good diffusion defeats differential cryptanalysis, which tracks how input differences propagate.[33,35,36]

2.2 Substitution–permutation networks

An SPN round applies three layers to the whole state: key mixing (XOR a round key), a substitution layer of small S-boxes in parallel, and a permutation / linear layer that moves bits between S-boxes so that the next round's S-boxes each see output from several previous ones.[33] Because every layer must be invertible, decryption runs the inverse layers in reverse order. AES, Serpent and PRESENT are SPNs.

2.3 Feistel networks

Horst Feistel's design at IBM (published for a general audience in 1973) splits the block into halves L and R and iterates[37]

Li = Ri-1 Ri = Li-1 ⊕ F(Ri-1, Ki)

The remarkable property is that the round is invertible whatever F is: given (Li, Ri), recover Ri-1 = Li and Li-1 = Ri ⊕ F(Li, Ki). So F can be a non-invertible, highly non-linear function, and decryption is the same circuit with the subkeys in reverse order. Luby and Rackoff proved that three Feistel rounds with independent pseudorandom round functions give a pseudorandom permutation, and four give a strong PRP (secure even when the adversary can also query the inverse).[38] DES, Blowfish, Twofish and Camellia are Feistel ciphers.

A third structure, the Lai–Massey scheme used by IDEA, mixes the two halves through their difference in a group so that, like Feistel, the round function itself need not be invertible.[16]

2.4 S-boxes, P-boxes and round functions

An S-box (substitution box) is a small lookup table mapping m input bits to n output bits; it is the main non-linear component. Design criteria include low differential uniformity (the maximum number of inputs pairs with a given input/output difference), high non-linearity (distance from all affine functions) and good avalanche behaviour.[33,39]

  • DES: eight 6→4-bit S-boxes, each with four 4-bit permutations selected by the outer two input bits. They turned out to be hardened against differential cryptanalysis years before it was publicly described.[9,36]
  • AES: a single 8→8-bit bijective S-box built from multiplicative inversion in GF(28) followed by an affine map; its maximum differential probability is 4/256 and maximum linear correlation 2−3.[6,40]
  • Serpent: eight 4→4-bit S-boxes, used in bitslice fashion.[14]
  • Blowfish, Twofish: key-dependent S-boxes, generated from the key.[12,13]

A P-box (permutation box) rearranges bit positions; more generally a linear layer mixes them. DES uses a fixed 32-bit permutation P after the S-boxes and an expansion permutation E (32→48 bits) before them; AES replaces bit permutations with byte-oriented ShiftRows and the MDS matrix of MixColumns, chosen so that any two rounds involve at least 5 “active” S-boxes and any four rounds at least 25 (the wide trail strategy).[9,40]

The round function is the composition used once per round: for DES the Feistel F = expand → XOR subkey → S-boxes → P; for AES the four transformations described in §3.3.

2.5 Key schedules

The key schedule expands the master key into round keys. Its quality matters: weak schedules enable related-key and slide attacks and produce weak keys. Examples:

  • DES: Permuted Choice 1 selects 56 bits, split into two 28-bit registers that are rotated left by 1 or 2 positions per round; Permuted Choice 2 selects 48 bits as each subkey. Its simplicity creates 4 weak keys (for which encryption is an involution) and 6 pairs of semi-weak keys.[8,9]
  • AES: a word-oriented recurrence using RotWord, SubWord and round constants (§3.3.5).[6]
  • Blowfish: deliberately slow; generating its subkeys and S-boxes requires 521 Blowfish encryptions, the property later exploited for the bcrypt password hash.[12,41]

2.6 The avalanche effect

A cipher exhibits the avalanche effect if flipping one input bit (plaintext or key) changes each output bit with probability about ½. Feistel described it informally;[37] Webster and Tavares formalised the strict avalanche criterion (SAC).[39] For AES with a 128-bit block we therefore expect about 64 output bits to change; the avalanche script measures 63.9 on average over 1000 random trials. Full diffusion is reached quickly: in AES, after two rounds every output byte depends on every input byte.[40]

3. Block cipher algorithms

3.1 Data Encryption Standard (DES)

DES grew out of IBM's Lucifer cipher and was published by the US National Bureau of Standards as FIPS 46 in 1977; its final revision, FIPS 46-3 (1999), was withdrawn in 2005.[8,9] It is a 16-round Feistel cipher on 64-bit blocks with a 64-bit key of which 8 bits are parity, leaving 56 effective key bits.

  • Initial / final permutation (IP and IP−1): fixed bit shuffles with no cryptographic value (they eased 1970s hardware loading).
  • Round function F: expansion E (32→48 bits, duplicating edge bits) → XOR 48-bit subkey → eight 6→4 S-boxes → permutation P.[9]
  • Key schedule: PC-1, per-round left rotations (1 or 2 bits), PC-2 (§2.5).
  • Complementation property: EK̄(P̄) = EK(P), which halves the cost of brute force under chosen plaintext.[8]

Cryptanalysis. Differential cryptanalysis breaks full DES with 247 chosen plaintexts, and linear cryptanalysis with about 243 known plaintexts.[8,35,36] Neither is as practical as brute force on 56 bits: in 1998 the EFF's purpose-built DES Cracker recovered a key in 56 hours for under US$250 000.[20]

3.2 Triple DES (3DES / TDEA)

Double encryption EK2(EK1(P)) adds almost nothing: a meet-in-the-middle attack encrypts P under all K1, decrypts C under all K2, and matches the middle values, costing about 257 operations and 256 memory.[19] Triple DES therefore uses three passes in Encrypt–Decrypt–Encrypt form:[11]

C = EK3( DK2( EK1(P) ) ) P = DK1( EK2( DK3(C) ) )

Setting K1 = K2 = K3 collapses EDE to single DES, which gave backward compatibility. With three independent keys (keying option 1) the key is 168 bits but meet-in-the-middle limits strength to about 112 bits.[5] The deeper problem is the 64-bit block: by the birthday bound, block collisions appear after about 232 blocks (32 GiB), and the Sweet32 attack used this to recover HTTP cookies from long-lived 3DES TLS connections.[42] NIST responded by limiting one key bundle to 220 blocks in SP 800-67 Rev. 2, disallowing 3DES for encryption after 31 December 2023, and withdrawing SP 800-67 on 1 January 2024.[10,11]

3.3 Advanced Encryption Standard (AES)

In 1997 NIST launched an open competition to replace DES. Fifteen candidates were accepted in 1998; five finalists (MARS, RC6, Rijndael, Serpent, Twofish) were announced in 1999; and Rijndael, by Joan Daemen and Vincent Rijmen, was selected in October 2000 for its combination of security, performance, efficiency and flexibility.[43] AES was published as FIPS 197 on 26 November 2001 (editorially updated in May 2023).[6] The full design rationale is in Daemen and Rijmen's book.[40]

AES is Rijndael restricted to a 128-bit block. The block is held in a 4×4 byte state, filled column by column (s[r,c] = in[r + 4c]). Bytes are elements of GF(28) defined by the irreducible polynomial m(x) = x8 + x4 + x3 + x + 1 ({11b}).[6]

3.3.1 SubBytes

Each byte is replaced independently using the S-box: take the multiplicative inverse in GF(28) (with {00} mapped to itself), then apply the affine transformation[6]

b'i = bi ⊕ b(i+4) mod 8 ⊕ b(i+5) mod 8 ⊕ b(i+6) mod 8 ⊕ b(i+7) mod 8 ⊕ ci, c = {63}

Example from FIPS 197: {53}−1 = {ca}, and the affine map sends {ca} to {ed}, so S({53}) = {ed}. Also S({00}) = {63}. The inversion gives the non-linearity; the affine map removes the algebraic simplicity of pure inversion and ensures there are no fixed points (S(a) ≠ a) or “opposite” fixed points (S(a) ≠ ā).[40]

3.3.2 ShiftRows

Row r of the state is rotated left by r bytes (row 0 unchanged, row 1 by 1, row 2 by 2, row 3 by 3). This moves the four bytes of each column into four different columns, so MixColumns in the next round mixes bytes that came from different columns.[6]

3.3.3 MixColumns

Each column is treated as a polynomial over GF(28) and multiplied modulo x4 + 1 by a(x) = {03}x3 + {01}x2 + {01}x + {02}; equivalently, multiplied by the matrix[6]

┌ s'₀ ┐ ┌ 02 03 01 01 ┐ ┌ s₀ ┐ │ s'₁ │ = │ 01 02 03 01 │ │ s₁ │ │ s'₂ │ │ 01 01 02 03 │ │ s₂ │ └ s'₃ ┘ └ 03 01 01 02 ┘ └ s₃ ┘

Multiplication by {02} (“xtime”) is a left shift followed by a conditional XOR with {1b}; {03}·x = {02}·x ⊕ x. The matrix is MDS (maximum distance separable), giving branch number 5: a change in k input bytes of a column changes at least 5−k output bytes.[40] A standard test column: db 13 53 45 → 8e 4d a1 bc.

3.3.4 AddRoundKey

The 128-bit round key (four words from the key schedule) is XORed into the state. It is the only step that depends on the key; the initial AddRoundKey is called key whitening.[6]

3.3.5 Key expansion

The key schedule produces 4(Nr+1) 32-bit words w[i]. The first Nk words are the key; thereafter[6]

temp = w[i−1] if i mod Nk == 0: temp = SubWord(RotWord(temp)) ⊕ Rcon[i/Nk] else if Nk == 8 and i mod Nk == 4: temp = SubWord(temp) (AES-256 only) w[i] = w[i−Nk] ⊕ temp

RotWord rotates a word by one byte, SubWord applies the S-box to each byte, and Rcon[j] = [xj−1, 0, 0, 0] with the powers of x in GF(28): 01 02 04 08 10 20 40 80 1b 36.

3.5 Other notable block ciphers

Blowfish (1993)

Bruce Schneier's unpatented replacement for DES: a 16-round Feistel cipher on 64-bit blocks with variable key length (32–448 bits). It has four key-dependent 8×32-bit S-boxes and an 18-entry P-array, all derived from the key by repeatedly encrypting with the cipher itself, starting from the hexadecimal digits of π.[12] The expensive key setup makes Blowfish unsuitable for frequent rekeying, but it is the basis of the bcrypt password hash.[41] Its 64-bit block makes it vulnerable to Sweet32-style birthday attacks for large volumes of data.[42]

Twofish (1998)

An AES finalist by Schneier, Kelsey, Whiting, Wagner, Hall and Ferguson: a 16-round Feistel network on 128-bit blocks with 128/192/256-bit keys. Its F-function uses key-dependent 8×8 S-boxes (built from fixed permutations q0, q1), a 4×4 MDS matrix over GF(28), a pseudo-Hadamard transform, 1-bit rotations, and input/output whitening.[13]

Serpent (1998)

An AES finalist by Anderson, Biham and Knudsen, designed with a very large security margin: a 32-round SPN on 128-bit blocks, with eight different 4×4 S-boxes (each round uses one of them 32 times in parallel) and a linear mixing layer. It is designed for bitslice implementation, computing all 32 S-boxes of a round with logical operations on 32-bit words.[14] NIST's report credited Serpent with a high security margin, but selected Rijndael for its overall balance of security, performance across platforms, and implementation flexibility.[43]

Camellia (2000)

Developed by Mitsubishi Electric and NTT. Camellia is an 18-round (128-bit key) or 24-round (192/256-bit key) Feistel cipher on 128-bit blocks, with key-dependent FL/FL−1 layers inserted every six rounds and S-boxes based on inversion in GF(28) like AES.[15,47] Its security and performance are comparable to AES, and it is standardised in ISO/IEC 18033-3 and specified for IETF use in RFC 3713.

IDEA (1991)

The International Data Encryption Algorithm by Xuejia Lai and James Massey (originally PES, 1990) encrypts 64-bit blocks with a 128-bit key over 8 rounds plus an output transformation (“8.5 rounds”). Its confusion comes from mixing three algebraically incompatible group operations on 16-bit words: XOR, addition modulo 216, and multiplication modulo 216+1 (with 0 representing 216).[16] IDEA was the cipher of PGP 2.x; classes of weak keys and its 64-bit block keep it in legacy use only.

4.1 Electronic Codebook (ECB)

ECB encrypts each block independently. It is deterministic at the block level: identical plaintext blocks give identical ciphertext blocks, so structure survives encryption. The classic demonstration encrypts a bitmap image; the outline is still visible because large areas of identical pixels form identical 16-byte blocks.[7,21]

4.2 Cipher Block Chaining (CBC)

CBC XORs each plaintext block with the previous ciphertext block before encrypting, so equal plaintext blocks encrypt differently; decryption is Pi = DK(Ci) ⊕ Ci-1 and can run in parallel. CBC is IND-CPA secure when the IV is unpredictable; a counter IV or the previous message's last ciphertext block is not enough.[21,23] CBC needs padding (or ciphertext stealing), cannot be parallelised for encryption, and is malleable: flipping a bit in Ci-1 flips the same bit of Pi (while garbling Pi-1).

4.3 Cipher Feedback (CFB) and Output Feedback (OFB)

Both turn the block cipher into a stream cipher, so the block cipher is only ever used in the encryption direction and no padding is needed.[21]

  • CFB-s feeds the last s bits of ciphertext back into a shift register that is encrypted to produce the next s keystream bits (s = 1, 8, 64 or 128). Because the keystream depends on the ciphertext, CFB is self-synchronising: after a bit error or lost segment, decryption recovers once the corrupted ciphertext has shifted out of the register. The IV must be unpredictable.
  • OFB feeds the block-cipher output back: Oi = EK(Oi-1). The keystream is independent of the data (a synchronous stream cipher) and can be precomputed; bit errors do not propagate. The IV must be a nonce, because reusing it reproduces the whole keystream.

4.4 Counter mode (CTR)

CTR encrypts a sequence of distinct counter blocks T1, T2, … (typically nonce ‖ block counter) to make a keystream: Ci = Pi ⊕ EK(Ti). It is fully parallel, supports random access, needs no padding and no decryption circuit, and is IND-CPA secure provided no counter block is ever repeated under the same key.[21,23] It is the confidentiality engine inside GCM, CCM and GCM-SIV.

4.5 Galois/Counter Mode (GCM)

GCM, designed by McGrew and Viega and standardised in SP 800-38D, combines CTR encryption with a polynomial MAC, GHASH, computed in GF(2128) with the field polynomial x128 + x7 + x2 + x + 1.[28,50]

  1. Hash key H = EK(0128).
  2. Pre-counter block J0 = IV ‖ 031 ‖ 1 for a 96-bit IV (other lengths are hashed with GHASH, which is discouraged).
  3. Encrypt with CTR starting at inc32(J0).
  4. S = GHASHH(A ‖ 0v ‖ C ‖ 0u ‖ [len(A)]64 ‖ [len(C)]64), where GHASH evaluates the polynomial X1Hm ⊕ X2Hm−1 ⊕ … ⊕ XmH.
  5. Tag T = MSBt(EK(J0) ⊕ S), with t ∈ {128, 120, 112, 104, 96}, or 64 and 32 for special applications.

Limits: plaintext at most 239−256 bits (about 64 GiB) per invocation; with random 96-bit IVs, at most 232 invocations per key.[28] With empty plaintext GCM becomes the MAC GMAC. GCM is fast in hardware (carry-less multiply instructions), and AES-GCM is mandatory-to-implement in TLS 1.3.[1]

4.6 GCM-SIV (AES-GCM-SIV)

GCM-SIV (Gueron and Lindell; specified as AES-GCM-SIV in RFC 8452) is a nonce-misuse-resistant AEAD in the SIV (“synthetic IV”) tradition of Rogaway and Shrimpton.[24,31,51] For each nonce it:

  1. derives a fresh 128-bit message-authentication key and a 128/256-bit message-encryption key from the master key and nonce (AES over counter ‖ nonce);
  2. computes S = POLYVAL(auth key, AAD ‖ plaintext ‖ lengths), where POLYVAL is a little-endian relative of GHASH over the polynomial x128 + x127 + x126 + x121 + 1;
  3. XORs the nonce into S, clears the top bit, and encrypts it to obtain the 128-bit tag;
  4. encrypts the plaintext in CTR mode using the tag (with its top bit set) as the initial counter.

Because the IV is a pseudorandom function of the whole message, repeating a nonce only reveals whether the same (AAD, plaintext) was encrypted twice. The price is two passes over the data (encryption cannot start until the whole plaintext has been hashed).[31]

4.7 Counter with CBC-MAC (CCM)

CCM (SP 800-38C) authenticates with CBC-MAC and then encrypts with CTR, using the same key for both.[30] The first CBC-MAC block B0 encodes flags (tag length, length-field size), the nonce and the message length; then come the encoded AAD and the plaintext. The MAC is encrypted with counter block 0, and the payload with counter blocks 1, 2, …. Nonce length is 7–13 bytes (a longer nonce leaves fewer bytes for the length field, since the two total 15 bytes), and the tag is 4–16 bytes (even lengths). CCM is not “online”: the message length must be known before processing starts. It is used where only an AES encryption core is available, for example in Wi-Fi WPA2 (CCMP).[30,52]

4.8 XTS for storage encryption

Disk encryption has unusual constraints: each 512-byte or 4096-byte sector must be encrypted independently, in place, with no room for an IV or tag. XTS-AES (IEEE 1619, approved in SP 800-38E) is a tweakable block cipher mode built on Rogaway's XEX construction, with ciphertext stealing for partial final blocks.[3,53] With the key split as K = K1 ‖ K2, the data-unit (sector) number i and block index j:

T = EK2(i) ⊗ αj (multiplication in GF(2¹²⁸)) Cj = EK1(Pj ⊕ T) ⊕ T

Each block in each sector gets a distinct “whitening” tweak, so moving ciphertext between positions or sectors does not produce meaningful plaintext. Limits and caveats: a data unit may hold at most 220 blocks;[3] XTS is deterministic, so an attacker who sees two snapshots of a disk learns which 16-byte blocks changed; and it provides no authentication: modifying a ciphertext block randomises the corresponding 16 plaintext bytes undetectably. SP 800-38E explicitly approves XTS only for confidentiality on storage devices.[3]

4.9 Padding and ciphertext stealing

Ciphertext stealing (CTS) lets CBC handle messages that are not a multiple of the block size without expanding them. Encrypt as CBC with the final partial block zero-padded; then transmit the last full ciphertext block and only as many bytes of the penultimate one as the partial block had: the “stolen” bytes are recomputable by the receiver. The SP 800-38A Addendum defines three variants that differ only in the ordering of the last two blocks:[48]

  • CBC-CS1: keeps natural order (the partial block is second to last);
  • CBC-CS2: swaps the last two blocks only when the final block is partial;
  • CBC-CS3: always swaps them (the variant used by Kerberos).

The message must be at least one full block long. XTS uses the same idea for partial sectors.[3] With CTR-based modes the question disappears, because the keystream is simply truncated.

5. Stream ciphers

5.1 Fundamentals and keystream generation

A stream cipher approximates the one-time pad: a short key (and a per-message nonce or IV) seeds a deterministic keystream generator whose output z1, z2, … is XORed with the plaintext. Security requires the keystream to be computationally indistinguishable from random and never reused; a stream cipher by itself gives no integrity, since flipping a ciphertext bit flips exactly the same plaintext bit.[7,8] A modern keystream generator has three parts: an initialisation phase that loads key and IV into an internal state and mixes it thoroughly, a state-update function, and an output (filter) function.[22]

5.2 Synchronous versus self-synchronising stream ciphers

Synchronous

Keystream depends only on key and IV: σi+1 = f(σi, K), zi = g(σi, K). No error propagation, but an inserted or deleted ciphertext bit desynchronises everything after it. Examples: OFB, CTR, ChaCha20, Trivium.[8]

Self-synchronising (asynchronous)

Keystream depends on the key and the previous t ciphertext bits: zi = g(K, ci−t, …, ci−1). Recovers automatically t bits after an error, at the cost of limited error propagation. Example: CFB-1 / CFB-8.[8,21]

5.3 Linear feedback shift registers

An LFSR of length L shifts its register by one position each clock and inserts a new bit equal to the XOR of selected “tap” positions. The taps are described by a connection polynomial; when that polynomial is primitive over GF(2), every non-zero seed produces a maximum-length sequence (m-sequence) of period 2L−1 with excellent statistical properties (Golomb's randomness postulates).[8,58]

LFSRs alone are cryptographically worthless: the Berlekamp–Massey algorithm recovers the shortest LFSR generating a sequence of linear complexity L from just 2L consecutive output bits.[59] Designs therefore add non-linearity: non-linear combiners of several LFSRs, non-linear filters on one LFSR's state, irregular clocking, or non-linear feedback shift registers (NFSRs), as in Grain and Trivium. Each must resist correlation and algebraic attacks.[8,22]

5.4 RC4

RC4 was designed by Ron Rivest in 1987 and kept as a trade secret until its description was leaked anonymously in 1994.[60] Its state is a permutation S of the 256 byte values plus two indices. The key-scheduling algorithm (KSA) scrambles S with the key; the generator (PRGA) repeatedly swaps two entries and outputs S[S[i] + S[j]] (code in §7). Its simplicity made it ubiquitous (WEP, WPA-TKIP, SSL/TLS), but it is badly broken:

  • The second output byte is 0 with probability about 2/256, twice the expected value.[61]
  • Fluhrer, Mantin and Shamir showed that when the IV is prepended to the key, as in WEP, the key can be recovered from enough packets.[62]
  • Many-session biases allowed practical plaintext recovery in TLS, after which RFC 7465 (2015) prohibited RC4 cipher suites in TLS.[17,60]

5.5 Salsa20 and ChaCha20

Salsa20 (Bernstein, 2005) is an ARX design (only 32-bit Addition, Rotation and XOR, which is naturally constant-time). It fills a 4×4 matrix of 32-bit words with four constants (spelling “expand 32-byte k”), the 256-bit key, a 64-bit nonce and a 64-bit block counter; applies 20 rounds (10 “double rounds” of column and row rounds); and adds the original matrix to the result to give 64 bytes of keystream. Salsa20/12 is in the eSTREAM software portfolio.[63,64]

ChaCha (2008) changes the quarter-round to diffuse faster and rearranges the matrix to vectorise better, with the same 20-round core.[65] The IETF version in RFC 8439 uses a 32-bit block counter and a 96-bit nonce, so one (key, nonce) pair can encrypt up to 232 64-byte blocks (256 GiB).[18] The state is:

a += b; d ^= a; d <<<= 16; c += d; b ^= c; b <<<= 12; a += b; d ^= a; d <<<= 8; c += d; b ^= c; b <<<= 7;

A double round applies four quarter rounds to the columns and four to the diagonals. ChaCha20 is fast on CPUs without AES instructions, which is why it is offered in TLS 1.3 and is the only cipher in WireGuard.[1,2] The extended-nonce variants XSalsa20 and XChaCha20 accept 192-bit nonces, which are safe to generate at random.[32]

6. Authenticated encryption

6.1 Authenticated encryption (AE) and AEAD

Confidentiality alone is not enough. An active attacker who can modify ciphertexts can exploit malleability or turn the receiver's reactions into a decryption oracle (padding oracles, §4.10). Authenticated encryption guarantees both privacy (IND-CPA) and integrity of ciphertexts (INT-CTXT: the adversary cannot produce any new ciphertext that decrypts successfully). Bellare and Namprempre proved that these two together imply security against chosen-ciphertext attacks (IND-CCA).[57]

AEAD (authenticated encryption with associated data), formalised by Rogaway, adds a second input, the associated data A, that is authenticated but not encrypted.[69] RFC 5116 defines the standard interface:[70]

C = AEAD-Encrypt(K, N, P, A) (C includes the tag) P | FAIL = AEAD-Decrypt(K, N, C, A)

Associated data is anything the receiver must be able to read in the clear but that must not be altered or transplanted: packet headers, protocol version and record type, sequence numbers, IP addresses, file names and metadata, a database row's primary key, or a “purpose” label that binds the ciphertext to its context. Binding context through AAD stops an attacker moving a valid ciphertext from one field, user or record to another.

ChaCha20-Poly1305 in detail

RFC 8439 §2.8 combines the two primitives as follows:[18,73]

  1. Generate the one-time Poly1305 key as the first 32 bytes of the ChaCha20 block with counter 0.
  2. Encrypt the plaintext with ChaCha20 starting at counter 1.
  3. Compute Poly1305 over AAD ‖ pad16 ‖ C ‖ pad16 ‖ len(AAD) ‖ len(C) (lengths as 64-bit little-endian integers). Poly1305 evaluates a polynomial modulo the prime 2130−5 at a clamped point r and adds s.
  4. Append the 16-byte tag.

Because the Poly1305 key is fresh for every nonce, Poly1305's one-time-MAC security holds; reusing a nonce reuses (r, s), and two tags under the same key let an attacker solve for them and forge.

6.4 Authentication tag verification

  • Verify before release. Decryption must return either the full plaintext or FAIL, never unverified plaintext.[70] Streaming interfaces that emit plaintext before checking the tag reintroduce chosen-ciphertext attacks.
  • Constant-time comparison. Compare tags with a constant-time function (e.g. hmac.compare_digest, CRYPTO_memcmp, sodium_memcmp); an early-exit memcmp leaks how many leading bytes matched, allowing byte-by-byte forgery.[46]
  • One error, no detail. Return a single, uniform failure (same message and timing) whether the tag, padding or length was wrong.[26,54]
  • Tag length. Prefer full 128-bit tags; truncated GCM tags are weaker than their length suggests.[28,56]
  • Limit failures. Protocols such as TLS tear down the connection on any authentication failure.[1]

6.5 Nonce reuse vulnerabilities and nonce strategies

For GCM and ChaCha20-Poly1305, reusing a (key, nonce) pair is a complete failure. Take GCM with two messages under the same nonce and one ciphertext block each (A = ∅):

T₁ = C₁·H² ⊕ L·H ⊕ E_K(J₀) T₂ = C₂·H² ⊕ L·H ⊕ E_K(J₀) ⇒ T₁ ⊕ T₂ = (C₁ ⊕ C₂)·H² (all arithmetic in GF(2¹²⁸))

The unknown mask EK(J0) cancels, leaving a polynomial equation in H whose roots can be found efficiently. With H the attacker can forge tags for arbitrary ciphertexts under that nonce, on top of learning P1 ⊕ P2 from the reused keystream.[29] Böck et al. found HTTPS servers on the Internet that repeated GCM nonces, and demonstrated forgeries against them.[55]

Nonce strategies.
  1. Counter: a per-key message counter (as TLS 1.3 does, XORed with a per-connection IV). Unique by construction, but state must never roll back (beware VM snapshots and multiple senders sharing a key).[1]
  2. Random 96-bit: acceptable up to 232 messages per key for GCM.[28]
  3. Random 192-bit with XChaCha20-Poly1305: collision risk negligible.[32]
  4. Misuse-resistant AES-GCM-SIV when duplicates cannot be ruled out.[31]
  5. Rekey long before any limit: derive fresh keys per session or per file.[5]

7.4 Measuring the avalanche effect of AES

import os
from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes

def aes_block(key, block):
    e = Cipher(algorithms.AES(key), modes.ECB()).encryptor()
    return e.update(block) + e.finalize()

def hamming(a, b):
    return sum(bin(x ^ y).count("1") for x, y in zip(a, b))

key, trials, total = os.urandom(16), 1000, 0
for _ in range(trials):
    p = bytearray(os.urandom(16))
    c1 = aes_block(key, bytes(p))
    bit = int.from_bytes(os.urandom(1), "big") % 128
    p[bit // 8] ^= 1 << (bit % 8)          # flip one plaintext bit
    total += hamming(c1, aes_block(key, bytes(p)))
print(f"average ciphertext bits changed: {total/trials:.2f} of 128")

7.6 Toy Feistel cipher

Shows that a non-invertible round function (a truncated hash) still gives an invertible cipher, and that decryption is the same network with reversed subkeys.

toy_feistel.py
# Toy 64-bit Feistel cipher -- for learning only, NOT secure.
import hashlib

def F(half: int, k: bytes) -> int:
    """Round function. Note: it does NOT need to be invertible."""
    h = hashlib.sha256(half.to_bytes(4, "big") + k).digest()
    return int.from_bytes(h[:4], "big")

def subkeys(key: bytes, rounds: int = 16):
    """Toy key schedule: one 64-bit subkey per round."""
    return [hashlib.sha256(key + bytes([i])).digest()[:8] for i in range(rounds)]

def feistel(block: int, keys) -> int:
    L, R = block >> 32, block & 0xFFFFFFFF
    for k in keys:
        L, R = R, L ^ F(R, k)          # L_i = R_{i-1};  R_i = L_{i-1} XOR F(R_{i-1}, K_i)
    return (R << 32) | L               # undo the last swap

encrypt = lambda b, key: feistel(b, subkeys(key))
decrypt = lambda b, key: feistel(b, subkeys(key)[::-1])   # same circuit, keys reversed

key, p = b"toy key", 0x0123456789ABCDEF
c = encrypt(p, key)
print(hex(c), "->", hex(decrypt(c, key)))
assert decrypt(c, key) == p

7.7 LFSR and its period

lfsr.py
# Fibonacci LFSR. taps are 1-based positions counted from the left (output at right).
def lfsr(state: int, taps, nbits: int, n: int):
    out = []
    for _ in range(n):
        out.append(state & 1)                       # output bit
        fb = 0
        for t in taps:
            fb ^= (state >> (nbits - t)) & 1        # XOR of tapped bits
        state = (state >> 1) | (fb << (nbits - 1))
    return out, state

def period(seed, taps, nbits):
    s, i = seed, 0
    while True:
        _, s = lfsr(s, taps, nbits, 1); i += 1
        if s == seed:
            return i

bits, _ = lfsr(0b1000, [4, 3], 4, 30)
print("".join(map(str, bits)))                      # repeats every 15 bits

# ChaCha20 quarter round (RFC 8439, sec. 2.1) with the RFC's test vector
M = 0xFFFFFFFF
rotl = lambda v, c: ((v << c) & M) | (v >> (32 - c))

def quarter_round(a, b, c, d):
    a = (a + b) & M; d ^= a; d = rotl(d, 16)
    c = (c + d) & M; b ^= c; b = rotl(b, 12)

9. Exercises

Click an exercise to reveal its solution.

9.1 Brute-forcing DES. A cluster tests 1012 DES keys per second. How long does an exhaustive search take in the worst case and on average? How long for AES-128?

256 ≈ 7.21×1016 keys ÷ 1012 /s ≈ 72 000 s ≈ 20 hours worst case, about 10 hours on average (half the key space). Using the complementation property halves it again. For AES-128: 3.4×1038 ÷ 1012 ≈ 3.4×1026 s ≈ 1.1×1019 years.

9.2 PKCS#7. A message is exactly 32 bytes long and is encrypted with AES-CBC and PKCS#7. How long is the ciphertext (excluding the IV), and why?

48 bytes. PKCS#7 always adds at least one byte, so an aligned message receives a full extra block of sixteen 0x10 bytes. Otherwise the receiver could not tell whether a final byte 0x01 was padding or data.[25]

9.3 Feistel inversion. Show that a Feistel round is invertible even if F is a constant function, and write the decryption equations.

Given Li = Ri-1 and Ri = Li-1 ⊕ F(Ri-1, Ki): Ri-1 = Li, then Li-1 = Ri ⊕ F(Li, Ki). Only forward evaluation of F is needed, so any F works (including a constant, though that would be insecure). Running the same network with subkeys Kr, …, K1 decrypts, as the toy Feistel in §7.6 shows.[37,38]

9.4 Meet-in-the-middle. Why does double DES with two independent 56-bit keys give only about 57 bits of security? What does the attack need?

For a known pair (P, C): compute and store EK1(P) for all 256 K1; then for each K2 compute DK2(C) and look it up. Matches are candidate key pairs, filtered with a second (P, C) pair. Cost: about 256 + 256 = 257 operations and 256 blocks of memory, instead of 2112. The same idea limits three-key 3DES to about 112 bits.[5,19]

9.5 MixColumns by hand. Compute MixColumns on the column (01, 01, 01, 01), then verify the first output byte for the column (db, 13, 53, 45).

Each output byte is {02}·01 ⊕ {03}·01 ⊕ 01 ⊕ 01 = 02 ⊕ 03 ⊕ 01 ⊕ 01 = 01, so the column is unchanged: (01, 01, 01, 01). For db 13 53 45: {02}·db = (1b6 → b6) ⊕ 1b = ad; {03}·13 = 26 ⊕ 13 = 35; ad ⊕ 35 ⊕ 53 ⊕ 45 = 8e. The full result is 8e 4d a1 bc.[6]

9.6 Two-time pad. The same AES-CTR key and nonce encrypted two 14-byte messages: C₁ = 7bc590a138667fc94283a1865e05 and C₂ = 68d490b23e6c0ba857f7c5944013. You know P₁ = "ATTACK AT DAWN". Find P₂.

C₁ ⊕ C₂ = 13110013060a7461157464121e16 = P₁ ⊕ P₂. XOR with the ASCII of ATTACK AT DAWN gives “RETREAT AT SIX”. The keystream cancels entirely, so the key was never needed.[21]

9.7 CBC bit flipping. A server decrypts the CBC cookie "user=bob;admin=0" (exactly one 16-byte block P₁, IV prefixed) and checks admin. Without the key, how do you become admin?

P1 = DK(C1) ⊕ IV. The character “0” is at offset 15; XOR byte 15 of the IV with '0' ⊕ '1' = 0x30 ⊕ 0x31 = 0x01. The decrypted block becomes user=bob;admin=1, with no other damage because only the IV changed. In multi-block messages, modifying Ci-1 does the same to Pi but garbles Pi-1. The fix is authenticated encryption.[7,57]

9.8 Birthday bounds. After how much data do you expect a block collision for a 64-bit block cipher? For a 128-bit one?

Around 2n/2 blocks. 64-bit: 232 blocks × 8 bytes = 32 GiB, which is practical (Sweet32 needed a few hundred GB for a high-probability attack).[42] 128-bit: 264 blocks × 16 bytes = 268 bytes ≈ 256 EiB. In practice, rekey well before either bound.

9.9 LFSR. Using the register of Figure 9 (feedback s₀ ⊕ s₁), seed (s₃ s₂ s₁ s₀) = 1000, write the first 15 output bits. What is the period, and why is it maximal? How many output bits does Berlekamp–Massey need to recover this LFSR?

Output 000100110101111, then it repeats: the period is 15 = 24−1, because x4 + x3 + 1 is primitive over GF(2), so the register cycles through all 15 non-zero states. Berlekamp–Massey needs 2L = 8 bits.[58,59]

9.10 GCM nonce reuse. Two one-block messages with no AAD were encrypted with the same key and nonce. Express T₁ ⊕ T₂ and explain how it leads to forgery.

Each tag is T = C·H2 ⊕ L·H ⊕ EK(J0) with the same length block L and mask. Then T₁ ⊕ T₂ = (C₁ ⊕ C₂)·H2, so H2 = (T₁ ⊕ T₂)·(C₁ ⊕ C₂)−1 and taking a square root (unique in GF(2128)) gives H. Then EK(J0) = T₁ ⊕ C₁·H2 ⊕ L·H, and the attacker can compute a valid tag for any ciphertext under that nonce. With longer messages the equation is a higher-degree polynomial, whose few roots are still easy to find.[29]

9.11 Choose the mode. Pick an algorithm for: (a) TLS on a phone without AES hardware; (b) full-disk encryption; (c) many servers encrypting with one key and no shared counter; (d) a sensor with only an AES core.

(a) ChaCha20-Poly1305, fast in software and constant-time.[18] (b) XTS-AES, length-preserving with per-sector tweaks, accepting no integrity.[3] (c) AES-GCM-SIV or XChaCha20-Poly1305 with random nonces.[31,32] (d) AES-CCM, which needs only the forward AES function.[30]

9.12 Encrypt-and-MAC. Show that Encrypt-and-MAC with HMAC is not IND-CPA secure even when the encryption scheme is.

HMAC is deterministic. In the IND-CPA game, query the encryption of M0 and record its tag T0 = HMAC(M0). Submit challenge (M0, M1): if the challenge tag equals T0 the bit was 0, otherwise 1. The advantage is essentially 1.[57]

9.13 Limits. How much data can one (key, nonce) pair encrypt with RFC 8439 ChaCha20? How many words of round key does AES-256 use?

ChaCha20: 232 blocks × 64 bytes = 238 bytes = 256 GiB.[18] AES-256: Nr = 14, so 4(14+1) = 60 words (15 round keys).[6]

9.14 Padding oracle (thought experiment). Why does Encrypt-then-MAC prevent Vaudenay's padding-oracle attack on CBC?

The attack submits modified ciphertexts and learns whether the padding was valid after decryption. Under Encrypt-then-MAC the receiver verifies the MAC over the ciphertext first; every modified ciphertext is rejected before decryption, so padding validity is never computed for attacker-chosen ciphertexts and no oracle exists.[26,57,72]
