1 Introduction and the running example

Quality in PowerShell rests on three complementary activities. Debugging answers “why does this behave the way it does?” by pausing execution and inspecting state. Testing answers “does it still do what we promised?” by encoding expectations as executable checks. Code quality practices, chiefly static analysis, catch whole classes of defects, style drift and security risks before the code runs at all. The tools covered here are built into PowerShell (the script debugger and the diagnostic streams) or are maintained by the PowerShell team and community: Pester, the de facto test framework, and PSScriptAnalyzer, the static code checker[1,2].

Most examples in this article work on one small module, OrderTools, so that debugging, tests and analysis all target the same code. Create the layout below and paste the module in.

Text
OrderTools/
├── src/
│   └── OrderTools.psm1
├── tests/
│   ├── OrderTools.Tests.ps1
│   └── OrderTools.Integration.Tests.ps1
├── PSScriptAnalyzerSettings.psd1
└── build.ps1
PowerShell
# src/OrderTools.psm1
Set-StrictMode -Version 3.0

function Get-OrderTotal {
    <#
    .SYNOPSIS
        Calculates the total of an order, with an optional percentage discount.
    .PARAMETER Line
        Order lines. Each object needs numeric Quantity and UnitPrice properties.
    .PARAMETER DiscountPercent
        Discount from 0 to 100 applied to the subtotal.
    .EXAMPLE
        [pscustomobject]@{ Quantity = 2; UnitPrice = 9.99 } | Get-OrderTotal -DiscountPercent 10
    #>
    [CmdletBinding()]
    [OutputType([decimal])]
    param(
        [Parameter(Mandatory, ValueFromPipeline)]
        [ValidateNotNull()]
        [psobject[]] $Line,

        [ValidateRange(0, 100)]
        [decimal] $DiscountPercent = 0
    )
    begin {
        [decimal] $subtotal = 0
    }
    process {
        foreach ($item in $Line) {
            if ($item.Quantity -lt 0) {
                throw [System.ArgumentOutOfRangeException]::new(
                    'Quantity', 'Quantity cannot be negative.')
            }
            $subtotal += [decimal] $item.Quantity * [decimal] $item.UnitPrice
            Write-Verbose ('Added {0} x {1}; subtotal is now {2}' -f
                $item.Quantity, $item.UnitPrice, $subtotal)
        }
    }
    end {
        $total = $subtotal * (1 - $DiscountPercent / 100)
        Write-Debug "Raw total before rounding: $total"
        [math]::Round($total, 2, [System.MidpointRounding]::AwayFromZero)
    }
}

function Get-ExchangeRate {
    [CmdletBinding()]
    [OutputType([decimal])]
    param(
        [Parameter(Mandatory)] [ValidatePattern('^[A-Z]{3}$')] [string] $From,
        [Parameter(Mandatory)] [ValidatePattern('^[A-Z]{3}$')] [string] $To
    )
    $uri = "https://api.example.com/latest?base=$From&symbols=$To"
    Write-Verbose "GET $uri"
    $response = Invoke-RestMethod -Uri $uri -Method Get -ErrorAction Stop
    [decimal] $response.rates.$To
}

function ConvertTo-Currency {
    [CmdletBinding()]
    [OutputType([decimal])]
    param(
        [Parameter(Mandatory)] [decimal] $Amount,
        [string] $From = 'USD',
        [Parameter(Mandatory)] [string] $To
    )
    $rate = Get-ExchangeRate -From $From -To $To
    [math]::Round($Amount * $rate, 2, [System.MidpointRounding]::AwayFromZero)
}

function Export-OrderReport {
    [CmdletBinding(SupportsShouldProcess)]
    param(
        [Parameter(Mandatory)] [psobject[]] $Order,
        [Parameter(Mandatory)] [string] $Path
    )
    $rows = foreach ($o in $Order) {
        [pscustomobject]@{
            Id    = $o.Id
            Total = Get-OrderTotal -Line $o.Lines -DiscountPercent $o.Discount
        }
    }
    if ($PSCmdlet.ShouldProcess($Path, 'Write order report')) {
        $rows | Export-Csv -Path $Path -NoTypeInformation
    }
}

Export-ModuleMember -Function Get-OrderTotal, Get-ExchangeRate,
    ConvertTo-Currency, Export-OrderReport

2 Debugging

PowerShell includes a built-in script debugger that works in the console, in Visual Studio Code with the PowerShell extension, and in other hosts. It can stop a script at a line, a command or a variable access; step through code; show and change variables; and display the call stack[4]. Because the debugger is part of the engine, the same cmdlets and commands work locally, in remote sessions, in jobs and in other runspaces.

2.1 Breakpoints

A breakpoint is a designated point where execution pauses and the debugger takes over. Set-PSBreakpoint creates three kinds[5]:

TypeTriggers when…Key parameters
Linea specific line (and optionally column) of a script file is about to run-Script, -Line, -Column
Commanda named command or function is invoked; wildcards are allowed-Command
Variablea variable is read, written, or both-Variable, -Mode Read|Write|ReadWrite (default Write)

Each breakpoint can carry an -Action script block. The action runs every time the breakpoint is hit and, by default, execution continues afterwards; the debugger stops only if the action uses the break keyword[5]. That makes actions useful both for conditional breakpoints and for “logpoints” that record values without stopping.

PowerShell
# Line breakpoint: requires a saved script file
Set-PSBreakpoint -Script .\Invoke-Report.ps1 -Line 14

# Command breakpoint: stop whenever Get-OrderTotal is called, from any script
Set-PSBreakpoint -Command Get-OrderTotal

# Variable breakpoint: stop whenever $subtotal is assigned
# (note: the variable name has no leading $)
Set-PSBreakpoint -Variable subtotal -Mode Write

# Conditional breakpoint: only break when the subtotal goes over 1,000
Set-PSBreakpoint -Variable subtotal -Mode Write -Action {
    if ($subtotal -gt 1000) { break }
}

# Logpoint: record every call without stopping
Set-PSBreakpoint -Command Invoke-RestMethod -Action {
    Write-Host "[trace] Invoke-RestMethod called at $(Get-Date -Format o)"
}

# Manage breakpoints
Get-PSBreakpoint                       # list
Disable-PSBreakpoint -Id 2             # keep, but ignore
Enable-PSBreakpoint  -Id 2
Get-PSBreakpoint | Remove-PSBreakpoint # clear all

Two more ways to enter the debugger are useful when you cannot easily set a breakpoint in advance. Pressing Ctrl+Break breaks into a running script in the console[4]. Inserting Wait-Debugger into code “stops a script in the debugger before running the next statement”, which is handy for code that runs in a job, a remote session or a scheduled context; remove those lines once you have finished debugging[6].

In Visual Studio Code, the PowerShell extension maps the same engine features to the editor: click in the gutter to set a line breakpoint, add conditions or hit counts by right-clicking it, and press F5 to start a debug session[7].

2.2 Stepping through scripts

Once stopped, you control execution one statement at a time. The step commands differ in how they treat function calls[4]:

  • Step Into (s) runs the next statement and stops, descending into any function or script it calls.
  • Step Over (v) runs the next statement, but runs called functions to completion without stopping inside them.
  • Step Out (o) finishes the current function and stops at the caller; in the main script body it runs to the end or to the next breakpoint.
  • Continue (c) runs until the script ends or the next breakpoint is hit.

Pressing Enter on an empty prompt repeats the last s, v or l command, which makes long stepping sessions quick[4].

A typical session against the running example looks like this:

Console
PS> Set-PSBreakpoint -Command Get-OrderTotal
PS> $lines = @([pscustomobject]@{ Quantity = 3; UnitPrice = '4.10' })
PS> $lines | Get-OrderTotal -DiscountPercent 5
Entering debug mode. Use h or ? for help.

Hit Command breakpoint on 'Get-OrderTotal'

At OrderTools.psm1:24 char:5
+     begin {
+     ~~~~~~~
[DBG]: PS>> s
At OrderTools.psm1:25 char:9
+         [decimal] $subtotal = 0
[DBG]: PS>> v
[DBG]: PS>> l          # show surrounding source
[DBG]: PS>> o          # finish this block and return to the caller

For quick, non-interactive tracing there is also Set-PSDebug. -Trace 1 prints each line as it runs, -Trace 2 also reports variable assignments, function calls and script calls, -Step prompts before each line (and implies trace level 1), and -Strict requires variables to be assigned before they are referenced, equivalent to Set-StrictMode -Version 1. Set-PSDebug -Off turns all of these off[8].

2.3 Variable inspection

At the [DBG] prompt you are in the scope of the paused code, so any expression you type is evaluated against live state. You can display a variable by typing its name, drill into objects, and even change values to test a hypothesis before you edit the source[4].

Console
[DBG]: PS>> $item                         # whole object
Quantity UnitPrice
-------- ---------
       3 4.10

[DBG]: PS>> $item.UnitPrice.GetType().FullName
System.String                             # aha: price arrived as text
[DBG]: PS>> $item | Format-List *          # all properties
[DBG]: PS>> Get-Variable -Scope Local      # every local variable
[DBG]: PS>> $DiscountPercent = 0           # change state, then continue
[DBG]: PS>> $PSDebugContext.InvocationInfo.ScriptLineNumber

Two caveats matter. First, debugger command letters take priority, so a variable named $s or $c cannot be shown by typing just s or c: use $s, or Write-Output $s. Second, the automatic variable $PSDebugContext is defined only while the debugger is active; it holds the breakpoints that were hit and the InvocationInfo for the current position, so you can test if ($PSDebugContext) in a profile prompt or a breakpoint action[4,9].

Set-StrictMode is the preventive counterpart to inspection. With -Version 3.0 (or Latest) PowerShell raises errors for references to uninitialized variables, references to non-existent properties, method-style function calls such as Add(1,2), and out-of-bounds array indexes. These are exactly the mistakes that otherwise surface as a mysterious $null several lines later[10]. Microsoft notes that the meaning of Latest can change between releases, so pinning an explicit version keeps behaviour predictable[10].

2.4 Call stacks

The call stack is the chain of scripts and functions that led to the current statement. Get-PSCallStack “displays the current call stack”, and inside the debugger the shortcut k does the same[4,11]. Each frame is a CallStackFrame object, so you can filter it, log it or format it just like any other output.

PowerShell
function Get-CallerName {
    # Frame 0 is this function, frame 1 is whoever called us
    (Get-PSCallStack)[1].Command
}

function Invoke-Inner { "Get-CallerName was called from: $(Get-CallerName)" }
function Invoke-Outer { Invoke-Inner }

Invoke-Outer   # -> Get-CallerName was called from: Invoke-Inner

# Log a readable stack trace when something goes wrong
try {
    Get-OrderTotal -Line ([pscustomobject]@{ Quantity = -1; UnitPrice = 1 })
}
catch {
    Write-Warning $_.Exception.Message
    Write-Warning $_.ScriptStackTrace   # stack captured where the error was thrown
}

$_.ScriptStackTrace on an ErrorRecord is often more useful than Get-PSCallStack in a catch block, because it records the stack at the moment the error was raised rather than where it was handled.

2.6 Verbose and diagnostic output

Not every problem needs an interactive debugger. PowerShell separates output into numbered streams so that diagnostic messages never pollute the data a function returns[13]:

#StreamWritten byDefault preference
1SuccessWrite-Output or implicit outputn/a
2ErrorWrite-Error$ErrorActionPreference = 'Continue'
3WarningWrite-Warning$WarningPreference = 'Continue'
4VerboseWrite-Verbose$VerbosePreference = 'SilentlyContinue'
5DebugWrite-Debug$DebugPreference = 'SilentlyContinue'
6InformationWrite-Information, Write-Host (5.0+)$InformationPreference = 'SilentlyContinue'
–ProgressWrite-Progress$ProgressPreference (no stream number; cannot be redirected)

Default preference values are as documented alongside the common parameters that override them[14]. A function decorated with [CmdletBinding()] automatically receives the common parameters -Verbose, -Debug, -ErrorAction, -WarningAction, -InformationAction and others, which override the preference variables for that one call[14].

PowerShell
$line = [pscustomobject]@{ Quantity = 2; UnitPrice = 9.99 }

Get-OrderTotal -Line $line -Verbose
# VERBOSE: Added 2 x 9.99; subtotal is now 19.98
# 19.98

Get-OrderTotal -Line $line -Debug
# DEBUG: Raw total before rounding: 19.98
# 19.98

# Capture diagnostics without mixing them into the data:
$result = Get-OrderTotal -Line $line -Verbose 4>&1
$messages = $result | Where-Object { $_ -is [System.Management.Automation.VerboseRecord] }
$value    = $result | Where-Object { $_ -isnot [System.Management.Automation.VerboseRecord] }

# Send every stream to a log file
& .\Invoke-Report.ps1 *> .\run.log

# Structured, taggable messages on the Information stream
Write-Information -MessageData 'Report started' -Tags 'Audit' -InformationAction Continue

Redirection operators such as 4>&1 (verbose into success) and *> (all streams to a file) are documented with the streams themselves[13]. In tests this is valuable: you can assert that a function emits a particular warning without the warning cluttering the test output.

Rule of thumb. Use Write-Verbose for “what am I doing” narration a user may want to switch on, Write-Debug for developer-level internal state, Write-Warning for recoverable problems, and Write-Error or throw for failures. Reserve Write-Host for deliberate host display; see §5.1.

2.7 Exercises: debugging

Exercise D1: catch the culprit

The following script prints the wrong grand total. Using only a variable breakpoint with an action, find the line that sets $grand to a string, without editing the script.

PowerShell
# buggy.ps1
$orders = @(10, 20, '30', 40)
$grand = 0
foreach ($o in $orders) {
    $grand = $o + $grand
}
"Grand total: $grand"
Show solution
PowerShell
Set-PSBreakpoint -Script .\buggy.ps1 -Variable grand -Mode Write -Action {
    Write-Host ("grand = {0} [{1}] at line {2}" -f $grand, $grand.GetType().Name,
        $PSDebugContext.InvocationInfo.ScriptLineNumber)
    if ($grand -is [string]) { break }
}
.\buggy.ps1

The action logs every assignment and breaks the first time $grand becomes a [string]. That happens on line 5 when $o is '30': because the left operand is a string, + performs concatenation ('30' + 30 gives '3030'). Fix it by casting, for example $grand += [int] $o, or by validating input types. The breakpoint uses -Script so it fires only in that file; the action runs and continues unless it calls break[5].

Exercise D2: who called me?

Write a function Write-TraceLog that writes a verbose message prefixed with the name of the function that called it and the caller’s line number, for example VERBOSE: [Get-Data:12] fetching.

Show solution
PowerShell
function Write-TraceLog {
    [CmdletBinding()]
    param([Parameter(Mandatory)] [string] $Message)
    $caller = (Get-PSCallStack)[1]
    Write-Verbose ("[{0}:{1}] {2}" -f $caller.Command, $caller.ScriptLineNumber, $Message)
}

function Get-Data {
    [CmdletBinding()] param()
    Write-TraceLog 'fetching'
}

Get-Data -Verbose

Frame [0] of Get-PSCallStack is Write-TraceLog itself and frame [1] is its caller[11]. Note that -Verbose on Get-Data flows to the nested call because the preference is inherited through scope.

Exercise D3: silence versus capture

Call Get-OrderTotal -Verbose so that (a) the numeric result is stored in $total, (b) verbose messages are written to verbose.log, and (c) nothing verbose appears on screen.

Show solution
PowerShell
$total = Get-OrderTotal -Line $line -Verbose 4> .\verbose.log

3 Testing

Automated tests are executable statements about behaviour. Martin Fowler’s test pyramid captures the economics: write many fast, low-level unit tests, fewer integration tests, and only a small number of slow, broad, end-to-end tests, because high-level tests are slower and more brittle[15]. The levels below are defined by scope, the amount of real system involved, rather than by tool. Pester can express all of them.

3.1 Unit testing

A unit test exercises one small piece of code, typically a single function, in isolation from slow or non-deterministic collaborators such as the network, the file system or the clock. Unit tests are fast enough to run on every save, and when they fail they point to a precise location. In PowerShell the “unit” is usually a function; dependencies are replaced with mocks (§3.4).

PowerShell
# tests/OrderTools.Tests.ps1  (unit level)
BeforeAll {
    Import-Module "$PSScriptRoot/../src/OrderTools.psm1" -Force
}

Describe 'Get-OrderTotal' {
    It 'multiplies quantity by unit price and sums the lines' {
        $lines = @(
            [pscustomobject]@{ Quantity = 2; UnitPrice = 10 }
            [pscustomobject]@{ Quantity = 1; UnitPrice = 5.5 }
        )
        Get-OrderTotal -Line $lines | Should -Be 25.5
    }

    It 'rejects negative quantities' {
        $bad = [pscustomobject]@{ Quantity = -1; UnitPrice = 10 }
        { Get-OrderTotal -Line $bad } |
            Should -Throw -ExceptionType ([System.ArgumentOutOfRangeException])
    }
}

Good unit tests follow the Arrange, Act, Assert shape, test one behaviour each, have names that read as specifications, and are independent of execution order.

3.2 Integration testing

An integration test checks that components work together with real collaborators: the module plus the real file system, a real CSV serializer, a test database or a local web service. They catch mismatches that unit tests with mocks cannot, such as wrong file encodings, path handling or serialization formats, at the cost of speed. Tag them so they can be run separately (§4.4)[16].

PowerShell
# tests/OrderTools.Integration.Tests.ps1
BeforeAll {
    Import-Module "$PSScriptRoot/../src/OrderTools.psm1" -Force
}

Describe 'Export-OrderReport' -Tag 'Integration' {
    It 'writes a CSV that round-trips through Import-Csv' {
        $orders = @(
            [pscustomobject]@{ Id = 'A1'; Discount = 0
                Lines = @([pscustomobject]@{ Quantity = 1; UnitPrice = 10 }) }
            [pscustomobject]@{ Id = 'B2'; Discount = 50
                Lines = @([pscustomobject]@{ Quantity = 4; UnitPrice = 2.5 }) }
        )
        $path = Join-Path $TestDrive 'report.csv'

        Export-OrderReport -Order $orders -Path $path

        $rows = Import-Csv -Path $path
        $rows | Should -HaveCount 2
        $rows[1].Id    | Should -Be 'B2'
        [decimal] $rows[1].Total | Should -Be 5
    }

    It 'honours -WhatIf and writes nothing' {
        $path = Join-Path $TestDrive 'whatif.csv'
        Export-OrderReport -Order @() -Path $path -WhatIf
        $path | Should -Not -Exist
    }
}

The second test exercises SupportsShouldProcess, which adds -WhatIf and -Confirm to the function[17]. $TestDrive provides an isolated temporary folder (§3.5)[18].

3.3 Acceptance testing

Acceptance tests verify that the system meets a user-facing requirement, treating it as a black box. For PowerShell tools that often means running the script the way an operator would (in a fresh process, with real arguments) and checking observable outcomes such as exit codes, files produced and output text. Writing them in the Given–When–Then style keeps them readable to non-developers[19].

PowerShell
# tests/Acceptance.Tests.ps1
Describe 'Feature: nightly order report' -Tag 'Acceptance' {
    BeforeAll {
        $script:scriptPath = "$PSScriptRoot/../Invoke-NightlyReport.ps1"
    }

    Context 'Given a folder with two order files' {
        BeforeAll {
            $script:inbox = New-Item -ItemType Directory -Path "$TestDrive/inbox"
            Copy-Item "$PSScriptRoot/data/*.json" $inbox
            $script:out = "$TestDrive/out.csv"
        }

        It 'When the report runs, then it exits with code 0' {
            & pwsh -NoProfile -File $scriptPath -Inbox $inbox -OutFile $out
            $LASTEXITCODE | Should -Be 0
        }

        It 'Then the report contains one row per order' {
            (Import-Csv $out) | Should -HaveCount 2
        }
    }
}

Running the script in a child pwsh process proves it works without anything that happened to be loaded in the developer’s session. Note that the second It depends on the first; this is acceptable for a scenario walk-through but is exactly what you avoid in unit tests.

3.4 Mocking

A test double is any object that stands in for a real dependency during a test. Gerard Meszaros’s vocabulary, popularised by Fowler, distinguishes dummies (passed but never used), fakes (working but simplified implementations), stubs (return canned answers), spies (stubs that also record how they were called) and mocks (pre-programmed with expectations, verified by behaviour)[20,21]. Fowler’s key distinction is between state verification (check the result) and behaviour verification (check the interactions); only mocks insist on the latter[20].

In PowerShell, functions and cmdlets are resolved by name at run time, so a test framework can intercept a command call and substitute a script block. Pester’s Mock does exactly that, and its call history lets the same mock behave as a stub (return data) or a spy/mock (assert on calls with Should -Invoke)[22]. Mock what is slow, non-deterministic, external or destructive: Invoke-RestMethod, Get-Date, Restart-Computer, Send-MailMessage. Do not mock the code under test, and avoid mocking so much that the test only verifies the mocks. Concrete Pester syntax is in §4.6.

3.5 Test fixtures

A fixture is the fixed state a test needs: input objects, files, environment variables, or a module loaded into the session. Fixtures should be created fresh, isolated from other tests and the machine, and torn down afterwards. Pester provides four setup/teardown blocks[23]:

  • BeforeAll runs once before all tests in its block and children; AfterAll runs once afterwards.
  • BeforeEach runs before every test in its block and children; AfterEach runs after every test, inside a finally, so it runs even if the test failed.
  • Nested setups run outermost to innermost, teardowns innermost to outermost.

Pester also supplies two isolated scratch areas. TestDrive is a temporary PSDrive (TestDrive:\, with the real path in $TestDrive for .NET calls). Files created in a block are removed when that block exits and the whole drive is deleted at the end of the test file[18].

PowerShell
Describe 'Import-OrderFile' {
    BeforeAll {
        # Shared, read-only fixture built once
        $script:sample = @'
[{ "Id": "A1", "Quantity": 2, "UnitPrice": 3.5 }]
'@
    }

    BeforeEach {
        # Fresh file per test so tests cannot interfere
        $script:file = Join-Path $TestDrive 'orders.json'
        Set-Content -Path $file -Value $sample -Encoding utf8
        $script:oldCulture = [cultureinfo]::CurrentCulture
    }

    AfterEach {
        # Restore global state even if a test failed
        [cultureinfo]::CurrentCulture = $oldCulture
    }

    It 'parses numbers independently of culture' {
        [cultureinfo]::CurrentCulture = 'de-DE'
        (Get-Content $file -Raw | ConvertFrom-Json).UnitPrice | Should -Be 3.5
    }
}

Pester documents that variables defined in BeforeAll can be read, but not reassigned, by child blocks, whereas BeforeEach, It and AfterEach share one scope[23]. The $script: prefix above makes the intent explicit.

3.6 Regression testing

A regression is a defect in behaviour that used to work. Regression testing re-runs existing tests after a change to confirm nothing has broken; in practice, your whole automated suite is the regression suite, and it is only as good as its coverage of real failures. The discipline that makes it effective is: every bug fix starts with a failing test that reproduces the bug. The test fails before the fix, passes after, and guards against the bug forever.

Suppose a user reports that a price of 2.345 is shown as 2.34. The .NET [math]::Round() method defaults to banker’s rounding (MidpointRounding.ToEven), so [math]::Round([decimal] 2.345, 2) gives 2.34 rather than the 2.35 most users expect[24]. That is why OrderTools passes AwayFromZero explicitly. A regression test pins the decision:

PowerShell
Describe 'Get-OrderTotal regressions' -Tag 'Regression' {
    # Issue #42: totals ending in exactly half a cent must round up
    It 'rounds midpoint values away from zero (issue #42)' {
        $line = [pscustomobject]@{ Quantity = 1; UnitPrice = 2.345 }
        Get-OrderTotal -Line $line | Should -Be 2.35
    }

    # Issue #57: string prices from CSV import must be accepted
    It 'accepts numeric strings for UnitPrice (issue #57)' {
        $line = [pscustomobject]@{ Quantity = '3'; UnitPrice = '4.10' }
        Get-OrderTotal -Line $line | Should -Be 12.30
    }
}

Linking test names to issue numbers makes the purpose of each test obvious to future maintainers, who might otherwise delete an “odd-looking” test. Run the full suite in continuous integration on every pull request so regressions are caught before merge (§6).

3.7 Exercises: testing

Exercise T1: classify the tests

Classify each test as unit, integration or acceptance: (a) Get-ExchangeRate with Invoke-RestMethod mocked; (b) Export-OrderReport writing a real file to $TestDrive; (c) running pwsh -File Invoke-NightlyReport.ps1 and checking the e-mail an operator receives in a test mailbox.

Show solution

(a) Unit: the only collaborator is replaced with a double. (b) Integration: the module is combined with the real file system and the real CSV cmdlets. 4 Pester

Pester is the ubiquitous test and mock framework for PowerShell. It is installed from the PowerShell Gallery and run with Invoke-Pester; the examples here follow the Pester 6 documentation[1].

PowerShell
Install-Module -Name Pester -Force
Import-Module Pester -PassThru
Invoke-Pester -Output Detailed ./tests

4.1 Pester architecture

Since version 5, Pester runs every test file in two distinct phases[25]:

  1. Discovery. Pester executes the Describe and Context script blocks to build a tree of blocks and tests. It bodies and setup/teardown blocks are recorded but not run. Filters (tags, names, lines) are applied to the tree at this point.
  2. Run. Pester walks the tree, invoking BeforeAll, BeforeEach, each It, AfterEach and AfterAll in order, and collects results into a result object that drives output, test-result files and code coverage.

This design produces two golden rules: put all test code inside It, BeforeAll, BeforeEach, AfterEach or AfterAll, and put nothing directly in Describe, Context or the top of the file. Code placed there runs during Discovery and its results are not available during Run. Code that must generate tests dynamically belongs in BeforeDiscovery[25]. Pester 6 performs discovery and run file by file, whereas Pester 5 discovered all files first[25].

Every aspect of a run is controlled by a configuration object from New-PesterConfiguration, grouped into sections such as Run, Filter, Output, TestResult, CodeCoverage and Should[26].

PowerShell
$config = New-PesterConfiguration
$config.Run.Path               = './tests'
$config.Run.Exit               = $true          # non-zero exit code on failure (for CI)
$config.Filter.ExcludeTag      = 'Acceptance'
$config.Output.Verbosity       = 'Detailed'
$config.TestResult.Enabled     = $true          # write a test-results XML file
Invoke-Pester -Configuration $config

4.2 Test files

Pester discovers files whose names end in .Tests.ps1, conventionally one per source file or function (Get-Planet.ps1 → Get-Planet.Tests.ps1)[1,28]. Load the code under test from a BeforeAll at the top of the file, using $PSScriptRoot so the path works from any current directory[1].

PowerShell
# Dot-source a script file that defines functions
BeforeAll {
    . $PSScriptRoot/../src/Get-Planet.ps1
}

# or: import a module freshly so edits are picked up
BeforeAll {
    Import-Module "$PSScriptRoot/../src/OrderTools.psm1" -Force
}

# or: the common "sibling file" convention, Foo.Tests.ps1 next to Foo.ps1
BeforeAll {
    . $PSCommandPath.Replace('.Tests.ps1', '.ps1')
}

4.3 Describe and Context

Describe groups tests, usually for one function or feature, and Context groups tests further, usually by scenario or state (“when the input is empty”, “when the API is down”). Both create a scope: setup blocks, mocks and TestDrive contents defined in a block apply to that block and its children[18,22,23,28]. Both accept -Tag, -Skip and -ForEach.

PowerShell
Describe 'ConvertTo-Currency' -Tag 'Unit' {
    BeforeAll {
        Mock -ModuleName OrderTools Get-ExchangeRate { 0.5 }
    }

    Context 'when the amount is positive' {
        It 'converts using the current rate' {
            ConvertTo-Currency -Amount 10 -To 'EUR' | Should -Be 5
        }
    }

    Context 'when the amount is zero' {
        It 'returns zero' {
            ConvertTo-Currency -Amount 0 -To 'EUR' | Should -Be 0
        }
    }

    # Data-driven blocks: one Context per currency
    Context 'currency <_>' -ForEach 'EUR', 'GBP', 'JPY' {
        It 'passes the target currency through' {
            ConvertTo-Currency -Amount 1 -To $_ | Out-Null
            Should -Invoke -ModuleName OrderTools Get-ExchangeRate -Times 1 -Exactly `
                -ParameterFilter { $To -eq $_ }
        }
    }
}

Watch the $_ in the filter. Inside the -ParameterFilter script block, $_ still refers to the current -ForEach item because Pester runs the filter in the test’s scope. When in doubt, use named hashtable data (-ForEach @{ Currency = 'EUR' }) and refer to $Currency.

4.4 It blocks

An It block is one test. It passes if its script block completes without throwing and fails on the first failed assertion or unhandled exception. Its name should read as a specification. Useful options include -Skip (report as skipped), -Tag, and -ForEach/-TestCases for data-driven tests, where each hashtable key becomes a variable and <name> placeholders in the test name are expanded[29]. Use single-quoted names so PowerShell does not expand the placeholders first[29].

PowerShell
Describe 'Get-OrderTotal discounts' {
    It 'applies <Discount>% to 100 to give <Expected>' -ForEach @(
        @{ Discount = 0;    Expected = 100 }
        @{ Discount = 12.5; Expected = 87.5 }
        @{ Discount = 100;  Expected = 0 }
    ) {
        $line = [pscustomobject]@{ Quantity = 1; UnitPrice = 100 }
        Get-OrderTotal -Line $line -DiscountPercent $Discount | Should -Be $Expected
    }

    It 'rejects a discount of <_>' -ForEach -1, 101 {
        $line = [pscustomobject]@{ Quantity = 1; UnitPrice = 100 }
        { Get-OrderTotal -Line $line -DiscountPercent $_ } |
            Should -Throw -ExceptionType ([System.Management.Automation.ParameterBindingException])
    }

    It 'supports Windows-only rounding mode' -Skip:(-not $IsWindows) {
        # skipped on Linux and macOS
    }
}

# Output (Detailed):
#   [+] applies 0% to 100 to give 100
#   [+] applies 12.5% to 100 to give 87.5
#   [+] applies 100% to 100 to give 0
#   [+] rejects a discount of -1
#   [+] rejects a discount of 101

Run a subset by tag with Invoke-Pester -TagFilter Unit -ExcludeTagFilter Slow or the equivalent Filter.Tag/Filter.ExcludeTag configuration[16]. Note that -ForEach data is evaluated during Discovery, so it cannot use variables created in BeforeAll; use BeforeDiscovery for computed test data[25].

4.5 Assertions

Assertions compare an actual value with an expectation and throw a descriptive error on mismatch. The classic syntax pipes the actual value into Should with an operator; any operator can be negated with -Not[30].

-BeGreaterThan, -BeLessOrEqual, …numeric or comparable ordering$ms | Should -BeLessThan 500

-BeTrue, -BeFalsetruthy / falsy(Test-Path $p) | Should -BeTrue

Two pitfalls catch many newcomers. First, -Throw needs a script block, otherwise the error is thrown before Should ever runs. Second, piping a collection into Should -Be unrolls it; use -HaveCount and per-element checks, or wrap with ,$array.

PowerShell
It 'returns a decimal rounded to two places' {
    $t = Get-OrderTotal -Line ([pscustomobject]@{ Quantity = 3; UnitPrice = 0.333 })
    $t | Should -BeOfType [decimal]
    $t | Should -Be 1.00
}

It 'exposes a mandatory Line parameter' {
    Get-Command Get-OrderTotal | Should -HaveParameter Line -Mandatory
}

It 'reports a clear message for negative quantities' {
    { Get-OrderTotal -Line ([pscustomobject]@{ Quantity = -2; UnitPrice = 1 }) } |
        Should -Throw -ExpectedMessage '*cannot be negative*'
}

It 'warns without polluting output' {
    function Test-Warn { Write-Warning 'careful'; 42 }
    $out = Test-Warn -WarningVariable w -WarningAction SilentlyContinue
    $out | Should -Be 42
    $w   | Should -HaveCount 1
}

Pester 6 adds a new family of hyphenated assertions, such as Should-Be, Should-BeNull, Should-Throw and Should-BeEquivalent for deep object comparison, which produce clearer failure messages. The classic syntax remains available and can be disabled with Should.DisableV5 = $true once a code base has migrated[3].

4.6 Mocking

Mock replaces a command with a script block for the duration of the block in which it is declared (Describe, Context or It), and records every call[22]. Should -Invoke then asserts how often, and with which parameters, the mock was called. Key parameters[22]:

  • -ParameterFilter: a script block in which the call’s parameters are variables; the mock applies only when it returns true. Several filtered mocks plus one unfiltered default can coexist.
  • -ModuleName: inject the mock into a module’s scope, so calls made from inside that module are intercepted. This is essential when testing exported functions that call other commands.
  • -Verifiable: mark a mock so Should -InvokeVerifiable fails if it was never called.
  • -RemoveParameterType / -RemoveParameterValidation: relax a mocked command’s signature when real types are hard to construct.

By default, Should -Invoke counts calls in the current It when used inside an It, and in the enclosing Describe or Context when used in AfterAll; -Scope overrides this[22].

PowerShell
BeforeAll {
    Import-Module "$PSScriptRoot/../src/OrderTools.psm1" -Force
}

Describe 'Get-ExchangeRate' {
    BeforeAll {
        # Stub: canned API response, injected into the module's scope
        Mock -ModuleName OrderTools Invoke-RestMethod {
            [pscustomobject]@{ rates = [pscustomobject]@{ EUR = 0.92 } }
        }
    }

    It 'returns the rate for the target currency' {
        Get-ExchangeRate -From USD -To EUR | Should -Be 0.92
    }

    It 'calls the API once with the right query string' {
        $null = Get-ExchangeRate -From USD -To EUR
        Should -Invoke -ModuleName OrderTools -CommandName Invoke-RestMethod `
            -Times 1 -Exactly -ParameterFilter {
                $Uri -eq 'https://api.example.com/latest?base=USD&symbols=EUR' -and
                $Method -eq 'Get'
            }
    }

    Context 'when the API is unavailable' {
        BeforeAll {
            Mock -ModuleName OrderTools Invoke-RestMethod {
                throw [System.Net.Http.HttpRequestException]::new('503 Service Unavailable')
            }
        }

        It 'surfaces the failure as a terminating error' {
            { Get-ExchangeRate -From USD -To EUR } | Should -Throw '*503*'
        }
    }
}

For private (non-exported) functions, Pester offers InModuleScope, which runs a script block inside the module’s scope so you can call internals directly. The Pester documentation recommends testing through the public interface and using -ModuleName on mocks where possible, keeping InModuleScope for cases that really need module internals[31].

PowerShell
It 'can test a private helper when unavoidable' {
    InModuleScope OrderTools {
        # Private functions and $script: variables are visible here
        Get-Command Get-OrderTotal | Should -Not -BeNullOrEmpty
    }
}

4.7 Code coverage

Code coverage measures which commands in your source were executed by the tests. Enable it in the configuration; by default Pester writes coverage.xml in JaCoCo format, which CI systems such as Azure DevOps and many GitHub Actions can display. CodeCoverage.OutputFormat can also be Cobertura, and CodeCoverage.CoveragePercentTarget sets the threshold reported in the summary[27]. The older -CodeCoverage parameter of Invoke-Pester is no longer used[27].

PowerShell
$config = New-PesterConfiguration
$config.Run.Path                           = './tests'
$config.CodeCoverage.Enabled               = $true
$config.CodeCoverage.Path                  = './src'
$config.CodeCoverage.OutputFormat          = 'JaCoCo'
$config.CodeCoverage.OutputPath            = './out/coverage.xml'
$config.CodeCoverage.CoveragePercentTarget = 85
$config.Run.PassThru                       = $true

$result = Invoke-Pester -Configuration $config

'{0:N1}% of {1} commands covered' -f $result.CodeCoverage.CoveragePercent,
    $result.CodeCoverage.CommandsAnalyzedCount

# List what the tests never executed
$result.CodeCoverage.CommandsMissed |
    Select-Object File, Line, Command | Format-Table -AutoSize

Pester 6 measures coverage with a profiler-based tracer by default, which is faster than the breakpoint-based approach; CodeCoverage.UseBreakpoints = $true restores the older behaviour. The default target is 75% and the default output file is coverage.xml[26,27].

Interpret coverage carefully. Coverage shows what was executed, not what was verified: a test with no assertions still raises coverage. Use the “missed commands” list to find untested branches, especially error-handling paths, and treat the percentage as a floor, not a goal.

5 Code Quality

Tests prove behaviour; quality tooling keeps the code base consistent, readable and safe. The cornerstone is PSScriptAnalyzer, complemented by agreed style conventions, comment-based help, and measured performance.

5.1 PSScriptAnalyzer

PSScriptAnalyzer is “a static code checker for PowerShell modules and scripts”. It checks code against a set of rules based on best practices identified by the PowerShell team and community, reports diagnostic records (errors and warnings) with suggested fixes, and can reformat code[2]. It supports Windows PowerShell 5.1 and PowerShell 7.2.11 or later, and its source is on GitHub under the MIT licence[2,32]. Diagnostics have a severity of Error, Warning or Information, and parse errors are reported as ParseError[33,34].

PowerShell
Install-Module -Name PSScriptAnalyzer -Force          # PowerShellGet 2.x
# or: Install-PSResource -Name PSScriptAnalyzer       # PSResourceGet 1.x

Invoke-ScriptAnalyzer -Path ./src -Recurse
Invoke-ScriptAnalyzer -Path ./src -Recurse -Severity Error, Warning
Invoke-ScriptAnalyzer -Path ./src/OrderTools.psm1 -IncludeRule PSAvoidUsingCmdletAliases
Get-ScriptAnalyzerRule | Select-Object RuleName, Severity | Sort-Object Severity

Given this deliberately poor function:

PowerShell
# bad.ps1
function Do-Cleanup($ComputerName, $Password) {
    $files = gci C:\Temp

    $files | % { Remove-Item $_.FullName }
    $global:LastCleanup = Get-Date

Settings files. Rather than passing switches each time, put a PSScriptAnalyzerSettings.psd1 in the project root. -Settings accepts a path, a hashtable or the name of a built-in preset, and a settings file in the root is picked up automatically when that folder is passed as -Path[34]. Built-in presets include CodeFormatting, CodeFormattingOTBS, CodeFormattingAllman, CodeFormattingStroustrup, PSGallery, ScriptSecurity, ScriptingStyle, ScriptFunctions, CmdletDesign and DSC[34].

    Rules        = @{

            Enable         = $true

Suppressing a finding. When a rule is wrong for a specific case, suppress it locally with SuppressMessageAttribute and a justification, rather than disabling it project-wide. The rule name is the category, the second argument is an empty string, and Scope/Target can widen the suppression; parse errors cannot be suppressed[34].

PowerShell
function Show-Banner {
    [Diagnostics.CodeAnalysis.SuppressMessageAttribute(
        'PSAvoidUsingWriteHost', '',
        Justification = 'Interactive banner intended only for the host.')]
    [CmdletBinding()]
    param()
    Write-Host 'OrderTools 1.0' -ForegroundColor Cyan
}

Fixing and formatting. Invoke-ScriptAnalyzer -Fix applies the suggested corrections that some rules provide (for example, expanding aliases); it supports -WhatIf, and Microsoft recommends using source control before running it[34]. Invoke-Formatter reformats a script string according to formatting settings.

PowerShell
Invoke-ScriptAnalyzer -Path ./bad.ps1 -Fix -WhatIf
$formatted = Invoke-Formatter -ScriptDefinition (Get-Content ./bad.ps1 -Raw) -Settings CodeFormattingOTBS

5.2 Style conventions

Consistent style reduces the cognitive load of reading code. The community-maintained PowerShell Practice and Style guide, which combines “The Community Book of PowerShell Practices” and “The PowerShell Style Guide”, is the most widely cited reference[35]. Its main recommendations, many of which PSScriptAnalyzer can enforce, are:

  • Verb-Noun naming with approved verbs. Use a verb from Get-Verb and a singular noun, for example Get-OrderTotal, not Calc-Orders. Get-Verb “gets approved PowerShell verbs”, and when a module exports a command with an unapproved verb, Import-Module displays a warning[36]. Rule: PSUseApprovedVerbs[33].
  • PascalCase for public identifiers (functions, parameters, properties) and lowercase for language keywords[35].
  • Full command and parameter names in scripts. Aliases and positional parameters are fine at the prompt, but in shared code write Get-ChildItem -Path, not gci. Rules: PSAvoidUsingCmdletAliases, PSAvoidUsingPositionalParameters[33].
  • Consistent brace and indentation style. The guide recommends One True Brace Style (opening brace on the same line) and four-space indentation[35]. Rules: PSPlaceOpenBrace, PSUseConsistentIndentation[33].
  • Advanced functions. Use [CmdletBinding()], typed and validated parameters, and [OutputType()]; support -WhatIf/-Confirm for anything that changes state[17,37].
  • Output objects, not text. Return rich objects and let the caller format them; avoid Format-* inside functions.
PowerShell
# Before
function getfiles($p) { gci $p | ? { $_.length -gt 1mb } | ft name, length }

# After
function Get-LargeFile {
    [CmdletBinding()]
    [OutputType([System.IO.FileInfo])]
    param(
        [Parameter(Mandatory, ValueFromPipeline)]
        [ValidateScript({ Test-Path -Path $_ -PathType Container })]
        [string] $Path,

        [ValidateRange(0, [long]::MaxValue)]
        [long] $MinimumSize = 1MB
    )
    process {
        Get-ChildItem -Path $Path -File |
            Where-Object -FilterScript { $_.Length -gt $MinimumSize }
    }
}

5.3 Static analysis

Static analysis inspects code without running it. PowerShell exposes its own parser, so analysis is not limited to PSScriptAnalyzer: you can parse any script into an abstract syntax tree (AST) and query it. PSScriptAnalyzer itself is built on the AST, and you can write custom rules as PowerShell functions that take a ScriptBlockAst or Token[] parameter and return DiagnosticRecord objects[38].

PowerShell
# Parse without executing; collect syntax errors
$tokens = $null; $errors = $null
$ast = [System.Management.Automation.Language.Parser]::ParseFile(
    (Resolve-Path ./src/OrderTools.psm1), [ref] $tokens, [ref] $errors)
$errors | Select-Object Message, @{ n = 'Line'; e = { $_.Extent.StartLineNumber } }

# Find every command invoked in the file, and how often
$ast.FindAll({ $args[0] -is [System.Management.Automation.Language.CommandAst] }, $true) |
    ForEach-Object { $_.GetCommandName() } |
    Group-Object | Sort-Object Count -Descending

# Find functions that lack [CmdletBinding()]
$ast.FindAll({ $args[0] -is [System.Management.Automation.Language.FunctionDefinitionAst] }, $true) |
    Where-Object {
        -not $_.Body.ParamBlock -or
        -not ($_.Body.ParamBlock.Attributes.TypeName.Name -contains 'CmdletBinding')
    } |
    Select-Object Name, @{ n = 'Line'; e = { $_.Extent.StartLineNumber } }

Static analysis also runs well as a test. Wrapping PSScriptAnalyzer in Pester makes analyzer findings fail the build in the same report as test failures:

PowerShell
# tests/Quality.Tests.ps1
BeforeDiscovery {
    $files = Get-ChildItem "$PSScriptRoot/../src" -Include *.ps1, *.psm1 -Recurse
}

Describe 'Static analysis: <_.Name>' -ForEach $files -Tag 'Quality' {
    It 'has no PSScriptAnalyzer findings' {
        $findings = Invoke-ScriptAnalyzer -Path $_.FullName `
            -Settings "$PSScriptRoot/../PSScriptAnalyzerSettings.psd1"
        $findings | Should -BeNullOrEmpty -Because (
            ($findings | ForEach-Object { "$($_.RuleName) line $($_.Line)" }) -join '; ')
    }
}

BeforeDiscovery is used because the file list generates the tests[25].

The built-in rules cannot find every injection path. InjectionHunter, published to the PowerShell Gallery by Microsoft, adds custom PSScriptAnalyzer rules “to detect coding practices that can pose injection attack risks”, such as Measure-InvokeExpression and Measure-CommandInjection[40]. Load custom rule modules like this with the custom rule path parameter of Invoke-ScriptAnalyzer (-CustomRulePath, which the documentation also spells CustomizedRulePath)[38].

Static analysis is a pre-deployment control; at run time, defenders rely on logging. On Windows, script block logging records the content of the script blocks PowerShell processes, whether interactive or automated, as event ID 4104. It can be enabled through Group Policy, the registry or powershell.config.json, and Microsoft recommends Protected Event Logging for anything beyond diagnostics[41].

5.5 Documentation

PowerShell has a first-class documentation model: comment-based help placed in a function or script is parsed by Get-Help. The supported keywords include .SYNOPSIS, .DESCRIPTION, .PARAMETER, .EXAMPLE, .INPUTS, .OUTPUTS, .NOTES and .LINK; they are not case-sensitive and can appear in any order[42]. PSScriptAnalyzer’s ProvideCommentHelp rule (Information severity) flags exported functions without help[33].

PowerShell
function Get-OrderTotal {
    <#
    .SYNOPSIS
        Calculates the total of an order.

    .DESCRIPTION
        Sums Quantity x UnitPrice across all order lines, applies an optional
        percentage discount and rounds to two decimal places using
        midpoint-away-from-zero rounding.

    .PARAMETER Line
        One or more order line objects with numeric Quantity and UnitPrice.

    .PARAMETER DiscountPercent
        Discount between 0 and 100. Defaults to 0.

    .INPUTS
        System.Management.Automation.PSObject[]

    .OUTPUTS
        System.Decimal

    .EXAMPLE
        PS> [pscustomobject]@{ Quantity = 2; UnitPrice = 9.99 } | Get-OrderTotal
        19.98

    .EXAMPLE
        PS> Import-Csv .\lines.csv | Get-OrderTotal -DiscountPercent 10

    .NOTES
        Uses [decimal] arithmetic to avoid binary floating-point error.

    .LINK
        ConvertTo-Currency
    #>
    [CmdletBinding()]
    param( <# ... #> )
}

Help is testable. The following Pester test fails if any exported command lacks a synopsis, examples or parameter descriptions, turning documentation into an enforced quality gate:

PowerShell
BeforeDiscovery {
    Import-Module "$PSScriptRoot/../src/OrderTools.psm1" -Force
    $commands = Get-Command -Module OrderTools
}

Describe 'Help for <_.Name>' -ForEach $commands -Tag 'Quality' {
    BeforeAll {
        $script:help = Get-Help $_.Name -Full
    }
    It 'has a synopsis' {
        $help.Synopsis | Should -Not -BeLike "*$($_.Name)*"   # auto-generated synopsis = missing
    }
    It 'has at least one example' {
        $help.Examples.Example | Should -Not -BeNullOrEmpty
    }
    It 'describes parameter <Name>' -ForEach @(
        $_.Parameters.Values | Where-Object Name -notin
            [System.Management.Automation.PSCmdlet]::CommonParameters |
            ForEach-Object { @{ Name = $_.Name; Command = $_ } }
    ) {
        ($help.Parameters.Parameter | Where-Object Name -eq $Name).Description |
            Should -Not -BeNullOrEmpty
    }
}

For modules published externally, platyPS generates Markdown help from comment-based help and compiles it to the MAML external-help format used by Update-Help[43]. Beyond help, maintain a README.md with installation and quick-start, and a CHANGELOG.md.

5.6 Performance testing

Performance work starts with measurement. Measure-Command “measures the time it takes to run scriptblocks and cmdlets” and returns a TimeSpan; it runs the script block in the current scope and discards its output[44]. A single measurement is noisy (JIT compilation, caching, other processes), so repeat it and compare medians.

PowerShell
function Measure-Benchmark {
    [CmdletBinding()]
    param(
        [Parameter(Mandatory)] [hashtable] $Case,     # name -> scriptblock
        [int] $Iterations = 10
    )
    foreach ($name in $Case.Keys) {
        & $Case[$name] | Out-Null                    # warm-up run
        $times = 1..$Iterations | ForEach-Object {
            (Measure-Command -Expression $Case[$name]).TotalMilliseconds
        }
        $sorted = $times | Sort-Object
        [pscustomobject]@{
            Case     = $name
            MedianMs = [math]::Round($sorted[[int]($sorted.Count / 2)], 2)
            MinMs    = [math]::Round($sorted[0], 2)
        }
    }
}

$n = 20000
Measure-Benchmark -Case @{
    'Array +='    = { $a = @(); foreach ($i in 1..$n) { $a += $i } }
    'List[T].Add' = { $l = [System.Collections.Generic.List[int]]::new()
                      foreach ($i in 1..$n) { $l.Add($i) } }
    'Assignment'  = { $a = foreach ($i in 1..$n) { $i } }
} | Sort-Object MedianMs

Microsoft’s performance guidance lists the patterns that matter most in scripts[45]:

  • Array addition. $array += $item copies the whole array each time. Prefer List[T] or let PowerShell collect loop output by assignment. (PowerShell 7.5 optimised array addition, but the advice still applies for compatibility.)
  • String building. Repeated += on strings is slow for large outputs; use -join or [System.Text.StringBuilder].
  • Suppressing output. Assigning to $null or casting to [void] is fastest; piping to Out-Null is slower in tight loops, especially in Windows PowerShell 5.1.
  • Large files. Get-Content | Where-Object is much slower than [System.IO.File]::ReadLines() or a StreamReader.
  • Lookups. Build a hashtable keyed on the join property once instead of filtering a collection inside a loop.
  • Pipelines. Avoid wrapping a cmdlet pipeline inside another pipeline per item, and avoid calling a small function in a very tight loop; move the loop into the function.
  • Object creation. Use [pscustomobject]@{} rather than New-Object plus Add-Member.

Performance expectations can be captured as tests too. Keep thresholds generous (a 2–5× margin over a typical run) and tag them so slow or shared CI agents can skip them; the goal is to catch order-of-magnitude regressions such as an accidental O(n²) loop, not to benchmark precisely.

PowerShell
Describe 'Get-OrderTotal performance' -Tag 'Performance' {
    BeforeAll {
        $script:lines = foreach ($i in 1..50000) {
            [pscustomobject]@{ Quantity = 1; UnitPrice = 1 }
        }
        Get-OrderTotal -Line $lines[0..10] | Out-Null    # warm-up
    }

    It 'totals 50,000 lines in under 2 seconds' {
        $elapsed = Measure-Command { Get-OrderTotal -Line $lines }
        $elapsed.TotalSeconds | Should -BeLessThan 2
    }

    It 'scales roughly linearly' {
        $small = (Measure-Command { Get-OrderTotal -Line $lines[0..4999] }).TotalMilliseconds
        $large = (Measure-Command { Get-OrderTotal -Line $lines }).TotalMilliseconds
        # 10x the data should take well under 30x the time
        ($large / [math]::Max($small, 1)) | Should -BeLessThan 30
    }
}

Exercise Q1: clean up Do-Cleanup

Rewrite bad.ps1 from §5.1 so that PSScriptAnalyzer reports no findings with default rules, keeping the behaviour (delete files in a folder on a remote computer).

Show solution
PowerShell
function Remove-TempFile {
    <#
    .SYNOPSIS
        Removes files from a folder on a remote computer.
    .PARAMETER ComputerName
        Target computer.
    .PARAMETER Credential
        Credential for the remote session.
    .PARAMETER Path
        Folder to clean on the remote computer.
    .EXAMPLE
        Remove-TempFile -ComputerName srv01 -Credential (Get-Credential) -WhatIf
    #>
    [CmdletBinding(SupportsShouldProcess, ConfirmImpact = 'High')]
    param(
        [Parameter(Mandatory)] [string] $ComputerName,
        [Parameter(Mandatory)]
        [System.Management.Automation.PSCredential]
        [System.Management.Automation.Credential()]
        $Credential,
        [string] $Path = 'C:\Temp'
    )
    if ($PSCmdlet.ShouldProcess("${ComputerName}:$Path", 'Remove all files')) {
        $removed = Invoke-Command -ComputerName $ComputerName -Credential $Credential -ScriptBlock {
            param($Folder)
            $files = Get-ChildItem -Path $Folder -File
            $files | Remove-Item -Force
            $files.Count
        } -ArgumentList $Path
        Write-Verbose "Removed $removed file(s) from $ComputerName"
        $script:LastCleanup = Get-Date
    }
}

Changes: approved verb Remove with a singular noun[36]; [PSCredential] instead of a plain password[33]; SupportsShouldProcess for a destructive action[37]; full cmdlet names; Write-Verbose instead of Write-Host; a script-scoped instead of global variable; and a script block passed to Invoke-Command with -ArgumentList instead of Invoke-Expression on a built string[39].

Exercise Q3: measure, then optimise

This function joins 10,000 customers to 50,000 orders and is slow. Measure it, rewrite it, and show the speed-up.

PowerShell
function Join-OrderSlow($Customers, $Orders) {
    $result = @()
    foreach ($o in $Orders) {
        $c = $Customers | Where-Object Id -eq $o.CustomerId
        $result += [pscustomobject]@{ Order = $o.Id; Customer = $c.Name }
    }
    $result
}
Show solution
PowerShell
function Join-OrderFast {
    param($Customers, $Orders)
    $byId = @{}
    foreach ($c in $Customers) { $byId[$c.Id] = $c }   # O(n) index, built once
    foreach ($o in $Orders) {                          # output collected by caller
        [pscustomobject]@{ Order = $o.Id; Customer = $byId[$o.CustomerId].Name }
    }
}

$customers = 1..10000 | ForEach-Object { [pscustomobject]@{ Id = $_; Name = "C$_" } }
$orders    = 1..50000 | ForEach-Object { [pscustomobject]@{ Id = $_; CustomerId = Get-Random -Max 10000 } }

(Measure-Command { Join-OrderFast $customers $orders }).TotalSeconds
# Join-OrderSlow on the same data typically runs for many minutes; try it with 2,000 orders first.

The slow version is O(n×m): it pipes all customers through Where-Object for every order, and it grows an array with +=. The fast version uses a hashtable lookup and lets PowerShell collect loop output, both recommended by Microsoft’s performance guidance[45]. Measure with Measure-Command[44] and confirm both functions return the same rows with a Pester test before you swap them.

6 Putting it together: a quality pipeline

The practices above pay off most when they run automatically on every change. A single build.ps1 can run analysis, unit tests with coverage, and integration tests, producing machine-readable reports for a CI server.

PowerShell
# build.ps1
[CmdletBinding()]
param([ValidateSet('Fast', 'Full')] [string] $Mode = 'Fast')

$ErrorActionPreference = 'Stop'
New-Item -ItemType Directory -Path ./out -Force | Out-Null

# 1. Static analysis
$findings = Invoke-ScriptAnalyzer -Path ./src -Recurse -Settings ./PSScriptAnalyzerSettings.psd1
$findings | Format-Table RuleName, Severity, ScriptName, Line -AutoSize
if ($findings | Where-Object Severity -in 'Error', 'Warning') {
    throw "PSScriptAnalyzer reported $(@($findings).Count) finding(s)."
}

# 2. Tests
$config = New-PesterConfiguration
$config.Run.Path                           = './tests'
$config.Run.Exit                           = $true
$config.Output.Verbosity                   = 'Normal'
$config.TestResult.Enabled                 = $true
$config.TestResult.OutputPath              = './out/testResults.xml'
$config.CodeCoverage.Enabled               = $true
$config.CodeCoverage.Path                  = './src'
$config.CodeCoverage.OutputPath            = './out/coverage.xml'
$config.CodeCoverage.CoveragePercentTarget = 80
$config.Filter.ExcludeTag = if ($Mode -eq 'Fast') { 'Integration', 'Acceptance', 'Performance' }
                            else                  { 'Performance' }

YAML
# .github/workflows/ci.yml
name: ci
on: [push, pull_request]
jobs:
  test:
    strategy:
      matrix:
        os: [ubuntu-latest, windows-latest, macos-latest]
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - name: Install modules
        shell: pwsh
        run: |
          Set-PSRepository PSGallery -InstallationPolicy Trusted
          Install-Module Pester, PSScriptAnalyzer -Scope CurrentUser
      - name: Build and test
        shell: pwsh
        run: ./build.ps1 -Mode Full

The checklist that results is short. Run the analyzer with a committed settings file; write a failing test before every bug fix; keep unit tests fast and mocked, integration tests tagged and isolated in TestDrive; watch missed-command coverage rather than chasing a percentage; document every exported command and test that the help exists; and measure before you optimise. When something still goes wrong, the debugger and the diagnostic streams turn “it doesn’t work” into a specific line, variable and call stack.
