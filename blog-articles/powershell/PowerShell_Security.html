A technical field guide for Windows administrators, security engineers, SOC analysts, and incident responders. This article combines platform security fundamentals, authenticated automation, access-control design, defensive telemetry, and safe analysis of suspicious PowerShell. All examples are for systems you own or are explicitly authorized to administer. Sources are numbered in the Vancouver citation style and linked at the end.

Operating assumptions. Examples labeled Windows require Windows. Windows PowerShell 5.1 (powershell.exe) and modern PowerShell 7 (pwsh.exe) can coexist and have different configuration and event providers. Unless specifically identified otherwise, language examples work in current PowerShell 7 and frequently also in Windows PowerShell 5.1; security features may depend on OS version, policy, installed modules, and privileges. Verify requirements in a test environment before deployment. 1, 2, 3

1. Security model: what PowerShell actually protects

PowerShell is simultaneously a shell, scripting language, .NET host, management interface, and remoting client/server. It inherits authority from the process access token, the authenticated identity, the target service's authorization rules, and the execution environment's controls. A successful command is not automatically an authorized or trustworthy command. 4, 5, 3

A useful model is a series of independent gates:

  1. Identity: who is running the command (Windows logon, service principal, managed identity, etc.)?
  2. Authorization: what may that identity do to this resource, in this context?
  3. Code trust: where did the script originate, has it been altered, and is execution approved by application control?
  4. Execution restriction: what language constructs, commands, and remoting endpoints are exposed?
  5. Detection and response: what evidence is retained, forwarded, correlated, and acted upon?

These gates are complementary rather than interchangeable. For example, a valid Authenticode signature establishes file integrity and signer association under an applicable trust chain; it does not establish that the logic is safe. A restrictive execution policy can discourage accidental script execution but is explicitly not a security boundary. By contrast, properly deployed operating-system application control is designed to enforce code trust at the OS level. 6, 7, 8, 3

Control Primary benefit Important limitation
Execution policy Avoids some accidental execution of untrusted scripts Not a security boundary; does not stop interactive commands
Authenticode signatures Verify file integrity and signer identity Signed code may still be malicious or overprivileged
ACLs, RBAC, JEA Limit actions available to a principal Roles and endpoints must be reviewed for overbroad permissions
Constrained Language Mode (CLM) Reduces language features available to untrusted code Manually setting CLM is not equivalent to enforced application control
App Control for Business Enforces an organization-defined code policy Effectiveness depends on policy design, deployment, and script enforcement settings
AMSI and EDR Scan activity and detect suspicious behavior Coverage and detection depend on enabled products, policy, and telemetry
Script/block/module logging, WEF Preserve evidence and centralize investigation Logs can expose secrets and can be incomplete without correct configuration

The security engineering principle is least privilege plus layered controls: minimize standing admin rights; use scoped, short-lived identities and narrowly constrained endpoints; sign or approve code appropriately; monitor important actions; and test the ability to detect abuse. This aligns with NIST zero-trust guidance. 4, 9, 10, 11

1.1 Discover the running environment

powershell
# Read-only inventory: safe on an ordinary workstation.
$PSVersionTable | Format-List PSVersion, PSEdition, OS, Platform
$PSHOME
$ExecutionContext.SessionState.LanguageMode
Get-ExecutionPolicy -List

# On Windows, inspect group membership and token attributes.
whoami /user
whoami /groups
whoami /priv

# Find both editions if installed.
Get-Command powershell, pwsh -ErrorAction SilentlyContinue |
    Select-Object Name, Source

Get-ExecutionPolicy describes PowerShell's script execution policy; it does not enumerate machine-wide allowlisting. LanguageMode describes the current session's language restrictions; a single observation does not prove that an enterprise control is correctly enforced. whoami /priv reports privileges associated with the logon token, not necessarily that every privilege is enabled. 6, 12, 8

2. PowerShell security fundamentals

2.1 Execution policies and their precedence

On Windows, common execution policies include Restricted (no script files), RemoteSigned (locally created scripts may run; internet-origin scripts generally require a trusted signature), AllSigned (signature required for scripts, including local ones), Unrestricted (warns in some internet-origin cases), and Bypass (no execution-policy warning/block). The effective policy is resolved through scoped precedence: MachinePolicy → UserPolicy → Process → CurrentUser → LocalMachine. Group Policy values outrank local settings. On non-Windows platforms, execution-policy enforcement is not implemented. 6

powershell
# Windows: inspect first. This makes no configuration changes.
Get-ExecutionPolicy -List
Get-ExecutionPolicy

# For a personally administered Windows workstation, set a user-level
# policy only after reviewing organizational policy requirements.
Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser

# A process-scoped choice is temporary; it is not an isolation boundary.
# Do not interpret any execution policy as malware prevention.

Security boundary distinction: a user able to execute commands can still supply equivalent operations interactively or through other allowed execution paths. Do not use AllSigned or RemoteSigned as a substitute for App Control, endpoint protection, and privilege restrictions. Also inspect the Mark of the Web before unblocking a downloaded script; unblocking removes an origin marker but does not make the file trustworthy. 6, 8

powershell
# Windows: examine rather than immediately unblock.
Get-Item -Path '.\utility.ps1' -Stream * -ErrorAction SilentlyContinue
Get-AuthenticodeSignature -FilePath '.\utility.ps1' |
    Select-Object Status, StatusMessage, SignerCertificate
Get-FileHash -Path '.\utility.ps1' -Algorithm SHA256

2.2 Code signing, certificates, and trusted publishers

Authenticode signing binds the file's content to a digital signature and an X.509 code-signing certificate. A useful enterprise model requires a validated certificate chain, appropriate code-signing usage, protected private keys, change review, and revocation/expiration procedures. A publisher that was trusted yesterday can still distribute buggy or compromised code tomorrow. 7, 13

powershell
# Windows; run in a LAB with a suitable code-signing certificate.
# Do not select an arbitrary production signing identity.
$cert = Get-ChildItem Cert:\CurrentUser\My -CodeSigningCert |
    Where-Object { $_.HasPrivateKey } |
    Select-Object -First 1

if (-not $cert) {
    throw 'No usable code-signing certificate in CurrentUser\My.'
}

# The script should already exist and have passed review.
Set-AuthenticodeSignature -FilePath '.\ReviewedUtility.ps1' `
    -Certificate $cert -HashAlgorithm SHA256

$signature = Get-AuthenticodeSignature '.\ReviewedUtility.ps1'
$signature | Select-Object Status, StatusMessage,
    @{n='Publisher';e={$_.SignerCertificate.Subject}}

if ($signature.Status -ne 'Valid') {
    throw "Signature validation failed: $($signature.Status)"
}

An AllSigned trust prompt for an unfamiliar publisher should trigger independent provenance verification, not reflexively selecting “always run.” Root trust and publisher trust are separate concerns. Protect keys in hardware-backed or otherwise tightly controlled stores where possible; timestamping supports long-term signature validation according to certificate and timestamp rules. 7, 13

2.3 Security boundaries and least privilege

PowerShell can administer services, the registry, directories, processes, certificates, and cloud resources to the extent that the executing identity has permission. Running the shell elevated increases the blast radius of mistakes and compromise. Apply separation between daily user accounts and administrative accounts, and choose dedicated service identities with rights restricted to the required resource. 4, 10, 11

powershell
# Windows: check whether this token belongs to the Administrators group.
$identity = [Security.Principal.WindowsIdentity]::GetCurrent()
$principal = [Security.Principal.WindowsPrincipal]::new($identity)
$isAdmin = $principal.IsInRole(
    [Security.Principal.WindowsBuiltInRole]::Administrator
)
[pscustomobject]@{
    Identity = $identity.Name
    AdministratorsGroupEnabled = $isAdmin
}

Being an administrator does not make all actions automatically legitimate. Ask: Can this task run without elevation? Can the script run against one machine, service, API permission, or JEA endpoint rather than the entire environment? Can the operator receive temporary rather than permanent access? 4, 10, 11

3. Authentication and authorization

Authentication establishes an identity. Authorization decides which operations the identity may perform. PowerShell is often the client of the underlying authentication system rather than the system that issues authentication tokens. Be especially careful to distinguish a Windows process token, a Kerberos service ticket, an OAuth access token, a Microsoft Entra role, and a permission granted to an API application: they are not interchangeable. 5, 14, 9, 15

3.1 Windows authentication: Kerberos and NTLM

In an Active Directory domain, Windows integrated authentication commonly negotiates Kerberos when conditions permit; NTLM can be used in other configurations or fallback scenarios. Kerberos uses a Key Distribution Center and tickets; NTLM is a challenge-response family that organizations often audit and reduce because of its security and compatibility trade-offs. WinRM remoting commonly uses Kerberos or NTLM under its negotiated security context. 5, 16, 17

powershell
# Windows: inspect local tickets; this does not extract ticket secrets.
klist

# Windows: ask how the current session identifies itself.
whoami /user

# Domain controllers: read existing Security events if permitted.
# Requires audit policies and read privileges.
Get-WinEvent -FilterHashtable @{
    LogName   = 'Security'
    Id        = 4768, 4769, 4771, 4776
    StartTime = (Get-Date).AddHours(-4)
} -MaxEvents 50 |
    Select-Object TimeCreated, Id, ProviderName, MachineName

On appropriately audited domain controllers, 4768 relates to Kerberos ticket-granting ticket requests, 4769 to service-ticket requests, 4771 to Kerberos preauthentication failures, and 4776 to NTLM credential validation. Interpret events using their full fields and the correct host role; not every authentication produces every event and an individual failure does not prove an attack. 16, 17

3.2 Remoting authentication and delegation

PowerShell remoting on Windows commonly uses WinRM/WS-Management; modern PowerShell can also use SSH-based remoting. WinRM encrypts remoting messages after authentication even when the listener uses HTTP, but HTTPS still provides TLS server authentication and transport protections and is important when required by the environment. Avoid broad TrustedHosts entries and credential delegation by default; Kerberos generally provides stronger mutual-authentication properties in suitable domain configurations. 5, 18

powershell
# Windows, authorized target only; test identity and transport.
Test-WSMan -ComputerName 'adminhost.example.test'

# Kerberos-authenticated domain remoting when correctly configured.
# No embedded passwords or broad TrustedHosts changes.
Invoke-Command -ComputerName 'adminhost.example.test' `
    -Authentication Kerberos `
    -ScriptBlock { Get-Service -Name WinRM |
        Select-Object Name, Status }

This command requires an already configured remoting endpoint, network access, an authorized principal, and usable Kerberos configuration. Authentication succeeds before the remote endpoint applies its authorization and session constraints. Avoid enabling unrestricted remote management to solve connectivity problems. 5, 10, 18

3.3 OAuth 2.0 and Microsoft Entra ID

OAuth 2.0 primarily defines a framework for delegated authorization: the client obtains an access token with the applicable scope or permissions for an API. Do not confuse OAuth with a standalone identity proof; authentication is commonly provided in conjunction with OpenID Connect or platform sign-in. For Microsoft Graph PowerShell, distinguish delegated access (user context plus granted permissions) from application access (app identity, frequently unattended). Modern OAuth deployment should follow current security best practices for token handling and client authentication. 15, 19, 14, 9

powershell
# Requires Microsoft.Graph.Authentication and a permitted Entra tenant.
# Delegated, interactive, least-privileged scope for reading YOUR profile.
Import-Module Microsoft.Graph.Authentication
Connect-MgGraph -Scopes 'User.Read' -NoWelcome
Get-MgContext | Select-Object TenantId, ClientId, AuthType, Scopes
Disconnect-MgGraph

# Unattended app-only PATTERN: prior app registration, administrator
# consent, and approved code-signing/client-auth certificate required.
# Replace placeholders in an authorized test tenant.
# Connect-MgGraph -TenantId '<tenant-guid>' -ClientId '<app-guid>' `
#     -CertificateThumbprint '<approved-certificate-thumbprint>'

Get-MgContext is useful for auditing what kind of Graph authentication was established; it is not proof that a specific API operation will be permitted. When appropriate, managed identities avoid distributing long-lived application secrets. Restrict token access, scope grants to the minimal permissions, handle consent deliberately, and revoke access when no longer needed. Do not print or persist bearer tokens in telemetry. 14, 9, 19

3.4 RBAC: Windows, JEA, Entra roles, and Graph permissions

RBAC expresses principal → role → permitted actions within scope. Examples include Windows group membership, a JEA role capability, Microsoft Entra directory roles, Azure resource RBAC, and Microsoft Graph application/delegated permissions. These systems have different enforcement points: an Entra directory role is not automatically an Azure resource role, and Graph access depends on the app's permission model and endpoint semantics. 9, 20, 10

Authorization layer Example question Correct check
Windows token / ACL Can this account modify a protected service? Process token, group membership, resource ACL
JEA endpoint Can this operator restart this approved service? Session configuration, role capability, command constraints
Microsoft Entra directory Can a principal administer directory objects? Assigned role, scope, eligible/active state
Azure resource RBAC Can this principal manage a particular VM? Role assignment at resource/subscription scope
Microsoft Graph Can this caller read this API resource? Delegated/application permissions plus resource-specific checks

Design exercise: if an inventory job needs only to read directory users, it should not request broad directory-write permissions or an organization-wide admin role. Prefer a scoped read-only permission and audit the granted consent. 9, 20

4. Security features and secure credential handling

4.1 SecureString and PSCredential: representation is not a vault

System.Security.SecureString attempts to reduce some accidental plaintext exposure but is not a complete defense against memory inspection or process compromise. On non-Windows systems, its internal storage is not encrypted. Modern .NET guidance prefers an opaque handle to credentials held outside the process where possible. PSCredential is a convenient username-plus-SecureString container for APIs that require explicit credentials; neither type grants additional permissions. 21, 22

powershell
# Interactive input: never hard-code a production password.
$credential = Get-Credential -Message 'Enter credentials for the test system'

# Pass directly to an API that supports a PSCredential parameter.
# Example pattern; the target must permit this authentication method.
# $result = Invoke-Command -ComputerName 'testhost.example.test' `
#     -Credential $credential -ScriptBlock { Get-Date }

# Avoid displaying: $credential.GetNetworkCredential().Password
# Avoid: ConvertTo-SecureString 'literal-password' -AsPlainText -Force

PowerShell's CLIXML format has an important platform-specific distinction. On Windows, exporting a PSCredential with Export-Clixml uses Windows DPAPI and is generally readable only by the exporting Windows user on that computer; it is not a portable secret repository. On non-Windows systems, do not assume exported credential objects are protected the same way. Do not commit credential exports to repositories. 23

powershell
# Windows-only, controlled lab: store for the same user/machine.
$credential = Get-Credential
$path = Join-Path $env:USERPROFILE 'credential-lab.xml'
$credential | Export-Clixml -Path $path

# Same Windows user on the same machine:
$restored = Import-Clixml -Path $path
$restored.UserName

# Remove after testing; a real application should favor an approved vault.
Remove-Item $path

4.2 SecretManagement and SecretStore

Microsoft.PowerShell.SecretManagement defines a common abstraction for interacting with registered vaults; Microsoft.PowerShell.SecretStore is a local vault implementation. A vault does not remove the need to control who can run the process, how the vault is unlocked, where the keys reside, and which identities have access. For unattended jobs, an enterprise cloud vault, managed identity, or protected service-account secret often offers a more appropriate operational trust model than an interactive password-protected local store. 24, 25, 26

powershell
# Lab setup, with modules from an organizationally approved source.
# PowerShellGet or PSResourceGet may be available, depending on system.
Install-Module Microsoft.PowerShell.SecretManagement -Scope CurrentUser
Install-Module Microsoft.PowerShell.SecretStore -Scope CurrentUser

Import-Module Microsoft.PowerShell.SecretManagement
Import-Module Microsoft.PowerShell.SecretStore

Register-SecretVault -Name LocalLabVault `
    -ModuleName Microsoft.PowerShell.SecretStore -DefaultVault

# First use may prompt to configure the vault password.
# Read-Host avoids putting the test value into source-code history.
$testSecret = Read-Host 'Enter a NON-PRODUCTION test secret' -AsSecureString
Set-Secret -Name LabApiKey -Secret $testSecret -Vault LocalLabVault

# Inspect metadata rather than printing any secret.
Get-SecretInfo -Vault LocalLabVault
$retrieved = Get-Secret -Name LabApiKey -Vault LocalLabVault
$retrieved.GetType().FullName

# Lab cleanup: remove only the test secret created above.
Remove-Secret -Name LabApiKey -Vault LocalLabVault

Get-Secret -AsPlainText returns plaintext and should be avoided unless a documented API specifically requires it and no better interface is available. A locked SecretStore session can be opened with Unlock-SecretStore under the vault's configured authentication rules; automation must handle unlocking without embedding passwords in scripts or logs. Review extension-vault trust and module supply-chain provenance. 25, 26

4.3 Constrained Language Mode (CLM)

PowerShell language modes include FullLanguage, ConstrainedLanguage, RestrictedLanguage, and NoLanguage. CLM limits access to arbitrary .NET types and other language capabilities commonly abused in untrusted code, while preserving substantial administrative utility. Properly enforced system lockdown occurs through compatible Windows application-control policy; merely assigning a new value to $ExecutionContext.SessionState.LanguageMode in a user-controlled session is not an enterprise security boundary. JEA typically offers an even narrower command-focused experience. 12, 8, 3

powershell
# Read-only: inspect the current language mode.
$ExecutionContext.SessionState.LanguageMode

# You can test script compatibility separately, but do not use a local
# language-mode assignment as proof of centrally enforced lockdown.
# Verify the machine's application-control state and policy rollout.

Operational implication: test legitimate scripts under your real enforced policy; complex reflection, unmanaged calls, and arbitrary type construction may fail. Avoid “fixes” that globally turn off application control. Scope exceptions to signed, reviewed code and the actual business need. 12, 8

4.4 Just Enough Administration (JEA)

JEA is a Windows PowerShell remoting model for assigning narrowly defined administrative capabilities through role capability files (.psrc) and session configuration files (.pssc). A user may be allowed to invoke Get-Service while being denied broad shell commands. JEA can use virtual accounts and logs/transcripts for accountability, but its security depends on controlling endpoint files, exposed commands, parameters, and any executable escape paths. 10, 27, 11

powershell
# Windows lab: define a small READ-ONLY role. Creates local files only.
# This is a starting template, NOT a production-ready deployment.
New-Item -ItemType Directory -Force -Path 'C:\JEA-Lab' | Out-Null

New-PSRoleCapabilityFile -Path 'C:\JEA-Lab\ServiceReader.psrc' `
    -VisibleCmdlets 'Get-Service'

New-PSSessionConfigurationFile -Path 'C:\JEA-Lab\ServiceAudit.pssc' `
    -SessionType RestrictedRemoteServer `
    -RunAsVirtualAccount `
    -RoleDefinitions @{
        'CONTOSO\JEA_Service_Readers' = @{
            RoleCapabilities = 'ServiceReader'
        }
    }

Test-PSSessionConfigurationFile 'C:\JEA-Lab\ServiceAudit.pssc'

# STOP: before Register-PSSessionConfiguration, place the .psrc under
# an appropriate module's RoleCapabilities directory, protect ACLs,
# confirm identity/group names, constrain parameters, configure
# transcripts, and perform negative tests using a non-admin identity.

The example intentionally does not register an endpoint or grant anybody new remote access. For a real endpoint, prefer explicit cmdlets/parameters instead of wildcards, test every reachable command for alternate effects, avoid unrestricted external executables and risky providers, and make role-capability files administrator-writable only. Multiple matching roles can combine into a more permissive effective set, so review role composition. 27, 11

4.5 App Control for Business and script enforcement

Microsoft App Control for Business (the product family historically associated with WDAC) creates a Windows-enforced policy governing approved code, including script-related enforcement. Under supported configurations, PowerShell recognizes system lockdown and applies constraints to untrusted scripts; exact treatment depends on the active policy, OS, and PowerShell implementation. A PowerShell script that is not trusted by the policy may still run with CLM restrictions rather than being categorically blocked, so the phrase “application allowlisting” must not be interpreted as “every disallowed script is guaranteed not to start.” 8, 28

A careful rollout uses audit-first deployment, baseline collection, identification of required scripts and modules, explicit signer/publisher rules, limited exceptions, staged enforcement, and review of App Control telemetry. Policies can affect scheduled tasks, software installation, management agents, and administrator tooling; a badly designed policy can disrupt operations. 8, 28

Illustrative rollout checklist (architectural, not an auto-deployment script):

  1. Enumerate signed business-critical scripts and trusted distribution channels.
  2. Define who can sign code and how the private key is protected.
  3. Test realistic scripts with the candidate policy in a disposable image/VM.
  4. Collect App Control audit events and distinguish policy gaps from obsolete tooling.
  5. Enforce gradually, monitor breaks, and document a recovery method.
  6. Verify effective lockdown from an unprivileged account, not just configuration text. 8, 28

5. Defensive security: build useful PowerShell telemetry

The core detection challenge is dual use: the same PowerShell features that enable legitimate administration can also enable execution, discovery, persistence, and lateral movement. Strong detection therefore correlates command content, parent-child process relationships, identity, endpoint, network activity, time, and expected administrative behavior. MITRE ATT&CK classifies PowerShell execution under T1059.001 and Windows Remote Management abuse under T1021.006. 29, 30, 31

5.1 Script Block Logging, Module Logging, and Transcription

Telemetry What it helps answer Key caveat
Script Block Logging (4104) What script-block text was processed? May include sensitive values; long blocks may span multiple events
Module Logging (commonly 4103) Which commands/pipeline details were used in enabled modules? Coverage depends on configured module names and policy
Transcription What appeared in a host session's inputs and outputs? Output may reveal secrets; recording and host coverage vary
Windows process creation (4688) Which process launched with what parent and optional command line? Requires audit configuration; command-line capture is a separate setting
EDR process and network events What behavior surrounded PowerShell execution? Depends on agent deployment, telemetry retention, and product schema

Important channel distinction: Windows PowerShell 5.1 commonly writes script-block events to Microsoft-Windows-PowerShell/Operational. PowerShell 7 on Windows uses PowerShellCore/Operational and its own policy/configuration mechanisms. Validate that the provider is registered and that events arrive on both installed editions. 1, 2, 32

powershell
# Windows: discover actual log availability.
Get-WinEvent -ListLog '*PowerShell*' -ErrorAction SilentlyContinue |
    Select-Object LogName, IsEnabled, RecordCount

# Inspect the Windows PowerShell 5.1 and PowerShell 7 channels.
$channels = @(
    'Microsoft-Windows-PowerShell/Operational',
    'PowerShellCore/Operational'
)
foreach ($channel in $channels) {
    try {
        Get-WinEvent -FilterHashtable @{
            LogName   = $channel
            Id        = 4104
            StartTime = (Get-Date).AddHours(-24)
        } -MaxEvents 25 -ErrorAction Stop |
            Select-Object TimeCreated, Id, MachineName, Message
    } catch {
        Write-Verbose "No readable recent events in $channel"
    }
}

For enterprise configuration use Group Policy/MDM with the applicable PowerShell templates; on Windows PowerShell, look under Windows Components → Windows PowerShell for script-block, module, and transcription settings, and on PowerShell 7 use the corresponding PowerShell Core templates or supported configuration. Protect transcripts and logs with restricted ACLs, secure retention, centralized forwarding, and—where appropriate—Protected Event Logging. 1, 2, 33

powershell
# Lab-only: enable 5.1 Script Block Logging on a Windows test VM.
# Requires elevation; an enterprise should deploy the policy centrally.
$path = 'HKLM:\Software\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging'
New-Item -Path $path -Force | Out-Null
New-ItemProperty -Path $path -Name EnableScriptBlockLogging `
    -PropertyType DWord -Value 1 -Force | Out-Null

# Newly launched Windows PowerShell processes should receive the policy.
# Do not silently change organization-managed endpoints.

Module logging and transcription lab: module logging is configured for selected modules (for example through policy) and often produces 4103 events containing pipeline execution details. A transcription records a console session's input/output to an assigned file. The following controlled experiment illustrates the distinction; do not use it with actual credentials or sensitive output. 1, 2

powershell
# Windows lab, ordinary interactive session; protect the destination.
$directory = Join-Path $env:TEMP 'PS-Transcript-Lab'
New-Item -ItemType Directory -Path $directory -Force | Out-Null
$transcript = Join-Path $directory 'console-session.txt'
Start-Transcript -Path $transcript -Force
Get-Date
Get-Service -Name EventLog -ErrorAction SilentlyContinue
Stop-Transcript

# Review and secure the transcript; remove the LAB file afterward.
Get-Item -LiteralPath $transcript | Select-Object FullName, Length
Remove-Item -LiteralPath $transcript

The test above demonstrates interactive transcription only; it does not turn on central transcription policy or module logging. For production, enable the appropriate Group Policy settings and protected destination, then generate known test activity and check for 4103 and transcript artifacts. 1, 2

A useful validation is to run a harmless marker in a new PowerShell session and then locate its corresponding 4104 record. When collecting telemetry, deliberately avoid generating real credentials in command lines or sample script blocks. 1, 2

powershell
# Harmless marker for an authorized logging verification.
$labMarker = 'PS-SEC-LOGGING-VALIDATION-EXAMPLE'
Write-Output $labMarker

# Read 4104 events; search messages only for the synthetic marker.
Get-WinEvent -FilterHashtable @{
    LogName   = 'Microsoft-Windows-PowerShell/Operational'
    Id        = 4104
    StartTime = (Get-Date).AddMinutes(-15)
} -ErrorAction SilentlyContinue |
    Where-Object Message -Match 'PS-SEC-LOGGING-VALIDATION-EXAMPLE' |
    Select-Object TimeCreated, RecordId, Message

5.2 Windows Event Forwarding (WEF)

Windows Event Forwarding centralizes selected events to a Windows Event Collector using Windows Event Log/WS-Management capabilities. Source-initiated subscriptions allow many machines to forward events according to a subscription defined on the collector; collector-initiated subscriptions are another option. Configure the service, group policies, transport, firewall, source authorization, collection filters, and retention according to the deployment model. 34, 35

powershell
# Windows collector: read-only inspection of subscription state.
# These commands may require administrative rights.
wecutil es                 # Enumerate existing subscriptions.
# wecutil gs '<sub-id>'      # Examine one approved subscription.
# wecutil gr '<sub-id>'      # Check subscription runtime status.

# View forwarded events after a collector and source are configured.
Get-WinEvent -LogName ForwardedEvents -MaxEvents 20 |
    Select-Object TimeCreated, Id, ProviderName, MachineName

Design pattern: send Security 4688 process-creation data, selected authentication records, and PowerShell Operational 4103/4104 data to a restricted collector or SIEM. Budget for event volume, preserve provenance (original host/UTC timestamps), watch collection lag/dropout, and do not forward everything blindly. PowerShell source code, command lines, and transcripts may themselves constitute sensitive data. 1, 2, 34, 32

5.3 AMSI and endpoint detection and response (EDR)

The Antimalware Scan Interface (AMSI) lets compatible applications submit script and other content for inspection by registered antimalware products. PowerShell integrates with AMSI on Windows; the availability of an interface does not guarantee a malicious script will be found. An EDR product complements it with endpoint telemetry, behavioral detections, investigation, and response workflows. Microsoft's Defender XDR hunting schema exposes process-creation fields such as DeviceName, FileName, ProcessCommandLine, InitiatingProcessFileName, and timestamps. 36, 37, 3

powershell
# Defender for Endpoint: locally inspect service state (Windows).
# This is a signal, NOT proof of full EDR health or AMSI effectiveness.
Get-Service -Name WinDefend, Sense -ErrorAction SilentlyContinue |
    Select-Object Name, Status, StartType

# Antivirus state may be unavailable or managed by another security product.
Get-MpComputerStatus -ErrorAction SilentlyContinue |
    Select-Object AMServiceEnabled, AntivirusEnabled,
                  RealTimeProtectionEnabled, AntispywareEnabled

For enterprise controls, assess agent health, current intelligence, isolation/tamper-protection settings, prevention rules, and event completeness. If alerts occur, preserve evidence and follow an approved containment workflow rather than trying random bypasses. Microsoft Defender includes attack-surface reduction rules targeting suspicious script behaviors such as obfuscation; such signals require context and tuning. 37, 38

5.4 Query examples: process telemetry and script evidence

Microsoft Defender XDR advanced hunting (KQL): this is a hunting hypothesis, not a definitive malware verdict. It inspects PowerShell process-creation records for command-line flags or invocation patterns associated with abuse. Some approved automation uses the same flags. 37, 31

kusto
DeviceProcessEvents
| where Timestamp > ago(7d)
| where FileName in~ ('powershell.exe', 'pwsh.exe')
| extend Cmd = tolower(ProcessCommandLine)
| where Cmd contains '-encodedcommand'
    or Cmd contains '-enc '
    or Cmd contains '-noprofile'
    or Cmd contains '-windowstyle hidden'
| project Timestamp, DeviceName, AccountName, FileName,
          ProcessCommandLine, InitiatingProcessFileName,
          InitiatingProcessCommandLine, ProcessId
| order by Timestamp desc

Windows event-log triage (read-only): retrieve recent script-block events, annotate a limited set of indicators, then investigate independently. Keyword matching alone does not determine intent. 1, 2, 31

powershell
$log = 'Microsoft-Windows-PowerShell/Operational'
$pattern = '(?i)\b(Invoke-Expression|DownloadString|FromBase64String)\b'

Get-WinEvent -FilterHashtable @{
    LogName = $log; Id = 4104
    StartTime = (Get-Date).AddDays(-1)
} -MaxEvents 1000 -ErrorAction SilentlyContinue |
    Where-Object { $_.Message -match $pattern } |
    ForEach-Object {
        [pscustomobject]@{
            TimeCreated = $_.TimeCreated
            RecordId    = $_.RecordId
            MachineName = $_.MachineName
            Indicator   = [regex]::Match($_.Message, $pattern).Value
        }
    }

For production detection engineering, parse each 4104 record's event data, correlate fragmented script blocks by ScriptBlockId and message sequence where relevant, and combine with 4688 or EDR process trees, identities, service tickets, network connections, and approved-management baselines. Queries should be tested against real schemas and normal traffic, with false-positive and false-negative evaluation. 1, 32, 37, 31

6. Offensive-security awareness: recognize abuse without reproducing it

The purpose of this section is to recognize unauthorized activity, safely inspect potential evidence, and improve controls. The examples do not execute a payload, harvest credentials, disable security tooling, or contact an attacker-controlled endpoint. MITRE ATT&CK provides a behavior-centered vocabulary, not a list of inherently malicious command strings. 29, 39, 30, 40

6.1 PowerShell and living-off-the-land techniques

“Living off the land” describes using native, preinstalled, or otherwise trusted tools for adversarial objectives. An attacker may prefer familiar Windows management components because they are available, capable, and often present in normal administrator activity. PowerShell becomes suspicious through context and sequences, not simply because a shell process exists. 29, 31

ATT&CK concept Defender-observable signal Alternative benign explanation Best corroboration
PowerShell interpreter (T1059.001) powershell.exe/pwsh.exe started from an unusual parent Management agent or software installer Parent process, signer, user, change ticket
Obfuscated information (T1027) Encoded or unusually constructed script text Vendor packaging, encoded automation Script content, AMSI/EDR verdict, follow-on actions
WinRM remote services (T1021.006) Remote PowerShell session on an unexpected host Authorized centralized operations Authentication details, source host, JEA role, timing
Credential access (T1003 family) Unexpected interaction with credential-bearing processes or objects Approved endpoint software or support tool Protected-process telemetry, approvals, identity anomalies

The table illustrates hypotheses. Attackers can avoid any single string, and benign tools can trigger the same heuristic. A mature detection is validated against organization-specific administrative patterns. 29, 39, 30, 31, 40

6.2 Suspicious script triage: preserve, identify, and inspect offline

Never execute unknown code “to see what it does” on a production workstation. First preserve it according to your evidence-handling policy, calculate a cryptographic hash, inspect signer and origin metadata, and use static parsing. PowerShell's built-in parser can produce an Abstract Syntax Tree (AST) without running the file. For untrusted material, prefer an isolated analysis environment with appropriate restrictions and no production credentials. 7, 13, 29

powershell
# READ-ONLY offline triage. Inspect a copied specimen, never run it.
$specimen = 'C:\LabEvidence\untrusted-script.ps1'

Get-Item -LiteralPath $specimen |
    Select-Object FullName, Length, CreationTimeUtc, LastWriteTimeUtc
Get-FileHash -LiteralPath $specimen -Algorithm SHA256
Get-AuthenticodeSignature -LiteralPath $specimen |
    Select-Object Status, StatusMessage,
        @{n='Signer';e={$_.SignerCertificate.Subject}}

# Parse as data, without script invocation or Invoke-Expression.
$tokens = $null
$parseErrors = $null
$ast = [System.Management.Automation.Language.Parser]::ParseFile(
    $specimen, [ref]$tokens, [ref]$parseErrors
)

# Inventory literal command names visible in the syntax tree.
$commands = $ast.FindAll({
    param($node)
    $node -is [System.Management.Automation.Language.CommandAst]
}, $true)

$commands | ForEach-Object { $_.GetCommandName() } |
    Sort-Object -Unique
$parseErrors | Select-Object Message, Extent

Static-analysis limitations: AST inventory does not reliably reveal dynamically assembled command names, downloaded content, custom binary extensions, runtime reflection, or behavior that depends on external state. Parsing is therefore a first pass, not a clean bill of health. Keep evidence copies immutable and avoid piping unknown contents into Invoke-Expression, dot-sourcing them, importing them as modules, or running “deobfuscators” from untrusted authors. 29, 39

6.3 Obfuscation: inspect patterns rather than chase strings

Common suspicious patterns include unusually long encoded arguments, nested string assembly, repeated conversions between encodings, compressed content, runtime code generation, and scripts whose entry point is hidden behind layers of indirection. However, encoding is not encryption; Base64 has legitimate uses and does not establish maliciousness on its own. MITRE classifies obfuscation-related behavior under T1027 and documents corresponding behavioral detection strategies. 39, 31

powershell
# Inert test fixture: inspect a sample command line as TEXT.
# No encoded payload is created or executed.
$sample = @'
pwsh.exe -NoProfile -EncodedCommand <REDACTED-LAB-DATA>
'@

$flags = [ordered]@{
    EncodedCommand = $sample -match '(?i)-encodedcommand\b|-enc\b'
    NoProfile      = $sample -match '(?i)-noprofile\b|-nop\b'
    HiddenWindow   = $sample -match '(?i)-windowstyle\s+hidden'
}
[pscustomobject]$flags

Instead of relying only on flag detection, ask whether the process appeared under a plausible parent, whether the account was supposed to run it, whether its script source was approved, and what happened immediately afterward. A process argument of -NoProfile is particularly common in legitimate noninteractive jobs. 37, 31

6.4 Credential theft awareness and detection

Credential-access scenarios include attempts to steal passwords, password hashes, Kerberos tickets, or access tokens, as well as misuse of already-authorized credentials. For PowerShell analysts, signs may include suspicious access to credential-bearing processes, unusual authentication failures, atypical sign-ins, unexpected secret-store enumeration, or lateral movement shortly after privileged execution. Defenders should evaluate Credential Guard, LSA protection, privileged access restrictions, MFA, and audit coverage as appropriate to their environment. 41, 16, 17, 40

powershell
# Windows: triage authentication failures (read-only).
Get-WinEvent -FilterHashtable @{
    LogName   = 'Security'
    Id        = 4625, 4771, 4776
    StartTime = (Get-Date).AddHours(-6)
} -MaxEvents 100 -ErrorAction SilentlyContinue |
    Group-Object Id |
    Select-Object Name, Count

# Investigate on the appropriate hosts, including domain controllers.
# Counts alone do not reveal theft or distinguish mistyped passwords.

A high count of failures may come from stale service credentials, misconfigured applications, password spraying, or other causes. Do not attribute intent from event counts alone. Combine account and device context, source addresses, timeline, and known maintenance or incidents. Never collect actual passwords or tokens into investigation notebooks. 41, 16, 17

6.5 Remote execution abuse and lateral movement

Legitimate remoting and unauthorized lateral movement may both involve WinRM and Invoke-Command. Indicators include a workstation unexpectedly becoming an admin source, remote management initiated by a user without change approval, new access to many hosts, an anomalous logon path, or child processes spawned from a remoting service context. Monitor source and destination, not only the target's PowerShell events. Review the remoting endpoint's ACL, role capabilities, and configured authentication methods. 5, 10, 30

powershell
# Windows: inspect configured endpoint names and access controls.
# Reads session configurations; does NOT enable remoting.
Get-PSSessionConfiguration -ErrorAction SilentlyContinue |
    Select-Object Name, Permission, RunAsUser

# Operational question for the incident record:
# Who initiated the connection, from where, with what authorization,
# against which endpoint, and what was executed afterward?

Do not respond to an abnormal remoting event by indiscriminately disabling WinRM on critical infrastructure. Use a targeted containment decision aligned with documented dependencies, then preserve event evidence, inspect affected principals, and revoke excessive or compromised access as appropriate. 5, 10, 30

7. Incident response workflow and detection engineering

7.1 An investigation sequence

  1. Validate the alert. Record the triggering event, clock/timezone, initiating process, full command-line metadata, and detection source.
  2. Establish expected behavior. Identify the operator, scheduled task, agent, maintenance window, approved script/signing process, and target system.
  3. Build a timeline. Correlate PowerShell 4103/4104, Security 4688, relevant authentication events, EDR process trees, DNS/network events, and any WinRM activity.
  4. Preserve evidence. Hash script artifacts; store event exports, signed manifests, and file metadata in a restricted case location with a chain-of-custody process.
  5. Constrain the blast radius. If compromise is supported by evidence, use authorized isolation, account restrictions, and credential-rotation procedures; coordinate with system owners.
  6. Eradicate and recover. Remove confirmed unauthorized persistence or content through approved playbooks; restore trusted baselines and monitor recurrence.
  7. Improve detections. Adjust logging, least privilege, application control, allowlists, and alert logic based on confirmed findings.

These steps are an operational synthesis of layered PowerShell telemetry and MITRE's behavior-oriented detection model. They are not proof that a specific event is malicious. 1, 34, 37, 31

7.2 Scoring a PowerShell investigation

A practical triage model uses explanatory factors rather than a binary keyword rule. A sample reviewer rubric assigns points for unusual parentage, unexpected identity or host, encoded or opaque command arguments, lack of provenance, abnormal child/network behavior, and corroborating authentication anomalies. Scores are prioritization aids only and require local calibration and analyst review. 37, 31

Factor Low concern Higher concern
Identity Known automation identity with expected permissions Unfamiliar privileged interactive logon
Parent process Documented agent or scheduled task Unusual document, browser, or remote-management chain
Script provenance Reviewed, approved and expected Unsigned, altered, or source unknown
Command content Predictable read-only inventory Opaque, constructed, or unexpected capability usage
Behavior after launch Expected administrative API calls New persistence, credential access, or unexpected outbound traffic
Context Maintenance window and ticket Off-hours lateral execution without change record

7.3 Hardening blueprint

Implement controls in a dependency-aware order. First establish asset and identity inventory; remove unnecessary permanent administrator privileges; protect privileged identity workflows; deploy trusted script distribution and signing; use application control where supported; constrain administrative interfaces with JEA; enable appropriately protected logs; forward key events; and validate detections through benign simulations and tabletop exercises. 4, 8, 10, 1, 34

Minimum measurable acceptance criteria for a managed Windows fleet might include: a tested log collection path for each installed PowerShell edition; visibility into process creation and principal context; a documented exception process for scripts; no plaintext production credentials in source control or command lines; restricted remoting endpoints; and periodic detection tests using harmless, known markers. 9, 1, 2, 32

8. Exercises and worked solutions

The following exercises are intentionally non-destructive. Use a disposable Windows lab where Windows-specific features are required. For any administrative change, obtain authorization first. Most tasks have both a conceptual goal and a concrete, verifiable result.

Exercise 1 — Execution policy versus enforcement

Task. An administrator sets AllSigned and claims that unauthorized code can no longer run. Identify three reasons this conclusion is unsound. Provide a read-only command that reveals policy precedence.

Worked solution. AllSigned requires signed script files in the applicable Windows execution-policy context, but (1) execution policy is not a security boundary; (2) signed scripts can be malicious or compromised; and (3) interactive commands and other execution surfaces are not prevented by AllSigned. Use:

powershell
Get-ExecutionPolicy -List

Inspect MachinePolicy and UserPolicy before trying to change an effective policy. OS-enforced App Control, rights restrictions, and endpoint monitoring address distinct risks. 6, 7, 8

Exercise 2 — Triage script provenance

Task. You receive an unfamiliar maintenance.ps1 from a third-party vendor. List the minimum checks to make without running it. Then write the relevant commands.

Worked solution. Establish source provenance, change approval, hash, signer status, file metadata, and an offline content review. In a lab directory containing a copied artifact:

powershell
$file = '.\maintenance.ps1'
Get-FileHash -LiteralPath $file -Algorithm SHA256
Get-AuthenticodeSignature -LiteralPath $file |
    Select-Object Status, StatusMessage, SignerCertificate
Get-Item -LiteralPath $file |
    Select-Object FullName, Length, LastWriteTimeUtc
Get-Content -LiteralPath $file -Raw   # View as TEXT, don't execute.

A valid signature is useful evidence, not permission to skip code review. Inspect dependencies and the publisher's distribution channel. 7, 13

Exercise 3 — Choose the correct identity

Task. A daily Microsoft Graph report reads only the signed-in user's profile. Should it request an organization-wide administrator role, delegated User.Read, or an app-only broad directory permission?

Worked solution. For an interactive user-scoped report, prefer the least-privileged delegated User.Read example, subject to the API's requirements. Application permissions are more appropriate for workloads without user interaction, but require their own authorization and consent design. A directory administrator role is unjustified for this narrow action. 14, 9

powershell
Connect-MgGraph -Scopes 'User.Read' -NoWelcome
Get-MgContext | Select-Object AuthType, Scopes, TenantId
Disconnect-MgGraph

Exercise 4 — Evaluate SecureString

Task. A teammate states: “Passwords inside SecureString are encrypted on Linux, and exporting a PSCredential with CLIXML is a portable encrypted backup.” Explain the errors and propose a safer automation pattern.

Worked solution. SecureString does not encrypt its internal storage on non-Windows platforms. Windows CLIXML credential export uses DPAPI bound to the Windows exporting identity and machine; it is not designed as portable credential transport. Favor an approved centralized vault with a short-lived access mechanism or a managed identity where applicable. Avoid plaintext literals, credential exports in source control, and unnecessary -AsPlainText conversion. 21, 23, 25

Exercise 5 — Design a JEA role

Task. A support group must list Windows service status but must not modify services, invoke arbitrary executables, or enter a general administrative shell. Which JEA properties and controls should be used?

Worked solution. Begin with a RestrictedRemoteServer session, a role capability that explicitly exposes Get-Service only, a role definition for the authorized group, protected role files, and transcription/auditing. Negative-test Stop-Service, Set-Service, and arbitrary external commands using an account in the support group; none should be accessible unless explicitly required. Avoid wildcards and review whether other mapped roles expand rights. 10, 27, 11

powershell
# Role capability template for a lab file only:
New-PSRoleCapabilityFile -Path '.\ServiceRead.psrc' `
    -VisibleCmdlets 'Get-Service'

# Deployment requires the module layout, ACL checks, PSSC mapping,
# a controlled endpoint registration, and non-admin negative tests.

Exercise 6 — Find the right log channel

Task. A fleet runs both powershell.exe and pwsh.exe. An analyst searches only Microsoft-Windows-PowerShell/Operational for 4104 and concludes no scripts ran. What was missed?

Worked solution. The analyst may have omitted the PowerShell 7 PowerShellCore/Operational channel and may not have verified provider registration, script-block logging policy, collection coverage, or event retention. Search both and verify logging with a harmless marker. An absence of 4104 without validated logging is absence of evidence, not proof of no execution. 1, 2

powershell
Get-WinEvent -ListLog '*PowerShell*' -ErrorAction SilentlyContinue |
    Select-Object LogName, IsEnabled, RecordCount

Exercise 7 — Write a high-signal process query

Task. Write a Microsoft Defender XDR hunting query for PowerShell started by Microsoft Word, but avoid asserting that all results are malicious.

Worked solution. Correlate child image and unusual parent; return enough context to review each hit. The query requires Microsoft Defender for Endpoint process telemetry. 37, 31

kusto
DeviceProcessEvents
| where Timestamp > ago(7d)
| where FileName in~ ('powershell.exe', 'pwsh.exe')
| where InitiatingProcessFileName =~ 'WINWORD.EXE'
| project Timestamp, DeviceName, AccountName,
          FileName, ProcessCommandLine,
          InitiatingProcessFileName, InitiatingProcessCommandLine
| order by Timestamp desc

Interpretation: investigate document provenance and subsequent behavior. Office-driven automation or security testing may be legitimate; verify the organizational baseline and change records before escalation.

Exercise 8 — Static AST inspection

Task. A copied script includes Get-Process, Get-Service, and an unknown expression built from strings. Write an offline method that lists literal command names and explain what it could miss.

Worked solution. Use Parser.ParseFile rather than executing or importing the specimen:

powershell
$tokens = $null
$errors = $null
$ast = [System.Management.Automation.Language.Parser]::ParseFile(
    'C:\LabEvidence\sample.ps1', [ref]$tokens, [ref]$errors
)
$ast.FindAll({
    param($n)
    $n -is [System.Management.Automation.Language.CommandAst]
}, $true) |
    ForEach-Object GetCommandName |
    Sort-Object -Unique

This method can miss commands assembled dynamically or behavior controlled by data obtained only at runtime. The presence of a command name is not proof that it was executed. 29, 39

Exercise 9 — Diagnose a “credential theft” alert

Task. Your SOC reports 4771 failures and a PowerShell process on an administrator workstation. List four additional pieces of evidence needed before classifying this as credential theft.

Worked solution. Collect (1) the affected principal and whether failures occurred on the domain controller; (2) source IP, destination, status codes, and chronology; (3) the PowerShell process tree, account, and command content; and (4) contemporaneous authentication successes, managed-service changes, endpoint alerts, or unusual network behavior. Stale service credentials may explain some failures. Escalate if the correlated evidence supports compromise, not simply because one event ID is present. 37, 16, 17, 40

Exercise 10 — Design a logging validation test

Task. A company says “Script Block Logging is enabled everywhere.” Define an evidence-based test for both installed PowerShell editions, including data-protection safeguards.

Worked solution. On a controlled representative workstation, verify policy and event-provider state, launch a new session in each edition, execute a harmless unique marker, then confirm corresponding 4104 records in the correct provider/channel. Confirm the WEF/SIEM copy includes source-host and timestamp fields and meets latency/retention objectives. Restrict access to logs and transcripts, test that protected logging works where configured, and avoid real credentials in test markers. Record any missing events as deployment failures needing remediation. 1, 2, 34

Exercise 11 — Harden a remoting workflow

Task. An automation team proposes adding * to WinRM TrustedHosts, granting permanent local administrator membership, and saving a password in a script to simplify inventory collection. Provide a safer architecture.

Worked solution. Use Kerberos where domain configuration permits; otherwise establish appropriately authenticated and encrypted transport. Restrict the remote endpoint with JEA or a read-only service identity, authorize only necessary hosts, eliminate standing privileges, and use a managed secret/identity pattern rather than a literal password. Centralize WinRM and PowerShell telemetry, track approvals, and test access denials. A wildcard TrustedHosts list and broad privileges create avoidable trust and lateral-movement exposure. 5, 25, 10, 11

Exercise 12 — Prioritize an investigation

Task. Two incidents arrive. A: a signed deployment agent runs pwsh.exe -NoProfile during an approved patch window. B: an unfamiliar document process launches encoded PowerShell under a privileged user, followed by unusual remote-management activity. Which deserves immediate triage, and why?

Worked solution. B has several corroborating signals: anomalous parentage, opaque command content, privilege context, and follow-on remote activity. A is more readily explained by an established administrative baseline, though a signature alone cannot exonerate it. Priority reflects converging evidence, not a rule that -NoProfile is inherently safe or -EncodedCommand inherently malicious. Preserve evidence and validate both cases with process, identity, network, and policy records. 37, 29, 30, 31

9. Final reference checklist

  • Do not confuse policy with enforcement: execution policy is advisory defense in depth; App Control and access controls enforce different boundaries. 6, 8
  • Do not confuse identity with permissions: Kerberos/NTLM, OAuth tokens, Windows ACLs, Entra roles, and Graph scopes answer different questions. 5, 9, 20, 15
  • Do not confuse a credential wrapper with secure storage: SecureString, PSCredential, CLIXML, and SecretStore have materially different models. 21, 23, 25
  • Do not confuse a detected string with a confirmed incident: use parent process, account, script content, network behavior, time, and baselines. 37, 29, 31
  • Do not assume logging exists because it was configured: test both 5.1 and 7 channels and secure the evidence you collect. 1, 2, 34
  • Do not run unknown specimens: hash, verify signatures, read as text, and parse offline before making an incident-response decision. 7, 13, 29
