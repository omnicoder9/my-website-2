Part IThe shape of the recursion

1Two functions, one difference

Here are two solutions to two different problems, printed one above the other:

func maxDepth(t *TreeNode) int {
    if t == nil { return 0 }
    return 1 + max(maxDepth(t.Left), maxDepth(t.Right))
}

func maxPathSum(t *TreeNode) int {
    if t == nil { return 0 }
    return t.Val + max(hang(t.Left), hang(t.Right))
}

They have the same shape, the same base case, the same two recursive calls and the same combining step. One of them is a complete and correct solution. The other is a fragment: it computes something true about every node and never mentions the answer, because the answer to maximum path sum is not a value any node returns. It is a value some node writes down, and the number the function hands back to its caller is a different quantity serving a different purpose.

This is the whole subject. Tree problems are where recursion stops being a technique and becomes the natural shape of the data, because a tree is defined recursively: a node, and two smaller trees. The consequence is that the recursive skeleton is almost free and almost identical everywhere, and all of the actual engineering moves into three questions that the skeleton does not answer:

  1. What travels down? What does a node need to know that only its ancestors can tell it?
  2. What travels up? What summary of a subtree is sufficient for the parent, and what does the parent have to recompute if the summary is too thin?
  3. Where is the answer written? Is it the value returned to the caller, or something recorded at a node on the way through?

Everything in this article is an answer to those three questions. Depth, diameter, path sums, ancestors, validation, serialisation, reconstruction and rerooting are not a list of tricks to memorise; they are a small number of positions in a space with three axes, and once the axes are visible the problems stop looking like separate problems. Twenty-two of them are drawn as numbered call plates through the article and collected in a ledger at the end.

The code is given in Go, Java, C++, Rust, C# and TypeScript. All six implementations of all eleven listings compile without warnings and print byte-identical output; that identity is a build gate rather than a claim. Every quantitative statement comes from tree_lab.py, a deterministic stdlib-only program run when this page was generated, whose complete output is reproduced verbatim at the end.

2What a tree forbids

A tree is a connected acyclic graph; a rooted tree adds a distinguished vertex and thereby an orientation to every edge. The definition is short and the consequences are large, and almost every algorithm below is cashing in one of them.

An n-vertex tree has exactly n − 1 edges, so a tree is the sparsest connected graph and the densest acyclic one: add any edge and you create exactly one cycle, remove any edge and you get exactly two components. Between any two vertices there is exactly one simple path. That uniqueness is the fact that makes lowest common ancestor well defined, that makes distance in a tree computable as depth(a) + depth(b) − 2 depth(lca(a,b)), and that makes a subtree a contiguous interval in an Euler tour. It is also why there is no visited set in any of the binary-tree code in this article: in a general graph a depth-first search must remember where it has been, and in a tree the parent pointer is the entire memory required [1,2,3].

The counting facts matter for a different reason. The number of distinct shapes of a binary tree with n nodes is the Catalan number Cn [4,5], and log2 Cn / n tends to 2. The lab computes it directly: 1.4036 at n = 10, 1.8919 at 100, 1.9842 at 1,000 and 1.9997 at 100,000. The shape of a binary tree is worth two bits per node and no more, which is the yardstick against which every serialisation format in §17 is measured, and the reason succinct tree representations exist at all [6,7].

Labelled trees are counted by Cayley's formula, nn−2 [8]; unlabelled rooted trees by Otter's constant [9]. Neither number appears in a competitive-programming solution, but both explain why an algorithm that enumerates trees is hopeless and one that walks a given tree is trivial, which is a distinction worth internalising early.

Finally, a caution about vocabulary that costs people points in contests. A binary tree is any tree with at most two children per node. A binary search tree is a binary tree with an ordering invariant. A balanced binary tree is one whose height is logarithmic in n, which is a promise nothing in the problem statement provides unless it says so. Most wrong answers in this area come from silently assuming the third when only the first was given.

3The two channels

Write the general recursion out with every slot named and the structure of the subject becomes visible:

The two recursive calls are the tree. The other three lines are the problem. The downward channel is the argument list: everything a node is told by its ancestors. The upward channel is the return value: everything a node tells its parent about the subtree beneath it. The record is a side effect on state that outlives the call — a captured variable, a field, an output buffer.

The two channels have completely different economics. Downward context is free to compute and expensive to widen: each additional piece of context is copied into every call, and if it is a mutable buffer it must be undone on the way back out (§13). Upward summaries are the opposite: they cost nothing to carry but everything to choose. A summary that is too thin forces the parent to recompute what the child already knew, which is exactly how an O(n) algorithm silently becomes O(n2). The canonical example is "balanced binary tree" solved by calling a separate height() from every node; the fix is not a faster height() but a fatter return value.

The balanced-tree example is worth doing concretely, because it is the cheapest possible demonstration that the return type is a design decision. Asked whether every node's two subtree heights differ by at most one, the obvious code returns a boolean and calls a separate height() twice per node. Each height() is a full traversal of a subtree, so the total is the sum of all subtree sizes — which is the sum of all depths, Θ(n log n) on a balanced tree and Θ(n2) on a path. Widen the return type from bool to "height, or a sentinel meaning unbalanced" and the same algorithm is O(n) on every shape, with no cleverness and no extra state. Nothing was optimised; the child was simply allowed to say what it already knew.

The third channel is the one people forget exists. If the answer to the problem is a property of a path or a pair rather than of a subtree, then the quantity that is well behaved under composition and the quantity you actually want are different, and the recursion must return the first while recording the second. That is the content of §10 and §11, and the source of the two most instructive bugs in this whole area.

A fourth possibility deserves naming so it can be ruled out: some problems need information a node's subtree does not contain and its ancestors do not carry either — information from the rest of the tree entirely. No single pass can supply it. That is not a defect in the recursion, it is a theorem about it, and the remedy is §20.

4The null is a node

The base case is not an edge case. In a well-designed tree recursion the empty tree is a value of the same type as every other tree, and the base case returns that tree's honest answer: height 0, sum 0, "yes it is a valid search tree", "no I did not find your target". When the base case has to return something dishonest — a sentinel meaning "ignore me" — that is usually a signal that the return type is wrong, not that the tree is awkward.

Attach a square to every missing child and the picture becomes exact. Knuth calls the result an extended binary tree [10]:

An n-node binary tree has exactly n + 1 missing children. The lab verifies this on all five of its shapes, from a perfect tree to a degenerate path: node calls n = 131,071 and null calls n + 1 = 131,072 in every case. A recursion that tests for null inside the callee therefore makes 2n + 1 calls, of which (n + 1)/(2n + 1) — 50.0002% at this size — do nothing whatever except return. The alternative, testing at the call site, removes 131,072 of 262,143 calls at the cost of writing the test twice.

Which is better is a genuine trade and not a matter of taste. Testing inside the callee is shorter, uniform, and impossible to get wrong; testing at the call site halves the call count and is measurably faster in languages where a call is not free, but it duplicates the guard and tends to sprout bugs at the top-level entry point where a null root is still possible. For contest code the callee test wins on time-to-write. For a hot path in production the call-site test is worth the ugliness. What is not defensible is believing that the empty calls are not happening.

How the empty tree is spelled differs across the six languages in this article, and the differences are not cosmetic. Go, Java, C# and C++ use a nullable pointer or reference, so the empty tree and a bug that lost a pointer are the same value and the compiler cannot help. TypeScript's TreeNode | null under --strict forces the check at every dereference, which is the type system doing exactly the work §4 is about. Rust's Option<Rc<RefCell<TreeNode>>> is the most verbose and the most honest: Option makes emptiness a case you must handle, Rc says a node has one owner and many transient observers during a walk, and RefCell is the price of methods like Morris threading that mutate through a shared handle [11]. The listings are noticeably longer in Rust for this reason, and the noise is buying something real: none of the three classic null-related traversal bugs is expressible.

The same count explains a fact used repeatedly later: any encoding that writes a sentinel for each missing child writes exactly n + 1 sentinels, on every shape, which is why the serialisations in §17 are the same length for a path and for a perfect tree.

5Order is a position, not an algorithm

Pre-order, in-order and post-order are frequently taught as three traversals. They are one traversal with the visit placed at one of three points relative to the recursive calls.

This is worth more than a mnemonic, because the placement determines what information is available when the node is visited, and that is the only thing that matters when choosing:

  • Pre-order visits a node before its children exist as answers. Nothing about the subtree is known yet, so pre-order is the order for problems where the node's contribution depends on its ancestors: carrying bounds down, accumulating a path, serialising (§17).
  • Post-order visits a node after both children have returned. It is the only order in which a node may use its subtrees' answers, so every "compute something about each subtree" problem is post-order whether or not anybody says the word. Tree dynamic programming is post-order by definition.
  • In-order is special to binary trees, and on a search tree it emits the keys in sorted order [12]. That single property turns a whole family of BST questions — the k-th smallest, validation, the two swapped nodes — into questions about a sorted sequence.

All three cost the same and touch the same nodes in the same physical order; only the moment of the visit differs. A useful consequence is that a single walk can do all three at once, which is how the lab's instrumentation collects depth, height and subtree sizes in one pass rather than three.

Level order — sometimes called breadth-first order — is the exception. It is genuinely a different traversal with different mechanics and different memory behaviour, and it gets Part IV to itself.

6Depth-first and breadth-first are a bet on shape

Depth-first search keeps one frame per ancestor of the current node, so its peak memory is the height. Breadth-first search keeps one queue entry per node on the current frontier, so its peak memory is the maximum width. These are not merely different; on any given tree they are close to inversely related, because a tree that is tall is thin and a tree that is wide is short.

The uniformly random shape is the interesting row: it is the only one where the two costs are within half a percent of each other, which is what you would expect from a family whose height and width are both Θ(√n). That is not an accident of the generator: the average height of a uniformly random binary tree with n internal nodes is asymptotically 2√(πn) [13], and the lab builds its instances with Rémy's algorithm, which samples that distribution exactly [14]. The logarithmic law for search trees built from random permutations is a different theorem about a different measure [15,16], and the general machinery behind both is standard [17,18,19].

The practical reading is that "use BFS, it is safer" and "use DFS, it uses less memory" are both folklore, and which one is true is a property of the input. On a wide, shallow tree — an n-ary directory listing, a scene graph, a parse tree of a flat document — breadth-first is the one that explodes. On a deep, thin tree — a linked list wearing a tree's type, a comment thread, a chain of single-child nodes produced by sorted insertion — depth-first is the one that explodes, and it explodes by crashing rather than by allocating.

It is worth knowing where each of those shapes actually comes from, because the answer is rarely "an adversary". Perfect and near-perfect trees come from anything built by halving: a segment tree over an array, a merge tree, a heap laid out in an array. Random-BST shapes come from inserting keys that arrive in no particular order, which is the common case and the reason unbalanced search trees survive in practice at all. Uniform random shapes come from grammars and from randomly generated test data — a parse tree of a random expression is much closer to Θ(√n) than to Θ(log n). And degenerate paths come from sorted input, from linked structures typed as trees, from deeply nested JSON or XML, and from comment threads and file-system chains — none of which is hostile, all of which is common.

7The stack you did not declare

A recursive traversal allocates memory. It does not look like it does, which is why this is the most common way for otherwise-correct tree code to fail in production and the most common way for an accepted contest solution to fail on the one test case designed to break it.

The lab asks the concrete question: with a budget of 1,000 live frames — CPython's default limit [20] — how many nodes fit?

Extrapolating Devroye's law, a random binary search tree would need on the order of 10101 nodes to exhaust the same budget [15,21]. The spread between the worst finite shape and the best is 234× in this table and unbounded in general, which is the point: is n small enough to recurse? is not a question about n.

The adversary's job is correspondingly easy. Building a binary search tree by inserting sorted keys produces the left path in the first row. The same code, the same input size, a different permutation, and a solution that recursed is now a stack overflow. This is CWE-674, uncontrolled recursion [22,23], and it is a denial-of-service class in parsers and serialisers for exactly this reason: attacker-controlled nesting depth becomes attacker-controlled stack depth.

Language runtimes differ in ways worth knowing. The JVM's stack size is fixed per thread and configurable with -Xss [24]; C and C++ inherit a per-thread limit from the operating system with no defined behaviour on exhaustion [25]; Go grows goroutine stacks dynamically, starting small and copying on overflow, so deep recursion in Go degrades in allocation rather than crashing at a fixed depth [26]; Rust has no tail-call guarantee and will abort on stack overflow rather than unwinding [27]. None of these guarantees tail call elimination for the general case, and the general tree recursion is not tail recursive anyway: there are two calls and work after the second [28].

The remedies, in the order they should be reached for: bound the depth by construction (a balanced structure, or a problem statement that promises one); convert to an explicit stack (§19), which moves the memory to the heap where it is large and measurable; or convert to an iterative two-pass scheme over a pre-computed order (§20), which is what the rerooting listing does and why it is written iteratively even though its recursive form is shorter.

Two details in that listing are worth more than they look. The base case returns 0 rather than 1 because the empty tree has no levels — and the sign of getting this wrong is not a crash but an answer that is uniformly one too large, which passes exactly the tests that do not include an empty input.

The second is minDepth, which is not the mirror image of maxDepth and is the neatest small trap in the area [30]. Replacing max with min gives a function that reports 1 for a node with one child and a long chain beneath it, because the missing child returns 0 and 0 is smaller. The definition of minimum depth is the distance to the nearest leaf, and a null child is not a leaf. The fix is to notice that the recursion's base case is doing double duty — standing both for "empty tree" and for "no path this way" — and to separate them.

This is the general lesson of the up channel in miniature. The return value is a summary, and the summary must be closed under the operation the parent performs on it. Height is closed under max and has an identity, 0, which the empty tree can honestly supply. Distance-to-nearest-leaf is not: the empty tree has no honest value for it at all, and the code has to say so structurally.

A word on how to count the cost of a tree recursion, since the habit of writing down a recurrence is actively unhelpful here. The recurrence T(n) = T(k) + T(n − k − 1) + O(1) has no closed form without knowing k, and k is the shape, which the problem does not give you. The useful accounting is different and always works: each node is visited once, so the total is the number of nodes times the work done at a node. Maximum depth does O(1) per node, so it is O(n) on every shape, balanced or not — the height affects the space, never the time.

That framing makes the classic blow-up obvious rather than surprising. If the work at a node is itself a traversal — calling height() from every node, scanning an array to find a root, searching a subtree for a value — the total is O(n × h), which is O(n log n) if you are lucky about shape and O(n2) if you are not. Every such case in this article is repaired the same way: move the repeated computation into the return value, so the node receives it instead of recomputing it. When someone says a tree solution is "O(n) with the right return type", that is what they mean, and it is nearly always literally true.

9Diameter, and the elbow

The diameter of a tree is the number of edges on the longest path between any two nodes [33]. It is the first problem where the thing you want and the thing you can compose are different objects, and the resolution is the pattern that the next two sections both reuse.

Every path in a tree has a highest point — the vertex closest to the root, which is the lowest common ancestor of its two endpoints. The path descends from there into at most two subtrees. So classify the paths by their highest point, ask each node "what is the longest path whose highest point is me?", and the answer is height(left) + height(right). Taking a maximum over all nodes gives the diameter, and every path is considered exactly once because every path has exactly one highest point.

That is the record. The return is different: what the parent needs from this node is not a path bent at this node, which cannot be extended upward, but the longest path hanging downward from it, which can. Hence one function computing two quantities, one returned and one written to a variable that outlives the call.

Three variants follow immediately, and each is the same code with one substitution. Weighted diameter: replace "1 +" with "+ w(edge)" and the recursion is unchanged. Diameter of an n-ary tree: the record becomes the sum of the two largest child heights rather than left plus right, which is the smallest possible instance of the prefix/suffix problem in §20. And the diameter of a free (unrooted) tree can be found without any of this, by the two-sweep trick — breadth-first from any vertex to find the furthest vertex u, then breadth-first from u — which is correct precisely because of the unique-path property from §2, and is the standard example of a tree fact that has no analogue in general graphs.

The naive alternative — loop over all nodes, and for each one call a separate height() on its two children — is correct and costs O(n × h), which is O(n log n) on a balanced tree and O(n2) on the path from §7. The single-pass version is not a clever optimisation of it; it is the observation that height() was already being computed by the outer walk and thrown away.

10Binary tree maximum path sum

Now the same structure with values instead of edges, and negatives in the input [34]. A path is any sequence of nodes connected parent-to-child, going down and then up at most once; find the maximum sum.

Two quantities per node:

  • hang(v) = the best path that starts at v and descends into at most one child. This is what the parent can extend, so this is what is returned.
  • through(v) = v.val + max(hang(left),0) + max(hang(right),0), the best path whose highest point is v. This is a candidate answer, so this is what is recorded.

The clipping at zero is the second idea: a subtree whose best downward path is negative is simply refused, which is legal because a path may stop at v. Refusing is what makes the empty-subtree base case return 0 honestly.

The classic wrong answer is to return through instead of hang. It is worth being precise about why this is wrong, because "you return the wrong variable" undersells it: the returned number is a promise to the parent that a path with this sum can be extended upward through this node, and a bent path has already used both children, so the promise cannot be kept. The parent then constructs a "path" that visits some node twice.

The lab quantifies the damage over 20,000 random trees with values in [−9, 9]. Returning the bend produces a different answer from the truth in 47.5% of trials, and in 100% of those differences it overstates — the failure mode is always a phantom path, never a missed one. More striking, in 52.5% of trials the correct answer is not equal to any node's return value at all, and only 39.3% of the time is it recorded at the root. A solution structured to return the answer therefore cannot be patched; the answer is not in the return channel.

Across all trials, 12.0% of nodes had through > hang — the bend is rarely the winner locally, which is precisely why a solution that only checks the root's value passes small hand-written tests.

11Lowest common ancestor

Given two nodes p and q, find the deepest node that has both in its subtree [35]. The problem is old and much studied — Aho, Hopcroft and Ullman posed it in 1976 [36], Harel and Tarjan gave the first linear-preprocessing constant-query solution in 1984 [37], and it remains one of the most-reused primitives in competitive programming [38,39] — but the single-query version is four lines and belongs here, in the up channel.

The trick is that one pointer carries three different meanings depending on what is beneath it:

  1. nil — neither target is in my subtree.
  2. a pointer to p or q — exactly one target is below me, and here it is.
  3. a pointer to some other node — the answer has already been found below me, and here it is.

The node that receives a non-null result from both sides is by definition the deepest node with both targets beneath it, so it records the answer by returning itself. Because case 3 is passed upward unchanged, the answer survives to the root without a separate output variable.

Two preconditions are hiding in this code and both are worth stating out loud, because contest versions of the problem vary on them. First, it assumes both targets are present; if q is absent the function returns p, which is confidently wrong rather than detectably wrong. Fixing that requires the fatter return value — a count of targets found — which is what the lab's instrumented version uses. Second, it compares nodes by identity, not by value. In Rust that distinction is explicit and unavoidable: the listing uses Rc::ptr_eq, because two distinct nodes may hold the same integer and comparing values would find the wrong one [11].

A variant that shows the machinery generalising: find the lowest common ancestor of all the deepest leaves. Return a pair — the depth below this node, and the answer for this subtree — and combine by comparing the two child depths: if they are equal, this node is the answer for its subtree; otherwise the answer comes from the deeper side. Same walk, same post-order, fatter return value, and the pattern is the one from §3 rather than anything new about ancestors.

On a binary search tree the problem collapses: walk down from the root and the first node whose value lies between p and q is the answer, in O(h) with no recursion and no stack. This is the standard example of an invariant converting a search into a decision.

The single-pass version costs O(n) per query, which is fine for one query and ruinous for many. What to do about that is §21; it needs a different channel entirely.

Part IIIThe down channel

12Validate binary search tree

The problem that most cleanly isolates the downward channel [40]. Is this binary tree a binary search tree?

The tempting answer is to check, at each node, that the left child is smaller and the right child is larger. It is a correct check of something. It is not a correct check of this.

Three nodes are enough to break it, and the lab's search over 30,000 random trees found exactly that counterexample as its smallest: root 3, left child 2, and 6 hanging to the right of the 2. Every parent-child pair is correctly ordered. The tree is not a search tree, because 6 sits in the left subtree of 3 and 6 > 3. Across the whole corpus the local check falsely accepted 1,058 trees — 4.9% of every invalid tree present — with zero false rejections, which is the signature of a test that answers a different question rather than a weaker version of the right one.

The constraint a node must satisfy is not set by its children. It is set by its ancestors, and specifically by the open interval left over from every turn taken on the way down: go left and the upper bound becomes the parent's value, go right and the lower bound does.

Two implementation notes that cause real submissions to fail. Using INT_MIN and INT_MAX as the initial bounds breaks when the tree legitimately contains those values, which is why the listings use nullable bounds (*int, Integer, optional<int>, Option<i32>, int?, number | null) rather than sentinels. And the in-order alternative — walk in order, check the sequence is strictly ascending — is correct, elegant, and needs only the previous value as state, but it is O(h) in stack and it must compare against the previous visited value, not the previous parent.

The in-order framing pays for itself on the sibling problem: two nodes of a BST have been swapped, recover it without changing its structure. In-order, the sequence has either one descent (adjacent nodes swapped) or two (non-adjacent), and the answer is the first element of the first descent and the second element of the last one. Stated as a tree problem it is fiddly; stated as a problem about a nearly-sorted sequence it is four lines, and the translation is exactly the observation from §5 that in-order on a search tree is the sorted sequence.

A last remark on what "validate" is for. In a contest the tree is given and the question is a question. In production the same check is an assertion about an invariant that some other code is supposed to maintain, and the interesting failure is not that the check is wrong but that it is O(n) and therefore gets deleted from the hot path, at which point nothing is checking. That is an argument for making invariants unrepresentable — constructors that cannot build an invalid tree — rather than for making the checker faster.

One accounting note, because it is where "this is O(n)" stops being true. Enumerating paths is an output-sensitive problem: the traversal is linear, but the answers are not, and copying each recorded path costs its length. A perfect tree with n nodes has (n + 1)/2 leaves and each path is log n long, so in the worst case the copying alone is Θ(n log n) even though the walk is Θ(n). No implementation trick removes that; it is the size of what was asked for. The thing to check is that you are not paying it unnecessarily — a problem that asks only for the count of such paths, or for the best one, should never build the list.

14Variations on carried context

Four moves recur often enough to be worth naming as a group, because recognising which one a problem needs is most of the work of solving it.

Carry a bound. The node cannot decide alone; its ancestors constrain it. Validate BST is the archetype; so is "is this a valid heap", "is every node within k of its parent", and any problem where a global invariant is checked locally.

Carry an accumulator. The node's contribution is a function of the whole path above it. Sum-of-root-to-leaf-numbers, count-good-nodes, and path-sum are all this. The accumulator is a value if you only need the aggregate and a buffer if you need to report the path, and the difference is exactly whether an undo is required.

Carry a position. The node's identity in some external indexing scheme is derived from its parent's. Maximum width of a binary tree assigns index 2i and 2i + 1 to the children of i and measures each level's span [45]. The classic failure here is arithmetic rather than algorithmic: on a left-leaning tree of depth 60 the index overflows 64 bits long before the tree becomes large, and the standard fix is to re-base the indices at the start of every level.

Part IVThe frontier

15Level order

Breadth-first traversal is the one place in this article where the recursion is genuinely the wrong tool, because the state that has to be maintained is not a path from the root but a frontier: the set of nodes at the current distance. A stack cannot hold it; a queue can. The technique predates the trees literature and comes from maze routing and shortest paths [47,48], and it is the unweighted special case of Dijkstra's algorithm [49].

The problem statement asks for the nodes grouped by level [50], and the entire mechanism that produces the grouping is a single line: read the queue's length before expanding, then dequeue exactly that many.

Freezing the width is what separates one level from the next, because during the inner loop the queue contains the tail of the current level followed by the head of the next. Without the freeze you get a correct traversal with no level boundaries; with an extra sentinel value pushed between levels you get the same result more expensively; with a (node, depth) pair you get it again and pay a word per node. The length-freeze is the cheapest of the three and the only one that needs no extra memory at all.

Two implementation variants are worth knowing and one is worth avoiding. Holding a second array for the next level, and swapping at the end of each round, is exactly equivalent and reads more clearly in languages where dequeuing from the front of a list is O(n) — the TypeScript listing does this deliberately, since Array.shift is not a constant-time operation. Pushing a null sentinel between levels also works and costs an extra queue slot per level. What is worth avoiding is recursion with a depth parameter that appends into out[depth]: it is correct, and it is a depth-first traversal wearing a breadth-first interface, so it has the memory profile of the former and none of the early termination of the latter.

The memory question from §6 applies with full force. The queue's peak size is the tree's maximum width, which on a perfect tree with 131,071 nodes is 65,536 — half the tree resident at once, against 18 stack frames for the depth-first walk. Breadth-first is not the safe choice; it is a different choice.

The tokenisation deserves one paragraph of pedantry, because it is where working solutions break on the graders' harder inputs. Values may be negative, so a delimiter that is not a comma must not be a minus sign; values may be multi-digit, so a fixed-width character-per-node format is wrong; values may in principle be arbitrary strings, in which case the sentinel must be a token that cannot occur in the data, and length-prefixing is the honest answer. None of this is deep, and all of it is the difference between an encoding that round-trips and one that round-trips on the examples. The listing's round-trip assertion — serialize(deserialize(s)) == s — is the cheapest possible test and catches every one of these.

Third, level-order with sentinels is the format LeetCode itself uses to display trees, which is why it feels canonical. It is a perfectly good encoding and a worse decoder: rebuilding from it requires a queue and a pairing rule, where pre-order requires one cursor. Choose pre-order unless a grader forces otherwise.

18Reconstruction from two traversals

Given the pre-order and in-order sequences of a binary tree, rebuild it [55]. The problem is a good test of whether §5 landed, because the solution is a sentence: pre-order names the root, in-order counts how many nodes fall on each side of it.

The naive implementation scans the in-order array to locate the root at every step, which costs O(n2) on the path shape and is the intended trap; a hash map from value to in-order index fixes it. The second trap is subtler: the recursion must consume the pre-order array with a shared cursor rather than slicing it, because the number of nodes in the left subtree is known only from the in-order side, and passing slices around invites off-by-one errors that produce a valid tree with the wrong shape.

The precondition is the interesting part. The pair (pre-order, in-order) determines the tree only when the values are distinct. The lab measures what happens otherwise: over 4,000 random trees, reconstruction failed for 86.5% of the 1,900 trees containing a repeated value, and for 0 of the 2,100 with distinct values. This is not a bug that testing on random data will find reliably, and it is not a property of the code — it is a property of the data, and the only correct responses are to require distinctness or to use an encoding that does not depend on it, which is the argument for §17's sentinel format as the default.

The in-order plus post-order pairing works too, by symmetry: post-order names the root from its last element and in-order still counts the sides, so the same code runs with the pre-order cursor moving backwards and the children built right before left. Getting that order wrong is the standard way to produce a mirror image of the intended tree and pass exactly the symmetric test cases.

Two related facts worth carrying: pre-order plus post-order does not determine a binary tree (it cannot distinguish a single left child from a single right child) though it does determine a full binary tree; and for a binary search tree, pre-order alone is sufficient, because in-order is recoverable by sorting.

19In-order without a stack

In-order traversal is the standard vehicle for this question [56], and there are two ways to remove the recursion, with quite different costs.

The first is mechanical: replace the call stack with an explicit stack of nodes. Push the entire left spine, pop, visit, turn right, repeat. The memory moves from the (small, fixed, fatal-on-overflow) call stack to the (large, growable, measurable) heap, which is the whole point — and it is usually the right answer for production code operating on attacker-influenced input, per §7.

The conversion is mechanical for pre-order and in-order and genuinely awkward for post-order, and the reason is the subject of this whole article: a post-order visit needs to know that it has already returned from both children, which is state the call stack was keeping for free. The three standard remedies are a visited flag per stack entry (which is what the lab's instrumented walks use), a second stack producing reversed root-right-left order (short, and it changes the output order rather than the traversal), or the last-visited-node pointer (constant extra space, and the one people get wrong). If a conversion feels harder than it should, check whether the order you need is post-order; that is almost always the explanation.

The second removes the auxiliary memory entirely. Knuth posed the problem of traversing in order with no stack, no tag bits and the tree unaltered at the end [57]; Morris answered it in 1979 [58]. Each node's in-order predecessor is temporarily threaded to point back at it, the thread is followed once, and then cut — a descendant of the threaded-list representation of Perlis and Thornton [59] and a cousin of the pointer-reversal technique used by Schorr and Waite for garbage collection [60,61,62].

Part VBeyond one pass

20When the subtree is not enough

Every problem so far has had an answer that a node could compute from its own subtree plus what its ancestors chose to tell it. Now take a problem where it cannot: for every node, the sum of distances to all other nodes [64].

A post-order pass gives each node the sum of distances within its own subtree. The lab's verdict on that pass is blunt: on a random tree with 2,000 nodes, the number of nodes whose answer is correct after pass 1 is 1 — the root, whose subtree happens to be the whole tree. The mean shortfall over all nodes is 99.8%. This is not a pass that nearly works.

The observation that rescues it: everything a child cannot see is exactly what its parent already knows. Move the root from a parent p to a child c and every node inside c's subtree gets one step closer while every node outside gets one step further away, so

ans[c] = ans[p] - size[c] + (n - size[c])

and a second pass in pre-order propagates the finished answer downward, each child taking one arithmetic step from its parent. Two linear passes in opposite directions.

This pattern is called rerooting and it generalises far beyond this problem [65,66]. The recipe: define a subtree aggregate that composes associatively; compute it upward; then, for each node, compute the aggregate of "the tree with this node's subtree removed" from the parent's finished value and hand it down. When the aggregate is not invertible — a maximum, for instance, where you cannot subtract a child's contribution — the standard remedy is prefix and suffix aggregates over each node's child list, which keeps the whole thing linear.

The non-invertible case is worth spelling out, because it is where people abandon the technique. Suppose the aggregate is a maximum over children rather than a sum — the height of the tree seen from each node, say. Pass 2 needs "the best among my parent's other children", and you cannot subtract my contribution from a maximum. The fix is to compute, for each node's child list, the prefix maxima and the suffix maxima; then the best excluding child i is max(prefix[i-1], suffix[i+1]), available in O(1) after O(deg) preprocessing per node, and Σdeg = 2(n − 1), so the whole thing is still linear. This one pattern covers most rerooting problems that are not sums: maxima, minima, second-best, and any monoid without inverses.

Note the listing is iterative in all six languages. That is deliberate: rerooting is the technique you reach for on large trees, large trees are where §7 bites, and a solution whose entire selling point is linearity should not fail on a path.

21Ancestors in logarithmic time

The §11 solution to lowest common ancestor costs O(n) per query. For a single query that is optimal — you cannot do better than looking at the tree. For 200,000 queries on a 200,000-node tree it is 4×1010 operations and a wrong answer in every sense that matters.

The fix is to spend time once so that each query is cheap. The simplest version worth knowing is binary lifting: store, for every node v and every k, the 2k-th ancestor of v. Any climb of d steps is then the binary expansion of d, at most log n jumps [67,38].

The memory cost is the honest drawback: n log n words, which at n = 2×105 is about 3.6 million integers — fine, but not free, and the reason the Euler-tour approach is preferred when only LCA is needed.

Binary lifting is not the theoretical end of the line. Euler tour plus a range-minimum structure gives O(n log n) preprocessing with O(1) queries, or O(n)/O(1) with the Bender–Farach-Colton method [68,69], which descends from Harel and Tarjan's original linear-preprocessing result [37,70] and from the equivalence between LCA and range-minimum queries [71,72,73]. If the queries are all known in advance, Tarjan's offline algorithm answers them in near-linear total time using union-find [74,75]. Binary lifting is nonetheless the one to reach for first: it is twenty lines, it also answers "k-th ancestor" directly, and it extends to path aggregates by storing a combined value alongside each jump.

22The competitive-programming toolkit

Beyond the classics, a handful of techniques come up often enough that recognising the shape is worth more than remembering the code. Each is a different answer to "my subtree summary is not enough".

Euler tour: a subtree is an interval. Record entry and exit times in a depth-first walk and the subtree of v becomes the contiguous range [tin[v], tout[v]). Every subtree query — sum, minimum, count — is now a range query on an array, answerable with a Fenwick tree [76] or a segment tree, and "is u an ancestor of v" becomes an interval containment test. This is the single highest-leverage transformation in the list: it converts tree problems into array problems, where the toolbox is much larger. The same tour underlies the LCA-to-RMQ reduction [77,68].

Heavy-light decomposition: a path is O(log n) intervals. Split the edges into heavy (to the largest child) and light, and any root-to-node path crosses at most log n light edges. Path queries and updates then reduce to a logarithmic number of range operations on the same array. The decomposition comes from Sleator and Tarjan's dynamic trees [78,79], and link-cut trees are the fully dynamic version of the same idea [80].

Small-to-large merging. When each node must merge sets from its children, always merge the smaller into the larger. Each element moves only when the set containing it at least doubles, so it moves at most log n times and the total is O(n log n) — the same amortised argument as union by size [75]. The specialised form for subtree queries with no updates is known as DSU on tree.

Centroid decomposition. A centroid is a node whose removal leaves no component larger than n/2; recursing on the pieces gives a decomposition of depth log n, and any path in the tree passes through the centroid of exactly one level. That turns "count paths with property P" into a sequence of independent problems about paths through a fixed vertex [38,39].

Tree DP. Nothing more than the up channel with a vector instead of a scalar: for each node, an answer for each state. House robber III is the two-state case — taken and free — and the reason it is instructive is that returning one number instead of two forces the parent to re-examine its grandchildren, which is how a linear algorithm becomes exponential [81].

23N-ary trees and graphs that are trees

Almost everything above generalises from two children to a child list with no change of substance. maxDepth becomes a maximum over a loop; the down channel is unchanged; the up channel folds a list instead of two values. The lab's rerooting listing is already written this way, over an adjacency list rather than left and right pointers, because the problems that motivate rerooting are naturally n-ary.

Three differences are real and worth stating.

First, the null child disappears. The n+1 sentinel count of §4 is specific to a fixed arity; a child list has no empty slots, so the call count drops to exactly n and serialisation needs an explicit child count or a closing delimiter instead of a null marker.

Second, the parent must be excluded by hand. Given an undirected adjacency list, the recursion is over neighbours, and one of them is the node you came from. Passing the parent down and skipping it is the standard device; it is O(1) and correct on any tree. Using a visited set instead is also correct, costs more, and is the honest choice only when the input is not guaranteed acyclic — which is the point at which you are no longer working on a tree at all [1,82].

Third, the aggregate must be associative in the child order or the answer becomes order-dependent. This matters for rerooting: removing one child's contribution from a fold is easy for a sum and impossible for a maximum, which is why the prefix/suffix trick from §20 exists.

Serialising an n-ary tree is the clearest illustration of the first difference. With no null slots to mark, the encoder must record arity some other way: either the child count before the children, or an explicit closing delimiter after them — which is to say, either a length prefix or balanced parentheses, the same two options every wire format has ever had. Both round-trip with a single cursor, exactly as in §17; the sentinel trick is the one thing that does not survive the generalisation, because it was never about nulls but about a fixed number of slots per node.

The wider context is that a tree is the shape a graph search leaves behind. Depth-first search on any graph induces a DFS tree, and the classical graph algorithms — bridges, articulation points, strongly connected components — are statements about back edges relative to that tree [1]. The habit of asking "what travels up, what travels down" is exactly the habit those algorithms require: Tarjan's low value is a subtree summary in the up channel, and the entry time it is compared against is context in the down channel.

24Where the recursion is the wrong tool

A catalogue of cases where the natural approach in this article should be abandoned, because knowing when a technique stops applying is most of knowing the technique.

When the depth is attacker-controlled. Per §7: a recursive parser, validator or serialiser over untrusted nested input is a denial-of-service vector, and the fix is an explicit stack with an explicit depth limit, not a bigger stack [22].

When the tree is a list. If the structure is guaranteed to be a path, every algorithm here is a loop with extra steps. This sounds like a joke and is a real failure mode: sorted insertion into an unbalanced BST produces exactly this, and the resulting O(n) operations are often blamed on the algorithm rather than the construction. The remedy is a balanced structure — AVL [83], red-black [84], treap [85], splay [86] — or an entirely different one, a skip list [87] or a B-tree if the data does not fit in memory [88].

When the question is about an interval, not a subtree. If every query is a range on an array, building a tree over the array (segment tree, Fenwick tree) is right, but walking a tree that exists in the input is not. Recognising which of the two you have is the distinction between "there is a tree in this problem" and "a tree is a good index for this problem".

When breadth-first stops earlier. Minimum depth, nearest marked node, shortest path in an unweighted tree: the recursion visits every node and the queue stops at the answer.

When the answer is a global aggregate over pairs. Sum of all pairwise distances, number of paths with a given property — these want centroid decomposition or rerooting, not a single traversal, and attempting them with one pass produces the quadratic solutions §20 measured.

When the tree is enormous and the query is one value. Counting nodes in a complete tree in O(log2 n) by comparing spine heights beats a full traversal by orders of magnitude [89], and the same instinct — can I answer this without looking at everything? — applies whenever the tree carries a structural promise.

When the tree changes between queries. Everything preprocessed in §21 and §22 assumes a static tree. Under insertions, deletions or re-rootings the tables are invalidated and rebuilding them per update is worse than not having them; that is the problem link-cut trees and Euler-tour trees exist to solve [78], and it is a much larger commitment than anything else in this article.

When the recursion is a fiction. If the "tree" is a DAG with shared subtrees, a recursive walk visits shared nodes once per path and the cost becomes exponential. Memoising on node identity fixes it; failing to notice does not.

25How to recognise which problem you have

A procedure, in the order the questions are worth asking. It is deliberately mechanical, because under contest conditions the failure is almost never that the recursion was too hard to write.

1. Can a node answer for itself given only its subtree? If yes, you need only the up channel: write the post-order recursion and decide what the return type must be. If the parent has to recompute anything the child already knew, widen the return type until it does not — a pair, a tuple, a small struct. That is the fix for balanced-tree checks, largest-BST-subtree and every tree DP.

2. Does the node need something only its ancestors know? Then it goes in the argument list: a bound, an accumulator, a position, a counter. If it is a mutable buffer, the undo is mandatory and the copy at the recording site is mandatory.

3. Is the thing you want composable? If the quantity you are asked for cannot be extended upward — a path that bends, a pair that meets — then it is recorded, not returned, and something else is returned. Ask: what would my parent be able to use? Diameter, maximum path sum and LCA all fall out of that one question.

4. Does the answer depend on the rest of the tree? If node v's answer involves nodes outside v's subtree, no single pass suffices. Two passes: up for subtree aggregates, down to hand each child the outside. If the aggregate is not invertible, prefix and suffix folds over the child list.

5. How many queries? One query means the single pass is optimal. Many queries mean preprocessing: Euler tour for subtree ranges, binary lifting for ancestors, heavy-light for paths. The lab's break-even was 17 queries; the threshold is always low.

None of this is specific to contests; the same six questions organise tree code in compilers, query planners and file systems, and both Skiena and Sedgewick present the material in that spirit [90,91].

6. What is the worst-case height? If it is not logarithmic by construction, decide deliberately whether to recurse. This question is asked last and should be asked first.

26What to take away

The recursion is three lines and it is the same three lines in every problem in this article and in every language it is written in. What varies is small, finite and enumerable: what the parent tells the child, what the child tells the parent, where the answer is written down, and whether one pass is enough.

The claims worth keeping, each of them measured rather than asserted:

  • More than half the calls in a naive binary-tree recursion are on empty subtrees — exactly n+1 of 2n+1 — and that count is also the size of every sentinel-based encoding.
  • Depth-first and breadth-first have inverse memory profiles, spanning five orders of magnitude across the same node count, so the choice is a claim about the shape of the input.
  • "Random tree" names two different laws, logarithmic and square-root in height, and the 1,000-frame stack budget they imply differs by a factor of 234 in the lab and without bound in general.
  • The plausible local test for a binary search tree accepts 4.9% of invalid trees, and is broken by three nodes.
  • In more than half of random trials, the maximum path sum equals no node's return value, so a solution shaped to return the answer cannot be repaired.
  • After one upward pass of a rerooting problem, 1 node in 2,000 has the right answer; one line of arithmetic in a second pass fixes the other 1,999 and turns a quadratic algorithm into a linear one.
  • Preprocessing for ancestor queries pays for itself after 17 queries, and removes the dependence on height that made the simple solution fragile.

The last one generalises past trees. Nearly every technique in Part V is the same bargain: pay a linear pass to convert a question about a shape into a question about an array, because the array is where the tools are. The tree-shaped part is the easy part. Knowing which part of a problem is the tree-shaped part is the skill.

EXPERIMENT 4: maximum path sum: the value you return is not the answer
==============================================================================

At each node the recursion computes two different quantities:
  RETURN  = best path that goes DOWN from this node into one child
  RECORD  = best path that BENDS at this node (left + node + right)
The answer is the maximum RECORD anywhere.  A solution that returns the
bend is wrong, because a bent path cannot be extended by the parent.


over 20000 random trees of 4-24 nodes with values in [-9,9]
------------------------------------------------------------------------------
nodes where RECORD > RETURN            : 33424 of 279677 (12.0%)
trials where the answer is NOT equal to any node's RETURN : 10491 (52.5%)
trials where the answer is recorded at the root           : 7869 (39.3%)
trials where 'return the bend' differs from the truth     : 9496 (47.5%)
  ... of which it OVERSTATES the answer                   : 9496 (100.0% of the differences)

The bug is not that the wrong number is returned to the caller.  The
bug is that the returned number is a promise the parent cannot keep:
the parent will try to extend a path that already used both children.

EXPERIMENT 6: when one pass up is not enough: rerooting

'Sum of distances from every node to every other node.'  A post-order pass

random rooted tree, n=2000

method                          operations    per node
