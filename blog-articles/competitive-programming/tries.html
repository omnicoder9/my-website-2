A question a hash table cannot answer

Type three letters into a search box and something has to decide, in the time between your keystrokes, which of several million strings begin with those three letters. This is not the question a hash table answers. A hash table answers is this exact key present, and it answers it beautifully, in expected constant time, by taking the key apart and scattering it. Scattering is the point: a good hash function is one whose output tells you nothing about its input, so that keys which look alike do not collide. car and card land in unrelated buckets by design.

Which means that after you have built the hash table, the fact that car is a prefix of card is gone. It was destroyed on purpose, and there is no way to get it back except by reading every key. That is the whole motivation for the structure this article is about, and it is worth stating plainly before any code appears, because most of the mistakes people make with tries come from reaching for one when the question they actually have is is this key present.

A trie is what you get if you refuse to destroy that information. Instead of storing a key somewhere, you spend the key: one character buys one edge, and the key is consumed walking down from the root. When the key runs out you plant a flag. Nothing anywhere in the structure holds the string card. The string is the route you took.[1, 2]

Everything else follows from that one decision, in both directions. The good follows: a prefix query is just a walk that stops early, so it costs what the prefix costs and not what the dictionary costs; the keys come out in sorted order if you visit children in order, because the tree is a lexicographic ordering; and the longest key that prefixes some input is found by walking the input and remembering the last flag you passed. The bad follows too: you now pay for a node per distinct prefix rather than a slot per key, every lookup is a chain of dependent pointer dereferences rather than one indexed load, and the structure's memory behaviour is a fight you will have to have with your allocator and your cache.[3]

The claim this article defends is narrower and more useful than “tries are good for prefixes”. It is this: every classic trie problem is the same trie. What differs between Implement Trie and Word Search II and Maximum XOR of Two Numbers is not the data structure. It is two decisions, made independently: what you hang on a node besides its children, and how you walk. Once you can read a problem statement and answer those two questions, the code writes itself, in any language, and the half-dozen interview problems that get filed under “trie” collapse into about five patterns.

To make that concrete before the argument starts: the same structure that answers autocomplete is, in 2026, what a large language model server uses to avoid recomputing the attention cache for a system prompt it has already seen. SGLang's RadixAttention keys a radix tree by token sequence, so that requests sharing a prefix share the computed key-value tensors, and evicts least-recently-used leaves first so that common ancestors survive.[4] The tokens are integers rather than letters and the payload is a GPU tensor rather than a boolean, but the walk is the walk from Figure 1, and it is the walk from 1959.

What a trie is, exactly

A trie over an alphabet Σ is a rooted tree in which every edge is labelled with a symbol of Σ, no node has two out-edges with the same label, and some nodes are marked terminal. The key represented by a node is the concatenation of the edge labels from the root to it. The set of keys stored is the set of paths ending at terminal nodes. The root represents the empty string.

Three invariants come out of that definition, and every implementation in this article maintains them without ever saying so:

  • The path is the key. There is no field anywhere holding a key. If you want to print the keys you must reconstruct them by remembering the edges you walked, or by hanging the string on the terminal node as a payload, which is a choice with a cost.
  • Terminal and internal are independent. A node can be terminal and still have children (car inside card). A node can be internal and not terminal (ca). Forgetting this is the single most common trie bug: search("appl") must return false even though the path exists, and the only thing that distinguishes it from search("apple") is the flag.
  • Sibling order is the alphabet order. If you enumerate children in symbol order you enumerate keys in lexicographic order, for free. This is what a hash table cannot do and a B-tree does differently.[5]

The payload slot is where the interesting engineering lives, so it is worth naming the standard occupants now. For a plain dictionary the slot is empty. For Word Search II it holds the matched word so that you can emit it without reconstructing the path. For Map Sum Pairs it holds the sum of every value in the subtree beneath it, maintained on insert. For an autocomplete engine it holds a bounded list of the highest-scoring keys below. For Aho–Corasick it holds a pointer to another node entirely. The children map and the terminal bit never change.

The cost model, honestly stated

The standard claim is that a trie's operations are O(L) in the length of the key and independent of the number of keys n. That is true and it is the reason to use one, but it is worth being precise about what it is being compared against, because the comparison is usually made against the wrong thing.

Against a hash table, O(L) is not a win: hashing the key also reads all L characters, so both are O(L), and the hash table then does one indexed load while the trie does L dependent loads. On exact lookup a well-tuned hash table beats a trie, essentially always, and by a lot. The trie's independence from n matters against structures whose cost genuinely does grow with n: a sorted array with binary search costs O(L log n) character comparisons in the worst case, and a B-tree the same. It also matters when the comparison is against no structure at all, which is the honest baseline for prefix queries, because without a trie the fallback is to scan.

measured, not asserted

Over a 63,875-word English dictionary, a prefix query takes a mean of 3.11 edge traversals — it is asking about a prefix, and prefixes are short. Binary search over the same keys takes about 16 probes, each of which is a string comparison. A linear scan takes 63,875 string comparisons. The trie's number does not change when the dictionary doubles; the other two do. Full method and output in §23.

Where it came from, and what the name means

René de la Briandais described the structure in 1959, at the Western Joint Computer Conference, as a solution to a file-search problem with variable-length keys: rather than compare whole keys, walk them symbol by symbol through a tree of linked sibling lists.[6] The linked-list node he used is not a footnote — it is one of the two node layouts still in competition sixty-seven years later, and the article's fifth section is largely about the other one.

Edward Fredkin named it the following year in Communications of the ACM, taking the syllable from retrieval, which is why the word is properly pronounced “tree” and why almost nobody does, since saying “tree” for a thing that is a tree defeats the purpose of having said anything.[1] Fredkin's paper is worth reading for a reason unrelated to naming: he was designing a memory, not a library data structure, and the cost model he worries about — how many words of core does a node consume, how many are wasted — is exactly the cost model that ART and HAT-tries revisit in the 2000s and 2010s.

Donald Morrison's PATRICIA followed in 1968, with the observation that in a trie over real data most nodes have exactly one child, so most nodes are doing no work: collapse each chain into a single edge labelled with a string rather than a symbol.[7] We measure that claim in §16; on English it removes 45.6% of nodes. Aho and Corasick added failure links in 1975 and turned the trie into a finite automaton that matches many patterns in one pass over the text.[8] Bentley and Sedgewick proposed the ternary search tree in 1997 as an explicit compromise between the trie's array node and a binary search tree.[9] Knuth's treatment in The Art of Computer Programming volume 3, section 6.3, remains the reference for the analysis.[2]

The pattern in that timeline is worth naming. Nobody has improved the trie since 1959, because there is nothing to improve: the definition is forced once you decide the key is the path. What every subsequent contribution does is change the representation of a node — collapse it, shrink it, make it adaptive, make it succinct, make it cache-resident, make it hashable — while leaving the walk untouched. That is a useful thing to know when reading a new paper with “trie” in the title.

Implement Trie: the whole idea in forty lines

The canonical exercise[10] asks for three operations: insert(word), search(word), and startsWith(prefix). Almost everyone writes all three separately. They are one function with three endings.

The function is walk: follow one edge per character, and return the node you land on, or nothing if an edge is missing. Then search is walk and check the flag, startsWith is walk and check you arrived, and insert is walk, creating the missing edges as you go. Writing it this way is not a stylistic preference. It is the difference between a trie you can extend to the next twelve problems and three functions that happen to look similar.

Some notes that apply across all six versions. The node type has no “is root” flag, because the root is not special: it is the node reached by the empty string, and treating it as a normal node is what makes startsWith("") correctly return true. The children array is indexed by ch - 'a', which is a real constraint and not just an exercise convenience — §21 discusses what happens when the alphabet is Unicode rather than twenty-six letters. Rust's version uses get_or_insert_with and the walk returns Option<&Trie>, so the “stop at the missing edge” behaviour is expressed by the ? operator rather than an early return; that is the same algorithm wearing the local idiom.

Complexity: insert and both queries are O(L) time with L the length of the argument, and insert allocates at most L nodes. No operation looks at the number of keys stored. Deletion is the one operation the exercise omits and the one people get wrong: clearing the terminal flag is correct but leaks the path, and removing the path is only safe as far up as the first node that has another child or is itself terminal. Most production tries never delete, or delete lazily, for exactly this reason.

What a node costs

The array of twenty-six pointers in Listing 1 is the version everyone writes first and nobody ships. To see why, it helps to measure rather than assert, so the numbers below come from building a trie over the 63,875 lowercase words in the standard American English word list and counting.

First, how many nodes there are. 63,875 keys totalling 528,877 characters produce 145,250 nodes. That is 2.27 nodes per key, against 8.28 characters per key: 72.5% of the characters in the dictionary are absorbed by sharing. But the aggregate hides the more interesting fact, which is how that ratio moves as the dictionary fills up.

This is the property that makes tries scale on natural-language-like data and fail on random data: the marginal key is cheap only to the extent that the corpus repeats itself. A dictionary of random 16-character strings gets no sharing below depth three or four and the trie degenerates into an expensive linked representation of the strings. Whenever you are deciding whether a trie is worth it, the question to ask is not “how many keys” but “how much do the keys agree”.

The fan-out is tiny, and that is the whole problem

Second, how many children each node has. If nodes routinely used most of an alphabet, a dense array would be the right representation and there would be no literature. They do not.

Two independent optimisations fall out of that histogram, and they are the two great families of trie engineering. The 53% of nodes with exactly one child are pure overhead and can be collapsed into their parent's edge — that is PATRICIA, and it is §16. The remaining nodes mostly have two, three or four children, so a representation that can be small when the fan-out is small is worth a great deal — that is the adaptive radix tree, and it is the reason DuckDB's index is what it is.[11, 12]

The layouts, in the order the field arrived at them:

  • Dense array. One pointer slot per symbol. O(1) child lookup, no comparisons, catastrophic waste. Correct for small alphabets — a binary trie over bits has two slots and wastes nothing, which is why §12 uses one without apology.
  • Linked or sorted list of (symbol, pointer) pairs. De la Briandais's original.[6] Size proportional to actual fan-out; child lookup is a scan or a small binary search. Cheap in memory, worse in cache behaviour when fan-out is large.
  • Bitmap plus packed pointers. A 32-bit (or 256-bit) mask of which symbols exist, plus a dense array of only the pointers that do; the index of a child is the population count of the mask below its bit. This is Bagwell's hash-array-mapped trie applied to a symbol alphabet[13] and it is close to optimal for space at one popcount per level.
  • Adaptive node classes. ART keeps four node types — for up to 4, 16, 48 and 256 children — and promotes a node when it outgrows its class.[11] The Node4 and Node16 layouts hold their keys in a sorted byte array that fits a single cache line and can be searched with SIMD; Node48 uses a 256-byte index into 48 pointers; Node256 is the dense array. Because 98.7% of nodes in our census have four children or fewer, almost every node in a real workload is a Node4.
  • Succinct. Encode the tree shape as a bit vector — LOUDS or a balanced-parentheses sequence — with rank/select structures for navigation, reaching within a constant factor of the information-theoretic minimum.[14, 15, 16] Static, hard to update, and unbeatable when the dictionary is fixed and large. SuRF applies this to range filtering in LSM-tree storage engines.[17]

a caveat about the byte counts

The figures above are an allocation model, not a measurement of a running heap: they assume 8-byte pointers and a 16-byte header per node and ignore allocator rounding, which in a real runtime can add 20–50% and which managed runtimes account for differently again. The ratios between layouts are robust; the absolute megabytes are indicative. The one number that is not modelled at all is the one that usually decides the benchmark, which is cache misses per lookup: a trie walk is a chain of dependent loads, so its latency is governed by how many of those loads miss, and that is precisely what burst tries, HAT-tries and ART's cache-line-sized nodes are designed to reduce.[3, 18, 19]

For the rest of the article the listings keep the dense array, because it makes the algorithm legible and because on a 26-letter alphabet with a few thousand keys it is genuinely fine. Every one of them can be converted to a hash map node by replacing two lines, and to an ART node by replacing the node type and nothing else. That is the point of keeping the walk separate from the representation.

Add and Search Words: when the walk forks

The second canonical problem[20] adds one thing to the dictionary: a search pattern may contain ., which matches any single character. This is the smallest possible change to the interface and it changes the shape of the walk completely.

Up to now the walk has been forced: at each character there is exactly one edge you are allowed to take, and if it is missing you are done. A wildcard removes the constraint. At a . you must try every child, and each of those is a separate search of the remaining pattern. The walk becomes a depth-first search with backtracking, and the natural expression is a loop that turns into a recursion exactly at the positions where the choice is not forced.

The complexity is where this problem earns its place. With no wildcards the search is O(L). With w wildcards it is O(26w · L) in the worst case, but that bound is so pessimistic as to be misleading, because the branching factor at a real node is not 26 — it is 1.43 on average, and it depends sharply on where in the key the wildcard sits. Near the root almost every letter exists; near a leaf almost none do.

The practical consequence, if you are ever tempted to build a wildcard search on a trie for real: patterns anchored at the front are cheap and patterns anchored at the back are not, so if your users' patterns are of the form *ing rather than runn*, you should be indexing the reversed keys. That trick recurs often enough that §13 is about it.

The same branching walk, with a different acceptance test at each step, gives you approximate matching. Keep a row of a Levenshtein dynamic-programming table at each node, extend it by one character per edge, and prune the subtree whenever the row's minimum exceeds your edit budget; the trie's shared prefixes mean the shared part of the DP table is computed once for all keys beneath.[21] This is how a spell-checker with a million-word lexicon answers in microseconds.

Word Search II: driving the trie from outside

Given a grid of letters and a list of words, return every word that can be spelled by a path of orthogonally adjacent cells without reusing a cell.[22] The naive solution is to run a grid DFS once per word, which is correct and, on adversarial input, hopeless. The trie solution inverts the loop: walk the grid once, and carry a trie node along with the path, so that the dictionary is consulted at every step rather than at the end.

This is the third walk shape, and the most important one to internalise because it generalises far beyond grids: the trie is not being searched, it is being offered characters by an external process, and its job is to say no as early as possible. Any search whose state includes a growing string — a board path, a stack of tiles, a sequence of moves — can carry a trie node beside that string and get its pruning for free.

Three implementation details in Listing 3 are worth pulling out, because each of them is a pattern in its own right.

Store the word at the terminal. The alternative is to accumulate the path in a string builder as you descend, which costs an append and a pop at every cell. Hanging the string on the node trades a few kilobytes of memory for that entire class of work, and it is the first appearance of the payload slot doing something real.

Clear it once emitted. The board may spell the same word by several routes. Setting the payload to null after the first emission deduplicates without a set, in O(1), and does so correctly because the node is unique to the word.

Unlink dead subtrees. After exploring a node, if it has no children and no word, nothing beneath it can ever match again; cutting it from its parent means every future path that reaches the parent will be refused one step earlier. This is the part most solutions skip, and the measured effect of skipping it is not small.

the pruning result, including the part that is uncomfortable

On a 12×12 board of English-frequency letters against a 3,000-word dictionary, the trie-driven search takes 3,136 DFS calls against the naive solution's 528,375 — a 168× reduction. Pruning dead subtrees removes a further 1.0%, which is nothing.

On a 10×10 board of nothing but a, against a dictionary of the ten words a, aa, …, aaaaaaaaaa, the naive search takes 55 calls, because every word matches immediately at the first cell. The trie-driven search without pruning takes 4,409,236, because it dutifully explores every self-avoiding path in the grid. With pruning it takes 140.

The trie made the problem 80,000× worse until the pruning was added. It is not a decoration on the technique; on the input the technique is sold for, it is the technique.

There is a third scenario in the lab worth knowing about, because it shows the limit. Add ten more words to that dictionary — ab, aab, and so on — and the pruning stops firing entirely: the search never enters the b branches, because the board contains no b, so those nodes are never emptied and their parents never become dead. The cost goes back to 4.4 million calls. Pruning only removes what you have already exhausted, which means it protects you against a dictionary you have consumed and not against one you have merely failed to enter.

Longest Common Prefix: the forced descent

Find the longest string that prefixes every member of an array.[23] The right answer in production is not a trie: scan the first string character by character, comparing against every other string, and stop at the first disagreement. That is O(total characters) time and O(1) space, and it is what you should write.

The trie solution is O(total characters) time and O(total characters) space, which is strictly worse. It is in this article anyway, for two reasons. The first is that it makes the structural claim visible: the longest common prefix of a set of keys is, in a trie, the path from the root that is forced — you descend while there is exactly one child and no word has ended, and where you stop is the answer. The second is that the walk generalises where the linear scan does not. If the question becomes “longest common prefix of these three keys out of the million I have indexed”, or “the deepest node with at least k keys below it”, the trie already holds the answer and the scan has to start over.

The terminal check is the part people get wrong. Given ["ab", "abc"] the answer is "ab", and the node for ab has exactly one child, so a loop that only tests the child count walks straight past it and returns "abc". A key that ends is a key that stops agreeing.

Replace Words: stop at the first terminal

Given a dictionary of roots and a sentence, replace every word by the shortest root that is a prefix of it, leaving the word alone if no root applies.[24] cattle becomes cat; rattled becomes rat.

This is the forced descent again, with one addition that turns out to be the single most reusable line in the whole article: check the terminal flag on the way down, and return the first time it is set. Because the walk visits prefixes in order of increasing length, the first terminal you meet is the shortest root, and you are finished. Do not walk to the end of the word and work backwards.

Change “return at the first terminal” to “remember the last terminal and keep going” and the same walk answers the longest-matching-prefix question instead, which is a considerably more important problem than a word-replacement puzzle. It is how an IP router picks a route: the forwarding table is a set of address prefixes of varying length and the rule is that the most specific match wins, so the lookup is a walk down a binary trie over address bits, remembering the deepest prefix passed.[25] Serious implementations do not walk one bit at a time — they expand the trie to consume several bits per level, trading memory for depth in exactly the way §19 describes[26] — or compress the whole structure into a few cache lines so that a lookup table for the global routing table fits in a processor's cache.[27, 28] It is also how a URL router matches /api/v2/users/:id, how a filesystem resolves a mount point, and how a tokeniser finds the longest matching token.

Map Sum Pairs: put the answer on the path

Support insert(key, value) and sum(prefix), where the sum is over the values of every key with that prefix, and re-inserting a key overwrites its value rather than adding to it.[29]

The obvious implementation walks to the prefix node and then traverses the whole subtree adding up terminal values, which is O(size of the subtree) per query and can be the entire dictionary. The good implementation notices that the query is always about a subtree, and that a subtree is exactly the set of nodes on the paths through it, so the aggregate can be maintained incrementally on insert: each node stores the sum of everything below it, and an insert adds the delta to every node on the key's path. Query becomes a walk.

The delta is the subtle part. If you add val to each node on the path, a second insert of the same key double-counts. Keeping a plain map from key to current value at the root, and propagating val - previous, makes the operation idempotent in the way the specification demands. That map is a genuine extra structure, and it is sometimes worth avoiding by storing the previous value at the terminal node instead — the same information, one fewer hash table.

This is the second great pattern and the one that unlocks the largest number of problems. Anything that is a decomposable aggregate over a set of keys can be hung on the path: a count, a sum, a maximum, a minimum, a bitmask of which keys are present, a Bloom filter of the subtree[30], a bounded list of the best keys below. What all of these share is that the value at a node can be computed from the values at its children, which is what makes maintenance on insert O(L) rather than O(subtree).

the one thing that does not decompose

Deletion. A count decrements cleanly, and so does a sum, but a maximum does not: removing the maximum key from a subtree requires knowing the second largest, which the node did not store. If a payload must survive deletion, it has to be either a multiset, or recomputable from children on the way back up, or you accept a rebuild. This is the same problem that makes maintaining top-k lists on a mutable trie annoying, and the usual answer is to rebuild the affected path's lists from the children on the return leg of the insert.

Autocomplete, prefix counts and top-k

The problem the trie was invented for, in its modern form: as the user types, return the three highest-ranked completions of what they have typed so far.[31] It is Plate 6 with a different aggregate, and the interesting part is choosing which.

There are three implementations, in increasing order of how much work you move from query time to insert time.

Walk and collect. Descend to the prefix node, then DFS its subtree collecting terminals until you have k. If children are visited in symbol order and the ranking is lexicographic, this is optimal: the first k terminals you meet are the answer, and you touch O(k · L) nodes. This is the correct answer to the standard exercise, whose ranking is lexicographic precisely so that this works.

Sort once, collect the first k. If the ranking is by frequency or score rather than alphabet, sorting the dictionary by rank before insertion and appending each key to a bounded list at every node on its path gives O(1) query: the list at each node is already the top-k for that subtree, because keys were offered in rank order. Insert cost rises to O(L · k) and the memory cost is k pointers per node, which for k=10 over 145,250 nodes is real but not prohibitive.

Maintain a heap or a sorted list per node. Necessary when scores change at runtime — a search engine's completion ranking is not static. This is where the aggregate stops decomposing cleanly and you start rebuilding node lists from children on the return leg of an update.

Related aggregates that ride the same machinery: the count of keys under a prefix (increment on insert, one integer per node); the sum of prefix scores[32], where the score of a key is the sum over its prefixes of how many keys share that prefix, answered by keeping a visit counter at each node and summing the counters along the key's path; and the longest word in the dictionary buildable one character at a time[33], which is a DFS that refuses to descend through a non-terminal node.

The production versions of this are worth knowing about because they diverge from the textbook shape. Lucene stores its terms dictionary as a finite state transducer rather than a trie: it shares suffixes as well as prefixes, which turns the tree into a DAG and buys a large constant factor on a static index.[34] And a full autocomplete service does not answer from a trie at all at the top of the funnel — it answers from a cache of the most common prefixes, and reaches the trie only for the tail.

Maximum XOR: the alphabet is {0,1}

Given an array of integers, find the maximum value of a XOR b over all pairs.[35] The pairwise solution is O(n²) and is fine until it is not; for n = 200,000 it is 2×1010 operations.

The trie solution begins with a reframing that is worth more than the problem is: an integer is a string over the alphabet {0,1}, of fixed length, most significant bit first. Insert every number as a 31-bit string. Then for each number, walk down from the root taking the opposite bit at every level whenever a child with that bit exists, and the value you accumulate is the maximum XOR achievable between that number and anything in the set. Greed is correct here because XOR is bit-independent and a higher bit outweighs every lower bit combined.

The measured effect, on random 31-bit integers: at n = 5,000 the pairwise solution performs 12,497,500 comparisons and the trie performs 155,000 bit steps, a factor of 80. At n = 20,000 the factor is 323, and it keeps growing, because one side is quadratic and the other is linear with a 31× constant.

Binary tries are the most under-taught trie variant, and they generalise further than the XOR problem suggests:

  • Add a subtree count to each node and you can answer “how many stored values XOR with x to something less than k” — descend, and at each level add the count of the branch you are not taking when that branch's bit choice would keep you below k.
  • Add a minimum-value field and the trie answers queries with a constraint on the partner, such as the maximum XOR with any element not exceeding a bound.[36]
  • Store prefixes rather than values and it becomes an IP forwarding table (§9).
  • Willard's x-fast and y-fast tries build predecessor search on top of a binary trie over the universe, reaching O(log log U) time.[2]

Reversal, wrapping and other key tricks

A trie indexes prefixes. That sounds like a hard limit, and most of the time it is not: a surprising number of problems that appear to need suffix matching, or two-sided matching, or matching modulo some transformation, become prefix problems once you change what you insert.

Insert the reversal to index suffixes. A trie over reversed keys answers “which stored keys end with this?” in the same O(L) walk, because a suffix of the key is a prefix of its reversal. The standard exercise is a stream checker that must report whether any dictionary word ends at the current character[37]: keep the last few characters of the stream, reverse them, and walk a trie of reversed words. The trick generalises to any “ends with” index, and it is the cheapest possible answer to a question that otherwise invites a suffix automaton.

Insert both, and match the middle. Palindrome Pairs asks for all pairs of words whose concatenation is a palindrome.[38] The decomposition is that for a + b to be a palindrome, either a is longer, in which case b reversed must be a prefix of a and the rest of a must itself be a palindrome, or the mirror case. Store the words reversed in a trie, annotate each node with the list of word indices whose remaining suffix is a palindrome, and each query becomes a single descent that harvests candidates from the annotations it passes. The palindrome-suffix list is a payload in exactly the Plate 6 sense: it is computed at insert time and read at query time.

Insert every rotation. If the question is about cyclic strings, inserting all L rotations of each key costs a factor of L in space and makes every cyclic query a plain prefix query. This is usually the wrong trade, and it is worth knowing precisely so you can recognise when L is small enough that it is the right one.

Insert a canonical form. Case-folding, Unicode normalisation[39], or a collation key[40] applied before insertion makes the trie index equivalence classes rather than byte strings. The important discipline is that the same transformation must be applied to the query, and that the transformation must be a function of the key alone — a context-sensitive fold, of which there are several in Unicode, breaks the character-by-character walk that the whole structure depends on.

Insert with a sentinel. Appending a symbol that appears in no key makes every key a leaf, which removes the terminal flag entirely and turns “is this a key” into “does this node have the sentinel child.” Suffix trees rely on this to guarantee that no suffix is a prefix of another (§18), and approximate-match structures rely on it to make the leaf set and the key set the same thing.[21]

The common thread is worth stating as a rule. The trie is fixed; the key is the parameter. Before you conclude a problem does not fit, ask what you would have to insert for it to fit, and price that.

Aho–Corasick: the trie becomes an automaton

Everything so far walks the trie from the root for each query. The last structural idea in the article removes that restriction, and it is the one that turns a data structure into a machine.

The problem: find every occurrence of every pattern in a set, in one pass over a text, in time proportional to the text length plus the number of matches, independent of how many patterns there are. Aho and Corasick solved it in 1975[8] by adding one pointer to every node of a trie of the patterns.

That pointer is the failure link, and it generalises the failure function of Knuth–Morris–Pratt from one pattern to many.[41] The failure link of a node v points to the node representing the longest proper suffix of v's string that is also a node in the trie. Its meaning is precise: if you are at v having consumed some text, and the next character has no edge out of v, then following the failure link puts you at the deepest node still consistent with the text you have read. You never re-read a character.

Two details do most of the work. The first is that failure links are computed by breadth-first search, because the link of a node is found by following the link of its parent until a node with the right child appears; the parent's link must therefore already be correct. The second is the output link: a node can be the end of one pattern while a suffix of its string is another pattern, so she must report both she and he. Chaining each node to the nearest terminal reachable by failure links, and walking that chain on a match, is what makes the “plus the number of matches” term in the complexity honest.

Running the eight-node automaton over ushers reports she ending at index 3, he ending at index 3, and hers ending at index 5 — three matches, one pass, ten nodes, six characters read exactly once each. All six implementations in this article agree on that output.

Aho–Corasick is the correct answer to a class of real problems that come up far more often than the interview version suggests: intrusion detection rules, content filters, virus signatures, dictionary-based tokenisers, and any log pipeline that must match a few thousand fixed strings per line. It is also worth knowing where its cost lives. Construction is O(sum of pattern lengths) and the automaton is a trie plus one pointer per node, so the memory analysis of §5 applies unchanged. If the pattern set is static and matching speed dominates everything, the failure links can be eliminated entirely by precomputing a full goto table — a genuine DFA, one array lookup per character, at a cost of one pointer per node per alphabet symbol, which for a 256-symbol alphabet is the array[26] disaster from §5 multiplied by ten.[42]

Path compression: radix trees and PATRICIA

Section 5 measured the disease: 53.0% of the nodes in the dictionary trie have exactly one child. A node with one child asks no question. It consumes a character, it costs a header and a pointer array, and it hands control to its only child. Path compression is the cure, and it is the single highest-value modification you can make to a trie.

The rule is: collapse every chain of one-child nodes into a single edge labelled with the whole string. A node then exists only where the key set actually branches, or where a key ends. The result is called a radix tree, a compressed trie, or — in Morrison's 1968 formulation over binary keys — PATRICIA, for Practical Algorithm To Retrieve Information Coded In Alphanumeric.[7] Morrison's version stores at each node the index of the next bit that actually discriminates, skipping the bits in between entirely, which is why the structure has exactly n internal nodes for n keys regardless of how long the keys are.

Measured on the 63,875-word dictionary: path compression takes the trie from 145,250 nodes to 79,053, removing 45.6% of them. The mean edge label becomes 1.84 characters and the longest is 14, but the distribution is heavily skewed — 57.4% of the surviving edges are still a single character, which is the honest number to keep in mind. Path compression removes the long thin tails, not the branchy interior.

Three consequences follow, and only the first is usually mentioned.

Fewer nodes means fewer cache misses, not just less memory. A trie traversal is a pointer chase, and a pointer chase is the access pattern that modern hardware is worst at: each step is a dependent load that cannot be issued until the previous one returns.[3] Halving the node count roughly halves the number of serialised memory round-trips on a lookup, which matters more than the byte count.

The edge label must be compared, not just matched. A plain trie's descent is a sequence of single-character array indexings. A radix tree's descent is a sequence of string comparisons, which either succeed entirely or fail partway through, and a failure partway through means the key is absent — there is no backtracking. Implementations that store the label inline in the node (as ART does, up to a fixed prefix length) keep the comparison in the same cache line as the child pointers; implementations that store it as a separate allocation reintroduce the pointer chase they were trying to remove.

Insertion becomes edge splitting. Inserting a key that diverges in the middle of a label requires cutting the edge in two and creating a branch node at the cut. This is where compressed tries get their reputation for fiddly code, and it is the reason many production implementations expose only a bulk-load path or accept a rebuild.

Almost every trie in production is a radix tree. Linux's XArray and its successor the maple tree index page-cache and virtual-memory ranges with compressed multi-bit tries[48, 49]; Redis's rax is a radix tree used for stream indexes and cluster key tracking[50, 51]; and the Adaptive Radix Tree combines path compression with the variable node sizing of §5 to produce the structure that DuckDB uses for its indexes.[11, 52]

Ternary search trees

There is a third position between the array-per-node trie and the hash-map -per-node trie, and it is the one most often forgotten. Bentley and Sedgewick's ternary search tree gives each node a single character and three children: less, equal, and greater.[9] A descent compares the current key character against the node's character; on a match it consumes the character and follows the equal child, and otherwise it keeps the character and follows less or greater.

The structure is exactly a trie whose per-node child map is implemented as a binary search tree, flattened into the same node type. That gives it a set of properties that are hard to get any other way:

  • Space is proportional to the number of characters actually stored, with no alphabet term at all. Three pointers and a character per node, regardless of whether the alphabet is 26 symbols or 65,536. The array[26] node wastes 96.2% of its slots on English; a TST wastes nothing.
  • Lookup is O(L + comparisons), where the comparison term is the depth of the per-node BSTs. Balanced, that is log of the fan-out, and since §5 measured mean fan-out at 1.432, in practice it is very close to nothing.
  • Near-neighbour and wildcard search fall out naturally, which was Bentley and Sedgewick's motivating application: a search allowing one mismatch descends all three children at the point where budget is spent.
  • The keys come out sorted from an in-order traversal, like any trie and unlike any hash table.

The costs are real too. Insertion order determines the shape of the per-node BSTs, and inserting a sorted dictionary produces degenerate linked lists at every level — the standard fix is to insert the median key first, recursively, which requires knowing the key set in advance. And the three-pointer node makes the per-character constant higher than a well-tuned adaptive node, which is why the modern engineering answer (§5) is variable-sized nodes rather than a BST.

TSTs remain the right default in one specific circumstance: a large alphabet, a static or near-static key set, and a requirement for approximate matching. That describes a spell checker, and it is not a coincidence that spell checkers are what Bentley and Sedgewick built.

Suffix tries and what replaced them

Insert every suffix of a single string into a trie and you get a structure that can answer, in time proportional to the pattern length, whether that pattern occurs anywhere in the string — because every substring of a string is a prefix of one of its suffixes. This is the suffix trie, and it is the most powerful and least practical member of the family.

The impracticality is quadratic space: a string of length n has n suffixes of average length n/2, so the trie has O(n²) nodes. For a 1 MB text that is on the order of 1012 nodes, which is not a constant-factor problem.

Path compression (§16) fixes it exactly. A compressed suffix trie — a suffix tree — has at most 2n−1 nodes, because it has n leaves and every internal node branches. Edge labels are stored as (start, end) offsets into the original string rather than as copied text, so the whole structure is O(n) words. Weiner gave the first linear-time construction in 1973[53], McCreight simplified it in 1976[54], and Ukkonen's 1995 online algorithm is the one that is actually taught, because it builds the tree left to right and its invariants can be explained.[55] Gusfield's book remains the standard treatment.[56]

What a suffix tree buys, beyond substring search: longest repeated substring (the deepest internal node), longest common substring of two strings (a generalised suffix tree over both, deepest node with leaves from each), all occurrences of a pattern (the leaves under the pattern's node), and the matching statistics that underpin much of sequence alignment.[57]

And yet suffix trees are rare in production, for a reason worth internalising: the constant factor is brutal. A suffix tree over an n-character text typically occupies 10–20 bytes per character in a good implementation, and the traversal is a pointer chase over a structure far larger than cache. The suffix array — the sorted list of suffix start positions, with a table of longest common prefixes alongside — answers most of the same questions with binary search, occupies 4–8 bytes per character, and has contiguous access patterns.[58] Compressed and self-indexing variants push this further, storing the index in space close to the compressed text itself.[16] For most tasks the suffix array is the correct choice and the suffix tree is the correct explanation.

The directed acyclic word graph, or suffix automaton, is the third member of the family: minimise the suffix trie as a DFA and equivalent states merge, yielding a linear-size automaton that recognises exactly the substrings of the text.[59] It is the structure that makes clear what all of these have in common with §14: once you compress or minimise a trie hard enough, it stops being a tree and becomes an automaton.

Nothing says a trie edge must consume one character. It consumes one symbol, and the symbol size is a free parameter: read the key one bit at a time and the alphabet is 2; four bits at a time and it is 16; a byte at a time and it is 256. This choice is the single most consequential tuning decision in any real trie, and it trades three quantities against each other that do not move together.

Which of these you are optimising determines the answer completely:

  • In-memory index, latency-bound. Depth is what costs you, because each level is a dependent cache miss. Go wide — but pay for the width with adaptive node sizing rather than fixed arrays, which is precisely what ART does: node types holding 4, 16, 48 and 256 children, promoted as a node fills.[11] The measured fan-out distribution in §5 explains why those four sizes and not others.
  • Authenticated data structure. Proof size is what costs you, because every proof crosses a network. Go narrow. Ethereum's Merkle Patricia Trie uses 16-way nodes and pays for it with proofs that carry fifteen sibling hashes per level[60]; the state-tree redesign in EIP-7864 moves to a binary tree specifically to shrink proofs for stateless verification.[61, 62] The trade is a deeper tree and more hashing, accepted deliberately.[63, 64]
  • Disk or page-oriented storage. The unit is the page, not the node, and the right branching factor is whatever fills a page — which is the reasoning that produces a B-tree rather than a trie.[5]
  • Succinct or read-only representation. If the structure is static, the pointers can go away entirely: a bitmap plus rank/select operations encodes the tree shape in close to the information-theoretic minimum[14, 15], and the same idea applied to a trie yields SuRF, a filter that answers range queries in a few bits per key.[17] Bagwell's hash array mapped trie is the widely-copied practical form of the bitmap idea.[13]

The historical version of this argument is the double-array trie, which represents a wide-alphabet automaton in two integer arrays with O(1) transitions and no pointers at all, at the cost of a painful insertion procedure.[65] It is still the fastest known representation for a static, wide-alphabet trie, and it is why Japanese morphological analysers have used it for thirty years.

Tries in production

The trie's reputation as an interview structure does it a disservice. It is one of the most widely deployed data structures in systems software, usually under a different name and always with the engineering of §5, §16 and §19 applied.

Databases

The Adaptive Radix Tree is the standard modern answer for a main-memory ordered index: path-compressed, with four node sizes chosen from the measured fan-out distribution, and small enough that a lookup touches a handful of cache lines.[11] A later paper adds optimistic lock coupling to make it concurrent without per-node latches on the read path.[66] DuckDB uses an ART for its indexes, including the ones created implicitly by PRIMARY KEY and UNIQUE constraints, and documents the consequences that follow from it — notably that these indexes are memory-resident and that their size is a real planning consideration.[12, 52] HOT, the height-optimised trie, attacks the same problem by choosing a different discriminative-bit split per node so that the tree's height adapts to the key distribution.[67]

Caches and in-memory stores

Redis contains a hand-written radix tree, rax, used for stream entry IDs, client-side caching key tracking and cluster bookkeeping.[50, 51] Its design notes are unusually candid about the trade-offs, including where the implementation chose simplicity over the last few percent. The burst trie and its descendant the HAT-trie make the complementary choice — keep the top of the structure as a trie and let the bottom degenerate into small cache-resident containers, on the observation that most nodes near the leaves have almost no children.[18, 19] §5's finding that 30.2% of nodes are leaves and 83.2% have at most one child is the same observation, measured.

Operating systems

Linux's XArray is a radix-tree-derived structure that indexes the page cache by file offset; the maple tree, merged more recently, replaces the red-black tree of virtual memory areas with a range-indexed B-tree-like structure built on the same lineage.[48, 49] Both exist because the workload is integer-keyed, sparse, and read-mostly under RCU, which is the exact profile a compressed trie serves well.

Networking

IP forwarding is longest-prefix matching over a binary trie, and thirty years of work has gone into making that lookup fit in cache: level-compressed tries, controlled prefix expansion trading memory for fewer levels, and the tree bitmap scheme that stores a node's shape and its children separately so a multi-bit node fits in one memory access.[25, 26, 27, 28]

Search and text

Lucene's terms dictionary is a finite state transducer built from the sorted term list: it shares suffixes as well as prefixes, is built once and never mutated, and maps terms to postings-list offsets in the same traversal.[34] Levenshtein automata built over the same structure give approximate matching in a single traversal rather than a scan.[21]

Blockchains

Ethereum's state is a Merkle Patricia Trie: a 16-way path-compressed trie where every node is identified by the hash of its contents, so the root hash commits to the entire state and a proof of any key is the path to it.[60] The design is now being revised — EIP-7864 replaces it with a binary tree to reduce proof sizes for stateless clients, trading depth and hashing cost for bandwidth, which is §19's table read in the proof-size column.[61, 62, 63] The migration is substantial enough that the tooling and security implications are being worked through in public.[64]

Machine learning infrastructure

The most recent addition, and the one that would have surprised Fredkin: LLM serving systems index the key-value attention cache by token prefix, so that requests sharing a prompt prefix reuse the computed state instead of recomputing it. SGLang calls this RadixAttention and manages the cache as a radix tree with an LRU eviction policy over its leaves[4]; it composes with paged attention's block-level memory management.[68] The keys are token sequences instead of words, the payload is a tensor block instead of a dictionary entry, and the walk is the 1959 walk.

When not to use a trie

An article that only shows what a structure is good at teaches you to reach for it wrongly. Here is the honest list, with the measurements that support it.

Exact lookup, and nothing else. If the only operation is “is this key present” or “what is this key's value”, a hash table wins on every axis that matters. It touches one or two cache lines; the trie touches one per character. It does not care about key length beyond hashing it once. The trie's O(L) guarantee is theoretically attractive and practically irrelevant when L is 8 and the hash table's expected O(1) has a constant of 1.

Random or high-entropy keys. The trie's whole economy comes from shared prefixes. UUIDs, hashes and random identifiers share nothing: the node count approaches the total character count, the tree is a bush of depth logₖn with a long thin tail, and you have paid a pointer per character to build a very expensive hash table. §5's measured 2.27 nodes per key on English becomes something near L nodes per key on random data.

Memory pressure with a naive node type. The dictionary trie with array[26] nodes needs 33.7 MB to index 529 KB of text — a 63.7× inflation, and 96.2% of the allocated pointer slots are null. This is the default implementation in most textbooks and most interview answers. It is a factor of 6.8 worse than a well-chosen node layout and it is the reason people conclude tries are impractical, when what is impractical is that node type.

Unicode, unless you have thought about it. The array[26] node is a lie about text. Real keys are UTF-8, where a character is one to four bytes[69] and the trie should almost always branch on bytes rather than code points — which keeps the alphabet at 256, makes edges byte-comparable, and preserves code-point order because UTF-8 is designed so that byte order equals code-point order. Branching on code points means a 1.1 million-way alphabet and a hash map per node. Neither approach handles the harder problem: canonical equivalence means two byte sequences can represent the same text, so the key must be normalised before insertion[39], and “alphabetical” order in any particular language is a collation algorithm, not a byte comparison.[40]

When the trie makes the search worse. The most instructive result in the lab. On a 10×10 board of nothing but the letter a, with the ten words a through aaaaaaaaaa, the naive Word Search II makes 55 DFS calls and the trie-driven version without pruning makes 4,409,236 — roughly eighty thousand times worse. The trie does not filter anything, because every path is alive, and the naive version's early exit on “no word starts like this” never fires either; what actually differs is that the trie version explores the full board-path space while the naive version's word-by-word loop terminates each word quickly. Adding subtree pruning brings it to 140 calls, still 2.5× worse than naive. The trie is a filter, and a filter that filters nothing is pure overhead.

Ordered range queries at scale. A trie gives you sorted iteration and prefix ranges, which is more than a hash table offers, but a B-tree gives you the same thing with page-sized nodes and a disk-friendly access pattern.[5] If the data does not fit in memory, this is not a close call.

When you would have to build it first. §8 is the general case: Longest Common Prefix over an array is O(sum of lengths) with a linear scan and O(sum of lengths) to build a trie and then walk it. Any single-pass question over a key set that you are given, rather than maintaining, has this property. The trie pays off when it is built once and queried many times, which is a statement about the workload and not about the structure.

the shape of the mistake

Every failure mode above is the same mistake in a different costume: using the trie for its reputation rather than for the one thing it does that nothing else does, which is to make the set of keys sharing a prefix into a single object you can point at. If your question does not contain a prefix, the answer does not contain a trie.

Six findings from that output are worth stating as claims rather than as table rows.

  1. Prefix sharing is front-loaded. The first thousand keys cost 5.89 nodes each; the last 13,875 cost 1.35. The elasticity of nodes to keys is 0.771, meaning a trie over English words grows sublinearly and the benefit accelerates — the structure gets cheaper per key the more keys it holds, which is the opposite of every hash table's behaviour under load.
  2. The dense node is indefensible. Mean internal fan-out is 1.432 against an alphabet of 26. An array of 26 pointers therefore leaves 96.2% of its slots null, and the five layouts modelled span a factor of 6.8 in total memory. This single decision is the difference between 527.6 and 78.1 bytes per key.
  3. Half the nodes ask no question. 53.0% of nodes have exactly one child and 30.2% have none. Path compression removes 45.6% of all nodes, and the resulting edge labels average only 1.84 characters — the win comes from eliminating many short chains, not a few long ones.
  4. The prefix query's advantage is asymptotic, not constant. At a thousand keys, a trie descent and a binary search on a sorted array are within a few percent of each other in wall time. At 63,875 keys the trie takes 0.30 microseconds and binary search 0.48, while a linear scan takes 4,273. The trie's step count rises from 1.06 to 3.11 across that whole range; binary search's rises from 10 to 16. What the trie really buys is independence from n.
  5. A filter that filters nothing is overhead. On English text the trie-driven Word Search II makes 3,136 DFS calls against the naive version's 528,375 — a 168× improvement. On an adversarial board it makes 4,409,236 against 55. And the third scenario shows pruning reclaiming exactly 0.0%, because pruning removes branches the search has exhausted, never branches it never entered.
  6. Wildcard position dominates wildcard count. One . at the end of a five-letter pattern costs 1.4× the nodes of an exact match. The same wildcard at the front costs 11.5×. Two at the front cost 87×. The reason is that a wildcard multiplies the frontier by the fan-out at its depth, and fan-out is highest near the root.

The eighth experiment is §19's branching-factor table, and the seventh verifies the binary trie against brute force at every size up to 5,000 keys before reporting its speedups — a habit worth keeping in any measurement code, because a fast wrong answer is easy to produce and hard to notice.

The claim made in §1 was that every problem in this article is the same trie, and that what varies is only what a node carries and how the walk moves. Here is the evidence, collected. The rows fall into four bands, and the bands are the real taxonomy.

Descent — the walk is determined by the input. One step per character, no choices, no backtracking. Membership, prefix existence, longest matching prefix, and path compression all live here, and so does the observation that this walk is O(L) regardless of how many keys are stored.

Branching — the walk forks because the input underspecifies the path. Wildcards, approximate matching, and Camelcase Matching are all this shape, and the cost is governed by where the forks are rather than how many, as §6 measured.

Payload — the walk is a descent, but the node carries something beyond its children, and the answer is read off rather than searched for. Aggregates, counts, top-k lists, binary-trie extrema, and the transformed keys of §13.

Automaton — the text drives the trie rather than the other way round, and the structure carries links that let it reposition without re-reading. Word Search II is the elementary case, where the board drives the walk; Aho–Corasick is the complete one, where failure links make the repositioning free.

When you meet an unfamiliar string problem, the productive question is not “is this a trie problem.” It is: what would a node have to carry, and who is driving the walk. If both have answers, you have the solution; if either does not, you are in §21.

Practice and resources

An order to work through the problems, chosen so that each one adds exactly one idea to the last.

  1. Implement Trie[10] — the structure. Write it in a language you are not fluent in, to stop yourself pattern-matching.
  2. Longest Common Prefix[23] — the forced descent, and the discipline of noticing that the trie is not needed.
  3. Replace Words[24] — the early return, which is the longest-matching-prefix primitive in disguise.
  4. Map Sum Pairs[29] — the payload on the path, and the delta that makes overwrite correct.
  5. Design Add and Search Words[20] — the fork, and the first walk whose cost is not O(L).
  6. Maximum XOR[35] — the reframing of an integer as a string, which is the largest single conceptual step in the list.
  7. Word Search II[22] — external driving, plus the pruning without which the solution is a liability.
  8. Stream of Characters[37] — reversal, and then rewrite it with Aho–Corasick and compare.
  9. Palindrome Pairs[38] — the hardest of the classic set, and the one that most rewards drawing the decomposition before coding.
  10. Aho–Corasick from scratch — not a problem so much as a rite. Build the failure links by BFS, get the output links right, and test against {he, she, his, hers} on ushers.

Where to read further

For the structure itself, Knuth's treatment in Sorting and Searching[2] is still the most complete, and it is where the history in §3 is documented. Sedgewick and Wayne give the clearest undergraduate presentation, with R-way tries and ternary search trees developed side by side[70]; CLRS is the standard reference for the surrounding material[71]; Skiena is the best single source for deciding whether a structure fits a problem[72]; and Laaksonen is the competitive-programming treatment, which is where the problem-shaped versions live.[73] cp-algorithms has a careful, implementation-focused article on Aho–Corasick that covers the cases the original paper leaves implicit.[42]

For strings more broadly, Gusfield remains the standard on suffix structures[56], Crochemore and Rytter cover the algorithmic core[57], and Navarro is the modern reference for compact and self-indexing representations.[16] For the engineering, read the ART paper[11] and then the rax implementation notes[50] back to back: one is the principled version and the other is what shipping it looks like.

And the two original papers are short, readable and worth the hour. De la Briandais describes the linked-list node representation and the file-searching problem it solved[6]; Fredkin's Trie Memory names the structure, argues for it as a general-purpose memory organisation, and is written with a confidence about the future of computing that has aged remarkably well.[1]
