Computer Architecture and Organization

How a processor turns stored instructions into computation, from the stored-program machines of the 1940s to today's multicore systems-on-chip, with the history behind each idea and worked examples.

October 2026 · References in Vancouver style; bracketed numbers link to the reference list.

Computer architecture is the set of attributes of a computer that a programmer can see: the instruction set, the registers, the data types and the memory model. Computer organization (often called microarchitecture) is the way a particular implementation realizes that architecture with datapaths, control logic, pipelines and caches. The distinction was made explicit by the designers of the IBM System/360, who defined architecture as "the attributes of a system as seen by the programmer" so that a family of machines with very different hardware could run the same software [1]. Modern textbooks keep the same split: one instruction set architecture (ISA) can be implemented by many microarchitectures that trade cost, speed and power differently [2,3].

This article walks through the core ideas in roughly the order a processor uses them: how instructions and data are stored, how an ISA is defined, how an instruction is fetched and executed, and how hardware overlaps, reorders and replicates that work to go faster. It then covers the problems that appear once several processors share memory, the hardware support that makes virtual machines efficient, and the system-on-chip designs that now integrate most of a computer onto one die.

1. Von Neumann and Harvard architectures

History

The first large automatic computers did not keep their programs in memory. The Harvard Mark I, conceived by Howard Aiken in 1937 and delivered to Harvard in 1944, read its instructions from punched paper tape and kept its numbers in separate counters. It weighed about five tons, was roughly 50 feet long, and kept producing results until 1959 [4]. Because the instruction path and the data path were physically separate, the term Harvard architecture came to mean any design with separate storage and pathways for instructions and data [2].

In 1945 John von Neumann circulated the First Draft of a Report on the EDVAC. It described a machine made of a central arithmetic part, a central control part, a memory, and input and output organs, in which the program's instructions are stored as numbers in the same memory as the data they operate on [5]. Storing the program in memory meant a program could be loaded, changed, and even generated by another program, which is the basis of compilers, loaders and operating systems. In 1948 Williams and Kilburn reported a working electronic stored-program machine at the University of Manchester [6]. Designs that follow this model are called von Neumann or stored-program architectures.

Concepts

The defining property of the von Neumann model is that instructions are data. The processor keeps a program counter (PC) that holds the address of the next instruction, fetches the word at that address, decodes it, and executes it, and the program can modify memory that will later be fetched as instructions [3,5]. The cost of this simplicity is that a single connection between processor and memory must carry both instruction fetches and data transfers. John Backus named this limitation the von Neumann bottleneck in his 1977 ACM Turing Award lecture, describing the "tube" between CPU and store through which every word must pass [21]. As processor speed grew much faster than memory speed, Wulf and McKee warned in 1995 that performance would eventually be bounded by memory latency, the so-called memory wall [22].

A Harvard machine can fetch the next instruction while the current instruction reads or writes data, and instruction and data memories can have different widths and technologies. The trade-off is that a program cannot easily treat its own code as data, and memory must be split between the two in advance.

Modern practice: the modified Harvard architecture

Almost every high-performance processor today is a hybrid. Main memory is unified, as in von Neumann's design, so programs can be loaded and generated like any other data. Close to the core, however, the first level of cache is split into a separate L1 instruction cache and L1 data cache, so that a pipeline can fetch an instruction and access data in the same clock cycle without a structural conflict [2,3]. This arrangement is often called a modified Harvard architecture.

Pure Harvard designs remain common in small microcontrollers and digital signal processors. Microchip's 8-bit AVR core, for example, "uses a Harvard architecture with separate memories and buses for program and data," and pre-fetches the next instruction from program memory while the current one executes [20].

2. CPU architecture and instruction sets

The ISA as a contract

The instruction set architecture is the boundary between software and hardware. It specifies the instructions and their encodings, the registers, the data types, the addressing modes, how memory is addressed, and how exceptions and privileged operations behave [2]. When IBM introduced System/360 in 1964, its architects used a single ISA across models that differed in speed and cost by large factors, so that customers could move to a larger machine without rewriting their programs [1]. Binary compatibility has shaped the industry ever since. The x86 architecture that began with Intel's 8086 is still extended rather than replaced, and Intel documents it in a multi-volume software developer's manual [23].

The first single-chip microprocessor, the Intel 4004 of 1971, was a 4-bit processor of about 2,300 transistors designed for a Busicom calculator chipset [11]. Gordon Moore had observed in 1965 that the number of components on an integrated circuit was doubling at a regular rate [24], and the ISA has had to absorb fifty years of that growth: wider words, more registers, floating point, vector instructions and privileged features for operating systems and hypervisors.

Classifying instruction sets

One useful classification asks where an instruction's operands come from [2]:

  • Stack architectures take operands implicitly from the top of an operand stack.
  • Accumulator architectures use one implicit register as a source and destination.
  • Register-memory architectures allow one operand to come straight from memory (x86 is an example).
  • Load-store (register-register) architectures allow only load and store instructions to touch memory, and all arithmetic works on registers. RISC-V, Arm and MIPS are load-store designs [2,25].

The same statement C = A + B looks different in each style:

# Load-store (RISC-V)              # Register-memory (x86-64, Intel syntax)
lw   t0, 0(a0)     # t0 = A         mov  eax, [A]      # eax = A
lw   t1, 4(a0)     # t1 = B         add  eax, [B]      # eax += B (memory operand)
add  t2, t0, t1    # t2 = A + B     mov  [C], eax      # C = eax
sw   t2, 8(a0)     # C = t2

Other design dimensions include the number and width of registers, the addressing modes (register, immediate, displacement, indexed and so on), the supported data types, the operations, the control-flow instructions, and the instruction encoding, which can be fixed-length or variable-length [2].

Example: the RISC-V base encoding

RISC-V, which began at the University of California, Berkeley, is an open ISA that anyone can implement without a license [26]. Its RV32I base has 32 integer registers, x0 to x31, with x0 hardwired to zero; it is a load-store architecture; and its base instructions are a fixed 32 bits long, with an optional "C" extension adding 16-bit compressed forms [25]. Base instructions use four core formats (R, I, S and U) plus the B and J variants for branches and jumps, and the register fields always sit in the same bit positions, which makes decoding simple [25].

By contrast, x86 instructions are variable in length. An instruction can carry optional prefixes, an opcode of one to three bytes, addressing-form bytes, a displacement and an immediate, up to a maximum of 15 bytes, and 64-bit mode provides 16 general-purpose registers [23]. Variable-length encoding packs common instructions densely but makes it harder to find where the next instruction starts, a point that matters for the RISC and CISC debate below.

3. Reduced Instruction Set Computing (RISC) versus Complex Instruction Set Computing (CISC)

How CISC arose

Maurice Wilkes proposed building a processor's control unit as a small internal program, and in 1953 Wilkes and Stringer described the technique, microprogramming, in detail [7]. Each machine instruction is carried out by a sequence of microinstructions held in a fast control store. Microprogramming made it cheap to add rich, high-level instructions: if memory was slow and expensive, a single instruction that did a lot of work saved fetches and program space. Before RISC, most computers used microprogrammed control, with microinstructions 50 to 100 bits wide and microprograms of one to four thousand microinstructions; Patterson spent a 1979 sabbatical at DEC helping with microcode bugs in the newly announced VAX [27]. Designs in this tradition, with many instructions, many addressing modes, memory operands and variable-length encodings, came to be called complex instruction set computers (CISC).

The RISC argument

At IBM, work led by John Cocke on the 801 project began around 1975 [15]. The 801 used a simple instruction set designed together with an optimizing compiler, so that most instructions could execute in a single cycle [28]. In September 1980 David Patterson and David Ditzel published "The case for the reduced instruction set computer," arguing that VLSI technology, better compilers and the rarity of complex instructions in real programs favored simple instruction sets that could be implemented quickly and well [14,27]. The Berkeley RISC I processor, whose first chips arrived in the fall of 1981, had 31 instructions, each executing in one clock cycle, and 78 32-bit registers [15]. Stanford's MIPS project under John Hennessy followed a similar path and was commercialized by MIPS Computer Systems; Sun's SPARC, with Patterson consulting, appeared in 1987; and the UK company Arm developed a continuing series of RISC designs that are now licensed for phones, tablets and game consoles [15]. Hennessy and Patterson received the 2017 ACM Turing Award for this work, and their award lecture argued that open ISAs such as RISC-V and domain-specific architectures start a "new golden age" for the field [26].

Convergence

The two camps have since borrowed heavily from each other. High-performance x86 processors translate x86 instructions into simpler internal micro-operations and then execute those with a RISC-like out-of-order pipeline [2]. RISC ISAs, in turn, have grown large with vector, cryptographic and virtualization extensions [19]. A careful 2013 study by Blem, Menon and Sankaralingam measured ARM and x86 processors and concluded that, for the platforms studied, whether the ISA is RISC or CISC is largely irrelevant to power and performance; the microarchitecture and design goals matter much more [29]. The practical differences that remain are decoder complexity, code density, and the legal and ecosystem questions of who may implement an ISA.

4. The instruction execution cycle: fetch, decode, execute

Every stored-program processor repeats the same basic loop, which follows directly from von Neumann's design: get the next instruction from memory, work out what it asks for, and do it [3,5]. Textbooks usually divide the loop into finer steps.

The steps

  1. Fetch. The processor sends the program counter to memory (or to the instruction cache) and loads the returned word into the instruction register (IR). It then advances the PC to the next sequential instruction, which in RISC-V is PC + 4 for a 32-bit instruction [3,25].
  2. Decode. The control unit examines the opcode and function fields to determine the operation. In a RISC-V design the register file can be read in parallel with decoding because the source register fields are always in the same place [3].
  3. Execute. The ALU performs the arithmetic or logical operation, computes a memory address (base register plus offset), or compares registers for a branch [3].
  4. Memory access. Loads read data memory and stores write it; other instructions pass through this step [3].
  5. Write back. The result is written to the destination register, and a taken branch or jump replaces the PC [3].

Between instructions the processor checks for interrupts (external events such as a timer or device) and exceptions (events caused by the instruction itself, such as a page fault). If one is pending, it saves the PC and some state, switches to a privileged mode and jumps to a handler [3]. A design has precise exceptions when the saved state looks as if every earlier instruction finished and no later one started, which becomes difficult and important once instructions overlap [30].

Worked example

Consider lw x5, 8(x6) on a simple RISC-V processor. In fetch, the PC is used to read the 32-bit instruction and the PC becomes PC + 4. In decode, the I-format fields give opcode = load, rs1 = 6, rd = 5 and immediate = 8, and register x6 is read. In execute, the ALU adds x6 + 8 to form the address. In memory access, the word at that address is read. In write back, the word is written into x5. An add uses the same steps but skips the memory access, and a beq finishes after execute by choosing between PC + 4 and the branch target [3].

The time a program takes is captured by the classic performance equation [2,3]:

CPU time = Instruction count × Cycles per instruction (CPI) × Clock cycle time

The ISA and compiler largely set the instruction count; the organization sets CPI and, together with circuit technology, the cycle time. Every technique in sections 6 to 8 is an attempt to reduce one factor without inflating another.

5. Registers and arithmetic logic units (ALUs)

Registers

Registers are the fastest storage in the machine, built into the processor and read or written within a clock cycle. They fall into two groups [2,3]:

  • Architectural (programmer-visible) registers: general-purpose integer registers, floating-point and vector registers, the program counter, and status or flag registers. RISC-V provides 32 integer registers with x0 fixed at zero [25]; x86-64 provides 16 general-purpose registers and an RFLAGS register whose bits record conditions such as zero, sign, carry and overflow [23]; the 8-bit AVR core provides 32 eight-bit working registers [20].
  • Internal (microarchitectural) registers: the instruction register, memory address and data registers, pipeline registers between stages, and in out-of-order cores a much larger physical register file used for renaming (section 8). These are invisible to software but essential to the implementation [2].

Having many registers lets compilers keep variables out of memory, which reduces loads and stores and is one reason load-store ISAs provide large register files [2]. The Berkeley RISC I went further, with 78 32-bit registers [15].

The arithmetic logic unit

The ALU is the combinational circuit that performs integer arithmetic (add, subtract, compare) and bitwise logic (AND, OR, XOR, shifts). It takes two operands and a control code and produces a result plus condition outputs such as zero, carry and overflow [3]. A simple ALU is built from one-bit slices, each containing an adder and logic gates, connected through a carry chain. In a ripple-carry adder each slice waits for the carry from the one below, so delay grows linearly with word width; carry-lookahead adders compute carries in parallel with generate and propagate signals so that delay grows roughly with the logarithm of the width [3]. Subtraction reuses the adder by inverting the second operand and setting the carry-in to one (two's complement), and a set-less-than operation is derived from the sign of the subtraction [3].

Real processors contain many such units. The CDC 6600 of 1964 already had ten independent functional units in its central processor, including separate add, multiply, divide, shift, boolean and branch units [8], and modern cores have several integer ALUs, multipliers, floating-point and vector units, and load and store units that can all be busy in the same cycle [2].

6. Control units and datapaths

A processor is usually described as two cooperating halves [3]. The datapath contains the elements that hold and transform data: the PC, instruction and data memories (or caches), the register file, the ALU, adders, multiplexers and sign extenders. The control unit reads the instruction and produces the signals that steer the datapath: which register to write, which input a multiplexer selects, which operation the ALU performs, and whether memory is read or written.

Single-cycle, multicycle and pipelined organizations

In a single-cycle implementation every instruction completes in one long clock cycle, so the clock period must fit the slowest instruction, usually a load [3]. A multicycle implementation breaks execution into steps of one short cycle each and reuses units such as the ALU across steps, so simple instructions take fewer cycles than complex ones [3]. A pipelined implementation, covered in the next section, keeps the steps separate and overlaps instructions in different steps.

Hardwired versus microprogrammed control

A hardwired control unit is a block of combinational logic, or a finite-state machine, that produces control signals directly from the opcode and current state. It is fast and suits a regular ISA. A microprogrammed control unit stores the control signals for each step as microinstructions in a control store and sequences through them, an approach introduced by Wilkes and Stringer [7]. Microprogramming makes a complex ISA easier to design and fix, which is why it dominated before RISC [27]. Later x86 designs added writable on-chip memory so that microcode could be patched after manufacture [27]. RISC designs favored hardwired control because simple, uniform instructions could be decoded directly and pipelined [2,14].

7. Pipelining and instruction-level parallelism

The idea

Pipelining applies the assembly-line principle to instructions. The datapath is divided into stages separated by pipeline registers, and in each clock cycle a new instruction enters the first stage while earlier ones advance. Each instruction still takes the same number of steps, but in the ideal case one instruction finishes every cycle, so throughput approaches one instruction per cycle and the speedup over an unpipelined design approaches the number of stages [2,3]. The classic RISC pipeline has five stages: instruction fetch (IF), instruction decode and register read (ID), execute (EX), memory access (MEM) and write back (WB) [3].

Overlap is an old idea. The CDC 6600 of 1964 overlapped memory access with arithmetic across its functional units, and the IBM System/360 Model 91 of 1967 was designed to fetch and decode instructions far ahead of execution so that its functional units stayed busy [8,10].

Hazards

Overlap creates hazards, situations in which the next instruction cannot proceed in the next cycle [2,3]:

  • Structural hazards occur when two instructions need the same hardware in the same cycle, for example a single memory port for both instruction fetch and data access. Split instruction and data caches remove the most common case [3].
  • Data hazards occur when an instruction needs a result that an earlier instruction has not yet written. Forwarding (bypassing) routes a result from a later pipeline stage back to the ALU input. A load followed immediately by an instruction that uses the loaded value still needs a one-cycle stall because the data arrives only at the end of MEM [3].
  • Control hazards arise from branches, because the next instruction's address is not known until the branch is resolved. Processors predict the outcome and fetch speculatively, flushing the wrong-path instructions when a prediction fails [2,3].

Branch prediction

Static schemes, such as predicting backward branches taken, are simple but limited. Dynamic predictors record each branch's recent behavior in hardware tables. Yeh and Patt's two-level adaptive predictor of 1991 used a history of recent branch outcomes to select among saturating counters, reaching much higher accuracy than single-level schemes in their simulations [31]. Today's predictors are far more elaborate, because in a deep, wide pipeline each misprediction discards many instructions' worth of work [2].

Instruction-level parallelism

Instruction-level parallelism (ILP) is the amount of independent work among nearby instructions that hardware or a compiler can overlap [2]. Pipelining exploits ILP by overlapping stages. Further exploitation needs either the compiler (loop unrolling, software pipelining, very long instruction word designs) or the hardware (multiple issue, dynamic scheduling, speculation). How much ILP real programs contain is limited. Wall's 1991 study found that, once branch prediction, register renaming and memory disambiguation were modeled realistically, the parallelism available in typical programs was far lower than idealized machines with perfect prediction and unlimited resources suggested [32].

Worked example: pipeline CPI

Suppose 25% of instructions are loads, 20% of loads are followed immediately by a dependent instruction (one-cycle stall each), 15% of instructions are branches, and 10% of branches are mispredicted with a three-cycle penalty. Then CPI = 1 + (0.25 × 0.20 × 1) + (0.15 × 0.10 × 3) = 1 + 0.05 + 0.045 = 1.095. The ideal CPI of 1 is reached only if every hazard is hidden; the arithmetic follows the stall-cycle model in Hennessy and Patterson [2].

8. Superscalar processors and out-of-order execution

Issuing more than one instruction per cycle

A superscalar processor fetches, decodes and issues several instructions per cycle into multiple functional units, so CPI can drop below 1 (equivalently, instructions per cycle, IPC, rises above 1) [2,33]. The compiler does not have to mark which instructions are independent; the hardware discovers this at run time. Smith and Sohi's 1995 survey describes the phases of such a machine: instruction fetch and branch prediction, decode and register renaming, dispatch into instruction windows, issue and execution when operands are ready, and in-order commit [33].

Dynamic scheduling and Tomasulo's algorithm

An in-order pipeline stalls whenever the instruction at the head is waiting, even if younger instructions are ready. Dynamic scheduling lets ready instructions go ahead. The CDC 6600 used a centralized scoreboard to track register and functional-unit use and let independent instructions proceed [8]. Robert Tomasulo's algorithm for the floating-point unit of the IBM System/360 Model 91 added reservation stations that hold waiting instructions with their operands or tags, and a common data bus that broadcasts results to every waiting station [9]. Because tags name the producing unit rather than an architectural register, Tomasulo's scheme effectively renamed registers in hardware and removed false dependences between instructions that merely reused the same register name [2,9].

Register renaming, the reorder buffer and speculation

Modern out-of-order cores generalize these ideas [2,33]:

  • Register renaming maps each architectural destination register to a fresh physical register, eliminating write-after-read and write-after-write (name) dependences so that only true data dependences constrain execution.
  • Issue queues (reservation stations) hold renamed instructions until their source operands are available and a functional unit is free; then they issue, possibly out of program order.
  • A reorder buffer (ROB) records instructions in program order and retires (commits) them in that order, which keeps exceptions precise and allows speculative instructions after a mispredicted branch to be discarded [30].
  • Load and store queues track memory operations so that loads can bypass earlier stores whose addresses are known not to conflict.

Examples

The MIPS R10000 of 1996 was a four-way superscalar processor that fetched and decoded four instructions per cycle, renamed registers into larger physical register files, and executed instructions out of order with in-order graduation [34]. The Alpha 21264 of 1999 combined four-wide fetch, a tournament-style branch predictor and out-of-order issue [35]. Contemporary x86 and Arm cores use the same principles at much larger scale, with hundreds of instructions in flight [2].

Multithreading

Even an aggressive out-of-order core leaves many issue slots empty because a single thread lacks enough ILP. Simultaneous multithreading (SMT), studied by Tullsen, Eggers and Levy in 1995, lets instructions from several hardware threads issue in the same cycle and share the core's functional units [36]. Intel's Hyper-Threading Technology, first shipped in the Xeon processor family, made one physical processor appear as two logical processors that share caches, execution units and branch predictors while keeping separate architectural state, for less than 5% additional die area [37].

Limits and side effects

Wider and deeper out-of-order machines need disproportionately more power and area for renaming, wake-up and bypass logic. Combined with the end of Dennard scaling, in which voltage had fallen in step with transistor size so that power density stayed roughly constant [13], this pushed the industry from ever-faster single cores toward multiple cores in the mid-2000s [2,26]. Speculation also has security consequences. The Spectre attacks showed in 2019 that a processor's mispredicted, later-discarded instructions can leave measurable traces in caches, letting an attacker infer data the program never architecturally revealed [38].

9. Multicore and multiprocessor systems

Classifying parallel machines

Michael Flynn classified computers by the number of instruction streams and data streams they process: single instruction, single data (SISD); single instruction, multiple data (SIMD); multiple instruction, single data (MISD); and multiple instruction, multiple data (MIMD) [39]. Multicore processors and multiprocessors are MIMD machines; vector units and GPUs exploit SIMD-style data parallelism [2].

Why multicore

From the 1970s to the early 2000s, smaller transistors brought both more transistors and faster, cooler ones [13,24]. When supply voltage stopped scaling, higher clock rates and wider single cores became limited by power, and designers turned the growing transistor budget into multiple cores per chip [26]. Olukotun and colleagues had argued in 1996 that a single-chip multiprocessor would use die area more efficiently than an ever-wider superscalar core [16]. IBM's POWER4, described in 2002, placed two processor cores on one chip with a shared L2 cache [40], and Sun's Niagara (UltraSPARC T1) combined many simple cores and hardware threads to run 32 threads at once for throughput-oriented server workloads [41].

Organizations

  • Shared-memory multiprocessors give all processors a single physical address space. In a symmetric multiprocessor (SMP), or uniform memory access (UMA) system, all processors reach memory with roughly equal latency, typically through a shared bus or crossbar [2].
  • Distributed shared memory or NUMA systems attach memory to each node, so access time depends on whether the address is local or remote. The Stanford DASH multiprocessor of the early 1990s showed how a directory-based coherence protocol could make such a machine scale while keeping a shared-memory programming model [43].
  • Message-passing clusters give each node a private address space and communicate over a network; they are the basis of large-scale systems and are outside the scope of this article.

Today's single-socket chips are themselves small NUMA systems, with many cores, banked shared caches and several memory controllers on an on-chip network [2]. Heterogeneous multicore designs mix core types: Apple's M1, for example, pairs four high-performance cores with four high-efficiency cores [18].

Amdahl's law

Adding cores speeds up only the part of a program that runs in parallel. Gene Amdahl argued in 1967 that the sequential fraction of a workload limits the benefit of parallel hardware [44]. In its usual form, with a parallel fraction f and n processors:

Speedup(f, n) = 1 / [ (1 − f) + f / n ]

With f = 0.9 and n = 8, the speedup is 1 / (0.1 + 0.1125) ≈ 4.7, and no number of cores can push it past 10. Hill and Marty extended the model to multicore chips with a fixed resource budget and showed that asymmetric designs, with one large core for the sequential part and many small ones for the parallel part, can beat symmetric designs [45]. A related constraint is power: Esmaeilzadeh and colleagues projected in 2011 that, because of power limits, a growing fraction of a chip's transistors could not be switched on at full speed at once, a phenomenon they called dark silicon [46].

10. Cache coherence and memory consistency

Once each core has private caches, two separate questions arise [42,47]. Coherence concerns a single memory location: all processors must agree on the order of writes to it, and a read must return the most recent write in that order. Consistency concerns the order in which accesses to different locations become visible: it defines which values loads may return across the whole memory system, and it is part of the ISA's contract with programmers [42,47].

The coherence problem

Suppose cores A and B both cache location X with value 0. If A writes 1 to X in its private cache and B later reads X from its own cache, B sees a stale 0 unless the hardware intervenes. Coherence protocols prevent this, usually by enforcing a single-writer, multiple-reader invariant: at any moment a cache block either has one core that may write it or any number that may only read it [42]. Most protocols are write-invalidate: before writing, a core obtains exclusive permission and invalidates other copies. Write-update protocols instead send the new value to sharers [2].

Snooping and directory protocols

Snooping protocols broadcast every coherence request on a shared bus or ordered network, and every cache watches ("snoops") the traffic and responds for blocks it holds. Goodman's 1983 write-once scheme showed how caches on a shared bus could cut memory traffic while remaining consistent [48]. Papamarcos and Patel's 1984 protocol, often called the Illinois or MESI protocol, added an Exclusive state so that a processor reading data that no one else holds can later write it without a bus transaction [49].

Broadcast does not scale to many cores. Directory protocols keep, for each memory block, a record of which caches hold it, and send messages only to those caches. Censier and Feautrier described a directory solution to multicache coherence in 1978 [50], and DASH demonstrated a distributed directory in a scalable multiprocessor [43]. Large multicore chips use directories or snoop filters held alongside the shared cache [42].

The O state lets a dirty block be shared without first writing it back to memory; Nagarajan et al. describe MOESI and other variants in detail [42].

Memory consistency models

Coherence alone does not say what a program with several shared variables will see. Leslie Lamport defined sequential consistency (SC) in 1979: the result of any execution is the same as if the operations of all processors were executed in some single sequential order, and the operations of each processor appear in that order as specified by its program [51]. SC is intuitive but forbids many hardware optimizations, such as letting a load bypass an earlier store held in a write buffer [47].

Real ISAs therefore specify relaxed models and provide fence (memory barrier) instructions that restore ordering where software needs it [42,47]:

  • Total store order (TSO). x86 processors behave as if each core had a first-in, first-out store buffer: a core's loads may complete before its own earlier stores become visible to other cores, but all cores see stores in one global order. Sewell and colleagues formalized this as x86-TSO [52].
  • Weak ordering and release consistency, introduced by Gharachorloo and colleagues for scalable shared-memory machines, allow most reordering and use synchronization operations (acquire and release) as the points where order is enforced [53].
  • Arm uses a weakly ordered model; in ARMv8 it was revised to be "other-multicopy atomic," which Pulte and colleagues formalized in 2018 [54].
  • RISC-V defines the RISC-V Weak Memory Ordering model (RVWMO) as its default [25].

Programming languages sit on top. The C++11 memory model, whose foundations Boehm and Adve set out, promises sequentially consistent behavior to programs free of data races and lets compilers map atomic operations onto each ISA's fences and ordered instructions [55].

11. Hardware virtualization support

History and the formal requirements

A virtual machine monitor (VMM), or hypervisor, lets several operating systems run on one physical machine, each in its own virtual machine. IBM pioneered the idea in the 1960s with CP-40 and CP-67, which led to the VM/370 time-sharing system [56]. In 1974 Popek and Goldberg stated the conditions a VMM must meet: equivalence (programs behave as on the real machine), resource control (the VMM keeps full control of resources) and efficiency (most instructions run directly on the hardware). They proved that a VMM can be built for a conventional third-generation architecture if the set of sensitive instructions, those that read or change privileged machine state, is a subset of the privileged instructions, those that trap when executed in user mode [12]. In that case the guest operating system can run deprivileged, and every sensitive operation traps to the VMM, a technique called trap-and-emulate.

The x86 problem and software solutions

The original x86 architecture did not meet this condition: some sensitive instructions behaved differently in user and kernel mode without trapping, so pure trap-and-emulate was impossible [57]. VMware worked around this with binary translation, rewriting guest kernel code on the fly so that problematic instructions were replaced with safe sequences [57]. The Xen project took a different route, paravirtualization, in which the guest operating system is modified to call the hypervisor explicitly instead of executing privileged instructions [58].

CPU virtualization extensions

Intel's VT-x, described in 2005, added a new processor mode structure: VMX root operation for the hypervisor and VMX non-root operation for guests. Transitions are called VM entries and VM exits, and a memory-resident virtual-machine control structure (VMCS) holds guest and host state and specifies which events cause exits [17]. AMD introduced comparable support known as AMD-V or SVM [57]. Adams and Agesen, comparing the approaches in 2006, found that first-generation hardware support did not yet outperform mature binary translation, mainly because VM exits were expensive and memory virtualization was still done in software [57].

Arm added virtualization extensions with a hypervisor mode (EL2 in ARMv8), which KVM/ARM used to bring the Linux KVM hypervisor to Arm processors [59]. RISC-V's "H" extension, ratified in 2021, turns supervisor mode into hypervisor-extended supervisor mode (HS-mode) and runs guests in virtual supervisor (VS) and virtual user (VU) modes [19,60].

Memory virtualization

A guest operating system manages its own page tables that map guest virtual addresses to what it believes are physical addresses. Early hypervisors maintained shadow page tables, software-maintained tables that map guest virtual addresses directly to host physical addresses, which required trapping guest page-table updates [57]. Hardware two-dimensional or nested paging removes this work: the processor walks the guest's page tables and a second, hypervisor-controlled table in hardware. AMD calls this nested paging, and Bhargava and colleagues showed that page-walk caching can contain the cost of the longer two-dimensional walk [61]; Intel calls its version extended page tables (EPT) [23]. RISC-V's H extension defines the same two stages, a VS-stage translation from guest virtual to guest physical address and a G-stage translation from guest physical to supervisor physical address [60].

12. System-on-Chip (SoC) architecture

From chipsets to single dies

A system-on-chip integrates most of a computer's components on one die: processor cores, caches, graphics and other accelerators, memory controllers, and I/O interfaces. Wolf, Jerraya and Martin traced how multiprocessor SoCs (MPSoCs) emerged in embedded systems such as phones and media devices, where cost, power and size favored integrating heterogeneous processors and specialized hardware on a single chip [62]. The same forces now shape laptops and servers. Integration shortens the distance between components, which lowers latency and the energy spent moving data, and it lets designers add special-purpose blocks that do common tasks far more efficiently than general-purpose cores [26,62].

Building blocks

  • CPU clusters, often heterogeneous: high-performance cores for latency-sensitive work and efficiency cores for background tasks [18].
  • Graphics processing units for graphics and data-parallel compute.
  • Domain-specific accelerators such as neural-network engines, image signal processors and video encoders and decoders. Hennessy and Patterson argue that such domain-specific architectures are the main route to further gains in performance per watt now that general-purpose scaling has slowed [26]; Google's TPU is a well-known data-center example of the approach [63].
  • Memory subsystem: memory controllers, often a system-level cache shared by all blocks, and in some designs memory in the same package.
  • On-chip interconnect. Early SoCs used shared buses; as the number of blocks grew, Benini and De Micheli proposed networks on chip (NoCs) with routers and links that carry packets between blocks, borrowing ideas from computer networks [64].
  • Security, power management and I/O: secure enclaves, power and clock controllers, storage controllers and high-speed external interfaces.

Example: Apple M1

Apple announced its M1 SoC for Mac computers on 10 November 2020. Built on a 5-nanometer process with 16 billion transistors, it combined an eight-core CPU (four high-performance and four high-efficiency cores), up to eight GPU cores, a 16-core Neural Engine, an image signal processor, a Secure Enclave, media encode and decode engines, a storage controller with encryption hardware and a Thunderbolt controller with USB 4 support. Its unified memory architecture placed high-bandwidth, low-latency memory in a single pool within the package, so that every block could reach the same data without copying it between separate memories [18]. The design illustrates several themes from this article at once: heterogeneous multicore (section 9), a coherent shared memory system (section 10) and domain-specific accelerators beside general-purpose cores.

Design trade-offs

SoC architects must decide which functions deserve dedicated hardware, how to share memory bandwidth among blocks with very different access patterns, how to keep caches and accelerators coherent, and how to power-gate blocks that are idle. Power limits mean that not every block can run at full speed at the same time, which is one reason heterogeneous, specialized hardware has become attractive [26,46]. Complexity has moved from a single processor into the coordination of many processors and accelerators on one die, with the on-chip network and the memory system as the components that tie them together [62,64].

Conclusion

The ideas in this article build on each other. The stored-program model defines what a processor must do; the ISA defines the contract with software; the datapath and control unit carry out the instruction cycle; pipelining, superscalar issue and out-of-order execution overlap and reorder that cycle to extract instruction-level parallelism; and when single cores ran into power and ILP limits, designers replicated cores, which brought the problems of coherence and consistency. Hardware virtualization extends the privilege model so that one machine can host many, and systems-on-chip integrate cores, accelerators and memory on a single die. Hennessy and Patterson describe the present as a new golden age for the field, driven by open instruction sets, domain-specific hardware and new security concerns [26]. The underlying principles, though, remain the ones that von Neumann, Wilkes, Tomasulo, Lamport and Popek and Goldberg set out decades ago.
