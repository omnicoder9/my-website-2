The asymmetry nobody declares

A language model is a distribution over token sequences. A tool is a thing in the world with a type signature, a failure mode and, often, a bank account attached. Function calling is the name the industry gave to the machinery that joins them, and the name is half right: it describes the outbound half, the part where a sampler is squeezed into a shape a parser will accept, and says nothing about the inbound half, where bytes the model did not produce and cannot audit are pasted into its context and read with the same fluency as its own prior tokens.

Both halves are crossings of the same boundary and neither is symmetric with the other. Going out, the industry has built an impressive apparatus: schemas, validators, grammar-derived masks, repair loops, abstract-syntax-tree matchers. Going in, in the default architecture, there is essentially nothing. The result of a web search and the result of a division arrive in the same envelope, with the same standing, and are read the same way.

That asymmetry is this article's subject. The claim is not that inbound verification is missing because nobody thought of it — a large literature has thought of it [1,2,3] — but that the two halves are enforced by mechanisms of categorically different strength, that the strength on each side varies enormously across the twelve places a tool call touches, and that the variation is systematic. Where the tool is a closed formal system — a relational database, exact arithmetic, a deterministic program — inbound claims can be checked to the bit. Where the tool touches the world — a search index, a messaging API, another company's CRM — the inbound claim collapses to provenance: you know who said it, and nothing else. Meanwhile the outbound apparatus is roughly as strong in both cases, because a schema does not know or care what is on the other end of the wire.

So the organising question is: where does the guarantee come from? For each call site, what mechanism actually makes the outbound obligation hold, what mechanism can check the inbound claim, and how far apart are the two? The answer is rarely the mechanism the vocabulary suggests. "Structured outputs" sounds like a guarantee about content; it is a guarantee about shape, and it buys that shape by moving the model's distribution somewhere it would not otherwise have gone. "Function calling" sounds like calling a function; the only property anything checks is that the arguments type-check. "Idempotency" is the one place in the whole stack where a hard guarantee is available, and it is available precisely because the model is not allowed to participate in it.

This is not a new problem and the outbound half has a clear lineage. Retrieval and browsing were bolted on first, with a human-feedback loop to keep the citations honest [4,5]; the calculator arrived as a training-time annotation, with GSM8K's solutions carrying explicit arithmetic markers that a tool could execute [6]. Then came the two moves that made everything since possible: interleaving reasoning with actions so a model could condition on what a tool returned [7], and teaching a model to insert its own API calls by self-supervision, keeping only those calls that reduced perplexity on the continuation [8,9]. Scaling followed — thousands of APIs retrieved rather than enumerated [10,11], models orchestrating other models [12,13], and benchmarks to measure any of it [14]. What did not follow, at anything like the same rate, was machinery for deciding whether the thing that came back was true.

A note on what this article is not. It is not a tutorial: there are excellent ones, and the protocol documentation is good [15,16]. It is not a survey of the tool-learning literature, which has been surveyed [17]. It is an attempt to be precise about a distinction that practice keeps eliding — between an obligation that is enforced and one that is merely requested, and between a result that is checked and one that is merely received. Twelve numbered call sites follow, each scored on two ladders, and the ledger at the end sorts them by the gap.

Two ladders

Every claim in this article about how strong a mechanism is gets placed on one of two six-rung ladders. The ladders are ordinal, not numeric: rung four is stronger than rung three, and no arithmetic on the difference is intended beyond counting how many rungs apart the two sides of a call site sit.

The enforcement ladder asks what makes the outbound obligation hold. It runs from asking nicely to not letting the model near the value at all. The checkability ladder asks how much of the inbound claim can be established without simply trusting the tool's word. It runs from unattributed free text to a claim that is true by construction, because the tool is the thing the claim is about.

Two features of these ladders matter more than their exact wording.

The first is that the top of the enforcement ladder is reached by removing the model, not by improving it. E5 is not a better-trained sampler; it is a value the sampler never emits — an idempotency key minted by the client, a session handle threaded by the harness, a sandbox boundary the program cannot argue with. This is why the strongest guarantee in the stack, exactly-once effect, is also the one least discussed in the tool-use literature: it is not a machine-learning result. It is a distributed-systems result from the 1970s [18,19], and the recent protocol work has been rediscovering it. The 2026-07-28 revision of the Model Context Protocol, which retired session state from the transport, put the reasoning plainly: if a server needs state across calls, mint an explicit handle from a tool and have the model pass it back as an argument, because a handle the model can see works better than state hidden in the transport [20]. That is E5 as a design principle — make the guaranteed thing an opaque token, and let the model carry it without being asked to understand it.

The second is that the checkability ladder is not a ranking of tool quality. V5 is not "good"; it is a statement about what the claim is. When a database returns a row, the claim "our system of record holds this" is unfalsifiable in a specific and useful sense: the database is the referent, so there is no gap between the report and the fact. The moment the claim becomes "and this is true of the world" — that the address is where the customer lives, that the balance reflects yesterday's settlement — the referent moves outside the tool and the rung drops to V1. Most production incidents involving a database tool are not about the first claim. They are about somebody scoring the second claim as though it were the first.

How the plates are scored

Each of the twelve call sites gets a plate with the same five fields — what the call site binds, what enforces it, what the inbound claim is, what checks it, and what a violation looks like on the wire — plus an evidence line and a divergent gauge showing the two rungs. Rungs are assigned from the stated criteria on the ladders, by argument, and they are the weakest part of the apparatus: a reader who thinks tool-result interpretation deserves V1 rather than V0 because a URL is usually attached will not find that unreasonable. The finding is not any single placement. It is the shape of the whole set, which is robust to shifting two or three plates by a rung.

A word on the published numbers, since tool use is measured badly and often. The evaluations quoted here differ in what they hold fixed: abstract-syntax-tree matching against a reference call [21], state transitions in a simulated service [22,23], execution against live third-party APIs whose variance is itself a confound — which is why a stabilised re-release of one such benchmark exists [24] — retrieval-style question answering over documents and tables [25], web search with multi-hop recovery [26], and end-to-end task completion in an operating system or a repository [27,28,29]. Cross-benchmark comparison is therefore mostly illegitimate, and the field's own methodological audit found cost unreported, baselines undertuned and held-out sets thin [30]. Numbers here are used to establish direction and order of magnitude, never to rank systems.

Where a plate cites a number, that number comes from one of two places. Published results are cited to their source in the usual way. Everything else comes from a lab of nine deterministic experiments, written in the Python standard library with no randomness that is not seeded, run at build time, and reproduced verbatim below. The lab is not an evaluation of any model. Several of its experiments are exact enumerations of small formal objects — a grammar of 180 strings, a six-checkpoint fault model, a carry-chain recurrence — chosen precisely because they can be computed rather than estimated. Two of them (arity, retries) are parameterised by stated assumptions rather than measurements, and are labelled as such; what they establish is the shape of a relationship, not its height.

I

The declaration

what the model is asked to guarantee before anything crosses

Before any bytes move, three things have to be settled: what the tool says about itself, what shape the model's answer must take, and how the two are joined. All three are usually discussed as plumbing. All three are places where an obligation is created, and in two of the three nothing whatsoever enforces it.

The tool definition is the load-bearing fiction of the entire arrangement. A name, a sentence or two of description, and a JSON Schema [31] constitute the model's whole picture of a capability it will never observe directly. The schema is machine-checked against the arguments the model produces; it is checked against nothing at all on the other side. There is no mechanism — not in OpenAPI [16], not in MCP [15], not in any vendor's tool API — that verifies that archive_ticket archives tickets, or that the due_date field wants an ISO 8601 date rather than a Unix timestamp.

It is worth being precise about how thin the formal layer is. The interchange syntax is a two-page grammar [34,35]; the schema vocabulary adds types, ranges, enumerations and required-field lists [32]; the transport, in the protocol that has become the default, is remote procedure calls in that syntax [36]. Nothing in that stack has a slot for a precondition, a postcondition, an invariant, a unit, or a statement about what the tool does to the world. The contract is a type signature without a specification, and every specification-shaped thing — conventions, correlations between fields, what counts as a sensible call — travels as prose.

The gap this leaves is not a gap in structure. It is a gap in convention, and it is exactly the gap that shows up in production. A schema can say that reporter.id is a string; it cannot say that your API expects USR-12345 rather than a bare integer or a UUID. It can say escalation.sla_hours is an integer; it cannot say that critical tickets carry a four-hour SLA and feature requests carry none. Anthropic's engineering write-up of this problem is unusually direct about the diagnosis — JSON Schema defines what is structurally valid but cannot express usage patterns — and the fix is telling: not a richer schema language but worked examples, which lifted internal parameter accuracy from 72% to 90% [33]. Examples are an E1 mechanism. They move a prior. They guarantee nothing. And they beat the guarantee-shaped thing because the failure they address was never a well-formedness failure.

Structured output is where the strongest outbound machinery lives, and it works. Compile the schema to a finite-state machine or a grammar, run it alongside decoding, and mask every token that cannot continue to an accepting string [37,38,39,41]. Invalid output does not become unlikely; it becomes impossible. Nothing else in this article achieves that.

The reason it is worth belabouring how rare well-formedness is: over a seven-symbol alphabet and eighteen positions there are 1.9 × 1015 strings, of which 180 are grammatical objects — a fraction of 9.5 × 10-14 lab L1. A trained model is enormously better than chance at finding them: on that toy, the model concentrates 4.4 × 108 times more probability mass inside the grammar than counting alone would predict. But it still leaves the overwhelming majority of its mass outside, which is why the mask exists and why "just prompt it to return JSON" is an E0 answer to an E4 problem.

What the mask costs is subtler than it looks, and the toy is small enough to settle exactly rather than argue about. Masking is local: at each step it removes tokens that cannot lead anywhere legal, then renormalises what is left. It does not, and cannot cheaply, weight the surviving tokens by how much grammatical future lies beyond them. The resulting distribution over legal strings is therefore not the model's own conditional distribution given legality — the object rejection sampling would give you. On the lab's grammar the total variation distance between the two is 0.4805: the mask satisfies the constraint and lands almost half its mass in the wrong place. Greedy decoding under the mask returns a string whose likelihood is 0.19 times that of the most likely grammatical string, and the true conditional's mode receives 0.0228 of the masked distribution's mass against 0.1469 of its own. This is Park and colleagues' result [40], reproduced here at a scale where every quantity is exact.

That distortion is the theoretical half of a live empirical dispute. Tam and colleagues reported that format restrictions degrade reasoning [42]; practitioners replied that the effect was an artefact of prompting and schema design [43]; a benchmark built to settle it found the picture genuinely mixed [44]. The 2026 position is sharper and more interesting: Lee and colleagues decompose the loss by when it arrives and find that the dominant cost is not the decoder at all but the prompt — asking for a format costs most of the accuracy before any token is masked — with the practical corollary that reasoning and formatting should be separated into two passes [45]. They also report that recent closed-weight models show little of the effect, which a concurrent paper disputes by evaluating nearer the capability frontier [46]. A third strand finds that structural constraints can suppress tool calls outright [47]. None of this is settled. What is settled is the direction of the mechanism: the constraint is real, the constraint is not free, and the price is paid somewhere other than where the guarantee is claimed.

Two implementation details deserve mention because they are where the guarantee actually leaks. The first is that grammars are defined over characters and models emit tokens, so a mask computed on the character language can accept a token that straddles a boundary the grammar meant to forbid, or reject a token whose prefix was legal — the alignment problem that token-healing hacks and, properly, subword-aligned constraint engines address [48,49]. The second is that the constraint need not be a grammar at all: a monitor can consult a type checker or the repository's symbol table at each step, which enforces a property no context-free description can state [50]. Between them sits a design question the field is still arguing about — whether to constrain hard and lose reasoning room, or to admit reasoning-shaped regions into the grammar and constrain only where it matters [51]. Production serving stacks now treat all of this as a first-class scheduling concern rather than a decoding trick [52].

There is a second, quieter finding worth carrying forward. BFCL's format sensitivity study varied five presentation dimensions — return syntax, documentation syntax, tool-call tags, plain text versus Markdown, and prompt wording — across 26 configurations and 39 models, on 200 entries drawn from a 2,351-entry pool [53]. Models did better returning calls in Python or JSON than in either XML variant, and several models trained specifically for tool use collapsed to near-zero accuracy when the return format changed underneath them. That is not a fact about grammars. It is a fact about training distributions wearing a grammar's clothes, and it means the same schema, in two notations, is two different obligations.

Function calling proper is the join: pick a name, fill the arguments, hand it over. The enforcement available is validate-and-retry, which is a real mechanism with a real limit — it terminates on validity, the only property it can test.

The limit is quantifiable. Give a call eight required arguments of mixed kind — three enumerations, three typed scalars, one free-form string, one nested object — and assume per-field reliabilities that favour the constrained kinds. On those assumptions the call type-checks 92.87% of the time and is the right call 52.15% of the time lab L2. The 7.13% that fails validation is precisely the part a repair loop can see; two retries clear 99% of it. The 40.72% that is valid and wrong raises no error, triggers no retry, and constitutes 85.1% of all failures.

The assumptions are stated rather than measured and the exact heights should not be quoted as findings. The shape should. Validity is multiplicative in the number of fields and so is correctness, but they decay at different rates, and the band between them — the region a schema validator is structurally incapable of entering — widens monotonically with arity. Every argument you add to a tool buys a little more precision and a lot more silent failure, which is a reason to prefer several small tools to one general one that would otherwise be defensible only on aesthetic grounds.

Two field kinds behave differently and the difference is instructive. An enumeration is the one place where the schema constrains meaning, not just type: there are four legal priorities and the model must pick one of them, so validity and correctness are much closer together. A free-form string is the opposite: it always type-checks, so its entire error rate falls into the invisible band. The design advice follows immediately and is more useful than most: every free-form string in a tool schema is an unmonitored failure channel, and turning one into an enumeration converts invisible errors into visible ones.

II

The crossing

the one call site where the guarantee is real, and is not the model's

Everything so far has been about a string. At some point the string becomes a request, the request crosses a network, and the properties that hold are no longer properties of a grammar.

The invocation is the only call site in this article with a hard guarantee available, and it is worth being precise about why. The guarantee is not that the model chose well or that the arguments were right. It is that the effect happens once. And the mechanism is not learned, prompted or validated: it is an idempotency key [55] — a value generated outside the sampler, echoed by the server, used to collapse retries onto a single effect. The model never emits it. That is the whole point, and it is the defining property of the top rung: the guarantee holds because the model is not party to it.

Without that mechanism, the arithmetic is unforgiving. Under a lognormal latency distribution with a 350 ms median, a timeout at the median produces exactly 2.000 side effects per logical operation; at the 95th percentile it still produces 1.0526, which is 5.3% duplicated writes lab L8. Moving the timeout out to the 99.9th percentile reduces duplication to 0.1% and costs 5.6 seconds of client patience per stuck call — the tail-at-scale trade, unchanged by any of this [57].

None of this is new. The impossibility at the bottom of it is the two-generals result [18], the design consequences were written down for RPC forty years ago [19], and the warning against pretending a remote call is a local one is thirty [54]. What is new is the participant. A retry loop written by a human has a human's model of what a timeout means. A retry loop driven by a language model has whatever the transcript implies, and the transcript is the problem: a timeout and a failure produce the same shape of token. The model reads "error: deadline exceeded", concludes reasonably that the operation did not happen, and tries again. It is not reasoning badly. It is reasoning correctly from a premise the protocol never established, because the protocol cannot establish it.

The operational vocabulary for this is mature and mostly absent from agent frameworks: bounded retries with backoff and jitter, circuit breakers that stop a failing dependency from consuming the caller [58], deduplication keyed on a client-supplied identifier [56], and the distinction between an operation that is safe to repeat and one that is merely likely to be [59,60]. The authorisation layer has been catching up faster than the reliability layer: the same protocol revision that removed session state also required issuer validation on the OAuth path, closing an authorisation-server mix-up [20,61].

The protocol layer has been converging on the right answer, which is to move state out of the transport and make it an explicit, model-visible argument. MCP's 2026-07-28 revision retired the initialize handshake and the session header outright, and its rationale for handles-as-arguments is a distributed-systems argument rather than a modelling one [20,62]. The same revision requires method and tool names to travel in HTTP headers so that gateways can route and authorise without parsing the body — which is to say, it moved the enforcement point outside anything the model produces.

III

Five kinds of result

the tool classes, ordered by how much of their answer can be checked

The taxonomy that industry uses — search, databases, calculators, code execution, external applications — looks like a list of use cases. Ordered by what can be checked on the way back, it turns out to be a list of epistemic categories, and the ordering is almost the reverse of the ordering by popularity.

Search is the lowest-enforcement call site in the set and one of the two lowest on checkability. The outbound obligation — a query string — is satisfied by any string at all, which means the schema is doing no work whatsoever. The real obligation is to ask for the thing that would settle the question, and that has no mechanical expression: there is no validator for a badly chosen query.

Inbound, the result is text about the world, with a URL attached. The URL is provenance, and provenance is genuinely valuable — it is the difference between V0 and V1, and the entire attribution literature exists to make it meaningful [1,68]. But provenance is not verification, and the gap shows up whenever anyone measures it: an evaluation of generative search engines found that a minority of generated sentences were fully supported by their own citations [2]. Retrieval also brings problems that are not about truth at all. Irrelevant retrieved passages degrade reasoning even when the relevant passage is present [65,66]; long contexts are used unevenly, with middle positions systematically underweighted [69,70]; and when retrieved text contradicts what the model already believes, the resolution is not principled — it depends on how confident each source sounds [71,72,73].

There are mechanisms that raise this rung and they are worth naming, because the plate's V1 is a statement about the default, not a ceiling. A model trained to emit retrieval and critique tokens can decide when to retrieve and grade what came back [74]; a system that quotes verbatim and is scored on whether the quote supports the claim converts an unverifiable assertion into a checkable one [68]. Neither establishes that the source is right, which is the recurring limit: attribution is a claim about provenance and the hallucination literature is consistent that provenance is not truth [75,76].

And retrieved text is the front door for indirect prompt injection [67,77], which is not a search problem but a tool-result-interpretation problem, and is treated at T11.

The database is the one call site in the set where inbound checkability exceeds outbound enforcement, and understanding why is worth more than the fact.

Outbound, a query language is a formal language, so the full structured-output apparatus applies — and did, early: incremental parsing against the grammar and the live schema was demonstrated for text-to-SQL before "structured outputs" was a product category [78,79]. A constrained decoder can reject a column name that does not exist in this database, which is a genuinely stronger guarantee than schema validation, because it is checked against the world rather than against a declaration about the world.

Inbound, the claim is definitionally checkable, but only the narrow claim. When the tool returns rows, the assertion "the system of record holds these rows" has no gap between report and fact; the relational model is precisely the discipline of making stored relations the referent [82,83]. The wider assertion — that those rows are true of the world — is a different claim with a different rung, and confusion between the two is where database tools do their damage.

Between the two sits the gap that text-to-SQL benchmarks were built to measure: the difference between a query that executes and a query that answers the question [80,81]. A wrong join returns rows. A date boundary off by one day returns rows. An inner join that silently drops the customers with no orders returns rows, and they are all real. Execution accuracy is a V-side measurement masquerading as an E-side one, and the plate's failure signature is drawn directly from it.

The calculator is the call site everyone uses as the pedagogical example, and it is genuinely the best-behaved one: E4 outbound, V4 inbound, the only entry in the set where a routine mechanism can independently establish that the returned value is the right value. It is also the one where the standard explanation of why the tool is needed is wrong in an instructive way.

The usual story is that models are bad at arithmetic. The sharper story is that arithmetic contains serial dependencies whose length is unbounded in the input, and a fixed-depth architecture has to represent them some other way. Log-precision transformers sit inside uniform TC0 [88], and — this is the part the usual story omits — division and iterated multiplication are also in uniform TC0 [89], so the complexity class does not forbid the arithmetic. What it forbids is learning it as an unbounded serial procedure. The observed failure is therefore length generalisation, not arithmetic per se [90,91,92,93], and the fixes that work are representational: position-coupled digit embeddings recover addition far beyond the training length [87], and the tasks a transformer learns to generalise on are the ones expressible as short parallel programs [86].

The theory is worth stating carefully because it is routinely overstated in both directions. Attention has known representational limits on certain unbounded dependencies [94], and a transformer's ability to recognise formal languages tracks the Chomsky hierarchy in ways a recurrent network's does not [95]. But chain of thought changes the accounting: intermediate tokens are serial computation, and a model permitted enough of them is strictly more expressive than one that must answer in a single forward pass [96]. That is the precise sense in which a calculator and a scratchpad are the same kind of remedy, differing in who does the arithmetic and therefore in whether the result can be checked.

The carry chain makes this exact. In n-digit addition, a position generates a carry, propagates one, or absorbs it; a chain is a generating position followed by a run of propagating ones, and its length is the depth of serial dependency that must be resolved. The distribution is computable in closed form — Knuth worked out the average as an exercise in analysis [85] — and the lab computes the exact tail: at 64 digits the expected longest chain is 2.23 and 2.71% of additions contain a chain of four or more; at 128 digits that rises to 5.48% lab L4.

Read that as an error budget. A rule that resolves chains up to length three and pattern-matches the rest has an error rate bounded below by the tail beyond its depth — 2.71% of 64-digit additions, rising with n, which is the observed signature. The calculator does not make the model better at addition. It moves the serial dependency onto a device designed around it, which is what adders have been since the first machine designers wrote down what carry propagation costs [97].

What delegation does not remove is the choice of arithmetic. The lab's tax computation rounds 1,000 line items two defensible ways and gets $412.89 and $412.91 lab L5; summing ten thousand dimes in binary64 lands 1.6 × 10-10 away from a thousand dollars [84,98]. Neither is a bug. Both are choices, and no schema in the stack has a place to record which one the caller meant. The tool call is exact; the specification is not.

Code execution is the interesting case because the obligation it enforces is not the one you would guess. Nothing constrains the program to be correct. What is enforced, at the top rung, is confinement: the program may do what the sandbox permits and nothing else, and the sandbox is a mechanism that does not consult the model. System-call filtering [107], a hypervisor boundary [105], a user-space kernel [106], a verified instruction subset [108,109] — all of them treat generated code exactly as the literature has treated untrusted code since Lampson posed the confinement problem [103,104,110].

Inbound, determinism buys the third rung: run it again and compare, and add a test suite to go further, which is how generated code has been evaluated from the beginning [101,102]. That is the strongest routine inbound check on this list, and it is available for exactly the reason the database's is — the referent is a closed formal system.

The second thing code execution buys is architectural, and it has become the most consequential recent change in how tool calls are made. If the model writes a program that calls the tools, rather than emitting one call per inference pass, then loops, conditionals, filtering and joins happen in the program, and only the result enters the context. Anthropic reports average context on complex research tasks falling from 43,588 to 27,297 tokens, twenty-plus round trips collapsing into one, and a 200 KB intermediate becoming a 1 KB answer; internal knowledge retrieval moved from 25.6% to 28.5% and GAIA from 46.5% to 51.2% [33,111,112]. The idea is not new — program-aided prompting made it in 2023 [99,100] — but its application to orchestration rather than to computation is, and it changes the accounting: intermediate results that never enter the window cannot mislead the model, cannot be injected into, and cannot be lost in the middle of it.

The last tool class is everything else: send the message, update the record, cancel the meeting, issue the refund. These are the calls people actually want agents for, and they are the worst-served on both ladders. Outbound, the enforcement is post-hoc validation and, if someone has bothered, a human approval gate — neither of which is a property of the call. Inbound, the receipt is provenance and nothing more, and reading the state back is another call with the same problem.

One partial answer to the enforcement problem at this call site is to let the agent build its own tools and reuse the ones that worked, which converts an unconstrained action space into a growing library of validated procedures — the skill-library pattern demonstrated in an open-ended environment where every proposed skill had to survive execution before it was kept [117]. The training-data analogue is the same move applied to trajectories: generate multi-turn interactions against a simulated user and keep only those that pass a verifier [118]. Both work by adding a mechanical acceptance test where none existed, which is the general shape of every genuine improvement in this article.

The distinguishing feature is not difficulty but irreversibility. Undo is a property of the target system. It is not in HTTP [116], not in MCP [15], and cannot be, because a protocol cannot promise what an application does not implement. Every guarantee at this call site is therefore borrowed from the application, negotiated per integration, and absent by default.

The measured consequence is a persistent gap between talking about an action and taking one. Dual-control benchmarks, where both the agent and a simulated user can change the world, sit well below single-control performance on the same domains [113,114]; long-horizon computer-use tasks average hundreds of tool calls each and are still solved at low rates [115,119]; and studies of multi-agent traces find that a large share of failures are specification and inter-agent misalignment rather than reasoning errors [120]. The common structure is that a wrong action at step k is not observable at step k. It is observable when somebody reads their email.

IV

The two judgements

choosing the tool, and reading what it said

Two things at a tool call site are judgements rather than mechanisms: which tool to reach for, and what the answer means. Both are unenforced on the way out and unchecked on the way back, and between them they account for most of what goes wrong in a system where every individual component is working.

Tool selection is where catalogue growth turns a determinate choice into an underdetermined one, and the way it does so is easy to miss because the obvious metric does not move.

The lab holds forty requests fixed and grows the catalogue around them from 40 to 1,152 tools, where the added tools share a verb and an object with the targets and differ only in a qualifier — which is what happens when a second and third server is connected. Raw top-1 accuracy reads 1.000 at both ends. The mean margin over the runner-up collapses from 0.419 to 0.000, the number of tools scoring within 2% of the top rises from 1.00 to 4.00, and accuracy net of a tie-break that carries no information falls from 1.000 to 0.250 lab L3. The retriever is right because the target's description happens to be the shortest of the tied set. That is length normalisation, not relevance.

Two things follow. The first is a measurement warning: top-1 on a retrieval benchmark can be a report about the tie-break rather than about the retrieval, and the margin is the diagnostic. The second is architectural: once k tools are tied, no ranking improvement helps, because the request genuinely does not contain the information that separates them. The correct move is to ask the user. Almost nothing in the tool-calling stack rewards that; abstention is a scored category in BFCL [21,121] and a rare one elsewhere.

The context cost compounds it. Definitions for fifty-eight tools across five servers run to roughly 55,000 tokens before the first user message, with a single issue-tracker server contributing about 17,000; Anthropic reports seeing 134,000 tokens of definitions internally before optimisation [33]. The lab's synthetic catalogue reaches 151,932 tokens at 1,152 tools, against a flat ~1,024 for a scheme that loads one search tool and expands four definitions on demand lab L3. Deferring definition loading moved internal evaluation scores from 49% to 74% on one model and 79.5% to 88.1% on another [33] — improvements attributed to context savings, though the mechanism is not separated from the reduction in tie-breaking, and both are plausible.

There is a caution to record. Independent testing of on-demand discovery against a purpose-built optimiser reported markedly lower retrieval accuracy for the generic search tool at catalogue sizes in the thousands. That comparison comes from a vendor of the competing product and is not, on its own, a result; but it points at something the lab corroborates from a different direction, which is that discovery does not remove the ambiguity, it relocates it.

The final judgement is the least defended position in the entire architecture. A tool result arrives as tokens in the same window, in the same format, with the same standing as everything else. Nothing marks it as data rather than instruction, and nothing checks what its values mean.

Take the values first, because the boring failure is more common than the dramatic one. The lab counts the encodings of a single six-field record under plausible convention choices: 3,840 distinct wire forms of the same fact. Four of them are surface forms that two different logical values share exactly — 03/04/2026 is the fourth of March and the third of April; 1.234 is one thousand two hundred thirty-four and one and a bit lab L7. A strict parser rejects all but one form. A lenient parser accepts the ambiguous ones and silently picks a value, and the model, reading prose, has no signal that a choice was made. This is why RFC 3339 exists [124,125], and why "the model misread the result" is usually a euphemism for "two components disagreed about a convention and neither said so".

Now the standing of the text. Indirect prompt injection is the case where content in a tool result is written to be read as instruction [67,77], and its persistence is a structural fact rather than a modelling failure. The architecture provides no channel separation: instructions and data are the same tokens. Training a priority ordering helps and does not settle it [122,123]; benchmarks exist to measure it [126,127,128]; and the strongest results come from giving up on the model entirely and enforcing outside it. CaMeL extracts control and data flow from the trusted user query and runs a custom interpreter that mediates every tool call against capability policies, solving 77% of AgentDojo tasks with provable security against 84% undefended [3] — an E5 mechanism, at a measured cost in capability. A design-pattern paper generalises the move [129], and privilege-control systems report indirect-injection success rates falling from 39.9% to 1.0% [130]. A 2026 adaptive evaluation is the necessary corrective: most headline numbers are measured against static injection sets, and attackers who know the defence recover substantially [131].

The attack surface is also wider than text. Adversarial inputs can be optimised to make an agent call the wrong tool with attacker-chosen arguments, which is the T10 failure induced deliberately [132]; and the industry's own risk register now lists excessive agency and unverified tool output alongside the prompt-level attacks [133].

The exposure arithmetic explains why this is not a marginal risk. With a 2,000-token system prompt and 800-token results, untrusted text passes half the context window after three calls; at 30 calls it is 91.6% of the window. And it persists: over a thirty-call run with the whole transcript retained, results collectively sit in front of 465 downstream decisions, 15.5 per result lab L6. Keeping only the last four results cuts that to 114 — which is what programmatic orchestration achieves as a side effect of never putting the intermediates in the window at all.

V

The seam

what a failure looks like, and when anyone finds out

Everything above assumed the failure was visible. It usually is not, and the pattern of which failures are visible is not arbitrary.

The lab's last experiment builds a small formal world — three typed tools, a handful of identifiers, a table of true answers — and asks a precise question of six fault classes. A fault is visible at a checkpoint when no correct execution anywhere in the intent space produces the same observation there. That turns detectability into a set-membership computation rather than an opinion lab L9.

Three classes are visible to a mechanical check that runs before the result is used. Malformed output fails the parser. A wrong argument type fails the schema validator. An unknown tool name fails the catalogue lookup. These are the classes the industry has tooling for, and it is worth noticing that they are also the classes that structured outputs already eliminates — which means the tooling and the guarantee are pointed at the same three-sixths of the problem.

The other three are not detectable at any mechanical checkpoint, and the reason is structural rather than incidental. A wrong tool, called with well-typed arguments, returning a well-shaped result, produces observations that are pointwise identical to those of a correct call. So does a right tool called with a well-typed wrong value. Separating them requires the task's own reference — an oracle the pipeline does not have, because if it had a reference answer it would not need the tool. And the sixth class is worse still: a correct call answered incorrectly by the tool is invisible even to that reference, because the call itself was right. It requires an independent second source.

The obvious response — have the model check its own work — runs into the same wall from the inside. Iterated self-critique with an external signal works, and the signal is doing the work: Reflexion's gains come from execution feedback and test results, not from introspection [136], and self-refinement helps most where a task has a cheap external grader [137]. Where there is no external signal, controlled studies find that models do not reliably improve their own reasoning and sometimes degrade correct answers into incorrect ones [138], and the planning literature reaches the same conclusion by a different route: a model is a good generator of candidate plans and a poor verifier of them, so the verifier should be a separate, sound component [139,140]. Mapped onto this article's ladders, self-critique is a V0 mechanism dressed as a V4 one. It moves nothing, because it has no referent the model did not already have.

The cost of late detection is arithmetic. A fault at a uniformly chosen position in a fifty-call run is followed by 24.5 further calls — 49% of the run spent building on a wrong premise lab L9. This is the same finding that multi-agent failure taxonomies arrive at empirically, where the largest categories are specification problems and inter-agent misalignment rather than reasoning errors, and where the authors are explicit that better base models will not be sufficient [120].

It is also, precisely, the ironies-of-automation result [141]. The components that fail visibly get monitored, so their failures become rare and cheap. The components that fail silently accumulate the residual risk, and the human left to catch them is out of practice, working from a transcript in which every step looks green [142,143,144]. Error conventions help at the margin — a problem document is better than a stringified exception [134] — but a convention is an E2 mechanism, and E2 is not where the residual risk lives.

The aggregate is the article's finding. Mean enforcement across the twelve sites is 2.67 rungs; mean checkability is 1.67. Every call site, on average, holds the model to a standard one full rung above the standard the world is held to. Eight of twelve are outbound-heavy, three are level, and exactly one — the database — can check more than it enforces.

The clustering is sharper than the average. Every site scoring V3 or above is a site where the tool is a closed formal system: a relational database, exact arithmetic, a deterministic program. All three of them. Nothing that touches the world — no search index, no messaging API, no third-party application — scores above V1, and the two judgement sites score V0. Checkability is not distributed according to how much the call matters, how much it costs, or how irreversible it is. It is distributed according to whether the thing on the other end is a formal object, and formal objects are the ones we least needed help with.

The same reading explains why the recent engineering wins have the shape they do. Programmatic tool calling [33,111], capability-mediated interpreters [3], idempotency keys [55], deferred tool loading, protocol handles minted by tools rather than sessions hidden in transports [20]: every one of them works by moving a decision out of the sampler and into a mechanism. None of them makes the model more reliable. They make the model's reliability matter less, at the specific points where it was load-bearing and unchecked.

What would actually close the gap

If the gap is between what is enforced outbound and what can be checked inbound, there are two ways to close it, and only one of them is being worked on hard.

The first is to keep raising enforcement, which the field is doing well: better grammars, cheaper masks, deferred loading, code-as-orchestration, capability interpreters. The returns here are real but bounded in a specific way — every one of these mechanisms guarantees a property of the call, and the failures that dominate are properties of the match between the call and the intent. No amount of E5 makes a well-formed call the right call. The lab's L2 and L9 are the same observation from two directions: the enforceable properties and the consequential properties are nearly disjoint sets.

The second is to raise checkability, which mostly means manufacturing referents that do not currently exist. Some of this is cheap and underused. Making a tool deterministic and its result reproducible moves it from V1 to V3 for the cost of removing a timestamp. Returning a structured result with an explicit convention declaration — units, calendar, rounding mode — collapses most of the 3,840 encodings to one. Having a second, independent implementation of a critical computation gives V4 for the price of writing it twice, which is what safety engineering has always charged [144,146]. And for the classes where no referent exists, the honest response is not a better checker but a smaller blast radius: irreversibility is a property of the target system, so scope the capability rather than the prompt.

The most durable practical advice on the subject predates most of the machinery and still holds: prefer the simplest composition that works, add agentic autonomy only where the task genuinely needs it, and treat the tool interface as a first-class design surface rather than a wrapper [147]. Read through the ladders, that advice is a rung argument. Every step from a fixed workflow toward an autonomous loop trades an enforced constraint for an unchecked claim.

There is a third response, which does not close the gap so much as decline to open it: notice when the request is underdetermined, and say so. The lab's tool-selection result is the clean case: at four tied candidates the retriever is not making a decision, it is reporting a tie-break, and the useful output is a question rather than a call. That there is almost no machinery for this — no rung on either ladder for "declined to guess" — says something about what the current stack is optimised for.

The question this article opened with was where the guarantee comes from. For the outbound half, the answer is now good and getting better, and it comes from automata and from architecture rather than from the model. For the inbound half, the answer at the nine call sites scoring V2 or below is: it comes from the assumption that the tool told the truth, which is not a guarantee, and which nothing in the protocol stack has ever claimed to be one.
