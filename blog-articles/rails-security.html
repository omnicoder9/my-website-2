01 Framework & threat model

The defaults are the argument

Rails has shipped continuously since July 2004, and for most of that time its security story has been the same story told once per release: take a protection that careful developers were applying by hand, make it a framework default, and accept the upgrade pain.1 Escaping in templates, forgery tokens in forms, allow-listed parameters, encrypted cookies, encrypted credentials, a content security policy DSL, constant-time credential checks, rate limiting, a first-party authentication generator — each arrived as an opt-in and then became something you have to deliberately switch off.

That trajectory produces an unusual property. A Rails application generated today is, out of the box, resistant to most of the injection classes that dominated web application security for two decades. The framework's own guide is blunt about the limits of this: security is not plug-and-play, it depends on the people using the framework, and it depends on every layer beneath the application.2 The failures that actually reach production in 2026 are rarely "Rails forgot to escape HTML". They are stale framework versions, missing authorisation checks, leaked secrets, over-permissive admin surfaces and business logic that trusts the wrong actor.3

This article covers the mechanisms Rails provides, the history that produced them, the ways applications routinely defeat them, and the tooling and standards that surround them. Code is written against Rails 8.1, the current stable series as of mid-2026; version-specific behaviour is called out where it matters.

Threat model in one paragraph

Assume the client is hostile and fully controls every byte it sends: URL, query string, body, headers, cookies, upload filenames and MIME types. Assume it can also cause a victim's browser to issue requests carrying that victim's cookies. Assume any string that reaches a template, a SQL fragment, a shell command, a file path, a redirect target or a deserialiser is attacker-chosen unless you can point at the line of code that constrained it. Rails' guide frames the same posture as understanding attack methods before choosing countermeasures.2 Everything below follows from that.

How Rails handles vulnerabilities in itself

Rails runs a coordinated disclosure process. Reports go through a HackerOne program rather than public issue trackers; the security team acknowledges the report, works under embargo, notifies distributors through distros@openwall, and publishes to the public security announcements list the moment the embargo lifts.4 The maintenance policy divides work into new features, bug fixes, security issues and severe security issues, and specifies which release series are still eligible for each.5 The practical consequence for an application team is simple and frequently ignored: if your series is out of the security window, no patch is coming, however severe the finding.6

02 Chronology

Fifteen years of moving protections into the defaults

The history is worth knowing because the escape hatches in modern Rails are mostly artefacts of the migrations that introduced each default. Every html_safe in a legacy codebase is a fossil of the Rails 3 escaping switch; every permit! is a fossil of the strong parameters migration.

2009–2010: escaping by default

Before Rails 3, template output was unescaped unless the developer wrapped it in the h() helper. Michael Koziarski's October 2009 commit inverted that: strings carry an "html safe" flag, the ERB buffer became a SafeBuffer that escapes anything unsafe concatenated into it, and a raw helper was added for content the developer asserts is trusted.7 Yehuda Katz's contemporaneous write-up states the resulting rule compactly: a plain String passed into <%= %> is always escaped; a SafeBuffer never is.8 The change was backported to Rails 2.3 as the rails_xss plugin so that existing applications could adopt it incrementally.9

March 2012: mass assignment becomes a headline

Egor Homakov had filed an issue on the Rails tracker about the prevalence of mass-assignment vulnerabilities; it was closed on the grounds that securing applications was the application developer's job.10 He then demonstrated the problem against the nearest large Rails application. GitHub's public key form updated a PublicKey record straight from the submitted parameter hash, so adding a public_key[user_id] field attached his key to another account — in the demonstration, the Rails organisation's — giving him push access to the framework's own repository.11 GitHub suspended the account, reinstated it after establishing no malicious intent, and used the incident to publish a disclosure policy.12,13 By Homakov's own later account he regretted the disclosure route, while noting that GitHub patched within an hour and Rails within five.11

January 2013: parameter parsing to remote code execution

CVE-2013-0156 remains the most severe vulnerability in Rails' history. Action Pack's XML parameter parser honoured type annotations that allowed a request body to be decoded as YAML or as a Ruby Symbol, and YAML deserialisation instantiates arbitrary objects.14 The upstream record describes the failure as improperly restricted casts of string values, permitting object-injection attacks, arbitrary code execution, or denial of service through nested XML entity references, across every 2.3, 3.0, 3.1 and 3.2 release before the patches.15 XML parsing was on by default, so essentially every Rails application was exposed; a Metasploit module followed within days, and the recommended workarounds for teams that could not upgrade immediately were to remove the XML parser or strip the YAML and Symbol type handlers from it.16 The generalised lesson outlived the patch: passing untrusted input to YAML.load is remote code execution, which is why Brakeman still ships a dedicated check for it.17

2013 onwards: the defaults consolidate

Strong Parameters was released as a gem in the Rails 3.2 era in March 2012, weeks after the GitHub incident, and became the default in Rails 4.0 in June 2013.18 Rails 4.0 removed attr_accessible and attr_protected outright in favour of it, with the protected_attributes gem offered as a transitional crutch.19 That gem stopped being supported at Rails 5.0, and the current recommendation is a full migration rather than any of the community forks.20 In the same period CSRF tokens started being masked per request to blunt the BREACH compression side-channel.21 Rails 5.2 brought the Content Security Policy DSL and encrypted credentials.22 Rails 7.0 added Active Record Encryption and open-redirect protection; Rails 7.1 added authenticate_by; Rails 7.2 added controller rate limiting; Rails 8.0 shipped an authentication generator.2,23

03 Action Dispatch

Sessions, cookies and the key that holds them together

Everything that follows — CSRF, authentication, authorisation — rests on the session, so it belongs first. Rails defaults to ActionDispatch::Session::CookieStore, which serialises the session hash into a cookie rather than storing it server-side. Rails encrypts that cookie by default, so it provides both integrity and confidentiality, and both the encryption key and the verification key for signed cookies are derived from secret_key_base.2

The consequences are worth stating explicitly, because the cookie store is a genuine trade-off rather than a free win:2

  • 4 kB ceiling. Session cookies are small. Store identifiers, not objects.
  • The client keeps the bytes. Cookies persist on machines you do not control and can be copied between them. Nothing sensitive belongs in a session, even encrypted.
  • Session cookies do not self-invalidate. A cookie captured today remains valid until something server-side rejects it. This is the replay problem: a user who saves a cookie holding a credit balance, spends the balance, and restores the cookie gets the balance back. The fix is not a nonce; it is keeping mutable state in the database and only the user id in the session.
  • Distinct salts matter. Reusing one salt across signed and encrypted cookie configuration derives the same key for different purposes and weakens both.

Fixation and expiry

Session fixation is the attack where the adversary plants a session identifier they already know — usually via XSS setting document.cookie — and waits for the victim to authenticate into it. One line defeats it:

class SessionsController < ApplicationController
  def create
    user = User.authenticate_by(params.expect(user: [:email_address, :password]))
    return redirect_to new_session_path, alert: "Try again." unless user

    reset_session                       # new session id; the planted one dies here
    session[:user_id] = user.id
    redirect_to after_authentication_url
  end
end

reset_session issues a new identifier and invalidates the old one, which also limits session hijacking. Devise performs this automatically on sign-in and sign-out; hand-rolled authentication must do it explicitly, and must copy across any session values it wants to keep.2 Sessions that never expire widen the window for forgery, hijacking and fixation alike, so server-side expiry — sweeping a sessions table on an interval — is preferable to trusting a client-held expiry timestamp.2

Rotation

Changing cookie configuration without logging everyone out is what rotations are for. Set the new configuration, register a rotation for the old one, let traffic upgrade cookies in place, then remove the rotation:

# config/initializers/cookie_rotator.rb
Rails.application.config.action_dispatch.signed_cookie_digest = "SHA256"

Rails.application.config.action_dispatch.cookies_rotations.tap do |cookies|
  cookies.rotate :signed, digest: "SHA1"     # read old, write new
end

The same mechanism is exposed on ActiveSupport::MessageEncryptor and MessageVerifier for any other signed or encrypted message your application produces.2 Rotating secret_key_base itself is a different matter: it expires every live session, invalidates signed and encrypted cookies, and can affect Active Storage URLs. It is the correct response to a suspected key exposure, but it is a user-visible event and should be planned as one.2

04 Action Pack

Cross-site request forgery

CSRF exploits an asymmetry in how browsers handle credentials: a request originating from any site carries the cookies for its destination. An attacker page cannot read your application's responses, but it can cause a state-changing request that the application will happily authenticate. The countermeasure is a token the attacker's page cannot obtain.

What Rails actually does

Forgery protection is on for new applications through config.action_controller.default_protect_from_forgery, which is equivalent to declaring protect_from_forgery with: :exception in ApplicationController.2 Rails stores a random token in the session, embeds a derived value in every generated form and in the csrf-token meta tag, and verifies it on every non-GET request.24 Three details are worth understanding, because they explain behaviour that otherwise looks like a bug.

Masking. The value in the page is not the session token. Rails generates a fresh random one-time pad per request, XORs it with the raw token, and sends the pad concatenated with the result — so the rendered token differs on every response.24 This was added deliberately to mitigate BREACH, the compression side-channel attack that recovers predictable plaintext from TLS responses; a token that appears identically in every response is an ideal target.21 If you have ever wondered why the meta tag changes on refresh, that is why.

Per-form tokens. With per_form_csrf_tokens enabled, the raw token is not the session token but an HMAC-SHA256 over the session token, the normalised action path and the HTTP method.24 A token harvested from one form is then useless against a different endpoint.

Origin checking. With forgery_protection_origin_check enabled, Rails additionally compares the Origin header against the request's own origin, so a token replay from a foreign origin fails even if the token is valid.24

Getting it right in a modern front end

Turbo reads the token from the meta tags and sends it as X-CSRF-Token.2 Any other client has to do the same:

<!-- app/views/layouts/application.html.erb -->
<head>
  <%= csrf_meta_tags %>
</head>
// Minimal fetch wrapper for non-GET requests
const token = document.head.querySelector("meta[name=csrf-token]")?.content;

await fetch("/orders", {
  method: "POST",
  headers: { "Content-Type": "application/json", "X-CSRF-Token": token },
  body: JSON.stringify(payload)
});

Failure modes

  • GET with side effects. Rails does not verify tokens on GET, because GET is assumed idempotent. A destructive GET route has no CSRF protection at all, and never will have.2
  • Persistent login cookies. If "remember me" state lives outside the session, invalidating the session on a token failure does not log the attacker's victim out. Handle it explicitly: 
    class ApplicationController < ActionController::Base
  rescue_from ActionController::InvalidAuthenticityToken do
    sign_out_user           # clear your own persistent cookies too
    redirect_to new_session_path, alert: "Your session expired. Please sign in again."
  end
end
  • JavaScript responses served to <script> tags. Cross-origin script tags cannot be distinguished from same-origin ones, so Rails blocks JavaScript responses to non-XHR requests. Actions that deliberately serve JSONP-style payloads must skip protection explicitly — and should not contain anything sensitive.2
  • Skipping wholesale for APIs. Token-authenticated APIs that never read a cookie do not need CSRF tokens, because there is no ambient credential to forge with. APIs that authenticate by cookie do, whatever their content type.
  • XSS defeats it entirely. Script running in your origin can read the token out of the DOM. There is no CSRF configuration that survives an XSS bug.2

A contested detail

In April 2025 a Full Disclosure post argued that masking as implemented is not meaningfully protective, since the one-time pad is transmitted alongside the masked token and can therefore be used to recover and re-mask the raw value.25 The observation about reversibility is correct by construction — masking was proposed as a BREACH countermeasure, whose goal is to make the ciphertext differ per response, not to hide the token from a client that already legitimately receives it.21 Whether that framing fully answers the critique is a live argument in the community; what is not in dispute is that neither position changes application-level guidance, since the session token remains unreadable across origins.

05 Action View & Active Support

Cross-site scripting

Rails escapes template output by default, which removes the large majority of reflected and stored XSS from a typical application. What remains is the set of places where the application asserts that a string is trusted. The interesting question is never "does Rails escape?" but "where did this string acquire its safe flag?"

The three assertions

<%= @comment.body %>              <!-- escaped. Correct default. -->
<%= raw @comment.body %>          <!-- NOT escaped. Trust asserted, nothing checked. -->
<%== @comment.body %>             <!-- identical to raw, easier to miss in review -->
<%= @comment.body.html_safe %>    <!-- identical again, and the most common in the wild -->

<%= sanitize @comment.body, tags: %w[p br strong em a ul ol li],
                            attributes: %w[href title] %>
<!-- filtered against an allow-list, then marked safe. The only safe way
     to render user-authored markup. -->

The OWASP Rails cheat sheet is explicit that any field rendered through raw, html_safe or similar is a potential XSS target.26 Treat every occurrence in a codebase as a finding requiring justification, and grep for them as a routine part of review.

Allow-lists, not deny-lists

The Rails guide's historical example is instructive: early versions of strip_tags removed known-bad substrings, so an attacker submitted nested tags such that removing the inner occurrence reconstituted a valid <script> tag.2 Deny-lists fail the same way against encoding tricks, mixed-case variants, and JavaScript in CSS properties. Both Action View and Action Text build their sanitisation helpers on the rails-html-sanitizer gem, which is allow-list-based.2

The places escaping does not reach

  • Attribute and URL contexts. HTML escaping does not make a javascript: URL safe. A user-supplied value interpolated into link_to's href is an injection point; validate the scheme yourself.
  • JavaScript contexts. Interpolating a Ruby value into an inline script needs json_escape or a data attribute, not HTML escaping.
  • Controller-rendered strings. Actions that return a string directly rather than rendering a view bypass the template escaping entirely; escape in the controller.2
  • Client-side rendering. A JSON payload rendered into the DOM by your own JavaScript is outside Rails' escaping altogether. This is where most remaining XSS in modern Rails applications lives.
  • Mutation after marking. Once a SafeBuffer has been mutated in place, its safety flag may no longer describe its contents — which is precisely the bug behind CVE-2026-33170, where SafeBuffer#% failed to propagate the unsafe flag to the formatted result, so a mutated buffer formatted with untrusted arguments reported itself as safe and bypassed auto-escaping.27

Custom CSS is a scripting surface

The Samy worm on MySpace is the canonical demonstration: MySpace blocked script tags but permitted style attributes, and some browsers of the era executed JavaScript from CSS URL values, so the payload rode in on background:url('javascript:…') with eval used to reconstruct blocked strings.2 The guidance that follows is unchanged: if you need user-selectable styling, take structured input — a colour, an image identifier — and generate the CSS yourself rather than accepting a stylesheet.2

06 Active Record

SQL injection

Active Record parameterises values whenever you let it. find, find_by and hash conditions bind their arguments; the risk lives in the methods that accept SQL fragments, where escaping has to be applied deliberately.2 The framework has spent a decade narrowing that surface, but it has not eliminated it, and it cannot: raw SQL remains a legitimate requirement.

The safe constructions

# Positional binding
Order.where("total >= ? AND placed_at > ?", params[:min], 30.days.ago)

# Named binding
Order.where("total >= :min AND placed_at > :since", min: params[:min], since: 30.days.ago)

# Hash conditions — always bound, always safe
Order.where(status: params[:status], customer_id: current_user.id)

# Chain rather than concatenate
Order.where(customer_id: current_user.id).where("total >= ?", params[:min])

# Outside a model instance
ActiveRecord::Base.sanitize_sql(["status = ?", params[:status]])

# LIKE patterns need their own escaping — % and _ are wildcards
Order.where("reference LIKE ?", "%#{Order.sanitize_sql_like(params[:q])}%")

The first three come straight from the framework's own guidance; the sanitize_sql family exists for code that is not inside a model.2 The sanitize_sql_like case is the one teams forget: binding a value protects against injection but not against a user supplying a pattern of pure wildcards.

The dangerous constructions

# String interpolation into a fragment — the classic
Project.where("name = '#{params[:name]}'")
# → ') UNION SELECT id, login AS name, password_digest AS description, 1,1,1 FROM users --

# Raw execution
ActiveRecord::Base.connection.execute("DELETE FROM orders WHERE id = #{params[:id]}")
Order.find_by_sql("SELECT * FROM orders WHERE reference = '#{params[:ref]}'")

# Column-position methods that accept SQL
Order.calculate(:sum, params[:column])
Order.joins("LEFT JOIN #{params[:table]} ON ...")
Order.delete_by(params[:conditions])

The UNION example is the canonical read primitive: it appends a second query whose column count matches the first, renaming columns so the application displays them — which is why the guide pairs its SQL injection section with a reminder that password digests had better be worth stealing nothing.2 Justin Collins has maintained a catalogue of Active Record methods that forward raw SQL at rails-sqli.org since 2013; it remains the most complete reference on which arguments are and are not sanitised.28

What Rails 6 changed

Sorting is the most common way user input reaches SQL, because order(params[:sort]) looks declarative. Ben Toews' pull request introduced deprecation warnings for non-attribute arguments to the "dangerous" query methods, with known-safe values required to be wrapped in Arel.sql.29,30 Rails 6.1 turned those warnings into errors for order, reorder and pluck; over the same series delete_all and destroy_all stopped accepting arguments, while the newly added delete_by, destroy_by and reselect arrived with the same string-accepting behaviour as where and select.31 The net effect: the old footgun was closed and three new ones opened. Audit accordingly.

# Wrong: user input decides the ORDER BY expression
Order.order(params[:sort])

# Wrong: Arel.sql silences the guard without adding safety
Order.order(Arel.sql(params[:sort]))

# Right: map input onto a fixed set of expressions
SORTS = { "recent" => { placed_at: :desc }, "value" => { total: :desc } }.freeze
Order.order(SORTS.fetch(params[:sort], SORTS["recent"]))

A caveat about nil

Rack and Active Record between them once made params[:token] arrive as [nil], which passes a .nil? check while still generating an IS NULL clause — a bypass documented in CVE-2012-2660, CVE-2012-2694 and CVE-2013-0155. Rails responded with deep_munge, which normalises those shapes before they reach your code; it can be disabled, and should not be.2

07 Action Pack

Mass assignment and strong parameters

Mass assignment is convenience that becomes a vulnerability the moment the parameter hash is attacker-controlled — which it always is. The question is never whether the framework binds parameters to attributes, but where the allow-list lives.

Where the allow-list lives, and why it moved

Rails 3 put the list on the model: attr_accessible for allow-listing and attr_protected for deny-listing. Both were opt-in, and neither expressed the fact that different roles may write different attributes without a declaration per role. Strong Parameters moved the decision to the controller, where request context is available, and made it mandatory: an unfiltered ActionController::Parameters raises rather than assigning.18 Rails 4.0 removed the model macros entirely.19

class ProfilesController < ApplicationController
  def update
    @profile = current_user.profile        # scoping is authorisation, see below
    if @profile.update(profile_params)
      redirect_to @profile, notice: "Profile updated."
    else
      render :edit, status: :unprocessable_entity
    end
  end

  private

  # Rails 8: expect/1 replaces require + permit and returns 400 on a malformed shape
  def profile_params
    params.expect(profile: [ :display_name, :bio, :locale,
                             links_attributes: [[ :id, :title, :url, :_destroy ]] ])
  end
end

Rails 8 added expect as a single-step replacement for require followed by permit, and it is stricter in a way that matters for security rather than only ergonomics: the expected shape becomes part of the contract. Under the old pattern, submitting user=123 where a hash was expected made permit run against a String and raise NoMethodError — a 500, and a small denial-of-service and information-disclosure primitive. expect returns a handled 400 instead. Arrays of nested hashes are declared with the double-bracket syntax.32

The ways applications reopen the hole

  • permit! allows every key, recursively. It exists for internal, non-user-facing parameter hashes and should never appear on a path reachable from a request.
  • Permitting a foreign key. :user_id, :account_id, :organisation_id in a permit list re-creates the 2012 GitHub bug exactly. Derive ownership from the session and scope the query, never from the body.
  • Permitting a role or state column. :admin, :role, :verified, :credits — privilege and money columns should be writable only through explicit, audited actions.
  • Nested attributes. accepts_nested_attributes_for extends the write surface to associated records, including their id — which lets a request rewrite a record it does not own unless the association is scoped.
  • Serialised and JSON columns. Permitting a whole hash column allows arbitrary keys inside it. Enumerate the keys you accept.

Filtering is not authorisation

This is the single most common conceptual error in Rails security review. permit answers "which attributes may be written in this action?" It does not answer "may this user write to this record?" The second question needs either a scoped query — current_user.orders.find(params[:id]) rather than Order.find(params[:id]) — or an explicit policy layer such as Pundit or CanCanCan. Broken access control is ranked first in the OWASP Top 10:2025, where it also absorbs the server-side request forgery category that stood separately in 2021.33,34

08 Active Model & Active Record

Authentication and password storage

Since version 8.0, Rails generates an authentication system rather than assuming a gem. bin/rails generate authentication creates User and Session models, a sessions controller, a passwords controller with a reset flow, an Authentication controller concern, the mailer and the migrations, and adds bcrypt to the Gemfile. It deliberately does not generate a sign-up flow — that is application-specific.2

Hashing

has_secure_password stores a bcrypt digest and adds three validations: presence on creation, confirmation via password_confirmation, and a maximum of 72 bytes. It does not validate minimum length or complexity — that is yours to write.2 The 72-byte ceiling is not arbitrary: bcrypt uses the password as a Blowfish key, and Blowfish keys top out at 72 bytes, so anything longer is silently ignored.35 bcrypt's design goal, set out in Provos and Mazières' 1999 paper, was precisely that its cost be adjustable as hardware improves.36

class User < ApplicationRecord
  has_secure_password
  has_many :sessions, dependent: :destroy

  normalizes :email_address, with: ->(e) { e.strip.downcase }

  validates :password, length: { minimum: 12 }, allow_nil: true
  validate  :password_not_breached, if: -> { password.present? }
end
# config/initializers/bcrypt.rb — benchmark on the hardware that serves logins
BCrypt::Engine.cost = 12 unless Rails.env.test?

bcrypt-ruby's own default cost is 12.37 OWASP sets the floor at a work factor of 10 and tells you to use one as large as verification server performance allows, recommending Argon2id for new deployments and bcrypt at cost 10 or above for existing systems.35 Cost is exponential — each increment doubles the work — so the correct procedure is to benchmark on production-class hardware and pick the highest value that keeps login latency inside budget. In the test environment, drop the cost; otherwise every fixture user costs a quarter of a second.

Verification without a timing oracle

The obvious implementation leaks. User.find_by(email:)&.authenticate(password) returns immediately when no record matches and spends a bcrypt comparison when one does, so response time answers the question "does this address have an account?" without any password. Having confirmed that, an attacker can try credentials from other breaches — password reuse being common — or mount a targeted phishing attempt.38

Rails 7.1 added authenticate_by, which digests the submitted password regardless of whether a record was found, so the elapsed time no longer depends on the answer.39 The pull request author is careful about the limits of the guarantee: timing is not constant in the strict sense, particularly if the lookup column is not indexed.38 It is a substantial improvement rather than a proof.

class SessionsController < ApplicationController
  rate_limit to: 10, within: 3.minutes, only: :create

  def create
    if user = User.authenticate_by(params.permit(:email_address, :password))
      start_new_session_for user
      redirect_to after_authentication_url
    else
      # One message for both failure cases — no enumeration through copy either
      redirect_to new_session_url, alert: "Try another email address or password."
    end
  end
end

The rest of the account lifecycle

  • Rate limiting. Rails 7.2 added rate_limit to Action Controller: a declarative limit keyed by IP address (or any lambda), returning 429 when exceeded.40 Rails 8 added named limits so a single controller can carry both a burst limit and a sustained one.41 For blocklists, safelists and filtering that should happen before the router, Rack::Attack — released by Kickstarter in 2012 — still occupies the layer below.42
  • Password reset. The generated flow issues a token valid for fifteen minutes by default.2 Reset endpoints are the classic enumeration leak: "no account with that address" is a free user list. Return the same response either way.
  • Reset must invalidate sessions. A password change that leaves existing sessions alive does not evict an attacker who already has one.
  • Generic errors everywhere. Sign-in, reset and sign-up should all be indistinguishable between "wrong password" and "no such user".2
  • Privilege separation for admin. Separate credentials, a separate subdomain, and IP restrictions where feasible; the same-origin policy then prevents an XSS bug on the public site from reaching admin cookies.2
09 Action Dispatch

Content Security Policy

CSP is the second line behind output escaping: it tells the browser which script, style, frame and connection sources are legitimate, so that an injection that gets past escaping still does not execute. Rails 5.2 shipped a DSL for it.22

# config/initializers/content_security_policy.rb
Rails.application.config.content_security_policy do |policy|
  policy.default_src :self
  policy.font_src    :self, :data
  policy.img_src     :self, :https, :data
  policy.object_src  :none
  policy.base_uri    :self
  policy.form_action :self
  policy.frame_ancestors :none
  policy.script_src  :self
  policy.style_src   :self
  policy.report_uri  "/csp-violation-report-endpoint"
end

# Per-request nonce; applied to script-src and style-src by default
Rails.application.config.content_security_policy_nonce_generator =
  ->(request) { SecureRandom.base64(16) }
Rails.application.config.content_security_policy_nonce_directives = %w[script-src]

The policy can be overridden per controller, disabled per action, and can take lambdas for per-request values such as a tenant's subdomain.2

Nonces beat unsafe-inline

Retrofitting CSP onto an application with inline scripts tempts you into 'unsafe-inline', which reduces script-src to decoration. Nonces are the documented alternative, and Rails wires them into the helpers:2

<%= javascript_include_tag "application", nonce: true %>
<%= javascript_tag nonce: true do %>
  window.APP_LOCALE = "<%= j I18n.locale %>";
<% end %>

<%# exposes the nonce to code that injects script elements at runtime %>
<%= csp_meta_tag %>

Setting config.content_security_policy_nonce_auto = true attaches the nonce automatically to the relevant helpers, which is useful for third-party view code.2

The caching trade-off

A random nonce per request changes the response body, and therefore the ETag, on every request — which is incompatible with conditional-GET caching. Rails documents the alternative of deriving the nonce from the session id, which preserves ETags at the cost of tying nonce entropy to session entropy, and warns that nonce_auto can cause cache fragmentation.2 There is no configuration that gives you both; pick deliberately.

Deploy in report-only first

# Collect violations without blocking anything
Rails.application.config.content_security_policy_report_only = true

Enforce only once the report stream is quiet. Rails also supports report-only on a per-controller basis, which lets you tighten one area at a time.2

10 Action Dispatch

Security headers, transport and origin controls

Rails emits a set of response headers on every request without any configuration, and leaves a second set for you to enable.2

# The defaults, as Rails ships them
config.action_dispatch.default_headers = {
  "X-Frame-Options"                   => "SAMEORIGIN",
  "X-XSS-Protection"                  => "0",
  "X-Content-Type-Options"            => "nosniff",
  "X-Permitted-Cross-Domain-Policies" => "none",
  "Referrer-Policy"                   => "strict-origin-when-cross-origin"
}

# Tighten, add, or clear
config.action_dispatch.default_headers["X-Frame-Options"] = "DENY"

Two of these merit comment. X-XSS-Protection is set to 0 deliberately: the legacy browser XSS auditors it controlled introduced their own vulnerabilities, and the header is deprecated.2 Referrer-Policy at strict-origin-when-cross-origin prevents paths and query strings — which routinely contain identifiers and tokens — from leaking to third parties in the Referer header.2

Transport

# config/environments/production.rb
config.force_ssl = true   # redirects HTTP → HTTPS, marks cookies secure,
                          # and emits Strict-Transport-Security

One setting covers redirect, cookie flags and HSTS.2 Note that HSTS is sticky by design: browsers remember it, so enabling it on a domain you cannot keep on HTTPS is a self-inflicted outage. Mozilla's web security guidelines, which the Rails guide points to for header and TLS configuration, are the reference for choosing max-age and preload settings.43

Host header and DNS rebinding

ActionDispatch::HostAuthorization rejects requests whose Host header is not in an allow-list, defeating DNS rebinding and Host-header poisoning of generated URLs. It is enabled in development but must be configured explicitly elsewhere:2

# config/environments/production.rb
config.hosts << "app.example.com"
config.hosts << /\Aadmin\.example\.com\z/

config.host_authorization = {
  exclude: ->(request) { request.path == "/up" }   # let the health check through
}

Permissions-Policy and CORS

# config/initializers/permissions_policy.rb
Rails.application.config.permissions_policy do |policy|
  policy.camera     :none
  policy.microphone :none
  policy.geolocation :none
  policy.payment    :self
end
# config/initializers/cors.rb — only if a separate origin must read your API
Rails.application.config.middleware.insert_before 0, Rack::Cors do
  allow do
    origins "https://app.example.com"     # never "*" alongside credentials
    resource "/api/*", headers: :any, methods: [:get, :post, :patch, :delete]
  end
end

Rails uses the Permissions-Policy name for the middleware while still emitting the older Feature-Policy header, pending broader browser support.2 For CORS the framework defers to the rack-cors middleware, which is preconfigured in API-only applications.2 A wildcard origin combined with credentialed requests is the standard misconfiguration; enumerate origins.

Redirects

Open redirects are a phishing primitive and, historically, an XSS one via data: URLs.2 Rails 7.0 made redirect_to validate its target by default, raising ActionController::Redirecting::UnsafeRedirectError for off-host destinations unless allow_other_host: true is passed.44 Upgrading applications enable it by uncommenting raise_on_open_redirects in the new-framework-defaults initialiser.44 Passing a user-supplied parameter together with allow_other_host: true restores the vulnerability exactly.

11 Active Record

Encryption at rest

Rails 7.0 added Active Record Encryption: declared attributes are encrypted before they reach the database and decrypted transparently on read, so a database dump, a replica, a backup or a leaked log does not yield plaintext.45

$ bin/rails db:encryption:init
# emits primary_key, deterministic_key and key_derivation_salt
# for config/credentials.yml.enc
class Patient < ApplicationRecord
  encrypts :notes                                          # non-deterministic
  encrypts :email, deterministic: true, downcase: true     # queryable
end

Patient.find_by(email: "a@example.com")   # works — deterministic
Patient.find_by(notes: "…")               # returns nil — by design

The one decision that matters

Non-deterministic encryption uses AES-256-GCM with a random initialisation vector, so the same plaintext produces different ciphertext every time and the column cannot be queried or usefully indexed. Deterministic mode derives the IV from an HMAC-SHA-256 of the key and the plaintext, so equal plaintexts produce equal ciphertexts — which is what makes equality queries and unique indexes work, and also what makes the column vulnerable to frequency analysis. The guide's recommendation is unambiguous: non-deterministic for everything unless you must query the column.45 Omitting deterministic_key disables deterministic mode entirely, which is a reasonable default for applications that never need it.45

Operational notes

  • Key generation. bin/rails db:encryption:init emits three values into your credentials; generated values are 32 bytes, with documented minimums of 12 bytes for the primary key and 20 for the salt.45,46
  • Column width. Ciphertext plus its JSON envelope is substantially longer than the plaintext. Size columns before migrating, not after.
  • Encryption is not access control. Anything the application can read, application-layer code — and anything that achieves code execution — can read. It defends against theft of data at rest, not against a compromised process.
  • Filter the logs. Encrypting a column while config.filter_parameters lets its value through means the plaintext is in your log aggregator anyway.
12 Railties

Encrypted credentials and secrets management

Rails' answer to configuration secrets has changed several times. Rails 5.1 introduced encrypted secrets in config/secrets.yml.enc; Rails 5.2 replaced them with credentials in config/credentials.yml.enc decrypted by config/master.key or RAILS_MASTER_KEY; Rails 6.0 added per-environment credential files and keys.22,47 Rails 8.0 removed the legacy read_encrypted_secrets toggle, leaving credentials as the built-in mechanism.48

$ bin/rails credentials:edit                       # shared
$ bin/rails credentials:edit --environment production
$ bin/rails secret                                 # generate a new random secret
# decrypted view of config/credentials.yml.enc
secret_key_base: 3b7cd72...
active_record_encryption:
  primary_key: ...
  deterministic_key: ...
  key_derivation_salt: ...
stripe:
  secret_key: sk_live_...
Rails.application.credentials.stripe.secret_key   # → "sk_live_…"
Rails.application.credentials.stripe.secret_key!  # raises KeyError if blank

The encrypted file is designed to be committed; the key is not.2 The bang accessor is worth adopting as a habit — a nil secret usually fails much later and much more confusingly than at boot.

Credentials or environment variables?

Both are in use, and the choice is mostly about who operates the application.

DimensionEncrypted credentialsEnvironment variablesExternal secret manager

A common production arrangement uses credentials for application secrets and environment variables for deployment-specific configuration, with RAILS_MASTER_KEY injected by the platform.48 Work on the Rails main branch is heading towards a combined API — discussed as Rails.app.creds, backed by ActiveSupport::CombinedConfiguration, checking environment variables first and falling back to encrypted credentials — but it has not shipped in a stable release as of mid-2026, so treat the naming as provisional.49,48

Practices that survive contact with production

  • Never commit the key. Rails adds config/master.key to .gitignore; verify it on every repository you inherit, and scan history rather than assuming.2
  • Environment-scoped keys. Per-environment credential files mean a compromised staging key does not decrypt production secrets.47
  • Treat plaintext artefacts as sensitive. credentials:edit decrypts to a temporary file. Editor swap files, backup files and clipboard history all persist it.48
  • Filter aggressively. Extend config.filter_parameters beyond the generated defaults, and remember it does not cover values you interpolate into your own log lines.
  • Have a rotation runbook. Which secrets rotate independently, which require a deploy, which log users out. Write it before the incident.
13 Toolchain

Dependencies, scanning and the patch cadence

Software supply chain failures entered the OWASP Top 10 as a distinct category at position three in the 2025 edition, expanding the older "vulnerable and outdated components" entry to cover dependencies, build systems and distribution infrastructure.33,34 For a Rails application this is mostly a question of whether anyone is watching the Gemfile and the release announcements.

Brakeman was released on 27 August 2010 — two days before Rails 3.0 — as Justin Collins' summer internship project at AT&T Interactive, intended as a stop-gap until commercial tools supported Ruby.50 Sixteen years later it still works across Rails 2.3 through 8.x, emits SARIF and other CI-friendly formats, and exits non-zero on findings so a pipeline can gate on it.51 bundler-audit and the advisory database it consumes are maintained under the RubySec umbrella.52,53,54

Updating without breaking everything

The Rails guide's advice on dependencies is deliberately conservative: Rails does not bump its own dependencies merely to encourage newer versions, because application owners must update regardless, and it points at bundle update --conservative gem_name as the way to move a vulnerable dependency with minimal collateral change.2

$ bundle update --conservative nokogiri     # move one gem, keep the rest pinned
$ bundle exec bundle-audit check --update   # confirm the advisory clears

The cadence you are signing up for

Rails ships security releases across all supported series simultaneously. On 13 August 2025, 7.1.5.2, 7.2.2.2 and 8.0.2.1 addressed CVE-2025-24293 and CVE-2025-55193.55 The first of those is instructive: Active Storage maintains an allow-list of image transformation methods, and three entries in that list could be used to circumvent the safe defaults, enabling command injection where an application accepted user-supplied transformation methods or parameters with image_processing and mini_magick.56,57 On 23 March 2026, 7.2.3.1, 8.0.4.1 and 8.1.2.1 addressed ten issues at once: an unescaped exception page in development mode, multiple XSS vulnerabilities across Action Pack, Action View and Active Support, two denial-of-service vectors in Active Storage range requests, two more in Active Support number formatting, a path traversal and a glob injection in Active Storage's disk service, and insufficient metadata filtering in direct uploads.58

Rails 7.0 and 7.1 reached end of life on 29 October 2025, with 7.0.10 and 7.1.6 as their final releases.6 Five months later those applications had ten unpatched issues and no upgrade path shorter than a version migration — the concrete form of the end-of-life risk.59,60 Not every advisory requires the same urgency, but the decision has to be made from the advisory text, which is why subscribing to the security announcements list matters more than any scanner.4

One further pattern from recent history: CVE-2024-26144 was a sensitive session leak in Active Storage, where blobs were served with both a Set-Cookie header and Cache-Control: public, so an intermediary that cached the response could hand one user another user's session.61 It had been fixed in 7.1.0 as an ordinary bug before anyone recognised it as a security issue. Bug fixes and security fixes are not always distinguishable at the time they land, which is an argument for tracking the current patch level rather than only the advisories.

14 Application surface

Files, redirects, logs and the rest of the attack surface

Uploads and downloads

User-controlled filenames are path traversal waiting to happen, and the guide is specific that filtering should validate against a permitted character set rather than stripping bad sequences — because stripping ../ from ....// yields ../.2 Downloads need the mirror check: confirm the resolved path is inside the expected directory before calling send_file.2

def download
  root = Rails.root.join("storage", "reports").to_s
  path = File.expand_path(File.join(root, params[:name]))
  raise ActionController::BadRequest unless path.start_with?(root + File::SEPARATOR)

  send_file path, disposition: "attachment"
end

Store uploads outside the document root so that a file with an executable extension cannot be served as code, name files on disk by database identifier rather than by submitted name, and process media asynchronously — synchronous image processing is a denial-of-service amplifier.2 Do not trust a client-declared content type: the March 2026 direct-upload advisory exists because internal flags in the blob metadata could be set by the client to skip MIME detection entirely.58

Command execution

user_input = "hello; rm -rf ."

system("/bin/echo #{user_input}")     # shell parses the semicolon
system("/bin/echo", user_input)       # argument vector; no shell involved

open("| ls")                          # Kernel#open executes when the arg starts with |
File.open("| ls")                     # does not

Pass an argument vector rather than a command string, and prefer File.open, IO.open or URI#open over Kernel#open, which executes a command when its argument begins with a pipe.2

Header injection and response splitting

CRLF sequences in a value that becomes a response header allow an attacker to append headers or an entire second response. Rails escapes these for the Location header; anything else you construct from user input is your responsibility.2

Regular expressions

Two distinct problems. First, Ruby's ^ and $ anchor to line boundaries, not string boundaries, so a validation regex without \A and \z can be defeated with an embedded newline. Second, catastrophic backtracking: several 2024–2026 Rails advisories are ReDoS findings in framework helpers, including number_to_delimited in the March 2026 batch.58,27 Application regexes applied to unbounded user input deserve the same scrutiny.

Logging

Logs are a data store with weaker access controls than your database. Filter parameters, avoid interpolating credentials or tokens into log lines, and remember that error-reporting services receive request context by default. Rails also treats log output as an attack surface in its own right — CVE-2025-55193 was ANSI escape injection in Active Record logging.55

Admin interfaces

Admin surfaces concentrate privilege and receive the least attention. The guide's recommendations are worth following literally: separate credentials from the public application, consider restricting by source IP, and place the admin interface on its own subdomain so the same-origin policy prevents an XSS bug on the main site from reading admin cookies.2

17 Judgement

Where reasonable people disagree

A survey that presents every framework default as settled would be misleading. Four questions remain genuinely open.

Should the encrypted credentials file be in the repository at all? Rails' position is that an encrypted blob is safe to commit as long as the key is kept elsewhere, which gives you code and configuration versioned together.2 The objection is that it concentrates every secret behind a single key with no per-secret access control and no read auditing, and that git history preserves every previous ciphertext. Teams with compliance obligations generally end up at an external secret manager regardless; teams without them usually find credentials sufficient.

Is deterministic encryption worth the queryability? The guide states plainly that determinism makes cryptanalysis easier and recommends non-deterministic encryption unless you must query the column.45 In practice email addresses need lookup, which pushes the most obviously sensitive column into the weaker mode. Blind-index designs are the usual alternative and are not built in.

Does CSRF token masking do what it claims? Covered above: the 2025 Full Disclosure post argues the construction is reversible by design, while the original pull request framed masking narrowly as BREACH mitigation rather than concealment.25,21 Both descriptions of the mechanism are accurate; the disagreement is about what property it was ever meant to provide.

Do secure defaults help the applications that most need them? Every hardening default is opt-in for existing applications, arriving as a new-framework-defaults initialiser that upgraders must uncomment. Applications that are years behind — the ones most likely to be vulnerable — are precisely the ones that never reach the release carrying the fix. The March 2026 release is the argument in miniature: the protections existed, and the applications that needed them most were on series that no longer receive them.58,59

18 Closing

What the framework can and cannot carry

Rails gives you escaping, parameterisation, forgery tokens, an allow-list gate on mass assignment, encrypted sessions, encrypted columns, encrypted credentials, a policy DSL for the browser, a default header set, constant-ish credential verification, rate limiting and a coordinated disclosure process behind all of it. That is a large amount of security to receive for typing rails new, and it is why the injection classes that defined web security for twenty years are largely solved problems in a current Rails application.

What it cannot carry is the part that depends on knowing your domain: whether this user may see this record, whether this workflow can be abused, whether this secret should exist, whether anyone is reading the advisories. The guide's own framing — that security depends on the people using the framework and on every layer beneath it — has not needed revision in twenty years.2 The framework's job is to make the safe path the default one. Everything after that is yours.

On using this document

Version-specific behaviour changes between Rails series. Where a mechanism is described as a default, that describes a newly generated application on the current stable series; upgraded applications inherit defaults through the new_framework_defaults initialisers and may not have enabled them. Verify against the release notes for your own version before relying on any behaviour described here.

The authoritative and continuously updated source is the Rails guide, Securing Rails Applications. Security announcements are published to the Rails security announcements category on the official forum the moment each embargo lifts.
