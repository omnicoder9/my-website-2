00The system around the model

A computer vision model that scores well in a notebook is a small part of a working product. Sculley and colleagues at Google observed that in real machine learning systems the learning code is a small fraction of the whole, surrounded by data collection, feature extraction, verification, serving infrastructure, configuration and monitoring, and that each of these accrues its own technical debt [1]. Case studies across industries report the same pattern: most deployment failures come from data management, integration, monitoring and organizational issues rather than from the choice of architecture [2,3].

Vision adds problems of its own. Inputs are large (a single uncompressed 1080p frame is about 3 MB), they come from physical sensors whose geometry and timing must be known, labels are expensive and often noisy, and the world the camera sees changes with lighting, seasons, lenses and firmware. The discipline that handles this is usually called MLOps: the practices, roles and tooling that automate and monitor the path from data to deployed model [4]. This article follows that path end to end.

Three ideas run through every section:

  • Everything is versioned and addressable. Images, labels, calibration files, code, environments and model weights each get an immutable identifier, so any prediction can be traced to the exact inputs that produced it.
  • Every transition is gated by an automated check. Ingestion validates images, CI validates models, deployment validates health, monitoring validates the live input distribution. Google's ML Test Score rubric lists such tests for data, model, infrastructure and monitoring [5].
  • The physical sensor is part of the model. A model trained on one camera's optics, exposure and timing is implicitly calibrated to that camera. Changing the sensor is a distribution shift, and should be managed like one.

01Data pipelines, image ingestion, preprocessing and labeling

The data pipeline turns raw sensor output into training-ready, labeled, versioned examples, and the same preprocessing code must later run in serving. Most silent accuracy losses in production come from a mismatch between these two paths (training–serving skew) [1,5].

Ingestion: land, validate, deduplicate, address by content

A robust ingestion pipeline treats every image as untrusted input. Files arrive truncated, in unexpected color modes (CMYK JPEGs, 16-bit PNGs, palette images), with EXIF orientation flags, or as exact duplicates uploaded twice. The pattern in Figure 2 handles these in stages, each writing to a separate storage zone so a bad batch can be quarantined without touching curated data.

Three details cause a disproportionate share of bugs:

  • EXIF orientation. Phones usually store pixels in sensor order and record rotation in the Exif Orientation tag (tag 274, 0x0112) [6]. Some decoders apply it and others ignore it, so the same file can reach training rotated and reach serving upright. Apply it once, explicitly, at ingestion (Pillow provides ImageOps.exif_transpose) and then strip it [7].
  • Channel order and color space. OpenCV decodes to BGR order by default while Pillow and most training frameworks use RGB [8,9]. Swapped channels rarely crash anything; they quietly cost accuracy.
  • Truncated files. Reading only the header (as some "verify" calls do) does not prove the image decodes. Force a full decode during validation.
ingest.py — validate, normalize orientation, store by content hashPython 3.10+
import hashlib, io, json, pathlib, time
from PIL import Image, ImageOps, UnidentifiedImageError

STORE = pathlib.Path("/data/cas")          # content-addressed store
MANIFEST = pathlib.Path("/data/manifest.jsonl")
MIN_SIDE, MAX_SIDE = 64, 12000

class Rejected(Exception):
    def __init__(self, code: str): super().__init__(code); self.code = code

def normalize(raw: bytes) -> tuple[bytes, dict]:
    try:
        im = Image.open(io.BytesIO(raw))
        im.load()                           # full decode: catches truncation
    except (UnidentifiedImageError, OSError) as e:
        raise Rejected("undecodable") from e
    im = ImageOps.exif_transpose(im)        # apply Exif orientation once
    if im.mode not in ("RGB", "L"):
        im = im.convert("RGB")              # CMYK, P, RGBA, I;16 -> RGB
    w, h = im.size
    if min(w, h) < MIN_SIDE or max(w, h) > MAX_SIDE:
        raise Rejected("bad_size")
    buf = io.BytesIO()
    im.save(buf, format="PNG")              # canonical, lossless, no EXIF
    return buf.getvalue(), {"width": w, "height": h, "mode": im.mode}

def ingest(raw: bytes, source: str, camera_id: str | None, calib_id: str | None) -> str:
    data, info = normalize(raw)
    digest = hashlib.sha256(data).hexdigest()
    path = STORE / digest[:2] / digest[2:4] / f"{digest}.png"
    if not path.exists():                   # idempotent: duplicates are free
        path.parent.mkdir(parents=True, exist_ok=True)
        tmp = path.with_suffix(".tmp")
        tmp.write_bytes(data)
        tmp.rename(path)                    # atomic on POSIX filesystems
        with MANIFEST.open("a") as f:
            f.write(json.dumps({"sha256": digest, "source": source,
                                "camera_id": camera_id, "calib_id": calib_id,
                                "ingested_at": time.time(), **info}) + "\n")
    return digest

Hashing the normalized bytes rather than the uploaded bytes means that two uploads that differ only in metadata deduplicate to one record. Exact hashes miss near-duplicates (re-encoded or resized copies); perceptual hashes or embedding similarity catch those, and are important for preventing leakage of near-identical frames between training and test splits.

Preprocessing: one function, two call sites

Resize policy (stretch, letterbox, center-crop), interpolation method, normalization constants and channel layout are part of the model. Put them in one versioned function that both the training data loader and the serving path import, or bake them into the exported graph. For high-throughput training, decoding and augmentation can move to the GPU with libraries such as NVIDIA DALI, which removes a common CPU bottleneck [10]. Section 04 shows the arithmetic.

Labeling and label quality

Annotation formats should be boring and standard. The COCO format, introduced with the Microsoft COCO dataset, stores images, categories and annotations (boxes, polygons, RLE masks, keypoints) in JSON and is read by most tools [11]. Store labels separately from images, keyed by image hash, so relabeling never mutates pixels and each label set gets its own version.

Labels contain errors, including in curated benchmarks. Northcutt and colleagues estimated an average of at least 3.3% label errors across the test sets of ten widely used datasets, enough to change which model ranks best [12]. Practical controls:

  • Written guidelines with visual examples of edge cases (occlusion, truncation, minimum box size), versioned alongside the labels.
  • Overlap sampling: send a fraction of items to two or more annotators and measure agreement. For categorical labels, Cohen's kappa corrects raw agreement for chance: κ = (po − pe) / (1 − pe) [13]. For boxes, use IoU between annotators.
  • Model-assisted error finding: confident learning uses out-of-sample predicted probabilities to estimate which given labels are likely wrong, so reviewers inspect a short ranked list instead of the whole set [14].
  • Active learning: prioritize unlabeled images where the current model is uncertain or where committee members disagree, which usually reaches a target accuracy with fewer labels than random sampling [15].

Datasheets for datasets provide a template for documenting how data was collected, labeled and intended to be used. Ship one with each dataset version [16].

Exercise 1.1 — The upside-down validation set

A detector reaches 0.71 mAP on images uploaded through your web app but 0.52 on images that customers send from a mobile SDK, although the scenes look similar. Inspecting failures, you see many photos taken in portrait mode. Training used OpenCV's cv2.imread; the SDK path uses Pillow's Image.open. What is the most likely cause and the fix?

Show solution

Exif orientation is being handled differently on the two paths. Portrait phone photos are typically stored in landscape sensor order with an Orientation tag. Recent OpenCV versions apply the tag inside imread by default, while Image.open returns pixels in stored order, so the SDK path feeds rotated images to the model [6–8]. Fix it at ingestion: call ImageOps.exif_transpose once, re-encode without EXIF, and use the same decode function on every path. Add a regression test with a fixture image for each of the eight orientation values.

Exercise 1.2 — Is the labeling guideline working?

Two annotators each label the same 100 images as defect or no defect. Both say defect on 40, both say no defect on 40, A says defect and B says no on 10, and A says no and B says defect on 10. Compute Cohen's kappa.

Show solution

Observed agreement po = (40 + 40)/100 = 0.80. Each annotator says defect 50% of the time, so chance agreement pe = 0.5·0.5 + 0.5·0.5 = 0.50. Then κ = (0.80 − 0.50)/(1 − 0.50) = 0.60 [13]. Raw agreement of 80% looks good, but a third of it is what two coin-flipping annotators would reach. Review the 20 disagreements, extend the guideline with those cases, and re-measure.

02Dataset and model versioning

Code alone does not determine a model's behavior; code plus data plus configuration plus environment does. Versioning gives each of these an immutable identifier and records how they combine. Two tools cover most needs: a data version control layer for large files, and a model registry for trained artifacts.

Data versioning

Git is not designed for gigabytes of images. Tools such as DVC keep small pointer files in Git that contain content hashes of the data, while the data itself lives in a cache and a remote object store [17]. Checking out a Git commit and running dvc pull restores the exact dataset that commit refers to. DVC pipelines (dvc.yaml) additionally record each stage's dependencies and outputs, so stale stages are recomputed and up-to-date ones are skipped.

Note the --group-by site_id in the split stage. Frames from the same video, camera or site are strongly correlated; a random per-image split leaks near-duplicates into the test set and inflates metrics. Split by the unit you will generalize to.

Model versioning and lineage

A model registry stores trained artifacts with a version number, metadata and a lifecycle state, and lets deployment refer to a model by a movable alias rather than a file path. MLflow's registry, for example, supports versions and aliases such as champion, so promotion and rollback reduce to moving an alias [18]. Each version should carry a model card describing intended use, evaluation data, and performance broken down by relevant conditions [19].

Exercise 2.1 — Why did the test score jump?

A colleague retrains with a new random image-level 80/20 split of 40,000 frames sampled from 200 short traffic videos. Test mAP rises from 0.62 to 0.78 with no model change. What happened, and how would you design the split?

Show solution

Leakage. Consecutive frames from one video are near-duplicates, so a random per-frame split puts nearly identical frames in both train and test, and the test set measures memorization. Split by video (or by camera or site if you must generalize to new locations), stratify by condition (day/night, weather), and run a near-duplicate check across splits with perceptual hashes or embeddings. Record the split seed and grouping key as a pipeline parameter so the split itself is versioned [17].

Exercise 2.2 — Minimum metadata for a model version

At minimum: git commit of training code; dataset version (tag or content hash) and split definition; label-set version and guideline revision; training config and hyperparameters including seeds; container image digest (framework, CUDA, cuDNN versions); hardware type; calibration-set IDs of the source cameras; preprocessing version; evaluation metrics overall and per slice with the evaluation-set version; exported artifact hashes (ONNX, engine files) with export settings such as precision; and a model card covering intended use and limitations [18,19]. Serving logs must record the model version and preprocessing version with each prediction to close the loop.

03Experiment tracking and reproducible training

An experiment tracker records, for every training run, the parameters, code version, data version, environment, metrics over time and output artifacts. Without it, teams lose the ability to answer "which run produced this model, and what changed since the last good one?" MLflow is a widely used open-source example; its tracking component logs parameters, metrics and artifacts to a server that also hosts the model registry [18,20].

Levels of reproducibility

Pineau and colleagues, reporting on the NeurIPS 2019 reproducibility program, distinguish between re-running the same code and data and obtaining results that hold up more broadly; their checklist asks for code, data, hyperparameter ranges, number of runs and variance [21]. For a production team, three levels are useful:

LevelGuaranteeWhat it takes
TraceableYou know exactly what produced the modelTracker logs commit, data hash, config, image digest
Statistically reproducibleRe-running lands within the known run-to-run spreadAbove, plus several seeds per config and reported variance
Bitwise reproducibleIdentical weights on identical hardware and softwareAbove, plus fixed seeds, deterministic kernels, fixed worker seeding, same GPU model and library versions

Bitwise reproducibility is expensive and fragile: PyTorch documents that completely reproducible results are not guaranteed across releases, platforms or CPU versus GPU, and that deterministic algorithms can be slower [22]. Aim for statistical reproducibility in normal work and keep a deterministic mode for debugging.

Exercise 3.1 — Sources of nondeterminism

Two runs with the same seed, code, data and container on the same GPU type finish with validation mAP of 0.684 and 0.671. List at least five plausible sources of the difference.

Show solution

(1) Non-deterministic CUDA kernels, for example atomic-add based backward passes for some convolution and scatter/index operations; (2) cuDNN autotuning (cudnn.benchmark=True) selecting different algorithms per run; (3) DataLoader workers with unseeded or identically seeded NumPy/random state, so augmentations differ or repeat; (4) multi-GPU reductions whose floating-point summation order varies; (5) data order changes from filesystem listing order when the manifest is not sorted; (6) asynchronous evaluation on a model still being updated; (7) different driver versions on otherwise identical nodes. PyTorch's reproducibility notes cover items 1–3 [22]. Report the run-to-run spread from several seeds before treating a 0.013 difference as meaningful.

04GPU computing: CUDA, memory management, batching

The execution model in brief

A CUDA program launches kernels over a grid of thread blocks. Each block runs on one streaming multiprocessor (SM); threads are scheduled in groups of 32 called warps, which execute the same instruction together [23]. The GPU has its own memory: a large, high-bandwidth global memory (device DRAM), on-chip shared memory per block, and registers per thread. Data must be copied from host (CPU) memory to device memory across PCIe or NVLink, and that copy is often the bottleneck for vision workloads because images are large relative to the compute done per byte.

The roofline model makes this precise: attainable throughput is the minimum of peak compute and (memory bandwidth × arithmetic intensity), where arithmetic intensity is FLOPs per byte moved [24]. Elementwise preprocessing (normalize, convert layout) has an intensity well under one FLOP per byte and is memory-bound; large convolutions and matrix multiplies are compute-bound and benefit from Tensor Cores and reduced precision.

preprocess.cu — uint8 HWC (as decoded) to normalized float CHW (as the network expects)CUDA C++
#include <cstdint>
#include <cuda_runtime.h>

__global__ void hwc_u8_to_chw_f32(const uint8_t* __restrict__ src, float* __restrict__ dst,
                                  int H, int W, float3 mean, float3 inv_std) {
    int x = blockIdx.x * blockDim.x + threadIdx.x;   // column
    int y = blockIdx.y * blockDim.y + threadIdx.y;   // row
    if (x >= W || y >= H) return;                    // guard partial blocks
    int i = (y * W + x) * 3;                         // interleaved RGB input
    int o = y * W + x;                               // planar output
    int plane = H * W;
    dst[o]             = (src[i]     * (1.f / 255.f) - mean.x) * inv_std.x;
    dst[o + plane]     = (src[i + 1] * (1.f / 255.f) - mean.y) * inv_std.y;
    dst[o + 2 * plane] = (src[i + 2] * (1.f / 255.f) - mean.z) * inv_std.z;
}

void launch_preprocess(const uint8_t* d_src, float* d_dst, int H, int W, cudaStream_t s) {
    const float3 mean    = {0.485f, 0.456f, 0.406f};               // ImageNet statistics
    const float3 inv_std = {1.f / 0.229f, 1.f / 0.224f, 1.f / 0.225f};
    dim3 block(32, 8);                                            // 256 threads, warp-aligned rows
    dim3 grid((W + block.x - 1) / block.x, (H + block.y - 1) / block.y);
    hwc_u8_to_chw_f32<<<grid, block, 0, s>>>(d_src, d_dst, H, W, mean, inv_std);
}

Copying the image as uint8 and converting on the GPU moves a quarter of the bytes that copying float32 would, which matters when the copy is the bottleneck.

Overlapping transfer and compute

Host-to-device copies can only run asynchronously, and therefore overlap with kernels, when the host buffer is page-locked ("pinned") memory and the copy is issued on a non-default stream [25]. In PyTorch this is DataLoader(pin_memory=True) combined with tensor.to("cuda", non_blocking=True) [26]. Figure 4 shows the effect.

Memory management

PyTorch uses a caching allocator: freed blocks stay reserved by the process for reuse, so nvidia-smi shows reserved memory, not live tensors. Use torch.cuda.memory_allocated() for live tensors, memory_reserved() for the cache, and max_memory_allocated() for the peak; the allocator's behavior, including fragmentation-related settings, is configurable through PYTORCH_CUDA_ALLOC_CONF [26]. During training, memory is roughly weights + gradients + optimizer state + activations saved for backward; with Adam in FP32, the first three alone are about 16 bytes per parameter (4 each for weights, gradients and two moment estimates). At inference, activations need not be kept, which is why torch.inference_mode() cuts memory substantially.

Batching

Batching amortizes kernel launch overhead and weight reads over many images and lets matrix units run at high occupancy, so throughput rises with batch size until the GPU saturates. Latency for each image in the batch rises too. Section 05 applies this to serving and Section 08 quantifies the trade-off.

gpu_utils.py — overlapped loading, memory probes, OOM-safe batch searchPyTorch 2.x
import torch
from torch.utils.data import DataLoader

loader = DataLoader(ds, batch_size=64, num_workers=8, pin_memory=True,
                    persistent_workers=True, prefetch_factor=4)

def report(tag: str) -> None:
    mib = 2**20
    print(f"{tag}: allocated={torch.cuda.memory_allocated()/mib:.0f} MiB "
          f"reserved={torch.cuda.memory_reserved()/mib:.0f} MiB "
          f"peak={torch.cuda.max_memory_allocated()/mib:.0f} MiB")

@torch.inference_mode()
def largest_batch(model, shape=(3, 640, 640), start=256, dtype=torch.float16) -> int:
    """Binary-search the largest inference batch that fits, leaving headroom."""
    lo, hi = 1, start
    while lo < hi:
        mid = (lo + hi + 1) // 2
        try:
            x = torch.empty((mid, *shape), device="cuda", dtype=dtype)
            model(x); torch.cuda.synchronize()
            lo = mid
        except torch.cuda.OutOfMemoryError:
            hi = mid - 1
        finally:
            torch.cuda.empty_cache()        # return cached blocks between probes
    return max(1, int(lo * 0.8))            # 20% headroom for fragmentation and variance

model = model.cuda().eval().half()
for images, _ in loader:
    images = images.to("cuda", non_blocking=True).half()   # overlaps with prior compute
    with torch.inference_mode():
        out = model(images)
report("after first batch")

Exercise 4.1 — Will it fit?

You fine-tune a ResNet-50 (about 25.6 million parameters [27]) with Adam in FP32 on 224×224 RGB images at batch size 64. Estimate (a) the memory for weights, gradients and optimizer state, and (b) the memory for the input batch alone. Why is the real peak several GB higher?

Show solution

(a) 25.6 M × 16 bytes ≈ 410 MB (weights 102 MB, gradients 102 MB, two Adam moments 205 MB). (b) 64 × 3 × 224 × 224 × 4 bytes = 38,535,168 bytes ≈ 36.8 MiB. The peak is dominated by activations stored for the backward pass: every convolution, batch-norm and ReLU output for all 64 images. These scale linearly with batch size and with image area, which is why halving resolution or using mixed precision (Section 08) frees so much memory. Measure with torch.cuda.max_memory_allocated() rather than trusting the estimate [26].

Exercise 4.2 — GPU at 35% utilization

Training shows 35% GPU utilization. top shows 8 Python worker processes each near 100% CPU. What is the bottleneck and what are three fixes?

Show solution

The input pipeline: JPEG decoding and augmentation on the CPU cannot keep up. Fixes: (1) move decode and augmentation to the GPU with a library such as DALI [10]; (2) pre-decode and resize to the training resolution once, storing uint8 arrays or smaller JPEGs; (3) add CPU workers if cores are available, and make sure pin_memory=True and non_blocking=True are set so copies overlap with compute [26]. Confirm with a profiler that data-loader wait time drops.

Online serving and dynamic batching

Individual requests arrive one image at a time, but GPUs are efficient on batches. A dynamic batcher holds requests in a queue for at most a few milliseconds and runs whatever has accumulated as one batch. Clipper introduced adaptive batching for low-latency prediction serving [28]; NVIDIA Triton Inference Server exposes it as configuration, with a preferred batch size and a maximum queue delay [29].

Capacity planning starts from Little's law, L = λW: the mean number of requests in the system equals arrival rate times mean time in the system [30]. It holds for any stable queue regardless of distributions, which makes it a reliable sanity check.

from PIL import Image, ImageOps

MEAN = np.array([0.485, 0.456, 0.406], np.float32)
STD = np.array([0.229, 0.224, 0.225], np.float32)

sess = ort.InferenceSession("model.onnx",
        providers=["CUDAExecutionProvider", "CPUExecutionProvider"])
INPUT = sess.get_inputs()[0].name
queue: asyncio.Queue = asyncio.Queue(maxsize=MAX_QUEUE)
ready = False

def preprocess(data: bytes) -> np.ndarray:            # same function as training
    im = ImageOps.exif_transpose(Image.open(io.BytesIO(data))).convert("RGB")
    x = np.asarray(im.resize((224, 224), Image.BILINEAR), np.float32) / 255.0
    return ((x - MEAN) / STD).transpose(2, 0, 1)        # HWC -> CHW

async def batcher() -> None:
    loop = asyncio.get_running_loop()
    while True:
        items = [await queue.get()]
        deadline = loop.time() + MAX_WAIT_S
        while len(items) < MAX_BATCH and (left := deadline - loop.time()) > 0:
            try:
                items.append(await asyncio.wait_for(queue.get(), left))
            except asyncio.TimeoutError:
                break
        batch = np.stack([x for x, _ in items])
        try:   # run the blocking session call off the event loop
            out = await loop.run_in_executor(None, lambda: sess.run(None, {INPUT: batch})[0])
            for (_, fut), row in zip(items, out):
                if not fut.done(): fut.set_result(row)
        except Exception as e:
            for _, fut in items:
                if not fut.done(): fut.set_exception(e)

@asynccontextmanager
async def lifespan(app: FastAPI):
    global ready
    sess.run(None, {INPUT: np.zeros((MAX_BATCH, 3, 224, 224), np.float32)})  # warm-up
    task = asyncio.create_task(batcher()); ready = True
    yield
    task.cancel()

@app.get("/readyz")

@app.post("/v1/classify")
async def classify(file: UploadFile):
    try:
        x = preprocess(await file.read())
    except Exception:
        raise HTTPException(415, "The file is not a decodable image.")
    fut = asyncio.get_running_loop().create_future()
    try:
        queue.put_nowait((x, fut))
    except asyncio.QueueFull:                          # shed load instead of queueing forever
        raise HTTPException(503, "Server is at capacity. Retry with backoff.")
    logits = await fut
    p = np.exp(logits - logits.max()); p /= p.sum()
    top = np.argsort(p)[::-1][:5]
    return {"model": MODEL_VERSION,
            "top5": [{"class_id": int(i), "p": float(p[i])} for i in top]}

A bounded queue gives backpressure: when the GPU is saturated, new requests get an immediate 503 that clients can retry, rather than waiting until they time out. Readiness and liveness are separate endpoints because they mean different things to an orchestrator (Section 07).

Streaming inference

For live video, the right unit is the frame deadline. If inference takes longer than the frame interval, an unbounded queue grows forever and the system reports events from further and further in the past. Keep only the most recent frame, run detection on it, and let a tracker interpolate between detections. Video arrives compressed, usually H.264 or H.265; decoding on dedicated hardware (NVDEC on NVIDIA GPUs, VPU blocks on edge SoCs) keeps CPU free [31].

stream.py — latest-frame reader so latency stays boundedOpenCV
import threading, time, cv2

class LatestFrame:
    """Reads continuously; consumers always get the newest frame and its capture time."""
    def __init__(self, url: str):
        self.url = url
        self.cap = cv2.VideoCapture(url)
        self.lock = threading.Lock()
        self.frame, self.t, self.seq = None, 0.0, 0
        threading.Thread(target=self._run, daemon=True).start()

    def _run(self) -> None:
        while True:
            ok, f = self.cap.read()
            if not ok:
                time.sleep(0.5); self.cap.open(self.url); continue   # reconnect
            with self.lock:
                self.frame, self.t, self.seq = f, time.time(), self.seq + 1

    def get(self):
        with self.lock:
            return self.frame, self.t, self.seq

src = LatestFrame("rtsp://cam-07.local/stream1")
last = -1
while True:
    frame, t_cap, seq = src.get()
    if frame is None or seq == last:
        time.sleep(0.002); continue
    dropped, last = seq - last - 1, seq
    dets = detect(frame)                          # your model
    publish(dets, capture_ts=t_cap, frames_dropped=dropped,
            age_ms=(time.time() - t_cap) * 1000)  # export age as a metric

The time.time() taken after read() returns is only an approximation of capture time. When cameras provide hardware timestamps, use those (Section 11).

Batch inference

Offline jobs maximize throughput and must be restartable. Shard the input manifest, process each shard with the largest batch that fits, write one output object per (model version, shard), and skip shards whose outputs already exist. This makes the job idempotent: re-running after a crash only redoes missing shards. Always record the model version in the output path so that a backfill with a new model never mixes results with the old one.

Exercise 5.2 — Choosing the batch delay

Your SLO is p99 latency ≤ 120 ms. Batch-1 inference takes 18 ms; batch-16 takes 44 ms. Preprocessing and network add 25 ms at p99. What maximum queue delay is safe, and what risk remains?

Shipping the artifact is the start. 07Containers and orchestration: Docker, Kubernetes

Vision services depend on a fragile stack: GPU driver, CUDA runtime, cuDNN, framework, runtime library and system codecs. Containers package everything above the kernel and driver into one immutable image, which gives the same environment in CI, staging and production [39]. GPU access from a container requires the host driver plus the NVIDIA Container Toolkit, which exposes devices and driver libraries to the container at start time (for example with docker run --gpus all) [40].

Building images

Multi-stage builds compile or download dependencies in one stage and copy only the results into a slim runtime stage, which reduces image size and attack surface [41]. Pin base images by digest, install from a lock file, run as a non-root user, and keep model weights out of the image when they change more often than the code (mount them or download by registry version at start-up).

Orchestration with Kubernetes

Kubernetes schedules containers (in pods) across a cluster, restarts failed ones, rolls out new versions and scales replicas. It grew out of Google's experience with the Borg and Omega cluster managers [42]. Three features matter most for inference:

  • GPU scheduling. With a device plugin installed, GPUs are requested as an extended resource such as nvidia.com/gpu. GPUs are specified in limits, and containers do not share a GPU by default [43].
  • Probes. A startup probe protects slow model loading; a readiness probe removes a pod from load balancing until it can serve; a liveness probe restarts a stuck process [44]. Report ready only after the model has loaded and run a warm-up batch.
  • Autoscaling. The Horizontal Pod Autoscaler adjusts replica counts from CPU, memory or custom metrics [45]. CPU utilization is a poor signal for GPU inference; queue depth or GPU utilization exported through a metrics adapter tracks load more directly.

08Performance optimization: mixed precision, quantization, batching

Mixed precision

Mixed precision runs most operations in a 16-bit format while keeping numerically sensitive parts in FP32. Micikevicius and colleagues showed that training with FP16 activations and gradients matches FP32 accuracy across many models when three techniques are used: an FP32 master copy of the weights, loss scaling to keep small gradients from underflowing, and FP32 accumulation of FP16 products [46]. bfloat16 keeps FP32's 8 exponent bits and cuts the mantissa to 7 bits, so it has the same dynamic range as FP32 and usually needs no loss scaling [47]. On GPUs with Tensor Cores, both formats run matrix operations much faster than FP32 and halve activation memory [23].

amp_train.py — automatic mixed precision training loopPyTorch 2.3+
import torch

scaler = torch.amp.GradScaler("cuda")                 # dynamic loss scaling for FP16
for images, targets in loader:
    images = images.cuda(non_blocking=True); targets = targets.cuda(non_blocking=True)
    opt.zero_grad(set_to_none=True)
    with torch.autocast(device_type="cuda", dtype=torch.float16):  # or torch.bfloat16
        loss = criterion(model(images), targets)
    scaler.scale(loss).backward()      # scale up so small gradients survive FP16
    scaler.unscale_(opt)               # unscale before clipping
    torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    scaler.step(opt)                   # skips the step if inf/NaN gradients appeared
    scaler.update()

Autocast chooses per operation: matrix multiplies and convolutions run in the low-precision type, while reductions and losses that need range stay in FP32 [49].

Quantization

Quantization stores weights, and usually activations, as 8-bit integers. Jacob and colleagues defined the affine scheme r = S(q − Z) used by most integer inference engines, and showed that integer-only inference can keep accuracy close to floating point when combined with quantization-aware training [48]. INT8 weights take a quarter of FP32's memory and allow integer matrix units.

  • Post-training quantization (PTQ) needs only a few hundred representative unlabeled images to calibrate activation ranges. Per-channel weight scales and a good calibration method (max, percentile, or entropy) matter; Krishnamoorthi and Wu et al. report that 8-bit PTQ with per-channel weights stays within about 1% of floating-point accuracy for most convolutional networks evaluated [50,51].
  • Quantization-aware training (QAT) simulates quantization during fine-tuning so the network adapts to it. Use it when PTQ loses too much accuracy, as often happens with compact architectures such as depthwise-separable networks [50].

Calibration images must come from the deployment distribution. Calibrating a night-time camera model on daytime images clips the activation ranges that matter at night.

Exercise 8.1 — Quantize by hand

An activation tensor has calibrated range [−2.0, 6.0]. Using asymmetric uint8 quantization, compute S and Z, quantize r = 1.0, dequantize the result, and give the error.

Show solution

S = (6.0 − (−2.0)) / 255 = 8/255 ≈ 0.031373. Z = round(0 − (−2.0)/S) = round(63.75) = 64. q = round(1.0/S) + Z = round(31.875) + 64 = 32 + 64 = 96. Dequantized: S(96 − 64) = 32 × 0.031373 ≈ 1.00392; error ≈ 0.0039, within half a step (S/2 ≈ 0.0157) as expected [48].

Exercise 8.2 — FP16 overflow

An FP16 model produces NaNs in a feature map computed as a sum of squares over a 128×128 window of pixel values on a 0–255 scale. Why, and what are two fixes?

Show solution

The sum can reach 128 × 128 × 255² ≈ 1.07 × 10⁹, far above FP16's maximum of 65,504, so it overflows to infinity and later becomes NaN. Fixes: normalize inputs to [0, 1] first (maximum sum 16,384, which fits), keep this reduction in FP32 (autocast already runs many reductions in FP32 [49]), or use bfloat16, which has FP32's exponent range [47].

Deploying safely and rolling back

Shadow deployment sends a copy of live traffic to the candidate and logs its outputs without returning them, so you can compare against the champion on real inputs with no user impact [55]. Canary releases route a small fraction of traffic to the new version and compare its health and quality signals against the baseline before widening the rollout [56]. Rollback should never require retraining or rebuilding: keep the previous model version and image available, deploy by immutable version, and make "point the alias back" the standard procedure. Practice it, so it works on the day it is needed [5].

gate.py — paired bootstrap and slice checks; exits non-zero on failurePython · NumPy
import json, sys
import numpy as np

def paired_bootstrap_ci(cand: np.ndarray, champ: np.ndarray, n=2000, seed=0, alpha=0.05):
    """CI of mean(cand) - mean(champ) for per-image scores evaluated on the same images."""
    rng = np.random.default_rng(seed)
    m = len(cand); diffs = np.empty(n)
    for b in range(n):
        idx = rng.integers(0, m, m)              # resample images, keep pairing
        diffs[b] = cand[idx].mean() - champ[idx].mean()
    return np.quantile(diffs, [alpha / 2, 1 - alpha / 2])

def main(path: str) -> int:
    r = json.load(open(path))                    # produced by the evaluation job
    cand, champ = np.array(r["candidate"]["per_image"]), np.array(r["champion"]["per_image"])
    failures = []
    lo, hi = paired_bootstrap_ci(cand, champ)
    if lo < -0.005:
        failures.append(f"overall: 95% CI of delta [{lo:+.4f}, {hi:+.4f}] allows a >0.5 pt drop")
    for name, s in r["slices"].items():
        if s["n"] >= 200 and s["candidate"] - s["champion"] < -0.02:
            failures.append(f"slice {name}: {s['champion']:.3f} -> {s['candidate']:.3f}")
    if r["candidate"]["p99_ms"] > r["budget"]["p99_ms"]:
        failures.append(f"latency p99 {r['candidate']['p99_ms']} ms over budget")
    if r["candidate"]["export_top1_agreement"] < 0.999:
        failures.append("export parity below 99.9%")
    for f in failures: print("GATE FAIL:", f)
    print("GATES PASSED" if not failures else f"{len(failures)} gate(s) failed")
    return 1 if failures else 0

if __name__ == "__main__":
    sys.exit(main(sys.argv[1]))

Exercise 9.2 — Designing the canary

Ground-truth labels for production images arrive only after human review, about 48 hours later. What can a one-hour canary check, and what can't it?

Show solution

Within an hour you can compare operational signals (error rate, latency, memory, crash loops) and label-free quality proxies against the champion on the same traffic: prediction class distribution, confidence histogram, detection count per image, agreement rate with the champion (from shadow mode), and the fraction routed to human review [55,56]. You cannot measure accuracy until labels arrive, so keep the canary at a small share for long enough to accumulate reviewed labels on disagreements, or gate full rollout on a 48-hour checkpoint.

10Monitoring, logging, drift analysis, human review

A deployed model fails in two ways. It can fail loudly (errors, timeouts, crashes), which standard service monitoring catches. Or it can fail quietly, returning well-formed but wrong answers because the world changed. Vision models are particularly exposed to the quiet kind: a lens gets dirty, a firmware update changes auto-exposure, a new product variant appears, winter arrives.

Operational monitoring

Start with the four golden signals from site reliability engineering: latency, traffic, errors and saturation [57]. For inference, add queue depth, batch size actually achieved, GPU utilization and memory, frames dropped (streaming), and model load failures. Expose them in a pull-based metrics system such as Prometheus, using histograms for latencies so percentiles can be computed across replicas [58].

Structured prediction logs

Log every prediction as a structured record: request ID, timestamp, model version, preprocessing version, camera ID and calibration ID, input statistics, outputs with scores, and latency. Store a sampled subset of input images (subject to the privacy constraints in Section 12) so that drift alarms can be investigated and reviewed images can become training data.

Kinds of drift

Gama and colleagues' survey distinguishes changes in the input distribution p(x) from changes in the relationship p(y|x) [59]. In practice, three kinds are worth separating:

  • Covariate shift (p(x) changes): new lighting, camera, viewpoint or compression. Detectable without labels.
  • Label shift (p(y) changes, p(x|y) stable): the defect rate rises from 1% to 5%. Black-box shift estimation can estimate the new class proportions from the model's own confusion matrix and predictions, without new labels [60].
  • Concept drift (p(y|x) changes): the definition of a defect changes, or a new look-alike class appears. Generally needs fresh labels to detect.

For detection without labels, Rabanser and colleagues compared many approaches and found that two-sample tests on reduced representations work well, notably on the softmax outputs of a pretrained classifier ("black-box shift detection") [61]. For multivariate representations such as embeddings, the kernel maximum mean discrepancy (MMD) is a standard two-sample statistic [62]. For individual scalar features, the population stability index (PSI) is a simple, widely used summary [63]:

PSI = Σi (ai − ei) · ln(ai / ei)

where ei and ai are the reference and current fractions in bin i. Common rules of thumb treat PSI below 0.1 as stable, 0.1 to 0.25 as moderate change and above 0.25 as major change; these thresholds are conventions, so calibrate them on your own historical data [63].

Do not rely on model confidence as a drift alarm by itself. Ovadia and colleagues found that the calibration of predictive uncertainty degrades under dataset shift, so a model can stay confident while becoming wrong [54,64].

def psi(ref: np.ndarray, cur: np.ndarray, bins=10, eps=1e-6) -> float:
    edges = np.histogram_bin_edges(ref, bins=bins)
    e = np.histogram(ref, edges)[0] / len(ref)
    a = np.histogram(np.clip(cur, edges[0], edges[-1]), edges)[0] / len(cur)
    e, a = np.clip(e, eps, None), np.clip(a, eps, None)
    return float(np.sum((a - e) * np.log(a / e)))

def mmd2_rbf(X: np.ndarray, Y: np.ndarray, gamma: float) -> float:
    """Biased MMD^2 estimate with an RBF kernel (Gretton et al., 2012)."""
    def k(A, B):
        d = (A**2).sum(1)[:, None] + (B**2).sum(1)[None] - 2 * A @ B.T
        return np.exp(-gamma * d)
    return float(k(X, X).mean() + k(Y, Y).mean() - 2 * k(X, Y).mean())

def mmd_permutation_test(X, Y, n_perm=200, seed=0):
    rng = np.random.default_rng(seed)
    Z = np.vstack([X, Y]); n = len(X)
    med = np.median(((Z[:200, None] - Z[None, :200])**2).sum(-1))   # median heuristic
    gamma = 1.0 / max(med, 1e-12)
    obs = mmd2_rbf(X, Y, gamma)
    null = []
    for _ in range(n_perm):
        p = rng.permutation(len(Z))
        null.append(mmd2_rbf(Z[p[:n]], Z[p[n:]], gamma))
    return obs, (1 + sum(v >= obs for v in null)) / (1 + n_perm)    # statistic, p-value

Human review

Human review closes the loop between monitoring and data. Route three streams to reviewers:

  1. Uncertain predictions (scores near the decision threshold, or disagreement between champion and shadow model). These are the most informative to label, which is the active-learning argument from Section 01 [15].
  2. Drift investigations: samples from slices or time windows flagged by drift alarms.
  3. A uniform random sample of all traffic. This stream is essential: uncertainty-selected samples are biased toward hard cases, so only a random sample gives an unbiased estimate of live accuracy.

Reviewed items flow into the label store as a new label version, with the reviewer, guideline revision and review time recorded. Where the model's decisions have significant effects on people, human review is also a governance requirement, not only an engineering choice.

11Camera calibration management and sensor synchronization

Whenever a system measures something in the world (distances, sizes, positions, 3D structure) or fuses several sensors, the model's output depends on calibration parameters as much as on its weights. Those parameters need the same version control, validation and monitoring as the model.

The camera model

The pinhole model maps a 3D point X in world coordinates to pixel coordinates through the extrinsics [R | t] (camera pose) and the intrinsic matrix K [65]:

s·[u, v, 1]T = K [R | t] [X, Y, Z, 1]T, K = [[fx, 0, cx], [0, fy, cy], [0, 0, 1]]

Real lenses add distortion. The Brown–Conrady model, used by OpenCV, combines radial terms k1, k2, k3 and tangential terms p1, p2 [66,67]. With normalized coordinates (x, y) and r² = x² + y²:

xd = x(1 + k1r² + k2r⁴ + k3r⁶) + 2p1xy + p2(r² + 2x²)

Zhang's method estimates K and distortion from several images of a planar pattern such as a checkerboard in different orientations, and is the basis of OpenCV's calibrateCamera [67,68]. The returned RMS reprojection error, in pixels, is the first quality check; values well under one pixel are typical for a good calibration with a sharp target.

Calibration as a managed artifact

  • Identity. Each calibration gets an immutable ID tied to the physical camera's serial number, lens, focus and zoom setting, and resolution. Intrinsics are only valid for the resolution and optical settings at which they were measured.
  • Storage. Store calibrations in a versioned registry next to models, not in config files on devices. Every image record (Section 01) and every prediction log (Section 10) carries its calibration ID.
  • Validation. Gate new calibrations on reprojection error, coverage of the image area by target detections, and plausibility (principal point near the center, focal length near the lens specification).
  • Monitoring. Mechanical shocks, temperature and refocusing change calibration. Check it continuously where possible: reproject fixed fiducial markers in the scene, or compare stereo epipolar error, and alarm when error grows.

Sensor synchronization

Fusing two cameras, or a camera with an IMU, lidar or radar, requires knowing when each measurement was taken in a common time base. Errors come from three sources:

  • Clock offset between devices. Separate devices have separate clocks that drift. The Precision Time Protocol (IEEE 1588) synchronizes clocks over Ethernet and, with hardware timestamping, is designed for sub-microsecond accuracy [69].
  • Trigger and exposure timing. Free-running cameras capture at unrelated instants. A shared hardware trigger makes several cameras expose together. Timestamp at the middle of the exposure, not at readout or arrival on the host, because USB or network buffering adds variable delay.
  • Rolling shutter. Most CMOS sensors expose rows sequentially, so each row has a different capture time; fast motion produces skew, and per-row timing must be modeled for accurate fusion [70].

Residual constant offsets, for example between a camera and an IMU, can be estimated jointly with the spatial calibration; the Kalibr toolbox implements a continuous-time method for this [71,72].

import numpy as np

def match_nearest(t_ref: np.ndarray, t_other: np.ndarray, tol_s: float) -> np.ndarray:
    """For each reference timestamp, index of the nearest other timestamp, or -1 if none within tol.
    Both arrays must be sorted and in the same (PTP-synchronized) time base."""
    j = np.searchsorted(t_other, t_ref)
    j0, j1 = np.clip(j - 1, 0, len(t_other) - 1), np.clip(j, 0, len(t_other) - 1)
    pick = np.where(np.abs(t_other[j0] - t_ref) <= np.abs(t_other[j1] - t_ref), j0, j1)
    return np.where(np.abs(t_other[pick] - t_ref) <= tol_s, pick, -1)

def interpolate_imu(t_img: np.ndarray, t_imu: np.ndarray, gyro: np.ndarray) -> np.ndarray:
    """Linear interpolation of 3-axis gyro readings to image mid-exposure times."""
    return np.stack([np.interp(t_img, t_imu, gyro[:, k]) for k in range(3)], axis=1)

Exercise 11.1 — What does 5 ms cost?

A camera with focal length f = 1000 px is mounted on a robot arm rotating at 200°/s. The camera–IMU time offset is mis-estimated by 5 ms. How large is the resulting image-space error near the image center?

Show solution

Angle error = 200°/s × 0.005 s = 1°. Near the principal point, displacement ≈ f·tan(1°) = 1000 × 0.01746 ≈ 17.5 px. That is far larger than a typical sub-pixel reprojection error, which is why temporal calibration is estimated jointly with spatial calibration in tools like Kalibr [71,72] and why hardware timestamps and PTP matter [69].

Exercise 11.2 — The technician refocused the lens

A field technician refocuses a measurement camera to fix blurry images. Afterwards, measured part widths are 1.2% too large, while the detector still finds every part. Which calibration parameters are likely invalid, how could monitoring have caught it, and what process prevents it?

Show solution

Refocusing changes the effective focal length and can change distortion, so the intrinsics fx, fy and distortion coefficients are stale; measurements scale with focal length, consistent with a ~1% size error [65,68]. Monitoring: reproject a fixed fiducial of known size in the scene and alarm when its measured size or reprojection error drifts. Process: lock focus mechanically, record focus state in the calibration record, require a new calibration (new calib ID) after any optical change, and make the runtime refuse to measure when the calibration validation fails.

12Cloud versus edge: bandwidth, latency, privacy and cost

Where inference runs is an architectural decision with consequences for latency, bandwidth, privacy, cost and operations. Edge computing places computation near the data source to reduce latency and bandwidth and to keep data local [73,74]. The choice is rarely all-or-nothing.

Bandwidth arithmetic

Uncompressed 1080p video in 8-bit YUV 4:2:0 uses 1.5 bytes per pixel: 1920 × 1080 × 1.5 × 30 fps ≈ 93 MB/s ≈ 746 Mbit/s per camera. H.264 compression reduces this by two orders of magnitude or more, to a few Mbit/s depending on content and quality [31], but compression artifacts are themselves a distribution shift if the model was trained on uncompressed or differently compressed frames. Edge inference that sends only detections (bytes per frame) or short event clips reduces uplink by further orders of magnitude.

Privacy constraints

Images frequently contain personal data: faces, license plates, screens, documents. The EU General Data Protection Regulation requires that personal data be "adequate, relevant and limited to what is necessary" (data minimisation, Article 5(1)(c)) and that controllers implement data protection by design and by default (Article 25); biometric data processed to identify a person is a special category under Article 9 [76]. On-device processing that emits only aggregate counts or anonymized events is often the most direct way to meet these requirements. Where images must be retained for review and retraining, blur faces and plates at the edge before upload, restrict retention periods, and record the legal basis with the dataset's datasheet [16].
