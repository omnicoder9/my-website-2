Computer architecture for high-performance computing

How Much Has to Be in Flight?

Every level of a supercomputer — a vector lane, a cache, a NUMA hop, an HBM stack, an NVMe queue, a parallel file system — is a pipe with a bandwidth and a latency. It delivers its rated bandwidth only while the product of the two is outstanding inside it. That single requirement, and the five ways a machine can satisfy it, organise the whole subject.

Part IThe law

§1A machine is a stack of pipes

Ask what a supercomputer is and you will be told about its parts. So many cores, so many accelerators, so much memory, a fabric of this topology, a file system of that capacity. The June 2026 TOP500 list describes its leading system in exactly this way: 13,789,440 cores, a proprietary interconnect, 2.198 exaflop/s measured on High Performance Linpack.1, 2 The description is accurate and it explains almost nothing, because the same list records that this machine delivers 1.001 per cent of that figure on High Performance Conjugate Gradient, a benchmark that solves a real sparse system.3

The gap is not a defect of the machine and it is not a defect of the benchmark. It is the thing this article is about.

Consider instead a different description. A machine is a stack of pipes. Each pipe has two numbers: how fast it can move bytes when it is full, and how long one byte takes to get from one end to the other. Registers to L1 is a pipe. L1 to L2 is a pipe. A core to its socket's DRAM is a pipe, and a core to another socket's DRAM is a slower one. A streaming multiprocessor to its HBM stack is a pipe. A node to its neighbour across the fabric is a pipe. A compute node to a parallel file system is the slowest pipe in the building. They differ in their two numbers by seven orders of magnitude and in nothing else that matters here.

Now the constraint. A pipe runs at its stated rate only when enough work is inside it. Not queued to enter it, not finished and waiting to be consumed: inside it, issued and not yet complete. The quantity of work required is exactly the product of the two numbers. This is Little's Law, proved for queueing systems in 1961 and true of any stable flow whatever, including one made of wires.4, 5

Write it the way an architect has to read it:

bytes that must be outstanding = peak bandwidth × unloaded latency

Nothing in that sentence is a tuning parameter. If the pipe's bandwidth is 460.8 GB/s and its latency is 80 nanoseconds, then 36,864 bytes must be in flight at every instant or the pipe is not running at 460.8 GB/s. There is no third option and no clever implementation that avoids it. The only questions an architecture can answer are how much and who supplies it.

§2The concurrency ladder

Run that arithmetic over one machine and the result is startling in a way the component list never is. Take representative figures for a 2026-era node: an L1 cache serving 384 GB/s at 1.3 ns, a socket of DDR5 serving 460.8 GB/s at 80 ns, an HBM3E-equipped accelerator serving 8 TB/s at 600 ns, a Gen5 NVMe drive at 14 GB/s and 80 µs, and a parallel file system at 2.5 TB/s and 2 ms. These are declared inputs, not measurements; substitute your own and the shape does not change.

At L1 the machine must hold 499 bytes in flight, which is 8 cache lines: a modestly unrolled loop supplies that without trying. At DRAM it must hold 36,864 bytes, 576 lines. At HBM it must hold 4,800,000 bytes. At the parallel file system it must hold 5,000,000,000 bytes — five gigabytes of I/O issued and not yet returned — before that file system runs at the rate on its datasheet. The span from top to bottom is a factor of 10,016,026.

That factor is the article's first claim, and it reframes the whole subject. The levels of a memory hierarchy are usually taught as a sequence of speeds. They are better understood as a sequence of concurrency requirements, rising far faster than the latencies do, because bandwidth has improved much more quickly than latency for four decades.6, 7, 8, 9 Every doubling of bandwidth at constant latency doubles the number of things that must be outstanding. The memory wall is often described as a growing gap between processor speed and memory speed. It is more precisely a growing demand for memory-level parallelism, and it grows whether or not the processor gets any faster.10, 11

This is why the same machine can be an exaflop machine and a five-petaflop machine depending on which benchmark you run. HPL keeps its operands in registers and cache; its concurrency requirement at DRAM is nearly zero.12 HPCG streams a sparse matrix with indirect addressing; its requirement is enormous and it has no reuse with which to lower it.3 Neither result is wrong about the hardware. They are measurements of two different pipes.

§3Balance, intensity, and the ridge point

The complementary question to how much must be in flight is how much traffic does this computation actually require. Divide the operations by the compulsory bytes and you have arithmetic intensity; compare it to the machine's ratio of peak flop rate to peak byte rate and you know which of the two is binding. This is the roofline model, and its value is that it turns a vague sense of “memory bound” into a number you can compute before writing any code.13, 14

The ridge point — the intensity at which the machine stops rewarding extra flops — is the machine's whole personality in one number. On a 2009 server socket it sat at 3.32 flop per byte. On a low-precision 2026 accelerator, counting the tensor pipeline's peak against its HBM4 bandwidth, it sits near 2272.73: a factor of 684.15, 16 Of ten kernels drawn from real workloads, seven are left of the 2009 ridge and nine are left of the 2026 one. Nothing about the kernels changed.

The drift is not a law of nature, and it is worth resisting the fatalism that usually accompanies the memory-wall story. A64FX, designed for Fugaku with HBM2 attached to a deliberately modest vector throughput, has a ridge point of 3.00 flop per byte — below the 2009 socket's.17 That is a design decision, purchased with silicon area and power that were not spent on arithmetic. The June 2026 list shows what it bought: Fugaku delivers 3.620 per cent of its HPL rate on HPCG, against 0.554 per cent for Aurora and around one per cent for the exascale machines, a spread of 6.5× between machines whose peak rates differ by far less.2

Two clarifications the roofline picture invites and does not itself supply. First, the ridge point is precision-dependent: a machine quoting fifty petaflops of four-bit arithmetic against twenty-two terabytes per second is describing a ridge that no double-precision code will ever approach.18, 19 Mixed-precision algorithms are, read this way, a technique for moving the kernel right rather than waiting for the machine to move left.20, 21 Second, the roofline says whether bandwidth or arithmetic binds; it does not say whether you will reach the bandwidth bound. That is the concurrency question, and the two are usually taught apart.22, 23

§4Five ways to be concurrent

If every level demands work in flight, the architecture of a machine can be read as an answer to the question of where that work comes from. There turn out to be only five answers, and every mechanism in the rest of this article is one of them or a combination. The Berkeley survey of parallel computing reached a related conclusion by another route, organising the field around a small set of computational patterns and observing that what distinguishes them is almost always what they do to memory.24

  • L, lanes. Concurrency inside one instruction. A vector operation, a warp, a tensor-core tile: one instruction that names many independent element operations, and therefore potentially many independent addresses.25, 26
  • T, threads. Independent instruction streams. Cores, hardware threads, resident warps, MPI ranks. Each one contributes whatever it can hold outstanding on its own.27
  • O, outstanding. Transfers in flight within one stream. Miss-status holding registers, load queues, prefetch, asynchronous copies, I/O queue depth, RDMA operations posted and not yet complete.11, 28
  • P, partitions. Independent servers that can be busy at once. DRAM banks, channels, pseudo-channels, NUMA nodes, flash dies, storage targets. Bandwidth at any level is a sum over partitions.29, 30
  • R, reuse. The odd one out: instead of supplying the concurrency, remove the requirement. Caches, blocking, scratchpads, register tiling, operator fusion. A transfer that never happens needs no slot.31, 32, 33

Four of these meet the demand. One abolishes it. That asymmetry is the reason locality optimisations are worth more than they appear: raising arithmetic intensity moves you right on the roofline and lowers the number of transfers that must be outstanding to sustain whatever traffic remains. It is the only lever with both effects.

The rest of this article walks the machine — cores, vectors, caches, placement, GPUs, spatial accelerators, memory, storage — and for each mechanism records five things: what gap it hides, what it demands in return, what it costs, how you would recognise from a measurement that it is being starved, and which of the five suppliers it draws on. These are the flight plates, numbered and collected into a ledger at the end.

Part IICores, threads, vectors

§5Cores: the unit that everything is counted in

A core is a machine that fetches, decodes, and retires an instruction stream. Since Dennard scaling ended around 2005, the number of them has been the main way vendors convert transistor budget into throughput, because frequency stopped being available and single-stream performance stopped improving at its historical rate.34, 35, 36 Density scaling on its own, the observation usually named for Moore37, never promised usable performance; what ended was the voltage scaling that made extra transistors free to switch, and the consequence is a power budget under which a growing fraction of a chip cannot run at full speed at once.38 The responses now taken seriously — specialisation, better algorithms, better software — all sit above the device layer rather than inside it.39, 40, 41 The June 2026 list's leading system reaches its position with 13,789,440 of them and no accelerators at all.2

Read through the concurrency lens, a core is a supplier of type T with a bounded capacity of type O. It can have some number of independent misses outstanding, and that number, not its clock, sets what it can pull from memory.

The arithmetic is unforgiving. A core with sixteen line fills in flight, each 64 bytes, against an 80 ns DRAM latency, can sustain 12.80 GB/s. That is 2.78 per cent of a 460.8 GB/s socket. To saturate the socket's pins you need 36.0 such cores running memory-bound code simultaneously.

Three consequences follow that are not obvious from the datasheet.

First, the STREAM benchmark is a measurement of aggregate concurrency, not of the memory system.42 A single-threaded STREAM result on a modern socket is bounded by one core's outstanding-miss capacity and tells you almost nothing about the DRAM. Reporting it without the thread count is one of the older ways to mislead.43, 44

Second, core count and bandwidth are not independent design variables. A socket whose core count is below the ratio above cannot reach its own memory bandwidth on any workload. Vendors know this, which is why core counts and channel counts move together, and why the interesting number on a spec sheet is bytes per second per core.45, 46

Third, adding cores to a memory-bound kernel helps until it doesn't, and the crossover is computable in advance. Past the saturation point the extra cores add queueing delay, which raises latency, which raises the concurrency requirement, which is a feedback loop rather than a plateau.47, 48

§6Threads: out-of-order windows and SMT

Within a core, two mechanisms manufacture outstanding transfers. The out-of-order window finds independent work in one stream; simultaneous multithreading imports it from a second.27

The window is the more expensive and the more misunderstood. Its purpose is usually described as hiding latency, but the latency it can hide is bounded by how many independent long-latency operations fit inside it. A window of five hundred instructions containing one chain of dependent loads hides one load's latency, not five hundred. The relevant capacity is the number of independent misses, which is the MSHR count, not the reorder buffer size.10, 11, 28 Runahead execution and its descendants exist precisely to keep generating independent misses when the window has otherwise stalled.49

SMT supplies concurrency of type T at almost no area cost, and its value depends entirely on whether the two streams stall at different times.27 On a latency-bound kernel it can nearly double throughput, because the second thread's misses use MSHRs the first thread was not using. On a bandwidth-bound kernel it does nothing, because the bandwidth was already saturated and the second thread only adds queueing. On a cache-bound kernel it can make things worse, because two working sets now share one L1 and L2.50, 51 The three cases are distinguishable in advance by asking which resource the kernel had already exhausted.

Threads also bring an obligation that has nothing to do with performance and everything to do with whether the program is correct. Two streams sharing memory need a consistency model, and the strong one everyone reasons with informally is not the one any machine implements.52, 53 The programming models used in practice — OpenMP for shared memory54, 55, MPI across nodes56, 57, and portability layers such as Kokkos and RAJA above both58, 59 — are in large part attempts to make that obligation expressible without making it the application programmer's daily problem.

This is the first appearance of a pattern worth naming. Most performance advice takes the form “mechanism X helps.” The useful form is “mechanism X supplies concurrency of kind K, and helps exactly when K is what you were short of.” Enabling SMT on a code that was short of bandwidth is not a mistake of degree; it is a category error.

§7Prefetch: guessing at the requirement

A hardware prefetcher is a device that supplies outstanding transfers without being asked, by extrapolating an address sequence.60, 61 It is the one mechanism in this article that can raise a level's utilisation with no change to the program, which is why it is present on every serious processor and why so much performance is invisible in the source.

Its limits are structural. It needs a pattern regular enough to extrapolate, which excludes pointer chasing and most sparse indirection. It usually stops at page boundaries, because the physical address beyond the page is unpredictable, which caps a stream's usable depth at the page size divided by the stride. And it competes for the same MSHRs demand misses need: a prefetcher that is wrong consumes the exact resource whose scarcity motivated it.

The measurable consequence is that on a machine with an aggressive prefetcher, bandwidth counters routinely exceed the traffic the source code implies, sometimes substantially. When that happens the useful diagnostic is not “the prefetcher is broken” but the roofline question asked against measured traffic rather than compulsory traffic: the gap between the two is precisely the wasted work.13, 14

Software prefetch instructions and, on accelerators, asynchronous copy primitives, are the explicit form of the same idea. They move the guess from hardware into the program, which is better when the program knows something the predictor cannot and worse otherwise. Modern GPU kernels stage tiles through asynchronous copies for exactly this reason: the program knows the tile schedule, so it can keep loads outstanding across a barrier that would otherwise drain the pipeline.62, 63

§8SIMD and vector processing

A vector instruction names many element operations at once. Its first and largest benefit is not arithmetic throughput but issue bandwidth: one fetch, one decode, one dependency check, for L operations. Cray understood this in 1976 and the argument has not changed.25, 26 Its second benefit, available only when the addresses cooperate, is that a single instruction can generate up to L independent memory requests, which makes it a supplier of type L and of type O.

Modern instruction sets differ in how they express the length. AVX-512 fixes it in the encoding; the ARM Scalable Vector Extension and the RISC-V vector extension leave it to the implementation, so one binary runs at the width the hardware happens to have.64, 65 The A64FX cores in Fugaku pair 512-bit SVE with HBM2, which is the same balance decision discussed above expressed in the instruction set.17

Two costs recur, and both are quantifiable.

Tails. A loop of n elements at width L issues ⌈n/L⌉×L lanes. For large arrays this is a rounding error. For short ones it is not: at n = 100 and L = 64, 21.88 per cent of the lanes issued do nothing. Kernels called many times on small arrays — which describes a great deal of scientific code — pay this on every call.

Divergence. When the operation is conditional, masked lanes still occupy slots. Take a predicate that is true for 9.592 per cent of 100,000 elements, primality being a convenient irregular pattern with real clustering. Useful lane occupancy is 9.592 per cent at every vector width, as it must be. What changes with width is the fraction of vectors that can be skipped entirely: 80.82 per cent at width 2, 39.34 per cent at width 8, 0.00 per cent at width 64.

At width 64 the machine issues 10.43 lanes for every lane that does something. Widening the vector did not make the sparse work slower in absolute terms, but it converted skippable work into masked work and removed the only mechanism — skipping — by which sparsity was being exploited. This is a specific, computable reason why very wide machines suit dense regular workloads and not sparse ones, and it is independent of memory bandwidth.

Part IIICaches and placement

§9The cache line, and what a cache is for

A cache is usually introduced as a device that reduces latency. That description is true and it obscures the more important fact: a cache reduces the number of transfers, which is the quantity Little's Law is denominated in. Every hit is one fewer request that had to be outstanding at the level below. In the vocabulary of this article, a cache is the only mechanism of type R in the core, and R is the only supply that works by lowering demand.

The unit of transfer is the line, typically 64 bytes. This quantisation is the source of most of the surprises. A program that reads one useful byte per line moves 64 bytes for it, so its measured bandwidth can sit at the machine's peak while one byte in sixty-four of that traffic is wanted. Both numbers are real; only one is on the dashboard.

The classic taxonomy divides misses into compulsory, capacity, and conflict.66, 67, 68 Compulsory misses are set by the algorithm and cannot be removed, only overlapped. Capacity misses are set by the working set relative to the cache and are what blocking addresses.31, 32 Conflict misses are set by the index function, and they are the ones that make performance appear non-deterministic to people who have not looked.

An exact experiment makes the third category vivid. Walk 256 cache lines — 16 KiB, one quarter of a 32 KiB 8-way cache's line capacity — three times, at various strides. At 64 and 128 byte strides you see 256 cold misses and nothing more. At 256 bytes and beyond, every one of the 768 accesses misses.

Capacity never changed. The set index is bits 6 through 11 of the address, so a 256-byte stride advances the index by four, and 256 lines land on sixty-four divided by four, that is sixteen sets, of eight ways each. The cache is one eighth full and thrashing completely. This is not a corner case invented for the demonstration: 256 bytes is thirty-two floats, a plausible row length.

§10Blocking, padding, and the folklore

Two standard fixes address the two standard problems, and an exact model shows something the folklore does not.

Take an n = 128 matrix product in double precision on a 32 KiB 8-way L1, counting every scalar access. In the natural i-j-k order with a leading dimension of 128, the model records 2,135,072 misses. Pad the leading dimension to 129 — one extra double per row, eight bytes, no change to the algorithm — and it records 268,416, a factor of 7.95.

The mechanism is visible in the arithmetic of the index function. A row of 128 doubles is exactly 16 cache lines, and stepping 16 lines advances the set index by 16, so the 128 rows of the matrix land on four of the sixty-four sets. One padding word breaks the alignment and spreads them. The same problem is fixed by loop interchange, which lands on 266,240 misses — within one per cent of the padded figure, by a completely different route. Two pieces of standard advice, one underlying cause.

Blocking then attacks capacity misses, and here the exact count disagrees with the rule of thumb.32, 69, 70 The usual guidance is to choose the largest block b such that three b×b double blocks fit in the cache, which for 32 KiB gives b = 36. The measured minimum is at b = 24, with 37,093 misses. Following the rule gives 87,297 misses: 135.3 per cent worse than the optimum, and worse than a block half its size.

The reason is that the capacity rule assumes the only constraint is total bytes. In a set-associative cache with a padded leading dimension, a block's rows are scattered across sets in a pattern that depends on the stride, and the effective capacity available to a tile is well below the nominal one. This is why automatic tuners search rather than compute71, 72, why hand-tuned libraries encode block sizes per microarchitecture70, and why cache-oblivious formulations are attractive despite giving up the constant factor.73 The theory of what tiling buys is settled33, 74, 75, 76; the constant is empirical. The same lower-bound machinery carries up to the distributed case, where it says how much communication a matrix product must perform for a given amount of memory per rank77 and how an algorithm can spend extra memory to reduce it.78

§11NUMA: the pipe depends on who touched the page

On any machine with more than one memory controller, a “pipe to DRAM” is not one pipe. It is several, with different latencies and different bandwidths depending on which controller owns the page, and the owner is determined by a policy most programs never mention.79, 80

Linux and most other systems default to first touch: a page is placed on the node of the thread that first writes to it. The consequence is that an array's placement is decided by the initialisation loop, which is very often serial, and very often written by someone who was not thinking about placement at all.81

Model four nodes, each with 460.8 GB/s of local DRAM and 128 GB/s of coherent link bandwidth out of the node, at 80 ns local and 140 ns remote. All threads read one shared array. The only variable is placement.

Single-threaded first touch puts every page on one node. Three quarters of the traffic crosses that node's outbound links, and the achievable aggregate is 170.7 GB/s. Parallel first touch, in which each thread initialises the region it will read, reaches 1843.2 GB/s: a factor of 10.80, from the same binary, on the same silicon, with the same access pattern. Interleaving pages round-robin recovers 31 per cent of that gap, reaching 682.7 GB/s.

The concurrency reading adds something the bandwidth comparison alone does not. Interleaving does nothing for latency: three quarters of accesses are still remote, so the mean stays at 125 ns and the transfers that must be in flight rise in proportion to the bandwidth gained. And the best policy is the hungriest of all. Parallel first touch requires 2,304 lines outstanding across the machine to sustain its 1,843.2 GB/s — 144 cores at sixteen line fills each, which is more than many four-socket machines have.

So the honest statement about NUMA is not that remote memory is slow. It is that placement changes both terms of Little's Law at once, in opposite directions, and that the policy which maximises bandwidth also maximises the concurrency you must find to use it.

Part IVGPUs and the CUDA model

§12The bargain a GPU offers

A GPU makes a trade that is easy to state and easy to get wrong. It removes almost everything a CPU spends area on to reduce latency — the deep out-of-order window, the large private caches, the branch predictors — and spends the area on arithmetic units and on register file. In exchange it requires the program to supply enough independent work that latency does not need hiding by the hardware, because it is hidden by there being something else to run.82, 83, 84

Read against Little's Law, this is not a different philosophy of computing. It is the same equation with the supply term moved from hardware to software.

The magnitude is worth computing, because it explains the shape of the chip. An HBM3E-class accelerator sustaining 8 TB/s at roughly 600 ns of latency must hold 4,800,000 bytes in flight. A coalesced warp-wide 32-bit load requests 128 bytes. So the machine must have about 37,500 warp-loads issued and not yet returned, continuously, to run its memory system at the rate on the box.

Now count the supply. A large GPU has on the order of 132 streaming multiprocessors with 64 warp slots each. If every resident warp has four loads outstanding, the machine supplies 33,792 — 90.1 per cent of the requirement. Six per warp overshoots it; four does not quite reach it.

That is the whole design in one line. The enormous register file, the 64 warp slots, the absence of a reorder buffer, the insistence on thousands of threads: these are not stylistic preferences. They are the number 37,500, expressed in silicon.85, 86, 87 The observation is old enough to predate the programming model: an analysis of graphics hardware in 2004 found that matrix multiplication on GPUs was limited by bandwidth and cache, not by arithmetic, several years before anyone was running linear algebra on them in earnest.88, 89

It also explains why the GPU is a poor CPU. Every one of those warp slots needs registers and shared memory allocated at launch, so the machine can only supply that concurrency for programs with thousands of independent threads. Give it one thread and it is a slow, in-order, low-clock core.

§13CUDA as a concurrency contract

CUDA's programming model is usually taught as a hierarchy: threads in warps, warps in blocks, blocks in a grid, with shared memory and barriers at the block level.62, 90 Read as an interface, it is a contract about concurrency: the program promises to expose parallelism at three granularities, and in return the hardware promises to schedule around latency without being told how.

Each level of the hierarchy corresponds to a supplier from the list in §4. The warp is L: 32 lanes issuing one instruction, generating up to 32 addresses. Resident warps are T: independent streams whose stalls interleave. Loads in flight per warp are O. Shared memory is R. The partitioning across SMs and across memory channels is P. A CUDA kernel that performs badly is short of one of these five, and which one is usually identifiable from two counters.

Two things about the model deserve emphasis because they are where the abstraction leaks.

The first is that a block's resources are allocated for its lifetime. Registers per thread and shared memory per block are decided by the compiler and the source, and they divide into a fixed per-SM budget to give the number of resident warps. A kernel using 64 registers per thread on a machine with 65,536 registers per SM holds 32 of 64 warp slots. Nothing about the algorithm changed; a register allocation decision halved the machine's capacity to hide latency.

The second is that the model has been steadily acquiring explicit concurrency primitives as the implicit ones ran out. Asynchronous copy, pipelined barriers, cluster-level cooperation and, in the current toolkit, tile-level programming interfaces are all mechanisms for keeping transfers outstanding across points where the older model would have drained.62, 91 The direction of travel is from “have enough threads” toward “say what is in flight”, which is the same direction CPUs travelled when they acquired prefetch instructions.

§14Occupancy is a requirement, not a goal

Occupancy — resident warps as a fraction of the maximum — is the most cited and most misused number in GPU work. Volkov's demonstration that carefully written kernels can beat higher-occupancy ones is fifteen years old and still surprises people.85, 92 The concurrency framing dissolves the paradox: occupancy is the supply side of an equation whose demand side is set by the kernel's own instruction mix, and there is no reason for the supply to exceed the demand.

Model one warp scheduler issuing one instruction per cycle, with a 400-cycle memory latency, running warps that execute a arithmetic instructions and then one dependent load. Little's Law gives the warps needed directly: roughly 400/(a+1).

At a = 63 the machine needs 7 warps and a kernel at 12 per cent occupancy saturates issue. At a = 15 it needs 25. At a = 3 it needs 100, which is above the 64-slot ceiling, so 64 warps reach 63.7 per cent of issue and no tuning improves it. At a = 0 they reach 16.0 per cent. The threshold is exact: a kernel needs at least 6 arithmetic instructions per memory instruction before 64 warp slots can cover a 400-cycle latency at all.

That threshold is the most practically useful number in this section, because it partitions kernels into two classes before any of them are written. Above it, occupancy tuning is a real lever. Below it, the kernel is latency-bound by construction and the only remedies are the ones that change a itself: fusion, register tiling, raising arithmetic intensity. Combine this with the register table and the picture sharpens further — at 64 registers per thread the threshold rises from 6 to 12, so a spill can move a kernel across the line.

One further effect falls out of the model and is worth knowing because it looks like a measurement error. Sixty-four identical warps released on the same cycle progress in lockstep, reach their loads together, and stall together, leaving the issue port idle in bursts. Cycle-level GPU simulators exist precisely to expose effects of this kind93, and this one is small enough to compute exactly. The simulation records 47,344 cycles against 40,960 for the same warps spread across one iteration period: a 1.156× penalty produced by symmetry alone.

§15GPU memory hierarchy: registers, scratchpad, L2, HBM

The GPU's hierarchy is shaped by the same two questions as the CPU's, but it answers them with different proportions. The register file is enormous because it is the concurrency budget. Shared memory is a software-managed scratchpad rather than a cache because the compiler and programmer know the tile schedule better than a replacement policy does.62, 82 The L2 is comparatively small relative to the bandwidth behind it, because on a machine with this much concurrency its job is coalescing and coherence rather than capacity.

The mechanism specific to this hierarchy, and the one with the largest performance range, is coalescing. A warp's 32 lane addresses are resolved into a set of memory sectors, and the traffic generated is the number of distinct sectors, not the number of useful bytes.

Thirty-two lanes reading consecutive 4-byte elements request 4 sectors and move exactly the 128 bytes wanted. Offset by one element, they request 5 sectors. At stride two, eight. And thirty-two lanes reading one field of a 48-byte structure request 32 sectors and move 1,024 bytes to deliver 128 — an eightfold amplification, on a machine whose entire design premise is that memory bandwidth is precious.

Two details of the model matter. First, permutation within the warp is free: reversing the lanes or applying an arbitrary shuffle inside a 128-byte window still requests four sectors, because only the set of sectors counts. The intuition that scattered access is slow is not quite right; what is slow is access that is spread. Second, this is not an optimisation applied to traffic after the fact. It is the definition of how much traffic the instruction generates, which is why array-of-structures to structure-of-arrays conversion is worth restructuring a program for.62, 94, 95

Shared memory is then the type-R lever. A tiled kernel stages a block of operands into scratchpad once and reads them many times, converting global traffic into on-chip traffic and lowering the number of HBM transfers that must be outstanding.85, 96 The bank structure of the scratchpad reintroduces the partition question at a smaller scale: a stride that maps every lane onto the same bank serialises them, which is the set-conflict problem of §9 in a different building.

§16Tensor cores and the tile

A tensor core executes a small matrix multiply-accumulate as one instruction. It is the L supplier taken to its conclusion: one instruction, one issue slot, hundreds of multiply-accumulates, operands read from registers or scratchpad in a fixed layout.87, 97 It is also, in roofline terms, a device for moving the ridge point sharply to the right.

That last point is the one that gets lost. Raising peak arithmetic without raising bandwidth converts compute-bound kernels into memory-bound ones. A GEMM at n = 1024 has an arithmetic intensity around 85 flop per byte; it is compute-bound on every machine in this article's table except the low-precision 2026 part, where the ridge sits at 2272.73 and it is not. The tensor pipeline is then idle waiting for HBM, and the correct response is not to use it harder but to restructure the surrounding computation so more work happens per byte loaded.63, 98, 99 The compiler infrastructure that has grown up around this problem — scheduling languages that separate what is computed from the order in which it is computed100, and multi-level intermediate representations that keep tiling decisions expressible far enough down the stack101 — is best understood as tooling for moving kernels rightward on the roofline.

This is the clearest case in the article of a machine improvement that changes the category of a workload. FlashAttention is the well-known example of the corresponding software move: the same mathematics, tiled and fused so that intermediate results never reach HBM, converting a bandwidth-bound kernel into a compute-bound one by removing traffic rather than accelerating it.63 It is a type-R optimisation of exactly the kind §4 predicted would be worth the most.

The precision dimension compounds this. Reduced-precision formats multiply peak arithmetic without touching the bytes moved per element in the same proportion, so each precision step moves the ridge further right. Mixed precision algorithms answer by doing most of the arithmetic in the cheap format and correcting in the expensive one, which raises effective intensity rather than chasing peak.18, 19, 20 The theory of when this is numerically safe is now substantial.21

§17The integrated node: when the copy disappears

For fifteen years the standard accelerated node was a CPU with its own memory, an accelerator with its own memory, and a PCIe link between them over which the program copied data explicitly. Two of the machines in the June 2026 top five have abandoned that arrangement in different directions, and both are worth reading against the thesis.

El Capitan is built from MI300A parts, in which CPU and GPU chiplets share one package and one pool of HBM.2, 102 JUPITER and Alps use Grace Hopper superchips, in which a CPU with its own LPDDR is joined to a GPU with its own HBM by a coherent link far faster than PCIe.2 The marketing description of both is that the copy disappears. The architectural description is more careful: in the first the copy disappears because there is one memory; in the second it becomes a coherent access over a link with its own bandwidth and its own latency, which is to say it becomes a NUMA hop of the kind §11 already described.

What integration genuinely removes is a staging cost: the requirement to have the data resident in the right memory before the kernel runs, and therefore the requirement to overlap the copy with something else. That is a real and substantial simplification, and it is the reason fine-grained CPU-GPU interaction — a kernel that touches a large sparse structure the CPU also updates — becomes practical when it previously was not.

What integration does not remove is anything in Little's Law. A GPU reading its own package's HBM still needs 4,800,000 bytes in flight. A GPU reading across a coherent link to the CPU's memory needs the link's bandwidth times the link's latency, and since the link is slower and longer than local HBM in both terms, the code that crosses it is precisely the code that needs the most concurrency to do so at rate. Unified memory therefore has a characteristic failure mode: excellent occupancy, correct code, and most of the time spent servicing page faults or remote accesses at a granularity far larger than a cache line, because the runtime's placement decisions are being made by a heuristic that cannot see the access pattern.62, 103

The general form of this observation applies to every mechanism that makes one address space out of several. NUMA, memory tiers, CXL pools, unified host-device memory: each is a promise that the program need not say where the data is, and each converts an explicit cost the programmer could schedule into an implicit cost they cannot see. Whether that is a good trade depends on whether the implicit cost is small, and it is small exactly when the access pattern is one the placement heuristic predicts.79, 81

There is a cleaner way to state the trade, and it is the same one that appeared at first touch. Every abstraction over placement is a decision to have the runtime answer a question that the program could have answered better and the hardware cannot answer at all. When the runtime guesses well the program is simpler at no cost. When it guesses badly the cost is invisible in the source, absent from the test suite, and expressed as a factor rather than a percentage.

Part VSpatial and specialised machines

§18Dataflow: a pipeline supplies its own concurrency

Everything so far has treated concurrency as something a program must supply to a machine built around a sequential instruction stream. A spatial architecture inverts that. If the computation is laid out as a physical pipeline, the work in flight is the contents of the pipeline stages, and it is there by construction whether or not the program says anything.104, 105, 106 It is the oldest live alternative to the stored-program organisation set out in 1945, and the reason it keeps returning is that the bottleneck that organisation creates is the one this article has been counting.107, 108

A systolic array is the purest form: operands enter at the edges, move between neighbours, and produce results without returning to memory. Its arithmetic intensity is not a property of the algorithm as written but of the array's geometry, which is why a matrix engine of the right shape can run at a byte-per-flop ratio no general machine can match.106, 109 The concurrency is structural: a pipeline of depth D at an initiation interval of one holds D results in flight with no scheduler, no register renaming, and no cache.

The cost is legibility and generality. The pipeline computes one thing. A change to the computation is a change to the wiring. And the clock is slow: a reconfigurable fabric runs an order of magnitude below a CPU. Working the arithmetic: a 300 MHz fabric needs 160 independent initiation-interval-one pipelines to match one 3 GHz core with eight lanes and two fused-multiply-add units at 96.0 GFlop/s. At 128 pipelines it holds 4,096 results in flight.

That comparison is the whole trade in one row. The fabric spends area on structure; the core spends area on discovering at run time that independent work exists. Which is better depends entirely on whether the structure is known in advance and stable enough to be worth building. That is a question about the workload, not about the technology, which is why answers have flipped repeatedly over four decades.108, 110, 111

§19FPGAs, and the cost of the configuration

An FPGA is a fabric of lookup tables, registers, DSP blocks and on-chip memory, wired by a configuration bitstream. It occupies a specific and narrow niche in the concurrency picture: it supplies L and P abundantly, R readily through distributed on-chip memory, and T and O not at all.112, 113

Three costs recur, and all three are quantifiable in advance.

Clock rate. An order of magnitude below a CPU, which as computed above requires a large number of parallel pipelines merely to reach parity. For regular dense arithmetic, a GPU almost always wins this race.114, 115

Configuration time. Milliseconds, sometimes more. A fabric that delivers a fourfold speedup and takes 100 ms to configure needs 133 ms of equivalent CPU work before it breaks even end-to-end; at a hundred milliseconds of configuration and a twofold speedup, 200 ms. For a kernel called once this is fatal and for a kernel called for an hour it is irrelevant, and knowing which case you are in requires no experiment.

Development cost. High-level synthesis has narrowed the gap between writing C and writing register-transfer logic, but the achievable initiation interval is set by loop-carried dependences the tool cannot remove, and the gap between an II of 1 and an II of 4 is a factor of four in throughput.112

Where FPGAs have won at scale, it has been for workloads that are irregular enough to defeat SIMD, stable enough to justify a bitstream, and latency sensitive enough that batching is not an option: network processing, encryption, and search ranking.113, 116 Microsoft's datacentre deployment is the reference case, and it is notable that its dominant use became network-attached acceleration — a place in the machine where the alternative is a fixed-function ASIC rather than a CPU.116

§20Domain accelerators and near-memory compute

A domain-specific accelerator is the argument of §17 applied selectively: build the structure for the operations that dominate, keep a general machine for everything else.117, 118 The tensor processing unit is the most thoroughly documented instance, and its published analysis makes the concurrency argument explicitly: the first generation's systolic array was frequently limited not by arithmetic but by the bandwidth feeding it, which is the same roofline the rest of this article has been drawing.109, 119 Later designs answer with more on-chip memory and higher-bandwidth attachment, which is to say with R and P.

Two structural observations are worth separating from the marketing.

First, a domain accelerator changes the ridge point, not the law. Eyeriss and its successors are analysed in terms of data reuse per byte fetched, and their designs are classified by which operand stays stationary.120, 121 That is a taxonomy of type-R strategies, and it is the same taxonomy blocking gives for a cache.

Second, the most radical version of the idea — move the computation to the memory rather than the data to the computation — has been technically demonstrated and commercially difficult for thirty years.122, 123 Measurements of real processing-in-memory hardware show it wins convincingly on kernels with almost no reuse and loses on kernels with any, because the in-memory processor has no cache and a weak arithmetic unit.123 The concurrency reading is that it converts an O problem into a P problem: instead of needing thousands of transfers in flight over a long pipe, it needs thousands of short pipes. Whether that is a good trade depends on whether the operands can be partitioned so they are already in the right bank, which is a property of the algorithm.

Part VIMemory systems

§21DRAM: banks, rows, and why bandwidth is a sum

The bandwidth figure on a memory specification is not the speed of anything. It is a sum over parts that can be busy simultaneously.

A DRAM device is organised into banks, each with a row buffer. Reading an address requires activating its row into the buffer, reading a column, and eventually precharging. Only one row per bank is open at a time, so consecutive accesses to different rows of one bank serialise at a cost the streaming case never sees.29, 30 Memory controllers therefore reorder aggressively to group accesses by open row, and address interleaving spreads consecutive lines across banks and channels so that a sequential stream hits many banks at once.29, 124

Count the partitions in a modern socket. Twelve DDR5 channels, each split into two independent sub-channels, each with 32 banks per rank, gives 768 independently addressable servers. Set that against the requirement computed in §2: 576 line fills in flight to sustain the socket's peak. The ratio is 1.33.

That near-coincidence is not an accident and it is the point of this section. The partition count is not a detail beside the bandwidth number; it is what makes the bandwidth number reachable rather than nominal. A machine with the same peak and a quarter of the banks would publish the same figure and never approach it, because the requests would collide.

The failure modes follow directly. A stride that maps every access to one bank sees a small fraction of peak with an unchanged request rate. Unpopulated channels remove partitions and therefore bandwidth, which is why a machine with half its DIMM slots filled can measure at half its rating with every other component identical. And refresh, error correction, and the row-buffer policy all take their cut from the same budget, which is why measured STREAM figures land in the eighty-per-cent range rather than at peak.42, 125 Refresh is also where DRAM's most consequential security failure lives: repeated activation of one row can disturb its neighbours, a physical side effect of the same density that makes the capacity affordable.126

§22HBM: buying bandwidth with wires

High-bandwidth memory attacks the pin limit rather than the frequency limit. Instead of driving a narrow bus fast across a motherboard, it stacks DRAM dies and connects them to the compute die over a very wide, very short interface on an interposer or directly on package.127, 128 The published HBM4 standard specifies transfer rates up to 8 Gb/s across a 2,048-bit interface for as much as 2 TB/s per stack, and doubles the independent channels per stack from 16 to 32, each divided into two pseudo-channels.16

Notice what that second sentence is doing. Half the headline is bandwidth and half is partitions: the channel doubling is a statement about how many independent request streams the stack can serve, which is exactly the quantity §20 identified as making bandwidth reachable. A wide bus with too few independent channels would publish the same peak and deliver less of it.

The costs are equally structural. Capacity per package is a fraction of what DIMM slots hold, so a working set that exceeds on-package memory falls off a cliff rather than degrading. Cost per byte is several times higher. Thermal density under a stack constrains the compute die above and beside it. And the supply chain is narrow enough that memory availability, not silicon availability, has repeatedly been the binding constraint on accelerator production. Packaging is the enabling technology throughout: the same chiplet and interposer methods that make a stack attachable also make it possible to compose one processor from dies built on different processes.102

The strategic consequence for HPC is visible in the June 2026 list. Fugaku, whose A64FX packages HBM2 with every core group, delivers 3.620 per cent of its HPL rate on HPCG — the highest ratio in the top ten — while machines with far higher peak rates deliver around one per cent.2, 17 Attaching high-bandwidth memory to a modest arithmetic rate produces a machine that looks unimpressive on the list everyone quotes and performs well on the workloads many people run. That is a balance decision in the sense of §3, and it is a real one with real costs, not a free lunch: Fugaku's absolute HPCG figure is below El Capitan's.

§23Capacity, tiers, and the pooled future

Bandwidth is one axis and capacity is another, and the two have been diverging. HBM buys bandwidth at the cost of capacity; DIMMs buy capacity at the cost of bandwidth; and no single technology currently offers both at a price anyone wants to pay. The architectural response has been to build machines with more than one kind of memory and to make the difference visible, or to hide it and accept the consequences.

Compute Express Link is the current mechanism for the hiding version.129 It allows memory to be attached over a PCIe-class physical layer — the same electrical generation that reached 128 GT/s and 512 GB/s bidirectionally per x16 link in the 7.0 specification130 — and to be presented to software as ordinary cacheable memory at a longer latency. Pooling studies on cloud platforms report meaningful capacity savings from sharing a pool across hosts.103 The motivation is the one warehouse-scale operators have documented for years: memory is stranded because it is provisioned per host for a peak that individual hosts rarely reach together.131

The concurrency reading is unchanged and unforgiving. A CXL-attached tier is a pipe with a longer latency and, usually, a lower bandwidth. Its required transfers in flight are therefore higher per unit of delivered bandwidth than local DRAM's, which means the workloads that tolerate it best are those that already have abundant memory-level parallelism, and the ones that tolerate it worst are the pointer-chasing workloads people most want to give more capacity to. Adding a tier does not change any term in the equation; it adds another instance of it, and the tiering policy decides which pages experience which.79, 103

This is the same lesson as first touch in §11, one level out. Every mechanism that makes the address space heterogeneous — NUMA nodes, memory tiers, pools, unified host-device memory — introduces a placement decision that the source code does not express, and whose default is chosen by whoever wrote the allocator. The performance consequences are large, invisible in the program text, and absent from every test that does not measure them.

Part VIIStorage systems

§24NVMe: queues as the interface

For thirty years the storage interface was a queue of depth one wearing a disguise. NVMe removed the disguise. Its central design decision is a large number of submission and completion queue pairs, one per core where possible, with deep queues, so that the operating system can express concurrency instead of serialising it through a single lock.132, 133

Nothing in this article requires a separate explanation. It is Little's Law again, denominated in commands.

Model a device with 80 µs of unloaded latency and 128 internal service channels. Reaching one million IOPS requires 80 commands outstanding at every instant. A thread issuing one synchronous read at a time obtains 12,500 IOPS, and the drive is idle 99.2 per cent of the time while meeting every specification it was sold with.

The same structure appears at every level below the interface. Flash parallelism is P: dies and planes that can be busy simultaneously, which is why the capacity of a drive and its throughput are correlated for reasons that have nothing to do with the interface. Garbage collection is the partition story's dark side: background work on a die appears as latency on an unrelated foreground request, which is why steady-state figures differ so much from burst figures and why tail latency is the metric that matters.134, 135

The interfaces that expose this structure — open-channel devices, zoned namespaces — are attempts to let the host schedule the partitions rather than have the device guess.136, 137 They trade a simple abstraction for control over exactly the concurrency this article keeps counting, and the reported benefit is largely in predictability rather than in peak.

The current specification set, revised in full in August 2026, continues in the same direction, extending the model to migration, security and management rather than changing the fundamental queue-based contract.132

§25Parallel file systems: striping and locks

A parallel file system takes a file, cuts it into stripes, and spreads the stripes over many storage targets so that many clients may read and write at once. Lustre and GPFS/Storage Scale differ in a great many details and agree on this one.138, 139, 140 The stripe count is the partition count, and it is chosen when the file is created, usually by a default nobody revisited.

Two failures dominate real deployments, and both are exactly computable.

Too few stripes. A file with a stripe count of one lives on one target. A thousand clients writing to it obtain one target's bandwidth while the rest of the machine is idle. On a system with 64 targets, the default costs a factor of 64, and the file system is working correctly throughout.

Misalignment. Take 1,024 clients each writing a contiguous record at its own offset. When the record is exactly the stripe size, every client's write lands inside one stripe and no two clients touch the same one. Shrink the record by 2.3 per cent, to 1,024,000 bytes, and the exact count is 992 boundary crossings and 1,000 stripes written by two different clients.

Those shared stripes are where distributed locking becomes visible. The file system must serialise conflicting extent writes, so a workload that appeared embarrassingly parallel acquires a serial component determined by a number — the record size — that the application chose for reasons unrelated to storage. This is the mechanism behind a large fraction of “the file system is slow today” reports, and the standard mitigations all work by removing the sharing: collective I/O that reorganises data into stripe-aligned chunks before writing141, one file per rank at the cost of an enormous namespace, or a middleware layer that maps the logical file onto physically disjoint pieces.142

Longitudinal studies of production file systems find the same pattern from the other end: aggregate utilisation is low, contention is bursty, and the worst episodes correlate with access patterns rather than with total load.143, 144

§26Metadata: the axis bandwidth cannot buy

A storage system has at least two pipes, not one. Bandwidth moves bytes. Metadata operations create, stat, open and unlink files, and they have their own latency, their own concurrency requirement, and their own servers. A job that reads a terabyte in a minute and then spends an hour listing the directory it came from has not encountered a bandwidth problem.

The IO500 benchmark makes this structural by construction: its score is the geometric mean of a bandwidth score and a metadata score, so a system cannot buy its position with one axis.145, 146

Plot the seventeen entries on the ISC26 ten-node production list and the spread is remarkable. Metadata rate per unit of bandwidth ranges over a factor of 186, from 1.3 to 237.1 thousand operations per second per GiB/s. 9 of the seventeen change rank if the metadata axis is dropped. The leading entry combines 2,551 GiB/s with 24.1 million metadata operations per second for a score of 7839.31; another entry with less than one GiB/s of bandwidth ranks above nothing at all and yet outscores several systems on metadata alone.

Two design responses to the metadata problem are visible in that list.

The first is to distribute the namespace, so metadata operations are served by many nodes rather than one. This works and it complicates every operation that spans directories.

The second is to stop providing POSIX semantics. DAOS is the clearest example: an object store over non-volatile media with no central metadata server, no distributed lock manager in the POSIX sense, and a transactional model in place of the file abstraction.147 Its results in that list are what a system looks like when the serialisation the interface required has been removed rather than optimised. Ceph makes a related trade in a different direction, computing placement rather than looking it up.148 Burst buffers add a fast tier in front of the capacity tier and are, read this way, a partition-count and latency intervention on the write path.149

§27Distributed storage: placement without a lookup

A parallel file system and a distributed object store solve overlapping problems with different commitments, and the difference is instructive because it is a concurrency difference rather than a capacity one.

The file system's central difficulty is that it must maintain a namespace and a set of guarantees — a path resolves to an inode, a write is atomic with respect to concurrent readers at some granularity, a rename is a single event — across many servers. Every one of those guarantees is a place where operations from different clients must be ordered relative to one another, which is to say a place where concurrency is deliberately destroyed. The metadata server and the distributed lock manager are not overheads bolted onto an otherwise parallel system; they are the mechanism by which the system keeps the promises its interface made.138, 139, 140

Object stores relax the promises and get the concurrency back. Ceph's contribution is the sharpest illustration: rather than storing a map from object to location and consulting it on every access, it computes the location from the object name with a deterministic function over the cluster topology, so a client can find data without asking anyone.148 A lookup that never happens needs no server, no replica, and no round trip; in the vocabulary of §4 this is a type-R optimisation applied to metadata rather than to bytes. The cost is that changing the cluster changes the function, so data must move when the topology does.

DAOS pushes the same argument further by targeting byte-addressable non-volatile media and dropping the block-oriented, lock-mediated model entirely in favour of a transactional key-array interface with no central metadata service in the traditional sense.147 Its position on the IO500 list is what that looks like from outside: metadata rates an order of magnitude above systems with comparable bandwidth, because the operations that used to serialise no longer exist rather than having been made faster.

Two caveats keep this from being a recommendation.

First, the guarantees the object stores dropped were not decorative. A great deal of scientific software assumes a POSIX file, and the work of porting is real work that produces no science. The middleware answer — keep the file interface, map it onto disjoint physical pieces underneath — is why libraries that reorganise I/O before it reaches the storage layer have been worth their complexity for two decades.141, 142, 144

Second, replication and erasure coding move the partition arithmetic again. Replication multiplies write traffic by the replica count and lets any replica serve a read; erasure coding reduces the write amplification and turns a read of one object into a read from several servers, which raises the number of requests that must be outstanding to keep the same bandwidth. Neither is uniformly better, and the choice is another instance of the trade this article keeps finding: fewer bytes moved against more transfers that must be in flight to move them.

Part VIIIThe whole machine

§28The fabric and the collective

Between the node and the storage sits the interconnect, and it obeys the same law with different constants. A 200 Gb/s link at 2 µs of latency requires 50,000 bytes in flight to run at rate, which is why RDMA interfaces are built around posting many operations rather than sending one and waiting.150, 151

Topology is the partition question at machine scale. Fat trees provision bisection bandwidth so that any permutation of traffic can be served152; dragonfly topologies trade some of that guarantee for far fewer long cables and rely on adaptive routing to avoid the worst cases.150, 153 Ultra Ethernet and UALink are the current attempts to standardise, respectively, the scale-out transport and the scale-up accelerator fabric.151, 154

The application-visible cost is almost always a collective. An allreduce over p ranks costs on the order of log p dependent steps whatever the algorithm, and each step has the fabric's latency in it.56, 155, 156 Cost models that make this explicit — a latency term, a per-byte term, and a rate at which a processor may inject messages — long predate the machines that make it painful.157, 158

Model a job with one second of parallel work, a 5 µs collective per doubling, and a millisecond of serial section.

At 16 cores it is 98.5 per cent efficient. At 256, 79.1 per cent. At 4,096, 18.7 per cent. At 16.8 million cores, 0.005 per cent — and the wall time over that last factor of 4,096 in cores changes by 1.16×, in the wrong direction past the optimum of 131,072 cores.

The lesson is not that networks are slow. It is that strong scaling consumes the very thing this article has been counting: at high core counts the work per core is too small to hide the coordination the extra cores require. Weak scaling avoids the problem by growing the work159, 160, which is why the machines on the list are sized for problems that grow. And noise makes it worse than the model says, because a collective is a synchronisation point at which the slowest participant sets the pace, so rare delays on individual nodes are amplified by the rank count.135, 161, 162

§29Composing the levels

Everything above has treated the levels one at a time. A real job traverses all of them, and the composition has two properties worth stating explicitly.

The requirements do not add; they nest. A core supplying sixteen outstanding line fills contributes those sixteen to the DRAM level only while it is running. During a collective it contributes nothing, and during an I/O phase it contributes nothing to either. The machine's aggregate concurrency at any level is therefore a function of what phase the application is in, which is why bulk-synchronous applications show a sawtooth in every bandwidth counter and why overlapping phases is worth so much more than it appears.

The scarcest supply moves. In a compute phase, the binding constraint is usually O at DRAM or T at the accelerator. In a communication phase it is O at the fabric. In a checkpoint it is P at the storage targets. A machine balanced for one is unbalanced for the others, and no single number summarises it. This is the honest reason a machine has a TOP500 position, an HPCG position, a Green500 position, an IO500 position and a Graph500 position, and why they disagree.1, 145, 163

The resilience story is the same argument at a longer timescale. As node counts rise, the mean time between failures falls, so checkpoints must be more frequent, so the storage system's concurrency requirement is driven by the failure rate of the compute system.164, 165, 166 Multi-level checkpointing answers by writing most checkpoints to a nearer, faster level and only occasionally to the file system, which is a partition and reuse argument applied to fault tolerance.167 The published design papers for the large United States systems make the same accounting visible from the procurement side: node counts, memory per node, injection bandwidth and storage tiers are chosen together against a target workload rather than maximised independently.168, 169, 170

There is a broader version of this point that the exascale reports made twenty years ago and that has held up: the cost of a machine is increasingly the cost of moving data, and the energy cost of a floating-point operation has fallen much faster than the energy cost of fetching its operands.171, 172, 173 Every mechanism in the ledger below is, at bottom, an answer to that.

§30A decision procedure

The practical value of the framing, if it has any, is that it turns performance work into a short sequence of questions with observable answers. Each step distinguishes a supplier, and each has a signature that does not require guessing.

Is the level saturated at all? Compare delivered bandwidth at the level in question against its peak. If it is at peak, the level is not the problem and the question moves up or down the hierarchy. This is the only step that requires no theory.

If not saturated, is the latency elevated? This is the discriminating observation and it is usually available. If latency is at or near the unloaded figure while bandwidth is far below peak, the machine is short of requests: the pipe is not busy, and the remedy is on the supply side. If latency has risen substantially, the pipe is congested and the remedy is to move less, not to ask more often. The two situations look identical on a bandwidth chart and demand opposite responses, which is why so much tuning advice contradicts itself.

If short of requests, which supplier is missing? Four checks, in increasing order of how much work they imply:

  • Partitions. Are the requests spread over the available servers? Bank-conflict counters, channel population, NUMA node distribution, stripe counts, queue counts. This is the cheapest to check and the most often wrong, because the defaults are frequently one.
  • Outstanding transfers. Is each stream keeping several requests in the air? Look at loads in flight per core, queue depth, posted RDMA operations. A synchronous loop anywhere in the path caps this at one and no other change will help.
  • Threads. Are there enough independent streams? Compute the required number from the level's latency and bandwidth rather than from the number of cores available, then compare.
  • Lanes. Are the vector or warp addresses generating the requests you think they are? Sector or line counts per instruction against the useful bytes; a ratio above one is amplification and it is the difference between measured and useful bandwidth.

If none of these is missing, ask whether the traffic should exist. Compulsory traffic against measured traffic, which is the roofline question asked in the direction people usually skip. Every byte that need not move is worth more than any of the four supplies above, because it lowers both terms of the equation at once. This is where blocking, fusion, layout changes and precision decisions belong, and it is where the largest wins in this article came from: the padding change in §10 was worth 7.95× and cost eight bytes per row.

The procedure has an obvious limitation worth stating: it assumes you can observe latency and bandwidth separately at the level of interest. On a CPU this is usually true through performance counters; at the storage and fabric layers it often is not, and the substitute — varying the concurrency deliberately and watching whether throughput responds — is slower but answers the same question.44, 144

§32What would refute this

The thesis is that every level of an HPC machine is a pipe whose delivered bandwidth is governed by Little's Law, that architecture is the business of supplying or removing the resulting concurrency requirement, and that the five suppliers exhaust the design space. Each clause can fail, and it is worth saying how.

A level that reaches its peak with less in flight than the law predicts. This would mean the quoted latency is not the latency that matters — that some pipelining internal to the device makes the effective service time shorter than the round trip. This is not a refutation so much as a correction of the input, and it happens: prefetch-friendly DRAM with open row buffers has a shorter effective latency than the random-access figure suggests. The claim survives if the corrected latency is used, and would genuinely fail only if no consistent latency could be assigned.

A sixth supplier. The taxonomy in §4 claims completeness, which is the strongest and most falsifiable thing in the article. A mechanism that raises delivered bandwidth without supplying lanes, threads, outstanding transfers, or partitions, and without removing traffic, would break it. Compression is the interesting candidate: it moves fewer bytes for the same logical data, which is arguably a sixth category rather than reuse. I would classify it under R, but the classification is arguable and the argument would be worth having.

A level where the requirement is met but the bandwidth is not delivered. This would indicate a bottleneck the law does not see — arbitration, protocol overhead, ordering constraints. These exist, and the correct reading is that the law gives a necessary condition, not a sufficient one. The article should be read as claiming that under-supply explains most observed shortfalls, not all of them. That is a weaker claim and it is the one the evidence supports.

The ordering could be wrong. The article asserts that reuse is worth more than the other four because it acts on both terms. A workload with no reuse available — a genuine random-access traversal — makes that claim vacuous rather than false, but a machine class where reuse consistently underperformed straightforward partition-count increases would be evidence against the emphasis.

§33Against this article

Four objections seem to me serious, and the fourth is the strongest.

“This is just the roofline model with extra vocabulary.” Partly. The roofline answers whether arithmetic or bandwidth binds; it says nothing about whether the bandwidth bound will be reached, and in practice a great many codes sit well below the memory roof for concurrency reasons the diagram cannot express. Cache-aware and hierarchical roofline variants extend the model in the capacity direction rather than the concurrency one.22, 23 The addition here is small but it is not nothing: two questions rather than one, and a taxonomy of answers to the second.

“Little's Law is an equilibrium result and real machines are bursty.” True and important. The law holds for time averages in a stable system; it says nothing about a phase that lasts less than a few latencies. Short kernels, launch overheads and the convoy effect in §14 are all cases where the average is not the story. The law remains the right accounting for steady-state throughput, and the article's experiments are averages over runs long enough for that to hold.

“The declared inputs are chosen to make the point.” They are chosen to be representative, and every one is stated in the source so it can be varied. The qualitative conclusions — that requirements span orders of magnitude, that one core cannot saturate a socket, that occupancy is a derived requirement — hold across any plausible substitution. Individual figures do not: the exact core count needed to saturate a socket moves with the latency assumed.

“The experiments are models, and the article presents them with the authority of measurements.” This is the real objection. The cache simulator is an exact LRU model of a cache that does not exist in that simple form on any shipping processor, which has multiple levels, non-inclusive policies, prefetchers, and replacement policies that are not LRU. The warp scheduler model has one issue port where a real SM has four. I have been careful to describe them as exact over their models rather than accurate about hardware, and the numbers should be read that way: they establish that a mechanism can produce an effect of a given size and shape, not that a particular machine exhibits that size. Where I have wanted a claim about real hardware I have used published measurements and the June 2026 lists instead. The reader is entitled to discount every simulated figure by whatever they think the model gap is worth, and the argument should survive that discount, because the argument is the law and the taxonomy, not the constants.

==============================================================================
SUMMARY OF FINDINGS
==============================================================================

E1    one core with 16 line fills in flight tops out at 12.80 GB/s, 2.8% of a
      460.8 GB/s socket; 36.0 such cores are needed before the DRAM pins, not
      the cores, become the limit

E1    sustaining 8.0 TB/s of HBM at 600 ns needs 37,500 coalesced warp-loads
      outstanding at every instant, which is the entire warp population of a
      large GPU several times over -- occupancy is Little's Law cast in
      silicon

E1    a 12-channel DDR5 socket contains 768 independently addressable banks
      and needs 576 line fills in flight to reach its peak -- a ratio of 1.33.
      The partition count is not an implementation detail beside the bandwidth
      figure; it is what makes the bandwidth figure reachable

E1    required bytes in flight span 10,016,026x across one machine, from 499 B
      at L1 to 5,000,000,000 B at the parallel file system

E2    the ridge point runs from 3.32 flop/byte on a 2009 socket to 2273 on a
      2026 low-precision part, a factor of 684, and the count of memory-bound
      kernels goes from 7 to 9 of 10 with no change to any kernel. The trend
      is not monotone: A64FX sits at 3.00, BELOW the 2009 socket, because HBM
      was attached to a deliberately modest flop rate

E2    on the 67th TOP500 list HPCG runs at 3.62% of HPL on Fugaku (HBM on
      every core) and 0.55% on Aurora, a 6.5x spread in delivered fraction
      between machines whose peak flop rates differ by far less

E3    an n=128 matrix product on a 32 KiB 8-way L1 misses 2,135,072 times at a
      leading dimension of 128 and 268,416 at 129 -- a 7.95x reduction bought
      by allocating one extra double per row. 128 doubles is 16 lines, 16
      folds 128 rows onto 4 of the 64 sets, and one word of padding unfolds
      them. Loop interchange fixes the same problem and lands on 266,240
      misses, the identical number reached by padding to 136

E3    the textbook block-size rule -- pick the largest b with 3b^2 doubles
      inside the cache -- gives b = 36 here. The exact model's minimum is b =
      24, using 13,824 of the 32,768 bytes available, and following the rule
      costs 135.3% more misses (87,297 against 37,093). Capacity is the wrong
      quantity: associativity and the leading dimension decide

E3    a 16 KiB working set that fits three times over in a 32 KiB cache misses
      on every one of 768 accesses once the stride reaches 256 bytes, because
      the index function folds all 256 lines onto 16 sets of 8 ways: capacity
      was never the binding constraint

E4    the predicate is true for 9.59% of the array, so a scalar branch skips
      90.4% of the work; a VL=2 machine can skip 80.8% of its vectors and a
      VL=64 machine only 0.0%. Widening the vector converts skippable work
      into masked-off work: at VL=64 the machine issues 10.4 lanes for every
      lane that does something

E4    a unit-stride VL=8 double vector touches 1 cache line; the same eight
      elements at stride 8 touch 8 lines and move 8x the bytes -- the vector
      length did not change, the address pattern did

E5    a kernel needs at least 6 arithmetic instructions per memory instruction
      before 64 warp slots can hide a 400-cycle latency; below that threshold
      the SM is idle in exact proportion to the shortfall and no occupancy
      tuning can help, because the required occupancy exceeds what the
      hardware has to offer

E5    64 identical warps released on the same cycle take 1.156x longer than
      the same 64 warps spread evenly across one iteration period (47,344 vs
      40,960 cycles at 31 arithmetic instructions per load). Nothing about the
      work changed; the warps synchronised themselves into a convoy and left
      the issue port idle in bursts

E5    a kernel that spills to 64 registers per thread holds 32 of 64 warp
      slots, which raises the arithmetic-per-load ratio it must reach to
      saturate issue from 6 to 12; a register allocation decision made by the
      compiler sets the maximum latency the hardware can hide

E6    a warp whose 32 lanes read one field of a 48-byte struct requests 32
      sectors and moves 1,024 bytes to deliver 128, an 8x amplification; the
      identical loads over a packed array request 4 sectors and move exactly
      128 -- the permutation of lanes within the warp costs nothing at all,
      which is why reversal and an XOR shuffle both stay at 4

E7    the same code on the same silicon delivers 170.7 GB/s when one thread
      touched the array first and 1843.2 GB/s when the threads that read it
      touched it first -- a 10.80x difference produced entirely by which core
      executed the first store to each page

E7    interleaving recovers 31% of the gap but leaves the mean latency at
      125.0 ns, so the lines that must be in flight rise 4.00x over the
      single-node case while the latency to be covered does not fall at all;
      the best policy is also the hungriest, needing 2,304 lines in flight,
      which is 144 cores at 16 line fills each -- more than a four-socket
      machine usually has

E8    reaching 1,000,000 IOPS from a device with 80 us of latency requires 80
      requests outstanding at all times, no matter how fast the flash is; a
      thread issuing one synchronous read at a time gets 12,500 IOPS and the
      drive is idle 99.2% of the time

E8    1,024 clients writing 1 MiB records to a file with a stripe count of 1
      put every byte on one target and use one sixty-fourth of the servers a
      stripe count of 64 would use; keeping 64 stripes but shrinking the
      record by 2.3 per cent to 1,024,000 bytes produces 992 boundary
      crossings and leaves 1,000 stripes shared between two clients, which is
      exactly where the lock traffic comes from
