Rerun it.
Four practices that decide whether you can.

Idempotency, immutability, physical layout and continuous delivery are usually taught as four separate disciplines. They are better understood as four answers to one question, asked at three in the morning: can we safely run that again?

The question every pipeline is eventually asked

At some point — usually between two and four in the morning, usually during a quarter close — someone will ask an engineer a question that sounds administrative and is in fact architectural: can we just run it again?

Everything that follows in this article is an answer to that question. A pipeline that can be rerun safely is a pipeline that can be repaired, backfilled, migrated, tested, and reasoned about. A pipeline that cannot be rerun safely is not really a pipeline at all; it is a one-way transformation that happens to have executed successfully so far, and its correctness is a historical accident rather than a property of the system.

The distinction is not academic. The economics of data platforms have inverted over the last fifteen years. Compute is elastic and metered; storage is cheap and effectively unbounded; engineering attention is the scarcest input by an order of magnitude. Under those conditions the dominant cost of a data platform is not the cost of running it — it is the cost of the hours spent establishing whether a number is right, and the cost of the decisions taken while nobody was sure.[1] The practices in this article are all, in one way or another, mechanisms for converting that uncertainty into something cheaper: a rerun, a diff against yesterday's snapshot, a failing test on a pull request.

Four of them carry most of the weight.

  • IdempotencyRunning the same work twice leaves the system in the same state as running it once.
  • ImmutabilityRaw data is never destroyed or edited in place; change is expressed by appending new versions.
  • LayoutPartitioning, clustering and file sizing — the physical arrangement that determines what a query has to read.
  • CI/CDChanges to pipelines are versioned, tested and promoted through environments, exactly like application code.

They are usually taught separately, which obscures the most useful thing about them: they are load-bearing for each other. Idempotency is much easier to achieve when the storage layer is immutable, because “replace this partition” becomes an atomic metadata operation rather than a delete-then-insert race. Immutability is only affordable when the layout is sane, because keeping every version of a badly partitioned table is keeping every version of a problem. Continuous integration for data is only practical when you can spin up a full-size test environment cheaply, which requires zero-copy clones, which requires immutability. And so on around the loop. Teams that adopt one practice in isolation typically discover the other three by paying for them.

What follows is a working tour: the history that produced each practice, the concepts that make it precise, the mechanisms that implement it in current systems, the costs it imposes, and the specific ways it is usually got wrong. There is a runnable implementation at the end — about 150 lines of standard-library Python that does all four at once, which is useful mainly for showing how few moving parts the ideas actually require.

Where these practices came from

None of the four is native to data engineering. Each was imported, usually a decade or two after being worked out somewhere else, and usually because a change in hardware economics made it suddenly affordable.

The oldest root is Codd's insistence in 1970 that the logical description of data be separated from its physical arrangement, so that storage layout could be changed without rewriting the applications that queried it.[2] That separation is the reason a modern engineer can add a clustering key to a table without touching a single downstream query, and it is worth remembering that it had to be argued for.

The vocabulary of correctness arrived shortly after. Gray's 1981 survey named the properties a transaction should have and, more usefully, the limits of what transactions could promise.[3] Haerder and Reuter fixed the acronym in 1983.[4] Atomicity in particular — all of a change becomes visible, or none of it does — is the single guarantee that makes the write-audit-publish pattern of section 14 possible, and it took the analytical world roughly thirty-five years to get it back after giving it up for scale.

Immutability as a storage strategy has an equally specific origin. Rosenblum and Ousterhout's log-structured filesystem, published in 1992, made the case that never overwriting a block in place produced faster writes and better crash recovery than update-in-place, and that the cost — garbage collection of superseded blocks — was a price worth paying.[5] Every table format discussed later in this article is a restatement of that argument at a different level of the stack, with “garbage collection” renamed VACUUM or expire_snapshots.

Kimball's dimensional modelling work through the 1990s contributed the load discipline: the idea that a warehouse load is a defined, repeatable procedure with a grain, a set of keys, and explicit rules for what happens when a dimension attribute changes — the slowly changing dimension types that remain the standard vocabulary for versioning history in a table.[6]

Then came the scale-out era, and with it a temporary collapse in guarantees. MapReduce made deterministic re-execution the basis of fault tolerance: if a task fails, run it again on another machine, which works precisely because the map and reduce functions are required to be deterministic and side-effect-free.[7] Spark generalised this into lineage-based recovery over immutable partitioned collections.[8] Both were, in effect, industrial-scale arguments for idempotency, though neither used the word much.

The storage layer of that era was less fortunate. HDFS held the entire filesystem namespace in the NameNode's memory, which made large numbers of small files an operational hazard rather than a mere inefficiency.[9] Hive layered SQL over that filesystem and encoded partitions as directory paths, which was simple, legible, and responsible for a decade of tables partitioned by a column that turned out to have four million distinct values.[10] Dremel showed that a columnar format with per-block statistics could make interactive queries over web-scale data possible, establishing the pattern — store statistics next to the data, skip blocks that cannot match — that all modern layout tuning exploits.[11]

The final act is the return of transactions. Snowflake's architecture, published in 2016, was built on immutable micro-partitions with metadata-driven pruning.[12] Netflix released Iceberg in 2017 to fix the correctness problems of tracking table contents through directory listings on an eventually consistent object store.[13] Delta Lake, published in 2020, showed that a compacted write-ahead log kept alongside the data files could deliver serialisable transactions, time travel and fast metadata operations on top of a plain key-value object store.[14] What had been given up for scale was reclaimed, and the four practices could finally be implemented rather than merely aspired to.

Idempotency: what the word actually promises

The mathematical definition is unhelpfully simple. An operation f is idempotent if f(f(x)) = f(x) for all x: applying it twice is indistinguishable from applying it once. HTTP borrows the term for methods whose repeated application has the same intended effect as a single application — PUT and DELETE qualify, POST generally does not — and is careful to note that this is a property of the intent of the request, not a promise that the observable response will be byte-identical.[15] That caveat transfers directly to data pipelines, where the useful question is never “did the second run produce the same logs?” but “did it produce the same table?”

Where the concept becomes concrete is in messaging semantics, and the vocabulary there is worth getting right because it is routinely misused in vendor material.

At-most-once delivery drops messages rather than risk duplicating them. Almost nobody wants this for analytical data. At-least-once is the default behaviour of essentially every queue, scheduler and retry loop in existence: the sender retries until it receives an acknowledgement, and because acknowledgements themselves can be lost, duplicates are inevitable. Exactly-once is achievable, but only inside a transactional boundary that spans the whole path from input to output.

Kafka's implementation is the canonical worked example and repays study because it shows exactly how much machinery is required. Each producer is assigned a producer ID and attaches a monotonically increasing sequence number per topic-partition; the broker tracks the last committed sequence number and rejects any request whose sequence number is not exactly one greater, which lets it discard the duplicates that retries produce.[16] That gets you deduplication within a producer session. Extending the guarantee across sessions and across the consume-transform-produce cycle requires a transactional ID, a producer epoch to fence out zombie instances after a restart, and consumer offsets committed inside the same transaction as the output records.[17] Stream processing on top of that needed a further proposal to handle state stores and rebalances,[18] and yet another to stop the design from requiring one producer per input partition.[19] Exactly-once was shipped in Kafka 0.11 behind a single configuration flag,[20] and the amount of protocol design behind that flag is a fair measure of how hard the guarantee is.

Stream processors reach the same place by a different route. Flink's fault tolerance rests on periodic distributed snapshots of operator state, a direct descendant of the Chandy–Lamport algorithm for determining consistent global states of a distributed system without stopping it.[21,22] On failure the job rewinds to the last checkpoint and replays; correctness depends on sources being replayable and sinks being either transactional or idempotent.

The wider lesson, drawn out at length in the distributed-systems literature, is that each of these guarantees is purchased with coordination, and coordination is the resource that does not scale.[23] Which brings us to the guarantee that batch data engineering actually builds, and which deserves its own name: effectively-once. Retries happen. Duplicate deliveries happen. The pipeline does not attempt to prevent them; it makes them harmless, by ensuring that the write converges to the same state regardless of how many times the work is attempted.[24] This is a weaker guarantee than exactly-once and a considerably more robust one, because it does not require the whole path to be enclosed in a single transaction. It requires only that the last step — the write — be idempotent.

Exactly-once is a property of a closed system. Effectively-once is a property of a well-built sink — and a sink is something you control.

The four shapes of an idempotent write

In practice there are four ways to write to a table, and only one of them is unconditionally unsafe. It is also, unfortunately, the most natural thing to type.

Blind append. INSERT INTO target SELECT … is not idempotent and never can be. A retry after a partial failure, a duplicated schedule trigger, or a manual rerun by an engineer who did not realise the first run had succeeded all produce the same result: duplicate rows, no error, and a metric that is quietly wrong until someone reconciles it against a source system. This pattern is responsible for a disproportionate share of data incidents precisely because it fails without signalling.

Partition overwrite (delete-then-insert). The run computes the full contents of one or more partitions and replaces them wholesale. Because the unit of replacement is the partition rather than the row, the operation is naturally idempotent: running it five times leaves the partition in the state determined by the input, not by the number of attempts. This is the workhorse of batch data engineering, and its correctness depends entirely on two things — that the partition boundary is derived from the data rather than from the clock, and that the delete and the insert are atomic with respect to readers. On a plain object store neither is free, which is why transactional table formats matter so much here.[14]

Merge / upsert. MERGE INTO reconciles incoming rows against existing ones on a key, updating matches and inserting the rest. It is idempotent provided that the key is a genuine business key and that ties are broken deterministically — typically by a source sequence number, a change-data-capture log position, or a last-updated timestamp taken from the source rather than from the pipeline. Merges on a surrogate key generated at load time are not idempotent, because the surrogate differs between runs. Merges without a tiebreak are not idempotent either, because when two versions of the same key arrive in one batch, which one wins depends on scan order.

Append plus idempotency ledger. Where the output genuinely must be append-only — an event store, an audit table, an immutable fact log — the run computes a stable key from its inputs, checks a ledger of already-applied keys, and no-ops if the key is present. The key is usually a digest of the sorted input batch, which has the pleasant property of distinguishing “the same day rerun” from “the same day restated with corrected data”. The critical detail is that the ledger write and the data write must be in one transaction; otherwise the race condition has simply been relocated.

Two ancillary points are worth stating explicitly because they are where otherwise careful implementations leak.

First, determinism is a prerequisite, not a bonus. If a transformation calls random(), generates a UUID per row, reads current_timestamp, or depends on the physical order in which files were scanned, then no write strategy can make the pipeline idempotent, because the input to the write differs between runs. MapReduce's requirement that user functions be deterministic was not pedantry; it was the precondition for re-execution as a recovery strategy.[7]

Second, the source must be replayable. An idempotent write is useless if reading the same logical slice twice returns different data. This is why pipelines that consume from mutable operational tables usually land a raw, timestamped extract first and transform from that: the landed extract is the replayable source, and the fact that the upstream database has moved on becomes irrelevant.[25]

Time is the enemy: logical intervals and backfill

The most common single defect in scheduled pipelines is a call to the wall clock. It is worth dwelling on because it is so easy to write and so hard to see in review.

Consider a daily job whose SQL contains WHERE event_date = CURRENT_DATE - 1. On the day it runs, it is correct. Six weeks later, when someone needs to reprocess March because a bug was found in the currency conversion, every one of those historical runs computes the same predicate — yesterday — and the backfill silently rewrites the same partition thirty times. The job is deterministic in the trivial sense that it always does the same thing, and useless in the sense that what it does has no relationship to the day it is supposed to represent.

Orchestrators solve this by giving each run a logical identity. Airflow's model is explicit about it: a DAG run covers a data interval, runs are treated as atomic and idempotent items, and the scheduler will create a run for every interval between the start date and now that has not yet been executed — the behaviour called catchup.[26] The templated interval boundaries, not the system clock, are what the task should use to decide what it reads and where it writes. Catchup exists precisely because runs are supposed to be independent and repeatable; if they are not, catchup turns from a recovery feature into a way of amplifying a bug across a year of history.

Three practical corollaries follow.

Half-open intervals, always. A daily partition is [2026-03-01T00:00Z, 2026-03-02T00:00Z). Closed intervals on both ends double-count boundary records; intervals expressed in local time double-count or drop an hour twice a year. Store and partition in UTC, present in local time.

Write scope must equal read scope. If the run reads the interval for 1 March, it must write only the partitions derived from 1 March. A run that reads one day and updates a running total across the whole table is not idempotent, and no amount of orchestrator configuration will make it so. Aggregates of this kind should be recomputed from the partitioned base, or maintained as a separate incremental model with its own idempotency story.

Late-arriving data needs a stated policy. Real event streams deliver records whose event time falls in a partition that has already been processed. The choices are to widen the reprocessing window (each run rewrites the last N days, which stays idempotent because it is still partition overwrite), to route late records to the current partition and accept that the table is partitioned by arrival rather than occurrence, or to reject them. All three are defensible; leaving it undecided is not, because the resulting behaviour depends on which of two timestamps happened to be used in the partition expression.

The non-idempotent tail

Everything above concerns writes to tables, where the state is under the pipeline's control. The harder problem is the tail of the pipeline where it is not.

A reverse-ETL job that pushes a customer segment into a marketing tool triggers an email campaign. A pipeline step that posts to a webhook fires a downstream workflow. A job that writes a file to a partner's SFTP endpoint causes an invoice to be raised. None of these side effects can be undone by rerunning, and none of them is made safe by an idempotent warehouse write. This is the part of the pipeline where a 3 a.m. rerun does actual damage, and it deserves explicit design rather than hope.

The standard mitigations, in rough order of preference:

Push the idempotency key outward. Most mature APIs accept an idempotency key on write requests: a client-generated identifier that the server records, so that a repeated request with the same key returns the original result instead of performing the action again. Where the receiving system supports this, the pipeline should derive the key deterministically from the logical run identity and the payload — not from a UUID generated at call time, which defeats the whole mechanism.

Separate computation from emission. Compute the desired outward-facing state into a table, idempotently. Then have a separate, small process compute the diff between that table and the last successfully emitted state, and send only the diff. Reruns of the computation are free; the emitter is the only component that must be careful, and it is small enough to be careful in.

Make the outward action a declaration of state, not an event. “Set this customer's segment to lapsed” is safe to repeat. “Send the lapsed-customer email” is not. Where the receiving system permits a declarative interface, using it converts an at-least-once problem into a non-problem.

Gate on environment. Test and CI environments must be physically incapable of reaching production side-effect endpoints — not by configuration convention but by credentials that do not exist in that environment. This is the data equivalent of the standard operational rule that the blast radius of a mistake should be bounded by something other than the care of the person making it.[27]

Immutability: why nobody deletes raw data any more

The second practice is easier to state and harder to hold to: raw data is never modified or destroyed. Corrections are expressed as new records, new versions or new snapshots, never as edits to the original.

The argument for it was made most forcefully by Nathan Marz under the heading of human fault tolerance. Distributed systems literature spends most of its energy on machine failure, but the failures that actually destroy data warehouses are human: a transformation with an inverted join condition, a deployment that swapped two columns, a deduplication rule that was subtly wrong for eight months. If the pipeline overwrites its inputs, these mistakes are unrecoverable — the evidence needed to fix them was consumed by the process that made them. If the master dataset is immutable and append-only, every such mistake is recoverable by fixing the code and recomputing, because the raw record of what happened is still there.[28]

Pat Helland made the complementary economic argument: immutability used to be unaffordable and is not any more. When storage was expensive, update-in-place was a necessity; when storage is cheap and coordination is expensive, keeping every version and never coordinating on mutation is the better trade.[29] The same reasoning had already reshaped filesystem design three decades earlier.[5]

The third strand is the log. Kreps's argument that an ordered, append-only log is the natural common substrate for data integration — because every derived system can be rebuilt by replaying it from the beginning — is what makes reprocessing a routine operation rather than an emergency.[30] Event sourcing applies the same idea at the application level: persist the sequence of state changes rather than the current state, and derive the current state on demand.[31] The later argument that a single replayable log removes the need to maintain two parallel batch and streaming code paths follows directly.[32]

In practice this crystallises into a small number of rules that are worth stating as rules because they are the ones teams negotiate away first:

  • The landing zone is read-only after write. Ingestion writes files; nothing else ever modifies them. If a source sends a correction, it lands as a new file with a later ingestion timestamp.
  • Transformations write to new locations. A silver table is a derived artefact of the bronze layer, reproducible by rerunning the transformation. It is never the same physical bytes with a few columns fixed up.
  • History is modelled, not overwritten. When a dimension attribute changes, the change is recorded as a new versioned row with validity dates — Kimball's Type 2 — rather than an update that erases what the attribute used to be.[6]
  • Deletes are physical only under a policy. Removing data is a deliberate, audited operation governed by retention and legal requirements, not a side effect of a pipeline step.

The machinery: commit logs, snapshots and time travel

Immutability at the level of a table — as opposed to a directory of files — is delivered by the open table formats, and it is worth understanding the mechanism because almost every operational property downstream is a consequence of it.

The construction is the same in outline across implementations. Data lives in immutable columnar files. A separate metadata layer records which files constitute the table at each point in time. A commit consists of writing new data files, writing a new metadata entry that lists the resulting file set, and atomically swapping a single pointer to make it current. Readers resolve the pointer once at the start of a query and are therefore isolated from concurrent writes for its duration.

Iceberg tracks individual data files rather than directories, precisely so that table state does not depend on listing a filesystem; each snapshot is a complete set of files, listed through manifest files, and transitions between metadata files are atomic, which is what provides snapshot isolation.[13,33] Delta Lake takes the write-ahead-log route: an ordered log of commit records, periodically compacted into Parquet checkpoints, giving ACID properties and fast metadata operations over object stores whose only native primitives are key-value put and list.[14] Snowflake reaches similar ground from the warehouse side, with immutable micro-partitions and metadata that records the range of values each one contains.[12,34]

Four capabilities fall out of this design, and each of them is doing real work elsewhere in this article.

Atomic publish. Consumers see the complete effect of a write or none of it. This is what makes the write-audit-publish pattern of section 14 possible: a staged snapshot can be validated at full volume before it becomes visible.

Time travel. Because old snapshots still reference live files, querying the table as of a previous version or timestamp costs nothing extra. Its practical uses are unglamorous and constant: diffing today's load against yesterday's to explain a metric movement, reproducing a model training set exactly, and rolling back a bad deployment by repointing rather than restoring from backup.[35]

Schema and partition evolution. Columns are tracked by identifier rather than position, so they can be added, renamed or dropped without rewriting data; partition layouts can be changed for future writes without invalidating old data.[35] The significance for immutability is that a schema change no longer requires a full-table rewrite, which is the operation most likely to be executed badly at scale.

Branching. Because a snapshot is just a named pointer into an immutable file set, a branch is cheap: a second pointer. This is what enables zero-copy environments for testing, and the staging branch in write-audit-publish.[36] Catalog-level implementations extend the idea to multiple tables at once, giving Git-like semantics over the whole warehouse.[37]

Outside the analytical stack, immutability is also enforceable at the object level. S3 Object Lock implements a write-once-read-many model in which an object version cannot be deleted or overwritten for a specified retention period, or while a legal hold is in place.[38] It offers two modes: governance mode, which permits privileged users to lift the lock, and compliance mode, in which the protection cannot be removed by any user including the root account until the retention period expires.[39] The distinction matters because compliance mode is the one assessed against records-retention regulations, and it is also the one that will happily lock you into paying for a petabyte of mistakes for seven years.[38]

What immutability costs

Practices become dogma when their costs go unstated, so it is worth being blunt about the three that immutability imposes.

Storage and metadata growth. The storage bill is the obvious cost and usually the least important, given object-store pricing. The metadata growth is the one that bites: every retained snapshot pins the files it references, so a table with a long retention window and a high commit rate accumulates file counts that slow down query planning. Iceberg and Delta both provide snapshot expiry and file cleanup for this reason, and both make the retention window a deliberate configuration rather than a default to be ignored.[40,41]

History is not the same as recoverability. Keeping seven years of snapshots does not mean you can restore to any of them usefully; it means the metadata says you can. If the transformation code that produced snapshot 4,120 no longer exists in any branch, the snapshot is an artefact you can read but not explain. Immutable data is only half of reproducibility; the other half is version-controlled transformations, which is one of several places where practice four turns out to be a precondition for practice two.[42]

The erasure problem. This is the genuinely hard one. GDPR Article 17 gives data subjects a right to erasure of personal data, exercisable within a defined period.[43] An architecture whose central commitment is that nothing is ever deleted is, on the face of it, in direct tension with a legal requirement that certain things must be.

The tension is resolvable but not for free, and the resolution has several moving parts. A row-level DELETE against a transactional table format removes the row from the current snapshot, but the underlying files are still referenced by earlier snapshots; the data is genuinely gone from storage only once retention expires and a cleanup operation removes unreferenced files.[41] Where deletion vectors are used — a performance optimisation that marks rows as deleted without rewriting the file — an additional purge step is required to rewrite the underlying files without the deleted rows, or the bytes remain on disk.[41] Vendor guidance is explicit that default history retention (thirty days in one common configuration) must be reconciled against the statutory response window, and that the cleanup step is what actually discharges the obligation.[44]

Two design decisions make all of this dramatically easier, and both must be taken early. The first is to segregate personal data: if the bronze layer stores a surrogate user_id and personal attributes live in one narrow, well-known table, then erasure touches one table rather than four hundred.[41] The second is to keep the retention window on tables containing personal data as short as the recovery requirement genuinely allows, and to keep long-horizon history on the derived, de-identified tables where it does not create exposure. Immutability is a default, not a vow; the discipline is in deciding which data is immutable for how long, and writing that decision down where an auditor can read it.

Layout I: bytes scanned is the bill

Partitioning and clustering are usually filed under performance tuning, which undersells them. On a modern platform the physical layout of a table is the primary determinant of what that table costs to use, because every serious query engine now charges — in credits, in slot-seconds, or in scanned bytes — for data read rather than for rows returned. A well-laid-out table and a badly laid-out table containing identical data can differ by two orders of magnitude in the cost of the same query.

The mechanism has three layers, and it is worth separating them because they are often conflated.

Partition pruning happens at planning time, before any data is read. The engine evaluates the query's predicates against partition metadata and eliminates whole partitions. Because this is metadata-only, its cost is negligible and its effect is total: a pruned partition is not read at all. BigQuery makes the consequence unusually visible by being able to estimate the exact bytes a query will scan before it runs, precisely because pruning is resolved from metadata.[45]

File and row-group skipping happens one level down. Columnar formats store per-column statistics — minimum, maximum, null count — for each row group, and engines use them to skip blocks that cannot contain matching rows. Snowflake maintains equivalent metadata per micro-partition and uses it to avoid scanning partitions that cannot satisfy the filter.[34] Delta Lake's data-skipping algorithms use the same principle over file-level statistics.[46] The critical property is that skipping only works if related values are physically near each other: statistics on a column whose values are randomly scattered across every file will have min–max ranges that overlap completely, and no file can be skipped. This is the whole justification for clustering.

Column projection is the columnar format's native advantage: a query touching six columns of a two-hundred-column table reads only those six column chunks. Parquet's recommended configuration — row groups of 512 MB to 1 GB, sized so that a row group fits within a storage block — exists to make the sequential I/O of those column chunks large enough to be efficient.[47]

The point that gets lost in tuning guides is that all three gates are set at write time. An analyst cannot make a badly partitioned table prune. A more powerful warehouse does not make overlapping statistics informative. Layout is a property the writer confers on the data, and changing it later means rewriting the data. This is why layout belongs in the same conversation as idempotency and immutability rather than in a performance appendix.

Layout II: choosing a partition key, and the small-file tax

The rule for choosing a partition key can be stated in one sentence: partition on the column that appears in the WHERE clause of most queries, at a granularity that produces partitions in the hundreds of megabytes. Everything difficult about the decision is contained in the second half of that sentence.

Over-partitioning is by far the more common failure, because the intuition it violates is a good intuition everywhere else. Finer partitioning means better pruning; better pruning means faster queries; therefore partition by hour, or by hour and region, or by customer_id. What this misses is that each partition is at minimum one file, and that files have a fixed cost independent of their contents.

Hadoop made the cost brutally legible: every file, directory and block was an object in the NameNode's memory, occupying roughly 150 bytes as a rule of thumb, which meant that ten million small files consumed around three gigabytes of NameNode heap and that a billion files was simply not feasible.[48,9] The metadata ceiling was a hard architectural limit, and small files could exhaust it while the DataNodes still had most of their disk free.[49]

Object stores removed the central metadata server and therefore the hard ceiling, and a generation of engineers concluded that the small-file problem had gone away. It has not; it has changed shape. The cost is now paid in query planning — listing objects, opening files, parsing footers, deserialising statistics — and in the per-request latency of object-store APIs, which is dominated by round trips rather than bytes. A table of ten thousand one-megabyte files and a table of ten one-gigabyte files hold the same data and behave nothing alike. This is the reason table formats track files explicitly in metadata rather than by listing directories,[13] and the reason every lakehouse platform ships a compaction command.

The other end of the distribution has its own penalty. Very large files reduce parallelism, force the engine to read more than it needs when only a few rows match, and increase the memory required to buffer a row group during writes.[47] The practical guidance converges: Delta Lake's OPTIMIZE defaults to a target file size of 1 GB, configurable downward,[46] and Parquet's own documentation recommends row groups of 512 MB to 1 GB.[47]

Several hard constraints are worth memorising because they turn design questions into arithmetic:

  • BigQuery caps a table at 4,000 partitions. Daily partitioning therefore gives roughly eleven years of history; hourly gives about five months.[45] If the retention requirement exceeds the partition budget, the granularity is wrong, not the requirement.
  • Partitioning is preferred to table sharding. Splitting data across date-suffixed tables forces the engine to maintain schema and metadata per table and to check permissions per table.[45]
  • Layout work has a size threshold. Google's own partitioning and clustering recommender only considers tables above 100 GB for partitioning and 10 GB for clustering, on the grounds that below those sizes the benefit is small and unpredictable.[50] A great deal of layout tuning is applied to tables too small for it to matter.

Two refinements deserve mention because they remove common footguns. Iceberg's hidden partitioning decouples the physical partition layout from the query: the table is partitioned by a transform of an existing column, such as day(event_ts), and the engine derives the partition filter from a predicate on the original column. Analysts do not need to know the partitioning scheme, and queries do not silently degrade because someone filtered on the timestamp rather than the derived partition column.[35] Partition evolution addresses the fact that the right granularity changes as a table grows: the layout can be changed for future data without rewriting what already exists.[35]

Finally, compaction is not free and is not a background nicety. Rewriting files consumes compute proportional to the data rewritten, and the frequency of compaction is a direct trade between query performance and maintenance cost.[51] The trade should be made explicitly, per table, with reference to how often the table is queried — not set once in a platform default and forgotten.

Layout III: clustering, the second axis

Partitioning is a coarse instrument: it works by physical separation, so it is limited to keys with few enough distinct values to yield sensibly sized groups. Clustering is the complementary tool — it sorts or co-locates related rows within a partition, so that per-file statistics become selective and skipping works.

Snowflake's model is instructive because it makes the underlying quantity measurable. Data is stored in micro-partitions, each with metadata about the range of values it contains; as data is loaded, clustering information is recorded and used to skip micro-partitions that cannot match a predicate.[34] Defining a clustering key causes the platform to maintain that co-location automatically, with no further administration.[52] The diagnostic is clustering depth: the average number of micro-partitions whose value ranges overlap for the specified columns. A low depth means ranges are disjoint and pruning is effective; a high depth means the table is poorly clustered for those columns.[53] Being able to ask a table how well clustered it is, rather than inferring it from query times, is the difference between tuning and guessing.

The lakehouse equivalents have evolved through three generations. Plain OPTIMIZE performs bin-packing compaction, which is idempotent: running it twice on unchanged data has no effect the second time.[46] Adding ZORDER BY sorts data by a space-filling curve over several columns so that multi-column filters can skip files; it is explicitly not idempotent, though it operates incrementally, and its effectiveness degrades as columns are added.[46] Liquid clustering replaces both partitioning and Z-ordering for new tables in that ecosystem: clustering keys can be changed without rewriting the table, and the physical layout is applied incrementally when optimisation runs rather than at every write.[51,54] The direction of travel across vendors is consistent: move layout from a decision made once at table creation to a policy the platform maintains adaptively.

Choosing clustering columns follows a short set of rules with a genuine tension in the middle. Cluster on columns that appear in selective filters and join predicates. Choose enough distinct values for pruning to be meaningful, but few enough that rows sharing a value can actually be co-located in the same files.[52] Order matters — the leading column does the most work — and effectiveness falls off quickly with each additional column, so three or four is a practical ceiling.[46] And clustering is not free: maintaining it costs compute, and on a write-heavy table with poorly chosen keys that cost can exceed the query savings it produces.

The failure mode worth naming is layout by aspiration: a table clustered on six columns because six different teams each asked for one. The result is a table clustered on nothing in particular, paying continuous reclustering cost for no measurable pruning benefit. The remedy is empirical — read the query history, find the predicates that actually appear, cluster on those, and measure the depth afterwards.

CI/CD for data: what makes it different

The fourth practice is the one with the clearest external template and the least direct transfer. Continuous integration — every change integrated and verified frequently against a shared mainline — and continuous delivery — software kept in a releasable state through an automated pipeline of increasingly realistic verification — are well-documented disciplines with more than a decade of evidence behind them.[55,42] Multi-year research across tens of thousands of respondents established that the four delivery metrics — deployment frequency, lead time for changes, change failure rate, and time to restore service — predict organisational performance, and that throughput and stability rise together rather than trading off against each other.[56,57]

Applying this to data is not simply a matter of putting SQL in Git, because a data pipeline has a dimension that an application deployment does not: state. When you deploy version 4 of a service, version 3 stops existing. When you deploy version 4 of a transformation, the table it writes to still contains rows produced by versions 1 through 3. The deployment changes the future; it does not change the past unless you explicitly backfill. Four consequences follow.

There are two kinds of change, and they need different treatment. A change that only affects future rows can be deployed and left to take effect. A change that alters the meaning of existing rows requires a backfill, which is a data migration with its own risk profile — and which is only tractable if the pipeline is idempotent and partition-aligned. The reviewer's first question on any transformation change should be which of the two it is.

Tests have four distinct targets, not one. The test pyramid still applies — many fast, isolated tests underneath fewer slow, integrated ones[58] — but the layers mean something specific here:

  • Unit tests on logic. Given fixed input rows, the transformation produces expected output rows. No warehouse required; these run in seconds and should cover the edge cases that production data will eventually supply.
  • Schema and contract tests. The output has the expected columns, types and nullability, and upstream sources still supply what the model assumes. Schema drift in a source is one of the most common causes of silent production breakage, and detecting it at the boundary is far cheaper than debugging its effects.[59]
  • Data assertions. Properties that must hold of the data itself: primary keys unique, foreign keys resolvable, categorical columns within their permitted set, numeric ranges plausible, row counts within a tolerance of recent history, freshness within the stated SLA. This is the layer that formal work on production machine-learning data validation has developed furthest.[60,61]
  • Integration tests. The whole DAG runs end to end against a representative slice, in an isolated environment, and produces a table someone can inspect.

Environments must be cheap or they will not be used. This is where immutability pays for continuous integration directly. Zero-copy cloning — creating a writable table that shares the underlying immutable files with production until modified — makes a full-size test environment a metadata operation rather than a copy.[62] Without it, teams test against a 1% sample and discover the interesting failures in production.

Where ownership is federated across domain teams rather than centralised in a platform group, all of the above becomes a requirement rather than a preference: decentralised ownership without automated verification produces decentralised breakage.[63]

Infrastructure and orchestration are code too. Warehouses, roles, grants, schedules and cluster configurations should be declared in version control and applied by the same pipeline that deploys transformations, so that an environment can be reconstructed from the repository rather than from institutional memory.[64,65] Ad hoc grants applied in a console are the data platform's equivalent of a server configured by hand.

The delivery pipeline in practice

The concrete shape this takes has converged over the last few years to something that can be described in a single diagram.

The first two lanes are ordinary software practice applied to analytics code. Development happens on a branch, against a cloned environment. Pull requests trigger an automated build — and the key optimisation here is selective building. dbt's state comparison identifies the models modified relative to the last successful production run and builds only those and their downstream dependencies, deferring unmodified upstream models to the production environment rather than rebuilding them.[66,67] This is what makes per-pull-request verification affordable on a project with two thousand models; without it, CI costs more than production. Incremental models need one extra step, since a model that does not yet exist in the pull request's schema will otherwise build in full-refresh mode and mask the very bug the change might introduce — cloning the incremental models into the pull request schema first restores the correct behaviour.[62]

The third lane is the part with no direct application-development analogue, and it is the one worth investing in. Write-audit-publish is a three-stage commit for data: write the new data into an isolated branch or staging snapshot that consumers cannot see, run the full battery of quality checks against it at production volume, and only then publish — atomically — by fast-forwarding the production pointer. If the audit fails, the branch is discarded and production is untouched; no consumer ever observed the bad data.[68,36]

The pattern is old — staging tables before production loads are as old as warehousing — but its modern form is qualitatively different in two ways. Because branches share the underlying immutable data files, staging costs no additional storage and publishing is a metadata operation rather than a copy.[36] And because publication is atomic, there is no window in which consumers see a partially loaded table. It is, in effect, blue-green deployment applied to a dataset rather than a service,[69] and it inherits the same property: the rollback path is the same mechanism as the deployment path, so it is exercised constantly rather than rehearsed annually.

Two further practices complete the picture. Promotion by artefact — the same compiled project manifest moves from development to staging to production, rather than each environment building from source — ensures that what was tested is what runs.[42] And measurement: the four delivery metrics translate readably to data platforms, where change failure rate becomes the proportion of deployments that trigger a data incident, and time to restore becomes the interval between a bad number appearing on a dashboard and a corrected number replacing it.[56] Both are considerably easier to compute when every publish is a recorded snapshot transition and every rollback is a pointer swap.

A worked example: all four in 150 lines

The following program is a deliberately small demonstration that the four practices fit together without any infrastructure at all. It uses nothing outside the Python standard library. Data files are content-addressed and written once; table state is an append-only list of snapshots with a single mutable pointer per branch; loads are keyed by logical date and input digest and recorded in a ledger; rows are routed to partitions by event time; and every load goes through write, audit and publish, with a failed audit leaving the published pointer where it was.

It is a toy in exactly one respect — the target file size is four rows rather than half a gigabyte — and faithful in every other.

idempotent_wap.pypython 3.10+ · stdlib only
#!/usr/bin/env python3
"""
idempotent_wap.py - a dependency-free miniature of the four practices.

Implements, in about 150 lines and with nothing but the standard library:

  * IMMUTABILITY  - data files are content-addressed and never rewritten;
                    table state is an append-only log of snapshots.
  * IDEMPOTENCY   - a run is keyed by (table, logical_date, input_digest);
                    re-running it converges to the same snapshot.
  * LAYOUT        - rows are routed to partitions by *event* time, and small
                    files are compacted into larger ones on demand.
  * CI/CD         - every write goes through write -> audit -> publish, and a
                    failed audit leaves the published snapshot untouched.

Run:  python3 idempotent_wap.py
"""

from __future__ import annotations
import hashlib, json, os, shutil, tempfile
from collections import defaultdict
from dataclasses import dataclass, field, asdict

TARGET_FILE_ROWS = 4          # stand-in for "128 MB - 1 GB"
STORE = os.path.join(tempfile.gettempdir(), "wap_demo")


# --------------------------------------------------------------------- store
def digest(payload: bytes) -> str:
    return hashlib.sha256(payload).hexdigest()[:12]


def put_file(rows: list[dict]) -> tuple[str, int]:
    """Write an immutable, content-addressed data file. Returns (id, rowcount)."""
    body = json.dumps(rows, sort_keys=True, separators=(",", ":")).encode()
    fid = "f-" + digest(body)
    path = os.path.join(STORE, "data", fid + ".json")
    if not os.path.exists(path):                     # write-once, never rewrite
        os.makedirs(os.path.dirname(path), exist_ok=True)
        with open(path, "wb") as fh:
            fh.write(body)
    return fid, len(rows)


def read_file(fid: str) -> list[dict]:
    with open(os.path.join(STORE, "data", fid + ".json"), "rb") as fh:
        return json.load(fh)


# ----------------------------------------------------------------- snapshots
@dataclass
class Snapshot:
    version: int
    parent: int | None
    operation: str
    # partition value -> list of data-file ids
    manifest: dict[str, list[str]] = field(default_factory=dict)
    # idempotency ledger: run_key -> version that produced it
    applied: dict[str, int] = field(default_factory=dict)


class Table:
    """An append-only commit log with a single mutable pointer per branch."""

    def __init__(self) -> None:
        self.log: list[Snapshot] = [Snapshot(0, None, "CREATE")]
        self.branches: dict[str, int] = {"main": 0}

    def head(self, branch: str = "main") -> Snapshot:
        return self.log[self.branches[branch]]

    def commit(self, base: Snapshot, operation: str,
               manifest: dict, applied: dict) -> Snapshot:
        snap = Snapshot(len(self.log), base.version, operation,
                        manifest, applied)
        self.log.append(snap)                        # history only ever grows
        return snap

    def fast_forward(self, branch: str, snap: Snapshot) -> None:
        self.branches[branch] = snap.version         # the one atomic mutation

    def scan(self, version: int | None = None,
             partitions: list[str] | None = None) -> list[dict]:
        snap = self.log[version if version is not None else self.branches["main"]]
        out = []
        for part, fids in sorted(snap.manifest.items()):
            if partitions and part not in partitions:
                continue                             # <-- partition pruning
            for fid in fids:
                out.extend(read_file(fid))
        return out


# ------------------------------------------------------------------ the load
def run_key(logical_date: str, batch: list[dict]) -> str:
    payload = json.dumps(sorted(batch, key=lambda r: r["id"]),
                         sort_keys=True).encode()
    return f"{logical_date}:{digest(payload)}"


def load(tbl: Table, logical_date: str, batch: list[dict],
         checks) -> tuple[str, int]:
    """WRITE to a staging branch, AUDIT it, PUBLISH only if it passes."""
    base = tbl.head("main")
    key = run_key(logical_date, batch)

    if key in base.applied:                          # <-- idempotency ledger
        return "skipped (already applied)", base.version

    # --- WRITE ------------------------------------------------------------
    # Route by EVENT time, never by wall clock, so a rerun lands identically.
    by_part: dict[str, list[dict]] = defaultdict(list)
    for row in batch:
        by_part[row["event_ts"][:10]].append(row)

    manifest = {p: list(f) for p, f in base.manifest.items()}
    for part, rows in by_part.items():
        # Partition overwrite: the partition, not the row, is the unit of
        # replacement. This is what makes the whole run safely repeatable.
        rows = sorted(rows, key=lambda r: r["id"])
        files = []
        for i in range(0, len(rows), TARGET_FILE_ROWS):
            fid, _ = put_file(rows[i:i + TARGET_FILE_ROWS])
            files.append(fid)
        manifest[part] = files

    applied = dict(base.applied)
    applied[key] = len(tbl.log)
    staged = tbl.commit(base, f"LOAD {logical_date}", manifest, applied)
    tbl.fast_forward("audit", staged)

    # --- AUDIT ------------------------------------------------------------
    rows = tbl.scan(version=staged.version)
    failures = [name for name, fn in checks if not fn(rows)]
    if failures:
        # Publish never happens. The staged snapshot stays in the log as
        # evidence; main has not moved, so no consumer ever saw the data.
        return f"REJECTED by audit: {', '.join(failures)}", base.version

    # --- PUBLISH ----------------------------------------------------------
    tbl.fast_forward("main", staged)
    return "published", staged.version


def compact(tbl: Table) -> int:
    """Rewrite many small files into few large ones. Data unchanged."""
    base = tbl.head("main")
    manifest, before, after = {}, 0, 0
    for part, fids in base.manifest.items():
        rows = []
        for fid in fids:
            rows.extend(read_file(fid))
        before += len(fids)
        rows.sort(key=lambda r: (r["region"], r["id"]))   # <-- clustering
        files = [put_file(rows[i:i + TARGET_FILE_ROWS * 3])[0]
                 for i in range(0, len(rows), TARGET_FILE_ROWS * 3)]
        after += len(files)
        manifest[part] = files
    snap = tbl.commit(base, "OPTIMIZE", manifest, dict(base.applied))
    tbl.fast_forward("main", snap)
    return before - after


# ----------------------------------------------------------------- the demo
CHECKS = [
    ("unique_id", lambda rs: len({r["id"] for r in rs}) == len(rs)),
    ("no_null_region", lambda rs: all(r.get("region") for r in rs)),
    ("amount_in_range", lambda rs: all(0 <= r["amount"] <= 10_000 for r in rs)),
]


def batch(day: str, ids: range, region: str = "eu", bad: bool = False):
    return [{"id": i, "event_ts": f"{day}T0{i % 10}:15:00Z",
             "region": None if (bad and i == ids[0]) else region,
             "amount": 100 + i} for i in ids]


if __name__ == "__main__":
    shutil.rmtree(STORE, ignore_errors=True)
    tbl = Table()

    print("== day 1 ============================================")
    print(load(tbl, "2026-03-01", batch("2026-03-01", range(1, 8)), CHECKS))

    print("\n== day 1, run again (the 3 a.m. rerun) ==============")
    print(load(tbl, "2026-03-01", batch("2026-03-01", range(1, 8)), CHECKS))
    print("rows in table:", len(tbl.scan()), "  <- unchanged")

    print("\n== day 2, with a null region ========================")
    print(load(tbl, "2026-03-02", batch("2026-03-02", range(8, 14), bad=True), CHECKS))
    print("main is still at version", tbl.branches["main"],
          "and holds", len(tbl.scan()), "rows")

    print("\n== day 2, corrected =================================")
    print(load(tbl, "2026-03-02", batch("2026-03-02", range(8, 14), "us"), CHECKS))

    print("\n== backfill: day 1 restated with a corrected amount ==")
    fixed = batch("2026-03-01", range(1, 8))
    fixed[2]["amount"] = 9_999
    print(load(tbl, "2026-03-01", fixed, CHECKS))
    print("rows in table:", len(tbl.scan()), "  <- still no duplicates")

    print("\n== layout ===========================================")
    head = tbl.head()
    print("files per partition:",
          {p: len(f) for p, f in sorted(head.manifest.items())})
    print("files removed by compaction:", compact(tbl))
    print("files per partition:",
          {p: len(f) for p, f in sorted(tbl.head().manifest.items())})
    print("pruned scan (2026-03-02 only):",
          len(tbl.scan(partitions=["2026-03-02"])), "rows")

    print("\n== time travel ======================================")
    for v in (1, 4, tbl.branches["main"]):
        print(f"  version {v:>2}: {len(tbl.scan(version=v)):>2} rows "
              f"({tbl.log[v].operation})")

Running it produces the following:

Three things in that transcript are worth pointing at.

The rerun of day 1 is a no-op, because the idempotency key — logical date plus a digest of the sorted batch — is already in the ledger. But the backfill of day 1, in which one row's amount was corrected, is not a no-op: the digest differs, so the run proceeds and replaces the partition. The distinction between “the same work again” and “different work for the same period” falls out of the key construction rather than requiring a separate mechanism.

The failed audit on day 2 leaves main at version 1. The staged snapshot remains in the log — it is evidence, and inspecting it is how you debug the failure — but no reader following main ever saw it. This is the whole value of separating publication from writing.

And compaction produces a new snapshot rather than modifying the old one. The data is unchanged; only its physical arrangement differs; and the earlier snapshots still resolve correctly against the files they reference, which is why time travel to version 1 still returns seven rows after the layout has been rewritten twice.

Two observations about the shape of that table. First, the table-format row is doing disproportionate work: transactional formats are the substrate that makes idempotent partition overwrite, cheap branching, and zero-copy test environments possible at once, which is why the choice of table format is the highest-leverage decision on the list.[14,35] Second, there is no row for the practices themselves. No tool makes a pipeline idempotent. The tools remove the excuses.

How the four interlock

It is worth closing on the dependency structure, because the most common failure of adoption is not rejecting the practices but adopting one of them alone and concluding that the benefit was oversold.

Immutability makes idempotency verifiable. Without snapshots, “the rerun produced the same result” is an assertion; with them, it is a diff between two versions of the same table. Idempotency makes immutability affordable, because a table you can rebuild from raw data by rerunning does not need every intermediate version retained. Layout makes immutability survivable, because retaining a long history of a well-compacted table is a storage cost whereas retaining a long history of a table with four million small files is an operational one. And CI/CD is what converts all three from things a careful engineer does into properties the system enforces — a test that fails when a transformation stops being idempotent, an assertion that catches the schema drift, a deployment path that cannot skip the audit step.

The reverse dependencies are just as strong. Continuous integration for data is impractical without cheap full-size environments, which requires zero-copy clones, which requires an immutable storage layer.[62] Backfilling — the operation that makes a code fix meaningful for historical data — requires both idempotency and partition alignment, or it is a bespoke data migration every time. Write-audit-publish requires atomic publication, which is a property of the table format.[36]

Which returns us to the question at 3 a.m. A team that has all four can answer it in a sentence: yes, rerun it, and here is the snapshot diff afterwards showing what changed. A team that has none of them answers it with a meeting. The gap between those two responses is not primarily technical sophistication — the mechanisms in this article are, individually, simple, and the worked example fits on two screens. The gap is whether the properties were designed in at the start or are being retrofitted under pressure, which is the same thing that has always separated engineering from assembly.

Rerunnable, replayable, prunable, reviewable. Everything else in a data platform is a detail of implementation.
