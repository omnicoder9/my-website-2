1. Why inference needs a compiler

A trained neural network is, at heart, a dataflow graph of tensor operators: convolutions, matrix multiplications, normalizations, activations and reshapes. Frameworks such as PyTorch and TensorFlow execute that graph by calling one hand-written library kernel per operator. That approach is flexible, but it leaves performance on the table. Each kernel reads its inputs from and writes its outputs to device memory, the framework pays dispatch overhead for each call, and a vendor library can only ship kernels for the shapes, data types and operator combinations its authors anticipated.1

Deep-learning (DL) compilers treat the model as a program to be optimized as a whole. They lower it through a series of intermediate representations (IRs), apply transformations at each level, and generate code specialized for the target hardware, whether that is a CPU, GPU, mobile NPU or custom accelerator.1,3 For inference the payoff is especially large: the weights are fixed, the graph usually does not change between requests, and the compiled artifact can be reused millions of times, so even an expensive compile is quickly amortized.

Key idea. A DL compiler applies classical compiler ideas (IR design, dataflow analysis, loop transformation, instruction selection) to tensor programs. It adds domain knowledge that a general-purpose compiler such as LLVM does not have, for example that two operators can be fused or that a weight tensor is constant and can be pre-transformed.1,5

2. Anatomy of an ML compiler

Almost every DL compiler follows the same broad pipeline, described in the survey by Li et al.1 The frontend imports a model from a framework or an exchange format such as ONNX16 and builds a high-level (graph) IR. Hardware-independent optimizations happen there. The graph is then lowered to a low-level (tensor/loop) IR where hardware-specific scheduling happens, and finally the backend emits code, often through LLVM5 or a vendor toolchain.

Multi-level IRs and MLIR

Different optimizations need different levels of abstraction: fusion decisions are easy on a graph of named operators, while tiling and vectorization need explicit loops. Early compilers built bespoke IRs for each level. MLIR (Multi-Level Intermediate Representation) generalizes this by letting a compiler define many dialects that coexist in one IR and are progressively lowered into each other.4 Its linalg dialect, for instance, represents tensor computations as structured operations that can be tiled, fused and vectorized before being lowered to loops.34 IREE, OpenXLA's StableHLO tooling and Triton are all built on MLIR.7,12,17

3. A performance model: the roofline

To know which optimization matters, you need to know what limits a kernel. The roofline model of Williams, Waterman and Patterson bounds attainable performance by two ceilings: peak compute throughput and peak memory bandwidth multiplied by the kernel's arithmetic intensity (AI), the number of floating-point operations per byte moved to or from main memory.2

attainable FLOP/s = min( peak FLOP/s , bandwidth × AI )

Two lessons follow. First, elementwise operators such as ReLU or bias-add do roughly one FLOP per element loaded, so on modern accelerators they are memory-bound; the only way to make them faster is to move fewer bytes, which is exactly what fusion does. Second, large matrix multiplications are compute-bound, so the compiler must keep the arithmetic units busy through tiling, vectorization and use of tensor or matrix units.2,3

4. Graph-level optimizations

At the graph level the compiler sees whole operators and their dependencies. Common passes include:1,14

  • Constant folding. Subgraphs that depend only on constants (for example, a weight transpose or a shape computation) are evaluated once at compile time.
  • Dead-code and redundant-node elimination. Unused outputs, identity ops and duplicate subexpressions (common-subexpression elimination) are removed.
  • Algebraic simplification. Rewrites such as x * 1 → x, merging consecutive transposes or reshapes, and folding a batch normalization into the preceding convolution.
  • Operator fusion (Section 5) and layout transformation (Section 6).

Example: folding batch normalization into convolution

At inference time batch normalization uses fixed statistics, so it is an affine transform per output channel. It can be folded into the preceding convolution's weights and bias, eliminating an entire operator, as described for quantized inference by Jacob et al.:18

BN(conv(x)) = γ · (W∗x + b − μ) / √(σ² + ε) + β
            = (γ/√(σ²+ε) · W) ∗ x  +  (γ (b − μ)/√(σ²+ε) + β)
                \_____ W' _____/       \__________ b' __________/

ONNX Runtime's "basic" level performs fusions of this kind, for example Conv + BatchNorm and Conv + Add.14

Superoptimization of graphs

Instead of a hand-written list of rewrite rules, TASO automatically generates candidate graph substitutions, formally verifies them, and searches over their application with a cost model, finding rewrites that manual rule sets missed.21

5. Operator fusion

Fusion merges several operators into one kernel so that intermediate results stay in registers or on-chip memory instead of being written to and re-read from device memory. It also removes kernel-launch overhead. TVM's original paper groups operators into categories (injective, reduction, complex-out-fusable such as conv2d, and opaque) and fuses according to rules over those categories.3 XLA uses fusion as one of its central optimizations,6 and TorchInductor fuses pointwise and reduction operators into generated Triton kernels on GPUs.8

Kinds of fusion

  • Elementwise (loop) fusion: chains of pointwise ops become one loop nest.
  • Epilogue / prologue fusion: pointwise ops are folded into the output (or input) stage of a GEMM or convolution kernel.
  • Reduction fusion: e.g. a softmax or LayerNorm, whose reductions and pointwise steps are combined into a single kernel. ONNX Runtime's "extended" level includes fusions such as LayerNormalization, GELU and Attention.14
  • Algorithmic fusion: some patterns need a new algorithm, not just loop merging. FlashAttention fuses the whole attention computation and uses tiling with an online softmax so that the full N×N attention matrix is never written to GPU high-bandwidth memory.20

Fusion is not free. Fusing too aggressively can increase register pressure, reduce parallelism, or force recomputation. Production compilers use heuristics or cost models to decide what to fuse, and Halide made the tradeoff between parallelism, locality and recomputation an explicit part of its scheduling language.22

6. Data layout

The same 4-D activation tensor can be stored as NCHW (channels outer) or NHWC (channels inner), or in blocked layouts such as NCHWc, where channels are split into fixed-size blocks that match the hardware's vector width. The best layout depends on the operator and the target: vector units and matrix engines want the dimension they reduce over to be contiguous. Compilers therefore pick layouts per operator and insert (and later try to cancel) layout transforms between them.1,3 ONNX Runtime applies NCHWc layout optimizations for its CPU execution provider at its highest optimization level.14 Because weights are constant, their layout transform is done once at compile time and is free at run time.

7. Precision and quantization

Lower-precision arithmetic both reduces memory traffic and unlocks faster hardware units. Common inference formats are FP16 and BF16, 8-bit integers (INT8), FP8, and for large language model weights, 4-bit formats.

Affine (asymmetric) quantization

Jacob et al. define the widely used integer-only scheme that maps a real value r to an integer q with a scale S and zero point Z:18

r = S · (q − Z)   ⇔   q = clamp(round(r / S) + Z, qmin, qmax)

The zero point is chosen so that real zero is exactly representable, which matters for zero-padding. Matrix multiplications are then carried out with integer multiply-accumulate into 32-bit accumulators and rescaled afterwards.18

Where the compiler helps

  • Calibration and placement. Static (post-training) quantization runs representative data through the model to choose scales; dynamic quantization computes activation scales at run time. ONNX Runtime provides both, plus a QDQ (QuantizeLinear/DequantizeLinear) format that execution providers fuse into true integer kernels.15
  • Precision selection. TensorRT can be allowed to choose FP16, INT8 or FP8 per layer and picks the fastest kernels that satisfy the allowed precisions.13
  • FP8. Micikevicius et al. proposed two 8-bit floating-point encodings: E4M3 (4 exponent bits, 3 mantissa bits) for more precision and E5M2 (5 exponent, 2 mantissa) for more range.19
  • Mixed precision. FP16 has a narrow range compared with FP32, which is why sensitive operations (reductions, softmax, normalization) are often kept at higher precision.36

8. Loop-level scheduling

Once the graph is fixed, each (possibly fused) operator becomes a loop nest. The key insight, introduced by Halide for image processing, is to separate the algorithm (what is computed) from the schedule (how loops are ordered, tiled, parallelized and stored).22 TVM adopted this idea for deep learning and extended it with primitives for GPUs and accelerators, including tensorization (mapping an inner loop block to a hardware tensor instruction) and latency hiding.3 TensorIR later made the schedulable unit an explicit "block" to make tensorization more systematic.26

PrimitiveWhat it doesWhy it helps
split / tileBreak a loop into outer and inner loopsWorking set fits in cache, shared memory or registers
reorderChange loop nesting orderContiguous inner-loop access; better reuse
vectorizeMap inner loop to SIMD lanesUses AVX / NEON / SVE units
parallel / bindMap loops to CPU threads or GPU blocks and threadsUses all cores and SMs
unrollReplicate loop bodyExposes instruction-level parallelism
cache_read / cache_writeStage data in faster memoryReuse from shared memory or registers
compute_at / inlinePlace a producer inside its consumer's loopLoop-level fusion
tensorizeReplace a sub-block with an intrinsicUses tensor cores and matrix engines

Primitive names follow TVM's TensorIR scheduling API.26,33

An alternative to schedule languages is the polyhedral model, which represents loop nests as integer sets and finds legal transformations mathematically; Tensor Comprehensions applied it to deep-learning kernels.31 A third approach is tile-level programming: Triton lets the programmer write a kernel in terms of blocks of data, and the compiler handles intra-block details such as memory coalescing, shared-memory management and scheduling within the block.11

9. Auto-tuning

For a single matmul the space of legal schedules (tile sizes, loop orders, unroll factors, thread bindings) easily runs into billions of points, and the best choice depends on shapes and hardware. Instead of relying on hand-tuned heuristics, compilers search the space empirically.

  • AutoTVM searches within human-written schedule templates, guided by a statistical cost model trained on measurements (gradient-boosted trees and TreeGRU models were explored), and can transfer learning across workloads.23
  • Ansor removes the need for templates. It generates program "sketches" from a hierarchical search space, fills in details by random annotation, fine-tunes with evolutionary search and a learned cost model, and allocates tuning time across a network's subgraphs with a task scheduler. Its authors reported improvements of up to 3.8×, 2.6× and 1.7× over the prior state of the art on Intel CPU, ARM CPU and NVIDIA GPU respectively.24
  • MetaSchedule expresses search spaces as probabilistic programs over TensorIR scheduling primitives, unifying template-based and template-free tuning.25
  • Library-style selection. TensorRT times multiple candidate kernel implementations ("tactics") for each layer while building an engine and keeps the fastest.13 TorchInductor's max-autotune mode benchmarks Triton and template-based matmul configurations.9

10. Runtime-level tricks

  • Static memory planning. When tensor lifetimes are known at compile time, buffers can be assigned to a small arena with reuse, avoiding allocator calls on the hot path.1
  • Launch-overhead removal. CUDA Graphs record a sequence of kernel launches once and replay them as a single unit, reducing CPU launch overhead.29 torch.compile(mode="reduce-overhead") uses CUDA graphs for this purpose.9
  • Dynamic shapes. Batch size and sequence length often vary. Compilers either specialize and cache per shape, use symbolic shapes, or bucket shapes. TVM's Relax IR makes symbolic shapes first-class to compile dynamic workloads such as LLMs end-to-end.27 TorchDynamo can mark dimensions as dynamic and guard on shape properties.8
  • Heterogeneous partitioning. ONNX Runtime assigns subgraphs to "execution providers" (for example TensorRT, CUDA or CPU), falling back for unsupported operators.14

11. Tools in practice (with code)

Snippets were written against the documented APIs listed in the references. These projects evolve quickly; check the version you have installed.

11.1 PyTorch 2: torch.compile (TorchDynamo + TorchInductor)

PyTorch 2 introduced TorchDynamo, which captures graphs by intercepting Python bytecode just before execution using CPython's frame evaluation API (PEP 523), and TorchInductor, the default backend, which generates Triton kernels for GPUs and C++/OpenMP for CPUs.8,10 When Dynamo meets code it cannot trace, it inserts a graph break and falls back to Python for that part. In the PyTorch 2 paper, the authors report a 2.27× geometric-mean inference speedup and 1.41× training speedup on an NVIDIA A100 across more than 180 real-world models.8

import torch, torch.nn as nn

class MLP(nn.Module):
    def __init__(self, d=1024):
        super().__init__()
        self.fc1, self.fc2 = nn.Linear(d, 4*d), nn.Linear(4*d, d)
    def forward(self, x):
        return self.fc2(torch.nn.functional.gelu(self.fc1(x)))

model = MLP().cuda().half().eval()
x = torch.randn(64, 1024, device="cuda", dtype=torch.half)

# mode: "default" | "reduce-overhead" (CUDA graphs) | "max-autotune" | "max-autotune-no-cudagraphs"
compiled = torch.compile(model, mode="max-autotune", fullgraph=True)

with torch.inference_mode():
    y = compiled(x)   # first call compiles; later calls reuse the cached kernels

fullgraph=True turns any graph break into an error, which is useful for checking that the whole model is captured.9 Setting the environment variable TORCH_LOGS="output_code" prints the generated kernels so you can inspect the fused GELU epilogue.

11.2 Triton: writing a fused kernel by hand

Triton kernels are Python functions decorated with @triton.jit that operate on blocks of data. Below, bias-add and ReLU are fused into one pass over memory, adapted from the pattern in Triton's vector-add tutorial.11,12

import torch, triton, triton.language as tl

@triton.jit
def bias_relu_kernel(x_ptr, b_ptr, y_ptr, n_elem, n_col, BLOCK: tl.constexpr):
    pid  = tl.program_id(axis=0)                 # which block am I?
    offs = pid * BLOCK + tl.arange(0, BLOCK)       # element indices for this block
    mask = offs < n_elem                          # guard the ragged last block
    x = tl.load(x_ptr + offs, mask=mask)
    b = tl.load(b_ptr + offs % n_col, mask=mask)  # broadcast bias along rows
    tl.store(y_ptr + offs, tl.maximum(x + b, 0.0), mask=mask)

def bias_relu(x, b):
    y = torch.empty_like(x)
    n = x.numel()
    grid = lambda meta: (triton.cdiv(n, meta["BLOCK"]),)
    bias_relu_kernel[grid](x, b, y, n, x.shape[-1], BLOCK=1024)
    return y

One read of x, one write of y: half the device-memory traffic of running add and ReLU as separate kernels (Exercise 2).

11.3 JAX and XLA: seeing StableHLO

XLA (Accelerated Linear Algebra) is an open-source compiler for machine learning, developed under the OpenXLA project, that takes models from frameworks such as JAX, TensorFlow and PyTorch.6 Its portable input operation set is StableHLO.7 JAX's ahead-of-time API lets you inspect each stage.35

import jax, jax.numpy as jnp

def layer(x, w, b):
    return jax.nn.gelu(x @ w + b)

x = jnp.ones((8, 512)); w = jnp.ones((512, 512)); b = jnp.zeros((512,))

lowered  = jax.jit(layer).lower(x, w, b)
print(lowered.as_text())        # StableHLO: dot_general, add, ... before optimization
compiled = lowered.compile()
print(compiled.as_text())       # backend HLO after XLA passes: look for "fusion"

11.4 Apache TVM: a hand-written schedule in TensorIR

TVM is an end-to-end compiler that started at the University of Washington.3 Its current stack uses Relax for graphs and TensorIR for loop programs.26,27,33 This snippet defines a matmul with tensor expressions and applies the schedule primitives from Section 8 by hand; MetaSchedule can search for them automatically.25

import tvm
from tvm import te, tir

n = 1024
A = te.placeholder((n, n), name="A")
B = te.placeholder((n, n), name="B")
k = te.reduce_axis((0, n), name="k")
C = te.compute((n, n), lambda i, j: te.sum(A[i, k] * B[k, j], axis=k), name="C")

sch = tir.Schedule(te.create_prim_func([A, B, C]))
blk = sch.get_block("C")
i, j, kk = sch.get_loops(blk)
io, ii = sch.split(i, factors=[None, 32])     # tile rows
jo, ji = sch.split(j, factors=[None, 32])     # tile columns
sch.reorder(io, jo, kk, ii, ji)                 # j-inner loop is contiguous in B and C
sch.vectorize(ji)
sch.parallel(io)
lib = tvm.build(sch.mod, target="llvm")
print(sch.mod.script())                          # inspect the transformed TensorIR

11.5 ONNX Runtime: graph optimizations and quantization

ONNX Runtime applies graph optimizations when a session is created. The levels are basic, extended and layout optimizations, selected with GraphOptimizationLevel (ORT_DISABLE_ALL, ORT_ENABLE_BASIC, ORT_ENABLE_EXTENDED, ORT_ENABLE_ALL), and the optimized graph can be serialized for offline use.14

import onnxruntime as ort
from onnxruntime.quantization import quantize_dynamic, QuantType

# 1) Dynamic INT8 quantization of weights (activations quantized at run time)
quantize_dynamic("model.onnx", "model.int8.onnx", weight_type=QuantType.QInt8)

# 2) Graph optimization; save the optimized graph to look at it in Netron
so = ort.SessionOptions()
so.graph_optimization_level = ort.GraphOptimizationLevel.ORT_ENABLE_ALL
so.optimized_model_filepath = "model.int8.opt.onnx"
sess = ort.InferenceSession("model.int8.onnx", so, providers=["CPUExecutionProvider"])

Quantization API from the ONNX Runtime quantization guide.15

11.6 NVIDIA TensorRT: building an engine

TensorRT parses a network (typically from ONNX), applies layer and tensor fusion, chooses precisions, times candidate kernels for the target GPU, and serializes the result as an engine (plan) file that is specific to that GPU model and TensorRT version.13

# Command line
trtexec --onnx=model.onnx --fp16 --saveEngine=model.plan
import tensorrt as trt

logger  = trt.Logger(trt.Logger.WARNING)
builder = trt.Builder(logger)
network = builder.create_network(0)          # explicit batch is the default in TensorRT 10
parser  = trt.OnnxParser(network, logger)
with open("model.onnx", "rb") as f:
    assert parser.parse(f.read()), parser.get_error(0)

config = builder.create_builder_config()
config.set_flag(trt.BuilderFlag.FP16)                                 # allow FP16 kernels
config.set_memory_pool_limit(trt.MemoryPoolType.WORKSPACE, 1 << 30)  # 1 GiB scratch
plan = builder.build_serialized_network(network, config)              # fusion + tactic timing happen here
open("model.plan", "wb").write(plan)

11.7 MLIR and IREE

IREE (Intermediate Representation Execution Environment) is an MLIR-based end-to-end compiler and runtime that lowers ML models to a unified IR that scales from datacenter to mobile and edge deployments.17 A matmul in MLIR's linalg dialect looks like this:34

func.func @mm(%A: tensor<128x256xf32>, %B: tensor<256x64xf32>,
              %C: tensor<128x64xf32>) -> tensor<128x64xf32> {
  %0 = linalg.matmul ins(%A, %B : tensor<128x256xf32>, tensor<256x64xf32>)
                     outs(%C : tensor<128x64xf32>) -> tensor<128x64xf32>
  return %0 : tensor<128x64xf32>
}
# Compile for the host CPU and run with IREE's tools
iree-compile mm.mlir --iree-hal-target-backends=llvm-cpu -o mm.vmfb
iree-run-module --module=mm.vmfb --function=mm \
  --input=128x256xf32=1 --input=256x64xf32=1 --input=128x64xf32=0

Recent IREE releases also accept --iree-hal-target-device=local with a CPU backend flag; see the IREE getting-started guide for your version.17

13. Exercises with solutions

Exercise 1: Arithmetic intensity of GEMM versus GEMV

(a) Compute the FLOPs, the minimum bytes moved and the arithmetic intensity of an FP16 matrix multiplication with M = N = K = 4096. (b) Repeat for M = 1 (a matrix-vector product, as in single-token LLM decoding). (c) On a hypothetical accelerator with 100 TFLOP/s and 2 TB/s, which one is memory-bound?

Show solution

(a) FLOPs = 2MNK = 2 × 4096³ ≈ 1.374 × 10¹¹. Minimum bytes = 2 bytes × (MK + KN + MN) = 2 × 3 × 4096² ≈ 1.007 × 10⁸. AI ≈ 1365 FLOP/byte.

(b) FLOPs = 2NK ≈ 3.36 × 10⁷. Bytes ≈ 2 × (K + KN + N) ≈ 3.36 × 10⁷. AI ≈ 1 FLOP/byte.

(c) The ridge point is 100 × 10¹² / 2 × 10¹² = 50 FLOP/byte. The GEMM (1365) is compute-bound; the GEMV (≈1) is heavily memory-bound and can reach at most about 2 TFLOP/s. This is why weight quantization and batching help LLM decoding so much: they reduce bytes per useful FLOP.2

Exercise 2: Bytes saved by fusion

A model computes y = relu(x + b) on N = 16 777 216 FP32 elements, as two separate kernels (add, then ReLU). Ignoring the small bias vector, how many bytes of device memory traffic does each version need, and what is the saving from fusion?

Show solution

Unfused: add reads x and writes t (2 × 4N bytes); ReLU reads t and writes y (2 × 4N bytes). Total 16N = 268 MB.

Fused: read x, write y. Total 8N = 134 MB. Fusion halves the traffic, so a memory-bound kernel runs roughly twice as fast and launches once instead of twice.3

Exercise 3: Affine quantization by hand

Quantize the real range [−1.0, 3.0] to UINT8 (0–255) using r = S(q − Z). Find S and Z, quantize r = 1.5, dequantize it back, and give the error.

Show solution

S = (3.0 − (−1.0)) / 255 = 4/255 ≈ 0.015686. Z = round(0 − rmin/S) = round(63.75) = 64.

q = round(1.5 / S) + Z = round(95.625) + 64 = 96 + 64 = 160.

r̂ = S(160 − 64) = 96 × 0.015686 ≈ 1.5059. Error ≈ 0.0059, within the maximum rounding error of S/2 ≈ 0.0078.18

Exercise 4: Fold a batch norm

A convolution output channel has bias b. The following BatchNorm has γ = 2, β = 0.5, μ = 1, σ² = 3, ε = 1. Give the folded weight scale and bias.

Show solution

Scale = γ / √(σ² + ε) = 2 / √4 = 1, so W' = W. Bias b' = (b − μ) × scale + β = (b − 1) + 0.5 = b − 0.5. The BatchNorm node disappears entirely.18

Exercise 5: Pick a tile size

A GPU matmul kernel stages one T × T tile of A and one T × T tile of B in 48 KiB of shared memory, in FP32. What is the largest power-of-two T that fits? Why might a tuner still pick a smaller one?

Show solution

2 × T² × 4 bytes ≤ 49 152 ⇒ T² ≤ 6144 ⇒ T ≤ 78. The largest power of two is T = 64 (32 KiB). A tuner may choose smaller or rectangular tiles because using less shared memory allows more thread blocks per SM (higher occupancy), and register pressure, double buffering and the problem shape all change the optimum. This is why measurement-driven tuning beats a single formula.23,24

Exercise 6: Find the graph break

@torch.compile(fullgraph=True)
def f(x):
    if x.sum() > 0:
        return x * 2
    return x - 1

Why does this fail with fullgraph=True, and how can you rewrite it?

Show solution

The branch depends on a tensor's value, which is unknown at trace time, so Dynamo must break the graph; with fullgraph=True that becomes an error.8,9 Rewrite it as data flow, which computes both sides and selects:

return torch.where(x.sum() > 0, x * 2, x - 1)

or use the control-flow operator torch.cond(pred, true_fn, false_fn, (x,)), which captures both branches in the graph.37

Exercise 7 (hands-on): Measure fusion yourself

Time the MLP from Section 11.1 eagerly and under torch.compile for batch sizes 1, 8 and 256, using torch.cuda.synchronize() around the timed region and discarding the first (compiling) call. Then rerun with mode="reduce-overhead". Explain the pattern.

Show expected findings

At small batch sizes the work per kernel is tiny, so launch and Python overhead dominate; reduce-overhead (CUDA graphs) tends to help most there.9,29 At large batch sizes the GEMMs dominate and are already compute-bound in vendor libraries, so the gains come mainly from fusing the GELU into the matmul epilogue and are more modest. Exact numbers depend on your GPU and versions, which is the point of measuring.

14. Trivia with answers

1. What does XLA stand for?

Accelerated Linear Algebra.6

2. What does MLIR stand for, and at which conference was its paper published?

Multi-Level Intermediate Representation; the paper appeared at CGO 2021 (IEEE/ACM International Symposium on Code Generation and Optimization).4

3. What does IREE stand for?

Intermediate Representation Execution Environment.17

4. Which image-processing language introduced the "algorithm versus schedule" split that TVM borrowed?

Halide (PLDI 2013).22,3

5. Which Python Enhancement Proposal makes TorchDynamo possible?

PEP 523, which added a frame evaluation API to CPython.10,8

6. How many 8-bit multiply-accumulate units are in the first-generation Google TPU's matrix unit?

65 536, arranged as a 256 × 256 systolic array.28

7. In FP8 E4M3, what do the 4 and 3 refer to?

4 exponent bits and 3 mantissa bits (plus a sign bit). E5M2 trades a mantissa bit for an extra exponent bit.19

8. At which workshop was the original Triton paper presented?

MAPL 2019, the ACM SIGPLAN International Workshop on Machine Learning and Programming Languages, co-located with PLDI.11

9. What is the default backend of torch.compile?

"inductor" (TorchInductor).9

10. Which TVM auto-scheduler generates programs from "sketches" without manual templates?

Ansor (OSDI 2020).24

11. Does FlashAttention compute an approximation of attention?

No. It computes exact attention; the speedup comes from IO-awareness (tiling and recomputation that reduce reads and writes to GPU high-bandwidth memory).20

12. What three ingredients define the roofline model?

Peak floating-point performance, peak memory bandwidth, and the kernel's operational (arithmetic) intensity.2

15. Glossary

Arithmetic intensityFLOPs performed per byte of main-memory traffic.2
Dialect (MLIR)A namespace of operations, types and attributes at one abstraction level.4
Execution providerONNX Runtime's plug-in interface to a hardware backend.14
Graph breakA point where TorchDynamo stops capturing and falls back to Python.8
GuardA runtime check that a cached compiled graph is still valid for the current inputs.8
ScheduleThe mapping of a computation to loops, memory and parallel hardware.22
TacticOne candidate kernel implementation timed by TensorRT for a layer.13
TensorizationReplacing a loop sub-nest with a hardware tensor instruction.3,26
Zero pointThe integer that represents real 0 in affine quantization.18
