1What is auto-tuning?

Auto-tuning (also autotuning, iterative compilation or empirical optimisation) is the automatic search for the values of performance-relevant parameters of a program, a library or a compiler, by generating candidate variants and evaluating them, usually by running them on the target machine1,2. Instead of trusting one fixed heuristic, the tool treats "which variant is fastest?" as an optimisation problem and solves it with search, measurement and, increasingly, machine learning3,2.

The things being tuned vary widely. Library generators tune block sizes and unroll depths for dense linear algebra4,5 and pick factorisations for fast Fourier transforms6,7. Compiler auto-tuners choose which optimisation flags to enable and in what order to run passes8,2. Tensor and image-processing compilers search over schedules (tilings, loop orders, vectorisation and parallelisation choices) for each kernel9,10,11. GPU auto-tuners pick thread-block shapes, work per thread and pipeline depths12,13,14.

One-sentence definition. An auto-tuner closes the loop between code generation and measurement: it proposes a configuration, builds the corresponding program, measures it, and uses that feedback to propose better configurations15,1.

2Why compilers cannot just "know"

Optimising compilers make thousands of decisions using hand-written heuristics and analytical cost models. These are tuned by compiler developers for "typical" code on "typical" hardware, and they are necessarily approximate3,16. Three facts make exact prediction hard:

  • Hardware is complex and diverse. Performance depends on cache sizes and associativity, prefetchers, TLBs, vector widths, out-of-order windows and memory bandwidth, and these differ between processor generations. This was the original motivation for PHiPAC and ATLAS, which generate many variants of matrix multiply at install time instead of shipping one hand-tuned version per processor4,17.
  • Optimisations interact. One transformation can enable or destroy the opportunity for another, so the order in which passes run matters. In general, the phase-ordering problem has been shown to be undecidable when sequences are unbounded18, and even practical exhaustive exploration of phase orders is expensive19.
  • The landscape is rugged. Runtime as a function of tile sizes or unroll factors is non-smooth and has many local minima, which is why early iterative-compilation work described the space as a "non-linear optimisation space"20,21.

The payoff from getting these decisions right is large. Leiserson et al. took a 4096×4096 matrix multiply from a naive Python program to a parallel, cache-blocked, vectorised C version using AVX intrinsics and measured a 62,806× speedup, yet the final version still reached only about 41% of the machine's peak22. Much of that path consists of choosing parameters, such as block sizes, that an auto-tuner can search for.

3Anatomy of an auto-tuner

Almost every auto-tuner, from ATLAS to TVM, has the same four parts1,15,10:

  1. A parameterised program or code generator that turns a configuration into concrete code (for example, C with -DTILE=32, a Halide schedule, or a Triton kernel with a given BLOCK_SIZE).
  2. A search space: the parameters, their legal values and the constraints between them.
  3. A search strategy that decides which configuration to try next, possibly guided by a cost model.
  4. An evaluator that compiles, runs and measures, then feeds the result back and records the best configuration found.

Example: loop tiling

Tiling (blocking) splits an iteration space into blocks so that the data a block touches stays in cache while it is reused. Wolf and Lam formalised tiling as a data-locality transformation29, and high-performance GEMM implementations block for each level of the memory hierarchy30. The best tile size depends on cache capacities, the data layout and the rest of the generated code, which is why it is a classic auto-tuning target21,31.

How big is the space?

Spaces grow combinatorially. The GCC manual documents hundreds of optimisation options and tunable --param values26; in the GCC 13.3 build used for this article, gcc --help=optimizers listed 260 -f options and gcc --help=params listed 283 parameters. Treating just the 260 options as on/off switches gives 2260 ≈ 1.9×1078 combinations. Phase ordering is worse, because sequences can repeat passes and vary in length18,19. Tensor compilers face spaces of "billions of possible program variants" for a single operator23. Exhaustive search is therefore possible only for tiny sub-spaces, and the main design question is how to search cleverly.

Constraints matter. Many configurations are invalid: a GPU block can exceed the hardware's thread limit, a tile can exceed shared memory, or a pass sequence can crash the compiler. Good tuners let you declare restrictions (Kernel Tuner and CLTune both support constraints on parameter combinations13,12) or treat failures as infinitely slow (OpenTuner reports them as an error state15).

5Search strategies

No single search algorithm is best on every problem; the "no free lunch" theorems show that, averaged over all possible objective functions, all black-box optimisers perform equally32. In practice auto-tuning spaces have structure, and the following strategies are used most:

StrategyIdeaUsed by (examples)
Exhaustive / gridTry every point of a (coarsened) gridSmall spaces; ATLAS searches its parameters largely one at a time over bounded ranges (an orthogonal line search)17,31

Hill climbing / local searchMove to a better neighbour until none exists; restart randomlyKernel Tuner strategies; OpenTuner techniques13,15
Simulated annealingAccept worse moves with probability e−Δ/T, cooling T over time34AutoTVM's explorer over its cost model23
Genetic / evolutionary algorithmsMutate and recombine a population of configurations35Pass sequences for code size8; Ansor's evolutionary search11

Bayesian optimisationFit a probabilistic surrogate model and pick the next point by an acquisition function36SMAC37, BaCO38, Optuna-style tuners39
Learned cost model + searchTrain a model to predict performance, search the model, measure only the top candidatesAutoTVM, Ansor, Halide autoscheduler23,11,24

Bergstra and Bengio explain why random search often beats grid search: when only a few parameters really matter (low effective dimensionality), a grid wastes most of its trials repeating the same values of the important parameters, whereas random samples try a new value each time33.

6Empirical, model-driven and learned

There are three ways to decide which variant is fastest:

  • Empirical search measures real runs. ATLAS, PHiPAC and FFTW popularised this approach17,4,6. It is accurate on the machine where it runs but costs time.
  • Model-driven optimisation computes parameters from an analytical model of the hardware, such as choosing a tile so that the working set fits in cache. Yotov et al. replaced ATLAS's empirical search with a model and found that the model-driven code generator could produce code with performance comparable to the empirically tuned one31. Mullapudi et al.'s original Halide autoscheduler likewise used an analytical approach41.
  • Learned cost models sit in between. They are trained on measurements and then used to rank many candidates cheaply. AutoTVM learns statistical cost models over "billions of possible program variants"23; Ansor samples programs from a hierarchical search space and fine-tunes them with evolutionary search and a learned cost model11; Adams et al. combine tree search with a cost model trained on randomly generated Halide programs24. Earlier, Stephenson et al. used genetic programming to evolve compiler heuristics16, Agakov et al. used models to focus iterative search42, and Cummins et al. learned heuristics directly from source code with deep learning43.

7Measuring performance honestly

An auto-tuner is only as good as its measurements. If noise is larger than the difference between two configurations, the search ends up optimising noise. Mytkowicz et al. showed that seemingly harmless details, such as the size of the UNIX environment or the link order of object files, can bias measurements enough to reverse conclusions about an optimisation44. Hoefler and Belli give rules for reporting parallel performance, including reporting the variation across repeated runs and using appropriate summary statistics40.

Practical rules used by real tuners:

  • Repeat each measurement and summarise with a robust statistic such as the median or minimum; Kernel Tuner, for example, runs each configuration several times by default and reports the average13.
  • Warm up caches, JITs and GPU clocks before timing. FFTW's FFTW_MEASURE mode actually runs candidate plans, and the manual warns that it overwrites the input and output arrays during planning45.
  • Check correctness for each variant: a fast wrong answer is worthless. CLTune can verify each kernel's output against a reference12.
  • Tune on representative inputs. OSKI chooses sparse register-block sizes at run time because the best choice depends on the specific matrix46.
  • Cap runaway candidates with a time limit. OpenTuner passes a limit to every run so that very slow configurations can be cut off15.

8When does tuning happen?

The trade-off is between tuning cost and specialisation. ATLAS pays its search cost once when the library is installed17. FFTW pays it when a plan is created; it offers flags ranging from FFTW_ESTIMATE (no measurement, a heuristic plan) through FFTW_MEASURE and FFTW_PATIENT to FFTW_EXHAUSTIVE, and the result can be saved and reloaded as wisdom45,50. PyTorch's torch.backends.cudnn.benchmark makes cuDNN benchmark several convolution algorithms and select the fastest47.

9Systems tour

9.1 Self-tuning libraries

PHiPAC (Portable High Performance ANSI C, 1997) introduced a methodology for writing portable C matrix-multiply code generators whose parameters are searched on each machine4. ATLAS (Automatically Tuned Linear Algebra Software) applied "automated empirical optimisation of software" to the BLAS5,17. FFTW composes FFT algorithms from codelets generated by a special-purpose compiler, genfft, and a planner measures alternatives at run time6,51,27. SPIRAL represents signal-processing transforms as formulas, rewrites them into many alternative algorithms, and searches among them7. OSKI tunes sparse matrix kernels to the matrix it is given46. Auto-tuning was also applied to stencil codes on multicore processors52.

9.2 Flag selection and phase ordering

Cooper, Schielke and Subramanian used a genetic algorithm to find optimisation sequences that reduce code size8. Bodin, Kisuki, Knijnenburg, O'Boyle and Rohou studied iterative compilation in a non-linear optimisation space20, and Kisuki et al. searched tile sizes and unroll factors together21. Milepost GCC extracted program features inside GCC and used machine learning to predict good optimisations for new programs, so that less search was needed53. Ashouri et al. survey this area and divide it into the optimisation selection problem and the phase-ordering problem2.

9.3 General-purpose tuning frameworks

OpenTuner provides a Python framework where users define a search space and a run method; it then runs an ensemble of search techniques coordinated by an AUC Bandit meta-technique. Its authors evaluated it on seven projects, including GCC/G++ flags, Halide, HPL and PetaBricks, and reported speedups of up to 2.8× over those projects' prior techniques15. Active Harmony combined with the CHiLL loop-transformation framework tuned compiler transformation parameters at scale25. BaCO uses Bayesian optimisation specialised for compiler parameter types such as permutations, ordinals and categoricals, with known constraints38.

9.4 DSL and tensor compilers

Halide separates an image-processing algorithm from its schedule (how loops are split, ordered, vectorised, parallelised and fused), and its original paper already used stochastic search to find schedules9. Later autoschedulers used analytic heuristics41 and then learned cost models with tree search24. TVM brought the same idea to deep learning10: AutoTVM tunes templates written by developers with learned cost models23; Ansor generates the search space automatically and reported up to 3.8×, 2.6× and 1.7× speedups over the state of the art on Intel CPUs, ARM CPUs and NVIDIA GPUs11; MetaSchedule unifies these approaches as probabilistic programs54.

9.5 GPU kernels

CLTune tunes OpenCL kernels12 and Kernel Tuner tunes CUDA, OpenCL and C kernels from Python, with many search strategies13. Triton, a language and compiler for tiled GPU kernels55, has a built-in @triton.autotune decorator that benchmarks a list of configurations and re-tunes whenever the values of selected arguments change14. PyTorch's torch.compile has a "max-autotune" mode that, according to its documentation, leverages Triton- or template-based matrix multiplications on supported devices and Triton-based convolutions on GPU, at the price of longer compilation56.

9.6 Learning the compiler's own heuristics

A newer direction trains models that replace heuristics inside a production compiler. MLGO replaced LLVM's inlining-for-size heuristic with learned models and reported up to 7% size reduction compared with LLVM -Oz49; its training infrastructure is open source57. CompilerGym exposes compiler optimisation problems, such as LLVM phase ordering, as reinforcement-learning environments58.

10Worked example: tuning a tiled matrix multiply

This example is small enough to run on a laptop but has the same structure as real tuners. The C kernel takes its tile sizes as preprocessor macros, so every configuration is a separate compilation.

mm.c
/* mm.c - tiled matrix multiply; tile sizes are compile-time parameters */
#include <stdio.h>
#include <stdlib.h>
#include <time.h>
#ifndef N
#define N 512
#endif
#ifndef TI
#define TI 32
#endif
#ifndef TJ
#define TJ 32
#endif
#ifndef TK
#define TK 32
#endif
#define MIN(a,b) ((a)<(b)?(a):(b))
static double A[N][N], B[N][N], C[N][N];

int main(void) {
  for (int i = 0; i < N; i++)
    for (int j = 0; j < N; j++) { A[i][j] = (i + j) % 7; B[i][j] = (i * j) % 5; }
  struct timespec t0, t1;
  clock_gettime(CLOCK_MONOTONIC, &t0);
  for (int ii = 0; ii < N; ii += TI)
    for (int kk = 0; kk < N; kk += TK)
      for (int jj = 0; jj < N; jj += TJ)
        for (int i = ii; i < MIN(ii + TI, N); i++)
          for (int k = kk; k < MIN(kk + TK, N); k++) {
            double a = A[i][k];
            for (int j = jj; j < MIN(jj + TJ, N); j++)
              C[i][j] += a * B[k][j];
          }
  clock_gettime(CLOCK_MONOTONIC, &t1);
  double s = (t1.tv_sec - t0.tv_sec) + 1e-9 * (t1.tv_nsec - t0.tv_nsec);
  printf("%.6f %g\n", s, C[N/2][N/3]);   /* print a result so work is not removed */
  return 0;
}

The tuner uses a two-phase strategy common in practice: global random sampling to find a good region33, then hill climbing on neighbouring configurations13. It caches results so no configuration is measured twice, and it uses the median of three runs to resist noise40.

tune.py
"""tune.py - a minimal empirical auto-tuner: random search, then hill climbing.
Usage: python3 tune.py [budget]"""
import random, subprocess, sys, statistics, os, tempfile

SPACE = {                       # the search space: parameter -> legal values
    "TI":  [4, 8, 16, 32, 64, 128, 256, 512],
    "TJ":  [8, 16, 32, 64, 128, 256, 512],
    "TK":  [4, 8, 16, 32, 64, 128, 256, 512],
    "OPT": ["-O2", "-O3"],
    "UNROLL": ["", "-funroll-loops"],
}
CACHE = {}                      # memoise: never measure a configuration twice
TMP = tempfile.mkdtemp()

def measure(cfg, reps=3):
    """Compile with the configuration, run it `reps` times, return the median time."""
    key = tuple(sorted(cfg.items()))
    if key in CACHE:
        return CACHE[key]
    exe = os.path.join(TMP, "mm")
    cmd = ["gcc", cfg["OPT"], "-march=native", f"-DTI={cfg['TI']}", f"-DTJ={cfg['TJ']}",
           f"-DTK={cfg['TK']}", "-DN=1024", "mm.c", "-o", exe] + ([cfg["UNROLL"]] if cfg["UNROLL"] else [])
    subprocess.run(cmd, check=True)
    times = [float(subprocess.run([exe], capture_output=True, text=True).stdout.split()[0])
             for _ in range(reps)]
    CACHE[key] = statistics.median(times)     # median resists outliers from noise
    return CACHE[key]

def random_cfg():
    return {p: random.choice(v) for p, v in SPACE.items()}

def neighbours(cfg):
    """Configurations that differ in one parameter by one step."""
    for p, vals in SPACE.items():
        i = vals.index(cfg[p])
        for j in (i - 1, i + 1):
            if 0 <= j < len(vals):
                yield {**cfg, p: vals[j]}

def tune(budget=40, seed=1):
    random.seed(seed)
    best = {"TI": 512, "TJ": 512, "TK": 512, "OPT": "-O2", "UNROLL": ""}  # untiled baseline
    base = best_t = measure(best)
    print(f"baseline (untiled, -O2): {base:.4f} s")
    for _ in range(budget // 2):                       # phase 1: global random sampling
        c = random_cfg(); t = measure(c)
        if t < best_t: best, best_t = c, t
    improved = True
    while improved and len(CACHE) < budget:            # phase 2: local hill climbing
        improved = False
        for c in neighbours(best):
            t = measure(c)
            if t < best_t:
                best, best_t, improved = c, t, True
                break
    print(f"evaluated {len(CACHE)} configurations")
    print(f"best: {best}  {best_t:.4f} s  speedup {base / best_t:.2f}x")

if __name__ == "__main__":
    tune(int(sys.argv[1]) if len(sys.argv) > 1 else 40)

Output of python3 tune.py 40 on the 4-core cloud container used to write this article (GCC 13.3, N = 1024):

$ python3 tune.py 40
baseline (untiled, -O2): 0.3373 s
evaluated 28 configurations
best: {'TI': 8, 'TJ': 512, 'TK': 16, 'OPT': '-O3', 'UNROLL': '-funroll-loops'}  0.1215 s  speedup 2.78x

Three points are worth noticing. First, the best configuration is not the "obvious" square tile: it uses a narrow TI with a long TJ, which keeps the inner j loop long enough to vectorise well. Second, the tuner also enabled -funroll-loops, showing that flags and loop parameters interact21. Third, the result is specific to this machine, compiler and problem size; you should expect a different winner on your hardware, which is the reason auto-tuning exists17.

OpenTuner: the same matrix multiply, with a framework

import opentuner
from opentuner import ConfigurationManipulator, IntegerParameter, EnumParameter
from opentuner import MeasurementInterface, Result

class MatMulTuner(MeasurementInterface):
    def manipulator(self):
        m = ConfigurationManipulator()
        for p in ("TI", "TJ", "TK"):
            m.add_parameter(IntegerParameter(p, 4, 512))
        m.add_parameter(EnumParameter("OPT", ["-O2", "-O3"]))
        return m

    def run(self, desired_result, input, limit):
        cfg = desired_result.configuration.data
        build = self.call_program(
            "gcc {OPT} -march=native -DN=1024 -DTI={TI} -DTJ={TJ} -DTK={TK} mm.c -o ./mm".format(**cfg))
        if build["returncode"] != 0:
            return Result(state="ERROR", time=float("inf"))
        return Result(time=self.call_program("./mm")["time"])

if __name__ == "__main__":
    MatMulTuner.main(opentuner.default_argparser().parse_args())

OpenTuner chooses among its search techniques automatically and stores results in a database15,59. Run it with, for example, python3 mmtuner.py --test-limit=200.

Kernel Tuner: GPU thread-block size

import numpy as np
import kernel_tuner

kernel_string = """
__global__ void vector_add(float *c, float *a, float *b, int n) {
    int i = blockIdx.x * block_size_x + threadIdx.x;
    if (i < n) c[i] = a[i] + b[i];
}"""
n = np.int32(10_000_000)
a = np.random.randn(n).astype(np.float32)
b = np.random.randn(n).astype(np.float32)
c = np.zeros_like(b)
tune_params = {"block_size_x": [32, 64, 128, 256, 512, 1024]}
results, env = kernel_tuner.tune_kernel("vector_add", kernel_string, n, [c, a, b, n], tune_params)

Kernel Tuner inserts each value of block_size_x into the kernel as a compile-time constant, launches it, and records the time13.

Triton: autotuning inside the kernel definition

import triton, triton.language as tl

@triton.autotune(
    configs=[triton.Config({"BLOCK_SIZE": 128},  num_warps=4),
             triton.Config({"BLOCK_SIZE": 1024}, num_warps=8)],
    key=["n_elements"],          # re-tune when this argument's value changes
)
@triton.jit
def add_kernel(x_ptr, y_ptr, out_ptr, n_elements, BLOCK_SIZE: tl.constexpr):
    pid  = tl.program_id(axis=0)
    offs = pid * BLOCK_SIZE + tl.arange(0, BLOCK_SIZE)
    mask = offs < n_elements
    x = tl.load(x_ptr + offs, mask=mask)
    y = tl.load(y_ptr + offs, mask=mask)
    tl.store(out_ptr + offs, x + y, mask=mask)

The decorator benchmarks every configuration the first time it sees a new value of the key arguments and caches the winner14.

12Auto-tuning versus profile-guided optimisation

Profile-guided optimisation (PGO) also uses runtime feedback, but in a different way. With PGO the program is built with instrumentation (GCC -fprofile-generate, then -fprofile-use; Clang has equivalent options), run on training inputs, and rebuilt with the recorded execution counts to guide inlining, layout and branch decisions26,60. AutoFDO collects profiles with hardware sampling in production instead of instrumentation48.

They are complementary: one can auto-tune the flags of a PGO build.

13Hard problems

  • Search cost. Each evaluation costs a compile plus several runs. Learned cost models and transfer learning across tasks reduce the number of real measurements23,11.
  • Noise and bias. Measurements can be biased by factors unrelated to the configuration44, and small differences need many repetitions to be trusted40.
  • Input sensitivity. The best configuration can change with problem size or input structure, which is why OSKI tunes at run time and Triton re-tunes when its key arguments change46,14.
  • Portability. Results tuned on one machine may not carry over to another; libraries such as ATLAS therefore re-tune on each installation17.
  • Huge, structured spaces. Phase ordering is undecidable in general18, and schedule spaces are trees of dependent decisions rather than flat vectors11,54.
  • Generalisation of learned heuristics. Models trained on one set of programs must generalise to unseen code; this is a central theme of the ML-in-compilers literature3,2.

14A short history

The roots of the idea are older than compilers that tune themselves. Rice's 1976 "algorithm selection problem" framed the choice of the best algorithm for a given input as a problem in its own right28. The late 1990s brought the first widely used self-tuning libraries (PHiPAC, ATLAS, FFTW)4,5,6 and the first iterative-compilation studies20,8. The 2000s added machine learning to cut search time42,53, and the 2010s generalised tuning into frameworks and DSL compilers15,9,10. Today auto-tuning is built into everyday ML stacks through Triton and PyTorch14,56, and learned models are replacing heuristics inside LLVM49.

How many configurations does the SPACE in tune.py contain? If one evaluation (compile plus three runs) takes about 0.6 s, how long would exhaustive search take?

Show solution

TI has 8 values, TJ 7, TK 8, OPT 2 and UNROLL 2, so 8 × 7 × 8 × 2 × 2 = 1,792 configurations. At 0.6 s each that is about 1,075 s, or roughly 18 minutes. That is feasible, but adding just one more 8-valued parameter makes it about 2.4 hours, which shows why spaces explode1.

Exercise 2 · Flags and pass orders Counting

(a) How many on/off combinations do 260 independent flags give? (b) How many pass sequences of length 10 can be formed from 50 passes if passes may repeat?

Show solution

(a) 2260 ≈ 1.85 × 1078. (b) 5010 ≈ 9.8 × 1016. Neither can be enumerated, which is why flag selection and phase ordering use heuristic search or learned models2,19.

Exercise 3 · Why random search works Probability

How many uniform random samples do you need so that, with probability at least 95%, at least one lands in the best 5% of the space?

Show solution

The probability that all n samples miss the top 5% is 0.95ⁿ. We need 1 − 0.95ⁿ ≥ 0.95, so n ≥ ln 0.05 / ln 0.95 ≈ 58.4, giving 59 samples, regardless of how large the space is. This size-independence is part of the argument for random search as a strong baseline33.

Exercise 4 · A model-driven tile size Modelling

Choose a square tile size T (a power of two) so that three T×T tiles of 8-byte doubles fit in a 32 KiB L1 data cache.

Show solution

3 · T² · 8 ≤ 32,768 gives T ≤ 36.9, so T = 32 (24 KiB). This is the kind of reasoning a model-driven optimiser uses31,29. Compare with the tuned result in section 10, which preferred rectangular tiles: real performance also depends on vectorisation, associativity conflicts and prefetching, which a simple capacity model ignores.

Exercise 5 · How many repetitions? Statistics

Two configurations differ by 2% in true mean runtime. Each run has a coefficient of variation of 3%. Roughly how many runs of each do you need before the difference of means is about two standard errors?

Show solution

The standard error of a difference of two means of n runs each is σ√(2/n) with σ = 3%. We want 2 · 3% · √(2/n) ≤ 2%, so √(2/n) ≤ 1/3 and n ≥ 18. Noise of this size forces many repetitions, and bias (which repetition cannot remove) is a separate problem40,44.

Exercise 6 · Add simulated annealing Coding

Replace the hill-climbing phase in tune.py with simulated annealing.

Show solution 
import math

def anneal(start, budget, t0=0.2, alpha=0.9):
    cur, cur_t = start, measure(start)
    best, best_t, temp = cur, cur_t, t0
    while len(CACHE) < budget:
        cand = random.choice(list(neighbours(cur)))
        t = measure(cand)
        delta = (t - cur_t) / cur_t                 # relative slowdown
        if delta < 0 or random.random() < math.exp(-delta / temp):
            cur, cur_t = cand, t                    # accept, sometimes uphill
        if t < best_t:
            best, best_t = cand, t
        temp *= alpha                               # cool down
    return best, best_t

Using relative slowdown makes the temperature independent of the absolute runtime. Accepting worse moves with probability e−Δ/T lets the search escape local minima early and behave like hill climbing as T → 034. Note that a neighbour already in CACHE costs nothing, so a real implementation should also stop after a maximum number of iterations.

Exercise 7 · Break-even point Design

Tuning a kernel at first call takes 10 s and makes each later call 0.2 ms faster. After how many calls does tuning pay off? When would you instead tune at install time or offline?

Show solution

10 s / 0.2 ms = 50,000 calls. For a short-lived program, tune offline or at install time and store the result, as ATLAS does at installation and FFTW does with wisdom files17,50. For long-running servers or training jobs, run-time tuning amortises easily, which is the setting for cuDNN benchmark mode and Triton's autotuner47,14.

Exercise 8 · Over-fitting the tuner Discussion

You tuned mm.c for N = 1024 on your laptop. List three reasons the winning configuration might be poor in production.

Show solution

(1) A different problem size changes the working set and how tiles divide the matrix (input sensitivity)46. (2) A different CPU has different caches and vector units, so the optimum moves (portability)17. (3) The tuning run may have been biased, for example by environment size, link order or frequency scaling, so the "winner" may have won by noise44. Remedies: tune over a set of representative sizes, re-tune per machine, and repeat measurements.

17Trivia questions

1. What does ATLAS stand for, and when was it first published?

Automatically Tuned Linear Algebra Software, presented by Whaley and Dongarra at Supercomputing 19985.

2. What does PHiPAC stand for?

Portable High Performance ANSI C, a 1997 methodology for generating and searching matrix-multiply code4.

3. Which prize did FFTW's authors receive in 1999?

The J. H. Wilkinson Prize for Numerical Software61.

4. In which programming language is FFTW's codelet generator genfft written?

Objective Caml (OCaml)51.

5. What does FFTW call a saved set of tuned plans?

Wisdom, which can be exported and imported between runs50.

6. How much faster than Python was Leiserson et al.'s best matrix multiply, and what fraction of peak did it reach?

62,806× faster, at about 40% (40.45%) of the machine's peak22.

7. What is OpenTuner's meta-technique for sharing trials between search techniques?

A multi-armed bandit with a sliding window and area-under-the-curve credit assignment, called the AUC Bandit15.

8. Name two innocuous-looking factors that Mytkowicz et al. showed can bias performance measurements.

The size of the UNIX environment and the link order of object files44.

9. Is the phase-ordering problem decidable?

Not in general: Touati and Barthou showed it is undecidable in its general form, while some restricted versions are decidable18.

10. What speedups did Ansor report over the prior state of the art?

Up to 3.8× on Intel CPUs, 2.6× on ARM CPUs and 1.7× on NVIDIA GPUs11.

11. Which LLVM heuristic did MLGO replace first, and with what result?

Inlining for size, with up to 7% size reduction compared with -Oz49.

12. According to Bergstra and Bengio, why does random search often beat grid search?

Because objective functions often have low effective dimensionality: only a few parameters matter, and random sampling explores more distinct values of them than a grid with the same budget33.

13. Did a model-driven approach ever match ATLAS's empirical search?

Yes. Yotov et al. built a model-driven version of ATLAS's code generator that produced code with comparable performance31.

14. What did Rice formalise in 1976 that underlies auto-tuning?

The algorithm selection problem: choosing the best algorithm for a given problem instance28.

18Glossary

Configuration
One assignment of values to all tuning parameters; one point in the search space15.
Search space
The set of legal configurations, including constraints between parameters1.
Iterative compilation
Compiling and measuring many variants of a program to choose the best20,21.
Phase ordering
Choosing the order (and repetition) of compiler passes19,18.
Cost model
A function that predicts the performance of a configuration without running it; analytical or learned31,23.
Schedule
In Halide and TVM, the description of how an algorithm is mapped to loops, tiles, threads and vectors9,10.
Wisdom
FFTW's stored record of tuned plans50.
Surrogate / acquisition function
In Bayesian optimisation, the probabilistic model of the objective and the rule for choosing the next point36.
