1What is high-level synthesis?

High-level synthesis (HLS), also called behavioural or architectural synthesis, is the automatic translation of an algorithmic description of behaviour into a register-transfer-level (RTL) hardware design that implements it1,2,3. The input is usually a function written in C, C++ or SystemC, with no notion of clock cycles. The output is a structural description, in Verilog or VHDL, of a datapath (functional units, registers, multiplexers and memories) and a controller (a finite-state machine) that sequences it cycle by cycle1,4.

Seen from a compiler writer's chair, HLS is a compiler whose target is not an instruction set but a circuit. A conventional compiler maps operations onto a fixed set of functional units and registers that the processor already has. An HLS compiler decides how many functional units and registers to build, when each operation runs, and which piece of hardware runs it. These three decisions are called allocation, scheduling and binding, and they are the heart of every HLS tool1,2.

Why bother? Writing RTL by hand is slow and error-prone, and it fixes the micro-architecture early. HLS raises the abstraction level so that designers can explore many architectures from one source, simulate at software speed, and retarget designs to new clock rates or devices. These productivity arguments, and the rise of FPGAs as accelerators, drove the adoption of HLS in industry5,6,7.

HLS is not magic. The quality of the result depends heavily on how the source is written and on the directives the designer adds. Comparative studies report that HLS designs can approach hand-written RTL in performance, often at some cost in area, and that results vary widely between tools and coding styles6,8.

2Abstraction levels and the HLS flow

Gajski and Kuhn's Y-chart describes a design in three domains (behavioural, structural and physical) and at several levels of abstraction, drawn as concentric rings from system level on the outside down to circuit level at the centre9,4. Synthesis is a move from the behavioural axis to the structural axis. HLS makes that move at the algorithmic level, producing an RTL structure that logic synthesis then lowers to gates4,2.

Inside an HLS tool, the classic sequence of tasks is: compile the specification into a formal model, allocate hardware resources, schedule operations into clock cycles, bind operations and variables to resources, and generate the RTL architecture1. 3The front end: from C to a data-flow graph

Modern HLS tools reuse software compiler infrastructure for their front ends. LegUp was built on LLVM11; Bambu, from the PandA framework at Politecnico di Milano, accepts C/C++ through GCC or Clang front ends12,13; and AMD (formerly Xilinx) released the source code of the LLVM-based front end of Vitis HLS in 2021, while keeping the back end, which does the FPGA-specific scheduling and RTL generation, closed14,15.

The front end parses the program, inlines functions, and runs familiar optimisations such as constant propagation, dead-code elimination and loop transformations. Then it builds a control and data-flow graph (CDFG): a control-flow graph whose basic blocks each contain a data-flow graph (DFG) of operations, with edges for data dependences4,2. Parallelising transformations matter more than in software, because every exposed operation can get its own hardware. The SPARK framework showed that code motion, speculation and if-conversion applied before scheduling can improve HLS results substantially16.

What does not synthesise. Hardware is fixed at build time, so features that need a run-time heap or an unbounded stack are restricted. Vitis HLS, for example, does not support dynamic memory allocation or operating-system calls in the synthesised function, and it restricts recursion and pointer use; the full list is in the coding-style chapter of its user guide10. Surveys of other tools report similar restrictions6.

Running example: the diffeq loop body

The loop body below solves the differential equation y″ + 3xy′ + 3y = 0 by forward Euler steps. It is the classic "diffeq" example that Paulin and Knight used to illustrate force-directed scheduling, and it remains a standard teaching case17,2. We reuse u*dx, so our version has five multiplications.

diffeq.c
void diffeq(int x, int y, int u, int dx, int a,
            int *x_out, int *y_out, int *u_out, int *cont) {
    int m1 = 3 * x;          // MUL
    int m2 = u * dx;         // MUL
    int m4 = 3 * y;          // MUL
    int a1 = x + dx;         // ALU   x1 = x + dx
    int m3 = m1 * m2;        // MUL   3x·u·dx
    int m5 = m4 * dx;        // MUL   3y·dx
    int a2 = y + m2;         // ALU   y1 = y + u·dx
    int c1 = a1 < a;         // ALU   loop condition
    int s1 = u - m3;         // ALU
    int s2 = s1 - m5;        // ALU   u1 = u - 3x·u·dx - 3y·dx
    *x_out = a1; *y_out = a2; *u_out = s2; *cont = c1;
}

4Scheduling

A schedule assigns every operation a start time (a control step, or clock cycle) such that each operation starts only after its operands are ready. Two families of problem appear in practice2,1:

  • Resource-constrained scheduling: given a fixed set of functional units, minimise latency.
  • Time-constrained (latency-constrained) scheduling: given a latency bound, minimise the hardware needed.

With resource limits, scheduling a precedence graph to minimise length is NP-complete in general18, so tools use heuristics or mathematical programming. Hu's 1961 algorithm is optimal for one special case, unit-time operations on identical units with tree-shaped precedence, and it is the ancestor of the list schedulers used in HLS19,2.

4.1 ASAP, ALAP and mobility

The as-soon-as-possible (ASAP) schedule starts each operation the moment its predecessors finish. The as-late-as-possible (ALAP) schedule, computed backwards from a latency bound, starts each operation as late as it can without delaying the end. The difference is the operation's mobility (slack). Operations with zero mobility lie on a critical path2,17.

4.2 List scheduling, force-directed scheduling, ILP and SDC

List scheduling walks forward one control step at a time. At each step it collects the ready operations, sorts them by a priority (commonly the ALAP time or the length of the longest path to the sink), and starts as many as the free units allow2. It is fast and usually good, but it is greedy.

Force-directed scheduling, introduced in the HAL system, solves the time-constrained problem. It computes, for each step, a distribution graph of the expected number of operations of each type, and places operations so as to balance those distributions, which reduces the number of units needed17.

Integer linear programming (ILP) gives exact solutions: binary variables xi,t say that operation i starts at step t, with constraints for precedence and per-step resource counts. Hwang, Lee and Hsu showed a formulation that is practical for moderate sizes20, but ILP time grows quickly with design size.

SDC scheduling (system of difference constraints) expresses dependences, latency bounds, clock-period chaining limits and relative timing as constraints of the form sj − si ≤ c. The constraint matrix is totally unimodular, so a linear program returns integer start times in polynomial time. Resource limits are handled heuristically by adding extra ordering constraints21. SDC scheduling underpins AutoPilot, the tool that became Vivado HLS and then Vitis HLS, and LegUp5,11.

Chaining and multicycling. If two dependent operations together fit in one clock period, the scheduler can chain them in the same cycle without a register between them. An operation slower than one period can be multicycled across several steps, or implemented as a pipelined unit. Both decisions depend on delay estimates for the target technology, which is why HLS tools ask for a clock period and a target device1,21,10.

4.3 Source code: a list scheduler in Python

sched.py (runs with Python 3, no dependencies)
# Data-flow graph of the diffeq body: name -> (operation class, predecessors)
DFG = {
    "m1": ("mul", []),            "m2": ("mul", []),
    "m4": ("mul", []),            "a1": ("alu", []),
    "m3": ("mul", ["m1", "m2"]),  "m5": ("mul", ["m4"]),
    "a2": ("alu", ["m2"]),        "c1": ("alu", ["a1"]),
    "s1": ("alu", ["m3"]),        "s2": ("alu", ["s1", "m5"]),
}
LAT = {"mul": 1, "alu": 1}

def asap(g, lat):
    t = {}
    for v in g:                                  # g is in topological order
        t[v] = max([t[p] + lat[g[p][0]] for p in g[v][1]], default=0)
    return t

def alap(g, lat, bound):
    succ = {v: [w for w in g if v in g[w][1]] for v in g}
    t = {}
    for v in reversed(list(g)):
        t[v] = min([t[s] for s in succ[v]], default=bound) - lat[g[v][0]]
    return t

def list_schedule(g, lat, units):
    """Resource-constrained list scheduling; priority = ALAP time (least slack first)."""
    length = max(asap(g, lat)[v] + lat[g[v][0]] for v in g)
    prio = alap(g, lat, length)
    start, busy, step = {}, [], 0
    while len(start) < len(g):
        busy = [(c, f) for c, f in busy if f > step]       # units still occupied
        ready = [v for v in g if v not in start and
                 all(p in start and start[p] + lat[g[p][0]] <= step for p in g[v][1])]
        for v in sorted(ready, key=lambda v: prio[v]):
            c = g[v][0]
            if sum(1 for b, _ in busy if b == c) < units[c]:
                start[v] = step
                busy.append((c, step + lat[c]))
        step += 1
    return start

s = list_schedule(DFG, LAT, {"mul": 2, "alu": 1})
print(sorted(s.items(), key=lambda kv: kv[1]))
# [('m1', 0), ('m2', 0), ('a1', 0), ('m4', 1), ('m3', 1), ('a2', 1),
#  ('m5', 2), ('s1', 2), ('c1', 3), ('s2', 4)]      -> latency 5

5Allocation and binding

Allocation chooses how many units of each type to build (two multipliers and one ALU in our running schedule). Binding then maps each operation to a specific unit instance, each value that crosses a clock edge to a register, and each array to a memory. Binding also determines the multiplexers, because a unit or register that is shared needs a multiplexer on each input to select between its sources1,2.

5.1 Functional-unit binding

Two operations are compatible if they can share a unit, that is, they are of a suitable type and never execute in the same step. Finding the fewest units is a clique-partitioning problem on the compatibility graph; Tseng and Siewiorek's Facet system used a clique-partitioning heuristic for exactly this22. When the schedule is fixed, the number of units of a type equals the maximum number of concurrent operations of that type, but which operations share a unit still changes the interconnect cost2.

For the 5-cycle schedule found in §4, one valid binding, the one the widget above draws, is MUL0 ← {m1, m4, m5}, MUL1 ← {m2, m3} and ALU ← {a1, a2, s1, c1, s2}.

5.2 Register binding and the left-edge algorithm

A value needs a register from the cycle after it is produced until the cycle in which it is last read. Values whose lifetimes do not overlap can share a register. In straight-line code the lifetimes are intervals, the conflict graph is an interval graph, and the left-edge algorithm colours it optimally: sort intervals by start time and put each into the first register that is free by then23,2. The algorithm was first devised for channel routing of wires by Hashimoto and Stevens in 1971, and Kurdahi and Parker brought it to register allocation in the REAL program24,23.

left_edge.py
def left_edge(intervals):
    """intervals: name -> (birth, death), half-open. Returns (assignment, #registers)."""
    regs, out = [], {}                       # regs[i] = time register i becomes free
    for name, (b, d) in sorted(intervals.items(), key=lambda kv: kv[1][0]):
        for i, free_at in enumerate(regs):
            if free_at <= b:
                regs[i] = d; out[name] = i; break
        else:
            regs.append(d); out[name] = len(regs) - 1
    return out, len(regs)

print(left_edge({"m1": (1, 2), "m2": (1, 2), "a1": (1, 4), "m4": (2, 3),
                 "m3": (2, 3), "m5": (3, 5), "s1": (3, 5)}))
# ({'m1': 0, 'm2': 1, 'a1': 2, 'm4': 0, 'm3': 1, 'm5': 0, 's1': 1}, 3)

With loops and branches, lifetimes are no longer simple intervals, and tools fall back on graph colouring or clique partitioning, as in software register allocation2,22.

6Generating RTL: the FSMD

The output of scheduling and binding is naturally described as a finite-state machine with datapath (FSMD): each control step becomes a state of the controller, and in each state the controller drives multiplexer selects and register enables so that the bound units compute the scheduled operations4,1.

The listing below is hand-written to show the shape of HLS output for this schedule and binding. Real tools emit much more verbose, structural code with explicit multiplexers and handshake ports, but the state-per-step structure is the same.

diffeq_fsmd.v (illustrative, Verilog-2001)
module diffeq_fsmd (
  input  wire               clk, rst, start,
  input  wire signed [31:0] x_in, y_in, u_in, dx, a,
  output reg  signed [31:0] x, y, u,
  output reg                cont, done);

  localparam IDLE=3'd0, S0=3'd1, S1=3'd2, S2=3'd3, S3=3'd4, S4=3'd5;
  reg [2:0] state;
  reg signed [31:0] r0, r1, r2;      // shared registers from left-edge binding

  always @(posedge clk) begin
    if (rst) begin state <= IDLE; done <= 1'b0; end
    else case (state)
      IDLE: if (start) begin
              x <= x_in; y <= y_in; u <= u_in; done <= 1'b0; state <= S0;
            end
      //        MUL0                 MUL1              ALU
      S0: begin r0 <= 3 * x;     r1 <= u * dx;     r2 <= x + dx;       state <= S1; end // m1 m2 a1
      S1: begin r0 <= 3 * y;     r1 <= r0 * r1;    y  <= y + r1;       state <= S2; end // m4 m3 a2
      S2: begin r0 <= r0 * dx;                     r1 <= u - r1;       state <= S3; end // m5    s1
      S3: begin                                    cont <= (r2 < a);   state <= S4; end //       c1
      S4: begin x <= r2;                           u <= r1 - r0;
                done <= 1'b1;                                         state <= IDLE; end // s2
      default: state <= IDLE;
    endcase
  end
endmodule

Non-blocking assignments (<=) read register values from the start of the cycle, so in state S1 the expression y + r1 uses the old r1 (the value u·dx) even though r1 is overwritten in the same state. This is exactly the register-sharing behaviour that the lifetime analysis allows.

7Loops: unrolling and pipelining

Most of the run time of an accelerator is spent in loops, so loop optimisations are the main lever in HLS5,25.

  • Unrolling replicates the loop body k times (or fully), exposing more operations to the scheduler at the cost of more hardware. Fully unrolled loops become pure spatial parallelism10,25.
  • Pipelining starts a new iteration every II cycles, the initiation interval, before earlier iterations have finished. It is the hardware form of software pipelining26,27.

7.1 What limits the initiation interval?

Modulo scheduling theory gives a lower bound, the minimum initiation interval MII = max(ResMII, RecMII)27:

  • ResMII (resource bound): for each resource type, the number of uses per iteration divided by the number of units, rounded up. A dual-port RAM read four times per iteration forces II ≥ ⌈4/2⌉ = 2.
  • RecMII (recurrence bound): for each dependence cycle that crosses iterations, the total latency around the cycle divided by its iteration distance, rounded up. An accumulation acc += x[i] through an adder with latency L forces II ≥ L.

Rau's iterative modulo scheduling starts at the MII and tries to place every operation in a modulo reservation table, increasing II until it succeeds27. HLS tools report the II they achieve and the reason when they miss the target10.

Breaking a recurrence with partial sums (C++)
// II limited by adder latency L: each add waits for the previous one
float sum_slow(const float x[1024]) {
  float acc = 0;
  for (int i = 0; i < 1024; i++) {
#pragma HLS PIPELINE II=1        // requested, but RecMII = L
    acc += x[i];
  }
  return acc;
}

// L independent accumulators: the recurrence distance becomes L, so RecMII = 1
constexpr int L = 4;                  // set to the adder latency
float sum_fast(const float x[1024]) {
  float part[L] = {0};
#pragma HLS ARRAY_PARTITION variable=part type=complete
  for (int i = 0; i < 1024; i++) {
#pragma HLS PIPELINE II=1
    part[i % L] += x[i];
  }
  float acc = 0;
  for (int k = 0; k < L; k++) acc += part[k];
  return acc;
}

Floating-point addition is not associative, so the reordered sum can differ in the last bits. A compiler must not do this rewrite on its own unless the user relaxes floating-point semantics, which is why HLS designers often write it by hand. Vitis HLS documents an option to allow such unsafe floating-point reassociation10.

8Memories, interfaces and dataflow

8.1 Arrays become memories

By default an array in the synthesised function becomes an on-chip RAM, and an FPGA block RAM has at most two ports, so at most two accesses per cycle10,25. When a pipelined loop needs more, the array must be partitioned into several smaller memories, or into individual registers. Vitis HLS offers block, cyclic and complete partitioning through #pragma HLS ARRAY_PARTITION variable=… type=… factor=… dim=…10.

8.2 Interfaces

The arguments of the top-level function become hardware ports. Interface synthesis decides their protocol: scalar arguments can become registers on an AXI4-Lite control interface (s_axilite), pointers to large arrays can become AXI4 memory-mapped masters (m_axi) that read external DRAM in bursts, and hls::stream arguments become AXI4-Stream ports (axis). In Vitis HLS these are chosen with #pragma HLS INTERFACE mode=… port=…, which applies only to the top-level function10.

8.3 Task-level pipelining with DATAFLOW

Loop pipelining overlaps iterations of one loop. Dataflow overlaps whole functions or loops: with #pragma HLS DATAFLOW, a producer → consumer chain of tasks runs concurrently, connected by FIFOs or ping-pong buffers, so the consumer starts before the producer has finished10,25. This is the coarse-grained parallelism behind streaming accelerators such as hls4ml and FINN28,29.

Dataflow: read → compute → write (Vitis HLS C++)
#include <hls_stream.h>

static void rd(const int *in, hls::stream<int> &s, int n) {
  for (int i = 0; i < n; i++) {
#pragma HLS PIPELINE II=1
    s.write(in[i]);
  }
}
static void sq(hls::stream<int> &a, hls::stream<int> &b, int n) {
  for (int i = 0; i < n; i++) {
#pragma HLS PIPELINE II=1
    int v = a.read(); b.write(v * v);
  }
}
static void wr(hls::stream<int> &s, int *out, int n) {
  for (int i = 0; i < n; i++) {
#pragma HLS PIPELINE II=1
    out[i] = s.read();
  }
}
void square_all(const int *in, int *out, int n) {
#pragma HLS INTERFACE mode=m_axi port=in  offset=slave bundle=gmem0
#pragma HLS INTERFACE mode=m_axi port=out offset=slave bundle=gmem1
#pragma HLS INTERFACE mode=s_axilite port=n
#pragma HLS INTERFACE mode=s_axilite port=return
#pragma HLS DATAFLOW
  hls::stream<int> s1, s2;
  rd(in, s1, n);
  sq(s1, s2, n);
  wr(s2, out, n);
}

9Bit widths and arbitrary-precision types

A C int is a fixed-size type, commonly 32 bits, but every extra bit of an operand costs logic, registers and wiring in hardware5. HLS tools therefore provide arbitrary-precision types: Vitis HLS has ap_int<W>, ap_uint<W> and fixed-point ap_fixed<W,I>10, and Catapult uses the open-source Algorithmic C types ac_int and ac_fixed30,31. SystemC offers sc_int, sc_bigint and fixed-point types in its standard library32.

Rule of thumb for exact accumulation. Multiplying a signed a-bit value by a signed b-bit value needs a + b bits, and adding n such products needs a further ⌈log₂ n⌉ guard bits. A 16-tap filter with 16-bit samples and coefficients therefore needs a 36-bit accumulator (16 + 16 + 4).

Tools also run bit-width analysis on their own, propagating value ranges through the IR to trim unused high bits from operations and registers. Bit-width optimisation was one of the code transformations in AutoPilot, the ancestor of Vitis HLS5.

10Worked example: a FIR filter end to end

A finite impulse response (FIR) filter computes y[n] = Σt=0T−1 c[t]·x[n−t]. It is the standard first HLS design because every optimisation in this article shows up in it25. The code below targets Vitis HLS; the pragmas are the documented forms10.

fir.cpp
#include <ap_int.h>
#include <hls_stream.h>

#define TAPS 16
typedef ap_int<16> sample_t;
typedef ap_int<16> coef_t;
typedef ap_int<36> acc_t;            // 16 + 16 + log2(16) bits: exact

static const coef_t C[TAPS] = {
  -12, -33, 41, 160, 90, -310, -520, 2900,
  2900, -520, -310, 90, 160, 41, -33, -12};    // symmetric low-pass example

void fir(hls::stream<sample_t> &in, hls::stream<acc_t> &out, int n) {
#pragma HLS INTERFACE mode=axis      port=in
#pragma HLS INTERFACE mode=axis      port=out
#pragma HLS INTERFACE mode=s_axilite port=n
#pragma HLS INTERFACE mode=s_axilite port=return

  static sample_t shift[TAPS];          // delay line, kept between calls
#pragma HLS ARRAY_PARTITION variable=shift type=complete dim=1

SAMPLES:
  for (int i = 0; i < n; i++) {
#pragma HLS PIPELINE II=1               // inner loop is unrolled automatically
    sample_t x = in.read();
    acc_t acc = 0;
  TAPS_LOOP:
    for (int t = TAPS - 1; t > 0; t--) {
      shift[t] = shift[t - 1];
      acc += shift[t] * C[t];
    }
    shift[0] = x;
    acc += x * C[0];
    out.write(acc);
  }
}

Pipelining the outer loop makes Vitis HLS unroll the inner loop, so the 16 multiply-accumulates become 16 parallel multipliers feeding an adder tree10. Complete partitioning turns shift into 16 registers, which removes the two-port memory limit that would otherwise force a large II (§7.1).

fir_tb.cpp (C testbench, reused for co-simulation)
#include <cstdio>
#include <cstdlib>
#include <ap_int.h>
#include <hls_stream.h>
#define TAPS 16
typedef ap_int<16> sample_t;  typedef ap_int<36> acc_t;
void fir(hls::stream<sample_t> &, hls::stream<acc_t> &, int);

static const int C[TAPS] = {-12,-33,41,160,90,-310,-520,2900,
                             2900,-520,-310,90,160,41,-33,-12};

int main() {
  const int N = 256;
  static int x[N];
  hls::stream<sample_t> in;  hls::stream<acc_t> out;
  srand(1);
  for (int i = 0; i < N; i++) { x[i] = (rand() % 65536) - 32768; in.write(x[i]); }
  fir(in, out, N);
  int errors = 0;
  for (int n = 0; n < N; n++) {
    long long ref = 0;                                   // golden model
    for (int t = 0; t < TAPS; t++) if (n - t >= 0) ref += (long long)C[t] * x[n - t];
    long long got = out.read().to_int64();
    if (got != ref) { if (errors++ < 5) printf("n=%d got %lld want %lld\n", n, got, ref); }
  }
  printf(errors ? "FAIL: %d errors\n" : "PASS\n", errors);
  return errors != 0;                // non-zero return marks the test as failed
}

At a 100 MHz clock, version D filters N = 1024 samples in about 1024 + D cycles, roughly 10 µs, and accepts one sample per cycle. Version B is about T times slower but uses one multiplier. Choosing between such points is design-space exploration, and automating it is an active research area34.

11Beyond static scheduling: new directions

11.1 Dynamically scheduled HLS

Classic HLS fixes the schedule at compile time, so it must assume the worst case for every data-dependent branch and memory access. Dynamatic instead generates dataflow circuits in which each operation fires when its operands arrive, using handshake signals between units35. The design builds on synchronous elastic circuits36, and its authors report better performance than statically scheduled HLS on code with irregular control flow and memory accesses35.

11.2 MLIR and CIRCT

MLIR lets one compiler hold many levels of IR, called dialects, and lower between them step by step37. The CIRCT project applies MLIR to hardware, with dialects for handshake (dataflow) circuits, static control, finite-state machines and RTL-level hardware, and a path to SystemVerilog38. ScaleHLS uses MLIR to represent and optimise HLS designs at the graph, loop and directive levels, and emits code for a downstream HLS tool39. Calyx is an IR for accelerator generators that mixes structural hardware with a control language, and CIRCT includes a Calyx dialect40,38.

11.3 Domain-specific front ends

Several projects separate what is computed from how it is mapped to hardware. HeteroCL and Allo, both from Cornell, are Python-embedded languages that apply scheduling customisations (loop tiling, memory partitioning, data types) separately from the algorithm41,42. In machine learning, hls4ml translates trained neural networks into HLS C++ for low-latency FPGA inference, first for particle-physics triggers28, and FINN builds streaming dataflow accelerators for quantised neural networks29.

11.4 Neighbours: hardware construction languages

Not every high-level hardware language is HLS. Chisel is a Scala-embedded language in which the designer still writes the cycle-level structure, but uses software abstractions to generate it43. Bluespec SystemVerilog describes hardware as guarded atomic rules that its compiler schedules into cycles44; its compiler is open source45. Google's XLS is an HLS toolchain whose main input is DSLX, a Rust-inspired language, and which emits Verilog and SystemVerilog46.

mac.x (DSLX for Google XLS)
// A multiply-accumulate step; XLS schedules it into pipeline stages.
fn mac(acc: u32, a: u16, b: u16) -> u32 {
    acc + (a as u32) * (b as u32)
}

#[test]
fn mac_test() {
    assert_eq(mac(u32:1, u16:2, u16:3), u32:7)
}

11.5 SystemC-based HLS

Commercial ASIC-oriented tools such as Siemens Catapult and Cadence Stratus take C++ or SystemC31,47. SystemC (IEEE 1666) adds modules, ports, clocked threads and signals to C++32, and Accellera's SystemC Synthesizable Subset defines the part that synthesis tools are expected to accept48.

mac_sc.h (synthesisable SystemC style)
#include <systemc.h>
SC_MODULE(mac_sc) {
  sc_in<bool>           clk, rst;
  sc_in<sc_int<16> >    a, b;
  sc_out<sc_int<40> >   acc_out;

  void run() {
    sc_int<40> acc = 0;
    acc_out.write(0);
    wait();                                   // reset state ends here
    while (true) {
      acc += a.read() * b.read();
      acc_out.write(acc);
      wait();                                 // one clock edge per iteration
    }
  }
  SC_CTOR(mac_sc) {
    SC_CTHREAD(run, clk.pos());
    reset_signal_is(rst, true);
  }
};

12Verification and trust

The standard flow verifies in two steps. C simulation runs the source and its testbench as ordinary software. C/RTL co-simulation then runs the same testbench against the generated RTL in a logic simulator and compares outputs10. Co-simulation only checks the inputs the testbench supplies, so it cannot prove the tool correct.

That matters because HLS tools are large optimising compilers and do have bugs. Herklotz et al. fed large numbers of randomly generated C programs to several mainstream HLS tools and found crashes and miscompilations49. In response, the same group built Vericert, an HLS tool for a subset of C that is written and proved correct in the Coq proof assistant on top of the CompCert verified C compiler, so its generated Verilog is guaranteed to match the C semantics50.

For performance claims, the community relies on shared benchmark suites: CHStone, a set of twelve C programs for HLS51, and MachSuite, a suite of accelerator kernels52.

13A short history

15Exercises with solutions

Exercise 1 · ASAP, ALAP and mobility Warm-up

For y = (a + b)·(c − d) + e·f, with all operations taking one cycle, write the DFG (n1 = a+b, n2 = c−d, n3 = e·f, n4 = n1·n2, n5 = n4+n3). Compute the ASAP and ALAP steps and the mobility of each node.

Show solution
n1n2n3n4n5
ASAP00012
ALAP (bound 3)00112
Mobility00100

The critical path is n1 (or n2) → n4 → n5, length 3. Only n3 has slack, so it can move to step 1 to share a multiplier with n4 if needed2.

Exercise 2 · List scheduling under resource limits Scheduling

Schedule the DFG of Exercise 1 with one multiplier and one ALU, using ALAP time as the priority. What is the latency, and is it optimal?

Show solution 
step 0: ALU n1    MUL n3
step 1: ALU n2    MUL –      (n4 waits for n2)
step 2: ALU –     MUL n4
step 3: ALU n5    MUL –      → latency 4

It is optimal. n1 and n2 must share the single ALU, so the later of them finishes at the end of step 1 at best; n4 then needs step 2 and n5 step 3. A second ALU would give latency 3.

Exercise 3 · Minimum initiation interval Pipelining

A loop body reads five elements x[i..i+4] from one dual-port RAM, adds them into v, and updates acc = acc·k + v. The multiplier has latency 3 and the adder latency 1. Compute ResMII, RecMII and MII. Then suggest how to reach II = 1.

Show solution

ResMII = ⌈5 reads / 2 ports⌉ = 3. RecMII: the cycle acc → × → + → acc has latency 3 + 1 = 4 and distance 1, so RecMII = 4. MII = max(3, 4) = 427.

To reach II = 1: (i) partition x (cyclic factor 5, or a sliding window of registers) so that ResMII = 1; (ii) rewrite the recurrence with look-ahead, for example acci+4 = acci·k⁴ + (vik³ + vi+1k² + vi+2k + vi+3), keeping four interleaved accumulators. The dependence distance becomes 4, so RecMII = ⌈4/4⌉ = 1. The extra multipliers are the price.

Exercise 4 · Left-edge register allocation Binding

Assign registers to the lifetimes a[0,3), b[1,2), c[2,5), d[3,4), e[4,6), f[5,7) with the left-edge algorithm. How many registers are needed, and why is that optimal?

Show solution 
a[0,3) → R0     b[1,2) → R1     c[2,5) → R1 (R1 free at 2)
d[3,4) → R0     e[4,6) → R0     f[5,7) → R1 (R1 free at 5)

Two registers. At most two intervals overlap at any time (for example a and b at time 1), and for interval graphs the maximum overlap equals the minimum number of colours, which left-edge achieves23,2.

Exercise 5 · Choose a partitioning Memory

A loop pipelined at II = 1 reads A[4i], A[4i+1], A[4i+2] and A[4i+3] each iteration. A has 1024 elements and maps to dual-port block RAM. Which ARRAY_PARTITION directive is the cheapest that allows II = 1?

Show solution

#pragma HLS ARRAY_PARTITION variable=A type=cyclic factor=2. Cyclic factor 2 puts even indices in one bank and odd in the other; each iteration then makes two reads per bank, which two ports can serve. Block partitioning would not help, because all four addresses fall in the same block. Cyclic factor 4 also works with single-port banks but uses more memories10.

Exercise 6 · Pipeline arithmetic Analysis

A loop runs 1000 iterations with a body of depth 8 cycles. Give the latency without pipelining, pipelined at II = 1, and pipelined at II = 2.

Show solution

Without pipelining: 1000 × 8 = 8000 cycles. II = 1: (1000 − 1)·1 + 8 = 1007 cycles. II = 2: 999·2 + 8 = 2006 cycles25. The pipeline's start-up cost (the depth) matters only for short loops.

Exercise 7 · Size the accumulator Bit widths

A 64-tap FIR filter uses signed 12-bit samples and signed 10-bit coefficients. What accumulator width guarantees no overflow? Write the ap_int type.

Show solution

Each product needs 12 + 10 = 22 bits. Summing 64 products adds ⌈log₂ 64⌉ = 6 bits, so 28 bits suffice: typedef ap_int<28> acc_t;10. Using a C int would waste 4 bits in every adder of the tree, and using a 64-bit long long would waste 36.

Exercise 8 · Make it synthesisable Coding style

Which lines below cause problems for HLS, and how would you fix them?

int fib(int n) { return n < 2 ? n : fib(n-1) + fib(n-2); }
void top(int n, int *out) {
  int *buf = (int*)malloc(n * sizeof(int));
  for (int i = 0; i < n; i++) buf[i] = fib(i);
  printf("done\n");
  for (int i = 0; i < n; i++) out[i] = buf[i];
  free(buf);
}
Show solution

(1) malloc/free: dynamic allocation is not synthesisable; use a fixed-size array with a documented maximum n. (2) The recursive fib: unbounded recursion has no fixed hardware; rewrite it as a loop (and here, compute the sequence incrementally in the first loop). (3) printf: Vitis HLS ignores such display-only system calls during synthesis, so it is harmless but does nothing in hardware10.

#define NMAX 64
void top(int n, int out[NMAX]) {
  int f0 = 0, f1 = 1;
  for (int i = 0; i < NMAX; i++) {
#pragma HLS PIPELINE II=1
    if (i < n) out[i] = f0;
    int t = f0 + f1; f0 = f1; f1 = t;
  }
}

Exercise 9 · Pipelined units in the scheduler Coding

Change the Python list scheduler in §4.3 so that a multiplier with latency 2 is pipelined: it can accept a new operation every cycle even though each result takes two cycles. What latency do you get for the diffeq body with 2 multipliers and 1 ALU, and with 1 multiplier and 1 ALU?

Show solution

Separate latency (when the result is ready) from occupancy (how long the unit is busy). Keep using lat in the readiness test and use a new occ table when marking units busy:

LAT = {"mul": 2, "alu": 1}
OCC = {"mul": 1, "alu": 1}     # pipelined: busy for one cycle only
...
                busy.append((c, step + OCC[c]))   # was: step + lat[c]

Results: 6 cycles with 2 multipliers and 1 ALU (7 if the multiplier is not pipelined), and 7 cycles with 1 multiplier and 1 ALU (11 if not pipelined). Pipelined units are why HLS tools prefer pipelined cores for long-latency operations1.

16Trivia questions

1. What are the three domains of the Gajski–Kuhn Y-chart?

Behavioural, structural and physical (geometric). Concentric rings mark the abstraction levels9,4.

2. The left-edge algorithm used for register allocation was invented for which problem?

Channel routing of wires, by Hashimoto and Stevens in 1971. Kurdahi and Parker applied it to registers in REAL (1987)24,23.

3. Which HLS system introduced force-directed scheduling, and which example equation is it known for?

HAL, by Paulin and Knight (1989). Their running example was the differential-equation solver now called the "diffeq" benchmark, used in §3 of this article17.

4. What does SDC stand for, and why is it attractive for scheduling?

System of difference constraints. Its constraint matrix is totally unimodular, so linear programming gives integer schedules in polynomial time21.

5. Which tool did Xilinx acquire in January 2011, and where did its technology come from?

AutoPilot, from AutoESL Design Technologies, based on technology originally developed at UCLA54,55. It became Vivado HLS and later Vitis HLS7.

6. LegUp started at which university, and what is it called today?

The University of Toronto11. Microchip acquired LegUp Computing in 2020, and the product is now SmartHLS59,60.

7. Which part of Vitis HLS was open-sourced in 2021, and which part was not?

The LLVM-based front end was released on GitHub; the back end, which does FPGA-specific optimisation, scheduling and RTL generation, stayed closed14,15.

8. Which verified compiler does Vericert build on?

CompCert. Vericert adds a verified HLS back end that produces Verilog, with proofs in Coq50.

9. Intel planned to deprecate its HLS Compiler after which version, and what did it recommend instead?

After version 23.4; Intel recommended migrating designs to the oneAPI Base Toolkit61.

10. What is the name of Google XLS's own design language?

DSLX, a Rust-inspired domain-specific language46.

11. How many programs are in the CHStone HLS benchmark suite?

Twelve, covering arithmetic, media processing, security and microprocessor kernels51.

12. Which 1961 operations-research paper is the ancestor of list scheduling?

T. C. Hu's "Parallel sequencing and assembly line problems", which gave an optimal algorithm for unit-time tasks with tree-shaped precedence19.

13. Bambu is part of which framework, from which university?

The PandA framework from Politecnico di Milano12,13.

14. Who bought Catapult C in 2011, and who bought it back in 2015?

Calypto Design Systems acquired Catapult C from Mentor Graphics in 2011, and Mentor acquired Calypto in 201556,58. The tool is now sold by Siemens31.
