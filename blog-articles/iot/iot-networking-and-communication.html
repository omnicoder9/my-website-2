IoT Networking and Communication: From Radios to Messages

How connected devices find each other, move bits across constrained links, and exchange meaningful data: the link technologies, the Internet protocols adapted for constrained nodes, the messaging protocols that carry telemetry and commands, and the architectures that hold it all together.

Level: intermediate (undergraduate networking assumed) · Includes runnable Python examples, inline diagrams, exercises and trivia · References in Vancouver style; numbers in square brackets point to the list at the end.

1. Introduction

The ITU defines the Internet of Things (IoT) as a global infrastructure that enables advanced services by interconnecting physical and virtual "things" based on interoperable information and communication technologies [1]. Communication is therefore the defining feature of an IoT system: a temperature sensor that cannot report its reading is just a thermometer. Surveys of the field group the enabling technologies into identification, sensing, communication, computation and services, with communication spanning everything from short-range radios to cellular networks and the application protocols on top [2].

IoT networking differs from classic enterprise networking because many devices are constrained. RFC 7228 formalises this by classifying devices by memory: Class 0 devices have far less than 10 KiB of RAM and 100 KiB of flash, Class 1 about 10 KiB and 100 KiB, and Class 2 about 50 KiB and 250 KiB [3]. The same RFC describes constrained-node networks whose links have low throughput, high loss and small frame sizes, and whose nodes often sleep to save energy [3]. Almost every design decision in this article (header compression, UDP-based protocols, publish/subscribe brokers, mesh routing) is a response to those constraints.

2. The IoT communication stack

A useful way to organise the many technologies is a layered stack similar to the Internet model. Physical/link technologies (IEEE 802.15.4, Bluetooth LE, Wi-Fi, LoRa, cellular) move frames; an adaptation layer such as 6LoWPAN fits IPv6 into small frames [4,5]; IP, UDP and TCP provide end-to-end delivery [6–8]; security is provided by TLS or DTLS [9,10]; and application/messaging protocols such as MQTT or CoAP carry the data [11,12]. Some technologies, notably Zigbee, Z-Wave, Modbus RTU, CAN and BACnet MS/TP, define their own non-IP upper layers, which is why gateways are common in IoT deployments [13–17].

3. Network technologies

No single radio serves every IoT use case. Comparative studies of low-power wide-area networks (LPWANs) highlight a fundamental trade-off between range, data rate and energy consumption: technologies that reach kilometres at milliwatt power levels do so by using very low data rates and narrow bandwidths or spread-spectrum coding [20,21]. Short-range technologies such as Bluetooth LE and IEEE 802.15.4 trade range for higher data rates and mesh topologies [22,23].

Wi-Fi (IEEE 802.11)

Wi-Fi is defined by IEEE 802.11, which specifies the MAC and multiple PHYs across the 2.4, 5 and 6 GHz bands [24]. It is the default choice for mains-powered devices that need bandwidth, such as cameras, appliances and smart speakers, because it reuses existing home and enterprise access points. Two features matter for IoT: the 802.11ah (Wi-Fi HaLow) PHY for sub-1 GHz long-range operation, incorporated into the 802.11-2020 revision [24], and Target Wake Time (TWT) in 802.11ax (Wi-Fi 6), which lets an access point negotiate when a station wakes so that it can sleep between service periods [25].

Bluetooth Low Energy

Bluetooth LE operates in the 2.4 GHz ISM band using 40 channels with 2 MHz spacing; three of them (37, 38 and 39) are primary advertising channels and the rest carry data [22,26]. Devices either advertise (broadcast small packets, used by beacons) or form connections in which a central and a peripheral exchange data at agreed connection intervals and sleep in between [22]. Data is organised by the Generic Attribute Profile (GATT) into services and characteristics [26]. Bluetooth 5 added the LE 2M PHY and the long-range LE Coded PHY, and Core Specification 6.0 added Channel Sounding for secure distance measurement [26].

Zigbee and Z-Wave

Zigbee builds network, security and application layers on IEEE 802.15.4, whose 2.4 GHz PHY provides 16 channels and 250 kbit/s [13,23]. A Zigbee network has one coordinator, routers that relay traffic, and end devices that may sleep; it supports mesh and tree routing, and application interoperability comes from the Zigbee Cluster Library [13]. Revision 23 of the specification (2023) strengthens security, for example with dynamic link keys for joining [13].

Z-Wave uses sub-GHz radios whose PHY and MAC are standardised as ITU-T G.9959 [14]. Its classic mesh uses source routing: the controller computes the route and places the list of repeaters in the frame. Security analysis of the protocol describes a limit of 232 nodes per network and up to four repeater hops per route [27].

Thread and Matter

Thread is an IPv6-based, low-power mesh network built on IEEE 802.15.4 and 6LoWPAN [4,29]. Every device has an IPv6 address; routers form a self-healing mesh, sleepy end devices attach to a parent router, and one or more border routers connect the mesh to Wi-Fi/Ethernet networks [29]. Because Thread carries ordinary IPv6/UDP, any IP application protocol can run over it. Thread 1.4 (2024) focused on interoperable border routers and credential sharing between ecosystems [28].

Matter is not a radio. It is an application-layer standard from the Connectivity Standards Alliance that defines a common data model (clusters, attributes, commands), security and commissioning over IP networks: Wi-Fi, Thread and Ethernet, with Bluetooth LE used during commissioning [30,31]. Devices are discovered using DNS-based service discovery [31,47]. Matter's multi-admin feature allows one device to be controlled by several ecosystems at once, and version 1.4 (November 2024) added device types such as solar inverters, batteries and heat pumps [30].

LoRaWAN

LoRa is a chirp spread-spectrum physical layer from Semtech; LoRaWAN is the MAC and network architecture standardised by the LoRa Alliance and recognised by the ITU as Recommendation Y.4480 [32,33,48]. End devices transmit to every gateway in range; gateways forward packets over IP to a network server, which deduplicates them and routes them to application servers. This star-of-stars topology keeps end devices simple [32,34]. LoRaWAN defines device classes: Class A devices open two short receive windows after each uplink and are the lowest power; Class B adds beacon-synchronised scheduled receive slots; Class C listens continuously [32].

The spreading factor (SF7 to SF12) trades data rate for range and robustness: each step up doubles the symbol duration [34,48]. The nominal bit rate is Rb = SF × (BW / 2SF) × CR, where CR is the coding rate [34]. Air time matters because European sub-bands commonly impose a 1% duty cycle, limiting how often a device may transmit [34]. Adaptive Data Rate (ADR) lets the network server instruct devices close to a gateway to use faster spreading factors [32].

NB-IoT, LTE-M and 4G/5G

3GPP Release 13 introduced two cellular technologies for massive machine-type communication. NB-IoT uses a 180 kHz carrier that can be deployed in-band within an LTE carrier, in an LTE guard band, or stand-alone; it targets a maximum coupling loss of 164 dB (about 20 dB beyond legacy GPRS) for devices deep inside buildings, with a battery life target of ten years [35]. LTE-M (eMTC) uses a 1.4 MHz bandwidth, offers higher data rates (around 1 Mbit/s peak in Release 13), and supports connected-mode mobility and voice, which suits wearables and asset trackers [36]. Both use power-saving mode (PSM) and extended discontinuous reception (eDRX) so that devices can remain registered while their radios are off for long periods [35,36].

For high-bandwidth or time-critical devices, 4G LTE and 5G NR are used. The ITU's IMT-2020 vision defines three 5G usage scenarios: enhanced mobile broadband (eMBB), ultra-reliable and low-latency communications (URLLC), and massive machine-type communications (mMTC) [37]. URLLC targets industrial control and vehicle communication, while the NR specification in 3GPP TS 38.300 also covers reduced-capability (RedCap) devices for mid-range IoT such as industrial sensors and wearables [38].

Ethernet

Wired Ethernet (IEEE 802.3) remains the backbone of industrial and fixed installations because it is deterministic enough for many control applications, immune to radio interference and simple to secure physically [39]. Power over Ethernet delivers power and data on one cable; the four-pair IEEE 802.3bt amendment raised power delivery to up to 90 W at the source [40]. Single-pair Ethernet brings IP to field instruments: 10BASE-T1L, defined in IEEE 802.3cg, runs at 10 Mbit/s over a single twisted pair up to about 1 km [41].

NFC/RFID and UWB

NFC operates at 13.56 MHz over a few centimetres and is standardised by ISO/IEC 18092 (NFCIP-1), which is compatible with the ISO/IEC 14443 proximity-card standard [42,43]. Its very short range is a security feature for payments, access control and "tap to pair" commissioning. UHF RFID (ISO/IEC 18000-63, the EPC Gen2 air interface) works at 860–960 MHz, letting a reader inventory hundreds of passive tags metres away for logistics and retail [44].

Ultra-wideband (UWB) uses very short pulses over channels at least 500 MHz wide. IEEE 802.15.4z (2020) enhanced the UWB PHYs with secure ranging, so devices can measure time of flight with centimetre-level accuracy, which enables digital car keys, indoor positioning and asset tracking [45,46]. The FiRa Consortium builds interoperability profiles on top of 802.15.4z [46].

4. Network protocols

IoT systems increasingly use the same Internet protocols as everything else, adapted where needed for constrained links. The IETF has defined a family of such adaptations (6LoWPAN, RPL, CoAP, DTLS profiles) so that "IP all the way to the sensor" is practical [4,12,19,49].

TCP/IP and UDP

TCP provides a reliable, ordered byte stream with flow and congestion control. A connection is opened with a three-way handshake (SYN, SYN-ACK, ACK) and every byte is acknowledged [8]. TCP suits protocols such as MQTT, HTTP/1.1 and Modbus TCP, but its handshake, retransmission timers and per-connection state cost energy and memory on small devices, and head-of-line blocking can delay fresh data behind lost old data [3,8].

UDP is connectionless; its header is only 8 bytes (source port, destination port, length, checksum) and it adds no reliability [7]. CoAP, DTLS, DNS, DHCP and QUIC are built on UDP and add whatever reliability they need themselves [10,12,50–52]. For a single small sensor reading, a UDP datagram avoids connection setup entirely, which is why constrained-network protocols favour it [12].

IPv4 and IPv6

IPv4 uses 32-bit addresses (about 4.3 billion) and a header of at least 20 bytes [53]. With billions of connected devices, IPv4 depends on network address translation (NAT), which breaks end-to-end reachability: a server cannot easily open a connection to a device behind NAT, so devices usually keep an outbound connection to a broker or cloud service. IPv6 uses 128-bit addresses, a fixed 40-byte header and extension headers, and requires every link to support an MTU of at least 1280 bytes [6]. Hosts can configure their own addresses with stateless address autoconfiguration (SLAAC), often forming the 64-bit interface identifier from the link-layer address [54,55].

6LoWPAN

IEEE 802.15.4 frames carry at most 127 bytes at the PHY [23], far below IPv6's 1280-byte minimum MTU [6]. 6LoWPAN (IPv6 over Low-Power Wireless Personal Area Networks) solves this with an adaptation layer that adds fragmentation and reassembly and header compression [4]. The IPHC scheme of RFC 6282 removes fields that can be inferred from the link layer or context (version, payload length, link-local prefixes, interface identifiers derived from MAC addresses) and also compresses UDP headers; in the best case a 40-byte IPv6 header shrinks to 2 bytes [5]. For LPWANs such as LoRaWAN and NB-IoT, whose frames are even smaller, the IETF defined SCHC (Static Context Header Compression), in which both ends share a pre-provisioned context describing the expected headers [18].

RPL: routing for low-power and lossy networks

RPL (pronounced "ripple") is the IETF's IPv6 routing protocol for low-power and lossy networks [19]. It builds a Destination-Oriented Directed Acyclic Graph (DODAG) rooted at a border router. The root sends DODAG Information Object (DIO) messages; each node computes a rank (its logical distance from the root) using an objective function and selects a preferred parent with a lower rank. Nodes can solicit DIOs with DIS messages and advertise reachability towards the root with Destination Advertisement Object (DAO) messages, enabling downward routes in storing or non-storing mode [19]. DIO transmission is paced by the Trickle algorithm, which sends rarely when the network is stable and quickly when inconsistencies appear [57]. A common objective function, MRHOF, minimises a path metric such as expected transmission count (ETX) with hysteresis to avoid parent flapping [58].

DNS and DHCP

The Domain Name System maps names to addresses [50]. Devices use it to locate cloud brokers (for example mqtt.example.com); a hard-coded IP address is fragile because it breaks when the service moves. On local networks without a DNS server, multicast DNS resolves names ending in .local [59] and DNS-SD advertises services such as _matter._tcp or _coap._udp using PTR, SRV and TXT records [47]. Matter uses DNS-SD for commissioning and operational discovery [31].

The Dynamic Host Configuration Protocol assigns IPv4 addresses and options (gateway, DNS servers, NTP) through a four-message DISCOVER, OFFER, REQUEST, ACK exchange, often remembered as "DORA" [51]. IPv6 networks can use SLAAC [54], DHCPv6 [60] or both. Reserving addresses by MAC address in DHCP is a simple way to keep stable addresses for devices that must be firewalled individually.

TLS and DTLS

TLS 1.3 secures TCP connections with a handshake that needs only one round trip before application data in the full case, and removes legacy algorithms; all its key-exchange modes provide forward secrecy except plain pre-shared-key (PSK) mode [9]. DTLS 1.3 provides equivalent protection over UDP, adding sequence numbers, retransmission timers and a cookie exchange against denial-of-service amplification [10]. RFC 7925 profiles both for IoT, recommending specific cipher suites and authentication options: pre-shared keys, raw public keys, or certificates, depending on the device's capabilities [49].

Mutual TLS (both client and server present certificates) is the most common way to authenticate devices to MQTT brokers and cloud platforms. Each device gets a unique key pair and certificate, so a single compromised device can be revoked without affecting others. NIST recommends that manufacturers give each device a unique identity and support secure updates [61]. Where a gateway or proxy terminates transport security, OSCORE protects CoAP messages end to end at the object level instead [62].

HTTP/HTTPS and WebSockets

HTTP is the request/response protocol of the web; its semantics (methods, status codes, headers) are defined independently of the version used on the wire [63]. It is ubiquitous, firewall-friendly and well tooled, so many cloud IoT APIs expose REST endpoints over HTTPS. Its drawbacks for devices are verbose text headers and the absence of server push in the request/response model. HTTP/3 runs over QUIC, a UDP-based transport with integrated TLS 1.3 that avoids TCP head-of-line blocking [52,64].

WebSockets start as an HTTP/1.1 request with Upgrade: websocket and then switch to a full-duplex, message-framed channel over the same TCP connection [65]. The server proves it understood the handshake by returning Sec-WebSocket-Accept, the Base64-encoded SHA-1 hash of the client's key concatenated with a fixed GUID [65]. WebSockets are how browser dashboards receive live IoT data, and both MQTT and CoAP define WebSocket bindings so they can traverse web infrastructure [11,66].

5. IoT messaging protocols

Messaging protocols sit at the application layer and decide how devices and services exchange data. Two interaction styles dominate. In request/response (HTTP, CoAP, Modbus, OPC UA client/server) a client asks and a server answers. In publish/subscribe (MQTT, AMQP via brokers, DDS, OPC UA PubSub) producers publish to named topics and consumers subscribe, so senders and receivers are decoupled in space and time [2]. Field and building protocols (Modbus, CAN, BACnet) predate the IoT but remain essential because millions of installed devices speak them [16,17,68].

MQTT

MQTT is a lightweight publish/subscribe protocol originally created by Andy Stanford-Clark (IBM) and Arlen Nipper in 1999 to monitor oil pipelines over satellite links [69]. Version 3.1.1 is an OASIS standard and ISO/IEC 20922 [70]; version 5.0 became an OASIS standard in March 2019 [11]. Clients connect over TCP (port 1883, or 8883 with TLS, as registered with IANA) or over WebSockets to a broker, which routes each published message to every client with a matching subscription [11,71].

Key concepts

  • Topics are UTF-8 strings with /-separated levels. Topic filters may contain the single-level wildcard + and the multi-level wildcard # [11].
  • Quality of Service. QoS 0 is "at most once" (fire and forget); QoS 1 is "at least once" (PUBLISH/PUBACK, duplicates possible); QoS 2 is "exactly once" using a four-step PUBLISH, PUBREC, PUBREL, PUBCOMP exchange [11].
  • Retained messages are stored by the broker and delivered immediately to new subscribers, so a dashboard sees the last known value at once [11].
  • Will message (Last Will and Testament): the broker publishes it on the client's behalf if the client disconnects without a clean DISCONNECT [11].
  • Keep alive and sessions: a persistent session lets the broker queue QoS 1/2 messages for an offline client [11].
  • MQTT 5 additions include reason codes on all acknowledgements, user properties, message and session expiry, topic aliases, shared subscriptions ($share/group/filter) for load balancing, and request/response correlation data [11].

The packet format is compact. Every packet begins with a fixed header of at least two bytes: a byte holding the packet type and flags, then the Remaining Length encoded as a variable byte integer of one to four bytes, where each byte carries seven bits of value and a continuation bit, allowing packets up to 268,435,455 bytes [11].

MQTT-SN

MQTT-SN (MQTT for Sensor Networks) adapts MQTT for non-TCP networks such as Zigbee or UDP over 6LoWPAN [74]. Its main changes are: topic names are replaced by 2-byte topic IDs (registered at run time, predefined, or two-character short names) to shrink every PUBLISH; a gateway translates between MQTT-SN and MQTT, and can be discovered with ADVERTISE, SEARCHGW and GWINFO messages; sleeping clients are supported, with the gateway buffering messages while they sleep; and a "QoS −1" mode lets very simple devices publish to predefined topics without even connecting [74].

CoAP

The Constrained Application Protocol (CoAP) is a specialised web transfer protocol for constrained nodes and networks: a compact, binary, RESTful protocol over UDP with GET, POST, PUT and DELETE methods, URIs and content types, so it maps easily to HTTP through proxies [12]. The fixed header is just 4 bytes: version (2 bits), type (2 bits), token length (4 bits), code (8 bits) and message ID (16 bits), followed by an optional token, options and a payload after a 0xFF marker [12].

  • Message types: Confirmable (CON, retransmitted until acknowledged), Non-confirmable (NON), Acknowledgement (ACK) and Reset (RST) [12].
  • Observe (RFC 7641): a client registers interest with a GET carrying the Observe option and the server sends notifications whenever the resource changes, which gives publish/subscribe behaviour without a broker [75].
  • Block-wise transfer (RFC 7959) splits large payloads such as firmware images into blocks [76].
  • Discovery: GET /.well-known/core returns the server's resources in CoRE Link Format [77].
  • Security: DTLS on port 5684 (coaps://), or OSCORE for end-to-end protection through proxies [12,62]. Plain CoAP uses UDP port 5683 [12].

AMQP

The Advanced Message Queuing Protocol (AMQP) 1.0 is an OASIS standard (2012) and ISO/IEC 19464 [79,80]. It is a binary, peer-to-peer wire protocol with a rich type system. Communication is organised into connections that carry multiplexed sessions, which in turn carry unidirectional links between nodes such as queues; message transfer is governed by credit-based flow control and explicit settlement that supports at-most-once and at-least-once delivery [79]. Unlike the older AMQP 0-9-1, version 1.0 does not prescribe a broker model of exchanges and queues, so it connects clients, brokers and cloud services alike [79]. In IoT, AMQP is typically used behind the device edge, between gateways, cloud ingestion services and enterprise systems, where its transactional and routing features matter more than header size. The IANA ports are 5672 (amqp) and 5671 (amqps) [71].

DDS

The Data Distribution Service (DDS), standardised by the Object Management Group, is a data-centric publish/subscribe middleware: applications read and write typed data samples in a shared "global data space", organised by topics within a domain [81]. There is no broker. Participants discover each other and exchange data peer to peer using the RTPS wire protocol, normally over UDP multicast and unicast [82]. DDS's distinctive strength is its set of QoS policies (reliability, durability, history depth, deadline, latency budget, liveliness, ownership and others), which let a designer state real-time requirements declaratively [81]. It is used in robotics, defence and autonomous vehicles; ROS 2, the Robot Operating System, uses DDS as its default middleware [83].

XMPP

The Extensible Messaging and Presence Protocol streams XML "stanzas" (<message/>, <presence/>, <iq/>) over long-lived TCP connections between clients and federated servers [84]. Entities are addressed by Jabber IDs of the form localpart@domain/resource; clients connect on TCP port 5222 and servers federate on 5269; TLS and SASL authentication are mandatory to implement [84]. Built-in presence (online/offline state) and federation are attractive for device-to-person scenarios, while XML's verbosity makes it heavier than MQTT or CoAP on constrained links.

OPC UA

OPC Unified Architecture (IEC 62541) is the leading interoperability standard for industrial automation [85]. It combines a communication stack with an information model: servers expose an address space of nodes (objects, variables, methods, types) connected by typed references, so a client can browse a machine and understand its semantics, not just read raw registers [85,86]. Services include Browse, Read, Write, Call and Subscriptions with monitored items that report data changes [86]. Security is built in: applications authenticate with X.509 application-instance certificates, and channels can be signed or signed and encrypted [85]. Besides client/server over the binary opc.tcp protocol (port 4840 registered with IANA [71]), Part 14 defines PubSub, which maps OPC UA data onto UDP multicast, MQTT or AMQP for one-to-many distribution [86].

Modbus

Modbus, introduced by Modicon in 1979, is a simple request/response protocol between a client (master) and servers (slaves) [68]. Its data model has four tables: coils (1-bit read/write), discrete inputs (1-bit read-only), input registers (16-bit read-only) and holding registers (16-bit read/write) [68]. A protocol data unit (PDU) is a function code plus data, at most 253 bytes; common function codes are 0x01 Read Coils, 0x03 Read Holding Registers (1 to 125 registers per request), 0x06 Write Single Register and 0x10 Write Multiple Registers. Errors are reported by setting the high bit of the function code and returning an exception code [68].

On serial lines (Modbus RTU over RS-485), the frame is a 1-byte server address, the PDU and a 16-bit CRC [15]. On Ethernet (Modbus TCP, port 502), the CRC is dropped and a 7-byte MBAP header is prepended: transaction identifier, protocol identifier (0), length and unit identifier [88]. Classic Modbus has no authentication or encryption, so it must be confined to protected network segments (see network segmentation) [89].

C · Modbus RTU CRC-16 (polynomial 0xA001, reflected)#include <stdint.h>
#include <stddef.h>

/* Returns the CRC; transmit the LOW byte first, then the HIGH byte. */
uint16_t modbus_crc16(const uint8_t *buf, size_t len)
{
    uint16_t crc = 0xFFFF;
    for (size_t i = 0; i < len; i++) {
        crc ^= buf[i];
        for (int b = 0; b < 8; b++)
            crc = (crc & 1) ? (crc >> 1) ^ 0xA001 : (crc >> 1);
    }
    return crc;
}
/* Request "read 10 holding registers from address 0 of server 1":
   01 03 00 00 00 0A  -> CRC 0xCDC5 -> frame 01 03 00 00 00 0A C5 CD */

CAN

The Controller Area Network was developed by Bosch for in-vehicle networks; CAN 2.0 was published in 1991 and the data link layer is standardised as ISO 11898-1 [16,91]. CAN is a multi-master serial bus on which every node can transmit. Frames carry an identifier (11-bit standard or 29-bit extended) that denotes the message content and its priority, not a destination address [91]. Arbitration is bitwise and non-destructive: a dominant bit (0) overrides a recessive bit (1) on the wire, so if two nodes start together, the one with the lower identifier wins and continues while the other backs off and retries [16,91]. Classical CAN carries up to 8 data bytes per frame; CAN FD, included in ISO 11898-1:2015, allows up to 64 bytes and a faster data phase [16]. Robust error detection (CRC, bit stuffing, acknowledgement, form checks) and fault confinement, in which a node that keeps causing errors eventually disconnects itself ("bus-off"), make CAN reliable in harsh environments [91]. Higher-layer protocols such as CANopen and SAE J1939 define application semantics on top.

BACnet

BACnet, the data communication protocol for building automation and control networks, is ANSI/ASHRAE Standard 135 and ISO 16484-5 [17,94]. It models every device as a collection of standard objects (Analog Input, Binary Output, Schedule, Trend Log and many others) whose properties are accessed through services such as ReadProperty, WriteProperty and SubscribeCOV (change of value), with Who-Is/I-Am for device discovery [17]. BACnet runs over several data links, most commonly BACnet/IP on UDP port 47808 (0xBAC0) and MS/TP over RS-485 for field controllers [17,71]. Because classic BACnet relies on network isolation for security, the standard added BACnet Secure Connect (BACnet/SC), which carries BACnet over TLS-secured WebSocket connections through hubs [17].

6. Network architectures

Topology determines range, resilience, latency and battery life. Classic wireless sensor network research already framed these trade-offs: sensor nodes are densely deployed, prone to failure and energy-limited, so topology and routing must adapt as nodes die or move [95].

Star topology

All nodes talk to a central hub: a Wi-Fi access point, a LoRaWAN gateway or a cellular base station. End devices are simple and can sleep because they never relay others' traffic, but the hub is a single point of failure and its radio range bounds coverage [24,32].

Mesh topology

Mains-powered nodes relay traffic for one another, extending coverage and routing around failures. Thread and Zigbee meshes self-heal when a router disappears [13,29]. The cost is relaying energy and multi-hop latency, which is why battery devices usually join as non-routing end devices.

Tree topology

A hierarchical structure in which each node has one parent. Zigbee defines a cluster-tree option with address-based tree routing [13], and RPL's DODAG is a tree-like graph optimised for many-to-one traffic towards a root [19]. Trees simplify routing but concentrate traffic near the root.

Point-to-point

A dedicated link between two endpoints: NFC between phone and tag, a BLE connection between a wearable and its phone, a serial line between a PLC and a meter [15,22,42]. Simple and secure by isolation, but it does not scale to many devices without a hub.

Cellular networks

Cellular IoT devices connect to base stations (eNB in LTE, gNB in 5G) operated by a mobile network operator, which provides wide-area coverage, mobility, SIM-based authentication and managed quality of service [35,36,38]. Private LTE/5G networks bring the same model to factories and ports, using 5G URLLC for time-critical control [37]. The architecture is a star at the radio level, but the operator's core network adds features such as power-saving timers negotiated with each device [36].

Wireless sensor networks (WSN)

A WSN is a collection of small, battery-powered nodes that sense their environment and cooperatively deliver data to one or more sinks [95]. Akyildiz and colleagues identified the design factors that still drive WSN design today: fault tolerance, scalability, production cost, hardware constraints, topology, environment, transmission media and power consumption [95]. Data aggregation inside the network (for example, sending only the average or maximum of a cluster) saves energy because radio transmission dominates a node's energy budget [95]. Modern WSNs commonly use IEEE 802.15.4, 6LoWPAN and RPL, with operating systems such as Contiki-NG [19,23,96].

Ad hoc networks

An ad hoc network forms without fixed infrastructure: nodes discover neighbours and route for each other. In mobile ad hoc networks (MANETs) the topology changes as nodes move, so routing protocols must react quickly while keeping control traffic low [97]. AODV is a classic reactive protocol: a route is discovered only when needed by flooding a Route Request and receiving a Route Reply, with sequence numbers to avoid loops [98]. Vehicle-to-vehicle, drone swarms and disaster-recovery sensor deployments are typical ad hoc IoT scenarios.

Software-defined networking (SDN)

SDN separates the control plane (deciding where traffic goes) from the data plane (forwarding packets). A logically centralised controller programs switches through a southbound API such as OpenFlow, and applications drive the controller through northbound APIs [99,100]. For IoT this enables dynamic policies: quarantining a misbehaving device, giving video cameras a separate path, or reconfiguring a factory network when a production line changes [100].

Network segmentation

IoT devices are attractive targets: they are numerous, often run outdated software and may ship with default credentials. The Mirai botnet of 2016 compromised hundreds of thousands of cameras, routers and DVRs largely by trying default Telnet passwords, and used them for record-breaking denial-of-service attacks [101]. Segmentation limits the damage a compromised device can do. IEC 62443-3-2 formalises it as zones (groups of assets with common security requirements) connected by conduits (controlled communication paths) [102], and NIST SP 800-82 recommends separating operational technology from IT networks with firewalls and demilitarised zones [89].

Practical measures include VLANs or separate SSIDs for IoT devices; firewall rules that allow only the flows a device needs (for example outbound TLS to its broker and nothing else); a DMZ for brokers and historians that both IT and OT must reach; and blocking device-to-device traffic unless it is required. Manufacturer Usage Description (MUD) files let a device announce the network access it needs so that the network can enforce matching policies automatically [103].

Exercise 1: Choosing a link technology

A city wants to monitor 5,000 parking spaces. Each sensor sends a 10-byte occupancy update when a car arrives or leaves (about 20 times a day), runs on a battery for 5+ years, and is embedded in asphalt, often under a car. Shortlist two technologies and justify the choice.

Solution

NB-IoT or LoRaWAN. Both are LPWAN technologies for small, infrequent payloads and multi-year battery life [21]. NB-IoT's 164 dB maximum coupling loss target suits sensors in difficult radio locations, and operator networks remove the need to install gateways [35]. LoRaWAN avoids subscription fees and lets the city run its own gateways; 20 short uplinks a day are well within European duty-cycle limits at moderate spreading factors [32,34]. Wi-Fi and BLE lack the range, and LTE-M is acceptable but optimised for higher rates and mobility that are not needed here [36].

Exercise 2: LoRa time on air and duty cycle

Using the Semtech time-on-air formula, compute the air time of a 20-byte payload at SF7 and at SF12 (BW = 125 kHz, coding rate 4/5, explicit header, CRC on, 8-symbol preamble; low-data-rate optimisation on for SF12). With a 1% duty cycle, what is the minimum interval between transmissions at SF12?

Solution

Symbol time Tsym = 2SF/BW; preamble time = (npreamble + 4.25)·Tsym; payload symbols = 8 + max(⌈(8PL − 4SF + 28 + 16·CRC − 20·IH) / (4(SF − 2DE))⌉·(CR + 4), 0) [48].

  • SF7: Tsym = 128/125,000 = 1.024 ms. Preamble = 12.25 × 1.024 = 12.54 ms. Payload symbols = 8 + ⌈(160 − 28 + 28 + 16)/28⌉ × 5 = 8 + 7 × 5 = 43, giving 44.03 ms. Total ≈ 56.6 ms.
  • SF12 (DE = 1): Tsym = 4096/125,000 = 32.768 ms. Preamble = 401.4 ms. Payload symbols = 8 + ⌈(160 − 48 + 28 + 16)/40⌉ × 5 = 8 + 4 × 5 = 28, giving 917.5 ms. Total ≈ 1.319 s.
  • With a 1% duty cycle, on-time/(on + off) ≤ 0.01, so the device must stay silent for 99 × 1.319 s ≈ 130.6 s: at most one uplink about every 2.2 minutes at SF12, versus about every 5.6 s at SF7 [34].

Exercise 3: Link budget

A LoRa transmitter outputs +14 dBm and the receiver sensitivity at SF12/125 kHz is about −137 dBm. Ignoring antenna gains and margins, what is the link budget, and what free-space distance would it allow at 868 MHz? Why are real ranges much shorter?

Solution

Link budget = 14 − (−137) = 151 dB (sensitivity figure from the transceiver datasheet [48]). Free-space basic transmission loss is L = 32.4 + 20 log10 f(MHz) + 20 log10 d(km) [106]. At 868 MHz, 20 log10 868 ≈ 58.8 dB, so 20 log10 d = 151 − 32.4 − 58.8 = 59.8, d ≈ 980 km. Real links are limited to a few kilometres in cities (more in open country) because buildings, terrain, vegetation, the curvature of the earth, interference and the need for fade margin add tens of dB of extra loss beyond free space [20,34].

Exercise 4: Header overhead

A sensor sends a 10-byte reading. Compare the network/transport header bytes for (a) IPv4 + UDP, (b) IPv4 + TCP (no options, excluding the handshake), (c) uncompressed IPv6 + UDP and (d) 6LoWPAN IPHC + NHC best case.

Solution
  • (a) 20 + 8 = 28 bytes of headers for 10 bytes of data [7,53].
  • (b) 20 + 20 = 40 bytes, plus SYN/SYN-ACK/ACK and teardown packets on a new connection [8,53].
  • (c) 40 + 8 = 48 bytes [6,7].
  • (d) In the best case 2 bytes of IPHC, plus a 1-byte UDP NHC header, 1 byte of compressed ports and the 2-byte checksum: about 6 bytes [5]. This is why 6LoWPAN makes IPv6 practical over 127-byte frames.

Exercise 6: MQTT Remaining Length encoding

Encode the Remaining Length value 321 as an MQTT variable byte integer.

Solution

321 = 2 × 128 + 65. First byte: 65 with the continuation bit set, 65 + 128 = 193 = 0xC1. Second byte: 2 = 0x02. The encoding is C1 02 [11]. Check: (0xC1 & 0x7F) + 0x02 × 128 = 65 + 256 = 321.

Exercise 7: Modbus frame

Write the complete Modbus RTU request that reads 10 holding registers starting at address 0 from server 1, and the equivalent Modbus TCP request with transaction ID 0x0001.

Solution

PDU: function 0x03, start address 0x0000, quantity 0x000A [68].

RTU: 01 03 00 00 00 0A C5 CD: address 01, the PDU, then the CRC 0xCDC5 sent low byte first [15].

TCP: 00 01 00 00 00 06 01 03 00 00 00 0A: transaction 0x0001, protocol 0x0000, length 6 (unit ID + 5-byte PDU), unit 0x01, then the PDU, with no CRC [88].

Exercise 8: CAN arbitration

Three nodes start transmitting simultaneously with standard identifiers 0x123, 0x0F0 and 0x0F8. Which wins, and at which bit does each loser drop out?

Solution

In binary (11 bits): 0x123 = 001 0010 0011, 0x0F0 = 000 1111 0000, 0x0F8 = 000 1111 1000. At bit 3 (counting from the most significant bit as 1), 0x123 sends recessive 1 while the others send dominant 0, so 0x123 loses there. 0x0F0 and 0x0F8 are identical until bit 8, where 0x0F8 sends 1 and 0x0F0 sends 0, so 0x0F0 wins. The lowest identifier always wins, and the winner's frame is not corrupted [16,91].

Exercise 9: IPv6 link-local address

Derive the EUI-64 based link-local IPv6 address of a device with MAC B8:27:EB:12:34:56.

Solution

Insert FF:FE in the middle: B8:27:EB:FF:FE:12:34:56. Flip the universal/local bit (0x02) of the first byte: 0xB8 XOR 0x02 = 0xBA. Result: fe80::ba27:ebff:fe12:3456 [55].

Exercise 10: Segment a smart building

A building has IP cameras, BACnet/IP HVAC controllers, Zigbee lighting via a gateway, staff laptops and a cloud-connected analytics service. Propose zones and the conduits between them.

Solution (one reasonable design)
  • Zones: (1) corporate IT (laptops); (2) cameras VLAN; (3) building automation VLAN (BACnet/IP controllers, Zigbee gateway); (4) IoT DMZ (video recorder, BACnet supervisory server, MQTT/HTTPS gateway to the cloud).
  • Conduits: cameras → video recorder only (RTSP/HTTPS); BACnet controllers ↔ supervisory server on UDP 47808 only; the DMZ gateway → cloud on outbound TLS 443/8883 only; IT → DMZ web UIs over HTTPS with authentication; no route from IT or the Internet directly into the camera or BACnet VLANs.
  • Rationale: BACnet/IP and many cameras have weak native security, so isolation and allow-listing per IEC 62443 zones and conduits contain a compromise [17,89,102]. If the devices support it, migrate to BACnet/SC and use MUD to automate the camera policies [17,103].

Exercise 11: Protocol choice for a robot fleet

A warehouse runs 40 autonomous robots that share position at 50 Hz with each other on a local network, and also send hourly summaries to a cloud dashboard. Which protocols would you use?

Solution

Use DDS (for example via ROS 2) locally: it is brokerless, discovers peers automatically and offers QoS policies such as best-effort reliability and history depth 1 for high-rate state data [81,83]. A gateway then publishes summaries to the cloud over MQTT over TLS (or AMQP into an enterprise system), because DDS multicast discovery is not designed to cross the Internet and MQTT's broker model fits device-to-cloud traffic [11,79].

Key takeaways

  • Pick the link from the use case: range, data rate, energy, mobility, cost and whether you want to run infrastructure yourself [20,21].
  • IPv6 with 6LoWPAN and RPL brings end-to-end IP to tiny radios; Thread and Matter build interoperable smart homes on that foundation [4,19,29,30].
  • MQTT dominates device-to-cloud telemetry, CoAP serves constrained REST, DDS serves real-time peer-to-peer data, and OPC UA, Modbus, CAN and BACnet remain the languages of industry, vehicles and buildings [11,12,16,17,68,81,85].
  • Secure every layer: unique device identities, TLS/DTLS, least-privilege topic ACLs, and segmentation into zones and conduits [49,61,102].
