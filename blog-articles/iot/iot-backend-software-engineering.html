1 Introduction: what an IoT backend actually does

An Internet of Things (IoT) system couples constrained physical devices to software that stores, analyses and acts on what those devices report. Surveys of the field describe a layered stack: a perception (device) layer, a network layer, and a middleware/application layer where data is aggregated, processed and exposed to users [1]. This article is about that last layer, the backend and the frontend that sits on top of it. It is the part of an IoT product that looks most like conventional distributed-systems software, but it has to cope with conditions that ordinary web backends rarely face all at once:

  • Many long-lived, intermittently connected clients. Devices sit behind cellular or low-power links and come and go; the backend must hold state on their behalf (the "device shadow" or "twin" idea) [2,3].
  • Write-heavy, append-mostly data. Telemetry is a stream of timestamped measurements, a workload that motivated dedicated time-series engines [4].
  • Unreliable delivery. Messages arrive late, out of order and sometimes twice, so the backend must be designed around delivery guarantees and idempotent processing rather than assuming them away [5–7].
  • Control flows back to the physical world. A command to open a valve has real consequences, so authorization, auditing and confirmation matter more than in a typical CRUD app [8].

Some processing is pushed towards the network edge ("fog computing") to cut latency and bandwidth [9]; the patterns below apply whether the backend runs in a cloud region, an on-premises cluster or an edge gateway.

2 Backend development

2.1 REST APIs

Representational State Transfer (REST) was defined by Roy Fielding in his 2000 doctoral dissertation as an architectural style built from constraints: client–server, statelessness, cacheability, a uniform interface, a layered system and optional code-on-demand [10]. In practice, an IoT REST API exposes resources such as devices, telemetry series, commands and firmware images, and manipulates them with the HTTP methods whose semantics are defined in RFC 9110 [11].

Several HTTP features map directly onto IoT problems:

And an implementation sketch in TypeScript with Express, showing optimistic concurrency, merge patch and RFC 9457 errors:

src/routes/config.ts
import express from "express";
import { createHash } from "node:crypto";
import { db } from "../db";          // thin wrapper around pg.Pool

export const router = express.Router();

const etagOf = (version: number) => `"v${version}"`;

const problem = (res: express.Response, status: number, title: string, detail?: string) =>
  res.status(status).type("application/problem+json").json({ type: "about:blank", title, status, detail });

router.get("/devices/:id/config", async (req, res) => {
  const row = await db.one("SELECT desired, version FROM device_config WHERE device_id=$1", [req.params.id]);
  if (!row) return problem(res, 404, "Device not found");
  res.set("ETag", etagOf(row.version)).json(row.desired);
});

// RFC 7396 JSON Merge Patch: null deletes a key, objects merge recursively
function mergePatch(target: any, patch: any): any {
  if (patch === null || typeof patch !== "object" || Array.isArray(patch)) return patch;
  const out = (target && typeof target === "object" && !Array.isArray(target)) ? { ...target } : {};
  for (const [k, v] of Object.entries(patch)) {
    if (v === null) delete out[k]; else out[k] = mergePatch(out[k], v);
  }
  return out;
}

router.patch("/devices/:id/config", express.json({ type: "application/merge-patch+json" }), async (req, res) => {
  const ifMatch = req.get("If-Match");
  if (!ifMatch) return problem(res, 428, "Precondition Required", "Send If-Match with the ETag you read");
  const expected = Number(ifMatch.replace(/"v?/g, ""));

  const updated = await db.tx(async t => {
    const cur = await t.one("SELECT desired, version FROM device_config WHERE device_id=$1 FOR UPDATE", [req.params.id]);
    if (!cur) return null;
    if (cur.version !== expected) return "conflict" as const;
    const next = mergePatch(cur.desired, req.body);
    return t.one(
      "UPDATE device_config SET desired=$2, version=version+1, updated_at=now() WHERE device_id=$1 RETURNING desired, version",
      [req.params.id, next]);
  });

  if (updated === null) return problem(res, 404, "Device not found");
  if (updated === "conflict") return problem(res, 412, "Precondition Failed", "Config changed since you read it");
  res.set("ETag", etagOf(updated.version)).json(updated.desired);
});

Status 428 Precondition Required is defined in RFC 6585 [12]; 412 and the If-Match semantics are in RFC 9110 [11].

2.2 WebSocket APIs

REST is request/response. Dashboards and some gateways need the server to push. The WebSocket protocol (RFC 6455, December 2011) upgrades an HTTP/1.1 connection to a full-duplex, message-framed channel over a single TCP connection [16]. The opening handshake is an HTTP GET with Upgrade: websocket; the server proves it understood by returning Sec-WebSocket-Accept, the base64 SHA-1 of the client key concatenated with the fixed GUID 258EAFA5-E914-47DA-95CA-C5AB0DC85B11 [16]. Frames from client to server must be masked; frames from server to client must not be [16]. RFC 8441 later defined how to run WebSockets over HTTP/2 streams using extended CONNECT [17].

WebSocket gives you a pipe, not a protocol, so you must design your own message envelope, subscription model, authentication and back-pressure. A minimal, production-shaped server with the popular ws library:

src/ws-server.ts
import { WebSocketServer, WebSocket } from "ws";
import http from "node:http";
import { verifyAccessToken } from "./auth";       // validates JWT (see 2.4)
import { bus } from "./bus";                       // internal pub/sub fed from Kafka or Redis

type ClientMsg =
  | { op: "sub"; deviceIds: string[] }
  | { op: "unsub"; deviceIds: string[] }
  | { op: "ping" };

const server = http.createServer();
const wss = new WebSocketServer({ noServer: true, maxPayload: 64 * 1024 });

server.on("upgrade", async (req, socket, head) => {
  // Browsers cannot set Authorization on a WebSocket, so use a short-lived token in a subprotocol or query
  const token = new URL(req.url!, "http://x").searchParams.get("access_token");
  const claims = token && await verifyAccessToken(token).catch(() => null);
  if (!claims) { socket.write("HTTP/1.1 401 Unauthorized\r\n\r\n"); return socket.destroy(); }
  wss.handleUpgrade(req, socket, head, ws => wss.emit("connection", ws, claims));
});

wss.on("connection", (ws: WebSocket, claims: { sub: string; tenant: string }) => {
  const subs = new Set<string>();
  const onTelemetry = (evt: { deviceId: string; tenant: string }) => {
    if (evt.tenant !== claims.tenant || !subs.has(evt.deviceId)) return;
    // back-pressure: drop for this client if it is falling behind instead of buffering forever
    if (ws.bufferedAmount > 1_000_000) return;
    ws.send(JSON.stringify({ type: "telemetry", data: evt }));
  };
  bus.on("telemetry", onTelemetry);

  ws.on("message", raw => {
    let msg: ClientMsg;
    try { msg = JSON.parse(raw.toString()); } catch { return ws.close(1003, "bad json"); }
    if (msg.op === "sub") msg.deviceIds.slice(0, 500).forEach(d => subs.add(d));
    else if (msg.op === "unsub") msg.deviceIds.forEach(d => subs.delete(d));
    else if (msg.op === "ping") ws.send(JSON.stringify({ type: "pong", t: Date.now() }));
  });

  // heartbeat: detect half-open TCP connections
  let alive = true;
  ws.on("pong", () => (alive = true));
  const hb = setInterval(() => { if (!alive) return ws.terminate(); alive = false; ws.ping(); }, 30_000);
  ws.on("close", () => { clearInterval(hb); bus.off("telemetry", onTelemetry); });
});

server.listen(8080);

Close code 1003 ("unsupported data") and the ping/pong control frames are defined in RFC 6455 §7.4.1 and §5.5.2–5.5.3 [16]. Browsers expose WebSockets through the WebSocket interface, which has no API for custom request headers [18], hence the token-in-URL pattern; keep such tokens short-lived and keep them out of access logs.

For describing asynchronous, message-driven APIs (WebSocket, MQTT, Kafka channels) the AsyncAPI specification plays the role that OpenAPI plays for HTTP [19].

2.3 Device management APIs

Device management covers the device lifecycle: registration, inventory and metadata, state, configuration, firmware updates, diagnostics and decommissioning. Two well-known designs are worth knowing:

  • OMA LwM2M models a device as a tree of numbered Objects, Instances and Resources (for example, Object 3 is "Device", Object 5 is "Firmware Update") and defines operations such as Read, Write, Execute and Observe over CoAP [20,21]. Version 1.2 added MQTT and HTTP transports [20].
  • Shadow / twin documents. AWS IoT's Device Shadow and Azure IoT Hub's device twin both keep a JSON document with a desired section (what the cloud wants) and a reported section (what the device last said), plus version numbers; the service computes a delta and pushes it to the device when it reconnects [2,3].
src/shadow/delta.ts
// Compute the delta between desired and reported, recursively, like a device shadow service.
export type Json = null | boolean | number | string | Json[] | { [k: string]: Json };

export function delta(desired: Json, reported: Json): Json | undefined {
  if (isObj(desired) && isObj(reported)) {
    const out: Record<string, Json> = {};
    for (const k of Object.keys(desired)) {
      const d = delta(desired[k], (reported as any)[k]);
      if (d !== undefined) out[k] = d;
    }
    return Object.keys(out).length ? out : undefined;
  }
  return JSON.stringify(desired) === JSON.stringify(reported) ? undefined : desired;
}
const isObj = (x: Json): x is { [k: string]: Json } => !!x && typeof x === "object" && !Array.isArray(x);

2.4 Authentication and authorization

There are two very different populations of clients: humans and services (operators, dashboards, integrations) and devices. They need different mechanisms.

ClientTypical authenticationAuthorization
DeviceMutual TLS with a per-device X.509 certificate [22,23]; on very constrained links, pre-shared keysTopic ACLs keyed on the certificate identity, e.g. a device may only publish to t/{tenant}/{deviceId}/# [24]
Operator in a browserOAuth 2.0 authorization code flow via an identity provider [25]Roles/scopes in a JWT access token [26]
Input-limited device with a screen (TV, kiosk)OAuth 2.0 device authorization grant: the device shows a code, the user approves on a phone [27]Scopes
Backend serviceOAuth 2.0 client credentials, optionally mTLS-bound tokens [25,28]Scopes, service identity

JWTs are compact signed claim sets [26]; RFC 8725 lists the pitfalls that matter in practice: pin the accepted algorithms (never accept alg: none unless intended), validate issuer and audience, and use explicit typing [29]. NIST's zero-trust architecture guidance argues for authenticating and authorizing every request rather than trusting network location [30], which is a good default for IoT backends whose devices sit on untrusted networks.

src/auth.ts
import { createRemoteJWKSet, jwtVerify } from "jose";

const JWKS = createRemoteJWKSet(new URL("https://idp.example.com/.well-known/jwks.json"));

export async function verifyAccessToken(token: string) {
  const { payload } = await jwtVerify(token, JWKS, {
    issuer: "https://idp.example.com/",
    audience: "iot-api",
    algorithms: ["RS256", "ES256"],   // RFC 8725 §3.1: pin algorithms
    typ: "at+jwt",                     // explicit typing, RFC 8725 §3.11
    clockTolerance: 30,
  });
  return payload as { sub: string; tenant: string; scope: string };
}

// Express middleware: require a scope, e.g. requireScope("devices:command")
export const requireScope = (scope: string) => async (req: any, res: any, next: any) => {
  try {
    const tok = (req.get("Authorization") ?? "").replace(/^Bearer /, "");
    const claims = await verifyAccessToken(tok);
    if (!claims.scope.split(" ").includes(scope)) return res.status(403).end();
    req.user = claims; next();
  } catch { res.status(401).set("WWW-Authenticate", 'Bearer realm="iot"').end(); }
};

2.5 Device provisioning services

Provisioning is how a device gets from "box on a pallet" to "trusted member of a tenant". It answers: who is this device, which customer owns it, which hub or broker should it talk to, and what credential should it use from now on? Common patterns:

  1. Factory-injected certificate. Each device gets a unique key pair (ideally generated inside a secure element) and a certificate signed by the manufacturer CA; the cloud trusts that CA. The X.509 profile is RFC 5280 [23].
  2. Claim / bootstrap certificate, then exchange. Devices ship with a shared, low-privilege claim credential, connect once, submit a certificate signing request and receive a unique certificate. AWS IoT calls this "fleet provisioning by claim" [31].
  3. Enrollment groups and allocation policies. Azure's Device Provisioning Service (DPS) matches a device's attestation (X.509, TPM or symmetric key) to an enrollment and assigns it to one of several IoT hubs according to a policy such as lowest latency or even distribution [32].
  4. Standards-based enrollment. EST (RFC 7030) defines certificate enrollment over HTTPS [33]; BRSKI (RFC 8995) lets a device with a manufacturer-installed identity (IDevID) securely join an owner's network with no human typing credentials [34].
provisioning/handler.py
"""Provisioning endpoint: verifies the claim, signs the CSR, registers the device."""
from cryptography import x509
from cryptography.x509.oid import NameOID
from cryptography.hazmat.primitives import hashes
import datetime, uuid

def provision(serial: str, csr_pem: bytes, claim_cert_fp: str, ca_key, ca_cert, db):
    if not db.claim_cert_allowed(claim_cert_fp):
        raise PermissionError("unknown claim certificate")
    enrollment = db.find_enrollment(serial)            # pre-registered by the factory or customer
    if enrollment is None or enrollment.status != "pending":
        raise PermissionError("serial not enrolled or already provisioned")

    csr = x509.load_pem_x509_csr(csr_pem)
    if not csr.is_signature_valid:
        raise ValueError("CSR signature invalid")

    device_id = f"dev-{uuid.uuid4()}"
    now = datetime.datetime.now(datetime.timezone.utc)
    cert = (x509.CertificateBuilder()
            .subject_name(x509.Name([x509.NameAttribute(NameOID.COMMON_NAME, device_id)]))
            .issuer_name(ca_cert.subject)
            .public_key(csr.public_key())               # device's own key, generated on-device
            .serial_number(x509.random_serial_number())
            .not_valid_before(now)
            .not_valid_after(now + datetime.timedelta(days=365 * 2))
            .add_extension(x509.BasicConstraints(ca=False, path_length=None), critical=True)
            .sign(ca_key, hashes.SHA256()))

    with db.transaction():
        db.insert_device(device_id, serial, enrollment.tenant_id,
                         cert.fingerprint(hashes.SHA256()).hex())
        db.mark_enrollment_used(serial)
    return {"deviceId": device_id, "certificate": cert.public_bytes(serialization_pem()),
            "endpoint": enrollment.broker_endpoint}

def serialization_pem():
    from cryptography.hazmat.primitives.serialization import Encoding
    return Encoding.PEM

2.6 Configuration management

Configuration (sampling interval, thresholds, feature flags, network settings) is desired state. Treat it declaratively: store a versioned document per device or per group, let devices pull or receive a delta, and have them report the version they applied. Good practice:

  • Layering. Effective config = fleet defaults ⊕ model-specific ⊕ group ⊕ device overrides, merged with JSON Merge Patch semantics [14].
  • Versioning and concurrency. Monotonic version numbers per document; ETag/If-Match on writes [11]; devices ignore deltas whose version is older than the one they hold (shadow services expose exactly such a version field [2]).
  • Validation before rollout. Validate against a JSON Schema in the API, then roll out to a canary group before the whole fleet.
  • Audit. Keep every version, who changed it, and when; NIST's baseline for IoT manufacturers lists device configuration and logging among the core capabilities a product should support [8].
schema/config.sql (PostgreSQL)
CREATE TABLE config_layer (
  scope        text    NOT NULL CHECK (scope IN ('fleet','model','group','device')),
  scope_id     text    NOT NULL,
  doc          jsonb   NOT NULL,
  version      integer NOT NULL DEFAULT 1,
  updated_by   text    NOT NULL,
  updated_at   timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (scope, scope_id)
);

CREATE TABLE config_history (LIKE config_layer, changed_at timestamptz NOT NULL DEFAULT now());

CREATE FUNCTION config_audit() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  INSERT INTO config_history SELECT OLD.*, now();
  RETURN NEW;
END $$;
CREATE TRIGGER trg_config_audit BEFORE UPDATE ON config_layer
  FOR EACH ROW EXECUTE FUNCTION config_audit();

jsonb stores JSON in a decomposed binary form that supports indexing and containment operators [35].

2.7 Command-and-control services

Commands ("reboot", "open valve", "start firmware update") are the riskiest traffic in an IoT system. A command service should treat each command as a durable entity with a state machine, not as a fire-and-forget message:

  • Idempotency keys. The API takes an Idempotency-Key header so a retried POST does not create two commands; an IETF draft standardises this header [36], and the underlying principle is that retried messages must be safe to process again [6].
  • Expiry. A "turn on heater" issued yesterday should not execute when the device reconnects tomorrow. MQTT 5 supports a per-message Message Expiry Interval [5].
  • Request/response correlation. MQTT 5 adds Response Topic and Correlation Data properties precisely for request/response over publish/subscribe [5].
  • Two-person rule and confirmation for dangerous commands, enforced server-side, not just in the UI.
src/commands/send.ts
import mqtt from "mqtt";
import { randomUUID } from "node:crypto";
import { db } from "../db";

const client = mqtt.connect("mqtts://broker.internal:8883", { protocolVersion: 5, clientId: "cmd-svc-1" });

export async function sendCommand(tenant: string, deviceId: string, name: string, args: object,
                                  idemKey: string, ttlSec = 300) {
  // Insert-or-return-existing makes the API idempotent per (tenant, idemKey)
  const cmd = await db.one(`
    INSERT INTO command (id, tenant, device_id, name, args, idem_key, status, expires_at)
    VALUES ($1,$2,$3,$4,$5,$6,'QUEUED', now() + make_interval(secs => $7))
    ON CONFLICT (tenant, idem_key) DO UPDATE SET idem_key = EXCLUDED.idem_key
    RETURNING *`, [randomUUID(), tenant, deviceId, name, args, idemKey, ttlSec]);

  if (cmd.status !== "QUEUED") return cmd;                    // already sent earlier

  client.publish(`devices/${deviceId}/commands/${cmd.id}`, JSON.stringify({ name, args }), {
    qos: 1,
    properties: {
      messageExpiryInterval: ttlSec,                          // broker drops it if undelivered in time
      responseTopic: `devices/${deviceId}/commands/${cmd.id}/ack`,
      correlationData: Buffer.from(cmd.id),
    },
  }, async err => {
    await db.none("UPDATE command SET status=$2, updated_at=now() WHERE id=$1 AND status='QUEUED'",
                  [cmd.id, err ? "FAILED" : "SENT"]);
  });
  return cmd;
}

2.8 Event-driven architecture

In an event-driven architecture, services communicate by emitting facts ("device.telemetry.received", "alert.raised") rather than calling each other synchronously. Producers do not know their consumers, which decouples teams and lets new consumers (an ML feature pipeline, a billing meter) be added without changing the producer [37,38]. IoT systems are naturally event-driven because the devices themselves are event sources.

A consistent envelope pays off. CloudEvents is a CNCF specification for describing event data in a common way, with required attributes id, source, specversion and type [39]:

telemetry event as a CloudEvent
{
  "specversion": "1.0",
  "id": "0193b1e4-7c1a-7a3e-9f2b-5d7c1e0a9b11",
  "source": "/tenants/acme/devices/dev-42",
  "type": "com.example.telemetry.v1",
  "time": "2026-11-15T08:41:07.215Z",
  "datacontenttype": "application/json",
  "subject": "dev-42",
  "data": { "seq": 98121, "tempC": 21.7, "rh": 44.0, "battery": 0.82 }
}

The id here is a UUIDv7, whose leading bits are a Unix-epoch millisecond timestamp, so ids sort roughly by creation time [40]; the timestamp format is RFC 3339 [41].

One trap in event-driven systems is the dual write: a service updates its database and then publishes an event, and crashes in between. The transactional outbox pattern writes the event into an outbox table in the same database transaction, and a separate relay publishes it [42]:

outbox pattern (PostgreSQL)
BEGIN;
  UPDATE device SET status = 'offline', status_changed_at = now() WHERE id = 'dev-42';
  INSERT INTO outbox (id, aggregate_id, type, payload)
  VALUES (gen_random_uuid(), 'dev-42', 'device.status.changed',
          '{"deviceId":"dev-42","status":"offline"}');
COMMIT;
-- A relay process (or a change-data-capture connector) reads the outbox in order,
-- publishes to Kafka, then marks rows as sent. Consumers must still be idempotent,
-- because the relay can publish a row more than once if it crashes after publishing.

2.9 Microservices

Lewis and Fowler characterised microservices as suites of small services, each running in its own process, organised around business capabilities, independently deployable, and owning their own data [43]. In IoT, a typical decomposition is: device registry, provisioning, ingestion, telemetry query, rules/alerting, command, firmware (OTA), notification and tenant/billing.

2.10 Serverless computing

Serverless (Functions-as-a-Service) runs short, stateless functions in response to events, with the provider handling provisioning and scaling and billing per invocation [45,46]. The Berkeley view of serverless highlights the trade-offs: excellent elasticity and no idle cost, but limited execution time, no direct addressing between functions, and cold-start latency [46]. That makes serverless a good fit for bursty, per-message work such as enrichment, notifications, webhooks and lightweight rules, and a poor fit for long-lived connections or stateful stream joins.

A message broker is an intermediary that accepts messages from producers and routes them to consumers, decoupling the two in space (they need not know each other's address), time (they need not be online together) and rate (the broker buffers bursts) [37]. Three delivery shapes recur:

3.2 MQTT brokers: Mosquitto, EMQX and HiveMQ

MQTT is a lightweight publish/subscribe protocol standardised by OASIS; version 3.1.1 was also published as ISO/IEC 20922:2016 [53], and version 5.0 became an OASIS Standard in March 2019 [5]. Key features for backend engineers:

  • QoS levels. 0 = at most once, 1 = at least once (PUBLISH/PUBACK), 2 = exactly once between two hops (PUBLISH/PUBREC/PUBREL/PUBCOMP) [5].
  • Sessions. With Clean Start = 0 and a Session Expiry Interval, the broker keeps subscriptions and queued QoS 1/2 messages for a disconnected client [5].
  • Retained messages. The broker stores the last retained message on a topic and sends it to new subscribers immediately, which is ideal for "current status" topics [5].
  • Last Will and Testament. A message the broker publishes on the client's behalf if it disconnects ungracefully, the standard way to detect devices going offline [5].
  • MQTT 5 additions. Reason codes on every ack, user properties, topic aliases, message expiry, request/response properties and shared subscriptions [5].

3.3 Event streaming and Apache Kafka

Kafka was built at LinkedIn and described in 2011 as a distributed messaging system for log processing, combining the throughput of log aggregators with a messaging API [49]. Its core abstraction is the topic, split into partitions, each an ordered, immutable sequence of records identified by an offset [50]. Records are retained for a configured time or size regardless of whether they have been consumed, so new consumers can replay history [50]. Partitions are replicated; a producer with acks=all waits until all in-sync replicas have the record [50]. Since Kafka 4.0, clusters run in KRaft mode, with Kafka's own Raft-based controller quorum replacing ZooKeeper [50].

Event streaming differs from a queue: consuming a record does not delete it, and each consumer group stores its own position. That is what lets the same telemetry topic feed a real-time alerting job, a TimescaleDB sink and a nightly data-lake export independently. Stream processors such as Apache Flink add windowing, joins and state on top of these streams [57], and the Dataflow model gives the vocabulary (event time vs processing time, windows, watermarks, triggers) needed for out-of-order IoT data [7].

A consumer that writes to a database, commits offsets only after the write, and tolerates replays:

sink/kafka_to_timescale.py
from confluent_kafka import Consumer, KafkaException
import json, psycopg

consumer = Consumer({
    "bootstrap.servers": "kafka:9092",
    "group.id": "timescale-sink",
    "enable.auto.commit": False,          # commit manually, after the DB write succeeds
    "auto.offset.reset": "earliest",
    "isolation.level": "read_committed",  # skip records from aborted transactions
})
consumer.subscribe(["telemetry.raw"])

conn = psycopg.connect("postgresql://ingest@timescale/iot", autocommit=False)

UPSERT = """
INSERT INTO telemetry (device_id, ts, seq, temp_c, rh, battery)
VALUES (%(device_id)s, %(ts)s, %(seq)s, %(tempC)s, %(rh)s, %(battery)s)
ON CONFLICT (device_id, ts, seq) DO NOTHING          -- replay-safe: duplicates are ignored
"""

try:
    while True:
        batch = consumer.consume(num_messages=500, timeout=1.0)
        if not batch:
            continue
        rows = []
        for m in batch:
            if m.error():
                raise KafkaException(m.error())
            r = json.loads(m.value())
            r["device_id"] = m.key().decode()
            rows.append(r)
        with conn.cursor() as cur:
            cur.executemany(UPSERT, rows)
        conn.commit()                                   # 1) data durable
        consumer.commit(asynchronous=False)             # 2) then advance offsets
finally:
    consumer.close()

If the process dies between step 1 and step 2, the batch is consumed again after restart; the ON CONFLICT DO NOTHING clause [58] makes that harmless. This is the at-least-once + idempotent sink pattern, the workhorse of IoT pipelines.

3.4 RabbitMQ

RabbitMQ is a broker originally built around AMQP 0-9-1, in which producers publish to exchanges that route messages to queues by binding rules; exchange types are direct, fanout, topic and headers [51]. It also supports AMQP 1.0, the OASIS-standard messaging protocol [60], and MQTT through a plugin. For durability RabbitMQ recommends quorum queues, a replicated queue type based on the Raft consensus algorithm [61]. Reliability rests on two mechanisms [48]:

  • Publisher confirms: the broker acknowledges to the publisher once it has taken responsibility for a message.
  • Consumer acknowledgements: the broker removes a message only after the consumer acks it; if the channel closes first, the message is requeued and redelivered with the redelivered flag set.

RabbitMQ fits IoT command fan-out, firmware-job work queues and integration tasks. A worker with manual acks, a prefetch limit and a dead-letter exchange for poison messages [62]:

3.5 Message persistence

Persistence answers: if the broker restarts, what survives? The answers differ by system:

  • MQTT: the standard defines what session state the server must keep (subscriptions, unacknowledged QoS 1/2 messages, queued messages for offline clients, retained messages) but not how it is stored; brokers persist to disk or to a cluster store [5,24]. Mosquitto writes an in-memory database to disk when persistence true is set [24].
  • RabbitMQ: durable queues plus persistent messages (delivery mode 2) survive restarts; quorum queues replicate to a majority before confirming [52,61].
  • Kafka: every record is written to a partition log on disk and replicated; durability is tuned with replication factor, min.insync.replicas and producer acks [50].

3.6 Message acknowledgment

An acknowledgement transfers responsibility for a message. Where the ack happens relative to the work decides the guarantee:

Ack timingCrash after ack, before workCrash after work, before ackResult
Ack first, then processMessage lostn/aAt most once
Process first, then ackn/aMessage redeliveredAt least once (needs idempotent processing)

Kafka expresses the same choice through when offsets are committed [50]; RabbitMQ through manual vs automatic acknowledgement mode [48]; MQTT through when the client sends PUBACK [5].

3.7 Delivery guarantees

At most once never duplicates but may lose; at least once never loses but may duplicate; exactly once is achievable only within a closed system. Kafka's exactly-once semantics combine idempotent producers with transactions that atomically write output records and consumer offsets, so a read-process-write loop inside Kafka has its effects applied once [50,59]. As soon as the side effect leaves Kafka (a database write, an SMS, a valve opening) you are back to at-least-once delivery plus idempotent effects, which is why Helland argues that idempotence must be designed into the application itself [6]. MQTT's QoS 2 is exactly-once on a single client–broker hop [5].

Rule of thumb. End-to-end "exactly once" = at-least-once delivery + idempotent processing + deduplication keyed on a stable message identity. Build all three.

3.8 Duplicate message handling

Duplicates come from publisher retries, QoS 1 redelivery, consumer restarts before commit, bridge failover and device firmware that re-sends unacknowledged batches. The idempotent receiver pattern [37] needs a stable identity for each message, assigned at the source:

  • Best: (deviceId, seq) where seq is a per-device monotonically increasing counter persisted in device flash.
  • Good: an event UUID created on the device (UUIDv7 gives you time ordering too [40]).
  • Fallback: (deviceId, timestamp), safe only if the device can never emit two readings with the same timestamp.
  • Avoid: a hash of the payload, because two genuine identical readings would be collapsed.

Three implementation strategies, from strongest to cheapest:

1. Unique constraint in the target store (strongest)
-- Natural idempotency: the write itself rejects duplicates.
ALTER TABLE telemetry ADD CONSTRAINT telemetry_uniq UNIQUE (device_id, ts, seq);
INSERT INTO telemetry (...) VALUES (...) ON CONFLICT DO NOTHING;
2. Inbox table for side effects (same transaction as the effect)
CREATE TABLE inbox (
  consumer   text   NOT NULL,
  message_id text   NOT NULL,
  seen_at    timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (consumer, message_id)
);

-- inside the consumer, one transaction:
BEGIN;
  INSERT INTO inbox (consumer, message_id) VALUES ('alerting', :msg_id)
    ON CONFLICT DO NOTHING
    RETURNING 1;                      -- no row returned ⇒ duplicate ⇒ ROLLBACK and ack
  INSERT INTO alert (...) VALUES (...);
COMMIT;
-- purge old rows periodically: DELETE FROM inbox WHERE seen_at < now() - interval '7 days';
3. Redis SET NX with TTL (fast, bounded window)
import { createClient } from "redis";
const redis = createClient({ url: "redis://cache:6379" });
await redis.connect();

  // SET key value NX EX ttl  → "OK" if the key was set, null if it already existed
  const r = await redis.set(`dedupe:${deviceId}:${seq}`, "1", { NX: true, EX: ttlSec });
  return r === "OK";
}
// Caveat: if the process crashes after firstSeen() but before the side effect, the retry is
// treated as a duplicate and skipped. Use this for best-effort effects (notifications),
// and strategy 1 or 2 for anything that must happen exactly once.

3.9 Ordering and synchronization

Global ordering across a fleet is neither achievable cheaply nor needed. What matters is per-device order for state that changes over time. Lamport showed in 1978 that in a distributed system "happened before" is only a partial order and introduced logical clocks to reason about it [64]; IoT systems face the same problem with device clocks that drift or reset.

  • Partition by device. Use the device id as the Kafka record key so that one device's records live in one partition, which Kafka keeps ordered [50]. MQTT preserves order per topic for messages of the same QoS from one client [5].
  • Carry a sequence number and apply "last write wins by sequence", not by arrival time, when updating the latest-state cache.
  • Use event time, not processing time, for windows and aggregates, and use watermarks to decide how long to wait for late data [7].
  • Beware of retries reordering. A non-idempotent Kafka producer with several in-flight requests can reorder records on retry; the idempotent producer prevents this [59].
  • Time synchronization. Stamp readings on the device and on ingestion; if they disagree beyond a threshold, flag the device's clock rather than silently trusting either.

-- KEYS[1] = "state:{deviceId}"    ARGV[1] = seq    ARGV[2] = json payload

  return 0                      -- stale or duplicate: ignore

4.2 Time-series databases: TimescaleDB and InfluxDB

Time-series workloads are dominated by inserts of recent data and range queries over recent windows. Facebook's Gorilla paper documented the pattern at scale and showed that delta-of-delta timestamp encoding plus XOR-based float compression shrank data points to an average of 1.37 bytes [4]; similar ideas appear throughout modern time-series engines.

TimescaleDB

TimescaleDB is a PostgreSQL extension. A hypertable looks like one table but is automatically partitioned into time-based chunks [70]. Continuous aggregates are materialized views over time buckets that refresh incrementally on a schedule [71]. Because it is still PostgreSQL, telemetry can be joined with the device registry in one SQL query.

schema/telemetry_timescale.sql
CREATE EXTENSION IF NOT EXISTS timescaledb;

CREATE TABLE telemetry (
  device_id text        NOT NULL,
  ts        timestamptz NOT NULL,
  seq       bigint      NOT NULL,
  temp_c    double precision,
  rh        double precision,
  battery   double precision,
  UNIQUE (device_id, ts, seq)                    -- dedupe key; must include the time column
);
SELECT create_hypertable('telemetry', by_range('ts', INTERVAL '1 day'));

                           timescaledb.compress_orderby = 'ts DESC');
SELECT add_compression_policy('telemetry', INTERVAL '7 days');

-- Drop raw data after 90 days
SELECT add_retention_policy('telemetry', INTERVAL '90 days');

-- 5-minute rollup, kept for 2 years, refreshed every 5 minutes
CREATE MATERIALIZED VIEW telemetry_5m WITH (timescaledb.continuous) AS
SELECT device_id,
       time_bucket(INTERVAL '5 minutes', ts) AS bucket,
       avg(temp_c) AS temp_avg, min(temp_c) AS temp_min, max(temp_c) AS temp_max,
       last(battery, ts) AS battery_last,
       count(*) AS n
FROM telemetry
GROUP BY device_id, bucket
WITH NO DATA;

  start_offset => INTERVAL '1 day', end_offset => INTERVAL '5 minutes',
  schedule_interval => INTERVAL '5 minutes');

Apache Cassandra

Cassandra was built at Facebook for inbox search and described by Lakshman and Malik as a decentralised structured storage system spread across many commodity servers with no single point of failure [77]. Data modelling is query-first: a table's partition key decides which nodes store a row, and clustering columns sort rows within a partition [78]. For telemetry, bucket the partition key by time so no partition grows without bound:

CREATE TABLE iot.telemetry_by_device_day (
  device_id text,

4.4 Object storage and data lakes

Object storage (Amazon S3, Azure Blob, Google Cloud Storage, MinIO and others) stores immutable blobs under keys at low cost; S3, for example, is designed for 99.999999999% (eleven nines) durability of objects over a year [79]. In IoT it holds firmware images, raw message archives, device logs, camera frames and the analytical copy of telemetry.

A data lake organises those objects for analytics. Telemetry is typically written in Apache Parquet, a columnar file format with efficient compression and encoding [80], under time-partitioned prefixes, and managed with an open table format such as Apache Iceberg, which adds snapshots, schema evolution and hidden partitioning on top of plain files [81]. Armbrust and colleagues call the combination of open file formats, a transactional metadata layer and warehouse-style performance a lakehouse [82].

4.5 Distributed databases

When one node is not enough, data is partitioned (sharded) across nodes and replicated for fault tolerance [38]. The CAP theorem says that during a network partition a system cannot be both consistent (linearisable) and available [44], so designs choose:

  • Leaderless / eventually consistent (Dynamo-style, Cassandra): tunable quorums, high write availability, application tolerates stale reads [76,77].
  • Consensus-replicated, strongly consistent: Google's Spanner pairs Paxos-replicated shards with TrueTime, a clock API with bounded uncertainty, to give externally consistent transactions across datacenters [83]. Open-source systems inspired by it include CockroachDB and YugabyteDB.

For IoT, the device registry and command store usually want strong consistency (you must not double-assign a device or lose a command), while telemetry tolerates eventual consistency in exchange for write throughput.

5.1 Real-time transport: WebSockets vs Server-Sent Events

Server-Sent Events (SSE) are defined in the WHATWG HTML standard: the browser opens an HTTP request with the EventSource API, and the server streams a text/event-stream response made of event:, data:, id: and retry: fields [87]. The browser reconnects automatically and sends the last seen id in a Last-Event-ID header, so the server can resume the stream [87]. SSE is one-way (server to client); WebSockets are bidirectional [16].

    res.write(`id: ${a.id}\nevent: alert\ndata: ${JSON.stringify(a)}\n\n`);

  const lastId = req.get("Last-Event-ID");
  if (lastId) for (const a of await alertsSince(req.user.tenant, lastId)) send(a);

  const onAlert = (a: any) => { if (a.tenant === req.user.tenant) send(a); };
  alertBus.on("alert", onAlert);
  const keepAlive = setInterval(() => res.write(": ping\n\n"), 25_000);   // comment line keeps proxies open
  req.on("close", () => { clearInterval(keepAlive); alertBus.off("alert", onAlert); });
});

5.2 Frameworks and TypeScript

React, Angular and Vue all re-render views from state; they differ in how state changes are detected. React components re-render when state set via hooks changes, and side effects such as opening a socket belong in useEffect, whose cleanup function must close what the effect opened [89]. Angular's signals are reactive values that notify consumers when they change [90]. Vue tracks reactive dependencies through JavaScript proxies and re-runs effects when a dependency changes [91]. TypeScript adds static types; its compatibility rules are structural, so a message shape defined once can be shared by backend and frontend [92].

A React hook that manages a WebSocket with exponential backoff, resubscription and cleanup:

web/src/hooks/useTelemetry.ts
import { useEffect, useRef, useState } from "react";
import { ServerMsg, isServerMsg, TelemetryMsg } from "../../../shared/messages";

type Point = TelemetryMsg["data"];

export function useTelemetry(deviceIds: string[], getToken: () => Promise<string>, maxPoints = 600) {
  const [series, setSeries] = useState<Record<string, Point[]>>({});
  const [connected, setConnected] = useState(false);
  const key = deviceIds.slice().sort().join(",");               // stable dependency
  const lastSeq = useRef<Record<string, number>>({});

  useEffect(() => {
    let ws: WebSocket | null = null;
    let attempt = 0;
    let stopped = false;
    let timer: number | undefined;

    const connect = async () => {
      const token = await getToken();
      ws = new WebSocket(`wss://api.example.com/ws?access_token=${encodeURIComponent(token)}`);
      ws.onopen = () => {
        attempt = 0; setConnected(true);
        ws!.send(JSON.stringify({ op: "sub", deviceIds }));
      };
      ws.onmessage = ev => {
        const msg: unknown = JSON.parse(ev.data);
        if (!isServerMsg(msg) || msg.type !== "telemetry") return;
        const p = msg.data;
        if ((lastSeq.current[p.deviceId] ?? -1) >= p.seq) return;   // drop duplicates / stale
        lastSeq.current[p.deviceId] = p.seq;
        setSeries(s => {
          const arr = [...(s[p.deviceId] ?? []), p];
          return { ...s, [p.deviceId]: arr.length > maxPoints ? arr.slice(-maxPoints) : arr };
        });
      };
      ws.onclose = () => {
        setConnected(false);
        if (stopped) return;
        const delay = Math.min(30_000, 500 * 2 ** attempt++) * (0.5 + Math.random()); // backoff + jitter
        timer = window.setTimeout(connect, delay);
      };
    };
    connect();

    return () => { stopped = true; clearTimeout(timer); ws?.close(); };   // cleanup on unmount/change
  }, [key]);   // eslint-disable-line react-hooks/exhaustive-deps

  return { series, connected };
}

5.3 Real-time dashboards and device status interfaces

A dashboard's first job is answering "is anything wrong?" in under five seconds. Practical rules:

  • Summarise first, detail on demand. Fleet KPIs (online %, active alerts by severity, devices with stale data), then a filterable table, then per-device pages.
  • Show data freshness. Display "last seen 2 min ago" and grey out values older than the expected report interval; a stale value that looks live is worse than no value.
  • Do not use colour alone. Pair status colours with icons or text. WCAG 2.2 success criterion 1.4.1 requires that colour is not the only visual means of conveying information [93].

5.5 Historical telemetry

Historical views must never pull millions of raw points into a browser. Two techniques work together:

  1. Server-side resolution selection. Pick raw, 5-minute or 1-hour data from the time range requested, using continuous aggregates (§4.2) [71].
  2. Visual downsampling. Largest-Triangle-Three-Buckets (LTTB), introduced in Steinarsson's 2013 thesis, keeps the points that preserve the visual shape of a series better than naive averaging, which flattens peaks [96].
web/src/lib/lttb.ts
export type XY = [number, number];
/** Largest-Triangle-Three-Buckets downsampling (Steinarsson, 2013). */
export function lttb(data: XY[], threshold: number): XY[] {
  if (threshold >= data.length || threshold < 3) return data;
  const out: XY[] = [data[0]];
  const every = (data.length - 2) / (threshold - 2);
  let a = 0;
  for (let i = 0; i < threshold - 2; i++) {
    // average of the next bucket
    const s = Math.floor((i + 1) * every) + 1, e = Math.min(Math.floor((i + 2) * every) + 1, data.length);
    let ax = 0, ay = 0; for (let j = s; j < e; j++) { ax += data[j][0]; ay += data[j][1]; }
    ax /= (e - s); ay /= (e - s);
    // pick the point in this bucket forming the largest triangle with a and the next-bucket average
    const rs = Math.floor(i * every) + 1, re = Math.floor((i + 1) * every) + 1;
    let maxA = -1, pick = rs;
    for (let j = rs; j < re; j++) {
      const area = Math.abs((data[a][0] - ax) * (data[j][1] - data[a][1]) - (data[a][0] - data[j][0]) * (ay - data[a][1]));
      if (area > maxA) { maxA = area; pick = j; }
    }
    out.push(data[pick]); a = pick;
  }
  out.push(data[data.length - 1]);
  return out;
}

5.7 Device configuration interfaces

Configuration screens edit desired state, so they should: validate before sending (the same JSON Schema the API uses), show desired vs reported side by side with a "pending" badge until the device confirms (the shadow model from §2.3 [2]), and send the If-Match ETag so concurrent edits fail loudly with 412 rather than silently overwriting [11].

web/src/components/ConfigForm.tsx
import { useEffect, useState } from "react";
interface Cfg { reportIntervalSec: number; thresholds: { tempHighC: number } }

export function ConfigForm({ deviceId, reported }: { deviceId: string; reported?: Partial<Cfg> }) {
  const [cfg, setCfg] = useState<Cfg | null>(null);
  const [etag, setEtag] = useState<string>("");
  const [msg, setMsg] = useState("");

  useEffect(() => { (async () => {
    const r = await fetch(`/api/devices/${deviceId}/config`);
    setEtag(r.headers.get("ETag") ?? ""); setCfg(await r.json());
  })(); }, [deviceId]);

  if (!cfg) return <p>Loading…</p>;
  const pending = reported && reported.reportIntervalSec !== cfg.reportIntervalSec;

  async function save() {
    if (cfg!.reportIntervalSec < 5 || cfg!.reportIntervalSec > 3600) return setMsg("Interval must be 5–3600 s");
    const r = await fetch(`/api/devices/${deviceId}/config`, {
      method: "PATCH", headers: { "Content-Type": "application/merge-patch+json", "If-Match": etag },
      body: JSON.stringify({ reportIntervalSec: cfg!.reportIntervalSec, thresholds: cfg!.thresholds }),
    });
    if (r.status === 412) return setMsg("Someone else changed this config. Reload to see their changes.");
    if (!r.ok) return setMsg((await r.json()).title ?? "Save failed");
    setEtag(r.headers.get("ETag") ?? ""); setMsg("Saved. Waiting for the device to apply it…");
  }

  return (
    <form onSubmit={e => { e.preventDefault(); save(); }}>
      <label>Report interval (s)
        <input type="number" min={5} max={3600} value={cfg.reportIntervalSec}
               onChange={e => setCfg({ ...cfg, reportIntervalSec: +e.target.value })} />
      </label>
      {pending && <span className="badge">pending: device reports {reported!.reportIntervalSec}s</span>}
      <label>High-temperature alert (°C)
        <input type="number" step={0.5} value={cfg.thresholds.tempHighC}
               onChange={e => setCfg({ ...cfg, thresholds: { tempHighC: +e.target.value } })} />
      </label>
      <button type="submit">Save</button> <output>{msg}</output>
    </form>
  );
}

5.8 Alert management

Alert fatigue is the main failure mode of monitoring UIs. The process-industry alarm-management standard ANSI/ISA-18.2 frames alarms as having a lifecycle and defines states such as unacknowledged, acknowledged, returned-to-normal and shelved (temporarily suppressed by an operator) [101]. Borrow that model:

  • Separate condition from notification. "Temperature > 80 °C on dev-42" is one alert, even if the condition is evaluated 1,000 times.
  • Use hysteresis and durations. Raise at > 80 °C for 2 minutes, clear at < 75 °C, to avoid flapping.
  • Acknowledge, shelve, escalate. Every action is audited with who and when.
  • Group alerts by site or root cause (a gateway outage should not page 500 times).

5.9 Remote control interfaces

Remote control UIs send commands to the physical world, so the UI must make the asynchronous, uncertain nature of the command explicit:

  • Show the command's state (queued → sent → delivered → succeeded/failed/expired) from §2.7, not an optimistic "done".
  • Require confirmation for destructive actions, and enforce authorization on the server too (scope devices:command).
  • Generate the idempotency key once per user intent, so a double-click or retry cannot send two commands [36].
  • Disable controls for offline devices or clearly say the command will wait until the device reconnects (and until when, given its expiry [5]).
web/src/components/RemoteButton.tsx
import { useRef, useState } from "react";
type CmdState = "idle" | "QUEUED" | "SENT" | "DELIVERED" | "SUCCEEDED" | "FAILED" | "EXPIRED";

export function RemoteButton({ deviceId, name, label, dangerous = false, online }:
  { deviceId: string; name: string; label: string; dangerous?: boolean; online: boolean }) {
  const [state, setState] = useState<CmdState>("idle");
  const idem = useRef<string>(crypto.randomUUID());          // one key per user intent

  async function run() {
    if (dangerous && !window.confirm(`Really ${label.toLowerCase()} on ${deviceId}?`)) return;
    const r = await fetch(`/api/devices/${deviceId}/commands`, {
      method: "POST", headers: { "Content-Type": "application/json", "Idempotency-Key": idem.current },
      body: JSON.stringify({ name, args: {}, ttlSec: 120 }),
    });
    if (r.status !== 202) return setState("FAILED");
    const { id } = await r.json();
    setState("QUEUED");
    const es = new EventSource(`/api/commands/${id}/events`);  // status updates pushed via SSE
    es.addEventListener("status", e => {
      const s = JSON.parse((e as MessageEvent).data).status as CmdState;
      setState(s);
      if (["SUCCEEDED", "FAILED", "EXPIRED"].includes(s)) { es.close(); idem.current = crypto.randomUUID(); }
    });
  }
  const busy = !["idle", "SUCCEEDED", "FAILED", "EXPIRED"].includes(state);
  return (
    <span>
      <button onClick={run} disabled={busy}>{label}</button>
      {!online && <small> device offline: command will wait up to 2 min</small>}
      {state !== "idle" && <small aria-live="polite"> {state.toLowerCase()}</small>}
    </span>
  );
}

The confirm dialog keeps the example short; production UIs usually use an in-page modal that names the device and the consequence.

7 Exercises

Exercise 7.1: find the duplicate bug

This consumer occasionally stores the same reading twice after deploys. Why, and how do you fix it?

consumer = Consumer({"group.id": "sink", "enable.auto.commit": True})
for msg in poll_forever(consumer):
    cur.execute("INSERT INTO telemetry VALUES (%s, %s, %s)", parse(msg))
    conn.commit()
Show solution

With auto-commit, offsets are committed periodically in the background. When the process is stopped, any records processed since the last automatic commit are delivered again to the next consumer in the group [50]. The plain INSERT has no uniqueness check, so replays become duplicate rows. Fix both sides: commit offsets manually after the database commit, and make the write idempotent with a unique key on (device_id, ts, seq) and ON CONFLICT DO NOTHING [58]. The second fix alone is sufficient for correctness; the first reduces wasted work.

Exercise 7.2: ordering under parallelism

You increase a topic from 6 to 12 partitions to add consumers. A week later, operators report that the "latest state" tile occasionally shows an older value. What happened?

Show solution

The default partitioner maps a key to a partition by hashing it modulo the partition count [50]. Adding partitions changes that mapping, so records for one device written before and after the change live in different partitions, and two consumers can process them in either order. Ordering is guaranteed only within a partition [50]. Defences: make the latest-state update conditional on a per-device sequence number (the Lua script in §3.9 or the DynamoDB condition in §4.3), and plan partition counts ahead of time or migrate through a new topic.

Exercise 7.3: offline detection

Design how the backend decides that a device is offline. Consider MQTT features and a Redis-based approach.

Show solution
  • Fast path: the device sets a Last Will message, such as devices/dev-42/status = offline (retained). If the connection drops without a DISCONNECT, the broker publishes it [5]. On connect, the device publishes online retained, so any new subscriber sees the current status immediately [5].
  • Keep-alive: the broker detects a dead connection after 1.5 × the keep-alive interval without traffic, which is what triggers the Will [5].
  • Belt and braces: also refresh online:{id} in Redis with a TTL on every message (§4.6) [63], because a device can be "connected" yet stuck and not sending telemetry.
  • Debounce flaps (for example, only alert if offline for more than 5 minutes) to avoid alert storms during broker restarts.

Exercise 7.4: capacity estimate

50,000 devices send 300-byte JSON messages every 10 s. Kafka retains 7 days with replication factor 3. Estimate (a) message rate, (b) daily ingress, (c) raw Kafka disk use before compression.

Show solution

(a) 50,000 / 10 = 5,000 msg/s. (b) 5,000 × 300 B = 1.5 MB/s, × 86,400 s ≈ 129.6 GB/day. (c) 129.6 GB × 7 days × 3 replicas ≈ 2.7 TB, plus per-record overhead and minus compression. Batching with linger.ms and a compression codec reduces this substantially for repetitive JSON [50]; switching to a binary encoding helps further.

Exercise 7.5: secure the topic tree

Write Mosquitto ACL rules so that a device can publish its own telemetry and read only its own commands, while a dashboard service can read all telemetry but publish nothing.

Exercise 7.6: write the continuous aggregate query

Return hourly min/avg/max temperature over the past 7 days for every device of tenant acme, using the 5-minute continuous aggregate from §4.2.

Show solution 
SELECT b.device_id,
       time_bucket('1 hour', b.bucket) AS hour,
       min(b.temp_min) AS tmin,
       sum(b.temp_avg * b.n) / sum(b.n) AS tavg,   -- weight by sample count
       max(b.temp_max) AS tmax
FROM telemetry_5m b
JOIN device d ON d.id = b.device_id
JOIN tenant t ON t.id = d.tenant_id AND t.name = 'acme'
WHERE b.bucket > now() - INTERVAL '7 days'
GROUP BY 1, 2 ORDER BY 1, 2;

Averaging the 5-minute averages directly would be wrong when buckets hold different sample counts; weighting by n gives the true hourly mean. Rolling up a continuous aggregate this way is a supported pattern [71].

9 Glossary

At-least-once
Delivery guarantee under which messages are never lost but may be duplicated; requires idempotent consumers [6].
Consumer group
Set of Kafka consumers sharing the partitions of a topic, each partition read by one member [50].
Continuous aggregate
TimescaleDB materialized view over time buckets that refreshes incrementally [71].
Dead-letter exchange
RabbitMQ exchange receiving messages that were rejected, expired or exceeded a delivery limit [62].
Device shadow / twin
Cloud-side JSON document holding desired and reported device state [2,3].
Event time
When an event happened at the source, as opposed to when it is processed [7].
Hypertable
TimescaleDB table automatically partitioned into time chunks [70].
Idempotency key
Client-supplied identifier that lets a server recognise a retried request [36].
Last Will and Testament
MQTT message the broker publishes when a client disconnects ungracefully [5].
Outbox
Table written in the same transaction as business data, from which events are relayed to a broker [42].
Retained message
Last message on an MQTT topic stored by the broker for future subscribers [5].
Shared subscription
MQTT 5 subscription ($share/group/filter) whose messages are load-balanced across group members [5].
Watermark
A stream processor's estimate that no events older than a given event time are still to arrive [7].
