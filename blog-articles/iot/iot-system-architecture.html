IoT System Architecture: From Sensor to Dashboard

How an Internet of Things system is put together, layer by layer: the devices that sense and act, the networks that carry their messages, the edge that filters and decides locally, the cloud platform that registers, ingests, stores and reasons over data, and the applications people actually use.

Includes 9 diagrams, 18 code listings, an interactive edge-filter demo, 10 exercises and 15 trivia questions with solutions. References follow the Vancouver style; numbers in square brackets link to the list at the end.

1. Introduction

ITU-T Recommendation Y.2060 describes the Internet of Things (IoT) as a global infrastructure for the information society that enables advanced services by interconnecting physical and virtual things, based on existing and evolving interoperable information and communication technologies [1]. The phrase itself is usually traced to Kevin Ashton, who used it as the title of a 1999 presentation at Procter & Gamble about linking RFID in supply chains to the internet [2].

An IoT system architecture is the arrangement of components, and of the responsibilities and interfaces between them, that turns physical phenomena into data, data into decisions, and decisions back into physical actions. Because real deployments mix microcontrollers with kilobytes of RAM, radios that can send only a few bytes at a time, and elastic cloud services, architects divide the problem into layers, each of which can evolve independently [3,4].

This article uses a five-layer view that is common in practice and maps cleanly onto the formal reference architectures discussed in Section 2:

A recurring theme is where computation should happen. Edge computing, as defined by Shi et al., refers to enabling technologies that allow computation to be performed at the edge of the network, on downstream data on behalf of cloud services and upstream data on behalf of IoT services [6]. Bonomi et al.'s earlier “fog computing” proposal made the same argument for latency-sensitive and geographically distributed IoT applications [7].

Several standards bodies publish reference architectures. They differ in vocabulary but agree on the core separation of sensing, communication, processing and application concerns.

Why so many models? A reference architecture is a template, not a blueprint. Its value is a shared vocabulary that lets a device team, a network team and a cloud team agree on interfaces before writing code [5,9].

Layer 13. Device layer

The device layer is where the digital system touches the physical world. A typical node combines one or more sensors and actuators, signal-conditioning electronics, a microcontroller (MCU) running firmware, a radio or wired interface, a power source and a secure identity [3,4].

3.1 Sensors

A sensor converts a physical, chemical or biological stimulus into an electrical signal; a transducer is the more general term for any device converting one form of energy to another [11]. Key characteristics that drive architecture decisions include range (span), resolution, accuracy, sensitivity, hysteresis, response time and the sampling rate needed to capture the phenomenon [11]. Sampling theory requires the sampling frequency to exceed twice the highest frequency component of interest, which is why vibration monitoring generates far more data than room-temperature monitoring [11].

Many digital sensors use the I²C bus, a two-wire (SDA, SCL) serial bus with 7-bit (optionally 10-bit) addressing and speed grades of 100 kbit/s (Standard-mode), 400 kbit/s (Fast-mode), 1 Mbit/s (Fast-mode Plus) and 3.4 Mbit/s (High-speed mode) [12].

3.2 Actuators

Actuators perform the reverse conversion: an electrical command becomes motion, heat, light, sound or a change in flow. Common IoT actuators include relays and contactors, solenoid valves, DC, stepper and servo motors, heaters and LEDs [3,4]. They usually need a driver stage (transistor, H-bridge, relay) because MCU pins cannot source the necessary current. Architecturally, actuation introduces safety concerns: a command must be authenticated, idempotent, and the device must have a defined safe state if connectivity is lost. The IIRA treats the control domain, where sensing and actuation loops close, as the most safety-critical functional domain [9].

3.3 Embedded processors

IoT devices range from tiny 8-bit MCUs to Linux-capable application processors. RFC 7228 classifies constrained devices by memory [13]:

Above Class 2 sit devices such as the ESP32 family, which integrates Wi-Fi and Bluetooth with a dual-core MCU and is programmed with Espressif's FreeRTOS-based ESP-IDF framework [14], and Linux single-board computers that often serve as gateways.

3.4 Firmware

Firmware is the software that runs on the device. Simple nodes use a “super-loop”; more complex ones use a real-time operating system (RTOS) such as FreeRTOS [15] or Zephyr [16], which provide tasks, timers, queues, and (in Zephyr's case) networking, Bluetooth and device-driver subsystems. Three firmware concerns are architectural:

  • Power management. Battery devices spend most of their life asleep, waking on a timer or interrupt; protocol choice (Section 4) must tolerate this.
  • Secure boot. A bootloader such as MCUboot verifies a cryptographic signature on the application image before running it, and supports image-swapping strategies so a failed update can be rolled back [17].
  • Over-the-air (OTA) update. The IETF SUIT architecture (RFC 9019) describes the roles involved (author, distribution system, device), and a signed manifest that tells the device what to install and how to verify it [18]. NIST lists software update as one of six core baseline capabilities of an IoT device [19].

Sending only meaningful changes plus a periodic heartbeat is a simple but powerful pattern: the radio is usually the largest energy consumer, so fewer transmissions translate directly into longer battery life.

3.5 Device identification

Every device needs an identifier that the platform can trust. Identifiers exist at several levels:

  • Hardware/link addresses such as the IEEE EUI-64 used by IEEE 802.15.4 radios, from which 6LoWPAN derives IPv6 interface identifiers [20].
  • Logical identifiers such as a UUID (RFC 9562) [21] or a cloud “thing name”/device ID.
  • Cryptographic identity: a private key held on the device and a corresponding X.509 certificate (RFC 5280) [22]. IEEE 802.1AR defines a manufacturer-installed Initial Device Identifier (IDevID) and operator-installed Locally significant Device Identifiers (LDevIDs) [23].

NIST names device identification, both logical and physical, as the first capability in its IoT core baseline [19]. In practice the private key should be generated inside, and never leave, a secure element or TPM, so a cloned firmware image cannot impersonate the device.

Layer 24. Connectivity layer

The connectivity layer moves bits between devices, gateways and the cloud. Choosing a network is a three-way trade-off between range, data rate and energy; no single technology wins on all three [4].

4.3 Gateways and message transmission

ITU-T Y.2060 recognises that devices may connect to the network directly, through a gateway, or through an ad-hoc local network behind a gateway [1]. A connectivity gateway bridges a local network (BLE, 802.15.4, RS-485) to an IP backhaul, and is frequently also the edge computer described in Section 5.

In MQTT, clients never address each other; they publish to and subscribe from topics on a broker [31]. Good topic design separates telemetry from commands, puts the device ID in a predictable position, and avoids leading slashes. AWS guidance, for example, recommends prefixes such as dt/ for data telemetry and cmd/ for commands [37].

Delivery guarantees

MQTT defines three Quality of Service levels [31]: QoS 0 “at most once” (fire and forget), QoS 1 “at least once” (PUBLISH/PUBACK, duplicates possible), and QoS 2 “exactly once” (a four-step PUBLISH/PUBREC/PUBREL/PUBCOMP handshake). Because QoS 1 can deliver duplicates, downstream consumers should be idempotent, for example by de-duplicating on a message sequence number. CoAP achieves reliability over UDP with Confirmable messages that are retransmitted with exponential back-off until acknowledged [30]. Transport security is provided by TLS 1.3 for TCP [32] and DTLS 1.3 for UDP [38].

4.4 Device-to-device communication

Not every message needs the cloud. Device-to-device (D2D) communication keeps latency low and keeps working when the internet link is down. Examples include BLE connections and broadcasts between a phone and a wearable [26], Thread mesh networks in which routers relay packets for sleepy end devices [25], and Matter, an application-layer standard from the Connectivity Standards Alliance that runs over Wi-Fi, Thread and Ethernet and uses Bluetooth LE for commissioning, so that devices from different vendors can control each other locally [39]. CoAP also supports IP multicast for group communication on local networks [30]. The W3C Web of Things Thing Description provides a machine-readable JSON-LD description of a device's properties, actions and events, which helps heterogeneous devices discover how to talk to one another [40].

Layer 35. Edge layer

The edge layer performs computation close to where data is produced. Shi et al. argue that pushing processing to the edge reduces response time, saves bandwidth and energy, and improves privacy, since raw data need not leave the site [6]. In the IIRA three-tier pattern the edge tier gathers data from edge nodes over a proximity network, and connects to the platform tier over an access network [9].

5.1 Edge gateways

An edge gateway is a more capable computer (often an industrial PC or Linux single-board computer) that terminates local protocols, runs application logic, buffers data and maintains a secure connection to the cloud. Commercial edge runtimes package this as managed software:

  • AWS IoT Greengrass V2 is an open-source edge runtime and cloud service in which applications are deployed as components; it supports local messaging, ML inference and stream management on the device [41].
  • Azure IoT Edge runs cloud workloads as containerised modules, with a runtime made of the IoT Edge agent (deploys and monitors modules) and the IoT Edge hub (local message broker and proxy to IoT Hub) [42].
  • Node-RED is a flow-based, low-code programming tool built on Node.js that wires together hardware devices, APIs and services, and is widely used on gateways [43].

5.2 Local data processing, filtering and aggregation

Raw sensor streams contain noise, duplicates, and far more samples than most applications need. Three standard reductions are applied at the edge:

  • Deadband (report-by-exception): forward a value only when it differs from the last forwarded value by more than a threshold.
  • Outlier rejection: discard physically impossible values or spikes, for example with a rolling median filter.
  • Windowed aggregation: replace N raw samples with summary statistics (count, min, max, mean) per time window, the same windowing concept used by cloud stream processors [44].

5.3 Protocol translation

Brownfield sites are full of equipment that speaks Modbus, OPC UA, BACnet or proprietary serial protocols. The gateway translates these into the cloud's preferred protocol and data model. Modbus is a simple case: a client reads 16-bit holding registers with function code 0x03; over TCP each request carries a 7-byte MBAP header (transaction ID, protocol ID 0, length and unit ID) followed by the PDU [29].

5.4 Local storage and real-time decision-making

Wide-area links fail. A store-and-forward buffer on the gateway persists messages while offline and replays them, in order, once the connection returns; Greengrass, for instance, provides a stream manager for buffering and exporting data streams [41], and Azure IoT Edge hub stores messages locally when the device is offline [42].

Real-time decisions are those whose deadline is shorter than a cloud round-trip can guarantee: stopping a conveyor when a light curtain is broken, closing a valve on over-pressure, or shedding load. These belong at the edge, and safety-critical ones in the device or PLC itself [6,9]. The cloud can still tune the thresholds (via a device twin or shadow, Section 6.3) without being in the loop.

5.5 Edge AI and TinyML

TinyML is machine-learning inference on microcontroller-class hardware at milliwatt power levels [45]. Running models on the device lets it send conclusions (“bearing fault likely”) instead of raw high-rate data. TensorFlow Lite Micro (TFLM) is an interpreter-based framework designed for this setting; it avoids dynamic memory allocation by placing all tensors in a single caller-provided memory arena, and supports only the operators a model registers so the binary stays small [46,47]. The MLPerf Tiny benchmark standardises four representative tasks: keyword spotting, visual wake words, image classification and anomaly detection [48].

Models are usually quantised to 8-bit integers. Jacob et al. describe the affine mapping r = S(q − Z) between a real value r and its integer representation q, with scale S and zero-point Z, which allows inference using integer-only arithmetic [49]. This cuts model size by about four times relative to 32-bit floats and suits MCUs without floating-point units.

Design rule of thumb Put inference where the data is richest and the link is thinnest. A microphone sampled at 16 kHz produces orders of magnitude more data than an LPWAN link like LoRaWAN can carry [27], so keyword spotting must run on the device; slow-changing temperature data can be analysed in the cloud.

Layer 46. Platform and cloud layer

The platform layer provides the shared services that every application needs: knowing which devices exist, admitting them securely, talking to them at scale, and turning their messages into stored, queryable, actionable data. AWS IoT Core, for example, comprises a device gateway and message broker, a rules engine, a registry, the Device Shadow service and Jobs [50]; Azure IoT Hub offers device-to-cloud telemetry, cloud-to-device messages, direct methods, device twins and a per-device identity registry [51].

6.1 Device registries

A registry is the authoritative inventory of devices: identity, credentials or certificate references, type, hardware and firmware version, location, owner and group membership. In AWS IoT the registry stores things, optionally classified by thing types and organised into thing groups [50]; Azure IoT Hub keeps an identity registry that controls which devices may connect [51]. Group membership is what lets an operator target “all firmware 2.3 sensors in Building B” with a configuration change or update.

6.2 Device provisioning

Provisioning binds a physical device to a registry entry, credentials and initial configuration, ideally with zero touch on the factory floor or at install time. Patterns include:

  • Per-device certificates at manufacture (just-in-time registration on first connect).
  • Fleet provisioning by claim (AWS): devices share a limited claim certificate, which they exchange on first connection for a unique certificate according to a provisioning template; a pre-provisioning hook can validate the request [52].
  • Azure Device Provisioning Service (DPS): a helper service that verifies attestation (X.509, TPM or symmetric key) and assigns the device to one of possibly many IoT hubs according to an allocation policy [53].
  • Standards-based onboarding: IETF BRSKI (RFC 8995) uses a manufacturer-signed voucher and the device's IEEE 802.1AR IDevID to join a network securely [23,54]; FIDO Device Onboard (FDO) defines late binding of a device to its owner's platform via an ownership voucher [55].

6.3 Device management

Device management covers configuration, monitoring, remote commands, diagnostics and firmware updates across the fleet's life. Two abstractions dominate:

  • State documents. AWS Device Shadows and Azure device twins are cloud-hosted JSON documents with desired and reported sections. Applications write desired state; the device acts and writes reported state; the service computes the difference (the shadow's delta) and delivers it to the device, even if it was offline when the change was made [56,57].
  • Jobs/bulk operations. AWS IoT Jobs define remote operations (such as an OTA update) sent to one or many devices and track each device's execution status [58].

On constrained devices, OMA LwM2M provides an equivalent standardised object model over CoAP, including objects for device information and firmware update [36].

6.4 Message brokers and IoT ingestion services

The message broker terminates millions of long-lived device connections, authenticates them, and routes published messages to subscribers. Open-source options include Eclipse Mosquitto, a lightweight broker implementing MQTT 5.0, 3.1.1 and 3.1 [59]. Managed services (AWS IoT Core, Azure IoT Hub) combine a broker with identity, throttling and routing [50,51].

Behind the device-facing broker, an ingestion service decouples bursty device traffic from downstream consumers. A distributed log such as Apache Kafka stores records in partitioned, replicated topics, and lets multiple consumer groups read the same stream independently and replay it [60]. Typical ingestion duties are schema validation, enrichment with registry metadata (site, asset type), de-duplication of QoS 1 retries, and fan-out to hot (stream) and cold (batch) paths.

6.5 Stream processing

IoT data is an unbounded, often out-of-order stream. The Dataflow model formalises how to compute over it with windows (where in event time to group data), watermarks (when the system believes a window's input is complete) and triggers (when to emit results) [44]. Apache Flink provides tumbling, sliding, session and global windows [61]; Azure Stream Analytics exposes tumbling, hopping, sliding, session and snapshot windows in a SQL-like language [62].

6.6 Databases and cloud storage

IoT data is overwhelmingly time-stamped, append-mostly and queried by time range, so time-series databases are the default for telemetry. InfluxDB ingests points in line protocol: a measurement name, optional comma-separated tags (indexed metadata), one or more fields (values) and an optional timestamp [63]. Telegraf is InfluxData's plugin-driven agent that collects metrics from sources such as MQTT and Modbus and writes them to InfluxDB and other outputs [64]. TimescaleDB extends PostgreSQL with hypertables that partition data by time while keeping full SQL [65].

Other data has other homes: the registry and asset metadata in a relational or document database; device state in the shadow/twin service; and raw and historical data in inexpensive object storage (a data lake) for batch analytics and model training. Rules engines can route messages directly to such stores; AWS IoT rule actions, for example, include writing to Amazon S3, DynamoDB and Kinesis [66].

6.7 Rules engines

A rules engine evaluates each incoming message against declarative conditions and triggers actions without custom servers. AWS IoT rules use an SQL-like statement in which the FROM clause is an MQTT topic filter, the SELECT clause shapes the payload and the WHERE clause filters; matching messages invoke actions such as republishing, writing to a database, or sending a notification [66].

6.8 APIs

Applications should not talk to devices directly; they use platform APIs. REST, as defined in Fielding's dissertation, organises an API around resources with a uniform interface and stateless interactions [35], and OpenAPI 3.1 provides a standard, language-agnostic description of HTTP APIs from which documentation and client SDKs can be generated [67]. Commands sent through an API are usually asynchronous: the API records desired state or enqueues a message and returns 202 Accepted, and the client watches for the device's reported state. For live updates to browsers, WebSocket (RFC 6455) provides a full-duplex channel [68], and MQTT can itself run over WebSockets [31].

Layer 57. Application layer

The application layer is where IoT creates value for people and business processes. In ITU-T Y.2060 it sits on top of generic and specific service-support capabilities [1]; in the IIRA it corresponds to the application and business functional domains [9].

7.1 Web dashboards and monitoring interfaces

Dashboards present current state and trends. Grafana is a widely used open-source tool in which a dashboard is a set of panels, each backed by a query to a data source such as InfluxDB, PostgreSQL/TimescaleDB or Prometheus, with variables for templating (for example, choosing a site or device) [69]. Good monitoring interfaces show fleet health (devices online, last-seen time, battery, firmware version) separately from process data (temperatures, flows), because the first tells you whether to trust the second.

7.2 Mobile applications

Mobile apps serve two roles: day-to-day monitoring and control through the platform's APIs, and local commissioning of new devices, typically over Bluetooth LE because every smartphone has it [26]. Matter, for example, uses Bluetooth LE to commission devices onto a Wi-Fi or Thread network [39]. Push notifications to phones are delivered through platform services such as Firebase Cloud Messaging, which can deliver messages to Android, Apple and web clients [70].

7.3 Alerts and notifications

An alert turns a condition into a human action. Grafana Alerting separates alert rules (queries and conditions evaluated periodically, optionally with a pending period before firing), contact points (email, chat, webhook, paging integrations) and notification policies that route and group alerts [71]. Equivalent functionality exists in the cloud rules engines [66] and stream processors [62]. Practical design rules:

  • Require a condition to persist (for example 10 minutes) before alerting, to avoid flapping on noise.
  • Alert on missing data (a device that stops reporting) as well as bad values; MQTT's retained Will message (Listing 2) gives an immediate offline signal [31].
  • Group and de-duplicate so one failed gateway produces one page, not two hundred.

7.4 Remote device control

Remote control must work even when devices sleep or links drop. The robust pattern is desired-state convergence: the application sets desired state in the shadow or twin; the device receives the delta when it next connects, acts, and reports its new state [56,57]. For immediate, synchronous actions with a timeout, Azure IoT Hub offers direct methods, which succeed only if the device is online [51].

7.5 Reporting

Reports aggregate history for compliance, maintenance planning and business decisions: daily minimum/maximum temperatures for food-safety records, uptime and overall equipment effectiveness for a factory, or energy use per building. They are typically produced from downsampled time-series data or from the data lake in batch, rather than from the hot stream [3]. Grafana dashboards can be shared as snapshots or exported, and SQL-capable stores like TimescaleDB integrate with standard BI tools [65,69].

7.6 Automation interfaces

Automation interfaces let users and other systems express “when X, if Y, do Z” without code. Home Assistant automations are structured exactly as triggers, conditions and actions [72]; Node-RED flows serve the same role on gateways and servers [43]; and enterprise integrations use webhooks and the platform's REST API [67].

8. Cross-cutting concern: security and trust

Security is not a layer; it must be designed into every layer. The 2016 Mirai botnet showed why: it spread by logging in to internet-exposed IoT devices using a short list of factory-default credentials, peaked at roughly 600,000 infected devices, and launched some of the largest denial-of-service attacks then recorded [73]. Today's baselines respond directly to that experience:

BaselineWhat it requires (selected)
NISTIR 8259 / 8259A [19,74]Six core device capabilities: device identification, device configuration, data protection, logical access to interfaces, software update, and cybersecurity state awareness.
ETSI EN 303 645 [75]Thirteen categories of provisions for consumer IoT, starting with no universal default passwords, a vulnerability-disclosure policy and keeping software updated.
OWASP IoT Top 10 (2018) [76]Ranks “weak, guessable, or hardcoded passwords” first, followed by insecure network services and insecure ecosystem interfaces.

Mapping these to the layers: hardware-protected keys and secure boot at the device layer [17,23]; mutual TLS/DTLS at the connectivity layer [32,38]; least-privilege MQTT topic policies so a device may publish only under its own ID [37]; signed firmware manifests for updates [18]; and network policies such as Manufacturer Usage Descriptions (RFC 8520), which let a device declare the network access it needs so that the network can block everything else [77].

Common anti-pattern One shared certificate or API key for the whole fleet. If any one device is compromised, every device can be impersonated, and the credential cannot be revoked without bricking the fleet. Use per-device identities from the start (Section 3.5) [19].

11. Exercises (with solutions)

Exercise 1. Layer mapping

Assign each component to one of the five layers: (a) a soil-moisture probe, (b) a LoRaWAN gateway, (c) an InfluxDB instance, (d) a Raspberry Pi running a TinyML anomaly model on vibration data from five motors, (e) a Grafana alert to a phone, (f) an AWS IoT rule.

Solution

(a) Device. (b) Connectivity: a LoRaWAN gateway relays radio frames to the network server and does not interpret application payloads [27]. (c) Platform/cloud (database). (d) Edge (local processing and AI near the data) [6]. (e) Application (alerts and notifications) [71]. (f) Platform (rules engine) [66].

Exercise 2. Choosing a network

A city wants to read 50,000 water meters once per hour. Meters are in basements, battery powered, and must last 10 years. Compare Wi-Fi, BLE, LoRaWAN and NB-IoT.

Solution

Wi-Fi and BLE lack the range and infrastructure (no access point in every basement). LoRaWAN offers km range with low power and Class A devices that sleep between uplinks, but needs a gateway network [27]. NB-IoT reuses operator cellular infrastructure and was designed for deep indoor coverage and low device cost [28]. Either LPWAN fits; the decision turns on whether the city wants to own gateways (LoRaWAN) or pay an operator subscription (NB-IoT).

Exercise 3. MQTT topic design

Design topics for telemetry and commands for devices identified by site and device ID. Then write the subscription a dashboard would use for all temperature readings at site plant1.

Solution

Telemetry: dt/<site>/<deviceId>/<metric>; commands: cmd/<site>/<deviceId>/<action>, following the AWS recommendation to separate telemetry and command prefixes [37]. Dashboard subscription: dt/plant1/+/temp, where + matches exactly one level [31].

Exercise 4. QoS and duplicates

A billing system counts energy-meter pulses published at QoS 1. Occasionally totals are too high. Why, and how do you fix it without moving to QoS 2?

Solution

QoS 1 is “at least once”: if a PUBACK is lost the sender retransmits, and the consumer may receive the message twice [31]. Fix: include a monotonic per-device sequence number (as in Listing 2) or send cumulative counter values rather than increments, and make the consumer idempotent by discarding sequence numbers it has already seen.

Exercise 5. Edge data reduction

A gateway receives 20 sensors × 10 samples/s. It forwards one summary (count, min, max, mean) per sensor per minute. What is the reduction factor in message count?

Solution

Raw: 20 × 10 × 60 = 12,000 samples per minute. Forwarded: 20 summaries per minute. Reduction = 12,000 / 20 = 600×. This is the bandwidth benefit of edge aggregation described by Shi et al. [6].

Exercise 6. Quantisation arithmetic

An int8 input tensor has scale S = 0.05 and zero-point Z = −10. What int8 value represents r = 1.30? What real value does q = 50 represent?

Solution

Using r = S(q − Z) [49]: q = r/S + Z = 1.30/0.05 + (−10) = 26 − 10 = 16. For q = 50: r = 0.05 × (50 − (−10)) = 0.05 × 60 = 3.0.

Exercise 7. Constrained device class

A sensor MCU has 16 KiB RAM and 128 KiB flash. Which RFC 7228 class is it closest to, and which application protocol is more appropriate: HTTPS or CoAP over DTLS?

Solution

It is close to Class 1 (about 10 KiB RAM, 100 KiB flash) [13]. Class 1 devices cannot easily run a full HTTP/TLS/TCP stack but can use protocols designed for constrained nodes, such as CoAP over UDP with DTLS [13,30,38].

Exercise 8. Provisioning risk

Fleet provisioning by claim puts the same claim certificate on many devices. What prevents an attacker who extracts it from registering thousands of fake devices?

Solution

The claim certificate's policy should allow only the provisioning topics; the provisioning template can call a pre-provisioning hook that checks the submitted serial number against a manufacturing allow-list and rejects duplicates [52]. Stronger still: per-device factory identities (IDevID) [23] or ownership vouchers such as FDO [55].

Exercise 9. Window choice

You need (a) a dashboard value updated every minute showing the average of the last 10 minutes, and (b) a count of how long each door stayed open. Which window types fit?

Solution

(a) A hopping/sliding window of size 10 minutes with a 1-minute hop. (b) A session window keyed by door, which groups events separated by less than a gap timeout into one session [44,62].

Exercise 10. Remote control while offline

A user changes a setpoint while a battery device is asleep for 15 minutes. Explain what happens with (a) a device shadow and (b) an Azure direct method.

Solution

(a) The desired state is stored; when the device wakes and connects it receives the delta, applies it and updates reported state [56]. (b) A direct method is a synchronous request that requires the device to be online; it fails after its timeout [51]. Use state documents for settings and direct methods for interactive, time-bound actions.

12. Trivia (with solutions)

  1. Who is credited with coining the phrase “Internet of Things”, and in what year?

    Answer

    Kevin Ashton, in a 1999 presentation at Procter & Gamble [2].

  2. Which university's coffee pot became one of the first webcams?

    Answer

    The Trojan Room coffee pot at the University of Cambridge Computer Laboratory; a camera was pointed at it in 1991 and the images went on the web in 1993 [78].

  3. Which university connected a Coke machine to the ARPANET so people could check if it was stocked and cold?

    Answer

    Carnegie Mellon University's Computer Science Department [79].

  4. How many layers does the ITU-T Y.2060 IoT reference model have?

    Answer

    Four (application; service and application support; network; device), plus management and security capabilities [1].

  5. What does the # wildcard match in an MQTT topic filter?

    Answer

    Any number of levels, including zero; it must be the last character of the filter [31].

  6. What is CoAP's default UDP port?

    Answer

    5683 (and 5684 for CoAP over DTLS) [30].

  7. What is the maximum frame size of IEEE 802.15.4, which motivated 6LoWPAN header compression?

    Answer

    127 octets [20].

  8. What are the three exchanged packets after PUBLISH in an MQTT QoS 2 flow?

    Answer

    PUBREC, PUBREL and PUBCOMP [31].

  9. Name the five primitives of NIST's “Networks of Things” model.

    Answer

    Sensor, aggregator, communication channel, eUtility and decision trigger [10].

  10. How much spectrum does an NB-IoT carrier occupy?

    Answer

    180 kHz [28].

  11. Which four tasks make up the MLPerf Tiny benchmark?

    Answer

    Keyword spotting, visual wake words, image classification and anomaly detection [48].

  12. What Modbus function code reads holding registers?

    Answer

    0x03 [29].

  13. What is the first provision in ETSI EN 303 645?

    Answer

    No universal default passwords [75].

  14. Roughly how many devices did the Mirai botnet infect at its peak?

    Answer

    About 600,000 [73].

  15. What does the IEEE 802.1AR acronym “IDevID” stand for?

    Answer

    Initial Device Identifier, a manufacturer-installed secure identity [23].

Key takeaways

  • Layers are about separating concerns and interfaces; formal models (ITU-T Y.2060, ISO/IEC 30141, IIRA) give the vocabulary [1,5,9].
  • Reduce data as early as possible: deadband on the device, aggregation at the edge, windows in the cloud [6,44].
  • Prefer publish/subscribe for telemetry and desired-state documents for control [31,56,57].
  • Give every device its own cryptographic identity, a secure boot chain and a signed update path [18,19].
  • Design for disconnection: store-and-forward at the edge, local real-time decisions, and alerts on missing data.
