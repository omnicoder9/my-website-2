1What device and fleet management is

Device management is the set of functions that keep an individual IoT device identifiable, reachable, correctly configured, healthy, secure and up to date from the day it is manufactured until the day it is retired. Fleet management applies those functions to large populations of devices at once: grouping them, querying them, rolling changes out in stages and measuring the health of the population rather than the individual. ITU-T Y.2060 makes management one of two "vertical" capability sets that cut across every layer of the IoT reference model, and lists device management functions such as remote activation and de-activation, diagnostics, firmware and software updating, and device working-status management [1].

Telecommunications operators organised network management long before the IoT into five functional areas, usually abbreviated FCAPS: Fault, Configuration, Accounting, Performance and Security management, defined in ITU-T M.3400 [2]. FCAPS still maps well onto IoT fleets. Fault management becomes device diagnostics and alarm handling, configuration management becomes desired-state configuration and firmware management, performance management becomes remote and health monitoring, and security management becomes authentication, credential rotation and revocation. Surveys of IoT management protocols compare the protocols that implement these functions, from SNMP and NETCONF to TR-069 and OMA Lightweight M2M (LwM2M), along exactly these lines [3].

Security guidance increasingly treats management as a security capability in its own right. NIST's baseline for IoT device manufacturers asks that devices offer a unique identity, configurable settings, protected data, logical access control, a secure software update mechanism and "cybersecurity state awareness" (the ability to report on their own security state) [4]. Those six capabilities line up almost one-for-one with the sections of this article.

1.1 Three ways to manage devices

Standards-based protocols

OMA LwM2M defines a client, a bootstrap server and an LwM2M server, a fixed set of operations and a registry of numbered objects (Device, Firmware Update, Location and so on) carried over CoAP [8,9]. NETCONF with YANG models fills the same role for routers and gateways [10,11].

Cloud device-management services

AWS IoT (thing registry, fleet provisioning, Device Shadow, Jobs, fleet indexing, Device Defender) and Azure IoT Hub (Device Provisioning Service, device twins, Device Update) provide hosted equivalents with vendor-specific MQTT topics [12–17].

Update-centric platforms

Eclipse hawkBit, Mender and balena focus on getting software onto devices safely: artefact storage, staged rollouts, A/B images and delta updates [18–20].

Open-source device stacks

Eclipse Leshan (Java LwM2M server and client), Zephyr's LwM2M and hawkBit clients, and the MCUboot bootloader give embedded developers the device-side pieces [21–23].

2Device registration

Registration creates the record that says a device exists: its identifier, its type, its owner and the attributes operators will later query (site, model, hardware revision). In AWS IoT this is the thing registry; in Azure IoT Hub it is the identity registry; in LwM2M it is the server's list of registered clients [8,12,15]. Registration and provisioning are often confused. Registration is about the record; provisioning (§3) is about putting credentials and configuration on the device so it can connect to the right service.

2.1 Identifiers

Every device needs an identifier that is unique within the management domain and stable for the device's life. NIST lists "device identification" as the first core capability: the device can be uniquely identified both logically and physically [4]. Typical choices are a serial number, a MAC-derived EUI-64, a URN, or the hash of a device certificate's public key. In LwM2M the identifier is the Endpoint Client Name, sent in the ep query parameter of the Register operation [8].

2.2 LwM2M registration on the wire

The LwM2M Client Registration interface has three operations: Register, Update and De-register. Register is a CoAP POST to /rd carrying the endpoint name, the registration lifetime in seconds, the LwM2M version and the binding mode, with a CoRE Link Format payload listing the objects and instances the client supports [8,24]. The server replies 2.01 Created with a Location-Path that the client uses for later Update and De-register requests [8]. If the client does not send an Update before its lifetime expires, the server considers the registration gone, which makes lifetime a built-in liveness signal (§8).

2.3 A minimal device registry API

The registry below is deliberately small. It stores devices with attributes and a lifecycle state, enforces legal state transitions (so a decommissioned device cannot quietly come back), and supports attribute queries, the basis of fleet grouping in §14. It uses only the Python standard library.

registry.py: an in-memory device registry with lifecycle states
from dataclasses import dataclass, field
from datetime import datetime, timezone
from enum import Enum

class State(Enum):
    MANUFACTURED = "manufactured"
    REGISTERED = "registered"
    PROVISIONED = "provisioned"
    ACTIVE = "active"
    MAINTENANCE = "maintenance"
    DECOMMISSIONED = "decommissioned"

# Allowed lifecycle transitions; anything else is rejected.
ALLOWED = {
    State.MANUFACTURED: {State.REGISTERED},
    State.REGISTERED: {State.PROVISIONED, State.DECOMMISSIONED},
    State.PROVISIONED: {State.ACTIVE, State.DECOMMISSIONED},
    State.ACTIVE: {State.MAINTENANCE, State.DECOMMISSIONED},
    State.MAINTENANCE: {State.ACTIVE, State.DECOMMISSIONED},
    State.DECOMMISSIONED: set(),          # terminal
}

def now():
    return datetime.now(timezone.utc).isoformat()

@dataclass
class Device:
    device_id: str
    model: str
    attributes: dict = field(default_factory=dict)
    state: State = State.MANUFACTURED
    history: list = field(default_factory=list)

class Registry:
    def __init__(self):
        self._devices: dict[str, Device] = {}

    def register(self, device_id, model, **attributes):
        if device_id in self._devices:
            raise ValueError(f"{device_id} already registered")
        d = Device(device_id, model, dict(attributes))
        self._devices[device_id] = d
        self.transition(device_id, State.REGISTERED, reason="registered")
        return d

    def transition(self, device_id, new_state, reason=""):
        d = self._devices[device_id]
        if new_state not in ALLOWED[d.state]:
            raise ValueError(f"{d.state.value} -> {new_state.value} not allowed")
        d.history.append((now(), d.state.value, new_state.value, reason))
        d.state = new_state

    def query(self, **match):
        """Return devices whose attributes (or model/state) match all filters."""
        def ok(d):
            view = {**d.attributes, "model": d.model, "state": d.state.value}
            return all(view.get(k) == v for k, v in match.items())
        return [d for d in self._devices.values() if ok(d)]

if __name__ == "__main__":
    r = Registry()
    r.register("urn:dev:sn:TH-000172", "TH-2", site="plant-7", hw="rev-c")
    r.transition("urn:dev:sn:TH-000172", State.PROVISIONED, "cert issued")
    r.transition("urn:dev:sn:TH-000172", State.ACTIVE, "first connect")
    print([d.device_id for d in r.query(site="plant-7", state="active")])

3Device provisioning

Provisioning (also called onboarding or enrolment) gives a device the credentials, trust anchors and endpoint information it needs to join its operational service. NIST SP 1800-36 distinguishes network-layer onboarding, which gives the device its network credentials, from application-layer onboarding, which connects it to the cloud or application service, and argues both should be trusted: performed so that the device and the network authenticate each other and credentials are delivered confidentially [6].

3.2 Azure DPS: attestation and allocation

The Azure IoT Hub Device Provisioning Service supports three attestation mechanisms: X.509 certificates, Trusted Platform Module (TPM) and symmetric keys. Enrolments are either individual or group. An allocation policy decides which hub a device lands on; DPS documents four: evenly weighted distribution (the default), lowest latency, static configuration via the enrolment list, and custom allocation using an Azure Function [15]. For a symmetric-key enrolment group, each device's key is derived by computing an HMAC-SHA256 of its registration ID keyed with the group key, so the group key itself never has to sit on a device [29].

dps_keys.py: derive a per-device key and a DPS SAS token (standard library only)
import base64, hashlib, hmac, time, urllib.parse

def derive_device_key(group_key_b64: str, registration_id: str) -> str:
    """Per-device key = Base64(HMAC-SHA256(groupKey, registrationId))."""
    key = base64.b64decode(group_key_b64)
    sig = hmac.new(key, registration_id.encode("utf-8"), hashlib.sha256).digest()
    return base64.b64encode(sig).decode()

def sas_token(resource_uri: str, key_b64: str, ttl_s=3600, policy="registration"):
    expiry = int(time.time()) + ttl_s
    uri = urllib.parse.quote(resource_uri, safe="")
    to_sign = f"{uri}\n{expiry}".encode()
    sig = base64.b64encode(hmac.new(base64.b64decode(key_b64), to_sign,
                                    hashlib.sha256).digest()).decode()
    return (f"SharedAccessSignature sr={uri}&sig={urllib.parse.quote(sig, safe='')}"
            f"&se={expiry}&skn={policy}")

id_scope, reg_id = "0ne00000000", "th-000172"
group_key = base64.b64encode(b"demo-group-key-do-not-use").decode()
dev_key = derive_device_key(group_key, reg_id)

# MQTT connection parameters for DPS registration
username = f"{id_scope}/registrations/{reg_id}/api-version=2019-03-31"
password = sas_token(f"{id_scope}/registrations/{reg_id}", dev_key)
register_topic = "$dps/registrations/PUT/iotdps-register/?$rid=1"
print(username, register_topic, sep="\n")

The username format, the 2019-03-31 API version, the register topic and the status-polling topic $dps/registrations/GET/iotdps-get-operationstatus/?$rid={request_id}&operationId={operationId} are taken from Microsoft's MQTT documentation for DPS, which also notes that TPM attestation is not supported over MQTT [30]. In production the group key would live only on the factory provisioning tool or in a hardware security module.

3.3 AWS IoT fleet provisioning by claim

In AWS IoT fleet provisioning by claim, devices are manufactured with a claim certificate whose policy only allows the provisioning MQTT API. On first connection the device calls CreateKeysAndCertificate (or CreateCertificateFromCsr, which keeps the private key on the device), receives a certificateOwnershipToken, and then calls RegisterThing on a named provisioning template, optionally passing parameters such as its serial number to a pre-provisioning hook [12,31]. The ownership token expires after one hour [31].

fleet_provision.py: AWS IoT fleet provisioning by claim with paho-mqtt 2.x
import json, ssl, threading
import paho.mqtt.client as mqtt

ENDPOINT = "example-ats.iot.eu-west-1.amazonaws.com"
TEMPLATE = "ThermostatTemplate"
SERIAL = "TH-000172"
result, done = {}, threading.Event()

def on_message(client, userdata, msg):
    body = json.loads(msg.payload)
    if msg.topic.endswith("/rejected"):
        result["error"] = body; done.set(); return
    if msg.topic == "$aws/certificates/create/json/accepted":
        result.update(body)               # certificatePem, privateKey, certificateOwnershipToken
        client.publish(f"$aws/provisioning-templates/{TEMPLATE}/provision/json", json.dumps({
            "certificateOwnershipToken": body["certificateOwnershipToken"],
            "parameters": {"SerialNumber": SERIAL}}), qos=1)
    elif msg.topic.endswith("/provision/json/accepted"):
        result["thingName"] = body["thingName"]; done.set()

c = mqtt.Client(mqtt.CallbackAPIVersion.VERSION2, client_id=SERIAL)
c.tls_set(ca_certs="AmazonRootCA1.pem", certfile="claim.crt", keyfile="claim.key",
          tls_version=ssl.PROTOCOL_TLS_CLIENT)
c.on_message = on_message
c.connect(ENDPOINT, 8883)
c.subscribe([("$aws/certificates/create/json/+", 1),
             (f"$aws/provisioning-templates/{TEMPLATE}/provision/json/+", 1)])
c.loop_start()
c.publish("$aws/certificates/create/json", "", qos=1)   # empty payload
done.wait(30); c.loop_stop(); c.disconnect()
# Persist result["certificatePem"] / result["privateKey"] to secure storage,
# then reconnect with the new certificate; never reuse the claim cert.
print(result.get("thingName"), result.get("error"))

Security note. A claim credential is shared by many devices, so a leaked claim key lets an attacker mint device identities. AWS recommends restricting what the claim certificate may do and validating requests in a pre-provisioning hook [12]. Voucher-based schemes such as BRSKI and FDO avoid shared secrets by giving each device a unique manufacturer identity from the start [7,25].

4Device discovery

Discovery answers two questions: which devices are out there, and what can each one do. On a local network, Multicast DNS lets devices answer name queries without a DNS server, and DNS-Based Service Discovery lets them advertise service instances such as _coap._udp or _mqtt._tcp using ordinary PTR, SRV and TXT records [32,33]. Constrained devices running CoAP list their resources at the well-known URI /.well-known/core in CoRE Link Format [24], and a CoRE Resource Directory lets sleepy devices register those links with a server that others can query [34]. The W3C Web of Things Discovery Recommendation (December 2023) adds a two-phase process: an introduction phase (for example DNS-SD, a QR code or a well-known URL) followed by an exploration phase in which a Thing Description Directory is queried for detailed metadata [35].

In managed fleets, discovery is mostly the inverse: the device discovers its management server. LwM2M handles this through bootstrapping, in which a Bootstrap-Server writes the Security (Object 0) and Server (Object 1) instances that tell the client which LwM2M server to register with. The server can then use the Discover operation to learn which objects, instances and attributes a client supports [8].

5Device authentication

Authentication proves that a device is the device it claims to be, and (in mutual authentication) that the service is genuine too. ETSI EN 303 645, the European consumer-IoT baseline, makes "no universal default passwords" its first provision, and requires that any password be unique per device or set by the user [36]. 6Device configuration

Modern fleets manage configuration as desired state. The operator writes what the configuration should be, the device reports what it actually is, and the platform computes the difference. AWS IoT Device Shadow documents have desired, reported and a computed delta section, plus a version that increments on every update and is used to reject stale writes [13]. The device receives deltas on $aws/things/thingName/shadow/update/delta and acknowledges by publishing to .../shadow/update [43]. Azure IoT Hub device twins follow the same pattern with desired and reported properties and an incrementing $version [16]. Because the shadow persists while the device is offline, configuration reaches devices that reconnect hours later.

shadow_agent.py: apply shadow deltas safely on the device
import json
import paho.mqtt.client as mqtt

THING = "TH-000172"
BASE = f"$aws/things/{THING}/shadow"
# Validation rules: only known keys, only sane values.
SCHEMA = {"interval": (int, 10, 3600), "setpoint": (float, 5.0, 35.0)}
config = {"interval": 300, "setpoint": 21.0}
last_version = -1

def validate(key, value):
    if key not in SCHEMA: return False
    typ, lo, hi = SCHEMA[key]
    try: v = typ(value)
    except (TypeError, ValueError): return False
    return lo <= v <= hi

def on_delta(client, userdata, msg):
    global last_version
    doc = json.loads(msg.payload)
    if doc["version"] <= last_version:      # out-of-order or duplicate
        return
    last_version = doc["version"]
    accepted, rejected = {}, {}
    for k, v in doc["state"].items():
        (accepted if validate(k, v) else rejected)[k] = v
    config.update({k: SCHEMA[k][0](v) for k, v in accepted.items()})
    # Report what we actually run; report rejects so operators can see them.
    client.publish(f"{BASE}/update", json.dumps({"state": {"reported": {
        **config, "rejected": rejected or None}}}), qos=1)

def on_connect(client, userdata, flags, rc, props=None):
    client.subscribe(f"{BASE}/update/delta", qos=1)
    client.publish(f"{BASE}/update", json.dumps({"state": {"reported": config}}), qos=1)

c = mqtt.Client(mqtt.CallbackAPIVersion.VERSION2, client_id=THING)
c.on_connect = on_connect
c.message_callback_add(f"{BASE}/update/delta", on_delta)
# c.tls_set(...); c.connect(ENDPOINT, 8883); c.loop_forever()

Other configuration channels exist for other device classes. LwM2M servers change configuration with the Write and Write-Attributes operations on object resources [8]. Gateways and routers often use NETCONF, whose candidate datastore and commit model allow a whole configuration to be validated and applied atomically, with data described by YANG modules [10,11]. A device can also publish a Manufacturer Usage Description (MUD) URL so the network can automatically configure access rules limiting whom the device may talk to [44].

7Remote monitoring

Remote monitoring is the continuous collection of telemetry and state from devices so that operators can see the fleet without visiting it. NIST calls the device-side part of this cybersecurity state awareness when it concerns security, but the same channels carry operational metrics [4]. Three monitoring streams matter:

  1. Telemetry: application measurements, ideally in a self-describing format such as SenML, which carries names, units, values and times in JSON or CBOR [45].
  2. State: the reported configuration and firmware version (the shadow or twin), and LwM2M resources that the server can Observe, receiving a Notify whenever the value changes or a period passes [8,46].
  3. Connectivity events: connect and disconnect notifications. AWS IoT publishes lifecycle events on $aws/events/presence/connected/clientId and .../disconnected/clientId, and warns that these messages may arrive out of order or be duplicated, so consumers should order them by timestamp [47].

LwM2M Observe requests can carry notification attributes that tune how chatty a device is: minimum period (pmin), maximum period (pmax), and greater-than, less-than and step thresholds (gt, lt, st) [8]. For example, Write-Attributes /3303/0/5700?pmin=10&pmax=600&st=0.5 asks a temperature sensor to report at most every 10 s, at least every 10 min, and whenever the value moves by 0.5.

8Device health monitoring

Health monitoring asks a narrower question than remote monitoring: is this device working as it should? Its building blocks are a liveness signal (heartbeat), health metrics (battery, memory, signal quality, reboot count, error codes) and a rule for deciding when a device is unhealthy.

8.1 Liveness signals that protocols give you for free

  • MQTT keep-alive. If the server receives no packet within one and a half times the Keep Alive interval, it must close the connection as if the network had failed, and it then publishes the client's Will message if one was set [48].
  • LwM2M registration lifetime. A client must send a registration Update before its lifetime expires; otherwise the server removes the registration [8].
  • Platform lifecycle events such as AWS presence events [47].

8.2 Detecting failures well

Deciding that a device is dead from missing heartbeats is a classic failure-detection problem. Chen, Toueg and Aguilera defined quality-of-service metrics for failure detectors, notably detection time (how long until a crash is suspected), mistake recurrence time and mistake duration (how often and for how long a live process is wrongly suspected) [49]. A fixed timeout trades these off crudely. The φ accrual failure detector of Hayashibara and colleagues instead outputs a continuous suspicion level φ computed from the observed distribution of heartbeat inter-arrival times; each application chooses its own threshold [50]. This suits IoT fleets, where a cellular tracker and a mains-powered gateway have very different heartbeat jitter.

heartbeat_monitor.py: a φ-accrual health monitor for a fleet
import math, statistics, time
from collections import defaultdict, deque

class PhiAccrual:
    """φ = -log10(P(next heartbeat arrives later than now)), normal approximation."""
    def __init__(self, window=100, min_std=0.5):
        self.intervals = deque(maxlen=window)
        self.last = None
        self.min_std = min_std

    def heartbeat(self, t):
        if self.last is not None:
            self.intervals.append(t - self.last)
        self.last = t

    def phi(self, now):
        if len(self.intervals) < 3:
            return 0.0
        mean = statistics.fmean(self.intervals)
        std = max(statistics.pstdev(self.intervals), self.min_std)
        elapsed = now - self.last
        # Survival function of the normal distribution.
        p_later = 0.5 * math.erfc((elapsed - mean) / (std * math.sqrt(2)))
        return -math.log10(max(p_later, 1e-300))

class FleetHealth:
    def __init__(self, suspect=3.0, dead=8.0):
        self.det = defaultdict(PhiAccrual)
        self.metrics = {}
        self.suspect, self.dead = suspect, dead

    def on_heartbeat(self, dev, t, **metrics):
        self.det[dev].heartbeat(t)
        self.metrics[dev] = metrics

    def status(self, dev, now):
        phi = self.det[dev].phi(now)
        m = self.metrics.get(dev, {})
        if phi >= self.dead: return "OFFLINE", phi
        if phi >= self.suspect: return "SUSPECT", phi
        if m.get("batt", 100) < 15 or m.get("err", 0) != 0:
            return "DEGRADED", phi
        return "HEALTHY", phi

if __name__ == "__main__":
    fh, t = FleetHealth(), 0.0
    for i in range(20):                     # 60 s heartbeats with ±2 s jitter
        t += 60 + (2 if i % 2 else -2)
        fh.on_heartbeat("TH-000172", t, batt=80, err=0)
    for late in (60, 63, 66, 90):
        s, phi = fh.status("TH-000172", t + late)
        print(f"{late:>3} s since last beat: {s:8} phi={phi:.1f}")

Fleet-level health is then a matter of aggregating these per-device states: the share of devices offline per site, the battery distribution, or reboot counts per firmware version. A sudden change in such statistics is an anomaly-detection problem, for which point, contextual and collective anomalies need different techniques [51]. AWS IoT Device Defender applies this idea to security: its Detect feature watches device- and cloud-side metrics against rules or machine-learned models, and its Audit feature checks configurations against best practice [52].

9Firmware management

Firmware management is everything around an update except the transfer itself: knowing which firmware every device runs, building and signing images, deciding which devices are eligible for which image, and guaranteeing that only authentic, newer images are installed. NIST's core baseline requires that a device's software can be updated by authorised entities only, using a secure and configurable mechanism [4], and ETSI EN 303 645 devotes a whole provision group to keeping software updated [36].

9.1 The IETF SUIT model

The IETF Software Updates for Internet of Things (SUIT) working group published an architecture in RFC 9019 and an information model in RFC 9124. The architecture separates the firmware image from a signed manifest that describes it, so devices can decide whether to accept an update before downloading or installing the payload [53]. RFC 9124 lists what a manifest must carry and the threats each element addresses, including a monotonically increasing sequence number to prevent rollback to older, vulnerable firmware, vendor and class identifiers to stop an image for one device type being installed on another, and a payload digest [54]. Zandberg and colleagues showed that secure updates built from open standards (SUIT-style manifests, CBOR, COSE signatures and CoAP transport) are practical on low-end microcontrollers [55].

9.2 Signing and key compromise

If a single signing key protects a whole fleet, its compromise is catastrophic. The Update Framework (TUF) addresses this with separate roles (root, targets, snapshot and timestamp), threshold signatures and explicit key rotation, so that compromising one key does not let an attacker push arbitrary updates [56]. NIST SP 800-193 frames firmware resiliency as three principles, protection of firmware and its update path, detection of corrupted or unauthorised firmware, and recovery to a known good state [57], which is exactly what the A/B and rollback mechanisms in §10 implement.

9.3 Firmware inventory

A firmware inventory joins three things: what each device reports it runs (shadow, twin, or LwM2M /3/0/3 Firmware Version), what the release system says was built, and what the deployment system says was targeted [8,13]. Discrepancies, such as a device reporting a version that was never released, are both a fault signal and a security signal.

10OTA updates

Over-the-air (OTA) updating delivers new software to deployed devices over their normal network connection. Bauwens and colleagues review the key principles of OTA updating in the IoT, among them how updates are disseminated through the network, whether whole images or smaller delta or modular updates are sent, and how they are installed, with energy and bandwidth as the dominant constraints on low-power networks [58]. Three properties distinguish a robust OTA system:

  1. Atomicity and recoverability. A power cut during an update must never leave a device unbootable.
  2. Automatic rollback. A new image that boots but does not work must be reverted without human help.
  3. Staged rollout. An update reaches a small group first and the deployment halts automatically if failures rise.

10.1 A/B images and confirm-or-revert

In an A/B scheme the device has two system slots. The update is written to the inactive slot while the device keeps running; the bootloader is told to try the new slot once; and the new software must confirm itself after it starts successfully, otherwise the next boot falls back. Android's A/B (seamless) updates keep two copies of partitions for exactly this reason [59]. Mender uses a dual A/B layout in which the client writes the inactive partition and the update must be committed; if the device reboots before commit, the bootloader rolls back [19]. On microcontrollers, MCUboot supports a test swap that reverts on the next boot unless the application sets the "image OK" flag in the image trailer to make it permanent [23].

ota_agent.py: device-side A/B update with verification, trial boot and rollback (simulation)
import hashlib, json, pathlib

STATE = pathlib.Path("bootstate.json")   # stands in for bootloader environment

def load():
    return json.loads(STATE.read_text()) if STATE.exists() else {
        "active": "A", "trial": None, "tries": 0,
        "seq": {"A": 1, "B": 0}, "version": {"A": "2.4.1", "B": None}}

def save(s): STATE.write_text(json.dumps(s))
def other(slot): return "B" if slot == "A" else "A"

def install(manifest: dict, image: bytes, verify_sig) -> str:
    s = load()
    if not verify_sig(manifest):                       return "REJECTED: bad signature"
    if manifest["seq"] <= s["seq"][s["active"]]:        return "REJECTED: rollback attempt"
    if hashlib.sha256(image).hexdigest() != manifest["sha256"]:
        return "REJECTED: digest mismatch"
    target = other(s["active"])
    pathlib.Path(f"slot_{target}.bin").write_bytes(image)   # inactive slot only
    s["seq"][target], s["version"][target] = manifest["seq"], manifest["version"]
    s["trial"], s["tries"] = target, 0                # request one trial boot
    save(s)
    return f"STAGED in {target}; reboot to test"

def bootloader_select(max_tries=1) -> str:
    """Runs at power-on. Boots the trial slot at most max_tries times."""
    s = load()
    if s["trial"] and s["tries"] < max_tries:
        s["tries"] += 1; save(s); return s["trial"]
    if s["trial"]:                                   # trial never confirmed
        s["trial"] = None; save(s)
    return s["active"]

def confirm_if_healthy(running_slot: str, healthy: bool) -> str:
    """Called by the application after start-up self-tests."""
    s = load()
    if s["trial"] != running_slot:
        return "no trial in progress"
    if healthy:
        s["active"], s["trial"] = running_slot, None; save(s)
        return f"COMMITTED {s['version'][running_slot]}"
    s["trial"] = None; save(s)                       # next boot uses old slot
    return "ROLLBACK requested"

if __name__ == "__main__":
    STATE.unlink(missing_ok=True)
    img = b"\x7fFIRMWARE-2.5.0"
    m = {"seq": 2, "version": "2.5.0", "sha256": hashlib.sha256(img).hexdigest()}
    print(install(m, img, verify_sig=lambda m: True))
    slot = bootloader_select()
    print("booted", slot, "->", confirm_if_healthy(slot, healthy=False))
    print("next boot uses", bootloader_select())
    print(install({**m, "seq": 1}, img, lambda m: True))   # anti-rollback check

Two details matter in real devices. The trial counter must be decremented by the bootloader before jumping to the new image, so a crash loop still ends in rollback; and the anti-rollback sequence number should be stored in tamper-resistant storage, as RFC 9124's rollback-protection requirement intends [23,54]. (In this simulation a rejected trial leaves the higher sequence number recorded for the inactive slot only, so the device can retry the same release later.)

10.2 LwM2M Firmware Update object

LwM2M standardises OTA through Object 5 (Firmware Update). The server either writes the image into resource 0 (Package) or writes a download URI into resource 1 (Package URI) for the client to pull; it then executes resource 2 (Update). Resource 3 (State) reports progress and resource 5 (Update Result) reports the outcome [8].

Eclipse hawkBit is a back-end for rolling out software to edge devices, controllers and gateways [18]. diag_handler.py: a device-side diagnostic command dispatcher
import json, os, shutil, time, collections

LOG = collections.deque(maxlen=2000)          # ring buffer of recent log lines
BOOT_TIME = time.monotonic()
ERRORS = set()                                  # LwM2M-style error codes

def log(msg): LOG.append(f"{time.time():.0f} {msg}")

def self_test():
    checks = {
        "flash_free_ok": shutil.disk_usage("/").free > 10 * 2**20,
        "sensor_ok": os.path.exists("/dev/i2c-1"),
        "clock_sane": time.time() > 1.7e9,
    }
    if not checks["sensor_ok"]: ERRORS.add(8)      # peripheral malfunction
    return 200 if all(checks.values()) else 500, checks

HANDLERS = {
    "selfTest": lambda p: self_test(),
    "getLogs":  lambda p: (200, list(LOG)[-int(p.get("lines", 100)):]),
    "uptime":   lambda p: (200, {"seconds": round(time.monotonic() - BOOT_TIME)}),
    "errors":   lambda p: (200, sorted(ERRORS) or [0]),
}

def dispatch(method: str, payload: str) -> tuple[int, str]:
    """Map a direct-method / job command to a handler; never raise to caller."""
    handler = HANDLERS.get(method)
    if handler is None:
        return 404, json.dumps({"error": f"unknown method {method}"})
    try:
        status, body = handler(json.loads(payload or "{}"))
        log(f"diag {method} -> {status}")
        return status, json.dumps(body)
    except Exception as e:
        return 500, json.dumps({"error": repr(e)})

if __name__ == "__main__":
    log("boot"); print(dispatch("selfTest", "")); print(dispatch("errors", ""))

12Fault management

Fault management detects, isolates and corrects abnormal operation; in FCAPS it covers alarm surveillance, fault localisation, testing and correction [2]. Avižienis and colleagues give the vocabulary that keeps this precise: a fault (for example, a cracked solder joint or a software bug) can be activated to produce an error (an incorrect internal state), which may propagate to a failure (the delivered service deviates from correct service) [62]. Their four means of attaining dependability, namely fault prevention, fault tolerance, fault removal and fault forecasting, map onto fleet practices such as code review, watchdogs and A/B images, field fixes via OTA, and trend analysis of health metrics [62].

12.1 Alarm lifecycle

A practical alarm model has four states: raised when a rule fires, acknowledged when an operator takes ownership, cleared when the condition goes away, and closed after review. Three techniques keep alarm volume manageable: de-duplication (one alarm per device and condition), correlation (one alarm for a gateway outage rather than one per child device) and hysteresis (raise at 15 % battery, clear only above 25 %).

12.2 Avoiding self-inflicted faults: reconnect storms

Large fleets cause their own outages. When a broker restarts, thousands of devices that retry at fixed intervals reconnect in synchronised waves. Exponential backoff spreads retries out, and adding randomness ("jitter") removes the synchronisation; Brooker's analysis for AWS showed that "full jitter" (a random delay between zero and the exponential cap) markedly reduces both total work and completion time compared with plain exponential backoff [63].

backoff.py: reconnect with capped exponential backoff and full jitter
import random, time

def full_jitter(attempt, base=1.0, cap=300.0):
    """sleep = random(0, min(cap, base * 2**attempt))"""
    return random.uniform(0, min(cap, base * 2 ** attempt))

def connect_with_backoff(connect, max_attempts=None):
    attempt = 0
    while max_attempts is None or attempt < max_attempts:
        try:
            return connect()
        except OSError as e:
            delay = full_jitter(attempt)
            print(f"connect failed ({e}); retry {attempt} in {delay:.1f}s")
            time.sleep(delay)
            attempt += 1
    raise TimeoutError("gave up")

Fault-management checklist for a fleet. Hardware and software watchdogs; a crash counter persisted across reboots; automatic rollback of new firmware (§10); jittered reconnects; health rules with hysteresis; alarms correlated by topology (gateway, cell, site); and a remote Reboot and Factory Reset path (LwM2M /3/0/4, /3/0/5) as the last resort [8,57,63].

13Device decommissioning

Decommissioning removes a device from service so that it can no longer connect, act or leak data, while preserving the records needed for audit. It is the stage most often neglected. NIST IR 8259 asks manufacturers to plan, as part of their post-market communication with customers, for how long a device will be supported and what customers should do when it reaches end of life [5]. A sound workflow has five steps:

  1. Quiesce. Stop jobs and rollouts targeting the device; mark it as being retired in the registry so automation leaves it alone.
  2. Revoke credentials. Deactivate or revoke the device certificate so it fails authentication immediately. For X.509, revocation is published through CRLs or answered by OCSP responders [37,64].
  3. Deregister. Remove the device from management servers (LwM2M De-register, a DELETE on the registration location) and from groups, rules and dashboards [8].
  4. Sanitise. Wipe user data, keys and configuration on the device (factory reset) and choose a sanitisation method (clear, purge or destroy) appropriate to the media and its sensitivity, following NIST SP 800-88 Rev. 2 [65]. ETSI EN 303 645 asks that users be given a simple way to erase their data from devices and associated services [36].
  5. Archive and dispose. Keep the registry record, telemetry and audit trail per retention policy; record the disposal method; or, for resale, transfer ownership so a new owner can onboard it, as FIDO Device Onboard supports through ownership vouchers [7].
decommission.py: retire an AWS IoT thing (boto3), idempotent and audited
import json, datetime, boto3
from botocore.exceptions import ClientError

iot = boto3.client("iot")

def decommission(thing: str, reason: str, audit_path="decom-audit.jsonl"):
    steps = []
    # 1. Quiesce: tag the thing so automation skips it
    iot.update_thing(thingName=thing, attributePayload={
        "attributes": {"lifecycle": "decommissioning"}, "merge": True})
    steps.append("flagged")
    # 2. Revoke every certificate attached to the thing
    principals = iot.list_thing_principals(thingName=thing)["principals"]
    for arn in principals:
        cert_id = arn.split("/")[-1]
        iot.update_certificate(certificateId=cert_id, newStatus="REVOKED")
        for pol in iot.list_attached_policies(target=arn)["policies"]:
            iot.detach_policy(policyName=pol["policyName"], target=arn)
        iot.detach_thing_principal(thingName=thing, principal=arn)
        steps.append(f"revoked {cert_id}")
    # 3. Deregister: remove from groups, then delete the thing
    for g in iot.list_thing_groups_for_thing(thingName=thing)["thingGroups"]:
        iot.remove_thing_from_thing_group(thingGroupName=g["groupName"], thingName=thing)
    try:
        iot.delete_thing(thingName=thing)
        steps.append("thing deleted")
    except ClientError as e:
        steps.append(f"delete failed: {e.response['Error']['Code']}")
    # 4–5. Sanitisation is device-side (factory reset) or physical; record it here
    record = {"thing": thing, "reason": reason, "steps": steps,
              "at": datetime.datetime.now(datetime.timezone.utc).isoformat()}
    with open(audit_path, "a") as f:
        f.write(json.dumps(record) + "\n")
    return record

Revoked certificates are kept (not deleted) so the registry can prove which credential belonged to which device. Note that the attribute update in step 1 is lost when the thing is deleted, which is why the script writes its own audit record.

Platform decommissioning. Sometimes the service retires rather than the device. Google retired Cloud IoT Core on 16 August 2023, about a year after announcing it, which forced its customers to migrate entire fleets to other platforms [66]. Standards-based management (LwM2M, MQTT, X.509) and devices whose endpoints and trust anchors can be reconfigured remotely reduce that risk [8,48].

14Fleet management

Fleet management treats devices as a population. Its core tools are:

  • Grouping. Static groups (by customer, site, hardware revision) and dynamic groups defined by a query, whose membership changes as device state changes. AWS fleet indexing indexes registry attributes, shadow state and connectivity so they can be searched and aggregated [67].
  • Bulk operations. Jobs that run a document against a group, with rollout, abort and timeout controls (§10.4) [60].
  • Fleet metrics. Aggregates such as the share of devices connected, firmware-version distribution, or 95th-percentile battery drain per model.
  • Policy. Who may change what, across which group, with which approvals.

15Asset tracking

Asset tracking uses IoT devices to know where things are and what has happened to them: pallets, containers, vehicles, tools, medical equipment. Outdoors, satellite positioning (GNSS) is the default; indoors, where GNSS is unavailable, systems rely on Wi-Fi, Bluetooth Low Energy, ultra-wideband, RFID and other technologies, using techniques such as received signal strength, time of flight, angle of arrival and fingerprinting, each with different accuracy, cost and energy trade-offs [68]. LwM2M's Location object (Object 6) carries latitude, longitude, altitude, radius (uncertainty), velocity and timestamp in a standard form [8].

Location alone is not tracking. GS1's EPCIS 2.0 standard (ratified June 2022) records events about identified objects along five dimensions, which it summarises as what, when, where, why and how; "how" (sensor data such as temperature) is new in version 2.0 [69]. An EPCIS event can say, for example, that pallet X (what) was shipped (why) from dock 4 of site Y (where) at a given time (when) while at 3 °C (how).

geofence.py: haversine distance and enter/exit events for tracked assets
import math

R_EARTH_M = 6_371_000    # mean Earth radius

def haversine_m(lat1, lon1, lat2, lon2):
    p1, p2 = math.radians(lat1), math.radians(lat2)
    dp, dl = p2 - p1, math.radians(lon2 - lon1)
    a = math.sin(dp / 2) ** 2 + math.cos(p1) * math.cos(p2) * math.sin(dl / 2) ** 2
    return 2 * R_EARTH_M * math.asin(math.sqrt(a))

class Geofence:
    def __init__(self, name, lat, lon, radius_m):
        self.name, self.lat, self.lon, self.r = name, lat, lon, radius_m
        self.inside = {}                      # asset -> bool

    def update(self, asset, lat, lon, accuracy_m=0):
        d = haversine_m(self.lat, self.lon, lat, lon)
        was = self.inside.get(asset)
        # Use the fix's uncertainty radius (LwM2M /6/0/3) as hysteresis.
        if d + accuracy_m <= self.r:     now_in = True
        elif d - accuracy_m > self.r:    now_in = False
        else:                           now_in = was       # ambiguous: keep state
        self.inside[asset] = now_in
        if was is not None and now_in != was:
            return {"asset": asset, "fence": self.name,
                    "event": "ENTER" if now_in else "EXIT", "distance_m": round(d)}
        return None

if __name__ == "__main__":
    depot = Geofence("depot", 51.5007, -0.1246, 500)
    track = [(51.5010, -0.1240, 20), (51.5030, -0.1200, 20), (51.5100, -0.1100, 30)]
    for lat, lon, acc in track:
        print(depot.update("pallet-0042", lat, lon, acc))

The haversine formula is numerically well behaved for the short distances typical of geofences, which is why Sinnott recommended it for computing great-circle distances [70].

16Lifecycle management

Lifecycle management ties every previous section together across time, from design to disposal. NIST IR 8259 splits manufacturer responsibilities into pre-market activities (identifying customers and use cases, researching their cybersecurity needs, deciding what to address and how) and post-market activities (communicating with customers about support, updates and end of life) [5]. IEC 62443-4-1 specifies secure development lifecycle requirements for industrial components, including security update management and handling of security-related issues after release [71]. NIST SP 1800-36 treats onboarding as one stage of a managed lifecycle rather than a one-time event, so a device may need to be onboarded again, for example after a factory reset [6].

Regulation is turning lifecycle commitments into obligations. The EU Cyber Resilience Act, Regulation (EU) 2024/2847 of 23 October 2024, covers products with digital elements including most connected devices [72]. Its recitals explain that the support period during which manufacturers handle vulnerabilities should be no less than five years (unless the product's expected use is shorter), and they refer to a 24-hour deadline for an early-warning notification of actively exploited vulnerabilities [72]. For a fleet operator, this makes the "end of support" date as important a registry attribute as the firmware version.

18Exercises with solutions

Exercise 1. Classify each activity under FCAPS: (a) pushing a new reporting interval to 2,000 sensors; (b) raising an alarm when a gateway stops sending heartbeats; (c) revoking a leaked device certificate; (d) charting 95th-percentile message latency per site.

Solution

(a) Configuration; (b) Fault; (c) Security; (d) Performance. Accounting, the fifth area, would cover usage-based billing such as data volume per customer [2].

Exercise 2. An LwM2M client registers with lt=3600 and then loses power. How long might the server keep showing it as registered, and how would you shorten detection without draining the battery?

Solution

Up to one lifetime, about an hour after the last Update, because the server removes a registration only when the lifetime expires without an Update [8]. Options: shorten the lifetime for mains-powered devices only; for battery devices, combine a longer lifetime with an observed resource whose pmax forces periodic notifications, or with a φ-accrual detector that flags "suspect" well before the lifetime ends [50].

Exercise 3. Compute the derived symmetric key for registration ID sensor-01 using the derive_device_key function from §3.2, and explain why the factory must never write the group key itself to devices.

Solution

Run derive_device_key(group_key_b64, "sensor-01"); the result is a Base64-encoded 32-byte HMAC-SHA256 value. If the group key were on devices, extracting it from any one device would let an attacker derive valid keys for every registration ID in the group. Microsoft's guidance is that the group key is not used directly for attestation, only to derive per-device keys [29].

Exercise 4. A shadow has desired: {"interval": 60, "mode": "eco"} and reported: {"interval": 60, "mode": "boost", "fw": "2.4.1"}. What is the delta?

Solution

{"mode": "eco"}. The delta contains only desired fields whose values differ from (or are missing in) reported; fw is reported-only, so it does not appear [13].

Exercise 5. A firmware manifest has sequence number 41 and the device is running sequence 42. The signature and digest are valid. Should the device install it? Which standard requirement applies?

Solution

No. Installing it would be a rollback to an older (possibly vulnerable) image. RFC 9124 requires a monotonically increasing sequence number so devices can reject older manifests even if they are validly signed [54]. The install() function in §10.1 rejects it with "rollback attempt".

Exercise 6. Using the rollout configuration in §10.4 (base 50/min, factor 2, cap 1,000/min, rate increases after every 100 successes), roughly how many minutes does it take to start updates on a 10,000-device group, ignoring failures?

Solution

Approximate the steps: 100 devices at 50/min (2 min), 100 at 100/min (1 min), 100 at 200/min (0.5 min), 100 at 400/min (0.25 min), 100 at 800/min (0.125 min), then the remaining 9,500 at the 1,000/min cap (9.5 min): about 13.4 minutes. The point is that exponential rollout is cautious only at the start; with a high cap, most of the fleet updates quickly, so abort thresholds must be set to trip during the early, slow phase [60].

Exercise 7. Run heartbeat_monitor.py. At roughly how many seconds after the last heartbeat does the device become SUSPECT (φ ≥ 3)? What happens if the jitter is increased to ±20 s?

Solution

With intervals of 58 and 62 s (mean 60, standard deviation 2), φ = 3 corresponds to a survival probability of 10−3, about 3.1 standard deviations above the mean, so about 66 s. With ±20 s jitter the standard deviation is 20 s and the threshold moves to about 122 s. The detector adapts to each device's behaviour, which a single fixed timeout cannot do [49,50].

Exercise 8. Order these decommissioning steps and justify the position of the first two: delete thing, factory reset, revoke certificate, cancel pending jobs, archive telemetry.

Solution

Cancel pending jobs, revoke certificate, delete thing (deregister), factory reset (sanitise), archive telemetry. Jobs are cancelled first so automation does not act on a device mid-retirement; the credential is revoked before deregistration so the device cannot reconnect, or be re-provisioned by claim, in the window between steps [5,37,65]. Archiving can run in parallel but must finish before records are purged.

Exercise 9. 20,000 devices reconnect after a broker restart. With fixed 5 s retries, what load does the broker see? Sketch the effect of full jitter with base 1 s and cap 300 s.

Solution

Fixed retries produce synchronised waves: up to 20,000 connection attempts every 5 s (about 4,000 per second on average, concentrated into spikes). With full jitter, attempt n waits a uniform random time in [0, min(300, 2n)] s, so by the sixth retry attempts are spread over a 64 s window and the waves disappear [63].

Exercise 10. Extend geofence.py to emit EPCIS-style events. Which EPCIS dimension does each field you add fill?

Solution

Add epc or asset ID (what), event time and time-zone offset (when), a read point or business location such as the geofence's site identifier (where), a business step such as "departing" or "arriving" for EXIT and ENTER (why), and sensor readings such as temperature (how) [69].

Exercise 11. Which LwM2M paths would you read to diagnose a tracker that reports "connection lost during download" during an OTA update?

Solution

/5/0/5 (Update Result, value 4 means connection lost during download), /4/0/2 and /4/0/3 (signal strength and link quality), /4/0/8 (cell ID), and /3/0/11 (error code 4, low received signal strength, or 7, IP connectivity failure). A fix might be to schedule downloads when signal is strong or use a smaller delta image [8,58].
