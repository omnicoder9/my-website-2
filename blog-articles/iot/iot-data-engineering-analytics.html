1. Introduction and the reference data pipeline

An Internet of Things (IoT) system exists to turn physical phenomena into decisions. The international IoT reference architecture, ISO/IEC 30141, describes this as a set of domains running from the physical entities and the sensing/actuating devices attached to them, through networks and gateways, to the application and service domains that consume the resulting information [1]. Data engineering is the discipline that makes the middle of that chain reliable: it moves bytes off devices, gives them a time and an identity, checks them, reshapes them, and stores them so that analytics and machine learning (ML) can trust them. Kleppmann's framing of data systems in terms of reliability, scalability and maintainability applies directly to IoT, where the data volume is high, the sources are unreliable, and the cost of a wrong answer is often physical [2].

IoT data has several characteristics that distinguish it from typical business data. It is overwhelmingly time-stamped measurement data; it arrives continuously and out of order because devices buffer readings during connectivity gaps; it is noisy because sensors drift, saturate and fail; and its meaning depends heavily on context (which sensor, mounted where, observing what property of which object), which is why ontologies such as W3C SOSA/SSN model an observation as a sensor's estimate of an observable property of a feature of interest [3]. 2. Data acquisition

2.1 Sensor readings

A sensor reading is an observation: the result of a procedure carried out by a sensor that estimates the value of a property at a point in time [3]. A complete reading therefore carries more than a number. At minimum it needs (i) the value and its unit, (ii) the observed property (e.g. air temperature), (iii) the identity of the sensor/device, (iv) the time at which the phenomenon was observed, and ideally (v) quality information such as accuracy or a status flag. The OGC SensorThings API encodes the same idea with its Observation entity, which links a result and phenomenonTime to a Datastream that in turn names the Sensor, the ObservedProperty and the unit of measurement [6].

Readings may be periodic (a temperature every 10 s), burst/waveform (a 1-s vibration capture at kilohertz rates, usually summarised on the device), or derived (an RMS or a count computed in firmware). Distinguishing raw from derived values matters downstream, because averaging an already-averaged value, or summing RMS values, produces silent errors.

2.2 Telemetry collection

Telemetry is the regular, automated flow of readings and device-health data from devices to a collection point. The dominant open protocol for IoT telemetry is MQTT, an OASIS standard publish/subscribe protocol in which clients publish messages to hierarchical topics on a broker and other clients subscribe to topic filters [7]. Three MQTT features shape telemetry design:

  • Quality of Service (QoS). QoS 0 delivers at most once, QoS 1 at least once (duplicates possible) and QoS 2 exactly once between a client and the broker [7]. Because QoS 1 can duplicate, the pipeline must deduplicate, for example by a per-device sequence number.
  • Retained messages and the Will message. A retained message is stored by the broker and sent to new subscribers; a Will message is published by the broker if a client disconnects ungracefully, giving a cheap liveness signal [7].
  • Topic design. MQTT itself does not prescribe a topic or payload schema. The Eclipse Sparkplug specification adds one for industrial telemetry: a fixed topic namespace (spBv1.0/<group>/<message type>/<edge node>/[<device>]), birth/death certificates (NBIRTH, DBIRTH, NDEATH…) that announce a device's metrics and state, and a Protocol Buffers payload [8].

Behind the broker, telemetry is typically landed in a durable, partitioned log such as Apache Kafka, which stores records in topics split into partitions; ordering is guaranteed only within a partition, so a common practice is to key records by device ID to keep each device's stream ordered [9].

2.3 Event collection

Not every datum is a periodic measurement. Events are discrete occurrences: a door opened, a threshold was crossed, a firmware update failed, a pallet passed an RFID gate. Events are sparse, carry their own semantics, and are often more valuable per byte than telemetry. The CNCF CloudEvents specification provides a vendor-neutral envelope for them; its required context attributes are id, source, specversion and type, with optional time, subject and datacontenttype [10]. Using one envelope for all events lets a single router, schema registry and audit trail serve every event type.

2.4 Data sampling

Sampling converts a continuous signal into discrete values. The Nyquist–Shannon sampling theorem states that a signal containing no frequencies higher than W hertz is completely determined by samples spaced 1/(2W) seconds apart [11,12]. Sampling more slowly than twice the highest frequency present causes aliasing: high-frequency energy folds back and masquerades as a low-frequency component that cannot be removed afterwards. Practical systems therefore place an analog anti-aliasing low-pass filter before the analog-to-digital converter and sample with margin above the Nyquist rate.

IoT designers also choose when to transmit, which is distinct from when to sample:

StrategyHow it worksTypical use

Design tip. Report-by-exception produces an irregular series in which a missing value means "unchanged", not "unknown". Downstream resampling must then use forward-fill up to the heartbeat interval, not interpolation, or it will invent dynamics that never happened.

2.5 Data serialization

Serialization turns an in-memory reading into bytes for transmission. On constrained links every byte costs energy and airtime, so the choice matters.

  • JSON (RFC 8259) is human-readable and universal. JSON exchanged between systems that are not part of a closed ecosystem must be UTF-8, and because numbers have no fixed precision the RFC warns that interoperability is best within the range and precision of IEEE 754 double [13].
  • CBOR (RFC 8949) is a binary data model that is a superset of JSON's, explicitly designed for small code size, fairly small message size and extensibility without version negotiation; it adds byte strings and tagged values such as tag 1 for epoch-based date/time [14].
  • Protocol Buffers are schema-based: each field is identified on the wire by its field number and wire type, and integers use variable-length varint encoding, so field names are never transmitted [15].
  • SenML (RFC 8428) is a standard data model for sensor measurements, with JSON, CBOR and XML representations; base fields such as bn (base name) and bt (base time) are factored out of a pack of records, and units come from a registry (e.g. Cel, %RH, V) [16].

2.6 Timestamping

Every IoT record should carry at least two times: the event time at which the phenomenon was observed (stamped as close to the sensor as possible) and the ingestion time at which the platform received it. Stream processors distinguish these explicitly, and correct results for windows and joins depend on event time, not on processing time [17,18].

  • Format. RFC 3339 profiles ISO 8601 for Internet use, e.g. 2026-11-15T19:28:33.250Z; "Z" denotes UTC and numeric offsets such as +01:00 are allowed [19,20]. Store UTC and convert only for display.
  • Clock synchronization. NTPv4 (RFC 5905) synchronizes clocks over packet networks and can usually keep time within tens of milliseconds over the public Internet and better than a millisecond on LANs under good conditions [21]. IEEE 1588 Precision Time Protocol (PTP) targets sub-microsecond synchronization on networks with hardware time-stamping, as needed for synchrophasors or motion control [22].
  • Epoch pitfalls. NTP's 64-bit timestamp counts 32-bit seconds from 1 January 1900; the first NTP era wraps in 2036, and RFC 5905 defines era numbers to disambiguate [21].
  • Ordering without trusted clocks. When device clocks cannot be trusted, a monotonically increasing per-device sequence number gives a reliable order and gap detection. This is a practical instance of Lamport's observation that a logical "happened-before" order can be maintained without synchronized physical clocks [23].
Rule of thumb. A battery device that wakes from deep sleep may have no valid wall-clock time. Have it send its sequence number and a monotonic uptime offset; let the gateway convert to UTC using its own NTP-disciplined clock and the measured transmission delay.

2.7 Device metadata

Metadata turns numbers into information. Useful device metadata includes identity (serial, hardware revision), configuration (sampling rate, calibration coefficients and date), firmware version, installation context (site, asset, mounting position, location), and ownership. Two standards provide shared vocabularies:

  • W3C SOSA/SSN models sosa:Sensor, sosa:Observation, sosa:ObservableProperty, sosa:FeatureOfInterest and sosa:Platform (the thing a sensor is mounted on) [3].
  • OGC SensorThings API defines a REST/JSON data model with Thing, Location, HistoricalLocation, Datastream, Sensor, ObservedProperty, Observation and FeatureOfInterest entities [6].

Metadata changes over time (a sensor is moved, recalibrated or re-flashed). It should therefore be stored versioned with validity intervals, so that each historical reading can be joined to the metadata that was true when it was taken (see the as-of join in Section 3.7). Sparkplug birth certificates are a protocol-level mechanism for announcing a device's metric definitions whenever it (re)connects [8].

2.8 Data validation

Validation should happen as early as possible (on the gateway or at ingestion) so that bad data is quarantined rather than silently averaged into results. ISO/IEC 25012 defines fifteen data-quality characteristics, including accuracy, completeness, consistency, credibility, currentness, precision and traceability; these make good headings for an IoT validation policy [24]. Typical checks are:

  1. Syntactic/schema checks — required fields, types, enumerations, expressed declaratively in JSON Schema (draft 2020-12) or enforced by a Protobuf/Avro schema [15,25].
  2. Range/physical plausibility — value within the sensor's measurement range and physically possible (relative humidity 0–100 %).
  3. Temporal checks — timestamp not in the future or excessively stale; sequence number strictly increasing (detects duplicates from QoS 1 and replays).
  4. Rate-of-change and "stuck sensor" checks — a 20 °C jump in one second or a perfectly constant value for hours both indicate sensor faults.
  5. Cross-sensor consistency — e.g. dew point not above air temperature.
Listing — s2_validate.pyPython · executed
import math, time

SCHEMA = {  # field: (type, min, max)
    "temp": (float, -40.0, 85.0),   # typical industrial sensor range
    "rh":   (float, 0.0, 100.0),
    "batt": (float, 2.0, 4.3),
}

def validate(msg, last_seq, now=None, max_skew_s=300):
    errors = []
    now = time.time() if now is None else now
    for field, (typ, lo, hi) in SCHEMA.items():
        v = msg.get(field)
        if not isinstance(v, (int, float)) or isinstance(v, bool):
            errors.append(f"{field}: missing or not numeric")
        elif math.isnan(v) or not (lo <= v <= hi):
            errors.append(f"{field}: {v} outside [{lo}, {hi}]")
    if abs(msg.get("t", 0) - now) > max_skew_s:
        errors.append("t: timestamp skew too large")
    if last_seq is not None and msg.get("seq", -1) <= last_seq:
        errors.append("seq: duplicate or out-of-order")
    return errors

msg = {"dev": "th-0042", "t": 1763234913.25, "temp": 121.0,
       "rh": 48.2, "batt": 3.71, "seq": 1287}
print(validate(msg, last_seq=1287, now=1763234915.0))

3. Data processing

3.1 Stream processing

Stream processing computes results continuously over unbounded data. The Dataflow model, which underlies Apache Beam and influenced Apache Flink and Spark Structured Streaming, decomposes every streaming computation into four questions: what is computed (transformations), where in event time (windowing), when in processing time results are emitted (triggers, driven by watermarks), and how refinements relate (accumulation) [17].

  • Windows. Tumbling (fixed, non-overlapping), sliding (fixed length, overlapping by a slide interval) and session windows (bounded by gaps of inactivity) [17].
  • Watermarks. A watermark with timestamp t asserts that event time has progressed to t and no more elements with timestamp ≤ t are expected; windows whose end is before the watermark can be finalised [18]. Elements arriving after the watermark are late and are either dropped, sent to a side output, or used to update an already-emitted result within an allowed lateness.
  • State and fault tolerance. Stream processors keep per-key state (running sums, the last value, a model) and checkpoint it so that processing can resume after failure; Flink and Spark Structured Streaming document exactly-once state semantics when sources are replayable [26,27].

The listing below is a self-contained, dependency-free tumbling-window operator with an event-time watermark and allowed lateness. It illustrates what a framework such as Flink does internally.

Listing — s4_stream.pyPython · executed
from collections import defaultdict

WINDOW = 60          # tumbling window length, seconds (event time)
LATENESS = 10        # allowed lateness before a window is closed

class TumblingAverager:
    def __init__(self):
        self.windows = defaultdict(lambda: [0.0, 0])   # (dev, start) -> [sum, n]
        self.watermark = float("-inf")

    def on_event(self, dev, ts, value):
        start = ts - ts % WINDOW
        if start + WINDOW <= self.watermark:
            return [("LATE-DROPPED", dev, ts, value)]
        acc = self.windows[(dev, start)]
        acc[0] += value; acc[1] += 1
        # Watermark: max event time seen minus allowed lateness
        self.watermark = max(self.watermark, ts - LATENESS)
        return self._fire()

    def _fire(self):
        out = []
        for (dev, start) in sorted(list(self.windows)):
            if start + WINDOW <= self.watermark:
                s, n = self.windows.pop((dev, start))
                out.append((dev, start, round(s / n, 2), n))
        return out

op = TumblingAverager()
events = [("a", 5, 20.0), ("a", 30, 22.0), ("a", 65, 23.0),
          ("a", 58, 21.0),   # late but within allowed lateness
          ("a", 75, 24.0), ("a", 130, 25.0), ("a", 40, 99.0)]  # last is too late
for e in events:
    for result in op.on_event(*e):
        print(result)
Output
('a', 0, 21.0, 3)
('a', 60, 23.5, 2)
('LATE-DROPPED', 'a', 40, 99.0)

The event at t = 58 s arrives after the event at 65 s but is still accepted because the watermark (65 − 10 = 55 s) has not yet passed the end of window [0, 60). The event at t = 40 s arrives when the watermark is at 120 s and is dropped. Exercise 3 asks what changes with zero allowed lateness.

3.2 Batch processing

Batch processing computes over a bounded, complete dataset, typically hours or days of history in a data lake. MapReduce popularised fault-tolerant parallel batch computation on commodity clusters [28], and Apache Spark generalised it with in-memory resilient distributed datasets and a unified engine for SQL, streaming and ML [29]. For IoT history, columnar file formats such as Apache Parquet are the norm because analytical queries read a few columns (say, temp and ts) across billions of rows, and columnar layout enables efficient compression and encoding per column [30].

How should batch and stream coexist? The Lambda architecture runs a batch layer (recomputes accurate views from the immutable master dataset), a speed layer (low-latency incremental views over recent data) and a serving layer that merges them [4]. Kreps proposed the Kappa architecture as a simplification: keep a single stream-processing code path and reprocess history by replaying the retained log through a new version of the job [5]. 3.3 Data transformation and normalization

Transformation reshapes data: parsing, unit conversion, renaming to a canonical schema, pivoting from "one row per reading" (long/narrow) to "one column per signal" (wide), and resampling irregular readings onto a regular time grid. pandas, whose core data structures were introduced by McKinney [31], provides time-aware indexing, resample, rolling windows and time-zone handling for exactly this work [32].

Normalization has two meanings in IoT. Schema normalization maps heterogeneous vendor payloads into one canonical model (one unit per quantity, one naming convention, SenML or SensorThings-style records [6,16]). Numeric normalization rescales features for comparison and ML: the z-score (x − μ)/σ, min–max scaling to [0, 1], or robust scaling using the median and interquartile range. Compute scaling statistics per device (or per device type) when sensors have different baselines, and compute them only on training data to avoid leakage.

3.4 Filtering

"Filtering" covers two different operations:

  • Record filtering removes records: invalid readings (Section 2.8), duplicates, records from decommissioned devices, or values inside a deadband.
  • Signal filtering attenuates noise. The moving average is optimal-ish for white noise but smears steps; the exponentially weighted moving average (EWMA), zt = λxt + (1 − λ)zt−1, needs only one value of state and was introduced for process monitoring by Roberts [33]; the running median removes impulsive spikes while preserving edges; the Kalman filter (Section 5.5) is the optimal linear estimator when the process and noise models are known [34].
EWMA: z_t = λ·x_t + (1 − λ)·z_(t−1), 0 < λ ≤ 1 (small λ → heavier smoothing) Moving average: y_t = (1/N)·Σ_(i=0..N−1) x_(t−i)

3.5 Aggregation

Aggregation summarizes many readings into fewer: per window (count, mean, min, max, standard deviation, percentiles), per device group, or per site. Two practical rules matter. First, keep count alongside every mean so that aggregates can be re-aggregated correctly (a mean of means is wrong when windows have different counts). Second, store min/max with downsampled data so that spikes remain visible after rollup. Time-series databases implement automated rollups ("continuous aggregates" in TimescaleDB, downsampling tasks in InfluxDB) for exactly this purpose [35,36].

Raw IoT series also compress extremely well because consecutive timestamps and values are similar. Facebook's Gorilla time-series database encodes timestamps with delta-of-delta coding and values by XOR-ing each float with its predecessor, reducing an average 16-byte data point to about 1.37 bytes [37].

3.6 Anomaly detection (in the stream)

Chandola and colleagues distinguish point anomalies (a single extreme value), contextual anomalies (normal in general but abnormal in context, such as 25 °C in a freezer) and collective anomalies (a sequence that is abnormal as a whole) [38]. In a stream processor the first line of defence is cheap, explainable statistics:

  • Streaming z-score. Welford's algorithm updates the mean and variance one value at a time without storing history and without the catastrophic cancellation of the naïve Σx² formula [39].
  • Hampel identifier. Flags a point whose distance from the rolling median exceeds k robust standard deviations, where the robust standard deviation is 1.4826 × the median absolute deviation (MAD); the median and MAD resist the very outliers being searched for [40,41].
Listing — s5_anomaly.pyPython · executed
import math, numpy as np

class StreamingZScore:
    """Welford's online mean/variance with a z-score alarm."""
    def __init__(self, threshold=4.0, warmup=30):
        self.n, self.mean, self.m2 = 0, 0.0, 0.0
        self.k, self.warmup = threshold, warmup

    def update(self, x):
        is_anom = False
        if self.n >= self.warmup:
            sd = math.sqrt(self.m2 / (self.n - 1))
            is_anom = sd > 0 and abs(x - self.mean) / sd > self.k
        if not is_anom:                 # don't let outliers poison the baseline
            self.n += 1
            d = x - self.mean
            self.mean += d / self.n
            self.m2 += d * (x - self.mean)
        return is_anom

def hampel(x, half_window=10, n_sigma=4.0):
    """Flag points far from the rolling median (robust to outliers)."""
    x = np.asarray(x, float); flags = np.zeros(len(x), bool)
    for i in range(half_window, len(x) - half_window):
        w = x[i - half_window:i + half_window + 1]
        med = np.median(w); mad = 1.4826 * np.median(np.abs(w - med))
        flags[i] = mad > 0 and abs(x[i] - med) > n_sigma * mad
    return flags

rng = np.random.default_rng(1)
signal = 50 + rng.normal(0, 1, 500)
signal[[120, 300, 301, 450]] += [9, -8, 12, 7]          # injected faults
det = StreamingZScore()
print("z-score :", [i for i, v in enumerate(signal) if det.update(v)])
print("Hampel  :", np.flatnonzero(hampel(signal)).tolist())

3.7 Data enrichment

Enrichment joins telemetry with reference data: device registry, asset hierarchy, site location, product or batch being processed, weather, tariff. In streams this is a stream-table join, where the table is a changelog of the reference data [2]. The subtle part is temporal correctness: a reading must be joined with the metadata that was valid at the reading's event time, not with today's metadata. In pandas this is an as-of join [32]:

import pandas as pd

readings = pd.DataFrame({
    "ts": pd.to_datetime(["2026-11-15T08:00Z", "2026-11-15T09:30Z", "2026-11-15T11:00Z"]),

# Slowly changing device metadata: which room / firmware a device had, valid from 'ts'

    "device": ["th-0042"] * 2,

3.8 Event correlation

Event correlation finds meaningful patterns across multiple events, devices or streams: "door opened and then temperature rose by 2 °C within five minutes", or "three neighbouring smoke detectors alarm within 30 s". Luckham's complex event processing (CEP) formalised this as detecting patterns over event streams using causal and temporal relationships, and deriving higher-level "complex events" from them [42]. Engines such as FlinkCEP express patterns declaratively (sequence, followed-by, within-time constraints) [43]. A hand-written state machine shows the idea:

from collections import deque

WINDOW_S = 300   # correlate events that occur within 5 minutes

class DoorThenWarmRule:
    """Alarm if a 'door_open' is followed by a temperature rise >= 2 degC
    in the same room within WINDOW_S, and no 'door_close' came in between."""
    def __init__(self):
        self.open_doors = {}                 # room -> (ts, temp at open)
        self.last_temp = {}

    def on_event(self, ev):
        room, ts, kind = ev["room"], ev["ts"], ev["type"]
        if kind == "temp":
            self.last_temp[room] = ev["value"]
            if room in self.open_doors:
                t_open, temp0 = self.open_doors[room]
                if ts - t_open > WINDOW_S:
                    del self.open_doors[room]          # pattern expired
                elif temp0 is not None and ev["value"] - temp0 >= 2.0:
                    del self.open_doors[room]
                    return f"ALARM {room}: door open {ts - t_open:.0f}s, +{ev['value'] - temp0:.1f} degC"
        elif kind == "door_open":
            self.open_doors[room] = (ts, self.last_temp.get(room))
        elif kind == "door_close":
            self.open_doors.pop(room, None)
        return None

rule = DoorThenWarmRule()
stream = [{"room": "A", "ts": 0, "type": "temp", "value": 3.9},
          {"room": "A", "ts": 10, "type": "door_open"},
          {"room": "B", "ts": 15, "type": "door_open"},
          {"room": "B", "ts": 40, "type": "door_close"},
          {"room": "A", "ts": 120, "type": "temp", "value": 5.0},
          {"room": "A", "ts": 240, "type": "temp", "value": 6.2}]

4. Data analysis

4.1 Statistical analysis

Descriptive statistics (mean, median, standard deviation, percentiles, histograms) and correlation analysis are the first step on any IoT dataset; the NIST/SEMATECH e-Handbook is a free, authoritative guide to exploratory data analysis and process monitoring [41]. For monitoring, statistical process control is particularly relevant:

  • Shewhart charts plot a statistic against control limits, conventionally at ±3σ around the centre line, separating common-cause from special-cause variation [41,44].
  • EWMA charts detect small, persistent shifts better than Shewhart charts by smoothing successive observations [33].
  • CUSUM (cumulative sum) charts accumulate deviations from a target and signal when the sum crosses a decision interval, which makes them sensitive to small sustained shifts [45].
CUSUM (upper): S_t = max(0, S_(t−1) + x_t − (μ0 + k)), alarm when S_t > h

4.2 Time-series analysis

Most IoT signals combine a trend, one or more seasonal cycles (daily, weekly, machine cycle) and a remainder. STL decomposes a series into these three components with locally weighted regression (loess) and is robust to outliers [46]. Autocorrelation and partial autocorrelation plots reveal persistence and periodicity; many models require stationarity (constant mean and variance), achieved by differencing or transformation. The classical modelling families are ARIMA [47] and exponential smoothing (ETS); Hyndman and Athanasopoulos give a modern, open-access treatment of both, including time-series cross-validation [48].

Common pitfall. Never shuffle time-series data into random train/test splits. Evaluate forecasts on a rolling origin: train on data up to time t, test on t + 1…t + h, advance t and repeat [48].

4.3 Predictive analytics

Predictive analytics estimates future or unobserved values: next-day energy demand, the probability that a compressor fails within 30 days, the expected arrival time of a truck. Methods range from the statistical models above to gradient-boosted trees and random forests on engineered features [49], and recurrent neural networks such as LSTMs, which were designed to learn long-range temporal dependencies [50]. In IoT the dominant success factor is usually feature engineering on domain-meaningful windows (RMS, kurtosis, spectral band energy, slopes) rather than the choice of model.

4.4 Trend detection

A trend is a persistent, monotonic change, such as gradually rising bearing vibration or falling battery capacity. The non-parametric Mann–Kendall test asks whether later values tend to be larger than earlier ones: it sums the signs of all pairwise differences, S = Σi<j sgn(xj − xi), and under the null hypothesis of no trend S is approximately normal with variance n(n − 1)(2n + 5)/18 [51,52]. The Theil–Sen estimator measures the magnitude as the median of all pairwise slopes, which is robust to outliers [53]. Neither test assumes normally distributed data, which suits noisy sensor series (though serial correlation inflates significance and should be addressed by prewhitening or block methods).

import math, numpy as np

def mann_kendall(x):
    """Mann-Kendall trend test (no ties correction). Returns S, Z, two-sided p."""
    x = np.asarray(x); n = len(x)
    s = sum(np.sign(x[j] - x[i]) for i in range(n - 1) for j in range(i + 1, n))
    var = n * (n - 1) * (2 * n + 5) / 18
    z = (s - np.sign(s)) / math.sqrt(var) if s != 0 else 0.0
    p = math.erfc(abs(z) / math.sqrt(2))
    return s, z, p

def sen_slope(x):
    """Theil-Sen estimator: median of all pairwise slopes."""
    n = len(x)
    return float(np.median([(x[j] - x[i]) / (j - i) for i in range(n) for j in range(i + 1, n)]))

def haversine_km(lat1, lon1, lat2, lon2, r=6371.0088):
    p1, p2 = math.radians(lat1), math.radians(lat2)
    dphi, dlmb = p2 - p1, math.radians(lon2 - lon1)
    a = math.sin(dphi / 2)**2 + math.cos(p1) * math.cos(p2) * math.sin(dlmb / 2)**2
    return 2 * r * math.asin(math.sqrt(a))

4.5 Fault detection

Fault detection asks "is something wrong now?"; fault diagnosis asks "what, and where?". ISO 13374-1 standardises the data-processing chain for machine condition monitoring as six blocks: data acquisition, data manipulation, state detection, health assessment, prognostic assessment and advisory generation [54] (Figure 7). Faults may be detected by limit checks against standards (ISO 20816-1 defines vibration-severity evaluation zones A–D for machines [55]), by model residuals (the difference between a measured value and a physics or data-driven model's prediction), or by the anomaly detectors of Sections 3.6 and 5.6.

In IoT, it is equally important to detect sensor faults (bias, drift, stuck-at, spikes, dropouts) as opposed to process faults; a stuck-at value can look perfectly healthy to a threshold rule. Redundant sensors and cross-checks (Section 5.5) help tell the two apart.

4.6 Predictive maintenance

Maintenance strategies range from reactive (run to failure) through preventive (fixed intervals) to condition-based and predictive maintenance (PdM), where interventions are scheduled from the measured condition and predicted remaining useful life (RUL). Jardine and colleagues' review describes condition-based maintenance as three steps, data acquisition, data processing, and maintenance decision-making, and splits the analysis into diagnostics and prognostics [56]. The value of PdM comes from avoiding both unplanned downtime and unnecessary preventive replacements; its prerequisites are labelled failure history (or a physics model), sensors that respond to the failure mode of interest, and a maintenance organization that can act on predictions. A widely used open benchmark is NASA's C-MAPSS turbofan engine run-to-failure simulation dataset [57]. Modelling details follow in Section 5.4.

4.7 Behavioral analysis

Behavioral analysis profiles how entities normally behave and detects deviations. In IoT the entity may be a person or space (occupancy patterns from motion and CO2 sensors, used to drive HVAC), a machine (duty cycles, start/stop frequency) or the device itself. Device behaviour is especially useful for security: Sivanathan and colleagues showed that IoT devices can be identified and classified from network-traffic characteristics such as activity cycles, port numbers, signalling patterns and cipher suites [58], which makes behavioural baselines effective for spotting compromised or misconfigured devices. Typical techniques include daily/weekly profiles (e.g. a median curve per hour of the week with percentile bands), clustering of usage patterns, and Markov models of state transitions.

4.8 Geospatial analysis

Fleet, logistics, agriculture and smart-city applications attach location to readings. GeoJSON (RFC 7946) is the standard interchange format; it uses the WGS 84 datum and, a frequent source of bugs, orders coordinates as [longitude, latitude] [59]. Core operations are:

  • Distance. The haversine formula computes great-circle distance on a sphere and is numerically well-conditioned for small distances [60]; the listing in Section 4.4 uses the GRS 80 mean Earth radius of 6371.0088 km [61]. For survey-grade accuracy use ellipsoidal (geodesic) methods.
  • Geofencing. Point-in-polygon or distance-to-point tests trigger events when assets enter or leave zones.
  • Spatial indexing and aggregation. Uber's H3 system tiles the globe with hexagons at 16 resolutions (0–15), built from 122 base cells, and is convenient for aggregating readings into uniform cells [62]. Spatial databases such as PostGIS provide indexes, spatial joins and geodesic functions [63].
  • Clustering and simplification. DBSCAN finds dense clusters of arbitrary shape (for instance stop locations in GPS traces) and labels sparse points as noise [64]; the Douglas–Peucker algorithm simplifies tracks by discarding points within a tolerance of the simplified line [65].

5.1 Machine learning at the edge

Edge computing moves computation close to where data is produced. Shi and colleagues motivate it by response-time requirements, bandwidth cost, battery life, and data privacy [66]. Edge inference converts high-rate raw data (audio, vibration, video) into low-rate insights (a class label, an anomaly score), which is often the only economically viable way to use such data over constrained networks.

5.2 TinyML

TinyML is machine learning on ultra-low-power microcontrollers, typically consuming milliwatts or less, so that inference can run always-on from a battery [67]. TensorFlow Lite for Microcontrollers (TFLM) is a widely used runtime for this class of device; its authors describe an interpreter-based design with no dynamic memory allocation, where all tensors live in a single, statically sized "tensor arena" provided by the application [69]. MLPerf Tiny standardises benchmarking with four tasks: keyword spotting, visual wake words, image classification and anomaly detection [68].

Model compression is essential. Quantization maps real values to 8-bit integers through an affine mapping r = S(q − Z) with scale S and zero point Z, enabling integer-only arithmetic and reducing weight storage four-fold relative to 32-bit floats [70]. Pruning, knowledge distillation and architecture search for small networks complement it.

  static tflite::MicroMutableOpResolver<3> resolver;

  if (interpreter.Invoke() != kTfLiteOk) return -1;
  TfLiteTensor* out = interpreter.output(0);
  int best = 0;
  for (int c = 1; c < out->dims->data[1]; ++c)
    if (out->data.int8[c] > out->data.int8[best]) best = c;

5.3 Computer vision

Cameras are the richest IoT sensors. Convolutional neural networks (CNNs) learn hierarchical visual features and underpin modern vision [72]. For embedded use, MobileNets factorise standard convolutions into depthwise and pointwise (1×1) convolutions, cutting computation substantially with a small accuracy cost, and expose width and resolution multipliers to trade accuracy for latency [73]. YOLO frames object detection as a single regression from image to bounding boxes and class probabilities in one network evaluation, enabling real-time detection [74]. At the TinyML extreme, the Visual Wake Words dataset (derived from COCO) defines a binary "person / no person" task sized for microcontrollers [75], and is one of the MLPerf Tiny tasks [68]. Classical libraries such as OpenCV remain indispensable for capture, calibration and pre-processing [76].

IoT vision applications include visual inspection on production lines, people counting and occupancy, meter reading, safety-gear compliance and traffic monitoring. Running inference on the camera and transmitting only events or counts also reduces the privacy exposure of transmitting raw video, an argument made for edge processing generally [66].

5.4 Predictive maintenance models

PdM models fall into three families: classification ("will it fail within w cycles?"), regression of RUL, and survival/degradation models. For RUL regression on run-to-failure data such as C-MAPSS [57], a common choice is a piecewise-linear target that is held constant early in life, because degradation is not observable when a machine is new [77]. Leakage alert. Split by unit (machine), never by row. Rows from the same machine are highly correlated, so a random row split lets the model "recognise" machines it will be tested on and wildly overstates accuracy. Likewise, features must use only past data at each time step.

Sequence models (LSTMs [50], 1-D CNNs) can learn features directly from the raw multivariate series, at the cost of more data and less interpretability. Whatever the model, evaluate on the business question: lead time before failure, false-alarm cost, and how many failures would have been caught.

5.5 Sensor fusion

Sensor fusion combines several imperfect sensors into an estimate better than any one alone. The canonical tool is the Kalman filter, which recursively estimates the state of a linear dynamic system from noisy measurements by alternating a predict step (propagate the state and its uncertainty through the process model) and an update step (correct with the measurement, weighted by the Kalman gain) [34,79]. One of its first practical applications was navigation for NASA's Apollo program [80].

Predict: x̂⁻_k = A·x̂_(k−1) + B·u_k P⁻_k = A·P_(k−1)·Aᵀ + Q Update: K_k = P⁻_k·Hᵀ·(H·P⁻_k·Hᵀ + R)⁻¹ x̂_k = x̂⁻_k + K_k·(z_k − H·x̂⁻_k) P_k = (I − K_k·H)·P⁻_k

For orientation from an inertial measurement unit (IMU), a complementary filter is the lightweight workhorse: gyroscopes are smooth but drift (integrated bias), accelerometers are drift-free but noisy and disturbed by linear acceleration, so the filter high-passes the integrated gyro and low-passes the accelerometer tilt. Mahony and colleagues formalised nonlinear complementary filters on the rotation group SO(3) [81], and Madgwick's gradient-descent filter is a popular low-cost alternative for IMU and MARG (magnetic, angular rate and gravity) sensors [82].

import numpy as np

def kalman_1d(z, q=1e-4, r=0.25, x0=0.0, p0=1.0):
    """Scalar Kalman filter for a slowly varying level (random-walk model)."""
    x, p, out = x0, p0, []
    for zk in z:
        p = p + q                     # predict: x_k = x_{k-1} + w,  w ~ N(0, q)
        k = p / (p + r)               # Kalman gain
        x = x + k * (zk - x)          # update with measurement z_k = x_k + v, v ~ N(0, r)
        p = (1 - k) * p
        out.append(x)
    return np.array(out)

def complementary_pitch(acc_pitch, gyro_rate, dt=0.01, alpha=0.98):
    """Fuse accelerometer tilt (noisy, unbiased) with gyro rate (smooth, drifts)."""
    theta, out = acc_pitch[0], []
    for a, w in zip(acc_pitch, gyro_rate):
        theta = alpha * (theta + w * dt) + (1 - alpha) * a
        out.append(theta)
    return np.array(out)

rng = np.random.default_rng(3)
true = np.full(400, 22.0)
z = true + rng.normal(0, 0.5, 400)
est = kalman_1d(z, x0=z[0])
print(f"raw RMSE {np.sqrt(np.mean((z-true)**2)):.3f}  ->  Kalman RMSE {np.sqrt(np.mean((est[50:]-true[50:])**2)):.3f}")

gyro_only = pitch[0] + np.cumsum(gyro) * 0.01

5.6 Anomaly detection with machine learning

When "normal" is multivariate and nonlinear, learned detectors outperform per-signal thresholds [38]. Isolation Forest exploits the fact that anomalies are few and different: random axis-parallel splits isolate them in fewer steps, so a short average path length in an ensemble of random trees signals an anomaly [83]. It trains on unlabelled data, is fast, and works well on engineered features. Autoencoders trained on normal data flag inputs with high reconstruction error, and are the reference approach of the MLPerf Tiny anomaly-detection task, which uses machine-sound data [68]. Forecast-residual methods flag observations far from a time-series model's prediction (Section 4.2).

5.7 Reinforcement learning

Reinforcement learning (RL) learns a policy that maps states to actions by maximising cumulative reward through interaction, formalised as a Markov decision process [84]. Q-learning learns action values with the update Q(s,a) ← Q(s,a) + α[r + γ maxa′ Q(s′,a′) − Q(s,a)], and converges to the optimal values under standard conditions [85]. Deep Q-networks replace the table with a neural network, which enabled learning directly from high-dimensional inputs [86]. IoT applications include HVAC and building-energy control, demand response, and adaptive duty cycling of sensors and radios. Because exploration on real equipment can be costly or unsafe, RL controllers are usually trained in simulation or on a digital twin and deployed with safety constraints and fall-back rules.

Listing — s11_qlearn.pyPython · executed
import numpy as np

# Toy thermostat: states = room temp 15..25 degC, actions = 0 off, 1 heat
rng = np.random.default_rng(0)
temps = np.arange(15, 26); Q = np.zeros((len(temps), 2))
alpha, gamma, eps = 0.1, 0.9, 0.1

def step(s, a):
    t = temps[s] + (1 if a == 1 else -1) * (rng.random() < 0.8)
    t = int(np.clip(t, 15, 25))
    reward = -abs(t - 21) - 0.3 * a                 # comfort penalty + energy cost
    return t - 15, reward

for episode in range(2_000):
    s = int(rng.integers(len(temps)))               # random start state each episode
    for _ in range(50):
        a = int(rng.integers(2)) if rng.random() < eps else int(Q[s].argmax())
        s2, r = step(s, a)
        Q[s, a] += alpha * (r + gamma * Q[s2].max() - Q[s, a])   # Q-learning update
        s = s2
print("policy (1=heat):", dict(zip(temps.tolist(), Q.argmax(1).tolist())))

5.8 Intelligent automation

Intelligent automation closes the loop from insight to action: an anomaly score opens a maintenance work order, a predicted demand peak pre-cools a building, a vision model rejects a defective part. A robust design layers three mechanisms:

  1. Deterministic safety rules that always apply (interlocks, physical limits) and can override any model.
  2. Model-driven decisions (predictions, RL policies) operating inside those limits, with confidence thresholds below which they defer.
  3. Human-in-the-loop escalation for low-confidence or high-impact actions, with feedback captured as labels for retraining.

The ISO 13374 chain ends in exactly this step, "advisory generation" [54]. Event-driven automation is naturally built on the stream-processing and CEP tools of Section 3 [43], and low-code tools such as Node-RED are widely used for wiring device events to actions on gateways [87].

5.9 Federated learning

Federated learning (FL) trains a shared model across many devices or sites while the raw data stays local. In Federated Averaging (FedAvg), each round the server sends the current model to a fraction of clients; each client runs several epochs of local stochastic gradient descent on its own data; and the server replaces the global model with the average of client models weighted by their number of samples, w ← Σk (nk/n) wk [88]. McMahan and colleagues reported that this reduced the number of communication rounds needed by 10–100× compared with synchronised stochastic gradient descent [88]. FL was deployed at scale for next-word prediction in Google's Gboard keyboard [89].

Federated learning is not automatically private: model updates can leak information. Secure aggregation protocols let the server learn only the sum of client updates [90], and differential privacy can bound what any individual contributes [91]. IoT data are also strongly non-IID (each factory, home or vehicle sees a different distribution), which slows or destabilises FedAvg; FedProx adds a proximal term that keeps local models close to the global one [92]. Kairouz and colleagues survey these open problems in depth [91]. Frameworks such as Flower simplify building FL systems across heterogeneous clients [93].

import numpy as np

rng = np.random.default_rng(42)
TRUE_W = np.array([2.0, -1.0, 0.5])

def make_client(n, shift):
    X = rng.normal(shift, 1, (n, 3))                 # non-IID: each site differs
    y = X @ TRUE_W + rng.normal(0, 0.1, n)
    return X, y

clients = [make_client(n, s) for n, s in [(50, -1), (200, 0), (120, 2)]]

def local_sgd(w, X, y, epochs=5, lr=0.01, batch=10):
    w = w.copy()
    for _ in range(epochs):
        idx = rng.permutation(len(y))
        for b in range(0, len(y), batch):
            j = idx[b:b + batch]
            grad = 2 * X[j].T @ (X[j] @ w - y[j]) / len(j)
            w -= lr * grad
    return w

w_global = np.zeros(3)
for rnd in range(20):                                 # communication rounds
    updates, sizes = [], []
    for X, y in clients:                              # raw data never leaves the client
        updates.append(local_sgd(w_global, X, y)); sizes.append(len(y))
    w_global = np.average(updates, axis=0, weights=sizes)   # FedAvg: weighted by n_k
print("federated w:", w_global.round(3), " true w:", TRUE_W)

7. Exercises with solutions

Try each exercise before opening its solution.

Exercise 1 — Sampling a vibration signal

A gearbox produces vibration components up to 3 kHz that you need to analyse. What is the theoretical minimum sampling rate, and what else must the acquisition chain include to avoid aliasing?

Show solution

By the sampling theorem, the rate must exceed 2 × 3 kHz = 6 kHz [12]. The ADC must be preceded by an analog anti-aliasing low-pass filter, because any energy above half the sampling rate (from other machine components, electrical noise) would otherwise fold into the band of interest. Since real filters are not brick-walls, practical systems sample comfortably above 6 kHz so the filter's transition band fits below the Nyquist frequency.

Exercise 2 — Payload budget

A fleet of 1,000 sensors each sends one reading every 10 s. Using the payload sizes from Figure 2 (JSON 81 B, Protobuf 36 B), compute the daily payload volume for each encoding (ignore protocol overhead).

Show solution

Messages/day = 1,000 × 86,400 / 10 = 8,640,000. JSON: 8.64 M × 81 B = 699.8 MB/day. Protobuf: 8.64 M × 36 B = 311.0 MB/day, a 55.6 % reduction. Over a cellular data plan, or in battery terms (radio airtime is often the dominant energy cost), this difference is substantial. Batching several readings per message (as SenML packs do [16]) reduces per-message protocol overhead further.

Exercise 3 — Watermarks

Re-run the tumbling-window example of Section 3.1 with LATENESS = 0. Which outputs change, and why?

Show solution

With zero lateness the watermark equals the maximum event time seen. After the event at t = 65 s the watermark is 65, so window [0, 60) fires immediately with only two values (20.0, 22.0 → mean 21.0, n = 2). The event at 58 s then arrives behind the watermark and is dropped. Output (verified by running):

('a', 0, 21.0, 2)
('LATE-DROPPED', 'a', 58, 21.0)
('a', 60, 23.5, 2)
('LATE-DROPPED', 'a', 40, 99.0)

This is the latency–completeness trade-off of the Dataflow model: smaller lateness gives earlier but less complete results [17].

Exercise 4 — Welford by hand

Compute the mean, population variance and sample variance of the readings 2, 4, 4, 4, 5, 5, 7, 9.

Show solution

Mean = 40/8 = 5. Sum of squared deviations = 9 + 1 + 1 + 1 + 0 + 0 + 4 + 16 = 32. Population variance = 32/8 = 4 (σ = 2). Sample variance = 32/7 ≈ 4.571. Welford's update reaches the same m2 = 32 incrementally without storing the values [39].

Exercise 5 — Mann–Kendall statistic

Compute S for the series 3, 1, 4, 1, 5.

Show solution

List all 10 pairs (i < j) and the sign of xj − xi: (3,1)−, (3,4)+, (3,1)−, (3,5)+, (1,4)+, (1,1)0, (1,5)+, (4,1)−, (4,5)+, (1,5)+. Six positive, three negative, one tie: S = 3. With n = 5, Var(S) = 5·4·15/18 ≈ 16.7, so Z = (3 − 1)/√16.7 ≈ 0.49: no significant trend [51,52].

Exercise 6 — Haversine sanity check

Without code, estimate the distance between (0°, 0°) and (0°, 1° E). Then explain why GeoJSON for the second point is [1.0, 0.0].

Show solution

On the equator one degree of longitude spans 2πR/360 = 2π × 6371.0088/360 ≈ 111.2 km, which the haversine function reproduces [60,61]. GeoJSON orders positions as longitude, then latitude [59], so 1° E, 0° N is [1.0, 0.0].

Exercise 7 — FedAvg arithmetic

Three clients return a single scalar weight: client A (n = 100) w = 1.0; B (n = 300) w = 2.0; C (n = 600) w = 0.5. What is the FedAvg global weight, and what would an unweighted mean give?

Show solution

FedAvg: (100·1.0 + 300·2.0 + 600·0.5)/1000 = (100 + 600 + 300)/1000 = 1.0 [88]. Unweighted mean: (1.0 + 2.0 + 0.5)/3 ≈ 1.167. The weighting gives each sample, rather than each client, equal influence.

Exercise 8 — Int8 quantization

A tensor is quantized with scale S = 0.05 and zero point Z = −10. (a) Which real value does q = 30 represent? (b) Quantize r = 1.23.

Show solution

(a) r = S(q − Z) = 0.05 × (30 + 10) = 2.0. (b) q = round(r/S) + Z = round(24.6) − 10 = 15, which dequantizes to 1.25: a quantization error of 0.02, bounded by S/2 [70].

Exercise 9 — Kalman gain intuition

In the scalar filter of Section 5.5, the predicted variance is P⁻ = 1 and measurement variance R = 0.25. Compute the gain. What happens to the gain as R → ∞, and as R → 0?

Show solution

K = P⁻/(P⁻ + R) = 1/1.25 = 0.8, so the estimate moves 80 % of the way to the measurement. As R → ∞ (useless sensor) K → 0 and the filter ignores measurements; as R → 0 (perfect sensor) K → 1 and the estimate equals the measurement [34,79].

Exercise 10 — Design a cold-chain pipeline

A grocery chain has 400 refrigerated trucks, each with 4 temperature probes, a door sensor and GPS, on intermittent cellular coverage. Food-safety rules require proof that product stayed below 5 °C. Sketch the data pipeline, naming one concrete technique for each stage.

Show solution

One good answer: Acquisition — sample probes every 30 s, buffer locally during coverage gaps, encode as CBOR SenML packs [14,16], stamp event time from a GNSS-disciplined clock plus sequence numbers; publish over MQTT QoS 1 [7]. Validation — schema, range, duplicate and stuck-probe checks at ingestion [24]. Processing — Kafka keyed by truck ID [9]; Flink job with event-time windows and generous allowed lateness for buffered data [18]; as-of join to the trip/load manifest [32]; CEP rule "door open and temperature +2 °C within 5 min" [43]. Storage — time-series DB for live views, Parquet in the lake for audit [30]. Analysis — per-trip compliance report using max and time-above-threshold, not just means; geofence-based stop detection with DBSCAN [64]; trend detection on compressor duty cycle for predictive maintenance [51]. Automation — notify driver and dispatcher on breach; human approval before discarding stock.

8. Trivia questions with answers

  1. What does CBOR stand for, and which RFC currently defines it?
    Answer

    Concise Binary Object Representation, RFC 8949 (December 2020), which obsoletes the original RFC 7049 [14].

  2. In what year does the first NTP timestamp era roll over?
    Answer

    2036; NTP counts 32-bit seconds from 1 January 1900, and RFC 5905 introduces era numbers to handle the wrap [21].

  3. Which spaceflight program was one of the first practical users of the Kalman filter?
    Answer

    NASA's Apollo program, for onboard navigation, following work at NASA Ames led by Stanley Schmidt [80].

  4. Name the four MLPerf Tiny benchmark tasks.
    Answer

    Keyword spotting, visual wake words, image classification and anomaly detection [68].

  5. How many base cells does the H3 grid have, and how many resolutions?
    Answer

    122 base cells and 16 resolutions (0–15) [62].

  6. In GeoJSON, which comes first in a position: latitude or longitude?
    Answer

    Longitude, then latitude (then optional altitude) [59].

  7. What average size per data point did Facebook's Gorilla achieve for time-series compression?
    Answer

    About 1.37 bytes, down from 16 bytes for a raw timestamp–value pair [37].

  8. Which MQTT QoS level guarantees exactly-once delivery?
    Answer

    QoS 2 [7].

  9. Which consumer product was an early large-scale deployment of federated learning?
    Answer

    Google's Gboard mobile keyboard, for next-word prediction [89].

  10. Why does Isolation Forest not need a distance or density measure?
    Answer

    It relies on the fact that anomalies are easier to isolate: random partitioning separates them with shorter average path lengths [83].

  11. What is the SenML unit symbol for degrees Celsius?
    Answer

    Cel [16].

  12. What are the three layers of the Lambda architecture?
    Answer

    Batch layer, speed layer and serving layer [4].

  13. Which four mandatory attributes does every CloudEvent carry?
    Answer

    id, source, specversion and type [10].

  14. What scaling constant converts the median absolute deviation into a consistent estimator of the standard deviation for Gaussian data?
    Answer

    Approximately 1.4826 (= 1/Φ⁻¹(0.75)) [41].
