1Why IoT testing is different

An IoT product is a distributed system whose nodes are small computers with sensors, actuators, batteries and radios, connected through gateways and networks to cloud services that people operate around the clock. A defect can sit in any of those layers, and the interesting ones sit between them: a firmware retry loop that is harmless on one device and becomes a reconnect storm across a fleet, or a cloud change that breaks devices that cannot be reached to fix. Testing therefore has to cover physics (power, temperature, radio), software (firmware and back-end), and operations (updates, monitoring, recovery) as one system.

Three words are used precisely in dependability engineering. A fault is the adjudged cause of an error, such as a bug or a cracked solder joint; an error is the part of the system state that may lead to a failure; and a failure is when the delivered service deviates from correct service [1]. The same taxonomy lists the means of attaining dependability: fault prevention, fault tolerance, fault removal and fault forecasting [1]. Testing is fault removal; reliability engineering and operations are mostly fault tolerance and forecasting. ISO/IEC 25010 makes reliability a product-quality characteristic with four sub-characteristics: faultlessness, availability, fault tolerance and recoverability [2]. ISO/IEC/IEEE 29119 supplies the general vocabulary for test levels, test types and test processes used below [3].

What makes IoT harder than web or mobile testing

  • Hardware in the loop of every bug. Timing, analogue noise, brown-outs and flash wear do not exist in a unit-test process.
  • Hostile and variable networks. Lossy, high-latency, intermittently connected links are the normal case, not the exception.
  • Energy is a requirement. A firmware change that adds 50 µA of average current can cut years off battery life.
  • Physical environment. Devices are qualified for temperature, humidity, vibration, ingress and electromagnetic compatibility.
  • You cannot easily recall a device. Updates are over the air, so the update mechanism is the most safety-critical code on the device.
  • Scale. Behaviour that is rare per device becomes daily at fleet scale.

A 2018 survey of IoT testing tools grouped them by test level and found that most tools cover only a slice: device-level emulation, network simulation, or cloud load generation, with few covering end-to-end behaviour [4]. A practical strategy combines many cheap, fast tests low in the stack with fewer, slower, more realistic tests higher up, the shape popularised as the test pyramid [5]. Figure 1 maps that shape onto an IoT product.

Safety standards make the same progression explicit. IEC 61508-3 links software verification techniques to safety integrity levels, recommending more rigorous testing and analysis as the level rises [6], and ISO 26262-4 describes system integration testing on hardware-in-the-loop test benches, vehicles and other environments [7]. Even where no safety standard applies, the vocabulary of those standards (model-, software-, processor- and hardware-in-the-loop) is the clearest way to describe how realism grows across a test plan.

2Software-in-the-loop testing

Software-in-the-loop (SIL) testing runs the production control code, compiled for the host computer, in a closed loop with a simulated plant: the model of the room, motor, tank or battery that the code controls. Because both sides run in software on a simulated clock, an hour of behaviour can be checked in milliseconds and the test is fully repeatable. SIL sits in a ladder of "X-in-the-loop" stages (Figure 2): model-in-the-loop (MIL) tests the control algorithm as a model; SIL tests the real code; processor-in-the-loop (PIL) runs the compiled code on the target processor or an instruction-set simulator; and hardware-in-the-loop (HIL) runs the real device against a real-time simulated plant [8].

To keep SIL honest, the controller source must be the same file that goes into the firmware build, with hardware access behind a thin interface. Plant models can be written directly, as below, or exchanged between tools as Functional Mock-up Units under the Functional Mock-up Interface (FMI) standard, which defines a tool-independent C API and packaging for simulation models [9,10]. Embedded operating systems increasingly support SIL directly: Zephyr's native_sim target builds an entire Zephyr application, kernel included, as a Linux executable [11], and full-system emulators such as QEMU and Renode run unmodified firmware images for PIL-style testing [12,13].

2.1 A SIL test in Python

The listing below tests a thermostat with hysteresis and a relay-protection timer against a first-order thermal model. The tests encode requirements: reach the setpoint within 20 minutes, stay in a band, do not chatter the relay, and fail safe if the sensor returns NaN.

sil_thermostat.py: controller under test, plant model and pytest requirements (all four tests pass)
"""Software-in-the-loop test: the real controller code runs against a
simulated room (plant model) on a simulated clock, so an hour of
behaviour is checked in milliseconds."""
from dataclasses import dataclass

# ---- code under test (would be shared with the firmware build) ----
@dataclass
class Thermostat:
    setpoint: float = 21.0
    hysteresis: float = 0.5
    heater_on: bool = False
    min_switch_s: int = 60           # protect the relay from chattering
    _last_switch: int = -10**9

    def step(self, t: int, temp: float) -> bool:
        if t - self._last_switch < self.min_switch_s:
            return self.heater_on
        want = (temp < self.setpoint - self.hysteresis or
                (self.heater_on and temp < self.setpoint + self.hysteresis))
        if want != self.heater_on:
            self.heater_on, self._last_switch = want, t
        return self.heater_on

# ---- plant model: first-order thermal room ----
@dataclass
class Room:
    temp: float = 15.0
    outside: float = 5.0
    k_loss: float = 1 / 1800         # 1/s, heat loss to outside
    heater_gain: float = 0.015       # degC/s at full power

    def advance(self, dt: float, heater: bool) -> float:
        self.temp += dt * (self.k_loss * (self.outside - self.temp)
                           + (self.heater_gain if heater else 0.0))
        return self.temp

def run(seconds=3600, dt=1, sensor_fault_at=None):
    ctl, room, trace, switches, prev = Thermostat(), Room(), [], 0, False
    for t in range(0, seconds, dt):
        reading = room.temp
        if sensor_fault_at is not None and t >= sensor_fault_at:
            reading = float("nan")   # injected fault: sensor returns NaN
        on = ctl.step(t, reading)
        switches += on != prev; prev = on
        trace.append(room.advance(dt, on))
    return trace, switches

def test_reaches_setpoint_within_20_minutes():
    trace, _ = run()
    assert max(trace[:1200]) >= 20.5

def test_stays_in_band_after_warmup():
    trace, _ = run()
    assert all(19.5 <= x <= 22.5 for x in trace[1800:])

def test_relay_does_not_chatter():
    _, switches = run()
    assert switches <= 3600 // 60

def test_nan_sensor_fails_safe_heater_off():
    trace, _ = run(sensor_fault_at=1800)
    assert trace[-1] < trace[1800]   # NaN comparisons are False -> off

The last test shows why SIL is worth writing: injecting a NaN reading is trivial in simulation and awkward on hardware. The controller happens to fail safe because every comparison with NaN is false, which is a property worth pinning down with a test rather than leaving to luck. With these parameters the simulated room reaches 20.5 °C after 703 s and then holds between 20.5 °C and 21.5 °C with 21 relay switches in the hour.

3Hardware-in-the-loop testing

Hardware-in-the-loop (HIL) testing connects the real device under test (DUT) to a real-time simulator that emulates the rest of the world through the device's actual electrical interfaces: analogue sensor voltages, digital inputs, buses such as CAN, I²C or Modbus, and radio links. Fathy and colleagues define HIL as a simulation in which some physical components are replaced by real-time models while the real hardware remains in the loop, and note its benefits for testing hazardous, expensive or not-yet-built conditions [8]. The simulator must keep up with real time, because the firmware's timing is part of what is under test.

Open-source frameworks make HIL rigs scriptable from ordinary test runners. labgrid abstracts boards, power switches, serial consoles and USB devices behind Python drivers so that the same pytest suite runs on any rig in a lab [14], and Espressif's pytest-embedded plugin flashes and talks to targets, including QEMU, from pytest [15]. Zephyr's Twister runner executes the same test suites on emulators and on physical boards listed in a hardware map [16].

3.1 A HIL test case

The test below is written against a small rig abstraction so it can run anywhere the rig provides the same fixtures. It sets a simulated temperature through a DAC that drives the device's thermistor input, cuts power mid-operation, and checks behaviour through telemetry. The instrument classes are thin wrappers, so the listing is shown for structure rather than executed here.

test_hil_thermostat.py: HIL test against a rig abstraction (structure; needs a physical rig)
import pytest, time

# Fixtures come from conftest.py: 'rig' wraps a programmable supply (SCPI),
# a DAC channel wired to the thermistor input, and an MQTT probe on the test broker.

def test_heater_turns_on_when_cold(rig):
    rig.supply.set(voltage=3.3, current_limit=0.5); rig.supply.on()
    rig.wait_for_telemetry("status", lambda m: m["state"] == "online", timeout=30)
    rig.thermistor.set_celsius(17.0)               # DAC emulates the sensor
    msg = rig.wait_for_telemetry("telemetry", lambda m: m["heater"], timeout=10)
    assert abs(msg["temp_c"] - 17.0) < 0.5          # ADC chain calibrated end to end
    assert rig.relay_sense.read() == 1                  # physical output really switched

def test_brownout_recovers_without_flash_corruption(rig):
    for cycle in range(200):
        rig.supply.on(); time.sleep(rig.rng.uniform(0.05, 2.0))
        rig.supply.ramp(to=1.6, seconds=0.2)          # slow sag, below BOR threshold
        rig.supply.off(); time.sleep(0.5)
    rig.supply.on()
    boot = rig.wait_for_telemetry("status", lambda m: "boot" in m, timeout=30)
    assert boot["config_crc_ok"] and boot["reset_reason"] in ("POR", "BOR")

Rig discipline. HIL rigs drift: probes come loose, attenuators heat, firmware from yesterday's run is still in flash. Start every test by power-cycling and reflashing, record instrument serial numbers and firmware hashes with each result, and run a known-good "golden" device through the rig daily so that rig failures are not mistaken for product failures.

4Firmware testing

Firmware testing starts with unit tests of modules compiled for the host, with hardware access replaced by test doubles. Grenning's approach to test-driven development in embedded C separates hardware-independent logic from a thin hardware abstraction layer, and substitutes fakes for the abstraction at link time [17]. Unity is a small C unit-test framework, CMock generates mocks from headers, and Ceedling builds and runs the combination [18]. Zephyr provides its own Ztest framework and Twister runner for host, emulator and board targets [16].

4.1 Unit tests with a fake HAL

The first listing is a temperature-sensor driver that retries bus errors, range-checks the result and detects a stuck sensor. The second tests it with Unity, using a fake hal_i2c_read that can be told to fail.

temp_sensor.c: driver under test
#include "temp_sensor.h"

#define TS_ADDR      0x48u
#define TS_REG_TEMP  0x00u
#define TS_RETRIES   3
#define STUCK_LIMIT  50          /* identical samples before we call it stuck */

static int16_t last_raw;
static uint16_t same_count;

void ts_reset(void) { last_raw = 0; same_count = 0; }

ts_status_t ts_read_centi_c(int32_t *out)
{
    uint8_t b[2];
    int rc = -1;
    for (int i = 0; i < TS_RETRIES && rc != 0; i++) {
        rc = hal_i2c_read(TS_ADDR, TS_REG_TEMP, b, 2);
    }
    if (rc != 0) return TS_ERR_BUS;

    /* 12-bit two's complement, left-aligned, 0.0625 degC per LSB */
    /* divide, not >>: right-shifting a negative value is implementation-defined */
    int16_t raw = (int16_t)((int16_t)(((uint16_t)b[0] << 8) | b[1]) / 16);
    int32_t centi = ((int32_t)raw * 625) / 100;

    if (centi < -5500 || centi > 12500) return TS_ERR_RANGE;

    same_count = (raw == last_raw) ? (uint16_t)(same_count + 1) : 0;
    last_raw = raw;
    if (same_count >= STUCK_LIMIT) return TS_ERR_STUCK;

    *out = centi;
    return TS_OK;
}
test_temp_sensor.c: Unity tests with a link-time fake for the I²C HAL
#include "unity.h"
#include "temp_sensor.h"

/* ---- fake HAL: link-time substitution for the real I2C driver ---- */
static uint8_t fake_bytes[2];
static int fake_failures;          /* fail this many calls, then succeed */
static int fake_calls;

int hal_i2c_read(uint8_t addr, uint8_t reg, uint8_t *buf, uint8_t len)
{
    (void)addr; (void)reg;
    fake_calls++;
    if (fake_failures > 0) { fake_failures--; return -5; /* -EIO */ }
    for (uint8_t i = 0; i < len; i++) buf[i] = fake_bytes[i];
    return 0;
}

static void set_raw12(int16_t raw) {
    uint16_t v = (uint16_t)((uint16_t)raw << 4);
    fake_bytes[0] = (uint8_t)(v >> 8); fake_bytes[1] = (uint8_t)v;
}

void setUp(void)    { ts_reset(); fake_failures = 0; fake_calls = 0; }
void tearDown(void) {}

void test_converts_positive_temperature(void) {
    int32_t t; set_raw12(400);                 /* 400 * 0.0625 = 25.00 C */
    TEST_ASSERT_EQUAL(TS_OK, ts_read_centi_c(&t));
    TEST_ASSERT_EQUAL_INT32(2500, t);
}

void test_converts_negative_temperature(void) {
    int32_t t; set_raw12(-160);                /* -10.00 C */
    TEST_ASSERT_EQUAL(TS_OK, ts_read_centi_c(&t));
    TEST_ASSERT_EQUAL_INT32(-1000, t);
}

void test_retries_transient_bus_errors(void) {
    int32_t t; set_raw12(400); fake_failures = 2;
    TEST_ASSERT_EQUAL(TS_OK, ts_read_centi_c(&t));
    TEST_ASSERT_EQUAL_INT(3, fake_calls);
}

void test_reports_bus_error_after_retries(void) {
    int32_t t = 12345; fake_failures = 3;
    TEST_ASSERT_EQUAL(TS_ERR_BUS, ts_read_centi_c(&t));
    TEST_ASSERT_EQUAL_INT32(12345, t);         /* output untouched on error */
}

void test_detects_stuck_sensor(void) {
    int32_t t; ts_status_t s = TS_OK; set_raw12(400);
    for (int i = 0; i < 51 && s == TS_OK; i++) s = ts_read_centi_c(&t);
    TEST_ASSERT_EQUAL(TS_ERR_STUCK, s);
}

int main(void) {
    UNITY_BEGIN();
    RUN_TEST(test_converts_positive_temperature);
    RUN_TEST(test_converts_negative_temperature);
    RUN_TEST(test_retries_transient_bus_errors);
    RUN_TEST(test_reports_bus_error_after_retries);
    RUN_TEST(test_detects_stuck_sensor);
    return UNITY_END();
}

Two habits pay off. First, build the tests with sanitizers: compiling with -fsanitize=address,undefined found a real defect in an earlier draft of this very test, a left shift of a negative value, which the C standard leaves undefined [19,20]. The driver itself divides by 16 rather than right-shifting because right-shifting a negative signed value is implementation-defined [19]; MISRA C restricts such constructs for the same reason [21]. Second, measure coverage. Running the suite under gcov -b reported 100 % of lines executed but only 85.71 % of branches taken (12 of 14), because the out-of-range branch is never exercised [22]. Line coverage alone would have hidden that gap. Safety-critical avionics software goes further and requires modified condition/decision coverage (MC/DC) at the highest level, where each condition in a decision must be shown to affect the outcome independently [23,24].

4.2 Property-based tests and fuzzing

Hand-written examples test the cases a developer thought of. Property-based testing, introduced by QuickCheck, generates many random inputs and checks that stated properties hold, then shrinks any failure to a minimal example [25]. Hypothesis brings the approach to Python [26], and coverage-guided fuzzers such as libFuzzer do the same for C parsers by mutating inputs to reach new code paths [27]. Parsers for frames, packets and configuration are the best targets because they consume untrusted input.

frame_codec.py: a framed telemetry codec with CRC-16 and four property tests (all pass)
"""A telemetry frame codec and property-based tests (Hypothesis).
Frame: 0x7E | type:u8 | len:u8 | payload[len] | crc16:u16 (big-endian)"""
import struct
from hypothesis import given, strategies as st

SOF = 0x7E

def crc16_ccitt_false(data: bytes, crc: int = 0xFFFF) -> int:
    for byte in data:
        crc ^= byte << 8
        for _ in range(8):
            crc = ((crc << 1) ^ 0x1021) if crc & 0x8000 else crc << 1
            crc &= 0xFFFF
    return crc

class FrameError(ValueError):
    pass

def encode(ftype: int, payload: bytes) -> bytes:
    if not (0 <= ftype <= 255 and len(payload) <= 255):
        raise FrameError("type or length out of range")
    body = bytes([SOF, ftype, len(payload)]) + payload
    return body + struct.pack(">H", crc16_ccitt_false(body))

def decode(frame: bytes) -> tuple[int, bytes]:
    if len(frame) < 5 or frame[0] != SOF:
        raise FrameError("short frame or bad start byte")
    n = frame[2]
    if len(frame) != 5 + n:
        raise FrameError("length field disagrees with frame size")
    (crc,) = struct.unpack(">H", frame[-2:])
    if crc != crc16_ccitt_false(frame[:-2]):
        raise FrameError("CRC mismatch")
    return frame[1], frame[3:3 + n]

# ---------------- tests ----------------
def test_crc_check_value():
    assert crc16_ccitt_false(b"123456789") == 0x29B1   # catalogue check value

@given(st.integers(0, 255), st.binary(max_size=255))
def test_roundtrip(ftype, payload):
    assert decode(encode(ftype, payload)) == (ftype, payload)

@given(st.binary(max_size=300))
def test_decoder_never_crashes_on_garbage(data):
    try:
        decode(data)
    except FrameError:
        pass                      # rejecting is fine; any other exception fails

@given(st.integers(0, 255), st.binary(min_size=1, max_size=64), st.data())
def test_any_single_bit_flip_is_detected(ftype, payload, data):
    frame = bytearray(encode(ftype, payload))
    bit = data.draw(st.integers(0, len(frame) * 8 - 1))
    frame[bit // 8] ^= 1 << (bit % 8)
    try:
        assert decode(bytes(frame)) != (ftype, payload)
    except FrameError:
        pass

The first test pins the CRC to its published check value: CRC-16/CCITT-FALSE (catalogued as CRC-16/IBM-3740) of the ASCII string "123456789" is 0x29B1 [28]. The other three state properties: encode then decode is the identity, the decoder never raises anything except its own error type on garbage, and any single-bit flip is detected. The same three properties make a good libFuzzer harness for the C version of the codec.

5Integration testing

Integration tests check that components work together through their real interfaces: device firmware with the broker, broker with the ingestion service, ingestion with the database. The most valuable IoT integration tests use a real message broker rather than a mock, because protocol semantics such as retained messages, Last Will and Testament, session expiry and QoS retransmission are exactly where assumptions break. MQTT 5.0 specifies that a broker publishes a client's Will Message when the network connection closes without a DISCONNECT, including when the keep-alive expires without traffic [29]. A real broker such as Eclipse Mosquitto starts in milliseconds and is small enough to start from a pytest session fixture [30,31]; Testcontainers does the same for brokers, databases and other dependencies packaged as containers [32].

test_mqtt_integration.py: pytest against a real Mosquitto broker (three tests pass in about 4 s)
"""Integration tests against a real Mosquitto broker started per test session.
Requires: mosquitto on PATH, paho-mqtt >= 2.0, pytest."""
import json, queue, socket, subprocess, time
import pytest
import paho.mqtt.client as mqtt

def free_port() -> int:
    with socket.socket() as s:
        s.bind(("127.0.0.1", 0)); return s.getsockname()[1]

@pytest.fixture(scope="session")
def broker(tmp_path_factory):
    port = free_port()
    conf = tmp_path_factory.mktemp("mq") / "m.conf"
    conf.write_text(f"listener {port} 127.0.0.1\nallow_anonymous true\n")
    proc = subprocess.Popen(["mosquitto", "-c", str(conf)])
    for _ in range(50):                       # wait until it accepts TCP
        try: socket.create_connection(("127.0.0.1", port), 0.1).close(); break
        except OSError: time.sleep(0.1)
    yield port
    proc.terminate(); proc.wait(5)

def client(port, cid, **kw) -> mqtt.Client:
    c = mqtt.Client(mqtt.CallbackAPIVersion.VERSION2, client_id=cid,
                    protocol=mqtt.MQTTv5)
    for k, v in kw.items(): setattr(c, k, v)
    return c

def collector(port, topic):
    q = queue.Queue()
    c = client(port, f"col-{time.monotonic_ns()}")
    c.on_message = lambda _c, _u, m: q.put(m)
    c.connect("127.0.0.1", port); c.loop_start()
    c.subscribe(topic, qos=1)
    time.sleep(0.2)
    return c, q

def test_telemetry_reaches_backend(broker):
    sub, q = collector(broker, "t/+/telemetry")
    dev = client(broker, "dev-1"); dev.connect("127.0.0.1", broker); dev.loop_start()
    dev.publish("t/dev-1/telemetry", json.dumps({"temp": 21.5}), qos=1).wait_for_publish(2)
    msg = q.get(timeout=2)
    assert json.loads(msg.payload) == {"temp": 21.5}
    dev.disconnect(); dev.loop_stop(); sub.loop_stop()

def test_last_will_marks_device_offline(broker):
    dev = client(broker, "dev-2")
    dev.will_set("t/dev-2/status", "offline", qos=1, retain=True)
    dev.connect("127.0.0.1", broker, keepalive=2); dev.loop_start()
    dev.publish("t/dev-2/status", "online", qos=1, retain=True).wait_for_publish(2)
    sub, q = collector(broker, "t/dev-2/status")
    assert q.get(timeout=2).payload == b"online"          # retained state
    dev.loop_stop(); dev.socket().close()     # simulate power loss: no DISCONNECT
    # broker sends the will at once on a dropped TCP link, or after 1.5 x keepalive
    seen = [b"online", q.get(timeout=6).payload]
    assert seen == [b"online", b"offline"]
    sub.loop_stop()

def test_retained_status_survives_for_late_subscriber(broker):
    sub, q = collector(broker, "t/dev-2/status")
    assert q.get(timeout=2).payload == b"offline"
    sub.loop_stop()

Writing this test exposed a timing subtlety worth knowing. Closing the socket counts as a network failure, so Mosquitto published the will immediately; it did not wait for 1.5 times the keep-alive. A first draft subscribed only after the drop and therefore saw just one retained message. The test now subscribes first and documents both paths. Contract testing tools such as Pact complement these tests by checking that a consumer's expectations of a message or API match what the provider actually emits, without running both at once [33].

6Protocol conformance testing

Conformance testing checks an implementation against the requirements of a standard; interoperability testing checks that two implementations work together. ISO/IEC 9646 defined the classic methodology: abstract test suites written independently of any implementation, executable test cases derived from them, and test verdicts of pass, fail or inconclusive [34]. ETSI's TTCN-3 is a standardised language for writing such test suites [35], and the Eclipse IoT-Testware project publishes TTCN-3 suites for MQTT, CoAP and other IoT protocols [36]. Eclipse Paho provides an MQTT test broker and client test suite used for interoperability testing [37].

For many radio and smart-home protocols, conformance testing is also a market gate. Matter products are certified by the Connectivity Standards Alliance through authorised test labs before they may use the Matter mark [38], and products that use Bluetooth technology must complete the Bluetooth SIG qualification process [39]. A sensible internal practice is to run the public conformance suites in CI long before formal certification, so that certification becomes a formality.

7Network simulation

IoT software must be tested on the networks it will really meet: lossy low-power radio meshes, congested cellular links, satellite back-haul with seconds of latency, and links that disappear for hours. There are two complementary techniques. Network simulation models an entire network in software, so thousands of virtual nodes can be studied repeatably; network emulation inserts controlled impairments into real traffic between real software or devices.

Simulators

ns-3 is a discrete-event network simulator with models for Wi-Fi, LTE, 6LoWPAN and more, written in C++ with Python bindings [42].

Cooja, the Contiki simulator, mixes simulation levels so that some nodes run real compiled sensor-node firmware while others are abstract models [43].

OMNeT++ is a component-based discrete-event simulation framework widely used with network model libraries [44].

Emulators

tc-netem in the Linux kernel adds delay, jitter, loss, duplication, corruption, reordering and rate limits to an interface, including a Gilbert-Elliott burst-loss model [45].

Toxiproxy is a TCP proxy whose "toxics" add latency, bandwidth limits, timeouts and connection resets, scriptable from tests [46].

RF shield boxes and attenuators do the same for real radio links in a HIL rig.

Applying impairment profiles with tc-netem (run as root on the bridge interface)

7.1 Why burst loss matters

Radio losses arrive in bursts, not as independent coin flips. Gilbert's two-state channel model, extended by Elliott, captures this with a "good" state and a "bad" state and transition probabilities between them [47]. The mean loss rate is pGB/(pGB+pBG) and the mean burst length is 1/pBG when the bad state drops every packet. The simulator below confirms both and shows that independent drops with the same average rate give bursts four times shorter, which is why a retry policy tuned on independent loss fails in the field.

gilbert_elliott.py: burst-loss model
"""Gilbert-Elliott two-state burst-loss model. Use it to drive a test
double for a radio link, or to choose tc-netem 'loss gemodel' parameters."""
import random

def simulate(n, p_gb, p_bg, loss_good=0.0, loss_bad=1.0, seed=1):
    """p_gb: P(Good->Bad) per packet, p_bg: P(Bad->Good) per packet."""
    rng, bad, lost = random.Random(seed), False, []
    for _ in range(n):
        lost.append(rng.random() < (loss_bad if bad else loss_good))
        bad = (rng.random() >= p_bg) if bad else (rng.random() < p_gb)
    return lost

def stats(lost):
    bursts, run = [], 0
    for x in lost + [False]:
        if x: run += 1
        elif run: bursts.append(run); run = 0
    return sum(lost) / len(lost), (sum(bursts) / len(bursts) if bursts else 0)

if __name__ == "__main__":
    p_gb, p_bg = 0.01, 0.25
    print(f"theory: loss={p_gb / (p_gb + p_bg):.3f}, mean burst={1 / p_bg:.1f}")
    rate, burst = stats(simulate(200_000, p_gb, p_bg))
    print(f"sim:    loss={rate:.3f}, mean burst={burst:.1f}")
    # same average loss with independent drops gives far shorter bursts:
    rate_i, burst_i = stats(simulate(200_000, 0, 0, loss_good=rate))
    print(f"iid:    loss={rate_i:.3f}, mean burst={burst_i:.1f}")

8Load and stress testing

Load testing checks behaviour at expected peak traffic; stress testing pushes beyond it to find the breaking point and see how the system fails; soak testing holds a realistic load for days to reveal leaks and slow degradation. IoT back-ends have characteristic load shapes: very many long-lived connections with small messages, synchronised bursts when devices report on the same schedule, and reconnect storms after an outage when every device tries to come back at once. Randomised, capped exponential back-off with jitter is the standard defence against the last of these [48].

Three ideas keep load tests honest. First, Little's law, L = λW, relates the average number of messages in the system to arrival rate and time in system, so a rising queue at constant rate means rising latency [49]. Second, report percentiles, not averages: at fleet scale the slowest 1 % of requests dominates user-visible behaviour [50]. Third, generate load open-loop, on a schedule that does not slow down when the system does. A closed-loop generator that waits for each reply before sending the next quietly stops offering load during a stall and under-reports the latency; Tene calls this coordinated omission and the HdrHistogram project documents how to correct for it [51].

mqtt_load.py: open-loop MQTT load generator measuring latency from scheduled send time
"""Open-loop MQTT load generator. Each simulated device publishes on a fixed
schedule; latency is measured from the *scheduled* send time, so a stalled
client cannot hide queueing delay (avoids coordinated omission).
usage: python mqtt_load.py --port 1883 --devices 200 --rate 5 --seconds 20"""
import argparse, struct, threading, time
import paho.mqtt.client as mqtt

def percentile(sorted_vals, p):
    if not sorted_vals: return float("nan")
    k = min(len(sorted_vals) - 1, max(0, round(p / 100 * len(sorted_vals)) - 1))
    return sorted_vals[k]

def main():
    ap = argparse.ArgumentParser()
    ap.add_argument("--host", default="127.0.0.1"); ap.add_argument("--port", type=int, default=1883)
    ap.add_argument("--devices", type=int, default=100); ap.add_argument("--rate", type=float, default=1.0)
    ap.add_argument("--seconds", type=float, default=10); ap.add_argument("--qos", type=int, default=1)
    a = ap.parse_args()

    lat, lock = [], threading.Lock()
    def on_msg(_c, _u, m):
        sched = struct.unpack(">d", m.payload[:8])[0]
        with lock: lat.append(time.time() - sched)

    sub = mqtt.Client(mqtt.CallbackAPIVersion.VERSION2, client_id="load-sink")
    sub.on_message = on_msg
    sub.connect(a.host, a.port); sub.subscribe("load/#", qos=a.qos); sub.loop_start()

    pubs = []
    for i in range(a.devices):
        c = mqtt.Client(mqtt.CallbackAPIVersion.VERSION2, client_id=f"load-{i}")
        c.connect(a.host, a.port); c.loop_start(); pubs.append(c)
    time.sleep(1)

    period, start, sent = 1.0 / a.rate, time.time() + 0.5, 0
    n_ticks = int(a.seconds * a.rate)
    for tick in range(n_ticks):                      # one scheduler, all devices
        for i, c in enumerate(pubs):
            sched = start + tick * period + i * period / a.devices   # spread phases
            delay = sched - time.time()
            if delay > 0: time.sleep(delay)
            c.publish(f"load/{i}", struct.pack(">d", sched) + b"x" * 56, qos=a.qos)
            sent += 1
    time.sleep(2)
    for c in pubs + [sub]: c.loop_stop(); c.disconnect()

    s = sorted(lat)
    print(f"offered {sent / a.seconds:.0f} msg/s, received {len(s)}/{sent} "
          f"({len(s) / sent:.1%})")
    for p in (50, 90, 99, 99.9):
        print(f"  p{p:<4} latency {percentile(s, p) * 1000:8.2f} ms")
    print(f"  max    latency {s[-1] * 1000:8.2f} ms")

9Power consumption testing

For battery-powered devices, energy is a functional requirement and must be tested on every release. Current draw spans six orders of magnitude, from microamps asleep to tens or hundreds of milliamps during radio transmission, and the transitions last microseconds, so ordinary multimeters miss most of the charge. Purpose-built instruments sample fast across that range: Nordic's Power Profiler Kit II measures from about 200 nA to 1 A [56], and Qoitech's Otii Arc and the Joulescope are similar source-measure and energy analysers with scripting interfaces for CI [57,58]. Some debug probes integrate energy measurement, such as TI's EnergyTrace [59]. EEMBC's ULPMark benchmarks compare microcontroller energy efficiency in a standard way [60].

With a measured profile, battery life follows from the average current. Real batteries deliver less than nameplate capacity at low temperature and under pulsed load, and self-discharge over time, so estimates should be derated; Linden's handbook gives discharge characteristics by chemistry [61].

battery_life.py: average current and battery life from a measured profile
"""Estimate battery life from a measured duty-cycle current profile."""
from dataclasses import dataclass

@dataclass
class Phase:
    name: str
    current_ma: float
    duration_s: float     # per wake cycle

def average_current_ma(phases, period_s):
    active = sum(p.duration_s for p in phases if p.name != "sleep")
    sleep = next(p for p in phases if p.name == "sleep")
    charge = sum(p.current_ma * p.duration_s for p in phases if p.name != "sleep")
    charge += sleep.current_ma * (period_s - active)
    return charge / period_s

    """derating covers temperature, pulse load and end-of-life voltage cutoff."""
    usable = capacity_mah * derating
    sd_ma = capacity_mah * self_discharge_pct_yr / 100 / (365 * 24)
    return usable / (avg_ma + sd_ma) / 24

For temperature-driven mechanisms the Arrhenius relation gives an acceleration factor exp[(Ea/k)(1/Tuse − 1/Ttest)], with activation energies Ea listed per failure mechanism in JEDEC JEP122 [71]. For humidity-driven corrosion, Peck's model multiplies this by a power of the humidity ratio; Peck's fit is usually quoted as an exponent of about 2.66 and an activation energy of about 0.79 eV [72].

    return (rh_test / rh_use) ** n * arrhenius_af(ea_ev, t_use_c, t_test_c)

    (exponential model): T = MTBF * -ln(1 - C)."""

The zero-failure formula comes from the exponential (constant failure rate) model: with no failures in T unit-hours, the one-sided lower confidence bound on MTBF at confidence C is T/(−ln(1−C)) [73]. """Software-implemented fault injection (SWIFI) for a gateway's sensor
pipeline. Faults are injected at the driver boundary; the tests assert
that the system degrades in the documented way instead of crashing."""
import contextlib, math, random

class SensorDriver:                         # real driver (stubbed here)
    def read(self) -> float:
        return 21.0

class FaultInjector:
    """Wraps a driver; the active fault mode alters what read() returns."""
    MODES = ("none", "exception", "nan", "stuck", "spike", "delay")

    def __init__(self, inner, seed=0):
        self.inner, self.mode, self.rng, self._last = inner, "none", random.Random(seed), None

    @contextlib.contextmanager
    def fault(self, mode):
        assert mode in self.MODES
        prev, self.mode = self.mode, mode
        try: yield
        finally: self.mode = prev

    def read(self):
        v = self.inner.read()
        if self.mode == "exception": raise OSError(5, "I2C NACK")
        if self.mode == "nan": return math.nan
        if self.mode == "stuck": self._last = self._last if self._last is not None else v; return self._last
        if self.mode == "spike": return v + self.rng.choice((-1, 1)) * 500
        if self.mode == "delay": raise TimeoutError("bus timeout")
        self._last = v
        return v

class Pipeline:
    """Code under test: validates readings, keeps last good value, flags quality."""
    def __init__(self, driver, lo=-40, hi=85, max_step=10):
        self.d, self.lo, self.hi, self.max_step = driver, lo, hi, max_step
        self.last_good, self.errors = None, 0

    def sample(self):
        try:
            v = self.d.read()
        except (OSError, TimeoutError):
            self.errors += 1
            return {"value": self.last_good, "quality": "comm_error"}
        if math.isnan(v) or not (self.lo <= v <= self.hi) or (
                self.last_good is not None and abs(v - self.last_good) > self.max_step):
            return {"value": self.last_good, "quality": "invalid"}
        self.last_good = v
        return {"value": v, "quality": "good"}

def test_fault_campaign():
    fi = FaultInjector(SensorDriver()); p = Pipeline(fi)
    assert p.sample() == {"value": 21.0, "quality": "good"}
    expected = {"exception": "comm_error", "delay": "comm_error",
                "nan": "invalid", "spike": "invalid", "stuck": "good"}
    for mode, quality in expected.items():
        with fi.fault(mode):
            r = p.sample()
        assert r["quality"] == quality, mode
        assert r["value"] == 21.0                      # last good value held
    assert p.sample()["quality"] == "good"             # recovers after fault

12Resilience testing

Resilience testing asks whether the whole system keeps delivering acceptable service while parts of it fail, and whether it recovers afterwards. Netflix's chaos engineering made this a continuous practice in production: build a hypothesis around steady-state behaviour, vary real-world events, run experiments in production, automate them to run continuously, and minimise the blast radius [79,80]. Its first tool, Chaos Monkey, randomly terminated production instances so that engineers would build services that tolerate it [81]. For Kubernetes-hosted IoT back-ends, Chaos Mesh and LitmusChaos inject pod, network and I/O faults [82,83], and AWS Fault Injection Service runs controlled experiments against AWS resources [84].

On the device side, resilience patterns are well known and testable. A circuit breaker stops calling a failing dependency after repeated failures, fails fast for a cool-down period, and then lets a single probe through before closing again [85]. Combined with store-and-forward buffering and jittered back-off [48], it prevents a gateway from hammering a struggling cloud service and from losing data.

circuit_breaker.py: circuit breaker and a scripted 90-second outage on a fake clock (test passes)
"""Circuit breaker for a gateway's cloud uplink, plus a resilience test that
drives it with a scripted outage on a fake clock."""
import time

class CircuitOpen(Exception):
    pass

class CircuitBreaker:
    def __init__(self, fail_threshold=5, reset_after_s=30.0, clock=time.monotonic):
        self.fail_threshold, self.reset_after_s, self.clock = fail_threshold, reset_after_s, clock
        self.state, self.failures, self.opened_at = "closed", 0, 0.0

    def call(self, fn, *args):
        if self.state == "open":
            if self.clock() - self.opened_at < self.reset_after_s:
                raise CircuitOpen()                   # fail fast, spare the backend
            self.state = "half_open"                  # let one probe through
        try:
            result = fn(*args)
        except Exception:
            self.failures += 1
            if self.state == "half_open" or self.failures >= self.fail_threshold:
                self.state, self.opened_at = "open", self.clock()
            raise
        self.state, self.failures = "closed", 0
        return result

# ---------------- resilience test ----------------
class FakeClock:
    def __init__(self): self.t = 0.0
    def __call__(self): return self.t

class FlakyCloud:
    """Cloud endpoint that is down between t=10 s and t=100 s."""
    def __init__(self, clock): self.clock, self.calls = clock, 0
    def send(self, msg):
        self.calls += 1
        if 10 <= self.clock() < 100: raise ConnectionError("503")
        return "ack"

def test_breaker_limits_load_during_outage_and_recovers():
    clock = FakeClock(); cloud = FlakyCloud(clock)
    cb = CircuitBreaker(fail_threshold=5, reset_after_s=30, clock=clock)
    buffered, outcomes = [], []
    for step in range(200):                          # one message per second
        clock.t = float(step)
        try:
            outcomes.append(cb.call(cloud.send, step))
        except (ConnectionError, CircuitOpen):
            buffered.append(step)                    # store-and-forward
    failed_calls = cloud.calls - len(outcomes)
    assert failed_calls <= 8                         # 5 to trip + a few half-open probes, not 90
    assert cb.state == "closed" and outcomes[-1] == "ack"
    assert all(10 <= s < 100 + 30 for s in buffered) # buffered only during outage + one reset period

Only 7 calls reached the failing service (5 to trip the breaker and 2 half-open probes, at 44 s and 74 s), instead of 90, and the 94 messages produced during the outage and the remaining cool-down were buffered for later delivery. 13OTA update testing

Over-the-air (OTA) update code is the one part of the firmware that must never fail, because a broken update path cannot be fixed by another update. RFC 9019 describes the architecture for IoT firmware updates, including the requirement that devices be able to recover from a failed update, and RFC 9124 lists the manifest information a device needs to decide whether an image is authentic, intended for it, and newer than what it runs [86,87]. In practice the mechanism is usually an A/B (dual-bank) scheme: write the new image to the inactive slot, verify it, boot it once as a trial, and revert automatically unless the new firmware confirms itself. MCUboot implements this for microcontrollers with its test-and-revert swap modes [88]; Mender, SWUpdate and RAUC provide similar A/B schemes for embedded Linux [89,90,91].

OTA testing should prove that property rather than assume it. The Monte Carlo test below cuts power after a random number of flash operations, many thousands of times, for a single-bank in-place update and for an A/B update. On a HIL rig the same campaign uses a programmable supply or relay and real flash.

ota_powercut.py: Monte Carlo power-cut campaign for two update designs (both tests pass)
"""Monte Carlo power-cut test for two OTA designs. Power is cut at a random
step of the update; afterwards the device boots and we check it still runs
some valid firmware. In a real HIL rig the 'cut' is a relay or a
programmable supply; here each flash operation is one step."""
import random

def in_place_update(flash, steps_done, n_blocks=64):
    """Single-bank: erase then write the only image slot."""
    ops = [("erase", "A")] + [("write", "A", i) for i in range(n_blocks)] + [("mark_valid", "A")]
    return run_ops(flash, ops, steps_done)

def ab_update(flash, steps_done, n_blocks=64):
    """Dual-bank: write inactive slot B, then flip a pending flag; the bootloader
    tries B once and falls back to A unless the app confirms B."""
    ops = ([("erase", "B")] + [("write", "B", i) for i in range(n_blocks)]
           + [("mark_valid", "B"), ("set_pending", "B"), ("reboot",), ("confirm", "B")])
    return run_ops(flash, ops, steps_done)

def run_ops(flash, ops, steps_done):
    for op in ops[:steps_done]:
        kind, slot = op[0], (op[1] if len(op) > 1 else None)
        if kind == "erase": flash[slot] = {"valid": False, "blocks": 0}
        elif kind == "write": flash[slot]["blocks"] += 1
        elif kind == "mark_valid": flash[slot]["valid"] = flash[slot]["blocks"] == 64
        elif kind == "set_pending": flash["pending"] = slot
        elif kind == "reboot": flash["trial"] = flash.pop("pending", None)
        elif kind == "confirm": flash["active"], flash["trial"] = slot, None
    return len(ops)

def boots(flash):
    """Bootloader: try the trial slot once, else the active slot; verify validity."""
    for slot in (flash.get("trial"), flash.get("pending"), flash["active"]):
        if slot and flash[slot]["valid"]:
            return True
    return False

def fresh():
    return {"A": {"valid": True, "blocks": 64}, "B": {"valid": False, "blocks": 0},
            "active": "A"}

def campaign(update, trials=10_000, seed=7):
    rng, total, bricked = random.Random(seed), update(fresh(), 0), 0
    for _ in range(trials):
        flash = fresh()
        update(flash, rng.randint(0, total))   # power cut after k operations
        bricked += not boots(flash)
    return bricked / trials

def test_in_place_update_bricks_on_power_cut():
    assert campaign(in_place_update) > 0.9

def test_ab_update_never_bricks():
    assert campaign(ab_update) == 0.0

if __name__ == "__main__":
    print(f"single-bank bricked: {campaign(in_place_update):.1%}")
    print(f"A/B bricked:         {campaign(ab_update):.1%}")

A complete OTA test plan also covers: images that are valid but crash on boot (does the revert fire?); images signed with the wrong key or carrying an older sequence number (are they refused, as the manifest model requires [87]?); interrupted and resumed downloads over a lossy link; low battery at update time; flash wear from repeated retries; and fleet-level rollout controls such as staged percentages and automatic abort on rising error rates. Field history shows why. In August 2017 a faulty automatic firmware update left several hundred LockState smart locks, many used by rental hosts, unable to operate remotely, and affected units could not be repaired remotely [92]. In January 2016 a Nest thermostat software update led to battery drain that took some thermostats offline and left homes without heating [93].

14Observability

The word comes from control theory: Kalman defined a system as observable when its internal state can be determined from its outputs [94]. In software operations, observability means being able to answer new questions about what a running system is doing from the telemetry it already emits, without shipping new code [95]. Monitoring tells you that something is wrong against questions decided in advance; observability helps you find out why. Google's SRE book frames monitoring around four golden signals for user-facing systems: latency, traffic, errors and saturation [96].

Telemetry is usually discussed as three signals: logs (timestamped records of discrete events), metrics (numeric measurements aggregated over time) and traces (the path of one request through many components). OpenTelemetry, a Cloud Native Computing Foundation project, standardises APIs, SDKs, semantic conventions and the OTLP wire protocol for all three, so instrumentation is not tied to one vendor's back-end [97]. IoT adds constraints that cloud-native observability rarely meets: devices may be offline for days, every byte over a cellular or LPWAN link costs energy and money, clocks drift, and a crash on a microcontroller leaves no log file behind.

Design rules for device telemetry

  • Count on the device, ship aggregates: a histogram of radio retries per hour costs a few bytes; a log line per retry costs a battery.
  • Always record why the device last reset (power-on, brown-out, watchdog, fault, OTA) and send it after every boot.
  • Capture crashes as compact core dumps or fault registers in a reserved RAM or flash region and upload them later; ESP-IDF and Memfault both support this pattern [98,99].
  • Timestamp with a monotonic counter plus the last known wall-clock offset, and let the back-end correct for drift.
  • Tag everything with device ID, firmware version and hardware revision, so a regression can be tied to a release.

15Logging and tracing

The Syslog Protocol, RFC 5424, defines a message format with eight severity levels from Emergency (0) to Debug (7), a timestamp, host, application name and optional structured data, and remains the common denominator for gateway and Linux-based devices [100]. On microcontrollers, logging frameworks such as Zephyr's logging subsystem support compile-time filtering by level and module, deferred processing so that logging does not block time-critical code, and multiple back-ends such as UART, RTT or a network sink [101]. Whatever the transport, logs should be structured, with machine-readable fields rather than free text, so that queries such as "all watchdog resets on firmware 2.4.1 in site 17" are possible.

Distributed tracing follows one unit of work across services. Google's Dapper paper described the model now used everywhere: a trace is a tree of spans, each with a trace identifier shared by the whole tree, its own span identifier and its parent's identifier, recorded with low overhead and sampling [102]. The W3C Trace Context recommendation standardises how that context propagates: the traceparent header carries a version, a 16-byte trace-id, an 8-byte parent-id and trace flags as lower-case hex, for example 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01 [103]. MQTT 5.0 user properties are name-value pairs carried with a PUBLISH packet and forwarded to subscribers [29], which makes them a natural place for traceparent in an MQTT pipeline.

trace_mqtt.py: W3C traceparent over MQTT 5 user properties with structured JSON logs
"""Carry a W3C Trace Context 'traceparent' through MQTT 5 user properties and
emit structured JSON logs that share the trace id, so a reading can be
followed from device to gateway to cloud consumer."""
import json, logging, os, secrets, sys, time
import paho.mqtt.client as mqtt
from paho.mqtt.packettypes import PacketTypes
from paho.mqtt.properties import Properties

class JsonFormatter(logging.Formatter):
    def format(self, r):
        doc = {"ts": round(r.created, 3), "level": r.levelname, "svc": r.name, "msg": r.getMessage()}
        doc.update(getattr(r, "ctx", {}))
        return json.dumps(doc, separators=(",", ":"))

def logger(name):
    h = logging.StreamHandler(sys.stdout); h.setFormatter(JsonFormatter())
    lg = logging.getLogger(name); lg.addHandler(h); lg.setLevel(logging.INFO); lg.propagate = False
    return lg

def new_traceparent(trace_id=None, sampled=True):
    trace_id = trace_id or secrets.token_hex(16)        # 16 bytes -> 32 hex chars
    span_id = secrets.token_hex(8)                      # 8 bytes -> 16 hex chars
    return f"00-{trace_id}-{span_id}-{'01' if sampled else '00'}"

def parse_traceparent(tp):
    ver, trace_id, parent_id, flags = tp.split("-")
    assert ver == "00" and len(trace_id) == 32 and len(parent_id) == 16
    return trace_id, parent_id, flags

def publish_traced(client, topic, payload, tp):
    props = Properties(PacketTypes.PUBLISH)
    props.UserProperty = [("traceparent", tp)]
    return client.publish(topic, payload, qos=1, properties=props)

if __name__ == "__main__":
    port = int(os.environ.get("MQTT_PORT", "1883"))
    dev_log, gw_log, cloud_log = logger("device"), logger("gateway"), logger("ingest")
    done = []

    def on_cloud(_c, _u, m):                            # cloud consumer
        tp = dict(m.properties.UserProperty)["traceparent"]
        tid, parent, _ = parse_traceparent(tp)
        cloud_log.info("stored reading", extra={"ctx": {"trace_id": tid, "parent_span": parent,
                                                        "topic": m.topic}})
        done.append(tid)

    def on_gw(c, _u, m):                                # gateway: new span, same trace
        tid, parent, flags = parse_traceparent(dict(m.properties.UserProperty)["traceparent"])
        tp = f"00-{tid}-{secrets.token_hex(8)}-{flags}"
        gw_log.info("forwarding", extra={"ctx": {"trace_id": tid, "parent_span": parent}})
        publish_traced(c, "cloud/" + m.topic, m.payload, tp)

    mk = lambda cid: mqtt.Client(mqtt.CallbackAPIVersion.VERSION2, client_id=cid, protocol=mqtt.MQTTv5)
    cloud, gw, dev = mk("ingest"), mk("gw-7"), mk("sensor-42")
    cloud.on_message, gw.on_message = on_cloud, on_gw
    for c in (cloud, gw, dev): c.connect("127.0.0.1", port); c.loop_start()
    cloud.subscribe("cloud/#", qos=1); gw.subscribe("site/+/temp", qos=1); time.sleep(0.3)

    dev_log.info("sampled", extra={"ctx": {"trace_id": parse_traceparent(tp)[0], "temp_c": 21.4}})
    publish_traced(dev, "site/sensor-42/temp", b'{"temp_c":21.4}', tp)
    for _ in range(30):
        if done: break
        time.sleep(0.1)
    for c in (cloud, gw, dev): c.loop_stop(); c.disconnect()

16Metrics and alerting

Two checklists help decide which metrics to collect. Gregg's USE method asks, for every resource, about utilisation, saturation and errors [104]; on a gateway that means CPU, memory, flash wear, the uplink and the store-and-forward buffer. Wilkie's RED method asks, for every service, about request rate, errors and duration [105]. Prometheus is the de facto open-source metrics system for this: targets expose counters, gauges, histograms and summaries over HTTP, Prometheus scrapes and stores them as labelled time series, and rules written in PromQL raise alerts that Alertmanager groups, deduplicates, silences and routes [106,107].

16.1 Alert on symptoms and error budgets

Good alerts page a human only for conditions that need urgent action and that users would notice; everything else becomes a ticket or a dashboard [96]. The SRE practice is to define a service level objective (SLO) such as "99.9 % of device messages are delivered to storage within 60 s over 30 days" and treat the remaining 0.1 % as an error budget. The Site Reliability Workbook recommends alerting on the burn rate of that budget with multiple windows: page if 2 % of a 30-day budget is consumed in one hour (burn rate 14.4) or 5 % in six hours (burn rate 6), each confirmed by a shorter window so that the alert also resets quickly; open a ticket for 10 % in three days [108].

burn_rate.py: error-budget arithmetic
"""Error-budget arithmetic behind burn-rate alerts."""
def budget_minutes(slo, days=30):
    return (1 - slo) * days * 24 * 60

def burn_rate_threshold(budget_fraction, window_h, period_days=30):
    """Burn rate that consumes `budget_fraction` of the budget in `window_h`."""
    return budget_fraction * period_days * 24 / window_h

def time_to_exhaustion_h(error_ratio, slo, period_days=30):
    return period_days * 24 / (error_ratio / (1 - slo))

if __name__ == "__main__":

    print(f"5% in 6h  -> burn rate {burn_rate_threshold(0.05, 6):.1f}")
    print(f"10% in 3d -> burn rate {burn_rate_threshold(0.10, 72):.1f}")
    print(f"1% errors vs 99.9% SLO exhausts budget in {time_to_exhaustion_h(0.01, 0.999):.0f} h")

17High availability

IEC 60050-192 defines availability as the ability to be in a state to perform as required, and gives the usual measures: mean operating time between failures (MTBF) and mean time to restoration (MTTR) [109]. Steady-state availability is MTBF/(MTBF+MTTR). Components in series multiply their availabilities; redundant components in parallel fail only when all fail, so their unavailabilities multiply; and a k-of-n cluster follows the binomial distribution [110]. These formulas assume independent failures, which is the assumption that real outages most often break.

availability.py: series, parallel and k-of-n availability
"""Steady-state availability of series, parallel and k-of-n structures."""
from math import comb

def a_unit(mtbf_h, mttr_h):
    return mtbf_h / (mtbf_h + mttr_h)

def series(*a):                      # all must work
    p = 1.0
    for x in a: p *= x
    return p

def parallel(*a):                    # at least one must work (independent failures)
    q = 1.0
    for x in a: q *= 1 - x
    return 1 - q

def k_of_n(k, n, a):                 # at least k of n identical units
    return sum(comb(n, i) * a**i * (1 - a)**(n - i) for i in range(k, n + 1))

def downtime_min_per_year(a):
    return (1 - a) * 365.25 * 24 * 60

if __name__ == "__main__":
    gw = a_unit(mtbf_h=20_000, mttr_h=48)            # truck roll to replace a gateway
    lte, broker = 0.995, 0.999
    single = series(gw, lte, broker)
    dual_wan = series(gw, parallel(lte, 0.99), broker)          # add wired backhaul
    cluster = series(gw, parallel(lte, 0.99), k_of_n(2, 3, 0.999))
    for name, a in [("gateway alone", gw), ("single path", single),
                    ("+ dual WAN", dual_wan), ("+ 2-of-3 broker", cluster)]:
        print(f"{name:16s} A={a:.5f}  downtime={downtime_min_per_year(a):8.0f} min/yr")

Adding a wired back-up link and a three-node broker cluster recovers most of the loss, but the result can never exceed the gateway's own 99.76 %. The cheapest improvement is often not more redundancy in the cloud but a shorter MTTR at the edge (a spare on site), or edge autonomy so that local control keeps working when the uplink does not, as edge runtimes such as AWS IoT Greengrass are designed to do [111].

Two classic results shape these designs. Gray's 1985 analysis of Tandem systems found that administration and software, not hardware, caused most outages, and argued for process pairs and transactions to mask software faults [117]. The CAP theorem, proved by Gilbert and Lynch, shows that during a network partition a distributed store must choose between consistency and availability [118]. IoT systems partition constantly, which is why most choose availability at the edge (keep accepting readings locally) and reconcile later.

18Disaster recovery

High availability handles component failures inside a site or region; disaster recovery (DR) handles the loss of a whole site, region, account or data set, whether through natural disaster, operator error, ransomware or a provider outage. Two objectives frame every DR plan. The recovery time objective (RTO) is the longest acceptable time to restore service, and the recovery point objective (RPO) is the point in time to which data must be recovered, which sets how much data may be lost [119]. NIST SP 800-34 describes contingency planning as a process from business impact analysis through recovery strategies, plan testing and maintenance [119], and ISO 22301 specifies requirements for a business continuity management system [120].

18.1 What is special about IoT disaster recovery

  • Devices hold part of the state. Buffered readings on gateways can backfill the RPO gap after a cloud restore, if buffers are large enough and replays are idempotent.
  • Devices must find the recovered service. Endpoints baked into firmware cannot fail over. Use DNS names you control or a provisioning service that can reassign devices, and test that devices actually reconnect to the DR region. Azure IoT Hub, for example, documents Microsoft-initiated and customer-initiated failover between paired regions and the device reconnection that follows [116].
  • Identity must survive. Device registries, certificates, CA keys and policies are as critical as the data. Losing the registry can strand an entire fleet.
  • Recovery causes a thundering herd. Every device reconnects and replays its buffer at once, so DR capacity must cover the surge, and devices must back off with jitter [48].
  • Operator error is a disaster too. The February 2017 Amazon S3 outage in US-EAST-1 began when a command to remove a small number of servers was entered incorrectly and removed a larger set; AWS responded by adding safeguards to the tool [122].

An untested DR plan is a hope, not a plan. NIST SP 800-34 calls for testing, training and exercises of contingency plans [119]. For IoT, a DR exercise should measure achieved RPO and RTO against targets, include a sample of real devices reconnecting to the recovery environment, restore the device registry and certificates from backup, and verify that OTA updates can still be signed and delivered from the recovered site.

Exercise 1. Place each test at MIL, SIL, PIL or HIL: (a) a Simulink model of a pump controller run against a tank model; (b) the pump firmware compiled for Linux and run against the same tank model; (c) the firmware running in Renode with a simulated tank; (d) the production board driving a real pump relay while a real-time computer simulates tank level through an analogue input.

Solution

(a) MIL, (b) SIL, (c) PIL, because the real binary runs on an emulated target processor, (d) HIL [8,13].

Exercise 2. A CoAP client uses the default transmission parameters (ACK_TIMEOUT 2 s, ACK_RANDOM_FACTOR 1.5, MAX_RETRANSMIT 4). In a conformance test you drop every ACK. What is the longest time from the first transmission to the last retransmission, and how long should the test wait before expecting the client to give up?

Solution

The initial timeout is chosen between 2 s and 3 s and doubles after each retransmission. The worst case to the last retransmission is MAX_TRANSMIT_SPAN = 2 × (24 − 1) × 1.5 = 45 s, and the time to wait for a final ACK is MAX_TRANSMIT_WAIT = 2 × (25 − 1) × 1.5 = 93 s, as derived in RFC 7252 [40]. A conformance test should timestamp each retransmission and check the doubling, not just the count.

Exercise 3. A Gilbert-Elliott link has pGB = 0.02 and pBG = 0.4, and every packet in the bad state is lost. What are the mean loss rate and mean burst length? Change the parameters in gilbert_elliott.py to check.

Solution

Loss = 0.02/(0.02 + 0.4) ≈ 4.8 %; mean burst = 1/0.4 = 2.5 packets [47]. A protocol that retries immediately loses about 60 % of first retries (the chance of staying in the bad state); one that waits a few packet times usually succeeds.

Exercise 4. An ingest service receives 50,000 messages per second and the mean time a message spends in the service is 120 ms. How many messages are inside the service on average? If latency rises to 2 s at the same rate, what happens to memory?

Solution

By Little's law, L = λW = 50,000 × 0.12 = 6,000 messages; at 2 s it is 100,000 messages, so in-flight memory grows about 17 times [49]. Rising in-flight counts at a constant arrival rate are an early stress-test warning.

Exercise 5. A sensor sleeps at 2 µA and wakes every 300 s for 0.5 s at 20 mA. Estimate the average current and the life on a 220 mAh coin cell with 80 % derating.

Solution

Iavg = 2 µA × 299.5/300 + 20 mA × 0.5/300 ≈ 2.0 + 33.3 = 35.3 µA. Life ≈ 176 mAh / 0.0353 mA ≈ 4,980 h ≈ 208 days. The active phase is 94 % of the charge, so shorten it (faster radio join, fewer retries) before touching sleep current. Coin cells also lose capacity under high pulse currents, so a 20 mA pulse may need a buffer capacitor [61].

Exercise 6. The fault-injection campaign in Section 11 showed that a stuck sensor is reported as good. Extend the pipeline to flag it, and add a test.

Solution 
class StuckAwarePipeline(Pipeline):
    def __init__(self, driver, stuck_limit=5, **kw):
        super().__init__(driver, **kw)
        self.stuck_limit, self._same, self._prev = stuck_limit, 0, None

    def sample(self):
        r = super().sample()
        if r["quality"] == "good":
            v = r["value"]
            self._same = self._same + 1 if v == self._prev else 0
            self._prev = v
            if self._same >= self.stuck_limit:
                return {"value": v, "quality": "suspect_stuck"}
        return r

def test_stuck_detected():
    fi = FaultInjector(SensorDriver()); p = StuckAwarePipeline(fi, stuck_limit=5)
    with fi.fault("stuck"):
        q = [p.sample()["quality"] for _ in range(7)]
    assert q[:5] == ["good"] * 5 and q[5] == "suspect_stuck"

The test passes. Choose the limit from the sensor's noise floor: a real 12-bit sensor rarely repeats exactly for minutes, but a slowly changing, heavily filtered one might, so the limit should be validated against field data.

Exercise 7. Using Arrhenius with Ea = 0.7 eV, how many years at 40 °C does a 1,000-hour test at 85 °C represent? What assumption could make the answer badly wrong?

Solution

AF ≈ 26.0 (from accel_life.py), so 1,000 h ≈ 26,000 h ≈ 3.0 years. The answer assumes the dominant failure mechanism is the one with that activation energy and that the stress does not introduce mechanisms absent in use; plastics, batteries and electrolytic capacitors can fail at 85 °C in ways that never happen at 40 °C [71,73].

Exercise 8. How many failure-free unit-hours are needed to demonstrate an MTBF of 100,000 h at 60 % confidence under the exponential model?

Solution

T = 100,000 × (−ln 0.4) ≈ 91,600 unit-hours, for example 100 units for about 920 h [73].

Exercise 9. Two gateways, each 99.761 % available, are deployed as an active/standby pair at a site. What is the pair's availability if failures are independent? Name two common-cause failures that would invalidate the calculation.

Solution

1 − (0.00239)2 ≈ 0.9999943, about 3 minutes of downtime a year [110]. Common causes include a shared power supply or UPS, a shared uplink, the same firmware bug triggered by the same input, and a site-wide event such as flooding. In practice the pair's availability is set by these, not by the product formula.

Exercise 10. A service has a 99.5 % 30-day SLO. Over the last hour its error ratio was 2 %. What is the burn rate, would the fast-burn page in alerts.yml fire after adjusting the threshold for this SLO, and when would the budget run out at this rate?

Solution

Burn rate = 0.02 / 0.005 = 4. The fast-burn threshold is 14.4 × 0.005 = 7.2 % errors, so it does not fire; the 6-hour rule (6 × 0.005 = 3 %) would not fire either. At burn rate 4 the 30-day budget lasts 30/4 = 7.5 days, which is the kind of slow burn the 3-day ticket rule (burn rate 1) is for [108].

Exercise 11. The cloud database is backed up every 6 h and a full restore takes 3 h. Gateways buffer 24 h of readings and replay them idempotently on reconnect. What are the effective RPO for device readings and the RTO? What else must be in the DR test?

Solution

Without buffering the worst-case RPO is 6 h. Because gateways can replay up to 24 h, and the worst gap is 6 h of lost data plus 3 h of restore, the effective RPO for readings is close to zero, as long as replay is idempotent and the recovered ingest can absorb the replay surge. RTO is at least 3 h plus failover of DNS or endpoints and device reconnection. The test must also restore the device registry and certificates, show real devices reconnecting, and check OTA signing from the recovered site [119,121].

Exercise 12. Extend ota_powercut.py so that the new image is valid but crashes on boot and therefore never confirms. What must the bootloader model do so the device ends up on A, and what test would show it?

Solution

The trial must be one-shot: on the next boot after an unconfirmed trial, the bootloader clears the trial flag and boots the confirmed slot, as MCUboot's test-and-revert mode does [88]. In the model, boots() must consume trial and the test must boot twice, asserting that the second boot selects A and that the device reports the failed update to the server.

Exercise 13. Parse traceparent: 00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-00. Is it sampled? What should a gateway forward?

Solution

Version 00, trace-id 0af7651916cd43dd8448eb211c80319c, parent-id b7ad6b7169203331, flags 00, so not sampled. The gateway should keep the trace-id and flags and replace the parent-id with its own span-id, even if it does not record the span [103].

21Trivia with answers

1. Who introduced "observability" as a formal property of systems?

Answer

Rudolf E. Kálmán, in control theory, around 1960; his 1963 paper gives the mathematical description used today [94].

2. In the IP code, what do the two digits of IP67 mean?

Answer

6: dust-tight; 7: protected against the effects of temporary immersion in water [67].

3. Which company's blog introduced the "Simian Army", and what did Chaos Monkey do?

Answer

Netflix, in 2011. Chaos Monkey randomly disabled production instances to make sure services survived such failures [81].

4. Why did NASA's Mars Pathfinder keep resetting itself in July 1997, and how was it fixed?

Answer

A priority inversion: a low-priority task held a mutex needed by a high-priority bus task while medium-priority tasks ran, so a watchdog detected the missed deadline and reset the system. Engineers reproduced it on a ground replica and fixed it by enabling priority inheritance on the mutex, uploaded to the spacecraft [123].

5. What software fault destroyed Ariane 5 on its first flight in 1996?

Answer

An unprotected conversion of a 64-bit floating-point value to a 16-bit signed integer overflowed in inertial reference system software reused from Ariane 4, whose trajectory never produced such large values. Both inertial units failed the same way [124]. It is a classic argument for testing reused components against the new operating envelope.

6. How long is a W3C trace-id, in bytes and hex characters?

Answer

16 bytes, written as 32 lower-case hex characters; an all-zero trace-id is invalid [103].

7. How many severity levels does syslog define, and what is level 0?

Answer

Eight, numbered 0 to 7; 0 is Emergency ("system is unusable") [100].

8. Where does the burn-rate threshold 14.4 come from?

Answer

Consuming 2 % of a 30-day error budget in one hour: 0.02 × 720 h / 1 h = 14.4 [108].

9. What is the check value of CRC-16/CCITT-FALSE?

Answer

0x29B1, the CRC of the ASCII string "123456789" [28].

10. What does a Weibull shape parameter β = 1 reduce to?

Answer

The exponential distribution, with a constant failure rate, the flat floor of the bathtub curve [74,73].

11. Who named the load-testing pitfall "coordinated omission"?

Answer

Gil Tene, author of HdrHistogram, whose documentation describes recording latency with correction for it [51].

12. What caused the February 2017 Amazon S3 outage in US-EAST-1?

Answer

An operator command intended to remove a small number of servers was entered incorrectly and removed more capacity, including servers supporting two S3 subsystems, which then needed a full restart [122].

13. Which 1985 Tandem report found that administration and software caused more outages than hardware?

Answer

Jim Gray's "Why do computers stop and what can be done about it?" [117].
