1. What is an embedded system?

An embedded system is a computer built into a larger product to perform a dedicated function, usually interacting with the physical world through sensors and actuators. Lee and Seshia describe such devices as cyber-physical systems, in which computation, networking and physical processes are tightly coupled, so timing and concurrency are part of a program's correctness rather than mere performance concerns [1]. Wolf likewise frames embedded design around constraints that general-purpose computing rarely faces: tight cost, limited memory, real-time deadlines and low energy budgets [2].

In the Internet of Things (IoT), the embedded system is the "thing": a sensor node, smart lock, wearable, industrial controller or gateway. Its software, stored in non-volatile memory and executed directly by the processor, is called firmware. Firmware sits closer to the hardware than ordinary application software: it configures clocks, owns the interrupt vector table, talks to peripherals through memory-mapped registers and often runs for years without a reboot.

Key characteristics of IoT embedded systems
  • Resource-constrained: often tens to hundreds of kilobytes of RAM and flash on a microcontroller (MCU).
  • Reactive and concurrent: events from hardware interrupts, timers and radios arrive asynchronously.
  • Timing-critical: some outputs are only correct if they arrive before a deadline.
  • Energy-limited: many devices run on batteries or harvested energy for years.
  • Long-lived and remote: they must recover from faults on their own and be securely updatable in the field.

2. Embedded systems architecture

Most IoT firmware is organised in layers, each hiding hardware detail from the one above. At the bottom is the silicon: a processor core (for example an Arm Cortex-M), on-chip memories and peripherals such as GPIO, timers, UART, SPI, I²C, ADCs and radios. Above it sit the start-up code and vendor support files, the hardware abstraction layer, device drivers, an optional operating system or scheduler, middleware (network stacks, file systems, security libraries) and finally the application.

2.1 Processor and memory map

Arm's Cortex-M family dominates 32-bit microcontrollers. The ARMv7-M architecture defines a fixed 4 GB address map divided into regions for code, SRAM, peripherals, external RAM, external devices and the private peripheral bus (PPB) that hosts system components such as the Nested Vectored Interrupt Controller (NVIC), SysTick timer and System Control Block [3]. Because peripherals appear at fixed addresses, firmware controls hardware simply by reading and writing memory locations: a technique called memory-mapped I/O [4].

3. Bare-metal programming

Bare-metal firmware runs directly on the hardware with no operating system. The programmer is responsible for everything that happens from reset: setting up the stack, copying initialised data from flash to RAM, zeroing uninitialised data, configuring clocks and then entering main(). On Cortex-M, the processor itself loads the initial stack pointer from the first word of the vector table and the reset handler address from the second word, so a reset handler can be written entirely in C [3,4].

3.3 The super-loop pattern

Without an OS, firmware is commonly structured as a super-loop: a for(;;) that polls flags set by interrupt handlers and calls short, non-blocking functions in turn. It is simple, deterministic and small, but response time depends on the length of the longest pass through the loop, and the design becomes hard to maintain as concurrent activities multiply. This is the main motivation for moving to an RTOS [9].

4. Firmware development workflow

Firmware is cross-compiled: built on a desktop host for a different target architecture, for example with the Arm GNU Toolchain (arm-none-eabi-gcc) [10]. The resulting ELF file is converted to a binary or HEX image and programmed into flash through a debug probe using SWD or JTAG, using tools such as OpenOCD [11] or probe-rs [12], and debugged with GDB [13].

4.1 Good practice

  • Coding standards. MISRA C:2023 restricts C to a safer subset for critical systems [14]; BARR-C:2018 focuses on practical rules that reduce bugs [15]. Safety-related products follow functional-safety standards such as IEC 61508 [16].
  • Test off target. Isolate logic behind a HAL so it can be unit-tested on the host, and use emulators such as QEMU [17] or Renode [18] for continuous integration without hardware.
  • Design for updates and security from day one. NIST recommends that IoT device manufacturers plan for secure, authenticated software updates as a core device capability [19].

5. Bootloaders

A bootloader is the first code that runs after reset (often after an immutable ROM boot stage). On an MCU it typically decides which firmware image to run, verifies its integrity and authenticity, optionally installs a pending update and then jumps to the application. MCUboot, a widely used open-source secure bootloader for 32-bit MCUs and the default for Zephyr, verifies cryptographic signatures on images and supports several upgrade strategies, including swapping primary and secondary slots so that a faulty update can be reverted [20,21]. On Linux-class devices, U-Boot plays the same role: it initialises DRAM, loads the kernel and device tree and passes control to the kernel [22].

6. Device drivers

A device driver is the software component that knows how to operate a particular piece of hardware and exposes it to the rest of the system through a well-defined interface. On a bare-metal MCU this may be a simple module with init(), read() and write() functions. In an RTOS, drivers are integrated with the kernel so that a thread can block while a transfer completes. Zephyr, for example, defines a generic device model in which each driver implements an API structure of function pointers for its device class and devices are instantiated from the devicetree at build time [24,25].

In Linux, drivers run in kernel space and register with a bus (PCI, USB, I²C, SPI or the platform bus for memory-mapped SoC peripherals). The kernel matches devices described in the devicetree against drivers' of_match_table entries and calls the driver's probe() function [26,27]. The devicetree itself is a hardware description format standardised by devicetree.org [28].

6.1 Driver design checklist

  • Separate the bus (I²C, SPI) from the device logic so the same sensor driver works on any controller.
  • Use interrupts or DMA instead of busy-waiting for long transfers, and define a timeout for every wait.
  • Make ownership and concurrency explicit: who may call the driver, from which context (thread or ISR), and which lock protects it.
  • Expose power hooks (suspend/resume) so the power manager can switch the device off [29].

7. Hardware abstraction layers (HAL)

A hardware abstraction layer provides a uniform programming interface over differing hardware, so higher layers do not depend on register details. Abstraction exists at several levels:

  • Core level. CMSIS-Core gives every Cortex-M vendor a common way to access the NVIC, SysTick, system control block and core intrinsics, with standard names such as NVIC_EnableIRQ() [23].
  • Vendor peripheral level. STMicroelectronics' STM32Cube HAL offers portable, handle-based APIs (for example HAL_GPIO_WritePin, HAL_UART_Transmit_IT) together with thinner "low-layer" (LL) APIs that are closer to the registers [30].
  • Cross-vendor level. Zephyr's device APIs and devicetree make the same application source build for boards from many vendors [25,31]; in Rust, the embedded-hal crate defines traits such as OutputPin, I2c and SpiDevice that any chip HAL can implement and any driver can consume [32].
Trade-offEvery abstraction costs some code size and latency, and generic HALs may not expose every hardware feature. A common strategy is to use the vendor HAL for initialisation and drop to low-layer or register access in time-critical paths.

8. Interrupt handling

An interrupt is a hardware signal that suspends the current instruction stream so that an interrupt service routine (ISR) can respond to an event. On Cortex-M the NVIC supports up to 240 external interrupts on the Cortex-M4, each with a programmable priority where a lower number means a higher urgency [5]. On exception entry the processor automatically pushes eight registers (R0–R3, R12, LR, PC and xPSR) onto the stack, so ISRs can be ordinary C functions with no special keyword [3,5]. Two hardware optimisations reduce overhead: tail-chaining, where a pending interrupt is entered directly after another finishes without unstacking and re-stacking, and late arrival, where a higher-priority interrupt that arrives during stacking is serviced first [4].

8.1 Rules for safe ISRs

  1. Keep ISRs short. Acknowledge the hardware, move data to a buffer and defer heavy processing to a task (the "top half / bottom half" split).
  2. Clear the interrupt source before returning, or the interrupt will immediately fire again.
  3. Share data safely. Variables written in an ISR and read elsewhere must be volatile [8], and multi-word updates need a critical section or a lock-free structure such as a single-producer/single-consumer ring buffer.
  4. Never block in an ISR. RTOSes provide special ISR-safe APIs, for example FreeRTOS functions ending in FromISR [9].
  5. Mind the priorities relative to the RTOS: in FreeRTOS Cortex-M ports, ISRs that call kernel APIs must have a priority numerically at or above configMAX_SYSCALL_INTERRUPT_PRIORITY (that is, logically lower or equal urgency) [9].

9. Memory management

Embedded memory is scarce and usually without virtual memory, so its layout is decided largely at link time. A typical MCU RAM image contains .data (initialised globals), .bss (zero-initialised globals), a heap if one is used and one or more stacks. Each RTOS task gets its own stack, and stack overflow is a classic cause of silent corruption; FreeRTOS offers optional stack-overflow checking hooks for this reason [9].

9.1 Static versus dynamic allocation

Dynamic allocation with malloc/free is risky in long-running embedded software because of fragmentation, non-deterministic execution time and the possibility of allocation failure at run time. MISRA C:2023 therefore states that the dynamic memory functions of <stdlib.h> shall not be used (Rule 21.3) [14]. RTOSes offer safer alternatives: FreeRTOS ships five heap schemes, from heap_1 (allocate only, never free) to heap_5 (spans non-contiguous regions), and every kernel object can also be created statically with caller-supplied memory [9]. Fixed-size block pools (Zephyr memory slabs, for instance) give constant-time allocation without fragmentation.

9.2 Memory protection

The Cortex-M MPU divides memory into regions with access permissions and execute-never attributes; violations raise a MemManage fault [5]. RTOSes use it to catch stack overflows and to isolate untrusted threads: Zephyr, for example, supports user-mode threads whose memory access is limited by the MPU [33]. On Arm's ARMv8-M architecture (Cortex-M23/M33), TrustZone extends this by partitioning the system into secure and non-secure worlds.

10. Real-time processing

A real-time system must produce correct results and meet timing constraints. In a hard real-time system, a missed deadline is a failure; in a soft one it degrades quality [34]. What matters is predictability, the worst-case response time, not average speed.

10.1 Scheduling theory

Liu and Layland's 1973 paper laid the foundations. For n independent periodic tasks with deadlines equal to their periods, fixed-priority rate-monotonic (RM) scheduling (shorter period gets higher priority) is optimal among fixed-priority policies, and the task set is guaranteed schedulable if total utilisation satisfies the bound below; dynamic-priority earliest-deadline-first (EDF) scheduling can use up to 100 % of the processor [35].

U = Σ Ci/Ti ≤ n(21/n − 1)   →   ln 2 ≈ 0.693 as n → ∞   (RM)      U ≤ 1   (EDF)

The RM bound is sufficient but not necessary: task sets above it may still be schedulable, which exact response-time analysis can confirm [34].

10.2 Priority inversion

When a high-priority task waits for a mutex held by a low-priority task, a medium-priority task can preempt the low one and delay the high one indefinitely. Sha, Rajkumar and Lehoczky formalised the priority inheritance and priority ceiling protocols that bound this blocking [36]. FreeRTOS mutexes implement priority inheritance, unlike its binary semaphores [9].

11. Watchdogs

A watchdog timer (WDT) is an independent counter that resets the system unless software periodically restarts ("kicks" or "feeds") it. It is the last line of defence against hangs caused by software bugs, deadlocks, corrupted memory or electrical upsets. Ganssle stresses that a watchdog is only as good as its design: it should run from an independent clock, be impossible for crashed code to disable, and be kicked only after the software has proved it is healthy, never from a timer interrupt that keeps running even when the application is stuck [37].

  • Independent watchdog: clocked from a separate low-speed oscillator, so it keeps running if the main clock fails.
  • Window watchdog: also resets if the kick arrives too early, catching code that runs away in a tight loop.
  • Task-level health checks: in multitasking firmware, a supervisor kicks the hardware watchdog only when every monitored task has reported progress (as in the FreeRTOS example above) [38].
  • Post-mortem data: record the reset cause and a small crash log in a RAM region that survives reset, so watchdog resets can be diagnosed in the field [38].

Embedded Linux exposes hardware watchdogs through /dev/watchdog: any write keeps the system alive, and the driver can be configured so that closing the device without first writing the "magic" character V does not stop the watchdog, protecting against a daemon that crashes [39].

12. Power optimization and sleep modes

For battery-powered IoT nodes, firmware decides battery life. Average current is dominated by how long the device is awake and how deeply it sleeps in between:

Iavg = (Iactive·tactive + Isleep·tsleep) / (tactive + tsleep)     Battery life ≈ Capacity / Iavg

12.1 Sleep modes

Cortex-M processors enter low-power states with the WFI (wait for interrupt) and WFE (wait for event) instructions. The SLEEPDEEP bit in the System Control Register selects between sleep and deep sleep, and SLEEPONEXIT lets an interrupt-driven application return to sleep automatically after each ISR [5]. What "deep sleep" actually switches off is chip-specific. On the ESP32, for example, light sleep clock-gates the CPUs and digital peripherals while retaining RAM, whereas deep sleep powers down the CPUs and most RAM, leaving the RTC domain running so that a timer, external pin, touch sensor or the ultra-low-power co-processor can wake the chip, which then restarts from the boot process [40].

12.2 Firmware techniques

  • Tickless idle. A periodic OS tick wakes the CPU needlessly. FreeRTOS's tickless idle mode stops the tick when no task is ready and programs a single wake-up for the next timeout [9]; Zephyr's power-management subsystem similarly selects a low-power state based on the expected idle time [29].
  • Race to sleep. Run fast, finish the work and sleep as early as possible; use DMA so the CPU can sleep during transfers.
  • Gate everything. Disable clocks to unused peripherals, put sensors into their own shutdown modes and configure unused GPIOs to avoid floating inputs.
  • Batch radio traffic. Radio transmission is usually the largest current draw, so aggregate readings and transmit less often.

13. Firmware updates and over-the-air (OTA) updates

Devices deployed for years will need bug fixes and security patches. The IETF's SUIT working group published RFC 9019, an architecture for firmware updates on constrained IoT devices: an author builds and signs firmware, a manifest describes the image (version, digest, target device, dependencies, signature) and a status tracker reports progress, and the device must verify the manifest before installing anything [41]. RFC 9124 defines the information the manifest must contain to defeat threats such as rollback to vulnerable versions or installing firmware intended for a different device [42].

13.1 Design principles

  • Atomicity. A power cut at any instant must leave a bootable image. Dual-slot (A/B) layouts achieve this at the cost of flash space; ESP-IDF, for instance, uses two OTA app partitions plus an otadata partition that records which one to boot [43].
  • Authenticity and integrity. Verify a signature over the image (or its manifest) with a public key stored in immutable memory before booting it [20,41].
  • Anti-rollback. Use a monotonic version or security counter so attackers cannot reinstall older, vulnerable firmware [42].
  • Health confirmation. New images run in a trial state until the application marks them valid; ESP-IDF's app rollback feature reverts if esp_ota_mark_app_valid_cancel_rollback() is not called [43], and MCUboot's swap-with-revert mode behaves the same way [20].
  • Bandwidth. For low-power radios, consider delta updates and resumable downloads; Zephyr documents OTA over Bluetooth LE, LwM2M and other transports using MCUboot-compatible images [44].

14.1 C

C remains the lingua franca of firmware. Its abstract machine maps closely onto real hardware, pointers can address memory-mapped registers, and volatile gives defined semantics for hardware access [8]. The current standard is ISO/IEC 9899:2024 (C23) [8], though most embedded code targets C99 or C11 for toolchain compatibility. Because the language permits undefined behaviour, safety-related projects apply coding standards such as MISRA C:2023 [14] and BARR-C [15] enforced by static analysis. All examples in Sections 3–13 are in C.

Embedded C idioms worth knowing

  • Fixed-width types from <stdint.h> (uint32_t) rather than int, whose width varies by target [8].
  • Unsigned arithmetic for timers: (now - start) >= timeout is wrap-safe because unsigned overflow is defined as modulo 2N [8].
  • Bit manipulation with masks and shifts, and static for module-private state.

14.2 C++

C++ adds type-safe abstractions that, used carefully, cost nothing at run time. constexpr functions can be evaluated during compilation [45], templates let peripherals be described as types, and RAII ties resource release (such as re-enabling interrupts) to scope exit. The C++ Core Guidelines recommend RAII for resource management and prefer compile-time checking to run-time checking [46]. Embedded projects commonly build with -fno-exceptions -fno-rtti and avoid the heap after start-up; Zephyr and Arm Mbed-style frameworks support C++ applications.

14.3 Rust

Rust offers memory safety without a garbage collector. Its ownership and borrowing rules let the compiler reject data races and use-after-free errors, which in embedded code also models the fact that a peripheral should have exactly one owner [47]. Embedded programs are written with #![no_std], linking against the core library instead of the operating-system-dependent standard library [47]. The ecosystem is layered: peripheral access crates (PACs) generated from vendor SVD files with svd2rust, chip HAL crates on top, and board support crates above those [47]. The embedded-hal 1.0 traits let one sensor driver run on any chip [32]. For concurrency, RTIC uses the NVIC's hardware priorities to schedule tasks with compile-time-checked resource sharing [48], while Embassy provides an async/await executor that puts the core to sleep when no task is ready [49].

14.4 MicroPython

MicroPython is a lean implementation of Python 3 that includes a small subset of the standard library and is optimised to run on microcontrollers; it provides an interactive prompt (REPL) on the device and hardware modules such as machine for pins, buses, timers, watchdogs and sleep [50,51]. Interrupt handlers have strict rules: on most ports a "hard" ISR cannot allocate heap memory, so it should only update pre-allocated state and defer heavier work with micropython.schedule(); the documentation also recommends allocating an emergency exception buffer so errors inside ISRs can be reported [52].

14.5 Python

Full CPython [53] runs on Linux-class embedded devices such as gateways and single-board computers. It is excellent for orchestration, data processing, cloud connectivity and test automation, but it is not deterministic enough for hard real-time control, which is usually delegated to an MCU or kernel driver. Libraries such as gpiozero wrap the Linux GPIO interfaces in a high-level API [54].

14.6 Embedded Java

Oracle's Java ME Embedded targets resource-constrained devices with a compact Java virtual machine. Applications are packaged as IMlets (derived from the MIDlet model), and the Device Access (Device I/O) API gives Java code controlled access to GPIO, I²C, SPI, UART and other peripherals, subject to security permissions [55]. The most recent release documented by Oracle is 8.3 [55]. Java's garbage collection and runtime footprint make it better suited to gateways and higher-end devices than to small MCUs.

14.7 Assembly

Assembly is still required where C cannot express the operation: early start-up, context-switch code that saves and restores registers, special instructions (WFI, CPSID, barriers) and occasionally hand-tuned DSP loops. Cortex-M processors execute only the Thumb instruction set (with 32-bit Thumb-2 encodings on ARMv7-M) [3]. When assembly functions are called from C they must follow the Arm Procedure Call Standard: arguments arrive in R0–R3, the result returns in R0, R0–R3 and R12 may be clobbered, and R4–R11 must be preserved [56]. The GNU assembler syntax used below is documented in the binutils manual [57].

15.1 FreeRTOS

FreeRTOS is a small, portable real-time kernel. Its scheduler always runs the highest-priority task that is able to run, optionally time-slicing among tasks of equal priority; tasks communicate through queues, semaphores, mutexes (with priority inheritance), event groups and lightweight direct-to-task notifications [9]. Configuration is through the FreeRTOSConfig.h header, where options such as configTICK_RATE_HZ, configUSE_PREEMPTION and configUSE_TICKLESS_IDLE are set [9]. The kernel is distributed under the MIT licence [58]. A complete task/ISR/watchdog example appears in Section 10.4.

15.2 Zephyr

Zephyr is a scalable RTOS that supports multiple hardware architectures and is permissively licensed under Apache 2.0 [31]; the project is hosted by the Linux Foundation [63]. Hardware is described with devicetree and software features are selected with Kconfig, so a single application can be rebuilt for many boards [25]. Threads with negative priorities are cooperative (never preempted by other threads) while non-negative priorities are preemptible [33]. Zephyr integrates the MCUboot bootloader for device firmware upgrade [21] and provides a power-management subsystem [29].

15.3 Embedded Linux

Embedded Linux brings the full Linux kernel, drivers and user space to devices with an MMU and tens of megabytes of RAM or more. A typical system consists of a bootloader (often U-Boot) [22], the kernel plus a devicetree blob describing the board [28], a root file system and applications. Distributions are built from source rather than installed: the Yocto Project uses the OpenEmbedded build system and BitBake recipes and layers to produce custom, reproducible images [64], while Buildroot uses Kconfig and Makefiles to generate a toolchain, kernel and root file system with a simpler workflow [65]. Real-time behaviour improved substantially when the PREEMPT_RT patches were merged into mainline Linux 6.12 in 2024 [59]. Drivers follow the kernel's device model (Section 6) [26,27].

15.4 RIOT OS

RIOT is an open-source operating system for low-end IoT devices with only kilobytes of memory. Baccelli and colleagues describe its design goals as a developer-friendly, standards-based platform: a microkernel with multithreading, a tickless real-time scheduler, programming in standard C and C++, partial POSIX compliance and a full IPv6/6LoWPAN network stack; it is licensed under LGPL-2.1 [60]. RIOT's documentation covers its supported boards, modules and APIs such as message-passing IPC and the ztimer timer subsystem [66].

15.5 Contiki and Contiki-NG

Contiki, introduced by Dunkels, Grönvall and Voigt in 2004, combined an event-driven kernel with optional preemptive multithreading and the ability to load and unload program modules at run time on tiny sensor nodes [67]. Its signature abstraction is the protothread: a stackless, extremely lightweight thread that lets event-driven code be written in a sequential, blocking style with only a couple of bytes of state per thread [68]. Because protothreads do not preserve the stack, local variables that must survive a wait are declared static. Contiki-NG began in 2017 as a fork of Contiki focused on dependable, standards-based IPv6 communication for next-generation IoT devices, including 6LoWPAN, RPL, TSCH and CoAP, and is released under the BSD-3-Clause licence [61,69].

15.6 TinyOS

TinyOS, developed at UC Berkeley for wireless sensor networks, pioneered a component-based, event-driven design: applications are built by wiring components together through bidirectional interfaces of commands and events, long operations are split-phase (a command starts them and an event signals completion), and deferred work runs as run-to-completion tasks [70]. It is written in nesC, a C dialect designed for TinyOS that enables whole-program analysis, including compile-time detection of data races [71]. Development has largely ceased, but its ideas influenced later sensor-network operating systems [62].

17. Exercises with solutions

Try each exercise before opening its solution.

Exercise 1 · The vanishing flag C, interrupts

A UART ISR sets int rx_done = 1; and main() waits with while (!rx_done) { }. The program works at -O0 but hangs forever at -O2. Why, and how do you fix it?

Show solution

Without volatile, the compiler may assume nothing outside the loop changes rx_done, load it once, and turn the loop into an infinite loop. Declaring it static volatile int rx_done; forces a fresh read on every iteration, because accesses to volatile objects must be performed as written [8]. For data larger than one machine word, also protect the read with a critical section, since volatile does not make accesses atomic.

Exercise 2 · SysTick arithmetic Cortex-M

(a) The core runs at 84 MHz. What reload value gives a 1 ms SysTick interrupt? (b) SysTick is a 24-bit down-counter. What is the longest interval it can time directly at 84 MHz?

Show solution

(a) The counter counts reload+1 cycles per period, so RELOAD = 84 000 000 / 1000 − 1 = 83 999. (b) The maximum reload is 224 − 1 = 16 777 215 [5], so the longest period is 16 777 216 / 84 000 000 ≈ 0.1997 s (about 200 ms). Longer intervals need a software counter or a low-power timer.

Exercise 3 · RAM budget Memory

An MCU has 32 KB of SRAM. The map file shows .data = 1.2 KB and .bss = 6 KB. The application uses FreeRTOS with four tasks of 1 KB stack each, a 2 KB main/ISR stack, and kernel objects that need 3 KB. How much RAM is left, and what would you do with it?

Show solution

Used: 1.2 + 6 + 4 × 1 + 2 + 3 = 16.2 KB, leaving 15.8 KB. Keep a safety margin (for example 20–30 %) for stack growth found during testing; enable stack-overflow checking ([9]) and measure the high-water mark of each task stack with uxTaskGetStackHighWaterMark() before shrinking stacks. Prefer static allocation for kernel objects so the map file shows the true footprint [9].

Exercise 4 · Rate-monotonic schedulability Real-time

Three periodic tasks (C = worst-case execution time, T = period = deadline): τ1 (1 ms, 4 ms), τ2 (2 ms, 6 ms), τ3 (1 ms, 10 ms). Is the set guaranteed schedulable under RM? Under EDF?

Show solution

U = 1/4 + 2/6 + 1/10 = 0.250 + 0.333 + 0.100 = 0.683. The Liu–Layland bound for n = 3 is 3(21/3 − 1) ≈ 0.780 [35]. Since 0.683 ≤ 0.780 the set is schedulable under RM, with priorities τ1 > τ2 > τ3. Under EDF it is schedulable because U ≤ 1 [35].

Check with response-time analysis for τ3: R = 1 + ⌈R/4⌉·1 + ⌈R/6⌉·2. Start with R = C3 = 1: R = 1 + 1 + 2 = 4; then R = 1 + ⌈4/4⌉·1 + ⌈4/6⌉·2 = 4, converged at R3 = 4 ms ≤ 10 ms [34].

Exercise 5 · Battery life Power

A sensor wakes every 10 s, is active for 50 ms at 10 mA and sleeps at 5 µA. It runs from a 2000 mAh battery. Estimate the average current and battery life (ignore self-discharge and regulator losses).

Show solution

Iavg = (10 mA × 0.05 s + 0.005 mA × 9.95 s) / 10 s = (0.5 + 0.04975) / 10 ≈ 0.055 mA (55 µA). Life ≈ 2000 mAh / 0.055 mA ≈ 36 400 h ≈ 4.1 years. Note that the active burst contributes about 91 % of the charge: halving the active time is worth far more than halving the sleep current.

Exercise 6 · Priority inversion RTOS

A low-priority logging task takes a binary semaphore that guards the SPI flash. A high-priority control task then blocks on the same semaphore. A medium-priority networking task becomes ready and runs for 200 ms. What happens to the control task, and how do you fix it?

Show solution

The control task is blocked for the whole time the medium task runs, because the logger (which holds the semaphore) cannot run: classic unbounded priority inversion [36]. Replace the binary semaphore with a mutex that implements priority inheritance (FreeRTOS xSemaphoreCreateMutex()) so the logger temporarily inherits the control task's priority [9], or use a priority-ceiling protocol [36]. Also keep the critical section short.

Exercise 7 · Spot the bad watchdog Reliability

A developer kicks the watchdog inside SysTick_Handler() "so it never times out". What is wrong with this design?

Show solution

SysTick keeps firing even when the main loop or a task is deadlocked or stuck in an infinite loop, so the watchdog never resets a hung system: it has been defeated. The kick should happen only after the software proves it is healthy, for instance from a supervisor that checks every task has reported progress [37,38].

Exercise 8 · Power cut during an update OTA

Compare what happens if power fails halfway through writing a new image in (a) a single-slot design that overwrites the running application and (b) an A/B dual-slot design.

Show solution

(a) The application region now holds a partial image; unless a separate recovery bootloader can re-download it, the device is "bricked". (b) Only the inactive slot was being written; the boot flag still points at the old, verified image, which boots normally and can retry the download. After a complete download the bootloader verifies the new image before switching, and trial boot with confirmation allows automatic rollback [20,41,43].

Exercise 9 · MicroPython ISR error MicroPython

This handler raises MemoryError when the button is pressed. Why? def isr(p): events.append(time.ticks_ms())

Show solution

Appending to a list (and creating a new integer object) can allocate heap memory, which is forbidden inside a hard interrupt handler. Either store into a pre-allocated array (for example array.array with an index) or call micropython.schedule() to run the work later in normal context [52].

Exercise 10 · Calling convention Assembly

The word_copy routine in Section 14.7 modifies R0–R3 but never pushes anything onto the stack. Is this legal when called from C? What would change if it needed R4?

Show solution

Yes. Under AAPCS, R0–R3 (and R12) are caller-saved scratch registers, so a callee may overwrite them freely [56]. R4–R11 are callee-saved: if the routine used R4 it would have to push {r4, lr} on entry and pop {r4, pc} on exit, keeping the stack 8-byte aligned at public interfaces [56].

Exercise 11 · Design challenge Integration

Design the firmware architecture for a battery-powered soil-moisture sensor that reports every 15 minutes over a low-power wireless link for 5 years and must accept security patches. Name the OS, sleep strategy, watchdog strategy and update mechanism.

Show solution

One sound answer: Zephyr or Contiki-NG on a Cortex-M MCU with an IEEE 802.15.4 or BLE radio [31,61]. The device spends almost all its time in the deepest sleep mode with an RTC alarm (tickless kernel [29]), wakes to sample and transmit, and returns to sleep. An independent watchdog is kicked by a supervisor only when the measurement-and-transmit cycle completes [37]. Updates use MCUboot with signed images in two slots, test-boot and confirm, anti-rollback counters and a manifest following RFC 9019/9124 [20,41,42]. Size the battery with the Exercise 5 method, including radio retries.

18. Trivia quiz

Quick-fire questions; open each to check your answer.

1. What does the very first 32-bit word of a Cortex-M vector table contain?
The initial value of the Main Stack Pointer; the second word is the reset handler address [3].
2. Why must the addresses in a Cortex-M vector table have bit 0 set?
Bit 0 indicates Thumb state, and Cortex-M processors execute only Thumb instructions; a vector with bit 0 clear causes a fault [3].
3. How many registers does a Cortex-M4 push automatically on exception entry (without floating-point context)?
Eight: R0–R3, R12, LR, PC and xPSR [5].
4. Which exception do RTOSes typically use to perform context switches on Cortex-M, and why?
PendSV, set to the lowest priority so that context switches are deferred until all other interrupts have completed [4].
5. What is the limiting rate-monotonic utilisation bound as the number of tasks grows without limit?
ln 2 ≈ 0.693, i.e. about 69.3 % [35].
6. In which year, and in which journal, did Liu and Layland publish their scheduling paper?
1973, in the Journal of the ACM [35].
7. What programming language was created for TinyOS?
nesC, a component-oriented dialect of C [71].
8. What are Contiki's stackless lightweight threads called?
Protothreads [68].
9. Under what licence is the FreeRTOS kernel distributed?
The MIT licence [58].
10. Which foundation hosts the Zephyr Project, and what licence does Zephyr use?
The Linux Foundation [63]; Apache 2.0 [31].
11. In which mainline Linux release was PREEMPT_RT real-time support merged?
Linux 6.12 (2024) [59].
12. Which RFC defines the IETF SUIT firmware update architecture for IoT devices?
RFC 9019 (2021); the manifest information model is RFC 9124 [41,42].
13. Which MISRA C:2023 rule forbids the dynamic memory functions of <stdlib.h>?
Rule 21.3 [14].
14. How wide is the Cortex-M SysTick counter?
24 bits [5].
15. When did Contiki-NG start, and what was it forked from?
2017, as a fork of the Contiki OS [61].
16. What character must be written to /dev/watchdog before closing it to stop a Linux watchdog that supports "magic close"?
The character V [39].
17. In MicroPython, which function defers work out of a hard interrupt handler?
micropython.schedule() [52].
18. In Rust, which attribute tells the compiler not to link the standard library?
#![no_std]; the program uses the core library instead [47].
19. Which protocol prevents unbounded priority inversion by temporarily raising a lock holder's priority?
The priority inheritance protocol [36].
20. Which Cortex-M register bit makes WFI enter deep sleep instead of ordinary sleep?
SLEEPDEEP in the System Control Register [5].
