1What an IoT cloud platform does

The first article in this series described devices, protocols and architectures. This one moves up the stack, to the services that accept device connections at scale and turn telemetry into stored, searchable, actionable data. Whatever the vendor, an IoT cloud platform has to do six jobs.

1. Identity and provisioning

Give each device a credential (an X.509 certificate, a TPM-backed key or a symmetric key), register it, and assign it to the right endpoint. Azure's Device Provisioning Service exists to do this "zero-touch" [1].

2. Connectivity and messaging

Terminate thousands to millions of long-lived, mutually authenticated connections, usually MQTT [2]. AWS IoT Core accepts MQTT, MQTT over secure WebSockets, HTTPS and LoRaWAN [3].

3. Device state and management

Keep a cloud-side copy of each device's state (AWS shadows, Azure device twins), push configuration, and run remote jobs such as firmware updates [4, 5, 6].

4. Routing and processing

Filter, enrich and route messages to storage, streams and functions, for example with AWS IoT's SQL-like rules or IoT Hub message routing [7, 8].

5. Storage, analytics and visualisation

Persist time series, index events, model assets and show dashboards. This is where Kafka, Redis, Elasticsearch, Prometheus and Grafana come in [9, 10, 11, 12].

6. Operating it all

Package services as containers, schedule them on Kubernetes, and declare the infrastructure as code with Terraform and Ansible [13, 14, 15, 16].

Two design points recur across every platform. First, devices and the cloud talk through a publish/subscribe broker, so producers and consumers never need to know each other's addresses [2]. Second, the cloud keeps a document of desired and reported state per device, so a back-end application can change a setting while the device is offline and the device catches up when it reconnects [4, 5].

3AWS IoT

3.1 AWS IoT Core

AWS IoT Core "provides the cloud services that connect your IoT devices to other devices and AWS cloud services" [3]. Its message broker supports MQTT and MQTT over secure WebSockets for publish/subscribe, HTTPS for publishing, and LoRaWAN through AWS IoT Core for LoRaWAN [3]. Devices that authenticate with an X.509 client certificate connect with MQTT on port 8883, or on port 443 if the client negotiates the ALPN protocol name x-amzn-mqtt-ca, which is useful behind firewalls that only allow HTTPS ports [29].

Three IoT Core features matter most in practice:

  • Rules engine. Rules are written in an SQL-like syntax with SELECT, FROM (an MQTT topic filter), WHERE and optional SET clauses, and each rule triggers one or more actions [7, 30].
  • Device Shadow. The Device Shadow service attaches shadows to thing objects. A shadow document holds desired, reported and delta state [4].
  • Thing registry and policies. Each device is a "thing" with a certificate and a policy that limits which topics it can use.
publish_telemetry.py: AWS IoT Device SDK for Python v2, MQTT 5 client with mutual TLS
# pip install awsiotsdk   (AWS IoT Device SDK for Python v2)
import json, threading, time, random
from awscrt import mqtt5
from awsiot import mqtt5_client_builder

ENDPOINT = "abc123example-ats.iot.eu-west-1.amazonaws.com"  # from: aws iot describe-endpoint
THING = "sensor-01"
TOPIC = f"site/plant1/{THING}/telemetry"
connected = threading.Event()

client = mqtt5_client_builder.mtls_from_path(
    endpoint=ENDPOINT,
    cert_filepath="certs/device.pem.crt",
    pri_key_filepath="certs/private.pem.key",
    ca_filepath="certs/AmazonRootCA1.pem",
    client_id=THING,
    on_lifecycle_connection_success=lambda data: connected.set(),
)
client.start()
if not connected.wait(timeout=15):
    raise SystemExit("could not connect")

for i in range(10):
    body = {"deviceId": THING, "temperature": round(random.uniform(18, 35), 1),
            "ts": int(time.time() * 1000)}
    future = client.publish(mqtt5.PublishPacket(
        topic=TOPIC, payload=json.dumps(body).encode(),
        qos=mqtt5.QoS.AT_LEAST_ONCE))
    future.result(timeout=10)          # wait for PUBACK
    time.sleep(5)
client.stop()

The SDK is AWS's open-source Python client for connecting devices to AWS IoT, built on the AWS Common Runtime [31]. The device must have a certificate registered to a thing, with a policy that allows iot:Connect for its client ID and iot:Publish on its topic.

IoT rule SQL: forward hot readings, adding the site name from the topic
SELECT deviceId, temperature, ts, topic(2) AS site
FROM 'site/+/+/telemetry'
WHERE temperature > 30

topic(2) returns the second level of the topic (here plant1), and the FROM clause takes an ordinary MQTT topic filter with wildcards [7]. Section 9 shows a Lambda function that this rule can invoke, and Section 12 creates the rule with Terraform.

3.2 AWS IoT Device Management

Device Management covers registration, organisation into thing groups, and remote operations at fleet scale [32]. Two features do most of the work:

  • Jobs "define a set of remote operations that can be sent to and run on one or more devices connected to AWS IoT", such as firmware downloads, reboots or certificate rotation [6].
  • Fleet indexing lets you "index, search, and aggregate your devices' data" from the registry, shadows and connectivity status, so you can query, for instance, every disconnected device on firmware 1.2 [33].

3.3 AWS IoT Greengrass V2

Greengrass is "an open source Internet of Things (IoT) edge runtime and cloud service that helps you build, deploy and manage IoT applications on your devices" [21]. Software is packaged as components, which can run as Lambda functions, Docker containers, native OS processes or custom runtimes [21]. Each component is described by a recipe in JSON or YAML; the only RecipeFormatVersion currently defined is 2020-01-25, and each entry in Manifests defines the lifecycle and requirements for a platform [34]. Greengrass Version 1 reached end of support on 7 October 2026, so new projects should use V2 [21].

com.example.TempFilter-1.0.0.yaml: a Greengrass V2 component recipe
RecipeFormatVersion: "2020-01-25"
ComponentName: com.example.TempFilter
ComponentVersion: "1.0.0"
ComponentDescription: Reads a local sensor and publishes readings above a threshold.
ComponentPublisher: Example Corp
ComponentConfiguration:
  DefaultConfiguration:
    threshold: 30
    accessControl:
      aws.greengrass.ipc.mqttproxy:
        com.example.TempFilter:mqttproxy:1:
          policyDescription: Allow publishing filtered readings to IoT Core
          operations:
            - aws.greengrass#PublishToIoTCore
          resources:
            - site/plant1/+/telemetry
Manifests:
  - Platform:
      os: linux
    Lifecycle:
      Install: python3 -m pip install --user awsiotsdk
      Run: python3 -u {artifacts:path}/temp_filter.py --threshold {configuration:/threshold}
    Artifacts:
      - URI: s3://example-gg-artifacts/com.example.TempFilter/1.0.0/temp_filter.py

Recipe variables such as {artifacts:path} and {configuration:/threshold} are resolved by the Greengrass nucleus at deploy time, and the accessControl block grants the component permission to publish through the nucleus's IPC MQTT proxy [34].

3.4 AWS IoT SiteWise

SiteWise is "a managed service with which you can collect, store, organize and monitor data from industrial equipment" [35]. Equipment and processes are represented as asset models (for example, a "Pump" model with measurements such as flow and vibration, and computed metrics such as hourly averages), from which individual assets are instantiated into a hierarchy such as site, line and machine [35]. The bundled dashboard tool, SiteWise Monitor, is in maintenance and closed to new customers; AWS recommends Amazon Managed Grafana with the SiteWise plugin instead, while SiteWise itself remains fully supported [24, 22].

3.5 AWS IoT FleetWise

FleetWise is "a managed service that you can use to collect vehicle data and organize it in the cloud" [36]. Its data model is worth knowing even if you never use the service, because it is a clean design for any high-volume, schema-heavy fleet [37]:

  • a signal catalog contains a collection of signals (such as vehicle speed);
  • a vehicle model is a declarative structure that standardises the format of vehicles and the relationships between signals;
  • a decoder manifest contains the decoding information for each signal, for example how to extract it from a CAN frame;
  • a campaign is defined in the cloud and tells the in-vehicle Edge Agent which data to select, collect and transfer.

Status. AWS IoT FleetWise is no longer open to new customers. Existing customers can continue to use it, but AWS points new projects to the Guidance for Connected Mobility on AWS [36, 23].

4Microsoft Azure IoT

4.1 Azure IoT Hub

IoT Hub "is a managed service that acts as a central message hub in a cloud-based IoT solution" [38]. Devices authenticate with SAS tokens or X.509 certificates [38]. Over MQTT, IoT Hub speaks MQTT v3.1.1 on port 8883, and a device sends telemetry by publishing to the topic name devices/{device-id}/messages/events/ [39]. Unlike a general-purpose broker, IoT Hub fixes the topic structure, so devices cannot publish to arbitrary topics or to each other.

Each device has a device twin: "JSON documents that store device state information including metadata, configurations, and conditions". Back-end apps set desired properties, which the device reads; the device sets reported properties, which back-end apps read and query [5]. Message routing sends device-to-cloud messages to endpoints including Storage containers, Service Bus queues and topics, Event Hubs, Cosmos DB and the built-in endpoint [8].

azure_device.py: telemetry and reported properties with the Azure IoT device SDK for Python
# pip install azure-iot-device
import json, os, time, random
from azure.iot.device import IoTHubDeviceClient, Message

conn_str = os.environ["IOTHUB_DEVICE_CONNECTION_STRING"]
client = IoTHubDeviceClient.create_from_connection_string(conn_str)
client.connect()

def on_desired(patch):                 # desired-property change handler
    print("desired patch:", patch)
    if "setpoint" in patch:
        client.patch_twin_reported_properties({"setpoint": patch["setpoint"]})

client.on_twin_desired_properties_patch_received = on_desired

for _ in range(10):
    msg = Message(json.dumps({"temperature": round(random.uniform(18, 35), 1)}))
    msg.content_type = "application/json"
    msg.content_encoding = "utf-8"     # lets routing queries read the body
    msg.custom_properties["level"] = "telemetry"
    client.send_message(msg)
    time.sleep(5)
client.shutdown()

The azure-iot-device package in this repository connects devices to IoT Hub and to the Device Provisioning Service [40]. Setting the content type and encoding matters if you write routing queries on the message body [8].

4.2 Device Provisioning Service (DPS)

DPS is a "helper service for IoT Hub that enables zero-touch, just-in-time provisioning" [1]. A device is built knowing only the global DPS endpoint, an ID scope and its own credential. At first boot it registers with DPS, which checks the credential against an enrollment (individual, or a group sharing a CA or key), picks a hub with an allocation policy and returns the assignment [1]. The built-in policies are lowest latency, evenly weighted distribution (the default) and static configuration; custom allocation calls a webhook hosted in Azure Functions [1]. DPS supports X.509 and TPM-based attestation [1], plus symmetric keys, where each device in a group gets a derived key computed as an HMAC-SHA256 of its registration ID using the base64-decoded group key [41].

provision.py: derive a per-device key and register with DPS
import base64, hashlib, hmac, os
from azure.iot.device import ProvisioningDeviceClient, IoTHubDeviceClient

def derive_device_key(group_key_b64: str, registration_id: str) -> str:
    """HMAC-SHA256 of the registration ID with the decoded enrollment-group key."""
    key = base64.b64decode(group_key_b64)
    sig = hmac.new(key, registration_id.encode("utf-8"), hashlib.sha256).digest()
    return base64.b64encode(sig).decode()

reg_id = "sensor-01"
device_key = derive_device_key(os.environ["DPS_GROUP_KEY"], reg_id)   # do this at the factory

prov = ProvisioningDeviceClient.create_from_symmetric_key(
    provisioning_host="global.azure-devices-provisioning.net",
    registration_id=reg_id,
    id_scope=os.environ["DPS_ID_SCOPE"],
    symmetric_key=device_key,
)
result = prov.register()
if result.status == "assigned":
    state = result.registration_state
    client = IoTHubDeviceClient.create_from_symmetric_key(
        symmetric_key=device_key, hostname=state.assigned_hub, device_id=state.device_id)
    client.connect()
    print("connected to", state.assigned_hub)

Derive keys on the manufacturing line and never ship the group key on devices: anyone who extracts a group key can mint credentials for every device in the group [41].

4.3 Azure IoT Operations

Azure IoT Operations is "a unified data plane for the edge" that "offers modular and scalable data services on Azure Arc-enabled Kubernetes clusters" [26]. Microsoft announced general availability in November 2024 [25]. Its main parts are an edge-native MQTT broker, Akri connectors (for example an HTTP/REST connector) that bring in data from assets, data flows that transform and contextualise data and route it to cloud endpoints, and an "operations experience" web UI where OT staff manage assets and data flows [26]. Version 1.5.x introduced an Essentials SKU alongside the existing offering, now called Standard [26].

The broker is compatible with MQTT v3.1.1 and v5, is built from a stateless front end and a stateful, sharded back end, and is configured with Kubernetes custom resources such as Broker, BrokerListener, BrokerAuthentication and BrokerAuthorization [42]. This is a clear sign of where industrial IoT is heading: the edge is now a Kubernetes cluster, managed from the cloud through Azure Arc, rather than a single gateway box.

4.4 Azure Digital Twins

Azure Digital Twins is a "platform as a service (PaaS) offering that enables the creation of twin graphs" of whole environments such as buildings, factories or energy networks [43]. Models are written in the JSON-like Digital Twins Definition Language (DTDL); the service supports DTDL versions 2 and 3, with version 3 recommended [43, 44]. Microsoft stresses that these twins are not the same thing as IoT Hub device twins: a device twin mirrors one device's state, while a digital-twin graph models rooms, machines and their relationships, and can be updated from many devices [43].

5ThingsBoard

ThingsBoard is an IoT platform "for device management, data collection, processing, and visualization", available for self-hosting and as a cloud service [45]. It is popular in teaching and in small and medium deployments because one server process gives you device registry, telemetry storage, a rule engine and dashboards.

  • Device connectivity. Over MQTT, a device publishes JSON to v1/devices/me/telemetry and uses its access token as the MQTT username, with no password [46]. Over HTTP it posts to /api/v1/$ACCESS_TOKEN/telemetry [47].
  • Rule engine. A rule chain is a directed graph of rule nodes connected by relations; each node processes one incoming message and produces one or more outgoing messages [48].
  • REST API. Applications authenticate (historically by posting credentials to /api/auth/login and sending the returned JWT in an X-Authorization: Bearer header) and then read telemetry, manage devices and so on. Current documentation marks JWT authentication as deprecated in favour of API keys, available since version 4.3 [49].
  • Licensing. From version 4.4, ThingsBoard merged its Community and Professional editions into one source-available product under the Business Source License 1.1; each release converts to Apache 2.0 four years after release [27]. Check whether your use is covered before deploying a new version commercially.
Shell: send telemetry to ThingsBoard over MQTT and HTTP, then read it back over REST
# Device side: the access token is the MQTT username
mosquitto_pub -d -q 1 -h tb.example.com -p 1883 \
  -t v1/devices/me/telemetry -u "$DEVICE_TOKEN" \
  -m '{"temperature": 25.4, "humidity": 61}'

# Same thing over HTTP
curl -s -X POST "https://tb.example.com/api/v1/$DEVICE_TOKEN/telemetry" \
  -H "Content-Type: application/json" -d '{"temperature": 25.9}'

# Application side: log in (JWT flow; newer versions also offer API keys)
JWT=$(curl -s -X POST https://tb.example.com/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"tenant@example.com","password":"'"$TB_PASSWORD"'"}' | jq -r .token)

curl -s -H "X-Authorization: Bearer $JWT" \
  "https://tb.example.com/api/plugins/telemetry/DEVICE/$DEVICE_ID/values/timeseries?keys=temperature"

6EMQX

EMQX describes itself as "a large-scale distributed MQTT messaging platform", "fully compliant with both MQTT 5.0 and 3.x standards", with native clustering [50]. The vendor states that a single node "stably supports 1.5M MQTT device connections" and that the Enterprise edition supports up to 100 million concurrent connections per cluster [50]; treat these as vendor benchmarks, since real capacity depends on message rates, payload sizes, TLS and rule load. Where AWS IoT Core and IoT Hub are managed services, EMQX is a broker you run yourself (or buy as EMQX Cloud), so you control topic design, authentication back ends and data integrations.

Since version 5.0, EMQX uses HOCON (Human-Optimized Config Object Notation) for configuration; emqx.conf holds critical system settings, and from 5.8.4 a base.hocon file is the recommended config-as-code source [51]. Built-in data integrations stream MQTT messages to external systems; for example, a Kafka sink publishes matching MQTT messages to Kafka topics [52]. From 5.9.0 the project moved from Apache 2.0 to the Business Source License 1.1, and running a cluster of more than one node requires a licence file [28].

emqx.conf (HOCON): static three-node cluster, mutual-TLS listener, packet limits
node {
  name   = "emqx@10.0.0.11"
  cookie = "change-me-long-random-secret"
  data_dir = "/opt/emqx/data"
}

cluster {
  name = iot-prod
  discovery_strategy = static
  static.seeds = ["emqx@10.0.0.11", "emqx@10.0.0.12", "emqx@10.0.0.13"]
}

listeners.ssl.default {
  bind = "0.0.0.0:8883"
  max_connections = 1000000
  ssl_options {
    cacertfile = "/etc/emqx/certs/ca.pem"
    certfile   = "/etc/emqx/certs/server.pem"
    keyfile    = "/etc/emqx/certs/server.key"
    verify     = verify_peer              # require client certificates
    fail_if_no_peer_cert = true
  }
}

mqtt {
  max_packet_size   = 1MB
  max_inflight      = 32
  session_expiry_interval = 2h
}

In Kubernetes, the EMQX operator or a DNS-based discovery strategy usually replaces the static seed list. Section 11 shows Prometheus scraping the broker's metrics.

7Google Cloud and its partner ecosystem

Google Cloud no longer offers a first-party device-connection service. Cloud IoT Core was deprecated with a retirement date of 16 August 2023 [17]. Google's current reference architecture instead has third-party IoT platforms, commercial or open source (Eclipse Hono is one example given), run on Google Cloud and provide MQTT/HTTPS ingestion, device and credential management and rules engines, with Pub/Sub and Dataflow carrying data into back-end services such as BigQuery, Cloud SQL and Cloud Storage [18].

For manufacturing, Google offers the Manufacturing Data Engine (MDE), "an end-to-end solution that delivers scalable and seamless connectivity between the factory floor and the cloud" when combined with Manufacturing Connect [53]. MDE handles acquisition, transformation and storage in Google Cloud, while Manufacturing Connect and its edge gateway (MCe) are built by the partner Litmus Automation exclusively for Google [53]. So on Google Cloud the "IoT platform" is a partner product, and Google provides the data and analytics services behind it.

Migration pattern. A device fleet that used Cloud IoT Core typically moved to (a) a managed broker from another vendor, (b) a self-hosted broker such as EMQX on Google Kubernetes Engine bridging to Pub/Sub, or (c) a partner platform from the Google Cloud ecosystem. All three keep Pub/Sub, Dataflow and BigQuery as the analytics path [18].

8Docker and Kubernetes

Docker is "an open platform for developing, shipping, and running applications". It uses a client-server architecture: the docker client talks to the dockerd daemon over a REST API, and images are stored in registries [13]. Containers give IoT back ends, and increasingly gateways, a reproducible unit of deployment [54]; Greengrass V2 can even run a component as a Docker container [21].

Kubernetes is a "portable, extensible, open source platform for managing containerized workloads and services" [14]. It descends from Google's internal Borg and Omega cluster managers [55]. It joined the CNCF on 10 March 2016 and graduated on 6 March 2018 [56]. A Deployment manages a set of Pods for a workload that usually holds no state [57], which is exactly how a telemetry bridge or API service should be built: any replica can handle any message, and state lives in Kafka, Redis or a database.

Dockerfile: a small MQTT-to-Kafka bridge
FROM python:3.12-slim

# Run as an unprivileged user
RUN useradd --create-home --uid 10001 bridge
WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt   # paho-mqtt, confluent-kafka, prometheus-client

COPY bridge.py .
USER 10001
EXPOSE 9100                                          # Prometheus metrics
ENTRYPOINT ["python", "-u", "bridge.py"]
bridge.py: subscribe with a shared subscription, produce to Kafka keyed by device
import json, os
import paho.mqtt.client as mqtt
from confluent_kafka import Producer
from prometheus_client import Counter, start_http_server

MSGS = Counter("bridge_messages_total", "MQTT messages forwarded to Kafka")
producer = Producer({"bootstrap.servers": os.environ["KAFKA_BOOTSTRAP"],
                     "enable.idempotence": True})

def on_connect(client, userdata, flags, reason_code, properties):
    # MQTT 5 shared subscription: replicas split the load instead of all receiving every message
    client.subscribe("$share/bridge/site/+/+/telemetry", qos=1)

def on_message(client, userdata, msg):
    device = msg.topic.split("/")[2]
    producer.produce("telemetry.raw", key=device, value=msg.payload)
    producer.poll(0)
    MSGS.inc()

start_http_server(9100)
c = mqtt.Client(mqtt.CallbackAPIVersion.VERSION2, protocol=mqtt.MQTTv5)
c.on_connect, c.on_message = on_connect, on_message
c.tls_set(ca_certs="/certs/ca.pem", certfile="/certs/bridge.pem", keyfile="/certs/bridge.key")
c.connect(os.environ["MQTT_HOST"], 8883)
c.loop_forever()

Keying each Kafka record by device ID sends all of a device's readings to the same partition, which preserves their order [9]. Shared subscriptions ($share/<group>/<filter>) are an MQTT 5.0 feature that spreads messages across the members of a group [2].

9AWS Lambda and Azure Functions

AWS Lambda is a "serverless compute service. With Lambda, you can run code without provisioning or managing servers" [58]. Serverless functions suit IoT because traffic is bursty and event-driven: a rule fires only when a message matches, and you pay per invocation rather than for idle servers. The Berkeley view of serverless computing describes this model and its limits, including cold starts, execution-time caps and the need to keep state in external storage [59].

lambda_function.py: invoked by the IoT rule from Section 3.1
import json, os
import boto3

iot_data = boto3.client("iot-data")
LIMIT = float(os.environ.get("TEMP_LIMIT", "30"))

def lambda_handler(event, context):
    # The rule's SELECT output arrives as the event: {"deviceId":..., "temperature":..., "ts":..., "site":...}
    temp = float(event["temperature"])
    if temp <= LIMIT:
        return {"status": "ignored"}
    alert = {"deviceId": event["deviceId"], "site": event.get("site"),
             "temperature": temp, "ts": event.get("ts"), "severity": "high"}
    iot_data.publish(topic=f"alerts/{event['site']}/temperature", qos=1,
                     payload=json.dumps(alert))
    return {"status": "alerted"}

On Azure, an Azure Function can be triggered by IoT Hub messages. IoT Hub support "is based on the Azure Event Hubs Binding", so the function binds to the hub's Event Hubs-compatible endpoint; the IoT Hub trigger does not support identity-based connections, so it uses a connection string setting [60].

function_app.py: Azure Functions (Python v2 model) processing IoT Hub telemetry
import json, logging
import azure.functions as func

app = func.FunctionApp()

# "IoTHubEventHubConnection" is an app setting holding the hub's Event Hubs-compatible connection string
@app.event_hub_message_trigger(arg_name="event", event_hub_name="my-iot-hub",
                               connection="IoTHubEventHubConnection",
                               consumer_group="functions")
def telemetry(event: func.EventHubEvent):
    body = json.loads(event.get_body().decode("utf-8"))
    device = event.iothub_metadata.get("connection-device-id")
    if body.get("temperature", 0) > 30:
        logging.warning("High temperature %s from %s", body["temperature"], device)

Use a dedicated consumer group for each reader of the endpoint, so that the function and, say, a stream-analytics job do not compete for the same events [60].

10Kafka, Redis and Elasticsearch

10.1 Apache Kafka

Kafka is "an event streaming platform" [9]. Events are durably stored in topics, topics are split into partitions spread across brokers, events with the same key land in the same partition, retention is configurable per topic, and Kafka Connect imports and exports data continuously [9]. It was built at LinkedIn for high-volume log processing [61]. In IoT, Kafka sits between ingest and everything else: brokers such as EMQX write into it [52], and storage, analytics and alerting consumers read from it independently, each at its own pace. Because data is retained, a new consumer, for example a retrained anomaly detector, can replay last week's telemetry.

10.2 Redis

Redis is an in-memory data store often used for the "hot" layer of an IoT system: the last known value per device, rate limits, session state and short-lived queues. Redis Streams act "like an append-only log", with XADD appending entries [62], and the Redis time-series data type stores real-valued samples with commands such as TS.ADD [10].

redis-cli: latest value, a stream of events, and a time series
HSET device:sensor-01 temperature 25.4 ts 1763200000000 fw 1.4.2
XADD events:plant1 * device sensor-01 type door_open
TS.CREATE temp:sensor-01 RETENTION 604800000 LABELS site plant1 kind temperature
TS.ADD temp:sensor-01 * 25.4
TS.RANGE temp:sensor-01 - + AGGREGATION avg 60000

10.3 Elasticsearch

Elastic provides "an open source search, analytics, and AI platform" built around Elasticsearch [63]. For IoT the most relevant feature is the data stream, a layer over a set of indices "optimized for storing append-only time series data" such as device logs and events [11]. Elasticsearch is strongest where you need full-text search and ad-hoc filtering across events (for example "all error logs mentioning watchdog from firmware 1.4 in the last day"), and Grafana can query it directly [64].

11Prometheus and Grafana

Prometheus is an "open-source systems monitoring and alerting toolkit originally built at SoundCloud". It collects time series "via a pull model over HTTP", and it joined the CNCF in 2016 as the second hosted project after Kubernetes [65]. It graduated on 9 August 2018 [66]. In IoT, Prometheus monitors the platform (brokers, bridges, consumers, Kubernetes) rather than device telemetry itself, which belongs in a time-series database designed for millions of high-cardinality series. Scrape targets are listed under scrape_configs [67].

Grafana "enables you to query, visualize, alert on, and explore your metrics, logs, and traces" [12]. It ships with core data sources including Prometheus and Elasticsearch [64], which makes it a common single pane for both platform health and device data. On AWS, Amazon Managed Grafana with the SiteWise plugin is now the recommended replacement for SiteWise Monitor dashboards [24].

12Terraform and Ansible

Terraform is "an infrastructure as code tool that lets you build, change, and version cloud and on-prem resources" in human-readable configuration files [15]. For IoT it is the natural way to create things, policies, topic rules and the functions they call, so that every environment (dev, test, prod) is identical and reviewable. The AWS provider includes an aws_iot_topic_rule resource [68].

main.tf: an IoT thing, a least-privilege policy and the topic rule from Section 3.1
terraform {
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 6.0" }
  }
}

provider "aws" { region = "eu-west-1" }

data "aws_caller_identity" "me" {}
locals {
  arn_prefix = "arn:aws:iot:eu-west-1:${data.aws_caller_identity.me.account_id}"
}

resource "aws_iot_thing" "sensor" {
  name = "sensor-01"
}

resource "aws_iot_policy" "sensor" {
  name = "sensor-publish-own-topic"
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      { Effect = "Allow", Action = "iot:Connect",
        Resource = "${local.arn_prefix}:client/$${iot:Connection.Thing.ThingName}" },
      { Effect = "Allow", Action = "iot:Publish",
        Resource = "${local.arn_prefix}:topic/site/*/$${iot:Connection.Thing.ThingName}/telemetry" }
    ]
  })
}

resource "aws_iot_topic_rule" "hot" {
  name        = "hot_readings"
  enabled     = true
  sql         = "SELECT deviceId, temperature, ts, topic(2) AS site FROM 'site/+/+/telemetry' WHERE temperature > 30"
  sql_version = "2016-03-23"

  lambda {
    function_arn = aws_lambda_function.alert.arn   # defined elsewhere in the module
  }
}

resource "aws_lambda_permission" "iot_invoke" {
  statement_id  = "AllowIoTInvoke"
  action        = "lambda:InvokeFunction"
  function_name = aws_lambda_function.alert.function_name
  principal     = "iot.amazonaws.com"
  source_arn    = aws_iot_topic_rule.hot.arn
}

The $${...} escape stops Terraform from interpolating the AWS IoT policy variable iot:Connection.Thing.ThingName, so AWS substitutes the connected thing's name at connect time and each device can publish only to its own topic.

Ansible uses an "agent-less architecture", connecting with "SSH with existing OS credentials to access remote machines" [16], and playbooks are written in YAML [69]. That makes it a good fit for Linux edge gateways, which rarely run a configuration agent but almost always run SSH. A common split is Terraform for cloud resources and Ansible for the fleet of gateways.

15Exercises with solutions

Exercise 1. Write an AWS IoT rule that selects only readings with humidity above 80 from any device on any site, publishing to topics of the form site/<site>/<device>/telemetry, and adds the device name from the topic as a field called device.

Solution
SELECT humidity, ts, topic(3) AS device
FROM 'site/+/+/telemetry'
WHERE humidity > 80

The FROM clause takes an MQTT topic filter, the single-level wildcard + matches one level, and topic(3) returns the third topic level [7].

Exercise 2. A shadow has desired state {"fan":"on","setpoint":21,"mode":"eco"} and reported state {"fan":"off","setpoint":21}. What is the delta, and what should the device do with it?

Solution

The delta holds the desired fields that differ from reported: {"fan":"on","mode":"eco"}. setpoint matches and is left out. The device applies both changes and then updates its reported state, after which the delta is empty [4].

Exercise 3. A company ships 50 000 sensors provisioned through an Azure DPS symmetric-key enrollment group. Explain why the group key must not be flashed onto the sensors, and what is flashed instead.

Solution

Each device gets a derived key, the HMAC-SHA256 of its own registration ID computed with the group key [41]. If the group key were on a device, anyone who extracted it could derive valid keys for any registration ID in the group and impersonate every sensor. With derived keys, compromising one device exposes only that device's key.

Exercise 4. Your devices are spread across Europe, North America and Asia, with one IoT Hub per region. Which DPS allocation policy fits best, and which policy would you choose to always place a device in a hub you name?

Solution

Lowest latency, which assigns the device to the hub with the lowest latency to it. To force a particular hub, use static configuration. Evenly weighted distribution is the default, and custom allocation calls an Azure Functions webhook [1].

Exercise 5. Write the mosquitto_pub command that sends {"battery": 3.7} as telemetry to a ThingsBoard server at tb.local for a device whose access token is A1B2C3.

Solution
mosquitto_pub -h tb.local -p 1883 -q 1 -t v1/devices/me/telemetry -u A1B2C3 -m '{"battery": 3.7}'

The access token is the MQTT username, with no password, and telemetry goes to v1/devices/me/telemetry [46].

Exercise 6. You expect 2.4 million concurrent MQTT connections. Using the vendor's single-node figure for EMQX, estimate a minimum cluster size that survives the loss of one node, and name the licensing point you must check.

Solution

At the vendor's 1.5 million connections per node [50], two nodes are the bare minimum for 2.4 million, so N+1 redundancy gives three. In practice you would load-test with your own message rates and TLS settings, since the vendor number is a benchmark. From EMQX 5.9.0, under BSL 1.1, a cluster of more than one node requires a licence file [28].

Exercise 7. The MQTT-to-Kafka bridge in Section 8 keys records by device ID. What does this guarantee, and what would break if it used a random key?

Solution

Events with the same key go to the same partition, and consumers read a partition in the order it was written [9]. So each device's readings stay in order. With random keys, one device's readings would be spread across partitions and could be processed out of order, which breaks logic such as "temperature rose for five consecutive readings".

Exercise 8. In 2026 a team finds a design document that routes alarms through AWS IoT Events and stores data in AWS IoT Analytics. What do they need to know?

Solution

Both services have reached end of support: IoT Analytics on 15 December 2025 and IoT Events on 20 May 2026 [19, 20]. The design must be rebuilt on supported services. AWS gives feature-by-feature alternatives for IoT Analytics, and illustrative guidance for IoT Events using Kinesis Data Streams and CloudWatch [19, 20].

Exercise 9. Write a PromQL alert expression that fires when an EMQX scrape target is down, and explain why Prometheus would notice even if the broker process crashed completely.

Solution

up{job="emqx"} == 0. Prometheus collects metrics with a pull model over HTTP [65], so a crashed target simply fails its scrape and Prometheus records up as 0. In a push model, a dead process just goes quiet, and silence is harder to tell apart from "no traffic".

Exercise 10. You manage 40 Linux gateways and an AWS account. Assign each task to Terraform or Ansible: (a) create IoT topic rules; (b) install Docker on the gateways; (c) create the Lambda function; (d) rotate the broker config file on every gateway.

Solution

Terraform for (a) and (c): it builds and versions cloud resources [15, 68]. Ansible for (b) and (d): it is agentless and reaches machines over SSH using YAML playbooks [16, 69].

Exercise 11. Why should the bridge in Section 8 run as a Kubernetes Deployment with several replicas, and what MQTT feature stops each replica from receiving a copy of every message?

Solution

A Deployment manages a set of interchangeable Pods for a workload that holds no state [57], so replicas can be added for throughput and resilience. An MQTT 5.0 shared subscription ($share/bridge/...) spreads messages across the subscribers in the group instead of sending each one to all of them [2].

Exercise 12. A startup's device fleet ran on Google Cloud IoT Core. Sketch two migration options that keep BigQuery as the analytics store.

Solution

(1) Adopt a partner IoT platform running on Google Cloud, which handles MQTT/HTTPS ingestion and device management and hands data to Pub/Sub and Dataflow, then BigQuery [18]. (2) Run a broker such as EMQX on Kubernetes and bridge messages into Pub/Sub, with Dataflow writing to BigQuery. Either way, Cloud IoT Core itself is gone after its 16 August 2023 retirement date [17].
