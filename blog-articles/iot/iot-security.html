IoT Security: Devices, Networks, Identity and Standards

How to secure an Internet of Things system end to end: hardware roots of trust and signed firmware on the device, encrypted and segmented networks, cryptographic identity and fine-grained access control, the threats that keep recurring, and the standards that tie it together.

Includes 11 diagrams, 16 code listings, 8 exercises and 18 trivia questions with solutions. All code is defensive. References follow the Vancouver style; numbers in square brackets link to the list at the end.

1. Introduction: why IoT security is different

The Internet of Things (IoT) connects sensors, actuators and embedded controllers to networks and cloud services. NIST defines an IoT device as one with at least one transducer (sensor or actuator) for interacting with the physical world and at least one network interface [1]. That physical coupling is what makes IoT security different from ordinary IT security: a compromised thermostat, insulin pump, or programmable logic controller can cause physical harm, not just data loss [2].

IoT devices also bring constraints that ordinary IT security assumes away. Many run on microcontrollers with kilobytes of RAM, have no user interface, operate for 10 to 20 years in the field, and are deployed in places where an attacker can physically touch them [3]. The IETF's survey of IoT security notes that the device lifecycle (manufacture, bootstrapping, operation, maintenance, decommissioning) creates distinct security problems at each stage [3].

Learning objectives. After working through this article you should be able to:
  1. Explain how a hardware root of trust, secure boot and code signing combine to establish firmware integrity.
  2. Configure mutual TLS between a device and a broker and build a small device PKI with OpenSSL.
  3. Design a segmented IoT network with explicit firewall rules and intrusion detection.
  4. Choose between RBAC and ABAC for a given IoT authorization problem and express the policy in code.
  5. Recognise the most common IoT vulnerabilities and map defences to NISTIR 8259, the NIST CSF 2.0, ETSI EN 303 645, ISO/IEC 27400, IEC 62443 and the OWASP IoT Top 10.

2. Device security

2.1 Hardware root of trust

A root of trust (RoT) is a component that must behave as expected because its misbehaviour cannot be detected; everything else in the platform's security is built on it. NIST SP 800-193 divides platform firmware resiliency into three roots of trust: the root of trust for update (RTU), the root of trust for detection (RTD) and the root of trust for recovery (RTRec), and asks that each be protected against modification, typically by immutable code in ROM or by hardware-enforced write protection [5].

Hardware roots of trust in IoT appear in several forms:

  • Immutable boot ROM containing the first-stage verifier and a hash of the manufacturer's public key fused into one-time-programmable (OTP) memory.
  • Secure elements and discrete TPMs, which store keys in tamper-resistant silicon and perform cryptography internally so the private key never leaves the chip [6].
  • DICE (Device Identifier Composition Engine), a TCG architecture for low-cost microcontrollers. At reset, hardware combines a Unique Device Secret (UDS) with a measurement of the first mutable code to derive a Compound Device Identifier (CDI). If the firmware changes, the CDI and all keys derived from it change too, so the identity is bound to the software that is running [7].

2.2 Secure boot and measured boot

Secure boot means each boot stage cryptographically verifies the next stage before handing over control, and refuses to run code whose signature does not check out. Measured boot instead records a hash of each stage into tamper-evident storage (such as TPM Platform Configuration Registers) so that a remote verifier can later decide whether the device booted known-good code [6,8]. The two are complementary: secure boot enforces locally, measured boot reports remotely.

A TPM PCR cannot be written directly, only extended: the new value is the hash of the old value concatenated with the new measurement [6]. 2.4 Hardware security modules (HSM)

Where a TPM protects one device, a hardware security module protects the keys that protect all devices: the firmware-signing key, the device-issuing CA key, and keys used in manufacturing. HSMs are validated against FIPS 140-3, which defines four increasing security levels. Physical security requirements grow from production-grade components at Level 1, to tamper evidence at Level 2, to tamper detection and response (zeroising keys when the enclosure is opened) at Level 3, to a complete protective envelope against environmental attacks at Level 4 [13]. NIST key-management guidance recommends that keys be generated and stored in such validated modules, and that signing keys have a defined cryptoperiod [14].

Design rule. If an attacker steals the firmware-signing private key, secure boot on every device in the fleet is defeated at once. Keep that key in an HSM, require multi-person authorisation (M-of-N) to use it, and never let it sit in a CI runner's file system.

2.5 Secure firmware, code signing and firmware integrity

Secure firmware starts with a secure development process. NIST's Secure Software Development Framework (SSDF) groups practices into preparing the organisation, protecting the software, producing well-secured software, and responding to vulnerabilities [15]; IEC 62443-4-1 sets equivalent lifecycle requirements for industrial products [16]. Practical measures include memory-safe languages where possible, compiler hardening flags, fuzzing of parsers, removal of debug code from release builds, and a software bill of materials (SBOM) so that known-vulnerable components can be found later [17].

Code signing attaches a digital signature over a hash of the firmware image, made with a private key held by the manufacturer. The device verifies it with a public key it already trusts. Approved signature algorithms are specified in FIPS 186-5 (ECDSA, EdDSA including Ed25519, and RSA) [18]; the post-quantum ML-DSA algorithm was standardised in FIPS 204 in 2024 and is worth considering for devices with long field lifetimes [19].

Firmware integrity means a device detects and rejects firmware that has been modified, whether at rest in flash, in transit during an update, or by rollback to an older, vulnerable version. The IETF SUIT architecture specifies that update manifests must be authenticated, must carry a monotonically increasing sequence number to prevent rollback, and should be bound to the device class they are intended for [20].

Example: signing an image with MCUboot's imgtool. MCUboot is an open-source secure bootloader for 32-bit microcontrollers; its imgtool utility generates keys and signs images, and the bootloader verifies them before booting [9].

2.6 Debug interface protection

Production boards often still expose JTAG (IEEE 1149.1) [22], Arm SWD, or a UART console. Through these an attacker can halt the CPU, dump flash and RAM, or get a root shell. The OWASP IoT Top 10 lists Lack of physical hardening (I10) partly for this reason [4], and IEC 62443-4-2 requires embedded devices to protect physical diagnostic and test interfaces [23].

Defensive measures, roughly from weakest to strongest:

  1. Remove headers and test-point labels (raises effort only slightly).
  2. Disable the UART console and login prompt in release firmware.
  3. Set the MCU's debug-lock or readout-protection fuses at end of line, so the debug port is permanently disabled or wipes flash on reconnection.
  4. Use authenticated debug: the port reopens only after a challenge-response with a per-device key held by the manufacturer, so field returns can still be analysed.

2.7 Physical tamper resistance

Physical attacks range from simple (opening the case, reading an external flash chip) to sophisticated. Side-channel analysis recovers keys from power consumption or electromagnetic emissions; Kocher, Jaffe and Jun showed in 1999 that differential power analysis can extract keys from a smart card using statistics over many traces [24]. Fault injection (voltage or clock glitching) tries to skip instructions such as the signature check in a bootloader.

Tamper resistance is layered: tamper-evident seals and enclosures; tamper-detecting switches and meshes; tamper-responding circuits that zeroise keys; and side-channel-hardened cryptographic implementations inside a secure element. These map to the FIPS 140-3 physical security levels described above [13]. ETSI EN 303 645 additionally requires that critical security parameters stored on a device be protected and that hard-coded unique-per-device credentials be resistant to physical and software tampering [25].

3. Network security

3.1 TLS and DTLS

Transport Layer Security (TLS) provides confidentiality, integrity and server (optionally client) authentication over a reliable stream such as TCP. TLS 1.3 removed static RSA and static Diffie-Hellman key exchange, so every full handshake has forward secrecy, and it encrypts more of the handshake than earlier versions [26]. Its 0-RTT "early data" mode is not protected against replay, and the specification warns applications to use it only for idempotent requests [26].

Many IoT protocols, including CoAP, run over UDP, which can lose and reorder packets. DTLS adapts TLS to datagrams with explicit sequence numbers, retransmission timers and a cookie exchange that blunts denial-of-service amplification. DTLS 1.3 (RFC 9147) is the datagram counterpart to TLS 1.3 [27]. RFC 7925 profiles TLS and DTLS for constrained devices; for example it specifies TLS_PSK_WITH_AES_128_CCM_8 for pre-shared keys and TLS_ECDHE_ECDSA_WITH_AES_128_CCM_8 for certificate-based authentication [28]. NIST SP 800-52 Rev. 2 requires US federal servers to support TLS 1.2 and to support TLS 1.3 by 1 January 2024 [29].

3.2 Mutual TLS

In ordinary TLS only the server presents a certificate. In mutual TLS (mTLS) the server sends a CertificateRequest and the client must reply with its own certificate and a CertificateVerify signature that proves possession of the matching private key [26]. For IoT this is the standard way to authenticate a device to a broker or API without passwords. Tokens can then be bound to the device certificate so a stolen token is useless without the key [33].

3.3 Network segmentation

Segmentation limits how far an attacker can move after compromising one device. NIST SP 800-82 Rev. 3 recommends separating operational-technology networks from corporate IT and using defence-in-depth architectures with demilitarised zones (DMZs) between them [2]. IEC 62443 formalises this as zones (groups of assets with common security requirements) connected by conduits (controlled communication paths), each zone assigned a target security level [35]. In a home or office, the simplest equivalent is a separate VLAN or SSID for IoT devices with no route to laptops and servers.

The IETF's Manufacturer Usage Description (MUD) lets a device announce a URL pointing to a manufacturer-signed file that describes the network access it needs; the network can then generate access rules automatically [36].

NIST's firewall guidance recommends a default-deny policy in which only explicitly required traffic is permitted, and that rules be based on documented business needs and reviewed regularly [37]. 3.5 VPNs

A virtual private network protects traffic across untrusted networks, for example between a remote site's gateway and the vendor cloud, or for a technician's remote maintenance session. NIST SP 800-77 Rev. 1 covers IPsec VPNs and recommends IKEv2 with strong, modern algorithms [39]. WireGuard is a newer design with a small code base and a fixed modern cipher suite (Curve25519, ChaCha20-Poly1305, BLAKE2s) [40]. A VPN protects the path, not the endpoint: it does not replace device authentication, and a VPN that drops every device onto one flat network can make lateral movement easier rather than harder.

3.6 Secure communication protocols

Beyond the transport, the choice of protocol and its configuration matter:

  • MQTT 5.0 supports username/password and enhanced (challenge-response) authentication, but leaves confidentiality to TLS; the specification notes that MQTT over TLS uses port 8883 [30].
  • CoAP defines security modes NoSec, PreSharedKey, RawPublicKey and Certificate; NoSec should never be used outside a separately protected network [31].
  • Radio protocols (BLE, Zigbee, Thread, LoRaWAN) each have their own link-layer security, but link-layer keys are often network-wide. Ronen and colleagues showed that a firmware-update key shared across a whole product line of Zigbee smart bulbs could be extracted by side-channel analysis and used to spread a worm between bulbs [41]. End-to-end security above the link layer is therefore advisable.

3.7 Intrusion detection

An intrusion detection system (IDS) monitors traffic or host activity for signs of attack; an intrusion prevention system (IPS) can also block it. NIST SP 800-94 distinguishes signature-based, anomaly-based and stateful protocol analysis methods, and network-based, wireless, network behaviour analysis and host-based deployments [42]. IoT traffic is usually highly regular (the same device talks to the same few endpoints on a schedule), which makes behavioural baselining unusually effective.

3.8 Zero-trust architecture

Zero trust abandons the idea that anything inside the network perimeter is trustworthy. NIST SP 800-207 states seven tenets, including that all communication is secured regardless of network location, that access to resources is granted per session, and that access is determined by dynamic policy including the observable state of the client and its identity [45]. It describes a logical model in which a policy decision point (policy engine plus policy administrator) instructs a policy enforcement point to allow or deny each session [45].

For IoT, zero trust usually means strong device identity (certificates bound to hardware), device posture checks (is the firmware current? does remote attestation pass? [8]), fine-grained authorisation per topic or API, and micro-segmentation so that each device class can reach only its own services.

4. Identity and access management

4.1 Device identity

Device identification is the first capability in the NISTIR 8259A core baseline: a device should be uniquely identifiable both logically and physically [46]. A serial number or MAC address identifies a device but cannot authenticate it, because anyone can copy it. A cryptographic identity is a key pair whose private key never leaves the device, plus a certificate that binds the public key to the device identifier.

IEEE 802.1AR defines a Secure Device Identifier: an IDevID installed by the manufacturer for the device's lifetime, and one or more LDevIDs issued locally by the operator [47]. BRSKI (RFC 8995) uses the IDevID to let a new device and a network authenticate each other automatically at first power-on, after which the device enrols for an operational certificate [48], for example using Enrollment over Secure Transport (EST, RFC 7030) [49].

4.2 Public Key Infrastructure (PKI)

A PKI is the set of policies, roles, systems and procedures used to issue, manage and revoke certificates. Internet PKI certificates follow the X.509 profile of RFC 5280, which defines certificate fields, extensions such as basicConstraints and keyUsage, and the path validation algorithm [50]. A typical IoT PKI is a three-tier hierarchy: an offline root CA, one or more online issuing CAs (often one per product line or factory), and end-entity device certificates.

4.3 Certificate management

Certificates have to be issued, renewed, and revoked across their whole life, at fleet scale. Key protocols:

  • Enrolment: EST over HTTPS [49], ACME (designed for web servers but increasingly used for devices) [52], or BRSKI for zero-touch onboarding [48].
  • Revocation status: Certificate Revocation Lists defined in RFC 5280 [50] or the Online Certificate Status Protocol (OCSP) [53]. Constrained devices often cannot fetch either, which is one reason short-lived certificates are attractive: a 90-day certificate that is not renewed simply expires.
  • Inventory and monitoring: track every certificate's issuer, expiry and owning device; alert well before expiry. Unplanned expiry of a fleet's broker certificate is an availability incident.

4.4 Authentication

Authentication verifies a claimed identity. In IoT there are three directions to get right: device to service, service to device (so a device does not accept commands from an impostor), and user to device or app. NIST SP 800-63B-4 sets requirements for user authenticators, including minimum password length and screening passwords against lists of commonly used or compromised values [54]. For devices, certificate- or key-based authentication backed by hardware is preferred over shared secrets, and ETSI EN 303 645 requires that where passwords are used they be unique per device or set by the user, never a universal default [25].

For constrained devices that cannot run a full OAuth stack, the IETF ACE framework adapts OAuth 2.0 to CoAP and CBOR-based tokens [55].

4.5 Authorization

Authorization decides what an authenticated entity may do. The principle of least privilege applies directly: a temperature sensor should be allowed to publish to its own telemetry topic and nothing else. The NISTIR 8259A baseline includes logical access to interfaces, meaning the device can restrict access to its local and network interfaces and the protocols and services they expose [46].

4.6 Role-based access control (RBAC)

In RBAC, permissions are assigned to roles, and subjects acquire permissions by being assigned roles. Sandhu and colleagues' RBAC96 model family defines RBAC0 (users, roles, permissions, sessions), RBAC1 (adds role hierarchies), RBAC2 (adds constraints such as separation of duty) and RBAC3 (both) [56]. RBAC suits the human side of IoT well: operators, installers, auditors and administrators.

4.7 Attribute-based access control (ABAC)

ABAC evaluates rules over attributes of the subject, object, action and environment [57]. It handles conditions that roles cannot express cleanly, such as "a device may write only to topics of its own site, only while its firmware is not on the known-vulnerable list, and only during its maintenance window". NIST SP 800-162 describes the policy decision and enforcement points, attribute sources, and the governance needed to keep attributes trustworthy [57].

4.8 Credential rotation

Every credential has a cryptoperiod, the time span during which it is authorised for use. NIST SP 800-57 explains that limiting cryptoperiods limits the amount of data exposed if a key is compromised and the time available for attacks against it [14]. In IoT fleets rotation must be automatic, tolerant of devices that are offline for weeks, and must never brick a device: keep the old credential valid until the new one is confirmed working.

The EST protocol's /simplereenroll operation exists for exactly this case: the client authenticates with its current certificate to obtain a new one [49]. The not_valid_after_utc property is documented in the cryptography library [21].

4.9 Secrets management

Secrets include private keys, API tokens, Wi-Fi passphrases, and symmetric keys. Rules of thumb drawn from NIST key-management guidance [14] and ETSI EN 303 645 [25]:

  • Never hard-code secrets in firmware images or source repositories. A secret in a firmware image is shared by every unit and can be extracted from any one of them.
  • Generate on the device when possible, using a hardware random number generator; entropy sources should meet guidance such as NIST SP 800-90B [59].
  • Store in hardware (TPM, secure element, or a TrustZone-protected key store) so keys are non-exportable.
  • Centralise back-end secrets in a secrets manager or HSM-backed service with audit logging. HashiCorp Vault's PKI secrets engine, for instance, can issue short-lived certificates on demand [60].
  • Scope and expire every secret, and have a tested plan for revoking it.

5. Common vulnerabilities and threats

This section explains each threat at the level a defender needs: what goes wrong, a documented real-world example where one exists, and the controls that stop it. It deliberately contains no attack tooling.

5.1 Default credentials and weak authentication

"Weak, guessable, or hardcoded passwords" is item I1 in the OWASP IoT Top 10 [4]. The Mirai botnet of 2016 spread almost entirely by logging into devices over Telnet with factory-default usernames and passwords; Kolias and colleagues report that its scanner used a dictionary of 62 credential pairs [61]. Weak authentication also covers missing rate-limiting, unauthenticated local APIs, and authentication checked only in the mobile app rather than on the device or server.

Defences. Provision a unique credential per device or force the user to set one on first use (ETSI EN 303 645 provision 5.1 [25]); prefer certificate-based device authentication; rate-limit and lock out repeated failures; and close Telnet entirely. CISA's Secure by Design guidance urges manufacturers to eliminate default passwords altogether [62]. Regulators have moved too: the UK's product security regulations, in force since 29 April 2024, prohibit universal default passwords on consumer connectable products [63].

5.2 Insecure firmware

Firmware frequently ships with outdated third-party components (OWASP I5, "Use of insecure or outdated components" [4]), debug features, or memory-safety bugs. The 2020 "Ripple20" disclosures, a set of 19 vulnerabilities in the widely embedded Treck TCP/IP library, illustrate the supply-chain dimension: CISA's advisory notes that the library is used across many vendors' products, so a single flaw reaches far beyond the original vendor [64]. Defences: SSDF practices [15], an SBOM for every release [17], secure boot (Section 2.2) and a working update channel (Section 5.6).

5.3 Unencrypted communications

OWASP I7 is "Insecure data transfer and storage" [4]. Cleartext MQTT on port 1883, HTTP device APIs, and CoAP in NoSec mode [31] expose credentials and data to anyone on the path. Defences: TLS 1.3 or DTLS 1.3 everywhere [26,27], IDS alerts on cleartext protocols (Section 3.7), and encryption of sensitive data at rest. ETSI EN 303 645 requires security-relevant communications to be encrypted, and the NISTIR 8259A baseline includes data protection as a core device capability [25,46].

5.4 Exposed APIs

OWASP I2 ("Insecure network services") and I3 ("Insecure ecosystem interfaces", covering web, back-end API, cloud and mobile interfaces) [4] together account for many large IoT breaches: a device that exposes an unauthenticated management port to the Internet, or a cloud API that returns any device's data when the device ID in the URL is changed (broken object-level authorisation). Defences: do not expose device services to the Internet (Section 3.4); authenticate every API call and authorise it against the specific object (Section 4.7); inventory and minimise open ports; and test ecosystem interfaces, for example against the OWASP IoT Security Verification Standard [65].

5.5 Insecure OTA updates

OWASP I4 is "Lack of secure update mechanism" [4]. Failure modes include unsigned images, signatures checked only by the app rather than the device, update keys shared across products, downloads over HTTP, and no rollback protection. Ronen and colleagues' research on Zigbee smart lights is the canonical example: by recovering the key used to protect firmware updates through power analysis, they could produce firmware the bulbs would accept, and showed how it could spread from bulb to bulb [41].

5.6 Hardware tampering

With physical access, attackers read external flash chips, attach to debug ports, probe buses, or perform side-channel and fault-injection attacks (Sections 2.6 and 2.7) [24]. OWASP I10 is "Lack of physical hardening" [4]. The design goal is that compromising one unit on a workbench must not compromise the fleet, which is why per-device keys matter more than any enclosure.

5.7 Botnets and DDoS attacks

A botnet is a network of compromised devices controlled by an attacker. Antonakakis and colleagues' measurement study of Mirai found it peaked at about 600,000 infected devices, mostly cameras, DVRs and routers, and traced attacks including those on the security journalist Brian Krebs's website and on the DNS provider Dyn in October 2016 [66]. CISA warned at the time that Mirai's public source-code release lowered the bar for further IoT botnets [67].

A distributed denial-of-service (DDoS) attack overwhelms a target with traffic from many sources. IoT devices make good DDoS sources because they are numerous, always on, rarely monitored and often have unmetered bandwidth. Defenders of IoT networks contribute by preventing infection and by egress filtering, so that compromised devices cannot send arbitrary traffic to the Internet (Section 3.4).

5.8 Supply-chain attacks

Supply-chain attacks compromise a product before it reaches the customer: a malicious or vulnerable third-party library, a compromised build server or signing key, counterfeit components, or malicious modification during manufacturing or distribution. NIST SP 800-161 Rev. 1 provides a framework for cybersecurity supply chain risk management (C-SCRM) [68]. Technical controls include SBOMs [17], signed and verifiable build provenance (Sigstore is one open framework for signing and transparency logs [69]), hardware-backed identity injected in a controlled factory step (Section 4.1), and acceptance testing of incoming devices.

5.9 Device spoofing

Spoofing means impersonating a legitimate device, for example by copying its MAC address, serial number or a shared API key, in order to inject false data or receive commands. If identity is merely an identifier, spoofing is trivial. Defences: cryptographic identity with non-exportable private keys (Sections 2.3, 4.1), mTLS (Section 3.2), and remote attestation so the service knows both which device it is talking to and what software it is running [8].

5.10 Replay attacks

In a replay attack, an adversary records a valid message (such as "unlock door") and sends it again later. Encryption alone does not stop this, because the replayed message is still validly encrypted. Defences are freshness mechanisms: nonces in challenge-response exchanges, monotonic sequence numbers with a sliding acceptance window, and timestamps with bounded clock skew. IPsec ESP is a classic example; RFC 4303 requires receivers to support an anti-replay window of at least 32 packets and recommends 64 as the default [70]. TLS and DTLS record layers include sequence numbers for the same reason [26,27].

The sequence number must be covered by the message authentication code, otherwise an attacker simply changes it. The counter must also survive reboots (store it in non-volatile memory) or be re-keyed after reset.

5.11 Man-in-the-middle attacks

In a man-in-the-middle (MITM) attack the adversary sits between two parties, relaying and possibly altering traffic while each believes it is talking directly to the other. On IoT networks this is often done with rogue Wi-Fi access points, ARP or DNS spoofing, or by exploiting a device that skips certificate verification. The defence is authenticated key exchange: TLS 1.3 authenticates the server through its certificate and CertificateVerify signature, so a MITM without the server's private key cannot complete the handshake [26], provided the client actually validates the certificate chain and name per RFC 5280 [50]. Certificate or public-key pinning to a private CA further narrows which certificates a device will accept. Wireshark is useful for confirming in a lab that no cleartext leaves a device [72].

6. Security standards and frameworks

6.1 NISTIR 8259 series

The NISTIR 8259 series is NIST's core guidance for IoT device manufacturers.

  • NISTIR 8259 describes six recommended activities: four before a device is sold (identify expected customers and use cases; research customers' cybersecurity needs and goals; determine how to address them; plan for adequate support) and two after (define approaches for communicating to customers; decide what to communicate and how) [1].
  • NISTIR 8259A defines the technical core baseline of six device capabilities: device identification, device configuration, data protection, logical access to interfaces, software update, and cybersecurity state awareness [46].
  • NISTIR 8259B defines four non-technical supporting capabilities: documentation; information and query reception; information dissemination; and education and awareness [73].
  • NISTIR 8259C and 8259D (released as drafts in December 2020) describe how to build profiles from the baselines, with 8259D giving a profile for the US federal government [74]. That federal work was finalised in NIST SP 800-213 [75], and NISTIR 8425 applies the baselines to consumer IoT products [76].

6.2 NIST Cybersecurity Framework 2.0

CSF 2.0, published in February 2024, organises cybersecurity outcomes into six Functions: Govern, Identify, Protect, Detect, Respond, Recover. Govern is new in version 2.0 and covers strategy, roles, policy and supply-chain risk management [77]. The CSF is outcome-based and technology-neutral, so it suits an organisation's IoT programme as a whole rather than an individual device design.

6.3 ETSI EN 303 645

ETSI EN 303 645 is a European standard of baseline security provisions for consumer IoT products. Its cybersecurity provisions are grouped into 13 categories, the first three of which are no universal default passwords, implementing a means to manage reports of vulnerabilities, and keeping software updated; further categories cover secure storage of sensitive parameters, secure communication, minimising exposed attack surfaces, software integrity, personal data, resilience to outages, telemetry, ease of deleting user data, installation and maintenance, and input validation. A separate clause addresses data protection [25]. The UK's product security regulations draw on its first three provisions [63], and the EU Cyber Resilience Act sets horizontal essential requirements for products with digital elements sold in the EU [78].

6.4 ISO/IEC 27400

ISO/IEC 27400:2022 provides guidelines on IoT security and privacy: it describes risk sources, principles and controls for IoT systems, addressed to the different stakeholders in an IoT system's lifecycle (such as IoT service providers, developers and users) [79]. It is guidance rather than a certifiable management-system standard, and is typically used alongside an ISO/IEC 27001 information security management system.

6.5 IEC 62443 (industrial cybersecurity)

IEC 62443 is a multi-part series for industrial automation and control systems (IACS). Its parts are organised into general concepts, policies and procedures for asset owners, system requirements, and component requirements. Key ideas:

  • Zones and conduits for segmentation, with a target security level (SL 1 to SL 4) per zone, rising from protection against casual or coincidental violation to protection against sophisticated, well-resourced attackers [35].
  • Seven foundational requirements: identification and authentication control, use control, system integrity, data confidentiality, restricted data flow, timely response to events, and resource availability [23,35].
  • IEC 62443-4-1 specifies a secure product development lifecycle [16]; IEC 62443-4-2 specifies technical requirements for components, distinguishing software applications, embedded devices, host devices and network devices [23].

NIST SP 800-82 Rev. 3 is a complementary US guide to OT security that references IEC 62443 concepts [2].

8. Exercises (with solutions)

Try each exercise before opening its solution.

Exercise 1: Chain of trust

A device's boot ROM verifies the bootloader, and the bootloader verifies the application, but the bootloader's public key is stored in ordinary rewritable flash. What is the weakness and how would you fix it?

Solution

An attacker who can write flash (through a debug port, an exploit, or a malicious update) can replace the public key with their own and then sign any bootloader they like. The trust anchor must be immutable: store the key, or its hash, in ROM or one-time-programmable fuses, so the boot ROM checks the bootloader's key against a value that cannot be changed in the field [5]. Also lock the debug port (Section 2.6).

Exercise 2: PCR arithmetic

Using the Python extend() function from Section 2.2, can software running after boot set a PCR back to its "golden" value after loading a malicious kernel? Why or why not?

Solution

No. An extend computes SHA-256(old ‖ measurement). Reaching a chosen target value from the current one would require finding a SHA-256 preimage, which is computationally infeasible, and PCRs can only be reset by a platform reset, which restarts measurement from the boot ROM [6]. That is what makes measured boot trustworthy for remote attestation [8].

Exercise 3: Build and inspect a PKI

Run the OpenSSL script in Section 4.2. Then (a) try to use thermo-0042.crt as a CA to sign another certificate and verify the result; (b) explain the outcome.

Solution

(a) openssl verify fails with an error indicating an invalid CA certificate. (b) The device certificate has basicConstraints=CA:FALSE and keyUsage=digitalSignature only, and the issuing CA has pathlen:0, so RFC 5280 path validation forbids any certificate below it from acting as a CA [50]. These constraints stop a stolen device key from minting new device identities.

Exercise 4: Firewall review

A colleague adds iifname "vlan30" accept at the top of the forward chain in Section 3.4 "to fix a camera that cannot reach its cloud". What happens, and what would you do instead?

Solution

Because nftables evaluates rules in order and accept is final for that chain, every packet from the IoT VLAN is accepted, to any destination including the corporate network and the Internet. Segmentation is gone. Instead, find out the exact destinations the camera needs (vendor documentation, or a MUD file [36]), and add a narrow rule for those addresses and ports, preferably through a proxy or VPN, with logging. This follows NIST's advice that firewall rules be specific and justified [37].

Exercise 5: RBAC or ABAC?

A hospital requires that "infusion pumps may receive dosage-limit updates only from the pharmacy system, only for pumps in the same ward, and only if the pump's firmware is a validated version". Which model fits better? Sketch the rule.

Solution

ABAC, because the decision depends on attributes of the subject (system = pharmacy), the object (pump ward, firmware version) and possibly the environment, not on a fixed role [57]. Sketch in Rego, following Section 4.7 [58]:

allow if {
    input.subject.system == "pharmacy"
    input.action == "update_dosage_limits"
    input.subject.ward == input.resource.ward
    input.resource.firmware_version in data.validated_versions[input.resource.model]
}

Exercise 6: Replay window

Using ReplayWindow(size=64) from Section 5.10, starting fresh, which of these sequence numbers are accepted: 10, 12, 11, 12, 80, 15, 17?

Solution

10 ✓ (new top), 12 ✓ (new top), 11 ✓ (inside window, unseen), 12 ✗ (duplicate), 80 ✓ (new top; window now covers 17 to 80), 15 ✗ (80 − 15 = 65 ≥ 64, too old), 17 ✓ (80 − 17 = 63, inside window, unseen). This mirrors the ESP anti-replay window in RFC 4303 [70].

Exercise 7: Map to frameworks

For the control "each device ships with a unique password printed on its label", name the relevant ETSI EN 303 645 provision category, OWASP IoT Top 10 item, and NISTIR 8259A capability.

Solution

ETSI EN 303 645: "No universal default passwords" (provision 5.1) [25]. OWASP: I1, weak, guessable or hardcoded passwords [4]. NISTIR 8259A: logical access to interfaces, since the device restricts access to its interfaces to authorised entities [46]. A better design is certificate-based device identity, with the label password used only for local first-time setup.

Exercise 8: Threat modelling

List one threat and one control for each layer of Figure 1 for a smart door lock that has BLE, Wi-Fi, a cloud API and a phone app.

Solution

Device: debug port used to extract keys → debug lock, keys in a secure element [13]. Local radio: BLE unlock command replayed → nonce challenge-response (Section 5.10) [71]. WAN: MITM on Wi-Fi → TLS 1.3 with certificate validation [26]. Update channel: malicious firmware → signed manifests with anti-rollback [20]. Cloud and app: one user unlocks another's door by changing an ID → object-level authorisation on every API call [4].

10. Key takeaways

  • Anchor trust in hardware: immutable boot code, keys in a TPM or secure element, secure and measured boot [5,6].
  • Sign everything that runs, verify it on the device, and prevent rollback [20].
  • Give every device a unique cryptographic identity and use mutual TLS [26,47].
  • Segment by default-deny, watch traffic with IDS, and grant access per session in zero-trust style [37,42,45].
  • Automate certificate lifecycle and secret rotation; short-lived credentials limit damage [14].
  • Most real IoT compromises still start with default credentials and exposed services [4,66].
  • Use the standards together: NISTIR 8259 and ETSI EN 303 645 for products, IEC 62443 for industrial systems, ISO/IEC 27400 and CSF 2.0 for the organisation [1,23,25,77,79].
