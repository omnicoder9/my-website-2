Angular Services

An Angular service is a dependency-injected unit of reusable application behavior. Services are the usual home for business operations, shared state, HTTP access, authentication state, logging, configuration, and other capabilities that should not be owned by a single view. Their effectiveness depends less on the decorator than on scope, contracts, state ownership, and separation of responsibilities.

1. What an Angular service is

Angular dependency injection supplies dependencies to consumers instead of requiring those consumers to construct dependencies directly. A dependency may be a class instance, configuration object, function, tokenized value, or another service. Angular’s injector resolves providers, creates instances when needed, and reuses those instances within the provider’s injector scope.[1][2][3]

Capability

A service exposes an operation such as calculating a price, fetching a customer, recording a log event, or signing out a session.

State owner

A service may own state shared across multiple components or routes and expose read-only reactive projections of that state.[1][10]

Integration boundary

A service can isolate browser APIs, HTTP endpoints, storage, telemetry vendors, or other external systems behind an application-level contract.[1][12][13]

Angular’s current documentation describes services as reusable code for data clients, state management, authentication and authorization, logging, error handling, event dispatch, and utilities. The framework does not require every reusable function to become a service; dependency injection is most valuable when behavior needs lifecycle management, substitution, configuration, state, or other injected dependencies.[1][2][19]

A useful design test Make something a service when consumers should depend on a capability rather than construct or know the implementation. Keep a stateless, deterministic helper as a plain function when dependency injection adds no value.

2. Historical development

AngularJS: injectable singleton objects

AngularJS organized shared code as services registered with a module. Its documentation described services as lazily instantiated singleton objects within an injector, created through factories and injected into controllers, directives, filters, and other services. Built-in services used names such as $http and $route.[6]

Angular 2: class-oriented services and hierarchical DI

The rewritten Angular framework retained dependency injection but centered applications on TypeScript classes and a hierarchical injector system. Archived Angular 2 guidance defined a service broadly as a focused class or value, encouraged components to delegate data access and logging, and documented that dependencies are singleton-like within an injector rather than necessarily across every injector in the application.[7][8]

Root provision and tree-shakable providers

Later Angular guidance standardized @Injectable({ providedIn: 'root' }) as the common application-wide pattern. Root provision creates one shared instance in the root injector and lets build optimization remove unused services.[9][3]

Signals and service-owned reactive state

Angular signals introduced a native reactive primitive whose reads are tracked and whose updates notify consumers. Services can own writable signals privately and expose read-only or computed signals to components, complementing RxJS streams used for asynchronous and event-oriented workflows.[10][11]

Current Angular: @Service shorthand

Current Angular documentation includes @Service() as an ergonomic shorthand for a root-provided service that uses inject(). @Injectable remains appropriate for constructor injection, non-root provision, and advanced provider configuration, and it remains the most portable syntax across modern Angular versions.[2][24]

Compatibility choice used in this article Most examples use @Injectable({ providedIn: 'root' }). It is explicit, widely recognized, supports both constructor and inject()-based dependencies, and works across a broad range of maintained Angular codebases.

3. Creating and injecting services

3.1 A minimal service

tax-calculator.service.ts
import { Injectable } from '@angular/core';

@Injectable({
  providedIn: 'root',
})
export class TaxCalculatorService {
  calculateSubtotal(
    unitPrice: number,
    quantity: number,
  ): number {
    if (!Number.isFinite(unitPrice) || unitPrice < 0) {
      throw new RangeError('unitPrice must be non-negative');
    }

    if (!Number.isInteger(quantity) || quantity < 0) {
      throw new RangeError('quantity must be a non-negative integer');
    }

    return unitPrice * quantity;
  }
}

The class becomes injectable through its decorator metadata, while providedIn: 'root' registers a root provider. Angular creates the instance only when something requests it, then reuses that root-scoped instance for later requests from the same injector hierarchy.[3][4]

3.2 Injecting with inject()

order-summary.component.ts
import { CurrencyPipe } from '@angular/common';
import { Component, inject } from '@angular/core';
import { TaxCalculatorService } from './tax-calculator.service';

@Component({
  selector: 'app-order-summary',
  standalone: true,
  imports: [CurrencyPipe],
  template: `
    <p>Subtotal: {{ subtotal | currency }}</p>
  `,
})
export class OrderSummaryComponent {
  private readonly taxCalculator =
    inject(TaxCalculatorService);

  readonly subtotal =
    this.taxCalculator.calculateSubtotal(49.95, 3);
}

The inject() function may be called in an injection context, including field initializers, constructors, provider factories, guards, interceptors, and service creation. Calling it later in an arbitrary instance method or lifecycle hook is outside the class-creation injection context and produces an error.[5]

3.3 Constructor injection

constructor-injection example
import { Injectable } from '@angular/core';

@Injectable({ providedIn: 'root' })
export class CheckoutService {
  constructor(
    private readonly pricing: PricingService,
    private readonly orders: OrderApi,
  ) {}

  placeOrder(cart: Cart): Observable<Order> {
    const request = this.pricing.toOrderRequest(cart);
    return this.orders.create(request);
  }
}

Constructor injection makes dependencies visible in the constructor signature and remains useful in existing applications and classes that need @Injectable. Current @Service() shorthand is documented for inject()-based dependencies rather than constructor injection.[2][24]

4. Providers, tokens, and scope

A provider is a recipe that associates a dependency-injection token with a value or construction strategy. Angular supports automatic provision through decorator or token metadata and manual provision through application, route, component, directive, or NgModule provider arrays.[3][4]

4.1 Root-scoped services

application-wide service
@Injectable({ providedIn: 'root' })
export class CurrentUserStore {
  // One shared instance in the application root injector.
}

Root scope is appropriate for services whose identity should be shared across the application: HTTP API clients, authentication state, global telemetry, configuration, and application-wide caches. Root scope does not make mutable state automatically safe or well designed; it only determines instance lifetime and visibility.[3][4]

4.2 Component-scoped services

isolated service instance per component subtree
@Component({
  selector: 'app-order-editor',
  standalone: true,
  providers: [OrderDraftStore],
  templateUrl: './order-editor.component.html',
})
export class OrderEditorComponent {
  readonly draft = inject(OrderDraftStore);
}

A component provider creates an instance associated with that component’s injector and exposes it to eligible descendants. Each component instance receives its own service instance, and the instance becomes unreachable when the component subtree is destroyed. This is useful for editor drafts, wizard state, sandboxed widgets, and reusable feature instances.[3][4]

4.3 Route-scoped services

route-scoped providers
export const ADMIN_ROUTES: Routes = [
  {
    path: '',
    providers: [
      AdminAuditService,
      { provide: ADMIN_API_URL, useValue: '/api/admin' },
    ],
    children: [
      { path: '', component: AdminHomePage },
      { path: 'users', component: AdminUsersPage },
    ],
  },
];

Route-level providers create a feature-scoped environment injector. They are useful when services should exist only for a route subtree or when lazy features require an isolated configuration or cache.[3][4]

4.4 InjectionToken for non-class dependencies

api-config.token.ts
import { InjectionToken } from '@angular/core';

export interface ApiConfig {
  readonly baseUrl: string;
  readonly requestTimeoutMs: number;
}

export const API_CONFIG =
  new InjectionToken<ApiConfig>('api.config', {
    providedIn: 'root',
    factory: () => ({
      baseUrl: '/api',
      requestTimeoutMs: 15_000,
    }),
  });
inject a configuration token
@Injectable({ providedIn: 'root' })
export class CustomerApi {
  private readonly config = inject(API_CONFIG);
  private readonly http = inject(HttpClient);

  getById(id: string): Observable<CustomerDto> {
    return this.http.get<CustomerDto>(
      `${this.config.baseUrl}/customers/${encodeURIComponent(id)}`,
    );
  }
}

Interfaces do not exist at runtime and therefore cannot serve directly as injection tokens. InjectionToken gives non-class values a runtime identity and can define its own root factory.[3]

4.5 Provider recipes

manual provider forms
providers: [
  // Class token creates the same class.
  AuditService,

  // Replace one implementation with another.
  { provide: PaymentGateway, useClass: SandboxPaymentGateway },

  // Supply a literal or prebuilt object.
  { provide: FEATURE_FLAGS, useValue: { newCheckout: true } },

  // Alias one token to an existing instance.
  { provide: Logger, useExisting: StructuredLogger },

  // Build a value from other injected dependencies.
  {
    provide: ORDER_POLICY,
    useFactory: () => {
      const config = inject(APP_CONFIG);
      return createOrderPolicy(config.region);
    },
  },
]

Provider substitution is one of DI’s main architectural benefits: consumers depend on a stable token while configuration selects the concrete implementation. useExisting aliases an existing instance; useClass can create a distinct instance under the requested token.[3]

4.6 Hierarchical resolution

Angular resolves a dependency from the nearest eligible provider and searches upward through element and environment injector hierarchies. A child can override a parent provider, but a parent cannot see a provider declared only in a descendant. Multiple providers for the same token at different levels therefore produce intentionally different instances or implementations.[4]

The “singleton service” qualification A service is singleton within a particular injector that owns its provider. Re-providing the same service at a component, route, lazy module, or other child injector creates another scoped instance.

5. Business logic services

Components should mediate the user experience: receive input, expose view state, and translate user actions into application operations. Domain calculations, workflow rules, and integration orchestration are easier to test and reuse when moved into focused services or plain domain functions rather than embedded in templates and event handlers.[1][7][9]

5.1 A pure domain policy

order-pricing-policy.ts
export interface LineItem {
  readonly sku: string;
  readonly unitPriceCents: number;
  readonly quantity: number;
}

export interface PricingResult {
  readonly subtotalCents: number;
  readonly discountCents: number;
  readonly totalCents: number;
}

export class OrderPricingPolicy {
  price(
    items: readonly LineItem[],
    discountRate: number,
  ): PricingResult {
    if (discountRate < 0 || discountRate > 1) {
      throw new RangeError('discountRate must be between 0 and 1');
    }

    const subtotalCents = items.reduce(
      (sum, item) =>
        sum + item.unitPriceCents * item.quantity,
      0,
    );

    const discountCents =
      Math.round(subtotalCents * discountRate);

    return {
      subtotalCents,
      discountCents,
      totalCents: subtotalCents - discountCents,
    };
  }
}

This class has no Angular dependencies. It can remain a plain TypeScript class and be constructed by a provider factory if runtime configuration or substitution is required.

provide a plain domain class
export const ORDER_PRICING =
  new InjectionToken<OrderPricingPolicy>('order.pricing', {
    providedIn: 'root',
    factory: () => new OrderPricingPolicy(),
  });

5.2 An application workflow service

place-order.service.ts
@Injectable({ providedIn: 'root' })
export class PlaceOrderService {
  private readonly pricing = inject(ORDER_PRICING);
  private readonly orderApi = inject(OrderApi);
  private readonly logger = inject(Logger);

  execute(
    cart: Cart,
    customer: Customer,
  ): Observable<Order> {
    const pricing = this.pricing.price(
      cart.items,
      customer.discountRate,
    );

    const request: CreateOrderRequest = {
      customerId: customer.id,
      items: cart.items.map(item => ({
        sku: item.sku,
        quantity: item.quantity,
      })),
      expectedTotalCents: pricing.totalCents,
    };

    return this.orderApi.create(request).pipe(
      tap(order => {
        this.logger.info('order.created', {
          orderId: order.id,
          itemCount: request.items.length,
        });
      }),
    );
  }
}

The application service coordinates domain policy, data access, and logging without owning rendering concerns. The server must still calculate authoritative prices and enforce business invariants; client-side calculations provide interaction and early validation but cannot establish trust.

6. Shared state services

Services are a natural location for state that must outlive one component or be observed by several consumers. Angular signals provide synchronous state reads and dependency tracking, while RxJS observables model asynchronous streams, cancellation, multicasting, and event composition. A service can expose either or both, but should preserve a single owner for each mutable value.[10][11]

6.1 Encapsulated signal store

cart.store.ts
import {
  Injectable,
  computed,
  signal,
} from '@angular/core';

export interface CartItem {
  readonly productId: string;
  readonly name: string;
  readonly unitPriceCents: number;
  readonly quantity: number;
}

@Injectable({ providedIn: 'root' })
export class CartStore {
  private readonly _items =
    signal<readonly CartItem[]>([]);

  readonly items = this._items.asReadonly();

  readonly itemCount = computed(() =>
    this._items().reduce(
      (sum, item) => sum + item.quantity,
      0,
    ),
  );

  readonly subtotalCents = computed(() =>
    this._items().reduce(
      (sum, item) =>
        sum + item.unitPriceCents * item.quantity,
      0,
    ),
  );

  add(product: Product): void {
    this._items.update(items => {
      const existing = items.find(
        item => item.productId === product.id,
      );

      if (existing) {
        return items.map(item =>
          item.productId === product.id
            ? { ...item, quantity: item.quantity + 1 }
            : item,
        );
      }

      return [
        ...items,
        {
          productId: product.id,
          name: product.name,
          unitPriceCents: product.priceCents,
          quantity: 1,
        },
      ];
    });
  }

  remove(productId: string): void {
    this._items.update(items =>
      items.filter(item => item.productId !== productId),
    );
  }

  clear(): void {
    this._items.set([]);
  }
}

The mutable signal is private, while consumers receive a read-only signal and computed projections. Signal reads are tracked, and computed values are derived rather than manually synchronized. Angular advises using computed signals for derived state and reserving effects for synchronization with imperative, non-signal APIs.[10][11]

6.3 Model asynchronous state explicitly

customer.store.ts
export type LoadState<T> =
  | { readonly status: 'idle' }
  | { readonly status: 'loading' }
  | { readonly status: 'loaded'; readonly data: T }
  | { readonly status: 'error'; readonly message: string };

@Injectable({ providedIn: 'root' })
export class CustomerStore {
  private readonly api = inject(CustomerApi);

  private readonly _state =
    signal<LoadState<Customer>>({ status: 'idle' });

  readonly state = this._state.asReadonly();

  readonly customer = computed(() => {
    const state = this._state();
    return state.status === 'loaded' ? state.data : null;
  });

  load(id: string): void {
    this._state.set({ status: 'loading' });

    this.api.getById(id).subscribe({
      next: customer =>
        this._state.set({
          status: 'loaded',
          data: customer,
        }),
      error: error =>
        this._state.set({
          status: 'error',
          message: userFacingMessage(error),
        }),
    });
  }
}

A discriminated state model prevents impossible combinations such as loading === true while an unrelated stale error remains active. For requests that need cancellation, deduplication, repeated refresh, or composition, retain the RxJS pipeline in the service rather than nesting subscriptions.

6.4 RxJS-backed store

search.store.ts
@Injectable({ providedIn: 'root' })
export class SearchStore {
  private readonly api = inject(ProductApi);

  private readonly querySubject =
    new BehaviorSubject<string>('');

  readonly query$ = this.querySubject.asObservable();

  readonly results$ = this.query$.pipe(
    map(query => query.trim()),
    debounceTime(250),
    distinctUntilChanged(),
    switchMap(query =>
      query
        ? this.api.search(query)
        : of<readonly Product[]>([]),
    ),
    shareReplay({
      bufferSize: 1,
      refCount: true,
    }),
  );

  setQuery(query: string): void {
    this.querySubject.next(query);
  }
}

RxJS is especially suitable when state is fundamentally a stream of asynchronous events. Signals are especially convenient for synchronous application state consumed by Angular templates. Conversion APIs can bridge the two when necessary, but excessive back-and-forth conversion obscures ownership and lifecycle.

7. API communication services

Angular provides HttpClient for backend communication. Its request methods return cold RxJS observables: no request is sent until subscription, and each independent subscription normally sends a new request. Angular recommends isolating reusable data-access logic in injectable services rather than scattering endpoint details across components.[12][13]

7.1 Configure HttpClient

app.config.ts
import { ApplicationConfig } from '@angular/core';
import {
  provideHttpClient,
  withInterceptors,
} from '@angular/common/http';

export const appConfig: ApplicationConfig = {
  providers: [
    provideHttpClient(
      withInterceptors([
        requestIdInterceptor,
        authInterceptor,
        apiErrorInterceptor,
      ]),
    ),
  ],
};

Functional interceptors are the current Angular recommendation because their ordering and behavior are more predictable in complex configurations. Interceptors can add authentication, logging, caching, retry policy, deadlines, or other cross-cutting request behavior.[14]

7.2 A typed CRUD API client

customer.api.ts
import {
  HttpClient,
  HttpParams,
} from '@angular/common/http';
import { Injectable, inject } from '@angular/core';
import { Observable, map } from 'rxjs';

export interface CustomerDto {
  readonly id: string;
  readonly displayName: string;
  readonly email: string;
  readonly version: number;
}

export interface Customer {
  readonly id: string;
  readonly name: string;
  readonly email: string;
  readonly version: number;
}

export interface CreateCustomerRequest {
  readonly displayName: string;
  readonly email: string;
}

@Injectable({ providedIn: 'root' })
export class CustomerApi {
  private readonly http = inject(HttpClient);
  private readonly config = inject(API_CONFIG);

  list(
    search = '',
    page = 1,
  ): Observable<readonly Customer[]> {
    const params = new HttpParams()
      .set('search', search)
      .set('page', page);

    return this.http
      .get<readonly CustomerDto[]>(
        `${this.config.baseUrl}/customers`,
        { params },
      )
      .pipe(
        map(items => items.map(toCustomer)),
      );
  }

  getById(id: string): Observable<Customer> {
    return this.http
      .get<CustomerDto>(
        `${this.config.baseUrl}/customers/` +
        encodeURIComponent(id),
      )
      .pipe(map(toCustomer));
  }

  create(
    request: CreateCustomerRequest,
  ): Observable<Customer> {
    return this.http
      .post<CustomerDto>(
        `${this.config.baseUrl}/customers`,
        request,
      )
      .pipe(map(toCustomer));
  }

  update(
    customer: Customer,
  ): Observable<Customer> {
    return this.http
      .put<CustomerDto>(
        `${this.config.baseUrl}/customers/` +
        encodeURIComponent(customer.id),
        {
          displayName: customer.name,
          email: customer.email,
          version: customer.version,
        },
      )
      .pipe(map(toCustomer));
  }

  delete(id: string): Observable<void> {
    return this.http.delete<void>(
      `${this.config.baseUrl}/customers/` +
      encodeURIComponent(id),
    );
  }
}

function toCustomer(dto: CustomerDto): Customer {
  return {
    id: dto.id,
    name: dto.displayName,
    email: dto.email,
    version: dto.version,
  };
}

The generic type on an HttpClient request is a TypeScript assertion about the expected response; Angular does not perform runtime schema validation. Validate untrusted responses at the application boundary when correctness or security depends on shape and value constraints.[13]

7.3 Separate transport and workflow

customer.service.ts
@Injectable({ providedIn: 'root' })
export class CustomerService {
  private readonly api = inject(CustomerApi);
  private readonly logger = inject(Logger);

  register(
    command: RegisterCustomerCommand,
  ): Observable<Customer> {
    const request: CreateCustomerRequest = {
      displayName: command.name.trim(),
      email: command.email.trim().toLowerCase(),
    };

    return this.api.create(request).pipe(
      tap(customer =>
        this.logger.info('customer.registered', {
          customerId: customer.id,
        }),
      ),
    );
  }
}

The API client understands URLs, transport DTOs, and response mapping. The application service understands the user operation and business workflow. Keeping these layers distinct reduces coupling between component behavior and backend representation.

7.4 Normalize HTTP failures

api-failure.ts
export type ApiFailure =
  | { kind: 'offline'; message: string }
  | { kind: 'unauthorized'; message: string }
  | { kind: 'forbidden'; message: string }
  | { kind: 'not-found'; message: string }
  | {
      kind: 'validation';
      message: string;
      fields: Record<string, string>;
    }
  | {
      kind: 'server';
      message: string;
      requestId?: string;
    };

export function normalizeHttpError(
  error: HttpErrorResponse,
): ApiFailure {
  if (error.status === 0) {
    return {
      kind: 'offline',
      message: 'The service could not be reached.',
    };
  }

  if (error.status === 401) {
    return {
      kind: 'unauthorized',
      message: 'Sign in is required.',
    };
  }

  if (error.status === 403) {
    return {
      kind: 'forbidden',
      message: 'This action is not permitted.',
    };
  }

  if (error.status === 404) {
    return {
      kind: 'not-found',
      message: 'The requested resource was not found.',
    };
  }

  if (
    error.status === 422 &&
    isValidationProblem(error.error)
  ) {
    return {
      kind: 'validation',
      message: error.error.message,
      fields: error.error.fields,
    };
  }

  return {
    kind: 'server',
    message: 'The server could not complete the request.',
    requestId: error.headers.get('x-request-id') ?? undefined,
  };
}

Expected failures should be handled near the operation that can recover or present meaningful feedback. Angular’s global ErrorHandler is intended for unexpected, unhandled errors rather than replacing local HTTP error handling.[16][17]

8. Utility services

A utility service wraps reusable behavior that benefits from injection, configuration, platform abstraction, state, or substitution. Pure calculations that have no dependencies are usually simpler as exported functions.

8.1 Abstract time for deterministic tests

clock abstraction
export abstract class Clock {
  abstract now(): Date;
}

@Injectable({ providedIn: 'root' })
export class SystemClock implements Clock {
  now(): Date {
    return new Date();
  }
}

// Application provider:
providers: [
  { provide: Clock, useExisting: SystemClock },
]

Consumers can depend on Clock rather than calling new Date(), allowing tests to substitute a deterministic implementation.

test clock
class FixedClock implements Clock {
  constructor(private readonly instant: Date) {}

  now(): Date {
    return new Date(this.instant);
  }
}

8.2 Isolate browser APIs

clipboard.port.ts
export abstract class ClipboardPort {
  abstract writeText(value: string): Promise<void>;
}

@Injectable({ providedIn: 'root' })
export class BrowserClipboard
  implements ClipboardPort {

  async writeText(value: string): Promise<void> {
    if (!navigator.clipboard) {
      throw new Error('Clipboard API is unavailable');
    }

    await navigator.clipboard.writeText(value);
  }
}

An abstraction keeps components independent of the browser API and provides a natural place for capability checks, normalization, server-rendering guards, and test doubles.

8.3 Prefer a plain function when DI adds nothing

normalize-email.ts
export function normalizeEmail(value: string): string {
  return value.trim().toLowerCase();
}

A stateless deterministic helper does not need a class, injector registration, or mock framework. Overusing services for tiny functions creates indirection without improving ownership.

9. Logging services

A logging service establishes a consistent event vocabulary, level policy, context model, redaction policy, and transport boundary. Angular’s ErrorHandler provides a centralized hook for unhandled framework-reported exceptions, while expected operational failures should be handled where they occur.[16][17]

9.1 Define a structured contract

logger.ts
export type LogLevel =
  | 'debug'
  | 'info'
  | 'warn'
  | 'error';

export interface LogContext {
  readonly [key: string]:
    string | number | boolean | null | undefined;
}

export abstract class Logger {
  abstract debug(
    event: string,
    context?: LogContext,
  ): void;

  abstract info(
    event: string,
    context?: LogContext,
  ): void;

  abstract warn(
    event: string,
    context?: LogContext,
  ): void;

  abstract error(
    event: string,
    error?: unknown,
    context?: LogContext,
  ): void;
}

9.2 Browser implementation with redaction

structured-logger.service.ts
@Injectable({ providedIn: 'root' })
export class StructuredLogger implements Logger {
  private readonly app = inject(APP_METADATA);

  debug(event: string, context: LogContext = {}): void {
    this.write('debug', event, context);
  }

  info(event: string, context: LogContext = {}): void {
    this.write('info', event, context);
  }

  warn(event: string, context: LogContext = {}): void {
    this.write('warn', event, context);
  }

  error(
    event: string,
    error?: unknown,
    context: LogContext = {},
  ): void {
    this.write('error', event, {
      ...context,
      errorName:
        error instanceof Error ? error.name : 'UnknownError',
      errorMessage:
        error instanceof Error
          ? error.message
          : String(error ?? ''),
    });
  }

  private write(
    level: LogLevel,
    event: string,
    context: LogContext,
  ): void {
    const record = {
      timestamp: new Date().toISOString(),
      level,
      event,
      application: this.app.name,
      version: this.app.version,
      context: redact(context),
    };

    const method =
      level === 'error' ? console.error :
      level === 'warn' ? console.warn :
      level === 'debug' ? console.debug :
      console.info;

    method(record);
  }
}

const SENSITIVE_KEYS =
  /password|token|authorization|cookie|secret|session/i;

function redact(context: LogContext): LogContext {
  return Object.fromEntries(
    Object.entries(context).map(([key, value]) => [
      key,
      SENSITIVE_KEYS.test(key) ? '[REDACTED]' : value,
    ]),
  );
}

OWASP recommends consistent logging, validation and sanitization of event data, protection against log injection, and exclusion or masking of sensitive information. Client logs are useful for diagnostics but are not a trusted audit trail because the browser and its network traffic are controlled by the user.[20]

9.4 HTTP timing interceptor

request-logging.interceptor.ts
export const requestLoggingInterceptor:
  HttpInterceptorFn = (request, next) => {
    const logger = inject(Logger);
    const startedAt = performance.now();

    return next(request).pipe(
      tap({
        next: event => {
          if (event.type === HttpEventType.Response) {
            logger.info('http.response', {
              method: request.method,
              path: safePath(request.url),
              status: event.status,
              durationMs:
                Math.round(performance.now() - startedAt),
            });
          }
        },
        error: error => {
          logger.warn('http.failure', {
            method: request.method,
            path: safePath(request.url),
            status:
              error instanceof HttpErrorResponse
                ? error.status
                : 0,
            durationMs:
              Math.round(performance.now() - startedAt),
          });
        },
      }),
    );
  };

Do not log request bodies, authorization headers, cookies, full query strings, or user-entered values by default. Use a controlled allow-list of metadata and a server-generated correlation identifier when available.[20]

10. Authentication services

An authentication service should expose session state and authentication operations without making components understand token formats, cookie mechanics, identity-provider details, or HTTP interception. Authentication establishes identity; authorization still belongs to the server for every protected operation.

10.1 Same-origin cookie or BFF session

For a same-origin application or Backend-for-Frontend design, the server can hold tokens and issue a Secure, HttpOnly, appropriately scoped session cookie. JavaScript cannot read an HttpOnly cookie; the browser sends it according to cookie rules. OWASP advises against storing authentication tokens or session identifiers in localStorage or sessionStorage because any script executing in the origin can read them.[21]

auth.service.ts — cookie-backed session
export interface AuthenticatedUser {
  readonly id: string;
  readonly displayName: string;
  readonly roles: readonly string[];
}

type AuthState =
  | { readonly status: 'checking' }
  | { readonly status: 'anonymous' }
  | {
      readonly status: 'authenticated';
      readonly user: AuthenticatedUser;
    };

@Injectable({ providedIn: 'root' })
export class AuthService {
  private readonly http = inject(HttpClient);
  private readonly router = inject(Router);

  private readonly _state =
    signal<AuthState>({ status: 'checking' });

  readonly state = this._state.asReadonly();

  readonly user = computed(() => {
    const state = this._state();
    return state.status === 'authenticated'
      ? state.user
      : null;
  });

  readonly isAuthenticated = computed(
    () => this._state().status === 'authenticated',
  );

  initialize(): Observable<void> {
    return this.http
      .get<AuthenticatedUser>('/api/session')
      .pipe(
        tap(user =>
          this._state.set({
            status: 'authenticated',
            user,
          }),
        ),
        map(() => undefined),
        catchError(error => {
          if (
            error instanceof HttpErrorResponse &&
            error.status === 401
          ) {
            this._state.set({ status: 'anonymous' });
            return of(undefined);
          }

          return throwError(() => error);
        }),
      );
  }

  signIn(
    credentials: {
      username: string;
      password: string;
    },
  ): Observable<void> {
    return this.http
      .post<AuthenticatedUser>(
        '/api/session',
        credentials,
      )
      .pipe(
        tap(user =>
          this._state.set({
            status: 'authenticated',
            user,
          }),
        ),
        map(() => undefined),
      );
  }

  signOut(): Observable<void> {
    return this.http
      .delete<void>('/api/session')
      .pipe(
        finalize(() => {
          this._state.set({ status: 'anonymous' });
          void this.router.navigateByUrl('/login', {
            replaceUrl: true,
          });
        }),
      );
  }
}

The service stores only derived user/session state, not the cookie credential. For cross-origin cookie requests, withCredentials, CORS, cookie scope, SameSite policy, and CSRF protections must be designed together on the server and client.

10.2 In-memory access token service

Some browser applications handle OAuth access tokens directly. Current OAuth browser guidance discusses BFF, service-worker, web-worker, in-memory, and persistent storage trade-offs; no client-side storage choice neutralizes malicious script execution. If the application must possess a bearer token, keep storage and refresh logic behind a narrow service and avoid persistent web storage unless the threat model explicitly accepts its exposure.[22][21]

10.3 Attach a bearer token with an interceptor

auth.interceptor.ts
export const authInterceptor:
  HttpInterceptorFn = (request, next) => {
    const token = inject(AccessTokenService).read();

    if (
      !token ||
      !request.url.startsWith('/api/')
    ) {
      return next(request);
    }

    return next(
      request.clone({
        setHeaders: {
          Authorization: `Bearer ${token}`,
        },
      }),
    );
  };

Angular interceptors execute in the injector context that registered them and can inject an authentication service. Requests and headers are immutable, so the interceptor clones the request to add a header. Apply credentials only to intended API origins; never attach a bearer token indiscriminately to third-party URLs.[14]

10.4 Authentication service in a route guard

authenticated.guard.ts
export const authenticatedGuard:
  CanActivateFn = (_route, state) => {
    const auth = inject(AuthService);
    const router = inject(Router);

    return auth.isAuthenticated()
      ? true
      : router.createUrlTree(['/login'], {
          queryParams: {
            returnUrl: state.url,
          },
        });
  };
A route guard is user experience, not authorization It can prevent navigation in the normal client, but it cannot protect an API or resource from a modified browser. The server must enforce permissions independently.

10.5 Authentication state rules

  • Represent startup as an explicit checking state so the UI does not briefly show anonymous content before session discovery completes.
  • Do not infer authorization solely from decoded client token claims; the server remains authoritative.
  • Clear cached user-specific state on sign-out and account changes.
  • Avoid logging passwords, tokens, cookies, reset links, or complete identity assertions.[20][21]
  • Distinguish session expiration from network failure so offline users are not incorrectly signed out.

project.service.ts
@Injectable({ providedIn: 'root' })
export class ProjectService {
  private readonly api = inject(ProjectApi);
  private readonly logger = inject(Logger);

  create(
    command: CreateProjectCommand,
  ): Observable<Project> {
    const name = command.name.trim();

    if (name.length < 3) {
      return throwError(
        () => new Error(
          'Project name must contain at least 3 characters',
        ),
      );
    }

    return this.api.create({ name }).pipe(
      tap(project =>
        this.logger.info('project.created', {
          projectId: project.id,
        }),
      ),
    );
  }

  archive(id: string): Observable<Project> {
    return this.api.archive(id).pipe(
      tap(project =>
        this.logger.info('project.archived', {
          projectId: project.id,
        }),
      ),
    );
  }
}
project.store.ts
type ProjectState =
  | { status: 'loading'; projects: readonly Project[] }
  | { status: 'ready'; projects: readonly Project[] }
  | {
      status: 'error';
      projects: readonly Project[];
      message: string;
    };

@Injectable({ providedIn: 'root' })
export class ProjectStore {
  private readonly api = inject(ProjectApi);
  private readonly projectService = inject(ProjectService);

  private readonly _state = signal<ProjectState>({
    status: 'loading',
    projects: [],
  });

  readonly state = this._state.asReadonly();

  readonly activeProjects = computed(() =>
    this._state().projects.filter(
      project => !project.archived,
    ),
  );

  load(): void {
    this._state.update(state => ({
      status: 'loading',
      projects: state.projects,
    }));

    this.api.list().subscribe({
      next: projects =>
        this._state.set({
          status: 'ready',
          projects,
        }),
      error: error =>
        this._state.update(state => ({
          status: 'error',
          projects: state.projects,
          message: userFacingMessage(error),
        })),
    });
  }

  create(name: string): void {
    this.projectService.create({ name }).subscribe({
      next: project =>
        this._state.update(state => ({
          status: 'ready',
          projects: [...state.projects, project],
        })),
      error: error =>
        this._state.update(state => ({
          status: 'error',
          projects: state.projects,
          message: userFacingMessage(error),
        })),
    });
  }

  archive(id: string): void {
    this.projectService.archive(id).subscribe({
      next: updated =>
        this._state.update(state => ({
          status: 'ready',
          projects: state.projects.map(project =>
            project.id === updated.id
              ? updated
              : project,
          ),
        })),
      error: error =>
        this._state.update(state => ({
          status: 'error',
          projects: state.projects,
          message: userFacingMessage(error),
        })),
    });
  }
}

12.5 What to test

  • Business invariants and edge cases independently of Angular.
  • Provider substitution and scope where multiple instances matter.
  • DTO mapping and runtime validation at API boundaries.
  • HTTP method, path, parameters, headers, body, and error normalization.
  • Shared-state transitions, derived values, and stale-data behavior.
  • Logging redaction and event naming without asserting incidental console formatting.
  • Authentication startup, expiration, sign-out, and 401/network distinction.

13.2 Use a facade selectively

checkout.facade.ts
@Injectable({ providedIn: 'root' })
export class CheckoutFacade {
  private readonly cart = inject(CartStore);
  private readonly checkout = inject(CheckoutService);

  readonly items = this.cart.items;
  readonly total = this.cart.subtotalCents;

  placeOrder(): Observable<Order> {
    return this.checkout.placeOrder(
      this.cart.items(),
    ).pipe(
      tap(() => this.cart.clear()),
    );
  }
}

A facade can give a page one cohesive dependency when it coordinates several lower-level services. Avoid facades that merely mirror every method of another service or become a universal application gateway.

13.3 Separate commands from queries

Read operations often benefit from caching and sharing, while commands mutate server or application state and need explicit success and failure handling. Distinguishing query methods from command methods clarifies retry, idempotency, cache invalidation, and user feedback.

13.4 Cache with an invalidation policy

explicit cache refresh
@Injectable({ providedIn: 'root' })
export class ProductCatalog {
  private readonly api = inject(ProductApi);

  private readonly refreshSubject = new Subject<void>();

  readonly products$ = this.refreshSubject.pipe(
    startWith(undefined),
    switchMap(() => this.api.list()),
    shareReplay({
      bufferSize: 1,
      refCount: true,
    }),
  );

  refresh(): void {
    this.refreshSubject.next();
  }

  create(
    request: CreateProductRequest,
  ): Observable<Product> {
    return this.api.create(request).pipe(
      tap(() => this.refresh()),
    );
  }
}

A cache without ownership, lifetime, keying, and invalidation rules eventually serves stale or cross-user data. Clear user-specific caches when identity changes and decide whether errors, completion, and late subscribers should reuse previous results.

13.5 Keep effects at integration boundaries

Use computed signals for derived values. Effects are appropriate for synchronizing signal state to imperative APIs such as storage, analytics, canvas, or non-reactive libraries; they should not become an indirect chain for propagating ordinary application state.[11]

effect at an imperative DOM boundary
@Injectable({ providedIn: 'root' })
export class ThemeStore {
  private readonly _theme =
    signal<'light' | 'dark'>('light');

  readonly theme = this._theme.asReadonly();

  constructor() {
    effect(() => {
      document.documentElement.dataset['theme'] =
        this._theme();
    });
  }

  setTheme(theme: 'light' | 'dark'): void {
    this._theme.set(theme);
  }
}

13.6 Consider rendering environments

Root services may run during server rendering as well as in the browser. Avoid accessing window, document, localStorage, or navigator during service construction without platform-aware abstraction. Prefer injected ports or defer access until a browser-only operation is invoked.

14. Common pitfalls

PitfallWhy it hurtsBetter approach
“God service” with unrelated methods Every feature depends on one unstable class. Split by capability and reason to change.
Root scope for every mutable store Temporary feature state survives too long and leaks across instances. Choose component, route, feature, or root scope deliberately.[3][4]
Component calls HttpClient directly everywhere URLs, DTOs, and error handling are duplicated. Encapsulate data access in reusable clients.[13]
Public writable signal Any consumer can mutate state without enforcing invariants. Keep writable state private and expose read-only projections.[10]
Nested subscriptions Cancellation, errors, and completion become hard to reason about. Compose streams with operators such as switchMap.
Calling inject() in arbitrary methods The method may execute outside an injection context. Resolve dependencies during construction.[5]
Persisting tokens in web storage by default Any same-origin script can read and exfiltrate them. Prefer HttpOnly cookie/BFF designs or a threat-modeled alternative.[21][22]
Logging entire errors and request objects Credentials, PII, query strings, and internal data may leak. Allow-list structured metadata and redact sensitive keys.[20]
Using global ErrorHandler for expected failures Users receive generic handling and recovery context is lost. Handle expected errors at the operation boundary.[17]
Mocking every service in every test Tests reproduce implementation wiring instead of behavior. Test pure logic directly and mock only external boundaries.

17. Conclusion

Angular services are the framework’s primary mechanism for composing reusable capabilities through dependency injection. They can isolate business workflows, own reactive shared state, centralize HTTP contracts, abstract platform utilities, standardize logging, and represent authentication state. Provider scope determines lifetime and sharing, while tokens and factories make implementations replaceable.[1][2][3][4]

The strongest service architecture is explicit about boundaries: components own presentation and interaction; business services own workflows; stores own mutable client state; API clients own transport; utilities own platform abstractions; loggers own observability policy; authentication services own session representation; and the server owns authoritative validation, security, and access control.
