Angular Directives

A directive is an Angular class that attaches reusable behavior to an element, component, or template. Components are directives with templates; attribute directives enhance an existing host; structural directives control whether and how embedded views are created. Modern Angular also provides built-in control-flow blocks, which replace many historical structural-directive use cases but are template syntax rather than directive instances.

1. The directive model

Angular classifies directives into components, attribute directives, and structural directives. A component owns a template. An attribute directive changes an existing element, component, or directive. A structural directive changes the rendered view structure by creating, moving, or removing embedded views.[1][2]

Component directive

Selected by an element such as <app-user-card> and associated with its own template.

Attribute directive

Selected by an attribute such as [appTooltip] and attached to an existing host without introducing its own view template.[3]

Structural directive

Applied to <ng-template> and responsible for creating embedded views through TemplateRef and ViewContainerRef.[4]

The @Directive decorator supplies metadata such as the selector, inputs, outputs, providers, host bindings, host directives, and export name. Current Angular directives are standalone by default; a directive intended for an NgModule declaration explicitly sets standalone: false.[2]

minimal standalone directive
import { Directive } from '@angular/core';

@Directive({
  selector: '[appEnhance]',
})
export class EnhanceDirective {}
import and apply a standalone directive
import { Component } from '@angular/core';
import { EnhanceDirective } from './enhance.directive';

@Component({
  selector: 'app-example',
  standalone: true,
  imports: [EnhanceDirective],
  template: `
    <button appEnhance type="button">
      Enhanced button
    </button>
  `,
})
export class ExampleComponent {}
Use a directive for reusable host behavior For a one-off class, style, property, or event, ordinary template bindings are simpler. Create an attribute directive when the behavior deserves a reusable, named contract that can be applied across multiple hosts.[3]

2. Historical development

AngularJS: directives as the HTML extension mechanism

AngularJS described directives as the mechanism that taught the browser new application-oriented syntax. Its HTML compiler traversed the DOM, matched directive registrations against elements and attributes, and executed compile and link behavior. Built-in directives included ngRepeat, ngIf, ngClass, form directives, and many others.[17][18][19]

Angular 2: three directive categories

The rewritten Angular framework formalized components, attribute directives, and structural directives. Early documentation used NgIf, NgFor, and NgSwitch as the principal structural examples, while NgClass and NgStyle represented attribute behavior.[20][21][22]

Standalone directives

Modern directives can be imported directly by standalone components rather than declared and exported through an NgModule. Current decorator behavior marks directives standalone by default.[2]

Angular 15: directive composition

The directive composition API allows a component or directive to statically apply host directives through hostDirectives, optionally exposing selected inputs and outputs.[14]

Angular 17: built-in control flow

Angular introduced built-in @if, @for, and @switch blocks. They are compiled template syntax and do not require importing CommonModule or directive classes.[5][16]

Angular 20: legacy control-flow directives deprecated

NgIf, NgFor, and NgSwitch are deprecated since Angular 20. Current documentation directs new code to @if, @for, and @switch and states an intent to remove the directives in a future major release.[6][7][8][15]

Existing code versus new code Learn the asterisk directives because they are common in long-lived applications and libraries. For new conditional, repeated, and switched template logic, use built-in control flow unless a custom structural abstraction provides domain-specific value.

3. Built-in directives and built-in control flow

Angular’s @angular/common package contains directives for classes, styles, templates, dynamic components, and historical control-flow patterns. Built-in @if, @for, and @switch are part of the template language rather than classes from @angular/common.[1][5][16]

4. *ngIf and @if

NgIf conditionally creates an embedded view when its input is truthy and can select separate then and else templates. Angular expands the asterisk shorthand into an <ng-template> carrying the directive. The API is deprecated since version 20 in favor of @if.[4][6]

4.1 Legacy shorthand

legacy *ngIf example
import { Component, signal } from '@angular/core';
import { NgIf } from '@angular/common';

@Component({
  selector: 'app-legacy-profile',
  standalone: true,
  imports: [NgIf],
  template: `
    <section *ngIf="user(); else signedOut">
      <h2>Welcome, {{ user()!.name }}</h2>
    </section>

    <ng-template #signedOut>
      <p>Sign in to continue.</p>
    </ng-template>
  `,
})
export class LegacyProfileComponent {
  readonly user = signal<User | null>(null);
}

4.2 What the asterisk means

structural shorthand expansion
<!-- Shorthand -->
<section *ngIf="user">
  {{ user.name }}
</section>

<!-- Conceptual expanded form -->
<ng-template [ngIf]="user">
  <section>
    {{ user.name }}
  </section>
</ng-template>

The host element remains inside the embedded template; the directive itself is placed on the generated <ng-template>. This is why only one structural-directive shorthand can appear on a physical element: one asterisk expansion produces one template host.[4]

4.3 Current @if syntax

modern @if block
@if (user(); as currentUser) {
  <section>
    <h2>Welcome, {{ currentUser.name }}</h2>
  </section>
} @else {
  <p>Sign in to continue.</p>
}

@if can contain @else if and @else branches and can save an expression result with as. It requires no import and avoids the microsyntax and separate template-reference pattern for common conditions.[5]

4.4 Side-by-side migration

NgIf to @if
<!-- Before -->
<div *ngIf="loading; else content">
  Loading…
</div>

<ng-template #content>
  <app-results />
</ng-template>

<!-- After -->
@if (loading) {
  <div>Loading…</div>
} @else {
  <app-results />
}

5. *ngFor and @for

NgFor renders one embedded view per item in an iterable. Its template context exposes the item, index, count, first, last, even, and odd values. A custom trackBy function supplies stable identity when object references change. The directive is deprecated since Angular 20 in favor of @for.[7][23]

5.1 Legacy loop

legacy *ngFor example
import { Component, signal } from '@angular/core';
import { NgFor } from '@angular/common';

interface Product {
  readonly id: string;
  readonly name: string;
}

@Component({
  selector: 'app-legacy-product-list',
  standalone: true,
  imports: [NgFor],
  template: `
    <article
      *ngFor="
        let product of products();
        trackBy: trackById;
        index as index;
        first as first
      ">
      <h2>{{ index + 1 }}. {{ product.name }}</h2>
      <span *ngIf="first">Featured first result</span>
    </article>
  `,
})
export class LegacyProductListComponent {
  readonly products = signal<readonly Product[]>([]);

  trackById(
    _index: number,
    product: Product,
  ): string {
    return product.id;
  }
}

5.2 Context variables

Legacy variableModern variableMeaning
index$indexZero-based position.
count$countTotal rendered items.
first$firstTrue for the first item.
last$lastTrue for the last item.
even$evenTrue for an even index.

5.3 Current @for syntax

modern @for block
@for (
  product of products();
  track product.id;
  let index = $index;
  let first = $first
) {
  <article>
    <h2>{{ index + 1 }}. {{ product.name }}</h2>

    @if (first) {
      <span>Featured first result</span>
    }
  </article>
} @empty {
  <p>No products matched your search.</p>
}

The track expression identifies data items so Angular can associate them with existing views and minimize DOM work when a collection changes. Stable business identifiers are generally preferable; $index is suitable for truly static collections, while identity uses object identity and can lead to less effective reconciliation.[5]

5.4 Identity must be stable

stable and unstable tracking
<!-- Good: stable identity -->
@for (user of users(); track user.id) {
  <app-user-row [user]="user" />
}

<!-- Risky: new random identity every render -->
@for (user of users(); track randomId()) {
  <app-user-row [user]="user" />
}

A tracking expression must describe the same logical item across updates. A volatile value causes Angular to discard and recreate views, losing local DOM and component state.

5.5 Side-by-side migration

NgFor to @for
<!-- Before -->
<li
  *ngFor="
    let item of items;
    trackBy: trackItem;
    index as i
  ">
  {{ i }} — {{ item.name }}
</li>

<!-- After -->
@for (item of items; track item.id; let i = $index) {
  <li>{{ i }} — {{ item.name }}</li>
}

6. ngSwitch and @switch

The legacy switch family uses [ngSwitch] on a container and structural *ngSwitchCase and *ngSwitchDefault views inside it. Every matching legacy case view is rendered, and unmatched static content within the switch container is preserved. The API family is deprecated since Angular 20 in favor of @switch.[8]

6.1 Legacy switch directives

legacy NgSwitch example
import {
  NgSwitch,
  NgSwitchCase,
  NgSwitchDefault,
} from '@angular/common';

@Component({
  selector: 'app-legacy-status',
  standalone: true,
  imports: [
    NgSwitch,
    NgSwitchCase,
    NgSwitchDefault,
  ],
  template: `
    <section [ngSwitch]="status()">
      <p *ngSwitchCase="'loading'">
        Loading…
      </p>

      <p *ngSwitchCase="'ready'">
        Ready
      </p>

      <p *ngSwitchCase="'error'">
        The request failed.
      </p>

      <p *ngSwitchDefault>
        Unknown status
      </p>
    </section>
  `,
})
export class LegacyStatusComponent {
  readonly status =
    signal<'loading' | 'ready' | 'error'>(
      'loading',
    );
}

6.2 Current @switch block

modern @switch block
@switch (status()) {
  @case ('loading') {
    <p>Loading…</p>
  }

  @case ('ready') {
    <p>Ready</p>
  }

  @case ('error') {
    <p>The request failed.</p>
  }

  @default {
    <p>Unknown status</p>
  }
}

@switch compares with strict equality, has no fallthrough, and supports consecutive @case clauses that share one block. It can optionally provide @default. Modern Angular also supports exhaustive checking for union types when the switched value is a template variable and the template uses the documented @default never form.[5]

6.3 Group several cases

consecutive modern cases
@switch (role()) {
  @case ('owner')
  @case ('administrator') {
    <app-admin-tools />
  }

  @case ('editor') {
    <app-editor-tools />
  }

  @default {
    <app-read-only-view />
  }
}

7. NgClass

NgClass adds and removes CSS classes on its host. It accepts a class string, string array, Set<string>, or an object whose keys are class names and whose values determine inclusion.[9]

7.1 Supported binding forms

NgClass object form
import { NgClass } from '@angular/common';

@Component({
  selector: 'app-status-card',
  standalone: true,
  imports: [NgClass],
  template: `
    <article
      class="card"
      [ngClass]="{
        'card--selected': selected(),
        'card--disabled': disabled(),
        'card--warning': severity() === 'warning'
      }">
      ...
    </article>
  `,
})
export class StatusCardComponent {
  readonly selected = signal(false);
  readonly disabled = signal(false);
  readonly severity =
    signal<'normal' | 'warning'>('normal');
}
string, array, and Set forms
<div [ngClass]="'compact elevated'">...</div>
<div [ngClass]="['compact', 'elevated']">...</div>
<div [ngClass]="classSet()">...</div>

7.2 Prefer native class binding for most new code

class binding alternatives
<!-- Preferred for a small, explicit set -->
<article
  class="card"
  [class.card--selected]="selected()"
  [class.card--disabled]="disabled()">
  ...
</article>

<!-- Aggregate built-in class binding -->
<article
  class="card"
  [class]="{
    'card--selected': selected(),
    'card--disabled': disabled()
  }">
  ...
</article>

The current Angular style guide prefers class bindings over NgClass because the syntax aligns more directly with HTML and avoids the additional directive cost. NgClass remains useful in existing code and when its accepted input forms fit an established API.[1][15]

7.3 Replace bound collections when they change

immutable class-map update
readonly classes = signal<
  Readonly<Record<string, boolean>>
>({
  selected: false,
});

select(): void {
  this.classes.update(current => ({
    ...current,
    selected: true,
  }));
}

8. NgStyle

NgStyle updates inline styles from an object map. Keys may include CSS property names and optional unit suffixes, while values provide the applied style values.[10]

8.1 Multiple dynamic styles

NgStyle example
import { NgStyle } from '@angular/common';

@Component({
  selector: 'app-progress-bar',
  standalone: true,
  imports: [NgStyle],
  template: `
    <div
      class="progress"
      [ngStyle]="{
        '--progress': percentage() + '%',
        'height.px': thickness(),
        'opacity': disabled() ? 0.5 : 1
      }">
    </div>
  `,
})
export class ProgressBarComponent {
  readonly percentage = signal(35);
  readonly thickness = signal(8);
  readonly disabled = signal(false);
}

8.2 Prefer style bindings for new code

style binding alternative
<div
  [style.--progress]="percentage() + '%'"
  [style.height.px]="thickness()"
  [style.opacity]="disabled() ? 0.5 : 1">
</div>

The Angular style guide recommends built-in style binding over NgStyle for readability and lower directive overhead. Individual style bindings also make units and affected properties immediately visible.[1][15]

Inline styles are not a replacement for CSS architecture Bind values that are genuinely dynamic. Put stable presentation, responsive rules, interaction states, and design-system tokens in CSS classes and custom properties.

9. Other useful built-in directives

9.1 NgTemplateOutlet

NgTemplateOutlet instantiates a prepared TemplateRef with an optional context and injector. The $implicit context property is available to an unassigned let variable.[28]

NgTemplateOutlet with context
import { NgTemplateOutlet } from '@angular/common';

@Component({
  selector: 'app-list-shell',
  standalone: true,
  imports: [NgTemplateOutlet],
  template: `
    <ng-template #row let-item let-index="index">
      <p>{{ index + 1 }}. {{ item.name }}</p>
    </ng-template>

    @for (item of items(); track item.id; let i = $index) {
      <ng-container
        [ngTemplateOutlet]="row"
        [ngTemplateOutletContext]="{
          $implicit: item,
          index: i
        }" />
    }
  `,
})
export class ListShellComponent {
  readonly items = signal<readonly Item[]>([]);
}

9.2 NgComponentOutlet

NgComponentOutlet declaratively instantiates a component type and inserts its host view. Inputs, injectors, environment injectors, projected content, and the created component instance can be configured through its API.[29]

dynamic component outlet
import { NgComponentOutlet } from '@angular/common';

@Component({
  selector: 'app-widget-host',
  standalone: true,
  imports: [NgComponentOutlet],
  template: `
    <ng-container
      *ngComponentOutlet="
        widgetType();
        inputs: widgetInputs()
      " />
  `,
})
export class WidgetHostComponent {
  readonly widgetType =
    signal<Type<unknown> | null>(null);

  readonly widgetInputs =
    signal<Record<string, unknown>>({});
}

9.3 ngNonBindable

display Angular syntax literally
<pre ngNonBindable>
  Angular interpolation looks like {{ expression }}.
</pre>

ngNonBindable disables Angular binding and directive processing for an element’s descendants, which is useful in documentation and code examples.[3]

10. Custom attribute directives

An attribute directive packages host behavior under a selector such as [appHighlight]. Current guidance recommends ordinary template bindings for one-off behavior and a directive when the behavior should be reusable. Application-specific selector prefixes reduce collisions with native attributes and third-party directives.[3][15]

10.1 Modern host-metadata directive

highlight.directive.ts
import {
  Directive,
  input,
  signal,
} from '@angular/core';

@Directive({
  selector: '[appHighlight]',
  host: {
    '[style.backgroundColor]':
      'active() ? color() : null',
    '[class.app-highlight]': 'active()',
    '[attr.aria-description]':
      'active() ? description() : null',

    '(mouseenter)': 'activate()',
    '(mouseleave)': 'deactivate()',
    '(focusin)': 'activate()',
    '(focusout)': 'deactivate()',
  },
})
export class HighlightDirective {
  readonly color = input('gold', {
    alias: 'appHighlight',
  });

  readonly description = input(
    'Highlighted content',
    {
      alias: 'appHighlightDescription',
    },
  );

  protected readonly active = signal(false);

  protected activate(): void {
    this.active.set(true);
  }

  protected deactivate(): void {
    this.active.set(false);
  }
}
apply the attribute directive
<p
  appHighlight="lightblue"
  appHighlightDescription="Important account notice"
  tabindex="0">
  Review your account details.
</p>

The directive exposes input signals and declares host property, attribute, class, style, and event bindings in the decorator’s host object. Host bindings use the same binding syntax as component templates.[13][30]

10.2 Selector/input shorthand

input alias matches selector
readonly color = input('gold', {
  alias: 'appHighlight',
});
bind a value through the selector input
<p [appHighlight]="selectedColor()">
  Dynamic color
</p>

Giving an input the same public name as the selector allows the directive attribute itself to carry a value. Secondary inputs commonly share the selector prefix, such as appHighlightDescription.

10.3 Dependency injection on the host element

inject a co-located directive
@Directive({
  selector: '[appFieldErrors]',
})
export class FieldErrorsDirective {
  private readonly control = inject(NgControl, {
    self: true,
    optional: true,
  });

  readonly invalid = computed(
    () => !!this.control?.invalid,
  );
}

A directive instance participates in the host element’s injector. It can resolve services and other directives available on that element or through its injector ancestry, subject to dependency-injection modifiers.

11. HostListener, HostBinding, and host metadata

@HostListener declares a host or global DOM event listener. @HostBinding binds a class member or getter to a host property, attribute, class, or style. Both APIs remain available, but current Angular documentation says to prefer the decorator metadata host property and describes the decorators as retained for backwards compatibility.[11][12][13]

11.1 Classic decorator form

HostListener and HostBinding
import {
  Directive,
  HostBinding,
  HostListener,
  Input,
} from '@angular/core';

@Directive({
  selector: '[appLegacyHighlight]',
})
export class LegacyHighlightDirective {
  @Input('appLegacyHighlight')
  color = 'gold';

  @HostBinding('class.app-highlight')
  active = false;

  @HostBinding('style.backgroundColor')
  get backgroundColor(): string | null {
    return this.active ? this.color : null;
  }

  @HostListener('mouseenter')
  onPointerEnter(): void {
    this.active = true;
  }

  @HostListener('mouseleave')
  onPointerLeave(): void {
    this.active = false;
  }
}

11.2 Preferred host-metadata equivalent

preferred host metadata
@Directive({
  selector: '[appHighlight]',
  host: {
    '[class.app-highlight]': 'active()',
    '[style.backgroundColor]':
      'active() ? color() : null',
    '(mouseenter)': 'active.set(true)',
    '(mouseleave)': 'active.set(false)',
  },
})
export class HighlightDirective {
  readonly color = input('gold', {
    alias: 'appHighlight',
  });

  protected readonly active = signal(false);
}

11.3 Event arguments and false

HostListener return value
@Directive({
  selector: '[appConfirmClick]',
})
export class ConfirmClickDirective {
  @HostListener('click', ['$event'])
  confirm(event: MouseEvent): boolean {
    return window.confirm(
      'Continue with this action?',
    );
  }
}

@HostListener accepts an event name and argument expressions such as $event. If a host-listener handler returns false, Angular applies preventDefault to the bound event.[11]

11.4 Global event targets

global host event
@Directive({
  selector: '[appEscapeCloses]',
  host: {
    '(document:keydown.escape)':
      'closed.emit()',
  },
})
export class EscapeClosesDirective {
  readonly closed = output<void>();
}

Host event names can use document:, window:, or body: prefixes. Global listeners should represent a focused behavior and must not make every directive instance compete for the same shortcut without a clear activation policy.[13]

11.5 Host-binding collisions

When a template binding and a component host binding target the same property, Angular resolves collisions according to whether the competing values are static or dynamic. If both are dynamic, the component’s host binding wins. Avoid depending on subtle collision rules; expose an input or choose a non-conflicting host property when consumers should control the value.[13]

12. Custom structural directives

A structural directive receives a TemplateRef representing the content of its host template and a ViewContainerRef representing the insertion location. It chooses whether, when, and with what context to create an embedded view.[4][24][25]

12.1 Permission-gated rendering

if-permission.directive.ts
import {
  Directive,
  EmbeddedViewRef,
  TemplateRef,
  ViewContainerRef,
  effect,
  inject,
  input,
} from '@angular/core';

export type Permission =
  | 'orders.read'
  | 'orders.edit'
  | 'users.manage';

@Directive({
  selector: '[appIfPermission]',
})
export class IfPermissionDirective {
  private readonly template =
    inject(TemplateRef<unknown>);

  private readonly container =
    inject(ViewContainerRef);

  private readonly permissions =
    inject(PermissionStore);

  readonly appIfPermission =
    input.required<Permission>();

  private view:
    EmbeddedViewRef<unknown> | null = null;

  constructor() {
    effect(() => {
      const allowed = this.permissions.has(
        this.appIfPermission(),
      );

      if (allowed && !this.view) {
        this.view =
          this.container.createEmbeddedView(
            this.template,
          );
      } else if (!allowed && this.view) {
        this.container.clear();
        this.view = null;
      }
    });
  }
}
permission structural directive
<button
  *appIfPermission="'orders.edit'"
  type="button">
  Edit order
</button>

The effect is created in the directive’s component-tree context and tracks both the permission input and any signals read by PermissionStore.has. Component effects may safely create and destroy dependent views during Angular synchronization.[31]

Visibility is not authorization A structural directive can improve the interface by hiding unavailable actions, but it cannot secure an operation. The server must independently enforce permissions.

12.2 Structural microsyntax

The asterisk shorthand maps a naked expression to the directive’s selector input, maps key-expression pairs to prefixed inputs, and maps let declarations to properties of the embedded-view context. For a selector select, the key from maps to selectFrom.[4]

microsyntax translation
<!-- Shorthand -->
<p *select="let data; from: source">
  {{ data }}
</p>

<!-- Expanded form -->
<ng-template
  select
  let-data
  [selectFrom]="source">
  <p>{{ data }}</p>
</ng-template>

12.3 A context-providing appLet directive

let.directive.ts
import {
  Directive,
  EmbeddedViewRef,
  TemplateRef,
  ViewContainerRef,
  effect,
  inject,
  input,
} from '@angular/core';

export interface LetContext<T> {
  $implicit: T;
  appLet: T;
}

@Directive({
  selector: '[appLet]',
})
export class LetDirective<T> {
  private readonly template =
    inject(TemplateRef<LetContext<T>>);

  private readonly container =
    inject(ViewContainerRef);

  readonly appLet = input.required<T>();

  private view:
    EmbeddedViewRef<LetContext<T>> | null = null;

  constructor() {
    effect(() => {
      const value = this.appLet();

      if (!this.view) {
        this.view =
          this.container.createEmbeddedView(
            this.template,
            {
              $implicit: value,
              appLet: value,
            },
          );
        return;
      }

      this.view.context.$implicit = value;
      this.view.context.appLet = value;
      this.view.detectChanges();
    });
  }

  static ngTemplateContextGuard<T>(
    _directive: LetDirective<T>,
    context: unknown,
  ): context is LetContext<T> {
    return true;
  }
}
appLet usage
<ng-container
  *appLet="
    expensiveViewModel();
    as viewModel
  ">
  <h2>{{ viewModel.title }}</h2>
  <p>{{ viewModel.summary }}</p>
</ng-container>

The static context guard tells Angular’s template type checker that values exposed by the embedded context have type T. Structural directives can also define input guards for type narrowing based on the bound expression.[4][32]

12.4 One asterisk directive per element

nest structural behavior
<!-- Invalid shorthand composition -->
<li
  *appIfPermission="'orders.read'"
  *appLet="order as current">
</li>

<!-- Explicit nesting -->
<ng-container
  *appIfPermission="'orders.read'">
  <li *appLet="order as current">
    {{ current.number }}
  </li>
</ng-container>

Only one structural directive can use shorthand on an element because there is only one generated template host. Use <ng-container> or explicit nested <ng-template> elements to define the ordering.[4][26]

13. Directive composition

The directive composition API applies directives to a component or directive host at compile time through hostDirectives. Host directives are instantiated even though consumers do not write their selectors, and their lifecycle hooks run before the host component or directive hooks.[14]

focusable.directive.ts
@Directive({
  selector: '[appFocusable]',
  host: {
    '[attr.tabindex]': 'disabled() ? -1 : 0',
    '[class.focus-ring]': 'focused()',
    '(focus)': 'focused.set(true)',
    '(blur)': 'focused.set(false)',
  },
})
export class FocusableDirective {
  readonly disabled = input(false);
  protected readonly focused = signal(false);
}
compose host directives
@Directive({
  selector: '[appPressable]',
  hostDirectives: [
    {
      directive: FocusableDirective,
      inputs: ['disabled: pressDisabled'],
    },
  ],
  host: {
    'role': 'button',
    '(keydown.enter)': 'pressed.emit()',
    '(click)': 'pressed.emit()',
  },
})
export class PressableDirective {
  readonly pressed = output<void>();
}
consumer-facing composed API
<div
  appPressable
  [pressDisabled]="saving()"
  (pressed)="save()">
  Save
</div>

By default, a host directive’s inputs and outputs are not exposed through the host’s public template API. The composition metadata selectively aliases and exposes those contracts.[14]

13.1 Composition limitations

  • Host directives are statically known at compilation time; they are not added dynamically at runtime.
  • Their selectors are ignored when they are applied through hostDirectives.
  • A composed directive must be standalone.
  • Use composition for cohesive reusable behavior, not to accumulate unrelated responsibilities on one host.[14]

14. DOM access, rendering, and security

Attribute directives sometimes need access to their host through ElementRef. Angular warns that direct DOM access is a last resort and should be combined with the platform’s security guidance. Direct DOM APIs may be unavailable during server rendering and can bypass Angular’s normal rendering abstractions and sanitization paths.[27][33][34]

14.1 Prefer declarative host bindings

declarative host behavior
@Directive({
  selector: '[appInvalidState]',
  host: {
    '[class.invalid]': 'invalid()',
    '[attr.aria-invalid]': 'invalid()',
  },
})
export class InvalidStateDirective {
  readonly invalid = input(false, {
    alias: 'appInvalidState',
  });
}

Host metadata works across Angular renderers, participates in change detection, and keeps the directive’s DOM contract visible in its metadata.

14.2 Use Renderer2 for imperative rendering integration

imperative host measurement
@Directive({
  selector: '[appMeasured]',
})
export class MeasuredDirective {
  private readonly element =
    inject<ElementRef<HTMLElement>>(ElementRef);

  private readonly renderer = inject(Renderer2);

  private readonly destroyRef = inject(DestroyRef);

  constructor() {
    afterNextRender(() => {
      const width =
        this.element.nativeElement
          .getBoundingClientRect()
          .width;

      this.renderer.setAttribute(
        this.element.nativeElement,
        'data-width',
        String(Math.round(width)),
      );
    });
  }
}

DOM measurement should occur only in browser rendering and after Angular has rendered the relevant element. Renderer2 supports renderer-aware mutation, including style encapsulation for nodes it creates, but it does not automatically make an unsafe string trustworthy.[27][33][34]

14.3 Do not compile untrusted templates

Angular templates are executable code. Do not construct directive markup, event expressions, or templates from untrusted strings. Bind untrusted values into fixed templates and rely on Angular’s context-sensitive sanitization; avoid bypass APIs unless the trust boundary is rigorously established.[34]

15. Directive lifecycle and cleanup

Directive classes can implement the same lifecycle interfaces used by components, including initialization, input-change handling, custom checks, and destruction. Event listeners declared through Angular host metadata are managed with the directive instance, while manually registered resources require explicit cleanup.[2][13]

15.1 Clean up external listeners

effect cleanup in a directive
@Directive({
  selector: '[appMediaQuery]',
})
export class MediaQueryDirective {
  private readonly destroyRef = inject(DestroyRef);

  readonly query = input(
    '(prefers-reduced-motion: reduce)',
    {
      alias: 'appMediaQuery',
    },
  );

  constructor() {
    effect(onCleanup => {
      const media = matchMedia(this.query());

      const update = (): void => {
        // Respond to media.matches.
      };

      media.addEventListener('change', update);
      update();

      onCleanup(() => {
        media.removeEventListener(
          'change',
          update,
        );
      });
    });
  }
}

An effect cleanup callback runs before the effect reruns and when the effect is destroyed, making it suitable for resources associated with a reactive input. For non-reactive resources, DestroyRef.onDestroy provides explicit lifecycle cleanup.[31]

16. Testing directives

DOM-oriented attribute directives are best tested through a small host component that exercises their supported bindings and events. Angular’s testing guide recommends querying matching hosts with By.directive, inspecting rendered styles and properties, and obtaining a directive instance from the host element’s injector.[35]

16.3 High-value cases

  • The selector attaches only to intended host elements.
  • Default and explicitly bound input values produce the correct host state.
  • Keyboard, pointer, focus, and global event handling works and cleans up correctly.
  • Accessibility attributes remain synchronized with visual state.
  • A structural directive creates no duplicate embedded views during repeated updates.
  • Context variables and template guards infer the intended strict-template types.
  • Host-directive input and output aliases expose only the intended public API.

17. Production design patterns

17.1 Directive or component?

RequirementUse
Own markup and layoutComponent.
Enhance many kinds of existing hostsAttribute directive.
Create or suppress embedded viewsStructural directive.
One local class, style, property, or eventTemplate binding.
Common conditional or list renderingBuilt-in @if or @for.
Reusable cluster of host behaviorsHost directive composition.

17.2 Name behavior, not implementation

semantic directive naming
<!-- Better: semantic capability -->
<button appCopyToClipboard>Copy</button>

<!-- Weaker: implementation detail -->
<button appClickListenerWithToast>
  Copy
</button>

A selector should communicate what the host gains. Follow the application prefix and camel-case attribute-selector convention to avoid collisions.[15]

17.3 Keep directives focused on presentation behavior

Directive code should primarily relate to host behavior and rendering. Move business rules, API access, and reusable data transformations into services or plain functions and inject the resulting capability where needed.[15]

17.4 Treat inputs and outputs as a public API

Use required inputs when the directive cannot operate without a value, defaults when there is a sensible behavior, and prefixed secondary inputs for structural microsyntax. Keep signal inputs and outputs readonly so the class does not replace Angular-managed signal objects.[15][30]

17.5 Reuse embedded views when possible

A structural directive should avoid clearing and recreating a view when only the context value changed. Updating an existing EmbeddedViewRef preserves child component and DOM state and reduces allocation.

17.6 Support strict templates

Generic structural directives should provide context guards, and narrowing directives should provide input guards. With strictTemplates, Angular can infer directive generics, input compatibility, event types, and embedded-view context types.[4][32]

18. Common pitfalls

PitfallConsequenceBetter approach
Writing new *ngIf, *ngFor, or ngSwitch code The application adopts APIs deprecated since Angular 20. Use @if, @for, and @switch for new code.[6][7][8]
Two asterisk directives on one element There is no unambiguous single template expansion order. Nest ng-container or ng-template layers.[4][26]
Using NgClass or NgStyle for two simple bindings Extra syntax and directive overhead. Use class and style binding.[15]
Creating a directive for one local event Indirection without reuse. Use an ordinary template listener.[3]
Directly writing unsanitized HTML through nativeElement Angular’s binding sanitization is bypassed. Use fixed templates and safe bindings.[34]
Unstable @for tracking Views and component state are unnecessarily recreated. Track a stable data key.[5]
Recreating an embedded view on every input change Child state is lost and rendering work increases. Update the existing view context when structure is unchanged.
Assuming directive outputs bubble Ancestors never receive the custom event automatically. Listen directly or forward explicitly.
Using @HostBinding and @HostListener in new code by habit The code ignores current host-metadata guidance. Prefer the host object; understand decorators for existing code.[11][12][13]
Hiding authorization behind a structural directive Client-side visibility is mistaken for security. Authorize the operation on the server.

19. Complete example: accessible selectable rows

This example combines an attribute directive, host metadata, signal inputs and outputs, keyboard interaction, directive composition, modern control flow, class bindings, and a parent-owned selection model.

selectable-item.ts
export interface SelectableItem {
  readonly id: string;
  readonly label: string;
  readonly disabled?: boolean;
}
selectable.directive.ts
import {
  Directive,
  input,
  output,
} from '@angular/core';

@Directive({
  selector: '[appSelectable]',
  host: {
    'role': 'option',
    '[attr.aria-selected]': 'selected()',
    '[attr.aria-disabled]': 'disabled()',
    '[attr.tabindex]':
      'disabled() ? -1 : 0',

    '[class.selectable]': 'true',
    '[class.selectable--selected]':
      'selected()',
    '[class.selectable--disabled]':
      'disabled()',

    '(click)': 'activate()',
    '(keydown.enter)': 'activate()',
    '(keydown.space)': 'activate($event)',
  },
})
export class SelectableDirective {
  readonly itemId =
    input.required<string>({
      alias: 'appSelectable',
    });

  readonly selected = input(false);
  readonly disabled = input(false);

  readonly selectedChange =
    output<string>();

  protected activate(
    event?: KeyboardEvent,
  ): void {
    event?.preventDefault();

    if (!this.disabled()) {
      this.selectedChange.emit(
        this.itemId(),
      );
    }
  }
}
selectable-list.component.ts
import {
  Component,
  computed,
  input,
  model,
} from '@angular/core';
import {
  SelectableDirective,
} from './selectable.directive';

@Component({
  selector: 'app-selectable-list',
  standalone: true,
  imports: [SelectableDirective],
  host: {
    'role': 'listbox',
    '[attr.aria-label]': 'label()',
  },
  template: `
    @for (item of items(); track item.id) {
      <div
        [appSelectable]="item.id"
        [selected]="selection().has(item.id)"
        [disabled]="item.disabled ?? false"
        (selectedChange)="toggle($event)">
        {{ item.label }}
      </div>
    } @empty {
      <p>No options are available.</p>
    }
  `,
})
export class SelectableListComponent {
  readonly label = input('Options');

  readonly items =
    input.required<
      readonly SelectableItem[]
    >();

  readonly selection =
    model<ReadonlySet<string>>(
      new Set<string>(),
    );

  protected toggle(id: string): void {
    this.selection.update(current => {
      const next = new Set(current);

      if (next.has(id)) {
        next.delete(id);
      } else {
        next.add(id);
      }

      return next;
    });
  }
}
preferences.component.ts
@Component({
  selector: 'app-preferences',
  standalone: true,
  imports: [SelectableListComponent],
  template: `
    <app-selectable-list
      label="Notification channels"
      [items]="channels"
      [(selection)]="selectedChannels" />

    <p>
      Selected:
      {{ selectedChannels().size }}
    </p>
  `,
})
export class PreferencesComponent {
  readonly channels:
    readonly SelectableItem[] = [
      { id: 'email', label: 'Email' },
      { id: 'sms', label: 'SMS' },
      {
        id: 'push',
        label: 'Push notifications',
        disabled: true,
      },
    ];

  readonly selectedChannels =
    signal<ReadonlySet<string>>(
      new Set(['email']),
    );
}

The attribute directive owns reusable row behavior. The component owns list structure and selection state. @for tracks stable item IDs, and the parent uses a model input for the editable selection value.

22. Conclusion

Angular directives attach reusable behavior to hosts and templates. Attribute directives enhance an existing element through inputs, outputs, dependency injection, and host bindings. Structural directives use template and view-container abstractions to control embedded views. Components remain the directive form that owns markup.[1][2][3][4]

Modern Angular separates common control flow from custom structural behavior. Use @if, @for, and @switch for ordinary template branching and iteration; reserve custom structural directives for domain-specific rendering abstractions. Prefer class and style bindings over NgClass and NgStyle in new code, and prefer the decorator host metadata over HostListener and HostBinding while retaining fluency with those APIs for established codebases.[5][6][7][8][13][15]
