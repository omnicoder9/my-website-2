01the problem

The tax on being big

Every Angular application that survives long enough acquires a tax collector. It is not the framework. It is the set of dependencies that accumulate between the parts of the codebase while nobody is looking, and the tax is levied in the currency an engineering organisation actually cares about: how long it takes one team to ship a change without breaking another team's screen.

The symptoms are consistent enough across companies to be diagnostic. A single-line change to a shared formatting helper triggers a forty-minute CI run and touches eleven projects. A component library upgrade is blocked for a quarter because three teams inherited a private Sass variable that was never public API. Two features fetch the same customer record through two different services, with two different shapes, and disagree about whether a suspended account counts as active. A new engineer's first pull request is rejected not because the code is wrong but because it imported the right symbol from the wrong path. Nobody in any of these stories wrote bad code. They wrote code without a rule about what may import what.

This is not an Angular-specific failure, and it is much older than Angular. Parnas argued in 1972 that the criterion for decomposing a system into modules should be the concealment of a design decision that is likely to change, not the flowchart of processing steps 1 — advice that most frontend codebases invert by organising directories around kinds of file. Lehman's laws describe the rest: a program in use undergoes continuing change, and its complexity increases unless work is explicitly done to reduce it 2. Conway supplies the final piece, which is that the structure you get is the structure of the communication paths in the organisation that built it, whether or not anyone designed it 3. Enterprise Angular architecture is mostly the practice of making those three observations operational: decide what may change independently, spend real effort holding the boundaries in place, and align the boundaries with the teams 4.

What follows assumes an expert reader and a specific baseline: Angular v22, released 3 June 2026, in which signal forms, asynchronous signal APIs and Angular Aria are stable and zoneless change detection is the default for new workspaces 5,6,7. It also assumes an application in the range where the tax is real — roughly, more than three teams, more than a hundred routes, a lifespan measured in years, and a compliance obligation that someone in legal can name. Below that threshold most of this is overhead. Above it, none of it is optional.

The argument is organised around a single question that every section answers a different slice of: what may import what? Import edges are the only thing in a TypeScript codebase that is simultaneously a compile-time fact, a build-time cost, a runtime bundle boundary, and a social contract between teams. Get the edges right and most of the other decisions become local. Get them wrong and no amount of state-management sophistication will save you.

Eighteen rules are stated along the way, each in the shape of a lint rule, because that is where most of them should end up. They are collected in §20, together with the configuration that enforces them.

02history

Twelve years of moving the composition unit

Angular's architectural advice has changed more than its API surface, and the changes are easier to follow if you track one variable: what is the smallest thing you can compose and lazily load?

AngularJS had angular.module(), a global registry with string-keyed dependency injection. Angular 2 replaced it with @NgModule, which owned three distinct concerns at once: template compilation scope, DI providers, and — after the router grew loadChildren — the lazy-loading boundary. Bundling those three concerns into one decorator was the defining architectural feature of Angular from 2016 to roughly 2022, and also its defining source of confusion, since a developer adding a component to a template had to reason about a file they were not editing.

Ivy (v9) decoupled compilation from module membership. Standalone components (v14, default from v19) removed the compilation-scope role from NgModules entirely; the Angular team's current position is unambiguous that new code should not use them at all, and the NgModules guide has been relegated to the "extended ecosystem" section of the documentation 8. Standalone APIs moved the DI role to bootstrapApplication and to route-level providers arrays 9, and the router had already taken over the lazy-loading role. The three concerns were finally separable.

What replaced NgModules as the enterprise unit of organisation was not another decorator. It was the library — a directory with its own index.ts, its own tsconfig path mapping, its own tags, and its own place in a dependency graph that a linter can check. That shift, which Nrwl's monorepo patterns pushed into the Angular mainstream from 2018 onward, is why so much of this article is about workspace layout rather than about Angular APIs 10.

Attempting zoneless before the components are signal-driven produces a long tail of views that silently fail to update 13.

03foundations

The unit of architecture is the import graph

A frontend architecture diagram is worth exactly as much as the linter that enforces it. The diagram on the wiki says features depend on data access, never the reverse; the import graph says what actually happens. Only one of those two is executable, and it is not the diagram.

Three properties make the import graph the right object to design against. First, it is total: every coupling between two pieces of TypeScript is an edge, and there are no informal couplings that escape it (a shared global, a monkey patch, and an InjectionToken all show up as imports of something). Second, it is checkable in milliseconds by tooling that already exists. Third, it is the thing the bundler uses, so decisions about the graph are simultaneously decisions about chunk boundaries and about what a user downloads before the first paint.

Two rules do most of the work.

R01One public API per library
rule
Every library exposes exactly one entry point (index.ts). No import may name a path inside another library.
enforced by
@nx/enforce-module-boundaries, or Sheriff's encapsulation check on barrel-less modules 14,15
buys
Freedom to restructure a library's internals without a workspace-wide search-and-replace; a reviewable diff whenever the surface changes.
costs
An index.ts to maintain, and the temptation to export everything from it, which converts the barrel into a fiction.
tell
Imports containing /src/lib/. Every one of them is a promise you did not intend to make.
R02Arrows point one way
rule
Library types form a partial order — shell → feature → {ui, data-access} → domain → util — and imports may only go downward.
enforced by
depConstraints keyed on a type:* tag 10
buys
Cycle-freedom by construction, a topological build order, and the ability to reason about a leaf library without reading its consumers.
costs
Occasional duplication when two layers genuinely want the same helper and neither should own it.
tell
A ui library that injects a service. It compiles, it works, and it has just made your presentational layer untestable without HTTP.

The dependency rule is the same one Martin states for layered systems and Cockburn states for ports and adapters: source-code dependencies point toward stability, and the volatile outer ring depends on the stable inner one rather than the reverse 16,17. Angular does not enforce it. TypeScript does not enforce it. A ninety-line ESLint configuration does.

Two subtleties are worth stating explicitly because they are where teams lose the thread.

Relative imports leak. A path like ../../feature-search/src/internal/search-state is an edge in the graph that no tsconfig alias sanctions, and many boundary checkers only inspect aliased specifiers. Configure the check to normalise relative paths against project roots, or ban parent-directory traversal past the library root outright. The checker in §08 flags these as relative-escape.

Types are edges too. import type { Invoice } from '@acme/billing/data-access' disappears at runtime, so it costs nothing in the bundle, but it is a full-weight coupling in every other sense: the moment the shape changes, your code changes. Boundary rules should treat type-only imports exactly like value imports. The bundle is not the only cost that matters.

04composition

What replaced the feature module

"Feature module" survives as vocabulary long after the @NgModule that gave it its name became legacy. What the phrase now denotes is a route subtree plus the providers it owns plus the code split that carries it — three things that used to travel in one decorator and now travel separately, which is an improvement precisely because it lets you vary them independently.

The modern shape of a feature is a Routes array exported from a library, loaded by the shell:

R04The route is the split point
rule
Code splitting happens at route boundaries by default; anything finer is a deliberate @defer decision with a measured payoff.
enforced by
loadComponent/loadChildren plus a bundle budget in angular.json that fails the build 18
buys
Predictable chunk boundaries that map onto the navigation model users already have, and an initial payload that does not grow when a distant team ships a feature.
costs
A round trip on first navigation to each area; mitigate with route preloading, not with eager bundling.
tell
An initial chunk that grows every sprint and a main.js nobody can attribute.

@defer operates one level below the route: it splits within a rendered view on a trigger such as on viewport, on interaction or on idle 18. The right mental model is that routes split by where the user is and defer blocks split by what the user has not looked at yet. A dashboard whose sixth widget is a charting library is the canonical case. A defer block around something that is visible on load is a net loss, and, as §17 covers, it has accessibility consequences that are easy to miss.

R05Providers live at the narrowest shared injector
rule
A dependency is provided at the narrowest injector that all of its consumers share: providedIn: 'root' only for genuinely application-wide state.
enforced by
Code review plus an architectural test that asserts which tokens appear in the root ApplicationConfig 9
buys
Lazy state that is created and discarded with its route; two tenants of the same component tree that cannot see each other's caches.
costs
You must know where a service is provided to know how many instances exist — the cost of hierarchical DI, and it is real.
tell
A store that resets when the user navigates away, or one that stubbornly does not.

The failure mode worth naming: a service marked providedIn: 'root' that is also listed in a lazy route's providers array yields two instances, one per injector, with the tree-shakable root instance quietly shadowed inside the subtree. This is not a bug in Angular; it is the documented resolution order 9. It is, however, one of the most reliable ways to lose two hours.

05organisation

Slicing by domain, not by file type

The Angular style guide's project-structure advice is short and, read carefully, quite strong: organise directories by feature area, and explicitly avoid directories named after kinds of code such as components, directives and services 19. That single instruction eliminates the most common enterprise layout — a top-level components/ folder with four hundred entries — and leaves open the harder question of what a "feature area" is.

Strategic domain-driven design supplies the answer that has held up best in Angular practice. Subdomains are identified by looking for coherent sets of business capabilities that share a vocabulary; a bounded context is the scope within which a term such as booking or invoice means exactly one thing; a context map records how the contexts relate 20. Steyer's adaptation of this to Angular workspaces — domains as columns, technical layers as rows, one library per populated cell — has become the de facto reference layout for large Angular codebases 21,22.

The discipline in the matrix is that the columns are the load-bearing structure. Rows can be refactored — merging a thin ui library into its feature is a one-afternoon change. Columns cannot: moving a concept from billing to booking means renegotiating what the words mean, and that conversation involves people who do not read TypeScript.

R03Domains talk through published contracts only
rule
A library in one domain may not import a library in another domain, except from that domain's api library.
enforced by
notDependOnLibsWithTags on scope:* tags, with an allow exception for @acme/*/api 14
buys
The freedom to restructure a domain's internals without a cross-team negotiation, and a single reviewable file when the contract does change.
costs
A curated api library per domain that somebody has to maintain, plus real pressure to keep it small.
tell
A pull request that touches libs/booking/** and libs/billing/** for the same reason.

How do you find the columns? Three heuristics, in order of reliability. Language boundaries: where the same noun means two different things, you have two contexts — "account" in identity and "account" in billing are not the same entity and should not share a type. Change correlation: mine the version-control history for files that change together; clusters that co-change but do not share a directory are telling you the current layout is wrong. Team boundaries: Conway's law is a constraint, not a warning 3, and Team Topologies' stream-aligned team is a workable unit of ownership for one column 4.

What does not work is deriving the columns from the backend's service topology. Backend services are decomposed for operational reasons — write throughput, storage engine, on-call rotation — that have no necessary relationship to how a user's task decomposes. A single booking screen that fans out to six services is a normal, healthy screen. Letting six services dictate six frontend domains is how you end up with a UI that makes the user do the orchestration.

Three notes on where teams get this wrong.

The ui/feature line is about injection, not about looks. A component is ui if its entire behaviour is determined by its inputs; it becomes feature the moment it injects anything with a network or a store behind it. This is why the boundary is checkable and why the Angular style guide's advice to keep components focused on presentation and to push validation rules and data transformations into separate functions or classes lands so cleanly on it 19.

domain is not a synonym for "interfaces". A domain library containing nothing but exported interface declarations is a symptom: the invariants that ought to live there have leaked upward into components. If an invoice cannot be voided after it has been paid is expressed as an *ngIf in a template, three screens will eventually disagree about it. Put it in a pure function in domain, test it without TestBed, and let every screen ask.

The api library is the pressure valve. Without it, R03 forces either total duplication between domains or a shared kernel that grows without limit. With it, cross-domain coupling is explicit, small, reviewable, and — because it is a separate library — versionable. Keep it to models, injection tokens and facade interfaces. The moment a component lands in an api library, the boundary has been renegotiated without anyone noticing.

The implementation lives in libs/billing/data-access and registers itself against the token in the billing shell. Booking imports the token and the types, never the implementation, and can be tested against a two-line fake. This is the same inversion that hexagonal architecture describes, expressed in Angular's injector 17.

07organisation

Shared libraries and the shared-kernel trap

Every workspace grows a shared column, and it is the single most reliable place for an architecture to rot. The mechanism is not mysterious. Shared code is, by construction, the code with the most consumers; every addition to it increases the blast radius of every future change to it; and the marginal cost of one more addition always looks like zero to the person making it.

Steyer's warning about the overgrown shared kernel is the standard formulation: prefer dedicated api libraries that expose a small, stable interface from one domain over promoting that code into shared 21. The practical version is a promotion rule with a number in it.

R06Shared means three
rule
Code moves into shared only when three or more domains already use a copy of it, and it carries no domain vocabulary.
enforced by
Review checklist plus a graph query: reject scope:shared libraries whose reverse-dependency count is below three 10
buys
A shared column that stays small enough to be genuinely stable, and duplication that stays where it belongs — in cheap, local code.
costs
Two or three copies of a helper live in the workspace for a while. This is correct; premature sharing is more expensive than duplication.
tell
A file named shared/utils/index.ts exporting more than a dozen unrelated symbols, or a shared type with a field only one domain sets.

Three failure patterns are worth naming individually because they wear different disguises.

The shared model. One Customer interface used by identity, billing and support. It starts with six fields, acquires creditLimit for billing and lastTicketId for support, and every consumer now compiles against fields it must ignore. The DDD answer is that these are three different concepts that happen to share a name, and the shared thing is at most the identifier 20. Share CustomerId, not Customer.

The shared component with a mode flag. A card that takes variant: 'booking' | 'billing' | 'support' is three components wearing a trench coat, and every future change to one variant risks the other two. Either the variance is presentational — in which case it belongs in the design system as a documented, tokenised variant (§16) — or it is behavioural, in which case each domain should own its own component and share only the primitives beneath it.

The shared service that knows about a domain. The banTransitiveDependencies and bannedExternalImports options exist partly for this: a scope:shared library that imports @angular/material, or that mentions an invoice, has stopped being shared 26.

Versioning deserves a word. Inside a monorepo, shared libraries are usually consumed by path mapping and have no version at all — the version is the commit, which is exactly the property that makes atomic cross-library refactors possible. That property evaporates the moment a library is published to a registry and consumed by a repository you do not control. At that point semantic versioning is not optional, a deprecation window must be stated in calendar time rather than in versions, and automated dependency updates become the mechanism that keeps consumers within the support window 27,28.

08enforcement

Making the rules executable

An architecture that lives in a document decays at the rate at which people join and leave the team. An architecture that lives in a lint rule decays at the rate at which people disable lint rules, which is much slower and, crucially, leaves a diff.

Two tools dominate. In an Nx workspace, @nx/enforce-module-boundaries reads tags from each project's configuration and evaluates a depConstraints array; projects with no tags may depend on nothing, which makes the default fail-closed 10,14. In a plain Angular CLI workspace — or anywhere you want folder-level rather than project-level granularity — Sheriff assigns tags from path patterns, enforces module encapsulation through index.ts (or, in barrel-less mode, through an internal directory), and reports through ESLint or its own CLI with zero runtime dependencies beyond TypeScript 29,15.

The equivalent in Sheriff derives tags from the directory layout rather than from per-project configuration, which suits a single-application workspace that has grown modules rather than libraries:

Two options repay a closer look. allSourceTags lets a constraint match on a conjunction of tags, which is what you need once a second dimension appears — a platform:server library and a platform:web library of the same type should not have the same permissions 30. And banTransitiveDependencies, disabled by default but recommended, stops a project from importing something it never declared and only receives by accident through another library's dependency 26,31.

09delivery

Monorepo mechanics and the blast radius

The monorepo is not the architecture; it is the substrate that makes the architecture cheap to enforce. Its concrete benefits are narrow and worth stating precisely, because teams adopt it for the wrong ones.

What it buys: atomic cross-library refactors (a rename and all its call sites in one commit); a single dependency resolution, which eliminates the class of bug where two libraries disagree about the RxJS version; one place for the boundary rules; and a task graph that lets tooling skip work it can prove is unnecessary 10.

What it does not buy: any reduction in coupling. A monorepo with no boundary rules is strictly worse than several repositories, because the friction that would have stopped a cross-team import has been removed and nothing has replaced it.

Three mechanics deserve attention at enterprise scale.

Affected computation is only as good as the graph. Dynamic imports behind a string variable, runtime configuration that selects an implementation, and assets referenced from templates are all edges the static graph may not see. When CI passes and production breaks, an invisible edge is the first hypothesis.

Caching is a correctness feature before it is a speed feature. A task cache keyed on inputs forces you to declare what a task's inputs actually are, which surfaces the tasks that secretly depend on the wall clock, the network or the machine. Those tasks were already flaky; the cache just made the flakiness legible.

Ownership must be expressed in the same place as the boundaries. A CODEOWNERS file whose paths line up with the domain columns turns every cross-domain pull request into an automatic review request for the affected team 33. When ownership paths and boundary tags disagree, one of them is lying.

10delivery

When the deployable should split

Micro frontends are a deployment strategy sold as an architecture. The distinction matters, because the architectural work — bounded contexts, published contracts, one-way dependencies — is exactly the same work whether the result ships as one bundle or twelve. What federation adds is the ability for teams to release on independent cadences, and what it charges for that is paid in duplicated framework code, version skew, cross-application debugging, and a shared-state problem that has no clean answer 34.

The honest test is a question about release, not about size: can team B ship on Tuesday without team A's code being green? If the answer must be yes — because of regulatory certification per module, or because one area is maintained by a vendor, or because the release trains genuinely cannot be merged — federation earns its cost. If the answer is merely "it would be nice", a modulith with enforced boundaries gives you most of the benefit and none of the runtime tax 22.

When you do split, the current Angular-native mechanism is Native Federation. It reimplements Module Federation's mental model — hosts, remotes, shared dependencies with version negotiation — on top of browser standards (ECMAScript modules and import maps) rather than on top of a specific bundler, and it delegates to Angular's esbuild-based application builder so that federated applications stay on the CLI's supported path 35,36,37,38. The predecessor plugin remains available for webpack-based workspaces 39, but with webpack-based builders deprecated in v22 5, new work should not start there 40.

Four hazards account for most federation incidents.

Singleton drift. @angular/core, the router and any authentication service must be singletons across host and remotes, or you get two router instances fighting over the URL and two token caches disagreeing about expiry. Declare them singleton with strict version checks and treat a version mismatch as a build failure, not a runtime warning.

Version skew as a first-class state. Remotes deploy independently, which means at any instant a host may load a remote built against an older contract. Every federated boundary needs a compatibility policy — usually: the contract is additive-only within a major version, and the host tolerates unknown fields.

Styling collisions. Two remotes shipping different versions of the design system produce visual drift that no test catches. Ship design tokens as CSS custom properties resolved by the host (§16), not as a bundled stylesheet per remote.

Cross-application accessibility. Focus management, live regions and landmark structure are page-level concerns, and no remote owns the page. The host must own the document outline and the post-navigation focus contract (§17), with remotes rendering into it. This is the single most commonly skipped piece of federation work.

11boundaries

The API abstraction layer

The network is the largest source of change your application does not control. A backend team renames a field, adds a pagination envelope, splits one endpoint into two, or migrates from a REST resource to a query API — and in a codebase without an abstraction layer, each of those events produces a diff that touches components.

The remedy is old and has a name from domain-driven design: an anti-corruption layer, a translation boundary whose job is to keep another system's model out of yours 20. In Angular it has a natural home, because the library taxonomy already gives it one.

R07Only data-access speaks HTTP
rule

buys
One place to add retries, caching, correlation ids and auth; components that are testable without a network double.
costs
A layer of indirection between a component and its data, which feels like ceremony until the second consumer arrives.
tell
A component with a subscribe() in ngOnInit and a URL string in its constructor.
R08Wire shapes stay in the mapper

Two design decisions inside the mapper repay attention. Parse, do not validate at the edge and hope. PlainDate.parse throwing on a malformed date converts a class of runtime mystery into a failure at a known location with a known correlation id. Make illegal states unrepresentable downstream. Mapping 'PD' | 'DU' | 'VD' onto a domain union means the exhaustiveness checker, not a code reviewer, catches the day a fourth status appears — provided strict is on, which at this scale it must be 42,43.

Generate the client, hand-write the model

If the backend publishes an OpenAPI description 44, generate the transport layer from it and check the generated code into a directory nobody edits. The three practical options for Angular are the vendor-neutral openapi-generator with its typescript-angular target 45, ng-openapi-gen 46, and the newer ng-openapi, which emits inject()-based services, provider functions and optional httpResource bindings rather than NgModule scaffolding 47. All three generate DTOs and clients. None of them can generate your domain model, because your domain model encodes decisions the API description does not contain. Generate the left half of the pipeline; write the right half.

Reads, writes, and where signals fit

Since v22 the resource APIs are stable, and they change the shape of read paths substantially 5,48. A resource is a reactive read whose request is derived from signals and whose result is exposed as value(), status() and error() — which means the loading and error states that used to be three correlated booleans in a component become one object owned by the data-access layer.

Where a domain needs more than a read cache — optimistic updates, undo, cross-screen coordination — a signal-based store belongs in the same data-access library rather than in a parallel state layer of its own; NgRx's signal store is the mainstream option and composes with the resource APIs rather than replacing them 49,50.

Two cautions. Resources present errors in status() and error() rather than forwarding them to the application ErrorHandler, which is a deliberate design choice and is documented as such 51 — the consequence is that a resource failure your UI ignores is a failure nobody hears about. And resources model reads. Writes remain imperative: a command returns a promise or an observable, has a success and failure path the caller must handle, and needs the idempotency discipline that safe methods do not 52. Do not contort a mutation into a resource.

Contract tests, not integration hope

The mapper is where an API change should fail, and it should fail in CI rather than in production. Two complementary techniques: intercept at the network layer with Mock Service Worker so that component and end-to-end tests exercise the real client code against a controlled response 53; and, where the backend team will cooperate, run consumer-driven contract tests so the provider's build breaks when it removes a field you depend on 54. Both are cheaper than the alternative, which is discovering the change from a support ticket.

Cross-cutting HTTP policy

Interceptors are the middleware layer of the browser-side stack. Functional interceptors — plain functions of (req, next) registered through provideHttpClient(withInterceptors([...])) — are the current idiom; they run inside an injection context, so inject() works directly in the function body, and they avoid the class-and-token ceremony of the DI-based variety 41,55,56.

The ordering semantics are explicit in the documentation and are the part teams most often get wrong: interceptors are chained in the order listed, so the first one processes the request first and sees the response last 41. Four consequences follow directly.

  • Auth above retry means a retried request carries a freshly refreshed token. Below it, the retry replays the same expired credential and you get a deterministic 401 storm.
  • Cache above auth is a data-leak: a cached response keyed without the identity dimension can be served to the next user of the same browser profile.
  • Telemetry last measures what the user actually experienced, including retries and cache hits. Placed first, it measures your own instrumentation.
  • Correlation first, so that every downstream interceptor and every log line produced during the request has an id to attach to (§14).
R09Cross-cutting HTTP policy is declared once, in order
rule
Auth, correlation, retry, timeout, caching and telemetry are interceptors registered in one place, with the order documented as a decision.
enforced by
A single provideAcmeHttp() in shared/http; features never call provideHttpClient themselves
buys
Consistent behaviour across every call in the application, and one file to change when the auth scheme moves.
costs
A chain that is invisible at the callsite: a developer reading a service cannot see what happens to the request.
tell
Two features implementing retry differently, or a bearer token pasted into a setHeaders call.

The retry operator above is deliberately conservative in two ways that are worth copying: it refuses to replay a non-idempotent verb unless the caller supplied an idempotency key 52, and it fails fast on 4xx rather than hammering an endpoint that has already given a definitive answer. RxJS's retry with a delay factory is what makes the exponential backoff and the status-dependent decision expressible in one place 57.

HttpContextToken is the pressure valve that keeps the chain from becoming tyranny: it carries per-request metadata that an interceptor can read, so a single call can opt out of caching, request a longer timeout, or declare itself retryable without the interceptor needing to know anything about that endpoint 41. Prefer it over inspecting URLs with regular expressions, which is how interceptors acquire knowledge of domains they should not have.

One boundary note. An interceptor registered on the root injector applies to every request in the application, including those issued by a federated remote sharing the same HttpClient. In a federated topology, decide deliberately whether the host's interceptor chain is the contract for all remotes — usually it should be, for auth and correlation — and whether remotes may add their own.

Error handling

Angular's own guidance states the principle more sharply than most application code follows it: errors should be surfaced to developers at the callsite whenever possible, because that is where the context needed to recover exists. The framework catches errors it invokes your code from — constructors, lifecycle hooks, template expressions — and routes them to the application ErrorHandler; it does not catch errors from APIs your code calls directly, and it treats what reaches the ErrorHandler as unexpected: potentially unrecoverable, possibly indicating corrupted state 51,58.

That framing gives you a taxonomy, and the taxonomy gives you four different mechanisms.

R10Expected failures never reach the ErrorHandler
rule
A 4xx that the UI has an answer for is handled where the call is made; ErrorHandler is reserved for the genuinely unexpected.

tell
A crash-reporting tool whose top issue is “validation failed”.

provideBrowserGlobalErrorListeners() attaches error and unhandledrejection listeners to the window and forwards them to the ErrorHandler; the CLI adds it to new applications, and the Angular team recommends handling these globally for most applications 59,51. Under server-side rendering, Angular installs unhandledRejection and uncaughtException handlers on the server process so that a rendering failure degrades rather than taking the process down 51,60.

Four design decisions that separate mature error handling from the rest:

Error boundaries are a routing concern. Angular has no component-level error boundary primitive in the React sense; the effective equivalent is a route-level error state plus a shell component that can render a recovery affordance without unmounting the application chrome. Design the failure screen for each domain, not one for the application.

De-duplicate before you report. An error inside a change-detection cycle can fire on every cycle. Without a fingerprint-and-window guard, one broken component generates thousands of events, exhausts the reporting quota, and hides everything else.

Adopt a machine-readable error contract. If the backend emits application/problem+json per RFC 9457, the mapper can translate a type URI into a domain error the UI can switch on, instead of parsing prose 61. Where the backend does not, the mapper is still the place to impose one.

Test the failure path. TestBed rethrows unexpected errors by default precisely so that framework-caught failures cannot pass silently; the rethrowApplicationErrors: false escape hatch exists for the rare test that asserts resilience, and reaching for it routinely defeats the mechanism 51.

Logging and observability

Browser logging has one property that server logging does not: the log is produced on a machine you do not own, by a runtime you cannot inspect, for a user who will not file a ticket. Everything about the design follows from that.

Structure first, transport second

A log line that is a sentence is a log line that cannot be aggregated. Emit objects with a stable schema: level, event name, correlation id, route, release, and a bounded property bag. The abstraction should be a Logger injected from a shared/observability library, never console directly, so that transport, sampling and redaction are swappable without touching call sites.

R11Every log line is structured and correlated

Note the two defensive details. Route normalisation strips identifiers so that /trips/8f3c-… aggregates as /trips/:id rather than producing a cardinality explosion. Redaction works from an allow-list of fields, because a deny-list fails open the first time somebody adds a property.

Correlation is the point

A browser-side error rate is nearly useless in isolation and extremely useful when it joins to a backend trace. The mechanism is the W3C Trace Context recommendation: the browser generates or propagates a traceparent header on outbound requests, the gateway continues the trace, and the resulting span tree spans both runtimes 63. The correlation interceptor from §12 is the only place this needs to be implemented.

OpenTelemetry's JavaScript packages provide the browser end: a web tracer provider, exporters over OTLP, and automatic instrumentation for document load, fetch, XHR and user interaction 64,65. Two caveats belong in any honest recommendation. Browser instrumentation is the least mature part of the OpenTelemetry surface, and consolidation into a dedicated browser SDK is ongoing 66. And the auto-instrumentation bundle is not small; on a latency-sensitive application, measure the instrumentation's own cost before adopting it wholesale.

Configuration management

The configuration question in enterprise frontend work is not "where do I put the API URL". It is "how many artifacts do we build, and what varies between environments". Getting the first question right and the second wrong produces a release process in which the thing tested in staging is not the thing shipped to production.

R13Build once, configure at runtime
rule
One artifact is promoted from staging to production unchanged; environment differences are fetched at startup, not compiled in.
enforced by
A single build in CI plus provideAppInitializer fetching /assets/config.json before bootstrap completes 9
buys
What you tested is what you shipped; a configuration change is a file swap and a cache purge rather than a rebuild and a redeploy.
costs
One extra request before the application is usable, and a startup failure mode when the config endpoint is unavailable.
tell
A CI pipeline with a build step per environment, or a hotfix whose diff is one string.

Three points about this shape. The token is typed, so no consumer reads environment.someString and hopes. Parsing happens once and throws with a readable message, which converts a class of silent misconfiguration into a loud startup failure — the right trade, because a frontend that boots with the wrong API base URL fails in a hundred confusing ways later. And the fetch uses the same HTTP stack as everything else, so it inherits retry and correlation.

Compile-time configuration via environment.ts and the CLI's fileReplacements is not wrong; it is appropriate for values that genuinely differ per build rather than per deployment — the build id, whether to enable development-only diagnostics, which locale bundle is being produced 67. The failure is using it for values that differ per environment, which forces a build per environment and destroys the promotion model.

Feature flags are configuration with a shorter half-life

Flags belong at the third resolution stage: evaluated per session or per user, not baked into the bundle. Three disciplines keep them from becoming permanent architecture. Every flag gets an owner and an expiry date recorded where the flag is defined. Flag reads happen at a boundary — a guard, a route, a provider — rather than scattered through templates. And flag state is exposed as a signal, so that a flip is a normal reactive update rather than a requirement to reload.

R12Nothing shipped to a browser is secret
rule
No credential, signing key, private endpoint or internal hostname appears in the bundle, in config.json, or in a flag payload.
enforced by

buys
A threat model that is stated rather than assumed; a clean answer when a security reviewer asks what an attacker learns from view-source.
costs
Some convenience: every privileged operation needs a server-side counterpart.
tell
An API key in environment.prod.ts, or a comment reading // TODO: move to backend.

Two adjacent controls belong in the same conversation because they are configured in the same place and are frequently deferred until an audit. A Content Security Policy that constrains script-src, connect-src and frame-ancestors is the single highest-value header for a single-page application 69; Angular's built-in contextual escaping handles the common injection cases but does not substitute for it 68. Trusted Types raises the floor further by making DOM injection sinks refuse raw strings, and Angular's sanitisation is designed to interoperate with it 70. Both are far cheaper to adopt at the start of a project than after three years of accumulated inline handlers.

Design systems and the token pipeline

A design system inside an enterprise Angular workspace is a library like any other, subject to the same boundary rules, with one additional property that makes it unusually hard: its consumers include people who do not write TypeScript. The contract has to be legible to designers, expressible in a design tool, and compilable into CSS. That is what design tokens are for.

The interoperability problem was chronic until recently — every tool had its own JSON shape — and it is now largely solved. The Design Tokens Community Group's format module reached its first stable version (2025.10) in October 2025, with more than twenty editors and participation from Adobe, Google, Microsoft, Salesforce, Figma and others; it specifies a single JSON shape with $value and $type, composite types for shadows, gradients and typography, references that survive transforms, and standardised metadata including $description and $deprecated 71,72,73. Style Dictionary consumes it and emits platform-specific artifacts 74.

The three-tier structure is the part that makes tokens more than variables. Reference tokens (color.blue.60 = #2E5AAC) hold raw values and carry no meaning. System tokens (--mat-sys-primary) name a role — where the value is used, not what it is. Component tokens (--mat-button-label-text-color) express one component's contract. Angular Material's Material 3 implementation is built exactly this way: the mat.theme mixin takes colour, typography and density inputs and emits system-level CSS custom properties, with overrides mixins for narrowly targeted customisation that validate token names and preserve compatibility when tokens are renamed 75,76,77.

R14Application styles name tokens, never values
rule
No stylesheet outside the design system contains a hex colour, a raw pixel spacing value, or a font stack.
enforced by
A stylelint rule banning colour literals outside libs/shared/design-system/** 76
buys
Theming, dark mode, density and brand refreshes become configuration; a rebrand is a token release rather than a codebase migration.
costs
An indirection every developer must learn, and a token vocabulary that has to be designed rather than accumulated.
tell
A dark-mode bug report that lists nine unrelated screens.

Three ways to build the components, and when each is right

Angular now offers a genuine spectrum, and choosing wrongly is expensive in both directions. Angular Material gives pre-styled, accessible components and is the right answer when the brand can live inside Material's design language 78. Angular CDK gives unstyled behaviour primitives — overlay, drag and drop, layout, accessibility utilities — and is the right answer when you need Material's engineering but none of its appearance 79,80. Angular Aria, stable since v22, sits between them: headless directives implementing WAI-ARIA authoring patterns — accordion, autocomplete, combobox, grid, listbox, menu, menubar, multiselect, select, tabs, toolbar, tree — that handle keyboard interaction, ARIA attributes, focus management and screen-reader support while you supply the markup and the CSS. The documentation names design-system and enterprise component-library work as its primary use cases, and equally names the cases where it is the wrong tool: pre-styled needs, simple native form controls, and rapid prototyping 81.

Whichever you pick, three practices separate a design system that gets adopted from one that gets forked.

Wrap native elements rather than replacing them. The Angular accessibility guidance is explicit: reuse native elements where possible, and prefer an attribute selector on a native <button> over a custom element that reimplements its behaviour — the pattern Angular Material itself uses 82,83,84. Where a native element cannot have children, use content projection and a container component, as MatFormField does 85.

Two mechanical notes. A component's content and view queries are part of that contract too, and marking query results readonly keeps Angular's assignment from being overwritten by consumer code 86,19. And if the product uses a utility CSS framework rather than component-scoped styles, Angular documents a supported Tailwind integration — but the token rule above does not relax: the utility scale itself must be generated from the same token source, or you have two design systems 87,73.

Version and deprecate like a public package. Even inside a monorepo, a component's inputs and outputs are an API. Renaming an input is a breaking change; the fact that you can fix all call sites atomically is a convenience, not a licence to skip the changelog 27.

Make the documentation executable. A Storybook story is simultaneously documentation, a visual-regression fixture and an accessibility test target 88,89. A component with no story is a component nobody outside the owning team will risk adopting.

Accessibility

Accessibility arrives in enterprise planning through two doors, and it is worth being honest about which one opens first. The ethical case is that a substantial share of your users navigate by keyboard, magnification or screen reader, and an inaccessible interface excludes them from a service they are entitled to use. The commercial case is that, since 2025, it is enforceable law across two of the largest markets in the world.

The regulatory floor, as of August 2026

The European Accessibility Act (Directive (EU) 2019/882) became enforceable on 28 June 2025, extending accessibility obligations from public-sector bodies to a broad range of private services including e-commerce, banking, transport ticketing and e-books, and applying to any business serving EU consumers regardless of where it is headquartered 90,91. The harmonised technical standard is EN 301 549, whose current published version (v3.2.1) incorporates WCAG 2.1 Level AA; a revision incorporating WCAG 2.2 is expected 92. In the United States, the Department of Justice's Title II rule of 24 April 2024 adopted WCAG 2.1 Level AA for state and local government web content and mobile apps; an interim final rule published 20 April 2026 extended the compliance dates to 26 April 2027 for entities serving populations of 50,000 or more and 26 April 2028 for smaller entities and special districts, leaving the substantive requirements unchanged 93,94.

WCAG 2.2 itself has been a W3C Recommendation since 5 October 2023, updated 12 December 2024, and was approved as ISO/IEC 40500:2025 95,96. It adds nine success criteria and removes 4.1.1 Parsing as obsolete; six of the nine are Level A or AA, so a team targeting AA inherits them 97. Four of those six bite hardest in dense enterprise UIs: 2.4.11 Focus Not Obscured, which sticky headers and toolbars violate constantly; 2.5.7 Dragging Movements, which requires a pointer alternative to every drag interaction — directly relevant to CDK drag-and-drop kanban boards and reorderable tables 80; 2.5.8 Target Size (Minimum), setting a 24 × 24 CSS pixel floor with a spacing exception, which compact data grids routinely fail; and 3.3.8 Accessible Authentication, which rules out cognitive-function tests in login flows and explicitly permits password managers and paste.

Why the industry is getting worse, not better

WebAIM's annual analysis of the top one million home pages found detected WCAG 2 failures on 95.9% of pages in its February 2026 run, up from 94.8% in 2025 — the first regression after six consecutive years of small improvements. Detected errors averaged 56.1 per page, a 10.1% increase year over year, across 56,114,377 distinct errors. WebAIM attributes the reversal primarily to rising page complexity and ARIA volume, noting that home pages averaged 1,437 elements, a 22.5% increase in a single year, and pointing at heavier framework use and AI-assisted coding as likely contributors. The same six failure categories — low contrast, missing alternative text, missing form labels, empty links, empty buttons and missing document language — have topped the list for seven consecutive years and account for 96% of all detected errors 98.

Two conclusions follow for anyone building with a component framework. First, the failures are not exotic; they are the basics, at scale, in generated markup. Second, automated detection is a floor rather than a ceiling: these figures cover only automatically detectable failures, so full conformance is certainly rarer than the residual 4.1% suggests 98.

What single-page applications break specifically

An SPA violates the one contract every assistive technology was built around: that following a link loads a document, which resets focus and announces a new title. When the router swaps the view instead, focus falls to <body> and nothing is announced.

Testing that finds real problems

Build a three-layer programme and be honest about what each layer covers. Automated engines such as axe-core detect a minority of WCAG issues — reliably, cheaply, on every commit — and are best wired into unit tests, Storybook stories and end-to-end runs 89,104,88. Lint rules from angular-eslint catch a further class in templates before the code runs 62,82. Neither substitutes for manual keyboard traversal of each critical flow and periodic testing with real assistive technology, which is where the failures that matter most — a focus order that makes no sense, a live region that announces the wrong thing, a modal that traps nothing — actually surface 105.

Testing, CI, and the upgrade calendar

Two operational disciplines determine whether the architecture above survives contact with three years of feature work: what the pipeline refuses to merge, and how the framework version is managed.

The test shape that matches the taxonomy

The library types are also a testing strategy, which is one of the underrated benefits of the taxonomy. domain and util libraries are pure, so they take plain unit tests with no TestBed and run in milliseconds. ui libraries take component tests driven entirely through inputs, which is only possible because R02 forbids them from injecting anything. data-access libraries take tests against a mocked transport 53. feature libraries take component tests with test harnesses and faked facades. Only the shell and the application take end-to-end tests, and there should be few of them.

Angular's CLI now integrates Vitest as a test runner, which materially changes the economics of the pyramid: a fast watch-mode unit suite makes the pure domain and util layers pleasant to test, which is the precondition for putting logic there in the first place 106.

Two v22-era mechanics change how these are written. Under zoneless change detection, tests must await rendering rather than relying on Zone.js to flush; TestBed configured with provideZonelessChangeDetection() is the way to make tests match production behaviour 7,13. And TestBed rethrows unexpected errors by default, so a framework-caught failure fails the test instead of vanishing 51.

The upgrade calendar is an architectural constraint

Angular ships a major release every six months, with a support window per major that combines active support and long-term support; the update guide provides version-to-version migration paths and the CLI's ng update runs schematics that perform most mechanical migrations 107,108. Treating this as a project rather than as a recurring maintenance item is the single most common way a large Angular codebase becomes unmaintainable, because the cost of skipping versions is superlinear: each skipped major means migrations that must be applied in sequence, dependencies that no longer have overlapping supported ranges, and a codebase whose idioms diverge from every answer, example and language model the team consults.

Two smaller pieces of the toolchain earn their place at scale. For teams using AI coding assistants, the CLI now ships an MCP server that exposes workspace-aware context and Angular-specific guidance to the assistant, which is a meaningful mitigation for the pattern WebAIM identified: generated code that compiles, works, and quietly violates conventions the model was not told about 112,98.

None of this is a substitute for judgement, and a ruleset applied without judgement produces its own pathology: an allow array that grows until the rules describe nothing, or a team that routes around the linter by putting everything in shared. The rules are a way of making architectural intent cheap to check, so that the expensive human attention goes to the questions that are actually hard — where the bounded contexts are, which duplication is healthy, and what the interface between two teams should be.

The thread running through all eighteen is the same one this article opened with. In a codebase of any size, the import graph is the architecture: it decides build times, bundle boundaries, blast radius, and which team has to be in the room for a change. Angular v22 has made the framework-level part of this easier than it has ever been — standalone components removed a layer of ceremony, signals made state flow legible, zoneless change detection removed a global mechanism nobody could reason about, and Angular Aria removed the excuse for inaccessible custom widgets. What remains is the part no framework release will do for you: deciding what may import what, writing it down in a form a machine can check, and defending it on the days when the shortcut would be easier.
