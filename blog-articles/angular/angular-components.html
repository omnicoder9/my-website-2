Angular Components

An Angular component is a directive with a template. It owns a host element, renders a view, exposes a public binding contract, participates in dependency injection and change detection, and moves through a managed lifecycle from construction to destruction. Applications become component trees whose boundaries should express clear ownership of presentation, state, and user interaction.

1. The component model

Angular identifies components as its fundamental UI building blocks. Every component combines a TypeScript class, a template, and a selector, with Angular-specific configuration supplied through @Component metadata. Components are a specialized subset of directives and, unlike ordinary directives, are always associated with a template; only one component can match a given element.[1][2][3]

Selector matches host
Injector creates class
Inputs initialize
Template renders view
Lifecycle updates and cleanup

Host

The DOM element that matches the component selector. Angular renders the component template inside this host element.[4][5]

View

The nodes declared by the component’s own template, including descendant component hosts and embedded views.

Content

Nodes supplied between the component’s opening and closing tags and projected into ng-content. Projected content remains owned by the declaring parent view.[6]

minimal component
import { Component } from '@angular/core';

@Component({

  template: `
    <img
      src="/images/profile.webp"
      alt="User profile">
  `,
})
export class ProfilePhotoComponent {}
A component is more than its class Its behavior is the class, template, metadata, dependency-injection context, host bindings, styles, and interaction with parents and children. Component tests therefore often need to exercise the class and rendered DOM together.[32]

2. Historical development

AngularJS directives established component-like UI units

AngularJS extended HTML through directives. Later AngularJS versions added the .component() API as a restricted, simpler directive configuration aimed at component-based architecture, one-way bindings, controller lifecycle hooks, and easier migration to modern Angular.[7][8]

Angular 2 made components the primary view abstraction

The rewritten Angular framework described applications as trees of components. A class controlled a region of screen, metadata connected the class to its selector and template, data binding coordinated class and view, and lifecycle hooks exposed creation, update, projection, view, and destruction phases.[9][10]

NgModule-era composition

Early modern Angular components were declared in NgModules. A component became available through its declaring module and the module’s imports and exports. This model remains supported for established applications.[2][9]

Standalone composition

Standalone components made template dependencies explicit in the component’s own imports metadata and removed the requirement for declaration in an NgModule. Current Angular components are standalone by default; older components can specify standalone: false. Angular recommends standalone components for new development.[1][2][11][12]

Signals and function-based component contracts

Modern Angular added signal state and compiler-recognized input(), output(), model(), and query functions. Templates track signal reads, inputs become read-only signals, outputs are typed emitter references, and queries return live signals.[13][14][15][16]

Declarative lazy and dynamic rendering

Built-in @defer blocks can split template dependencies into lazy chunks, while NgComponentOutlet, ViewContainerRef.createComponent(), and standalone createComponent() cover runtime-selected and programmatically hosted components.[17][18]

The selector determines how a component is used in another template. 4. Templates and views

A component template declares its own view. Angular templates extend HTML with interpolation, property and event binding, control flow, variables, directives, pipes, child components, content projection, and deferred blocks.[19]

4.1 A signal-driven template

component template and reactive state
import {
  Component,
  computed,
  signal,
} from '@angular/core';

@Component({
  selector: 'app-task-list',
  standalone: true,
  template: `
    <h1>{{ heading() }}</h1>

    <button
      type="button"
      (click)="showCompleted.update(
        value => !value
      )">
      {{ showCompleted()
        ? 'Hide completed'
        : 'Show completed'
      }}
    </button>

    @for (
      task of visibleTasks();
      track task.id
    ) {
      <article
        [class.completed]="task.completed">
        {{ task.title }}
      </article>
    } @empty {
      <p>No tasks to display.</p>
    }
  `,
})
export class TaskListComponent {
  readonly heading = signal('Tasks');
  readonly tasks = signal<readonly Task[]>([]);
  readonly showCompleted = signal(false);

  readonly visibleTasks = computed(() =>
    this.tasks().filter(task =>
      this.showCompleted() || !task.completed,
    ),
  );
}

When a template reads a signal, Angular records the dependency. Updating that signal marks the component so its affected view bindings can be synchronized on the next render.[13][36]

4.2 View versus projected content

multi-slot content projection
@Component({
  selector: 'app-card',
  standalone: true,
  template: `
    <section class="card">
      <header>
        <ng-content select="[cardTitle]">
          Untitled
        </ng-content>
      </header>

      <div class="card__body">
        <ng-content />
      </div>
    </section>
  `,
})
export class CardComponent {}
use projected content
<app-card>
  <h2 cardTitle>Account</h2>
  <p>Projected content belongs to the parent view.</p>
</app-card>

ng-content is a compiler-recognized projection placeholder rather than a runtime component or DOM element. Projection selectors and placeholders are processed at build time. Projected nodes remain part of the parent’s view, which affects change detection and dependency injection.[6]

Do not conditionally wrap ng-content Angular creates projected content even when an ng-content placeholder is hidden by a control-flow block. For conditional content, use template fragments or an explicit input-driven API.[6]

4.3 View and content queries

signal queries
import {
  Component,
  ElementRef,
  computed,
  contentChildren,
  viewChild,
} from '@angular/core';

@Component({
  selector: 'app-action-bar',
  standalone: true,
  template: `
    <button #primary type="button">
      Primary
    </button>

    <ng-content />
  `,
})
export class ActionBarComponent {
  readonly primaryButton =
    viewChild<ElementRef<HTMLButtonElement>>(
      'primary',
    );

  readonly projectedActions =
    contentChildren(ActionComponent);

  readonly actionCount = computed(
    () => this.projectedActions().length,
  );

  focusPrimary(): void {
    this.primaryButton()
      ?.nativeElement
      .focus();
  }
}

View queries find children declared in the component’s own template; content queries find projected children. Current query functions return signals that update as matching children appear or disappear. Queries do not pierce component boundaries.[16]

5.2 View encapsulation modes

ModeBehaviorTypical use
ViewEncapsulation.Emulated Default. Angular rewrites component selectors and adds generated attributes to scope the component’s styles to its own template. General application components.
ViewEncapsulation.ShadowDom Uses the browser’s native Shadow DOM, including style and event-retargeting boundaries. Components that deliberately require native encapsulation.
ViewEncapsulation.None Component styles are global and can affect the entire document. Explicit theme or global-style components; use cautiously.

In emulated mode, component styles do not normally leak outward, but global styles can still affect elements inside the component. Shadow DOM provides browser-enforced style isolation, whereas no encapsulation makes the styles global.[20]

5.4 Projected content and styles

Emulated component styles apply to nodes created by the component’s own template. Projected nodes are created by the parent, so styling arbitrary projected internals through private selectors creates coupling. Prefer explicit projection marker elements, CSS custom properties, or documented classes for customization.[6][20]

6. Component lifecycle

The component lifecycle is the sequence between creation and destruction. Angular traverses the component tree to check bindings, visiting a component once in each traversal. Hooks that run during this traversal should not cause further mid-pass state changes that invalidate already-checked views.[21]

PhaseHookPurpose
CreationconstructorStandard JavaScript construction and dependency capture.
Input changesngOnChangesRuns when bound inputs change; first run precedes ngOnInit.
InitializationngOnInitRuns once after initial inputs are initialized and before the component’s own template is initialized.
Custom checkingngDoCheckRuns whenever the component is checked; use only for specialized custom detection.
Projected contentngAfterContentInitRuns once after projected content initializes.
Projected contentngAfterContentCheckedRuns whenever projected content is checked.
ViewngAfterViewInitRuns once after the component view and view children initialize.
ViewngAfterViewCheckedRuns whenever the component view and view children are checked.
RenderingafterNextRenderRuns once after the next application-wide DOM rendering completes.
RenderingafterEveryRenderRuns after every application-wide rendering completion.
DestructionngOnDestroyRuns once before the component is destroyed.

6.1 ngOnChanges

input-change lifecycle hook
import {
  Component,
  OnChanges,
  SimpleChanges,
  input,
} from '@angular/core';

@Component({
  selector: 'app-chart',
  standalone: true,
  template: `<canvas></canvas>`,
})
export class ChartComponent
  implements OnChanges {

  readonly data =
    input.required<readonly DataPoint[]>();

  ngOnChanges(
    changes: SimpleChanges,
  ): void {
    if (changes['data']) {
      this.rebuildScale(this.data());
    }
  }

  private rebuildScale(
    data: readonly DataPoint[],
  ): void {
    // Recalculate non-reactive chart state.
  }
}

ngOnChanges receives current and previous input values. The change record keys use the TypeScript input property name rather than an external alias.[21]

6.2 ngOnInit

initialization from an input
@Component({
  selector: 'app-report',
  standalone: true,
  template: `...`,

6.3 ngDoCheck

ngDoCheck runs very frequently. Use it only when ordinary inputs, immutable updates, signals, and framework-provided differs cannot express the required custom change detection. Keep its work minimal.[21][40]

6.6 Render callbacks for DOM work

afterNextRender
import {
  Component,
  ElementRef,
  afterNextRender,
  inject,
} from '@angular/core';

@Component({
  selector: 'app-autofocus-field',
  standalone: true,
  template: `<input type="text">`,
})
export class AutofocusFieldComponent {
  private readonly host =
    inject<ElementRef<HTMLElement>>(
      ElementRef,
    );

  constructor() {
    afterNextRender(() => {
      this.host.nativeElement
        .querySelector('input')
        ?.focus();
    });
  }
}

Render callbacks run after Angular has rendered all components into the DOM and must be registered in an injection context. They do not run during server rendering or build-time pre-rendering. Angular advises avoiding direct DOM manipulation in other lifecycle hooks because the DOM may not be fully rendered and read/write interleaving can cause layout thrashing.[21][22]

6.7 Cleanup with DestroyRef

lifecycle cleanup
@Component({
  selector: 'app-network-status',
  standalone: true,
  template: `
    <p>{{ online() ? 'Online' : 'Offline' }}</p>
  `,
})
export class NetworkStatusComponent {
  readonly online = signal(navigator.onLine);

  private readonly destroyRef =
    inject(DestroyRef);

  constructor() {
    const controller = new AbortController();

    window.addEventListener(
      'online',
      () => this.online.set(true),
      { signal: controller.signal },
    );

    window.addEventListener(
      'offline',
      () => this.online.set(false),
      { signal: controller.signal },
    );

    this.destroyRef.onDestroy(() => {
      controller.abort();
    });
  }
}

DestroyRef colocates cleanup with resource setup and is useful when cleanup logic should be passed into helper functions. ngOnDestroy remains appropriate when the class benefits from the lifecycle interface.[21]

Keep lifecycle hooks small Angular’s style guidance recommends implementing lifecycle interfaces and delegating complex work to focused methods or services. Frequently invoked checked hooks are particularly sensitive to expensive logic.[24]

7.4 Organize by feature

Angular’s style guide recommends grouping related files by feature area, colocating a component’s TypeScript, template, styles, and tests, and using matching base file names. Avoid organizing the entire application into broad technical folders such as components and services when feature boundaries provide a clearer structure.[24]

8. Component communication

Component communication should make ownership explicit. Inputs deliver data from a parent into a child; outputs report child events; model inputs represent an editable value contract; projected content supplies markup; queries provide tightly scoped imperative references; and shared services or stores coordinate state that outlives a direct parent–child relationship.[14][15][16]

8.1 Inputs: parent to child

signal inputs
@Component({
  selector: 'app-user-card',
  standalone: true,
  template: `
    <article
      [class.selected]="selected()">
      <h2>{{ user().displayName }}</h2>
    </article>
  `,
})
export class UserCardComponent {
  readonly user =
    input.required<UserSummary>();

  readonly selected = input(false);
}
parent-to-child binding
<app-user-card
  [user]="user"
  [selected]="user.id === selectedId()" />

Signal inputs are read-only inside the child and are recorded statically by the compiler. Required inputs remove implicit undefined and produce template errors when omitted.[14]

8.2 Outputs: child to parent

typed output
export interface UserActivated {
  readonly userId: string;
  readonly source: 'mouse' | 'keyboard';
}

@Component({
  selector: 'app-user-row',
  standalone: true,
  template: `
    <button
      type="button"
      (click)="activate('mouse')"
      (keydown.enter)="activate('keyboard')">
      {{ name() }}
    </button>
  `,
})
export class UserRowComponent {
  readonly userId = input.required<string>();
  readonly name = input.required<string>();

  readonly activated =
    output<UserActivated>();

  activate(
    source: UserActivated['source'],
  ): void {
    this.activated.emit({
      userId: this.userId(),
      source,
    });
  }
}
child-to-parent event
<app-user-row
  [userId]="user.id"
  [name]="user.displayName"
  (activated)="openUser($event)" />

Outputs do not bubble through the DOM. Name them for events that occurred rather than commands the parent should execute.[15]

8.6 Shared state through a service

shared component state
@Injectable({ providedIn: 'root' })
export class SelectionStore {
  private readonly _selectedId =
    signal<string | null>(null);

  readonly selectedId =
    this._selectedId.asReadonly();

  select(id: string): void {
    this._selectedId.set(id);
  }

  clear(): void {
    this._selectedId.set(null);
  }
}

Use a shared service when components are not in a simple direct relationship or when state must survive one component’s lifetime. Scope the service at root, route, or component level according to the intended sharing boundary.

9. Smart and presentational components

“Smart” or container components and “presentational” components are architectural roles, not Angular runtime types. The distinction helps separate state acquisition and orchestration from reusable rendering and interaction. Angular’s style guidance similarly recommends keeping component code focused on presentation and delegating reusable business logic and data operations to services.[24][25][26]

Container component

  • Connects to route state, stores, services, or use cases.
  • Chooses data and loading/error states.
  • Translates child events into application commands.
  • Usually tied to one feature or page.

Presentational component

  • Receives values through inputs.
  • Emits semantic events through outputs.
  • Owns view-local interaction state.
  • Avoids knowledge of routes and backend contracts.

            <td>{{ order.customerName }}</td>
            <td>
              {{ order.totalCents / 100
                | currency:'USD'
              }}
            </td>

            </td>

9.3 Avoid dogma

A presentational component may legitimately inject accessibility, localization, or formatting capabilities. A container may contain substantial page-specific markup. The goal is clear ownership and low coupling, not an absolute prohibition on dependencies.

9.4 Signals that a split may help

  • A reusable widget imports the router and several API services.
  • A page component contains complex table, chart, or form rendering that is difficult to test independently.
  • Several screens copy the same markup but acquire data differently.
  • A child mutates parent-owned objects instead of exposing events.
  • Loading, error, and selection orchestration obscures the reusable UI contract.

10. Change detection and component boundaries

Angular checks component trees to synchronize template bindings. Component metadata can choose the default eager strategy or OnPush. Signals read by a template notify Angular when their values change, and new input values and handled events are important notifications for component checking.[27][28][36]

10.1 OnPush component

OnPush and signals
@Component({
  selector: 'app-order-total',
  standalone: true,
  changeDetection:
    ChangeDetectionStrategy.OnPush,
  template: `
    <p>
      Total:
      {{ totalCents() / 100 | currency:'USD' }}
    </p>
  `,
  imports: [CurrencyPipe],
})
export class OrderTotalComponent {
  readonly lines =
    input.required<readonly OrderLine[]>();

  readonly totalCents = computed(() =>
    this.lines().reduce(
      (total, line) =>
        total +
        line.unitPriceCents * line.quantity,
      0,
    ),
  );
}

OnPush allows Angular to skip a subtree when it has not received relevant notifications. When an OnPush component is checked, Angular also checks its ancestors. Mutable input objects can undermine the intended boundary because an unchanged reference does not represent a new input.[27][28]

10.2 Replace input values rather than mutating them

immutable input update
readonly order = signal<Order>(initialOrder);

// Preferred:
order.update(current => ({
  ...current,
  status: 'approved',
}));

// Risky:
order().status = 'approved';

10.3 Derive view state

memoized view derivation
readonly filteredOrders = computed(() => {
  const query =
    this.query().trim().toLowerCase();

  return this.orders().filter(order =>
    order.number
      .toLowerCase()
      .includes(query),
  );
});

Prefer computed state or pure pipes to repeatedly executing expensive transformations inside a template. This keeps rendering deterministic and caches derived results until dependencies change.

11. Dynamic components

Dynamic rendering is appropriate when the component type is unknown until runtime, such as dashboards, plugins, schema-selected editors, and overlay content. Angular supports declarative NgComponentOutlet, container-attached programmatic creation, and standalone component creation with explicit host placement.[17]

11.1 NgComponentOutlet

declarative dynamic component
import { NgComponentOutlet } from '@angular/common';

@Component({
  selector: 'app-profile-host',
  standalone: true,
  imports: [NgComponentOutlet],
  template: `
    <ng-container
      [ngComponentOutlet]="
        profileComponent()
      "
      [ngComponentOutletInputs]="
        profileInputs()
      "
      #outlet="ngComponentOutlet" />

    <button
      type="button"
      (click)="
        outlet.componentInstance
          ?.refresh()
      ">
      Refresh
    </button>
  `,
})
export class ProfileHostComponent {
  readonly user = input.required<User>();

  readonly profileComponent = computed(
    () => this.user().isAdministrator
      ? AdminProfileComponent
      : StandardProfileComponent,
  );

  readonly profileInputs = computed(() => ({
    user: this.user(),
  }));
}

NgComponentOutlet can receive inputs, projected content, a custom injector, and an environment injector. Its exported directive instance exposes the current component instance after rendering.[17][38]

11.2 ViewContainerRef.createComponent()

container-attached dynamic component
import {
  Component,
  ViewContainerRef,
  inject,
} from '@angular/core';

@Component({
  selector: 'app-inline-widget-host',
  standalone: true,
  template: `

      Add widget

A component created through a view container is inserted into that container’s logical and visual view hierarchy at the container location. Angular manages its host view as part of the parent tree.[17][39]

11.3 Declarative bindings at creation

input, output, and two-way dynamic bindings
import {
  Component,
  ViewContainerRef,
  inputBinding,
  outputBinding,
  signal,
  twoWayBinding,
} from '@angular/core';

@Component({
  selector: 'app-warning-host',
  standalone: true,
  template: `
    <button
      type="button"
      (click)="showWarning()">
      Show warning
    </button>
  `,
})
export class WarningHostComponent {
  private readonly container =
    inject(ViewContainerRef);

  readonly canClose = signal(true);
  readonly expanded = signal(true);

  showWarning(): void {
    this.container.createComponent(
      WarningComponent,
      {
        bindings: [
          inputBinding(
            'canClose',
            this.canClose,
          ),
          twoWayBinding(
            'expanded',
            this.expanded,
          ),
          outputBinding<boolean>(
            'closed',
            confirmed => {
              console.log(
                'Closed',
                confirmed,
              );
            },
          ),
        ],
      },
    );
  }
}

Binding helpers configure dynamic input, output, and two-way contracts in a template-like form and avoid manual synchronization after creation. Dynamic creation can also attach host directives.[17]

11.4 Standalone createComponent()

explicit dynamic host
const hostElement =
  document.createElement('app-toast');

document.body.append(hostElement);

const ref = createComponent(
  ToastComponent,
  {
    hostElement,
    environmentInjector,
    bindings: [
      inputBinding(

The standalone creation API does not automatically attach the component to an existing Angular view or DOM location. The caller controls the host element and view attachment and must also ensure destruction and cleanup.[17]

dynamic component-specific provider

  parent: environmentInjector,
  providers: [

11.6 Prefer static composition when possible

Static templates provide simpler typing, dependency analysis, projection, testing, hydration, and accessibility review. Use dynamic APIs only when the type or placement is genuinely runtime-defined.

12. Deferred component loading

When the component type is known in the template but its code should load later, Angular recommends @defer rather than manual dynamic imports in many cases. Eligible dependencies inside a defer block can be split into a separate JavaScript chunk and loaded on configured triggers.[17][18]

deferred component view
@defer (
  on viewport;
  prefetch on idle
) {
  <app-analytics-dashboard />
} @placeholder {
  <div class="dashboard-skeleton">
    Loading dashboard…
  </div>
} @loading (
  after 150ms;
  minimum 500ms
) {
  <app-spinner />
} @error {
  <p role="alert">
    The dashboard could not be loaded.
  </p>
}

Placeholder, loading, and error dependencies are eager, while eligible dependencies in the primary block are deferred. Direct imports rather than barrel aggregation may be necessary for the bundler to preserve a separate lazy chunk.[18][41]

12.1 Choose the right mechanism

RequirementMechanism
Known component, delay code and rendering@defer.
Runtime-selected known types in a templateNgComponentOutlet.
Insert runtime components into an Angular view containerViewContainerRef.createComponent().
Render into an arbitrary host outside an existing viewStandalone createComponent().

project-list.store.ts
@Injectable()
export class ProjectListStore {
  private readonly api = inject(ProjectApi);

  private readonly _state =
    signal<ProjectListState>({
      status: 'idle',
      projects: [],
    });

  readonly state =
    this._state.asReadonly();

  readonly projects = computed(
    () => this._state().projects,
  );

  load(): void {
    this._state.set({
      status: 'loading',
      projects: this.projects(),
    });

    this.api.list().subscribe({
      next: projects => {
        this._state.set({
          status: 'ready',
          projects,
        });
      },
      error: () => {
        this._state.set({
          status: 'error',
          projects: this.projects(),
          message:
            'Projects could not be loaded.',
        });
      },
    });
  }
}

15. Production component architecture

15.1 Keep components focused

Component code should generally relate to the displayed UI and its interaction. Move backend communication, storage, caching, complex business policy, and cross-feature state into services or domain code. Angular’s style guidance explicitly recommends focused components, presentation logic in the class rather than an overly complex template, and simple lifecycle methods.[24][25][26]

15.2 Colocate component files

feature-oriented layout
src/
└── orders/
    ├── order-card/
    │   ├── order-card.component.ts
    │   ├── order-card.component.html
    │   ├── order-card.component.css
    │   └── order-card.component.spec.ts
    └── orders-page/
        ├── orders-page.component.ts
        ├── orders-page.component.html
        └── orders-page.component.spec.ts

15.3 Treat bindings as a public API

  • Use required inputs for essential data.
  • Use defaults for optional presentation behavior.
  • Keep inputs read-only inside presentational components.
  • Emit identifiers and stable event payloads rather than component instances.
  • Use semantic event names such as submitted, closed, or selectionChanged.
  • Expose model inputs only for values the component is designed to edit.

15.4 Keep local state local

Focus, expansion, hover, temporary editing, and other view-local state belong in the component. State shared across routed children may belong in a route-scoped store; application-wide identity or configuration may belong in a root service.

15.5 Prefer composition

Build larger views by composing components, directives, projected content, and services. Component inheritance can share inputs, outputs, and host metadata, but often couples implementation and lifecycle behavior. Prefer base classes only when the subtype relationship is stable and semantically meaningful.

15.6 Preserve native semantics

Choose native elements before recreating controls with generic elements. Bind visual state and ARIA state from the same source. Dynamic and projected components should receive the same keyboard, focus, labeling, and lifecycle scrutiny as statically declared components.

16. Common pitfalls

PitfallConsequenceBetter approach
Component performs HTTP, storage, validation, logging, and rendering The class becomes difficult to test and reuse. Delegate integration and business logic to focused services.[24][25][26]
Mutating parent-owned input objects Ownership is hidden and optimized boundaries may not observe a new value. Emit an event or use an explicit model input with immutable replacement.
Using lifecycle hooks for ordinary derived state State is duplicated and hook ordering becomes significant. Use computed signals or pure transformations.
Expensive work in ngDoCheck or checked hooks The work repeats across many change-detection traversals. Use explicit reactive dependencies and keep hooks lean.[21][24]
DOM reads and writes in ngAfterViewChecked Layout thrashing and unstable rendering. Use phased render callbacks and declarative templates.[21][22]
Querying children to read normal data flow Parent and child internals become tightly coupled. Use inputs, outputs, models, or shared state.
Assuming projected content belongs to the receiver Change detection and provider behavior is misunderstood. Remember it remains in the declaring parent’s view.[6]
Using dynamic components for a statically known layout Typing, testing, hydration, and lifecycle management become harder. Prefer static templates or @defer when only lazy loading is needed.[17][18]
Creating a dynamic component without destroying it Views, subscriptions, and DOM nodes can leak. Let a view container own it or explicitly detach and destroy the reference.
Using ViewEncapsulation.None casually Component CSS leaks across the application. Use emulated encapsulation by default and global styles deliberately.[20]

19. Conclusion

Angular components are compiled UI units built from a class, metadata, a host element, a template, and optional styles. They compose into a tree, receive data through inputs, report events through outputs, model editable values, project content, query view or content children, receive scoped dependencies, and participate in change detection and lifecycle management.[1][2][3][13][14][15][16][21]

Strong component architecture depends on boundaries more than decorators. Keep components focused on presentation, give state one clear owner, use standalone imports to expose template dependencies, scope services according to lifetime, use lifecycle hooks only for lifecycle-specific work, prefer static composition and deferred views when possible, and reserve dynamic creation for genuinely runtime-defined interfaces.
