Angular Dependency Injection

Dependency injection is Angular’s runtime mechanism for connecting consumers to values they require without forcing those consumers to construct the values themselves. Angular DI is hierarchical: the provider location determines who can resolve a token, which injector owns the created value, how long it lives, and whether another provider can override it.

1. Dependency injection in one model

Angular describes dependency injection as both a design pattern and a framework mechanism. A dependency can be any JavaScript value, including a class instance, object, string, function, factory result, or configuration record. Consumers request values by token; providers tell an injector how to obtain those values; injectors resolve and cache provider results according to their scope.[1][2][3]

Consumer requests token
Current injector checks records
Parents searched if allowed
Provider creates value
Value cached and returned

Token

The runtime identity of a dependency. A class can serve as its own token; non-reified types generally use InjectionToken<T>.[4][5]

Provider

A configuration record that maps a token to a class, value, existing token, or factory. A class listed directly in providers is shorthand for a class provider.[3][6]

Injector

The runtime registry and resolver. It creates a dependency on first request when necessary and reuses the resulting value within that provider record’s injector.[1][7]

The essential rule A token does not inherently mean “one global instance.” The provider’s owning injector determines instance identity and lifetime. The same token may resolve to different values in different branches of the hierarchy.[7][8]

2. Historical development

AngularJS: string-named services and provider recipes

AngularJS made dependency injection pervasive across controllers, directives, filters, services, module configuration, and run blocks. Its injector created and wired objects from registered recipes such as value, factory, service, provider, and constant. AngularJS service instances were lazily instantiated and singleton within an injector.[9][10][11]

Dependency annotation under JavaScript minification

AngularJS commonly identified dependencies by function-parameter names, with alternatives such as an explicit $inject array or inline array annotation. Strict DI mode could require explicit annotation so name-changing minification would not break resolution.[9]

Modern Angular: TypeScript metadata and hierarchical injectors

The rewritten Angular framework adopted class and token-based provider APIs, decorator metadata, and a hierarchy tied both to application environments and the component/element tree. The hierarchy enables scoped instances and local overrides instead of only application-wide service identity.[7][8][12]

Tree-shakable provider declarations

@Injectable({ providedIn: 'root' }) and factory-backed InjectionToken declarations associate provision with the dependency itself. Angular documentation recommends these patterns because unused dependencies can be removed by build optimization, unlike unconditional manual registration that retains the provider reference.[2][3][13]

Functional injection

The inject() function allows token resolution in class field initializers, constructors, factories, guards, interceptors, and other injection contexts. Current Angular documentation also includes @Service() as shorthand for a root-provided service using functional injection, while @Injectable remains necessary for constructor injection and advanced provision choices.[2][14][15]

3. A first injectable dependency

3.1 Declare a root provider

exchange-rate.service.ts
import { Injectable } from '@angular/core';

@Injectable({
  providedIn: 'root',
})
export class ExchangeRateService {
  convert(
    amount: number,
    rate: number,
  ): number {
    if (!Number.isFinite(amount) || !Number.isFinite(rate)) {
      throw new TypeError('amount and rate must be finite');
    }

    return amount * rate;
  }
}

@Injectable marks the class so Angular can generate the metadata required to create its dependencies. providedIn: 'root' defines an automatically available root provider and normally yields one shared instance for consumers resolving through that root environment injector.[2][15][16]

3.2 Resolve it in a component

conversion-preview.component.ts
import { Component, inject } from '@angular/core';
import { CurrencyPipe } from '@angular/common';
import { ExchangeRateService } from './exchange-rate.service';

@Component({
  selector: 'app-conversion-preview',
  standalone: true,
  imports: [CurrencyPipe],
  template: `
    <p>{{ converted | currency:'EUR' }}</p>
  `,
})
export class ConversionPreviewComponent {
  private readonly rates = inject(ExchangeRateService);

  readonly converted =
    this.rates.convert(125, 0.91);
}

When the component is created, its field initializer executes in an injection context. inject(ExchangeRateService) asks the active injector for that class token; the injector locates the provider, creates the service if needed, caches it in the provider’s injector, and returns it.[1][14][17]

4. Providers

Angular’s Provider type includes class, value, existing, factory, constructor, and nested provider forms. The provide property identifies the token; the remaining provider property defines how the value is obtained.[3][6]

4.1 Type and class providers

class providers
providers: [
  // Shorthand:
  AuditService,

  // Expanded equivalent:
  {
    provide: AuditService,
    useClass: AuditService,
  },

  // Substitute a different implementation:
  {
    provide: PaymentGateway,
    useClass: SandboxPaymentGateway,
  },
]

useClass tells the injector to instantiate the specified class for the requested token. The replacement class can differ from the token’s class, which supports environment-specific implementations and test doubles.[3][18]

4.2 Value providers

useValue provider
export interface BuildInfo {
  readonly version: string;
  readonly commit: string;
}

export const BUILD_INFO =
  new InjectionToken<BuildInfo>('build.info');

export const appConfig: ApplicationConfig = {
  providers: [
    {
      provide: BUILD_INFO,
      useValue: {
        version: '3.4.0',
        commit: 'a7c12de',
      },
    },
  ],
};

useValue associates a token with a pre-existing value. It is appropriate for immutable configuration, constants, feature flags, and test doubles. Mutating a shared object supplied with useValue mutates the same object observed by all consumers of that provider.[3]

4.3 Existing providers and aliases

useExisting provider
@Injectable({ providedIn: 'root' })
export class StructuredLogger {
  info(event: string): void {
    console.info({ event });
  }
}

export abstract class Logger {
  abstract info(event: string): void;
}

export const appConfig: ApplicationConfig = {
  providers: [
    StructuredLogger,
    {
      provide: Logger,
      useExisting: StructuredLogger,
    },
  ],
};

useExisting aliases another token and returns that token’s existing value. In this example, resolving Logger and StructuredLogger returns the same object. Using useClass: StructuredLogger under both tokens could create two independent instances instead.[3][19]

4.4 Factory providers

useFactory with functional injection
export interface RetryPolicy {
  readonly maxAttempts: number;
  readonly baseDelayMs: number;
}

export const RETRY_POLICY =
  new InjectionToken<RetryPolicy>('retry.policy');

export const appConfig: ApplicationConfig = {
  providers: [
    {
      provide: RETRY_POLICY,
      useFactory: () => {
        const config = inject(APP_CONFIG);

        return config.production
          ? { maxAttempts: 3, baseDelayMs: 250 }
          : { maxAttempts: 1, baseDelayMs: 0 };
      },
    },
  ],
};

A factory provider invokes useFactory to create the value. A factory can resolve dependencies with inject() because provider factories execute in an injection context. The older explicit deps array remains available when dependencies should be supplied as factory parameters.[14][20]

factory provider with deps
{
  provide: RETRY_POLICY,
  useFactory: (
    config: AppConfig,
  ): RetryPolicy => ({
    maxAttempts: config.production ? 3 : 1,
    baseDelayMs: config.production ? 250 : 0,
  }),
  deps: [APP_CONFIG],
}

4.5 Multi-providers

multi-provider token
export interface StartupTask {
  run(): void | Promise<void>;
}

export const STARTUP_TASKS =
  new InjectionToken<readonly StartupTask[]>(
    'startup.tasks',
  );

providers: [
  {
    provide: STARTUP_TASKS,
    multi: true,
    useClass: LoadFeatureFlagsTask,
  },
  {
    provide: STARTUP_TASKS,
    multi: true,
    useClass: WarmReferenceDataTask,
  },
]
consume a multi-provider array
@Injectable({ providedIn: 'root' })
export class StartupCoordinator {
  private readonly tasks =
    inject(STARTUP_TASKS, { optional: true }) ?? [];

  async run(): Promise<void> {
    for (const task of this.tasks) {
      await task.run();
    }
  }
}

Setting multi: true makes the injector aggregate all providers for the token into an array. Multi-providers support extensible configuration in which independent features contribute values to one token.[18][19][20]

5. Injection tokens

TypeScript interfaces, callable signatures, arrays, generic types, and primitive types do not provide a class constructor that Angular can use as a runtime token. InjectionToken<T> creates a unique runtime object with a compile-time result type.[4][5]

5.1 A typed configuration token

api-configuration.token.ts
import { InjectionToken } from '@angular/core';

export interface ApiConfiguration {
  readonly baseUrl: string;
  readonly timeoutMs: number;
}

export const API_CONFIGURATION =
  new InjectionToken<ApiConfiguration>(
    'api.configuration',
  );
manual token provider
export const appConfig: ApplicationConfig = {
  providers: [
    {
      provide: API_CONFIGURATION,
      useValue: {
        baseUrl: '/api',
        timeoutMs: 15_000,
      },
    },
  ],
};

The token description is used for debugging; Angular identifies an InjectionToken by object identity. Creating two tokens with the same description creates two different tokens and can cause resolution failure.[4][5]

5.2 A factory-backed tree-shakable token

tree-shakable InjectionToken
export interface LocalePreferences {
  readonly locale: string;
  readonly timeZone: string;
}

export const LOCALE_PREFERENCES =
  new InjectionToken<LocalePreferences>(
    'locale.preferences',
    {
      providedIn: 'root',
      factory: () => ({
        locale: navigator.language || 'en-US',
        timeZone:
          Intl.DateTimeFormat()
            .resolvedOptions()
            .timeZone || 'UTC',
      }),
    },
  );

A token factory automatically supplies the value and can itself call inject(). The token provider is root-scoped by default when a factory is declared unless a supported providedIn value changes the scope. Factory-backed tokens can be removed when no reachable code requests them.[3][4]

5.3 Abstract classes as tokens

abstract class token
export abstract class Clock {
  abstract now(): Date;
}

@Injectable({ providedIn: 'root' })
export class SystemClock implements Clock {
  now(): Date {
    return new Date();
  }
}

providers: [
  SystemClock,
  {
    provide: Clock,
    useExisting: SystemClock,
  },
]

An abstract class exists at runtime and can therefore serve as a token while also expressing a TypeScript contract. InjectionToken is preferable when a class-shaped abstraction would be artificial or when the dependency is not an object with methods.

5.4 Export one canonical token instance

token identity
// tokens.ts — define once and import everywhere
export const FEATURE_POLICY =
  new InjectionToken<FeaturePolicy>(
    'feature.policy',
  );

// Never recreate a token at the injection site:
const wrong = new InjectionToken<FeaturePolicy>(
  'feature.policy',
);

6. Tree-shakable providers

Tree-shaking removes code that the build can prove is unreachable. Angular’s preferred automatic provider declarations attach the provider to the dependency: @Injectable({ providedIn: 'root' }), current @Service(), or an InjectionToken factory. If no reachable consumer injects the dependency, optimization can remove the dependency and its provider metadata.[2][3][13][15]

Automatic provision

tree-shakable class provider
@Injectable({
  providedIn: 'root',
})
export class AnalyticsClient {}

Manual provision

eager provider reference
export const appConfig: ApplicationConfig = {
  providers: [
    AnalyticsClient,
  ],
};

Manual provider arrays are necessary for substitutions, scoped instances, configuration values, and feature installers. They also create an explicit application reference to the provider, so a manually registered service is normally retained even if no consumer ultimately requests it.[13][16]

6.1 Lightweight token pattern for libraries

Angular documents a lightweight injection-token pattern for library authors. A heavy component or service class used as a token can create a value-position reference that keeps code reachable. A lightweight token decouples the injectable API identity from the optional implementation so unused implementation code can be removed.[21]

lightweight library token
export interface AnalyticsSink {
  track(
    name: string,
    properties?: Record<string, unknown>,
  ): void;
}

export const ANALYTICS_SINK =
  new InjectionToken<AnalyticsSink>(
    'analytics.sink',
  );

// Optional implementation resides in a separate entry point.
@Injectable()
export class VendorAnalyticsSink
  implements AnalyticsSink {
  track(
    name: string,
    properties: Record<string, unknown> = {},
  ): void {
    // Vendor integration.
  }
}

7. Injector hierarchy

Current Angular documentation distinguishes two primary injector hierarchies: the EnvironmentInjector hierarchy outside the component tree and the ElementInjector hierarchy attached implicitly to DOM elements. NgModule-based applications additionally use a flattened ModuleInjector hierarchy assembled from module providers and imports.[7][8][22]

Platform EnvironmentInjector └── Application root EnvironmentInjector ├── Route EnvironmentInjector: /admin │ └── Component ElementInjector: AdminShell │ └── Child ElementInjector: AdminUsers └── Component ElementInjector: AppRoot ├── Child ElementInjector: Header └── Child ElementInjector: MainContent └── Child ElementInjector: ProductPage

7.1 Environment injectors

An EnvironmentInjector exists outside the component tree. Application bootstrap providers, root automatic providers, route providers, and dynamically created environment injectors participate in this hierarchy. Environment injectors can be explicitly destroyed and report their destroyed state.[7][22][23]

application environment providers
export const appConfig: ApplicationConfig = {
  providers: [
    provideHttpClient(),
    { provide: API_URL, useValue: '/api' },
  ],
};
route environment providers
export const ADMIN_ROUTES: Routes = [
  {
    path: '',
    providers: [
      AdminSession,
      {
        provide: API_URL,
        useValue: '/api/admin',
      },
    ],
    children: [
      { path: '', component: AdminHomePage },
      { path: 'users', component: AdminUsersPage },
    ],
  },
];

7.2 Element injectors

Angular creates an element injector for each DOM element participating in Angular’s view model. It is empty by default and receives records from component or directive providers and viewProviders. Descendant elements search upward through element injectors when resolving a dependency.[7][8]

component element provider
@Component({
  selector: 'app-order-editor',
  standalone: true,
  providers: [
    OrderDraftStore,
  ],
  template: `
    <app-order-lines />
    <app-order-totals />
  `,
})
export class OrderEditorComponent {
  readonly draft = inject(OrderDraftStore);
}

Each OrderEditorComponent instance creates its own OrderDraftStore. Descendant components such as app-order-lines and app-order-totals can resolve that editor-specific instance unless they override the token locally.[3][8]

7.3 Simplified resolution order

For a component or directive request, Angular first searches the current element injector and then parent element injectors. If the token is not found in the reachable element hierarchy, resolution continues through the relevant environment injector hierarchy. Failure at the final null injector produces a NullInjectorError unless the request is optional.[8][24]

7.4 Local overrides

nearest provider wins
@Injectable({ providedIn: 'root' })
export class ThemeService {
  readonly name = 'global';
}

@Component({
  selector: 'app-preview',
  standalone: true,
  providers: [
    {
      provide: ThemeService,
      useClass: PreviewThemeService,
    },
  ],
  template: `...`,
})
export class PreviewComponent {
  // Resolves PreviewThemeService, not the root instance.
  readonly theme = inject(ThemeService);
}

A nearer provider shadows a provider for the same token farther up the hierarchy. Sibling and ancestor branches do not see providers declared only below or beside them because dependency lookup proceeds upward, not downward or sideways.[3][8][24]

8. Constructor injection

Constructor injection declares dependencies as constructor parameters. Angular resolves each token before invoking the constructor and supplies the resulting values. A class type annotation can serve directly as the token; @Inject(token) identifies tokens that cannot be inferred from the parameter’s class type.[17][25]

8.1 Class-token constructor injection

constructor injection
@Injectable({ providedIn: 'root' })
export class CheckoutService {
  constructor(
    private readonly cart: CartStore,
    private readonly orders: OrderApi,
    private readonly logger: Logger,
  ) {}

  placeOrder(): Observable<Order> {
    return this.orders
      .create(this.cart.toRequest())
      .pipe(
        tap(order =>
          this.logger.info(
            `Created order ${order.id}`,
          ),
        ),
      );
  }
}

8.2 Constructor injection with @Inject

@Inject with InjectionToken
@Injectable({ providedIn: 'root' })
export class ReportClient {
  constructor(
    private readonly http: HttpClient,
    @Inject(API_CONFIGURATION)
    private readonly config: ApiConfiguration,
  ) {}

  getReport(id: string): Observable<Report> {
    return this.http.get<Report>(
      `${this.config.baseUrl}/reports/` +
      encodeURIComponent(id),
    );
  }
}

Without @Inject(API_CONFIGURATION), the interface type is unavailable at runtime and cannot identify the provider. The parameter decorator supplies the actual runtime token.[4][25]

8.3 Constructor decorators for resolution control

constructor resolution modifiers
constructor(
  @Optional()
  private readonly analytics: Analytics | null,

  @Self()
  @Optional()
  private readonly localControl: NgControl | null,

  @SkipSelf()
  private readonly parentTheme: ThemeService,

  @Host()
  @Optional()
  private readonly hostForm: ControlContainer | null,
) {}

@Optional, @Self, @SkipSelf, and @Host correspond to functional injection options. They respectively permit a null result, restrict lookup to the current injector, begin lookup at the parent, or stop element-injector lookup at the host boundary.[8][26][27][28]

8.4 Strengths and trade-offs

StrengthTrade-off
Dependencies are visible in the public constructor signature.Many dependencies can create a long constructor and expose architectural over-coupling.
Works naturally with parameter decorators such as @Inject and @Optional.Optional dependency nullability can be obscured in older code if types are not strict.
Easy to instantiate manually when constructor arguments are simple.Angular-created classes still require injectable metadata when their dependencies need compilation support.[15]

9. Functional injection with inject()

inject() resolves a token from the currently active injector. It is legal only while an injection context is active, such as class construction, field initialization, a provider factory, an InjectionToken factory, a router guard, an interceptor, or a function explicitly run in an injection context.[14][17][29]

9.1 Field-initializer injection

functional injection in a service
@Injectable({ providedIn: 'root' })
export class InvoiceService {
  private readonly clock = inject(Clock);
  private readonly invoices = inject(InvoiceApi);
  private readonly config = inject(API_CONFIGURATION);

  createDraft(): InvoiceDraft {
    return {
      createdAt: this.clock.now(),
      currency: this.config.defaultCurrency,
      lines: [],
    };
  }
}

9.2 Functional framework APIs

inject() in a route guard
export const authenticatedGuard:
  CanActivateFn = (_route, state) => {
    const auth = inject(AuthService);
    const router = inject(Router);

    return auth.isAuthenticated()
      ? true
      : router.createUrlTree(['/login'], {
          queryParams: {
            returnUrl: state.url,
          },
        });
  };
inject() in an HTTP interceptor
export const requestIdInterceptor:
  HttpInterceptorFn = (request, next) => {
    const ids = inject(RequestIdGenerator);

    return next(
      request.clone({
        setHeaders: {
          'X-Request-ID': ids.next(),
        },
      }),
    );
  };

Router guards and functional HTTP interceptors execute in injection contexts, so they can resolve services without defining a class solely for dependency injection.[29]

9.3 Resolution options

functional resolution modifiers
const localStore = inject(DraftStore, {
  self: true,
  optional: true,
});

const inheritedTheme = inject(ThemeService, {
  skipSelf: true,
});

const hostContainer = inject(ControlContainer, {
  host: true,
  optional: true,
});

The InjectOptions object supports optional, self, skipSelf, and host. host applies to element-injector lookup and has no effect for environment-injector resolution. Incompatible combinations include self with skipSelf and self with host.[8][26]

9.4 The injection-context boundary

invalid late inject() call
@Component({ /* ... */ })
export class IncorrectComponent {
  ngOnInit(): void {
    // ERROR NG0203: lifecycle methods run after construction.
    const api = inject(CustomerApi);
  }
}
capture dependency during construction
@Component({ /* ... */ })
export class CorrectComponent {
  private readonly api = inject(CustomerApi);

  ngOnInit(): void {
    this.api.load();
  }
}

Calling inject() in an arbitrary method or lifecycle hook fails because the class-creation context has ended. Angular reports error NG0203 for calls outside an injection context.[14][29][30]

9.5 runInInjectionContext()

run external code in an injection context
@Injectable({ providedIn: 'root' })
export class PluginRunner {
  private readonly environmentInjector =
    inject(EnvironmentInjector);

  run(plugin: () => void): void {
    runInInjectionContext(
      this.environmentInjector,
      plugin,
    );
  }
}

runInInjectionContext() temporarily makes a supplied injector active for the synchronous stack frame. inject() cannot be deferred past an await or into a later asynchronous callback merely because that callback was created inside the function.[29][31]

9.6 Reusable injection functions

custom inject helper
export function injectFeatureFlags(): FeatureFlags {
  assertInInjectionContext(injectFeatureFlags);

  return inject(FEATURE_FLAGS, {
    optional: true,
  }) ?? DEFAULT_FEATURE_FLAGS;
}

assertInInjectionContext() lets a reusable function fail with an error that points to the helper API rather than only the internal inject() call.[29][32]

10. Singleton services and scope

Angular documentation often describes a root-provided service as a singleton because consumers resolving through the root provider receive one shared instance. The more precise statement is that a provider record normally creates and caches one value in the injector that owns that record. Re-providing the same token in another injector creates another scoped value.[2][8][16][24]

10.1 Application-wide instance

root-scoped shared service
@Injectable({
  providedIn: 'root',
})
export class CurrentUserStore {
  private readonly _user =
    signal<User | null>(null);

  readonly user = this._user.asReadonly();

  setUser(user: User): void {
    this._user.set(user);
  }

  clear(): void {
    this._user.set(null);
  }
}

Root scope is suitable for application configuration, authentication state, root API clients, telemetry, and caches intentionally shared across the application. It is not appropriate merely because a service is convenient to inject.

10.2 Instance per component subtree

component-scoped service
@Injectable()
export class WizardStore {
  private readonly _step = signal(0);
  readonly step = this._step.asReadonly();

  next(): void {
    this._step.update(value => value + 1);
  }
}

@Component({
  selector: 'app-onboarding-wizard',
  standalone: true,
  providers: [WizardStore],
  template: `
    <app-wizard-progress />
    <router-outlet />
  `,
})
export class OnboardingWizardComponent {
  readonly wizard = inject(WizardStore);
}

Every wizard component instance receives an independent store, and its descendants can share that instance. Angular ties the component-provided instance to the component’s lifetime; when the component subtree is destroyed, that scoped provider is destroyed as well.[3][24]

10.3 Instance per route environment

route-scoped checkout state
export const CHECKOUT_ROUTES: Routes = [
  {
    path: '',
    providers: [
      CheckoutSession,
      CheckoutDraftStore,
    ],
    component: CheckoutShellPage,
    children: [
      { path: 'address', component: AddressPage },
      { path: 'payment', component: PaymentPage },
      { path: 'review', component: ReviewPage },
    ],
  },
];

Route providers create a child environment injector for the route subtree. They are useful for state and dependencies that should be shared across routed children but should not become application-global.[3][22][24]

10.4 Platform scope

providedIn: 'platform' places a provider in the platform injector above application injectors. It can therefore be shared by multiple Angular applications using the same platform. This is specialized behavior; application state normally belongs at root or a narrower explicit scope.[4][7]

11. Resolution modifiers

11.1 Optional injection

optional dependency
const analytics = inject(ANALYTICS, {
  optional: true,
});

analytics?.track('page.view');

Optional injection returns null instead of throwing when the token cannot be resolved. The consumer must model and handle the nullable result rather than asserting that the value exists.[26][27]

11.2 Self-only lookup

self lookup
const localControl = inject(NgControl, {
  self: true,
  optional: true,
});

self: true prevents fallback to parent injectors. It is useful when behavior is valid only if a token is provided on the current element or injector.[8][26][28]

11.3 Skip the local provider

skipSelf lookup
@Injectable()
export class ChildThemeService {
  private readonly parent = inject(
    ThemeService,
    { skipSelf: true },
  );

  readonly inheritedName = this.parent.name;
}

skipSelf: true begins resolution at the parent injector. A local implementation can use this to decorate or extend an inherited service while avoiding injection of itself.[26][27]

11.4 Host boundary

host-bounded lookup
@Directive({
  selector: '[appFieldError]',
  standalone: true,
})
export class FieldErrorDirective {
  private readonly container = inject(
    ControlContainer,
    {
      host: true,
      optional: true,
    },
  );
}

host: true stops element-injector resolution at the current component’s host boundary. It is meaningful for element injection and is a no-op for environment injectors.[26][33]

12. providers and viewProviders

A component’s providers are available to the component’s view descendants and to eligible projected content. viewProviders restricts the values to the component’s own view and excludes content projected through <ng-content>. Projected content belongs to the parent’s view and resolves dependencies accordingly.[24][34]

viewProviders isolates view-only state
@Injectable()
export class InternalPanelState {}

@Component({
  selector: 'app-secure-panel',
  standalone: true,
  viewProviders: [
    InternalPanelState,
  ],
  template: `
    <app-panel-toolbar />
    <ng-content />
  `,
})
export class SecurePanelComponent {
  readonly state = inject(InternalPanelState);
}
content projection boundary
<!-- The toolbar is in SecurePanel's view and can inject the state. -->
<app-secure-panel>
  <!-- Projected content belongs to the parent view and cannot
       resolve SecurePanel's viewProviders entry. -->
  <app-external-panel-content />
</app-secure-panel>

Use viewProviders when a dependency is an implementation detail of the component’s own template. Use providers when projected directives or components should participate in the same scoped service contract.

13. Environment providers and library configuration

EnvironmentProviders wrap provider collections intended only for environment injectors. makeEnvironmentProviders() prevents such provider bundles from being accidentally placed in a component’s element injector, where application-wide initialization or multi-provider behavior could be incorrect.[35][36]

13.1 Build a typed provideFeature() API

provide-audit.ts
export interface AuditOptions {
  readonly endpoint: string;
  readonly includeConsole: boolean;
}

export const AUDIT_OPTIONS =
  new InjectionToken<AuditOptions>(
    'audit.options',
  );

export function provideAudit(
  options: AuditOptions,
): EnvironmentProviders {
  return makeEnvironmentProviders([
    {
      provide: AUDIT_OPTIONS,
      useValue: options,
    },
    AuditClient,
    AuditQueue,
    {
      provide: APP_INITIALIZER,
      multi: true,
      useFactory: () => {
        const queue = inject(AuditQueue);
        return () => queue.restore();
      },
    },
  ]);
}
consume the environment provider bundle
export const appConfig: ApplicationConfig = {
  providers: [
    provideAudit({
      endpoint: '/api/audit',
      includeConsole: false,
    }),
  ],
};

A feature installer function creates a discoverable, typed configuration API and keeps related providers together. Environment-provider wrapping communicates that the bundle belongs at application, route, or other environment scope rather than a component injector.[35][36]

13.2 NgModule-based provider configuration

NgModule provider
@NgModule({
  providers: [
    LegacyFeatureService,
  ],
})
export class LegacyFeatureModule {}

NgModule applications use a ModuleInjector hierarchy whose providers are flattened from imported modules. Standalone applications generally prefer application configuration, route providers, and provideFeature()-style APIs, though NgModule provider patterns remain relevant in existing applications and libraries.[7][8]

14. Dynamic injectors

Most application code should let Angular create and manage injectors. Advanced infrastructure can create a child EnvironmentInjector explicitly from providers and a parent. The resulting injector is destroyable and must be cleaned up when its dynamically hosted feature is removed.[22][23][37]

      [

        },

      ],

      `plugin:${pluginId}`,
    );
  }
}
destroy a dynamic injector
const injector =

    'inventory',
    [InventoryPluginService],
  );

try {
  const plugin =
    injector.get(InventoryPluginService);

} finally {

}

Injector.get for deferred lookup
@Injectable({ providedIn: 'root' })

15. Complete example: configurable notification subsystem

The following subsystem combines tree-shakable services, an interface token, an alias, a factory-backed configuration token, a multi-provider extension point, application installation, local override, constructor injection, and functional injection.

notification.tokens.ts
export type NotificationLevel =
  | 'info'
  | 'warning'
  | 'error';

export interface Notification {
  readonly level: NotificationLevel;
  readonly message: string;
  readonly timestamp: Date;
}

export interface NotificationSink {
  publish(notification: Notification): void;
}

export const NOTIFICATION_SINK =
  new InjectionToken<NotificationSink>(
    'notification.sink',
  );

export interface NotificationPolicy {
  readonly minimumLevel: NotificationLevel;
  readonly consoleEnabled: boolean;
}

export const NOTIFICATION_POLICY =
  new InjectionToken<NotificationPolicy>(
    'notification.policy',
    {
      providedIn: 'root',
      factory: () => ({
        minimumLevel: 'info',
        consoleEnabled: true,
      }),
    },
  );

export interface NotificationEnricher {
  enrich(
    notification: Notification,
  ): Notification;
}

export const NOTIFICATION_ENRICHERS =
  new InjectionToken<
    readonly NotificationEnricher[]
  >('notification.enrichers');
in-memory-notification-sink.ts
@Injectable({ providedIn: 'root' })
export class InMemoryNotificationSink
  implements NotificationSink {

  private readonly _items =
    signal<readonly Notification[]>([]);

  readonly items = this._items.asReadonly();

  publish(notification: Notification): void {
    this._items.update(items => [
      notification,
      ...items,
    ]);
  }

  clear(): void {
    this._items.set([]);
  }
}
correlation-enricher.ts
@Injectable({ providedIn: 'root' })
export class CorrelationEnricher
  implements NotificationEnricher {

  private readonly ids = inject(RequestIdGenerator);

  enrich(
    notification: Notification,
  ): Notification {
    return {
      ...notification,
      message:
        `${notification.message} ` +
        `[${this.ids.current()}]`,
    };
  }
}
notification.service.ts
@Injectable({ providedIn: 'root' })
export class NotificationService {
  private readonly sink = inject(NOTIFICATION_SINK);

  private readonly policy =
    inject(NOTIFICATION_POLICY);

  private readonly enrichers =
    inject(
      NOTIFICATION_ENRICHERS,
      { optional: true },
    ) ?? [];

  notify(
    level: NotificationLevel,
    message: string,
  ): void {
    if (!isEnabled(level, this.policy.minimumLevel)) {
      return;
    }

    const base: Notification = {
      level,
      message,
      timestamp: new Date(),
    };

    const enriched = this.enrichers.reduce(
      (current, enricher) =>
        enricher.enrich(current),
      base,
    );

    this.sink.publish(enriched);

    if (this.policy.consoleEnabled) {
      console.info(enriched);
    }
  }
}

function isEnabled(
  level: NotificationLevel,
  minimum: NotificationLevel,
): boolean {
  const rank: Record<NotificationLevel, number> = {
    info: 0,
    warning: 1,
    error: 2,
  };

  return rank[level] >= rank[minimum];
}
provide-notifications.ts
export interface NotificationOptions {
  readonly minimumLevel?: NotificationLevel;
  readonly consoleEnabled?: boolean;
}

export function provideNotifications(
  options: NotificationOptions = {},
): EnvironmentProviders {
  return makeEnvironmentProviders([
    InMemoryNotificationSink,
    {
      provide: NOTIFICATION_SINK,
      useExisting: InMemoryNotificationSink,
    },
    {
      provide: NOTIFICATION_POLICY,
      useValue: {
        minimumLevel:
          options.minimumLevel ?? 'info',
        consoleEnabled:
          options.consoleEnabled ?? true,
      },
    },
    {
      provide: NOTIFICATION_ENRICHERS,
      multi: true,
      useClass: CorrelationEnricher,
    },
  ]);
}
app.config.ts
export const appConfig: ApplicationConfig = {
  providers: [
    provideNotifications({
      minimumLevel: 'warning',
      consoleEnabled: false,
    }),
  ],
};
notification-center.component.ts
@Component({
  selector: 'app-notification-center',
  standalone: true,
  template: `
    <button
      type="button"
      (click)="notifications.clear()">
      Clear

local policy override
@Component({
  selector: 'app-preview-shell',

The application provider installs the default graph in the root environment injector. The preview shell overrides only the policy token in its element subtree; the sink and enrichers continue resolving from parent injectors. 16. Testing dependency-injected code

Angular’s testing utilities configure a test injector through TestBed. Tests can replace production providers with values, spies, alternate classes, aliases, or factories and can resolve the system under test from the configured injector.[38]

16.1 Test pure logic without DI

plain unit test
describe('isEnabled', () => {
  it('filters levels below the threshold', () => {
    expect(isEnabled('info', 'warning'))
      .toBeFalse();

    expect(isEnabled('error', 'warning'))
      .toBeTrue();
  });
});

Dependency injection should not force all logic through TestBed. Pure functions and classes with explicit plain dependencies can be tested directly.

16.2 Substitute providers

provider-substitution test
describe('NotificationService', () => {
  let service: NotificationService;
  let sink: jasmine.SpyObj<NotificationSink>;

  beforeEach(() => {

      providers: [
        NotificationService,

  });
});

17. Circular dependencies and forward references

A runtime DI cycle occurs when constructing dependency A requires B while constructing B requires A. Angular reports circular dependency error NG0200. The best fix is usually to redesign responsibilities or introduce a lower-level abstraction rather than hide the cycle.[24][39]

runtime circular dependency
@Injectable({ providedIn: 'root' })
export class AService {
  private readonly b = inject(BService);
}

@Injectable({ providedIn: 'root' })
export class BService {
  private readonly a = inject(AService);
}

17.1 Break the cycle with a port

dependency inversion breaks the cycle
export interface SessionReader {
  currentUserId(): string | null;
}

export const SESSION_READER =
  new InjectionToken<SessionReader>(
    'session.reader',
  );

@Injectable({ providedIn: 'root' })
export class AuthService
  implements SessionReader {

  currentUserId(): string | null {
    // ...
    return null;
  }
}

@Injectable({ providedIn: 'root' })
export class AuditService {
  private readonly session =
    inject(SESSION_READER);
}

providers: [
  AuthService,
  {
    provide: SESSION_READER,
    useExisting: AuthService,
  },
]

17.2 forwardRef() solves declaration timing, not design cycles

forward reference
@Component({
  selector: 'app-tree-node',
  standalone: true,
  imports: [
    forwardRef(() => TreeNodeComponent),
  ],
  template: `...`,
})
export class TreeNodeComponent {}

forwardRef() delays resolving a reference whose declaration is not yet available, including self-references in decorator metadata. It does not remove a runtime cycle in which two services require each other during construction.[40]

18. Debugging dependency injection

18.1 NullInjectorError

A NullInjectorError means the resolver reached the end of the permitted hierarchy without a provider for the requested token. Check automatic provision, application or route providers, component ancestry, token identity, and resolution modifiers.[24]

18.2 Unexpected multiple instances

Common causes include repeating a service in component providers, providing it separately in sibling branches, or installing it independently in a lazy route. Inspect the provider location rather than assuming @Injectable alone guarantees one instance.[8][24]

accidental local singleton override
@Component({
  // Creates a new instance for every component instance.
  providers: [CurrentUserStore],
})
export class ProfileComponent {}

18.3 Token identity mismatch

same description, different tokens
// feature-a.ts
export const CONFIG =
  new InjectionToken<Config>('config');

// feature-b.ts — not the same token:
export const CONFIG =
  new InjectionToken<Config>('config');

Descriptions do not identify tokens; object identity does. Define and export the token once, then import that same object everywhere.[4][5]

18.4 Duplicate non-multi providers

When the same injector receives multiple ordinary providers for one token, later configuration can replace earlier configuration. Multi-providers must use multi: true consistently for the token. Prefer one installation API to make ordering explicit.

18.5 Diagnostic checklist

  • What exact token is requested?
  • At what element, route, or environment is the consumer created?
  • Which injector owns the nearest provider?
  • Has the token been recreated in another file?
  • Do self, skipSelf, host, or optional change the search?
  • Was a root service accidentally re-provided locally?
  • Does a factory create an indirect cycle?
  • Is inject() being called after construction or after an asynchronous boundary?

19. Production architecture patterns

19.1 Inject capabilities, not concrete infrastructure

capability-oriented token
export abstract class FileStore {
  abstract put(
    path: string,
    data: Blob,
  ): Observable<void>;
}

@Injectable()
export class S3FileStore implements FileStore {
  // ...
}

providers: [
  S3FileStore,
  {
    provide: FileStore,
    useExisting: S3FileStore,
  },
]

Consumers depend on the capability contract, while the provider configuration selects the implementation. This supports testing, platform variants, and migration without changing every consumer.

19.2 Scope by lifetime and sharing

Provider scope should match the state’s natural lifetime. Root scope is not a default for every mutable object; component and route providers are valuable for independent feature instances and automatic cleanup.[3][8][22]

19.3 Avoid the service-locator style

hidden dependency through Injector
@Injectable({ providedIn: 'root' })
export class AvoidThis {
  constructor(
    private readonly injector: Injector,
  ) {}

  save(): void {
    // Hidden dependency:
    this.injector.get(OrderApi).save();
  }
}

Injecting Injector and resolving arbitrary services throughout methods hides the dependency graph and weakens testability. Prefer direct injection unless retrieval is genuinely dynamic or deferred.

19.4 Offer provider installer functions

Reusable libraries should expose functions such as provideAudit(options) that return environment providers. This centralizes defaults, multi-provider registration, implementation aliases, and validation of options.[35][36]

19.5 Treat injected configuration as immutable

immutable configuration
export const APP_OPTIONS =
  new InjectionToken<Readonly<AppOptions>>(
    'app.options',
  );

providers: [
  {
    provide: APP_OPTIONS,
    useValue: Object.freeze({
      apiUrl: '/api',
      production: true,
    }),
  },
]

Provider identity is shared within scope. Immutable configuration prevents one consumer from silently changing another consumer’s environment.

19.6 Keep provider factories deterministic

Provider factories should create dependencies, not perform uncontrolled application workflows. Put startup work behind explicit initializers or lifecycle services so errors, ordering, and cleanup remain observable.

20. Common pitfalls

PitfallConsequenceBetter approach
Assuming every service is globally singleton Local or route providers create separate instances. Identify the injector that owns the provider.[8][24]
Recreating an InjectionToken The provider and consumer use different object identities. Export one canonical token instance.[4][5]
Using useClass when an alias is intended Two tokens can produce separate class instances. Use useExisting for shared identity.[19]
Calling inject() in ngOnInit or an event handler No active injection context; NG0203. Capture the dependency in a field initializer or constructor.[14][30]
Manual root registration for every service Unused services remain referenced and configuration becomes centralized noise. Use automatic tree-shakable provision when no substitution or narrower scope is needed.[3][13]
Component-scoping authentication state Each component sees a different session instance. Provide session state at root unless isolation is intentional.
Using Injector.get() everywhere Dependencies become hidden and late failures replace explicit contracts. Inject exact dependencies directly.
Using forwardRef() to conceal a service cycle The runtime circular construction remains. Introduce a lower-level token or split responsibilities.[39][40]
Providing environment-only infrastructure in a component Initializers and global multi-providers may run at the wrong scope. Return EnvironmentProviders from installation APIs.[35][36]
Making optional injection non-null with ! A legitimate missing provider becomes a runtime failure. Handle null explicitly or make the provider required.[26]

21. Decision guide

QuestionRecommended choice
Is this an application-wide class service?@Injectable({ providedIn: 'root' }) or current @Service() when its constraints fit.
Is the dependency an interface, function, primitive, or configuration object?InjectionToken<T>.
Should two tokens resolve to the same object?useExisting.
Does creation depend on runtime configuration?useFactory or a token factory.
Can several features contribute values?Multi-provider token.
Should each component instance have independent state?Component providers.
Should a route subtree share state?Route providers.
Should projected content be excluded?viewProviders.
Does a library provider bundle belong only in environment scope?makeEnvironmentProviders().
Is the code a guard, interceptor, resolver, or provider factory?Functional inject().

23. Conclusion

Angular dependency injection is a hierarchical mapping from runtime tokens to provider recipes and cached values. Automatic root providers make common services globally available and tree-shakable; manual providers enable substitution, configuration, extension, and narrower lifetimes. InjectionToken gives non-class contracts a runtime identity, while constructor injection and inject() provide complementary ways to express dependencies.[1][3][4][7][14]

The most important architectural decision is provider location. It determines visibility, identity, cleanup, override behavior, and the practical meaning of “singleton.” Design tokens around capabilities, place providers at the narrowest scope that matches the required lifetime, and let consumers depend on explicit contracts rather than constructing infrastructure or searching an injector manually.
