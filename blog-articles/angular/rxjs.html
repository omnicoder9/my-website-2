RxJS

RxJS models values and events as observable sequences. An Observable describes a potentially lazy execution; an Observer receives next, error, and completion notifications; a Subscription represents disposable execution; operators create new Observables by transforming, combining, flattening, sharing, recovering, or terminating streams. In Angular, this model underlies HttpClient, router events, reactive forms, and many ecosystem APIs.

1. RxJS in one model

RxJS is a JavaScript library for composing asynchronous and event-based programs with observable sequences. Its core vocabulary includes Observable, Observer, Subscription, Subject, schedulers, and operators inspired partly by collection operations such as mapping, filtering, and reduction.[1][2]

Source describes values
Operators build pipeline
Subscribe starts execution
Observer receives notifications

Observable

A producer abstraction that can emit zero or more values synchronously or asynchronously and then optionally terminate.[3]

Observer

A consumer object containing some or all of the next, error, and complete callbacks.[4]

Subscription

A disposable handle for an Observable execution. Calling unsubscribe() cancels that execution and runs its teardown logic.[5]

Marble notation depicts time from left to right, emitted values as symbols, completion as |, and an error as #. It is a reasoning and testing notation rather than a runtime data format.

The critical distinction An Observable is not the emitted value and not necessarily an already-running process. It is a description whose execution normally begins for a particular consumer when that consumer subscribes.[3][6]

2. Historical development

Reactive Extensions

Reactive Extensions established a common abstraction for live sequences and declarative event processing, complementing pull-based enumerable sequences with push-based observable sequences. Rx implementations spread across .NET and other languages, and RxJS became the JavaScript implementation.[7][8]

RxJS 4

The earlier rx package was developed by Microsoft with the open-source community and exposed a large prototype-oriented API for composing asynchronous and event-based programs.[9]

RxJS 5 rewrite

The modern rxjs package was a rewrite of the earlier Reactive-Extensions/RxJS codebase, with goals that included better performance, modularity, debuggable call stacks, and a reduced API surface while preserving broad conceptual compatibility.[8][10]

Pipeable operators and modular imports

RxJS 5.5 introduced pipeable operator style, and RxJS 6 standardized it while providing compatibility tooling for earlier prototype-patched code. Pipeable composition made operator dependencies explicit and allowed Observable instances to remain unmodified.[2][11]

RxJS 7

RxJS 7 continued API reduction and type improvements. From RxJS 7.2, creation functions and pipeable operators can be imported from the top-level rxjs package. As of 4 August 2026, npm lists 7.8.2 as the public production release.[10][12]

RxJS 8 development

The official repository’s main development branch targets RxJS 8, while 7.x remains a maintained branch. Code intended for current production applications should be written against the installed version rather than unreleased branch APIs.[8]

3. Observables

An Observable is a lazy push-based computation that can produce zero to potentially unbounded values over time. A function returns one synchronous value, a Promise settles with one eventual result, and an Observable can deliver multiple synchronous or asynchronous notifications from subscription onward.[3]

3.1 Create an Observable manually

manual Observable
import {
  Observable,
} from 'rxjs';

const clock$ = new Observable<Date>(
  subscriber => {
    subscriber.next(new Date());

    const timerId = setInterval(() => {
      subscriber.next(new Date());
    }, 1_000);

    return () => {
      clearInterval(timerId);
    };
  },
);

The Observable constructor receives subscription logic. It can emit notifications and return teardown logic that releases timers, listeners, sockets, or other resources when execution ends.[3][6]

3.2 Subscription starts execution

independent subscriptions
const first =
  clock$.subscribe(value => {
    console.log(
      'first',
      value.toISOString(),
    );
  });

const second =
  clock$.subscribe(value => {
    console.log(
      'second',
      value.toISOString(),
    );
  });

setTimeout(() => {
  first.unsubscribe();
  second.unsubscribe();
}, 5_000);

Each subscription to this cold Observable creates an independent timer. Calling subscribe starts the work; merely constructing the Observable does not start it. Observable callbacks are not inherently asynchronous—an Observable such as of() emits synchronously unless scheduling changes its behavior.[3][6]

3.3 Notification grammar

An Observable execution may emit any number of next notifications and then at most one terminal notification: either error or complete. No notifications are delivered after termination.[3][13]

Observable contract
const finite$ = new Observable<number>(
  subscriber => {
    subscriber.next(1);
    subscriber.next(2);
    subscriber.next(3);
    subscriber.complete();

    // Ignored after completion.
    subscriber.next(4);
  },
);

3.4 Prefer creation functions

common creation functions
import {
  defer,
  EMPTY,
  from,
  fromEvent,
  interval,
  of,
  timer,
} from 'rxjs';

const values$ = of(1, 2, 3);

const array$ = from([
  'alpha',
  'beta',
]);

const clicks$ =
  fromEvent<MouseEvent>(
    document,
    'click',
  );

const ticks$ = interval(1_000);

const delayed$ = timer(2_000);

const deferred$ = defer(() => {
  const requestedAt = new Date();

  return of(requestedAt);
});

const nothing$ = EMPTY;

Creation functions encode established source behavior and teardown correctly. defer delays source construction until each subscription, which is useful when a value or resource must be fresh per execution.[3][14]

“Hot” and “cold” describe producer/execution behavior, while “unicast” and “multicast” describe whether consumers share an execution. Operators such as share and shareReplay can turn a cold source into a shared observable execution.

3.6 Angular HttpClient Observables

Angular HTTP Observable
@Injectable({
  providedIn: 'root',
})
export class ProductApi {
  private readonly http =
    inject(HttpClient);

  list(): Observable<
    readonly Product[]
  > {
    return this.http.get<
      readonly Product[]
    >('/api/products');
  }
}

Angular HttpClient methods return RxJS Observables. Subscribing sends the request, and multiple subscriptions to the same request Observable create separate backend requests. Unsubscribing from an in-progress request aborts it.[15]

4. Observers and subscribers

An Observer is a consumer contract with next, error, and complete callbacks. Observer objects may be partial; omitted callbacks do not prevent the source execution from occurring.[4][13]

4.1 Observer object

partial Observer
import {
  Observer,
  of,
} from 'rxjs';

const observer:
  Partial<Observer<number>> = {
    next: value => {
      console.log('value', value);
    },

    error: error => {
      console.error('failed', error);
    },

    complete: () => {
      console.log('complete');
    },
  };

of(1, 2, 3).subscribe(observer);

4.2 Subscriber

RxJS internally wraps subscription callbacks in a Subscriber, which implements Observer behavior and extends Subscription behavior. Application code generally supplies an Observer object rather than constructing Subscribers directly.[16]

4.3 Always design the error path

explicit terminal handlers
source$.subscribe({
  next: value => {
    render(value);
  },

  error: error => {
    reportUnexpectedFailure(error);
  },

  complete: () => {
    markFinished();
  },
});

If an Observable errors and the subscription has no error handler, RxJS reports the error asynchronously through its unhandled-error mechanism, where surrounding synchronous try/catch cannot catch it. Prefer pipeline-level recovery for expected failures and a terminal error handler for unexpected failures.[6][17]

4.4 Prefer the object form

readable subscribe form
source$.subscribe({
  next: handleValue,
  error: handleError,
  complete: handleComplete,
});

The object form makes notification roles explicit and avoids positional ambiguity. It also aligns with the Observer abstraction.

5. Subscriptions and teardown

A Subscription represents a disposable resource, normally an active Observable execution. Calling unsubscribe() runs registered teardown and marks the Subscription closed. Unsubscription is cancellation, not normal completion, so it does not invoke the Observer’s complete callback.[5][6]

5.1 Manual teardown

manual unsubscription
import {
  interval,
} from 'rxjs';

const subscription =
  interval(1_000).subscribe(value => {
    console.log(value);
  });

setTimeout(() => {
  subscription.unsubscribe();
}, 5_500);

5.2 Composite subscriptions

Subscription.add
import {
  Subscription,
  fromEvent,
  interval,
} from 'rxjs';

const composite =
  new Subscription();

composite.add(
  interval(1_000).subscribe(
    value => console.log(value),
  ),
);

composite.add(
  fromEvent(window, 'resize')
    .subscribe(() => {
      console.log('resized');
    }),
);

// Later:
composite.unsubscribe();

A parent Subscription can contain child subscriptions and teardown functions. Unsubscribing the parent unsubscribes its children.[5]

5.3 Producer teardown

resource-safe custom source
const pointerMoves$ =
  new Observable<PointerEvent>(
    subscriber => {
      const handler = (
        event: PointerEvent,
      ): void => {
        subscriber.next(event);
      };

      window.addEventListener(
        'pointermove',
        handler,
      );

      return () => {
        window.removeEventListener(
          'pointermove',
          handler,
        );
      };
    },
  );

Every custom Observable that acquires a resource should return corresponding teardown. RxJS invokes teardown on explicit unsubscription and when the subscription closes through completion or error.

5.4 Finalization

finalize on every termination path
import {
  finalize,
} from 'rxjs';

request$.pipe(
  finalize(() => {
    this.loading.set(false);
  }),
).subscribe({
  next: response => {
    this.data.set(response);
  },
  error: error => {
    this.error.set(error);
  },
});

finalize invokes its callback when the source completes, errors, or is explicitly unsubscribed, making it suitable for resource and loading-state cleanup.[18]

6. Subjects

A Subject is both an Observable and an Observer. Consumers can subscribe to it, while producers can call next, error, and complete. A Subject multicasts each notification to its currently registered observers.[19][20]

6.1 Basic Subject

multicast Subject
import {
  Subject,
} from 'rxjs';

const notifications =
  new Subject<string>();

notifications.subscribe(value => {
  console.log('A', value);
});

notifications.subscribe(value => {
  console.log('B', value);
});

notifications.next('saved');
notifications.next('synchronized');
notifications.complete();

6.2 Hide the writable side

encapsulated Subject
@Injectable({
  providedIn: 'root',
})
export class ToastBus {
  private readonly messagesSubject =
    new Subject<ToastMessage>();

  readonly messages$ =
    this.messagesSubject.asObservable();

  show(message: ToastMessage): void {
    this.messagesSubject.next(message);
  }
}

Exposing asObservable() prevents consumers from calling Subject mutation methods through the published property. Keep the Subject private and expose domain methods that validate or enrich events.[20]

6.3 Events versus state

SemanticsSuitable source
“A save just occurred.”Subject<SaveEvent>.
“The current authenticated user is …”BehaviorSubject or signal/store with a current value.
“Late subscribers need the last five log entries.”ReplaySubject with a bounded buffer.
“Publish only the final value when processing completes.”AsyncSubject, or a finite pipeline designed around completion.

6.4 Subject termination is permanent

terminal Subject
const subject =
  new Subject<number>();

subject.next(1);
subject.complete();

// Ignored:
subject.next(2);

A Subject cannot be “reopened” after error or completion. If the application requires a repeatable workflow, model each execution as a new Observable rather than completing a long-lived state Subject accidentally.

7. BehaviorSubject

A BehaviorSubject requires an initial value, retains the latest value, and emits that current value immediately to each new subscriber. It represents a value that has a meaningful current state rather than a transient event.[19][21]

BehaviorSubject state store
import {
  BehaviorSubject,
  distinctUntilChanged,
  map,
} from 'rxjs';

export interface SessionState {
  readonly status:
    | 'anonymous'
    | 'authenticated';

  readonly user:
    User | null;
}

@Injectable({
  providedIn: 'root',
})
export class SessionStore {
  private readonly stateSubject =
    new BehaviorSubject<SessionState>({
      status: 'anonymous',
      user: null,
    });

  readonly state$ =
    this.stateSubject.asObservable();

  readonly user$ = this.state$.pipe(
    map(state => state.user),
    distinctUntilChanged(),
  );

  authenticate(user: User): void {
    this.stateSubject.next({
      status: 'authenticated',
      user,
    });
  }

  signOut(): void {
    this.stateSubject.next({
      status: 'anonymous',
      user: null,
    });
  }
}

7.1 Current-value semantics

late BehaviorSubject subscriber
const theme =
  new BehaviorSubject<
    'light' | 'dark'
  >('light');

theme.next('dark');

theme.subscribe(value => {
  // Immediately receives "dark".
  console.log(value);
});

7.2 When to use it

  • The state always has a defined initial value.
  • New subscribers need the current value immediately.
  • The source is shared and imperative writes are deliberately controlled.
  • Observable interoperability is needed across an existing RxJS architecture.
Do not use BehaviorSubject merely to obtain storage In modern Angular, a writable signal is often simpler for synchronous local or shared state. BehaviorSubject remains valuable when the state participates deeply in RxJS operator pipelines, must implement Observable APIs, or needs synchronous emission on subscription.[22]

8. ReplaySubject

A ReplaySubject stores a bounded or time-bounded history and replays retained values to new subscribers. Unlike BehaviorSubject, it need not have an initial current value and can replay more than one item.[19][23]

bounded replay buffer
import {
  ReplaySubject,
} from 'rxjs';

const recentLogs =
  new ReplaySubject<LogEntry>(
    3,
  );

recentLogs.next({
  level: 'info',
  message: 'Started',
});

recentLogs.next({
  level: 'info',
  message: 'Connected',
});

recentLogs.next({
  level: 'warning',
  message: 'Slow response',
});

recentLogs.next({
  level: 'info',
  message: 'Recovered',
});

recentLogs.subscribe(entry => {
  // Receives the most recent three entries.
  console.log(entry);
});

8.1 Time-bounded replay

count and time window
const recentEvents =
  new ReplaySubject<AppEvent>(
    100,
    30_000,
  );

The constructor can bound replay by buffer size and time window. Always choose explicit limits for long-lived streams; an unbounded replay buffer can retain every value and consume increasing memory.[23]

8.2 Appropriate uses

  • Late subscribers need recent events rather than only the current value.
  • A short bootstrap history must be replayed to dynamically created consumers.
  • A library contract must provide a replaying Observable independent of Angular state primitives.

9. Operators

Operators are the primary composition units of RxJS. Pipeable operators accept an Observable and return a new Observable without mutating the source. Creation and combination functions construct an Observable from inputs, while pipeable operator factories accept configuration and return the transformation function used by pipe.[2][24]

9.1 A declarative pipeline

pipeable operator chain
import {
  debounceTime,
  distinctUntilChanged,
  filter,
  map,
} from 'rxjs';

const normalizedQueries$ =
  rawQueries$.pipe(
    map(query =>
      query.trim().toLowerCase(),
    ),
    debounceTime(250),
    distinctUntilChanged(),
    filter(query =>
      query.length >= 2,
    ),
  );

Each operator returns a new Observable whose subscription logic delegates to its source. No values flow until a consumer subscribes to the final pipeline.[2]

9.3 Map, filter, and tap

common operators
import {
  filter,
  map,
  tap,
} from 'rxjs';

const activeUserNames$ =
  users$.pipe(
    filter(user => user.active),
    map(user => user.displayName),
    tap(name => {
      console.debug(
        'active user',
        name,
      );
    }),
  );

map transforms values, filter selects values, and tap observes notifications for logging or other transparent side effects without changing the downstream value.[24][25]

9.4 Stateful accumulation with scan

reducer-style scan
interface CounterState {
  readonly count: number;
}

type CounterAction =
  | { readonly type: 'increment' }
  | { readonly type: 'decrement' }
  | { readonly type: 'reset' };

const state$ = actions$.pipe(
  scan<CounterAction, CounterState>(
    (state, action) => {
      switch (action.type) {
        case 'increment':
          return {
            count: state.count + 1,
          };

        case 'decrement':
          return {
            count: state.count - 1,
          };

        case 'reset':
          return {
            count: 0,
          };
      }
    },
    { count: 0 },
  ),
);

scan emits each intermediate accumulated state, unlike reduce, which waits for source completion.

9.5 Combine current or final values

combineLatest and forkJoin
import {
  combineLatest,
  forkJoin,
  map,
} from 'rxjs';

const filters$ = combineLatest({
  query: query$,
  category: category$,
  sort: sort$,
});

const viewModel$ = filters$.pipe(
  map(filters =>
    buildViewModel(filters),
  ),
);

const bootstrap$ = forkJoin({
  user: userApi.getCurrent(),
  settings: settingsApi.get(),
  permissions: permissionsApi.get(),
});

combineLatest emits combinations after each input has emitted at least once and then reacts to subsequent changes. forkJoin waits for all finite inputs to complete and emits their final values; it is unsuitable when an input never completes.[26]

10. Pipeable operators

A pipeable operator has the conceptual type Observable<T> → Observable<R>. An operator factory accepts configuration first and returns that transformation. The source remains unchanged, allowing pipelines to be composed and reused.[2]

10.1 Build a reusable custom operator

custom pipeable operator
import {
  MonoTypeOperatorFunction,
  distinctUntilChanged,
  filter,
  map,
  pipe,
} from 'rxjs';

export function normalizedSearch(
  minimumLength = 2,
): MonoTypeOperatorFunction<string> {
  return pipe(
    map(value =>
      value.trim().toLowerCase(),
    ),
    distinctUntilChanged(),
    filter(value =>
      value.length >= minimumLength,
    ),
  );
}
use the custom operator
const query$ =
  rawQuery$.pipe(
    debounceTime(250),
    normalizedSearch(3),
  );

TypeMeaning
OperatorFunction<T, R>Transforms Observable<T> to Observable<R>.
MonoTypeOperatorFunction<T>Transforms Observable<T> to another Observable<T>.

10.3 Operator order changes semantics

catchError placement
const recoverEachRequest$ =
  query$.pipe(
    switchMap(query =>
      searchApi.search(query).pipe(
        catchError(() => of([])),
      ),
    ),
  );

const terminateOuterOnError$ =
  query$.pipe(
    switchMap(query =>
      searchApi.search(query),
    ),
    catchError(() => of([])),
  );

In the first pipeline, a failed inner request becomes an empty result and later queries still work. In the second, an error reaches the outer pipeline, which replaces the entire search stream with one fallback sequence; later query values no longer initiate requests.[27]

11. Higher-order Observables and flattening

A higher-order Observable emits other Observables. Flattening operators subscribe to projected inner Observables and define concurrency, ordering, and cancellation rules. Choosing the wrong operator can create stale responses, duplicated submissions, lost work, or uncontrolled concurrency.[2][28]

11.1 switchMap: latest wins

typeahead with switchMap
const results$ = query$.pipe(
  debounceTime(250),
  distinctUntilChanged(),

  switchMap(query =>
    searchApi.search(query).pipe(
      catchError(() => of([])),
    ),
  ),
);

switchMap unsubscribes from the previous inner Observable when a new source value arrives and emits only from the latest projected Observable. It fits searches, route-parameter-driven reads, and other replaceable work.[28]

11.2 concatMap: preserve order

ordered saves
const savedDrafts$ =
  draftChanges$.pipe(
    concatMap(draft =>
      api.saveDraft(draft),
    ),
  );

concatMap queues inner Observables and processes them one at a time in source order. It fits ordered writes when every operation must run.

11.3 mergeMap: concurrent work

bounded concurrent upload
const uploadedFiles$ =
  files$.pipe(
    mergeMap(
      file => api.upload(file),
      4,
    ),
  );

mergeMap subscribes to multiple inner Observables concurrently. Its concurrency parameter can bound simultaneous work. Use it when operations are independent and cancellation of earlier work is undesirable.

11.4 exhaustMap: ignore re-entry

ignore duplicate submissions
const loginResult$ =
  loginClicks$.pipe(
    exhaustMap(() =>
      authApi.login(credentials()),
    ),
  );

exhaustMap ignores new source values while the current inner Observable remains active. It fits submit actions that must not overlap.

11.5 Selection table

OperatorWhen a new outer value arrivesTypical use
switchMapUnsubscribes previous inner; switches to new inner.Search, route-driven reads, replaceable calculations.
concatMapQueues new inner after prior inner completes.Ordered saves and commands.
mergeMapRuns new inner concurrently.Independent parallel tasks.
exhaustMapIgnores new value while current inner is active.Duplicate-submit protection.

12. Multicasting and sharing

Two subscribers to a cold pipeline normally create two source executions. Multicasting operators coordinate subscribers through a shared execution. Sharing is an execution policy, not a universal optimization: it changes cancellation, caching, timing, and side-effect semantics.[19][24]

12.1 Duplicate cold execution

two HTTP subscriptions
const product$ =
  http.get<Product>(
    '/api/products/p1',
  );

// Two independent requests:
product$.subscribe();
product$.subscribe();

Angular documents that each subscription to an HttpClient request Observable sends a new backend request.[15]

12.2 Share a live execution

shared geolocation watch
const location$ =
  new Observable<GeolocationPosition>(
    subscriber => {
      const watchId =
        navigator.geolocation
          .watchPosition(
            position =>
              subscriber.next(position),
            error =>
              subscriber.error(error),
          );

      return () => {
        navigator.geolocation
          .clearWatch(watchId);
      };
    },
  ).pipe(
    share(),
  );

12.3 Share and replay one result

shared replaying request
@Injectable({
  providedIn: 'root',
})
export class ConfigurationService {
  private readonly http =
    inject(HttpClient);

  readonly configuration$ =
    this.http.get<AppConfiguration>(
      '/api/configuration',
    ).pipe(
      shareReplay({
        bufferSize: 1,
        refCount: true,
      }),
    );
}

This pipeline shares one active source subscription among concurrent consumers and retains the latest value for late consumers. The chosen reset and retention behavior must match application requirements; a replayed error, stale result, or permanently retained source can be surprising if sharing is added mechanically.

12.4 Questions before sharing

  • Should subscribers share side effects or receive independent executions?
  • Should late subscribers receive a retained value?
  • When should the source unsubscribe?
  • When should cached state reset after completion or error?
  • How will the application refresh or invalidate stale data?

13. Error handling

An error notification terminates its Observable execution. catchError intercepts the error channel and replaces the failed source with another Observable or rethrows an error. Recovery must therefore return an Observable whose values and completion behavior fit the downstream contract.[3][27]

13.1 Recover with a fallback value

fallback recovery
const products$ =
  productApi.list().pipe(
    catchError(error => {
      logger.error(
        'Product list failed',
        error,
      );

      return of<
        readonly Product[]
      >([]);
    }),
  );

13.2 Model loading and failure as data

error state as a discriminated union
type LoadState<T> =
  | {
      readonly status: 'loading';
    }
  | {
      readonly status: 'ready';
      readonly value: T;
    }
  | {
      readonly status: 'error';
      readonly message: string;
    };

const state$ = productApi.list().pipe(
  map(products => ({
    status: 'ready',
    value: products,
  } satisfies LoadState<
    readonly Product[]
  >)),

  startWith({
    status: 'loading',
  } satisfies LoadState<
    readonly Product[]
  >),

  catchError(error =>
    of({
      status: 'error',
      message:
        toUserMessage(error),
    } satisfies LoadState<
      readonly Product[]
    >),
  ),
);

Converting an expected failure into typed UI state keeps the template Observable alive and avoids using thrown errors for ordinary empty/error presentation.

13.3 Log and rethrow

rethrow after logging
const result$ = request$.pipe(
  catchError(error => {
    logger.error(
      'Request failed',
      error,
    );

    return throwError(
      () => error,
    );
  }),
);

13.4 Retry transient failures carefully

bounded exponential retry
const configuration$ =
  http.get<Configuration>(
    '/api/configuration',
  ).pipe(
    retry({
      count: 3,
      delay: (
        error,
        retryCount,
      ) => {
        if (!isTransient(error)) {
          return throwError(
            () => error,
          );
        }

        return timer(
          250 * 2 ** (retryCount - 1),
        );
      },
    }),
  );

retry resubscribes to a failed source. Retries are most appropriate for transient and idempotent operations. Automatically retrying a non-idempotent mutation can duplicate server-side effects unless the protocol supplies idempotency guarantees.[29][30]

13.5 Bound waiting time

timeout and fallback
const result$ = slowSource$.pipe(
  timeout({
    first: 3_000,
    each: 10_000,
  }),

  catchError(error => {
    return of(
      createTimeoutFallback(error),
    );
  }),
);

13.6 Always release UI state

cleanup across all terminal paths
this.loading.set(true);

request$.pipe(
  finalize(() => {
    this.loading.set(false);
  }),
).subscribe({
  next: value => {
    this.value.set(value);
  },
  error: error => {
    this.failure.set(
      toUserMessage(error),
    );
  },
});

13.7 Keep recovery at the correct boundary

Recover inside switchMap when each request may fail independently and the outer interaction should continue. Recover outside when the entire workflow should terminate or switch to a permanent fallback. Report technical details to logging while exposing safe, actionable messages to users.

14. Subscription management

Subscription management is primarily lifetime management. A subscription must not outlive the component, service, request, user action, or resource that owns it. Prefer APIs that make the lifetime declarative and use manual subscriptions only when an imperative side effect is required.

14.1 Prefer finite sources when possible

finite subscription with take
const firstUser$ =
  users$.pipe(
    filter(
      (
        user,
      ): user is User =>
        user !== null,
    ),
    take(1),
  );

take(n) completes after the requested number of values. Finite HTTP request Observables also normally complete after their response, although cancellation can still matter while a request is in flight.[31][15]

14.2 Generic RxJS takeUntil

takeUntil notifier
const stop$ =
  fromEvent(
    stopButton,
    'click',
  );

interval(1_000).pipe(
  takeUntil(stop$),
).subscribe(value => {
  console.log(value);
});

takeUntil mirrors the source until the notifier emits, then completes the result.[32]

14.3 Angular takeUntilDestroyed

automatic Angular lifecycle teardown
import {
  Component,
  inject,
} from '@angular/core';
import {
  takeUntilDestroyed,
} from '@angular/core/rxjs-interop';

@Component({
  selector: 'app-notifications',
  standalone: true,
  template: `...`,
})
export class NotificationsComponent {
  private readonly dispatcher =
    inject(NotificationDispatcher);

  private readonly popup =
    inject(PopupService);

  constructor() {
    this.dispatcher.messages$.pipe(
      takeUntilDestroyed(),
    ).subscribe(message => {
      this.popup.show(message);
    });
  }
}

takeUntilDestroyed completes the pipeline when the owning Angular context is destroyed and avoids a dedicated destroy Subject. Outside an injection context, pass an explicit DestroyRef.[33]

14.4 Let flattening operators own inner cancellation

cancel stale inner work
const detail$ =
  selectedId$.pipe(
    switchMap(id =>
      productApi.get(id),
    ),
  );

When a new ID arrives, switchMap unsubscribes the prior request. Angular notes that this cancellation can clean up stale HttpClient requests.[28][15]

14.5 Manual subscription for imperative effects

imperative subscription with owned lifetime
@Component({
  selector: 'app-route-title',
  standalone: true,
  template: `...`,
})
export class RouteTitleComponent {
  private readonly destroyRef =
    inject(DestroyRef);

  private readonly title =
    inject(Title);

  private readonly route =
    inject(ActivatedRoute);

  constructor() {
    this.route.data.pipe(
      map(data =>
        String(
          data['title'] ?? 'Application',
        ),
      ),
      takeUntilDestroyed(
        this.destroyRef,
      ),
    ).subscribe(title => {
      this.title.setTitle(title);
    });
  }
}

14.6 Preferred order

  1. Template consumption through AsyncPipe.
  2. Signal conversion through toSignal when component logic needs a current reactive value.
  3. Finite operators such as take, or cancellation through flattening.
  4. takeUntilDestroyed for imperative Angular subscriptions.
  5. Manual Subscription aggregation when integrating with non-Angular ownership boundaries.

15. Angular AsyncPipe

Angular’s AsyncPipe subscribes to an Observable or Promise, returns the latest emitted value, marks the component for checking when a new value arrives, unsubscribes when the component is destroyed, and switches subscriptions when the bound Observable reference changes.[34]

15.1 Basic template consumption

AsyncPipe

15.2 Bind once with a template variable

AsyncPipe and @if

  <app-user-card [user]="user" />
} @else {
  <app-user-skeleton />
}

Binding once avoids repeated pipe expressions in the same view and gives the template a narrowed local value.

15.3 Render explicit state

state stream in a template
@switch (state$ | async) {
  @case ({ status: 'loading' }) {
    <app-spinner />
  }

  @case ({ status: 'ready' }; as state) {
    <app-product-list
      [products]="state.value" />
  }

  @case ({ status: 'error' }; as state) {
    <p role="alert">
      {{ state.message }}
    </p>
  }
}

15.4 Keep Observable identity stable

stable Observable property
@Component({
  // ...
})
export class ProductPageComponent {
  readonly product$ =
    inject(ProductApi).get('p1');
}
unstable expression anti-pattern
<!-- Avoid a method that constructs a new Observable
     every template evaluation. -->
<p>{{ loadProduct() | async }}</p>

Because AsyncPipe unsubscribes and resubscribes when the expression reference changes, creating a new Observable repeatedly in a template can restart work such as HTTP requests. Construct pipelines in the class or a service and expose stable Observable properties.[34][15]

16. Angular signals interoperability

The @angular/core/rxjs-interop package bridges RxJS and Angular signals. toSignal subscribes to an Observable and exposes its latest value as a Signal; toObservable monitors a Signal through an effect and exposes stabilized values as an Observable.[22]

16.1 Observable to Signal

toSignal
import {
  toSignal,
} from '@angular/core/rxjs-interop';

@Component({
  selector: 'app-temperature',
  standalone: true,
  template: `
    <p>
      {{ temperature().value }}
      °C
    </p>
  `,
})
export class TemperatureComponent {
  private readonly service =
    inject(TemperatureService);

  readonly temperature =
    toSignal(
      this.service.temperature$,
      {
        initialValue: {
          value: 20,
        },
      },
    );
}

toSignal subscribes immediately, can therefore trigger source side effects, and automatically unsubscribes with its creation context by default. Reuse the returned Signal rather than repeatedly converting the same Observable.[22]

16.2 BehaviorSubject and requireSync

synchronous first emission
readonly state =
  toSignal(
    this.store.state$,
    {
      requireSync: true,
    },
  );

When the Observable is guaranteed to emit synchronously on subscription, as BehaviorSubject does, requireSync: true lets the resulting Signal avoid an undefined initial state and enforces that guarantee at runtime.[22]

16.3 Signal to Observable

toObservable
import {
  toObservable,
} from '@angular/core/rxjs-interop';

readonly query = signal('');

readonly query$ =
  toObservable(this.query);

readonly results$ =
  this.query$.pipe(
    debounceTime(250),
    distinctUntilChanged(),
    switchMap(query =>
      this.api.search(query),
    ),
  );

toObservable emits the signal’s stabilized value. Multiple synchronous signal writes may coalesce so that only the final stabilized value is emitted after the effect runs.[22]

16.4 Keep each abstraction in its strength

  • Use signals for synchronous current state and template derivation.
  • Use RxJS for cancellation, concurrency, temporal logic, event streams, retries, and multi-source coordination.
  • Convert at architectural boundaries rather than bouncing repeatedly between abstractions.

17. Complete example: cancellable Angular search

This example uses a FormControl Observable, normalization, debouncing, distinctness, switchMap cancellation, inner error recovery, explicit loading state, shared template consumption, and AsyncPipe-managed subscription lifetime.

search.models.ts
export interface SearchResult {
  readonly id: string;
  readonly title: string;
  readonly summary: string;
}

export type SearchState =
  | {
      readonly status: 'idle';
      readonly results:
        readonly SearchResult[];
    }
  | {
      readonly status: 'loading';
      readonly query: string;
      readonly results:
        readonly SearchResult[];
    }
  | {
      readonly status: 'ready';
      readonly query: string;
      readonly results:
        readonly SearchResult[];
    }
  | {
      readonly status: 'error';
      readonly query: string;
      readonly message: string;
      readonly results:
        readonly SearchResult[];
    };
search-api.service.ts
@Injectable({
  providedIn: 'root',
})
export class SearchApi {
  private readonly http =
    inject(HttpClient);

  search(
    query: string,
  ): Observable<
    readonly SearchResult[]
  > {
    return this.http.get<
      readonly SearchResult[]
    >('/api/search', {
      params: { query },
    });
  }
}
search-page.component.ts
import {
  AsyncPipe,
} from '@angular/common';
import {
  ChangeDetectionStrategy,
  Component,
  inject,
} from '@angular/core';
import {
  FormControl,
  ReactiveFormsModule,
} from '@angular/forms';
import {
  catchError,
  debounceTime,
  distinctUntilChanged,
  map,
  of,
  startWith,
  switchMap,
} from 'rxjs';

@Component({
  selector: 'app-search-page',
  standalone: true,
  imports: [
    AsyncPipe,
    ReactiveFormsModule,
  ],
  changeDetection:
    ChangeDetectionStrategy.OnPush,
  templateUrl:
    './search-page.component.html',
})
export class SearchPageComponent {
  private readonly api =
    inject(SearchApi);

  readonly queryControl =
    new FormControl(
      '',
      {
        nonNullable: true,
      },
    );

  readonly state$ =
    this.queryControl.valueChanges.pipe(
      startWith(
        this.queryControl.value,
      ),

      map(query =>
        query.trim(),
      ),

      debounceTime(250),

      distinctUntilChanged(),

      switchMap(query => {
        if (query.length < 2) {
          return of<SearchState>({
            status: 'idle',
            results: [],
          });
        }

        return this.api.search(query).pipe(
          map(results => ({
            status: 'ready',
            query,
            results,
          } satisfies SearchState)),

          startWith({
            status: 'loading',
            query,
            results: [],
          } satisfies SearchState),

          catchError(error =>
            of({
              status: 'error',
              query,
              message:
                toSearchMessage(error),
              results: [],
            } satisfies SearchState),
          ),
        );
      }),
    );
}
search-page.component.html
<section>
  <h1>Search</h1>

  <label for="query">
    Search articles
  </label>

  <input
    id="query"
    type="search"

  }

The AsyncPipe owns the outer subscription. switchMap owns cancellation of stale HTTP requests. Placing catchError inside the inner request keeps the FormControl stream active after a request failure.

19. Production architecture patterns

19.1 Name streams clearly

Observable naming
readonly selectedUserId$ =
  this.selectionStore
    .selectedUserId$;

readonly user$ =
  this.selectedUserId$.pipe(
    switchMap(id =>
      this.api.getUser(id),
    ),
  );

A trailing $ is a common project convention for Observable values. Use it consistently if adopted, but do not encode implementation details into public domain names unnecessarily.

19.2 Expose read-only streams

write encapsulation
private readonly refreshSubject =
  new Subject<void>();

readonly refresh$ =
  this.refreshSubject.asObservable();

refresh(): void {
  this.refreshSubject.next();
}

19.3 Compose one view model

single template view model
readonly viewModel$ =
  combineLatest({
    user: this.user$,
    permissions: this.permissions$,
    settings: this.settings$,
  }).pipe(
    map(({
      user,
      permissions,
      settings,
    }) => ({
      user,
      canEdit:
        permissions.includes(
          'user.edit',
        ),
      density:
        settings.density,
    })),
  );

A single view-model Observable can avoid multiple AsyncPipe subscriptions, make cross-source consistency explicit, and centralize loading/error policy.

19.4 Keep domain events semantic

typed event union
type OrderEvent =
  | {
      readonly type:
        'order-created';
      readonly orderId: string;
    }
  | {
      readonly type:
        'order-cancelled';
      readonly orderId: string;
      readonly reason: string;
    };

Prefer typed domain events over loosely typed global Subjects. Avoid using a Subject as a hidden application-wide command bus; it obscures ownership, ordering, and failure behavior.

19.5 Validate external data

TypeScript generics on HttpClient or Observable declarations do not validate runtime JSON. Validate untrusted external data at the boundary before publishing it through a strongly typed stream.[15]

19.6 Avoid nested subscriptions

flatten instead of nesting
// Avoid:
userId$.subscribe(id => {
  api.getUser(id).subscribe(user => {
    render(user);
  });
});

// Prefer:
userId$.pipe(
  switchMap(id =>
    api.getUser(id),
  ),
).subscribe(user => {
  render(user);
});

Flattening operators make cancellation, ordering, concurrency, errors, and teardown part of one composable chain.

19.7 Keep effects at edges

Use transformation operators for data and tap only for transparent effects such as diagnostics. Business-state mutation hidden inside a reusable operator pipeline makes behavior difficult to reason about and test.

20. Common pitfalls

PitfallConsequenceBetter approach
Calling subscribe inside subscribe Cancellation, errors, and teardown become fragmented. Use a flattening operator.
Choosing switchMap for writes that must all complete Earlier operations are cancelled when a new value arrives. Use concatMap or bounded mergeMap.
Choosing mergeMap for replaceable searches Stale responses can arrive after newer responses. Use switchMap.
Putting catchError at the wrong level The outer interaction stream terminates unexpectedly. Recover at the inner boundary when the workflow should continue.[27]
Unbounded ReplaySubject Every emitted value remains retained. Specify a buffer and, when appropriate, a time window.[23]
Public writable Subject Any consumer can violate event or state invariants. Keep it private and expose asObservable().
Multiple AsyncPipe expressions over one cold HTTP source Multiple backend requests may occur. Bind once, compose a view model, or share deliberately.[15][34]
Creating an Observable in a template method AsyncPipe repeatedly replaces subscriptions and restarts work. Expose a stable property.[34]
Retrying every error Permanent failures waste resources; writes may duplicate effects. Retry only classified transient failures with limits.
Forgetting teardown in a custom Observable Timers, listeners, or sockets remain active. Return teardown from subscription logic.[3][5]
Using BehaviorSubject as a mutable global variable State changes lack a controlled domain API. Encapsulate writes or use a store abstraction.
Converting repeatedly between Observable and Signal Extra subscriptions, effects, timing boundaries, and complexity. Convert once at architectural boundaries.[22]

23. Conclusion

RxJS provides a uniform algebra for asynchronous and event-based values. Observables describe executions, Observers consume notifications, Subscriptions own cancellation and teardown, Subjects multicast imperative notifications, BehaviorSubject represents a current value, ReplaySubject retains bounded history, and pipeable operators produce new declarative pipelines without mutating their sources.[1][2][3][4][5][19]

Production RxJS code is defined by explicit semantics: know whether execution is cold or shared, choose flattening by cancellation and ordering requirements, recover errors at the correct boundary, bound replay and retry, keep Subject writes private, and align subscription lifetime with resource ownership. In Angular templates, prefer AsyncPipe; in imperative Angular effects, use takeUntilDestroyed; use signal interoperability deliberately where a current synchronous value or signal-based derivation improves the design.
