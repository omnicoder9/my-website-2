Routing in Angular

Angular routing maps browser URLs to a tree of application views. A production router configuration does more than switch components: it defines URL contracts, controls code loading, coordinates data acquisition, protects navigation transitions, preserves browser history, and determines how deep links behave when they arrive directly from outside the application.

1. Routing as application architecture

Angular Router, published in @angular/router, is Angular’s official navigation library. In a client-rendered single-page application, the server initially supplies the host page; later in-app navigations update the displayed content and browser URL without replacing the entire document. Angular describes three primary routing elements: route definitions, outlets, and links.[1]

Routes

A Routes array contains Route configuration objects. Each route can match URL segments, activate or lazily load content, redirect, run guards and resolvers, provide data, and own child routes.[2][3]

Outlets

RouterOutlet is a placeholder in a component template. The router activates matched components into the appropriate primary or named outlet.[4][5]

Navigation

RouterLink creates router-aware links, while Router.navigate and navigateByUrl support imperative navigation. Both cooperate with browser history.[6][7]

The URL should be treated as a public application interface. A useful URL can be bookmarked, shared, refreshed, opened in another tab, traversed with Back and Forward, and interpreted without inspecting transient component state. Route design therefore belongs alongside domain modeling and API design rather than being deferred to template wiring.

URL created
Routes recognized
Guards evaluated
Resolvers executed
Views activated

Angular exposes router lifecycle events for these phases, including route recognition, guard checking, resolution, activation, completion, cancellation, failure, and skipped navigation.[8]

2. History: from hash fragments to route trees

Early single-page routing

Before widespread History API support, single-page applications commonly stored client-side paths in the URL fragment after #. Fragment changes did not request a different resource from the server, making hash routing practical even on servers without rewrite configuration.[9]

The browser History API

The History API introduced operations such as pushState() and replaceState(), enabling scripts to add or replace session-history entries and associate serializable state with them without forcing a document load. Traversing those entries produces popstate behavior.[10][11]

AngularJS ngRoute

AngularJS offered the optional ngRoute module. Its $route service mapped locations to controllers and templates, while ngView inserted the active template into the application shell. Official AngularJS documentation describes support for both hashbang URLs and HTML5 pushState mode.[12][13][14]

Angular 2 and the component router

The rewritten Angular framework shipped a component-oriented router in @angular/router. Archived Angular 2 documentation already covered route arrays, RouterOutlet, RouterLink, child routes, guards, resolvers, named outlets, wildcard routes, and lazy-loaded bundles.[15][16]

Standalone configuration

Current Angular can configure routing through provideRouter() during application bootstrap. Optional router features are supplied as additional feature functions, while RouterModule.forRoot() and forChild() remain relevant in NgModule-based applications and libraries.[17][2][16]

AngularJS is not modern Angular The historical APIs $routeProvider, $route, $routeParams, and ngView belong to AngularJS. Modern Angular uses Routes, Router, ActivatedRoute, and RouterOutlet.

3. Setting up the router

A standalone Angular application commonly exports a route table from app.routes.ts and passes it to provideRouter() in the application configuration. provideRouter installs the providers required for routing and accepts optional features such as component input binding, preloading, scrolling behavior, debug tracing, and custom router options.[17][18]

src/app/app.config.ts
import { ApplicationConfig, inject } from '@angular/core';
import {
  provideRouter,
  withComponentInputBinding,
  withInMemoryScrolling,
  withNavigationErrorHandler,
  withPreloading,
  PreloadAllModules,
  RedirectCommand,
  Router,
} from '@angular/router';

import { routes } from './app.routes';

export const appConfig: ApplicationConfig = {
  providers: [
    provideRouter(
      routes,
      withComponentInputBinding(),
      withPreloading(PreloadAllModules),
      withInMemoryScrolling({
        anchorScrolling: 'enabled',
        scrollPositionRestoration: 'enabled',
      }),
      withNavigationErrorHandler(error => {
        const router = inject(Router);
        console.error('Navigation failed', error);
        return new RedirectCommand(router.parseUrl('/error'));
      }),
    ),
  ],
};

withComponentInputBinding() can bind matching query parameters, path and matrix parameters, static route data, and resolved data directly to routed component inputs. Resolver data has the highest precedence when multiple sources use the same key.[19]

The application shell imports router directives used by its template and contains the primary outlet:

src/app/app.component.ts
import { Component } from '@angular/core';
import {
  RouterLink,
  RouterLinkActive,
  RouterOutlet,
} from '@angular/router';

@Component({
  selector: 'app-root',
  standalone: true,
  imports: [RouterLink, RouterLinkActive, RouterOutlet],
  templateUrl: './app.component.html',
})
export class AppComponent {}

3.1 Base URL and location strategy

Angular uses HTML5-style URLs by default. A routed application normally includes a <base href="/"> element so the browser and router can resolve application-relative URLs correctly. Deployments under a subpath need a matching base, such as /portal/.[20]

src/index.html
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <base href="/">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Acme</title>
</head>
<body>
  <app-root></app-root>
</body>
</html>

Hash-based routing remains available for environments where clean-path rewrites cannot be configured, but HTML5 paths are generally preferable because they produce conventional URLs and integrate naturally with server rendering and deep links.[9][20]

4. Route configuration

A Route is a declarative object. Common properties include path, component, loadComponent, loadChildren, redirectTo, children, outlet, title, data, resolve, guard arrays, route-scoped providers, and runGuardsAndResolvers.[3]

src/app/app.routes.ts
import { Routes } from '@angular/router';

import { HomePage } from './pages/home.page';
import { NotFoundPage } from './pages/not-found.page';
import { authGuard } from './routing/auth.guard';
import { productResolver } from './routing/product.resolver';

export const routes: Routes = [
  {
    path: '',
    title: 'Acme Store',
    component: HomePage,
  },
  {
    path: 'products',
    loadChildren: () =>
      import('./products/product.routes').then(m => m.PRODUCT_ROUTES),
  },
  {
    path: 'account',
    canActivate: [authGuard],
    loadComponent: () =>
      import('./account/account.page').then(m => m.AccountPage),
  },
  {
    path: 'legacy-product/:id',
    redirectTo: ({ params }) => `/products/${params['id']}`,
  },
  {
    path: '**',
    title: 'Page not found',
    component: NotFoundPage,
  },
];

4.1 First-match-wins semantics

Angular evaluates routes in configuration order and stops when it finds the first match. Specific static paths should precede parameterized paths, and the catch-all ** route must be last. Otherwise a broad route can shadow a more specific route.[2]

specific routes before broad routes
export const USER_ROUTES: Routes = [
  { path: 'new', component: NewUserPage },       // /users/new
  { path: ':id/edit', component: EditUserPage }, // /users/42/edit
  { path: ':id', component: UserDetailPage },    // /users/42
  { path: '', component: UserListPage },         // /users
];

4.2 Redirects and pathMatch

Redirect routes use redirectTo. The default redirect matching mode is prefix; an empty-path redirect normally requires pathMatch: 'full' so that the empty prefix does not redirect every URL.[21]

redirect routes
export const routes: Routes = [
  {
    path: '',
    pathMatch: 'full',
    redirectTo: 'dashboard',
  },
  {
    path: 'old-reports/:id',
    redirectTo: 'reports/:id',
  },
  {
    path: 'dashboard',
    component: DashboardPage,
  },
];

4.3 Titles, static data, and route-scoped providers

metadata and route-level dependency injection
{
  path: 'admin',
  title: 'Administration',
  data: {
    breadcrumb: 'Admin',
    requiredRole: 'administrator',
  },
  providers: [
    AdminAuditService,
    { provide: ADMIN_API_ROOT, useValue: '/api/admin' },
  ],
  canActivateChild: [adminChildGuard],
  children: [
    { path: '', component: AdminOverviewPage },
    { path: 'users', component: AdminUsersPage },
  ],
}

The route’s providers array creates an environment injector for that route and its children. This allows feature-specific dependencies and configuration to share the route subtree’s lifetime and scope.[3]

5. RouterOutlet

RouterOutlet marks where routed content is inserted. The outlet remains in the DOM as an anchor; Angular places the activated component adjacent to it. An unnamed outlet is the primary outlet.[4][5]

primary outlet and lifecycle events
@Component({
  selector: 'app-shell',
  standalone: true,
  imports: [RouterOutlet],
  template: `
    <app-header />
    <main>
      <router-outlet
        (activate)="onActivate($event)"
        (deactivate)="onDeactivate($event)" />
    </main>
    <app-footer />
  `,
})
export class AppShell {
  onActivate(component: unknown): void {
    console.debug('Activated', component);
  }

  onDeactivate(component: unknown): void {
    console.debug('Deactivated', component);
  }
}

Outlets emit activate, deactivate, attach, and detach events. Attach and detach participate in route reuse strategies, while activate and deactivate reflect component instantiation and destruction.[4][5]

5.1 Named outlets and secondary routes

A page can contain multiple outlets. Each named outlet corresponds to the outlet property of a route, allowing independent branches of the router state tree to appear in the URL and UI.[4][5]

primary and named outlets
<!-- app-shell.component.html -->
<router-outlet />
<router-outlet name="modal" />
secondary route configuration
export const routes: Routes = [
  {
    path: 'products',
    component: ProductListPage,
  },
  {
    path: 'compose',
    outlet: 'modal',
    component: ComposeMessageDialog,
  },
];
navigate to a named outlet
<a
  [routerLink]="[
    '/products',
    { outlets: { modal: ['compose'] } }
  ]">
  Compose message
</a>

Named outlets are useful for URL-addressable dialogs, side panels, and persistent auxiliary workflows, but they make URL trees and navigation commands more complex. Use them when independent navigation state is genuinely valuable rather than merely to avoid a local component state variable.

6. Navigation

6.1 Declarative navigation with RouterLink

RouterLink turns an element into a router-aware link. A string is shorthand for a command array containing one path, while an array can combine static segments, dynamic values, and matrix parameters. Absolute commands begin at the application root; relative commands are interpreted from the current activated route.[6][7]

RouterLink examples
<nav>
  <a routerLink="/">Home</a>

  <a [routerLink]="['/products', product.id]">
    {{ product.name }}
  </a>

  <a [routerLink]="['edit']">
    Edit relative to the current route
  </a>

  <a [routerLink]="['../']">
    Parent route
  </a>

  <a
    [routerLink]="['/products']"
    [queryParams]="{ category: 'books', page: 2 }"
    fragment="results">
    Books
  </a>
</nav>

6.2 Active-link state

active navigation link
<a
  routerLink="/products"
  routerLinkActive="active"
  ariaCurrentWhenActive="page"
  [routerLinkActiveOptions]="{ exact: true }">
  Products
</a>

RouterLinkActive adds and removes classes according to whether a linked route is active. Exact matching is appropriate for links such as the home page that would otherwise remain active for every descendant URL.

6.3 Programmatic navigation

Router.navigate() accepts a link-command array plus navigation extras. navigateByUrl() accepts a complete URL string or UrlTree. Prefer declarative links for ordinary user navigation because anchors preserve browser affordances such as opening in a new tab, copying the target, and accessible link semantics.[7]

programmatic navigation
import { Component, inject } from '@angular/core';
import { ActivatedRoute, Router } from '@angular/router';

@Component({ /* ... */ })
export class ProductActions {
  private readonly router = inject(Router);
  private readonly route = inject(ActivatedRoute);

  openProduct(id: string): Promise<boolean> {
    return this.router.navigate(['/products', id]);
  }

  editCurrentProduct(): Promise<boolean> {
    return this.router.navigate(['edit'], {
      relativeTo: this.route,
    });
  }

  updateSort(sort: 'name' | 'price'): Promise<boolean> {
    return this.router.navigate([], {
      relativeTo: this.route,
      queryParams: { sort },
      queryParamsHandling: 'merge',
      replaceUrl: true,
    });
  }

  finishCheckout(orderId: string): Promise<boolean> {
    return this.router.navigateByUrl(`/orders/${orderId}`, {
      replaceUrl: true,
      state: { source: 'checkout' },
    });
  }
}

6.4 Navigation extras

OptionEffectTypical use
relativeToResolves commands against an ActivatedRoute.Feature-local navigation.
queryParamsBuilds the query string.Filters, pagination, sorting.
queryParamsHandlingReplaces, merges, or preserves existing query values.Updating one filter without losing others.
fragmentAdds a URL fragment.Section links.
replaceUrlReplaces the current history entry.Redirect-like transitions and noisy filter changes.
skipLocationChangeNavigates without pushing the normal URL change into browser history.Specialized internal transitions; use sparingly.
stateAssociates serializable navigation state with the history entry.Transient navigation context that is not a URL contract.

Router links and programmatic navigation support query parameters, fragments, relative paths, history replacement, and navigation state.[6][7][10]

Do not hide essential state in navigation extras History state is convenient for transient context, but URLs should still identify the page. A refresh, copied link, server render, or direct visit may not reproduce an earlier in-memory navigation path.

7. Route parameters and query parameters

7.1 Path parameters

A colon-prefixed path segment declares a route parameter. For example, products/:id matches a URL such as /products/42, and the value is available through the activated route’s parameter map.[22]

path parameter configuration
export const PRODUCT_ROUTES: Routes = [
  {
    path: ':id',
    component: ProductDetailPage,
  },
];
reactively read a path parameter
import { Component, computed, inject } from '@angular/core';
import { ActivatedRoute } from '@angular/router';
import { toSignal } from '@angular/core/rxjs-interop';
import { map } from 'rxjs';

@Component({
  selector: 'app-product-detail',
  standalone: true,
  template: `<h1>Product {{ productId() }}</h1>`,
})
export class ProductDetailPage {
  private readonly route = inject(ActivatedRoute);

  readonly productId = toSignal(
    this.route.paramMap.pipe(
      map(params => params.get('id') ?? ''),
    ),
    { initialValue: '' },
  );
}

ActivatedRoute exposes both snapshots and observable state. A snapshot is convenient when the component instance will not be reused for another parameter value. Observables are safer when navigation can change parameters while Angular retains the same component instance, such as moving from /products/41 to /products/42.[22][23]

snapshot versus observable state
const initialId = this.route.snapshot.paramMap.get('id');

// Reactive alternative:
this.route.paramMap.subscribe(params => {
  const currentId = params.get('id');
  this.load(currentId);
});

7.2 Query parameters

Query parameters are global to the URL rather than tied to a specific route segment. They are appropriate for optional view state such as search terms, filters, sort order, pagination, and display modes. Angular exposes them through queryParamMap and supports creating them through links and navigation extras.[22][23]

drive a data query from URL state
import { combineLatest, distinctUntilChanged, map, switchMap } from 'rxjs';

readonly products$ = combineLatest([
  this.route.queryParamMap.pipe(
    map(params => params.get('q')?.trim() ?? ''),
    distinctUntilChanged(),
  ),
  this.route.queryParamMap.pipe(
    map(params => Number(params.get('page') ?? '1')),
    map(page => Number.isFinite(page) && page > 0 ? page : 1),
    distinctUntilChanged(),
  ),
]).pipe(
  switchMap(([query, page]) =>
    this.productApi.search({ query, page }),
  ),
);
merge one query parameter
<a
  [routerLink]="[]"
  [queryParams]="{ page: page + 1 }"
  queryParamsHandling="merge">
  Next page
</a>

Keeping list state in the URL makes filtering and pagination bookmarkable and supports browser history. It also requires parsing and validating string values at the routing boundary rather than trusting them as already typed application data.

7.3 Bind route state directly to inputs

With withComponentInputBinding() enabled, route state can flow directly into matching component inputs. This removes some ActivatedRoute plumbing and creates a clear routed-component contract.[19][24]

component inputs populated by route state
import { Component, input } from '@angular/core';

@Component({
  selector: 'app-product-detail',
  standalone: true,
  template: `
    <h1>Product {{ id() }}</h1>
    <p>Tab: {{ tab() }}</p>
  `,
})
export class ProductDetailPage {
  readonly id = input.required<string>();
  readonly tab = input('overview');
}
matching route keys
{
  path: 'products/:id',
  component: ProductDetailPage,
  resolve: {
    // A resolver with the same key would override lower-precedence sources.
  },
}

7.4 Matrix parameters and fragments

Angular also supports matrix parameters scoped to a path segment and URL fragments. Matrix parameters use semicolons, while fragments follow #. Query parameters are usually more familiar for cross-route filtering; matrix parameters can be useful when optional state logically belongs to one segment.[6][22]

matrix parameters
this.router.navigate([
  '/products',
  { view: 'grid', featured: true },
]);

// Result resembles:
// /products;view=grid;featured=true

8. Lazy loading

An eagerly referenced route component is included with the route configuration’s JavaScript bundle. loadComponent defers a standalone component, while loadChildren defers a child route collection or feature module. Lazy code is compiled into separate chunks requested when the route is matched or preloaded.[2][25]

8.1 Lazy-load a standalone component

loadComponent
{
  path: 'help',
  loadComponent: () =>
    import('./help/help.page').then(m => m.HelpPage),
}

8.2 Lazy-load a feature route tree

root route
{
  path: 'products',
  loadChildren: () =>
    import('./products/product.routes')
      .then(m => m.PRODUCT_ROUTES),
}
src/app/products/product.routes.ts
import { Routes } from '@angular/router';

import { ProductShellPage } from './product-shell.page';

export const PRODUCT_ROUTES: Routes = [
  {
    path: '',
    component: ProductShellPage,
    children: [
      {
        path: '',

            .then(m => m.ProductListPage),

  },

8.3 Preloading

Lazy loading reduces initial work but introduces a later request when the route is first visited. Preloading strategies can request lazy route configurations in the background after bootstrap, trading additional network and parsing work for faster future navigation. Angular offers PreloadAllModules and supports custom strategies.[25][17]

preload all lazy route configurations
provideRouter(
  routes,
  withPreloading(PreloadAllModules),
)

8.4 Choosing boundaries

Route typeLikely strategyReasoning
Primary landing pageEagerAvoid delaying the first meaningful view.
Large admin featureLazyMany users may never enter it.
Small frequently used detail pageEager or preloadedA separate request may cost more than the bytes saved.
Rare editor with heavy dependenciesLazyStrong separation and initial-bundle reduction.
Deeply nested chain of tiny lazy routesUsually consolidateExcessive waterfalls can harm navigation latency.

Angular’s performance guidance explicitly describes the eager/lazy trade-off: lazy loading can reduce the initial bundle, but future requests and deeply nested lazy boundaries can also create costs.[25][2]

9. Route guards

Guards control whether the router can match, activate, activate a child of, or deactivate a route. Current Angular documentation emphasizes functional guard types: CanActivateFn, CanActivateChildFn, CanDeactivateFn, and CanMatchFn.[26][3]

Guards are not server-side access control Browser JavaScript can be inspected and modified. Angular explicitly warns never to rely on client-side guards as the sole authorization mechanism; every protected operation and resource must be authorized on the server.[26]

9.1 Guard return values

A guard can return a boolean, a UrlTree or RedirectCommand, a promise, or an observable. Angular uses the first asynchronous result. For most guards, false cancels navigation; for CanMatch, false causes the router to try another matching route. When redirecting, return a URL tree or redirect command instead of returning false and separately calling navigate().[26]

9.2 CanActivate: authenticated route

src/app/routing/auth.guard.ts
import { inject } from '@angular/core';
import {
  CanActivateFn,
  RedirectCommand,
  Router,
} from '@angular/router';

import { AuthStore } from '../auth/auth.store';

export const authGuard: CanActivateFn = (route, state) => {
  const auth = inject(AuthStore);
  const router = inject(Router);

  if (auth.isAuthenticated()) {
    return true;
  }

  const loginTree = router.createUrlTree(['/login'], {
    queryParams: { returnUrl: state.url },
  });

  return new RedirectCommand(loginTree, {
    replaceUrl: true,
  });
};
guarded route
{
  path: 'account',
  canActivate: [authGuard],
  loadComponent: () =>
    import('../account/account.page').then(m => m.AccountPage),
}

9.3 CanActivateChild: protect a subtree

admin-child.guard.ts
import { inject } from '@angular/core';
import { CanActivateChildFn, Router } from '@angular/router';
import { AuthStore } from '../auth/auth.store';

export const adminChildGuard: CanActivateChildFn = () => {
  const auth = inject(AuthStore);
  const router = inject(Router);

  return auth.hasRole('administrator')
    ? true
    : router.parseUrl('/forbidden');
};
protected child routes
{
  path: 'admin',
  canActivateChild: [adminChildGuard],
  children: [
    { path: '', component: AdminHomePage },
    { path: 'users', component: AdminUsersPage },
    { path: 'audit', component: AuditLogPage },
  ],
}

9.4 CanDeactivate: unsaved changes

unsaved-changes.guard.ts
import { CanDeactivateFn } from '@angular/router';

export interface DirtyAware {
  hasUnsavedChanges(): boolean;
}

export const unsavedChangesGuard:
  CanDeactivateFn<DirtyAware> = component => {
    if (!component.hasUnsavedChanges()) {
      return true;
    }

    return window.confirm(
      'You have unsaved changes. Leave this page?',
    );
  };
editor route
{
  path: 'products/:id/edit',
  component: ProductEditorPage,
  canDeactivate: [unsavedChangesGuard],
}

A native confirmation dialog is simple but difficult to customize and test. A production application can return an observable or promise from a dialog service instead. The guard should represent actual unsaved state, not merely whether a form has ever become dirty.

9.5 CanMatch: conditional route selection

same path, conditional route match
import { inject } from '@angular/core';
import { CanMatchFn } from '@angular/router';
import { FeatureFlags } from '../flags/feature-flags';

export const newDashboardGuard: CanMatchFn = () =>
  inject(FeatureFlags).enabled('new-dashboard');

export const routes: Routes = [
  {
    path: 'dashboard',
    canMatch: [newDashboardGuard],
    loadComponent: () =>
      import('./new-dashboard.page').then(m => m.NewDashboardPage),
  },
  {
    path: 'dashboard',
    loadComponent: () =>
      import('./classic-dashboard.page')
        .then(m => m.ClassicDashboardPage),
  },
];

This works because a rejected CanMatch route falls through to later candidates rather than canceling the entire navigation.[26]

9.6 Guard composition and placement

  • Place authentication at the narrowest common parent that accurately represents the protected area.
  • Use canActivateChild when every descendant needs the same policy.
  • Use canMatch when the decision affects route selection or whether lazy configuration should match.
  • Return redirects rather than producing navigation as a side effect.
  • Keep guards fast; long-running data retrieval usually belongs in a resolver or component data layer.
  • Do not duplicate server authorization rules in a way that can drift. The guard should provide user experience, while the server remains authoritative.

10. Route resolvers

A resolver obtains essential data before route activation and exposes it as route data. The navigation remains blocked until the resolver completes, which can eliminate an initial empty component state but also delays the transition. Angular recommends keeping resolvers lightweight, handling errors, considering caching and timeouts, and fetching only data that is essential before rendering.[27]

10.1 Functional resolver

product.resolver.ts
import { inject } from '@angular/core';
import {
  RedirectCommand,
  ResolveFn,
  Router,
} from '@angular/router';
import { catchError, of } from 'rxjs';

import { Product } from '../products/product';
import { ProductApi } from '../products/product.api';

export const productResolver: ResolveFn<Product> = route => {
  const api = inject(ProductApi);
  const router = inject(Router);
  const id = route.paramMap.get('id');

  if (!id) {
    return new RedirectCommand(router.parseUrl('/products'));
  }

  return api.getById(id).pipe(
    catchError(() =>
      of(new RedirectCommand(
        router.parseUrl('/products/not-found'),
        { replaceUrl: true },
      )),
    ),
  );
};
route with resolver
{
  path: ':id',
  component: ProductDetailPage,
  resolve: {
    product: productResolver,
  },
}

10.2 Read resolved data

read resolver data from ActivatedRoute
import { Component, computed, inject } from '@angular/core';
import { ActivatedRoute } from '@angular/router';
import { toSignal } from '@angular/core/rxjs-interop';

@Component({
  selector: 'app-product-detail',
  standalone: true,
  template: `
    <h1>{{ product().name }}</h1>
    <p>{{ product().description }}</p>
  `,
})
export class ProductDetailPage {
  private readonly route = inject(ActivatedRoute);
  private readonly routeData = toSignal(this.route.data, {
    initialValue: this.route.snapshot.data,
  });

  readonly product = computed(
    () => this.routeData()['product'] as Product,
  );
}

With router component input binding enabled, a matching required input provides a more direct contract:

resolved data as a component input
@Component({
  selector: 'app-product-detail',
  standalone: true,
  template: `
    <h1>{{ product().name }}</h1>
    <p>{{ product().description }}</p>
  `,
})
export class ProductDetailPage {
  readonly product = input.required<Product>();
}

Angular supports both reading resolver data from ActivatedRoute.data and binding it to component inputs through withComponentInputBinding().[27][19]

10.3 Parent-child ordering

Resolvers execute from parent to child. A child resolver can read data already resolved by its parent through the parent snapshot, which is useful when child resources depend on a parent entity.[27]

child resolver using parent resolved data
{

11.2 Parameter and data inheritance

A child activated route has parent and root relationships in the router-state tree. Read values from the appropriate route node rather than assuming every child’s own parameter map contains ancestor parameters. Applications that need broad inheritance can configure router options, but explicit route-tree traversal or input contracts often make ownership clearer.[23][18]

const workspaceId$ = this.route.parent!.paramMap.pipe(
  map(params => params.get('workspaceId')),

12. Wildcard routes and not-found behavior

A path of ** is the router wildcard. Because route matching is first-match wins, the wildcard belongs at the end of the relevant route array. It can render a not-found component or redirect elsewhere.[2][21]

application-level not-found route
export const routes: Routes = [
  { path: '', component: HomePage },
  { path: 'products', loadChildren: () => import('./products/routes') },
  { path: '**', component: NotFoundPage },
];

12.1 Feature-local wildcard

feature-specific fallback
export const DOCS_ROUTES: Routes = [
  { path: '', component: DocsIndexPage },
  { path: ':slug', component: DocsArticlePage },
  { path: '**', component: DocsNotFoundPage },
];

A local wildcard lets a feature present domain-specific recovery rather than sending every invalid child URL to the application-wide 404 page.

12.2 Client 404 versus server fallback

When a user navigates inside a running application, Angular can match **. A direct request or browser refresh reaches the web server before Angular exists. For client-rendered routing, the server must return index.html for application routes it does not recognize as files; Angular then starts and decides whether the path is valid. Angular’s deployment documentation explicitly requires this fallback for deep links.[28]

Fallback does not mean every backend URL becomes HTML Configure SPA fallback after static assets and API routes. A request for a missing JavaScript file or /api/products/42 should not silently return the Angular host document.

13. Navigation lifecycle, events, and errors

The router exposes an observable event stream. Events cover start, recognition, lazy configuration loading, guard checks, resolution, activation, successful completion, cancellation, failure, skipped navigation, and scrolling.[8][29]

navigation progress and error observation
import { DestroyRef, inject } from '@angular/core';
import { takeUntilDestroyed } from '@angular/core/rxjs-interop';
import {
  NavigationCancel,
  NavigationEnd,
  NavigationError,
  NavigationStart,
  Router,
} from '@angular/router';
import { filter } from 'rxjs';

export class NavigationMonitor {
  private readonly router = inject(Router);
  private readonly destroyRef = inject(DestroyRef);

  readonly isNavigating = signal(false);

  constructor() {
    this.router.events
      .pipe(takeUntilDestroyed(this.destroyRef))
      .subscribe(event => {
        if (event instanceof NavigationStart) {
          this.isNavigating.set(true);
        }

        if (
          event instanceof NavigationEnd ||
          event instanceof NavigationCancel ||
          event instanceof NavigationError
        ) {
          this.isNavigating.set(false);
        }
      });

    this.router.events.pipe(
      filter((event): event is NavigationError =>
        event instanceof NavigationError,
      ),
      takeUntilDestroyed(this.destroyRef),
    ).subscribe(event => {
      console.error('Navigation error', {
        url: event.url,
        error: event.error,
      });
    });
  }
}

Use event subscriptions for cross-cutting concerns such as progress indicators, analytics, diagnostics, and global error reporting. Do not use them to reproduce route-specific guard and resolver logic in an opaque global subscriber.

import { Component, inject } from '@angular/core';
import { ActivatedRoute, Router, RouterLink } from '@angular/router';
import { toSignal } from '@angular/core/rxjs-interop';
import { combineLatest, map, switchMap } from 'rxjs';

@Component({
  selector: 'app-product-list',
  standalone: true,
  imports: [RouterLink],
  template: `
    <h1>Products</h1>

    <label>
      Search
      <input
        type="search"
        [value]="query()"
        (change)="updateQuery($event)">
    </label>

    @for (product of products(); track product.id) {
      <article>
        <h2>
          <a [routerLink]="[product.id]">{{ product.name }}</a>
        </h2>
      </article>
    }
  `,
})
export class ProductListPage {
  private readonly route = inject(ActivatedRoute);
  private readonly router = inject(Router);
  private readonly api = inject(ProductApi);

  readonly query = toSignal(
    this.route.queryParamMap.pipe(
      map(params => params.get('q') ?? ''),
    ),
    { initialValue: '' },
  );

  readonly products = toSignal(
    this.route.queryParamMap.pipe(
      map(params => ({
        q: params.get('q') ?? '',
        page: Number(params.get('page') ?? '1'),
      })),
      switchMap(search => this.api.search(search)),
    ),
    { initialValue: [] },
  );

  updateQuery(event: Event): void {
    const q = (event.target as HTMLInputElement).value.trim();

    this.router.navigate([], {
      relativeTo: this.route,
      queryParams: {
        q: q || null,
        page: 1,
      },
      queryParamsHandling: 'merge',
      replaceUrl: true,
    });
  }
}

15.3 High-value routing tests

  • Specific paths win over parameterized and wildcard paths.
  • Relative links resolve correctly from nested routes.
  • Parameter changes update a reused component.
  • Query parsing handles missing, repeated, malformed, and out-of-range values.
  • Guards allow, reject, and redirect as intended.
  • Resolver success, not-found, timeout, and service failure paths are handled.
  • Lazy route configuration can be loaded and activated.
  • Nested parent and child components render together.
  • Unknown URLs activate the correct local or application-wide fallback.

16. Deployment and deep links

Internal router navigation does not require the server to know every route. Direct navigation does. A request for /products/42 reaches the server first, so a client-rendered deployment must serve the host index.html when no static file or backend route matches. After Angular starts, the router reads the URL and activates the correct route.[28]

16.1 Nginx example

nginx.conf
server {
  listen 80;
  server_name example.com;
  root /var/www/acme/browser;

  # Backend requests must be handled before SPA fallback.
  location /api/ {
    proxy_pass http://api:8080/;
  }

  # Existing files are served normally.
  # Unknown application paths load the Angular host page.
  location / {
    try_files $uri $uri/ /index.html;
  }
}

16.2 Apache example

.htaccess
<IfModule mod_rewrite.c>
  RewriteEngine On

  # Do not rewrite real files or directories.
  RewriteCond %{REQUEST_FILENAME} -f [OR]
  RewriteCond %{REQUEST_FILENAME} -d
  RewriteRule ^ - [L]

  # Do not rewrite backend endpoints.
  RewriteRule ^api/ - [L]

  # Send remaining application paths to Angular.
  RewriteRule ^ index.html [L]
</IfModule>

16.3 SSR and prerendering

Server-side rendering and prerendering change where initial route HTML is produced, but they do not eliminate the client route configuration. Angular’s rendering documentation distinguishes client-side rendering, server-side rendering, and build-time prerendering, and supports server routing policies for hybrid applications.[31][32]

17. Production routing architecture

17.1 Design URLs around resources and tasks

IntentPreferAvoid
Product identity/products/42/page?screen=product&id=42
Nested resource/organizations/7/projects/19Hidden global selection state.
Search/filter state/products?q=router&sort=priceNon-bookmarkable component-only filters.
Editing task/products/42/editAmbiguous boolean flags on a detail URL.
Stable feature section/settings/securityIndex-number paths tied to menu order.

17.2 Keep route configuration feature-local

A root route table should identify top-level application areas, not import every page. Feature route files can own their children, guards, providers, resolvers, and local wildcard behavior. This preserves lazy boundaries and keeps route order understandable.

17.3 Treat route parsing as an input boundary

Path and query values are strings supplied through a user-controlled URL. Parse numbers, dates, enums, and arrays explicitly; reject or normalize malformed values; and never assume that a parameter is authorized merely because it matched a route.

normalize query parameters
const page = Math.max(
  1,
  Number.parseInt(params.get('page') ?? '1', 10) || 1,
);

const allowedSorts = new Set(['name', 'price', 'rating']);
const requestedSort = params.get('sort') ?? 'name';
const sort = allowedSorts.has(requestedSort)
  ? requestedSort
  : 'name';

17.4 Avoid loading everything in resolvers

Resolvers block activation. Fetch the identity-defining data needed to decide whether the route can render, then let independent widgets stream or load after activation. This keeps navigation responsive and failures isolated.[27]

17.5 Make navigation failures visible

Provide explicit handling for rejected guards, missing entities, resolver failures, and chunk-load failures. A route that silently remains on the old page after a failed navigation creates uncertainty. Global error handling and route-specific redirects should have distinct responsibilities.

18. Common pitfalls

PitfallConsequenceBetter approach
Putting ** near the top It shadows later routes because the first match wins. Place wildcard routes last.[2]
Empty redirect without pathMatch: 'full' The empty prefix can match every URL. Use full matching for root redirects.[21]
Using a snapshot for reusable parameterized views The component may not react when only the parameter changes. Subscribe to paramMap or bind inputs.[22][19]
Calling navigate() inside a guard after returning false Navigation logic becomes side-effectful and race-prone. Return a UrlTree or RedirectCommand.[26]
Treating guards as authorization Users can modify browser code and call APIs directly. Enforce authorization server-side.[26]
One resolver fetches the entire page Navigation blocks on unrelated or slow data. Resolve essentials; load secondary data after activation.[27]
Lazy-loading every tiny page Navigation waterfalls and many small chunks. Choose feature-scale boundaries.[25]
No server fallback Deep links and refreshes return server 404 responses. Fallback application paths to index.html.[28]
Storing filter state only in components Back, refresh, sharing, and bookmarks lose state. Use query parameters for meaningful view state.
Overusing named outlets URL creation and route-state reasoning become difficult. Reserve them for independently navigable auxiliary views.

20. Conclusion

Angular Router is a URL-driven composition engine. Its route table recognizes paths, creates a router-state tree, evaluates navigation policy, acquires essential data, activates components into outlets, and synchronizes application transitions with browser history. The same model supports simple two-page applications and deeply nested, lazily loaded feature systems.[1][3][8]

Maintainable routing begins with stable URL contracts and clear ownership. Route files own matching and composition; outlets own placement; links own ordinary navigation; guards own client-side transition policy; resolvers own essential pre-activation data; components and stores own ongoing page state; and the server owns authorization, deep-link delivery, and authoritative resource behavior.
