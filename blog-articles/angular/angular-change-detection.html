Angular Change Detection

Change detection is the process by which Angular evaluates view bindings and updates the rendered DOM when application state differs from the values previously rendered. Modern Angular separates two questions: what notifies the framework that synchronization is needed, and which views are eligible to be checked during the resulting traversal.

1. The change-detection model

At a high level, Angular walks the application’s attached view tree, evaluates template bindings for eligible components, executes change-detection lifecycle hooks, and writes changed binding results through its rendering system. The traversal proceeds from parent views toward descendants, and Angular advises against making further state changes in the middle of the same pass because each component is intended to be visited once per traversal.[1][17]

State or event notification
Synchronization scheduled
Eligible views traversed
Bindings compared
DOM updated

Notification

A signal write, bound event, input update, AsyncPipe emission, explicit mark, Zone.js turn, or other supported API tells Angular that rendering may be stale.[7][8]

Eligibility

The component strategy, dirty flags, view attachment, and event/input ancestry determine whether a view is checked in a traversal.[2][3][4]

Evaluation

Angular reevaluates template expressions and selected lifecycle hooks synchronously for each checked view, then applies changed values to the DOM.[17][19]

a checked template binding
@Component({
  selector: 'app-price',
  standalone: true,
  template: `
    <p>
      Total:
      {{ quantity() * unitPriceCents() }}
    </p>
  `,
})
export class PriceComponent {
  readonly quantity = signal(2);
  readonly unitPriceCents = signal(1_299);
}

Angular does not compare arbitrary JavaScript object graphs. It reevaluates the expressions represented by compiled bindings and compares the current result with the stored prior result. A component’s change-detection strategy controls when its view participates in that evaluation.[3][31]

Scheduler versus detector Zone.js, signals, listeners, and explicit APIs can schedule synchronization. The detector is the view traversal and binding evaluation that follows. Excessive scheduling and expensive checked work are separate performance problems and should be diagnosed separately.

2. Historical development

AngularJS: digest loops and watchers

AngularJS linked template expressions to scope watchers. Calling $apply() entered the AngularJS context and initiated a $digest loop that repeatedly checked watched expressions until the model stabilized. Deep and collection watches carried greater cost than reference watches.[25]

Angular 2: component view detectors

The rewritten framework replaced scope watchers with component views and generated binding checks. Its public strategies were Default, described as CheckAlways, and OnPush, described as CheckOnce.[26]

Angular Zone and automatic scheduling

Angular used an Angular-specific Zone to know when asynchronous work completed and then initiate change detection, removing the normal need for AngularJS-style manual $apply() calls.[27]

Signals make dependencies explicit

Signals introduced explicit reactive producers and consumers. A signal read by a template marks that view when the signal changes, reducing reliance on generic “something asynchronous happened” scheduling.[5]

Angular 18–20: experimental to stable zoneless

Angular 18 introduced experimental zoneless support. The Angular roadmap records zoneless as stable from Angular 20.2 after work on server rendering, errors, tooling, and framework compatibility.[28][29]

Angular 21–22: new defaults

Zoneless scheduling is the application default from Angular 21. Angular 22 then makes OnPush the default component strategy, introduces the explicit name Eager for the older always-check behavior, and deprecates Default as an alias of Eager.[2][3][7][8]

Version-sensitive terminology Most existing Angular literature says “Default strategy” because Default/CheckAlways was historically the component default. In Angular 22, OnPush is the default; ChangeDetectionStrategy.Eager is the opt-in eager behavior; and ChangeDetectionStrategy.Default is a deprecated alias scheduled for removal.[3]

3. What happens during a check

3.1 Compiled binding evaluation

multiple binding kinds
@Component({
  selector: 'app-account-summary',
  standalone: true,
  template: `
    <h1>{{ account().name }}</h1>

    <button
      type="button"
      [disabled]="saving()"
      (click)="save()">
      {{ saving() ? 'Saving…' : 'Save' }}
    </button>
  `,
})
export class AccountSummaryComponent {
  readonly account = input.required<Account>();
  readonly saving = signal(false);

  save(): void {
    // ...
  }
}

Text interpolation, property bindings, class/style bindings, directive inputs, child-component inputs, and host bindings are all represented in the compiled view. Angular evaluates them for an eligible view and only writes a target when the result has changed.

3.2 Lifecycle hooks inside the pass

ngDoCheck, ngAfterContentChecked, and ngAfterViewChecked can execute very frequently. Angular warns that checked hooks can significantly affect performance and that state changes during later content/view hooks can trigger ExpressionChangedAfterItHasBeenCheckedError.[17][19]

custom check hook
export class DiagnosticsComponent
  implements DoCheck {

  ngDoCheck(): void {
    // Runs whenever Angular checks this directive/component.
    // Keep any work extremely small.
  }
}

DoCheck can implement custom input-change detection beyond normal binding comparisons, but the API documentation recommends caution; it can run even when the directive’s own component view is skipped.[31]

3.3 Development-mode consistency check

In development mode, Angular performs an additional verification to detect bindings that changed after they were checked. An unstable expression, a child that mutates parent state, or a late lifecycle mutation can produce ExpressionChangedAfterItHasBeenCheckedError. Production mode omits this developer consistency error.[18]

unstable template expression to avoid
@Component({
  selector: 'app-unstable',
  standalone: true,
  template: `
    <!-- Different value on repeated evaluation. -->
    <p>{{ Math.random() }}</p>
  `,
})
export class UnstableComponent {
  protected readonly Math = Math;
}

3.4 Render callbacks are after traversal

post-render DOM measurement
@Component({
  selector: 'app-measured-panel',
  standalone: true,
  template: `<section #panel>...</section>`,
})
export class MeasuredPanelComponent {
  readonly panel =
    viewChild.required<ElementRef<HTMLElement>>(
      'panel',
    );

  constructor() {
    afterNextRender(() => {
      const box =
        this.panel().nativeElement
          .getBoundingClientRect();

      console.log(box.width);
    });
  }
}

afterNextRender and afterEveryRender run after Angular finishes rendering the application. They are preferable to using checked lifecycle hooks merely to wait for the DOM.[17]

4. Eager and historical Default strategy

ChangeDetectionStrategy.Eager tells Angular to check the component whenever a change-detection traversal reaches it. ChangeDetectionStrategy.Default currently maps to the same enum value but is deprecated. Before Angular 22, Default/CheckAlways was the usual implicit strategy and remains common in existing code.[2][3][26]

explicit current eager strategy
import {
  ChangeDetectionStrategy,
  Component,
} from '@angular/core';

@Component({
  selector: 'app-legacy-dashboard',
  standalone: true,
  changeDetection:
    ChangeDetectionStrategy.Eager,
  template: `
    <h1>{{ title }}</h1>
    <p>{{ lastUpdated }}</p>
  `,
})
export class LegacyDashboardComponent {
  title = 'Operations';
  lastUpdated = new Date();
}

4.1 Behavior

If an eager component is reached during a scheduled traversal, Angular evaluates its bindings even when the component itself did not receive a new input or explicit dirty notification. An eager subtree can therefore be simple to integrate with mutable or externally updated state, but it offers less subtree-skipping than OnPush.[2][3]

4.2 When Eager can be appropriate

  • A compatibility component depends on legacy mutable state that does not notify Angular explicitly.
  • A library host dynamically creates user components that may themselves rely on eager behavior and Zone.js notifications.
  • A migration is being staged and correctness must precede optimization.

The zoneless guide notes that eager components can still work without Zone.js as long as state changes notify Angular through signals, AsyncPipe, markForCheck, listeners, or other supported APIs.[7]

4.3 Eager does not mean immediate

Changing a plain field does not itself synchronously render the DOM. A traversal must still be scheduled or invoked. Under Zone.js that scheduling may be broad; under zoneless mode a supported notification is required.

strategy and scheduling are separate
@Component({
  selector: 'app-status',
  standalone: true,
  changeDetection:
    ChangeDetectionStrategy.Eager,
  template: `<p>{{ status }}</p>`,
})
export class StatusComponent {
  status = 'idle';

  updateOutsideAngular(): void {
    // Merely assigning this field is not a zoneless
    // scheduling notification.
    this.status = 'ready';
  }
}

5. OnPush

OnPush is Angular 22’s default component strategy. It allows Angular to skip a component subtree unless the subtree has received a recognized reason to be checked. Historically, applications opted into it with ChangeDetectionStrategy.OnPush; explicitly writing the strategy remains useful for cross-version clarity.[2][3][4]

explicit OnPush component
@Component({
  selector: 'app-product-list',
  standalone: true,
  changeDetection:
    ChangeDetectionStrategy.OnPush,
  template: `
    <ul>
      @for (
        product of products();
        track product.id
      ) {
        <li>{{ product.name }}</li>
      }
    </ul>
  `,
})
export class ProductListComponent {
  readonly products =
    input.required<
      readonly Product[]
    >();
}

5.1 What marks or checks an OnPush subtree

AsyncPipe receives a valueAsyncPipe calls markForCheck and updates its latest value.[6][7]

5.2 Input identity and mutation

replace object identity
interface User {
  readonly id: string;
  readonly name: string;
}

readonly user = signal<User>({
  id: 'u1',
  name: 'Ada',
});

// Preferred:
user.update(current => ({
  ...current,
  name: 'Ada Byron',
}));

// Risky:
// user().name = 'Ada Byron';

If an input object is mutated while its reference remains the same, the parent-to-child input comparison does not report a new value. This is a common reason an OnPush child appears stale. Immutable replacement, signals, or explicit marking keeps ownership and notification visible.[4]

5.3 Events inside OnPush

bound event marks the subtree
@Component({
  selector: 'app-counter',
  standalone: true,
  changeDetection:
    ChangeDetectionStrategy.OnPush,
  template: `
    <p>{{ count }}</p>

    <button
      type="button"
      (click)="count = count + 1">
      Increment
    </button>
  `,
})
export class CounterComponent {

}

The event handler is an Angular-recognized notification, so the updated plain field is rendered even though the component is OnPush.

5.4 Signals are natural OnPush state

signal notification
@Component({
  selector: 'app-clock',
  standalone: true,
  changeDetection:
    ChangeDetectionStrategy.OnPush,
  template: `
    <time>{{ currentTime() }}</time>
  `,
})
export class ClockComponent {
  readonly currentTime =
    signal(new Date());

  update(): void {
    this.currentTime.set(
      new Date(),
    );
  }
}

5.5 Ancestor and sibling behavior

An event handled within an OnPush subtree causes Angular to check that subtree and its ancestors. Clean OnPush subtrees outside the event path can remain skipped. A new input to one OnPush child does not automatically require checking a clean OnPush sibling.[4]

6. Zone.js-based change detection

Zone.js patches asynchronous browser APIs so Angular can observe tasks such as timers, events, and network activity. In the historical zone-based model, completion of work in the Angular Zone provides a broad indication that application state might have changed and can schedule a traversal.[9][10][12][27]

6.1 Opt into Zone.js scheduling in current Angular

Zoneless is the default from Angular 21. A current standalone application that intentionally wants Zone.js-based scheduling can add provideZoneChangeDetection() and keep Zone.js in its polyfills/dependencies.[7][9]

zone-based application configuration
import {
  ApplicationConfig,
  provideZoneChangeDetection,
} from '@angular/core';

export const appConfig:
  ApplicationConfig = {
  providers: [
    provideZoneChangeDetection(),
  ],
};

6.2 Event and run coalescing

coalesce zone-triggered checks
export const appConfig:
  ApplicationConfig = {
  providers: [
    provideZoneChangeDetection({
      eventCoalescing: true,
      runCoalescing: true,
    }),
  ],
};

Event coalescing can combine change detection caused by related bubbling events. Run coalescing can combine multiple NgZone.run() calls in one event-loop turn and schedule a single detection through an animation frame.[11]

6.3 Run non-UI work outside Angular

escape and reenter NgZone
@Component({
  selector: 'app-animation-host',
  standalone: true,
  template: `
    <p>Completed frames: {{ completedFrames() }}</p>
  `,
})
export class AnimationHostComponent {
  private readonly zone =
    inject(NgZone);

  readonly completedFrames =
    signal(0);

  start(): void {
    this.zone.runOutsideAngular(() => {
      let frame = 0;

      const animate = (): void => {
        frame++;

        drawFrame(frame);

        if (frame < 1_000) {
          requestAnimationFrame(
            animate,
          );
          return;
        }

        this.zone.run(() => {
          this.completedFrames.set(
            frame,
          );
        });
      };

      requestAnimationFrame(animate);
    });
  }
}

Tasks scheduled inside runOutsideAngular continue outside the Angular Zone and do not cause its normal change-detection scheduling. run reenters for state that must be rendered. This is particularly useful for high-frequency animation, polling, and third-party libraries that do not update Angular state on every callback.[10][12]

6.4 Zone pollution

Angular calls repeated scheduling by timers, animation frames, or third-party tasks that do not change application state “zone pollution.” The official guidance recommends identifying the source with Angular DevTools and moving irrelevant work outside the Angular Zone.[12][21]

6.5 Zone.js is not the detector

Zone.js indicates that work may have happened. It does not know whether application state changed or which specific binding changed. OnPush, signals, dirty flags, and view attachment still govern which work the traversal performs.

7. Zoneless Angular

Zoneless change detection removes Zone.js as the scheduling mechanism and relies on explicit Angular notifications. It is enabled by default in Angular 21 and later. The stable provider remains useful for Angular 20 applications and tests, or when an application must explicitly override configuration.[7][8][29]

7.1 Default Angular 21+ configuration

default zoneless bootstrap
bootstrapApplication(
  AppComponent,
  appConfig,
);

// No zoneless provider is required in Angular 21+,
// provided provideZoneChangeDetection() is absent.

7.2 Explicit Angular 20 configuration

explicit stable zoneless provider
import {
  provideZonelessChangeDetection,
} from '@angular/core';

bootstrapApplication(
  AppComponent,
  {
    providers: [
      provideZonelessChangeDetection(),
    ],
  },
);

provideZonelessChangeDetection has been stable since Angular 20.2.[8]

7.4 Notifications that schedule zoneless synchronization

  • ChangeDetectorRef.markForCheck(), including its use by AsyncPipe.
  • ComponentRef.setInput().
  • Updating a signal read by a template.
  • A bound template or host listener callback.
  • Attaching or removing an eligible view.
  • Registering a render hook, when the hook itself performs a supported notification.

These are the current core scheduling notifications documented for zoneless applications.[7][8]

7.5 Plain fields need an explicit notification

mark a plain-field update
@Component({
  selector: 'app-message',
  standalone: true,
  template: `<p>{{ message }}</p>`,
})
export class MessageComponent {
  private readonly cdr =
    inject(ChangeDetectorRef);

  message = 'waiting';

  updateFromExternalCallback(): void {
    externalLibrary.onMessage(
      value => {
        this.message = value;
        this.cdr.markForCheck();
      },
    );
  }
}

A signal would perform this notification automatically if read by the template. For existing plain-field code, markForCheck is the normal compatibility bridge.

7.6 NgZone compatibility caveats

NgZone.run and runOutsideAngular may remain in code and are compatible with zoneless applications. However, NgZone.onMicrotaskEmpty, onUnstable, onStable, and isStable are not appropriate zoneless scheduling contracts; Angular recommends render callbacks or direct browser APIs instead.[7]

7.7 SSR stability

Server rendering needs to know when asynchronous work that affects output is pending. Angular’s zoneless guidance directs applications toward PendingTasks for custom asynchronous work rather than relying on Zone.js stability events.[7]

7.8 Migration checklist

  1. Profile and remove assumptions that every async callback triggers rendering.
  2. Use signals for template state, AsyncPipe for Observables, and bound listeners for UI events.
  3. Call markForCheck from external callbacks that update plain fields.
  4. Replace Zone stability observables with render callbacks or explicit pending-task registration.
  5. Run tests in zoneless mode and verify that updates arrive through real notifications.
  6. Remove Zone.js from polyfills and dependencies.

8. Manual change detection

ChangeDetectorRef exposes targeted APIs for marking, detaching, checking, and reattaching a view. Manual detection is powerful but should be used to express a clear lifetime or scheduling policy, not as a routine fix for unclear state ownership.[13][14]

8.1 markForCheck(): schedule eligibility

mark a view for a future pass
@Component({
  selector: 'app-external-status',
  standalone: true,
  changeDetection:
    ChangeDetectionStrategy.OnPush,
  template: `<p>{{ status }}</p>`,
})
export class ExternalStatusComponent {
  private readonly cdr =
    inject(ChangeDetectorRef);

  status = 'idle';

  constructor() {
    externalSdk.onStatus(
      status => {
        this.status = status;
        this.cdr.markForCheck();
      },
    );
  }
}

markForCheck does not synchronously check the view. It marks the view so the next scheduled traversal includes it.[13][14]

8.2 detectChanges(): check immediately

local synchronous check
@Component({
  selector: 'app-preview',
  standalone: true,
  template: `<pre>{{ text }}</pre>`,
})
export class PreviewComponent {
  private readonly cdr =
    inject(ChangeDetectorRef);

  text = '';

  refreshImmediately(
    nextText: string,
  ): void {
    this.text = nextText;
    this.cdr.detectChanges();
  }
}

detectChanges synchronously checks the current view and its children. Prefer normal scheduling unless the caller genuinely needs a local immediate render or owns a detached view.[13]

8.3 Detach and poll locally

detached high-frequency view

8.4 Conditional detach and reattach

view attachment controlled by state
@Component({
  selector: 'app-live-panel',
  standalone: true,
  template: `...`,
})
export class LivePanelComponent {
  private readonly cdr =
    inject(ChangeDetectorRef);

  readonly live = input(true);

      if (this.live()) {

        this.cdr.detach();

9. Signals, AsyncPipe, and Observable state

9.1 Template-read signals

signal-based notification
@Component({
  selector: 'app-progress',
  standalone: true,
  changeDetection:
    ChangeDetectionStrategy.OnPush,
  template: `
    <progress
      [value]="progress()"
      max="100">
    </progress>
  `,
})
export class ProgressComponent {
  readonly progress = signal(0);

  setProgress(value: number): void {
    this.progress.set(value);
  }
}

When an OnPush template reads a signal, Angular tracks the view as a signal consumer. Updating that signal marks the view automatically.[5]

9.2 AsyncPipe

Observable template state
@Component({
  selector: 'app-user-name',
  standalone: true,
  imports: [AsyncPipe],
  template: `
    @if (user$ | async; as user) {
      <p>{{ user.name }}</p>
    }
  `,
})
export class UserNameComponent {
  readonly user$ =
    inject(UserService)
      .currentUser$;
}

AsyncPipe subscribes to an Observable or Promise, stores the latest value, marks the component when a new value arrives, replaces subscriptions when the expression reference changes, and unsubscribes on destruction.[6]

9.3 Stable Observable identity

stable stream property
// Good: one pipeline/property.
readonly state$ =
  this.route.params.pipe(
    switchMap(params =>
      this.api.get(params['id']),
    ),
  );
unstable AsyncPipe source
<!-- Avoid a method that constructs a new
     cold Observable on every evaluation. -->
<p>{{ loadState() | async }}</p>

A changing Observable reference causes AsyncPipe to unsubscribe and subscribe again. If the source is cold, repeated construction can restart work such as HTTP requests.

9.4 Plain fields versus reactive primitives

Observable consumed by AsyncPipeYes, through markForCheck.[6][7]

10. Performance optimization

Angular’s performance guidance starts with measurement. Angular DevTools and the Angular track in Chrome DevTools visualize change-detection cycles, component rendering, lifecycle hooks, and the time attributed to each view. Optimize a demonstrated bottleneck rather than applying manual detection everywhere.[1][20][21]

10.1 Profile first

enable Angular Chrome profiling in development
import {
  enableProfiling,
} from '@angular/core';

enableProfiling();

The Chrome integration is development-only and correlates Angular-specific activity with the browser performance timeline.[20]

10.2 Reduce scheduled traversals

  • Use zoneless scheduling so Angular runs when supported notifications indicate a possible view change.[7]
  • In zone-based applications, move unrelated timers, animation loops, and third-party work outside NgZone.[12]
  • Use event/run coalescing when profiling shows multiple Zone-triggered checks per event-loop turn.[11]
  • Debounce or throttle high-frequency domain events before they update rendered state.

10.3 Reduce views checked

  • Use OnPush boundaries and immutable input replacement so clean subtrees can be skipped.[4]
  • Use stable @for track keys to preserve embedded views and child component identity.
  • Detach views only when their display can legitimately update on a separate cadence.[13]
  • Keep frequently changing state close to the smallest consuming subtree.

10.4 Reduce work per checked view

memoized signal derivation
readonly sortedOrders =
  computed(() =>
    [...this.orders()]
      .sort(compareOrders),
  );
pure pipe caching boundary
@Pipe({
  name: 'orderTotal',
  standalone: true,
  pure: true,
})
export class OrderTotalPipe
  implements PipeTransform {

  transform(
    lines: readonly OrderLine[],
  ): number {
    return calculateTotal(lines);
  }
}

Angular identifies slow template expressions and checked lifecycle hooks as a primary source of long change-detection cycles. The official guidance recommends improving the algorithm first, then considering pure pipes or memoization. Pure pipes rerun when their input values change.[19]

10.5 Avoid template allocation and side effects

template allocation
<!-- Avoid constructing a new object
     on every checked evaluation. -->
<app-chart
  [options]="{
    animated: true,
    density: density()
  }" />
stable computed options
readonly chartOptions =
  computed(() => ({
    animated: true,
    density: this.density(),
  }));

Methods and getters used by templates should be deterministic and inexpensive. Never mutate other bound state while evaluating a template expression.

10.6 Avoid frequent checked lifecycle hooks

ngDoCheck, ngAfterContentChecked, and ngAfterViewChecked are invoked during checking and can dominate a profile when they perform nontrivial work. Prefer signals, computed state, queries, and render callbacks.[17][19][31]

10.7 Layout work belongs after render

DOM reads and writes inside checked hooks can force layout recalculation. Use render phases or afterRenderEffect for necessary DOM integration and separate reads from writes where possible.[17]

10.8 A practical optimization order

  1. Record a representative interaction with Angular DevTools or Chrome DevTools.
  2. Determine whether the cost is too many cycles, too many checked views, or expensive work in a checked view.
  3. Fix algorithms and repeated template/lifecycle computation.
  4. Adopt zoneless notifications and OnPush-compatible state flow.
  5. Move irrelevant high-frequency work outside Angular or coalesce it.
  6. Use detach/manual detection only after the update cadence is explicitly defined.

11. Complete example: high-frequency telemetry dashboard

The example separates a high-frequency data source from rendered cadence. A service receives every sample outside the Angular Zone, stores only the latest value, and notifies a signal-backed dashboard at a bounded interval. The dashboard uses OnPush and computed selectors; a heavy chart is detached and checked locally.

telemetry.model.ts
export interface TelemetrySample {
  readonly timestamp: number;
  readonly temperature: number;
  readonly pressure: number;
}
telemetry-gateway.service.ts
@Injectable({
  providedIn: 'root',
})
export class TelemetryGateway {
  private readonly zone =
    inject(NgZone);

  private readonly latestSubject =
    new BehaviorSubject<
      TelemetrySample | null
    >(null);

  readonly latest$ =
    this.latestSubject
      .asObservable();

  connect(): void {
    this.zone.runOutsideAngular(() => {
      telemetrySdk.onSample(
        sample => {
          this.latestSubject.next(
            sample,
          );
        },
      );
    });
  }
}

@Injectable()

    inject(TelemetryGateway);

@Component({
  selector: 'app-telemetry-chart',
  standalone: true,
  template: `
    <canvas #canvas></canvas>
  `,
})
export class TelemetryChartComponent
  implements OnDestroy {

  private readonly cdr =
    inject(ChangeDetectorRef);

  private readonly store =
    inject(TelemetryStore);

  private readonly canvas =
    viewChild.required<
      ElementRef<HTMLCanvasElement>
    >('canvas');

  private readonly points:
    TelemetrySample[] = [];

  private readonly timerId:
    ReturnType<typeof setInterval>;

  constructor() {
    this.cdr.detach();

    effect(() => {
      const sample =
        this.store.latest();

      if (sample) {
        this.points.push(sample);
      }
    });

    this.timerId =
      setInterval(() => {
        drawChart(
          this.canvas().nativeElement,
          this.points,
        );

        this.cdr.detectChanges();
      }, 500);
  }

  ngOnDestroy(): void {
    clearInterval(this.timerId);
  }
}

12. Testing change detection

12.1 Production-like zoneless testing

force zoneless TestBed behavior
beforeEach(() => {
  TestBed.configureTestingModule({
    providers: [
      provideZonelessChangeDetection(),
    ],
  });
});

If Zone.js is absent, TestBed uses zoneless behavior by default. If Zone.js is loaded, the provider can force zoneless scheduling so tests validate the same notification contracts as production.[7][8]

12.2 Prefer real notifications and whenStable

zoneless-compatible test
it('renders a signal update', async () => {
  const fixture =
    TestBed.createComponent(
      CounterComponent,
    );

  fixture.componentInstance
    .count
    .set(5);

  await fixture.whenStable();

  expect(
    fixture.nativeElement
      .textContent,
  ).toContain('5');
});

The zoneless guide recommends avoiding unnecessary fixture.detectChanges() in new tests because it can force rendering even when production code failed to issue a notification. whenStable() allows Angular’s scheduler to perform the synchronization that real application notifications requested.[7]

12.3 Set inputs through ComponentRef

input notification in a test
it('renders a new input', async () => {
  const fixture =
    TestBed.createComponent(
      ProductListComponent,
    );

  fixture.componentRef.setInput(
    'products',
    [product],
  );

  await fixture.whenStable();

  expect(
    fixture.nativeElement
      .textContent,
  ).toContain(product.name);
});

12.4 Explicit detection remains valid

imperative fixture check
fixture.componentInstance.title =
  'Changed';

fixture.detectChanges();

expect(
  fixture.nativeElement.textContent,
).toContain('Changed');

ComponentFixture.detectChanges() remains useful for existing suites, direct class-field mutation, and tests specifically exercising manual detection. The fixture also exposes changeDetectorRef and checkNoChanges utilities.[23][24]

12.5 Detect missing zoneless notifications

development consistency polling
bootstrapApplication(
  AppComponent,
  {
    providers: [
      provideCheckNoChangesConfig({
        exhaustive: true,
        interval: 1_000,
      }),
    ],
  },
);

provideCheckNoChangesConfig can periodically check all attached, non-detached views as eager during development and surface bindings changed without a scheduling notification. This is especially useful during zoneless migration because ordinary follow-up checks can skip clean OnPush views.[22]

12.6 Zone-specific fakeAsync tests

The current tick() testing API requires Zone.js and is not supported by the Vitest runner. Prefer async/await, controlled Observables, fake timers provided by the selected test runner, or framework stabilization APIs in zoneless-oriented tests.

13. Debugging stale or unstable views

13.1 Stale OnPush child

SymptomLikely causeCorrection
Child does not reflect changed object fieldParent mutated the object while preserving input identityReplace the object or write through a signal.[4]
External SDK callback changes a plain field but UI remains staleNo zoneless scheduling notificationUse a template signal or call markForCheck.[7][13]
Dynamically created child ignores assigned inputDirect instance property assignmentUse ComponentRef.setInput.[16]
Detached view remains staleDirty detached views are not traversedCall local detectChanges or reattach.[13][14]
AsyncPipe repeats workTemplate creates a new cold Observable referenceExpose a stable pipeline or share deliberately.[6]

13.2 ExpressionChangedAfterItHasBeenCheckedError

late parent mutation hazard
export class ChildComponent
  implements AfterViewInit {

  readonly ready =
    output<void>();

  ngAfterViewInit(): void {
    // Can cause a parent binding to change
    // after it was already checked.
    this.ready.emit();
  }
}

The error means a binding produced a different value during Angular’s development verification after the regular pass. Fix the data flow or lifecycle timing; do not hide the problem by adding arbitrary setTimeout or global detectChanges calls.[18]

13.3 Find the expensive component

  1. Record the slow interaction in Angular DevTools Profiler.
  2. Select a tall change-detection bar and inspect component/directive time.
  3. Enable the change-detection-only view to see which OnPush components were actually checked.
  4. Use Chrome DevTools Angular track for correlation with layout, scripting, and third-party work.

Angular DevTools visualizes checked and skipped components and reports per-cycle duration; Chrome DevTools provides a correlated framework/browser timeline.[20][21]

14. Production architecture patterns

14.1 Build OnPush-compatible data flow

  • Own mutable state in one component, service, or store.
  • Expose signals, immutable input values, and Observable view models.
  • Use outputs and command methods rather than child mutation of parent objects.
  • Keep state close to the smallest subtree that renders it.

14.2 Treat external callbacks as boundaries

explicit integration notification
externalSdk.onChange(value => {
  // Signal path:
  this.value.set(value);

  // Or plain-field compatibility:
  this.legacyValue = value;
  this.cdr.markForCheck();
});

14.3 Separate high-frequency acquisition from render cadence

A sensor, drag stream, animation, or market feed may produce more events than the UI can use. Sample, throttle, aggregate, or detach locally rather than rendering every event.

14.4 Prefer reactive derivation over checked hooks

computed instead of ngDoCheck
readonly total =
  computed(() =>
    this.lines().reduce(
      (sum, line) =>
        sum +
        line.price *
          line.quantity,
      0,
    ),
  );

14.5 Keep strategy explicit in libraries

Angular 22 makes OnPush implicit, but a reusable library may still declare OnPush explicitly for compatibility and documentation. A dynamic host that must support arbitrary eager user components needs additional care, as the zoneless guide explains.[7]

14.6 Manual detection is an ownership contract

Detach only when one piece of code clearly owns the refresh schedule and cleanup. Document the cadence, visibility behavior, destruction, and whether child views are included.

PitfallConsequenceBetter approach
Assuming Default is still the current implicit strategyVersion-specific behavior is misunderstoodIn Angular 22, OnPush is default; use Eager explicitly and avoid deprecated Default.[2][3]
Mutating OnPush input objectsInput comparison sees the same referenceImmutable replacement or signal state.[4]
Expecting every async callback to render in zoneless modePlain-field updates remain staleUse signals, AsyncPipe, listeners, setInput, or markForCheck.[7][8]
Calling detectChanges everywhereHidden scheduling bugs and excessive synchronous workUse normal notifications; reserve detection for controlled local rendering.
Calling ApplicationRef.tick for local updatesThe entire attached application is processedmarkForCheck or local detectChanges.[13][15]
Detaching without a refresh ownerPermanent stale UIDefine polling/event cadence and destruction cleanup.[13]
Heavy work in checked hooksEvery relevant traversal slows downComputed state, pure pipes, memoization, or event-driven work.[19]
Zone-based timer pollutionUnnecessary application traversalsRun irrelevant work outside NgZone or migrate zoneless.[12]
Creating Observables in template methodsAsyncPipe resubscribes and can restart workExpose stable Observable properties.[6]
Using late lifecycle mutations to fix initializationExpressionChanged errors or extra cyclesInitialize in constructor, input derivation, or ngOnInit.[17][18]

18. Conclusion

Angular change detection consists of notification, scheduling, view eligibility, binding evaluation, and rendering. Zone.js historically supplied broad asynchronous notifications; zoneless Angular instead relies on explicit framework notifications such as template signal writes, AsyncPipe emissions, bound listeners, setInput, and markForCheck.[7][8][9]

Angular 22 changes the strategy baseline: OnPush is now the default, Eager names the old always-check behavior, and Default is a deprecated alias. Effective performance work follows the same hierarchy regardless of version—profile first, reduce unnecessary schedules, skip unaffected subtrees, remove slow checked computations, and use manual detection only where a clearly owned rendering cadence requires it.[2][3][19][20][21]
