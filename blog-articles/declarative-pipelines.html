01 · The thesis

Two descriptions of the same pipeline

Every data pipeline is a claim about the world: that some set of tables ought to exist, ought to contain particular rows, and ought to be no more than some number of minutes out of date. There are two ways to write that claim down. You can write the steps that produce it, or you can write the claim itself and make something else work out the steps.

For most of the last fifteen years, data engineering did the first. The canonical artifact of the field — an Airflow DAG file — is a Python program whose job is to enumerate tasks and wire them together in the correct order. The ordering is authored by hand. The graph exists because the engineer typed it. Nothing in the file says what any of those tasks produce; the file describes a procedure, and the data is a side effect of running it.

The alternative is older than the field, and it is the same alternative that databases resolved in 1970: describe the result, and let a planner decide the execution. That idea has now been rebuilt three separate times inside data engineering — in the transformation layer, in the orchestrator, and finally inside the query engines themselves — and the rebuild is far enough along that it is worth being precise about what changed, what it bought, and what it cost.

This article traces that shift: where the idea came from, what problem it was actually solving, how the current generation of tools implement it, where the abstraction leaks, and what a working engineer should and should not hand over to a planner.

02 · Definitions

What "declarative" actually means

The word is used loosely enough in vendor material that it is worth anchoring it. The cleanest formulation is Robert Kowalski's, from 1979: an algorithm has two separable components, a logic component that says what is to be computed and a control component that says how the computation proceeds. The logic determines what the program means; the control determines how fast it runs.[1] Declarative programming, on this reading, is the practice of writing only the logic and letting an execution engine supply the control.

The literature makes a further distinction that matters a great deal for pipelines, because almost every real tool sits on the wrong side of it. Declarative programming in the strong sense means the programmer supplies only the logic and the system supplies all of the control. In the weak sense, the programmer supplies logic plus some control hints to make execution tractable.[2][3] Nothing in production data engineering is strongly declarative. A dbt model that sets materialized='incremental' and a unique_key is supplying control. A dynamic table with TARGET_LAG = '10 minutes' is supplying control. The interesting question is never "is this declarative?" but "which decisions have been handed over, and which have been kept?"

A working definition for pipelines. A pipeline is declarative to the extent that the author states properties of the desired output — its contents, its dependencies, its freshness, its constraints — and an engine derives the execution plan: what to run, in what order, over what slice of data, and how often.

That phrasing makes the shift legible as a series of specific transfers of authority. Six decisions have to be made before any pipeline can run, and each of them can sit with the author or with the engine:

  1. Dependency order. What must be finished before this thing starts.
  2. Scope of work. Which parts need rebuilding at all.
  3. Physical materialisation. Whether the result is a view, a table, an appended partition, or a continuously maintained index.
  4. Trigger. When execution happens.
  5. Quality enforcement. What happens to rows that violate an invariant.
  6. Business logic. What the numbers actually mean.

The sixth never moves. It is the irreducible content of the pipeline, and no engine can infer it. The declarative turn is the story of the first five migrating, one at a time, from the author to the runtime.

03 · Prior art

The prior art the field already had

Data engineering did not invent this idea; it rediscovered it, comparatively late, and from at least four directions at once.

The relational model

Codd's 1970 paper set out to provide data independence — the independence of application programs from changes in data representation — and proposed a model in which users describe the relations they want rather than the access paths by which those relations are assembled.[4] Chamberlin and Boyce's 1974 SEQUEL paper turned that model into something a non-mathematician could type, replacing bound variables and quantifiers with keyword templates over tabular structures.[5] Chamberlin's own retrospective marks that 1974 workshop as the moment the clock started on relational databases, precisely because it staged a direct confrontation between the network model and the relational one.[6]

The consequence is the one every data engineer takes for granted: a SELECT is a specification, and the query optimiser is a planner that chooses join order, access method and parallelism without asking. Declarative pipelines are, structurally, an attempt to lift that same contract from the level of a single query to the level of a whole graph of tables.[44]

Make

The second ancestor is not a database at all. Stuart Feldman's make, first implemented at Bell Labs in April 1976 and described formally in 1979, solved a problem that is recognisably the same problem: given a set of artifacts, a set of dependencies between them, and commands that produce each one, work out the minimum set of commands needed to bring everything up to date.[7][9] Feldman's description file, in his words, "really defines the graph of dependencies"; make performs a depth-first search of that graph and decides what work is necessary by comparing file modification times.[8]

Every element of the modern declarative pipeline is present in that 1976 design: a declared artifact, declared prerequisites, an inferred order, and a staleness test that prunes the work. What changed in the intervening half-century is the staleness test — file mtimes are a poor proxy when the artifact is a hundred-billion-row partitioned table — and the fact that the artifacts now live in a warehouse rather than a filesystem. The shape is unchanged.

Reconciliation loops

The third ancestor is infrastructure. The Borg–Omega–Kubernetes lineage established the reconciliation controller loop as a general design pattern: a controller compares a desired state against an observed state and takes action to converge the two. Because all action is based on observation rather than on a state diagram, the loop is robust to failure and restart — a controller that crashes simply picks up where it left off.[10] That property is exactly what a pipeline wants and what a step-list cannot give you: a re-run of a procedure has to be reasoned about, whereas a re-evaluation of a desired state is inherently safe.

Terraform generalised the same pattern to configuration. Its language is declarative by design — it describes the desired end state rather than step-by-step instructions — and its providers compute dependencies automatically to create or destroy resources in the correct order.[11][12] The plan/apply split, in which a diff between declared and recorded state is rendered for human review before anything executes, has since been copied almost verbatim into the data tooling.[66]

Functional data engineering

The fourth ancestor is internal to the field. In 2018, Maxime Beauchemin — who had built Airflow four years earlier — published an argument that batch processing should adopt functional-programming discipline: tasks should be deterministic and idempotent, producing the same result on every re-run; partitions rather than rows should be the atomic unit of state; and a pure task should always fully overwrite its output partition rather than mutating it with UPDATE, APPEND or DELETE.[21][22] The pairing he identified as the key to reproducibility — immutable data plus versioned logic — is the precondition for everything that follows.[23][24]

This matters because declarativity is not primarily an ergonomic improvement. It is a correctness argument that only works if re-execution is safe. An engine can only decide to skip work, or to rebuild a downstream cone, if recomputation is guaranteed to produce the same answer. Idempotency is not a nice property of declarative pipelines; it is the load-bearing assumption underneath the planner.

04 · History

How the imperative era happened

It is easy, from here, to read the 2010s scheduler generation as a wrong turn. It was not. It was a rational response to a stack in which nothing else could be assumed.

Hadoop-era pipelines had to coordinate heterogeneous, long-running jobs across machines that failed regularly. Apache Oozie, the first widely deployed answer, described workflows as directed acyclic graphs of actions in XML, with coordinator jobs triggered by time and data availability.[13] It was declarative in form — XML, no control flow — and almost universally disliked, because the declaration was verbose, Hadoop-specific, and had no expressive escape hatch when the shape of the problem did not match the schema.

Spotify's Luigi, built in late 2011 by Erik Bernhardsson and Elias Freider and open-sourced in 2012, made the opposite bet.[14][15] Its own documentation is explicit that it is conceptually similar to make, with tasks that depend on other tasks — but that, unlike Oozie and Azkaban, "everything in Luigi is in Python. Instead of XML configuration or similar external data files, the dependency graph is specified within Python."[14] That single sentence is the pivot of the decade. It trades a declarative but rigid configuration format for a general-purpose language, and in doing so buys expressiveness at the cost of analysability.[16]

Airflow, started at Airbnb in October 2014 by Beauchemin and announced publicly in June 2015, took the same bet and executed it better.[17][18] It joined the Apache incubator in March 2016 and became a top-level project in 2019.[17] Its design principle was configuration-as-code in plain Python: workflows could be version-controlled, developed concurrently, tested, and extended with operators and hooks reaching into whatever the rest of the stack happened to be.[19][20]

Airflow won, decisively, and the reasons are worth stating plainly because they are the same reasons imperative escape hatches persist inside declarative tools today:

  • Dynamism. A DAG can be generated by a loop over a config file, a database query, or an API call at parse time. No fixed schema can express that.
  • Heterogeneity. Real pipelines touch an FTP server, a vendor API with a bespoke auth flow, a Spark cluster, and a Tableau extract refresh. An operator model absorbs all of that; a table-definition model does not.
  • Testability and review. Python DAGs go through the same code review and CI as everything else, which was a genuine advance over GUI schedulers.

The documentation of the era states the limitation as neutrally as it can: while a DAG orchestrates task sequences, dependencies and run frequencies, "it doesn't dictate the specifics of what actually happens within each task."[20] That is the whole problem in one line.

05 · The bind

What a task graph cannot say

Consider the single most common node in production Airflow deployments circa 2021: a BashOperator running dbt run. It is one vertex in the graph. It writes, in a mature project, several hundred tables.

When it fails, the orchestrator knows precisely one fact: the task failed. It does not know which of the several hundred tables were written before the failure, which are now stale, which downstream consumers should stop trusting their inputs, or whether a partial write left the warehouse in a state where the next run will double-count. The lineage the orchestrator displays is a lineage of tasks, which is an arbitrary artifact of how the engineer chose to group work, rather than a lineage of the physical objects anyone actually cares about.[33]

The gap shows up in three concrete places.

Partial-failure semantics. A task-centric scheduler retries the task. If the task is not idempotent — and nothing in the model requires it to be — the retry can corrupt. This is the practical reason Beauchemin's functional discipline had to be argued for rather than assumed: the framework does not enforce it.[21]

Scheduling granularity. Time-based triggers are the only thing a task graph natively understands, so the schedule becomes a proxy for readiness. A downstream DAG runs at 06:00 because upstream "usually finishes by 05:30". When it does not, the downstream job runs on stale inputs and reports success. Airflow's own asset documentation names this as the motivating scenario: a machine-learning team's DAG should run when the data engineering team's DAG has actually produced an update, not at a time that is empirically correlated with it.[43]

Selective rebuild. Given a code change, which tables are wrong? A task graph cannot answer this, because it does not know which tables each task writes, let alone which columns. So the operational default becomes "rebuild everything", and the warehouse bill becomes a function of caution rather than of change.

Every one of these is a question about state, and the imperative model describes transitions. That mismatch is the reason the field moved.

06 · The transformation layer

dbt and the inversion

The first successful transfer of authority happened outside the orchestrator entirely. dbt began in 2016 as an internal tool at Fishtown Analytics, a small Philadelphia consultancy founded by Tristan Handy, Drew Banin and Connor McArthur, who had worked together at RJMetrics; the company renamed itself dbt Labs in 2021.[25][26] The founders expected to be its only two users.[26]

Handy's account of the originating problem is unusually precise about what was missing. Cloud warehouses had made it cheap to load raw data and transform it in place, which moved the transformation step into SQL — but, as he put it, "there's these fundamental things in data engineering that everybody has to figure out how to do… and the biggest thing is just things depend on other things. SQL doesn't have a concept of this thing depends on this thing, so run them in this order." From its first version, dbt had that concept.[27]

The mechanism

The mechanism is a single function. A dbt model is a SELECT statement in a file; the only legal way for one model to name another is {{ ref('other') }}. At compile time that reference does two things at once: it renders to the fully qualified relation name for the current target environment, and it registers an edge in the project's dependency graph.

The consequences compound. Because the graph is derived from the code, environment promotion becomes free: the same model renders against dev or prod without an edit. Because the graph is a first-class object, node selection becomes a query language — build this model and everything downstream of it, or everything upstream of it, or only what changed. Because the graph is materialised as a manifest, documentation and lineage are generated rather than maintained.

Materialisation as a declaration

The second thing dbt made declarative is the physical shape of the output. The author writes a SELECT; a materialized config decides what the engine does with it — wrap it in a view, rebuild it as a table, merge new rows into an existing table, or inline it as a common table expression in every consumer.[28] The same business logic can move between these without being rewritten, which is a real achievement: the decision about when to pay for the arithmetic is separated from the decision about what the arithmetic is.[29]

Tests followed the same pattern. Rather than writing an assertion task, the author attaches properties to a column in YAML — unique, not_null, accepted_values, relationships — and dbt compiles each into a query that should return zero rows. The invariant lives beside the model rather than in a separate validation pipeline.

What it did not do

dbt declared the graph and the materialisation but pointedly not the trigger. A dbt project has no scheduler; something else has to run dbt build. For most of its life the something else was Airflow, and the result was the hybrid that dominated the early 2020s: a declarative transformation layer nested inside an imperative orchestrator, with the orchestrator blind to everything inside the transformation layer.[84]

It also did not understand the SQL. dbt Core treats model bodies as templated strings; Jinja is expanded, the result is sent to the warehouse, and syntax errors surface at runtime.[67] This is the seam that the next generation of tools attacked, and it is discussed in §13.

07 · The orchestrator

Assets, not tasks

The second transfer moved the trigger. If the orchestrator knows which objects exist and which depend on which, then "run this at 06:00" can be replaced by "keep this no more than an hour behind its inputs", and the scheduler becomes a solver.

Dagster made this its organising principle with software-defined assets: a model in which each persistent object — a table, a file, a trained model — is declared by a function annotated with its identity and its dependencies. The framing from the Dagster team is that the author declares what the end state of an asset should be, and the orchestrator supplies the execution logic required to reach that state.[30] Sandy Ryza's formulation is sharper still: rather than describing the chaos that exists, an asset definition declares the order you want to create, and an asset-based orchestrator materialises and maintains it.[31] Nick Schrock has consistently described this as a shift from a workflow scheduler to a data control plane.[32][33]

The practical payoff is that lineage becomes a lineage of physical objects rather than of tasks, which is the thing data consumers actually want, and integrations with external tools can expand into the graph — a dbt project's several hundred models become several hundred nodes rather than one.[30][31]

Declarative automation

Dagster's 1.8 release in 2024 replaced its earlier auto-materialisation policies with declarative automation: an AutomationCondition attached to an asset, built from composable boolean operands.[36][81] AutomationCondition.eager() updates an asset whenever any of its dependencies update, propagating changes downstream automatically; on_cron() fires only once all dependencies have updated since a given tick; on_missing() fills in partitions as upstream data becomes available.[34] These compose with &, | and ~, and a daemon evaluates them continuously and issues materialisation requests when they hold.[35]

The design detail worth noticing is that the shipped conditions are themselves built from smaller ones and can be decomposed. The default eager() policy contains a sub-condition preventing execution when upstream data is missing, and a sub-condition restricting updates to the latest time partition; both can be removed by name if your situation differs.[37] An adjacent condition, all_deps_blocking_checks_passed(), lets an asset refuse to execute while its upstream quality checks are failing.[37] This is the declarative model earning its keep: policies about when become expressions that can be inspected, tested and composed, rather than scheduling code that has to be read.

Airflow converges

Airflow moved in the same direction. Datasets arrived in 2.4 and were promoted to first-class assets in Airflow 3.0, generally available in April 2025, alongside an asset-centric decorator syntax, watchers that respond to external signals, and event-driven scheduling built on top of them.[38][40] A DAG can be scheduled on a list of assets and will run once all of them have been updated since its last run; conditional expressions over assets allow more elaborate trigger logic.[39] Airflow 3.2 added asset partitions, so that a downstream DAG fires only when the specific slice it consumes has changed rather than on every upstream update — the most consequential change to data-aware scheduling since assets were introduced.[41][42]

Notably, Airflow kept both models side by side rather than replacing one with the other.[38] That is the right call, and it reflects the practical reality described in §15: a great deal of real work is genuinely procedural, and forcing it into an asset shape produces worse code, not better.[83] Prefect makes the same argument from the other side, positioning itself around "negative engineering" — removing retry, timeout and state-handling boilerplate from ordinary Python rather than replacing Python with a specification format.[80][83]

08 · The engine

The pipeline moves inside the engine

The third transfer is the most recent and the most aggressive: pushing the whole pipeline abstraction down into the query engine, so that there is no external orchestrator at all.

Delta Live Tables to Spark Declarative Pipelines

Databricks launched Delta Live Tables in 2022 as a framework in which each table is declared as a query and the runtime derives the dependency graph, the batch-versus-stream incrementalisation, the data-quality enforcement and the orchestration.[48] At the 2025 Data + AI Summit the company donated the core engine to Apache Spark as Spark Declarative Pipelines and rebranded the commercial product under the Lakeflow umbrella.[44][45] The framing in the announcement is exact about what is being extended: the contribution takes Spark's declarative power, which previously applied to individual queries, and raises it to the level of entire pipelines — the user defines what the pipeline should do, and Spark determines how.[44] Michael Armbrust's description of the programming model is one sentence: you declare a series of datasets and data flows, and Spark figures out the right execution plan.[46]

Existing DLT code continues to run; the migration is largely a rename, with import dlt becoming from pyspark import pipelines as dp, the @table decorator now creating streaming tables and a new @materialized_view decorator covering the batch case.[47] The open-source path matters less for portability in practice — almost nobody abandons the managed runtime, since doing so costs Auto Loader, catalog integration and serverless compute — than for procurement teams that require no lock-in at the compute layer.[48][49]

Dynamic tables

Snowflake's dynamic tables take the same idea and reduce the surface area further. A single DDL statement carries three declarations: what the table contains (a SELECT), how fresh it must be (TARGET_LAG), and how it should be maintained (REFRESH_MODE). Snowflake parses the query, identifies the base tables, registers the object for refresh, and schedules everything thereafter.[55] Dependencies are inferred; the refresh order across a DAG follows the topology; and all dynamic tables in a graph refresh from synchronised snapshots so the pipeline is internally consistent.[58][85]

The semantics of TARGET_LAG deserve emphasis because they are widely misread. It is a staleness target, not a refresh interval: '10 minutes' means the data should be no more than ten minutes old, not that a refresh fires every ten minutes.[56] Snowflake picks a cadence intended to hold the promise — a four-hour target might refresh every three and a half hours — and the lag is measured relative to the base tables at the root of the pipeline rather than to the direct upstream.[57] Setting the target to DOWNSTREAM defers scheduling to dependants, which effectively suspends automatic refresh for the whole graph and is the standard development idiom.[56][58]

Snowflake is explicit that the target is best-effort: actual lag can exceed it when warehouse size, data volume, query complexity or pipeline depth constrain throughput, and applications should not assume the data is always within target.[56] This is a general property of declarative freshness contracts and a good instinct to carry into any of them.

Streaming

The streaming world arrived at the same destination from the opposite direction. Flink SQL's continuous queries over dynamic tables are, in principle, materialised-view maintenance: the query defines the view, the input stream supplies the changes, and the engine keeps the result up to date incrementally.[60] FLIP-435 pushed this further with materialized tables that carry a declared SQL statement and a declared freshness, explicitly so that batch and streaming transformations can be defined the same way and task orchestration is managed automatically.[59]

The academic lineage behind this is deep and is worth knowing about, because it explains why some declarations can be honoured cheaply and others cannot. Incremental view maintenance research runs from first-order delta rules through DBToaster's higher-order IVM in 2012, Differential Dataflow's timestamp-based generalisation in 2013, Noria's partial IVM in 2018, and DBSP's reformulation of databases as streams over commutative groups in 2023.[62] Streaming databases such as Materialize and RisingWave deploy these as long-running dataflows that maintain results continuously, in contrast to systems that emit changes downstream and leave consumption to the user; warehouses bridge the two by pairing change data capture with scheduled or target-freshness maintenance.[62][63] The persistent obstacles named in this literature are precisely the ones practitioners hit: manual incrementalisation, semantic differences between SQL implementations, and the fact that most systems optimise for sub-second latency when many real use cases are well served by seconds to tens of minutes.[61]

Ingestion

Ingestion declarativised too, though it is discussed less. Airbyte observed that API source connectors — the overwhelming majority of connectors — are also the most formulaic, solving small variations of the same problems: authenticate, paginate, slice, retry, map.[70] Its low-code CDK replaces connector code with a YAML manifest that the runtime interprets, and the payoff is not just less code.[69] Because the connector is a declaration, a capability like resumable full refresh can be implemented once in the framework rather than per connector, and metadata such as "which pagination strategy does this connector use" can be extracted without reading any code.[70] That second property — the declaration is queryable — recurs everywhere in this article and is the underrated half of the argument.

09 · Concepts

Anatomy of a declarative runtime

Strip away the branding and every one of these systems does the same six things. The differences are in how much of each step is inferred and how durably the results are recorded.

Parse. Read the declarations — SQL files with templating, decorated Python functions, YAML manifests, or DDL statements — into an internal representation. The critical variable here is how deeply the engine understands what it read. Treating a model body as a string is cheap and permissive; parsing it into an abstract syntax tree is expensive and enables everything in §13.

Resolve. Extract dependencies and build the DAG. In dbt this means collecting ref() and source() calls; in Dagster, reading deps and input parameters; in Snowflake, identifying the base tables a dynamic table's query reads from.[55] The engineering requirement is that the reference be the only way to express a dependency. The moment a model can reach another table by writing its physical name directly, the graph stops being sound and the whole edifice becomes advisory.

Diff. Compare the declared state against a recorded state. The recorded state is the piece practitioners most often underestimate. It is what allows an engine to answer "has this changed?" without re-running anything, and its contents vary: file mtimes for make, a state file for Terraform, a manifest of node checksums for dbt, an event log and materialisation history for Dagster, change-tracking metadata for dynamic tables.[11][57]

Plan. Select the subgraph that needs work and choose how to do it. This is where materialisation strategy, incremental predicates and partition selection get resolved. In Terraform and SQLMesh this step is exposed to the user as a reviewable artifact before anything runs — the plan/apply split.[11][66] In most data tools it is implicit, which is a meaningful loss of control.

Execute. Emit work in topological order, with concurrency where the graph permits and retries where the runtime allows. Nothing about this step is conceptually interesting, which is exactly the point: it is the part that was previously hand-written.

Record. Write back fingerprints, lineage, row counts and quality results. Skipping this step is what separates a build tool from a control plane. It is also what makes declarative pipelines legible to things that are not the engine — catalogs, observability tools, and increasingly agents.[86]

10 · Examples

One pipeline, four dialects

The same trivial pipeline — clean orders, join to customers, aggregate daily revenue — written four ways. Read them for what each one omits.

Airflow, task-centric

from airflow import DAG
from airflow.providers.common.sql.operators.sql import SQLExecuteQueryOperator
import pendulum

with DAG(
    dag_id="revenue",
    schedule="0 6 * * *",                # a guess about upstream readiness
    start_date=pendulum.datetime(2026, 1, 1),
    catchup=False,
) as dag:
    clean   = SQLExecuteQueryOperator(task_id="clean",   sql="sql/stg_orders.sql")
    cust    = SQLExecuteQueryOperator(task_id="cust",    sql="sql/stg_customers.sql")
    facts   = SQLExecuteQueryOperator(task_id="facts",   sql="sql/fct_orders.sql")
    revenue = SQLExecuteQueryOperator(task_id="revenue", sql="sql/revenue_daily.sql")

    [clean, cust] >> facts >> revenue   # the edges are typed by hand

Four tasks, four SQL files, and one line of hand-authored topology. If someone edits fct_orders.sql to read from a table that isn't stg_orders, the >> line is now a lie and nothing detects it. The 0 6 * * * is the load-bearing assumption.

dbt, model-centric

-- models/marts/revenue_daily.sql
{{ config(materialized='incremental', unique_key='revenue_date') }}

select
    order_date as revenue_date,
    region,
    sum(net_amount) as revenue
from {{ ref('fct_orders') }}
{% if is_incremental() %}
where order_date >= (select max(revenue_date) from {{ this }})
{% endif %}
group by 1, 2

# models/marts/_marts.yml
models:
  - name: revenue_daily
    columns:
      - name: revenue_date
        data_tests: [not_null]
      - name: revenue
        data_tests:
          - dbt_utils.accepted_range: {min_value: 0}

No topology, no schedule. The edge to fct_orders is implied by ref(); the physical strategy is a config; the invariants are properties of columns. What is still imperative: the is_incremental() block, in which the author hand-writes the predicate that selects the new slice.

Dagster, asset-centric

import dagster as dg

@dg.asset(
    deps=["fct_orders"],
    automation_condition=dg.AutomationCondition.eager(),
    partitions_def=dg.DailyPartitionsDefinition(start_date="2026-01-01"),
    kinds={"snowflake"},
    owners=["team:analytics"],
)
def revenue_daily(context: dg.AssetExecutionContext, warehouse) -> None:
    day = context.partition_key
    warehouse.execute(f"""
        delete from revenue_daily where order_date = '{day}';
        insert into revenue_daily
        select order_date, region, sum(net_amount)
        from fct_orders where order_date = '{day}'
        group by 1, 2
    """)

The trigger is now a declaration too: eager() means "update whenever an upstream dependency updates", and the daily partition definition makes the unit of work explicit rather than encoding it in a WHERE clause.[34] Ownership and storage kind are metadata the catalog can read. The body of the function remains ordinary imperative code — deliberately.

Spark Declarative Pipelines / Lakeflow, engine-native

CREATE OR REFRESH STREAMING TABLE orders_clean (
  CONSTRAINT valid_order   EXPECT (order_id IS NOT NULL) ON VIOLATION FAIL UPDATE,
  CONSTRAINT valid_amount  EXPECT (net_amount >= 0)        ON VIOLATION DROP ROW
)
AS SELECT order_id, customer_id, order_date, amount - coalesce(discount, 0) AS net_amount
   FROM STREAM read_files('/volumes/raw/orders', format => 'json')
   WHERE status <> 'cancelled';

CREATE OR REFRESH MATERIALIZED VIEW revenue_daily
AS SELECT order_date, region, sum(net_amount) AS revenue
   FROM orders_clean JOIN dim_customer USING (customer_id)
   GROUP BY 1, 2;

There is no orchestrator, no schedule, no incremental predicate and no separate test suite. Dependency order, streaming-versus-batch incrementalisation, retries, checkpoint state and quality enforcement are all the runtime's problem.[44][50] This is the furthest right on Figure 2 — and correspondingly the least portable.

11 · Implementation

A declarative engine in a hundred lines

The mechanism is genuinely small. The following is a complete, runnable transformation engine using nothing outside the Python standard library. It parses model declarations, derives the graph from ref() calls, fingerprints each node together with its ancestors, diffs against recorded state, plans the minimum work, executes in topological order, and records the result. It is not a toy in the sense of being fake — it is a toy in the sense of being small.

"""
minimesh — a ~120-line declarative transformation engine.

Dependency-free (sqlite3 + hashlib + re from the standard library). It shows the
five moves every declarative pipeline engine makes: parse, resolve, diff, plan,
record.

    python3 minimesh.py
"""
import hashlib
import re
import sqlite3
import sys

# --- 1. THE DECLARATION -----------------------------------------------------
# Each model states what it *is*, never when or in what order to build it.
# {{ ref('x') }} is the only legal way to name another model.

MODELS = {
    "stg_orders": dict(
        materialized="table",
        sql="""select order_id, customer_id, order_date,
                      amount - coalesce(discount, 0) as net_amount
               from raw_orders
               where status <> 'cancelled'"""),
    "stg_customers": dict(
        materialized="table",
        sql="""select customer_id, lower(trim(email)) as email, region
               from raw_customers"""),
    "fct_orders": dict(
        materialized="table",
        sql="""select o.order_id, o.order_date, o.net_amount, c.region
               from {{ ref('stg_orders') }} o
               join {{ ref('stg_customers') }} c using (customer_id)"""),
    "revenue_daily": dict(
        materialized="table",
        sql="""select order_date, region, round(sum(net_amount), 2) as revenue
               from {{ ref('fct_orders') }}
               group by order_date, region"""),
}

TESTS = [("revenue_daily", "revenue is never negative", "revenue < 0")]

REF = re.compile(r"\{\{\s*ref\(\s*['\"]([A-Za-z0-9_]+)['\"]\s*\)\s*\}\}")


# --- 2. RESOLVE: the graph is derived, never authored -----------------------
def resolve(models):
    """Extract edges from the SQL itself, then topologically sort."""
    deps = {name: set(REF.findall(m["sql"])) for name, m in models.items()}
    order, seen, stack = [], set(), set()

    def visit(n):
        if n in seen:
            return
        if n in stack:
            raise ValueError(f"cycle through {n}")
        stack.add(n)
        for d in sorted(deps[n]):
            visit(d)
        stack.discard(n)
        seen.add(n)
        order.append(n)

    for n in sorted(models):
        visit(n)
    return order, deps


def render(name, models):
    """Replace ref() with the physical relation name."""
    return REF.sub(lambda m: m.group(1), models[name]["sql"])


# --- 3. DIFF: fingerprint code + upstream fingerprints ----------------------
def fingerprints(order, deps, models):
    """A node's fingerprint folds in every ancestor, so an upstream edit
    invalidates the whole cone below it without anyone tracking it by hand."""
    fp = {}
    for n in order:
        h = hashlib.sha256()
        h.update(re.sub(r"\s+", " ", models[n]["sql"]).strip().encode())
        h.update(models[n]["materialized"].encode())
        for d in sorted(deps[n]):
            h.update(fp[d].encode())
        fp[n] = h.hexdigest()[:12]
    return fp


def read_state(con):
    con.execute("create table if not exists _state(name text primary key, fp text)")
    return dict(con.execute("select name, fp from _state"))


# --- 4. PLAN ----------------------------------------------------------------
def plan(order, fp, state):
    out = []
    for n in order:
        if n not in state:
            out.append((n, "create", "not materialised"))
        elif state[n] != fp[n]:
            out.append((n, "update", f"{state[n]} → {fp[n]}"))
        else:
            out.append((n, "skip", "unchanged"))
    return out


# --- 5. EXECUTE + RECORD ----------------------------------------------------
def apply(con, steps, models, fp):
    built = 0
    for name, action, _ in steps:
        if action == "skip":
            continue
        con.execute(f"drop table if exists {name}")
        con.execute(f"create table {name} as {render(name, models)}")
        con.execute("insert or replace into _state values (?,?)", (name, fp[name]))
        built += 1
    con.commit()
    return built


def run_tests(con, tests):
    results = []
    for model, label, predicate in tests:
        (bad,) = con.execute(
            f"select count(*) from {model} where {predicate}").fetchone()
        results.append((model, label, bad))
    return results

A node's fingerprint folds in the fingerprints of all its ancestors, so an edit to stg_orders changes the fingerprint of fct_orders and revenue_daily without anyone tracking that relationship by hand. Three properties are worth naming, because production engines differ from this only in degree.

  • The graph is never authored. Deleting the ref() from fct_orders deletes the edge. There is no second place to keep in sync.
  • Invalidation is transitive by construction. The sibling stg_customers is untouched by the edit not because a rule said so, but because its fingerprint does not include stg_orders.
  • The plan is a value. It can be printed, reviewed, diffed in CI, or refused. Everything Terraform's plan step buys you is available here for about fifteen lines.[11]

What this toy does not do is the part that consumes the remaining engineering effort in real systems: incremental materialisation, partition-aware backfill, concurrency, and understanding the SQL well enough to know whether a change is breaking. Those are the next two sections.

12 · The hard part

Incrementality is the whole game

A declarative pipeline that recomputes everything on every tick is trivially correct and economically absurd. Everything difficult about these systems is the attempt to be both correct and incremental — to produce the answer a full recomputation would have produced, while touching a small fraction of the data.

The strategies form a rough progression. A view defers everything to read time: zero maintenance cost, full recomputation per query. A table pays once per run for a full rebuild. An incremental model merges or appends a slice, which is cheap but shifts a correctness obligation onto the author: the predicate selecting "new" rows is hand-written, and it is wrong whenever data arrives late.[28][29] A materialised view or dynamic table moves that obligation to the engine, which computes the delta from change-tracking metadata. A streaming table handles append-only ingestion with exactly-once semantics. A continuously maintained incremental view — Materialize, RisingWave, Flink — keeps the answer live as a long-running dataflow.[63]

Two caveats travel with the whole curve.

The first is that incrementalisability is a property of the query, not of the tool. Snowflake documents that a dynamic table guarantees incremental refresh only where feasible, and silently reverts to a full refresh when it cannot determine how to compute the delta — for example when the query uses an unsupported expression.[58] The failure is a cost failure rather than a correctness failure, which makes it the kind that goes unnoticed until the bill arrives. The general advice that follows is unglamorous and correct: avoid non-deterministic functions and keep transformations deterministic, or you forfeit the optimisation you declared for.[55]

The second is that the theory here is genuinely hard. The incremental-view-maintenance literature has spent forty years on it, and nested and correlated subqueries remained difficult long after first-order delta rules were well understood; higher-order IVM, differential dataflow and DBSP each bought generality at the cost of additional maintained state.[62] When a vendor says a pipeline "just" refreshes incrementally, that word is doing an enormous amount of work.

Change data capture as a declaration

The clearest demonstration that a declarative surface can compress real complexity is change data capture. Maintaining a slowly changing dimension by hand means a MERGE statement that has to handle inserts, updates, deletes, out-of-order arrivals, tombstones for deleted keys, and the start/end timestamps that make history queryable. It is routinely a hundred and fifty lines and it is routinely wrong.[54]

The declarative form states the same thing as a set of properties:

CREATE FLOW customer_history AS AUTO CDC INTO dim_customer
FROM STREAM(cdc.customers)
KEYS (customer_id)
APPLY AS DELETE WHEN operation = 'DELETE'
SEQUENCE BY sequence_num
COLUMNS * EXCEPT (operation, sequence_num)
STORED AS SCD TYPE 2;

Each clause is a property, not a step. KEYS declares identity; SEQUENCE BY declares the logical ordering, which the runtime interprets as a monotonically increasing representation of correct order and uses to process events that arrive out of order.[52] STORED AS SCD TYPE 2 declares that history is retained, and the engine propagates sequencing values into __START_AT and __END_AT columns; deletes become tombstones that are retained temporarily for correctness under out-of-order arrival.[53] The documented constraints are as informative as the features: there must be exactly one distinct update per key at each sequencing value, null sequencing values are unsupported, and the source must be append-only or handled explicitly.[52][53]

Those constraints are the shape of the bargain. The engine will handle ordering, tombstones and history if — and only if — you can state your data's identity and ordering precisely. Most of the difficulty of adopting declarative CDC is discovering that you cannot.

13 · The frontier

Comprehension: from templating to parsing

There is a ceiling built into dbt's original design, and the last three years of tooling have been an assault on it. dbt Core does not understand the SQL it runs. Jinja is expanded into a string, the string is sent to the warehouse, and errors surface at runtime.[67] The graph is therefore a graph of models, not of columns, and the engine cannot answer the question that actually determines the cost of a change: which downstream values are now different?

SQLMesh, built by Tobiko Data from 2022, attacked this directly. It parses raw SQL with its companion transpiler SQLGlot, which yields compile-time validation and automatic column-level lineage, and it is state-aware rather than stateless.[64][66] The column-level lineage is not an observability feature; it is the input to change classification. SQLMesh uses it to distinguish breaking from non-breaking changes and therefore to decide which downstream models actually require rebuilding.[64][65]

Its second idea, virtual data environments, follows from the same foundation. In a conventional workflow each developer or CI run materialises a physical copy of the tables it touches, so compute and storage scale with the number of environments. Virtual environments instead create logical references to production data; only genuinely modified models are materialised, and promotion to production switches pointers rather than rebuilding tables.[64] Combined with a plan/apply workflow that previews the exact impact of a change before executing it, this is the Terraform pattern applied to data.[66]

dbt Labs arrived at the same conclusion from the other direction. It acquired SDF Labs in January 2025 for its SQL parsing technology and shipped the resulting dbt Fusion engine in May 2025 — a Rust rewrite with native SQL comprehension, providing type checking and column-level lineage ahead of runtime rather than discovering errors by executing against the warehouse.[72][73] Fusion was open-sourced under Apache 2.0 as part of dbt Core v2.0 in June 2026.[76][77]

Why this is the frontier and not a detail. Every capability in this article scales with how much the engine understands. A string-templating engine can infer the graph. A parsing engine can infer the columns, and therefore the blast radius of an edit, and therefore the minimum correct plan. Each increment of comprehension converts another human judgement into a derived fact.

14 · Contracts

Quality as a declaration

The last thing to migrate is the definition of correctness. In the imperative model, a data quality check is a task: run a query, compare a count, raise an alert. It lives downstream of the thing it validates, in a different file, often in a different repository, and its relationship to the pipeline is conventional rather than structural.

Declarative quality inverts this. In Lakeflow and Spark Declarative Pipelines, expectations are optional clauses inside the statement that creates the dataset. An expectation has a name, a boolean SQL predicate, and a violation policy.[50] The three policies map onto three different operational contracts:

With WARN — the default — invalid rows are still written to the target and the violation is recorded in metrics, so the team can track quality without halting the pipeline. With DROP ROW the offending records are discarded before the write. With FAIL UPDATE the update stops on the first invalid record.[50][51]

Two second-order effects make this more than syntactic sugar. The first is that pass/fail counts per constraint land in the pipeline event log automatically, because the engine — not the author — is running the check; quality dashboards become a query over that log rather than a separate instrumentation project.[51] The second is more interesting: expectations configured to fail modify the Spark query plan so as to track the information needed to identify which input record caused the violation, and the resulting error message names it directly.[50] That is only possible because the check was declared rather than executed as an opaque downstream task. Declaring a thing lets the planner do something with it.

The same pattern recurs across the ecosystem in different vocabularies: dbt's column tests compiled to zero-row queries; Dagster's asset checks, which can be composed into automation conditions so that a downstream asset refuses to run while an upstream check is failing.[37] The structural claim is identical in each: the invariant belongs beside the definition, not downstream of it.

15 · Costs

Where the abstraction leaks

A fair account has to be specific about failure modes, because the marketing is not. Declarative pipelines fail in patterned ways, and the patterns are predictable from first principles.

The escape hatch is imperative code in disguise

dbt's Jinja layer exists because SQL lacks variables, loops and abstraction, and it is what makes dbt usable at scale. It is also the thing that prevents the engine from reasoning about the model, and the criticism has been made bluntly from inside the ecosystem: because dbt does not know anything about its SQL and simply runs it, it is limited in how data-aware it can be.[67] A macro that emits different SQL depending on a variable is a program, and a program's output is not knowable without running it. Every declarative tool has this seam somewhere — custom materialisations, pre- and post-hooks, Python models, user-defined functions — and the seam is exactly where the guarantees stop.[68]

The configuration cliff

Declarative systems have an envelope. Inside it, work that used to take three hundred lines takes ten. At the edge, there is frequently no graceful degradation: the supported expression set does not cover your case, and there is no lower-level API to drop down to. The documented restrictions are honest about this — dynamic tables do not support stored procedures or external functions in their definitions and are unsuitable when you need data fresher than the minimum target lag or strictly guaranteed refresh timing.[55] The AUTO CDC APIs are not supported by open-source Spark Declarative Pipelines and require particular product tiers.[52] None of this is unreasonable; all of it is the kind of thing discovered in month four rather than week one.

Debugging by inference

When the plan is derived, a wrong plan is diagnosed by reconstructing the engine's reasoning. The stack trace points at generated SQL nobody wrote. This is the classic law of leaky abstractions: the abstraction saves you from the underlying complexity right up until it doesn't, and then you need to understand both the domain and the abstraction.[79] Practitioners running these systems in anger make the point in almost these words — the declarative premise is excellent and the operational complexity can be tricky.[49] Even the enthusiasts note that abstractions are leaky and can backfire, and that whether the declarative form is faster or slower than a hand-tuned imperative equivalent is an empirical question rather than a given.[78]

Determinism is assumed, not enforced

Every reuse decision rests on the premise that recomputation yields the same answer. A current_timestamp() in a model body, a source table that is mutated in place, a late-arriving row that lands behind an incremental watermark — each of these silently violates the premise, and the engine has no way to notice. This is why the functional discipline predates and underwrites the declarative one: immutable partitions and versioned logic are what make the planner's decisions sound.[21][22]

YAML is not automatically an improvement

The move from Python to configuration is not costless, and the practitioner joke about becoming a "YAML engineer" is pointed at something real.[71] Configuration formats lose the abstraction mechanisms of a programming language: there is no function, no type, no test in the ordinary sense. Large declarative projects reinvent these badly — through templating, through generation, through convention — and the result can be harder to reason about than the code it replaced. The tools that handle this well provide a real escape into a general-purpose language for the cases that need it, and accept that the escape costs them analysability.[71]

Coupling

A declaration is portable only if its semantics are standardised, and most of these semantics are not. TARGET_LAG, expectation violation policies, automation conditions and CDC clauses are all vendor-specific. Even the Spark donation, which is genuine, produces code that runs on vanilla Spark only with effort and at the cost of the managed runtime's features.[48] The practical framing from teams making the choice is that a platform-native declarative runtime is a strong choice if you are already committed to that platform, and a portable transformation framework is the safer bet if you are not.[84]

16 · Landscape

The landscape, mid-2026

The tooling has consolidated sharply. Fivetran acquired Census in May 2025 and Tobiko Data — the company behind SQLMesh and SQLGlot — in September 2025, then announced an all-stock merger with dbt Labs in October 2025 which completed on 1 June 2026.[74][75][82] George Fraser leads the combined company, with Tristan Handy as president.[75] The obvious question — why buy dbt when you already own a dbt competitor — has an obvious answer, and the community read is that SQLMesh was bought for the technology and dbt for the installed base.[87] dbt Core v2.0, shipping the open-sourced Fusion engine, landed the same day the merger closed.[76][77] Users are right to watch how the open-source cores are maintained now that a single vendor owns three of the four major transformation frameworks.[82]

17 · Practice

What to declare, and what to keep

The useful question is not whether to adopt a declarative tool but which of the six decisions from §2 to hand over, in what order, and under what preconditions. A defensible sequence, and the reasoning behind it:

  1. Declare the graph first, always. Hand-maintained edge lists rot; derived ones cannot. This is the highest-value, lowest-risk transfer, and it is available in every tool discussed here. If your dependency edges are typed by a human, fix that before anything else.
  2. Earn idempotency before you declare anything about scope. An engine's right to skip work is only as sound as your guarantee that recomputation is safe. Full partition overwrites, immutable raw storage and versioned logic are the preconditions.[21][24] Adopting incremental materialisation on top of a non-deterministic pipeline buys a faster route to wrong answers.
  3. Declare freshness rather than schedules where the platform supports it. A cron expression encodes a guess about upstream timing; a lag target or an eager automation condition encodes the actual requirement, and lets the engine do nothing when nothing has changed.[34][56] Keep cron for genuinely calendar-bound obligations — a regulatory file that must be sent at 09:00 — where the clock is the requirement.
  4. Declare invariants next to definitions, not downstream. The cost is a few lines of YAML or a constraint clause; the benefit is that violation counts become engine-recorded facts and that downstream execution can be gated on them.[37][51]
  5. Treat materialisation as a tuning knob, not an architecture. Start with tables and views. Move to incremental or engine-maintained strategies when a specific model's cost or latency justifies it, and re-check that the query is still incrementalisable.[58] The whole point of separating logic from materialisation is that this decision stays reversible.
  6. Keep the escape hatch, and keep it small. The pipelines that age worst are not the ones with imperative code in them; they are the ones where imperative code has leaked into every model as a macro that quietly changes what the SQL means. Confine generality to explicit places and accept that the engine's guarantees stop there.[71]

There is also a claim worth resisting. The strong version of the declarative argument — that the orchestrator disappears, that pipelines become pure specification, that data engineering collapses into schema design — is not what the evidence shows. Airflow kept its task model alongside assets deliberately.[38] Prefect built a business on the premise that removing boilerplate from ordinary Python beats replacing Python with configuration.[83] Dagster's asset bodies are imperative functions. Even the most fully engine-native systems reserve a Python interface for the cases their SQL surface cannot express.[52] The realistic end state is not a declarative field; it is a field with a much larger declarative core and a much smaller, better-marked imperative perimeter.

The underrated argument

Ergonomics is the usual case made for declarative pipelines, and it is the weakest one. The stronger case is epistemic. A declared pipeline is a description that can be read without being executed — by a planner deciding what to rebuild, by a catalog resolving lineage, by a CI job classifying a change as breaking, by a reviewer evaluating a diff, and now by agents that need pipeline definitions they can read, edit, validate and trace.[88]

Airbyte's observation about its connector manifests captures the whole thesis in miniature: because the connector is a declaration, you do not need to inspect any code to determine which pagination strategy it uses — it is stated explicitly.[70] That is a small fact with a large shadow. An imperative pipeline's properties can only be discovered by running it and watching. A declarative pipeline's properties can be looked up. Fifty years after Codd proposed data independence and Feldman wrote down a dependency graph, that remains the whole argument.[4][8]
