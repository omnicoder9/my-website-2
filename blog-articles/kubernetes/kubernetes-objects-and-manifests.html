section/intro

1. The question behind the outline

The textbook picture of a Kubernetes object has one writer. You describe what you want in a manifest, the API server stores it, and controllers work until the world matches. The documentation's own phrase for an object is a record of intent: once you create it, the system works to ensure it exists, and the object tells the cluster what you want your workload to look like1. Four fields carry that intent (apiVersion, kind, metadata and spec) and a fifth, status, reports how far the cluster has got1,2.

That picture is correct and incomplete. Take one Deployment in a production cluster and list who writes to it. The author writes the file. kubectl fills in a namespace the file left out and stores a copy of what it sent in an annotation. The API server assigns a UID, a resourceVersion, a generation and a creation time, fills in about a dozen defaults, and records which manager touched which field. Admission webhooks may add or change fields before the object is stored. The Deployment controller writes status and a revision annotation; the HorizontalPodAutoscaler rewrites spec.replicas through the scale subresource; the garbage collector and a list of finalizers decide when, if ever, the object goes away3,4,5,6. Listing 2 below shows the result: of the fields visible on the live object, the author wrote a minority.

So the object is not a document the author owns and the cluster executes. It is a shared document with an author and several other writers who never coordinate directly, and most of what is difficult about objects and manifests (the three-way merge, server-side apply, the difference between labels and annotations, stuck namespaces, the Norway problem) is a question about which of them decides a given value. This article takes the outline it was given (the object model, YAML and declarative configuration, labels, selectors and annotations, and namespaces) and asks of every item on it: whose field is it?

The design history supports reading it this way. Omega, Google's second cluster manager, replaced a monolithic scheduler with shared state and optimistic concurrency control, so that independent components could write the same cell state and resolve conflicts at commit time7. Kubernetes kept the idea and made the API server the single place where that shared state lives; its designers list be careful with ownership among the lessons Borg taught them8,9.

The writer ladder

Each of the 38 items in the outline becomes a plate, and each plate is placed on a six-rung ladder by one rule: the rung is the writer whose output decides the item's effective value in normal operation, whatever other writers may also touch it. The rungs follow the path a write takes (Figure 1).

Rung is not enough on its own, because two items can be decided by the same writer and behave very differently when someone else disagrees. So each plate also carries a conflict rule, the mechanism that settles a disagreement between writers: none (one writer only), immutable (the second writer is refused), separated (writers cannot reach each other's part), version-checked (a stale write is refused), field-managed (server-side apply names the owner and reports a conflict), last-write-wins (the later writer silently replaces the earlier) and negotiated (every party must consent, as with finalizers).

Every plate has the same four fields (who writes it, who reads it, how it is contested, and what failure looks like) and a small gauge, the object silhouette: a miniature of a live object's keys with the rows the plate concerns lit in its rung's colour, a six-cell strip underneath marking the deciding writer (filled) and the others who also write (outlined), and the conflict rule. The silhouette is the same on every plate so that plates can be compared at a glance: where the lit rows sit says which part of the object is at stake, and the strip says who is holding it.

The behaviour described is that of Kubernetes v1.37, released on 26 August 2026, whose first patch release, 1.37.1, followed on 23 September 202610,11. Numbers in the text come from a runnable standard-library Python lab of nine deterministic experiments (seed 20260925), executed when this page was built; its source and full output are in the lab section, and nothing in the prose is quoted from anywhere else. The lab reaches one conclusion worth stating before the details. Silent overwriting lives at the client. Of the 9 items decided by kubectl or another client tool, 6 resolve disagreement by last-write-wins; of the 6 items decided by the API server, 6 resolve it by structure, through immutability, separation or a version check. Much of the project's work on objects and manifests over the last five years (server-side apply, ApplySet, KYAML, declarative validation) has been either moving a decision from the client rung to the server or removing a choice the client used to make silently.

2. The object model

Listing 1 is a manifest for a small Deployment. It states the minimum: identity, labels, a selector, a Pod template. It deliberately omits spec.replicas, because a HorizontalPodAutoscaler owns that field, and the autoscaling documentation says as much12.

Listing 2 is the same object read back from the API server. The comments name the writer of each field. Several blocks the author never wrote are now present: identity and concurrency fields in metadata, defaults in spec, a status block and a managedFields list that records which manager last set which field13,14.

Identity: apiVersion, kind, name, namespace, uid

An object is identified by its group, version and kind, which name its schema, and by its name and namespace, which name the instance1,2,15. Names are unique per kind within a namespace; a UID, assigned by the server, distinguishes objects that have held the same name at different times16. Different kinds accept different name grammars. Most take a DNS subdomain of up to 253 characters, some a DNS label of up to 63 as defined in RFC 1123, and Services an RFC 1035 label, which must begin with a letter16,17,18. The lab's fifth experiment runs one set of candidate strings through five of these grammars (Table 2).

apiVersion looks like the author's choice and mostly is, but its effect is the server's. The server can serve an object at several versions while storing it at one, converting on every read and write, so two clients speaking different versions each see a projection of the same stored object3,19. That is separation rather than contest, and it is why the plate for apiVersion sits on the server's rung. Versions are retired under a published deprecation policy20, and since v1.37 the storage version migrator runs by default, so objects written at an old storage version are rewritten rather than left for a future upgrade to trip over10,21.

Desired and observed: spec and status

spec states desired state; status reports observed state, and controllers reconcile the one toward the other1,5. The API conventions add two pieces of bookkeeping that make the loop observable: metadata.generation increases whenever spec changes, and a controller records the generation it has acted on in status.observedGeneration2. When they are equal, status describes the spec you last wrote; when they differ, status is news about an older intent.

The status subresource turns this division into an ownership boundary. With it enabled, a write to the main resource ignores changes to status, and a write to /status ignores changes to anything else2,22. No other boundary in the object model is as clean. An author cannot write status even by accident; a controller updating status cannot disturb the author's spec. Figure 2 colours every field of a live Deployment by the writer that decides it.

Bookkeeping: resourceVersion, managedFields, generation

resourceVersion is an opaque string that changes whenever the object changes. Clients must treat it as a token, not a number to compare, and pass it back on update so that the server can refuse a write based on a version that is no longer current2,3. It is the mechanism behind the version-checked conflict rule, and the lab measures what it prevents in the section on concurrency. managedFields is the server-side apply record: a list of managers, each with the set of fields it owns, the operation it used and the API version it spoke14.

Relationships: ownerReferences and finalizers

Two metadata fields exist so that objects can outlive, or not outlive, one another. ownerReferences point from a dependent to its owners; the garbage collector deletes dependents whose owners are gone, and a controller marks the one owner that manages it with controller: true6,24. The reference has a UID but no namespace field, and that single omission is what forbids cross-namespace ownership: a namespaced owner is assumed to be in the dependent's own namespace, and if it is not found there the reference counts as absent24. finalizers are keys that must all be removed before the object can be deleted; a delete request on an object with finalizers sets metadata.deletionTimestamp and returns, and the object stays visible until the last finalizer is cleared by whichever controller owns it25,26.

Of the eleven object-model plates, the author decides four: spec, kind, name and the labels map. Two of those four are immutable once created. The server decides metadata and apiVersion, controllers decide status and ownership, and the lifecycle machinery decides finalizers. The namespace plate is the odd one: the author can decide it, but when a manifest leaves it out the value comes from the request, which kubectl takes from its --namespace flag or from the current context27,28, so the item is coded to the client. Listing 1 states its namespace for exactly that reason.

3. YAML and declarative configuration

The object model says what a Kubernetes object is. This part of the outline is about how a person's intent reaches one: the text format, the file, the command and the merge.

YAML is a front end, and its parser is a writer

The API's objects are JSON-shaped trees3,33. YAML is the format people write them in, and the configuration guidance recommends it over JSON for files people edit34. The library Kubernetes uses to read manifests converts YAML to JSON and then decodes the JSON into Go types35, which makes the YAML parser a writer in its own right: it decides the type of every unquoted scalar before any Kubernetes code sees the value.

How it decides depends on which YAML. The YAML 1.1 type repository resolves y, yes, on, NO and off to booleans, numbers with a leading zero to octal, numbers separated by colons to base 60, and dates to timestamps36,37,38,39. YAML 1.2's core schema dropped most of that: booleans are only true and false in three capitalisations, a leading zero no longer means octal, and colon-separated numbers are strings40. The lab's fourth experiment implements both resolvers from the specifications and runs 38 scalars of the kind that appear in manifests through them (Figure 3). Under YAML 1.1, 29 of them resolve to something other than a string; under the 1.2 core schema, 22; the two schemas disagree on 15. The disagreement is not academic, because a label value, an annotation value and an environment variable's value must all be strings, and a boolean or a number in any of them is refused when the JSON is decoded.

Some hazards survive the move to 1.2 entirely. 1.10 is a float under both schemas, so a version number written without quotes arrives as 1.1, and 0755 is a number under both, just a different one: 493 under 1.1 and 755 under 1.2. The general case has a name. The Norway problem is that a country code of NO, unquoted, is a boolean under YAML 1.1 typing41, and the Kubernetes project cites it by name as a reason for KYAML42.

KYAML, proposed in KEP-5295, is a strict subset of YAML that any YAML parser can read. It double-quotes every string value, uses braces and brackets for every mapping and list so that structure does not depend on indentation, and keeps comments and trailing commas, which JSON forbids42,43. kubectl gained -o kyaml as an alpha output format in v1.34 and turned it on by default as beta in v1.35; the project has said it has no plans to make KYAML the default output, and kubectl's kuberc preferences file can set it per user42,44,45. Seen from the ladder, KYAML does not move the parse to another writer. It removes the parser's discretion, which is the other way to take a silent decision away from the client.

Manifests, files and multi-document YAML

A manifest is a file of object specifications46. Several can share a file, separated by a line of three hyphens, and kubectl creates them in the order they appear47. The file is never sent anywhere as a unit: each document becomes its own request, so the order of documents is a dependency order that only the client knows about, and a failure halfway through leaves half an apply. Listing 5 puts the Namespace first, then its quota, then the Service and the Deployment. The documentation's own advice is to put a Service before the workloads it selects, so that the scheduler can spread their Pods47.

Three techniques, three owners of the truth

The documentation distinguishes three ways of managing objects and warns against mixing them on one object46. Imperative commands act on live objects directly and leave nothing behind but the change48. Imperative object configuration (kubectl create, replace and delete with -f) treats the file as the whole truth, and the object-management page is explicit about the cost: changes made to live objects by anything else must be copied into the file or they are lost at the next replace46,49. Declarative object configuration (kubectl apply) treats the file as one writer among several, preserving what other writers set on fields the file does not mention50.

The difference between replace and apply is a difference in what the command assumes about other writers. The lab's first experiment makes it exact by enumerating every history of a single field (Figure 4). Three facts describe a field at apply time: whether it was in the previously applied file (P), whether it is in the new one (N), and whether another writer has since set it to something else (O). That gives eight histories, and each strategy has a fixed outcome for each. Replace clobbers the other writer's value in all 4 histories where one exists. Client-side apply clobbers it in 3 (whenever the file states the field, or used to) and keeps it in one. Server-side apply clobbers nothing: where the file states a field someone else holds it reports a conflict, 2 histories, and where the file has dropped it the other writer keeps it.

The fleet half of the experiment gives the same result a rate. Four hundred 20-field objects, each applied 50 times while other writers touch each field with probability 5% between applies, produce 1,008.4 silent overwrites per thousand applies under replace, 584.1 under client-side apply, and none under server-side apply, which surfaces 554.6 conflicts instead. One more column matters in practice. When the last-applied annotation is missing (an object made with kubectl create and no --save-config, for instance), client-side apply cannot know what it used to own and never removes a field that has left the file: 527.0 such leaks per thousand applies.

The last-applied record and server-side apply

Client-side apply's three-way merge compares the new file, the live object and the kubectl.kubernetes.io/last-applied-configuration annotation. A field in the file is set; a field in the annotation but no longer in the file is deleted; a field in neither is left alone50. The annotation is the client's memory of what it owns, kept inside the object it describes and rewritten on every apply. It knows nothing about edits made any other way, and it counts against the 256 KiB limit on an object's total annotation size32.

Server-side apply moves that memory to the server. Each apply names a field manager, the server records the fields that manager owns in managedFields, and an apply that tries to set a field another manager owns, to a different value, fails with a conflict unless the caller forces it14,52. Two managers applying the same value share ownership. The feature reached general availability in v1.2253. Listing 7 is what the author of Listing 1 would see had they put replicas back in the file after the autoscaler had taken it over. The server-side apply documentation describes exactly this hand-over, and advises removing the field from the configuration so that the autoscaler owns it alone12,14.

Server-side apply is still not kubectl's default. KEP-3805, opened in 2023, proposes making it so, and gives the reason it has not happened: server-side apply is not fully backwards compatible with client-side behaviour, and breaking every user of kubectl apply has a cost54. GitOps controllers did not wait. Argo CD offers server-side apply as a sync option and Flux's kustomize-controller applies server-side55,56, which suits the OpenGitOps principle that the desired state is continuously reconciled rather than applied once57. The practical advice from the project is blunt: server-side apply is the better apply, and you should be using it58.

Concurrency: what resourceVersion prevents

Every update to an object is a read, a modification and a write, and between the read and the write another writer may have committed. Kubernetes handles this with optimistic concurrency in the manner Kung and Robinson described: no locks, a check at commit time59. An update carries the resourceVersion it was based on; if the object has moved on, the server refuses it with 409 Conflict and the client re-reads and retries2,3,60. The guarantee comes from etcd, whose revisions give each key a version to compare-and-swap against61.

The failure it prevents is the lost update62. In the lab's second experiment, writers each increment a counter on the same object 50 times with randomly interleaved reads and writes (Figure 5). Blind writes lose 36.0% of increments with two writers and 87.6% with sixteen. With the precondition nothing is lost, and the price is paid in retries: 0.40 refused writes per committed write with two writers, 2.60 with sixteen. The price rises with contention, which is the argument for giving each writer its own fields rather than asking many writers to take turns at one.

Patches: how a partial write addresses a list

Not every write sends the whole object. kubectl patch supports three encodings, and they differ precisely in how they treat lists63. A JSON merge patch replaces any list it mentions wholesale64. A JSON patch addresses list elements by position65. A strategic merge patch merges list elements by a declared key (for containers, the name), and it is not available for custom resources, which have no such declarations63.

The lab's third experiment races an author's image bump against three edits another writer might make to the same containers list (appending a sidecar, prepending one, removing a container), under five encodings and in both orders (Figure 6). A full replace and a JSON merge patch lose one writer's intent in all six races. An unguarded JSON patch succeeds five times and, in the sixth, writes the author's image into the wrong container, because the index it was computed against has moved; adding a test operation turns that corruption into a refusal. The strategic merge patch keeps both intents in all six, because it names the element instead of pointing at its position.

Create, replace, delete, and what apply leaves behind

kubectl create proposes an object and the server assigns its identity; a second create of the same name is refused66. kubectl replace sends a whole object and overwrites every field in it51. kubectl delete starts a deletion that the garbage collector and finalizers finish, in background, foreground or orphan mode6,67. None of these knows about an object that has disappeared from a directory of manifests; that is what apply's --prune flag tries to handle, and ApplySet, introduced in v1.27, is its redesign, recording set membership on a parent object rather than inferring it from a label selector the user supplies68,69. Before any of them, kubectl diff shows what the server would store, using server-side dry-run so that defaulting and admission run without persisting anything3,70. Tools that layer on top of these verbs, Kustomize (built into kubectl since v1.14) among them, change what the file contains but not who writes the live object71,72.

4. Labels, selectors and annotations

Borg identified tasks by job name and index. Kubernetes replaced that with arbitrary key/value labels and selectors over them, and its designers count don't just number containers: give them labels among the lessons they took from Borg8. Labels are identifying metadata intended for selection; annotations are non-identifying metadata that tools and people attach for their own use29,31. The distinction is about who reads the value: a label is read by other objects' selectors, an annotation by whoever wrote it.

Syntax: one string, five grammars

A label key has an optional prefix, which must be a DNS subdomain followed by a slash, and a name of at most 63 characters that begins and ends with an alphanumeric and may contain dashes, underscores and dots between. A value has the same shape, with the same 63-character limit, and may be empty. The kubernetes.io/ and k8s.io/ prefixes are reserved for Kubernetes core components29. These grammars are close to the name grammars of the object model but not the same, and the lab's fifth experiment shows how far apart they are (Table 2): of 18 candidate strings, 4 are valid as a namespace name, an object name, a Service name, a label key and a label value; 3 are valid as none of them.

Recommended labels

The recommended labels share the app.kubernetes.io prefix: name, instance, version, component, part-of and managed-by74. They are a vocabulary, not a mechanism. Nothing requires them, and managed-by in particular is a claim that nothing checks. Helm's conventions fill several of them for every chart it installs75. The one that matters most for correctness is instance, as the selector experiment below shows.

Selectors: equality-based and set-based

An equality-based requirement tests a key with =, == or !=; a set-based requirement uses in, notin, or a bare key or !key for existence29. Requirements are joined by commas, which mean AND; there is no OR. The forms appear in two places with different expressive power. Services and ReplicationControllers take a plain map, which can express only equality; the newer workload resources take a LabelSelector with matchLabels and matchExpressions, the two ANDed together29,76,77. Field selectors, which filter on fields such as status.phase, are a separate and much narrower mechanism78.

The lab's sixth experiment implements the string grammar and a matcher, and checks them against the cases in Table 3. The cases worth noticing are the negative ones. tier!=db matches an object that has no tier label at all, and env notin (prod) matches an object with no labels, because a negative requirement is satisfied by absence. That is correct by the documented semantics and a common source of selectors that match more than their author meant29.

A selector's author decides what it says, but controllers decide what it matches, continuously, and act on the result. A ReplicaSet acquires any Pod that matches its selector and has no controller owner, including a Pod it did not create79. The Deployment documentation warns against selectors that overlap other controllers', because the controllers will then fight over the same Pods, and makes a Deployment's selector immutable in apps/v123. The second half of the experiment asks how often overlap happens under three labelling schemes (Figure 7). It fills 2,000 namespaces with 12 workloads each, drawn with Zipf-like popularity from a catalogue of 30 applications, so that the same application is sometimes installed twice in a namespace, as happens with two releases of one chart. Labelled by app alone, 99.5% of namespaces contain at least one pair of workloads whose selectors overlap. Adding a tier label reduces this to 87.8%. Using the recommended name and instance pair reduces it to 0.0%, because instance is unique by construction. The recommended labels are usually argued for on grounds of consistency across tools; this is a correctness argument.

Annotations and organisational metadata

Annotations may be large and structured, and they are where tools keep state that has no place in the schema: the Deployment controller's revision number, kubectl's last-applied record, a restart timestamp, a checksum of a mounted configuration30,31. The documentation also recommends them for things people need: build and release information, pointers to logs and dashboards, the team to call31,80. Their combined size per object is capped at 256 KiB32. The coding places the annotations field on the client's rung, because kubectl and other tools write most of its keys, and places annotations as a practice on the controller's rung, because the keys that do work are controllers' bookkeeping.

Organisational metadata (team, cost centre, data classification) is the case where the ladder is least kind to intentions. Written by authors, it is optional and therefore missing; nothing contests it and nothing requires it. The fix is to move the decision down the ladder, to admission. A ValidatingAdmissionPolicy, generally available since v1.30, evaluates a CEL expression on every write and can refuse a Deployment without a team label4,81; webhooks can do the same with arbitrary code82. v1.36 added admission policies loaded from files on the control plane, which API clients cannot delete83,84, and made declarative validation of built-in types generally available85.

5. Namespaces

A namespace is a scope for names. Names must be unique within a namespace but not across namespaces, and a namespace is also the unit to which quota, limit ranges, role bindings and Pod Security settings attach27,86,87,88,89. The docs suggest namespaces for clusters shared by many users across several teams and say that clusters with a few users need not use them at all27.

What namespaces separate, and what they do not

The four initial namespaces are default, kube-node-lease, kube-public and kube-system, and the docs ask you not to create your own with a kube- prefix27. The NamespaceLifecycle admission plugin refuses to delete default, kube-system and kube-public, and refuses to create objects in a namespace that is being deleted4. Since v1.22 the control plane sets an immutable kubernetes.io/metadata.name label on every namespace, equal to its name, so that selectors can pick namespaces by name without trusting a label a person wrote30.

Not every resource lives in a namespace. Nodes, PersistentVolumes, StorageClasses, ClusterRoles, CustomResourceDefinitions and Namespaces themselves are cluster-scoped, with one name space for the whole cluster; kubectl api-resources --namespaced=false lists them27. RBAC mirrors the split: a Role grants within one namespace, a ClusterRole across all of them or over cluster-scoped kinds88. For a shared cluster the cluster-scoped kinds are where naming collisions happen, since no namespace can disambiguate two teams' CRDs of the same name90.

Namespaces are not a network boundary. Every Pod can reach every Service until a NetworkPolicy selects it, and the policy is enforced by the network plugin, not by the API server91. The Kubernetes hardening guidance from the NSA and CISA, and the project's own multi-tenancy guide, both treat the namespace as the building block of isolation and list what must be added to it: RBAC, quota, network policy, Pod Security90,92,93.

Cross-namespace names

Service discovery follows the namespace. A Service gets a DNS name of the form service.namespace.svc.cluster.local, and a Pod's resolver is configured with a search list that begins with its own namespace, so a bare name finds a Service only in the same namespace94,95. The list is applied by the ordinary resolver rules: a name with fewer dots than ndots is tried against every search domain before it is tried as written96, and Kubernetes sets ndots to 594.

The lab's eighth experiment implements those rules and counts the queries each form of a name costs from a Pod in namespace web, assuming the usual A and AAAA pair per attempt (Figure 8). A Service in the same namespace resolves in 2 queries. db.data resolves in 4. Written out as db.data.svc.cluster.local without a trailing dot, it takes 8, because four dots are fewer than five and the search list goes first; with the trailing dot it takes 2. An external name such as api.example.com costs 8 with three search domains and 10 when the node adds a fourth. The bare name db, from the wrong namespace, costs 8 queries and fails, which is the most common cross-namespace mistake of all.

Deletion

Deleting a namespace deletes everything in it. The namespace enters the Terminating phase, the namespace controller deletes its contents, and the namespace itself carries a finalizer in spec.finalizers that is removed only when the contents are gone27,97. Every finalizer on every object inside therefore has to be cleared, by its own controller, before the namespace can go. If a controller has been uninstalled while its finalizers remain, or an aggregated API that serves some of the namespace's resources is unavailable so that its contents cannot even be listed, the namespace stays Terminating, and its status conditions say which25,97.

The lab's seventh experiment gives the arithmetic of that negotiation (Figure 9). If each finalizer-bearing object has an independent chance q that its controller is gone, a namespace with k of them is stuck with probability 1 − (1 − q)^k. At q = 5%, 14 such objects give even odds of a stuck namespace, and 20 give 64.15%; at q = 1%, it takes 69. The simulation agrees with the formula to within sampling noise. The lesson is not that finalizers are dangerous but that deletion is a vote with as many voters as there are finalizers, and a namespace full of an operator's resources gives that operator a veto.

Conventions

Namespaces are a flat list, and conventions fill in what the API does not provide: one namespace per team, per application, or per environment; labels that say who owns a namespace; Pod Security levels set by label89,98,99. Hierarchical namespaces were proposed to let policy flow from a parent to its children100, but the core API has no hierarchy. The conventions that hold are the ones something enforces. A Pod Security label is read by admission on every Pod; a team label is read by nobody unless a policy requires it.

6. What the census shows

Figure 10 places all 38 plates on the grid of deciding writer against conflict rule. Six observations follow from the counts.

The author decides less than a third of the outline. 12 of the 38 items are decided at the author's rung, and 8 of those 12 are either immutable once created (kind, name, the two selector forms) or uncontested because they live in the file (the manifest, the resource configuration, organisation and naming conventions). What the author writes that other writers can change is short: spec, the labels map, labels as practice, and whatever replace sends.

Silent overwriting lives at the client. 6 of the 10 items resolved by last-write-wins are decided by kubectl or another client tool, and 6 of the 9 client-decided items are resolved that way. The client rung is where the object model has the least structure, because the client acts once, holds no durable state except what it writes into the object, and cannot see what other writers intend.

The server resolves by structure. All 6 server-decided items are settled by immutability, separation or a version check. None is last-write-wins. The API server's job, seen this way, is not to store objects but to partition them, so that writers who never coordinate cannot corrupt one another.

Half the outline is contested. 19 of 38 items (50.0%) have a conflict rule under which two writers can actually disagree: last-write-wins, version-checked, field-managed or negotiated. The other half are immutable, separated or single-writer.

Namespaces are decided furthest from the author. The mean rung is 1.74 overall; by family it is 1.73 for the object model, 1.42 for YAML and declarative configuration, 1.71 for labels and selectors, and 2.25 for namespaces. Namespaces feel like the simplest part of the outline and are the part a manifest's author controls least.

The two axes are needed together. Deciding writer and conflict rule together separate 94.5% of the 703 pairs of plates; the writer alone separates 80.7%, and the outline's own four families 75.8%. 18 of the 42 cells are occupied.

Read against the release history, the counts describe a direction of travel. Server-side apply, generally available in v1.22, moved the record of who owns a field from an annotation the client rewrites to a list the server maintains14,53. ApplySet, in v1.27, moved prune bookkeeping from label heuristics to an explicit parent object69. KYAML, from v1.34, removes the parser's discretion rather than moving it43. Declarative validation, generally available in v1.36, moves validation rules for built-in types into declarations the server enforces uniformly85. Each step either takes a decision away from the client rung or removes a choice the client used to make silently. The step that has not happened, making server-side apply kubectl's default, is the one that would move the most items at once54.

The coding has limits worth stating. The deciding writer is a judgement about normal operation, and several items could be argued one rung either way: labels as a field (author or controller), apiVersion (author or server), cross-namespace communication (network plugin, or nobody). Each is coded by the rule in the introduction, and the ledger records the coding so that anyone can recount. The conclusions depend on the pattern (client items overwhelmingly last-write-wins, server items entirely structural), and moving any single disputed item does not change it.

section/rules

7. Working rules

The census suggests a short set of habits. Each is a way of making sure a field has one writer, or that disagreement is reported rather than silent.

State only what you mean to own. Leave replicas out when an autoscaler runs, leave defaults out unless you mean to pin them, and leave out anything a controller or webhook maintains12,34. Under server-side apply every stated field is a claim14.

Prefer server-side apply, with a named field manager per pipeline. A conflict is information; a silent overwrite is a later incident14,58. Pick one technique per object and do not mix apply with create and replace46.

Quote every string that could be read as something else. Or write KYAML, or generate manifests with a tool that quotes for you42. Version numbers, file modes, country codes and anything that says yes or no are the usual suspects (Figure 3).

State the namespace in the file. A manifest without one belongs to whoever runs it27.

Select with name and instance. The recommended pair is what makes two installs of one application distinguishable to a selector74; a selector that is immutable once created should be right the first time23.

Enforce organisational metadata at admission. A label that nothing requires will be missing81.

Use patches that name what they change. Strategic merge for built-in lists, test operations to guard JSON patches, and server-side apply for custom resources, where strategic merge is not available63.

Treat every finalizer as a voter on deletion. Uninstall operators only after their resources are gone, and read a stuck namespace's conditions before removing anything by hand25,97.

def outcome(strategy, P, N, O, annotation=True):
    """P: field was in the previously applied config; N: field is in the new config;
    O: another writer has since set the field to a different value."""
    if strategy == "replace":
        if O: return "CLOBBER"

    if strategy == "ssa":
        if N: return "CONFLICT" if O else "SET"
        if P: return "KEEP" if O else "REMOVE"

def apply_patch(state, patch):
    kind, body = patch
    s = copy.deepcopy(state)
    if kind in ("put", "merge"): return copy.deepcopy(body), None
    if kind == "smp":
        for op, c, pos in body:
            names = [x["name"] for x in s]
            if op == "upsert":
                if c["name"] in names: s[names.index(c["name"])] = dict(c)
                else: s.insert(pos if pos is not None else len(s), dict(c))
            else:
                s = [x for x in s if x["name"] != c]
        return s, None
    for op, i, v in body:                                     # jsonpatch
        if op == "test":
            if i >= len(s) or s[i]["name"] != v: return state, "FAIL"
        elif op == "replace_image":
            if i >= len(s): return state, "FAIL"
            s[i]["image"] = v
        elif op == "remove":
            if i >= len(s): return state, "FAIL"
            s.pop(i)
        elif op == "add":
            if i == "-": s.append(dict(v))
            elif i > len(s): return state, "FAIL"
            else: s.insert(i, dict(v))
    return s, None

def parse_selector(s):
    reqs = []
    for part in re.findall(r"[^,(]+(?:\([^)]*\))?", s):
        part = part.strip()
        if not part: continue
        m = re.fullmatch(r"(\S+)\s+(in|notin)\s+\(([^)]*)\)", part)
        if m:
            reqs.append((m.group(1), m.group(2), {v.strip() for v in m.group(3).split(",")})); continue
        m = re.fullmatch(r"(\S+?)\s*(==|!=|=)\s*(\S*)", part)
        if m:
            op = {"=": "eq", "==": "eq", "!=": "ne"}[m.group(2)]
            reqs.append((m.group(1), op, {m.group(3)})); continue
        if part.startswith("!"): reqs.append((part[1:], "doesnotexist", set())); continue
        reqs.append((part, "exists", set()))
    return reqs
def matches(reqs, labels):
    for k, op, vals in reqs:
        has = k in labels
        if op == "eq" and not (has and labels[k] in vals): return False
        if op == "ne" and has and labels[k] in vals: return False
        if op == "in" and not (has and labels[k] in vals): return False
        if op == "notin" and has and labels[k] in vals: return False
        if op == "exists" and not has: return False
        if op == "doesnotexist" and has: return False
    return True
