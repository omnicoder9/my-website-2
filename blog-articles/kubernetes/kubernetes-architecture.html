1The question

A Kubernetes cluster is usually drawn as a control plane on top and a fleet of nodes underneath, with arrows running up and down between them. The drawing invites a simple reading: the top is the brain, the bottom is the body, and if the brain stops, so does everything else. This article describes the architecture component by component, as the outline requires, but it carries one question through every section so that the description adds up to something: what keeps running when the control plane stops?

The question is not academic. Kubernetes was designed as a set of independent control loops that meet only at the API server, each driving some part of the world toward a declared state1,2. Nodes never receive commands from the control plane in the imperative sense; they watch for desired state and report status3. A design like that should degrade in a particular way when its hub disappears, and each component's behaviour during that interval tells you what the component actually depends on. Engineers at Amazon call the property static stability: a system whose data plane keeps doing what it was last told, without the control plane, is statically stable4.

The short answer, developed in the census of section 8, is that nearly everything in the data plane holds. Containers keep running, Service rules stay programmed, cluster DNS keeps answering, and load balancers keep forwarding. What fails is change: no new pods, no rescheduling, no scaling, no configuration. The longer answer is more interesting. The places where the architecture is fragile are not where it stops but where it starts again: thousands of clients relisting at once, a node lifecycle controller that finds every node stale, admission webhooks that cannot be reached because the pods serving them were never scheduled, and a restored etcd whose history is older than every cache in the cluster. Failures that feed on their own recovery load are what the systems literature calls metastable5,6, and the way back is where Kubernetes shows that shape.

Two devices carry the argument. Each component, API mechanism and etcd mechanism gets a numbered plate (A01 to E07) with the same four fields: what it depends on, what copy of state it holds, what it does when the API server goes, and what happens on the way back. Each plate carries a holdover bar, a small gauge that places the element on a six-rung ladder, from H0 (its loss stalls the cluster) to H5 (it needs nothing from the control plane), with a chip for its return behaviour. A stdlib Python lab, run at build time, supplies every measured number in the text; its source and verbatim output are in section 12.

2Cluster architecture

A Kubernetes cluster consists of a control plane and a set of worker machines called nodes; every cluster needs at least one worker node to run Pods7,8. The control plane makes global decisions, such as scheduling, and detects and responds to cluster events. The nodes host the Pods that make up the application workload. In production the control plane usually runs across several machines and the cluster runs many nodes, which is what gives it fault tolerance8.

The architectural decision that shapes everything else is that the API server is the only component that talks to the store. Schedulers, controllers, kubelets and proxies are all clients of the API server; they read desired state through watches and write back status and decisions, and none of them reads etcd directly3,9. The design descends from Google's Borg, where a logically centralised controller kept state in a Paxos-replicated store, and from Omega, which moved to shared state with optimistic concurrency so that independent schedulers and controllers could act in parallel2,10,11. Kubernetes took Omega's lesson and wrapped the shared store in a single REST front end with validation, defaulting and admission, so that every client sees the same schema and the same rules2,12.

The communication pattern is hub and spoke. All API use from nodes and Pods terminates at the API server, which is configured to listen on HTTPS with client authentication and authorisation enabled; nodes are provisioned with the cluster's root certificate so they can verify it3. Traffic in the other direction, from the API server to the kubelet for kubectl logs, exec and port-forwarding, is the exception and is the only reason the control plane ever initiates a connection to a node3.

Clusters can be assembled by hand, which is instructive because every certificate and flag must be placed explicitly13, but most self-managed clusters are built with kubeadm. Listing 1 is a kubeadm configuration of the kind used to bootstrap a highly available control plane behind a load-balanced endpoint: it fixes the Kubernetes version, points every node at the shared endpoint, passes flags to control-plane components as name/value pairs (the v1beta4 format), and carries the kubelet and kube-proxy configuration in the same file14,15. The kubelet section selects the systemd cgroup driver, which must match the runtime16, and the kube-proxy section selects nftables mode, discussed in section 4.

Scale is bounded by tested thresholds rather than hard limits. Kubernetes is designed for configurations of no more than 5,000 nodes, 110 pods per node, 150,000 pods in total and 300,000 containers in total18,19. Those figures reappear later, because the cost of the way back scales with the number of watchers.

3Control plane components

Five components make up the control plane: the API server, etcd, the scheduler, the controller manager and, on cloud providers, the cloud controller manager8. The first two hold state; the other three are reconcilers that hold only caches.

kube-apiserver

The API server validates and configures data for the API objects, services REST operations, and provides the front end to the cluster's shared state through which all other components interact20. It is designed to scale horizontally: several stateless instances run side by side and traffic is balanced between them8. Every request passes the same pipeline (authentication, authorisation, admission, validation, then a write to etcd), which section 6 draws in detail as Figure 5.

Although it stores nothing itself, the API server is not a thin proxy. It keeps a watch cache for each resource, fed by a single etcd watch, and serves watches and most lists from memory. Since v1.31 it can serve even consistent reads from that cache by first confirming, with a cheap etcd request, that the cache has caught up to the latest revision21; v1.34 made the cache snapshottable so that paginated lists at older revisions can also be answered from memory22; and v1.33 began streaming large list responses instead of materialising them whole23. The v1.37 release, published on 26 August 2026 with 67 enhancements, finished making watch-cache initialisation resilient: a server whose cache is still warming answers with HTTP 429 rather than passing a flood of reads through to etcd24. Admission to the server itself is governed by API Priority and Fairness, which classifies requests into priority levels and queues them fairly, returning 429 when a level's queues are full25,26.

Identity is established before any of this. The API server supports client certificates, bearer tokens and OpenID Connect among other authenticators27, and every request is then authorised; clusters normally run the Node authoriser, which limits each kubelet to objects bound to its own node, together with RBAC28–30.

etcd

etcd is the consistent and highly available key-value store that Kubernetes uses as its backing store for all cluster data8. It is covered at length in section 7. From the architecture's point of view two facts matter here: only the API server connects to it9, and every write in the cluster requires a Raft majority of its members31,32.

kube-scheduler

The scheduler watches for newly created Pods that have no node assigned and, for each one, selects a node for it to run on35. Selection runs in two phases: filtering finds the nodes that can run the Pod at all (resources, affinity, taints, volume topology), and scoring ranks the feasible ones35. The decision is published as a binding and the kubelet on the chosen node takes it from there. Scheduling is therefore a one-way decision recorded in the API: a scheduler that stops leaves bound Pods untouched and new Pods pending.

The scheduler is built on the scheduling framework, a set of extension points (PreEnqueue, QueueSort, PreFilter, Filter, PostFilter, PreScore, Score, NormalizeScore, Reserve, Permit, PreBind, Bind, PostBind) into which plugins are compiled36. A scheduling cycle runs serially; the binding cycle that follows can run concurrently with the next Pod's scheduling cycle36. Most default behaviour lives in plugins configured through a scheduler profile37.

Two details of the default configuration have large effects at scale. First, the scheduler stops filtering once it has found enough feasible nodes. With the default adaptive setting the target is 50 - nodes/125 percent of the cluster, never less than 5 percent and never fewer than 100 nodes38. The lab evaluates that rule: a 500-node cluster examines 230 nodes (46 percent), a 2,000-node cluster 680, and a 5,000-node cluster only 500 (10 percent). Second, the default NodeResourcesFit scoring strategy is LeastAllocated, which spreads load; MostAllocated and RequestedToCapacityRatio pack it instead37,39. The lab placed the same stream of 700 small Pods (1,312 CPU in total) on 100 nodes of 16 CPU under each strategy: afterwards, LeastAllocated left room for 0 eight-CPU Pods and 0 empty nodes, while MostAllocated left room for 36 and 18 empty nodes that an autoscaler could remove.

kube-controller-manager

The controller manager runs the built-in controllers: the node lifecycle controller, the Job controller, the EndpointSlice controller, the ServiceAccount controller and dozens more. Each is logically a separate process, but they are compiled into one binary and run in one process to reduce complexity8,40. A controller is a non-terminating loop that watches the shared state through the API server and makes changes that move the current state toward the desired state1. Controllers are level-triggered: they act on the difference between the latest observed state and the specification, not on the stream of events that produced it, which is what lets them resume after any gap.

Only one controller manager may act at a time, so replicas elect a leader through a Lease object in the coordination.k8s.io group41. By default the lease lasts 15 s, the holder must renew within a 10 s deadline, and candidates retry every 2 s40. The holder gives up acting at the renew deadline, before another candidate could take the lease, so two leaders never overlap if clocks advance at similar rates; that is the classic lease argument, which trades a bounded unavailability for safety42,43.

Caches are also the controllers' main hazard. A controller acting on a stale view can delete or duplicate resources, and automated testing of real controllers has found many such bugs47. Kubernetes v1.36 added staleness mitigation and metrics so that controllers can tell when their cache is behind before acting on it48.

cloud-controller-manager

The cloud controller manager embeds cloud-specific control logic and lets a cluster link to a provider's API while keeping the components that interact with that platform separate from those that only interact with the cluster50. It runs three controllers of interest: the node controller, which initialises Node objects with provider data such as zones and addresses and deletes Nodes whose instances have gone; the route controller, which programs pod-network routes in the provider's network; and the service controller, which creates, updates and deletes provider load balancers for Services of type LoadBalancer50.

Because the CCM is usually deployed as Pods in the cluster it manages, it faces a bootstrapping problem: new nodes start with an uninitialized taint that only the CCM removes, so the CCM's own Pods must tolerate it, and must not depend on anything, such as a CNI that waits for initialised nodes, that in turn waits for the CCM51. The same cycle reappears on the way back.

4Node components

Node components run on every node, maintain running Pods and provide the runtime environment: the kubelet, kube-proxy (optional when a network plugin implements Services itself) and a container runtime8. These are the components whose behaviour answers the article's question, because they are the ones that keep workloads alive.

kubelet

The kubelet is the primary node agent. It takes a set of PodSpecs, provided mainly through the API server, and ensures that the containers described in them are running and healthy; it does not manage containers that Kubernetes did not create8,52. It registers the node, reports its status and capacity, runs probes, mounts volumes through the volume manager and drives the runtime through the CRI. Its own behaviour is configured with a versioned KubeletConfiguration file rather than flags17.

Two heartbeats tell the control plane that a node is alive: updates to the Node's .status, and a Lease object in the kube-node-lease namespace53. The lease was introduced because writing the full Node status every few seconds was expensive in large clusters; the kubelet now renews a small Lease every 10 s by default and writes status only when it changes or at a longer interval41,53,54. The lease duration is 40 s17. When heartbeats stop, the node lifecycle controller marks the node's Ready condition Unknown and applies the node.kubernetes.io/unreachable taint53,55.

Static Pods

Static Pods are managed directly by the kubelet on a specific node, from manifests in a directory it watches, without the API server observing them; the kubelet creates a read-only mirror Pod in the API so they are visible58. kubeadm uses them to run the control plane itself: the API server, controller manager, scheduler and, in the stacked topology, etcd are static Pods, which is how the control plane can start before there is a control plane15,58. Kubernetes v1.37 made a long-standing rule mandatory: static Pods may not reference API objects such as Secrets, ConfigMaps or ServiceAccounts, because the kubelet cannot guarantee it can fetch them24,58. kube-proxy

kube-proxy is a network proxy on each node that implements part of the Service concept. It watches Services and EndpointSlices and programs the node's packet-processing rules so that traffic to a Service's virtual IP reaches one of its backends60,61. Three Linux modes exist. iptables has long been the default; nftables, which uses the newer kernel API and scales better with large Service counts, graduated to general availability in v1.3362,63; and ipvs has been deprecated, with a deprecation warning since v1.35 and removal planned for a later release64. The rules kube-proxy writes are an implementation detail, not an API; tooling that parses its chains breaks across versions65.

kube-proxy's holdover is the purest kind of frozen state. Rules live in the kernel and keep forwarding while kube-proxy, or the API server, is gone; what goes stale is the set of endpoints, so a Pod that dies during an outage keeps receiving its share of traffic until kube-proxy relists60.

Container runtime: CRI, containerd and CRI-O

The kubelet drives containers through the Container Runtime Interface, a gRPC API with two services: RuntimeService for Pod sandboxes and containers, and ImageService for pulling and listing images66,67. CRI was introduced in v1.5 so that runtimes could be swapped without recompiling the kubelet68. Below it, runtimes create containers that conform to the OCI runtime specification from images in the OCI image format69,70. The in-tree Docker adapter, dockershim, was removed in v1.24; Docker-built images still run, because they are OCI images71.

containerd is a general-purpose runtime whose CRI plugin serves the kubelet. Its configuration format version 3 splits CRI settings into separate plugins for images and runtime, as Listing 4 shows72. containerd 2.3.0, released in 2026, is the project's first annual long-term-support release, supported for at least two years, and moves minor releases onto a four-month cadence aligned with Kubernetes73,74. The SystemdCgroup option must agree with the kubelet's cgroup driver16; since v1.34 the kubelet can ask the runtime which driver it uses instead of being configured separately75.

CRI-O is an OCI-based implementation of the CRI built only for Kubernetes; its versions track Kubernetes minor versions76. Listing 5 is a drop-in configuration fragment.

5Supporting infrastructure

The components above make a cluster that can schedule and run containers. A cluster that can run applications also needs name resolution, a pod network, storage, a source of images, and a way for traffic to get in. Kubernetes defines interfaces and API objects for each of these and leaves the implementations to add-ons, which is why this infrastructure is where clusters differ most.

DNS

Kubernetes creates DNS records for Services and Pods so that workloads can find Services by name rather than by IP address78. A Service checkout-api in namespace shop gets an A or AAAA record checkout-api.shop.svc.cluster.local, pointing at its cluster IP or, for a headless Service, at the ready Pods themselves; named ports get SRV records of the form defined in RFC 278278,79. The kubelet writes each Pod's /etc/resolv.conf with the cluster DNS server, a search path of <namespace>.svc.cluster.local, svc.cluster.local and cluster.local, and options ndots:578. The last setting means any name with fewer than five dots is first tried against every search domain, so a lookup of an external name such as api.example.com can cost several queries before the absolute one; writing it with a trailing dot avoids them.

The cluster DNS server is almost always CoreDNS. Its kubernetes plugin builds records from a watch on Services and EndpointSlices, and its cache plugin caches responses, capped here at 30 s80,81. Listing 7 is the Corefile kubeadm installs. Because CoreDNS answers from state it already holds, it keeps resolving existing Services while the API server is away; what it cannot do is learn about new ones. The cache plugin's optional serve_stale directive extends the same idea to upstream answers81.

Networking

The Kubernetes network model has three rules: every Pod gets its own IP address that is unique across the cluster, Pods can reach all other Pods without network address translation, and agents on a node can reach all Pods on that node82. Kubernetes does not implement the model itself. The container runtime calls a network plugin that implements the Container Network Interface to attach each Pod sandbox to the network and allocate its address83,84. Listing 8 is the simplest possible configuration: a bridge on the node, addresses from a per-node range, and a port-mapping plugin chained after it. Production plugins add routing or encapsulation between nodes and usually enforce NetworkPolicy as well83.

On top of Pod networking sits the Service abstraction: a stable virtual IP and DNS name in front of a changing set of Pods85. The set is published as EndpointSlices, which the EndpointSlice controller keeps to no more than 100 endpoints each by default86. Slices replaced the original Endpoints object, which held every endpoint of a Service in a single object, because any change to one endpoint had to be sent in full to every watcher, and every node's kube-proxy is a watcher87. The Endpoints API was formally deprecated in v1.3388. The lab models the difference for a 5,000-node cluster at 130 bytes per endpoint: with 5,000 endpoints behind one Service, one Pod change pushes 3,250 MB through Endpoints but 65 MB through slices, and a full rolling update pushes 16,250 GB against 325 GB. Below 100 endpoints the two are identical; the gain is entirely in large Services.

Storage

Storage is split between two API objects. A PersistentVolume is a piece of storage in the cluster, provisioned by an administrator or dynamically; a PersistentVolumeClaim is a user's request for storage of a given size and access mode, which the control plane binds to a matching volume89. A StorageClass names a provisioner and parameters so that claims can be satisfied on demand90. Drivers implement the Container Storage Interface, whose controller service creates and attaches volumes and whose node service stages and publishes them on a host91. The split matters during an outage: mounts belong to the node and keep working, while provisioning, attachment and detachment are all driven by controllers through the API.

Container registries

Images are pulled by the container runtime, not by Kubernetes, from registries that implement the OCI distribution specification92,93. The kubelet decides whether to pull from the Pod's imagePullPolicy, and referring to images by digest rather than tag makes the pulled content immutable93. A registry is outside the control plane entirely, and the layers a node has already pulled stay on the node, so a registry outage stops new pulls but nothing already running.

Ingress infrastructure

Ingress exposes HTTP and HTTPS routes from outside the cluster to Services, but an Ingress object does nothing on its own: a separately deployed Ingress controller implements it94. The Ingress API is frozen, and new features go into Gateway API instead94. The most widely deployed controller, Ingress NGINX, has been retired. The retirement was announced on 11 November 2025, best-effort maintenance continued until March 2026, and the project now receives no releases or security fixes95; in January 2026 the Kubernetes Steering and Security Response Committees issued a joint statement urging users to migrate96.

Gateway API is the successor. It splits the concerns that Ingress mixed together into role-oriented resources: a GatewayClass defined by the infrastructure provider, a Gateway owned by the cluster operator that defines listeners, and Routes owned by application teams that attach to it97,98. Listing 9 shows a Gateway with a TLS listener and an HTTPRoute that splits traffic between a stable and a canary backend by weight, which Ingress could only express through controller-specific annotations. Gateway API v1.6, released on 3 August 2026, moved TCPRoute and UDPRoute to the Standard channel99, and Ingress2Gateway 1.0, released in March 2026, converts existing Ingress objects100.

6Kubernetes API architecture

Everything in Kubernetes is an object in the API, and everything that changes the cluster does so by writing one. The API is a resource-oriented HTTP interface; kubectl is only a client of it101.

API groups and versions

The API is divided into groups so that parts of it can evolve independently. The core group, which predates groups, has no name and is served at /api/v1; every other group is served at /apis/<group>/<version>, for example /apis/apps/v1102. Versioning is per group and signals stability: alpha versions (v1alpha1) may change or disappear without notice, beta versions (v1beta1) are well tested but may still change, and stable versions (v1) are supported for many releases102. The deprecation policy makes those promises concrete: an API element can be removed only by incrementing the group's version, beta versions must be served for at least 9 months or 3 releases after deprecation, and GA versions may be deprecated but not removed within a major version of Kubernetes103. The server stores each object at one storage version and converts between versions on the way in and out, which is how one object can be read through several versions at once104.

Resources, resource types and scope

The vocabulary is precise. A kind names an object schema (Deployment); a resource type is the name used in the URL (deployments); a single instance of a resource type is a resource, and the set of instances is a collection104. Some resources have subresources, such as status, scale or binding, which are separate endpoints with their own authorisation104. Resource types are either namespaced, living inside a namespace that forms part of their URL, or cluster-scoped, such as Nodes, Namespaces and PersistentVolumes104,105. Figure 4 decomposes one path of each kind, and Listing 10 walks the same paths with kubectl get --raw.

CRUD operations and concurrency

API verbs map onto HTTP methods: GET serves get, list and watch; POST serves create; PUT serves update; PATCH serves patch; and DELETE serves delete and deletecollection104. The same verbs are what RBAC rules grant28,30. PATCH accepts four content types: JSON Patch (RFC 6902), JSON Merge Patch (RFC 7386), the Kubernetes-specific strategic merge patch, and apply patches for server-side apply104,106,107.

Concurrency is optimistic. Every object carries a resourceVersion, an opaque string that changes on every write; an update that carries a resourceVersion succeeds only if the stored object still has it, and otherwise fails with 409 Conflict so the client can re-read and retry104. Underneath, the API server's etcd storage layer implements this as a transaction that compares the key's modification revision before writing108,109. Deletion is also cooperative: an object with finalizers is only marked with a deletion timestamp until the controllers responsible remove their finalizers110, and owner references let the garbage collector delete dependents in the foreground or background49,111.

The watch API

Watches are what make the architecture work. A client lists a collection, receives the collection's resourceVersion, then opens a watch from that version and receives a stream of ADDED, MODIFIED and DELETED events, each stamped with the resourceVersion of the change104. Periodic BOOKMARK events advance the client's resourceVersion without carrying an object, so an idle watcher does not fall behind the retained history104. If a client asks to resume from a resourceVersion that is no longer retained, the server answers 410 Gone and the client must list again from scratch104. client-go's reflector implements exactly this cycle and feeds an informer's local cache44.

How long history is retained is set by etcd compaction, which the API server triggers every 5 minutes by default20. The lab computes what that means for a client that disconnects: with a 5-minute interval, a watch disconnected for up to 300 s can always resume; one disconnected for 450 s resumes with probability 0.50; and one disconnected for 600 s or more never can, because at least one compaction has passed its revision. Any outage longer than a few minutes therefore ends with every informer in the cluster relisting, which is the load that section 9 examines. Two recent changes shrink the cost of a relist: streaming lists, in which an informer asks the watch cache to send the initial state as a stream of events rather than one large response23,112, and etcd's RangeStream, available behind the EtcdRangeStream feature gate in v1.37, which lets the API server read large ranges from etcd without buffering them whole113,114.

7etcd

etcd is the only component of a Kubernetes cluster whose loss loses data. Everything else can be rebuilt from what etcd holds.

A distributed key-value store

etcd stores data in a flat binary key space with multi-version concurrency control. Every modification creates a new revision of the whole store; each key records the revision that created it, the revision that last modified it and the number of times it has been modified; and old versions remain readable until they are compacted130. The data lives in bbolt, an embedded B+tree database, with a write-ahead log in front of it130,131. The client API offers ranges, puts, deletes, multi-key transactions with compare-and-swap, watches on keys and prefixes from any retained revision, and leases109. By default reads and writes are linearizable; clients can ask for serializable reads, which any member answers from local state and which may be stale33. Independent testing found etcd's key-value operations strict serializable under faults, while noting that its locks cannot be safe in an asynchronous system132.

Kubernetes state in etcd

The API server stores each object under a key built from a prefix, the resource type, the namespace and the name, such as /registry/deployments/shop/checkout-api; the prefix is set by --etcd-prefix and built-in types are encoded as protobuf by default20,108. The etcd revision becomes the object's resourceVersion, which is why watches, 409 conflicts and 410 Gone all trace back to etcd's revision history104,108. Because only the API server reads these keys, their layout is not an API, and nothing else should depend on it.

Raft consensus

etcd replicates its log with Raft, a consensus algorithm designed to be easier to understand than Paxos while providing the same guarantees31,133. One member is leader; it appends client writes to its log and replicates them to followers, and an entry is committed once a majority has stored it31,134. Followers that hear no heartbeat within an election timeout start an election. Each member randomises its timeout so that, usually, one member times out first and wins before any other stands31. etcd uses the etcd-io/raft library, which draws each timeout from between one and two times the configured value135, and defaults to a 100 ms heartbeat and a 1,000 ms election timeout34.

Randomisation is not a detail. No deterministic protocol can guarantee consensus in an asynchronous system with even one faulty process136, so Raft keeps safety unconditionally and relies on timing only for liveness. The lab simulates leader failure with 0.5 to 5 ms message delays. With no randomisation, 23.4 percent of 3-member trials and 49.9 percent of 5-member trials elected nobody within 60 s, because candidates kept splitting the vote. With etcd's full spread, a 3-member cluster found a leader in 1,295 ms on average and within 1,891 ms in 99 percent of trials, and only 0.4 percent needed a second round.

Quorum and high availability

A cluster of n voting members needs floor(n/2)+1 of them to commit anything, so it tolerates floor((n-1)/2) failures; this is why etcd recommends odd sizes, since an even member adds a vote to the quorum without adding tolerance32. Under a network partition etcd chooses consistency: the minority side stops accepting writes rather than diverge, the trade-off the CAP theorem describes137–139. The lab puts numbers on the arithmetic. If each member is up 99 percent of the time, independently, 3 members give 3.53 nines of availability and 4 give only 3.23: the fourth member makes the cluster 1.99 times more likely to be down. Going from 3 to 5 cuts unavailability by a factor of 30.3.

Independence is the assumption that placement breaks. With members up 99.9 percent of the time and zones up 99.95 percent, three members in one zone give 3.30 nines, about 265 minutes of expected downtime a year; spreading them 2+1 across two zones changes nothing, because losing the zone with two members still loses quorum; spreading them across three zones gives 5.17 nines, about 3.5 minutes. Zone count matters more than member count.

Because every write adds a revision, history grows without bound until it is compacted. etcd holds every Secret in the cluster, so both its transport and its storage need protection. 8The holdover census

The 33 plates placed through sections 3 to 7 answer the article's question element by element. Figure 10 sets them on one time axis: how long each keeps doing its job after the API server becomes unreachable, and what it does when the API server comes back.

The distribution over the ladder is lopsided. 4 elements stall the cluster outright (the API server, etcd's members, its leader and its quorum), 10 stop cleanly, 4 run on a clock, 8 freeze and keep serving, 2 hold local desired state and 5 need nothing from the control plane. 15 of 33 keep doing their job indefinitely. The split follows the architecture's own boundary: control-plane components average rung 0.83, while node and supporting-infrastructure elements average 3.58, a gap of 2.75 rungs. That gap is static stability made visible. The data plane was built to keep executing the last instructions it received, and it does3,4.

The clocks are the exceptions worth knowing by heart. A leader-election lease lapses after 10 s, which is harmless because another replica cannot act either; a node's heartbeat lapses after 40 s, which matters on the way back; a service-account token lapses after an hour, which matters only in a long outage; and a certificate lapses after a year, which is an outage of its own making.

The return axis tells the other half. 13 elements resume quietly, 9 reload at the cost of load on the API server, 6 act on running state when they return, evicting, detaching, deleting or rescheduling, and 5 cannot finish without a person. Figure 11 crosses the two axes.

Two patterns stand out. Every element that corrects on return is a reconciler meeting a copy of the world that froze while it was away: the controller manager and its node lifecycle controller, the cloud controller manager, operators, CSI attachment and the cloud load balancer's backend set. And every element that needs a person involves either a dependency cycle (a webhook that must admit its own Pods, an aggregated API whose absence blocks namespace deletion) or state that cannot be rederived (permanent quorum loss, a restore that rewinds time, an expired certificate). There are 11 hazardous returns against 4 stalls. The census also shows that the pair of coordinates carries information that neither carries alone: the (rung, return) profile separates 94.9 percent of all 528 pairs of elements, against 81.8 percent for rung alone and 82.2 percent for family.

9The way back

If the architecture's risk sits in its return, the return deserves the same scrutiny as the components. Four mechanisms dominate it.

The relist storm

When the API server comes back after more than a compaction interval, every informer in the cluster has lost its place in history and must relist (section 6). Clients back off between attempts, and client-go's reflector adds jitter to that backoff44. The lab shows why the jitter is load-bearing. It models 25,000 watchers returning after a 180 s outage to a server that completes 1,500 relists per second and queues at most 1,000, each client backing off from 0.8 s, doubling to a 30 s cap. Without jitter the clients stay synchronised: they arrive at a peak rate of 250,000 per second, are rejected 300,000 times, and take 741 s to finish relisting. With full jitter, the scheme Amazon's builders recommend154, the peak is 1,750 per second, nothing is rejected, and everyone has relisted after 30 s. The same clients and the same server differ by a factor of 741 to 30 in recovery time purely through timing.

This is the signature of a metastable failure: the recovery load itself keeps the system in the overloaded state, and removing the original trigger does not end it5,6. The API server's own defences point the same way. Priority and Fairness returns 429 with a retry hint instead of accepting work it cannot finish25, and v1.37's watch-cache change makes a warming server shed load rather than pass it through to etcd24.

Evictions on the way back

The node lifecycle controller watches node leases. When a node's lease is stale beyond a grace period it taints the node node.kubernetes.io/unreachable, and Pods that do not tolerate the taint for longer are evicted; by default Pods tolerate it for 300 s53,56. Tainting is rate-limited to 0.1 nodes per second, and when more than 55 percent of a zone's nodes are unhealthy the zone counts as partially disrupted and the rate drops to 0.01 per second, or to zero in clusters of 50 nodes or fewer; if every zone is fully disrupted, eviction stops altogether40,53,57.

That brake exists precisely for the way back. After an outage every lease is stale, so the controller sees a cluster in which every node has failed; nodes become Ready again only as their kubelets' requests get through the relist queue. The lab couples the two models on 5,000 nodes. Without jitter, the slow drain lets the controller taint 43 nodes and evict Pods from 3 whose kubelets were healthy all along; with full jitter it taints 3 and evicts none. With full jitter but an API server that completes only 30 relists a second, the drain takes 833 s and Pods are evicted from 5 nodes; without the zone-disruption brake, the same slow drain evicts Pods from 26.

Dependency cycles

The failures that need a person share a structure: something the control plane needs in order to recover is itself provided by a workload the control plane must first recover. The admission webhook served from the cluster is the common case116; the cloud controller manager that must initialise the nodes its own Pods run on is another51; and an aggregated API whose backend never returns leaves discovery incomplete, so namespace deletion stalls121. The static Pod exists to break the deepest of these cycles: the control plane itself is started by the kubelet from files, with no reference to the API it serves24,58.

Restoring time

A restore from snapshot is the one return in which the store moves backwards. Informers hold resourceVersions newer than any in the restored store, controllers remember objects that no longer exist, and kubelets run Pods the store has never heard of. The Kubernetes guidance, to stop every API server before restoring and restart every watching component afterwards, is a way of forcing all those caches to be discarded together9.

10Design rules

The census and the lab reduce to a short set of rules for operating the architecture as it is built.

  1. Treat the control plane as the part that is allowed to fail. Nearly everything that serves traffic holds without it. Invest in the data plane's static stability, including enough node capacity that no workload depends on being rescheduled promptly4.
  2. Spread etcd across three zones before adding members. In the lab, three members across three zones gave 5.17 nines where five members across three zones gave 5.43; three members in one or two zones gave 3.30. Never run an even number of voters15,32.
  3. Keep the store small and compacted. Watch the database size and the NOSPACE alarm, defragment one member at a time, and treat a stalled compaction as an incident measured in hours, not days144.
  4. Back up to somewhere the cluster cannot delete, and rehearse the restore, including stopping and restarting every API server and watching component9,140.
  5. Prefer in-process admission to webhooks. Write validation as ValidatingAdmissionPolicy where CEL can express it; where a webhook is necessary, exclude its own namespace and kube-system and think about its failurePolicy as a recovery decision116,117.
  6. Every client of the API server must back off with jitter, and custom controllers should use the client-go or controller-runtime machinery that already does44,154.
  7. Leave the zone-disruption brake on and size the API server for the relist it will face after an outage, not for steady state25,53.
  8. Put the clocks on a calendar. Certificates expire after a year under kubeadm; renewals and upgrades should happen well inside that148.
  9. Use apply for shared objects. Field ownership turns timing races into explicit ownership decisions124.
  10. Plan the Ingress NGINX migration now. The controller receives no further fixes; Gateway API is the supported path95,97.

Release facts later than mid-2026 (Kubernetes v1.37, etcd v3.7, containerd 2.3, Gateway API v1.6 and the Ingress NGINX retirement) were checked against their announcements on 24 September 2026. Configuration defaults are quoted from the reference documentation for the versions named and may differ in distributions and managed services.

Every measured number in the text is read from the output of a deterministic lab written in standard-library Python with seed 20260924, run as part of the build; its output is reproduced verbatim below. The lab consists of models, not measurements of a running cluster. Availability assumes independent member failures within a zone. The election simulation abstracts Raft to timeouts, vote requests and message delay. The relist model treats every client as a single request of equal cost against a server with a fixed service rate and queue. The eviction model couples that queue to a simplified node lifecycle controller with a 5 s monitor period. The fan-out model counts bytes at an assumed 130 bytes per endpoint. The concurrency model is a Poisson process of writers. The shapes of these results are robust to the parameters; their magnitudes are illustrations. The census rungs and return codes are editorial judgements made against the cited behaviour, recorded in the plates so that each can be checked and disputed.

Listings were validated as far as the build environment allowed: YAML, JSON and TOML files parse, shell scripts pass bash -n, and the Go controller was syntax-checked with gofmt but not compiled, because the build environment could not fetch modules.

def e1_quorum():
    say("E1  Raft quorum arithmetic and member placement")
    rows = []
    for n in range(1, 8):
        q = n // 2 + 1
        tol = n - q
        av = {}
        for p in (0.99, 0.999):
            a = sum(comb(n, k) * p**k * (1 - p)**(n - k) for k in range(q, n + 1))
            av[str(p)] = a
        rows.append(dict(n=n, quorum=q, tolerates=tol,
                         a99=av["0.99"], a999=av["0.999"],
                         nines99=-math.log10(1 - av["0.99"]),
                         nines999=-math.log10(1 - av["0.999"])))
        say(f"  n={n} quorum={q} tolerates={tol}  A(p=.99)={av['0.99']:.8f} "
            f"({-math.log10(1-av['0.99']):.2f} nines)  A(p=.999)={av['0.999']:.10f}")
    # even sizes: n=4 vs n=3 unavailability ratio
    u3 = 1 - rows[2]["a99"]; u4 = 1 - rows[3]["a99"]
    u5 = 1 - rows[4]["a99"]
    say(f"  unavailability ratio n=4/n=3 at p=.99: {u4/u3:.3f}; n=3/n=5: {u3/u5:.1f}")
    # zone placement: members fail independently with p_m, zones with p_z
    pm, pz = 0.999, 0.9995
    def placement(counts):
        n = sum(counts); q = n // 2 + 1
        tot = 0.0
        Z = len(counts)
        for mask in range(1 << Z):
            pzone = 1.0; alive_members = []
            for zi in range(Z):
                up = (mask >> zi) & 1
                pzone *= pz if up else (1 - pz)
                if up:
                    alive_members.append(counts[zi])
            m = sum(alive_members)
            pq = sum(comb(m, k) * pm**k * (1 - pm)**(m - k) for k in range(q, m + 1)) if m >= q else 0.0
            tot += pzone * pq
        return tot
    plc = []
    for label, counts in (("3 members, 1 zone", [3]), ("3 members, 2 zones (2+1)", [2, 1]),
                          ("3 members, 3 zones", [1, 1, 1]), ("5 members, 3 zones (2+2+1)", [2, 2, 1]),
                          ("5 members, 5 zones", [1, 1, 1, 1, 1])):
        a = placement(counts)
        plc.append(dict(label=label, avail=a, nines=-math.log10(1 - a),

    say()

def raft_trial(rng, n, T, spread, dmin, dmax, H, cap_ms=60000.0):
    """Leader (node 0) crashes at t=0. Returns (time to new leader ms, rounds, ok)."""
    live = list(range(1, n))
    maj = n // 2 + 1
    term = {i: 1 for i in live}
    voted = {i: None for i in live}
    role = {i: "F" for i in live}
    votes = {i: 0 for i in live}
    deadline = {}
    ev = []  # (time, seq, kind, a, b, term)
    seq = [0]
    def push(t, kind, a, b=None, tm=None):
        seq[0] += 1
        heapq.heappush(ev, (t, seq[0], kind, a, b, tm))
    last_hb = -rng.uniform(0, H)
    gen = {i: 0 for i in live}
    def arm(i, now):
        gen[i] += 1
        d = now + T * (1.0 + spread * rng.random())
        deadline[i] = d
        push(d, "timer", i, gen[i])
    for i in live:
        arm(i, last_hb + rng.uniform(dmin, dmax))
    max_term_started = 1
    while ev:
        t, _, kind, a, b, tm = heapq.heappop(ev)
        if t > cap_ms:
            return cap_ms, max_term_started - 1, False
        if kind == "timer":
            if b != gen[a] or role[a] == "L":
                continue
            term[a] += 1; max_term_started = max(max_term_started, term[a])
            role[a] = "C"; voted[a] = a; votes[a] = 1
            arm(a, t)
            for j in live:
                if j != a:
                    push(t + rng.uniform(dmin, dmax), "rv", j, a, term[a])
        elif kind == "rv":  # a receives RequestVote from b for term tm
            if tm > term[a]:
                term[a] = tm; voted[a] = None; role[a] = "F"
            if tm == term[a] and voted[a] in (None, b):
                voted[a] = b
                arm(a, t)
                push(t + rng.uniform(dmin, dmax), "vote", b, a, tm)
        elif kind == "vote":  # a receives a vote for term tm
            if role[a] == "C" and tm == term[a]:
                votes[a] += 1
                if votes[a] >= maj:
                    return t, term[a] - 1, True
    return cap_ms, max_term_started - 1, False

def relist_storm(rng, mode, clients=25000, outage=180.0, mu=1500.0, qcap=1000,
                 base=0.8, cap=30.0, bin_s=0.1):
    """All clients lose the API server at t=0; it returns at t=outage.
    mode: 'lockstep' (deterministic doubling), 'full' (full jitter),
          'equal' (equal jitter). Server: FIFO, rate mu, max qcap in system."""
    heap = []
    for c in range(clients):
        heapq.heappush(heap, (0.0, rng.random(), c, 0))
    done_at = [None] * clients
    completions = []  # min-heap of completion times of in-system requests
    last_fin = outage
    arrivals = {}
    rejected = 0
    def backoff(k):
        b = min(cap, base * (2 ** k))
        if mode == "lockstep":
            return b
        if mode == "full":
            return rng.uniform(0, b)
        return b / 2 + rng.uniform(0, b / 2)
    while heap:
        t, _, c, k = heapq.heappop(heap)
        if t < outage:  # connection refused
            heapq.heappush(heap, (t + backoff(k), rng.random(), c, k + 1))
            continue
        b = int((t - outage) / bin_s)
        arrivals[b] = arrivals.get(b, 0) + 1
        while completions and completions[0] <= t:
            heapq.heappop(completions)
        if len(completions) >= qcap:
            rejected += 1
            heapq.heappush(heap, (t + backoff(k), rng.random(), c, k + 1))
            continue
        fin = max(t, last_fin) + 1.0 / mu
        last_fin = fin
        heapq.heappush(completions, fin)
        done_at[c] = fin - outage
    peak_bin = max(arrivals.values())
    done_sorted = sorted(done_at)
    per_s = {}
    for b, v in arrivals.items():
        sec = int(b * bin_s)
        per_s[sec] = per_s.get(sec, 0) + v
    horizon = int(done_sorted[-1]) + 2
    series = [per_s.get(i, 0) for i in range(horizon)]
    return dict(mode=mode, peak_per_s=peak_bin / bin_s, rejected=rejected, series=series,
                t50=done_sorted[len(done_sorted) // 2], t99=done_sorted[int(0.99 * len(done_sorted))],
                t100=done_sorted[-1], done=done_at)

def e5_eviction(storm):
    say("E5  Node lifecycle on return: which nodes lose their pods?")
    # 5,000 nodes; node i's kubelet renews its lease at the time its first
    # request clears (we map the first 5,000 clients of E4 to kubelets).
    tol = 300.0; mon = 5.0
    out = []
    def run(ready_at, G, label, rate=0.1, rate2=0.01, thr=0.55, large=50):
        n = len(ready_at)
        # lease last renewed at outage start; controller restarts with the API
        # server at t=0 (relative) and evaluates every `mon` seconds.
        tainted_at = [None] * n
        tokens = 1.0; last = 0.0
        t = 0.0
        evicted = 0
        full_disruption_ticks = 0
        partial_ticks = 0
        fr_series = []; taint_times = []
        while t <= 1800.0:
            notready = [i for i in range(n) if ready_at[i] > t]
            frac = len(notready) / n
            fr_series.append(round(frac, 5))
            if frac >= 1.0:
                r = 0.0; full_disruption_ticks += 1
            elif frac >= thr:
                r = rate2 if n > large else 0.0; partial_ticks += 1
            else:
                r = rate
            tokens = min(1.0, tokens + r * (t - last)); last = t
            for i in notready:
                if r > 0 and tainted_at[i] is None and tokens >= 1.0:
                    tainted_at[i] = t; tokens -= 1.0; taint_times.append(t)
            t += mon
        for i in range(n):
            if tainted_at[i] is not None and ready_at[i] > tainted_at[i] + tol:
                evicted += 1
        tainted = sum(1 for x in tainted_at if x is not None)
        ev_times = sorted(tainted_at[i] + tol for i in range(n)
                          if tainted_at[i] is not None and ready_at[i] > tainted_at[i] + tol)
        return dict(label=label, tainted=tainted, evicted=evicted,
                    full_ticks=full_disruption_ticks, partial_ticks=partial_ticks,
                    frac_series=fr_series, taint_times=taint_times, evict_times=ev_times)
    for mode in ("lockstep", "equal", "full"):
        done = storm[mode]["done"][:5000]
        # the outage (180 s) exceeds any node-monitor grace period, so every
        # node starts NotReady and stays so until its kubelet's request clears.
        r = run(list(done), None, f"{mode} backoff")
        r["t100"] = storm[mode]["t100"]
        out.append(r)
        say(f"  {mode:8s} tainted {r['tainted']:4d}  pods evicted on {r['evicted']:4d} nodes "
            f"(full-disruption ticks {r['full_ticks']}, partial {r['partial_ticks']})")
    # slow return: server capacity cut to 60 req/s so the drain takes minutes
    rng = random.Random(SEED + 5)
    slow = relist_storm(rng, "full", mu=30.0)
    done = slow["done"][:5000]
    r = run(list(done), None, "full jitter, server at 30 req/s")
    r["t100"] = slow["t100"]; r["t99"] = slow["t99"]
    out.append(r)
    say(f"  slow server: all relisted at +{slow['t100']:.0f} s; tainted {r['tainted']}, "
        f"pods evicted on {r['evicted']} nodes (partial-disruption ticks {r['partial_ticks']})")
    # counterfactual: same slow drain with the zone logic disabled
    def run_nozone(ready_at):
        n = len(ready_at); tainted_at = [None] * n; tokens = 1.0; last = 0.0; t = 0.0
        while t <= 1800.0:
            tokens = min(1.0, tokens + 0.1 * (t - last)); last = t
            for i in range(n):
                if ready_at[i] > t and tainted_at[i] is None and tokens >= 1.0:
                    tainted_at[i] = t; tokens -= 1.0
            t += mon
        return sum(1 for i in range(n) if tainted_at[i] is not None and ready_at[i] > tainted_at[i] + tol)
    nz = run_nozone(list(done))
    say(f"  same slow drain without the zone-disruption brake: pods evicted on {nz} nodes")
    OUT["E5"] = dict(tol=tol, rows=out, slow_t100=slow["t100"], nozone_evicted=nz)
    say()

# ------------------------------------------------------- E6 scheduler
def e6_scheduler():
    say("E6  Scheduler: how many nodes are scored, and what scoring does to packing")
    def to_find(n, pct=None):
        if n < 100: return n
        if pct is None:
            pct = 50 - n // 125
            if pct < 5: pct = 5
        k = n * pct // 100
        return max(k, 100)
    samp = []
    for n in (50, 100, 500, 1000, 2000, 5000):
        k = to_find(n)
        samp.append(dict(n=n, k=k, pct=100.0 * k / n))
        say(f"  {n:5d} nodes -> feasible nodes sought {k:5d} ({100.0*k/n:5.1f}%)")
    # packing: 100 nodes x 16 CPU; place a seeded stream of small pods,
    # then count how many 8-CPU pods still fit.
    rng = random.Random(SEED + 6)
    stream = [rng.choice([1, 1, 2, 2, 3]) for _ in range(700)]
    res = []
    for policy in ("LeastAllocated", "MostAllocated"):
        free = [16] * 100
        placed = 0
        for cpu in stream:
            best = None; best_s = None
            for i in range(100):
                if free[i] >= cpu:
                    used = 16 - free[i]
                    s = (16 - used) / 16 if policy == "LeastAllocated" else used / 16
                    if best is None or s > best_s:
                        best, best_s = i, s
            if best is not None:
                free[best] -= cpu; placed += 1
        big = sum(f // 8 for f in free)
        empty = sum(1 for f in free if f == 16)
        res.append(dict(policy=policy, placed=placed, used=sum(16 - f for f in free),
                        big_fit=big, empty_nodes=empty))
        say(f"  {policy:15s} placed {placed} small pods ({sum(16-f for f in free)} CPU); "
            f"8-CPU pods that still fit: {big}; empty nodes left: {empty}")
    OUT["E6"] = dict(sampling=samp, packing=res, stream_cpu=sum(stream))
    say()

def e7_fanout():
    say("E7  Endpoint fan-out: bytes pushed to kube-proxies for one pod change")
    per_ep = 130  # bytes per serialized endpoint entry (model assumption)
    nodes = 5000
    rows = []
    for eps in (10, 100, 1000, 5000):
        endpoints_obj = eps * per_ep
        slice_obj = min(eps, 100) * per_ep
        one_change_endpoints = endpoints_obj * nodes
        one_change_slices = slice_obj * nodes
        rolling_endpoints = one_change_endpoints * eps
        rolling_slices = one_change_slices * eps
        rows.append(dict(eps=eps, one_endpoints_mb=one_change_endpoints / 1e6,

                         roll_endpoints_gb=rolling_endpoints / 1e9,
                         roll_slices_gb=rolling_slices / 1e9,
                         ratio=endpoints_obj / slice_obj))
        say(f"  {eps:5d} endpoints: one change -> Endpoints {one_change_endpoints/1e6:9.2f} MB, "
            f"EndpointSlice {one_change_slices/1e6:7.2f} MB; full rolling update "

    say()

# --------------------------------------- E8 optimistic concurrency vs SSA
def e8_concurrency():
    say("E8  Writers on one object: resourceVersion preconditions vs field ownership")
    rows = []
    for r in (0.25, 1.0):
        for k in (1, 2, 4, 8, 16):
            rng = random.Random(SEED + 8 + k)
            horizon = 4000.0; per = 0.5  # each writer wants one update per 2 s
            events = []
            for w in range(k):
                tt = rng.expovariate(per)
                while tt < horizon:
                    events.append((tt, w)); tt += rng.expovariate(per)
            events.sort()
            last_commit = [0.0] * k
            commits = []  # (time, writer)
            attempts = 0; success = 0
            owner = None; ssa_conf = 0; ssa_writes = 0
            for (ts, w) in events:
                start = max(ts, last_commit[w])  # a controller works one key at a time
                tries = 0
                while True:
                    tries += 1
                    hi = start + r
                    clash = False
                    for (c, cw) in commits[-400:]:
                        if cw != w and start < c < hi:
                            clash = True; break
                    if not clash or tries >= 100:
                        commits.append((hi, w)); last_commit[w] = hi; break
                    start = hi
                attempts += tries; success += 1
                # SSA: no precondition. Each manager owns its own fields; with
                # probability 0.1 a write also sets the shared field. The first
                # manager to set it owns it; others get a 409 conflict unless forced.
                ssa_writes += 1
                if rng.random() < 0.10:
                    if owner is None:
                        owner = w
                    elif owner != w:
                        ssa_conf += 1
            rows.append(dict(r=r, k=k, attempts_per_success=attempts / success,
                             conflict_pct=100.0 * (attempts - success) / attempts,
                             ssa_conflict_pct=100.0 * ssa_conf / ssa_writes))
            say(f"  latency {r:4.2f} s, {k:2d} writers: {attempts/success:6.2f} attempts per update "
                f"({100.0*(attempts-success)/attempts:5.1f}% rejected as stale); "
                f"field-ownership conflicts {100.0*ssa_conf/ssa_writes:5.1f}%")
    OUT["E8"] = dict(rows=rows, per_writer_rate=0.5, shared_field_pct=10)
    say()
