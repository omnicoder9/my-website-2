Thesis

What survives the replacement?

Every workload resource in Kubernetes does the same thing for a living: it notices that a Pod is missing, wrong or surplus, and it replaces it. The six built-in workload resources this article covers 1 differ almost entirely in what they promise will survive that replacement. A ReplicaSet promises nothing about the individual Pod, only about the count. A StatefulSet promises the name, the DNS record and the storage. A DaemonSet promises the node. An Indexed Job promises the index. A CronJob promises the schedule slot. Read the API through that question and most of its shape stops looking like a list of options and starts looking like a set of consequences.

The question also predicts which rollouts may run two copies at once. A Deployment can surge because nothing about a Pod has to be unique. A StatefulSet cannot surge, because a name cannot be held twice and a single-writer volume cannot be mounted twice. A DaemonSet can surge, because two Pods can share a node. A Job lets you forbid overlap per index precisely because the index is what survives. The organising device below codes 37 mechanisms, one for each concept in the brief, on five survivor slots — name, DNS, volume, node and position — and the ledger at the end shows the pattern holding across all of them.

Facts about current behaviour are taken from the Kubernetes documentation, API reference and enhancement proposals as of Kubernetes v1.37, released on 26 August 2026 2,3. Quantitative claims come from a nine-experiment, standard-library Python lab run at build time; its output is embedded verbatim in the final section, and every number quoted in the prose and figures is read from it.

Concepts

The controller is the unit

Kubernetes inherits its central idea from Borg and Omega: the user states a desired outcome and a family of independent control loops works to make the observed world match it 4,5,6. The documentation calls these loops controllers and describes each one as tracking at least one resource type, reading the object's specification and acting through the API server until the current state approaches the desired state 7. Feedback-control language fits exactly: the specification is the set point, the controller is the regulator, the Pods are the plant and the status block is the sensor reading 8. Burns and colleagues describe the consequence for Kubernetes' design directly: rather than one central orchestrator, behaviour emerges from many small controllers each reconciling one kind of object 6.

Spec, status and generation

Every workload object separates spec, which the user writes, from status, which the controller writes. The API conventions require that status be reconstructable from observation and never be used as an input, and they define metadata.generation and status.observedGeneration so a client can tell whether the controller has yet seen the latest spec 9. A rollout tool that waits on a Deployment's conditions without first checking that observedGeneration has caught up is reading a report about the previous version.

Labels, selectors and ownership

Controllers find their Pods by label selector, not by list. A selector is a query — matchLabels for equality, matchExpressions for In, NotIn, Exists and DoesNotExist — evaluated against whatever Pods exist 10. Because the query is open, a second mechanism records who owns what: each dependent carries an ownerReferences entry, at most one of which may be marked controller: true 11. Garbage collection follows those references, deleting dependents in the background by default, in the foreground if asked, or orphaning them 12. Ownership chains are short and typed: Deployment → ReplicaSet → Pod; CronJob → Job → Pod; StatefulSet → Pod and, under a retention policy, → PersistentVolumeClaim; DaemonSet → Pod.

The survivor slots

To compare controllers, this article asks of each mechanism: when a Pod under it is replaced, which of five properties carry over to the replacement? The name (the Pod's metadata.name); a DNS record that resolves to whichever Pod currently holds the identity; a volume whose contents the replacement inherits; the node the replacement runs on; and a position — an ordinal, a completion index or a schedule slot — that gives the Pod a numbered place in a larger whole. A filled slot means the property survives replacement by design. An empty slot means the replacement is free to differ, which is a capability as much as a limitation: it is what lets two copies coexist.

Each plate in the sections that follow carries a four-field record — what the mechanism holds constant, how it replaces, what it is reconciled from, and what it breaks when — and a small gauge showing its five slots and lifetime. Lifetimes are of three kinds: serve indefinitely, run to completion, or run on a timetable.

apps/v1 ReplicaSet

ReplicaSets

A ReplicaSet maintains a stable set of replica Pods running at any given time, and is the lowest-level workload controller that most users meet 14. It is defined by three fields: a replicas count, a selector that identifies the Pods it may count, and a Pod template for the Pods it creates. The API server rejects a ReplicaSet whose template labels do not satisfy its own selector, since such a controller would create Pods it could never see 14.

Replica management and selectors

The ReplicaSet counts any Pod that matches its selector and is not terminating. Its documentation is explicit that this extends to Pods it did not create: a Pod with no controller owner whose labels match is acquired immediately 14. The consequence, demonstrated in the listing below, is that a hand-made Pod with the right labels becomes a replica, and if the count is already satisfied the controller deletes something to restore it. Selectors are therefore part of the safety design, not a convenience; two ReplicaSets with overlapping selectors will fight, and the documentation warns against overlapping selectors across controllers for exactly that reason 10,14.

Pod templates

The template is a recipe for future Pods. Editing a ReplicaSet's template does not change or restart any existing Pod; only Pods created afterwards follow the new template 14. That is the gap the Deployment fills, and it is why the documentation recommends Deployments rather than direct ReplicaSets for almost every case 14,15.

Scaling

Scaling is a write to spec.replicas, usually through the scale subresource that both kubectl scale and the HorizontalPodAutoscaler use 19. On scale-down the controller prefers victims in a documented order: Pending or unschedulable Pods first; then Pods with a lower controller.kubernetes.io/pod-deletion-cost annotation; then Pods on nodes running more replicas; then more recently created Pods, with creation times bucketed on a logarithmic scale 14. Nothing in that order refers to which Pod is "the" Pod, because none is.

Self-healing

Self-healing is the same arithmetic run after a loss. If a Pod is deleted, fails, or is evicted, the count drops and the controller creates a replacement — with a new name, a new UID and, in general, a new IP and node 14,20. The slower case is a node that stops reporting: the Pods on it are not gone, merely unreachable. Kubernetes adds a default toleration for the not-ready and unreachable taints with tolerationSeconds: 300 to Pods that do not set their own, so by default a replica on a dead node is evicted, and replaced, about five minutes after the node is tainted 21.

Experiment E3 makes the value of the loop concrete. Five replicas, each failing as an exponential process with a seven-day mean time between failures, were simulated for thirty days. Without a controller, the expected number of the original five still alive after thirty days is 0.069, and the chance that even one survives is 6.70%. With a controller replacing each loss after 30 seconds, all five were Ready for 99.97% of the month; stretching replacement to ten minutes still left all five Ready 99.51% of the time. The simulated figures agree with the closed form for independent alternating renewal processes, (MTBF/(MTBF+repair))n, to within 0.008 percentage points.

Relationship with Deployments

A Deployment owns ReplicaSets the way a ReplicaSet owns Pods. It creates one ReplicaSet per distinct Pod template, labels it with a hash of that template, and moves replicas between the old and new ReplicaSets during a rollout 15. Editing a ReplicaSet that a Deployment owns is overwritten on the Deployment's next reconcile. Standalone ReplicaSets remain useful for custom orchestration that needs exactly "n copies, never updated in place" — which is precisely, and only, what they promise.

apps/v1 Deployment

Deployments

A Deployment provides declarative updates for Pods and ReplicaSets: the user describes the desired template and replica count, and the Deployment controller changes the actual state to the desired state at a controlled rate 15. Deployments, ReplicaSets, StatefulSets and DaemonSets graduated together to the apps/v1 API in Kubernetes 1.9 in December 2017, the release that froze the shapes still used today 22.

Declarative deployment and ReplicaSets

The controller adds a pod-template-hash label to each ReplicaSet it creates and to that ReplicaSet's Pods, which keeps sibling ReplicaSets from selecting each other's Pods 15. A rollout is triggered if and only if spec.template changes; scaling, or editing fields outside the template, does not create a revision 15. In apps/v1 the selector is immutable after creation, because changing it would orphan every existing ReplicaSet 15,23.

Rolling updates

The default strategy is RollingUpdate, bounded by two numbers. maxSurge is how many Pods may exist above the desired count; maxUnavailable is how many below it may be unavailable. Both default to 25%, they may not both be zero, and — the detail most often misstated — percentages convert to absolute numbers in opposite directions: maxSurge rounds up, maxUnavailable rounds down 23. At least one vendor guide gets this backwards for small counts, claiming the default allows two of two replicas to be unavailable 24; the API reference's rule gives zero.

Experiment E1 tabulates the rule for 1–20 replicas. At 1, 2 and 3 replicas the default maxUnavailable rounds to zero, so a small Deployment can only surge; it never dips below its count, but it needs room for an extra Pod or the rollout cannot start. At ten replicas the defaults allow 3 extra Pods and 2 unavailable, so the cluster must briefly hold 13 Pods while serving from as few as 8.

Experiment E2 runs a tick-level model of the controller over a ten-replica rollout in which each new Pod takes 20–40 seconds to become Ready. The default finished in 73 s with availability never below 8 and a peak of 13 Pods. maxSurge: 1, maxUnavailable: 0 never lost a replica but took 340 s, because it serialises every readiness wait; the mirror image, maxSurge: 0, maxUnavailable: 1, took 341 s and spent the time one replica short. Surging the full count gave a blue–green-shaped rollout in 40 s at the cost of 20 Pods at peak. There is no free point on this curve: speed is bought with either spare capacity or reduced capacity, and the two knobs choose which.

Two conditions make the bounds mean what they say. A readiness probe is required for "available" to mean "able to serve"; without one a Pod is Ready as soon as its containers run 20. And minReadySeconds sets how long a Pod must stay Ready before it counts as available, which catches the process that starts cleanly and falls over a few seconds later 15.

Deployment strategies

The only other built-in strategy is Recreate, which deletes every old Pod before creating any new one 15. It is the right choice when two versions must never run together — a schema migration that the old binary cannot tolerate, or a single-writer volume. In E2 it finished in 40 s, as fast as a full surge, but with zero capacity for the first 20 s. Canary, blue–green and traffic-weighted strategies are not Deployment strategies; they are built from two Deployments and a Service, or from a progressive-delivery controller layered on top 25.

Rollbacks and revision history

Because old ReplicaSets are retained at zero replicas, a rollback is just another rollout: kubectl rollout undo writes the old template back into the Deployment, whose hash matches the retained ReplicaSet, which is scaled back up 15,26. The revision number lives in the deployment.kubernetes.io/revision annotation and moves forward on rollback rather than back. revisionHistoryLimit, default 10, caps how many idle ReplicaSets are kept; setting it to zero makes rollback impossible 15.

The limit is a count, but what operators care about is a time horizon. E9 converts one into the other:

Scaling

Scaling a Deployment changes the replica count without creating a revision. If a scale arrives mid-rollout, the controller uses proportional scaling, spreading the additional replicas across the old and new ReplicaSets in proportion to their current sizes, so that a half-finished rollout stays half-finished rather than being silently completed or reversed 15. A HorizontalPodAutoscaler targets the Deployment's scale subresource, and then spec.replicas should be removed from manifests that are re-applied, or each apply will fight the autoscaler 19.

Pausing and resuming

kubectl rollout pause sets spec.paused. While paused, template edits accumulate without triggering a rollout; on resume they roll out as a single revision 15,26. Scaling continues to work while paused, and a paused Deployment cannot be rolled back until it is resumed 15.

Deployment status

Status reports counts — replicas, updatedReplicas, readyReplicas, availableReplicas, unavailableReplicas — and conditions. Available reflects whether the minimum is met; Progressing reflects whether the rollout is moving, with reasons such as NewReplicaSetAvailable and, after progressDeadlineSeconds (default 600) without progress, ProgressDeadlineExceeded 15. The documentation is explicit that Kubernetes takes no action on a stalled rollout beyond reporting it; deciding to roll back belongs to whatever is watching the condition 15. Since v1.35 a terminatingReplicas count has also been reported for Deployments and ReplicaSets, in beta, so that tooling can see Pods that are going but not yet gone 27,28.

apps/v1 StatefulSet

StatefulSets

A StatefulSet manages Pods that are created from the same template but are not interchangeable: each has a persistent identifier that it keeps across any rescheduling 13. The documentation lists what that identifier buys: stable unique network identifiers, stable persistent storage, ordered graceful deployment and scaling, and ordered automated rolling updates 13. In survivor terms it fills four slots at once — name, DNS, volume and position — and that is the whole of its difference from a Deployment.

Stateful applications

"Stateful" here means something narrower than "has data". A cache that can be refilled is better served by a Deployment. A StatefulSet earns its constraints when members of a group must be told apart: a replica that must find the same disk after a restart, a peer that must be addressable by a name others have written into their configuration, or a cluster member whose bootstrap depends on which members already exist 13,29.

Stable Pod identities

Pods are named <statefulset>-<ordinal>, ordinals running from 0 to n−1 by default, or from .spec.ordinals.start if set, which supports numbering from 1 or migrating replicas between StatefulSets one ordinal at a time 13,31. The controller also labels each Pod with its name and its ordinal (apps.kubernetes.io/pod-index), so a Service or policy can select a single member 13.

Stable network identities and Headless Services

A StatefulSet names a governing Service in serviceName, and the documentation requires that Service to be headless (clusterIP: None) and to exist before the Pods need it; creating it is the user's responsibility 13. A headless Service publishes a DNS record per ready Pod instead of a virtual IP, giving each member a name of the form <pod>.<service>.<namespace>.svc.cluster.local that follows the identity from IP to IP 30,32. The documentation warns about negative caching: a client that looks a name up before the Pod exists may cache the miss for some seconds 13.

Persistent storage

Each entry in volumeClaimTemplates produces one PersistentVolumeClaim per ordinal, named <template>-<pod>; when a Pod is rescheduled, its replacement mounts the same claim 13,33. That is the volume slot, and its cost is placement: a claim bound to a zonal or node-local volume pulls the Pod back to wherever that volume lives. StorageClasses with volumeBindingMode: WaitForFirstConsumer delay binding until the first Pod is scheduled, so the volume is created where the scheduler put the Pod rather than the other way round 34. Access mode ReadWriteOncePod makes the single-writer guarantee explicit 33.

By default, deleting or scaling down a StatefulSet does not delete its claims; data outlives the Pods unless told otherwise 13. persistentVolumeClaimRetentionPolicy makes the choice explicit with two fields, whenDeleted and whenScaled, each Retain (the default) or Delete 13,35. The feature reached general availability in v1.32 35.

Ordered deployment and ordered scaling

Under the default OrderedReady policy, Pods are created one at a time in ordinal order, each only after its predecessors are Running and Ready, and removed in reverse order, each only after its successors have fully terminated 13. Parallel launches or terminates all Pods at once; it affects scaling only, not updates 13. Deleting a StatefulSet object does not guarantee ordered termination; scaling it to zero first does 13.

E4 prices the ordering. With a 45-second initialisation per member, ordered scale-up from zero takes 135 s for three replicas and 405 s for nine, against 45 s under Parallel. The order is worth paying for when bootstrap really depends on it — a member that clones its data from the previous ordinal, as in the documentation's replicated MySQL example 36 — and is pure latency otherwise.

Pod management policies

The choice between OrderedReady and Parallel is fixed at creation 31. Its failure mode under OrderedReady is total: if ordinal 1 never becomes Ready, ordinals 2 and up are never created, and a scale-up simply stalls. That is correct behaviour for a system whose later members depend on earlier ones, and an outage generator for one whose members are independent.

StatefulSet updates

Two update strategies exist. OnDelete updates a Pod only when someone deletes it. RollingUpdate, the default, replaces Pods from the highest ordinal to the lowest, waiting for each to be Running and Ready before the next 13. A partition holds back every ordinal below it, which is how a StatefulSet canaries: set the partition to n−1, update the template, watch one member, then lower the partition 13,37. In E4's run with five replicas and partition 3, ordinals 4 and 3 were updated and 0, 1 and 2 were left on the old revision. The controller tracks revisions with ControllerRevision objects rather than ReplicaSets 38.

maxUnavailable for StatefulSet rolling updates was introduced as alpha in v1.24 and has been beta, enabled by default, since v1.35 39,40,41. It lets several ordinals update at once, with the caveat in the API reference that it may not be effective under OrderedReady. What it cannot be is a surge: there is no maxSurge for StatefulSets, because a second pg-1 cannot exist and a ReadWriteOncePod claim cannot be attached to two Pods. E4 shows why the setting is a quorum decision rather than a speed setting: for a majority-quorum system of three members only maxUnavailable: 1 keeps a majority up; for five, values 1 and 2 do; for seven, 1 to 3 42.

The documentation records one sharp edge as a known issue: if a template change produces a Pod that never becomes Ready, the rolling update stops and waits, and reverting the template is not enough — the broken Pods must be deleted by hand before the controller recreates them from the reverted template 13.

Databases on Kubernetes

A StatefulSet supplies identity and storage. It supplies nothing about replication, leader election, failover, backup or membership change, which are the hard parts of running a database 29,42. The documentation's own tutorials make this visible: the replicated MySQL example derives each member's server ID from its ordinal and clones data from the previous ordinal with an init container 36, and the ZooKeeper tutorial derives myid from the ordinal and adds a PodDisruptionBudget so voluntary disruptions cannot take out a quorum 43,44. In practice that logic lives in operators — controllers for a custom resource that encode a specific system's runbook 45. Some build on StatefulSets; one prominent PostgreSQL operator, CloudNativePG, deliberately does not, managing its PersistentVolumeClaims directly so that it, rather than the generic controller, decides which instance is recreated and when 46,47. That choice is the survivor model in miniature: the operator keeps the name, volume and position slots but takes ordering and update policy away from a controller that cannot know which member is the primary.

apps/v1 DaemonSet

DaemonSets

A DaemonSet ensures that all, or some, nodes run a copy of a Pod. As nodes join, Pods are added to them; as nodes leave, those Pods are garbage-collected 16. The only slot it fills is the node, and that single guarantee is what makes it the home for anything that must see a host from the inside.

One Pod per node

The DaemonSet controller decides eligibility from nodeSelector, node affinity and taints, then creates one Pod per eligible node and pins it by adding node affinity on the node's name; the default scheduler performs the binding 16. It also adds tolerations so its Pods are not evicted for conditions that would evict ordinary workloads — among them not-ready and unreachable with no time limit, disk, memory and PID pressure, and unschedulable 16,21. Taints such as the control-plane taint are not tolerated automatically; the manifest below adds that toleration so the agent also covers control-plane nodes.

Node agents

The documentation's canonical uses are a cluster storage daemon, a log collector and a node-monitoring daemon on every node 16. The pattern generalises: whenever the work's natural unit is "this machine", replacement must land on the same machine, and so the agent's useful state — positions, sockets, host rules — is kept on the host rather than in the Pod.

Logging agents

Kubernetes' logging architecture recommends a node-level agent, usually run as a DaemonSet, that reads container log files from the node and forwards them 48. The agent's read position is the state that matters, and keeping it on a hostPath volume lets a replacement agent resume where its predecessor stopped. That is the volume slot surviving through the node rather than through a claim.

Monitoring agents

Node exporters need the host's view of CPU, memory, file systems and network, so they typically run with host namespaces and read-only host mounts. One per node is the definition of complete coverage, and a gap during replacement is a gap in the metrics for that node.

Storage agents

A Container Storage Interface driver is split into a controller plugin and a node plugin; the node plugin must run on every node that will mount volumes, and it registers with the kubelet over a socket on the host 49. While the node plugin is down, new mounts on that node fail. This is the most consequential DaemonSet in many clusters and the one where update strategy deserves the most care.

Networking agents

Network plugins implement the Pod network on each node, and their per-node components conventionally run as DaemonSets in the host network namespace 50. kubeadm installs kube-proxy as a DaemonSet for the same reason 51. An agent that programs the datapath has to be present before Pods on that node can communicate, which is why such DaemonSets usually run at node-critical priority.

Rolling updates

DaemonSets support RollingUpdate (the default) and OnDelete 52. Rolling updates are bounded by maxUnavailable, default 1, and maxSurge, default 0, the latter added so a new agent can start beside the old one on the same node 52,53. Surge is possible here and not for a StatefulSet because the slot that survives — the node — can be shared by two Pods; the name, which cannot, is not held. The price is that both agents briefly coexist on the host: a shared hostPath state file then has two writers, and a hostPort can only be bound by one of them, so surge suits agents written to tolerate a predecessor.

E5 rolls an agent across 200 nodes with a 15-second restart. With maxUnavailable: 1 the rollout takes 50.0 minutes; with 10% it takes 2.5. The surprising result is what does not change: in both cases the total uncovered time is 3,000 node-seconds, because every node is still without an agent for one restart. Raising maxUnavailable compresses the same gap into fewer, wider windows. Only surge removes it, at the cost of 20 extra Pods at peak for a 10% surge.

batch/v1 Job

Jobs

A Job creates one or more Pods and retries them until a specified number terminate successfully; then the Job is complete 17. Everything that came before served forever. A Job's lifetime has an end, so its controller holds a different invariant: not "n running" but "n succeeded".

Batch workloads

The documentation describes three shapes. A non-parallel Job runs one Pod to success. A Job with a fixed completion count runs until completions Pods succeed. A work-queue Job leaves completions unset, sets parallelism, and is done when any Pod succeeds and all have finished, the Pods coordinating among themselves over a queue 17; the work-queue shape is the batch pattern Burns describes for decoupling producers from a pool of interchangeable workers 54. Pods of a Job must use restartPolicy: Never or OnFailure 17. The Job controller tracks Pods with a finalizer, batch.kubernetes.io/job-tracking, so a Pod cannot be removed before it is counted 17.

Completion modes

completionMode: NonIndexed, the default, treats every success as interchangeable. Indexed gives each Pod a completion index from 0 to completions−1, exposed as an annotation, a label, the environment variable JOB_COMPLETION_INDEX, and the Pod hostname <job>-<index>; the Job is complete when every index has one success 17,55. With a headless Service and a matching subdomain, indexed Pods are addressable by DNS, which is how distributed-training frameworks find their peers 17,56. Indexed mode is the Job's version of a StatefulSet ordinal: the position survives replacement and nothing else does.

Parallel Jobs

parallelism caps concurrently running Pods; the controller may run fewer, for instance near the end of a fixed-count Job 17. More parallelism is not proportionally faster. E6 schedules 100 tasks with log-normally distributed durations (median 65 s) onto k parallel slots. At parallelism 10 the makespan is 95.4% efficient; at 100 it is only 26.5%, because the Job cannot finish before its slowest task, which here took 277 s. This is the tail-at-scale effect in batch form 57: past a point, parallelism buys waiting for stragglers.

Restart behaviour

With restartPolicy: OnFailure a failed container is restarted inside the same Pod by the kubelet, keeping the Pod's name, node and emptyDir contents; with Never the controller replaces the whole Pod 17,20. Replacement is throttled by an exponential back-off — 10 s, 20 s, 40 s and so on, capped at six minutes — so the default budget of six retries, backoffLimit: 6, spends 630 s in back-off alone before the Job is declared failed 17. activeDeadlineSeconds caps total run time and takes precedence over the retry budget 17.

By default a replacement Pod is created as soon as the failed one begins terminating, so for a while two Pods can exist for the same work. podReplacementPolicy: Failed waits until the old Pod has fully terminated; it reached general availability in v1.34, and is the only value allowed when a Pod failure policy is set 58. For an Indexed Job this is the switch that turns "the index survives" into "the index is held by one Pod at a time".

Job failure policy

backoffLimit is one budget for the whole Job. E6 shows how badly that scales. If each attempt fails independently with probability 0.05, a 50-completion Job exhausts the default budget 2.1% of the time, a 100-completion Job 28.0%, and a 200-completion Job 89.4%; from 128 completions upward it fails more often than not. At a 1% failure rate the same thing happens more slowly — a 500-completion Job still fails 24.6% of the time. The budget measures the size of the Job, not the health of any piece of it.

Kubernetes now offers three finer tools, all generally available. podFailurePolicy (GA in v1.31) matches failed Pods against ordered rules on exit codes or Pod conditions and chooses an action: FailJob, Ignore, Count or FailIndex 59,60,61. Ignoring the DisruptionTarget condition stops node drains and preemptions from consuming the budget. backoffLimitPerIndex with maxFailedIndexes (GA in v1.33) gives each index its own budget: a failed index is recorded in status.failedIndexes while the others keep running 62,63. In E6's 100-completion case with a per-index limit of one retry, the probability that at least one index fails is 22.1%, but the difference that matters is what survives it — 99 finished indexes and a precise list of the one that did not, instead of an aborted Job. When backoffLimitPerIndex is set, the Job-wide backoffLimit defaults to 2147483647 so that the per-index budgets, not the global one, govern 64.

Success policy

successPolicy (GA in v1.33) declares an Indexed Job successful when a named set of indexes, or a count of them, has succeeded, after which lingering Pods are terminated 65,66. It exists for leader–worker shapes, where the leader's success is the result and the workers have no independent completion.

Job cleanup and delegation

Finished Jobs and their Pods remain until deleted, so that logs and status can be read. ttlSecondsAfterFinished asks the TTL-after-finished controller to delete the Job, cascading to its Pods, a fixed time after it completes or fails 67. Since v1.35, spec.managedBy is generally available: a Job whose field names another controller is skipped by the built-in one, which is how MultiKueue mirrors a Job onto a worker cluster and syncs its status back 68,69,70. The field is immutable, so ownership of reconciliation cannot change hands mid-flight 68.

batch/v1 CronJob

CronJobs

A CronJob creates Jobs on a repeating schedule, and has been a stable API since v1.21 18. It owns Jobs as a Deployment owns ReplicaSets, one layer up, and what survives from one run to the next is only the schedule slot.

Scheduled Jobs

The documentation is candid that a CronJob creates a Job approximately once per scheduled time, and that in some circumstances two Jobs or none may be created for a slot; Jobs should therefore be idempotent 18,71. Since v1.32 each created Job carries a batch.kubernetes.io/cronjob-scheduled-timestamp annotation naming the slot it belongs to, which is the natural idempotency key 18. CronJob names should stay within 52 characters, because the controller appends 11 characters to form Job names and Job names are limited to 63 18.

Cron syntax

The schedule uses the five-field cron format — minute, hour, day of month, month, day of week — with the usual lists, ranges and steps, plus macros such as @hourly, @daily, @weekly, @monthly and @yearly 18. The five fields match POSIX crontab, though step values and macros are common extensions beyond the POSIX text 72. When both day-of-month and day-of-week are restricted, cron traditionally fires if either matches, a rule that surprises everyone once 72.

Concurrency policies

concurrencyPolicy decides what happens when a slot arrives while the previous Job is still running: Allow (the default) runs both, Forbid skips the new slot, and Replace stops the running Job and starts the new one 18. E7 runs a seven-minute job on a five-minute schedule for 24 hours. Allow started 288 Jobs with up to 2 running at once. Forbid completed 144 and skipped 144. Replace started 288 and completed 0: every run was killed by its successor. A policy that is safe when the job is fast becomes a silent total outage when the job slows down, and nothing in the CronJob's status says so.

Missed schedules

The controller checks schedules every ten seconds 18. If it was down, it counts how many slots were missed since the last scheduled time; if there are more than 100, it starts nothing and logs an error asking for startingDeadlineSeconds to be set or reduced 18. startingDeadlineSeconds both skips any slot that would start more than that many seconds late and restricts the missed-slot count to that window 18. E7 converts the 100-slot rule into outage lengths: about 101 minutes for an every-minute schedule, 8.4 hours for every five minutes and 101 hours for hourly. A deadline of 200 s means at most 4 every-minute slots can ever fall inside the window, so the limit becomes unreachable. Values below ten seconds risk the Job never being scheduled at all 18.

History limits

successfulJobsHistoryLimit and failedJobsHistoryLimit, defaults 3 and 1, cap how many finished Jobs are kept 18. Keeping one failed Job is enough to read the most recent failure and not enough to see a pattern; ship Job logs and events somewhere longer-lived if the pattern matters.

Time zones

Without timeZone, schedules are interpreted in the local time zone of the kube-controller-manager. timeZone accepts an IANA zone name and has been stable since v1.27; putting TZ= or CRON_TZ= inside the schedule string has been rejected by validation since v1.29 18,73,74. A zone with daylight-saving time contains local times that do not occur and times that occur twice. E8 matches daily schedules minute by minute against the 2026 zone rules: in America/New_York, 30 2 * * * has no matching instant on 8 March and 30 1 * * * matches twice on 1 November; in Europe/London the gap and the overlap both fall on 01:30 (29 March and 25 October). That is what a wall-clock matcher does; the Kubernetes documentation does not specify how the controller resolves these instants, so the robust choices are Etc/UTC or a slot outside 01:00–03:00 local time.

The rule that falls out is simple enough to use as a design check. A controller can run two copies of a member at once exactly when nothing it guarantees about that member must be unique. The Deployment's maxSurge, the DaemonSet's maxSurge and the Job's default TerminatingOrFailed replacement all exist where the surviving slots can be shared — none at all, or a node. The StatefulSet has no surge, because its name and single-writer volume cannot be shared; the Job grew podReplacementPolicy: Failed for workloads whose index must be held by one Pod at a time; the CronJob's Forbid is the same switch for schedule slots. Each "no overlap" option in the API marks a place where a slot became exclusive.

Choosing a workload resource is then a matter of answering five questions in order. Must the replacement have the same name, or be reachable at the same DNS name? Must it see the same data? Must it run on the same node — every node? Does it have a numbered place in a larger whole? Does it ever finish, and on what timetable? The first answer that is yes picks the resource; every further yes is a constraint that resource will impose on rollouts, scaling and recovery.

Appendix

Method and lab

The lab is a single Python 3 file using only the standard library, run at build time with seed 20260930. It writes a text transcript, reproduced below, and a JSON file from which this page's numbers and figures are drawn. Output was byte-identical across three runs under different PYTHONHASHSEED values; traversal orders are lists, never sets. The experiments are models of controller semantics as documented, not measurements of a cluster: E2 uses one-second ticks and instant termination; E3 assumes independent exponential failures; E4 and E5 assume fixed readiness and restart times; E6's probabilities assume independent attempts with a constant failure rate; E7 ignores the controller's ten-second polling; E8 is a naive wall-clock matcher against Python's zoneinfo rules, used to show where ambiguous instants fall, not to predict the controller's handling of them. Each simplification removes a source of noise that would blur the structural point and none changes its direction.

The plate coding is the author's: each mechanism was coded for which of the five properties its documentation guarantees across replacement, using the cited pages, and the ledger counts are derived from that coding.
