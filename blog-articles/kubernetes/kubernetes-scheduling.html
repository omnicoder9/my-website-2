Every Kubernetes scheduling feature is a way of telling one function what to look at. That function takes a single pending pod, looks at a snapshot of the cluster, picks a node, and moves on to the next pod without looking back. The interesting question about each feature is therefore not what it promises but how much of the cluster its promise depends on, and what happens to the promise after the pod is bound.

01 One pod, one moment

The default scheduler, kube-scheduler, watches for pods that have no node and assigns each one to a node where it can run1. It does so in two steps the documentation calls filtering and scoring: filtering finds the nodes where the pod could run at all, the feasible nodes, and scoring ranks them; the scheduler then picks the highest-ranked node, choosing at random among ties1. A pod that no node can take stays Pending until something in the cluster changes1. Under the plugin architecture introduced by the scheduling framework, each step is a set of extension points into which plugins are compiled, and the scheduling cycle, the part that decides, runs serially, one pod after another, while the binding cycle that records the decision may run concurrently2,3.

That last sentence carries the article's argument. A serial, one-pod-at-a-time decision is a greedy online algorithm: it commits the current pod to the best node it can see, without knowing which pods arrive next, and it does not revisit the commitment. Placing items into bins is NP-hard in general4, and even in one dimension simple greedy rules come with worst-case bounds rather than guarantees: First Fit can use about 1.7 times the optimal number of bins5. Kubernetes accepts that bargain because the alternative, deciding for many pods at once, costs time on the critical path of every deployment. Google's Borg made the same trade, examining machines in random order until it had found enough feasible ones to score6, and the shared-state design of Omega made scheduling decisions optimistic and resolved conflicts after the fact7. Kubernetes inherited both instincts8.

A greedy decision is cheap when it depends only on the pod and the node in front of it. It becomes expensive, and order-dependent, when it depends on other pods: whether they have arrived yet, where they went, what they will do next. The scheduling features in the reader's outline differ mostly along that axis, so the article measures them on it. Each feature becomes a plate: a short specification with a fixed set of four fields (what it decides, what it reads, where in the pod's life it acts, and what happens after binding) and a small gauge, collected at the end into a ledger. The gauge carries two codes.

The first is a coupling rung, K0 to K5, which records the widest state a correct decision has to read. K0 is the pod alone. K1 is the node's labels, metadata that changes rarely and never because of other pods. K2 is the node's mutable state: its taints, its conditions, and its remaining allocatable resources, which other pods consume. K3 is the set of co-tenants on the same node, identified by their labels. K4 is the set of co-tenants across a whole topology domain such as a zone. K5 is the whole cluster: every pod's priority, the queue, the window of nodes the scheduler happens to look at. The second code is a recheck mark: whether the condition is ever evaluated again after the pod is bound (N, never; E, yes, by evicting; V, only in the sense that the pod can later be chosen as a preemption victim). The track between them shows the nine stations of a pod's life at which the mechanism acts: queue, PreFilter, Filter, PostFilter, PreScore, Score, Reserve, Bind, and run time on the node.

The thesis, stated as a question, is the title: what does one pod at a time cost? The answer the ledger and the lab give is specific. The cost appears at K2, where resource consumption already makes outcomes depend on arrival order, and grows with every rung that ties a pod to other pods. Meanwhile the re-checking runs the other way: of the 32 plates that are predicates rather than machinery, only four are ever evaluated again after binding, all four are K2 taint mechanisms, and nothing that couples a pod to other pods is maintained at all.

The numbers in this article come from a small, deterministic model of the scheduler written for it in the Python standard library: a filter-score-normalise-select loop with the default plugin weights, a PostFilter preemption step, one traced cycle and eight experiments. Its source and complete output are in the appendix. It is a model of the documented behaviour, not the scheduler itself, and each simplification is named where it matters. Version-specific statements refer to Kubernetes v1.37, released on 26 August 2026 with 67 enhancements9.

02 The scheduler: a cycle, two lists and a coin

The scheduling cycle

A pod's life in the scheduler begins in a queue. Before a pod may enter the active queue, PreEnqueue plugins can hold it back; the user-facing form of that hook is schedulingGates, a list of names on the pod that keeps it in the SchedulingGated state until a controller removes them all10–12. The QueueSort plugin orders the active queue, and the default plugin, PrioritySort, orders by priority and then by arrival13. A pod that fails a cycle goes back to wait, and QueueingHint callbacks, stable since v1.34, let each plugin say which cluster events could make that pod schedulable, so that a rejected pod is retried when something relevant changes instead of on a timer2,14,15.

The cycle itself then runs a fixed sequence of extension points, drawn in Figure 12. PreFilter plugins compute per-pod state once, for example the label counts every topology rule needs. Filter plugins answer yes or no for each node. If no node passes, PostFilter plugins run; the default one is preemption. PreScore computes shared state for scoring, Score plugins rate each feasible node, and NormalizeScore rescales a plugin's ratings before they are combined. Reserve claims the node's resources in the scheduler's cache so that the next cycle sees them as used, and Permit can approve, deny or hold the pod, which is how gang schedulers keep a pod waiting for its siblings. Binding then runs on its own: PreBind for volumes and devices, Bind to write the Binding object to the API server, PostBind to clean up. A failure in binding un-reserves the node and returns the pod to the queue.

Filtering

Filtering is where most hard constraints live. The default profile enables, among others, NodeUnschedulable, NodeName, TaintToleration, NodeAffinity, NodePorts, NodeResourcesFit, the volume plugins, PodTopologySpread and InterPodAffinity13,16. NodeResourcesFit compares the pod's resource requests, not its actual usage, with the node's allocatable capacity minus the requests of pods already there17. That is the first place where other pods enter the decision: a node's remaining capacity is a sum over its tenants. The rung of filtering as a whole is therefore K2, and every rung above it is added by a specific plugin.

Scoring

Each Score plugin rates each feasible node; each plugin's ratings are normalised into the range 0 to 100; the scheduler multiplies each by the plugin's weight and sums2. In the default profile TaintToleration carries weight 3, NodeAffinity, InterPodAffinity and PodTopologySpread weight 2, and NodeResourcesFit, NodeResourcesBalancedAllocation and ImageLocality weight 113. NodeResourcesFit scores with the LeastAllocated strategy by default, preferring emptier nodes, and can be switched to MostAllocated or to a RequestedToCapacityRatio curve18. Because scores are normalised across the feasible set, a node's score is relative: the same node scores differently depending on which other nodes passed the filter. That is why this article puts scoring at K4 rather than K2.

The weights matter more than their small integers suggest. In the lab's traced cycle (Figure 2) a web pod with a preferred affinity for SSD nodes is placed on a node that the placement fills to 100 per cent, because the SSD preference contributes 2 × 100 = 200 points and an empty node can win at most 100 points from NodeResourcesFit. Node a1 totals 800 against 662.5 for the emptier b2. Nothing is wrong here; a preference stated with weight 80 out of 100 was honoured. But the outcome is set by weights the pod author never sees.

Node selection

In a large cluster the scheduler does not look at every node. The percentageOfNodesToScore setting tells it to stop filtering once it has found that share of the cluster as feasible nodes; left unset, a linear formula gives 50 per cent for a 100-node cluster and 10 per cent for a 5,000-node cluster, never below 5 per cent19. In the source the formula is 50 − n/125 in integer arithmetic, with a floor of 100 nodes, and each cycle starts where the previous one stopped, so successive pods see different windows20. Multiplying out gives a property the documentation does not state: the number of feasible nodes the scheduler stops at is not monotone in cluster size. It rises to a peak of 812 nodes at a cluster of 3,124, falls to 500 at 5,000, and reaches the 5 per cent floor at 5,625 nodes, after which it grows linearly again (Figure 3). Kubernetes' documented scalability envelope is 5,000 nodes and 150,000 pods21.

What does stopping early cost? Borg's answer was that a random sample of feasible machines is nearly as good as all of them6, and the load-balancing literature explains why: the best of a few random choices is already far better than one22, an idea Sparrow turned into a scheduler23. The lab tests it on 5,000 nodes of 16 CPUs with random existing load, placing 300 two-CPU pods with LeastAllocated scoring. Examining every node gives zero regret by construction. The adaptive 10 per cent filters 500 nodes per pod instead of 5,000, lands in the global best score tier 97.0% of the time, and loses 0.19 points on a 0-100 scale on average; at 1 per cent, which the floor turns into 100 nodes, the best-tier rate is 87.3%. The analytic picture agrees: the best of k uniformly sampled nodes sits, in expectation, in the top 1/(k+1) of the distribution, so 500 samples land in the top 0.2 per cent. The price of sampling is real only for scores that distinguish many nodes finely; a score with a few dozen distinct values, like whole-CPU free capacity, is saturated by a few hundred samples. Node selection is a K5 mechanism for a subtler reason than cost. Which nodes are examined depends on where the previous pod's cycle stopped, so a pod's outcome depends on the pods before it even when no constraint mentions them.

Scheduler profiles

One kube-scheduler process can host several profiles, each with its own schedulerName, plugin set, weights and arguments; a pod selects one through spec.schedulerName, and pods that name none get default-scheduler16,24. Profiles share the process's cache and queue, which avoids the races of running separate schedulers over the same nodes. Listing 1 configures a default profile with a cluster-wide zone spread and a second profile that packs batch pods with MostAllocated. Profile-level percentageOfNodesToScore overrides the global value25.

The scheduling framework

The framework is not a constraint but the grammar of all of them. It defines, for every extension point, what a plugin may return: a Filter plugin returns success or one of several failure codes, one of which, UnschedulableAndUnresolvable, tells the scheduler not to bother preempting for that node; a Score plugin returns an integer between MinNodeScore and MaxNodeScore; a Permit plugin may return Wait with a timeout2. Plugins are Go code compiled into a scheduler binary; out-of-tree plugins such as coscheduling and capacity scheduling are maintained in the scheduler-plugins project and built into a custom kube-scheduler26. Listing 2 is a schematic Score plugin of the simplest kind, one that reads only node labels.

Custom schedulers

Beyond profiles there are two further ways to change placement. A scheduler extender is an HTTP webhook consulted at fixed points, configured in the extenders list of the scheduler configuration25; it predates the framework and pays a network round trip per call. A second scheduler is a separate process that claims pods whose schedulerName names it27. It can use any algorithm: Poseidon integrated the Firmament flow-network scheduler this way28, and Firmament itself showed that treating all pending tasks as one min-cost flow problem can be fast enough for cluster scale29, an approach whose ancestry runs through Quincy30. Batch systems such as Volcano replace kube-scheduler for their workloads with gang scheduling and queue-level policies31. The cost is coordination. Two schedulers that both believe a node has room can both bind to it; the conflict is caught only when the kubelet's admission check refuses the second pod. That is Omega's optimistic concurrency without Omega's transactional cell state7, which is one reason the framework and profiles were built: to keep custom logic inside one process with one cache.

03 Node selection: rules about the node alone

The rules in this family read node labels and nothing else. That makes them the cheapest and most predictable constraints in the system, and it makes them the clearest illustration of the phrase that recurs in every Kubernetes affinity field name: IgnoredDuringExecution.

nodeName

Setting spec.nodeName is not a constraint on the scheduler; it removes the scheduler. The documentation is explicit that a pod with nodeName set is ignored by the scheduler and taken directly by the kubelet on the named node, which may reject it, for example for lack of resources, in which case the pod fails rather than waits32. There is no queue, no preemption and no retry. The field exists because binding is setting it: every scheduler's final act is to write a Binding that fills it in1. Listing 3 shows the direct form. Its rung is K0 because nothing is read at all.

nodeSelector and node labels

nodeSelector is a map of label keys to values; a node is eligible only if it carries every pair32. The labels themselves come from several authors. The kubelet sets well-known labels such as kubernetes.io/hostname, kubernetes.io/os and kubernetes.io/arch, cloud providers set topology.kubernetes.io/zone and topology.kubernetes.io/region, and operators add their own33. Because a node's kubelet could otherwise label its own node to attract sensitive workloads, the NodeRestriction admission plugin prevents kubelets from setting labels under the node-restriction.kubernetes.io/ prefix, which is therefore the safe namespace for isolation labels32,34.

Node affinity: required and preferred

Node affinity is the expressive form of the same idea. It reached beta in Kubernetes 1.6, alongside pod affinity, taints and tolerations, and support for running more than one scheduler35. Its required part holds a list of nodeSelectorTerms; the terms are alternatives (ORed), and the matchExpressions inside one term must all hold (ANDed). The operators are In, NotIn, Exists, DoesNotExist, Gt and Lt; NotIn and DoesNotExist give anti-affinity against nodes. If a pod sets both nodeSelector and required node affinity, both must be satisfied32,36. The preferred part is a list of weighted preferences, each weight between 1 and 100; for each node the scheduler adds the weights of the terms the node matches, and the NodeAffinity score plugin normalises those sums and contributes them with its own weight32. Listing 4 uses both parts.

The suffix in both field names, IgnoredDuringExecution, is a specification: if a node's labels change after the pod is scheduled, the pod keeps running32. Removing a node from a pool by relabelling it moves nothing; the label is consulted again only by the next pod's cycle. The ledger codes all of these plates N. That is a reasonable design for labels, which describe hardware and location and rarely change; the cost of re-checking would be borne on every label edit for a benefit that seldom arises. It becomes a less obvious design when the same suffix is attached, a section later, to rules about other pods, which change all the time.

Because labels never depend on other pods, a label rule cannot by itself make an outcome depend on arrival order. The lab checks this directly in experiment E2: when 120 random pod sets, each pod pinned to a zone by nodeSelector and no zone asked for more than half its capacity, are each scheduled in 30 random orders, no order leaves any pod Pending (0.0% of runs). Labels are the one family where the greedy decision is also the right one.

04 Pod affinity and anti-affinity: rules about the neighbours

Inter-pod affinity and anti-affinity constrain a pod relative to pods already running, not to nodes. A rule names a label selector, which picks out the relevant pods, and a topologyKey, which names a node label; all nodes that share a value of that label form one topology domain. Affinity says: place this pod in a domain that already contains a matching pod. Anti-affinity says: place it in a domain that contains none32.

Co-location and separation

Co-location serves latency and locality: a web tier in the same zone as its cache, a sidecar workload on the same node as the service it inspects. Separation serves availability: no two replicas of a quorum on one node, or one replica per zone. Listing 5 expresses both at once. The rules apply in both directions where it matters. The design that introduced them specified that the required anti-affinity of a pod already running is honoured when placing a newcomer, so a pod can be refused because an existing pod declared it unwelcome37. The lab's InterPodAffinity filter models that symmetry. For affinity there is a documented special case: if no pod anywhere matches the selector and the incoming pod matches its own selector, the first member of a self-affine group may be placed anywhere, since otherwise no group could ever start32.

Topology domains

The topologyKey is what turns a rule about neighbours into a rule of a certain size. With kubernetes.io/hostname a domain is one node and the rule reads the node's tenants: rung K3. With topology.kubernetes.io/zone a domain is a zone, and deciding whether one node is acceptable requires counting matching pods on every node in its zone: rung K4. The documentation warns that inter-pod affinity and anti-affinity need substantial processing and are not recommended in clusters larger than several hundred nodes, and that every node must carry the topology label consistently, since a node without it simply belongs to no domain32. The matchLabelKeys field, beta since v1.31, narrows the selector to pods sharing the incoming pod's values for given keys, so that during a rolling update the old revision's replicas do not count against the new one38.

Required and preferred rules

Required rules are filters, and as filters they have a hard arithmetic consequence. A required anti-affinity against one's own replicas with a hostname key allows at most one replica per node; with a zone key, at most one per zone. Experiment E3 shows the cap exactly: on six nodes in three zones, hostname separation leaves replica 7 onward Pending, and zone separation leaves replica 4 onward Pending; at 12 replicas that is 6 and 9 Pending pods respectively (Figure 4). The preferred form, a score, places all 12 and spreads them as evenly as its weight allows, at most 4 per zone.

A preferred rule's weight (1 to 100) sets its strength only within the InterPodAffinity plugin; across plugins, InterPodAffinity's own weight of 2 competes with every other score13. Preferred rules therefore guarantee nothing, and required rules guarantee only at placement time. The field names say IgnoredDuringExecution here too: if the cache the web tier was co-located with is rescheduled to another zone, the web pods stay where they are. The rule was true of the cluster for one instant.

The coupling has a second consequence the documentation does not dwell on: order dependence. Whether a pod with a hostname anti-affinity can be placed depends on which nodes its siblings have already taken, and therefore on which other pods have already filled the remaining nodes. Section 8 measures how much.

05 Taints and tolerations: the rule that keeps checking

Affinity is a property of the pod that attracts it to nodes. A taint is the opposite: a property of the node that repels pods, unless a pod carries a matching toleration39. A taint has a key, an optional value and an effect; a toleration matches it with the Equal operator (key and value equal) or the Exists operator (key present, value ignored), and a toleration with an empty key and Exists tolerates everything39. A toleration permits; it never attracts. A pod that tolerates a dedicated node's taint is merely allowed there, and will land elsewhere unless something else steers it.

The three effects

NoSchedule keeps new pods off unless they tolerate the taint; pods already running are untouched. PreferNoSchedule is the soft version, a score: the scheduler tries to avoid the node39. In the default profile that score has the highest weight of any plugin, 313. NoExecute is different in kind. It affects pods already running: a pod that does not tolerate a NoExecute taint is evicted as soon as the taint appears; a pod that tolerates it without tolerationSeconds stays indefinitely; a pod that tolerates it with tolerationSeconds stays for that many seconds and is then evicted39. Since v1.29 the component that enforces this, the taint eviction controller, is separate from the node lifecycle controller, and that decoupling became stable in v1.3440.

NoExecute is the only scheduling predicate in this article that is evaluated for the whole life of the pod. Everything else is checked once. The ledger's matrix shows this as four E marks, all in the taint family and all at rung K2: node state, not other pods.

Node condition taints

The node lifecycle controller turns node conditions into taints. Nodes that are not ready or unreachable receive node.kubernetes.io/not-ready and node.kubernetes.io/unreachable with effect NoExecute; nodes under memory, disk or PID pressure, nodes with an unavailable network and cordoned nodes receive NoSchedule taints such as node.kubernetes.io/memory-pressure and node.kubernetes.io/unschedulable33,39. This is how a failed node's pods eventually move: the condition becomes a taint, the taint evicts, and the owning controller creates replacements that go through the scheduler afresh41. Pressure on a live node is handled separately, by the kubelet's own node-pressure eviction, which ranks pods by whether their usage exceeds requests and then by priority42.

The eviction timing is set by tolerations most pods never declare. The DefaultTolerationSeconds admission plugin adds tolerations for the not-ready and unreachable taints with tolerationSeconds: 300 to every pod that does not already have them34. DaemonSet pods instead receive NoExecute tolerations for those taints with no time limit, so they are never evicted for those conditions43. The default therefore means that an ordinary pod stays bound to a dead node for five minutes before its replacement is created.

That five minutes is a trade between two errors: evicting pods from a node that was only briefly unreachable, and leaving them on a node that is really gone. Experiment E5 makes the trade explicit under openly illustrative assumptions (two transient NotReady episodes per node per day, exponentially distributed with a 90-second mean). With the default 300 seconds, a transient blip evicts with probability 0.036 and costs 0.071 spurious evictions per node-day; at 30 seconds the same node suffers 1.43 per day (Figure 5). The inputs are invented; the shape is not. A shorter tolerationSeconds, as in Listing 6, buys faster recovery from real failures at an exponentially rising rate of false ones, and the right value depends on how flaky the node-to-control-plane path is in a particular environment.

Dedicated nodes

The documentation's dedicated-nodes recipe needs two mechanisms because each does half the job: a taint keeps other pods off, and a label with node affinity keeps the dedicated pods on39. Listing 6 shows both, for a GPU pool. With NoSchedule, pods that were on the node before it was tainted stay; switching the taint to NoExecute would evict them. Since v1.35 tolerations can also compare numerically, with Gt and Lt operators in alpha, so that a pod can tolerate, say, a node whose advertised service level is above a threshold44. Dynamic resource allocation, generally available since v1.34, gives devices their own claim-and-allocate path through the scheduler rather than forcing them into labels and taints45,46.

06 Topology spread constraints: rules about the count

Topology spread constraints replace the yes-or-no of anti-affinity with a number. A constraint names a topologyKey, a label selector, a maxSkew and a whenUnsatisfiable policy, and asks that matching pods be spread across the domains so that no domain exceeds the emptiest eligible domain by more than maxSkew47,48. It was introduced to express what anti-affinity could not: three replicas per zone are fine, as long as no zone has five more than another49.

Zones, nodes and failure domains

The same mechanism spreads across whatever a label names. With topology.kubernetes.io/zone it spreads across availability zones, so that a zone outage takes a bounded share of the replicas; with kubernetes.io/hostname it spreads across nodes; with a rack or power-feed label it spreads across any failure domain an operator chooses to describe47,50. Constraints can be combined, and a pod must satisfy all of its DoNotSchedule constraints at once. When a pod declares no constraints and the cluster has not been configured otherwise, the scheduler applies internal defaults: a soft spread with maxSkew 3 across hostnames and 5 across zones47. Listing 1 shows how a cluster operator replaces them.

maxSkew, topologyKey and whenUnsatisfiable

For each candidate node the scheduler counts matching pods in that node's domain, adds one if the incoming pod matches its own selector, and subtracts the global minimum over eligible domains; the node passes if the result is at most maxSkew47. Eligible domains are those containing at least one node that carries the topology key and, by default, satisfies the pod's node affinity (nodeAffinityPolicy: Honor); taints are ignored in that count by default (nodeTaintsPolicy: Ignore), a choice KEP-3094 made configurable51,52. minDomains handles the case of too few domains: while fewer eligible domains exist than minDomains, the global minimum is taken as zero, which forces pods to wait for new domains instead of piling into the existing ones47,53. matchLabelKeys restricts counting to the current rollout, as it does for affinity54. whenUnsatisfiable: DoNotSchedule makes the constraint a filter; ScheduleAnyway makes it a score that prefers nodes reducing skew47. Listing 7 uses most of these fields.

The definition hides a trap that experiment E4 makes visible. Skew is measured against the emptiest domain, so the smallest domain governs the whole spread. Thirty-six one-CPU replicas on a cluster with 36 CPUs, where two zones have four four-CPU nodes and the third has one, cannot all run under maxSkew: 1: once the small zone is full at four replicas, the others may hold only five each. The lab places 14 of 36 and leaves the rest Pending; maxSkew 2 places 16, and maxSkew 3 places 18. ScheduleAnyway places all 36 and ends with a skew of 12 (Figure 6). Spread constraints are rules about counts across a domain, which makes them K4, and they inherit every inequality in the underlying capacity.

The second trap is time. The documentation lists among the known limitations that there is no guarantee the constraints remain satisfied when pods are removed: scaling a Deployment down can leave the distribution imbalanced, and rebalancing is left to tools such as the descheduler47,55. The ReplicaSet controller's scale-down ranking does not look at zones. Among otherwise equal pods it deletes first those on nodes running more replicas of the same set56, a node-level heuristic. E4 measures both cases. If 15 replicas spread 5/5/5 are scaled to 9 by deletions that ignore placement, the result violates maxSkew: 1 with probability 0.80, computed exactly by enumerating the hypergeometric outcomes. If deletions follow the node-level heuristic and the zones are equal, the balance survives; if the zones have two, three and four nodes, the same heuristic leaves 2/3/4 every time, a skew of 2 (Figure 7). The scheduler never revisits either result.

07 Priority and preemption: the rule that reaches into other pods

Every mechanism so far decides where a pod goes. Priority decides which pod goes first, and preemption decides which other pods leave to make room. They are the only scheduling mechanisms that act on pods other than the one being scheduled, which makes them K5 in this article's terms: correct behaviour depends on the priorities of everything in the cluster.

PriorityClasses and pod priority

A PriorityClass is a cluster-scoped object that maps a name to an integer value; user-defined classes may use any 32-bit integer up to one billion, and larger values are reserved for the built-in system classes57–59. Two such classes ship with every cluster, system-cluster-critical and system-node-critical, for components the cluster cannot run without57. One class may be marked globalDefault; pods naming no class get its value, or zero if there is none57. The Priority admission plugin resolves priorityClassName into the pod's integer priority field at creation, so changing a class later does not change running pods34,57. Listing 8 defines three classes.

Priority has three effects. It orders the scheduling queue, so that higher-priority pending pods are attempted first57. It entitles a pod to preempt lower-priority pods. And it enters the kubelet's ranking when a node under resource pressure must evict pods42.

Preemption

When no node passes the filters, the DefaultPreemption PostFilter plugin looks for a node on which removing lower-priority pods would let the pending pod fit57,60. For each candidate node it removes all lower-priority pods, checks that the pod would then pass every filter, and adds back as many of the removed pods as it can, highest priority first, trying first to spare pods whose eviction would violate a PodDisruptionBudget61,62. Among candidate nodes it prefers, in order, the fewest PDB violations, the lowest highest-victim priority, the smallest sum of victim priorities, the fewest victims, and then the most recently started victims61. The victims are deleted with their normal graceful termination period, and the preemptor's nominatedNodeName is set to the chosen node; the pod is not bound there yet, and if another node frees up first the scheduler may place it elsewhere57. PodDisruptionBudgets are honoured on a best-effort basis: preemption tries to avoid violating them but will if it must63, and the scheduler does not preempt across nodes, so a pod whose required affinity points at a lower-priority pod on another node gains nothing from evicting it57.

The candidate ranking is lexicographic, and the order of its criteria is a policy. Experiment E6 fills an eight-node cluster almost completely with pods of priority 100, 200 or 300 and then admits a priority-1000 pod needing four to six CPUs, 60 times over. The default rule chose 1.78 victims on average where 1.40 would have sufficed, evicting more pods than necessary in 35% of trials, because it minimises the highest victim priority before the victim count. In those trials the highest victim priority averaged 110: the rule protected the 200s and 300s by sacrificing more 100s. When the evicted pods re-enter the queue they may preempt in turn; in 3.3% of arrivals they did, for 1.83 pods disrupted per high-priority arrival. With a budget of zero on roughly 30 per cent of pods, the PDB-aware ranking evicted 0 protected pods where a budget-blind ranking would have evicted 33 (Figure 8).

Non-preempting priorities

A class with preemptionPolicy: Never keeps the queue precedence of its value without the right to evict57,64. It suits batch work that should start before other batch work when capacity frees up but should never displace anything running. Such pods can still be preempted by preempting classes above them. The design reflects the distinction the rest of this section turns on: priority as order, and priority as power.

Scheduling fairness

kube-scheduler has no notion of fair share. Priority is a total order on pods; within a priority level the queue is ordered by arrival13. Nothing stops a steady stream of high-priority pods from starving everything below it, and the documentation warns that a higher-priority pod can be placed ahead of a lower-priority one even after the lower one was nominated for a node57. Fairness across tenants is the province of admission-level systems. Kueue, a SIG Scheduling project, decides when a job may start against quotas and cohorts, leaving placement to kube-scheduler65,66; the research lineage includes dominant resource fairness, which generalises max-min fairness to several resource types67.

The cost priority imposes on the classes below it is a classical queueing result. For a single server with non-preemptive priorities, Cobham's formula gives the low class a mean wait inflated by the factor 1/((1 − ρH)(1 − ρ)), where ρH is the high class's load and ρ the total68,69. Experiment E7 first checks its queue simulator against that formula at ρ = 0.8 (simulated 6.89 against Cobham's 6.67 for the low class) and then models a 20-slot cluster with half the work at high priority. At ρ = 0.95, non-preemptive priority holds the low class's mean wait to 1.54 service times. Preemption with restart, which is what evicting a pod without checkpointing amounts to, drives it to 62.4, because the evicted work is redone: 5.3% of all work is wasted, lifting the effective load to 1.004, past capacity, so the low class has no steady state at all (Figure 9). Below about ρ = 0.7 the three policies are indistinguishable. Near saturation preemption converts a scheduling preference into lost capacity.

Workload-aware scheduling

The newest scheduling work in Kubernetes responds directly to the one-pod-at-a-time limit. Workload-aware scheduling, introduced in v1.35, adds Workload and PodGroup APIs so that a group of pods can be scheduled all-or-nothing70,71. In v1.37 those APIs, gang scheduling, workload-aware preemption and shared resource claims for pod groups graduated to beta, and a new CompositePodGroup API expresses multi-level topology constraints and preemption policies for heterogeneous groups such as those managed by JobSet and LeaderWorkerSet72–76. v1.37 also added alpha support for preempting pods to make room for an in-place resize of a running pod77. These are, in this article's vocabulary, attempts to let one decision read and commit for many pods at once.

08 What one pod at a time costs

The plates describe what each mechanism reads. Experiment E2 measures what reading it one pod at a time costs. The design holds the cluster fixed (six eight-CPU nodes in three zones) and generates 120 pod sets for each rung, each scheduled in 30 random arrival orders with the default weights. Every pod set is first checked by an exhaustive search that schedules it under exactly the same incremental filters in some order, so every set is known to be schedulable; any pod left Pending is stranded by the order and the greedy choice, not by lack of room. The rungs add one coupling at a time. K1 pods carry only zone nodeSelectors at half capacity. K2 pods carry no constraints but fill 83 to 92 per cent of the cluster's CPU. K3 adds four pods with a required hostname anti-affinity. K4 adds six more with a DoNotSchedule zone spread at maxSkew 1.

Figure 10 gives the result. Under the default LeastAllocated scoring, no order strands a pod at K1, 41.5% of orders strand at least one pod at K2, 51.1% at K3 and 56.5% at K4. Every single K2-to-K4 pod set has at least one stranding order. The K2 figure is mostly a scoring effect: LeastAllocated is a worst-fit rule, which spreads pods evenly and leaves every node with a fragment too small for the next large pod. Switching the same runs to MostAllocated, a best-fit rule, almost removes it (0.14%), and with packing out of the way the coupling shows through clearly: 5.2% at K3 and 34.6% at K4, more than two hundred times the K2 rate. Experiment E8 isolates the packing effect: on ten eight-CPU nodes, after 30 small pods the spreading strategy can no longer fit a six-CPU pod anywhere, while the packing strategy fits it until about 55 small pods and keeps 4.9 nodes empty at the 30-pod mark, nodes a cluster autoscaler could remove (Figure 11). Borg used a hybrid of best-fit and worst-fit to limit such stranded resources6, and multi-resource packing heuristics improve on both78.

Preemption is the scheduler's mechanism for repairing a bad greedy decision after the fact, and the lab tests whether it does. In 1,600 K4 runs, the constrained pods were given priority 1000 and everything else 100. Without priorities the runs averaged 0.598 Pending pods each, 0.449 of them constrained. With priorities and preemption, no constrained pod was ever left Pending, and the low-priority pods left Pending averaged 0.605. Preemption did not reduce the stranding. It chose who was stranded. That is often exactly what an operator wants, but it is a reallocation, not a repair.

These numbers are the measured half of the article's answer. The other half is in the ledger: the higher a mechanism's rung, the less it is maintained. Rung K1 rules are never re-checked, harmlessly, because labels rarely change. Rung K2 contains the only rules that are re-checked, the NoExecute taints. Rungs K3 and K4, which tie a pod to other pods, are checked once, at placement, and never again, even though the pods they refer to come and go constantly. Rung K5 acts on other pods but only to remove them. The coupling that makes a decision order-dependent is also the coupling that no component keeps true afterwards. Out-of-band tools fill the gap: the descheduler evicts pods that violate spread or affinity rules so that they can be rescheduled55, and simulators such as kube-scheduler-simulator let operators see what a configuration would do before it does it79. The design is consistent with the lesson of Borg and Omega that a central scheduler should stay simple and fast and leave richer policy to layers above it8,80. It is a cost, and it is a choice.

FILTERS = ("NodeAffinity", "TaintToleration", "NodeResourcesFit", "InterPodAffinity", "PodTopologySpread")


def filter_node(pod, node, pre, why=None):
    checks = (("NodeAffinity", nodeaff_ok(pod, node)),
              ("TaintToleration", taints_ok(pod, node)),
              ("NodeResourcesFit", fit_ok(pod, node)),
              ("InterPodAffinity", interpod_ok(pod, node, pre)),
              ("PodTopologySpread", spread_ok(pod, node, pre)))
    for name, ok in checks:
        if not ok:
            if why is not None:
                why[name] = why.get(name, 0) + 1
            return False
    return True


# ---- scoring: raw -> normalised [0,100] -> weighted sum (default weights)
WEIGHTS = {"TaintToleration": 3, "NodeAffinity": 2, "NodeResourcesFit": 1,
           "NodeResourcesBalancedAllocation": 1, "InterPodAffinity": 2, "PodTopologySpread": 2}


def score_nodes(pod, feasible, pre, strategy="least", detail=False):
    raw = {k: [] for k in WEIGHTS}
    for n in feasible:
        raw["TaintToleration"].append(sum(1 for t in n.taints if t[2] == "PreferNoSchedule"
                                          and not tolerates(pod.tolerations, t)))
        raw["NodeAffinity"].append(sum(w for w, t in pod.pref_aff if term_match(n.labels, t)))
        fc = (n.ucpu + pod.cpu) / n.cpu
        fm = (n.umem + pod.mem) / n.mem if n.mem else fc
        if strategy == "least":
            raw["NodeResourcesFit"].append(((1 - fc) + (1 - fm)) * 50)
        else:
            raw["NodeResourcesFit"].append((fc + fm) * 50)
        raw["NodeResourcesBalancedAllocation"].append((1 - abs(fc - fm) / 2) * 100)
        s = 0
        for w, tk, c in pre.affp:
            s += w * c.get(n.labels.get(tk), 0)
        for w, tk, c in pre.antip:
            s -= w * c.get(n.labels.get(tk), 0)
        raw["InterPodAffinity"].append(s)
        sp = 0
        for ms, tk, when, c, selfm, mind in pre.spread:
            sp += c.get(n.labels.get(tk), 0)
        raw["PodTopologySpread"].append(sp)
    norm = {}
    for k, v in raw.items():
        if not v:
            norm[k] = v
            continue
        if k == "TaintToleration":           # reverse: fewer intolerable taints is better
            mx = max(v)
            norm[k] = [100.0 if mx == 0 else 100 - x * 100 / mx for x in v]
        elif k == "NodeAffinity":
            mx = max(v)
            norm[k] = [0.0 if mx == 0 else x * 100 / mx for x in v]
        elif k == "InterPodAffinity":
            lo, hi = min(v), max(v)
            norm[k] = [0.0 if hi == lo else (x - lo) * 100 / (hi - lo) for x in v]
        elif k == "PodTopologySpread":      # simplified: fewer matching pods in the domain is better
            lo, hi = min(v), max(v)
            norm[k] = [100.0 if hi == 0 else 100 * (hi + lo - x) / hi for x in v]
        else:
            norm[k] = list(v)
    tot = [sum(WEIGHTS[k] * norm[k][i] for k in WEIGHTS) for i in range(len(feasible))]
    if detail:
        return tot, raw, norm
    return tot


def num_feasible_to_find(n_all, pct=0):
    """kube-scheduler numFeasibleNodesToFind (adaptive when pct == 0)."""
    if n_all < 100:
        return n_all
    p = pct
    if p == 0:
        p = 50 - n_all // 125
        if p < 5:
            p = 5
    k = n_all * p // 100
    return 100 if k < 100 else k


def schedule_one(cl, pod, rng, strategy="least", pct=None, stats=None):
    pre = Pre(cl, pod)
    n_all = len(cl.nodes)
    want = n_all if pct is None else num_feasible_to_find(n_all, pct)
    feasible, why, seen = [], {}, 0
    start = cl.next_start
    for i in range(n_all):
        n = cl.nodes[(start + i) % n_all]
        seen += 1
        if filter_node(pod, n, pre, why):
            feasible.append(n)
            if len(feasible) >= want:
                break
    cl.next_start = (start + seen) % n_all
    if stats is not None:
        stats["seen"] = seen
        stats["why"] = why
    if not feasible:
        return None
    tot = score_nodes(pod, feasible, pre, strategy)
    best = max(tot)
    ties = [n for n, s in zip(feasible, tot) if s == best]
    pick = ties[0] if len(ties) == 1 else ties[rng.randrange(len(ties))]
    if stats is not None:
        stats["score"] = best
    return pick


# ---- preemption (DefaultPreemption, simplified: no nominated-pod bookkeeping, no
#      graceful-termination delay, single-node victims only as in the real plugin)
UNRESOLVABLE = ("NodeAffinity", "TaintToleration")


def preempt(cl, pod, budgets=None):
    if not pod.preempt:
        return None
    cands = []
    for n in cl.nodes:
        if not nodeaff_ok(pod, n) or not taints_ok(pod, n):
            continue
        lower = [q for q in n.pods if q.priority < pod.priority]
        if not lower:
            continue
        for q in lower:
            cl.unbind(q)
        pre = Pre(cl, pod)
        if not filter_node(pod, n, pre):
            for q in lower:
                cl.bind(q, n)
            continue
        lower.sort(key=lambda q: (-q.priority, q.t0, q.name))
        used = {}

        def violates(q):
            if budgets is None or q.pdb is None:
                return False
            return used.get(q.pdb, 0) >= budgets.get(q.pdb, 0)

        viol = [q for q in lower if violates(q)]
        nonv = [q for q in lower if not violates(q)]
        victims = []
        for group in (viol, nonv):
            for q in group:
                cl.bind(q, n)
                if filter_node(pod, n, Pre(cl, pod)):
                    continue
                cl.unbind(q)
                victims.append(q)
                if q.pdb is not None:
                    used[q.pdb] = used.get(q.pdb, 0) + 1
        nviol = 0
        if budgets is not None:
            for g, u in used.items():
                nviol += max(0, u - budgets.get(g, 0))
        for q in victims:
            cl.bind(q, n)
        cands.append((nviol, max(q.priority for q in victims), sum(q.priority for q in victims),
                      len(victims), cl.nodes.index(n), n, victims))
    if not cands:
        return None
    cands.sort(key=lambda c: c[:5])
    c = cands[0]
    return c[5], c[6], c[0]


def place_all(cl, pods, rng, strategy="least", use_preempt=False):
    pending = []
    for p in pods:
        n = schedule_one(cl, p, rng, strategy)
        if n is None and use_preempt:
            r = preempt(cl, p)
            if r:
                node, victims, _ = r
                for q in victims:
                    cl.unbind(q)
                    pending.append(q)
                cl.bind(p, node)
                continue
        if n is None:
            pending.append(p)
        else:
            cl.bind(p, n)
    return pending

ZONES = ("a", "b", "c")


def mk_cluster(cpu=8):
    nodes = []
    for zi, z in enumerate(ZONES):
        for j in range(2):
            nm = f"{z}{j+1}"
            nodes.append(Node(nm, {"topology.kubernetes.io/zone": z, "kubernetes.io/hostname": nm}, cpu))
    return Cluster(nodes)


def gen_instance(rng, rung):
    cap = 48
    target = 24 if rung == 1 else rng.randint(40, 44)
    pods, tot, i = [], 0, 0
    sizes = [1, 2, 2, 3, 3, 4]
    zone_load = {z: 0 for z in ZONES}
    if rung >= 3:
        for k in range(4):
            s = rng.choice((2, 3, 4))
            pods.append(Pod(f"A{k}", s, labels={"app": "a"},
                            anti_req=[({"app": "a"}, "kubernetes.io/hostname")]))
            tot += s
    if rung >= 4:
        for k in range(6):
            s = rng.choice((1, 2, 3))
            pods.append(Pod(f"B{k}", s, labels={"app": "b"},
                            spread=[(1, "topology.kubernetes.io/zone", "DoNotSchedule", {"app": "b"}, 0)]))
            tot += s
    while tot < target:
        s = rng.choice(sizes)
        if tot + s > target:
            s = target - tot
        p = Pod(f"g{i}", s, labels={"app": "g"})
        if rung == 1:
            # labels only: each pod pins a zone, but no zone is asked for more than half its capacity
            room = max(8 - zone_load[z] for z in ZONES)
            if room <= 0:
                break
            s = min(s, room)
            p.cpu = s
            ok = [z for z in ZONES if zone_load[z] + s <= 8]
            z = rng.choice(ok)
            zone_load[z] += s
            p.node_selector = {"topology.kubernetes.io/zone": z}
        pods.append(p)
        tot += s
        i += 1
    return pods


def witness(pods, budget=200000):
    """DFS for ANY order+placement that schedules everything under the same incremental filters."""
    cl = mk_cluster()
    order = sorted(pods, key=lambda p: (-(bool(p.anti_req) or bool(p.spread)), -p.cpu, p.name))
    calls = [0]

    def dfs(i):
        if i == len(order):
            return True
        calls[0] += 1
        if calls[0] > budget:
            raise TimeoutError
        p = order[i]
        pre = Pre(cl, p)
        tried = set()
        for n in cl.nodes:
            key = (n.ucpu, n.labels["topology.kubernetes.io/zone"] if (p.spread or p.node_selector) else "",
                   tuple(sorted(q.labels.get("app") for q in n.pods if q.labels.get("app") in ("a",))))
            if key in tried:
                continue
            if filter_node(p, n, pre):
                tried.add(key)
                cl.bind(p, n)
                if dfs(i + 1):
                    cl.unbind(p)
                    return True
                cl.unbind(p)
        return False
    try:
        return dfs(0)
    except TimeoutError:
        return None

            v2 += 1
    log(f"  same scale-down, deleting from the most-loaded node first: P(skew > 1) = {v2/T:.4f}  ({T} trials)")
    # asymmetric zones: 2/3/4 nodes, 15 replicas placed 5/5/5 by zone spread, round-robin inside zones
    layout = {"a": [3, 2], "b": [2, 2, 1], "c": [2, 1, 1, 1]}
    v3 = 0
    fin = {}
    for _ in range(T):
        per_node = [[z, c] for z in ZONES for c in layout[z]]
        for _ in range(6):
            mx = max(c for _, c in per_node)
            cand = [i for i, (_, c) in enumerate(per_node) if c == mx]
            per_node[cand[r.randrange(len(cand))]][1] -= 1
        pz = tuple(sum(c for zz, c in per_node if zz == z) for z in ZONES)
        fin[pz] = fin.get(pz, 0) + 1
        if max(pz) - min(pz) > 1:
            v3 += 1
    log(f"  asymmetric zones (2/3/4 nodes, node loads a=3,2 b=2,2,1 c=2,1,1,1): node-ranked deletion"
        f" P(skew > 1) = {v3/T:.4f}  outcomes {dict(sorted(fin.items()))}")
    OUT["e4_drift"] = {"p_uniform": p_exact, "dist": {str(k): v / tot for k, v in sorted(dist.items())},
                       "p_node_ranked": v2 / T, "p_node_ranked_asym": v3 / T,
                       "asym_outcomes": {"/".join(map(str, k)): v / T for k, v in sorted(fin.items())}}

def e6():
    log("=" * 72)
    log("E6  preemption: the victim rule against the fewest-victims rule, and cascades")
    log("=" * 72)
    r = random.Random(SEED + 6)
    TR = 60
    more, chosen_tot, min_tot, cpu_over, cascades, disrupted = 0, 0, 0, 0, 0, 0
    prio_saved = 0
    for t in range(TR):
        nodes = [Node(f"n{i}", {"kubernetes.io/hostname": f"n{i}", "topology.kubernetes.io/zone": ZONES[i % 3]}, 8)
                 for i in range(8)]
        cl = Cluster(nodes)
        k = 0
        for n in nodes:
            while True:
                s = r.choice((1, 1, 2, 2, 3))
                if n.ucpu + s > n.cpu - r.choice((0, 0, 1)):
                    break
                q = Pod(f"l{k}", s, priority=r.choice((100, 200, 300)))
                q.t0 = k
                cl.bind(q, n)
                k += 1
        hp = Pod("H", r.choice((4, 5, 6)), priority=1000)
        res = preempt(cl, hp)
        if not res:
            continue
        node, victims, _ = res
        # brute force: fewest victims on any single node
        best_min = 99
        for n in nodes:
            need = hp.cpu - (n.cpu - n.ucpu)
            if need <= 0:
                best_min = 0
                continue
            sizes = sorted((q.cpu for q in n.pods), reverse=True)
            acc, c = 0, 0
            for s in sizes:
                acc += s
                c += 1
                if acc >= need:
                    break
            if acc >= need:
                best_min = min(best_min, c)
        chosen_tot += len(victims)
        min_tot += best_min
        if len(victims) > best_min:
            more += 1
        cpu_over += sum(q.cpu for q in victims) - (hp.cpu - (node.cpu - node.ucpu))
        prio_saved += max(q.priority for q in victims)
        # cascade: victims re-enter the queue with preemption enabled
        for q in victims:
            cl.unbind(q)
        cl.bind(hp, node)
        queue = sorted(victims, key=lambda q: -q.priority)
        disrupted_here = len(victims)
        steps = 0
        while queue and steps < 50:
            steps += 1
            q = queue.pop(0)
            nn = schedule_one(cl, q, r)
            if nn:
                cl.bind(q, nn)
                continue
            rr = preempt(cl, q)
            if rr:
                n2, v2, _ = rr
                for x in v2:
                    cl.unbind(x)
                cl.bind(q, n2)
                disrupted_here += len(v2)
                queue += v2
                queue.sort(key=lambda x: -x.priority)
        if disrupted_here > len(victims):
            cascades += 1
        disrupted += disrupted_here
    d = {"trials": TR, "mean_victims": chosen_tot / TR, "mean_min_victims": min_tot / TR,
         "share_more_than_min": more / TR, "mean_cpu_over": cpu_over / TR,
         "cascade_share": cascades / TR, "disrupted_per_arrival": disrupted / TR,
         "mean_top_victim_priority": prio_saved / TR}
    OUT["e6"] = d
    log(f"  trials={TR}  victims chosen (mean)={d['mean_victims']:.2f}  fewest possible (mean)={d['mean_min_victims']:.2f}"
        f"  trials evicting more than the minimum={100*d['share_more_than_min']:.1f}%")
    log(f"  evicted cpu beyond the shortfall (mean)={d['mean_cpu_over']:.2f}  highest victim priority (mean)={d['mean_top_victim_priority']:.1f}")
    log(f"  cascades: arrivals whose victims went on to preempt others={100*d['cascade_share']:.1f}%"
        f"  pods disrupted per high-priority arrival={d['disrupted_per_arrival']:.2f}")
    # PDB: one protected group with budget 0
    r = random.Random(SEED + 61)
    viol_aware = viol_blind = 0
    TR2 = 60
    for t in range(TR2):
        nodes = [Node(f"n{i}", {"kubernetes.io/hostname": f"n{i}"}, 8) for i in range(6)]
        cl = Cluster(nodes)
        k = 0
        for n in nodes:
            while n.ucpu < 7:
                s = r.choice((1, 2))
                if n.ucpu + s > 8:
                    break
                q = Pod(f"l{k}", s, priority=r.choice((100, 200)), pdb="db" if r.random() < 0.3 else None)
                cl.bind(q, n)
                k += 1
        hp = Pod("H", 4, priority=1000)
        a = preempt(cl, hp, budgets={"db": 0})
        b = preempt(cl, hp, budgets=None)
        if a:
            viol_aware += sum(1 for q in a[1] if q.pdb == "db")
        if b:
            viol_blind += sum(1 for q in b[1] if q.pdb == "db")
    OUT["e6_pdb"] = {"trials": TR2, "pdb_victims_aware": viol_aware, "pdb_victims_blind": viol_blind}
    log(f"  PDB budget 0 on ~30% of pods, {TR2} trials: protected pods evicted with PDB-aware ranking={viol_aware}"
        f"  if PDBs were ignored={viol_blind}  (best effort: avoided, not forbidden)")

def qsim(lam, c, share_h, policy, n_jobs, seed):
    """M/M/c with two classes. policy: fifo | prio (non-preemptive) | preempt (restart from zero)."""
    r = random.Random(seed)
    t = 0.0
    ev = []
    seq = 0
    jid = 0
    for _ in range(1):
        heapq.heappush(ev, (r.expovariate(lam), seq, "arr", None))
        seq += 1
    busy = []        # running jobs: dict
    qH, qL = [], []  # waiting (FIFO within class)
    waits = {"H": [], "L": []}
    wasted = 0.0
    done_work = 0.0
    arrived = 0
    evictions = 0

    def start(job, now):
        nonlocal seq
        job["start"] = now
        job["end"] = now + job["svc"]
        job["gen"] += 1
        busy.append(job)
        heapq.heappush(ev, (job["end"], seq, "dep", (job, job["gen"])))
        seq += 1

    def pick():
        if policy == "fifo":
            cands = []
            if qH:
                cands.append(qH)
            if qL:
                cands.append(qL)
            if not cands:
                return None
            qq = min(cands, key=lambda q: q[0]["arr"])
            return qq.pop(0)
        if qH:
            return qH.pop(0)
        if qL:
            return qL.pop(0)
        return None

    while ev:
        t, _, kind, data = heapq.heappop(ev)
        if kind == "arr":
            if arrived < n_jobs:
                cls = "H" if r.random() < share_h else "L"
                job = {"cls": cls, "arr": t, "svc": r.expovariate(1.0), "gen": 0, "first": None}
                arrived += 1
                heapq.heappush(ev, (t + r.expovariate(lam), seq, "arr", None))
                seq += 1
                if len(busy) < c:
                    job["first"] = t
                    start(job, t)
                elif policy == "preempt" and cls == "H" and any(b["cls"] == "L" for b in busy):
                    vic = max((b for b in busy if b["cls"] == "L"), key=lambda b: b["start"])
                    busy.remove(vic)
                    wasted += t - vic["start"]
                    evictions += 1
                    qL.insert(0, vic)
                    job["first"] = t
                    start(job, t)
                else:
                    (qH if cls == "H" else qL).append(job)
        else:
            job, gen = data
            if gen != job["gen"] or job not in busy:
                continue
            busy.remove(job)
            done_work += job["svc"]
            waits[job["cls"]].append(job["first"] - job["arr"])
            nxt = pick()
            if nxt is not None:
                if nxt["first"] is None:
                    nxt["first"] = t
                start(nxt, t)
    # note: for an evicted job "first" is its FIRST start; queueing after eviction is
    # charged to wasted work, not to wait, so waits understate preemption's cost.
    def stats(w):
        w = sorted(w[len(w) // 10:])  # drop warm-up tenth
        if not w:
            return 0, 0
        return sum(w) / len(w), w[int(0.95 * (len(w) - 1))]
    mh, ph = stats(waits["H"])
    ml, pl = stats(waits["L"])
    return {"mean_H": mh, "p95_H": ph, "mean_L": ml, "p95_L": pl,
            "wasted_share": wasted / (wasted + done_work), "evictions_per_H": evictions / max(1, len(waits["H"]))}
