What May Redis Forget?

Architecture and design patterns for Redis as cache, database, message broker and coordinator, and beside Kafka, PostgreSQL, Elasticsearch, Spring Boot and Kubernetes

Every Redis pattern answers the same question in a different place. When the server loses something it has already said OK to, where does the truth come back from, and what breaks while it is gone? This article files twenty-two patterns as plates on a six-station write path, measures nine of their failure modes in a deterministic lab, and finds that the harm a pattern can do is set less by which product holds the truth than by whether the OK is sent before the truth is safe.

How to read a plate. The gauge's six stations are ∅ nowhere, M primary memory, R replica memory, D local disk, L external log, S system of record. A filled station is where the truth lives; the red flag is where the OK is sent; hatching marks the span in which an acknowledged fact can vanish. Harm codes: H latency or load, D duplicate work, S stale answer, L acknowledged data lost, X safety invariant broken.

The question under every pattern

Redis is usually introduced by what it is fast at. That framing is accurate and not very useful to an architect, because almost every design decision about Redis is a decision about something else: what happens to a write it has already acknowledged and then cannot keep. Redis executes commands against data held in memory [1], it replicates asynchronously by default [2], and its persistence options trade a window of possible loss against throughput [3,4]. None of this is a defect. It is a position on a design space that systems such as RAMCloud occupy more expensively [5], and it means the useful question about any Redis pattern is narrower than whether Redis is reliable.

The question this article asks of each pattern is: what may Redis forget, and who notices? Forgetting comes through three channels, and they behave differently. Redis forgets data when a crash lands inside an fsync window or a failover promotes a replica that had not yet received the latest writes. It forgets time when a TTL or lease expires while its holder still acts on it. And it forgets listeners when a push channel such as Pub/Sub, keyspace notifications or client-tracking invalidations has nobody connected at the moment of delivery, because those channels deliver at most once [6–8].

Each pattern below is a plate with the same five fields: what Redis holds, the commands that hold it, where the truth lives, what happens when Redis loses it, and the condition under which the pattern breaks. Every plate also carries a small gauge, the acknowledgement flag. The gauge draws the write path as six stations ordered by how much survives a failure: nowhere, the primary's memory, a replica's memory, the primary's local disk, an external replayable log such as a Kafka topic, and the system of record. A filled station marks where the truth of that pattern lives. The flag marks where the client is told OK. When the flag stands to the left of the truth, or the truth sits left of the dashed durability line, the span between them is hatched: that is the interval in which an acknowledged fact can vanish.

The plates also carry a harm code, from mildest to worst: H for latency and load only, D for duplicated work, S for a stale or wrong answer, L for acknowledged data lost, and X for a broken safety invariant such as mutual exclusion. The ten families come straight from the brief: Redis as cache, database, broker and coordination system, then Redis beside Kafka, PostgreSQL, Elasticsearch, Spring Boot and Kubernetes, and finally Redis in event-driven systems. The organising claim, tested by the census in the last section, is that the harm column is predicted mainly by the gauge's geometry, not by the family a pattern belongs to.

The machine every pattern runs on

One thread of commands

Redis serves each command to completion on a single main thread, so a slow command delays every client behind it; the latency guide says so directly and recommends against O(N) commands on large values [1]. Since version 6 network reads and writes can be offloaded to I/O threads, configured by io-threads, but command execution stays serial [9]. That seriality is the property most patterns lean on. A Lua script or a function runs atomically [10,11], MULTI/EXEC applies a queued batch without interleaving but does not roll back a failed command [12], and pipelining amortises round trips without adding atomicity [13]. When a plate below says one script does two things together, it means this: no other client can observe the state between them.

Persistence: two files and one window

Durability comes from two mechanisms [3]. RDB writes a point-in-time snapshot from a forked child; restart is fast and the file is compact, but everything since the last snapshot is lost on a crash. The append-only file logs every write, and the appendfsync setting decides when the log reaches the disk: always, every second, or whenever the operating system chooses. Sanfilippo's own account of the trade-offs remains the clearest description of why every second is the default [4]. The lab's fifth experiment puts numbers on it for a primary taking 10,000 writes per second: a crash under everysec loses 5,098 acknowledged writes on average, 10,021 at the 99th percentile, and up to 19,998 when a stalled fsync stretches the window to two seconds. Snapshots alone every five minutes would lose 1,500,000 on average.

Replication, and what WAIT does not promise

Replicas receive a stream of the primary's writes, asynchronously [2]. WAIT blocks the caller until a given number of replicas acknowledge, and WAITAOF, added in 7.2, blocks until the local AOF and a given number of replicas have fsynced [14,15]. Both documentation pages carry the same caveat: neither makes Redis strongly consistent, because a failover can still promote a replica that did not take part. Sentinel decides failover by a quorum of observers and a down-after period [16]. The setting that matters most during a partition is min-replicas-to-write with min-replicas-max-lag, which makes an isolated primary refuse writes instead of accepting writes that will be discarded when it rejoins as a replica [2,9]. The replication section of INFO reports the primary's master_repl_offset and each replica's acknowledged offset, and the difference between them is the loss window to alert on [17]. In the lab, 30% of clients stranded on an isolated primary for the default 30-second detection plus failover lose 99,000 writes; with a 10-second lag bound they lose 30,000.

These are not hypothetical failure modes. Jepsen's analysis of the experimental Redis-Raft module, which tried to give Redis linearizable replication, found twenty-one issues in early builds, including the loss of all committed data on any failover in one configuration [18], using the Elle checker to infer anomalies from client histories [19]. The general lesson, set out at length by Kleppmann, is that asynchronous replication with automatic failover trades bounded loss for availability [20,21], and that the bound depends on lag more than on any configuration flag [22].

Cluster: 16,384 slots

Redis Cluster partitions the keyspace into 16,384 hash slots by CRC16 of the key modulo 16,384, and lets a key name a hash tag in braces so that related keys share a slot [23]. Multi-key commands, transactions and scripts work only within a slot, which is why every multi-key listing in this article uses hash tags. The lab reimplements the slot function and reproduces the specification's test vector: CRC16 of the string 123456789 is 0x31C3, which maps to slot 12,739. Keys tagged {42} all land in slot {{N:e7.tags.user:{42}:profile}}, while user:43:profile lands in 2,190. The specification is explicit that Cluster does not guarantee strong consistency and can lose acknowledged writes during a partition [23].

Slots are what make resharding cheap. Moving from three primaries to four by reassigning a quarter of each range moves 4,098 slots and 24.97% of keys; a naive hash-modulo-N scheme would move 75.08% [24]. The same mechanism concentrates load: one hash tag carrying 30% of traffic makes its primary serve 53.3% of requests against a fair share of 33.3%. Sequential keys are not perfectly uniform under CRC16, either. Spread over 16,384 slots, 100,000 keys give a chi-square of 21,279 on 16,383 degrees of freedom, a variance about 30% above a uniform hash, although the three primaries still receive counts within 0.3% of each other.

The current product line

Redis 8.0 added the OSI-approved AGPLv3 as a licence option alongside the source-available licences adopted in 2024, and folded the former Redis Stack modules, including JSON, time series, probabilistic types and the query engine, into core [25,26]. As of this writing the newest release line is 8.10, generally available on 29 July 2026, with 8.10.1 following on 17 August as a security release [27]. The Linux Foundation fork, Valkey, continues under BSD with its own 9.x line [28]. Two 8.x additions matter to the patterns here: vector sets [29], and, from 8.4, conditional SET and DELEX options that compare a key's value before writing or deleting it, which replace the Lua scripts long used to release locks safely [30,31].

Redis as cache

A cache is the one role in which forgetting is the design. The truth lives in the system of record; Redis holds a copy that may vanish by expiry or eviction at any time, and the only harm should be load. The first plate keeps the truth in the database and only ever answers from a copy of it; the second moves the copy into the application process, and is exposed for a reason the gauge makes visible. What goes wrong with caches is rarely loss. It is the shape of the misses.

A1

Cache-aside with early recompute

Holds
A copy of a row or query result, rebuilt from the database on a miss.
Commands
HGETALL and PTTL in one MULTI; SET NX PX for a refresh lock; HSET and EXPIRE with jittered TTL.
Truth lives
The database. Redis may drop the key at any moment, by TTL or by eviction.
When Redis forgets
Extra database load and a latency spike. No wrong answers, provided writes do not race the fill.
Breaks when
Hot keys expire together, or a slow recompute lets a herd of misses through.

Cache-aside, sometimes called lazy loading, reads from Redis, falls back to the database on a miss, and writes the result back with a TTL [32]. Facebook's memcache paper documents the two failures that follow at scale: thundering herds when a hot key expires, and stale sets when a slow reader writes back a value older than a concurrent update; it introduced leases to suppress both [33]. The listing below combines three defences that the lab measures separately: a refresh lock taken with SET NX PX, probabilistic early recomputation, and jittered TTLs.

Probabilistic early recomputation, called XFetch by Vattani, Chierichetti and Lowenstein, lets each reader refresh the value early with a probability that rises as expiry approaches and scales with how long the last recompute took; they prove it optimal within a broad class of such schemes [34]. The lab's third experiment drives one hot key at 500 requests per second with a 200 ms recompute. Without protection, each expiry triggers 100.9 recomputes on average and 124 at the 99th percentile, almost exactly the arrival rate times the recompute time. With a lock, one recompute runs and 99.8 requests either wait or receive the stale value. XFetch with beta of 1 cuts the mean to 2.71 and refreshes about 1,036 ms before expiry with no hard misses; but 62.5% of cycles still see more than one recompute, which is why the listing pairs it with the lock.

The second shape is synchronised expiry across many keys, which happens after a bulk load, a cold start or a deploy that warms the cache at once. The fourth experiment loads 10,000 keys with a one-hour TTL. With identical TTLs every key expires in the same second, 10,000 misses at once; adding uniform jitter of plus or minus 1% spreads them over 72 seconds with a peak of 162 per second, and 10% brings the peak to 27 per second.

When memory fills, Redis evicts according to maxmemory-policy [35]. Its LRU is approximate: on each eviction it samples a few keys, five by default, and keeps a small pool of good candidates between evictions, a design Sanfilippo described when the pool was introduced alongside LFU [36]. LFU keeps a logarithmic, probabilistically incremented 8-bit counter per key that decays over time. The second experiment compares these with exact LRU on a 20,000-key Zipf workload, the access shape web caches have long been observed to follow [37]. Sampled LRU with five samples stays within 0.29 points of exact LRU at every size tested, from 49.41% versus 49.12% hit ratio at a 2% cache to 77.29% versus 77.12% at 20%. LFU beats exact LRU by 7.18 points at the smallest cache and 2.13 at the largest; under heavy skew, frequency is a better predictor than recency, the observation behind ARC and TinyLFU [38,39]. Che's approximation gives the analytical reason the curves bend the way they do [40], and Belady's optimal policy remains the unreachable ceiling [41].

A2

Server-assisted client-side caching

Holds
Values copied into the application's own memory, invalidated by pushes from Redis.
Commands
HELLO 3 and CLIENT TRACKING ON (or REDIRECT on RESP2); invalidate push messages.
Truth lives
The primary's memory. The local copy is only as current as the last invalidation that arrived.
When Redis forgets
A dropped connection silently drops invalidations, and the process serves stale values.
Breaks when
The client keeps its local cache across a reconnect instead of flushing it.

Client-side caching moves the copy one step further from the truth, into the application process. With CLIENT TRACKING, Redis remembers which keys each connection has read and pushes an invalidation when one changes, over RESP3 push messages or a redirected Pub/Sub connection [8,42,43]. The gauge shows why this plate is exposed even though the flag and the truth coincide: the truth sits in the primary's memory, and the invalidation stream is a push channel. The reference documentation tells clients to flush their local cache whenever the connection to Redis is lost [8]. A client that skips that step serves stale values with no error. TAO, Facebook's graph cache, faced the same problem one level up and accepted eventual consistency in exchange for read throughput [44].

Redis as database

As a database, Redis holds the only authoritative copy, so the gauge's question becomes literal. Its data structures are the reason to use it this way: hashes for records, sorted sets for rankings and time-ordered indexes [45], per-field expiry on hashes since 7.4 [46], and, in Redis 8, JSON, a query engine and vector sets in core [25,29]. The cost is the window between the OK and the disk.

B1

Primary store with AOF every second

Holds
Authoritative records: sessions, carts, profiles, counters, leaderboards.
Commands
Hashes and sorted sets; appendonly yes; appendfsync everysec; asynchronous replicas.
Truth lives
The local append-only file after the next fsync; replicas a few milliseconds behind.
When Redis forgets
Up to about a second of acknowledged writes on a crash; the replication lag on a failover.
Breaks when
A disk stall stretches the fsync window, or an isolated primary keeps taking writes.

The default durable configuration is AOF with everysec and one or more replicas. The flag sits at primary memory, the truth one station later at local disk, and the hatched span is the window the lab measured: about half a second of writes on average, a second at the 99th percentile, and two seconds when fsync stalls. On failover, loss is bounded by replication lag instead: with a 3 ms mean lag at 10,000 writes per second, the lab loses 29.9 writes on average and 138 at the 99th percentile. Those are small numbers. The partition case is the large one, and it is controlled by min-replicas-max-lag rather than by persistence.

B2

Acknowledged durability with WAITAOF

Holds
The same records, for the writes that must not be lost.
Commands
The write, then WAITAOF 1 1 timeout; check both returned counts before replying.
Truth lives
The fsynced AOF on the primary and on at least one replica, before the caller proceeds.
When Redis forgets
Only a failover that promotes a replica other than the one that fsynced.
Breaks when
It is called under appendfsync everysec, where each wait lasts until the next tick.

WAITAOF moves the flag right, to the station where the truth already is [15]. It is the only covered plate in the census that can still lose acknowledged data, and the reason is instructive: Sentinel chooses the replica to promote by priority and replication offset, not by which replica confirmed an fsync [16]. The latency cost depends entirely on the fsync policy. Under everysec, WAITAOF 1 0 waits for the next tick, 501 ms on average in the lab, and WAITAOF 1 1 waits for the later of two independent ticks, 667 ms. Plain WAIT 1 adds only the replication round trip, 3.24 ms against a 0.25 ms baseline. WAITAOF is therefore meant for appendfsync always, or for the small set of writes that justify a visible pause.

Redis as message broker

Redis offers three messaging shapes with very different memories. Pub/Sub keeps nothing. Lists, with LMOVE, give a simple work queue. Streams, added in 5.0, keep an append-only log with consumer groups, per-consumer pending lists and explicit acknowledgement, a design openly modelled on Kafka's consumer groups [47,48].

C1

Pub/Sub fan-out

Holds
Nothing. A message goes to whoever is subscribed at that instant and is then gone.
Commands
PUBLISH and SUBSCRIBE; SPUBLISH and SSUBSCRIBE for sharded channels in a cluster.
Truth lives
Nowhere. PUBLISH returns how many clients received the message, not how many acted on it.
When Redis forgets
A disconnected, restarting or slow subscriber misses messages permanently.
Breaks when
Anyone treats it as a queue.

Pub/Sub delivers each message to the subscribers connected at that instant [6]. The documentation calls the semantics at-most-once: a subscriber that is disconnected, or that falls behind far enough to hit its output-buffer limit and be dropped, never sees what it missed. In a cluster, classic Pub/Sub broadcasts every message to every node; sharded Pub/Sub, added in 7.0, routes a channel by slot like a key [49]. The gauge has no truth station at all. Pub/Sub is right for presence, live dashboards and cache-invalidation fan-out where a missed message is superseded by the next one; it is wrong anywhere the message is the record.

C2

Streams with consumer groups

Holds
An append-only log, consumer-group cursors, and a pending-entries list per consumer.
Commands
XADD, XREADGROUP, XACK, XAUTOCLAIM, XTRIM.
Truth lives
The stream on the primary, durable after the next AOF fsync.
When Redis forgets
Tail entries vanish on a crash or failover; a crash between effect and XACK redelivers.
Breaks when
Effects are not idempotent, or trimming removes entries nobody has acknowledged.

Streams make the message the record. XREADGROUP hands each entry to one consumer in a group and records it in that consumer's pending-entries list until XACK; XAUTOCLAIM transfers entries that have been pending longer than a threshold to a live consumer [47,50]. That is at-least-once delivery, and it moves the question to the consumer: where does the record that an entry was applied live? The ninth experiment simulates 100,000 entries with a 0.2% chance of a crash at a random step and compares four placements. Acknowledging after the effect duplicates 55 entries and loses none; acknowledging first loses 81; writing a dedupe key before the effect, a common intermediate fix, trades duplicates for 42 losses, because a crash between the mark and the effect leaves a record claiming work that never happened. Only an effect and dedupe record committed atomically gives zero duplicates and zero losses.

The listing does exactly that when the effect itself lives in Redis: one script sets the dedupe key with NX and applies the change, so a redelivered entry is a no-op. Hohpe and Woolf named this the idempotent receiver [51]. When the effect lives in a database, the dedupe record has to go into the same database transaction, which is the point Helland makes about entities that must remember the messages they have seen [52].

Redis as coordination system

Coordination is where forgetting time does the damage. A lock in Redis is a lease in the sense of Gray and Cheriton: a grant that expires, so that a crashed holder cannot block everyone forever [53]. The price of expiry is that a holder that is paused, by garbage collection, a page fault or a stalled VM, can wake up and act after its lease has passed to someone else.

D1

Lease lock without fencing

Holds
One key that means someone owns this resource for the next N milliseconds.
Commands
SET lock token NX PX; compare-and-delete to release.
Truth lives
The primary's memory, and nothing else.
When Redis forgets
Two workers both believe they hold the lock: after a failover that lost the key, or after a pause outlived the lease.
Breaks when
It is relied on for correctness rather than to save duplicated work.

The single-instance recipe is SET with NX and PX and a random token, released by deleting the key only if the token still matches [31,54]. Redlock extends this across several independent primaries and grants the lock when a majority agree within the validity time [54]. In 2016 Kleppmann argued that no lease-based lock without fencing can be safe under process pauses, network delay and clock jumps, and that Redlock additionally depends on timing assumptions [55]; Sanfilippo replied that the algorithm's assumptions are reasonable and that the pause argument applies to any lease-based lock [56]. Whatever one concludes about Redlock, the sixth experiment illustrates the point neither side disputes: a lease alone cannot stop a paused holder from acting late, and if correctness depends on exclusion, the resource itself has to reject stale writers.

The experiment models work with a median of 2 seconds, plus a 2% chance per acquisition of a heavy-tailed pause. With a 5-second lease, 3.56% of acquisitions end with the holder writing after its lease has expired; a watchdog that renews the lease every third of its life cuts that to 0.085%, but not to zero, because the pause freezes the renewer too. Beyond about 20 seconds the two curves meet, since work rarely outlasts the lease and only the pause matters. Longer leases shrink the rate, to 0.005% at 30 seconds, but never to zero, and they lengthen the outage when a holder truly dies. With a fencing check at the resource, no stale write is accepted at any lease length.

D2

Lease lock with fencing at the resource

Holds
The same lease, demoted to an optimisation; the resource enforces exclusion.
Commands
SET NX PX; every write to the resource carries a version or token the resource checks.
Truth lives
The resource, typically a database row version.
When Redis forgets
Wasted work. The stale writer's update matches zero rows and is abandoned.
Breaks when
The protected resource cannot check a token, as with an external API or a file.

Fencing, in Burrows's description of Chubby, is a sequencer the protected server checks on every request [57]. Kleppmann's version is a monotonically increasing token [55]. The simplest form needs no token service at all: the resource keeps a version, and every write is conditional on the version the worker read. A lock still saves work, by stopping two workers from starting the same job, but it is no longer responsible for safety. One trap is worth naming: if the fencing counter is itself an INCR in Redis, a failover can lose increments and reissue a number, so the counter inherits exactly the forgetting it was meant to guard against. Consensus services such as ZooKeeper and Raft-based stores exist to provide such sequences durably [58,59].

D3

Token-bucket rate limiter

Holds
Per-client token count and last refill time.
Commands
One Lua script: HMGET, refill by the server's TIME, HSET, PEXPIRE.
Truth lives
The primary's memory.
When Redis forgets
The bucket comes back full, and the client gets a fresh allowance.
Breaks when
The limit enforces a contract or a bill rather than protecting capacity.

Rate limiters are coordination over a shared quota. The token bucket dates to traffic shaping in packet networks [60]; Stripe described running several limiter types in Redis [61], and Cloudflare described the sliding-window counter that approximates a sliding log with two counters [62]. The eighth experiment sends an adversarial client against a limit of 100 per minute and measures the most requests admitted in any 60-second window. A sliding log admits exactly 100 but stores a timestamp per request. A fixed window admits 200, double the limit, across a window boundary. The sliding-window counter admits 184. The token bucket admits 199: a full bucket plus a minute's refill, so it bounds the long-run rate, not the per-window count.

The script uses the server's clock through redis.call('TIME') rather than a timestamp from the client, so that callers with skewed clocks share one notion of now, and it returns the token count as a string because Lua numbers are converted to integers in replies [10]. Lamport's point about the absence of a shared clock is the reason for the first choice [63].

Redis and Kafka

Kafka and Redis divide the work along the gauge. Kafka is a replicated, partitioned log retained by time or compacted by key [48,64]; Kreps's essay on the log explains why such a log makes a good system of record for derived data [65]. Redis is a fast place to put the derived data. Kafka 4.0 removed ZooKeeper in favour of KRaft, and from 4.2 share groups, the queue semantics proposed in KIP-932 with per-record acknowledgement and delivery counts, are production-ready [66,67]. That overlaps with Redis Streams consumer groups; the deciding question is still which side holds the truth.

E1

Materialised view fed from a topic

Holds
A query-shaped projection of one or more Kafka topics.
Commands
One script upserts the view and the partition offset together.
Truth lives
The topic, replayable from retained or compacted log.
When Redis forgets
Stale reads until the consumer replays from the last offset it stored.
Breaks when
Retention deletes records the view needs in order to rebuild.

A materialised view in Redis, fed by a Kafka consumer, is the read side of CQRS in Fowler's sense [68]. Because the topic holds the truth, the view can be thrown away and rebuilt, provided the consumer knows where it stopped. Kafka's delivery-semantics section notes that storing the consumer's position in the same system as its output is how to make processing effectively exactly-once [69]. The listing stores the partition offset in a Redis hash and updates it in the same script as the view, so a replayed record, whether after a rebalance, a crash or a deliberate rebuild, is a no-op. On assignment the consumer seeks to Redis's stored offset, not Kafka's committed one [70].

E2

Idempotency ledger for consumers

Holds
The identities of records already applied, each with an expiry.
Commands
SET seen:id NX EX inside the same script as the effect.
Truth lives
The primary's memory.
When Redis forgets
Forgotten identities let redelivered records apply twice.
Breaks when
The expiry is shorter than the redelivery horizon, or the effect lives outside Redis.

The reverse arrangement, a Redis set of already-processed identities protecting an effect somewhere else, is common and weaker. Its truth is in Redis's memory, so a failover can forget identities and let a redelivery through; its expiry must outlast the longest redelivery horizon. It is an advisory record: losing it converts a guarantee of no duplicates into a duplicate, not into lost data. That distinction, between authoritative and advisory state, turns out to explain the census's exceptions.

Redis and PostgreSQL

PostgreSQL is the commonest system of record behind Redis, and the three plates here differ in a single respect: whether PostgreSQL commits before or after the client is told OK.

F1

Invalidation from the write-ahead log

Holds
Cached rows; invalidations derived from PostgreSQL's change stream.
Commands
Debezium reads logical decoding; a consumer issues DEL or UNLINK per change.
Truth lives
PostgreSQL, whose WAL is the ordered record of every change.
When Redis forgets
A missed invalidation leaves a stale entry until its TTL.
Breaks when
TTLs are removed because invalidation is assumed to be complete.

Invalidating a cache from application code after a write is a dual write: two systems, no transaction across them, and any crash between them leaves the cache stale. Reading the database's own change stream removes the second write from the application. PostgreSQL's logical decoding exposes committed changes in commit order through replication slots [71], and Debezium's connector turns them into change events [72]. LISTEN/NOTIFY is lighter but is a push channel with the same at-most-once character as Pub/Sub for a listener that is not connected [73]. The plate is graded S rather than H because a missed or reordered invalidation still leaves a stale entry; the TTL is the backstop, which is why removing it is the failure condition.

F2

Transactional outbox relay

Holds
Events committed in the same transaction as the state they describe.
Commands
INSERT INTO outbox inside the business transaction; Debezium Server writes XADD.
Truth lives
The outbox row in PostgreSQL.
When Redis forgets
The relay re-reads from its stored position and re-sends: duplicates, never gaps.
Breaks when
Consumers are not idempotent.

The transactional outbox writes an event row in the same transaction as the business change, and a relay publishes the rows afterwards [74]. Debezium ships an outbox event router for exactly this [75], and Debezium Server can publish directly to Redis Streams and store its own offsets in Redis [76]. Redis's integration documentation shows a sink option that waits for a replica to acknowledge each write before proceeding [77]. If Redis forgets the stream tail or the stored offset, the relay replays from the database's position: duplicates, never gaps, which is the D on the plate.

F3

Write-behind to the database

Holds
The write itself, queued in Redis for a later flush to PostgreSQL.
Commands
HSET plus XADD to a flush stream; a worker batches rows into SQL.
Truth lives
Intended to be PostgreSQL, but only Redis until the flush commits.
When Redis forgets
Writes the user was told had succeeded never reach the database.
Breaks when
A crash lands inside the flush lag, or the database rejects a row Redis accepted.

Write-behind inverts the order. The client writes to Redis, gets an OK, and a worker later flushes to PostgreSQL. It is the only plate in the census whose truth station is the system of record while its flag stands at primary memory: the widest hatched span on any gauge. It earns its place where write rates exceed what the database can absorb and the business accepts bounded loss, metrics and counters for example. The test is simple: if the database can reject a row Redis has already accepted, a constraint violation say, the user has been told something false.

Redis and Elasticsearch

Elasticsearch is itself eventually visible: a document indexed now becomes searchable after the next refresh, one second by default for indices that are being searched [78]. Redis sits on both sides of it, as a buffer before indexing and as a cache after search. The current release line is 9.x, with 9.3 released in February 2026 [79].

G1

Ingest buffer ahead of bulk indexing

Holds
Documents or log lines waiting to be sent in a _bulk request.
Commands
XADD with MAXLEN; a worker reads the group, sends _bulk, acknowledges per item.
Truth lives
The stream, until Elasticsearch confirms each bulk item.
When Redis forgets
Entries inside the fsync window are gone; nothing upstream can resend them.
Breaks when
Partial bulk failures are acknowledged as if they had succeeded.

Using a stream as an ingest buffer smooths bursts into efficient _bulk requests [80]. The bulk API reports success or failure per item, and the common bug is to acknowledge the whole batch when the HTTP call succeeds. The listing acknowledges only the items that succeeded, leaves the rest pending for XAUTOCLAIM, and uses the stream entry ID as the document _id so that a retry overwrites rather than duplicates [81]. Where documents have their own versions, Elasticsearch's optimistic concurrency control rejects out-of-order writes [82]. The plate is still graded L: if Redis holds the only copy of a log line, a crash in the fsync window loses it, and no amount of care downstream brings it back.

G2

Query cache keyed by index generation

Holds
Serialised search responses.
Commands
GET and SET under hash(query) plus a generation number; INCR the generation on reindex.
Truth lives
The Elasticsearch index.
When Redis forgets
The query runs again.
Breaks when
The generation is bumped before the new index is refreshed and searchable.

Elasticsearch has its own shard request cache, invalidated on refresh [83], so an application-level cache in Redis earns its keep for expensive, repeated queries across many nodes or for results post-processed by the application. Keying each entry by a generation number turns invalidation into a single INCR. The ordering matters: when a reindex finishes, switch the alias to the new index first [84], confirm it is refreshed, then bump the generation. Done the other way round, readers repopulate the new generation from the old index.

Redis and Spring Boot

Spring Boot is where most Java teams meet Redis, through Spring Data Redis and the Lettuce client [85,86]. The current releases are Spring Boot 4.1 and Spring Data Redis 4.1.0, released in June 2026 with Lettuce 7.5, support for the 8.4 DELEX command, annotation-driven Pub/Sub listeners, and a cache reset that can use FLUSHDB when Redis serves only as a cache [87,88].

H1

@Cacheable over a repository

Holds
Method results keyed by their arguments.
Commands
RedisCacheManager: GET and SET with an entry TTL; DEL on @CacheEvict.
Truth lives
The repository behind the method.
When Redis forgets
The method runs again.
Breaks when
An eviction runs before the surrounding transaction commits, and a reader refills the old value.

The cache abstraction maps @Cacheable, @CachePut and @CacheEvict onto a cache manager [89], and Boot auto-configures RedisCacheManager when Redis is on the classpath, with entry TTLs set per cache name [90]. Two details decide whether the plate stays at H. First, sync = true serialises concurrent misses only within one JVM; across a fleet of instances the stampede from the third experiment returns, so hot entries still need the locking or early recompute shown earlier. Second, an eviction that runs before the surrounding transaction commits lets a concurrent reader refill the cache with the old row. The cache manager's transactionAware option defers puts and evictions until after commit [85].

H2

Spring Session store

Holds
HTTP session attributes for every signed-in user.
Commands
One hash per session with an expiry; the indexed repository adds keyspace events.
Truth lives
The primary, copied asynchronously to replicas.
When Redis forgets
Users are signed out and carts emptied.
Breaks when
Sessions share an instance whose eviction policy treats them as cache entries.

Spring Session stores HTTP sessions in Redis so that any instance can serve any request [91]. The indexed repository additionally subscribes to keyspace events to publish session-expired events, which inherits the push-channel caveat of plate J1. The plate is graded L because the sessions exist nowhere else. The most frequent production mistake is to point sessions at the same instance as the cache, configured with allkeys-lru or allkeys-lfu, so that a burst of cache traffic evicts signed-in users.

Redis and Kubernetes

Kubernetes adds a fourth way to forget: the scheduler. A pod can be rescheduled, its node drained, its container killed by a failing probe. Which of these costs data depends on whether the deployment treats Redis as cattle or as state.

I1

Ephemeral cache Deployment

Holds
A disposable cache in one or more pods.
Commands
maxmemory with allkeys-lfu; persistence off; an emptyDir volume or none.
Truth lives
The system of record.
When Redis forgets
A cold cache after every reschedule.
Breaks when
Something quietly starts depending on what is in it.

A cache-only Redis belongs in an ordinary Deployment, with persistence off and either no volume or an emptyDir that disappears with the pod [92]. It is the one plate in the family where every reschedule is expected. The risk is organisational: once something starts depending on what is in the cache, the deployment is a database that nobody has configured as one.

I2

StatefulSet with Sentinel and volumes

Holds
Authoritative data on pods with stable identities.
Commands
StatefulSet, headless Service, volumeClaimTemplates, a disruption budget, Sentinel or an operator.
Truth lives
The AOF on each pod's persistent volume.
When Redis forgets
The same windows as B1, plus whatever the orchestrator adds when it moves pods.
Breaks when
A liveness probe restarts a primary that is busy, or a node drain takes two members at once.

A Redis that holds truth needs a StatefulSet: stable pod names, stable DNS through a headless Service, and a PersistentVolumeClaim per pod that follows the pod across rescheduling [93,94]. A PodDisruptionBudget stops voluntary disruptions, such as node drains, from taking more than one member at a time [95]. Probes need care: a liveness probe that fails during a long AOF rewrite or a large key deletion can restart a healthy primary, so the listing uses a cheap TCP liveness check with generous thresholds and a PING readiness check [96]. The termination grace period gives Redis time to finish a final write when it receives SIGTERM [97]. In a cluster, nodes should announce stable hostnames rather than pod IPs, which change on every restart; redis.conf provides cluster-announce-hostname for this [9].

Redis in event-driven systems

The previous families meet in event-driven systems, where Redis typically plays several roles at once: event bus, scheduler, deduplication ledger and projection store. Event sourcing, in Fowler's description, makes the event log the record of state [98]; notification merely announces that state changed somewhere else. The distinction maps directly onto the gauge. Notification can tolerate a missing truth station. A record cannot.

J1

Keyspace notifications as triggers

Holds
Nothing. Changes to keys are announced on Pub/Sub channels.
Commands
notify-keyspace-events; SUBSCRIBE __keyevent@0__:expired.
Truth lives
Nowhere.
When Redis forgets
Disconnected listeners miss events, and expired fires when Redis notices, not at the TTL.
Breaks when
It is used as a durable trigger for billing, reminders or workflow steps.

Keyspace notifications publish an event on a Pub/Sub channel when a key changes or expires [7]. They are disabled by default because they cost CPU, and the documentation warns of two limits: delivery is fire-and-forget, so a disconnected listener misses events, and an expired event is generated when Redis actually deletes the key, by lazy access or by its background sampling, not at the instant the TTL elapses [7,99]. Using them to trigger a reminder email works until the listener restarts.

J2

Delayed events from a sorted set

Holds
Future jobs, scored by due time.
Commands
ZADD; one script moves due members to a stream with XADD and ZREM.
Truth lives
The local AOF.
When Redis forgets
Jobs scheduled inside the fsync window disappear.
Breaks when
Two movers run without atomicity, or job scores and the mover use different clocks.

A sorted set scored by due time is a compact delayed-job scheduler [45]. The listing moves due members into a stream in one script, so a member is either still scheduled or already enqueued, never both and never neither, and workers then consume the stream with the at-least-once machinery of plate C2. Using the server's TIME inside the script means the mover and the scores share a clock only if producers also derive scores from Redis time; otherwise the plate's breaking condition, two clocks, applies.

Put together, the families form one topology. PostgreSQL commits state and outbox rows together; Debezium carries the outbox into a Redis stream and invalidations into the cache; Kafka carries high-volume events to consumers that maintain Redis views; a stream buffers documents for Elasticsearch; Spring Boot services read through caches and keep sessions in a separate instance; and Kubernetes runs the stateless caches as Deployments and the stateful instances as StatefulSets. The figure marks each Redis role with the station where its truth lives.

The ledger, and what it shows

Of the twenty-two plates, 13 are exposed in the gauge's sense: the OK is sent before the truth is durable, or the truth never becomes durable. Eleven are severe, losing acknowledged data or breaking a safety invariant, and 10 of those eleven are exposed. The rule that a plate is severe exactly when it is exposed holds for 18 of 22 plates, 81.8%. The mean harm rank is 2.77 for exposed plates and 1 for covered ones. Redis holds the only copy of the truth in 7 plates.

The four exceptions are more informative than the rule. Three are exposed but not severe: client-side tracking (A2), the token bucket (D3) and the idempotency ledger (E2). All three hold advisory state, a hint that a copy is current, a count against a quota, a note that work was done, and losing advisory state degrades a guarantee rather than destroying a fact. A lost invalidation becomes a stale read, a lost bucket becomes a fresh allowance, a lost dedupe key becomes a duplicate. The fourth exception, WAITAOF (B2), is covered but severe, and its residual loss comes from a different mechanism altogether: the failover's choice of replica, which no acknowledgement on the write path can constrain.

So the census supports a narrower and more useful claim than the opening one. Severity follows from two properties, both visible on the gauge: whether the OK runs ahead of durable truth, and whether what Redis holds is authoritative or advisory. Family is a weak guide. Five of the ten families mix mild and severe plates (coordination, PostgreSQL, Elasticsearch, Spring Boot and Kubernetes); two are uniformly mild (cache and Kafka, both of which keep the truth outside Redis); three are uniformly severe (database, broker and event-driven, all of which make Redis the record). The one time-channel plate that breaks safety, the unfenced lock, is exposed because its truth is volatile, which is why fencing, which moves the truth to the resource, is the remedy, and a longer lease is not.

What the lab cannot show

The lab is a set of models, not measurements of a Redis deployment. Its parameters, 10,000 writes per second, a 3 ms mean replication lag, a 2% pause rate with a Pareto tail, are illustrative, chosen to be plausible rather than fitted to any system. The eviction experiment reimplements Redis's sampling and LFU counter from their published descriptions rather than running Redis's code. The harm codes are judgements made per plate and stated in each plate's fields so that a reader can disagree with a specific one. The listings were executed against a live Redis 7.0 server where they touch Redis alone; the Kafka, Debezium, Elasticsearch, Spring and Kubernetes listings were checked against their documentation but not run end to end. The DELEX path in the lock listing requires Redis 8.4 or later and falls back to the Lua script on older servers.

Choosing by position

The practical reading of the ledger is a single habit. For any proposed use of Redis, draw the gauge before writing code: mark where the truth lives, mark where the OK is sent, and decide whether the state is authoritative or advisory. If the truth is to the right of the flag and the state is authoritative, someone will eventually be told something false, and the design must either move the flag (WAITAOF, a database commit first, an outbox) or move the truth (a topic, a row version, a system of record). Dean and Barroso's observation that rare events dominate behaviour at scale applies here with force [100]: a window of a second is invisible in testing and certain in a year of production.

def zipf_sampler(rng, n, s):
    w = [1.0 / (i + 1) ** s for i in range(n)]
    c, acc = [], 0.0
    for x in w:
        acc += x; c.append(acc)
    tot = acc
    perm = list(range(n)); rng.shuffle(perm)
    def draw():
        return perm[bisect.bisect_left(c, rng.random() * tot)]
    return draw

class Keyed:
    def __init__(self):
        self.keys = []; self.pos = {}
    def add(self, k):
        self.pos[k] = len(self.keys); self.keys.append(k)
    def remove(self, k):
        i = self.pos.pop(k); last = self.keys.pop()
        if i < len(self.keys):
            self.keys[i] = last; self.pos[last] = i
    def __contains__(self, k): return k in self.pos
    def __len__(self): return len(self.keys)

def run_policy(trace, cap, policy, rng, warm):
    hits = cnt = 0
    if policy == "lru-exact":
        od = OrderedDict()
        for i, k in enumerate(trace):
            if k in od:
                od.move_to_end(k); h = 1
            else:
                h = 0
                if len(od) >= cap: od.popitem(last=False)
                od[k] = True
            if i >= warm: hits += h; cnt += 1
        return hits / cnt
    ks = Keyed(); last = {}; ctr = {}; pool = []
    samples = {"redis-lru-5":5, "redis-lru-10":10, "redis-lfu":5, "random":1}[policy]
    LOG_FACTOR, INIT = 10, 5
    for i, k in enumerate(trace):
        if k in ks:
            h = 1
            if policy == "redis-lfu":
                c = ctr[k]
                if c < 255:
                    base = max(0, c - INIT)
                    if rng.random() < 1.0 / (base * LOG_FACTOR + 1): ctr[k] = c + 1
            last[k] = i
        else:
            h = 0
            if len(ks) >= cap:
                if policy == "random":
                    victim = ks.keys[rng.randrange(len(ks))]
                else:
                    cand = [ks.keys[rng.randrange(len(ks))] for _ in range(samples)]
                    for c in cand:
                        score = (i - last[c]) if policy != "redis-lfu" else (255 - ctr[c])
                        if all(c != q for _, q in pool):
                            pool.append((score, c))
                    pool.sort(key=lambda x: (-x[0], x[1]))
                    del pool[16:]
                    victim = None
                    while pool:
                        _, q = pool.pop(0)
                        if q in ks: victim = q; break
                    if victim is None:
                        victim = cand[0]
                ks.remove(victim); last.pop(victim, None); ctr.pop(victim, None)
            ks.add(k); last[k] = i; ctr[k] = INIT
        if i >= warm: hits += h; cnt += 1
    return hits / cnt

def e3():
    hdr("E3  Stampede at expiry: no protection vs lock vs probabilistic early recompute")
    rng = random.Random(SEED + 3)
    lam, delta, ttl, cycles = 500.0, 0.2, 60.0, 2000
    out = {}
    # unprotected: requests arriving during [T, T+delta) all recompute
    rec = []
    for _ in range(cycles):
        t, n = 0.0, 1
        while True:
            t += rng.expovariate(lam)
            if t >= delta: break
            n += 1
        rec.append(n)
    m = sum(rec) / cycles
    p99 = sorted(rec)[int(0.99 * cycles)]
    print(f"unprotected: mean recomputes per expiry {m:.1f}, p99 {p99} (lambda*delta = {lam*delta:.0f})")
    out["none"] = dict(mean=round(m,1), p99=p99)
    # lock: one recompute, others wait or serve stale
    waits = []
    for _ in range(cycles):
        t, n = 0.0, 0
        while True:
            t += rng.expovariate(lam)
            if t >= delta: break
            n += 1
        waits.append(n)
    mw = sum(waits) / cycles
    print(f"lock (SET NX PX): 1 recompute; requests blocked or served stale per expiry {mw:.1f}")
    out["lock"] = dict(blocked=round(mw,1))
    # XFetch: request at time t (value written at 0, expires at ttl) recomputes if
    # t - delta*beta*ln(U) >= ttl. A recompute in flight suppresses nothing (no lock).
    for beta in (0.5, 1.0, 2.0):
        recs, leads, misses = [], [], 0
        for _ in range(cycles):
            t, n, first = 0.0, 0, None
            done_at = None
            while True:
                t += rng.expovariate(lam)
                if done_at is not None and t >= done_at: break
                if t >= ttl:
                    misses += 1; n += 1
                    if done_at is None: done_at = t + delta; first = t
                    continue
                if t - delta * beta * math.log(1.0 - rng.random()) >= ttl:
                    n += 1
                    if done_at is None:
                        done_at = t + delta; first = t
            recs.append(n); leads.append(ttl - first)
        mr = sum(recs) / cycles; ml = sum(leads) / cycles
        p1 = sum(1 for r in recs if r > 1) / cycles
        print(f"XFetch beta={beta}: mean recomputes {mr:.2f}, P(>1) {100*p1:.1f}%, "
              f"mean lead before expiry {1000*ml:.0f} ms, hard misses {misses}")
        out[f"xf{beta}"] = dict(mean=round(mr,2), p_gt1=round(100*p1,1), lead_ms=round(1000*ml),
                               misses=misses)
    OUT["e3"] = out

def e6():
    hdr("E6  Lease locks: holder still writing after its lease expired")
    rng = random.Random(SEED + 6)
    n = 200000
    out = {}
    def pause():
        if rng.random() < 0.02:
            return 0.5 / (1.0 - rng.random()) ** (1 / 1.5)   # Pareto alpha 1.5, xm 0.5 s
        return 0.0
    print("work ~ lognormal(median 2 s, sigma 0.5); 2% of acquisitions hit a pause ~ Pareto(1.5, 0.5 s)")
    for ttl in (5, 10, 20, 30, 60):
        stale = renew_stale = 0
        for _ in range(n):
            w = math.exp(math.log(2.0) + 0.5 * rng.gauss(0, 1))
            p = pause()
            if w + p > ttl: stale += 1
            # watchdog renewal every ttl/3; the pause stops the renewer too.
            # lease expires if the pause outlasts the remaining lease at pause start.
            # the pause starts at a uniform point s of the work; the lease was last
            # renewed at the most recent multiple of ttl/3 before s
            s = rng.random() * w
            ph = s % (ttl / 3)
            if p > ttl - ph: renew_stale += 1
        out[str(ttl)] = dict(stale=round(100*stale/n,3), renew=round(100*renew_stale/n,3))
        print(f"TTL {ttl:3d} s: stale writes {100*stale/n:6.3f}%  with watchdog renewal {100*renew_stale/n:6.3f}%  "
              f"with fencing token accepted 0.000%")
    OUT["e6"] = out

def crc16(data: bytes) -> int:
    crc = 0
    for b in data:
        crc ^= b << 8
        for _ in range(8):
            crc = ((crc << 1) ^ 0x1021) & 0xFFFF if crc & 0x8000 else (crc << 1) & 0xFFFF
    return crc

def key_slot(key: str) -> int:
    s = key.find("{")
    if s != -1:
        e = key.find("}", s + 1)
        if e != -1 and e != s + 1:
            key = key[s+1:e]
    return crc16(key.encode()) & 16383

def e8():
    hdr("E8  Rate limiters: 100 requests per 60 s, adversarial client")
    L, W = 100, 60.0
    # adversary: idle, then tries every 10 ms from t=50 s to t=200 s (crosses boundaries)
    times = [50.0 + 0.01 * i for i in range(int(150 / 0.01))]
    def maxwin(adm):
        best = j = 0
        for i in range(len(adm)):
            while adm[i] - adm[j] >= W: j += 1
            best = max(best, i - j + 1)
        return best
    res = {}
    # fixed window
    adm, cur, c = [], -1, 0
    for t in times:
        w = int(t // W)
        if w != cur: cur, c = w, 0
        if c < L: c += 1; adm.append(t)
    res["fixed window"] = (maxwin(adm), len(adm), "1 counter")
    # sliding log
    adm, log = [], []
    for t in times:
        while log and t - log[0] >= W: log.pop(0)
        if len(log) < L: log.append(t); adm.append(t)
    res["sliding log"] = (maxwin(adm), len(adm), f"{L} timestamps")
    # sliding window counter
    adm, counts = [], {}
    for t in times:
        w = int(t // W); el = (t - w * W) / W
        est = counts.get(w - 1, 0) * (1 - el) + counts.get(w, 0)
        if est < L: counts[w] = counts.get(w, 0) + 1; adm.append(t)
    res["sliding counter"] = (maxwin(adm), len(adm), "2 counters")
    # token bucket (equivalently GCRA), capacity L, refill L/W per s, starts full
    adm, tok, last = [], float(L), 0.0
    for t in times:
        tok = min(L, tok + (t - last) * L / W); last = t
        if tok >= 1: tok -= 1; adm.append(t)
    res["token bucket"] = (maxwin(adm), len(adm), "2 fields")
    for k, (mw, tot, mem) in res.items():
        print(f"{k:16s} max admitted in any 60 s window {mw:4d}  ({mw/L:.2f}x)  total {tot:4d}  state {mem}")
    OUT["e8"] = {k: dict(maxwin=v[0], total=v[1], state=v[2]) for k, v in res.items()}
