Graphics Systems

Hardware, software, GPUs, APIs, displays, input and output devices, graphics engines and rendering engines

Prepared November 2026 · References follow the Vancouver (numbered) style

Abstract. A graphics system is the combination of hardware and software that turns a description of a scene into an image that a person can see, and that turns the person's actions back into changes to that scene. This article walks through each layer of such a system: the hardware that stores and scans out pixels, the software that models, transforms and rasterizes geometry, the graphics processing unit (GPU) that runs that work in parallel, the application programming interfaces (APIs) that sit between programs and GPUs, the display technologies that emit light, the devices people use to give input and receive output, and the graphics and rendering engines that bind it all together. Each section includes worked examples, source code, diagrams and exercises with solutions. Three small live demonstrations (a software rasterizer, a WebGL triangle and a ray tracer) run directly in this page.

1. Introduction: what a graphics system is

Computer graphics is the creation, storage and manipulation of models and images by computer [1,2]. Interactive computer graphics began with Ivan Sutherland's Sketchpad (1963), which let a user draw and constrain shapes directly on a display with a light pen [3]. Every system since has had the same basic structure: an application holds a model of something (a CAD part, a game world, a chart), software converts that model into an image, hardware stores the image and drives a display, and input devices let the user act on the model again [1].

Figure 1 shows this loop in a modern desktop or mobile computer. The central processing unit (CPU) runs the application and the graphics driver. The GPU, which has its own high-bandwidth memory, does the heavy per-vertex and per-pixel work. A display controller reads the finished image from a region of memory called the framebuffer and sends it to the screen many times per second [1,4].

The rest of this article follows the figure from hardware upward. Two ideas recur throughout. The first is the pipeline: images are made by passing data through a fixed sequence of stages, each of which can run in parallel with the others [4]. The second is abstraction: each layer (driver, API, engine) hides the detail of the layer below it so that programs can run on many kinds of hardware [1,5].

2. Graphics hardware

2.1 Vector and raster displays

Early graphics hardware used vector (random-scan) displays. The display processor steered a cathode-ray tube's electron beam directly along each line segment of the picture, so the image was a list of drawing commands that had to be redrawn continuously [1]. Almost all modern systems use raster displays instead. A raster image is a rectangular grid of picture elements (pixels), stored in memory and sent to the screen row by row in a fixed order, regardless of what the picture contains [1,2]. Figure 2 compares the two.

2.2 The framebuffer

The framebuffer is the block of memory that holds one value per pixel. Its size depends on the resolution and on the number of bits per pixel (the color depth) [1,4]:

framebuffer bytes = width × height × (bits per pixel ÷ 8)

A 1920 × 1080 image with 8 bits for each of red, green, blue and alpha (32 bits per pixel) needs 1920 × 1080 × 4 = 8,294,400 bytes, just under 8 MiB. Real systems keep more than one buffer. A depth buffer (z-buffer) stores, for each pixel, the distance to the nearest surface drawn so far, so that hidden surfaces can be removed simply by comparing depths. The z-buffer was described by Catmull in 1974 [6] and is now built into every GPU [4]. Systems also double- or triple-buffer the color image so that the display never shows a half-drawn frame (Section 6.3).

2.3 The parts of a graphics card

A discrete graphics card, or the graphics block in a system-on-chip, combines several kinds of hardware [4,7]:

  • Programmable shader cores, many simple processors that run small programs (shaders) on vertices, pixels and general data (Section 4).
  • Fixed-function units for jobs that are the same in every program: primitive assembly, rasterization, texture filtering, depth testing and blending, and in recent designs ray–triangle intersection [4,8].
  • Video memory with very high bandwidth, plus caches. Graphics is usually limited by how fast data can be moved, not by arithmetic [7,9].
  • A display controller (scan-out engine) that reads the framebuffer at the display's refresh rate and sends pixels over a link such as HDMI or DisplayPort.
  • A host interface, usually a PCI Express bus on desktops, through which the CPU sends commands and data. Integrated GPUs share system memory with the CPU instead [7].

Dedicated graphics hardware is old. Clark's Geometry Engine (1982) put the transformation and clipping of geometry into a custom VLSI chip [10], and Silicon Graphics' RealityEngine (1993) combined geometry processors, rasterizers and texture-mapping hardware into a complete, highly parallel pipeline [11]. The modern GPU descends from those designs (Section 4.1).

2.4 Scan conversion in hardware: Bresenham's algorithm

The most basic hardware job is scan conversion: deciding which pixels best represent a geometric shape. Bresenham published his line algorithm in 1965 to drive a digital pen plotter [12]. Its value is that it uses only integer addition, subtraction and bit shifts, which are cheap in hardware. For a line with slope between 0 and 1, it steps one pixel in x at a time and keeps an integer decision variable D that says whether the true line has moved more than half a pixel above the current row [1,12].

Listing 1. Bresenham's line algorithm for all octants (C).

#include <stdlib.h>   /* abs */

void plot(int x, int y);   /* writes one pixel to the framebuffer */

/* Integer-only line drawing. Works for every slope and direction. */
void bresenham_line(int x0, int y0, int x1, int y1)
{
    int dx =  abs(x1 - x0), sx = (x0 < x1) ? 1 : -1;
    int dy = -abs(y1 - y0), sy = (y0 < y1) ? 1 : -1;
    int err = dx + dy;                 /* error term e_xy */

    for (;;) {
        plot(x0, y0);
        if (x0 == x1 && y0 == y1) break;
        int e2 = 2 * err;
        if (e2 >= dy) { err += dy; x0 += sx; }   /* step in x */
        if (e2 <= dx) { err += dx; y0 += sy; }   /* step in y */
    }
}

3. Graphics software

3.1 Layers of graphics software

Graphics software is built in layers (Figure 4). At the top are applications and the engines or toolkits they are built on. Below them, a graphics API such as Vulkan, Direct3D 12, Metal, OpenGL or WebGPU gives a standard way to describe drawing work. A vendor driver translates API calls into commands for one particular GPU and compiles shaders into its machine code. The operating system manages GPU memory, schedules work from different programs, and composites application windows into the final screen image [4,13,14].

3.2 Modeling and transformation

Most 3D scenes are modeled as meshes of triangles, because a triangle is always planar and convex and is easy to rasterize [2,4]. Each vertex passes through a chain of coordinate systems (Figure 5). Using homogeneous coordinates, a 3D point is written as a 4-vector (x, y, z, 1), so that translation, rotation, scaling and perspective projection can all be expressed as 4 × 4 matrix multiplications and combined into one matrix [1,2].

The perspective projection matrix is the one non-affine step. It copies −z (the distance in front of the camera) into the w component, so that the later divide by w makes distant objects smaller. Listing 2 builds the standard OpenGL-convention matrix, which maps the view frustum to the cube −1 ≤ x, y, z ≤ 1 [2,15].

Listing 2. A perspective projection matrix and a matrix–vector product (JavaScript, column-major like OpenGL).

// fovy in radians; returns a Float32Array in column-major order.
function perspective(fovy, aspect, near, far) {
  const f = 1 / Math.tan(fovy / 2);
  const nf = 1 / (near - far);
  return new Float32Array([
    f / aspect, 0, 0,                    0,
    0,          f, 0,                    0,
    0,          0, (far + near) * nf,   -1,
    0,          0, 2 * far * near * nf,  0,
  ]);
}

// out = m * v, with m column-major and v = [x, y, z, w]
function transform(m, v) {
  const out = [0, 0, 0, 0];
  for (let row = 0; row < 4; row++)
    for (let col = 0; col < 4; col++)
      out[row] += m[col * 4 + row] * v[col];
  return out;
}

const P = perspective(Math.PI / 3, 16 / 9, 0.1, 100);
const clip = transform(P, [1, 1, -5, 1]);
const ndc  = clip.slice(0, 3).map(c => c / clip[3]);   // perspective divide
console.log(ndc);   // x, y shrink with distance; z lies in [-1, 1]

3.3 Rasterization with edge functions

Once triangles are in window coordinates, the rasterizer finds the pixels whose centers lie inside each triangle. Pineda showed in 1988 that this test can be done in parallel for every pixel with edge functions [16]. For a directed edge from a to b, the function

E(p) = (bx − ax)(py − ay) − (by − ay)(px − ax)

is positive on one side of the edge, negative on the other and zero on it. A point is inside a triangle when all three edge functions have the same sign. The three values, divided by the triangle's doubled area, are also the point's barycentric coordinates, which are used to interpolate colors, texture coordinates and depth across the triangle [2,4,16]. Because each pixel is independent, GPUs evaluate edge functions for blocks of pixels at once. The live demo below runs the same algorithm in JavaScript.

Demo 1: software rasterizer with barycentric color interpolation.

Listing 3. The core of the Demo 1 rasterizer (JavaScript).

function edge(a, b, p) {                       // Pineda edge function
  return (b.x - a.x) * (p.y - a.y) - (b.y - a.y) * (p.x - a.x);
}

function drawTriangle(img, v0, v1, v2) {        // img: ImageData
  const area = edge(v0, v1, v2);
  if (area === 0) return;                       // degenerate triangle
  const minX = Math.max(0, Math.floor(Math.min(v0.x, v1.x, v2.x)));
  const maxX = Math.min(img.width - 1, Math.ceil(Math.max(v0.x, v1.x, v2.x)));
  const minY = Math.max(0, Math.floor(Math.min(v0.y, v1.y, v2.y)));
  const maxY = Math.min(img.height - 1, Math.ceil(Math.max(v0.y, v1.y, v2.y)));

  for (let y = minY; y <= maxY; y++) {
    for (let x = minX; x <= maxX; x++) {
      const p = { x: x + 0.5, y: y + 0.5 };     // sample at pixel center
      const w0 = edge(v1, v2, p) / area;        // barycentric weights
      const w1 = edge(v2, v0, p) / area;
      const w2 = edge(v0, v1, p) / area;
      if (w0 < 0 || w1 < 0 || w2 < 0) continue; // outside the triangle
      const i = 4 * (y * img.width + x);
      for (let c = 0; c < 3; c++)               // interpolate RGB
        img.data[i + c] = w0 * v0.rgb[c] + w1 * v1.rgb[c] + w2 * v2.rgb[c];
      img.data[i + 3] = 255;
    }
  }
}

3.4 Compositing

Graphics software often combines separately rendered images, for example a user-interface layer over a 3D view, or each window on a desktop. Porter and Duff defined the algebra for this in 1984 by storing an alpha (coverage) value with every pixel [17]. Their over operator, written for colors that are already multiplied by their alpha (premultiplied), is

Cout = Cs + Cd(1 − αs),    αout = αs + αd(1 − αs)

where s is the source (top) layer and d the destination. The same equation is what a GPU's blending hardware computes when an API sets the blend factors to (ONE, ONE_MINUS_SRC_ALPHA) [4,15].

4. Graphics processing units (GPUs)

4.1 From fixed function to programmable, unified cores

Early consumer graphics accelerators implemented a fixed pipeline: the application could set parameters (light positions, texture modes), but could not change the algorithm. In 2001, Lindholm, Kilgard and Moreton described a user-programmable vertex engine that let applications supply their own per-vertex programs [18]. Programmable pixel (fragment) processing followed, and high-level languages such as Cg made shaders practical to write [19]. Direct3D 10 then defined a common instruction set for all shader stages [20], and NVIDIA's Tesla architecture (2006) replaced separate vertex and pixel processors with one array of unified processors that could run any stage, as well as general-purpose compute programs [21]. Since then GPUs have been used for scientific computing and machine learning as well as graphics [22,23]. In 2018, NVIDIA's Turing architecture added fixed-function ray-tracing units that traverse bounding-volume hierarchies and test rays against triangles in hardware [8].

4.2 The logical graphics pipeline

Every modern API exposes roughly the same logical pipeline (Figure 6) [4,13,15]. Programmable stages run shader programs written by the application; fixed-function stages are configured but not programmed.

4.3 How a GPU runs shaders: throughput over latency

A CPU core is designed to finish one thread as fast as possible, using large caches, branch prediction and out-of-order execution. A GPU is designed for throughput: it spends its transistors on many simple arithmetic units and hides memory latency by keeping a very large number of threads in flight, switching to another group of threads whenever one group waits on memory [7,9].

The GPU groups threads that run the same shader into batches that execute one instruction at a time across all their lanes. NVIDIA calls this model single-instruction, multiple-thread (SIMT) and the batch of 32 threads a warp [21,24]; AMD calls the batch a wavefront. When threads in a warp take different sides of a branch, the hardware runs each side in turn with the inactive lanes masked off. This is called divergence, and it wastes throughput [21,25]. Figure 7 shows the general organization.

4.4 Parallel rendering and work distribution

Because primitives can land anywhere on screen, a parallel renderer must at some point redistribute ("sort") work between processors. Molnar et al. classify parallel renderers by where that sort happens: sort-first (before geometry processing), sort-middle (between geometry and rasterization) and sort-last (after rasterization, by compositing) [26]. Desktop GPUs are mostly sort-middle. Many mobile GPUs use tile-based rendering, which bins triangles into small screen tiles first and then renders each tile entirely in on-chip memory, saving external memory bandwidth and power [4].

4.5 GPU compute

The same cores can run non-graphics programs. In CUDA, the programmer writes a kernel that is launched over a grid of thread blocks; each thread uses its index to choose which data element to process [24,25]. Graphics APIs offer the same model through compute shaders [13,27]. Listing 4 shows the classic SAXPY (y ← a·x + y) operation both ways.

Listing 4a. SAXPY as a CUDA kernel.

__global__ void saxpy(int n, float a, const float *x, float *y)
{
    int i = blockIdx.x * blockDim.x + threadIdx.x;   // global thread index
    if (i < n) y[i] = a * x[i] + y[i];                 // guard the tail
}

// Host side: one thread per element, 256 threads per block.
// saxpy<<<(n + 255) / 256, 256>>>(n, 2.0f, d_x, d_y);

Listing 4b. The same operation as a WebGPU compute shader (WGSL).

struct Params { a : f32, n : u32 };
@group(0) @binding(0) var<uniform> params : Params;
@group(0) @binding(1) var<storage, read>       x : array<f32>;
@group(0) @binding(2) var<storage, read_write> y : array<f32>;

@compute @workgroup_size(256)
fn main(@builtin(global_invocation_id) id : vec3<u32>) {
  let i = id.x;
  if (i < params.n) {
    y[i] = params.a * x[i] + y[i];

Exercises for Section 4

4.1 A warp of 32 threads reaches an if/else. Eight threads take the if branch, which costs 100 cycles; 24 take the else branch, which costs 40 cycles. Under the SIMT model, how long does the warp take, and what fraction of lane-cycles do useful work?

Show solution

Both paths run one after the other, so the warp takes 100 + 40 = 140 cycles. Useful lane-cycles are 8·100 + 24·40 = 1,760 out of 32·140 = 4,480, so efficiency is about 39%. If all 32 threads had taken the else branch, the warp would have needed only 40 cycles [21,25].

4.2 A full-screen pass shades every pixel of a 1920 × 1080 image with one thread per pixel. How many 32-thread warps are needed?

Show solution

1920 × 1080 = 2,073,600 threads; 2,073,600 ÷ 32 = 64,800 warps. The GPU keeps many of these resident at once on each SM so that it can switch between them while others wait on memory [9].

4.3 SAXPY reads two 4-byte floats and writes one per element, and does two floating-point operations (a multiply and an add). Suppose a GPU has 500 GB/s of memory bandwidth and 20 TFLOP/s of arithmetic throughput. Which limit does SAXPY hit, and what is its maximum speed?

Show solution

Each element moves 12 bytes for 2 FLOPs, an arithmetic intensity of 2/12 ≈ 0.167 FLOP/byte. At 500 GB/s, memory allows 500 × 109 × 0.167 ≈ 83 GFLOP/s, far below 20 TFLOP/s. SAXPY is memory-bound; the "roofline" reasoning used here is described by Hennessy and Patterson [7].

5. Graphics APIs

5.1 What an API does

A graphics API defines the objects (buffers, textures, shaders, pipelines), the commands (draw, dispatch, copy) and the rules for ordering and synchronization that a program uses to drive a GPU. It lets the same program run on hardware from different vendors, because each vendor's driver implements the specification [13,15]. Shading languages are part of the API: GLSL for OpenGL and Vulkan [28], HLSL for Direct3D [29], the Metal Shading Language for Metal [30] and WGSL for WebGPU [31]. Vulkan consumes shaders in SPIR-V, a binary intermediate representation that several source languages can compile to [32].

5.2 Two generations of design

OpenGL, which Silicon Graphics created and which the Khronos Group now maintains, and Direct3D up to version 11 present the GPU as a state machine: the program sets current state and issues draws, and the driver works out memory placement, hazards and synchronization behind the scenes [4,15]. That made them easy to use but gave the driver work that is hard to predict and hard to spread across CPU threads.

The explicit APIs (Vulkan, Direct3D 12 and Metal, and in the browser WebGPU) move that work to the application. Programs allocate memory themselves, record command buffers on any thread, build pipeline state objects up front so shaders can be compiled before drawing, and insert their own barriers and fences [13,14,30]. WebGPU keeps the same structure but adds validation and automatic resource-state tracking so that it is safe to expose to web pages [27].

frame = (frame + 1) % MAX_FRAMES_IN_FLIGHT;
Why the extra work? Fences let the CPU know when the GPU is done with a frame's resources; semaphores order work between GPU queues and the presentation engine. In OpenGL the driver inserts equivalent synchronization implicitly. Making it explicit lets an engine record commands on many threads and avoid unpredictable stalls [4,13].

6. Display systems

6.1 Display technologies

A display converts the electrical signal for each pixel into light. The main technologies differ in how they do this [1,35]:

  • Cathode-ray tube (CRT). An electron beam scans phosphor dots row by row; the phosphor glows briefly, so the image must be refreshed many times per second to avoid visible flicker [1].
  • Liquid-crystal display (LCD). A backlight shines through a layer of liquid crystal whose orientation, set by an electric field, controls how much light passes through polarizers and color filters. Heilmeier and colleagues demonstrated electrically controlled liquid-crystal light modulation in 1968 [36]. Each pixel is held by a thin-film transistor between refreshes, so LCDs do not flicker the way CRTs do, but black levels depend on how well the crystal blocks the backlight.
  • Organic light-emitting diode (OLED). Each subpixel is a thin organic film that emits its own light when current flows. Tang and VanSlyke reported an efficient organic electroluminescent device in 1987 [37]. Because pixels can switch fully off, OLEDs give very deep blacks.
  • Projectors and head-mounted displays use microdisplays (LCD, LCoS, micro-mirror or micro-OLED) with optics that magnify the image onto a screen or into the eye [4].

6.2 Resolution, refresh rate and pixel density

A display's resolution is its pixel count; its refresh rate is how many new images it can show per second. Together these set the time the renderer has for each frame: 1000 / f milliseconds at f Hz, so 16.7 ms at 60 Hz [4]. Pixel density, in pixels per inch (PPI), is the diagonal pixel count divided by the diagonal size in inches; how sharp the image looks also depends on viewing distance [35].

6.3 Double buffering, vertical sync and tearing

If a program drew directly into the buffer the display was reading, the viewer would see partly drawn frames. Instead the program draws into a back buffer while the display scans out the front buffer; when the frame is done, the two are swapped. If the swap happens while the display is in the middle of a scan, the top of the screen shows the old frame and the bottom the new one, a visible seam called tearing. Waiting for the vertical blanking interval before swapping (vsync) prevents tearing but can add latency and, if a frame misses its deadline, makes it wait for the next refresh. Triple buffering and variable-refresh-rate displays reduce these problems [1,4]. Figure 8 shows the timing.

6.4 Color: gamut, transfer functions and HDR

A display's gamut is the range of colors its three primaries can mix. Standards fix the primaries and white point so that content looks the same on different devices. The sRGB standard used on most computer displays shares its primaries with ITU-R BT.709 (HDTV) and uses the D65 white point [34,38]. Ultra-high-definition television (ITU-R BT.2020) specifies much more saturated primaries [39]. Figure 9 compares the two on the CIE 1931 chromaticity diagram.

Pixel values are not proportional to light. Human vision is more sensitive to differences between dark tones than between bright ones, so images are stored with a nonlinear transfer function ("gamma") that spends more code values on dark tones [35]. The sRGB transfer function is defined piecewise in IEC 61966-2-1 [38]; Listing 7 implements it. Lighting calculations and blending must be done on linear values, so renderers decode textures to linear on read and encode back to sRGB on write; GPUs do both in hardware for sRGB-format textures and framebuffers [4,15].

Listing 7. The sRGB transfer functions (C).

#include <math.h>

/* Encoded sRGB value (0..1) -> linear light (0..1). IEC 61966-2-1. */
double srgb_to_linear(double c)
{
    return (c <= 0.04045) ? c / 12.92
                          : pow((c + 0.055) / 1.055, 2.4);
}

/* Linear light (0..1) -> encoded sRGB value (0..1). */
double linear_to_srgb(double l)
{
    return (l <= 0.0031308) ? 12.92 * l
                            : 1.055 * pow(l, 1.0 / 2.4) - 0.055;
}

High dynamic range (HDR) video extends the brightness range as well as the gamut. ITU-R BT.2100 defines two HDR transfer functions: Perceptual Quantization (PQ), which encodes absolute luminance up to 10,000 cd/m², and Hybrid Log-Gamma (HLG), which is designed to stay compatible with standard-range displays [40].

7. Input and output devices

7.1 Input devices

Interactive graphics depends on input devices that let a person point, select and manipulate. Sketchpad used a light pen pointed directly at the screen [3]. In 1967, English, Engelbart and Berman compared the light pen, joystick, knee control and a new device, the mouse, for selecting text on a display, and found the mouse fastest and most accurate overall [41]. Myers traces how these research devices became today's standard interfaces [42]. Common devices today include:

  • Keyboards and mice, and trackpads that report relative motion and gestures.
  • Touchscreens and pen tablets that report absolute position, often with pressure and tilt; browsers expose mouse, pen and touch through one unified Pointer Events interface [43].
  • Game controllers with analog sticks, triggers and buttons.
  • Six-degree-of-freedom (6-DoF) trackers for head-mounted displays and hand controllers, which report position and orientation. Sutherland built the first head-mounted 3D display, with head tracking, in 1968 [44].
  • Cameras and depth sensors for hand, body and eye tracking.

Most of these connect over USB using the Human Interface Device (HID) class, in which a device sends a report descriptor that tells the host what its reports contain, so one generic driver can serve many devices [45].

7.2 Logical input devices

Graphics standards separate a physical device from the role it plays. The Graphical Kernel System (GKS), the first ISO graphics standard, defined six logical input device classes: locator (a position), stroke (a sequence of positions), valuator (a scalar value), choice (one of a set of alternatives), pick (an object on screen) and string (text) [1,46]. A touchscreen can act as a locator, a stroke or a pick device depending on the application. Programs read input either by polling a device's current state (common in games, once per frame) or by handling events from a queue (common in desktop and web applications) [1,5].

7.3 From pointer to scene: picking

To find what the user clicked in a 3D scene, the program reverses the transformation chain of Figure 5. The pixel position is converted to normalized device coordinates, then multiplied by the inverse of the projection and view matrices to get a ray in world space, which is then intersected with scene objects [2,4]. Listing 8 does the first step with Pointer Events [43].

Listing 8. Pointer position to NDC, and NDC to a world-space ray (JavaScript).

canvas.addEventListener('pointerdown', (e) => {
  const r = canvas.getBoundingClientRect();
  const px = e.clientX - r.left, py = e.clientY - r.top;
  const ndcX = (2 * px) / r.width - 1;          // left -1 .. right +1
  const ndcY = 1 - (2 * py) / r.height;         // top +1 .. bottom -1 (y flips)
  const ray = pickRay(ndcX, ndcY, invViewProj); // see below
  const hit = scene.intersect(ray);
  if (hit) select(hit.object);
});

// Unproject two points (near and far plane) and join them.
function pickRay(x, y, invVP) {
  const unproject = (z) => {
    const p = transform(invVP, [x, y, z, 1]);   // transform() from Listing 2
    return [p[0] / p[3], p[1] / p[3], p[2] / p[3]];
  };
  const near = unproject(-1), far = unproject(1);  // OpenGL NDC depth range
  const d = far.map((v, i) => v - near[i]);
  const len = Math.hypot(...d);
  return { origin: near, dir: d.map(v => v / len) };
}

7.5 Output devices beyond the monitor

Besides displays (Section 6), graphics systems drive printers, plotters, 3D printers, VR headsets and haptic devices. Pen plotters are vector devices that draw line segments directly; Bresenham's algorithm was invented for one [12]. Printers are raster devices, but most can place only a dot or no dot of each ink, so they reproduce continuous tone by halftoning: spreading dots so that their average density matches the desired gray [47]. Error diffusion, introduced by Floyd and Steinberg in 1976, rounds each pixel to the nearest available level and pushes the rounding error onto neighbors that have not yet been processed, using the weights 7/16, 3/16, 5/16 and 1/16 [47,48]. Listing 9 implements it.

Listing 9. Floyd–Steinberg error diffusion to 1-bit output (Python).

def floyd_steinberg(img):
    """img: list of rows of floats in [0, 1] (linear gray). Modified in place;
    returns a list of rows of 0/1 dots."""
    h, w = len(img), len(img[0])
    out = [[0] * w for _ in range(h)]
    for y in range(h):
        for x in range(w):
            old = img[y][x]
            new = 1 if old >= 0.5 else 0
            out[y][x] = new
            err = old - new
            if x + 1 < w:               img[y][x + 1]     += err * 7 / 16
            if y + 1 < h and x > 0:     img[y + 1][x - 1] += err * 3 / 16
            if y + 1 < h:               img[y + 1][x]     += err * 5 / 16
            if y + 1 < h and x + 1 < w: img[y + 1][x + 1] += err * 1 / 16
    return out

8. Graphics engines

8.1 What an engine provides

A graphics engine, and its larger relative the game engine, is a reusable software framework that sits between an application's content and the graphics API. Gregory describes a game engine as a set of runtime layers (platform independence, core systems, resource management, rendering, collision and physics, animation, audio, input, and gameplay foundations) plus a set of tools for building content [5]. Commercial and open-source engines such as Unreal Engine, Unity and Godot follow this general structure [49–51]. Figure 11 shows the layers.

8.2 The game loop

At the heart of every interactive engine is a loop that reads input, updates the simulation and renders a frame, as fast as the display allows [5]. Physics and gameplay are usually stepped with a fixed time step so that results do not depend on frame rate, while rendering runs as often as possible and interpolates between the last two simulation states to look smooth (Listing 10).

Listing 10. A fixed-timestep game loop with render interpolation (C++).

#include <chrono>

void runGameLoop(Game& game, Renderer& renderer)
{
    using clock = std::chrono::steady_clock;
    const double dt = 1.0 / 60.0;          // simulation step: 60 Hz
    double accumulator = 0.0;
    auto previous = clock::now();

    while (game.running()) {
        auto now = clock::now();
        double frameTime = std::chrono::duration<double>(now - previous).count();
        previous = now;
        if (frameTime > 0.25) frameTime = 0.25;   // avoid a "spiral of death"
        accumulator += frameTime;

        game.pollInput();

        while (accumulator >= dt) {               // catch up in fixed steps
            game.savePreviousState();
            game.update(dt);
            accumulator -= dt;
        }

        double alpha = accumulator / dt;          // 0..1 between two states
        renderer.draw(game.interpolatedState(alpha));
        renderer.present();                       // may block on vsync
    }
}

8.3 Scenes, components and data layout

Engines organize the world as a scene graph, a hierarchy in which each node's transform is relative to its parent, so moving a car also moves its wheels [1,5]. Many engines now also use an entity–component–system (ECS) design, in which an entity is just an identifier, components are plain data stored in tightly packed arrays, and systems loop over every entity that has a given set of components. Storing each component type contiguously makes the loops friendly to CPU caches and easy to split across threads [5].

Listing 11. A minimal entity–component–system sketch (C++).

#include <vector>
#include <cstdint>

using Entity = std::uint32_t;
struct Position { float x, y, z; };
struct Velocity { float x, y, z; };

struct World {
    // Structure of arrays: each component type is stored contiguously.
    std::vector<Entity>   movers;      // entities that have both components
    std::vector<Position> positions;   // positions[i] belongs to movers[i]
    std::vector<Velocity> velocities;

    Entity spawn(Position p, Velocity v) {
        Entity e = static_cast<Entity>(movers.size());
        movers.push_back(e); positions.push_back(p); velocities.push_back(v);
        return e;
    }
};

// A "system": a tight loop over packed data, easy to vectorize or split.
void movementSystem(World& w, float dt) {
    for (std::size_t i = 0; i < w.movers.size(); ++i) {
        w.positions[i].x += w.velocities[i].x * dt;
        w.positions[i].y += w.velocities[i].y * dt;
        w.positions[i].z += w.velocities[i].z * dt;
    }
}

9. Rendering engines

9.1 Two ways to find what is visible

A rendering engine is the part of the system that turns a scene description into pixels. Every renderer must solve visibility: for each pixel, which surface is seen? There are two basic orderings (Figure 13) [2,4,54]:

  • Rasterization (object order): for each triangle, find the pixels it covers, and keep the nearest using the z-buffer. This is what the GPU pipeline of Figure 6 does, and it is the basis of real-time rendering [4].
  • Ray tracing (image order): for each pixel, cast a ray into the scene and find the nearest surface it hits. Whitted's 1980 algorithm extended this recursively with reflection, refraction and shadow rays [55].

9.2 The rendering equation

Kajiya's rendering equation (1986) states what a physically correct renderer must compute [56]. In the form used by Pharr, Jakob and Humphreys [54], the radiance Lo leaving point p in direction ωo is

Lo(p, ωo) = Le(p, ωo) + ∫Ω fr(p, ωo, ωi) Li(p, ωi) |cos θi| dωi

where Le is emitted light, fr is the bidirectional reflectance distribution function (BRDF) describing the material, Li is light arriving from direction ωi, and the integral covers the hemisphere Ω above the surface (Figure 14). Because Li is itself the light leaving some other surface, the equation is recursive. Path tracing estimates the integral by Monte Carlo sampling of random light paths; its error falls in proportion to 1/√N for N samples per pixel [54,56].

9.3 Shading models

Real-time renderers approximate the integral with a small number of lights and simplified BRDFs. Gouraud (1971) interpolated colors computed at vertices [57]; Phong (1975) interpolated normals and added a specular highlight term [58]; Blinn (1977) reformulated the highlight using the half vector h between the light and view directions [59]. Modern engines use physically based BRDFs with energy-conserving microfacet specular terms, such as the model Karis described for Unreal Engine 4 [54,60]. Listing 12 is a Blinn–Phong fragment shader.

Listing 12. Blinn–Phong shading for one directional light (GLSL).

#version 300 es
precision highp float;

in vec3 vNormal;          // world-space normal (interpolated)
in vec3 vWorldPos;
uniform vec3 uLightDir;   // direction *towards* the light, normalized
uniform vec3 uCameraPos;
uniform vec3 uAlbedo;
uniform float uShininess; // e.g. 32.0
out vec4 outColor;

void main() {
  vec3 n = normalize(vNormal);
  vec3 l = normalize(uLightDir);
  vec3 v = normalize(uCameraPos - vWorldPos);
  vec3 h = normalize(l + v);                              // Blinn half vector

  float diffuse  = max(dot(n, l), 0.0);                   // Lambert
  float specular = (diffuse > 0.0) ? pow(max(dot(n, h), 0.0), uShininess) : 0.0;

  vec3 color = 0.05 * uAlbedo + diffuse * uAlbedo + specular * vec3(1.0);
  outColor = vec4(color, 1.0);  // write to an sRGB framebuffer to encode
}

9.4 A small ray tracer

The core operation of a ray tracer is intersecting a ray with geometry. A ray o + t·d meets a sphere of center c and radius r where |o + t·d − c|² = r², a quadratic in t [2,54]. Demo 3 uses this, Blinn–Phong shading, a shadow ray and one level of mirror reflection, in the manner of Whitted [55], all on the CPU.

Demo 3: Whitted-style ray tracer in JavaScript.

Listing 13. Ray–sphere intersection (C++).

#include <cmath>
#include <optional>

struct Vec3 { double x, y, z; };
inline Vec3   operator-(Vec3 a, Vec3 b) { return {a.x-b.x, a.y-b.y, a.z-b.z}; }
inline double dot(Vec3 a, Vec3 b)       { return a.x*b.x + a.y*b.y + a.z*b.z; }

// Returns the nearest t > eps where origin + t*dir hits the sphere.
std::optional<double> hitSphere(Vec3 origin, Vec3 dir, Vec3 center, double radius)
{
    const double eps = 1e-6;
    Vec3 oc = origin - center;
    double a = dot(dir, dir);
    double halfB = dot(oc, dir);
    double c = dot(oc, oc) - radius * radius;
    double disc = halfB * halfB - a * c;
    if (disc < 0) return std::nullopt;         // ray misses
    double s = std::sqrt(disc);
    double t = (-halfB - s) / a;                // nearer root first
    if (t > eps) return t;
    t = (-halfB + s) / a;                       // origin inside sphere
    if (t > eps) return t;
    return std::nullopt;
}

9.5 Real-time rendering architectures

A real-time rendering engine organizes a frame as a sequence of passes. In forward rendering, each object is shaded with all the lights that affect it as it is drawn. In deferred rendering, introduced in hardware by Deering et al. in 1988 [61], a first pass writes surface attributes (albedo, normal, roughness, depth) into a set of screen-sized buffers called the G-buffer, and a second pass computes lighting once per pixel. This decouples the cost of lights from the cost of geometry, at the price of memory bandwidth and difficulty with transparency and hardware antialiasing [4] (Figure 15). Other common passes include shadow maps, which render depth from the light's viewpoint and compare against it [62], screen-space effects, and post-processing such as tone mapping.

9.6 Offline and hybrid rendering

Film production uses offline renderers that can spend minutes or hours per frame. Pixar's Reyes architecture (1987) diced surfaces into micropolygons smaller than a pixel and shaded those [63]; Cook, Porter and Carpenter's distributed ray tracing (1984) added motion blur, depth of field and soft shadows by sampling over time, lens and light area [64]. Modern production renderers are mostly physically based path tracers [54]. Hardware ray-tracing units now let real-time engines combine both approaches: rasterize primary visibility, then trace rays for shadows, reflections or global illumination, using denoising to cope with few samples per pixel [4,8].

10. Summary and further reading

A graphics system is a pipeline of layers that each solve one part of the problem of making images interactively:

  • Hardware stores pixels in framebuffers and scans them out; fixed-function units do the operations every program needs [1,4].
  • Software models scenes, transforms them through a chain of coordinate spaces, rasterizes and composites [2,17].
  • GPUs achieve throughput by running many threads in SIMT groups and hiding latency by switching between them [9,21].
  • APIs standardize access to GPUs; modern explicit APIs give the application control of memory and synchronization [13,14,27,30].
  • Displays convert values to light under defined gamuts and transfer functions [38–40].
  • Input and output devices close the interaction loop, and their latency shapes how the system feels [4,41,46].
  • Graphics engines organize content, simulation and rendering around a game loop [5].
  • Rendering engines approximate the rendering equation with rasterization, ray tracing or both [4,54,56].

For further study, Hughes et al. [1] and Marschner and Shirley [2] cover the foundations, Akenine-Möller et al. [4] is the standard reference for real-time techniques, Pharr, Jakob and Humphreys [54] cover physically based rendering in depth (and the full text is freely available online), and Gregory [5] covers engine architecture. The API specifications [13,15,27] are the final word on API behavior.
