Mainframe Hardware Architecture

Processors, memory, I/O, reliability, cryptography and hardware management on IBM Z: a technical article with worked examples, source code and exercises

Abstract. The IBM mainframe is the longest-lived compatible computer architecture in commercial use: programs written for System/360 in the 1960s can still run unmodified on current IBM Z machines.1,2 This article describes the hardware that makes that possible. It covers the central processor complex and the z/Architecture instruction set, multi-core and multi-processor organisation, the memory and cache hierarchy, the channel subsystem and storage controllers, the redundancy and fault-tolerance mechanisms behind mainframe availability, the on-chip and adapter-based cryptographic hardware, and the Hardware Management Console. Each section includes concrete examples drawn from recent machines (chiefly IBM z15 and z16, with notes on z17), and most include source code in High Level Assembler (HLASM), REXX, JCL or IOCP. Exercises with worked solutions close the article.

Scope note. "Mainframe" here means IBM Z and its predecessors (System/360, /370, /390, zSeries, System z). Machine figures quoted are maxima for the named generation and come from IBM's own technical guides; real configurations are usually smaller.

1. Central processing units

On a mainframe the term "CPU" is used in two senses. Architecturally, a CPU is the entity defined in the z/Architecture Principles of Operation: something that fetches and executes instructions, owns a program-status word (PSW) and a register set, and takes interruptions.2 Physically, IBM calls each core a processor unit (PU), and the machine as a whole is the central processor complex (CPC).3,4

1.1 Processor unit characterisation

Every PU on an IBM Z machine is physically identical. At installation (or later, by a concurrent upgrade) each PU is characterised as one of several types, which changes what work it may run and how it is priced, but not its silicon.3,5

1.2 Current processor chips

IBM designs its own mainframe processors. Three recent generations illustrate the direction of travel:

  • z15 processor (IBM z15, 2019): 12 cores per chip at 5.2 GHz in 14 nm silicon-on-insulator technology, with a 256 MB shared L3 cache on each processor chip and a separate system-controller (SC) chip holding a 960 MB L4 cache per drawer.5,6
  • Telum (IBM z16, 2022): 8 cores per chip at 5.2 GHz in 7 nm, each core with a private 32 MB L2. The separate L3 and L4 chips were removed; instead the L2 caches are pooled into a "virtual" L3 and L4 (Section 5). Telum also added an on-chip AI accelerator for inference.3,7,8
  • Telum II (IBM z17, 2025): 8 cores at 5.5 GHz, about 40% more on-chip cache than Telum, a virtual L3 of 360 MB and virtual L4 of 2.88 GB, and an on-chip data processing unit (DPU) for I/O acceleration.9

Mainframe cores run at higher clock frequencies than most server processors and devote unusual amounts of area to cache and to error checking. That reflects the workload: large shared databases and transaction systems with poor locality and a high premium on correctness.10

1.3 The PSW and the register set

Each z/Architecture CPU has a 128-bit PSW holding the instruction address, condition code, addressing mode, interruption masks, protection key and problem/supervisor state. The programmer-visible register set is:2

  • 16 general registers of 64 bits (GR0–GR15);
  • 16 floating-point registers of 64 bits, overlaid on the first halves of 32 vector registers of 128 bits when the vector facility is installed;
  • 16 access registers of 32 bits, used in access-register mode to select address spaces;
  • 16 control registers of 64 bits, used by the operating system;
  • a prefix register, a CPU timer, a clock comparator and the TOD clock.

2. Mainframe processors and instruction sets

2.1 From System/360 to z/Architecture

System/360, announced in 1964, was the first computer family deliberately designed so that one architecture, defined separately from any implementation, would run unchanged on machines of very different speed and cost.1 Amdahl, Blaauw and Brooks defined architecture as "the attributes of a system as seen by the programmer", which is the separation every later IBM mainframe has kept.1

The architecture has been extended rather than replaced: System/370 added virtual storage; 370-XA introduced 31-bit addressing and the channel subsystem; ESA/370 and ESA/390 added access registers and multiple address spaces; and z/Architecture (first shipped on the z900 in 2000) added 64-bit registers and addressing.2,4 Current machines run only in z/Architecture mode, but 24-bit and 31-bit programs still execute because the addressing mode is selected by bits in the PSW.2

2.2 Instruction formats

z/Architecture is a big-endian, byte-addressed, register–memory CISC architecture. Instructions are 2, 4 or 6 bytes long, and the first two bits of the operation code give the length.2 Storage operands are addressed by base + index + displacement, with 12-bit unsigned displacements in the original formats and 20-bit signed "long" displacements in the newer Y-suffixed formats.2

2.3 Notable instruction-set features

  • Decimal arithmetic. Packed-decimal instructions (AP, SP, MP, DP, ZAP, CP, ED) have been in the architecture since System/360, and decimal floating point was added in hardware with the z10 generation; both matter for financial workloads.2,10
  • Atomic primitives. COMPARE AND SWAP (CS, CSG), COMPARE DOUBLE AND SWAP (CDS) and the interlocked-access facility instructions provide serialisation across CPUs (Listing 3).2
  • Vector facility. 32 vector registers of 128 bits with integer, string, floating-point and, on later machines, packed-decimal vector operations.2,5
  • Millicode. Complex instructions are implemented in millicode, a firmware layer written in a subset of z/Architecture plus special instructions, rather than in hard-wired logic.10
  • Architected accelerators. Cryptography (CPACF, Section 11), compression (DEFLATE CONVERSION CALL, DFLTCC, from z15) and on z16 the NEURAL NETWORK PROCESSING ASSIST (NNPA) instruction are exposed as instructions.2,5,8

2.4 Discovering facilities at run time

Because the architecture keeps growing, programs test for optional features with STORE FACILITY LIST EXTENDED (STFLE). STFLE stores a bit string in which bit n is one if facility n is installed; for example, bit 17 indicates the message-security assist (CPACF), bit 129 the vector facility and bit 151 the DEFLATE-conversion facility.2

3. Multi-core and multi-processor architectures

3.1 Drawers, chips and the SMP fabric

A modern IBM Z CPC is a shared-memory symmetric multiprocessor (SMP) built from CPC drawers. A z16 can have up to four drawers, each containing four dual-chip modules (eight Telum chips), memory, and PCIe fan-outs to I/O. The largest model offers up to 200 PUs that can be characterised for customer use and up to 40 TB of customer memory.3 The z15 used a different packaging (up to five drawers, single-chip modules, plus an SC chip per drawer) and offered up to 190 characterisable PUs.5

3.2 Logical partitioning (PR/SM)

The physical SMP is almost never used as a single system. PR/SM (Processor Resource/Systems Manager), a hypervisor that runs in firmware, divides the CPC into up to 85 logical partitions (LPARs) on z16, each running its own operating system.3 An LPAR's logical processors are dispatched on physical PUs; they may be dedicated or shared, with shared processors receiving capacity in proportion to LPAR weights. HiperDispatch lets z/OS cooperate with PR/SM so that a logical processor stays on the same physical core and chip, keeping its cache contents warm.3,12

3.3 Serialisation between processors

All CPUs in a configuration see one storage image, and z/Architecture defines a strong storage-ordering model: with few exceptions, stores by one CPU are observed by other CPUs in the order they were made.2 Programs synchronise with interlocked-update instructions such as COMPARE AND SWAP.

If another CPU changed the counter between the fetch and the CSG, the compare fails, the condition code is set to 1, and the current storage value is placed in R2 so the loop can retry.2

3.4 Clustering beyond one box: Parallel Sysplex

Beyond a single CPC, up to 32 z/OS images can be joined in a Parallel Sysplex, which shares data through one or more coupling facilities (CFs). A CF is an LPAR running Coupling Facility Control Code, usually on ICF processors, that holds lock, cache and list structures accessed over dedicated coupling links.3,13 Because every member can update every database with locking and cache coherence handled by the CF, work can be routed to any member and a failed member's work can be taken over by the survivors (Section 10).13

4. Memory architecture

4.1 Address types

z/Architecture distinguishes three kinds of address:2

  1. Virtual addresses, used by programs, which dynamic address translation (DAT) converts into
  2. real addresses, which prefixing converts into
  3. absolute addresses, which name physical locations in the configuration's main storage.

Prefixing gives each CPU its own 8 KB low-core area (the prefix storage area) holding PSWs and interruption information, even though all CPUs share one absolute storage. Real addresses 0–8191 refer to the area named by the CPU's prefix register, and the absolute block at that prefix maps back to real address 0.2

4.2 Dynamic address translation

A 64-bit virtual address is translated through up to five table levels: region-first, region-second and region-third tables, a segment table and a page table. The base page size is 4 KB; the enhanced-DAT facilities add 1 MB "large" pages (stopping the walk at the segment table) and 2 GB pages (stopping at the region-third table).2 The operating system only builds the upper table levels a given address space actually needs, so small address spaces translate with fewer memory references. Translations are cached in a translation-lookaside buffer (TLB).

4.3 Storage protection

Every 4 KB block of real storage has a storage key: a 4-bit access-control value, a fetch-protection bit, and reference and change bits. A store is permitted only if the PSW key is zero or matches the block's key, and fetches are also checked when fetch protection is on.2 z/OS uses key 0 for the nucleus, keys 1–7 for system components and key 8 for ordinary problem programs, so a stray store from an application cannot overwrite system data.4 The reference and change bits feed the page-replacement algorithm.

4.4 Physical memory and RAIM

Main memory is packaged in the CPC drawers. Since the z196, IBM Z has used a redundant array of independent memory (RAIM): data and check information are striped across several memory channels so that the loss of an entire DIMM, or even a channel, is corrected on the fly, much as RAID protects disks.3,5 On the z15 the RAIM design uses five channels, four carrying data and one carrying redundancy, so 20% of the installed physical memory is not available to customers.5 A fixed portion of memory, the hardware system area (HSA), is reserved for firmware structures such as the I/O configuration.3

5. Cache hierarchy

Commercial workloads have large instruction and data footprints and frequent cross-processor sharing, so IBM has historically spent more silicon on cache than other server vendors. The z10 paper by Mak et al. describes the design goals that still apply: a deep hierarchy, inclusive higher-level caches that act as coherence filters, and directories that track which cores hold each line.14

5.1 The virtual-cache design

Telum replaced dedicated L3 and L4 arrays with large private L2s and a protocol that lets them behave as shared levels. When a core evicts a line from its L2, the line can be placed in another core's L2 on the same chip (which then acts as L3) or on another chip in the drawer (acting as L4), instead of being written back or dropped. Lookups to the virtual levels travel over on-chip rings and the drawer fabric.3,7 IBM reported that this gave each core more effective cache than z15 while letting a single core use a large share of the chip's capacity when its neighbours are idle.7

5.2 Coherence and cache-aware programming

Cache coherence is maintained in hardware; software never flushes caches for correctness on IBM Z. Lines are 256 bytes, which is larger than on most other platforms and matters when laying out data that different CPUs update.3,14 Two placement rules follow:

  • Keep fields written by different CPUs in different 256-byte lines to avoid false sharing.
  • Use the PREFETCH DATA (PFD) and NEXT INSTRUCTION ACCESS INTENT (NIAI) instructions where profiling shows a benefit; both are hints and do not change results.2

6. Input/output architecture

The mainframe I/O design separates the CPU from device handling. A CPU issues a single START SUBCHANNEL (SSCH) instruction naming a subchannel and pointing to an operation-request block (ORB); the channel subsystem then executes a channel program, a list of channel command words (CCWs), without further CPU involvement, and signals completion with an I/O interruption.2,12 This asynchronous, offloaded model is why a mainframe can sustain very large numbers of concurrent I/O operations.

6.1 Channel programs

A format-1 CCW is eight bytes: a command code (for example X'02' read, X'01' write, X'06' read multiple count-key-data on DASD), flag bits such as command chaining (CC) and data chaining (CD), a 16-bit byte count and a 31-bit data address.2 Chaining lets one SSCH perform a whole sequence of seek, search and transfer operations. With High Performance FICON (zHPF) the channel instead sends a transport-control word (TCW) describing the whole transfer in fewer, larger frames, which reduces protocol overhead and increases achievable I/O rates.15,16

7. Channel subsystems

7.1 Structure

The channel subsystem (CSS) is the part of the machine that directs information between main storage and devices. Its components are:2,12

  • Subchannels. One per device per partition; each holds the state of the I/O operation for that device, and is addressed by a subchannel number (not the device number).
  • Channel paths, identified by an 8-bit CHPID, which correspond to physical channel ports identified by a physical channel ID (PCHID).
  • Control units and devices, defined to the CSS in the I/O configuration.
  • SAPs, the processors that run the CSS code, choose among the available channel paths to a device, and queue work when all paths are busy.

Because each CHPID is an 8-bit value, one channel subsystem can address at most 256 channel paths. To grow beyond that, IBM introduced multiple logical channel subsystems (LCSSs); a z16 supports six LCSSs, each with up to 15 LPARs (with a total of 85), and up to four subchannel sets per LCSS, so that alias devices (for example, Parallel Access Volume aliases) and Metro Mirror secondary devices can be defined without using up the first set.3,15

7.2 Defining the configuration: IOCP and HCD

The I/O configuration is stored in an I/O configuration data set (IOCDS) on the Support Element and loaded into the HSA at power-on reset. Installations usually maintain it with the Hardware Configuration Definition (HCD) dialog of z/OS, which generates IOCP statements internally; the statements themselves show the structure clearly.12,15

Listing 7. A REXX exec that issues the commands and captures the replies

/* REXX - display channel path and device status via TSO CONSOLE */
/* Requires CONSOLE authority in RACF (TSOAUTH class).            */
parse arg chp dev
if chp = '' then chp = '50'
if dev = '' then dev = '8000'
"CONSPROF SOLDISP(NO) UNSOLDISP(NO)"
"CONSOLE ACTIVATE"
cmds = 'D M=CHP('chp')' '|' 'D M=DEV('dev')'
do while cmds <> ''
  parse var cmds cmd '|' cmds
  cmd = strip(cmd)
  "CONSOLE SYSCMD("cmd") CART(CHPCHK)"
  rc2 = getmsg('reply.', 'SOL', 'CHPCHK', , 10)   /* wait 10 s */
  say '===' cmd '==='
  if rc2 = 0 then
    do i = 1 to reply.0
      say reply.i
    end
  else say 'No response (GETMSG rc='rc2')'
end
"CONSOLE DEACTIVATE"
exit 0

The exec uses the TSO/E CONSOLE command and the GETMSG function, with a command-and-response token (CART) to match each reply to its command.18

8. Storage controllers

Mainframe disks are not individual drives but logical volumes emulated by an enterprise storage system. The current IBM family is the DS8000 series (for example DS8900F and its successors). Inside, a DS8000 is a pair of POWER-based servers ("central processor complexes"), each with its own cache memory, that share a set of flash enclosures through redundant device adapters. Writes are acknowledged once they are stored in the cache of one server and the non-volatile storage (NVS) of the other, so that a single server failure loses no data.16

8.1 CKD volumes and count-key-data

To z/OS the storage system presents count-key-data (CKD) volumes that emulate the IBM 3390 disk geometry: 15 tracks per cylinder, 56,664 bytes per track, with records described by a count field, an optional key and data. A 3390 Model 9 has 10,017 cylinders, and Extended Address Volumes (EAV) extend this to far larger sizes.4,16

8.2 Performance features tied to the mainframe

  • Parallel Access Volumes (PAV, HyperPAV, SuperPAV). Alias device numbers let several I/Os run to the same logical volume at once, avoiding the "one I/O per device" queueing of the original architecture.16
  • zHPF and zHyperLink. Described in Section 6; zHyperLink lets Db2 and VSAM perform synchronous reads from DS8000 cache.3,16
  • Easy Tier. Automatically moves hot extents to the fastest flash tier.16

8.3 Replication

DS8000 Copy Services (FlashCopy point-in-time copies, synchronous Metro Mirror, asynchronous Global Mirror, and z/OS Global Mirror) are the building blocks for disaster recovery. Combined with z/OS HyperSwap, managed by GDPS, a primary storage system can fail and z/OS switches I/O to the Metro Mirror secondary without an application outage.16,19

9. Hardware redundancy

IBM's design philosophy for mainframe reliability, availability and serviceability (RAS) is that every error should be detected, most should be corrected, and the rest should be contained without corrupting data.21

9.1 Inside the processor

The S/390 G5 (1998) duplicated the instruction and execution units of each processor and compared their results every cycle; any mismatch caused the instruction to be retried from a checkpoint held in a separate recovery unit (R-unit), and a persistent fault caused the processor's state to be moved to a spare processor.21 Later cores replaced full duplication with extensive error detection (parity, residue checking and other checkers) in the data flow, but kept the checkpointed R-unit and instruction retry.10 Caches and arrays are protected by error-correcting codes, and failing cache lines can be deleted dynamically.3

9.2 Sparing

Every IBM Z machine ships with spare PUs. If a PU fails, its architected state is transferred to a spare by firmware, and the operating system continues without noticing; this is called transparent CP sparing.3,21 Spare memory and I/O spares (for example, redundant fan-out and PCIe paths) apply the same idea elsewhere.

9.3 Redundancy across the system

10. High availability and fault tolerance

Hardware redundancy protects against component failure inside one box. Higher availability comes from combining it with concurrent maintenance and clustering.

10.1 Concurrent maintenance and upgrade

Most field-replaceable units, including I/O features, power and cooling parts, can be replaced while the system runs. On multi-drawer machines, enhanced drawer availability allows a whole CPC drawer to be removed for repair or upgrade after its workload has been moved to the remaining drawers.3 Capacity on Demand lets additional PUs and memory, already physically present, be enabled without an outage.3

10.2 Parallel Sysplex and GDPS

Within a site, Parallel Sysplex data sharing means that the loss of one z/OS image, LPAR or whole CPC removes capacity but not service, because surviving members already have access to the same data through the coupling facility.13 Across sites, GDPS automates disk replication, HyperSwap and site failover.19 IBM's z16 documentation cites up to 99.99999% availability for a correctly configured combination of z16, z/OS, Parallel Sysplex, GDPS and DS8000 storage; this is a design target for that full stack, not a property of a single box.3

10.3 Availability arithmetic

The value of redundancy can be estimated with standard reliability formulas. For components in series, availability is the product of the individual availabilities; for n independent redundant components in parallel, the unavailability is the product of the individual unavailabilities:

A_series   = A1 × A2 × … × An
A_parallel = 1 − (1 − A1)(1 − A2)…(1 − An)

These formulas assume independent failures, which is why mainframe sites separate redundant components physically (different power feeds, different switch fabrics, different sites). Exercise 6 applies them.

11. Hardware cryptographic accelerators

IBM Z provides cryptography at two levels, both managed on z/OS by the Integrated Cryptographic Service Facility (ICSF).3,22

11.1 CPACF: on-core symmetric crypto

The CP Assist for Cryptographic Functions (CPACF) is a coprocessor attached to every core. It implements the message-security-assist instructions, including KM (cipher message), KMC (cipher message with chaining), KMA (cipher message with authentication, for AES-GCM), KIMD/KLMD (compute message digest for SHA-1, SHA-2 and SHA-3), KMAC, PRNO (random numbers) and, from z15, KDSA for elliptic-curve signatures.2,5 Because it runs synchronously in the core at clock speed, CPACF makes bulk encryption cheap enough for pervasive encryption: z/OS data-set encryption, Coupling Facility structure encryption and encrypted network traffic.23

CPACF can also use protected keys: a key that is wrapped by a per-LPAR wrapping key held in the HSA, so the clear key value never appears in operating-system storage.3,23

         BR    R14

         DC    X'510E527F9B05688C1F83D9AB5BE0CD19'  SHA-256 H4..H7
         DC    XL16'00'                             MBL (128 bits)
MSG      DC    C'abc'
MSGLEN   EQU   *-MSG

Listing 9 follows the KIMD and KLMD definitions in the Principles of Operation: the first operand is unused, the second is an even–odd register pair giving the address and length of the data, and the instruction may end with condition code 3 after processing part of the data, in which case it is simply reissued.2 (Remember that in z/OS the literal C'abc' is EBCDIC, so the digest differs from the familiar ASCII test vector; see Exercise 8.)

11.2 Crypto Express: tamper-responding HSMs

The Crypto Express feature (Crypto Express7S on z15, Crypto Express8S on z16) is a PCIe adapter holding a hardware security module certified to FIPS 140 Level 4, the highest physical-security level. Each adapter can be configured as:3,22

  • a CCA coprocessor (Common Cryptographic Architecture, IBM's banking-oriented API, including PIN processing and EMV);
  • an EP11 coprocessor (Enterprise PKCS #11, for standards-based secure-key cryptography);
  • an accelerator for clear-key RSA operations such as TLS handshakes.

In secure-key mode, keys are encrypted under a master key held only inside the tamper-responding adapter, and the clear key never leaves it. Crypto Express8S added quantum-safe algorithms (CRYSTALS-Dilithium and CRYSTALS-Kyber) to both CCA and EP11.3

11.3 Calling ICSF

Applications reach both levels through ICSF callable services; ICSF decides whether to use CPACF, a coprocessor, or software. Every CCA verb has the same leading parameters: return code, reason code, exit-data length and exit data, then a rule array of 8-byte keywords that selects options.22

12. Hardware management consoles

12.1 HMC and Support Element

Each CPC has two Support Elements (SEs): dedicated service processors, one primary and one alternate, that hold the machine's firmware, the IOCDSs and activation profiles, and that monitor and control the hardware. Operators and system programmers normally work through a Hardware Management Console (HMC), which talks to the SEs of one or many CPCs over a private network and presents a web-based interface.3,25 From z15, the HMC and SE functions can run on a Hardware Management Appliance installed inside the CPC frame instead of on separate desktop or rack-mounted consoles.3,5

12.2 What the HMC is used for

  • Activation. Power-on reset (which loads an IOCDS into the HSA), activating LPARs from image profiles, and IPL (initial program load) of an operating system from a load device.
  • Configuration. Changing LPAR weights and processor counts, configuring channel paths and crypto domains online or offline, and managing Capacity on Demand records.
  • Monitoring and service. Hardware messages, operating-system messages, problem reporting to IBM ("call home"), and guided repair of field-replaceable units.
  • Firmware management. Concurrent application of Microcode Change Levels (MCLs).
  • Dynamic Partition Manager (DPM). A simplified mode for Linux and z/VM systems in which partitions and their I/O are defined from the HMC without IOCP.3

Because the HMC can stop, reset or reconfigure production systems, access is controlled by user roles and auditing, and the HMC network is kept separate from general corporate networks.25

12.3 Automation interfaces

Two programmatic interfaces expose HMC functions. BCPii (Base Control Program internal interface) lets authorised z/OS programs query and control CPCs and LPARs through the SE without a network connection.3 The HMC Web Services API provides a REST interface over HTTPS (port 6794) for external automation.26

Listing 12. Listing CPCs and partitions through the HMC Web Services API (Python)

"""List CPCs and their logical partitions via the HMC Web Services API.
Uses only the Python standard library plus 'requests'."""
import requests

HMC = "https://hmc.example.com:6794"
CA_BUNDLE = "/etc/pki/hmc-ca.pem"        # verify the HMC certificate

def main(user: str, password: str) -> None:
    s = requests.Session()
    s.verify = CA_BUNDLE
    # 1. Log on: returns a session token used on later requests
    r = s.post(f"{HMC}/api/sessions",
               json={"userid": user, "password": password})
    r.raise_for_status()
    s.headers["X-API-Session"] = r.json()["api-session"]
    try:
        # 2. List CPCs managed by this HMC
        cpcs = s.get(f"{HMC}/api/cpcs").json()["cpcs"]
        for cpc in cpcs:
            print(f"CPC {cpc['name']}  status={cpc['status']}")
            # 3. List logical partitions on each CPC (classic mode)
            lpars = s.get(f"{HMC}{cpc['object-uri']}/logical-partitions"
                          ).json()["logical-partitions"]
            for lp in lpars:
                print(f"   LPAR {lp['name']:8}  {lp['status']}")
    finally:
        # 4. Log off
        s.delete(f"{HMC}/api/sessions/this-session")

if __name__ == "__main__":
    import getpass
    main(input("HMC user: "), getpass.getpass())

The resource URIs (/api/sessions, /api/cpcs, …/logical-partitions) and the X-API-Session header are defined in the Web Services API book.26 For production automation IBM maintains an open-source Python client, zhmcclient, that wraps these calls.27

13. Exercises and solutions

Try each exercise before opening its solution. Exercises 1–4 are conceptual, 5–7 are quantitative and 8–10 involve code.

Exercise 1. Processor characterisation

A customer's z16 has 20 active PUs: 8 CPs, 6 zIIPs, 4 IFLs and 2 ICFs. A CP fails. What happens, and does the customer's software bill change?

Show solution

Firmware moves the failed CP's state to a spare PU, which is then characterised as a CP (transparent sparing, Section 9.2). The configuration still has 8 CPs, so capacity and CP-based software charges are unchanged; IBM replaces the failed hardware later.3 The SAPs, IFP and spares are not counted among the 20 customer PUs, and every z16 includes spare PUs for this purpose.

Exercise 2. Instruction length

The first byte of three instructions is X'1A', X'58' and X'E3'. Using the rule that bits 0–1 of the opcode determine length (00 = 2 bytes, 01 or 10 = 4 bytes, 11 = 6 bytes), give each instruction's length. Identify the instructions.

Show solution

X'1A' = 0001 1010: bits 0–1 = 00, so 2 bytes. It is AR (Add Register), RR format.
X'58' = 0101 1000: bits 0–1 = 01, so 4 bytes. It is L (Load), RX format.
X'E3' = 1110 0011: bits 0–1 = 11, so 6 bytes. X'E3' is the first byte of the RXY family; the second opcode byte in the last byte of the instruction selects, for example, LG (X'E3..04').2

Exercise 3. Prefixing

CPU 0 has prefix X'00010000' and CPU 1 has prefix X'00012000'. To what absolute address does each CPU's real address X'000000A0' map? What absolute address does CPU 0 reach with real address X'00010000'?

Show solution

For real addresses below 8 KB (X'0000'–X'1FFF') the prefix is substituted: CPU 0 reaches absolute X'000100A0' and CPU 1 reaches X'000120A0'. Real addresses in the block equal to the prefix map to absolute 0 to 8191, so CPU 0's real address X'00010000' reaches absolute X'00000000'.2 This reverse mapping makes absolute page zero reachable while keeping each CPU's low core private.

Exercise 4. Channel subsystem limits

Why did IBM introduce multiple logical channel subsystems rather than simply making the CHPID wider? Why are PAV alias devices often put in subchannel set 1?

Show solution

The CHPID is an 8-bit field in architected structures used by existing operating systems and I/O programs; widening it would break compatibility. Adding LCSSs, each with its own 256 CHPIDs, raises the total number of channels without changing the field.12 Subchannel set 0 has a fixed maximum number of subchannels (just under 64 K). Alias devices and mirror secondaries consume subchannels without being base volumes, so placing them in set 1 and higher leaves set 0 free for base devices.3,15

Exercise 5. Effective memory-access time

Assume a load hits L1 92% of the time (4 cycles), L2 6% (16 cycles), L3 1.5% (60 cycles) and goes to L4 or memory 0.5% (400 cycles on average). Compute the average access time in cycles and in nanoseconds at 5.2 GHz. By how much does it improve if a larger L2 converts half of the L3 accesses into L2 hits?

Show solution 
Baseline:  0.92×4 + 0.06×16 + 0.015×60 + 0.005×400
         = 3.68  + 0.96    + 0.90     + 2.00     = 7.54 cycles
Cycle time at 5.2 GHz = 1 / 5.2e9 s ≈ 0.1923 ns
           7.54 × 0.1923 ≈ 1.45 ns

Improved:  L2 = 6.75%, L3 = 0.75%
           3.68 + 0.0675×16 + 0.0075×60 + 2.00
         = 3.68 + 1.08      + 0.45      + 2.00   = 7.21 cycles ≈ 1.39 ns
Improvement ≈ 4.4%

The rare long-latency misses (0.5% of accesses) contribute 27% of the average, which is why IBM invests so heavily in large L3/L4 capacity (Section 5).

Exercise 6. Availability

One CPC with its z/OS image has availability 0.9995. (a) What is the annual downtime? (b) What is the availability of a two-CPC Parallel Sysplex, assuming independent failures and that either CPC can run the whole workload? (c) If the shared coupling facility has availability 0.99999 and is a single point of failure, what is the combined availability?

Show solution 
(a) (1 − 0.9995) × 8760 h = 0.0005 × 8760 = 4.38 h per year
(b) 1 − (0.0005)^2 = 1 − 2.5e-7 = 0.99999975
(c) 0.99999975 × 0.99999 ≈ 0.99998975
    → downtime ≈ (1 − 0.99998975) × 525,600 min ≈ 5.4 min per year

The single coupling facility dominates the result, which is why IBM recommends at least two CFs, on separate CPCs, with structures duplexed or rebuildable.13

Exercise 7. RAIM capacity

On a machine where RAIM uses five channels, four of which hold data, how much physical memory must be installed to provide 2 TB of customer memory, ignoring the HSA? How does this compare with simple mirroring?

Show solution

Usable fraction = 4/5 = 80%, so physical = 2 TB / 0.8 = 2.5 TB. Mirroring stores every byte twice, so it needs 4 TB for the same protection against a full channel or DIMM failure. RAIM achieves channel-level fault tolerance at a 25% overhead (relative to usable) instead of 100%.5

Exercise 8. CPACF and code pages

You run Listing 9 on z/OS and compare the result with the published SHA-256 test vector for "abc" (ba7816bf…). They differ. Why? Change the listing to produce the published vector.

Show solution

HLASM assembles C'abc' in EBCDIC (X'818283'), whereas the test vector hashes ASCII (X'616263'). Replace the constant with:

MSG      DC    X'616263'          'abc' in ASCII/UTF-8

or use HLASM's CA'abc' constant type, which assembles ASCII characters.11 The digest will then be ba7816bf 8f01cfea 414140de 5dae2223 b00361a3 96177a9c b410ff61 f20015ad.

Exercise 9. Spot the bug

A programmer writes this lock-free update. What is wrong?

RETRY    LG    R2,COUNTER
         LGR   R3,R2
         AGHI  R3,1
         CSG   R2,R3,COUNTER
         JNE   RETRY
Show solution

The code is correct but inefficient: on failure, CSG already loads the current value into R2, so jumping back to the LG refetches it unnecessarily. Loop to the LGR instead, as in Listing 3. A real bug would be using CS (32-bit) on a 64-bit counter, or placing COUNTER in the same 256-byte cache line as other heavily updated fields, which causes false sharing (Section 5.2).2

Exercise 10. IOCP

Extend Listing 6 so that partition PROD2 alone has a third FICON path (CHPID 52, PCHID 19C) to control unit 8000, through the same switch, link address 6112.

Show solution 
         CHPID PATH=(CSS(0),52),SHARED,PARTITION=((PROD2),(=)),        X
               SWITCH=61,PCHID=19C,TYPE=FC
         CNTLUNIT CUNUMBR=8000,PATH=((CSS(0),50,51,52)),               X
               LINK=((CSS(0),6110,6111,6112)),CUADD=0,                 X
               UNITADD=((00,256)),UNIT=2107

The CHPID's access list contains only PROD2, so only that partition can use the path, while the control unit now lists three paths and three link addresses in matching order. The (=) candidate list notation means the candidate list equals the access list. In practice you would make this change in HCD and activate it dynamically.12,15
