Mainframe Storage and Data Management

DASD, data set organisations, VSAM, PDS and PDSE, generation data groups, tape, SMS, backup, replication and disaster recovery on z/OS: a technical article with worked examples, source code and exercises

Abstract. On z/OS, data does not live in a hierarchical file system of byte streams, as on UNIX or Windows. It lives in data sets: named, catalogued collections of records whose organisation (sequential, partitioned, keyed and so on) is declared when the data set is created and is understood by the access methods that read and write it.1,2 This article explains the storage and data management stack from the bottom up. It starts with direct access storage devices (DASD) and their count-key-data track format, then covers the main data set organisations (sequential, partitioned, PDSE and VSAM), generation data groups, and tape. It then turns to how an installation manages billions of bytes with few people: storage pools, the Storage Management Subsystem (SMS) and its automatic class selection (ACS) routines, backup and recovery with DFSMShsm and DFSMSdss, and finally replication and disaster recovery with DS8000 Copy Services and GDPS. Each section includes JCL, IDCAMS, COBOL, REXX or ACS source code, and the article closes with exercises and worked solutions.

Scope note. Examples assume z/OS 2.5 or 3.1 with DFSMS. Storage controller hardware and the channel subsystem are covered in the companion article Mainframe Hardware Architecture, and DD statement syntax in more depth in the JCL article; this article cross-references them rather than repeating them. High-level qualifiers such as PROD and NICK are placeholders.

1. DASD (direct access storage devices)

DASD is IBM's term for any storage device that can reach a record directly, without reading everything before it. In practice it means disk. Every z/OS disk volume today is emulated: a storage controller such as the IBM DS8000 family stores data on flash drives arranged in RAID arrays and presents it to the host as IBM 3390 volumes.3,4 The 3390 itself was a physical disk drive introduced in 1989; its geometry survives because z/OS, its access methods and decades of applications are written against it.3,5

1.1 Count-key-data (CKD) format

Unlike the fixed 512-byte or 4 KB sectors of other platforms, a 3390 track holds variable-length records in count-key-data format. Each record has a count field (which includes the record's address, its key length and its data length), an optional key field, and a data field. A record's address is written CCHHR: two bytes of cylinder, two bytes of head (track within the cylinder) and one byte of record number.2,6 Because the hardware knows record boundaries, a channel program can ask the controller to search a track for a record with a given key, a capability that the original ISAM access method and the PDS directory search depend on.2

1.2 Volumes, the VTOC and the catalog

Each DASD volume has a six-character volume serial (volser) and a volume table of contents (VTOC). The VTOC holds data set control blocks (DSCBs): a format-1 (or, on EAV, format-8) DSCB for each data set describes its attributes and first extents, and format-3 DSCBs describe further extents. An optional VTOC index speeds up searches.2,8 The VTOC only says what is on one volume. To find a data set by name without knowing its volume, z/OS uses the integrated catalog facility: a master catalog, which points to user catalogs by high-level qualifier alias, and user catalogs, each made of a basic catalog structure (BCS, a VSAM KSDS) and, on every volume holding VSAM or SMS-managed data, a VSAM volume data set (VVDS).9

1.3 Data set names

A data set name has up to 44 characters, made of qualifiers of one to eight characters separated by periods. Each qualifier starts with a letter or national character (@ # $) and may contain digits and hyphens. The first qualifier, the high-level qualifier (HLQ), usually identifies the owner and selects the user catalog through an alias.2,9 For example, PROD.PAYROLL.MASTER.KSDS has four qualifiers and is catalogued in whatever user catalog the alias PROD points to.

1.4 Large volumes and parallel access

Volumes beyond 65,520 cylinders are extended address volumes (EAV). The space above that line is cylinder-managed and is allocated in multicylinder units of 21 cylinders; data sets that are "EAS-eligible", which today includes VSAM, sequential, PDS, PDSE and most others, may live there.2,5 Large volumes would queue I/O on a single device address, so the controller and z/OS support parallel access volumes (PAV, HyperPAV and SuperPAV), which let several alias addresses run I/O to one base volume at once.3 The companion hardware article describes PAV and subchannel sets in detail.

2.1 Record formats

The RECFM attribute describes how records are laid out in blocks. The commonest values are F (fixed), V (variable, each record preceded by a 4-byte record descriptor word and each block by a 4-byte block descriptor word), U (undefined, used for load modules) and the modifiers B (blocked), S (spanned), A (ANSI carriage control) and M (machine carriage control).2,7 So RECFM=FB,LRECL=80 is the classic card-image source file, and RECFM=VBA,LRECL=137 is a typical print file: up to 132 bytes of text, one carriage-control byte and four bytes of RDW.

2.2 Indexed data sets: from ISAM to VSAM KSDS

The first indexed organisation on System/360 was the indexed sequential access method (ISAM). ISAM stored records in key order on prime tracks, kept track and cylinder indexes in hardware-searchable CKD keys, and sent inserts to overflow areas that slowed access until the data set was reorganised.2,11 VSAM replaced it in the 1970s with a design based on a balanced index tree that splits control intervals in place instead of chaining overflow records, similar in spirit to the B-tree of Bayer and McCreight.11,12 z/OS no longer processes ISAM data sets. Old programs written to the ISAM macros can run against a VSAM KSDS through the ISAM interface, which translates the requests.2 In practice, "indexed data set" on z/OS today means a VSAM key-sequenced data set, described next.

3.2 Control intervals, control areas and the index

VSAM moves data between disk and storage in control intervals (CIs). A CI holds records, free space, and control information at its end: a 4-byte CIDF (control interval definition field) and 3-byte RDFs (record definition fields).2,14 CIs are grouped into control areas (CAs), which are normally one cylinder or smaller. In a KSDS, the index component is a tree. The sequence set is the lowest level, with one index record per CA that holds the highest key in each CI of that CA; the index set levels above it point down to sequence-set records.11,14

Free space is reserved at load time with FREESPACE(ci-percent ca-percent). Inserts that fit go into the CI's free space. Otherwise VSAM performs a CI split; if no free CI remains in the CA, a CA split, which is far more expensive. Splits never require an offline reorganisation, which was VSAM's chief advantage over ISAM, but heavy splitting fragments the data set, so files with many inserts are periodically reorganised by unloading and reloading them with REPRO.11,14

3.5 Size limits and extended addressability

A VSAM data set that is not in extended format is limited to 4 GB, because relative byte addresses (RBAs) are 32 bits. A data class with extended format and extended addressability removes that limit for KSDS, ESDS, RRDS, VRRDS and LDS, and requires the data set to be SMS-managed.2,17 Extended format also enables striping, compression and, with an encryption key label, z/OS data set encryption.2

4. Partitioned data sets (PDS)

A partitioned data set is a library: a single data set containing named members, each of which is a sequential stream of records, plus a directory at the start of the data set that maps member names to their locations.1,2 Source code, JCL procedures, REXX execs, ISPF panels and (traditionally) load modules are all kept in PDSs. A member is referenced in JCL as DSN=NICK.TEST.SOURCE(PAYCALC).

4.1 The directory

The directory is a chain of 256-byte blocks, each with an 8-byte key equal to the last member name in the block, so the controller can search it by key. Each entry has an 8-byte name, a 3-byte TTR (track and record, relative to the start of the data set), a flag byte, and up to 62 bytes of user data. ISPF stores member statistics (version, dates, line counts, user ID) in that user data.2 One directory block therefore holds up to 21 entries without user data, or about six entries with ISPF statistics. The number of directory blocks is fixed at allocation, and when it is exhausted a STOW fails and the user sees an E37 or a "directory full" message.2,18

4.2 Wasted space and compression

A PDS never reuses space in place. When a member is replaced or deleted, its old records stay where they were and only the directory entry changes; new data is always written after the last used track.2 Eventually the data set fills up (an E37 or D37 abend) even though most of it is dead space. The fix is to compress it in place with IEBCOPY, as in Listing 6.

5. Partitioned data sets extended (PDSE)

A PDSE looks like a PDS to programs (same DSORG=PO, same BPAM macros, same member syntax in JCL) but is implemented completely differently. It is allocated with DSNTYPE=LIBRARY.2,19 Internally a PDSE is made of 4 KB pages, and its directory is an indexed structure kept in the same pages as the data, so members can be found quickly however many there are.19

6. Sequential data sets in depth

Physical sequential (PS) data sets are the workhorse of batch processing. Records are written and read in order through the queued sequential access method (QSAM), which blocks and deblocks records and overlaps I/O with processing using multiple buffers, or the lower-level basic sequential access method (BSAM), where the program handles blocks itself.2 There are three formats:

  • Basic format (the default): up to 65,535 tracks per volume, 16 extents per volume, up to 59 volumes.2
  • Large format (DSNTYPE=LARGE): more than 65,535 tracks per volume, without needing SMS. Programs that use BSAM and relative track addresses may need changes.2,7
  • Extended format (selected through an SMS data class): up to 123 extents per volume, and support for striping across volumes, compression (generic or zEDC) and data set encryption. Each block carries a hidden 32-byte suffix.2,17

6.1 Buffering

For QSAM the BUFNO subparameter of DCB sets the number of buffers. The default is five for most data sets; raising it lets the access method read ahead more blocks per I/O, which reduces elapsed time for large sequential jobs. Extended-format and striped data sets get their own defaults based on the stripe count.2 With half-track blocking, BUFNO=30 transfers 15 tracks, one cylinder, per I/O sequence.

7. Generation data groups (GDG)

Batch systems often keep a series of versions of the same file: today's sales extract, yesterday's, last week's. A generation data group manages such a series under one name. The GDG base is a catalog entry that holds the group's attributes; each version, a generation data set (GDS), is an ordinary data set whose name is the base name followed by a qualifier of the form GnnnnVnn: a four-digit generation number and a two-digit version number.2,15 Because the last qualifier takes nine characters including the period, the base name may be at most 35 characters.2

Programs and JCL refer to generations relatively: (0) is the most recent, (-1) the one before, and (+1) a new generation being created. Relative numbers are resolved once per job, so within a job, every step that refers to (+1) means the same new data set, and (0) keeps meaning the generation that was current when the job started.2,7

8. Tape storage

Magnetic tape remains the cheapest medium per byte for data that must be kept for years but read rarely, and a removed or vaulted cartridge cannot be reached by a network attacker. Mainframe tape has two forms today: physical drives and libraries (IBM 3592-family enterprise drives and LTO drives in automated libraries such as the TS4500), and virtual tape, chiefly the IBM TS7700 family.1,20

8.1 Labels and files

A tape volume is strictly sequential. A standard-labelled (SL) volume starts with a VOL1 label holding the volser, and each data set on it is wrapped in header labels (HDR1, HDR2) and trailer labels (EOF1/EOF2, or EOV1/EOV2 if it continues on another volume). HDR1 holds the last 17 characters of the data set name, its expiration date and its file sequence number; HDR2 holds the record format, block length and record length.2 In JCL, LABEL=(3,SL) selects the third file on the volume.7

8.2 Tape management with DFSMSrmm

A tape management system keeps the inventory: which volumes exist, which data sets they hold, when they expire and where they are (in the library, in transit, in an offsite vault). DFSMSrmm is IBM's tape manager for z/OS. Retention is driven by vital record specifications (VRSs) that match data set names and say how many cycles or days to keep and whether to move volumes to another location.5,21 An expired volume returns to scratch status and can be reused.

8.3 Virtual tape

Writing small data sets directly to physical cartridges wastes capacity and drive time. A TS7700 presents up to hundreds of virtual 3490E drives to z/OS and writes each virtual volume first to a disk cache, the tape volume cache. Depending on the model, volumes are then premigrated to physical 3592 cartridges, many virtual volumes per cartridge, or kept on disk only.20 Two or more TS7700 clusters can be joined in a grid over IP, which replicates virtual volumes between sites according to per-volume copy policies (immediate, deferred or no copy). This makes the grid itself a disaster recovery mechanism for tape data.20,22 The TS7700 is managed from z/OS through SMS constructs (the storage group, management class, storage class and data class names are passed to the library and mapped to its own policies).20

10. SMS (Storage Management Subsystem)

System-managed storage was IBM's answer, in the late 1980s, to storage growing faster than the staff who looked after it. 10.3 Control data sets and activation

The SMS configuration (classes, groups, ACS object code, volume and library lists) is built in a source control data set (SCDS) with ISMF, translated and validated, and then activated. 11. Backup and recovery

Data on z/OS is protected at several levels: copies of individual data sets, copies of whole volumes, point-in-time copies made by the storage controller, and recovery of the catalogs that make data findable. Two DFSMS components do most of the work: DFSMSdss, a utility for dumping, restoring, copying and moving data, and DFSMShsm, a started task that automates backup, migration and recovery using management class policies.10,23,26

11.2 DFSMShsm: automated backup and space management

DFSMShsm has two halves.5,23

  • Space management moves data sets that have not been used for a while from primary DASD to migration level 1 (ML1, compressed on cheaper DASD) and later to migration level 2 (ML2, usually tape or virtual tape). 12. Data replication and disaster recovery

Backups protect against losing a data set; replication protects against losing a site. Two measures frame every design. The recovery point objective (RPO) is how much data, measured in time, the business can afford to lose. The recovery time objective (RTO) is how long it can afford to be without service.28 Nightly tape backups sent offsite give an RPO of up to a day and an RTO of hours to days; synchronous disk mirroring with automated failover can give an RPO of zero and an RTO of minutes.22

Synchronous mirroring makes every write wait for the remote controller to acknowledge it, so its cost grows with distance. Light in optical fibre travels at roughly 200,000 km/s, about 5 µs per kilometre, so each round trip adds about 10 µs per kilometre of separation, plus protocol and switching overhead.22 At 50 km that is about 0.5 ms per write, which is acceptable; at 1,000 km it would be 10 ms, which is not. Longer distances therefore use asynchronous replication, accepting a non-zero RPO.22,27

12.2 HyperSwap and GDPS

HyperSwap swaps every z/OS system in a sysplex from the primary to the secondary Metro Mirror devices by changing the device addresses in the unit control blocks. Applications keep running because their I/O simply goes to the other copy.22 IBM's Geographically Dispersed Parallel Sysplex (GDPS) family automates this and the wider recovery process: monitoring the mirror, freezing it consistently when a failure starts (so that the secondary is a usable image rather than a mix of before and after), restarting systems at the other site, and running planned site switches through scripts.22 The offerings include GDPS Metro (synchronous, with HyperSwap), GDPS Global – GM and GDPS Global – XRC (asynchronous), three- and four-site combinations, and GDPS Continuous Availability, which runs workloads active-active across distant sites using software replication.22

12.3 Logical corruption and cyber resilience

Mirroring faithfully copies mistakes and malicious changes too: if ransomware encrypts a volume at site A, Metro Mirror encrypts site B within milliseconds. Protecting against logical corruption needs point-in-time copies that cannot be changed. DS8000 Safeguarded Copy keeps many immutable, hidden backup generations of production volumes inside the controller; they cannot be mounted or altered by host software, but can be recovered to separate volumes in an isolated environment for analysis and restore.29 Combined with a physically separate recovery system, this is the IBM Z Cyber Vault pattern. TS7700 logical WORM and offline vaulted tapes give similar protection for tape data.20,29

12.4 A worked DR design

A bank with a production site and a second data centre 25 km away, and a policy that no committed transaction may be lost in a single-site failure, needs synchronous mirroring between the two sites with HyperSwap: RPO 0, RTO of minutes. To survive a regional disaster that takes out both, it adds Global Mirror to a third site 800 km away, accepting an RPO of a few seconds there. Safeguarded Copy on the primary controller, taken every few hours and kept for several days, covers logical corruption, and daily DFSMShsm backups and ABARS aggregates on TS7700 grid tape cover single data set recovery and long-term retention. Each layer answers a different failure, and no single one replaces the others.22,23,29

Exercise 10. ACS routine

Write a management class ACS routine that gives MCNOMIG (never migrate) to all Db2 and IMS production data, MCGDG to any generation data set, MCTEMP to data sets whose HLQ is TEMP, and MCSTD to everything else.

Show solution 
PROC MGMTCLAS
  FILTLIST DBDATA INCLUDE(PROD.DB2.**, PROD.IMS.**)
  SELECT
    WHEN (&DSN = &DBDATA)
      SET &MGMTCLAS = 'MCNOMIG'
    WHEN (&DSTYPE = 'GDS')
      SET &MGMTCLAS = 'MCGDG'
    WHEN (&HLQ = 'TEMP')
      SET &MGMTCLAS = 'MCTEMP'
    OTHERWISE
      SET &MGMTCLAS = 'MCSTD'
  END
END

Order matters: the first WHEN that is true wins, so a Db2 GDS gets MCNOMIG. Temporary (&&) data sets have &DSTYPE = 'TEMP' and are not given a management class by most installations because they are deleted at job end.17

Exercise 12. Space report

Extend Listing 11 so that it takes a pattern such as NICK.*, finds matching data sets and warns about any that use more than 90% of their allocation. Hint: the ISPF services LMDINIT and LMDLIST list data set names.

Show solution 
/* REXX - DSWARN: warn about nearly full data sets (run under ISPF) */
parse arg pattern .
if pattern = '' then pattern = userid()'.*'
address ispexec
"LMDINIT LISTID(LID) LEVEL("pattern")"
dsn = ''
do forever
   "LMDLIST LISTID("lid") OPTION(LIST) DATASET(DSN)"
   if rc <> 0 then leave
   x = listdsi("'"strip(dsn)"'" 'NORECALL')
   if x > 4 then iterate               /* migrated, VSAM, etc.   */
   if sysalloc > 0 then do
      pct = 100 * sysused / sysalloc
      if pct > 90 then say left(strip(dsn),44),
         format(pct,3,1)'% of' sysalloc sysunits
   end
end
"LMDLIST LISTID("lid") OPTION(FREE)"
"LMDFREE LISTID("lid")"
exit 0
