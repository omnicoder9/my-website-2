1. Introduction and platform context

The IBM mainframe, today the IBM Z family running the z/OS operating system, is a platform for high-volume transaction processing and batch workloads in banking, insurance, government and retail. Its lineage goes back to the System/360, announced in 1964, and the platform has kept a strong commitment to backward compatibility: programs written decades ago can still run on current hardware.1 That continuity is why the mainframe language ecosystem spans languages from the late 1950s (COBOL) to the present (Java, Python).

This article concentrates on the languages. Hardware and operating-system internals are covered in companion articles, so only the facts that shape how programs are written are summarised here:

  • Architecture. z/Architecture is a 64-bit, big-endian architecture with 16 general-purpose registers. It supports 24-, 31- and 64-bit addressing modes (AMODE), and has hardware instructions for packed-decimal arithmetic as well as binary and floating-point arithmetic, including decimal floating point.2
  • Character encoding. Traditional z/OS data is encoded in EBCDIC rather than ASCII. A program that exchanges data with other platforms must convert code pages. Code page 1047 is common in z/OS UNIX and code page 037 in North American data sets.1
  • Data sets, not files. Classic z/OS storage is organised into record-oriented data sets (sequential, partitioned PDS/PDSE, and VSAM), each with a record format (RECFM), a logical record length (LRECL) and a block size (BLKSIZE). z/OS UNIX System Services also provides a POSIX hierarchical file system.1
  • Execution environments. Programs run as batch jobs (submitted with JCL), as online transactions under CICS or IMS, as Db2 stored procedures, or as z/OS UNIX processes.1

3. COBOL

COBOL (COmmon Business-Oriented Language) was designed in 1959 by the CODASYL committee, with the first specification published in 1960, to provide a machine-independent, English-like language for business data processing.3 The language is standardised internationally; the current edition is ISO/IEC 1989:2023.4 On z/OS, the main implementation is IBM Enterprise COBOL for z/OS, which implements much of the standard plus IBM extensions for CICS, Db2, IMS, XML and JSON processing, and Language Environment integration.5,6

COBOL's lasting role comes from a few design choices. It has native fixed-point decimal data types that map directly to hardware packed-decimal instructions, so monetary amounts avoid binary floating-point rounding errors.2,5 It describes record layouts declaratively, matching the record-oriented z/OS data set model. And its verbose syntax lets business rules be read years after they were written.

Points to notice:

  • ASSIGN TO CUSTIN names a DD name, not a data set. The actual data set is bound at run time by a JCL DD statement called CUSTIN (see JCL). This indirection lets the same program run against test and production data without being recompiled.6
  • The paragraph numbering convention (1000-, 2000-…) is not required by the language. It is a widely used house style that makes large programs easier to navigate.
  • The program uses scope terminators (END-IF, END-READ) and the PERFORM … UNTIL loop rather than GO TO. This structured style has been available since the COBOL 85 standard.5
  • GOBACK returns control to the caller, which is the operating system for a main program and the calling program for a subprogram. The special register RETURN-CODE becomes the step's condition code, which JCL can test.6

3.2 Data declarations and file handling

Level numbers and the PICTURE clause

COBOL data is declared hierarchically with level numbers. Level 01 starts a record or group item, and levels 02–49 are subordinate items. Level 77 declares an independent elementary item, 66 is used with RENAMES, and 88 declares a condition name: a named value or set of values for the item immediately above it.5 The PICTURE (PIC) clause describes an elementary item's category and size:

SymbolMeaningExample
XAny characterPIC X(30): 30 characters
AAlphabetic character or spacePIC A(10)
9Decimal digitPIC 9(8): 8-digit number
SOperational signPIC S9(5)
VImplied decimal point (takes no storage)PIC S9(9)V99: 9 integer digits, 2 decimal places
Z, -, ,, ., $, CR, DBEditing symbols for display and report outputPIC -(9)9.99, PIC $$$,$$9.99

USAGE: how numbers are stored

The USAGE clause determines the internal representation, which matters for both correctness and performance.5,6

DISPLAY (default)Zoned decimal: one digit per byte, sign in the zone of the last byte7 bytesData that is printed or exchanged as text
PACKED-DECIMAL / COMP-3Packed decimal: two digits per byte, sign in the last half-byte4 bytesMoney and other decimal arithmetic
BINARY / COMP / COMP-4Binary integer (halfword, fullword or doubleword)4 bytesCounters, subscripts, lengths
COMP-5Native binary, not limited by the PICTURE digits4 bytesInterfacing with C or assembler, API parameters
COMP-1 / COMP-2Short / long hexadecimal floating point4 / 8 bytes (no PIC)Scientific values

A packed-decimal field of n digits takes n/2 + 1 bytes, rounded down. That is why the 11-digit balance in our record occupies 6 bytes. In hexadecimal, the value +1234.56 in PIC S9(9)V99 COMP-3 is stored as the six bytes X'00000123456C' (the 11 digits 00000123456 followed by the sign), where C is the positive sign nibble (D means negative and F unsigned).2

Other important data clauses

  • VALUE sets an initial value; figurative constants include ZERO, SPACES, HIGH-VALUES and LOW-VALUES.
  • REDEFINES lets two descriptions share the same storage, for example to view a date as PIC 9(8) or as separate year, month and day fields.
  • OCCURS declares a table (array). OCCURS … DEPENDING ON declares a variable-length table, and INDEXED BY declares an index for efficient access and for SEARCH and SEARCH ALL (binary search).
  • WORKING-STORAGE persists across calls to a subprogram until it is cancelled, while LOCAL-STORAGE is allocated fresh on each call. Use LOCAL-STORAGE for recursive or reentrant designs.5

Exercise 3.1: data sizes

How many bytes does each item occupy? (a) PIC S9(5) COMP-3 (b) PIC 9(5) (c) PIC S9(9) COMP (d) PIC S9(4) COMP (e) PIC S9(13)V99 COMP-3

Show solution

(a) 3 bytes: 5 digits plus sign = 6 half-bytes. (b) 5 bytes: one digit per byte. (c) 4 bytes: binary items of 5–9 digits use a fullword. (d) 2 bytes: 1–4 digits use a halfword. (e) 8 bytes: 15 digits plus sign = 16 half-bytes.5

Exercise 3.2: condition names

Add an 88-level condition CUST-DORMANT that is true when the open date is before 2000-01-01. Explain why an 88-level cannot express this directly, and give a working alternative.

Show solution

An 88-level can list values and ranges with THRU, so this is in fact expressible for a numeric date field:

           05  CUST-OPEN-DATE      PIC 9(8).
               88  CUST-DORMANT        VALUE 00000000 THRU 19991231.

This works because YYYYMMDD dates sort numerically in date order. Where the rule depends on run-time data, such as "older than ten years from today", a condition name cannot be used because its values are fixed at compile time. Compute the comparison in the procedure division instead, for example with FUNCTION INTEGER-OF-DATE and FUNCTION CURRENT-DATE.5

3.3 Copybooks

A copybook is a source member that is included in a program at compile time by the COPY statement. On z/OS, copybooks are members of a partitioned data set (PDS or PDSE) that the compiler finds through the SYSLIB DD statement, or through additional libraries named by the LIB compiler option and COPY … OF/IN library-name.5,6 Copybooks are the main way to keep one record layout shared by every program that reads or writes a file, or by both sides of a CALL.

COBOL copybook: CUSTREC

      *----------------------------------------------------------
      * CUSTREC - customer record, 80 bytes, RECFM=FB
      *----------------------------------------------------------
       01  CUST-RECORD.
           05  CUST-ID             PIC X(8).
           05  CUST-NAME           PIC X(30).
           05  CUST-TYPE           PIC X.
               88  CUST-RETAIL         VALUE 'R'.
               88  CUST-BUSINESS       VALUE 'B'.
           05  CUST-BALANCE        PIC S9(9)V99 COMP-3.
           05  CUST-OPEN-DATE      PIC 9(8).
           05  FILLER              PIC X(27).

The REPLACING phrase changes text as the copybook is included, which allows one layout to be used several times in the same program with different names. Pseudo-text delimiters ==…== match partial words when the copybook is written with a placeholder prefix:5

      * Copybook ADDRESS written with the placeholder prefix :PFX:
       01  :PFX:-ADDRESS.
           05  :PFX:-STREET        PIC X(30).
           05  :PFX:-CITY          PIC X(20).

      * In the program:
           COPY ADDRESS REPLACING ==:PFX:== BY ==BILL==.
           COPY ADDRESS REPLACING ==:PFX:== BY ==SHIP==.

Good practice for copybooks: keep one record per copybook; never change a field's length without recompiling every program that uses it (a cross-reference or impact-analysis tool helps here); and generate Db2 host-variable copybooks with DCLGEN rather than writing them by hand (see SQL).6

3.4 Subprograms and linkage

A COBOL program calls another with the CALL statement. The called program describes the parameters it receives in its LINKAGE SECTION and lists them in PROCEDURE DIVISION USING. No storage is allocated for linkage items. Instead, they are mapped onto the caller's storage through addresses passed in a parameter list, following the standard z/OS linkage conventions: register 1 points to a list of addresses, register 13 to a save area, register 14 holds the return address and register 15 the entry point address.5,8

COBOL: CALCINT (subprogram)

       IDENTIFICATION DIVISION.
       PROGRAM-ID. CALCINT.
      *----------------------------------------------------------
      * Compute one year's interest for a customer record.
      *----------------------------------------------------------
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-RATE                 PIC SV9(4) COMP-3.
       LINKAGE SECTION.
           COPY CUSTREC.
       01  LS-INTEREST             PIC S9(7)V99 COMP-3.

       PROCEDURE DIVISION USING CUST-RECORD LS-INTEREST.
           EVALUATE TRUE
               WHEN CUST-BUSINESS  MOVE 0.0350 TO WS-RATE
               WHEN CUST-RETAIL    MOVE 0.0200 TO WS-RATE
               WHEN OTHER          MOVE 0      TO WS-RATE
           END-EVALUATE
           COMPUTE LS-INTEREST ROUNDED = CUST-BALANCE * WS-RATE
               ON SIZE ERROR
                   MOVE 0 TO LS-INTEREST
           END-COMPUTE
           GOBACK.

Parameter passing

PhraseWhat is passedEffect of changes by the callee
BY REFERENCE (default)Address of the caller's itemVisible to the caller
BY CONTENTAddress of a temporary copyNot visible to the caller
BY VALUEThe value itself in the parameter listNot visible; mainly for calling C and other languages

The caller's and callee's parameter descriptions must agree in size and layout. The compiler cannot check this across separately compiled programs, which is another reason to share layouts through copybooks.6

Static and dynamic calls

  • Static call. CALL 'literal' compiled with the NODYNAM option. The binder includes the subprogram in the same executable. The call is fast, but a change to the subprogram means relinking every caller.
  • Dynamic call. CALL identifier (a data item containing the program name), or CALL 'literal' compiled with DYNAM. The subprogram is a separate executable loaded at run time from the STEPLIB, JOBLIB or link list. It can be replaced without relinking callers, and CANCEL releases it so that its next call starts in its initial state.6

COBOL also supports nested programs (contained within another program's source and ended with END PROGRAM), GLOBAL and EXTERNAL data sharing, and the INITIAL and RECURSIVE attributes on PROGRAM-ID. Interlanguage calls to C, PL/I and assembler are supported through Language Environment.5,9

Exercise 3.3: BY REFERENCE vs BY CONTENT

Program A contains 01 WS-N PIC 9(3) VALUE 5. and executes CALL 'B' USING BY CONTENT WS-N followed by DISPLAY WS-N. Program B adds 1 to its linkage item. What is displayed? What changes with BY REFERENCE?

Show solution

With BY CONTENT, B updates a temporary copy, so A displays 005. With BY REFERENCE, B updates A's own storage, so A displays 006.5

4. Assembler (HLASM)

IBM High Level Assembler (HLASM) is the assembler for z/OS, z/VM and z/VSE. It translates symbolic machine instructions into object code and provides a powerful macro language and conditional assembly.10 Assembler is used where direct control matters: operating-system components, exits for products such as JES, CICS and security managers, performance-critical routines, and access to system services that higher-level languages do not expose.11 The instructions themselves are defined in the z/Architecture Principles of Operation.2

Statement format and key concepts

  • Each statement has a name field (starting in column 1), an operation, operands and optional remarks. Column 72 is the continuation column.10
  • Instructions are machine instructions (L, ST, A, MVC, BCT…), assembler instructions (CSECT, USING, DC, DS, EQU, END), or macro calls (WTO, GETMAIN/STORAGE, OPEN, GET, PUT).
  • Storage is addressed as base register plus displacement (plus optional index). The USING instruction tells the assembler which register holds a base address so that it can compute displacements.10
  • By convention, a called program saves the caller's registers in the caller's 72-byte save area (pointed to by register 13) and chains its own save area, then restores registers and returns through register 14 with a return code in register 15.8

HLASM: HELLO, with standard entry and exit linkage

HELLO    CSECT
HELLO    AMODE 31
HELLO    RMODE ANY
*---------------------------------------------------------------
* Entry linkage: save caller's registers, establish addressing,
* chain our save area to the caller's.
*---------------------------------------------------------------
         STM   R14,R12,12(R13)     Save caller's registers
         LR    R12,R15             Entry address -> base register
         USING HELLO,R12
         LA    R15,SAVEAREA        Our save area
         ST    R13,4(,R15)         Back chain
         ST    R15,8(,R13)         Forward chain
         LR    R13,R15
*---------------------------------------------------------------
         WTO   'HELLO FROM HLASM'  Write to operator / job log
*---------------------------------------------------------------
* Exit linkage: restore registers, return code 0.
*---------------------------------------------------------------
         L     R13,4(,R13)         Caller's save area
         LM    R14,R12,12(R13)     Restore registers
         SR    R15,R15             Return code 0
         BR    R14                 Return
*
SAVEAREA DS    18F
         YREGS ,                   Register equates R0-R15
         END   HELLO

This program is not reentrant, because its save area lives inside the program itself. Reentrant programs (which can be shared by many tasks at once and placed in read-only storage) obtain working storage dynamically, for example with the STORAGE OBTAIN macro, and are assembled and bound with the RENT option.11,8

Decimal arithmetic in assembler

Assembler shows clearly what COBOL compiles into. The fragment below adds two packed-decimal amounts and converts the result to printable characters, using the pack, add-decimal and edit instructions.2

         ZAP   TOTAL,AMT1          TOTAL = AMT1 (zero and add)
         AP    TOTAL,AMT2          TOTAL = TOTAL + AMT2
         MVC   OUTAMT,EDPAT        Copy edit pattern
         ED    OUTAMT,TOTAL        Edit packed -> characters
*
AMT1     DC    PL4'1234.56'        Packed: X'0123456C'
AMT2     DC    PL4'100.25'         Packed: X'0010025C'
TOTAL    DS    PL4
EDPAT    DC    X'4020202021204B2020'   Fill, digits, '.', digits
OUTAMT   DS    CL9

Note that HLASM ignores the decimal point in a P-type constant except to determine scale. The program itself must keep track of where the implied decimal point is, just as V does in a COBOL picture.10

Exercise 4.1: sum a table of fullwords

Write the body of an assembler routine that sums the five fullwords in TABLE DC F'10,20,30,40,50' into RESULT, using a BCT loop. Compute the number of entries with the assembler rather than hard-coding 5.

Show solution 
         LA    R2,TABLE            R2 -> first entry
         LA    R3,NENTRIES         R3 = loop count
         SR    R4,R4               R4 = accumulator
LOOP     A     R4,0(,R2)           Add current entry
         LA    R2,4(,R2)           Step to next fullword
         BCT   R3,LOOP             Decrement R3, loop if not zero
         ST    R4,RESULT           RESULT = 150
*
TABLE    DC    F'10,20,30,40,50'
NENTRIES EQU   (*-TABLE)/4         Number of entries, here 5
RESULT   DS    F

BCT (Branch on Count) subtracts one from the register and branches if the result is not zero. (*-TABLE)/4 is evaluated at assembly time, where * is the current location counter, so adding entries to the table updates the count automatically.2,10

5. PL/I

PL/I (Programming Language One) was developed by IBM, with the SHARE user group, in the mid-1960s for System/360. It was intended to unify the scientific strengths of FORTRAN and the commercial data handling of COBOL in a single language.3 It was standardised as ISO 6160:1979.12 IBM Enterprise PL/I for z/OS is the current compiler. PL/I remains in use in banking, insurance and manufacturing systems, especially in Europe.13

Distinctive features include:13

  • A rich type system: FIXED DECIMAL, FIXED BINARY, FLOAT, CHARACTER, CHARACTER VARYING, BIT, PICTURE, POINTER and AREA, and hierarchical structures similar to COBOL records.
  • ON-units for exception handling, such as ON ENDFILE, ON ZERODIVIDE, ON CONVERSION and ON ERROR, which predate exceptions in most modern languages.
  • Both record I/O (READ/WRITE, like COBOL) and stream I/O (GET/PUT with LIST, DATA or EDIT formats).
  • Block structure, recursion, pointer-based storage (BASED, ALLOCATE, FREE), and a powerful compile-time preprocessor.

PL/I: CUSTSUM, reading the same customer file

CUSTSUM: PROCEDURE OPTIONS(MAIN);
   DECLARE CUSTIN FILE RECORD INPUT;
   DECLARE 1 CUST_REC,
             2 CUST_ID       CHARACTER(8),
             2 CUST_NAME     CHARACTER(30),
             2 CUST_TYPE     CHARACTER(1),
             2 CUST_BALANCE  FIXED DECIMAL(11,2),
             2 CUST_OPENED   PICTURE '(8)9',
             2 *             CHARACTER(27);
   DECLARE EOF      BIT(1)              INIT('0'B);
   DECLARE N_RECS   FIXED BINARY(31)    INIT(0);
   DECLARE TOTAL    FIXED DECIMAL(15,2) INIT(0);

   ON ENDFILE(CUSTIN) EOF = '1'B;

   OPEN FILE(CUSTIN);
   READ FILE(CUSTIN) INTO(CUST_REC);
   DO WHILE (EOF = '0'B);
      N_RECS = N_RECS + 1;
      TOTAL  = TOTAL + CUST_BALANCE;
      READ FILE(CUSTIN) INTO(CUST_REC);
   END;
   CLOSE FILE(CUSTIN);

   PUT SKIP EDIT('Records: ', N_RECS) (A, F(9));
   PUT SKIP EDIT('Total:   ', TOTAL)  (A, F(18,2));
END CUSTSUM;

FIXED DECIMAL(11,2) occupies 6 bytes in packed format, exactly matching the COBOL PIC S9(9)V99 COMP-3 field. This is why COBOL and PL/I programs can share data sets directly. The file name CUSTIN is again bound to a data set by a JCL DD statement.14

6. C and C++

IBM provides two C/C++ compiler families for z/OS: the long-established z/OS XL C/C++, part of z/OS, and IBM Open XL C/C++ for z/OS, which is based on the open-source LLVM/Clang infrastructure.15 Both target the ISO C and C++ standards (ISO/IEC 9899 and ISO/IEC 14882),16,17 with level of support depending on product release. C and C++ are used for system software, middleware, ports of open-source tools to z/OS UNIX, and new applications that need portable code or close access to z/OS services.

Mainframe-specific points for C programmers:15

  • Two worlds of files. fopen() accepts POSIX path names in z/OS UNIX, and MVS data set names written as "//'HLQ.CUST.DATA'" or DD names written as "DD:CUSTIN".
  • Record I/O. Adding type=record to the mode string makes each fread() return exactly one record, which suits fixed and variable-record data sets.
  • Character sets. By default the compiler generates EBCDIC (code page 1047) literals. The ASCII option and CONVLIT, together with z/OS enhanced ASCII support, help with code written for ASCII platforms.
  • Decimal data. XL C supports a decimal(n,p) type (header <decimal.h>) that maps to packed decimal and can share data directly with COBOL and PL/I.
  • Interfaces. C programs can call z/OS services and other Language Environment languages, and the #pragma linkage directive declares OS-linkage functions such as assembler routines.

Exercise 6.1: EBCDIC awareness

A C program compiled for EBCDIC tests if (c >= 'A' && c <= 'Z') to detect upper-case letters. Why is this wrong on z/OS, and what should be used instead?

Show solution

In EBCDIC the letters are not contiguous: A–I, J–R and S–Z occupy three separate ranges (X'C1'–X'C9', X'D1'–X'D9', X'E2'–X'E9'), with non-letter code points between them. The range test would accept those gap characters. Use isupper(c) from <ctype.h>, which is correct for the current locale and code page.15,16

Java: CustSum using JZOS

import com.ibm.jzos.ZFile;
import com.ibm.jzos.ZUtil;
import java.math.BigDecimal;

public class CustSum {

    /** Decode a signed packed-decimal field to a BigDecimal. */
    static BigDecimal unpack(byte[] b, int off, int len, int scale) {
        long v = 0;
        for (int i = 0; i < len; i++) {
            int hi = (b[off + i] >> 4) & 0x0F;
            int lo =  b[off + i]       & 0x0F;
            v = v * 10 + hi;
            if (i < len - 1) {
                v = v * 10 + lo;
            } else if (lo == 0x0D || lo == 0x0B) {
                v = -v;                       // negative sign nibble
            }
        }
        return BigDecimal.valueOf(v, scale);
    }

    public static void main(String[] args) throws Exception {
        String enc = ZUtil.getDefaultPlatformEncoding();   // e.g. IBM-1047
        ZFile in = new ZFile("//DD:CUSTIN", "rb,type=record,noseek");
        byte[] rec = new byte[in.getLrecl()];
        BigDecimal total = BigDecimal.ZERO;
        int count = 0, n;
        try {
            while ((n = in.read(rec)) >= 0) {
                String id = new String(rec, 0, 8, enc);
                BigDecimal bal = unpack(rec, 39, 6, 2);    // bytes 40-45
                total = total.add(bal);
                count++;
                System.out.println(id + " " + bal);
            }
        } finally {
            in.close();
        }
        System.out.println("Records: " + count + "  Total: " + total);
    }
}

The bytes hold the digit nibbles 0,0,0,0,0,0,1,2,3,4,5 followed by the sign nibble. The digits give 12345, and scale 2 makes that 123.45. Sign nibble D is negative, so the result is −123.45. Sign nibble F is unsigned (treated as positive), so the second result is 123.45.2

Python: decode customer records with the standard library

"""Summarise customer records copied to z/OS UNIX in binary, e.g.:
       cp -B "//'HLQ.CUST.DATA'" cust.bin
"""
from decimal import Decimal

RECLEN = 80
CODEPAGE = "cp037"          # EBCDIC (US/Canada); Python also has cp500, cp1140

def unpack(field: bytes, scale: int) -> Decimal:
    digits = field.hex()                      # e.g. '00000012345c'
    sign = -1 if digits[-1] in "bd" else 1
    return Decimal(sign * int(digits[:-1])).scaleb(-scale)

total, count = Decimal(0), 0
with open("cust.bin", "rb") as f:
    while rec := f.read(RECLEN):
        cust_id = rec[0:8].decode(CODEPAGE)
        cust_type = rec[38:39].decode(CODEPAGE)
        balance = unpack(rec[39:45], 2)
        total += balance
        count += 1
        print(f"{cust_id} {cust_type} {balance:>14}")

print(f"Records: {count}  Total: {total}")

9. REXX

REXX (REstructured eXtended eXecutor) was designed by Mike Cowlishaw at IBM, starting in 1979, as an easy-to-read procedural language for scripting and macros.22 It was standardised as ANSI X3.274-1996.23 On z/OS, TSO/E REXX is part of the base operating system. It runs in TSO/E (foreground or batch through IKJEFT01), as ISPF and ISPF edit macros, in z/OS UNIX, and in products such as NetView and System Automation.24

REXX has a single data type, the character string, and numbers are strings that look like numbers, with arithmetic precision set by NUMERIC DIGITS. Its PARSE instruction is a compact template-based tool for splitting records. Commands that REXX does not recognise as its own instructions are passed to the current host command environment (TSO, ISPEXEC, ISREDIT, CONSOLE, SH and others), which is what makes it an automation language.24 Data set I/O in TSO/E REXX uses the EXECIO command.

REXX: CUSTSUM (TSO/E)

/* REXX - summarise a customer listing data set                    */
/* Expects a text extract with: id(1-8) name(9-38) type(39) amount  */
parse arg dsn .
if dsn = '' then dsn = "'HLQ.CUST.TEXT'"

if sysdsn(dsn) \= 'OK' then do
  say 'Data set' dsn 'not available:' sysdsn(dsn)
  exit 8
end

"ALLOC FI(INDD) DA("dsn") SHR REUSE"
"EXECIO * DISKR INDD (STEM line. FINIS"
"FREE FI(INDD)"

total. = 0                         /* default value for stem total. */
do i = 1 to line.0
  parse var line.i id 9 name 39 type 40 amount .
  total.type = total.type + amount
end

say 'Records read:' line.0
say 'Retail total:  ' total.R
say 'Business total:' total.B
exit 0

The template id 9 name 39 type 40 amount . uses absolute column positions: id receives columns 1–8, name 9–38, type column 39, and amount the first blank-delimited word after that, with the period discarding the rest.24 REXX cannot do arithmetic on packed-decimal bytes directly, so the script reads a text extract in which the amount is printable. Producing that extract is a typical job for DFSORT (Section 11). Note also that compound variables such as total.type act as associative arrays, with the value of type substituted into the name.

SQL descends from the relational model proposed by E. F. Embedded SQL in COBOL

Multi-row results are processed with a cursor, and every statement's outcome is reported in the SQL communication area (SQLCA): SQLCODE 0 means success, +100 means no (more) rows, and a negative value means an error.29

Exercise 12.1: static or dynamic?

A shared date-validation routine is called from 400 programs and changes twice a year. Should it be called statically or dynamically? Justify your answer.

Show solution

Dynamically. With static calls, every change means rebinding all 400 callers, and any caller not rebound keeps running the old copy. With dynamic calls, the routine is bound once, all callers pick up the new version the next time it is loaded, and there is only one copy in storage. The small cost of the dynamic call is usually negligible compared with this maintenance benefit.6

13. Runtime environments

Language Environment

z/OS Language Environment (LE) is the common runtime for COBOL, PL/I, C/C++ and LE-conforming assembler. It provides storage management, condition (exception) handling, message services, date and time services, and the interlanguage-call support that lets these languages call each other.35 LE organises execution into a process containing one or more enclaves (roughly, a main program and its subprograms), each of which contains one or more threads.35

LE behaviour is controlled by runtime options, which can be set installation-wide, per region, in the program (CEEUOPT), in the PARM of the EXEC statement, or through a CEEOPTS DD statement:9,36

//CEEOPTS  DD *
  RPTOPTS(ON)
  RPTSTG(ON)
  TERMTHDACT(UADUMP)
  HEAPPOOLS(ON)
/*

RPTOPTS reports the options in effect, RPTSTG reports storage use (useful for tuning heap and stack settings), TERMTHDACT controls what diagnostic output is produced when a thread ends because of an unhandled condition, and HEAPPOOLS enables a faster heap allocator for programs that allocate many small pieces of storage.36 LE callable services, all named CEE…, are available from any LE language; for example CEELOCT gets the local date and time and CEEHDLR registers a user condition handler.36

Addressing modes

Most existing COBOL and PL/I programs run in 31-bit addressing mode (AMODE 31), which can address up to 2 GB. 64-bit addressing gives access to storage "above the bar". Java and modern C/C++ applications commonly run in 64-bit mode, and Enterprise COBOL added 64-bit support with the LP(64) option in release 6.4. A program in one addressing mode cannot simply call a program in the other, so mixed-mode applications need interoperability support from LE or the products involved.2,6

14.1 Debugging

Abend codes

When a program fails, z/OS ends it abnormally (abends) with a system completion code (Sxxx) or a user code (Unnnn). Knowing the common codes speeds diagnosis a great deal.38

Diagnostic tools

  • Language Environment dump (CEEDUMP). A formatted dump with the call traceback, condition information and, if the program was compiled with TEST, local variables. It shows which program and statement failed.39
  • Compiler listings. The LIST and MAP listings let you translate the offset in an abend message into a source statement and field.6
  • IBM Debug for z/OS (z/OS Debugger). An interactive source-level debugger for COBOL, PL/I, C/C++ and assembler in batch, CICS, IMS and Db2, used from a 3270 terminal or from IDEs such as IBM Developer for z/OS and VS Code with Z Open Editor. It supports breakpoints, stepping, watching variables and code coverage.40
  • Run-time checks during testing. SSRANGE and NUMCHECK catch out-of-range subscripts and invalid numeric data at the point of error, before they corrupt storage or cause an S0C7 elsewhere.6
  • System dumps and IPCS, and fault-analysis products such as IBM Fault Analyzer, for problems that the formatted dumps do not explain.39

Exercise 14.1: diagnose an S0C7

CUSTRPT abends with S0C7 while processing the 4,182nd record. The CEEDUMP points to the statement ADD CUST-BALANCE TO WS-TOTAL-BAL. Describe how you would find and fix the problem.

Show solution
  1. The statement and field show that CUST-BALANCE holds invalid packed data in record 4,182.
  2. Browse the input data set in hexadecimal (for example ISPF browse with HEX ON) at record 4,182, positions 40–45. Typical findings are spaces (X'40') or a bad sign nibble, often from a file built by a program with a different layout.
  3. Fix the data at its source, and make the program robust: validate with IF CUST-BALANCE IS NUMERIC before arithmetic (as in VALCUST, Exercise 3.4), write rejected records to an error file, and set a non-zero return code.
  4. During testing, compile with NUMCHECK so that invalid data is reported clearly.6,38

14.2 Performance optimization

On a mainframe, CPU time is often charged for directly, so efficiency has a clear financial value. The main techniques fall into four groups.41

Compiler and runtime options

  • Compile production code with OPT(2) and the highest ARCH level supported by every machine the program may run on, including disaster-recovery machines.41
  • Use NOSSRANGE, NONUMCHECK and NOTEST (or TEST without hooks) in production, and keep the checking options for testing.
  • TRUNC(OPT) can be faster than TRUNC(STD) but is safe only if binary values never exceed their PICTURE size; TRUNC(BIN) is usually slowest.41
  • Use LE options such as HEAPPOOLS(ON), and size the initial heap and stack based on RPTSTG(ON) output.36

Data representation

  • Use binary (COMP or COMP-5) or indexes for subscripts and counters, and packed decimal for business arithmetic. Avoid arithmetic on DISPLAY numbers, which must be converted first.41
  • Give packed-decimal fields an odd number of digits (for example S9(7) rather than S9(6)), so that every half-byte is used.
  • Keep operands in an arithmetic statement of the same type and scale where possible, to avoid conversions.

I/O

  • Let the system choose block sizes (omit BLKSIZE) so that records are blocked efficiently on disk. Unblocked or poorly blocked data sets multiply the number of I/O operations.7
  • For VSAM, tune buffers (BUFND, BUFNI, or System-Managed Buffering) to the access pattern, and avoid random access where a sequential pass would do.7
  • Let DFSORT do sorting, selection and reformatting; it is highly optimised and usually much faster than equivalent application code.32

Database access

  • Select only the columns needed instead of SELECT *; filter in SQL instead of in the program; and use multi-row FETCH for large result sets.29
  • Bind with EXPLAIN(YES) and review the access paths in the plan table, making sure predicates can use indexes.29
  • Commit at sensible intervals in long batch programs, to release locks and limit the work redone after a failure; restartable batch design is described in IBM's batch modernisation guidance.42

Exercise 14.2: spot the inefficiencies

Identify three performance problems in this fragment and suggest fixes.

       01  WS-I        PIC 9(4).
       01  WS-TOTAL    PIC 9(9)V99.
       01  WS-TABLE.
           05  WS-AMT  PIC S9(6) COMP-3 OCCURS 5000 TIMES.
           PERFORM VARYING WS-I FROM 1 BY 1 UNTIL WS-I > 5000
               COMPUTE WS-TOTAL = WS-TOTAL + WS-AMT (WS-I)
           END-PERFORM
Show solution
  1. WS-I is a DISPLAY number used as a subscript, so it is converted on every iteration. Declare it PIC S9(8) COMP, or better, use an index (INDEXED BY) and PERFORM VARYING the index.
  2. WS-TOTAL is DISPLAY (zoned) and unsigned, so each addition converts it to packed and back and has to manage the sign. Declare it PIC S9(9)V99 COMP-3.
  3. WS-AMT has an even number of digits (6), so every field wastes a half-byte and the arithmetic may need extra instructions. Use S9(7) COMP-3, which takes the same 4 bytes.

(The loop could also stop at the number of entries actually in use rather than always running to 5000, using OCCURS … DEPENDING ON.)5,41

Exercise 15.1: capstone

Design (in outline) a nightly batch job that (1) loads the day's transactions from a sequential file into Db2, (2) applies them to customer balances, and (3) produces a report. Name the language used in each part and the main risks you would guard against.

Show solution
  1. JCL defines the steps; a workload scheduler starts the job after the transaction file arrives. Use IF tests so later steps run only if earlier ones succeed.
  2. DFSORT sorts transactions by customer ID and removes obviously invalid records.
  3. A COBOL program with embedded SQL reads the sorted file, validates each record (avoiding S0C7), applies UPDATEs, and checks SQLCODE after every statement. It commits every n records and records restart information so that it can resume after a failure.
  4. A second COBOL program (or a Db2 query unloaded with DFSORT formatting) produces the report.
  5. A REXX or Python script checks the return codes and the report totals, and notifies operations.

Key risks: invalid input data, partial updates after an abend (handled by commit and restart logic), locking conflicts with online work (commit frequency, isolation level), and changes to record layouts (shared copybooks, DCLGEN).29,30,42
