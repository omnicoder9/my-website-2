Mainframe Databases

Db2 for z/OS, IMS DB and VSAM, and the database theory behind them: a technical article with worked examples, source code and exercises

Abstract. Much of the world's transactional business data lives in two IBM database managers that run on z/OS: the hierarchical Information Management System (IMS), first delivered in 1968 for the Apollo programme, and the relational Db2 for z/OS, announced in 1983.1,2,3 Both sit on the access methods of z/OS, above all the Virtual Storage Access Method (VSAM). This article explains these platforms and the database principles they implement. It covers the hierarchical and relational data models, the architecture of IMS DB and Db2 for z/OS, the use of VSAM as a database storage layer, SQL and embedded SQL in COBOL, B-tree indexing, normalisation, cost-based query optimisation, transactions and the ACID properties, locking and concurrency control, backup and recovery, and replication for availability and disaster recovery. Every section includes concrete examples, most include source code (SQL, COBOL, JCL, IMS DBDGEN and PSBGEN macros, IDCAMS and Db2 utility control statements), and a set of exercises with worked solutions closes the article.

Scope note. Product details refer to Db2 13 for z/OS and IMS 15 unless stated otherwise. Companion articles in this series cover mainframe hardware, operating systems, programming languages and JCL; a separate article covers VSAM and z/OS storage management in general, so VSAM is treated here only as a foundation for databases. One running example, a small retail bank with customers, accounts and transactions, is used throughout so that the same data can be compared across models.

1. Data on the mainframe: an overview

A database management system (DBMS) separates the logical description of data from the way it is stored, controls concurrent access by many programs, and guarantees that committed changes survive failures.4,5 On z/OS three layers usually cooperate to provide this:

  • Access methods, chiefly VSAM, which store records in data sets on direct-access storage and provide keyed, relative or sequential access.6
  • Database managers, chiefly IMS DB (hierarchical) and Db2 for z/OS (relational), which add a data model, a data language, locking, logging and recovery.2,7
  • Transaction managers, such as CICS Transaction Server and IMS Transaction Manager, which schedule short online programs that call the database managers, and the z/OS Resource Recovery Services (RRS), which coordinates commit across them.8,9

1.2 The running example

The bank in this article keeps customers, each with one or more addresses and one or more accounts, and each account has a history of transactions. In a hierarchical database this is a tree rooted at the customer. In a relational database it is four tables linked by keys. In plain VSAM it is a keyed record file for each entity, and every relationship must be maintained by the application.

2. Hierarchical databases

In the hierarchical model a database is a collection of trees. Each node type is a record type (IMS calls it a segment type); one segment type is the root, and every other segment type has exactly one parent type. A single occurrence of the root together with all its dependants is a database record.2,4 The model fits data that has a natural one-to-many ownership structure, such as a customer owning accounts, a bill of materials, or an order with its lines.

2.1 Hierarchic sequence

Segments in a database record have a defined order called hierarchic sequence: top to bottom, then left to right, then front to back (by sequence field among twins of the same type).13 Sequential retrieval visits segments in that order, so the physical design determines the cost of every navigational path. A program that wants all transactions for a customer walks down from the root; a program that wants "every account with a balance over 1 million" across all customers must scan every database record unless a secondary index exists.

2.2 Strengths and limits

Because parent-child paths are stored as physical adjacency or pointers, a hierarchical DBMS can retrieve a root and its dependants in very few I/Os, and it can do so with predictable cost. This is why IMS remains attractive for very high-volume, well-understood transaction paths.2 The price is rigidity. Many-to-many relationships, such as a joint account owned by two customers, do not fit a single tree; IMS represents them with logical relationships that link segments in different physical databases. Queries that the designer did not anticipate need secondary indexes or full scans, and the program, not the DBMS, chooses the access path. Codd cited exactly these dependencies (on ordering, indexing and access paths) as the motivation for the relational model.10

3. IMS DB

IMS consists of a transaction manager (IMS TM) and a database manager (IMS DB). The database manager can be used by IMS TM transactions, by batch programs, by CICS through the Database Control (DBCTL) interface, and by Java and distributed applications through the IMS Universal drivers and IMS Connect.2,13 Programs access data through the Data Language/One (DL/I) call interface.

3.1 Definitions: DBD, PSB and ACB

Three control blocks describe an IMS database and a program's view of it:13,2

  • The database description (DBD) defines the physical database: its organisation and access method, its data set groups, and each segment type with its parent, length, fields and sequence field.
  • The program specification block (PSB) contains one or more program communication blocks (PCBs). Each database PCB names a DBD, lists the sensitive segments (SENSEG) the program may see, and gives processing options (PROCOPT) such as G (get), I (insert), R (replace), D (delete) and A (all).
  • Application control blocks (ACBs) are the DBDs and PSBs merged into the internal form used at run time, built by the ACB generation utility or held in the IMS catalog when IMS-managed ACBs are enabled.

DBDs and PSBs are written as assembler macro statements and processed by the DBDGEN and PSBGEN utilities. Listing 1 defines the bank database as a HIDAM database (described in the next section) and Listing 2 a PSB for an inquiry program.

3.4 Secondary indexes, logical relationships and HALDB

A secondary index is itself an IMS database (VSAM KSDS) that indexes any segment on any field and can present the indexed segment as if it were the root, giving an alternative processing sequence. Logical relationships connect segments in different physical databases so that, for example, a joint account can be reached from both owners. High Availability Large Databases (HALDB), the PHDAM, PHIDAM and PSINDEX types, split a database into partitions selected by key range or a user exit, so that each partition can be reorganised, recovered or taken offline independently.13

3.5 Fast Path

IMS Fast Path offers the data entry database (DEDB), divided into up to 2,048 areas, each a VSAM data set that can be replicated as multiple area data sets for availability. Updates are kept in buffers until commit and written afterwards, which shortens lock hold times; sequential dependent segments allow fast insert-only journaling such as transaction histories.13,2

SQL access to IMS. IMS also exposes its databases to SQL through the IMS catalog and the IMS Universal JDBC driver, mapping segments to tables and parent keys to foreign keys. This lets Java programs and reporting tools query IMS data without DL/I, although high-volume programs normally still use DL/I.14

4. Relational databases

E. F. Codd's 1970 paper, written at IBM San Jose, proposed that a database should present data only as relations: sets of tuples over named attributes, with no user-visible ordering, pointers or access paths.10 Relationships between entities are represented by values (a foreign key in one relation matching a primary key in another), and data is retrieved with a high-level language based on relational algebra or calculus. The DBMS, not the program, decides how to find the data. This property, physical data independence, means that adding an index or reorganising storage does not change application programs.10,4

4.1 Core concepts

  • A relation (table) has a heading of attributes (columns), each drawn from a domain (data type), and a body of tuples (rows). In theory a relation has no duplicate rows and no row order; SQL tables relax the first rule unless a key is declared.4,15
  • A candidate key is a minimal set of attributes whose values are unique in every row. One is chosen as the primary key.
  • A foreign key is a set of attributes whose values must match a candidate key of another (or the same) table. The rule that every non-null foreign key value matches an existing key is referential integrity.
  • Relational algebra operators (selection, projection, join, union, difference and others) take relations and return relations, so they compose. SQL queries are compiled into trees of such operators.10,16

4.2 From System R to DB2

IBM's System R project (1974–1979) built a full relational DBMS to test whether Codd's model could perform well enough. It produced the SEQUEL (later SQL) language, the first cost-based optimiser, and much of the locking and recovery technology still used today.17,11,16,18 Its results led directly to SQL/DS for VM and VSE in 1981 and to DATABASE 2 (DB2) for MVS, announced in 1983.3 SQL was standardised by ANSI in 1986 and by ISO in 1987; the current standard is ISO/IEC 9075:2023.15

5.2 Data structures

Db2 organises data in a containment hierarchy:7,19

  • A storage group is a named set of volumes (or an SMS storage class) on which Db2 creates data sets.
  • A database is a logical grouping of table spaces and index spaces, used for authorisation and operational commands such as -START DATABASE.
  • A table space holds the rows of one or more tables in pages of 4, 8, 16 or 32 KB. Current releases use universal table spaces (UTS), either partition-by-range (PBR, partitioned on key ranges, up to 4,096 partitions) or partition-by-growth (PBG, new partitions added as data grows). Older segmented and classic partitioned types are deprecated.
  • An index space holds one index.
  • Pages are cached in buffer pools (BP0, BP8K0, BP16K0, BP32K and so on) in DBM1's storage.
  • The catalog (database DSNDB06, tables such as SYSIBM.SYSTABLES and SYSIBM.SYSINDEXES) describes every object and is itself queryable with SQL. The directory (DSNDB01) holds internal information such as packages and recovery records.

Each table space or index space partition is a VSAM linear data set, discussed in Section 6.

5.3 Data sharing

In a Parallel Sysplex, up to 32 Db2 subsystems can form a data sharing group that reads and updates one shared copy of the data. Coherency is managed through structures in the coupling facility: a lock structure for global locks, group buffer pools that hold changed pages and track which members have cached each page, and a shared communications area for status.21,22 Applications see one database and can run on any member, so a member can be stopped for maintenance without an outage. The hardware side of Parallel Sysplex is described in the companion hardware article.

5.4 Program preparation, packages and plans

A static SQL program goes through these steps:23

  1. The Db2 precompiler or the Db2 coprocessor built into the COBOL, PL/I and C compilers replaces each EXEC SQL statement with a call to Db2 and writes the SQL into a database request module (DBRM).
  2. The modified source is compiled and link-edited into a load module. A consistency token is stored in both the load module and the DBRM.
  3. BIND PACKAGE checks authority, validates the SQL against the catalog, has the optimiser choose an access path for every statement, and stores the result as a package in a collection.
  4. BIND PLAN creates a plan whose package list names the collections the program may use. At run time Db2 matches the consistency token in the load module with a package.

Because access paths are fixed at bind time, static SQL has no optimisation cost at run time and its performance is stable, but a REBIND is needed to take advantage of new indexes or statistics. Dynamic SQL is optimised at PREPARE time, with results cached in the dynamic statement cache.23,24 Listing 7 in Section 7 shows the JCL.

6. VSAM as a database foundation

VSAM provides four main data set organisations: the key-sequenced data set (KSDS) with a B-tree-like index on a primary key, the entry-sequenced data set (ESDS) in arrival order, the relative record data set (RRDS) addressed by slot number, and the linear data set (LDS), a byte stream in 4 KB control intervals with no record structure.6,25 General VSAM design, catalogs and SMS are covered in the companion storage article; this section looks only at the three ways VSAM serves databases.

6.1 VSAM under Db2

Every Db2 table space and index space partition is a VSAM LDS, accessed by Db2 through the z/OS Media Manager, which gives Db2 full control of page layout, buffering and logging.19 Db2 normally creates these data sets itself through a storage group, but a database administrator can define them with IDCAMS (USING VCAT). 6.2 VSAM under IMS

IMS uses VSAM KSDS for HISAM databases, HIDAM primary indexes and secondary indexes, and either VSAM ESDS or IMS's own Overflow Sequential Access Method (OSAM) for the data of HDAM, HIDAM and HALDB databases. Fast Path DEDB areas are VSAM ESDS data sets processed by IMS's own media manager calls.13

6.3 VSAM as an application database

Many CICS applications keep master files directly in VSAM KSDSs, using the key as a primary index and alternate indexes (AIX) as secondary indexes. Such a file has no SQL, no joins and no declarative constraints, but CICS file control makes it transactional: a file defined as recoverable has its changes logged and backed out if a task abends, and record-level locks are held until syncpoint.6,25 With VSAM record-level sharing (RLS) the SMSVSAM server and coupling facility structures let CICS regions on several z/OS images update the same KSDS with record-level locking, much like Db2 data sharing; DFSMS Transactional VSAM (DFSMStvs) extends the same protection to batch jobs, using RRS for two-phase commit.6,9

7. SQL and embedded SQL

SQL began as SEQUEL in System R.17 It combines a data definition language (DDL: CREATE, ALTER, DROP), a data manipulation language (DML: SELECT, INSERT, UPDATE, DELETE, MERGE) and a data control language (GRANT, REVOKE). Db2 for z/OS implements most of the ISO standard's core features plus extensions of its own.15,20

8. Database indexing

An index maps key values to the locations of rows, so that a query can find matching rows without reading the whole table. Almost all database indexes, including Db2's and the VSAM KSDS index, descend from the B-tree of Bayer and McCreight (1972), and specifically from the B+-tree variant in which all keys appear in the leaf level and leaves are chained for sequential scans.29,30

8.1 Structure of a Db2 index

A Db2 for z/OS index is a balanced tree of pages: one root page, zero or more levels of non-leaf pages, and leaf pages that hold each key value with one or more record identifiers (RIDs). A RID locates a row by page number and by slot in that page's ID map.7,24 Every lookup from root to leaf touches the same number of pages, the index's number of levels (NLEVELS in SYSIBM.SYSINDEXES).

The number of levels grows with the logarithm of the number of keys, to the base of the fan-out (entries per page). If a 4 KB leaf page holds about 250 entries of a 10-byte key and its RID, 100 million keys need ⌈log250108⌉ = 4 levels. This is why indexed access to very large tables remains a handful of page reads, most of them for upper levels that stay in the buffer pool.30

8.2 Index types and options in Db2 for z/OS

  • Unique index: enforces uniqueness; required for a primary key or unique constraint.
  • Clustering index: Db2 tries to insert rows in this index's key order, so a range scan through it reads data pages sequentially. The cluster ratio statistic measures how well this holds and falls as inserts fill free space; REORG restores it.
  • Partitioned and non-partitioned indexes: on a PBR table space, a partitioned index has one physical piece per data partition, which keeps partition-level utilities independent. A data-partitioned secondary index (DPSI) is partitioned but not on the partitioning key; queries that cannot limit partitions must probe every piece.
  • INCLUDE columns on a unique index carry extra non-key columns so that more queries can be answered by index-only access.
  • Index on expression, for example on UPPER(CUST_NAME), makes predicates on that expression indexable.
  • Index compression and larger index page sizes reduce disk space and levels; RANDOM key ordering spreads inserts of ascending keys across pages to avoid a hot spot.

Source: Db2 13 for z/OS SQL reference and performance documentation.20,24 Db2 12 also introduced fast index traversal, which keeps an in-memory structure of the non-leaf levels of frequently used unique indexes to cut lookup CPU.12

8.3 Choosing indexes

Every index speeds up some reads and slows every insert, every delete and every update of its columns, and adds work to utilities. Good candidates are primary and foreign keys (foreign key indexes also make referential checks on parent deletes cheap), columns in frequent equality and range predicates, and columns in ORDER BY or GROUP BY clauses of frequent queries. For a multi-column index, put equality-predicate columns first and the range column last, because Db2 can match index columns only from the left up to and including the first range predicate.24

9. Database normalisation

Normalisation is the process of structuring relations so that each fact is stored once, which prevents update anomalies: inconsistencies that arise when a repeated fact is changed in one place but not another, when a fact cannot be recorded without an unrelated one, or when deleting one fact loses another. Codd defined the first three normal forms; Boyce–Codd normal form (BCNF), fourth (4NF) and fifth (5NF) normal forms followed.31,32,33,34,35 Each form is defined in terms of functional dependencies: X → Y holds if any two rows that agree on X also agree on Y.

9.1 Worked example

Suppose a bank's old statement file, converted from a flat VSAM record, is loaded into one table:

STATEMENT(ACCT_ID, CUST_ID, CUST_NAME, BRANCH_ID, BRANCH_CITY,
          TXN1_TS, TXN1_AMT, TXN2_TS, TXN2_AMT, ... TXN20_TS, TXN20_AMT)

Its dependencies are: ACCT_ID → CUST_ID, BRANCH_ID; CUST_ID → CUST_NAME; BRANCH_ID → BRANCH_CITY; (ACCT_ID, TXN_TS) → AMOUNT.

  1. First normal form (1NF) requires every attribute to hold a single value, with no repeating groups. The twenty TXN column pairs are a repeating group (an OCCURS clause in COBOL terms). Move them to their own relation: STMT(ACCT_ID, CUST_ID, CUST_NAME, BRANCH_ID, BRANCH_CITY) and TXN(ACCT_ID, TXN_TS, AMOUNT).
  2. Second normal form (2NF) forbids a non-key attribute depending on only part of a composite key. TXN's key is (ACCT_ID, TXN_TS) and AMOUNT depends on all of it, so TXN is in 2NF. Had we kept BRANCH_ID in TXN, it would depend on ACCT_ID alone and violate 2NF.
  3. Third normal form (3NF) forbids a non-key attribute depending on another non-key attribute (a transitive dependency). In STMT, CUST_NAME depends on CUST_ID and BRANCH_CITY on BRANCH_ID. Split them out: ACCOUNT(ACCT_ID, CUST_ID, BRANCH_ID), CUSTOMER(CUST_ID, CUST_NAME), BRANCH(BRANCH_ID, BRANCH_CITY).
  4. BCNF requires that the left side of every non-trivial functional dependency is a superkey. It differs from 3NF only when a relation has overlapping candidate keys, as in Exercise 6.
  5. 4NF deals with independent multi-valued facts. If a customer has several phone numbers and several email addresses, one relation CONTACT(CUST_ID, PHONE, EMAIL) must store every combination; 4NF splits it into CUST_PHONE and CUST_EMAIL.33

The result is exactly the design of Listing 4 plus a BRANCH table: the normalised design and the natural entity model coincide, which is typical.

9.2 Denormalisation

Normalisation optimises for update correctness, not read speed. Mainframe designs sometimes keep controlled redundancy, such as the running BALANCE column on ACCOUNT (derivable by summing TXN), because the derived value is read far more often than it changes and is maintained in the same unit of work as the transactions. Db2 can also maintain redundancy for the designer through materialized query tables, whose contents are defined by a query and which the optimiser can use automatically to answer matching queries.20,24 IMS designs are inherently denormalised in the sense that the hierarchy fixes one access path; secondary indexes and logical relationships are the controlled redundancy.

10. Query optimisation

Because SQL says what data is wanted and not how to get it, the DBMS must choose an access path. System R introduced the approach every major relational optimiser still follows: enumerate alternative plans, estimate the cost of each from catalog statistics, and pick the cheapest.16 Selinger and colleagues modelled cost as page fetches plus a weighted count of calls to the storage layer (a CPU proxy), estimated the fraction of rows each predicate keeps (its filter factor or selectivity), and searched join orders by dynamic programming, keeping plans that produce "interesting orders" useful for later joins, grouping or sorting.16 Db2 for z/OS's optimiser is a direct descendant, with a far richer cost model that includes CPU, I/O, buffer pool size, prefetch, parallelism and sort costs.24

10.1 Statistics

The optimiser is only as good as its statistics, which the RUNSTATS utility collects into the catalog. Key values include the number of rows (CARDF), the number of distinct values in a column (COLCARDF) and in index key prefixes (FIRSTKEYCARDF, FULLKEYCARDF), index levels and leaf pages (NLEVELS, NLEAF), the cluster ratio, and optional frequency and histogram statistics for skewed or correlated columns.24,36 Without frequency statistics Db2 assumes values are uniformly distributed, so the filter factor of COL = value is 1/COLCARDF.

10.3 Access path stability and tuning

For static SQL, Db2 keeps the access paths chosen at bind time. When a package is rebound, plan management (the PLANMGMT option) can retain the previous copies, APREUSE asks Db2 to reuse the existing access paths where possible, APCOMPARE reports differences, and REBIND ... 11. Transactions and ACID properties

A transaction is a sequence of operations treated as one indivisible change to the database. Gray described the transaction concept in 1981, and Haerder and Reuter coined the acronym ACID in 1983 for its four properties:37,38

11.1 Logging and write-ahead

Both Db2 and IMS follow the write-ahead logging rule: a log record describing a change must be on stable storage before the changed page is written to the database, and all of a transaction's log records must be on stable storage before the commit is acknowledged.38,39 Changed pages can then be written later, asynchronously, because the log contains enough to redo them. Db2 records changes in active log data sets (normally duplexed), offloads full ones to archive logs, and records the log inventory in the bootstrap data set (BSDS); log positions are relative byte addresses (RBAs), or log record sequence numbers (LRSNs) in data sharing.19 IMS writes its online log data sets (OLDS) through a write-ahead data set (WADS) and archives them to system log data sets (SLDS).13

After a failure, Db2 restart proceeds in four phases: log initialisation, current status rebuild, forward log recovery (redo committed work not yet on disk) and backward log recovery (undo work that was in flight).19 The same redo-then-undo structure was formalised in the ARIES recovery method developed at IBM.39

11.2 Distributed transactions and two-phase commit

A CICS transaction that updates a Db2 table, an IMS database and a VSAM file must commit all three or none. z/OS does this with the two-phase commit protocol: in phase 1 the coordinator (CICS, IMS TM or RRS) asks each resource manager to prepare, which forces its log so that it can either commit or back out later; if all vote yes, in phase 2 the coordinator logs the decision and tells each to commit.5,9 A participant that loses contact between the phases is in doubt and must hold its locks until the coordinator tells it the outcome; Db2 shows such threads with -DISPLAY THREAD(*) TYPE(INDOUBT) and lets an operator resolve them with -RECOVER INDOUBT.28

11.3 Savepoints

A savepoint marks a point within a unit of work to which the program can roll back without abandoning the whole transaction:

EXEC SQL SAVEPOINT BEFORE_FEE ON ROLLBACK RETAIN CURSORS END-EXEC
EXEC SQL INSERT INTO BANK.TXN VALUES (:ACCT, CURRENT TIMESTAMP, 'FE', -5.00)
END-EXEC
IF SQLCODE NOT = 0
   EXEC SQL ROLLBACK TO SAVEPOINT BEFORE_FEE END-EXEC
END-IF

Locks acquired after the savepoint are not released by rolling back to it; they are released at commit or full rollback.20

12. Database locking and concurrency

Isolation requires controlling the interleaving of concurrent transactions. Db2 and IMS both use locking, managed by the IRLM. The theoretical basis is two-phase locking: if every transaction acquires all its locks before releasing any, the result is equivalent to some serial order (it is serialisable).40,41 Db2 holds write locks to commit (strict two-phase locking), so no other transaction can read or overwrite uncommitted changes, except at isolation level UR.

12.1 Lock granularity and modes

Db2 locks at several levels: table space (or partition), table, page and row, chosen by the table space's LOCKSIZE. To avoid checking every row lock before locking a whole table, it uses the multiple-granularity scheme of Gray and colleagues: before taking an S or X lock on a page or row, a transaction takes an intent lock (IS or IX) on the containing table space.42,24 Db2 adds an update (U) mode, taken when a row is read with intent to update; U is compatible with S but not with another U, which prevents the classic deadlock in which two readers both try to upgrade to X.

12.3 Deadlocks and timeouts

A deadlock is a cycle of transactions each waiting for a lock another holds. IRLM checks for cycles at a regular interval (the deadlock detection cycle) and chooses a victim, which receives SQLCODE −911 (rolled back) or −913 (statement failed, not rolled back, as in some CICS and IMS environments). A transaction that waits longer than the timeout value gets the same codes with a timeout reason.24,27 Deadlocks are best prevented by design: access tables and rows in a consistent order, keep units of work short, read with intent to update (FOR UPDATE OF, which takes U locks) rather than reading and later updating, and commit often in batch.

Online applications that show data to a user and update it minutes later cannot hold locks across the think time. Instead they read without retaining locks, then update only if the row is unchanged. Db2 supports this with a row change timestamp column maintained automatically:20

ALTER TABLE BANK.CUSTOMER ADD COLUMN ROW_TS TIMESTAMP NOT NULL
  GENERATED ALWAYS FOR EACH ROW ON UPDATE AS ROW CHANGE TIMESTAMP;

-- Screen 1:  SELECT CUST_NAME, ROW CHANGE TIMESTAMP FOR CUSTOMER ...
-- Screen 2:
UPDATE BANK.CUSTOMER SET CUST_NAME = :NEWNAME
 WHERE CUST_ID = :ID
   AND ROW CHANGE TIMESTAMP FOR CUSTOMER = :TS_READ;
-- SQLCODE +100 means someone else changed the row: re-read and retry.

12.5 Utilities, claims and drains; IMS locking

Db2 utilities use claims and drains rather than ordinary locks: every SQL application registers a claim on the objects it uses, and a utility that needs exclusive access drains them by waiting for current claimers to commit while blocking new ones.24 That is why long-running batch jobs that never commit can block online REORG. IMS uses the same IRLM (or, without data sharing, its internal program isolation lock manager) to lock database records and segments, and the PROCOPT of each PCB determines whether a program reads with or without integrity (PROCOPT GO reads without locking, like UR).13,14

13. Database backup and recovery

Logging handles failures of programs and systems; media recovery handles loss or corruption of the data itself. The technique is the same in Db2 and IMS: restore a backup copy, then apply logged changes made since the copy, up to the current time or to a chosen earlier point.38,5 Two business measures drive the design: the recovery point objective (RPO), how much committed data may be lost, and the recovery time objective (RTO), how long recovery may take.44

13.3 Recovery strategy

  • Copy frequency trades backup cost against recovery time: the more log to apply, the longer recovery takes.
  • Keep dual active logs and dual archives on separate devices; a lost log makes recovery to current impossible.
  • Test recovery regularly, including point-in-time recovery of whole referential sets and full system recovery at the disaster site.
  • For the largest systems, volume-level fast replication (FlashCopy-based BACKUP SYSTEM, or storage snapshots) gives near-instant backups, and disk mirroring (Section 14) protects against site loss.

14. Database replication

Replication keeps copies of data in more than one place, for disaster recovery, for availability during maintenance, to feed analytics and distributed systems, or to move workloads between sites. Mainframe sites use three broad approaches.44,45

ApproachExamplesWhat is copiedTypical RPO
Synchronous disk mirroringMetro Mirror (PPRC), with GDPS or HyperSwapEvery disk write, before the I/O completesZero, within metropolitan distance (tens of km)
Asynchronous disk mirroringGlobal Mirror, z/OS Global Mirror (XRC)Consistent groups of disk writes, shortly afterSeconds, at unlimited distance

Disk mirroring is transparent to the database: because Db2 and IMS write-ahead logs are mirrored in the same consistency group as the data, a restart at the remote site is just like a restart after a power failure.44 Synchronous mirroring adds the round-trip delay to each write (light in fibre travels about 1 km in 5 µs, so 100 km adds about 1 ms), which is why it is limited to metropolitan distances.

14.1 Log-based replication

Logical replication reads committed changes from the log and applies them as SQL at the target. For Db2 for z/OS, a capture program reads the log through the instrumentation facility interface, which requires the source table to be defined with DATA CAPTURE CHANGES so that full before and after images are logged.45,20 Q Replication sends the changes over IBM MQ queues to an apply program; Change Data Capture can target Db2 on other platforms, other DBMSs, files or Kafka. Because the target is a separate database, it can be used for queries or as the active side of an active-active configuration, such as GDPS Continuous Availability, which switches workloads between two sites in seconds.44

Listing 17. Enabling capture, and an illustrative trigger-based change table

-- Required for log-based capture products:
ALTER TABLE BANK.TXN DATA CAPTURE CHANGES;

-- A minimal do-it-yourself alternative for teaching: record each insert
-- in a change table that a downstream job reads and then deletes.
CREATE TABLE BANK.TXN_CHG
  (OP CHAR(1) NOT NULL, ACCT_ID CHAR(10) NOT NULL,
   TXN_TS TIMESTAMP NOT NULL, AMOUNT DECIMAL(15,2) NOT NULL,
   CAPTURED TIMESTAMP NOT NULL)
  IN DATABASE BANKDB;

CREATE TRIGGER BANK.TXN_CDC
  AFTER INSERT ON BANK.TXN
  REFERENCING NEW AS N
  FOR EACH ROW MODE DB2SQL
  INSERT INTO BANK.TXN_CHG
    VALUES ('I', N.ACCT_ID, N.TXN_TS, N.AMOUNT, CURRENT TIMESTAMP);

-- Apply side (on the target system), idempotent so it can be re-run:
MERGE INTO REPL.TXN T
USING (SELECT ACCT_ID, TXN_TS, AMOUNT FROM STAGE.TXN_CHG) S
   ON T.ACCT_ID = S.ACCT_ID AND T.TXN_TS = S.TXN_TS
 WHEN NOT MATCHED THEN INSERT VALUES (S.ACCT_ID, S.TXN_TS, S.AMOUNT);

The trigger approach puts capture work inside every transaction and adds a write to each insert, which is why production products read the log instead; it is shown only to make the mechanism concrete. The apply step is idempotent because a replay after a failure must not create duplicates.

14.2 IMS replication

IMS supports remote copies through disk mirroring, through IMS Remote Site Recovery, which ships IMS log data to a tracking IMS at a remote site, and through InfoSphere IMS replication, which captures IMS log records and applies them to another IMS database or, through CDC, to relational targets.2,45

Replication is not backup. A replica faithfully copies mistakes: a batch job that deletes the wrong rows deletes them at every site within seconds. Point-in-time recovery from image copies and logs (Section 13) is still needed, and some sites keep an additional delayed or snapshot copy for this reason.44

Exercise 1. Hierarchic sequence

Using the database record in Figure 2, a program issues GU CUSTOMER(CUSTID = C001) and then repeated unqualified GN calls. List the segments returned, in order, and say what status code ends the sequence if C001 is the last customer in the database. Which segment does GNP TXN return if the program is positioned on ACCOUNT A20 with that account as parent?

Show solution

GN returns segments in hierarchic sequence (top to bottom, left to right): ADDRESS home, ADDRESS work, ACCOUNT A10, TXN t1, TXN t2, ACCOUNT A20, TXN t3. The next GN finds no more segments and returns status GB (end of database).14 With A20 established as parent, GNP TXN returns TXN t3, and a further GNP TXN returns GE because no more TXN segments exist under that parent.

Exercise 3. SQL

Write a query that lists, for every customer whose accounts hold more than 100,000 in total, the customer's name, the number of accounts and the total balance, largest total first. Then change it so that loan accounts (type LON, whose balances are amounts owed) are subtracted rather than added.

Show solution 
SELECT C.CUST_NAME, COUNT(*) AS N_ACCTS, SUM(A.BALANCE) AS TOTAL
  FROM BANK.CUSTOMER C
  JOIN BANK.ACCOUNT  A ON A.CUST_ID = C.CUST_ID
 GROUP BY C.CUST_ID, C.CUST_NAME
HAVING SUM(A.BALANCE) > 100000
 ORDER BY TOTAL DESC;

-- Net position: subtract loans
SELECT C.CUST_NAME, COUNT(*) AS N_ACCTS,
       SUM(CASE A.ACCT_TYPE WHEN 'LON' THEN -A.BALANCE
                            ELSE A.BALANCE END) AS NET
  FROM BANK.CUSTOMER C
  JOIN BANK.ACCOUNT  A ON A.CUST_ID = C.CUST_ID
 GROUP BY C.CUST_ID, C.CUST_NAME
HAVING SUM(CASE A.ACCT_TYPE WHEN 'LON' THEN -A.BALANCE
                            ELSE A.BALANCE END) > 100000
 ORDER BY NET DESC;

Exercise 4. A duplicate key in embedded SQL

In production, Listing 8 occasionally fails with SQLCODE −803 on the INSERT into TXN. Explain why, and propose two fixes.

Show solution

The primary key of TXN is (ACCT_ID, TXN_TS), and TXN_TS is set to CURRENT TIMESTAMP, which has microsecond precision by default. Two deposits to the same account in the same microsecond (possible with parallel batch, or in data sharing where two members post to the same account) produce the same key, and Db2 returns −803 (duplicate key).27 Because SQL-ERROR then rolls back, the balance update is undone too, so the data stays correct but the deposit is lost unless retried. Fixes: (1) make the key unique by construction, for example by adding a sequence number from a Db2 SEQUENCE object or an identity column to the key, or by using a higher-precision timestamp such as TIMESTAMP(12); or (2) treat −803 like −911, retrying the unit of work so that a fresh timestamp is taken. Option 1 is better because it removes the failure rather than handling it.20

Exercise 5. Index matching and levels

(a) TXN has an index on (ACCT_ID, TXN_TYPE, TXN_TS). For WHERE ACCT_ID = ? AND TXN_TS BETWEEN ? AND ?, how many index columns can match, and how is the TXN_TS predicate used? How would you improve it without a new index? (b) An index has 500 million entries and about 300 entries fit in a page. How many levels will it have?

Show solution

(a) Matching proceeds from the leftmost column and stops at the first column without a predicate. ACCT_ID matches; TXN_TYPE has no predicate, so MATCHCOLS = 1. The TXN_TS predicate can still be applied to index entries before any data page is read (index screening), but Db2 must read every index entry for that account. If the transaction types are a small known set, adding AND TXN_TYPE IN ('DP','WD','FE','IN') lets Db2 match all three columns with an IN-list access path, probing one narrow range per type.24

(b) 3003 = 2.7 × 107 < 5 × 108 ≤ 3004 = 8.1 × 109, so ⌈log300(5 × 108)⌉ = 4 levels: a root, two non-leaf levels and the leaf level.30 In practice non-leaf pages hold more entries than leaves (they hold only key separators and page pointers), so the real figure may be one level fewer.

Exercise 6. BCNF

The bank assigns each customer one adviser per product (mortgages, pensions, savings), and each adviser handles exactly one product. The relation is ADVICE(CUST_ID, PRODUCT, ADVISER_ID). Find the functional dependencies and candidate keys. Is the relation in 3NF? In BCNF? Decompose it if needed, and say what is lost.

Show solution

Dependencies: (CUST_ID, PRODUCT) → ADVISER_ID, and ADVISER_ID → PRODUCT. Candidate keys: (CUST_ID, PRODUCT) and (CUST_ID, ADVISER_ID). Every attribute belongs to some candidate key, so there are no non-prime attributes and the relation is in 3NF. It is not in BCNF, because ADVISER_ID → PRODUCT has a left side that is not a superkey: the product an adviser handles is repeated in every row for each of the adviser's customers, and changing an adviser's product means updating many rows.32,35

BCNF decomposition: ADVISER(ADVISER_ID, PRODUCT) and CUST_ADVISER(CUST_ID, ADVISER_ID). The join reconstructs the original without loss, but the dependency (CUST_ID, PRODUCT) → ADVISER_ID can no longer be enforced by a key in either table: nothing stops a customer being assigned two mortgage advisers. It must be enforced by a trigger or application logic. This trade-off, BCNF versus dependency preservation, is the classic reason some designs stop at 3NF.4

Exercise 7. Query optimisation

TXN has 100 million rows; COLCARDF for ACCT_ID is 2 million. (a) Estimate the rows returned by WHERE ACCT_ID = ?. (b) One corporate account has 10 million transactions. What goes wrong, and what statistics fix it? (c) Rewrite WHERE ACCT_ID = ? AND YEAR(TXN_TS) = 2026 so that both predicates can match the primary key index.

Show solution

(a) Filter factor 1/2,000,000, so 100,000,000 / 2,000,000 = 50 rows on average.24

(b) The uniform estimate of 50 rows is badly wrong for the corporate account. If a query with a literal value is optimised for 50 rows, Db2 may choose a nested loop with random I/O where a scan with sequential prefetch or a different join order would be far cheaper. Collecting frequency statistics on ACCT_ID (RUNSTATS ... COLGROUP(ACCT_ID) FREQVAL COUNT n, or histogram statistics) records the skew. For statements with host variables, the optimiser cannot know the value at bind time; options include the REOPT bind option (REOPT(ALWAYS) for static SQL, REOPT(ONCE) or REOPT(AUTO) for dynamic SQL), which re-optimises using the actual values, or a separate statement for known large accounts.24,36

(c) WHERE ACCT_ID = ? AND TXN_TS >= '2026-01-01-00.00.00' AND TXN_TS < '2027-01-01-00.00.00'. Now both predicates are on bare columns and can match the (ACCT_ID, TXN_TS) index with MATCHCOLS = 2. Check with EXPLAIN, since some Db2 releases perform this rewrite internally.

Exercise 8. A deadlock without two tables

Two online transactions run this logic on the same account at the same moment, at isolation CS with row locking: SELECT BALANCE INTO :B FROM ACCOUNT WHERE ACCT_ID = ? with WITH RS, then compute a new balance, then UPDATE ACCOUNT SET BALANCE = :NEWB WHERE ACCT_ID = ?. Why can they deadlock, and what is the fix? What bug would there be if they ran at plain CS instead?

Show solution

At RS each transaction keeps an S lock on the row it read. Both hold S (S is compatible with S, Table 1). Each then requests X for the update, which is incompatible with the other's S, so each waits for the other: a deadlock, and IRLM rolls one back with −911.24 Fix: declare the intent to update when reading, so that Db2 takes a U lock (SELECT ... FOR UPDATE OF BALANCE through a cursor, or WITH RS USE AND KEEP UPDATE LOCKS on the singleton select). U is not compatible with U, so the second reader waits at the read rather than deadlocking at the update. Better still, avoid the read-compute-write pattern: UPDATE ... SET BALANCE = BALANCE + :AMT does it in one statement, as Listing 8 does.

At plain CS the lock on the read row is released as soon as the read completes, so both transactions read the same old balance and the second update overwrites the first: a lost update. The deadlock at RS was in fact protecting against this bug.43

Exercise 9. Choosing an isolation level

An end-of-day report sums all account balances and also sums them by branch, in two separate queries in one unit of work, while online transfers continue. Auditors require the two totals to agree. Which Db2 isolation level is needed, and what are the alternatives?

Show solution

At CS or UR the first and second scans can see different states: a transfer that commits between (or during) them moves money from a row already counted to one not yet counted. RS keeps locks on all qualifying rows until commit, so a transfer touching a row already read must wait; if new accounts can also be opened (inserts), only RR prevents phantoms that the second query would count.43,24 But RR or RS on whole-table scans blocks online work and may escalate to a table space lock. Better alternatives on a mainframe: compute both totals in a single statement (GROUP BY ROLLUP(BRANCH_ID)), so they come from the same pass; run the report against a consistent point-in-time copy (a FlashCopy-based image, or a replica at a quiesce point); or run in a batch window after online work stops.

Exercise 10. A recovery plan

Full image copies of BANKDB are taken every Sunday at 02:00 with SHRLEVEL CHANGE, incremental copies every other day at 02:00, and the scheduler runs QUIESCE TABLESPACESET before every batch job. On Wednesday a faulty batch job ran from 13:00 to 13:40 and corrupted TXN and ACCOUNT. Online work continued until 15:00, when the error was found. What do you recover, to where, and what data is at risk?

Show solution

Stop update access to BANKDB (-STOP DATABASE or -START DATABASE ... ACCESS(RO)). Find the quiesce point taken before the 13:00 job in SYSIBM.SYSCOPY or with REPORT RECOVERY. Recover both table spaces of the referential set to that log point (RECOVER ... TOLOGPOINT): Db2 restores Sunday's full copy, merges Monday's to Wednesday's incrementals, and applies the log up to the quiesce point. Then rebuild indexes, run CHECK DATA if anything is in CHECK-pending, and take a new full image copy so that the next recovery does not have to go back through the point-in-time.36

Everything committed between the quiesce point (about 12:59) and 15:00 is removed, including about two hours of good online transactions. Those must be re-applied: from transaction journals, by re-entry, or by using a log analysis tool to generate SQL that redoes the good changes (or, alternatively, that undoes only the bad job's changes, which avoids the point-in-time recovery altogether if the bad changes can be isolated). This is why RPO for logical errors is usually much worse than for hardware failures, and why replication alone (Section 14) does not help.

Exercise 11. Replication distance

A bank has its primary data centre, a second centre 15 km away, and a disaster recovery site 900 km away. A Db2 commit causes on average two log writes in series. Estimate the extra commit latency if each site is mirrored synchronously, using 5 µs per km of fibre each way, and recommend a configuration.

Show solution

Each synchronous write waits for a round trip. At 15 km: 2 × 15 × 5 µs = 0.15 ms per write, 0.3 ms per commit, which is acceptable. At 900 km: 2 × 900 × 5 µs = 9 ms per write, 18 ms per commit, before any protocol overhead, which would cripple a high-volume OLTP system and serialise hot log writes. Recommendation: synchronous Metro Mirror with HyperSwap to the 15 km site (RPO zero, near-zero RTO for disk failure), and asynchronous Global Mirror to the 900 km site (RPO of seconds), managed together by GDPS in a three-site configuration. Add log-based replication if a queryable or active-active copy is needed.44

Exercise 12. VSAM and Db2

Db2 stores table spaces in VSAM linear data sets rather than in key-sequenced data sets. Give three reasons.

Show solution

(1) Db2 manages its own page format, free space, row placement (clustering), compression and indexes; a KSDS would impose VSAM's own record format and a second, redundant index on top. (2) Db2 must control when pages are written, to obey the write-ahead logging rule and to batch writes from its buffer pools; with an LDS and Media Manager it reads and writes whole 4 KB control intervals directly, without VSAM's record-level buffering and locking. (3) An LDS has no record structure to maintain, so there are no control interval or control area splits; Db2's own space map pages and REORG handle growth.19,6 By contrast, a CICS application that keeps data directly in VSAM depends on the KSDS's key index and record management, because it has no DBMS of its own (Section 6.3).
