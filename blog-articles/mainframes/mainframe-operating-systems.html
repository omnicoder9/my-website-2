Mainframe Operating Systems

z/OS, z/VM, Linux on IBM Z, z/VSE and z/TPF: initialization, configuration, tasks, memory, scheduling, logging and recovery

Technical article with worked examples, source code, exercises and solutions · References in Vancouver style · October 2026

Abstract. IBM Z mainframes run a family of operating systems that differ sharply in purpose: z/OS for general-purpose, high-integrity batch and transaction work; z/VM as a hypervisor and interactive system; Linux on IBM Z as an open-source workload platform; z/VSE (now continued by a third party as VSEn) for smaller installations; and z/TPF for extreme-volume transaction processing. This article explains each system, then follows the operational life of a mainframe system through initialization (IPL), configuration, process and memory management, job scheduling, logging and monitoring, and recovery and maintenance. Each section includes runnable examples (JCL, REXX, operator commands, z/VM CP and CMS commands, and Linux shell) and closes with exercises. Every factual statement is referenced to IBM documentation, IBM Redbooks or peer-reviewed literature.

Scope. Hardware is covered only as far as the operating systems need it (logical partitions, address spaces, I/O configuration). A companion article treats mainframe hardware architecture in depth. Version numbers refer to z/OS 3.2, z/VM 7.4 and z/TPF 2025 documentation unless stated otherwise. Examples use illustrative names (system SYS1, user NICK); adapt data set names, volumes and suffixes to your installation, and run commands that change a system only with the authority to do so.

1. The operating system landscape

All current IBM Z operating systems run on the z/Architecture, the 64-bit extension of ESA/390 introduced in 2000 with the zSeries 900, which added 64-bit general registers, 64-bit virtual addressing, and multiple address-space modes while preserving compatibility with 24- and 31-bit programs[1]. The architecture is defined formally in the z/Architecture Principles of Operation, which is the contract between hardware and every operating system described here[2].

A modern machine is almost always partitioned. The Processor Resource/Systems Manager (PR/SM) firmware hypervisor divides one machine into logical partitions (LPARs), each of which can run its own operating system image; z/VM can then subdivide an LPAR into many virtual machines[3,4]. The operating systems therefore coexist on the same hardware, and choosing among them is a question of workload, not of machine.

1.1 A short history

MVS (Multiple Virtual Storage) grew out of OS/360 and its successors OS/VS1 and OS/VS2 in the early 1970s. Its defining move was to give each user or job its own virtual address space, rather than a region in one shared space, which improved isolation and allowed the system to grow with virtual storage[5]. MVS later became OS/390 and then z/OS[3].

The virtual machine line began with the CP-40 and CP-67 research systems at IBM's Cambridge Scientific Center and became VM/370 in 1972[6,12]. Popek and Goldberg later formalized the conditions under which an architecture can be efficiently virtualized[13], and IBM's System/370-XA added the Start Interpretive Execution (SIE) instruction, which lets the hardware run a guest directly while the control program retains control[14]. SIE remains the foundation of z/VM and of KVM on IBM Z.

2. z/OS

z/OS is IBM's flagship mainframe operating system. Its core is the MVS base control program, surrounded by components such as the Job Entry Subsystem (JES), the Time Sharing Option/Extensions (TSO/E) for interactive users, the Interactive System Productivity Facility (ISPF), Data Facility Storage Management Subsystem (DFSMS), Resource Access Control Facility (RACF) and z/OS UNIX System Services[3,15].

2.1 Address spaces

Every unit of significant work in z/OS runs in an address space: a batch job, a logged-on TSO user, a started task such as a database manager, and many system functions (for example the master scheduler, JES2 and the console address space) each have one[3]. Address spaces are isolated from each other by default, which is how z/OS protects one workload from another while running thousands of them concurrently[15].

2.2 Data sets and catalogs

z/OS stores data primarily in data sets rather than in a byte-stream file hierarchy. Data sets have a record format (RECFM), logical record length (LRECL) and organization (sequential, partitioned, VSAM), and are located through the catalog structure, headed by the master catalog[3]. z/OS UNIX adds hierarchical file systems (zFS) alongside data sets (section 7).

2.3 First example: a batch job

Job Control Language (JCL) tells z/OS what program to run and which data sets it needs. A job consists of a JOB statement, one or more EXEC statements (steps), and DD (data definition) statements[16]. The job below allocates a data set with the do-nothing program IEFBR14, writes a record into it with the IEBGENER utility, and runs a third step only if the second succeeded.

DISP=(NEW,CATLG,DELETE) means "create the data set; catalog it if the step ends normally; delete it if the step abends". BLKSIZE=0 asks the system to choose an optimal block size, and &SYSUID resolves to the submitting user's ID[16]. The IF/THEN/ENDIF construct tests the return code of an earlier step[16].

2.4 Operator interface

Operators control z/OS with system commands entered at a console, from SDSF, or by automation. Most commands have short forms: D for DISPLAY, S for START, P for STOP, F for MODIFY, C for CANCEL[17]. JES2 commands begin with the JES2 command character, conventionally $[18].

3. z/VM

z/VM consists of two main parts. The Control Program (CP) is the hypervisor: it creates virtual machines that each appear to have their own processors, storage and devices. The Conversational Monitor System (CMS) is a single-user operating system that runs inside a virtual machine and gives users and administrators an interactive environment[4,7]. This split dates back to CP-67/CMS[6].

3.1 The user directory

Every virtual machine is defined by an entry in the CP user directory, which specifies its storage, virtual processors, minidisks (slices of real DASD), network connections and privilege classes[19]. Directory entries are usually managed with the Directory Maintenance Facility (DirMaint) or an equivalent product[4].

The first line gives the user ID, the password field (AUTOONLY means the guest can only be started by XAUTOLOG, not by an interactive logon), initial storage (4 GB), maximum storage (8 GB) and privilege class G. MACHINE ESA 4 allows up to four virtual CPUs, NICDEF attaches a virtual network adapter to a virtual switch, and each MDISK defines a minidisk by device type, start cylinder, size in cylinders, volume label and access mode[19].

3.2 CP privilege classes

CP commands are grouped into privilege classes. IBM defines classes A (system operator), B (system resource operator), C (system programmer), D (spooling operator), E (system analyst), F (service representative) and G (general user); an installation can redefine them[19,20].

3.3 CMS and REXX

CMS gives each user a file system on minidisks accessed by file mode letters (A, B, ...), an editor (XEDIT) and a REXX interpreter[21,22]. A REXX program can issue CP commands and capture their output with the DIAG(8, ...) function[22].

A terminal value of DSC means the user is logged on but disconnected, which is the normal state for server guests such as Linux[20].

3.4 Single System Image and live guest relocation

The z/VM Single System Image (SSI) feature clusters up to four z/VM systems that share a common directory and resources, and live guest relocation can move a running Linux guest between members without stopping it, for example to allow maintenance on one member[4,19].

4. Linux on IBM Z

Linux on IBM Z is the ordinary Linux kernel compiled for the 64-bit s390x architecture, with device drivers for mainframe I/O such as DASD (disk), FCP-attached SCSI, OSA network adapters, HiperSockets and cryptographic coprocessors. It can run directly in an LPAR, as a z/VM guest, or as a KVM guest[8]. IBM publishes the kernel features and the s390-tools commands in Device Drivers, Features, and Commands[8], and the z/VM side of a Linux deployment in Getting Started with Linux on IBM Z[23].

4.1 Mainframe-specific devices

Mainframe I/O devices are addressed by a bus ID such as 0.0.0100 (channel subsystem ID, subchannel set ID, device number). A device must be set online before Linux uses it[8].

4.2 Knowing where you run

The file /proc/sysinfo reports the machine, LPAR and hypervisor layers that the kernel can see[8]. When Linux runs as a z/VM guest, the vmcp command passes CP commands to z/VM[8].

5. z/VSE and VSEn

z/VSE (Virtual Storage Extended) is IBM's entry mainframe operating system, aimed at smaller installations that run batch and CICS transaction workloads[9]. Work runs in partitions: static partitions named BG (background) and F1 to FB (foreground), plus dynamic partitions created on demand. The VSE/POWER spooling subsystem queues jobs and output, and VSE JCL is distinct from z/OS JCL[9].

IBM z/VSE 6.2 reached end of service on 30 September 2023, and IBM has no follow-on release. IBM licensed the z/VSE source code and most of the stack to 21st Century Software, which offers derivative VSE products[10]. That company announced its first release, VSEn V6.3, in March 2022, stating that it keeps compatibility with earlier z/VSE versions and leaves commands, jobs and APIs unchanged[24].

Lines beginning * $$ are VSE/POWER job entry control statements; lines beginning // are VSE JCL; /* ends in-stream data and /& ends the job[9].

6. z/TPF

z/TPF (Transaction Processing Facility) is a special-purpose operating system for very high volumes of short transactions, historically airline reservations and payment processing. Its design is organized around messages rather than jobs or users[11].

6.1 Message flow and the ECB

For each input message, z/TPF creates an entry control block (ECB), which is private to that message's processing (the Entry) and points to the message. Control passes to the first ECB-controlled program, which converts the message and places the ECB on a ready list for an I-stream engine (processor). Application programs then process it. If a program must wait for I/O, the Entry waits while the processor runs other work. When processing completes the Entry issues EXITC, and the system releases all storage the message used. A "shutdown level" limits the number of input messages in the system so that unlimited input cannot exhaust main storage[11].

6.2 Program linkage

z/TPF programs transfer control with Enter/Back macros rather than a conventional call stack: ENTRC enters a program and expects a return, ENTNC enters without return, ENTDC enters and discards all prior linkage, and BACKC returns to the program that last issued ENTRC[25].

The design is deliberately lean: each Entry is short-lived, holds storage only while it runs, and returns everything at exit, which is what allows z/TPF to sustain very high message rates[11].

7. UNIX and Linux concepts on mainframes

The mainframe hosts UNIX and Linux in two different ways, and the distinction matters.

  • z/OS UNIX System Services is a component of z/OS that provides a POSIX-conforming UNIX environment: a hierarchical file system (zFS), a shell, UNIX processes and threads, and sockets. UNIX processes are z/OS address spaces or run inside them, so the same security (RACF), workload management and accounting apply to both worlds[3,26].
  • Linux on IBM Z is a separate operating system, native Linux, that happens to run on mainframe hardware (section 4)[8].

7.1 z/OS UNIX configuration

The kernel options and file system mounts for z/OS UNIX are set in the BPXPRMxx PARMLIB member[26,27]. A user needs an OMVS segment in RACF (with a UID, home directory and shell) to use z/OS UNIX[26].

7.2 Bridging data sets and files

The z/OS UNIX shell can address MVS data sets directly with the //'DATA.SET.NAME' syntax, and batch jobs can run shell commands through BPXBATCH[26].

Exercise 7.1. UNIX on z/OS versus Linux on Z

A developer says: "Our z/OS has a UNIX shell, so we can just run our x86 Linux binaries there." Explain why this is wrong, and name the two mainframe options that would let them run Linux software.

Show solution

z/OS UNIX is a POSIX environment inside z/OS, not Linux; it runs z/OS programs compiled for z/Architecture and z/OS interfaces[26]. x86 binaries need recompiling for the target in any case, since IBM Z is a different instruction set[2]. To run Linux software they can deploy Linux on IBM Z (s390x) in an LPAR or as a z/VM or KVM guest, rebuilding or obtaining s390x builds of the software[8].

8. Operating system initialization (IPL)

On IBM Z, booting is called Initial Program Load (IPL). The operator, usually at the Hardware Management Console, names a load address (the device holding the IPL program) and a load parameter; the hardware reads the IPL record from that device and passes control to it[2,3].

8.1 z/OS IPL sequence

The load parameter is eight characters. Positions 1 to 4 give the device number of the volume containing the I/O definition file (IODF) and the LOADxx member; positions 5 and 6 give the LOADxx suffix; position 7 is the initialization message suppression indicator (IMSI), which controls which prompts the operator sees; and position 8 selects an alternate nucleus[15,27].

LOADxx identifies the IODF, the master catalog, the sysplex name, the PARMLIB concatenation and the IEASYSxx members to use[27]. IEASYSxx then names the other PARMLIB members that configure each component, and its values can be overridden by the operator during IPL[27,28].

Each xx value is a two-character suffix that selects a member: SMF=00 selects SMFPRM00, OMVS=(00,01) concatenates BPXPRM00 and BPXPRM01, and PROG=(00,A1) selects the PROGxx members that define APF-authorized libraries and the link list[27]. After IPL, D IPLINFO shows which members were actually used[17].

A cold start, quick start and warm start differ in how much prior state is reused; for example, the CLPA option rebuilds the pageable link pack area from LPALSTxx, while a quick start reuses the existing PLPA page data set[15,28].

8.2 z/VM IPL

z/VM's CP is IPLed from its system residence volume. It reads the SYSTEM CONFIG file, which defines system-wide settings such as the CP-owned and user volumes, features, and the virtual switches; it then automatically logs on (XAUTOLOGs) the AUTOLOG1 user, whose PROFILE EXEC typically starts service machines and guests[4,19].

8.3 Linux on IBM Z IPL

Linux uses the zipl boot loader to write an IPL record that the hardware can read from a DASD, SCSI disk or z/VM reader. After changing kernels or kernel parameters, zipl must be rerun, and chreipl chooses the device used for the next re-IPL (reboot)[8]. Under z/VM, a guest is IPLed with the CP command IPL 0100, matching the IPL statement in Listing 3[20].

Exercise 8.1. Decoding a load parameter

An operator IPLs with load parameter 0A8225M1. What does each part mean? Write a small REXX function that decodes any 8-character load parameter.

Show solution

0A82 is the device number of the IODF/LOADxx volume; 25 selects member LOAD25; M is the IMSI character; 1 selects alternate nucleus IEANUC01. The IMSI character determines whether the operator is prompted for system parameters and which messages are suppressed[27].

9. System configuration and administration

9.1 z/OS: PARMLIB, symbols and dynamic change

z/OS configuration lives mostly in PARMLIB members, which are read at IPL and, for many components, can be reloaded without IPL by the SET command (for example SET SMF=01 or SET PROG=A2)[17,27]. System symbols such as &SYSNAME let one set of members serve several systems in a sysplex[27,29].

Security administration is done in RACF (or an equivalent external security manager). APF authorization, in particular, is security-relevant: programs from APF-authorized libraries can obtain supervisor state, so the APF list must be tightly controlled[15,30].

9.2 Interactive administration with REXX

TSO/E REXX is the standard scripting language for z/OS administrators. External functions such as LISTDSI return data set attributes into REXX variables[31].

9.3 z/VM and Linux

On z/VM, the main configuration points are SYSTEM CONFIG (system-wide) and the user directory (per guest)[19]. On Linux on IBM Z, mainframe device configuration is managed persistently with the zdev tools (lszdev, chzdev), alongside ordinary Linux administration[8].

Exercise 9.1. Add a guest

Write a directory entry for a new Linux guest LINUX02 with 2 GB initial and 4 GB maximum storage, two virtual CPUs, a 10016-cylinder minidisk at virtual address 0100 on volume LXVOL3, and a NIC at 0600 on VSWITCH1. Which CP command starts it without anyone logging on?

Show solution

Start it with XAUTOLOG LINUX02, which logs the guest on disconnected and runs its IPL[19,20]. The guest also needs authority to couple to the virtual switch, granted with SET VSWITCH VSWITCH1 GRANT LINUX02 (and the matching MODIFY VSWITCH statement in SYSTEM CONFIG to make it permanent)[19,20].

10. Process and task management

10.1 z/OS dispatchable units

Within an address space, z/OS dispatches two kinds of work. A task, represented by a task control block (TCB), is the normal unit of work for programs; tasks can create subtasks with the ATTACH macro. A service request block (SRB) represents a short, high-priority system routine that can run in any address space and cannot be interrupted in the same way as a task[3,30]. The dispatcher chooses among ready TCBs and SRBs according to priorities set by the Workload Manager[15,32].

An event control block (ECB) is a fullword that one unit of work WAITs on and another POSTs; it is the basic z/OS synchronization primitive. Serialization of shared resources across tasks and systems uses ENQ/DEQ, managed sysplex-wide by global resource serialization (GRS)[29,30]. (The z/OS ECB is unrelated to z/TPF's entry control block of section 6.)

10.2 Workload Manager

Workload Manager (WLM) lets an installation state business goals instead of fixed priorities. Work is classified into service classes, each with a goal (average response time, percentile response time, execution velocity, or discretionary) and an importance from 1 (highest) to 5. WLM continuously adjusts dispatching priority, storage and I/O priority to meet the most important goals first[32].

10.3 z/VM and Linux

The z/VM CP scheduler moves virtual machines between a dispatch list (allowed to run) and an eligible list (waiting for resources), and divides processor time according to each guest's SHARE setting, either relative or absolute[33]. For example, SET SHARE LINUX01 RELATIVE 200 gives that guest twice the default relative share of 100[20,33]. Inside a Linux guest, ordinary Linux process scheduling applies[8].

Exercise 10.1. Goals versus priorities

A night batch job is assigned to a velocity-30, importance-3 class. During the day it competes with CICS (importance 1). What does WLM do when CICS is missing its goal, and why is that better than giving CICS a fixed higher priority?

Show solution

WLM takes resources from less important work that is meeting or exceeding its goal (here, the batch) and gives them to the importance-1 work that is missing its goal, adjusting dispatching priority and other controls[32]. With fixed priorities, CICS would always win even when it is already comfortably meeting its target, starving batch unnecessarily; goal-based management only intervenes as much as needed to meet stated business objectives[32].

11. Memory management

Mainframe operating systems use the hardware's dynamic address translation (DAT) to map virtual to real storage in 4 KB pages, with large pages also available[2,34].

11.1 z/OS virtual storage map

Each z/OS address space has a 64-bit (16 exabyte) virtual range. Historical boundaries remain significant because of addressing modes: the line at 16 MB (the limit of 24-bit addressing) and the bar at 2 GB (the limit of 31-bit addressing). Below the bar, the address space contains private areas for the job and common areas shared by all address spaces, such as the nucleus, the system queue area (SQA), the common service area (CSA) and the link pack area (LPA)[3,15]. Storage above the bar is obtained in large chunks called memory objects with the IARV64 service, and the amount a job may use is limited by MEMLIMIT[34].

11.2 Real and auxiliary storage

The Real Storage Manager (RSM) allocates real storage frames, and the Auxiliary Storage Manager (ASM) moves pages to and from page data sets when real storage is overcommitted[15]. Page data sets are named at IPL by the PAGE= parameter (Listing 13) and their use is displayed with D ASM[17,27].

REGION limits storage below the bar (0M requests all available, subject to installation exits), while MEMLIMIT limits storage above the bar[16,34].

11.3 z/VM and Linux

z/VM itself manages guest memory with demand paging, so guest storage can exceed real storage; CP pages guest storage to CP-owned paging volumes[19,33]. Guest memory sizing is therefore a performance trade-off: an oversized Linux guest fills its memory with page cache, which z/VM must then back with real or paged storage[4,23]. Linux on IBM Z offers cooperative memory management (cmm) so that z/VM can reclaim unused guest pages[8].

Exercise 11.1. Addressing modes

A legacy program runs AMODE 24. Can it address a buffer obtained above the 16 MB line? What about a 31-bit program and a memory object above the bar?

Show solution

No: 24-bit addressing reaches only the first 16 MB, so an AMODE 24 program cannot address storage above the line without switching modes. A 31-bit program reaches up to 2 GB, so it cannot address a memory object above the bar; it must run in AMODE 64 (or use 64-bit instructions in a mode-switching routine)[2,3,34].

12. Job scheduling

12.1 Job entry subsystems

On z/OS, a Job Entry Subsystem receives jobs, queues them by class and priority, selects them for execution in initiators, and spools their output[3]. JES2 is IBM's strategic JES. IBM announced that the z/OS release after 2.4 (z/OS 2.5) would be the last to include JES3, and JES3 technology was transferred to Phoenix Software International for a vendor-supported successor[35].

A job's CLASS parameter determines which initiators can run it; each initiator is configured to serve one or more classes[16,18]. Operators manage initiators and queues with JES2 commands.

12.2 Dependencies inside and between jobs

Within a job, steps run in order, and COND or IF/THEN/ELSE/ENDIF decide whether a step runs (Listing 1)[16]. Dependencies between jobs, calendars and time triggers are usually handled by a workload automation product (IBM's offering, originally Tivoli Workload Scheduler for z/OS, is now IBM Z Workload Scheduler) that submits JCL when its predecessors finish[3]. JES2 can also express simple ordering itself: JOBGROUP statements define a group of jobs and their dependencies, and TYPRUN=HOLD keeps a job queued until an operator or program releases it[16].

12.3 Other systems

z/VSE uses VSE/POWER queues and partition classes in a similar way (Listing 8)[9]. Under z/VM, CMS batch facilities and guest automation (for example AUTOLOG1's PROFILE EXEC) start work, and Linux guests use standard Linux schedulers such as cron and systemd timers[8,19].

Exercise 12.1. Restart from the failing step

A five-step job (STEP1 to STEP5) abended in STEP4. Steps 1 to 3 are expensive and their outputs are cataloged. How do you rerun from STEP4 only, and what JCL must you check first?

Show solution

Add RESTART=STEP4 to the JOB statement and resubmit; the system skips the earlier steps[16]. Before rerunning, check every DD in steps 4 and 5 that uses DISP=NEW: data sets partly created by the failed step may still exist (or be cataloged), and you must delete them or change the disposition. Also check that any backward references or IF tests to steps 1 to 3 still make sense, since those steps will not run[16].

14. System recovery and maintenance

14.1 Recovery architecture

Reliability, availability and serviceability (RAS) are designed across hardware and software. On the hardware side, IBM mainframes detect and recover from errors through mechanisms such as instruction retry and spare processors, much of it transparent to the operating system[40]. In z/OS, the Recovery Termination Manager (RTM) gives control to recovery routines when an error occurs: programs establish ESTAE-type routines (for tasks) or functional recovery routines (FRRs, for system code) that can clean up, record diagnostic data and either retry or let termination continue[15,30].

At sysplex level, the Automatic Restart Manager (ARM) restarts registered subsystems after failure, either on the same system or another system in the sysplex, and the Cross-System Coupling Facility (XCF) detects failed members[29].

14.2 Dumps

z/OS has several dump types: SVC dumps (taken by the system or by operator command), transaction and SYSMDUMP dumps of a single address space, and the stand-alone dump (SADMP), which is IPLed when the system itself is no longer usable[38].

14.3 Software maintenance with SMP/E

z/OS software is installed and serviced with SMP/E (System Modification Program/Extended). Its key commands are RECEIVE (bring SYSMODs, such as PTFs, and HOLDDATA into the global zone), APPLY (install them into the target libraries), ACCEPT (make them permanent in the distribution libraries) and RESTORE (remove an applied but not accepted SYSMOD)[41]. Running APPLY CHECK first reports what would happen without changing anything[41].

Maintenance is applied to an alternate copy of the system residence volumes and activated at the next IPL, so a failing change can be backed out by IPLing the previous set[15,41]. BYPASS(HOLDSYSTEM) should only be used after the reported system holds (actions such as an IPL or a PARMLIB change) have been reviewed[41].

14.4 z/VM and Linux

z/VM service is applied with the SERVICE and PUT2PROD commands, and in an SSI cluster members can be serviced one at a time while guests are moved away with live guest relocation[4]. Linux guests are patched with the distribution's package manager; if a guest fails to boot, an administrator can IPL a rescue system or a previous kernel through zipl menu entries or re-IPL settings[8].

Exercise 14.1. Planning a PTF

A PTF arrives with ++HOLD ... SYSTEM REASON(IPL). Describe a safe end-to-end process to install it on a production z/OS system.

Show solution
  1. RECEIVE the PTF and current HOLDDATA into the global zone[41].
  2. Run APPLY ... CHECK against a target zone that represents a clone of the production SYSRES set, and read the hold reasons and any missing requisites[41].
  3. APPLY for real into the clone, bypassing the IPL hold only because you plan an IPL[41].
  4. IPL a test system from the clone and verify; then schedule an IPL of production from it, keeping the old SYSRES available for fallback[15].
  5. After a period of stable running, ACCEPT the PTF into the distribution libraries; before that, it can still be removed with RESTORE[41].

These exercises combine several sections. Try them before opening the solutions.

Exercise 15.1. Choose the operating system

Match each workload to the most suitable environment and justify briefly: (a) a payments switch processing tens of thousands of short authorizations per second; (b) consolidating 300 lightly used Linux web servers; (c) a bank's core COBOL batch and CICS applications with DB2; (d) a small installation's long-standing VSE batch, now needing a supported platform.

Show solution

(a) z/TPF, designed for very high message rates with short-lived Entries[11]. (b) Linux guests under z/VM, which shares real resources among many virtual machines[4,7]. (c) z/OS, with JES batch, CICS, WLM goal management and sysplex availability[3,32]. (d) VSEn from 21st Century Software, since IBM z/VSE 6.2 is out of service, or a migration to z/OS[10,24].

Exercise 15.2. Trace an IPL problem

After a PARMLIB change, a z/OS system stops during NIP with a message that page data set PAGE.SYS1.LOCAL2 cannot be found. What happened, and how do you recover without editing PARMLIB from another system?

Show solution

The PAGE= parameter in the active IEASYSxx names a page data set that is not cataloged or not on an online volume[27]. Re-IPL with an IMSI character that makes the system prompt for system parameters, then override at the prompt, for example by specifying the earlier IEASYSxx suffix with SYSP= or by giving a corrected PAGE= value[27,28]. Afterwards fix the member and confirm with D ASM and D IPLINFO[17].

Exercise 15.3. Write a REXX health snapshot

Using TSO/E REXX, write an exec that lists the data sets that begin with a given high-level qualifier and prints the space each one uses, flagging any more than 90% full.

Show solution

OUTTRAP captures the output of a TSO command in a stem variable, and LISTDSI returns allocated and used space in SYSALLOC and SYSUSED (in the units reported in SYSUNITS)[31]. For PDSE and some other data set types SYSUSED may not be available, which the test for an empty value handles[31].

Exercise 15.4. Virtualization theory

Popek and Goldberg's condition says an architecture is efficiently virtualizable if its sensitive instructions are a subset of its privileged instructions. Why does that matter for z/VM, and what did SIE add?

Show solution

If every instruction that could reveal or change machine state traps when executed in problem state, a control program can run a guest operating system in problem state and emulate each trapped instruction, giving equivalence, resource control and efficiency[13]. System/370 largely met this, which is why CP-67 and VM/370 were possible[6,12]. SIE moved much of the work into hardware: the guest runs under interpretive execution and leaves SIE only for events the host must handle, greatly reducing overhead[14].

Exercise 15.5. Linux guest storage

A Linux guest defined with 16 GB shows only 2 GB of application memory use but 13 GB of page cache. z/VM paging is high. What would you change?

Show solution

Reduce the guest's defined storage closer to its working set (for example 4 GB) so that Linux does not fill memory with cache that z/VM must back, and consider enabling cooperative memory management so z/VM can reclaim unused pages; monitor the result with the Performance Toolkit and INDICATE[8,23,33].
