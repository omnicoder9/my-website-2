1. Why transaction processing matters on the mainframe

A transaction, in the computing sense, is a collection of operations on shared state that is treated as one indivisible unit: either all of its effects become permanent, or none do.1,2 Gray described the concept in 1981 as an agreement between the application and the system that the state changes it makes are atomic, consistent, durable and isolated from concurrent work; the acronym ACID for these four properties was coined by Haerder and Reuter two years later.1,3 Business processes are naturally transactional. Moving money between two accounts, booking a seat, or recording an insurance claim each change several records that must stay in agreement, and each must survive a power failure that happens a millisecond after the customer is told "done".

The mainframe's position in this work dates from its earliest commercial software. IBM's Information Management System (IMS) grew out of a 1966 project with North American Rockwell and Caterpillar to manage the bill of materials for the Apollo programme, and its transaction manager became generally available in 1969.4 The Customer Information Control System (CICS) was announced in 1968 as a product to let utility companies give terminal users on-line access to customer records, and it became IBM's general-purpose transaction monitor.5 Both products are still developed and are the main online transaction managers on z/OS today; IBM MQ, introduced in the 1990s as MQSeries, provides the message-oriented middleware that connects them to each other and to the rest of the enterprise.6,7

The term middleware refers to the software layer between the operating system and the application that supplies services the application would otherwise have to build itself: communication, transaction coordination, security, naming, and scheduling.8 CICS, IMS TM and MQ are all middleware in this sense. A COBOL programmer writing a CICS program never opens a socket, schedules a thread, or writes a recovery log; the transaction manager does these, and the program only states where a unit of work begins and ends.

The operating system services that CICS and IMS depend on (address spaces, TCBs, the system logger, WLM) are covered in the mainframe operating systems article; the batch side of the platform is covered in the JCL article; and the database-manager view of ACID, locking protocols and Db2/IMS DB internals is the subject of the companion databases article. 2. Transaction processing systems and OLTP

2.1 What a TP system is

Bernstein and Newcomer define a transaction processing system as one that provides the tools to ease or automate the programming, execution and administration of transaction processing applications.8 In practice a TP system consists of three cooperating parts:2,8

  • A TP monitor (transaction manager). It receives requests, starts a task for each one, runs the right application program, coordinates commit and recovery, and returns the reply. CICS and IMS TM are TP monitors.
  • One or more resource managers. These own recoverable data: Db2, IMS DB, VSAM files under CICS file control, and MQ queues. Each keeps its own log and can undo or redo its own changes.
  • Communications and presentation. Terminal networks (historically SNA/VTAM and 3270 displays), and today TCP/IP, HTTP, web services, IMS Connect, the CICS Transaction Gateway and z/OS Connect for REST APIs.9,10

The X/Open Distributed Transaction Processing (DTP) model formalizes this division into an application program (AP), resource managers (RMs) and a transaction manager (TM), with standard interfaces between them: the TX interface between AP and TM, and the XA interface between TM and RMs.11,12 On z/OS, CICS and IMS act as transaction managers for their own resources, and z/OS Resource Recovery Services (RRS) acts as a system-wide syncpoint manager that any authorized resource manager can register with.13

2.2 Online transaction processing (OLTP)

OLTP is the class of workloads in which many users submit short, predefined, mostly update-heavy requests and expect a reply within a second or so. Gray and Reuter characterize OLTP by high transaction rates, a large number of concurrent users, short transactions that each touch a small amount of data, strict response-time targets, and a requirement for continuous availability.2 It contrasts with batch processing, which runs long jobs over large volumes of data without a user waiting, and with analytical processing (OLAP), which runs long read-mostly queries.6

2.3 Conversational and pseudo-conversational design

A business conversation (for example, "enter account number, see balance, enter amount, confirm") spans several screens and therefore several user think-times of seconds or minutes. A conversational program keeps a task, its storage, and any locks it holds alive throughout the conversation. A pseudo-conversational program instead ends its task after sending each screen, saving the state it needs, and a new task is started when the user responds.5,9 Pseudo-conversational design is the norm in CICS because it frees all resources during user think-time, which is what lets one region serve thousands of terminals.5 IMS has the equivalent pattern: a non-conversational transaction processes one input message and ends, while an IMS conversational transaction keeps state between messages in a scratchpad area (SPA) managed by IMS, not in a held task.4

Consequence for integrity. Because each screen of a pseudo-conversation is a separate transaction, no locks are held between screens. Two users can read the same record on screen 1 and both try to update it on screen 2. The program must detect this itself, typically by saving a version number or timestamp with the screen state and checking it before updating (Section 5.3).5,8

3. The transaction lifecycle

Every OLTP request passes through the same sequence of stages, whatever the product. The names below are generic; Table 2 maps them to CICS and IMS terms.2,8

  1. Arrival. A request arrives on a terminal session, a TCP/IP socket, an HTTP connection, or an MQ queue.
  2. Identification and security. The transaction manager identifies which transaction is requested (a CICS 1–4 character transaction identifier, or an IMS transaction code of up to 8 characters) and checks that the user may run it.9,10
  3. Scheduling. The request is queued and dispatched when capacity allows. CICS attaches a task; IMS places the message on a transaction queue and schedules the program into a dependent region.4,9
  4. Begin unit of work. A unit of work (UOW, also called a logical unit of work or unit of recovery) begins implicitly at the start of the task or after the previous syncpoint.9,13
  5. Execution. The application reads and updates recoverable resources. Each resource manager writes undo/redo information to its log and acquires locks.
  6. Syncpoint. The application, or the end of the task, requests commit. The transaction manager runs the commit protocol (one-phase if only one resource manager is involved, two-phase otherwise). Alternatively, the application or a failure causes rollback.
  7. Reply and release. Output is sent, locks are released, storage is freed, and the task ends or waits for the next message.

4. Commit and rollback

4.1 The commit point and write-ahead logging

The instant at which a unit of work becomes permanent is its commit point. Before that instant, a failure must leave no trace of the UOW; after it, a failure must not lose any part of it. Transaction managers achieve this with a log: before any change to a recoverable resource is made permanent, a record describing how to undo it is written to the log (the write-ahead logging rule), and the UOW commits at the moment its commit record is safely on non-volatile storage.2,3 After a failure, the recovery process reads the log, redoes committed work that may not have reached the data, and undoes uncommitted work.3

In CICS the recovery manager domain coordinates syncpoints, and recoverable changes to CICS-owned resources (recoverable VSAM files, recoverable temporary storage and transient data queues) are recorded on the system log, DFHLOG, which is a log stream managed by the z/OS system logger.9,16 IMS records changes in its online log data sets (OLDS), with the write-ahead data set (WADS) used to harden log records quickly before they are written to the OLDS.4,10 Db2 and MQ each keep their own logs and take part in the CICS or IMS commit as resource managers.7,9

4.2 Commit in CICS

A CICS task begins a unit of work when it starts. The UOW ends, and a new one begins, at each EXEC CICS SYNCPOINT command. If the program issues no syncpoint, CICS takes one automatically when the task ends normally.16,17 Rollback is requested with EXEC CICS SYNCPOINT ROLLBACK. If the task abends, CICS performs dynamic transaction backout, undoing all changes to recoverable resources made since the last syncpoint.16

Which resources are protected depends on how they are defined, not on the program. A VSAM file is recoverable only if its CICS FILE definition (or, for VSAM record-level sharing, its ICF catalog entry) says so; a temporary storage queue is recoverable only if its TSMODEL marks it recoverable; a transient data queue only if its definition does.9,16 Db2 updates made through the CICS–Db2 attachment and MQ operations performed with the syncpoint option are always included in the CICS UOW.7,9

A common surprise. Writing to a non-recoverable resource (for example, a non-recoverable TS queue, or an MQ message put with MQPMO_NO_SYNCPOINT) is not undone by SYNCPOINT ROLLBACK. If such a write announces that something happened, it can announce an event that was later backed out.7,16

4.3 Commit in IMS

In an IMS message processing program (MPP), the unit of work normally corresponds to the processing of one input message. For a transaction defined with MODE=SNGL, IMS takes a sync point each time the program issues a GU call to the I/O PCB to retrieve the next message; for MODE=MULT, sync points occur only when the program ends or issues a checkpoint call.4,18 At the sync point IMS commits database changes, releases locks, and sends the output messages that the program inserted; output messages are not sent before commit, so a backed-out transaction never sends a reply that claims success.4

IMS provides several rollback calls that differ in what happens next:18

  • ROLB backs out database changes and cancels output messages since the last sync point, then returns control to the program. If the program supplies an I/O area, IMS returns the first segment of the current input message, so the program can, for example, send an error reply.
  • ROLL backs out the same changes, discards the input message, and terminates the program with user abend code U778.
  • ROLS backs out to the last sync point or, with a token, to an intermediate point set by SETS; it can also be used to have IMS return a status code instead of abending when a database is unavailable.

Batch message processing programs (BMPs), which run batch-style work against online databases, commit with the CHKP (checkpoint) call, and should do so frequently so that they do not hold locks that block online transactions; symbolic checkpoints (CHKP with XRST) also let a failed BMP restart from its last checkpoint.4,18

4.4 Atomicity across several resource managers

When a single UOW updates a VSAM file, a Db2 table and an MQ queue, the transaction manager must make all three commit or all three back out. If only one resource manager has been changed, it can simply be told to commit (a one-phase commit). Otherwise the transaction manager uses the two-phase commit protocol described in Section 11, in which it acts as the coordinator and each resource manager as a participant.2,16 An important optimization: a resource manager that was only read in the UOW can vote "read-only" in phase 1 and be left out of phase 2.2,19

5. Transaction isolation from the transaction manager's view

5.1 Isolation levels in brief

Isolation is the property that concurrent transactions do not see each other's intermediate states. The ANSI SQL standard defines isolation levels by the anomalies (dirty read, non-repeatable read, phantom) each level allows; Berenson and colleagues showed that these definitions are incomplete and added others, such as lost update and write skew.20 Db2 for z/OS implements four isolation levels, uncommitted read (UR), cursor stability (CS), read stability (RS) and repeatable read (RR), selected at bind time or per statement.21 The mechanics of locking that implement these levels belong to the database manager and are covered in the companion databases article. This section is about what the transaction manager and the application must do.

5.2 Isolation boundaries are commit boundaries

Locks taken by Db2, IMS DB, or CICS file control on recoverable resources are held until the end of the unit of work, in other words until the next syncpoint.4,9,21 Two consequences follow:

  • A UOW that runs long, or that waits for anything (a user, a remote system, an MQ reply), holds its locks the whole time. This is why OLTP transactions are kept short and why pseudo-conversational design releases everything between screens.
  • Issuing a syncpoint in the middle of a task gives up isolation for everything before it. Splitting a UOW for performance is only safe if the parts are independently consistent.

CICS adds its own serialization primitive for resources that are not under a database manager. EXEC CICS ENQ RESOURCE(...) obtains an exclusive lock on an arbitrary name; by default it is held until the end of the unit of work (MAXLIFETIME(UOW)), or it can be held until task end with MAXLIFETIME(TASK), and released explicitly with DEQ.17 IMS similarly isolates updates through program isolation, which holds database locks for updated segments until the sync point so that other programs cannot see uncommitted changes.4

5.3 Lost updates in pseudo-conversations: optimistic concurrency

Because no locks survive between the screens of a pseudo-conversation, the standard defence against lost updates is optimistic concurrency control: remember a version of the record when it is shown, and update only if the version has not changed.8 In Db2 this is often an update timestamp or a version column; with VSAM it is a field in the record. The check and the update must be in the same UOW so that they are atomic.

5.4 Deadlocks and timeouts

When two UOWs each wait for a lock the other holds, neither can proceed. Database managers detect deadlocks and choose a victim; Db2 for z/OS, for example, returns SQLCODE −911 (with the UOW rolled back) or −913 (statement failed, rollback left to the application).21 For locks managed outside a database (for example CICS ENQ, or VSAM record locks in non-RLS mode), CICS relies on the transaction's deadlock timeout, DTIMOUT: a task that waits longer than that interval is purged and abends with code AKCS, which triggers dynamic backout.9 The application-level defence is to acquire resources in a consistent order, such as always reading the lower account number first in a funds transfer (Listing 5 does this).2

6. CICS Transaction Server

6.1 Architecture

CICS Transaction Server for z/OS runs as one or more regions, each a z/OS address space that acts as a small operating system for transactions: it has its own dispatcher, storage manager, loader, security interface, and recovery manager.5,9 Inside a region, each request runs as a task, a lightweight unit of work that CICS dispatches on a small number of z/OS TCBs. Historically all application code ran on a single quasi-reentrant (QR) TCB, which serialized access to shared storage. Programs defined as threadsafe can run on open TCBs (for example the L8 and L9 TCBs used by the Db2 and MQ adapters) concurrently with other tasks, which avoids TCB switches and lets one region use more than one processor.9,22 Java programs run in JVM servers inside the region.9

Large installations split work across many regions connected by multiregion operation (MRO) within a z/OS image or sysplex, and by intersystem communication (ISC) over IPIC (TCP/IP) or LU 6.2 to other systems.5,9 A classic topology separates terminal-owning regions (TORs), which handle the network, from application-owning regions (AORs), which run programs, and sometimes file-owning regions (FORs). CICSPlex System Manager (CICSPlex SM) manages a group of regions as one system and can route each transaction dynamically to the least-loaded AOR.9

6.2 Resources

Everything a CICS application uses is a named, defined resource: TRANSACTION, PROGRAM, FILE, TDQUEUE, TSMODEL, TRANCLASS, DB2CONN, MQCONN, URIMAP, and so on. Definitions are stored in the CICS system definition data set (CSD) and installed into the running region, or deployed in CICS bundles.9 The transaction definition names the first program to run and carries operational attributes such as the transaction class, priority, and deadlock timeout. 6.6 Recovery and restart in CICS

CICS recovery operates at three levels:5,16

  • Dynamic transaction backout undoes the changes of a single failing task, using log records the recovery manager keeps for in-flight UOWs.
  • Emergency restart after a region failure reads the system log, backs out the UOWs that were in flight when the region failed, and re-establishes in-doubt UOWs so they can be resolved with their coordinator.
  • Forward recovery rebuilds a damaged data set from a backup plus the after-images on a forward-recovery log, usually with a product such as CICS VSAM Recovery.

When a UOW cannot complete its syncpoint (for example, a remote coordinator is unreachable while the UOW is in doubt, or a data set needed for backout is unavailable), CICS shunts the UOW: it releases the task but keeps the UOW's log records and retains locks on the affected records until the problem is resolved.16 The TRANSACTION attributes WAIT, WAITTIME and ACTION control whether an in-doubt UOW waits for its coordinator or is resolved unilaterally by commit or backout after a time limit.9,16

7. IMS Transaction Manager

7.1 Architecture

IMS consists of a database manager (IMS DB) and a transaction manager (IMS TM), which can be used together or separately; IMS TM can also front-end Db2 databases.4,10 An IMS online system runs as a control region, which owns the network, the message queues and the logs, plus supporting address spaces such as DL/I separate address space (DLISAS) and the database recovery control (DBRC) region. Application programs run in dependent regions:4,23

  • Message processing programs (MPPs) run in message processing regions and process messages from the IMS message queues.
  • IMS Fast Path (IFP) programs run in IFP regions and process Fast Path messages that bypass the normal message queues through the expedited message handler, for the highest volumes and shortest response times.
  • Batch message processing programs (BMPs) are batch programs that run online, with access to IMS databases and the message queues.
  • Java message processing (JMP) and Java batch processing (JBP) regions run Java applications.

IMS TM is message-driven. Every input, from a terminal, from IMS Connect over TCP/IP, from MQ through the IMS bridge, or from another program, is a message placed on a queue for its transaction code. IMS schedules a program into a dependent region whose class matches, and the program loops reading messages until the queue is empty.4 Messages can be inserted to the originating terminal (through the I/O PCB) or to another destination (through an alternate PCB), including another transaction, which is how IMS programs pass work to each other asynchronously.18

Access from outside the IMS network is through Open Transaction Manager Access (OTMA), a protocol over the z/OS cross-system coupling facility (XCF) used by IMS Connect, the MQ IMS bridge and other clients.10 OTMA supports two commit modes: commit-then-send (commit mode 0), in which IMS commits and then delivers the output asynchronously, and send-then-commit (commit mode 1), in which IMS sends the reply before commit and can use synchronization level SYNCPT so the client takes part in the commit decision through RRS.10

7.3 Conversations, shared queues and Fast Path

An IMS conversational transaction receives a scratchpad area (SPA) as the first segment of each input message; the program updates and reinserts it, and IMS keeps it between steps of the conversation, so no region or lock is held while the user thinks.4,18 In a Parallel Sysplex, IMS shared queues place the message queues in coupling facility list structures managed by the Common Queue Server (CQS), so any IMS in the group can process any message; with IMS DB or Db2 data sharing this gives workload balancing and continued service if one IMS fails.10,24 Fast Path data entry databases (DEDBs) and the expedited message handler give IFP programs the shortest path through IMS, and are used for the highest-volume work such as teller and card transactions.4

8. Message queues and IBM MQ

8.1 Concepts

Message-oriented middleware lets programs communicate by putting messages on queues and getting messages from queues, rather than by calling each other directly. The sender and receiver need not run at the same time, need not know each other's location, and need not run at the same speed.7,25 IBM MQ implements this with queue managers, which own queues and move messages between them over channels. A message put to a remote queue is placed on a transmission queue and sent by a message channel agent to the target queue manager.7 On z/OS a queue manager runs as its own subsystem with a master address space and a channel initiator address space.7

MQ provides the guarantee that makes it suitable for transaction processing: a persistent message put inside a unit of work is delivered once and only once, provided both ends use syncpoint control. The message becomes visible to other applications only when the putting UOW commits, and it is removed from the queue only when the getting UOW commits; if the getter backs out, the message is restored to the queue and its backout count is increased.7 Non-persistent messages are faster but can be lost if a queue manager restarts.7

8.4 A batch consumer with poison-message handling

Listing 9 is a C program that drains a queue in batch, processing each message in its own UOW and moving messages that have failed three times to the backout queue. The pattern (get under syncpoint, process, commit or back out, check backout count) applies in any environment.7

#include <cmqc.h>
#include <string.h>
#include <stdio.h>

#define BOTHRESH 3
extern int process(const char *msg, MQLONG len);   /* returns 0 if OK */

int drain(MQHCONN hc, MQHOBJ hReq, MQHOBJ hBack)
{
    MQMD   md  = {MQMD_DEFAULT};
    MQGMO  gmo = {MQGMO_DEFAULT};
    MQPMO  pmo = {MQPMO_DEFAULT};
    MQLONG cc, rc, len;
    char   buf[4096];

    gmo.Options = MQGMO_WAIT | MQGMO_SYNCPOINT
                | MQGMO_FAIL_IF_QUIESCING | MQGMO_CONVERT;
    gmo.WaitInterval = 30000;                  /* 30 seconds, then stop */
    pmo.Options = MQPMO_SYNCPOINT | MQPMO_FAIL_IF_QUIESCING;

    for (;;) {
        memcpy(md.MsgId,    MQMI_NONE, sizeof md.MsgId);   /* get next msg */
        memcpy(md.CorrelId, MQCI_NONE, sizeof md.CorrelId);
        md.Encoding = MQENC_NATIVE;
        md.CodedCharSetId = MQCCSI_Q_MGR;

        MQGET(hc, hReq, &md, &gmo, sizeof buf, buf, &len, &cc, &rc);
        if (rc == MQRC_NO_MSG_AVAILABLE) return 0;        /* queue empty */
        if (cc == MQCC_FAILED) { fprintf(stderr, "MQGET %d\n", (int)rc); return 8; }

        if (md.BackoutCount >= BOTHRESH) {
            /* Poison message: move it aside in the same UOW */
            MQPUT(hc, hBack, &md, &pmo, len, buf, &cc, &rc);
            if (cc == MQCC_OK) MQCMIT(hc, &cc, &rc);
            else               MQBACK(hc, &cc, &rc);
            continue;
        }
        if (process(buf, len) == 0)
            MQCMIT(hc, &cc, &rc);      /* message removed for good   */
        else
            MQBACK(hc, &cc, &rc);      /* message back on the queue, */
    }                                  /* BackoutCount incremented   */
}

8.5 Bridges and shared queues

The MQ–CICS bridge and the MQ–IMS bridge let a message on a queue run an existing CICS program or IMS transaction without changing the program; the bridge gets the message, invokes the transaction, and puts the output on the reply-to queue.7,10 On z/OS, MQ shared queues store messages in coupling facility list structures so that every queue manager in a queue-sharing group can put and get them; if one queue manager fails, the others continue processing its messages, and the work load balances itself because whichever server is free gets the next message.7,24

9. Asynchronous processing

9.1 Why decouple

In a synchronous design the caller waits while the callee works, so the slowest component sets the response time for everyone, and an outage anywhere stops the whole chain. Asynchronous designs let the requester hand off work and continue: the request is captured reliably (often in the same UOW as the business change that caused it) and processed later, possibly elsewhere.8,25 Asynchronous processing also smooths load peaks, because a queue absorbs a burst that the servers then work through at their own pace.7 The cost is that the end-to-end process is no longer one atomic transaction: it becomes a chain of transactions linked by reliable messages, and the design must handle the intermediate states.8,26

9.3 Asynchronous options in IMS and MQ

An IMS program can pass work to another transaction by inserting a message to an alternate PCB whose destination is a transaction code; the message is placed on that transaction's queue at sync point, so the hand-off is atomic with the program's database updates.18 With MQ, the same effect is achieved by putting a persistent message under syncpoint; triggering (Listing 7) or a long-running listener then processes it.7

9.4 Designing for reliable asynchrony

Messaging literature describes a set of patterns that keep asynchronous systems correct:25

  • Request–reply with correlation. The requester sets a reply-to queue; the responder copies the request's MsgId into the reply's CorrelId (the MQ report option MQRO_COPY_MSG_ID_TO_CORREL_ID describes this convention), and the requester gets the reply by CorrelId.7,25
  • Idempotent receiver. If a message can ever be delivered twice (for example, a non-transactional sender that retries), the receiver records the IDs of processed messages in the same UOW as its updates and ignores duplicates.25
  • Dead-letter and backout queues. Messages that cannot be delivered go to the queue manager's dead-letter queue; messages that repeatedly fail processing go to a backout queue for investigation.7
  • Compensation. When a multi-step process cannot be one ACID transaction, each step is a local transaction with a defined compensating transaction that semantically undoes it; this is the saga model of Garcia-Molina and Salem.26

10.2 The X/Open DTP model and XA

The X/Open DTP reference model separates the application, the resource managers and the transaction manager, and the XA specification defines the calls a TM uses to drive an RM through a two-phase commit: xa_start and xa_end to associate work with a global transaction identifier (XID), xa_prepare, xa_commit and xa_rollback for the protocol, and xa_recover to list in-doubt transactions after a failure.11,12 Java transaction managers expose the same model through JTA, and products such as the CICS Transaction Gateway and Db2 accept XA coordination.9

10.3 z/OS Resource Recovery Services

RRS is a z/OS component that acts as a system-level syncpoint manager. Resource managers (Db2, IMS, MQ, CICS, WebSphere Application Server for z/OS, and others) register with RRS; applications or work managers then express units of recovery to RRS, which drives two-phase commit across all registered resource managers and logs its decisions in its own log streams.13 Applications that are not running under CICS or IMS use the RRS callable services SRRCMIT (commit) and SRRBACK (back out) to end a unit of recovery.13 RRS also participates in cascaded transactions, in which a resource manager is itself the coordinator for further participants.13

10.4 When not to use a distributed transaction

Two-phase commit holds locks across the network for at least two message round trips, and a participant that has voted yes cannot release its locks until it learns the outcome. If the coordinator becomes unreachable, participants stay in doubt with their locks held (Section 11.4).2,8 For processes that cross organizational boundaries, involve slow or unreliable partners, or last longer than a few seconds, designers usually prefer local transactions linked by reliable messages and compensating transactions (Section 9.4).25,26

11. Two-phase commit

11.1 The basic protocol

The two-phase commit (2PC) protocol was described by Gray in his 1978 notes on database operating systems.28 One party, the coordinator, decides the outcome; the others, participants, obey it.2,28

  1. Phase 1 (prepare / vote). The coordinator asks every participant to prepare. A participant that can guarantee it will be able to commit, whatever happens next, forces a prepared record to its log and votes yes. From that moment it is in doubt: it may not commit or back out on its own. A participant that cannot commit votes no and backs out.
  2. Decision. If all votes are yes, the coordinator forces a commit record to its log. This write is the commit point of the whole distributed transaction. Otherwise the decision is backout.
  3. Phase 2 (commit / abort). The coordinator sends the decision to each participant, which applies it, releases its locks, and acknowledges. When all acknowledgements arrive, the coordinator writes an end record and can forget the transaction.

11.2 Optimizations

The basic protocol costs two message round trips and several forced log writes per participant. Mohan, Lindsay and Obermarck analysed variants in the R* distributed database:19

  • Presumed abort. If the coordinator has no record of a transaction, it presumes it aborted. The coordinator therefore need not force-write an abort record, and participants need not acknowledge an abort.
  • Presumed commit. The reverse presumption, which saves acknowledgements for commits at the cost of a forced record at the start of the protocol.
  • Read-only participants. A participant that made no updates votes read-only, writes nothing, and is excluded from phase 2.

Two further optimizations are widely used. With single-phase commit, if only one recoverable resource manager was updated, the coordinator just tells it to commit. With the last agent optimization, the coordinator prepares all participants except one, then passes the decision to that last agent, which commits and so effectively becomes the coordinator; this saves a round trip and is used by CICS for links to other systems.2,16

11.3 A runnable simulation

Listing 11 models 2PC with presumed abort. It is a teaching model, not production code: it shows the state each participant is in and why the coordinator's log alone is enough to resolve in-doubt participants after a crash.2,19

"""Two-phase commit with presumed abort: a teaching simulation."""

class Participant:
    def __init__(self, name, will_vote_yes=True, read_only=False):
        self.name, self.will_vote_yes, self.read_only = name, will_vote_yes, read_only
        self.log, self.state = [], "ACTIVE"

    def prepare(self, uow):
        if self.read_only:                 # nothing to commit: vote and forget
            self.state = "DONE"
            return "READ_ONLY"
        if not self.will_vote_yes:         # e.g. constraint failed, lock timeout
            self.log.append(("ABORT", uow)); self.state = "ABORTED"
            return "NO"
        self.log.append(("PREPARED", uow))  # forced to disk before voting yes
        self.state = "IN_DOUBT"            # may no longer decide on its own
        return "YES"

    def decide(self, uow, outcome):
        if self.state != "IN_DOUBT":
            return
        self.log.append((outcome, uow)); self.state = outcome

class Coordinator:
    def __init__(self, participants):
        self.participants, self.log = participants, []

    def commit(self, uow, crash_after_votes=False):
        votes = {p.name: p.prepare(uow) for p in self.participants}       # phase 1
        print(f"{uow}: votes {votes}")
        if all(v in ("YES", "READ_ONLY") for v in votes.values()):
            self.log.append(("COMMIT", uow))   # the commit point: force-write
            outcome = "COMMITTED"
        else:
            outcome = "ABORTED"                 # presumed abort: no forced record
        if crash_after_votes:
            print(f"{uow}: coordinator crashed before phase 2")
            return None
        for p in self.participants:                                        # phase 2
            if votes[p.name] == "YES":
                p.decide(uow, outcome)
        self.log.append(("END", uow))
        return outcome

    def recover(self, uow):
        """After restart: a COMMIT record means commit; no record means abort."""
        outcome = "COMMITTED" if ("COMMIT", uow) in self.log else "ABORTED"
        for p in self.participants:
            p.decide(uow, outcome)
        return outcome

if __name__ == "__main__":
    db2, mq, vsam = Participant("DB2"), Participant("MQ"), Participant("VSAM", read_only=True)
    c = Coordinator([db2, mq, vsam])
    print("UOW1 ->", c.commit("UOW1"))

    db2, mq = Participant("DB2"), Participant("MQ", will_vote_yes=False)
    c = Coordinator([db2, mq])
    print("UOW2 ->", c.commit("UOW2"), "| DB2 state:", db2.state)

    db2, mq = Participant("DB2"), Participant("MQ")
    c = Coordinator([db2, mq])
    c.commit("UOW3", crash_after_votes=True)
    print("UOW3 participants:", db2.state, mq.state)
    print("UOW3 after recovery ->", c.recover("UOW3"), "|", db2.state, mq.state)

On restart, the coordinator finds the commit record and completes the commit. 11.4 In-doubt units of work in practice

The weakness of 2PC is the in-doubt window: a participant that has voted yes is blocked until it hears from the coordinator.2 Products give operators ways to manage this:

  • CICS shunts an in-doubt UOW, keeping locks on the records it changed (retained locks), and resolves it automatically when the link to the coordinator is restored. The TRANSACTION attributes WAIT(YES|NO), WAITTIME and ACTION(BACKOUT|COMMIT) say whether to wait and what to do if waiting is not allowed or times out; CEMT INQUIRE UOW and CEMT SET UOW let an operator inspect and force the outcome.9,16
  • A unilateral decision by a participant is called a heuristic decision. If it differs from the coordinator's decision, the result is a heuristic mixed outcome: part of the transaction committed and part backed out, and the inconsistency must be repaired by hand. CICS reports such mismatches with messages when the link is re-established.12,16
  • In the X/Open model a resource manager reports heuristic outcomes with specific XA return codes, and xa_recover lets a recovering transaction manager find its in-doubt transactions.12
Operator guidance. Forcing an in-doubt UOW to commit or back out should be a last resort, used only when the coordinator's log is lost or the delay is costing more than a possible inconsistency. Where possible, find the coordinator's decision first (from its logs or console messages) and force the participant to match it.16

12.4 Reading the numbers

A rising average response time on its own says little. Break it into components: if most time is waiting for admission to a transaction class or for MXT, the region is throttling and the fix is capacity or class limits; if it is lock waits, look for a hot record or a long UOW; if it is CPU dispatch wait, the system is short of processor at that WLM importance; if it is Db2 or I/O time, look at the database side.2,30 Queue depth tells the same story for messaging: a growing CURDEPTH with a recent LGETTIME means consumers are working but too slowly, while a growing depth with an old LGETTIME means no one is consuming at all.7

13. High-volume transaction management

13.1 Sizing with Little's law

Little's law states that in a stable system the average number of items in the system equals the arrival rate multiplied by the average time each spends in it: L = λW.33 For a TP system, the number of concurrently active transactions equals the transaction rate times the average residence time. At 3,000 transactions per second with an average in-region time of 40 ms, a CICS configuration needs about 3,000 × 0.040 = 120 concurrently active tasks, and limits such as MXT and TRANCLASS MAXACTIVE must allow for that plus headroom for peaks and for slowdowns, which raise W and therefore L.9,33

13.2 Techniques

The techniques below appear repeatedly in IBM guidance and in the literature.2,4,9,24

  • Keep UOWs short. Lock hold time is the main limit on concurrency. Do validation and reads before locking, update last, and commit promptly. In BMPs, checkpoint frequently.
  • Scale out with cloning. Run several identical AORs or IMS systems and route work among them: CICSPlex SM workload management for CICS, Sysplex Distributor and port sharing for TCP/IP clients, IMS shared queues, and MQ shared queues. Db2 data sharing, VSAM record-level sharing and IMS data sharing let every clone update the same data.7,9,24
  • Remove affinities. A transaction has an affinity if it must run in a particular region, for example because it relies on a TS queue or storage left there by a previous transaction. Affinities defeat dynamic routing and should be removed by moving the state to shared resources (shared TS, coupling facility data tables, Db2).9,24
  • Threadsafe programs. Making CICS programs threadsafe lets Db2 and MQ calls run on open TCBs without switching back to the QR TCB, which reduces CPU per transaction and removes the single-TCB bottleneck.22
  • Avoid hot spots. A single record updated by every transaction (a "next invoice number" counter, a daily total) serializes the whole system. Use the CICS named counter server in the coupling facility for unique numbers, partition totals and add them up later, or append rather than update.2,9
  • Admission control. Transaction classes, MXT and IMS scheduling limits prevent overload from turning into thrashing: past a certain concurrency, more active work only increases contention and response time.9,10
  • Defer non-essential work. Audit trails, notifications and analytics feeds can be written as protected STARTs or persistent messages and processed asynchronously, outside the critical path (Section 9).7,17
  • Short paths for the extremes. IMS Fast Path and, at the far end, z/TPF trade generality for path length when volumes are measured in many thousands of transactions per second.4,15

13.3 Availability is part of volume

For high-volume services, availability and throughput are designed together. In a Parallel Sysplex with cloned regions, shared data and shared queues, a single region, LPAR or even CPC can be taken down for maintenance or fail, and its work is absorbed by the others; with workload routing, users see at most the loss of in-flight transactions on the failed component, which are backed out and can be retried.24 The companion hardware architecture article in this series describes the coupling facility that makes this possible.

Exercise 1: Where are the commit points?

A CICS task runs this sequence against a file ORDERS defined with RECOVERY(BACKOUTONLY) and a non-recoverable TS queue. The task abends with ASRA at step 6. Which changes survive?

1. WRITE FILE('ORDERS') ... order 100
2. WRITEQ TS QUEUE('ORDLOG') ... "order 100 written"
3. EXEC CICS SYNCPOINT
4. WRITE FILE('ORDERS') ... order 101
5. WRITEQ TS QUEUE('ORDLOG') ... "order 101 written"
6. (abend ASRA)
Show solution

Order 100 survives: it was committed at step 3. Order 101 is removed by dynamic transaction backout because it is a change to a recoverable file since the last syncpoint. Both TS queue entries survive, because the queue is not recoverable. The log therefore says "order 101 written" for an order that does not exist, which is the problem described in the warning in Section 4.2. Fix it by making the TS queue recoverable (through its TSMODEL) or by writing the log record to a recoverable resource.16,17

Exercise 2: ROLB or ROLL?

An IMS MPP discovers half way through a message that a database it needs is unavailable. The business wants the user to receive a polite "try again later" reply, and the database updates already made for this message must be undone. Which call should the program use, and why not the other?

Show solution

Use ROLB. It backs out database changes and output messages since the last sync point and returns control to the program, which can then insert the error reply to the I/O PCB. ROLL would also back out, but it discards the input message and terminates the program with abend U778, so no reply could be sent.18 A related technique is the INIT call with the STATUSGA function, which tells IMS to return a status code to the program, instead of abending it, when a database is unavailable.18

Exercise 3: Sizing with Little's law

A payment service must handle a peak of 4,500 transactions per second. Measured average in-region response time is 25 ms at normal load. (a) How many tasks are active on average at peak? (b) The service is spread across 6 cloned AORs. What MAXACTIVE would you start with for the payment transaction class in each AOR if you want 50% headroom? (c) During a Db2 slowdown, response time rises to 200 ms. What happens?

Show solution

(a) L = λW = 4,500 × 0.025 = 112.5 active tasks on average.33

(b) 112.5 / 6 ≈ 19 per AOR; with 50% headroom, about 28, so MAXACTIVE(30) is a reasonable starting value, to be tuned from SMF 110 data.

(c) At 200 ms, L = 4,500 × 0.2 = 900 tasks would be needed. With MAXACTIVE(30) per AOR (180 total), the class limit is reached; new tasks queue for admission and response time grows further, but the regions are protected from storage exhaustion and the slowdown is visible as TRANCLASS waits. This is the purpose of admission control: it turns a downstream slowdown into queuing rather than a region failure.9,33

Exercise 4: The reply that never comes

A CICS program puts a request with MQPMO_SYNCPOINT, then immediately issues MQGET with MQGMO_WAIT and a 30-second wait interval for the reply, matching on CorrelId. Every call ends with reason MQRC_NO_MSG_AVAILABLE (2033) after 30 seconds, although the server is healthy. What is wrong?

Show solution

The request was put inside the task's unit of work, which has not committed, so the message is not yet visible to the server. The server cannot reply to a request it cannot see. Issue EXEC CICS SYNCPOINT after the put and before the get (or put the request with MQPMO_NO_SYNCPOINT if it need not be atomic with other work).7

Exercise 5: Two-phase commit outcomes

A coordinator uses presumed abort with participants Db2 and MQ. For each case, state the final outcome and what each participant does. (a) Db2 votes yes, MQ votes no. (b) Both vote yes; the coordinator fails before writing its commit record. (c) Both vote yes; the coordinator writes its commit record, sends COMMIT to Db2, then fails before contacting MQ.

Show solution

(a) Backout. MQ backed out when it voted no. Db2 is in doubt until it receives the abort decision, then backs out. Under presumed abort the coordinator does not need to force an abort record.19

(b) Backout. Both participants are in doubt. On restart the coordinator finds no commit record and presumes abort; when the participants ask (or the coordinator resynchronizes), they are told to back out.2,19

(c) Commit. Db2 commits. MQ stays in doubt, holding its locks, until the coordinator restarts, finds the commit record, and resends COMMIT. This is the case Listing 11 demonstrates.19

Exercise 6: A queue that never empties

Monitoring shows BANK.XFER.REQUEST with CURDEPTH 1, IPPROCS 1, and LGETTIME a fraction of a second ago, every time you look, for an hour. CPU use by transaction XFRQ is high. What is likely happening, and how should the application have prevented it?

A poison message: XFRQ gets the message, fails, backs out, and the message returns to the queue, again and again. Exercise 7: The lost address change

Two clerks open the same customer's record on a pseudo-conversational CICS screen. Clerk A changes the address and presses Enter; ten seconds later clerk B changes the phone number and presses Enter. The phone number is saved, but the address change is gone. Explain, and give two fixes.

Show solution

Each screen is a separate task, so no lock is held between display and update. B's task rewrote the whole record from the copy B saw, which had the old address. This is a lost update.20

Fix 1: optimistic concurrency. Save a version number (or last-update timestamp) with the screen state; at update time, re-read with UPDATE and reject the change if the version differs (Listing 2).8 Fix 2: update only the fields the user changed, re-reading the current record in the update task, so B's task applies "phone = new" to the current record that already has A's address. Fix 1 is the more general solution because it also catches conflicting changes to the same field.

Before the key ordering in Listing 5 was added, transfers from account 111 to 222 and from 222 to 111 submitted at the same instant sometimes both abended with AKCS. Explain the abend and why ordering the reads fixes it.

Show solution

Task 1 locked 111 and waited for 222; task 2 locked 222 and waited for 111. Neither could continue, a deadlock. After the DTIMOUT interval CICS purged the waiting tasks with abend AKCS, and dynamic backout released their locks.9 If every task locks the lower key first, both transfers try to lock 111 first; one waits for the other to finish, and a cycle of waits cannot form.2

Exercise 9: Order the log writes

Place these events of a successful two-phase commit in the correct order and mark which must be forced to disk: (A) participant writes PREPARED; (B) coordinator sends COMMIT; (C) coordinator writes COMMIT; (D) participant votes YES; (E) participant writes COMMITTED and releases locks; (F) coordinator writes END.

Show solution

A (forced), D, C (forced; this is the commit point), B, E, F (need not be forced). The participant must force PREPARED before voting so it can keep its promise after a crash; the coordinator must force COMMIT before telling anyone so the decision survives a crash. END only lets the coordinator forget the transaction, so losing it costs at most a redundant resynchronization.19,28

Exercise 10: Design choice

A travel booking needs a flight (on z/TPF at an airline), a hotel (a partner's REST API), and a payment (CICS and Db2 at your bank). Should this be one distributed transaction with two-phase commit? If not, outline the alternative.

Show solution

No. The participants belong to different organizations, the external API is unlikely to support a 2PC protocol, and any participant in doubt would hold seats, rooms or funds locked for an unbounded time if a coordinator failed.2,8 Use a saga: reserve flight, reserve hotel, take payment, each as a local transaction, with compensating transactions (cancel flight, cancel hotel, refund) run in reverse order if a later step fails.26 Connect the steps with persistent messages put under syncpoint with each local update, and make each step idempotent so retries are safe.7,25
