Job Control Language on z/OS: A Practical Technical Guide

Technical article · Covers z/OS 2.x and 3.x with JES2 (and JES3 for legacy sites) · References in Vancouver style

Abstract. Job Control Language (JCL) is the language through which a user tells z/OS what batch work to run, which programs to execute, and which data sets and devices those programs need. This article covers JCL from the coding rules through the JOB, EXEC and DD statements, data set allocation, cataloged and in-stream procedures, conditional execution with COND and IF/THEN/ELSE, return and completion codes, job-to-job dependencies, restart of failed jobs, the JES2 and JES3 job entry subsystems, and enterprise scheduling and automation. Every section includes working examples, and the article closes with exercises and worked solutions. Statements of fact are referenced to IBM product documentation and IBM Redbooks.

1. What JCL is and where it fits

On z/OS, a batch job is a unit of work that runs without interaction with a user. JCL is the set of control statements that describes such a job to the operating system: it identifies the job and its owner, names each program to run (a job step), and describes every data set, device or output class each step needs.1,2 JCL is not a programming language in the usual sense. It has no loops or variables in the procedural sense; it is a declarative description of resources and execution order that the system reads, checks, and acts on.3

A job reaches the system through a job entry subsystem (JES), either JES2 or JES3. JES reads the JCL, converts it into internal control blocks, queues the job until an initiator is available in a suitable job class, and after execution manages the job's printed (SYSOUT) output.3,4 The z/OS component that interprets JCL and allocates the resources each step needs is the job scheduler, with its converter/interpreter and allocation functions.2

Figure 1. The phases a JES2 job passes through. JES3 adds further scheduling phases, described in Section 13.3,4

Every job uses three core statement types, and a handful of supporting ones:1

StatementPurpose

EXECMarks the start of a step; names the program (PGM=) or procedure to run.

2. Coding rules and statement format

JCL inherits its format from 80-column punched cards. Most statements consist of up to five fields: identifier, name, operation, parameter, and comments.1

  • Identifier field: // in columns 1 and 2 (/* for a delimiter, //* for a comment).
  • Name field: starts in column 3; 1 to 8 alphanumeric or national ($ # @) characters, the first of which must be alphabetic or national.
  • Operation field: the statement type (JOB, EXEC, DD ...), preceded and followed by at least one blank.
  • Parameter field: positional parameters first, then keyword parameters (KEYWORD=value), separated by commas with no embedded blanks.
  • Comments field: anything after the blank that ends the parameter field.

JCL is coded in columns 1 through 71. To continue a statement, end the line after a complete parameter and its comma, and start the next line with // in columns 1-2, a blank in column 3, and the continued parameter anywhere in columns 4 through 16.1 Columns 73-80 are historically used for sequence numbers and are ignored.

//PAYROLL1 JOB (ACCT01),'N KNAPP',CLASS=A,MSGCLASS=X,      THIS IS A
//             NOTIFY=&SYSUID                               COMMENT
//*-------------------------------------------------------------------
//* A comment statement: everything after //* is ignored
//*-------------------------------------------------------------------
//STEP01   EXEC PGM=IEFBR14
//NEWDS    DD   DSN=&SYSUID..TEST.DATA,DISP=(NEW,CATLG,DELETE),
//             SPACE=(TRK,(1,1)),RECFM=FB,LRECL=80
//
Listing 1. A minimal job. The final // is the null statement, which marks the end of the job. &SYSUID is a system symbol replaced by the submitting user ID; the double period in &SYSUID..TEST is needed because one period ends the symbol name.1
Symbols. JCL supports symbolic parameters in procedures, symbols set with the SET statement, and z/OS system symbols such as &SYSUID. Substitution happens before the statement is interpreted, so a symbol can supply any part of a parameter value.1,2

3. The JOB statement

The JOB statement is the first statement of every job. Its name field is the job name, which JES uses to identify the job together with the JES-assigned job number (for example JOB01234).1,3

//jobname JOB (accounting-information),'programmer-name',keyword-parameters

The two positional parameters, accounting information and programmer name, may be required by an installation's exits even though z/OS itself treats them as optional.1 The most commonly coded keyword parameters are:

ParameterMeaning
CLASS=Job class; determines which initiators may select the job. Classes and their attributes are defined by the installation in JES initialization.1,5
MSGCLASS=Output class for the job log, JCL listing and system messages.
MSGLEVEL=(s,m)s: 0 = JOB statement only, 1 = all JCL including procedure statements, 2 = only the submitted JCL. m: 0 = allocation/termination messages only if the job abends, 1 = always.1
NOTIFY=TSO/E user to notify when the job ends; NOTIFY=&SYSUID notifies the submitter.
REGION=Virtual storage limit for every step; REGION=0M requests all available private storage, subject to installation exits.1
TIME=Maximum processor time for the job, (minutes,seconds); TIME=NOLIMIT or 1440 removes the limit. Exceeding it causes abend S322.1,13
TYPRUN=SCAN checks the JCL for syntax errors without running it; HOLD holds the job until an operator releases it; JCLHOLD (JES2) holds it before conversion.1
COND=Job-level return code test (Section 10).
RESTART=, RD=Restart controls (Section 12).
PRTY=, SCHENV=, SYSAFF=, SYSTEM=Selection priority, WLM scheduling environment, and system affinity.1
USER=, GROUP=Security identity under which the job runs, checked by the security product (for example RACF).
//NIGHTLY  JOB (D123,FIN),'GL BATCH',
//             CLASS=B,MSGCLASS=X,MSGLEVEL=(1,1),
//             REGION=0M,TIME=(30,0),NOTIFY=&SYSUID

4. The EXEC statement

Each EXEC statement begins a job step. A job can contain at most 255 steps, counting the steps inside procedures it calls.1 The first positional parameter is either PGM=, naming a load module or program object, or PROC= (or just a procedure name), naming a procedure.

//STEP10   EXEC PGM=MYPROG,PARM='DATE=20261030,MODE=FULL',
//             REGION=64M,TIME=(5,0),COND=(4,LT)
//STEP20   EXEC PROC=SORTPROC        same as: EXEC SORTPROC
ParameterMeaning
PGM=Program to run, located through STEPLIB, then JOBLIB, then the system link list. PGM=*.stepname.ddname refers back to a program created in an earlier step.1,2
PARM=Up to 100 characters passed to the program.1
PARMDD=Names a DD statement whose data set supplies a longer parameter string, up to 32,760 bytes; mutually exclusive with PARM.1
COND=Return code tests that decide whether the step is bypassed (Section 10).
REGION=, TIME=Step-level storage and CPU limits; JOB-level values take precedence where coded.1
RD=Restart definition for the step (Section 12).

Programs are located through special DD statements. JOBLIB must appear immediately after the JOB statement (before the first EXEC) and applies to every step; STEPLIB follows an EXEC statement and applies to that step only, overriding JOBLIB for it.1,2

//BUILD    JOB (ACCT),'N KNAPP',CLASS=A,MSGCLASS=X
//JOBLIB   DD   DSN=PROD.LOADLIB,DISP=SHR
//STEPA    EXEC PGM=PGMA                   found in PROD.LOADLIB
//STEPB    EXEC PGM=PGMB
//STEPLIB  DD   DSN=TEST.LOADLIB,DISP=SHR  STEPB searches TEST.LOADLIB
//         DD   DSN=PROD.LOADLIB,DISP=SHR  ...then PROD.LOADLIB
Listing 3. JOBLIB and STEPLIB. The unnamed second DD under STEPLIB is a concatenation.

5. The DD statement

A DD (data definition) statement connects a ddname used inside a program to an actual resource. A COBOL program, for example, refers to a file through the ddname in its ASSIGN clause, and the JCL decides which data set that ddname means for this run.2,3 This separation lets the same program run against test and production data without being recompiled.

//ddname   DD   DSN=data.set.name,DISP=(status,normal,abnormal),
//             UNIT=unit,VOL=SER=volser,SPACE=(...),
//             RECFM=..,LRECL=..,BLKSIZE=..

5.1 Key parameters

ParameterMeaning
DSN= (DSNAME=)Data set name: up to 44 characters, in qualifiers of 1-8 characters separated by periods. &&name denotes a temporary data set; a member is written LIB(MEMBER); a generation of a GDG is written BASE(+1), BASE(0), BASE(-1).1,12
DISP=Status and disposition (below).
SPACE=Primary and secondary space and directory blocks for new DASD data sets.
UNIT=, VOL=Device type or group, and volume serial; usually unnecessary for cataloged or SMS-managed data sets.
DCB subparametersRECFM, LRECL, BLKSIZE, DSORG; coded directly or inside DCB=(...). Omitting BLKSIZE on a new DASD data set lets the system choose an optimal block size.1,12
DATACLAS, STORCLAS, MGMTCLASDFSMS classes that supply attributes, placement and life-cycle policy for SMS-managed data sets.1,12
LIKE=, REFDD=Copy attributes from a model data set or earlier DD.
DSNTYPE=LIBRARY (PDSE), PDS, LARGE, EXTREQ/EXTPREF (extended format), HFS.1
SYSOUT=Route output to a JES output class; SYSOUT=* means "same as MSGCLASS".
*, DATAIn-stream data follows.
DUMMYNo data set: reads get end-of-file at once, writes are discarded.
PATH=A z/OS UNIX file, with PATHOPTS, PATHMODE and PATHDISP.1

5.2 DISP: status and disposition

DISP=(status,normal-termination,abnormal-termination) tells the system whether a data set exists, how it may be shared, and what to do with it when the step ends normally or abnormally.1,2

SubparameterValues
StatusNEW create (default) · OLD exists, exclusive use · SHR exists, shared read · MOD append, or create if it does not exist
Normal endDELETE · KEEP · PASS (to a later step) · CATLG · UNCATLG
Abnormal endDELETE · KEEP · CATLG · UNCATLG (PASS is not allowed)

If the normal disposition is omitted, a NEW data set is deleted at step end and an existing one is kept. If the abnormal disposition is omitted, the normal disposition is used (with PASS treated as the default for the status).1 The classic pattern for a new permanent data set is therefore DISP=(NEW,CATLG,DELETE): catalog it on success, remove it on failure so a rerun does not trip over a half-written copy.

Exclusive enqueues. DISP=OLD, NEW and MOD obtain an exclusive enqueue on the data set name, normally held for the whole job, not just the step. A job that writes a file other jobs read with DISP=SHR will block those readers until it ends.2

6. Data set allocation

Allocation is the process of assigning data sets and devices to a step's DD statements before the program runs, including creating new data sets on DASD.2,12 If allocation fails (for example, a data set to be created already exists, or a referenced one is not cataloged) the step does not run and the job usually ends with a JCL error.

6.1 SPACE

SPACE=(unit,(primary,secondary,directory),RLSE,CONTIG)
  unit      = TRK | CYL | average-block-length
  directory = PDS directory blocks (omit for sequential; for a PDSE it is ignored
              except as an indication of a library)
  RLSE      = release unused space when the data set is closed

With AVGREC=U|K|M the first subparameter is an average record length and quantities are counted in records (units, thousands, millions).1 A non-extended sequential data set can occupy at most 16 extents on a volume; running out of space produces abends such as SB37, SD37 or SE37.12,13

6.2 Allocation examples

6.3 Temporary data sets and passing between steps

A data set named &&name, or a new data set with no DSN, is temporary and is deleted at the end of the job at the latest. DISP=(NEW,PASS) hands it to a later step, which can refer back with DSN=*.stepname.ddname or simply the same &&name.1,2

//EXTRACT  EXEC PGM=EXTRPGM
//OUTFILE  DD DSN=&&EXTR,DISP=(NEW,PASS),SPACE=(CYL,(10,10)),
//            RECFM=FB,LRECL=200
//REPORT   EXEC PGM=RPTPGM
//INFILE   DD DSN=&&EXTR,DISP=(OLD,DELETE)
//*        equivalent: DSN=*.EXTRACT.OUTFILE

6.4 Generation data groups

A generation data group (GDG) is a catalog structure that keeps a rolling set of chronologically related data sets under one base name. The base is defined once with IDCAMS, specifying how many generations to keep; JCL then uses relative generation numbers.11,12

//DEFGDG   EXEC PGM=IDCAMS
//SYSPRINT DD SYSOUT=*
//SYSIN    DD *
  DEFINE GENERATIONDATAGROUP -
         (NAME(PROD.GL.DAILY) LIMIT(7) SCRATCH NOEMPTY)
/*
//*--- in the daily job: read today's input, write a new generation
//DAILY    EXEC PGM=GLPOST
//PREV     DD DSN=PROD.GL.DAILY(0),DISP=SHR         current generation
//NEW      DD DSN=PROD.GL.DAILY(+1),DISP=(NEW,CATLG,DELETE),
//            SPACE=(CYL,(20,10),RLSE),RECFM=FB,LRECL=300
Listing 6. With LIMIT(7) and SCRATCH, the oldest generation is uncataloged and deleted when an eighth is created. Relative numbers are resolved once per job, so a later step in the same job still refers to the new generation as (+1).1,12

7. Input and output definitions

7.1 In-stream data

DD * introduces data that follows in the job stream. It ends at a /* delimiter or at the next JCL statement (// in columns 1-2). DD DATA allows lines beginning with // in the data (for example JCL being written to a file), and ends only at the delimiter; DLM=xx chooses a different two-character delimiter.1

//WRITEJCL EXEC PGM=IEBGENER
//SYSPRINT DD SYSOUT=*
//SYSIN    DD DUMMY
//SYSUT2   DD DSN=&SYSUID..JCL.CNTL(NEWJOB),DISP=SHR
//SYSUT1   DD DATA,DLM=$$
//NEWJOB   JOB (ACCT),'GENERATED',CLASS=A
//S1       EXEC PGM=IEFBR14
/*  this line is data too, because the delimiter is $$
$$
Listing 7. Copying JCL into a library member with IEBGENER. SYSUT1 is input, SYSUT2 output, SYSPRINT messages, and SYSIN (control statements) is DUMMY for a straight copy.10

7.2 Output: SYSOUT and the OUTPUT statement

SYSOUT=class writes to the JES spool rather than to a data set. Further routing and formatting comes from an OUTPUT statement, referenced explicitly by OUTPUT=*.name or applied implicitly with DEFAULT=YES.1

//RPTOUT   OUTPUT DEST=RMT5,COPIES=2,FORMS=STD1
//REPORT   EXEC PGM=RPTPGM
//SYSPRINT DD SYSOUT=A,OUTPUT=*.RPTOUT
//AUDIT    DD SYSOUT=(X,,AUD1)            class X, form AUD1
//NEXTJOB  DD SYSOUT=(A,INTRDR)           internal reader

Writing to SYSOUT=(A,INTRDR) sends records to the JES internal reader, which treats them as a newly submitted job: a common way for one job to submit another.1,2

7.3 Concatenation, DUMMY and dumps

Several input data sets can be read as one by concatenating DD statements: the first carries the ddname and the rest leave the name field blank. Sequential concatenations may mix data sets with compatible attributes; library concatenations are searched in order for a member.1,12

//SORTIN   DD DSN=PROD.SALES.EAST,DISP=SHR
//         DD DSN=PROD.SALES.WEST,DISP=SHR
//         DD DSN=PROD.SALES.NORTH,DISP=SHR
//SYSUDUMP DD SYSOUT=*                    formatted dump if step abends
//OPTFILE  DD DUMMY                       program sees immediate EOF

Reserved ddnames include JOBLIB, STEPLIB, SYSABEND, SYSUDUMP, SYSMDUMP, SYSCHK and SYSCKEOV; each has a defined system meaning.1

7.4 A sort step

//SORT     EXEC PGM=SORT

8. Procedures and procedure libraries (PROCs)

A procedure is a named, reusable sequence of JCL steps. An in-stream procedure is coded inside the job between PROC and PEND; a cataloged procedure is a member of a procedure library and is shared by many jobs.1,2 Procedures may call other procedures, nested to 15 levels.1

8.1 Where procedures are found

The system procedure libraries (including SYS1.PROCLIB) are defined to JES, for JES2 through PROCLIB initialization statements or PROCxx DD statements in the JES2 started procedure.5 A job can name its own libraries, searched before the system ones, with JCLLIB, which must come after the JOB statement and before the first EXEC:1

//MYJOB    JOB (ACCT),'N KNAPP',CLASS=A,MSGCLASS=X
//MYLIBS   JCLLIB ORDER=(&SYSUID..PROCLIB,DEPT.SHARED.PROCLIB)
//         INCLUDE MEMBER=STDDDS        copies JCL from member STDDDS
//S1       EXEC MYPROC

8.2 Symbolic parameters

//COPYPROC PROC IN=,OUT=,SPC='(CYL,(1,1),RLSE)',CLS='*'

8.3 Overriding and adding statements

A caller can change any procedure step without editing the procedure:1,2

  • EXEC parameter overrides use parameter.procstepname=value, for example REGION.COPY=32M or PARM.COMPILE='LIST'. Without a step name, most parameters apply to every step in the procedure; PARM without a step name applies to the first step and nullifies PARM on later steps.
  • DD overrides are coded as //procstepname.ddname DD ... after the EXEC that calls the procedure, in the same order as the DD statements in that step. Only the parameters coded change; a parameter coded with no value (SPACE=) is nullified.
  • Added DD statements use the same naming with a ddname not present in the procedure, and follow any overrides for that step.
//S1       EXEC COPYPROC,IN=PROD.MASTER,OUT=NKNAPP.MASTER.BKUP,
//             REGION.COPY=16M
//COPY.SYSUT2 DD UNIT=SYSALLDA,SPACE=(CYL,(50,10),RLSE)  override
//COPY.SYSUDUMP DD SYSOUT=*                               addition

9. Return codes, completion codes and abends

When a step's program ends normally, it passes a return code (also reported as the step's condition code) in general register 15. The value can be from 0 to 4095.1,2 IBM utilities and compilers follow a widely used convention:3,10

RCConventional meaning
0Successful.
4Warning; output probably usable.
8Error; results questionable.
12Severe error.
16Terminal error; often an unusable data set or missing DD.

Application programs set their own codes: COBOL through the RETURN-CODE special register, PL/I through PLIRETC, and assembler by loading register 15.

When a step ends abnormally (an abend), there is no return code; instead there is a completion code:13

  • System completion codes are three hexadecimal digits written Sxxx, for example S0C7 (data exception, typically invalid packed-decimal data), S0C4 (protection exception), S806 (program not found), S322 (CPU time exceeded), S222 (cancelled by operator), SB37/SD37/SE37 (out of space).
  • User completion codes are decimal, written Unnnn, from 0 to 4095, issued by an application or product through the ABEND macro or a language service.

A JCL error is different again: the job fails during conversion or allocation and no step runs (or the failing step does not start). The job log shows messages such as IEFC-prefixed syntax messages or IEF allocation messages.1,2 The job's overall highest return code, or its abend code, is reported by JES2 in message $HASP395 at job end and is visible through SDSF.4

IEF142I NKNAPPA S010 - STEP WAS EXECUTED - COND CODE 0004
IEF272I NKNAPPA S020 - STEP WAS NOT EXECUTED.
$HASP395 NKNAPPA ENDED - RC=0004
Listing 11. Typical job-log messages (illustrative). IEF142I reports a step's condition code; IEF272I reports a bypassed step.2

10. Conditional execution

JCL offers two mechanisms for deciding whether a step runs: the older COND parameter and the IF/THEN/ELSE/ENDIF statement construct.1

10.1 The COND parameter

COND=(code,operator) or COND=(code,operator,stepname) describes a test that, when true, bypasses the step. The test reads "if code operator the return code of a previous step". Operators are GT GE EQ NE LT LE. Up to eight tests can be coded; if any one is true, the step is skipped.1

//S3  EXEC PGM=REPORT,COND=(4,LT)
//*   bypass S3 if 4 < RC of any previous step, i.e. if any RC > 4

//S4  EXEC PGM=FIXUP,COND=(0,EQ,S2)
//*   bypass S4 if S2 ended with RC 0  (run S4 only when S2 failed)

//S5  EXEC PGM=MERGE,COND=((8,LE,S1),(4,LT,S2))
//*   bypass if S1 RC >= 8 OR S2 RC > 4

Normally a step is bypassed automatically after an earlier abend. Two special values change that: COND=EVEN runs the step even if a previous step abended, and COND=ONLY runs it only if a previous step abended.1 On the JOB statement, COND= applies the test to every step: when it becomes true, all remaining steps are bypassed, and step-level COND parameters are then ignored.1

Reading COND correctly. The reversed logic ("the condition describes when not to run") is the most common source of COND mistakes. Read COND=(4,LT) aloud as "skip if four is less than a previous return code".

10.2 IF/THEN/ELSE/ENDIF

The IF construct expresses the condition under which steps run, in ordinary relational syntax, and can be nested up to 15 levels.1 Its relational expressions may test:

  • RC (highest return code of steps so far) or stepname.RC / stepname.procstepname.RC;
  • ABEND / ¬ABEND (also NOT ABEND), and ABENDCC=Sxxx or ABENDCC=Unnnn;
  • stepname.RUN (true if the step started).

Operators are GT GE EQ NE LT LE or > >= = ¬= < <=, combined with AND (&), OR (|) and NOT (¬).1

//UPDATE   EXEC PGM=UPDMAST
//MASTER   DD   DSN=PROD.MASTER,DISP=OLD
//*
//CHKUPD   IF (UPDATE.RC <= 4) THEN
//REPORT     EXEC PGM=RPTGEN
//RPT        DD SYSOUT=*
//         ELSE
//ALERT      EXEC PGM=IEBGENER
//SYSIN      DD DUMMY
//SYSPRINT   DD SYSOUT=*
//SYSUT2     DD SYSOUT=(A,INTRDR)        submit a recovery job
//SYSUT1     DD DSN=PROD.JCL(RECOVER),DISP=SHR
//         ENDIF
//*
//ONABEND  IF (ABEND) THEN
//DIAG       EXEC PGM=DIAGPGM
//         ENDIF
Listing 12. IF/THEN/ELSE. The second construct runs a diagnostic step only after an abend. A test on RC alone does not make a step run after an abend; the condition must test ABEND, ABENDCC or stepname.RUN.1
IntentCOND form (on the step)IF form (around the step)
Run only if all previous RCs ≤ 4COND=(4,LT)IF (RC <= 4) THEN
Run only if STEP1 RC = 0COND=(0,NE,STEP1)IF (STEP1.RC = 0) THEN
Run only if STEP1 failed (RC ≥ 8)COND=(8,GT,STEP1)IF (STEP1.RC >= 8) THEN
Run only after an abendCOND=ONLYIF (ABEND) THEN
Run whatever happensCOND=EVENIF (ABEND | ¬ABEND) THEN

COND on an EXEC statement inside an IF construct is still honoured: the step runs only if the IF condition allows it and its own COND test is false.1

11. Job dependencies

Steps in one job always run in sequence. Dependencies between jobs (job B must wait for job A) can be expressed in several ways, from simplest to most capable:

11.1 Chaining through the internal reader

The last step of job A copies job B's JCL to SYSOUT=(A,INTRDR), conditionally on success (Listing 12 shows the pattern). It is simple but hides the dependency inside JCL, and B is not visible as "waiting" before A finishes.2

11.2 Serialization by job name and data set

JES2 will not run two jobs with the same job name at the same time unless the installation allows duplicate job names to run, so identically named jobs naturally queue behind each other.5 Exclusive data set enqueues (DISP=OLD) also serialize jobs, but only implicitly.

11.3 JES2 job execution control: JOBGROUP

Since z/OS 2.2, JES2 supports job groups: a JOBGROUP definition submitted to JES2 that names member jobs with GJOB statements and expresses dependencies between them with AFTER, BEFORE and CONCURRENT. Each member job joins the group with a SCHEDULE JOBGROUP= statement.1,18

//PAYGRP   JOBGROUP (ACCT01),'N KNAPP'
//EXTRACT  GJOB
//CALC     GJOB
//         AFTER NAME=EXTRACT,WHEN=(RC<=4)
//PRINT    GJOB
//         AFTER NAME=CALC
//PAYGRP   ENDGROUP
//*
//EXTRACT  JOB (ACCT01),'N KNAPP',CLASS=A,MSGCLASS=X
//         SCHEDULE JOBGROUP=PAYGRP
//S1       EXEC PGM=PAYEXTR
//...
//CALC     JOB (ACCT01),'N KNAPP',CLASS=A,MSGCLASS=X
//         SCHEDULE JOBGROUP=PAYGRP
//S1       EXEC PGM=PAYCALC
//...
Listing 13. A JES2 job group: CALC runs after EXTRACT ends with RC ≤ 4, and PRINT after CALC. If a dependency's WHEN condition is not met, the default action flushes the dependent job; the ACTION and OTHERWISE keywords change this. Consult the JCL Reference for the full syntax at your z/OS level.1,18

JES2 also provides the SCHEDULE statement for single jobs, including HOLDUNTL= (hold until a date and time), STARTBY= (try to start by a deadline) and WITH= (run on the same system as another job).1

11.4 JES3 dependent job control

JES3 offered dependent job control (DJC) through the //*NET JECL statement: jobs in a named network are held until a specified number of predecessors complete, and can be released or flushed according to how those predecessors end.1,7

//JOBB     JOB (ACCT),'N KNAPP',CLASS=A
//*NET NETID=PAYNET,NHOLD=1,RELEASE=(JOBC)

11.5 Workload schedulers

Production sites normally define cross-job dependencies (including time, calendar, file-arrival and cross-platform conditions) in a workload scheduler rather than in JCL; see Section 14.9,14

12. Restarting failed jobs

When a long job fails part-way through, rerunning it from the beginning may waste hours or, worse, repeat updates that already succeeded. z/OS supports two kinds of restart, each either automatic (the system restarts the job immediately, with operator consent) or deferred (the user resubmits the job later):1,2,17

  • Step restart resumes execution at the start of a named step.
  • Checkpoint restart resumes within a step from a checkpoint the program took with the CHKPT macro (written to a SYSCKEOV or named checkpoint data set).

12.1 RD: restart definition

ValueMeaning
RD=RAllow automatic step restart (and automatic checkpoint restart).
RD=RNCAllow automatic step restart; suppress CHKPT checkpoints.
RD=NRTake checkpoints but do not restart automatically.
RD=NCNo checkpoints and no automatic restart.

Automatic restart applies only to abends with eligible completion codes and requires operator authorization when the system asks.1,17

12.2 Deferred step restart with RESTART=

The common practical technique is deferred step restart: correct the problem, then resubmit the job with RESTART= on the JOB statement. Steps before the named step are not executed.1

//NIGHTLY  JOB (D123,FIN),'GL BATCH',CLASS=B,MSGCLASS=X,
//             RESTART=POST                 resume at step POST
//NIGHTLY  JOB ...,RESTART=(POST.UPDATE)    procstep UPDATE of step POST
//NIGHTLY  JOB ...,RESTART=*                from the first step
//NIGHTLY  JOB ...,RESTART=(POST,CHK0004)   checkpoint restart

12.3 Designing jobs that can be restarted

Restart is only safe if the job is designed for it. The points below summarize the guidance in IBM's JCL User's Guide and batch Redbooks:2,9

  1. Make steps idempotent. A step that creates DISP=(NEW,CATLG,DELETE) output deletes it on abend, so a rerun can recreate it. For return-code failures (no abend), the normal disposition applies and the data set is cataloged, so add a delete-if-exists step (Listing 5) at the start of each restartable section.
  2. Do not depend on passed temporary data sets across a restart point. &&TEMP data sets and backward references to steps that will not run are not available in a restarted job; either make the intermediate data set permanent or restart at the step that creates it.
  3. Be careful with GDGs. If a failed run already cataloged a (+1) generation, on restart (0) refers to it, and a new (+1) creates yet another. Restart instructions often change relative numbers, or a scheduler manages this automatically.
  4. Remember that bypassed steps' return codes are not available. In a restarted job, COND or IF tests that refer to steps before the restart point cannot be evaluated against their earlier results.
  5. Back up before update. Steps that update data in place (DISP=OLD or databases) need a backup step or database commit/rollback logic.
Restart in schedulers. Workload schedulers such as IBM Z Workload Scheduler provide step-level restart and cleanup that automate many of these points, deleting or uncataloging data sets created by the failed run before resubmitting.14

13.3 Initiators and classes

Execution is controlled by initiators, each eligible to select jobs from one or more classes. JES2 initiators can be controlled by JES2 or, in WLM-managed classes, started and stopped by the Workload Manager according to service goals.4,5 An installation typically uses classes to separate short test jobs, long production jobs, and jobs needing particular resources.

14. Job scheduling and automation

JES decides which waiting job runs next; it does not decide when a job should be submitted. Production batch is therefore driven by a workload scheduler that holds a calendar-based plan, submits jobs when their time, predecessor and resource conditions are met, tracks completion, and handles errors and restarts.9,14

14.1 IBM Z Workload Scheduler

IBM Z Workload Scheduler (previously IBM Tivoli Workload Scheduler for z/OS, and earlier OPC) consists of a controller that maintains the long-term and current plans and a tracker on each system that submits jobs and reports events back. Work is defined as applications (job streams) of operations with predecessor relationships, run cycles and resource requirements.14 It can also tailor JCL at submission, replacing scheduler variables such as the planned date:14

//*%OPC SCAN
//GLDAILY  JOB (D123,FIN),'GL BATCH',CLASS=B,MSGCLASS=X
//POST     EXEC PGM=GLPOST,PARM='RUNDATE=&OYMD1'
Listing 14. Scheduler JCL tailoring: the //*%OPC SCAN directive enables variable substitution, and &OYMD1 is replaced by the occurrence's input-arrival date before submission.14

Other vendors provide comparable z/OS schedulers. The principles are the same: dependencies live in the scheduler's database, not in the JCL, so the JCL stays simple and restartable.

14.2 Submitting and monitoring jobs programmatically

Jobs can be submitted and monitored without a 3270 session:

  • TSO/E SUBMIT and the ISPF editor's SUB command, with output viewed in SDSF.3
  • The internal reader from any program or job step (Section 7.2).2
  • The z/OSMF REST jobs interface, which accepts JCL over HTTPS (PUT /zosmf/restjobs/jobs) and returns job status and spool files as JSON.20
  • The Zowe CLI, an open-source Open Mainframe Project tool that uses z/OSMF, for example zowe zos-jobs submit data-set "NKNAPP.JCL.CNTL(NIGHTLY)" --wait-for-output, which suits CI/CD pipelines.21

15. A complete worked example

The following job brings the pieces together: it uses a private procedure library, deletes leftovers from an earlier run so it can be rerun, sorts and validates input, updates a GDG, and reports or alerts depending on outcome.

//SALESDLY JOB (D123,SALES),'N KNAPP',CLASS=B,MSGCLASS=X,
//             MSGLEVEL=(1,1),REGION=0M,NOTIFY=&SYSUID
//*==================================================================
//* Daily sales processing
//*  CLEAN   - remove work files left by a previous failed run
//*  SORT    - sort and filter raw input
//*  VALID   - validate; RC 0 ok, 4 warnings, 8+ reject
//*  POST    - post to the master GDG (only if VALID RC <= 4)
//*  REPORT  - summary report
//*  ALERT   - notify operations if anything failed or abended
//*==================================================================
//         JCLLIB ORDER=SALES.PROD.PROCLIB
//         SET HLQ=SALES.PROD
//JOBLIB   DD DSN=&HLQ..LOADLIB,DISP=SHR
//*
//CLEAN    EXEC PGM=IDCAMS
//SYSPRINT DD SYSOUT=*
//SYSIN    DD *
  DELETE SALES.PROD.SORTED NONVSAM PURGE
  IF LASTCC <= 8 THEN SET MAXCC = 0
/*
//SORT     EXEC PGM=SORT
//SYSOUT   DD SYSOUT=*
//SORTIN   DD DSN=&HLQ..RAW.EAST,DISP=SHR
//         DD DSN=&HLQ..RAW.WEST,DISP=SHR
//SORTOUT  DD DSN=&HLQ..SORTED,DISP=(NEW,CATLG,DELETE),
//            SPACE=(CYL,(20,10),RLSE),RECFM=FB,LRECL=120
//SYSIN    DD *
  SORT FIELDS=(1,10,CH,A)
  OMIT COND=(11,1,CH,EQ,C'X')
/*
//         IF (SORT.RC = 0) THEN
//VALID      EXEC PGM=SALEVAL
//SALESIN    DD DSN=&HLQ..SORTED,DISP=SHR
//ERRORS     DD SYSOUT=*
//         ENDIF
//*
//         IF (VALID.RUN & VALID.RC <= 4) THEN
//POST       EXEC PGM=SALEPOST
//SALESIN    DD DSN=&HLQ..SORTED,DISP=SHR
//MASTPREV   DD DSN=&HLQ..MASTER(0),DISP=SHR
//MASTNEW    DD DSN=&HLQ..MASTER(+1),DISP=(NEW,CATLG,DELETE),
//              SPACE=(CYL,(50,20),RLSE),RECFM=FB,LRECL=200
//REPORT     EXEC SALESRPT,MAST=&HLQ..MASTER(+1)
//         ENDIF
//*
//         IF (ABEND | RC > 4) THEN
//ALERT      EXEC PGM=IEBGENER
//SYSPRINT   DD SYSOUT=*
//SYSIN      DD DUMMY
//SYSUT1     DD DSN=&HLQ..JCL(ALERTJOB),DISP=SHR
//SYSUT2     DD SYSOUT=(A,INTRDR)
//         ENDIF
//
Listing 16. A restartable daily job. SALESRPT is assumed to be a cataloged procedure in SALES.PROD.PROCLIB with a symbolic parameter MAST; SALEVAL and SALEPOST are application programs. In IDCAMS, a DELETE of a missing data set sets condition code 8, which the IF LASTCC resets.1,11,16

If POST abends, its new generation is deleted by the abnormal disposition and the job can be restarted with RESTART=POST: SORTED is a cataloged permanent data set, so it is still there, and MASTER(0) still refers to the previous master. Note that after a restart at POST, the IF (VALID.RUN & ...) test sees VALID as not run; a restart procedure would either restart at VALID or remove that condition.

16. Exercises with solutions

Try each exercise before opening its solution. All answers follow the JCL Reference.1

Exercise 1: Find the errors

The following job contains five errors. Identify and correct them.

//1STJOB  JOB (ACCT),'TRAINEE',CLASS=A,MSGCLASS=X
//STEP1   EXEC PGM=IEBGENER
//SYSPRINT DD SYSOUT=*
//SYSIN    DD DUMMY
//SYSUT1   DD DSN=TRAINEE.INPUT.DATA,DISP=SHR
//SYSUT2   DD DSN=TRAINEE.OUTPUT.DATA,DISP=(NEW,PASS,CATLG),
//            SPACE=(TRK,(5,5)) ,RECFM=FB,LRECL=80
//STEPNUMBER2 EXEC PGM=IEFBR14
Show solution
  1. 1STJOB: a name must start with an alphabetic or national character. Use JOB1ST.
  2. DISP=(NEW,PASS,CATLG) is legal syntax, but PASS for a permanent data set nobody uses later means it is deleted (as a NEW data set) at job end without being cataloged. Use DISP=(NEW,CATLG,DELETE).
  3. The abnormal disposition CATLG would keep a partial output after an abend; DELETE is the safe choice (fixed by the same change).
  4. SPACE=(TRK,(5,5)) ,RECFM=FB: the blank after the closing parenthesis ends the parameter field, so ,RECFM=FB,LRECL=80 is treated as a comment and the attributes are lost. Remove the blank.
  5. STEPNUMBER2 has 11 characters; names are limited to 8. Use STEP2.
//JOB1ST   JOB (ACCT),'TRAINEE',CLASS=A,MSGCLASS=X
//STEP1    EXEC PGM=IEBGENER
//SYSPRINT DD SYSOUT=*
//SYSIN    DD DUMMY
//SYSUT1   DD DSN=TRAINEE.INPUT.DATA,DISP=SHR
//SYSUT2   DD DSN=TRAINEE.OUTPUT.DATA,DISP=(NEW,CATLG,DELETE),
//            SPACE=(TRK,(5,5)),RECFM=FB,LRECL=80
//STEP2    EXEC PGM=IEFBR14

Exercise 2: Evaluate COND

STEP1 ends with RC 0, STEP2 with RC 8. For each step below, does it run?

//STEP3 EXEC PGM=A,COND=(8,LT)
//STEP4 EXEC PGM=B,COND=(4,LT,STEP2)
//STEP5 EXEC PGM=C,COND=((0,NE,STEP1),(12,LE,STEP2))
//STEP6 EXEC PGM=D,COND=(8,EQ)
//STEP7 EXEC PGM=E,COND=EVEN
Show solution

Remember: if the test is true, the step is bypassed. Assume steps 3 to 7 that run each end with RC 0.

  • STEP3: is 8 < any previous RC (0, 8)? No. Runs.
  • STEP4: is 4 < STEP2's RC (8)? Yes. Bypassed.
  • STEP5: 0 ≠ STEP1 RC (0)? No. 12 ≤ STEP2 RC (8)? No. Neither test is true. Runs.
  • STEP6: is 8 equal to any previous RC (0, 8, and STEP3 and STEP5 RC 0)? STEP2's 8 matches. Bypassed.
  • STEP7: COND=EVEN only means "also run after an abend"; with no return code tests and no abend, it runs.

Exercise 3: COND to IF

Rewrite STEP4 and STEP5 of Exercise 2 using IF/THEN/ENDIF instead of COND.

Show solution

Invert each test: a step with COND runs when all its tests are false.

//IF4      IF (STEP2.RC <= 4) THEN
//STEP4      EXEC PGM=B
//         ENDIF
//IF5      IF (STEP1.RC = 0 & STEP2.RC < 12) THEN
//STEP5      EXEC PGM=C
//         ENDIF

By De Morgan's law, "not (A or B)" becomes "not A and not B", which is why the two COND tests become an AND.

Exercise 4: Allocate a library

Write a one-step job that creates a PDSE named &SYSUID..JCL.CNTL for 80-byte fixed-blocked records, with 10 primary and 5 secondary tracks, cataloged on success and deleted on failure.

Show solution 
//MAKELIB  JOB (ACCT),'N KNAPP',CLASS=A,MSGCLASS=X,NOTIFY=&SYSUID
//ALLOC    EXEC PGM=IEFBR14
//NEWLIB   DD DSN=&SYSUID..JCL.CNTL,DISP=(NEW,CATLG,DELETE),
//            DSNTYPE=LIBRARY,SPACE=(TRK,(10,5,1)),
//            RECFM=FB,LRECL=80

DSNTYPE=LIBRARY makes it a PDSE. A directory quantity is still coded (any nonzero value) to show that a partitioned data set is wanted; for a PDSE the directory grows as needed. BLKSIZE is omitted so the system chooses an optimal value.

Exercise 5: Override a procedure

Using COPYPROC from Listing 9, write an EXEC statement and any override statements that copy PROD.CUST to NKNAPP.CUST.COPY, send SYSPRINT to class A, give the output 100 cylinders primary, and add a SYSUDUMP DD to the COPY step.

Show solution 
//CP       EXEC COPYPROC,IN=PROD.CUST,OUT=NKNAPP.CUST.COPY,
//             CLS=A,SPC='(CYL,(100,10),RLSE)'
//COPY.SYSUDUMP DD SYSOUT=*

Class and space are best changed through the symbolic parameters the procedure already provides. An equivalent override for space would be //COPY.SYSUT2 DD SPACE=(CYL,(100,10),RLSE), which must come before the added COPY.SYSUDUMP statement because overrides follow the procedure's DD order and additions come last.

Exercise 6: Generation data groups

A GDG PROD.TRANS has LIMIT(3) and currently holds G0010V00, G0011V00 and G0012V00. A job contains two steps: the first writes PROD.TRANS(+1); the second reads PROD.TRANS(+1) and PROD.TRANS(-1). Which absolute generations does the second step read, and what happens to G0010V00?

Show solution

Relative numbers are resolved relative to the state at the start of the job, so within the job (0) remains G0012V00 throughout. The first step creates G0013V00. The second step reads (+1) = G0013V00 and (-1) = G0011V00. With a limit of 3, cataloging G0013V00 rolls off the oldest generation, G0010V00, which is uncataloged (and deleted if the GDG has the SCRATCH attribute).

Exercise 7: Make a job restartable

This job abended in STEP3 with SB37. What does the abend mean, how do you fix it, and how do you rerun only the failed part?

//STEP1 EXEC PGM=EXTRACT
//OUT   DD DSN=&&EXT,DISP=(NEW,PASS),SPACE=(TRK,(50,10))
//STEP2 EXEC PGM=ENRICH
//IN    DD DSN=&&EXT,DISP=(OLD,DELETE)
//OUT   DD DSN=PROD.ENRICHED,DISP=(NEW,CATLG,DELETE),
//         SPACE=(CYL,(10,10),RLSE)
//STEP3 EXEC PGM=SUMMARY
//IN    DD DSN=PROD.ENRICHED,DISP=SHR
//OUT   DD DSN=PROD.SUMMARY,DISP=(NEW,CATLG,DELETE),
//         SPACE=(TRK,(1,1),RLSE)
Show solution

SB37 means the output data set needed more space but no further extent could be obtained (for example, the volume limit of extents was reached or no secondary space remained).13 Increase the allocation, e.g. SPACE=(CYL,(5,5),RLSE) on PROD.SUMMARY.

Because STEP3's DISP has DELETE for abnormal termination, the partial PROD.SUMMARY was deleted. PROD.ENRICHED was cataloged by STEP2 and still exists. The job can therefore be resubmitted with RESTART=STEP3 on the JOB statement. Restarting at STEP2 would not work, because the temporary &&EXT created by STEP1 no longer exists, and STEP2 would also fail allocating PROD.ENRICHED, which is already cataloged.

Exercise 8: Job dependencies

Jobs LOADA and LOADB can run in parallel. Job MERGE must start only when both have ended with RC ≤ 4. Express this with a JES2 job group.

Show solution 
//NIGHTGRP JOBGROUP (ACCT01),'N KNAPP'
//LOADA    GJOB
//LOADB    GJOB
//MERGE    GJOB
//         AFTER NAME=LOADA,WHEN=(RC<=4)
//         AFTER NAME=LOADB,WHEN=(RC<=4)
//NIGHTGRP ENDGROUP

Each of the three jobs must also contain // SCHEDULE JOBGROUP=NIGHTGRP after its JOB statement. LOADA and LOADB have no dependencies, so they become eligible immediately and can run in parallel; MERGE becomes eligible only when both AFTER conditions are satisfied.1,18 In a site with a workload scheduler, the same rule would normally be defined in the scheduler as two predecessors with a return code condition.

Exercise 10: Interpret a job log

A job's log shows IEF142I ... STEP01 - STEP WAS EXECUTED - COND CODE 0000, then IEA995I SYMPTOM DUMP OUTPUT ... SYSTEM COMPLETION CODE=0C7 for STEP02, and IEF272I ... STEP03 - STEP WAS NOT EXECUTED. What happened, and what is the most likely cause?

Show solution

STEP01 completed with RC 0. STEP02 abended with system completion code S0C7, a data exception, which in COBOL programs is most often caused by arithmetic on a numeric field containing invalid packed-decimal data (for example, spaces or uninitialized storage).13 STEP03 was bypassed because, after an abend, later steps are skipped unless they specify COND=EVEN/ONLY or are in an IF construct that tests for an abend.1
