SECTION 01

The question

Two processes cannot touch each other. Everything called interprocess communication is a scheme for getting a third party to hold something on their behalf, and the schemes differ mostly in how much of the message that third party agrees to remember.

A process is an address space with a protection boundary around it. That boundary is the point of the abstraction: one program's mistake should not be another program's corruption.1,2,3 But almost no useful program is alone. A shell runs a pipeline, a browser runs a renderer in a sandbox, a database runs a write-ahead-log writer, a phone runs an application that wants the camera. Each of these needs the boundary to hold and to be crossed at the same time, and the operating system's answer is a vocabulary of objects that live in the kernel and can be named by more than one process at once.

That vocabulary is usually taught as a list: pipes, named pipes, message queues, signals, semaphores, shared memory, sockets, remote procedure calls. The list is accurate and almost useless, because it sorts the mechanisms by their interface rather than by anything an engineer has to decide. It is the organisation of the standard references on the subject, which are excellent as references and offer no way to choose.4,5 Ask a practical question of the list — will my message arrive whole, will anyone notice if it does not, will the thing still be there tomorrow — and the list has no column for it.

Here is a different sort. Take one property, and one only: between the moment the sender acts and the moment the receiver looks, what does the kernel object itself still know? Not what the sender intended, not what the protocol on top reconstructs — what the kernel is holding, and would report if asked.

Answer that for each mechanism and they fall onto a ladder with six rungs. At the bottom, a shared memory segment holds pages and nothing else: no record that a write happened, no order, no arrival. One rung up, a standard signal holds a single bit, so a thousand notifications and one notification are the same object. Then a count, which keeps the number but not the contents. Then an ordered stream of bytes, which keeps every byte and destroys every boundary. Then framed messages, which keep the boundaries. And at the top, framed messages carrying something the sender could not have written into the payload at all — a priority the kernel sorts by, an open file descriptor, a set of credentials the kernel vouches for.

Sorting this way makes three things visible that the conventional list hides. The first is that everything a serialisation library or an RPC stub does is reconstruction: length prefixes rebuild the boundary that a stream destroyed, schemas rebuild the type that no rung ever kept, and a request identifier rebuilds the association between a call and its reply. The second is that the rung a mechanism occupies is nearly independent of how long its object survives; across the 32 mechanisms tabulated here the correlation between the two is -0.126, so “shared memory is faster” and “shared memory leaks” are answers to unrelated questions. The third is the one that organises the second half of this article: of the 9 mechanisms here that sit above the byte stream, exactly 1 survives a machine boundary. Everything richer than a stream is something one kernel promises, and there is no such thing as one kernel between two machines.

SECTION 02

Where the vocabulary came from

The mechanisms were not designed as a family. They were four separate responses to four separate problems, thirty years apart, and the incoherence of the modern interface is a fossil record of that.

Doug McIlroy's 1964 Bell Labs memorandum proposed connecting programs “like garden hose”, screwing in another segment when data needed massaging another way.6,7 He spent nine years pressing the idea before Ken Thompson implemented it; the pipe appears in the Unix source record on 15 January 1973 and in the Third Edition manual the following month.8,9 What Thompson built was not quite what McIlroy had asked for, and it arrived with the property that has defined it since: it is a byte stream with no notion of a record, because the shell that would use it was joining programs whose only common language was text.10,11,12

The second layer arrived because that answer was not enough for transactions. Columbus UNIX, a Bell Labs variant maintained in Ohio for administrative databases and telephone switching support, was developed specifically to remedy what its authors saw as Research Unix's missing pieces: interprocess communication and file locking.13,14 The three facilities added there — message queues, semaphores and shared memory — reached the wider world in System V in 1983 and are still called System V IPC.15,16,17 They carry the marks of their origin everywhere: they are named by integer keys rather than paths, they are not file descriptors and so do not work with select or poll, and they persist in the kernel until somebody explicitly destroys them.

The third layer arrived from Berkeley in the same year, and for a different reason again: 4.2BSD needed an interface to a network, and produced the socket, which generalised over address families so that the local case and the remote case looked alike.18,19 That generalisation is the single most consequential design decision in this whole history, and section 8 is about the part of it that could not be made to work.

The fourth layer is POSIX. The 1993 realtime amendment specified a parallel set of message queues, semaphores and shared memory with path-like names and descriptor semantics, explicitly to replace the System V set.20,21 It succeeded technically and only partly in practice; both families are still present, still specified, and still different, in the current edition of the standard, published as IEEE Std 1003.1-2024 in June 2024 and as ISO/IEC/IEEE 9945:2026 in March 2026.22,23

Running alongside all of this is a research tradition that took the opposite approach: rather than adding mechanisms to a kernel with a rich system-call surface, make message passing the only primitive and build everything else on it. Accent and then Mach organised the system around ports and messages;24,25 Liedtke's L4 work established that the cost of that design was an implementation problem rather than an inherent one, taking IPC from hundreds of microseconds to a few;26,27 seL4 later carried the same structure through a machine-checked proof of functional correctness.28,29 Cheriton's V system had meanwhile shown that a synchronous message-passing kernel could carry a whole distributed operating system.30 The theoretical statement of the same position is older still: Hoare's communicating sequential processes takes message passing as the primitive from which concurrency is built, and Brinch Hansen's multiprogramming nucleus had already reduced an operating system to process creation plus message passing five years earlier.31,32 Lauer and Needham had already argued that message-passing and shared-memory system structures are duals, mutually translatable with equivalent performance, which is worth holding on to when the two look like rival religions.33

The practical result is that a Linux programmer in 2026 faces a vocabulary assembled by four committees who were not talking to each other, plus a research tradition that says the whole thing could have been one primitive. There is no organising principle in the interface. There is one in the behaviour.

SECTION 03

Three questions that get asked as one

How the two ends find each other, how much the kernel keeps, and how long the object lasts are independent. Most arguments about IPC are two people answering different ones.

Every mechanism in this article settles three separate things, and the conventional list conflates them so thoroughly that they have no separate names.

Rendezvous. How does the second process come to hold a reference to the same kernel object? The available schemes are surprisingly few. An anonymous pipe uses inheritance: you must be a descendant of the creator.34,35 A FIFO, a Unix socket and a POSIX object use a name in a filesystem, with the filesystem's permission model coming along whether you wanted it or not.36,37 System V uses an integer key, usually derived from a path by ftok, which can collide.16 A signal uses a process identifier, which can be reused between the moment you read it and the moment you send — a race that pidfd_open exists to close.38 A socket uses an address and a port. Each of these is a different answer to “who is allowed to join”, and it is usually the security answer.

Retention. What does the object hold between the send and the receive? This is the ladder, and it is the subject of this article.

Lifetime. When does the object cease to exist? Four regimes appear: descriptor-scoped, where the object dies with the last open file description; name-scoped, where a name persists but its contents never do; kernel-persistent, where the contents survive with no process attached; and filesystem-persistent, where they survive a reboot.

These three are not correlated in any useful way, and treating them as one produces most of the folklore. “Shared memory is fastest” is a retention claim used to answer a throughput question and it is only sometimes true; section 10 measures a case where a shared page is slower than a pipe. “System V IPC leaks” is a lifetime claim, true, and entirely unrelated to what those objects retain. “Use Unix sockets, they are local” is a rendezvous claim that happens also to buy two rungs of retention, which is the real reason to prefer them and not the one usually given.

One clarification about the coding rule, because it is what keeps the ladder from being an opinion. A mechanism's rung is the most structure a receiver can obtain from the mechanism alone, given nothing but the mechanism's own interface. If two programs agree that every message on a pipe begins with a four-byte length, they have a framed channel, but the pipe has not changed rung: a third program attaching to the same pipe would see bytes, and the kernel would not tell it otherwise. If two programs use a POSIX message queue, a third program can call mq_receive and get exactly one message without knowing anything about the sender's conventions. That difference is what the ladder measures, and it is the difference between a guarantee and a convention.

SECTION 04

K0: the shared page

The fastest mechanism is the one that keeps no record of anything. Every property people want from it has to be built on top, including the property of being able to read it at all.

Two processes map the same physical pages. There is no system call on the data path, no copy, and no bound on throughput other than memory.15,39,40 There is also no record. The kernel has arranged for both parties to address the same bytes and has then stepped out of the transaction entirely: it does not know that a write occurred, it will not tell the reader that anything changed, and it has no opinion about whether the bytes the reader sees were ever simultaneously true.

That last point is the one people underestimate, so the lab measured it. A writer stamps a single incrementing counter into every slot of a shared record; a reader takes snapshots. A snapshot containing two different counter values is a state that never existed at any instant. At a record of one 8-byte word, an aligned machine store, there were no such snapshots in 2,000. At two words the rate is 29.3%; at a kilobyte it is 97.0%, and the torn reads straddle a mean of 2.06 generations. The hardware gives you atomicity for exactly one aligned word and not one byte more.41,42 What the reader wants and cannot have from the mechanism is linearizability: the guarantee that every operation appears to take effect at a single instant between its invocation and its return.43

The repair is old. Lamport's 1977 note on concurrent reading and writing gives the construction now universally called a seqlock: the writer increments a counter to an odd value, writes, increments to even; the reader reads the counter, the record and the counter again, and retries if either the first read was odd or the two disagree.44,45 In the lab it removes every inconsistent snapshot. It also charges 543,019 retries per successful read against this particular writer, which holds the record dirty almost continuously. That figure is not a property of seqlocks; it is a property of a writer with a hundred-percent duty cycle, and it is worth quoting only to make the general point. Correctness at K0 is not free and it is not supplied. It is purchased, in a currency the interface never mentions.

Everything else at this rung has the same shape. Mutual exclusion is purchased with a futex, whose whole design is that the uncontended case never enters the kernel, so that the kernel's record is of contention only.46,47,48 Ordering between the write of a payload and the write of the flag that announces it is purchased with memory barriers, which the language must be persuaded to emit and which no system call will supply.49 Notification — the plain fact that something is there to read — is purchased with a separate object entirely, usually an eventfd, and section 10 shows what that costs. None of this is a Linux peculiarity: the POSIX interface for a shared memory object specifies how to create and size it and says nothing whatever about telling anyone that its contents changed.50

The modern high-performance interfaces have arrived back here deliberately. An io_uring instance is a pair of ring buffers mapped into both the process and the kernel, with memory barriers as the protocol and the completion queue as the only evidence that anything happened.51,52 It is the exokernel argument arriving by a different road: give the application the resource and let it impose its own abstraction.53 It is extremely fast for the same reason it is difficult: the kernel is one of the two parties, and the kernel has taken the K0 position.

SECTION 05

K1 and K2: a bit and a count

The signal is the oldest notification mechanism in Unix and it retains one bit. Everything built to replace it is the same object with a number in it instead.

A standard signal is a bit in a mask.54,55 If the target has SIGUSR1 blocked or is not scheduled, the first delivery sets the bit; the next nine hundred and ninety-nine find it already set and do nothing. The sending call returns success every time. There is no error, no counter, and no way for either party to discover afterwards how many events occurred.

The lab sent a thousand. One arrived.

Real-time signals, added by the 1993 realtime amendment,20,54 are queued: the kernel keeps an instance per send, delivers lowest-numbered first, and charges the queue against RLIMIT_SIGPENDING. All 1,000 arrived. This is the whole difference between K1 and K2 — a count survives, so N events stay N — and it is worth pausing on how narrow the improvement is. A count still distinguishes nothing about the individual events. Two different things that both increment the same counter are, to the receiver, the same thing twice.

The third bar in the figure is the more interesting one. With RLIMIT_SIGPENDING lowered to 64, the kernel accepted all 1,000 sends and delivered 64. It refused none of them. A bound on a queue is not the same thing as a refusal at the door, and a sender that checks its return values learns nothing from either. This is the general form of a failure that recurs at every rung in this article and gets its own section: a call that returns success has told you that the kernel accepted something, and nothing whatever about whether anyone will see it.

The rest of this group is the same K2 content in better packaging. A POSIX semaphore is a non-negative count with a queue of waiters.56,57 A System V semaphore set is an array of counts with atomic multi-operations and, uniquely in this whole vocabulary, an undo list the kernel applies if a process dies holding one.15,58 An eventfd is a 64-bit counter in a file description, which is the same object as the classical self-pipe trick with one object instead of two and with the enormous practical advantage that it composes with poll.59,60 Dijkstra's semaphore is sixty years old and has not been improved on as a primitive;61,62 what has been improved is the plumbing around it.

One member of the group is not about data at all. A pidfd is a descriptor that refers to a process and remains valid after that process exits.38 It exists because process identifiers are reused, so that between reading a pid and signalling it another program may have taken the number. That is a rendezvous bug, not a retention one, and it is the only mechanism here introduced to fix one.

SECTION 06

K3: the ordered stream

The pipe kept every byte and threw away every edge. Fifty years later that is still the default assumption of almost every program that talks to another one.

A pipe is a bounded ring of pages with a reader and a writer, and its contract is that bytes come out in the order they went in and none are lost or duplicated.34,63,64 It says nothing about where one write ends and the next begins. Four writers pushing records into one pipe produce a stream in which the records may be arbitrarily interleaved, and the reader has no way to tell.

Except that POSIX does make one promise, and it is a strange one. A write of PIPE_BUF bytes or fewer is atomic with respect to other writers.34,65 Above that size the guarantee lapses. PIPE_BUF is 4,096 bytes on this host and is required to be at least 512 anywhere. It is the only framing guarantee in the entire byte-stream family, it is expressed as a size rather than as a structure, and almost no wire protocol mentions it.

The measured cliff is exact. At 4,096 bytes, none of 240 records arrived mixed. At 8,192 bytes, 191 did — 79.6%. At a record the size of the whole pipe, 96.7%. Note the experimental design: the reader is throttled deliberately, because on Linux the pipe implementation holds its mutex across an entire write unless it has to sleep, so a large write into an empty pipe is atomic in practice and not in specification.63 A system that appears to work under light load and shreds its records under back-pressure is the characteristic pipe failure, and it is characteristic precisely because the guarantee is conditional in a way the interface does not expose.

Sockets of type SOCK_STREAM are the same rung with a different rendezvous. The lab pushed 4,000 messages of varying length through an AF_UNIX stream socket and asked one question of each receive: did this call return exactly one message?

The answer was no, 94 times out of 94. The largest single read returned 157 messages. Both framed socket types returned exactly one message on all 4,000 receives. This is not a defect in the stream socket; it is the rung. And the syscall count in the same figure is the reason the rung persists: the stream moved the same data in 94 calls where the framed types needed 4,000. Coalescing is the same property as boundary loss, seen from the cost side.

Two members of this group deserve separate mention. TCP over loopback is a byte stream between two processes on one machine that nonetheless instantiates the full transport state machine: sequence numbers, windows, retransmission timers, and a TIME_WAIT that the application did not ask for.66,67 Section 10 measures what that costs against a Unix socket doing the same job. And splice moves page references between a pipe and another descriptor without copying through user space,68 which is the K3 interface over a K0 mechanism — an arrangement whose sharpest consequence was CVE-2022-0847, in which an uninitialised flag on exactly this path let an unprivileged process write to files it could only read.69,70

SECTION 07

K4 and K5: frames, and what only the kernel can say

Above the stream, the kernel starts keeping the edges of a message. Above that, it starts adding things to the message that the sender was not permitted to write.

A framed carrier keeps the boundary. One send is one receive; the receiver does not parse, does not buffer, and cannot be confused by a peer that writes in two calls what it described in one. AF_UNIX datagram and sequenced-packet sockets do this, as do both families of message queue.71,72 The lab's measurement of this is unexciting because there is nothing to measure: 4,000 of 4,000, both types, no exceptions. That is the point of a guarantee.

The distinction that matters inside this group is between a frame and an attribute. A frame is something about the message's shape. An attribute is content the kernel adds, or vouches for, that the sender could not have serialised into the payload — and there are exactly three kinds of it in the standard vocabulary.

A priority the kernel orders by. POSIX message queues take an unsigned priority on send and deliver the highest first.72,73 The lab sent five messages tagged low, high, mid, high, low and received them high, high, mid, low, low. A priority field inside a JSON payload would have achieved nothing, because the ordering happens in the queue and the queue does not parse payloads. System V message queues do the same thing with a different shape: a signed long type per message, selectable on receive, which turns one queue into a set of channels.15,74

A capability. SCM_RIGHTS passes an open file description over an AF_UNIX socket, and what arrives in the receiver is not a number but an entry in its descriptor table.71,75 In the lab a process created an anonymous file with memfd_create,76 so that the object had no path anywhere in the filesystem, wrote to it, and sent the descriptor. The receiver read 40 bytes from an object it had no name for and could not have opened. No serialisation format can produce that, because the thing transferred is not a value. It is authority, in exactly the sense Dennis and Van Horn meant in 1966, and it is the mechanism that lets a privileged process open a resource and hand it to an unprivileged one without handing over the ability to open others.77,78 It is also the mechanism by which a careless privileged process becomes Hardy's confused deputy.79

An identity. SO_PEERCRED and SCM_CREDENTIALS report the process, user and group identifiers the kernel knows the peer to have.71,80 In the lab the sender's payload claimed to be pid 1 running as uid 31337; the kernel reported pid 221 and uid 0, which was the truth. This is the only field in the entire vocabulary that the sender is structurally unable to compose, and it is why local service authentication over a Unix socket can be a one-line getsockopt where the same service over TCP needs a credential system.

Both of the last two fail in a way worth noting, because it is silent. Over a TCP socket the lab's sendmsg accepted the SCM_RIGHTS control message without error and the receiver got 0 descriptors. The SO_PEERCRED call succeeded and returned pid 0, uid -1, gid -1 — an empty answer rather than an error. The socket API's generalisation over address families, which is what made networking programmable in 1983, has here produced an interface that compiles, runs, returns success, and does nothing.

SECTION 08

The boundary the ladder cannot cross

Every rung above the byte stream is available only between processes that share a kernel. This is not an implementation gap. It is what the rungs are made of.

Count the rungs by reach. 9 of the 32 mechanisms tabulated here sit above K3. Exactly 1 of them crosses a machine boundary: the UDP datagram, which keeps the frame and gives up order, delivery and duplicate suppression to do it.81 Everything else that keeps a frame, a priority, a descriptor or a credential is local-only.

The reason is structural. A frame that the kernel guarantees is a frame that one kernel guarantees, out of a data structure it owns, on behalf of two processes it scheduled. Between two machines there is no such object. There are two kernels, each with its own idea of what happened, and a network in between that is permitted to lose, duplicate and reorder. A descriptor cannot be passed because a descriptor is an index into a table in a kernel the receiver is not running on. Credentials cannot be vouched for because the vouching kernel is not the one being asked. Even the priority is unavailable, because ordering by priority requires a single queue and there is not one.

What is left, if you insist on reliability and order, is TCP: a byte stream, K3, the same rung as the pipe from 1973.66 The one interesting exception proves the rule: AF_VSOCK carries sockets between a virtual machine and its hypervisor, and it can offer richer local semantics than TCP precisely because there is still a single host underneath both.82 The entire apparatus of distributed systems engineering sits on top of that fact.

This is also the exact place where the socket abstraction's greatest strength turns into its most persistent trap. 4.2BSD made the local and remote cases look alike so that programs could be written once, and they can.18,83 But looking alike is not being alike. Waldo and colleagues put the argument in its sharpest form in 1994: the difference between local and distributed computing is not a difference of degree in latency but a difference in kind, in partial failure and in concurrency, and an abstraction that papers over it produces systems that work in testing and fail in a manner nobody designed for.84 Tanenbaum and van Renesse had made a narrower version of the same complaint about RPC six years earlier;85 Saltzer, Reed and Clark had made the most general version a decade before that, arguing that a function requiring the knowledge and help of the endpoints cannot be completely implemented in the communication system, and that a lower-level implementation of it can at best be a performance optimisation.86

The retention ladder is a restatement of the end-to-end argument in a form that can be looked up in a table. If a property is not on the rung your carrier occupies, it is not going to appear because you crossed a boundary; the boundary is where properties are lost, not gained. And since the boundary truncates every carrier to K3, every property above K3 that a distributed system needs is a property that distributed system will be implementing itself.

SECTION 09

Rebuilding above the ladder

Framing, typing, addressing and call semantics are the four things no rung supplies at a distance, so they are the four things every wire protocol contains.

Given a byte stream, a program that wants messages must put the boundaries back. The universal answer is a length prefix: a fixed-width integer, then that many bytes.87,88 It is a small thing, and the lab measured all three of its costs to see which one is real.

The bytes are negligible: 16,000 bytes of prefix on 1,834,393 bytes of body, or 0.865% of the stream. The system calls are not negligible, and they run in an unexpected direction. A naive reader that reads the four-byte header and then the body needs 8,000 receives for 4,000 messages, twice as many as the 4,000 that SOCK_SEQPACKET needs. A buffered reader over the same stream needs 973, four times fewer than the framed socket. The stream can be read in bulk precisely because it does not respect message edges; the framed socket cannot, because respecting them is its job. Reconstruction is not simply a tax. It is a trade, and which side wins depends on whether you are counting correctness or syscalls.

Typing is the second reconstruction, and no rung supplies any of it. What is on the wire is bytes; that they represent an unsigned 64-bit identifier and an IEEE 754 timestamp is an agreement. The lab encoded the same four fields four ways. A fixed-layout struct is 36 bytes and 518 nanoseconds to encode and decode. JSON89 is 66 bytes and 5,680 nanoseconds — 1.83 times the size and 11.0 times the time, for information the receiver mostly already knew.

That comparison is what the whole serialisation industry is about. A self-describing format carries the type information in every message;89,90 a schema-driven one moves it into an artefact both ends compiled against, so the wire carries field numbers rather than names.87,88 The second is cheaper on every message and converts the type problem into a versioning problem that lasts as long as the deployment does.91 Formats such as Cap'n Proto and FlatBuffers push further, arranging the encoding so that the received bytes can be addressed in place with no decode step at all — which is to say, they get back to K0 and inherit its problems along with its speed.92,93 There is also a security dimension that follows directly from the rung: a decoder that will construct whatever the encoder names has granted the sender a capability it never meant to, which is why language-native serialisation over an untrusted channel is a standing vulnerability class rather than an occasional bug.

The fourth reconstruction is call semantics, and it is the one that does not work. A remote procedure call presents arguments out and a result back, in the shape of a language construct that the transport cannot support.94,95 The idea is old — White's RFC 707 sketched it in 197696 — and Birrell and Nelson's 1984 implementation is where it became practical, with a stub generator, a binding service, and a transport protocol built for the request-response shape rather than borrowed from a stream. They were careful to say what could not be delivered: the semantics of a remote call cannot be made identical to a local one, because the callee can vanish. What the caller gets on a timeout is indistinguishable between a lost request and a lost reply, so the achievable guarantee is at-most-once, and everything stronger has to be built by the application out of idempotence and deduplication.84,94 That analysis was correct in 1984 and it is correct now; the intervening forty years produced ONC RPC,97,98 CORBA, Java RMI, SOAP and gRPC,99 and did not produce a way around it.

Two of this group's members are interesting because they answer the problem by moving the retainer rather than by rebuilding. A message bus interposes a broker in user space that holds typed, framed, addressed messages100 — genuine K4 retention, paid for with a second process and an extra crossing per message. Android's Binder goes the other way and puts the broker in the kernel, with descriptor-passing and caller credentials as first-class parts of the transaction, which is the K5 position generalised into a full object model.101 Wayland makes the same bet in user space, using descriptor passing over a Unix socket to hand graphics buffers between client and compositor rather than copying them.75,102 Both are answers to the same observation: if the kernel will not keep your structure, somebody has to.

SECTION 10

What the crossing costs

Latency is set by the wakeup, not by the copy, which is why the fastest mechanism on paper is not the fastest in a ping-pong.

The folklore ranks the mechanisms by copies: shared memory has none, a pipe has two, a socket has two and some protocol work, TCP has more. As a bandwidth model that is roughly right. As a latency model it is wrong, and it is wrong in a way that changes designs.

An eight-byte round trip through a pipe took a median of 3.29 microseconds. The same round trip through a shared page with an eventfd doorbell took 3.50 — 1.06 times as long, not a fraction. The shared page eliminated the copy of eight bytes, which was never the cost. What remained was two context switches and two trips through the scheduler, and the pipe was already doing those in one system call each way while the shared-memory arrangement needed a separate object to do the waking.15,59

Bulk transfer is the opposite regime and confirms the folklore. Copying 64 KiB buffers into a shared page ran at 34,709 MB/s against loopback TCP's 1,928, a factor of 18. The shared-page figure excludes synchronisation entirely, which is exactly the point: it is the number you get if the notification problem is already solved elsewhere, and section 4 is about how much solving it costs.

The two socket comparisons are worth reading as a pair. A Unix stream socket round trip took 5.23 microseconds; loopback TCP took 8.59, a factor of 1.64, for identical bytes between identical processes on the same host.67,71 The difference is the transport state machine that loopback TCP is obliged to run even though there is no network — including, unless the program disables it, the delayed-transmission behaviour that Nagle proposed for congested wide-area links and that has no business on a loopback round trip.103 Programs that connect to 127.0.0.1 for want of a local convention are paying that difference on every message, plus the ephemeral-port and TIME_WAIT accounting, and receiving in exchange an interface that cannot pass a descriptor or authenticate a peer.

All of these figures were measured on a machine with 1 CPU, so every one of them includes a context switch that a second core would sometimes hide. That makes the absolute numbers pessimistic and the ranking, if anything, conservative: on a multiprocessor a shared page with a spin-wait can beat a pipe on latency, at the price of burning a core. The structural claim survives either way, because it is about which cost dominates rather than about its size. Bershad and colleagues made the same observation for cross-domain calls in 1990, showing that most of the cost of a local RPC was not copying but control transfer and argument marshalling, and that removing the control transfer was where the order of magnitude lived.104,105 Liedtke's L4 work is the same finding pushed into the kernel's design.26

SECTION 11

How much it will hold, and what happens when it will not

Every retaining mechanism has a bound. The bounds span four orders of magnitude, none of them appear in any interface, and the behaviour at the bound differs by mechanism.

“The kernel will buffer it” is a design assumption with a number attached, and the number is usually unknown to the person making the assumption. The lab filled each mechanism with a non-blocking writer until it refused.

The smallest default here is the POSIX message queue at 10 messages — and note that its mq_msgsize maximum on this host is 8,192 bytes, so the bound is on count, not volume.72 A System V message queue took 256 messages of 64 bytes before refusing, because its bound is msgmnb in bytes: 16,384 of them.16 A pipe held 65,536 bytes by default and 1,048,576 after F_SETPIPE_SZ.34,106 A Unix stream socket held 180,224. Loopback TCP accepted 3,916,288 bytes, against an auto-tuned SO_SNDBUF of 3,939,840.80 That is a spread of roughly four orders of magnitude between the smallest and largest default in the same vocabulary on the same machine.

The behaviour at the bound differs too, and the differences are load-bearing. A blocking write to a full pipe sleeps, which propagates back-pressure to the producer — the pipeline's oldest and best property. A non-blocking write returns EAGAIN, which puts the decision in the application. A datagram socket may discard. A real-time signal queue, as section 5 showed, accepts the send and drops the signal. Three of those are visible to the sender and one is not, and the one that is not is the oldest.

Which brings the argument to the failure that recurs at every rung. What does it mean when a write returns success?

In the lab, a process filled a pipe with 65,536 bytes while the reader was alive and idle. Every write returned success. The reader then exited without having read one byte, and all 65,536 bytes ceased to exist. The writer learned about it on the next write, as EPIPE, and learned nothing at all about the bytes already lost. Over TCP the same shape at a larger scale: 3,924,480 bytes reported written, 0 ever read, and ECONNRESET on a subsequent attempt.5,66

A successful write says the kernel accepted custody of some bytes. It does not say they were read, will be read, or still exist. At every rung in this article, from the shared page to TCP, that is the strongest statement the interface makes, and every acknowledgement scheme ever written exists because it is not enough.

There is a related asymmetry in how the mechanisms report a peer's departure, and it does not follow the ladder. When a peer exited without saying anything, an AF_UNIX stream socket gave the receiver EOF and a sequenced-packet socket gave it EOF. A datagram socket on the same host, between the same two processes, gave nothing (blocked until the timeout). End-of-stream is a property of a connection, not of a frame, and a mechanism can be a rung higher on retention while being strictly worse at telling you the conversation is over.

SECTION 12

What survives the participants

The objects that remember the most are the objects nobody reclaims. Kernel persistence and kernel retention are different properties that happen to be spelled the same way in casual speech.

A pipe dies when its last descriptor closes. A System V shared memory segment does not die when its last attacher exits; it stays until somebody calls shmctl with IPC_RMID, or the machine reboots.15,16 That difference has nothing to do with what either object retains, and everything to do with which namespace holds the reference.

The lab created seven objects in a child process and let the child exit without cleaning up anything.

5 of 7 survived. The anonymous pipe and the memfd were reclaimed, because both are descriptor-scoped and there was no descriptor left, which the lab confirmed by looking for them under /proc after the child had gone.107 The FIFO node, the Unix socket path, the POSIX shared memory object, the POSIX message queue and the System V message queue all persisted.36,37,72 This is the practical content of the phrase “kernel-persistent”, and it is why ipcs output and /dev/shm listings on a long-lived host read like a sediment layer of every process that ever crashed there.

The FIFO is the instructive case. Its node survived holding nothing at all: a name in a directory, a mode bit saying it is a pipe, and no buffer, because the buffer only ever existed while both ends were open. The name persists and the contents never do — which is the exact inverse of a shared memory object, whose contents persist and whose name is optional. Two mechanisms that sit on adjacent rungs of retention and behave in opposite ways on lifetime.

Nothing in this is accidental; it is a difference in what the reference count is counting. Descriptor-scoped objects are counted by open file descriptions, which the kernel reclaims when a process exits, so the cleanup is automatic and the rendezvous is restricted to processes that can be handed a descriptor. Name-scoped and kernel-persistent objects are counted by entries in a namespace, which nothing reclaims, so the cleanup is manual and the rendezvous is open to anyone with the name and the permission. You get one or the other. The mechanisms that made themselves reachable by name made themselves un-reclaimable in the same stroke.

The rebuild burden is monotone in the rung by construction, and that is not the interesting part. E2's first version used an unthrottled reader and found zero tearing at every record size, which was not a refutation of the PIPE_BUF rule but an artefact: Linux holds the pipe mutex across a whole write unless it has to sleep, so with an empty pipe even a large write is atomic in practice. Throttling the reader so the pipe stayed full produced the cliff in figure 3. E4's first version sampled without yielding, and on a single-CPU host that meant the reader took thousands of samples of a frozen state per scheduling slice, so the reported rate was dominated by a handful of scheduling events rather than by the record width. Adding sched_yield between samples produced the monotone curve in figure 5. A third defect was found and kept: the harness for E5 originally deadlocked, because the echo child on a datagram socket never saw an end-of-stream when the parent closed its end. That is not a bug in the experiment, it is the finding that became part of E8.

# E1  What a signal retains.
#
# A standard signal is one bit of pending state per signal number.  A real-time
# signal is queued.  We send the same number of each to a process that is not
# yet listening, and count what is still there when it looks.
# ---------------------------------------------------------------------------

def e1_signal_retention(n_send=1000):
    results = {}

    for sig, name in ((signal.SIGUSR1, "SIGUSR1 (standard)"),
                      (signal.SIGRTMIN, "SIGRTMIN (real-time)")):
        ready_r, ready_w = os.pipe()      # child -> parent: "I am blocking"
        go_r, go_w = os.pipe()            # parent -> child: "drain now"
        count_r, count_w = os.pipe()      # child -> parent: how many arrived

        pid = os.fork()
        if pid == 0:                                        # ---- child
            try:
                os.close(ready_r); os.close(go_w); os.close(count_r)
                signal.pthread_sigmask(signal.SIG_BLOCK, {sig})
                os.write(ready_w, b"x")
                os.read(go_r, 1)                            # wait for sender
                got = 0
                while True:
                    # drain the pending set without blocking
                    if signal.sigtimedwait({sig}, 0) is None:
                        break
                    got += 1
                os.write(count_w, struct.pack("<Q", got))
            finally:
                os._exit(0)

        os.close(ready_w); os.close(go_r); os.close(count_w)
        os.read(ready_r, 1)                                 # child is blocking

        sent_ok = 0
        refused = 0
        for _ in range(n_send):
            try:
                os.kill(pid, sig)
                sent_ok += 1
            except OSError as exc:
                if exc.errno == errno.EAGAIN:
                    refused += 1
                else:
                    raise
        os.write(go_w, b"x")
        got = struct.unpack("<Q", os.read(count_r, 8))[0]
        os.waitpid(pid, 0)
        for fd in (ready_r, go_w, count_r):
            os.close(fd)

        results[name] = {"sent_attempted": n_send, "sent_accepted": sent_ok,
                         "refused_eagain": refused, "delivered": got,
                         "lost_silently": sent_ok - got}
        kv(f"{name}: accepted by kill()", sent_ok)
        kv(f"{name}: refused with EAGAIN", refused)
        kv(f"{name}: actually delivered", got)
        kv(f"{name}: accepted but never delivered", sent_ok - got)

    lim = resource.getrlimit(resource.RLIMIT_SIGPENDING)
    kv("RLIMIT_SIGPENDING (soft, hard)", lim)
    results["rlimit_sigpending"] = list(lim)

    # and the same send fails in the open instead of succeeding into a void.
    soft, hard = lim
    resource.setrlimit(resource.RLIMIT_SIGPENDING, (64, hard))
    try:
        ready_r, ready_w = os.pipe(); go_r, go_w = os.pipe()
        count_r, count_w = os.pipe()
        pid = os.fork()
        if pid == 0:
            try:

                signal.pthread_sigmask(signal.SIG_BLOCK, {signal.SIGRTMIN})

                got = 0
                while signal.sigtimedwait({signal.SIGRTMIN}, 0) is not None:
                    got += 1
                os.write(count_w, struct.pack("<Q", got))
            finally:
                os._exit(0)
        os.close(ready_w); os.close(go_r); os.close(count_w)

        ok = eag = 0
        for _ in range(n_send):

    kv("SIGRTMIN, queue bound lowered to 64: delivered", got)
    kv("SIGRTMIN, queue bound lowered to 64: lost silently", ok - got)

The only framing a pipe has

Four writers push fixed-size homogeneous records through one pipe while the reader drains slowly, so the buffer stays full and writers are forced to sleep mid-write. Identical pressure in every run; only the record size changes.

At PIPE_BUF (4,096 B) none of 240 records arrived mixed. At 8 KiB, 79.6%. At the pipe's whole capacity, 96.7%.
# E2  The only framing a pipe has.
#
# POSIX guarantees that a write of PIPE_BUF bytes or fewer to a pipe is atomic
# with respect to other writers.  Above that size the guarantee lapses.  Four
# writers each push fixed-size homogeneous records; the reader counts records
# that came back mixed.
# ---------------------------------------------------------------------------

def e2_pipe_atomicity(writers=4, records=60, sizes=(4096, 8192, 65536)):
    """Four writers push fixed-size homogeneous records through one pipe while
    the reader deliberately drains slowly, so the pipe stays full and writers
    are forced to sleep mid-write.  Identical pressure in every run; only the
    record size changes."""
    pipe_buf = select.PIPE_BUF
    out = {"PIPE_BUF": pipe_buf, "writers": writers, "runs": []}

    for size in sizes:
        r, w = os.pipe()
        capacity = fcntl.fcntl(w, F_GETPIPE_SZ)
        kids = []
        for i in range(writers):
            pid = os.fork()
            if pid == 0:
                os.close(r)
                payload = bytes([65 + i]) * size
                for _ in range(records):
                    off = 0
                    while off < size:
                        off += os.write(w, payload[off:])
                os.close(w)
                os._exit(0)
            kids.append(pid)
        os.close(w)

        want = writers * records * size
        buf = bytearray()
        reads = 0
        while len(buf) < want:
            chunk = os.read(r, 4096)
            if not chunk:
                break
            buf += chunk
            reads += 1
            if reads % 48 == 0:          # keep the pipe pressed against its bound
                time.sleep(0.004)
        os.close(r)
        for pid in kids:
            os.waitpid(pid, 0)

        torn = 0
        blocks = len(buf) // size
        for b in range(blocks):
            seg = buf[b * size:(b + 1) * size]
            if seg.count(seg[0]) != size:
                torn += 1
        rate = torn / blocks if blocks else 0.0
        out["runs"].append({"record_size": size, "pipe_capacity": capacity,
                            "records": blocks, "torn": torn, "torn_rate": rate,
                            "at_or_below_pipe_buf": size <= pipe_buf})
        kv(f"record {size:>6} B  (PIPE_BUF={pipe_buf}, capacity={capacity})",
           f"{blocks} records")
        kv(f"record {size:>6} B  records arriving mixed",
           f"{torn}  ({rate:.3%})")
    return out

Where the message boundary goes

The same 4,000 pseudo-random-length messages through AF_UNIX stream, sequenced-packet and datagram sockets. Of each receive, one question: did this call return exactly one message?

Stream: 94 receives, 0 exact, largest coalesce 157. Sequenced-packet and datagram: 4,000 of 4,000 exact.
# E3  Where the message boundary goes.
#
# The same sequence of writes is pushed through three AF_UNIX socket types.
# The receiver makes one large recv() per call and asks a single question:
# did this call return exactly one message?
# ---------------------------------------------------------------------------

def e3_boundaries(n_msgs=4000):
    rng = random.Random(SEED)
    msgs = [bytes([(i * 7 + 13) & 0xFF]) * rng.randint(16, 900)
            for i in range(n_msgs)]
    total = sum(len(m) for m in msgs)
    out = {"messages": n_msgs, "total_bytes": total, "kinds": {}}

    for kind, styp in (("SOCK_STREAM", socket.SOCK_STREAM),
                       ("SOCK_SEQPACKET", socket.SOCK_SEQPACKET),
                       ("SOCK_DGRAM", socket.SOCK_DGRAM)):
        a, b = socket.socketpair(socket.AF_UNIX, styp)
        pid = os.fork()
        if pid == 0:
            a.close()
            for m in msgs:
                b.sendall(m) if styp == socket.SOCK_STREAM else b.send(m)
            b.close()
            os._exit(0)
        b.close()

        recvs = 0
        got = bytearray()
        exact = 0
        idx = 0
        biggest = 0
        while len(got) < total:
            chunk = a.recv(1 << 16)
            if not chunk:
                break
            recvs += 1
            # how many whole messages does this single call complete?
            spans = 0
            probe = bytes(got) + chunk
            base = len(got)
            cursor = base
            j = idx
            while j < n_msgs and cursor + len(msgs[j]) <= len(probe):
                cursor += len(msgs[j])
                j += 1
                spans += 1
            if spans == 1 and cursor == len(probe):
                exact += 1
            biggest = max(biggest, spans)
            got += chunk
            idx = j
        a.close()
        os.waitpid(pid, 0)

        rec = {"recv_calls": recvs,
               "calls_returning_exactly_one_message": exact,
               "exact_rate": exact / recvs if recvs else 0.0,
               "max_messages_in_one_call": biggest,
               "bytes_received": len(got),
               "syscalls_per_message": recvs / n_msgs}
        out["kinds"][kind] = rec
        kv(f"{kind}: recv() calls for {n_msgs} messages", recvs)
        kv(f"{kind}: calls returning exactly one message",
           f"{exact}  ({rec['exact_rate']:.2%})")
        kv(f"{kind}: most messages in a single call", biggest)
    return out

A shared page keeps no record of the write

A writer stamps one counter into every slot of a shared record; a reader snapshots. Two different counters in one snapshot is a state that never existed. The reader yields to the writer between samples, because this host has one CPU and would otherwise re-read a frozen state thousands of times.

8 B: 0.0%. 1,024 B: 97.0%. A seqlock over the same page: 0.0%, at 543,019 retries per successful read against a writer with a near-100% duty cycle.
# E4  A shared page keeps no record of the write.
#
# The writer stamps the same counter into every slot of a shared record.  A
# consistent reader must never see two different counters in one snapshot.
# Run once bare, once behind a seqlock built in the same shared page.
# ---------------------------------------------------------------------------

def e4_shared_memory_tearing(widths=(1, 2, 8, 32, 128), samples=2000):
    """The writer stamps one counter into every slot of a shared record; a
    consistent reader must never see two different counters in one snapshot.
    Sweeping the record width shows where the hardware's free atomicity ends.
    The last width is then repeated behind a seqlock built in the same page."""
    out = {"samples": samples, "widths": {}}

    def run(slots, seqlock):
        size = 8 * (slots + 1)                  # slot 0 is the sequence word
        fd = os.memfd_create("e4", 0)
        os.ftruncate(fd, size)
        mm = mmap.mmap(fd, size, mmap.MAP_SHARED,
                       mmap.PROT_READ | mmap.PROT_WRITE)
        os.close(fd)
        stop_r, stop_w = os.pipe()

        pid = os.fork()
        if pid == 0:                                        # ---- writer
            os.close(stop_w)
            n = 0
            try:
                while True:
                    if n % 256 == 0:
                        rr, _, _ = select.select([stop_r], [], [], 0)
                        if rr:
                            break
                    n = (n + 1) & 0xFFFFFFFF
                    if seqlock:
                        struct.pack_into("<Q", mm, 0, 2 * n - 1)   # odd: busy
                    for s in range(1, slots + 1):
                        struct.pack_into("<Q", mm, 8 * s, n)
                    if seqlock:
                        struct.pack_into("<Q", mm, 0, 2 * n)       # even: done
            finally:
                os._exit(0)
        os.close(stop_r)

        inconsistent = retries = observed = 0
        spread = []
        fmt = "<%dQ" % slots
        for _ in range(samples):
            # one CPU: hand it to the writer, so each snapshot follows a fresh
            # slice of writing rather than re-reading a frozen state
            os.sched_yield()
            if seqlock:
                while True:
                    s1 = struct.unpack_from("<Q", mm, 0)[0]
                    if s1 & 1:
                        retries += 1
                        continue
                    vals = struct.unpack_from(fmt, mm, 8)
                    s2 = struct.unpack_from("<Q", mm, 0)[0]
                    if s1 == s2:
                        break
                    retries += 1
            else:
                vals = struct.unpack_from(fmt, mm, 8)
            observed += 1
            distinct = len(set(vals))
            if distinct != 1:
                inconsistent += 1
                spread.append(distinct)

        os.write(stop_w, b"x")
        os.waitpid(pid, 0)
        os.close(stop_w)
        mm.close()
        return {"slots": slots, "record_bytes": 8 * slots,
                "snapshots": observed, "inconsistent": inconsistent,
                "rate": inconsistent / observed if observed else 0.0,
                "mean_distinct_values_when_torn":
                    (sum(spread) / len(spread)) if spread else 0.0,
                "seqlock_retries": retries}

    for slots in widths:
        res = run(slots, False)
        out["widths"][slots] = res
        kv(f"record of {slots:>3} x 8 B ({8*slots:>4} B), bare: never existed",
           f"{res['inconsistent']:>5} / {res['snapshots']}  ({res['rate']:.3%})"
           + (f"   mean {res['mean_distinct_values_when_torn']:.2f} values"
              if res["inconsistent"] else ""))

    wide = max(widths)
    out["seqlock"] = run(wide, True)
    kv(f"record of {wide:>3} x 8 B, seqlock: inconsistent",
       f"{out['seqlock']['inconsistent']:>5} / {out['seqlock']['snapshots']}"
       f"  ({out['seqlock']['rate']:.3%})")
    kv("seqlock retries paid for those reads", out["seqlock"]["seqlock_retries"])
    out["retries_per_read"] = (out["seqlock"]["seqlock_retries"]
                               / out["seqlock"]["snapshots"])
    return out
