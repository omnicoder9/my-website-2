1. What state is, and why it needs managing

State is data that changes over time and that the UI depends on. React calls state a component's memory: values a component needs to remember between renders, such as the current input text or the selected image in a gallery [1]. Ordinary local variables do not survive a re-render, and changing them does not trigger one; state does both [1].

State management is the set of decisions about where each piece of data lives, who may change it, how changes are expressed, and how the rest of the application learns about those changes. As an application grows, React's guidance is to be intentional about how state is organised and how data flows between components, because redundant or duplicated state is a common source of bugs [2,3].

React's model is declarative: rather than imperatively editing the UI, you describe what the UI should look like for each state and React updates the screen to match [2]. Good state management therefore means choosing a small, consistent set of state from which everything visible can be computed.

Key idea. UI = f(state). Keep the inputs to f minimal and non-contradictory, put each one in the narrowest place that works, and compute everything else.

2. Different types of state

An important architectural distinction is that not all state is the same kind of thing. Data you own in the browser behaves differently from a copy of data owned by a server, and both differ from data that belongs in the URL. Treating them alike is the root of many over-engineered stores.

These properties call for caching, deduplication, background refetching and invalidation, which general-purpose client stores do not provide out of the box.

3. Built-in React state

3.1 Component state

Component state is state declared inside a component with a Hook such as useState or useReducer. It is private to that component instance: rendering the same component twice gives each copy its own isolated state [1].

React associates state with a component's position in the UI tree, not with the JSX variable. React preserves a component's state as long as the same component renders at the same position; if a different component type renders there, or the component is removed, its state is destroyed [11]. You can force a reset by giving the component a different key [11].

jsx
// Changing `key` tells React this is a different Chat, so its state resets.
function Messenger({ contactId }) {
  return <Chat key={contactId} contactId={contactId} />;
}

3.2 useState

useState(initialState) returns a pair: the current value and a set function that updates it and triggers a re-render [4]. Four rules explain nearly every useState surprise:

  1. State is a snapshot. Setting state does not change the variable in the already-running render; it requests a new render with the new value [12].
  2. Updates are batched. React waits until event-handler code has finished before processing state updates. To update the same state several times based on its previous value, pass an updater function such as n => n + 1 [13].
  3. Treat state as read-only. Objects and arrays in state should be replaced, not mutated; create a new copy and pass it to the setter [14].
  4. Bail-out by identity. If the new value is identical to the current one, as determined by Object.is, React will skip re-rendering the component and its children [4].
jsx
import { useState } from 'react';

export default function Counter() {
  const [count, setCount] = useState(0);

  function addThree() {
    // Wrong: each call sees the same snapshot, so the result is count + 1.
    // setCount(count + 1); setCount(count + 1); setCount(count + 1);

    // Right: updater functions are queued and applied in order.
    setCount(c => c + 1);
    setCount(c => c + 1);
    setCount(c => c + 1);
  }

  return <button onClick={addThree}>Count: {count}</button>;
}

For expensive initial values, pass the function itself (useState(createInitialTodos)), not its result; React only calls an initializer function during the first render [4].

jsx
const [form, setForm] = useState({ name: '', address: { city: '' } });

// Immutable nested update: copy each level you change.
setForm(prev => ({
  ...prev,
  address: { ...prev.address, city: 'Lisbon' },
}));

3.3 useReducer

When many event handlers update the same state in related ways, React recommends consolidating the logic into a reducer: a function (state, action) => nextState that lives outside the component [15]. Event handlers then dispatch actions that describe what happened rather than how to change the state [15]. Reducers must be pure: given the same inputs they return the same output, without side effects or mutation [15,16].

The signature is useReducer(reducer, initialArg, init?); it returns [state, dispatch] [16].

jsx
import { useReducer } from 'react';

const initialState = { items: [], nextId: 1 };

function todosReducer(state, action) {
  switch (action.type) {
    case 'added':
      return {
        items: [...state.items, { id: state.nextId, text: action.text, done: false }],
        nextId: state.nextId + 1,
      };
    case 'toggled':
      return {
        ...state,
        items: state.items.map(t => (t.id === action.id ? { ...t, done: !t.done } : t)),
      };
    case 'deleted':
      return { ...state, items: state.items.filter(t => t.id !== action.id) };
    default:
      throw new Error(`Unknown action: ${action.type}`);
  }
}

export default function Todos() {
  const [state, dispatch] = useReducer(todosReducer, initialState);
  return (
    <>
      <button onClick={() => dispatch({ type: 'added', text: 'Write article' })}>Add</button>
      <ul>
        {state.items.map(t => (
          <li key={t.id}>
            <label>
              <input type="checkbox" checked={t.done}
                     onChange={() => dispatch({ type: 'toggled', id: t.id })} />
              {t.text}
            </label>
            <button onClick={() => dispatch({ type: 'deleted', id: t.id })}>×</button>
          </li>
        ))}
      </ul>
    </>
  );
}

Because the reducer is a plain function, it can be unit-tested without rendering anything. The same pattern underlies Redux, which is why moving from useReducer to Redux Toolkit is usually straightforward.

3.4 Lifting state up

When two components need to change together, remove the state from both, move it to their closest common parent, and pass it down via props [17]. React describes the result as making each piece of state have a single "source of truth" and distinguishes controlled components (driven by props) from uncontrolled ones (driven by their own local state) [17].

jsx
import { useState } from 'react';

function Panel({ title, isActive, onShow, children }) {
  return (
    <section>
      <h3>{title}</h3>
      {isActive ? <p>{children}</p> : <button onClick={onShow}>Show</button>}
    </section>
  );
}

export default function Accordion() {
  // Lifted: the parent decides which single panel is open.
  const [activeIndex, setActiveIndex] = useState(0);
  return (
    <>
      <Panel title="About" isActive={activeIndex === 0} onShow={() => setActiveIndex(0)}>
        A component library.
      </Panel>
      <Panel title="Etymology" isActive={activeIndex === 1} onShow={() => setActiveIndex(1)}>
        From the Greek for "to change".
      </Panel>
    </>
  );
}

3.5 Derived state

Derived state is any value that can be computed from existing props or state. React's guidance is direct: if you can calculate something during rendering, do not put it in state, and do not use an Effect to synchronise it [3,18]. Storing redundant copies leads to values that drift out of sync. The documented principles for structuring state are: group related state, avoid contradictions, avoid redundant state, avoid duplication, and avoid deeply nested state [3].

jsx
import { useEffect, useMemo, useState } from 'react';

// ❌ Redundant state kept in sync by an Effect: extra render, easy to get wrong.
function ProductListBad({ products, query }) {
  const [visible, setVisible] = useState([]);
  useEffect(() => {
    setVisible(products.filter(p => p.name.includes(query)));
  }, [products, query]);
  return <List items={visible} />;
}

// ✅ Derived during render.
function ProductList({ products, query }) {
  const visible = products.filter(p => p.name.includes(query));
  return <List items={visible} />;
}

// ✅ If the calculation is genuinely expensive, memoise it.
function BigProductList({ products, query }) {
  const visible = useMemo(
    () => products.filter(p => p.name.includes(query)),
    [products, query]
  );
  return <List items={visible} />;
}

useMemo caches a calculation between re-renders and should be used only as a performance optimisation; code should still work without it [19]. A related pattern is storing an ID rather than a copy of a selected object, then deriving the object from the list, which prevents duplicated data from diverging [3].

3.6 Context API

Passing props through many intermediate components ("prop drilling") becomes verbose. Context lets a parent make information available to any component in the tree below it, however deep, without passing it explicitly through props [20]. The API is three steps: create a context, provide a value, and read it with useContext [20,21]. In React 19 you can render <ThemeContext value={…}> directly as the provider [21].

jsx
import { createContext, useContext, useMemo, useState } from 'react';

const ThemeContext = createContext(null);

export function ThemeProvider({ children }) {
  const [theme, setTheme] = useState('light');
  // Memoise so consumers do not re-render when the provider's parent re-renders.
  const value = useMemo(() => ({ theme, setTheme }), [theme]);
  return <ThemeContext value={value}>{children}</ThemeContext>;
}

export function useTheme() {
  const ctx = useContext(ThemeContext);
  if (ctx === null) throw new Error('useTheme must be used inside <ThemeProvider>');
  return ctx;
}

function ToggleButton() {
  const { theme, setTheme } = useTheme();
  return (
    <button onClick={() => setTheme(t => (t === 'light' ? 'dark' : 'light'))}>
      Theme: {theme}
    </button>
  );
}

Context is a transport mechanism, not a store. React automatically re-renders all the children that use a particular context, starting from the provider that receives a different value, and the comparison uses Object.is [21]. Passing a new object literal on every render therefore re-renders every consumer; memoising the value (as above) avoids this [21]. Context has no built-in selectors, so a component that reads one field re-renders when any field changes. For frequently changing, widely shared data, a store with selector-based subscriptions is usually a better fit.

React documents combining useReducer with context to scale up: one context for the state and another for dispatch, so components that only dispatch do not re-render on state changes [22].

jsx
const TasksContext = createContext(null);
const TasksDispatchContext = createContext(null);

export function TasksProvider({ children }) {
  const [tasks, dispatch] = useReducer(tasksReducer, initialTasks);
  return (
    <TasksContext value={tasks}>
      <TasksDispatchContext value={dispatch}>{children}</TasksDispatchContext>
    </TasksContext>
  );
}
export const useTasks = () => useContext(TasksContext);
export const useTasksDispatch = () => useContext(TasksDispatchContext);

3.7 Bridging to external stores

State that lives outside React (a third-party store, a browser API such as navigator.onLine) is read safely with useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot?) [23]. getSnapshot must return the same value if the store has not changed; returning a new object on every call causes an error or infinite loop warning [23]. Libraries such as Zustand and React Redux build on this primitive, and it is the right tool when writing your own small store.

jsx
import { useSyncExternalStore } from 'react';

function subscribe(callback) {
  window.addEventListener('online', callback);
  window.addEventListener('offline', callback);
  return () => {
    window.removeEventListener('online', callback);
    window.removeEventListener('offline', callback);
  };
}

export function useOnlineStatus() {
  return useSyncExternalStore(
    subscribe,
    () => navigator.onLine,   // client snapshot
    () => true                // server snapshot (SSR)
  );
}

4.1 Redux

Redux keeps the whole application's global state in a single store and is defined by three principles: a single source of truth (one object tree in one store), state is read-only (the only way to change it is to emit an action, an object describing what happened), and changes are made with pure functions (reducers) [24]. This gives Redux its predictability: every change is an explicit, serialisable event, which enables logging, replay and time-travel debugging.

js
// "Classic" Redux shown for understanding only; prefer Redux Toolkit (next section).
const initial = { value: 0 };

function counterReducer(state = initial, action) {
  switch (action.type) {
    case 'counter/incremented':
      return { ...state, value: state.value + 1 };
    case 'counter/amountAdded':
      return { ...state, value: state.value + action.payload };
    default:
      return state;
  }
}

The Redux style guide lists as essential rules: do not mutate state, reducers must not have side effects, and do not put non-serialisable values in state or actions [25]. It also advises modelling actions as events rather than setters [25].

4.2 Redux Toolkit

Redux Toolkit (RTK) is the official, recommended way to write Redux logic today [6]. The original createStore is marked deprecated to steer users towards RTK [6]. RTK's configureStore sets up the store with good defaults, including the thunk middleware and development-time checks for accidental mutation and non-serialisable values [6,26]. createSlice generates action creators and action types from reducer definitions and uses Immer internally, so you can write "mutating" logic that is converted into correct immutable updates [27,28].

ts
// store.ts
import { configureStore, createSlice, type PayloadAction } from '@reduxjs/toolkit';

type CartItem = { id: string; price: number; qty: number };
type CartState = { items: CartItem[] };

const cartSlice = createSlice({
  name: 'cart',
  initialState: { items: [] } as CartState,
  reducers: {
    itemAdded(state, action: PayloadAction<Omit<CartItem, 'qty'>>) {
      const existing = state.items.find(i => i.id === action.payload.id);
      if (existing) existing.qty += 1;           // Immer turns this into an immutable update
      else state.items.push({ ...action.payload, qty: 1 });
    },
    itemRemoved(state, action: PayloadAction<string>) {
      state.items = state.items.filter(i => i.id !== action.payload);
    },
  },
  selectors: {
    selectTotal: state => state.items.reduce((sum, i) => sum + i.price * i.qty, 0),
  },
});

export const { itemAdded, itemRemoved } = cartSlice.actions;
export const { selectTotal } = cartSlice.selectors;

export const store = configureStore({ reducer: { cart: cartSlice.reducer } });
export type RootState = ReturnType<typeof store.getState>;
export type AppDispatch = typeof store.dispatch;
tsx
// App.tsx
import { Provider, useDispatch, useSelector } from 'react-redux';
import { store, itemAdded, selectTotal, type RootState } from './store';

function CartTotal() {
  const total = useSelector((s: RootState) => selectTotal(s));
  return <p>Total: {total.toFixed(2)}</p>;
}

function AddButton() {
  const dispatch = useDispatch();
  return <button onClick={() => dispatch(itemAdded({ id: 'book', price: 12.5 }))}>Add book</button>;
}

export default function App() {
  return (
    <Provider store={store}>
      <AddButton />
      <CartTotal />
    </Provider>
  );
}

4.3 Zustand

Zustand is a small, fast store built around hooks. create returns a hook; components select the slice of state they need and re-render only when that slice changes. No context provider is required [5]. When a selector returns a new object or array each time, wrap it in useShallow to compare results shallowly and avoid unnecessary re-renders [29]. The persist middleware saves store data to storage such as localStorage [30].

ts
import { create } from 'zustand';
import { persist } from 'zustand/middleware';
import { useShallow } from 'zustand/react/shallow';

type Prefs = {
  theme: 'light' | 'dark';
  fontSize: number;
  setTheme: (t: Prefs['theme']) => void;
  bumpFont: () => void;
};

export const usePrefs = create<Prefs>()(
  persist(
    set => ({
      theme: 'light',
      fontSize: 16,
      setTheme: theme => set({ theme }),
      bumpFont: () => set(s => ({ fontSize: s.fontSize + 1 })),
    }),
    { name: 'prefs' } // localStorage key
  )
);

// Re-renders only when `theme` changes.
function ThemeLabel() {
  const theme = usePrefs(s => s.theme);
  return <span>{theme}</span>;
}

// Selecting several fields: useShallow avoids re-rendering on unrelated changes.
function FontControls() {
  const { fontSize, bumpFont } = usePrefs(
    useShallow(s => ({ fontSize: s.fontSize, bumpFont: s.bumpFont }))
  );
  return <button onClick={bumpFont}>A+ ({fontSize}px)</button>;
}

4.4 MobX

MobX makes state observable and automatically tracks which computations and components use which data. Its philosophy is that anything that can be derived from the application state should be derived, automatically [31]. It distinguishes observable state, actions that modify it, and derivations: computed values and reactions such as rendering [31]. With mobx-react-lite, wrapping a component in observer makes it re-render precisely when the observables it read during the last render change [32].

tsx
import { makeAutoObservable } from 'mobx';
import { observer } from 'mobx-react-lite';

class TimerStore {
  secondsPassed = 0;
  constructor() {
    makeAutoObservable(this); // fields → observable, getters → computed, methods → actions
  }
  increase() { this.secondsPassed += 1; }
  reset() { this.secondsPassed = 0; }
  get minutes() { return Math.floor(this.secondsPassed / 60); }
}

const timer = new TimerStore();
setInterval(() => timer.increase(), 1000);

const TimerView = observer(({ store }: { store: TimerStore }) => (
  <button onClick={() => store.reset()}>
    {store.minutes} min {store.secondsPassed % 60} s
  </button>
));

export default function App() {
  return <TimerView store={timer} />;
}

4.5 Jotai

Jotai takes an atomic, bottom-up approach to global React state: state is built by combining small atoms, and re-renders are optimised based on atom dependencies [33]. An atom config is created with atom(initialValue); a derived atom is created by passing a read function that calls get on other atoms, and it updates when its dependencies change [34]. Its model is described as inspired by Recoil [33], which makes it a natural migration path for Recoil users.

tsx
import { atom, useAtom, useAtomValue, useSetAtom } from 'jotai';

const priceAtom = atom(10);
const qtyAtom = atom(1);
const totalAtom = atom(get => get(priceAtom) * get(qtyAtom));    // derived, read-only
const resetAtom = atom(null, (_get, set) => {                     // write-only action atom
  set(priceAtom, 10);
  set(qtyAtom, 1);
});

function Qty() {
  const [qty, setQty] = useAtom(qtyAtom);
  return <input type="number" value={qty} onChange={e => setQty(Number(e.target.value))} />;
}

function Total() {
  const total = useAtomValue(totalAtom); // re-renders only when total changes
  return <strong>{total}</strong>;
}

function Reset() {
  const reset = useSetAtom(resetAtom);   // never re-renders on state changes
  return <button onClick={reset}>Reset</button>;
}

4.6 Recoil (legacy)

Recoil, created at Meta, introduced atoms (units of shared state) and selectors (pure derived state) as a graph that flows into React components [35]. Its GitHub repository has since been archived and is read-only, so it receives no further development [36]. It should be treated as a legacy choice: do not start new projects on it, and plan migrations for existing ones. Because Jotai's model was inspired by Recoil, it is a natural destination [33].

4.7 XState

XState models logic as finite state machines and statecharts and runs them as actors [37]. Statecharts, introduced by David Harel, extend finite state machines with hierarchy (nested states), concurrency (parallel regions) and communication, which keeps complex behaviour manageable [38]. The benefit in UI code is that impossible states become unrepresentable: a request cannot be both "loading" and "error" because the machine is in exactly one state per region. The @xstate/react package provides useMachine to run a machine in a component [39].

tsx
import { setup, assign, fromPromise } from 'xstate';
import { useMachine } from '@xstate/react';

const fetchUser = fromPromise(async ({ input }: { input: { id: string } }) => {
  const res = await fetch(`/api/users/${input.id}`);
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json() as Promise<{ name: string }>;
});

const userMachine = setup({
  types: {
    context: {} as { id: string; user?: { name: string }; error?: string },
    events: {} as { type: 'FETCH' } | { type: 'RETRY' },
  },
  actors: { fetchUser },
}).createMachine({
  id: 'user',
  context: { id: '42' },
  initial: 'idle',
  states: {
    idle: { on: { FETCH: 'loading' } },
    loading: {
      invoke: {
        src: 'fetchUser',
        input: ({ context }) => ({ id: context.id }),
        onDone: { target: 'success', actions: assign({ user: ({ event }) => event.output }) },
        onError: { target: 'failure', actions: assign({ error: ({ event }) => String(event.error) }) },
      },
    },
    success: {},
    failure: { on: { RETRY: 'loading' } },
  },
});

export function UserCard() {
  const [snapshot, send] = useMachine(userMachine);
  if (snapshot.matches('idle')) return <button onClick={() => send({ type: 'FETCH' })}>Load</button>;
  if (snapshot.matches('loading')) return <p>Loading…</p>;
  if (snapshot.matches('failure'))
    return <p>{snapshot.context.error} <button onClick={() => send({ type: 'RETRY' })}>Retry</button></p>;
  return <p>Hello, {snapshot.context.user?.name}</p>;
}

For plain data fetching, a server-state library (section 6) is usually simpler; XState shines for multi-step flows such as wizards, checkout, media players and connection lifecycles.

4.8 Valtio

Valtio wraps a plain object in a JavaScript Proxy; you mutate the proxy directly and Valtio tracks the changes [40]. In components, useSnapshot returns an immutable snapshot and re-renders only when the parts of state the component actually accessed have changed [41]. The rule of thumb is: read from snapshots in render, mutate the proxy in callbacks [41].

tsx
import { proxy, useSnapshot } from 'valtio';

const state = proxy({ count: 0, todos: [] as { id: number; text: string }[] });

const actions = {
  inc: () => { state.count++; },
  addTodo: (text: string) => { state.todos.push({ id: Date.now(), text }); },
};

export function Counter() {
  const snap = useSnapshot(state);   // read from the snapshot
  return <button onClick={actions.inc}>{snap.count}</button>; // mutate the proxy
}

5. URL, form and persistent state

5.1 URL state

Search filters, sort order, the selected tab and pagination often belong in the URL, so that they survive a reload, can be bookmarked or shared, and work with the back button. React Router's useSearchParams returns the current URLSearchParams and a function to update them [8]. Treat the URL as the source of truth and derive everything else from it.

tsx
import { useSearchParams } from 'react-router';

export function ProductFilters() {
  const [params, setParams] = useSearchParams();
  const page = Number(params.get('page') ?? '1');
  const q = params.get('q') ?? '';

  return (
    <>
      <input
        value={q}
        onChange={e =>
          setParams(prev => {
            const next = new URLSearchParams(prev);
            next.set('q', e.target.value);
            next.set('page', '1'); // reset paging when the filter changes
            return next;
          })
        }
      />
      <button onClick={() => setParams(prev => {
        const next = new URLSearchParams(prev);
        next.set('page', String(page + 1));
        return next;
      })}>
        Next page ({page + 1})
      </button>
    </>
  );
}

5.2 Form state

Forms combine field values, validation errors, touched/dirty flags and submission status. React Hook Form manages this with useForm, registering inputs via register and relying on uncontrolled inputs to minimise re-renders [9]. React 19 also offers useActionState, which updates state from the result of a form action and exposes a pending flag [42].

tsx
import { useForm } from 'react-hook-form';

type Inputs = { email: string; age: number };

export function SignupForm() {
  const { register, handleSubmit, formState: { errors, isSubmitting } } = useForm<Inputs>();

  async function onSubmit(data: Inputs) {
    await fetch('/api/signup', { method: 'POST', body: JSON.stringify(data) });
  }

  return (
    <form onSubmit={handleSubmit(onSubmit)} noValidate>
      <input {...register('email', { required: 'Email is required', pattern: { value: /\S+@\S+/, message: 'Invalid email' } })} />
      {errors.email && <p role="alert">{errors.email.message}</p>}

      <input type="number" {...register('age', { valueAsNumber: true, min: { value: 18, message: 'Must be 18+' } })} />
      {errors.age && <p role="alert">{errors.age.message}</p>}

      <button disabled={isSubmitting}>Sign up</button>
    </form>
  );
}

5.3 Persistent state

State that must outlive the page goes either to the backend (which then makes it server state) or to browser storage. localStorage stores string key/value pairs that persist across browser sessions for the page's origin [10]. Values must be serialised (for example with JSON.stringify), and other tabs on the same origin are notified of changes through the storage event [43]. Storage access is synchronous and can throw (for example in some private-browsing modes), so guard it.

tsx
import { useSyncExternalStore, useCallback } from 'react';

function subscribe(cb: () => void) {
  window.addEventListener('storage', cb);           // other tabs
  window.addEventListener('local-storage', cb);     // this tab (custom event below)
  return () => {
    window.removeEventListener('storage', cb);
    window.removeEventListener('local-storage', cb);
  };
}

export function useLocalStorage(key: string, fallback: string) {
  const value = useSyncExternalStore(
    subscribe,
    () => { try { return localStorage.getItem(key) ?? fallback; } catch { return fallback; } },
    () => fallback
  );
  const setValue = useCallback((v: string) => {
    try { localStorage.setItem(key, v); } catch { /* quota or disabled */ }
    window.dispatchEvent(new Event('local-storage'));
  }, [key]);
  return [value, setValue] as const;
}

Note that the snapshot here is a string, so getSnapshot returns a stable value as useSyncExternalStore requires [23]. Parsing JSON inside getSnapshot would return a new object on every call; parse in the consumer or cache the parsed value instead. For stores, Zustand's persist middleware packages this pattern [30].

6. Server-state and data-fetching libraries

These libraries solve a different problem from general-purpose client state management. They manage a cache of remote data: deduplicating requests, deciding when data is stale, refetching in the background, retrying failures, and invalidating after mutations. Putting fetched data into Redux or Zustand by hand means re-implementing all of that.

6.1 TanStack Query (React Query)

TanStack Query handles fetching, caching, synchronising and updating server state [7]. Queries are identified by a queryKey and fetched by a queryFn. Its documented defaults are aggressive but sensible: cached data is considered stale immediately (staleTime: 0), stale queries are refetched in the background on mount, window refocus and network reconnect; inactive queries are garbage-collected after five minutes (gcTime); and failed queries are retried three times with exponential backoff [44]. After a mutation, queryClient.invalidateQueries marks matching queries stale and refetches active ones [45,46].

tsx
import { QueryClient, QueryClientProvider, useMutation, useQuery, useQueryClient } from '@tanstack/react-query';

const queryClient = new QueryClient();

type Account = { id: string; balance: number };

function useAccounts() {
  return useQuery({
    queryKey: ['accounts'],
    queryFn: async (): Promise<Account[]> => {
      const res = await fetch('/api/accounts');
      if (!res.ok) throw new Error('Failed to load accounts');
      return res.json();
    },
    staleTime: 30_000, // treat as fresh for 30 s
  });
}

function Accounts() {
  const qc = useQueryClient();
  const { data, isPending, isError, error, isFetching } = useAccounts();

  const deposit = useMutation({
    mutationFn: (v: { id: string; amount: number }) =>
      fetch(`/api/accounts/${v.id}/deposit`, { method: 'POST', body: JSON.stringify(v) }),
    onSuccess: () => qc.invalidateQueries({ queryKey: ['accounts'] }),
  });

  if (isPending) return <p>Loading…</p>;
  if (isError) return <p>{error.message}</p>;
  return (
    <ul aria-busy={isFetching}>
      {data.map(a => (
        <li key={a.id}>
          {a.id}: {a.balance}
          <button disabled={deposit.isPending} onClick={() => deposit.mutate({ id: a.id, amount: 10 })}>+10</button>
        </li>
      ))}
    </ul>
  );
}

export default function App() {
  return <QueryClientProvider client={queryClient}><Accounts /></QueryClientProvider>;
}

6.2 SWR

SWR is a React Hooks library for data fetching from Vercel. Its name comes from stale-while-revalidate, an HTTP cache invalidation strategy described in RFC 5861: return cached (stale) data first, then send the fetch request (revalidate), and finally deliver up-to-date data [47,48]. The core API is useSWR(key, fetcher) [47].

tsx
import useSWR from 'swr';

const fetcher = (url: string) => fetch(url).then(r => {
  if (!r.ok) throw new Error(r.statusText);
  return r.json();
});

export function Profile() {
  const { data, error, isLoading, mutate } = useSWR('/api/user', fetcher);
  if (error) return <p>Failed to load</p>;
  if (isLoading) return <p>Loading…</p>;
  return <p>Hello {data.name} <button onClick={() => mutate()}>Refresh</button></p>;
}

6.3 RTK Query

RTK Query is a data-fetching and caching tool included in Redux Toolkit. You define endpoints with createApi, typically using fetchBaseQuery, and it auto-generates React hooks for each endpoint and stores the cache in the Redux store [49]. Cache invalidation is declarative through tags: queries provide tags and mutations invalidate them [49]. It is the natural choice when an application already uses Redux.

ts
import { createApi, fetchBaseQuery } from '@reduxjs/toolkit/query/react';
import { configureStore } from '@reduxjs/toolkit';

type Post = { id: number; title: string };

export const api = createApi({
  reducerPath: 'api',
  baseQuery: fetchBaseQuery({ baseUrl: '/api' }),
  tagTypes: ['Post'],
  endpoints: build => ({
    getPosts: build.query<Post[], void>({
      query: () => 'posts',
      providesTags: ['Post'],
    }),
    addPost: build.mutation<Post, Partial<Post>>({
      query: body => ({ url: 'posts', method: 'POST', body }),
      invalidatesTags: ['Post'], // triggers a refetch of getPosts
    }),
  }),
});

export const { useGetPostsQuery, useAddPostMutation } = api;

export const store = configureStore({
  reducer: { [api.reducerPath]: api.reducer },
  middleware: getDefault => getDefault().concat(api.middleware),
});

6.4 Apollo Client

Apollo Client is a GraphQL client that manages both remote and local data. Its InMemoryCache stores results in a normalised form, splitting responses into individual objects identified by __typename and id so that an update to one object is reflected everywhere it appears [50,51].

tsx
import { ApolloClient, HttpLink, InMemoryCache, gql } from '@apollo/client';
import { ApolloProvider, useQuery } from '@apollo/client/react';

const client = new ApolloClient({
  link: new HttpLink({ uri: '/graphql' }),
  cache: new InMemoryCache(),
});

const GET_DOGS = gql`
  query GetDogs {
    dogs { id breed }
  }
`;

function Dogs() {
  const { loading, error, data } = useQuery(GET_DOGS);
  if (loading) return <p>Loading…</p>;
  if (error) return <p>Error: {error.message}</p>;
  return <ul>{data.dogs.map((d: { id: string; breed: string }) => <li key={d.id}>{d.breed}</li>)}</ul>;
}

export default function App() {
  return <ApolloProvider client={client}><Dogs /></ApolloProvider>;
}

6.5 Relay

Relay is a JavaScript framework for fetching and managing GraphQL data in React applications, developed at Meta [52]. Each component declares the data it needs in a GraphQL fragment colocated with the component; a compiler combines fragments into efficient queries ahead of time and generates types [52]. Relay is opinionated and works best with a server that follows its conventions, but rewards that with strong consistency and performance at scale.

tsx
import { graphql, useFragment, useLazyLoadQuery } from 'react-relay';

function UserName({ user }) {
  const data = useFragment(
    graphql`
      fragment UserName_user on User {
        name
      }
    `,
    user
  );
  return <h2>{data.name}</h2>;
}

export function ProfilePage({ id }) {
  const data = useLazyLoadQuery(
    graphql`
      query ProfilePageQuery($id: ID!) {
        user(id: $id) {
          ...UserName_user
        }
      }
    `,
    { id }
  );
  return <UserName user={data.user} />;
}

7. Choosing an approach

A practical decision procedure, consistent with React's guidance to keep state minimal and close to where it is used [3,17]:

  1. Can it be computed? Then it is derived state. Compute it during render [18].
  2. Does it come from a server? Use a server-state library (TanStack Query, SWR, RTK Query, Apollo or Relay), not a client store.
  3. Should it survive reload or be shareable as a link? Put it in the URL.
  4. Is it a form? Use a form library or React 19 actions.
  5. Is it used by one component? useState, or useReducer if updates are complex.
  6. Is it shared by a few nearby components? Lift it to the closest common parent.
  7. Is it shared widely but changes rarely? Context.
  8. Is it shared widely and changes often? A store: Zustand, Redux Toolkit, Jotai, MobX or Valtio.
  9. Does it have many explicit modes and transitions? XState.
  10. Must it outlive the session? Persist to storage or the backend.

8. Common pitfalls

  • Mutating state. state.items.push(x); setState(state) keeps the same reference, so React may skip the update [4,14]. Copy, or use Immer/RTK.
  • Stale closures. Reading count inside an async callback captures the snapshot from that render [12]. Use updater functions or refs.
  • Syncing state with Effects. An Effect that only sets state from other state is redundant derived state [18].
  • Mirroring props in state. useState(props.color) ignores later prop changes, because the initial value is only used on the first render [3].
  • Unmemoised context values. A fresh object literal as the provider value re-renders every consumer [21].
  • Server data in a client store. Hand-rolled loading flags and refetch logic grow into an incomplete cache; use a server-state library [7].
  • Unstable selectors. Selectors that return new objects cause re-renders on every store change; use useShallow or memoised selectors [29].
  • Contradictory flags. isLoading and isError both true; replace boolean soup with a single status or a state machine [3,37].

Exercise 4 · Write a reducer

Write a reducer for a stopwatch with actions start, stop, tick (adds 1 second only while running) and reset. Then wire it to a component with useReducer and an interval. Write one plain test for the reducer.

Show solution

import { useEffect, useReducer } from 'react';

const initial = { running: false, seconds: 0 };

export function stopwatch(state, action) {
  switch (action.type) {
    case 'start': return { ...state, running: true };
    case 'stop':  return { ...state, running: false };
    case 'tick':  return state.running ? { ...state, seconds: state.seconds + 1 } : state;
    case 'reset': return initial;
    default: throw new Error(`Unknown action ${action.type}`);
  }
}

export default function Stopwatch() {
  const [state, dispatch] = useReducer(stopwatch, initial);

  useEffect(() => {
    if (!state.running) return;
    const id = setInterval(() => dispatch({ type: 'tick' }), 1000);
    return () => clearInterval(id);
  }, [state.running]);

  return (
    <>
      <p>{state.seconds}s</p>
      <button onClick={() => dispatch({ type: state.running ? 'stop' : 'start' })}>
        {state.running ? 'Stop' : 'Start'}
      </button>
      <button onClick={() => dispatch({ type: 'reset' })}>Reset</button>
    </>
  );
}

Exercise 6 · Context without wasted renders

An AuthProvider exposes { user, login, logout } by passing a new object literal as its value. Every consumer re-renders whenever the provider's parent renders. Fix it and add a hook that throws a helpful error when used outside the provider.

const AuthContext = createContext(null);

  const [user, setUser] = useState(null);

Exercise 7 · Redux Toolkit slice

Create a notifications slice with actions added(text), dismissed(id) and allCleared(), plus a selector for the unread count. Each notification is { id, text, read }; adding uses nanoid for the id via a prepare callback.

Show solution
ts
import { createSlice, nanoid, type PayloadAction } from '@reduxjs/toolkit';

type Note = { id: string; text: string; read: boolean };

const notificationsSlice = createSlice({
  name: 'notifications',
  initialState: [] as Note[],
  reducers: {
    added: {
      reducer(state, action: PayloadAction<Note>) {
        state.push(action.payload);
      },
      prepare(text: string) {
        return { payload: { id: nanoid(), text, read: false } };
      },
    },
    dismissed(state, action: PayloadAction<string>) {
      const n = state.find(x => x.id === action.payload);
      if (n) n.read = true;
    },
    allCleared() {
      return []; // returning a new value replaces state
    },
  },
  selectors: {
    selectUnreadCount: state => state.filter(n => !n.read).length,
  },
});

export const { added, dismissed, allCleared } = notificationsSlice.actions;
export const { selectUnreadCount } = notificationsSlice.selectors;
export default notificationsSlice.reducer;

Exercise 8 · Zustand cart

Build a Zustand store for a cart with add(product), remove(id) and clear(). Show a header badge that re-renders only when the item count changes, and persist the cart to localStorage.

Show solution
ts
import { create } from 'zustand';
import { persist } from 'zustand/middleware';

type Product = { id: string; name: string; price: number };
type Line = Product & { qty: number };
type Cart = {
  lines: Line[];
  add: (p: Product) => void;
  remove: (id: string) => void;
  clear: () => void;
};

export const useCart = create<Cart>()(
  persist(
    set => ({
      lines: [],
      add: p => set(s => {
        const found = s.lines.find(l => l.id === p.id);
        return {
          lines: found
            ? s.lines.map(l => (l.id === p.id ? { ...l, qty: l.qty + 1 } : l))
            : [...s.lines, { ...p, qty: 1 }],
        };
      }),
      remove: id => set(s => ({ lines: s.lines.filter(l => l.id !== id) })),
      clear: () => set({ lines: [] }),
    }),
    { name: 'cart', partialize: s => ({ lines: s.lines }) } // don't persist functions
  )
);

// The selector returns a number, so the badge re-renders only when the count changes.
export function CartBadge() {
  const count = useCart(s => s.lines.reduce((n, l) => n + l.qty, 0));
  return <span className="badge">{count}</span>;
}

Selectors that return primitives are compared by value, so no useShallow is needed here [5,29]. partialize selects which fields are persisted [30].

Exercise 11 · Server state with optimistic updates

Using TanStack Query, write a useToggleFavourite mutation that flips favourite on an item in the ['items'] cache immediately, rolls back on error, and refetches when it settles.

Show solution
ts
import { useMutation, useQueryClient } from '@tanstack/react-query';

type Item = { id: string; favourite: boolean };

export function useToggleFavourite() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: (id: string) => fetch(`/api/items/${id}/favourite`, { method: 'POST' }),
    onMutate: async (id) => {
      await qc.cancelQueries({ queryKey: ['items'] });            // avoid overwriting optimistic data
      const previous = qc.getQueryData<Item[]>(['items']);
      qc.setQueryData<Item[]>(['items'], old =>
        old?.map(i => (i.id === id ? { ...i, favourite: !i.favourite } : i))
      );
      return { previous };
    },
    onError: (_err, _id, ctx) => {
      if (ctx?.previous) qc.setQueryData(['items'], ctx.previous); // roll back
    },
    onSettled: () => qc.invalidateQueries({ queryKey: ['items'] }), // resync with the server
  });
}

This follows the documented mutation lifecycle (onMutate, onError, onSettled) and invalidation pattern [45,46].
