1. What routing is, and why React leaves it to libraries

Routing is the mapping from a URL to the part of an application that should be shown for it. When a user visits /products/42?tab=reviews, a router decides that the "product detail" page should render, that 42 is the product identifier, and that the reviews tab should be open. Navigation is the act of moving between those URLs, whether by clicking a link, submitting a form, pressing the browser's Back button, or being redirected by code.

React itself is a library for building user interfaces and does not ship a general-purpose router. The React team's guide to building an app from scratch says that the core tooling does not "include any further solutions for common functionality like routing", and that "you need to set up a router to map URLs to different parts of your app" [1]. The same guide points readers to dedicated routing libraries, which is why the React ecosystem has several competing routers, each with different trade-offs.

Every router, whatever its API, has to answer the same questions:

  • Matching: which route definition matches the current URL, and what values did its dynamic parts capture?
  • Rendering: which components render, and how do parent layouts wrap child pages?
  • Navigation: how does the app change the URL without a full page reload, and how does it react when the user goes back or forward?
  • Data: when and where is the data for a route loaded, and what happens while it loads or if it fails?
  • Control: who may see a route, and can a navigation be stopped (for example, when a form has unsaved changes)?

2. Client-side and server-side routing

2.1 Server-side routing

In classic server-side routing, every navigation is a full HTTP request. The browser asks the server for /about, the server decides what to send back, and the browser discards the current document and renders the new one. This is simple and robust: each URL is a real document, the server can enforce access rules on every request, and the page works without JavaScript. The cost is that every navigation repaints the whole page and loses in-memory state.

2.2 Client-side routing

In client-side routing, JavaScript in the page intercepts navigations, updates the URL itself and renders the new view without requesting a new document. The browser primitive behind this is the History API, which lets scripts add, replace and move between entries in the session history [2]. Two details matter:

  • history.pushState() and history.replaceState() change the URL and history stack, but they do not fire a popstate event [3]. The router has to re-render itself after calling them.
  • The popstate event fires when the active history entry changes because the user pressed Back or Forward, or code called history.back() or history.forward() [3]. The router listens for it to stay in sync with the browser.

The following dependency-free router shows the whole mechanism in about 40 lines. Real libraries add matching, nesting, data loading and much more, but the core loop is the same.

mini-router.js 
// A tiny client-side router built on the History API.
const routes = [
  { pattern: /^\/$/,             view: () => "<h1>Home</h1>" },
  { pattern: /^\/about$/,        view: () => "<h1>About</h1>" },
  { pattern: /^\/users\/(\d+)$/, view: (id) => `<h1>User ${id}</h1>` },
];

function render() {
  const path = window.location.pathname;
  for (const { pattern, view } of routes) {
    const match = path.match(pattern);
    if (match) {
      document.getElementById("app").innerHTML = view(...match.slice(1));
      return;
    }
  }
  document.getElementById("app").innerHTML = "<h1>404 Not found</h1>";
}

function navigate(to) {
  window.history.pushState({}, "", to); // changes the URL, no request
  render();                             // pushState does not fire popstate
}

// Intercept same-origin link clicks.
document.addEventListener("click", (event) => {
  const link = event.target.closest("a[href]");
  if (!link || link.origin !== window.location.origin) return;
  if (event.metaKey || event.ctrlKey || event.shiftKey || link.target) return;
  event.preventDefault();
  navigate(link.pathname + link.search);
});

// Back and Forward buttons.
window.addEventListener("popstate", render);

render();

Deep links need server help. With client-side routing, a user may load /users/7 directly or refresh on it. The server must answer that URL with the application's HTML (often a catch-all "serve index.html" rule), or the user sees a 404 before any JavaScript runs.

2.3 Hybrid routing

Modern frameworks blur the line. The first request is handled on the server, which renders HTML for fast first paint and search engines, and later navigations are handled on the client. React Router's framework mode and the Next.js App Router both work this way [4][5]. In Next.js, layouts and pages are Server Components by default, and a file opts into client-side interactivity with the "use client" directive [5].

AspectServer-side routingClient-side routing
What a navigation doesRequests and renders a new documentUpdates the URL with the History API and re-renders in place
In-memory stateLost on every navigationKept across navigations

Where access rules are enforcedOn the server, per requestIn the UI for experience, but still required on the server for security

4. React Router

React Router can be used in three modes. Declarative mode uses JSX <Routes> and <Route> elements; data mode defines routes as objects passed to createBrowserRouter and adds loaders, actions and pending states; framework mode adds a Vite plugin, file-based route modules, server rendering and type generation [4]. The examples below use data mode, because it shows the most routing features without a build plugin.

Version 8 notes. React Router 8 was released on 17 June 2026. It requires React 19.2.7 or newer and Node 22.22.0 or newer, ships ESM only, removes the separate react-router-dom package in favour of react-router, and turns middleware on by default [6]. Code written for version 7 mostly works if you change "react-router-dom" imports to "react-router".

4.1 Setting up a router

main.jsx 
import { StrictMode } from "react";
import { createRoot } from "react-dom/client";
import { createBrowserRouter, RouterProvider } from "react-router";
import Root from "./routes/root";
import Home from "./routes/home";
import Team, { loader as teamLoader } from "./routes/team";
import NotFound from "./routes/not-found";

const router = createBrowserRouter([
  {
    path: "/",
    Component: Root,              // layout: renders <Outlet /> for children
    children: [
      { index: true, Component: Home },                  // matches "/"
      { path: "teams/:teamId", Component: Team, loader: teamLoader },
      { path: "*", Component: NotFound },                // splat: anything else
    ],
  },
]);

createRoot(document.getElementById("root")).render(
  <StrictMode>
    <RouterProvider router={router} />
  </StrictMode>
);

The route object fields used here (path, Component, loader, children) are described in the route object reference, which also documents action, lazy, middleware, shouldRevalidate and handle [12]. The data-mode setup with createBrowserRouter and RouterProvider imported from "react-router" follows the official "Picking a Mode" guide [4].

4.2 Nested routes and layouts

Child routes are listed in children; the parent's path prefixes the child's, and the parent renders the matched child through <Outlet /> [13]. An index route (index: true) renders at the parent's own URL and cannot have children [13]. A route with children but no path is a layout route: it wraps its children in shared UI without adding a URL segment [13].

routes/root.jsx 
import { NavLink, Outlet, useNavigation } from "react-router";

export default function Root() {
  const navigation = useNavigation();
  return (
    <div className="app">
      <nav>
        <NavLink to="/" end>Home</NavLink>
        <NavLink to="/teams/react">React team</NavLink>
      </nav>
      {navigation.state === "loading" && <p className="spinner">Loading…</p>}
      <main>
        <Outlet />
      </main>
    </div>
  );
}

4.3 Dynamic segments and route parameters

A path segment that starts with : is dynamic, and its value is available from useParams() or the params argument of a loader. A trailing ? makes a segment optional, and * captures the rest of the URL as params["*"] [13].

routes/team.jsx 
import { useLoaderData, useParams } from "react-router";

export async function loader({ params }) {
  const res = await fetch(`/api/teams/${params.teamId}`);
  if (!res.ok) throw new Response("Team not found", { status: 404 });
  return res.json();
}

export default function Team() {
  const team = useLoaderData();       // value returned by the loader
  const { teamId } = useParams();     // "react" for /teams/react
  return (
    <article>
      <h1>{team.name}</h1>
      <p>Slug: {teamId}</p>
    </article>
  );
}

4.4 Loaders and actions

A loader fetches data before the route renders, and an action handles a mutation such as a form submission. Loaders receive the route params, and actions receive the request, from which form data can be read [12]. React Router's <Form> submits to the route's action without a full page reload, and the component can read the action's result with useActionData() [12].

routes/new-project.jsx 
import { Form, redirect, useActionData } from "react-router";

export async function action({ request }) {
  const formData = await request.formData();
  const title = String(formData.get("title") ?? "").trim();
  if (!title) return { error: "Title is required" };

  const res = await fetch("/api/projects", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ title }),
  });
  const project = await res.json();
  return redirect(`/projects/${project.id}`);
}

export default function NewProject() {
  const result = useActionData();
  return (
    <Form method="post">
      <label>
        Title <input name="title" />
      </label>
      {result?.error && <p role="alert">{result.error}</p>}
      <button type="submit">Create</button>
    </Form>
  );
}

4.5 Programmatic navigation

Links are the default way to navigate, because they are accessible and work with open-in-new-tab. When navigation has to happen in response to code (after a timer, or after a non-form operation), use the useNavigate() hook:

import { useNavigate } from "react-router";

function LogoutButton() {
  const navigate = useNavigate();
  async function handleClick() {
    await fetch("/api/logout", { method: "POST" });
    navigate("/login", { replace: true }); // replace: don't keep the old entry
  }
  return <button onClick={handleClick}>Log out</button>;
}

5. TanStack Router

TanStack Router's headline feature is type safety. Its overview lists "100% inferred TypeScript support" and type-safe navigation [7]: if a route expects a postId parameter, a <Link> to it without that parameter is a compile-time error. It supports file-based routing through a bundler plugin and code-based routing; the code-based form is shown here because it is self-contained.

router.tsx 
import {
  createRootRoute, createRoute, createRouter,
  Link, Outlet, RouterProvider,
} from "@tanstack/react-router";

type Post = { id: string; title: string; body: string };

const rootRoute = createRootRoute({
  component: () => (
    <>
      <nav>
        <Link to="/">Home</Link>{" "}
        <Link to="/posts/$postId" params={{ postId: "1" }}>First post</Link>
      </nav>
      <Outlet />
    </>
  ),
});

const indexRoute = createRoute({
  getParentRoute: () => rootRoute,
  path: "/",
  component: () => <h1>Welcome</h1>,
});

const postRoute = createRoute({
  getParentRoute: () => rootRoute,
  path: "/posts/$postId",            // $ marks a dynamic segment
  loader: async ({ params }): Promise<Post> => {
    const res = await fetch(`/api/posts/${params.postId}`);
    return res.json();
  },
  component: PostPage,
});

function PostPage() {
  const post = postRoute.useLoaderData(); // typed as Post
  return <article><h1>{post.title}</h1><p>{post.body}</p></article>;
}

const routeTree = rootRoute.addChildren([indexRoute, postRoute]);
export const router = createRouter({ routeTree });

// Register the router so Link, useNavigate etc. are typed app-wide.
declare module "@tanstack/react-router" {
  interface Register { router: typeof router }
}

export function App() {
  return <RouterProvider router={router} />;
}

5.1 Validated, typed search parameters

TanStack Router treats search parameters as first-class, typed state. A route's validateSearch function receives the raw parsed search object and returns a typed value; components then read it with Route.useSearch() [8].

type ProductSearch = { page: number; sort: "newest" | "price" };

const productsRoute = createRoute({
  getParentRoute: () => rootRoute,
  path: "/products",
  validateSearch: (search: Record<string, unknown>): ProductSearch => ({
    page: Number(search.page) > 0 ? Number(search.page) : 1,
    sort: search.sort === "price" ? "price" : "newest",
  }),
  component: Products,
});

function Products() {
  const { page, sort } = productsRoute.useSearch(); // { page: number; sort: ... }
  return (
    <>
      <p>Page {page}, sorted by {sort}</p>
      <Link to="/products" search={(prev) => ({ ...prev, page: prev.page + 1 })}>
        Next page
      </Link>
    </>
  );
}

6. Wouter

Wouter is a minimalist router for React and Preact. Its README describes it as "only 2.1 KB gzipped" and lists a small set of components (<Route>, <Link>, <Switch>, <Redirect> and an optional <Router>) and hooks (useRoute, useLocation, useParams, useSearch, useSearchParams and useRouter) [9]. A <Route> with the nest prop creates a nested context, so child routes match relative to it [9].

App.jsx 
import { Link, Route, Switch, useLocation, useParams } from "wouter";

function User() {
  const { name } = useParams();
  return <h1>Hello, {name}!</h1>;
}

function GoHomeButton() {
  const [, navigate] = useLocation();   // [currentPath, navigate]
  return <button onClick={() => navigate("/")}>Home</button>;
}

export default function App() {
  return (
    <>
      <nav>
        <Link href="/">Home</Link> <Link href="/users/ada">Ada</Link>
      </nav>
      <Switch>
        <Route path="/"><h1>Home</h1></Route>
        <Route path="/users/:name" component={User} />
        <Route path="/settings" nest>
          <Route path="/profile">Profile settings</Route>  {/* /settings/profile */}
        </Route>
        <Route>404: No such page!</Route>
      </Switch>
      <GoHomeButton />
    </>
  );
}

Wouter does not include data loaders or actions. It suits applications where routing is a thin layer and data fetching is handled by another library.

7. Next.js App Router

The Next.js App Router uses the file system as the route table. Each folder under app/ is a URL segment; a page file makes that segment publicly routable, and a layout file wraps the pages beneath it in shared UI that is kept across navigations [10].

app/ ├── layout.tsx → root layout for every page ├── page.tsx → / ├── blog/ │ ├── layout.tsx → wraps all /blog pages │ ├── page.tsx → /blog │ └── [slug]/ │ └── page.tsx → /blog/:slug └── docs/ └── [[...slug]]/ └── page.tsx → /docs, /docs/a, /docs/a/b …

7.1 Dynamic segments

A folder named [slug] is a dynamic segment, [...slug] is a catch-all that matches one or more segments as an array, and [[...slug]] is an optional catch-all that also matches the parent path with slug undefined [14]. Since Next.js 15, params is passed to a page as a Promise, so a Server Component awaits it and a Client Component unwraps it with React's use() [14].

app/blog/[slug]/page.tsx 
export default async function Page({
  params,
}: {
  params: Promise<{ slug: string }>;
}) {
  const { slug } = await params;
  const post = await fetch(`https://example.com/api/posts/${slug}`).then((r) => r.json());
  return (
    <article>
      <h1>{post.title}</h1>
      <p>{post.body}</p>
    </article>
  );
}

7.2 Server and Client Components

Layouts and pages are Server Components by default, so they can fetch data on the server and send no component JavaScript to the browser. Interactive pieces are marked with "use client" at the top of the file, above the imports, which declares a boundary between the server and client module graphs [5].

7.3 Linking and navigating

The <Link> component from next/link performs client-side navigation, and Next.js automatically prefetches routes linked with <Link> when they enter the viewport [15]. Client Components can read the current location with usePathname() and useSearchParams() from next/navigation [15].

app/components/nav-links.tsx 
"use client";

import Link from "next/link";
import { usePathname } from "next/navigation";

const links = [
  { href: "/", label: "Home" },
  { href: "/blog", label: "Blog" },
];

export function NavLinks() {
  const pathname = usePathname();
  return (
    <nav>
      {links.map((l) => (
        <Link key={l.href} href={l.href}
              aria-current={pathname === l.href ? "page" : undefined}>
          {l.label}
        </Link>
      ))}
    </nav>
  );
}

8. Reach Router

Reach Router was a separate router from Ryan Florence, one of React Router's original authors. In May 2019 the maintainers announced that they were "bringing together the best of React Router and Reach Router into a new, hook-based API", and that "React Router will be the surviving project", while @reach/router 1.0 would continue to receive bug fixes [11]. That merged API became React Router version 6, and new projects should not start on Reach Router.

For maintenance work, it helps to recognise Reach Router's style, where the route path is a prop on the page component itself:

// Reach Router (legacy)
import { Router, Link } from "@reach/router";

const App = () => (
  <Router>
    <Home path="/" />
    <Dashboard path="dashboard">
      <Invoice path="invoices/:invoiceId" />   {/* receives props.invoiceId */}
    </Dashboard>
  </Router>
);

The equivalent in React Router moves the path from the component to a route definition, reads the parameter with useParams(), and renders children through <Outlet /> instead of props.children [13]:

// React Router equivalent
const router = createBrowserRouter([
  { path: "/", Component: Home },
  {
    path: "dashboard",
    Component: Dashboard,          // renders <Outlet />
    children: [{ path: "invoices/:invoiceId", Component: Invoice }],
  },
]);

9. Core concepts in depth

9.1 Dynamic routes

A dynamic route has one or more segments that match any value instead of a fixed string, so one definition serves many URLs. The syntax differs by library but the idea is the same:

LibraryDynamic segmentCatch-all
React Routerteams/:teamId, optional :lang? [13]files/* → params["*"] [13]
TanStack Router/posts/$postId/files/$ (splat)
Wouter/users/:name [9]Wildcards in the path pattern
Next.js[slug] folder [14][...slug], optional [[...slug]] [14]

9.2 Nested routes

Nested routes mirror the nesting of the UI. A URL such as /dashboard/invoices/7 can render a dashboard layout, an invoices sidebar inside it, and an invoice detail inside that. Each level owns its own segment of the URL, its own data and its own error handling. In React Router the parent renders the child through <Outlet /> [13]; in Next.js nested folders and layout files produce the same structure [10]. The benefit is that navigating between two invoices re-renders only the innermost level, so the outer layout keeps its state, such as scroll position or an open menu.

9.3 Route parameters

Route parameters are the values captured by dynamic segments. They are always strings in the URL, so convert and validate them before use:

import { useParams } from "react-router";

function Invoice() {
  const { invoiceId } = useParams();
  const id = Number(invoiceId);
  if (!Number.isInteger(id) || id <= 0) {
    return <p>Invalid invoice number.</p>;
  }
  // … load and render invoice `id`
}

Treat parameters as untrusted input. Encode them when building API URLs (encodeURIComponent), and never use them to build HTML or database queries directly.

9.4 Protected routes

A protected route is only shown to users who meet a condition, typically being signed in or holding a role. The right place to check is before the route renders, so that protected data is never fetched for an unauthorised user and the protected UI never flashes on screen.

Client-side checks are not security. A route guard in the browser improves the user experience, but anyone can modify client code. Every request for protected data must be authorised on the server. OWASP's authorization guidance states that "permission should be validated correctly on every request" [16].

In React Router, a layout route with a loader can guard all of its children by throwing a redirect. Remembering the original location lets the login page send the user back afterwards:

routes/require-auth.jsx 
import { Outlet, redirect } from "react-router";
import { getCurrentUser } from "../auth";

export async function loader({ request }) {
  const user = await getCurrentUser();
  if (!user) {
    const url = new URL(request.url);
    const from = url.pathname + url.search;
    throw redirect(`/login?redirectTo=${encodeURIComponent(from)}`);
  }
  return { user };
}

export default function RequireAuth() {
  return <Outlet />;
}

// In the route table:
// { Component: RequireAuth, loader: requireAuthLoader,
//   children: [{ path: "account", Component: Account }, …] }

TanStack Router uses the same pattern with beforeLoad. Its authenticated-routes guide shows a pathless _authenticated route whose beforeLoad throws redirect({ to: "/login", search: { redirect: location.href } }) when the user is not authenticated [17]:

import { createFileRoute, redirect } from "@tanstack/react-router";

export const Route = createFileRoute("/_authenticated")({
  beforeLoad: async ({ location, context }) => {
    if (!context.auth.isAuthenticated) {
      throw redirect({
        to: "/login",
        search: { redirect: location.href },
      });
    }
  },
});

9.5 Navigation guards

A navigation guard runs when a navigation is about to happen and can allow it, redirect it, or cancel it. Protected routes are one kind of guard (they decide whether you may enter). The other common kind decides whether you may leave, usually to protect unsaved work.

React Router's useBlocker(shouldBlock) returns a blocker whose state is "unblocked", "blocked" or "proceeding". When it is blocked, proceed() lets the navigation continue and reset() cancels it and keeps the user on the page. It is available in framework and data modes, not declarative mode [18].

routes/edit-profile.jsx 
import { useState, useEffect } from "react";
import { Form, useBlocker } from "react-router";

export default function EditProfile() {
  const [dirty, setDirty] = useState(false);

  // In-app navigations (links, navigate(), Back within the app)
  const blocker = useBlocker(
    ({ currentLocation, nextLocation }) =>
      dirty && currentLocation.pathname !== nextLocation.pathname
  );

  // Leaving the document (closing the tab, typing a new URL)
  useEffect(() => {
    if (!dirty) return;
    const onBeforeUnload = (e) => { e.preventDefault(); };
    window.addEventListener("beforeunload", onBeforeUnload);
    return () => window.removeEventListener("beforeunload", onBeforeUnload);
  }, [dirty]);

  return (
    <Form method="post" onChange={() => setDirty(true)} onSubmit={() => setDirty(false)}>
      <input name="displayName" />
      <button type="submit">Save</button>

      {blocker.state === "blocked" && (
        <div role="dialog" aria-modal="true">
          <p>You have unsaved changes. Leave anyway?</p>
          <button type="button" onClick={() => blocker.proceed()}>Leave</button>
          <button type="button" onClick={() => blocker.reset()}>Stay</button>
        </div>
      )}
    </Form>
  );
}

A router can only intercept navigations inside the application. Closing the tab or typing a new address leaves the document, which only the browser's beforeunload event can intercept; the browser then shows its own generic confirmation [19].

9.6 Lazy-loaded routes

A lazy-loaded route downloads its code only when the user first navigates to it. React provides lazy(load), where load returns a Promise that resolves to a module whose default export is a component; lazy must be called at the top level of a module, not inside a component [20]. While the code loads, the nearest <Suspense> boundary shows its fallback [21].

import { lazy, Suspense } from "react";
import { Routes, Route } from "react-router";   // declarative mode

const Reports = lazy(() => import("./pages/Reports")); // top level, not in a component

export function AppRoutes() {
  return (
    <Suspense fallback={<p>Loading page…</p>}>
      <Routes>
        <Route path="/" element={<Home />} />
        <Route path="/reports" element={<Reports />} />
      </Routes>
    </Suspense>
  );
}

In data mode, React Router's route object has its own lazy field, so the router can load a route's component, loader and action together, in parallel with navigation, instead of discovering the code only when rendering [12]:

createBrowserRouter([
  {
    path: "/admin",
    lazy: async () => {
      const { default: Component, loader, action } = await import("./routes/admin");
      return { Component, loader, action };
    },
  },
]);

9.7 Route-based code splitting

Code splitting breaks a JavaScript bundle into chunks that load on demand. The dynamic import() expression is the language feature that makes this possible: it loads a module asynchronously and returns a Promise [22], and bundlers emit a separate chunk for each dynamically imported module. Routes are natural split points, because a user visits only a few pages per session. web.dev's guide walks through splitting a React app with React.lazy and Suspense [23].

Routers increasingly automate this. TanStack Router offers autoCodeSplitting for file-based routes, or manual splitting with .lazy.tsx files and createLazyFileRoute [24]. React Router 8 enables route-module splitting by default in framework mode [6].

Two practical points: keep the loading fallback close to the content that is loading, so the rest of the layout stays visible; and prefetch likely next routes (for example on link hover or when a link enters the viewport, as Next.js does by default [15]) so that the split rarely causes a visible wait.

9.8 URL state and query parameters

The URL is the most durable place for UI state that someone might want to bookmark, share or restore with Back: search terms, filters, sort order, the current page or the selected tab. The browser's URLSearchParams interface parses and builds the query string [25].

React Router's useSearchParams() returns a [searchParams, setSearchParams] tuple, where searchParams is a URLSearchParams object and calling the setter performs a navigation [26]. Because it navigates, each change becomes a history entry unless you pass { replace: true }.

routes/products.jsx 
import { useSearchParams } from "react-router";

export default function Products() {
  const [searchParams, setSearchParams] = useSearchParams();
  const q = searchParams.get("q") ?? "";
  const page = Math.max(1, Number(searchParams.get("page")) || 1);

  function update(changes, options) {
    setSearchParams((prev) => {
      const next = new URLSearchParams(prev);
      for (const [key, value] of Object.entries(changes)) {
        if (value === "" || value == null) next.delete(key);
        else next.set(key, String(value));
      }
      return next;
    }, options);
  }

  return (
    <>
      <input
        value={q}
        onChange={(e) => update({ q: e.target.value, page: null }, { replace: true })}
        placeholder="Search products"
      />
      <p>Showing page {page} for “{q}”</p>
      <button disabled={page === 1} onClick={() => update({ page: page - 1 })}>Previous</button>
      <button onClick={() => update({ page: page + 1 })}>Next</button>
    </>
  );
}

Guidelines for URL state: keep defaults out of the URL so links stay short; validate every value read from it, since users can edit it; use replace for rapid changes like typing so Back is not cluttered; and reset dependent values (such as page) when a filter changes. TanStack Router's validateSearch (section 5.1) builds these rules into the route definition [8].

Exercise 1: Extend the mini router

Extend mini-router.js from section 2.2 so that (a) the document title changes with each route, and (b) query strings work: /search?q=react should render "Results for react".

      return p.outerHTML;

Exercise 3: Load data and handle a missing record

Give the :userId route from exercise 2 a loader that fetches /api/users/:userId. If the API returns 404, show a friendly "User not found" message inside the layout instead of crashing the app.

Show solution 
import { isRouteErrorResponse, useLoaderData, useRouteError } from "react-router";

export async function userLoader({ params }) {
  const res = await fetch(`/api/users/${encodeURIComponent(params.userId)}`);
  if (res.status === 404) throw new Response("Not found", { status: 404 });
  if (!res.ok) throw new Error("Failed to load user");
  return res.json();
}

function UserDetail() {
  const user = useLoaderData();
  return <h2>{user.name}</h2>;
}

function UserError() {
  const error = useRouteError();
  if (isRouteErrorResponse(error) && error.status === 404) {
    return <p>User not found.</p>;
  }
  return <p>Something went wrong loading this user.</p>;
}

// Route: { path: ":userId", Component: UserDetail, loader: userLoader,
//          ErrorBoundary: UserError }

Throwing from a loader stops the route from rendering and sends the error to the nearest error boundary. Putting the boundary on the child route keeps the users list visible around the error.

Exercise 4: Protected route with return-to-origin

Protect /account and /account/billing. Unauthenticated visitors go to /login; after logging in they return to the page they asked for. Make sure the redirect target cannot send users to another website.

Show solution 
import { Form, Outlet, redirect } from "react-router";
import { getCurrentUser, logIn } from "./auth";

// 1. Guard: a pathless layout route around the protected pages.
async function requireAuth({ request }) {
  if (!(await getCurrentUser())) {
    const url = new URL(request.url);
    throw redirect(`/login?redirectTo=${encodeURIComponent(url.pathname + url.search)}`);
  }
  return null;
}

// 2. Only allow same-site relative paths, to prevent open redirects.
function safeRedirect(to) {
  return typeof to === "string" && to.startsWith("/") && !to.startsWith("//")
    ? to
    : "/";
}

// 3. Login action: authenticate, then go back.
async function loginAction({ request }) {
  const form = await request.formData();
  await logIn(form.get("email"), form.get("password"));
  const redirectTo = new URL(request.url).searchParams.get("redirectTo");
  return redirect(safeRedirect(redirectTo));
}

function LoginPage() {
  return (
    <Form method="post">
      <input name="email" type="email" />
      <input name="password" type="password" />
      <button>Log in</button>
    </Form>
  );
}

export const routes = [
  { path: "/login", Component: LoginPage, action: loginAction },
  {
    loader: requireAuth,
    Component: Outlet,
    children: [
      { path: "/account", Component: Account },
      { path: "/account/billing", Component: Billing },
    ],
  },
];

A <Form> without an action attribute posts to the current URL, including its query string, so redirectTo reaches the action. The check in safeRedirect rejects absolute URLs and protocol-relative URLs such as //evil.example. Remember that the server API behind Account and Billing must still check the session on every request [16].

Exercise 5: Warn before losing unsaved changes

Write a reusable hook, useUnsavedChangesWarning(isDirty), that blocks in-app navigation and tab closing while isDirty is true, and returns what a component needs to show a confirmation dialog.

Show solution 
import { useEffect, useState } from "react";
import { useBlocker } from "react-router";

export function useUnsavedChangesWarning(isDirty) {
  const blocker = useBlocker(
    ({ currentLocation, nextLocation }) =>
      isDirty &&
      (currentLocation.pathname !== nextLocation.pathname ||
       currentLocation.search !== nextLocation.search)
  );

  useEffect(() => {
    if (!isDirty) return;
    const handler = (event) => event.preventDefault();
    window.addEventListener("beforeunload", handler);
    return () => window.removeEventListener("beforeunload", handler);
  }, [isDirty]);

  return {
    isBlocked: blocker.state === "blocked",
    confirm: () => blocker.proceed?.(),
    cancel: () => blocker.reset?.(),
  };
}

// Usage
function Editor() {
  const [text, setText] = useState("");
  const [saved, setSaved] = useState("");
  const { isBlocked, confirm, cancel } = useUnsavedChangesWarning(text !== saved);
  /* … render textarea, and a dialog when isBlocked … */
}

proceed and reset exist only while the blocker is in the "blocked" state, hence the optional calls [18]. The beforeunload listener is added only while dirty, because an always-on listener can affect browser caching and shows a prompt even when nothing would be lost [19].

Exercise 7: Typed search parameters in TanStack Router

Define a /issues route in TanStack Router whose search parameters are status ("open" or "closed", default "open") and page (positive integer, default 1). Add a link that switches to closed issues and resets the page.

Show solution 
import { createRoute, Link } from "@tanstack/react-router";

type IssueSearch = { status: "open" | "closed"; page: number };

export const issuesRoute = createRoute({
  getParentRoute: () => rootRoute,
  path: "/issues",
  validateSearch: (search: Record<string, unknown>): IssueSearch => {
    const page = Number(search.page);
    return {
      status: search.status === "closed" ? "closed" : "open",
      page: Number.isInteger(page) && page > 0 ? page : 1,
    };
  },
  component: Issues,
});

function Issues() {
  const { status, page } = issuesRoute.useSearch();
  return (
    <>
      <h1>{status} issues, page {page}</h1>
      <Link to="/issues" search={{ status: "closed", page: 1 }}>Show closed</Link>
    </>
  );
}

Because validateSearch declares the return type, useSearch() is typed and a link such as search={{ status: "pending" }} fails type-checking [8]. Invalid values typed by hand into the address bar fall back to the defaults.

Exercise 9 (conceptual): Pick a router

For each scenario, choose a router and justify it in one sentence: (a) a marketing site with a blog that must rank well in search engines; (b) an embeddable 3-screen widget where every kilobyte counts; (c) a large TypeScript dashboard with many filterable tables; (d) an existing app on @reach/router.

Show solution
  1. Next.js App Router (or React Router framework mode): pages render on the server as Server Components by default, so crawlers receive full HTML [5].
  2. Wouter: it covers routes, links and parameters at about 2.1 KB gzipped [9].
  3. TanStack Router: typed search parameters and type-safe links make filter state in the URL reliable across many screens [7][8].
  4. Migrate to React Router: React Router is the designated successor, and Reach Router receives bug fixes only [11].

11. Summary

  • Routing maps URLs to UI, and React leaves it to libraries [1].
  • Client-side routing uses the History API to change the URL without a document load, and listens for popstate to handle Back and Forward [2][3]. Server-side and hybrid routing render on the server for the first load or every load.
  • Dynamic segments capture route parameters; nested routes let layouts persist while inner pages change.
  • Protected routes and navigation guards belong before rendering (loaders, beforeLoad) and before leaving (useBlocker, beforeunload), but real authorization always happens on the server.
  • Routes are the natural unit of code splitting, through React.lazy or a router's own lazy routes.
  • Shareable UI state belongs in the URL's query string, read and written through validated, typed helpers.
