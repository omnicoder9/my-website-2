React Fundamentals

Concepts, hooks, rendering internals and application architecture, with source code, exercises and solutions

Technical article · Written 19 November 2026 against the React 19 documentation on react.dev · 92 references, Vancouver style

1. Introduction

React is a JavaScript library for building user interfaces out of small, reusable pieces called components. A React application is a tree of components, each of which is a JavaScript function that returns markup.(1,2) Rather than telling the browser step by step how to change the page, you describe what the interface should look like for a given state, and React works out how to update the screen to match.(3,4)

This article walks through the ideas that every React developer relies on. It starts with JSX and components, moves through props, state, events and context, covers each built-in hook, then explains how React renders, reconciles and hydrates. It closes with how React fits into a full application stack. Each major section ends with exercises, and every solution is hidden behind a toggle so you can try the problem first.

How to run the examples. All examples are written for React 19 with function components. The React team recommends starting new projects with a framework such as Next.js or React Router, or with a build tool such as Vite, and no longer recommends Create React App for new apps.(5,6) Any of these will run the code below. Examples import from react and react-dom and assume a module bundler that supports JSX.
A note on sources. Factual claims are cited to the official React documentation (react.dev), the React blog, the archived legacy documentation, React working group publications and the official documentation of the other libraries mentioned. Community sources are used only for patterns the official docs do not name, and are marked as such.

3. JSX

JSX is a syntax extension for JavaScript that lets you write HTML-like markup inside a JavaScript file.(7) It is optional, but most React code uses it because it keeps rendering logic and markup together. The example from the outline is a complete component:

JSX is stricter than HTML. A component must return a single root element, every tag must be closed (for example <img />), and most attributes are written in camelCase, so class becomes className and stroke-width becomes strokeWidth.(7)

3.1 JSX transformation

Browsers do not understand JSX, so a compiler such as Babel or TypeScript transforms it into plain JavaScript function calls before the code runs. Under the classic transform, each tag became a call to React.createElement. React 17 introduced a new transform that imports special functions from react/jsx-runtime automatically, so files no longer need to import React just to use JSX.(18)

3.2 React elements

The result of evaluating JSX, or of calling createElement(type, props, ...children), is a React element: a plain, lightweight object that describes what should appear on screen. Elements are immutable; you do not change an element's props after creating it, you create a new element instead.(19) A lowercase tag such as <div> refers to a built-in browser component, while a capitalised tag such as <Welcome> refers to your own component, which is why component names must start with a capital letter.(1)

3.3 Fragments

Because a component must return one root, you sometimes need to group elements without adding an extra DOM node. <Fragment>, usually written with the shorthand <>...</>, does exactly that. When you need a key on a fragment, for example inside a list, you must use the explicit <Fragment key={...}> form.(20)

3.4 JSX expressions

Curly braces open a window from JSX back into JavaScript. You can use them as text content and as attribute values, and any JavaScript expression works inside, including variables, function calls and object literals. "Double curlies" such as style={{ color: 'red' }} are simply an object literal inside the braces.(21)

3.5 Conditional JSX

JSX has no special syntax for conditions. You use JavaScript: an if statement before the return, the conditional operator cond ? a : b, or logical AND cond && a. Returning null renders nothing.(13) Section 6 covers the common pitfalls.

3.6 Component composition

Components can be nested inside other components. Content placed between a component's opening and closing tags arrives as a special prop called children, which lets you build generic wrappers like cards, panels and layouts that do not need to know what is inside them.(8)

4. Components

Components let you split the UI into independent, reusable pieces and think about each piece in isolation. A component is a JavaScript function that returns markup, and its name must begin with a capital letter.(1)

4.1 Function components and class components

Function components are the modern standard. They receive props as their argument, return JSX, and use hooks for state and other features. Class components extend React.Component, read props from this.props, keep state in this.state, and respond to lifecycle methods. Class components are still supported, but the React documentation recommends defining components as functions in new code.(22)

One feature still requires a class: error boundaries, which need static getDerivedStateFromError or componentDidCatch. There is no hook equivalent yet.(22) See section 10.7.

4.2 Component hierarchy and parent-child relationships

Because components render other components, an application forms a tree. React and many related tools model the UI as a render tree, with the root component at the top and each child below the component that rendered it. Components near the top tend to affect the rendering of everything below them, while leaf components re-render often.(2) A parent communicates with its children by passing props, and a child communicates back by calling functions the parent passed down.(23)

4.3 Composition and reusability

React favours composition, building complex components out of simpler ones, over inheritance. A component written once, such as Avatar or Card, can be rendered any number of times with different props.(1,8) The children prop (section 3.6) and passing components or elements as props are the main composition tools.

4.4 Components must be pure

React assumes every component is a pure function during rendering: given the same props, state and context it returns the same JSX, and it does not change objects or variables that existed before it was called.(24,25) Side effects such as network requests, subscriptions or DOM mutations belong in event handlers or, as a last resort, in effects. In development, Strict Mode calls component functions twice to help surface impure code.(24,26)

4.5 Controlled and uncontrolled components

A component is controlled when the important information in it is driven by props from its parent, and uncontrolled when it keeps that information in its own local state.(23) The terms are most often used for form inputs. A controlled <input> receives its value from state and reports changes through onChange; an uncontrolled input is given only an initial defaultValue and keeps its own value in the DOM, which you can read with a ref.(27,28)

Pitfall. If you pass value without onChange, the input becomes read-only and React warns about it. The value you pass must also stay a string, not switch between undefined and a string, or the input flips between uncontrolled and controlled.(27)

4.6 Component patterns

Presentational and container components

This pattern, popularised by Dan Abramov in 2015, separates components that decide how things look (presentational, receiving data via props) from components that decide how things work (containers, which fetch data and hold state). Abramov later added a note that he no longer recommends splitting components this way dogmatically, because hooks let you share stateful logic without the split.(29) The underlying idea, keeping display components free of data-fetching concerns, is still useful.

Higher-order components (HOCs)

A higher-order component is a function that takes a component and returns a new component. It is a pattern that emerges from React's compositional nature rather than part of the React API.(30) HOCs were widely used for cross-cutting concerns before hooks; today a custom hook is usually simpler.(31)

Render props

A render prop is a prop whose value is a function that a component calls to know what to render, which lets it share behaviour while the caller controls the output.(32)

Compound components

Compound components are a set of components that work together and share implicit state, in the way <select> and <option> do in HTML. The official docs do not name this pattern; it is described in community sources such as Kent C. Dodds' writing, and is typically implemented with context.(16,33)

Rendering a context object directly as a provider, as in <TabsContext value={...}>, is supported from React 19; earlier versions use <TabsContext.Provider value={...}>.(34)

5. Props, state and one-way data flow

5.1 Props

Props are the information you pass to a JSX tag. A component receives all of its props as a single object argument, which is usually destructured in the parameter list, and you can give a prop a default value with ordinary destructuring defaults.(8) Props are read-only snapshots: a component should never change its own props. When a parent passes different props, the child simply renders again with the new values.(8,24)

You can forward all props to a child with spread syntax, <Avatar {...props} />, but the docs advise using it sparingly because it hides which props a component actually uses.(8)

5.2 State

Regular local variables do not persist between renders, and changing them does not tell React to render again. State solves both problems: useState returns the current value and a setter function, and calling the setter stores the new value and triggers a re-render.(9) State is private to the component instance that declares it; rendering the same component twice gives two independent copies.(9)

State behaves like a snapshot

Setting state does not change the variable in the code that is already running; it requests a new render. Within one render, the value of a state variable is fixed, even inside event handlers that run later.(36) React also batches updates: it waits until all code in the event handler has run before re-rendering. To apply several updates to the same variable based on its previous value, pass an updater function.(35)

Treat state as immutable

When state holds an object or array, do not mutate it. Create a new copy with the change, for example with spread syntax, and pass the copy to the setter. Mutating the existing object does not trigger a render and can cause stale UI.(37)

State is tied to a position in the tree

React keeps a component's state for as long as the same component is rendered at the same position in the UI tree. If you render a different component type at that position, or give it a different key, React discards the old state.(38) Changing the key is therefore a deliberate way to reset a component, for example <Chat key={contactId} />.

5.3 One-way data flow

In React, data flows down the component hierarchy from parent to child through props. This is called one-way data flow.(3) When two components need to share data, you lift the state up to their closest common parent and pass the value and an updater function down as props. This gives each piece of state a single "source of truth".(23)

Here each Panel is controlled by its parent: the parent owns activeIndex, and the panels report clicks through the onShow callback. This is the controlled-component idea from section 4.5 applied to your own components.(23)

6. Conditional rendering, lists and keys, and events

6.1 Conditional rendering

Because JSX is JavaScript, conditional rendering uses JavaScript operators.(13)

Pitfall. Do not put a number on the left of &&. If messageCount is 0, then {messageCount && <p>New messages</p>} renders the digit 0. Write messageCount > 0 && ... instead.(13)

6.2 Lists and keys

To render a list, transform an array of data into an array of elements with map(), often after filter(). Each element in the array needs a key that is unique among its siblings.(14) Keys tell React which array item each component corresponds to, so it can match them up when items are inserted, removed or reordered.(12,14)

The rules for keys are: keys must be unique among siblings (they need not be globally unique), and keys must not change between renders. Use IDs from your data. The array index works only if the list is never reordered, inserted into or filtered; generating keys on the fly, such as with Math.random(), makes keys change on every render and forces React to recreate components and lose their state.(14) A component does not receive key as a prop.(14)

6.3 Event handling

Event handlers are functions you pass to JSX as props such as onClick, onChange or onSubmit. Pass the function itself, onClick={handleClick}, not the result of calling it, onClick={handleClick()}, which would run during rendering.(15) Event handlers are the main place for side effects in React, and they do not need to be pure.(15,24)

Events propagate (bubble) up the tree, as in the DOM. Call e.stopPropagation() to stop a parent handler from running, and e.preventDefault() to suppress the browser's default behaviour for the event. By convention, props that represent events in your own components are named onSomething.(15)

7. Context

Passing props through many intermediate components that do not use them, known as prop drilling, becomes awkward. Context lets a parent component make information available to any component in the tree below it, however deep, without passing it explicitly through props.(16) Using context takes three steps: create it with createContext, read it with useContext, and provide a value from a parent.(16,40)

A component reads the value from the nearest provider above it. When the provided value changes, every component that reads that context re-renders.(40) Before reaching for context, the docs suggest first trying plain props or passing JSX as children; common uses for context include theming, the current user, routing and managing state that many distant components need.(16) Combining useReducer with context is a recommended way to scale state management for complex screens.(41)

8. Component lifecycle

Every component goes through the same lifecycle: it mounts when it is added to the screen, it updates when it receives new props or state (usually in response to an interaction), and it unmounts when it is removed from the screen.(17)

In class components, these moments map to methods such as componentDidMount, componentDidUpdate and componentWillUnmount.(22) In function components, the React docs encourage a different mental model. Instead of thinking about the component's lifecycle, think about each effect on its own: an effect describes how to start synchronising with an external system and how to stop. React may start and stop that synchronisation many times while the component stays mounted, whenever the effect's dependencies change.(17)

The table is an approximation for orientation, not an exact equivalence; the docs warn that effects are better understood as synchronisation than as lifecycle callbacks.(17,22)

The function version covers all three class methods in one place, and it is harder to forget the update case.(17)

9.1 Rules of Hooks

Hooks rely on being called in the same order on every render. Two rules follow from that.(43)

  1. Only call hooks at the top level. Do not call them inside conditions, loops, nested functions, after an early return, inside event handlers, or inside try/catch/finally blocks.
  2. Only call hooks from React functions: from function components or from custom hooks, not from regular JavaScript functions.

The eslint-plugin-react-hooks linter enforces these rules.(43) The one exception is use, which can be called conditionally.(44)

9.2 State hooks: useState and useReducer

useState

const [state, setState] = useState(initialState) declares a state variable. If you pass a function as initialState, React calls it only on the first render, which is useful when the initial value is expensive to compute (useState(createInitialTodos), not useState(createInitialTodos())). If the new value is identical to the current one, as determined by Object.is, React skips re-rendering the component and its children.(45)

useReducer

useReducer(reducer, initialArg, init?) moves state update logic out of event handlers into a single reducer function, (state, action) => newState. Event handlers then dispatch actions that describe what happened.(46,47) Reducers must be pure, and they are a good fit when many handlers update the same state in related ways.(47)

useContext

useContext(SomeContext) returns the context value from the closest provider above the calling component, or the default passed to createContext if there is none. See section 7.(40)

9.3 Effect hooks: useEffect and useLayoutEffect

useEffect

useEffect(setup, dependencies?) lets a component synchronise with an external system, such as a network connection, a browser API, a third-party widget or a timer.(48,49) React runs setup after the component is committed to the screen. If setup returns a cleanup function, React runs it before re-running the effect with new dependencies and when the component unmounts.(48)

Dependency arrays

useEffect(fn)After every render

You do not choose the dependencies freely: every reactive value (props, state and anything derived from them) read inside the effect must be listed, and the linter checks this. To remove a dependency, you change the code so the effect no longer needs it.(17,48)

Effect cleanup

In development with Strict Mode, React mounts every component, unmounts it, and mounts it again, which runs setup, cleanup and setup. This stress-tests your cleanup logic: if the user-visible behaviour differs from running setup once, the cleanup is missing or incomplete.(26,49)

The ignore flag prevents a slow response for an old userId from overwriting a newer one.(49) For production data fetching, the docs recommend using your framework's built-in mechanism or a client-side cache library instead of writing effects by hand.(48,49)

You might not need an effect. Effects are an escape hatch for stepping outside React. Do not use one to transform data for rendering (compute it during render instead) or to handle user events (use the event handler). Unnecessary effects make code slower and harder to follow.(39)

useLayoutEffect

useLayoutEffect has the same signature as useEffect, but it fires before the browser repaints the screen. Use it to measure layout, for example a tooltip's height, and adjust before the user sees anything. It blocks painting and can hurt performance, so prefer useEffect where possible.(50)

9.4 Ref hooks: useRef and useImperativeHandle

useRef

useRef(initialValue) returns an object with a single current property. The same object is returned on every render, and changing ref.current does not trigger a re-render, so refs suit values that do not affect the output, such as timer IDs. Do not read or write ref.current during rendering, except for lazy initialisation.(51,52) Refs are also how you access DOM nodes: pass the ref object as the ref attribute, and React sets current to the node.(53)

useImperativeHandle

useImperativeHandle(ref, createHandle, dependencies?) customises the value a parent receives through a ref, so that a component can expose a small, deliberate API, such as focus() and scrollIntoView(), instead of the whole DOM node.(54) Since React 19, function components receive ref as an ordinary prop, so forwardRef is no longer needed for new code.(34,55)

9.5 Performance hooks: useMemo and useCallback

useMemo(calculateValue, dependencies) caches the result of a calculation between re-renders and recomputes it only when a dependency changes.(56) useCallback(fn, dependencies) caches a function definition, which matters mainly when you pass the function to a child wrapped in memo or use it as a dependency of another hook.(57,58) Both are performance optimisations: your code should work correctly without them.(56,57)

Without useMemo and useCallback, visible and handleSelect would be new values on every render, and memo would never skip re-rendering List. The React Compiler can apply this kind of memoisation automatically at build time, which reduces the need to write these hooks by hand.(59)

9.6 Concurrent hooks: useTransition and useDeferredValue

useTransition

const [isPending, startTransition] = useTransition() lets you mark a state update as a transition, a non-urgent update that can be interrupted. While a transition renders in the background, the UI stays responsive to urgent updates such as typing, and isPending tells you a transition is in progress.(60) Since React 19, the function passed to startTransition can be async; the docs call such functions Actions.(34,60)

Text input updates must not be wrapped in a transition, because inputs need to update synchronously.(60)

useDeferredValue

useDeferredValue(value, initialValue?) returns a version of value that may "lag behind". During an urgent update, React first re-renders with the old deferred value, then tries a background re-render with the new value, which it abandons if value changes again.(61) It is a good fit when you do not control the state update itself, for instance a value that arrives as a prop.

The child must be wrapped in memo for this to help, because otherwise it would re-render with the urgent update anyway.(61)

9.7 Other hooks: useId and useSyncExternalStore

useId

useId() generates a unique ID string that is stable across the server and the client, which makes it suitable for linking labels and accessibility attributes. It must not be used to generate list keys.(62)

useSyncExternalStore

useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot?) subscribes a component to a store that lives outside React, such as a state library or a browser API. subscribe registers a callback and returns an unsubscribe function; getSnapshot returns the current value, and must return the same value when the store has not changed.(63)

Defining subscribe outside the component keeps its identity stable, so React does not resubscribe on every render.(63)

9.8 Custom hooks and hook composition

A custom hook is a function whose name starts with use and that calls other hooks. Custom hooks let you share stateful logic between components, not state itself: each call gets its own independent state.(31) Because hooks are just functions, they compose: a custom hook can call built-in hooks and other custom hooks, and pass values from one to the next.(31)

10. React rendering and internals

10.0 Trigger, render, commit

Every screen update in React happens in three steps.(4)

  1. Trigger. A render is triggered either by the initial render, when you call createRoot(domNode).render(<App />), or because the component's (or an ancestor's) state was updated.(4,64)
  2. Render. React calls your components to work out what should be on screen. On the initial render it calls the root component; on later renders it calls the component whose state update triggered the render, and recursively the components it returns.(4)
  3. Commit. React applies changes to the DOM. On the initial render it adds all the DOM nodes it created. On re-renders it applies the minimal operations needed to make the DOM match the latest render output, and only changes DOM nodes if there is a difference between renders. The browser then repaints the screen.(4)

10.1 The virtual DOM

The virtual DOM is a programming concept in which an ideal, or "virtual", representation of the UI is kept in memory and synced with the real DOM by a library such as ReactDOM. The legacy React documentation notes that in React the term is usually associated with React elements, the objects that represent the UI, and that React also uses internal objects called "fibers" to hold additional information about the component tree.(11) The current documentation does not use the term "virtual DOM" much; it describes the same idea as rendering followed by a commit that applies only the differences.(4) The benefit is a declarative API: you describe the UI for a state, and React handles attribute manipulation, event handling and manual DOM updates.(11)

10.2 The reconciliation algorithm

When state or props change, React has two trees of elements: the one from the previous render and the new one. It needs to work out the most efficient way to update the UI to match. Generic algorithms for transforming one tree into another have a complexity on the order of O(n3), which would be far too slow for UIs. React instead uses a heuristic O(n) algorithm based on two assumptions:(12)

  1. Two elements of different types will produce different trees.
  2. The developer can hint at which child elements may be stable across renders with a key prop.

In practice this gives three rules.(12)

  • Different element types: if the root elements have different types (for example <a> becoming <img>, or <Article> becoming <Comment>), React tears down the old tree, unmounting components and destroying their state, and builds the new one from scratch.
  • Same DOM element type: React keeps the same underlying DOM node and only updates the changed attributes, then recurses on the children.
  • Same component type: the component instance stays the same, so state is maintained across renders; React updates its props and renders it again.

When recursing on a list of children, React walks both lists at the same time. Without keys, inserting an element at the start forces React to mutate every child; with keys, React can match children by identity and just insert the new one.(12,14) This is the same mechanism that preserves or resets state by position, described in section 5.2.(38)

10.3 Fiber architecture

Fiber is the reconciliation engine introduced in React 16. Its main goal is to enable incremental rendering of the virtual DOM.(11) Andrew Clark's design notes describe incremental rendering as the ability to split rendering work into chunks and spread it out over multiple frames, together with the ability to pause, abort or reuse work as new updates come in and to assign priority to different types of update.(65)

A fiber is a JavaScript object that represents a unit of work. Clark describes it as a reimplementation of the call stack specialised for React components, a "virtual stack frame" that React can keep in memory and execute whenever it wants, rather than relying on the JavaScript call stack, which must run to completion.(65) Each fiber corresponds to a component instance or DOM element and holds its type, key, props, pending work, and pointers to its child, sibling and parent (return) fibers. Work happens in two phases: a render (reconciliation) phase, which can be interrupted, and a commit phase, which applies the changes to the host environment in one go.(65)

10.4 Concurrent rendering

React 18 introduced concurrent rendering, a behind-the-scenes mechanism that lets React prepare multiple versions of the UI at the same time. Its key property is that rendering is interruptible: React may start rendering an update, pause in the middle, and continue later, or even abandon an in-progress render altogether. React guarantees that the UI appears consistent even if a render is interrupted, by waiting to perform DOM mutations until the end, once the entire tree has been evaluated.(66) Concurrent rendering is used when you opt into concurrent features such as startTransition, useDeferredValue and Suspense, and requires the createRoot API.(66,67)

10.5 Automatic batching

Batching is when React groups multiple state updates into a single re-render for better performance. Before React 18, React batched updates only inside React event handlers; updates inside promises, setTimeout, native event handlers or any other event were not batched. With createRoot, React 18 batches all updates automatically, wherever they come from.(66,68) You can opt out for a specific update with flushSync, although this is rarely needed.(68)

10.6 Suspense

<Suspense fallback={...}> lets you display a fallback until its children have finished loading. Only Suspense-enabled data sources activate it: data fetching with Suspense-enabled frameworks, lazy-loading component code with lazy,(69) and reading the value of a cached promise with use. Suspense does not detect data fetched inside an effect or an event handler.(70)

If an update caused by a transition makes an already-visible component suspend, React keeps showing the existing content instead of replacing it with the fallback, which avoids jarring loading states.(60,70)

10.7 Error boundaries

By default, if a component throws during rendering, React removes its UI from the screen. An error boundary is a component that catches such errors and shows a fallback instead. It must be a class component that implements static getDerivedStateFromError (to update state and show the fallback) and optionally componentDidCatch (to log the error). There is currently no way to write an error boundary as a function component, though packages such as react-error-boundary provide one you can reuse.(22)

Error boundaries do not catch errors inside event handlers, in asynchronous code such as setTimeout callbacks, during server-side rendering, or errors thrown in the boundary itself. Use ordinary try/catch for event handlers.(71)

10.8 Portals

createPortal(children, domNode, key?) renders children into a different part of the DOM, for example a modal into document.body so that it is not clipped by a parent's overflow: hidden. A portal changes only the physical placement of the DOM node. Everything else behaves as if the children were rendered in place: they can read context from the parent tree, and events bubble up according to the React tree rather than the DOM tree.(72)

10.9 Client rendering, server rendering, hydration and streaming

Client-side rendering (CSR)

In a purely client-rendered app, the server sends a mostly empty HTML page and a JavaScript bundle. The browser downloads and runs the bundle, and createRoot(...).render(...) builds the whole DOM.(64) Nothing meaningful appears until the JavaScript has loaded and run.

Server-side rendering (SSR) and server rendering APIs

With server rendering, React renders components to HTML on the server so the browser can show content before any JavaScript runs. react-dom/server offers renderToString, which renders to a string but does not support streaming or waiting for data;(73) renderToPipeableStream, which renders to a Node.js stream;(74) and renderToReadableStream, which renders to a Web Stream for environments such as Deno and edge runtimes.(75)

Hydration

Server HTML is not interactive on its own. On the client, hydrateRoot(domNode, reactNode) attaches React to the existing HTML: React renders the same tree in the browser and attaches event handlers to the DOM produced by the server, rather than creating new nodes.(76) The tree rendered on the client must produce the same output as the server. Differences, called hydration mismatches, are treated as bugs; common causes include rendering Date.now(), random values or browser-only APIs during render.(76)

Streaming rendering and selective hydration

Before React 18, server rendering was "all or nothing" in three ways: the server had to fetch all data before sending any HTML, the client had to load all the JavaScript before hydrating anything, and it had to hydrate everything before the user could interact with anything. React 18's Suspense-based SSR architecture removes these waterfalls with two features.(66,77)

  • Streaming HTML. The server sends the shell of the page immediately, with fallbacks for any <Suspense> boundaries that are still waiting for data. When the data is ready, React streams the remaining HTML along with a small inline script that puts it in the right place.(74,77)
  • Selective hydration. Each Suspense boundary can hydrate independently, so React can start hydrating before all the code has loaded. If the user interacts with a part of the page that has not hydrated yet, React prioritises hydrating that part.(77)

Server Components

React Server Components are a newer type of component that renders ahead of time, before bundling, in an environment separate from the client app or the SSR server. They can run once at build time or for each request, and can read data directly, for example from a file system or database, without an API layer. They are used through frameworks that support them.(78)

11. React application architecture

React itself is a library for rendering UI. It does not prescribe how you handle routing, data fetching, server communication or persistence. For this reason, the React team recommends building new apps with a framework that provides these features, or composing your own stack from libraries.(5) A typical application can be thought of as five logical layers. These are logical layers, not mandatory requirements of React.

Presentation layerReact components · JSX · CSS · UI libraries
Application state and business logicHooks · Context · Redux · Zustand · TanStack Query
Routing and data accessReact Router · API clients · Fetch · Axios
Backend servicesREST APIs · GraphQL · WebSockets · Authentication
PersistencePostgreSQL · Oracle · MongoDB · Redis

11.1 Presentation layer

This is React's own territory: components, JSX and the styles applied to them. React does not prescribe a styling method; in React you specify a CSS class with className and can pass inline styles as an object to style.(7,21) Component libraries supply ready-made, accessible building blocks on top.

11.2 Application state and business logic

Built-in tools cover a lot: useState and useReducer for local state, context for sharing it, and custom hooks for reusing logic.(31,41) Libraries step in when state is global, large or comes from a server.

  • Redux is a library for predictable, centralised global state, with Redux Toolkit as the recommended way to write Redux logic.(79)
  • Zustand is a small state-management library built around hooks, with stores created by a single create call.(80)
  • TanStack Query manages server state: fetching, caching, synchronising and updating data from an API.(81)

11.3 Routing and data access

React Router maps URLs to components and can be used as a library or as a full framework.(82) For talking to servers, the browser's Fetch API provides a promise-based interface for HTTP requests,(83) and Axios is a promise-based HTTP client for the browser and Node.js.(84) Wrapping these calls in a small API client module keeps components free of URL and header details.

11.4 Backend services

React does not care what the backend is. Common choices are REST, the architectural style Roy Fielding defined for distributed hypermedia systems in his 2000 dissertation;(85) GraphQL, a query language for APIs in which the client asks for exactly the fields it needs;(86) and WebSockets, which open a two-way interactive session between browser and server for real-time features.(87) Authentication is typically handled by the backend or an identity provider, often using standards such as OAuth 2.0,(88) with the React app storing only what it needs to show the signed-in state.

11.5 Persistence

Data is ultimately stored in databases such as PostgreSQL, an open-source object-relational database;(89) Oracle Database;(90) MongoDB, a document database;(91) and Redis, an in-memory data store often used for caching, sessions and queues.(92) Client-side React code never connects to these directly. It goes through backend services, or, in frameworks that support React Server Components, server-only components can read from the database on the server.(78)

13. Summary

  • A React UI is a tree of pure components that turn props and state into JSX.(1,24)
  • JSX compiles to function calls that create React elements, which are plain descriptions of the UI.(18,19)
  • Data flows down through props; changes flow up through callbacks; shared state lives in the closest common parent or in context.(3,16,23)
  • State is a per-render snapshot tied to a position in the tree. Updates are batched, and objects must be replaced rather than mutated.(35–38)
  • Hooks must be called unconditionally at the top level. Effects synchronise with external systems and need cleanup; many effects are unnecessary.(39,43,49)
  • Rendering is trigger, render, commit. Reconciliation uses element types and keys to decide what to keep, and Fiber makes that work interruptible, which underpins concurrent features, Suspense and streaming SSR with selective hydration.(4,12,65,66,77)
  • React is one layer of an application; routing, data, backends and storage come from frameworks and libraries around it.(5)
