1. What "deploying React" means

React itself is a UI library. What you deploy is the output of a build tool or framework that wraps it. The React team now recommends starting new apps with a framework such as Next.js or React Router, or with a build tool such as Vite when you want a client-only app [1]. That choice decides what kind of infrastructure you need:

Output typeTypical toolingWhat runs in productionNatural targets
Static single-page app (SPA)Vite, React Router in SPA modeOnly files: index.html, hashed JS/CSS, imagesCDN or static host: S3 + CloudFront, Netlify, Azure SWA, Firebase, Nginx
Static site generation (SSG)Next.js static export, Astro, etc.Pre-rendered HTML per route, plus JSSame as above
Server rendering (SSR) / React Server ComponentsNext.js, React Router framework modeA Node.js (or edge) server process plus static assetsVercel, Netlify, Amplify, or containers on Kubernetes

Running vite build writes an optimised bundle to dist/ by default, with content-hashed file names for JS and CSS under dist/assets/ [2]. A static SPA is therefore just a folder of files, and everything in this article about static hosting applies to that folder.

2. Core concepts

2.1 Build-time versus runtime configuration

Vite exposes environment variables to client code through import.meta.env, and only variables prefixed with VITE_ are exposed. They are replaced statically at build time [3]. Two consequences follow. First, anything in a VITE_ variable is public, because it ends up in JavaScript that every visitor downloads, so secrets must never go there. Second, a bundle built with VITE_API_URL=https://staging… will always point at staging. If you want to build once and promote the same artifact through staging and production, which the Twelve-Factor methodology recommends by keeping config out of the build [4], you need a runtime configuration file. Section 10 shows one.

2.2 Client-side routing and the "SPA fallback"

Client-side routers change the URL with the browser History API (history.pushState) without asking the server for a new page [5]. That works until a user refreshes on /orders/42 or opens a shared link. The browser then requests /orders/42 from the server, and no such file exists. Every static host therefore needs a rule along the lines of "if the path is not a real file, serve index.html with status 200." Vite's deployment guide calls this out for each platform [6], and you will see the same rule written in a different syntax for every host below.

2.3 Caching hashed assets

HTTP caching is defined in RFC 9111 [7]. The Cache-Control header's immutable directive tells the browser that a response will not change while it is fresh, and no-cache means a cached copy must be revalidated with the server before use [8]. Because Vite puts a content hash in every asset name [2], a new deploy produces new URLs. That gives a simple, safe policy:

PathCache-ControlReason
/assets/* (hashed)public, max-age=31536000, immutableContent never changes under a given URL
/index.html and SPA fallbackno-cacheMust always reference the newest hashed bundle
Unhashed public files (favicon.ico, robots.txt)Short max-age, e.g. 3600Can change without a URL change

Common failure. If index.html is cached for a long time at the CDN or in the browser, users keep loading an old HTML file that references JavaScript files that may have been deleted. The result is a blank page after a deploy.

2.4 Immutable artifacts and environments

Continuous integration means integrating work into the mainline frequently, with each integration verified by an automated build and tests [9]. Continuous delivery extends that by keeping the mainline always deployable. In practice for React that means: build once per commit, store the artifact (a dist/ folder or a container image tagged with the commit SHA), and deploy that exact artifact to each environment in turn.

4.1 ESLint

ESLint statically analyses code to find problems, and current versions use a flat configuration file, eslint.config.js [10]. The --max-warnings=0 flag above turns warnings into a failing exit code, which is what you want in CI.

eslint.config.js
import js from '@eslint/js';
import globals from 'globals';
import reactHooks from 'eslint-plugin-react-hooks';
import tseslint from 'typescript-eslint';

export default tseslint.config(
  { ignores: ['dist', 'coverage'] },
  {
    files: ['**/*.{ts,tsx}'],
    extends: [js.configs.recommended, ...tseslint.configs.recommended],
    languageOptions: { globals: globals.browser },
    plugins: { 'react-hooks': reactHooks },
    rules: {
      ...reactHooks.configs.recommended.rules,
      'no-console': ['error', { allow: ['warn', 'error'] }],
    },
  },
);

4.2 Unit and integration tests

Vitest is a test runner that reuses Vite's configuration and transform pipeline [11]. React Testing Library encourages tests that interact with components the way a user does, by querying for roles and text rather than implementation details [12]. A component test like the one below is a "unit" test of the component, and an "integration" test when it renders several components together with a mocked network.

src/components/LoginForm.test.tsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { describe, it, expect, vi } from 'vitest';
import { LoginForm } from './LoginForm';

describe('LoginForm', () => {
  it('submits the email and password', async () => {
    const onSubmit = vi.fn();
    render(<LoginForm onSubmit={onSubmit} />);

    await userEvent.type(screen.getByLabelText(/email/i), 'ada@example.com');
    await userEvent.type(screen.getByLabelText(/password/i), 'correct horse');
    await userEvent.click(screen.getByRole('button', { name: /sign in/i }));

    expect(onSubmit).toHaveBeenCalledWith({
      email: 'ada@example.com',
      password: 'correct horse',
    });
  });
});

End-to-end tests drive a real browser against a running build. Playwright supports Chromium, Firefox and WebKit from one API [13], and is a good fit for a post-deploy smoke test against a preview URL.

e2e/smoke.spec.ts
import { test, expect } from '@playwright/test';

const BASE = process.env.BASE_URL ?? 'http://localhost:4173';

test('deep link survives a hard refresh', async ({ page }) => {
  const res = await page.goto(`${BASE}/settings/profile`);
  expect(res?.status()).toBe(200);              // SPA fallback is working
  await expect(page.getByRole('heading', { name: 'Profile' })).toBeVisible();
});

4.3 Security scanning

Three layers are worth scanning for a React app:

  • Dependencies. npm audit checks installed packages against a database of known vulnerabilities, and --audit-level sets the severity that produces a non-zero exit code [14]. Use npm ci rather than npm install in CI, because it installs exactly what the lockfile says and fails if package.json and the lockfile disagree [15].
  • Source code. Static application security testing (SAST) looks for injection risks and similar issues. The OWASP Top 10 is the usual reference list for web application risk categories [16]. GitLab ships SAST and dependency-scanning templates (Section 11.2) [17].
  • Container images. Trivy scans container images, filesystems and IaC files for known vulnerabilities and misconfigurations [18].
shell
# Fail the job on HIGH or CRITICAL findings in the image you are about to ship
trivy image --exit-code 1 --severity HIGH,CRITICAL --ignore-unfixed \
  registry.example.com/web:${GIT_SHA}

5. Managed hosting: Vercel and Netlify

Both platforms connect to a Git repository, build on every push, give each pull request its own preview URL, and serve the result from a global edge network. They differ in defaults and in how much server-side compute they offer.

5.1 Vercel

Vercel is built by the maintainers of Next.js, and Next.js on Vercel needs no configuration. The Next.js documentation also lists Node.js servers, Docker containers and static export as supported deployment options [19], so Next.js is not tied to Vercel. For a Vite SPA, project behaviour is set in vercel.json [20], including rewrites that serve index.html for client-side routes [21] and response headers.

vercel.json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "buildCommand": "npm run build",
  "outputDirectory": "dist",
  "rewrites": [
    { "source": "/((?!api/).*)", "destination": "/index.html" }
  ],
  "headers": [
    {
      "source": "/assets/(.*)",
      "headers": [
        { "key": "Cache-Control", "value": "public, max-age=31536000, immutable" }
      ]
    },
    {
      "source": "/(.*)",
      "headers": [
        { "key": "X-Content-Type-Options", "value": "nosniff" },
        { "key": "Referrer-Policy", "value": "strict-origin-when-cross-origin" }
      ]
    }
  ]
}

Rewrites apply only when no static file matches the path, so /assets/index-abc123.js is still served as itself. The negative lookahead keeps /api/* free for serverless functions.

5.2 Netlify

Netlify reads build settings, redirects and headers from netlify.toml in the repository [22]. A redirect with status 200 is a rewrite: the URL in the address bar stays the same while different content is served [23], which is exactly the SPA fallback.

netlify.toml
[build]
  command = "npm run build"
  publish = "dist"

[build.environment]
  NODE_VERSION = "24"

# Proxy API calls to a backend so the browser sees a single origin (no CORS)
[[redirects]]
  from   = "/api/*"
  to     = "https://api.example.com/:splat"
  status = 200
  force  = true

# SPA fallback: must come after more specific rules
[[redirects]]
  from   = "/*"
  to     = "/index.html"
  status = 200

[[headers]]
  for = "/assets/*"
  [headers.values]
    Cache-Control = "public, max-age=31536000, immutable"

# Deploy-preview builds can point at a staging API
[context.deploy-preview.environment]
  VITE_API_URL = "https://staging-api.example.com"

6. AWS: S3 + CloudFront, and Amplify

6.1 S3 + CloudFront

Amazon S3 can host a static website directly, but S3 website endpoints do not support HTTPS [24]. The production pattern is therefore a private S3 bucket behind a CloudFront distribution. CloudFront reaches the bucket through origin access control (OAC), which AWS recommends over the older origin access identity, and the bucket policy allows reads only from that distribution [25].

Because the bucket is private, a request for /orders/42 returns 403 (or 404) from S3. CloudFront custom error responses can replace that with /index.html and a 200 status [26].

infra/main.tf (Terraform, abridged)
resource "aws_s3_bucket" "site" {
  bucket = "example-web-prod"
}

resource "aws_s3_bucket_public_access_block" "site" {
  bucket                  = aws_s3_bucket.site.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

resource "aws_cloudfront_origin_access_control" "site" {
  name                              = "example-web-oac"
  origin_access_control_origin_type = "s3"
  signing_behavior                  = "always"
  signing_protocol                  = "sigv4"
}

resource "aws_cloudfront_distribution" "site" {
  enabled             = true
  default_root_object = "index.html"
  aliases             = ["www.example.com"]

  origin {
    origin_id                = "s3-site"
    domain_name              = aws_s3_bucket.site.bucket_regional_domain_name
    origin_access_control_id = aws_cloudfront_origin_access_control.site.id
  }

  default_cache_behavior {
    target_origin_id       = "s3-site"
    viewer_protocol_policy = "redirect-to-https"
    allowed_methods        = ["GET", "HEAD"]
    cached_methods         = ["GET", "HEAD"]
    compress               = true
    # AWS managed "CachingOptimized" policy; it honours origin Cache-Control
    cache_policy_id        = "658327ea-f89d-4fab-a63d-7e88639e58f6"
  }

  # SPA fallback: private S3 returns 403 for unknown keys
  custom_error_response {
    error_code            = 403
    response_code         = 200
    response_page_path    = "/index.html"
    error_caching_min_ttl = 0
  }
  custom_error_response {
    error_code            = 404
    response_code         = 200
    response_page_path    = "/index.html"
    error_caching_min_ttl = 0
  }

  restrictions {
    geo_restriction { restriction_type = "none" }
  }
  viewer_certificate {
    acm_certificate_arn      = var.acm_certificate_arn   # must be in us-east-1
    ssl_support_method       = "sni-only"
    minimum_protocol_version = "TLSv1.2_2021"
  }
}

data "aws_iam_policy_document" "site" {
  statement {
    actions   = ["s3:GetObject"]
    resources = ["${aws_s3_bucket.site.arn}/*"]
    principals {
      type        = "Service"
      identifiers = ["cloudfront.amazonaws.com"]
    }
    condition {
      test     = "StringEquals"
      variable = "AWS:SourceArn"
      values   = [aws_cloudfront_distribution.site.arn]
    }
  }
}

resource "aws_s3_bucket_policy" "site" {
  bucket = aws_s3_bucket.site.id
  policy = data.aws_iam_policy_document.site.json
}

The custom error response applies to every path, including a genuinely missing image, which will now return index.html. If that matters, use a CloudFront Function on viewer request to rewrite only extension-less paths to /index.html, and drop the error responses.

Upload in two passes so each set of files gets the right cache header, then invalidate only the files whose URLs do not change. CloudFront invalidation removes objects from edge caches before they expire, and invalidation paths beyond a monthly free allowance are billed [27].

scripts/deploy-s3.sh
#!/usr/bin/env bash
set -euo pipefail
: "${BUCKET:?}" "${DISTRIBUTION_ID:?}"

# 1. Hashed assets: cache for a year. Upload first so the new index.html
#    never references a file that is not there yet.
aws s3 sync dist/assets "s3://${BUCKET}/assets" \
  --cache-control "public, max-age=31536000, immutable"

# 2. Everything else (index.html, favicon, robots.txt): always revalidate.
#    --delete removes files that no longer exist locally, but we exclude
#    assets/ so users mid-session on the old bundle keep working.
aws s3 sync dist "s3://${BUCKET}" \
  --exclude "assets/*" \
  --cache-control "no-cache" \
  --delete

# 3. Invalidate only the unhashed entry points.
aws cloudfront create-invalidation \
  --distribution-id "${DISTRIBUTION_ID}" \
  --paths "/index.html" "/"

6.2 AWS Amplify Hosting

Amplify Hosting combines Git-triggered CI/CD with managed hosting, and also supports server-rendered Next.js apps [28]. The build is described in amplify.yml, with preBuild and build phases, an artifacts.baseDirectory to publish, and paths to cache between builds [28].

amplify.yml
version: 1
frontend:
  phases:
    preBuild:
      commands:
        - nvm use 24
        - npm ci
    build:
      commands:
        - npm run lint
        - npm test
        - npm run build
  artifacts:
    baseDirectory: dist
    files:
      - '**/*'
  cache:
    paths:
      - node_modules/**/*

For SPA routing, the Amplify documentation gives a rewrite rule that sends every path without a known static file extension to /index.html with type 200 (Rewrite) [29]:

Amplify console → Rewrites and redirects (JSON)
[
  {
    "source": "</^[^.]+$|\\.(?!(css|gif|ico|jpg|js|png|txt|svg|woff|woff2|ttf|map|json|webp)$)([^.]+$)/>",
    "target": "/index.html",
    "status": "200"
  }
]

7. Azure Static Web Apps and Firebase Hosting

7.1 Azure Static Web Apps

Azure Static Web Apps reads routing, headers and fallback rules from staticwebapp.config.json. Its navigationFallback setting serves a given file for requests that match no static file, with an exclude list for paths that should 404 normally [30].

public/staticwebapp.config.json
{
  "navigationFallback": {
    "rewrite": "/index.html",
    "exclude": ["/assets/*", "/*.{png,jpg,gif,svg,ico,txt}"]
  },
  "routes": [
    { "route": "/admin/*", "allowedRoles": ["administrator"] }
  ],
  "globalHeaders": {
    "X-Content-Type-Options": "nosniff",
    "Referrer-Policy": "strict-origin-when-cross-origin"
  },
  "mimeTypes": { ".json": "application/json" }
}

Placing the file in Vite's public/ folder copies it into dist/. When you create the resource from the Azure portal it generates a GitHub Actions workflow. The app_location, api_location and output_location inputs tell the deploy action where the source, optional Functions API and build output live [31].

.github/workflows/azure-static-web-apps.yml

Firebase Hosting is configured in the hosting block of firebase.json: public names the directory to deploy, rewrites handles the SPA fallback, and headers sets caching [32]. 8. Nginx: web server and reverse proxy

When you run your own servers or containers, Nginx usually serves the static build and proxies API calls to a backend. Two directives do most of the work. try_files checks for files in order and falls back to the last argument [34], which implements the SPA fallback. proxy_pass forwards a location to an upstream server [35], which removes the need for CORS because the browser sees one origin. The gzip module compresses text responses on the fly [36].

nginx/default.conf
upstream api_backend {
    server api:3000;              # Docker Compose service or Kubernetes Service name
    keepalive 32;
}

server {
    listen 8080;                  # non-root port (see Section 9)
    server_name _;
    root  /usr/share/nginx/html;
    index index.html;

    # --- Compression -------------------------------------------------------
    gzip on;
    gzip_comp_level 5;
    gzip_min_length 1024;
    gzip_types text/css application/javascript application/json image/svg+xml;
    gzip_vary on;

    # --- Security headers --------------------------------------------------
    add_header X-Content-Type-Options "nosniff" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;
    add_header Content-Security-Policy "default-src 'self'; img-src 'self' data:; connect-src 'self' https://*.ingest.sentry.io; frame-ancestors 'none'" always;

    # --- Hashed assets: cache forever --------------------------------------
    location /assets/ {
        add_header Cache-Control "public, max-age=31536000, immutable";
        # add_header in a location replaces inherited ones, so repeat security headers
        add_header X-Content-Type-Options "nosniff" always;
        try_files $uri =404;      # a missing asset must be a real 404, not index.html
    }

    # --- API reverse proxy -------------------------------------------------
    location /api/ {
        proxy_pass http://api_backend/;           # trailing slash strips the /api prefix
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 30s;
    }

    # --- Health check for load balancers / Kubernetes probes ---------------
    location = /healthz {
        access_log off;
        default_type text/plain;
        return 200 "ok\n";
    }

    # --- SPA fallback ------------------------------------------------------
    location / {
        add_header Cache-Control "no-cache";
        add_header X-Content-Type-Options "nosniff" always;
        try_files $uri $uri/ /index.html;
    }
}

Nginx header inheritance. add_header directives are inherited from the enclosing level only if the current level defines none [34]. As soon as a location adds its own Cache-Control, the server-level security headers disappear for that location unless you repeat them, as done above. A shared include file avoids the repetition.

A Content Security Policy restricts where scripts, styles and connections may come from, which limits the damage of cross-site scripting [37]. Note that connect-src must list every telemetry endpoint from Section 12, or the browser will block those requests.

9. Docker: containerizing a React app

A multi-stage build uses several FROM statements in one Dockerfile and copies only the needed output from earlier stages into the final image [38]. For React, the Node.js toolchain (hundreds of megabytes) stays in the build stage and the final image contains only Nginx and the static files. Docker's best-practice guide also recommends ordering instructions so that rarely changing layers (dependency install) come before frequently changing ones (source copy), to maximise cache hits [39].

Dockerfile
# syntax=docker/dockerfile:1

# ---------- Stage 1: install dependencies ----------
FROM node:24-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci

# ---------- Stage 2: test and build ----------
FROM deps AS build
COPY . .
ARG VITE_APP_VERSION=dev
ENV VITE_APP_VERSION=$VITE_APP_VERSION
RUN npm run lint && npm test && npm run build

# ---------- Stage 3: runtime ----------
# Unprivileged variant runs as a non-root user and listens on 8080
FROM nginxinc/nginx-unprivileged:1.28-alpine AS runtime
COPY nginx/default.conf /etc/nginx/conf.d/default.conf
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 8080
HEALTHCHECK --interval=30s --timeout=3s CMD wget -qO- http://127.0.0.1:8080/healthz || exit 1

The nginxinc/nginx-unprivileged image runs Nginx as a non-root user and listens on port 8080 by default, because non-root processes cannot bind ports below 1024 [40]. A .dockerignore file keeps local folders out of the build context, which makes builds faster and prevents a host node_modules or .env file from leaking into the image [41].

10. Kubernetes: container orchestration

Kubernetes runs your image as a set of identical Pods managed by a Deployment, which replaces Pods gradually during an update according to its rolling-update strategy (maxSurge, maxUnavailable) [43]. A readiness probe decides whether a Pod receives traffic, and a liveness probe decides whether it should be restarted [44]. A Service gives the Pods a stable address, an Ingress routes external HTTP(S) traffic to Services and requires an ingress controller to be installed [45], and a HorizontalPodAutoscaler changes the replica count based on observed metrics such as CPU [46].

11.3 Jenkins

A declarative Jenkinsfile describes the pipeline as stages, with post blocks for cleanup and notifications, when conditions for branch-specific stages, and input for manual approval [52]. With the Docker Pipeline plugin, agent { docker { … } } runs stages inside a container so build agents do not need Node.js installed [53].

Jenkinsfile
pipeline {
  agent none
  options {
    timestamps()
    disableConcurrentBuilds()
    timeout(time: 30, unit: 'MINUTES')
  }
  environment {
    REGISTRY = 'registry.example.com'
    IMAGE    = "${REGISTRY}/web:${env.GIT_COMMIT.take(7)}"
  }
  stages {
    stage('Verify and build') {
      agent { docker { image 'node:24-alpine'; args '-v $HOME/.npm:/root/.npm' } }
      stages {
        stage('Install') { steps { sh 'npm ci' } }
        stage('Checks') {
          parallel {
            stage('ESLint')   { steps { sh 'npm run lint' } }
            stage('Tests')    { steps { sh 'npm test' } }
            stage('Security') { steps { sh 'npm run audit' } }
          }
        }
        stage('Build') {
          steps {
            sh "VITE_APP_VERSION=${env.GIT_COMMIT.take(7)} npm run build"
            stash name: 'dist', includes: 'dist/**'
          }
        }
      }
    }
    stage('Image') {
      when { branch 'main' }
      agent { label 'docker' }
      steps {
        withCredentials([usernamePassword(credentialsId: 'registry',
                         usernameVariable: 'U', passwordVariable: 'P')]) {
          sh '''
            echo "$P" | docker login -u "$U" --password-stdin "$REGISTRY"
            docker build -t "$IMAGE" .
            docker push "$IMAGE"
          '''
        }
      }
    }
    stage('Deploy to production') {
      when { branch 'main' }
      agent { label 'kubectl' }
      steps {
        input message: 'Deploy to production?', ok: 'Deploy'
        withKubeConfig([credentialsId: 'prod-kubeconfig']) {
          sh 'kubectl set image deployment/web web="$IMAGE"'
          sh 'kubectl rollout status deployment/web --timeout=120s'
        }
      }
    }
  }
  post {
    failure { echo "Build failed: ${env.BUILD_URL}" }
  }
}

The withKubeConfig step comes from the Kubernetes CLI plugin. stash and unstash move files between stages that run on different agents.

12.1 Web Vitals as your frontend SLIs

Core Web Vitals are Google's user-centric performance metrics. The current set is Largest Contentful Paint (good at or below 2.5 s), Interaction to Next Paint (at or below 200 ms) and Cumulative Layout Shift (at or below 0.1), each assessed at the 75th percentile of page loads [56]. Every RUM tool below collects them. You can also send them anywhere yourself:

src/vitals.ts
import { onCLS, onINP, onLCP, type Metric } from 'web-vitals';

function send(metric: Metric) {
  const body = JSON.stringify({ name: metric.name, value: metric.value,
                                rating: metric.rating, id: metric.id,
                                page: location.pathname });
  // sendBeacon survives page unload; fall back to fetch keepalive
  if (!navigator.sendBeacon?.('/api/vitals', body)) {
    fetch('/api/vitals', { method: 'POST', body, keepalive: true });
  }
}

12.5 OpenTelemetry

OpenTelemetry is a vendor-neutral standard and SDK set. In the browser, a WebTracerProvider with auto-instrumentations creates spans for document load, fetch and XHR calls, and an OTLP exporter sends them to a collector [61]. OTLP is the protocol's wire format over HTTP or gRPC [62], and nearly every backend in this section (Datadog, New Relic, Grafana Tempo, Sentry) accepts it, which means you can switch vendors without re-instrumenting.

src/otel.ts
import { WebTracerProvider } from '@opentelemetry/sdk-trace-web';
import { BatchSpanProcessor } from '@opentelemetry/sdk-trace-base';
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-http';
import { ZoneContextManager } from '@opentelemetry/context-zone';
import { registerInstrumentations } from '@opentelemetry/instrumentation';
import { getWebAutoInstrumentations } from '@opentelemetry/auto-instrumentations-web';
import { resourceFromAttributes } from '@opentelemetry/resources';
import { ATTR_SERVICE_NAME, ATTR_SERVICE_VERSION } from '@opentelemetry/semantic-conventions';

const provider = new WebTracerProvider({
  resource: resourceFromAttributes({
    [ATTR_SERVICE_NAME]: 'web',
    [ATTR_SERVICE_VERSION]: import.meta.env.VITE_APP_VERSION,
  }),
  spanProcessors: [
    new BatchSpanProcessor(
      new OTLPTraceExporter({ url: 'https://otel.example.com/v1/traces' })
    ),
  ],
});

provider.register({ contextManager: new ZoneContextManager() });

registerInstrumentations({
  instrumentations: [
    getWebAutoInstrumentations({
      '@opentelemetry/instrumentation-fetch': {
        // add W3C traceparent headers to calls to our own API
        propagateTraceHeaderCorsUrls: [/^https:\/\/api\.example\.com\//],
      },
    }),
  ],
});

12.7 LogRocket

LogRocket records sessions so you can replay what a user saw, together with console output, network requests and errors. The SDK is started with LogRocket.init and your app ID, and identify attaches a user to the session [66].

src/logrocket.ts
import LogRocket from 'logrocket';
import setupLogRocketReact from 'logrocket-react';

LogRocket.init('example-org/web', {
  release: import.meta.env.VITE_APP_VERSION,
  dom: { inputSanitizer: true },                // do not record typed values
  network: {
    requestSanitizer: (request) => {
      if (request.headers['Authorization']) request.headers['Authorization'] = '[redacted]';
      return request;
    },
  },
});
setupLogRocketReact(LogRocket);

export function onLogin(user: { id: string; plan: string }) {
  LogRocket.identify(user.id, { plan: user.plan });   // avoid sending raw PII
}

Privacy and performance. Session replay and RUM can capture personal data and add JavaScript weight. Mask inputs by default, sample sessions rather than recording all of them, and load non-critical SDKs after the first paint. Choose one replay tool rather than running several in parallel.

12.8 Logging

For containerised deployments, Nginx writes access logs to stdout and errors to stderr in the official images, and the cluster's log agent ships them to a store such as Loki, Datadog or New Relic. A JSON log format makes those logs queryable:

nginx/nginx.conf (http block excerpt)
log_format json escape=json
  '{"time":"$time_iso8601","status":$status,"method":"$request_method",'
  '"uri":"$request_uri","bytes":$body_bytes_sent,"rt":$request_time,'
  '"ua":"$http_user_agent","trace":"$http_traceparent"}';
access_log /dev/stdout json;

Logging the W3C traceparent header lets you jump from a slow request in the logs to the matching OpenTelemetry trace.

Exercise 1. The refresh 404

A Vite SPA served by Nginx works when users click around, but refreshing on /reports/2026 returns 404 Not Found. The server block is below. Explain the cause and fix it so that missing files under /assets/ still return 404.

server {
    listen 8080;
    root /usr/share/nginx/html;
    location / {
        try_files $uri =404;
    }
}
Show solution

The router changed the URL with history.pushState [5], but on refresh the browser asks Nginx for /reports/2026, which is not a file. try_files $uri =404 then returns 404. Fall back to index.html for app routes and keep a strict rule for assets [34]:

location /assets/ {
    try_files $uri =404;
}
location / {
    try_files $uri $uri/ /index.html;
}

Exercise 2. Blank page after deploy

After each release a few users see a blank page with the console error Failed to load module script … /assets/index-9a1b2c.js 404. The CDN caches everything for 24 hours. Explain what is happening and write the cache policy that fixes it.

Show solution

Users get a cached old index.html that references the previous hashed bundle. The deploy removed that bundle (for example with aws s3 sync --delete), so the request 404s. Fix it in two ways at once:

  1. Serve index.html with Cache-Control: no-cache so browsers and CDNs revalidate it each time, and serve /assets/* with public, max-age=31536000, immutable [8].
  2. Do not delete old assets immediately. Users with the app already open may still lazy-load chunks from the previous build. Exclude assets/ from --delete, and clean up old assets on a schedule (for example with an S3 lifecycle rule).

Then invalidate only /index.html and / on CloudFront after each deploy [27].

Exercise 3. Review a Dockerfile

List at least five problems with this Dockerfile and rewrite it.

FROM node:latest
COPY . .
RUN npm install
RUN npm run build
EXPOSE 5173
CMD ["npm", "run", "dev"]
Show solution
  1. node:latest is unpinned and large. Pin a version and prefer a slim or Alpine variant.
  2. COPY . . before installing busts the dependency cache on every source change. Copy the lockfile first [39].
  3. npm install may change the lockfile. Use npm ci for reproducible installs [15].
  4. Without a .dockerignore, the host's node_modules and .env enter the image [41].
  5. It runs the Vite dev server in production: unoptimised, with dev tooling exposed. Serve dist/ from Nginx instead.
  6. The final image contains the whole Node toolchain and source code. Use a multi-stage build [38].
  7. It runs as root. Use a non-root runtime image [40].

The rewritten file is the Dockerfile in Section 9.

Exercise 4. One image, many environments

Your team builds a separate Docker image for staging and production because VITE_API_URL differs. QA tested the staging image, but production broke. Explain why separate builds are risky and describe a design that ships the exact image QA tested.

Show solution

Vite inlines import.meta.env.VITE_* at build time [3], so two builds are two different artifacts. Dependency resolution, build tooling or the commit itself can differ between them, and production runs code that nobody tested. Twelve-Factor recommends strict separation of config from code [4].

Build once, tag the image with the commit SHA, and inject configuration at runtime: load /config.js from index.html, read it through a typed config module, and mount a different config.js per environment from a ConfigMap (Section 10.1). Serve config.js with no-cache. Remember that this file is public, so it must contain only public values such as API URLs and DSNs, never secrets.

Exercise 5. Zero-downtime rollout arithmetic

A Deployment has replicas: 4, maxSurge: 25% and maxUnavailable: 25%. (a) What are the most and fewest Pods that may exist and be available during a rollout? (b) A new image has a bug and its Pods never become ready. What happens with and without a readiness probe? (c) Which settings guarantee capacity never drops below 4?

Show solution

(a) 25% of 4 is 1 for both settings (surge rounds up, unavailable rounds down) [43]. So at most 4 + 1 = 5 Pods exist, and at least 4 − 1 = 3 must be available.

(b) With a readiness probe, new Pods never become Ready, so the rollout stalls after replacing at most one old Pod and the Service keeps sending traffic only to ready old Pods [44]. kubectl rollout status times out and the pipeline can run kubectl rollout undo. Without a probe, Kubernetes treats a running container as ready, routes users to broken Pods and keeps rolling, so the outage reaches 100%.

(c) maxUnavailable: 0 with maxSurge: 1 (or more), as in Section 10.2, plus a readiness probe.

Exercise 6. Gate the deploy

Modify a GitHub Actions workflow so that (a) pull requests run lint and tests but never deploy, (b) pushes to main deploy only after lint, tests and the build pass, (c) two merges in quick succession do not deploy at the same time, and (d) no long-lived AWS keys are stored in GitHub.

Show solution

See the workflow in Section 11.1. The key parts are:

deploy:
  if: github.ref == 'refs/heads/main' && github.event_name == 'push'   # (a)
  needs: e2e                     # (b) e2e needs build, build needs lint/test/security
  environment: production        # optional manual approval

Exercise 7. Unreadable stack traces

Sentry shows errors like TypeError: Cannot read properties of undefined (reading 'map') at a (index-4f2e.js:1:48213). Explain why and list the steps to get readable traces without exposing your source code publicly.

Show solution

The bundle is minified, so names and line numbers refer to the compressed output. Sentry needs the matching source maps [58]:

  1. Generate maps in the build with build.sourcemap: 'hidden', which writes .map files without adding a sourceMappingURL comment to the bundle.
  2. Upload them in CI with @sentry/vite-plugin, using an auth token stored as a CI secret.
  3. Set the same release in the plugin and in Sentry.init (for example the git SHA) so events match the right maps [57].
  4. Delete the .map files from dist/ after upload (filesToDeleteAfterUpload) so they are never deployed.

Exercise 8. OpenTelemetry CORS failure

After adding the OpenTelemetry browser SDK, the console shows a CORS error for POST https://otel.example.com/v1/traces, and backend traces are not linked to frontend spans. Fix both problems.

Show solution
  1. Exporter CORS. The browser sends a preflight request to the collector. Add your site's origin to receivers.otlp.protocols.http.cors.allowed_origins in the collector config (Section 12.5). Also add the collector host to the page's CSP connect-src [37].
  2. Trace propagation. By default, the fetch instrumentation adds traceparent only to same-origin requests. List the API in propagateTraceHeaderCorsUrls [61], and make the API's CORS policy accept the traceparent (and tracestate) request headers. The backend's OpenTelemetry SDK then continues the same trace.
