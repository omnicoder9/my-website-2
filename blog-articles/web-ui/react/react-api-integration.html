1. Why integration deserves its own design

React is a library for rendering user interfaces; it deliberately ships no networking layer. Every byte that travels between a React app and a backend goes through browser platform APIs: fetch() and XMLHttpRequest for request/response traffic [1], the WebSocket interface for full-duplex connections [2], and EventSource for server-to-client streams [3]. Libraries such as Axios, TanStack Query or Apollo Client are layers on top of those primitives, not replacements for them.

That has an important consequence, stated in the brief for this article: a React frontend can work with virtually any backend that exposes a suitable interface. The browser does not know, or care, whether a response was produced by Java, C#, Python, JavaScript or Go. What matters is the contract: the protocol (HTTP, WebSocket), the message format (JSON, Protocol Buffers), and the semantics both sides agree on.

The data a component shows from a backend is server state: it is owned remotely, can change without the UI knowing, and must be fetched asynchronously. React's own documentation notes that fetching inside useEffect is possible but that you then have to handle race conditions, caching and waterfalls yourself, and recommends a framework's data-fetching mechanism or a client-side cache library instead [4]. Much of this article is about doing that well.

2. HTTP fundamentals every React developer needs

2.1 Methods, safety and idempotency

HTTP semantics are defined in RFC 9110 [5]. Two method properties matter for client code. A safe method is read-only by contract: GET, HEAD, OPTIONS and TRACE. An idempotent method can be repeated with the same effect as sending it once: the safe methods plus PUT and DELETE [5]. POST and PATCH are neither, which is why a client should not blindly retry a failed POST: it may create a duplicate. Libraries that retry automatically (TanStack Query retries failed queries, but not mutations, by default [6]) follow the same reasoning.

Table 1. Common methods and their properties (RFC 9110 §9)
MethodTypical useSafeIdempotent
GETRead a resource or collectionYesYes
POSTCreate a subordinate resource; run a processNoNo
PUTReplace a resource's whole stateNoYes
PATCHPartially modify a resourceNoNo (not guaranteed)
DELETERemove a resourceNoYes

2.2 Status codes

Status codes fall into five classes: 1xx informational, 2xx successful, 3xx redirection, 4xx client error and 5xx server error [5]. Client code should branch on the class first (is it 2xx?) and on specific codes only when behaviour differs, for example 401 (re-authenticate), 404 (show "not found"), 409 (conflict), 422 (validation) or 429 (back off, honouring Retry-After [7]).

2.3 Same-origin policy and CORS

When a React dev server runs at http://localhost:5173 and the API at http://localhost:8080, they are different origins. Browsers then require the server to opt in through Cross-Origin Resource Sharing (CORS) response headers such as Access-Control-Allow-Origin. Requests that are not "simple" (for example, a JSON body with Content-Type: application/json, or a custom Authorization header) trigger a preflight OPTIONS request first. If the request carries credentials, the server must echo a specific origin rather than the wildcard * and send Access-Control-Allow-Credentials: true [8]. CORS is enforced by the browser, so it is always fixed on the server, or avoided in development with a dev-server proxy (section 12.4).

2.4 Caching

HTTP has its own caching model (Cache-Control, ETag, conditional requests with If-None-Match) defined in RFC 9111 [9]. It operates below your JavaScript and composes with in-memory caches such as TanStack Query's: the browser may answer a fetch() from its HTTP cache, and the library decides when to call fetch() at all.

3. The Fetch API

The Fetch API is the browser's native, promise-based interface for HTTP requests, standardized by WHATWG [1,10]. It is available in every modern browser and in Node.js 18 and later, so it needs no dependency.

3.1 Two facts that cause most Fetch bugs

  1. A fetch() promise does not reject on HTTP error statuses. It rejects only on network failure (or abort); a 404 or 500 resolves normally with response.ok === false [11,12]. You must check ok or status yourself.
  2. The body is a stream that you read once, with response.json(), .text(), .blob() and similar methods, each of which returns a promise [1].

3.2 A reusable, typed helper

Wrapping fetch() once gives every component consistent error handling. The helper below throws for non-2xx responses and understands the standard application/problem+json error format of RFC 9457 [13].

3.3 Fetching in an effect, correctly

If you fetch inside useEffect, you must handle the case where the component re-renders with new inputs, or unmounts, before the response arrives. React's documentation shows this "race condition" and recommends ignoring stale results in the cleanup function [14]. Cancelling the request with an AbortController is better still, because it also frees the network connection [15]. In development with Strict Mode, React runs setup, then cleanup, then setup again, precisely to surface missing cleanup [4].

This pattern is correct but grows quickly once you need caching, deduplication, retries and refetching. Section 6 replaces it with TanStack Query.

4. Axios

Axios is a promise-based HTTP client for the browser and Node.js; in the browser it uses XMLHttpRequest, and in Node.js the native http module [16]. Its main differences from raw fetch():

  • Automatic JSON serialization of request bodies and parsing of responses [16].
  • It rejects for responses outside the 2xx range by default (configurable with validateStatus), exposing error.response, error.request and error.config [17].
  • Request and response interceptors for cross-cutting logic such as auth headers, logging and token refresh [18].
  • Cancellation through the standard AbortController signal option; the older CancelToken API is deprecated [19].

The Authorization: Bearer scheme used above is defined for OAuth 2.0 access tokens in RFC 6750 [20]. Where to keep the token is a security decision discussed in section 12.1.

5. REST: resource-oriented APIs

REST (Representational State Transfer) is the architectural style Roy Fielding defined in his 2000 dissertation. Its constraints are client–server separation, statelessness, cacheability, a uniform interface, a layered system and, optionally, code-on-demand [21]. In practice, "REST API" usually means an HTTP API where:

  • URLs identify resources (/projects/42/tasks), not actions.
  • HTTP methods carry the verb with their RFC 9110 semantics [5].
  • Status codes carry the outcome, and errors use a consistent body such as RFC 9457 problem details [13].
  • The contract is often described with the OpenAPI Specification, from which typed clients can be generated [22].

6. TanStack Query: server state in React

TanStack Query (formerly React Query) is a library for fetching, caching, synchronizing and updating server state; it is transport-agnostic, so the query function can use fetch, Axios, graphql-request or anything returning a promise [23]. Its defaults are worth knowing because they explain most "why did it refetch?" questions [6]:

  • Cached data is considered stale immediately (staleTime: 0), and stale queries refetch on mount, on window refocus and on network reconnect.
  • Inactive query data is garbage-collected after five minutes (gcTime).
  • Failed queries are retried three times with exponential backoff on the client.

A query is identified by its query key, an array that must include every variable the query function depends on [24].

Mutations are for create, update and delete operations; after a successful mutation you typically invalidate related queries so they refetch [25], or update the cache optimistically and roll back on error [26] (see Exercise 4).

7. GraphQL, Apollo Client, Relay and graphql-request

7.1 Concepts

GraphQL is a query language and runtime specified by the GraphQL Foundation. A server publishes a strongly typed schema; clients send operations (queries, mutations, subscriptions) that select exactly the fields they need, and the response mirrors the shape of the selection [27,28]. Over HTTP, an operation is conventionally sent as a POST with a JSON body containing query, variables and optionally operationName, as described by the GraphQL-over-HTTP draft [29].

A response may contain both data and an errors array; partial success is part of the specification [27]. With the traditional application/json response type, servers commonly return HTTP 200 even when errors is present, so a GraphQL client must inspect errors, not just the status code [29].

7.2 Apollo Client

Apollo Client is a comprehensive GraphQL state-management library with a normalized in-memory cache, React hooks and devtools [30]. In Apollo Client 4, the React hooks are imported from @apollo/client/react and the HTTP endpoint is configured with an explicit HttpLink [31].

7.3 Relay

Relay is Meta's GraphQL client for React. It is built around fragments colocated with the components that use them and an ahead-of-time Relay compiler that validates and optimizes queries at build time [32]. It asks more of the schema (for example, the Relay conventions for global object identification and connections) and pays that back with strong guarantees at scale.

7.4 graphql-request

graphql-request is a minimal GraphQL client for browsers and Node.js: it sends an operation and returns a promise, with no cache of its own [33]. That makes it a good partner for TanStack Query, which supplies the caching.

graphql-request throws when the response contains errors, so the GraphQL-level failures from section 7.1 surface as rejected promises [33].

8. WebSockets and Socket.IO

8.1 The protocol

The WebSocket protocol (RFC 6455) starts as an HTTP/1.1 request with an Upgrade: websocket header; after the server answers 101 Switching Protocols, both sides exchange framed messages over the same TCP connection in either direction at any time [34]. URLs use ws:// or, over TLS, wss://. The browser's WebSocket interface exposes open, message, error and close events and a send() method [2]. It does not reconnect automatically and has no built-in concept of rooms, acknowledgements or request/response, so applications add those themselves or use a library.

8.2 Socket.IO

Socket.IO is a library for low-latency, bidirectional, event-based communication. It adds automatic reconnection, packet buffering while disconnected, acknowledgements, broadcasting to rooms and namespaces, and a fallback to HTTP long-polling when WebSockets are unavailable [35]. Its documentation stresses that Socket.IO is not a WebSocket implementation: it uses WebSocket as a transport when it can but adds its own protocol, so a Socket.IO client cannot connect to a plain WebSocket server, and the reverse is also true [35].

The client API (io(), emit, on, off, acknowledgements as a trailing callback) is documented in the Socket.IO v4 client reference [36].

9. Server-Sent Events

Server-Sent Events (SSE) are specified in the HTML Living Standard. The server keeps an HTTP response open with Content-Type: text/event-stream and writes UTF-8 text events; the browser's EventSource interface parses them and dispatches DOM events [37,3]. SSE is one-directional (server to client), but it has properties WebSockets lack out of the box: the browser reconnects automatically, the server can set the reconnection delay with a retry: field, and on reconnect the browser sends a Last-Event-ID header so the server can resume [37,38].

One limitation: over HTTP/1.1 browsers cap the number of concurrent connections per domain (six in major browsers), and each open EventSource uses one; HTTP/2 multiplexing raises that limit substantially [38]. Also note that the EventSource constructor cannot set custom request headers, so authentication normally relies on cookies (withCredentials: true for cross-origin) [3].

10. gRPC-Web

gRPC is an RPC framework in which services and messages are defined in Protocol Buffers (.proto files), a language-neutral binary serialization format, and code is generated for each language [39]. Native gRPC relies on HTTP/2 features, notably trailers, that browser JavaScript cannot control, so browsers use gRPC-Web, a variant protocol. By default a gRPC-Web client talks to a proxy, typically Envoy, which translates to native gRPC for the backend [40,41].

gRPC-Web currently supports unary calls and server-side streaming; client-side and bidirectional streaming are not supported [41]. The Connect protocol family (Connect-ES) is an alternative that generates idiomatic TypeScript clients and can speak gRPC-Web as well as its own HTTP-friendly protocol [42].

11.1 Java / Spring Boot: REST and WebSockets

Spring Web MVC maps HTTP requests to annotated controller methods; @RestController writes return values directly to the response body as JSON [43]. For real-time messaging, Spring supports STOMP, a simple text messaging protocol, over WebSocket, with @MessageMapping handlers and a broker that fans messages out to subscribers [44]. Cross-origin access can be enabled per controller with @CrossOrigin or globally [45].

The Client class, brokerURL, activate() and publish() are from STOMP.js v5 and later [46].

11.2 C# / ASP.NET Core: REST and SignalR

ASP.NET Core minimal APIs define HTTP endpoints with lambdas such as app.MapGet [47]. SignalR adds real-time functionality through hubs whose methods clients can call and which can call client methods; it negotiates the best available transport among WebSockets, Server-Sent Events and long polling [48]. The JavaScript client is the @microsoft/signalr package; withAutomaticReconnect() enables reconnection, by default waiting 0, 2, 10 and 30 seconds before successive attempts [49].

11.3 Python / FastAPI: REST and WebSockets

FastAPI declares routes with decorators and validates request bodies through Pydantic models, generating an OpenAPI schema automatically [50]. WebSocket endpoints use @app.websocket [51], CORS is enabled with CORSMiddleware [52], and SSE can be served with a StreamingResponse [53].

The React side is the useWebSocket hook from section 8.1 pointed at ws://localhost:8000/ws, plus the http() helper or TanStack Query for /api/todos.

11.4 Node.js / Express: REST and GraphQL

Express defines routes with app.get, app.post and similar methods [54]. Apollo Server can be mounted in an Express app; for Apollo Server 5 with Express 5 the middleware comes from the @as-integrations/express5 package [55].

Both the Apollo Client example (7.2) and the graphql-request example (7.4) work unchanged against this server.

11.5 Node.js / NestJS: REST, GraphQL and microservices

NestJS organizes servers into modules, controllers and providers. Controllers handle REST requests with decorators such as @Get() and @Post() [56]; the @nestjs/graphql module supports code-first resolvers [57]; and the microservices package lets services communicate over transports other than HTTP, including TCP, Redis, NATS, MQTT, RabbitMQ, Kafka and gRPC [58]. The React app talks only to the HTTP or GraphQL edge; the microservice transports stay behind it.

11.6 Go / Gin: REST APIs

Gin is an HTTP web framework for Go with a fast router, JSON binding and validation, and middleware support [59]. CORS is provided by the gin-contrib/cors middleware [60].

12. Cross-cutting concerns

12.1 Authentication and token storage

Two common designs exist. In a cookie session, the server sets a cookie with the HttpOnly, Secure and SameSite attributes; HttpOnly keeps it out of reach of JavaScript, which limits the damage of a cross-site scripting (XSS) bug [61]. Cookies are sent automatically, so the server must defend against cross-site request forgery (CSRF), for example with SameSite plus anti-CSRF tokens [62]. With bearer tokens, the client attaches Authorization: Bearer … to each request [20]; this is not vulnerable to CSRF in the same way, but anything readable by JavaScript is readable by an XSS payload. OWASP advises against storing session identifiers in localStorage for that reason [63]. Many teams therefore keep a short-lived access token in memory and a refresh token in an HttpOnly cookie.

For cross-origin cookie requests, use credentials: "include" with fetch() or withCredentials: true with Axios, and configure the server as described in section 2.3 [8].

12.2 Errors, retries and timeouts

  • Normalize errors in one place (the http() helper or an Axios interceptor) so components see one shape.
  • Retry only idempotent operations automatically [5]; respect 429 and 503 with Retry-After [7].
  • fetch() has no timeout option of its own; combine it with AbortSignal.timeout(ms) or an AbortController [15]. Axios has a timeout option [16].
  • Show errors accessibly, for example in an element with role="alert", and offer a retry action.

12.3 Configuration per environment

Never hard-code backend URLs. With Vite, only variables prefixed VITE_ are exposed to client code through import.meta.env, and they are embedded in the bundle at build time, so they must never contain secrets [64].

12.4 Development proxy

A dev-server proxy lets the browser call /api on its own origin while Vite forwards the request to the backend, which sidesteps CORS during development [65]. Production then mirrors the arrangement with a reverse proxy or by serving the SPA from the same origin.

A practical rule of thumb: start with REST or GraphQL over fetch/Axios and a cache library; add SSE when the server only needs to push updates (notifications, progress, feeds); use WebSockets, Socket.IO or SignalR when both sides send frequently (chat, collaboration, games); and choose gRPC-Web when the organization already defines services in Protocol Buffers.

14. Exercises with solutions

Try each exercise before opening its solution.

Exercise 1. The silent 500

This code shows "Saved!" even when the server answers 500 Internal Server Error. Explain why and fix it.

Show solution

A fetch() promise only rejects on network errors; an HTTP 500 resolves with ok === false [11,12]. The request also omits Content-Type, so many servers will not parse the body as JSON.

Exercise 2. Search-as-you-type race condition

A search box fetches /api/search?q=… on every keystroke. Typing "rea" quickly sometimes shows results for "re". Write a component that always shows results for the latest query and cancels outdated requests.

Show solution

Responses can arrive out of order. Abort the previous request in the effect's cleanup [14,15].

With TanStack Query the same result follows from queryKey: ["search", q]: each key has its own cache entry, and the signal passed to queryFn lets the library cancel queries that are no longer needed [24].

Exercise 3. Refresh the token once

Your API returns 401 when the access token expires; POST /auth/refresh (using an HttpOnly refresh cookie) returns a new one. Write an Axios response interceptor that refreshes and retries the original request. If five requests fail at once, only one refresh call may be made.

Show solution

Share one in-flight refresh promise and mark retried requests so a failing refresh cannot loop [18].

Exercise 4. Optimistic toggle with rollback

Using TanStack Query, toggle a todo's done flag with PATCH /api/todos/:id. The checkbox should update instantly and revert if the request fails.

Show solution

Cancel in-flight refetches, snapshot the cache, write the optimistic value, restore it on error, and invalidate when the mutation settles [26].

Exercise 5. GraphQL partial errors

(a) Write a query that fetches only the title of open todos from the Express server in 11.4, using a variable. (b) A colleague says "the request returned 200, so it worked." Why might they be wrong?

Show solution

(b) A GraphQL response may contain both data and errors, and with application/json responses servers typically use status 200 regardless [27,29]. The client must check errors; graphql-request does so by throwing [33], and Apollo Client exposes them through error according to its error policy [30].

Exercise 6. A WebSocket that comes back

Extend the useWebSocket hook from 8.1 so it reconnects after an unexpected close with exponential backoff (1 s, 2 s, 4 s … capped at 30 s), resets the delay after a successful connection, and does not reconnect after the component unmounts.

Show solution

The browser's WebSocket never reconnects by itself [2], so the hook owns that loop.

Libraries such as Socket.IO [35], SignalR's withAutomaticReconnect() [49] and STOMP.js's reconnectDelay [46] provide this behaviour for you.

Exercise 7. Streaming job progress from FastAPI

Write a FastAPI endpoint that streams progress for a job as SSE events (event: progress, data from 0 to 100), and a React progress bar that consumes it and closes the stream at 100.

Show solution

Closing explicitly matters: when the server ends the response, EventSource treats it as a dropped connection and reconnects [37]. Events are separated by a blank line and use the text/event-stream type [38]; StreamingResponse sends the generator's output as it is produced [53].

Exercise 8. Pick the transport

For each feature, choose a communication method and justify it in one sentence: (a) an admin table of 10,000 orders with filters; (b) live notifications badge; (c) a collaborative whiteboard; (d) a dashboard backed by existing internal gRPC services; (e) a product page that needs data from four services in one round trip.

Show solution
  1. REST + TanStack Query: cacheable, paginated GET requests are the natural fit [9,23].
  2. SSE: one-way server push with automatic reconnection and resume [37].
  3. WebSockets (or Socket.IO / SignalR): both sides send frequent, low-latency messages [34,35,48].
  4. gRPC-Web through Envoy, reusing the existing .proto contracts [40].
  5. GraphQL: the client selects exactly the fields it needs across types in a single operation [28].

Summary

  • All React networking reduces to fetch/XHR, WebSocket and EventSource; libraries add ergonomics, caching and protocols on top.
  • Treat backend data as server state: use TanStack Query, Apollo Client or Relay rather than hand-written effects for anything non-trivial.
  • Know each primitive's sharp edges: fetch does not reject on 4xx/5xx, GraphQL errors can arrive with 200, WebSockets do not reconnect, SSE is one-way, gRPC-Web needs a proxy.
  • CORS and authentication are server-side configuration that the client must match.
  • Spring Boot, ASP.NET Core, FastAPI, Express, NestJS and Gin all expose the same protocols, so the React side looks almost identical whichever you choose.
