0 Introduction: what Vue protects, and what it cannot

Vue.js is a client-side rendering framework. It turns templates and reactive state into DOM nodes, and in doing so it makes the most common web vulnerability, cross-site scripting, much harder to introduce by accident. The Vue team is explicit that this protection has limits: Vue escapes content it renders through its template syntax, but it cannot protect an application that hands it untrusted templates, untrusted HTML, untrusted URLs or untrusted styles[1]. Everything outside the browser, including authentication, authorization, secrets and the dependency tree, is outside Vue's reach entirely.

This article works through thirteen topics a Vue 3 team needs to get right. Each section explains the concept, shows TypeScript source code for a Vue 3 + Vite stack (with Node/Express where a server is needed), and ends with exercises and worked solutions. Claims are referenced with numbered citations in the Vancouver style; the full reference list is at the end.

A shared-responsibility model

A useful way to frame the work is to ask, for every threat, which layer can actually enforce the control:

LayerCan enforceCannot enforce
Vue runtimeHTML-escaping of {{ }} interpolation and bound attribute valuesSafety of v-html, URLs, styles, user-supplied templates
Your Vue codeChoosing safe sinks, sanitizing HTML, validating for UX, handling tokens carefullyAny authorization decision (the user controls the browser)
HTTP headersCSP, HSTS, cookie attributes, CORSLogic flaws in your API
API serverAuthentication, authorization, validation, CSRF checks, rate limitingCode running in a compromised browser
Build & supply chainLockfiles, audits, provenance, secret scanningA malicious package you deliberately install

The OWASP Top 10:2025 reflects the same breadth: alongside Injection (which includes XSS), it lists Broken Access Control, Security Misconfiguration, Software Supply Chain Failures, Cryptographic Failures and Authentication Failures among the most critical web application risks[2].

Rule zero. The browser is an untrusted client. Anything the Vue app checks (route guards, disabled buttons, form validation) is a usability feature. The server must re-check every security decision[3,4].

1 Cross-Site Scripting (XSS)

Concept

XSS occurs when an application includes attacker-controlled data in a page without neutralizing it, so the browser interprets the data as code[5]. Because the injected script runs with the page's origin, it can read anything the page can read, call your API with the user's session, and alter what the user sees[6]. Three variants are commonly distinguished[7,8]:

  • Reflected XSS: the payload arrives in the request (for example a query parameter) and is echoed in the response.
  • Stored XSS: the payload is saved (a comment, a profile name) and served to other users later.
  • DOM-based XSS: the payload never touches the server's HTML; client-side JavaScript reads it from a source such as location.hash and writes it into a dangerous sink such as innerHTML. Single-page applications are especially exposed to this variant.

How Vue helps

Vue automatically escapes dynamic content. Text interpolation ({{ value }}) is rendered as text, and attribute bindings (:title="value") are set as attribute values, so a string such as <script>alert(1)</script> is displayed literally instead of being parsed as markup[1].

vue
<script setup lang="ts">
import { ref } from 'vue'
// Imagine this came from an API or the URL
const comment = ref('<img src=x onerror="alert(document.cookie)">')
</script>

<template>
  <!-- SAFE: rendered as literal text, the <img> is never created -->
  <p>{{ comment }}</p>
  <!-- SAFE: value is escaped into the attribute -->
  <span :title="comment">hover me</span>
</template>

Where Vue apps still get XSS

The Vue security guide lists the patterns that bypass this protection[1]. In practice they reduce to six sinks:

  1. User-controlled templates. Vue templates are compiled into JavaScript. If a template string, or server-rendered HTML that Vue mounts onto, contains user content, then {{ }} inside that content is executed as an expression. The Vue team's rule is "never use non-trusted templates"[1].
  2. v-html and the innerHTML prop in render functions, which insert raw HTML[9]. Covered in sections 6 and 7.
  3. URL injection. Binding user data to href or src allows javascript: URLs. Vue does not sanitize URLs[1].
  4. Style injection. Binding user-controlled CSS can be used for clickjacking (overlaying a fake login box, for example). Vue recommends allowing users to control only specific, safe properties[1].
  5. Direct DOM APIs in template refs or third-party libraries: el.innerHTML, insertAdjacentHTML, document.write, eval, setTimeout(string)[8].
  6. Dynamic <script> rendering or event-handler attributes built from user data, which Vue strongly discourages[1].

ts
// src/security/safeUrl.ts
const ALLOWED_PROTOCOLS = new Set(['http:', 'https:', 'mailto:'])

/**
 * Returns the URL if its protocol is allow-listed, otherwise 'about:blank'.
 * Relative URLs are resolved against the current origin first, so
 * "  JaVaScRiPt:alert(1)" and "java\tscript:" are normalised by the URL parser.
 */
export function safeUrl(input: string, base = window.location.origin): string {
  try {
    const url = new URL(input.trim(), base)
    return ALLOWED_PROTOCOLS.has(url.protocol) ? url.href : 'about:blank'
  } catch {
    return 'about:blank'
  }
}

The guide also notes that URL sanitization is best done on the backend before the URL is ever stored, in addition to any client-side check[1]. Using the platform URL parser rather than a regular expression matters because browsers tolerate whitespace, mixed case and control characters inside the scheme.

2 Cross-Site Request Forgery (CSRF)

Concept

CSRF tricks a victim's browser into sending an authenticated, state-changing request to your site from a page the attacker controls[11]. It works because browsers attach cookies to requests based on the destination, not on which site initiated the request. The attacker cannot read the response, but does not need to: a forged "transfer money" or "change email" request is enough[12].

Is a Vue SPA affected? It depends on how the API authenticates:

  • If the browser authenticates automatically (session cookies, HTTP Basic, client certificates), the API is a CSRF target, regardless of whether the frontend is a SPA.
  • If every request carries a bearer token that JavaScript adds to an Authorization header, a cross-site page cannot make the browser attach it, so classic CSRF does not apply. That design has its own trade-offs (section 9).

Defences, in layers

The OWASP cheat sheet recommends a token-based defence as the primary control, with other mechanisms as defence in depth[12]:

  1. Synchronizer token (stateful): the server stores a random token in the session and requires it in a header or form field.
  2. Signed double-submit cookie (stateless): the token is an HMAC bound to the session identifier, sent both as a cookie and as a header; the server recomputes and compares. OWASP warns that the naive, unsigned double-submit pattern is weaker and recommends the signed variant[12].
  3. Custom request header for API calls: browsers will not send custom headers cross-origin without a CORS preflight, which your server will refuse[12,13].
  4. SameSite cookies: SameSite=Lax or Strict stops the browser sending the cookie on most cross-site requests[14]. OWASP treats this as defence in depth, not a replacement for tokens[12].
  5. Fetch Metadata and Origin checks: rejecting state-changing requests whose Sec-Fetch-Site is cross-site, or whose Origin header is not your own[12].
  6. Never change state on GET; safe methods must be side-effect free[12].

Server: signed double-submit token (Express, TypeScript)

ts
// server/csrf.ts
import crypto from 'node:crypto'
import type { Request, Response, NextFunction } from 'express'

const SECRET = process.env.CSRF_SECRET!          // from a secret manager, never in the repo
const SAFE = new Set(['GET', 'HEAD', 'OPTIONS'])

function sign(sessionId: string, nonce: string) {
  return crypto.createHmac('sha256', SECRET).update(`${sessionId}!${nonce}`).digest('base64url')
}

export function issueCsrfToken(req: Request, res: Response) {
  const nonce = crypto.randomBytes(32).toString('base64url')
  const token = `${nonce}.${sign(req.session.id, nonce)}`
  // Readable by JS on purpose (no HttpOnly): the SPA copies it into a header.
  res.cookie('__Host-csrf', token, { secure: true, sameSite: 'strict', path: '/' })
  res.status(204).end()
}

export function verifyCsrf(req: Request, res: Response, next: NextFunction) {
  if (SAFE.has(req.method)) return next()

  // Defence in depth: Fetch Metadata
  const site = req.get('Sec-Fetch-Site')
  if (site && site !== 'same-origin' && site !== 'none') return res.sendStatus(403)

  const header = req.get('X-CSRF-Token') ?? ''
  const cookie = req.cookies['__Host-csrf'] ?? ''
  const [nonce, mac] = header.split('.')
  if (!nonce || !mac || header !== cookie) return res.sendStatus(403)

  const expected = Buffer.from(sign(req.session.id, nonce))
  const actual = Buffer.from(mac)
  if (expected.length !== actual.length || !crypto.timingSafeEqual(expected, actual)) {
    return res.sendStatus(403)
  }
  next()
}

The __Host- cookie prefix requires Secure, Path=/ and no Domain attribute, which stops a sibling subdomain from overwriting the cookie[14,15]. The session cookie itself should be HttpOnly; Secure; SameSite=Lax (or Strict).

Client: sending the token from Vue

ts
// src/api/http.ts
import axios from 'axios'

export const http = axios.create({
  baseURL: '/api',
  withCredentials: true,          // send the session cookie
  xsrfCookieName: '__Host-csrf',  // axios reads this cookie...
  xsrfHeaderName: 'X-CSRF-Token', // ...and copies it into this header
  withXSRFToken: (cfg) => !cfg.baseURL || cfg.baseURL.startsWith('/'), // same-origin only
  timeout: 10_000,
})

// Call once at app start so the cookie exists before the first POST
export const initCsrf = () => http.get('/csrf')

Axios supports xsrfCookieName, xsrfHeaderName and withXSRFToken; the last option controls whether the XSRF header is attached, which should be limited to your own origin so the token is never leaked to third-party hosts[16].

With fetch the equivalent is a small wrapper:

ts
function readCookie(name: string) {
  return document.cookie.split('; ').find(c => c.startsWith(name + '='))?.split('=')[1]
}
export function apiPost(path: string, body: unknown) {
  return fetch(`/api${path}`, {
    method: 'POST',
    credentials: 'same-origin',
    headers: {
      'Content-Type': 'application/json',
      'X-CSRF-Token': decodeURIComponent(readCookie('__Host-csrf') ?? ''),
    },
    body: JSON.stringify(body),
  })
}

Exercise 2.1

A team argues: "Our API only accepts Content-Type: application/json, so we are safe from CSRF." Evaluate the claim.

Show solution

Partly true but fragile. A cross-site HTML form can only send application/x-www-form-urlencoded, multipart/form-data or text/plain, and a cross-origin fetch with application/json triggers a CORS preflight[13]. However, the protection disappears if the server's body parser also accepts text/plain that happens to contain JSON, if CORS is misconfigured to reflect arbitrary origins with credentials, or if a future endpoint accepts form posts. OWASP lists content-type checks only as supporting measures; use a CSRF token plus SameSite cookies[12].

Exercise 2.2

Why does verifyCsrf use crypto.timingSafeEqual instead of === to compare the MAC?

Show solution

A plain string comparison can return early at the first differing byte, so response timing may leak how many leading bytes of a guess are correct. A constant-time comparison removes that side channel. The length check before it is required because timingSafeEqual throws on buffers of different lengths.

3 Content Security Policy (CSP)

Concept

CSP is an HTTP response header that tells the browser which sources of script, style, images, frames and connections a page may use, and whether inline script and eval are allowed[17,18]. Its main purpose is to reduce the impact of XSS: even if an attacker injects markup, a strict policy prevents the injected script from running. It is a second line of defence, not a substitute for output encoding[19].

Strict, nonce-based CSP

Host allow-lists (script-src https://cdn.example.com) are hard to keep safe because any script on an allowed host, including JSONP endpoints or old library versions, can be abused. The recommended approach is a strict policy based on per-response nonces or hashes, optionally with 'strict-dynamic', which lets a trusted (nonced) script load further scripts while ignoring host allow-lists[17,19,20].

http
Content-Security-Policy:
  default-src 'self';
  script-src 'nonce-R4nd0mPerResponse' 'strict-dynamic';
  style-src 'self' 'nonce-R4nd0mPerResponse';
  img-src 'self' data: https:;
  connect-src 'self' https://api.example.com;
  object-src 'none';
  base-uri 'none';
  frame-ancestors 'none';
  form-action 'self';
  upgrade-insecure-requests;
  report-to csp-endpoint

Key directives explained[17,18]:

  • object-src 'none' blocks plugin content; base-uri 'none' stops an injected <base> tag from redirecting relative script URLs.
  • frame-ancestors 'none' prevents your app being framed (clickjacking defence). It only works as a header, not in a <meta> tag.
  • connect-src limits where fetch/XHR/WebSocket may connect, which constrains data exfiltration.
  • report-to (or the older report-uri) tells the browser where to send violation reports.

Vue- and Vite-specific considerations

  • Avoid 'unsafe-eval' by precompiling templates. Single-File Components compiled by Vite ship render functions, so the runtime-only build is enough. The full build that compiles template strings in the browser generates code at runtime, which a CSP without 'unsafe-eval' blocks[17,21].
  • Nonces with Vite. Vite's html.cspNonce option adds a nonce placeholder to the script and style tags it generates and emits a <meta property="csp-nonce"> tag; your server must replace the placeholder with a fresh random value on every response[22].
  • Roll out in report-only mode first with Content-Security-Policy-Report-Only, then enforce once reports are clean[19].
  • Trusted Types. require-trusted-types-for 'script' makes the browser reject plain strings passed to DOM XSS sinks such as innerHTML, accepting only objects produced by an approved policy[23,24]. This turns DOM XSS into a policy-review problem. Check current browser support before enforcing it.

// vite.config.ts
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'

export default defineConfig({
  plugins: [vue()],
  html: { cspNonce: '__CSP_NONCE__' },   // placeholder, replaced per request
  build: { sourcemap: false },            // see section 12
})
ts
// server/serve-spa.ts: inject a fresh nonce and send the CSP header
import crypto from 'node:crypto'
import fs from 'node:fs/promises'
import express from 'express'

const app = express()
const template = await fs.readFile('dist/index.html', 'utf8')
app.use('/assets', express.static('dist/assets', { immutable: true, maxAge: '1y' }))

app.get('*', (_req, res) => {
  const nonce = crypto.randomBytes(16).toString('base64')
  res.setHeader('Content-Security-Policy', [
    "default-src 'self'",
    `script-src 'nonce-${nonce}' 'strict-dynamic'`,
    `style-src 'self' 'nonce-${nonce}'`,
    "img-src 'self' data: https:",
    "connect-src 'self'",
    "object-src 'none'",
    "base-uri 'none'",
    "frame-ancestors 'none'",
  ].join('; '))
  res.type('html').send(template.replaceAll('__CSP_NONCE__', nonce))
})

Because the HTML now differs per response, it must not be cached by shared caches; static, hashed assets in /assets can still be cached aggressively.

Exercise 3.1

A policy reads script-src 'self' 'unsafe-inline' https://cdn.jsdelivr.net. List two weaknesses and propose a replacement.

Show solution

(1) 'unsafe-inline' allows injected inline scripts and event handlers, which defeats CSP's XSS protection. (2) Allowing an entire public CDN lets an attacker load any package hosted there, including old vulnerable versions or gadgets that execute code. Replacement: script-src 'nonce-{random}' 'strict-dynamic'; object-src 'none'; base-uri 'none', serving third-party scripts with a nonce (and Subresource Integrity if they are static)[19,20,25].

Exercise 3.2

Why should the nonce never be a constant baked into the build?

Show solution

A nonce only proves "this script was placed by the server for this response" if the attacker cannot predict it. A constant nonce is visible in the page source and can simply be added to an injected <script nonce="...">. The CSP specification requires nonces to be unique per response and unguessable[17].

4 Input validation

Concept

Input validation ensures only properly formed data enters a workflow. OWASP recommends validating as early as possible, on the server side, using allow-lists (what is permitted) rather than deny-lists (what is forbidden), checking both syntax (format, type, length) and semantics (is this value meaningful for this user and context)[4].

Two misconceptions are common in frontend code:

  • Client-side validation is not a security control. An attacker can call your API directly. Client-side validation improves usability; the server must repeat it[4].
  • Validation is not the XSS defence. Many valid inputs, such as a surname like O'Brien or a comment discussing <script> tags, are dangerous in some output context. Encoding at output time (section 5) is the primary XSS control; validation reduces attack surface[4,7].

One schema, two enforcement points

Sharing a schema between the Vue client and the Node server keeps rules consistent. The example uses Zod, but any runtime schema library works.

ts
// shared/schemas/profile.ts
import { z } from 'zod'

export const ProfileSchema = z.object({
  displayName: z.string().trim().min(1).max(50)
    .regex(/^[\p{L}\p{M}\p{N} .'\-]+$/u, 'Letters, numbers, spaces and . \' - only'),
  email: z.string().trim().toLowerCase().email().max(254),
  age: z.coerce.number().int().min(13).max(130),
  website: z.string().url().max(2048)
    .refine(u => ['http:', 'https:'].includes(new URL(u).protocol), 'http(s) only')
    .optional(),
  role: z.enum(['reader', 'editor']),       // allow-list
}).strict()                                  // reject unknown keys (mass assignment)

export type Profile = z.infer<typeof ProfileSchema>

<!-- ProfileForm.vue: client-side validation for UX -->

    <label>Display name <input v-model="form.displayName" maxlength="50" /></label>

ts
// server/routes/profile.ts: the authoritative check
router.put('/profile', requireAuth, verifyCsrf, async (req, res) => {
  const parsed = ProfileSchema.safeParse(req.body)
  if (!parsed.success) return res.status(400).json({ error: 'Invalid input' })

  if (parsed.data.role !== req.user.role && !req.user.isAdmin) return res.sendStatus(403)

The .strict() call rejects unexpected properties, which prevents mass-assignment attacks where a client adds fields such as isAdmin: true. The role check is semantic validation that only the server, knowing who the user is, can perform[4].

5 Output encoding

Concept

Output encoding converts data into a form that the receiving interpreter treats as data, never as code. The correct encoding depends on the context the data lands in, and OWASP's XSS prevention guidance is organised around those contexts[7]:

Encoding URL components

ts
// BAD: '&' or '#' in the term breaks the URL; '../' can change the path
const bad = `/api/search?q=${term}&page=${page}`
const badPath = `/api/users/${userId}/orders`

// GOOD
const params = new URLSearchParams({ q: term, page: String(page) })
const good = `/api/search?${params}`
const goodPath = `/api/users/${encodeURIComponent(userId)}/orders`

// With axios, pass params as an object and let it encode:
await http.get('/search', { params: { q: term, page } })

Encoding data embedded in HTML for hydration

Server-side rendering frequently serialises state into a script tag. JSON.stringify alone is not safe in this context: a string containing </script> ends the script element and lets the rest be parsed as HTML[7].

ts
// server/render.ts
function serializeForScript(state: unknown): string {
  return JSON.stringify(state)
    .replace(/</g, '\\u003c')        // prevents </script> and <!--
    .replace(/ /g, '\\u2028')   // line separators are invalid in older JS parsers
    .replace(/ /g, '\\u2029')
}

const html = `<script nonce="${nonce}">window.__STATE__=${serializeForScript(state)}</script>`

A safer alternative is to place the JSON in a non-executing element, for example <script type="application/json" id="state">, and read it with JSON.parse(el.textContent); the < escaping is still required.

Encoding in render functions

Render functions follow the same rules as templates: children passed as strings become text nodes, and props become attributes or DOM properties. Only the innerHTML prop bypasses encoding[1].

ts
import { h } from 'vue'
h('p', userText)                    // SAFE: text node
h('a', { href: safeUrl(link) }, t)  // SAFE: validated URL, encoded attribute
h('div', { innerHTML: userText })   // UNSAFE: equivalent to v-html

6 Safe HTML rendering

Concept

Sometimes an application genuinely needs to display rich text: a CMS article, a Markdown comment, an email body. The safe approaches, from most to least preferable, are[1,7]:

  1. Do not render HTML. Store and render structured data (paragraphs, links, emphasis) through components.
  2. Render a restricted markup language to components, for example parse Markdown into an AST and map nodes to Vue elements, so no HTML string ever reaches the DOM.
  3. Sanitize HTML with a well-maintained, DOM-based sanitizer such as DOMPurify, configured with an allow-list, and render the result. OWASP recommends DOMPurify for this case[7].
  4. Isolate untrusted HTML in a sandboxed <iframe> on a separate origin when you must render arbitrary documents (for example, received emails).

import { defineComponent, h, type VNode } from 'vue'
import { fromMarkdown } from 'mdast-util-from-markdown'
import type { Content } from 'mdast'
import { safeUrl } from '@/security/safeUrl'

function render(node: Content): VNode | string | null {
  const kids = () => ('children' in node ? node.children.map(render) : [])
  switch (node.type) {
    case 'text':      return node.value                       // text node, encoded
    case 'paragraph': return h('p', kids())
    case 'emphasis':  return h('em', kids())
    case 'strong':    return h('strong', kids())
    case 'inlineCode':return h('code', node.value)
    case 'link':      return h('a', { href: safeUrl(node.url), rel: 'nofollow noopener noreferrer' }, kids())
    case 'list':      return h(node.ordered ? 'ol' : 'ul', kids())
    case 'listItem':  return h('li', kids())
    default:          return null   // raw 'html' nodes and anything unknown are dropped
  }
}

export default defineComponent({
  props: { source: { type: String, required: true } },
  setup(props) {
    return () => h('div', { class: 'md' }, fromMarkdown(props.source).children.map(render))
  },
})

Because the component never creates an HTML string, there is nothing for an attacker to inject into; unknown node types, including raw HTML embedded in the Markdown, are simply discarded.

7 Avoiding unsafe v-html

Concept

v-html sets an element's innerHTML. The Vue API reference warns that dynamically rendering arbitrary HTML "can be very dangerous because it can easily lead to XSS attacks" and to use it only on trusted content, never on user-provided content[9]. Note that scripts inserted through innerHTML do not run, but HTML event handlers do, so an <img onerror> payload is the classic exploit[10].

"Trusted" is narrower than it sounds. Content from your own CMS was typed by an editor whose account could be phished; content from your own API may contain data another user submitted; translations may come from a vendor. Treat v-html as needing a written justification.

Policy: make v-html rare and reviewable

  1. Lint it. eslint-plugin-vue provides vue/no-v-html. Set it to error and allow exactly one exception, inside SafeHtml.vue.
  2. Funnel through one component. All rich-text rendering goes through SafeHtml, which always sanitizes.
  3. Ban the other HTML sinks too: innerHTML in render functions and template refs, insertAdjacentHTML, document.write, outerHTML[8].
  4. Back it with Trusted Types so a forgotten sink fails closed in supporting browsers[23].

8 Authentication security

Concept

Authentication establishes who the user is. In a Vue application the frontend collects credentials and reflects authentication state, but the server must perform and enforce it. Route guards that hide pages from unauthenticated users are UX: an attacker can bypass them by editing the JavaScript or calling the API directly, so each API endpoint must check the session and the user's permission for the specific resource[2,3].

Credential policy (NIST SP 800-63B-4)

Current NIST guidance departs from older "complexity" rules[28]:

  • Passwords used as a single factor must be at least 15 characters; passwords used only as part of multi-factor authentication must be at least 8.
  • Verifiers should permit at least 64 characters and accept all printing ASCII characters, spaces and Unicode.
  • Composition rules (mandatory digits, symbols) must not be imposed, and periodic forced changes must not be required; change is required on evidence of compromise.
  • New passwords must be checked against a blocklist of commonly used, expected or compromised values.

On the server, store passwords with a slow, salted, memory-hard hash; OWASP currently recommends Argon2id, with scrypt, bcrypt or PBKDF2 as alternatives under specific parameters[29].

Login flow hygiene

  • Generic errors. Respond "Invalid username or password" for both unknown users and wrong passwords, to avoid account enumeration[3].
  • Rate-limit and throttle login, registration, password reset and MFA verification endpoints[3].
  • Prefer phishing-resistant MFA such as passkeys/WebAuthn; NIST describes phishing resistance as a property of authenticators like these[28].
  • Regenerate the session ID on login and on privilege change, to prevent session fixation[30].
  • Set idle and absolute session timeouts and invalidate the session server-side on logout[30].
  • Use OAuth 2.0 / OpenID Connect correctly when delegating login: authorization code flow with PKCE; the implicit grant should not be used[31,32].

9 Token storage considerations

Concept

If a Vue app authenticates to an API with tokens (OAuth access tokens, JWTs), it must keep them somewhere. Every option is a trade-off between exposure to XSS, exposure to CSRF, and complexity. The underlying fact that shapes all of them: if an attacker achieves XSS, they can make authenticated requests as the user from inside the page, whatever the storage mechanism. Storage choice decides whether they can also steal the token and use it elsewhere, for how long, and with what scope[33,34].

The Backend-for-Frontend pattern

RFC 10017 (OAuth 2.0 for Browser-Based Applications, BCP 212) describes three architectures and recommends the BFF, in which a server-side component acts as a confidential OAuth client, holds the tokens, and gives the browser only an HttpOnly session cookie[33]. The Vue app calls the BFF on the same origin; the BFF attaches the access token when proxying to resource servers.

If tokens must live in the SPA

For a pure SPA acting as a public OAuth client, follow RFC 9700 and RFC 10017[32,33]:

  • Use the authorization code flow with PKCE (S256)[31].
  • Keep access tokens short-lived and narrowly scoped.
  • Refresh tokens for public clients must be either sender-constrained (for example with DPoP) or rotated on each use, so a stolen refresh token is detectable[32].
  • Keep tokens in memory rather than Web Storage, and never put them in URLs: RFC 6750 says bearer tokens should not be passed in query parameters because URLs are logged and leaked through referrers[35].
  • Validate JWTs properly on the server: pin the algorithm, check iss, aud and exp; never accept alg: none[36,37].
ts
// src/security/tokenStore.ts: memory-only access token with single-flight refresh
let accessToken: string | null = null
let expiresAt = 0
let inflight: Promise<string> | null = null

async function refresh(): Promise<string> {
  // Refresh token lives in an HttpOnly cookie scoped to /auth/refresh (rotated server-side)
  const r = await fetch('/auth/refresh', { method: 'POST', credentials: 'same-origin',
                                          headers: { 'X-Requested-With': 'fetch' } })
  if (!r.ok) throw new Error('session expired')
  const { access_token, expires_in } = await r.json()
  accessToken = access_token
  expiresAt = Date.now() + (expires_in - 30) * 1000
  return access_token
}

export async function getAccessToken(): Promise<string> {
  if (accessToken && Date.now() < expiresAt) return accessToken
  inflight ??= refresh().finally(() => { inflight = null })
  return inflight
}

export function clearTokens() { accessToken = null; expiresAt = 0 }

Exercise 9.1

A colleague says, "Moving the JWT from localStorage to an HttpOnly cookie makes us immune to XSS." Correct the statement.

Show solution

It prevents injected script from reading and exfiltrating the token, which limits the attack to the lifetime of the victim's open page. It does not prevent injected script from using the session: requests made from the page automatically carry the cookie. XSS must still be prevented with encoding, sanitization and CSP. In addition, the cookie now makes the API a CSRF target, so CSRF defences become mandatory[12,33].

Exercise 9.2

Why does getAccessToken share a single in-flight promise?

Show solution

When several API calls start at once with an expired token, each would otherwise call /auth/refresh. With refresh-token rotation, the first call invalidates the refresh token and the others present a now-used token, which the server may treat as theft and revoke the whole token family[32]. Single-flight refresh avoids this.

10 Dependency vulnerabilities

Concept

A typical Vue project installs hundreds of transitive packages, and all of their code either runs on developer machines and CI (build tools, install scripts) or ships to users (runtime libraries). OWASP Top 10:2025 lists Software Supply Chain Failures as its own category, covering vulnerable components and compromised dependencies, build systems and distribution[2]. Risks include[27,38]:

  • Known vulnerabilities in a direct or transitive dependency (a sanitizer bypass, a prototype-pollution bug).
  • Malicious packages: typosquats (vuejs-router instead of vue-router), dependency confusion between private and public names, or a legitimate package whose maintainer account is taken over.
  • Install-time code execution through lifecycle scripts such as postinstall, which run with the developer's or CI runner's privileges.
  • Unpinned versions that silently pull a new, compromised release.

Controls

  1. Commit the lockfile and install with npm ci. package-lock.json records the exact version and an integrity hash for every package[39]. npm ci installs exactly what the lockfile says, fails if package.json and the lockfile disagree, and never rewrites either file[40].
  2. Minimise dependencies. Every package is code you trust. Prefer platform APIs (URL, crypto.randomUUID, Intl) over micro-packages[38].
  3. Vet new packages: maintainer history, download trends, repository link, open security advisories, and whether the published package has provenance[38,41].
  4. Restrict install scripts in CI with npm ci --ignore-scripts where your dependencies allow it, or an allow-list of packages that need them[38].
  5. Scope private packages (@yourorg/…) and point that scope at your private registry in .npmrc, preventing dependency confusion[38].
  6. Automate updates and alerts with Dependabot (section 13)[42].
  7. Use Subresource Integrity for any script or stylesheet loaded from a CDN, so a tampered file is refused by the browser[25].

11 Secure API communication

Transport

  • HTTPS everywhere, TLS 1.2 or later, preferably 1.3[43]. Mixed content is blocked by browsers, and upgrade-insecure-requests in CSP helps during migration[17].
  • HSTS: Strict-Transport-Security: max-age=31536000; includeSubDomains instructs the browser to use only HTTPS for the host, preventing SSL-stripping on later visits[44].

CORS, configured narrowly

CORS relaxes the same-origin policy; it is not a protection mechanism by itself. A server that reflects any Origin back in Access-Control-Allow-Origin while also sending Access-Control-Allow-Credentials: true lets any website read authenticated responses[13,45]. The simplest secure setup for a Vue SPA is to serve the app and API from the same origin (via a reverse proxy) and not enable CORS at all.

ts
// server/cors.ts: explicit allow-list when cross-origin is unavoidable
import cors from 'cors'
const ALLOWED = new Set(['https://app.example.com', 'https://admin.example.com'])

export default cors({
  origin: (origin, cb) => cb(null, !origin || ALLOWED.has(origin)),
  credentials: true,
  methods: ['GET', 'POST', 'PUT', 'DELETE'],
  allowedHeaders: ['Content-Type', 'X-CSRF-Token', 'Authorization'],
  maxAge: 600,
})

API design rules the Vue client relies on

The OWASP REST Security Cheat Sheet recommends, among others[45]:

  • Authorization on every endpoint and for every object ID (the invoice example in section 8).
  • Accept only the expected content type and validate request bodies (section 4).
  • Return generic error messages; do not leak stack traces.
  • Send security headers on API responses, including Cache-Control: no-store for sensitive data and X-Content-Type-Options: nosniff.
  • Rate-limit to reduce brute force and abuse.

12 Secrets management

Concept

The most important fact for frontend developers: a Vue application cannot keep a secret. Everything in the built bundle is downloaded by every visitor. Vite makes this explicit: only variables prefixed with VITE_ are exposed to client code through import.meta.env, they are statically embedded in the bundle at build time, and Vite's documentation warns that VITE_* variables should not contain sensitive information[46]. Hard-coded credentials in code are a recognised weakness[47].

Pattern: proxy third-party calls through your server

ts
// BAD (client): the key ships to every visitor
const r = await fetch(`https://api.maps.example/geocode?key=${import.meta.env.VITE_MAPS_KEY}&q=${q}`)

// GOOD (server): key stays server-side; endpoint is authenticated and rate-limited
router.get('/geocode', requireAuth, geocodeRateLimit, async (req, res) => {
  const q = z.string().min(1).max(200).parse(req.query.q)
  const url = new URL('https://api.maps.example/geocode')
  url.search = new URLSearchParams({ q, key: process.env.MAPS_API_KEY! }).toString()
  const upstream = await fetch(url, { signal: AbortSignal.timeout(5000) })
  res.status(upstream.status).json(await upstream.json())
})

Lifecycle controls

The OWASP Secrets Management Cheat Sheet recommends centralising secrets in a dedicated manager, granting least-privilege access, rotating automatically, auditing access, and detecting leaks in code and CI[49]. Concretely for a Vue repository:

  • Keep .env.local and .env.*.local out of git; Vite's convention is that *.local files are for local overrides and should be git-ignored[46].
  • Enable GitHub secret scanning and push protection, which detect known credential formats in commits and can block a push that contains one[50].
  • Store CI secrets as GitHub Actions secrets or in an external manager, pass them to steps that need them, and never print them; GitHub redacts registered secrets from logs, but transformed values may not be redacted[51].
  • Do not publish production source maps publicly unless reviewed: they reveal original source and comments.
  • Rotate immediately on any leak. Deleting the commit does not help, because clones, forks and caches keep it[49].

13 npm dependency auditing

npm audit

npm audit sends a description of your dependency tree to the configured registry and reports known vulnerabilities with severity and the dependency path that pulls each one in[52]. Useful options[52]:

CommandPurpose
npm auditReport all known vulnerabilities
npm audit --audit-level=highExit non-zero only for high or critical; suitable as a CI gate
npm audit --omit=devReport only dependencies installed in production
npm audit --jsonMachine-readable output for tooling
npm audit fixApply compatible (semver-respecting) updates
npm audit fix --forceAlso apply major-version updates; may break the app, review carefully
npm audit signaturesVerify registry signatures and provenance attestations of installed packages

Triaging results

Audit output needs judgement. OWASP's vulnerable-dependency guidance distinguishes cases: a patched version exists (upgrade); a fix exists only in a new major version (plan the upgrade, add mitigations meanwhile); no fix exists (assess exploitability, mitigate or replace the package); and the vulnerable code path is not reachable in your use (document and accept the risk with a review date)[27]. For a Vue SPA, a vulnerability in a dev-only build tool and one in a library shipped to browsers carry different risk; --omit=dev helps separate them, but build tools still run on CI with access to secrets[38,52].

When a vulnerable transitive dependency is fixed upstream but the direct dependency has not yet updated, npm's overrides field forces a specific version throughout the tree[53]:

json
{
  "overrides": {
    "some-transitive-lib": "^2.4.1"
  }
}

Test thoroughly after overriding, and remove the override once the direct dependency catches up.

Dependabot

Dependabot security updates open pull requests that bump vulnerable dependencies to a fixed version when GitHub has an advisory for them; version updates keep dependencies current on a schedule you configure in dependabot.yml[42,54].

yaml
# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: npm
    directory: /
    schedule: { interval: weekly }
    open-pull-requests-limit: 10
    groups:
      vue:
        patterns: ['vue', 'vue-router', 'pinia', '@vue/*', '@vitejs/*', 'vite']
  - package-ecosystem: github-actions
    directory: /
    schedule: { interval: weekly }

Provenance

Packages published from a CI system with provenance carry a signed statement linking the package to its source repository and build; npm audit signatures verifies these attestations for installed packages[41,52]. If you publish internal Vue component libraries, publish them with provenance so consumers can verify them.

Show solution
