Vue-Based Application Architectures

From single-page apps to micro-frontends: how to render, route, split, deploy and organise Vue applications, with working code, exercises and solutions.

November 2026 · Examples target Vue 3 (Composition API, <script setup>), Vue Router, Pinia, Vite and Nuxt 4. Citations follow the Vancouver system; numbers refer to the reference list at the end.

1Introduction and the four decisions

Vue describes itself as a progressive framework: it can enhance static HTML without a build step, be embedded as Web Components, power a single-page application (SPA), render on the server, generate static sites, or target desktop, mobile and the terminal[1,2]. That flexibility is the reason "Vue architecture" is not one thing. The same component model sits underneath very different systems, and the hard choices are about everything around the components.

This article treats architecture as a small number of decisions that are expensive to change later. Every architecture in the sections that follow is a particular combination of answers to these four questions.

DecisionQuestionTypical answers
RenderingWhere and when is HTML produced?In the browser (CSR), on the server per request (SSR), at build time (SSG), or a mix per route [3,4]
NavigationWho owns the URL?The client router (SPA), the server (MPA), or both (SSR with hydration)
Deployment unitWhat ships independently?One bundle, one app per page, or many independently deployed frontends [5]
Code organisationHow is code partitioned around teams and the business?By technical layer, by feature, or by domain/bounded context [6–8]

The first five topics below (SPA, MPA, SSR, SSG, PWA) are mainly about rendering and navigation. Micro-frontends are a deployment decision. Component-driven, modular and domain-driven design are about code organisation. Headless CMS, BFF and microservices integration are about how the frontend talks to the systems behind it. Real products combine several of them: a Nuxt storefront is typically SSR + SSG per route, organised in layers, fed by a headless CMS through a BFF.

Vocabulary used throughout

  • Hydration: the client-side step in which Vue takes over server-rendered HTML and attaches event listeners and reactivity instead of re-creating the DOM [9].
  • Core Web Vitals: Google's user-centred metrics, namely Largest Contentful Paint (LCP, loading), Interaction to Next Paint (INP, responsiveness) and Cumulative Layout Shift (CLS, visual stability) [10]. They are the yardstick used when comparing rendering strategies below.
  • Time to First Byte (TTFB) and First Contentful Paint (FCP): when the first byte of the response, and the first rendered content, arrive. Rendering choices trade these against each other [3].

A running example keeps the code concrete: Acme Shop, an online store with a catalogue, a cart, checkout, customer accounts, editorial content and an admin area. Each section shows how one architecture applies to it.

2Single-page applications

2.1 Concept

MDN defines an SPA as a web application that loads a single web document and then updates the body content of that document through JavaScript APIs such as fetch when different content is shown [11]. Navigation between "pages" is handled in the browser: the router intercepts link clicks, updates the address bar through the History API, and swaps components without a full document reload [12,13]. Vue Router is the official client-side router [13,14], and Pinia is the officially recommended state-management library [15,16].

The strengths are a fluid, app-like experience after the first load, a clean split between a static frontend and an API, and very simple hosting (any static file server or CDN). The costs are equally well known: the browser must download, parse and execute JavaScript before meaningful content appears, which hurts FCP and LCP on slow devices, and content that only exists after JavaScript runs is harder for crawlers and link previews [3].

Good fit: authenticated dashboards, internal tools, editors and admin panels, where SEO does not matter and users keep the app open for long sessions. Poor fit: content and commerce pages that live or die by search traffic and first-load speed.

2.2 Project structure and bootstrapping

A Vite-based Vue SPA has one HTML entry, one JavaScript entry and a router. The application is created once and mounted onto a root element.

2.3 Routing, code splitting and guards

Route components should be imported lazily with dynamic import(), so that the bundler emits a separate chunk per route and each chunk is only fetched when that route is first visited [17]. Navigation guards run before each navigation and can cancel or redirect it, which is where authentication checks usually live [18].

2.4 Client state with Pinia

Pinia stores can be written in a "setup" style that mirrors the Composition API: refs become state, computeds become getters and functions become actions [16].

2.5 History mode and the server

Vue Router offers HTML5 history mode (createWebHistory), hash mode (createWebHashHistory) and memory mode (createMemoryHistory, used for SSR and tests). Hash mode works without server configuration because the part after # is never sent to the server, but the Vue Router documentation notes that it has a bad impact on SEO. HTML5 mode produces clean URLs but requires the server to answer every unknown path with index.html, otherwise users get a 404 when they refresh or open a deep link [19].

Pitfall: with a catch-all fallback the server no longer returns 404 for unknown URLs, so the SPA itself must render a "not found" route (the last route above) [19].

2.3 Conceptual: why does lazy-loading route components improve LCP for the home page but can make the first visit to other pages slower? How would you mitigate the second effect?

Show solution

Lazy routes remove other pages' code from the initial bundle, so less JavaScript must be downloaded and executed before the home page renders [3,17]. The first navigation to another route must now fetch its chunk, adding a network round trip. Mitigations include prefetching likely-next chunks when the browser is idle or a link becomes visible (for example by calling the same import() function early), and keeping very small, frequently used routes in the main chunk.

3Multi-page applications

3.1 Concept

In a multi-page application (MPA) every navigation requests a new HTML document from the server. The server, not a client router, owns the URL space. This is the web's default model, and it remains a strong choice when most pages are content, forms or server-rendered views from a back-end framework such as Laravel, Rails, Django or Spring.

Vue fits MPAs in two ways. First, it can progressively enhance server-rendered HTML: Vue can be loaded without a build step and mounted on selected elements, and the documentation lists "enhancing static HTML" as a first-class use case [2]. For very light enhancement the Vue team also publishes petite-vue, a small subset of Vue optimised for sprinkling interactivity onto existing pages [21]. Second, Vite can build an MPA with several HTML entry points, each with its own JavaScript bundle, by listing them in build.rollupOptions.input [20].

The "islands" idea generalises the first approach: the server renders a static page, and independent interactive regions ("islands") are hydrated or mounted separately, each with its own small script [22]. Islands keep JavaScript proportional to interactivity rather than to page size.

3.2 Multiple entry points with Vite

Each HTML file references its own entry module, and Rollup extracts code shared between entries into common chunks. Each page gets its own small Vue app, and no client router is required.

3.3 Mounting islands into server-rendered pages

When the HTML comes from a back-end template, a small "island loader" can find placeholders and mount a Vue component on each one. Using defineAsyncComponent means only the code for islands that actually appear on the page is downloaded [23].

Because each island is a separate app, islands do not share Vue reactivity automatically. If two islands must coordinate (for example a cart counter in the header and an add-to-cart button), a shared Pinia instance can be passed to every createApp call, or islands can communicate through DOM CustomEvents [24].

3.4 The hybrid middle ground

Some teams want server-side routing and controllers but Vue page components. Inertia.js, which describes itself as a way to build "the modern monolith", is one well-known approach: the server keeps its routes and controllers and returns the name of a page component plus its props, while the client swaps components without full reloads [25]. Architecturally this is an SPA whose router lives on the server.

4Server-side rendered applications

4.1 Concept

With server-side rendering (SSR), the same Vue components that run in the browser are rendered to an HTML string on the server for each request. The browser displays that HTML immediately; the client bundle then hydrates it, making it interactive without re-creating the DOM [9]. An application that runs on both server and client this way is often called universal or isomorphic, and Nuxt's default rendering mode is exactly this universal rendering [4].

The Vue documentation lists the advantages as faster time-to-content (especially on slow devices and networks), a unified mental model (one language and one component model for the whole app) and better SEO, because crawlers see fully rendered pages [9]. It also lists the trade-offs: development constraints (browser-only APIs can only be used in certain lifecycle hooks), more involved build and deployment (a Node.js or edge server is needed instead of static hosting) and more server-side load [9]. web.dev adds a performance nuance: SSR improves FCP but the page may look ready before it is interactive, so hydration cost still matters for responsiveness [3].

4.2 SSR from first principles

Vue's low-level SSR API is small. createSSRApp creates an app in SSR mode, and renderToString from vue/server-renderer renders it. On the client, calling createSSRApp and mount on the same root element hydrates instead of re-rendering [9]. Vite provides the build and dev-server plumbing: in development the server loads the server entry through Vite's ssrLoadModule, and production uses separate client and server builds [26].

4.3 Writing SSR-friendly code

The Vue SSR guide singles out several rules that matter architecturally [9]:

  • Cross-request state pollution. A Node server is long-lived and serves many users. Module-level singletons (a store created at import time, a cached user object) are shared across requests and can leak one user's data into another's response. Create app, router and store per request, as the factory above does [9,27].
  • Lifecycle limits. Only setup()/<script setup> and onServerPrefetch run on the server; onMounted and onUpdated do not. Access window, document or localStorage only in client-only hooks [9,28].
  • Hydration mismatch. If the client's first render differs from the server HTML (random IDs, Date.now(), locale-dependent formatting, invalid HTML nesting), Vue warns and patches the DOM, which costs time and can cause visual glitches. Since Vue 3.5, an intentional mismatch can be suppressed with the data-allow-mismatch attribute [9].

4.4 SSR with Nuxt

In practice most Vue teams use Nuxt rather than hand-rolling SSR. Nuxt renders universally by default and provides useFetch and useAsyncData, which run on the server, serialise the result into the page payload and reuse it during hydration so the client does not fetch the same data twice [4,29].

4.3 Conceptual: SSR improved LCP on product pages, but INP got worse on low-end phones. Explain why, and name two mitigations.

Show solution

SSR sends content earlier, which helps LCP, but the page still has to download and execute the full client bundle to hydrate; while that work runs, the main thread is busy and interactions are delayed [3,10]. Mitigations: reduce the hydrated surface (render static parts without interactivity, hydrate islands or lazily hydrate below-the-fold components), split code so the initial bundle is smaller [17,30], and defer non-critical third-party scripts.

5Static site generation

5.1 Concept

Static site generation (SSG), also called pre-rendering, runs the SSR step once at build time for a known set of routes and writes the resulting HTML files to disk. web.dev's taxonomy calls this static rendering and notes that it gives fast FCP and TTFB because HTML can be served directly from a CDN, with the limitation that every URL must be known and generated ahead of time [3]. The pages are still hydrated on the client, so they can be fully interactive.

Vue offers SSG at three levels:

  • VitePress, a Vite- and Vue-powered static site generator for content-centric sites such as documentation and blogs, where Markdown is the main authoring format [31].
  • Nuxt prerendering, either for the whole app (nuxt generate) or for selected routes. Nuxt's crawler follows links from the pages it renders to discover further routes [32].
  • Hybrid rendering through Nuxt routeRules, where each route pattern chooses its own strategy: prerender at build, server-render per request, cache with stale-while-revalidate (swr) or incremental static regeneration (isr), or render only on the client (ssr: false) [4].

5.2 Prerendering with Nuxt

Dynamic routes that are not reachable by links (for example products listed only through search) can be added programmatically with the prerender:routes hook or listed explicitly [32].

5.3 Hybrid rendering: one strategy per route

Pure SSG struggles when there are hundreds of thousands of pages or when content changes often. Hybrid rendering lets the architecture match the data: marketing pages are static, product pages are cached and refreshed in the background, the cart is client-only [4].

Note: ISR and SWR depend on a cache layer. Nitro implements them on its own server or delegates to the hosting platform's CDN where supported, so behaviour can differ between deployment targets [4,33].

5.4 VitePress for documentation

For pure content sites VitePress is lighter than a full application framework. Pages are Markdown, Vue components can be used inside Markdown, and the output is static HTML that becomes a SPA after the first load [31].

Exercises: SSG

5.1 Acme Shop has 40 marketing pages edited weekly, 200,000 products whose prices change hourly, per-user wish lists, and an admin back office. Assign a rendering strategy to each and write the routeRules.

Show solution
  • Marketing pages: prerender, rebuilt (or revalidated by webhook) on publish.
  • Products: too many to prerender in every build and prices change hourly, so use swr with a TTL shorter than the price-change interval (or isr on a platform that supports on-demand revalidation).
  • Wish lists: user-specific, so never cache shared HTML; client-render with ssr: false (or SSR with Cache-Control: private).
  • Admin: client-only; no SEO, authenticated, interaction-heavy.

All rule types used are documented route-rule options in Nuxt [4].

5.2 Why must a prerendered page avoid reading cookies or request headers during render?

Show solution

A prerendered page is rendered once at build time, with no real user request, and the same HTML is then served to everyone [3,32]. Anything request-specific would either be missing or, worse, baked in for all users. Personalisation must happen on the client after hydration, or the route must use SSR instead.

6Progressive web applications

6.1 Concept

A progressive web app (PWA) is a web app built with web platform technologies that can be installed and that offers app-like capabilities such as offline operation, while still working as an ordinary website in browsers that lack those capabilities [34]. Two technologies carry most of the weight:

  • The web app manifest, a JSON file that tells the browser how the app should behave when installed: name, icons, start URL, display mode and colours [35].
  • The service worker, a script that acts as a proxy between the web app, the browser and the network. It can intercept requests, serve responses from caches, and enable offline experiences, background sync and push notifications. Service workers only run in secure contexts (HTTPS, or localhost during development) [36].

PWA is orthogonal to rendering: an SPA, an SSR app or a static site can all be PWAs. The architectural work is deciding what to cache and how to keep it fresh. Jake Archibald's "Offline Cookbook" catalogues the standard strategies, including cache-first, network-first and stale-while-revalidate [37]. Google's Workbox library implements them as reusable modules [38], and vite-plugin-pwa integrates Workbox and manifest generation into Vite builds [39].

StrategyBehaviourUse for
Cache firstServe from cache; go to network only on a missContent-hashed JS/CSS, fonts
Network firstTry network; fall back to cache when offlineHTML documents, API reads that must be fresh
Stale-while-revalidateServe cache immediately and update it in the backgroundAvatars, product images, non-critical API data
Network onlyNever cachePayments, mutations, analytics

Strategy descriptions follow the Offline Cookbook [37].

7Micro-frontends

7.1 Concept

Cam Jackson's article on martinfowler.com defines micro-frontends as "an architectural style where independently deliverable frontend applications are composed into a greater whole" [5]. The motivation mirrors microservices: several teams, each owning a business capability end to end, should be able to build, test and deploy their part of the UI without coordinating releases with everyone else [5,42].

The article lists the benefits as incremental upgrades, simple and decoupled codebases, independent deployment and autonomous teams, and the costs as larger payloads (duplicated dependencies), differences between environments, and operational and governance complexity [5]. Micro-frontends are therefore an organisational scaling tool. A single team rarely benefits from them.

7.2 Integration approaches

The same article describes several ways to compose micro-frontends [5]:

ApproachHow it worksTrade-off
Server-side template compositionA server or edge layer stitches HTML fragments from several appsFast first paint; client interactivity needs extra work
Build-time integrationEach micro-frontend is an npm package the container depends onSimple, but every change requires rebuilding and redeploying the container, which the article advises against because it defeats independent deployment
Run-time via iframesEach app lives in an iframeStrong isolation; awkward routing, deep linking, accessibility and responsive layout
Run-time via JavaScriptEach app exposes a global mount function loaded by the containerFlexible and the most common option
Run-time via Web ComponentsEach app is a custom elementFramework-agnostic standard interface

In the Vue ecosystem the JavaScript route is usually implemented with Module Federation, which lets separately built and deployed bundles share modules and dependencies at run time [43,44]. Its Vite implementation is @module-federation/vite [45]. The Web Components route uses Vue's defineCustomElement [46,47]. A third option, single-spa, is a router and lifecycle manager for mounting several frontend applications, possibly written in different frameworks, on one page [48].

7.3 Module Federation with Vite

The remote exposes modules; the host declares where to find remotes. Shared dependencies such as vue and pinia should be marked as singletons so that only one copy loads and all remotes use the same runtime [43,45].

In the host, a remote module is imported like any other async module. Wrapping it in defineAsyncComponent provides loading and error states, so an unavailable remote degrades one region rather than the whole page [23].

Remotes can also contribute routes. The shell loads each remote's route table and registers it under a prefix with router.addRoute, so each team owns the pages beneath its path.

7.4 Web Components as the contract

When teams use different frameworks, or a stable, framework-neutral interface is required, a Vue component can be compiled to a native custom element with defineCustomElement [46]. Custom elements, shadow DOM and HTML templates are standard browser APIs, so any host page can use the element [47]. In Vue, files named *.ce.vue have their styles inlined into the element's shadow root [46].

7.5 Communication and governance rules

  • Prefer the URL and DOM events over shared state. The micro-frontends article recommends minimising communication and, where needed, using custom events, callbacks and the address bar rather than shared stores [5]. Shared global state reintroduces the coupling the architecture tries to remove.
  • Share a design system, not components' internals. Visual consistency comes from a versioned design system package and design tokens.
  • Align boundaries with teams and business capabilities, not with technical layers. Conway's observation that systems mirror the communication structures of the organisations that build them applies directly [49,50].
  • Plan for failure. Each remote is a network dependency; the shell must render something useful when one is down.

Exercises: Micro-frontends

Show solution

Publish a tiny contract package (types only) that both teams depend on, and use CustomEvent for transport [24]. Event names are namespaced to avoid collisions.

7.2 A team proposes splitting a four-developer admin app into five micro-frontends "for scalability". Give an argued recommendation.

Show solution

Recommend against. Micro-frontends address the coordination cost of many autonomous teams deploying independently [5]. With one small team, that cost is low, while the architecture adds duplicated payload, cross-app integration testing, versioning of shared dependencies and more pipelines to operate [5]. A modular monolith (section 9) with enforced module boundaries gives most of the code-organisation benefit and can be split later along the same boundaries if the organisation grows.

7.3 What problems can appear if the host and a remote each bundle their own copy of Vue, and how does the configuration above prevent it?

Show solution

Users download Vue twice. Each copy also has its own runtime internals, so values created by one copy (application context, injection keys, plugin instances such as a Pinia store installed on the host) are not visible to components rendered by the other, leading to subtle failures like inject() returning undefined. Declaring vue (and pinia) as shared with singleton: true makes Module Federation negotiate a single copy at run time, and requiredVersion surfaces incompatible versions [43,44].

8Component-driven architecture

8.1 Concept

Component-driven architecture builds user interfaces from the bottom up: small, reusable, independently developed and tested components are composed into larger components, then into screens. Vue's own model is component-based: components encapsulate template, logic and style, receive data through props and communicate upward through emitted events, and are typically authored as single-file components (SFCs) [51,52].

Brad Frost's Atomic Design is a widely used vocabulary for the hierarchy: atoms (buttons, inputs), molecules (a search field: label + input + button), organisms (a header), templates (page-level layouts) and pages (templates filled with real content) [53]. Storybook is the most common workshop tool for building components in isolation, documenting their states as "stories" and running visual and interaction tests against them [54,55].

8.2 Principles for Vue components

  1. Props down, events up. A component never mutates its props; it emits events and lets the owner change state [51].
  2. Separate logic from presentation with composables. Stateful logic that does not render anything belongs in a composable function, which can be shared and tested without mounting a component [41].
  3. Use slots for composition. Slots let the parent supply content and layout so generic components do not grow endless configuration props.
  4. Type the public API. With <script setup lang="ts">, defineProps and defineEmits accept type-only declarations, and generic components can be declared with the generic attribute [56,57].

8.3 An atom with a typed API

Destructuring defineProps with default values, as above, is reactive from Vue 3.5 onward [56].

8.4 A generic organism

A data table that works for any row type shows the value of generic components and scoped slots: the table owns layout, sorting and empty states, while each page decides how a cell is rendered [56].

8.5 Stories as living documentation

Storybook stories in Component Story Format (CSF) are plain ES modules: a default export describes the component and named exports describe its states [54,55].

Exercises: Component-driven architecture

9Modular frontend architecture

9.1 Concept

A modular frontend is a single deployable application whose code is divided into modules with explicit public interfaces and controlled dependencies. It is sometimes called a modular monolith. It aims for the maintainability benefits of micro-frontends (clear ownership, local reasoning, parallel work) without their operational cost.

Two partitioning axes are combined:

  • Layers separate concerns within a module. Martin Fowler describes the common presentation / domain / data split and argues that, for larger applications, the top-level partition should be by domain area, with layers inside each area [6].
  • Feature or domain slices separate the business areas. Feature-Sliced Design (FSD) is a published methodology for frontends that standardises the layers app, pages, widgets, features, entities and shared (an older processes layer is deprecated), with the rule that a module may only import from layers below it [7].

9.2 A folder structure for Acme Shop

Each slice exposes only what other slices may use through its index.ts. Everything else is private by convention and, ideally, by lint rule.

9.3 Enforcing boundaries

Boundaries that are not enforced erode. ESLint's built-in no-restricted-imports rule can forbid import paths and patterns, which is enough to block "deep imports" into another slice's internals [58].

9.4 Modules as Vue plugins

For larger domain modules, a "module manifest" lets each module register its own routes, stores and global components through Vue's plugin mechanism, so app/ does not need to know module internals [59].

9.5 Packaging modules: workspaces and Nuxt layers

When modules need separate versioning or reuse across apps, they can become packages in a monorepo. pnpm workspaces link local packages so they can depend on each other with the workspace: protocol [60]. In Nuxt, layers package pages, components, composables, server routes and configuration that an app can extends, merging them into the final application [61].

Modular monolith vs micro-frontends: both partition by domain. The difference is the deployment unit. A modular monolith ships as one artefact and shares one Vue runtime and router, so it avoids run-time integration problems. Micro-frontends add independent deployment at the cost of that integration [5].

Exercises: Modular architecture

9.1 pages/checkout/CheckoutPage.vue contains import { toCents } from '@/entities/cart/lib/money'. The lint rule fails. Fix it properly.

Show solution

Decide whether toCents is part of the cart entity's public contract. If it is a general money utility, move it to shared/lib/money.ts (lowest layer, importable by everyone) [7]. If it is cart-specific, re-export it from entities/cart/index.ts and import from '@/entities/cart'. Disabling the rule for the line is not a fix: it hides a dependency that will later block refactoring of the cart's internals [58].

9.2 Add a featureFlag property to AppModule so that modules can be switched off without code changes. Update installModules.

Show solution

Because route components are lazy, a disabled module's code is never downloaded [17].

10Domain-driven frontend design

10.1 Concept

Domain-driven design (DDD), introduced by Eric Evans, centres software on a model of the business domain expressed in a ubiquitous language shared by developers and domain experts [8]. Its strategic tool is the bounded context: large models are divided into contexts, each with its own consistent model and language, and the relationships between contexts are made explicit [8,62]. Its tactical patterns include entities (identity over time), value objects (defined by their attributes and immutable), aggregates (consistency boundaries with a root) and repositories (collection-like access to aggregates) [8].

On the frontend, DDD is not about copying back-end aggregates into the browser. It is about three practical things:

  1. Aligning modules, routes, stores and teams with bounded contexts (Catalogue, Ordering, Customer, Content), which is also what micro-frontend and modular boundaries should follow [5,62].
  2. Keeping business rules that genuinely live in the UI (validation, pricing display, eligibility) in plain TypeScript that does not depend on Vue, so it can be tested and reused.
  3. Protecting the frontend model from back-end data shapes with an anti-corruption layer (ACL), a translation layer between subsystems with different semantics [63].

10.2 Value objects and an aggregate in plain TypeScript

10.3 Repository port and anti-corruption adapter

The domain declares what it needs (a port); infrastructure supplies an adapter that talks HTTP and translates the legacy API's shape into the domain model, which is the ACL's job [63].

10.4 Wiring the domain into Vue

Vue's provide/inject is a lightweight dependency-injection mechanism; typing the key with InjectionKey keeps it type-safe [64]. The application layer is a composable or Pinia store that orchestrates domain objects and the repository. Because Cart is immutable, the store replaces it on every change, which Vue's reactivity tracks naturally.

Pinia setup stores can call inject() for values provided at the app level [16]. In tests, provide an in-memory repository instead, and the domain classes need no Vue at all.

Organisational alignment: Conway's law suggests that module boundaries will drift toward team communication boundaries [49,50]. Choosing bounded contexts first, and then assigning teams and modules to them, keeps the two aligned instead of fighting each other.

Exercises: Domain-driven frontend design

10.1 Implement an EmailAddress value object that normalises case and whitespace, rejects invalid input, and supports equality. Use it in a signup form so invalid addresses never reach the API.

Show solution

Value objects are defined by their attributes and compared by value, not identity [8]. The UI now passes an EmailAddress, not a string, so downstream code cannot receive an unvalidated value.

10.2 The Catalogue context calls a product Product with a price. The Ordering context needs a CartLine with a unitPrice fixed at the moment of adding. Should both contexts share one Product type? Explain.

Show solution

No. In DDD each bounded context owns its model, and the same real-world concept can be modelled differently in different contexts [8,62]. In Catalogue, price is the current list price and may change; in Ordering, the unit price is a snapshot that must not change under the customer. Sharing one type couples the contexts and invites bugs (for example, re-pricing a cart when the catalogue changes). Translate at the boundary: Ordering receives a SKU and a price and builds its own CartLine.

11Headless CMS integration

11.1 Concept

A headless CMS stores and manages content and exposes it through an API, leaving presentation entirely to the consuming applications. Contentful's Content Delivery API, for example, is a read-only API that returns published entries and assets as JSON for any client to render [65]. Git-based alternatives keep content in the repository: Nuxt Content reads Markdown, YAML and JSON files and exposes them through a query API inside the Nuxt app [66].

Architecturally, the questions are: where is content fetched (build time, server, browser), how are API credentials protected, how does structured content map to Vue components, and how do pages update when editors publish?

ConcernRecommended approach
FetchingOn the server or at build time (SSR/SSG) for SEO and to keep tokens off the client [4,29]
CredentialsPrivate runtime config, never bundled into client code [67]
Rendering rich contentMap typed content blocks to components; avoid raw v-html with untrusted HTML [68]
FreshnessPrerender + rebuild on publish, or swr/isr caching with webhook-triggered invalidation [4]

11.2 A typed CMS client behind a Nuxt server route

Nuxt's runtime config separates private keys, available only on the server, from public keys that are exposed to the client [67]. Placing the CMS call in a server route keeps the delivery token secret and lets the server reshape and cache the response [69].

11.3 Mapping content blocks to components

Editors compose pages from typed blocks (hero, rich text, product carousel). A discriminated union describes the blocks, and a renderer maps each type to a component with Vue's dynamic <component :is> [51].

Security: the Vue security guide warns that rendering user-provided HTML with v-html is a cross-site scripting risk, and that such content should be sanitised or rendered as structured data instead [68]. CMS rich text should preferably be delivered as a structured document (nodes) and rendered with components; if HTML must be used, sanitise it on the server with an allow-list sanitiser before it reaches v-html.

11.4 Publishing workflow

For prerendered sites, the CMS calls a deploy webhook on publish to trigger a rebuild. For swr-cached routes, content refreshes after the TTL; for instant updates, a webhook handler can purge the relevant cache entry. Preview mode for editors usually bypasses caching and uses the CMS's preview API with a separate token.

Exercises: Headless CMS

11.1 Editors add a new block type, quote, before the frontend supports it. Currently the page crashes. Make the renderer resilient, and make TypeScript force developers to register every known block.

Show solution

Keep Record<Block['type'], Component>: adding quote to the Block union then fails type-checking until a component is registered. At run time, render a fallback for unknown types instead of undefined, and drop it in production.

11.2 A developer proposes calling the CMS directly from the browser with fetch and the delivery token in a VITE_ environment variable. List three problems.

Show solution
  1. Any variable embedded in client code is visible to every visitor; the token can be extracted and used to read all published (and possibly preview) content and to burn through API quotas [67].
  2. Content is fetched after JavaScript runs, so crawlers and link previews may see an empty page and LCP suffers [3].
  3. The frontend becomes coupled to the CMS's raw response shape; changing CMS vendors or content models touches every component. A server route acts as an anti-corruption layer [63].

12Backend-for-Frontend (BFF)

12.1 Concept

Sam Newman describes the Backends For Frontends pattern as one server-side component per user experience: rather than a single general-purpose API serving web, mobile and third parties, each frontend gets a backend tailored to its needs, ideally owned by the same team that owns the frontend [70]. Microsoft's Azure Architecture Center describes the same pattern and notes the trade-offs: tailored payloads and independent evolution, against more services to deploy and the risk of duplicated logic between BFFs [71].

For Vue applications the BFF typically does four jobs:

  1. Aggregation: one request from the page fans out to several services and returns exactly the view model the page needs.
  2. Shaping: renaming, filtering and flattening upstream data so components stay simple.
  3. Security: holding OAuth tokens on the server and giving the browser only an HttpOnly session cookie, which JavaScript cannot read [72]. The IETF's best-current-practice document on OAuth for browser-based applications (RFC 10017) describes this Backend for Frontend architecture as one of its recommended patterns [73].
  4. Caching and resilience: timeouts, fallbacks and response caching in one place.

Nuxt makes the BFF a natural part of the application: files in server/api become API endpoints served by Nitro, the server engine that runs on Node.js, serverless and edge platforms [33,69]. A standalone BFF (for example Node.js with Fastify) is equally valid when it must serve a Vite SPA or several clients.

12.2 An aggregating endpoint with partial failure

Promise.allSettled waits for all promises and reports each outcome, so one failing service does not fail the whole response [74]. AbortSignal.timeout() produces a signal that aborts a fetch after a given time [75].

Note the design choice: the BFF returns a view model (label, greeting) rather than raw domain data. That is the point of a BFF: the API belongs to this UI [70]. Where many fields are needed, the BFF can still hand domain data to the client, but it should not become a generic proxy.

12.3 Login flow: tokens stay on the server

The HttpOnly, Secure and SameSite attributes restrict script access, require HTTPS and limit cross-site sending of the cookie, respectively [72]. This is the shape of the BFF pattern described in RFC 10017 [73].

Exercises: BFF

12.1 The recommendations service is slow and identical for all users in the same segment. Cache it in the BFF for five minutes per segment.

Show solution

Nitro provides defineCachedFunction (and defineCachedEventHandler) with a maxAge in seconds and a getKey function that determines the cache key [76].

The cache key must not contain user-specific data, and the cached data must not be user-specific either; otherwise one user's data would be served to another.

12.2 The mobile team asks to reuse the web BFF's /api/dashboard. What does the pattern suggest, and when is sharing acceptable?

Show solution

Newman's pattern suggests one BFF per user experience, so the mobile app should get its own BFF, owned by the mobile team, that can evolve with mobile release cycles and payload needs [70]. Sharing is acceptable when the experiences are genuinely the same; to avoid duplicated logic across BFFs, push shared business logic down into the downstream services or a shared library rather than into one BFF [71].

13Microservices frontend integration

13.1 Concept

Lewis and Fowler characterise the microservice architectural style as building an application as a suite of small services, each running in its own process, communicating through lightweight mechanisms, built around business capabilities and independently deployable [77]. Newman's Building Microservices is the standard book-length treatment [78]. The frontend question is how a Vue application should consume dozens of such services without inheriting their complexity.

13.2 Integration patterns

PatternWhat it doesFrontend impact
Direct client-to-serviceBrowser calls each serviceMany round trips, CORS everywhere, auth in the browser, tight coupling to service topology [79]
API gatewaySingle entry point that routes, authenticates and applies cross-cutting policies [79]One origin and auth model; still service-shaped responses
Gateway aggregationGateway combines several requests into one [80]Fewer round trips, especially on high-latency networks
BFFPer-experience aggregation and shaping (section 12) [70]UI-shaped responses owned by the UI team
GraphQL layerA typed schema over many sources; clients request exactly the fields they need [81]Flexible queries; needs schema governance and query cost control
Micro-frontendsEach service team also owns its UI slice [5]Vertical ownership from database to pixels

These patterns combine. A common shape is: browser → CDN → Nuxt (SSR + BFF routes) → API gateway → services, with micro-frontends added only when the organisation needs independent UI deployment.

13.3 Resilience in the UI

Distributed systems fail partially. The circuit breaker pattern wraps a remote call and, after a threshold of failures, "trips" so that further calls fail fast for a period instead of piling up on a struggling service [82]. In the frontend architecture this belongs in the BFF; the Vue layer's job is to render partial results gracefully. Vue's onErrorCaptured hook lets a component catch errors from its descendants and act as an error boundary [28], and <Suspense> can coordinate loading states of async components (it is still marked experimental) [83].

Unlike user state, a circuit breaker's state is intentionally shared across requests in a server process: it describes the health of a downstream service, not a user. This is the opposite of the cross-request state pollution rule in section 4, and the distinction is worth stating in code review.

13.4 Contract-first clients

With many services, hand-written API types drift. Teams generate TypeScript types from each service's published OpenAPI or GraphQL schema in CI, so a breaking contract change fails the frontend build instead of production [81]. Generated types live in the infrastructure layer and are mapped to domain types there (section 10), so a service's internal renaming does not ripple through components [63].

13.5 Migrating a monolith frontend incrementally

Fowler's Strangler Fig pattern replaces a legacy system gradually: new functionality is built around the old system, routing traffic to the new parts piece by piece until the old one can be retired [84]. For frontends, a reverse proxy in front of both applications sends migrated paths to the new Vue app and everything else to the legacy one; micro-frontends offer the same pattern at the component level, which is why Jackson lists incremental upgrades as one of their benefits [5].

As each area is migrated, one more location block moves to the new application, until the final rule can be switched and the legacy system retired [84].

Exercises: Microservices integration

13.1 Use inventoryBreaker in a BFF endpoint so that when inventory is down, product pages show "Availability unknown" instead of failing.

Show solution

The fallback keeps the page useful, the timeout bounds latency [75], and the breaker stops hammering a failing service [82]. The StockWidget renders "Availability unknown" for status === 'unknown'.

13.2 A product page needs data from five services and currently makes five browser requests with a total latency of about 1.2 s on mobile. Propose an architecture change and estimate its effect qualitatively.

Show solution

Introduce an aggregating BFF (or gateway aggregation) endpoint that calls the five services in parallel inside the data centre and returns one view model [70,80]. The browser now pays one high-latency mobile round trip instead of several, and the internal calls run over low-latency links in parallel, so total time approaches that of the slowest service plus one round trip. If the page is SSR-rendered by the same Nuxt server, the data is embedded in the HTML payload and the browser makes no extra data request at all on first load [29].

A reference architecture for Acme Shop

  • Rendering: Nuxt with hybrid route rules: prerendered marketing and editorial pages, swr product pages, client-only cart and account [4].
  • Code organisation: Nuxt layers per bounded context (catalogue, ordering, customer, content) plus a design-system layer; feature-sliced structure inside each layer; ESLint-enforced public APIs [7,58,61].
  • Domain: plain TypeScript value objects and aggregates in each context; anti-corruption mappers at the edges [8,63].
  • Back end: Nuxt server routes as the web BFF, holding tokens and aggregating microservices behind an API gateway, with circuit breakers and cached segment data [70,76,79,82].
  • Content: headless CMS rendered through a typed block registry, refreshed by webhook [65].
  • Offline: PWA with precached static assets and network-first documents [37,39].
  • Growth path: if the organisation grows to many teams, a context layer can be extracted into a federated remote with the same boundaries [5,45].

Capstone exercise

14.1 A city library wants a Vue-based public catalogue (SEO matters), a members' area (loans, holds), offline access to a member's loan list on mobile, editor-managed event pages, and integration with three existing services (catalogue search, membership, events). One team of five developers will build it. Propose an architecture and justify each choice in one sentence.

Show solution
  • Nuxt with hybrid rendering: SSR (with short swr) for catalogue pages so they are crawlable and fresh; prerendered static pages for "about" content; ssr: false for the members' area [3,4].
  • Modular monolith, not micro-frontends: one team does not have the coordination problem micro-frontends solve [5]; organise as layers or slices per context (catalogue, membership, events) [7,61].
  • Nuxt server routes as BFF: aggregate the three services and keep the membership token in an HttpOnly session cookie flow [70,72,73].
  • Headless CMS for events: editors publish without deployments; event pages use swr plus webhook purge [4,65].
  • PWA: a service worker caches the loan list API with network-first so members can see it offline; static assets are precached [37,39].
  • Component-driven UI: a small design system in Storybook to keep public and members' areas consistent and accessible [53,54].
