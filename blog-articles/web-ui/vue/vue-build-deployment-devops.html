Build, Deployment and DevOps for Vue.js Applications

From vite build to a monitored production system: how a Vue single-page application is compiled, configured, packaged, shipped through CI/CD to AWS, Azure or Google Cloud, cached at the edge, and observed once it is live.

Written November 2026 against Vite 8, Vue 3 and current vendor documentation. Citations follow the Vancouver system; numbers in square brackets refer to the list at the end.

Introduction

A Vue application spends most of its life not on a developer's laptop but on a server, a CDN edge and in thousands of browsers. Getting it there reliably is a pipeline problem. Source code is transformed by a build tool into static HTML, JavaScript and CSS; those files are packaged (as a folder, a container image or both); an automated pipeline tests and promotes the package through environments; a web server or object store serves it, usually behind a content delivery network; and telemetry flows back so the team can see whether users are actually having a good time.

This article walks that pipeline end to end. Each section explains the concept, shows working configuration, and links every non-obvious claim to primary documentation. The running example is a typical Vue 3 single-page application (SPA) created with Vite and using Vue Router in HTML5 history mode, talking to a JSON API at /api.

1The Vite build system

1.1 What Vite does

Vite is the official build tool recommended by the Vue team and the default for projects scaffolded with npm create vue@latest.[1,2] It has two distinct halves. In development it runs a dev server that serves source files over native ES modules, transforming each file on demand and pushing changes through Hot Module Replacement (HMR), so start-up time does not grow with the size of the application.[2,3] For production, vite build bundles the application into a small set of optimised static files.[4]

Vite 8 (2026) replaced the previous pairing of esbuild (for dependency pre-bundling) and Rollup (for production bundling) with a single Rust-based bundler, Rolldown, which keeps a Rollup-compatible plugin API while making builds substantially faster.[5] For most Vue projects the switch is invisible: @vitejs/plugin-vue and the common Rollup-style plugins keep working. Configuration that previously lived under build.rollupOptions now lives under build.rolldownOptions, with the old name kept as a deprecated alias during the transition.[5,6]

1.2 The entry point is index.html

Unlike older bundlers, Vite treats index.html at the project root as the entry point. Script tags with type="module" and stylesheet links in that file are resolved, bundled and rewritten to hashed output files during the build.[2,4]

2.1 What changes inside Vue

Vue ships separate development and production builds. The development build contains extensive runtime warnings and devtools integration; the production build removes those code paths, which makes it smaller and faster. Bundlers such as Vite select the right one automatically based on the build mode.[1] Vue also exposes compile-time feature flags that bundlers replace with literal values so that dead code can be tree-shaken:[10]

  • __VUE_OPTIONS_API__ (default true): set to false if the app uses only the Composition API to drop Options API support.
  • __VUE_PROD_DEVTOOLS__ (default false): enables devtools in production builds. Leave it off.
  • __VUE_PROD_HYDRATION_MISMATCH_DETAILS__ (default false): verbose hydration warnings in production, relevant only to SSR.

With Vite, @vitejs/plugin-vue supplies the defaults; override them with define in vite.config.ts if needed.[10]

2.2 Modes are not the same as NODE_ENV

Vite distinguishes the mode (a label such as development, production or staging that selects which .env files are loaded) from NODE_ENV (which controls whether a production-optimised build is produced). Running vite build --mode staging produces a fully optimised production bundle that reads .env.staging. This lets you build several environment-specific bundles that are all production-grade.[9]

3Environment variables

3.1 The .env file hierarchy

Vite loads variables from files in the project root (or envDir) in this order of increasing priority:[9]

  1. .env: loaded in all modes
  2. .env.local: loaded in all modes, ignored by git
  3. .env.[mode]: loaded only in the specified mode
  4. .env.[mode].local: mode-specific, ignored by git

Mode-specific files win over generic ones, and variables that already exist in the process environment when Vite starts (for example those set by a CI runner) win over all files.[9]

3.2 Exposure rules: the VITE_ prefix

Only variables whose names start with VITE_ are exposed to client code through import.meta.env; the prefix can be changed with envPrefix. Vite also provides built-in constants: import.meta.env.MODE, BASE_URL, PROD, DEV and SSR.[9] Exposed values are statically replaced in the output at build time, so anything prefixed VITE_ is visible to anyone who downloads your JavaScript.[9]

Security rule. A browser bundle cannot keep a secret. API keys that grant privileged access, database passwords and signing tokens belong on a server, never in a VITE_ variable. Public identifiers (a Sentry DSN, a publishable analytics key) are acceptable because they are designed to be public.[9,11]

3.3 TypeScript IntelliSense

Augment ImportMetaEnv so typos in variable names become compile errors:[9]

3.4 Using env values inside vite.config.ts

Vite does not load .env files into process.env before evaluating the config, because which files apply depends on the mode. Use the exported loadEnv helper instead; passing '' as the prefix loads every variable, not only VITE_ ones.[12]

3.5 Build-time vs. runtime configuration

Because Vite inlines variables at build time, a bundle built for staging contains staging URLs. Teams that want to build once and deploy the same artefact to every environment, as the twelve-factor methodology recommends by keeping config in the environment rather than the code,[13] use a small runtime configuration file loaded before the app starts. The container entrypoint in section 8.4 generates such a file from environment variables.

5Asset optimisation

A production bundle is fast when it is small, split along user journeys, compressed on the wire and cached aggressively. Vite automates much of this; the rest is configuration.

5.1 How Vite handles assets

  • Imported assets (import logo from './logo.png') are given a content-hashed file name and the import resolves to its public URL. Assets smaller than assetsInlineLimit are inlined as base64 data URLs.[14]
  • The public/ directory is copied to the output root as-is, without hashing. Use it for files that must keep an exact name (robots.txt, favicon.ico, platform config files) and reference them with absolute paths.[14]
  • Query suffixes change how an import is handled: ?url returns a URL, ?raw the file contents as a string, ?inline forces inlining.[14]
  • Dynamic asset URLs can be built with new URL(`./img/${name}.png`, import.meta.url), which Vite resolves at build time.[14]

5.2 Code splitting with lazy routes

Every dynamic import() becomes a separate chunk that loads on demand. Lazy-loading route components (as in the router above) is the most effective split for SPAs, because users download only the views they visit. Vite also rewrites dynamic imports so that a chunk's dependencies and CSS are fetched in parallel rather than as a waterfall.[3]

5.3 Analysing bundle size

When a chunk crosses chunkSizeWarningLimit, Vite prints a warning.[6] Inspect what is inside with a visualiser plugin, then attack the largest items: replace heavy dependencies, import only the functions you use so tree-shaking can work, and move rarely used features behind dynamic imports.

5.4 Compression

Text assets compress extremely well. Servers can compress on the fly (Nginx gzip on), or serve pre-compressed .gz files produced at build time so no CPU is spent per request.[16] Most CDNs also compress automatically at the edge; configure compression in exactly one place to keep behaviour predictable.

5.5 Caching strategy

Content hashing enables the most important performance optimisation of all: because a hashed file's name changes whenever its content changes, the file can be cached for a year and marked immutable. The HTML entry point must not be cached that way, because it is the only file whose name is stable and it points to the current hashes.[17,18]

PathCache-ControlReason
/assets/* (hashed)public, max-age=31536000, immutableName changes with content; never revalidate.[18]
/index.htmlno-cacheStored but revalidated on every use, so new deploys are picked up immediately.[18,19]
/config.js, other un-hashed filesno-cache or a short max-ageContent may change without a name change.
Note the difference. no-cache does not mean "do not cache"; it means "cache, but revalidate before reuse". no-store forbids storage entirely.[18,19]

6Static site deployment

The output of vite build is a folder of static files. Any static host can serve it: a web server, an object store, or a managed platform. Vite's deployment guide covers GitHub Pages, GitLab Pages, Netlify, Vercel, Cloudflare Pages, Firebase, Azure Static Web Apps and others.[8]

6.1 The SPA fallback problem

With createWebHistory, URLs look like /orders/42. Navigating inside the app works, but a hard refresh or a shared link sends /orders/42 to the server, which has no such file and returns 404. Every host therefore needs a fallback rule: if a request does not match a real file, serve index.html and let the router handle it.[15] Each platform spells this differently:

PlatformFallback mechanism
Nginxtry_files $uri $uri/ /index.html;[15,20]
Azure Static Web AppsnavigationFallback in staticwebapp.config.json[21]
Firebase Hostingrewrites to /index.html in firebase.json[22]
Amazon S3 + CloudFrontCloudFront error response or function mapping 403/404 to /index.html
GitHub PagesNo server rewrites: copy index.html to 404.html, or use hash history

A catch-all route (/:pathMatch(.*)*) in the router then renders a proper "not found" view for URLs that are genuinely invalid, since the server now answers 200 for everything.[15]

7Nginx

Nginx is the most common web server for self-hosted Vue SPAs and the default base for containerised ones. A good configuration does five jobs: serve files from dist/, fall back to index.html for client-side routes, set correct cache headers, compress responses, and optionally reverse-proxy /api to the backend so the browser sees a single origin.

7.1 Key directives

  • try_files checks files in order and uses the last parameter as the fallback; try_files $uri $uri/ /index.html is the canonical SPA rule.[15,20]
  • location = /path is an exact match and takes precedence over prefix matches; ^~ prefix matches stop the regex search.[20]
  • add_header adds response headers; with the always parameter it applies to error responses too. Crucially, add_header directives are inherited from the enclosing level only if the current level defines none of its own.[23]
  • expires sets Expires and Cache-Control: max-age.[23]
  • gzip, gzip_types and gzip_min_length control on-the-fly compression; text/html is always compressed when gzip is on.[16]
  • log_format with escape=json produces machine-parsable access logs.[24]

8Docker

Containerising a Vue app produces an immutable, versioned artefact that runs identically on a laptop, in CI and in any cloud. The standard pattern is a multi-stage build: one stage with Node.js compiles the app, and a second, much smaller stage with Nginx serves only the compiled dist/ folder. Everything from the build stage that is not explicitly copied (Node, node_modules, source) is left behind.[27]

8.1 .dockerignore

The build context is sent to the builder; excluding local artefacts keeps it small and prevents a stale node_modules or .env.local leaking into the image.[28]

8.2 Multi-stage Dockerfile

Points worth noting:

  • Layer ordering. Copying the lockfile before the source means npm ci reruns only when dependencies change; the RUN --mount=type=cache form additionally persists npm's download cache between builds.[28]
  • COPY --from=build pulls files from an earlier stage; the final image contains Nginx and static files only.[27]
  • Templates. The official nginx image renders every *.template in /etc/nginx/templates/ with envsubst into /etc/nginx/conf.d/ and runs executable scripts in /docker-entrypoint.d/ before starting Nginx.[25]
  • HEALTHCHECK lets Docker (and Compose) know whether the container is actually serving.[28]
  • Pin versions. For reproducible builds, pin base images to a specific version or digest rather than a floating tag.[28]

10CI/CD concepts

Continuous integration means every change is automatically built and tested on a shared server; continuous delivery means every change that passes is packaged into a deployable artefact; continuous deployment goes one step further and releases it automatically. A Vue pipeline normally contains these stages:

Principles that apply on every platform:

  • Deterministic installs. Use npm ci (or the equivalent for pnpm/yarn) against a committed lockfile, and cache the package manager's download cache keyed on the lockfile hash.[31,32]
  • Build once, promote the same artefact. Re-building per environment risks shipping something different from what was tested.[13]
  • Least-privilege credentials. Prefer short-lived OpenID Connect (OIDC) tokens exchanged for cloud credentials over long-lived secrets stored in the CI system.[33,34]
  • Gates. Protect production with environments, required reviewers or manual approval.[32,35,36]

10.1 GitHub Actions

Workflows are YAML files in .github/workflows/. A workflow is triggered by events (on), contains jobs that run on runners, and each job runs steps that either execute shell commands or call reusable actions.[35] actions/setup-node can cache the npm cache directory automatically with cache: npm.[31,37]

Deploying to GitHub Pages

GitHub Pages can be published by a custom workflow that uploads a Pages artefact and deploys it; the deploy job needs pages: write and id-token: write permissions.[38] For a project site served at https://user.github.io/repo/, build with base: '/repo/'.[8]

Building and pushing a container image

Pin actions. Third-party actions run with your workflow's permissions. Pin them to a full commit SHA in security-sensitive repositories, and keep the top-level permissions block as narrow as possible.[35]

10.2 GitLab CI/CD

GitLab pipelines are defined in .gitlab-ci.yml at the repository root. Jobs are grouped into stages that run in order; cache speeds up repeated dependency downloads, artifacts pass build outputs to later jobs, rules decide when a job runs, and environment records deployments.[32,39]

  • cache:key:files derives the cache key from the lockfile, so the cache is invalidated exactly when dependencies change.[32]
  • artifacts:reports:junit makes test results appear in merge requests.[39]
  • needs lets a job start as soon as its dependencies finish instead of waiting for the whole previous stage, and when: manual inside rules creates a human approval gate.[32]
  • $CI_REGISTRY_IMAGE, $CI_COMMIT_SHORT_SHA and the registry credentials are predefined variables supplied by GitLab.[32]

10.3 Jenkins

Jenkins pipelines are written as code in a Jenkinsfile committed to the repository.[40] The declarative syntax structures a pipeline into agent, options, environment, stages and post sections; when conditions, parallel stages and input approval steps are built in.[36] With the Docker Pipeline plugin, a stage can run inside a container image so build agents need only Docker installed.[41]

  • reuseNode true runs the container on the same node and workspace as the enclosing pipeline, so node_modules installed in one stage is visible in the next.[36]
  • credentials() in an environment block and withCredentials inject secrets from the Jenkins credential store and mask them in logs.[36,40]
  • post conditions such as always, failure and cleanup run after stages finish, which makes them the right place for test reports and notifications.[36]
  • docker.build and docker.withRegistry come from the Docker Pipeline plugin.[41]

11Cloud deployment

All three major clouds offer two broad routes for a Vue SPA: static hosting (object storage or a managed static-site service, fronted by a CDN) and container hosting (run the Nginx image from section 8). Static hosting is cheaper and simpler when the frontend is purely static; containers suit teams that already standardise on images, need runtime configuration, or co-locate a reverse proxy with the frontend.

11.1 AWS: S3 + CloudFront

The recommended architecture keeps the S3 bucket private and lets only CloudFront read it using origin access control (OAC); the bucket policy grants s3:GetObject to the CloudFront service principal, conditioned on the distribution's ARN.[42]

Two CloudFront settings complete the SPA setup: set the default root object to index.html, and add custom error responses that map 403 and 404 from the origin to /index.html with status 200, so deep links reach the router. (A private S3 origin returns 403, not 404, for missing keys, which is why both codes are mapped.)

CloudFront respects Cache-Control headers stored as S3 object metadata, so cache policy is set at upload time.[43] aws s3 sync accepts --cache-control and --exclude, which allows a two-pass upload with different headers.[44] Because hashed assets get new names, only the un-hashed entry files need invalidating; AWS recommends versioned file names over invalidations for frequently updated content.[45,46]

In GitHub Actions, authenticate with OIDC instead of storing access keys: the job requests an ID token (id-token: write) and aws-actions/configure-aws-credentials exchanges it for temporary credentials of an IAM role whose trust policy names the repository.[33]

11.2 Azure: Static Web Apps

Azure Static Web Apps (SWA) builds and hosts static frontends with globally distributed content, preview environments for pull requests and an optional managed API. Routing, headers and the SPA fallback are configured in staticwebapp.config.json.[21,47] Place the file in public/ so that Vite copies it into dist/.

Excluding /assets/* from the fallback is important for the same reason as the Nginx =404 rule: a missing chunk must fail loudly rather than return HTML.[21] Deployment from GitHub uses the SWA action with the app and output locations:[47]

For multi-region, high-traffic or WAF-protected deployments, place Azure Front Door in front of the origin. Front Door is Microsoft's global CDN and application delivery service, combining edge caching, load balancing and a web application firewall.[48] The same container image from section 8 can also be run on any Azure container service, authenticating from CI via OIDC federated credentials.[34]

11.3 Google Cloud: Cloud Run, Firebase Hosting, Cloud Storage

Cloud Run (container)

Cloud Run runs a container image and routes HTTP traffic to it. The container must listen on the port given in the PORT environment variable, which defaults to 8080, which is why the Nginx template uses listen ${PORT}.[49,50]

Firebase Hosting (static)

Firebase Hosting serves static files from a global CDN. firebase.json declares the public directory, a rewrite for the SPA fallback, and per-path headers.[22]

Firebase applies rewrites only when no static file matches the request, so real assets are still served directly.[22]

Cloud Storage + Cloud CDN

A Cloud Storage bucket can host a static site behind an external Application Load Balancer with a custom domain and managed TLS, with Cloud CDN enabled on the backend bucket to cache content at Google's edge.[51,52] Upload with gcloud storage rsync and set Cache-Control metadata on objects in the same two-pass manner as the S3 script.

12CDN integration

A content delivery network caches responses at edge locations close to users. For an SPA almost every byte is cacheable, so a CDN typically serves the overwhelming majority of requests and the origin sees only cache misses and revalidations of index.html. CloudFront, Azure Front Door and Cloud CDN all follow the HTTP caching model defined in RFC 9111 and honour origin Cache-Control headers by default, subject to the cache policy you configure.[19,43,48,52]

12.1 Concepts

  • Cache key. The parts of a request (path, selected query strings, headers) that identify a cached object. Keep it minimal: hashed assets need only the path.
  • TTL. Derived from Cache-Control: max-age or s-maxage (which applies only to shared caches such as CDNs), unless overridden by CDN policy.[18,19]
  • Invalidation vs. versioning. Invalidations purge objects but take time to propagate and may be billed; versioned (hashed) file names avoid the need entirely.[45,46]
  • Revalidation. no-cache on index.html makes the edge (and the browser) ask the origin whether it changed, typically getting a cheap 304 Not Modified via ETag.[17]

12.2 Safe deploy ordering

  1. Upload new hashed assets. They are unreferenced, so nothing changes for users yet.
  2. Upload the new index.html (and config.js), which atomically switches new visitors to the new release.
  3. Invalidate the entry points at the CDN.
  4. Delete old assets only after a grace period (for example, after two further releases) so that tabs still running the old release can lazy-load their chunks.

This ordering, combined with the client-side vite:preloadError handler from section 2.3, eliminates nearly all "failed to fetch dynamically imported module" errors after a release.[4]

12.3 Serving assets from a separate CDN domain

base accepts a full URL, so base: 'https://cdn.example.com/orders/' makes every asset reference in the built HTML and JS point to the CDN.[12] Because Vite loads module scripts (which are fetched in CORS mode), the CDN must send an appropriate Access-Control-Allow-Origin header for the application's origin.

13Monitoring

Monitoring answers "is it working, and is it fast?" For a frontend, the server being up is necessary but not sufficient, because most of the work happens in the user's browser. A complete setup combines four layers.

LayerQuestionTooling

TracingWhere does time go across browser and API?OpenTelemetry, Sentry tracing

13.1 Core Web Vitals

Google's Core Web Vitals are Largest Contentful Paint (LCP, loading), Interaction to Next Paint (INP, responsiveness) and Cumulative Layout Shift (CLS, visual stability). The "good" thresholds are LCP of 2.5 s or less, INP of 200 ms or less, and CLS of 0.1 or less, measured at the 75th percentile of page loads.[53] SPAs are particularly prone to poor INP (heavy component updates on the main thread) and poor LCP (content that renders only after JavaScript loads), so these are worth tracking per release.

13.2 Distributed tracing with OpenTelemetry

OpenTelemetry provides vendor-neutral APIs and SDKs for traces, metrics and logs. Its browser SDK can record document-load timing and outgoing fetch calls as spans and propagate W3C trace context headers to the API, so a slow page can be traced through to the backend query that caused it. The project documents browser instrumentation as experimental, so pin versions and test upgrades.[54]

Load tracing early in main.ts, before the app mounts, so the document-load span is captured. Expose the collector through the same Nginx server (a location /otel/ proxy) to avoid CORS and ad-blocker issues.

14Logging

Logs are discrete, timestamped records of events. A Vue deployment produces logs in two places: on the server (Nginx access and error logs) and in the browser (application events that you choose to ship).

14.1 Server-side logs

The JSON log_format in section 7 produces one parseable object per request, including $request_id, which is also forwarded to the API as X-Request-ID so frontend and backend log lines can be correlated.[20,24] In the official Docker image, Nginx's access and error logs are linked to the container's standard output and standard error, so docker logs, Compose and every cloud container platform collect them without extra agents.[25] Following the twelve-factor approach, treat logs as event streams written to stdout and let the platform route them.[13]

14.2 Client-side logs

Browser console output is invisible to the team. Ship only what is useful (warnings, errors and significant business events), in batches, with context.

Privacy. Client logs can easily capture personal data from forms and URLs. Scrub before sending, apply retention limits, and document what is collected.

15Error tracking

Error tracking aggregates exceptions from all users, groups identical ones, and attaches the stack trace, release, browser, route and the user actions that led to the failure. Vue provides the hook; a service such as Sentry does the aggregation.

15.1 Vue's global error handler

app.config.errorHandler receives uncaught errors propagating from within the application, including errors thrown in component renderers, event handlers, lifecycle hooks, setup(), watchers, directive hooks and transition hooks. It is called with the error, the component instance and an information string identifying the source.[55] Errors outside Vue's control (third-party scripts, plain setTimeout callbacks, unhandled promise rejections) need browser-level listeners.

15.2 Sentry for Vue

The @sentry/vue SDK is initialised with the app instance, attaches to Vue's error handling, and with browserTracingIntegration also records page-load and navigation performance, using Vue Router to name transactions after routes.[11,56]

  • Release. Tag every event with the same release identifier used when uploading source maps (for example the commit SHA), so each error is resolved against the right maps and regressions can be linked to a deploy.[57]
  • Environment. Separate staging noise from production.
  • Sampling. Errors are typically captured in full while performance traces are sampled to control volume and cost.[56]

16Source maps

A minified production stack trace such as at e (index-DiwrgTda.js:1:20381) is useless for debugging. A source map is a JSON file that maps positions in generated code back to positions in the original sources. The format was standardised by Ecma International as ECMA-426 in December 2024. Its key fields are version, sources, optional sourcesContent, names and the Base64-VLQ-encoded mappings. A generated file usually points to its map with a trailing //# sourceMappingURL= comment.[58]

16.2 Upload, then delete

The recommended production pattern is to generate maps, upload them to the error tracker during the CI build, and then remove them from the deployed artefact so the original source is not publicly downloadable. Sentry's Vite plugin does all three; it also injects debug IDs into each bundle and its map, so Sentry can match them reliably without depending on URLs.[57,59] The vite.config.ts in section 4 shows the plugin configured with filesToDeleteAfterUpload, and the CI examples pass SENTRY_AUTH_TOKEN as a secret.

As a defence in depth, block map files at the web server in case one is ever deployed by mistake:

Self-hosted alternative. If you do not use a hosted tracker, keep the .map files as a CI artefact tied to the release, and resolve stack traces offline with any ECMA-426-compliant library when investigating an incident.[58]

Each exercise builds on the running example. Try it before opening the solution.

Exercise 1 · Environment variables

Which value wins?

A project has .env with VITE_API=/api, .env.staging with VITE_API=https://stg.example.com/api and .env.staging.local with VITE_API=http://localhost:9000/api. The CI runner exports VITE_API=https://ci.example.com/api and runs vite build --mode staging. (a) What is import.meta.env.VITE_API? (b) What are import.meta.env.MODE and import.meta.env.PROD? (c) Would DB_PASSWORD defined in .env.staging appear in the bundle?

Show solution

(a) https://ci.example.com/api. Variables already present in the process environment take precedence over every .env file. Without the CI variable, .env.staging.local would win, but .local files are normally git-ignored and therefore absent in CI.[9]

(b) MODE is "staging"; PROD is true, because vite build produces a production build regardless of the mode name.[9]

(c) No. Only variables with the VITE_ prefix (or the configured envPrefix) are exposed to client code.[9]

Exercise 2 · Build configuration

Deploy to a GitHub Pages project site

The app must be served from https://acme.github.io/orders/. Write the minimal changes to vite.config.ts and the router, and explain how to make deep links like /orders/items/7 survive a refresh on GitHub Pages.

Show solution

base rewrites every asset URL and sets import.meta.env.BASE_URL, which the router uses as its base.[12,15] GitHub Pages has no rewrite rules, so copy dist/index.html to dist/404.html in the workflow (as in section 10.1); Pages then serves the app for unknown paths and the router renders the correct view. The alternative is createWebHashHistory, which avoids server requests for routes at the cost of # in URLs.[15,38]

Exercise 3 · Nginx

Fix the refresh 404

Users report that https://app.example.com/orders/42 works when clicked inside the app but returns "404 Not Found" after pressing F5. The server block contains only root /usr/share/nginx/html; location / { }. Fix it without breaking 404s for missing JavaScript files.

Show solution

On refresh the browser asks the server for /orders/42, which is not a file. try_files tries the URI as a file, then as a directory, then internally redirects to /index.html so Vue Router can render the route.[15,20] The separate /assets/ block ensures a missing chunk returns a real 404 instead of HTML.

Exercise 4 · Caching

Why did the security headers disappear?

A colleague adds add_header Cache-Control "public, max-age=31536000, immutable"; inside location /assets/. Afterwards, security scanners report that JavaScript files no longer carry X-Content-Type-Options, which is set at server level. Explain and fix. Then explain why index.html must not receive the same header.

Show solution

add_header directives are inherited from the previous level only if the current level defines none. Adding any add_header to the location cancels inheritance of all server-level headers, so they must be repeated inside the location (as in section 7.2).[23]

index.html has a stable name and references the current hashed bundles. If it were cached as immutable for a year, browsers and CDNs would keep loading the old release. It should use no-cache so it is revalidated on every load.[17,18]

Exercise 5 · Docker

Make the image small and the build fast

Critique this Dockerfile and rewrite it:

Show solution

Problems: (1) the final image contains Node, the full node_modules and the source, making it hundreds of megabytes larger than needed; (2) COPY . . before installing means any source change invalidates the dependency layer; (3) npm install may modify the lockfile and is not deterministic; (4) there is no .dockerignore, so a local node_modules may be sent and copied in; (5) no cache headers or health check.

Exercise 6 · Runtime configuration

One image, three environments

The same image must run in dev, staging and production with different API URLs and Sentry DSNs, without rebuilding. Describe the mechanism end to end, and state one limitation.

Show solution

At container start, an entrypoint script in /docker-entrypoint.d/ (run by the official Nginx image before Nginx starts) writes /usr/share/nginx/html/config.js containing window.__APP_CONFIG__ = {...} from environment variables.[25] index.html loads /config.js with a classic script before the module entry, and runtime-config.ts merges it over build-time defaults. Nginx serves config.js with no-cache. This keeps configuration in the environment, as the twelve-factor methodology recommends.[13]

Limitations: values are still public (never put secrets there); values used at build time (such as base or tree-shaken feature flags) cannot change at runtime; and a read-only root filesystem requires writing to a mounted volume.

Exercise 11 · CDN

"Failed to fetch dynamically imported module"

After each release, Sentry shows a spike of TypeError: Failed to fetch dynamically imported module for about an hour. The deploy script runs aws s3 sync dist s3://bucket --delete followed by a CloudFront invalidation of /*. Explain the cause and propose a fix on both server and client.

Show solution

Cause. Users with the app already open are running the previous release, whose index.html references old hashed chunks. --delete removes those chunks, so the next lazy route load returns 403/404 (or HTML via the SPA fallback).

Server fix. Upload assets first without --delete, then index.html; invalidate only the entry points; prune old assets after a grace period (section 12.2). Versioned file names make a full /* invalidation unnecessary.[44,45]

Client fix. Listen for vite:preloadError and reload once so the user picks up the new index.html (section 2.3).[4]

Exercise 12 · Error tracking and source maps

Readable stack traces without publishing your source

Production errors in Sentry show only minified frames such as at n (index-DiwrgTda.js:1:20381). The security team does not want .map files to be publicly downloadable. Configure the build and pipeline, and list two ways to verify the result.

Show solution

'hidden' emits map files without the sourceMappingURL comment.[6] The Sentry Vite plugin uploads maps during the build, injects debug IDs linking each bundle to its map, and deletes the maps afterwards.[57,59] Set the same release in Sentry.init as in the upload.

Verification: (1) find dist -name '*.map' returns nothing and grep sourceMappingURL dist/assets/*.js finds no matches; (2) trigger a test error in staging and confirm Sentry shows original file names and line numbers from .vue and .ts files. Optionally add location ~* \.map$ { return 404; } as defence in depth.

Exercise 13 · Monitoring

Diagnose a slow release

After release 1.5.0, the 75th-percentile INP rises from 140 ms to 320 ms on the orders list page, while LCP and CLS are unchanged. Is this "good" according to Core Web Vitals? Where would you look, and which telemetry from this article helps?

Show solution

No. INP of 200 ms or less at the 75th percentile is "good"; 320 ms falls in "needs improvement".[53] INP measures responsiveness to interactions, so the regression is in event handling or re-rendering after a click or keypress, not in loading. Because vitals are tagged with release and path (section 13.1), you can confirm the regression began with 1.5.0 on one route. Then diff that release for changes to the list component, such as a watcher that now re-sorts thousands of rows synchronously, missing keys causing full re-renders, or a new deep reactive object. Sentry or OpenTelemetry traces for that route show whether time is spent in the browser or in a slower API response.[54,56]
