Enterprise Vue.js Development

Architecture, standards and delivery practices for large-scale Vue 3 applications, from component libraries and monorepos to observability, release management and backward compatibility.

Introduction and scope

Vue.js describes itself as a progressive framework that can be adopted incrementally, from enhancing static HTML to powering full single-page applications [1]. That flexibility is an asset for small teams, but at enterprise scale (dozens of developers, hundreds of screens, several products sharing one codebase, multi-year support windows) the same flexibility turns into risk unless the organization settles on explicit conventions. This article collects those conventions. Each section explains the concept, shows idiomatic Vue 3 code using the Composition API, <script setup> and TypeScript, and ends with an exercise and a worked solution.

All factual claims are referenced to primary sources (official framework documentation, W3C and IETF specifications, OWASP guidance and similar) using the Vancouver system: sources are numbered in the order they are first cited, and the full list appears in the References section. Recommendations that are the author's engineering judgement rather than documented fact are phrased as recommendations.

Baseline assumed. Vue 3 with Single-File Components (SFCs) [2], TypeScript [3], Vite as the build tool [4], Pinia for state [5], Vue Router [6] and Vue I18n [7]. Vue 2 reached end of life on 31 December 2023 [8], so new enterprise work should target Vue 3.

1. Large component libraries

Concepts

Components are Vue's primary unit of reuse. An SFC co-locates template, logic and styles, which the Vue team argues gives better cohesion than separating files by technology [2]. In a large library, three API surfaces matter for every component: props (input), emits and v-model (output), and slots (composition of content) [9]. Since Vue 3.4, defineModel() is the recommended way to implement two-way binding on a component [10]. Attributes that a component does not declare as props fall through to its root element by default, which can be turned off with inheritAttrs: false when a wrapper needs to forward them to an inner element instead [11].

The official Style Guide lists naming rules that become essential at scale: multi-word component names (to avoid clashes with current and future HTML elements), detailed prop definitions, PascalCase file names, and a prefix for base components such as Base, App or V [12]. Large libraries usually adopt a company prefix (for example Acme) for the same reason.

Heavy components (charts, rich-text editors, data grids) should be loaded on demand. defineAsyncComponent() accepts a loader returning a dynamic import() plus optional loading and error components, a delay and a timeout [13].

Example: a typed, accessible base button

<!-- packages/ui/src/components/AcmeButton.vue -->
<script setup lang="ts">
import { computed } from 'vue'

type Variant = 'primary' | 'secondary' | 'danger'
type Size = 'sm' | 'md' | 'lg'

const props = withDefaults(defineProps<{
  variant?: Variant
  size?: Size
  loading?: boolean
  disabled?: boolean
  type?: 'button' | 'submit' | 'reset'
}>(), {
  variant: 'primary',
  size: 'md',
  loading: false,
  disabled: false,
  type: 'button',
})

const emit = defineEmits<{ click: [event: MouseEvent] }>()

defineSlots<{
  default(): unknown
  icon?(): unknown
}>()

const isInert = computed(() => props.disabled || props.loading)

function onClick(e: MouseEvent) {
  if (isInert.value) return
  emit('click', e)
}
</script>

<template>
  <button
    :type="type"
    class="acme-btn"
    :class="[`acme-btn--${variant}`, `acme-btn--${size}`]"
    :aria-disabled="isInert || undefined"
    :aria-busy="loading || undefined"
    @click="onClick"
  >
    <span v-if="$slots.icon" class="acme-btn__icon" aria-hidden="true"><slot name="icon" /></span>
    <slot />
  </button>
</template>

Two design decisions are worth noting. First, the button uses aria-disabled instead of the native disabled attribute while loading, so it stays focusable and screen-reader users can still discover it; this follows the WAI-ARIA Authoring Practices pattern for buttons [14]. Second, all props are typed through defineProps<T>(), which Vue compiles into runtime prop declarations [3].

2. Shared UI design systems

Concepts

A design system is more than a component library: it includes design decisions (color, spacing, typography, motion) expressed as design tokens, usage guidelines, and the components that apply them. The W3C Design Tokens Community Group published the first stable version of its interchange format, the Design Tokens Format Module 2025.10, which defines a JSON format ($value, $type, aliases with curly-brace references) that tools can exchange [17]. Generating CSS custom properties from that file lets every Vue app consume tokens without coupling to a particular CSS framework.

Vue SFCs support scoped CSS, CSS modules and v-bind() inside <style> to connect reactive state to CSS custom properties [18]. For a design system, scoped styles with token-based custom properties keep components themeable while preventing leakage.

Documentation and visual review are normally done in Storybook, which provides a Vue 3 + Vite framework integration [19].

Example: tokens to CSS variables, then a theme provider

// packages/tokens/tokens.json (DTCG 2025.10 format)
{
  "color": {
    "brand": { "$type": "color", "$value": { "colorSpace": "srgb", "components": [0.11, 0.37, 0.85] } },
    "text":  { "$type": "color", "$value": { "colorSpace": "srgb", "components": [0.07, 0.09, 0.12] } },
    "action": { "$type": "color", "$value": "{color.brand}" }
  },
  "space": {
    "sm": { "$type": "dimension", "$value": { "value": 8,  "unit": "px" } },
    "md": { "$type": "dimension", "$value": { "value": 16, "unit": "px" } }
  }
}
// packages/ui/src/theme/useTheme.ts
import { inject, provide, readonly, ref, watchEffect, type InjectionKey, type Ref } from 'vue'

export type ThemeName = 'light' | 'dark' | 'high-contrast'
interface ThemeContext { theme: Readonly<Ref<ThemeName>>; setTheme(t: ThemeName): void }

const ThemeKey: InjectionKey<ThemeContext> = Symbol('acme-theme')

export function provideTheme(initial: ThemeName = 'light') {
  const theme = ref<ThemeName>(initial)
  watchEffect(() => document.documentElement.setAttribute('data-theme', theme.value))
  const ctx: ThemeContext = { theme: readonly(theme), setTheme: t => (theme.value = t) }
  provide(ThemeKey, ctx)
  return ctx
}

export function useTheme(): ThemeContext {
  const ctx = inject(ThemeKey)
  if (!ctx) throw new Error('useTheme() called without provideTheme() in an ancestor')
  return ctx
}

Using a typed InjectionKey makes inject() return the correct type [20], and exposing a readonly ref keeps mutations inside the provider, as the Vue documentation recommends [20].

Packaging the design system as a Vue plugin

// packages/ui/src/index.ts
import type { App, Plugin } from 'vue'
import AcmeButton from './components/AcmeButton.vue'
import AcmeTextField from './components/AcmeTextField.vue'
import './tokens.css'

export { AcmeButton, AcmeTextField }
export * from './theme/useTheme'

export const AcmeUI: Plugin<[{ prefix?: string }?]> = {
  install(app: App, options = {}) {
    const p = options.prefix ?? 'Acme'
    app.component(`${p}Button`, AcmeButton)
    app.component(`${p}TextField`, AcmeTextField)
  },
}

A plugin is an object with an install(app, options) method, typically used to register global components, provide app-wide values or add global properties [21]. Exporting each component individually as well lets consumers import only what they use, so bundlers can tree-shake the rest.

3. Monorepo architecture

Concepts

A monorepo stores several related projects (apps and shared packages) in one repository with well-defined relationships between them [22]. Benefits include atomic cross-package changes, a single dependency graph and shared tooling; costs include CI time and the need for task orchestration. pnpm workspaces link local packages using the workspace: protocol, which refuses to resolve to anything other than a local workspace package [23]. pnpm catalogs define dependency version ranges once in pnpm-workspace.yaml and reference them with the catalog: protocol, keeping versions consistent across packages [24]. Task runners such as Turborepo [25] or Nx [22] add dependency-aware task ordering and caching so only affected packages are rebuilt and retested.

4. Reusable composables

Concepts

A composable is a function that uses the Composition API to encapsulate and reuse stateful logic [27]. The official guide establishes several conventions: names start with use; inputs may be refs or getters, normalized with toValue() and tracked inside watchEffect(); the return value should be a plain object of refs so callers can destructure without losing reactivity; side effects must be cleaned up in onUnmounted(); and composables should be called synchronously within <script setup> or setup() [27]. Composables replace mixins, which the guide identifies as having unclear property sources, namespace collisions and implicit cross-mixin communication [27].

Example: a cancellable, typed data-fetching composable

// packages/composables/src/useAsyncData.ts
import { ref, shallowRef, toValue, watchEffect, onScopeDispose, type MaybeRefOrGetter, type Ref } from 'vue'

export interface AsyncState<T> {
  data: Ref<T | undefined>
  error: Ref<unknown>
  pending: Ref<boolean>
  refresh: () => Promise<void>
}

export function useAsyncData<T, A>(
  arg: MaybeRefOrGetter<A>,
  fetcher: (arg: A, signal: AbortSignal) => Promise<T>,
): AsyncState<T> {
  const data = shallowRef<T>()
  const error = ref<unknown>(null)
  const pending = ref(false)
  let controller: AbortController | undefined

  async function run(value: A) {
    controller?.abort()                     // cancel the stale request
    controller = new AbortController()
    const { signal } = controller
    pending.value = true
    error.value = null
    try {
      const result = await fetcher(value, signal)
      if (!signal.aborted) data.value = result
    } catch (e) {
      if (!signal.aborted) error.value = e
    } finally {
      if (!signal.aborted) pending.value = false
    }
  }

  // re-runs whenever a ref/getter read inside toValue() changes
  watchEffect(() => { void run(toValue(arg)) })
  onScopeDispose(() => controller?.abort())

  return { data, error, pending, refresh: () => run(toValue(arg)) }
}

The composable accepts a ref, getter or plain value, as the guide recommends [27]. It uses AbortController so that a superseded or unmounted request is cancelled rather than racing [28], and shallowRef for the payload because large API responses rarely need deep reactivity; the Vue performance guide recommends shallow reactivity for large immutable structures [29].

<script setup lang="ts">
import { useRoute } from 'vue-router'
import { useAsyncData } from '@acme/composables'
import { ordersApi } from '@acme/api-client'

const route = useRoute()
const { data: order, pending, error } = useAsyncData(
  () => route.params.id as string,
  (id, signal) => ordersApi.get(id, { signal }),
)
</script>

Composable design checklist

  • One responsibility per composable; compose small ones into larger ones.
  • Accept MaybeRefOrGetter inputs; return refs, never a reactive() object that loses reactivity on destructuring [27].
  • Register cleanup with onScopeDispose or onUnmounted so the composable is safe in components, stores and effectScope()s.
  • Do not touch window or document at module scope (it breaks SSR and tests); do so inside lifecycle hooks [27].

Show solution 
// useDebouncedRef.ts
import { readonly, ref, watch, onScopeDispose, toValue, type MaybeRefOrGetter } from 'vue'

export function useDebouncedRef<T>(source: MaybeRefOrGetter<T>, delayMs = 300) {
  const out = ref(toValue(source)) as { value: T }
  let timer: ReturnType<typeof setTimeout> | undefined
  watch(() => toValue(source), v => {
    clearTimeout(timer)
    timer = setTimeout(() => (out.value = v), delayMs)
  })
  onScopeDispose(() => clearTimeout(timer))
  return readonly(out)
}
// useDebouncedRef.spec.ts
import { describe, it, expect, vi } from 'vitest'
import { effectScope, nextTick, ref } from 'vue'
import { useDebouncedRef } from './useDebouncedRef'

describe('useDebouncedRef', () => {
  it('only updates after the delay', async () => {
    vi.useFakeTimers()
    const scope = effectScope()
    const q = ref('a')
    const d = scope.run(() => useDebouncedRef(q, 300))!
    q.value = 'ab'; await nextTick()
    q.value = 'abc'; await nextTick()
    vi.advanceTimersByTime(299)
    expect(d.value).toBe('a')
    vi.advanceTimersByTime(1)
    expect(d.value).toBe('abc')
    scope.stop()                   // triggers onScopeDispose cleanup
    vi.useRealTimers()
  })
})

5. Centralized state management

Concepts

The Vue guide notes that simple shared state can be a reactive object in a module, but recommends Pinia for large-scale production applications because it adds devtools integration, hot module replacement, plugins, SSR support and stronger conventions for team work [31]. Pinia supports two store styles: option stores (state, getters, actions) and setup stores, where refs become state, computeds become getters and functions become actions [5]. Destructuring a store directly breaks reactivity; storeToRefs() extracts state and getters as refs [5]. Stores can use other stores, and Pinia plugins can extend every store, for example for persistence or auditing [32].

A key enterprise rule is to separate server state (cached copies of backend data) from client state (UI preferences, the current user's session, wizard progress). Keeping only genuinely shared client state in global stores, and fetching server data close to where it is used, avoids a single huge store that every feature mutates.

Example: a feature store in setup syntax

// features/orders/store/useOrdersStore.ts
import { defineStore, acceptHMRUpdate } from 'pinia'
import { computed, ref } from 'vue'
import { ordersApi, type Order, type OrderStatus } from '@acme/api-client'

export const useOrdersStore = defineStore('orders', () => {
  const byId = ref<Record<string, Order>>({})
  const filter = ref<OrderStatus | 'all'>('all')
  const loading = ref(false)

  const list = computed(() => Object.values(byId.value))
  const visible = computed(() =>
    filter.value === 'all' ? list.value : list.value.filter(o => o.status === filter.value))

  async function load() {
    loading.value = true
    try {
      const orders = await ordersApi.list()
      byId.value = Object.fromEntries(orders.map(o => [o.id, o]))
    } finally {
      loading.value = false
    }
  }

  async function cancel(id: string) {
    const previous = byId.value[id]
    byId.value[id] = { ...previous, status: 'cancelled' }   // optimistic update
    try {
      await ordersApi.cancel(id)
    } catch (e) {
      byId.value[id] = previous                              // rollback
      throw e
    }
  }

  function $reset() { byId.value = {}; filter.value = 'all' }

  return { byId, filter, loading, list, visible, load, cancel, $reset }
})

if (import.meta.hot) import.meta.hot.accept(acceptHMRUpdate(useOrdersStore, import.meta.hot))

Setup stores do not get an automatic $reset(); Pinia's documentation shows defining one manually, as above [33].

<script setup lang="ts">
import { storeToRefs } from 'pinia'
import { useOrdersStore } from '../store/useOrdersStore'

const store = useOrdersStore()
const { visible, filter, loading } = storeToRefs(store)   // reactive refs
const { load, cancel } = store                             // actions can be destructured directly

</script>

6. API service layers

Concepts

Components should never call fetch with hand-built URLs. A dedicated service layer gives one place for base URLs, authentication headers, tenant headers, timeouts, retries, tracing headers and error normalization; it also makes components testable by mocking a typed module instead of the network. A useful standard for error responses is Problem Details for HTTP APIs (RFC 9457), which defines a JSON object with type, title, status, detail and instance members and the application/problem+json media type [35]. Configuration such as the API base URL comes from Vite environment variables; only variables prefixed with VITE_ are exposed to client code, and anything exposed this way ends up in the public bundle, so it must not contain secrets [36].

Example: the HTTP core

// packages/api-client/src/http.ts
import { getAccessToken, getTenantId } from '@acme/core/session'
import { currentTraceparent } from '@acme/core/telemetry'

export interface ProblemDetails {
  type?: string; title?: string; status: number; detail?: string; instance?: string
  [extension: string]: unknown
}

export class ApiError extends Error {
  constructor(public readonly problem: ProblemDetails, public readonly requestId?: string) {
    super(problem.title ?? `HTTP ${problem.status}`)
    this.name = 'ApiError'
  }
  get isUnauthorized() { return this.problem.status === 401 }
  get isForbidden()    { return this.problem.status === 403 }
  get isRetryable()    { return [408, 429, 502, 503, 504].includes(this.problem.status) }
}

const BASE_URL = import.meta.env.VITE_API_BASE_URL as string

export interface RequestOptions extends Omit<RequestInit, 'body'> {
  body?: unknown
  query?: Record<string, string | number | boolean | undefined>
  timeoutMs?: number
}

export async function http<T>(path: string, opts: RequestOptions = {}): Promise<T> {
  const url = new URL(path, BASE_URL)
  for (const [k, v] of Object.entries(opts.query ?? {})) if (v !== undefined) url.searchParams.set(k, String(v))

  const headers = new Headers(opts.headers)
  headers.set('Accept', 'application/json, application/problem+json')
  if (opts.body !== undefined) headers.set('Content-Type', 'application/json')
  const token = await getAccessToken()
  if (token) headers.set('Authorization', `Bearer ${token}`)
  const tenant = getTenantId()
  if (tenant) headers.set('X-Tenant-Id', tenant)
  const tp = currentTraceparent()
  if (tp) headers.set('traceparent', tp)

  const timeout = AbortSignal.timeout(opts.timeoutMs ?? 15_000)
  const signal = opts.signal ? AbortSignal.any([opts.signal, timeout]) : timeout

  const res = await fetch(url, {
    ...opts, headers, signal,
    body: opts.body === undefined ? undefined : JSON.stringify(opts.body),
    credentials: 'include',
  })

  if (!res.ok) {
    const isProblem = res.headers.get('Content-Type')?.includes('application/problem+json')
    const problem: ProblemDetails = isProblem ? await res.json() : { status: res.status, title: res.statusText }
    throw new ApiError(problem, res.headers.get('X-Request-Id') ?? undefined)
  }
  return res.status === 204 ? (undefined as T) : (res.json() as Promise<T>)
}

The traceparent header follows the W3C Trace Context format, which lets backend traces join the browser's trace (Section 12) [37]. AbortSignal.timeout() and AbortSignal.any() combine a caller's cancellation with a timeout [38].

Add retry with exponential backoff to http() for idempotent requests only, honoring a numeric Retry-After header on 429/503.

Show solution 
const IDEMPOTENT = new Set(['GET', 'HEAD', 'OPTIONS', 'PUT', 'DELETE'])

export async function httpWithRetry<T>(path: string, opts: RequestOptions = {}, maxAttempts = 3): Promise<T> {
  const method = (opts.method ?? 'GET').toUpperCase()
  for (let attempt = 1; ; attempt++) {
    try {
      return await http<T>(path, opts)
    } catch (e) {
      const retryable = e instanceof ApiError && e.isRetryable && IDEMPOTENT.has(method)
      if (!retryable || attempt >= maxAttempts || opts.signal?.aborted) throw e
      const retryAfter = Number((e.problem as any).retryAfterSeconds)   // or read the header in http()
      const backoff = Number.isFinite(retryAfter) ? retryAfter * 1000
        : Math.min(8000, 250 * 2 ** (attempt - 1)) * (0.5 + Math.random() / 2)  // jitter
      await new Promise(r => setTimeout(r, backoff))
    }
  }
}

Only methods defined as idempotent by HTTP semantics (RFC 9110, Section 9.2.2) are retried automatically, because repeating a non-idempotent POST could, for example, create a duplicate order [40]. RFC 9110 also defines Retry-After as either a date or a number of seconds [40]; to support it fully, have http() copy the header into the thrown error.

7. Feature-based folder organization

Concepts

Feature-based (or "vertical slice") organization puts everything a business capability needs (routes, views, components, stores, composables, API adapters, tests and translations) in one folder with a small public entry point. 8. Authentication and authorization

Concepts

Authentication establishes who the user is; authorization decides what they may do. In a browser application the second must always be enforced on the server: any check in Vue code can be bypassed by editing JavaScript or calling the API directly. OWASP ranks Broken Access Control as the top risk in its Top 10:2025 [44], and its Authorization Cheat Sheet requires deny-by-default and validating permissions on every request [45]. Client-side checks exist purely for user experience: hiding actions a user cannot perform and avoiding pointless navigation.

For sign-in, the current IETF Best Current Practice for OAuth 2.0 security (RFC 9700) says the implicit grant should not be used and that clients should use the authorization code grant with PKCE [46,47]. Many enterprises go further and use a Backend-for-Frontend (BFF) that performs the OAuth flow server-side and gives the browser only an HttpOnly, Secure, SameSite session cookie, so tokens are never readable by JavaScript. OWASP advises against storing session identifiers in localStorage because any XSS can read it [48]. Vue escapes text interpolation by default, but v-html, user-controlled URLs and user-provided templates bypass that protection [49].

Example: typed route meta and a global guard

// app/router-meta.d.ts

// app/guards.ts
import type { Router } from 'vue-router'
import { useSessionStore } from '@acme/core/session'

export function installAuthGuard(router: Router) {
  router.beforeEach(async (to) => {
    const session = useSessionStore()
    if (!session.initialized) await session.restore()          // e.g. GET /bff/session

    if (to.meta.requiresAuth && !session.isAuthenticated) {
      return { name: 'login', query: { redirect: to.fullPath } }
    }
    const required = to.matched.flatMap(r => r.meta.permissions ?? [])
    if (required.length && !required.every(p => session.can(p))) {
      return { name: 'forbidden' }
    }
    // returning nothing (undefined) confirms the navigation
  })
}

Augmenting the RouteMeta interface types the meta field, and to.matched lets a guard combine meta from parent and child routes [50]. Global beforeEach guards may be async and redirect by returning a route location, or cancel by returning false [6].

9. Multi-tenant applications

Concepts

A multi-tenant application serves several customer organizations from one deployment. OWASP's Multi-Tenant Security Cheat Sheet identifies cross-tenant data leakage as the central risk and calls for tenant context to be established from trusted sources (such as the authenticated session) and enforced at every layer, including caches and logs [52]. For the front end this has four consequences:

  1. Tenant resolution happens once at bootstrap (from subdomain, path segment or the session) and is treated as a hint; the server derives the authoritative tenant from the authenticated identity.
  2. Tenant configuration (branding, enabled features, locale defaults) is loaded before the app mounts.
  3. State isolation: when a user switches tenant, every store and cache must be cleared, otherwise tenant A's data can render under tenant B.
  4. Feature flags per tenant are applied in routing and UI, again with server enforcement.

Example: bootstrapping with tenant configuration

// apps/customer-portal/src/main.ts

}

10. Internationalization

Concepts

Vue I18n is the official-ecosystem internationalization plugin for Vue [7]. With legacy: false it runs in Composition API mode, exposing useI18n() which returns functions such as t (translation), d (date formatting) and n (number formatting) [55]. Locale messages can be lazy loaded per language and registered with setLocaleMessage(), so users download only the language they use [56]. Fallback locales define what is shown when a key is missing [57].

Locale identifiers follow BCP 47 language tags such as en-CA or fr-CA [58]. Dates, numbers, currencies, plural categories and list formats should come from the ECMAScript Intl API rather than hand-written code; Vue I18n's d and n delegate to Intl [59]. The document language must also be set on <html lang>, which WCAG 2.2 success criterion 3.1.1 (Language of Page) requires [16].

Example: setup with lazy loading

    en: { currency: { style: 'currency', currency: 'USD' } },
    fr: { currency: { style: 'currency', currency: 'EUR' } },
  },
  datetimeFormats: {
    en: { short: { year: 'numeric', month: 'short', day: 'numeric' } },
    fr: { short: { year: 'numeric', month: 'short', day: 'numeric' } },
  },
})

  const g = i18n.global
  if (!g.availableLocales.includes(locale)) {

  }
  g.locale.value = locale
  document.documentElement.lang = locale            // WCAG 3.1.1
  document.documentElement.dir = locale === 'ar' ? 'rtl' : 'ltr'
  await nextTick()
}

Enterprise practices

  • Keep messages per feature (features/orders/locales/*.json) and merge them at build time, so translations move with code.
  • Never concatenate translated fragments; use named interpolation so translators can reorder words.
  • Make the English messages file the TypeScript source of truth (MessageSchema above) to catch missing keys at compile time.
  • Store amounts as integer minor units plus an ISO 4217 currency code, and format at display time with Intl.NumberFormat [59].

11. Accessibility (WCAG)

Concepts

The Web Content Accessibility Guidelines (WCAG) 2.2 became a W3C Recommendation on 5 October 2023 and is organized under four principles: perceivable, operable, understandable and robust [16,61]. Most enterprise and public-sector procurement targets conformance level AA. WCAG 2.2 added criteria that particularly affect component libraries, including 2.4.11 Focus Not Obscured (Minimum), 2.5.7 Dragging Movements, 2.5.8 Target Size (Minimum) of 24 by 24 CSS pixels, and 3.3.8 Accessible Authentication (Minimum) [62].

Vue's accessibility guide gives SPA-specific advice: provide a skip link, manage focus on route change so that screen-reader users learn that the page changed, use semantic HTML and landmarks, and label form controls properly [63]. The WAI-ARIA Authoring Practices Guide (APG) gives keyboard and ARIA patterns for widgets such as dialogs, tabs, menus and comboboxes [14]; because a design system implements these patterns once, getting them right there fixes accessibility across every app.

12. Error handling standards

Concepts

Vue provides three layers for capturing errors. app.config.errorHandler is called for uncaught errors from component render functions, watchers, lifecycle hooks, event handlers and setup, receiving the error, the component instance and an information string [53]. onErrorCaptured() lets an ancestor component intercept errors from its descendants; returning false stops propagation [67]. Errors outside Vue (unhandled promise rejections, errors in plain modules) still need window-level listeners. In production builds Vue replaces long messages with short error codes, listed in the Production Error Code Reference [68].

An enterprise standard should define: (1) a typed error taxonomy; (2) what users see for each class (inline validation, toast, error page); (3) what is reported to telemetry; and (4) what must never be shown or logged (stack traces to users, personal data to logs) [69].

Example: error taxonomy

// packages/core/src/errors.ts
import { ApiError } from '@acme/api-client'

export type ErrorKind = 'validation' | 'auth' | 'forbidden' | 'not-found' | 'network' | 'server' | 'bug'

export function classify(e: unknown): ErrorKind {
  if (e instanceof ApiError) {
    const s = e.problem.status
    if (s === 400 || s === 422) return 'validation'
    if (s === 401) return 'auth'
    if (s === 403) return 'forbidden'
    if (s === 404) return 'not-found'
    return 'server'
  }
  if (e instanceof DOMException && (e.name === 'AbortError' || e.name === 'TimeoutError')) return 'network'
  if (e instanceof TypeError && /fetch/i.test(e.message)) return 'network'
  return 'bug'
}

export const isReportable = (k: ErrorKind) => k === 'server' || k === 'bug'

Example: global handler plugin

// packages/core/src/errorPlugin.ts
import type { App } from 'vue'
import type { Router } from 'vue-router'
import { classify, isReportable } from './errors'
import { logger } from './logger'
import { notify } from './notify'

export function installErrorHandling(app: App, router: Router) {
  app.config.errorHandler = (err, instance, info) => {
    const kind = classify(err)
    if (kind === 'auth') return void router.push({ name: 'login', query: { redirect: router.currentRoute.value.fullPath } })
    if (isReportable(kind)) logger.error('vue.unhandled', { info, component: instance?.$options.name ?? instance?.$options.__name }, err)
    notify.error(kind)                           // localized, non-technical message
  }

  window.addEventListener('unhandledrejection', ev => {
    const kind = classify(ev.reason)
    if (isReportable(kind)) logger.error('window.unhandledrejection', {}, ev.reason)
  })

  router.onError((err, to) => {
    // typically a failed lazy-loaded chunk after a new deployment
    if (/Failed to fetch dynamically imported module|Importing a module script failed/.test(String(err))) {
      window.location.assign(to.fullPath)        // hard reload fetches the new manifest
    } else logger.error('router.error', { to: to.fullPath }, err)
  })
}

router.onError() registers a handler for errors thrown during navigation, including failures to load lazy route components [70].

13. Logging and observability

Concepts

Observability means being able to understand a system's internal state from its outputs. OpenTelemetry (OTel) defines three primary signals: traces, metrics and logs [72]. A trace is a tree of spans representing the path of a request [73]. OpenTelemetry's JavaScript SDK supports browser instrumentation, including automatic instrumentation of document load, fetch and XMLHttpRequest, exporting over OTLP [74]. The W3C Trace Context specification defines the traceparent header that propagates trace identity across services, so a click in the browser and the resulting database query share one trace ID [37].

The OWASP Logging Cheat Sheet recommends structured, consistently formatted log events with timestamps and correlation identifiers, and lists data that must not be logged directly, such as session identifiers, access tokens, passwords and sensitive personal data [69].

Example: a structured logger with redaction

// packages/core/src/logger.ts
type Level = 'debug' | 'info' | 'warn' | 'error'
interface LogEvent {
  ts: string; level: Level; msg: string
  app: string; release: string; tenant?: string; route?: string; traceId?: string
  attrs?: Record<string, unknown>; err?: { name: string; message: string; stack?: string }
}

const REDACT = /pass(word)?|token|secret|authorization|cookie|ssn|card/i
const scrub = (o: Record<string, unknown> = {}) =>
  Object.fromEntries(Object.entries(o).map(([k, v]) => [k, REDACT.test(k) ? '[REDACTED]' : v]))

const buffer: LogEvent[] = []
const ctx = { app: 'admin-portal', release: import.meta.env.VITE_RELEASE ?? 'dev' } as Partial<LogEvent>
export const setLogContext = (c: Partial<LogEvent>) => Object.assign(ctx, c)

function emit(level: Level, msg: string, attrs?: Record<string, unknown>, e?: unknown) {
  const ev: LogEvent = {
    ts: new Date().toISOString(), level, msg, ...ctx, attrs: scrub(attrs) as LogEvent['attrs'],
    err: e instanceof Error ? { name: e.name, message: e.message, stack: e.stack } : undefined,
  } as LogEvent
  if (import.meta.env.DEV) console[level](msg, ev)
  if (level === 'warn' || level === 'error') { buffer.push(ev); if (buffer.length >= 20) flush() }
}

export function flush() {
  if (!buffer.length) return
  const body = JSON.stringify(buffer.splice(0))
  navigator.sendBeacon?.('/telemetry/logs', new Blob([body], { type: 'application/json' }))
}
addEventListener('visibilitychange', () => { if (document.visibilityState === 'hidden') flush() })

export const logger = {
  debug: (m: string, a?: Record<string, unknown>) => emit('debug', m, a),
  info:  (m: string, a?: Record<string, unknown>) => emit('info', m, a),
  warn:  (m: string, a?: Record<string, unknown>, e?: unknown) => emit('warn', m, a, e),
  error: (m: string, a?: Record<string, unknown>, e?: unknown) => emit('error', m, a, e),
}

navigator.sendBeacon() queues a small POST that the browser delivers even when the page is being unloaded, and flushing on visibilitychange to hidden is the recommended trigger [75].

Example: OpenTelemetry browser tracing

// packages/core/src/telemetry.ts
import { WebTracerProvider, BatchSpanProcessor } from '@opentelemetry/sdk-trace-web'
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-http'
import { ZoneContextManager } from '@opentelemetry/context-zone'
import { registerInstrumentations } from '@opentelemetry/instrumentation'
import { FetchInstrumentation } from '@opentelemetry/instrumentation-fetch'
import { DocumentLoadInstrumentation } from '@opentelemetry/instrumentation-document-load'
import { resourceFromAttributes } from '@opentelemetry/resources'
import { trace } from '@opentelemetry/api'

export function initTelemetry(opts: { service: string; release: string; apiOrigin: RegExp }) {
  const provider = new WebTracerProvider({
    resource: resourceFromAttributes({ 'service.name': opts.service, 'service.version': opts.release }),
    spanProcessors: [new BatchSpanProcessor(new OTLPTraceExporter({ url: '/telemetry/v1/traces' }))],
  })
  provider.register({ contextManager: new ZoneContextManager() })

  registerInstrumentations({
    instrumentations: [
      new DocumentLoadInstrumentation(),
      // inject traceparent only to our own API to avoid leaking headers / CORS failures
      new FetchInstrumentation({ propagateTraceHeaderCorsUrls: [opts.apiOrigin] }),
    ],
  })
}

export const tracer = trace.getTracer('acme-frontend')

The package names, WebTracerProvider, ZoneContextManager and the fetch/document-load instrumentations follow OpenTelemetry's browser getting-started guide [74]; API shapes evolve between SDK releases, so check the guide for the version you install. Exporting to a same-origin path (proxied to an OTel Collector) avoids CORS configuration and keeps collector credentials off the client.

14. Performance monitoring

Concepts

Google's Core Web Vitals measure user-perceived performance in the field: Largest Contentful Paint (LCP) for loading, Interaction to Next Paint (INP) for responsiveness and Cumulative Layout Shift (CLS) for visual stability. The "good" thresholds are LCP at or below 2.5 seconds, INP at or below 200 milliseconds and CLS at or below 0.1, assessed at the 75th percentile of page loads [76]. INP replaced First Input Delay as a Core Web Vital in March 2024 [77]. Lab tools such as Lighthouse catch regressions before release; real-user monitoring (RUM) shows what users actually experience.

For SPAs, INP is usually the hardest metric because heavy JavaScript runs on interaction. The Vue performance guide lists the main levers: route-level code splitting, avoiding unnecessary component abstractions in large lists, virtualizing long lists, keeping props stable so children do not re-render, v-once and v-memo, and reducing reactivity overhead for large immutable structures with shallowRef() and shallowReactive() [29].

Example: real-user monitoring with web-vitals

// packages/core/src/rum.ts
import { onCLS, onINP, onLCP, onTTFB, type Metric } from 'web-vitals'
import type { Router } from 'vue-router'

export function initRUM(router: Router, release: string) {
  const queue: object[] = []
  const send = (m: Metric) => queue.push({
    name: m.name, value: m.value, rating: m.rating, id: m.id,
    navigationType: m.navigationType,
    route: router.currentRoute.value.name, release,
  })
  onLCP(send); onINP(send); onCLS(send); onTTFB(send)

  addEventListener('visibilitychange', () => {
    if (document.visibilityState === 'hidden' && queue.length) {
      navigator.sendBeacon('/telemetry/vitals', JSON.stringify(queue.splice(0)))
    }
  })
}

The web-vitals library, maintained by the Chrome team, measures these metrics the same way Chrome reports them and exposes onLCP, onINP and onCLS callbacks with a rating field [78].

15. Dependency management

Concepts

A typical Vue application pulls in hundreds of transitive npm packages, which makes dependencies both a maintenance and a security concern; OWASP's Top 10:2025 includes Software Supply Chain Failures as a category [44]. Core practices are:

  • Commit the lockfile and install with a frozen lockfile in CI (npm ci or pnpm install --frozen-lockfile). npm ci fails if package.json and the lockfile disagree, and never writes to either [81].
  • One version of framework packages. Duplicated vue instances break reactivity and injection; use pnpm catalogs or overrides to enforce a single version [24].
  • Automated update PRs with Dependabot or Renovate, grouped by ecosystem (for example all @vue/* together) [82,83].
  • Vulnerability scanning with npm audit / pnpm audit in CI [84].
  • Understand semver ranges. Under Semantic Versioning a caret range (^3.5.0) accepts minor and patch updates, which are supposed to be backward compatible; versions below 1.0.0 make no stability promise [85].

Concepts

18. CI/CD pipelines

Concepts

Continuous integration runs the checks from Sections 15 to 17 on every change; continuous delivery keeps the main branch always releasable and automates deployment. DORA's research measures software delivery performance with a small set of metrics that began as the "four keys": deployment frequency, lead time for changes, change failure rate and time to restore service (since renamed failed deployment recovery time) [101]. Good pipelines for a Vue monorepo are affected-only (build and test only packages changed and their dependents, using the task runner's graph [25]), cached (dependency store and task outputs), parallel (shard end-to-end tests [102]) and reproducible (frozen lockfile, pinned Node version).

Example: GitHub Actions workflow

19. Release management

Concepts

In a monorepo, applications are deployed while shared packages are published with versions. Semantic Versioning defines the contract for published packages: MAJOR for incompatible API changes, MINOR for backward-compatible functionality and PATCH for backward-compatible bug fixes [85]. Changesets is a widely used tool for monorepos: contributors add a small markdown "changeset" declaring which packages changed and the bump type; at release time the tool computes versions (including dependents), updates changelogs and publishes [105]. Human-readable changelogs grouped as Added, Changed, Deprecated, Removed, Fixed and Security follow the Keep a Changelog convention [106].

For applications, safe release practices include feature flags to decouple deploy from release, progressive rollouts (canary or percentage-based), and an immediate rollback path (re-pointing to the previous immutable artifact).

20. Version compatibility

Concepts

Version compatibility concerns making several moving parts work together at a given time: the Vue core, its official libraries, build tools, Node.js, TypeScript and target browsers. Vue's release policy states that Vue follows Semantic Versioning, with a caveat that changes to TypeScript type definitions may occur in minor releases, and that minor releases are published roughly every three to six months, preceded by beta and release-candidate phases [108]. The same page warns that code compiled by a newer minor version of the compiler may not run on an older runtime, so vue and its compiler packages should be upgraded together [108]. Vite documents the browsers its default build targets and the Node.js versions it requires [4,109].

21. Backward compatibility

Concepts

Backward compatibility is the promise that code written against an older version of your API keeps working with a newer one. SemVer allows breaking changes only in a major release, and recommends deprecating functionality in a minor release before removing it, so users have time to migrate [85]. Vue itself demonstrates the practice: the 2-to-3 transition shipped a dedicated migration build with per-feature compatibility switches and deprecation warnings [114]. For an internal design system, the same techniques apply at smaller scale:

  • Deprecate, then remove. Keep old prop names or values working as aliases, log a development-only warning, document the replacement, remove in the next major.
  • Additive change by default. New optional props, new slots and new events are compatible; renaming or changing the type of existing ones is not.
  • Stable public surface. Only exports listed in package.json exports are public [110]; CSS class names and DOM structure should be documented as private unless stated otherwise.
  • Codemods for mechanical migrations, shipped with the major release.
  • API compatibility for the backend contract. The front end must tolerate unknown fields and new enum values, because an API may legitimately add them in a minor version.

Example: deprecating a prop value without breaking consumers

<!-- AcmeButton.vue (v4.3.0) -->
<script setup lang="ts">
import { computed } from 'vue'

type Variant = 'primary' | 'secondary' | 'destructive'
/** @deprecated use 'destructive'; will be removed in v5.0.0 */
type DeprecatedVariant = 'danger'

const props = withDefaults(defineProps<{ variant?: Variant | DeprecatedVariant }>(), { variant: 'primary' })

const resolvedVariant = computed<Variant>(() => {
  if (props.variant === 'danger') {
    if (import.meta.env.DEV) {
      console.warn('[AcmeButton] variant="danger" is deprecated; use variant="destructive". Removal in v5.0.0.')
    }
    return 'destructive'
  }
  return props.variant
})
</script>

Vite statically replaces import.meta.env.DEV, so the warning branch is removed from production bundles [36].
