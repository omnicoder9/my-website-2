1The question this article asks

Comparisons of web stacks usually proceed by inventory. Java has this, .NET has that, Node has the other; here is a table of features, here is a benchmark, here is a chart of survey popularity. The trouble with an inventory is that almost everything on it is true of almost everything on it. All seven of the stacks in this article route a URL to a function, deserialise a request body, wire objects together, talk to a database inside a transaction, render escaped output, and run on a machine that will eventually be asked to do more than it can. Feature parity arrived years ago. The differences that survive are not about what these systems can do.

A more useful question is temporal. Every application built on any of them has to settle the same list of decisions before it can serve a request correctly: which handler answers this path, whether the incoming JSON is the shape the handler expects, what happens when a value is absent, which object satisfies a dependency, where a transaction begins, how many queries a page runs, which version of a shared library is loaded, and what a unit of concurrency is. Nothing in that list is optional. What differs between stacks is the moment at which each decision becomes fixed, and the moment at which you are told you got it wrong — and those two moments are frequently not the same one.

So the organising question here is: when does the stack tell you? Not whether the mistake is possible, since every mistake on the list is possible everywhere, but where in the life of the software it surfaces. The compiler can refuse the program. A separate checking pass before deployment can refuse the build. The process can refuse to start. The first request down a path can fail. The thousandth concurrent request can fail while the first nine hundred and ninety-nine did not. Or nothing can happen at all, and a person finds out, usually from someone else.

This is an old idea with an old name. Binding time — the point in a program's life at which a name, a type, a value or an address becomes fixed — is one of the organising axes of programming-language design, and the theory of partial evaluation is in large part a theory of moving work from one binding time to an earlier one [1,2]. What is new is not the concept but the scale over which it now varies. A modern web stack is a language, a runtime, a framework, a package manager, a process model and a publishing schedule, and each of those six layers binds a different subset of the decisions, at a different moment, for reasons that were mostly settled before you arrived.

The six rungs above are the instrument used throughout this article. They are ordered by cost of discovery, and that ordering is the entire argument: a defect found by a compiler costs a keystroke, one found by a build costs a minute, one found at boot costs a rollback, one found under load costs an incident, and one that nothing detects costs whatever it costs. Jim Gray's distinction between faults that reproduce on demand and faults that appear only under production concurrency and timing is the same distinction seen from the other side: the lower rungs are where Bohrbugs live and the upper ones are where Heisenbugs are manufactured [3].

The ladder also names a practice rather than only a property. Failing fast — refusing to continue at the first sign that an assumption is broken, rather than carrying the damage forward — is the deliberate act of moving a discovery to an earlier rung, and it is a design decision with a literature of its own [4]. Every framework default discussed below is somebody's answer to it.

Two things follow that are worth saying before the detail begins. The first is that early binding is not free and is not always better. A decision fixed by the compiler is a decision that cannot be changed at run time, and the entire appeal of the dynamically typed web stacks — the reason PHP and Ruby and Python won the web they won — is that late binding buys a speed of change that early binding cannot [5]. The second is that most of these placements were not chosen by the people who live with them. They are inherited from a language designed in 1995, a servlet specification from 1997, a package manager written in a weekend in 2010, and a support policy published by a company that has never heard of your application.

What follows is an attempt to make the placements explicit. Eighteen decisions, seven stacks, one rung each: a hundred and twenty-six placements, collected in a ledger at the end. The evidence comes from two sources. Where a claim is about what a system does, it is cited to that system's own documentation or specification. Where a claim is about how much a placement costs, it comes from a lab of nine deterministic experiments, printed in full later in the article, whose output supplies every number quoted in the prose and every figure drawn from data.

2How seven stacks came to disagree

None of these systems was designed against the others. They were designed against the constraints of the year they appeared in, and each carries the shape of a problem that has since stopped existing.

The web's first programming model was a process per request, because that is what the Common Gateway Interface specified: the server starts a program, hands it the request in environment variables, reads a response from its standard output, and the program dies [6]. Everything expensive about that model — the fork, the interpreter start, the reconnection to the database — was a cost paid per request, and most of the history below is a record of stacks buying that cost back in different currencies.

It is also worth noting what the plumbing did and did not standardise. HTTP itself was re-specified in 2022 into a semantics document and a syntax document, so that every stack here shares one definition of what a request means [7,8]. The layer above it fragmented instead: Python has WSGI and ASGI, Ruby has Rack, PHP has a community-defined message interface, Java has a servlet specification, and the others have none at all [9,10]. Where that interface exists, the server and the framework can be replaced independently, which is a binding-time decision about deployment made twenty years before anyone deployed a container.

PHP began inside CGI. Rasmus Lerdorf's Personal Home Page tools were announced in 1995 as a set of C programs for form handling and page templating, and the language grew around the request as its unit of everything [11,12]. That decision has outlived every other thing about early PHP. Modern PHP is a just-in-time-compiled language with union types, enumerations, readonly classes and a mature package manager [13], but it still tears the world down at the end of each request, and as this article's ledger shows, that single structural choice earns it two of the board's rare rung-5 placements.

Java arrived the same year with the opposite instinct. Its white paper describes a language designed for reliability across a network of heterogeneous machines, with static typing and a virtual machine as the two load-bearing commitments [14]. The Servlet specification then made the server long-lived and the request a method call on a shared object, which is precisely the inversion of CGI: state persists by default and must be defended, rather than vanishing by default and needing to be reconstructed [15]. Enterprise Java's early answer to configuration and wiring was famously heavy, and Rod Johnson's 2002 critique and the Spring Framework that followed it moved the wiring decision into a container that walks the object graph at startup [16,17]. The language standardised its own additions along the way — generics arrived through the community process in 2004, and are the reason a modern Java signature carries the information a checker needs [18] — while its non-long-term releases now arrive every six months, the most recent being JDK 26 in March 2026 [19]. Spring Boot completed the arc by making that startup opinionated. The current generation is Spring Boot 4 on Spring Framework 7, released in November 2025 and built on Jakarta EE 11 [20,21,22].

Microsoft's line runs from Active Server Pages through the .NET Framework to the rewrite that mattered: .NET Core, announced in 2016 as a cross-platform, open-source runtime with a new web framework on top [23]. The rewrite is why the .NET column in this article looks the way it does — the stack had a second chance at its defaults, and used it to turn on nullable reference types, to make asynchrony a language feature the compiler rewrites rather than a library convention, and to standardise a configuration and options system that validates at start [24,25,26]. .NET 10, the current long-term support release, shipped in November 2025 with C# 14 [27].

Node.js is the youngest premise and the strictest one. Ryan Dahl's 2009 presentation argued that the dominant server model — a thread or process per connection, blocking on I/O — wasted memory on waiting, and proposed a single event loop with non-blocking I/O everywhere [28,29]. The argument had been made before in the research literature, and answered: SEDA proposed staged event-driven architecture for exactly these reasons [30], and both the counter-argument for threads and the observation that events and threads are dual descriptions of the same control flow were published before Node existed [31,32]. What Node added was not a new idea but a runtime in which the idea was not optional, and a package registry whose resolution policy would shape a decade of dependency management [33]. TypeScript arrived in 2012 to put a type system over the top, with the explicit constraint that its types are erased before execution [34,35]. Both the language TypeScript compiles to and the language Microsoft's other stack is written in are formal standards, which is rarer in this list than it sounds [36,37].

Python's web history is a series of interfaces rather than frameworks. PEP 333 defined WSGI in 2003 so that any framework could run under any server, which is the reason the Python web has never had a single dominant runtime story [38,39]; ASGI later did the same job for asynchronous applications [40]. Django appeared publicly in 2005 out of a newspaper's newsroom, and its defaults — an ORM, an admin, automatic escaping, a settings module evaluated at import — are the defaults of a stack built to publish content quickly [41]. The language itself has spent the last four years dismantling the assumption underneath its concurrency story: PEP 703 accepted the removal of the global interpreter lock in principle, and PEP 779 made the free-threaded build officially supported in Python 3.14, though still an opt-in binary [42,43,44]. FastAPI's contribution was to notice that the type annotations people were already writing could double as the wire schema, which moves the body-binding plate without adding a language feature [45].

Ruby was released in the same December as PHP's second version, designed around programmer enjoyment rather than any deployment model [46]. Rails made it a web language in 2004 by choosing convention over configuration and shipping an opinion about every layer at once [47]. Twenty years later the opinions are mostly unchanged and the runtime underneath has been rebuilt: YJIT brought a basic-block-versioning compiler into CRuby [48], and Ruby 4.0 shipped on Christmas Day 2025 with a second compiler, ZJIT, and an experimental isolation primitive [49].

Go is the only member of this list designed with the others in view. Rob Pike's account of its motivation is explicit that the language exists to solve engineering problems at scale — build times, dependency hygiene, the cost of concurrency — rather than to advance language theory [50]. It answers several of this article's eighteen questions by making them uninteresting: dependencies are compiled into the binary, wiring is ordinary code, and concurrency is cheap enough that the model needs no configuration [51,52]. It also spent its first decade refusing features on the grounds that they complicated the reading of code, which is why generics arrived only in 2022 and error handling is still an explicit value rather than a control-flow construct [53,54]. Go 1.27 arrived in August 2026 [55].

Two measurements are worth putting next to that history, because they do not agree with each other. Among developers surveyed by Stack Overflow in 2025, Node.js was the most used web technology and Python the fastest-growing language [56]. Among websites whose server-side language can be detected, PHP ran 70.2% of them in September 2026 [57,58]. Both numbers are correct. They measure different populations — what people are building now against what is currently deployed — and the gap between them is itself a binding-time fact: software outlives the enthusiasm that produced it, by a lot.

3The ladder, and the rule for placing things on it

The six rungs are defined by who does the detecting and what has already happened when they do.

Placing a stack on a rung requires a rule, or the exercise degenerates into advocacy. The rule used here is: the rung is where the mistake is caught by the stack as it is scaffolded — the official starter project, the default configuration, the tools the framework's own quick-start tells you to run — and not the best rung reachable by adding optional tooling. Under this rule TypeScript scores rung 4 on absence, because strict is on in the configuration the compiler generates, and Python scores rung 2, because Django's scaffold neither installs nor invokes a type checker. Every plate that would move under a different rule says so in its own text, and the ledger reports how much the whole board moves if the rule is relaxed.

The rule has an obvious objection: real teams add tools. A Python shop with mypy in a blocking CI job genuinely has rung-4 absence checking, and a Rails shop with Sorbet genuinely has rung-4 renaming. The rule survives the objection for two reasons. The tools are not free — they are a standing tax in configuration, annotation and false positives, which is why adoption is uneven — and, more importantly, the default is what the median deployment actually runs. The distribution of deployed PHP versions makes the point without argument: 28.7% of PHP sites were still on PHP 7 in September 2026, years after that branch stopped receiving security fixes, and 73.6% of those were on 7.4 alone [58,59]. Defaults are the observed behaviour of the population.

Each plate carries a gauge: a dial with seven needles, one per stack, pointing at the rung where that stack settles that decision. A tight fan means the ecosystems agree and the question has an answer everyone has converged on. A splayed fan means the same source file has a genuinely different meaning depending on which runtime executes it, and those are the plates worth arguing about.

The routing plate is the tightest fan on the board, and it is worth pausing on why. Every one of these frameworks builds a table mapping method and path to a function before it accepts a connection, and every one of them will refuse to start on a malformed or duplicated entry. Go's standard multiplexer panics at registration when two patterns conflict rather than silently preferring one [62]. This is what convergence looks like: a decision that everyone moved to rung 3 because the failure mode at rung 2 — a 404 in production for a path that plainly exists in the source — was intolerable to all of them.

The body-binding plate is where the fan opens. A declared type in TypeScript is a claim checked against the rest of the program, not against the network; the handbook is explicit that types are erased and have no run-time presence [35]. An interface describing a request body is therefore a statement about what the author believes, and the wire is under no obligation to agree. Java, C#, Python and Go each run a deserialiser that compares the incoming document to a declared structure and fails the request when they differ; PHP and Ruby run explicit validation layers that do the same job in a different idiom [66,77]. Adding a schema library to the TypeScript stack — zod is the common answer — moves this plate to rung 2 and closes the gap [64]. The point is not that TypeScript cannot do it. The point is that the scaffold does not, and that the language's own strength at rung 4 makes it unusually easy to believe otherwise.

How much does that gap actually cover? The first half of the lab's third experiment enumerates a payload space: four fields, each of which can be correct, of the wrong type, missing, null, or in range for its type but wrong in value. Of the 624 malformed payloads, 609 — 97.60% — are reachable by a declaration of type and presence alone. The remaining 15, 2.40%, satisfy every type and are still wrong: a quantity of minus four, a currency code of ZZZ, an identifier that is well-formed and belongs to somebody else. No type system of any strength rejects those. They have to be written down a second time as constraints, in every stack, and the frameworks that make that easy — Bean Validation annotations, pydantic fields, Laravel rules — are doing something a type checker structurally cannot.

The second half of that experiment is about a decision nobody thinks they are making. Once you have declared that a field is an integer, some component must decide what to do with the string "5", with "5abc", with the empty string, and with the boolean true. Running eleven realistic wire values against four declared types gives 44 cells, and resolving those cells under three documented policies — reject anything not already of the declared type, parse a token that is entirely the value, or coerce a leading numeric prefix and never fail — the three policies disagree about accept or reject on 30 of 44 cells, 68.2% of the grid. The weak policy accepts 40 of 44, and changes the datum it was handed in 31 of them, 70% of the whole grid.

The null result inside that experiment is the more interesting half: zero cells were accepted by more than one policy with different resulting values. The policies do not quietly compute different answers from the same bytes. They disagree about whether the request is valid at all. That is a better failure than the alternative, and it is also the reason PHP spent a major version cleaning up the comparison rules that made "foo" == 0 true, and why the language now offers a strict-types declaration that turns coercion into a TypeError [78,79]. Pydantic documents the same decision as an explicit conversion table with a strict mode beside it [65]. A declared type is not one decision. It is a decision plus a policy, and the policy belongs to the stack.

The escaping plate looks convergent and mostly is: Thymeleaf, Razor, JSX, Django templates, Blade and ERB all escape by default, and Rails has done so since 3.0 [73,74,75]. Dependency injection is the clearest case of a decision that has been deliberately moved down the ladder over twenty years. Spring's container walks the graph at startup and fails the context when a required bean is missing, which is rung 3 by construction [17]. ASP.NET Core validates the same graph on build in the development environment [80]. Symfony goes one rung further and compiles the container into a generated PHP class as a build artefact [81], while Laravel's container resolves on first use, which is rung 2 [84]. Go declines the entire mechanism: constructors are functions, wiring is a call in main, and a missing dependency is a compile error. That is the only rung-5 answer in the group, and it is bought by giving up the thing containers exist to provide — the ability to change the graph without changing the code that uses it.

Configuration is the same decision wearing different clothes, and the lab's eighth experiment prices it. Twenty-four configuration keys, each read on exactly one code path, with path probabilities spread log-uniformly from one request in three to one request in a hundred million — a hot route at one end, a failover branch at the other. Six of the keys are wrong. Binding and validating the whole configuration object at process start finds all six before a single request is served. Reading each key at its point of use finds one of six from a smoke test over the three hottest routes, and five of six within thirty days of traffic at 120 requests per second. The median wrong key waits 25,885 requests to be read for the first time; the worst waits a hundred million, which is ten days at that rate.

Ten days is the interesting number, because it is longer than a deployment window and shorter than a quarter. It is exactly the interval in which a change has been declared successful, the person who made it has moved on, and the relationship between the incident and its cause has become expensive to reconstruct. The twelve-factor formulation of configuration in the environment does not say when to read it [83]; the frameworks that bind eagerly into a typed object are adding a rung the pattern itself does not require [26,63].

Absence is the plate that provokes the most argument and has the cleanest arithmetic. Tony Hoare's description of the null reference as a billion-dollar mistake is usually quoted for the number; the useful part is his account of why he did it, which was that it was easy to implement [68]. C# and TypeScript both now default their scaffolds to checking it — nullable reference types and strictNullChecks are on in new projects [24,69] — and Spring Framework 7 has adopted JSpecify annotations so that the same analysis is available to Java code that opts in [21,70]. The other four discover absence when a request finds it.

The lab's ninth experiment measures what that discovery looks like. A chain of five optional links, present with probabilities from 0.999 down to 0.900, has 32 reachable states. The path where everything is present — the one the test exercises — accounts for 83.29% of requests, so 16.71% of traffic takes a path the test suite has never run. At 120 requests per second, 22 of the 32 states are more likely than not to have occurred within the first hour, 31 within a month, and the rarest state first appears after about 193 days. A type system that makes absence explicit asks five questions once, before the program runs: one per link, linear in the length of the chain. A runtime that discovers absence asks 31 questions one at a time, in an order chosen by traffic. Linear against exponential is the whole difference, and it is a difference in when, not in whether.

Renaming closes the group. Whether the set of call sites of a function is computable is the oldest question in this comparison and the one where the theoretical position is least controversial: a static type discipline is exactly a mechanism for proving properties of a program before running it, and the properties it proves include this one [89,90]. Java, C# and Go compile the question away. TypeScript answers it in a separate pass, now substantially faster since the compiler's port to Go [91]. Python, PHP and Ruby leave a residue that no checker can fully eliminate, because getattr, __call and send construct call sites from strings at run time — and that residue is the same mechanism that makes their frameworks' most-loved conveniences possible. Rails finds a model's attributes by asking the database at boot; Django builds forms from models the same way. You cannot have that and also have the rename check. Ousterhout's 1998 argument for scripting languages was precisely that the trade is worth making for a large class of programs [5], and the deployed web is not obviously evidence against him.

The first plate is unusual because it has no detector at all. The concurrency model is a premise rather than an event: nothing in the stack ever tells you what it is, and the failure mode is a design that assumed a different one. Node and Go fix the answer in the language — one loop that must never be blocked [92,97], or goroutines cheap enough that a request can have several [94]. Java, Python, PHP and Ruby leave it to a deployment decision: platform threads or virtual threads [93,111], WSGI workers or an ASGI event loop [39,40,96], process-per-request under FPM or a resident worker under FrankenPHP [101,110], Puma processes crossed with Puma threads [95]. The same source file is a different server under two of those settings, and the setting lives in a file that the person writing the handler frequently has never opened.

It is worth naming what the models cost when they are wrong in the other direction. Node's answer to CPU-bound work is a worker thread pool with an explicit message boundary, which is a real answer and also an admission that the single-loop premise does not cover every handler [112]. The JVM's flight recorder emits an event whenever a virtual thread fails to release its carrier, which is the closest thing in this comparison to a purpose-built detector for a rung-1 failure [113]. Neither exists in the scaffold; both have to be reached for.

The lab's second experiment runs one arrival trace through four of these models. In the first scenario, one handler in three hundred does 90 ms of uninterruptible CPU work — a PDF, an image resize, a regex over a large document — while every other request does 0.8 ms of CPU either side of a 6 ms database wait. Total demand is 57.9% of one core, so nothing is overloaded. On a single event loop, 32 slow requests push 1,156 innocent ones past 50 ms: 14.51% of the light traffic, from 0.4% of the requests. Under M:N scheduling over four carriers the same trace pushes none of them past 50 ms. The p99 differs by 23.71x.

The second scenario reverses the polarity and is the reason thread-per-request did not simply win. No handler is slow; one dependency is, at 300 ms, under 180 requests per second. Offered concurrency is 54.1 requests in flight at all times, and it is entirely waiting. The event loop and the M:N scheduler carry it on four carriers because waiting holds nothing. Thread-per-request needs 55 threads to stand still and has 64, so it copes. Process-per-request with 16 workers does not: the queue never drains and the last request in the trace waits 80.0 seconds. This is the arithmetic that made the C10K problem a problem [29] and the reason the event-loop argument was persuasive in 2009 [28], and it is also why the JVM spent a decade building virtual threads — to keep the blocking programming model while removing its cost [93].

The detector plate for that failure, D10, sits at rung 1 nearly everywhere, but the instruments differ in quality. .NET publishes thread-pool starvation counters and a documented diagnostic procedure [98]. The JVM records a flight-recorder event when a virtual thread cannot release its carrier, and JDK 24 removed the largest cause of that by letting virtual threads block inside synchronized without pinning [99]. Python's asyncio debug mode logs callbacks that run too long [100]. Node's answer is event-loop lag, measured by the application. PHP scores rung 0 on this plate and wins it: with a process per request there is no shared runtime to block, which is not a detector but the absence of the question.

That absence recurs on the next two plates, and it is the strongest structural result in this article. Because a PHP request begins with a fresh interpreter state and ends by destroying it [102], cross-request shared mutable state is not a bug you can write. Every other stack here keeps objects alive between requests by default, which is the whole point of a long-lived server and also the origin of the worst class of defect in this article: one user's data rendered into another user's page. Go's race detector catches the memory-model violations under the test command the scaffold already writes [103,104]; Ruby's Ractors offer isolation for code written to use them [105]; everywhere else the detector is an incident.

Reclamation is the same story told in latency. The lab's fifth experiment runs 60,000 requests at 200 rps over eight servers with gamma-distributed service times, once with a per-request arena and once against a tracing collector at three allocation rates. The arena spends 5.2% of the median request on teardown and has no global pause: its p99.9 of 25.86 ms is entirely service-time variance and queueing. At 200 MB/s the collector is invisible. At 3,200 MB/s the young collection runs every 10 ms and a major collection every 21 seconds; the median moves by about a millisecond, but p99.9 reaches 59.43 ms — 33.57 ms on top of the same distribution — and 79.4% of requests are extended by a pause they did not cause. Dean and Barroso's account of tail latency at scale is the canonical statement of why that matters more than the median it did not move [106].

Startup time is the last plate in the group and the one most often dismissed as a benchmark curiosity. The lab's sixth experiment prices it as an operational bill. Traffic steps from 400 to 1,600 requests per second; instances serve 100 rps each; the autoscaler wakes every ten seconds and targets 70% utilisation; clients abandon after three seconds in queue. Everything is held constant except how long a new instance takes to accept its first request. At 0.05, 0.30 and 1.00 seconds, nothing is dropped. At 3.00 seconds, 1,423 requests are dropped, 0.37% of the step. At 8.00 seconds, 6,566 are dropped, 1.71%, and the system takes 10.3 seconds to settle rather than 0.1.

The right-hand column of that table is the one to take away. To absorb the same step with zero loss, the 3-second stack needs 3 permanently idle instances and the 8-second stack needs 6, while the fast starters need none. That is not a latency number; it is a standing capacity purchase, made in machines, to cover the interval during which the platform cannot respond to reality. It is also why so much recent JVM and .NET engineering aims at this rung: ahead-of-time class loading and linking [107] and native ahead-of-time compilation [108] both move work from the first request to the build. PHP reaches the same place from the other direction with opcache preloading [109], and a Go binary is simply warm when it starts [55].

Lazy loading is the purest rung-0 decision in this article. When an object-relational mapper resolves an association on attribute access, the number of queries a page runs is determined by the shape of the data at run time, and no artefact of the development process objects. The lab's fourth experiment puts numbers on it with a 0.75 ms per-query cost: at 2 children the lazy version takes 2.25 ms against 0.75 for a join; at 200 children it takes 150.75 ms against 1.15 ms, a factor of 131; a 200 ms budget is exhausted at 265 children.

The important column is not the ratio but the fixture. A test that seeds two children renders in 2.25 ms and passes. Production, holding two hundred, renders in 150.75 ms and also passes — the output is byte-identical, which is precisely why every assertion still holds. Failing tests: zero. Type errors: zero. Warnings: zero. The 67-fold difference between the environment that runs the assertions and the environment that has the data is visible in exactly one place, a query log, and only to somebody already looking at it.

The mappers know this. Hibernate documents fetch strategies at length and warns about the exception thrown when a lazy association is touched outside its session [114]. EF Core makes lazy loading opt-in, requiring proxies to be installed explicitly, and throws rather than silently evaluating a query on the client [115,124]. Django documents the optimisation but leaves the default lazy [116]. Laravel and Rails both ship an opt-in strict mode — preventLazyLoading and strict_loading — which is an admission in code that the default is a rung-0 answer [117,118]. Go scores rung 5 here by not offering the feature: you write the query, so you cannot write a query you did not write [67].

Transaction boundaries produce the single most surprising placement on the board. Spring's declarative transactions are applied by a proxy around the bean, so a call from one method of an object to another method of the same object does not pass through the proxy and does not participate in the transaction. This is documented in Spring's own reference as a limitation of the proxy mode [119], it has been documented for two decades, and it still produces half-written aggregates in production, because nothing detects it: not the compiler, not the container, not the test that calls the outer method with a working database underneath. That is rung 0 in a stack that otherwise binds earlier than almost everything else here. Django's ATOMIC_REQUESTS makes the boundary the request itself, which is a rung-3 answer with its own hazards [120]; Rails and Laravel use explicit blocks [121]; Go passes a transaction handle as an argument, so the boundary is visible in every signature that participates in it [67]. Bertrand Meyer's argument for making obligations explicit in the interface rather than the documentation applies directly [122].

The mapper's other job — tracking which loaded objects are dirty and writing them back in one unit of work — is the pattern the whole layer is built on, and it is worth remembering that the catalogue describing it predates every framework in this article [125]. Nothing in the twenty-three years since has changed the arithmetic of a round trip; what changed is how many of them a single attribute access can produce without saying so.

The connection-pool plate is perfectly flat: seven stacks, one rung, no detector before load. The arithmetic is not hard — workers times pool size must not exceed what the database will accept, and Little's law tells you how much concurrency the offered load actually requires [123] — and essentially no scaffold does it for you. It is the clearest case in this article of a decision that could be made at rung 4 by anybody willing to multiply three integers, and is instead made at rung 1 by everybody.

evidence [57,59,131,132,133,134,135,136,137,138]

There are exactly three answers to the question of what a package manager should do when two dependants require different versions of the same library, and all seven stacks use one of them. Refuse to install: pip, Composer and Bundler search for a single version satisfying every constraint and fail loudly when none exists [126,127,139]. Mediate: Maven resolves by the shortest path to the root and says nothing about the constraints it just violated [85], while NuGet mediates but emits NU1605 when the resolution downgrades a package [128]. Duplicate: npm nests a private copy under each dependant so that both get what they asked for [33]. Go sits outside the trichotomy by removing upper bounds from the language of constraints altogether — minimal version selection takes the maximum version anyone requires, so a conflict is not expressible [51,129].

The lab's first experiment runs the same synthetic dependency graphs through all three policies while sweeping the share of declarations that are narrow — a tilde range or a pinned version — against open-ended ranges that any newer release satisfies. The first row is the one that matters. With every declaration open-ended, no graph is infeasible and the refusing policy refuses nothing, 0.00%; yet mediation by depth still ships 61.38% of applications running a library at a version older than one of its own dependants asked for, because the rule consults the shape of the graph rather than the constraints written in it. At a 10% narrow share the three policies answer the same graphs differently: 20.95% refused at install, 69.20% silently violated, and 20.95% resolved by installing 1.23 copies of the library on average.

That the duplicating policy needs a second copy exactly as often as the refusing policy refuses is true by construction rather than by measurement — a second copy is required precisely when no single version satisfies everyone — and the identity is the point. It is the same conflict in all three columns. What differs is whether it is raised as a question at install time, answered silently by a rule that does not read the constraints, or dissolved by making two versions coexist, which works until code compares identities across the copies and the failure arrives as a type mismatch between two classes with the same name.

The final plate is the only unanimous row on the board. Nothing in any of these seven stacks will tell you that the runtime you are on stops receiving security patches in fourteen months. The dates are public, published years ahead, and arrive whether or not anybody has touched the software. Java's long-term support releases land every two years and carry free updates for about three [131,140]. .NET ships every November, with long-term support releases supported for three years and standard-term releases for two [132]. Node.js is changing its schedule with version 27 in October 2026: one release a year, every release becoming long-term support, windows of about thirty months [133,141]. Python releases annually with five years of support [134,142]. PHP gives two years of active support and two more of security fixes [59]. Ruby branches last about three years [135]. Go supports the two most recent releases, which is about a year [137]. On top of the runtime sits the framework's own clock: Spring Boot ships a minor release every six months with twelve months of open-source support [138,143], Rails gives a year of bug fixes and two of security [136], Django designates every third release long-term with three years [144].

Two practical notes about that list. The framework windows are the ones people misremember: Spring's production line is documented branch by branch with dates attached [145], and Laravel publishes its own per-version support table alongside its release notes [146]. And because none of this is in any stack, an entire small industry exists to aggregate it — endoflife.date began as a spreadsheet of exactly the dates nothing else would tell you [147].

The lab's seventh experiment simulates a team that upgrades as late as each published window allows, over the ten years from September 2026. Seven runtimes produce 24 forced moves between them; five frameworks produce 23. Taken as deployed pairs, the framework's window closes before the runtime's in four of seven cases, so the framework sets the clock. A Java service on the current long-term support release with Spring Boot must move nine times in the decade, because the framework's twelve-month window binds long before the runtime's thirty-six. A .NET service on long-term support with ASP.NET Core must move three times, because the framework and the runtime are the same release train and share one date. That is a factor of three in forced upgrade events between two stacks usually described as equivalent enterprise choices, and it has nothing to do with either one's technical merit.

It is worth being clear about what this experiment is and is not. It measures publishing schedules, not effort: a Spring Boot minor upgrade is usually smaller than a .NET major, and both are smaller than the Python 2 to 3 transition that shaped a generation's expectations. What it measures accurately is the number of occasions on which somebody must be paid to touch working software for reasons external to it. And the deployed population suggests those occasions are widely declined: more than a quarter of PHP sites run a branch that stopped receiving security fixes years ago [58], which is the same phenomenon that made CVE-2024-4577 valuable to attackers long after it was patched [148].

Nine experiments, standard library only, one seed, no network and no external data. They are models rather than measurements of real systems: the cost constants — a 0.75 ms query, a 45 ms major collection, a 300 ms dependency — are stated inputs, not observations, and the results are about the shape of the relationship rather than the magnitude for any particular deployment. What the measurement supports is the narrower claim now in the text — that the arena's tail does not move when the code allocates more, and the collector's does.

Four results come out of the table that are not obvious from any individual plate.

The board is bottom-heavy. 74 of the 126 placements sit at rung 2 or below — first touch, under load, or nothing — against 22 at rung 4 or 5. The great majority of what a web stack decides for you is decided at run time and discovered by traffic. Every stack in this comparison, including the most statically typed, spends most of its rows in the lower half of the ladder, because most of these decisions are about the world rather than about the program: what arrives on the wire, how much data an account holds, how many requests are in flight, what somebody else published.

The spread within a plate is larger than the spread between stacks. The mean rung across all seven stacks is 2.25, and the difference between the earliest-binding stack (Go + net/http) and the latest (Java + Spring Boot) is 1.56 of a rung. The difference between the earliest-binding plate and the latest is 3.86 rungs. Which decision you are talking about matters several times more than which stack you are in, which is a direct argument against the way these comparisons are usually conducted.

Nobody is uniformly early, and the order is not the one the reputations predict. Go binds earliest by a distance, at a mean rung of 3.33 with eight rung-5 placements, and still sits at rung 1 on memory, on blocking and on the connection pool. Then .NET at 2.39, PHP at 2.17, Node and Python at 2.06, Rails at 2.00 — and Java with Spring last, at 1.78. That result deserves an explanation rather than a headline, because Java is the most statically typed stack in the comparison and it finishes bottom of a table about binding time.

The explanation is that its three rung-0 placements are all in the same place: the framework and the tooling, not the language. Maven mediates version conflicts silently, Spring applies transaction boundaries through a proxy that a self-invocation bypasses, and nothing reports a support window. Java's language rungs are excellent — it shares the top score on renaming — and its machine rungs are ordinary, because a long-lived multi-threaded server with a tracing collector has the failure modes of a long-lived multi-threaded server with a tracing collector, whatever the type system says. PHP finishes above it largely on the strength of two structural rung-5 placements that its type system had nothing to do with. If there is one lesson in the column ordering, it is that the type-system argument, which is the argument everybody has, decides four of the eighteen rows.

Two smaller shape facts are worth recording. .NET and Go each carry a single rung-0 placement, against three apiece for Java, Node and PHP; and PHP binds latest of all seven on the wiring group, at a mean of 2.00, while holding the board's only rung-5 answers on cross-request state and on reclamation. A stack can be late everywhere it assembles itself and early everywhere it executes.

The rung-0 cells cluster. There are 15 placements at rung 0, and they are not scattered: they concentrate in lazy loading, dependency mediation, ambient transaction boundaries and support windows. Three of those four are decisions made by a layer that exists to save you from thinking about something — the mapper, the resolver, the proxy — and the fourth is not made by software at all. Convenience that removes a decision from view does not remove the decision; it moves it to the rung where nothing is watching.

The last observation is the one worth carrying away from the table. Frameworks are, almost by definition, machines for moving decisions out of the application and into a default. That is why they are worth having, and the plates where every stack converges — routing at boot, escaping at render — are cases where the default is simply correct and the industry has stopped arguing. But every default also chooses a rung, and a default that hides a decision without deciding it well has bought convenience with discovery time. The question to ask of any framework feature is not whether it is clever. It is which rung it puts the mistake on.

11What the ledger does not decide

This article has deliberately measured one axis, and a stack choice is not made on one axis. Four things it does not capture are worth naming, because they routinely dominate the decision and should.

It does not measure the size of the labour market. The number of people who can maintain a Spring or Rails or Laravel application, at what price, in the city where the work is, is usually the largest single input into a stack choice and it is nowhere in the ledger. Nor does the ledger measure ecosystem depth: the existence of a maintained client for the payment processor you have already signed with is worth more than a rung. The registries differ by more than an order of magnitude in size and by more than that in metadata hygiene [149,150], and .NET alone reports over 478,000 packages on NuGet [27].

It does not measure whether any of this is where the effort should go. Knuth's warning about optimising the wrong 97% applies with equal force to rigour: moving a plate down a rung costs engineering time, and spending it on the plate that does not fail is the same error in a different currency [151]. The same caution applies to the volume argument. Rails is routinely described as a stack that does not scale, and one Rails deployment handled a reported peak of 117 million requests per minute on its application servers during a single shopping weekend in 2025 [152]. Whatever these ledger rows measure, it is not a ceiling.

It does not measure throughput or efficiency. Nothing here is a benchmark, and the published cross-framework benchmarks measure a workload that resembles almost nobody's application, as their own methodology page is careful to say [153]. Binding time and speed are close to orthogonal: PHP binds late and starts instantly, Java binds early and starts slowly, Go does both early. If throughput is the binding constraint, measure throughput.

Nor does it credit the tooling that has arrived since these stacks were designed, which is where most of the last decade's movement has been. Node now ships a test runner in the runtime [154]; Django 6.0 ships Content Security Policy support in the framework rather than in a plugin [155]; PHP 8.5 continues an annual cadence of language work that would have been unrecognisable to anyone who last read the language in 2010 [156]. Rungs move, and they mostly move downward.

It does not measure operational familiarity, which is the most underrated input of all. A team that has run one of these stacks in production for five years knows where its rung-1 failures come from, has the dashboards for them, and will detect a class of problem in minutes that a more rigorous but unfamiliar stack would surface as a mystery. Every rung in this article can be moved down by engineering effort, and the effort is much cheaper on the stack you already understand. Adding a schema library, turning on a strict-loading flag, putting a type checker in a blocking CI job, validating configuration at start: each of those is a day's work and moves a real plate.

And it does not measure the cost of early binding, which is real. Fixing a decision at rung 5 means it cannot be changed without a rebuild, and a great deal of what the dynamic stacks are loved for is the ability to change behaviour at run time — to reopen a class, to generate a method from a database column, to swap an implementation from a configuration file. Brooks's distinction between essential and accidental complexity applies to the ladder itself: moving a decision to an earlier rung removes accidental risk, but if the decision is genuinely not knowable until run time, an earlier rung just produces a program that lies [157,158].

What the ledger is good for is narrower and, I think, still useful. It converts a taste argument into a list of specific, checkable questions about a specific application. Does this system take untrusted input from a party who will send malformed documents, and does the stack refuse them at the boundary or in the handler? Does it have a hot path where one slow request can hold a shared runtime? Does it keep anything in memory between requests, and if so, what detects a leak across them? Does its mapper decide query counts, and is strict mode on? Does the transaction boundary appear in the signature or in an annotation? What is the shortest support window in the deployed pair, and who has the calendar entry for it?

Those are answerable in an afternoon for any of the seven, and the answers do more work than another round of the argument about types. The stacks compared here have all been in production for at least a decade, all of them run systems at scales that would embarrass most of the criticism aimed at them, and none of them is going to be retired by an article. What changes outcomes is not choosing the rigorous stack. It is knowing, for the decisions your application actually makes, which rung you are standing on — and moving the two or three that matter down one step, deliberately, before traffic does it for you.
