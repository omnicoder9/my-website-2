HTML DOM Construction

How a browser turns markup into a live tree of objects: the node tree and its node types; how the parser's output becomes the DOM; the document lifecycle, readyState and DOMContentLoaded; how scripts pause and reshape construction; how the DOM differs from the render tree; building and changing the tree with DOM APIs, innerHTML, templates and shadow DOM; and how to inspect the result. Grounded in the WHATWG DOM and HTML standards, the W3C CSS specifications, MDN and the Chrome and web.dev documentation.

Updated 17 November 2026109 references (Vancouver style)Includes exercises, trivia, live demos, a DOM construction lab and a playground

Earlier parts of this series described HTML as text: elements, attributes and document structure, semantics and forms. A browser never works with that text directly. It parses it into the Document Object Model (DOM), a tree of objects that scripts, style sheets, assistive technology and the browser's own rendering engine all read from.1,2 The companion article on HTML parsing algorithms explains how the tokenizer and tree builder decide what to create. This article is about what they create: the shape of the tree, the moments at which it exists and changes, and the many other ways nodes get into it.

Section 1 introduces the DOM and the pipeline from bytes to tree. Section 2 describes the node tree and its node types. Section 3 follows parser output into the DOM, and section 4 covers the document lifecycle. Section 5 is about scripts, section 6 about the gap between the DOM and what you see on screen, and sections 7 and 8 about building trees from script and from markup strings, including templates and shadow DOM. Section 9 shows how to inspect the tree, and sections 10 to 15 hold a worked example, exercises, trivia, a lab, a playground and a quick reference.

Two documents in one pageView Source shows the bytes the server sent. The Elements panel of developer tools shows the DOM, which can differ a great deal: Chrome's documentation puts it as "HTML represents initial page content and the DOM represents active, current page content".3 Keep the two apart throughout this article.

1Introduction

1.1 What the DOM is

The DOM Standard defines a platform-neutral model for events, aborting activities and node trees. In the DOM, a document is represented as a tree of nodes; each node is an object with properties and methods, and the same tree is exposed to every language that implements the bindings, in practice JavaScript.1,4 Three things are easy to confuse:

  • The model. The abstract tree: which nodes exist, how they are ordered and what each one's node document, parent and children are.4
  • The API. The interfaces scripts use to read and change the model: Node, Element, Document, querySelector(), append() and so on, written in Web IDL.5–7
  • The HTML layer. The HTML Standard adds element-specific interfaces such as HTMLInputElement, the HTML parser and serializer, and document features such as document.readyState and document.body.8–10

The DOM is not a copy of the markup. Tags that were omitted in the source exist as elements, misnested tags are rearranged, whitespace becomes text nodes, and once scripts run, the tree may bear little resemblance to the file the server sent.3,11,12

1.3 A short history

The W3C published the first DOM specification, Document Object Model Level 1, as a Recommendation on 1 October 1998, to give the competing scripting models of the late-1990s browsers a common, language-neutral API.16 Level 2 Core (13 November 2000) added namespaces and the event model, and Level 3 Core followed on 7 April 2004.17,18 The WHATWG then began a living DOM Standard; a snapshot of it became the W3C's DOM4 Recommendation on 19 November 2015.1,19 Since a memorandum of understanding signed on 28 May 2019, the W3C and the WHATWG have agreed that "HTML and DOM shall be developed principally in the WHATWG", with the W3C endorsing WHATWG Review Drafts instead of publishing its own versions.20

1.4 From bytes to a tree

Google's web.dev guide to the critical rendering path summarises DOM construction as "Bytes → characters → tokens → nodes → object model".21 The HTML Standard describes the same pipeline in more precise terms: the network delivers a byte stream; the encoding sniffing algorithm and a decoder turn it into an input stream of code points; the tokenizer emits tokens; and the tree construction stage turns tokens into nodes in a Document.22 The two halves of that pipeline are separate subjects. Tokenizing and the tree-construction rules (insertion modes, the stack of open elements, the adoption agency algorithm) are covered in the parsing article; this article picks up at the moment a node is inserted.

2.2 The interface hierarchy


Node interfaces form an inheritance chain. Every node is an EventTarget, so events can be dispatched to it; Node adds tree navigation and mutation; Element adds attributes, selectors and shadow roots; and HTML adds HTMLElement with one subclass per element, such as HTMLAnchorElement.5,6,8,25 An element whose name the parser does not recognise becomes an HTMLUnknownElement, unless its name contains a hyphen, in which case it is a candidate custom element and gets plain HTMLElement until it is defined.8,26





2.3 Tree relationships and structure rules


A node tree is an ordered tree: every node except the root has exactly one parent, and its children are ordered. The DOM Standard defines the familiar terms in terms of that structure (parent, child, sibling, ancestor, descendant, inclusive ancestor, root, first child, following, preceding) and defines tree order as preorder, depth-first traversal.27 On a Node these relationships appear as parentNode, childNodes, firstChild, lastChild, previousSibling and nextSibling; on elements, children, firstElementChild and friends skip text and comment nodes.5,28


Not every arrangement is allowed. A Document can have at most one DocumentType child and at most one element child (the document element), with the doctype before the element; comments and processing instructions may appear around them; text nodes cannot be children of a document at all. Attr nodes are never children: an element's attributes hang off its attribute list, outside the tree.29,30 Insertion methods enforce these rules by throwing a HierarchyRequestError DOMException, for example when you try to append a second element to document or insert a node into its own descendant.31

// HierarchyRequestError: a document can have only one element child

2.4 What the parser adds: implied elements and whitespace


The DOM of even a tiny document contains more nodes than its markup suggests. The HTML Standard lets authors omit the start and end tags of html, head, body and tbody (among others), and the tree builder creates those elements anyway.11,12 Whitespace between tags becomes text nodes, because, as MDN puts it, "HTML preserves all whitespace text content as you wrote them in the source code"; the exceptions are whitespace before head and some whitespace around body that the tree builder drops or moves.12,32

Use the element-only properties (firstElementChild, children) or selectors when you mean elements.28,32 For the same reason textContent returns whitespace exactly as stored, while innerText returns the text as rendered, with whitespace collapsed by CSS.33,34




3From parser output to DOM



3.1 The tree grows while the bytes arrive


The HTML parser does not wait for the whole response. Tree construction consumes tokens one at a time, and each start tag usually means "create an element for the token, insert it at the appropriate place, and push it onto the stack of open elements"; end tags pop elements off that stack, and character tokens are appended to a text node in the current element.12,35 So the DOM exists, partially, from the first few hundred bytes onward. A script running mid-document sees every element above it and nothing below it, and browsers can render the part of the page that has been built while the rest is still downloading.21,22


The parser creates nodes through the same internal algorithms as script APIs, with a few parser-only flags. Elements are made by the DOM Standard's create an element algorithm (which also decides whether a custom element is upgraded straight away), and they are inserted by insert, which runs the same insertion steps as appendChild().31,36,37 What is different is bookkeeping: elements created by the parser carry a "parser-inserted" flag where it matters (notably on script), and form controls remember the form element that was open when they were created.38,39

3.2 Error recovery decides the shape


Because HTML parsing never fails, the shape of the DOM for invalid markup is defined too, and it is often surprising. A p start tag implicitly closes an open p; a div inside a p closes the paragraph, so the </p> that follows creates a new, empty p; text and elements that are not allowed inside a table are foster-parented to just before the table; and misnested formatting elements are repaired by the adoption agency algorithm, which may clone elements.12,40 The rules themselves are the subject of the parsing article. For DOM code, the lesson is that a selector written against the source can miss the real tree.

3.3 Speculative parsing


When the tree builder has to stop and wait for a script (section 5), browsers do not sit idle. The HTML Standard allows a speculative HTML parser to scan ahead in the input and start fetching resources it finds, such as scripts, style sheets and images, without building any nodes; its only output is network requests, and the real parser later uses the results.43 This "preload scanner" is why a parser-blocking script costs less than it seems, and why resources hidden from it, for example URLs that only exist inside script strings, load later.43,44




4The document lifecycle



4.1 document.readyState


Every document has a current document readiness, exposed as document.readyState, which takes three values in order: "loading" while the parser is running, "interactive" once parsing has finished, and "complete" once the document and its subresources have loaded. Each change fires a readystatechange event at the document.9,45 A document created by the parser starts in "loading"; documents created with new Document(), DOMParser or createHTMLDocument() are born "complete", since no parser is feeding them.9,46



4.2 "The end": DOMContentLoaded and load


When the tree builder reaches the end of the input, it runs a sequence the HTML Standard calls the end (§13.2.7). Simplified, it does the following, in this order:47


    

  1. Set the document's readiness to "interactive" and pop every element off the stack of open elements.
    2. 

  2. Run, in document order, every script in the list of scripts that will execute when the document has finished parsing: defer scripts and non-async module scripts, waiting for each one to be ready.
    3. 

  3. Queue a task to fire DOMContentLoaded at the document. The event bubbles, so it can be heard on window too.
    4. 

  4. Wait until the set of async scripts and the ordered list of "as soon as possible" scripts are both empty, and until nothing (images, style sheets, frames) is delaying the load event.
    5. 

  5. Queue a task to set the readiness to "complete" and fire load at the Window; then, if the page is shown, fire pageshow.
    6. 



Two practical consequences follow. First, DOMContentLoaded means "the DOM is built and deferred scripts have run", not "everything is ready": MDN notes that it does not wait for style sheets, images or async scripts.48 Second, a defer script never needs a DOMContentLoaded listener, because it runs before the event, with the whole tree already in place.38,47

function whenReady(fn) {
  if (document.readyState === "loading") {
    document.addEventListener("DOMContentLoaded", fn, { once: true });
  } else {
    fn();   // "interactive" or "complete": the tree is already built
  }
}

5Scripts and DOM construction



5.1 Parser-blocking scripts


A classic script element without async or defer is parser-blocking. When the tree builder inserts it, it stops, the script is fetched if it has a src, and only after it has executed does parsing resume.38,49 The reason is document.write(): such a script may write markup into the input stream at the current position, so the parser cannot know what comes next until the script has run.50 While the script runs, document.currentScript refers to its element, and the DOM ends at that element.51


Style sheets join in. A script may read computed style, so a parser-inserted style sheet that is still loading is a script-blocking style sheet: a classic script after it waits until the sheet has loaded, and the parser waits with it.48,52 That is how a slow CSS file can delay DOM construction even though CSS never changes the DOM.

5.3 document.write() and the insertion point


While a parser-blocking script runs, the parser's input stream has an insertion point just after the script's end tag. document.write(markup) inserts characters there, and when the script finishes, the parser tokenizes them as if they had been in the file.50 After the document has finished parsing there is no insertion point, so a call to document.write() implicitly calls document.open(), which removes every node from the document and starts a new, empty parse.50,54 The HTML Standard says "use of this method is strongly discouraged", and Chrome has, since version 55, refused to run parser-blocking cross-site scripts injected with document.write() for users on 2G connections.50,55

5.4 Scripts inserted after parsing


Scripts added by DOM methods run when they are connected to the document, but scripts added as markup through innerHTML, outerHTML or insertAdjacentHTML() "do not execute at all". A script element that has already been prepared, for example one moved from another place in the document, never runs a second time.38,56 To run markup that contains scripts, create the element yourself or use setHTMLUnsafe() or createContextualFragment(), both of which create scripts that can run; setHTMLUnsafe() runs them only when its runScripts option is true.57–59

6The DOM is not what you see



6.1 DOM, CSSOM and the render tree


The DOM describes content. To draw it, a browser also parses style sheets into the CSS Object Model (CSSOM), then combines the two into what Grigorik calls the render tree: the nodes that will actually be drawn, each with its computed styles.14,60 The render tree leaves out nodes that are not visible, such as script, meta and head, and any element whose computed display is none, along with its descendants. An element with visibility: hidden stays, because it still takes up space as an empty box.15,60 The tree is also not one-to-one in the other direction: ::before and ::after pseudo-elements generate boxes without being DOM nodes, an element with display: contents generates no box of its own while its children do, and shadow trees (section 8.4) are rendered in place of, or around, the light DOM children of their host.15,61,62


The CSS specifications call the result the box tree; engines call it the layout tree, render tree or frame tree. Whatever its name, it is internal: scripts cannot walk it, only observe its effects through APIs such as getComputedStyle(), getBoundingClientRect() and checkVisibility().14,15,63





Try it: the DOM construction lab draws the DOM and an approximation of the render tree side by side for any markup you enter, using the browser's own computed styles.



6.2 The critical rendering path


The sequence from bytes to pixels (DOM, CSSOM, render tree, layout, paint) is the critical rendering path.64 DOM construction sits at its start and is affected by everything that blocks the parser. CSS is render-blocking by default: the browser will not paint content until the style sheets in the head have loaded, because painting unstyled content and then restyling it would be worse.64,65 The HTML Standard formalises this with render-blocking elements, and authors can opt any script or style sheet into the same behaviour with blocking="render".65 The companion articles on the critical rendering path and the browser rendering pipeline follow the rest of that path; here the point is how DOM work feeds it.



6.3 DOM changes and layout


Each DOM mutation invalidates some style and layout. Browsers batch that work and recompute it lazily, usually once per frame, but a script that reads a layout property such as offsetHeight right after a write forces the engine to update style and layout synchronously. Doing that in a loop, alternating writes and reads, is called layout thrashing.66 Large trees make every one of those steps slower; Lighthouse warns when a page's body has more than about 800 nodes and flags an error at about 1,400.67

    8Building the tree from markup
    


    8.1 innerHTML and the fragment parser
    

    Setting el.innerHTML runs the HTML fragment parsing algorithm with el as the context element. The algorithm creates a new, scripting-disabled document, puts an html element in it, sets the tokenizer state and insertion mode as if the parser were already inside an element like the context, parses the string, and returns the resulting children, which then replace the element's children.83,84 Because the context matters, the same string yields different trees in different places, as Figure 8 shows.
    




    Assigning innerHTML destroys and recreates every descendant: element references held by scripts now point at detached nodes, event listeners on them are gone, form state is lost, and scripts in the string do not run (section 5.4).56,84 MDN also calls innerHTML "probably the most common vector for cross-site scripting"; the security article covers safe alternatives in detail.56 insertAdjacentHTML() uses the same fragment parser but inserts without destroying existing children, and outerHTML replaces the element itself.84

    8.4 Shadow trees
    

    A shadow tree is a separate node tree attached to an element, its shadow host. Its root is a ShadowRoot, a kind of DocumentFragment. Nodes in the shadow tree are not children of the host, are not found by document.querySelector(), and are styled by the shadow tree's own style sheets; this encapsulation is what web components use.62,88 Instead, the host's own children (its light DOM) are assigned to slot elements inside the shadow tree, and rendering uses the flat tree, in which slotted nodes appear where their slot is.89–91
    

    Shadow roots can be created in two ways. el.attachShadow({ mode: "open" }) works on autonomous custom elements and on a fixed list of HTML elements: article, aside, blockquote, body, div, footer, h1 to h6, header, main, nav, p, section and span.92,93 Mode "open" exposes the root as el.shadowRoot; "closed" makes that property return null. Or the parser can build the shadow root as the page loads, from declarative shadow DOM: a template with a shadowrootmode attribute is replaced by a shadow root on its parent element, with the template's content inside it.85,87,94

    8.5 Custom elements and upgrades
    

    When the parser creates an element with a valid custom element name before customElements.define() has been called for it, the element is created as an undefined HTMLElement and matches :not(:defined). When the definition arrives, every such element in the document is upgraded: its prototype is changed and its constructor runs. If the definition already exists when the parser reaches the tag, the element is created synchronously with its constructor, and connectedCallback runs as soon as it is inserted, before its children have been parsed.26,96 That last point is a common trap: a custom element that reads its children in connectedCallback sees none when the definition is loaded early.

  }
});

    9.2 Walking the tree in code
    

    The DOM Standard provides two traversal objects, NodeIterator and TreeWalker, created with a root, a whatToShow bit mask (such as NodeFilter.SHOW_TEXT) and an optional filter. Both visit nodes in tree order; a TreeWalker can also move to parents and siblings.100,101
    

    Collect every non-empty text nodeJS
    function textNodes(root) {
  const walker = document.createTreeWalker(root, NodeFilter.SHOW_TEXT, {
    acceptNode: n => n.data.trim() ? NodeFilter.FILTER_ACCEPT : NodeFilter.FILTER_REJECT
  });
  const out = [];
  while (walker.nextNode()) out.push(walker.currentNode);
  return out;
}
