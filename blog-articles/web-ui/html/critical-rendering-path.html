The Critical Rendering Path

How a browser gets from the first byte of HTML to the first pixels on screen, and how to make that trip shorter: render-blocking and parser-blocking resources; critical resources, critical bytes and critical path length; async, defer and module scripts; critical CSS and media queries on style sheets; fonts, the LCP image and resource hints; and measuring the result with DevTools, Lighthouse, FCP, LCP and the Core Web Vitals. Includes a before-and-after optimisation measured in a real browser. Grounded in the WHATWG HTML Standard, the W3C Web Performance specifications, web.dev, MDN and the Chrome documentation.

Updated 17 November 202665 references (Vancouver style)Includes exercises, trivia, a measured case study, a CRP lab and a playground

Earlier parts of this series were about what to put in a document: its structure, media, metadata and scripts. This part is about when the user gets to see it. Between the moment the HTML starts arriving and the first paint, the browser must build the DOM, fetch and parse every style sheet that applies, run every script that stands in the way, compute layout and paint. That chain of work is the critical rendering path (CRP), and the order in which a page asks for its resources decides how long it is.1,2

Companion articles in the series cover the HTML parsing algorithm, DOM construction and the style, layout, paint and compositing stages in depth, and a separate article goes deep on resource hints. This article takes the performance view of the same pipeline. Section 2 summarises the path from bytes to pixels. Section 3 explains which resources block what. Section 4 introduces the three numbers that describe a critical path, and section 5 shows how to shorten it. Section 6 covers the metrics and tools, and section 7 applies everything to a real page, measured in Chromium before and after each fix. Sections 8 to 12 hold exercises, trivia, an interactive CRP lab, a playground and a quick reference.

1Introduction

1.1 What the critical rendering path is

MDN defines the critical rendering path as "the sequence of steps the browser goes through to convert the HTML, CSS, and JavaScript into pixels on the screen": request the document, parse HTML into the DOM, parse CSS into the CSSOM, combine them into a render tree, compute layout and paint.2 Ilya Grigorik's guide on web.dev, which popularised the term, describes the same pipeline and frames optimisation as prioritising the content that relates to the user's current action.1

The path is "critical" because each step depends on earlier ones. The render tree needs both the DOM and the CSSOM, so a slow style sheet delays the first paint even if the HTML arrived long ago. A classic script pauses the HTML parser, and the script itself may have to wait for style sheets.3,4 Anything the browser must fetch before it can show the first frame is a critical resource.5

1.2 Why it matters

Users do not see "page load"; they see a blank screen, then some content, then the main content. Google's Web Vitals programme measures exactly those moments. First Contentful Paint (FCP) records the first text or image painted, and Largest Contentful Paint (LCP), one of the three Core Web Vitals, records when the largest image or text block in the viewport was painted. A good LCP is 2.5 seconds or less for at least 75% of page loads.8–10 The critical rendering path sets a floor for both: nothing can paint before the render-blocking resources have arrived and been processed.11,12

Many sites miss the target. In the HTTP Archive's 2024 Web Almanac, 59% of mobile pages had a good LCP, and only 43% passed all three Core Web Vitals once INP replaced FID.13 Google recommends that site owners achieve good Core Web Vitals "for success with Search", saying they align with what its core ranking systems seek to reward.14

2From bytes to pixels

This section is a performance-oriented summary; the companion articles on parsing, DOM construction and the rendering pipeline go into each stage in depth.

2.1 The network: round trips and the first 14 KB

Before any parsing can begin, the browser must reach the server. A new HTTPS connection to an origin costs a DNS lookup, a TCP handshake and a TLS handshake (one round trip for a full TLS 1.3 handshake), then the request itself and the server's think time before the first byte arrives.27,31,36 That last interval is Time to First Byte (TTFB); web.dev suggests, as a rough guide, that most sites aim for 0.8 seconds or less.36

TCP does not send at full speed from the start. Under slow start the sender may only have a limited number of unacknowledged segments in flight, and that limit grows as acknowledgements come back. RFC 6928 set the initial window to 10 segments, at most 14,600 bytes.26,31 So the first round trip can carry about 14 KB, the next about twice that, and so on. web.dev's critical-CSS guide turns this into advice: keep the above-the-fold content and its critical CSS under about 14 KB compressed, so the first render needs as few round trips as possible.37

2.2 Building the DOM and the CSSOM

The HTML parser converts bytes to characters using the document's encoding, characters to tokens, tokens to nodes, and nodes into the DOM tree. CSS goes through the same stages into the CSS Object Model (CSSOM). The two are independent data structures.6 The DOM can be built incrementally: the parser can hand partial content to the renderer as it goes. The CSSOM cannot be used half-built, because a later rule can override an earlier one, so the browser waits for every applicable style sheet before rendering.11

2.3 Render tree, layout and paint

The render tree combines the two: it contains only the nodes that are visible, each with its computed styles, so <head>, <script> and elements with display: none are left out. Layout then computes the exact position and size of each box for the current viewport, and paint turns the boxes into pixels.3 Every time the DOM or CSSOM changes, some of this work runs again, which is why a script that runs late and changes styles can delay the paint of content that has already arrived.3,38

2.4 The preload scanner

When the main parser is stuck waiting for a script, browsers do not sit idle. A preload scanner, a secondary parser, reads ahead in the raw markup and starts fetching the resources it finds, such as style sheets, scripts and images. The HTML Standard allows this as speculative HTML parsing.39,40 The scanner only sees what is in the markup. Resources injected by script, images lazy-loaded through a data-src attribute, content rendered on the client, and CSS background images are invisible to it, and web.dev lists all of these as antipatterns.39 The 2024 Web Almanac found that the LCP element was not statically discoverable in the HTML on 35% of mobile pages.13

Rule of thumbPut the URLs of critical resources in the HTML, as plain src and href attributes. Everything the preload scanner can see starts downloading early, even while the parser is blocked.39

3What blocks rendering

Two kinds of blocking matter, and they are often confused. A render-blocking resource stops the browser from painting anything; a parser-blocking resource stops the HTML parser from building more of the DOM.4,41 MDN notes that the most common causes of render-blocking are initially loaded CSS and JavaScript files.41

3.1 Render-blocking: style sheets

By default, CSS is treated as a render-blocking resource: the browser will not render any processed content until the CSSOM has been built.11 This is deliberate. Without it the user would see a flash of unstyled content, a moment of raw HTML before the styles arrive.11 Since the rules are known, they can be used. A style sheet that does not apply to the current environment, because of its media attribute, does not block rendering:11,42

Which style sheets block the first render?HTML
<link rel="stylesheet" href="site.css">                       <!-- blocks: applies everywhere -->
<link rel="stylesheet" href="print.css" media="print">        <!-- does not block on screen -->
<link rel="stylesheet" href="wide.css" media="(min-width: 60em)">  <!-- blocks only on wide screens -->
<link rel="stylesheet" href="portrait.css" media="(orientation: portrait)">

The browser still downloads every style sheet, blocking or not, but gives the non-blocking ones a lower priority.11 In the measured example in section 7, Chromium fetched a media="print" style sheet at "VeryLow" priority instead of "VeryHigh". The HTML Standard says the user agent must apply a linked resource only when its media matches the environment, and adds that it may fetch such resources only when they are needed.42,43

Lighthouse's former "Eliminate render-blocking resources" audit spells out the conditions it used: a <link rel="stylesheet"> counts as render-blocking unless it has the disabled attribute or a media attribute that does not match the device; note that media="all" still blocks.35 Only link elements in the document's <head> can block rendering this way, according to MDN.44

3.2 Parser-blocking: classic scripts

A <script> without async, defer or type="module" is a parser-blocking script. The HTML Standard says that in this case "the script is fetched and evaluated immediately, blocking parsing until these are both complete".15 The reason is historical: the script might call document.write() and insert markup at that very point, so the parser cannot safely continue.4 Grigorik puts it plainly: by default, all JavaScript is parser-blocking.4

A parser-blocking script in the <head> is also effectively render-blocking. The body has not been parsed yet, so there is nothing to render until the script has been downloaded and run. Lighthouse's audit counted a <script> as render-blocking exactly when it was in the <head> and had neither defer nor async.35 This is the reasoning behind Souders' 2007 rule "put scripts at the bottom".30

3.3 CSS blocks scripts, too

A script may ask for computed styles, for example with getComputedStyle() or offsetWidth. To give it a correct answer, the browser delays the execution of a classic script while a style sheet that precedes it is still loading. The HTML Standard calls these script-blocking style sheets.16 Grigorik summarises the effect: JavaScript execution blocks on the CSSOM, and the browser delays script execution and DOM construction until it has finished downloading and constructing the CSSOM.4 So a slow style sheet before a script blocks both rendering and parsing.

3.4 Fonts block text

Web fonts are not render-blocking in the same sense, since the rest of the page can paint without them, but they can make text invisible. Font requests are only dispatched once the render tree shows which font variants are needed.7 Until the font arrives, the browser may render the text invisibly. According to web.dev, Chromium-based browsers and Firefox block text rendering for up to 3 seconds if the web font has not loaded, and Safari blocks it indefinitely.45 The font-display descriptor controls this behaviour (section 5.4).25,46

3.5 Opting in: blocking="render"

Sometimes you want to block rendering, for example to stop a script that sets the colour theme from causing a flash of the wrong theme. The HTML Standard defines a blocking attribute on script, style and link; the token render makes the element potentially render-blocking.18,44 While a document's set of render-blocking elements is non-empty, the document is render-blocked, but only until an implementation-defined timeout, so a lost resource cannot leave the page blank forever.17

Explicitly render-blocking resourcesHTML
<!-- An async script that must run before the first frame -->
<script blocking="render" async src="theme.js"></script>

<!-- A style sheet that would not otherwise block (inserted later, or async) -->
<link rel="stylesheet" href="above-fold.css" blocking="render">

Use it sparingly: every render-blocking element is a critical resource. Browser support varies; check MDN's compatibility data before relying on it.44

4Three numbers that describe a critical path

4.1 Critical resources, critical bytes and path length

Grigorik's guide reduces any critical path to three numbers:5,49

  • Critical resources: resources that could block the initial rendering of the page. The HTML document itself is always one.
  • Critical path length: the number of round trips, or the total time, needed to fetch all critical resources. It depends on the dependency graph (a style sheet referenced from another style sheet adds a round trip) and on size (a large file takes several round trips).
  • Critical bytes: the sum of the transfer sizes of all critical resources.

The optimisation strategy follows directly: reduce the number of critical resources, reduce the number of critical bytes, and shorten the path by fetching the remaining critical resources as early as possible.2,49

Two things stand out. Adding a script did not lengthen the path, because the preload scanner fetched it in parallel with the CSS; but it added a critical resource and critical bytes. And the last row reached the minimum, one round trip, without removing any feature: the script still runs and the style sheet still exists. They were simply taken off the critical path.5

4.3 Counting it for your own page

To compute the three numbers for a real page, list the resources that Table 2 marks as render-blocking, then:

  1. Count them, plus the HTML document: that is the number of critical resources.
  2. Add their compressed transfer sizes (the "Transferred" column in the DevTools Network panel, or transferSize in Resource Timing): that is the critical bytes.24,50
  3. Draw the dependency graph. Resources discovered from the HTML start together; a resource discovered only from inside another one, such as an @import or a font file named in a third-party style sheet, starts a round trip later, plus connection set-up if it lives on a new origin. Divide each resource's size by about 14 KB, doubling per round, to estimate its round trips. The longest chain is the critical path length.5,26,37

The CRP lab in section 10 does this arithmetic for you as you change a page's markup.

5Shortening the path

Grigorik's general sequence is: analyse and characterise the critical path; minimise the number of critical resources by eliminating them, deferring their download or marking them async; reduce the critical bytes; and order the remaining critical resources so that they download as early as possible.49 The subsections below apply that sequence to scripts, CSS, fonts and the LCP image.

5.1 Scripts: async, defer and modules

The HTML Standard defines three ways to keep an external script off the parser's critical path:15

  • defer (classic scripts): the script is fetched in parallel with parsing and evaluated when the page has finished parsing. Deferred scripts run in document order, and the DOMContentLoaded event waits for them.15,20,47
  • async (classic or module): the script is fetched in parallel with parsing and evaluated as soon as it is available, potentially before parsing completes, and in whatever order the downloads finish.15
  • type="module": module scripts behave like deferred scripts by default; the defer attribute has no effect on them, and async makes them run as soon as they and their imports are ready.15 <link rel="modulepreload"> lets the browser fetch a module's dependencies early instead of discovering them one level at a time.51

5.2 Critical CSS

If CSS is render-blocking, the fastest style sheet is one that needs no request. The critical CSS technique inlines the rules needed for the above-the-fold content in a <style> element and loads the rest without blocking.37,52 web.dev's recommended pattern uses preload and swaps the rel once the file has loaded, with a <noscript> fallback:52

Critical CSS inline, the rest loaded without blockingHTML
<head>
  <style>
    /* critical: only what the first screen needs (< ~14 KB compressed with the HTML) */
    body { margin: 0; font: 16px/1.5 system-ui, sans-serif }
    .top { background: #1f3a2c; color: #fff; padding: 12px 16px }
    .hero { width: 100%; height: auto; aspect-ratio: 12 / 7 }
  </style>
  <link rel="preload" href="/css/main.css" as="style"
        onload="this.onload=null; this.rel='stylesheet'">
  <noscript><link rel="stylesheet" href="/css/main.css"></noscript>
</head>

A common variant, used in the case study in section 7, requests the file with a non-matching media query and switches it to all when it loads: <link rel="stylesheet" href="main.css" media="print" onload="this.media='all'">. It works because a non-matching style sheet is not render-blocking (§3.1). Either way, an inline onload handler conflicts with a strict Content Security Policy, which is why web.dev suggests a small loader function such as Filament Group's loadCSS in production.11,52

Extracting the critical rules by hand does not scale. web.dev lists three tools that render the page in a headless browser and keep only the rules used above the fold: Critical, criticalCSS and Penthouse.37 Two cautions: inlined CSS is not cached separately and is re-sent with every HTML response, and inlining too much is itself one of the preload-scanner antipatterns, because it delays the discovery of everything after it.37,39

5.3 Media queries on style sheets

Splitting CSS by media lets the browser skip the blocking wait for rules that do not apply: print styles, styles for wide screens on a phone, styles for an orientation the device is not in.11 The media attribute on link is prescriptive: the browser must apply the style sheet only when the query matches.42

Splitting style sheets by mediaHTML
<link rel="stylesheet" href="base.css">                                   <!-- critical everywhere -->
<link rel="stylesheet" href="print.css"  media="print">                     <!-- never blocks on screen -->
<link rel="stylesheet" href="desktop.css" media="(min-width: 64em)">        <!-- blocks only on large screens -->
<link rel="stylesheet" href="dark.css"   media="(prefers-color-scheme: dark)">

The split only pays off if each file is meaningful on its own; many tiny files trade critical bytes for request overhead. Media queries inside a single file (@media blocks) do not help here: the whole file is still render-blocking.11

5.4 Fonts

Fonts sit at the end of a dependency chain: HTML → style sheet → render tree → font file. With a third-party font service there may be two extra origins (one for the CSS, one for the files), each needing its own connection.7,45 The font-display descriptor decides what the user sees while waiting. CSS Fonts Level 4 describes a font display timeline of a block period (text drawn invisibly), a swap period (fallback font drawn, replaced when the web font arrives) and a failure period (fallback kept).25

Practical rules from web.dev and MDN:7,45,46

  • Choose font-display: swap when the brand font matters and some reflow is acceptable, and optional when it is better to keep the fallback than to shift text after the first paint.
  • Serve WOFF2, which compresses about 30% better than WOFF, and subset fonts to the characters you use, for example with unicode-range.
  • Preconnect to a third-party font origin, adding crossorigin, because font requests are always made in CORS mode.
  • Preload only the one or two font files used above the fold; preloading is effective but takes bandwidth away from other resources.
  • Self-hosting the fonts removes the extra connections altogether.
A font set-up that keeps text visibleHTML
<link rel="preload" href="/fonts/display-latin.woff2" as="font" type="font/woff2" crossorigin>
<style>
  @font-face {
    font-family: Display;
    src: url(/fonts/display-latin.woff2) format("woff2");
    font-display: swap;            /* fallback text immediately */
    unicode-range: U+0000-00FF;    /* Latin subset */
  }
  h1 { font-family: Display, Georgia, serif; }
</style>

5.5 The LCP image

On 73.3% of mobile pages, and 83.3% of desktop pages, the LCP element is an image.13 Images are not render-blocking, but they are on the path to LCP, so the aim is to start their download as early as possible and avoid delaying them:34,38

  • Make it discoverable. Use a real <img src> (or srcset) in the HTML, not a CSS background or a script-inserted image, so the preload scanner can find it.39
  • Never lazy-load it. loading="lazy" defers the fetch until layout shows the image is near the viewport, which is after the render-blocking resources have been processed.38,53
  • Raise its priority. Chrome starts images at "Low" priority and boosts those in the viewport to "High" only at layout. fetchpriority="high" requests it at high priority from the start.19,34 In a Google Flights test, adding it to the LCP image improved LCP from 2.6 s to 1.9 s.34
  • Reserve its space. width and height attributes (or aspect-ratio) prevent the layout shift when it arrives.54
An LCP image the browser can start at onceHTML
<img src="/img/hero-800.jpg"
     srcset="/img/hero-400.jpg 400w, /img/hero-800.jpg 800w, /img/hero-1200.jpg 1200w"
     sizes="100vw" width="1200" height="700"
     alt="Coffee hills at dusk" fetchpriority="high">

5.7 Fewer bytes, fewer round trips

  • Compress and minify every text resource; critical bytes are counted after compression.5,37
  • Remove unused CSS and JavaScript from the critical files. The case-study style sheet was 106 KB before compression, of which the first screen used seven rules.
  • Cut the server's think time: TTFB comes before everything else, and web.dev's LCP guidance expects it to take about 40% of the LCP time on a well-optimised page.36,38
  • Avoid chains: @import inside CSS, scripts that load scripts and fonts referenced from third-party CSS each add a round trip that the preload scanner cannot remove.5,39
  • Render on the server: a page whose content appears only after a client-side framework has run puts the whole application bundle on the path to FCP and LCP.39

5.8 An order of work

  1. Measure: find the LCP element and list the render-blocking requests (section 6).
  2. Remove parser-blocking scripts from the <head>: defer, async or modules.
  3. Inline critical CSS; load the rest without blocking; add media to conditional style sheets.
  4. Make the LCP image discoverable, eager and high priority; reserve its space.
  5. Fix fonts: WOFF2, subsets, font-display, preconnect or self-host, preload the one that matters.
  6. Reduce bytes and server time; consider Early Hints.
  7. Measure again, in the lab and in the field.

6Measuring

6.1 Lab data and field data

Lab data comes from loading a page in a controlled environment, such as Lighthouse or a DevTools recording, with fixed device and network settings. It is repeatable and good for debugging. Field data comes from real users. The Chrome UX Report (CrUX) is a public dataset of how real-world Chrome users experience popular sites, and it is what Google's tools show as field data.10,58 The two often disagree: a lab test uses one device and one network, while the field covers cached and uncached visits on every kind of device. Core Web Vitals are assessed on field data at the 75th percentile of page loads, separately for mobile and desktop.10

6.3 Core Web Vitals

Google introduced Web Vitals on 5 May 2020, naming LCP, First Input Delay (FID) and CLS as the Core Web Vitals.32 On 12 March 2024, INP replaced FID, and developers had until 9 September 2024 to stop relying on FID.33 Today the set is LCP for loading, INP for interactivity and CLS for visual stability.10 Google Search's documentation recommends achieving good Core Web Vitals and gives the same thresholds.14

6.6 Lighthouse

Lighthouse loads the page once under simulated throttling and computes a performance score from weighted lab metrics. In Lighthouse 10 the weights are: TBT 30%, LCP 25%, CLS 25%, FCP 10% and Speed Index 10%; the documentation notes that the weights change over time.64 Since Lighthouse 13, render-blocking problems are reported through the "Render-blocking requests" insight rather than the older audit.12,35 A Lighthouse score is a diagnostic, not a field measurement: it does not tell you whether real users pass the Core Web Vitals.10,58

7.1 Set-up

  • Page. A coffee-shop landing page: a header bar, an h1 in a display web font, a paragraph, a 1200×700 hero image (52 kB JPEG) and three cards.
  • Resources. 7.5 What the numbers show

  • Removing render-blocking resources moved FCP the most: from 1.04 s to 0.38 s, a 63% cut, while the page content did not change at all. The two biggest steps were the scripts (−0.30 s) and the critical CSS (−0.30 s).12,49
  • Critical bytes fell from 55.4 kB to 1.2 kB: the whole critical path now fits in the first round trip of a fresh connection (RFC 6928's 14.6 kB window).26,37
  • The font was the worst offender for perceived speed. With font-display: block and a 357 kB TrueType file discovered late, the most important text on the page was invisible for over three seconds, longer than the default block period described by web.dev, though the load finished before the browser gave up waiting. Subsetting to WOFF2 shrank the file by 96%, and swap made the text visible at first paint.25,45
  • LCP improved by 38% (1.74 s to 1.09 s), but less than FCP did, because LCP is a 52 kB image that has to share a 1.6 Mbit/s link with every other download.38
  • fetchpriority="high" made no measurable difference here. Chromium did raise the image's priority from Low to High and started it at 0.23 s instead of 0.36 s, but over HTTP/1.1 the image still shared bandwidth with the JavaScript and CSS on other connections and finished at the same time. Hints change the order of work, not the size of the pipe; on a page with more competing requests, or over HTTP/2, the effect can be larger, as in the Google Flights example.34
  • Element render delay appeared. In steps 3 and 4 the image arrived at about 1.00 s, but LCP was recorded at about 1.06–1.09 s, just after the deferred vendor.js finished its 120 ms of work. Deferring a script does not make its main-thread cost disappear; the next fix would be to split or delay that bundle.38,61

Exercise 1: Count the critical path

Assume each file is under 14 KB compressed except app.css (40 KB). How many critical resources, roughly how many critical bytes, and what minimum critical path length (in round trips) does this page have?

Exercise 1HTML
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <title>Shop</title>                                <!-- HTML: 6 KB -->
  <link rel="stylesheet" href="app.css">             <!-- 40 KB -->
  <link rel="stylesheet" href="print.css" media="print">
  <script src="vendor.js" defer></script>
  <script src="consent.js"></script>                 <!-- 3 KB -->
</head>
<body>…<img src="hero.jpg" alt="…"></body>
</html>
Show solution

Three critical resources: the HTML, app.css and the parser-blocking consent.js. print.css does not match the screen, vendor.js is deferred and the image does not block rendering.5,11,15 Critical bytes ≈ 6 + 40 + 3 = 49 KB. Path length: one round trip for the HTML, then app.css and consent.js are fetched in parallel. Under slow start, 40 KB needs about two windows (roughly 14 KB, then 29 KB), so the path is at least three round trips in total, plus any connection set-up.26,31

Exercise 2: Predict the order

In what order do the log messages appear? Assume a.js is large and slow and b.js and c.js are tiny.

Exercise 2HTML
<script src="a.js" defer></script>       <!-- log("a") -->
<script src="b.js" async></script>       <!-- log("b") -->
<script type="module">log("m")</script>
<script>log("inline")</script>
<script src="c.js" defer></script>       <!-- log("c") -->
<script>document.addEventListener("DOMContentLoaded", () => log("DCL"))</script>
Show solution

inline first, since it runs as soon as the parser reaches it. b probably runs next, while parsing continues, but async scripts have no guaranteed position. After parsing, deferred scripts run in document order, a then c, even though c arrived first. The inline module behaves like a deferred script and joins the same ordered list, so m runs between a and c. DCL comes last of these. Likely output: inline, b, a, m, c, DCL.15,20,47 Try it with the "Script order" preset in the playground.

Exercise 4: Why is the LCP late?

A page has TTFB 0.4 s, and its LCP hero image finishes downloading at 1.2 s, but LCP is reported at 2.3 s. The image is a plain <img> with fetchpriority="high". Which LCP subpart is too large, and what are the likely causes?

Show solution

Element render delay (1.1 s, about half the total, against a guideline of under 10%). The image is ready but cannot be painted. Typical causes: a render-blocking style sheet or script that is still loading, a large script running on the main thread, or client-side code that inserts or reveals the image late (for example an A/B test that hides the page). Look at the Main track in the Performance panel around 1.2 s.29,38

Exercise 5: Media queries

On a phone in portrait orientation, 400 CSS pixels wide, which of these style sheets are render-blocking?

Exercise 5HTML
<link rel="stylesheet" href="a.css">
<link rel="stylesheet" href="b.css" media="all">
<link rel="stylesheet" href="c.css" media="screen and (min-width: 48em)">
<link rel="stylesheet" href="d.css" media="(orientation: portrait)">
<link rel="stylesheet" href="e.css" media="print">
<link rel="stylesheet" href="f.css" disabled>
Show solution

a, b and d. media="all" is the same as no attribute; c needs at least 48em (768px at the default font size); e is for print; f is disabled and is not even downloaded. All except f are still fetched; c and e at low priority.11,35,42

Exercise 6: Choose a font-display value

(a) A news site's body text uses a web font; editors care more about stable layout than the exact typeface. (b) A product's logo-like heading must appear in the brand font, and a short delay is acceptable. (c) An icon font. Which font-display value fits each?

Show solution

(a) optional: text appears at once in the fallback, and the web font is used only if it is ready almost immediately, so there is no late swap and no layout shift. (b) block (a short invisible period, then swap), or swap with a carefully matched fallback. (c) block: a fallback font would show meaningless characters. Better still, use SVG icons.25,45,46

Exercise 7: Read a Lighthouse report

A Lighthouse run reports FCP 1.2 s, Speed Index 1.4 s, LCP 4.8 s, TBT 40 ms and CLS 0.02. Field data from CrUX says LCP is 2.2 s at the 75th percentile. Which number decides whether the page passes the Core Web Vitals, and why might the two LCP values differ so much?

Show solution

The field value (2.2 s, good) decides; Core Web Vitals are assessed at the 75th percentile of real page loads. Lighthouse loads once, cold, on a simulated slow device and network, while many real visits are on fast devices or have the hero image cached. The lab number is still useful: a 4.8 s LCP with an FCP of 1.2 s suggests a large resource load delay or duration for the LCP image.10,38,58,64

Exercise 8: Spot the preload-scanner antipatterns

Exercise 8HTML
<style>.hero { background-image: url(hero.jpg) }</style>
<div class="hero"></div>
<img data-src="product.jpg" class="lazyload" alt="Product">
<script>
  const s = document.createElement("script");
  s.src = "app.js"; document.head.append(s);
</script>
Show solution

All three hide a URL from the preload scanner: a CSS background image (found only after the CSSOM and render tree exist), a script-driven lazy image using data-src, and a script-injected script. Fixes: use an <img> for the hero (or <link rel="preload" as="image">); use native loading="lazy", and only below the fold; use <script src="app.js" async> in the markup.39,53

9Trivia questions

  1. Which two rules in Steve Souders' 2007 book are about the critical rendering path?

    Answer

    Rule 5, "Put stylesheets at the top", and rule 6, "Put scripts at the bottom", out of 14 rules.30

  2. Where does the "14 KB" rule of thumb come from?

    Answer

    From TCP slow start: RFC 6928 (April 2013) raised the initial congestion window to 10 segments, at most 14,600 bytes, so that is about how much a fresh connection can deliver in its first round trip.26,37

  3. Does the browser download a style sheet with media="print" when you view the page on screen?

    Answer

    Yes, but at a lower priority, and it does not block rendering.11

  4. Which attribute has no effect on module scripts?

    Answer

    defer: modules are deferred by default. async does change their behaviour.15

  5. What is the "preload scanner"?

    Answer

    A secondary HTML parser that reads ahead of the main parser, while that parser is blocked, and starts fetching the resources it finds. The HTML Standard calls the process speculative HTML parsing.39,40

  6. When were the Core Web Vitals announced, and by whom on the Chromium Blog?

    Answer

    On 5 May 2020, in "Introducing Web Vitals: essential metrics for a healthy site" by Ilya Grigorik.32

  7. Which metric did INP replace, and when?

    Answer

    First Input Delay (FID), on 12 March 2024.33

  8. What is the LCP threshold for "good", and at what percentile?

    Answer

    2.5 seconds or less, at the 75th percentile of page loads, segmented by mobile and desktop.9,10

  9. Can an inline <svg> be the LCP element?

    Answer

    No. LCP considers img elements, image elements inside an SVG, videos, elements with a CSS url() background image and block-level elements containing text, but not inline svg elements.9

  10. How long do Chromium and Firefox hide text while waiting for a web font, by default?

    Answer

    Up to 3 seconds; according to web.dev, Safari waits indefinitely.45

  11. What did adding fetchpriority="high" to the LCP image do for Google Flights?

    Answer

    LCP improved from 2.6 s to 1.9 s in a test.34

  12. What HTTP status code lets a server send Link headers before the final response?

    Answer

    103 Early Hints, defined in RFC 8297 (December 2017) by Kazuho Oku.28

  13. What weight does TBT have in the Lighthouse 10 performance score?

    Answer

    30%, the largest single weight; LCP and CLS have 25% each, and FCP and Speed Index 10% each.64

  14. How long must a task be to count as a "long task"?

    Answer

    Longer than 50 ms.61,62

  15. What share of mobile pages passed the Core Web Vitals in the 2024 Web Almanac, measured with INP?

    Answer

    43%, compared with 48% when FID was used.13

  16. Can a document stay render-blocked forever because of blocking="render"?

    Answer

    No. A document is render-blocked only until an implementation-defined timeout has passed.17

  17. How much better does WOFF2 compress than WOFF?

    Answer

    About 30%, according to web.dev.45

  18. Which tool computes Speed Index for Lighthouse?

    Answer

    The Speedline Node.js module, from a video of the page load.63
