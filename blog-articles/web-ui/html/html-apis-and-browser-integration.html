HTML APIs and Browser Integration

How HTML becomes a live object model that JavaScript can read and change: the DOM tree, nodes, selection, manipulation, attributes and properties, events and propagation; the browser APIs built on top of it (Web Storage, History, Geolocation, Drag and Drop, Clipboard, Fullscreen, Web Workers and Web Components); and the ways scripts are attached to a page, from inline handlers to async, defer and module scripts. Grounded in the WHATWG HTML and DOM standards, the W3C API specifications and MDN.

Updated 14 November 2026124 references (Vancouver style)Includes exercises, trivia, live API demos, an event lab and a playground

The first article in this series described how a browser parses markup into a tree. Every article since has been about what goes into that tree: text, links, media, semantic structure, tables and, most recently, forms. This one is about what happens after the tree exists. The browser does not keep your HTML as text; it turns it into a Document Object Model, a set of live objects defined by the DOM Standard and exposed to JavaScript through interfaces such as Node, Element and EventTarget.1,2 Everything a script does to a page, from changing a heading to storing a preference or opening a video full screen, goes through those objects or through other APIs that the HTML Standard and its companion specifications attach to them.3,4

The article follows the outline in the table of contents. Section 2 covers the DOM itself, section 3 the browser APIs most often used with HTML, and section 4 the ways HTML and JavaScript are connected. Section 5 puts them together in one small application, and sections 6 to 10 hold exercises, trivia questions, an event lab, a playground and a quick-reference table. Most sections include a demo that runs in your browser, so the behaviour you read about can be checked on the spot.

1Introduction

1.1 Where these APIs are defined

No single specification covers the material in this article. The DOM Standard defines the node tree, the core interfaces and the event model.1 The HTML Standard defines the HTML element interfaces, the parser, the script element, event handler attributes, Web Storage, the History interface, drag and drop, Web Workers and custom elements.3 Several APIs live in their own documents, maintained either by the WHATWG or by a W3C working group. Bindings between all of them and JavaScript are written in Web IDL, which is why the same interface looks the same in every browser.5

1.2 How HTML, the DOM and JavaScript fit together

JavaScript the language knows nothing about documents. ECMAScript defines values, functions, objects and modules, and leaves it to a "host" to provide anything else.12 In a browser, the host is defined by the HTML Standard: it creates a global Window object for each document and puts the DOM interfaces and browser APIs on it.5,13 When you write document.querySelector("h1"), the JavaScript engine is calling a Web IDL operation that the browser's rendering engine implements, usually in C++ or Rust.2,5

1.3 A short history

Brendan Eich wrote the first JavaScript engine at Netscape in ten days in May 1995. The language shipped in Netscape Navigator 2.0 under the beta name LiveScript before being renamed JavaScript in December 1995.15 Navigator 2 and Internet Explorer 3 let scripts reach a handful of page objects such as forms, links and images; this informal, incompatible set is now called "DOM Level 0".15,16 The W3C published the first standard object model, DOM Level 1, as a Recommendation on 1 October 1998, and DOM Level 2, which added addEventListener() and the capture and bubble phases, on 13 November 2000.16,17

Today the DOM Standard maintained by the WHATWG is the authoritative version. Since a 2019 agreement between the two organisations, the W3C endorses WHATWG review drafts of the HTML and DOM standards rather than publishing competing versions.18 Most of the "browser APIs" in this article arrived in the HTML5 era: Web Storage, the History interface's pushState(), drag and drop and Web Workers were all developed as part of the HTML5 effort before being folded into, or split out from, the HTML Standard.19–22 Web Components came later. Early proposals were replaced by the current "v1" designs of custom elements and shadow DOM, which are now part of the HTML and DOM standards and supported by every major engine.23–25

1.4 Secure contexts, permissions and user activation

Many powerful APIs are available only in a secure context, which roughly means a page delivered over HTTPS, or from localhost or a file: URL during development.26,27 Geolocation and the asynchronous Clipboard API are examples.8,9 Some also require the user's permission, and some can only be started in response to a real user gesture such as a click or a key press. HTML calls this transient activation: a short window after a user interaction during which the page may do things like open a pop-up or enter full screen.28,29

2The DOM (Document Object Model)

The DOM Standard describes the DOM as a platform-neutral model for events, aborting activities and node trees.1 In practice it is the in-memory representation of a document: a tree of objects, each with properties and methods, that the browser keeps in sync with what is on screen. Changing the tree changes the page; the HTML source file is never touched.2

2.1 The DOM tree

A DOM is a node tree. The DOM Standard defines a tree as a finite hierarchical structure in which every object has at most one parent and an ordered list of zero or more children; the object with no parent is the root.31 For an HTML page the root is a Document node, whose children are the doctype and the html element.32 The markup below produces the tree in Figure 2.

A small documentHTML
<!DOCTYPE html>
<html lang="en">
<head><title>Shop</title></head>
<body>
  <h1 id="title">Mugs</h1>
  <!-- price list -->
  <ul class="items"><li>Blue</li><li>Red</li></ul>
</body>
</html>

Two details surprise people. First, whitespace between tags is kept as text nodes, so body above has seven child nodes, not three. Second, the parser adds elements you leave out: head and body exist in every HTML document's DOM even if the source omits their tags.34,35 Browser developer tools show the DOM, not the source, which is why the Elements panel can disagree with "View source".2

Every object in the tree implements the Node interface, and its nodeType property says which kind of node it is.33 Elements are one kind of node. 2.4 DOM parsing

The browser builds the DOM with the HTML parser, which the HTML Standard defines in two stages: a tokenizer that turns characters into tokens such as start tags, end tags, comments and text, and a tree construction stage that turns tokens into nodes.34 The parser never gives up. Every error, such as a missing end tag or a misnested element, has a defined recovery, which is why every browser builds the same tree from the same broken markup.34,40

Scripts can wait for the tree in three ways: put the script at the end of body, mark it defer or type="module" (see section 4.3), or listen for DOMContentLoaded, which fires once the document has been parsed and deferred scripts have run, without waiting for images.42,43 The load event on window waits for every subresource as well.44

Scripts can also run the parser on demand. DOMParser parses a string into a separate, inert Document; innerHTML, insertAdjacentHTML() and setHTMLUnsafe() parse a fragment straight into an existing element.45,46

Parsing a stringJS
const doc = new DOMParser().parseFromString(
  "<p>Unclosed <b>bold <i>both</b> italic?</i>", "text/html");
console.log(doc.body.innerHTML);
// "<p>Unclosed <b>bold <i>both</i></b><i> italic?</i></p>"  (the adoption agency algorithm at work)
console.log(doc.querySelectorAll("i").length); // 2

textContent, innerText and innerHTML all read and write an element's contents, but they are not interchangeable. textContent is defined by the DOM and returns the text of every descendant text node, including hidden ones and the contents of script and style. innerText is defined by HTML and is layout-aware: it returns text as rendered, skipping hidden content and turning <br> into line breaks, which means reading it forces a style calculation.33,53,54

Passive listeners deserve a note. Touch and wheel listeners can call preventDefault() to stop scrolling, so a browser that sees one must wait for it before scrolling. 2.9 Event propagation

When an event is dispatched to a node in a tree, it does not just visit that node. The DOM Standard computes an event path from the window down to the target and dispatches in three phases: the capturing phase runs capture listeners from the window down to the target's parent; the at-target phase runs the target's own listeners; and, if the event bubbles, the bubbling phase runs non-capture listeners from the parent back up to the window.10,62

Bubbling makes event delegation possible: instead of attaching a listener to every item in a list, attach one to the list and use event.target.closest() to find which item was clicked. The one listener keeps working for items added later.36,65 Not every event bubbles. focus and blur do not, but their twins focusin and focusout do; mouseenter and mouseleave do not, while mouseover and mouseout do; and load on an image does not bubble to the document.10

    3Browser APIs

    The DOM lets a script change the document. The APIs in this section let it do things a document alone cannot: remember data between visits, change the URL without reloading, ask where the user is, move data by dragging and copying, take over the screen, run code on another thread, and define new HTML elements. MDN lists well over a hundred such interfaces; the ones here are those most closely tied to HTML.4

    The demos in this section run in the page you are reading. Some need a secure context or a permission (Table 2), so if one does nothing, the message beside it explains why.

    3.1 Web Storage API

    Web Storage, defined in HTML §12, gives each origin two simple key–value stores, localStorage and sessionStorage. Both implement the same Storage interface: a length property and the methods key(), getItem(), setItem(), removeItem() and clear().19 Keys and values are always strings, so objects must be serialised, usually with JSON.19,66

    The Storage interfaceJS

// Store structured data as JSON

    Web Storage has three properties worth knowing before you rely on it. It is synchronous: every call blocks the main thread while the browser reads or writes, so it suits small values such as preferences, not large data sets, for which IndexedDB is the better tool.66,68 It is small: MDN reports that browsers store up to 5 MiB of local storage and 5 MiB of session storage per origin, and setItem() throws a QuotaExceededError when the limit is reached.19,69 And it can fail: the getters throw a SecurityError when storage is blocked, for example in a sandboxed iframe with an opaque origin or when the user has disabled site data, so production code wraps access in try/catch.19

    3.2 Local Storage

    localStorage is shared by every document of the same origin and has no expiry; data stays until the page's script or the user clears it.19,70 When one document changes it, the browser fires a storage event at the Window of every other same-origin document that uses that storage area. The event carries key, oldValue, newValue, url and storageArea. The document that made the change does not get the event, which makes it a simple way to keep several open tabs in sync.19,71

    Syncing a setting across tabsJS
    function applyTheme(name) { document.documentElement.dataset.theme = name; }

function saveTheme(name) {
  try { localStorage.setItem("theme", name); } catch { /* storage blocked or full */ }
  applyTheme(name);
}

// Fires in *other* tabs of this origin, never in the tab that called setItem()
window.addEventListener("storage", (e) => {
  if (e.key === "theme" && e.newValue) applyTheme(e.newValue);
});

    3.4 History API
    

    Every tab keeps a session history, the list of entries that the Back and Forward buttons move through.     3.5 Geolocation API
    

    The Geolocation API lets a page ask for the device's position. It is a W3C specification (a Candidate Recommendation Draft at the time of writing), exposed as navigator.geolocation, and it works only in secure contexts and only after the user grants permission.8 The position may come from GPS, Wi-Fi, mobile networks or IP address; the API does not say which, but reports an accuracy in metres.8,80

      3.11 Custom Elements
      

      A custom element is an element whose behaviour is defined by a JavaScript class registered with customElements.define().       4HTML and JavaScript
      

      HTML connects to JavaScript in two directions. The script element brings code into the page, and event handler attributes and listeners bring events from the page into code. The HTML Standard defines both, together with the timing rules that decide when each script runs.43,98
      


      4.1 Inline JavaScript
      

      An inline script is a script element whose code is written between its tags. Without a type attribute, or with a JavaScript MIME type such as text/javascript, it is a classic script.43 The parser stops when it reaches the end tag, runs the code, and then continues, so the script can see only the elements above it.34,43
      

      Inline scriptHTML
      <p id="greeting">Hello</p>

</script>
      

      Inline scripts are quick to write and need no extra request, but they cannot be cached separately, and a strict Content Security Policy blocks them unless they carry a matching nonce or hash. CSP exists because injected inline script is the usual payload of a cross-site scripting (XSS) attack.99,100 Inside an inline script, the text </script ends the element wherever it appears, even inside a string, so write it as <\/script>.101

      The async boolean attribute tells the browser to fetch the script in parallel with parsing and to run it as soon as it is available, interrupting the parser briefly if parsing is still going on.43 Several async scripts run in whatever order their downloads finish.       • Top-level await. Modules can use await outside any function.

      Progressive enhancement of a formJS
      const form = document.querySelector("#signup");

  const data = new FormData(form, event.submitter);   // includes the clicked button's name/value

  button.disabled = true;
  try {
    const res = await fetch(form.action, { method: form.method, body: data });
    if (!res.ok) throw new Error(res.statusText);

      5Putting it together: a small task app
      

      The application below uses most of this article in about 70 lines: a module script, a custom element with a shadow root and a slot, a template, form handling with FormData and requestSubmit(), one delegated click listener, a CustomEvent that crosses the shadow boundary, and localStorage with a fallback. It runs in a sandboxed frame without allow-same-origin, so the frame has an opaque origin and localStorage throws a SecurityError.19,85 The app catches it and keeps tasks in memory, which is exactly the defensive pattern section 3.1 recommends; the status line tells you which storage it is using.

  let store, status = "Saved in localStorage.";
  try { store = localStorage; store.setItem("probe", "1"); store.removeItem("probe"); }
  catch (err) { const m = new Map(); store = { getItem: k => m.get(k) ?? null, setItem: (k, v) => m.set(k, String(v)) };
                status = "localStorage unavailable (" + err.name + "); using memory."; }

  let tasks = JSON.parse(store.getItem("tasks") ?? "[]");
  if (!tasks.length) tasks = [{ id: 1, title: "Read about the DOM", done: true }, { id: 2, title: "Try the event lab", done: false }];

  // 2. A custom element with shadow DOM that listens for a composed CustomEvent
  customElements.define("task-counter", class extends HTMLElement {
    constructor() {
      super();
      this.attachShadow({ mode: "open" }).innerHTML =
        `<style>:host{display:block;margin-bottom:6px} output{font-weight:bold;color:#2457a6}</style>
         <slot></slot> · <output>0</output> left`;
    }
    connectedCallback() {
      document.addEventListener("tasks-changed", (e) => {
        this.shadowRoot.querySelector("output").value = e.detail.left;
      });
    }
  });

  // 3. Rendering from a template with textContent (safe for any title)
  const list = document.getElementById("list"), tpl = document.getElementById("item");
  function render() {
    list.replaceChildren(...tasks.map(t => {
      const li = tpl.content.firstElementChild.cloneNode(true);
      li.dataset.id = t.id; li.classList.toggle("done", t.done);
      li.querySelector("input").checked = t.done;
      li.querySelector("span").textContent = t.title;
      return li;
    }));
    store.setItem("tasks", JSON.stringify(tasks));
    document.dispatchEvent(new CustomEvent("tasks-changed", { detail: { left: tasks.filter(t => !t.done).length } }));
  }

  // 4. Form handling
  document.getElementById("add").addEventListener("submit", (e) => {
    e.preventDefault();
    const title = new FormData(e.target).get("title").trim();
    if (title) tasks.push({ id: Date.now(), title, done: false });
    e.target.reset(); render();
  });

  // 5. One delegated listener for every row, present and future
  list.addEventListener("click", (e) => {
    const action = e.target.closest("[data-action]")?.dataset.action;
    if (!action) return;
    const id = Number(e.target.closest("li").dataset.id);
    if (action === "delete") tasks = tasks.filter(t => t.id !== id);
    if (action === "toggle") tasks = tasks.map(t => t.id === id ? { ...t, done: !t.done } : t);
    render();
  });

  render();
</script>
