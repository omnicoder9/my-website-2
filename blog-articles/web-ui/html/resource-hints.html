Resource Hints

How to tell the browser what it is going to need before it finds out for itself: dns-prefetch and preconnect for connections; preload, modulepreload and fetchpriority for the current page; prefetch, the retired prerender and the Speculation Rules API for the next one; Link headers and 103 Early Hints on the server; and the pitfalls, measurements and browser support that decide whether a hint helps or hurts. Grounded in the WHATWG HTML and Fetch standards, the IETF RFCs, browser compatibility data, vendor documentation and a real measured experiment.

Updated 17 November 202669 references (Vancouver style)Includes exercises, trivia, a measured experiment, a hint checker, a support detector and a playground

Earlier articles in this series met the link element as a way to attach metadata and stylesheets, and looked at how images and media are fetched. This article is about a different family of rel values whose only job is speed. A resource hint tells the browser something about the future: which servers it will talk to, which files the page will need, or which page the user is likely to open next. The browser could find all of this out by itself, but only later, and on the web "later" is measured in network round trips. The HTML Standard lists these keywords alongside the other link types, and most of them are explicitly allowed to be ignored.1,2

Section 1 explains why hints exist and what a connection costs. Section 2 covers connection hints, section 3 the hints that fetch resources for the current page, and section 4 the hints that prepare the next navigation. Section 5 moves the hints into HTTP headers and 103 Early Hints. Sections 6 to 8 cover pitfalls, measurement and browser support, section 9 combines everything into one page, and sections 10 to 14 hold exercises, trivia, a hint checker, a playground and a quick reference.

1Introduction

1.1 The discovery problem

A browser can only fetch what it knows about. It learns about resources by parsing HTML, and while the main parser is blocked (for example by a synchronous script) a second, simpler parser called the preload scanner reads ahead through the raw markup and starts fetching the src and href URLs it finds.4 The scanner only reads HTML. It cannot see a font or background image that is referenced from a stylesheet, a script that another script injects, an image that a framework renders on the client, or an image whose real URL sits in a data-src attribute for a JavaScript lazy loader.4 Each of these is discovered only after something else has arrived and been processed, which puts it at the end of a request chain.

The HTTP Archive measures how common the problem is for the element that usually matters most. In 2024, 35% of mobile pages had a Largest Contentful Paint (LCP) element that was not statically discoverable in the HTML.5 Figure 1 shows the typical chain for a web font: HTML, then CSS, then the font, each waiting for the previous one.

1.2 What a connection costs

Fetching from a new origin costs more than the request itself. The browser must resolve the host name with DNS, open a TCP connection, which starts with a three-way handshake and therefore costs one full round trip before any data can be sent, and then negotiate TLS.7 A full TLS 1.2 handshake adds two more round trips, TLS 1.3 reduces the full handshake to one, and QUIC, used by HTTP/3, combines the transport and cryptographic handshakes into one.8–10 Latency, not bandwidth, is the bottleneck for most pages: even the speed of light in fibre puts New York and London 56 ms apart for a round trip.11 Google's web.dev guidance puts a typical DNS lookup at 20 to 120 ms and the saving from a preconnect at 100 to 500 ms.12

2Connection hints



2.1 dns-prefetch


The dns-prefetch keyword "specifies that the user agent should preemptively perform DNS resolution for the target resource's origin". Its processing model is short: parse the href, work out the network partition key for the document, and then the user agent "should resolve an origin" for that URL; because the result can be cached, later fetches to the origin can be faster.13 Only the host matters, so the path is ignored and the usual form is just the origin.



DNS pre-resolution for third-party originsHTML
<link rel="dns-prefetch" href="https://cdn.example">
<link rel="dns-prefetch" href="https://analytics.example">
<p>(Nothing visible: a dns-prefetch hint has no rendering.)</p>
Rendered in your browser



(Nothing visible: a dns-prefetch hint has no rendering.)



It is the cheapest hint and the oldest: Chrome resolved host names from links on a page before the keyword was standardised, and the Chromium design document describes an X-DNS-Prefetch-Control response header with the values on and off, and notes that by default Chromium does not pre-resolve host names found in hyperlinks on HTTPS pages.28,44 Firefox long supported the explicit hint on HTTP pages only, and extended it to HTTPS pages in version 127.45



2.2 preconnect


preconnect goes further: the user agent "should obtain a connection" to the origin, and "should attempt to initiate a preconnect and perform the full connection handshake", although it may perform only part of the handshake or skip it entirely, and must not delay the load event for it.14 Web.dev reports that Chrome closes a preconnected connection that is not used within 10 seconds, so a preconnect for something the page will not use soon is wasted work.12



Preconnect to the origins on the critical pathHTML
<!-- Images come from an image CDN: no credentials, no CORS -->
<link rel="preconnect" href="https://img.cdn.example">

<!-- Fonts are always fetched in CORS mode, so match it -->
<link rel="preconnect" href="https://fonts.cdn.example" crossorigin>

<!-- Fallback for browsers without preconnect: separate elements -->
<link rel="dns-prefetch" href="https://img.cdn.example">



Why crossorigin matters on a preconnect


Browsers keep separate connections for requests that are sent with credentials (cookies and the like) and requests that are not. The preconnect algorithm starts with useCredentials set to true and sets it to false only when the crossorigin attribute is in the Anonymous state and the target is cross-origin.14,46 Fonts and fetch() calls to another origin use CORS without credentials by default, so a preconnect without crossorigin warms the wrong pool. In web.dev's words, without the attribute the browser "only performs the DNS lookup" for those requests.12 If an origin serves both kinds of request, use two hints, one with and one without the attribute.





Do
Preconnect to the two or three origins that serve render-critical resources, issued as early as possible in the head or in a header.12


Don't
Combine the keywords as rel="preconnect dns-prefetch": web.dev reports that this cancels the preconnect in Safari. Use two link elements instead.12





2.3 Choosing origins


Each preconnect costs CPU on the client and a socket on the server, and web.dev warns that preconnecting to too many origins can cause bandwidth contention.12 A practical rule follows from the 10-second idle limit: preconnect only to origins whose first request starts within the first few seconds and is not already discoverable early in the HTML. Use dns-prefetch for origins that matter later or less (an analytics endpoint, a chat widget), because a DNS answer is cheap to hold. There is no point in preconnecting to the page's own origin: that connection already exists.

3Fetching for the current page



3.1 preload


preload is not optional. The link-type table says the user agent "must preemptively fetch and cache the target resource for current navigation according to the preload destination given by the as attribute", and web.dev puts the difference bluntly: "Preload is a mandatory fetch, not a hint."1,40 It fetches a resource that the page will certainly need but that the browser would otherwise discover late: a font named in CSS, a hero image set as a CSS background, a script that a loader will inject, or JSON that the first render depends on.



Typical preloadsHTML
<head>
  <link rel="preload" href="/fonts/brand.woff2" as="font" type="font/woff2" crossorigin>
  <link rel="preload" href="/img/hero.avif" as="image" type="image/avif" fetchpriority="high">
  <link rel="preload" href="/api/menu.json" as="fetch" crossorigin>
  <link rel="stylesheet" href="/css/site.css">
</head>



A preload only fetches. It does not apply a stylesheet, run a script or render an image; the resource sits in the document's memory until something on the page asks for the same thing, and then the stored response is used instead of a new request.6 The link element fires load when the response arrives and error on a network error, which lets a script apply a preloaded stylesheet once it is ready.6

3.2 The as attribute and how a preload is matched


The as attribute "must be specified" on a preload link, and it has no missing-value or invalid-value default.47 It names one of six preload destinations: fetch, font, image, script, style and track; anything else translates to null and the algorithm simply returns without fetching.6 The destination matters because Fetch uses it to choose the request's default priority and Accept header and the Content Security Policy directive that applies, and because it is part of the key used to match the preload to the later request.6,21



That key is the heart of preload. Each document has a map of preloaded resources, keyed by a preload key made of four fields: the URL, the destination, the request mode (same-origin, cors or no-cors) and the credentials mode.6 When the page later requests a resource, the browser builds the same key; if no entry matches, the preload is not used and the resource is fetched again. A matched entry is removed from the map, so a preload satisfies one request.6 Integrity metadata must also match when the integrity attribute is used.2,6





Two other attributes filter preloads. type is advisory: a user agent that does not support the given MIME type "should not fetch" the resource, which makes it a cheap way to preload a modern image or font format only where it will be used.48 media is prescriptive, so a preload with media="(max-width: 600px)" is fetched only when the query matches.49



3.3 Preloading fonts


Fonts are the classic preload because they are always at the end of a chain: the browser discovers them in CSS, and usually only when it knows a text node uses the face.4,50 Font requests are made in CORS mode, even for same-origin fonts, so a font preload needs crossorigin. Web.dev's warning is explicit: "Fonts preloaded without the crossorigin attribute will be fetched twice!"50 The measured experiment in section 7.1 shows exactly that, and the HTTP Archive's 2021 analysis gives the same warning: if crossorigin is omitted when the eventual request uses CORS, "you will end up with a duplicate request".51



A correct font preloadHTML
<link rel="preload" href="/fonts/brand-latin.woff2" as="font" type="font/woff2" crossorigin>
<style>
  @font-face {
    font-family: Brand;
    src: url(/fonts/brand-latin.woff2) format("woff2");
    font-display: swap;            /* show fallback text while it loads */
    unicode-range: U+0000-00FF;    /* only preload the subset you use first */
  }
</style>



3.4 Images and responsive preload


An img in the HTML is already discoverable, so it rarely needs a preload; fetchpriority="high" is usually the better tool (section 3.6). Preload helps when the important image is a CSS background or is rendered by script. For responsive images, imagesrcset and imagesizes mirror the srcset and sizes attributes of img, so that the preload selects the same candidate that the image will; they may only appear on a preload link whose as is image.52 They are supported from Chrome 73, Firefox 78 and Safari 17.2.53



Responsive preload that matches the imgHTML
<link rel="preload" as="image" fetchpriority="high"
      href="/img/hero-800.jpg"
      imagesrcset="/img/hero-400.jpg 400w, /img/hero-800.jpg 800w, /img/hero-1600.jpg 1600w"
      imagesizes="(max-width: 700px) 100vw, 700px">
<!-- … later, maybe rendered by a framework … -->
<img src="/img/hero-800.jpg" alt="Espresso being poured"
     srcset="/img/hero-400.jpg 400w, /img/hero-800.jpg 800w, /img/hero-1600.jpg 1600w"
     sizes="(max-width: 700px) 100vw, 700px">



Do not lazy-load what you preloadA preloaded LCP image that also has loading="lazy" is fetched early and then rendered late, after layout decides it is in the viewport. In 2022 the HTTP Archive found that only about 1 in 200 mobile pages preloaded their LCP image at all, and that 39% of mobile LCP images were not statically discoverable.54



3.5 modulepreload


ES modules have their own chain problem: a module's imports are discovered only after it is fetched and parsed, so a tree that is three imports deep costs three round trips. modulepreload "must preemptively fetch the module script and store it in the document's module map for later evaluation", and "optionally, the module's dependencies can be fetched as well".1,55 Unlike a plain preload as="script", it fetches with the module script settings (CORS mode, same-origin credentials by default) and puts the parsed result in the module map, so it is always reused by a later <script type="module"> or import.



Flattening a module graphHTML
<!-- app.js imports router.js, which imports store.js -->
<link rel="modulepreload" href="/js/app.js">
<link rel="modulepreload" href="/js/router.js">
<link rel="modulepreload" href="/js/store.js">
<script type="module" src="/js/app.js"></script>



If as is omitted on a modulepreload link it is treated as script.47 Chrome 147 and Safari 26.2 also accept as="json" for JSON modules, and Chrome 147 experimentally accepts as="style" for CSS modules.34 Broad support arrived late: Chrome 66 in 2018, but Firefox only in 115 and Safari in 17, both in 2023.3,34 The HTML Standard does not process modulepreload in Link headers, so it must be in the markup.1



3.6 fetchpriority


Browsers already assign every request a priority; in Chromium, stylesheets in the head and fonts get the highest priority, scripts high or medium, and images low until layout shows they are in the viewport, when they are boosted to high. Since Chrome 117 the first five large images get medium priority from the start.40 The fetchpriority attribute lets the page adjust this. It is an enumerated attribute with three states, high, low and auto; a missing or invalid value means auto.56 It sets the Fetch request's priority, which is one of "high", "low" or "auto", and it is accepted on img, link and script, and as the priority option of fetch().22,40,56 On HTTP/2 and HTTP/3 the browser communicates the result to the server, for example as an RFC 9218 urgency between 0 and 7.25



Raising the LCP image, lowering the restHTML
<img src="/img/hero.jpg" alt="…" fetchpriority="high">

<!-- Carousel slides that are not visible yet -->
<img src="/img/slide-2.jpg" alt="…" fetchpriority="low">
<img src="/img/slide-3.jpg" alt="…" fetchpriority="low">

<!-- A non-critical async script -->
<script src="/js/widget.js" async fetchpriority="low"></script>

<script>
  // Background fetch that must not compete with the page
  fetch("/api/recommendations", { priority: "low" });
</script>



The attribute "is a hint, not a directive"; the browser may ignore it.40 It can be large in practice: Google Flights improved LCP from 2.6 s to 1.9 s in a test by adding fetchpriority="high" to its hero image.40 Adoption has grown quickly: 0.03% of pages used it on the LCP element in 2022, 15% of mobile pages with LCP images in 2024 and 17% in 2025.54,57 Support: Chrome 101, Firefox 132 and Safari 17.2.35

4Preparing the next page



4.1 prefetch


prefetch looks ahead one navigation. It "specifies that the user agent should preemptively fetch and cache the target resource as it is likely to be required for a followup navigation".1 Its fetch is marked with the initiator "prefetch", and user agents "may delay the fetching" so that requests the current document needs go first.15 In Chromium a prefetch runs at the lowest priority.40 More generally, prefetching means "speculatively fetching documents or subresources in the background for pages that the user is likely to navigate to in the near future".58



Prefetching resources for the next step of a flowHTML
<!-- On the cart page: the checkout bundle is very likely next -->
<link rel="prefetch" href="/js/checkout.js">
<link rel="prefetch" href="/css/checkout.css">



Prefetched resources go to the HTTP cache, so they help only if the response is cacheable and the next page asks for the same URL. Browsers mark speculative requests with the Sec-Purpose request header (value prefetch), which lets servers and analytics tell them apart from real visits; Chrome sends it from version 110 and Firefox from 115.23,59 <link rel="prefetch"> has long been supported in Chrome and Firefox, while Safari still has it only behind a setting.60



4.2 The rise and fall of rel="prerender"


In June 2011 the Chromium team announced prerendering: a page could include <link rel="prerender"> and Chrome would load and render the target in a hidden tab, so that following the link was nearly instant; Google Search's Instant Pages used it on search results.29 It shipped in Chrome 13.30 Full prerendering was expensive: Chrome's own figures put it at typically 100 MiB of memory, capped at 150 MiB, which made it unsuitable for devices with 512 MB of RAM or less.33



In December 2017, Chrome 63 replaced it with NoState Prefetch: the keyword still works, but the browser now only fetches the page and its subresources into the cache, without running JavaScript or rendering, using about 45 MiB.30,33 Firefox and Safari never implemented the keyword, and the HTML Standard does not define it as a link type; in October 2025 Chrome marked NoState Prefetch itself as deprecated in favour of speculation rules.1,30,33 Only 0.1% of pages used rel="prerender" in 2021.51



4.3 The Speculation Rules API


Speculation rules are the modern replacement. Instead of a link element, the page includes a <script type="speculationrules"> whose JSON lists which URLs to prefetch (fetch the document only) or prerender (fetch, run and render it in an invisible tab), and how eagerly.39,42 The HTML Standard now defines the rule syntax in §7.6 Speculative loading; it notes that in that standard "prerender" rules are optionally converted to "prefetch", with full prerendering defined by the WICG Prerendering Revamped specification.20,26



List rules and document rulesHTML
<script type="speculationrules">
{
  "prerender": [{
    "source": "list",
    "urls": ["/products/espresso-machine"],
    "eagerness": "immediate"
  }],
  "prefetch": [{
    "where": {
      "and": [
        { "href_matches": "/*" },
        { "not": { "href_matches": "/logout" } },
        { "not": { "href_matches": "/cart/*" } },
        { "not": { "selector_matches": ".no-speculate, [rel~=nofollow]" } }
      ]
    },
    "eagerness": "moderate",
    "tag": "site-wide"
  }]
}
</script>



A list rule names URLs; a document rule uses a where condition (href_matches URL patterns, selector_matches CSS selectors, combined with and, or and not) to pick links that are present in the document.39,42 The source key can be omitted because it is implied by urls or where.39 The optional tag is sent to the server in the Sec-Speculation-Tags request header.61

4.4 Writing prerender-safe pages


A prerendered page runs its scripts before the user sees it, and may never be seen at all. document.prerendering is true while the page is "being presented in a non-interactive prerendering context", and the prerenderingchange event fires when the page is activated; the activation time is recorded as PerformanceNavigationTiming.activationStart.26 Chrome defers APIs that "cause intrusive behaviors (for example, prompts)" until activation, but your own code (analytics, ad impressions, a carousel's autoplay timer) must check for itself.39



Count a page view only when the page is actually shownJS
function onShown(callback) {
  if (document.prerendering) {
    document.addEventListener("prerenderingchange", callback, { once: true });
  } else {
    callback();
  }
}

onShown(() => {
  const nav = performance.getEntriesByType("navigation")[0];
  const wasPrerendered = nav && nav.activationStart > 0;
  sendBeacon("/analytics/pageview", { wasPrerendered });
});



On the server side, the Sec-Purpose header identifies speculative requests, so logs and analytics can count them separately.23,26 Do not speculate on URLs with side effects: HTTP defines GET as a safe method, but a site whose GET /logout or GET /cart/add?id=7 link changes state would have that link "clicked" by the speculation.62 Excluding them with not conditions, as in the example above, is the usual pattern.




5Hints from the server



5.1 The Link header


RFC 8288 defines a Link HTTP header that carries the same information as a link element: a target URI in angle brackets followed by parameters such as rel.24 The HTML Standard processes Link headers on document responses, but "for most link types, this algorithm does nothing": among the hints, only preload and preconnect have header processing.1,63 A preload header without an as parameter is dropped, just like the element, and a media parameter that does not match the environment skips the entry.63



Hints in a response headerHTTP
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Link: <https://fonts.cdn.example>; rel=preconnect; crossorigin
Link: </fonts/brand.woff2>; rel=preload; as=font; type="font/woff2"; crossorigin
Link: </img/hero.avif>; rel=preload; as=image; fetchpriority=high



Headers are seen before the first byte of HTML is parsed, so a header hint is never later than the same hint in the head. Their other advantage is that a CDN or server can add them without changing templates.



5.2 103 Early Hints


The server often needs hundreds of milliseconds of "think time" to build an HTML page, and during that time the connection is idle. RFC 8297 adds an informational status code: "The 103 (Early Hints) informational status code indicates to the client that the server is likely to send a final response with the header fields included in the informational response."18 The server sends a 103 with Link headers immediately, and the final 200 later. The RFC stresses that these fields "only provide hints to the client; they do not replace the header fields on the final response", and it is an Experimental RFC.18

Browsers impose several limits. In the HTML Standard only the first early-hint response in a navigation is handled, its Link headers are processed before those of the final response, and only the as, crossorigin, integrity and type attributes are taken into account.19 Chrome supports only preconnect and preload in early hints, only for top-level navigations, discards their work if the final response redirects to another origin, and recommends sending them over HTTP/2 or HTTP/3 because most browsers only accept them there; the RFC itself warns that some HTTP/1.1 clients mishandle informational responses.18,36 Support: Chrome 103 for both; Firefox 120 for preconnect and 123 for preload; Safari 17 for preconnect only.36,41 Chrome's documentation cites improvements of "several hundred milliseconds" observed by Shopify and Cloudflare.36

      link: [

  const html = await renderProductPage(req);   // the slow part

5.3 Why not HTTP/2 server push?


HTTP/2 server push let a server send responses the browser had not asked for. It was hard to use well, because the server could not know what the browser already had in its cache. Only 1.25% of HTTP/2 sites used it in 2021, falling to 0.7% in a later analysis, and Chrome disabled it by default in version 106; Chrome's announcement names 103 Early Hints as "a much less error-prone alternative".37 The difference is who decides: with push the server sends bytes; with a hint the browser decides whether to fetch, and can use what it already has.




6Pitfalls


Hints are cheap to write and easy to get wrong. A wrong hint is not neutral: a preload is a mandatory high-priority fetch, so a useless one takes bandwidth and connection slots from resources that matter.1,40



6.1 Unused preloads


If nothing on the page uses a preloaded resource, Chrome logs a console warning about three seconds after the load event.50 In the experiment for this article Chromium 153 printed:


The resource http://127.0.0.1:8077/unused.js was preloaded using link preload but not used within a few seconds from the window's load event. Please make sure it has an appropriate `as` value and it is preloaded intentionally.


In 2021 the HTTP Archive found that 21.5% of preload hints were unused within the first three seconds of loading.51 Common causes: a URL with a different query string or a cache-busting hash, a resource that is only used on some breakpoints, a component that was removed while its preload stayed in the template, and a preload that should have been a prefetch for the next page.



6.2 Double fetches


A preload that does not match the later request by URL, destination, mode and credentials mode is not used, and the resource is downloaded twice.6 The typical mismatches:


    

  • Missing crossorigin on fonts and on as="fetch" preloads for CORS requests. Chromium 153 reported it as: "A preload for 'http://127.0.0.1:8077/brand.ttf' is found, but is not used because the request credentials mode does not match. Consider taking a look at crossorigin attribute."50,51
    • 

  • Wrong or missing as. Per the standard an invalid destination means nothing is fetched; web.dev notes that in practice an omitted or invalid as can make scripts download twice.6,50
    • 

  • A different responsive candidate. A preload of hero-800.jpg without imagesrcset is wasted if the img picks hero-1600.jpg on a large screen.52
    • 

  • Uncacheable responses for prefetch and early hints. Chrome's early hints documentation warns that preloaded resources must be cacheable or they are fetched again.36
    • 




6.3 Too many hints


Preloading everything is the same as preloading nothing, only slower. Each preload raises a resource above others that the browser would have scheduled sensibly. On HTTP/1.1 the browser also has a limited number of connections per host: in a first version of the experiment, with a stylesheet, five images and a preloaded font all on one HTTP/1.1 origin, the last image could not start until 512 ms, when a connection became free, while the others started at about 260 ms. Preconnects have a similar cost: web.dev advises preconnecting only to critical origins, since an unused connection is closed after 10 seconds and too many can cause bandwidth contention.12





Do
Hint the one to three resources that are late-discovered and on the critical path for the first render: usually the LCP image, the main font and, for single-page apps, the main script or data.40,50


Don't
Preload what the preload scanner already finds early (an img or script near the top of the HTML), or lazy-load the image you preloaded.4,54

7.2 Resource Timing in the field


The Resource Timing API exposes one PerformanceResourceTiming entry per fetch. Its initiatorType is "link" for a request made by a link element, so a preloaded resource shows up as link and a duplicate request shows up as a second entry for the same URL.27 renderBlockingStatus says whether the resource could block rendering, deliveryType is "cache" when it came from the cache, and nextHopProtocol shows the HTTP version.27,64 For prerendered pages, subtract activationStart from paint timings, because the page was loaded before the user asked for it.26,65



Find duplicate and late resources in real user sessionsJS
const seen = new Map();
new PerformanceObserver((list) => {
  for (const e of list.getEntries()) {
    const n = (seen.get(e.name) || 0) + 1;
    seen.set(e.name, n);
    if (n === 2) report("duplicate-fetch", e.name, e.initiatorType);
  }
}).observe({ type: "resource", buffered: true });

new PerformanceObserver((list) => {
  const lcp = list.getEntries().at(-1);
  const nav = performance.getEntriesByType("navigation")[0];
  const res = performance.getEntriesByName(lcp.url)[0];   // the LCP image's fetch
  report("lcp", {
    time: lcp.startTime - (nav.activationStart || 0),     // corrected for prerender
    imageRequestStart: res && res.requestStart,           // how early was it fetched?
    initiator: res && res.initiatorType                   // "link" if preloaded
  });
}).observe({ type: "largest-contentful-paint", buffered: true });



7.3 Lab, field and experiments


A single local run, like the one above, shows the mechanism; it does not show the effect on real users. A sensible workflow is:


    

  1. Find the chain in a lab tool's waterfall (browser developer tools or a hosted test service): which critical resource starts late, and what does it wait for?4
    2. 

  2. Add one hint and re-run under a throttled network profile several times, since single runs vary.
    3. 

  3. Check for side effects: duplicate entries, the console warnings in section 6, and resources that became slower.
    4. 

  4. Measure in the field with Resource Timing and LCP from real users, ideally as an A/B test, because the benefit depends on users' networks, caches and devices. The Google Flights result in section 3.6 came from exactly such a comparison.40

Exercise 2: Why is the font downloaded twice?


Exercise 2HTML
<link rel="preload" href="https://fonts.cdn.example/inter.woff2" as="font">
<link rel="stylesheet" href="https://fonts.cdn.example/inter.css">


Show solution


The preload has no crossorigin, so it is a no-cors request with credentials, while the font that the stylesheet requests is a CORS request. The preload key's mode and credentials mode differ, so the preloaded response is not used.6,46 Add crossorigin (and type="font/woff2"). Exercise 5: Preload a CSS background hero
