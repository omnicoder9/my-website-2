The Browser Rendering Pipeline

What happens between an HTML document and the pixels on your screen: the CSS Object Model and style calculation, the layout tree, layout and reflow, paint and painting order, layers, rasterization and compositing; the event loop, requestAnimationFrame() and the frame budget; invalidation and layout thrashing; how the pipeline shows up in performance metrics; and how Blink, Gecko and WebKit organise the same work differently. Grounded in the WHATWG HTML Standard, the W3C CSS and performance specifications, and the engineering documentation published by the Chromium, Mozilla and WebKit projects.

Updated 17 November 202676 references (Vancouver style)Includes exercises, trivia, live pipeline demos, a render-tree inspector and a playground

Earlier articles in this series were about what you write: documents, semantic elements, media and the DOM APIs that scripts use to change a page. This one is about what the browser does with it. The companion articles on the HTML parsing algorithm and on DOM construction cover how bytes become a tree of nodes. This article picks up at that point and follows the tree through every later stage until it is a frame of pixels, and then explains why a page that changes one class name might redo all of that work, part of it, or almost none.1,2

Section 1 gives the big picture and a short history. Sections 2 to 4 walk the pipeline stage by stage: style, layout, then paint, layers, rasterization and compositing. Section 5 places the pipeline inside the event loop and explains frames, requestAnimationFrame() and long tasks. Section 6 covers invalidation, layout thrashing, containment and the metrics that measure rendering. Section 7 compares the engines. Section 8 follows one click through a whole frame, and sections 9 to 13 hold exercises, trivia, a pipeline lab, a playground and a quick reference.

Standards and enginesThe HTML Standard defines when a browser renders (the "update the rendering" step of the event loop) and the CSS specifications define what the result must look like. How an engine gets there, with which trees, threads, caches and GPU tricks, is left to the implementation.3–5 Where this article describes internals, it names the engine and cites that project's own documentation; the stage names differ between engines even when the work is the same.

1Introduction

1.1 From bytes to pixels

A browser that loads a page has to turn a stream of bytes into a picture, and then keep that picture up to date as scripts run, the user scrolls, animations tick and images arrive. The work is divided into stages that each take one data structure and produce the next.1,6 In broad strokes, every modern engine does the following:

  1. Parse HTML into a DOM tree of element and text nodes, and parse CSS into style sheets that scripts can reach through the CSS Object Model (CSSOM).7,8
  2. Calculate style. Match selectors to elements and run the cascade to give every element a computed value for every CSS property.4,9
  3. Build a layout tree (the "render tree" or "box tree") of the boxes that will actually be drawn. Elements with display: none are left out, and pseudo-elements such as ::before are added.10,11
  4. Lay out the boxes: compute each box's size and position from the viewport width, the formatting context it lives in and its content.5,12
  5. Paint: record, in the right stacking order, the drawing operations needed for each box. In current engines this produces a display list, not pixels.13,14
  6. Split into layers that can move independently, rasterize them into pixels (usually in tiles, often on the GPU), and composite the layers into the final frame.14,15

Then the browser waits for the next change. Most changes only invalidate part of this work, and much of the craft of front-end performance is choosing changes that invalidate as little as possible.2,16

1.2 The pipeline at a glance

Two properties of this diagram matter more than any single stage. First, each stage depends on the ones before it: layout needs computed styles, paint needs geometry, and raster needs a display list. A change early in the pipeline therefore forces all later stages to run again for the affected region. Second, the top row shares one thread with your JavaScript. While a script runs, the main thread cannot calculate style, lay out or paint, and only work that has already been handed to the compositor (scrolling, and some animations) can keep moving.6,14,17

Web performance guides compress this into the pixel pipeline: JavaScript → Style → Layout → Paint → Composite. A visual change does not have to run all five. Changing a geometric property such as width runs everything; changing only a paint property such as color skips layout; changing transform or opacity on an element that has its own layer can skip both layout and paint.2,16

1.4 A short history

Early browsers painted directly to the screen from the main thread. The design that every engine shares today, with a separate compositor, GPU rasterization and a display list between paint and pixels, arrived gradually through the 2010s.15,29

WebKit began as Apple's fork of KDE's KHTML engine and shipped with Safari in 2003.30 Google built Chrome on WebKit in 2008 and forked it as Blink in April 2013, citing Chromium's multi-process architecture as a reason the two projects had diverged.32 Mozilla's Gecko took a different route: its research engine Servo, written in Rust, produced components that moved into Firefox, most visibly the parallel style engine Stylo in Firefox 57 and the GPU renderer WebRender.31,33,36 Inside Chromium, the multi-year RenderingNG project rebuilt layout, paint and compositing around immutable data structures and clear stage boundaries.29,37

1.5 Recap: parsing and the DOM

The parsing and DOM-construction articles cover the first stage in depth; three facts from them matter here. First, the HTML parser is incremental: it can hand a partial DOM to the rest of the pipeline before the document has finished downloading, so a long page can render its top before its bottom arrives.7,38 Second, a classic <script> without async or defer stops the parser until it has been fetched and run, because it might call document.write(); and a script that runs after a style sheet has to wait for that style sheet, because it might ask for computed style.38,39 Third, the DOM is a live data structure. Every later stage is a cache derived from it, and every DOM or style change has to mark part of that cache as stale.40,41

Critical rendering pathThe order in which HTML, CSS and scripts are fetched and the tricks that get the first frame on screen sooner (render-blocking resources, async and defer, critical CSS, preloading) belong to the separate article on the critical rendering path. Section 6.5 here only summarises them.11,42

2Style

Style calculation answers one question for every element in the DOM: what is the value of every CSS property? Browsers support several hundred properties, so the answer is large, and computing it quickly is one of the main jobs of a rendering engine.4,33

2.1 CSS parsing and the CSSOM

Style sheets reach the engine from <link rel="stylesheet">, <style> elements, style attributes and the browser's own user-agent style sheet. Each is tokenized and parsed according to CSS Syntax into rules, and the CSS Object Model exposes the result to scripts as CSSStyleSheet objects with a cssRules list.8,38 Unlike the HTML parser, the CSS parser cannot render anything from half a style sheet: a later rule can override an earlier one, so a sheet is only useful once it is complete. That is why style sheets in the <head> are render-blocking by default.38,42

The CSSOM is live in both directions. Scripts can read and edit rules, and the engine notices changes and recalculates style. A constructable style sheet can be created with new CSSStyleSheet() and adopted by a document or shadow root without any <style> element at all.8

Reading and changing the CSSOMJS
const sheet = document.styleSheets[0];
console.log(sheet.cssRules[0].selectorText);   // "body"
sheet.insertRule(".note { color: teal }", sheet.cssRules.length);

// Constructable style sheets (no <style> element needed)
const extra = new CSSStyleSheet();
extra.replaceSync("h1 { letter-spacing: .02em }");
document.adoptedStyleSheets = [...document.adoptedStyleSheets, extra];

2.2 Selector matching

For each element the engine must find every rule whose selector matches it. Doing this naively, by testing every selector against every element, would be quadratic. Engines instead index rules by the rightmost part of their selector (the key selector): rules ending in an ID go in an ID map, rules ending in a class in a class map, and so on, so an element only tests the rules that could possibly apply.1 A selector such as .menu a span is then checked from right to left: the engine starts at a span and walks up through ancestors looking for an a and then a .menu.1,43 That walk is why the guidance on style performance is to keep selectors simple, to reduce the number of elements whose style is invalidated by a change, for example by matching elements with a single class rather than long descendant chains.43

Engines add further shortcuts that never change the result. Gecko's Stylo, for example, keeps a style sharing cache so that sibling elements with the same attributes and matching rules can share one computed style, and a rule tree that stores each distinct sequence of matched rules once; it also computes styles for different subtrees in parallel on several CPU cores.33

2.3 The cascade and value stages

Several declarations usually target the same property on the same element. The cascade picks one by comparing, in order: origin and importance (user-agent, user and author, with !important reversing the order), context (shadow trees), the style attribute, cascade layers (@layer), specificity, and finally the order of appearance.4,9 Properties with no winning declaration inherit from the parent if they are inherited properties (such as color and font-size) or take their initial value if not (such as border and display).4

CSS Cascading and Inheritance then describes a chain of values, each refined from the one before. Seeing the chain explains where in the pipeline each kind of value can be known.4

2.4 Style recalculation in practice

Style is not computed once; it is recalculated whenever something that affects it changes. Adding a class, changing an attribute that a selector depends on, hovering over an element with a :hover rule, resizing the viewport across a media-query boundary or loading a new style sheet can all make computed styles stale.37,43 The cost of a recalculation is roughly the number of elements whose style must be recomputed times the cost of matching rules for each. Changing a class on <body> can invalidate every element in the document; changing a class on a leaf usually affects only that element and perhaps its siblings.43 Section 6.1 returns to invalidation in detail.

Where it shows upIn the Chrome DevTools Performance panel, this stage appears as Recalculate Style; in Firefox's profiler as Styles. The event lists how many elements were affected, which is the first number to look at when style is slow.43,45

3Layout

3.1 The layout tree

Computed style says what each element should look like, but not every element produces something to draw, and some things that are drawn are not elements. The engine therefore builds a separate tree of boxes. The CSS specifications call it the box tree; WebKit and early Chrome called it the render tree of render objects, Chromium now calls it the layout tree, and Gecko calls it the frame tree of frames.1,10,41

  • An element whose display is none generates no box, and neither do its descendants. Hidden elements with visibility: hidden or opacity: 0 still generate boxes and take up space.10,11
  • An element with display: contents generates no box of its own, but its children do, as if they were children of its parent.10
  • Elements in the <head>, <script> elements and others hidden by the user-agent style sheet generate no boxes.11,46
  • ::before, ::after and ::marker pseudo-elements generate boxes that have no DOM node.10
  • Text gets its own boxes, and the engine adds anonymous boxes to keep the tree well formed, for example a block box around loose text that sits next to a block sibling.5

The render-tree inspector in section 11 builds this tree from any HTML you type, using the computed display of each element in a real document.

3.2 How layout works

Layout computes the position and size of every box. It starts at the root with the size of the viewport (the initial containing block) and works down the tree.5,12 In the common case of block layout, a parent tells each child how much inline space (width, in horizontal writing) it has; each child lays out its own children, works out its block size (height) from its content, and reports back; the parent then places the child below the previous one and adds its height to its own.1,5 Other layout modes, such as inline, flex, grid, table and multi-column layout, follow their own algorithms inside a formatting context, which is a region where one set of layout rules applies and from which floats and margins do not leak.5,10

Most layout is a single top-down pass, but some layout modes measure children more than once. A flex container may lay out each item once to find its natural size and again at its flexed size; a table measures every cell before it can choose column widths. Nesting such containers can multiply the work.12 Chromium's LayoutNG engine, which replaced Blink's legacy layout code, makes the output of layout an immutable fragment tree of positioned boxes and caches results by input constraints, so a child whose constraints have not changed can be reused instead of laid out again.12,41

Text makes layout expensive. To place text the engine has to shape it (turn characters into positioned glyphs using the font, which is complicated for scripts such as Arabic and Devanagari), find line-break opportunities and handle bidirectional text, all before it knows how tall a paragraph is.1,12

3.3 Reflow and incremental layout

Laying out the whole document again after every change would be far too slow, so engines do incremental layout. When a change affects geometry, the engine marks the box concerned as needing layout and marks each ancestor as having a child that needs layout (a "dirty bit" system); the next layout pass then visits only the dirty paths.1 A change that affects everything, such as a new font size on the root, a different viewport width or a newly loaded style sheet, triggers a global layout instead.1,47 Gecko's name for layout is reflow, and the two words are used interchangeably in performance writing.1,44

How far a change spreads depends on how much the box can affect its neighbours. Changing the height of one paragraph moves everything after it in the same flow and can change the height of every ancestor, while a box with a fixed size, or one isolated with CSS containment (section 6.2), keeps the effect inside itself.22,47

3.4 Forced synchronous layout and layout thrashing

Normally the engine lays out lazily, once per frame, just before paint. But scripts can ask geometric questions at any time: offsetWidth, getBoundingClientRect(), scrollTop, getComputedStyle() for a layout-dependent property, innerText and many more. If the DOM or style has changed since the last layout, the engine must run style and layout right now, inside the script, to answer correctly. That is a forced synchronous layout (or forced reflow).44,47

One forced layout is often harmless. The problem is a loop that alternates writes and reads, because every read after a write forces another full style-and-layout pass. That pattern is layout thrashing.47

Thrashing: read, write, read, write

N forced layoutsJS
for (const box of boxes) {
  // read (forces layout if anything is dirty)
  const w = box.parentElement.offsetWidth;
  // write (makes layout dirty again)
  box.style.width = (w / 2) + "px";
}

Batched: all reads, then all writes

One layoutJS
const widths = boxes.map(b => b.parentElement.offsetWidth);
boxes.forEach((box, i) => {
  box.style.width = (widths[i] / 2) + "px";
});
// layout runs once, before the next paint

4Paint, layers and compositing

After layout, the engine knows where every box is. The remaining stages turn that geometry into pixels, and they are where modern engines differ most from the textbook description of "paint the render tree to the screen".14,15,36

4.1 Paint and display lists

In current engines, paint does not produce pixels. It walks the layout tree and records a list of drawing commands, such as "fill this rectangle with this colour", "draw these glyphs at this position" or "draw this image clipped to this rounded rectangle". The result is called a display list (Gecko, WebRender) or a list of display items and paint ops (Chromium).14,49,50 Recording first and drawing later has several benefits: the list can be replayed at a different scale, split across threads, compared with the previous frame to find what changed, and rasterized on the GPU.14,36

Chromium also produces property trees during paint, four separate trees for transforms, clips, effects (opacity, filters, blending) and scrolling, so that later stages can apply these properties without walking the layout tree again.41

4.2 Painting order and stacking contexts

The order of commands in the display list decides what ends up on top. CSS 2.1 Appendix E defines it. Within each stacking context, the engine paints from back to front:13

  1. the background and borders of the element that forms the stacking context;
  2. child stacking contexts with negative z-index, most negative first;
  3. in-flow, non-positioned, block-level descendants (backgrounds and borders);
  4. non-positioned floats;
  5. in-flow inline content: text, images and inline blocks;
  6. positioned descendants with z-index: auto or 0, in tree order;
  7. child stacking contexts with positive z-index, lowest first.

A stacking context is atomic: its contents are painted together, and nothing outside can be placed between them. That explains the most common z-index surprise, an element with z-index: 9999 that still sits below another element, because its parent forms a stacking context that is itself below.13,51 Besides positioned elements with a z-index, many properties create a stacking context: opacity less than 1, any transform, filter, mix-blend-mode, isolation: isolate, contain: paint, will-change naming such a property, and position: fixed or sticky.20,23,51

4.3 Layers and compositing

If the whole page were one image, scrolling it or fading one element would mean painting and rasterizing everything again. Engines therefore divide the page into layers (Chromium: composited layers, earlier GraphicsLayers) that are rasterized separately and then combined, or composited, into the final frame.14,15 Moving, scaling, rotating or fading a layer only changes how the compositor draws its existing pixels; nothing has to be painted again. This is why transform and opacity animations can run smoothly even when the main thread is busy.6,16

Which parts of the page get their own layer is a heuristic decision made by the engine (layerization in RenderingNG). Common reasons in Chromium include: a 3D or animated transform, an animated opacity or filter, will-change: transform or opacity, <video>, WebGL and accelerated <canvas>, iframes, scrolling containers, fixed-position elements, and content that overlaps something that is already in a layer.15,16,23 The last reason is easy to trigger by accident: if one element with a high z-index is promoted, elements painted after it that overlap it may have to be promoted too, which can lead to a layer explosion of hundreds of layers.15,16

Asking for a layerCSS
/* Tell the engine ahead of time that this element's transform will change */
.drawer { will-change: transform; }

/* The old hack: a no-op 3D transform also forces a layer (avoid if will-change works) */
.legacy { transform: translateZ(0); }

/* Better: add the hint only while it is needed */
.drawer.is-opening { will-change: transform; }

Layers are not free. Each one needs GPU memory for its pixels (a full-screen layer on a 1080 × 2400 phone at 4 bytes per pixel is about 10 MB) and time to manage, so the guidance is to promote only elements that will actually animate, and to remove will-change when the animation ends.16,23,52

4.4 Rasterization

Rasterization executes the display list to fill in actual pixels. Chromium splits each layer into tiles and rasterizes only tiles that are visible or near the viewport, prioritising the ones on screen; it uses the Skia graphics library, usually on the GPU, and runs raster on worker threads or in the GPU process rather than on the main thread.14,17,54 Images are decoded during or before raster, which is why a large image can cause a checkerboard flash of empty tiles while scrolling quickly. Gecko's WebRender takes the GPU approach further: it sends the display list to the GPU and draws the whole visible scene there each frame, much as a game engine does, instead of keeping painted layers.36,49

Raster is where geometry finally meets the pixel grid. A shape edge that crosses a pixel only partly covers it, so the rasterizer computes a coverage value and blends the colour (anti-aliasing). Text is rasterized from glyph outlines, often with hinting and subpixel positioning. 4.5 The compositor thread and drawing the frame

When the main thread finishes paint, it commits the result (layers, display lists and property trees) to the compositor thread. From then on the compositor owns a copy and can produce frames without the main thread.14,17 For each frame the compositor decides which tiles to rasterize, waits for the new tiles (Chromium activates a pending tree only when enough of it is ready, so you never see a half-updated frame), and produces a compositor frame: a list of textured quads with their transforms. In Chromium, frames from the page, from cross-origin iframes in other processes and from the browser's own UI are aggregated by the Viz service in the GPU process and drawn to the screen.6,14

Because the compositor holds the scroll tree and the layers, it can handle scrolling itself: when you scroll, it moves the scrolling layer and draws a new frame, and only later tells the main thread. That is threaded scrolling. It breaks when a page registers a non-passive touchstart or wheel listener, because the compositor must then wait for the main thread to see whether the listener calls preventDefault().17,55

// The browser can scroll immediately, without waiting for this listener.

5Frames and the event loop

The pipeline does not run whenever it likes. In the HTML Standard, rendering is one step of the event loop, the same loop that runs your tasks, timers and event handlers. Knowing where in that loop rendering happens explains when your code's changes become visible and why some code janks.18,56

5.1 The event loop and "update the rendering"

A window event loop repeats a simple cycle. It picks one task from a task queue (a click handler, a setTimeout() callback, a network response, a parser chunk) and runs it to completion; then it runs every pending microtask (promise reactions, queueMicrotask(), mutation observers) until the microtask queue is empty; then, if this is a rendering opportunity, it runs the update the rendering steps.18,57 A rendering opportunity usually comes once per display refresh (60 times a second on a 60 Hz screen) and is skipped while a document is hidden; the browser may also skip a frame if nothing has changed.3,48

The update-the-rendering steps run, for each document that is being rendered, in a fixed order that the specification defines. Simplified:3

  1. run the resize steps (fire resize if the viewport changed);
  2. run the scroll steps (fire pending scroll and scrollend events);
  3. evaluate media queries and report changes to MediaQueryList listeners;
  4. update animations and send animation events (CSS animations, transitions, Web Animations);58
  5. run the fullscreen steps;
  6. run the animation frame callbacks (requestAnimationFrame());19
  7. recalculate style and layout, then deliver ResizeObserver notifications, repeating while observers change sizes at deeper levels of the tree;59
  8. run the IntersectionObserver update steps;
  9. record paint timing (first paint and first contentful paint);24
  10. update the rendering: paint and present the frame.

Two consequences follow. First, nothing you change in a task is painted until the task (and its microtasks) ends. Setting el.style.display = "block" and then "none" in the same task never shows the element. Second, if a task takes 200 ms, the page cannot produce a frame for 200 ms: animations driven by the main thread stop, and clicks wait in the queue.56,61

5.2 requestAnimationFrame()

requestAnimationFrame(callback) asks the browser to run callback during the next update-the-rendering step, just before style, layout and paint. That makes it the right place to make visual changes from JavaScript: the change is applied once, at the latest moment, and lands in the very next frame.19,48 All callbacks registered for one frame receive the same DOMHighResTimeStamp, which marks the start of that frame, so animation code should compute positions from the timestamp rather than assume a fixed interval.19,48 Browsers pause animation frame callbacks in background tabs and hidden iframes to save power.48

A time-based animation loopJS
const box = document.querySelector(".box");
let start;
function step(now) {                  // now = frame start time (ms)
  start ??= now;
  const t = Math.min((now - start) / 1000, 1);   // 0 → 1 over one second
  box.style.transform = `translateX(${t * 300}px)`; // composite-only change
  if (t < 1) requestAnimationFrame(step);
}
requestAnimationFrame(step);

A common mistake is to use setTimeout(fn, 16) for animation. Timers are not aligned with the display, so some frames get two updates and others none, and the motion stutters; on a 120 Hz display the animation also runs at half the possible rate.2,48 Another is to read layout in a requestAnimationFrame() callback after writing to the DOM, which forces layout in the middle of the frame; the usual pattern is to read in one callback and write in the next, or to read before writing.47

5.3 The frame budget

At 60 frames per second, each frame has 1000 ÷ 60 ≈ 16.7 ms. The browser needs part of that time for its own work, so the RAIL model recommends that your code finish within about 10 ms per frame during animations.2,62 On a 120 Hz display the budget halves to 8.3 ms. When a frame's work overruns, the browser misses the display's refresh and shows the previous frame again; the user sees that as jank.2

The frame meter in section 11 measures the interval between your browser's animation frames and lets you block the main thread for a chosen time, with one animation driven from the main thread and one composited, so you can watch only one of them stop.

5.4 Observers and idle callbacks

Several modern APIs exist so that scripts do not have to force layout to learn about geometry. ResizeObserver reports size changes once per frame, after layout, which makes it safe to use in place of polling offsetWidth; if a callback changes sizes again, the browser re-runs layout and delivers the new notifications, but only for elements deeper in the tree, and stops with the error "ResizeObserver loop completed with undelivered notifications" to avoid an infinite loop.3,59 IntersectionObserver reports visibility changes, also computed during the rendering steps rather than on every scroll event.3 requestIdleCallback() runs low-priority work in the idle time between frames, with a deadline that is never more than 50 ms away so that the page stays responsive to new input.60

5.5 Long tasks and responsiveness

A long task is one that keeps the main thread busy for more than 50 ms. While it runs, input cannot be processed and no new frame can be produced. The standard remedy is to break work into smaller tasks and yield to the event loop between them, so that rendering and input can run in the gaps; scheduler.yield() does this while keeping the continuation near the front of the queue.28,61 The Long Animation Frames API (LoAF) reports frames whose total work exceeded 50 ms and attributes the time to the scripts involved, which is more useful than the older Long Tasks API because it includes the rendering work in the frame.28

Yielding inside a long loopJS
async function processAll(items) {
  let last = performance.now();
  for (const item of items) {
    process(item);
    if (performance.now() - last > 8) {          // stay well under one frame
      await (globalThis.scheduler?.yield?.() ?? new Promise(r => setTimeout(r)));
      last = performance.now();
    }
  }
}

6Invalidation and performance

Every stage of the pipeline produces a cache: computed styles, the layout tree, fragments, display lists, layers, tiles. Invalidation is the bookkeeping that decides which parts of those caches a change has made stale, and it is where most rendering performance is won or lost.37,41

6.1 Style invalidation

When a class, attribute or state changes, the engine must find which elements' styles could be affected. Blink precomputes invalidation sets from the style sheets: for each class, ID or attribute that appears in a selector, which elements (the element itself, its descendants or its siblings) need their style recalculated when it changes. A rule such as .dark .card means that toggling dark on an element invalidates all its descendants with class card; a rule such as .dark * invalidates every descendant.37,43 Selectors such as :has() let a change on a descendant affect an ancestor's style, and engines have had to add new invalidation machinery to keep them fast.9,43

Rule of thumbToggle classes as close as possible to the elements that change, avoid universal descendant selectors in rules that toggle often, and check the "elements affected" count of each Recalculate Style event in DevTools.43,45

6.2 Layout invalidation and containment

Layout invalidation is harder, because geometry is not local: a taller paragraph can push down everything that follows and grow every ancestor. CSS Containment lets authors promise the engine that a subtree is independent, so that work inside it never has to spread outside, and vice versa.22

6.3 Paint and raster invalidation

When a change only affects appearance, the engine repaints only the display items that changed and re-rasterizes only the tiles they cover. Chromium compares the new paint output with the previous one and invalidates the affected area of each layer; DevTools' Paint flashing option highlights those areas in green as they are repainted.50,53 Large or expensive paints are still a cost: big blurred box-shadows, filters and gradients take longer to rasterize, so they are worth checking when an animation janks.65

6.5 The critical rendering path, briefly

Before the very first frame, the pipeline also has to wait for resources. The critical rendering path is the chain of HTML, render-blocking CSS and parser-blocking scripts that must be fetched and processed before the first paint: the browser will not render while style sheets in the head are still loading, and classic scripts block the parser.11,38,42 The usual optimisations are fewer and smaller render-blocking resources, defer or async on scripts, inlining critical CSS, and preloading late-discovered resources. These are covered in depth in the separate critical rendering path article of this series.42

7Engine architecture

Three rendering engines power almost every browser in use: Blink (Chrome, Edge, Opera, Samsung Internet and other Chromium-based browsers), Gecko (Firefox) and WebKit (Safari).30,32,35,49 They all implement the same specifications and pass many of the same shared tests, but their internal pipelines were designed at different times for different constraints.29,49

7.1 Processes and threads

A modern browser is several cooperating processes. In Chrome, the browser process runs the UI and networking, each site gets one or more sandboxed renderer processes that hold Blink and V8, and a GPU process talks to the graphics hardware.6,70 Inside a renderer, the main thread runs JavaScript, style, layout and paint; the compositor thread receives committed frames, handles scrolling and composited animations, and schedules raster work on raster worker threads; the GPU process's Viz service aggregates compositor frames from all renderers and draws them.14,17

7.2 Blink and RenderingNG

Blink's pipeline is described in the RenderingNG documentation as a sequence of stages: animate, style, layout, pre-paint (compute property trees and invalidate paint), scroll, paint, commit, layerize, raster (with image decode and paint worklets), activate, aggregate and draw.14 The redesign made each stage's output an explicit data structure with clear ownership: the immutable fragment tree from LayoutNG, the four property trees from pre-paint, paint chunks and display items from paint, and compositor frames for Viz.12,41 Its companion project BlinkNG enforced the stage boundaries in code (lifecycle states such as "style clean" and "layout clean"), so that, for example, nothing can read layout during paint.37 Raster and drawing go through Skia, Google's 2D graphics library, which is also used by Chrome OS, Android and Flutter.14,54

7.3 Gecko: Stylo and WebRender

Gecko builds a frame tree from the DOM and computed styles, runs reflow to give frames their geometry, and then builds a display list from the frame tree for each paint.1,49 Two components came from the Servo research engine. Stylo (Quantum CSS), written in Rust, computes styles for different parts of the DOM in parallel across CPU cores using work stealing, and arrived with Firefox Quantum in November 2017.33,71 WebRender, also in Rust, replaced the older painting and compositing back end: it turns Gecko's display list into its own scene of primitives and draws the entire visible frame on the GPU every time, batching similar primitives and avoiding the work of deciding what to put in layers.36,49 Firefox 67, released in May 2019, began enabling it gradually by default for Windows 10 users with NVIDIA graphics cards.34

7.4 WebKit

WebKit, the engine of Safari, grew from KDE's KHTML and KJS, which Apple acknowledged as the open-source basis of Safari when it was announced in January 2003.30 Its traditional terms are the ones in the classic description of browser internals: a render tree of render objects (renderers) built alongside the DOM, laid out and then painted into layers that are composited by the platform.1 Because it is the engine of Safari on iOS and iPadOS, where Apple's App Store rules have required browsers to use WebKit for web content (with exceptions now allowed in some regions), WebKit's rendering behaviour matters for every mobile site.72

7.5 Servo

Servo began at Mozilla Research in 2012 as an experiment in building a browser engine in Rust, designed for parallelism and memory safety from the start.73 Its style system and WebRender went into Firefox; the project itself moved to the Linux Foundation in 2020 and to Linux Foundation Europe in 2023, where it continues as an embeddable engine.31,73

8Putting it together: one click, one frame

Here is everything that happens when a user clicks a button that opens a side panel. The panel is in the DOM with class="panel"; the click handler adds open, which changes transform from translateX(100%) to none with a 300 ms transition, and also updates a counter in the header.16,18,55

The pageHTML
<style>
  .panel { position: fixed; inset: 0 0 0 auto; width: 320px;
           transform: translateX(100%); transition: transform .3s ease; }
  .panel.open { transform: none; }
</style>
<header>Cart <span id="count">0</span></header>
<button id="open">Open cart</button>
<aside class="panel">…</aside>
<script>
  document.getElementById("open").addEventListener("click", () => {
    document.querySelector(".panel").classList.add("open");
    count.textContent = Number(count.textContent) + 1;
  });
</script>
  1. Input. The browser process receives the click from the operating system and forwards it to the renderer that owns that part of the page. Because the click is not a scroll, the compositor thread passes it to the main thread as an event task.55
  2. Task. The event loop runs the task; the handler adds a class and changes a text node. Nothing is recomputed yet; the engine only marks style as dirty.18,37
  3. Microtasks. None are queued here, so the loop moves on.57
  4. Update the rendering. At the next rendering opportunity, the transition starts (animations step); then style is recalculated for the panel and the counter. The panel's new transform starts a transition; the counter's new text needs layout.3,58
  5. Layout. Only the header's line is dirty. Layout updates the text fragment and confirms that the header's size has not changed, so nothing else moves.12
  6. Pre-paint and paint. The panel gets a transform node in the property tree and, because it has an animated transform, its own composited layer. The header's text is repainted; the rest of the display list is reused.14,41
  7. Commit, raster, draw. The main thread commits; the compositor rasterizes the new tiles for the header text and the panel and sends the frame to Viz.14
  8. The next 300 ms. The transition runs on the compositor thread: each frame only changes the panel layer's transform. Even if the main thread is busy, the panel keeps sliding.15,16

Had the panel animated right or width instead, every frame of those 300 ms would have needed style, layout, paint and raster on the main thread. That is the whole argument for composite-only animation in one example.2,16

Exercise 4: The unbeatable z-index

  1. Which engine calls layout "reflow", and which calls the box tree a "frame tree"?

    Answer

    Answer

    No. Every callback queued for the same frame receives the same timestamp, the time at which that frame's rendering began.19,48

    Answer

    First Input Delay, on 12 March 2024.69

  9. What does a CLS session window group together?
    Answer

    Layout shifts less than 1 second apart, for at most 5 seconds; CLS is the largest window's total.67

  10. Which Firefox release first enabled WebRender by default, and for whom?
    Answer

    Firefox 67 (21 May 2019), gradually, for Windows 10 desktops with NVIDIA graphics cards.34

  11. Which graphics library does Chrome use for rasterization, and what else uses it?

Animate smoothly
  • Use transform and opacity.16
  • Drive JavaScript animation from requestAnimationFrame(), using its timestamp.48
  • Respect prefers-reduced-motion.
  • Keep page work under about 10 ms per 60 Hz frame.62


Avoid forced layout
  • Read geometry first, then write.47
  • Prefer ResizeObserver and IntersectionObserver to polling.59
  • Know the APIs that force layout.44


Skip work
  • contain: content on independent widgets.22
  • content-visibility: auto + contain-intrinsic-size on long pages.64
  • Reserve space for images and embeds to avoid layout shifts.67


Measure
  • Core Web Vitals: LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1 at the 75th percentile.66
  • Long Animation Frames for jank attribution.28
