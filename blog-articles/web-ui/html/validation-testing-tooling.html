HTML Validation, Testing, and Tooling

How to find out whether your markup is correct and whether your pages work: conformance checking with the W3C Markup Validation Service and the Nu Html Checker, invalid nesting, missing attributes, obsolete elements and browser compatibility; the everyday tools (Chrome and Firefox DevTools, VS Code and HTML language servers, Emmet, Prettier, HTMLHint, Lighthouse and axe DevTools); and the kinds of testing that sit on top of them, from accessibility and responsive testing to cross-browser, integration, visual regression and performance testing. Grounded in the WHATWG HTML Standard, W3C WAI guidance and each tool's own documentation, with real output from the tools run for this article.

Updated 15 November 2026142 references (Vancouver style)Includes exercises, trivia, real tool output, a markup checker lab and a playground

Eleven articles in this series have described what HTML is, from the fundamentals through forms, browser APIs and security. This one is about how you know you got it right. Browsers are deliberately forgiving: the HTML Standard defines exactly how a user agent must recover from almost every mistake, so a broken page usually still renders.1,2 That forgiveness hides errors from the author, which is why the standard also defines a separate class of software, the conformance checker, whose job is to report them,3 and why a whole toolchain of linters, formatters, auditors and test runners has grown up around it.

Section 1 explains what "valid" means and where checking fits in a workflow. Section 2 covers validation itself, section 3 the developer tools, and section 4 the kinds of testing. Section 5 combines them into a continuous-integration pipeline, and sections 6 to 10 hold exercises, trivia, a markup checker lab, a playground and a quick-reference table. Every tool output shown in a dark terminal block was produced by running that tool on 15 November 2026 against the sample page in section 2.1; versions are given with each one.

1Introduction

1.1 Why check HTML at all?

The HTML Standard gives three reasons for keeping documents conforming even though browsers can render non-conforming ones. Some errors cause real problems, such as markup whose error-recovery behaviour differs from what the author expected; some make documents harder to maintain; and some are disallowed because they are known to cause accessibility, interoperability or performance problems.4–6 The standard is explicit that the rules on content models exist partly because of how the parser recovers: a p containing a div, for instance, is split by the parser into two siblings, so the styling and scripting the author wrote no longer apply to the tree they imagined.6,7

Validity is necessary but not sufficient. A page can pass the validator and still be inaccessible, slow, broken in one browser or broken on a phone. The 2026 WebAIM Million survey found detectable WCAG failures on 95.9% of the top one million home pages, with an average of 56.1 errors per page; the six most common failure types (low-contrast text, missing alternative text, missing form labels, empty links, empty buttons and a missing document language) are all things automated tools can catch.8 That is the case for the rest of this article: validation catches one class of errors, and testing catches the others.

1.2 Valid, conforming and working

Three words are often used as if they meant the same thing. They do not.

  • Valid originally meant "conforms to a DTD". HTML 4.01 was an SGML application with three document type definitions, and the original validators checked a document against the DTD named in its doctype.9,10
  • Conforming is the modern term. The HTML Standard has no DTD; it defines conformance requirements in prose, many of which cannot be expressed in a DTD. It says that conformance checkers "must verify that a document conforms to the applicable conformance criteria" that can be checked by machine, and notes that a DTD-based validator on its own cannot be a conforming checker.3 In everyday usage "valid HTML" now means "conforming HTML", and this article follows that usage.
  • Working means the page does what users need in the browsers and conditions they actually have. That is a testing question, not a validation question.
"Valid" is no longer an accessibility requirementWCAG 2.0 and 2.1 had success criterion 4.1.1 Parsing, which required well-formed markup. WCAG 2.2 marks it obsolete and removed: the problems it guarded against are now handled by browsers and assistive technologies, which all build the same tree from the standardised parsing algorithm.12,13 Invalid nesting still matters for accessibility in practice (a p inside a ul breaks the list semantics), but it is caught by other criteria, such as 1.3.1 and 4.1.2.14

1.3 A short history of HTML checking

The first online HTML validation service was created by Dan Connolly and Mark Gaither, announced on the www-html mailing list in July 1994.10,15 Its successor, the W3C Markup Validation Service, was created and maintained by Gerald Oskoboiny (it began life as "The Kinder, Gentler HTML Validator") and still runs on an SGML parser derived from James Clark's SP, the OpenSP version from the OpenJade team.10 Because HTML5 is not an SGML application, a new kind of checker was needed: the Nu Html Checker (v.Nu), which validates against the HTML Standard's own rules and is the engine behind validator.w3.org/nu.16,17

Alongside validators grew repair tools and linters. HTML Tidy, created by the W3C's Dave Raggett, cleaned up and reformatted markup; it is still maintained by the HTML Tidy Advocacy Community Group.18,19 In-browser developer tools took off with Firebug, Joe Hewitt's Firefox extension, which stopped working when Firefox Quantum (version 57) ended support for legacy extensions in late 2017; its features had by then been rebuilt into Firefox's own DevTools.20 Automated, scriptable browsers arrived with Selenium, started at ThoughtWorks in Chicago in 2004 by Jason Huggins, and were standardised when WebDriver became a W3C Recommendation on 5 June 2018.21,22

1.4 Where each tool fits

The tools in this article differ mainly in when they give feedback. Editor features such as language-server diagnostics, Emmet and format-on-save respond in milliseconds while you type.27,28 Linters and validators run in seconds, before a commit or in continuous integration. Browser-based tests and audits take minutes, because they launch real browsers.29,30 Field data about real users, such as the Chrome UX Report, arrives over days and weeks.31,32 A good workflow catches each error at the earliest, cheapest stage that can detect it.

2Validation

2.1 The W3C Markup Validation Service

The W3C Markup Validation Service at validator.w3.org is a free service that checks a document by address, by file upload or by pasted input.36,37 It now has two engines. The original "Markup Validator" uses an SGML parser and DTDs, and supports the HTML family up to HTML 4.01 and XHTML 1.0 and 1.1, along with MathML, SMIL and SVG.10 Documents written to the current HTML Standard are checked by the Nu Html Checker at validator.w3.org/nu, which implements the standard's rules directly; its own about page describes it as "an ongoing experiment in better HTML checking", whose behaviour may change as the standard does.16,38 The checker is open source under the MIT licence, and the same code is available as a command-line tool, a Java archive, an npm package and a Docker image.17,39,40

Using the checker from scripts

The checker runs locally, which keeps unpublished pages private and works offline. The jar needs Java 17 or later; native binaries bundle their own runtime.17 Useful options include --errors-only, --Werror (exit non-zero on warnings too), --skip-non-html for directories, --filterfile to suppress known messages by regular expression, and --also-check-css and --also-check-svg.41

Running the Nu Html Checker locallyShell

# Or POST a document to a checker web service and get JSON back
curl -H "Content-Type: text/html; charset=utf-8" \
     --data-binary @broken.html "http://localhost:8888/?out=json"

The recommended way to use the checker as a web service is to POST the document as the request body, with a Content-Type header giving its media type and encoding, and out=json in the query string.17,42 The JSON response has a messages array. Each message has a type of "error", "info" or "non-document-error", an optional subType ("warning" for info, "fatal" for error), line and column fields, the message text and an extract of the source.43 The outcome rule is simple: any non-document error makes the result indeterminate; otherwise any error makes it a failure; otherwise it passes.43

2.2 HTML conformance checking

The HTML Standard defines a conformance checker as one of its classes of product, alongside browsers, authoring tools and data mining tools. A checker must verify the machine-checkable requirements on a document, but is exempt from those that depend on the author's intent: it can tell that an img has no alt, but not whether "photo" is a good alt.3,11 For syntax, the standard's parsing chapter says that conformance checkers must report at least one parse error condition when a document contains any, and must not report parse errors when there are none.2 Parse errors are only the syntax errors; the checker also has to check everything else, such as content models and attribute values.2,44

Validators, linters and formatters

Three kinds of tool are often lumped together. A validator (conformance checker) answers "does this conform to the standard?" A linter answers "does this follow our team's rules?", which may be stricter or looser than the standard and are switched on and off in a configuration file. A formatter rewrites code into a consistent layout and has no opinion about correctness. The same sample page shows the difference clearly:

Every element in the HTML Standard has a content model that says what it may contain, expressed largely through categories such as flow content, phrasing content and interactive content.44 Breaking a content model is the most common conformance error, and it matters because the parser often repairs the tree in a way the author did not expect.6 Four patterns account for most cases.

2.5 Deprecated and obsolete elements

The HTML Standard does not use the word "deprecated". It calls features obsolete, and section 16 sorts them into two groups. Obsolete but conforming features (such as a language attribute on script) produce warnings but do not make a document non-conforming. Non-conforming features "are entirely obsolete, and must not be used by authors".67–69 Browsers still implement many obsolete elements so that old pages keep working; section 16.3 tells them how, which is why <center> still centres and <marquee> still scrolls.70 Tools vary in wording: the Nu checker says an element "is obsolete", html-validate's rule is called deprecated, and HTMLHint's is tag-no-obsolete.17,46,47

2.6 Browser compatibility

A validator checks your page against the standard, not against browsers. A perfectly conforming page can use a feature that one of your users' browsers does not support yet. Compatibility is checked with data, not with a parser.

  • MDN browser-compat-data (BCD) is the open dataset behind the compatibility tables on MDN, and it also feeds tools such as editors and linters.71 Can I use presents similar data, with usage-weighted percentages.72
  • Baseline summarises that data into a single label. A feature is Baseline newly available when it works in all the core browsers (Chrome and Edge, Firefox, and Safari, on desktop and mobile), and Baseline widely available when 30 months have passed since that date. The labels are defined by the W3C WebDX Community Group and shown on MDN, Can I use and web.dev.73–75
  • Firefox's Compatibility view, in the Page Inspector, lists CSS compatibility issues for the selected element and the whole page against a list of target browsers you choose; it first appeared in Firefox Developer Edition 77.76
  • web-platform-tests is the shared cross-browser test suite that browser vendors run, with results published on wpt.fyi; the annual Interop project picks focus areas from it to improve consistency across engines.77–79

When a feature is not yet widely available, use feature detection and progressive enhancement: test for the API or CSS feature, and provide a fallback that still works.80 HTML itself is designed for this. Browsers ignore unknown elements and attributes and render their contents, so new markup usually degrades gracefully, while scripts can check before calling a new method.80,81

Feature detection for a dialogJS
const dialog = document.querySelector("dialog");
if (typeof dialog.showModal === "function") {
  dialog.showModal();                 // native modal dialog
} else {
  dialog.setAttribute("open", "");    // simple fallback: show it inline
}

The dialog element is now Baseline widely available, so this check matters less than it once did, but the pattern applies to any newer API.73,82

3Developer tools

Validation tells you what is wrong with the source. Developer tools show you what the browser actually made of it, and let you change it live. This section covers the two most widely used browser toolsets, the editor and its language tooling, two code-quality tools and two auditing tools.

3.1 Chrome DevTools

Chrome DevTools is the set of web developer tools built into Chrome (and, with small differences, into other Chromium-based browsers such as Edge).83 For HTML work, five panels matter most.

  • Elements shows the live DOM tree, not your source. You can edit nodes and attributes, drag elements to reorder them, and force states such as :hover and :focus.84 Because it shows the parsed tree, it is the quickest way to see what the parser did with invalid nesting: the sample page's div appears as a sibling of the p, not inside it.
  • Accessibility (a pane in Elements) shows "the accessibility tree, ARIA attributes, and computed accessibility properties of DOM nodes", that is, the name and role assistive technology will announce. DevTools can also find low-contrast text and suggest better colours, and the Rendering tab can emulate vision deficiencies.85
  • Issues collects problems the browser detected while loading the page, including cookie problems, mixed content, CORS errors, Content Security Policy violations, quirks-mode documents (a missing doctype) and autocomplete attribute problems.86
  • Device mode simulates mobile viewports, device pixel ratios, touch and network conditions. Google describes it as "a first-order approximation of how your page looks and feels on a mobile device": it does not run your code on a phone.87
  • Performance, Network, Recorder and Lighthouse cover loading and runtime behaviour: recording a trace, throttling the connection, recording and replaying a user flow, and running audits (section 3.8).35,88–90
Five-minute DevTools check for any pageOpen the Issues panel and fix anything listed; inspect each heading and control in the Accessibility pane to confirm its name and role; tab through the page and watch the focus ring; switch on device mode at 320 CSS pixels wide (the WCAG reflow width) and check nothing scrolls sideways; then run Lighthouse once.85–87,91

3.2 Firefox Developer Tools

Firefox ships its own toolset with the same broad layout: Page Inspector, Web Console, Debugger, Network Monitor, Performance and Storage tools.92 Three features stand out for HTML work.

  • The Compatibility view in the Page Inspector shows CSS compatibility issues for the selected element and an "All Issues" list for the page, flags experimental and deprecated properties, and lets you choose which browsers to check against.76
  • The Accessibility Inspector shows the accessibility tree and has a "Check for issues" menu for contrast, keyboard and text-label problems, a simulator for colour vision deficiencies and contrast loss, and a "Show Tabbing Order" option that numbers every focusable element on the page.93
  • Responsive Design Mode (Ctrl+Shift+M) simulates screen sizes, device pixel ratios, touch events, user agents and network throttling presets.94

Firefox's DevTools are the descendants of Firebug, the extension that popularised in-browser inspection; Mozilla retired Firebug in 2017 after rebuilding its features into the built-in tools.20 Testing in Firefox's tools is also a cheap cross-browser check, because Firefox uses a different engine (Gecko) from Chrome and Edge (Blink).95

Visual Studio Code has HTML support built in, with no extension required. As you type it offers IntelliSense suggestions for elements, attributes and values, closes tags automatically, highlights matching tags and shows hover documentation.27 It validates JavaScript and CSS embedded in script and style elements (controlled by html.validate.scripts and html.validate.styles), but it does not check HTML conformance itself, so a misnested div gets no squiggle out of the box.27 Its built-in HTML formatter is based on js-beautify and is configured with settings such as html.format.wrapLineLength and html.format.wrapAttributes.27

3.4 HTML language servers

Without a shared protocol, every editor has to reimplement completion and diagnostics for every language. The Language Server Protocol (LSP) "defines the protocol used between an editor or IDE and a language server that provides language features like auto complete, go to definition, find all references etc.".28,97 The editor sends notifications such as "this document changed"; the server answers requests such as "what completions are valid here?" and pushes diagnostics back. The current version of the specification is 3.18.97

VS Code's own HTML features come from vscode-html-languageservice, an open-source library from Microsoft that provides completion, hover, formatting, folding, document links and symbol information for HTML.98 The vscode-langservers-extracted package repackages the HTML, CSS, JSON and ESLint servers from VS Code as stand-alone executables (vscode-html-language-server, for example), so editors such as Neovim and Helix can use the same engine.99 Linters can be exposed the same way, which is how conformance and lint errors appear as squiggles while you type.

4Testing


Tools used by hand find problems once. Tests find them every time the code changes. This section turns each kind of check into something a machine can run on every commit, and is honest about what still needs a person.





4.1 HTML validation as a test


The cheapest test is a conformance check of every page you ship. Two points make it effective. First, check the output, not the templates: a framework component, a CMS or a static-site generator produces the HTML that browsers parse, and that is what must conform. Second, make the check fail the build, so errors cannot accumulate.41,45



package.json scriptsJS
{
  "scripts": {
    "build": "eleventy",
    "lint:html": "htmlhint \"src/**/*.html\"",
    "validate": "html-validate \"dist/**/*.html\"",
    "validate:nu": "java -jar node_modules/vnu-jar/build/dist/vnu.jar --errors-only --skip-non-html dist",
    "test": "npm run build && npm run validate && npm run validate:nu && playwright test"
  }
}


Pages that only exist after script runs (a single-page application, for example) can be validated by serialising the live DOM in a browser test and posting it to a local checker. Note that this validates the tree after parsing, so parse errors in the original source will have disappeared; use it in addition to, not instead of, checking the served HTML.1,42



tests/validate.spec.js: validating rendered pages with Playwright and a local Nu checkerJS
import { test, expect } from "@playwright/test";

for (const path of ["/", "/shop", "/checkout"]) {
  test(`HTML conforms: ${path}`, async ({ page, request }) => {
    await page.goto(path);
    const html = "<!DOCTYPE html>\n" + await page.locator("html").evaluate(el => el.outerHTML);
    const res = await request.post("http://localhost:8888/?out=json", {
      headers: { "Content-Type": "text/html; charset=utf-8" },
      data: html,
    });
    const { messages } = await res.json();
    const errors = messages.filter(m => m.type === "error");
    expect(errors, errors.map(e => `${e.lastLine}: ${e.message}`).join("\n")).toEqual([]);

}



4.2 Accessibility testing


Accessibility testing combines automated checks, which are fast and repeatable, with manual checks, which are the only way to judge most WCAG success criteria.13,110 The W3C maintains a searchable list of evaluation tools, and its guidance on choosing one is blunt: many accessibility checks cannot be automated and need human judgement, so tools assist evaluators rather than replace them.110,113



Automated: axe in a browser test


tests/a11y.spec.jsJS

import AxeBuilder from "@axe-core/playwright";

test("home page has no detectable WCAG A/AA violations", async ({ page }) => {
  await page.goto("/");

    .withTags(["wcag2a", "wcag2aa", "wcag21a", "wcag21aa", "wcag22aa"])

4.4 Cross-browser testing


Cross-browser testing checks that a site works across the browsers, versions and devices your users have.95 The number of engines matters more than the number of browser brands. Chrome, Edge, Opera, Samsung Internet and many others use Blink; Firefox uses Gecko; Safari uses WebKit.95 Testing one browser per engine catches most engine-specific bugs.





Playwright "supports Chromium, WebKit and Firefox on Windows, Linux and macOS, locally or in CI", using browser builds it downloads and pins to each release; its WebKit build comes from WebKit's main branch, so it approximates Safari rather than being Safari.34,123 Selenium, started in 2004, drives the real installed browsers through the W3C WebDriver protocol, which became a Recommendation in 2018; its bidirectional successor, WebDriver BiDi, adds event streaming such as console messages and network events.21,22,125 Cloud device labs extend this to real phones and older browser versions.



Reduce what you have to testEvery feature you use that is Baseline widely available is one fewer thing to check by hand in each browser.73 Standard HTML elements (button, details, dialog, form controls) are tested by browser vendors against the shared web-platform-tests suite; custom widgets rebuilt from divs are tested by nobody but you.77,78



4.5 Integration testing


An integration test checks that several parts work together: the HTML, the CSS that shows and hides things, the script that handles events, and the server that answers. For web pages that usually means a browser test that does what a user does. The Testing Library project states the principle well: "The more your tests resemble the way your software is used, the more confidence they can give you."126 Its recommended query order starts with queries "accessible to everyone", led by getByRole ("your top preference for just about everything"), then getByLabelText and getByText, with getByTestId as a last resort.127 Playwright's locators follow the same order.128



tests/signup.spec.js: an integration test written the way a user sees the pageJS
import { test, expect } from "@playwright/test";

test("visitor can sign up for the newsletter", async ({ page }) => {
  await page.goto("/");
  await page.getByRole("link", { name: "Newsletter" }).click();
  await expect(page).toHaveURL(/\/newsletter$/);

  const form = page.getByRole("form", { name: "Sign up" });
  await form.getByLabel("Email address").fill("not-an-email");
  await form.getByRole("button", { name: "Subscribe" }).click();
  // Native constraint validation blocks submission
  const valid = await form.getByLabel("Email address").evaluate(el => el.validity.valid);
  expect(valid).toBe(false);

  await form.getByLabel("Email address").fill("ada@example.com");
  await form.getByRole("button", { name: "Subscribe" }).click();
  await expect(page.getByRole("status")).toHaveText("Thanks! Check your inbox.");
});


Role-based locators make an integration test double as an accessibility test: if a developer replaces the button with a clickable div, or removes the label, the test fails, because the element no longer has the role or name the test asks for.14,128 Tests in a simulated DOM such as jsdom run faster but have no layout engine, so they cannot catch problems with visibility, overlap or scrolling; keep at least the critical paths in a real browser.129



4.6 Visual regression testing


A visual regression test takes a screenshot, compares it with an approved "golden" image, and fails if too many pixels differ. It catches changes that no functional assertion would notice: a CSS refactor that shifts a button, a font that fails to load, a z-index that hides a menu. Playwright's expect(page).toHaveScreenshot() generates the reference screenshots on first run, uses the pixelmatch library to compare later runs, and accepts tolerances such as maxDiffPixels and a per-pixel colour threshold (default 0.2).130,131 BackstopJS and hosted services offer the same workflow with review dashboards.132

test("product card looks right", async ({ page }) => {
  await page.goto("/shop");
  await expect(page.getByRole("article").first()).toHaveScreenshot("card.png", {
    maxDiffPixelRatio: 0.01,             // tolerate 1% anti-aliasing noise
    animations: "disabled",
    mask: [page.getByTestId("live-price")],  // hide content that changes
  });
});
// First run writes the reference image; later runs compare against it.
// After an intended change: npx playwright test --update-snapshots


The main difficulty is noise. Font rendering, anti-aliasing and GPU differences vary between operating systems, so golden images must be generated in the same environment that compares them (typically a pinned container in CI); dynamic content such as dates, adverts and prices must be masked or frozen; and animations must be disabled.29,130



4.7 Performance testing


Performance testing measures how quickly a page loads, becomes usable and stays stable. Google's Core Web Vitals define three user-centred metrics with "good" thresholds, assessed at the 75th percentile of page loads: Largest Contentful Paint (LCP) within 2.5 seconds, Interaction to Next Paint (INP) of 200 milliseconds or less, and Cumulative Layout Shift (CLS) of 0.1 or less.65,133–135 INP replaced First Input Delay as a Core Web Vital on 12 March 2024.26





Performance data comes in two kinds. Lab data is collected by loading a page in a controlled environment with fixed device and network settings, as Lighthouse and the DevTools Performance panel do; it is reproducible and good for debugging. Field data, also called real user monitoring (RUM), is collected from real visits and reflects real devices and networks.32 The Chrome UX Report (CrUX) is Google's public dataset of field data from Chrome users, and PageSpeed Insights shows CrUX field data alongside a Lighthouse lab run.31,105 WebPageTest adds detailed lab runs from many locations, with filmstrips and request waterfalls.136 INP needs real interactions, so lab tools use Total Blocking Time as a proxy.106,135



Much of performance is decided by HTML. Give images width and height so the browser can reserve space and avoid layout shift; use loading="lazy" for images below the fold but not for the LCP image, which may benefit from fetchpriority="high"; serve appropriately sized files with srcset and sizes; and load scripts with defer or type="module" so they do not block parsing.64,65,134,137–139

0.10 × 1.00 + 0.10 × 0.90 + 0.25 × 0.60 + 0.30 × 0.80 + 0.25 × 1.00 = 0.10 + 0.09 + 0.15 + 0.24 + 0.25 = 0.83, shown as 83 in orange ("needs improvement").106 LCP has the largest gap times weight (0.25 × 0.40 = 0.10 points available, against 0.06 for TBT), so start there: check that the LCP image is not lazy-loaded, is sized correctly and is discovered early.134,137









Exercise 6: Pass or fail?


Field data for a page at the 75th percentile: LCP 2.3 s, INP 240 ms, CLS 0.04. Does it pass the Core Web Vitals assessment? Which HTML change most often fixes a CLS problem?


Show solution


It fails: LCP and CLS are good, but INP is above 200 ms, and all three must meet their thresholds at the 75th percentile.133 For CLS, the most common HTML fix is giving images, videos and iframes explicit width and height attributes (or a CSS aspect-ratio) so the browser reserves space before they load.65,139









Exercise 7: Write the test


Write a Playwright test that fails if any page in ["/", "/about"] has an img without an alt attribute, without using axe.


Show solution


tests/alt.spec.jsJS
import { test, expect } from "@playwright/test";

for (const path of ["/", "/about"]) {
  test(`every img has alt: ${path}`, async ({ page }) => {
    await page.goto(path);
    await expect(page.locator("img:not([alt])")).toHaveCount(0);
  });
}


The selector img:not([alt]) matches images with no alt attribute at all; images with alt="" are correctly allowed, because an empty value marks a decorative image.11,128
