HTML Parsing Algorithms

How a browser turns a stream of bytes into a DOM tree, following the WHATWG HTML Standard step by step: encoding sniffing and input preprocessing, the 84-state tokenizer, the 21 insertion modes of tree construction, the stack of open elements and the list of active formatting elements, the adoption agency algorithm, foster parenting, error recovery, the way scripts and document.write() re-enter the parser, speculative parsing and fragment parsing. With a working teaching parser that you can step through, checked against your own browser.

Updated 17 November 202684 references (Vancouver style)Includes exercises, trivia, a tokenizer explorer, a step-through parser lab, a fragment explorer and a playground

Every earlier article in this series, from HTML fundamentals to HTML security and HTML integration, has relied on one quiet fact: whatever markup you send, the browser builds a tree from it, and every browser builds the same tree. That is not luck. The HTML Standard defines, in exact algorithmic detail, what a parser must do with every possible input, including input that breaks every authoring rule.1,2 This article opens up that algorithm. It explains each stage, shows why the strange results you sometimes see (a paragraph that splits in two, text that jumps out of a table, a bold tag that reappears after you closed it) are the deliberate output of well-defined rules, and lets you watch those rules run.

Section 1 explains why HTML has its own parsing algorithm and where it comes from. Section 2 covers the input stream: character encodings, newline normalisation and parse errors. Section 3 is about the tokenizer, and section 4, the longest, about tree construction. Section 5 shows how scripts interact with the parser, including document.write() and speculative parsing, and section 6 covers fragment parsing for innerHTML and related APIs. Section 7 walks through source code for a parser, and sections 8 to 12 hold exercises, trivia, a parser lab, a playground and a quick reference.

About the teaching parserThe tokenizer explorer and the parser lab on this page run MiniHTML, a compact JavaScript implementation of the standard's algorithm written for this article (about 600 lines). It covers the parts discussed here, including tables, foster parenting, the list of active formatting elements and the adoption agency algorithm, and it compares its output with your browser's own parser every time it runs. 1Introduction

1.1 Why HTML needs its own parsing algorithm

Most computer languages are parsed with a grammar: input that matches is accepted and anything else is rejected. XML takes this to its logical end. A fatal error, such as a missing end tag, obliges an XML processor to stop normal processing, so a single mistake means no document at all.5 HTML has never worked that way. Browsers have always displayed whatever they were given, because users blame the browser, not the page, when a page fails to appear. By the mid-2000s the web held billions of pages that relied on how one browser or another happened to recover from errors, and each browser recovered differently.6,7

The HTML Standard solved this by defining error recovery as part of the language. It still says which markup is conforming (that is what validators check), but it also gives a complete algorithm that turns any sequence of bytes into a DOM, with every error case spelled out.8,9 Two consequences follow:

  • Interoperability. Browsers, validators, search-engine crawlers, sanitizers and server-side libraries that follow the algorithm agree on the tree, even for broken markup. That agreement matters for security: a sanitizer that sees a different tree from the browser can be bypassed.10
  • No grammar. HTML is not parsed with a context-free grammar. The parser is two cooperating state machines (a tokenizer and a tree builder) whose behaviour depends on what has already been built, and scripts can inject new input while parsing is under way.2

1.2 A short history

The first HTML standard, HTML 2.0 (RFC 1866, 1995), defined HTML as an application of SGML, and HTML 4.01 (1999) kept that model.11,12 In practice no mainstream browser ever used an SGML parser. Browsers parsed "tag soup" with their own heuristics, and HTML 4.01 itself notes that many user agents do not support some SGML features, and advises authors to avoid SGML shorthand markup such as the null end tag.13 The result was four browser engines with four different error-recovery strategies.

Work on what became HTML5 began at the WHATWG in 2004. One of its founding principles was that specifications must be detailed enough for implementations to interoperate completely "without reverse-engineering each other", which for parsing meant writing down, rule by rule, what browsers already did with malformed markup.14 The parsing algorithm was already a full chapter, with tokenization and tree construction sections, in the W3C's First Public Working Draft of HTML 5 on 22 January 2008.7 Browsers then rebuilt their parsers around it: Firefox 4 shipped an HTML5 parser, written by Henri Sivonen and with its core translated mechanically from his Java Validator.nu parser into C++; WebKit and Blink adopted the algorithm in the same period; and Internet Explorer 10 announced full support for it in 2011.15–18 The W3C published HTML5 as a Recommendation on 28 October 2014, and since 2019 the WHATWG HTML Living Standard has been the single authoritative version.19,20

1.4 The parsing pipeline

The standard describes parsing as a pipeline (Figure 1). Bytes arrive from the network and pass through a byte stream decoder, which turns them into Unicode code points using the document's character encoding. An input stream preprocessor normalises newlines. The tokenizer turns characters into tokens, and the tree construction stage turns tokens into DOM nodes. Scripts run during tree construction and can call document.write(), which inserts new characters into the input stream, so the tree construction stage is re-entrant: while one token is still being processed, the tokenizer can be resumed and emit more tokens.2

Two pieces of shared state tie the stages together. The insertion mode (one of 21) tells the tree builder which set of rules applies to the next token; the tokenizer state (one of 84) tells the tokenizer how to read the next character. The tree builder changes the tokenizer state in a handful of places, for example after a <title> start tag, which is why <title><b></title> gives a title whose text is <b>.26,27 Section 4.2 adds the stack of open elements and the list of active formatting elements, which hold the rest of the parser's memory.28,29

2The input stream

2.1 Determining the character encoding

The parser works on characters, but the network delivers bytes, so the first job is to choose a character encoding. The standard's encoding sniffing algorithm tries a fixed sequence of sources and stops at the first that gives an answer (Figure 2). Each answer comes with a confidence: certain if the encoding came from a byte order mark, a user override or the transport layer (the charset parameter of Content-Type), and tentative otherwise.30

The prescan in step 5 is a small parser in its own right. It skips comments, looks for <meta> tags with a charset attribute or an http-equiv="content-type" pragma, and ignores everything else; user agents are encouraged to prescan only the first 1024 bytes. That limit is why the authoring rules require the <meta charset> element to appear entirely within the first 1024 bytes of the document.30,31 If the encoding was only tentative and the parser later meets a <meta charset> that names a different encoding, the "changing the encoding while parsing" rules apply: the user agent may change the decoder on the fly if the bytes seen so far decode identically, and otherwise navigates to the document again with the new encoding.32 The decoders themselves, and the list of encoding labels such as latin1 mapping to windows-1252, come from the Encoding Standard.24

2.2 Preprocessing the input stream

Before tokenization the decoded characters are normalised. Every CR LF pair and every lone CR becomes a single LF, so the tokenizer only ever sees one kind of newline.33 Some code points are reported as parse errors when they appear in the input stream: surrogates (surrogate-in-input-stream), noncharacters such as U+FFFF (noncharacter-in-input-stream) and control characters other than ASCII whitespace and NULL (control-character-in-input-stream). They are reported, not removed. NULL (U+0000) is handled later, by each tokenizer state, usually by reporting unexpected-null-character and either ignoring it or replacing it with U+FFFD REPLACEMENT CHARACTER.3,8

2.3 Parse errors

A parse error in HTML is a diagnosis, not an exception. The standard lists 52 named parse errors in §13.2.2, each with a code such as duplicate-attribute or eof-in-tag, a description and an example, and then says exactly how the parser recovers from each one.8 Conformance checkers must report at least one parse error for a document that has any; browsers usually report none and simply carry on with the recovery steps. The standard does allow a user agent to stop at the first parse error rather than recover, but no browser does that for text/html.8 The tokenizer's errors have names; the tree-construction stage reports errors without names, simply by saying "parse error" in the rule that applies.4

3Tokenization

3.1 A state machine with 84 states

The tokenizer is a state machine. It reads one character at a time, and the current state decides what that character means. The standard defines 84 states, numbered §13.2.5.1 (Data state) to §13.2.5.84 (Numeric character reference end state).3 They group naturally into families (Figure 3): five text states, the tag and attribute states, the comment and DOCTYPE states, the end-tag lookahead states used inside text-only elements, the script-escape states, the CDATA states used in SVG and MathML, the processing-instruction states, and the character-reference states.

3.2 The six kinds of token

The tokenizer emits six kinds of token: DOCTYPE, start tag, end tag, comment, character and end-of-file. A DOCTYPE token has a name, a public identifier, a system identifier and a force-quirks flag; start and end tags have a tag name, a list of attributes and a self-closing flag.3 Tag and attribute names are lowercased as they are read, which is why HTML is case-insensitive for element and attribute names. The current standard's processing-instruction states produce a processing-instruction node rather than a comment for markup such as <?php echo 1 ?> (see 3.6).3,34

Two details of tag tokens surprise people. First, the self-closing flag is only acknowledged for void elements (such as br and img) and in foreign content; on any other HTML element it is a parse error and has no effect, so <div/> is just <div>.8,35 Second, a duplicate attribute is dropped by the tokenizer, so the tree builder never even sees it.8

3.4 Text-only states: RCDATA, RAWTEXT, script data and PLAINTEXT

Inside some elements markup is not markup. The tokenizer cannot know this by itself, so the tree builder switches its state when it inserts those elements (§13.2.6.2).27 There are four text-only states:

  • RCDATA (for title and textarea): tags are text, but character references are decoded.
  • RAWTEXT (for style, xmp, iframe, noembed, noframes, and noscript when scripting is enabled): nothing is decoded.
  • Script data (for script): like RAWTEXT, plus 14 extra states that track <!-- and <script inside the script so that legacy "commented-out" scripts keep working.
  • PLAINTEXT (for plaintext): everything to the end of the file is text. There is no way out.3,35

In the first three, the only way out is an appropriate end tag: an end tag whose name matches the last start tag the tokenizer emitted. That is why </title> ends a title but </b> inside it does not, and why the string "</script>" inside a JavaScript string ends the script element. Authors must escape it, for example as "<\/script>".3,36

3.5 Character references

A & in data, RCDATA or an attribute value starts a character reference (§13.2.5.77–§13.2.5.84). Numeric references (&#169;, &#xA9;) are decoded with some fixes: zero, surrogates and values above U+10FFFF become U+FFFD, and the 27 code points from 0x80 to 0x9F that windows-1252 maps to printable characters are remapped, so &#x80; gives € rather than a control character.3 Named references are looked up in a table of 2,231 names in §13.5; for legacy compatibility, 106 of those names are also recognised without the trailing semicolon, such as &copy and &amp.37,38 The tokenizer takes the longest name that matches, which gives the famous result that &notit; is decoded as ¬it; (the legacy name &not followed by "it;"), while &notin; is ∉.3,37

Attribute values have one more rule. If a legacy reference without a semicolon is followed by = or by a letter or digit, it is not decoded at all. This keeps URLs such as href="?a=1&copy=2" intact, because otherwise every &copy= query parameter would turn into ©=.3 Authors should still write &amp; in attribute values: the syntax rules require named references to end with a semicolon.39

3.6 Comments, DOCTYPEs, CDATA and processing instructions

Markup that starts with <! goes to the markup declaration open state, which looks ahead for -- (a comment), DOCTYPE in any case (a DOCTYPE) or [CDATA[. Anything else becomes a bogus comment with an incorrectly-opened-comment error, so an old SGML declaration such as <!ELEMENT br EMPTY> ends up in the DOM as a comment.3,8 CDATA sections are recognised only in foreign content (SVG and MathML); in HTML content <![CDATA[x]]> becomes a bogus comment.3,40

The comment states are generous: <!--> and <!---> are empty comments, --!> closes a comment, and <!-- inside a comment is only reported as nested-comment, because comments do not nest.8 Historically, <? also produced a bogus comment. The current standard adds five processing-instruction states (§13.2.5.72–§13.2.5.76) and a syntax for processing instructions (§13.1.7).3,34 In Chromium 153, which was used to test this article, x<?php echo 1 ?>y produces a ProcessingInstruction node with target php and data echo 1 , while <?xml version="1.0"?> still becomes a comment. Other engines may not yet do this, so check before you rely on it.

4Tree construction

4.1 Insertion modes

The tree builder receives one token at a time and handles it according to the current insertion mode. Each of the 21 modes is a table of rules of the form "a start tag whose tag name is one of …: do this", ending with an "anything else" rule. Rules often switch to another mode, and many say "reprocess the token", which means handing the same token to the new mode's rules.4,26 Figure 4 shows the modes that a typical document passes through.

Older editions had more modes. The 2014 W3C Recommendation listed 23, including "in select" and "in select in table", which threw away almost any tag inside a select.19 The current standard has no select-specific modes: select, option and optgroup are handled by rules in "in body", so that a customizable select can contain other markup. In Chromium 153, <select><div>x</div></select> keeps the div.4,35

The initial mode is where a document's mode is decided (see 4.9); before html, before head and after head create the html, head and body elements if the markup leaves them out; in head handles metadata; and in body, by far the largest, handles everything else. That is how the optional tags of §13.1.2.4 work in practice: the authoring rules allow <html>, <head> and <body> to be left out precisely because the parser can always infer them.35,41–43

4.2 The stack of open elements and element scopes

The stack of open elements records the path from the root to the node where content is currently being inserted. The bottom is always the html element and the top is the current node. A start tag usually pushes an element; an end tag pops elements until the matching one is gone.28 Many rules ask whether an element is "in scope": walk down from the current node, and if you meet the target before you meet one of a list of boundary elements, it is in scope. The default list is applet, caption, html, table, td, th, marquee, object, template and a few MathML and SVG elements. The variants add more boundaries: list item scope adds ol and ul, button scope adds button, and table scope uses only html, table and template.28

Scope is why a </p> inside a table cell does not close a paragraph outside the table: the td is a boundary, so that p is not in button scope.28,35 The standard also defines a special category of about 80 HTML elements (such as address, div, li, p, table and ul), plus some MathML and SVG elements, which act as walls for the "any other end tag" rule and as candidates for the "furthest block" in the adoption agency algorithm.28

4.3 Implied end tags and auto-closing

Several elements close themselves when something else begins. In "in body", a start tag for a block-level element such as div, ul or h1 first closes an open p in button scope; a new li closes the previous li; and dd and dt close each other.35 The general mechanism is generate implied end tags: while the current node is a dd, dt, li, optgroup, option, p, rb, rp, rt or rtc, pop it.44

4.4 The list of active formatting elements

Formatting elements (a, b, big, code, em, font, i, nobr, s, small, strike, strong, tt and u) get special treatment, because authors routinely let them overlap block boundaries. The parser keeps a second structure, the list of active formatting elements, holding each formatting element that has been opened and not yet closed, plus markers that are pushed when entering applet, object, marquee, template, td, th and caption, so formatting does not leak into or out of those elements.29

Before inserting text or most elements in "in body", the parser runs reconstruct the active formatting elements: any entry in the list whose element is no longer on the stack of open elements is cloned and reopened at the current position. That is why bold text continues in the next paragraph when a b was never closed.29,45 To stop a page of thousands of unclosed <font> tags from creating thousands of clones, the list holds at most three entries with the same tag name, namespace and attributes after the last marker; pushing a fourth removes the earliest. The standard calls this the Noah's Ark clause, "but with three per family instead of two".29

4.5 The adoption agency algorithm

When an end tag for a formatting element arrives and that element is not the current node, the parser runs the adoption agency algorithm (AAA), defined in the "in body" rules.35,46 Its name describes what it does: a formatting element "adopts" content by being cloned into a block, and the block is re-parented. In outline:

  1. Find the formatting element: the last entry in the list of active formatting elements, after the last marker, with the end tag's name. If there is none, treat the token like any other end tag. If the element is in the list but not on the stack, remove it from the list. If it is on the stack but not in scope, ignore the token.
  2. Find the furthest block: the topmost special element on the stack that is above the formatting element. If there is none, the case is simple: pop up to and including the formatting element and remove it from the list. This is what happens with <b><i></b></i>.
  3. Otherwise, walk the elements between the furthest block and the formatting element (the inner loop). Elements that are not in the list of active formatting elements are removed from the stack; formatting elements are cloned, and the chain of clones is re-parented, with the furthest block at the bottom.
  4. Move the result into the common ancestor (the element below the formatting element on the stack), create a clone of the formatting element, move all of the furthest block's children into the clone, and append the clone to the furthest block. Update the list and the stack to match.
  5. Repeat. The outer loop runs at most 8 times, and within each run, the inner loop stops cloning a formatting element after it has passed 3 of them, removing further ones from the list instead. These limits bound the work on pathological input.35

The limits are the same in independent implementations: parse5, for example, uses AA_OUTER_LOOP_ITER = 8 and AA_INNER_LOOP_ITER = 3, and a Noah's Ark capacity of 3.47 Figure 6 shows the result for the misnested example from Figure 5.

4.6 Tables and foster parenting

Tables have the strictest content model in HTML: text and most elements are not allowed directly in table, tbody or tr. The table insertion modes enforce it. They insert implied tbody and tr elements where needed, and when they meet content that does not belong, they process it with the "in body" rules but with foster parenting enabled.49,50 Foster parenting changes the appropriate place for inserting a node: if the target would be a table, tbody, tfoot, thead or tr, the node is inserted into the table's parent, immediately before the table.51 Text is buffered first in the "in table text" mode: if it is only whitespace it stays in the table, and otherwise it is foster-parented with a parse error.52

Foster parenting is why a stray character inside a table, often a leftover from a template loop, shows up above the table rather than inside it, and why validating your markup is the quickest way to find it.50 Two kinds of content are allowed in a table without fostering: <input type="hidden"> (inserted directly, with a parse error) and the script-supporting elements script, style and template, which are processed with the "in head" rules.49

4.7 Foreign content: SVG and MathML

When the parser meets <svg> or <math> in HTML content it creates the element in the SVG or MathML namespace, and tokens inside it are processed by the rules for parsing tokens in foreign content (§13.2.6.5).53 These differ from the HTML rules in three main ways:

  • XML-like syntax. The self-closing flag is honoured (<path/> is an empty element) and CDATA sections are recognised.40,53
  • Case fixing. HTML lowercases names, but SVG has camelCase names, so the parser maps them back: foreignobject becomes foreignObject and the attribute viewbox becomes viewBox. MathML's definitionurl becomes definitionURL, and xlink:href and similar attributes are put in their namespaces.51,53
  • Breakout. A start tag for one of a fixed list of HTML elements (including b, div, p, table, ul and font with a color, face or size attribute) is a parse error that pops out of foreign content, so an unclosed <svg> cannot swallow the rest of the page.53

Integration points let HTML return inside foreign content: SVG foreignObject, desc and title, and MathML annotation-xml with an HTML or XHTML encoding are HTML integration points, and MathML mi, mo, mn, ms and mtext are MathML text integration points.4 Switching namespaces at these points is exactly where sanitizers and browsers have disagreed in the past (see 6.4).54

4.8 Templates

The content of a <template> element is parsed but not rendered and not part of the document tree. The parser inserts it into the template's template contents, a DocumentFragment owned by a separate inert document, so its scripts do not run and its images do not load.51,55 Because a template may hold a table row, a list item or anything else, the parser keeps a stack of template insertion modes. The "in template" mode (§13.2.6.4.16) looks at the first start tag inside the template and switches to the mode that fits it, for example "in table body" for <tr>; so <template><tr><td>x</template> keeps the tr, which would be dropped anywhere outside a table.56 A template with a shadowrootmode attribute is a declarative shadow root: the parser attaches a shadow root to the parent element instead of creating a template element. This only happens in the main parser and in the …Unsafe() methods, not with innerHTML.42,57

4.9 Quirks mode and the DOCTYPE

The DOCTYPE does one thing in today's HTML: in the "initial" insertion mode it chooses the document's mode. A document with no DOCTYPE, a DOCTYPE whose name is not html, a DOCTYPE token with the force-quirks flag, or one of a long list of legacy public identifiers is put in quirks mode; the XHTML 1.0 Transitional and Frameset identifiers, and HTML 4.01 Transitional and Frameset with a system identifier, give limited-quirks mode; and <!DOCTYPE html> gives no-quirks mode.41,58 The Quirks Mode Standard lists what changes in rendering.25

The mode also affects the parser itself in one place. In no-quirks mode a <table> start tag closes an open p; in quirks mode it does not, because old pages put tables inside paragraphs.35 So <p>1<table> produces a table inside the paragraph without a DOCTYPE and a table after it with one. Try it in the playground: the tree pane shows compatMode, which is BackCompat in quirks mode and CSS1Compat otherwise.23

4.10 The end

When the tokenizer emits the end-of-file token, the parser runs the steps in §13.2.7, "The end".59 In order, it:

  1. sets the document's readiness to "interactive" and pops every element off the stack of open elements;
  2. runs the scripts in the list of scripts that will execute when the document has finished parsing (classic scripts with defer and module scripts without async, in document order);
  3. queues a task to fire DOMContentLoaded at the document;
  4. waits until the async scripts and the "as soon as possible" scripts have run and nothing is delaying the load event (images, stylesheets, frames);
  5. sets readiness to "complete" and fires load at the window.59,60

5Scripts and the parser

5.1 Parser-blocking scripts and the insertion point

A classic <script> without async or defer stops the parser. When the tree builder sees the script's end tag (in the "text" insertion mode), it increments the parser's script nesting level, prepares the script, and, if the script is not ready yet, makes it the document's pending parsing-blocking script and pauses. The tokenizer does not continue until the script has been fetched, any script-blocking style sheets have loaded, and the script has run.61,62 Waiting for style sheets is deliberate: a script may read computed styles, so it must see the CSS that comes before it.61

While a script runs, the parser keeps an insertion point: the place in the input stream just after the </script> end tag. Anything the script writes with document.write() is inserted there, before the rest of the network input, and is tokenized next. This is the re-entrancy shown in Figure 1.2,63

5.3 document.write()

document.write() is the reason the parser must be re-entrant. Called from a parser-blocking script, it inserts its string at the insertion point and, unless the parser is paused, runs the tokenizer on it before returning, which is why the frame above finds #w immediately after the call.63,64 If the string contains a <script>, that script runs during the write, and its own writes nest further.64 The other cases are much less friendly:

  • No insertion point (the document has finished parsing, or the call comes from an event handler or a timer): the call implicitly runs document.open(), which throws the current document away and starts a new, empty one.63,65
  • External scripts: while a script from a file or a module script runs, the ignore-destructive-writes counter is raised, so a write that would implicitly open the document is ignored instead. This protects pages from async scripts that write too late.61,63
  • XML documents and code running during custom element construction: the call throws (the latter through the throw-on-dynamic-markup-insertion counter).63,66

The standard summarises: "This method has very idiosyncratic behavior", and "use of this method is strongly discouraged"; MDN marks it deprecated.63,67 It also hurts performance. A script that writes another, parser-blocking, cross-origin <script> forces a second network round trip with the parser stopped. In 2016 Chrome began blocking such scripts for users on 2G connections; in its field trial, 7.6% of 2G page loads contained one, and blocking them cut mean parse time by 38%.68

5.4 Speculative parsing and the preload scanner

A parser that stops at every blocking script would leave the network idle. So the standard allows user agents to run a speculative HTML parser ahead of the real one while it waits (§13.2.8). The speculative parser reads the rest of the input, finds resources such as scripts, style sheets and images, and starts fetching them; it must not change the real document, and it only makes speculative fetches, whose responses the real parser can reuse when it reaches the same markup.69 Browser documentation calls this the preload scanner: "a secondary HTML parser" that "parses the available content and requests high-priority resources like CSS, JavaScript, and web fonts".70,71 Firefox's HTML5 parser was designed for this from the start: it parses network streams off the main thread.15

The preload scanner can only find what is in the markup. Resources that scripts add, CSS background images and lazily loaded images are invisible to it, which is the main argument against injecting critical resources with JavaScript.70

6Fragment parsing

6.1 The fragment parsing algorithm

Setting innerHTML does not parse a document; it parses a fragment as if it appeared inside a given context element. The HTML fragment parsing algorithm (§13.4) creates a new document and a parser for it, and then uses the context element to set up the parser state:21

  1. The tokenizer starts in a state chosen by the context: RCDATA for title and textarea; RAWTEXT for style, xmp, iframe, noembed, noframes, and noscript if scripting is enabled; script data for script; PLAINTEXT for plaintext; and the data state otherwise.
  2. An html element is created as the root and pushed on the stack of open elements; if the context is a template, "in template" is pushed on the stack of template insertion modes.
  3. The insertion mode is reset "appropriately" as if the context element were the current node, so a tr context gives "in row" and a table context gives "in table".
  4. The form element pointer is set to the nearest form ancestor of the context, if any.
  5. The input is parsed to the end, and the children of the root html element are returned.21

So the same string can give different trees in different places. "<td>x" becomes a table cell when the context is a tr, but only the text "x" when it is a div, because "in body" ignores a stray <td>; and anything assigned to a textarea's innerHTML is text.21,35

Exercise 6: The DOCTYPE changes the tree


Explain why <p>1<table><p>2</table> gives a different tree with and without <!DOCTYPE html>.


Show solution


Without a DOCTYPE the document is in quirks mode, and in quirks mode a <table> start tag does not close an open p, so the table (and the fostered second p, inserted before the table inside the first p) ends up inside the first paragraph. With the DOCTYPE the <table> closes the paragraph and both paragraphs and the table are children of body.35,41









Exercise 7: A script that ends too early


Why does this break, and how do you fix it?


Exercise 7HTML
<script>var s = "</script>";</script>


Show solution


Script data is ended by the first appropriate end tag, </script followed by whitespace, / or >, whatever the JavaScript around it means. The script element contains only var s = " (a syntax error), and "; becomes text in the body. Write "<\/script>" or "</scr" + "ipt>", or move the code into an external file.3,36









Exercise 8: Noah's Ark


How many b elements are open around "y" in <p><b><b><b><b>x</p>y?


Show solution


Three. All four b elements are identical (same name, namespace and no attributes), so pushing the fourth onto the list of active formatting elements removed the first. When "y" is inserted after </p>, reconstruction reopens only the three that are still in the list. Give the b elements different attributes and all of them are reconstructed.29









Exercise 9: Fragments


What does each line leave in the element?


Exercise 9JS
const row = document.createElement("tr");    row.innerHTML = "<td>a</td>";
const box = document.createElement("div");   box.innerHTML = "<td>a</td>";
const ta  = document.createElement("textarea"); ta.innerHTML = "<b>a</b>";


Show solution


The row gets a td element, because the fragment parser starts in "in row" mode for a tr context. The div gets only the text "a": "in body" ignores <td> and </td>. The textarea gets the text <b>a</b>, because the tokenizer starts in the RCDATA state for that context.21









Exercise 10: document.write() after load


A button runs document.write("Thanks!") when clicked. What does the user see, and why?


Show solution


A blank page containing only "Thanks!". By the time of the click the parser has finished, so there is no insertion point; document.write() therefore calls document.open(), which removes the whole document, and writes into a new, empty one.63,65









Exercise 11: Write "has an element in scope"


Given the stack of open elements as an array of tag names (bottom first), write inScope(stack, target, extraBoundaries) that implements the standard's scope check for HTML elements, and use it to define button scope and table scope.


Show solution


SolutionJS
const DEFAULT = ["applet", "caption", "html", "table", "td", "th", "marquee", "object", "template"];

function inScope(stack, target, boundaries = DEFAULT) {
  for (let i = stack.length - 1; i >= 0; i--) {   // from the current node down
    if (stack[i] === target) return true;
    if (boundaries.includes(stack[i])) return false;
  }
  return false;                                      // not reached: html is a boundary
}
const inButtonScope = (s, t) => inScope(s, t, [...DEFAULT, "button"]);
const inListItemScope = (s, t) => inScope(s, t, [...DEFAULT, "ol", "ul"]);
const inTableScope = (s, t) => inScope(s, t, ["html", "table", "template"]);

inButtonScope(["html", "body", "p", "button", "span"], "p");   // false: the button is a wall
inScope(["html", "body", "p", "button", "span"], "p");         // true


The real lists also contain the MathML mi, mo, mn, ms, mtext and annotation-xml elements and the SVG foreignObject, desc and title elements, which a full implementation would compare by namespace as well as name.28

  1. What does the HTML Standard say about turning <image> into <img>?

    Answer
    2,231 names, of which 106 legacy names are also recognised without the semicolon.37,38

  7. Which element, once opened, can never be closed?
    Answer
    plaintext. It switches the tokenizer to the PLAINTEXT state, which has no exit, so the rest of the file is text.3,35
    8. 

  8. What do </br> and </p> have in common?
    Answer
    Both can create an element from an end tag. </br> is treated as <br>, and a </p> with no open p in button scope inserts an empty p element and then closes it.35

    Answer
    The outer loop runs at most 8 times, and the inner loop removes formatting elements from the list instead of cloning them once it has passed 3.35,47

Debugging a strange tree
Validate first: every surprise in the tree is a parse error somewhere. Then look for the usual suspects: an unclosed formatting element, a block inside a p, content between table rows, or a missing DOCTYPE.6,8

  
Never parse HTML with a regex
Use the browser (DOMParser, template) or a standard-conforming library such as parse5, html5lib or html5ever, so that you see the tree browsers see.47,72,80,81

  
Security
Sanitize parsed DOM, not strings; do not re-serialise and re-parse after sanitizing; prefer setHTML() or a maintained sanitizer.10,73

  
Performance
Send the encoding in the HTTP header, keep scripts non-blocking, and put critical resources in the markup where the preload scanner can find them.30,70

  
Testing parsers
Run the html5lib tokenizer tests and the web-platform-tests tree-construction tests; print trees in the .dat format to compare implementations.82,83
