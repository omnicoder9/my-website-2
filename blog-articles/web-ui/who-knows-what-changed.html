1The question under every front-end technology

Every interactive web page holds the same information twice. One copy lives in the program’s variables: the number of items in a basket, whether a menu is open, the text a person has typed. The other lives in the document tree that the browser lays out and paints. When the first copy changes, the second has to follow, and it has to follow completely: a basket count updated in the header but not in the checkout button is a defect, however elegant the code that produced it. Everything else a front-end technology offers — templates, components, routers, build tools, server rendering — sits on top of one question. When a value changes, who knows which parts of the page depend on it?

The question is older than the web. Trygve Reenskaug formulated model–view–controller at Xerox PARC in 1978–79 1, and Krasner and Pope’s description of the Smalltalk-80 implementation made the dependency mechanism explicit: a model notifies its dependents that it has changed, and each view decides how to redraw itself 2. Fowler’s survey of GUI architectures traces how much of the subsequent design space is a set of variations on who holds that list of dependents and who acts on it 3. A second lineage came from functional programming. Elliott and Hudak treated values that vary over time as first-class objects, so that a program describes relationships and a runtime keeps them true 4. That lineage also named the characteristic failure of automatic propagation — the glitch, a computation that briefly observes some inputs updated and others not 5 — and fixed it by evaluating dependents in topological order 6. Flapjax brought the idea to the browser in 2009 7, before any of the mainstream frameworks this article compares had shipped.

Read against that background, the history of front-end technologies is not a march from “imperative” to “declarative”, which is how it is usually told. It is the migration of a single piece of knowledge — the map from each value to the nodes that display it — between four possible holders: the programmer, the data model, the framework’s runtime, and the compiler. Each move buys precision, and each move is paid for with a rule that constrains how the programmer is allowed to write or read state, because a framework can only know about changes it is allowed to see. The comparisons that follow — jQuery against Backbone, AngularJS against React, React against Vue, Svelte against Solid, zone.js against signals, hydration against resumability — are all comparisons of where that map lives, how much of the page is re-examined to use it, and what the programmer must do to keep it accurate.

The article is organised to make that claim testable. Section 2 defines a six-rung ladder for the first axis and two further axes for the others. Sections 3 to 7 walk the history in four eras, with worked mechanisms and six experiments from a build-time lab whose output is reproduced verbatim in the appendix. Section 8 shows one counter written ten ways. Section 9 prices a single change under each strategy. Section 10 is the census itself: thirty-one plates, one per mechanism, each coded on the three axes and drawn with the same small gauge. Section 11 reports what the census shows, and Section 12 turns it into advice and states the limits of the method.

2A ladder of knowledge, and two further axes

The primary axis is the rung: at the moment a value changes, which party already holds the information needed to find the nodes that depend on it. Six positions are enough to place every technology in the census, and they are ordered by how early and how exactly that information is established.

At K0 nothing records the dependency: the code that changes state must also find and edit every node that shows it. At K1 state objects announce changes, but code subscribed to the announcement still decides what to redraw. At K2 the framework keeps the previous value of every watched expression and compares all of them whenever something might have changed. At K3 the framework re-runs a function that produces a description of the view and compares the new description with the old. At K4 the framework records which computations read which values while they run, so a write can notify exactly those readers. At K5 a compiler determines the dependencies from the source text before the program runs and emits specialised update code.

The right-hand column of Figure 1 is the important one. Every rung above K0 depends on the framework seeing something, and what it needs to see differs by rung. A K2 framework needs to know when to look, so writes must happen inside its turn. A K3 framework compares references, so writes must produce new references. A K4 framework records reads, so reads must go through a tracked accessor rather than a copy. A K5 framework reads the source, so writes must use syntax the compiler recognises. These rules are not incidental API style; they are the price of the knowledge, and Section 11 shows that when the plates were coded, the rule each technology imposes sorted by rung without exception.

Rung alone does not fix the cost of a change, because two technologies at the same rung can re-examine very different amounts of the page. The second axis is therefore the unit of update: the node the programmer names, a whole application, a view and its subtree, the path from the root to the changed component, one component, one binding, or a fragment rendered on the server. The third axis is where the knowledge is used: entirely in the client, on the server with the browser swapping in results, in a hybrid of static HTML and interactive islands, or resumed in the browser from state the server serialised into the page.

Each plate in Section 10 carries a gauge called a touch tree. It draws the same fifteen-component tree every time: a value is held in the root component and passed down, and a single binding in the right-most leaf displays it; the magenta ring marks that leaf, the one place that genuinely had to change. A filled node is a component re-run or re-checked in full; a dashed ring is a component compared and skipped; a ring with a dot is a single binding updated without re-running the component; a hatched node never executes in the browser. The two numbers are the lab’s count of expression evaluations and DOM writes for that one change, with four bindings per component. The gauge is deliberately the harshest common case — state held far from where it is read — because that is where the rungs separate; Section 9 shows the gentler case in which state is local.

31998–2009: the page is the program

The first era had no frameworks in the modern sense because the platform had only just acquired an object model. The W3C’s DOM Level 1 Recommendation of October 1998 gave scripts a language-neutral interface for reading and modifying documents 8, and DOM Level 2 Events in November 2000 standardised addEventListener and the capture-and-bubble model of event propagation 9; both are now maintained as the WHATWG DOM Living Standard 10. Nothing in those interfaces records that a text node shows a particular variable. Every page built directly on them is at K0, and so is every library of the era, because the libraries improved the vocabulary for finding and editing nodes without changing who had to know which nodes to edit.

The pressure that ended the era came from asynchronous requests. Jesse James Garrett’s February 2005 essay gave the name Ajax to the pattern of fetching data in the background and updating part of a page in place 11; the object that made it possible was later standardised as XMLHttpRequest 12. Partial updates multiplied the number of places where the page could fall out of step with the data, and they introduced the first ordering problem: two responses for the same region arriving in the opposite order to their requests. Prototype, released in 2005, extended DOM elements and supplied a class system to make such code manageable 13.

jQuery, which John Resig introduced at BarCamp New York on 14 January 2006 and released as 1.0 that August 14,15, became the dominant answer. Its proposition was a selection — a set of elements named by a CSS selector — and a chain of operations applied to the whole set, with the differences between browsers hidden underneath. The selector engine that shipped with it, Sizzle, was designed to be usable on its own 16; the platform later absorbed the idea directly when querySelectorAll became part of the Selectors API Recommendation 17. jQuery reached 4.0.0 on 17 January 2026, its first major release in almost ten years, dropping support for Internet Explorer 10 and older 15. It remains on roughly two-thirds of all websites that W3Techs surveys 18,19, and 23.4 per cent of respondents to Stack Overflow’s 2025 survey still reported using it 20. No other technology in this article is deployed on more pages.

What jQuery did not change is the rung. A handler that increments a counter must also update every element that displays the count, and the only record of which elements those are is the handler’s own code. In small pages that is a virtue: there is no mechanism to learn, and the cost of an update is exactly one DOM write, the minimum any strategy can achieve. The failure mode appears when a second part of the page begins to display the same value, and when code starts to read state back out of the DOM to decide what to do next, so that the document becomes the store of record. At that point the knowledge of dependencies is spread across every handler that touches the page, and no single place can answer the question in the title.

The browser itself had faced the same question earlier, for style rather than content, and its answer is instructive. When a class changes, the style engine must work out which elements now match which rules. Browser engines match selectors from right to left, testing the rightmost compound against an element first and walking up its ancestors only if that succeeds 21. The lab’s sixth experiment shows why that direction was chosen, and it is not the reason usually given. On a 3,000-node tree, finding every match for one selector, section div.item span, cost 7,858 node visits left to right and 9,170 right to left — the supposedly efficient direction lost, by a ratio of 0.86. But after toggling one class, recomputing a forty-rule stylesheet cost 348,187 visits left to right, which must re-run every rule over the whole document, against a mean of 887.7 right to left, which only needs to re-ask “does this element still match?” for the changed element and its descendants: a factor of 392. Right-to-left matching wins because it localises the question to the part of the tree that changed. The frameworks of the next twenty years would rediscover the same principle for content.

42010–2012: the first model–view wave

Three libraries released in 2010 each moved the knowledge off the programmer’s hands in a different direction, and between them they occupy three different rungs.

Backbone gave the data a home. Its models hold attributes and emit a "change" event when an attribute is set through the model’s set method; views subscribe to their models and typically respond by re-rendering their template 22. That is K1: the model knows that something changed, but the view still decides what to redraw, and the common decision — replace the view’s inner HTML — rebuilds everything the view owns. In the canonical touch tree a Backbone-style view one level below the root costs 28 evaluations and 28 DOM writes to change one number, and rebuilding the markup discards focus, scroll position and the state of any nested views. The rule it imposes is the mildest of any rung above K0: write through set, so the event fires.

Knockout went further than its contemporaries and, in retrospect, further than most of its successors for a decade. A Knockout observable is a function; reading it by calling it records the read, and computed observables and bindings re-evaluate automatically when anything they read changes 23,24. That is K4, fine-grained dependency tracking at the level of a single binding, in 2010 — three years before React was open-sourced. The rule is the K4 rule in its purest form: read through the accessor, and do not edit an array in place without going through the observable wrapper, because the tracker cannot see what it is not asked for.

AngularJS took the opposite approach and asked nothing of the programmer’s data. Any plain JavaScript object on a scope could be bound into a template. The framework kept a list of watch expressions — one for every binding — and, after any event that ran through its $apply method, it ran a digest: evaluate every watcher, compare each result with the last one, run the listeners of those that changed, and repeat until a full pass finds nothing dirty 25,26. This is K2. Because a listener may change a value that another watcher reads, the loop must run at least twice for any change, and it is bounded: after ten dirty iterations AngularJS aborts with the $rootScope:infdig error 27.

The lab’s second experiment reproduces the loop and shows what that bound means in practice. A chain of watchers, each writing a value the next one reads, settles in two iterations if the watchers were registered in dependency order, because one pass carries the change along the whole chain. Registered in reverse, each pass advances the change by one link, so a chain of n watchers needs n + 1 iterations: a chain of ten costs 11 iterations and 110 evaluations, and a chain of 11 throws. Nothing in the template tells the author which order the watchers were registered in. That is the characteristic cost of K2: the framework knows what changed only by looking at everything, and the price of looking depends on facts the programmer cannot see.

AngularJS was enormously productive for small and medium applications precisely because it asked for nothing. Its long-term support ended on 31 December 2021 28, yet 7.2 per cent of respondents to Stack Overflow’s 2025 survey still reported working with it 20.

52013–2018: the view as a function

React, open-sourced on 29 May 2013 29, proposed something that sounded extravagant: re-render the whole view whenever anything changes, and let the library work out the difference. Pete Hunt’s explanation that summer framed it as a way of making UI code as simple to reason about as a server-rendered page that is regenerated on each request 30. The render function returns a lightweight description of the view — the virtual DOM — and a reconciler compares it with the previous description to derive the minimal set of DOM operations. That is K3. Nobody knows in advance which nodes depend on a changed value; the framework finds out after the fact, by comparison.

Comparison is only affordable because it is approximate. The general problem of transforming one tree into another has cubic-time algorithms 31,32, and React’s documentation states the trade explicitly: it assumes that elements of different types produce different trees and that the programmer marks stable children with a key, which reduces reconciliation to linear time 33,34. The key is revealing. It is a piece of K0 knowledge — only the programmer knows that the row with key 998 is the same record it was before — passed into a K3 mechanism because the comparison cannot recover it.

Even with keys, how a list is reconciled matters. React’s child reconciler makes a single pass over the new children, keeping the largest old index placed so far and moving any child whose old index falls below it 35. Vue 3’s renderer instead computes a longest increasing subsequence of old positions and moves only the children outside it 36, using an algorithm family that goes back to Schensted and Fredman 37,38. The lab’s third experiment applies both to a thousand-row list and the operations used by the widely cited js-framework-benchmark 39. Swapping rows 2 and 999 costs the single-pass rule 997 moves against a minimum of 2. Moving the last row to the front costs 999 against 1; moving the first row to the end costs 1 against 1. The single-pass rule is optimal when items drift toward the end and pathological when one item jumps to the front. Without keys the picture is worse in a different way: prepending one row rewrites the content of all 1,000 rows, because every position now holds different data. These are counts of DOM operations, not timings; the point is that K3’s cost depends on the shape of the change as well as its size.

The limitation that mattered most in practice was the unit of update. When a component calls setState, React re-renders that component and every descendant, so state held high in the tree re-renders large subtrees for a change that affects one leaf: in the canonical touch tree, 60 evaluations to update one binding. PureComponent and later React.memo let a component skip re-rendering when a shallow comparison finds its props unchanged 40, which cuts the canonical cost to 19 — the path from root to leaf plus one comparison at each sibling — at the price of another rule: prop references must stay stable, so an inline object or callback defeats every comparison. React Fiber, the reconciler rewrite described in 2016, made rendering interruptible and prioritised 41; it changed when the comparison runs, not what is known.

Flux and then Redux answered a different problem, the tangle of two-way bindings between models and views, with a single direction of data flow: actions go to a store, the store computes new state with pure reducers, and views re-render from the result 42,43. Their contribution to the question in the title is subtle. A store that tells every subscriber “something changed” leaves each subscriber to work out whether its own slice changed, so dirty checking reappears one layer up: each selector is re-run and its result compared. The census therefore codes the pattern at K2, with immutability as the rule that makes the comparison cheap.

Vue approached the same problem from the Knockout side. Vue 2 converted each property of a component’s data into a getter and setter using ES5’s Object.defineProperty 44; during render the getters record which component read them, and a setter schedules exactly those components to re-render 45. That is K4 at the granularity of a component, with a virtual DOM diff inside each component that re-renders. The mechanism has well-documented blind spots that follow directly from the rung: because tracking is installed property by property when an object becomes reactive, Vue 2 cannot detect a property added later or an array element set by index 45. MobX brought the same idea to React, making observer components re-render when the observables they dereferenced change 46.

Angular — the 2016 rewrite, announced as final on 14 September that year and incompatible with AngularJS 47 — kept K2 but changed how the framework knows when to look. zone.js patches the browser’s asynchronous APIs so that the framework is told whenever a task it can see completes 48, after which change detection walks the component tree once, top down, checking every binding: 60 evaluations in the canonical tree. The OnPush strategy restricts the walk to components whose input references changed or that were explicitly marked 49, bringing the canonical cost to 16. The rule of the default strategy is invisible, which is its appeal and its weakness: code that runs outside the zone is never followed by a check.

Svelte took the remaining rung. Rich Harris’s 2016 announcement described a framework that runs at build time and disappears, compiling components into imperative code 50; his 2018 essay argued that the virtual DOM is overhead a compiler can remove 51; and Svelte 3 in 2019 made assignment itself the trigger for updates 52. The compiler sees every assignment to component state and every template expression that reads it, and emits update code that checks a dirty bit per variable. That is K5, and the canonical cost is 16 bit checks along the path. The rule is the compiler’s field of view: a change the compiler cannot see as an assignment — an array mutated by a method call, for example — does not update the page.

The platform acquired its own component model in the same period. Custom elements, now part of the HTML standard, let authors define new tags with lifecycle callbacks, including one for changes to attributes they declare as observed 53. They supply encapsulation and interoperability, not reactivity: an element’s author decides what to update, so a bare custom element sits at K0. Lit adds declared reactive properties that schedule an asynchronous update when assigned, and a template system that re-evaluates only the dynamic parts of a template and compares their values 54,55, which places it at K3 with a much smaller unit than a virtual DOM.

62019–2026: signals, compilers and convergence

The most recent era began inside React. Hooks, released in React 16.8 in February 2019, let function components hold state and effects 56. Hook state is stored by the order of calls, which is why the Rules of Hooks forbid calling a hook conditionally or in a loop 57: the rule is again the price of what the framework needs to see, here the identity of each piece of state across renders. React 18 in 2022 extended automatic batching so that several state updates in one task produce one render 58, and React 19 in December 2024 stabilised Actions and Server Components 59. React 19.2 in October 2025 added the Activity component and useEffectEvent 60, React Compiler reached 1.0 the same month 61, and React 19.3, released on 9 September 2026, made View Transitions and Fragment Refs stable 62. Governance moved as well: in February 2026 React, React Native and JSX passed from Meta to an independent React Foundation hosted by the Linux Foundation 63.

React Compiler is the clearest statement of React’s position on the ladder. It analyses components at build time and inserts the memoisation that programmers previously wrote by hand with memo, useMemo and useCallback 61. A compiler now decides where to compare, but the comparison itself still happens at run time. React therefore remains at K3 by choice, and has moved its effort into reducing the unit of update and, through Server Components, into the third axis.

Almost everywhere else, the era converged on K4 under the name signals. Ember’s Octane edition, released in December 2019, replaced observers with autotracking: properties marked @tracked are recorded as they are read during rendering, and only the affected template nodes are revalidated 64,65. Vue 3, released on 18 September 2020 66, rebuilt Vue’s tracking on ES2015 Proxies 67,68, which removed the property-addition blind spot, and paired it with a compiler that flags which nodes of a template are dynamic so the runtime diff skips the rest 69. Vue 2 reached end of life on 31 December 2023 70. Solid, which reached 1.0 in 2021, applied fine-grained tracking without a virtual DOM at all: component functions run once to build the DOM, and each signal’s subscribers are the individual DOM updates that read it 71. Preact added signals in September 2022 that can be bound directly into a text node so that the component never re-renders 72.

Angular is the one project that has walked the ladder in public. Signals arrived in 2023 73, and a signal read in a template marks that component’s view for refresh, making zone.js unnecessary 74. Angular 21, released on 19 November 2025, made zoneless change detection the default for new applications 75, and Angular 22, released on 3 June 2026, made OnPush the default for new applications, renamed the old default strategy Eager, and declared Signal Forms and the asynchronous resource APIs stable 76. The same framework family has now occupied K2 with a digest, K2 with zones, K2 along a path with OnPush, and K4 with signals.

Svelte moved in the opposite direction. Svelte 5, released in October 2024, replaced implicit assignment tracking with runes — compiler keywords such as $state and $derived — that compile to signals tracked at run time 77,78. The only K5 technology in the census was retired by its own authors in favour of K4. The reason follows from the rung: a compiler knows only what it can see, and dependency tracking that stops at the edge of a component file cannot follow state into ordinary modules and functions, whereas a run-time tracker records reads wherever they happen. Vue is converging from the other side: Vue 3.6, at release-candidate stage in 2026, rebuilds its reactivity core on the alien-signals design and adds an opt-in Vapor mode that compiles components to direct DOM operations with no virtual DOM 79. Solid 2.0 reached release candidate on 19 August 2026 with asynchronous values made part of the reactive graph 80,81. A proposal to standardise signals in JavaScript itself is before TC39 82.

Fine-grained propagation reintroduces the problem the functional-reactive literature named first. If a write notifies dependents eagerly, depth first, a computation with two paths back to the same source can run while one path is updated and the other is not. The lab’s fourth experiment makes this concrete. In the diamond where D reads both B and C and both read A, eager notification evaluates D twice, once with a stale C, for 4 evaluations and 1 glitch; evaluating in order of height takes 3 and none. On a random graph of 8 sources and 52 derived values, 500 writes cost 30,628 eager evaluations against 16,177 ordered ones, a ratio of 1.89; 27.1 per cent of eager evaluations saw inconsistent inputs, and 5,914 of them were sinks — the computations that would write to the DOM. This is why signal libraries do not notify eagerly: marking dependents dirty on write and recomputing lazily in dependency order, the solution FrTime described in 2006 6, is what makes K4 correct as well as precise 5.

7Where the knowledge is used

The third axis became central once server rendering returned to fashion. A page rendered to HTML on the server appears quickly, but in the classic arrangement the browser must then hydrate it: download the component code, execute every component again to rebuild the framework’s internal model of the page, and attach event listeners. Hevery’s critique is that hydration repeats on the client work the server has already done, only to recover knowledge — which handlers belong where, which state feeds which node — that the server possessed and discarded 83. Since 12 March 2024 the cost has been measured publicly, because Interaction to Next Paint replaced First Input Delay as a Core Web Vital 84.

Four responses are in the census. The islands architecture, named by Jason Miller in 2020, renders most of a page as static HTML and hydrates only the independently interactive regions 85; Astro adopted it with directives that declare which components ship code to the browser and when 86. React Server Components divide a React tree into components that run only on the server and never re-render in the browser, and client components marked with a directive, which behave as ordinary React 87. htmx returns the knowledge to the server entirely: any element can issue a request and swap the returned HTML into a target it names 88, an approach its authors set out at length as hypermedia-driven applications 89. Alpine sits next to it, adding a small amount of client behaviour to server-rendered markup through attributes, using a reactivity engine borrowed from Vue 90. Qwik takes the furthest step: it serialises the framework’s state and listener locations into the HTML so that the browser resumes rather than replays, and loads each handler’s code only when that handler first runs 91.

The lab’s fifth experiment is a counting model rather than a benchmark, but it shows the size of the differences. On a page of 240 components of which 18 are interactive, full hydration executes all 240 before the page can answer its first input; islands execute 18, 7.5 per cent of the page; a resumable page executes none, and over a session of 12 clicks drawn from a skewed popularity distribution it loads the code of 7.12 components on average (median 7). None of these strategies changes the rung: an island written in React is still K3 inside the island, and a resumed Qwik page is K4. What they change is how much of the rung’s machinery has to be rebuilt in the browser before it can be used.

8One counter, ten ways

The smallest program that exercises the question is a counter: one value, one button that changes it, one place that shows it. The ten listings below are each complete for their technology and deliberately minimal. The comment in each marks where the knowledge lives. 9The cost of one change

The first experiment prices a single change under every strategy in the census, on binary component trees from 15 to 1,023 components, with four bindings per component. Two placements of state are compared. In the drilled case the value is held at the root and passed down to one leaf, which is what happens to shared state in most applications; in the local case the leaf owns the value itself. Work is counted as expression evaluations and comparisons, with DOM writes counted separately.

With state held at the root of a 1,023-component tree, one change costs 8,184 evaluations under dirty checking with its mandatory second pass, 4,092 under an unmemoised virtual DOM or zone-based change detection, 2,044 evaluations and as many DOM writes under Backbone-style view re-rendering, 49 with memoised component boundaries, 40 with compiled dirty bits or OnPush, 4 when a signal marks one component, and exactly 1 when a signal updates one binding. The first two grow linearly with the size of the application (exponent 1.000); memoised and compiled strategies grow with the depth of the tree (exponents 0.224 and 0.217); signals do not grow at all. Memoisation alone recovers a factor of 83.5 at this size.

The local case changes the picture completely. When the leaf owns its state, the virtual DOM, memoised boundaries, compiled bits and component signals all cost 4 evaluations — the leaf’s own four bindings — and only the K2 strategies still pay for the whole tree, because they do not know where to start. The rung matters most when state is far from where it is read. That is the quantitative content of the advice, common in React circles, to keep state close to the components that use it: it is a way of making a K3 framework behave, for most changes, like a K4 one.

These are counts, not timings. A virtual-DOM comparison of an unchanged string is cheap, a signal carries bookkeeping on every read, and real applications are neither binary trees nor uniform. Benchmarks that measure wall-clock time on real operations, such as js-framework-benchmark, exist for that purpose 39. What the counts establish is the shape of each strategy’s cost — linear, logarithmic or constant in the size of the application — and that shape is fixed by the rung and the unit, not by implementation quality.

11What the census shows

Coded on the three axes, the thirty-one plates support six findings. The first is visible in Figure 8: the mean rung rises across the eras, from 0.00 in 1998–2009 to 2.33 in 2010–2012, 2.80 in 2013–2018 and 3.46 in 2019–2026 (Astro, which inherits the rung of whatever runs in its islands, is excluded). The rise is real, but it is not the whole story.

Second, fine-grained tracking is older than the virtual DOM. The first K4 plate is Knockout in 2010; the first K3 plate is React in 2013. K4 accounts for 1 of the three plates from 2010–2012, 2 of the ten from 2013–2018 and 9 of the thirteen rung-coded plates from 2019–2026. The industry did not progress from diffing to signals; it went from signals to diffing and back. What changed between Knockout and Solid was not the idea but its surroundings: Proxies to make tracking transparent, compilers to supply the accessors so that the programmer does not have to call them, and a body of work on glitch-free scheduling.

Third, the only K5 plate did not stay there. Svelte 1 to 4 is the census’s single case of dependencies established entirely at compile time, and Svelte 5 moved to K4. The compiler’s knowledge is bounded by what one compilation unit can see, and the other compile-time entries in the census — React Compiler, Vue’s patch flags, Vapor mode, Solid’s JSX transform — all use the compiler to prepare run-time knowledge rather than to replace it. The lesson is that compilers are the best place to supply accessors and remove boilerplate, and a poor place to hold the dependency graph itself.

Fourth, rung and unit are different axes. Figure 9 crosses them. Vue 2 and Vue 3 are K4 but update along a path, because tracking stops at the component and a virtual DOM diff runs inside it; Angular with OnPush is K2 along the same path; React with memoisation is K3 along it. Three different kinds of knowledge produce the same unit of update, which is why benchmark results for these three are closer than their mechanisms would suggest. The unit of update is set by the finest granularity at which the knowledge is recorded, not by the rung.

Fifth, every rung has its rule, and the rule sorts by rung. When the third field of each plate was written — what the programmer must let the framework see — it fell into its rung’s category in every case: write through a setter at K1; write inside the framework’s turn or replace immutably at K2; produce new references and keep render pure at K3; read through a tracked accessor at K4; write syntax the compiler recognises at K5. The failure field sorts the same way, because each characteristic failure is a violation of the rung’s rule: an in-place array edit that Knockout and Vue 2 never see, a mutated input that OnPush never re-checks, a destructured prop that Solid never updates, a push that Svelte 3 never compiles into an update. Choosing a front-end technology is, to a first approximation, choosing which of these mistakes a team will make and how it will find out.

Sixth, the two largest projects moved in opposite directions. Angular crossed from K2 to K4 over a decade and a breaking rewrite, and by 2026 defaults new applications to zoneless change detection and OnPush 75,76. React stayed at K3 and moved its effort to the other two axes: a compiler to shrink the unit of update 61 and Server Components to move work off the client 87. In Stack Overflow’s 2025 survey React was used by 44.7 per cent of respondents, Angular by 18.2, Vue by 17.6 and Svelte by 7.2, while Svelte had the highest admiration score of the four at 62.4 per cent 20. Popularity, in other words, does not track rung. The most-used framework is at K3 and the most-admired at K4, and both remain far behind jQuery in deployed pages.

The census suggests five practical questions to ask before choosing. First, where does your state live relative to where it is read? If most state is local to the component that displays it, the rungs from K3 upward cost almost the same (Section 9), and ecosystem, hiring and tooling should decide. If much state is shared and held high — dashboards, editors, collaborative tools — the difference between linear and constant cost per change becomes visible, and K4 or disciplined memoisation matters. Second, how much of the page is interactive? For content-led sites the third axis dominates: islands, server components or a hypermedia approach remove most of the client work regardless of rung (Section 7). Third, which rule will your team keep reliably? Immutability, stable references, call-order discipline, tracked reads and compiler-visible writes each fail in characteristic ways, and a team that already thinks in immutable data will find K3 easier than one that thinks in mutable objects, for which K4’s proxies feel natural. Fourth, how will the knowledge survive growth? K0 is optimal for a page with a handful of interactions and unmanageable for an application; K2 is effortless until the watcher count or ordering bites. Fifth, how long must the code live? jQuery’s persistence on two-thirds of the web 18 and AngularJS’s end of support 28 are the two poles: a stable K0 library with a small surface outlives frameworks, and a framework that changes rung may leave its users behind.

The account has limits that a reader should weigh. The rung assigned to each plate is a coding judgement about the mechanism a technology uses by default; most mature frameworks offer escape hatches to other rungs, and some plates, such as Flux and Redux at K2, describe a common pattern rather than a single library. The lab counts operations on idealised trees and does not measure time, memory or bundle size; its hydration model counts components rather than bytes; and its selector experiment uses random trees rather than real pages. Version details were checked against primary sources in September 2026 and will date. None of these limits touches the central claim, which is structural: each technology in this history is an answer to the question of who knows what changed, and its costs, rules and failures follow from the answer.

    out, st = [], [r]
    while st:
        n = st.pop(); out.append(n); st.extend(reversed(children[n]))
    return out

def path_to(parent, n):
    p = []
    while n >= 0:
        p.append(n); n = parent[n]
    return list(reversed(p))

def e1_costs(depth, scenario):

    C = len(parent)
    target = C - 1                      # right-most leaf reads the value
    path = path_to(parent, target)      # root .. target
    P = len(path)
    sib_bail = sum(len(children[n]) - 1 for n in path[:-1])
    lvl1 = [n for n in range(C) if level[n] == 1][-1]
    S1 = len(subtree(children, lvl1))
    r = {}

        r["zone_onpush"] = (P * K, 1, path, [])
        r["vdom"] = (C * K, 1, list(range(C)), [])
        r["vdom_memo"] = (P * K + sib_bail, 1, path,
                          [c for n in path[:-1] for c in children[n] if c not in path])
        r["compiled_bitmask"] = (P * K, 1, path, [])
        r["signals"] = (1, 1, [target], [])
        r["component_signal"] = (K, 1, [target], [])
        r["view_rerender"] = (S1 * K, S1 * K, subtree(children, lvl1), [])
        r["fragment_swap"] = (0, 3 * K, subtree(children, parent[target]), [])
    else:  # local: the leaf owns its own state
        r["manual"] = (1, 1, [target], [])
        r["digest"] = (2 * C * K, 1, list(range(C)), [])
        r["zone_default"] = (C * K, 1, list(range(C)), [])
        r["zone_onpush"] = (P * K, 1, path, [])

def digest(n, favourable, ttl0=10):
    v = [0] * (n + 1)
    # watcher j watches v[j-1] and writes v[j] = v[j-1] + 1
    order = list(range(1, n + 1)) if favourable else list(range(n, 0, -1))
    last = [None] * (n + 1)
    def run():
        ttl = ttl0; it = 0; evals = 0; dirty_iters = 0
        while True:
            it += 1; dirty = False
            for j in order:
                evals += 1
                val = v[j - 1]
                if val != last[j]:
                    last[j] = val; v[j] = val + 1; dirty = True
            if dirty:
                dirty_iters += 1
                if ttl == 0:
                    return it, evals, dirty_iters, True
                ttl -= 1
            else:
                return it, evals, dirty_iters, False
    run()               # settle
    v[0] += 1           # the one external change
    return run()

def lis_len(seq):
    tails = []
    for x in seq:
        i = bisect_left(tails, x)
        if i == len(tails): tails.append(x)
        else: tails[i] = x
    return len(tails)

def reconcile(old, new):
    oldpos = {k: i for i, k in enumerate(old)}
    common = [k for k in new if k in oldpos]
    inserts = len(new) - len(common)
    removes = len(old) - len(common)
    # React-style single pass: move if old index < lastPlacedIndex
    last = 0; react_moves = 0
    for k in new:
        if k in oldpos:
            oi = oldpos[k]
            if oi < last: react_moves += 1
            else: last = oi
    lis_moves = len(common) - lis_len([oldpos[k] for k in common])
    # unkeyed: rows compared by position, content rewritten where different
    m = min(len(old), len(new))
    unkeyed_patches = sum(1 for i in range(m) if old[i] != new[i])
    return {"react": react_moves, "lis": lis_moves, "inserts": inserts, "removes": removes,
            "unkeyed": unkeyed_patches, "unkeyed_create": max(0, len(new) - len(old)),
            "unkeyed_remove": max(0, len(old) - len(new))}

def make_dag(rng, nsrc, nder):
    inputs = [[] for _ in range(nsrc)]
    for i in range(nsrc, nsrc + nder):
        k = rng.choice([2, 2, 3])
        inputs.append(sorted(rng.sample(range(i), k)))
    deps = [[] for _ in inputs]
    for i, ins in enumerate(inputs):
        for j in ins:
            deps[j].append(i)
    height = [0] * len(inputs)
    for i in range(len(inputs)):
        if inputs[i]:
            height[i] = 1 + max(height[j] for j in inputs[i])
    return inputs, deps, height

def affected(deps, s):
    seen = [False] * len(deps); st = [s]; seen[s] = True; out = []
    while st:
        n = st.pop(); out.append(n)
        for d in deps[n]:
            if not seen[d]:
                seen[d] = True; st.append(d)
    return seen, out

def propagate_eager(deps, inputs, s):
    stale, _ = affected(deps, s)
    stale[s] = False
    evals = glitches = sink_glitches = 0
    def push(n):
        nonlocal evals, glitches, sink_glitches
        for d in deps[n]:
            evals += 1
            if any(stale[j] for j in inputs[d]):
                glitches += 1
                if not deps[d]:
                    sink_glitches += 1
            else:
                stale[d] = False
            push(d)
    push(s)
    return evals, glitches, sink_glitches

def propagate_topo(deps, height, s):
    seen, aff = affected(deps, s)
    aff = [a for a in aff if a != s]
    return len(aff)

        cls.append("item" if rng.random() < 0.15 else "")
    children = [[] for _ in range(N)]
    for i in range(1, N):
        children[parent[i]].append(i)
    def comp_match(c, n):
        t, needcls = c
        return tag[n] == t and (not needcls or cls[n] == "item")
    # --- (a) one selector, one query: find every match -------------------
    def ltr_query(sel):
        visits = N
        cur = [n for n in range(N) if comp_match(sel[0], n)]
        for c in sel[1:]:
            seen = [False] * N; nxt = []
            for r in cur:
                st = list(children[r])
                while st:
                    n = st.pop(); visits += 1; st.extend(children[n])
                    if comp_match(c, n) and not seen[n]:
                        seen[n] = True; nxt.append(n)
            cur = nxt
        return sorted(cur), visits
    def rtl_element(sel, n):
        # does element n match sel?  (key compound first, then ancestors)
        visits = 1
        if not comp_match(sel[-1], n):
            return False, visits
        i = len(sel) - 2; a = parent[n]
        while a >= 0 and i >= 0:
            visits += 1
            if comp_match(sel[i], a): i -= 1
            a = parent[a]
        return i < 0, visits
    def rtl_query(sel):
        visits = 0; out = []
        for n in range(N):
            m, v = rtl_element(sel, n); visits += v
            if m: out.append(n)
        return out, visits
    main = [("section", False), ("div", True), ("span", False)]
    a1, l1 = ltr_query(main); a2, r1 = rtl_query(main)
    assert a1 == a2
    # --- (b) a stylesheet, restyled after one class change ----------------
    utags = ["div", "span", "p", "li", "ul", "a", "section"]
