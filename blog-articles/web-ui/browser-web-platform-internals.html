The question

A browser is normally explained as a stack of parts. There is a process that owns the window, a process that runs the page, a process that talks to the graphics driver; there is a parser, a style engine, a layout engine, a compositor; there is an event loop with two queues; there are several dozen APIs for storing things and several more for moving bytes between machines. All of this is true, and almost none of it explains why the platform is shaped the way it is.

Here is a question that does. For any operation a page performs — reading a cookie, measuring an element, opening a socket, calling into compiled code — who waits? Something has to travel: to a deferred piece of the engine's own state, to the end of the current task, to another thread, to another process, to a machine on the other side of the world. While it travels, something is either stopped or free to do other work. Every design decision in the web platform since about 2010 has been an argument about that second clause.

The claim of this article is that the two facts — how far a request must travel, and whether the caller is stopped while it does — are separable, that they are usually confused, and that the platform's genuine mistakes are all the same mistake: a surface where the crossing is deep and the caller is stopped anyway. That combination is rare. It is also, without exception, legacy.

The ladder

Every crossing in this article is placed on a six-rung ladder. The rung is not a measure of cost in milliseconds, and it is not a measure of importance. It is the distance a request must go before its answer exists.

Alongside the rung, each crossing carries a second, independent property: its return posture. The caller may be held — stopped until the crossing completes; released — given control back at once, with the result arriving later on this agent's event loop; or the crossing may be one the caller never sees, performed by the engine or another agent on a schedule of its own. Thirty-two crossings are coded on both axes in the plates that follow, and collected in a ledger at the end.

The coding rule that keeps the rungs from being arbitrary: a crossing sits at the deepest rung its answer must reach on the platform as specified, not on the fastest path a particular engine has managed to build. Chrome caches cookies in the renderer; Safari and Firefox make similar bets. None of that changes where document.cookie is defined to read from, and none of it lets an engine return control to the caller first, because the API's signature forbids it. The rung records the boundary the specification obliges the engine to be able to cross; the posture records what the API's shape does to the caller while it crosses.

Why the distinction is worth making

Consider four operations that a working web developer would file in four different mental drawers. Reading element.offsetTop may run the entire layout algorithm over the document. Reading localStorage may require a round trip to another process. Awaiting a fetch() reaches a server on another continent. Calling an exported WebAssembly function reaches nothing at all — it is a direct call in the same address space. Ranked by distance, those are rungs one, five, five and zero. Ranked by what they do to the caller, the first two stop it and the last two do not, which means the shallowest and the deepest of the four are the two that block. Distance and blocking are not correlated in the platform we actually have; they are correlated in the platform people carry in their heads, and the gap between those two pictures is where most performance bugs live.

The web platform is specified across a genuinely unusual number of documents — living standards at the WHATWG 123, Recommendation-track work at the W3C 4, protocol standards at the IETF, and a language specification at Ecma 5— and it is implemented by three independent engine families that have agreed, since 2021, to measure their disagreements in public against a shared test suite 67. The seams between those documents are themselves specified: an interface definition language that every API is written in 8, and a document of shared primitives that the others build on 9. Interop 2026, the sixth cycle, selected twenty focus areas from thirty-three proposals out of more than a hundred and fifty submitted, plus four investigations; the previous cycle's shared score rose from 25 to 95 over the year and to 97 in the month after it closed 10111213. That is a useful thing to know before reading any account of "how browsers work": the places where they still differ are now enumerated, tested and scored, and the places described in this article are mostly not among them.

What the browser is made of

The single most consequential fact about a modern browser is that the code which runs your page has no capabilities. It cannot open a file, cannot open a socket, cannot read a cookie from the disk, cannot show a dialogue. It runs in a sandboxed process whose only external interface is a message channel to a process that can do those things 1415.

Structurally this is a departure from what a browser was. A reference architecture drawn up in 2005, when the field was still monolithic, described a browser as a layered pipeline of subsystems inside one address space 16; the multi-process design cuts that pipeline across the middle and puts an operating system boundary in the gap.

This arrangement is now eighteen years old in Chromium and rather newer elsewhere, and it was originally justified by robustness and responsiveness: one page's crash should not take the window with it, and one page's infinite loop should not freeze the others 1417. The security argument came later and turned out to be the stronger one. A renderer that has been fully compromised — arbitrary code execution inside the sandbox — still has to ask the browser process for everything, and the browser process can decline.

Then, in 2018, that guarantee stopped being sufficient. Speculative-execution attacks made it possible to read memory within a process without any memory-safety bug at all 1819, and a browser that put two websites in one renderer was therefore putting two websites' secrets within reach of each other. The response was Site Isolation: a process per site, extended to cross-origin iframes, so that the data of one site is never resident in a process where another site's code runs 2021. Firefox shipped the equivalent under the name Fission 22. The cost is memory and process count — a browser's memory footprint is largely a function of how many processes it is running 23— and the benefit is that a class of attack becomes an attack on the operating system's address-space separation rather than on a language runtime's.

Two consequences follow for everything below. First, every capability the platform offers has to be expressed as a message to another process, and a message to another process cannot be answered synchronously without stopping the caller. This is the deep reason that nearly every web API designed after about 2012 returns a promise, and the deep reason that the handful designed before it are the ones this article keeps returning to. Second, the browser has become a distributed system inside a single application, with a service for the network, a service for storage, a process for the GPU, and an interface definition language to describe the calls between them 24.

Rendering has its own process. The renderer produces a compositor frame — a list of quads referring to textures, together with the transforms that place them — and hands it to a display compositor in the GPU process, which combines frames from every renderer and from the browser's own user interface into what the screen shows 25262728. The significance of this is easy to miss: the last stage of drawing your page is performed by a process that is not running your code and cannot be blocked by it.

From bytes to a box tree

Inside the renderer, the page begins as bytes and ends as a structure the compositor can draw. The stages between are conventionally called the critical rendering path, and the conventional diagram of them is misleading in one specific way that is worth correcting.

The DOM is a tree of nodes with an API that has been specified, in its current form, as a living standard for over a decade 3. It is built incrementally by a parser that is designed to be resumed, so that a document can be displayed before it has finished arriving, and that is specified in extraordinary detail precisely because every real-world document is malformed in some way 33. The CSSOM is the parsed form of the stylesheets 3435. Scripts complicate both, because a classic script may write into the parser's input stream and so must block it 36, and elements such as canvas introduce their own imperative surfaces on top of the tree 37. The misleading part of the usual diagram is the arrow from "DOM + CSSOM" to "render tree", which suggests a merge. What actually happens is that the cascade is evaluated for each element to produce computed values 38, using selector matching that must run against a tree that is still changing 39, and the result is a set of computed styles attached to elements — not a third tree assembled from two others.

From computed style, layout produces a box tree, and this is where the platform's most persistent performance characteristic originates. Layout is a constraint problem over the whole document: a box's width can depend on its parent's, its height on its children's, its position on its siblings'. Chromium's current layout engine, LayoutNG, restructured this into an algorithm that produces immutable fragments from explicit constraint inputs, which makes subtrees independently recomputable and re-usable in a way the previous design could not manage 4041. The general problem, though, remains what a decade-old analysis found it to be: layout resists parallelisation not because engines are badly written but because the dependency structure of CSS box layout is genuinely sequential in the places that matter 42. Style is different — Firefox's Stylo demonstrated that selector matching and cascade evaluation parallelise well 43.

What actually determines when a page appears is rarely any single stage. Instrumenting the browser to attribute page-load time to its causes found the critical path dominated by dependencies between resources rather than by computation 44, a result that motivated schedulers which track those dependencies explicitly 45; on mobile hardware the balance shifts again, with compute a larger share than on the desktop 46.

What "the render tree" actually is

The phrase persists in every tutorial and no specification defines it. What engines build is a tree of layout objects that corresponds to the DOM only loosely: elements with display:none generate no box at all and simply are not there, pseudo-elements generate boxes with no node behind them, a single element may generate several boxes when its content is fragmented across columns or pages, and anonymous boxes are invented to satisfy the box model's structural rules 47. LayoutNG then produces from that a second, immutable structure — the fragment tree — which is what paint walks and what can be cached and reused when only part of the document changed 4026.

So the honest version of the diagram has the DOM as the only tree the author addresses, computed style as an annotation on it, and two further structures the author cannot see and should not reason about individually. The reason to know they exist is that the mismatch between them explains otherwise baffling behaviour: why toggling display costs more than toggling visibility, why a change inside a fragmented region is unusually expensive, and why an element you have hidden still costs something to keep in the document.

Invalidation, and the read that undoes it

Engines do not recompute style and layout when you change something. They mark the affected region dirty and recompute at the next rendering opportunity, because a task that makes four hundred DOM mutations should pay for one layout, not four hundred 26. This is the single most important optimisation in the renderer, and script can defeat it with one property access.

Ask for offsetTop, getBoundingClientRect(), scrollHeight or anything else defined in terms of the used values of the box model 48, and the engine cannot answer from a dirty tree. It flushes: it runs style and layout, right there, synchronously, inside your property access, and then returns a number. Do it once at the end of a batch and it costs one layout. Do it between every write and it costs one per read — the pattern universally called layout thrashing 49.

The lab models this with a dirty-bit invalidation scheme over a thousand elements, with a flush costing a fixed 0.25 ms plus 0.002 ms per dirty element. Fully interleaved, that is a thousand flushes and 252.0 ms; fully batched, one flush and 2.25 ms, a ratio of 112.0. The interesting result is not the ratio but the shape of the curve between the two.

Cost is linear in the number of surviving interleaved reads. There is no threshold below which the pattern becomes safe, and no plateau where cleaning up the last few reads stops paying. Moving nine reads in ten removes nine tenths of the cost, which sounds like a triumph until you notice it leaves the page at 27.25 ms — twelve times the batched figure, and still over the frame budget. To come within a factor of two of the batched cost, at most eight of the thousand reads may remain where they were. This is why the practical advice on this problem is always structural — separate a read phase from a write phase — rather than a matter of finding the worst offender.

The frame

Layout produces geometry; paint turns geometry into a list of drawing operations; compositing turns lists into textures and places them. The distinction between the last two matters more than it looks.

Paint does not draw. It records — a display list, an ordered sequence of operations that has not yet been executed 25. Rasterisation, the actual production of pixels, happens afterwards, on another thread, possibly at a different scale, possibly for a region that is not on screen yet. This separation is what makes it possible for scrolling to be smooth: the pixels for the content just below the fold can be produced before you scroll to it, and scrolling then becomes a matter of moving textures rather than re-drawing anything 26.

The older vocabulary for all this is worth translating, because it is still the vocabulary people use. Reflow is layout; repaint is paint without layout; a style recalculation is the cascade evaluation before either. The practical hierarchy is that changing a geometric property — width, top, font-size, adding or removing an element — invalidates layout and therefore everything after it; changing a purely visual property such as background-color or box-shadow invalidates paint but not layout; and changing transform or opacity on an element the compositor has already given its own layer invalidates neither 50. Three tiers, and the difference between the first and the third is roughly two orders of magnitude of work for a visually similar result.

Which brings us to the most useful practical fact in the whole rendering pipeline. Some visual changes require the main thread to run style, layout and paint again. Others require only that the compositor apply a different transform or opacity to layers it already holds 5152. The second kind can be produced by a thread that does not run JavaScript, and therefore can be produced while the main thread is busy.

Modelling the main-thread pipeline at 3.2 ms leaves 13.5 ms of headroom in a 16.67 ms budget, and the model behaves exactly as the arithmetic demands: a main-thread animation holds 60 fps until script exceeds 13.4 ms per frame and then falls off a cliff to 30, then 20, then 15. The compositor-driven line does not move. Over a six-second trace with a mean of 7.78 ms of script and a 60 ms spike every forty-seventh frame — a shape that is entirely ordinary for a real application — the main thread produced 329 of 360 frames and the longest gap between frames was 78.7 ms, while the compositor-driven animation produced all 360.

Two caveats keep this from being a slogan. The compositor's independence ends the moment an animation touches a property that requires layout, and the browser must then take the animation back to the main thread mid-flight. And a compositor that scrolls without the main thread scrolls stale content — which is a correct trade for scrolling and a wrong one for a page that needs to react to the scroll position, hence the existence of scroll-driven animations as a declarative form the compositor can evaluate itself 5354. The author-facing controls for the same problem are containment, which lets a subtree promise that its layout does not affect anything outside it 55, and view transitions, which let the engine animate between two states it has captured rather than making script drive the intermediate frames 56.

Note also what the frame rate is a proxy for. Web Vitals measures three things, and only one of them is smoothness: Largest Contentful Paint asks when the main content appeared 57, Cumulative Layout Shift asks whether it subsequently moved 58, and Interaction to Next Paint asks how long the page took to show a response to input 5960. The third is the one this article's ladder speaks to directly: an interaction cannot produce a frame until the main thread is free to produce one, so every held crossing on the main thread is an addition to that metric 616250. All of these are read out of one buffer of timestamped entries 6364, with input latency broken out separately 65, which is worth knowing because it means the measurements are available to the page itself rather than only to a laboratory.

The clock

A document has one event loop, and the event loop has a processing model that is specified step by step 6869. Informally: it takes one task from a task queue and runs it to completion; then it performs a microtask checkpoint, draining the microtask queue until the queue is empty; then, if this is a rendering opportunity, it runs animation frame callbacks 70and updates the rendering. Then it does it again.

Two queues, two very different guarantees. A task is the platform's yield point: between tasks, the loop can render, can dispatch input, can run something queued by another agent. A microtask is not a yield point at all. The checkpoint drains to empty, and microtasks queued by microtasks are drained in the same checkpoint, which means a chain of promise reactions runs to its end before anything else happens 71. Promise reactions are jobs in the ECMAScript sense, and the host — the browser — is what decides when jobs run; the HTML Standard's answer is "at the microtask checkpoint" 7273. Mutation observer records are delivered there too 74, and event dispatch — the propagation of an event through capture, target and bubble phases — is itself a task-time operation defined by the DOM Standard 75.

This is a good design. It is what makes await usable: a promise that is already resolved continues before the browser does anything else, so a sequence of awaits does not scatter your logic across four frames. But it means the length of a checkpoint is added directly to the length of the turn, and a turn is what a frame has to fit inside.

The model puts a 4 ms animation callback at the head of each turn and varies the number of promise reactions queued behind it at 0.05 ms each. Up to 200 reactions, the page holds 60 frames per second. At 254 the turn reaches 16.70 ms and the frame rate halves to 30 immediately; at 1000 it is 15 fps, at 2000 it is 8. Nothing degrades gradually, because a turn either fits the budget or misses a boundary and waits for the next one.

The comparison worth keeping is between two ways of spending the same fifty milliseconds of reaction work. In one checkpoint it is a 54.0 ms turn: three rendering opportunities pass inside it, two frames are dropped, and it is done in 54 milliseconds. One reaction per task, it is a thousand turns of 4.05 ms across 242 rendering opportunities, no frames dropped, and it takes 4.05 seconds — seventy-five times longer to finish. Neither schedule is correct in general. The microtask queue is where work goes when it must not be interleaved with anything; the task queue is where work goes when it must not cost a frame. A chain in which every reaction enqueues another never reaches the rendering step at all, and the page stops updating for as long as the chain continues.

The thing running inside the task

Two engine behaviours sit underneath every figure in this article and are invisible to the ladder, because they happen inside a task rather than across a boundary. The first is speculative compilation: a JavaScript engine begins by interpreting, observes the types that actually occur, compiles optimised code on that assumption, and bails out to the interpreter when the assumption is violated 7677. Warm code and cold code differ by an order of magnitude, and a change in the shape of an object can move code from one category to the other. The second is garbage collection, which in modern engines is generational, incremental and substantially concurrent precisely so that a collection does not appear as one long pause in the middle of a frame 78. Promises themselves have been reworked at the engine level for the same reason 79. None of this changes which rung a crossing sits on; all of it changes how long the caller sits there.

The platform's more recent answer to this is to stop making authors choose between two queues with fixed semantics, and to give the scheduler explicit priorities instead: scheduler.postTask() with user-blocking, user-visible and background priorities, and a yield primitive that returns control to the loop without losing the queue position 80. Long Animation Frames reports which script kept the loop busy when a frame was late 62.

And then there is the surface the platform has been trying to remove for fifteen years. A synchronous XMLHttpRequest crosses the sandbox, the network, and back, with the calling agent stopped for the entire round trip 81. Nothing about the rest of the design contemplates this; it stops script, rendering and input together, for a duration bounded only by the network. It is the only crossing in the whole set that combines the deepest rung with the most obstructive posture on purpose rather than by history.

The boundary that is not about time

Every crossing so far has been a question of when. The origin boundary is a question of whether.

An origin is a tuple: scheme, host, port 8485. Two documents with the same tuple may hold live references to each other's objects and call each other's functions. Two documents differing in any component of the tuple may not, whatever their relationship in the mind of the person who deployed them, and the only channels between them are ones that copy rather than share 86. There is no rung on the ladder for this. The distance is not the point; the permission is.

The platform also has a coarser grouping, the site: scheme plus registrable domain 8788. Same-site is used for cookies, for process allocation, and for a growing number of privacy decisions; it is not a security boundary in the sense that same-origin is. The three concepts — same-origin, same-site, and the informal "same website" a reader infers from an address bar — diverge more than is generally appreciated, so the lab counted the divergence over a fixed set of URLs.

Sixty-four document URLs, varying two schemes, eight hosts, two ports and two paths, produce 2016 unordered pairs. 32 of those pairs are same-origin. 352 are same-site. 736 share a registrable domain and would be described by any non-specialist as the same website. So 704 pairs — 95.7% of the ones that look like one site — are treated by the platform as mutual strangers. Breaking down what separates them: 192 pairs differ in all three components, 128 in the host alone, 128 in host and port, and only 32 in the scheme alone. The dominant separator is the host, which is to say the subdomain, which is to say the thing an organisation creates without thinking about it.

This is not a defect. It is the reason the web can host mutually hostile code in one window. The security literature on what happens when the boundary is weakened is long and consistent: frame-communication channels that seemed benign turned out to be exploitable 89, and the accumulated set of exceptions and legacy relaxations is the substance of a book-length treatment 90. What the platform has done instead of relaxing the boundary is build explicit, auditable ways through it.

Cross-Origin Resource Sharing is the main one: the browser will send a cross-origin request but will not reveal the response to the requesting script unless the server says so in a header, and for requests that are not simple it will ask first with a preflight 9183. Fetch Metadata headers run the same idea in the other direction, telling the server what kind of context the request came from so it can refuse 92. Content Security Policy constrains what a document may load and execute at all 93, and Subresource Integrity constrains what it may execute even from an allowed origin 94. Permissions Policy does the same for capabilities rather than resources, letting a document declare which powerful features it and its frames may use at all 95.

Isolation as a capability

The most interesting inversion arrived after Spectre. Because a high-resolution timer and shared memory together make cache-timing attacks practical from JavaScript 969798, browsers withdrew both. Getting them back requires a document to prove it is not sharing an address space with anything that has not consented: a Cross-Origin Opener Policy severing it from its opener's browsing context group, and a Cross-Origin Embedder Policy requiring every subresource to opt in 99. Only then does the document get SharedArrayBuffer and a finer clock.

So the platform now has a mechanism in which giving up ambient reachability buys a capability. The related Origin-Agent-Cluster header does something similar at the agent level, asking that a document's agent cluster be keyed by origin rather than by site 100. Both are worth noticing because they run against the direction people expect: the isolated document is the powerful one.

What the platform remembers

There are, depending on how you count, six or seven ways for a page to store something. They are not alternatives with different ergonomics. They are different points on the same two axes this article has been using, and three of them predate the process model that the other four were designed around.

Cookies are the oldest. The mechanism was specified retroactively in 2011, describing what implementations already did rather than what anyone would design 102. It has been under revision since: rfc6265bis reached its twenty-first draft in September 2025 103, and a further effort, draft-ietf-httpbis-layered-cookies, now proposes to obsolete both RFC 6265 and 6265bis 104. Fifteen years after the original, the web's most widely deployed state mechanism still has no updated standards-track RFC.

The reason it has taken this long is that the mechanism is no longer only a state mechanism. Third-party cookies are the substrate of cross-site tracking, which has been measured and characterised repeatedly 105106, and the browsers' countermeasures — partitioning, restricting, and in Safari's case a policy engine that decides per-domain — are all modifications to cookie behaviour rather than to anything else 107. Studies of what pages actually use, whether by crawling feature counters 108or by instrumenting the engine directly 109, keep finding the same thing: the surface is enormous, the usage is concentrated, and the concentrated part includes this.

The relevant fact for this article is the shape of the DOM interface. document.cookie is a string property. Reading it returns every cookie in scope, serialised; writing it sets one. The store itself is shared across every tab and lives with the network stack, which in a multi-process browser is not in the renderer. So a property access on a same-origin object requires, in principle, a cross-process read, performed synchronously with the caller stopped. Engines cache aggressively to avoid paying that in practice, but the API's signature makes it impossible for them to return control first. This is exactly why the Cookie Store API exists: the same store, addressed with promises, usable from a service worker where the synchronous form is not available at all 110.

Web Storage — localStorage and sessionStorage — has the same defect for the same reason and less excuse, since it was designed during the era it should have anticipated 111. A string keyed map with synchronous getters, backed by a store that must be durable, origin-partitioned and consistent across every document of that origin 112. It is not exposed to workers, and it cannot be, because the design assumes a caller that can be stopped.

The two modern stores make the opposite choice everywhere. Cache Storage holds whole Request and Response pairs, addressed by request rather than by key, and every operation on it returns a promise 113. IndexedDB is a transactional store for structured-cloneable values, with requests that deliver results as events on later turns of the loop 114115. IndexedDB's notorious sharp edge follows directly from this design: a transaction stays alive only while requests keep being made within it, so awaiting a promise unrelated to the transaction can let its turn end and the transaction commit underneath you. That is not a bug in the API so much as the visible seam between two scheduling models.

Storage as a whole is now specified as one thing, with a shared quota per origin and defined eviction behaviour, including a way for an origin to ask that its data be treated as persistent 112116. That matters because caching is not free of consequences merely because it is local. Which strategy a service worker uses is a real decision, and the lab quantified it.

Two thousand requests over twenty resources, each resource changing on the server at its own fixed period. Cache-first serves 99.0% of requests without touching the network and 90.3% of them are out of date. Network-first serves nothing stale and avoids no network at all. Stale-while-revalidate keeps the full 99.0% network avoidance while cutting stale responses to 36.9%, a 59.2% reduction, because it updates the cache on every hit and so is only ever stale for the first request after a change. A cache-first policy with a hundred-request freshness lifetime lands between them at 82.8% and 49.4% — which is what an ordinary HTTP max-age does 117118. Underneath all of it the transport has been rewritten twice in a decade — a framed, multiplexed HTTP/2 over TLS 119120and an HTTP/3 that moves the transport itself into user space 121— while the message semantics stayed deliberately unchanged 122, and priorities became an explicit, negotiable header rather than a tree 123.

The point is not that stale-while-revalidate wins. It is that these are not four qualities of implementation; they are four points on one curve, and the curve is the trade between a network you do not use and an answer you cannot vouch for 124.

The other agents

An agent, in the platform's own vocabulary, is an execution context with a heap and an event loop 100. A document is one. Every worker is another. Agents in the same cluster can share memory; agents in different clusters can only exchange copies.

A dedicated worker is the simplest case: a script with its own global scope, its own loop, and no access to the DOM 125. It communicates by postMessage, which serialises using the structured clone algorithm 101— a copy, with a defined set of types it can carry, and a documented failure for the ones it cannot. The copy is not free, which is why the algorithm also supports transfer: an ArrayBuffer may be moved rather than copied, at the cost of being detached in the sender.

Shared workers extend the idea to an agent that outlives any particular document and is shared across every document of an origin, each connecting over its own port 86. They are used less than they should be, and the reason is a lifetime problem rather than an API problem: nothing in particular owns a shared worker, and its state outlives the page that put it there.

Then there is the case where the shared-memory boundary genuinely disappears. A SharedArrayBuffer is addressable by every agent in a cluster, and the Atomics operations on it provide ordering guarantees and a wait-and-notify primitive 126127. This is real shared memory with real data races, and the platform's response to that is instructive: Atomics.wait is forbidden on a document's main thread, precisely because a blocking wait there would stop the event loop, and the feature as a whole is gated behind the cross-origin isolation described above 99. The platform will let you block, but only on a thread where blocking cannot cost a frame.

The agent in the middle

A service worker is an agent placed between a document and the network 113. It has no DOM, may be terminated at any time and restarted when needed, and its principal job is to answer fetch events — from a cache, from the network, or from nothing at all. From the document's point of view nothing has changed: a fetch is issued, a response arrives, and there is no way to tell which of the three happened.

That transparency is the source of both its power and its worst failure mode. A service worker can make a site work offline, can implement any of the routing strategies measured above, can receive push messages and can defer work until connectivity returns 128129. It can also cache a deployment so thoroughly that the mechanism which would update it is itself served from the cache, producing a site that is permanently and invisibly out of date. The lifecycle — install, wait, activate, with a new worker not taking control of existing clients until they are gone — exists to make this recoverable rather than to make it impossible 130.

What is worth noting on this article's axes is that the fetch handler is a crossing the calling document never observes at all. Eleven of the thirty-two crossings in the plate set have that character. The engine and its helper agents do most of the work of running a page, and script sees the result rather than the mechanism.

Another language in the same agent

WebAssembly is the only part of the platform that adds a second execution model to an existing agent rather than adding another agent. Its first version became a W3C Recommendation in December 2019 131. Version 2.0 reached Candidate Recommendation in 2025 132, and at that point the working group adopted an evergreen model: the specification stays at Candidate Recommendation and is updated in place, so the current Candidate Recommendation Draft is the standard and no further Recommendation is intended 133. The current release is 3.0 134135. Secondary sources that report Wasm 2.0 as reaching "Recommendation status" in December 2024 are describing a transition the working group has explicitly declined to make.

The design goals stated in the original paper were a compact binary format, a formally specified and machine-verified type system, near-native speed, and sandboxing that reuses the JavaScript engine's existing boundaries rather than adding new ones 136. Independent measurement has been more equivocal than the marketing: a systematic comparison found Wasm meaningfully slower than native code on real benchmarks, with the gap attributable to register pressure and the cost of the safety checks rather than to compilation quality 137. Studies of what is actually deployed have found the population dominated by a small number of use cases, with a substantial minority of cryptocurrency mining in earlier surveys 138139. And the memory model has its own hazards: linear memory is safe with respect to the host, but a buffer overflow within that linear memory is as exploitable as it ever was, and in some respects more so because the usual native mitigations are absent 140.

For the argument here, the interesting property is arithmetic. JavaScript has one numeric type for integers and it is IEEE 754 binary64 141142. Every integer up to 253 is exactly representable; above that, the representable integers are spaced two apart, then four, and so on. WebAssembly has i32 and i64, which are exact two's-complement integers that wrap.

The lab drew 200 000 pairs of operands at each of several widths and compared three results: the exact product, the binary64 product, and what JavaScript's conventional 32-bit multiplication idiom (a * b | 0) actually computes. Below 226 the systems agree on every pair. At full 32-bit operands only 3.55% of products are exactly representable, and the idiom disagrees with a true 32-bit multiply on 96.45% of pairs. The reason is mechanical: the idiom rounds to binary64 first and truncates to int32 second 143, so any information below the rounding threshold is gone before the truncation happens. Math.imul and Wasm's i32.mul are both defined as exact modular arithmetic and neither has this behaviour. It is a small example of a general point: Wasm is not only faster for some workloads, it is different, and the difference is specified.

The delivery path is the other half of the story. instantiateStreaming takes a Response and validates and compiles the module as its bytes arrive, so compilation overlaps download 144145. Engines compile twice: a fast baseline compiler produces working code immediately and an optimising tier replaces it later 146. What Wasm did not have until recently was any way to suspend: a long-running computation could not yield to the event loop, which is the gap the JavaScript Promise Integration proposal addresses 147, and which appears as a focus area in Interop 2026 7. Garbage-collected source languages have their own story, with a managed heap now available rather than emulated in linear memory 148149150.

The wires

Three ways to move bytes, at three levels of abstraction, with three different answers to the question of who waits.

Streams, and the price of not buffering

The Streams Standard is the platform's general answer to a producer and a consumer running at different rates 151. Its central mechanism is backpressure: a queue with a stated high water mark, and a signal that propagates back to the source when the queue is full 152. A fetch() response body is a readable stream, so this machinery is present in the most common operation on the platform whether the author engages with it or not 83.

Backpressure is usually presented as free — bounded memory at no cost. That is true only when refilling the queue is instantaneous, which it never is.

The lab delivers a 4000-chunk payload (65.5 MB of 16 KiB chunks) to a consumer whose capacity alternates between fast and slow phases, from a source that answers a pull six ticks later. An unbounded queue finishes at tick 8313 and holds the entire 65.5 MB in the reader's memory. A high water mark of 64 finishes at exactly the same tick while holding 1024 KiB — 62 times less memory for no time at all. A high water mark of 1 finishes at tick 39 991, 4.81 times slower, having starved the consumer on 8400 ticks, because every refill costs a round trip that a deeper queue would have hidden. Backpressure is neither free nor expensive; its price is one round trip for every chunk you decline to hold in advance, and the high water mark is where you set that price.

WebSockets, and what framing is worth

A WebSocket begins as an HTTP request, uses the upgrade mechanism, and then stops being HTTP: what follows is a bidirectional message stream with a frame header of two to fourteen bytes, masked from client to server 153. The protocol has since been given bootstraps over HTTP/2 154and HTTP/3 155, so the connection no longer requires a dedicated TCP connection of its own.

Comparing the framing overhead against a modelled HTTP poll of 480 request and 320 response header bytes: at a two-byte message the polled exchange costs 100 times the bytes; at 8 bytes, 57.7 times; at 512 bytes, 2.52; at 64 KiB, 1.01. One minute of 24-byte messages at 60 Hz is 106 KiB framed against 2897 KiB polled. The honest caveat is that this compares against HTTP/1.1 with uncompressed headers; HPACK and QPACK compress repeated headers on HTTP/2 and HTTP/3 respectively 156157, which narrows the gap substantially without closing it. The conclusion survives the caveat but changes shape: framing matters enormously for small frequent messages and not at all for bulk transfer, and the modern reason to reach for a socket is the server-initiated direction rather than the header bytes.

Where WebSockets are weak is backpressure. The API offers a buffered-amount counter that the author must poll, which is the Streams problem solved by hand and usually not solved at all — one of the motivations for WebTransport, which exposes streams and datagrams over HTTP/3 with the Streams Standard's own primitives 158159121.

WebRTC, and the cost of having no server in the middle

WebRTC is the only part of the platform where two browsers exchange data directly. Everything difficult about it follows from that. There is no server to address, so the two peers must discover a path through whatever their networks permit; there is no server to trust, so the security has to be established between the endpoints; and there is no server to blame, so the failure modes are network-shaped rather than application-shaped.

The architecture is spread across a dozen IETF documents and one W3C API 160161. Signalling is deliberately unspecified — the browsers exchange session descriptions by any means the application likes 162. Path discovery is Interactive Connectivity Establishment: each peer gathers candidate addresses, the candidates are paired, the pairs are ordered by a priority formula, and connectivity checks proceed in that order until one succeeds 163. Candidates come in kinds — a host address, a server-reflexive address discovered through STUN 164, a relayed address obtained from a TURN server 165— and the priority formula deliberately ranks them so that direct paths are tried before relayed ones.

The lab computed the ordering for a modest and entirely typical candidate set: four local candidates (two host, one server-reflexive, one relay) against three remote (one host, one server-reflexive, one relay). Twelve pairs. Ordered by the RFC 8445 priority formula, the first pair involving a relay is check number seven — so a connection that can only work through TURN pays six failed checks before its first plausible candidate is even attempted. Pair count is the product of the candidate counts, not the sum, so a laptop with several interfaces facing a peer with several is 144 pairs. This is why calls connect instantly on some networks and take several seconds on others, and it is a property of the protocol rather than of any implementation.

Security is not optional and not layered on: media is protected with SRTP 166with keys established by DTLS 167168, data channels run over SCTP inside DTLS 169170171, transports are enumerated normatively 172, and there are two whole documents on the threat model and the architecture that answers it 173174. There is even a specification for how much of the user's local IP configuration may be revealed during gathering, because candidate gathering is itself an information disclosure 175. Media transport has its own document 176, and the statistics interface exists because on a peer-to-peer link the application is the only thing that can observe the connection at all 177.

The ledger

Thirty-two crossings, each placed on a rung and given a posture. Collected, they answer the question the article opened with.

Fifteen of the thirty-two cross to another process or another machine; four cross nothing at all. The mean rung is 3.44. Eleven of the thirty-two are crossings the calling script never observes, which is a reasonable summary of how much of running a web page the engine does without being asked.

Eight of the thirty-two hold the caller. Their mean rung is 2.00, against 3.92 for everything else, and that gap is the finding. The platform does permit blocking — a DOM mutation blocks, a same-origin property access blocks, a WebAssembly call blocks, an Atomics.wait blocks — but almost only where the crossing is shallow, or where the blocking is the point and the API is withheld from the main thread for exactly that reason.

Three crossings sit in the corner where a deep rung meets a held caller: synchronous XMLHttpRequest, document.cookie and localStorage. Every one of the three predates the process model and every one now has an asynchronous replacement — fetch(), the Cookie Store API, and the two modern storage APIs respectively. That is the whole argument of this article reduced to a count. The platform's rule is not "avoid blocking" and it is not "everything must be a promise". The rule is that the posture must match the rung, and the surfaces where it does not are precisely the surfaces the platform has spent fifteen years trying to retire.

A second pattern is visible in the matrix and worth stating separately. The column of crossings the caller never sees is populated almost entirely at rungs X1, X4 and X5 — deferred engine state, other agents, other processes. The engine does deep work invisibly and shallow work visibly. When authors are surprised by performance, it is usually because a shallow-looking operation triggered something in that invisible column: a property read that ran layout, a style change that forced a new layer, a fetch that woke a service worker.

A third reading is about direction of travel. Sort the thirty-two crossings by the era in which their API was designed and the pattern in the matrix resolves into a timeline. The pre-2010 surfaces — cookies, Web Storage, synchronous XHR, and the layout-dependent geometry properties — are the ones that hold the caller. Everything specified after the multi-process model became universal releases it, and does so uniformly enough that a reader can predict the shape of an API they have never seen from the year it was written. Cache Storage, IndexedDB, service workers, streams, WebTransport, WebGPU, the Cookie Store API and the Web Neural Network API have almost nothing else in common, and they all return promises.

That uniformity has a cost worth acknowledging. An asynchronous API is harder to use correctly than a synchronous one, and the platform has spent a decade adding machinery — promises, async functions, the microtask checkpoint that makes them ergonomic, and now an explicit scheduler — to make the cost bearable. The bargain is that the difficulty is moved to a place where it is visible. A held caller on a deep crossing hides its cost inside a property access that looks like any other; a released caller puts the crossing in the syntax, where the author can see it and the profiler can attribute it.

What the ladder does not say

Four limits, stated plainly, because a device that explains everything explains nothing.

The rungs are not durations. A rung X5 crossing to a cache in the browser process may complete in microseconds; a rung X1 layout flush on a large document may take twenty milliseconds. The ladder measures how far a request goes, and distance and cost are correlated only loosely. Everywhere this article makes a claim about cost, the claim comes from the lab's stated model or from a cited source, not from the rung.

The postures are the API's, not the engine's. Coding localStorage at rung X5 with a held caller describes what the specification obliges an engine to be able to do and what the signature prevents it from doing instead. A given engine may answer most reads from a renderer-side cache and never leave the process. The plate is a statement about the surface, so the correct reading of a deep-and-held plate is "this API forbids the engine from releasing you", not "this call always costs a process hop".

The lab is models, not measurements. Eight experiments, stdlib Python, one seed, no browser. E1's event loop, E2's invalidation scheme, E3's pipeline costs, E5's change process and E7's queue are all stated models with parameters chosen to be plausible, and their numbers are exact consequences of those parameters rather than observations of any engine. Three of the eight are not like that: E4's origin counts are combinatorics over a definition, E6's arithmetic is exact and would be identical in any conforming implementation, and E8's framing arithmetic is read off RFC 6455's own frame format. Where a number in this article would change if you re-ran it in a real browser, it came from the first group.

Thirty-two crossings is a selection. There is no Web Audio plate, though an AudioWorklet is one of the platform's most interesting agents — a real-time thread with a hard deadline and no allocation 178. There is no WebGPU plate, though its command-buffer model is a clean example of an API designed around a deep crossing from the start 179180. There is no plate for the Storage Access API, which mediates a boundary that is neither purely temporal nor purely origin-based 181, and none for the machine-learning and pressure APIs now arriving on the same asynchronous pattern 182183. The selection was made to cover the mechanisms an ordinary page touches, and the ladder would take the others without modification.

One thing the exercise does establish, though, which is not obvious before you count: the modern web platform is more coherent than its reputation. Nearly forty years after the original proposal for a networked document system 184, the accumulated surface is very large and very old in places, and it is nonetheless organised around a rule that can be stated in a sentence and checked against every API in the set. Deep crossings release the caller. Shallow crossings may hold it. The exceptions are three, they are known, and each of them has a successor.
