Concurrency and Parallelism in Go

Goroutines, channels, the sync and context packages, the patterns built from them, and the bugs that bite when they are misused.

Examples verified with Go 1.27.0 on linux/amd64Requires Go 1.25 or laterAll examples pass go vet and -race unless marked otherwise

Abstract

Go builds concurrency into the language: the go statement starts a goroutine, channels carry values between goroutines, and select waits on several channel operations at once. The standard library adds locks, atomics, one-time initialization, condition variables and cancellation. This article explains each mechanism with reference to the language specification and the Go memory model, shows the canonical patterns (worker pools, fan-out/fan-in, pipelines, producer–consumer, rate limiting), diagnoses the three characteristic failure modes (deadlocks, data races, goroutine leaks), and closes with structured concurrency as a discipline that prevents most of them. Every program is complete and runnable, and ten exercises with worked solutions follow.

How to run the examples. Every listing is a complete package main. Put each in its own directory inside a module and run it with the race detector enabled, for example go run -race ./workerpool. Two examples use modules outside the standard library: golang.org/x/sync/errgroup and golang.org/x/time/rate, which you add with go get golang.org/x/sync golang.org/x/time. Outputs shown below are from real runs; where goroutine scheduling makes output order vary, the text says so.

1Concurrency versus parallelism

The two words are often used interchangeably, but in Go they name different things. Rob Pike’s definition is the one the Go project uses: concurrency is “the composition of independently executing processes,” while parallelism is “the simultaneous execution of (possibly related) computations” [1,2]. Put more briefly, “concurrency is about dealing with lots of things at once. Parallelism is about doing lots of things at once” [2].

Concurrency is a property of a program’s structure: it is decomposed into pieces that can make progress independently and that coordinate when they must. Parallelism is a property of its execution: several of those pieces run at the same instant on different CPU cores. A concurrent program may run on one core, interleaving its pieces, and still be correct and responsive. Given more cores, the same well-structured program can also run in parallel without being rewritten. Concurrency is what lets you exploit parallelism, but it does not guarantee it.

Go’s concurrency model descends from C. A. R. Hoare’s Communicating Sequential Processes (CSP), which proposed that input and output be treated as basic programming primitives and that parallel composition of sequential processes be the fundamental structuring method [3]. The Go FAQ explains that Go’s primitives come from the branch of that family whose main contribution was channels as first-class values, because experience showed that CSP “fits well into a procedural language framework” [4].

How much can parallelism help?

Parallel speed-up is bounded by the fraction of the work that must run serially. Amdahl argued in 1967 that the sequential portion of a computation limits the benefit of adding processors [5]; in the form now called Amdahl’s law, if a fraction p of the run time can be parallelized across n processors, the best possible speed-up is 1 / ((1 − p) + p/n). With p = 0.9, even infinitely many cores give at most a 10× speed-up. Coordination (locks, channel operations, merging results) adds to the serial fraction, which is why fine-grained parallelism often runs slower than a loop.

2Goroutines

A goroutine is “a function executing concurrently with other goroutines in the same address space. It is lightweight, costing little more than the allocation of stack space” [6]. Goroutines are not operating-system threads: the runtime multiplexes them onto a small number of threads, so that if one blocks, for example waiting for I/O, others continue to run [6]. The FAQ notes that it is practical to create hundreds of thousands of goroutines in one address space [4].

Creating goroutines

The go statement “starts the execution of a function call as an independent concurrent thread of control, or goroutine, within the same address space” [7]. The operand must be a function or method call. Two details of the specification matter in practice [7]:

  • The function value and its parameters are evaluated in the calling goroutine, before the new goroutine starts. Passing a value as an argument therefore snapshots it.
  • Unlike an ordinary call, execution does not wait for the function to complete, and any return values are discarded. To get a result out of a goroutine you must communicate it, typically over a channel or into memory that is later read after synchronization.
Loop variables and closures. Before Go 1.22, a for loop declared one variable shared by all iterations, so goroutines that captured it often all saw its final value. Since Go 1.22 each iteration has its own variable, which removes that bug for modules that declare go 1.22 or later [8,9]. Older code that passes the loop variable as an argument, or writes i := i, was working around the earlier rule.

Goroutine lifecycle

A goroutine is created by a go statement, runs until its function returns, and then terminates: “When the function terminates, its goroutine also terminates” [7]. In between it moves among three broad states: runnable (ready, waiting for a thread), running, and waiting (blocked on a channel, lock, timer, system call or network I/O). There is no way to kill a goroutine from outside, and goroutines have no identity that user code can address. A goroutine stops only when its function returns, when it calls runtime.Goexit, which “terminates the goroutine that calls it” after running its deferred calls [10], or when the whole program exits.

The program exits when main returns, and “it does not wait for other (non-main) goroutines to complete” [7]. An unrecovered panic in any goroutine also terminates the whole program. These two rules have the same lesson: every goroutine needs an owner who knows when it finishes and what happens to its errors and panics.

runtime.NumGoroutine “returns the number of goroutines that currently exist” [10]. It is a crude but useful leak check in tests. The time.Sleep calls here only make the demonstration readable; sleeping is never a correct way to synchronize.

Scheduling

The Go runtime contains an M:N scheduler that maps many goroutines onto fewer OS threads. The runtime source describes three entities [11]:

  • G, a goroutine: its stack, instruction pointer and scheduling state.
  • M, a machine: an OS worker thread.
  • P, a processor: a resource required to execute Go code. An M must hold a P to run Go code, but it can be blocked or in a system call without one. The number of Ps is GOMAXPROCS.

This design, introduced in Go 1.1 from Dmitry Vyukov’s proposal, gave each P its own queue of runnable goroutines so that threads do not contend for a single global lock, and lets an idle P steal work from another P’s queue [12]. When a goroutine blocks in a system call, its M hands off its P so that another M can keep running Go code; when a goroutine blocks on a channel or on network I/O, it is simply parked, and its M picks up another G [11,12].

Since Go 1.14 goroutines are asynchronously preemptible: “loops without function calls no longer potentially deadlock the scheduler or significantly delay garbage collection” [13]. Before that, a tight loop with no function calls could monopolize a thread. You can still call runtime.Gosched, which “yields the processor, allowing other goroutines to run” [10], but correct programs almost never need it.

Scheduling is not ordering. The scheduler gives no guarantees about which runnable goroutine runs next or how long it runs. Any program whose correctness depends on goroutines running in a particular order, or on one goroutine “getting there first,” is wrong. Order must be imposed with synchronization (Section 5).

Runtime behaviour

Stacks. Goroutine stacks start small and grow as needed. Go 1.4 switched to contiguous stacks and reduced the starting size from 8 KB to 2 KB [14]; a stack grows by allocating a larger one and copying, and the storage comes from the heap [6]. This is why goroutines are cheap enough to create one per connection or per request.

GOMAXPROCS. “The GOMAXPROCS variable limits the number of operating system threads that can execute user-level Go code simultaneously. There is no limit to the number of threads that can be blocked in system calls on behalf of Go code” [10]. Since Go 1.5 it has defaulted to the number of available cores rather than 1 [15]. Since Go 1.25, on Linux the default also respects a cgroup CPU bandwidth limit (for example a Kubernetes CPU limit) when that is lower than the number of logical CPUs, and the runtime updates the value if the limit changes [16]. Setting GOMAXPROCS explicitly turns this behaviour off [16].

Thread affinity. Normally a goroutine may run on any thread and move between them. runtime.LockOSThread “wires the calling goroutine to its current operating system thread” [10]. You need it only for APIs with thread-local state, such as some graphics libraries and certain system calls.

Goroutines are not garbage-collected while blocked. A goroutine blocked forever still holds its stack and everything reachable from it. This is the root of goroutine leaks (Section 18).

3Channels

A channel “provides a mechanism for concurrently executing functions to communicate by sending and receiving values of a specified element type” [7]. Channels are created with make, are reference values (copying one copies a handle to the same channel), and their zero value is nil. A single channel “may be used in send statements, receive operations, and calls to the built-in functions cap and len by any number of goroutines without further synchronization”, and channels “act as first-in-first-out queues” [7].

The guiding idea is Go’s best-known proverb: “Do not communicate by sharing memory; instead, share memory by communicating” [6,17]. Rather than letting several goroutines touch a value under a lock, hand ownership of the value from one goroutine to another through a channel, so that at any moment exactly one goroutine is responsible for it.

Unbuffered channels

make(chan T) creates a channel of capacity zero. “If the capacity is zero or absent, the channel is unbuffered and communication succeeds only when both a sender and receiver are ready” [7]. An unbuffered send is therefore a rendezvous: both goroutines meet, the value passes, and both continue. This makes an unbuffered channel a synchronization point as well as a data path.

Buffered channels

make(chan T, n) with n > 0 creates a buffered channel: “communication succeeds without blocking if the buffer is not full (sends) or not empty (receives)” [7]. cap(ch) reports the buffer size and len(ch) the number of queued elements [7]. A buffer decouples sender and receiver in time, which smooths bursts, but it does not make a slow consumer faster: once the buffer fills, senders block exactly as with an unbuffered channel.

Choosing a buffer size. Use unbuffered channels by default; they make hand-offs explicit and expose design errors early. Add a buffer when you know the number of values in advance (for example one slot per goroutine so that none ever blocks, see Section 18) or when you need a bounded queue or counting semaphore. Do not add buffering to “fix” a deadlock you do not understand; it usually just moves the deadlock to a larger input. len(ch) is a snapshot that may be stale by the time you act on it, so never use it to decide whether an operation will block.

Sending and receiving

The send statement ch <- v and the receive expression <-ch are the two channel operations. A receive can also be written in the two-value form v, ok := <-ch, where ok is false if the value is a zero value produced because the channel is closed and empty [7]. The behaviour of each operation depends on the channel’s state, and this table is worth memorizing:

Closing channels

close(ch) records that no more values will be sent. “After calling close, and after any previously sent values have been received, receive operations will return the zero value for the channel’s type without blocking” [7]. A for v := range ch loop receives “the successive values sent on the channel until the channel is closed” [7]. Because every waiting receiver wakes at once, closing is also Go’s idiomatic broadcast.

Three rules keep closing safe:

  1. Only the sender closes, never the receiver, because sending on a closed channel panics [7].
  2. Close exactly once. With several senders, have a coordinator close the channel after all senders have finished (typically after a WaitGroup), or use sync.Once.
  3. Closing is not required. A channel is garbage-collected when unreachable whether or not it is closed. Close it only when receivers need to be told that no more values are coming, for example to end a range loop.

Directional channels

A channel type may carry a direction: chan<- T is send-only and <-chan T is receive-only [7]. A bidirectional channel converts implicitly to either direction, so the usual practice is to create a chan T and pass it to functions whose parameter types state what each function may do. The compiler then rejects a send on a receive-only channel, and closing a receive-only channel is also an error [7]. A function that returns <-chan T owns the channel, and callers cannot close it out from under it.

4Select statements

A select statement “chooses which of a set of possible send or receive operations will proceed” [7]. All channel expressions in its cases are evaluated on entry. Then, “if one or more of the communications can proceed, a single one that can proceed is chosen via a uniform pseudo-random selection. Otherwise, if there is a default case, that case is chosen. If there is no default case, the ‘select’ statement blocks until at least one of the communications can proceed” [7]. The random choice prevents one busy channel from starving the others. Since communication on nil channels can never proceed, setting a channel variable to nil removes that case from consideration, and a select with only nil channels and no default blocks forever [7].

The four idioms in this listing recur everywhere: first ready wins, timeout with time.After [18], non-blocking operations with default, and disabling a case with a nil channel, which Ajmani’s “Advanced Go Concurrency Patterns” builds into the for-select event loop [19]. An empty select {} blocks forever.

Timers since Go 1.23. Go 1.23 made timer channels unbuffered and made unreferenced Timers and Tickers collectable even if they were never stopped, so time.After in a loop no longer pins memory until it fires [20]. Go 1.27 removed the asynctimerchan setting that restored the old behaviour [21]. Code that polled len(timer.C) must use a non-blocking receive instead [20].

5Channel synchronization

Concurrency bugs are often bugs of visibility: one goroutine writes a variable and another does not see the write, or sees it partially. The Go memory model defines when a read is guaranteed to observe a write, using a happens-before relation [22] in the sense introduced by Lamport for distributed systems [23]. Channel operations create the edges of that relation [22]:

  • “A send on a channel is synchronized before the completion of the corresponding receive from that channel.”
  • “The closing of a channel is synchronized before a receive that returns a zero value because the channel is closed.”
  • “A receive from an unbuffered channel is synchronized before the completion of the corresponding send on that channel.”
  • “The kth receive from a channel with capacity C is synchronized before the completion of the k+Cth send on that channel.”

The first rule is why the “publish then signal” idiom below is safe: everything the sender wrote before its send is visible to the receiver after its receive. The last rule is why a buffered channel of capacity C works as a counting semaphore that admits at most C goroutines at once [22].

Use chan struct{} for pure signals: an empty struct occupies no memory and makes it clear that the event, not a value, is what matters. The memory model’s own advice is blunt: programs that modify data accessed by multiple goroutines “must serialize such access”, and “if you must read the rest of this document to understand the behavior of your program, you are being too clever. Don’t be clever” [22].

6WaitGroups

“A WaitGroup is a counting semaphore typically used to wait for a group of goroutines or tasks to finish” [24]. Add(n) increments its counter, Done() decrements it, and Wait() blocks until it reaches zero. Go 1.25 added WaitGroup.Go, which “calls f in a new goroutine and adds that task to the WaitGroup” and removes the task when f returns [16,24]. It removes the most common WaitGroup bug (calling Add inside the new goroutine, where it may run after Wait) and the boilerplate defer wg.Done().

Rules for WaitGroups:

  • Call Add before the go statement, in the goroutine that will call Wait; or use wg.Go.
  • Never copy a WaitGroup after first use, and pass it by pointer. Values containing sync types should not be copied [24], and go vet’s copylocks analyzer reports locks passed by value [25] (see Exercise 8).
  • A WaitGroup only counts. It does not collect errors, cancel siblings or limit concurrency; for that, use errgroup (Section 19).
  • The function passed to wg.Go “must not panic” [24]: a panic in any goroutine crashes the program.

7Mutexes

Channels transfer ownership; mutexes protect state that stays in one place. Package sync “provides basic synchronization primitives such as mutual exclusion locks” [24]. When the state is a cache, a counter, or a struct of fields shared by many goroutines, a mutex is usually simpler and faster than funnelling every access through a goroutine. The Go wiki’s advice is to “use whichever is most expressive and/or most simple”: channels for passing ownership, distributing work and communicating asynchronous results; mutexes for caches and state [26].

sync.Mutex

A Mutex has Lock, Unlock and (rarely needed) TryLock. Its zero value is an unlocked mutex, and “a Mutex must not be copied after first use” [24]. In memory-model terms, “the n’th call to Mutex.Unlock ‘synchronizes before’ the m’th call to Mutex.Lock for any n < m” [24], so everything written while holding the lock is visible to the next holder.

Go’s mutex is not reentrant: locking a mutex the same goroutine already holds deadlocks. It is fair in a bounded sense. In normal mode, a woken waiter competes with newly arriving goroutines, which favours throughput; if a waiter fails to acquire the lock for more than 1 ms, the mutex switches to starvation mode and hands ownership directly to waiters in FIFO order [27].

sync.RWMutex

An RWMutex can be held by any number of readers (RLock/RUnlock) or by one writer (Lock/Unlock). To prevent writer starvation, once a writer is waiting, new readers block until the writer has acquired and released the lock; the documentation notes that “this prohibits recursive read-locking” [24]. An RWMutex pays off only for read-heavy workloads with non-trivial critical sections; for short critical sections a plain Mutex is often faster.

Practical rules: keep the mutex next to the fields it guards and document which fields those are; keep critical sections short and never block on I/O or a channel while holding a lock; prefer defer mu.Unlock() so that panics and early returns release the lock; and give types with a mutex pointer receivers. Plain Go maps are not safe for concurrent use: since Go 1.6 the runtime performs best-effort detection of concurrent map misuse and crashes the program when it finds it [28]. sync.Map exists for two specialized cases, but “most code should use a plain Go map instead, with separate locking or coordination” [24].

8Atomic operations

Package sync/atomic provides low-level atomic memory primitives: load, store, add, swap and compare-and-swap. Go 1.19 added typed wrappers (atomic.Int64, atomic.Bool, atomic.Pointer[T] and others) that make misuse such as mixing atomic and non-atomic access to the same variable much harder [29]. Go’s atomics are sequentially consistent: “If the effect of an atomic operation A is observed by atomic operation B, then A is synchronized before B. All the atomic operations executed in a program behave as though executed in some sequentially consistent order” [22].

Atomics fit single-word state: counters, flags, and a pointer to an immutable snapshot (the copy-on-write configuration above). They do not compose: two atomic operations in a row are not atomic together, so invariants that span several fields need a mutex. The package documentation itself warns that these functions “require great care to be used correctly” and that, except for special low-level applications, synchronization is better done with channels or the sync package [30].

9Once and Cond

sync.Once

Once.Do(f) calls f exactly once, however many goroutines call Do, and no call to Do returns until that single call of f has returned, so every caller sees fully initialized state [24]. If f panics, Do considers it to have returned, and future calls return without calling f [24]. Go 1.21 added OnceFunc, OnceValue and OnceValues, which wrap the common lazy-initialization use of Once in a function [31]; OnceValue “returns a function that invokes f only once and returns the value returned by f” [24].

sync.Cond

A condition variable lets goroutines wait for a condition on shared state that is protected by a lock. Wait atomically unlocks the associated lock and suspends the goroutine; when woken, it re-locks before returning. Because a woken goroutine cannot assume the condition still holds, Wait is always called in a loop that re-checks it [24]. Signal wakes one waiter and Broadcast wakes all. The documentation adds a caution: “For many simple use cases, users will be better off using channels than a Cond”; Broadcast corresponds to closing a channel and Signal to sending on one [24].

10The context package

Package context carries deadlines, cancellation signals and request-scoped values across API boundaries and between goroutines [32]. It was designed at Google for servers in which each incoming request spawns goroutines for databases and RPCs, all of which should stop when the request is cancelled or times out [33]. A Context is an interface with four methods: Deadline, Done (a channel closed on cancellation), Err and Value. Contexts are immutable and form a tree: each With… function returns a child of its parent, and cancelling a parent cancels all of its descendants [32].

Cancellation

context.WithCancel(parent) returns a child and a CancelFunc. Code that does blocking work selects on ctx.Done() and returns ctx.Err() when it is closed. Err returns nil while Done is open, then Canceled if the context was cancelled, or DeadlineExceeded if its deadline passed [32]. Go 1.20 added WithCancelCause and Cause so that a canceller can record why [34], and Go 1.21 added WithDeadlineCause, WithTimeoutCause, AfterFunc (run a function after a context is cancelled) and WithoutCancel (a copy that is not cancelled with its parent) [31].

Deadlines and timeouts

WithDeadline(parent, t) cancels the child at absolute time t; WithTimeout(parent, d) is defined as WithDeadline(parent, time.Now().Add(d)) [32]. A child’s deadline can only be earlier than its parent’s, never later. Always call the returned cancel, normally with defer, even if the deadline will fire anyway: “Failing to call the CancelFunc leaks the child and its children until the parent is canceled”, and go vet checks that cancel functions are used on all control-flow paths [32].

Context propagation

A context is passed explicitly down the call chain, so that the cancellation of an incoming request reaches every goroutine doing work for it. The documented conventions are [32,35]:

  • “Do not store Contexts inside a struct type; instead, pass a Context explicitly to each function that needs it. The Context should be the first parameter, typically named ctx.”
  • “Do not pass a nil Context, even if a function permits it. Pass context.TODO if you are unsure about which Context to use.”
  • “Use context Values only for request-scoped data that transits processes and APIs,” not for optional parameters. Keys should be of an unexported, package-defined type, because a key “must be comparable and should not be of type string or any other built-in type to avoid collisions.”
  • “Contexts are safe for simultaneous use by multiple goroutines,” so one context can be shared by all the goroutines working on a request.

11Worker pools

A worker pool runs a fixed number of goroutines that take jobs from a shared channel. It bounds concurrency (and therefore memory, open files, database connections or CPU use) independently of how many jobs arrive. Because a channel delivers each value to exactly one receiver, workers ranging over the same jobs channel share the work automatically [7]. The structure has three responsibilities that must be kept separate: a feeder sends jobs and closes jobs; workers range over jobs and send results; a closer waits for the workers and then closes results so that the collector’s range terminates.

Size CPU-bound pools near runtime.GOMAXPROCS(0); size I/O-bound pools by the capacity of the downstream resource. If jobs can fail, return errors in the Result type or use errgroup with SetLimit (Section 19), which is a worker pool with error propagation built in.

12Fan-out and fan-in

Fan-out means several goroutines read from the same channel until it is closed, which distributes work among them; fan-in means a function reads from several input channels and multiplexes them onto one output channel, which it closes when all inputs are closed [36]. Pike’s Google I/O talk introduced these as composable building blocks [37]. The essential detail of merge is that it closes its output only after every forwarding goroutine has finished, which a WaitGroup makes easy [36].

Fan-in loses ordering. If results must come out in input order, tag each item with its index and reorder at the end, or write into a pre-sized slice by index as in Section 1.

13Pipelines

The Go blog defines a pipeline as “a series of stages connected by channels, where each stage is a group of goroutines running the same function”; each stage receives values from upstream, transforms them, and sends them downstream [36]. Stages compose like Unix pipes, and each can be fanned out independently. The hard part is shutdown. If the consumer stops reading early, upstream stages block forever on their sends and leak. The blog’s guidelines are that stages close their outbound channels when all sends are done, and that stages keep receiving until inbound channels close or the senders are unblocked by an explicit cancellation signal [36]. Today that signal is a context.Context.

Every send in every stage is written as a select between out <- v and <-ctx.Done(). That single habit is what makes the pipeline cancellable; the final goroutine count of 1 shows that cancelling tore down all three stages.

14Producer–consumer patterns

The producer–consumer problem has one or more producers creating items and one or more consumers processing them through a shared, bounded buffer. A buffered channel is such a buffer: sends block when it is full, which gives producers natural back-pressure, and receives block when it is empty [7]. With several producers the only subtlety is closing: no single producer knows when the others are done, so a separate goroutine waits on the producers’ WaitGroup and closes the channel exactly once.

The same structure built by hand with a mutex and sync.Cond is shown in Section 9; comparing the two shows why a channel is usually the better choice here. Hoare’s paper presents a bounded buffer as one of CSP’s motivating examples [3].

15Rate limiting

Rate limiting caps how often an operation may happen, to protect a downstream service or respect a quota. Three approaches cover most needs:

  1. A ticker. Receiving from a time.Ticker before each operation gives a steady rate. The ticker “will adjust the time interval or drop ticks to make up for slow receivers” [38], so it never builds up a backlog. Always Stop a ticker you no longer need.
  2. A token bucket built from a buffered channel. Pre-fill a buffered channel with tokens to permit a burst, and refill it from a ticker with a non-blocking send.
  3. golang.org/x/time/rate. Its Limiter “implements a ‘token bucket’ of size b, initially full and refilled at rate r tokens per second” [39]. Wait(ctx) blocks until a token is available or the context is done, Allow() reports whether an event may happen now, and Reserve() tells you how long to wait [39]. Prefer it in production code.

A rate limiter limits frequency; a semaphore or worker pool limits concurrency. Many systems need both: at most 10 requests in flight, and at most 100 per second.

16Deadlocks

A deadlock is a set of goroutines each waiting for something that only another member of the set can provide. Coffman, Elphick and Shoshani identified four conditions that must all hold for a deadlock: mutual exclusion, hold and wait, no preemption, and circular wait [40]. Breaking any one of them prevents deadlock.

When every goroutine is blocked, the Go runtime detects it and aborts with fatal error: all goroutines are asleep - deadlock! [11]:

The runtime check is narrow. It fires only if no goroutine can run; a partial deadlock, where a few goroutines are stuck while others (an HTTP server, a ticker) keep running, goes unreported and looks like a hang or a leak. Common causes and their cures:

wg.Wait() before receiving results that workers are blocked sendingWait in a separate goroutine, then close the results channel (Section 11)

Ordering by account ID breaks the circular-wait condition: two opposite transfers both try to lock account 1 first, so one waits without holding anything.

17Race conditions

The memory model defines a data race as “a write to a memory location happening concurrently with another read or write to that same location, unless all the accesses involved are atomic data accesses as provided by the sync/atomic package” [22]. Programs without data races behave as if their goroutines were interleaved on one processor, a property the memory model calls DRF-SC: “data-race-free programs execute in a sequentially consistent manner” [22]. A racy program has no such guarantee. Races on multiword values such as interfaces, slices, maps and strings “can in turn lead to arbitrary memory corruption” [22].

A data race is one kind of race condition, a bug in which the result depends on timing. A program can be free of data races and still have race conditions at a higher level: for example, checking a balance under one lock and debiting it under another lets two goroutines both pass the check. Locks protect individual accesses; preserving an invariant requires holding the lock across the whole check-then-act sequence.

The race detector

Go ships a race detector, enabled with -race on go test, go run and go build [41]. It is built on the ThreadSanitizer runtime library [42,43] and reports the stack traces of both conflicting accesses and of the goroutines involved. Two properties determine how to use it [41]:

  • “The race detector only finds races that happen at runtime, so it can’t find races in code paths that are not executed.” A clean run therefore proves nothing about untested paths, so run it on tests with good coverage and, as the documentation suggests, on binaries under realistic workloads.
  • “For a typical program, memory usage may increase by 5-10x and execution time by 2-20x.” Use it routinely in CI and in canaries, but not usually in full production.

The fix for a data race is always synchronization: a mutex, an atomic, or confining the data to one goroutine. Exercise 3 shows all three. Reducing the window, for example by adding a sleep, hides the race without fixing it.

An empirical study of 171 concurrency bugs in six large Go projects, including Docker, Kubernetes and gRPC, found that more than half were caused by Go-specific problems, and that message passing was not less error-prone than shared memory: wrong use of message passing caused more of the blocking bugs studied than wrong use of shared memory did [44]. Channels prevent data races by design, but they introduce their own failure modes, which are the subject of the next section.

18Goroutine leaks

A goroutine leak is a goroutine that never terminates, usually because it is blocked forever on a channel operation or lock. As the Go code review guidelines warn, “Goroutines can leak by blocking on channel sends or receives: the garbage collector will not terminate a goroutine” even if the channel is unreachable [35]. Each leaked goroutine pins its stack and everything it references; in a server that leaks one per request, memory grows until the process dies.

The classic leak is an abandoned send. A function starts a worker, waits for its result with a timeout, and returns on timeout, leaving the worker blocked forever on an unbuffered send that no one will receive:

Both fixes work. A buffer of one guarantees that the single send succeeds whether or not anyone receives it; passing a context lets the worker abandon the send. The general cure is that every goroutine must have a guaranteed way to exit: every blocking send or receive should be in a select with a cancellation case, or be guaranteed to complete.

Detecting leaks

  • Count. Compare runtime.NumGoroutine() before and after a test, allowing a moment for goroutines to exit [10].
  • Dump. The goroutine profile in runtime/pprof, or /debug/pprof/goroutine?debug=2 with net/http/pprof, shows every goroutine’s stack; hundreds of goroutines parked at the same line is the signature of a leak [45].
  • The goroutine leak profile. Go 1.26 introduced an experimental goroutineleak profile, and Go 1.27 made it generally available [21,46]. It uses the garbage collector to find goroutines blocked on a channel, mutex or condition variable that is unreachable from any runnable goroutine, and that therefore can never be woken. The release notes caution that leaks involving primitives reachable from global variables or from the locals of runnable goroutines may be missed [21].

19Structured concurrency patterns

The bugs in Sections 16–18 share a root cause: goroutines whose lifetimes nobody owns. Structured concurrency, a term coined by Martin Sústrik [47] and developed by Nathaniel J. Smith, answers this by tying concurrent tasks to a lexical scope: a block that starts goroutines does not exit until all of them have finished [48]. Smith’s essay argues, using Go’s go statement as its main example, that an unrestricted “start a task and forget it” primitive breaks the abstraction of a function call, in the same way that goto breaks structured control flow [48].

Go does not enforce structured concurrency, but the community conventions amount to it. The code review guidelines ask that “when you spawn goroutines, make it clear when - or whether - they exit,” and recommend synchronous APIs: “Synchronous functions keep goroutines localized within a call, making it easier to reason about their lifetimes” [35]. In practice that means:

  1. Scope goroutines to a function. A function that starts goroutines waits for them before returning (with WaitGroup or errgroup). Callers who want concurrency can add it themselves [35].
  2. Propagate cancellation. Pass a context.Context into the scope and select on ctx.Done() in every blocking operation [32].
  3. Propagate errors. Return the first error to the scope’s caller and cancel the siblings.
  4. Bound concurrency. Limit the number of goroutines a scope may start.
  5. Make long-lived goroutines owned. Background goroutines (janitors, flushers) belong to an object with a Close or Shutdown method that stops them and waits for them (Exercise 9).

The golang.org/x/sync/errgroup package implements points 1–4. It “provides synchronization, error propagation, and Context cancellation for groups of goroutines working on subtasks of a common task” [49]. WithContext returns a group and a derived context that “is canceled the first time a function passed to Go returns a non-nil error or the first time Wait returns”; Wait blocks until all functions have returned and returns the first non-nil error; and SetLimit(n) caps the number of active goroutines, making Go block until a slot is free [49].

fetchAll is a well-formed concurrency scope: it starts goroutines, bounds them, cancels them on the first failure, waits for every one, and returns a single error. Nothing it starts can outlive it, so it cannot leak, and its caller sees an ordinary synchronous function.

Testing with testing/synctest

Concurrent code that uses time is hard to test: real sleeps make tests slow and flaky. Go 1.25 added testing/synctest. Its Test function runs a test in an isolated “bubble” in which “time is virtualized: time package functions operate on a fake clock and the clock moves forward instantaneously if all goroutines in the bubble are blocked”; Wait waits until every goroutine in the bubble is blocked [16,50]. Exercise 10 tests ten seconds of retry logic in a few milliseconds of real time. Run every concurrent test with -race, and consider -count greater than 1 to shake out timing-dependent failures.

21Exercises and solutions

Try each exercise before opening its solution. Every solution was run with -race on Go 1.27.0; the outputs shown are from those runs.

Exercise 1. Parallel sum basic

Write ParallelSum(xs []int, n int) int that splits xs into n contiguous chunks, sums each in its own goroutine, and returns the total. It must be race-free without a mutex, and correct when n exceeds len(xs).

Show solution

Give each goroutine its own slot in a results slice. Distinct slice elements are distinct memory locations, so there is no data race [22], and wg.Wait() makes every write visible to the final loop [24]. Clamping lo and hi with min makes surplus goroutines sum an empty slice.

Exercise 2. Ping-pong basic

Write two goroutines, ping and pong, that print alternately with a counter from 1 to 6, so that the order is guaranteed. Use only channels; no sleep, no mutex.

Show solution

An unbuffered channel is a rendezvous, so passing a “ball” back and forth forces strict alternation: only the goroutine holding the ball can print [7]. A separate done channel tells main when to stop.

Exercise 3. Fix the race three ways basic

Take the racy counter from Section 17 and make it correct (a) with sync.Mutex, (b) with sync/atomic, and (c) with no shared variable at all, confining the counter to one goroutine. Confirm with go run -race.

Show solution

Version (c) applies “share memory by communicating” [6]: the count lives in one goroutine, and others send it increment requests.

Exercise 4. First response wins intermediate

Write First(ctx, query, replicas...) that sends the query to every replica concurrently, returns the first successful answer, cancels the others, and leaks no goroutines, including when the context times out. (This is the “replicated search” from Pike’s talk [37].)

Show solution

Two details prevent leaks. The result channel has one slot per replica, so a losing replica can always deliver its result and exit even after First has returned. And defer cancel() tells the losers to stop work early [32].

Exercise 5. Bounded, ordered parallel map intermediate

Write a generic ParallelMap[T, U any](ctx, in []T, limit int, f func(context.Context, T) (U, error)) ([]U, error) that runs at most limit calls at a time, preserves input order, and stops early on the first error.

Show solution

errgroup provides the limit, the first-error result and cancellation [49]; writing to out[i] preserves order without sorting.

Exercise 6. Cancellable fan-in intermediate

Generalize merge from Section 12 into Merge[T any](ctx context.Context, cs ...<-chan T) <-chan T so that cancelling ctx stops all forwarding goroutines even if the consumer stops reading. Show that no goroutines remain after cancellation.

Show solution

Each forwarder’s send is a select with ctx.Done(), following the pipeline cancellation guideline [36]. The infinite counter sources also honour ctx, so everything exits.

Exercise 7. Rate-limited worker pool intermediate

Build a pool of 4 workers processing 10 jobs such that the total rate never exceeds 100 jobs per second, however many workers there are. Verify the elapsed time is consistent with the limit.

Show solution

One shared rate.Limiter is the global throttle; it is safe for concurrent use [39]. With burst 1, the first job runs at once and each of the other nine waits 10 ms, so the run takes at least about 90 ms.

Exercise 8. Find the deadlock intermediate

This program never finishes. Find both bugs, explain them, and fix them. Hint: run go vet first.

Show solution

Bug 1: the WaitGroup is copied. worker takes sync.WaitGroup by value, so Done decrements a copy and main’s counter never reaches zero. go vet reports exactly this [25]:

Bug 2: Wait happens before anyone receives. Even with a pointer, each worker blocks on the unbuffered send out <- id*id, so it never reaches Done, and main never gets past Wait to the receiving loop [7]. The fix is to wait and close in a separate goroutine while main receives.

Exercise 9. A TTL cache with an owned background goroutine advanced

Implement a string cache whose entries expire after a TTL. A background goroutine sweeps expired entries periodically. Provide Close(), which must be idempotent and must not return until the background goroutine has exited.

Show solution

An RWMutex guards the map; the janitor is owned by the cache and tracked by its WaitGroup; sync.Once makes closing the stop channel idempotent, avoiding the panic from closing a closed channel [7,24]; and the ticker is stopped on exit [38]. Because Close waits, a caller can rely on there being no leftover goroutine, which is the structured-concurrency guarantee from Section 19.

Exercise 10. Test time-dependent code instantly advanced

WithRetry(ctx, backoff, f) calls f until it succeeds, sleeping backoff between attempts, and gives up when ctx is done. Write tests showing that with a 10 s timeout and 3 s backoff, f is called exactly 4 times and the function returns after exactly 10 s. The test must finish in milliseconds.

Show solution

Run the test inside synctest.Test. Inside the bubble the clock is fake and advances only when every goroutine is blocked, so the timeline is deterministic: calls at 0, 3, 6 and 9 s, then the deadline at 10 s [50].
