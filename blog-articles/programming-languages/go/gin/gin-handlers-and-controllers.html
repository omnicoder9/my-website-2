Handlers and Controllers in Gin

A practical guide for Go developers · Gin v1.12.0, Go 1.25 · October 2026

Summary. In Gin every piece of request-processing code, from a one-line endpoint to authentication middleware, is a value of one type: gin.HandlerFunc. This article starts from that type and builds outward. It covers how handlers are called and chained, how to group them into controllers, how to read requests and write responses consistently, and how to keep HTTP code apart from business logic with dependency injection, service and repository layers, and small interfaces. Each claim is tied to the Gin source, the Go documentation, or the primary literature on the pattern. A complete, tested program runs through the article, and eight exercises with worked solutions close it.

Scope. Routing syntax and HTTP-method semantics are covered in a companion article, so they appear here only where a handler needs them.

2. Handler functions

A handler is the code that runs when a request matches a route. In Gin it is a function that receives a pointer to a gin.Context. The framework defines it as a named function type in gin.go (lines 50–51), next to a slice type for a sequence of handlers (lines 56–57)[2]:

// HandlerFunc defines the handler used by gin middleware as return value.
type HandlerFunc func(*Context)

// HandlersChain defines a HandlerFunc slice.
type HandlersChain []HandlerFunc

In Go a function type "denotes the set of all functions with the same parameter and result types"[4] (section "Function types"). Any function whose only parameter is *gin.Context and which returns nothing is therefore a valid gin.HandlerFunc, whether it is a named function, a function literal, or a method value. Gin draws no line between "endpoints" and "middleware". Both are HandlerFuncs. The only difference is where they sit in the chain and whether they call c.Next() (see §7).

What *gin.Context carries

gin.Context bundles everything a handler needs for one request: the incoming *http.Request (c.Request), a ResponseWriter (c.Writer), the path parameters, a key/value store for request-scoped data (c.Set/c.Get), an error list (c.Errors), and the remaining handler chain[5,3]. It also implements the standard context.Context interface through its Deadline, Done, Err and Value methods[3].

Contexts are pooled, so never keep one

Gin does not allocate a new Context for every request. Engine.ServeHTTP takes one from a sync.Pool, resets it, runs the handlers, and puts it back[2]:

A sync.Pool is "a set of temporary objects that may be individually saved and retrieved", and any item in it "may be removed automatically at any time"[6]. One consequence matters a great deal in practice. Once your handler returns, the *gin.Context it received may already be serving someone else's request. Gin's documentation says so directly: "When starting new Goroutines inside a middleware or handler, you SHOULD NOT use the original context inside it, you have to use a read-only copy" (c.Copy())[7] (section "Goroutines inside a middleware"). Exercise 5 works through this case.

3. Handler signatures

Gin's signature, func(*gin.Context), differs from the standard library's. In net/http a handler is any value with a ServeHTTP(ResponseWriter, *Request) method, and http.HandlerFunc is "an adapter to allow the use of ordinary functions as HTTP handlers"[8]. Gin folds the writer and request into one context object and adds flow control on top. There are five common ways to produce a value of the right type:

  • Function literals are closures. They "may refer to variables defined in a surrounding function"[4] (section "Function literals"). That is what makes the handler factory in case 4 work, and it is how most middleware is configured.
  • Method values. For a value h, the method value h.List "is a function value" callable with the method's arguments, with the receiver already bound[4] (section "Method values"). This is what lets controller methods be registered directly (§4).
  • Adapters. gin.WrapF and gin.WrapH turn an http.HandlerFunc or http.Handler into a gin.HandlerFunc[9], so existing standard-library handlers can be mounted unchanged.

No return value, so who handles errors?

A gin.HandlerFunc returns nothing. A handler that fails has to do one of two things. It can write an error response itself, or it can record the error with c.Error(err), which appends to c.Errors[3] so that a middleware further up the chain can render it (§6). 4. Controller organization

Gin has no "controller" type. Its API reference defines engines, router groups, contexts and handler functions, and nothing more[5]. "Controller" is a convention borrowed from MVC frameworks. In idiomatic Go it usually means a struct whose methods are handlers and whose fields are the dependencies those handlers share.

This shape has three advantages.

  1. Dependencies are explicit. The struct's fields list exactly what the handlers need, and the constructor is the only way to supply them (§10).
  2. Routes live next to their handlers. Register takes a *gin.RouterGroup. The caller picks the prefix and any group middleware, and the controller picks the relative paths. RouterGroup.Group accepts its own handlers, which are prepended to every route in the group[10]. Route-group syntax is covered in the companion routing article.
  3. The controller is easy to test. Because svc is an interface, a test can pass a stub (§13).

Package layout

Go does not require a particular directory structure. The official guide on organizing modules recommends putting server code that should not be imported by others under internal/[11]. The go command enforces this: code under internal/ "can be imported only by code in the directory tree rooted at the parent of the 'internal' directory"[12]. A layout that matches the layers in this article looks like this:

5. Request handlers

A request handler's job is narrow. It turns HTTP input into typed values, calls the code that does the work, and hands the result to the response step. Gin's binding API covers the first part.

Bind or ShouldBind?

Gin offers two families of binding methods[7] (section "Model binding and validation"):

FamilyExamplesOn error
Must bindBind, BindJSON, BindQuery, BindUri…Calls c.AbortWithError(400, err).SetType(ErrorTypeBind). This writes status 400 with Content-Type: text/plain and aborts the chain.
Should bindShouldBind, ShouldBindJSON, ShouldBindUri…Returns the error. "It is the developer's responsibility to handle the request and error appropriately."

The documentation warns that after a Must-bind failure, setting another status produces [WARNING] Headers were already written[7]. The source shows why: responseWriter.WriteHeader ignores a new code once the header has been written[13]. If you want one consistent error format, use the ShouldBind* methods and leave the rendering to a single response step.

Request DTOs and validation tags

Bind into a request-specific struct (a data-transfer object) rather than the domain type. The struct tags then describe the transport format and its validation without leaking into business code. Gin validates with go-playground/validator v10 through the binding tag[7,14]. For URI parameters, use the uri tag with ShouldBindUri[7] (section "Bind Uri").

Two details deserve comment.

  • Pass c.Request.Context() down, not c. The service layer should not depend on Gin at all. The standard context package also asks that a Context be passed "explicitly to each function that needs it", as the first parameter, and not stored in a struct[15].
  • The request body can be read only once. "The normal methods for binding request body consumes c.Request.Body and they cannot be called multiple times". Use ShouldBindBodyWith if you need to try several shapes[7] (section "Try to bind body into different structs").

6. Response handlers

"Response handler" here means the code that turns a result or an error into status, headers and body. Gin's Context provides renderers for JSON (JSON, IndentedJSON, PureJSON, SecureJSON…), XML, YAML, TOML, ProtoBuf, plain strings, raw bytes (Data), files and streams. It also has Negotiate, which picks a format from the Accept header[3,7]. Two behaviors catch people out:

  • c.JSON escapes HTML characters, so & becomes & in the example output below. c.PureJSON leaves them as they are[7] (section "PureJSON").
  • c.Status(code) sets a status without a body, which is right for 204 No Content. If a handler writes nothing at all, Gin flushes the pending status after the chain finishes, and the default is 200[2,13].

Status codes carry meaning

Choose status codes from their definitions in RFC 9110[16], not by habit. The example uses 201 Created with a Location header naming the new resource (sections 15.3.2 and 10.2.2), 204 No Content for a successful delete (15.3.5), 403 Forbidden (15.5.4), 404 Not Found (15.5.5), 409 Conflict for a duplicate (15.5.10), and 422 Unprocessable Content for input that parses but breaks a domain rule (15.5.21). Go's net/http constants note the same section numbers[8].

Centralizing error responses

Rather than repeating if errors.Is(...) { c.JSON(...) } in every handler, handlers call c.Error(err) and return. A single middleware runs c.Next(), then looks at c.Errors. Gin's own comment on Context.Error recommends this: "A middleware can be used to collect all the errors and push them to a database together, print a log, or append it in the HTTP response"[3].

This works with errors.Is because gin.Error has an Unwrap method "to allow interoperability with errors.Is(), errors.As() and errors.Unwrap()"[17]. errors.Is walks that chain of wrapped errors[18,19]. The c.Writer.Written() guard skips responses that a handler has already sent.

Headers must be set before the body. Code that runs after c.Next() can read c.Writer.Status(), but by then the downstream handler has usually written headers and body. Headers set at that point never reach the client. Exercise 3 shows a test that is fooled by this.

7. Handler chaining

When a route matches, Gin loads that route's HandlersChain into the context and calls c.Next()[2]. The whole mechanism is a few lines in context.go[3]:

From this you can work out the rules:

  1. Handlers run in order. c.index starts at −1 (set in reset), so the first Next() runs handler 0[3].
  2. Calling Next() runs the rest of the chain inside the current handler. Code before Next() runs on the way in, code after it runs on the way out. Gin's documented logger middleware relies on this to measure latency[7] (section "Custom Middleware").
  3. Not calling Next() is fine. When a handler returns, the loop in the outer Next() moves on to the following handler anyway. Explicit Next() is needed only when you want code to run after the downstream handlers.
  4. Abort() does not stop the current function. It sets the index to abortIndex (63), so the loop ends. The source comment says it directly: "Note that this will not stop the current handler"[3]. Always return after aborting.
  5. Handlers further up still finish. Aborting skips handlers that have not run yet. It does not unwind the ones that called Next(), and their "after" code still runs.

8. Multiple handlers per route

Every registration method (GET, POST, Handle, Group, Use…) is variadic in ...HandlerFunc[10]. When a route is registered, Gin builds its chain by copying the group's accumulated handlers and appending the route's own:

Two consequences follow. First, the order is fixed when the route is registered. The documentation's middleware example puts r.Use(...) calls before route registration[7] (section "Using middleware"), and that order matters, because a route registered earlier has already copied the old handler list. Second, per-route handlers are the natural home for checks that apply to one endpoint only, such as the role check on DELETE in Listing 4.

Passing data along the chain

Handlers in a chain share state through c.Set and c.Get. Since Gin v1.11 these accept any as the key[3]. Earlier releases, such as v1.10.1, took a string[20]. An unexported key type, as in Listing 10, means no other package can overwrite your value by accident. The context package recommends this for its own keys[15]. Typed getters such as GetString return the zero value when the key is missing or holds a different type[3], and Exercise 8 builds a typed accessor on top of them. Store request-scoped data only (the authenticated user, a request ID). The context package warns against using context values "for passing optional parameters to functions"[15], and the same reasoning applies to dependencies such as a database handle.

9. Separation of concerns

Dijkstra coined the phrase separation of concerns. He described it as "focussing one's attention upon some aspect" while studying it "in isolation for the sake of its own consistency", knowing that other aspects exist but setting them aside for the moment[21]. In a web service the main concerns are transport (HTTP), business rules, and persistence. Each changes for different reasons and should be testable on its own.

10. Dependency injection

Fowler coined the name dependency injection for the pattern in which a separate assembler supplies an object with its dependencies, instead of the object finding or building them itself. He described three forms: constructor injection, setter injection and interface injection[22]. Go has no DI container in its standard library, and none is needed. Constructor injection is plain Go: a New... function takes the dependencies as parameters and stores them in struct fields.

Guidelines:

  • Inject through constructors. Don't reach for package-level variables (the db global in Listing 11). A global hides the dependency and forces tests to share state.
  • Take the narrowest type that works. NewBookHandler takes a BookUseCases interface, not *BookService, so tests can substitute a stub (§12).
  • Keep dependencies out of c.Set. A database handle fetched with c.MustGet("db") is a service locator, so the compiler can no longer check that it was provided. MustGet panics if the key is missing[3].
  • Handler factories are injection too. RequireRole("admin") injects configuration through a closure. Exercise 6 does the same with a service.

11. Service and repository layers

Both layers come from Fowler's Patterns of Enterprise Application Architecture[23]. A Service Layer "defines an application's boundary with a layer of services that establishes a set of available operations and coordinates the application's response in each operation"[24]. A Repository "mediates between the domain and data mapping layers using a collection-like interface for accessing domain objects"[25].

Repository

The in-memory repository guards its map with a sync.RWMutex, because Gin serves requests concurrently and a Go map is not safe for concurrent writes. RWMutex allows "an arbitrary number of readers or a single writer"[6]. A PostgreSQL implementation would have the same method set and use database/sql. Callers would not change.

Service

The service returns domain errors (ErrValidation, ErrConflict, ErrNotFound), and the error middleware alone decides what HTTP status each one gets. Matching sentinel errors with errors.Is rather than == keeps working if a lower layer later wraps them with fmt.Errorf("...: %w", err)[19].

Is a service layer always worth it? For a pure CRUD endpoint the service may only forward calls, as List and Delete do here. Keep the layer anyway once a feature has real rules, such as Create's duplicate check. Then the rule has one home that both HTTP handlers and, say, a CLI or queue consumer can call.

12. Interface-based abstractions

A Go type satisfies an interface simply by having the right methods. There is no implements keyword. The specification says a type implements an interface if it is in the interface's type set, which for ordinary interfaces means its method set includes the interface's methods[4] (sections "Interface types", "Implementing an interface", "Method sets"). Several practices follow.

Define interfaces where they are used

The Go code-review guidelines state: "Go interfaces generally belong in the package that uses values of the interface type, not the package that implements those values", and advise against defining interfaces "before they are used"[26]. That is why BookUseCases is declared next to BookHandler, which uses it, and not next to BookService, which implements it. The handler states what it needs, and *BookService happens to fit. This is the dependency-inversion principle as Martin stated it: high-level modules and low-level modules both depend on abstractions[27].

Keep interfaces small

Effective Go notes that "interfaces with only one or two methods are common in Go code"[28] (section "Interfaces"). A handler that only reads books should ask for a one-method interface, not for BookUseCases. Exercise 6 does this and adds a function adapter in the style of http.HandlerFunc[8].

Check satisfaction at compile time

Because satisfaction is implicit, a typo in a method signature is caught only where the value is used as the interface. The idiom var _ BookRepository = (*memoryBookRepo)(nil) makes the compiler check it at the declaration instead. Both Effective Go (section "Interface checks") and the Go FAQ describe it[28,29].

Return concrete types, accept interfaces

NewMemoryBookRepo returns *memoryBookRepo and NewBookService returns *BookService. Callers decide which interface they need. The review guidelines say the implementing package "should return concrete (usually pointer or struct) types"[26].

13. Testing the layers

Gin's documentation tests handlers by building a router and calling ServeHTTP with an httptest.ResponseRecorder, with no network involved[7,30] (section "Testing"). With the layers above, each test can choose how much of the real stack to include:

  • Handler tests pass a stub BookUseCases, which checks the HTTP mapping alone.
  • Service tests pass a fake BookRepository. The brokenRepo below embeds the interface and overrides one method, a common Go trick for partial fakes. Calling a method it does not override would panic, which suits a test.
  • End-to-end tests wire the real service and in-memory repository.

gin.SetMode(gin.TestMode) turns off debug output during tests[5]. The testing package documents t.Fatalf and the go test conventions used here[31].

Exercise 1: Which of these are handlers? (signatures)

For each declaration, say whether it can be passed directly to r.GET("/x", …). If it can't, show the smallest change that makes it work.

// (a)
func a(c *gin.Context) {}
// (b)
func b(c *gin.Context) error { return nil }
// (c)
func c(w http.ResponseWriter, r *http.Request) {}
// (d)
type Ctl struct{}
func (Ctl) Show(c *gin.Context) {}
// (e)
func e() gin.HandlerFunc { return func(*gin.Context) {} }
Solution

(a) Yes, the signature matches gin.HandlerFunc exactly. (b) No, because the extra error result changes the function type[4]. Adapt it with the Handle adapter from Listing 3. (c) No, this is the net/http shape. Wrap it with gin.WrapF[9]. (d) Yes, as a method value Ctl{}.Show[4]. (e) Not e itself, which has type func() gin.HandlerFunc. Pass the result of calling it.

r.GET("/a", a)                          // (a) OK as is
r.GET("/b", Handle(b))                  // (b) via the AppHandler adapter
r.GET("/c", gin.WrapF(c))               // (c) via gin.WrapF
r.GET("/d", Ctl{}.Show)                 // (d) method value
r.GET("/e", e())                        // (e) call the factory

Exercise 2: Predict the chain (handler chaining)

Using Listing 8, predict the trace for GET /x?deny=1 if gate called c.Abort() but had no return after trace = append(trace, "gate still running"), and final were registered as a group handler instead (r.Group("/x", mw("B"), final), g.GET("", gate)).

Solution

Group handlers come before route handlers (Listing 9), so the chain is A, B, final, gate. final runs before gate and writes "ok" with status 200. gate then aborts, but the response is already committed. AbortWithStatus tries to write 401, and WriteHeader logs the "Headers were already written" warning and leaves the 200 in place[13]. The trace is:

A before | B before | final | gate | gate still running | B after | A after   (status 200)

Lesson: guards must come before the handlers they protect. Register them with Use/Group or list them first in the route.

Exercise 3: Spot the bug (response handlers)

A colleague adds this middleware, and its unit test checks w.Header().Get("X-Response-Time") on an httptest.ResponseRecorder. The test passes, but browsers never see the header. Explain why, and fix it.

func ResponseTime() gin.HandlerFunc {
	return func(c *gin.Context) {
		start := time.Now()
		c.Next()
		c.Header("X-Response-Time", time.Since(start).String())
	}
}
Solution

By the time c.Next() returns, the handler has called c.JSON, which wrote the status line and headers. Anything added afterwards is too late. The test is misleading: ResponseRecorder.Header() returns the live map, which the late call still changes, whereas Result().Header is "a snapshot of the headers at the time of the first write call"[30]. Running both against Gin v1.12.0 gave w.Header().Get(...) = "13.069µs" but w.Result().Header.Get(...) = "". Assert on w.Result().Header in tests. To fix the middleware, record the timing somewhere that doesn't depend on headers, or set only headers that are known before Next():

// Option 1: record the measurement where headers do not matter.
func ResponseTime() gin.HandlerFunc {
	return func(c *gin.Context) {
		start := time.Now()
		c.Next()
		log.Printf("%s took %s", c.FullPath(), time.Since(start))
	}
}

// Option 2: emit a header that is known *before* the body, such as a
// request ID, and set it before calling c.Next().
func RequestID() gin.HandlerFunc {
	return func(c *gin.Context) {
		id := c.GetHeader("X-Request-ID")
		if id == "" {
			id = strconv.FormatInt(time.Now().UnixNano(), 36)
		}
		c.Header("X-Request-ID", id) // before Next: reaches the client
		c.Next()
	}
}

Exercise 4: Add an update endpoint (all layers)

Add PUT /api/v1/books/:id. It must return 404 for an unknown ID and 409 if the new title/author pair belongs to a different book, and it must reuse createBookRequest for validation. Touch each layer once.

Solution

Add Update(ctx, Book) (Book, error) to BookRepository, Update(ctx, id, title, author) (Book, error) to BookUseCases, and rg.PUT("/:id", h.Update) to Register. Then:

// ---- Exercise 4: Update across all layers ----

// Repository: added to the interface and the in-memory implementation.
func (r *memoryBookRepo) Update(ctx context.Context, b Book) (Book, error) {
	r.mu.Lock()
	defer r.mu.Unlock()
	if _, ok := r.books[b.ID]; !ok {
		return Book{}, ErrNotFound
	}
	r.books[b.ID] = b
	return b, nil
}

// Service: same normalisation and duplicate rule as Create, but a book may
// keep its own title.
func (s *BookService) Update(ctx context.Context, id int64, title, author string) (Book, error) {
	title, author = strings.TrimSpace(title), strings.TrimSpace(author)
	if title == "" || author == "" {
		return Book{}, ErrValidation
	}
	if _, err := s.repo.FindByID(ctx, id); err != nil {
		return Book{}, err
	}
	if other, err := s.repo.FindByTitleAuthor(ctx, title, author); err == nil && other.ID != id {
		return Book{}, ErrConflict
	}
	return s.repo.Update(ctx, Book{ID: id, Title: title, Author: author})
}

// Handler.
func (h *BookHandler) Update(c *gin.Context) {
	var uri bookURI
	if err := c.ShouldBindUri(&uri); err != nil {
		_ = c.Error(err).SetType(gin.ErrorTypeBind)
		return
	}
	var req createBookRequest
	if err := c.ShouldBindJSON(&req); err != nil {
		_ = c.Error(err).SetType(gin.ErrorTypeBind)
		return
	}
	book, err := h.svc.Update(c.Request.Context(), uri.ID, req.Title, req.Author)
	if err != nil {
		_ = c.Error(err)
		return
	}
	c.JSON(http.StatusOK, gin.H{"data": book})
}

No change to ErrorHandler is needed: the new handler reports ErrNotFound and ErrConflict exactly as the others do. The test stub must also gain an Update method. If you forget, the compiler reports that stubBooks no longer implements BookUseCases[4].

Exercise 5: Background work (handler functions)

What is wrong with this handler, and what are two ways to fix it?

func (h *SignupHandler) Signup(c *gin.Context) {
	go func() {
		// BUG: c is recycled after this handler returns.
		_ = h.mail.SendWelcome(c, c.PostForm("email"))
	}()
	c.Status(http.StatusAccepted)
}
Solution

The goroutine uses c after the handler has returned, and by then Gin may have put the Context back in its pool and reused it for another request (Listing 1)[2,7]. There is a second problem. Even a correct copy of the request context is cancelled when the request finishes[8], which would cancel the email send.

Fix 1 (documented by Gin): pass cp := c.Copy() into the goroutine. The copy is "safely used outside the request's scope"[3].

Fix 2 (preferred when the service does not need Gin): read the values you need first, then detach from cancellation with context.WithoutCancel, which returns a context that "is not canceled when parent is canceled" (Go 1.21+)[15]. Add your own timeout:

// ---- Exercise 5: goroutines ----

type Mailer interface {
	SendWelcome(ctx context.Context, to string) error
}

type SignupHandler struct{ mail Mailer }

func (h *SignupHandler) Signup(c *gin.Context) {
	email := c.PostForm("email") // read everything you need *now*
	ctx := context.WithoutCancel(c.Request.Context())
	go func() {
		ctx, cancel := context.WithTimeout(ctx, 10*time.Second)
		defer cancel()
		if err := h.mail.SendWelcome(ctx, email); err != nil {
			log.Printf("welcome mail to %s: %v", email, err)
		}
	}()
	c.Status(http.StatusAccepted)
}

Exercise 6: A narrower dependency (interfaces, DI)

Write ShowBook(svc) gin.HandlerFunc, a handler factory for GET /books/:id that depends on the smallest interface that works. Then make it testable with a plain function, without a stub struct.

Solution

Declare a one-method interface where it is used[26], plus a function type with a method that satisfies it. This is the same trick as http.HandlerFunc[8]. *BookService satisfies bookGetter without modification.

// ---- Exercise 6: narrow consumer interface + func adapter ----

type bookGetter interface {
	Get(ctx context.Context, id int64) (Book, error)
}

// bookGetterFunc lets an ordinary function satisfy bookGetter,
// mirroring net/http's HandlerFunc adapter.
type bookGetterFunc func(ctx context.Context, id int64) (Book, error)

func (f bookGetterFunc) Get(ctx context.Context, id int64) (Book, error) { return f(ctx, id) }

func ShowBook(svc bookGetter) gin.HandlerFunc {
	return func(c *gin.Context) {
		var uri bookURI
		if err := c.ShouldBindUri(&uri); err != nil {
			_ = c.Error(err).SetType(gin.ErrorTypeBind)
			return
		}
		b, err := svc.Get(c.Request.Context(), uri.ID)
		if err != nil {
			_ = c.Error(err)
			return
		}
		c.JSON(http.StatusOK, gin.H{"data": b})
	}
}

Test: r.GET("/books/:id", ShowBook(bookGetterFunc(func(_ context.Context, id int64) (Book, error) { return Book{ID: id}, nil }))).

Exercise 7: Better validation errors (request and response handlers)

The error middleware currently echoes raw validator and parser messages (for example strconv.ParseInt: parsing "abc": invalid syntax), which leak implementation details. Change it so validation failures return a fields map, and other bind errors return a generic message.

Solution

When validation fails, the binding returns a validator.ValidationErrors value, and each element reports Field() and Tag()[14]. Detect it with errors.As, which also looks through gin.Error's Unwrap[18,17]:

// ---- Exercise 7: field-level validation errors ----

func validationDetails(err error) (map[string]string, bool) {
	var verrs validator.ValidationErrors
	if !errors.As(err, &verrs) {
		return nil, false
	}
	out := make(map[string]string, len(verrs))
	for _, fe := range verrs {
		out[fe.Field()] = "failed '" + fe.Tag() + "' rule"
	}
	return out, true
}
// Inside ErrorHandler, before the switch:
if fields, ok := validationDetails(last.Err); ok {
	c.JSON(http.StatusBadRequest, gin.H{"error": "validation failed", "fields": fields})
	return
}
// ...and in the ErrorTypeBind case, stop echoing raw parser messages:
case last.IsType(gin.ErrorTypeBind):
	status, msg = http.StatusBadRequest, "malformed request"

Observed output:

POST {"title":""}  -> 400 {"error":"validation failed","fields":{"Author":"failed 'required' rule","Title":"failed 'required' rule"}}
POST {bad json     -> 400 {"error":"malformed request"}

Exercise 8: Typed request-scoped values (chaining, multiple handlers)

An auth middleware stores the current user with c.Set("user", u), and handlers read it with c.MustGet("user").(User). List two risks, and replace the pattern with typed helpers.

Solution

Risks: (1) MustGet panics if the middleware did not run on that route[3], and the type assertion panics if a different type was stored under the key[4] (section "Type assertions"). (2) The string key "user" can be overwritten by any other package. Use an unexported key type[15] (supported as a c.Set key since Gin v1.11[3]) and a comma-ok accessor:

// ---- Exercise 8: typed accessors for request-scoped values ----

type User struct {
	ID    int64
	Email string
}

type userKeyType struct{}

var userKey userKeyType

func SetUser(c *gin.Context, u User) { c.Set(userKey, u) }

func CurrentUser(c *gin.Context) (User, bool) {
	v, ok := c.Get(userKey)
	if !ok {
		return User{}, false
	}
	u, ok := v.(User)
	return u, ok
}
