Middleware in Gin

A practical guide for Go developers · Written against Gin v1.12.0 and Go 1.25+ · gin-contrib/cors v1.7.9, gzip v1.2.8, timeout v1.2.3, requestid v1.0.8 · 30 October 2026

Middleware is where a Gin application handles everything that is not business logic: identifying the caller, deciding what they may do, recording what happened, surviving panics, and shaping the response for browsers and caches. This article explains how Gin runs middleware, then builds a production-style stack piece by piece. Every claim about Gin's behaviour is tied to its source code or documentation, and every Go example in this article compiles and is covered by tests.

Scope. Routing and handler design are covered in companion articles, so they appear here only where middleware depends on them. To run the examples, create a module and add the dependencies:

       github.com/gin-contrib/cors@v1.7.9 \
       github.com/gin-contrib/gzip@v1.2.8 \
       golang.org/x/time/rate

1. Middleware fundamentals

In Gin, middleware is not a separate concept from a handler. Both are values of the same type:[3]

// gin.go
type HandlerFunc func(*Context)
type HandlersChain []HandlerFunc

When you register a route, Gin builds a HandlersChain for it: the middleware attached to the engine and to every enclosing group, followed by the handlers you pass to GET, POST and so on. At request time Gin stores that chain on the *gin.Context together with an integer cursor, index, and starts walking it.[4,5] By convention the last function in the chain is "the handler" and the earlier ones are "middleware", but Gin treats them identically.[5]

The whole mechanism fits in a few lines of context.go:[4]

// context.go (Gin v1.12.0)
const abortIndex int8 = math.MaxInt8 >> 1 // 63

func (c *Context) Next() {
	c.index++
	for c.index < safeInt8(len(c.handlers)) {
		if c.handlers[c.index] != nil {
			c.handlers[c.index](c)
		}
		c.index++
	}
}

func (c *Context) Abort() {
	c.index = abortIndex
}

func (c *Context) IsAborted() bool {
	return c.index >= abortIndex
}

Three consequences follow directly from this code, and most of the rest of the article builds on them:

  1. Calling c.Next() runs the rest of the chain synchronously, then returns. Code after c.Next() runs once every later handler has finished. That is how a logger measures latency and reads the final status code.
  2. Not calling c.Next() does not stop the chain. The outer loop keeps advancing index, so the next handler still runs when the current one returns. You only need c.Next() when you want to do something after the downstream handlers.
  3. c.Abort() only moves the cursor. It sets index to 63, past the end of any legal chain, so the loop ends. It does not stop the function that called it and it does not write a response.

Because the cursor is an int8 and 63 is reserved as the "aborted" marker, Gin refuses to register a route whose combined chain has 63 or more handlers; combineHandlers panics with "too many handlers".[5] Real applications never come near the limit, but it explains the magic number.

Middleware as a factory

Gin's built-in middleware are functions that return a gin.HandlerFunc, for example gin.Logger() and gin.BasicAuth(accounts).[6,7] The outer function runs once at start-up and is the place for configuration and expensive set-up. The returned closure runs once per request. All the middleware in this article follow that shape:

func MyMiddleware(cfg Config) gin.HandlerFunc {
	// Runs once, when the router is built: validate cfg, compile regexes, etc.
	return func(c *gin.Context) {
		// Runs on every request, before the handler.
		c.Next()
		// Runs on every request, after the handler.
	}
}

The context is pooled

Gin recycles *gin.Context values through a sync.Pool on the engine and resets them between requests.[3,4] A context must therefore never be used after the request that owns it has finished. If middleware starts a goroutine that outlives the request, the Gin documentation requires passing it a read-only copy made with c.Copy().[8]

2. Global, group and route middleware

Gin lets you attach middleware at three levels. The only difference between them is which chains the function ends up in.[5,8]

r := gin.New()

// Global: added to the engine's root group. Applies to every route registered
// afterwards, and also to 404 (NoRoute) and 405 (NoMethod) responses.
r.Use(gin.Logger(), gin.Recovery())

// Group: applies to every route registered on the group (and its subgroups).
api := r.Group("/api", RateLimit(limiter, ByClientIP))
// Equivalent form:
// api := r.Group("/api"); api.Use(RateLimit(limiter, ByClientIP))

// Route-specific: listed before the final handler.
api.GET("/reports/slow", Timeout(2*time.Second), slowReport)

Global middleware

engine.Use appends to the root group's handler list and then rebuilds the handler chains for "no route" and "method not allowed" responses.[3] This is why global middleware such as security headers or request IDs also apply to 404 responses, while group middleware does not. gin.Default() is gin.New() plus engine.Use(Logger(), Recovery()).[3] When you want full control of the stack, start from gin.New().

Group middleware

RouterGroup.Group(path, handlers...) creates a child group whose handler list is a copy of the parent's list with the new handlers appended.[5] Groups nest, so an /admin group inside an authenticated group inherits both the global stack and authentication. The routing companion article covers groups in more depth.

Route-specific middleware

Any handler before the last one in a route registration is route middleware. This is the right place for something only one endpoint needs, such as a longer timeout on a report endpoint or a stricter rate limit on login.

Registration order matters. Chains are copied when a route is registered: handle calls combineHandlers, which allocates a new slice and copies the group's current handlers into it.[5] A Use call made after a route has been registered therefore does not affect that route. The test suite for this article confirms it: middleware added after GET /early was registered ran for /late and for 404 responses, but not for /early. Call Use before registering routes.

3. Middleware execution order

For a given route, the chain is: global middleware in the order passed to Use, then each enclosing group's middleware from outermost to innermost, then route middleware, then the handler.[5] Because each middleware can do work before and after c.Next(), execution forms an "onion": the "before" halves run outside-in and the "after" halves run inside-out.

This program makes the order visible:

package main

import (
	"fmt"

	"github.com/gin-gonic/gin"
)

func trace(name string) gin.HandlerFunc {
	return func(c *gin.Context) {
		fmt.Println(name, "before")
		c.Next()
		fmt.Println(name, "after")
	}
}

func main() {
	r := gin.New()
	r.Use(trace("global"))
	g := r.Group("/g", trace("group"))
	g.GET("/x", trace("route"), func(c *gin.Context) {
		fmt.Println("handler")
		c.String(200, "ok")
	})
	r.Run(":8080") // curl localhost:8080/g/x
}

Two practical rules follow from the onion model:

  • Anything that must observe the final outcome goes on the outside. A logger placed outside recovery sees the 500 that recovery writes for a panic. That is the order gin.Default() uses: Logger() first, then Recovery().[3]
  • Anything that must run even for rejected requests goes before the middleware that rejects them. CORS must sit before authentication, because browsers send preflight requests without credentials (see section 10).

4. c.Next() and c.Abort()

c.Next()

Call c.Next() when the middleware needs to act after downstream handlers finish: timing, logging, inspecting c.Errors, or post-processing. If the middleware only does work up front, such as setting a header or a context value, you can simply return. Gin's own BasicAuth does exactly that: on success it calls c.Set(AuthUserKey, user) and returns without calling c.Next().[7] Calling it explicitly anyway is harmless and makes intent clearer, which is the style used in this article.

c.Abort() and friends

Abort stops the handlers after the current one. Gin provides helpers that combine aborting with writing a response:[4]

MethodWhat it does
Abort()Sets the cursor to abortIndex. Writes nothing.
AbortWithStatus(code)Sets the status, writes headers immediately (WriteHeaderNow), then aborts.
AbortWithStatusJSON(code, obj)Aborts, then renders obj as JSON with the status.
AbortWithError(code, err)AbortWithStatus(code), then c.Error(err); returns the *gin.Error.
IsAborted()Reports whether the cursor is at or past abortIndex.

Always return after aborting. The source comment on Abort says it "will not stop the current handler".[4] Statements after c.AbortWithStatus(401) in the same function still run.

Aborting also does not cancel the "after" halves of outer middleware. Those calls to c.Next() are already on the stack, so they return normally and run their remaining code. That is desirable: the logger still logs the 401 and the request ID header is still present. The article's tests check both behaviours: with middleware outer → aborter → inner → handler, the observed sequence is outer before, outer after, and neither inner nor the handler runs.

Writing a response is not the same as aborting. If middleware calls c.JSON(401, …) without aborting, the handler still runs and appends its own body. Exercise 2 shows how that leaks data.

5. Writing custom middleware

A good custom middleware has four properties: it is built by a constructor that takes explicit configuration, it does no per-request work that could have been done once, it passes values to later handlers through the context rather than globals, and it is safe for concurrent use because one instance serves every request.

Passing values down the chain

c.Set(key, value) and c.Get(key) store per-request values in c.Keys, which in v1.12.0 is a map[any]any protected by a mutex.[4] Because the key is any, you can follow the advice the Go context package gives for context keys: use an unexported key type so that no other package can collide with it.[9] Pair each key with a typed accessor:

type userKey struct{}

c.Set(userKey{}, user)                // in the middleware

func CurrentUser(c *gin.Context) (*User, bool) { // used by handlers
	v, ok := c.Get(userKey{})
	if !ok {
		return nil, false
	}
	u, ok := v.(*User)
	return u, ok
}

gin.Context versus the request context

*gin.Context implements Go's context.Context interface, but its Deadline, Done, Err and Value methods only delegate to c.Request.Context() when the engine's ContextWithFallback option is enabled; it is off by default.[3,4] For cancellation and deadlines, pass c.Request.Context() to databases and HTTP clients. To change the request context in middleware, replace the request: c.Request = c.Request.WithContext(ctx).

6. Authentication middleware

Authentication answers "who is calling?". The middleware extracts credentials, verifies them, stores the resulting identity on the context, and rejects the request with 401 Unauthorized if verification fails. RFC 9110 requires a 401 response to include a WWW-Authenticate header naming the scheme the client should use.[10] For bearer tokens (OAuth access tokens, JWTs, opaque session tokens), RFC 6750 defines the Authorization: Bearer <token> request format and the error="invalid_token" attribute for rejected tokens.[11] Authentication scheme names are case-insensitive, so bearer must be accepted too.[10]

auth.go

package main

import (
	"context"
	"crypto/subtle"
	"errors"
	"net/http"
	"strings"

	"github.com/gin-gonic/gin"
)

// User is the authenticated principal stored in the request context.
type User struct {
	ID    string
	Roles []string
}

// userKey is an unexported key type, so no other package can collide with it.
type userKey struct{}

// TokenVerifier turns a bearer token into a User (JWT, opaque token, session...).
type TokenVerifier interface {
	Verify(ctx context.Context, token string) (*User, error)
}

var ErrInvalidToken = errors.New("invalid token")

// StaticTokens is a toy verifier used in the examples and tests.
type StaticTokens map[string]*User

func (s StaticTokens) Verify(_ context.Context, token string) (*User, error) {
	for t, u := range s {
		if subtle.ConstantTimeCompare([]byte(t), []byte(token)) == 1 {
			return u, nil
		}
	}
	return nil, ErrInvalidToken
}

// Authenticate requires an "Authorization: Bearer <token>" header (RFC 6750).
func Authenticate(v TokenVerifier) gin.HandlerFunc {
	return func(c *gin.Context) {
		scheme, token, ok := strings.Cut(c.GetHeader("Authorization"), " ")
		if !ok || !strings.EqualFold(scheme, "Bearer") || token == "" {
			c.Header("WWW-Authenticate", `Bearer realm="api"`)
			c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "missing bearer token"})
			return
		}
		user, err := v.Verify(c.Request.Context(), token)
		if err != nil {
			c.Header("WWW-Authenticate", `Bearer realm="api", error="invalid_token"`)
			c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "invalid token"})
			return
		}
		c.Set(userKey{}, user)
		c.Next()
	}
}

// CurrentUser returns the user stored by Authenticate.
func CurrentUser(c *gin.Context) (*User, bool) {
	v, ok := c.Get(userKey{})
	if !ok {
		return nil, false
	}
	u, ok := v.(*User)
	return u, ok
}

Notes on the design:

  • Verification sits behind an interface, so the middleware does not care whether tokens are JWTs checked locally or opaque tokens looked up in a store. The toy StaticTokens verifier compares with crypto/subtle.ConstantTimeCompare, whose run time does not depend on where the inputs first differ, so response timing does not reveal how much of a guessed token was correct.[12]
  • Error messages say what is wrong with the request ("missing", "invalid") and never why a specific token failed. OWASP recommends generic authentication failure messages.[13]
  • The middleware passes c.Request.Context() to the verifier so a slow token store respects request cancellation.

For simple internal tools Gin ships gin.BasicAuth; see section 16.

7. Authorization middleware

Authorization answers "is this caller allowed to do this?". It always runs after authentication, and it fails with 403 Forbidden: RFC 9110 defines 403 as the server understanding the request but refusing to fulfil it; if credentials were supplied, the server considers them insufficient, and the client should not simply repeat the request with the same credentials.[10] The OWASP Authorization Cheat Sheet recommends denying by default and checking permissions on every request on the server side.[14]

authz.go

package main

import (
	"net/http"

	"github.com/gin-gonic/gin"
)

// RequireRole allows the request only if the user holds at least one of roles.
// It must run after Authenticate. Anything not explicitly allowed is denied.
func RequireRole(roles ...string) gin.HandlerFunc {
	allowed := make(map[string]struct{}, len(roles))
	for _, r := range roles {
		allowed[r] = struct{}{}
	}
	return func(c *gin.Context) {
		user, ok := CurrentUser(c)
		if !ok {
			// Misconfiguration: authorization ran without authentication.
			c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "unauthenticated"})
			return
		}
		for _, r := range user.Roles {
			if _, ok := allowed[r]; ok {
				c.Next()
				return
			}
		}
		c.AbortWithStatusJSON(http.StatusForbidden, gin.H{"error": "forbidden"})
	}
}

Typical use attaches it to a group nested inside an authenticated group:

authed := api.Group("", Authenticate(tokens))
admin := authed.Group("/admin", RequireRole("admin"))
admin.DELETE("/users/:id", deleteUser)

Middleware is for coarse checks. Role checks at the route level work well in middleware. Object-level checks, such as "may Bob read order 42?", need the loaded object and belong in the handler or service layer. Broken object-level authorization is the first item in the OWASP API Security Top 10 (2023).[15]

8. Logging middleware

Gin's built-in gin.Logger() writes one human-readable line per request to gin.DefaultWriter. gin.LoggerWithConfig accepts a LoggerConfig with Formatter, Output, SkipPaths, SkipQueryString and a Skip function.[6] SkipQueryString is new in v1.12.0.[16] For machine-readable logs, a small middleware on top of the standard library's log/slog package is usually a better fit; slog produces structured key–value records and has a JSON handler.[17]

logging.go

package main

import (
	"log/slog"
	"time"

	"github.com/gin-gonic/gin"
)

// StructuredLogger writes one slog record per request, after the handler ran.
func StructuredLogger(logger *slog.Logger) gin.HandlerFunc {
	return func(c *gin.Context) {
		start := time.Now()
		path := c.Request.URL.Path // capture before handlers can modify it

		c.Next() // everything below runs on the way back out

		status := c.Writer.Status()
		level := slog.LevelInfo
		switch {
		case status >= 500:
			level = slog.LevelError
		case status >= 400:
			level = slog.LevelWarn
		}
		attrs := []slog.Attr{
			slog.String("request_id", RequestIDFrom(c)),
			slog.String("method", c.Request.Method),
			slog.String("path", path),
			slog.String("route", c.FullPath()), // "/users/:id", low-cardinality
			slog.Int("status", status),
			slog.Int("bytes", c.Writer.Size()),
			slog.Duration("latency", time.Since(start)),
			slog.String("client_ip", c.ClientIP()),
		}
		if len(c.Errors) > 0 {
			attrs = append(attrs, slog.String("errors", c.Errors.String()))
		}
		logger.LogAttrs(c.Request.Context(), level, "http_request", attrs...)
	}
}
  • All interesting fields (status, size, errors) are only known after c.Next() returns, so the log call sits at the end.
  • c.FullPath() returns the matched route pattern, such as /users/:id, which is far better for dashboards than raw paths with IDs in them.[4]
  • LogAttrs is the allocation-efficient form of slog logging.[17]

Do not log secrets. OWASP lists access tokens, passwords, session identifiers and similar data among things that should not be recorded directly in logs, and recommends sanitising user-controlled data to prevent log injection.[18] This logger records the path without the query string and never logs headers. Gin's recovery middleware masks the Authorization header in its request dump for the same reason.[19]

9. Recovery middleware

A Go panic unwinds the stack of the goroutine that raised it, running deferred calls, and a deferred call to recover can stop it.[20,21] Gin's Recovery middleware defers a recover() around c.Next(), so a panic anywhere later in the chain is caught, logged with a stack trace, and turned into a 500 by the default handler c.AbortWithStatus(http.StatusInternalServerError).[19] Without it, net/http would still recover the panic for that connection and log it, but the client would get a closed connection instead of an HTTP response.[22]

Gin offers four constructors: Recovery(), RecoveryWithWriter(w), CustomRecovery(fn) and CustomRecoveryWithWriter(w, fn).[19] The custom variants let you shape the response. Two other details from the v1.12.0 source are worth knowing: if the panic value is a broken-pipe or connection-reset error, or http.ErrAbortHandler, Gin records the error and aborts without writing a status, because the client has gone; and request dumps mask the Authorization header.[19]

recovery.go

package main

import (
	"log/slog"
	"net/http"
	"runtime/debug"

	"github.com/gin-gonic/gin"
)

// JSONRecovery converts a panic into a JSON 500 and logs the stack once.
func JSONRecovery(logger *slog.Logger) gin.HandlerFunc {
	// A nil writer disables Gin's own panic log; we log through slog instead.
	return gin.CustomRecoveryWithWriter(nil, func(c *gin.Context, rec any) {
		logger.Error("panic recovered",
			slog.Any("panic", rec),
			slog.String("request_id", RequestIDFrom(c)),
			slog.String("stack", string(debug.Stack())),
		)
		if c.Writer.Written() {
			c.Abort() // too late to change the status; just stop the chain
			return
		}
		c.AbortWithStatusJSON(http.StatusInternalServerError, gin.H{
			"error":      "internal server error",
			"request_id": RequestIDFrom(c),
		})
	})
}

Recovery only covers its own goroutine. recover only stops a panic in the goroutine where it is deferred.[20] A panic in a goroutine started by a handler is not caught by Gin's recovery middleware and terminates the whole process. Any goroutine you start needs its own defer/recover.

10. CORS middleware

Browsers block a script on one origin from reading responses from another origin unless the server opts in through the CORS protocol defined in the WHATWG Fetch Standard.[23,24] For requests that are not "simple" (for example, those with an Authorization header, a JSON Content-Type, or methods such as DELETE), the browser first sends a preflight: an OPTIONS request carrying Origin, Access-Control-Request-Method and possibly Access-Control-Request-Headers. The actual request is sent only if the preflight response approves it. The preflight never includes credentials.[23]

The official package is github.com/gin-contrib/cors.[2]

import "github.com/gin-contrib/cors"

r.Use(cors.New(cors.Config{
	AllowOrigins:     []string{"https://app.example.com"},
	AllowMethods:     []string{"GET", "POST", "PUT", "DELETE"},
	AllowHeaders:     []string{"Authorization", "Content-Type", "X-Request-ID"},
	ExposeHeaders:    []string{"X-Request-ID"},
	AllowCredentials: true,
	MaxAge:           12 * time.Hour,
}))

What v1.7.9 actually does, from its source:[2]

  • Requests without an Origin header, and requests whose Origin equals http:// or https:// plus the request's Host, pass through untouched.
  • If the origin is not allowed, the middleware aborts with 403 Forbidden.
  • For an allowed OPTIONS request it writes the preflight headers and aborts with OptionsResponseStatusCode, which defaults to 204 No Content. The route's handler never runs.
  • When origins are listed explicitly it echoes the request's origin and sets Vary: Origin so shared caches keep per-origin copies.
  • cors.New validates the configuration and panics at start-up on conflicts, for example AllowAllOrigins together with AllowOrigins, or no origin rule at all.
  • cors.Default() allows all origins, with methods GET, POST, PUT, PATCH, DELETE, HEAD and OPTIONS, headers Origin, Content-Length and Content-Type, and a 12-hour max age.

Register CORS globally, before authentication. Two reasons. First, a preflight carries no Authorization header, so an authentication middleware placed before CORS rejects it with 401 and the browser reports a CORS failure. Second, a preflight is an OPTIONS request, and if you only registered GET and POST, Gin finds no route; group middleware never runs, and the response is a 404. The article's tests confirm this: with cors.Default() attached to a group, a preflight to a route in that group returned 404 with no CORS headers. Global middleware also runs for 404 responses (see section 2), so r.Use(cors.New(...)) handles preflights correctly.

Wildcards and credentials do not mix. With AllowAllOrigins: true the package sends Access-Control-Allow-Origin: *.[2] The Fetch Standard says that for a request whose credentials mode is "include", the CORS check fails if Access-Control-Allow-Origin is *.[23] If your front end sends cookies or uses credentials: "include", list origins explicitly. Never "fix" this by echoing every incoming origin with credentials enabled; that disables the same-origin protection for every site.

11. Rate limiting

Rate limiting protects an API from abuse and from accidental overload. OWASP lists missing limits on request rate and resource use as API4: Unrestricted Resource Consumption in the API Security Top 10.[25] The standard response is 429 Too Many Requests, defined in RFC 6585, which may include a Retry-After header telling the client how long to wait.[26] RFC 9110 defines Retry-After as either an HTTP date or a number of seconds.[10]

The Go team's golang.org/x/time/rate package implements a token bucket: a Limiter created with rate.NewLimiter(r, b) refills at r tokens per second up to a burst size of b, and offers Allow, Reserve and Wait.[27] The middleware below keeps one limiter per key and uses Reserve so it can compute an accurate Retry-After. Calling Cancel on the reservation returns the token, because the request is rejected rather than delayed.[27]

ratelimit.go

package main

import (
	"context"
	"math"
	"net/http"
	"strconv"
	"sync"
	"time"

	"github.com/gin-gonic/gin"
	"golang.org/x/time/rate"
)

// KeyedLimiter holds one token bucket per key (client IP, user ID, API key...).
type KeyedLimiter struct {
	mu       sync.Mutex
	visitors map[string]*visitor
	limit    rate.Limit // tokens added per second
	burst    int        // bucket size
}

type visitor struct {
	limiter  *rate.Limiter
	lastSeen time.Time
}

func NewKeyedLimiter(limit rate.Limit, burst int) *KeyedLimiter {
	return &KeyedLimiter{visitors: make(map[string]*visitor), limit: limit, burst: burst}
}

func (l *KeyedLimiter) get(key string) *rate.Limiter {
	l.mu.Lock()
	defer l.mu.Unlock()
	v, ok := l.visitors[key]
	if !ok {
		v = &visitor{limiter: rate.NewLimiter(l.limit, l.burst)}
		l.visitors[key] = v
	}
	v.lastSeen = time.Now()
	return v.limiter
}

// Cleanup evicts keys idle for longer than ttl until ctx is cancelled,
// so the map does not grow without bound.
func (l *KeyedLimiter) Cleanup(ctx context.Context, every, ttl time.Duration) {
	t := time.NewTicker(every)
	defer t.Stop()
	for {
		select {
		case <-ctx.Done():
			return
		case now := <-t.C:
			l.mu.Lock()
			for k, v := range l.visitors {
				if now.Sub(v.lastSeen) > ttl {
					delete(l.visitors, k)
				}
			}
			l.mu.Unlock()
		}
	}
}

// RateLimit rejects requests over the limit with 429 and a Retry-After header.
func RateLimit(l *KeyedLimiter, key func(*gin.Context) string) gin.HandlerFunc {
	return func(c *gin.Context) {
		res := l.get(key(c)).Reserve()
		if d := res.Delay(); d > 0 {
			res.Cancel() // we will not wait, so give the token back
			c.Header("Retry-After", strconv.Itoa(int(math.Ceil(d.Seconds()))))
			c.AbortWithStatusJSON(http.StatusTooManyRequests, gin.H{"error": "rate limit exceeded"})
			return
		}
		c.Next()
	}
}

// ByClientIP keys on c.ClientIP(); configure trusted proxies or it can be spoofed.
func ByClientIP(c *gin.Context) string { return c.ClientIP() }

With rate.Every(10*time.Second) and a burst of 2, the test suite sees 200, 200, 429 with Retry-After: 10 on the third request.

Configure trusted proxies before keying on IP. c.ClientIP() consults X-Forwarded-For and X-Real-IP when the direct peer is a trusted proxy, and by default a new Gin engine trusts every address (0.0.0.0/0 and ::/0).[3] With that default, any client can choose its own rate-limit key by sending a forged header. Call r.SetTrustedProxies(nil) when there is no proxy, list your load balancer's addresses when there is one, or set r.TrustedPlatform to a constant such as gin.PlatformCloudflare on a supported platform.[3]

Two limits of this design: the state lives in one process, so each replica of a horizontally scaled service enforces its own limit; and the per-key map needs eviction, which Cleanup provides. For a shared limit across replicas, back the counter with a shared store such as Redis. The IETF HTTPAPI working group is standardising RateLimit and RateLimit-Policy response headers for advertising quotas; at the time of writing the specification is still an Internet-Draft.[28]

12. Request ID middleware

A request ID ties together every log line, error report and downstream call made for one request. There is no IETF standard header for this; X-Request-ID is a widespread convention. For distributed tracing across services, the W3C Trace Context Recommendation standardises the traceparent and tracestate headers, and tracing libraries such as OpenTelemetry use it.[29]

requestid.go

package main

import (
	"crypto/rand"
	"regexp"

	"github.com/gin-gonic/gin"
)

const RequestIDHeader = "X-Request-ID"

type requestIDKey struct{}

// Accept a client-supplied ID only if it is short and harmless to log.
var validRequestID = regexp.MustCompile(`^[A-Za-z0-9._-]{8,64}$`)

// RequestID reuses a well-formed incoming X-Request-ID or generates one,
// stores it on the context and echoes it in the response.
func RequestID() gin.HandlerFunc {
	return func(c *gin.Context) {
		id := c.GetHeader(RequestIDHeader)
		if !validRequestID.MatchString(id) {
			id = rand.Text() // 26 random base32 characters (Go 1.24+)
		}
		c.Set(requestIDKey{}, id)
		c.Header(RequestIDHeader, id)
		c.Next()
	}
}

// RequestIDFrom returns the ID set by RequestID, or "" if it did not run.
func RequestIDFrom(c *gin.Context) string {
	id, _ := c.Get(requestIDKey{})
	s, _ := id.(string)
	return s
}
  • Register it first, so the logger, recovery and error handler can all include the ID.
  • An incoming ID is accepted only if it matches a strict pattern. Anything else, including values with newlines, is replaced. Accepting arbitrary client input and writing it into logs invites the log injection OWASP warns about.[18]
  • crypto/rand.Text, added in Go 1.24, returns a cryptographically random 26-character base32 string.[30,31]

The gin-contrib/requestid package offers the same idea ready-made: requestid.New() reuses the incoming X-Request-ID or generates a UUID, sets the response header, and exposes requestid.Get(c). Options include WithGenerator, WithCustomHeaderStrKey and WithHandler.[32] Note that v1.0.8 reuses any non-empty incoming value as-is, without validation.[32]

13. Timeout middleware

Timeouts in a Go web service exist at two levels, and you need both.

Connection level. http.Server has ReadHeaderTimeout, ReadTimeout, WriteTimeout and IdleTimeout. They protect the server from slow or idle clients and are set when the server is constructed, not in Gin.[22] The complete program sets all four.

Request level. A deadline on the work a handler does: database queries, outbound calls, computation. In Go this is a context.Context deadline.[9,33]

The middleware below adds a deadline to the request context. It is cooperative: Go has no way to stop another goroutine from the outside, so handlers must pass c.Request.Context() to anything that blocks, or select on Done().[9]

timeout.go

package main

import (
	"context"
	"errors"
	"net/http"
	"time"

	"github.com/gin-gonic/gin"
)

// Timeout gives the rest of the chain a deadline through the request context.
// It is cooperative: handlers must watch c.Request.Context().Done().
func Timeout(d time.Duration) gin.HandlerFunc {
	return func(c *gin.Context) {
		ctx, cancel := context.WithTimeout(c.Request.Context(), d)
		defer cancel()
		c.Request = c.Request.WithContext(ctx)

		c.Next()

		if errors.Is(ctx.Err(), context.DeadlineExceeded) && !c.Writer.Written() {
			c.AbortWithStatusJSON(http.StatusServiceUnavailable, gin.H{"error": "request timed out"})
		}
	}
}

// slowReport is a handler that honours cancellation.
func slowReport(c *gin.Context) {
	select {
	case <-time.After(3 * time.Second): // stand-in for a slow query
		c.JSON(http.StatusOK, gin.H{"report": "done"})
	case <-c.Request.Context().Done():
		_ = c.Error(c.Request.Context().Err()) // record it; Timeout writes the response
	}
}

Which status code? RFC 9110 defines 408 Request Timeout as the server not receiving a complete request in time, which describes a slow client rather than a slow handler.[10] The standard library's http.TimeoutHandler answers 503 Service Unavailable when its handler runs too long, and this middleware follows that precedent.[22]

The gin-contrib/timeout package

github.com/gin-contrib/timeout takes a different approach. timeout.New(timeout.WithTimeout(d), timeout.WithResponse(h)) swaps in a buffered response writer, runs the rest of the chain in a new goroutine, and writes the timeout response if the timer fires first. The default timeout is 5 seconds and the default response is 408 with the body "Request Timeout".[34] Buffering means a handler cannot leak a half-written response.

It still depends on the handler cooperating. In v1.2.3, after writing the timeout response the middleware waits for the handler goroutine to finish so it can safely touch the context.[34] The client only gets the response when the server handler returns. The article's tests measured this against a real httptest.Server with a 100 ms timeout: a handler that ignored the context and slept for 2 s made the client wait 2 s for its 408, while a handler that selected on c.Request.Context().Done() returned the 408 in about 100 ms. The package's README likewise tells long-running handlers to check c.Request.Context().Done().[34]

14. Security headers

A handful of response headers tell browsers to enable protections that are off by default. The OWASP HTTP Security Response Headers Cheat Sheet is the reference for which to send and with what values; its REST Security Cheat Sheet adds API-specific recommendations.[35,36]

security.go

package main

import "github.com/gin-gonic/gin"

type SecurityConfig struct {
	HSTS bool // enable only when the site is served exclusively over HTTPS
}

// SecurityHeaders sets defensive response headers suitable for a JSON API.
func SecurityHeaders(cfg SecurityConfig) gin.HandlerFunc {
	return func(c *gin.Context) {
		h := c.Writer.Header()
		h.Set("X-Content-Type-Options", "nosniff")
		h.Set("X-Frame-Options", "DENY")
		h.Set("Content-Security-Policy", "default-src 'none'; frame-ancestors 'none'")
		h.Set("Referrer-Policy", "no-referrer")
		h.Set("Cross-Origin-Opener-Policy", "same-origin")
		h.Set("Cache-Control", "no-store")
		if cfg.HSTS {
			h.Set("Strict-Transport-Security", "max-age=63072000; includeSubDomains")
		}
		c.Next()
	}
}
HeaderPurposeSource
X-Content-Type-Options: nosniffStops browsers from MIME-sniffing a response into a different type, such as treating JSON as script.[23,35]
X-Frame-Options: DENYPrevents the response from being framed, which defends against clickjacking. Defined in RFC 7034; CSP frame-ancestors is its modern replacement, so the two are sent together for older browsers.[37,38]
Content-Security-PolicyFor a JSON API, default-src 'none' means a response rendered as a document can load nothing; frame-ancestors 'none' forbids framing.[36,38]
Strict-Transport-SecurityMakes the browser use HTTPS for the host for max-age seconds. OWASP suggests two years (63072000). Browsers ignore it on plain-HTTP responses, so it only takes effect over TLS.[35,39]
Referrer-Policy: no-referrerStops URLs, which may contain IDs or tokens, leaking to other sites through the Referer header.[40]
Cross-Origin-Opener-Policy: same-originIsolates the browsing context from cross-origin windows.[35]
Cache-Control: no-storeKeeps sensitive API responses out of shared and browser caches. Relax it on endpoints that are meant to be cached.[36,41]

Two headers are deliberately absent. X-XSS-Protection is deprecated, and OWASP recommends not setting it or setting it to 0.[35] Access-Control-* headers belong to the CORS middleware, not here.

Set headers before the body is written. HTTP headers are sent with the status line, so a header set after the handler has written its body is silently lost. This middleware sets everything before c.Next(). Exercise 3 shows what to do when a header's value is only known later.

15. Middleware error handling

Gin gives every request an error list, c.Errors. c.Error(err) appends to it and returns a *gin.Error; errors that are not already a *gin.Error are given the type ErrorTypePrivate.[4] The available types are ErrorTypePrivate, ErrorTypePublic, ErrorTypeBind, ErrorTypeRender and ErrorTypeAny, and the list has helpers such as Last(), ByType(), Errors() and JSON().[42] Gin's own gin.ErrorLogger() middleware calls c.Next() and renders c.Errors as JSON if any were recorded.[6]

That list lets you separate detecting an error from rendering it. Handlers call c.Error(err) and return; one middleware decides the status code and body for the whole API. The format below is the "problem details" object from RFC 9457, served as application/problem+json, with type, title, status and detail members plus a request_id extension member. RFC 9457 allows extension members and defines about:blank as the default type.[43]

errors.go

package main

import (
	"errors"
	"log/slog"
	"net/http"

	"github.com/gin-gonic/gin"
)

// APIError is an error that knows how it should be shown to clients.
type APIError struct {
	Status int
	Title  string
	Detail string
}

func (e *APIError) Error() string { return e.Title + ": " + e.Detail }

var ErrNotFound = &APIError{Status: http.StatusNotFound, Title: "Not Found", Detail: "resource does not exist"}

// ErrorHandler turns errors recorded with c.Error into one RFC 9457
// "problem details" response. Handlers just call c.Error(err) and return.
func ErrorHandler(logger *slog.Logger) gin.HandlerFunc {
	return func(c *gin.Context) {
		c.Next()

		if len(c.Errors) == 0 || c.Writer.Written() {
			return // nothing to do, or a response was already sent
		}
		err := c.Errors.Last().Err

		var apiErr *APIError
		if !errors.As(err, &apiErr) {
			// Unknown error: log the details, show the client nothing internal.
			logger.Error("unhandled error", slog.String("request_id", RequestIDFrom(c)), slog.Any("err", err))
			apiErr = &APIError{Status: http.StatusInternalServerError, Title: "Internal Server Error"}
		}
		c.Header("Content-Type", "application/problem+json")
		c.JSON(apiErr.Status, gin.H{
			"type":       "about:blank",
			"title":      apiErr.Title,
			"status":     apiErr.Status,
			"detail":     apiErr.Detail,
			"request_id": RequestIDFrom(c),
		})
	}
}

A handler then reads simply:

authed.GET("/items/:id", func(c *gin.Context) {
	item, err := store.Find(c.Request.Context(), c.Param("id"))
	if err != nil {
		_ = c.Error(err) // ErrorHandler chooses the response
		return
	}
	c.JSON(http.StatusOK, item)
})

For a missing item, the test suite receives 404 with Content-Type: application/problem+json and the body {"detail":"resource does not exist","request_id":"…","status":404,"title":"Not Found","type":"about:blank"}.

Rules that keep this robust:

  • Check c.Writer.Written() before rendering. If a handler or an aborting middleware already responded, writing again would append a second body.
  • Never send internal error text to clients. Unknown errors become a generic 500, and the details go to the log with the request ID. OWASP's Error Handling Cheat Sheet recommends exactly this split.[44]
  • Place it inside recovery and logging so its responses are logged and a panic in the error handler is still recovered.
  • Middleware should report errors the same way. A middleware that fails, for example when it cannot reach the token store, can call c.Error(err) and c.Abort() without writing, and let the error handler render the response. Choose one convention per application.

17. Putting it together

The program below wires every middleware from this article into one router. The comments explain each position in the chain. Together with the files above it forms a complete, runnable module.

main.go

package main

import (
	"context"
	"log"
	"log/slog"
	"net/http"
	"os"
	"time"

	"github.com/gin-contrib/cors"
	"github.com/gin-contrib/gzip"
	"github.com/gin-gonic/gin"
	"golang.org/x/time/rate"
)

func newRouter(logger *slog.Logger, tokens TokenVerifier, limiter *KeyedLimiter) *gin.Engine {
	r := gin.New()                                   // no default middleware; we choose the stack explicitly
	if err := r.SetTrustedProxies(nil); err != nil { // trust no proxy headers
		panic(err)
	}

	// Global middleware: runs for every request, including 404/405.
	r.Use(
		RequestID(),              // 1. first, so every later log line has an ID
		StructuredLogger(logger), // 2. outermost timer; sees the final status
		JSONRecovery(logger),     // 3. turns panics below it into a 500
		SecurityHeaders(SecurityConfig{HSTS: false}),
		cors.New(cors.Config{ // before auth, so preflights are not rejected
			AllowOrigins:     []string{"https://app.example.com"},
			AllowMethods:     []string{"GET", "POST", "PUT", "DELETE"},
			AllowHeaders:     []string{"Authorization", "Content-Type", RequestIDHeader},
			ExposeHeaders:    []string{RequestIDHeader},
			AllowCredentials: true,
			MaxAge:           12 * time.Hour,
		}),
		gzip.Gzip(gzip.DefaultCompression),
		ErrorHandler(logger),
	)

	// Group middleware: everything under /api/v1 is rate limited.
	api := r.Group("/api/v1", RateLimit(limiter, ByClientIP))
	api.GET("/health", func(c *gin.Context) { c.JSON(http.StatusOK, gin.H{"status": "ok"}) })

	// Route-specific middleware: only this route gets a deadline.
	api.GET("/reports/slow", Timeout(2*time.Second), slowReport)

	authed := api.Group("", Authenticate(tokens))
	authed.GET("/me", func(c *gin.Context) {
		u, _ := CurrentUser(c)
		c.JSON(http.StatusOK, gin.H{"id": u.ID, "roles": u.Roles})
	})
	authed.GET("/items/:id", func(c *gin.Context) {
		_ = c.Error(ErrNotFound) // ErrorHandler renders it
	})

	admin := authed.Group("/admin", RequireRole("admin"))
	admin.DELETE("/users/:id", func(c *gin.Context) { c.Status(http.StatusNoContent) })
	admin.GET("/panic", func(c *gin.Context) { panic("boom") })

	return r
}

func main() {
	logger := slog.New(slog.NewJSONHandler(os.Stdout, nil))
	limiter := NewKeyedLimiter(rate.Limit(5), 10) // 5 req/s, bursts of 10
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()
	go limiter.Cleanup(ctx, time.Minute, 3*time.Minute)

	tokens := StaticTokens{
		"alice-token": {ID: "alice", Roles: []string{"admin"}},
		"bob-token":   {ID: "bob", Roles: []string{"viewer"}},
	}

	srv := &http.Server{
		Addr:              ":8080",
		Handler:           newRouter(logger, tokens, limiter),
		ReadHeaderTimeout: 5 * time.Second,
		ReadTimeout:       10 * time.Second,
		WriteTimeout:      15 * time.Second,
		IdleTimeout:       60 * time.Second,
	}
	log.Fatal(srv.ListenAndServe())
}

Middleware is plain Go, so the standard net/http/httptest package is all you need: build a small engine, serve a request into an httptest.ResponseRecorder, and assert on the result.[48] gin.SetMode(gin.TestMode) silences debug output, and gin.CreateTestContext gives you a bare context for calling a middleware function directly.[49]

func TestRateLimit(t *testing.T) {
	gin.SetMode(gin.TestMode)

Exercise 3: An X-Response-Time header

Write middleware that adds X-Response-Time: <microseconds>us to every response. Why does this obvious version not work against a real server?

func ResponseTime() gin.HandlerFunc {
	return func(c *gin.Context) {
		start := time.Now()
		c.Next()
		c.Header("X-Response-Time", fmt.Sprint(time.Since(start).Microseconds(), "us"))
	}
}
Solution

By the time c.Next() returns, the handler has written its status and body, so the headers have already gone to the client. The late header is dropped. The fix is to set the header at the last possible moment, just before the status line is written, by wrapping gin.ResponseWriter:

// timingWriter stamps the header just before the status line is sent.
// Gin's writer only records the status in WriteHeader and actually sends it
// from WriteHeaderNow, which Write and WriteString call, so all four paths
// must be covered.
type timingWriter struct {
	gin.ResponseWriter
	start   time.Time
	stamped bool
}

func (w *timingWriter) stamp() {
	if !w.stamped && !w.Written() {
		w.stamped = true
		w.Header().Set("X-Response-Time", strconv.FormatInt(time.Since(w.start).Microseconds(), 10)+"us")
	}
}

func (w *timingWriter) WriteHeader(code int) { w.stamp(); w.ResponseWriter.WriteHeader(code) }
func (w *timingWriter) WriteHeaderNow()      { w.stamp(); w.ResponseWriter.WriteHeaderNow() }
func (w *timingWriter) Write(b []byte) (int, error) {
	w.stamp()
	return w.ResponseWriter.Write(b)
}
func (w *timingWriter) WriteString(s string) (int, error) {
	w.stamp()
	return w.ResponseWriter.WriteString(s)
}

func ResponseTime() gin.HandlerFunc {
	return func(c *gin.Context) {
		c.Writer = &timingWriter{ResponseWriter: c.Writer, start: time.Now()}
		c.Next()
	}
}

Embedding gin.ResponseWriter keeps every other method. Overriding WriteHeader alone is not enough: in Gin's writer, WriteHeader only records the status, and the status line is actually sent from WriteHeaderNow, which Write calls on the first body write.[50] A handler that calls c.Writer.Write directly would bypass a WriteHeader-only wrapper, so the solution stamps the header on all four paths. The tests check it against a real server for c.JSON, c.AbortWithStatus and a raw c.Writer.Write.

			return
		}
		got := []byte(c.GetHeader("X-API-Key"))
		match := 0
		for _, k := range valid {
			match |= subtle.ConstantTimeCompare(got, []byte(k)) // check all keys
		}
		if len(got) == 0 || match != 1 {
			c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "invalid API key"})
			return
		}
		c.Next()
	}
}

Matching on c.FullPath() (the route pattern) rather than the raw URL path avoids bypasses through alternate spellings of the same path. The loop compares against every key instead of returning at the first match, so timing does not reveal which key matched.

Exercise 5: Limit request body size

Write middleware that rejects bodies larger than n bytes with 413 Content Too Large, including chunked bodies with no Content-Length.

Solution 
func MaxBodyBytes(n int64) gin.HandlerFunc {
	return func(c *gin.Context) {
		if c.Request.ContentLength > n {
			c.AbortWithStatusJSON(http.StatusRequestEntityTooLarge, gin.H{"error": "body too large"})
			return
		}
		c.Request.Body = http.MaxBytesReader(c.Writer, c.Request.Body, n)
		c.Next()
	}
}

// Handlers must still check for *http.MaxBytesError when reading the body.
func isTooLarge(err error) bool {
	var mbe *http.MaxBytesError
	return errors.As(err, &mbe)
}

A declared Content-Length can be checked immediately. For everything else, http.MaxBytesReader makes reads past the limit fail with *http.MaxBytesError; it also tells the server to close the connection.[22] The middleware cannot know when the handler will read, so the handler (or a binding helper) must map that error to 413. RFC 9110 names status 413 "Content Too Large".[10]

Exercise 6: Fix the ordering

A single-page app on https://app.example.com calls this API with an Authorization header. Every call fails in the browser with a CORS error, yet curl with the same token works. Why? Fix it.

r := gin.New()
api := r.Group("/api")
api.Use(Authenticate(tokens))
api.Use(cors.New(cors.Config{AllowOrigins: []string{"https://app.example.com"},
	AllowHeaders: []string{"Authorization", "Content-Type"}}))
api.GET("/me", me)
Solution

Two problems. The Authorization header makes the browser send a preflight OPTIONS request first, and preflights carry no credentials.[23] No OPTIONS route exists, so Gin returns 404 and the group middleware never runs. Even if an OPTIONS route existed, Authenticate runs first and answers 401. Either way the preflight fails, so the browser never sends the real request. curl does not do preflights. Fix: register CORS globally, before authentication.

r := gin.New()
r.Use(cors.New(cors.Config{
	AllowOrigins: []string{"https://app.example.com"},
	AllowHeaders: []string{"Authorization", "Content-Type"},
}))
api := r.Group("/api", Authenticate(tokens))
api.GET("/me", me)

Exercise 7: Require all permissions

RequireRole allows a request if the user has any listed role. Write RequireAll(perms ...string) that requires every listed permission and reports the first missing one.

Solution 
func RequireAll(perms ...string) gin.HandlerFunc {
	return func(c *gin.Context) {
		u, ok := CurrentUser(c)
		if !ok {
			c.AbortWithStatus(http.StatusUnauthorized)
			return
		}
		have := make(map[string]bool, len(u.Roles))
		for _, r := range u.Roles {
			have[r] = true
		}
		for _, p := range perms {
			if !have[p] {
				c.AbortWithStatusJSON(http.StatusForbidden, gin.H{"error": "missing permission", "permission": p})
				return
			}
		}
		c.Next()
	}
}

Exercise 8: Per-user rate limits

Write a key function that rate-limits authenticated users by user ID and everyone else by IP. Where must the middleware go, and should you also keep the IP-based limiter?

Solution 
func ByUserOrIP(c *gin.Context) string {
	if u, ok := CurrentUser(c); ok {
		return "user:" + u.ID
	}
	return "ip:" + c.ClientIP()
}

It must run after Authenticate, otherwise CurrentUser finds nothing. Keep the IP limiter before authentication as well: it is the only thing throttling requests with bad tokens, which is where credential-stuffing traffic shows up.[25] The two limiters use separate KeyedLimiter instances.

api := r.Group("/api", RateLimit(ipLimiter, ByClientIP))
authed := api.Group("", Authenticate(tokens), RateLimit(userLimiter, ByUserOrIP))

Exercise 9: Test the security headers

Write a table-driven test proving that SecurityHeaders(SecurityConfig{HSTS: true}) sets nosniff, DENY and the HSTS value.

func TestSecurityHeadersSolution(t *testing.T) {
	r := gin.New()

		"Strict-Transport-Security": "max-age=63072000; includeSubDomains",

		}
	}
}

Exercise 10: Explain the slow timeout

A route uses timeout.New(timeout.WithTimeout(100*time.Millisecond)) from gin-contrib. The handler calls time.Sleep(2*time.Second). Clients receive 408, but only after about two seconds. Why, and what is the fix?

Solution

Go cannot kill a goroutine from outside. In v1.2.3 the middleware writes the timeout response and then waits for the handler goroutine to finish before returning, to avoid a data race on the context.[34] The client receives the response when the server handler returns. The fix is to make the handler cooperative: replace the sleep with a select on time.After and c.Request.Context().Done(), and pass c.Request.Context() to any database or HTTP calls. With that change, the measured response time dropped to about 100 ms.
