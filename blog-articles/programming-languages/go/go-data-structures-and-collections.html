Data Structures and Collections in Go

A technical article with runnable examples, exercises and solutions · Examples verified with Go 1.24 (go build, gofmt, go vet, -race where concurrent) · References in Vancouver style

Abstract. Go builds its data structures from a small set of composite types defined by the language itself: fixed-length arrays, slices that window onto arrays, hash maps, structs, and pointers. Understanding them means understanding what each value is in memory. An array is its elements; a slice is a three-word descriptor that shares an underlying array; a map value refers to a runtime hash table; a struct is its fields laid out together; a pointer is an address. This article describes each type with reference to the language specification, explains length and capacity, slicing, append and copy, aliasing and memory retention, map initialisation, iteration and concurrency, struct fields, nesting, anonymous structs, tags and embedding, and pointer declaration, dereferencing, nil pointers and pointer receivers. It covers the generic slices and maps packages (Go 1.21 and later), iterator helpers (Go 1.23) and the Swiss-table map implementation and omitzero tag option (Go 1.24), and ends with exercises and worked solutions.

1. Overview

Go has no built-in list, set or tree types. Instead the specification defines a handful of composite types (array, slice, map, struct and pointer, alongside function, interface and channel types) from which programs and the standard library build everything else [1]. The authors of The Go Programming Language describe arrays and structs as aggregate types whose values are concatenations of other values in memory, and slices and maps as dynamic data structures [2]. The distinction matters every time a value is assigned or passed, because, as the Go FAQ puts it, "everything in Go is passed by value. That is, a function always gets a copy of the thing being passed" [3]. Copying an array or a struct copies its contents; copying a slice or a map copies only a small descriptor or reference, so both copies see the same elements [4].

2. Arrays

"An array is a numbered sequence of elements of a single type, called the element type." Its length "is part of the array's type; it must evaluate to a non-negative constant" [1]. So [3]int and [4]int are different, mutually unassignable types, and an array's size can never change after it is declared [1,4]. Elements are indexed from 0 to len(a)-1; a constant index outside that range is a compile-time error, and a variable one causes a run-time panic [1].

Array literals can give every element, let the compiler count them with [...], or name specific indices, leaving the rest at their zero value [1]. Effective Go summarises the semantics that set Go apart from C: "Arrays are values. Assigning one array to another copies all the elements," and "if you pass an array to a function, it will receive a copy of the array, not a pointer to it" [4]. Gerrand's introduction to slices makes the same point: "An array variable denotes the entire array; it is not a pointer to the first array element (as would be the case in C)" [6].

Two arrays of the same type are equal if their corresponding elements are equal, so arrays with comparable elements can be used as map keys, which is a compact way to key by a fixed-size tuple [1]. A pointer to an array can be indexed, sliced and passed to len directly: p[i] is shorthand for (*p)[i] [1].

ex01_arrays/main.go 
package main

import "fmt"

func double(a [3]int) [3]int { // a is a copy of the caller's array
	for i := range a {
		a[i] *= 2
	}
	return a
}

func main() {
	var zero [3]int             // zero value: [0 0 0]
	primes := [...]int{2, 3, 5} // length inferred from the literal
	sparse := [5]string{1: "one", 4: "four"}

	fmt.Println(zero, primes, len(primes))
	fmt.Printf("%q\n", sparse)

	// Arrays are values: assignment and argument passing copy every element.
	copyOf := primes
	copyOf[0] = 99
	fmt.Println(primes, copyOf, double(primes), primes)

	// Arrays of comparable elements are comparable, so they can be map keys.
	fmt.Println(primes == [3]int{2, 3, 5})
	grid := map[[2]int]string{{0, 0}: "origin", {1, 2}: "point"}
	fmt.Println(grid[[2]int{1, 2}])

	// The length is part of the type: [3]int and [4]int are distinct types.
	fmt.Printf("%T vs %T\n", primes, [4]int{})

	// A pointer to an array can be indexed and ranged over directly.
	p := &primes
	p[1] = 7
	fmt.Println(*p, len(p))
}

Because the length is fixed and copies are made on assignment, arrays are used directly mostly for small fixed-size data (coordinates, hashes such as [32]byte, lookup tables) and, more often, as the hidden storage behind slices [6,2].

3. Slices

Slices are Go's general-purpose sequence type. Effective Go says that "slices wrap arrays to give a more general, powerful, and convenient interface to sequences of data" and that "most array programming in Go is done with slices rather than simple arrays" [4].

3.1 Slice internals

The specification defines a slice as "a descriptor for a contiguous segment of an underlying array" which "provides access to a numbered sequence of elements from that array" [1]. In the gc runtime the descriptor (often called the slice header) is a three-word structure: a pointer to the first element the slice can see, the length, and the capacity [7,6]:

// From src/runtime/slice.go (Go 1.24).
type slice struct {
	array unsafe.Pointer
	len   int
	cap   int
}

A slice value is this header, not the elements. Pike stresses that "even though the slice header is passed by value, the header includes a pointer to elements of an array", so a function that receives a slice can modify its elements but cannot change the caller's length or capacity [8]. That is why append returns a new slice that the caller must store [8,1].

3.2 Length and capacity

The length is the number of elements the slice currently exposes, reported by len. The capacity, reported by cap, "is the sum of the length of the slice and the length of the array beyond the slice" [1]. A slice can be resliced up to its capacity, so elements beyond the length but within the capacity are still reachable [1,6].

The zero value of a slice type is nil: no array, length 0, capacity 0 [1]. A nil slice can be ranged over, passed to len, and appended to; Pike notes that "a nil slice is functionally equivalent to a zero-length slice, even though it points to nothing" [8]. The Go code review guidelines therefore prefer var t []string over t := []string{} when declaring an empty slice [9]. The two differ only when compared with nil and in a few encoders: encoding/json, for instance, encodes a nil slice as null and an empty one as [] [10].

make([]T, length, capacity) "always allocates a new, hidden array to which the returned slice value refers" [1]. The example below shows a slice sharing its array with the original, a function writing through a copy of the header, and an append inside a function that changes the shared array but not the caller's length.

ex02_header/main.go 
package main

import "fmt"

func setFirst(s []int, v int) { s[0] = v } // modifies the shared array

func appendOne(s []int) { s = append(s, 1) } // only the local header changes

func main() {
	arr := [6]int{0, 1, 2, 3, 4, 5}
	s := arr[1:4] // pointer to arr[1], len 3, cap 5

	fmt.Println(s, len(s), cap(s))

	s[0] = 100 // writes through to arr[1]
	fmt.Println(arr)

	setFirst(s, 200)
	fmt.Println(arr[1], s[0])

	appendOne(s) // writes arr[4] but the caller's len is unchanged
	fmt.Println(s, len(s), arr)

	// Every element of the backing array, within capacity, is reachable.
	s = s[:cap(s)]
	fmt.Println(s)

	var nilSlice []int
	empty := []int{}
	fmt.Println(nilSlice == nil, empty == nil, len(nilSlice), len(empty))
}

After appendOne(s) the caller still sees three elements, yet arr[4] has become 1: the callee's append fitted within the capacity and wrote into the shared array, then discarded its new header [1,8]. Reslicing to s[:cap(s)] reveals the written element.

3.3 Slicing operations

A simple slice expression a[low:high] selects the half-open range from low up to but not including high; the result has length high - low. Either index may be omitted, defaulting to 0 and to the length of the operand [1]. The operand can be an array (which must be addressable), a pointer to an array, a slice, or a string. For arrays and strings the indices must satisfy 0 <= low <= high <= len(a); "for slices, the upper index bound is the slice capacity cap(a) rather than the length" [1]. Slicing a string yields a string and counts bytes, not characters [1].

"Slicing does not copy the slice's data. It creates a new slice value that points to the original array" [6]. The full slice expression a[low:high:max] produces the same elements but "controls the resulting slice's capacity by setting it to max - low" [1]. Capping capacity this way means the next append must allocate, so it cannot overwrite elements that belong to someone else. Full slice expressions are not allowed on strings [1].

ex03_slicing/main.go 
package main

import "fmt"

func main() {
	a := [8]int{0, 1, 2, 3, 4, 5, 6, 7}

	fmt.Println(a[2:5], a[:3], a[5:], a[:]) // half-open ranges [low, high)

	s := a[2:5]
	fmt.Println(len(s), cap(s)) // cap runs to the end of the array

	// Reslicing may extend up to cap, beyond len.
	t := s[1:5]
	fmt.Println(t, len(t), cap(t))

	// A full slice expression a[low:high:max] limits the capacity.
	u := a[2:5:5]
	fmt.Println(u, len(u), cap(u))
	u = append(u, 99) // cap exceeded: new array, a is untouched
	fmt.Println(u, a)

	v := a[2:5]
	v = append(v, 99) // spare capacity: overwrites a[5]
	fmt.Println(v, a)

	// Slicing a string yields a string (bytes, not runes).
	str := "héllo"
	fmt.Println(str[0:3], len(str))

	defer func() { fmt.Println("recovered:", recover()) }()
	i := 10
	_ = s[:i] // out of range at run time
}

3.4 Append and copy

The built-in append(s, x...) "appends zero or more values x to a slice s and returns the resulting slice of the same type as s." If the capacity of s is not large enough, "append allocates a new, sufficiently large underlying array that fits both the existing slice elements and the additional values. Otherwise, append re-uses the underlying array" [1]. A whole slice is appended with the ... suffix, and, as a special case, a string can be appended to a []byte [1]. Pike's rule of thumb follows directly: "since the slice header is always updated by a call to append, you need to save the returned slice after the call" [8].

How much the capacity grows is not specified by the language. In Go 1.24 the runtime doubles the capacity of small slices and, above a threshold of 256 elements, switches to growth of roughly 1.25 times plus a constant, "a smooth-ish transition between the two"; the requested size is then rounded up to an allocator size class [7]. Programs should not depend on exact capacities. When the final size is known, make([]T, 0, n) or slices.Grow allocates once [1,11].

copy(dst, src) "copies slice elements from a source src to a destination dst and returns the number of elements copied. ... The number of elements copied is the minimum of len(src) and len(dst)" [1]. It copies by length, never by capacity, and it handles overlapping source and destination correctly, which makes it the standard tool for shifting elements within one slice [1,6].

ex04_append/main.go 
package main

import "fmt"

func main() {
	// append grows the backing array when capacity runs out.
	var s []int
	prevCap := -1
	for i := range 20 {
		s = append(s, i)
		if cap(s) != prevCap {
			fmt.Printf("len=%-2d cap=%d\n", len(s), cap(s))
			prevCap = cap(s)
		}
	}

	// Appending a slice to a slice needs the ... suffix.
	a := []string{"x", "y"}
	b := []string{"z"}
	a = append(a, b...)
	fmt.Println(a)

	// Special case: append a string to a []byte.
	bs := append([]byte("go"), "pher"...)
	fmt.Println(string(bs))

	// copy copies min(len(dst), len(src)) elements and returns that count.
	dst := make([]int, 3)
	n := copy(dst, []int{1, 2, 3, 4, 5})
	fmt.Println(n, dst)

	// copy handles overlapping slices: shift left by one.
	nums := []int{1, 2, 3, 4, 5}
	copy(nums, nums[1:])
	fmt.Println(nums)

	// The aliasing trap: two appends to the same base share memory.
	base := make([]int, 3, 10)
	x := append(base, 1)
	y := append(base, 2) // overwrites x[3]
	fmt.Println(x, y)

	// Pre-sizing avoids repeated growth.
	out := make([]int, 0, 100)
	for i := range 100 {
		out = append(out, i*i)
	}
	fmt.Println(len(out), cap(out))
}

The safe pattern is either to write s = append(s, …) and use only the result, or to cap the base with a full slice expression (or slices.Clip) before handing it out [1,11].

3.5 Slice backing arrays

"A slice, once initialized, is always associated with an underlying array that holds its elements. A slice therefore shares storage with its array and with other slices of the same array; by contrast, distinct arrays always represent distinct storage" [1]. Effective Go puts it as "if you assign one slice to another, both refer to the same array" [4]. Every slice expression, assignment, function argument and in-place append creates another view of the same array, and a write through any view is visible through all of them. Only an append that exceeds capacity, make, a composite literal, or an explicit copy (copy, slices.Clone, append([]T(nil), s...)) produces new storage [1,11].

Two consequences are worth stating explicitly:

  • Because an append may or may not reallocate, after t := append(s, v) you cannot tell without checking capacity whether t and s still share elements. Code that keeps both must treat them as possibly aliased [8].
  • A slice field in a struct, or a slice stored in a map, is still only a header. Copying the struct or reading the map value copies the header, not the elements [4,2].

3.6 Slice memory behaviour

Because a slice holds a pointer into its array, the garbage collector keeps the entire array alive while any slice of it is reachable. Gerrand calls this a "possible gotcha": a small slice of a large buffer pins the whole buffer, and "the full array will be kept in memory until it is no longer referenced." The fix is to copy the interesting data to a new slice [6]. slices.Clone returns "a copy of the slice" (shallow, and possibly with "additional unused capacity") [11].

A related leak concerns slices of pointers. Removing elements by reslicing leaves the old pointers in the array beyond the new length, where they still keep their targets alive. Since Go 1.22, "functions that shrink the size of a slice (Delete, DeleteFunc, Compact, CompactFunc, and Replace) now zero the elements between the new length and the old length" [12], and the built-in clear (Go 1.21) zeroes a slice's elements by hand [13,1]. slices.Clip "removes unused capacity from the slice, returning s[:len(s):len(s)]" and slices.Grow guarantees room for another n elements without further allocation [11].

ex05_memory/main.go 
package main

import (
	"fmt"
	"slices"
)

type Item struct{ Name string }

// header returns the first n bytes of a big buffer without pinning it.
func header(buf []byte, n int) []byte {
	return slices.Clone(buf[:n]) // or: append([]byte(nil), buf[:n]...)
}

func main() {
	big := make([]byte, 1<<20) // 1 MiB
	copy(big, "GOPHER")

	pinned := big[:6]       // keeps the whole 1 MiB array reachable
	freed := header(big, 6) // independent 6-byte array
	fmt.Println(string(pinned), cap(pinned), string(freed), cap(freed))

	// slices.Delete zeroes the vacated tail (Go 1.22+), so pointers in it
	// no longer keep their targets alive.
	items := []*Item{{"a"}, {"b"}, {"c"}, {"d"}}
	full := items[:cap(items)]
	items = slices.Delete(items, 1, 3)
	fmt.Println(len(items), items[0].Name, items[1].Name, full[2] == nil, full[3] == nil)

	// slices.Clip drops unused capacity so later appends cannot clobber it.
	s := make([]int, 2, 8)
	c := slices.Clip(s)
	fmt.Println(cap(s), cap(c))

	// slices.Grow reserves room for n more elements in a single allocation.
	g := slices.Grow([]int{1}, 50)
	fmt.Println(len(g), cap(g) >= 51)

	// Shrinking with s[:0] keeps the allocation for reuse.
	reuse := []int{1, 2, 3}
	reuse = reuse[:0]
	fmt.Println(len(reuse), cap(reuse))
}

The clone of six bytes reports a capacity of 8 rather than 6, illustrating the documented "additional unused capacity": allocations are rounded up to a size class [11,7]. Whether a slice's array lives on the stack or the heap is decided by the compiler's escape analysis and does not affect correctness: "from a correctness standpoint, you don't need to know" [3].

4. Maps

"A map is an unordered group of elements of one type, called the element type, indexed by a set of unique keys of another type, called the key type" [1]. The key type must support == and !=, "thus the key type must not be a function, map, or slice"; the FAQ explains that "map lookup requires an equality operator, which slices do not implement" [1,3]. Structs and arrays of comparable types are valid keys, and interface-typed keys are allowed but panic at run time if a dynamic key value is not comparable [1,14]. Like slices, "maps hold references to an underlying data structure. If you pass a map to a function that changes the contents of the map, the changes will be visible in the caller" [4].

The specification leaves the implementation open. Since Go 1.24 the gc toolchain uses "a completely new implementation of the built-in map type, based on the Swiss Table design" [15]; the release notes credit it, together with other changes, with a 2–3% average CPU improvement and note that it can be disabled with GOEXPERIMENT=noswissmap at build time [16]. Programs see no semantic difference.

4.1 Map initialisation

There are three ways to obtain a map:

  1. The zero value. "The value of an uninitialized map is nil" [1]. "A nil map is equivalent to an empty map except that no elements may be added": reads return the zero value, len is 0, and ranging over it performs no iterations, but "assigning to an element of a nil map causes a run-time panic" [1]. Gerrand's advice is blunt: "don't do that" [14].
  2. make, with an optional capacity hint: make(map[string]int, 100). "The initial capacity does not bound its size: maps grow to accommodate the number of items stored in them" [1]. The hint only lets the runtime pre-size the table.
  3. A composite literal, map[K]V{k1: v1, …}, where element types may be elided for nested composite values [1].
ex06_mapinit/main.go 
package main

import "fmt"

func main() {
	// 1. Zero value: a nil map. Reads work; writes panic.
	var nilMap map[string]int
	fmt.Println(nilMap == nil, len(nilMap), nilMap["missing"])

	// 2. make, optionally with a size hint.
	ages := make(map[string]int)
	sized := make(map[string]int, 1000) // hint only; len is still 0
	fmt.Println(len(ages), len(sized))

	// 3. A composite literal.
	capitals := map[string]string{
		"France": "Paris",
		"Japan":  "Tokyo",
	}
	fmt.Println(len(capitals), capitals["Japan"])

	// Element types can be elided in literals of composite values.
	points := map[string][]int{"a": {1, 2}, "b": {3}}
	fmt.Println(points)

	// Writing to a nil map is a run-time panic.
	defer func() { fmt.Println("recovered:", recover()) }()
	nilMap["boom"] = 1
}

A nil map is useful as a read-only empty map, for example as the zero value of a struct field that is only read. Any type that will be written should initialise the map in a constructor or lazily on first write.

4.2 Key-value operations

m[k] = v inserts or updates an entry. A lookup m[k] of an absent key yields "the zero value for the element type" [1]. To tell "absent" from "present with value zero" use the comma-ok form v, ok := m[k], where ok "is true if the key x is present in the map, and false otherwise" [1,4]. delete(m, k) removes an entry, and "if the map m is nil or the element m[k] does not exist, delete is a no-op" [1]. len(m) gives the number of entries, and clear(m) (Go 1.21) "deletes all entries, resulting in an empty map" [1,13].

The maps package, added in Go 1.21, "provides several common operations on maps, using generic functions that work with maps of any key or element type" [13]. maps.Clone makes a "shallow clone: the new keys and values are set using ordinary assignment" [17]. Go 1.23 added iterator functions such as maps.Keys, maps.Values, maps.All and maps.Collect, and slices.Sorted, which "collects values from an iterator into a new slice, and then sorts the slice" [18,17]. Go has no set type; the Go blog notes that "a map of boolean values can be used as a set-like data structure" [14], and a map[T]struct{} is a common alternative whose values have size zero, because "a struct or array type has size zero if it contains no fields (or elements, respectively) that have a size greater than zero" [1].

ex07_mapops/main.go 
package main

import (
	"fmt"
	"maps"
	"slices"
)

type Point struct{ X, Y int }

func main() {
	stock := map[string]int{"apple": 5, "pear": 0}

	stock["kiwi"] = 7 // insert
	stock["apple"]++  // update in place: read, add, store

	// Comma-ok distinguishes "absent" from "present with zero value".
	n, ok := stock["pear"]
	fmt.Println(n, ok)
	n, ok = stock["plum"]
	fmt.Println(n, ok)

	delete(stock, "pear")
	delete(stock, "plum") // deleting a missing key is a no-op
	fmt.Println(len(stock), stock)

	// Struct keys: any comparable type works.
	visits := map[Point]int{}
	visits[Point{1, 2}]++
	visits[Point{1, 2}]++
	fmt.Println(visits[Point{1, 2}])

	// Maps are references: the copy shares storage.
	alias := stock
	alias["fig"] = 1
	fmt.Println(stock["fig"])

	// maps.Clone makes an independent (shallow) copy.
	snapshot := maps.Clone(stock)
	snapshot["fig"] = 100
	fmt.Println(stock["fig"], snapshot["fig"])

	// Sorted keys via iterators (Go 1.23+).
	fmt.Println(slices.Sorted(maps.Keys(stock)))

	// A set as map[T]struct{}.
	seen := map[string]struct{}{}
	for _, w := range []string{"a", "b", "a"} {
		seen[w] = struct{}{}
	}
	_, hasA := seen["a"]
	fmt.Println(len(seen), hasA)

	clear(stock) // Go 1.21+: removes every entry
	fmt.Println(len(stock), len(alias))
}

Map elements are not addressable: the specification's list of addressable operands includes slice indexing and fields of addressable structs but not map index expressions [1]. So &m[k] is illegal, and with a struct element type m[k].f = v does not compile. Either store pointers (map[K]*T) or read, modify and write back the whole value [1,14]. The compiler's messages for these cases are reproduced in Exercise 9.

4.3 Iteration

A for k, v := range m loop visits each entry once, but "the iteration order over maps is not specified and is not guaranteed to be the same from one iteration to the next" [1]. The gc runtime deliberately makes the order vary: its map implementation will "randomize iteration order by starting iteration at a random slot", so programs cannot come to depend on an order [19]. When order matters, collect and sort the keys first; with Go 1.23 that is slices.Sorted(maps.Keys(m)) [18].

Modifying a map while ranging over it is permitted and well defined in a limited way: "If a map entry that has not yet been reached is removed during iteration, the corresponding iteration value will not be produced. If a map entry is created during iteration, that entry may be produced during the iteration or may be skipped" [1]. Deleting the current entry inside the loop is therefore a safe way to filter a map in place.

ex08_mapiter/main.go 
package main

import (
	"fmt"
	"maps"
	"slices"
)

func main() {
	m := map[string]int{"a": 1, "b": 2, "c": 3, "d": 4, "e": 5}

	// Iteration order is unspecified; collect orders across runs.
	orders := map[string]bool{}
	for range 50 {
		var keys []byte
		for k := range m {
			keys = append(keys, k[0])
		}
		orders[string(keys)] = true
	}
	fmt.Println("distinct orders seen:", len(orders) > 1)

	// For deterministic output, sort the keys first.
	for _, k := range slices.Sorted(maps.Keys(m)) {
		fmt.Print(k, "=", m[k], " ")
	}
	fmt.Println()

	// Deleting entries during iteration is safe.
	for k, v := range m {
		if v%2 == 0 {
			delete(m, k)
		}
	}
	fmt.Println(slices.Sorted(maps.Keys(m)))

	// maps.Collect builds a map from an iterator of pairs.
	squares := maps.Collect(func(yield func(int, int) bool) {
		for i := 1; i <= 3; i++ {
			if !yield(i, i*i) {
				return
			}
		}
	})
	fmt.Println(squares)
}

4.4 Map concurrency considerations

"Maps are not safe for concurrent use: it's not defined what happens when you read and write to them simultaneously" [14]. The FAQ explains the trade-off: requiring every map operation to take a lock "would slow down most programs and add safety to few. This was not an easy decision, however, since it means uncontrolled map access can crash the program" [3]. Concurrent reads alone are safe; as soon as any goroutine writes, all access must be synchronised, in line with the memory model's general rule that "programs that modify data being simultaneously accessed by multiple goroutines must serialize such access" [3,20].

The gc runtime checks for some unsynchronised writes and, when it notices one, calls its internal fatal("concurrent map writes"), which aborts the program; unlike a panic, it cannot be recovered [19,3]. The check is not guaranteed to catch every race. A program in which two goroutines write to one map without a lock terminated like this with Go 1.24.7:

fatal error: concurrent map writes

goroutine 17 [running]:
...

Run under go run -race, the same program is reported as WARNING: DATA RACE with the stacks of both writes [5]. There are two standard remedies:

  • A map guarded by a mutex. Embed a sync.Mutex or sync.RWMutex next to the map in a struct and lock around every access, as in Gerrand's counter example [14,21]. A RWMutex lets many readers proceed at once.
  • sync.Map, which "is like a Go map[any]any but is safe for concurrent use by multiple goroutines without additional locking or coordination." The documentation warns that it "is specialized. Most code should use a plain Go map instead, with separate locking", and that it is optimised for keys "only ever written once but read many times" or for goroutines working on "disjoint sets of keys" [21].
ex09_mapsync/main.go 
package main

import (
	"fmt"
	"sync"
)

// Counter is a map guarded by a RWMutex: many readers or one writer.
type Counter struct {
	mu sync.RWMutex
	m  map[string]int
}

func NewCounter() *Counter { return &Counter{m: make(map[string]int)} }

func (c *Counter) Inc(key string) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.m[key]++
}

func (c *Counter) Get(key string) int {
	c.mu.RLock()
	defer c.mu.RUnlock()
	return c.m[key]
}

func main() {
	c := NewCounter()
	var wg sync.WaitGroup
	for i := range 100 {
		wg.Add(1)
		go func() {
			defer wg.Done()
			c.Inc([]string{"even", "odd"}[i%2])
		}()
	}
	wg.Wait()
	fmt.Println(c.Get("even"), c.Get("odd"))

	// sync.Map suits keys written once and read many times, or
	// goroutines working on disjoint key sets.
	var cache sync.Map
	for i := range 10 {
		wg.Add(1)
		go func() {
			defer wg.Done()
			cache.LoadOrStore(i%3, fmt.Sprint("value-", i%3))
		}()
	}
	wg.Wait()
	v, ok := cache.Load(2)
	fmt.Println(v, ok)
	n := 0
	cache.Range(func(k, v any) bool { n++; return true })
	fmt.Println("entries:", n)
}

value-2 true
entries: 3

5. Structs

"A struct is a sequence of named elements, called fields, each of which has a name and a type" [1]. Structs are Go's way of grouping data; there are no classes, and behaviour is attached with methods declared on the struct type [1,2].

5.1 Struct fields

Fields of the same type may be declared on one line, "within a struct, non-blank field names must be unique," and the zero value of a struct has every field set to its own zero value [1]. A field whose name begins with an upper-case letter is exported and visible to other packages; a lower-case field is accessible only inside its own package [1]. Fields are read and written with the selector x.f [1].

Composite literals can list fields by name (Employee{ID: 1, Name: "Ada"}), in which case order is free and omitted fields are zero, or positionally, which requires every field in declaration order [1]. The keyed form survives the addition of new fields and is the usual choice for types from other packages; go vet's composites check flags unkeyed literals of imported struct types [22].

Structs are values: assignment copies every field. "Struct types are comparable if all their field types are comparable. Two struct values are equal if their corresponding non-blank field values are equal" [1]. The compiler lays fields out in declaration order with alignment padding, so ordering fields from largest to smallest can shrink a struct, as unsafe.Sizeof shows below [23,1]. The empty struct struct{} has size zero [1,23].

ex10_structs/main.go 
package main

	"fmt"

		c bool
	}

5.2 Nested structs

A field may itself be a struct (stored inline, copied with its parent) or a pointer to a struct (shared, possibly nil). The choice is the same as for any other value: a nested value has clear ownership, while a nested pointer allows sharing, optionality and cycles such as a linked list or a manager reference [2,1]. Selectors chain: c.Billing.City [1]. A struct type cannot contain a field of its own type, since its size would be infinite, but it can contain a pointer to its own type [1,2].

ex11_nested/main.go 
package main

import "fmt"

type Address struct {
	Street, City string
}

type Customer struct {
	Name    string
	Billing Address  // nested struct value
	Ship    *Address // nested pointer: may be nil, may be shared
	Prefs   struct { // field of an anonymous struct type
		Newsletter bool
		Language   string
	}
}

func main() {
	c := Customer{
		Name:    "Rob",
		Billing: Address{Street: "1 Main St", City: "Sydney"},
	}
	c.Prefs.Language = "en"
	fmt.Println(c.Billing.City, c.Ship == nil, c.Prefs.Language)

	// A nested value is copied with its parent; a pointer is shared.
	c.Ship = &c.Billing
	d := c
	d.Billing.City = "Melbourne" // only d's copy changes
	d.Ship.City = "Perth"        // c.Billing changes via the shared pointer
	fmt.Println(c.Billing.City, d.Billing.City)

	// Anonymous struct: a one-off type without a name.
	point := struct{ X, Y int }{1, 2}
	fmt.Printf("%v %T\n", point, point)

	// Typical use: table-driven tests and ad-hoc groupings.
	tests := []struct {
		in   string
		want int
	}{
		{"", 0},
		{"go", 2},
		{"gopher", 6},
	}
	for _, tt := range tests {
		fmt.Print(len(tt.in) == tt.want, " ")
	}
	fmt.Println()

	// Identical anonymous struct types are interchangeable with a named one.
	type Coord struct{ X, Y int }
	var k Coord = point // assignable: same underlying type, one side unnamed
	fmt.Println(k)
}

5.3 Anonymous structs

A struct type can be written inline without a name: struct{ X, Y int }{1, 2}. Such types are useful for one-off groupings, such as a JSON payload decoded in one function, configuration nested inside a larger struct, and above all the slice of test cases in a table-driven test [2,24]. Two struct types are identical when they have the same sequence of fields with the same names, types and tags [1], and a value is assignable to a variable when the two types have identical underlying types and at least one is not a named type [1]. So an anonymous struct value can be assigned directly to a named struct with the same fields, as the last lines of the example show.

5.4 Struct tags

"A field declaration may be followed by an optional string literal tag, which becomes an attribute for all the fields in the corresponding field declaration. ... The tags are made visible through a reflection interface and take part in type identity for structs but are otherwise ignored" [1]. By convention, documented in reflect, a tag is "a concatenation of optionally space-separated key:"value" pairs" read with StructTag.Get or StructTag.Lookup; Lookup also "reports whether the value was explicitly set in the tag string" [25]. go vet's structtag check reports malformed tags [22].

The best-known consumer is encoding/json. Only exported fields are encoded; the tag gives the JSON name "possibly followed by a comma-separated list of options" [10]:

5.5 Embedded structs

"A field declared with a type but no explicit field name is called an embedded field." It must be a type name T or a pointer *T to a non-interface type name, and "the unqualified type name acts as the field name" [1]. Fields and methods of the embedded type are promoted: d.Name means d.Animal.Name [1]. A promoted name is shadowed by a field or method with the same name at a shallower depth, so an outer type can override a method and still call the inner one explicitly, as Robot.Describe does below [1,4].

Promotion also feeds method sets. "If S contains an embedded field T, the method sets of S and *S both include promoted methods with receiver T. The method set of *S also includes promoted methods with receiver *T. If S contains an embedded field *T, the method sets of S and *S both include promoted methods with receiver T or *T" [1]. This is how a struct embedding sync.Mutex gains Lock and Unlock, and how embedding lets a type satisfy an interface without writing forwarding methods [4,2].

Embedding is composition, not inheritance. Effective Go: "There's an important way in which embedding differs from subclassing. When we embed a type, the methods of that type become methods of the outer type, but when they are invoked the receiver of the method is the inner type, not the outer one" [4]. The inner method knows nothing about the outer struct, and there is no virtual dispatch back to an override in the outer type.

ex13_embed/main.go 
package main

	c.Lock()
	c.n++
	c.Unlock()
	fmt.Println(c.n)

	u.WriteString("hello, ")
	u.WriteString("gopher")

6. Pointers

"A pointer type denotes the set of all pointers to variables of a given type, called the base type of the pointer" [1]. Pointers let functions modify their caller's variables, avoid copying large values, and express optional or shared data. Go pointers are safer than C pointers: there is no pointer arithmetic in ordinary code (only through the unsafe package), and memory is garbage-collected, so a pointer never dangles [3,23].

6.1 Pointer declarations

The type *T is "pointer to T". "The value of an uninitialized pointer is nil" [1]. A pointer is obtained in one of three ways: the address operator &x, the built-in new(T), which "allocates storage for a variable of that type at run time, and returns a value of type *T pointing to it", or the address of a composite literal &T{…} [1]. Effective Go summarises new: it "allocates zeroed storage for a new variable of type T and returns its address" [4].

var p *int            // nil
q := new(int)         // *int pointing at a zeroed int
c := &Config{Port: 1} // *Config pointing at an initialised Config

6.2 Dereferencing

"For an operand x of pointer type *T, the pointer indirection *x denotes the variable of type T pointed to by x" [1]. Because *x denotes a variable, it can be read and assigned: *p = 42. Two shorthands remove most explicit dereferences. For a pointer to a struct, "x.f is shorthand for (*x).f", and for a pointer to an array, a[i] is shorthand for (*a)[i] [1]. So Go has no -> operator.

6.3 Address operators

"For an operand x of type T, the address operation &x generates a pointer of type *T to x. The operand must be addressable, that is, either a variable, pointer indirection, or slice indexing operation; or a field selector of an addressable struct operand; or an array indexing operation of an addressable array." As an exception, the operand may also be a composite literal [1]. Constants, map elements and the results of function calls are not addressable [1].

Taking the address of a local variable and returning it is safe. "Note that, unlike in C, it's perfectly OK to return the address of a local variable; the storage associated with the variable survives after the function returns" [4]. The compiler's escape analysis places such variables on the heap when it "cannot prove that the variable is not referenced after the function returns" [3]. Two pointers are equal "if they point to the same variable or if both have value nil" [1].

ex14_pointers/main.go 
package main

import "fmt"

type Config struct {
	Port    int
	Verbose bool
}

// newConfig returns the address of a local variable; this is safe in Go.
func newConfig() *Config {

	var p *int
	fmt.Println(p == nil)

	x := 41
	p = &x
	fmt.Println(*p) // dereference with *

	*p = 42 // write through the pointer
	fmt.Println(x)

	increment(&x) // simulate pass-by-reference
	fmt.Println(x)

	q := new(int)
	fmt.Println(*q, q != nil)

	c := &Config{Port: 9000}

	fmt.Println(c.Port, (*c).Verbose)

	fmt.Println(newConfig().Port)

	pp := &p
	**pp = 100
	fmt.Println(x)

	// Addresses of slice elements and struct fields are allowed.
	nums := []int{1, 2, 3}
	second := &nums[1]
	*second = 20
	portPtr := &c.Port
	*portPtr++
	fmt.Println(nums, c.Port)

	// Pointers are comparable: equal if they point to the same variable.
	a, b := 1, 1
	fmt.Println(&a == &a, &a == &b, *(&a) == *(&b))
}

6.4 Nil pointers

"If x is nil, an attempt to evaluate *x will cause a run-time panic," and likewise "if x is of pointer type and has the value nil and x.f denotes a struct field, assigning to or evaluating x.f causes a run-time panic" [1]. The panic value implements runtime.Error, an interface that distinguishes run-time errors from ordinary errors [26].

Calling a method on a nil pointer, however, is not itself an error: the method simply receives a nil receiver. Methods that check for nil can make the nil pointer a useful zero value, such as an empty list or tree [1,2].

The subtlest nil bug involves interfaces. "Under the covers, interfaces are implemented as two elements, a type T and a value V," and an interface is nil only if both are unset. Storing a nil *MyErr in an error produces an interface whose type is *MyErr, so it is not nil [3]. A function returning an interface should return a literal nil on success, not a typed nil pointer.

ex15_nil/main.go 
package main

import (
	"errors"
	"fmt"
	"runtime"
)

type Node struct {
	Val  int
	Next *Node
}

// Sum works on a nil receiver: a nil *Node is an empty list.
func (n *Node) Sum() int {
	if n == nil {
		return 0
	}
	return n.Val + n.Next.Sum()
}

type MyErr struct{}

func (*MyErr) Error() string { return "my error" }

func mayFail(fail bool) error {
	var p *MyErr // nil pointer
	if fail {
		p = &MyErr{}
	}
	return p // BUG: a non-nil interface holding a nil *MyErr
}

func deref(n *Node) (val int, err error) {
	defer func() {
		if r := recover(); r != nil {
			var re runtime.Error
			if e, ok := r.(error); ok && errors.As(e, &re) {
				err = re
			}
		}
	}()
	return n.Val, nil
}

func main() {
	list := &Node{1, &Node{2, &Node{3, nil}}}
	fmt.Println(list.Sum())

	var empty *Node
	fmt.Println(empty.Sum()) // method call on nil pointer is fine

	_, err := deref(nil) // field access through nil pointer panics
	fmt.Println(err)

	// Guard before dereferencing.
	if empty != nil && empty.Val > 0 {
		fmt.Println("unreachable")
	}

	// Typed nil inside an interface is not equal to nil.
	err = mayFail(false)
	fmt.Println(err == nil, err != nil)
	fmt.Printf("%T %v\n", err, err.(*MyErr) == nil)
}

6.5 Pointer receivers

A method's receiver may be a value T or a pointer *T [1]. A value receiver works on a copy, so changes it makes are lost, as BrokenInc shows below; a pointer receiver can modify the caller's value. The FAQ's first question is the decisive one: "does the method need to modify the receiver? If it does, the receiver must be a pointer." The second is efficiency: "if the receiver is large, a big struct for instance, it may be cheaper to use a pointer receiver" [3]. The Go code review guidelines add that a struct containing a sync.Mutex must use pointer receivers to avoid copying the lock, that a type should not mix receiver kinds, and "when in doubt, use a pointer receiver" [9].

Calls are convenient in both directions. "If x is addressable and &x's method set contains m, x.m() is shorthand for (&x).m()" [1], and a value method can be called on a pointer because the method set of *T includes methods declared on T. Method sets, however, are asymmetric: "The method set of a defined type T consists of all methods declared with receiver type T," while that of *T "is the set of all methods declared with receiver *T or T" [1]. Effective Go's rule: "value methods can be invoked on pointers and values, but pointer methods can only be invoked on pointers" [4]. So if Inc has a pointer receiver, only *Counter satisfies an interface requiring Inc, and map elements, which are not addressable, cannot call it unless the map stores pointers [1].

ex16_receivers/main.go 
package main

import "fmt"

type Counter struct{ n int }

func (c Counter) Value() int { return c.n } // value receiver: gets a copy
func (c *Counter) Inc()      { c.n++ }      // pointer receiver: mutates
func (c Counter) BrokenInc() { c.n++ }      // mutates only the copy

type Incrementer interface{ Inc() }

func main() {
	var c Counter
	c.Inc()       // Go rewrites this as (&c).Inc() because c is addressable
	c.BrokenInc() // no effect on c
	fmt.Println(c.Value())

	p := &c
	p.Inc()
	fmt.Println(p.Value()) // and (*p).Value() for value methods

	// Method sets: only *Counter has Inc, so only *Counter is an Incrementer.
	var i Incrementer = &c
	i.Inc()
	fmt.Println(c.n)
	// var j Incrementer = c // compile error: Counter does not implement Incrementer

	// Map elements are not addressable, so pointer methods need a pointer value.
	counters := map[string]*Counter{"a": {}}
	counters["a"].Inc()
	fmt.Println(counters["a"].Value())

	// Slice elements are addressable.
	cs := make([]Counter, 2)
	cs[1].Inc()
	fmt.Println(cs[0].Value(), cs[1].Value())

	// Range copies each element; mutate through the index instead.
	for _, x := range cs {
		x.Inc() // increments the copy
	}
	for i := range cs {
		cs[i].Inc()
	}
	fmt.Println(cs[0].Value(), cs[1].Value())
}

The final loop is a reminder that the range iteration variable is a copy of each element: calling a pointer method on it mutates the copy. Index into the slice, or range over a slice of pointers, to mutate the elements [1,2].

Exercise 1 — Reverse a slice in place

Write a generic Reverse[T any](s []T) that reverses its argument in place without allocating. Explain why it can modify the caller's data even though s is passed by value, and show that reversing a sub-slice affects only that part of the backing array.

Show solution sol1_reverse/main.go 
package main

import (
	"fmt"
	"slices"
)

// Reverse reverses s in place by swapping from both ends.
func Reverse[T any](s []T) {
	for i, j := 0, len(s)-1; i < j; i, j = i+1, j-1 {
		s[i], s[j] = s[j], s[i]
	}
}

func main() {
	nums := []int{1, 2, 3, 4, 5}
	Reverse(nums)
	fmt.Println(nums)

	words := []string{"a", "b", "c", "d"}
	Reverse(words[1:]) // a sub-slice reverses part of the backing array
	fmt.Println(words)

	Reverse([]int(nil)) // nil and empty slices are fine

	std := []int{1, 2, 3}
	slices.Reverse(std)
	fmt.Println(std)
}
Output 
[5 4 3 2 1]
[a d c b]
[3 2 1]

The slice header is copied, but the copy points at the same array, so element writes are visible to the caller [8,3]. The function never changes the length, so it needs no return value. Since Go 1.21 the standard library provides the same operation as slices.Reverse [11].

Exercise 3 — In-place de-duplication

Write Dedupe[T comparable](s []T) []T that removes adjacent duplicates (so a sorted input becomes unique) in O(n) time and without allocating. Make sure the abandoned tail holds no stale values, and compare your function with the standard library.

Show solution sol3_dedupe/main.go 
package main

import (
	"fmt"
	"slices"
)

// Dedupe removes adjacent duplicates in place and returns the shortened
// slice. The vacated tail is zeroed so it holds no stale references.
func Dedupe[T comparable](s []T) []T {
	if len(s) < 2 {
		return s
	}
	k := 1
	for i := 1; i < len(s); i++ {
		if s[i] != s[k-1] {
			s[k] = s[i]
			k++
		}
	}
	clear(s[k:])
	return s[:k]
}

func main() {
	in := []int{1, 1, 2, 3, 3, 3, 4, 5, 5}
	full := in
	out := Dedupe(in)
	fmt.Println(out, len(out), cap(out))
	fmt.Println(full) // same backing array, tail zeroed

	words := []string{"go", "go", "gopher"}
	fmt.Println(slices.Compact(words)) // the standard library equivalent
}
Output 
[1 2 3 4 5] 5 9
[1 2 3 4 5 0 0 0 0]
[go gopher]

The read index i scans every element and the write index k marks the end of the unique prefix. The result shares the input's array, which is why the caller must use the returned slice, just as with append [8]. clear(s[k:]) zeroes the tail so that, for pointer element types, nothing is kept alive needlessly [1,13]. slices.Compact does the same and, since Go 1.22, also zeroes the tail [11,12].

Exercise 4 — Word frequencies

Write topWords(text string, n int) that returns the n most frequent words (case-insensitive, punctuation trimmed), ordered by descending count and alphabetically among equal counts. The output must be the same on every run.

Show solution sol4_wordfreq/main.go 
package main

import (
	"cmp"
	"fmt"
	"maps"
	"slices"
	"strings"
)

type wordCount struct {
	Word  string
	Count int
}

func topWords(text string, n int) []wordCount {
	freq := make(map[string]int)
	for _, w := range strings.Fields(strings.ToLower(text)) {
		w = strings.Trim(w, ".,;:!?\"'")
		if w != "" {
			freq[w]++
		}
	}
	counts := make([]wordCount, 0, len(freq))
	for _, w := range slices.Sorted(maps.Keys(freq)) {
		counts = append(counts, wordCount{w, freq[w]})
	}
	slices.SortStableFunc(counts, func(a, b wordCount) int {
		return cmp.Compare(b.Count, a.Count) // descending by count
	})
	return counts[:min(n, len(counts))]
}

func main() {
	text := `The quick brown fox jumps over the lazy dog. The dog sleeps;
the fox runs. A fox is quick!`
	for _, wc := range topWords(text, 4) {
		fmt.Printf("%-6s %d\n", wc.Word, wc.Count)
	}
}
Output 
the    4
fox    3
dog    2
quick  2

The map accumulates counts using the zero value for absent keys, so freq[w]++ needs no existence check [1,14]. Map order is random, so the solution first builds the slice in sorted key order and then applies a stable sort by count, which preserves the alphabetical order among ties [1,11]. The built-in min (Go 1.21) keeps the slice expression in range when fewer than n words exist [13].

Exercise 5 — A concurrency-safe generic map

Implement SafeMap[K comparable, V any] with Load, Store, Len and an atomic read-modify-write Update(k, f). Increment counters for five keys from 1,000 goroutines and verify the result with the race detector.

Show solution sol5_safemap/main.go 
package main

import (
	"fmt"
	"sync"
)

// SafeMap is a generic map that is safe for concurrent use.
type SafeMap[K comparable, V any] struct {
	mu sync.RWMutex
	m  map[K]V
}

func NewSafeMap[K comparable, V any]() *SafeMap[K, V] {
	return &SafeMap[K, V]{m: make(map[K]V)}
}

func (s *SafeMap[K, V]) Load(k K) (V, bool) {
	s.mu.RLock()
	defer s.mu.RUnlock()
	v, ok := s.m[k]
	return v, ok
}

func (s *SafeMap[K, V]) Store(k K, v V) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.m[k] = v
}

// Update applies f to the current value under a single write lock,
// so read-modify-write sequences are atomic.
func (s *SafeMap[K, V]) Update(k K, f func(V, bool) V) {
	s.mu.Lock()
	defer s.mu.Unlock()
	old, ok := s.m[k]
	s.m[k] = f(old, ok)
}

func (s *SafeMap[K, V]) Len() int {
	s.mu.RLock()
	defer s.mu.RUnlock()
	return len(s.m)
}

func main() {
	hits := NewSafeMap[string, int]()
	var wg sync.WaitGroup
	for i := range 1000 {
		wg.Add(1)
		go func() {
			defer wg.Done()
			page := fmt.Sprint("/page/", i%5)
			hits.Update(page, func(n int, _ bool) int { return n + 1 })
		}()
	}
	wg.Wait()
	n, ok := hits.Load("/page/3")
	fmt.Println(hits.Len(), n, ok)
}
Output (go run -race) 
5 200 true

Reads take the shared lock and writes the exclusive lock [21]. Implementing the increment as Load followed by Store would be race-free but still wrong, because two goroutines could read the same old value; Update holds the write lock across the whole read-modify-write [20]. The pointer receivers are required: copying a SafeMap would copy its mutex [9,21].

Exercise 7 — Composition by embedding

Create an Audit struct with CreatedAt, UpdatedAt, Version and a pointer method Touch(time.Time). Embed it in Product and Order, have *Order override Touch so that it also touches its items, and call both through a common interface.

Show solution sol7_embed/main.go 
package main

import (
	"fmt"
	"time"
)

// Audit adds bookkeeping to any struct that embeds it.
type Audit struct {
	CreatedAt time.Time
	UpdatedAt time.Time
	Version   int
}

func (a *Audit) Touch(now time.Time) {
	if a.CreatedAt.IsZero() {
		a.CreatedAt = now
	}
	a.UpdatedAt = now
	a.Version++
}

type Toucher interface{ Touch(time.Time) }

type Product struct {
	Audit
	SKU   string
	Price int
}

type Order struct {
	Audit
	ID    int
	Items []Product
}

// Touch on Order shadows the promoted method and also touches its items.
func (o *Order) Touch(now time.Time) {
	o.Audit.Touch(now)
	for i := range o.Items {
		o.Items[i].Touch(now)
	}
}

func main() {
	t0 := time.Date(2026, 10, 30, 12, 0, 0, 0, time.UTC)
	o := &Order{ID: 1, Items: []Product{{SKU: "A1"}, {SKU: "B2"}}}

	for i, t := range []Toucher{o, &o.Items[0]} {
		t.Touch(t0.Add(time.Duration(i) * time.Hour))
	}
	fmt.Println(o.Version, o.Items[0].Version, o.Items[1].Version)
	fmt.Println(o.CreatedAt.Format(time.Kitchen), o.Items[0].UpdatedAt.Format(time.Kitchen))
}
Output 
1 2 1
12:00PM 1:00PM

Touch has a pointer receiver, so it is promoted to *Product but not to Product, and the interface values must hold pointers [1]. Order.Touch shadows the promoted method and calls o.Audit.Touch explicitly; the embedded method operates on the inner Audit only, exactly as Effective Go describes [4]. Item 0 was touched twice (once via the order, once directly), giving version 2.

Exercise 8 — A generic linked list with pointers

Implement a singly linked List[T] whose zero value is an empty list, with PushFront, a nil-safe Len, an in-place Reverse, and an All method returning an iter.Seq[T] for use with range.

Show solution sol8_list/main.go 
package main

import (
	"fmt"
	"iter"
)

type node[T any] struct {
	val  T
	next *node[T]
}

// List is a singly linked list; the zero value is an empty list.
type List[T any] struct {
	head *node[T]
	len  int
}

func (l *List[T]) PushFront(v T) {
	l.head = &node[T]{val: v, next: l.head}
	l.len++
}

func (l *List[T]) Len() int {
	if l == nil {
		return 0
	}
	return l.len
}

// Reverse relinks the nodes in place using three pointers.
func (l *List[T]) Reverse() {
	var prev *node[T]
	for cur := l.head; cur != nil; {
		next := cur.next
		cur.next = prev
		prev, cur = cur, next
	}
	l.head = prev
}

// All returns an iterator over the values, front to back.
func (l *List[T]) All() iter.Seq[T] {
	return func(yield func(T) bool) {
		for n := l.head; n != nil; n = n.next {
			if !yield(n.val) {
				return
			}
		}
	}
}

func main() {
	var l List[string]
	for _, s := range []string{"c", "b", "a"} {
		l.PushFront(s)
	}
	for v := range l.All() {
		fmt.Print(v, " ")
	}
	fmt.Println(l.Len())

	l.Reverse()
	for v := range l.All() {
		fmt.Print(v, " ")
	}
	fmt.Println()

	var none *List[int]
	fmt.Println(none.Len())
}
Output 
a b c 3
c b a 
0

Each node points to the next, ending in nil; the zero List has a nil head and is ready to use [1,2]. Reverse re-points each node's next in a single pass. Len checks for a nil receiver, so calling it through a nil *List is safe [1]. All returns a push iterator in the form defined by the iter package and supported by range-over-func since Go 1.23 [18]. For production use, container/list provides a doubly linked list [27].
