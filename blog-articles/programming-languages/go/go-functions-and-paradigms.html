Functions and Programming Paradigms in Go

A technical article with runnable examples, exercises and solutions · Examples verified with Go 1.27.3 (go run, gofmt, go vet) · References in Vancouver style

Abstract. Functions are the basic unit of behaviour in Go. They are declared with a compact signature syntax, take parameters by value, can return several results (optionally named), can be variadic, and are first-class values that may be stored, passed, returned and closed over. Methods are functions with a receiver, and the choice between value and pointer receivers determines method sets and therefore which interfaces a type satisfies. On these foundations Go supports several programming styles at once: procedural decomposition, a pragmatic subset of functional programming (higher-order functions, closures, lazy iterators), and an object-oriented style built on composition and delegation rather than inheritance. This article explains each feature with reference to the language specification and the Go authors' guidance, covers the Go 1.27 addition of generic methods, and closes with exercises and worked solutions.

1. Overview

Go is usually described as a procedural language in the C family that also supports object-oriented and functional techniques. Rob Pike, one of its designers, characterises it as "a compiled, statically typed, procedural language with pointers and so on" [1]. The Go FAQ answers the question "Is Go an object-oriented language?" with "Yes and no": Go "has types and methods and allows an object-oriented style of programming, there is no type hierarchy" [2]. And the official codewalk on functions notes that Go "supports first class functions, higher-order functions, user-defined function types, function literals, closures, and multiple return values", a feature set that "supports a functional programming style in a strongly typed language" [3,4].

Every one of these styles rests on the same small set of mechanisms, summarised below and then examined one by one.

2. Function declarations

"A function declaration binds an identifier, the function name, to a function" [5]. A declaration consists of the keyword func, the name, an optional type-parameter list, a parameter list, an optional result list, and a body. Consecutive parameters of the same type may share a single type annotation (x, y int), and if there is exactly one unnamed result it may be written without parentheses [5]. Go places the type after the name, so that, as Pike puts it, "Go's declarations read left to right" [6].

Some rules worth knowing:

  • If the signature declares results, "the function body's statement list must end in a terminating statement" (for example a return or a panic call) [5].
  • Parameters that are not used may be left unnamed or named _; "If the receiver's value is not referenced inside the body of the method, its identifier may be omitted in the declaration. The same applies in general to parameters of functions and methods" [5].
  • A function with type parameters is generic and "must be instantiated before it can be called or used as a value" [5,7].
  • Go has no function overloading: the FAQ explains that "Matching only by name and requiring consistency in the types was a major simplifying decision in Go's type system" [2]. There are also no default parameter values; variadic parameters and option functions (Section 17) fill that role.
  • Package-level functions can be referenced before they are declared in the source file, which is what makes mutual recursion between top-level functions straightforward (Section 11) [5].
ex01_decl/main.go 
package main

import "fmt"

// add has two parameters of the same type, so the type is written once.
func add(x, y int) int {
	return x + y
}

// greet has no parameters and no result.
func greet() {
	fmt.Println("hello, functions")
}

// scale ignores its second parameter; the blank identifier documents that.
func scale(x float64, _ string) float64 {
	return x * 2
}

// Max is generic: it is instantiated for each type argument (Go 1.18+).
func Max[T int | float64 | string](a, b T) T {
	if a > b {
		return a
	}
	return b
}

func main() {
	greet()
	fmt.Println(add(2, 3))
	fmt.Println(scale(1.5, "unused"))
	fmt.Println(Max(3, 7), Max(2.5, 1.5), Max("go", "c"))
	fmt.Printf("%T\n", add) // the type of a function is its signature
}
Output

The %T verb prints func(int, int) int: a function's type is its signature, independent of its name or parameter names [5]. Max uses a union constraint so that > is defined for every permitted type argument; the standard library provides cmp.Ordered for the general case [8] and, since Go 1.21, built-in min and max functions [9].

3. Parameters and return values

When a function is called, "new storage is allocated for the function's variables, which includes its parameters and results. Then, the arguments of the call are passed to the function, which means that they are assigned to their corresponding function parameters" [5]. The FAQ states the consequence plainly: "As in all languages in the C family, everything in Go is passed by value. That is, a function always gets a copy of the thing being passed, as if there were an assignment statement assigning the value to the parameter" [2].

What a copy means depends on the type. Copying an int, an array or a struct copies all of its contents. Copying a pointer copies the address, "but not the data it points to". And "Map and slice values behave like pointers: they are descriptors that contain pointers to the underlying map or slice data" [2]. A function can therefore change the elements of a slice it receives, but not its length as seen by the caller, because the length lives in the copied descriptor.

ex02_params/main.go 
package main

import "fmt"

type Point struct{ X, Y int }

func incInt(n int)            { n++ }
func incArray(a [3]int)       { a[0]++ }
func incStruct(p Point)       { p.X++ }
func incPointer(p *Point)     { p.X++ }
func setFirst(s []int)        { s[0] = 99 }
func grow(s []int)            { s = append(s, 4) }
func addKey(m map[string]int) { m["new"] = 1 }

func main() {
	n := 1
	a := [3]int{1, 2, 3}
	p := Point{1, 2}
	s := []int{1, 2, 3}
	m := map[string]int{}

	incInt(n)
	incArray(a)
	incStruct(p)
	fmt.Println("copies:", n, a, p) // unchanged

	incPointer(&p)
	fmt.Println("via pointer:", p) // X changed

	setFirst(s)
	grow(s)
	fmt.Println("slice:", s, len(s)) // element changed, length not

	addKey(m)
	fmt.Println("map:", m) // map contents changed
}
Output 
copies: 1 [1 2 3] {1 2}
via pointer: {2 2}
slice: [99 2 3] 3
map: map[new:1]
Design note. Pass-by-value is a semantic rule, not a performance promise: "Actual implementations may apply optimizations to avoid copying as long as the optimizations do not change the semantics" [2]. Take a pointer when the callee must modify the caller's variable or when the value is large; otherwise passing a value keeps ownership simple.

4. Multiple return values

"One of Go's unusual features is that functions and methods can return multiple values", which, according to Effective Go, replaces two clumsy C idioms: "in-band error returns such as -1 for EOF and modifying an argument passed by address" [10]. The convention is that a fallible function returns an error (or a boolean when no explanation is needed) as its "final return value" [11]. A related idiom, which Effective Go calls the "comma ok" idiom, returns a boolean that reports whether a lookup or assertion succeeded [10].

The specification gives multi-valued calls a special case: if the results of g "are equal in number and individually assignable to the parameters of another function or method f, then the call f(g(parameters_of_g)) will invoke f after passing the return values of g to the parameters of f in order" [5]. Similarly, return g() may forward all of g's results [5]. Results you do not need are discarded with the blank identifier _ [10].

ex03_multi/main.go 
package main

import (
	"errors"
	"fmt"
	"strconv"
)

func divmod(a, b int) (int, int) {
	return a / b, a % b
}

var ErrDivByZero = errors.New("division by zero")

func safeDiv(a, b int) (int, error) {
	if b == 0 {
		return 0, ErrDivByZero
	}
	return a / b, nil
}

func describe(q, r int) string {
	return fmt.Sprintf("quotient %d, remainder %d", q, r)
}

func main() {
	q, r := divmod(17, 5)
	fmt.Println(q, r)

	// The results of divmod feed describe's parameters directly.
	fmt.Println(describe(divmod(17, 5)))

	if _, err := safeDiv(1, 0); err != nil {
		fmt.Println("error:", err)
	}

	// The blank identifier discards a result we do not need.
	n, _ := strconv.Atoi("42")
	fmt.Println(n + 1)

	// The comma-ok idiom: a second boolean result reports success.
	ages := map[string]int{"ana": 31}
	if age, ok := ages["bob"]; !ok {
		fmt.Println("bob not found; zero value is", age)
	}
}
Output 
3 2
quotient 3, remainder 2
error: division by zero
43
bob not found; zero value is 0

Code Review Comments discourages in-band error values such as returning -1 or "" to signal failure, recommending an extra result instead [11].

5. Named return values

Results may be named, in which case "The result parameters act as ordinary local variables and the function may assign values to them as necessary", and an empty return "returns the values of these variables" [5]. "Regardless of how they are declared, all the result values are initialized to the zero values for their type upon entry to the function" [5]. Effective Go observes that names can serve as documentation: "they can make code shorter and clearer: they're documentation" [10].

The Go code review guidance is more cautious [11]:

  • Name results when "a function returns two or three parameters of the same type, or if the meaning of a result isn't clear from context" (for example (lat, long float64, err error)).
  • "Don't name result parameters just to avoid declaring a var inside the function."
  • "Naked returns are okay if the function is a handful of lines. Once it's a medium sized function, be explicit with your return values."
  • "in some cases you need to name a result parameter in order to change it in a deferred closure. That is always OK."

The last point works because "A 'return' statement that specifies results sets the result parameters before any deferred functions are executed" [5], so a deferred function literal can inspect and overwrite them. readAll below uses this to report an error from Close that would otherwise be lost.

ex04_named/main.go 
package main

import (
	"errors"
	"fmt"
	"io"
	"strings"
)

// Location's named results document what each float64 means.
func Location() (lat, long float64, err error) {
	return 49.28, -123.12, nil
}

// split uses a naked return; acceptable in a function this short.
func split(sum int) (x, y int) {
	x = sum * 4 / 9
	y = sum - x
	return
}

// readAll names err so that the deferred closure can change it.
func readAll(r io.ReadCloser) (data []byte, err error) {
	defer func() {
		if cerr := r.Close(); cerr != nil && err == nil {
			err = cerr
		}
	}()
	return io.ReadAll(r)
}

type failingCloser struct{ io.Reader }

func (failingCloser) Close() error { return errors.New("close failed") }

func zero() (n int, s string, p *int) {
	return // every named result starts as its zero value
}

func main() {
	fmt.Println(Location())
	fmt.Println(split(17))

	data, err := readAll(failingCloser{strings.NewReader("payload")})
	fmt.Printf("%q %v\n", data, err)

	n, s, p := zero()
	fmt.Printf("%d %q %v\n", n, s, p)
}
Output 
49.28 -123.12 <nil>
7 10
"payload" close failed
0 "" <nil>

Named results interact with shadowing. If an inner block redeclares a variable with the same name as a result, a naked return would be ambiguous, and the specification permits compilers to reject it ("A compiler may disallow an empty expression list in a 'return' statement if a different entity ... with the same name as a result parameter is in scope") [5]. 6. Variadic functions

"The final incoming parameter in a function signature may have a type prefixed with .... A function with such a parameter is called variadic and may be invoked with zero or more arguments for that parameter" [5]. Inside the function, the parameter of type ...T has type []T. Three cases are distinguished [5]:

  1. With no arguments for the parameter, "the value passed to p is nil".
  2. With one or more arguments, "the value passed is a new slice of type []T with a new underlying array whose successive elements are the actual arguments".
  3. If the final argument is a slice followed by ..., "it is passed unchanged as the value for a ...T parameter. In this case no new slice is created."

The third case means the callee shares the caller's backing array, which the example demonstrates with zeroFirst. The built-in append and functions such as fmt.Println and errors.Join are variadic [9,12].

ex05_variadic/main.go 
package main

import (
	"fmt"
	"strings"
)

func sum(nums ...int) int {
	total := 0
	for _, n := range nums {
		total += n
	}
	return total
}

// A variadic parameter must be last; fixed parameters come first.
func join(sep string, parts ...string) string {
	return strings.Join(parts, sep)
}

func inspect(nums ...int) {
	fmt.Println(nums == nil, len(nums), cap(nums))
}

func zeroFirst(nums ...int) {
	if len(nums) > 0 {
		nums[0] = 0
	}
}

func main() {
	fmt.Println(sum(), sum(1), sum(1, 2, 3))

	xs := []int{4, 5, 6}
	fmt.Println(sum(xs...)) // spread an existing slice

	fmt.Println(join("-", "a", "b", "c"))

	inspect()      // no arguments: nil slice
	inspect(1, 2)  // a new slice is created
	inspect(xs...) // the caller's slice is passed unchanged

	zeroFirst(xs...)
	fmt.Println(xs) // the callee modified our backing array

	fmt.Println(append([]int{1}, xs...))
}

7. Anonymous functions

"A function literal represents an anonymous function" [5]. It has the same form as a declaration without the name, and "can be assigned to a variable or invoked directly" [5]. Function literals are used for short callbacks (such as comparison functions for slices.SortFunc [13]), for goroutine bodies, for deferred cleanups, and to limit the scope of a block of code. Unlike function declarations, "Function literals cannot declare type parameters" [5].

ex06_anon/main.go 
package main

import (
	"cmp"
	"fmt"
	"slices"
	"strings"
)

type Person struct {
	Name string
	Age  int
}

func main() {
	// A function literal assigned to a variable.
	square := func(x int) int { return x * x }
	fmt.Println(square(9))

	// A function literal invoked immediately.
	result := func(a, b int) int { return a*10 + b }(4, 2)
	fmt.Println(result)

	// A function literal passed as an argument.
	people := []Person{{"Ana", 31}, {"Bo", 25}, {"Cy", 31}}
	slices.SortFunc(people, func(a, b Person) int {
		return cmp.Or(cmp.Compare(b.Age, a.Age), strings.Compare(a.Name, b.Name))
	})
	fmt.Println(people)

	// A function literal used to scope a deferred cleanup.
	func() {
		defer fmt.Println("inner cleanup")
		fmt.Println("inner work")
	}()
	fmt.Println("after inner")
}
Output

42
[{Ana 31} {Cy 31} {Bo 25}]
inner work
inner cleanup
after inner

cmp.Or returns its first non-zero argument, which makes it a convenient way to combine comparison keys [8].

8. Closures

The specification defines closures in one sentence: "Function literals are closures: they may refer to variables declared in a surrounding function. Those variables are then shared between the surrounding function and the function literal, and they survive as long as they are accessible" [5]. Two consequences follow:

  • A closure captures variables, not values. Several closures created in the same call share the same variables, as deposit and get do below [5,14].
  • A captured variable outlives the function that declared it. The FAQ explains that this is safe because "Each variable in Go exists as long as there are references to it"; if the compiler "cannot prove that the variable is not referenced after the function returns", it allocates the variable on the garbage-collected heap [2].

A function literal cannot refer to itself by a name introduced with := in the same statement, because the scope of a variable declared inside a function begins after the declaration [5]. The usual idiom is to declare the variable first (var fib func(int) int) and assign the literal afterwards, as in memoFib.

ex07_closures/main.go 
package main

import "fmt"

// counter returns a closure that owns its own count variable.
func counter() func() int {
	count := 0
	return func() int {
		count++
		return count
	}
}

// account returns two closures that share one balance variable.
func account(balance int) (deposit func(int), get func() int) {
	deposit = func(n int) { balance += n }
	get = func() int { return balance }
	return
}

// memoFib caches results in a map captured by the closure.
func memoFib() func(int) int {
	memo := map[int]int{}
	var fib func(int) int // declared first so the literal can call itself
	fib = func(n int) int {
		if n < 2 {
			return n
		}
		if v, ok := memo[n]; ok {
			return v
		}
		memo[n] = fib(n-1) + fib(n-2)
		return memo[n]
	}
	return fib
}

func main() {
	a, b := counter(), counter()
	fmt.Println(a(), a(), a(), b()) // independent state

	deposit, get := account(100)
	deposit(50)
	fmt.Println(get()) // both closures see the same variable

	fmt.Println(memoFib()(90))

	// Since Go 1.22 each iteration has a fresh i, so each closure
	// captures a different variable.
	var fs []func() int
	for i := range 3 {
		fs = append(fs, func() int { return i * i })
	}
	for _, f := range fs {
		fmt.Print(f(), " ")
	}
	fmt.Println()
}
Output

150

0 1 4

The loop at the end prints 0 1 4. Before Go 1.22, the variables declared by a for loop "were created once and updated by each iteration"; since Go 1.22 "each iteration of the loop creates new variables, to avoid accidental sharing bugs" [15]. Under the old semantics all three closures would have shared one i, a well-known trap described by Donovan and Kernighan [14]. The new behaviour applies to modules that declare go 1.22 or later in go.mod [15].

9. First-class functions

A value is first-class if it can be used like any other value: stored in variables and data structures, passed as an argument, and returned as a result. The term goes back to Christopher Strachey's 1967 lecture notes on programming-language concepts [16]. In Go, "functions can be passed around just like any other value. A function's type signature describes the types of its arguments and return values" [3].

Function values have a few special properties [5]:

  • The zero value of a function type is nil, and calling a nil function value "causes a run-time panic".
  • Function types "are not comparable", except that a function value "may be compared to the predeclared identifier nil". Two functions therefore cannot be tested for equality, and function values cannot be map keys.
ex08_firstclass/main.go 
package main

import (
	"fmt"
	"strings"
)

type Command struct {
	Name string
	Run  func(args []string) string // a function stored in a struct field
}

func upper(args []string) string { return strings.ToUpper(strings.Join(args, " ")) }
func count(args []string) string { return fmt.Sprint(len(args)) }

func main() {
	// Functions stored in a map form a dispatch table.
	ops := map[string]func(float64, float64) float64{
		"+": func(a, b float64) float64 { return a + b },
		"-": func(a, b float64) float64 { return a - b },
		"*": func(a, b float64) float64 { return a * b },
	}
	for _, op := range []string{"+", "-", "*"} {
		fmt.Printf("6 %s 3 = %g\n", op, ops[op](6, 3))
	}

	cmds := []Command{{"upper", upper}, {"count", count}}
	for _, c := range cmds {
		fmt.Println(c.Name, "->", c.Run([]string{"go", "is", "fun"}))
	}

	// A function value can be reassigned, and compared only with nil.
	f := upper
	fmt.Println(f != nil, f([]string{"ok"}))

	var missing func()
	defer func() { fmt.Println("recovered:", recover()) }()
	missing() // calling a nil function value panics
}

10. Higher-order functions

A higher-order function takes functions as arguments, returns a function, or both. In Abelson and Sussman's formulation, "Procedures that manipulate procedures are called higher-order procedures", and they are a central means of abstraction because they let a program name a general method of computation independently of the particular functions involved [17]. The codewalk illustrates the idea with a strategy for the dice game Pig, which is a function returning an action, which is itself a function [3].

Since generics arrived in Go 1.18, the classic trio Map, Filter and Reduce can be written once for all element types [7]. The standard library itself is full of higher-order functions: slices.SortFunc, slices.IndexFunc and slices.ContainsFunc [13], strings.Map and strings.FieldsFunc [18], and sync.OnceValue, which "returns a function that invokes f only once and returns the value returned by f" [19].

ex09_hof/main.go 
package main

import (
	"fmt"
	"strings"
	"sync"
	"unicode"
)

// Map, Filter and Reduce take functions as arguments.
func Map[T, U any](xs []T, f func(T) U) []U {
	out := make([]U, 0, len(xs))
	for _, x := range xs {
		out = append(out, f(x))
	}
	return out
}

func Filter[T any](xs []T, keep func(T) bool) []T {
	var out []T
	for _, x := range xs {
		if keep(x) {
			out = append(out, x)
		}
	}
	return out
}

func Reduce[T, A any](xs []T, init A, f func(A, T) A) A {
	acc := init
	for _, x := range xs {
		acc = f(acc, x)
	}
	return acc
}

// Compose returns a function: it takes and returns functions.
func Compose[A, B, C any](f func(A) B, g func(B) C) func(A) C {
	return func(a A) C { return g(f(a)) }
}

// Adder returns a function specialised by its argument.
func Adder(n int) func(int) int {
	return func(x int) int { return x + n }
}

func main() {
	nums := []int{1, 2, 3, 4, 5, 6}
	evens := Filter(nums, func(n int) bool { return n%2 == 0 })
	squares := Map(evens, func(n int) int { return n * n })
	total := Reduce(squares, 0, func(acc, n int) int { return acc + n })
	fmt.Println(evens, squares, total)

	labels := Map(nums, func(n int) string { return fmt.Sprintf("#%d", n) })
	fmt.Println(strings.Join(labels, ","))

	add10ThenDouble := Compose(Adder(10), func(x int) int { return x * 2 })
	fmt.Println(add10ThenDouble(1))

	// Standard-library higher-order functions.
	rot13 := func(r rune) rune {
		switch {
		case unicode.IsLower(r):
			return 'a' + (r-'a'+13)%26
		case unicode.IsUpper(r):
			return 'A' + (r-'A'+13)%26
		}
		return r
	}
	fmt.Println(strings.Map(rot13, "Hello, Gopher"))

	config := sync.OnceValue(func() string {
		fmt.Println("(loading config once)")
		return "prod"
	})
	fmt.Println(config(), config())
}

11. Recursion

A function is recursive if it calls itself, directly or through other functions. Recursion fits naturally when the data are themselves recursive, such as trees, nested lists and grammars [14]. Every recursive function needs a base case that stops the recursion and a recursive case that moves towards it.

Abelson and Sussman distinguish the shape of the process a procedure generates from the syntax of the procedure: a chain of deferred operations is a "linear recursive process", whereas a procedure that carries its state in variables is a "linear iterative process" [17]. They note that an implementation with tail-call optimisation "will execute an iterative process in constant space, even if the iterative process is described by a recursive procedure" [17]. The Go specification makes no such requirement, so in Go an iterative process is best expressed with a loop, as fibIter does.

Deep recursion is nonetheless practical in Go because goroutine stacks are not fixed in size. The FAQ explains that "Go's run-time uses resizable, bounded stacks. A newly minted goroutine is given a few kilobytes", and the run-time "grows (and shrinks) the memory for storing the stack automatically" [2,14]. The bound is set by runtime/debug.SetMaxStack, whose "initial setting is 1 GB on 64-bit systems, 250 MB on 32-bit systems"; exceeding it crashes the program, and the facility exists "mainly for limiting the damage done by goroutines that enter an infinite recursion" [20].

ex10_recursion/main.go 
package main

import "fmt"

func factorial(n uint64) uint64 {
	if n <= 1 {
		return 1 // base case
	}
	return n * factorial(n-1) // recursive case
}

// Naive Fibonacci makes an exponential number of calls.
func fib(n int, calls *int) int {
	*calls++
	if n < 2 {
		return n
	}
	return fib(n-1, calls) + fib(n-2, calls)
}

// fibIter expresses the same computation as an iterative process.
func fibIter(n int) int {
	a, b := 0, 1
	for range n {
		a, b = b, a+b
	}
	return a
}

type Tree struct {
	Left, Right *Tree
	Val         int
}

// Insert and InOrder recurse over a recursive data structure.
func (t *Tree) Insert(v int) *Tree {
	if t == nil {
		return &Tree{Val: v}
	}
	if v < t.Val {
		t.Left = t.Left.Insert(v)
	} else {
		t.Right = t.Right.Insert(v)
	}
	return t
}

func (t *Tree) InOrder(visit func(int)) {
	if t == nil {
		return
	}
	t.Left.InOrder(visit)
	visit(t.Val)
	t.Right.InOrder(visit)
}

// Mutual recursion: package-level functions may refer to each other.
func isEven(n int) bool {
	if n == 0 {
		return true
	}
	return isOdd(n - 1)
}

func isOdd(n int) bool {
	if n == 0 {
		return false
	}
	return isEven(n - 1)
}

func depth(n int) int {
	if n == 0 {
		return 0
	}
	return 1 + depth(n-1)
}

func main() {
	fmt.Println(factorial(20))

	calls := 0
	fmt.Println(fib(25, &calls), "calls:", calls)
	fmt.Println(fibIter(25), fibIter(90))

	var root *Tree
	for _, v := range []int{5, 3, 8, 1, 4, 9} {
		root = root.Insert(v)
	}
	root.InOrder(func(v int) { fmt.Print(v, " ") })
	fmt.Println()

	fmt.Println(isEven(10), isOdd(7))

	// A million nested calls succeed because goroutine stacks grow.
	fmt.Println(depth(1_000_000))
}

12. Function types

"A function type denotes the set of all functions with the same parameter and result types. The value of an uninitialized variable of function type is nil" [5]. Parameter names are not part of the type; within a list "the names ... must either all be present or all be absent" [5].

Declaring a named function type has two benefits. It documents intent (type Middleware func(http.Handler) http.Handler reads better than the raw signature), and, because methods can be declared on any defined type that is not a pointer or interface, it allows methods on functions [10,5]. The standard library's http.HandlerFunc is the canonical example: it "is an adapter to allow the use of ordinary functions as HTTP handlers. If f is a function with the appropriate signature, HandlerFunc(f) is a Handler that calls f" [21]. Effective Go walks through the same type and comments that a function receiver is "not that different from, say, the receiver being a channel and the method sending on the channel" [10].

Assignability rules make function types convenient: a value is assignable to a variable of type T if the two have "identical underlying types but are not type parameters and at least one of V or T is not a named type" [5]. A function literal (whose type is unnamed) can therefore be assigned directly to a BinOp. Go 1.27 also allows a generic function to be assigned to any matching function type with its type arguments inferred [5,22].

	}

type Middleware func(http.Handler) http.Handler

	for i := len(ms) - 1; i >= 0; i-- {
		h = ms[i](h)
	}
	return h
}

func Tag(name string) Middleware {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			fmt.Fprintf(w, "[%s ", name)
			next.ServeHTTP(w, r)
			fmt.Fprint(w, "]")
		})
	}
}

	fmt.Fprint(w, "hello "+strings.TrimPrefix(r.URL.Path, "/"))
}

	mul := BinOp(func(a, b int) int { return a * b })

	h := Chain(http.HandlerFunc(hello), Tag("outer"), Tag("inner"))

13. Methods

"A method is a function with a receiver. A method declaration binds an identifier, the method name, to a method, and associates the method with the receiver's base type" [5]. The receiver is "an extra parameter section preceding the method name" that "must declare a single non-variadic parameter". Its type "must be a defined type T or a pointer to a defined type T"; T "cannot be a pointer or interface type and it must be declared in the same package as the method" [5]. As the FAQ notes, methods "can be defined for any sort of data, even built-in types such as plain, 'unboxed' integers. They are not restricted to structs (classes)" [2].

A method can also be used as an ordinary function value in two ways [5,14]:

  • A method value x.M binds a receiver: "The expression x is evaluated and saved during the evaluation of the method value; the saved copy is then used as the receiver in any calls, which may be executed later."
  • A method expression T.M "is a function that is callable as a regular function with the same arguments as M prefixed by an additional argument that is the receiver of the method."

Method calls on concrete types are resolved at compile time: "The only way to have dynamically dispatched methods is through an interface. Methods on a struct or any other concrete type are always resolved statically" [2]. Code Review Comments asks that the receiver be named "a reflection of its identity", typically one or two letters, and never "me", "this" or "self", because "In Go, the receiver of a method is just another parameter" [11].

13.1 Generic methods (Go 1.27)

Until Go 1.26, methods of generic types could use the receiver's type parameters but could not declare their own; the FAQ's explanation for this restriction remains on the site [2]. Go 1.27 lifts it: "a method declaration may declare its own type parameters" [22]. The specification now says that if a method declaration specifies type parameters, "the method name denotes a generic method", which, "Like a generic function, ... must be instantiated before it can be called or used as a value" [5]. The release notes add that "methods of interfaces may not declare type parameters nor can interface methods be implemented by generic methods" [22]. The Go blog motivates the change with chained transformations like NewList(0, 2, 4).Map(add(2)).Map(divideBy(2)), which read left to right instead of "inside out" [24]. The standard library's first example is (*rand.Rand).N in math/rand/v2 [22,25].

14. Method receivers

The FAQ frames the receiver choice simply: "the receiver ... behaves exactly as if it were an argument to the method. Whether to define the receiver as a value or as a pointer is the same question, then, as whether a function argument should be a value or a pointer" [2].

14.1 Value receivers

A method with a value receiver func (c Counter) … receives a copy of the value it is called on. Changes it makes to the receiver are invisible to the caller: "valueMethod is called with a copy of the caller's argument (that's the definition of passing a value), so changes it makes will be invisible to the caller" [2]. Value methods can be called on both values and pointers; for a pointer pt, "pt.Mv is equivalent to (*pt).Mv" [5]. Because a method value saves its receiver when it is evaluated, a method value built from a value-receiver method takes a snapshot of the value at that moment [5].

14.2 Pointer receivers

A method with a pointer receiver func (c *Counter) … operates on the caller's variable. "If x is addressable and &x's method set contains m, x.m() is shorthand for (&x).m()" [5]; Effective Go describes this as the language "inserting the address operator automatically" [10]. The convenience applies only to addressable operands. Map elements, for example, are not addressable, so a pointer method cannot be called on m[k] when the map stores values:

14.3 Method sets and interfaces

The receiver type determines the method set, and the method set determines interface satisfaction. "The method set of a defined type T consists of all methods declared with receiver type T. The method set of a pointer to a defined type T ... is the set of all methods declared with receiver *T or T" [5]. Effective Go summarises: "value methods can be invoked on pointers and values, but pointer methods can only be invoked on pointers" [10].

The FAQ gives the reason. If an interface holds a *T, a method call can dereference the pointer to obtain a value, "but if an interface value contains a value T, there is no safe way for a method call to obtain a pointer", and even where the compiler could take an address, "if the method modifies the value the changes will be lost in the caller" [2]. So a T value does not satisfy an interface whose methods are declared on *T:

15. Functional programming concepts

Functional programming treats computation as the evaluation of functions and avoids mutable state. John Backus's 1978 Turing Award lecture argued for programs built by combining functions with an algebra of combining forms rather than by sequences of assignments [27], and John Hughes later argued that "higher-order functions and lazy evaluation, can contribute significantly to modularity", describing them as "two new kinds of glue" for assembling programs [28].

Go is not a functional language. Pike notes that "Some concurrency and functional programming experts are disappointed that Go does not take a write-once approach to value semantics" [1], and the specification does not require tail-call elimination (Section 11). Still, several functional ideas carry over well:

ConceptMeaningGo mechanism
First-class and higher-order functionsFunctions as values; functions over functionsFunction values, function types, generics (Sections 9, 10, 12)
Pure functionsResult depends only on inputs; no side effectsA discipline, not enforced by the compiler
ImmutabilityValues are not modified after creationPass and return values, copy before changing (slices.Clone, slices.Clip) [13]; constants are compile-time only
ClosuresFunctions that capture an environmentFunction literals (Section 8)

Go's iterators are a direct application of higher-order functions. iter.Seq[V] is declared as func(yield func(V) bool); "When called as seq(yield), seq calls yield(v) for each value v in the sequence, stopping early if yield returns false" [29]. Because an iterator produces values only on demand, an infinite producer can be combined with transformers and stopped after a few values, which is the modular style Hughes attributes to lazy evaluation [28,30]. The standard library uses the same shape for functions such as slices.Values, slices.Collect and strings.FieldsFuncSeq [13,18].

ex14_fp/main.go 
package main

import (
	"fmt"
	"iter"
	"slices"
)

// Pure: the result depends only on the arguments; no side effects.
func area(w, h float64) float64 { return w * h }

// withItem returns a new slice and leaves its input untouched.
func withItem(xs []string, x string) []string {
	return append(slices.Clip(xs), x)
}

// Currying: a two-argument function as a chain of one-argument ones.
func curriedPow(base int) func(exp int) int {
	return func(exp int) int {
		r := 1
		for range exp {
			r *= base
		}
		return r
	}
}

// Naturals is an infinite, lazily evaluated sequence.
func Naturals() iter.Seq[int] {
	return func(yield func(int) bool) {
		for n := 1; ; n++ {
			if !yield(n) {
				return
			}
		}
	}
}

func Filter[T any](seq iter.Seq[T], keep func(T) bool) iter.Seq[T] {
	return func(yield func(T) bool) {
		for v := range seq {
			if keep(v) && !yield(v) {
				return
			}
		}
	}
}

func MapSeq[T, U any](seq iter.Seq[T], f func(T) U) iter.Seq[U] {
	return func(yield func(U) bool) {
		for v := range seq {
			if !yield(f(v)) {
				return
			}
		}
	}
}

func Take[T any](seq iter.Seq[T], n int) iter.Seq[T] {
	return func(yield func(T) bool) {
		if n <= 0 {
			return
		}
		i := 0
		for v := range seq {
			if !yield(v) {
				return
			}
			i++
			if i == n {
				return
			}
		}
	}
}

	fmt.Println(area(3, 4), area(3, 4)) // same input, same output

	base := []string{"a", "b"}
	next := withItem(base, "c")
	fmt.Println(base, next)

	pow2 := curriedPow(2)
	fmt.Println(pow2(10), curriedPow(3)(4))

	// Only five values are ever computed, although Naturals is infinite.
	odd := func(n int) bool { return n%2 == 1 }
	square := func(n int) int { return n * n }
	pipeline := Take(MapSeq(Filter(Naturals(), odd), square), 5)

16. Procedural programming

Procedural programming organises a program as a hierarchy of procedures operating on data, with control expressed through sequence, selection and iteration. Its discipline comes from the structured programming movement [31] and from Wirth's method of "stepwise refinement", in which a task is decomposed into sub-tasks that are refined until each is directly expressible in the language [32].

This is Go's native idiom. Pike describes Go's semantics as "generally C-like" and the language as "procedural", and calls the goroutine model "the composition of independently executing functions of otherwise regular procedural code" [1]. The FAQ likewise notes that "the CSP model fits well into a procedural language framework" [2]. In practice, procedural Go means small package-level functions with clear inputs and outputs, explicit control flow, and data passed as arguments rather than held in global variables.

ex15_procedural/main.go 
package main

import (
	"cmp"
	"fmt"
	"maps"
	"slices"
	"strings"
	"unicode"
)

const text = `Go is expressive, concise, clean, and efficient.
Go compiles quickly to machine code. Go is fun.`

// The program is decomposed top-down into small procedures,
// each with a single responsibility.
func main() {
	words := tokenize(text)
	freq := countWords(words)
	top := topN(freq, 3)
	report(top)
}

func tokenize(s string) []string {
	notLetter := func(r rune) bool { return !unicode.IsLetter(r) }
	return strings.FieldsFunc(strings.ToLower(s), notLetter)
}

func countWords(words []string) map[string]int {
	freq := make(map[string]int)
	for _, w := range words {
		freq[w]++
	}
	return freq
}

type entry struct {
	word  string
	count int
}

func topN(freq map[string]int, n int) []entry {
	var es []entry
	for _, w := range slices.Sorted(maps.Keys(freq)) {
		es = append(es, entry{w, freq[w]})
	}
	slices.SortStableFunc(es, func(a, b entry) int { return cmp.Compare(b.count, a.count) })
	return es[:min(n, len(es))]
}

func report(es []entry) {
	for i, e := range es {
		fmt.Printf("%d. %-6s %d\n", i+1, e.word, e.count)
	}
}

17. Composition and delegation

Gamma, Helm, Johnson and Vlissides summarised a lesson of object-oriented design as "Favor object composition over class inheritance", and described delegation, in which a receiving object forwards requests to a component, as a way to make composition as powerful for reuse as inheritance [33]. Go builds this preference into the language. It has no classes and no subclassing; instead, "Go does not provide the typical, type-driven notion of subclassing, but it does have the ability to 'borrow' pieces of an implementation by embedding types within a struct or interface" [10]. Pike explains the motivation: "Type hierarchies result in brittle code", so "Go therefore encourages composition over inheritance, using simple, often one-method interfaces" [1]. Interfaces are satisfied implicitly: "a type automatically satisfies any interface that specifies a subset of its methods" [2].

17.1 Struct embedding

"A field declared with a type but no explicit field name is called an embedded field" [5]. Its fields and methods are promoted: "Promoted fields act like ordinary fields of a struct", and the outer type's method set includes the promoted methods according to whether T or *T is embedded [5]. Selectors resolve names by depth, picking "the field or method at the shallowest depth", so a method declared on the outer type hides (shadows) one of the same name from an embedded type [5,10].

Embedding is not inheritance. Effective Go stresses that "when they are invoked the receiver of the method is the inner type, not the outer one" [10]. There is no virtual dispatch back to the outer type: in the example, Dog defines its own Sound, but the promoted Speak method runs with an Animal receiver and calls Animal.Sound. Code that expects the template-method pattern from class-based languages has to be restructured around interfaces or function values instead.

17.2 Explicit delegation and decoration

When only some methods should be exposed, or behaviour must be added around a call, the outer type holds the component in a named field and writes forwarding methods. Effective Go shows that this is exactly what embedding automates: without it, "we would also need to provide forwarding methods" [10]. Embedding an interface type in a struct combines both: all methods are promoted from whatever value is stored, and the outer type overrides selected ones and delegates explicitly through the field (a.Store.Set). Wrapping an io.Writer to count bytes is the same pattern applied to the standard library's most widely implemented interface [34,2].

17.3 Functional options

A function-valued alternative to configuration structs combines several ideas from this article. Pike's 2014 post defines an option type as "a function that takes one argument, the Foo we are operating on", so that "an option is implemented as a function we call to set the state of that option" [35]. Dave Cheney popularised the pattern as "functional options", in which customisation "is performed not with configuration parameters stored in a structure, but with functions" [36]. A variadic parameter of the option type keeps the zero-option call short and lets new options be added without breaking callers.

ex16_composition/main.go 
package main

import (
	"fmt"
	"io"
	"os"
	"strings"
	"time"
)

// --- Struct embedding: fields and methods are promoted.
type Logger struct{ prefix string }

func (l *Logger) Log(msg string) { fmt.Println(l.prefix + msg) }

type Service struct {
	*Logger // embedded field
	Name    string
}

// --- Embedding is not inheritance: no virtual dispatch back to the outer type.
type Animal struct{}

func (Animal) Sound() string   { return "..." }
func (a Animal) Speak() string { return "says " + a.Sound() }

type Dog struct{ Animal }

func (Dog) Sound() string { return "woof" } // shadows Animal.Sound

// --- Explicit delegation: forward selected calls to a held component.
type Store interface {
	Get(k string) (string, bool)
	Set(k, v string)
}

type MapStore struct{ m map[string]string }

func (s *MapStore) Get(k string) (string, bool) { v, ok := s.m[k]; return v, ok }
func (s *MapStore) Set(k, v string)             { s.m[k] = v }

// AuditedStore embeds the Store interface (promotion) and overrides Set.
type AuditedStore struct {
	Store
	log []string
}

func (a *AuditedStore) Set(k, v string) {
	a.log = append(a.log, "set "+k)
	a.Store.Set(k, v) // delegate to the wrapped component
}

// --- Decorating an io.Writer by composition.
type countingWriter struct {
	w io.Writer
	n int
}

func (c *countingWriter) Write(p []byte) (int, error) {
	n, err := c.w.Write(p)
	c.n += n
	return n, err
}

// --- Functional options: configuration as composable functions.
type Server struct {
	addr    string
	timeout time.Duration
	maxConn int
}

type Option func(*Server)

func WithTimeout(d time.Duration) Option { return func(s *Server) { s.timeout = d } }
func WithMaxConn(n int) Option           { return func(s *Server) { s.maxConn = n } }

func NewServer(addr string, opts ...Option) *Server {
	s := &Server{addr: addr, timeout: 30 * time.Second, maxConn: 100}
	for _, opt := range opts {
		opt(s)
	}
	return s
}

func main() {
	svc := Service{Logger: &Logger{prefix: "[svc] "}, Name: "billing"}
	svc.Log("started " + svc.Name) // promoted from *Logger

	d := Dog{}
	fmt.Println(d.Sound(), "|", d.Speak()) // Speak's receiver is the Animal

	st := &AuditedStore{Store: &MapStore{m: map[string]string{}}}
	st.Set("lang", "go")
	v, _ := st.Get("lang") // promoted, not overridden
	var _ Store = st       // *AuditedStore still satisfies Store
	fmt.Println(v, st.log)

	cw := &countingWriter{w: os.Stdout}
	io.Copy(cw, strings.NewReader("composed writers\n"))
	fmt.Println("bytes written:", cw.n)

	s := NewServer(":8080", WithTimeout(5*time.Second))
	fmt.Println(s.addr, s.timeout, s.maxConn)
}
Output 
[svc] started billing
woof | says ...
go [set lang]
composed writers
bytes written: 17
:8080 5s 100

Exercise 1 — Minimum and maximum (multiple and named results, variadic)

Write minMax(nums ...int) (lo, hi int, ok bool) that returns the smallest and largest argument, with ok false when there are no arguments. Call it with literal arguments, with no arguments, and with a spread slice.

Show solution sol01_minmax/main.go 
package main

import "fmt"

// minMax reports the smallest and largest argument; ok is false when
// no arguments are given.
func minMax(nums ...int) (lo, hi int, ok bool) {
	if len(nums) == 0 {
		return 0, 0, false
	}
	lo, hi = nums[0], nums[0]
	for _, n := range nums[1:] {
		lo, hi = min(lo, n), max(hi, n)
	}
	return lo, hi, true
}

func main() {
	fmt.Println(minMax(3, -2, 9, 4))
	fmt.Println(minMax())
	data := []int{7, 7, 1}
	fmt.Println(minMax(data...))
}
Output 
-2 9 true
0 0 false
1 7 true

The fmt.Println(minMax(...)) calls use the multi-value special case: all three results become Println's variadic arguments [5]. Naming the results documents which int is which, the use case Code Review Comments endorses [11]. min and max are built-ins since Go 1.21 [9].

Exercise 2 — Joining non-empty parts (variadic)

Write joinNonEmpty(sep string, parts ...string) string that joins only the non-empty parts. It must work with zero parts and with a spread slice.

Show solution sol02_join/main.go 
package main

import (
	"fmt"
	"strings"
)

// joinNonEmpty joins the non-empty parts with sep.
func joinNonEmpty(sep string, parts ...string) string {
	var b strings.Builder
	for _, p := range parts {
		if p == "" {
			continue
		}
		if b.Len() > 0 {
			b.WriteString(sep)
		}
		b.WriteString(p)
	}
	return b.String()
}

func main() {
	fmt.Printf("%q\n", joinNonEmpty(", ", "a", "", "b", "c"))
	fmt.Printf("%q\n", joinNonEmpty("/"))
	path := []string{"usr", "", "local", "bin"}
	fmt.Printf("%q\n", joinNonEmpty("/", path...))
}
Output 
"a, b, c"
""
"usr/local/bin"

With no arguments parts is nil, and ranging over a nil slice performs no iterations, so no special case is needed [5].

Exercise 3 — A Fibonacci generator (closures)

Write fibGen() func() int that returns a function producing successive Fibonacci numbers 0, 1, 1, 2, … on each call. Show that two generators have independent state.

Show solution sol03_fibgen/main.go 
package main

import "fmt"

// fibGen returns a generator; each call yields the next Fibonacci number.
func fibGen() func() int {
	a, b := 0, 1
	return func() int {
		r := a
		a, b = b, a+b
		return r
	}
}

func main() {
	next := fibGen()
	for range 10 {
		fmt.Print(next(), " ")
	}
	fmt.Println()
	other := fibGen() // independent state
	fmt.Println(other(), other(), next())
}

0 1 55

a and b are local to each call of fibGen, and each returned literal captures its own pair; the variables "survive as long as they are accessible" [5].

Exercise 4 — Left-to-right composition (higher-order functions, generics)

Write a generic Pipe[T any](fs ...func(T) T) func(T) T such that Pipe(f, g)(x) == g(f(x)). Use it to build a string-cleaning function from standard-library functions, and check that Pipe with no functions is the identity.

Show solution sol04_pipe/main.go 
package main

import (
	"fmt"
	"strings"
)

// Pipe composes functions left to right: Pipe(f, g)(x) == g(f(x)).
func Pipe[T any](fs ...func(T) T) func(T) T {
	return func(x T) T {
		for _, f := range fs {
			x = f(x)
		}
		return x
	}
}

func main() {
	clean := Pipe(strings.TrimSpace, strings.ToLower,
		func(s string) string { return strings.ReplaceAll(s, " ", "-") })
	fmt.Println(clean("  Hello Go World  "))

	inc := func(n int) int { return n + 1 }
	dbl := func(n int) int { return n * 2 }
	fmt.Println(Pipe(inc, dbl)(5), Pipe(dbl, inc)(5), Pipe[int]()(5))
}
Output 
hello-go-world
12 11 5

strings.TrimSpace and strings.ToLower have type func(string) string, so they can be passed directly [18]. With no functions there is nothing for type inference to work from, so the type argument is written explicitly: Pipe[int]() [5].

Exercise 5 — Towers of Hanoi (recursion, function parameters)

Write hanoi(n int, from, to, via string, move func(from, to string)) int that solves the puzzle recursively, reports each move through the callback, and returns the number of moves. Verify that the count is 2n−1.

Show solution sol05_hanoi/main.go 
package main

import "fmt"

// hanoi moves n disks from 'from' to 'to' using 'via', calling move for
// each step, and returns the number of moves made.
func hanoi(n int, from, to, via string, move func(from, to string)) int {
	if n == 0 {
		return 0
	}
	moves := hanoi(n-1, from, via, to, move)
	move(from, to)
	moves++
	return moves + hanoi(n-1, via, to, from, move)
}

func main() {
	n := hanoi(3, "A", "C", "B", func(from, to string) {
		fmt.Print(from, "→", to, " ")
	})
	fmt.Println("\nmoves:", n)

	quiet := func(string, string) {}
	for _, d := range []int{10, 20} {
		fmt.Println(d, "disks:", hanoi(d, "A", "C", "B", quiet), "moves")
	}
}
Output 
A→C A→B C→B A→C B→A B→C A→C 
moves: 7
10 disks: 1023 moves
20 disks: 1048575 moves

Passing the move action as a function separates the algorithm from what is done with each move, so a silent callback can be used for counting. The recursion depth is only n, although the number of calls grows exponentially.

Exercise 6 — Retrying an operation (function types, closures, errors)

Define type Op func() error and write Retry(attempts int, op Op) error that returns nil on the first success, or all failures combined with errors.Join. Write a helper flaky(n int) Op that fails n times before succeeding.

Show solution sol06_retry/main.go 
package main

import (
	"errors"
	"fmt"
)

type Op func() error

// Retry runs op up to attempts times and returns nil on the first
// success, or all errors joined if every attempt fails.
func Retry(attempts int, op Op) error {
	var errs []error
	for i := range attempts {
		err := op()
		if err == nil {
			return nil
		}
		errs = append(errs, fmt.Errorf("attempt %d: %w", i+1, err))
	}
	return errors.Join(errs...)
}

var ErrBusy = errors.New("busy")

// flaky returns an Op that fails n times before succeeding.
func flaky(n int) Op {
	calls := 0
	return func() error {
		calls++
		if calls <= n {
			return ErrBusy
		}
		return nil
	}
}

func main() {
	fmt.Println(Retry(3, flaky(2)))
	err := Retry(2, flaky(5))
	fmt.Println(err)
	fmt.Println(errors.Is(err, ErrBusy))
}
Output 
<nil>
attempt 1: busy
attempt 2: busy
true

errors.Join "returns an error that wraps the given errors", so errors.Is still finds ErrBusy inside the joined value [12]. flaky keeps its call count in a closure (Section 8).

Exercise 8 — Generic memoisation (higher-order functions, closures, recursion)

Write Memoize[K comparable, V any](f func(K) V) func(K) V. Show that the wrapped function is called once per distinct argument, and use it to compute the 93rd Fibonacci number recursively.

Show solution sol08_memo/main.go 
package main

import "fmt"

// Memoize wraps f with a cache keyed by its argument.
func Memoize[K comparable, V any](f func(K) V) func(K) V {
	cache := make(map[K]V)
	return func(k K) V {
		if v, ok := cache[k]; ok {
			return v
		}
		v := f(k)
		cache[k] = v
		return v
	}
}

func main() {
	calls := 0
	slowSquare := func(n int) int { calls++; return n * n }
	sq := Memoize(slowSquare)
	fmt.Println(sq(4), sq(4), sq(5), "calls:", calls)

	// Recursive memoisation: declare the variable, then assign.
	var fib func(int) uint64
	fib = Memoize(func(n int) uint64 {
		if n < 2 {
			return uint64(n)
		}
		return fib(n-1) + fib(n-2)
	})
	fmt.Println(fib(93))
}
Output 
16 16 25 calls: 2
12200160415121876738

The key type must be comparable because it is used as a map key [5]. For the recursive case, fib is declared before it is assigned so that the literal can refer to the memoised version of itself; the recursion then runs in linear rather than exponential time. F(93) is the largest Fibonacci number that fits in a uint64.

Exercise 9 — Overriding one method by delegation (composition)

Given a Greeter interface with Greet and Farewell, write a type Shouting that wraps any Greeter, upper-cases the result of Greet, counts greetings, and passes Farewell through unchanged without writing a forwarding method for it.

Show solution sol09_audit/main.go 
package main

import (
	"fmt"
	"strings"
)

type Greeter interface {
	Greet(name string) string
	Farewell(name string) string
}

type English struct{}

func (English) Greet(n string) string    { return "Hello, " + n }
func (English) Farewell(n string) string { return "Goodbye, " + n }

// Shouting embeds a Greeter, overrides Greet and inherits Farewell.
type Shouting struct {
	Greeter
	calls int
}

func (s *Shouting) Greet(n string) string {
	s.calls++
	return strings.ToUpper(s.Greeter.Greet(n)) + "!"
}

func main() {
	var g Greeter = &Shouting{Greeter: English{}}
	fmt.Println(g.Greet("gopher"))
	fmt.Println(g.Farewell("gopher"))
	fmt.Println(g.Greet("again"), g.(*Shouting).calls)
}
Output 
HELLO, GOPHER!
Goodbye, gopher
HELLO, AGAIN! 2

Embedding the interface promotes Farewell automatically [5,10], while Shouting.Greet, at depth zero, shadows the promoted Greet and delegates to it explicitly through the field s.Greeter. The pointer receiver on Greet is needed so that calls is updated, which also means that only *Shouting satisfies Greeter [5,2].

Exercise 10 — Lazy primes (iterators, functional style)

Using iter.Seq, write an infinite sequence From(n) and a generic Filter, and print the squares of the first eight primes. The producer must stop when the consumer stops.

Show solution sol10_primes/main.go 
package main

import (
	"fmt"
	"iter"
)

func From(n int) iter.Seq[int] {
	return func(yield func(int) bool) {
		for ; yield(n); n++ {
		}
	}
}

func Filter[T any](seq iter.Seq[T], keep func(T) bool) iter.Seq[T] {
	return func(yield func(T) bool) {
		for v := range seq {
			if keep(v) && !yield(v) {
				return
			}
		}
	}
}

func isPrime(n int) bool {
	if n < 2 {
		return false
	}
	for d := 2; d*d <= n; d++ {
		if n%d == 0 {
			return false
		}
	}
	return true
}

func main() {
	count := 0
	for p := range Filter(From(2), isPrime) {
		fmt.Print(p*p, " ")
		count++
		if count == 8 {
			break // stops the infinite producer
		}
	}
	fmt.Println()
}
Output 
4 9 25 49 121 169 289 361

When the for loop executes break, the next call to yield returns false, Filter returns, and From's loop condition fails, so no further values are computed [29,30].

Exercise 11 — Generic methods (Go 1.27)

Give a generic List[E] type the methods Filter, Map[R any] and Fold[A any], and use them in a left-to-right chain. Which of the three needs Go 1.27, and why?

Show solution sol11_filter/main.go 
package main

import (
	"fmt"
	"strings"
)

type List[E any] struct{ elems []E }

func NewList[E any](elems ...E) List[E] { return List[E]{elems} }

func (l List[E]) Filter(keep func(E) bool) List[E] {
	var out []E
	for _, e := range l.elems {
		if keep(e) {
			out = append(out, e)
		}
	}
	return List[E]{out}
}

// Map is a generic method (Go 1.27+): it declares its own type parameter R.
func (l List[E]) Map[R any](f func(E) R) List[R] {
	out := make([]R, 0, len(l.elems))
	for _, e := range l.elems {
		out = append(out, f(e))
	}
	return List[R]{out}
}

// Fold is generic in the accumulator type A.
func (l List[E]) Fold[A any](init A, f func(A, E) A) A {
	acc := init
	for _, e := range l.elems {
		acc = f(acc, e)
	}
	return acc
}

func main() {
	words := NewList("go", "is", "a", "small", "language")
	lengths := words.
		Filter(func(s string) bool { return len(s) > 1 }).
		Map(func(s string) int { return len(s) })
	fmt.Println(lengths.elems)

	total := lengths.Fold(0, func(acc, n int) int { return acc + n })
	joined := words.Fold("", func(acc string, s string) string {
		return acc + strings.ToUpper(s[:1])
	})
	fmt.Println(total, joined)
}
Output 
[2 2 5 8]
17 GIASL

Filter uses only the receiver's type parameter E and would compile with any Go version since 1.18. Map and Fold introduce type parameters of their own (R, A) and are therefore generic methods, which require Go 1.27 [22,5]. Before 1.27 they had to be package-level generic functions, with the "inside out" call syntax the Go blog describes [24].

Exercise 12 — Choosing receivers (value vs pointer)

Write an Account type with Deposit, Withdraw (which returns a wrapped sentinel error on insufficient funds) and Balance, and a Money type with a String method. Justify each receiver choice.

Show solution sol12_bank/main.go 
package main

import (
	"errors"
	"fmt"
)

var ErrInsufficient = errors.New("insufficient funds")

type Account struct {
	Owner   string
	balance int
}

// Balance does not modify the receiver, but uses a pointer receiver
// for consistency with the mutating methods.
func (a *Account) Balance() int { return a.balance }

func (a *Account) Deposit(n int) { a.balance += n }

func (a *Account) Withdraw(n int) error {
	if n > a.balance {
		return fmt.Errorf("withdraw %d from %s: %w", n, a.Owner, ErrInsufficient)
	}
	a.balance -= n
	return nil
}

type Money int

// Money is a small immutable value, so a value receiver fits.
func (m Money) String() string { return fmt.Sprintf("$%d.%02d", m/100, m%100) }

func main() {
	acct := &Account{Owner: "ana"}
	acct.Deposit(5000)
	if err := acct.Withdraw(7000); err != nil {
		fmt.Println(err, errors.Is(err, ErrInsufficient))
	}
	_ = acct.Withdraw(1250)
	fmt.Println(Money(acct.Balance()))
}
Output 
withdraw 7000 from ana: insufficient funds true
$37.50

Deposit and Withdraw mutate the account, so their receivers must be pointers; Balance does not, but uses a pointer too because Code Review Comments advises "Don't mix receiver types" [11]. Money is a basic type with no mutable state, the case where "a value receiver makes sense" [11].
