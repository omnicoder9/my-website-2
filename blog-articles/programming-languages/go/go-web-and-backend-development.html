Web and Backend Development in Go

Building HTTP servers and APIs with the standard library: routing, middleware, identity, security controls, observability, real-time delivery, background work, caching and the move to microservices.

Examples verified with Go 1.27.0 and Go 1.26.10 on linux/amd64Requires Go 1.26 or laterAll code passes go vet; all tests pass with -race

Abstract

Go’s standard library contains a production-grade HTTP server, a pattern-matching router (since Go 1.22), structured logging, cryptography and test helpers. Most backend services can therefore be built from net/http plus a handful of focused modules. This article builds one realistic service, a task-tracking REST API, and uses it to explain each concern a backend engineer meets: server configuration and shutdown, routing, REST semantics, middleware, validation, RFC 9457 error responses, password authentication, cookie sessions, JWT bearer tokens, OAuth 2.0 and OpenID Connect, role-based and object-level authorization, rate limiting, CORS, versioning, OpenAPI documentation, logging, metrics, WebSockets, Server-Sent Events, file uploads, background jobs, caching and microservice communication. Each claim is tied to the governing specification or official documentation, every program compiles, the test suites pass under the race detector, and eleven exercises with worked, tested solutions close the article.

How to run the examples. All listings belong to one module, example.com/gw, laid out as below. Shared packages live under internal/; runnable programs live under cmd/; exercise solutions live under exercises/. Clone the layout, run go mod tidy, then go test -race ./.... The REST API starts with JWT_KEY_HEX=$(openssl rand -hex 32) go run ./cmd/tasks. Outputs shown are from real runs; request IDs and timestamps will differ on your machine.

Third-party modules are used only where the standard library has no equivalent: golang.org/x/time/rate, golang.org/x/crypto/argon2, golang.org/x/sync/singleflight, golang.org/x/oauth2, github.com/coreos/go-oidc/v3, github.com/golang-jwt/jwt/v5, github.com/coder/websocket and github.com/prometheus/client_golang.

1The net/http model

Everything in a Go web server reduces to one interface. “A Handler responds to an HTTP request” through a single method, ServeHTTP(ResponseWriter, *Request), and the HandlerFunc type is an adapter that lets an ordinary function with that signature serve as a handler [1]. Routers, middleware and whole applications are just handlers that call other handlers.

Four rules from the package documentation shape every handler you write [1]:

  • Concurrency. Server.Serve accepts connections and creates “a new service goroutine for each”. Handlers therefore run concurrently, and any state they share must be synchronized.
  • Headers before body. Changing the header map after calling WriteHeader or Write has no effect (except for 1xx responses and trailers). If a handler calls Write without WriteHeader, the status is 200, and if no Content-Type is set the server sniffs one from the first bytes.
  • Do not modify the request. Apart from reading the body, handlers should not modify the *Request they receive; to attach values, derive a new request with r.WithContext.
  • Request context. r.Context() is cancelled when the client’s connection closes, when the request is cancelled (HTTP/2), or when ServeHTTP returns. Pass it to every database call and outbound request so abandoned work stops.

The context package carries “deadlines, cancellation signals, and other request-scoped values across API boundaries and between processes” [2]. The Go team’s guidance is that the context should be the first parameter of each function on the call path of an incoming request, and that context values are for request-scoped data, not optional function parameters [2,3].

The same server speaks HTTP/1.1 and, over TLS, HTTP/2 transparently [1]. Go 1.24 added Server.Protocols to choose the protocols explicitly, including unencrypted HTTP/2 [4].

2HTTP server development

http.ListenAndServe(addr, handler) is convenient but unsuitable for production because it creates a server with no timeouts and gives you no handle with which to shut it down. The program below is the shape every service in this article follows: an explicit http.Server, structured logs, timeouts and graceful shutdown.

Timeouts

Every timeout field on http.Server defaults to zero, and “a zero or negative value means there will be no timeout” [1]. A server without timeouts lets a client hold a connection, and its goroutine and buffers, indefinitely by sending a request one byte at a time; this is the Slowloris attack, and it is why Valsorda calls setting timeouts essential for any Go server exposed to the internet [5].

Server-wide timeouts are blunt instruments: a streaming endpoint (Section 20) needs no write deadline, an upload endpoint needs a long read deadline. http.ResponseController lets an individual handler change its own read and write deadlines [1], and http.TimeoutHandler bounds a handler’s run time, replying 503 if it is exceeded [1].

Graceful shutdown

Server.Shutdown “gracefully shuts down the server without interrupting any active connections”: it closes the listeners, then idle connections, then waits for active connections to become idle; ListenAndServe returns ErrServerClosed immediately [1]. It does not wait for hijacked connections such as WebSockets, which must be tracked separately (for example with RegisterOnShutdown) [1]. signal.NotifyContext returns a context that is cancelled when one of the listed signals arrives [6]. Kubernetes stops a container by sending SIGTERM, waits for the termination grace period (30 seconds by default), and only then sends SIGKILL [7], so the shutdown timeout should fit inside that window.

3Request routing

Before Go 1.22, http.ServeMux matched only path prefixes, so most projects used third-party routers. Go 1.22 extended the patterns with methods and wildcards [8,9]. A pattern has the form [METHOD ][HOST]/[PATH] [1]:

PatternMatches [1,9]
GET /tasks/{id}GET or HEAD of /tasks/ plus exactly one segment; r.PathValue("id") returns it.
/files/{path...}Any method; the final wildcard captures the remainder of the path, slashes included.
/files/Any path beginning with /files/ (a trailing slash makes a prefix pattern).
GET /{$}Only / itself; {$} anchors the end of the path.
api.example.com/Any path, but only for that host.

Three properties make the new mux safe to use as an application router [1,9]:

  • Precedence by specificity. When two patterns match, the more specific one wins, independent of registration order: /tasks/new beats /tasks/{id}. If neither is more specific, for example /tasks/{id} versus /{resource}/latest, the patterns conflict and registration panics, so ambiguity is caught at start-up rather than in production.
  • Methods. A GET pattern also matches HEAD. If the path matches some pattern but the method matches none, the mux replies 405 Method Not Allowed with an Allow header, as HTTP requires [10].
  • Introspection. After routing, r.Pattern holds the pattern that matched [1]. Section 18 uses it as a low-cardinality metric label.

The tasks API registers its routes like this. Authentication and authorization are attached per route, inside the mux, for a reason explained in Section 5.

Compatibility. The new syntax changed the meaning of some existing patterns (for example, ones containing braces). Modules that declare a go version below 1.22 keep the old behaviour, and GODEBUG=httpmuxgo121=1 restores it explicitly [1,8].

Exercise 1 asks you to predict which of five overlapping patterns serves each of six requests; the solution is a table-driven test against the real mux.

4REST API development

REST is an architectural style defined in Fielding’s dissertation as a set of constraints: client–server, stateless interaction, cacheable responses, a uniform interface, a layered system, and optional code-on-demand [11]. The uniform interface is the part that shapes API design day to day: resources are identified by URIs, manipulated through representations, messages are self-descriptive, and hypermedia drives application state [11]. In practice a “REST API” means using HTTP’s own semantics, its methods, status codes, headers and caching, rather than tunnelling a private protocol through POST.

HTTP defines two properties that clients and intermediaries rely on. A safe method is essentially read-only; an idempotent method has the same intended effect on the server whether it is sent once or many times, so it may be retried automatically after a network failure [10].

Reading and writing JSON

JSON exchanged between systems that are not part of a closed ecosystem must be encoded as UTF-8 [14]. encoding/json is permissive by default in ways that matter for APIs [15]: unknown object keys are silently ignored, and keys match struct fields case-insensitively, so {"TITLE": "x"} populates Title. A decoder therefore needs explicit guards. DisallowUnknownFields turns unknown keys into errors [15], and http.MaxBytesReader “is similar to io.LimitReader but is intended for limiting the size of incoming request bodies”, returning a *MaxBytesError once the limit is exceeded [1]. Unbounded bodies are an instance of OWASP’s API4:2023, Unrestricted Resource Consumption [16].

The helpers map each failure to the right status, use errors.As to inspect wrapped error types [17], and reject a second JSON value after the first (dec.More()), which would otherwise be ignored.

Pagination

Collections must be bounded. Offset pagination (?page=7) is simple but skips or repeats items when rows are inserted while a client pages, and the database must still walk past every skipped row. Cursor pagination returns an opaque token that encodes the position of the last item served. The tasks API uses sortable IDs so the cursor is simply the last ID, base64url-encoded so clients treat it as opaque, and it advertises the next page both in the body and in a Link header with the registered next relation [18].

Conditional requests and optimistic concurrency

An entity tag (ETag) is an opaque validator for a representation [10]. It serves two purposes. On reads, a client that sends If-None-Match with the tag it holds gets 304 Not Modified and no body if nothing changed. On writes, a client that sends If-Match gets 412 Precondition Failed if the resource changed since it read it, which prevents the “lost update” where two clients overwrite each other [10]. If-Match uses the strong comparison and If-None-Match the weak comparison [10]. A server may insist on conditional writes with 428 Precondition Required, which RFC 6585 introduced for exactly this lost-update problem [13].

The store re-checks the version inside its lock, so two requests that both pass the If-Match check cannot both succeed; the loser gets 412. This is optimistic concurrency control: no lock is held between the client’s read and its write.

5Middleware

Middleware is a function that takes a handler and returns a handler, so it can act before and after the wrapped handler runs. Because http.Handler is the only contract, middleware from any library composes with any other. The Chain helper applies a list so that the first element is the outermost layer.

Points worth noting in this code:

  • Context keys. Values are stored under an unexported key type so no other package can collide with them; the context documentation recommends exactly this [2].
  • Untrusted input. A client-supplied X-Request-ID is accepted only if it matches a strict pattern; otherwise a client could inject newlines or megabytes into every log line. crypto/rand.Text, added in Go 1.24, returns a random string with at least 128 bits of entropy [19,4].
  • Panics. net/http already recovers a panicking handler, logs the stack trace and closes the connection, and treats a panic with http.ErrAbortHandler as a deliberate abort [1]. A recovery middleware adds a proper 500 response body and a structured log entry with the request ID. Neither protects goroutines that a handler starts itself.
  • Wrapping the writer. A response recorder hides optional interfaces such as http.Flusher and http.Hijacker. http.ResponseController finds them through an Unwrap method [1], so providing Unwrap keeps Server-Sent Events and WebSockets working behind middleware.
  • Security headers. X-Content-Type-Options: nosniff, a restrictive Content-Security-Policy with frame-ancestors 'none', and Cache-Control: no-store for sensitive responses are recommended defaults for APIs [20].

Ordering, and a subtle interaction with routing

Order matters. Request ID must be outermost so every inner layer can log it; recovery must be outside anything that might panic; CORS must answer preflight requests before authentication rejects them, because a CORS preflight request is sent without credentials [21,22]. Less obviously, ServeMux records the matched pattern in r.Pattern on the *Request it receives [1]. If a middleware between the logger and the mux calls r.WithContext, it creates a new request, and the logger’s copy never sees the pattern. That is why the tasks API attaches authentication per route, inside the mux, where the principal can be added to the context without hiding the route from the outer layers. The integration test in Section 25 checks that metrics are labelled route="GET /v1/tasks".

6Input validation

OWASP distinguishes syntactic validation (correct form: a date is a date) from semantic validation (correct meaning: the start date precedes the end date), recommends allow-lists over deny-lists, and stresses that validation must happen on the server, because client-side checks can be bypassed [23]. It also notes that validation reduces attack surface but is not a substitute for context-specific defences such as parameterized queries and output encoding [23].

Validation in Go is ordinary code. Struct-tag validators exist, but explicit checks are easy to read, easy to test, and can express cross-field rules. The validator below collects every failure so a client can fix all fields in one round trip.

Three details are easy to get wrong:

  • Characters versus bytes. len(s) counts bytes. A 200-character limit should use utf8.RuneCountInString, or a user writing in Greek or Japanese hits it at a fraction of the intended length.
  • Anchors. An allow-list regular expression without ^ and $ matches any input that merely contains a valid substring. Go’s regexp uses RE2 syntax and is “guaranteed to run in time linear in the size of the input”, so catastrophic backtracking cannot occur [24]; the length limit should still be checked first.
  • Normalize, then validate. The create handler trims whitespace before storing, and the blank check uses the trimmed value, so " " is rejected.

7Error responses

RFC 9457, Problem Details for HTTP APIs, defines a standard JSON body for errors and obsoletes RFC 7807 [25]. Its members are [25]:

MemberMeaning
typeA URI identifying the problem type; when absent it is "about:blank", in which case title should be the HTTP status phrase.
titleA short, human-readable summary of the problem type that does not change between occurrences.
statusThe HTTP status code, repeated for convenience.
detailAn explanation specific to this occurrence.
instanceA URI identifying this specific occurrence.
extensionsAdditional members such as errors or request_id; clients must ignore extensions they do not recognize.

The media type is application/problem+json [25]. The api.WriteProblem function in Section 4 implements this and fills in the request ID from the response header so a user’s bug report can be matched to a log line.

Error bodies must not leak internals. OWASP advises returning a generic message for unexpected errors while logging the details server-side, because stack traces, SQL fragments and file paths help attackers [26]. The tasks API follows a simple rule: messages for 4xx describe what the client can fix; every 5xx says “internal error”, and the specifics go to the log keyed by request ID.

One gap. The mux writes its own plain-text 404 and 405 responses. To make those problem documents too, register a catch-all / handler that returns a problem 404, or wrap the mux in a writer that rewrites plain-text error responses. Many teams accept the default for 405.

8Authentication

Authentication establishes who the caller is; authorization (Section 12) decides what they may do. The two are separate layers in the code, and keeping them separate is what lets the same authorization rules serve cookie-authenticated browsers and token-authenticated API clients. In this article both mechanisms produce the same value, an auth.Principal, which authentication middleware stores in the request context.

Storing passwords

Passwords must be stored with a slow, salted, purpose-built password hashing function, never with a fast hash such as SHA-256. OWASP recommends Argon2id first, with a minimum configuration of 19 MiB of memory, two iterations and one degree of parallelism, and lists scrypt, bcrypt and PBKDF2 as alternatives for when Argon2id is unavailable [27]. Argon2 is specified in RFC 9106, which makes Argon2id the primary variant [28]; Go’s implementation is argon2.IDKey [29].

The encoded string stores the parameters next to the hash, so you can raise the cost later and re-hash each user’s password the next time they log in. The comparison uses subtle.ConstantTimeCompare, whose running time depends on the length of its inputs but not their contents [30].

Password policy

NIST SP 800-63B-4 (2025) requires passwords used as the only authentication factor to be at least 15 characters long, allows a minimum of 8 when the password is part of multi-factor authentication, says verifiers should permit at least 64 characters, and says they shall not impose composition rules (such as requiring mixtures of character types) or require periodic changes [31]. It also requires checking new passwords against a blocklist of commonly used or compromised values, and requires verifiers to limit consecutive failed authentication attempts [31]. Exercise 3 implements these length rules.

The login endpoint

Two defences are visible here. First, the handler returns one message for “no such user” and “wrong password”, and hashes against a dummy value when the user does not exist, so neither the response body nor its timing reveals which accounts exist; OWASP calls out both channels of user enumeration [32]. Second, a per-IP limiter far stricter than the global one throttles password guessing (Section 13).

The response is a short-lived bearer token. Its shape (access_token, token_type, expires_in) mirrors the OAuth 2.0 token response [33] so that clients can later switch to a real authorization server without changes. This endpoint is not the OAuth “resource owner password credentials” grant, which the OAuth security BCP says must not be used [34]; it is a first-party login for the API’s own clients.

9Session management

For browser applications, a server-side session referenced by a cookie remains the simplest secure design. The cookie holds only a random, meaningless identifier; everything else lives on the server, so logging out or revoking access takes effect immediately. OWASP’s session guidance can be summarized as follows [35]:

  • Session IDs must be unpredictable, with at least 64 bits of entropy, and must not encode meaning. rand.Text provides 128 bits [19].
  • Issue a new session ID at login and at every privilege change; reusing a pre-login ID enables session fixation.
  • Enforce both an idle timeout and an absolute timeout on the server, and invalidate the session server-side at logout.
  • Set the cookie’s Secure, HttpOnly and SameSite attributes.

The cookie attributes each close a specific hole. Secure restricts the cookie to secure channels and HttpOnly hides it from scripts [36], so an XSS bug cannot read it. SameSite=Lax stops the browser sending it on cross-site subrequests such as a form POST from another site [37]. The __Host- name prefix is accepted by browsers only if the cookie is Secure, has Path=/ and has no Domain attribute, which stops a compromised or malicious subdomain from overwriting it [37].

Cross-site request forgery

Cookies are sent automatically, so any site can make the victim’s browser submit a state-changing request to yours. OWASP recommends defence in depth: synchronizer tokens or equivalent, SameSite cookies, and verifying the request’s origin with standard headers such as Origin and Sec-Fetch-Site [38]. Go 1.25 added http.CrossOriginProtection, which rejects non-safe cross-origin browser requests using Sec-Fetch-Site, falling back to comparing Origin with Host [39,1]. It always allows GET, HEAD and OPTIONS, so those methods must never change state [1].

The page is rendered with html/template, which escapes data contextually (HTML body, attribute, JavaScript, URL), so a user name containing <script> is displayed rather than executed [40]. The login handler drops any existing session before creating a new one, and redirects with 303 so that reloading the page does not resubmit the form.

10JWT

A JSON Web Token is “a compact, URL-safe means of representing claims to be transferred between two parties” [41]. A signed JWT uses the JWS compact serialization: three base64url-encoded parts, header, payload and signature, joined by dots [42]. The registered claims include iss (issuer), sub (subject), aud (audience), exp (expiry), nbf (not before), iat (issued at) and jti (token ID); for time claims, implementations may allow a small leeway, usually no more than a few minutes, for clock skew [41].

A signed JWT is signed, not encrypted: anyone holding it can base64url-decode the payload [42]. Never put secrets in it. The JWT best-current-practice RFC lists the mistakes that have produced real vulnerabilities [43]:

  • Trusting the token’s own alg. Libraries must let the application specify the allowed algorithms, and the application must reject anything else, including none. Otherwise an attacker can strip the signature or switch an RSA public key into an HMAC secret (“algorithm confusion”).
  • Weak keys. HMAC keys must have sufficient entropy; human-memorable passwords must not be used.
  • Skipping claim checks. Validate the issuer and audience so a token minted for one service cannot be replayed against another.

golang-jwt/jwt/v5 provides parser options for each of these checks: WithValidMethods, WithIssuer, WithAudience, WithExpirationRequired and WithLeeway [44]. The middleware implements the bearer-token usage of RFC 6750: the token arrives in Authorization: Bearer …, and a rejected token gets 401 with a WWW-Authenticate header carrying error="invalid_token" [45]. JWTs or sessions?

A self-contained token can be verified without a database lookup, which suits APIs called by many services. The price is revocation: a valid JWT remains valid until it expires. Keep access tokens short-lived (minutes), pair them with refresh tokens if needed, and keep a denylist of jti values for emergencies. In browsers, storing tokens in localStorage exposes them to any script on the page; OWASP advises against keeping sensitive data in web storage for that reason [35]. For a first-party browser application, an HttpOnly session cookie (Section 9) is usually the better choice.

11OAuth 2.0 and OpenID Connect

OAuth 2.0 is an authorization framework: it lets a third-party application obtain limited access to an HTTP service on behalf of a resource owner, without seeing the owner’s password [33]. It defines four roles: the resource owner (the user), the client (your application), the authorization server (which issues tokens) and the resource server (the API) [33]. OpenID Connect (OIDC) is “a simple identity layer on top of the OAuth 2.0 protocol”: it adds an ID token, a JWT that tells the client who the user is [46].

The authorization code flow with PKCE

The current security guidance is RFC 9700, the OAuth 2.0 Security Best Current Practice [34]. Its key rules for a web application are:

  • Use the authorization code grant. The implicit grant should not be used, and the resource owner password credentials grant must not be used [34].
  • Use PKCE. Public clients must use it and it is recommended for confidential clients; it binds the code to the client that started the flow [34,47]. The client sends code_challenge = BASE64URL(SHA256(code_verifier)) with the authorization request and the verifier with the token request [47].
  • Prevent CSRF on the redirect with state (or PKCE, or the OIDC nonce) [33,34].
  • Authorization servers must compare redirect URIs by exact string matching [34].

Validating the ID token

OIDC Core specifies how a client validates an ID token: the issuer must match the provider, the audience must contain the client’s client_id, the signature must verify with the provider’s keys, the token must not be expired, and the nonce must equal the value the client sent [46]. Discovery publishes the provider’s endpoints and key set at /.well-known/openid-configuration [48]. go-oidc performs discovery and the signature, issuer, audience and expiry checks; its documentation states that Verify does not check the nonce, which is the caller’s responsibility [49]. golang.org/x/oauth2 supplies PKCE helpers: GenerateVerifier, S256ChallengeOption and VerifierOption [50].

OIDC Core states that sub and iss, used together, are the only claims a relying party can rely on as a stable identifier for the user [46]. Email addresses change and can be reassigned, so link accounts by (iss, sub). After the callback, create an ordinary server-side session as in Section 9; there is rarely a reason to keep the provider’s tokens in the browser.

Service-to-service. When no user is involved, a backend obtains tokens with the client credentials grant [33], which golang.org/x/oauth2/clientcredentials implements [50]. The API then validates those tokens exactly as in Section 10, typically with asymmetric keys fetched from the authorization server.

12Authorization

Authorization failures dominate API security incidents. The first entry of the OWASP API Security Top 10 (2023) is Broken Object Level Authorization (BOLA): an endpoint receives an object ID and fails to check that the caller may access that object. The fifth is Broken Function Level Authorization: a caller reaches an operation their role should not reach [16]. The two need different checks.

Function level: roles and permissions

Role-based access control maps roles to permissions and checks permissions, not roles, in code. OWASP recommends denying by default and enforcing authorization on every request on the server side [51].

13Rate limiting

Rate limiting protects a service from abusive clients, runaway scripts and brute-force attacks, and stops one tenant from consuming capacity that others need. Google’s SRE book recommends per-customer limits and argues that a service should reject excess work cheaply and early rather than degrade for everyone [52]. OWASP lists missing rate limits under API4:2023, Unrestricted Resource Consumption [16].

golang.org/x/time/rate implements a token bucket “of size b, initially full and refilled at rate r tokens per second”, with Allow, Reserve and Wait methods for rejecting, scheduling or delaying events [53]. The middleware keeps one limiter per client key and evicts idle clients so memory stays bounded.

A rejected request gets 429 Too Many Requests, which may include Retry-After [13]; Retry-After is defined by HTTP Semantics and may be a delay in seconds [10]. Using Reserve and then cancelling the reservation gives the exact wait without consuming a token [53]. 14CORS

Browsers apply the same-origin policy: a script from one origin (scheme, host and port) may send requests to another origin, but may not read the responses unless that origin allows it. Cross-Origin Resource Sharing is the protocol, defined in the WHATWG Fetch standard, by which a server grants that permission [21,22]. It is important to understand what CORS is not: it relaxes a browser restriction and does nothing to stop non-browser clients, so it is never an access-control mechanism for your API [22].

Requests that use only “simple” methods and headers are sent directly, and the browser checks Access-Control-Allow-Origin on the response. Anything else, such as a PUT, a JSON content type or an Authorization header, triggers a preflight: an OPTIONS request carrying Access-Control-Request-Method and Access-Control-Request-Headers, which the server answers with the methods and headers it allows and, optionally, how long the answer may be cached [21]. Rules a server must follow [21,22]:

  • When credentials (cookies or HTTP authentication) are allowed, Access-Control-Allow-Origin must name the exact origin; the wildcard * is not accepted together with credentials.
  • When the response depends on the Origin request header, send Vary: Origin so shared caches do not serve one origin’s response to another.
  • Scripts can read only CORS-safelisted response headers unless others are listed in Access-Control-Expose-Headers, which is why the API exposes ETag, Location and Link.

Never reflect the request’s Origin back without checking it against an allow-list; that grants every website on the internet the right to read your users’ data with their cookies.

16API documentation

The OpenAPI Specification “defines a standard, programming language-agnostic interface description for HTTP APIs” that lets humans and computers discover a service’s capabilities without access to its source code [60]. Version 3.1 aligned its Schema Object with JSON Schema draft 2020-12 [60,61], so request and response bodies are described in standard JSON Schema. From one document you can render reference documentation, generate clients and server stubs, and validate traffic in tests.

Some details reflect the Go code exactly. TaskInput uses unevaluatedProperties: false because the decoder calls DisallowUnknownFields; in JSON Schema 2020-12, unevaluatedProperties sees properties declared in allOf subschemas, which additionalProperties does not [61]. Server-assigned fields are readOnly, error responses share one Problem schema, and the deprecated v1 operation is marked deprecated: true [60].

The spec is compiled into the binary with //go:embed [62] and served at GET /openapi.yaml (see Routes in Section 3), so documentation and code ship together. Two practices keep the document honest: validate it in CI (this one passes openapi-spec-validator), and test the server against it, either by generating types from the spec (“design-first”) or by generating the spec from annotated code (“code-first”). Design-first makes the contract the review artefact, which is usually the better default for public APIs.

17Logging

log/slog, added in Go 1.21, provides structured logging: records with a message, a level and key–value attributes, emitted by a pluggable Handler [63,64]. The standard library includes TextHandler and JSONHandler; LogAttrs is a more efficient form that accepts only typed attributes; and slog.SetDefault also redirects the older log package [63]. Structured records can be queried by field (“all 5xx for route X in the last hour”) instead of grepped.

OWASP’s logging guidance is the checklist to follow [65]:

  • Log security events: authentication successes and failures, authorization failures, input validation failures, and errors.
  • Never log passwords, session identifiers, access tokens, encryption keys or sensitive personal data. Logging the Authorization header logs a credential.
  • Prevent log injection by encoding untrusted data. A JSON handler escapes newlines and quotes, which is one reason to prefer it in production.
  • Correlate with an identifier that follows the request across components; here, the request ID, which also appears in error responses.

Use levels deliberately: Error for conditions that need a human, Warn for degraded operation such as retries, Info for one line per request, Debug off in production. A custom slog.Handler can attach the request ID from the context automatically, so application code calls log.InfoContext(ctx, ...) without repeating it.

18Metrics and tracing

Logs describe individual events; metrics aggregate. Google’s SRE book names four golden signals for a user-facing system: latency, traffic, errors and saturation [66]. Wilkie’s RED method narrows this for request-driven services to rate, errors and duration per endpoint [67]. Prometheus, the de facto open-source metrics system, defines four metric types: counters, which only increase (or reset on restart); gauges, which go up and down; histograms, which count observations in configurable buckets; and summaries [68].

Prometheus naming conventions ask for base units (seconds, bytes), a _total suffix on counters, and caution with labels, because “every unique combination of key-value label pairs represents a new time series” [69]. Labelling by raw path would create one series per task ID; labelling by r.Pattern creates one per route. promauto.With(reg) registers collectors on an explicit registry, so tests can create isolated registries [70].

Distributed tracing

When one user request crosses several services, a trace shows where the time went. The W3C Trace Context recommendation standardizes the traceparent header, which carries a version, a 16-byte trace ID, an 8-byte parent span ID and trace flags, so that vendors interoperate [71]. OpenTelemetry provides the Go SDK and instrumentation for net/http servers and clients that create spans and propagate the header automatically [72]. Section 24’s gateway forwards traceparent by hand to show the mechanism; in production, use the OpenTelemetry instrumentation.

19WebSockets

The WebSocket protocol provides full-duplex, message-oriented communication over a single TCP connection [73]. It starts as an HTTP/1.1 request with Upgrade: websocket, Connection: Upgrade, a random Sec-WebSocket-Key and Sec-WebSocket-Version: 13; the server answers 101 Switching Protocols with Sec-WebSocket-Accept, a hash of the key that proves it understood the handshake [73]. After that, both sides exchange frames: text, binary, ping, pong and close [73].

The standard library does not include a WebSocket server. github.com/coder/websocket is a small, context-aware implementation; its Accept performs the handshake and by default rejects cross-origin requests, with OriginPatterns to allow specific origins [74]. That check matters: the same-origin policy does not prevent a page on another site from opening a WebSocket to your server, and RFC 6455 tells servers to use the Origin header to reject unauthorized cross-origin connections from browsers [73].

  • Limits. SetReadLimit caps the size of an incoming message [74]; without a cap a client can make the server buffer arbitrarily large messages.
  • Liveness. A peer that vanishes without a close frame (a laptop lid closing) leaves a half-open TCP connection. Periodic pings detect it [73]. In coder/websocket, Ping waits for the pong to be read by a concurrent reader, which is one reason the handler always runs a reader goroutine [74].
  • Backpressure. Writes have a deadline, and a client too slow to keep up is disconnected by the broker rather than allowed to stall the publisher (see Broker.Publish below).
  • Authentication. The browser WebSocket constructor accepts only a URL and subprotocols, so a script cannot add an Authorization header [75]. Authenticate the upgrade request with the session cookie plus the origin check, or with a short-lived single-use ticket obtained over an authenticated API call.
  • Shutdown. Server.Shutdown does not wait for hijacked connections [1]; close WebSockets yourself, ideally with close code 1001 (“going away”) [73], from a RegisterOnShutdown hook.

20Server-Sent Events

When data flows only from server to client (notifications, progress, live dashboards), Server-Sent Events are simpler than WebSockets. They are defined in the WHATWG HTML standard: the server sends a long-lived text/event-stream response made of fields (data, event, id, retry) terminated by a blank line, and the browser’s EventSource parses it [76]. Lines starting with a colon are comments; several data lines in one event are joined with newlines; and the stream must be UTF-8 [76]. The browser reconnects automatically after a dropped connection, waiting the retry interval, and sends the last id it saw in a Last-Event-ID request header so the server can resume [76].

Both transports in the example are fed by one broker. Subscribing returns, under the same lock, any messages the client missed, so a reconnecting client sees no gap and no duplicates.

The handler uses http.ResponseController to flush after each event and to lift the server’s write deadline for this one response [1]; because the middleware recorder implements Unwrap, this works behind the middleware stack. It sends a comment every 15 seconds: the HTML standard notes that some legacy proxies drop idle HTTP connections and suggests exactly this [76]. 21File uploads

HTML forms upload files as multipart/form-data: a body divided into parts, each with a Content-Disposition header naming the form field and, for files, an optional original filename [77]. RFC 7578 warns that the filename is only a suggestion and that receivers must not use it blindly, because it may contain path components or characters with special meaning to the file system [77]. OWASP’s upload guidance adds: allow-list file types, do not trust the client’s Content-Type, generate the stored filename, limit the size, store outside the web root, and scan content where the risk warrants it [78].

  • Streaming. r.MultipartReader yields parts one at a time, whereas ParseMultipartForm buffers the whole form in memory and temporary files first [1,79].
  • Type detection. http.DetectContentType implements the WHATWG MIME sniffing algorithm, considers at most the first 512 bytes, and returns application/octet-stream when nothing matches [1,80]. The allow-list keys on the sniffed type, so an HTML file renamed .png is refused.
  • Confinement. os.Root, added in Go 1.24, opens files only beneath one directory and rejects names that escape it, including through symbolic links [81,4,82]. The server-chosen name already prevents traversal; the root is defence in depth.
  • No partial files. On any error, including the size limit tripping mid-copy, the partially written file is removed. The test checks this.

When serving uploads back, send X-Content-Type-Options: nosniff and, for anything a browser might render, Content-Disposition: attachment, ideally from a separate domain, so an uploaded HTML or SVG file cannot run script in your origin [78,20].

22Background jobs

Work that takes longer than a client should wait (exports, emails, image processing) belongs outside the request. HTTP has a pattern for this: answer 202 Accepted, whose body ought to describe the request’s status and point to a status monitor [10], then let the client poll that monitor. The tasks API returns 202 with a Location header for POST /v1/exports and a status document at GET /v1/exports/{id}.

Design choices in this queue:

  • Bounded, non-blocking enqueue. A full queue returns ErrQueueFull immediately, and the handler turns that into 503 with Retry-After. An unbounded queue converts overload into memory exhaustion.
  • Retries with jitter. Failed jobs are retried with exponential backoff and “full jitter”, sleeping a random time between zero and the exponential ceiling. Brooker’s simulations show that jitter spreads retries out and greatly reduces contention compared with plain exponential backoff [83].
  • Isolation. Each attempt gets its own timeout, and a panic becomes an error instead of crashing the worker and the process.
  • Ownership. Workers are started with sync.WaitGroup.Go, added in Go 1.25 [84,39], and main stops HTTP first, then cancels the workers, then waits for in-flight jobs (Section 25).
Durability. An in-process queue loses its contents when the process dies. When a job must not be lost, persist it. The transactional outbox pattern writes the job record in the same database transaction as the business change, and a separate worker reads and dispatches it, so the job exists if and only if the change committed [85]. Because a job may then run more than once (at-least-once delivery), handlers must be idempotent.

23Caching

HTTP caching

The cheapest request is one that never reaches your server. RFC 9111 defines how browsers, CDNs and proxies cache responses, steered by Cache-Control [86]:

stale-while-revalidate, from RFC 5861, additionally lets a cache serve a stale response while it revalidates in the background [87]. Revalidation uses the validators from Section 4: an ETag with If-None-Match, or Last-Modified with If-Modified-Since, answered by 304 Not Modified [10]. For content you can express as an io.ReadSeeker, http.ServeContent implements the conditional and range request logic for you [1] (Exercise 7). Responses that vary by a request header must say so with Vary [10], as the CORS middleware does.

The tasks API uses private, no-cache plus an ETag for task reads (cheap revalidation, never stale), private, max-age=5 for statistics, and no-store as the default for everything else.

Application caching

In-process caches hold the results of expensive computations or queries. The cache-aside pattern reads the cache, and on a miss loads from the source and stores the result; writes update the source and then invalidate the cache entry. A subtle failure is the thundering herd: when a hot key expires, hundreds of concurrent requests miss at once and all query the database. singleflight “provides a duplicate function call suppression mechanism” so that concurrent callers for the same key share one execution [88].

The loader runs under context.WithoutCancel [2] with its own timeout, so if the first caller disconnects, the callers sharing its result are not failed with that caller’s cancellation. The test fires 100 concurrent requests at a slow loader and checks that it ran exactly once:

With several replicas, each in-process cache is invalidated only locally, so either keep TTLs short or use a shared cache such as Redis with a pub/sub invalidation channel.

24Microservices

Lewis and Fowler describe the microservice style as building an application from a suite of small services, each running in its own process and communicating through lightweight mechanisms, often HTTP resource APIs; the services are organized around business capabilities, are independently deployable, and manage their own data [89]. The “database per service” pattern makes the last point concrete: other services reach a service’s data only through its API [90]. The benefits (independent deployment and scaling, team autonomy) come with the costs of a distributed system: partial failure, network latency and eventual consistency. A well-modularized monolith built from the packages in this article can be split later, and that is usually the better starting point.

The example has two services. orders handles POST /orders by calling inventory over HTTP. Every call between them needs a timeout, a retry policy and a defined behaviour when the dependency is down.

  • Timeouts. http.Client.Timeout limits the whole exchange, and a zero value means no timeout, which is what http.DefaultClient has [1]. The transport’s default of two idle connections per host is low for service traffic, hence MaxIdleConnsPerHost [1].
  • Connection reuse. If a response body is not read to EOF and closed, the transport may be unable to reuse the connection [1], so error paths drain a bounded amount.
  • Deadlines propagate. The handler derives a 2-second budget from the incoming request’s context and passes it down, so work stops when the caller gives up. The SRE book identifies missing deadlines and unbounded retries as common causes of cascading failure, and recommends propagating deadlines and limiting retries per request [91].
  • Retry only what is safe. Only idempotent requests may be retried blindly [10], and only on errors that may be transient: connection failures, 429 and 5xx. A 404 is final. To make POST retryable, use an idempotency key (Exercise 11) [92].
  • Fail fast when a dependency is down. A circuit breaker stops calling a failing dependency for a cooling-off period, so callers fail immediately instead of queueing behind timeouts [93] (Exercise 10).

Health checks and draining

Kubernetes distinguishes liveness probes, whose failure restarts the container, from readiness probes, whose failure removes the pod from service endpoints until it recovers [94]. The Kubernetes documentation warns that badly designed liveness probes can cause cascading failures [94]; a liveness check that pings the database restarts every replica when the database is slow. The gateway’s /livez checks only the process; /readyz reports whether it should receive traffic. On SIGTERM it fails readiness first, waits briefly so load balancers stop routing to it, and only then calls Shutdown.

HTTP/JSON or gRPC?

HTTP with JSON is universal, debuggable with curl, and cacheable. gRPC uses Protocol Buffers over HTTP/2 with generated, strongly typed clients and servers, and supports streaming in both directions [95]. A common split is HTTP/JSON at the public edge and gRPC between internal services. Every concern in this article (deadlines, retries, authentication, metrics, tracing) applies to both.

Exercise 1. Routing precedence basic

A mux registers these five patterns: /files/ (A), GET /files/{path...} (B), GET /files/{$} (C), GET /files/readme (D) and files.example.com/ (E). Which handler serves each request, and what does r.PathValue("path") return? (a) GET /files/; (b) GET /files/readme; (c) GET /files/a/b.txt; (d) POST /files/a; (e) HEAD /files/a; (f) GET http://files.example.com/files/a.

Show solution

(a) C, because {$} matches only the trailing slash and is more specific than B. (b) D: a literal segment is more specific than a wildcard. (c) B, with path = a/b.txt. (d) A: B accepts only GET and HEAD, and A accepts any method. (e) B with path = a, because a GET pattern also matches HEAD. (f) E: when two patterns would otherwise conflict and only one has a host, the one with the host wins [1]. The test encodes the answers and runs them against the real mux:

Exercise 2. Require JSON basic

Write middleware RequireJSON that answers 415 Unsupported Media Type for POST, PUT and PATCH requests whose Content-Type is not application/json. Parameters such as charset must be allowed, and the comparison must be case-insensitive.

Show solution

Parse the header with mime.ParseMediaType, which lower-cases the media type and separates parameters, instead of comparing strings. HTTP standardizes a hint only for some cases: Accept-Encoding when a content coding is unsupported [10], and Accept-Patch for PATCH [12]; echoing Accept for other methods is a helpful convention rather than a requirement.

Exercise 3. Validate a sign-up form basic

Validate a {username, email, password} request. The username is 3–30 characters, starting with a lowercase letter, followed by letters, digits or underscores. The email must be a bare address (not Name <addr>). The password follows NIST SP 800-63B-4 for a single-factor password. Return every error, not just the first.

Show solution

mail.ParseAddress parses RFC 5322 addresses, including display names [98], so comparing the parsed Address with the input rejects Name <addr>. For a password that is the only factor, NIST requires at least 15 characters, recommends allowing at least 64, and forbids composition rules [31]. Counting runes rather than bytes keeps the rule fair for non-ASCII passwords.

Exercise 4. Verify a JWT by hand intermediate

Using only the standard library, write Verify(token, key, now) for HS256 tokens. It must reject malformed tokens, any alg other than HS256 (including none), bad signatures and expired tokens. Test it against tokens minted by golang-jwt.

Show solution

The JWS signing input is the encoded header, a period, and the encoded payload, and the encoding is base64url without padding [42]. Check the algorithm before anything else, as RFC 8725 requires [43]; compare MACs with hmac.Equal, which runs in constant time; and parse the payload only after the signature verifies.

Exercise 5. Fixed-window limiter intermediate

Implement a fixed-window counter limiter, Allow(key, now) (bool, reset time.Time). Then write a test showing how many requests a “5 per minute” limit admits in the two seconds around a minute boundary, and explain why a token bucket does better.

Show solution

Truncating now to the window gives the window’s start; when it changes, all counters reset. Five requests in the last second of one window and five in the first second of the next all pass, so the limit is exceeded twofold within two seconds. A token bucket with capacity 5 and rate 5/min would admit the first five and then one token every 12 seconds, because tokens are earned continuously rather than restored all at once [53].

Exercise 6. CORS reasoning basic

(a) A team sets Access-Control-Allow-Origin: * and Access-Control-Allow-Credentials: true, and the browser still blocks their credentialed requests. Why? (b) A page on https://evil.example sends fetch("https://api.example.com/v1/transfer", {method: "POST", credentials: "include", body: form}) with a form-encoded body. Does CORS prevent the request from reaching the server? (c) Why must a CORS response that echoes the allowed origin carry Vary: Origin?

Show solution

(a) For credentialed requests the Fetch standard does not accept the wildcard; the server must echo the specific origin [21,22]. (b) No. A form-encoded POST is a “simple” request, sent without a preflight; CORS only stops the script from reading the response [21,22]. The state change still happens unless the server defends against CSRF, for example with http.CrossOriginProtection, SameSite cookies or tokens [38,1]. (c) Because the response differs by request origin, a shared cache without Vary: Origin could serve the response containing one origin’s Access-Control-Allow-Origin to another origin [21,10].

Exercise 7. Conditional GET and ranges for free intermediate

Serve an immutable generated document so that clients can revalidate with If-None-Match and download byte ranges, without writing any conditional-request logic yourself.

Show solution

Set an ETag derived from the content and call http.ServeContent, which handles If-Match, If-Unmodified-Since, If-None-Match, If-Modified-Since and If-Range, plus Range requests [1]. The test checks 200, then 304 on revalidation, then 206 for a range.

Exercise 8. Parse an event stream intermediate

Write Parse(r io.Reader, fn func(Event) bool) that turns a text/event-stream into events, following the HTML standard’s rules for comments, multi-line data, the default event type, the persistence of the last event ID, and the single optional space after the colon.

Show solution

The HTML standard specifies that a blank line dispatches the event, that lines starting with a colon are ignored, that only one leading space after the colon is removed, that data lines are joined with newlines, that the type defaults to message, and that the last event ID persists until changed [76]. An event with no data is not dispatched.

Exercise 9. Retry with backoff intermediate

Write retry.Do(ctx, attempts, base, maxDelay, fn) that retries fn with capped exponential backoff and full jitter, stops immediately on errors wrapped with retry.Permanent, and returns promptly when the context is cancelled.

Show solution

Full jitter sleeps a random time in [0, min(cap, base·2n)) [83]. A distinct wrapper type, detected with errors.As [17], marks permanent errors. On cancellation, errors.Join returns both the context error and the last failure, so errors.Is(err, context.DeadlineExceeded) still works [17].

Exercise 10. Circuit breaker hard

Implement a circuit breaker with three states. Closed: calls pass and consecutive failures are counted. Open: calls fail immediately with ErrOpen until a cooldown elapses. Half-open: exactly one trial call is allowed; success closes the circuit and failure re-opens it. Make the clock injectable so the test needs no sleeps.

Show solution

This is the state machine Fowler describes [93]. The mutex is released while fn runs so slow calls do not serialize the breaker, and a trial flag ensures only one half-open probe is in flight. Wrap svcclient.GetJSON in b.Call and map ErrOpen to 503 with Retry-After.

Exercise 11. Idempotency keys hard

Write middleware that makes POST safe to retry. When a request carries an Idempotency-Key header, the first request runs normally and its response is stored; a repeat with the same key and body gets the stored response; a repeat with the same key but a different body is rejected; and a repeat that arrives while the original is still running is rejected too.

Show solution

The IETF HTTPAPI working group’s Idempotency-Key draft (still a work in progress) specifies these behaviours, including 422 for a key reused with a different payload and 409 for a concurrent duplicate [92]. A hash of the body detects payload changes, and httptest.NewRecorder buffers the first response so it can be replayed. In production, store entries in a shared database with an expiry, and scope keys to the authenticated client so one client cannot replay another’s responses.
