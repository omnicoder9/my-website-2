Error Handling and Reliability in Go

A technical article with runnable examples, exercises and solutions · Examples verified with Go 1.27.3 (go run -race, gofmt, go vet) · References in Vancouver style

Abstract. Go treats errors as ordinary values returned alongside results, not as exceptions that unwind the stack. That one decision shapes everything else: errors are created with errors.New, fmt.Errorf or custom types; they are propagated explicitly with added context; they are wrapped into chains and trees that errors.Is, errors.As and the newer generic errors.AsType can search; and panic and recover are reserved for programming bugs and truly unrecoverable situations. This article covers each of these mechanisms with reference to the language specification, the standard library documentation and the Go team's published guidance, then widens the view to reliability engineering: defensive programming, validating untrusted input, degrading gracefully, retrying with capped exponential backoff and jitter, and bounding every remote call with a timeout. Eighteen runnable programs and ten exercises with worked solutions accompany the text.

1. Error handling philosophy

Most mainstream languages separate the normal path from the failure path with exceptions. Go deliberately does not. The Go FAQ explains: "We believe that coupling exceptions to a control structure, as in the try-catch-finally idiom, results in convoluted code. It also tends to encourage programmers to label too many ordinary errors, such as failing to open a file, as exceptional" [1]. Instead, "Go's multi-value returns make it easy to report an error without overloading the return value," and a separate pair of built-ins, panic and recover, exist "to signal and recover from truly exceptional conditions" [1].

The consequences are easy to state:

  • Failure is part of the signature. A function that can fail returns an error, by convention as its last result [2,3]. A caller cannot use the result without at least seeing that an error is possible.
  • Errors are values. Rob Pike's summary is that "Values can be programmed, and since errors are values, errors can be programmed" [4]. They can be stored, compared, wrapped, joined, passed over channels and inspected like any other data.
  • Every error deserves a decision. The Go proverbs put it as "Don't just check errors, handle them gracefully" and "Don't panic" [5]. Google's Go style guide asks that code "make a deliberate choice": handle the error, return it, or in exceptional situations stop the program [3].
  • Normal flow stays unindented. Handle the error first and return; "Code that runs if the terminal condition is not met should appear after the if block, and should not be indented in an else clause" [3].

The explicit style is sometimes criticised as verbose. The Go team examined many proposals for new syntax over several years, and in June 2025 announced that "For the foreseeable future, the Go team will stop pursuing syntactic language changes for error handling" [6]. Explicit if err != nil checks are therefore the stable idiom, and the way to reduce repetition is to program with error values, as Pike's errWriter does below [4].

ex01_values/main.go 
// Errors are values: they can be stored, compared and programmed with.
package main

import (
	"bytes"
	"errors"
	"fmt"
	"io"
	"strconv"
)

// errWriter remembers the first error and turns later writes into no-ops,
// so the caller checks once at the end (after Pike, "Errors are values").
type errWriter struct {
	w   io.Writer
	err error
}

func (ew *errWriter) write(s string) {
	if ew.err != nil {
		return
	}
	_, ew.err = io.WriteString(ew.w, s)
}

// limitedWriter fails once more than n bytes have been written.
type limitedWriter struct {
	buf bytes.Buffer
	n   int
}

var errFull = errors.New("writer full")

func (l *limitedWriter) Write(p []byte) (int, error) {
	if l.buf.Len()+len(p) > l.n {
		return 0, errFull
	}
	return l.buf.Write(p)
}

func main() {
	// 1. The ordinary pattern: the error is an extra result, checked at once.
	n, err := strconv.Atoi("42x")
	if err != nil {
		fmt.Println("parse failed:", err)
	} else {
		fmt.Println("parsed", n)
	}

	// 2. Programming with the error value: check once, after the sequence.
	lw := &limitedWriter{n: 12}
	ew := &errWriter{w: lw}
	ew.write("header;")
	ew.write("body;")
	ew.write("footer;")
	if ew.err != nil {
		fmt.Printf("write failed: %v (wrote %q)\n", ew.err, lw.buf.String())
	}
}
Output 
parse failed: strconv.Atoi: parsing "42x": invalid syntax
write failed: writer full (wrote "header;body;")

The first half is the everyday pattern: strconv.Atoi returns (int, error) and the caller checks at once. The second half follows Pike's observation about bufio.Scanner and bufio.Writer: by recording the first error and making later operations no-ops, the type lets the caller "loop until done, then worry about errors" so that "Error handling does not obscure the flow of control" [4]. Pike stresses that this "is not about how to avoid checking errors": "Whatever you do, always check your errors!" [4]

2. The built-in error interface

The specification defines error as a predeclared interface with one method [7]:

type error interface {
	Error() string
}

"It is the conventional interface for representing an error condition, with the nil value representing no error" [7]. Any type with an Error() string method is therefore an error, and fmt prints an error by calling that method [8]. Because error is an interface, the concrete type behind it can carry as much structure as needed; the interface only promises a human-readable description.

The most common surprise comes from interface semantics. An interface value is a pair of a dynamic type and a dynamic value, and it is nil only when both are unset. The FAQ's entry "Why is my nil error value not equal to nil?" shows a function that stores a nil *MyError in an error: the result holds (T=*MyError, V=nil), so "if the caller compares the returned error to nil, it will always look as if there was an error even if nothing bad happened" [1]. The remedy is to return an explicit nil, and to declare results with the error type rather than a concrete pointer type [1,3].

ex02_interface/main.go 
// The built-in error interface, and the typed-nil pitfall.
package main

import "fmt"

// Any type with an Error() string method satisfies the predeclared
// interface:  type error interface { Error() string }
type TempError float64

func (t TempError) Error() string { return fmt.Sprintf("temperature %.1f out of range", float64(t)) }

type MyError struct{ Op string }

func (e *MyError) Error() string { return e.Op + ": failed" }

// bad returns a nil *MyError inside a non-nil error interface.
func bad(fail bool) error {
	var p *MyError // nil pointer
	if fail {
		p = &MyError{Op: "bad"}
	}
	return p // WRONG: the interface holds (type=*MyError, value=nil)
}

// good returns an untyped nil when there is no error.
func good(fail bool) error {
	if fail {
		return &MyError{Op: "good"}
	}
	return nil
}

func main() {
	var err error = TempError(451)
	fmt.Println(err)               // fmt calls Error()
	fmt.Println(err.Error() != "") // the only method in the interface

	var none error
	fmt.Println(none == nil) // the zero value of an interface is nil

	e1, e2 := bad(false), good(false)
	fmt.Println("bad(false) == nil: ", e1 == nil)
	fmt.Println("good(false) == nil:", e2 == nil)
	fmt.Printf("dynamic type of bad(false): %T\n", e1)
}
Output 
temperature 451.0 out of range
true
true
bad(false) == nil:  false
good(false) == nil: true
dynamic type of bad(false): *main.MyError
Rule: never return a typed nil pointer as an error. Exported functions should declare their result as error, not *MyError, because "a concrete nil pointer can get wrapped into an interface and thus become a non-nil value" [3].

A convention worth adopting from the start concerns error text. Go's style guidance says error strings "should not be capitalized (unless beginning with an exported name, a proper noun or an acronym) and should not end with punctuation" because "error strings usually appear within other context before being printed to the user" [3]. Effective Go adds that "When feasible, error strings should identify their origin, such as by having a prefix naming the operation or package that generated the error" [2].

The standard library offers three constructors, and the interface admits a fourth way: your own type.

ex03_create/main.go 
// Four ways to create an error value.
package main

import (
	"errors"
	"fmt"
)

// 3. A custom type carries structured data.
type RangeError struct {
	Value, Min, Max int
}

func (e *RangeError) Error() string {
	return fmt.Sprintf("value %d outside [%d, %d]", e.Value, e.Min, e.Max)
}

func main() {
	// 1. errors.New: a fixed message. Every call yields a distinct value.
	a := errors.New("disk full")
	b := errors.New("disk full")
	fmt.Println(a, "|", a == b, "|", a == a)

	// 2. fmt.Errorf: a formatted message (optionally wrapping with %w).
	user, quota := "ana", 10
	c := fmt.Errorf("user %q exceeded quota of %d GiB", user, quota)
	fmt.Println(c)

	// 3. A custom error type.
	var d error = &RangeError{Value: 12, Min: 1, Max: 10}
	fmt.Println(d)

	// 4. errors.Join: several errors as one (nil values are dropped).
	e := errors.Join(a, nil, d)
	fmt.Println(e)
	fmt.Println(errors.Join(nil, nil) == nil)
}
Output 
disk full | false | true
user "ana" exceeded quota of 10 GiB
value 12 outside [1, 10]
disk full
value 12 outside [1, 10]
true

Two lines of output deserve comment. a == b is false even though both say "disk full": errors.New returns a pointer to a fresh unexported struct, so identity, not text, determines equality [8,9]. That is what makes sentinel errors (Section 10) work. And errors.Join "formats as the concatenation of the strings obtained by calling the Error method of each element of errs, with a newline between each string" [9], which is why the joined value prints on two lines.

4. Error propagation

When a function cannot deal with an error itself, it returns it to its caller, usually after adding context about what it was trying to do. Effective Go's example is os.Open, whose error reads "open /etc/passwx: no such file or directory": such an error "is useful even if printed far from the call that caused it" because it names the operation and the file [2]. Gerrand puts it as "It is the error implementation's responsibility to summarize the context" [8].

Three practical rules follow from the guidance:

  1. Add what the caller does not know. Each layer adds its own context (which file, which line, which key) and not context the caller already has. Placing %w at the end, as in "line %d: %w", keeps the text ordered from the outermost operation to the root cause [12].
  2. Handle once. "If you return an error, it's usually better not to log it yourself but rather let the caller handle it" [12]. Logging and returning the same error produces duplicate log lines at every level.
  3. Treat other results as unspecified on error. "If a function returns an error, callers must treat all non-error return values as unspecified unless explicitly documented otherwise" [3]. The functions below return zero values on failure so that nothing half-built escapes.
ex04_propagate/main.go 
// Propagating errors up the call stack, adding context at each layer.
package main

import (
	"errors"
	"fmt"
	"strconv"
	"strings"
)

type Config struct {
	Port    int
	Workers int
}

// parseLine is the lowest layer: it reports what was wrong with one line.
func parseLine(line string) (key string, val int, err error) {
	k, v, ok := strings.Cut(line, "=")
	if !ok {
		return "", 0, fmt.Errorf("missing '=' in %q", line)
	}
	n, err := strconv.Atoi(strings.TrimSpace(v))
	if err != nil {
		return "", 0, fmt.Errorf("key %s: %w", strings.TrimSpace(k), err)
	}
	return strings.TrimSpace(k), n, nil
}

// parseConfig adds the line number; it does not log, it returns.
func parseConfig(text string) (Config, error) {
	var c Config
	for i, line := range strings.Split(strings.TrimSpace(text), "\n") {
		k, v, err := parseLine(line)
		if err != nil {
			return Config{}, fmt.Errorf("line %d: %w", i+1, err)
		}
		switch k {
		case "port":
			c.Port = v
		case "workers":
			c.Workers = v
		default:
			return Config{}, fmt.Errorf("line %d: unknown key %q", i+1, k)
		}
	}
	return c, nil
}

// loadConfig adds the name of the source.
func loadConfig(name, text string) (Config, error) {
	c, err := parseConfig(text)
	if err != nil {
		return Config{}, fmt.Errorf("load config %s: %w", name, err)
	}
	return c, nil
}

func main() {
	// The top level handles the error exactly once (here, by printing it).
	for _, src := range []string{"port=8080\nworkers=4", "port=8080\nworkers=four"} {
		c, err := loadConfig("app.conf", src)
		if err != nil {
			fmt.Println("error:", err)
			var ne *strconv.NumError
			fmt.Println("  caused by bad number:", errors.As(err, &ne))
			continue
		}
		fmt.Printf("ok: %+v\n", c)
	}
}
Output 
ok: {Port:8080 Workers:4}
error: load config app.conf: line 2: key workers: strconv.Atoi: parsing "four": invalid syntax
  caused by bad number: true

The final message reads like a breadcrumb trail from the outermost operation to the root cause: load config app.conf: line 2: key workers: strconv.Atoi: parsing "four": invalid syntax. Because every layer used %w, the top level can still discover programmatically that the root cause was a *strconv.NumError (Section 7). Errors also propagate from goroutines, but not automatically: a goroutine has no caller to return to, so its error must be sent over a channel or collected in a shared slice, as later examples show.

5. Error wrapping

Go 1.13 standardised a convention: "an error which contains another may implement an Unwrap method returning the underlying error. If e1.Unwrap() returns e2, then we say that e1 wraps e2" [13,14]. Repeated unwrapping produces the error chain. Go 1.20 generalised this: an error may instead implement Unwrap() []error, and "Successive unwrapping of an error creates a tree" that errors.Is and errors.As search "pre-order, depth-first" [9,11].

The simplest way to wrap is the %w verb of fmt.Errorf. With %v instead, the message is identical but the link to the original error is lost:

ex05_wrap/main.go 
// Wrapping: %w versus %v, Unwrap chains, and error trees.
package main

import (
	"errors"
	"fmt"
	"io/fs"
)

func main() {
	base := fs.ErrNotExist

	wrapped := fmt.Errorf("open config: %w", base) // keeps the chain
	opaque := fmt.Errorf("open config: %v", base)  // text only

	fmt.Println(wrapped)
	fmt.Println(opaque)
	fmt.Println("wrapped is ErrNotExist:", errors.Is(wrapped, fs.ErrNotExist))
	fmt.Println("opaque  is ErrNotExist:", errors.Is(opaque, fs.ErrNotExist))

	// Walking a chain with errors.Unwrap.
	err := fmt.Errorf("layer 3: %w", fmt.Errorf("layer 2: %w", errors.New("layer 1")))
	for e := err; e != nil; e = errors.Unwrap(e) {
		fmt.Printf("  %T  %q\n", e, e.Error())
	}

	// Multiple %w (Go 1.20+) and errors.Join build a tree, not a chain.
	errA, errB := errors.New("A"), errors.New("B")
	both := fmt.Errorf("both failed: %w; %w", errA, errB)
	fmt.Println(both)
	fmt.Println("Unwrap() on a tree:", errors.Unwrap(both)) // nil: it has Unwrap() []error
	if u, ok := both.(interface{ Unwrap() []error }); ok {
		fmt.Println("children:", u.Unwrap())
	}
	fmt.Println(errors.Is(both, errA), errors.Is(both, errB))
}
Output 
open config: file does not exist
open config: file does not exist
wrapped is ErrNotExist: true
opaque  is ErrNotExist: false
  *fmt.wrapError  "layer 3: layer 2: layer 1"
  *fmt.wrapError  "layer 2: layer 1"
  *errors.errorString  "layer 1"
both failed: A; B
Unwrap() on a tree: <nil>
children: [A B]
true true

Note that errors.Unwrap returns nil for the multi-error: it "only calls a method of the form 'Unwrap() error'. In particular Unwrap does not unwrap errors returned by Join" [9]. In practice you rarely call Unwrap directly; Is and As walk the whole tree for you [13].

Whether to wrap

Wrapping is not free of consequences. Neil and Amsterdam explain that "wrapping an error makes that error part of your API. If you don't want to commit to supporting that error as part of your API in the future, you shouldn't wrap the error" [13]. Their example is a LookupUser function built on database/sql: if it wraps sql.ErrNoRows, callers will start testing for it, and the package can never switch databases without breaking them. The rule of thumb is: "Wrap an error to expose it to callers. Do not wrap an error when doing so would expose implementation details" [13]. Either way, "the error text will be the same"; the choice is only "whether to give programs additional information" [13].

6. errors.Is

errors.Is(err, target) "reports whether any error in err's tree matches target". An error matches "if it is equal to that target or if it implements a method Is(error) bool such that Is(target) returns true" [9]. The package documentation is explicit that errors.Is(err, fs.ErrExist) "is preferable to err == fs.ErrExist because the former will succeed if err wraps io/fs.ErrExist" [9].

ex06_is/main.go 
// errors.Is: matching a value anywhere in the error tree.
package main

import (
	"errors"
	"fmt"
	"io/fs"
	"os"
)

var ErrTimeout = errors.New("timeout")

// StatusError matches a target StatusError with the same code, so callers
// can write errors.Is(err, &StatusError{Code: 404}).
type StatusError struct {
	Code int
	URL  string
}

func (e *StatusError) Error() string { return fmt.Sprintf("GET %s: status %d", e.URL, e.Code) }

func (e *StatusError) Is(target error) bool {
	t, ok := target.(*StatusError)
	return ok && t.Code == e.Code // shallow comparison only; no Unwrap here
}

// netError claims to be ErrTimeout when it is a timeout.
type netError struct{ timeout bool }

func (e netError) Error() string { return "network error" }
func (e netError) Is(target error) bool {
	return target == ErrTimeout && e.timeout
}

func main() {
	_, err := os.Open("/definitely/missing.txt")
	fmt.Println(err)
	fmt.Println("== fs.ErrNotExist:", err == fs.ErrNotExist)          // false: it is a *fs.PathError
	fmt.Println("Is fs.ErrNotExist:", errors.Is(err, fs.ErrNotExist)) // true: found by unwrapping

	wrapped := fmt.Errorf("fetch: %w", &StatusError{Code: 404, URL: "/x"})
	fmt.Println(errors.Is(wrapped, &StatusError{Code: 404}))
	fmt.Println(errors.Is(wrapped, &StatusError{Code: 500}))

	fmt.Println(errors.Is(fmt.Errorf("dial: %w", netError{timeout: true}), ErrTimeout))
	fmt.Println(errors.Is(netError{timeout: false}, ErrTimeout))
	fmt.Println(errors.Is(nil, ErrTimeout), errors.Is(nil, nil))
}
Output 
open /definitely/missing.txt: no such file or directory
== fs.ErrNotExist: false
Is fs.ErrNotExist: true
true

The os.Open error is a *fs.PathError that wraps a system error, which in turn reports itself as fs.ErrNotExist; a plain == misses this, errors.Is finds it [9,15]. The custom Is methods show the two legitimate uses of the hook: matching by a field (the Go 1.13 post's template-matching example [13]) and declaring equivalence with an existing sentinel. The documentation adds a constraint: "An Is method should only shallowly compare err and the target and not call Unwrap on either" [9]; the traversal is errors.Is's job. Finally, the target must be comparable, and errors.Is(nil, nil) is true while errors.Is(nil, x) is false.

7. errors.As and errors.AsType

Where Is asks "is this particular value anywhere in the tree?", As asks "is there an error of this type, and if so give it to me". errors.As(err, &target) "finds the first error in err's tree that matches target, and if one is found, sets target to that error value and returns true" [9]. The target must be a non-nil pointer to a type that implements error or to any interface type; otherwise As panics, and go vet's errorsas check reports such calls at build time [9,16].

Go 1.26 added a generic form, errors.AsType[E error](err) (E, bool), which the release notes describe as "type-safe, faster, and, in most cases, easier to use" [17]. The package documentation now says "For most uses, prefer AsType" [9]. It returns the match directly, so the result can be scoped to an if statement and there is no pointer-to-pointer to get wrong. Its type parameter is constrained by error, so an interface target used with AsType must embed error, whereas errors.As accepts any interface.

ex07_as/main.go 
// errors.As and errors.AsType: extracting a typed error from the tree.
package main

import (
	"errors"
	"fmt"
	"io/fs"
	"os"
	"strconv"
)

// timeoutError satisfies the anonymous interface below.
type timeoutError struct{ op string }

func (e *timeoutError) Error() string { return e.op + ": i/o timeout" }
func (e *timeoutError) Timeout() bool { return true }

func main() {
	_, err := os.ReadFile("/no/such/file.txt")
	err = fmt.Errorf("load settings: %w", err)

	// Classic form: declare a target of the error type, pass its address.
	var pe *fs.PathError
	if errors.As(err, &pe) {
		fmt.Printf("As:     op=%s path=%s cause=%v\n", pe.Op, pe.Path, pe.Err)
	}

	// Go 1.26+: the generic AsType returns the value directly.
	if pe, ok := errors.AsType[*fs.PathError](err); ok {
		fmt.Println("AsType: path =", pe.Path)
	}

	// The target may be an interface type: match on behaviour. For AsType
	// the interface must include error; errors.As accepts any interface.
	err = fmt.Errorf("call backend: %w", &timeoutError{op: "read tcp"})
	if t, ok := errors.AsType[interface {
		error
		Timeout() bool
	}](err); ok {
		fmt.Println("timeout?", t.Timeout())
	}

	// strconv errors carry the function, the input and the reason.
	_, err = strconv.ParseInt("99999999999999999999", 10, 64)
	if ne, ok := errors.AsType[*strconv.NumError](err); ok {
		fmt.Printf("%s(%q): %v; range error: %v\n",
			ne.Func, ne.Num, ne.Err, errors.Is(ne, strconv.ErrRange))
	}

	// No match: zero value and false.
	_, ok := errors.AsType[*strconv.NumError](errors.New("plain"))
	fmt.Println("plain error is *NumError:", ok)
}
Output 
As:     op=open path=/no/such/file.txt cause=no such file or directory
AsType: path = /no/such/file.txt
timeout? true
ParseInt("99999999999999999999"): value out of range; range error: true
plain error is *NumError: false

The *strconv.NumError case shows why typed errors are valuable: it records "the failing function", "the input" and "the reason the conversion failed (e.g. ErrRange, ErrSyntax, etc.)", and because it has an Unwrap method, errors.Is(ne, strconv.ErrRange) also works [18]. Matching on behaviour, as with the anonymous Timeout() bool interface, is how net.Error is meant to be used [19].

8. fmt.Errorf

fmt.Errorf "formats according to a format specifier and returns the string as a value that satisfies error" [10]. Its special behaviour is the %w verb:

  • "If the format specifier includes a %w verb with an error operand, the returned error will implement an Unwrap method returning the operand" [10].
  • "If there is more than one %w verb, the returned error will implement an Unwrap method returning a []error containing all the %w operands in the order they appear in the arguments" (Go 1.20+) [10,11].
  • "It is invalid to supply the %w verb with an operand that does not implement the error interface. The %w verb is otherwise a synonym for %v" [10].
ex08_errorf/main.go 
// fmt.Errorf: formatting, %w placement, and the types it returns.
package main

import (
	"errors"
	"fmt"
	"io"
)

func main() {
	id, size := 42, 3.5
	e1 := fmt.Errorf("order %d: weight %.1f kg exceeds limit", id, size)
	e2 := fmt.Errorf("read order %d: %w", id, io.ErrUnexpectedEOF)
	e3 := fmt.Errorf("sync %d: %w; rollback: %w", id, io.ErrClosedPipe, io.ErrShortWrite)

	// The concrete type depends on how many %w verbs there are.
	for _, e := range []error{e1, e2, e3} {
		fmt.Printf("%-22T %v\n", e, e)
	}

	// %w at the end keeps the text in newest-to-oldest order.
	inner := errors.New("connection refused")
	fmt.Println(fmt.Errorf("query users: %w", fmt.Errorf("dial db: %w", inner)))
	fmt.Println(fmt.Errorf("%w: dial db", fmt.Errorf("%w: query users", inner)))

	// %q and %v are useful for reporting the offending input.
	field := "email"
	fmt.Println(fmt.Errorf("field %s: invalid value %q", field, "a@@b"))

	// A nil %w operand is formatted as a bad verb and nothing is wrapped.
	// (A non-error operand is invalid, and go vet reports it.)
	var nilErr error
	bad := fmt.Errorf("oops: %w", nilErr)
	fmt.Println(bad, errors.Unwrap(bad) == nil)
}

field email: invalid value "a@@b"

The %T column shows the three concrete types: without %w the result is a plain *errors.errorString (and since Go 1.26 an unformatted fmt.Errorf("x") allocates about as little as errors.New("x") [17]); with one %w it is a *fmt.wrapError; with several it is a *fmt.wrapErrors. These are unexported implementation details: rely on Unwrap, Is and As, not on the type names. The two "connection refused" lines illustrate the style guide's advice to "prefer placing the %w verb at the end with the form [...]: %w" so that the text mirrors the chain from newest to oldest [12].

Static checking

go vet's printf analyser checks Errorf calls like any other format call [16]. Go 1.27 extended it to report wrapping a pointer *E when E itself implements error, because "Wrapping a pointer in this way is usually a latent bug since it causes spurious failures of operations that test for a particular error type" [20]:

9. Custom error types

A custom type is the right tool when callers need data, not just a message. Gerrand's examples are a NegativeSqrtError that records the bad argument and json.SyntaxError, whose Offset field "isn't even shown in the default formatting of the error, but callers can use it to add file and line information" [8]. The standard library is full of them: *fs.PathError records Op, Path and Err [2,15]; *strconv.NumError records Func, Num and Err [18].

Design guidelines that follow from the documentation and blog posts:

  • Use a pointer receiver for struct error types and return them as error, so that identity and nil-ness behave predictably [1,3].
  • If the type contains a cause, add Unwrap() error so that Is and As can see through it [13].
  • Expose behaviour through small methods (Timeout(), Retryable()) and let callers match on an interface, which keeps them decoupled from your concrete type. Note that net.Error's Temporary method is now deprecated because "Temporary errors are not well-defined"; Timeout remains [19].
  • Add Is or As methods only for genuine equivalences [9].

The example maps any error to an HTTP status at a single boundary, which is a common use of typed errors in servers:

ex09_custom/main.go 
// Custom error types: structured data, Unwrap, and behaviour methods.
package main

import (
	"errors"
	"fmt"
	"net/http"
)

// FieldError reports one invalid input field.
type FieldError struct {
	Field, Reason string
}

func (e *FieldError) Error() string { return e.Field + ": " + e.Reason }

// OpError records which operation failed on which resource and why.
type OpError struct {
	Op       string
	Resource string
	Err      error // underlying cause
	retry    bool
}

func (e *OpError) Error() string   { return fmt.Sprintf("%s %s: %v", e.Op, e.Resource, e.Err) }
func (e *OpError) Unwrap() error   { return e.Err }
func (e *OpError) Retryable() bool { return e.retry }

// retryable is any error that can say whether a retry may succeed.
// AsType needs a type argument that implements error.
type retryable interface {
	error
	Retryable() bool
}

var ErrConflict = errors.New("version conflict")

// statusFor maps any error to an HTTP status by inspecting its tree.
func statusFor(err error) int {
	if _, ok := errors.AsType[*FieldError](err); ok {
		return http.StatusBadRequest
	}
	if errors.Is(err, ErrConflict) {
		return http.StatusConflict
	}
	if r, ok := errors.AsType[retryable](err); ok && r.Retryable() {
		return http.StatusServiceUnavailable
	}
	return http.StatusInternalServerError
}

	errs := []error{
		&FieldError{Field: "age", Reason: "must be between 0 and 150"},
		&OpError{Op: "update", Resource: "user/7", Err: ErrConflict},
		fmt.Errorf("handler: %w", &OpError{Op: "query", Resource: "db", Err: errors.New("too many connections"), retry: true}),
		errors.New("disk on fire"),
	}
	for _, err := range errs {
		code := statusFor(err)
		fmt.Printf("%d %-21s <- %v\n", code, http.StatusText(code), err)
	}
}

10. Sentinel errors

A sentinel error is a package-level variable that callers compare against, such as io.EOF, fs.ErrNotExist, sql.ErrNoRows or context.Canceled. The Go 1.13 post describes them as "a known sentinel value" used "to see if a specific error has occurred" [13]. Sentinels are cheap and readable, but they are API: once callers test for one, you must keep returning it [13].

Recommendations:

  • Name them ErrXxx, declare them with errors.New, and document which functions return them, as errors.ErrUnsupported's documentation does [9].
  • Return them wrapped with context (fmt.Errorf("get %q: %w", key, ErrNotFound)) and tell callers to use errors.Is. The Go 1.13 post even recommends fmt.Errorf("%w", ErrPermission) over returning the bare value, so that callers cannot come to depend on == [13].
  • io.EOF is the deliberate exception: "Read must return EOF itself, not an error wrapping EOF, because callers will test for EOF using ==" [21]. It also illustrates that a sentinel can signal a normal condition: "Functions should return EOF only to signal a graceful end of input" [21].
  • Because a var can be reassigned by any code in the program, some authors define sentinels as constants of a string-based error type [22]. The same author also cautions that you "really shouldn't be using sentinel errors" for anything a typed error or behaviour check would express better [22].
ex10_sentinel/main.go 
// Sentinel errors: package-level values that callers compare against.
package main

import (
	"errors"
	"fmt"
	"io"
	"strings"
)

// ErrNotFound is part of this package's API: callers may test for it.
var ErrNotFound = errors.New("not found")

type Store struct{ data map[string]string }

// Get returns an error wrapping ErrNotFound if key is absent.
func (s *Store) Get(key string) (string, error) {
	v, ok := s.data[key]
	if !ok {
		return "", fmt.Errorf("get %q: %w", key, ErrNotFound)
	}
	return v, nil
}

// constError lets a sentinel be a constant, so it cannot be reassigned.
type constError string

func (e constError) Error() string { return string(e) }

const ErrReadOnly = constError("store is read-only")

func main() {
	s := &Store{data: map[string]string{"a": "1"}}
	for _, k := range []string{"a", "b"} {
		v, err := s.Get(k)
		switch {
		case errors.Is(err, ErrNotFound):
			fmt.Println("miss:", err)
		case err != nil:
			fmt.Println("error:", err)
		default:
			fmt.Println("hit:", v)
		}
	}

	// io.EOF is the classic sentinel; Read returns it unwrapped, so == works,
	// but errors.Is is equally correct and more robust.
	r := strings.NewReader("go!")
	buf := make([]byte, 2)
	for {
		n, err := r.Read(buf)
		fmt.Printf("n=%d %q err=%v\n", n, buf[:n], err)
		if errors.Is(err, io.EOF) {
			break
		}
	}

	var err error = fmt.Errorf("put: %w", ErrReadOnly)
	fmt.Println(errors.Is(err, ErrReadOnly), err)
}

The strings.Reader loop shows the io.Reader contract in action: the final call returns n=0 together with EOF. In general a reader may return data and EOF in the same call, so callers should process n > 0 bytes before considering the error [21].

11. Panic and recover

The specification describes the mechanism precisely. "While executing a function F, an explicit call to panic or a run-time panic terminates the execution of F. Any functions deferred by F are then executed as usual," then those of its caller, "and so on up to any deferred by the top-level function in the executing goroutine. At that point, the program is terminated and the error condition is reported" [7]. Run-time errors such as an out-of-range index produce a panic whose value implements runtime.Error [7,23].

recover stops the sequence. If a deferred function calls recover during a panic, it receives the panic value; "If D returns normally, without starting a new panic, the panicking sequence stops" and the deferring function returns to its caller normally [7]. "The return value of recover is nil when the goroutine is not panicking or recover was not called directly by a deferred function" [7]. Since Go 1.21, panic(nil) causes a run-time panic of type *runtime.PanicNilError, so a non-nil result from recover reliably means a panic happened [7,23,24].

When to panic

The guidance is consistent across sources:

  • "Do not use panic for normal error handling. Instead, use error and multiple return values" [3]. Library functions "should avoid panic. If the problem can be masked or worked around, it's always better to let things continue to run rather than taking down the whole program" [2].
  • Panic is appropriate for programmer errors and broken invariants, the way the runtime panics on an out-of-bounds index or the standard library panics "on API misuse" [12], and during initialisation: "if the library truly cannot set itself up, it might be reasonable to panic" [2]. MustXxx helpers such as regexp.MustCompile follow this convention and "should only be called early on program startup, not on things like user input" [3].
  • A package may panic internally as a control-flow shortcut, for example in a recursive-descent parser, provided that "these panics are never allowed to escape across package boundaries" [12]. "The convention in the Go libraries is that even when a package uses panic internally, its external API still presents explicit error return values" [2,25].

Recovering at a boundary

Effective Go's main use for recover is "to shut down a failing goroutine inside a server without killing the other executing goroutines" [2]; net/http itself recovers a panic in a handler, on the assumption "that the effect of the panic was isolated to the active request" [26]. Recovery must happen in the goroutine that panicked: the spec's unwinding stops at "the top-level function in the executing goroutine" [7], so a panic in an unprotected goroutine terminates the whole program regardless of what its parent does.

ex11_panic/main.go 
// panic and recover: converting panics to errors at a boundary.
package main

import (
	"errors"
	"fmt"
	"runtime"
	"sync"
)

// safely runs f and converts any panic into an error. Deferred calls in f
// still run while the panic unwinds the stack.
func safely(name string, f func()) (err error) {
	defer func() {
		if r := recover(); r != nil {
			if re, ok := r.(runtime.Error); ok {
				err = fmt.Errorf("%s: runtime error recovered: %w", name, re)
				return
			}
			err = fmt.Errorf("%s: panic: %v", name, r)
		}
	}()
	f()
	return nil
}

// Internal panics as a control-flow shortcut, never escaping the package.
type parseError struct{ msg string }

func mustDigit(c byte) int {
	if c < '0' || c > '9' {
		panic(&parseError{fmt.Sprintf("bad digit %q", c)})
	}
	return int(c - '0')
}

func SumDigits(s string) (sum int, err error) {
	defer func() {
		if r := recover(); r != nil {
			pe, ok := r.(*parseError)
			if !ok {
				panic(r) // not ours: re-panic
			}
			sum, err = 0, errors.New("sumdigits: "+pe.msg)
		}
	}()
	for i := range len(s) {
		sum += mustDigit(s[i])
	}
	return sum, nil
}

func main() {
	var idx = 5
	fmt.Println(safely("index", func() {
		defer fmt.Println("  (deferred cleanup ran)")
		_ = []int{1, 2, 3}[idx]
	}))
	fmt.Println(safely("nil map", func() {
		var m map[string]int
		m["x"] = 1
	}))
	fmt.Println(safely("explicit", func() { panic("invariant violated") }))
	fmt.Println(safely("panic(nil)", func() { panic(nil) })) // Go 1.21+: *runtime.PanicNilError

	fmt.Println(SumDigits("2026"))
	fmt.Println(SumDigits("20x6"))

	// recover works only in the panicking goroutine: each goroutine needs
	// its own boundary, or a panic there crashes the whole program.
	var wg sync.WaitGroup
	errs := make([]error, 3)
	for i := range 3 {
		wg.Go(func() {
			errs[i] = safely(fmt.Sprintf("worker %d", i), func() {
				if i == 1 {
					panic("boom")
				}
			})
		})
	}
	wg.Wait()
	fmt.Println(errors.Join(errs...))
}
Output 
  (deferred cleanup ran)
index: runtime error recovered: runtime error: index out of range [5] with length 3
nil map: runtime error recovered: assignment to entry in nil map
explicit: panic: invariant violated
panic(nil): runtime error recovered: runtime error: panic called with nil argument
10 <nil>
0 sumdigits: bad digit 'x'

Points to notice: the deferred Println ran before the recovery, as the spec requires; runtime.Error distinguishes runtime faults from application panics, as its documentation suggests [23]; SumDigits re-panics on values it does not own, the pattern recommended in both Effective Go and Google's guide [2,12]; and it uses named results so that the deferred function can set the returned error [25]. Each worker started with sync.WaitGroup.Go (Go 1.25+) has its own safely boundary [27].

Recovering is not the same as being correct. After a panic, data touched by the aborted code may be half-updated (a mutex left locked, a map partly written). Recover at coarse boundaries (a request, a job), discard the state that request owned, log the value with a stack trace (runtime/debug.Stack [28]), and let truly corrupted processes crash and restart.

12. Defensive programming

Defensive programming is the discipline of writing each routine so that it protects itself from invalid inputs and its callers from its own failures. McConnell's classic treatment covers checking inputs from external sources, checking routine parameters, deciding how to handle bad inputs, and using assertions for conditions that "should never occur" [29]. Meyer's design by contract frames the same idea as explicit preconditions, postconditions and class invariants [30].

Go has no assertion facility. The FAQ explains why: "programmers use them as a crutch to avoid thinking about proper error handling and reporting. Proper error handling means that servers continue to operate instead of crashing after a non-fatal error" [1]. In Go the contract is therefore expressed with:

  • Guard clauses that validate arguments and return a descriptive error early (indent-error-flow style [3]).
  • Constructors that establish invariants, so that every value of the type is valid from birth, and unexported fields so that only methods can change it.
  • Explicit results instead of in-band signals: "Instead of requiring clients to check for an in-band error value, a function should return an additional value to indicate whether its other return values are valid" (an error or an ok bool) [3].
  • Defensive copies of slices and maps at API boundaries, since both share their backing storage with the caller.
  • Nil-safe methods where a nil receiver has a sensible meaning [31].
  • Not discarding errors, including from Close. It is "not usually appropriate to discard errors using _ variables"; where it is safe, "an accompanying comment should explain why" [3].
ex12_defensive/main.go 
// Defensive programming: guard clauses, invariants, defensive copies,
// nil-safe methods, and not losing errors from Close.
package main

import (
	"errors"
	"fmt"
	"io"
	"slices"
	"strings"
)

type Account struct {
	id      string
	balance int64 // cents; invariant: balance >= 0
	history []int64
}

var ErrInsufficient = errors.New("insufficient funds")

// NewAccount validates its arguments instead of trusting callers.
func NewAccount(id string, opening int64) (*Account, error) {
	if id == "" {
		return nil, errors.New("new account: empty id")
	}
	if opening < 0 {
		return nil, fmt.Errorf("new account %s: negative opening balance %d", id, opening)
	}
	return &Account{id: id, balance: opening}, nil
}

// Withdraw uses guard clauses, then keeps the invariant.
func (a *Account) Withdraw(amount int64) error {
	if a == nil {
		return errors.New("withdraw: nil account")
	}
	if amount <= 0 {
		return fmt.Errorf("withdraw %d: amount must be positive", amount)
	}
	if amount > a.balance {
		return fmt.Errorf("withdraw %d from %s (balance %d): %w", amount, a.id, a.balance, ErrInsufficient)
	}
	a.balance -= amount
	a.history = append(a.history, -amount)
	return nil
}

// History returns a copy so callers cannot mutate internal state.
func (a *Account) History() []int64 { return slices.Clone(a.history) }

// Balance is nil-safe: a nil *Account reports zero.
func (a *Account) Balance() int64 {
	if a == nil {
		return 0
	}
	return a.balance
}

// failingCloser simulates a writer whose Close reports a flush failure.
type failingCloser struct{ io.Writer }

func (failingCloser) Close() error { return errors.New("flush on close: disk quota exceeded") }

// save reports a Close error instead of silently dropping it.
func save(w io.WriteCloser, data string) (err error) {
	defer func() {
		if cerr := w.Close(); cerr != nil {
			err = errors.Join(err, cerr)
		}
	}()
	_, err = io.WriteString(w, data)
	return err
}

func main() {
	_, err := NewAccount("", 100)
	fmt.Println(err)

	acct, _ := NewAccount("acc-1", 5000)
	fmt.Println(acct.Withdraw(-1))
	fmt.Println(acct.Withdraw(7000))
	fmt.Println(acct.Withdraw(2000), acct.Balance())

	h := acct.History()
	h[0] = 999999 // modifies the copy only
	fmt.Println(acct.History())

	var missing *Account
	fmt.Println(missing.Balance(), missing.Withdraw(1))

	var sb strings.Builder
	fmt.Println(save(failingCloser{&sb}, "report"), "| written:", sb.String())
}

13. Input validation

Every value that crosses a trust boundary (an HTTP body, a CLI flag, a file, a message from another service) must be validated before use. OWASP defines input validation as checking "whether data meets an application's requirements before the application uses it" and recommends validating both "syntax (the expected type and format) and semantics (whether the value makes sense for the operation)" [32]. Its key practices map directly onto the Go standard library:

ex13_validate/main.go 
// Input validation at a trust boundary: limit, parse strictly, then
// validate syntax and semantics, reporting every problem at once.
package main

import (
	"encoding/json"
	"errors"
	"fmt"
	"net/http"
	"net/http/httptest"
	"net/mail"
	"strings"
	"unicode/utf8"
)

type FieldError struct{ Field, Msg string }

func (e *FieldError) Error() string { return e.Field + ": " + e.Msg }

type Signup struct {
	Name  string `json:"name"`
	Email string `json:"email"`
	Age   int    `json:"age"`
	Plan  string `json:"plan"`
}

var plans = map[string]bool{"free": true, "pro": true} // allowlist

// Validate checks each field against explicit rules and joins the failures.
func (s Signup) Validate() error {
	var errs []error
	add := func(field, format string, args ...any) {
		errs = append(errs, &FieldError{field, fmt.Sprintf(format, args...)})
	}
	if n := utf8.RuneCountInString(strings.TrimSpace(s.Name)); n < 1 || n > 50 {
		add("name", "must be 1-50 characters, got %d", n)
	}
	if a, err := mail.ParseAddress(s.Email); err != nil || a.Address != s.Email {
		add("email", "not a plain address: %q", s.Email)
	}
	if s.Age < 13 || s.Age > 130 {
		add("age", "must be between 13 and 130, got %d", s.Age)
	}
	if !plans[s.Plan] {
		add("plan", "must be one of free, pro; got %q", s.Plan)
	}
	return errors.Join(errs...)
}

// fieldErrors walks an error tree and collects every *FieldError.
func fieldErrors(err error) []*FieldError {
	var out []*FieldError
	var walk func(error)
	walk = func(e error) {
		if fe, ok := e.(*FieldError); ok {
			out = append(out, fe)
		}
		switch u := e.(type) {
		case interface{ Unwrap() error }:
			if c := u.Unwrap(); c != nil {
				walk(c)
			}
		case interface{ Unwrap() []error }:
			for _, c := range u.Unwrap() {
				walk(c)
			}
		}
	}
	if err != nil {
		walk(err)
	}
	return out
}

func handleSignup(w http.ResponseWriter, r *http.Request) {
	r.Body = http.MaxBytesReader(w, r.Body, 256) // bound size before parsing
	dec := json.NewDecoder(r.Body)
	dec.DisallowUnknownFields() // reject fields we do not expect
	var s Signup
	if err := dec.Decode(&s); err != nil {
		if _, ok := errors.AsType[*http.MaxBytesError](err); ok {
			http.Error(w, "request too large", http.StatusRequestEntityTooLarge)
			return
		}
		http.Error(w, "malformed JSON: "+err.Error(), http.StatusBadRequest)
		return
	}
	if err := s.Validate(); err != nil {
		var msgs []string
		for _, fe := range fieldErrors(err) {
			msgs = append(msgs, fe.Error())
		}
		http.Error(w, strings.Join(msgs, "; "), http.StatusUnprocessableEntity)
		return
	}
	fmt.Fprintf(w, "welcome, %s", s.Name)
}

func main() {
	bodies := []string{
		`{"name":"Ada","email":"ada@example.com","age":36,"plan":"pro"}`,
		`{"name":"","email":"Ada <ada@example.com>","age":7,"plan":"gold"}`,
		`{"name":"Ada","admin":true}`,
		`{"name":"Ada",`,
		`{"name":"` + strings.Repeat("A", 300) + `"}`,
	}
	for _, b := range bodies {
		rec := httptest.NewRecorder()
		handleSignup(rec, httptest.NewRequest("POST", "/signup", strings.NewReader(b)))
		fmt.Printf("%d %s\n", rec.Code, strings.TrimSpace(rec.Body.String()))
	}
}

The handler distinguishes three classes of bad input with three status codes: too large (413), not parseable as the expected JSON (400), and well-formed but semantically invalid (422). Returning every field error at once, rather than only the first, saves the client a round trip per mistake; the tree walk in fieldErrors is needed because errors.As stops at the first match (Exercise 4 generalises it).

On "be liberal in what you accept". The robustness principle is often quoted to justify tolerating malformed input. RFC 9413 revisits it and concludes that "ignoring faulty or ambiguous input is almost always the incorrect solution to the problem" [36]. For security-relevant input, strictness is the safer default.

14. Graceful degradation

A reliable system keeps doing something useful when parts of it fail. Google's SRE book describes two related techniques: "Load shedding drops some proportion of load by dropping traffic as the server approaches overload conditions", and "Graceful degradation takes the concept of load shedding one step further" by reducing the work done or the quality of the response [37]. Nygard's Release It! catalogues the same family of stability patterns (timeouts, circuit breakers, bulkheads, load shedding, fail fast) [38].

In Go these are ordinary code built from the error-handling tools above: an error from a dependency triggers a fallback rather than a failure, and the response is labelled as degraded so that monitoring and the user can tell.

ex14_degrade/main.go 
// Graceful degradation: fall back to stale data or a safe default, and
// shed load rather than collapse when overloaded.
package main

import (
	"errors"
	"fmt"
	"sync"
)

var ErrOverloaded = errors.New("overloaded: request shed")

type Recommender struct {
	fetch func(user string) ([]string, error) // the primary dependency

	mu    sync.Mutex
	cache map[string][]string // last good answer per user
	slots chan struct{}       // bounded concurrency for load shedding
}

type Result struct {
	Items    []string
	Degraded string // empty when served normally
}

// For serves fresh data if it can, stale data if it must, and a generic
// default as the last resort. It never fails the whole page.
func (r *Recommender) For(user string) Result {
	items, err := r.fetch(user)
	if err == nil {
		r.mu.Lock()
		r.cache[user] = items
		r.mu.Unlock()
		return Result{Items: items}
	}
	r.mu.Lock()
	stale, ok := r.cache[user]
	r.mu.Unlock()
	if ok {
		return Result{Items: stale, Degraded: "stale: " + err.Error()}
	}
	return Result{Items: []string{"bestsellers"}, Degraded: "default: " + err.Error()}
}

// Admit takes a slot without blocking or rejects the request immediately.
func (r *Recommender) Admit() (release func(), err error) {
	select {
	case r.slots <- struct{}{}:
		return func() { <-r.slots }, nil
	default:
		return nil, ErrOverloaded
	}
}

func main() {
	healthy := true
	r := &Recommender{
		cache: map[string][]string{},
		slots: make(chan struct{}, 2),
		fetch: func(user string) ([]string, error) {
			if !healthy {
				return nil, errors.New("recs backend unavailable")
			}
			return []string{"go-book-for-" + user}, nil
		},
	}
	fmt.Printf("%+v\n", r.For("ana")) // normal
	healthy = false
	fmt.Printf("%+v\n", r.For("ana")) // stale cache
	fmt.Printf("%+v\n", r.For("bo"))  // generic default

	// Load shedding: two requests in flight fill the slots; the third is
	// rejected at once instead of queueing without bound.
	var releases []func()
	for i := 1; i <= 3; i++ {
		rel, err := r.Admit()
		fmt.Printf("request %d admitted=%v err=%v\n", i, err == nil, err)
		if err == nil {
			releases = append(releases, rel)
		}
	}
	for _, rel := range releases {
		rel()
	}
}

The non-blocking select with a default case turns a bounded semaphore into a load shedder: when all slots are busy, new work is refused immediately with ErrOverloaded rather than piling up in memory and making every request slow.

Graceful shutdown

Degrading gracefully also means stopping gracefully. signal.NotifyContext returns a context that is cancelled when a listed signal arrives, and since Go 1.26 the cancellation cause records which signal it was [17,39]. http.Server.Shutdown "gracefully shuts down the server without interrupting any active connections" and, if its context expires first, returns the context's error [26].

// Graceful shutdown on a signal: stop accepting, finish in-flight work,
// but bound how long that may take.
//
// This demo sends SIGINT to itself, so it runs on Unix-like systems.
package main

import (
	"context"
	"errors"
	"fmt"
	"net"
	"net/http"
	"os"
	"os/signal"
	"syscall"
	"time"

	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()

	ln, err := net.Listen("tcp", "127.0.0.1:0")
	if err != nil {
		fmt.Println("listen:", err)
		return
	}
	srv := &http.Server{
		ReadHeaderTimeout: 5 * time.Second, // never leave server timeouts at zero
		Handler: http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			time.Sleep(100 * time.Millisecond) // in-flight work
			fmt.Fprint(w, "done")
		}),
	}
	serveErr := make(chan error, 1)
	go func() { serveErr <- srv.Serve(ln) }()

	// A client request that is in flight when the signal arrives.
	reply := make(chan string, 1)
	go func() {
		resp, err := http.Get("http://" + ln.Addr().String())
		if err != nil {
			reply <- "client error: " + err.Error()
			return
		}
		defer resp.Body.Close()
		reply <- "client got " + resp.Status
	}()
	time.Sleep(30 * time.Millisecond)
	syscall.Kill(os.Getpid(), syscall.SIGINT) // simulate Ctrl-C

	<-ctx.Done()
	fmt.Println("shutting down:", context.Cause(ctx))
	shutCtx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel()
	if err := srv.Shutdown(shutCtx); err != nil {
		fmt.Println("forced shutdown:", err)
	}
	fmt.Println(<-reply)
	err = <-serveErr
	fmt.Println("Serve returned ErrServerClosed:", errors.Is(err, http.ErrServerClosed))
}

The in-flight request completes with 200 OK even though the signal arrived while it was being served, and Serve returns http.ErrServerClosed, which a real program should treat as a normal exit, not a failure [26].

15. Retry strategies

Many failures in distributed systems are transient: a connection reset, a leader election, a brief overload. Retrying can turn them into successes, but naive retries can also turn a small outage into a large one. Marc Brooker describes retries as "selfish": a retrying client "spends more of the server's time to get a higher chance of success" [40]. The established practice, from both AWS and Google, is:

  1. Retry only what is safe. "APIs with side effects aren't safe to retry unless they provide idempotency" [40]. Classify errors: a 400 or a validation failure will fail again; a 503 or a timeout may not.
  2. Limit attempts. "Limit retries per request" and "Don't retry a given request indefinitely" [37]; consider a process-wide retry budget [37] or a token bucket [40].
  3. Back off exponentially, with jitter. "Always use randomized exponential backoff when scheduling retries" [37]. "Jitter adds some amount of randomness to the backoff to spread the retries around in time" so that clients that failed together do not retry together [40]. Brooker's simulations compare variants; "Full Jitter" (a uniform random delay up to the capped exponential bound) "uses less work, but slightly more time", and jittered backoff in general "should be considered a standard approach for remote clients" [41].
  4. Retry at one layer. "If each layer retries independently, the load on the database will increase 243x" in Brooker's five-layer example [40]; the SRE book likewise warns to "avoid amplifying retries by issuing retries at multiple levels" [37].
  5. Respect the caller's deadline. Waiting must stop when the context is done (Section 16).
ex15_retry/main.go 
// Retries with capped exponential backoff, full jitter, a retry limit,
// error classification and context cancellation.
package main

import (
	"context"
	"errors"
	"fmt"
	"math/rand/v2"
	"time"
)

// permanentError marks an error that must not be retried.
type permanentError struct{ err error }

func (p permanentError) Error() string { return p.err.Error() }
func (p permanentError) Unwrap() error { return p.err }

func Permanent(err error) error { return permanentError{err} }

type Policy struct {
	MaxAttempts int
	Base, Cap   time.Duration
	Rand        *rand.Rand // injectable for tests; nil means the global source
}

// backoff returns a "full jitter" delay: uniform in [0, min(Cap, Base*2^n)).
func (p Policy) backoff(n int) time.Duration {
	d := min(p.Cap, p.Base<<n)
	if p.Rand != nil {
		return time.Duration(p.Rand.Int64N(int64(d)))
	}
	return rand.N(d)
}

// Retry calls op until it succeeds, returns a permanent error, the attempts
// run out, or ctx is done. Only idempotent operations should be retried.
func Retry(ctx context.Context, p Policy, op func(context.Context) error) error {
	var errs []error
	for attempt := range p.MaxAttempts {
		err := op(ctx)
		if err == nil {
			return nil
		}
		errs = append(errs, fmt.Errorf("attempt %d: %w", attempt+1, err))
		if _, ok := errors.AsType[permanentError](err); ok {
			return errors.Join(errs...)
		}
		if attempt == p.MaxAttempts-1 {
			break
		}
		d := p.backoff(attempt)
		fmt.Printf("  attempt %d failed (%v); sleeping %v\n", attempt+1, err, d)
		t := time.NewTimer(d)
		select {
		case <-ctx.Done():
			t.Stop()
			return errors.Join(append(errs, context.Cause(ctx))...)
		case <-t.C:
		}
	}
	return errors.Join(errs...)
}

var ErrUnavailable = errors.New("503 service unavailable")

// failN returns an op that fails n times with err, then succeeds.
func failN(n int, err error) func(context.Context) error {
	calls := 0
	return func(context.Context) error {
		calls++
		if calls <= n {
			return err
		}
		return nil
	}
}

func main() {
	p := Policy{MaxAttempts: 4, Base: 2 * time.Millisecond, Cap: 20 * time.Millisecond,
		Rand: rand.New(rand.NewPCG(1, 2))} // fixed seed: reproducible output
	ctx := context.Background()

	fmt.Println("transient failures:")
	fmt.Println("result:", Retry(ctx, p, failN(2, ErrUnavailable)))

	fmt.Println("permanent failure:")
	fmt.Println("result:", Retry(ctx, p, failN(9, Permanent(errors.New("400 bad request")))))

	fmt.Println("attempts exhausted:")
	err := Retry(ctx, p, failN(9, ErrUnavailable))
	fmt.Println("result:", err)
	fmt.Println("is ErrUnavailable:", errors.Is(err, ErrUnavailable))

	fmt.Println("context deadline:")
	ctx, cancel := context.WithTimeout(ctx, time.Millisecond)
	defer cancel()
	slow := Policy{MaxAttempts: 5, Base: time.Second, Cap: time.Second, Rand: rand.New(rand.NewPCG(3, 4))}
	err = Retry(ctx, slow, failN(9, ErrUnavailable))
	fmt.Println("deadline exceeded:", errors.Is(err, context.DeadlineExceeded))
}

16. Timeouts and failure handling

"Timeouts are the maximum amount of time that a client waits for a request to complete" [40]; without them, a single hung dependency can tie up goroutines, connections and memory until the whole service stops. The SRE book advises that "It's usually wise to set a deadline" and that servers "should employ deadline propagation" rather than inventing new deadlines for each backend call [37].

In Go, the context package is the standard carrier for deadlines and cancellation: "Incoming requests to a server should create a Context, and outgoing calls to servers should accept a Context. The chain of function calls between them must propagate the Context" [43,44]. The important facts from its documentation:

  • WithTimeout "returns WithDeadline(parent, time.Now().Add(timeout))", and code "should call cancel as soon as the operations running in this Context complete"; failing to call the cancel function "leaks the child and its children until the parent is canceled", and go vet checks for this [16,43].
  • ctx.Err() is context.DeadlineExceeded after a timeout and context.Canceled after cancellation [43].
  • WithCancelCause, WithDeadlineCause and WithTimeoutCause record why: "Calling Cause on the canceled context or any of its children retrieves the cause" [43].
  • Pass the context as the first parameter, named ctx, and do not store it in a struct [43]. A function that takes a context "should usually return an error so that the caller can determine if the context was cancelled" [3].

For HTTP, http.Client.Timeout "specifies a time limit for requests made by this Client. The timeout includes connection time, any redirects, and reading the response body"; zero means no timeout [26]. Server-side, the http.Server fields ReadHeaderTimeout, ReadTimeout, WriteTimeout and IdleTimeout are all disabled when zero or negative, so production servers should set them explicitly [26].

// Timeouts: context deadlines, cancellation causes, HTTP client limits,
// and bounding a call that does not accept a context.
package main

import (
	"context"
	"errors"
	"fmt"
	"net"
	"net/http"
	"net/http/httptest"
	"time"
)

// query honours ctx: it returns early with ctx's error if ctx is done first.
func query(ctx context.Context, work time.Duration) (string, error) {
	select {
	case <-time.After(work):
		return "rows", nil
	case <-ctx.Done():
		return "", fmt.Errorf("query: %w", ctx.Err())
	}
}

var ErrSLO = errors.New("search exceeded its 20ms budget")

// legacyLookup ignores contexts; withTimeout bounds how long we wait for it.
func legacyLookup() int { time.Sleep(50 * time.Millisecond); return 7 }

func withTimeout[T any](d time.Duration, f func() T) (T, error) {
	ch := make(chan T, 1) // buffered: the goroutine can always finish and exit
	go func() { ch <- f() }()
	select {
	case v := <-ch:
		return v, nil
	case <-time.After(d):
		var zero T
		return zero, fmt.Errorf("gave up after %v: %w", d, context.DeadlineExceeded)
	}
}

func main() {
	// 1. A deadline for one operation; always defer cancel.
	ctx, cancel := context.WithTimeout(context.Background(), 20*time.Millisecond)
	defer cancel()
	_, err := query(ctx, 5*time.Millisecond)
	fmt.Println("fast query err:", err)
	_, err = query(ctx, time.Second)
	fmt.Println("slow query err:", err, "| deadline:", errors.Is(err, context.DeadlineExceeded))

	// 2. A cause explains *why* the context ended.
	ctx2, cancel2 := context.WithTimeoutCause(context.Background(), 20*time.Millisecond, ErrSLO)
	defer cancel2()
	_, err = query(ctx2, time.Second)
	fmt.Println("err:", err, "| cause:", context.Cause(ctx2))

	// 3. HTTP: a client-wide Timeout and a per-request context deadline.
	slow := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		select {
		case <-time.After(time.Second):
		case <-r.Context().Done(): // stop work when the client goes away
		}
	}))
	defer slow.Close()

	client := &http.Client{Timeout: 30 * time.Millisecond}
	_, err = client.Get(slow.URL)
	if ne, ok := errors.AsType[net.Error](err); ok {
		fmt.Println("client timeout, Timeout() =", ne.Timeout())
	}

	reqCtx, cancel3 := context.WithTimeout(context.Background(), 30*time.Millisecond)
	defer cancel3()
	req, _ := http.NewRequestWithContext(reqCtx, http.MethodGet, slow.URL, nil)
	_, err = http.DefaultClient.Do(req)
	fmt.Println("request ctx deadline:", errors.Is(err, context.DeadlineExceeded))

	// 4. Bounding a call that cannot be cancelled.
	v, err := withTimeout(10*time.Millisecond, legacyLookup)
	fmt.Println(v, err)
}

Case 4 shows the technique for code that cannot be cancelled: run it in a goroutine and stop waiting for it. The channel is buffered so the goroutine can still deliver its late result and exit instead of leaking. The work itself keeps running until it finishes, which is why context-aware APIs are always preferable.

Circuit breakers

Timeouts bound the cost of one call to a failing dependency; a circuit breaker bounds the cost of many. Fowler summarises the idea: "Once the failures reach a certain threshold, the circuit breaker trips", after which calls "return an error" immediately; after a delay a "half open" state lets a trial call through to test recovery. "Michael Nygard popularized the Circuit Breaker pattern to prevent this kind of catastrophic cascade" [38,45].

ex17_breaker/main.go 
// A minimal circuit breaker: fail fast while a dependency is unhealthy,
// then probe it again after a cool-down.
package main

import (
	"errors"
	"fmt"
	"sync"
	"time"
)

type State int

const (
	Closed   State = iota // calls pass through
	Open                  // calls fail fast
	HalfOpen              // one trial call is allowed
)

func (s State) String() string { return [...]string{"closed", "open", "half-open"}[s] }

var ErrOpen = errors.New("circuit open: failing fast")

type Breaker struct {
	mu        sync.Mutex
	state     State
	failures  int
	threshold int
	cooldown  time.Duration
	openedAt  time.Time
	now       func() time.Time // injectable clock
}

func (b *Breaker) Call(op func() error) error {
	b.mu.Lock()
	if b.state == Open {
		if b.now().Sub(b.openedAt) < b.cooldown {
			b.mu.Unlock()
			return ErrOpen
		}
		b.state = HalfOpen // cool-down over: allow one trial
	}
	b.mu.Unlock()

	err := op()

	b.mu.Lock()
	defer b.mu.Unlock()
	if err != nil {
		b.failures++
		if b.state == HalfOpen || b.failures >= b.threshold {
			b.state, b.openedAt = Open, b.now()
		}
		return err
	}
	b.state, b.failures = Closed, 0
	return nil
}

func main() {
	clock := time.Date(2026, 11, 2, 12, 0, 0, 0, time.UTC)
	b := &Breaker{threshold: 3, cooldown: 10 * time.Second, now: func() time.Time { return clock }}

	down := errors.New("dependency down")
	healthy := false
	op := func() error {
		if healthy {
			return nil
		}
		return down
	}
	step := func(label string) {
		err := b.Call(op)
		fmt.Printf("%-18s err=%-27v state=%v\n", label, err, b.state)
	}
	for i := 1; i <= 4; i++ {
		step(fmt.Sprintf("call %d", i))
	}
	clock = clock.Add(11 * time.Second)
	step("probe (still down)")
	clock = clock.Add(11 * time.Second)
	healthy = true
	step("probe (recovered)")
	step("normal call")
}
Output 
call 1             err=dependency down             state=closed
call 2             err=dependency down             state=closed
call 3             err=dependency down             state=open
call 4             err=circuit open: failing fast  state=open
probe (still down) err=dependency down             state=open
probe (recovered)  err=<nil>                       state=closed
normal call        err=<nil>                       state=closed

The injectable clock makes the state machine testable without sleeping. This minimal version lets every concurrent caller through during the half-open window; production implementations admit a single probe and usually count failures over a sliding time window rather than consecutively.

// Retryable reports whether the status suggests a retry might succeed.
func (e *HTTPError) Retryable() bool {
	switch e.Code {
	case 408, 429, 502, 503, 504:
		return true
	}
	return false
}

var ErrNotFound = &HTTPError{Code: 404}

func main() {
	err := fmt.Errorf("fetch /users/9: %w", &HTTPError{Code: 404})
	fmt.Println(err, errors.Is(err, ErrNotFound))

	err = fmt.Errorf("fetch /feed: %w", &HTTPError{Code: 503, Err: io.ErrUnexpectedEOF})
	he, _ := errors.AsType[*HTTPError](err)
	fmt.Println(err)
	fmt.Println("retryable:", he.Retryable(), "| EOF cause:", errors.Is(err, io.ErrUnexpectedEOF))
}

fetch /feed: http 503: unexpected EOF
retryable: true | EOF cause: true

Without the Is method, errors.Is would compare pointers and two distinct &HTTPError{Code: 404} values would never match. The Is method compares shallowly, as the documentation requires, and leaves traversal to errors.Is [9].

Exercise 4 — Find every match in an error tree (wrapping, generics)

errors.AsType returns only the first match. Write a generic All[E error](err error) []E that returns every error of type E in the tree, in the same order errors.Is visits them.

Show solution sol04_all/main.go 
package main

import (
	"errors"
	"fmt"
)

// All returns every error in err's tree that has type E, in the same
// pre-order, depth-first order used by errors.Is and errors.As.
func All[E error](err error) []E {
	var out []E
	var walk func(error)
	walk = func(e error) {
		if e == nil {
			return
		}
		if v, ok := e.(E); ok {
			out = append(out, v)
		}
		switch u := e.(type) {
		case interface{ Unwrap() error }:
			walk(u.Unwrap())
		case interface{ Unwrap() []error }:
			for _, c := range u.Unwrap() {
				walk(c)
			}
		}
	}
	walk(err)
	return out
}

type FieldError struct{ Field string }

func (e *FieldError) Error() string { return "bad " + e.Field }

func main() {
	err := fmt.Errorf("signup: %w", errors.Join(
		&FieldError{"name"},
		errors.New("unrelated"),
		fmt.Errorf("address: %w", errors.Join(&FieldError{"zip"}, &FieldError{"city"})),
	))
	for _, fe := range All[*FieldError](err) {
		fmt.Println(fe.Field)
	}
	first, _ := errors.AsType[*FieldError](err)
	fmt.Println("AsType finds only the first:", first.Field)
}
Output 
name
zip
city
AsType finds only the first: name

The traversal mirrors the documented algorithm: the error itself, then each child depth-first, via either Unwrap() error or Unwrap() []error [9]. (Unlike AsType, this simple version does not consult custom As methods.)

Exercise 5 — Panics as errors in concurrent tasks (panic, recover, goroutines)

Write RunAll(tasks ...func() error) error that runs each task in its own goroutine and returns all failures joined. A task that panics must not crash the program; instead its panic should become a *PanicError holding the value and the stack trace, and should unwrap to the panic value if that value is an error.

Show solution sol05_panicerror/main.go 
package main

import (
	"bytes"
	"errors"
	"fmt"
	"runtime/debug"
	"sync"
)

// PanicError carries the recovered value and the stack at the panic site.
type PanicError struct {
	Value any
	Stack []byte
}

func (p *PanicError) Error() string { return fmt.Sprintf("panic: %v", p.Value) }

// Unwrap exposes the panic value when it is itself an error.
func (p *PanicError) Unwrap() error {
	err, _ := p.Value.(error)
	return err
}

// RunAll runs each task in its own goroutine. A panicking task is
// converted to a *PanicError; the others are unaffected.
func RunAll(tasks ...func() error) error {
	errs := make([]error, len(tasks))
	var wg sync.WaitGroup
	for i, task := range tasks {
		wg.Go(func() {
			defer func() {
				if r := recover(); r != nil {
					errs[i] = fmt.Errorf("task %d: %w", i, &PanicError{Value: r, Stack: debug.Stack()})
				}
			}()
			if err := task(); err != nil {
				errs[i] = fmt.Errorf("task %d: %w", i, err)
			}
		})
	}
	wg.Wait()
	return errors.Join(errs...)
}

func main() {
	var m map[string]int
	err := RunAll(
		func() error { return nil },
		func() error { return errors.New("ordinary failure") },
		func() error { m["k"] = 1; return nil },
	)
	fmt.Println(err)
	if pe, ok := errors.AsType[*PanicError](err); ok {
		fmt.Println("stack captured:", bytes.Contains(pe.Stack, []byte("goroutine")))
	}
}
Output 
task 1: ordinary failure
task 2: panic: assignment to entry in nil map
stack captured: true

The recover must be inside each goroutine, since a panic unwinds only its own goroutine [7]. debug.Stack "returns a formatted stack trace of the goroutine that calls it", and calling it inside the deferred function captures the panicking goroutine's stack [28].

Exercise 6 — Honour the server's hint (retry strategies, behaviour interfaces)

Write a retry loop that normally waits backoff(n) between attempts, but if the error (anywhere in its tree) has a method RetryAfter() time.Duration, waits for that duration instead. It must stop when the context is done.

Show solution sol06_retryafter/main.go 
package main

import (
	"context"
	"errors"
	"fmt"
	"time"
)

// RateLimitError tells the client how long the server asked it to wait.
type RateLimitError struct{ After time.Duration }

func (e *RateLimitError) Error() string {
	return fmt.Sprintf("429 too many requests (retry after %v)", e.After)
}
func (e *RateLimitError) RetryAfter() time.Duration { return e.After }

type retryAfterer interface {
	error
	RetryAfter() time.Duration
}

// Retry waits backoff(n), unless the error carries a server hint, which wins.
func Retry(ctx context.Context, attempts int, backoff func(int) time.Duration, op func() error) error {
	var err error
	for n := range attempts {
		if err = op(); err == nil {
			return nil
		}
		if n == attempts-1 {
			break
		}
		wait := backoff(n)
		if ra, ok := errors.AsType[retryAfterer](err); ok {
			wait = ra.RetryAfter()
		}
		fmt.Printf("  attempt %d: %v; waiting %v\n", n+1, err, wait)
		select {
		case <-ctx.Done():
			return errors.Join(err, ctx.Err())
		case <-time.After(wait):
		}
	}
	return fmt.Errorf("after %d attempts: %w", attempts, err)
}

func main() {
	calls := 0
	op := func() error {
		calls++
		switch calls {
		case 1:
			return &RateLimitError{After: 3 * time.Millisecond}
		case 2:
			return errors.New("connection reset")
		}
		return nil
	}
	backoff := func(n int) time.Duration { return time.Millisecond << n }
	fmt.Println("result:", Retry(context.Background(), 5, backoff, op))
}
Output 
  attempt 1: 429 too many requests (retry after 3ms); waiting 3ms
  attempt 2: connection reset; waiting 2ms
result: <nil>

Matching on behaviour keeps the retry loop independent of any concrete error type; an HTTP client could implement RetryAfter from a Retry-After response header. In production you would also cap the hinted delay and add jitter [40].

Exercise 7 — Time budgets with a cause (timeouts, context.Cause)

Write CallWithBudget(ctx, name, budget, f) that runs f with a deadline and, when the deadline is what made f fail, returns an error for which both errors.Is(err, ErrBudget) and errors.Is(err, context.DeadlineExceeded) are true and whose message names the operation.

Show solution sol07_budget/main.go 
package main

import (
	"context"
	"errors"
	"fmt"
	"time"
)

var ErrBudget = errors.New("time budget exhausted")

// CallWithBudget runs f with a deadline whose cause is ErrBudget, and makes
// both ErrBudget and context.DeadlineExceeded visible to errors.Is.
func CallWithBudget(ctx context.Context, name string, budget time.Duration,
	f func(context.Context) error) error {
	ctx, cancel := context.WithTimeoutCause(ctx, budget,
		fmt.Errorf("%s: %w (%v)", name, ErrBudget, budget))
	defer cancel()
	err := f(ctx)
	if err != nil && ctx.Err() != nil {
		return fmt.Errorf("%w: %w", err, context.Cause(ctx))
	}
	return err
}

func sleepy(d time.Duration) func(context.Context) error {
	return func(ctx context.Context) error {
		select {
		case <-time.After(d):
			return nil
		case <-ctx.Done():
			return ctx.Err()
		}
	}
}

func main() {
	fmt.Println(CallWithBudget(context.Background(), "fast", 50*time.Millisecond, sleepy(time.Millisecond)))
	err := CallWithBudget(context.Background(), "render", 10*time.Millisecond, sleepy(time.Second))
	fmt.Println(err)
	fmt.Println(errors.Is(err, ErrBudget), errors.Is(err, context.DeadlineExceeded))
}
Output 
<nil>
context deadline exceeded: render: time budget exhausted (10ms)
true true

WithTimeoutCause "sets the cause of the returned Context when the timeout expires" [43], and two %w verbs make both the context error and the cause reachable [10].

Exercise 8 — Hedged requests (graceful degradation, timeouts, cancellation)

Write Hedged(ctx, hedgeAfter, primary, secondary): call the primary replica; if it has not answered within hedgeAfter, or if it fails, call the secondary as well. Return the first success and cancel the other call. If both fail, return both errors.

Show solution sol08_hedge/main.go 
package main

import (
	"context"
	"errors"
	"fmt"
	"time"
)

type replica func(ctx context.Context) (string, error)

// Hedged asks primary first; if it has not answered after hedgeAfter (or it
// failed), it also asks secondary. The first success wins and the loser is
// cancelled. If both fail, both errors are returned.
func Hedged(ctx context.Context, hedgeAfter time.Duration, primary, secondary replica) (string, error) {
	ctx, cancel := context.WithCancel(ctx)
	defer cancel() // stops whichever call is still running

	type result struct {
		v   string
		err error
	}
	results := make(chan result, 2) // buffered: senders never block
	launch := func(name string, r replica) {
		go func() {
			v, err := r(ctx)
			if err != nil {
				err = fmt.Errorf("%s: %w", name, err)
			}
			results <- result{v, err}
		}()
	}

	launch("primary", primary)
	timer := time.NewTimer(hedgeAfter)
	defer timer.Stop()
	launched, pending := 1, 1
	var errs []error
	for pending > 0 {
		select {
		case r := <-results:
			pending--
			if r.err == nil {
				return r.v, nil
			}
			errs = append(errs, r.err)
			if launched == 1 { // primary failed fast: hedge now
				launch("secondary", secondary)
				launched, pending = 2, pending+1
			}
		case <-timer.C:
			if launched == 1 {
				launch("secondary", secondary)
				launched, pending = 2, pending+1
			}
		case <-ctx.Done():
			return "", errors.Join(append(errs, ctx.Err())...)
		}
	}
	return "", errors.Join(errs...)
}

func after(d time.Duration, v string, err error) replica {
	return func(ctx context.Context) (string, error) {
		select {
		case <-time.After(d):
			return v, err
		case <-ctx.Done():
			return "", ctx.Err()
		}
	}
}

func main() {
	ctx := context.Background()
	fmt.Println(Hedged(ctx, 20*time.Millisecond, after(time.Millisecond, "primary fast", nil), after(time.Millisecond, "secondary", nil)))
	fmt.Println(Hedged(ctx, 20*time.Millisecond, after(time.Second, "primary slow", nil), after(time.Millisecond, "secondary", nil)))
	fmt.Println(Hedged(ctx, 20*time.Millisecond, after(time.Millisecond, "", errors.New("down")), after(time.Millisecond, "secondary", nil)))
	fmt.Println(Hedged(ctx, 20*time.Millisecond, after(time.Millisecond, "", errors.New("down")), after(time.Millisecond, "", errors.New("also down"))))
}
Output 
primary fast <nil>
secondary <nil>
secondary <nil>
 primary: down
secondary: also down

A buffered results channel lets the losing goroutine finish and exit after Hedged returns, and the deferred cancel tells it to stop early. Hedging trades a little extra load for lower tail latency, so the hedge delay is usually set near a high percentile of normal latency, and only idempotent requests should be hedged [40].

Exercise 10 — Validate a booking (input validation, errors.Join)

A booking has From and To dates as YYYY-MM-DD strings and a number of guests. Validate the syntax of both dates, then the semantics: the stay must start no earlier than today, end after it starts, last at most 30 nights, and have 1 to 8 guests. Report every problem in one error.

Show solution sol10_booking/main.go 
package main

import (
	"errors"
	"fmt"
	"time"
)

type Booking struct {
	From, To string // YYYY-MM-DD
	Guests   int
}

type FieldError struct{ Field, Msg string }

func (e *FieldError) Error() string { return e.Field + ": " + e.Msg }

// Parse validates syntax (date format) and semantics (ordering, ranges,
// limits) and returns every problem found, joined.
func (b Booking) Parse(today time.Time) (from, to time.Time, err error) {
	var errs []error
	from, ferr := time.Parse(time.DateOnly, b.From)
	if ferr != nil {
		errs = append(errs, &FieldError{"from", fmt.Sprintf("want YYYY-MM-DD, got %q", b.From)})
	}
	to, terr := time.Parse(time.DateOnly, b.To)
	if terr != nil {
		errs = append(errs, &FieldError{"to", fmt.Sprintf("want YYYY-MM-DD, got %q", b.To)})
	}
	if ferr == nil && terr == nil {
		nights := int(to.Sub(from).Hours() / 24)
		switch {
		case from.Before(today):
			errs = append(errs, &FieldError{"from", "is in the past"})
		case nights < 1:
			errs = append(errs, &FieldError{"to", "must be after from"})
		case nights > 30:
			errs = append(errs, &FieldError{"to", fmt.Sprintf("stay of %d nights exceeds 30", nights)})
		}
	}
	if b.Guests < 1 || b.Guests > 8 {
		errs = append(errs, &FieldError{"guests", fmt.Sprintf("must be 1-8, got %d", b.Guests)})
	}
	if err := errors.Join(errs...); err != nil {
		return time.Time{}, time.Time{}, fmt.Errorf("invalid booking: %w", err)
	}
	return from, to, nil
}

func main() {
	today := time.Date(2026, 11, 2, 0, 0, 0, 0, time.UTC)
	for _, b := range []Booking{
		{"2026-12-01", "2026-12-05", 2},
		{"2026-12-05", "2026-12-01", 0},
		{"01/12/2026", "2027-02-01", 3},
		{"2026-11-20", "2027-01-01", 2},
	} {
		from, to, err := b.Parse(today)
		if err != nil {
			fmt.Println(err)
			continue
		}
		fmt.Println("ok:", from.Format("Jan 2"), "to", to.Format("Jan 2"))
	}
}
Output 
ok: Dec 1 to Dec 5
invalid booking: to: must be after from
guests: must be 1-8, got 0
invalid booking: from: want YYYY-MM-DD, got "01/12/2026"
invalid booking: to: stay of 42 nights exceeds 30

Semantic checks run only when the syntax checks pass, so a bad date is not reported a second time as a bad ordering; this is the "syntax then semantics" order OWASP recommends [32]. time.DateOnly is the standard layout constant for "2006-01-02" [34].
