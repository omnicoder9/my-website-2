Architecture and Design Patterns in Go

From clean and hexagonal architecture to sagas, bulkheads and twelve-factor services: what each idea means, where it came from, and how it looks in idiomatic, runnable Go.

Technical article · 30 October 2026 · Go 1.22 or later · Vancouver-style references

Introduction

Architecture is the set of decisions that are expensive to change later: how a system is split into parts, which way the dependencies between those parts point, and how the parts communicate. Design patterns are smaller, reusable solutions to recurring problems inside those parts. Robert C. Martin puts the goal of architecture plainly: to minimise the human effort needed to build and maintain a system[1]. Most of the ideas in this article serve that goal by controlling dependencies, so that a change in one place does not ripple everywhere else. That idea goes back at least to Parnas's 1972 argument that modules should be split around design decisions likely to change, hiding each decision behind an interface[2].

The article has three parts. Part I covers architectural styles: layered, clean, hexagonal, domain-driven design, modular monoliths, microservices, event-driven architecture, CQRS and event sourcing. Part II covers the classic design patterns that do most of the day-to-day work in Go code: dependency injection, repository, factory, adapter, decorator, strategy, observer and middleware. Part III covers patterns for running systems that fail in production: circuit breakers, sagas, bulkheads and the twelve-factor methodology. Exercises with full solutions follow at the end.

How the code was checked. Every listing is a complete program or test from a single Go module (module example.com/goarch, go 1.22). Each one was compiled with Go 1.24, passed go vet and gofmt, and was run; the examples and tests that use goroutines were run under the race detector (-race)[3]. The output shown under each listing is the real output of that run. To try one, put the files in the directory named in the caption under a module root and run go run ./<dir> or go test ./.... Only the standard library is used.

Go's architectural toolkit

Most pattern catalogues were written for class-based languages. Go has no classes and no inheritance, so several patterns shrink or change shape. A handful of language features carry almost all of the architectural weight.

Packages and internal

The package is Go's unit of encapsulation: identifiers that start with an upper-case letter are exported, and everything else is private to the package[4]. The go command adds a second boundary. A package under a directory named internal can be imported only by code rooted at the parent of that internal directory[5]. The Go team's guide to module layout recommends internal for code that should not be imported by other modules[6]. The compiler enforces this boundary, which makes it much stronger than a naming convention. Section 5 uses it to build a modular monolith.

Implicit, consumer-owned interfaces

A Go type satisfies an interface simply by having the right methods. There is no implements declaration[4]. Rob Pike describes this as a deliberate choice: types do not need to know about the interfaces they satisfy, so dependencies between packages stay small[7]. The Go code review guidelines draw the architectural consequence: interfaces generally belong in the package that uses values of the interface type, not the package that implements them, and should not be defined before they are needed[8]. Effective Go notes that interfaces with one or two methods are common[9], and one of the Go proverbs states the principle directly: "The bigger the interface, the weaker the abstraction"[10]. This is the Dependency Inversion Principle almost for free. High-level code declares the abstraction it needs, and low-level code satisfies it without importing anything from the high-level package[11].

Composition, function values, context and errors

Go favours composition over inheritance. Struct embedding promotes the methods of an embedded field, and functions are first-class values[4,9]. A one-method interface can often be replaced by a function type such as http.HandlerFunc[12], which is why strategy, observer and middleware are often only a few lines in Go. The context package carries deadlines, cancellation and request-scoped values across API boundaries[13]. Error wrapping with %w and errors.Is/errors.As lets inner layers return sentinel errors that outer layers can check without depending on concrete error types[14,15].

A recurring rule of thumb. Write concrete code first. Introduce an interface at the point where a consumer needs to vary or fake a dependency, and declare it in the consumer's package. Most of the architectures below are this rule applied at a larger scale.

Part I · Architectural styles

1. Layered architecture

The Layers pattern organises a system into groups of subtasks at different levels of abstraction. Each layer provides services to the layer above it and uses only the layer directly below[16]. The most common enterprise form has three layers, presentation, domain (business logic) and data source, which Fowler describes as the standard way to separate concerns in information systems[17,18].

  • Presentation handles HTTP, CLI or UI concerns: parsing input, formatting output and mapping errors to status codes.
  • Business (domain or service) layer holds the rules, such as "a product is available if stock > 0".
  • Data access talks to databases and other storage.

In the example below each layer is a type, and each type holds a pointer to the concrete type beneath it. The routing pattern "GET /products/{id}" and r.PathValue use the method and wildcard matching added to net/http.ServeMux in Go 1.22[19].

Trade-offs

Layering is easy to understand and is a sensible default for small services. Its weakness is the direction of dependency. The business layer depends on the data layer, so business rules cannot be compiled or tested without the persistence code, and database concerns tend to leak upward. Fowler also warns that layering only by technical concern (all handlers in one place, all repositories in another) tends to scatter each feature across the code base, and he recommends dividing first by domain area for anything larger[18]. Clean and hexagonal architecture both fix the dependency direction by inverting it, which Exercise 1 does for this example.

2. Clean architecture

Martin's Clean Architecture combines earlier ideas (hexagonal, onion and others) into concentric rings: Entities (enterprise business rules), Use Cases (application business rules), Interface Adapters (controllers, presenters, gateways) and Frameworks and Drivers (web, database, UI)[1,20]. Its one essential rule is the Dependency Rule: source code dependencies can only point inwards. Nothing in an inner ring may name anything declared in an outer ring[20].

The use case below declares its own output ports (AccountGateway, TransferPresenter), and outer rings implement them. Only main, the outermost ring, knows every concrete type. In a real project each ring would be a package, for example internal/domain, internal/usecase, internal/adapter/postgres and cmd/server. The import graph would then show the Dependency Rule directly.

In Go

  • Put the interface next to the use case that consumes it, as the Go review guidelines recommend[8]. The use-case package then imports nothing from adapters.
  • The presenter is an example of what Martin calls a humble object: it is so simple that it barely needs testing, and the logic it would otherwise contain moves into testable inner code[1].
  • Do not create one interface per struct "just in case". Go makes it cheap to extract an interface later, at the point of use.

Pitfall. Copying the full ring structure into a small CRUD service often produces many packages of pass-through code. Martin himself treats the four rings as a schematic: there may be more or fewer, as long as the Dependency Rule holds[20].

3. Hexagonal architecture (ports and adapters)

Alistair Cockburn's hexagonal architecture has a stated intent: to allow an application to be driven equally by users, programs, automated tests or batch scripts, and to be developed and tested in isolation from its eventual run-time devices and databases[21]. The application sits inside a boundary. It talks to the outside only through ports, which are technology-agnostic interfaces, and adapters translate between each port and a specific technology.

  • Driving (primary) ports are the application's API, used by HTTP handlers, CLIs, message consumers and tests.
  • Driven (secondary) ports are what the application needs: storage, notification, payment and so on.

The hexagon shape has no special meaning. Cockburn chose it to leave room to draw several ports and to move away from the top-to-bottom picture of layers[21]. Jeffrey Palermo's onion architecture (2008) states the same inward dependency in rings[22], and Martin's clean architecture builds on both[20].

The same core is driven by an HTTP adapter and a CLI adapter, and Exercise 2 drives it a third way, from a unit test with fake driven adapters. That is exactly the "equally driven" property in Cockburn's intent.

4. Domain-driven design

Eric Evans's domain-driven design (DDD) is an approach to complex software in which the design is driven by a model of the business domain, built together with domain experts[23]. It has two halves.

Strategic design

  • Ubiquitous language: developers and domain experts use one shared vocabulary, and that vocabulary appears in the code. In the example, the methods are Place and AddLine, not Update or SetStatus[23].
  • Bounded context: an explicit boundary inside which a model and its language are consistent. A "customer" in billing and a "customer" in shipping can be different models in different contexts. Fowler calls bounded context the central pattern of DDD's strategic design[24]. Bounded contexts are the natural candidates for modules (Section 5) or services (Section 6).
  • Context mapping describes the relationships between contexts, such as an anti-corruption layer that translates another context's model into yours. That translation is the adapter pattern (Section 13) at the architectural scale[23].

Tactical building blocks

  • Entities have identity that lasts over time. Value objects have no identity, are immutable and are compared by value[23].
  • Aggregates are clusters of objects treated as one unit for data changes. Outside code may hold references only to the aggregate root, which enforces the invariants of the whole cluster[23]. Vernon's guidance is to keep aggregates small, to reference other aggregates by identity only, and to use eventual consistency between aggregates[25].
  • Repositories give collection-like access to aggregate roots (Section 11). Factories encapsulate complex creation (Section 12)[23].
  • Domain events record that something the domain experts care about has happened. Vernon presents them as a first-class tactical pattern[25].

Go fits the tactical patterns well. Unexported fields mean an aggregate's state can be changed only through its methods, and value types such as Money are copied on assignment, so they behave as immutable values unless you hand out pointers.

Pitfall. DDD's tactical patterns are costly in simple CRUD domains. Evans aims DDD at complex domains, and the strategic patterns (language, contexts) usually repay the effort sooner than the tactical ones[23].

5. Modular monoliths

A modular monolith is a single deployable unit that is internally divided into modules with explicit boundaries. Each module owns its data and exposes a narrow public API, so the system can be developed as if it were several services while being deployed as one. Newman describes the modular monolith as an often-overlooked option that keeps the simplicity of single-process deployment while still allowing parallel work[26]. Shopify's engineering team described restructuring its large Rails monolith into components with enforced boundaries instead of splitting it into services[27]. Fowler's "MonolithFirst" argues that most successful microservice systems started as monoliths, and that boundaries are easier to get right after the domain is understood[28].

  • Each module owns its tables. Other modules read that data through the module's API, never by querying its tables directly. This is the in-process version of "database per service"[29].
  • Modules depend on narrow interfaces they declare themselves, as ordering.PriceLookup does, so a module can later be extracted behind a network client with no change to its callers.
  • Rules about which module may depend on which should be enforced by tests, not by convention alone (Exercise 4).

6. Microservices

Lewis and Fowler define the microservice architectural style as an approach to developing a single application as a suite of small services, each running in its own process and communicating with lightweight mechanisms, often an HTTP resource API. The services are built around business capabilities and can be deployed independently by fully automated machinery[30]. Newman stresses independent deployability as the key property, and recommends modelling services around business domains, which in practice often means bounded contexts[31].

Two practices are central:

  • Decentralised data. Each service owns its database, and other services may reach that data only through the service's API[29,30].
  • Design for failure. Any call across the network can be slow or fail, so callers must set timeouts and degrade gracefully[30,32].

Note what the order service does when inventory is down. It does not hang, because a context deadline bounds the call[13]. It returns 502 Bad Gateway, which tells its own callers the failure is upstream. Sections 18 to 20 add circuit breakers, sagas and bulkheads to this foundation.

Costs

Microservices trade in-process calls for network calls, with their latency, partial failure and serialisation costs. They replace ACID transactions with eventual consistency and sagas (Section 19), and they need mature automation for deployment and monitoring[30,31]. Conway's law, the observation that a system's design tends to copy the communication structure of the organisation that builds it, is often cited as the reason service boundaries should follow team boundaries[31,33]. For a single team, a modular monolith usually gives most of the benefit at a fraction of the cost[26,28].

7. Event-driven architecture

In an event-driven architecture, components communicate by producing and reacting to events: records that something has happened. A producer does not know which consumers exist, and consumers can be added without changing it. Fowler points out that "event-driven" is used for at least four different patterns[34]:

  1. Event notification: a thin event tells others that something changed. Consumers call back if they need details.
  2. Event-carried state transfer: the event carries enough data for consumers to keep a local copy, so they do not need to call back.
  3. Event sourcing: events are the system of record (Section 9).
  4. CQRS: often combined with events to update read models (Section 8).

Messaging systems typically deliver at least once, so consumers must tolerate duplicates. Hohpe and Woolf call a consumer that can safely receive the same message more than once an Idempotent Receiver[35]. Kleppmann explains why effectively-once processing in practice depends on idempotence or deduplication[36]. The in-process broker below gives each subscriber its own goroutine and buffered queue, a publish-subscribe channel in Hohpe and Woolf's terms[35], and shows the difference between an idempotent and a non-idempotent consumer.

Publishing reliably: the transactional outbox

A service that updates its database and then publishes an event can crash between the two steps, so the change happens but the event is lost. The transactional outbox pattern fixes this. The service writes the event to an outbox table in the same database transaction as the state change, and a separate relay process reads the outbox and publishes the events[37]. Because the relay may publish an event more than once, consumers still need to be idempotent.

Pitfall. Fowler warns that event notification makes it easy to lose sight of the larger flow. The logic is spread across many handlers, and only monitoring at run time shows how it fits together[34].

8. CQRS

Command Query Responsibility Segregation grew out of Bertrand Meyer's Command-Query Separation principle: a method should either change state (a command) or return a result (a query), but not both[38,39]. Greg Young applied the idea at the level of architecture. CQRS uses separate models for updating information and for reading it[40,41]. The write model is shaped for enforcing rules. Read models are denormalised projections shaped for particular screens or queries, and they can use different storage and scale independently[42].

Here the projection runs synchronously, so reads are immediately consistent. In most deployments the projection consumes events asynchronously, and the read model then lags behind the write model. Exercise 9 deals with the "I saved it, but it's not in the list" problem that follows from this.

Use sparingly. Fowler cautions that for most systems CQRS adds risky complexity. He suggests using it only for specific bounded contexts where reads and writes really differ, not for a whole system[41].

9. Event sourcing

Event sourcing stores every change to application state as an event in an append-only sequence. The current state is not stored. It is derived by replaying the events[43]. This gives a complete audit log, makes it possible to rebuild state as of any past moment, and lets you build new read models by replaying history[43,44]. Event sourcing pairs naturally with CQRS. The event stream is the write model, and projections build the read models[40].

The code below shows the three essential mechanics:

  1. Rehydration: state is a left fold of an apply function over the stream. apply must be deterministic and must never fail, because past events are facts.
  2. Decide, then record: command methods such as Withdraw validate first and then raise events.
  3. Optimistic concurrency: Append succeeds only if the stream is still at the version the writer loaded. Otherwise the second writer gets a conflict and must reload and retry[44].

Practical concerns

  • Snapshots: long streams are slow to replay, so a store saves the folded state periodically and replays only newer events (Exercise 8)[44].
  • Schema evolution: events are stored forever, so their formats need versioning or "upcasting" of old events when they are read[44].
  • External systems: replaying events must not resend emails or charge cards again. Side effects belong in event handlers that are disabled during a rebuild[43].
Part II · Design patterns

10. Dependency injection

Fowler coined the term "dependency injection" in 2004 for the form of inversion of control in which a separate assembler supplies an object with its collaborators. The object does not construct or look them up itself. He distinguished constructor, setter and interface injection, and contrasted all three with the Service Locator[45]. DI is how the Dependency Inversion Principle is put into practice: high-level policy depends on abstractions, and concrete implementations are plugged in from outside[11].

Idiomatic Go rarely needs a container. The usual recipe is:

  • Constructor injection: required dependencies are parameters of NewX(...).
  • Functional options for optional dependencies and settings, with sensible defaults.
  • Consumer-owned interfaces that are small enough to fake by hand[8].
  • A composition root, usually main, which is the only place that names concrete types.

Time is a hidden dependency in much code. Injecting a Clock turns "send reminders before 8 p.m." into a deterministic test. The logger is built with log/slog, the standard structured-logging package, and ReplaceAttr removes the time attribute so the output is reproducible[46].

Tools

When a dependency graph has dozens of nodes, two approaches are common. Google's Wire generates the wiring code at compile time from provider functions, so errors appear at build time and no reflection is used at run time[47]. Uber's Fx is a run-time framework that also manages application lifecycle hooks[48]. Both are optional. Hand-written wiring in main is easy to read and is enough for most services.

Pitfall. Avoid a global registry from which code fetches its own dependencies. That is the Service Locator, and it hides dependencies from function signatures[45]. The context documentation likewise says context values are for request-scoped data, not for passing optional parameters to functions[13].

11. Repository pattern

Fowler's definition: a Repository mediates between the domain and data mapping layers using a collection-like interface for accessing domain objects[17]. Evans adds that repositories should exist only for aggregate roots, and should give the illusion of an in-memory collection of all objects of that type[23]. Business code then deals with Customer values and never with SQL rows.

Design notes

  • Every method takes a context.Context so that cancellation and deadlines reach the database driver. database/sql provides QueryContext and ExecContext for this purpose[13,49].
  • Map storage errors to domain errors. sql.ErrNoRows becomes the repository's own ErrNotFound, wrapped with %w so callers can use errors.Is without importing database/sql[14,49].
  • Return values, not pointers into the store. Otherwise callers can change "persisted" state without calling Save.
  • The lines var _ CustomerRepository = ... check at compile time that both implementations satisfy the interface. This is a common Go idiom[9].
  • One contract test suite run against every implementation keeps fakes honest (Exercise 10).

Pitfall. Generic repositories such as Repository[T] with Find(filter any) leak query semantics into the domain. Prefer methods named in the ubiquitous language, such as ByEmailDomain, that express what the domain actually needs[23].

12. Factory pattern

The Gang of Four describe two creational patterns. Factory Method defines an interface for creating an object but lets subclasses decide which class to instantiate. Abstract Factory provides an interface for creating families of related objects without naming their concrete classes[50]. Go has no subclasses, so the idea appears in three simpler forms:

  1. Constructor functions such as NewX(...). Effective Go describes them as the conventional way to create values that need initialisation[9].
  2. A simple factory, a function that returns an interface and picks the implementation from its arguments or configuration.
  3. A registry, in which implementations register a constructor under a name, usually from an init function, and clients ask for one by name. The standard library uses this shape for database/sql drivers (sql.Register / sql.Open)[49] and for image formats (image.RegisterFormat)[51].

Like sql.Register, which panics if a driver name is registered twice[49], Register panics on a duplicate name. That is a programming error found at start-up, not a run-time condition. Constructors return an error when the options they are given are invalid.

Return concrete types from constructors where you can, and interfaces from factories that genuinely choose among implementations. Returning an interface from every constructor hides useful methods and works against the advice to define interfaces at the consumer[8].

13. Adapter pattern

Intent: convert the interface of a class into another interface clients expect, so that classes with incompatible interfaces can work together[50]. Adapters are the "adapters" of hexagonal architecture[21], and an anti-corruption layer in DDD is a large adapter that protects your model from another context's model[23].

The adapter converts between units (cents and dollars) and error conventions (vendor codes and wrapped sentinel errors), and it adds context support the legacy SDK lacks. NotifierFunc is the function-type adapter that the standard library uses for http.HandlerFunc, which lets an ordinary function with the right signature serve as an http.Handler[12].

14. Decorator pattern

Intent: attach additional responsibilities to an object dynamically. Decorators are a flexible alternative to subclassing for extending functionality[50]. A decorator implements the same interface as the object it wraps, so decorators can be stacked in any order. In Go this means a struct that holds an interface value and implements that same interface.

Read the stack from the outside in. The cache answered the second GOOG request without calling anything. The retry layer hid the first transient failure. The logging layer, being innermost, recorded every real upstream attempt. If you swap the order, the behaviour changes: with logging outermost you would see one line per logical call instead of one per attempt. Order is a design decision.

The standard library uses decorators throughout. bufio.NewReader wraps an io.Reader, and http.TimeoutHandler and http.StripPrefix wrap an http.Handler[12]. HTTP middleware (Section 17) is the decorator pattern applied to handlers.

15. Strategy pattern

Intent: define a family of algorithms, encapsulate each one, and make them interchangeable, so the algorithm can vary independently of the clients that use it[50]. In Go a strategy is either an interface, when it has state or several methods, or simply a function value[4].

slices.SortFunc is the strategy pattern in the standard library: the sorting algorithm is fixed, and the comparison function is passed in[52]. A strategy is often selected at run time from configuration, and that is where it meets the factory registry of Section 12.

16. Observer pattern

Intent: define a one-to-many dependency between objects, so that when one object changes state all its dependents are notified and updated automatically[50]. The subject knows only that its observers satisfy a small interface, here func(T), so it stays decoupled from them. The example uses a type parameter so the same subject works for any payload type[53].

Concurrency details that matter

  • Do not call observers while holding the lock. sync.Mutex is not re-entrant: Lock blocks until the mutex is available[54]. An observer that calls Subscribe or unsubscribe from inside a notification would therefore deadlock. Copy the list, unlock, then notify (Exercise 13).
  • Return an unsubscribe function. Without one, short-lived observers leak.
  • Observer or event bus? Observer is synchronous and in-process, and the subject and observers share a lifetime. When producers and consumers must be decoupled in time, or across processes, use events and a broker (Section 7)[35].

17. Middleware pattern

Middleware is code that sits in the request path around a handler and deals with cross-cutting concerns: logging, authentication, request IDs, panic recovery, timeouts, compression. Structurally it combines two GoF patterns. Each middleware is a decorator of http.Handler, and the composed stack is a chain of responsibility in which any link may handle the request and stop it from going further[50]. In Go a middleware is conventionally a function func(http.Handler) http.Handler, which works because http.Handler is a one-method interface and http.HandlerFunc adapts plain functions to it[12].

  • Order matters. Chain(mux, RequestID, Logging, Recover, RequireToken) makes RequestID the outermost layer. Because Recover sits inside Logging, the log line shows the 500 that Recover wrote. If Recover were outermost, Logging would never see the panicking request complete.
  • Context keys use an unexported struct type. The context documentation says keys should not be strings or other built-in types, to avoid collisions between packages[13].
  • Response wrappers such as statusRecorder capture the status code. A production wrapper should also forward optional interfaces such as http.Flusher, or use http.ResponseController, so that streaming responses keep working[12].
  • net/http recovers panics in handlers on its own, but only by logging the panic and closing the connection[12]. A Recover middleware returns a proper 500 response instead.
Part III · Resilience and operations

18. Circuit breaker

Michael Nygard popularised the circuit breaker for software in Release It!. When calls to a dependency keep failing, the breaker "trips" and fails further calls immediately for a while, instead of letting every caller wait on timeouts and pile up threads and connections[32]. Fowler describes the three states[55]:

  • Closed: calls pass through and failures are counted.
  • Open: after a threshold of failures, calls fail fast without touching the dependency.
  • Half-open: after a cool-down period, a trial call is allowed. If it succeeds the breaker closes, and if it fails the breaker opens again.

Microsoft's guidance adds that a breaker is not a retry mechanism. Its purpose is to stop calls that are likely to fail, and it should be paired with timeouts and with monitoring of state changes[56].

  • The lock is released before fn runs. Holding it would serialise every call to the dependency.
  • Only one probe is allowed while half-open, so a recovering dependency is not hit by every waiting caller at once.
  • The clock is injectable (Section 10), so state transitions can be tested without sleeping (Exercise 12).
  • For production use, a maintained library such as Sony's gobreaker provides the same state machine with counts, a configurable trip function and state-change callbacks[57].

19. Saga pattern

Garcia-Molina and Salem introduced sagas in 1987 for long-lived transactions that should not hold database locks for their whole duration. A saga is a sequence of transactions T1…Tn, each with a compensating transaction Ci that semantically undoes Ti. The system guarantees that either the whole sequence T1…Tn runs, or some prefix T1…Tj runs followed by the compensations Cj…C1[58]. In microservices, where each service has its own database and distributed ACID transactions are impractical, sagas are the standard way to keep data consistent across services[59,60].

Richardson describes two ways to coordinate a saga[60]:

  • Choreography: each service listens for events and decides on its own what to do next (Section 7). There is no central coordinator, but the flow is implicit.
  • Orchestration: an orchestrator tells each participant what to do and tracks progress. The flow is explicit and easier to follow. The example below is an orchestrator.

What production sagas also need

  • Durable state. The orchestrator must persist which steps have completed, so that after a crash it can resume or compensate. Section 7's outbox fits naturally here[37].
  • Idempotent, retryable compensations. A compensation cannot simply fail. It is retried until it succeeds or is escalated to a person (Exercise 14).
  • Lack of isolation. Other transactions can see a saga's intermediate states, for example a booked flight whose hotel is not booked yet. Richardson lists countermeasures such as semantic locks, for example a status of PENDING[59].
  • Ordering steps well. Put steps that are likely to fail, and steps that cannot be compensated (such as charging a card or sending an email), as late as possible. Richardson calls the step after which the saga cannot fail its pivot transaction[59].

20. Bulkhead pattern

Ships are divided into watertight compartments, called bulkheads, so that a breach floods one compartment instead of sinking the ship. Nygard applies the idea to software: partition resources such as threads, connections and instances so that a failure or overload in one part cannot exhaust the resources of the others[32]. Microsoft's description is the same: isolate the elements of an application into pools so that if one fails, the others continue to work[61].

In Go the natural resource to limit is concurrency. A buffered channel makes a simple counting semaphore. Each dependency gets its own semaphore, and callers that cannot get a slot quickly are rejected instead of queueing forever.

The burst of slow report requests filled the two report slots, and the other eight were rejected after waiting at most 50 ms. Payments, drawing from a separate pool, all succeeded during the same period. Without the bulkheads, the report requests could have used up every goroutine, connection or upstream quota the process had.

  • golang.org/x/sync/semaphore provides a weighted semaphore with context-aware Acquire and non-blocking TryAcquire, which is useful when calls have different costs[62].
  • Bulkheads exist at several scales: per-dependency connection pools (database/sql's SetMaxOpenConns[49]), separate worker pools, and separate service instances for different classes of client[61].
  • Bulkheads and circuit breakers work well together. The bulkhead limits how much damage a slow dependency can do, and the breaker stops calling it once it is clearly unhealthy[32].

21. Twelve-factor applications

Factor names and summaries from Wiggins[63]; Go mappings are the author's.

  • Configuration errors are collected with errors.Join[15] and reported together at start-up, so a bad deploy fails at once instead of at the first request.
  • LoadConfig takes a getenv function instead of calling os.Getenv directly. That is dependency injection again, and it makes the function testable (Exercise 16).
  • signal.NotifyContext returns a context that is cancelled when one of the listed signals arrives[64]. Server.Shutdown stops accepting new connections and waits for active requests to finish, up to the deadline of the context it is given[12].
  • The twelve-factor logs factor says an app should not concern itself with routing or storing its output stream. It writes to stdout and lets the environment collect the stream[63].

Choosing an approach

These styles are not alternatives in a single list. They answer different questions, and real systems combine them: a modular monolith whose modules are bounded contexts, each built hexagonally, with an event-sourced, CQRS-style module where an audit trail matters.

Exercises marked code have solutions that were compiled and tested with go test -race. Those marked design ask for reasoning, and their model answers cite the relevant sources. Try each one before opening the solution.

codeExercise 1. Invert the layered dependency

In the layered example (Section 1), CatalogService depends on the concrete *ProductTable. Refactor it so that the business layer declares the abstraction it needs and the data layer satisfies it. Then write a unit test for Product that uses no storage at all.

Show solution

Declare a one-method ProductReader interface in the business package, which is where the Go guidelines say interfaces belong[8], and accept it in the constructor. *ProductTable already has a matching FindByID method, so it satisfies the interface without any change. This is the Dependency Inversion Principle: the high-level module now owns the abstraction[11]. A map type with one method is enough for a stub.

codeExercise 2. Drive the hexagon from a test

Write tests for the hexagonal booking core (Section 3) that use no HTTP and no real notifier. Check that (a) reserving a seat that is already taken returns ErrSeatTaken and sends no notification, and (b) a notifier failure is returned to the caller.

Show solution

A test is just another driving adapter, and a fake notifier is just another driven adapter. Cockburn's intent is that the application can be driven by automated tests in isolation from its devices[21]. t.Run groups the two cases as subtests[65].

codeExercise 3. Harden the aggregate

Extend the DDD order (Section 4) with (a) a Quantity value object that only allows 1–999, including after two lines for the same SKU are merged, (b) a RemoveLine behaviour, and (c) the invariant "an order with no lines cannot be placed".

Show solution

Invariants live inside the aggregate root, the only entry point for changes[23]. The value object validates itself on construction, so an invalid Quantity cannot exist. Merging re-validates by building a new value instead of mutating the old one.

designExercise 5. Monolith or microservices?

A start-up with six engineers in one team is building a marketplace with catalog, ordering, payments and notifications. Traffic is modest, but they expect to grow. One engineer proposes four microservices from day one. What would you recommend, and what would make you change your mind?

Show solution

Recommend a modular monolith with four modules aligned to bounded contexts, each owning its own tables and exposing a narrow API (Section 5). The reasons:

  • Microservices carry significant operational costs: distributed failure, eventual consistency, and the automation needed for independent deploys[30,31]. A team of six would spend much of its time on infrastructure.
  • Boundaries are hard to get right before the domain is understood, and moving a boundary between services is far more expensive than moving one between modules. Fowler's MonolithFirst makes this argument[28], and Newman presents the modular monolith as a legitimate long-term choice, not only a stepping stone[26].
  • With one team, Conway's law suggests a single deployable unit anyway[33].

Signals to extract a service: several teams need to deploy independently, one module has very different scaling or availability needs (payments, for example), or a module needs a different technology. Because modules already talk through interfaces such as PriceLookup, extraction means writing a network adapter (Section 6) behind the existing interface.

codeExercise 6. Retries and a dead-letter queue

The broker in Section 7 just prints handler errors. Write a handler wrapper that retries with exponential backoff and, if the event still fails, sends it to a dead-letter function and moves on, so a single "poison" event cannot block a queue.

Show solution

Hohpe and Woolf's Dead Letter Channel is where a messaging system moves messages it cannot deliver or process[35]. The wrapper is a decorator (Section 14) around Handler. Tests pass a base delay of 0 so they run instantly.

designExercise 7. Fix the double-counted revenue

In Section 7 the analytics consumer counted one order twice because the event was delivered twice. The in-memory Idempotent wrapper would fix the demo, but in production the consumer runs as several replicas and restarts often. How do you make it idempotent?

Show solution

The deduplication record must be durable, shared, and updated atomically with the effect. An in-memory map is lost on restart and is not shared between replicas.

  1. Give every event a unique ID at the producer. The outbox row ID works well[37].
  2. In the consumer, use one database transaction to insert the event ID into a processed_events table that has a unique constraint, and to apply the effect (UPDATE revenue SET total = total + $1). A duplicate violates the constraint, and the transaction rolls back without applying the effect a second time.
  3. Alternatively, make the effect naturally idempotent. For example, store per-order revenue keyed by order ID with an upsert, and compute the total from it.

This is the Idempotent Receiver pattern[35]. Kleppmann explains why exactly-once effects on top of at-least-once delivery depend on this kind of atomic deduplication[36].

codeExercise 8. Snapshots for event-sourced aggregates

Add snapshotting to an event store so that loading an aggregate replays at most N events after the latest snapshot. Show with a test that, after 1,050 events with N = 100, a load replays only 50 events and still gives the correct balance.

Show solution

A snapshot is a cached left fold: a version number plus the state at that version. Loading starts from the snapshot and replays only the events after it. Snapshots are an optimisation, and the events remain the source of truth[43,44].

designExercise 9. "I saved it, but it isn't in the list"

Your CQRS projection now runs asynchronously and lags a few hundred milliseconds behind the write model. Users create a task and are sent to a list page that does not show it yet. Give three ways to deal with this.

Show solution
  1. Return the version and wait for it. The command returns the position of the event it produced. The read model records the last position it has applied, and the query waits briefly (or the client polls) until projection.Version ≥ v.
  2. Update the UI optimistically. The client already knows what it submitted and shows it straight away, then reconciles when the read model catches up.
  3. Read your own writes from the write side. Serve that particular user's next request from the write model, or project synchronously for this one view, while other views stay asynchronous.

All three accept that read models are eventually consistent, which is an inherent trade-off of CQRS with separate stores[41,42]. If none of them is acceptable for a screen, that screen probably should not use a separate read model.

codeExercise 10. A repository contract test

Write one test suite that any CustomerRepository implementation must pass. Run it against the in-memory implementation from Section 11, and explain how you would run it against SQLCustomers.

Show solution

The suite takes a factory function, so each subtest gets a fresh, empty repository. The in-memory version runs on every go test. For SQL, add a second test function that opens a real database (for example from a TEST_DATABASE_URL environment variable, calling t.Skip when it is not set[65]), creates the schema, and calls the same testRepositoryContract. Because both implementations pass the same suite, the fast fake used in other tests is known to behave like the real thing.

codeExercise 11. A TTL cache decorator

codeExercise 12. Test the circuit breaker's state machine

Write tests for the breaker in Section 18 that check: non-consecutive failures do not trip it; consecutive failures do; an open breaker rejects calls; a failed half-open probe re-opens it; and only one probe runs at a time.

Show solution

A fake clock moves time forward instantly. The concurrent-probe case blocks the first probe on a channel, checks that a second call is rejected with ErrOpen, and then releases the first probe. This follows the half-open behaviour Fowler describes[55].

designExercise 13. Why copy before notifying?

A colleague "simplifies" Subject.Notify in Section 16 so that it loops over s.observers while holding s.mu. The tests still pass. Then, in production, an observer that unsubscribes itself after its first notification hangs the program. Explain why.

Show solution

Notify holds s.mu and calls the observer. The observer calls unsubscribe, which calls s.mu.Lock(). sync.Mutex is not re-entrant, and Lock blocks until the mutex becomes available[54]. It never will, because the goroutine waiting for it is the same one that holds it, so the program deadlocks. Copying the observer list under the lock and calling the observers after unlocking avoids this, and it also stops a slow observer from blocking Subscribe in other goroutines. The tests passed because none of them re-entered the subject. Add one that does.

codeExercise 14. Saga compensations that retry

Change the saga orchestrator (Section 19) so that each compensation is retried with exponential backoff, and so that compensations that still fail are reported together with the original error. Test that compensations run in reverse order and that a compensation that fails twice and then succeeds is still applied.

Show solution

Garcia-Molina and Salem assume compensations eventually succeed[58], so in practice they are retried, which is only safe if they are idempotent[59]. errors.Join keeps every failure available to errors.Is[15].

designExercise 15. Stacking resilience patterns

A handler calls a remote pricing service. You have a per-attempt timeout, retries, a circuit breaker and a bulkhead. In what order should they wrap the call, from outermost to innermost, and why?

Show solution

A common, defensible order is bulkhead → circuit breaker → retry → per-attempt timeout → call, with an overall deadline from the request context covering everything.

  • Bulkhead outermost: it caps concurrent work against this dependency, including any retries, so a slow dependency can hold at most N slots[61].
  • Breaker outside retry: when the breaker is open, the call fails fast without spending retries. If the breaker were inside the retry loop, each retry would just get ErrOpen, unless the retry layer treats ErrOpen as not worth retrying. Microsoft warns against retrying operations a breaker has marked as failing[56].
  • Retry outside the per-attempt timeout: each attempt gets its own deadline, and the retry layer decides whether to try again.
  • Everything inside the request deadline, so the total time cannot exceed what the caller is prepared to wait. context propagates the deadline through each layer[13].

Each layer is a decorator over the same function signature (Section 14), so the order is a single, visible line of wiring in the composition root.

codeExercise 16. Test twelve-factor configuration

Write a unit test for LoadConfig in Section 21 that does not touch the real process environment. Check one valid configuration and one invalid one.

Show solution

Because LoadConfig receives getenv as a parameter, a test can pass a map lookup. This avoids changing global state, so the tests can safely run in parallel. (t.Setenv also works, but it cannot be used in parallel tests[65].)
