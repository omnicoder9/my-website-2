Object-Oriented Programming in Go

A technical article with runnable examples, exercises and solutions · Examples verified with Go 1.27.3 (go run, gofmt, go vet, go test -race) · References in Vancouver style

Abstract. Go has no classes, no constructors in the language, no inheritance and no implements keyword, yet it supports an object-oriented style of programming. It does so with four small mechanisms: methods that can be declared on any defined type, package-level visibility controlled by the case of an identifier's first letter, interfaces that are satisfied implicitly, and embedding, which composes types rather than deriving one from another. This article shows how the classical ideas of encapsulation, abstraction and polymorphism map onto those mechanisms; covers interfaces in depth (declaration, implicit satisfaction, the empty interface any, type assertions, type switches, composition and embedding); explains struct embedding, method sets and why embedding is not subclassing; and then applies the pieces to dependency injection, the SOLID principles and the classic design patterns. Every claim is referenced to the language specification, the Go authors' documentation or the primary literature, and every program shown was compiled and run to produce the output printed beneath it.

1. Overview: is Go object-oriented?

The Go FAQ answers the question directly: "Yes and no. Although Go has types and methods and allows an object-oriented style of programming, there is no type hierarchy." It continues that interfaces provide "a different approach that we believe is easy to use and in some ways more general", that embedding provides "something analogous—but not identical—to subclassing", and that methods "can be defined for any sort of data, even built-in types such as plain, 'unboxed' integers. They are not restricted to structs (classes)" [1].

The omission of inheritance was deliberate. In his 2012 SPLASH keynote Rob Pike described Go's approach as "methods on any type, not just classes, but without any form of type-based inheritance like subclassing. This means there is no type hierarchy. This was an intentional design choice." He argued that "Type hierarchies result in brittle code. The hierarchy must be designed early, often as the first step of designing the program, and early decisions can be difficult to change once the program is written", and concluded: "Go therefore encourages composition over inheritance, using simple, often one-method interfaces to define trivial behaviors that serve as clean, comprehensible boundaries between components" [2].

The rest of this article follows the order of the classical OOP vocabulary, but the Go answer to each item is assembled from the same four mechanisms:

2. Building blocks: types and methods

A method is a function with a receiver. The specification requires the receiver's base type to be a defined type declared in the same package, and that type "must not be a pointer or interface type" [3]. Any defined type qualifies, not only structs, so an int-based or float64-based type can carry methods just as well as a struct can [1]. A value receiver operates on a copy; a pointer receiver can modify the caller's value. When a variable is addressable, the call x.m() on a pointer method is shorthand for (&x).m() [3].

ex01_methods/main.go 
// Example 1: Go's "objects" are values of defined types with methods.
package main

import (
	"fmt"
	"math"
)

// Celsius is a defined type with an underlying float64. Methods can be
// declared on it even though it is not a struct.
type Celsius float64

func (c Celsius) Fahrenheit() float64 { return float64(c)*9/5 + 32 }

func (c Celsius) String() string { return fmt.Sprintf("%.1f°C", float64(c)) }

// Point is a struct type: data (fields) plus behaviour (methods).
type Point struct{ X, Y float64 }

// Dist has a value receiver: it works on a copy of the Point.
func (p Point) Dist(q Point) float64 { return math.Hypot(q.X-p.X, q.Y-p.Y) }

// Scale has a pointer receiver: it modifies the caller's Point.
func (p *Point) Scale(f float64) { p.X *= f; p.Y *= f }

func main() {
	t := Celsius(21.5)
	fmt.Println(t, "=", t.Fahrenheit(), "°F") // String() is used by fmt

	p := Point{3, 4}
	fmt.Println(p.Dist(Point{}))
	p.Scale(2) // shorthand for (&p).Scale(2): p is addressable
	fmt.Println(p)

	// A method expression turns a method into an ordinary function
	// whose first parameter is the receiver.
	dist := Point.Dist
	fmt.Println(dist(Point{0, 0}, Point{6, 8}))
}
Output 
21.5°C = 70.7 °F

{6 8}
10

Three details recur throughout this article. First, there is no special "constructor": by convention a package provides a function such as New or NewThing that returns an initialised value [5]. Second, fmt prints a value using its String method when the value implements fmt.Stringer, which Celsius does without declaring so [6]. Third, the method expression Point.Dist yields an ordinary function whose first argument is the receiver, which shows that a method really is a function with a distinguished first parameter [3,7].

3. Encapsulation

Encapsulation, or information hiding, means that a module exposes a stable interface while keeping design decisions that are likely to change behind it. Parnas's classic formulation is that modules should be chosen so that each "hides" a design decision from the others [8]. In Go the unit of hiding is the package, not the type: there are no private, protected or public keywords, and every file in a package can see every identifier declared in that package [3,7].

3.1 Exported and unexported identifiers

Visibility is decided by spelling. The specification states that an identifier is exported if "the first character of the identifier's name is a Unicode uppercase letter (Unicode character category Lu); and the identifier is declared in the package block or it is a field name or method name. All other identifiers are not exported" [3]. Effective Go notes that names therefore "have semantic effect: the visibility of a name outside a package is determined by whether its first character is upper case" [5].

The same rule applies to types, functions, constants, variables, struct fields and methods. An exported struct type with unexported fields is the usual way to build an encapsulated "object": other packages can hold and pass the value, but can change it only through the exported methods, which are therefore able to enforce invariants. Effective Go recommends that getters omit the Get prefix ("the getter method should be called Owner (upper case, exported), not GetOwner") while setters, if needed, are called SetOwner [5].

ex02_encapsulation/bank/account.go 
// Package bank shows encapsulation through Go's export rules.
package bank

import (
	"errors"
	"fmt"

	"example.com/oop/ex02_encapsulation/bank/internal/ledger"
)

// ErrInsufficientFunds is exported so callers can test for it.
var ErrInsufficientFunds = errors.New("bank: insufficient funds")

// minimumOpening is unexported: an implementation detail of the package.
const minimumOpening = 100

// Account is exported; its fields are not, so other packages can only
// change an Account through its methods, which enforce the invariants.
type Account struct {
	owner   string
	balance int64 // cents; invariant: balance >= 0
	history []ledger.Entry
}

// New is the constructor. It validates input before an Account exists.
func New(owner string, opening int64) (*Account, error) {
	if opening < minimumOpening {
		return nil, fmt.Errorf("bank: opening deposit %d below minimum %d", opening, minimumOpening)
	}
	a := &Account{owner: owner}
	a.record("open", opening)
	return a, nil
}

// Owner is a getter. By convention it is not called GetOwner.
func (a *Account) Owner() string { return a.owner }

// Balance exposes the balance read-only.
func (a *Account) Balance() int64 { return a.balance }

func (a *Account) Deposit(amount int64) error {
	if amount <= 0 {
		return errors.New("bank: deposit must be positive")
	}
	a.record("deposit", amount)
	return nil
}

func (a *Account) Withdraw(amount int64) error {
	if amount > a.balance {
		return ErrInsufficientFunds
	}
	a.record("withdraw", -amount)
	return nil
}

// Statement returns a copy so callers cannot alias internal state.
func (a *Account) Statement() []string {
	out := make([]string, len(a.history))
	for i, e := range a.history {
		out[i] = e.String()
	}
	return out
}

// record is unexported: callable from any file in package bank only.
func (a *Account) record(kind string, amount int64) {
	a.balance += amount
	a.history = append(a.history, ledger.Entry{Kind: kind, Amount: amount})
}

3.2 Package-level visibility

Because unexported identifiers are visible throughout their package, all files of a package share them, and methods of one type may freely read the unexported fields of another type in the same package. The scope of a top-level constant, type, variable or function "is the package block" [3]. Package design therefore is encapsulation design in Go: deciding what goes in a package determines what can see what. The Go blog recommends short, lower-case package names chosen so that client code reads well, for example bytes.Buffer rather than bytes.ByteBuffer [9].

Two forms of access, exported and unexported, are sometimes not enough. The Go 1.4 release notes put the problem this way: "there are only two forms of access: local (unexported) and global (exported). Sometimes one wishes to have components that are not exported", and introduced internal packages: "When the go command sees an import of a package with internal in its path, it verifies that the package doing the import is within the tree rooted at the parent of the internal directory" [10,11]. In the bank example, bank/internal/ledger may be imported by bank and anything below it, but by nothing else. The official module-layout guide recommends internal for supporting packages precisely because "other projects cannot import code from our internal directory, we're free to refactor its API" [12].

4. Abstraction

Abstraction means programming against what something does rather than how it does it. Cardelli and Wegner describe data abstraction as separating a type's behaviour, given by its operations, from its representation [13]; Pike describes the same "powerful insight" of OOP: "that the behavior of data can be generalized independently of the representation of that data" [2]. Go has two tools for it: encapsulated concrete types (section 3), whose representation is hidden behind methods, and interfaces, which name a behaviour with no representation at all.

Effective Go's section on generality shows the second in the standard library: "in the hash libraries both crc32.NewIEEE and adler32.New return the interface type hash.Hash32. Substituting the CRC-32 algorithm for Adler-32 in a Go program requires only changing the constructor call; the rest of the code is unaffected by the change of algorithm" [5,14].

ex03_abstraction/main.go 
// Example 3: abstraction. Code depends on what a value does (hash.Hash32),
// not on how it does it (CRC-32 or Adler-32).
package main

import (
	"fmt"
	"hash"
	"hash/adler32"
	"hash/crc32"
	"io"
	"strings"
)

// checksum knows nothing about any concrete algorithm.
func checksum(h hash.Hash32, r io.Reader) (uint32, error) {
	if _, err := io.Copy(h, r); err != nil { // a Hash is an io.Writer
		return 0, err
	}
	return h.Sum32(), nil
}

func main() {
	const text = "The quick brown fox jumps over the lazy dog"

	// Both constructors return the interface type hash.Hash32, so swapping
	// the algorithm changes only the constructor call.
	algorithms := []struct {
		name string
		h    hash.Hash32
	}{
		{"crc32", crc32.NewIEEE()},
		{"adler32", adler32.New()},
	}
	for _, a := range algorithms {
		sum, err := checksum(a.h, strings.NewReader(text))
		if err != nil {
			panic(err)
		}
		fmt.Printf("%-7s %08x  (size %d bytes)\n", a.name, sum, a.h.Size())
	}
}
Output 
crc32   414fa339  (size 4 bytes)
adler32 5bdc0fda  (size 4 bytes)

checksum depends on two abstractions only: hash.Hash32 (to read the result) and io.Reader. Because every hash.Hash embeds io.Writer, the hash can be the destination of io.Copy [15]. Note the balance the Go authors recommend: return an interface from a constructor when the type "exists only to implement an interface", as here [5]; otherwise, return a concrete type and let consumers define the interfaces they need (section 10) [16].

5. Polymorphism

Cardelli and Wegner distinguish universal polymorphism, which comes in parametric and inclusion (subtype) forms, from ad hoc polymorphism such as overloading [13]. Go has the first two and deliberately omits the third:

  • Subtype polymorphism via interfaces. A variable of interface type can hold any value whose type implements the interface, and a method call on it "denotes the actual method with name f of the dynamic value" [3]. The FAQ is explicit that "The only way to have dynamically dispatched methods is through an interface. Methods on a struct or any other concrete type are always resolved statically" [1].
  • Parametric polymorphism via generics. Since Go 1.18 functions and types can have type parameters constrained by interfaces; each use is type-checked statically [3,4].
  • No overloading. "Method dispatch is simplified if it doesn't need to do type matching as well … Matching only by name and requiring consistency in the types was a major simplifying decision in Go's type system" [1].
ex04_polymorphism/main.go 
// Example 4: polymorphism. Subtype polymorphism via interfaces (dynamic
// dispatch) and parametric polymorphism via generics (static).
package main

import (
	"cmp"
	"fmt"
	"math"
	"slices"
)

type Shape interface {
	Area() float64
	Perimeter() float64
}

type Circle struct{ R float64 }
type Rect struct{ W, H float64 }
type Triangle struct{ A, B, C float64 } // side lengths

func (c Circle) Area() float64        { return math.Pi * c.R * c.R }
func (c Circle) Perimeter() float64   { return 2 * math.Pi * c.R }
func (r Rect) Area() float64          { return r.W * r.H }
func (r Rect) Perimeter() float64     { return 2 * (r.W + r.H) }
func (t Triangle) Perimeter() float64 { return t.A + t.B + t.C }
func (t Triangle) Area() float64 { // Heron's formula
	s := t.Perimeter() / 2
	return math.Sqrt(s * (s - t.A) * (s - t.B) * (s - t.C))
}

// Total works for every current and future Shape: the call s.Area()
// is dispatched at run time on the dynamic type stored in s.
func Total(shapes []Shape) (area float64) {
	for _, s := range shapes {
		area += s.Area()
	}
	return area
}

// Largest is parametric: one generic function, instantiated per type.
func Largest[S Shape](shapes []S) S {
	return slices.MaxFunc(shapes, func(a, b S) int { return cmp.Compare(a.Area(), b.Area()) })
}

func main() {
	shapes := []Shape{Circle{1}, Rect{3, 4}, Triangle{3, 4, 5}}
	for _, s := range shapes {
		fmt.Printf("%-16s area=%6.2f perimeter=%6.2f\n", fmt.Sprintf("%T", s), s.Area(), s.Perimeter())
	}
	fmt.Printf("total area = %.2f\n", Total(shapes))

	rects := []Rect{{1, 1}, {2, 5}, {3, 3}}
	fmt.Println("largest rect:", Largest(rects)) // S inferred as Rect
}
Output 
main.Circle      area=  3.14 perimeter=  6.28
main.Rect        area= 12.00 perimeter= 14.00
main.Triangle    area=  6.00 perimeter= 12.00
total area = 21.14
largest rect: {2 5}

Total is written once and works for any present or future Shape; adding a new shape requires no change to it. Largest uses the same interface as a constraint: it is instantiated for []Rect and returns a Rect, not a Shape, so no type assertion is needed by the caller. Use an interface-typed parameter when values of different types must be mixed at run time; use a type parameter when one call deals with one type and the static result type matters [4].

6. Interfaces

Interfaces are the centre of Go's object model. Effective Go summarises their purpose: "Interfaces in Go provide a way to specify the behavior of an object: if something can do this, then it can be used here" [5]. Formally, "An interface type defines a type set. A variable of interface type can store a value of any type that is in the type set of the interface. Such a type is said to implement the interface. The value of an uninitialized variable of interface type is nil" [3].

6.1 Interface declarations

In its basic form an interface is a list of method signatures: "The type set defined by such an interface is the set of types which implement all of those methods" [3]. Method names in an interface must be unique and not blank [3]. By convention, "one-method interfaces are named by the method name plus an -er suffix or similar modification to construct an agent noun: Reader, Writer, Formatter, CloseNotifier etc." [5]. Interfaces in idiomatic Go are small; Rob Pike's proverb puts it as "The bigger the interface, the weaker the abstraction" [17].

type Shape interface {
	Area() float64
	Perimeter() float64
}

type Stringer interface { String() string } // fmt.Stringer
type Writer interface { Write(p []byte) (n int, err error) } // io.Writer

Interfaces whose element is a type rather than a method (for example interface{ ~int | ~float64 }) are general interfaces; they may only be used as type constraints, not as the type of a variable [3]. Go 1.27 introduced generic methods on concrete types, but the release notes are explicit that "methods of interfaces may not declare type parameters nor can interface methods be implemented by generic methods" [18], so the following is still an error:

6.2 Implicit interface implementation

Go has no implements clause. The FAQ: "A Go type implements an interface by implementing the methods of that interface, nothing more. This property allows interfaces to be defined and used without needing to modify existing code. It enables a kind of structural typing that promotes separation of concerns and improves code re-use" [1]. Satisfaction is still checked statically: "interface satisfaction is statically checked at compile time so despite this decoupling interfaces are type-safe" [2].

Implicit satisfaction works in both directions across package boundaries. Your type can implement an interface from the standard library without importing anything special, and a standard-library type can implement an interface you declare after the fact.

ex05_interfaces/main.go 
// Example 5: declaring interfaces and satisfying them implicitly.
package main

import (
	"fmt"
	"strings"
)

// A one-method interface named with the -er convention.
type Writer interface {
	Write(p []byte) (n int, err error)
}

// Logger depends only on the Writer interface it declares itself.
type Logger struct {
	out    Writer
	prefix string
}

func (l Logger) Log(msg string) { fmt.Fprintf(l.out, "%s%s\n", l.prefix, msg) }

// Upper is our own type. It never mentions Writer, yet it implements it.
type Upper struct{ sb strings.Builder }

func (u *Upper) Write(p []byte) (int, error) {
	return u.sb.WriteString(strings.ToUpper(string(p)))
}

// Version implements fmt.Stringer, an interface from another package,
// again without naming it.
type Version struct{ Major, Minor, Patch int }

func (v Version) String() string { return fmt.Sprintf("v%d.%d.%d", v.Major, v.Minor, v.Patch) }

// Compile-time assertions: the build fails if these stop being true.
var (
	_ Writer       = (*Upper)(nil)
	_ Writer       = (*strings.Builder)(nil) // a standard-library type
	_ fmt.Stringer = Version{}
)

func main() {
	var sb strings.Builder // *strings.Builder has Write: it is a Writer
	Logger{out: &sb, prefix: "[std] "}.Log("hello")
	fmt.Print(sb.String())

	u := &Upper{}
	Logger{out: u, prefix: "[up] "}.Log("hello")
	fmt.Print(u.sb.String())

	fmt.Println("running", Version{1, 27, 3}) // fmt calls String()
}
Output 
[std] hello
[UP] HELLO
running v1.27.3

The block of var _ I = ... declarations is the idiom recommended by the FAQ and Effective Go to make the compiler confirm that a type implements an interface where no ordinary assignment would otherwise check it [1,5]. Effective Go adds a caution: "Don't do this for every type that satisfies an interface, though. By convention, such declarations are only used when there are no static conversions already present in the code, which is a rare event" [5]. The FAQ also explains why there is no type hierarchy to declare: "Types can satisfy many interfaces at once, without the complexities of traditional multiple inheritance … Interfaces can be added after the fact if a new idea comes along or for testing—without annotating the original types" [1].

Signatures must match exactly. A method func (t T) Equal(u T) bool does not satisfy interface{ Equal(Equaler) bool }: "The argument type of T.Equal is T, not literally the required type Equaler" [1]. Go has no covariant or contravariant method matching.

6.3 The empty interface (any) and interface values

An interface with no methods places no requirement on its type set, so "all types implement the empty interface". Since Go 1.18, "the predeclared type any is an alias for the empty interface; it is not a named type" [3,19]. any and interface{} are therefore interchangeable.

To use any well, one has to know what an interface value is. Pike's "Laws of Reflection" explains that "A variable of interface type stores a pair: the concrete value assigned to the variable, and that value's type descriptor" [20]; Russ Cox's description of the implementation shows the pair as a pointer to type information (an itab for non-empty interfaces) and a pointer to the data [21]. The FAQ draws the important consequence: "An interface value is nil only if the V and T are both unset … If we store a nil pointer of type *int inside an interface value, the inner type will be *int regardless of the value of the pointer … Such an interface value will therefore be non-nil even when the pointer value V inside is nil" [1].

ex06_any/main.go 
// Example 6: the empty interface (any) and the nil-interface trap.
package main

import (
	"errors"
	"fmt"
)

type MyError struct{ Code int }

func (e *MyError) Error() string { return fmt.Sprintf("code %d", e.Code) }

// bad returns a typed nil pointer inside a non-nil error interface.
func bad(fail bool) error {
	var p *MyError // nil pointer
	if fail {
		p = &MyError{500}
	}
	return p // WRONG: the interface holds (type=*MyError, value=nil)
}

// good returns an untyped nil when there is no error.
func good(fail bool) error {
	if fail {
		return &MyError{500}
	}
	return nil
}

func main() {
	// any is an alias for interface{}: every type implements it.
	values := []any{42, "gopher", 3.5, []int{1, 2}, nil, struct{ X int }{7}}
	for _, v := range values {
		fmt.Printf("%-10s dynamic type %T\n", fmt.Sprint(v), v)
	}

	var a any = 7
	var b interface{} = 7
	fmt.Println("a == b:", a == b) // same dynamic type and value

	fmt.Println("bad(false) == nil: ", bad(false) == nil)
	fmt.Println("good(false) == nil:", good(false) == nil)

	var target *MyError
	fmt.Println("errors.As:", errors.As(good(true), &target), target.Code)
}
Output

The FAQ's advice follows: "It's a good idea for functions that return errors always to use the error type in their signature … rather than a concrete type such as *MyError", and to return an explicit nil on success [1]. More generally, any throws away static type information. Pike's proverb is "interface{} says nothing" [17]: prefer a specific interface or a type parameter, and reserve any for genuinely heterogeneous data such as fmt arguments or decoded JSON [6,22].

6.4 Type assertions

A type assertion recovers a more specific type from an interface value. "For an expression x of interface type … and a type T, the primary expression x.(T) asserts that x is not nil and that the value stored in x is of type T" [3]. If T is a concrete type, the dynamic type must be identical to T; if T is an interface type, the dynamic type must implement T. A failed single-value assertion panics, while the two-value form v, ok := x.(T) "yields an additional untyped boolean value … No run-time panic occurs in this case" [3].

Asserting to an interface type is how Go code discovers optional capabilities. Effective Go describes the JSON encoder checking m, ok := val.(json.Marshaler) at run time [5,22], and the io package documents several such "upgrades": for example, io.Copy uses WriterTo or ReaderFrom if the source or destination implements them [15].

ex07_assertions/main.go 
// Example 7: type assertions, comma-ok, and optional-interface upgrades.
package main

import (
	"errors"
	"fmt"
	"io"
	"io/fs"
	"os"
	"strings"
)

// Flusher is an optional capability some writers have.
type Flusher interface{ Flush() error }

type bufWriter struct {
	buf     strings.Builder
	pending int
}

func (b *bufWriter) Write(p []byte) (int, error) { b.pending += len(p); return b.buf.Write(p) }
func (b *bufWriter) Flush() error {
	fmt.Println("  flushed", b.pending, "bytes")
	b.pending = 0
	return nil
}

// emit takes any io.Writer but upgrades to Flusher when possible.
func emit(w io.Writer, msg string) {
	io.WriteString(w, msg)
	if f, ok := w.(Flusher); ok { // assertion to an interface type
		f.Flush()
	}
}

func main() {
	var x any = "hello"

	s := x.(string) // asserts dynamic type is exactly string
	fmt.Println(s, len(s))

	n, ok := x.(int) // comma-ok form never panics
	fmt.Println(n, ok)

	func() {
		defer func() { fmt.Println("recovered:", recover()) }()
		_ = x.(int) // single-value form panics on failure
	}()

	fmt.Println("plain builder:")
	emit(&strings.Builder{}, "abc")
	fmt.Println("buffered writer:")
	emit(&bufWriter{}, "abcdef")

	// For errors, use errors.As / errors.AsType rather than a bare
	// assertion, because they also search wrapped errors.
	_, err := os.Open("/does/not/exist")
	wrapped := fmt.Errorf("loading config: %w", err)
	if _, ok := wrapped.(*fs.PathError); !ok {
		fmt.Println("bare assertion misses the wrapped *fs.PathError")
	}
	if pe, ok := errors.AsType[*fs.PathError](wrapped); ok {
		fmt.Println("errors.AsType found op =", pe.Op, "path =", pe.Path)
	}
}

6.5 Type switches

"A type switch compares types rather than values. It is otherwise similar to an expression switch. It is marked by a special switch expression that has the form of a type assertion using the keyword type rather than an actual type" [3]. With the form switch x := v.(type), in clauses "with a case listing exactly one type, the variable has that type; otherwise, the variable has the type of the expression in the TypeSwitchGuard". A nil case matches a nil interface value, and cases may name interface types as well as concrete ones; the first matching case wins [3].

ex08_typeswitch/main.go 
// Example 8: type switches over values and over a small expression tree.
package main

import (
	"fmt"
	"strings"
)

func describe(v any) string {
	switch x := v.(type) {
	case nil:
		return "nil"
	case int, int64: // several types: x keeps the type any
		return fmt.Sprintf("integer %v", x)
	case string:
		return fmt.Sprintf("string of length %d", len(x)) // x is string
	case fmt.Stringer: // interface case: anything with String()
		return "Stringer " + x.String()
	case error:
		return "error " + x.Error()
	case []any:
		parts := make([]string, len(x))
		for i, e := range x {
			parts[i] = describe(e)
		}
		return "[" + strings.Join(parts, ", ") + "]"
	default:
		return fmt.Sprintf("something else (%T)", x)
	}
}

type Color int

func (c Color) String() string { return [...]string{"red", "green", "blue"}[c] }

// A closed set of node types, processed with a type switch.
type Expr interface{}
type Num float64
type Add struct{ L, R Expr }
type Mul struct{ L, R Expr }

func eval(e Expr) float64 {
	switch n := e.(type) {
	case Num:
		return float64(n)
	case Add:
		return eval(n.L) + eval(n.R)
	case Mul:
		return eval(n.L) * eval(n.R)
	default:
		panic(fmt.Sprintf("eval: unknown node %T", n))
	}
}

func main() {
	for _, v := range []any{nil, 42, int64(7), "go", Color(2), fmt.Errorf("boom"), 2.5, []any{1, "a"}} {
		fmt.Println(describe(v))
	}
	// (2 + 3) * 4
	fmt.Println(eval(Mul{Add{Num(2), Num(3)}, Num(4)}))
}

The eval function shows the trade-off between a type switch and a method. A method Eval() on each node type makes adding new node types easy (each brings its own method) but adding new operations requires editing every type. A type switch makes adding operations easy (write another function) but a new node type requires editing every switch. This is the "expression problem"; in Go, a type switch over a closed set of types is the idiomatic replacement for the Visitor pattern [7,25]. Note the order of cases in describe: because the first matching case wins, a type that implemented both String and Error would be reported as a Stringer.

6.6 Interface composition

An interface may list other interfaces among its elements. The specification calls this "embedding interface E in T", and the resulting type set "is the intersection of the type sets defined by T's explicitly declared methods and the type sets of T's embedded interfaces" [3]: in other words, the method sets are united. The standard library is built this way; Effective Go describes io.ReadWriter: "A ReadWriter can do what a Reader does and what a Writer does; it is a union of the embedded interfaces" [5,15].

ex09_iface_composition/main.go 
// Example 9: building larger interfaces from small ones.
package main

import (
	"fmt"
	"io"
	"strings"
)

type Opener interface{ Open() error }
type Closer interface{ Close() error }
type Namer interface{ Name() string }

// Resource is the union of three one-method interfaces.
type Resource interface {
	Namer
	Opener
	Closer
}

type conn struct {
	host string
	open bool
}

func (c *conn) Name() string { return "conn:" + c.host }
func (c *conn) Open() error  { c.open = true; fmt.Println("open", c.host); return nil }
func (c *conn) Close() error { c.open = false; fmt.Println("close", c.host); return nil }

// use needs all three behaviours...
func use(r Resource) {
	if err := r.Open(); err != nil {
		return
	}
	defer r.Close()
	fmt.Println("using", r.Name())
}

// ...whereas shutdown needs only one, so it asks for only one.
func shutdown(cs ...Closer) {
	for _, c := range cs {
		c.Close()
	}
}

// upper composes io interfaces: it is an io.Reader that wraps an io.Reader.
type upper struct{ r io.Reader }

func (u upper) Read(p []byte) (int, error) {
	n, err := u.r.Read(p)
	copy(p, strings.ToUpper(string(p[:n])))
	return n, err
}

func main() {
	c := &conn{host: "db1"}
	use(c)
	shutdown(c, &conn{host: "cache"})

	// upper{r} is itself an io.Reader, so it plugs into io.Copy.
	var sb strings.Builder
	io.Copy(&sb, upper{strings.NewReader("small interfaces compose\n")})
	fmt.Print(sb.String())
}

6.7 Interface embedding

"Interface embedding" has two meanings in Go. The first, an interface inside an interface, was covered above. The second is an interface type embedded in a struct. The struct then has a field holding any implementation of that interface, and the interface's methods are promoted to the struct, so the struct itself implements the interface. Declaring a method of the same name on the struct overrides just that method. The standard library uses exactly this to implement sort.Reverse: the unexported type reverse embeds sort.Interface ("This embedded Interface permits Reverse to use the methods of another Interface implementation") and redefines only Less [28].

ex10_iface_embedding/main.go 
// Example 10: embedding an interface in a struct to override one method.
package main

import (
	"fmt"
	"sort"
)

type byLen []string

func (s byLen) Len() int           { return len(s) }
func (s byLen) Less(i, j int) bool { return len(s[i]) < len(s[j]) }
func (s byLen) Swap(i, j int)      { s[i], s[j] = s[j], s[i] }

// reverse embeds the sort.Interface it wraps. Len and Swap are promoted
// from the embedded value; Less is overridden. This is how sort.Reverse
// is implemented in the standard library.
type reverse struct {
	sort.Interface
}

func (r reverse) Less(i, j int) bool { return r.Interface.Less(j, i) }

// countingSorter wraps any sort.Interface and counts comparisons.
type countingSorter struct {
	sort.Interface
	compares int
}

func (c *countingSorter) Less(i, j int) bool {
	c.compares++
	return c.Interface.Less(i, j)
}

func main() {
	words := []string{"interface", "go", "struct", "method", "any"}

	sort.Sort(byLen(words))
	fmt.Println(words)

	sort.Sort(reverse{byLen(words)})
	fmt.Println(words)

	cs := &countingSorter{Interface: byLen(words)}
	sort.Sort(cs)
	fmt.Println(words, "comparisons:", cs.compares)

	// The embedded interface is a field: if it is nil, promoted calls panic.
	defer func() { fmt.Println("recovered:", recover()) }()
	var broken reverse
	broken.Len()
}
Output 
[go any struct method interface]
[interface struct method any go]
[go any struct method interface] comparisons: 10
recovered: runtime error: invalid memory address or nil pointer dereference

This is a convenient way to write wrappers, decorators and partial test doubles, because only the methods of interest have to be written. The cost is visible in the last lines: the embedded interface is an ordinary field whose zero value is nil, and calling a promoted method on it panics, since calling a method on a nil interface value "causes a run-time panic" [3]. A wrapper that embeds an interface also silently acquires every method that is later added to that interface.

7. Composition over inheritance

"Favor object composition over class inheritance" is the second principle of object-oriented design in the Gang of Four's Design Patterns, which warns that inheritance "breaks encapsulation" because a subclass is exposed to its parent's implementation [25]. Go builds the advice into the language by leaving inheritance out. Instead of "a Duck is a FlyingBird is a Bird", a Go design says "a Duck has wings and flippers, and therefore can move and swim". The "is-a" relation that callers need is expressed by interfaces, which are satisfied by whatever methods a type ends up with, however it got them [1,2].

ex13_composition/main.go 
// Example 13: composition over inheritance. Instead of a class tree
// (Bird -> FlyingBird -> Duck, Bird -> Penguin ...), small behaviours are
// modelled as interfaces and assembled per type.
package main

import (
	"fmt"
	"strings"
)

type Mover interface{ Move() string }
type Swimmer interface{ Swim() string }

// Reusable behaviour components.
type Wings struct{ Span float64 }

func (w Wings) Move() string { return fmt.Sprintf("flies (%.1fm wings)", w.Span) }

type Legs struct{ Count int }

func (l Legs) Move() string { return fmt.Sprintf("walks on %d legs", l.Count) }

type Flippers struct{}

func (Flippers) Swim() string { return "swims" }

// Types are built from components ("has-a"), not from parents ("is-a").
type Duck struct {
	Name string
	Wings
	Flippers
}

type Penguin struct {
	Name string
	Legs
	Flippers
}

type Robot struct {
	Model string
	mover Mover // a named field: behaviour chosen at construction time
}

func (r Robot) Move() string { return "robot " + r.mover.Move() }

func report(name string, v any) {
	var caps []string
	if m, ok := v.(Mover); ok {
		caps = append(caps, m.Move())
	}
	if s, ok := v.(Swimmer); ok {
		caps = append(caps, s.Swim())
	}
	fmt.Printf("%-8s %s\n", name, strings.Join(caps, ", "))
}

func main() {
	report("duck", Duck{"Donald", Wings{0.9}, Flippers{}})
	report("penguin", Penguin{"Pingu", Legs{2}, Flippers{}})
	report("robot", Robot{"R2", Legs{3}})
	report("drone", Robot{"D1", Wings{0.3}}) // swap behaviour, no new type
}
Output 
duck     flies (0.9m wings), swims
penguin  walks on 2 legs, swims
robot    robot walks on 3 legs
drone    robot flies (0.3m wings)

Three techniques are on display. Duck and Penguin reuse behaviour by embedding components, so the components' methods are promoted. Robot holds its behaviour in a named interface field and forwards to it explicitly, so the behaviour can be chosen at construction time (a robot that walks, a drone that flies) without defining new types. And report discovers capabilities with assertions to small interfaces rather than by asking which class something belongs to. Pike's argument for this style is that "The way pieces of a system interact should adapt as it grows, not be fixed at the dawn of time" [2].

A class hierarchy often answers three needs at once: code reuse, substitutability, and a taxonomy. Go separates them: reuse comes from embedding or plain fields and functions; substitutability comes from interfaces; and the taxonomy is usually dropped, because nothing in the language needs it [1].

8. Embedding structs

"A field declared with a type but no explicit field name is called an embedded field … The unqualified type name acts as the field name" [3]. A field or method f of an embedded field is promoted "if x.f is a legal selector that denotes that field or method f", and "Promoted fields act like ordinary fields of a struct" [3]. Selectors resolve by depth: "x.f denotes the field or method at the shallowest depth in T where there is such an f. If there is not exactly one f with shallowest depth, the selector expression is illegal" [3]. A method declared on the outer type is at depth 0 and therefore hides (shadows) a promoted method of the same name; Effective Go states the rule as "a field or method X hides any other item X in a more deeply nested part of the type" [5].

ex11_struct_embedding/main.go 
// Example 11: struct embedding — promotion, shadowing, and why it is
// not inheritance.
package main

import (
	"fmt"
	"sync"
)

type Animal struct{ Name string }

func (a Animal) Sound() string    { return "..." }
func (a Animal) Describe() string { return a.Name + " says " + a.Sound() }

type Dog struct {
	Animal // embedded field; its field name is Animal
	Breed  string
}

// Dog.Sound shadows (hides) the promoted Animal.Sound at depth 0.
func (d Dog) Sound() string { return "Woof" }

// Counter embeds sync.Mutex to gain Lock and Unlock.
type Counter struct {
	sync.Mutex
	n map[string]int
}

func (c *Counter) Inc(k string) {
	c.Lock() // promoted from the embedded sync.Mutex
	defer c.Unlock()
	c.n[k]++
}

func main() {
	// Go 1.27: struct literal keys may name promoted fields directly.
	d := Dog{Name: "Rex", Breed: "collie"}

	fmt.Println(d.Name, "/", d.Animal.Name) // same field, two selectors
	fmt.Println(d.Sound())                  // Dog.Sound (depth 0)
	fmt.Println(d.Animal.Sound())           // the hidden method is still reachable

	// Describe is promoted from Animal. Its receiver is the embedded
	// Animal value, so a.Sound() inside it calls Animal.Sound, not
	// Dog.Sound. There is no virtual dispatch on concrete types.
	fmt.Println(d.Describe())

	// A Dog is not an Animal: the following would not compile.
	// var a Animal = d // cannot use d (variable of struct type Dog) as Animal value
	var a Animal = d.Animal // explicit: take the embedded part
	fmt.Println(a.Name)

	c := Counter{n: map[string]int{}}
	c.Inc("x")
	c.Inc("x")
	fmt.Println(c.n)
}
Output

Woof
...
Rex says ...
Rex
map[x:2]

The fourth line of output is the most important lesson in this article. Effective Go: "There's an important way in which embedding differs from subclassing. When we embed a type, the methods of that type become methods of the outer type, but when they are invoked the receiver of the method is the inner type, not the outer one" [5]. Describe runs with an Animal receiver, and inside it a.Sound() is a static call to Animal.Sound. There is no virtual, no super, and no way for the embedded type to call "down" into the outer type, because "Methods on a struct or any other concrete type are always resolved statically" [1]. When that kind of hook is needed, pass the varying behaviour in as an interface (Exercise 11 and section 12.3).

Two more consequences follow. Embedding does not create a subtype, so a Dog cannot be passed where an Animal is expected; the outer type must hand over its embedded part explicitly:

And when two embedded types at the same depth provide the same name, the name becomes ambiguous. As Effective Go notes, this "is usually an error", although it is allowed "if the duplicate name is never mentioned in the program outside the type definition" [5]. The fix is to declare the method on the outer type and decide explicitly what it does:

Since Go 1.27, a key in a struct literal "may now be any valid field selector for the struct type, not just a (top-level) field name", which is why Dog{Name: "Rex", Breed: "collie"} compiles [18]. The specification adds that the embedded fields traversed to reach the key "must not be pointer types", and that a key may not name a promoted field inside an embedded struct that another key also sets [3]. With earlier versions one writes Dog{Animal: Animal{Name: "Rex"}, Breed: "collie"}.

Embedding exports too. Embedding promotes all exported methods of the embedded type into the outer type's API. Embedding sync.Mutex in an exported type, as Counter does here for brevity, lets every client call Lock and Unlock. In a public API prefer an unexported named field (mu sync.Mutex), so that the lock remains an implementation detail [5,7].

9. Method sets

Method sets decide which interfaces a type implements, so they are the link between methods and polymorphism. "The method set of a defined type T consists of all methods declared with receiver type T. The method set of a pointer to a defined type T (where T is neither a pointer nor an interface) is the set of all methods declared with receiver *T or T" [3]. For embedding, the specification adds that if a struct S embeds T, then S and *S both get the promoted methods with receiver T, and *S also gets those with receiver *T; if S embeds *T, both S and *S get methods with receiver T or *T [3].

Why is the rule asymmetric? The FAQ explains that "if an interface value contains a pointer *T, a method call can obtain a value by dereferencing the pointer, but if an interface value contains a value T, there is no safe way for a method call to obtain a pointer. (Doing so would allow a method to modify the contents of the value inside the interface, which is not permitted by the language specification.)" [1]. The convenience x.m() → (&x).m() exists only for addressable variables in direct calls; it does not change the method set of T [3].

ex12_method_sets/main.go 
// Example 12: method sets of T and *T, and how they decide interface
// satisfaction.
package main

import "fmt"

type Speaker interface{ Speak() string }
type Renamer interface{ Rename(string) }

type Cat struct{ name string }

func (c Cat) Speak() string       { return c.name + ": meow" } // value receiver
func (c *Cat) Rename(name string) { c.name = name }            // pointer receiver

// Embedding T vs *T changes the outer type's method set.
type ByValue struct{ Cat }    // method set of ByValue: Speak
type ByPointer struct{ *Cat } // method set of ByPointer: Speak, Rename

func main() {
	c := Cat{"tom"}
	c.Rename("tom2") // OK: c is addressable, so this is (&c).Rename
	fmt.Println(c.Speak())

	var s Speaker = c // Cat's method set contains Speak
	fmt.Println(s.Speak())
	s = &c // *Cat's method set contains Speak and Rename
	fmt.Println(s.Speak())

	var r Renamer = &c // only *Cat implements Renamer
	// var r2 Renamer = c // compile error: Cat does not implement Renamer
	//                    // (method Rename has pointer receiver)
	r.Rename("felix")
	fmt.Println(c.Speak())

	var _ Renamer = &ByValue{} // *ByValue gets Rename (promoted from *Cat)
	var _ Renamer = ByPointer{&c}
	// var _ Renamer = ByValue{} // compile error: ByValue lacks Rename

	// Map elements are not addressable, so pointer methods cannot be
	// called on them directly.
	cats := map[string]Cat{"a": {"a"}}
	// cats["a"].Rename("b") // compile error: cannot call pointer method Rename
	tmp := cats["a"]
	tmp.Rename("b")
	cats["a"] = tmp
	fmt.Println(cats["a"].Speak())
}

For choosing receivers, Go Code Review Comments gives a checklist: "If the method needs to mutate the receiver, the receiver must be a pointer", "If the receiver is a struct that contains a sync.Mutex or similar synchronizing field, the receiver must be a pointer to avoid copying", "Don't mix receiver types", and "when in doubt, use a pointer receiver" [16]. 10. Dependency injection

Dependency injection (DI) means that an object receives its collaborators from outside instead of constructing or looking them up itself. Fowler, who named the pattern, distinguishes constructor injection, setter injection and interface injection, and contrasts DI with the Service Locator [29]. In Go no framework is needed: a constructor that takes its dependencies as parameters is constructor injection, and main serves as the "composition root" where concrete implementations are wired together.

The Go-specific part is where interfaces live. Code Review Comments: "Go interfaces generally belong in the package that uses values of the interface type, not the package that implements those values. The implementing package should return concrete (usually pointer or struct) types", and "Do not define interfaces on the implementor side of an API 'for mocking'" [16]. Implicit satisfaction is what makes this possible: the consumer declares the narrow interface it needs, and any producer that happens to have those methods qualifies without importing the consumer [1]. A dependency with a single operation can be injected as a function value instead of an interface.

ex14_di/greeter/greeter.go 
// Package greeter shows dependency injection without a framework.
// The package declares the small interfaces it needs (consumer side).
package greeter

import (
	"fmt"
	"io"
	"time"
)

// UserStore is what Greeter needs from storage: one method.
type UserStore interface {

		part = "evening"
	}

	return err
}

Guidelines that follow from the sources:

  • Inject through constructors, store dependencies in unexported fields, and keep the set small. A constructor with many dependencies is a sign that the type has too many responsibilities (section 11).
  • Declare interfaces in the consuming package, sized to what the consumer actually calls [16,26].
  • Prefer function types for single-operation dependencies such as clocks, ID generators or random sources.
  • Avoid package-level mutable singletons as hidden dependencies; they make tests order-dependent. Wire everything in main.
  • Tools exist for very large dependency graphs: Google's Wire generates the wiring code at compile time (its README now states that the project "is no longer maintained") [31], and Uber's Fx is a run-time "dependency injection system for Go" [32]. 11. SOLID principles in Go

The SOLID principles were collected by Robert C. Martin [33]: Single responsibility, Open–closed (originally Meyer's [34]), Liskov substitution [35], Interface segregation and Dependency inversion. In his GolangUK 2016 keynote, Dave Cheney restated each for Go and concluded: "If you were to summarise this talk it would probably be; interfaces let you apply the SOLID principles to Go programs" [26].

PrincipleClassic statementGo expression
Single responsibilityA class should have one reason to change [33]Applies to packages as much as types: "each Go package is itself a small Go program, a single unit of change, with a single responsibility" [26]. Name packages for what they provide [9].
Open–closedOpen for extension, closed for modification [34]New types satisfy existing interfaces without edits to the code that uses them; embedding lets a type extend another: "embedding is a powerful tool which allows Go's types to be open for extension" [26].

Dependency inversionHigh-level modules should not depend on low-level modules; both depend on abstractions [33]The consumer owns the interface (section 10). Since "In Go, your import graph must be acyclic", push "the responsibility for the specifics, as high as possible up the import graph", i.e. to main [16,26].
ex15_solid/main.go 
// Example 15: the SOLID principles expressed with Go's features.
package main

import (
	"bytes"
	"crypto/sha256"
	"encoding/json"
	"fmt"
	"io"
	"os"
	"strings"
)

// --- S: single responsibility. Report holds data; encoding and storage
// are separate concerns living elsewhere.
type Report struct {
	Title string `json:"title"`
	Total int    `json:"total"`
}

// --- I: interface segregation. Save needs only io.Writer, not *os.File
// or a large "Storage" interface with Open/Seek/Close/Delete...
func Save(w io.Writer, r Report) error {
	return json.NewEncoder(w).Encode(r)
}

// --- O: open for extension, closed for modification. New exporters can be
// added without editing Export.
type Exporter interface {
	Export(Report) string
}

type TextExporter struct{}
type CSVExporter struct{}

func (TextExporter) Export(r Report) string { return fmt.Sprintf("%s: %d", r.Title, r.Total) }
func (CSVExporter) Export(r Report) string  { return fmt.Sprintf("%q,%d", r.Title, r.Total) }

func ExportAll(r Report, exps ...Exporter) {
	for _, e := range exps {
		fmt.Println(e.Export(r))
	}
}

// --- L: Liskov substitution. Every io.Writer passed to Save must honour
// io.Writer's contract (return n < len(p) only with a non-nil error).
// limitedWriter violates it by silently dropping bytes.
type limitedWriter struct{ buf bytes.Buffer }

func (l *limitedWriter) Write(p []byte) (int, error) {
	if len(p) > 8 {
		p = p[:8]
	}
	return l.buf.Write(p) // BUG: reports n=8 < len(p) with err == nil
}

// --- D: dependency inversion. The high-level policy (Publisher) owns the
// abstraction it needs; low-level details are plugged in from main.
type Sink interface {
	Put(name string, data []byte) error
}

type Publisher struct{ sink Sink }

func (p Publisher) Publish(r Report) error {
	var buf bytes.Buffer
	if err := Save(&buf, r); err != nil {
		return err
	}
	return p.sink.Put(r.Title+".json", buf.Bytes())
}

type stdoutSink struct{}

func (stdoutSink) Put(name string, data []byte) error {
	_, err := fmt.Printf("PUT %s %s", name, data)
	return err
}

func main() {
	r := Report{Title: "q3", Total: 42}

	// I: the same Save works with any writer, including several at once.
	h := sha256.New()
	if err := Save(io.MultiWriter(os.Stdout, h), r); err != nil {
		panic(err)
	}
	fmt.Printf("sha256 prefix: %x\n", h.Sum(nil)[:4])

	// O
	ExportAll(r, TextExporter{}, CSVExporter{})

	// L: substituting a writer that breaks the contract corrupts data
	// silently: Save reports success, but only 8 bytes were stored.
	lw := &limitedWriter{}
	fmt.Printf("Save err=%v stored=%q\n", Save(lw, r), lw.buf.String())
	// io.Copy (here via strings.Reader.WriteTo) checks n against len(p)
	// and reports io.ErrShortWrite.
	_, err := io.Copy(&limitedWriter{}, strings.NewReader("0123456789"))
	fmt.Println("io.Copy err:", err)

	// D
	if err := (Publisher{sink: stdoutSink{}}).Publish(r); err != nil {
		panic(err)
	}
}

The Liskov lines deserve attention. limitedWriter has the right signature, so the compiler accepts it as an io.Writer, but it breaks the documented contract: "Write must return a non-nil error if it returns n < len(p)" [15]. json.Encoder trusts that contract, so Save reports success after storing 8 bytes. Code that checks the count, such as strings.Reader.WriteTo used by io.Copy here, reports io.ErrShortWrite, which "means that a write accepted fewer bytes than requested but failed to return an explicit error" [15]. Interfaces in Go check signatures, not semantics, so Liskov substitution remains the implementer's responsibility, as Liskov and Wing's behavioural notion of subtyping requires [35].

12. Design patterns in Go

The 23 patterns in Design Patterns were described for C++ and Smalltalk, and the authors note that the choice of language "influences one's point of view" and that some patterns are supported directly by less common languages [25]. In Go several patterns shrink to an idiom: first-class functions replace single-method strategy and command objects, implicit interfaces make adapters trivial, and embedding provides decorators that forward everything except what they change. The examples below cover the patterns most often met in Go code.

12.1 Creational patterns

Factory function. A function that chooses and returns an implementation behind an interface; Effective Go's crc32.NewIEEE discussion (section 4) is the standard-library model [5]. Functional options. Rob Pike proposed configuring a value with a variadic list of option functions, each of which sets one option on the value it is applied to [36]; Dave Cheney popularised the pattern for constructors with defaults that can grow without breaking callers [37]. Singleton. A package-level value initialised exactly once, safely under concurrency, is sync.OnceValue: it "returns a function that invokes f only once and returns the value returned by f. The returned function may be called concurrently" [38].

type rot13Codec struct{}

	return strings.Map(func(r rune) rune {
		switch {
		case r >= 'a' && r <= 'z':
			return 'a' + (r-'a'+13)%26
		case r >= 'A' && r <= 'Z':
			return 'A' + (r-'A'+13)%26
		}
		return r
	}, s)
}

func NewCodec(name string) (Codec, error) {
	switch name {
	case "upper":
		return upperCodec{}, nil
	case "rot13":
		return rot13Codec{}, nil
	}
	return nil, fmt.Errorf("unknown codec %q", name)
}

// --- Functional options: a readable, extensible constructor.
type Server struct {
	addr    string
	timeout time.Duration
	maxConn int
}

func (s *Server) String() string {
	return fmt.Sprintf("Server{addr: %s, timeout: %v, maxConn: %d}", s.addr, s.timeout, s.maxConn)
}

type Option func(*Server)

func WithTimeout(d time.Duration) Option { return func(s *Server) { s.timeout = d } }
func WithMaxConn(n int) Option           { return func(s *Server) { s.maxConn = n } }

func NewServer(addr string, opts ...Option) *Server {
	s := &Server{addr: addr, timeout: 30 * time.Second, maxConn: 100} // defaults
	for _, opt := range opts {
		opt(s)
	}
	return s
}

// --- Singleton: one lazily initialised, concurrency-safe instance.

var loadConfig = sync.OnceValue(func() *Config {
	fmt.Println("(loading config once)")
	return &Config{Env: "prod"}
})

		if err != nil {
			fmt.Println("error:", err)

	for range 3 {
		wg.Go(func() { _ = loadConfig() })
	}

wg.Go, added in Go 1.25, "calls f in a new goroutine and adds that task to the WaitGroup" [38,39]. 12.2 Structural patterns

Adapter. A function type with a method makes any function satisfy a one-method interface. The standard library's http.HandlerFunc "is an adapter to allow the use of ordinary functions as HTTP handlers" [40]. A struct wrapper adapts a type whose method has the wrong name or signature. Decorator. A wrapper that implements the same interface as the value it wraps and adds behaviour before or after delegating; in HTTP code this is called middleware [25,40]. Composite. A type that implements an interface by delegating to a collection of values of that interface [25].

ex17_structural/main.go 
// Example 17: structural patterns — adapter, decorator, and composite.
package main

import (
	"fmt"
	"strings"
	"time"
)

// The target interface used throughout.
type Handler interface{ Handle(req string) string }

// --- Adapter: let an ordinary function satisfy Handler
// (the same trick as net/http.HandlerFunc).
type HandlerFunc func(string) string

func (f HandlerFunc) Handle(req string) string { return f(req) }

// --- Adapter for a third-party type with the "wrong" method name.
type LegacyEcho struct{}

func (LegacyEcho) Process(input string, upper bool) string {
	if upper {
		return strings.ToUpper(input)
	}
	return input
}

type legacyAdapter struct{ l LegacyEcho }

func (a legacyAdapter) Handle(req string) string { return a.l.Process(req, true) }

// --- Decorators: wrap a Handler, add behaviour, keep the interface.
type Middleware func(Handler) Handler

func Logging(prefix string) Middleware {
	return func(next Handler) Handler {
		return HandlerFunc(func(req string) string {
			resp := next.Handle(req)
			fmt.Printf("%s %q -> %q\n", prefix, req, resp)
			return resp
		})
	}
}

func Timing(clock func() time.Time) Middleware {
	return func(next Handler) Handler {
		return HandlerFunc(func(req string) string {
			start := clock()
			resp := next.Handle(req)
			return fmt.Sprintf("%s (%v)", resp, clock().Sub(start))
		})
	}
}

func Chain(h Handler, ms ...Middleware) Handler {
	for i := len(ms) - 1; i >= 0; i-- { // first middleware is outermost
		h = ms[i](h)
	}
	return h
}

// --- Composite: a Handler made of Handlers.
type Pipeline []Handler

func (p Pipeline) Handle(req string) string {
	for _, h := range p {
		req = h.Handle(req)
	}
	return req
}

func main() {
	reverse := HandlerFunc(func(s string) string {
		r := []rune(s)
		for i, j := 0, len(r)-1; i < j; i, j = i+1, j-1 {
			r[i], r[j] = r[j], r[i]
		}
		return string(r)
	})

	// Fake clock that advances 3ms per call, for deterministic output.
	t := time.Date(2026, 1, 1, 0, 0, 0, 0, time.UTC)
	clock := func() time.Time { t = t.Add(3 * time.Millisecond); return t }

	h := Chain(Pipeline{reverse, legacyAdapter{}}, Logging("[log]"), Timing(clock))
	fmt.Println(h.Handle("gopher"))
}
Output 
[log] "gopher" -> "REHPOG (3ms)"
REHPOG (3ms)

Chain applies the middleware so that the first one listed is the outermost, which is why the log line already contains the timing suffix added by the inner decorator. The clock is injected (section 10) so that the output is deterministic.

12.3 Behavioural patterns

Strategy. Interchangeable algorithms behind an interface, or simply a function value [25]; sort.Slice's less argument is a strategy [28]. Observer. Subscribers registered with a subject and notified of events [25]; in concurrent programs channels are often used instead. State. An object delegates to a state value whose type changes as the object moves through its life cycle [25]. Template method. In class-based languages a base class fixes an algorithm and subclasses override steps. Section 8 showed why that does not work through embedding; in Go, the fixed algorithm becomes a function and the steps become an interface parameter [1,25].

	for _, s := range b.subs {
		s.Notify(e)
	}
}

}

// --- Template method: the fixed algorithm is a function; the varying
// steps are an interface it receives (no abstract base class needed).
type ReportSteps interface {

func Render(steps ReportSteps, rows []string) string {

	b.WriteString(steps.Header() + "\n")
	for i, r := range rows {
		b.WriteString(steps.Row(i, r) + "\n")
	}
	return b.String()
}

// Package thermostat is the solution to Exercise 1.
package thermostat

import "fmt"

// Thermostat keeps its target inside [min, max]. All fields are
// unexported, so the invariant can only be changed through methods.
type Thermostat struct {
	min, max, target float64
}

func New(min, max float64) (*Thermostat, error) {
	if min >= max {
		return nil, fmt.Errorf("thermostat: min %.1f must be below max %.1f", min, max)
	}
	return &Thermostat{min: min, max: max, target: min}, nil
}

func (t *Thermostat) Target() float64 { return t.target }

func (t *Thermostat) SetTarget(v float64) error {
	if v < t.min || v > t.max {
		return fmt.Errorf("thermostat: %.1f outside [%.1f, %.1f]", v, t.min, t.max)
	}
	t.target = v
	return nil
}

	"cmp"
	"fmt"
	"math"
	"slices"

type Shape interface {
	Area() float64
	Perimeter() float64
}

type Circle struct{ R float64 }

Exercise 4 — A JSON-like formatter (any, type switches)

encoding/json decodes into any using nil, bool, float64, string, []any and map[string]any [22]. Write format(v any) string that turns such a value back into compact JSON text with object keys in sorted order, and reports unsupported types.

Show solution sol04_format/main.go 
package main

import (
	"fmt"
	"maps"
	"slices"
	"strconv"
	"strings"
)

// format renders a value decoded by encoding/json (nil, bool, float64,
// string, []any, map[string]any) back to compact JSON-like text.
func format(v any) string {
	switch x := v.(type) {
	case nil:
		return "null"
	case bool:
		return strconv.FormatBool(x)
	case float64:
		return strconv.FormatFloat(x, 'g', -1, 64)
	case string:
		return strconv.Quote(x)
	case []any:
		parts := make([]string, len(x))
		for i, e := range x {
			parts[i] = format(e)
		}
		return "[" + strings.Join(parts, ",") + "]"
	case map[string]any:
		var parts []string
		for _, k := range slices.Sorted(maps.Keys(x)) { // deterministic order
			parts = append(parts, strconv.Quote(k)+":"+format(x[k]))
		}
		return "{" + strings.Join(parts, ",") + "}"
	default:
		return fmt.Sprintf("<unsupported %T>", x)
	}
}

func main() {
	doc := map[string]any{
		"name": "gopher", "age": 16.0, "tags": []any{"go", true, nil},
		"meta": map[string]any{"z": 1.5, "a": "x"},
	}
	fmt.Println(format(doc))
	fmt.Println(format(42)) // int is not a JSON-decoded type
}
Output 
{"age":16,"meta":{"a":"x","z":1.5},"name":"gopher","tags":["go",true,null]}
<unsupported int>

Each single-type case gives x that type, so len, indexing and ranging work without further assertions [3]. Map iteration order is unspecified, hence slices.Sorted(maps.Keys(x)) [3,42].

Exercise 5 — Composing ReadCloser (interface composition, assertions)

Define ReadCloser by embedding io.Reader and io.Closer. Implement it with a type that counts bytes read and refuses reads after Close. In the consumer, use a type assertion to report whether the value is also an io.Seeker.

Show solution sol05_readcloser/main.go 
package main

import (
	"fmt"
	"io"
	"strings"
)

// ReadCloser composes two standard one-method interfaces.
type ReadCloser interface {
	io.Reader
	io.Closer
}

type countingRC struct {
	r      io.Reader
	n      int
	closed bool
}

func (c *countingRC) Read(p []byte) (int, error) {
	if c.closed {
		return 0, fmt.Errorf("read after close")
	}
	n, err := c.r.Read(p)
	c.n += n
	return n, err
}

func (c *countingRC) Close() error { c.closed = true; return nil }

var _ ReadCloser = (*countingRC)(nil)
var _ io.ReadCloser = (*countingRC)(nil) // identical method set

func consume(rc ReadCloser) {
	defer rc.Close()
	// Optional capability: can the underlying value seek?
	if _, ok := rc.(io.Seeker); ok {
		fmt.Println("seekable")
	} else {
		fmt.Println("not seekable")
	}
	b, _ := io.ReadAll(rc)
	fmt.Printf("read %q\n", b)
}

func main() {
	c := &countingRC{r: strings.NewReader("composed")}
	consume(c)
	fmt.Println("bytes:", c.n, "closed:", c.closed)
	_, err := c.Read(make([]byte, 1))
	fmt.Println(err)
}
Output 
not seekable
read "composed"
bytes: 8 closed: true
read after close

Your ReadCloser and io.ReadCloser have identical method sets, so any type implementing one implements the other; interface identity is structural [3,15]. countingRC wraps a *strings.Reader, which is seekable, but the wrapper does not forward Seek, so the assertion fails. Wrappers hide the optional interfaces of what they wrap, a well-known cost of decoration.

Exercise 6 — A read-only view (interface embedding in a struct)

Given a KV interface with Get, Set and Delete, write a readOnly wrapper that still implements KV, forwards Get without writing it out, and rejects Set and Delete.

Show solution sol06_readonly/main.go 
package main

import (
	"errors"
	"fmt"
)

type KV interface {
	Get(k string) (string, bool)
	Set(k, v string) error
	Delete(k string) error
}

type mapKV map[string]string

func (m mapKV) Get(k string) (string, bool) { v, ok := m[k]; return v, ok }
func (m mapKV) Set(k, v string) error       { m[k] = v; return nil }
func (m mapKV) Delete(k string) error       { delete(m, k); return nil }

var ErrReadOnly = errors.New("store is read-only")

// readOnly embeds KV: Get is promoted unchanged; Set and Delete are
// overridden. readOnly still satisfies KV.
type readOnly struct{ KV }

func (readOnly) Set(string, string) error { return ErrReadOnly }
func (readOnly) Delete(string) error      { return ErrReadOnly }

func main() {
	base := mapKV{"lang": "go"}
	var s KV = readOnly{base}

	fmt.Println(s.Get("lang"))
	fmt.Println(s.Set("lang", "rust"))
	fmt.Println(s.Delete("lang"))
	fmt.Println(base) // unchanged

	// The wrapper can still be bypassed through the embedded field:
	s.(readOnly).KV.Set("lang", "zig")
	fmt.Println(base)
}
Output 
go true
store is read-only
store is read-only
map[lang:go]
map[lang:zig]

Get is promoted from the embedded interface; Set and Delete at depth 0 hide the promoted ones [3,5]. The last lines show that embedding is not an access-control mechanism: the embedded field is reachable by its type name, so a wrapper that must be airtight should use an unexported named field and forward Get explicitly.

Exercise 7 — Which lines compile? (method sets)

Given func (v V) String() string and func (v *V) Inc(), and var v V, which of these compile? (1) var s1 Stringer = v (2) var s2 Stringer = &v (3) var i1 Incrementer = v (4) var i2 Incrementer = &v (5) v.Inc() (6) V{}.Inc(). Then predict the output of the program.

Show solution sol07_methodsets/main.go 
package main

import "fmt"

type Stringer interface{ String() string }
type Incrementer interface{ Inc() }

type V struct{ n int }

func (v V) String() string { return fmt.Sprint("V", v.n) }
func (v *V) Inc()          { v.n++ }

func main() {
	var v V
	var s1 Stringer = v  // (1) OK: String is in V's method set
	var s2 Stringer = &v // (2) OK: *V's method set includes V's methods
	// var i1 Incrementer = v // (3) error: Inc has a pointer receiver
	var i2 Incrementer = &v // (4) OK
	v.Inc()                 // (5) OK: v is addressable, so (&v).Inc()
	// V{}.Inc()            // (6) error: composite literal not addressable
	i2.Inc()
	fmt.Println(s1, s2, v) // s1 holds a copy made at (1)
}
Output 
V0 V2 V2

(3) fails because the method set of V excludes pointer-receiver methods; (6) fails because a composite literal is not addressable, so the (&x).m() shorthand does not apply [1,3]. In the output, s1 prints V0 because assigning v to an interface copied the value before the two increments, whereas s2 holds a pointer and sees the change.

Exercise 10 — Caching decorator (decorator pattern)

Given type Fetcher interface { Fetch(url string) (string, error) }, write WithCache(next Fetcher) Fetcher that remembers successful results and is safe for concurrent use, and a logging decorator. Stack them and show how many calls reach the origin.

Show solution sol10_decorator/main.go 
package main

import (
	"fmt"
	"sync"
)

type Fetcher interface {
	Fetch(url string) (string, error)
}

type slowFetcher struct{ calls int }

func (s *slowFetcher) Fetch(url string) (string, error) {
	s.calls++
	return "<html>" + url + "</html>", nil
}

// cachingFetcher decorates any Fetcher with a concurrency-safe cache.
type cachingFetcher struct {
	next  Fetcher
	mu    sync.Mutex
	cache map[string]string
}

func WithCache(next Fetcher) Fetcher {
	return &cachingFetcher{next: next, cache: map[string]string{}}
}

func (c *cachingFetcher) Fetch(url string) (string, error) {
	c.mu.Lock()
	defer c.mu.Unlock()
	if v, ok := c.cache[url]; ok {
		return v, nil
	}
	v, err := c.next.Fetch(url)
	if err == nil {
		c.cache[url] = v
	}
	return v, err
}

// loggingFetcher is a second decorator; decorators stack.
type loggingFetcher struct{ next Fetcher }

func (l loggingFetcher) Fetch(url string) (string, error) {
	fmt.Println("fetch", url)
	return l.next.Fetch(url)
}

func main() {
	origin := &slowFetcher{}
	f := loggingFetcher{WithCache(origin)}
	for _, u := range []string{"a", "b", "a", "a"} {
		body, _ := f.Fetch(u)
		fmt.Println(" ", body)
	}
	fmt.Println("origin calls:", origin.calls)
}
Output 
fetch a
  <html>a</html>
fetch b
  <html>b</html>
fetch a
  <html>a</html>
fetch a
  <html>a</html>
origin calls: 2

Each decorator implements the same interface as the value it wraps, so decorators stack in any order [25]. The cache's mutex is an unexported named field and the methods use a pointer receiver, as Code Review Comments requires for types containing a sync.Mutex [16,38]. Holding the lock during next.Fetch keeps the example simple but serialises all fetches; production code would release it during the call or use a per-key mechanism.

Exercise 11 — Template method without inheritance (embedding vs interfaces)

A programmer coming from Java writes a Base type with Describe() that calls Name(), embeds Base in Widget, and overrides Name. Predict what Widget{}.Describe() returns, then restructure the code so that the overriding works.

Show solution sol11_template/main.go 
package main

import "fmt"

// Broken attempt (inheritance thinking): Base.Describe calls b.Name(),
// which is always Base.Name, even when Base is embedded in Widget.
type Base struct{}

func (Base) Name() string       { return "base" }
func (b Base) Describe() string { return "I am " + b.Name() }

type Widget struct{ Base }

func (Widget) Name() string { return "widget" }

// Fix: make the varying step an interface and the fixed algorithm a
// function (or a method on a type that holds the interface).
type Namer interface{ Name() string }

func Describe(n Namer) string { return "I am " + n.Name() }

func main() {
	w := Widget{}
	fmt.Println(w.Describe()) // I am base   (surprise for Java/C++ users)
	fmt.Println(Describe(w))  // I am widget (dynamic dispatch via interface)
	fmt.Println(Describe(w.Base))
}

I am base
I am widget
I am base

The promoted Describe runs with the embedded Base as its receiver, and b.Name() on a concrete type is resolved statically [1,5]. Making the step an interface parameter restores dynamic dispatch, which in Go happens only through interfaces [1].

Exercise 12 — Segregate the interface (ISP)

func Archive(f *os.File, recs []Record) error writes tab-separated records. Change its signature so that the same function can write to a buffer, a hash and a byte counter at once, and demonstrate it.

Show solution sol12_isp/main.go 
package main

import (
	"bytes"
	"crypto/sha256"
	"fmt"
	"io"
)

type Record struct {
	ID   int
	Name string
}

// Before: func Archive(f *os.File, recs []Record) error
// After: Archive needs only the ability to write bytes.
func Archive(w io.Writer, recs []Record) error {
	for _, r := range recs {
		if _, err := fmt.Fprintf(w, "%d\t%s\n", r.ID, r.Name); err != nil {
			return err
		}
	}
	return nil
}

// byteCounter is a tiny io.Writer of our own.
type byteCounter int

func (c *byteCounter) Write(p []byte) (int, error) { *c += byteCounter(len(p)); return len(p), nil }

func main() {
	var buf bytes.Buffer
	h := sha256.New()
	var n byteCounter
	recs := []Record{{1, "ada"}, {2, "grace"}}
	if err := Archive(io.MultiWriter(&buf, h, &n), recs); err != nil {
		panic(err)
	}
	fmt.Print(buf.String())
	fmt.Printf("%d bytes, sha256 %x...\n", n, h.Sum(nil)[:6])
}
Output 
1	ada
2	grace
14 bytes, sha256 18aa4b82835f...

Archive only ever called Write, so io.Writer is all it should require; this is Cheney's Save example [26]. io.MultiWriter is itself a composite io.Writer [15], and the tiny byteCounter shows that a user-defined type joins in simply by having a Write method.
