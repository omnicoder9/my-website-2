1Overview

Deployment is everything that happens between "it works on my machine" and "it keeps working for users". For a Python application that usually means four jobs: turning the source tree into an installable artifact, choosing a runtime that will host it (a container, a single executable, a managed cloud service or a plain Linux server), running it as a supervised process that restarts and shuts down cleanly, and making it observable so that you can tell what it is doing once it is out of reach.

This article works through those jobs with one small project, tinysvc: a WSGI web service with a JSON endpoint, a health check and a Prometheus metrics endpoint. WSGI is the standard interface between Python web applications and web servers, which is why the same app object can run under the standard library's reference server during development and under Gunicorn in production.[1,2] Every file shown was built and run for this article; the terminal sessions are real captures.

2Packaging applications

Every other deployment route in this article starts from the same place: a project that can be built into a standard distribution and installed into a clean environment. Modern Python packaging rests on three standards. PEP 518 introduced the pyproject.toml file and its [build-system] table, whose requires key lists what is needed to run the build.[3] PEP 517 split the work between a build frontend, the tool you run, and a build backend, named by the build-backend key, which must provide build_wheel and build_sdist hooks.[4] PEP 621 standardised the [project] table for core metadata so that any backend can read it.[5] The PEPs are now historical documents; the maintained specifications live in the Python Packaging User Guide.[6]

The project file

The [build-system] table should always be present, whichever backend you choose.[7] Here it selects setuptools; Hatchling, Flit, PDM and others are drop-in alternatives because the frontend only talks to them through the PEP 517 hooks.[4] In [project], requires-python declares the oldest supported interpreter, dependencies lists what must be installed alongside the package, and each key of [project.optional-dependencies] defines an extra that users opt into, such as tinysvc[server].[7] The license value is an SPDX licence expression.[7] Finally, [project.scripts] declares a command: installers create a wrapper executable for every entry in the console_scripts group, named after the entry.[7,8]

The code lives under src/. This "src layout" stops tests and tools from importing the package straight out of the working directory, so you always exercise the installed copy, which is what users will get.[9] The package reads its own version from the installed metadata instead of repeating it in code; importlib.metadata.version() raises PackageNotFoundError when the distribution is not installed, hence the fallback.[10]

Building the distributions

The recommended frontend is build, which runs whatever backend pyproject.toml declares; calling setup.py directly is explicitly discouraged.[11] It produces a source distribution (.tar.gz) and a wheel (.whl):

A wheel is a ZIP-format archive with a specially formatted file name, and installing one needs no build step on the target machine.[12] Listing it shows the package files next to a .dist-info directory holding the metadata, the RECORD of installed files and the entry points:[8,13]

The file name encodes compatibility. Its pattern is {distribution}-{version}(-{build tag})?-{python tag}-{abi tag}-{platform tag}.whl, where the optional build tag must start with a digit.[12] py3-none-any means "any Python 3, no particular ABI, any platform": a pure-Python wheel. Wheels with compiled extensions carry tags such as cp313-cp313-manylinux_2_28_x86_64; a manylinux_x_y tag promises that the wheel works on any Linux distribution with glibc x.y or newer.[14] Exercise 2 parses these names.

3Docker containers

A container image bundles the interpreter, the operating-system libraries, the dependencies and the code into one artifact that runs the same way on a laptop, a CI runner and a cluster. The production entry point is a small module that configures logging and exposes the WSGI application to Gunicorn:

Each choice in this Dockerfile follows Docker's own guidance:

  • Multi-stage build. The first stage installs the project into a virtual environment; the final stage copies only that environment. Multi-stage builds "let you reduce the size of your final image" by separating the build from the output.[18]
  • .dockerignore. Excludes the local venv, caches, build output and secrets from the build context, using patterns similar to .gitignore.[18]
  • Pinned base image. A tag such as python:3.13-slim can resolve to a different image over time. For fully reproducible builds pin the digest as well (python:3.13-slim@sha256:…) and rebuild regularly to pick up security fixes.[18]
  • A non-root user. USER sets the user that runs the container's processes.[19] The account gets a home directory because Gunicorn creates its control socket under $HOME/.gunicorn when XDG_RUNTIME_DIR is not set.[20]
  • PYTHONUNBUFFERED=1. Forces stdout and stderr to be unbuffered, so log lines reach docker logs as soon as they are written.[21]
  • PORT. When PORT is set, Gunicorn's default bind address becomes 0.0.0.0:$PORT, so the image needs no --bind and platforms that inject PORT work unchanged.[20] EXPOSE only documents the port; it is docker run -p that publishes it.[19]
  • One process, threads for concurrency. Prometheus client libraries assume metrics are shared between threads; with several Gunicorn worker processes, each keeps its own counters unless you enable the client's multiprocess mode.[22] One worker with four threads keeps the example simple; setting threads above 1 selects Gunicorn's gthread worker.[20]
  • HEALTHCHECK. Docker runs the command periodically and marks the container healthy or unhealthy from its exit status (0 healthy, 1 unhealthy).[19] The slim image has no curl, so the check reuses the project's own tinysvc check command.
  • Exec-form CMD. The JSON array form runs Gunicorn directly as PID 1. The shell form wraps the command in /bin/sh -c, and the shell, not your program, then receives the stop signal.[19]

PID 1 is special

Inside a container your program usually runs as PID 1, the init process of the container's PID namespace. The kernel only delivers signals to that process if it "has established a signal handler" for them.[24] Python installs no SIGTERM handler by default, so a plain script ignores docker stop and is killed 10 seconds later. Either handle SIGTERM yourself or start the container with docker run --init, which runs a small init that forwards signals and reaps processes.[25,26] Exercise 3 measures the difference.

4Executables with PyInstaller

Sometimes the target machine has no Python at all: a colleague's laptop, a locked-down server, a customer site. PyInstaller analyses your program, collects the interpreter, the standard-library modules and every imported package, and produces either a one-folder bundle (the default, --onedir) or a single self-extracting executable (--onefile).[27] It needs an ordinary script as its starting point, not a console-script entry point, so the project carries a three-line wrapper:

tinysvc/__init__.py reads its version through importlib.metadata, which needs the package's .dist-info directory at run time. --copy-metadata tells PyInstaller to bundle that metadata.[27] (PyInstaller 6.22 detected the need here even without the flag, but stating it keeps the build explicit.)

The result is a native ELF executable of 8.4 MB that runs on a machine with no Python installed. It is not portable everywhere, though, and the reasons are worth knowing before you promise anyone a binary.

  • No cross-compilation. To ship for Windows, macOS and Linux you must run PyInstaller on each of them.[27]
  • glibc is forward-compatible only. The bundle links against the build machine's C library, so "always build your app on the oldest version of GNU/Linux you mean to support".[27] The executable above was built against glibc 2.39. It runs on Ubuntu 24.04 but fails on Debian 12, which has glibc 2.36:
  • Data files move. Files added with --add-data SRC:DEST are unpacked next to the bundled code, not in the current directory.[27] At run time the bootloader sets sys.frozen and stores the bundle folder in sys._MEIPASS; locate data relative to __file__ or that folder, never relative to the working directory.[28] Exercise 4 shows the failure and the fix.
  • One file still means a folder at run time. A --onefile program unpacks its contents to a temporary directory each time it starts (the /tmp/_MEI… path in the error above) and sys._MEIPASS points there; in a one-folder bundle it points to the bundle's _internal folder instead.[28]

5Cloud deployment

Cloud platforms differ in what you hand over, but they make the same demands of the application. The Twelve-Factor App methodology captures the most important two: configuration, meaning "everything that is likely to vary between deploys", belongs in environment variables rather than in code,[29] and an app should write its logs "unbuffered, to stdout" and leave routing and storage to the platform.[30] tinysvc already does both.

Fail fast on bad configuration

Because configuration arrives in environment variables, a typo in a variable name becomes a run-time bug. Read and validate every setting once at start-up and refuse to start if one is missing or malformed; the platform's health checks and deployment rollbacks then catch the mistake before users do. 6Linux services with systemd

On a virtual machine or bare-metal server, the init system is the supervisor. systemd starts the service at boot, restarts it when it fails, captures its output in the journal and can confine it in a sandbox. Here is a unit for the same Gunicorn command, installed into a virtual environment under /opt/tinysvc:

  • Type=notify makes systemd wait for the service to report READY=1 through sd_notify before it considers start-up complete, and NotifyAccess=main accepts that message only from the main process.[35] Gunicorn supports this; its own example unit uses Type=notify, ExecReload=/bin/kill -s HUP $MAINPID and KillMode=mixed.[36] (Testing for this article confirmed that Gunicorn 26.2 sends READY=1 to $NOTIFY_SOCKET.) For a program that does not notify, use Type=exec, which counts the unit as started once the binary has been executed.[35]
  • Restart=on-failure restarts the service when it exits with a non-zero status or is killed by a signal; RestartSec would otherwise default to 100 ms.[35]
  • TimeoutStopSec bounds how long the service may take to stop before systemd kills it, so a graceful shutdown must finish within it.[35]
  • RuntimeDirectory=tinysvc creates /run/tinysvc for the unit and removes it when the unit stops;[37] pointing XDG_RUNTIME_DIR there gives Gunicorn somewhere to put its control socket.[20]
  • Sandboxing. ProtectSystem=strict mounts the whole file system read-only apart from the API file systems, ProtectHome=yes makes home directories inaccessible, PrivateTmp=yes gives the service its own /tmp, and NoNewPrivileges=yes stops it gaining privileges through execve().[37]

7Logging

Logs are the first thing you reach for when something goes wrong in production, and the standard library's logging package is what nearly every Python library already uses. Its model has four parts: loggers that code calls, handlers that send records somewhere, formatters that turn records into text, and filters that can drop or modify records. Loggers form a hierarchy by dotted name, and a child logger propagates its records up to the handlers of its ancestors, so an application configures handlers once, near the root.[39]

The example follows the HOWTO's main recommendations:[39]

  • Create one logger per module with logging.getLogger(__name__), so the logger name shows where an event came from.
  • Pass values as arguments (log.info("order %s", order_id)) rather than pre-formatting an f-string. Formatting is deferred until a handler actually emits the record, so filtered-out debug messages cost almost nothing.
  • Use log.exception() inside an except block; it logs at ERROR level and appends the traceback.
  • Libraries should add only a NullHandler and never configure handlers themselves; configuration is the application's job.
  • Levels are numbers: DEBUG 10, INFO 20, WARNING 30, ERROR 40, CRITICAL 50, and the root logger defaults to WARNING.

Structured logs for machines

In a deployed service, logs are read by a log pipeline before they are read by a person. One JSON object per line lets the pipeline index fields such as route or invoice_id without fragile regular expressions; the Logging Cookbook shows the same technique of serialising a dictionary per record.[40] tinysvc does it with a small Formatter subclass, installed through dictConfig() so the whole configuration is data:[41]

Anything passed through extra= becomes an attribute of the log record, and the formatter copies every non-standard attribute into the JSON object. Writing to sys.stdout rather than to a file follows the twelve-factor rule that the platform, not the application, decides where logs go.[30] Docker, journald, Cloud Run and Lambda all collect a process's standard output.

Keeping slow handlers off the request path

A handler that writes to a network service or sends e-mail can block the thread that logs. QueueHandler and QueueListener move that work to a separate thread, which the documentation describes as important for web applications whose threads "need to respond as quickly as possible".[42] The listener should be stopped before the program exits, or records left on the queue are never processed.[42]

What not to log

Never log passwords, tokens, API keys or full payment details. Logs are copied to more places, and kept for longer, than the data they describe. Exercise 7 adds a filter that masks credentials before any handler sees them.

8Monitoring

Monitoring answers a narrow question continuously: is the service working right now, and if not, what is broken? Google's SRE book distinguishes black-box monitoring, testing externally visible behaviour as a user would, from white-box monitoring based on metrics the system exposes about its internals. It recommends four "golden signals" for any user-facing system:[43]

SignalDefinitionIn tinysvc
LatencyThe time it takes to service a requesttinysvc_request_duration_seconds histogram
TrafficHow much demand is placed on the systemRate of tinysvc_requests_total
ErrorsThe rate of requests that fail, explicitly or implicitlytinysvc_requests_total{status=~"5.."}

Health checks

The simplest black-box probe is a health endpoint. Orchestrators distinguish two kinds. A liveness check failing means "restart me"; a readiness check failing means "stop sending me traffic for now". Kubernetes acts on both, restarting unhealthy containers or no longer routing traffic to containers that are not ready.[44] Keep liveness checks cheap and local; if they test a database, a database outage restarts every replica at once. /healthz in tinysvc is a liveness check, and Exercise 8 adds a readiness check.

Metrics with Prometheus

Prometheus scrapes a text endpoint and stores each metric as a time series. For online-serving systems its instrumentation guide names the key metrics as "the number of performed queries, errors, and latency".[45] There are three everyday metric types. A counter only goes up (until the process restarts) and is queried as a rate; a gauge can go up and down, and "if the value can go down, it is a gauge"; a histogram counts observations into buckets so that quantiles can be estimated on the server.[45,46]

Note what the client library added: the counter is exposed as jobs_processed_total, and the histogram as cumulative _bucket series plus _count and _sum. app.py, below, applies the same ideas to HTTP requests. One line in it deserves attention: _route() maps every unknown path to "other". Each distinct label value creates a new time series, and Prometheus advises keeping the cardinality of most metrics below 10 and treating anything that might exceed 100 as a design problem.[45] Using the raw path as a label would let any visitor create unbounded series just by requesting random URLs.

9Observability

Monitoring tells you that something is wrong; observability is the ability to find out why without shipping new code. OpenTelemetry defines it as being able to understand a system from the outside and ask questions about it without knowing its inner workings, especially for "unknown unknowns".[47] The raw material is telemetry in three signals: metrics (aggregated numbers over time), logs (timestamped messages) and traces.[47]

A trace follows one request as it propagates through a distributed system, and it is made of spans: units of work with a name, timing data, attributes and a parent.[47] Logs become far more useful when they carry the trace and span IDs of the work that produced them, because you can then jump from a slow trace to exactly the log lines it caused.[47]

Tracing with OpenTelemetry

The OpenTelemetry SDK is set up once per process: create a TracerProvider, attach a span processor and exporter, and make it the global provider. Code then creates spans with start_as_current_span(); spans opened inside another become its children.[48] The example below adds a logging filter that stamps the current trace and span IDs on every record, and prints the finished spans:

Context propagation

A trace only spans several services if each call carries the trace context with it. OpenTelemetry's default propagator uses the W3C Trace Context headers.[49] The traceparent header printed above has four dash-separated fields: a version (00), a 16-byte trace ID, the 8-byte ID of the calling span, and trace flags.[50] In the flags, bit 01 means the caller sampled (recorded) the trace and bit 02, added in Trace Context Level 2, says the trace ID is random; 03 sets both.[50] The sender injects the context into outgoing headers and the receiver extracts it, as Exercise 9 does; instrumentation libraries do both for you and are the better choice where they exist.[51]

From demo to production

The demo exports to memory so that it can print. A real service exports over OTLP to a collector or a tracing back end, uses a batching span processor, and names itself with the service.name resource attribute so that its spans can be found. For popular frameworks you may not need to write any tracing code: OpenTelemetry's zero-code instrumentation installs instrumentation packages with opentelemetry-bootstrap -a install and wraps your start command with opentelemetry-instrument, for example with --traces_exporter console --service_name dice-server while you experiment.[52]

Finally, observability data should serve reliability goals. A service level indicator (SLI) measures the service's behaviour, ideally from the user's point of view, and a service level objective (SLO) attaches a target to it.[47] "99.5% of requests to / complete in under 300 ms over 28 days", computed from the latency histogram above, is the kind of statement that turns dashboards into decisions.

2. Read a wheel's compatibility tagsIntermediate

Write parse_wheel_name(filename) that splits a wheel file name into name, version, optional build tag, and the lists of Python, ABI and platform tags. Tag sets may be compressed with dots, as in py2.py3. Reject names that are not wheels or that have the wrong number of parts, then compare your result with packaging.utils.parse_wheel_filename().

Show solution

The name has five or six dash-separated fields, and the optional build tag must begin with a digit.[12] A dot inside a tag field lists alternatives, so py2.py3-none-any expands to two tags.[14]

3. Why does docker stop take ten seconds?Intermediate

The image below runs a script that sleeps. Time docker stop on it. Then make it stop promptly in two different ways: without changing the code, and by changing the code. Explain the exit codes.

Show solution

The script is PID 1 in its namespace, and the kernel only delivers a signal to PID 1 if a handler is installed for it.[24] Python installs none for SIGTERM, so the signal is discarded, Docker waits its 10-second grace period and sends SIGKILL.[23] Exit status 137 is 128 + 9 (SIGKILL). --init runs an init process as PID 1 that forwards the signal;[25] the script then receives SIGTERM with its default action and ends with 143 (128 + 15). Installing a handler lets the program exit with status 0 after cleaning up.[26]

4. Bundle a data file with PyInstallerIntermediate

motd_naive.py prints the contents of data/motd.txt. Freeze it with pyinstaller --onefile --add-data "data/motd.txt:data" and run the executable from another directory. Explain the failure and write a version that works both frozen and from source.

Show solution

The relative path is resolved against the current working directory, but the bundled file lives where the bootloader unpacked the program. In a bundle, sys.frozen is set and sys._MEIPASS holds the bundle folder; from source, the folder of __file__ plays the same role.[28]

5. Twelve-factor settings that fail fastIntermediate

Write load_settings(env) that builds an immutable settings object from environment variables: DATABASE_URL (required), PORT (integer 1–65535, default 8000), DEBUG (boolean, default false) and WEB_CONCURRENCY (integer, default 2). Report every problem in a single exception rather than stopping at the first.

Show solution

Taking the mapping as a parameter (defaulting to os.environ) makes the loader easy to test. Collecting all errors means one failed deployment reveals every misconfigured variable at once.[29]

6. A systemd unit for the workerIntermediate

Write a unit for worker.py from section 6, installed at /opt/worker. It should always be restarted, give up if it fails five times within a minute, run under a throwaway user with a writable state directory, allow 20 seconds for a graceful stop and apply the sandboxing options used for tinysvc. Verify it with systemd-analyze.

Show solution

DynamicUser=yes allocates a user and group when the unit starts and implies ProtectSystem=strict, so StateDirectory= provides the one writable path, under /var/lib/.[37] StartLimitIntervalSec and StartLimitBurst in [Unit] cap the restart loop.[35]

7. Redact secrets from logsIntermediate

Write a logging.Filter that masks the values of password=, token=, api_key= and secret= (any case) in the final message, including values supplied as %s arguments, and in extras with those names. Attach it to a handler so it protects every logger that uses the handler.

Show solution

A filter may modify the record as well as reject it, as the cookbook's contextual-information recipes do.[40] Merging the arguments into the message first with getMessage() catches secrets that arrive as arguments; setting args to None stops the formatter from applying them a second time.

8. Separate liveness from readinessIntermediate

Extend a WSGI app with /readyz, which returns 503 until a background warm-up task has finished and 200 afterwards, while /healthz always returns 200. Test it without starting a server.

Show solution

A WSGI application is just a callable taking environ and start_response,[1] so it can be called directly; wsgiref.util.setup_testing_defaults() fills in the rest of the environ.[2] An orchestrator would keep the instance alive (liveness passes) but hold back traffic until /readyz passes.[44]

9. Continue a caller's traceAdvanced

A request arrives with the header traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01 (the example from the W3C specification).
