1What an AST is

An abstract syntax tree (AST) is a tree that records the structure of a program and leaves out the details of how it was typed. In total = (price * 2) the tree holds an assignment whose target is the name total and whose value is a multiplication of price by the constant 2. The parentheses, the spaces and any comment on the line are gone, because they do not change what the program means. The standard library's ast module "helps Python applications to process trees of the Python abstract syntax grammar", and every node in such a tree is an instance of a class that inherits from ast.AST[1].

The tree is not a side product. It is the central data structure of CPython's compiler. The CPython developer documentation lists the steps that turn source code into bytecode as: tokenize the source code, parse the stream of tokens into an abstract syntax tree, transform the AST into an instruction sequence, construct a control flow graph and optimise it, and emit bytecode from that graph[2]. The first thing done with the tree is to build a symbol table, which works out which names are local, global or free in each scope[2].

Since Python 3.9 the parser is a PEG parser that was written to replace the older LL(1) parser[6]. One of its design goals is that grammar actions build AST nodes directly, so no intermediate concrete syntax tree (CST) is built along the way[6]. The set of node types is written in the Zephyr Abstract Syntax Definition Language (ASDL), in the file Parser/Python.asdl of the CPython source tree[2].

It uses tokenize.generate_tokens(), which yields TokenInfo tuples for source supplied as strings[3], then ast.parse(), then compile(), which accepts "a normal string, a byte string, or an AST object" as its source[4], and finally dis.dis() on the resulting code object.

The bytecode at the bottom is the business of the dis module and of code objects, which are covered in their own article. Bytecode is an implementation detail of CPython, and no guarantee is made that it stays the same between versions[5]. The tree is a more stable level to work at: its classes are public and documented. It is not frozen either, though. The documentation warns that "the abstract syntax itself might change with each Python release"[1], which is why section 11 is devoted to version differences.

2Parsing source with ast.parse

On Python 3.13 the signature is ast.parse(source, filename='<unknown>', mode='exec', *, type_comments=False, feature_version=None, optimize=-1)[1]. The result is the root node of a tree. Which root you get depends on mode[1]:

  • 'exec' (the default) parses a sequence of statements, such as a whole module, and returns an ast.Module.
  • 'eval' parses a single expression and returns an ast.Expression.
  • 'single' parses one interactive statement, as typed at the REPL, and returns an ast.Interactive.
  • 'func_type', added in Python 3.8, parses a function signature type comment such as (int, str) -> bool and returns an ast.FunctionType.

Notice the difference between 'eval' and 'single'. In 'eval' mode the root's body is the expression itself. In 'single' mode it is a list of statements, and the expression is wrapped in an Expr statement, which is how the REPL knows to print the value. Asking 'eval' mode to parse a statement is a SyntaxError:

A tree is not a guarantee that the code runs

Parsing checks the grammar and nothing else. The documentation is explicit that a successful parse "doesn't guarantee that the source code provided is valid Python code that can be executed", because the compilation step can raise further SyntaxError exceptions, and it gives the example that return 42 produces a valid AST node[1]. In particular, ast.parse() does no scoping checks; the compiler does them[1].

Type comments and older grammars

By default, comments are dropped. With type_comments=True the parser keeps type comments in the style of PEP 484 and PEP 526 and stores them in the type_comment field of the nodes that have one; without the flag that field is always None[1]. PEP 484 defined these comments for code that had to run on versions of Python without annotation syntax[7].

The feature_version argument takes a (major, minor) tuple and makes a "best-effort" attempt to parse with that version's grammar[1]. On 3.13 the lowest value accepted is (3, 7)[1]. Python 3.8 introduced the argument, with the example that feature_version=(3, 4) treats async and await as ordinary names[8]. A tool can use it to warn when code uses syntax that is too new for the oldest Python a project supports.

Parsing untrusted code

The documentation warns that "it is possible to crash the Python interpreter with a sufficiently large/complex string due to stack depth limitations in Python's AST compiler"[1]. The same warning appears for compile()[4]. A tool that parses code from strangers should run in a separate process with resource limits.

3Reading a tree

Dumping with ast.dump

Printing a node directly is not much help, so the module provides ast.dump(node, annotate_fields=True, include_attributes=False, *, indent=None, show_empty=False)[1]. The indent argument, added in Python 3.9, pretty-prints one node per line. include_attributes=True adds line and column numbers. show_empty, added in 3.13, includes empty lists that are normally left out[1]. Python 3.15 also stops printing optional Load() contexts by default[1], so dumps from newer versions are a little shorter than the 3.13 output shown here.

The same view is available from the shell: python -m ast parses a file, or standard input, and prints the dump. The command-line interface was added in Python 3.9 and accepts -m/--mode, -a for attributes, -i for the indent, and --no-type-comments[1].

Node classes and their fields

Every concrete node class lists the names of its children in a class attribute called _fields; the documentation's example is that ast.BinOp has the fields left, op and right[1]. Python 3.13 also added _field_types, which maps each field to its type[1]. The classes form a hierarchy that mirrors the ASDL grammar: abstract base classes such as ast.stmt, ast.expr, ast.operator and ast.expr_context, with concrete classes underneath.

ast.iter_fields() yields each (name, value) pair a node has, and ast.iter_child_nodes() yields its direct child nodes[1]. The node types you will meet most often are these:

The ctx field on Name, Attribute and Subscript records whether the expression is read (Load), assigned to (Store) or deleted (Del). In the first dump of this section, area has ctx=Store() while width and height have ctx=Load(). Since Python 3.8 every literal is an ast.Constant, whose kind is 'u' for strings written with a u prefix and None otherwise[1].

4Line and column information

Statement and expression nodes carry four position attributes: lineno, col_offset, end_lineno and end_col_offset[1]. The end positions arrived in Python 3.8, together with ast.get_source_segment(), which returns the exact source text a node came from[8]. Lines count from 1. Columns count from 0, and the end offset points just after the last character, so a slice line[node.col_offset:node.end_col_offset] covers the node[1].

There is one trap. The column offsets are "UTF-8 byte offsets", not character indexes[1]. As long as a line is plain ASCII the two agree. As soon as a non-ASCII character comes before the node, they drift apart:

The é takes two bytes in UTF-8, so every column after it is one larger than the character index. Slice the encoded bytes, or simply call ast.get_source_segment(), which does the conversion for you. It returns None when a node has no location information[1].

5Walking a tree

ast.walk for quick searches

ast.walk(node) yields the node and all its descendants "in no specified order"[1]. It is the right tool when you only want to find nodes of a certain type and do not care where they sit.

NodeVisitor for structured analysis

When context matters, subclass ast.NodeVisitor. Its visit() method calls visit_ClassName() for each node if you defined one, and generic_visit() otherwise[1]. The default generic_visit() visits all of the node's children. Because each method is called in tree order and you control when to descend, a visitor can keep state, such as the name of the function it is currently inside.

The calls to self.generic_visit(node) are essential. The documentation points out that the children of a node with a custom visitor method "won't be visited unless the visitor calls generic_visit() or visits them itself"[1]. 6Transforming a tree

ast.NodeTransformer is a NodeVisitor whose methods return a value that replaces the node they were given[1]:

  • return the same node to keep it unchanged;
  • return a different node to replace it;
  • return None to remove it;
  • return a list of nodes, where a statement is expected, to replace one statement with several.

As with the visitor, children are not processed unless you call self.generic_visit(node), normally first, or transform them yourself[1]. Locations for new nodes

Nodes you create yourself have no lineno or col_offset, but the compiler needs them. ast.fix_missing_locations() walks the tree and fills in any missing location by copying it from the parent node[1]. When a new node replaces an old one, ast.copy_location(new_node, old_node) copies the old node's position, which keeps tracebacks pointing at the right line[1]. ast.increment_lineno() shifts every line number in a tree, which helps when you splice generated code into a larger file[1].

8Back to source with ast.unparse

ast.unparse(), added in Python 3.9, turns a tree back into source code that would produce an equivalent tree if parsed again[1]. The documentation warns that the result "will not necessarily be equal to the original code", and that unparsing a highly complex expression can raise RecursionError[1]. Because the tree is abstract, anything it does not record is lost: comments, blank lines, the choice of quote character and redundant parentheses.

That last line is the property that matters: the text changed but the meaning did not. Comparing dumps is a simple way to check that two pieces of source are the same program; Python 3.14 adds ast.compare() for the same purpose[1]. When a tool must keep a file's comments and layout, it edits the text using the node positions from section 4 instead of unparsing, as the codemod in section 10 does.

9literal_eval: data, not code

eval() runs arbitrary code. Its documentation states that "calling it with untrusted user-supplied input will lead to security vulnerabilities"[4]. When the input is meant to be a data literal, such as a list, a dictionary or a number written in Python syntax, ast.literal_eval() is the right tool. It parses the string and evaluates only nodes that make up literals: strings, bytes, numbers, tuples, lists, dicts, sets, booleans, None and Ellipsis[1]. Names, calls, attribute access, operators and comprehensions are refused.

The documentation says the function "is not capable of evaluating arbitrarily complex expressions, for example involving operators or indexing"[1], and 2 ** 10 is duly refused. The output shows one exception in CPython 3.13: 3 + 4j is accepted, because a complex number has no literal form of its own and can only be written as a real part plus an imaginary part. Two other accepted inputs come from documented changes: set() has worked since Python 3.9, and leading spaces and tabs in a string have been stripped since 3.10[1].

"Safe" has limits

The documentation now says the function "had been documented as 'safe' in the past without defining what that meant. That was misleading."[1] It cannot run code, but "a relatively small input can lead to memory exhaustion or to C stack exhaustion, crashing the process", and it may raise ValueError, TypeError, SyntaxError, MemoryError or RecursionError[1]. Calling it on untrusted data "is thus not recommended"[1]. For data from outside, prefer a format with a dedicated parser, such as JSON, and limit the input size.

10Practical uses

Real tools are built on exactly these pieces. The Bandit security scanner "processes each file, builds an AST from it, and runs appropriate plugins against the AST nodes"[9]. The Black formatter "performs an AST safety check after formatting your code", so that reformatting cannot change what the program does[10]. pytest rewrites the assert statements in test modules as it imports them, using an import hook that writes new .pyc files, which is how it can show the values in a failing comparison[11]. A codemod that keeps comments

A codemod is an automated, mechanical edit across a code base, such as renaming a function everywhere. Unparsing would throw away every comment, so the careful approach is to use the tree only to find the exact positions and to edit the original text. Edits are applied from the end of the file backwards so that earlier offsets stay valid, and the work is done in bytes because column offsets are UTF-8 byte offsets[1].

11Version differences

Code that works with trees often has to support several Python versions, and the tree is one of the places where versions differ most. These are the changes most likely to affect a tool, all taken from the ast documentation unless another source is cited[1].

3.8ast.Constant used for every literal; Num, Str, Bytes, NameConstant and Ellipsis deprecated. end_lineno/end_col_offset, get_source_segment(), type_comments, feature_version and mode='func_type' added[8]. New nodes NamedExpr (the walrus operator) and TypeIgnore.
3.9ast.unparse(), indent for dump() and python -m ast added. Subscripts store the index directly instead of wrapping it in ast.Index; Index and ExtSlice deprecated. New PEG parser[6].

12Pitfalls

  • Forgetting generic_visit(). A visitor or transformer method that does not call it stops the walk at that node, and nothing beneath is seen (section 5)[1].
  • Missing locations. Nodes built by hand need fix_missing_locations() or copy_location() before compile(), or you get TypeError: required field "lineno" missing (section 7)[1].
  • Treating a parse as validation. ast.parse("return 42") succeeds; scoping and context errors only appear at compile()[1].
  • Character columns. col_offset is a UTF-8 byte offset, so slicing a str with it goes wrong after any non-ASCII character. Use get_source_segment() or slice bytes[1].
  • Expecting unparse() to round-trip text. It reproduces meaning, not formatting, and drops comments[1].
  • Relying on ast.walk() order. The order is unspecified[1]. Sort results by (lineno, col_offset) if you print them, or use a visitor.
  • Mismatched modes. A tree from mode='eval' must be compiled with 'eval', and its body is a single node, not a list.
  • Thinking literal_eval() is a sandbox. It does not run code, but it is not recommended for untrusted input because of memory and stack exhaustion[1].
  • Hard-coding node shapes. The abstract grammar can change in every release[1]. Pin a minimum version, check _fields, and test your tool against each Python version it supports.
  • Parsing huge or hostile input in-process. Deeply nested source can crash the interpreter[1,4].

Exercise 1: Node censuswalk · easy

Write census(source) that returns how many statement nodes and how many expression nodes a piece of source contains, using the abstract base classes ast.stmt and ast.expr. Try it on "for i in range(3):\n total = total + i\nprint(total)".

Show solution

ast.walk() visits every node, and isinstance() against the base classes groups them without listing each concrete type.

The three statements are the For, the Assign and the Expr that wraps the print call. The eleven expressions include every Name, Constant, Call and BinOp.

Exercise 2: What does this module import?walk · easy

Write imported_modules(source) that returns a sorted list of top-level package names a module imports, from both import a.b and from a.b import c. Relative imports (from . import x) should be ignored.

Show solution

Import holds a list of alias nodes. ImportFrom has a module string and a level, which is above zero for relative imports.

Because ast.walk() reaches every node, the import inside lazy() is found too.

Exercise 3: Missing docstringsvisitor · medium

Write a NodeVisitor that reports every public function, method and class (name not starting with _) that has no docstring, as line:qualified.name, for example 7:Cart.total.

Show solution

Keep a stack of enclosing names for the qualified name and use ast.get_docstring(). The same method handles FunctionDef, AsyncFunctionDef and ClassDef.

Exercise 4: Rename a variabletransformer · medium

Write a NodeTransformer that renames every use of a variable, including function parameters, and returns the new source with ast.unparse(). Rename n to count in:

def repeat(word, n):
    return word * n

n = 3
print(repeat("ab", n))
Show solution

Variables appear as Name nodes, but parameters are arg nodes, so both need a method.

A real refactoring tool would also have to respect scopes: a different n in an unrelated function should not change. That needs a symbol table, the step that follows parsing in the compiler[2].

Exercise 5: Your own constant foldertransformer · hard

Write a transformer that replaces any BinOp whose two operands are numeric constants with a single Constant holding the result, for +, -, * and /. It must fold nested expressions such as (2 + 3) * 4 and leave x * 2 alone. Compile the result and check that the folded code gives the same answer.

Show solution

Call generic_visit() first, so the operands are folded before their parent is examined; that is what makes nesting work. Use copy_location() so the new node keeps its position.

The type check keeps the folder away from cases such as "ab" * 3, and x * 2 survives because x is a Name. Note that (2 + 3) * 4 - x * 2 + 10 / 4 groups as ((20 - x*2) + 2.5), so 10 / 4 folds but cannot merge with 20. CPython's own optimiser, shown with optimize=1 in section 7, does this kind of folding for you[1].

Exercise 6: A safe calculatorevaluator · hard

Write calculate(expr) that evaluates arithmetic typed by a user: numbers, + - * / // % **, unary minus and parentheses. Anything else, such as names, calls or attribute access, must raise ValueError. Do not use eval().

Show solution

Parse in 'eval' mode and write a recursive evaluator that accepts an explicit allow-list of node types. Anything not on the list is rejected, which is safer than trying to block dangerous nodes one by one. A limit on the exponent keeps 9 ** 9 ** 9 from freezing the program.

Unlike ast.literal_eval(), which refuses operators[1], this evaluator accepts exactly the arithmetic you allow. Note that -2 ** 2 is -4: the tree shows that ** binds more tightly than unary minus, and the evaluator follows the tree. A ZeroDivisionError from 1 / 0 would still escape, which a real application should catch as well.
