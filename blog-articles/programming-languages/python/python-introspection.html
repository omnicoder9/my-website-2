Introspection in Python

Every Python object can tell you what it is, where it came from and what it can do. This article shows how to ask: from type() and dir() through the inspect module, stack frames, type hints, memory and garbage-collector queries, to the code objects behind every function.

1Overview

Introspection is a program examining its own objects while it runs: asking an object for its type, its attributes, its documentation, the parameters it accepts or the source code that defined it. Python supports this unusually well because almost everything is an ordinary object. Classes, functions, modules, stack frames and compiled code all carry their metadata as attributes you can read[1], and functions in particular are first-class objects whose attributes describe their own parameters, defaults and code[2].

The standard library has three layers of tools for this. The built-in functions type(), isinstance(), dir(), vars(), id(), callable() and help() answer quick questions[3]. The inspect module "provides several useful functions to help get information about live objects such as modules, classes, methods, functions, tracebacks, frame objects, and code objects"[4]. The sys and gc modules expose the interpreter itself: loaded modules, object sizes and the garbage collector's reference graph[5,6].

Introspection versus reflection

This article is about looking: every technique here reads an object without changing it. Acting on what you find, such as fetching or setting attributes by a computed name, building classes at run time or dispatching on a type, is usually called reflection and is covered in the companion article on reflection. The line is blurry (for example, getattr() is both), so section 3 also shows how some "read-only" questions can quietly run code.

The article assumes you can write functions and classes. Sections 2 to 5 cover the built-ins, sections 6 and 7 the inspect module and the call stack, section 8 type hints, section 9 sys and gc, and section 10 gives a short tour of code objects. Section 11 collects the pitfalls, and section 12 has seven exercises with tested solutions.

2Types, classes and the MRO

type(), isinstance() and issubclass()

With one argument, type(obj) returns the object's type, which is the same object as obj.__class__[1,3]. The documentation recommends isinstance() for testing a type, "because it takes subclasses into account"[3]. isinstance() returns True for an instance of the class or of "a (direct, indirect, or virtual) subclass thereof", and it accepts a tuple of classes or a union type such as int | str[3]. issubclass() asks the same question about classes, and "a class is considered a subclass of itself"[3].

The last line is worth remembering: bool is a subclass of int, so isinstance(True, int) is true while an exact type(...) is int check is not. Choose the exact check only when you really mean "this class and no subclass".

Virtual subclasses

The word virtual in the isinstance() definition refers to abstract base classes. An ABC can claim classes that do not inherit from it, either by explicit registration with register() or through a __subclasshook__() method[7,8]. Several ABCs in collections.abc use such a hook to recognise any class that defines the required methods, so a class with __len__() counts as Sized[9]. A virtual subclass does not appear in the class's MRO, which the next example confirms.

__mro__: the method resolution order

Every class has a __mro__ attribute, "the tuple of classes that are considered when looking for base classes during method resolution", and a mro() method whose result is stored there[1]. Python computes it with the C3 linearisation, which "behaves correctly even in the presence of 'diamond' inheritance"[1]. C3 was designed for the Dylan language[10] and adopted in Python 2.3; it keeps each class's listed parents in order and is monotonic: if C1 precedes C2 in the linearisation of C, it precedes C2 in the linearisation of every subclass of C[11].

When no order satisfies both rules, class creation fails, and that refusal is itself useful introspection: it tells you the hierarchy is contradictory.

3Attributes: dir, vars and __dict__

dir(obj) attempts "to return a list of valid attributes for that object", and without an argument it lists the names in the current local scope[3]. vars(obj) returns the object's __dict__, the mapping that stores its writable attributes[1,3]. The two answer different questions: vars() shows only what is stored on that object, while dir() also walks the class and its bases.

The documentation is frank about what dir() is for: "Because dir() is supplied primarily as a convenience for use at an interactive prompt, it tries to supply an interesting set of names more than it tries to supply a rigorously or consistently defined set of names, and its detailed behavior may change across releases"[3]. A class can also define __dir__() to return whatever list it likes[3]. Treat dir() as a hint, not a contract. Attributes produced on demand by __getattr__() never show up in it:

Objects without a __dict__

Not every object has a __dict__[1]. A class that declares __slots__ reserves fixed storage for the listed names and prevents the creation of a per-instance dictionary, and vars() raises TypeError for an object without one[1,3]. Built-in values such as integers have none either. dir() still works, because the slots are descriptors on the class.

Looking can run code

hasattr(obj, name) "is implemented by calling getattr(object, name) and seeing whether it raises an AttributeError or not"[3]. That means it runs properties, __getattr__() and any other descriptor, with all their side effects. When you only want to know what is there, inspect.getattr_static() retrieves attributes "without triggering dynamic lookup via the descriptor protocol, __getattr__() or __getattribute__()", and inspect.getmembers_static() (Python 3.11+) does the same for a whole object[4].

4Docstrings and help

A docstring is "a string literal that occurs as the first statement in a module, function, class, or method definition", and it becomes the object's __doc__ attribute[12]. inspect.getdoc() returns the docstring "cleaned up with cleandoc()", which removes the indentation that lines up with the surrounding code[4]. Since Python 3.13 the compiler itself strips the common leading whitespace from docstrings, which shrinks the bytecode cache[13], so on 3.13 __doc__ and getdoc() usually agree. help() is "intended for interactive use" and pages its output[3]; the pydoc module that powers it can render the same text to a string[14].

Do not rely on docstrings being present at run time. Running Python with -OO discards them[15], and code that reads __doc__ to build, say, a command-line help screen will then see None.

5Identity and callability

id(obj) returns an integer "guaranteed to be unique and constant for this object during its lifetime"; in CPython it is the object's memory address[3]. The guarantee covers only overlapping lifetimes: "Two objects with non-overlapping lifetimes may have the same id() value"[3]. Use is to compare identity, and never store an id() as a key for an object that may be freed.

sys.getrefcount() reports how many references point at an object; the number "is generally one higher than you might expect" because the call's own argument counts[5].

callable(obj) tells you whether an object can be called. "If this returns True, it is still possible that a call fails, but if it is False, calling object will never succeed"; classes are callable, and instances are callable when their class has a __call__() method[3].

6The inspect module

Predicates: what kind of object is this?

inspect offers a family of is*() predicates. isfunction() is true for "a Python function, which includes functions created by a lambda expression"; ismethod() for "a bound method written in Python"; isbuiltin() for "a built-in function or a bound built-in method"; isclass() for any class; and isgeneratorfunction() and iscoroutinefunction() for def-with-yield and async def functions[4]. isroutine() accepts any of the function or method kinds[4].

Two rows surprise people. K.method accessed on the class is a plain function, not a method; it only becomes a bound method when accessed on an instance. And K.klass is a method even on the class, because classmethod binds to the class.

getmembers()

inspect.getmembers(obj, predicate) returns "all the members of an object in a list of (name, value) pairs sorted by name", filtered by the optional predicate[4]. Combined with a predicate and the __module__ attribute that every function records[1], it answers questions such as "which functions does this module define, as opposed to import?"

signature(): parameters as data

inspect.signature() returns a Signature object for a callable and raises ValueError when no signature can be provided[4]. It was introduced by PEP 362 as a single, complete description of a function's parameters[16]. Each Parameter has a name, a default, an annotation and a kind: POSITIONAL_ONLY, POSITIONAL_OR_KEYWORD, VAR_POSITIONAL, KEYWORD_ONLY or VAR_KEYWORD[4]. The older getfullargspec() is "retained primarily for use in code that needs to maintain compatibility with the Python 2 inspect module API"; signature() is the recommended API[4].

Signature.bind() maps a set of arguments onto the parameters exactly as a call would, returning a BoundArguments object or raising TypeError; apply_defaults() fills in the parameters that were not passed[4]. This lets you check or log a call without making it.

Source code, files and modules

inspect.getsource() returns "the text of the source code for an object"; it raises OSError if the source cannot be retrieved and TypeError for a built-in module, class or function[4]. getsourcefile(), getsourcelines() and getmodule() answer where an object lives[4]. Decorators complicate this. functools.wraps() copies the wrapped function's name and docstring onto the wrapper and adds a __wrapped__ attribute pointing back at the original[17]. inspect.signature() and inspect.unwrap() follow that chain[4], so the decorated function still reports its real parameters and source.

Notice that the source of a decorated function includes its decorator lines. Because getsource() needs a source file to read, it raises OSError for code that has none, such as a function created with exec() from a string[4].

7Frames and the call stack

Each active function call has a frame object holding its code, its local and global namespaces, its current line and a link to the caller's frame (f_back)[1]. inspect.currentframe() returns the caller's frame, but this is a CPython implementation detail: "If running in an implementation without Python stack frame support this function returns None"[4]. The lower-level sys._getframe() "should be used for internal and specialized purposes only"[5].

Holding on to a frame keeps all its local variables alive and "can cause your program to create reference cycles". The inspect documentation recommends deleting the reference in a finally clause[4]:

inspect.stack() returns a list of FrameInfo records "for the caller's stack", innermost first. Each record has frame, filename, lineno, function, code_context, index and positions fields[4].

A frame's f_locals lets a debugger read the variables of any function on the stack. PEP 667 made its behaviour consistent in Python 3.13: for a function frame, f_locals is now a write-through proxy that always reflects the current values, whereas each call to locals() in a function produces "an independent snapshot"[13,18].

8Annotations and type hints

Annotations are arbitrary expressions attached to parameters, return values and variables. PEP 3107 introduced them with no fixed meaning[19], and PEP 484 gave them the standard meaning of type hints[20]. They are stored in __annotations__, a dictionary keyed by parameter name plus 'return'[1]. On Python 3.10 to 3.13 the recommended way to read them is inspect.get_annotations()[21]; typing.get_type_hints() goes further, evaluating string annotations into real objects, merging class annotations along the MRO and, unless you pass include_extras=True, stripping Annotated metadata[22]. typing.get_origin() and typing.get_args() take a generic hint apart[22].

With from __future__ import annotations (PEP 563), annotations are stored as strings instead of being evaluated at definition time[23]. __annotations__ then shows the strings; inspect.get_annotations(obj, eval_str=True) or get_type_hints() turns them back into objects[4,22].

Evaluation can fail. A common case is a name imported only under typing.TYPE_CHECKING, which the annotations HOWTO lists among the strings that cannot be evaluated at run time and the reason to evaluate only when the caller asks[21]:

Python 3.14 changes this

Python 3.14 implements PEP 649 and PEP 749: annotations are evaluated lazily when first requested, and the new annotationlib module provides annotationlib.get_annotations(), which supersedes inspect.get_annotations() (now an alias for it)[4,21,24]. Code that goes through these helpers rather than touching __annotations__ directly keeps working across versions.

9sys and gc: the running interpreter

sys.getsizeof()

sys.getsizeof(obj) returns an object's size in bytes. "Only the memory consumption directly attributed to the object is accounted for, not the memory consumption of objects it refers to", and the figure includes garbage-collector overhead for objects the collector manages[5]. Because it is shallow, getsizeof() of a container reports only the container's own array of pointers. The documentation points to a recipe that walks the contents recursively[5]; a compact version follows (exercise 5 extends it).

sys.modules

sys.modules "is a dictionary that maps module names to modules which have already been loaded". Because other code or threads can import modules while you look, the documentation says to iterate over sys.modules.copy() or tuple(sys.modules)[5].

The garbage collector's view

gc.get_referrers(*objs) returns "the list of objects that directly refer to any of objs", and gc.get_referents() the objects they refer to[6]. Both see only objects that support garbage collection, and the documentation warns that referrers may be "in a temporarily invalid state": "Avoid using get_referrers() for any purpose other than debugging"[6]. Used that way, it is the quickest answer to "what is keeping this object alive?"

Notice that on CPython 3.13 the referrer reported for holder.data is the Cache instance itself, not a separate attribute dictionary, so code that interprets referrers should be ready for both.

The collector does not track every object. "As a general rule, instances of atomic types aren't tracked and instances of non-atomic types (containers, user-defined objects...) are", but type-specific optimisations exempt some containers, such as dictionaries holding only atomic values[6]. gc.is_tracked() shows the result, which can change between versions:

10Code objects and dis

A function's __code__ attribute holds its code object. "Code objects represent byte-compiled executable Python code, or bytecode", and unlike a function, a code object "contains no context" such as globals and is immutable[1]. Its co_* attributes describe the compiled body: name, argument count, local variable names, constants, file and first line[1]. The dis module disassembles it[25].

Treat this output as version-specific: "Bytecode is an implementation detail of the CPython interpreter. No guarantees are made that bytecode will not be added, removed, or changed between versions of Python"[25]. Instruction sets, specialisation and how to read a disassembly are the subject of the companion article on Python bytecode; for introspection, the stable parts are the co_* metadata and dis.get_instructions(), which yields structured Instruction records instead of text[25].

11Pitfalls

One pitfall deserves a full example because it is so confusing in practice. Since hasattr() just catches AttributeError[3], a property that fails with an AttributeError of its own makes a real attribute look absent:

PitfallWhy it bitesDo this instead
type(x) == SomeClassRejects subclasses, including bool for int[3].isinstance(), or type(x) is C only when exactness is the point.
Trusting dir() as completeIts output is a convenience that may change between releases, can be overridden by __dir__(), and misses __getattr__() names[3].Use it to explore; test for a specific attribute directly.

Exercise 3: Check argument types at call timesignature · medium

Write a decorator @checked that, on each call, binds the arguments to the function's signature, applies defaults, and raises TypeError if any argument whose type hint is a plain class is not an instance of it. Hints that are not classes (such as list[int]) may be skipped. Keep the function's name and signature visible to inspect.

Signature.bind() does the argument matching[4], get_type_hints() resolves the hints[22], and functools.wraps() keeps the metadata[17].

Exercise 4: A logger that knows where it was calledframes · medium

Write log(message) that prints [module:function:line] message using the caller's frame, without leaving a reference cycle. Calls from module level should show <module> as the function.

Show solution

The caller's frame is f_back of the current frame; its code object gives the function name and its globals give the module name[1]. The finally clause follows the inspect documentation's advice[4].

Exercise 5: A better deep sizesys · medium

Extend the deep_size() function from section 9 so that it also counts the attributes of ordinary instances (through __dict__) and of slotted instances (through __slots__), and still handles cycles. Show that a self-referencing list does not loop forever.

Show solution

getsizeof() is shallow[5], and a slotted instance has no __dict__[1], so both storage forms need their own branch. getattr_static() could be used to avoid running properties, but slot values are read through their descriptors, which have no side effects.

Exercise 6: Who is holding on?gc · medium

Write holders(obj) that returns a list of human-readable descriptions of what refers to obj: the global names in a module, the indexes in a list, the keys in a dict, and the attribute names on an instance. Ignore the frame of holders() itself.

Show solution

Use gc.get_referrers() for debugging only, as its documentation says[6]. As section 9 showed, the referrer for an instance attribute can be the instance itself rather than a dictionary; vars() reads its attributes in either case[3].

    def post(self, url, data): ...
    def close(self): ...

class ClientV2:
