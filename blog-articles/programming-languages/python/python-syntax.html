Introduction

A Python program is read by a parser, and the input to the parser is a stream of tokens produced by a lexical analyser.1 The lexer divides the program into logical lines. The end of each logical line is marked by a NEWLINE token, and statements cannot cross logical line boundaries except where the syntax allows a NEWLINE, such as between the statements of a compound statement.1 A logical line is built from one or more physical lines (the lines you see in an editor) by the line-joining rules described in section 2.1

The ten sections below follow that order: first the lexical layer (comments and indentation), then the grammar (statements and expressions), then the meaning of names (variables, dynamic typing, keywords and identifiers), and finally the community conventions for writing code (naming and PEP 8). Each section ends with exercises. Open the solution only after you have tried the exercise.

1Comments

A comment starts with a hash character (#) that is not part of a string literal, and ends at the end of the physical line.1 Comments are ignored by the syntax.1 A comment may stand on its own line or follow code on the same line, but a # inside a string literal is just a character.2

Because a comment ends at the end of its physical line, Python has no multi-line comment token. A block comment is simply several comment lines in a row. PEP 8 asks that each line of a block comment start with # and a single space, and that inline comments be separated from the statement by at least two spaces and be used sparingly.3

Docstrings are not comments

A docstring is a string literal that occurs as the first statement in a module, function, class or method definition, and it becomes the __doc__ attribute of that object.4 Unlike a comment, a docstring is kept at run time, where code and tools can read it.4 PEP 257 recommends triple double quotes for all docstrings, and says a one-line docstring should be a phrase ending in a period that states the function's effect as a command (“Return …”), not as a description.4

A multi-line docstring consists of a summary line, a blank line and then a more detailed description.4 A string literal that is not the first statement of a definition is not a docstring. It is an ordinary expression statement: the string is evaluated and the result is discarded.5 The ast module shows this directly:

2Indentation

Most languages mark blocks with braces or keywords. Python uses indentation. Leading whitespace at the start of a logical line is used to compute the line's indentation level, and that level decides how statements are grouped.1 In a compound statement, each clause header begins with a keyword and ends with a colon, and the group of statements it controls (its suite) can be one or more indented statements on the following lines.6

How the lexer turns indentation into tokens

The lexer keeps a stack of indentation levels. Before the first line is read, a single zero is pushed on the stack and never popped. At the start of each logical line the line's indentation is compared with the top of the stack. If it is equal, nothing happens. If it is larger, it is pushed and one INDENT token is generated. If it is smaller, it must be one of the numbers already on the stack; every larger number is popped, and one DEDENT token is generated for each.1 You can watch this with the standard tokenize module:

Two common mistakes follow from that algorithm. Indenting a line more deeply than the block it belongs to is an “unexpected indent”. Dedenting to a column that is not on the stack is rejected because the new level matches no outer block.1

Tabs, spaces and blank lines

For the purpose of computing indentation, tabs are replaced, from left to right, by one to eight spaces so that the total number of characters up to and including the replacement is a multiple of eight.1 A source file that mixes tabs and spaces in a way that makes the meaning depend on how wide a tab is gets rejected with a TabError.1 PEP 8 settles the question for new code: use 4 spaces per indentation level, and prefer spaces to tabs.3

A logical line that contains only spaces, tabs, form feeds and possibly a comment is ignored, so blank lines never change indentation.1

Line joining

Indentation is only measured at the start of a logical line, so continuation lines can be laid out freely. Expressions in parentheses, square brackets or curly braces can be split over several physical lines without backslashes (implicit line joining).1 A physical line that ends in a backslash outside a string literal or comment is joined to the next line (explicit line joining).1 PEP 8 prefers implicit joining inside brackets over backslashes.3

3Statements

The Python glossary defines a statement as part of a suite (a “block” of code); a statement is either an expression or one of several constructs with a keyword, such as if, while or for.7 The language reference divides statements into two kinds.

  • Simple statements fit within a single logical line. Several simple statements may share one line if they are separated by semicolons.5 Examples: expression statements, assignments, pass, del, return, import, global and raise.5
  • Compound statements contain groups of other statements and control their execution. They generally span several lines.6 Examples: if, while, for, try, with, match, and function and class definitions.6

Assignment statements

Assignment statements (re)bind names to values and modify attributes or items of mutable objects.5 The reference allows several forms. A chained assignment assigns the same object to every target. An unpacking assignment needs an iterable with as many items as there are targets, unless one target is prefixed with *; that starred target receives a list of the remaining items.5 An augmented assignment such as x += 1 evaluates its target only once, and an annotated assignment combines a variable annotation with an optional assignment.5

The first line is legal, but PEP 8 discourages compound lines with several statements and recommends one statement per line.3

Compound statements: headers and suites

A compound statement consists of one or more clauses. Each clause has a header that starts with a keyword and ends with a colon, followed by a suite. All clause headers of one statement sit at the same indentation level.6 A suite may be written on the same line as the header, as semicolon-separated simple statements, but only an indented suite on the following lines can contain a nested compound statement.6

In the one-line form the semicolon binds more tightly than the colon, so either all of the statements after the colon run or none do.6

4Expressions

An expression is a piece of syntax that can be evaluated to some value: a combination of literals, names, attribute access, operators or function calls.7 Not every construct is an expression. while is a statement, and so is ordinary assignment with =.7

The rules behind each line come from chapter 6 of the language reference:

  • Precedence and grouping. Operators in the same precedence group are evaluated left to right, except exponentiation and conditional expressions, which group right to left.8
  • Chained comparisons. x < y <= z is equivalent to x < y and y <= z, except that y is evaluated only once, and z is not evaluated at all if x < y is false.8
  • Boolean operators. x and y returns x if it is false, otherwise y; x or y returns x if it is true, otherwise y. They return the last evaluated argument, not necessarily True or False.8
  • Conditional expressions. x if C else y evaluates C first, then only one of x or y.8
  • Lambdas. lambda parameters: expression creates an anonymous function object; its body cannot contain statements or annotations.8 PEP 8 recommends a def statement rather than binding a lambda to a name.3
  • Assignment expressions. NAME := expr, added in Python 3.8 by PEP 572, binds a name and also returns the value.8,9

Expression statements versus assignment

Any expression can stand alone as an expression statement; the value is computed and, outside the interactive prompt, discarded. This is mostly used to call functions.5 Assignment goes the other way. 5Variables

In Python, a variable is a name bound to an object. The execution model states it directly: names refer to objects, and names are introduced by name-binding operations.10 Binding operations include assignment targets, function parameters, def and class statements, for loop targets, names after as in with and except, import statements and assignment expressions.10 Using a name that has never been bound raises NameError.2,10

Every object has an identity, a type and a value. The identity never changes once the object is created; the is operator compares identities, and id() returns an integer that represents it.11 Assignment does not copy objects. It binds another name to the same object:

Whether a change through one name is visible through another depends on mutability. Objects whose value can change are mutable (lists and dictionaries); objects whose value cannot change once created are immutable (numbers, strings and tuples).11 An operation that “changes” an immutable object actually creates a new object and rebinds the name:

Scope

If a name is bound anywhere in a block, such as a function body, it is local to that block unless it is declared global or nonlocal. A name bound at module level is global.10 Because the decision is made for the whole block, reading a local name before it has been bound raises UnboundLocalError, a subclass of NameError.10

6Dynamic typing

In Python, types belong to objects, not to names. An object's type determines which operations it supports and which values it can have, and like its identity, an object's type cannot change.11 A name, however, can be rebound to an object of any type at any time, because binding just makes the name refer to an object.10 Nothing has to be declared in advance.

Duck typing

Idiomatic Python code usually asks what an object can do rather than what it is. The glossary calls this duck typing: a style that does not look at an object's type to decide whether it has the right interface, but simply calls the method or uses the attribute.7 Duck-typed code avoids tests with type() or isinstance().7

When an explicit check is needed, PEP 8 says object type comparisons should use isinstance() instead of comparing types directly.3 isinstance() also accepts instances of subclasses.12

Type hints are optional and not enforced

PEP 484 introduced a standard syntax for type hints, and PEP 526 added annotations for variables.13,14 Both proposals state that Python will remain a dynamically typed language and that the authors have no desire to make type hints mandatory.13,14 PEP 484 states that no type checking happens at run time; hints are read by external tools such as static type checkers.13

Some identifiers are reserved only in particular contexts. These soft keywords are match, case and _ in a match statement, and type in a type statement. 8Identifiers

Identifiers (names) are made of uppercase and lowercase letters A–Z and a–z, the underscore _, the digits 0–9 (which cannot be the first character), and “letter-like” or “digit-like” non-ASCII characters.1 A name must have at least one character and has no upper length limit, and case is significant.1

The output shows that str.isidentifier() accepts "for": it checks the shape of a name, not whether it is reserved, so combine it with keyword.iskeyword().15 first-name fails because - is the subtraction operator, not a name character.1

Unicode identifiers and normalisation

PEP 3131, accepted for Python 3.0, allows non-ASCII identifiers: the first character must have the Unicode property XID_Start and the rest XID_Continue.16 All names are converted to Unicode normalisation form NFKC while parsing, so two spellings that normalise to the same string are the same name.1,16 That normalisation happens only at the lexical level; run-time functions that take names as strings generally do not normalise them.1

PEP 3131 also sets a policy: identifiers in the Python standard library must be ASCII-only, and should use English words wherever feasible.16 PEP 8 repeats that rule for the standard library.3

Reserved classes of identifiers

Certain patterns of leading and trailing underscores have special meaning:1

PatternMeaning

__*Class-private names: inside a class body they are rewritten (mangled) to avoid clashes between base and derived classes.1

9Naming conventions

The language only enforces the identifier rules above. How names should look is a convention, set out in the naming section of PEP 8.3

Kind of nameConventionExample
ModulesShort, all-lowercase; underscores allowed if they help readability3textwrap, data_loader
ClassesCapWords (also called CamelCase)3HttpClient
ExceptionsCapWords, with the suffix Error if the exception is an error3ParseError
Functions and variablesLowercase, words separated by underscores3load_config, retry_count
Methods and instance variablesSame as functions; one leading underscore for non-public ones3self._cache
ConstantsAll capitals with underscores, at module level3MAX_RETRIES

PEP 8 also describes what underscores signal:3

  • _single_leading_underscore is a weak “internal use” indicator.
  • single_trailing_underscore_ avoids a clash with a keyword, for example class_.
  • __double_leading_underscore on a class attribute invokes name mangling.
  • __double_leading_and_trailing__ names are “magic” names reserved for Python; never invent them.

Finally, never use the characters l (lowercase el), O (uppercase oh) or I (uppercase eye) as single-character variable names, because in some fonts they are indistinguishable from the digits one and zero.3

10Code style (PEP 8)

PEP 8, the Style Guide for Python Code, was written in 2001 by Guido van Rossum, Barry Warsaw and Alyssa Coghlan as the convention for the code in the Python standard library.3 Its premise is that code is read much more often than it is written, so consistency makes code easier to understand; it quotes PEP 20, “Readability counts”.3,17 It is a guide, not a law. Consistency within a project matters more than consistency with PEP 8, consistency within one module or function matters most, and project-specific style guides take precedence for their project.3

The rules most often applied

TopicPEP 8 recommendation
Indentation4 spaces per level; spaces preferred over tabs.3
Line lengthAt most 79 characters; 72 for docstrings and comments.3
Line breaksPrefer implied continuation inside brackets to backslashes; for new code, break lines before binary operators.3
Blank linesTwo around top-level function and class definitions; one around method definitions.3
ImportsAt the top of the file, usually one per line, grouped as standard library, third-party, then local, with a blank line between groups.3
WhitespaceNo extra spaces immediately inside brackets; a single space on each side of assignment, comparison and Boolean operators.3
ComparisonsCompare to singletons such as None with is or is not, never with ==.3
Type checksUse isinstance() rather than comparing types directly.3
CommentsBlock comments start with # and one space; inline comments are separated by at least two spaces.3
