Metaclasses in Python

A class is an object, and every object has a type. The type of a class is its metaclass. This article follows a class statement step by step through the machinery that builds it, shows where a metaclass can step in, and explains when __init_subclass__, __set_name__ or a class decorator does the same job with less risk.

1Overview

The Python glossary defines a metaclass as "the class of a class". A class definition produces a class name, a class dictionary and a list of base classes, and the metaclass is responsible for taking those three things and creating the class[1]. Most object-oriented languages have a fixed, built-in way of doing this. Python lets you replace it with your own metaclass. The glossary adds that most users never need this tool, but that when the need arises metaclasses can give powerful, elegant solutions, and it lists logging attribute access, adding thread safety, tracking object creation and implementing singletons among their uses[1].

The language reference describes the default precisely: classes are constructed with type(); the class body runs in a new namespace, and the class name is bound to the result of type(name, bases, namespace)[2]. A custom metaclass replaces that call, so it can change how the namespace is prepared, how the class object is built, how the class behaves as an object (for example what len(cls) or repr(cls) returns), and what happens when the class is called to make an instance.

That power is also the reason to be careful. A metaclass is inherited by every subclass, and two unrelated metaclasses cannot be combined automatically. Python 3.6 therefore added two lighter hooks, __init_subclass__ and __set_name__, so that the most common jobs no longer need a metaclass at all[3]. This article covers both the full mechanism and those alternatives, and Section 8 has a table for choosing between them.

2Classes are objects

Every object in Python has an identity, a type and a value, and the type() function returns an object's type, which "is an object itself"[2]. Classes are no exception: a class is an object, so it has a type too. For an ordinary class that type is type, and type is its own type.

The fourth line of output prints True three times, which shows the two halves of Python's object model. Every class, including type, is an instance of type; every class, including type, inherits from object, the ultimate base of all classes[4].

A class is also made at run time. "A class definition is an executable statement": Python runs the class body in a new local namespace, then creates a class object from the base classes and that saved namespace, and binds the class name to it[5]. So a class statement inside a function produces a new, distinct class each time the function runs.

3Creating classes with type()

Called with one argument, type() returns the type of an object. Called with three, type(name, bases, dict) returns a new type object, "essentially a dynamic form of the class statement"[4]. The name becomes __name__, the bases tuple becomes __bases__ (with object added if it is empty), and the dictionary supplies the attributes and methods that a class body would define[4].

Keyword arguments given to the three-argument form go to the metaclass machinery, usually __init_subclass__, just as keywords in a class header (other than metaclass) would[4]. Unlike a class statement, though, type(name, bases, dict) never calls the metaclass's __prepare__ method. The documentation recommends types.new_class() when you need to create a class dynamically with the appropriate metaclass[4]. types.new_class(name, bases, kwds, exec_body) takes the parts of a class header, works out the metaclass, prepares the namespace and passes it to the exec_body callback to fill in[6].

The last case shows that type() still picks the most derived metaclass from the bases (here Meta, see Section 7), but the namespace was a plain dictionary built by the caller, so Meta.__prepare__ never ran.

4How a class is created

When a class definition is executed, the language reference lists five steps[2]:

  1. MRO entries are resolved. A base that is not a class may provide __mro_entries__(), which returns the classes to use in its place[2,7]. This is how class C(List[int]) works in the typing module.
  2. The appropriate metaclass is determined from the explicit metaclass= keyword, if any, and the metaclasses of all the bases (details in Section 7)[2].
  3. The class namespace is prepared. If the metaclass has a __prepare__ attribute, it is called as metaclass.__prepare__(name, bases, **kwds); otherwise the namespace is an empty ordered mapping[2].
  4. The class body is executed, approximately as exec(body, globals(), namespace)[2].
  5. The class object is created by calling metaclass(name, bases, namespace, **kwds)[2].

Step 5 has more inside it. When the metaclass is type, or any metaclass that ultimately calls type.__new__, three further things happen after the class object exists: type.__new__ collects every attribute in the namespace that defines __set_name__, calls each of those with the new class and the attribute's name, and then calls __init_subclass__ on the immediate parent of the new class in its method resolution order[2]. Only after all of that is the class passed to any class decorators, and the result bound to the class name[2].

Calling metaclass(...) is itself an ordinary call of an object, so it goes through type.__call__, which runs the metaclass's __new__ and then its __init__, exactly as calling any class runs its __new__ and __init__[2]. Why __prepare__ is a class method

__prepare__ runs before the class exists, so it cannot be an instance method of the metaclass (its "instance" would be the class not yet created). The reference says it should be implemented as a classmethod[2]. type.__prepare__ exists and returns an empty dictionary, so calling super().__prepare__() is safe.

Ordered namespaces

Since Python 3.6 the default class namespace is an insertion-ordered mapping, a change made by PEP 520[6,8]. The order in which attributes are defined in the class body is preserved in the class's __dict__[5]. Before that change, preserving declaration order was one of the main reasons to write a __prepare__ method, and it was the first use case that PEP 3115 gave for adding the hook[9].

5Writing a metaclass

The metaclass keyword

A metaclass is usually a subclass of type. You attach it with the metaclass keyword in the class header, or by inheriting from a class that already has one: in the reference's own example, both MyClass(metaclass=Meta) and its subclass MySubclass(MyClass) are instances of Meta[2]. The keyword syntax comes from PEP 3115, which replaced Python 2's practice of assigning a __metaclass__ variable in the class body[9]. In Python 3 that old variable is just an ordinary class attribute with no special meaning, as the last lines below show.

The attribute lookup explains why describe() works on B but not on B(). A lookup such as B.describe is handled by type.__getattribute__, which follows the same steps as an instance lookup except that the instance dictionary is replaced by a search through the class's MRO[10]. Just as an instance lookup falls back to the instance's type, a class lookup falls back to the class's type, the metaclass, as the output shows. An instance lookup stops at the instance's class and never reaches the metaclass. A metaclass method is therefore a little like a classmethod, except that it is invisible from instances.

Special methods on the class

Implicit calls to special methods such as len() look the method up on the object's type, not on the object itself[2]. For a class, the type is the metaclass. So the only way to make len(SomeClass) or iter(SomeClass) work is to define __len__ or __iter__ on its metaclass. Defining them on the class (even as class methods) affects instances, not the class.

Customising the namespace with __prepare__

The namespace returned by __prepare__ receives every assignment in the class body. It is passed to the metaclass's __new__, but when the final class object is created the namespace is copied into a new dict[2]. PEP 3115 gives this hook as the way for a metaclass "to get involved in the class construction process earlier"[9]. 6Controlling instance creation with __call__

"Classes are callable", and calling one normally passes the arguments to __new__ and then to __init__[2]. That call is handled by the metaclass, since a class is an instance of its metaclass: Model(42) means type(Model).__call__(Model, 42). type.__call__ calls __new__ and, if __new__ returns an instance of the class, calls __init__ on it[2]. Overriding __call__ in a metaclass therefore lets you decide whether a new instance is made at all.

Compare this with overriding __new__ on the class itself: in that version Python still calls __init__ on the returned object every time, because __new__ returned an instance of the class[2]. The metaclass version skips the whole call. The singleton is used here only to show the mechanism; in most programs a module-level object is the simpler choice.

7Metaclass conflicts

Python chooses the metaclass for a new class with three rules: if there are no bases and no explicit metaclass, type is used; if the explicit metaclass is not an instance of type (for example a plain function), it is used directly; otherwise "the most derived metaclass is used"[2]. The most derived metaclass is chosen from the explicit metaclass and the metaclasses of all the bases, and it must be a subtype of all of them. If no candidate meets that test, the class definition fails with TypeError[2].

The fix is a metaclass that derives from both, passed explicitly. PEP 487 points out that there is no automatic way to combine metaclasses, and that the problem tends to appear as a surprise when a class inherits from two libraries, or when a library starts using a metaclass it did not use before[3]. The most common real case involves abc.ABC, whose metaclass is ABCMeta; the abc documentation warns that inheriting from ABC "requires the usual precautions regarding metaclass usage, as multiple inheritance may lead to metaclass conflicts"[11].

A combined metaclass works only if both parents use cooperative super() calls, so that each one's __new__ and __init__ run. Every metaclass you publish raises this cost for your users, which is the strongest argument for the alternatives in the next section.

8Simpler alternatives

PEP 487 starts from the observation that customising class creation used to require a custom metaclass, which "then persists for the entire lifecycle of the class, creating the potential for spurious metaclass conflicts"[3]. It added two hooks that run inside type.__new__, so they work with the default metaclass and need no metaclass of their own[2,3].

__init_subclass__

__init_subclass__ is called on a class "whenever the containing class is subclassed", with the new subclass as its argument; it is implicitly a class method[2]. Keyword arguments in the subclass's header are passed to it, and the reference recommends taking the ones you need and passing the rest on with super()[2]. The default object.__init_subclass__ does nothing, "but raises an error if it is called with any arguments"[2].

The hook runs for subclasses only, not for the class that defines it; that is why Plugin itself is not in the registry and is not checked for run(). A metaclass's __init__, by contrast, also runs for the base class, which is why PluginMeta in Section 7 had to test if bases.

__set_name__

When a class is created, type.__new__ scans the class variables and calls __set_name__(self, owner, name) on each one that defines it[2]. This lets a descriptor learn the name it was assigned to, a job that used to need a metaclass. The Descriptor HowTo uses it so that each field records its own public and private names[10].

Class decorators

A class decorator is a function that receives the finished class and returns a class (usually the same one). @f1(arg) @f2 class Foo is roughly Foo = f1(arg)(f2(Foo))[5]. Class decorators were added by PEP 3129. During the debate on function decorators they were thought unnecessary "thanks to metaclasses", but experience showed that doing decorator-like work with metaclasses gave results that were "generally unpleasant and the implementation highly fragile"[12]. The PEP also names the key difference: "metaclasses are inherited, whereas class decorators are not"[12]. The @dataclass decorator in the standard library is a well-known example: it examines the class for annotated fields and adds generated special methods[13].

9Metaclasses in the standard library

abc.ABCMeta

The abc module provides ABCMeta, the metaclass for defining abstract base classes as outlined in PEP 3119, and the helper class ABC, whose metaclass is ABCMeta[11,14]. A class whose metaclass is derived from ABCMeta "cannot be instantiated unless all of its abstract methods and properties are overridden"[11]. ABCMeta also lets you register unrelated classes, even built-in ones, as "virtual subclasses": issubclass() then reports them as subclasses, but the ABC does not appear in their MRO[11]. It does this by implementing __instancecheck__ and __subclasscheck__, which the data model says are looked up on the metaclass and "cannot be defined as class methods in the actual class"[2].

enum.EnumType

Enumerations, added by PEP 435, are built by the metaclass EnumType (called EnumMeta before Python 3.11, which remains as an alias)[15,16]. EnumType sets the correct __repr__, __str__, __format__ and __reduce__ on the enum, creates the members, handles duplicates and provides iteration over the enum class[16]. The Enum HOWTO adds that it provides __contains__, __dir__, __iter__ and other methods that allow things that fail on a typical class, such as list(Color), and that it creates all the members while creating the class and then installs a custom __new__ so that no new members can be made[17].

Each of those five names is defined on the metaclass, which is why len(Color), Color.RED in Color, Color["BLUE"] and the value lookup Color(2) all work on the class. The HOWTO notes that most enum needs can be met with ordinary subclasses, decorators or functions, and that subclassing EnumType is for a "different Enum experience"[17].

A metaclass that was removed

Before Python 3.7 the typing module's Generic class used a custom metaclass. Since 3.7 it no longer does[18]; PEP 560 replaced it with the __class_getitem__ and __mro_entries__ hooks, partly to avoid metaclass conflicts[7]. The standard library itself has been moving work out of metaclasses where a lighter hook will do.

10Use cases

The data model lists ideas that have been explored with metaclasses: enum, logging, interface checking, automatic delegation, automatic property creation, proxies, frameworks, and automatic resource locking or synchronisation[2]. Registration and validation of subclasses have already been shown with __init_subclass__, which is now the better tool for them. This section shows two cases where a metaclass still earns its place because it changes how the class itself behaves.

Structural isinstance checks

A metaclass can define __instancecheck__ to change what isinstance() means for its classes[2]. Here a class matches any object that has the required methods, which is the idea behind ABCMeta.__subclasshook__ and typing.Protocol.

11Pitfalls

Dropping __classcell__

If any method in a class body uses super() or __class__, the compiler creates an implicit __class__ closure cell so that zero-argument super() can find the class being defined[2,19]. In CPython the cell is passed to the metaclass as a __classcell__ entry in the namespace, and it must reach type.__new__; failing to pass it on is a RuntimeError since Python 3.8[2]. A metaclass that rebuilds the namespace and filters out "dunder" names will trip over this.

Changing the namespace in __init__

By the time the metaclass's __init__ runs, type.__new__ has already copied the namespace into the class[2]. Editing the ns argument there changes nothing; use setattr(cls, ...), or edit the namespace in __new__ before calling super().__new__().

Late attributes skip __set_name__

__set_name__ is called only for attributes present when the class is created. If you assign the attribute afterwards, the hook is not called automatically, and you must call it yourself[2].

Special methods defined on the wrong level

Because implicit special method lookup goes to the type[2], a __len__ written as a class method on the class does not make len(cls) work. It belongs on the metaclass, as in Section 5.

Misspelled class keywords

Class keywords travel to __init_subclass__, and the default object.__init_subclass__ raises an error if it receives any[2]. A typo in a keyword therefore fails loudly, which is good, but the message does not say which keyword was wrong.

Other things to watch

  • Metaclasses spread. Every subclass inherits the metaclass[2], so adding one to a public base class can break user code that mixes your class with another library's (Section 7)[3].
  • The three-argument type() skips __prepare__[4]. Use types.new_class() when a metaclass relies on its namespace[6].
  • Python 2 code that sets __metaclass__ in the class body silently loses its metaclass in Python 3; the keyword form from PEP 3115 is required[9].
  • Clarity. A metaclass runs code that is not visible at the class definition. Prefer the lightest tool from the table in Section 8 that does the job, as the glossary's own advice that "most users never need this tool" suggests[1].

Exercise 2: Predict the orderCreation process · easy

Without running it, write down the order in which the five messages appear. Then check your answer against the creation steps in Section 4.

class Meta(type):
    def __new__(mcls, name, bases, ns):
        print("A: Meta.__new__", name)
        return super().__new__(mcls, name, bases, ns)

class Tag:
    def __set_name__(self, owner, name):
        print("B: __set_name__", name)

def deco(cls):
    print("C: decorator")
    return cls

@deco
class Thing(metaclass=Meta):
    print("D: body")
    label = Tag()
    def __init_subclass__(cls):
        print("E: __init_subclass__", cls.__name__)

class Child(Thing):
    pass
Show solution

The body runs first (D), then Meta.__new__ (A) whose super().__new__ calls __set_name__ (B), then the decorator (C). For Thing, no __init_subclass__ message appears, because the hook is called on the parent of the new class, and Thing's parent is object[2]. Child then triggers A again and finally E. Child is not decorated, because decorators are not inherited[12].

Exercise 6: Resolve a metaclass conflictConflicts · medium

class TrackedMeta(type):

    def __init__(cls, name, bases, ns, **kw):

        TrackedMeta.count += 1

class Tracked(metaclass=TrackedMeta):

Exercise 7: Counting instancesMetaclass __call__ · medium

Write a metaclass Counted so that every class using it keeps its own count of instances created, and len(SomeClass) returns that count. Subclasses must count separately from their parents.

Show solution

__call__ runs on each instantiation, and __len__ on the metaclass is what len(cls) looks up[2]. Storing the count in a dictionary keyed by class keeps subclasses separate; a plain cls.count += 1 would read the parent's inherited attribute the first time.

Exercise 8: Remove a metaclassRefactoring · hard

The metaclass below makes every Command subclass register itself under its lower-case name and requires a help string. Rewrite it without any metaclass so that the behaviour stays the same and type(Command) is plain type. Then show that your version mixes with an ABC base without any conflict.

class CommandMeta(type):
    commands = {}
    def __new__(mcls, name, bases, ns):
        cls = super().__new__(mcls, name, bases, ns)
        if bases:
            if not isinstance(ns.get("help"), str):
                raise TypeError(f"{name} needs a help string")
            mcls.commands[name.lower()] = cls
        return cls

class Command(metaclass=CommandMeta):
    pass
Show solution

__init_subclass__ runs for subclasses only, so the if bases test disappears. Checking "help" in vars(cls) keeps the original rule that each subclass must define its own help text rather than inherit it.

type(Deploy) is ABCMeta because of the ABC base, and there is no conflict because Command no longer brings a metaclass of its own.
