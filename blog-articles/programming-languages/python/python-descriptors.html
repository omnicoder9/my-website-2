1Overview

When you write obj.name, Python usually just looks name up in a dictionary: first the instance's __dict__, then the class's, then the base classes'[1]. A descriptor is an object that changes that. Formally, it is any object that defines __get__(), __set__() or __delete__(); when such an object is a class attribute, looking it up, assigning to it or deleting it calls the corresponding method instead of touching a dictionary[2]. In the words of the Python documentation, descriptors "let objects customize attribute lookup, storage, and deletion"[3].

Descriptors are not an exotic add-on. The glossary calls understanding them "a key to a deep understanding of Python", because they are the basis for functions and methods, properties, class methods, static methods and super()[2]. The mechanism arrived in Python 2.2 with PEP 252, which introduced "attribute descriptors (descriptors for short)" and already split them into data and non-data descriptors depending on whether they define __set__[4]. Python 3.6 added the fourth hook, __set_name__, through PEP 487[5].

This article builds descriptors up from a three-line example to the pure-Python equivalents of property, classmethod, staticmethod and slot members, then collects the mistakes people most often make with them. The Python Descriptor Guide is the primary source throughout[3].

2The descriptor protocol

The protocol is four optional methods, defined on the descriptor's class[1,3]:

MethodSignatureTriggered by
get__get__(self, instance, owner=None)obj.attr and Owner.attr
set__set__(self, instance, value)obj.attr = value
delete__delete__(self, instance)del obj.attr
name__set_name__(self, owner, name)creation of the owner class

Two words recur. The owner is the class in whose body the descriptor sits; instance is the object the attribute was accessed through, or None when it was accessed through the owner class itself[1]. __get__ should return the computed value or raise AttributeError[1]. These methods only take effect when the descriptor is in the class dictionary of the owner or of one of its parents; the object class itself implements none of them[1].

3Data and non-data descriptors

The single most important distinction: a descriptor that defines __set__ or __delete__ is a data descriptor; one that defines only __get__ is a non-data descriptor[1,3]. The difference decides who wins when the instance dictionary holds an entry with the same name[3]:

  • a data descriptor takes precedence over the instance dictionary;
  • the instance dictionary takes precedence over a non-data descriptor.

The instance dictionary really does contain both entries, but only one of them is ever seen through normal dotted access. The data model documentation states the rule in one line: data descriptors "always override a redefinition in an instance dictionary. In contrast, non-data descriptors can be overridden by instances"[1].

This also gives the recipe for a read-only attribute: define both __get__ and __set__, and make __set__ raise AttributeError[3]. A descriptor with only __get__ is not read-only, because an assignment simply creates a shadowing instance attribute:

4Attribute lookup order

For an instance lookup a.x, the default object.__getattribute__() "scans through a chain of namespaces giving data descriptors the highest priority, followed by instance variables, then non-data descriptors, then class variables, and lastly __getattr__() if it is provided"[3]. A descriptor found this way is called as type(a).__dict__['x'].__get__(a, type(a))[1].

PrioritySourceExample
1Data descriptor on the type (MRO)property, slot members
2Instance __dict__self.x = 1
3Non-data descriptor on the typefunctions, classmethod
4Plain class variablex = 5 in the class body
5__getattr__, if definedfallback hook

Two details are easy to miss. First, __getattr__ is not part of __getattribute__ at all: the dot operator and getattr() call it only after __getattribute__ raises AttributeError[3]. That includes an AttributeError raised from inside a property's __get__[1], which can hide bugs:

The real bug (a dictionary has no .path attribute) raised AttributeError inside the getter, so Python treated path as missing and quietly returned whatever __getattr__('path') produced. Second, lookups on a class and through super() follow different rules[1,3]:

  • Class binding: A.x becomes A.__dict__['x'].__get__(None, A), handled by type.__getattribute__(), which searches the MRO instead of an instance dictionary.
  • Super binding: super(A, a).x searches a.__class__.__mro__ for the base B following A and returns B.__dict__['x'].__get__(a, A); if x is not a descriptor it is returned unchanged.
  • Direct call: user code can call desc.__get__(a) itself, which is rare.

In the super binding the search started after B in the MRO, found the descriptor in A's dictionary and still called its __get__ with the instance[3].

5Naming: __set_name__

A descriptor is created before the assignment that names it, so originally it had no way to know whether it was called x or price. Authors had to repeat the name (price = Field("price")) or use a metaclass. PEP 487 fixed that in Python 3.6 by adding __set_name__, "an initializer for class attributes, especially if they are descriptors"[5].

When a class is created, type.__new__() scans the class variables and calls __set_name__(owner, name) on every one that has the hook[1]. Because this happens only inside the type constructor, a descriptor attached to a class later is not notified; you must call the hook yourself[1,3].

The hook is called on any class attribute that defines it, whether or not that object is also a descriptor[3].

6Per-instance storage

There is exactly one descriptor object per class attribute, shared by every instance. So a descriptor that needs to remember a value per instance must store it somewhere keyed by the instance. The obvious-but-wrong place is the descriptor itself:

There are three reliable alternatives.

1. A private attribute on the instance

The guide's validators use __set_name__ to compute a private name such as _age, then store the value with setattr(instance, "_age", value)[3]. It is simple and works with vars(), pickling and debugging, at the cost of a second visible attribute.

2. The instance dictionary under the same name

Because a data descriptor beats the instance dictionary during lookup (section 3), it can safely keep its value in instance.__dict__ under its own public name. Normal attribute access still goes through the descriptor; only the descriptor reads the dictionary directly.

3. A weak-key dictionary on the descriptor

When instances have no __dict__ (for example because the class uses __slots__), the descriptor can keep its own mapping. A weakref.WeakKeyDictionary discards an entry once there is no longer a strong reference to the key, and the documentation recommends it for associating data "with an object owned by other parts of an application without adding attributes to those objects"[6]. The instance must be hashable and weak-referenceable; with __slots__ that means listing '__weakref__'[1,6].

Descriptors as dataclass fields

@dataclass cooperates with descriptors. When a field's default is a descriptor object, the value passed to the generated __init__() goes to the descriptor's __set__() rather than replacing the descriptor, and to find the field's default the decorator calls the descriptor's class-access form, __get__(None, cls): a returned value becomes the default, while AttributeError means there is none[7].

8Descriptors inside Python

The data model documentation says outright that "Python methods (including those decorated with @staticmethod and @classmethod) are implemented as non-data descriptors", and that the @property decorator "is implemented as a data descriptor"[1]. Seeing pure-Python versions of them is the best way to understand what they do[3].

Functions and bound methods

Functions have a __get__() method, which makes them non-data descriptors that "return bound methods during dotted lookup from an instance"[3]. That is the whole secret of self: d.f is D.__dict__['f'].__get__(d, D), which returns a method object whose __self__ is d and whose __func__ is the plain function[3]. The binding only happens for functions stored on the class; a function stored on an instance is not turned into a bound method[1].

staticmethod and classmethod

The two decorators differ only in what their __get__ returns. A static method returns the underlying function unchanged, so no argument is inserted; a class method binds the function to the class, using type(obj) when only an instance is given[3].

property

Calling property() is "a succinct way of building a data descriptor that triggers a function call upon access to an attribute"[3]. Its signature is property(fget=None, fset=None, fdel=None, doc=None), and its getter, setter and deleter methods each return a copy of the property with one accessor replaced[8]. functools.cached_property

cached_property is the opposite design: it is a non-data descriptor. On first lookup it computes the value and writes it into the instance dictionary under the same name; from then on that dictionary entry shadows the descriptor, so later reads never call it. Unlike property it allows writes, and deleting the attribute clears the cache[9].

Since it needs a mutable instance __dict__, it does not work on classes whose __slots__ omit '__dict__'[9]. Before Python 3.12 it also took an undocumented per-property lock; that lock was removed in 3.12, so the getter may run more than once under concurrent access[9].

__slots__ and member descriptors

__slots__ replaces the per-instance dictionary with a fixed-length array of slot values[3]. The documentation is explicit about the mechanism: slots "are implemented at the class level by creating descriptors for each variable name"[1]. Those descriptors are data descriptors of type member_descriptor; the guide's pure-Python Member class stores values at a fixed offset and raises AttributeError for a slot that has not been assigned[3].

9Pitfalls

Descriptors only work on the class

The protocol applies only when the descriptor is in the owner class's dictionary or a parent's[1]. Put one on an instance and it is just an ordinary object:

Assigning on the class replaces the descriptor

__set__ handles assignment through an instance only; __set__(self, instance, value) has no class form[1]. Assigning to the class attribute rebinds the name in the class dictionary and silently destroys the descriptor for every instance.

Infinite recursion through the public name

Inside __get__ or __set__, using getattr(obj, public_name) or setattr(obj, public_name, value) calls the same descriptor again. Store under a private name or go straight to obj.__dict__ (section 6).

Forgetting the instance is None case

Class access passes None as instance[1]. A __get__ that assumes an instance will crash on Owner.attr, and with it help(), documentation generators and @dataclass, which probe the class form[7].

Other traps, briefly

  • Shared state: values stored on self inside the descriptor are shared by all instances (section 6).
  • Late attachment: __set_name__ is called only during class creation; attach a descriptor later and you must call it yourself[1].
  • Non-data shadowing: a descriptor with only __get__ can be overridden by assigning to the instance, so it is not read-only[3].
  • Swallowed AttributeError: an AttributeError escaping a getter triggers __getattr__ if the class has one (section 4)[1].
  • classmethod + property: no longer chains on 3.13+[8].
  • Slots: no class-level defaults for slot names, and no cached_property without '__dict__' in the slots[1,9].
  • Weak-key storage: the instance must be hashable; a class that defines __eq__ without __hash__ is not[1].

Exercise 6: A tiny record classHard

Write a Field(default) descriptor and a Record base class so that subclasses get a keyword-only constructor and a __repr__ listing their fields in definition order. Use __set_name__ to register each field on its owner class (no metaclass). Unknown keyword arguments should raise TypeError.

Show solution

Each Field appends its name to an _fields list on the owner in __set_name__, which runs in class-body order during class creation[1,5]. The list is copied from the parent first so subclasses do not share it.
