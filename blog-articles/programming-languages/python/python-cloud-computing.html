1What cloud computing is

The most widely cited definition comes from the US National Institute of Standards and Technology (NIST). It describes cloud computing as “a model for enabling ubiquitous, convenient, on-demand network access to a shared pool of configurable computing resources (e.g., networks, servers, storage, applications, and services) that can be rapidly provisioned and released with minimal management effort or service provider interaction”[1]. The same publication says the model is made up of five essential characteristics, three service models and four deployment models[1].

Part of the NIST modelMembers
Essential characteristicsOn-demand self-service; broad network access; resource pooling; rapid elasticity; measured service
Service modelsSoftware as a Service (SaaS); Platform as a Service (PaaS); Infrastructure as a Service (IaaS)
Deployment modelsPrivate cloud; community cloud; public cloud; hybrid cloud

In IaaS the consumer provisions processing, storage and networks and can run arbitrary software, including operating systems. In PaaS the consumer deploys applications onto the provider's platform using the languages, libraries and tools the provider supports. In SaaS the consumer uses the provider's applications[1].

“On-demand self-service” is what makes Python useful here. Every resource a cloud offers can be created, inspected and deleted through a web API, and each provider publishes Python libraries that wrap those APIs. A Python program can therefore do anything a person can do in the provider's web console: store a file, start a virtual machine, publish a message or deploy a function. The rest of this article shows how, for three providers:

  • Amazon Web Services through Boto3, the AWS SDK for Python (section 3);
  • Microsoft Azure through the Azure SDK for Python, a family of azure-* packages (section 4);
  • Google Cloud through the Google Cloud CLI and the Cloud Client Libraries for Python, the google-cloud-* packages (section 5);
  • serverless functions on all three: AWS Lambda, Azure Functions and Cloud Run functions (section 6).

Object storage is used as the running example for the three SDKs, because every provider has it, it is cheap, and it can be emulated on a laptop. The patterns it shows (credentials, clients, pagination, errors) carry over to every other service in the same SDK.

2Setting up and testing offline

Install each SDK into a virtual environment, so its many dependencies do not mix with other projects. The Python tutorial describes a virtual environment as a self-contained directory tree that holds a Python installation for a particular version of Python plus a number of additional packages[2].

Testing without a cloud account

Cloud code is awkward to test, because each run can cost money and changes real resources. Each provider's ecosystem has a way around this, and this article uses all three:

  • Moto mocks AWS inside the Python process. Wrapping a function in the @mock_aws decorator, or a block in with mock_aws():, makes every AWS call inside it go to an in-memory fake[3]. Moto's documentation recommends setting dummy credentials so tests can never touch a real account, and warns that the mock must be active before any Boto3 client is created[3].
  • Azurite is Microsoft's emulator for Azure Blob, Queue and Table storage. It runs on Node.js and is intended for development and testing only[4]. The connection string UseDevelopmentStorage=true is a shortcut that points the SDK at it[5].
  • For Cloud Storage, the examples use gcp-storage-emulator, an open-source community project (not a Google product) that answers Cloud Storage's JSON API on a local port. The google-cloud-storage library sends its requests there when the STORAGE_EMULATOR_HOST environment variable is set.

Every example below whose box shows an Output panel is a real file that was run, and the panel holds its unedited output. The examples ran with Azurite and the Cloud Storage emulator listening locally and with this environment, and with no real cloud credentials present:

3AWS with Boto3

Boto3 is the AWS SDK for Python. Its central object is the client, which the Boto3 guide describes as “a low-level interface to AWS whose methods map close to 1:1 with service APIs”[6]. Clients are generated from JSON service definitions, so every operation of every service is available, with its name converted to snake_case: the S3 operation PutObject becomes put_object()[6]. Parameters must be passed as keyword arguments[6].

Credentials and the default session

You should never put access keys in source code. The Boto3 credentials guide says so directly: “We do not recommend hard coding credentials in your source code”[7]. Instead, Boto3 looks for credentials in a fixed order and stops at the first place that has them. Among the places it checks, in order, are: parameters passed to boto3.client() or to a Session; environment variables; assume-role and web-identity providers; IAM Identity Center; the shared credentials file ~/.aws/credentials; the config file ~/.aws/config; the container credential provider; and finally the instance metadata service on an EC2 instance with an IAM role[7]. The same code can therefore run on a laptop (using a profile) and on AWS (using a role) without change.

A quick way to see which identity a program is running as is to call the Security Token Service. Under Moto, the account is a fixed fake one.

Working with Amazon S3

Amazon S3 stores objects (bytes plus metadata) under keys inside buckets. The example creates a bucket, writes two objects, reads one back, lists the bucket and cleans up. Outside us-east-1, create_bucket needs a LocationConstraint naming the region.

Two details are worth noticing. The body of a get_object response is a stream, read with .read(), not a bytes value. And the response of list_objects_v2 is a plain dictionary that mirrors the service's JSON, which is typical of the client interface.

Pagination

List operations return results in pages. The Boto3 guide's own example: S3's object listing “returns up to 1000 objects at a time, and you must send subsequent requests with the appropriate Marker in order to retrieve the next page”[8]. A paginator, obtained with client.get_paginator(operation_name), hides that loop; its paginate() method returns an iterable of pages[8]. Its search() method applies a JMESPath expression to every page and yields the matching items one by one[8].

A program that calls list_objects_v2 once and treats the result as complete has a bug that only shows up once a bucket passes 1,000 objects, which is often long after the code was tested. Use a paginator for every list call unless you know the result is small.

Handling errors

Boto3 reports every error returned by an AWS service as botocore.exceptions.ClientError. The error code is in error.response["Error"]["Code"], and request metadata such as the HTTP status is in error.response["ResponseMetadata"][9]. Some error codes are also exposed as exception classes on the client, such as s3.exceptions.NoSuchKey, but only some are, so the guide calls catching ClientError and checking the code “the best way to catch all service-side exceptions”[9]. The guide also warns that error messages may change and should not be relied on in code[9].

Presigned URLs

A presigned URL lets someone who has no AWS credentials download (or upload) one object for a limited time. The URL is signed with the credentials of the user who generated it, and it stays valid for the number of seconds given in ExpiresIn[10]. The guide recommends creating the client with Signature Version 4 and the bucket's region[10].

Amazon DynamoDB, waiters and retries

The same client pattern works for every service. DynamoDB is a key-value and document database; its low-level client spells out each attribute's type ("S" for string, "N" for number, sent as a string). Creating a table is asynchronous, so the example uses a waiter, which polls until a resource reaches the wanted state[6].

Network calls fail now and then, so Boto3 retries some failed requests itself. The default mode is legacy, which makes up to 5 attempts in total; standard mode makes 3 attempts by default and retries a wider set of errors consistently with the other AWS SDKs; adaptive adds client-side rate limiting and is marked experimental[11]. The mode and the number of attempts are set per client with a Config object[11].

Clients, resources and threads

Boto3 also has an older, object-oriented resource interface (boto3.resource("s3").Bucket("name")). The Boto3 team has said it “does not intend to add new features to the resources interface”, and that newer service features are reached through clients[12]. For new code, prefer clients.

Threads matter too. Clients are generally thread-safe, so one client can be shared by a pool of worker threads, but they cannot be shared across processes[6]. Resource objects and sessions are not thread-safe; the guide recommends creating a new one in each thread[6,12].

4The Azure SDK for Python

The Azure SDK for Python is not one package. Microsoft describes it as more than 180 separate libraries, each tied to one Azure service, and states that the libraries support Python 3.9 or later[13]. They come in two kinds[13]:

  • Management libraries (the “management plane”), whose names all begin with azure-mgmt-. They create, configure and delete Azure resources, the same tasks you can do in the Azure portal or the Azure CLI.
  • Client libraries (the “data plane”), such as azure-storage-blob, which let application code use a resource that already exists: upload a blob, send a queue message, read a secret.

Authentication with Microsoft Entra ID

Microsoft recommends token-based authentication through Microsoft Entra ID over connection strings or account keys, and says connection strings should be limited to cases where tokens are not an option, early proofs of concept, or prototypes that do not touch production or sensitive data[14]. Part of the reason is that a connection string grants full rights to the resource, while tokens support least privilege[14]. When an app is hosted on Azure, it should use a managed identity, so there is no secret to store or rotate at all[14].

The azure-identity package provides DefaultAzureCredential, a chain of credential types tried in order. Among them are environment variables for a service principal, workload identity, managed identity, the account signed in to Visual Studio Code, the Azure CLI (az login), Azure PowerShell and the Azure Developer CLI[15]. Like Boto3's chain, this lets one program run unchanged on a laptop and in Azure. Microsoft's guidance is to replace it with a specific credential such as ManagedIdentityCredential once the app is deployed, because a long chain is harder to debug and can behave differently depending on the machine's environment variables[15].

Signing in is not the same as being allowed in. For local development, Microsoft's quickstart has you assign your Entra user account the Storage Blob Data Contributor role on the storage account, which is needed to read and write blob data, and notes that a new role assignment can take a few minutes to take effect[16].

Working with Blob Storage

The Blob Storage library has three client classes. BlobServiceClient works with the storage account and its containers, ContainerClient with one container and its blobs, and BlobClient with a single blob[16]. list_blobs() returns a generator that “will lazily follow the continuation tokens returned by the service”[17], so, unlike a single Boto3 list call, the loop above sees every blob however many there are. download_blob() returns a downloader object; readall() collects its content as bytes.

Errors

Errors raised by the Azure libraries derive from azure.core.exceptions.AzureError. The most useful subclasses are ResourceNotFoundError (typically HTTP 404), ResourceExistsError (creating something that already exists), ClientAuthenticationError, and HttpResponseError for any other 4xx or 5xx response, which carries the status code and message[18]. Microsoft's advice is to catch the specific exceptions before the general ones[18].

Names are a common source of 400 errors. A container name must be 3 to 63 characters long, use only lowercase letters, digits and hyphens, start and end with a letter or digit, and must not contain two hyphens in a row[19]. A request that breaks these rules fails with status 400 (Bad Request)[19].

The first request fails because upload_blob's overwrite parameter defaults to False, in which case uploading over an existing blob raises ResourceExistsError[17]. The last request fails with the error code OutOfRangeInput, which the library exposes as the enumeration member StorageErrorCode.OUT_OF_RANGE_INPUT, because “Q3” is too short. Checking names in your own code before calling the service gives clearer messages; exercise 4 asks you to write such a check.

Management libraries and long-running operations

Management operations that take time return a poller. In the libraries built on azure-core, these methods start with begin_, and calling .result() on the poller blocks until the operation finishes[20]. Many libraries also offer asynchronous versions in an .aio subpackage, such as azure.storage.blob.aio[20]. Management libraries also change between major versions: in azure-mgmt-resource 26.0, ResourceManagementClient moved from azure.mgmt.resource to azure.mgmt.resource.resources[21], so older tutorials' imports fail with the current release. Pin the versions your code was written against.

5Google Cloud from Python

“Google Cloud SDK” is the older name for what Google now documents as the Google Cloud CLI, “a set of tools to create and manage Google Cloud resources”, with gcloud as its main command[22]. Python programs use the separate Cloud Client Libraries, one google-cloud-* package per service, such as google-cloud-storage[23]. The two meet in authentication: the CLI is the usual way to give the libraries credentials on a developer machine.

Application Default Credentials

The client libraries find credentials through Application Default Credentials (ADC). Once ADC is set up, a client created without any credential arguments finds and uses them automatically[24]. ADC looks in three places, in order[25]:

  1. the file named by the GOOGLE_APPLICATION_CREDENTIALS environment variable;
  2. the local credential file written by gcloud auth application-default login (under $HOME/.config/gcloud/ on Linux and macOS);
  3. the service account attached to the resource, which it gets from the metadata server when the code runs on Google Cloud.

The command gcloud auth application-default login is the documented way to give ADC your user credentials for local development[26]. On Google Cloud itself, nothing is needed: the attached service account is used[25].

Working with Cloud Storage

The google-cloud-storage package is installed with pip install google-cloud-storage and is built around a Client, from which you reach Bucket and Blob objects[23]. Against a real project, storage.Client() takes its credentials and project from ADC. For the emulator the example passes anonymous credentials and a dummy project name instead, and the library sends its requests to STORAGE_EMULATOR_HOST.

As with Azure, Client.list_blobs() returns an iterator, and the reference documentation points to that iterator's pages property rather than passing page tokens by hand[27]. A plain for loop over it sees every matching object.

Errors

create_bucket() raises Conflict if the bucket already exists[27]. More generally, the Google client libraries raise exceptions from google.api_core.exceptions. They all derive from GoogleAPICallError, and each HTTP status has its own class: NotFound for 404, Conflict for 409, Forbidden for 403 and so on[28].

Publishing to Pub/Sub

Pub/Sub is Google Cloud's messaging service. In its Python client, PublisherClient.topic_path() builds a topic's full name, the message data must be a bytestring, and publish() returns a future whose result() is the server-assigned message ID[29]. Because publish() returns a future instead of waiting, a program that publishes many messages can send them all first and then wait on the futures together, as the example does.

6Serverless computing

In serverless computing you hand the provider a function, and the provider runs it when an event arrives: an HTTP request, a new file in a bucket, a message on a queue, a timer. You do not choose, patch or keep running any servers, and billing follows use. AWS describes Lambda as “a serverless compute service” with pay-per-use billing and no upfront commitments[30]; Microsoft describes Azure Functions as a serverless compute service in which Azure handles provisioning, scaling and maintaining the servers, with event-driven triggers and bindings that connect functions to other services[31]; and Google's equivalent, renamed from Cloud Functions to Cloud Run functions in August 2024, runs functions on the Cloud Run platform[32].

All three services follow the same shape. You write an ordinary Python function with a signature the platform defines, and the platform calls it once per event. Because the function is ordinary Python, it can be imported and called in a unit test, with a stand-in for the event, and that is how every example in this section was tested.

AWS Lambda

A Lambda handler takes exactly two arguments, the event and a context object; a handler declared with one argument fails when Lambda calls it, and async handlers are not supported[33]. When the event is a JSON object, the runtime converts it to a Python dict[33]. The handler is named in the form file.function, so lambda_function.py with a function lambda_handler is lambda_function.lambda_handler[33]. For a synchronous invocation, the value the handler returns is serialised with json.dumps and sent back to the caller[33].

The context object reports on the invocation, with attributes such as aws_request_id, function_name and memory_limit_in_mb, and one method, get_remaining_time_in_millis(), which says how long the function has left before it times out[34].

AWS recommends initialising SDK clients and database connections outside the handler, because an execution environment is reused for later invocations and those objects survive between them[33,35]. It also recommends passing settings such as a bucket name through environment variables rather than hard-coding them[35]. This function follows both rules: it records an order as a JSON receipt in S3.

To test it, call the handler directly. Moto stands in for S3, and a tiny class stands in for the context. Note the order of the steps: the mock is started and the environment variable set before lambda_function is imported, because the module creates its client at import time and Moto must be active before any client is created[3].

Lambda supports Python as a managed runtime. As of this writing, the runtime list includes python3.12, python3.13 and python3.14 on Amazon Linux 2023, older python3.10 and python3.11 runtimes on Amazon Linux 2, and python3.15 in public preview[36]. Each Python runtime includes a version of Boto3, but AWS strongly recommends shipping the SDK in your deployment package if your code needs it[33].

Azure Functions

Azure Functions has two Python programming models. The recommended v2 model defines each function with decorators on a FunctionApp object in a file called function_app.py; the older v1 model used a main() function in __init__.py plus a separate function.json file per function[37]. An HTTP-triggered function receives an azure.functions.HttpRequest and returns an HttpResponse.

Microsoft's Python guide suggests pytest for tests and shows building mock inputs from the azure.functions classes, then reaching the plain function behind the decorator with .build().get_user_function()[37]. The same idea works with the standard library's unittest:

Where the function runs is chosen by its hosting plan. For new serverless apps Microsoft recommends the Flex Consumption plan and calls the original Consumption plan a legacy plan[38]. The two also differ in how long a function may run, as the table at the end of this section shows.

Cloud Run functions

Google's Python functions are written with the open-source Functions Framework[39]. The source lives in main.py, and requirements.txt must list functions-framework[40]. An HTTP function is registered with @functions_framework.http and receives a request object; an event-driven function is registered with @functions_framework.cloud_event and receives a CloudEvent, whose payload is in cloud_event.data[40]. The name a function is registered under is its entry point[40].

Locally, functions-framework --target word_count serves the function on port 8080[39]. In a test, the framework's create_app() builds the same web application in-process, and its test client sends requests without opening a port. The test sends the CloudEvent's attributes as ce- HTTP headers and its data as the JSON body.

Limits that shape serverless code

Serverless platforms cap how long and how large a single invocation may be. The figures below are the documented values on 28 October 2026; check them again before you depend on one.

Two habits follow from the way these platforms work. First, write idempotent handlers. AWS notes that event source mappings process each event at least once, so duplicates can occur, and it strongly recommends idempotent function code[35]; exercise 3 shows one way to achieve this. Second, do not keep per-request data in module-level variables: the environment is reused, and AWS warns against storing user data, events or other sensitive information there[33].

8Good practice and pitfalls

  • Keep secrets out of code. Let each SDK's credential chain find credentials, and on the cloud use roles, managed identities or attached service accounts[7,14,25]. A key committed to a repository has to be treated as leaked.
  • Grant least privilege. Give each program, and each function, only the permissions it uses. AWS recommends the most restrictive IAM policies that let a function do its job[35]; Microsoft points out that tokens support least privilege where a connection string grants full rights[14].
  • Always paginate. Any list call can return a partial result. Use paginators in Boto3 and iterate fully in the Azure and Google libraries[8,17,27].
  • Catch specific errors. Branch on error codes or specific exception classes, catch the specific ones first, and re-raise what you cannot handle[9,18].
  • Create clients once. Clients hold connection pools and configuration. Reuse them across calls, share Boto3 clients between threads but not processes[6], and in Lambda create them outside the handler[35].
  • Test without the cloud first. Unit-test logic against Moto, Azurite or an emulator, and keep a few integration tests that run against a real, disposable account.
  • Clean up. Resources keep costing money until deleted. Scripts that create resources should delete them, and long-lived ones should be tagged with an owner, as in the resource group example in section 4.

9Exercises

Each exercise can be solved and tested without a cloud account, using the same stand-ins as the article: Moto for AWS, Azurite for Azure and the Cloud Storage emulator for Google Cloud. Every solution below was run, and its output is shown.

Exercise 1: Storage reportBoto3 · pagination

Write prefix_summary(s3, bucket), which returns a dictionary mapping each top-level “folder” (the part of the key before the first /) to a pair: the number of objects and their total size in bytes. It must be correct for buckets with more than 1,000 objects.

Show solution

The paginator follows the continuation tokens, so all 1,200 objects are counted[8]. The .get("Contents", []) matters: a page with no objects has no Contents key at all, and indexing it would raise KeyError on an empty bucket.

Exercise 2: Does the bucket exist?Boto3 · errors

Write bucket_status(s3, name) that returns "exists", "missing" or "forbidden". Use head_bucket, which has no response body, so the error code is the HTTP status as a string. Any other error should propagate.

Show solution

The function branches on the error code, as the Boto3 guide recommends, and re-raises everything it does not recognise instead of hiding it[9]. The “forbidden” branch cannot be shown under Moto, which grants every request; against a real account it is what you get for a bucket owned by someone else.

Exercise 3: Process each event onceDynamoDB · idempotency

Serverless triggers can deliver the same event twice[35]. Write record_once(db, table, event_id, payload) that stores the event and returns True the first time it sees an event_id, and returns False without changing anything when it sees that ID again. Make the check and the write a single atomic request.

Show solution

A separate “read, then write if absent” would leave a gap in which two copies of the same event could both see nothing and both write. The condition expression makes DynamoDB do the check and the write together, and a failed condition surfaces as a modeled exception on the client[9].

Exercise 4: Validate container namesAzure · naming rules

Write valid_container_name(name), which applies Azure's container naming rules from section 4, and create_container_checked(service, name), which raises ValueError with a clear message for an invalid name instead of sending a request that will fail.

Show solution

The rules come from Azure's naming reference[19]. The pattern [a-z0-9](?:-?[a-z0-9])+ encodes three of them at once: it must start with a letter or digit, every hyphen must be followed by a letter or digit (so it cannot end with a hyphen or contain two in a row), and only the allowed characters can appear. The length check covers the rest.

Exercise 5: Upload only when changedAzure · blob properties

Write upload_if_changed(container, name, data). If the blob already exists with exactly the same content, do nothing and return False. Otherwise upload data, replacing any older version, and return True. Compare MD5 hashes rather than downloading the blob.

Show solution

The function stores the MD5 it computed in the blob's content settings, so the next call can compare against it with one metadata request. A missing blob raises ResourceNotFoundError[18], and overwrite=True is needed because the default is to refuse to replace an existing blob[17].

Exercise 6: Copy a folder between bucketsGoogle Cloud Storage

Write copy_prefix(client, source, destination, prefix) that copies every object whose name starts with prefix from one bucket to another, keeping the names, and returns how many objects it copied. Objects outside the prefix must not be copied.

Show solution

list_blobs() filters on the server by prefix and pages through the results for you[27], so this works for any number of objects. copy_blob asks the service to copy the data, so the bytes do not travel through your program.

Exercise 7: Stop before the timeoutAWS Lambda · context

Write a Lambda handler that processes a list of items in event["items"], one at a time. Before each item, it must check how much time is left, and if less than one second remains it must stop and return the items it did not reach, so the caller can resubmit them. Test it with a fake context whose clock runs down.

Show solution

get_remaining_time_in_millis() is the context method that reports the time left before the function times out[34]. Returning the leftovers, instead of being killed half-way, lets the caller retry only the unfinished work, and combined with an idempotent process() (exercise 3) a retry is always safe.

Exercise 8: One interface, three cloudsChallenge · all SDKs

Define a small ObjectStore protocol with put(name, data), get(name) and names(prefix), and write three adapters for it: Amazon S3, Azure Blob Storage and Google Cloud Storage. Then write one function that checks any store behaves correctly, and run it against all three.

Show solution

typing.Protocol describes the interface structurally, so the adapters do not need to inherit from it. Each adapter hides one SDK's habits: Boto3's paginator and missing Contents key[8], Azure's refusal to overwrite unless asked[17], and the Google client's iterator[27]. Code written against ObjectStore can then move between clouds, or be tested against an in-memory fake, without change. The cost is that features only one provider has, such as S3 presigned URLs, fall outside the shared interface.
