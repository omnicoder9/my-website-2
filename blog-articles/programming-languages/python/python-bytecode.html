Python Bytecode: How CPython Compiles and Runs Your Code

Every Python program you run on CPython is first turned into bytecode, a compact instruction stream for a stack-based virtual machine. This article opens that machine up: the compiler pipeline, the evaluation loop, code objects, the dis module, .pyc files, the specializing adaptive interpreter, and how to use all of it to reason about performance without fooling yourself.

1What bytecode is

Python source code is not executed directly. In CPython, the reference implementation, it is first compiled into bytecode, "the internal representation of a Python program in the CPython interpreter"[1]. The glossary describes this intermediate language as running on a virtual machine, and it notes that bytecode is also cached in .pyc files so that running the same file a second time can skip recompilation[1].

Two warnings frame everything in this article. First, bytecode is not portable: "bytecodes are not expected to work between different Python virtual machines, nor to be stable between Python releases"[1]. Second, the dis documentation calls bytecode "an implementation detail of the CPython interpreter" and makes no guarantee that instructions will not be "added, removed, or changed between versions of Python"[2]. Studying bytecode is still worth it: it shows you exactly what work the interpreter does for each line, which explains error messages, tracebacks, scoping rules and many performance effects.

The quickest way to see bytecode is the dis module, which "supports the analysis of CPython bytecode by disassembling it"[2]:

Each row is one instruction. Read it top to bottom: RESUME is a no-op that performs internal tracing, debugging and optimization checks[2]; LOAD_CONST pushes a constant; LOAD_FAST pushes a local variable; BINARY_OP pops two values and pushes the result of the operator; and RETURN_VALUE returns the value on top of the stack[2]. The leftmost numbers are source line numbers. The rest of the article explains where these instructions come from, what runs them, and how to read much longer listings.

Scope of this article

Everything here describes CPython, and the listings come from CPython 3.13. Other implementations, such as PyPy, are free to execute Python differently. When an instruction name or behaviour changed in a recent release, the text says so, because the dis documentation records those changes release by release[2].

2From source to code object

CPython's compiler turns source text into bytecode in five stages[3]:

  1. Tokenize the source text into a stream of tokens.
  2. Parse the tokens into an abstract syntax tree (AST). Since Python 3.9 the parser is a PEG parser that works on tokens rather than characters[3].
  3. Transform the AST into an instruction sequence. Before this, a symbol table is built so the compiler knows the scope of every name; code generation then picks the right load or store instruction for each variable[3].
  4. Build a control flow graph (CFG) of basic blocks and apply peephole optimizations to it[3].
  5. Assemble the final bytecode: pseudo-instructions are converted to real ones, jump targets are converted from labels to relative offsets, the exception table and locations table are built, and everything is wrapped in a code object[3].

You can drive this pipeline yourself with the built-in compile(), which compiles source "into a code or AST object" that exec() or eval() can run[4]. The mode argument is 'exec' for a sequence of statements, 'eval' for a single expression, and 'single' for one interactive statement[4].

The 'eval' code ends in RETURN_VALUE because an expression produces a value, whereas the 'exec' version stores its result in the name total. Both are top-level code, so they use LOAD_NAME, which looks names up by name at run time; inside a function the same expression compiles to LOAD_FAST for locals, as the next sections show.

Constant folding

Some work is done at compile time. CPython 3.13's AST optimizer contains functions such as fold_binop, fold_unaryop and fold_tuple that replace constant expressions with their results, with size limits (for example, at most 4096 characters for a folded string and 256 items for a folded collection) so that compilation cannot produce huge constants[5]. It also turns a literal list or set on the right of in or not in, or used as the iterable of a for loop, into a tuple or frozenset constant[5].

The multiplication disappeared: the code object holds the constant 86400. The list literal became the tuple constant (200, 201, 204), and the set literal became a frozenset constant, so no container is built at run time.

3The evaluation loop

The part of CPython that executes bytecode is the interpreter loop in Python/ceval.c. "At a high level, the interpreter consists of a loop that iterates over the bytecode instructions, executing each of them via a switch statement that has a case implementing each opcode"; that switch is generated from instruction definitions in Python/bytecodes.c[6]. To run a code object, the interpreter builds a frame holding the dynamic state of the execution, "including the instruction pointer, the globals and builtins"[6].

Instruction format

Since Python 3.6 every instruction uses 2 bytes[2]. Internally the bytecode is an array of 16-bit code units, each holding an 8-bit opcode followed by an 8-bit argument (the oparg), and the opcode always comes first so the format does not depend on machine byte order[6]. An 8-bit argument can only count to 255. Bigger arguments are built with EXTENDED_ARG, which "prefixes any opcode which has an argument too big to fit into the default one byte"; at most three prefixes are allowed, giving arguments of up to four bytes[2]. A stack machine

"The CPython bytecode interpreter is a stack machine, meaning that its instructions operate by pushing data onto and popping it off the stack"[6]. The stack lives in the frame, and its maximum depth is computed by the compiler and stored in co_stacksize so the frame can pre-allocate it[6]. Because of this, the stack depth at any instruction is known statically, and the compiler never emits sequences that would let it grow without bound[6]. The dis documentation describes each instruction in terms of a list called STACK whose top is STACK[-1][2], which makes the machine easy to model in Python.

The following toy interpreter executes a small subset of real CPython 3.13 instructions, printing the stack after each one. It is a teaching model, not how CPython is implemented, but it follows the documented stack effects: LOAD_FAST_LOAD_FAST pushes two locals, and BINARY_OP pops the right operand, then the left, and pushes the result[2].

The largest stack the toy machine needed was two items, which matches co_stacksize. dis.stack_effect() reports the same information per opcode: it returns the net change in stack size an instruction causes[2].

BUILD_LIST 3 consumes three items and pushes one list, a net change of −2. CALL 2 consumes the callable, the self-or-NULL slot and two arguments, and pushes one result[2], a net −3.

Calls between Python functions

Up to Python 3.10, a call from one Python function to another went through the C function call machinery and back into the interpreter, using several C stack frames per Python call. Since 3.11, CALL special-cases Python functions: it pushes a new frame and "jumps" to the start of the callee's bytecode, and RETURN_VALUE pops the frame and jumps back[6]. Frames are also lighter: most are allocated contiguously in a per-thread stack, and a full frame object is only created when something asks for one, such as sys._getframe()[6]. The 3.11 release notes measured a 1.7x speedup for simple recursive functions from call inlining[7].

4Code objects

The compiler's output is a code object. "Code objects represent byte-compiled executable Python code, or bytecode"[8]. A code object differs from a function object in two ways: the function holds a reference to its globals and its default argument values, while the code object "contains no context"[8]. Code objects are immutable and contain no references to mutable objects[8]. One code object can therefore back many functions: every time a def statement runs, it builds a new function object around the same code object.

The attributes

The data model lists the read-only attributes of code objects[8]. The most useful are:

AttributeMeaning
co_name, co_qualnameFunction name and fully qualified name (co_qualname since 3.11)
co_argcount, co_posonlyargcount, co_kwonlyargcountCounts of positional, positional-only and keyword-only parameters
co_nlocals, co_varnamesNumber of local variables, and their names, parameters first
co_cellvars, co_freevarsLocals used by nested scopes; variables taken from an enclosing scope
co_consts, co_namesLiterals used by the bytecode; names (globals, attributes) used by the bytecode
co_codeThe bytecode instruction sequence as bytes
co_stacksizeRequired evaluation stack size
co_flagsBit flags for the interpreter
co_filename, co_firstlinenoSource file and first line

Instruction arguments are mostly indexes into these tuples: LOAD_CONST i pushes co_consts[i], LOAD_FAST i pushes local co_varnames[i], and LOAD_GLOBAL uses co_names[namei >> 1], with the low bit saying whether to push a NULL first[2].

The data model notes that if a code object represents a function, the first item of co_consts is the docstring, or None[8]. The LOAD_GLOBAL argument for round is 1: shifting right by one gives index 0 in co_names, and the low bit of 1 means "also push NULL" so the stack has the shape CALL expects[2].

Flags

co_flags is a bitmap whose bits are named in the inspect module, for example CO_OPTIMIZED (uses fast locals), CO_VARARGS, CO_VARKEYWORDS, CO_GENERATOR and CO_COROUTINE[9]. The documentation stresses that these flags are CPython-specific and may change, and it recommends inspect's public functions for everyday introspection[9].

Nested code objects and closures

A function defined inside another is compiled into its own code object, which is stored as a constant of the outer one. Variables shared between them appear in co_cellvars of the outer code (locals referenced from a nested scope) and in co_freevars of the inner code (variables referenced from an outer scope)[8]. LOAD_DEREF reads such a variable through its cell[2].

Line numbers and positions

Two methods map instructions back to source. co_lines() (since 3.10, from PEP 626) yields (start, end, lineno) ranges of bytecode offsets[8,10]. co_positions() (since 3.11, from PEP 657) yields a (start_line, end_line, start_column, end_column) tuple for every instruction[8,11]. These tables are what let 3.11+ tracebacks underline the exact sub-expression that failed[11]. PEP 657's authors estimated that storing the column data makes the standard library's .pyc files about 22% larger[11], which is why -X no_debug_ranges exists to drop it[12].

Each instruction carries the column range of the source it came from: the division's BINARY_OP covers (a + 1) / (b - 1), while the two inner BINARY_OP instructions cover only a + 1 and b - 1. That is exactly the information a traceback needs to point at the failing part of a line. The old co_lnotab attribute is deprecated since 3.12 and may be removed in 3.15; use co_lines() instead[8].

Modifying code objects

Because code objects are immutable, you change one by making a modified copy with replace() (since 3.8)[8]. types.CodeType and types.FunctionType are the types of code objects and of user-defined functions[13], and calling FunctionType with a code object and a globals dictionary builds a new function. Do not hand-edit co_code

replace() lets you swap co_code as well, but the interpreter trusts the compiler's invariants, such as a statically known stack depth[6]. Invalid bytecode is not checked and can crash the process. Rewriting names, filenames or constants is safe; rewriting instructions is a job for well-tested libraries pinned to one Python version.

5The dis module in depth

The dis module offers three layers: functions that print a listing (dis(), disassemble(), distb(), show_code()), an object API that yields Instruction records (get_instructions() and the Bytecode class), and tables that describe the instruction set (opname, opmap, hasarg, hasjump and others)[2].

Reading a listing

dis.dis() accepts a module, class, function, method, code object, source string or raw bytecode, and it recurses into nested code objects such as inner functions[2]. Its columns are: the source line number (on the first instruction of each line), a --> marker for the current instruction, a label for jump targets, the instruction offset, the opcode name, the argument, and in parentheses the argument's interpretation[2]. Since 3.13, jump targets and exception handlers are shown as logical labels (L1, L2, ...) rather than byte offsets, and offsets are only printed when you ask for them with show_offsets=True[2].

Read the first listing as: load n and 0, compare them with <, and if the result is false jump forward to L1. The bool(<) annotation reflects a 3.13 detail: a bit in COMPARE_OP's argument asks for the result to be converted to an exact bool, which POP_JUMP_IF_FALSE now requires[2]. Offsets count bytes and go up in steps of two, with gaps where hidden CACHE entries sit.

Options that reveal more

Three keyword arguments change what dis() shows[2]:

  • depth limits recursion into nested code objects; depth=0 shows only the outer one.
  • show_caches=True prints the CACHE entries that follow some instructions.
  • adaptive=True shows the specialized instructions the interpreter has substituted at run time (section 9).

The same options are available on the command line. python -m dis disassembles a file, or standard input if no file is given; 3.13 added -C (show caches) and -O (show offsets)[2].

Instructions as data

For tools, parse instructions rather than text. dis.get_instructions() returns an iterator of Instruction named tuples[2]. Each has the opcode and its name, the raw argument (arg), the resolved value (argval), a human-readable form (argrepr), the offset, and position information. Python 3.13 added several fields: baseopname (the generic name of a specialized instruction), line_number, jump_target, start_offset, cache_offset, end_offset and cache_info[2].

The Bytecode class wraps the same iterator and adds methods: dis() returns the listing as a string and info() returns the same text as code_info(), a formatted summary of the code object[2]. The documentation warns that code_info()'s contents are "highly implementation dependent"[2], so use it for reading rather than parsing.

The opcode tables

dis.opname maps opcode numbers to names and dis.opmap maps names to numbers[2]. Collections such as hasarg (opcodes that use their argument, since 3.12), hasjump (opcodes with a jump target, since 3.13), hasconst, hasname, haslocal and hasfree let you classify instructions without hard-coding numbers[2]. The documentation recommends hasarg over the old HAVE_ARGUMENT threshold, and it deprecates hasjrel and hasjabs in 3.13 because all jumps are now relative[2].

CPython 3.13 has about 120 base opcodes (the opcode_tables.py example above counts them), plus specialized variants and pseudo-instructions, but a handful dominate ordinary code. This table summarises the ones you will meet most, with their documented behaviour[2].

Conditionals and loops

A loop compiles to GET_ITER, then a FOR_ITER at the top of the body that jumps past the loop when the iterator is exhausted, and a JUMP_BACKWARD at the bottom[2]. Since 3.12 FOR_ITER leaves the iterator on the stack when it finishes, which is why END_FOR and POP_TOP follow the loop[2].

The structure maps directly onto the source: L1 is the top of the loop, the POP_JUMP_IF_TRUE/JUMP_BACKWARD pair implements the if (skip the increment when the test fails), and L3 is where the loop exits.

Calls

In 3.13 the stack for a call holds the callable, then either self or NULL, then the arguments; keyword arguments use CALL_KW with a tuple of their names on top[2]. A plain function call gets its NULL from LOAD_GLOBAL's low argument bit, while a method call gets the method and self from LOAD_ATTR[2]:

Functions, defaults and comprehensions

A def statement is executable: it loads the compiled code object as a constant, runs MAKE_FUNCTION, and, if needed, SET_FUNCTION_ATTRIBUTE with a flag for defaults (0x01), keyword-only defaults (0x02), annotations (0x04) or a closure (0x08)[2]. Since Python 3.12, list, dict and set comprehensions are inlined into the surrounding code instead of being compiled as hidden nested functions (PEP 709)[14], so their loop appears directly in the enclosing listing with LIST_APPEND adding each element[2].

Exceptions are handled by a table, not by instructions

CPython uses "zero-cost" exception handling: setting up a try block costs nothing when no exception is raised[15]. The compiler emits pseudo-instructions such as SETUP_FINALLY and POP_BLOCK during compilation, then removes them and records which instruction ranges are protected by which handler in an exception table stored in co_exceptiontable[15]. When an exception occurs, the interpreter looks up the current instruction in the table and jumps to the handler, or unwinds to the caller if there is none[15]. dis prints the table after the listing:

7.pyc files and __pycache__

Compiling is not free, so CPython caches the result of compiling an imported module in a .pyc file and reuses it on later imports[1]. The script you run directly (python app.py) is compiled each time; the modules it imports are cached.

Where cache files go: PEP 3147 and PEP 488

Before Python 3.2, foo.pyc sat next to foo.py. Linux distributions that installed several Python versions side by side found that each version kept overwriting the others' cache files, since "you cannot compile a single Python source file for more than one Python version at a time"[16]. PEP 3147 moved caches into a __pycache__ directory and put a magic tag naming the interpreter in each file name, such as foo.cpython-32.pyc[16]. The tag comes from sys.implementation.cache_tag; if that is None, module caching is disabled[17]. PEP 3147 also introduced the __cached__ module attribute, which points to the .pyc that was read or written[16].

PEP 488 (Python 3.5) eliminated the old .pyo files and added an optimization tag instead: foo.cpython-35.opt-1.pyc for -O and .opt-2.pyc for -OO[12,18]. importlib.util.cache_from_source() computes these paths for you[19].

Inside a .pyc file

Since Python 3.7 a .pyc file starts with a 16-byte header of four 32-bit words, defined by PEP 552[20]:

  1. the magic number, which identifies the bytecode version;
  2. a flags word: 0 for a traditional timestamp-based file, bit 0 set for a hash-based file, and bit 1 (check_source) saying whether the hash should be checked;
  3. and 4. either the source file's modification time and size, or, for hash-based files, a 64-bit SipHash of the source[20].

After the header comes the module's code object serialized with marshal, a module that "exists mainly to support reading and writing the 'pseudo-compiled' code for Python modules of .pyc files"[21]. The magic number is exposed as importlib.util.MAGIC_NUMBER[19]; in CPython 3.13 it is built from the value 3571 followed by \r\n[22]. Treat .pyc files as code

The marshal documentation warns that the module "is not intended to be secure against erroneous or maliciously constructed data. Never unmarshal data received from an untrusted or unauthenticated source"[21]. It also says the format of code objects "is not compatible between Python versions" and that de-serializing a code object in the wrong version "has undefined behavior"[21]. Python 3.13 added an allow_code parameter to the marshal functions so you can refuse code objects outright[21].

When a cache file is reused: invalidation

Before loading a .pyc, the import system checks that it is up to date[23]. By default it compares the source's last-modified time and size, stored in the header, with the source file's current metadata[23]. PEP 552 added hash-based files for reproducible builds: timestamps make the output depend on file metadata, so two builds of identical sources could produce different bytes[20]. Hash-based files come in two kinds[23]:

  • checked: Python hashes the source on import and regenerates the cache if the hash differs;
  • unchecked: Python assumes the file is valid if it exists, which suits systems such as package managers that keep caches up to date themselves.

The --check-hash-based-pycs option overrides this with default, always or never; it does not affect timestamp-based files[12].

Controlling where (and whether) caches are written

  • -B, or a non-empty PYTHONDONTWRITEBYTECODE, stops Python writing .pyc files on import[12]. Inside a program, sys.dont_write_bytecode controls the same thing[17].
  • -X pycache_prefix=PATH or PYTHONPYCACHEPREFIX (3.8+) writes caches into a parallel tree under PATH instead of into __pycache__ directories next to the source[12]. The value appears as sys.pycache_prefix[17].

With a prefix, the cache tree mirrors the absolute path of the source directory under cache/, here the temporary directory the example ran in. (The prefix applies to every module, so the standard library modules imported at start-up were cached there too; the listing shows only util.)

Running without source

PEP 3147 keeps one backward-compatible case: if the source file is missing, "Python will import a lone pyc file if it lives where the source file would have been"[16]. A .pyc inside __pycache__ is never imported without its source[16]. compileall -b, covered next, writes files to those legacy locations[24].

8py_compile and compileall

You rarely need to compile by hand, because import does it automatically. Two standard modules exist for the cases where you do: installers that must write caches into directories users cannot write to, and build systems that need reproducible output.

py_compile: one file at a time

py_compile.compile(file, cfile=None, dfile=None, doraise=False, optimize=-1, invalidation_mode=..., quiet=0) compiles one source file and returns the path of the cache file it wrote, which by default is the PEP 3147 location[25]. With doraise=True a syntax error raises PyCompileError instead of being printed[25]. invalidation_mode takes a member of PycInvalidationMode: TIMESTAMP, CHECKED_HASH or UNCHECKED_HASH[25]. The default is TIMESTAMP, unless the SOURCE_DATE_EPOCH environment variable is set, in which case it is CHECKED_HASH[25].

The flags match PEP 552's layout: 3 means hash-based with check_source set, and 1 means hash-based and unchecked[20]. The stored hash equals importlib.util.source_hash() of the source bytes, which is the function the import system uses for these headers[19]. For the timestamp mode, bytes 8–16 hold the modification time and size instead.

compileall: whole trees

compileall compiles every .py file in a directory tree, which is useful at installation time so that "users who don't have write permission to the library directories" still get cached bytecode[24]. From the command line it accepts, among others, -q (quiet), -f (force), -j N (parallel workers; 0 means one per CPU), -o LEVEL (optimization level, repeatable), --invalidation-mode, -x REGEX (exclude paths), -b (legacy locations) and --hardlink-dupes[24]. In code, compile_dir() returns a true value only if every file compiled[24].

9The specializing adaptive interpreter

Python is dynamic: a + b might add integers, floats, strings or objects with a custom __add__, so a generic BINARY_OP has to find out which on every execution. In practice a given line usually sees the same types again and again. PEP 659, by Mark Shannon, proposed an interpreter that "speculatively specializes on the types or values" it observes[26], and it shipped in Python 3.11 as part of the work that made 3.11 an average of 25% faster than 3.10 on the pyperformance suite, with 10–60% depending on workload[7].

Quickening, families and de-optimization

PEP 659 defines quickening as "the process of replacing slow instructions with faster variants"[26]. Specializable instructions are organised in families: one adaptive instruction plus the specialized forms that can replace it[6]. The adaptive instruction counts executions and, at regular intervals, tries to specialize itself; the specialized forms check that their assumptions still hold and de-optimize back to the generic version if they do not[6]. The 3.11 release notes put it this way: Python only specializes code that is "hot" (executed multiple times), and it "can also de-specialize when code is too dynamic or when the use changes"[7].

The bookkeeping lives in the inline caches: 16-bit entries placed directly after the instruction in the bytecode[26]. All members of a family have the same number of cache entries, the first entry is the counter, and the compiler reserves the entries and fills them with zeros[6]. When a code object is created, _PyCode_Quicken() initialises those caches[27]. This is why, since 3.11, the bytecode inside a code object is stored in a mutable array (co_code_adaptive) rather than an immutable bytes object[27].

Watching it happen

After the integer warm-up, BINARY_OP became BINARY_OP_ADD_INT. When floats arrived, the specialized instruction's guard failed, it de-optimized and re-specialized as BINARY_OP_ADD_FLOAT, and the same happened again for strings. RESUME also became RESUME_CHECK, a variant added in 3.13[22]. Note the last line: co_code still reports the generic instructions, so tools that read co_code never see specialized opcodes.

Global and attribute loads are among the most profitable cases. LOAD_GLOBAL specializes into LOAD_GLOBAL_MODULE for module globals and LOAD_GLOBAL_BUILTIN for built-ins[6], and the LOAD_ATTR family includes LOAD_ATTR_INSTANCE_VALUE for ordinary instance attributes, LOAD_ATTR_MODULE for module attributes and LOAD_ATTR_SLOT for __slots__ classes[26].

Instruction.baseopname (3.13) gives the family name of a specialized instruction[2], which makes this kind of filtering easy. After the switch to a __slots__ class, the attribute loads re-specialized as LOAD_ATTR_SLOT.

Seeing the caches

With show_caches=True, dis prints the CACHE entries, and in 3.13 it decodes their fields[2]. Each Instruction also exposes them through cache_info as (name, size, data) triples[2].

What specialization means for you

You do not need to write code differently to benefit: specialization is automatic and invisible except through dis. The practical lessons are that type-stable code (the same types flowing through the same lines) gives the specializer the most to work with, and that microbenchmarks must warm up before measuring, because the first executions run the generic instructions.

10Bytecode changes between versions

Bytecode is an implementation detail, and it changes in almost every release[2]. Each change that older interpreters could not understand bumps the magic number; the history is kept as comments in importlib/_bootstrap_external.py, and since 3.11 the magic numbers of Python 3.n start at 2900 + 50n[22]. A few entries from that history show how much moves between releases[22]:

The dis documentation's "changed in version" notes tell the same story: jump arguments became instruction offsets in 3.10 and relative to the end of their caches in 3.12; FOR_ITER stopped popping the iterator in 3.12; POP_JUMP_IF_FALSE requires an exact bool in 3.13; and 3.13 replaced offsets with labels in the listing[2]. Python 3.12's inlined comprehensions (PEP 709) changed not just bytecode but visible behaviour: comprehensions no longer get their own frame in tracebacks, and sys.settrace no longer sees a call for each one[14].

The import system enforces the magic number: a cache file written by another version is rejected rather than run. Faking a different magic number shows it:

With the source present, a normal import would simply recompile and overwrite the stale file. Without it, the old cache is unusable, which is one reason to ship source rather than .pyc files.

Writing tools that survive upgrades

  • Look instructions up by name with dis.opmap and classify them with hasarg, hasjump and friends instead of hard-coding opcode numbers[2].
  • Work with Instruction fields such as argval, jump_target and baseopname rather than decoding co_code yourself[2].
  • Use co_lines() and co_positions(), not the deprecated co_lnotab[8].
  • Do not store marshalled code objects across versions; their format "is not compatible between Python versions"[21].
  • When behaviour matters, test against each Python version you support. Expect the listings in this article to look different on 3.14.

11Bytecode and performance

Bytecode tells you what work a line asks the interpreter to do: how many lookups, calls and temporary objects. It does not tell you how long that work takes, because instructions differ hugely in cost and specialization changes them at run time. Use dis to form a hypothesis and timeit to test it. timeit "avoids a number of common traps for measuring execution times", turns off garbage collection during timing by default, and its documentation advises that the minimum of repeated runs is usually the only number worth looking at[28]. 12Pitfalls

1. Assuming bytecode is stable

Code that hard-codes opcode numbers, instruction sequences or dis output will break on the next release[1,2]. Section 10 lists the defensive habits.

2. Stale timestamp-based caches

Timestamp-based .pyc files are validated only by the source's modification time and size[23]. If a file is replaced by one of the same size with the same recorded time (some deployment and archive tools preserve or normalise timestamps), the stale bytecode keeps running:

The second run printed the old value even though the file now says 0.25. Recompiling with SOURCE_DATE_EPOCH set produced a checked hash-based file[25], which compares the actual source content and picked up the change. If you suspect a stale cache, delete __pycache__ or switch to hash-based files in your build.

3. Unchecked hash-based files that are never refreshed

An unchecked hash-based .pyc is assumed valid whenever it exists[23]. That is correct only if something outside Python, such as a package manager, regenerates it when the source changes[25]. Edit the source by hand in such an installation and your change is silently ignored until the cache is rebuilt, or until you run with --check-hash-based-pycs always[12].

4. Thinking .pyc files hide your source

Shipping only bytecode is sometimes suggested as a way to protect code. The code object keeps every name, constant, docstring, line number and the full instruction stream, and dis recovers the logic directly:

5. Loading untrusted bytecode

A .pyc is executable code, and marshal is explicitly not safe against malicious data[21]. Never load cache files or marshalled data from an untrusted source.

6. Relying on assert for validation

Under -O, or compile(..., optimize=1), assert statements are removed from the bytecode entirely[4,12], as section 2 showed. Use if and raise for checks that must always run.

7. Reading the wrong view of the code

co_code always shows generic instructions, while dis(..., adaptive=True) shows the specialized ones currently in use[2]. get_instructions(show_caches=True) is deprecated and has no effect in 3.13; read cache_info instead[2]. Make sure the view you inspect is the one your question is about.

8. Treating instruction counts as timings

Fewer instructions is not the same as faster. One CALL can run for seconds; ten LOAD_FAST instructions take nanoseconds. Always confirm a bytecode-based hypothesis with timeit or a profiler[28].

13Exercises

Each exercise has a tested solution. Try it first, then open the solution. The solutions use CPython 3.13 instruction names, so the exact lists may differ on other versions.

Exercise 1: Predict the instructionsBeginner

Without running it, write down the instruction names (after RESUME) for def f(a, b, c): return a * b - c. Then check your answer with dis.get_instructions, and also print co_stacksize.

Show solution

The two loads of a and b are fused into LOAD_FAST_LOAD_FAST, the product is left on the stack, c is pushed, and the subtraction consumes both. The stack never holds more than two items.
