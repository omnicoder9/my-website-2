Monkey Patching in Python

How to change functions, methods, classes and modules while a program is running, why Python lets you, how to do it safely in tests with unittest.mock and pytest, and when you should reach for something else instead.

1What monkey patching is

Monkey patching means changing the behaviour of existing code at run time by replacing or adding attributes on the objects that hold it: a module's functions, a class's methods, or a single instance's attributes. The source files are not edited. Instead, some code that runs later reaches into an object that was already created and rebinds one of its names.

The technique is old and widely used in Python. In January 2008 Guido van Rossum posted two recipes to the python-dev mailing list that he had written for "a large project": a decorator that attaches a function to an existing class as a method, and a metaclass that copies several methods onto an existing class at once. He noted that neither recipe works on built-in types such as list[1]. In the same thread Kevin Teague explained that the name grew out of "guerilla patch", and argued that the term should be kept for dynamic changes made to a class with the intent of changing or correcting the behaviour of upstream code[2]. The gevent project, one of the best-known users of the technique, describes its own gevent.monkey module as code that will "carefully patch, in place, portions of the standard library"[3].

Three situations account for most monkey patching you will meet:

  • Tests replace slow, non-deterministic or external dependencies (the network, the clock, environment variables) with controlled stand-ins. Both unittest.mock.patch and pytest's monkeypatch fixture exist for this, and both undo the change afterwards[4,5].
  • Libraries that change the runtime, such as gevent, swap blocking standard-library functions for cooperative versions[3].
  • Hotfixes correct a bug in a third-party package without waiting for a new release.

The rest of this article shows the mechanics first, then the tools that make it safe, and ends with the risks and the alternatives that often make patching unnecessary.

2Why Python allows it

Python does not need any special feature to support monkey patching. It falls out of three ordinary rules of the language.

Namespaces are dictionaries that can be written to. A module object has a namespace implemented by a dictionary; m.x is equivalent to m.__dict__["x"], and attribute assignment m.x = 1 is equivalent to m.__dict__["x"] = 1[6]. Classes work the same way: a class has a namespace implemented by a dictionary, class attribute references are translated to lookups in it, and class attribute assignments update that dictionary[6]. Instances also have a dictionary, and attribute assignment on an instance updates the instance's dictionary, never the class's[6].

Names are looked up when the code runs, not when it is compiled. A function that calls greetings.greet() fetches the attribute greet from the module each time that line executes, so whatever is bound to that name at that moment is what gets called.

Each module is imported once and then shared. The first place the import system looks is sys.modules, a cache of every module that has already been imported. If the name is there, that module object satisfies the import and the search stops[7]. Every import config in a program therefore receives the same object, so a change made to it in one place is seen everywhere.

The file headings inside one figure (# file: config.py and so on) mark separate files that were written to one folder; the last one was run. worker never changed, yet its behaviour did, because it reads config.DEBUG at call time from the one shared module object.

4Patching classes and methods

On the class: every instance changes

Methods live in the class's dictionary, and functions stored in a class become bound methods when they are looked up through an instance[9]. So assigning a new function to the class changes the method for every instance, including ones created before the patch.

On one instance: bind it yourself

Patching a single object is trickier. Functions are non-data descriptors: their __get__ method produces a bound method only when the function is found on the class during a dotted lookup from an instance[9]. A function stored in an instance's own dictionary takes precedence over the class's function, but it is not bound, so self is never passed[9]. types.MethodType creates the bound method manually[9,10].

Two limits are worth knowing. A class that defines __slots__ and no __dict__ denies its instances a per-instance dictionary[6], so there is nowhere to store an instance-level patch. And a data descriptor such as a property always wins over the instance dictionary[9], so assigning to a read-only property on an instance fails. Properties, class methods and static methods should be patched on the class instead, which is also what the unittest.mock documentation advises[4].

Wrapping instead of replacing

Most real patches keep the original and call it, adding behaviour around it. functools.wraps copies the original's name and docstring onto the wrapper and adds a __wrapped__ attribute that refers to the wrapped function[11], which gives you a clean way back to the original.

5Patch where it is looked up

This is the rule that trips up almost everyone. Patching changes the object that one name refers to, and several names can refer to the same object. The unittest.mock documentation puts it this way: "you patch where an object is looked up, which is not necessarily the same place as where it is defined"[4].

The reason lies in how the two forms of import bind names. import rates binds the name rates to the module, so rates.fetch_rate is looked up in that module on every call. from rates import fetch_rate stores a reference to the function itself in the importing module's namespace at import time[12]. Rebinding rates.fetch_rate later does not touch that second reference.

So the target of a patch depends on the code under test, not on where the function was written. If the module did from rates import fetch_rate, patch invoice.fetch_rate; if it did import rates, patch rates.fetch_rate[4]. pytest's documentation gives the same advice for its own fixture: if your module does from os import getcwd, patch mymodule.getcwd rather than os.getcwd[5]. The same reasoning explains why a patch applied too late in a program's life can miss code that already grabbed a reference, which is why gevent asks to be patched "as early as possible", ideally before any other imports in the main module[3].

6Restoring originals safely

A patch that is never undone leaks into every piece of code that runs afterwards. In tests that means one test silently changes the result of another. The minimum is a try/finally, so the original comes back even if the code in between raises.

A reusable version is a context manager, which contextlib.contextmanager makes short[13]. A careful one has to handle three cases that naive code gets wrong:

  • The attribute did not exist before, so restoring means deleting it, not setting it back to some value.
  • The attribute is inherited, so reading it with getattr and writing it back would leave a new copy in the subclass's own dictionary.
  • The attribute is a staticmethod or classmethod. getattr runs the descriptor and returns the underlying function, so writing that back turns a static method into an ordinary method. inspect.getattr_static retrieves the attribute without triggering the descriptor protocol[14], and reading the object's own __dict__ avoids both problems.

Another way to lose a patch, or to keep a stale one, is importlib.reload. Reloading re-executes the module's code and rebinds the names in its dictionary, but references held elsewhere, such as names created by from module import name, are not rebound[15].

7unittest.mock.patch

The standard library's unittest.mock module packages everything in the previous section into one tool. patch() takes a target string in the form 'package.module.ClassName', imports it, replaces the named object, and restores the original afterwards; it works as a function decorator, a class decorator or a context manager[4]. The target is imported when the decorated function runs, not when it is decorated[4]. Unless you pass new, the replacement is a MagicMock that records how it was called[4].

patch.object, patch.dict and autospec

patch.object(target, "name") patches an attribute on an object you already hold, which avoids spelling a dotted path[4]. patch.dict patches a dictionary such as os.environ and restores it afterwards to a copy of its earlier state[4]. With autospec=True the mock copies the signature of the object it replaces, so a call with the wrong arguments raises TypeError instead of silently passing[4]. And by default patch() refuses to replace an attribute that does not exist, raising AttributeError; create=True turns that check off, which the documentation warns "can be dangerous" because tests can then pass against APIs that don't exist[4].

Patching in setUp: start, stop and cleanups

Every patcher also has start() and stop() methods for patching in setUp. The documentation cautions that you must make sure stop is called, which is easy to get wrong because tearDown does not run if setUp raises, and recommends TestCase.addCleanup()[4]. Cleanup functions run in last-in, first-out order and still run when setUp fails[16]. Since Python 3.11, TestCase.enterContext() enters a context manager and registers its exit as a cleanup in one call[16].

8pytest's monkeypatch fixture

pytest's built-in monkeypatch fixture helps you "safely set/delete an attribute, dictionary item or environment variable, or to modify sys.path for importing"[5]. Its methods are setattr, delattr, setitem, delitem, setenv, delenv, syspath_prepend, chdir and context, and "all modifications will be undone after the requesting test function or fixture has finished"[5]. The raising parameter, true by default, makes setattr and the deletion methods raise AttributeError or KeyError if the target does not exist[5]. setattr also accepts a dotted import path as a single string[17].

The fixture grew out of Holger Krekel's 2009 argument that patching should live inside the test that needs it and be undone automatically, rather than being spread across setUp and tearDown[18].

pytest's documentation adds two cautions. Patching built-in functions such as open or compile is not recommended because it can break pytest's own internals, and patching standard-library functions that pytest itself uses can break pytest too; when that is unavoidable, monkeypatch.context() limits the patch to a block[5,17].

9Why built-in types can't be patched

Try to add a method to str and Python refuses. Types implemented in C, the "static types", are created with the Py_TPFLAGS_IMMUTABLETYPE flag, which means their attributes "cannot be set nor deleted"; PyType_Ready applies the flag to static types automatically, and the flag exists since Python 3.10[19]. The same applies to classes in C extension modules such as datetime. The unittest.mock documentation notes that "datetime.date is written in C, so you cannot just monkey-patch out the static datetime.date.today() method"[8], and Guido van Rossum's 2008 recipes did not work on built-in types either[1].

The way around it is the rule from section 5: do not patch the type, patch the name the code under test uses to reach it. The unittest.mock documentation patches date inside the module under test with a mock whose today() returns a fixed date while calls to the constructor still build real dates[8].

Built-in functions are a different case. They are attributes of the ordinary builtins module, for example builtins.open[20], and a module's attributes can be rebound, so mock.patch("builtins.input") works, but it changes input for the whole process. The narrower form patches the built-in "within a module": mock.patch("mymodule.input") puts a module-level name in front of the built-in for that one module, and patch() adds create=True for you in this case[4].

10Real uses

gevent: changing the runtime

gevent provides cooperative concurrency on top of greenlets. Its patch_all() function replaces blocking parts of the standard library, such as socket, time.sleep and threading, with cooperative versions. Every patch flag except sys is on by default[3]. Because it rebinds names in modules, it must run before other code takes its own references: the documentation says the main module should begin with the patch "ideally before any other imports", and warns that patching too late can lead to unreliable behaviour or errors[3]. is_module_patched() and get_original() let you check what was patched and reach the original objects[3].

Ten calls to what looks like the blocking time.sleep finished in the time of one, because each call now yields to the gevent event loop.

freezegun: patching every reference at once

FreezeGun lets tests "travel through time by mocking the datetime module": while it is active, datetime.datetime.now(), datetime.date.today(), time.time() and related functions return a frozen time[21]. Since it cannot patch the C types themselves, its source walks every module in sys.modules and rebinds any attribute that refers to a real datetime/date class or time function to the fake, recording each change so it can be undone[21]. That is the "patch where it is looked up" rule, applied to every module at once.

Test doubles

The most common use by far is the one in sections 7 and 8: replacing network calls, clocks, random number generators and environment variables during a test, with the change undone automatically[4,5].

Hotfixes to third-party code

When a dependency has a bug and the fix has not been released, a small patch module applied at start-up can correct it. Python even provides a start-up hook: after setting up sys.path, the site module tries to import a module named sitecustomize, "which can perform arbitrary site-specific customizations"[22]. A responsible hotfix checks that it is patching the version it was written for, so it switches itself off once the upstream fix arrives. This also addresses Kevin Teague's concern that a patch should fail loudly if the method it targets disappears in a later release[2].

11Risks and alternatives

What can go wrong

  • The change is global. Modules are shared through sys.modules[7], so a patch made for one caller affects every caller in the process, including other threads and other libraries.
  • It depends on import order. Code that took its own reference with from module import name before the patch keeps the original[12]; this is why gevent insists on patching first[3].
  • It couples you to private details. A patch assumes a function's name, signature and role. If upstream renames or refactors it, the patch may stop working with no error at all. autospec=True and raising=True exist to catch some of these cases in tests[4,5].
  • It surprises readers. Someone reading vendorlib.mean sees one implementation; another one runs. Tracebacks point into code that is not in the file they are looking at.
  • Patches collide. Two libraries patching the same function, or a patch restored out of order, leave the program in a state neither intended. The term "guerilla patch" came from exactly this kind of interference between dynamic modifications[2].
  • Some things cannot be patched at all: attributes of built-in and C-extension types[19], and instances whose class uses __slots__ without __dict__[6].

Alternatives to try first

Dependency injection. Instead of letting code reach for a global collaborator that a test then patches, pass the collaborator in. Martin Fowler describes this as giving an object its dependencies from outside rather than having it look them up or construct them itself[23]. Default arguments keep the call site as simple as before.

Use the hooks a library provides. Many APIs are designed to be replaced. sys.excepthook, for example, is documented as customisable "by assigning another three-argument function to sys.excepthook"[24]. Assigning a documented hook is not really monkey patching; it is the intended interface.

Extend without modifying. Subclass the class and override the method, or wrap the object in your own class. To add behaviour for a type you do not own, including built-in types that cannot be patched, functools.singledispatch lets you register a new implementation of a generic function for that type[11].

Fix it upstream. A hotfix is a debt. Report the bug, link the issue next to the patch, and remove the patch when the fixed version ships.
