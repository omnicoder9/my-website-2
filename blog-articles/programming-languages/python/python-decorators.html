1Overview

A decorator is, in the words of the Python glossary, "a function returning another function, usually applied as a function transformation using the @wrapper syntax"[1]. You write the decorator's name on the line above a def (or a class), and Python passes the newly created function to the decorator and binds whatever comes back to the function's name[2]. The glossary stresses that the syntax "is merely syntactic sugar": decorating with @staticmethod means exactly the same as writing f = staticmethod(f) after the definition[1].

The @ syntax arrived in Python 2.4 through PEP 318[3]. Before then, the only way to apply a transformation such as classmethod was to reassign the name after the function body. PEP 318 points out that this "places the actual transformation after the function body", which for a long function separates an essential part of its behaviour from its interface[3]. Moving the transformation to the top of the definition fixed that. Class decorators followed in Python 3.0 with PEP 3129[4], and Python 3.9 relaxed the grammar so that any valid expression can follow the @[5].

Not the Gang of Four Decorator

The name invites confusion with the Decorator design pattern. PEP 318 admits that the name "is not consistent with its use in the GoF book" and suggests it owes more to its use in compilers[3]. A Python decorator can implement that pattern, but it is a more general tool: it may wrap, replace, register or simply annotate the object it receives.

Decorators are everywhere in Python code. The standard library uses them for properties, class and static methods, caching, data classes, single dispatch and abstract methods[6–9],. Typical uses you will build in this article include logging and timing calls, retrying failed operations, caching results, checking arguments and registering plugins.

The article assumes you can write functions with *args and **kwargs and simple classes. Sections 2 and 3 cover the two language features that make decorators possible; sections 4 to 8 build decorators step by step; section 9 tours the built-in ones; section 10 shows how to type them; section 11 collects the mistakes people make most often; and section 12 has eight exercises with worked solutions.

2Functions are objects

A decorator receives a function as an argument and returns a function as its result. That only works because Python functions are ordinary objects. A def statement creates a function object and binds it to a name[2]; after that you can assign it to another name, store it in a list or dictionary, pass it to another function and return it from a function. Functions also carry attributes: __name__, __qualname__ and __doc__ hold the function's name, qualified name and docstring, and __dict__ is "the namespace supporting arbitrary function attributes"[10].

Anything that can be called with the f(args) syntax is a callable. The glossary lists functions and methods, and adds that "an instance of a class that implements the __call__() method is also a callable"[1]. Decorators rely on this in both directions: the decorator itself can be any callable (a function or a class), and so can the thing it returns.

Higher-order functions

A function that takes or returns another function is called a higher-order function. apply_twice() above takes one. The next step is a function that builds and returns a new function, which brings us to closures.

3Closures

A function defined inside another function can read the variables of the enclosing function. The glossary calls this a nested scope: "a function defined inside another function can refer to variables in the outer function"[1]. Lexical nested scopes were added by PEP 227, as an option in Python 2.1 and as the default from Python 2.2[11].

The useful part is that the inner function keeps those variables after the outer function has returned. The inner function is then a closure, and the outer variables it refers to are its closure variables[1]. CPython stores them in the function's __closure__ attribute, a tuple of cell objects whose cell_contents attribute holds the current value[10].

Each call to make_multiplier() creates a new multiply function with its own cell, which is why double and triple remember different factors.

Changing a closure variable with nonlocal

By default nested scopes "work only for reference and not for assignment"[1]: assigning to a name inside the inner function creates a new local variable instead. The nonlocal statement, added in Python 3.0 by PEP 3104, makes the name refer to the binding in the nearest enclosing function scope[12], so the inner function can update it. This is how a decorator can keep state between calls.

Without the nonlocal line, count += 1 would make count local to increment() and the first call would fail.

Closures capture variables, not values

A closure looks up the variable's value when it runs, not when it is created. The Programming FAQ shows the classic trap: lambdas created in a loop all see the loop variable's final value, because "x is not local to the lambdas, but is defined in the outer scope, and it is accessed when the lambda is called — not when it is defined"[13]. Its fix is to bind the current value as a default argument, which is evaluated once, when the function is defined[2,13].

4The @ syntax

Put the two previous sections together and you have a decorator: a function that takes a function, defines a closure around it and returns the closure.

The @ line does the same reassignment for you. The language reference states the rule precisely: decorator expressions "are evaluated when the function is defined, in the scope that contains the function definition. The result must be a callable, which is invoked with the function object as the only argument. The returned value is bound to the function name instead of the function object"[2]. So these two pieces of code are equivalent, except that with @ the original function is never temporarily bound to the name[2]:

With the @ syntaxRoughly equivalent to
 
@announce
def greet(): ...
def greet(): ...
greet = announce(greet)
@f1(arg)
@f2
def func(): ...
def func(): ...
func = f1(arg)(f2(func))

The last line already hints at a problem: the name greet now refers to a function called wrapper. Section 5 fixes that.

Decorators run at definition time

Because the decorator is called when the def statement executes[2], its body runs once, when the module is imported, not each time the decorated function is called. Only the returned wrapper runs on every call. Registration decorators use this deliberately: they record the function and return it unchanged.

Any expression after the @ (Python 3.9+)

Until Python 3.9 a decorator had to be a dotted name, optionally followed by a single call[5]. PEP 614 relaxed the grammar to accept any valid expression, and the language reference now says functions "may be decorated with any valid assignment_expression"[2,5]. The PEP's motivating case was GUI code such as @buttons[0].clicked.connect, which used to need a temporary variable[5].

5A well-behaved decorator

The announce decorator above only works for functions that take no arguments and return nothing. A general-purpose decorator has to do three things:

  1. accept any arguments with *args and **kwargs and pass them on unchanged[1];
  2. return the wrapped function's result;
  3. copy the wrapped function's metadata onto the wrapper.

The problem: lost metadata

Without step 3, the decorated function loses its name, docstring and signature, which breaks help(), debugging output, documentation tools and anything else that inspects functions.

The fix: functools.wraps

functools.update_wrapper() updates "a wrapper function to look like the wrapped function"[7]. By default it copies __module__, __name__, __qualname__, __annotations__, __type_params__ and __doc__ (the tuple WRAPPER_ASSIGNMENTS) and merges the wrapped function's __dict__ into the wrapper's (WRAPPER_UPDATES)[7]. It also adds a __wrapped__ attribute that points at the original function, so you can reach it "for introspection and other purposes (e.g. bypassing a caching decorator such as @lru_cache)"[7]. functools.wraps() is the same thing packaged as a decorator for the wrapper function[7].

inspect.signature() reports the original signature because it follows __wrapped__ by default; pass follow_wrapped=False to see the wrapper's own (*args, **kwargs)[14]. inspect.unwrap() follows a whole chain of __wrapped__ attributes back to the innermost function[14].

6Decorators with arguments

A line such as @retry(times=3) looks like a decorator that takes arguments, but the rule from section 4 still holds: the expression after @ is evaluated first, and its result is the decorator. PEP 318 spells this out: @decomaker(argA, argB, ...) is equivalent to func = decomaker(argA, argB, ...)(func)[3]. So retry is a decorator factory: a function that returns a decorator, which in turn returns a wrapper. That gives three nested levels.

Each level has its own job: the factory captures the configuration (times, exceptions), the decorator captures the function, and the wrapper runs on every call. All three values are closure variables of the wrapper.

Optional arguments: @deco and @deco(...)

Some decorators can be used both bare and with arguments; functools.lru_cache is one, since Python 3.8 accepts @lru_cache as well as @lru_cache(maxsize=32)[7], and so is @dataclass[8]. 7Stacking decorators

You can apply several decorators to one function. They are "applied in nested fashion"[2]: PEP 318 gives @dec2 over @dec1 over def func as equivalent to func = dec2(dec1(func))[3]. The decorator nearest the def is applied first and ends up innermost; the top one is applied last and its wrapper runs first on each call.

Think of the decorators as layers of an onion: definition goes bottom-up, a call goes top-down through each wrapper to the function and back out again. Order matters whenever the layers interact. Put an authorisation check above a cache, for example, and every call is checked; put it below and cached results are returned without any check.

The standard library has its own ordering rules. The abc documentation says that when @abstractmethod "is applied in combination with other method descriptors, it should be applied as the innermost decorator", for example @classmethod above @abstractmethod[9].

8Class decorators and decorator classes

Two different ideas share similar names here. A class decorator is a decorator applied to a class. A decorator class is a class whose instances act as decorators.

Class decorators

PEP 3129 extended the @ syntax to class statements in Python 3.0, with the same meaning: @foo over @bar over class A is equivalent to A = foo(bar(A))[4]. The language reference confirms that the evaluation rules are the same as for function decorators and that the result is bound to the class name[2]. A class decorator receives the finished class object, so it can inspect it, register it, add or replace attributes, and return the same class (or a different one).

The best-known class decorator is @dataclasses.dataclass, covered in section 9. It "examines the class to find fields", which it defines as class variables with type annotations, generates methods such as __init__() and __repr__(), and "returns the same class that it is called on; no new class is created" (unless slots=True is used)[8].

Decorator classes

Since a decorator can be any callable[2] and instances of a class with a __call__() method are callable[1,10], a class can implement a decorator. Calling the class with the function creates an instance that stores it; calling the instance runs the wrapper logic. State lives naturally on the instance instead of in a nonlocal variable. Call functools.update_wrapper(self, func) in __init__ to copy the metadata[7].

There is a catch when a decorator class is used on a method. A plain function becomes a bound method when you look it up on an instance because functions are descriptors: they have a __get__() method, so "functions are non-data descriptors that return bound methods during dotted lookup from an instance"[15]. An instance of CountCalls has no __get__(), so it is returned unchanged and never receives self:

The fix is to make the decorator a descriptor too, returning a bound method from __get__(), which is exactly what the descriptor guide's pure-Python model of a function does with types.MethodType[15]:

A closure-based decorator does not have this problem, because the wrapper it returns is an ordinary function and binds like one. That is one reason function decorators are the more common choice.

9Built-in and standard library decorators

Python ships with a set of decorators you will use far more often than you write your own. The descriptor guide notes that @classmethod, @staticmethod, @property and @functools.cached_property "are all implemented as descriptors"[15].

@property

property returns a property attribute built from getter, setter and deleter functions[6]. Used as a decorator, it turns a method into the getter of a read-only attribute with the same name. A property object then has getter, setter and deleter methods "usable as decorators that create a copy of the property with the corresponding accessor function set to the decorated function", and the documentation warns to give each accessor the same name as the property[6].

@staticmethod and @classmethod

"A static method does not receive an implicit first argument"[6]. The descriptor guide explains that it returns the underlying function unchanged, whether you look it up on the class or an instance[15]. A class method "receives the class as an implicit first argument, just like an instance method receives the instance", and when called on a subclass it receives the subclass[6]. That makes class methods the standard way to write alternative constructors that also work for subclasses.

Changed in Python 3.13: no more @classmethod over @property

Python 3.9 allowed class methods to wrap other descriptors such as property(), which made "class properties" possible. That was deprecated in 3.11 and removed in 3.13: "Class methods can no longer wrap other descriptors such as property()"[6]. On 3.13 the stack below no longer gives you a computed class attribute: Config.env is a bound method wrapping the property object, and calling it fails.

@functools.cache and @functools.lru_cache

lru_cache wraps a function "with a memoizing callable that saves up to the maxsize most recent calls"; maxsize defaults to 128[7]. cache (Python 3.9+) is an unbounded cache that "returns the same as lru_cache(maxsize=None)" and is smaller and faster because it never evicts[7]. Both add cache_info(), which reports hits, misses, maxsize and current size, and cache_clear()[7]. They turn the exponential recursive Fibonacci function into a linear one:

In the second half, maxsize=2 means the cache holds only the two most recently used results: the second 1 is a hit, computing 3 evicts 2 (the least recently used), and the last 1 is a hit again.

Because the cache is a dictionary, "the positional and keyword arguments to the function must be hashable"[7]. Also note that f(a=1, b=2) and f(b=2, a=1) may get separate cache entries[7].

@functools.cached_property

cached_property (Python 3.8+) turns a method into a property "whose value is computed once and then cached as a normal attribute for the life of the instance"[7]. Unlike property it allows writes, and deleting the attribute clears the cache so the method runs again[7]. Since Python 3.12 it no longer takes a lock, so it does not stop the getter running twice under concurrent first access[7].

@functools.singledispatch

singledispatch turns a function into a generic function whose implementation is chosen by "the type of the first argument"[7]. Implementations are added with the register() decorator, which since Python 3.7 can read the type from an annotation[7].

@dataclasses.dataclass

The dataclasses module, first described in PEP 557 for Python 3.7, "provides a decorator and functions for automatically adding generated special methods such as __init__() and __repr__() to user-defined classes"[8,16]. Options such as frozen=True, order=True, kw_only=True and slots=True (the last two added in 3.10) are passed as decorator arguments, and @dataclass, @dataclass() and @dataclass(...) with all the defaults are equivalent[8].

10Typing decorators with ParamSpec

A decorator changes the type of the name it decorates, so a static type checker such as mypy needs to know what the decorator returns. Before Python 3.10 the best common annotation was Callable[..., R], and PEP 612 explains the cost: the decorated function's parameter types are lost, so a type checker accepts calls that fail at run time[17]. mypy's documentation makes the same point and recommends a parameter specification for "a more faithful type annotation"[18].

PEP 612 (Python 3.10) introduced parameter specification variables[17]. A ParamSpec captures the full parameter list of one callable so it can be forwarded to another, "a pattern commonly found in higher order functions and decorators"[19]. Inside the wrapper, *args is annotated P.args and **kwargs P.kwargs[19]. Since Python 3.12 you can declare it with the type parameter syntax as [**P] instead of P = ParamSpec("P")[19].

Adding or removing parameters with Concatenate

Some decorators supply an argument themselves, such as a database connection or a lock. Concatenate annotates "a higher-order callable which adds, removes, or transforms parameters of another callable"; its last argument must be a ParamSpec or ...[19]. PEP 612 describes Concatenate[int, P] as the parameters of P with a positional-only int parameter prepended[17].

For a decorator factory the same idea applies one level up: the factory returns Callable[[Callable[P, R]], Callable[P, R]]. When a decorator supports both bare and parameterised use, mypy's documentation recommends describing the two forms with @overload[18].

11Common pitfalls

Most decorator bugs come from a handful of mistakes. Each is shown below with its real symptom.

1. Forgetting to return the wrapper

The value the decorator returns is what gets bound to the name[2]. A decorator without a return statement returns None, so the function disappears:

2. Forgetting to return the result

The opposite mistake: the wrapper calls the function but drops its return value, so every decorated function silently returns None.

3. Mixing up @deco and @deco()

With a decorator factory, the expression after @ must be the call[3]. Writing @retry instead of @retry(3) passes the function as times, and the function's name is bound to the inner decorator. Nothing fails until the first call:

Section 6 shows how to write a decorator that accepts both forms.

4. Losing metadata

Without functools.wraps, every decorated function reports the wrapper's name, docstring and signature (section 5). Use it in every wrapper; it costs one line.

5. Work done at import time

Code in the decorator body, outside the wrapper, runs once when the module is imported[2]. Opening files, connecting to databases or reading the clock there happens at import, not per call, and the result is shared by every call. Keep per-call work inside the wrapper.

6. Shared mutable state

Closure variables live as long as the wrapper, so state kept there is shared by every call, every thread and every caller of the decorated function. That is the point of a cache or a counter, but it also means caches can grow without bound and counters need a lock if threads are involved.

7. Caching methods keeps instances alive

If a method is decorated with lru_cache, "the self instance argument is included in the cache", and the cache "keeps references to the arguments and return values until they age out of the cache or until the cache is cleared"[7]. The Programming FAQ states the consequence: "instances are kept alive until they age out of the cache or until the cache is cleared"[13]. It recommends cached_property for argument-less methods, which stores the result on the instance itself[13].

8. Wrong order with descriptors

@staticmethod, @classmethod and @property return descriptor objects, not functions[15]. A function decorator placed above them receives that object instead of a function. Put your own decorator below them (nearest the def), and keep @abstractmethod innermost[9]. On Python 3.13, also remember that @classmethod no longer wraps @property[6].

On Python 3.10 and later a staticmethod object is itself callable[6], which is why MathUtils.triple(4) still works. The call through an instance fails because wrapper is a plain function and is bound as an instance method[15], so the instance is passed as an extra argument.

9. Decorator classes on methods

A class-based decorator without __get__() does not bind to instances, so the method never receives self (section 8)[15].

10. Unhashable arguments to a cache

cache and lru_cache raise TypeError for lists, dicts and other unhashable arguments[7]. Convert them to tuples or frozensets before the call, or cache a helper that takes hashable arguments.

Exercise 1: Call counterclosures · easy

Write a decorator @counted that counts how many times the decorated function has been called and exposes the count as an attribute calls on the decorated function. The function's name and docstring must be preserved.

Show solution

Store the count as an attribute of the wrapper. Functions accept arbitrary attributes[10], and the wrapper is what the caller sees.

Exercise 2: Predict the outputstacking · easy

Without running it, write down the three lines this program prints, in order, and explain the order.

def bold(func):
    print("bold")
    return lambda: "<b>" + func() + "</b>"

def italic(func):
    print("italic")
    return lambda: "<i>" + func() + "</i>"

@bold
@italic
def text():
    return "hi"

print(text())
Show solution

Decorators are applied bottom-up at definition time, so italic runs (and prints) first, then bold. The result is bold(italic(text))[3], so the outer <b> wraps the inner <i>.

Exercise 3: Type checking at run timewraps · medium

Write @enforce_types, which checks each argument against the function's annotations (simple classes only, such as int or str) and raises TypeError with a helpful message if one does not match. Hint: inspect.signature(func).bind(*args, **kwargs) maps arguments to parameter names.

Show solution

Compute the signature once, at decoration time, rather than on every call. Signature.bind() maps the call's arguments to parameter names[14].
