01What code quality means

Code quality is mostly about the next person to read the code, who is often you. PEP 8, Python's style guide, rests on the observation that “code is read much more often than it is written”, so its rules aim to improve readability and make code consistent across the wide spectrum of Python projects.[1] The Zen of Python puts the same idea in two words: “Readability counts.”[2] Martin’s Clean Code makes the economic argument: messy code slows a team down a little more with every change until productivity approaches zero, and the only way to keep moving fast is to keep the code clean.[3]

In practice, Python teams pursue quality on three levels, and the rest of this article is organised around them.

LevelQuestion it answersWhere it is covered
ConventionsDoes the code look the way Python readers expect?PEP 8 (layout, naming), PEP 257 (docstrings)
Design habitsIs the code easy to understand and cheap to change?Clean code, refactoring, documentation, code review
AutomationCan a machine catch the problem before a person has to?Static analysis, linters (Ruff, Flake8, Pylint), formatters (Black), import sorters (isort), type checkers (mypy)

The levels support each other. Google’s review guidance tells reviewers that the style guide is the absolute authority on matters of style,[4] and automating the style guide frees review time for design, which that same guidance calls the most important thing to cover in a review.[5]

02PEP 8: the style guide

PEP 8, written by Guido van Rossum, Barry Warsaw and Alyssa Coghlan, gives the coding conventions for the Python code in the standard library, and most Python projects have adopted it.[1,6] It is a guide, not a law. Its section titled “A Foolish Consistency is the Hobgoblin of Little Minds” says consistency within one module matters most, then within a project, then with PEP 8 itself, and that a rule should be broken when following it would make the code less readable.[1]

2.1 Layout

  • Indentation: use 4 spaces per indentation level, and prefer spaces to tabs.[1]
  • Line length: limit lines to 79 characters, and docstrings and comments to 72. Teams that agree on it may raise the limit to 99 characters, provided comments and docstrings still wrap at 72.[1]
  • Blank lines: two blank lines around top-level functions and classes, one blank line around methods inside a class.[1]
  • Imports: one module per import line, at the top of the file, grouped as standard library, then related third-party, then local application imports, with a blank line between groups. Avoid wildcard imports (from module import *).[1]
  • Whitespace: no spaces just inside brackets or before a comma or colon; one space around assignment and comparison operators; no spaces around = for a keyword argument.[1]

2.3 Programming recommendations

PEP 8 also covers how to write common constructs. Compare to singletons such as None with is or is not, never with ==; use isinstance() rather than comparing types; use str.startswith() and str.endswith() rather than slicing; don’t compare booleans to True or False with ==; rely on the fact that empty sequences are false; name specific exceptions instead of a bare except:; make return statements consistent (either every return returns an expression or none does); and use a def rather than assigning a lambda to a name.[1]

03PEP 257: docstrings

A docstring is a string literal that occurs as the first statement in a module, function, class or method definition, and it becomes that object’s __doc__ attribute.[11] PEP 257, by David Goodger and Guido van Rossum, standardises their high-level structure rather than their markup. Its main rules are:[11]

  • All modules should normally have docstrings, as should the functions and classes a module exports and the public methods of a class.
  • Always use """triple double quotes"""; use r"""raw triple double quotes""" if the docstring contains backslashes.
  • A one-line docstring fits on one line with its quotes. It is a phrase ending in a period that prescribes the function’s effect as a command (“Do this”, “Return that”), and it must not just restate the signature.
  • A multi-line docstring has a summary line, a blank line, then a more elaborate description.
  • A function’s docstring should summarise its behaviour and document its arguments, return values, side effects, exceptions raised and restrictions on when it can be called.

The Python tutorial adds that the summary line should not restate the object’s name or type, should begin with a capital letter and end with a period, and that the parser strips the indentation of multi-line docstrings.[6]

Ruff implements the pydocstyle checks as its D rules, and the lint.pydocstyle.convention setting picks the rule subset that matches PEP 257 (or the Google or NumPy styles).[10,12]

Every message maps to a PEP 257 rule: triple double quotes (D300), a summary ending in a period (D400), a summary in the imperative mood (D401) starting with a capital letter (D403), no signature in the docstring (D402), a summary line followed by a blank line (D205), and a docstring on every public class and method (D101, D102). 04Clean code

Robert C. Martin’s Clean Code collects habits that make code easy to read and change. The book’s examples are in Java, but most of its advice carries over to Python directly. The points with the most leverage are:[3]

  • Meaningful names (chapter 2). Use intention-revealing names: a name should tell you why something exists, what it does and how it is used, so that it needs no comment. Avoid misleading names, meaningless distinctions such as data versus info, and encodings that the reader has to translate in their head.
  • Small functions that do one thing (chapter 3). “Functions should do one thing. They should do it well. They should do it only.” Keep each function at a single level of abstraction, and keep argument lists short; flag arguments (a boolean that switches behaviour) are a sign that the function does more than one thing.
  • Comments (chapter 4). A comment often compensates for code that failed to express itself. Prefer clearer code to a comment that explains unclear code, and keep comments for intent, warnings and legal notices.
  • Error handling (chapter 7). Use exceptions rather than return codes, and don’t return or pass null (in Python, None) when an exception or an empty collection would serve the caller better.
  • The Boy Scout Rule (chapter 1). Leave the code a little cleaner than you found it; continuous small improvements keep code from rotting.

Google’s Python style guide agrees on function size: it prefers small, focused functions and suggests considering a split once a function passes about 40 lines, while placing no hard limit.[13] Its review guidance says comments should mostly explain why code exists, not what it does; if code needs a “what” comment, the code should be made simpler.[5]

05Refactoring

Martin Fowler defines a refactoring (noun) as “a change made to the internal structure of software to make it easier to understand and cheaper to modify without changing its observable behavior”, and to refactor (verb) as restructuring software by applying a series of refactorings without changing its observable behaviour.[14,15] Its heart is a series of small behaviour-preserving transformations: each step is small, so it is unlikely to go wrong, and the system keeps working after every step.[14]

Three practices from Fowler’s book make refactoring safe and routine:[15]

  • Tests first. Before refactoring, make sure you have a solid suite of self-checking tests (chapters 1 and 4). Without them you cannot tell whether a change preserved behaviour.
  • Two hats. Kent Beck’s metaphor: at any moment you are either adding functionality or refactoring, never both at once (chapter 2).
  • Code smells. Chapter 3, written with Beck, lists symptoms that suggest a refactoring, such as Mysterious Name, Duplicated Code, Long Function, Long Parameter List, Primitive Obsession and Repeated Switches.

The online catalog names each refactoring and links it to its mechanics.[16] The ones used below are Rename Variable, Replace Magic Literal, Extract Function, Replace Nested Conditional with Guard Clauses and Replace Loop with Pipeline.[16]

06Documentation

Documentation works at several layers, and each answers a different question:

LayerAudience and questionPython mechanism
CommentsMaintainers: why is this code written this way?# ...
DocstringsCallers: how do I use this function, class or module?__doc__, help(), pydoc
Type hintsCallers and tools: what types go in and come out?annotations (PEP 484)
Executable examplesEveryone: does it really behave as described?doctest
Project docsNew users: what is this and how do I start?README, tutorials, generated API reference

PEP 257 fixes a docstring’s overall shape but not its inner markup. Google’s style guide fills that gap with Args:, Returns: (or Yields:) and Raises: sections, and sets the goal that a docstring should give enough information to write a call to the function without reading its code.[13] It allows either the descriptive style (“Fetches rows”) or the imperative style (“Fetch rows”) as long as a file is consistent; PEP 257 itself prefers the imperative.[11,13] Type hints, standardised by PEP 484, document types in a form tools can check; the PEP states that Python will remain dynamically typed and that the authors have no desire to make hints mandatory.[17]

The doctest module searches docstrings for text that looks like interactive Python sessions and runs those sessions to verify that they work exactly as shown. That keeps examples honest: the documentation is checked every time the tests run.[18]

The same docstring is what help() and pydoc show, so it doubles as the reference page. Ruff can check this Google-style layout with convention = "google":[12]

What to write where

Put the why in comments, the how to call it in docstrings, and the what types in annotations. Google’s style guide adds one rule of thumb for comments: if you would have to explain the code at the next code review, comment it now, but never describe what the code plainly does.[13]

07Code reviews

A code review is a second developer reading a change before it is merged. Google publishes its internal guidance as the Engineering Practices documents, and the core rule is this: a reviewer should approve a change once it definitely improves the overall code health of the system, even if it isn’t perfect, because “there is no such thing as ‘perfect’ code—there is only better code.”[4] Technical facts and data overrule opinions and personal preferences, and on matters of style the style guide is the absolute authority.[4]

7.1 What a reviewer looks for

Google lists these areas, most important first:[5]

AreaQuestion to ask
DesignDo the pieces interact sensibly, does the change belong here, and is now the right time for it?
FunctionalityDoes it do what the author intended, and is that good for users? Check edge cases and concurrency.
ComplexityCan a reader understand it quickly? Is it over-engineered, solving problems nobody has yet?
TestsAre there appropriate tests, and will they actually fail when the code is broken?
NamingDoes each name say what the thing is or does, without being hard to read?
CommentsAre they clear and necessary, and do they explain why rather than what?
Style and consistencyDoes it follow the style guide, and match the surrounding code where the guide is silent?
DocumentationIf the change affects how people build, test, use or release the code, is the documentation updated?

The same page asks reviewers to look at every human-written line they were assigned, to consider the change in the context of the whole file and system, and to point out good things as well as problems.[5]

7.2 Small changes, fast responses, kind comments

  • Keep changes small. Small changes are reviewed faster and more thoroughly, are less likely to introduce bugs and are easier to roll back. As a rough guide, 100 lines is usually a reasonable size and 1000 lines is usually too large; the right size is one self-contained change.[19]
  • Respond quickly. One business day is the maximum time it should take to respond to a review request. Slow reviews hold up the whole team and push people to accept worse code.[20]
  • Comment on the code, not the person, and explain why. Label the severity of each comment: “Nit:” for minor polish, “Optional” or “Consider” for suggestions, “FYI” for information. If the reviewer cannot understand the code, the fix is clearer code, not an explanation in the review tool that future readers will never see.[21]
  • Let machines review style. When a formatter and a linter run on every change, human reviewers no longer have to raise style points, and Black’s documentation notes that a consistent formatter produces the smallest possible diffs, which makes review faster.[22]

08Static analysis

Static analysis examines source code without running it. Pylint’s documentation describes the idea in one line: it “analyses your code without actually running it”, checking for errors, enforcing a coding standard and looking for code smells.[23] mypy makes the same promise for types: it finds bugs in your programs without even running them.[24] The tools in this article sit on a spectrum:

ToolWhat it analysesTypical finds
pycodestyleText and tokens against PEP 8Whitespace, line length, blank lines
PyflakesNames and scopes in the syntax treeUnused imports and variables, undefined names
mccabeControl flow graph of each functionFunctions that are too complex
PylintSyntax tree plus inferred values (astroid)Errors, smells, design problems, conventions
mypyType annotations and inferred typesNone misuse, wrong argument types, missing returns
RuffSyntax tree, reimplementing rules from many of the aboveMost of the above, very quickly

Pylint, rather than trusting annotations, infers the values your code actually holds, which makes it slower but lets it find more problems in code that isn’t fully typed.[23] Flake8 bundles pycodestyle, Pyflakes and Ned Batchelder’s mccabe script.[7]

8.2 Cyclomatic complexity

Thomas McCabe’s 1976 paper defines the cyclomatic complexity of a function as the number of linearly independent paths through its control-flow graph, and it suggests 10 as a reasonable, though not magical, upper bound per module.[26] Each if, elif, loop, except and boolean operator adds a path. Flake8 reports C901 when a function exceeds --max-complexity, and Ruff implements the same check.[8,10]

Both tools give delivery_fee a complexity of 7, above the limit of 5 set here. Exercise 7 asks you to bring it down with a lookup table.

Ruff can fix many problems itself. Fixes it marks as safe preserve the program’s behaviour; unsafe fixes might change behaviour or remove comments, so Ruff applies only safe fixes unless you also pass --unsafe-fixes.[28] --diff previews the changes without writing them.

10Formatting with Black

A linter tells you what is wrong; a formatter rewrites the layout for you. Black calls itself “the uncompromising code formatter”: “By using Black, you agree to cede control over minutiae of hand-formatting.” In return you get speed, determinism and freedom from pycodestyle nagging about formatting.[22] Its style configuration options are deliberately limited and rarely added.[30]

Key choices of the Black code style:[30]

  • Line length 88, about 10% over 80, because it produced significantly shorter files than 80.
  • Double quotes for strings, partly because they anticipate apostrophes in English text.
  • The magic trailing comma: a trailing comma you add to a collection tells Black to keep it exploded one item per line; remove the comma and Black may join it again.
  • Safety: with --safe, the default, Black checks that the code before and after formatting is semantically equivalent (the syntax trees match, apart from a few documented exceptions such as docstring whitespace).

Black normalised spacing and quotes, inserted the two blank lines PEP 8 asks for, split the long return line, and collapsed sizes onto one line. It kept colours exploded because of its magic trailing comma. In CI, --check reports without writing and exits non-zero when a file would change:

11Import sorting with isort

isort is a utility and library that sorts imports alphabetically and automatically separates them into sections and by type.[32] Its sections follow PEP 8’s grouping (standard library, third party, local), with a blank line between groups.[1] Like Black it can preview with --diff and verify with --check-only (-c).[32]

11.1 Making isort and Black agree

isort’s default wrapping style for long imports differs from Black’s, so the two can undo each other’s work. The black profile sets isort to Black’s choices: vertical hanging indent (multi_line_output = 3), trailing commas, parentheses and a line length of 88.[33]

12Putting it together

Each tool is most useful when it runs automatically, with the same settings for every developer and on the build server. PEP 518 reserves the [tool] table of pyproject.toml for this: a tool may use the sub-table tool.NAME if it owns that name on PyPI.[34] Ruff, Black, isort, mypy and Pylint all read their settings from there.[29]

There are two common set-ups. The first uses Ruff alone for linting, import sorting and formatting, which its documentation positions as a replacement for Flake8 and its plugins, Black, isort and pydocstyle.[12] The second uses the specialised tools side by side. Both add mypy for types.

Flake8 does not read pyproject.toml, hence the separate .flake8 file. E203 (whitespace before a colon) is ignored because Black treats the colon in a slice as a binary operator and puts spaces around it when the bounds are complex expressions, which pycodestyle would flag; Black’s documentation recommends ignoring E203 for this reason.[30]

A small script runs every check the way a CI job would. set -e stops at the first failure, so the job fails if any tool does.

12.1 Run the checks before every commit

The pre-commit framework manages and runs Git hooks declared in a .pre-commit-config.yaml file. Each entry names a repository, a pinned revision and the hooks to use; pre-commit install sets up the Git hook, and pre-commit run --all-files runs every hook over the whole repository, which is also how CI usually invokes it.[35] A configuration for the Ruff-only set-up looks like this. Adopting tools on an existing codebase

Turning every rule on at once in a large project buries the team in warnings. Start with the rules that find bugs (Pyflakes’ F, flake8-bugbear’s B), format the whole codebase in one dedicated commit, then add rule groups one at a time. Ruff’s documentation recommends choosing rules with lint.select rather than lint.extend-select, so the rule set is explicit and does not shift when the default changes.[28] mypy’s documentation likewise warns that --strict may be too aggressive at first for a large existing codebase.[25]
