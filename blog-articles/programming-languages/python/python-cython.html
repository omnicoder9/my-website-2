1What Cython is

Cython is a programming language and a compiler. The language is a superset of Python that adds optional static type declarations, and the compiler translates it into C (or C++) source that is then compiled into a CPython extension module[1]. The resulting module is imported like any other Python module, but its code runs as compiled C inside the CPython runtime and can call C functions directly[1,2]. Cython grew out of an earlier project called Pyrex, and its authors describe its two main uses as speeding up Python code and wrapping external C libraries[1,2].

The Python documentation itself lists Cython first among the third-party tools it recommends for writing extensions, noting that such tools help avoid reference-counting errors and code tied to one particular CPython version[3]. (A separate article in this series covers that raw C API; this one stays at the Cython level.)

fib.pyxPython syntax + optional C types
→
cythontranslates to fib.c (thousands of lines of C-API code)
→
gcc / clang / MSVCcompiles against Python.h
→
fib.cpython-313-…soimport fib from Python

Two facts follow from this pipeline and explain most of what is in this article:

  • Untyped code still goes through the Python object model. Cython can compile almost any Python module unchanged, but every variable is then a generic Python object and every + is a call into the C API. The Cython documentation puts the typical gain from compiling unmodified Python at about 20–50%[4].
  • Static types are where the speed comes from. Once a variable is declared as a C double or long, Cython can emit plain C arithmetic for it, which removes object allocation and dynamic dispatch from tight loops[1,5].
Version used here

All examples were built with Cython 3.3.0, the current release on PyPI on the day of writing[6]. Cython 3.1 dropped support for Python 2.7–3.7, and Cython 3.3 also dropped Python 3.8, so current releases need CPython 3.9 or later[7]. Section 12 summarises what changed between the long-lived 0.29 series and Cython 3.

3Static typing: def, cdef, cpdef

The cdef keyword declares C variables, C functions and C-level attributes. A cdef variable has a fixed C type and lives on the C stack, so arithmetic on it compiles to plain C[15]. The common types map onto C's:

Cython declarationC typeConverted from / to Python
cdef int i, cdef long n, cdef long long bigsigned integers of C's widthsint (raises OverflowError if it does not fit)
cdef Py_ssize_t ksigned size type used for indexingint
cdef double x, cdef float fIEEE floating pointfloat
cdef bint flagC int used as a booleanbool
cdef char *spointer to bytesbytes (borrowed, not copied)
cdef list items, cdef dict dPython object of an exact built-in typetype-checked Python object

Functions come in three kinds[15]:

  • def functions are Python functions: they take and return Python objects and can be called from anywhere.
  • cdef functions are C functions: they can take and return C values, they are called with the cheap C calling convention, and they are not visible from Python code outside the module.
  • cpdef functions are hybrids: Cython generates a C function plus a Python wrapper, so Cython callers get the fast C call and Python callers still see a normal function. A cpdef method can be overridden by a Python subclass, at the cost of a small check on each call.

Typed arguments are converted on entry, and the conversion is checked. A C int is 32 bits on mainstream platforms, so a larger Python integer cannot be squeezed into it:

Inside the function, however, C arithmetic is C arithmetic: add_cp(2**31 - 1, 1) does not raise, and what it returns is governed by C's rules for signed overflow. Section 11 shows the directive that adds checks, and Section 13 lists overflow among the classic pitfalls.

Type inference

Cython also infers C types for untyped local variables when that cannot change the program's meaning. By default it will not infer a C integer type for a variable used in arithmetic, because C integers can overflow where Python's cannot; the infer_types=True directive relaxes that[9]. Declaring loop counters and accumulators explicitly is still the clearest option.

4Pure Python mode

The .pyx syntax is not valid Python, so tools such as linters, formatters and the interpreter itself cannot read it. Cython therefore also accepts ordinary .py files in which C types are expressed with standard annotations (PEP 484 and PEP 526) and the decorators of the special cython module[4,16]. The same file runs unchanged under CPython, where the cython names are harmless no-ops, and runs fast when compiled[4].

The integration routine above comes from the Cython quick-start guide and is a good stress test because it is dominated by a tight numeric loop with a function call in it[18]. Four versions are compared: the plain Python function, the same source compiled by Cython without any types, the typed .pyx version and the typed pure-Python-mode version.

On this machine, compiling the unmodified Python bought a modest speed-up, in line with the documentation's 20–50% guidance for untyped code[4], while adding a handful of C type declarations made the function well over a hundred times faster. Both typed spellings produce the same C, so they run at the same speed. Your numbers will differ with the CPU, the compiler and the Python version, which is why every benchmark in this article prints its own measurements. Use timeit's best-of-several-runs approach as here: the minimum is the least noisy estimate, since other processes can only make a run slower[19].

The speed-up is in the loop, not the call

Each call still converts three Python arguments into C values and one C double back into a Python float. That overhead is constant, so a typed function that is called a million times with tiny inputs gains far less than one that loops a million times internally. Move loops into Cython rather than calling Cython from a Python loop.

6Reading the annotation report

Running cython -a (or cythonize -a) writes an HTML report next to the C file. Each source line is shaded by how much it interacts with the Python C API: white lines translate to pure C, yellow lines call into the C API, and darker yellow means more calls. Clicking a line shows the C code generated for it[5,18]. The shade is driven by a per-line score that Cython computes by counting C-API calls in the generated code, weighting calls to Python's C API five times and Cython's own helper functions twice[20].

The report is meant to be opened in a browser, but the scores are in the HTML, so a few lines of Python can print them. This makes the difference between the untyped and typed integration modules visible in a terminal:

In the untyped module every line in the loop is yellow: i, s and dx are Python objects, so each + and * calls a generic C-API function. In the typed module the whole loop scores zero. What remains is work done once per call: the function definitions (argument parsing and conversion), the division that sets dx (which keeps Python's ZeroDivisionError check, see Section 11) and the return (boxing a C double into a Python float). That is the pattern to aim for: yellow at the edges, white in the loop. The documentation recommends profiling first to find where time goes and then using the annotation to see why[18].

7Extension types

A cdef class defines an extension type: a Python class implemented as a C struct. Its attributes are declared up front with C types and stored directly in the struct rather than in a per-instance __dict__, so attribute access from Cython code is a struct field access[21,22]. By default those attributes are invisible to Python; readonly and public expose them for reading or for reading and writing[22].

8Typed memoryviews and NumPy

NumPy is already fast when an operation can be expressed as whole-array (vectorised) calls. It does not help when each step depends on the previous one, because that forces a Python-level loop over individual elements. Typed memoryviews are Cython's answer: a declaration such as double[::1] gives C-speed indexed access to any object that supports the buffer protocol, including NumPy arrays, array.array, bytearray and Cython arrays, without depending on NumPy at compile time[25,26].

The syntax encodes the element type, the number of dimensions and the memory layout: double[:] is a 1-D view with any stride, double[::1] requires C-contiguous data, and double[:, ::1] is a C-contiguous 2-D view. Adding const accepts read-only buffers as well[25].

An exponential moving average (EMA) is a good example of a calculation NumPy cannot vectorise directly, because each output depends on the previous output:

The header comment switches off bounds checking and negative-index handling for the whole file, which removes two branches from every element access (Section 11 explains the trade-off). Indexing a typed memoryview with a C integer compiles to pointer arithmetic, and the NumPy array out is only touched as a Python object twice, when it is created and when it is returned.

Two lessons sit in these numbers. First, a Python loop over a NumPy array is slower than the same loop over a list, because every values[i] creates a new NumPy scalar object. Second, the compiled memoryview loop removes that per-element overhead entirely. The Cython NumPy tutorial walks through the same progression, from an untyped loop to typed memoryviews, on a different kernel[27].

What a memoryview checks for you

The older np.ndarray[double] syntax

Cython also supports the older buffer syntax cnp.ndarray[cnp.float64_t, ndim=1] after cimport numpy. Memoryviews are the preferred replacement: the documentation lists a cleaner syntax, no need for the GIL in most uses, faster access, and the freedom to use them anywhere (arguments, module globals, cdef class attributes) with any object that exposes the PEP 3118 buffer interface[25,27,29]. Cython 3.1 stopped shipping its own copy of NumPy's C declarations; cimport numpy now uses the declarations that NumPy itself installs[7].

9Releasing the GIL: nogil and prange

In the standard ("GIL-enabled") build of CPython, the global interpreter lock ensures that only one thread executes Python bytecode at a time, so threads do not speed up CPU-bound Python code[30]. Code that does not touch Python objects does not need the lock, and Cython lets you release it explicitly[31]:

  • with nogil: releases the GIL for a block. The block should contain only C-level work; the compiler rejects operations on Python objects there (Section 13 shows the error), while raising an exception or entering a nested with gil: block re-acquires the lock[31].
  • A function declared cdef ... noexcept nogil can be called with the GIL released.
  • cython.parallel.prange is a parallel for loop implemented with OpenMP. With nogil=True it releases the GIL and splits the iterations across a pool of threads; variables updated with in-place operators such as += become reductions automatically, and other assigned variables become thread-private[32].

OpenMP must be enabled in the C compiler and linker, which for GCC means -fopenmp (MSVC uses /openmp)[32,33]. A setup.py is the natural place for those flags:

The Mandelbrot set is a classic embarrassingly parallel workload: each pixel is computed independently, but pixels inside the set take far longer than those outside, so a dynamic schedule that hands out rows as threads become free balances the load better than fixed blocks[32].

Free-threaded Python

Since 3.13, CPython also offers an optional free-threaded build, proposed in PEP 703, in which the GIL is disabled[34,35]. Cython has supported it since 3.1: a module marked with the freethreading_compatible=True directive declares itself safe to import without re-enabling the GIL, but the directive is only a promise; it does not make the code thread-safe[9,36]. Cython 3.3 also added experimental support for running prange with the GIL held, which only runs in parallel on free-threaded builds[32].

10Calling C libraries

Calling C is Cython's other main use. A C declaration is made visible with a cdef extern from "header.h": block, which copies the prototypes Cython needs; the header is #included in the generated C so the C compiler checks them against the real ones[37,38]. Cython ships ready-made declarations for the C standard library under libc (for example from libc.math cimport sqrt) and for the Python C API under cpython[38].

11Compiler directives

Compiler directives change how Cython translates code. They can be set for a whole file in a header comment such as # cython: boundscheck=False, for a single function with a decorator such as @cython.boundscheck(False), for a block with a with statement, on the command line with -X, or through the compiler_directives argument of cythonize()[9]. The ones you will meet most often:

DirectiveDefaultEffect when changed
boundscheckTrueFalse: no IndexError on out-of-range indexing; a bad index may read or corrupt memory.
wraparoundTrueFalse: negative indices are not translated to "from the end".
initializedcheckTrueFalse: no check that a memoryview has been assigned before use.
cdivisionFalseTrue: C semantics for /, // and % on C types, and no ZeroDivisionError check.
overflowcheckFalseTrue: C integer arithmetic raises OverflowError instead of overflowing.
infer_typesNone (safe only)True: also infer C integer types for arithmetic variables.
language_level3 in Cython 32: Python 2 semantics (legacy code only).
bindingTrue since 3.0False: compiled functions behave like built-in functions (less introspection).

The defaults come from the directive reference[9]. The documentation warns that the speed directives trade safety for speed: with boundscheck off, an index that would have raised IndexError "may instead cause segfaults or data corruption"[9]. Turn them off only in code whose indices are already proven correct, and keep the tests running against a build with checks on.

Division: Python semantics by default

Python's // rounds toward negative infinity and % takes the sign of the divisor, whereas C's integer division truncates toward zero[44]. Cython keeps the Python behaviour for C integers unless you ask for C's, at a cost the documentation puts at up to 35%[9]:

With cdivision(True) the zero check is also gone, so c_div(1, 0) is undefined behaviour in C; on x86-64 Linux it kills the process with a floating-point exception signal rather than raising anything Python can catch.

12What changed in Cython 3

Cython 3.0 was released on 17 July 2023 after the 0.29 series had been the stable line for about five years, and it changed several defaults[7,47]. The ones most likely to affect existing code are:

  • Python 3 semantics by default. language_level=3 is the default, so / is true division, print is a function and generators follow PEP 479. Before 3.0 this required setting language_level explicitly[47].
  • Exceptions propagate from cdef functions. A cdef function with a C return type and no exception declaration now checks for and propagates Python exceptions. In 0.29 the exception was printed and swallowed. The new noexcept keyword restores the old behaviour where you are sure the function cannot raise[15,47].
  • binding=True by default. Compiled def functions behave like Python functions for introspection: inspect.signature(), annotations and binding as methods all work[47].
  • Python semantics for **. a ** b on C integers can now return a double (for negative exponents), and on floats can return a complex number; the cpow=True directive restores C semantics[47].
  • Annotations are typing. x: int now means an exact Python int, and many more annotations are understood, which is what makes pure Python mode practical[4,47].
  • DEF and IF are deprecated. The compile-time constants and conditional compilation of the Pyrex era should be replaced with enums, cdef constants or ordinary runtime code[47].

The exception change is the one with the biggest effect on behaviour. The module below defines the same parser twice, once with the Cython 3 default and once with noexcept:

With noexcept the exception is reported as "ignored" on standard error and the function returns 0, so total_noexcept silently produces 7 from bad input. Under Cython 0.29 that was the behaviour of every cdef int function without an except clause, which made it a common source of bugs[47]. The cost of the safer default is an exception check after each call; a noexcept declaration is still appropriate for small, pure-C helpers such as the escape() function in Section 9[15].

Later 3.x releases built on that base. Cython 3.1 (May 2025) added support for the free-threaded build of CPython 3.13 and removed support for Python 2.7–3.7; 3.2 (November 2025) implemented PEP 701 f-strings and PEP 750 template strings; and 3.3 (August 2026) implemented match statements (PEP 634) and except*, and dropped Python 3.8[7].

13Pitfalls

  1. Typing too little, in the wrong place. One untyped variable in a hot loop keeps the whole loop on the Python object path. The annotation report (Section 6) shows this immediately; the Cython documentation names forgetting to type a critical loop variable as an easy way to "kill performance"[18].
  2. Typing too much. The same page warns against typing "everything in sight": unnecessary declarations add type checks and conversions, and an argument typed as list rejects tuples that a Python function would accept[18].
  3. Silent C semantics. Overflow, C division (with cdivision) and unchecked indexing (with boundscheck=False) produce wrong answers or crashes rather than exceptions (Section 11).
  4. Swallowed exceptions. A noexcept function, or legacy code built with legacy_implicit_noexcept, prints and drops exceptions (Section 12)[47].
  5. Touching Python objects without the GIL. The compiler catches this, which is far better than a crash at run time:
  1. Stale builds. A compiled module.so shadows module.py (Section 4), and cythonize only recompiles when a source is newer than its C file. If an edit seems to have no effect, check module.__file__ and force a rebuild with cythonize -f[9].
  2. Memoryview type mismatches. double[::1] accepts only C-contiguous float64 data (Section 8); convert at the boundary rather than weakening the type inside a hot loop.
  3. Binary distribution. An extension module is built for one Python version, operating system and CPU architecture. Publishing a package means building a wheel for each combination, which tools such as cibuildwheel automate on CI services[48]. Building against CPython's Limited API produces one abi3 wheel that works across Python versions, at some cost in speed[10,49].
  4. Debugging. A segmentation fault in compiled code has no Python traceback. Re-enable boundscheck and wraparound first; then use python -X faulthandler to get the Python-level stack, or cygdb, Cython's extension to GDB[50,51].

14Cython and the alternatives

Cython sits between writing C by hand and not writing C at all. A rough guide to the neighbouring tools:

ToolApproachTypical fit
CPython C APIHand-written C against Python.hMaximum control; most code and the most ways to get reference counting wrong[3]. Covered in this series' C extensions article.
CythonCompile Python-like code with optional C types to an extensionSpeeding up loops in existing Python code; wrapping C and C++ libraries.
ctypesStandard-library FFI; loads a shared library at run timeCalling a few functions in an existing library with no compile step[52].
CFFIFFI driven by C declarations, in ABI or API modeWrapping C libraries, also on PyPy[53].
pybind11C++11 header library for writing bindingsExposing existing C++ code with classes and templates[54].
NumbaJIT compiler for a NumPy-oriented subset of Python, via LLVMNumeric kernels without a build step[55].
mypycCompiles type-annotated Python with mypy's type checkerSpeeding up ordinary, fully annotated application code[56].

Cython's distinctive strengths are that it starts from valid Python, lets you add C types gradually where the profiler points, and treats C and C++ libraries as first-class citizens. That combination has made it a workhorse of the scientific Python ecosystem; scikit-learn, for example, keeps a chapter of its developer guide on Cython conventions for its own compiled modules[57].

Exercise 2. Find the swallowed exception easy

This module was ported from Cython 0.29 by adding noexcept everywhere "to keep the old behaviour". Explain what mean_sqrt([4, -1, 9]) returns and why, then fix it so the ValueError reaches the caller.

Show solution

With noexcept, Cython cannot report the exception to the caller: it prints it as "ignored" and the function returns 0.0, so the mean is (2 + 0 + 3) / 3. Removing noexcept gives the Cython 3 default, in which a double-returning cdef function propagates exceptions (Cython checks for an error after each call)[15,47].

Exercise 3. One file, two worlds medium

Write collatz.py in pure Python mode: a function longest(limit) that returns the starting number below limit with the longest Collatz chain (n → n/2 if even, 3n+1 if odd, until 1) and its number of steps. It must run unmodified in CPython and also compile with Cython. Run it both ways for limit = 300_000 and compare the time.

Show solution

The intermediate values exceed 231 for some starting points below 300,000, so n needs a 64-bit type (cython.longlong); a C int would overflow silently.

Exercise 4. Matrix–vector product with 2-D memoryviews medium

Write matvec(A, x) taking a C-contiguous 2-D float64 array and a 1-D vector, returning A @ x as a new NumPy array. Raise ValueError on mismatched shapes. Compare the result and speed with NumPy's @.

Show solution

The point of this exercise is the honest comparison: a simple loop compiles to fast C, but NumPy's @ calls an optimised BLAS library, so it is usually as fast or faster. Write Cython for the loops NumPy cannot express, not for the ones it already does well.

Exercise 5. Threads that really run in parallel hard

Exercise 6. Sort with the C library's qsort hard
