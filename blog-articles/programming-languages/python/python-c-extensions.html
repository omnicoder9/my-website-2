1Why write a C extension?

An extension module is a shared library that the CPython interpreter imports just like a .py file. Such modules "can do what Python code does – define functions, object types and methods – but also interact with native libraries or achieve better performance by avoiding the overhead of an interpreter"[1]. The Python Packaging User Guide sorts them into three use cases[2]:

  • Accelerator modules: self-contained modules "created solely to run faster", ideally with a pure-Python fallback.
  • Wrapper modules: modules that expose an existing C interface (a compression library, a GPU driver, a database client) to Python code.
  • Low-level system access: modules that reach CPython internals, the operating system or hardware. When such code does not need to call back into the interpreter, it can release the global interpreter lock (GIL) around long-running work[2], which is one way to get real parallelism from threads (section 8).

There are real costs too. Binary extensions must be compiled for every platform you support, users either need a compiler or a pre-built wheel, they "often will not work correctly with alternative interpreters such as PyPy", and the hand-written kind demands fluency in C as well as in the CPython C API[2]. The CPython documentation adds that the C extension interface is specific to CPython, and that if all you want is to call C library functions or system calls you should consider ctypes or cffi instead[1]. It also lists third-party tools (Cython, cffi, HPy, nanobind, Numba, pybind11, PyO3 and SWIG) that can "help avoid writing code that is tightly bound to a particular version of CPython, avoid reference counting errors, and focus more on your own code"[3].

So why learn the raw C API at all? Because every one of those tools generates or wraps it. Knowing what a reference count is, what a borrowed reference is, and why a function returns NULL is what lets you read a crash dump, review a pull request on a binding, or decide which tool fits. This article writes everything by hand first, then compares the alternatives in section 11.

A script copied it to a scratch folder, created a fresh virtual environment, and ran the commands you see in the Terminal panels, so every transcript is the real output of pip install plus a test script. 2The object model: PyObject, reference counts and errors

Everything is a PyObject*

Almost every C API function takes or returns PyObject*, "a pointer to an opaque data type representing an arbitrary Python object"[3]. All object types are extensions of PyObject: in a normal release build it holds just the object's reference count (ob_refcnt) and a pointer to its type (ob_type), and "every pointer to a Python object can be cast to a PyObject*"[4]. When you define your own type you start its struct with the PyObject_HEAD macro, which expands to a PyObject ob_base; member[4]. You should not touch the fields directly; use Py_REFCNT, Py_TYPE, Py_INCREF and friends[4].

Reference counting and ownership

All Python objects have a type and a reference count, which "counts how many different places there are that have a strong reference to an object". When the last strong reference is released, the count reaches zero and the object is deallocated[3]. CPython has a tracing garbage collector only for cycles; everything else depends on C code getting the counts exactly right. The documentation frames this as ownership of references[3]:

KindMeaningTypical functionsYour obligation
New referenceOwnership passes to the callerPyLong_FromLong, PySequence_GetItem, PyObject_GetIter, all PyObject_*/PyNumber_* genericsCall Py_DECREF exactly once, or hand it on (for example by returning it)
Borrowed referenceNo ownership transferredPyList_GetItem, PyTuple_GetItem, arguments passed to your functionNothing, but don't use it after its owner may have dropped it; take a reference with Py_NewRef if you need to keep it
Stolen referenceThe callee takes over a reference you ownedPyList_SetItem, PyTuple_SetItem (and the _SET_ITEM macros)Don't Py_DECREF it afterwards

The documentation's own example of the trap: "if you extract an item from a list using PyList_GetItem(), you don't own the reference — but if you obtain the same item from the same list using PySequence_GetItem() (which happens to take exactly the same arguments), you do own a reference to the returned object"[3]. It recommends the generic PyObject_, PyNumber_, PySequence_ and PyMapping_ operations as the safe default because they always return a new strong reference[3]. Only "few functions steal references", the two notable ones being PyList_SetItem() and PyTuple_SetItem()[3]. The ownership rules are walked through in more depth in the extending guide[5].

The error convention

"An important convention throughout the Python interpreter is the following: when a function fails, it should set an exception condition and return an error value (usually -1 or a NULL pointer)"[5]. The exception state is stored per thread; PyErr_Occurred() tells you whether one is set[3]. When a function you called fails, the rule is to "discard any object references that it owns, and return an error indicator, but it should not set another exception", because that would overwrite the original cause[3]. A few functions have return values that are ambiguous (PyFloat_AsDouble returns -1.0 both as a value and on failure) and then you must check PyErr_Occurred() explicitly[3,6].

3A first module

Here is a complete extension module, hello, with one function. It uses multi-phase initialisation, the design from PEP 489 that brings "extension modules closer to the way Python modules behave"[7]: the import system creates the module object itself and then runs your exec slot on it, rather than your code building and returning a finished module in one go[8].

Walking through it from the top:

  • #define PY_SSIZE_T_CLEAN then #include <Python.h>. Python.h must come before any standard header because it may set preprocessor definitions that affect them, and defining PY_SSIZE_T_CLEAN first is recommended[3].
  • The function. Its C signature is fixed by the METH_O flag: the module (or self) plus exactly one argument object[4]. On bad input it sets a TypeError and returns NULL. %T in PyErr_Format/PyUnicode_FromFormat formats the fully qualified type name of an object and was added in 3.13; %U inserts a str object[9].
  • PyMethodDef table. Each entry gives the Python name, the C function, the calling-convention flags and a docstring; an entry with a NULL name ends the array[4]. A docstring that starts with name(sig)\n--\n\n also gives the function a __text_signature__, which you can see in the transcript below.
  • Slots. Py_mod_exec runs after the module object exists and "typically ... adds classes and constants to the module"[10]. Py_mod_multiple_interpreters (3.12+) declares whether the module may be imported in sub-interpreters, even ones with their own GIL[10]. Py_mod_gil (3.13+) declares that the module is safe without the GIL; it is ignored on regular builds and matters on free-threaded ones (section 10)[10].
  • PyModuleDef. m_size = 0 means no per-module state; a positive size reserves memory you get with PyModule_GetState(), while -1 (only allowed with legacy single-phase init) means the module has global state and does not support sub-interpreters[10].
  • PyInit_hello. The import system finds the module by looking for an exported function named PyInit_<name>[8]. With multi-phase init it just returns the definition through PyModuleDef_Init(), which "is required before returning a PyModuleDef from a module initialization function"[8].

To build it, a pyproject.toml names the build backend, and a three-line setup.py declares the extension. The name passed to Extension is the import name, and it has to match the PyInit_ suffix[11].

pip install . invoked setuptools in an isolated build environment, compiled hello.c with the compiler flags Python itself was built with, and installed hello.cpython-313-x86_64-linux-gnu.so into the virtual environment. The filename suffix encodes the interpreter version and platform, which is why binary wheels have to be built per Python version unless you use the stable ABI (section 9).

4Working with objects safely

The next module, stats, computes the mean of any iterable. It shows the pattern you will write again and again: call an API function, check for failure, release every new reference on every path.

Points to notice:

  • PyObject_GetIter and PyIter_Next both return new references, so item is released as soon as it has been converted, and it is released on every exit path.
  • PyIter_Next returns NULL both at the end of iteration (no exception set) and on error (exception set)[12], so after the loop the code asks PyErr_Occurred() which one it was.
  • PyFloat_AsDouble accepts anything with __float__ (falling back to __index__) and returns -1.0 on failure[6], which is why Fraction and True work below and why the check is x == -1.0 && PyErr_Occurred().
  • Py_NewRef(obj) increments the count and returns the object, a compact way to say "I am handing you a new reference".

Exceptions raised deep inside (the TypeError from converting "two", or the one from PyObject_GetIter(42)) reach Python intact because the C code passes them on instead of replacing them. The last two lines show a reference leak made visible: sys.getrefcount is "generally one higher than you might expect" because its own argument counts[13], but what matters is the trend. After 1,000 calls the correct function leaves the count unchanged, while the leaky one has added 1,000 references that will never be released, so that object can never be freed. The same documentation warns not to trust the absolute number for immortal objects such as small integers and None[13], which is why the demo uses a fresh object().

5Parsing arguments and building results

For anything beyond one argument you choose a calling convention in the PyMethodDef flags[4]:

FlagsC signature receivesUse for
METH_NOARGSself, NULLNo arguments
METH_Oself, one objectExactly one positional argument
METH_VARARGSself, a tuplePositional arguments, parsed with PyArg_ParseTuple
METH_VARARGS | METH_KEYWORDSself, tuple, dict or NULLKeyword support via PyArg_ParseTupleAndKeywords
METH_FASTCALLself, a C array of PyObject*, a countFast positional calls with no tuple allocation (stable ABI since 3.10)

PyArg_ParseTuple and PyArg_ParseTupleAndKeywords take a format string of format units. In "U|n$U:repeat", U requires a str without conversion, n converts to Py_ssize_t, | makes the rest optional (and the C variables must be pre-set to their defaults, since they are left untouched when the argument is missing), $ makes the rest keyword-only, and the text after : is the function name used in error messages[14]. Objects you receive this way are borrowed, so you must not release them[14]. In the other direction, Py_BuildValue builds results: its O unit adds a new reference to the object, while N takes over one you already own[14].

Two details are worth a second look. PyList_SET_ITEM steals a reference, so the loop gives it one with Py_NewRef(text); without that, the list would later release references it never owned. And result from PyUnicode_Join may be NULL, which is returned as-is after the cleanup: the error simply propagates. The cast to (PyCFunction)(void (*)(void)) is the conventional way to store a function with a different signature in ml_meth without a compiler warning.

All of those error messages were generated by the C API from the format string and the kwlist, including "takes at most 2 positional arguments" for the keyword-only sep.

6Defining a new type

Built-in types such as list are static types: C structs that live for the whole process. The modern recommendation for extension types is the heap type, created at import time from a PyType_Spec, because static types "are immutable and process-global" and cannot reach "their" module state; "for new modules, using heap types by default is a good rule of thumb"[15]. PyType_FromModuleAndSpec() builds the type and associates it with the module[15,16], and type behaviour is supplied as an array of slots named after PyTypeObject fields with a Py_ prefix, such as Py_tp_dealloc and Py_nb_add[16].

The geometry module below defines an immutable-type Vec2 with two double fields, a constructor with keyword arguments, attribute access, a method, repr and +.

The pieces that are easy to get wrong:

  • Module state, not globals. The type object is stored in per-module state (m_size = sizeof(geometry_state)) rather than a static variable, so that each interpreter that imports the module gets its own copy[15]. m_traverse, m_clear and m_free let the garbage collector see and release that reference[10].
  • Finding the state from a slot. A slot function like nb_add gets no module argument. PyType_GetModuleByDef() (3.11+) walks the type's MRO to find the module created from our PyModuleDef and returns a borrowed reference[15,16].
  • Members. PyMemberDef maps attributes straight to struct fields. The Py_T_DOUBLE spelling and its siblings became available from Python.h in 3.12; older code includes structmember.h and uses T_DOUBLE[4].
  • Deallocation. Instances of a heap type own a reference to their type, so tp_dealloc must release it after freeing the object[17].
  • Garbage-collection support. "To avoid memory leaks, instances of heap types must implement the garbage collection protocol": set Py_TPFLAGS_HAVE_GC, visit the type in tp_traverse, and call PyObject_GC_UnTrack() first thing in tp_dealloc[15]. The reason is that "they can form a reference cycle with their own module object"[17]. The demo below builds exactly that cycle by storing an instance on the module; with the flag and traverse function removed, the same script printed module freed by the cyclic GC: False when we tried it.
  • Immutability. Heap types are mutable by default; Py_TPFLAGS_IMMUTABLETYPE makes them behave like built-in classes[15].

Returning Py_NotImplemented from nb_add is what makes a + 1 produce Python's normal "unsupported operand type(s)" error instead of a crash or a confusing message.

7Building and packaging

Everything above used the same pattern: a pyproject.toml whose [build-system] table selects setuptools, and a setup.py whose ext_modules keyword is "a list of instances of the setuptools.Extension class", each with a name and a list of sources[11]. Everything else in the project metadata stays in pyproject.toml. Setuptools can also read extension modules from a [tool.setuptools] ext-modules table in pyproject.toml, but that declarative form "is still considered experimental"[11], so this article keeps the small setup.py.

Useful Extension arguments include include_dirs, libraries and library_dirs for wrapping an external library, define_macros, and extra_compile_args. The compiler command line is assembled from CFLAGS/CPPFLAGS in the environment first, then Python's own shared-library flags, then include directories, then extra_compile_args[11]. We use that in section 10 to switch a macro on with CFLAGS=-D....

The everyday commands are:

CommandWhat it does
python -m pip install .Build in an isolated environment and install into the current one
python -m pip wheel --no-deps -w dist .Build a wheel file only (used in section 9)
python -m buildBuild an sdist and a wheel with the build front end
Stale object files

Setuptools keeps compiled object files in a build/ directory next to your sources and only recompiles a file when the source is newer. Changing only a compiler flag or a macro therefore does not force a rebuild. While preparing section 10, reinstalling with a new -D flag silently reused the old object file until build/ was deleted. When flags change, delete build/ first.

To publish, you build one wheel per platform and per Python version (or one per platform for the stable ABI, see section 9), usually in CI. Tools such as cibuildwheel exist for that job; the Packaging User Guide's page on binary extensions is the place to start[2].

8The GIL and releasing it

On a regular CPython build, "only a thread that holds the GIL may operate on Python objects or invoke Python's C API"[18]. Your C function is called with the GIL held, so while it runs, no other Python thread can. For long-running native code that does not touch Python objects, you can detach the thread state and let other threads run; the standard zlib and hashlib modules do exactly that while compressing or hashing[18]. The macros are:

  • Py_BEGIN_ALLOW_THREADS, which expands to { PyThreadState *_save; _save = PyEval_SaveThread(); (note the opening brace)[18];
  • Py_END_ALLOW_THREADS, which expands to PyEval_RestoreThread(_save); }[18].

Between them you must not call any Python C API function, not even Py_INCREF. The pattern is: extract everything you need into C variables, release, compute, re-acquire, build the result.

On this 4-CPU machine, four threads calling the GIL-holding version took four times as long as one call: they simply queued for the lock. The GIL-releasing version ran them in parallel for a 3.9× speed-up. (Timings vary from run to run; the shape of the result does not.)

9The Limited API and the stable ABI

A normal extension is compiled against one minor version of CPython, because the C API exposes struct layouts and macros that may change between 3.12 and 3.13. PEP 384 defined a stable ABI: extensions that restrict themselves to it "can work with different feature releases"[19]. In the current documentation's terms, the Limited API is the subset of the C API an extension may use, and the Stable ABI is the binary interface that results; "an extension compiled for Stable ABI 3.x is ABI-compatible with Python 3.x and above"[20]. You opt in by defining Py_LIMITED_API to the oldest version you support, in hex (0x030B0000 is 3.11), before including Python.h[20].

On the setuptools side, Extension(..., py_limited_api=True) and the wheel tag are configured separately: the second needs the bdist_wheel option py_limited_api set to the minimum tag, such as cp311[11].

One wheel, tagged cp311-abi3, containing sumsq.abi3.so, imported and ran unchanged on CPython 3.12, 3.13 and 3.14. The price is that macros which reach into structs (PyList_GET_ITEM, PySequence_Fast_ITEMS) and newer functions are unavailable, so code like sumsq uses PySequence_GetItem instead. The documentation also warns that ABI compatibility is not behavioural compatibility, so you should still test on every version you claim[20]. Exercise 5 ports the stats module and shows the compiler error you get when a feature is newer than your Py_LIMITED_API target.

The API tiers

Besides the Limited API there is an unstable tier whose names start with PyUnstable; it may change in any minor release without deprecation. Names that start with an underscore are private and can change even in patch releases[20].

10Free-threaded Python

PEP 703 added a build configuration, --disable-gil, that removes the GIL so threads can run Python code in parallel[21]. It shipped as an experimental build in 3.13[22], and PEP 779 set the criteria under which 3.14 makes it "officially supported but still optional"[23]. The interpreter is a separate binary (usually python3.13t), and its ABI differs: free-threaded builds are "not ... ABI compatible with the standard CPython build or with the stable ABI", so extensions must be rebuilt for them, and their tags carry a t[21,24]. You can detect the build from C with the Py_GIL_DISABLED macro[24], and from Python with sysconfig.get_config_var("Py_GIL_DISABLED") and sys._is_gil_enabled()[13,22]. The cost on single-threaded code is about 1% on macOS aarch64 up to 8% on x86-64 Linux on the pyperformance suite[22].

What makes this an extension-author's problem is the Py_mod_gil slot. If a module does not declare Py_MOD_GIL_NOT_USED, the default is Py_MOD_GIL_USED[10], and importing it on a free-threaded build re-enables the GIL for the whole process and prints a warning[22,24]. The declaration is a promise that your code protects its own shared state. The module below keeps two global counters, one updated without synchronisation and one under a PyMutex, a mutex type that became public in 3.13, takes one byte today, must be zero-initialised and must never be copied[25]. The slot is compiled in only when DECLARE_NO_GIL is defined.

The transcript shows both halves of the story:

  1. Built without the slot, the import re-enabled the GIL with a RuntimeWarning. The program was correct but ran single-file, and both totals were right.
  2. Built with the slot (note the rm -rf build, see section 7), the GIL stayed off and the threads really ran in parallel. The mutex-protected counter is still exactly 8,000,000; the unprotected one lost more than half of its updates (about 4.7 million) to the data race. The volatile qualifier forces a separate load and store per iteration, standing in for any read-modify-write of shared state.

The free-threading HOWTO lists the other changes to check before you add the slot[24]:

  • Borrowed references from containers another thread may be mutating are unsafe; use the strong-reference variants, for example PyList_GetItemRef() instead of PyList_GetItem() and PyDict_GetItemRef() instead of PyDict_GetItem().
  • Memory domains: only Python objects may be allocated with PyObject_Malloc; use PyMem_Malloc for plain buffers.
  • Keep releasing the thread state with Py_BEGIN_ALLOW_THREADS around blocking calls even without a GIL, so other threads can run the cyclic garbage collector.
  • Protect per-object state with critical sections (Py_BEGIN_CRITICAL_SECTION(obj)), which lock one or two objects and are no-ops on GIL builds[25], and guard caches and globals with a PyMutex or move them to thread-local storage.
  • No Limited API: the free-threaded build "does not currently support the Limited C API or the stable ABI"; with setuptools you can write py_limited_api=not sysconfig.get_config_var("Py_GIL_DISABLED")[24].

For older Pythons, wrap the slot in #if PY_VERSION_HEX >= 0x030D0000; modules that still use single-phase init call PyUnstable_Module_SetGIL() instead[24].

11Alternatives to the raw C API

Writing directly against the C API gives total control and no dependencies, at the cost of the bookkeeping you have seen. The CPython documentation itself points you to other tools first[1,3]. To compare them fairly, the examples below wrap the same tiny C library, which knows nothing about Python:

ctypes (standard library)

ctypes "provides C compatible data types, and allows calling functions in DLLs or shared libraries"[26]. No compiler is needed for the binding itself, but ctypes cannot read the header: functions are assumed to return int unless you set restype, and without argtypes "the number of arguments is not checked", and a wrong call "can corrupt memory or crash Python"[26].

cffi

cffi parses C declarations that you paste in. Its ABI mode (used here) loads the library at run time, while API mode compiles a small C module; the cffi documentation "highly recommend[s]" API mode when a compiler is available, notes that it is faster at run time, and warns that ABI mode "will crash if you call some function or access some fields of a structure that was slightly misdeclared"[27].

pybind11 and nanobind (C++)

pybind11 is "a lightweight header-only library that exposes C++ types in Python and vice versa", aimed at wrapping existing C++ code and modelled on Boost.Python[28]. Type conversion, overloads, exceptions (a C++ std::invalid_argument becomes ValueError) and reference counting are handled by templates. The py::mod_gil_not_used() tag is pybind11's way to set the Py_mod_gil slot.

nanobind is a newer library by pybind11's original author. It keeps most of pybind11's conventions but targets a smaller C++ subset; its documentation reports, for example, 24 bytes per bound instance instead of pybind11's 56, support for the stable ABI from Python 3.12, and a localised locking scheme for free-threaded builds[29]. Cython and others

Cython is "a programming language that makes writing C extensions for the Python language as easy as Python itself": Python-like source with optional C type declarations, translated into C and compiled into an extension module[30]. It is the most common route for accelerating existing Python code and has its own article in this series, so we leave it there. The CPython documentation's list also includes HPy, Numba, PyO3 (Rust) and SWIG[3].

12Debugging extensions

A bug in C rarely produces a tidy traceback. The usual result is a segmentation fault. This module has the single most common C API bug: it ignores a NULL return.

Three runs, three levels of information:

  1. Plain run. The process dies with exit status 139 (128 + signal 11, SIGSEGV) and says nothing useful.
  2. -X faulthandler. faulthandler installs handlers for SIGSEGV, SIGFPE, SIGABRT, SIGBUS and SIGILL and dumps the Python traceback on a crash; it can also be switched on with PYTHONFAULTHANDLER or faulthandler.enable()[31]. Now we know the Python line (crash.py, line 5) and which extension modules were loaded.
  3. gdb. Running the interpreter under gdb gives the C stack: Py_INCREF(op=0x0), called from buggy_third at buggy.c:11. That needs debug information for your extension (hence -g -O0); CPython also ships a python-gdb.py extension that adds py-bt, py-list, py-print and py-up/py-down to inspect Python frames from gdb, which needs debug information for Python itself (for example a distribution's python3-dbg package)[32].

Other tools worth knowing:

  • Python Development Mode (-X dev or PYTHONDEVMODE=1) enables faulthandler and installs debug hooks on the memory allocators that detect buffer overflows and underflows, allocator API violations and unsafe use of the GIL[33].
  • A debug build of CPython enables extra interpreter checks that are too slow for release builds[3], and is what the GDB guide recommends for serious debugging[32].
  • Reference-count tests, like the sys.getrefcount loop in section 4 and exercise 2, catch leaks on both success and error paths.
  • faulthandler in 3.14 can also print the C stack (c_stack=True, faulthandler.dump_c_stack()) where the platform supports it[31].

14Looking ahead: 3.14 and 3.15

The code in this article targets CPython 3.13 and keeps working on later versions, but the C API keeps evolving. Some changes you will see in newer documentation:

  • PyIter_NextItem() (3.14) returns 1, 0 or -1, so end-of-iteration and errors no longer share a NULL return; the documentation now prefers it to PyIter_Next()[12].
  • Free threading becomes a supported (still optional) build in 3.14[23].
  • A new export hook. 3.15 adds PyModExport_<name>, which returns an array of slots; PyInit_<name> remains supported, and if a module exports both, PyInit is ignored. Single-phase initialisation is soft-deprecated from 3.15, though there are no plans to remove it[8].
  • Slot-based type creation. 3.15 soft-deprecates PyType_FromModuleAndSpec() in favour of PyType_FromSlots()[16].
  • abi3t. 3.15 introduces a stable ABI for free-threaded builds, with stricter limits than abi3; free-threaded interpreters only load abi3t files[20].

Soft deprecation means no new features and no planned removal, so the 3.13-style code above is not on a countdown. The binding tools in section 11 tend to adopt such changes for you, which is one more argument for them in large projects[3].

1. clamp()warm-up

2. A leak-free dot productcore

Write vecops.dot(a, b, /) for two sequences of numbers of equal length, using METH_FASTCALL. Raise ValueError on a length mismatch and let conversion errors propagate. Then prove with sys.getrefcount that neither the success path nor the error path leaks.

Show solution

PySequence_Fast returns a list or tuple (a new reference) whose items can be read through a C array of borrowed pointers. A single done: label releases both sequences on every path.

3. Fix the crashcore

Fix buggy.third() from section 12 so that a short list raises IndexError instead of crashing. As a bonus, make it work for any sequence (tuples, strings), not just lists.

Show solution

The minimal fix is if (item == NULL) return NULL; before Py_NewRef. The better fix uses PySequence_GetItem, which accepts any sequence and already returns a new reference, so the function shrinks to one line[3]. (On a free-threaded build it also avoids the borrowed-reference problem described in section 10[24].)

4. Extend Vec2core

5. Port stats to the Limited APIstretch

Take stats.mean from section 4, define Py_LIMITED_API as 0x030C0000 (3.12), and build a single abi3 wheel that works on 3.12, 3.13 and 3.14. What fails to compile, and why?

Show solution

Py_mod_gil was added in 3.13[10], so a 3.12 Limited API target does not define it. Because it is a preprocessor macro, #ifdef Py_mod_gil keeps the slot for anyone who compiles against the 3.13+ Limited API and drops it otherwise. Everything else in mean (PyObject_GetIter, PyIter_Next, PyFloat_AsDouble, Py_NewRef) is in the stable ABI. Remember that an abi3 wheel cannot be used on a free-threaded build[24]. In the transcript, stats_first_try.c is the same file without the #ifdef guard.

6. Release the GIL around real workstretch

Write primes.count_primes(iterable_of_ints) that counts how many of the numbers are prime, and make four threads each running it on a different chunk run in parallel. Why can't you simply wrap the whole function body in Py_BEGIN_ALLOW_THREADS?

Show solution

Converting Python ints and allocating the result are C API calls and need the GIL[18]. So the function works in three phases: copy the values into a C buffer (allocated with PyMem_New, the right domain for non-object memory[24]), release the GIL for the primality tests, then re-acquire it to free the buffer and build the result.
