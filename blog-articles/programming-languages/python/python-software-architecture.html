1What architecture means

Bass, Clements and Kazman define the software architecture of a system as the set of structures needed to reason about it: software elements, the relations among them, and the properties of both[1]. Fowler, following Ralph Johnson, puts it more informally: architecture is the shared understanding that expert developers have of a system’s design, and it is “about the important stuff. Whatever that is”, which in practice tends to mean the parts that are hard to change later[2].

The common thread is decomposition: how a system is split into parts and which parts are allowed to know about which. Parnas argued in 1972 that modules should be chosen so that each one hides a design decision that is likely to change, rather than by following the steps of a flowchart[3]. Every style in this article is a different answer to that question at a different scale.

StyleUnit of decompositionMain question it answersSection
MVCRoles in a user interfaceHow do I keep display and input handling apart from the data being shown?2
LayeredHorizontal tiers of responsibilityWhich code may call which, and how do I keep business rules free of HTTP and SQL?3
Event-drivenProducers and consumers of eventsHow can parts react to a change without the source knowing who they are?4
MicroservicesIndependently deployable servicesHow can teams build, deploy and scale parts of a system separately?5
DDDBounded contexts and aggregatesHow do I model a complicated business domain so the code speaks its language?6

These are not rival choices. A typical Django or Flask service is MVC-shaped at the edge, layered inside, publishes events, may be one of several microservices, and may use DDD patterns for its core. The examples use only the standard library so that each one runs on its own, and they share one small domain (a shop selling coffee beans) so the styles are easy to compare.

2Model–View–Controller

2.1 Origins and the three roles

Trygve Reenskaug wrote the first technical note defining the terms model, view and controller for user-interface design at Xerox PARC, dated 10 December 1979[4]. The idea was developed in Smalltalk-80, and Krasner and Pope’s 1988 “cookbook” became the standard description of how to use it there[5]. Fowler’s catalog summarises MVC as splitting user-interface interaction into three distinct roles[6]:

  • Model: domain objects and their rules. In Fowler’s words, “Model objects are completely ignorant of the UI”[7].
  • View: displays the model’s state.
  • Controller: takes the user’s input and works out what to do with it, usually by calling the model[7].

Fowler calls MVC both the most quoted and the most misquoted pattern in UI development, and argues that it is really a bundle of ideas[7]. Two of them matter most. Separated presentation keeps domain objects independent of the screen, so one model can support several presentations. Observer synchronization means views observe the model: a controller changes the model and does not update the view directly, and the model’s change notification refreshes every view that depends on it[7].

Fowler warns about the cost: observer behaviour is implicit, so you cannot follow the flow just by reading the controller, and debugging it can mean stepping through notifications one by one[7].

2.3 MVC on the web: Django and Flask

Server-side web frameworks adapted MVC to the request–response cycle, where there is no long-lived view to observe the model. Django’s FAQ explains its own naming: a Django view is the Python callback for a URL and describes which data is presented; it normally delegates to a template, which describes how the data is presented; and the “controller” is probably the framework itself, the machinery that sends a request to the right view according to the URL configuration. Hence “MTV”: model, template, view[8].

Flask takes no position at all. Its documentation says the “micro” in microframework means keeping the core simple but extensible; Flask won’t make many decisions for you, such as which database to use, and as the codebase grows you are free to make the design decisions appropriate for your project[9]. For larger applications it offers blueprints, which let you factor an application into a set of components that are registered on the application object[10].

2.4 Where MVC goes wrong

  • Fat controllers. MVC says nothing about where business rules go once there is more than one screen. Putting them in request handlers duplicates them across endpoints. The usual fix is a service layer and a domain model behind the controller, which is the subject of the next section.
  • Models that know about the UI. As soon as a model formats HTML or reads a request object, separated presentation is lost and the model can no longer serve a second presentation[7].
  • Treating MVC as the whole architecture. MVC structures the user interface. Fowler uses it as one presentation pattern among several in a layered enterprise application[11].

3Layered architecture

3.1 Presentation, domain and data

One of the most common ways to structure an information-rich program is to divide it into three broad layers[12]:

  • Presentation: handles HTTP requests or other input and renders output.
  • Domain: business logic, validations and calculations.
  • Data source: manages persistent data in a database or remote services.

Dependencies run one way: presentation depends on the domain, which depends on the data source[12]. This layering drives the structure of Fowler’s Patterns of Enterprise Application Architecture[11,12]. Many applications add a service layer between presentation and domain, which his catalog describes as defining an application’s boundary with a layer of services that sets out the available operations and coordinates the response to each one[6]. Percival and Gregory call it the orchestration or use-case layer: it fetches what it needs, calls the domain, and saves the results, while the business rules stay in the domain[13].

The idea is older than business software. Dijkstra described the THE multiprogramming system in 1968 as a hierarchy of levels, each built only on the levels below it[14]. In a strict layering a layer may call only the one directly beneath it; a relaxed layering lets it call any lower layer. Either way, a lower layer never calls upward.

3.2 Inverting the data dependency

Classic layering has an awkward consequence: if the domain depends on the data layer, business rules import SQL code and cannot be tested without a database. A common variation puts a mapping interface between the domain and the data source so that the domain no longer depends on it[12]. Several names describe the same move:

  • Hexagonal architecture (ports and adapters), whose stated intent is to let an application be driven equally by users, programs, automated tests or batch scripts, and be developed and tested in isolation from its eventual run-time devices and databases[15].
  • The clean architecture, whose dependency rule says that source-code dependencies can only point inwards, towards entities and use cases[16].
  • The repository pattern, an abstraction over persistent storage that makes it look like an in-memory collection[6,13].

In Python the “port” is most naturally a typing.Protocol. Protocols give structural subtyping (static duck typing): a class satisfies the protocol by having the right methods, without inheriting from it[17,18]. The domain layer defines the protocol; the data layer implements it.

The same use case, transfer, runs unchanged against an in-memory adapter and an SQLite adapter. The in-memory version is what makes the service layer cheap to unit-test, which is the main practical benefit Percival and Gregory claim for the pattern[13]. The SQLite adapter binds values with ? placeholders, as the sqlite3 documentation instructs, to avoid SQL injection[19].

What this example leaves out

If the second save failed, the first would already be written. Production code wraps a use case in a single transaction, usually with a Unit of Work, which keeps track of everything a business transaction changes and writes the changes out together[6].

3.3 When layers should not be the top level

Layering suits small and medium applications, but Fowler advises against making it the top-level structure of a large one: once a layer grows too big, split the top level into domain-oriented modules, each of which is layered inside[12]. In Python terms, prefer shop/orders/{views,services,model,repository}.py and shop/billing/… over one giant views/, services/ and models/ package each. Those domain modules are natural candidates for bounded contexts (section 6) and, later, for separate services (section 5). Exercise 2 builds a small checker that enforces layer rules from import statements.

4Event-driven architecture

4.1 Events and the four patterns

An event is a record that something has happened, named in the language of the domain: OrderPlaced, not CallInventoryService. Hohpe and Woolf’s Event Message pattern uses messaging for reliable, asynchronous event notification between applications[20,21], and their Publish-Subscribe Channel delivers a copy of each event to every interested receiver[22]. The publisher does not know who is listening.

Fowler points out that “event-driven” is used for at least four different patterns, and that mixing them up causes confusion[23]:

PatternWhat the event carriesMain trade-off
Event notificationJust enough to say something changed; the sender does not expect a replyLow coupling, but the overall flow is not visible in any one place in the code[23]
Event-carried state transferThe changed data, so receivers can keep their own copyBetter resilience and latency, at the price of duplicated data and more work for receivers[23]
Event sourcingEvery state change, stored as the system of recordFull history and replay, but a different way of storing and querying state[23,24]
CQRSNot necessarily events; separate models for writing and readingUseful in some complex domains, but adds risky complexity to most systems[23,25]

4.2 An in-process message bus

Events are useful inside a single process too. Percival and Gregory’s message bus is a dictionary that maps event types to lists of handler functions; the domain model records events, and the bus dispatches them, so that, for example, the code that allocates stock does not also have to send email[13]. The version below follows that design. Handlers may return follow-up events, and the bus processes them in order from a queue.

Adding the audit trail did not change any existing handler, which is the point. Django ships a similar mechanism, signals, which let decoupled applications be notified when actions occur elsewhere. Its documentation is candid about the cost: signals give the appearance of loose coupling but can quickly lead to code that is hard to understand, adjust and debug, so where possible you should call the handling code directly[26]. The same advice applies to a home-made bus.

4.3 Asynchronous consumers, duplicates and dead letters

Once events cross a process boundary through a broker, two problems appear. First, a receiver may get the same message more than once, so it should be an Idempotent Receiver that can safely process the same message multiple times[27]. Second, some messages can never be processed; rather than block the queue, the system can move them to a Dead Letter Channel[28].

The example below simulates a broker with asyncio.Queue, which is designed for distributing work between concurrent tasks in async code (it is not thread-safe)[29]. Two consumers share the queue. queue.join() returns once every item has been marked done with task_done()[29].

4.4 Event sourcing and CQRS

Event sourcing stores every change to application state as a sequence of events. The current state can be rebuilt by replaying the log from empty, and the state at any earlier point can be found by replaying only the events up to that point[24]. If apply is a pure function from (state, event) to state, a rebuild is just functools.reduce. A projection reads the same log to build a separate model shaped for one kind of query, which is the CQRS idea of using a different model to read information from the one used to update it[25].

Real event stores add snapshots so a rebuild does not replay the whole history every time; Exercise 5 shows that a snapshot plus the later events gives the same answer as a full replay.

4.5 The costs

  • Hidden flow. Fowler notes that with event notification the logical flow often can only be discovered by monitoring a live system[23]. Percival and Gregory list the same cost for their message bus[13].
  • Eventual consistency. With state transfer, receivers hold copies that lag behind the source[23].
  • Duplicates and poison messages, handled above with idempotent receivers and dead letters[27,28].

5Microservices

5.1 A definition

Lewis and Fowler describe the microservice architectural style as building a single application as a suite of small services, each running in its own process and communicating through lightweight mechanisms, often an HTTP resource API. The services are built around business capabilities, are independently deployable by fully automated machinery, have a bare minimum of centralised management, and may use different languages and data stores[30]. They list nine common characteristics[30]:

  1. Componentization via services
  2. Organized around business capabilities
  3. Products not projects
  4. Smart endpoints and dumb pipes
  5. Decentralized governance
  6. Decentralized data management
  7. Infrastructure automation
  8. Design for failure
  9. Evolutionary design

The organisational characteristics are not incidental. Lewis and Fowler quote Conway’s law[30], from Conway’s 1968 paper: organisations which design systems are constrained to produce designs which are copies of their own communication structures[31]. Splitting services by business capability (ordering, inventory, billing) rather than by technical layer is a way of using that law deliberately. Percival and Gregory make the same point in Python terms: think in terms of verbs, not nouns, because a service per database table with CRUD endpoints can quickly degrade into a “distributed ball of mud”[13].

5.2 Two services in one file

The next example runs two services in one Python process so that it can be executed anywhere. The inventory service owns its stock data and exposes it only over HTTP; the order service is a client. Each server listens on a free port (port 0) in a background thread. Note the two different failures the client handles: an HTTP error means the remote service answered, while an OSError means it did not answer at all.

Not for production

The http.server module is not recommended for production and implements only basic security checks[32]. Real Python services normally run on a WSGI or ASGI server behind a framework such as Flask, Django or FastAPI. The architecture is the same.

5.3 Design for failure: the circuit breaker

Because services can fail at any time, Lewis and Fowler say applications need to be designed to tolerate the failure of services[30]. A remote call that hangs ties up the caller, and its callers in turn. The circuit breaker, popularised by Michael Nygard’s Release It!, wraps a call and counts failures; once they reach a threshold it trips, and further calls fail immediately without the remote call being made. After a timeout it lets a trial call through (the half-open state), and closes again if the trial succeeds[33].

The version below injects a clock so its behaviour can be shown deterministically.

At t=33 the reset timeout has passed, so one trial call is allowed; it fails and the breaker opens again. At t=63 the trial succeeds and the breaker closes. Exercise 6 pairs this with retries and exponential backoff.

5.4 Data: one database per service

Microservices prefer letting each service manage its own database[30]. Richardson’s Database per Service pattern makes it explicit: keep each service’s persistent data private and accessible only through its API. He lists the consequences: business transactions that span several services are not straightforward, and queries that join data across services are hard[34]. Two patterns address the first problem.

  • Transactional outbox. To update the database and publish a message atomically without a distributed transaction, store the message in an outbox table in the same local transaction as the business change, and have a separate process forward it to the broker[35].
  • Saga. A business transaction becomes a sequence of local transactions; if a step fails, earlier steps are undone by compensating transactions. The steps can be coordinated by events (choreography) or by a central orchestrator[36].

The failed order wrote neither a row nor a message, because both inserts were in one with db: transaction. The relay delivers each message at least once: if it crashed after publishing but before marking a row as sent, it would send that row again. That is why consumers need to be idempotent (section 4.3).

5.5 Should you use microservices?

Fowler’s advice is cautious. Microservices add a premium to a project’s cost and risk, so “don’t even consider microservices unless you have a system that’s too complex to manage as a monolith”[37]. He also observes that almost all the successful microservice stories he has heard started with a monolith that grew too big and was broken up, while systems built as microservices from scratch often ended up in serious trouble[38]. A well-modularised monolith, with domain-oriented packages that talk through narrow interfaces and events, keeps the option open.

6Domain-Driven Design

Domain-Driven Design (DDD) is an approach to software development that centres the work on programming a domain model; the name comes from Eric Evans’s 2003 book, which describes it as a catalog of patterns[39,40]. Fowler notes that it is particularly suited to complex domains with a lot of messy logic[39]. Its patterns fall into two groups: strategic design for structuring large systems, and the tactical building blocks used inside one model.

6.1 Strategic design: ubiquitous language and bounded contexts

The ubiquitous language is a common, rigorous language shared by developers and domain experts, based on the domain model used in the software and refined as understanding grows[41]. Class, method and event names in the code should be words the experts use.

A single language cannot cover a large organisation, because the same word means different things in different departments. DDD deals with large models by dividing them into bounded contexts, each with its own consistent model and language, and with explicit mappings between them[42]. Fowler gives “customer” and “product” as the polysemes that cause confusion again and again[42]. In the example below, Sales and Shipping each have their own model, and Shipping translates incoming messages at its boundary (an anti-corruption layer, in Evans’s terms[40]) instead of importing Sales’ classes.

Bounded contexts are the natural seams for packages in a modular monolith and for service boundaries if you later split it up.

Building blockMeaningPython idiom
EntityAn object defined by its identity, which persists while its attributes change[40]Class with an id; __eq__ and __hash__ on the id
Value objectCompared by the values of its properties, with no conceptual identity; should be immutable. Money (an amount plus a currency) is a classic example[43]@dataclass(frozen=True): assignment raises FrozenInstanceError, and __eq__ and __hash__ are generated[44]

6.3 An aggregate in Python

The Order below is an aggregate root. Its invariants (positive quantities, a single currency, a credit limit, no changes after submission) are enforced in one place because every change goes through its methods. It refers to the customer by id rather than holding a Customer object. Money and OrderLine are value objects. Submitting the order records a domain event, which the application layer would hand to the message bus of section 4.2 after saving.

Two orders with the same id are the same entity even though their other attributes differ, while two Money values are equal whenever their amounts and currencies are. The example uses Decimal rather than float for money because binary floats cannot represent most decimal fractions exactly.

6.4 Rules of thumb for aggregates

Vernon’s essays on aggregate design, later expanded in Implementing Domain-Driven Design[46], give four widely used rules:

  1. Model true invariants in consistency boundaries. An invariant is a business rule that must always be consistent; an aggregate exists to protect such rules[47].
  2. Design small aggregates: the root entity plus a minimal number of attributes and value-typed properties[47].
  3. Reference other aggregates by identity, not by holding direct object references[48].
  4. Use eventual consistency outside the boundary: any rule that spans aggregates will not be expected to be up to date at all times, so changes to other aggregates are made later, typically in response to domain events[48].

Vernon goes so far as to say that a properly designed bounded context modifies only one aggregate instance per transaction[47]. Percival and Gregory pair this with optimistic concurrency: a version number on the aggregate changes on every update, so of two clashing transactions only one can commit[13].

6.5 The anemic domain model

The most common way to get DDD wrong is to build entities that hold data but no behaviour, “little more than bags of getters and setters”, with all the logic in service functions. Fowler calls this the anemic domain model: it is really a procedural design and incurs the costs of a domain model without its benefits[49]. If your Order class has no methods and an order_service.py checks every rule, the domain model is anemic. For simple CRUD applications that may be the right choice, but then DDD’s tactical patterns add little.

7Choosing and combining

StyleReach for it whenWatch out for
MVCAny user interface, desktop or web. Django and Flask already give you a version of it.Business rules leaking into controllers or templates.
Layered / ports and adaptersAlmost every application with real business rules and a database.Layers as the top-level split of a large system[12]; pass-through layers that add nothing.
Event-drivenSide effects that should not block the main action; several independent reactions to one change; integration between services.Hidden control flow, duplicates, eventual consistency[23].
MicroservicesSeveral teams need to deploy and scale parts of a large system independently.The cost and risk premium[37]; starting with them before the boundaries are known[38].
DDDA domain whose rules are complex and central to the business[39].Ceremony on simple CRUD; anemic models[49].

A reasonable default path for a growing Python application is: start with a framework’s MVC structure; move rules out of request handlers into a domain model and service layer behind repository protocols; split the code into domain-oriented packages that follow bounded contexts; connect those packages with domain events; and extract a package into a separate service only when a team, scaling or deployment need justifies the premium.

Exercise 1: A second viewMVC · easy

Starting from the to-do model in section 2.2, add a SummaryView that prints how many items are left (“1 item left”, “2 items left”) every time the list changes. Do not modify the model or any controller.

Show solution

The new view only subscribes to the model, so both views refresh on every change. This is observer synchronization doing its job: the model supports several presentations without knowing about any of them[7].

Exercise 2: Enforce the layer rulesLayered · medium

A project has packages presentation, service, domain and adapters. Rules: a layer may import itself or layers below it (presentation → service → domain); adapters may import anything except presentation; only presentation may import adapters (it wires them in). Given a dictionary from file path to source text, use the ast module to list every violation.

Show solution

Parsing with ast rather than searching text means comments and strings that mention a module are ignored. Running a check like this in continuous integration stops dependency rules from eroding over time; the second violation is exactly the domain-depends-on-database problem that section 3.2 removes.

Exercise 3: A new adapter, the same contractPorts and adapters · medium

Write a JsonFileAccounts repository that stores balances in a JSON file and satisfies the same interface as InMemoryAccounts. Then write one contract test function and run it against both adapters. A missing account must raise KeyError.

Show solution

A shared contract test is what makes adapters genuinely interchangeable: the fast in-memory fake used in unit tests is checked against the same expectations as the real storage[13].

Exercise 4: One failing subscriberEvent-driven · easy

In a simple synchronous bus, an exception in one handler stops the others from running. Change publish so that every handler runs, and failures are recorded in a dead_letters list as (event, handler name, error).

Show solution

The dashboard is updated even though email failed. Recording the failure, rather than dropping it, mirrors a dead letter channel: the message is kept for inspection or a later retry[28].

Exercise 5: SnapshotsEvent sourcing · medium

An account’s balance is rebuilt from Deposited and Withdrawn events. Take a snapshot after the first three events, then write balance_from_snapshot that replays only the remaining events. Show that the result equals a full replay.

Show solution

Because apply is a pure function, folding the tail onto the snapshot must give the same result as folding the whole log. The log stays the source of truth[24]; the snapshot is only a cache.

Exercise 6: Retry with exponential backoffMicroservices · medium

Write retry(fn, attempts, base_delay, sleep). It calls fn; on ConnectionError it waits base_delay, then twice that, then four times, and so on, and re-raises after the last attempt. Inject sleep so the test can record the delays instead of waiting.

Show solution

Retries handle brief faults; a circuit breaker (section 5.3) handles long ones by not calling at all[33]. Retry only operations that are safe to repeat, or make the receiver idempotent[27].

Exercise 7: Splitting moneyDDD value objects · medium

Give a Money value object (integer cents plus currency) an allocate(ratios) method that splits it in the given proportions without losing or inventing a cent. Splitting 100.00 EUR three ways must give parts that add up to exactly 100.00.

Show solution

Rounding each share separately would give 33.33 × 3 = 99.99. Integer division first and then handing out the leftover cents keeps the total exact. Putting this rule on the value object, rather than in every caller, is what a value object is for[11,43].

Exercise 8: A library member aggregateDDD aggregates · hard

Model a library Member as an aggregate root. Invariants: a member may hold at most three books at once and may not borrow the same book twice. Books are a separate aggregate, so refer to them by ISBN. Each successful borrow or give_back records a domain event.

Show solution

The loan limit is a true invariant, so it lives inside the member’s consistency boundary[47]. Whether a book is available is a different aggregate’s rule; a handler reacting to BookLoaned would update the book’s status in a separate transaction, accepting eventual consistency between the two[48].
