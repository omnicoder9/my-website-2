1Overview

A design pattern is a named, reusable solution to a problem that keeps coming up in software design. The idea was popularised in 1994 by Gamma, Helm, Johnson and Vlissides, often called the "Gang of Four" (GoF), whose catalogue describes 23 patterns[1]. Each pattern in that catalogue has four essential elements: a name, the problem it addresses, the solution (the elements and how they collaborate) and the consequences, meaning the trade-offs of applying it[1]. The authors group the patterns by purpose into creational patterns (how objects are made), structural patterns (how classes and objects are composed) and behavioural patterns (how objects divide responsibility and communicate)[1].

The GoF examples are written in C++ and Smalltalk. Python is a dynamic language with first-class functions, classes that are themselves objects, and modules, and that changes what several patterns look like. In a 1996 talk, Peter Norvig argued that 16 of the 23 GoF patterns are either invisible or simpler in dynamic languages such as Lisp and Dylan, and he named Strategy, Factory Method, Observer and Builder among them[2]. You will see the same effect in Python throughout this article: the intent of a pattern stays the same, but the code often shrinks to a function, a dictionary or a decorator.

Dependency Injection is not one of the 23 GoF patterns. The name was settled on in 2004 by Martin Fowler and a group of advocates of "inversion of control" containers[3]. It is included here because it has become one of the most important structuring techniques in modern Python applications, and because it is the usual cure for the problems that Singleton causes.

The article assumes you know how to write classes and functions in Python. Each pattern section states the GoF intent, shows a classic implementation, then the idiomatic Python version, and ends with the pitfalls. Section 11 has eight exercises with worked solutions.

2Python features that reshape patterns

Four language features come up again and again in the sections that follow.

Duck typing

Python does not require an object to inherit from a particular class before you can use it. The glossary defines duck typing as a style that "does not look at an object's type to determine if it has the right interface; instead, the method or attribute is simply called or used"[4]. Many GoF patterns start with an abstract interface class, but in Python any object with the right methods already fits.

Abstract base classes and protocols

When you do want to spell out an interface, Python offers two tools. The abc module, introduced by PEP 3119, provides abstract base classes (ABCs)[5,6]. A class whose metaclass derives from ABCMeta cannot be instantiated unless all of its abstract methods and properties are overridden[5]. typing.Protocol, from PEP 544, describes an interface structurally: a class matches a protocol simply by having the right members, with no inheritance needed. PEP 544 calls this "static duck typing"[7,8].

Runtime protocol checks are shallow

An isinstance() check against a @runtime_checkable protocol only tests that the members exist. PEP 544 compares it to writing a chain of hasattr() calls[7]. It does not check argument types or return types; that is the job of a static type checker such as mypy or pyright.

Functions and classes are callable objects

A function is an object: you can store it in a variable, put it in a dictionary and pass it to another function. The glossary defines a callable as anything that can be called with the f(args) syntax, which includes functions, methods and instances of any class that defines __call__()[4]. Classes are callable too: calling a class returns a new instance[9], and the data model reference describes classes as objects that "normally act as factories for new instances of themselves"[10]. This one fact removes much of the machinery of Factory and Strategy: a class or a function can be passed around wherever a "factory object" or "strategy object" would be needed in C++ or Java.

Modules are objects that are imported once

The first place Python looks during an import is sys.modules, a cache of every module already imported[11]. A second import of the same module returns the same module object, so a module behaves like a ready-made single instance. Section 3 builds on this.

3Singleton

GoF intent: "Ensure a class only has one instance, and provide a global point of access to it"[1] (p. 127). Typical uses are a configuration object, a connection pool, or a registry that the whole program shares.

The Pythonic default: a module

The Python Programming FAQ recommends a module for sharing state across a program. Because there is only one instance of each module, changes made to the module object are seen everywhere, and the FAQ adds that "using a module is also the basis for implementing the singleton design pattern, for the same reason"[12].

The standard library uses the same idea in other places. None is a singleton: its type "has a single value" and "there is a single object with this value"[10]. The logging module guarantees that multiple calls to logging.getLogger() with the same name return a reference to the same Logger object, and it says loggers should never be instantiated directly[13]. That is the GoF Singleton intent, keyed by name.

The classic class-based Singleton

If you really need a class, override __new__(). The data model notes that classes which override __new__() can vary the usual "create a new instance" behaviour of a call[10]. The catch is that Python still calls __init__() on whatever __new__() returns, on every call, so naive code silently resets the shared state.

The fix is to do the initialisation once, inside the branch that creates the instance, and leave __init__() undefined.

A cached factory function

A lighter and more testable option keeps the class ordinary and makes a function return the shared instance. functools.cache (Python 3.9+) is an unbounded memoising cache, equivalent to lru_cache(maxsize=None)[14], so a zero-argument function decorated with it builds its result once.

Tests can create as many Settings objects as they like, and cache_clear() resets the shared one.

Thread safety

A lazily created singleton has a race: two threads can both see "no instance yet" and both create one. The functools documentation is explicit that its cache stays coherent under concurrent use, but "it is possible for the wrapped function to be called more than once if another thread makes an additional call before the initial call has been completed and cached"[14]. The program below forces the race with a barrier and a short sleep, then fixes it with a threading.Lock, which blocks any thread that tries to acquire it until it is released and works as a context manager in a with statement[15].

Consequences

A Singleton is global state with a class around it. Code that calls AppSettings() deep inside a function hides that dependency, and tests that change it leak into each other. Gamma et al. list "controlled access to sole instance" among its benefits[1], but in practice the safer design is usually to create the one instance at start-up and pass it in to the code that needs it. That is Dependency Injection, covered in section 9.

4Factory

"Factory" covers a family of creational patterns. The GoF Factory Method intent is to "define an interface for creating an object, but let subclasses decide which class to instantiate"[1] (p. 107). Abstract Factory provides "an interface for creating families of related or dependent objects without specifying their concrete classes"[1] (p. 87). In everyday Python the most common form is simpler still: a factory function that picks a class from a key.

A factory function with a registry

Because classes are callable objects[9], a dictionary that maps names to classes is already a factory. A small decorator lets each class register itself, so adding a format never means editing the factory.

Alternative constructors with @classmethod

A class method receives the class itself as its first argument, and when it is called on a subclass, the subclass is passed[9]. That makes it the natural place for named constructors, a lightweight factory method. The standard library is full of them: int.from_bytes() and float.fromhex() are class methods[16], and so are datetime.date.today() and date.fromisoformat()[17].

The classic Factory Method

In the GoF form, a base class does its work through an abstract "creator" method, and each subclass overrides that method to choose the product. It is still useful when the surrounding algorithm is fixed and only the product varies.

Self-registering subclasses with __init_subclass__

PEP 487 (Python 3.6) added __init_subclass__, a hook that runs for every subclass of the class that defines it, and it uses plugin registration as a motivating example[18]. A factory can use it to discover its products automatically.

Abstract Factory, briefly

Abstract Factory groups several factory methods that must produce matching products, for example a "dark theme" factory that creates dark buttons, dark menus and dark dialogs[1]. In Python a plain object (or module) with one method per product does the job, and the client receives that object as a parameter, which again is Dependency Injection.

5Strategy

GoF intent: "Define a family of algorithms, encapsulate each one, and make them interchangeable. Strategy lets the algorithm vary independently from clients that use it"[1] (p. 315). The pattern also illustrates the GoF principle "favor object composition over class inheritance"[1]: the context has a strategy rather than being a subclass for each algorithm.

Classic form with a protocol

Pythonic form: just pass a function

Norvig lists Strategy among the patterns made simpler by first-class functions[2]. When a strategy has one method and no state, the method can be the strategy. Python's own sorted() works this way: its key argument "specifies a function of one argument that is used to extract a comparison key from each element"[9]. Any parameters a strategy needs can be fixed in advance with functools.partial, which "freezes" some of a function's arguments and returns a new callable[14].

Keep the class version when a strategy carries real state, needs several cooperating methods, or must be configured and inspected (for example shown in an admin screen). Otherwise a function is shorter, easier to test and needs no interface declaration.

6Observer

GoF intent: "Define a one-to-many dependency between objects so that when one object changes state, all its dependents are notified and updated automatically"[1] (p. 293). The pattern is also known as Publish-Subscribe[1]. The object that changes is the subject; the objects that react are its observers.

A callback-based subject

In GoF, observers implement an Observer interface with an update() method. In Python the observer can be any callable[4], so a subject only needs a list of callables. The version below returns an "unsubscribe" function from subscribe(), and notifies a copy of the list so that an observer can safely unsubscribe while it is being notified.

Avoiding memory leaks with weak references

A subject that holds strong references to bound methods keeps their objects alive for as long as the subject lives, a classic source of leaks in long-running programs. A weak reference is "not enough to keep the object alive"[19]. A plain weak reference to a bound method does not work, because a bound method is created fresh on each attribute lookup and dies at once; weakref.WeakMethod exists for exactly this case and recreates the bound method while both the object and the function are alive[19].

Pitfalls
  • Order: observers should not depend on being called in a particular order.
  • Errors: in the simple version, an exception in one observer stops the rest from being notified. Wrap each call in try/except if observers are independent.
  • Cascades: an observer that changes the subject triggers another round of notifications; guard against infinite loops.

7Adapter

GoF intent: "Convert the interface of a class into another interface clients expect. Adapter lets classes work together that couldn't otherwise because of incompatible interfaces"[1] (p. 139). It is also known as Wrapper[1]. GoF distinguishes an object adapter, which wraps an instance, from a class adapter, which uses multiple inheritance[1]; in Python the object adapter is nearly always the better choice.

An object adapter

Suppose a dashboard expects thermometers with a celsius() method, and a vendor library offers a sensor that reports Fahrenheit through a differently named method.

Delegating everything else with __getattr__

When the adapter only needs to change one or two methods, __getattr__() can forward the rest. Python calls __getattr__() only when normal attribute lookup fails[10], so methods defined on the adapter win and everything else falls through to the wrapped object.

Adapters in the standard library

io.TextIOWrapper is "a buffered text stream providing higher-level access to a BufferedIOBase buffered binary stream"[20]. In pattern terms it adapts a byte stream to the text-stream interface, decoding on the way.

Functions can be adapted too. If a library calls callback(event) but your handler needs handle(event, logger), then functools.partial(handle, logger=log) or a one-line lambda is a complete adapter[14].

8Builder

GoF intent: "Separate the construction of a complex object from its representation so that the same construction process can create different representations"[1] (p. 97). In GoF, a director drives a builder through a fixed sequence of steps. In modern code the term usually means a fluent builder: an object whose methods each set one part and return the builder, ending with build().

A fluent builder with validation

Builders earn their keep when an object is assembled in steps, some steps repeat, and the result must be checked as a whole. An SQL query is a good example: filters accumulate, and the builder keeps values out of the SQL text by producing placeholders and a separate parameter list.

When Python does not need a builder

Many Builder examples in other languages exist to work around constructors with long lists of positional parameters. Python already has keyword arguments with defaults, and the dataclasses module generates __init__() and __repr__() for you[21]. kw_only=True (Python 3.10+) makes every field keyword-only, frozen=True makes assignment to fields raise FrozenInstanceError, field(default_factory=...) gives each instance its own mutable default, and dataclasses.replace() creates a modified copy[21]. Together they cover most of what a builder offers, with no extra class.

Note the last True in the output: replace() copies field values, so both requests share the same headers dictionary. Pass a fresh dictionary if the copy should have its own.

Prefer the dataclass when an object is built in one go. Reach for a builder when parts are added over time (as in the query example), when the same steps must produce different representations (the original GoF motivation), or when validation depends on combinations of steps.

9Dependency Injection

Fowler describes the idea as having a separate object, an assembler, that supplies a class with the implementation of each service it depends on, instead of letting the class find or build that implementation itself[3]. He names three forms: constructor injection, setter injection and interface injection[3]. The goal is the GoF principle "program to an interface, not an implementation"[1]: a class should depend on what a collaborator does, not on which concrete class does it.

The problem: hard-wired dependencies

This class cannot be tested without a mail server, and its output depends on the wall clock. The fix is to hand it both collaborators.

Constructor injection

Each dependency becomes a constructor parameter typed with a Protocol[7]. Production code passes the real objects; tests pass fakes. No framework is needed.

Testing with unittest.mock

unittest.mock lets you "replace parts of your system under test with mock objects and make assertions about how they have been used"[22]. create_autospec() builds a mock that mirrors a real class and checks call signatures, so a test fails if the code calls a method with the wrong arguments[22]. Injection is what makes this easy: the mock is simply passed in.

Setter injection, defaults and the composition root

Setter injection assigns a dependency after construction (service.mailer = ...). It suits optional collaborators but allows a half-configured object to exist. Fowler's own preference is to start with constructor injection, because it creates valid objects at construction time, and to switch to setters only when constructors become unwieldy[3]. In Python, a default argument value gives a convenient middle ground: callers get a sensible default, and tests override it.

All the real objects are then created in one place at start-up, often called the composition root. This is Fowler's assembler[3], and it is also where the single shared instances live: you get the benefits of Singleton (one connection pool, one settings object) without any class enforcing it.

Dependency Injection or Service Locator?

Fowler compares DI with the Service Locator pattern, in which a class asks a central registry for its dependencies. He finds the two roughly equivalent for application classes, prefers injection for classes that will be reused across applications, and stresses that the more important principle is separating configuration from use[3]. Python frameworks offer DI containers, but for most programs constructor parameters and a composition root are enough.

10Choosing a pattern

A pattern is a tool for a recurring problem, not a goal. Gamma et al. stress that every pattern has consequences, costs as well as benefits, that you should weigh before applying it[1]. The table pairs each pattern with the symptom that calls for it and the common way it is overused.

PatternReach for it whenOveruse looks like
SingletonA resource must exist exactly once (a pool, a registry)Global state hidden behind a class; tests that interfere with each other
FactoryThe concrete class depends on data (a file suffix, a config key)A factory for a class with one implementation
StrategyAn algorithm must be chosen at run timeInterface and three classes where one function argument would do
ObserverSeveral independent parts must react to one changeHard-to-trace chains of events; leaked subscribers
AdapterCode you cannot change has the wrong interfaceWrappers around your own code that you could simply rename
BuilderAn object is assembled in validated stepsA builder that only mirrors a dataclass constructor
Dependency InjectionA class talks to I/O, time, randomness or another serviceA heavyweight container for a small script

Exercise 1: The forgetful singletonSingleton · easy

The class below is meant to count page views across the whole program, but the count keeps going back to zero. Explain why and fix it without changing how callers use it (Counter().hit()).

class Counter:
    _instance = None
    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance
    def __init__(self):
        self.count = 0
    def hit(self):
        self.count += 1
        return self.count
Show solution

Python calls __init__() on the object returned by __new__() every time the class is called, so self.count = 0 runs on each Counter(). Move the initialisation into the branch that creates the instance.
