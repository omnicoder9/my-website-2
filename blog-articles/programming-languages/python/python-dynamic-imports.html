Dynamic Imports in Python

1What “dynamic import” means

An ordinary import json statement names its module in the source code. The statement does two separate things: it searches for the named module (loading it if necessary), and then it binds the result to a name in the local scope[1]. A dynamic import performs the first step with a module name that is only known when the program runs: a string read from a configuration file, a command-line option, a plugin directory or an installed package's metadata. You then keep the returned module object in whatever variable, dictionary or registry suits you.

Python exposes the import machinery through the importlib package, and its documentation recommends importlib.import_module() as a simpler API than the built-in __import__() for invoking that machinery[1,2]. The same package also lets you build modules from file paths, reload them, defer their loading and inspect installed distributions. Typical reasons to reach for these tools are:

  • Plugins and extensions: an application loads exporters, drivers or commands that third parties install separately.
  • Configuration-driven wiring: a setting such as "myapp.backends.redis:RedisCache" chooses the class to use.
  • Optional dependencies: use a fast library when it is installed and fall back otherwise.
  • Startup time: postpone loading heavy modules until the first time they are used.
  • Development tools: test runners, REPL helpers and auto-reloaders that load or re-execute code by path.

Every example in this article is a complete file that was run on CPython 3.13.17. Where an example needs more than one file, each file starts with a # file: comment that gives its path relative to the directory the program runs in.

2How the import system works

Dynamic imports use exactly the same machinery as the import statement, so it pays to know its parts. Four objects do most of the work.

PartRole
sys.modulesA dictionary that maps module names to modules already loaded. It is the first place every import looks[1,3].
FinderAn object that decides whether it can find a named module. It does not load anything; it returns a module spec describing the module[1].
Module specA ModuleSpec carrying the import-related information (name, loader, origin) needed to load a module. Specs were introduced by PEP 451 and are exposed afterwards as module.__spec__[1,4].
LoaderThe object that performs the critical step of loading: executing the module's code[1].

When you import foo.bar.baz, Python first imports foo, then foo.bar, then foo.bar.baz; if any intermediate import fails, the whole import raises ModuleNotFoundError[1]. For each name it checks sys.modules. On a miss it asks each meta path finder in sys.meta_path, in order, for a spec[1,3]. By default there are three of them: one for built-in modules, one for frozen modules, and the path based finder, which searches the import path[1]. The hook mechanism behind this design (meta path finders, path hooks and loaders) was first specified in PEP 302[5].

The cache is why importing a module twice runs its top-level code only once, and why a module's global state is shared by everything that imports it. You can watch the finders at work with importlib.util.find_spec(), which returns the spec that an import would use, or None when no finder knows the name[2].

Notice that this interpreter has four meta path finders, not three. The extra DistutilsMetaFinder comes from a distutils-precedence.pth file that setuptools installed in the system site-packages; running the same program with python -S, which skips the site module[6], leaves only the three defaults. Any installed package can extend the import system this way, a point Section 9 returns to. The built-in and frozen importers act as their own loaders, which is why the class names repeat.

The search path, sys.path

The path based finder walks the list of strings in sys.path. It is initialised from the PYTHONPATH environment variable plus an installation-dependent default[3], and the site module then adds the site-packages directories[7]. By default a “potentially unsafe” entry is also prepended: the script's directory for python script.py, the current working directory for python -m module, and an empty string (meaning the current directory) for -c and the REPL[3]. Section 9 shows why that matters. For each sys.path entry the path based finder obtains a path entry finder through the callables in sys.path_hooks and caches it in sys.path_importer_cache[3].

Controlling the cache

Because sys.modules is consulted first, it can be manipulated directly. If a name maps to None, the import stops with ModuleNotFoundError; if the name is missing, the search continues[1]. Test suites use this to simulate a missing optional dependency. The sys documentation warns, though, that replacing the dictionary may not work as expected and that deleting essential entries can make Python fail; when iterating over it, use sys.modules.copy() or tuple(sys.modules) because its size can change during iteration[3].

A loader adds the new module to sys.modules before executing the module's code. The language reference calls this crucial: a module may import itself, directly or indirectly, and registering it first prevents unbounded recursion and repeated loading[1]. It is also the reason a circular import sees a partially initialised module (Section 10).

3import_module and __import__

importlib.import_module(name, package=None) imports a module given its absolute or relative name and returns it. For a relative name such as "..mod", the package argument must name the anchor package, so import_module('..mod', 'pkg.subpkg') imports pkg.mod. Parent packages are imported automatically, and a failure raises ImportError or a subclass such as ModuleNotFoundError[2].

The built-in __import__(name, globals=None, locals=None, fromlist=(), level=0) is the function the import statement calls. It performs the search and creates the module, but it does not bind any name[1]. Its documentation describes it as an advanced function that is not needed in everyday programming and points to importlib.import_module() instead[8]. The most important difference is the return value: import_module() returns the module you asked for, such as pkg.mod, while __import__() returns the top-level package, such as pkg, unless fromlist is non-empty[2,8].

Most dynamic imports end by fetching an attribute from the module, so a common convention writes the target as "module:attribute". This is the same object reference syntax that packaging entry points use, importable.module:object.attr[9], and the standard library can resolve it for you with pkgutil.resolve_name() (added in Python 3.9)[10].

Modules created while the program runs

Finders cache what they have seen on disk. If your program writes or installs a module after the interpreter started, call importlib.invalidate_caches() before importing it; the documentation says this should be done so that all finders notice the new module[2].

4Importing a file by path

Sometimes the thing you have is a path, not a module name: a user-supplied script, a plugin file in a configuration directory, or a test fixture. importlib.util lets you run the import steps by hand. spec_from_file_location(name, location) builds a spec for a file, module_from_spec(spec) creates an empty module from it (preferred over creating a types.ModuleType yourself because the spec fills in the import-related attributes), and the loader's exec_module() runs the code[2]. The importlib documentation gives this recipe, with the caution that it only approximates an import statement and that alternatives such as adjusting sys.path or runpy.run_path() should be considered first[2].

The sys.modules step is not decoration. Code inside the module, and libraries such as pickle that look classes up by their module name, expect to find the module there. The next example skips that line and then tries to pickle an instance of a class defined in the file.

5Reloading a module

importlib.reload(module) recompiles and re-executes the module's code using the loader that originally loaded it, and binds the new objects into the module's existing dictionary[2]. It is the basis of auto-reloaders and of the REPL habit of editing a file and reloading it. Its limits all follow from one fact: only names inside the module are updated. The documentation lists the consequences[2]:

  • Other references to the old objects, such as names created elsewhere with from module import name, keep pointing at the old objects.
  • The module dictionary is retained, so a name that the new version no longer defines keeps its old value.
  • Existing instances keep using the old class definition, and so do subclasses defined elsewhere.
  • The init function of an extension module is not called again, and reloading sys, __main__ or builtins is not recommended.
  • The function is not thread-safe; guard concurrent reloads with a lock.

Robust reloaders therefore re-read values through the module (settings.DEBUG) rather than through from-imported names, which is one of the two fixes the documentation suggests[2], and many development servers sidestep the problem entirely by restarting the whole process when a file changes. Note also that reload() needs a module object that was imported successfully; a module that lacks a spec raises ModuleNotFoundError[2].

6Lazy imports

Importing a large library can dominate a command-line tool's startup time. Python offers three ways to postpone the cost until a module is actually used. To find out which imports are worth deferring, run python -X importtime, which reports the cumulative and self time of each import[6].

Module __getattr__ (PEP 562)

Since Python 3.7 a module can define __getattr__(name) and __dir__() functions. When normal attribute lookup on the module fails, __getattr__ is called before AttributeError is raised, and PEP 562 names lazy submodule imports as a widespread use case, alongside deprecation warnings for renamed attributes[12]. Lookups of a name as a global from inside the module bypass __getattr__[12]. When a submodule is imported, the import system also binds it as an attribute of its parent package[1], so __getattr__ runs only on first access.

importlib.util.LazyLoader

LazyLoader wraps another loader and postpones executing the module until one of its attributes is first accessed. It only works with loaders that define exec_module(), and the importlib recipe for it is reproduced below[2]. The documentation is unusually blunt about when to use it: for projects where startup time is not critical, the class is heavily discouraged, because errors raised while loading are postponed and appear out of context[2]. The second half of the example shows exactly that.

The lazy keyword (Python 3.15)

PEP 810, which is final and targets Python 3.15, makes lazy importing part of the language. A lazy soft keyword in front of import or from ... import defers loading and executing the module until the first time the imported name is used[13]. The keyword is only allowed at module level (not inside functions, class bodies or try blocks), and lazy from ... import * is a syntax error[13]. Python 3.15 also adds the -X lazy_imports option and the PYTHON_LAZY_IMPORTS environment variable: the value all makes every import lazy by default, and normal (the default) respects the keyword in the source[6]. The two examples below were run on CPython 3.15.0b4, because the syntax does not exist on 3.13.

7Plugin discovery

The Python Packaging User Guide describes three ways for an application to discover plugins automatically: a naming convention, namespace packages, and package metadata (entry points)[14]. All three end in a dynamic import.

Naming convention with pkgutil.iter_modules()

pkgutil.iter_modules() yields a ModuleInfo(module_finder, name, ispkg) for every top-level module on sys.path, or for every submodule on a path list you pass in[10]. Filtering by a name prefix gives a simple plugin system[14].

Namespace packages

A namespace package has no __init__.py and can be spread over several directories on sys.path. Its __path__ lists every portion, so passing it to iter_modules() finds plugins that separate distributions dropped into the same namespace[10,14]. Entry points with importlib.metadata

Entry points are the most widely used mechanism. They let an installed distribution advertise components it provides: each entry point has a group saying what kind of object it provides, a name identifying it within the group, and an object reference in the form importable.module:object.attr[9]. A plugin declares them in its pyproject.toml[14]:

When the plugin is installed, the build backend writes the entry points to an entry_points.txt file in the distribution's *.dist-info directory[9]. The application never needs to know the plugin's package name. It asks importlib.metadata.entry_points() for a group; the result is an EntryPoints collection, and each EntryPoint has name, group and value attributes, module and attr components, a dist attribute and a load() method that imports the object[15]. Since Python 3.12, entry_points() always returns an EntryPoints object rather than the older dictionary keyed by group[15].

8Package data with importlib.resources

Dynamically loaded code often ships data files: templates, schemas, word lists. Building paths from __file__ breaks as soon as the package is imported from a zip file. importlib.resources uses the import system itself to give access to resources inside packages[16]. files(anchor) takes a module object or module name (the anchor) and returns a Traversable that behaves like a directory you can join paths onto and read from[16]. When an API needs a real file on disk, as_file() provides a pathlib.Path and cleans up any temporary file it had to extract[16].

The 3.13 functional API accepts multiple path components, and requires encoding to be passed as a keyword argument when there is more than one[16].

9Security

Importing a module executes it. Any string that reaches import_module() chooses which code runs in your process, so dynamic imports deserve the same care as eval(), whose documentation warns that calling it with untrusted input will lead to security vulnerabilities[8]. MITRE catalogues the general weakness as CWE-470, “unsafe reflection”: a product uses external input to select which classes or code to use, so an attacker can select unexpected classes or methods[17].

The this module prints the Zen of Python as a side effect of being imported, which is harmless; a module chosen by an attacker need not be. CWE-470's mitigations are to avoid reflection where possible, not to use user-controlled input to select code, and otherwise to restrict the choice with an allowlist or an indirect selection[17]. Search-path hijacking

The other attack goes through sys.path. Because the script's directory (or the current directory) is prepended to the path[3], a file there with the same name as a standard-library or installed module is imported in its place. A last, quieter route is .pth files in site-packages: for backward compatibility, their lines that start with import are executed at every startup[19]. Python 3.15 deprecates those lines, and they are scheduled to be silently ignored in Python 3.18 and 3.19[19].

Checklist for code that imports by name
  • Never pass request data, file contents or environment input straight to import_module(), __import__(), pkgutil.resolve_name() or getattr() on a module.
  • Map public keys to fixed targets, or accept only names that you discovered yourself inside your own plugin package or entry-point group.
  • Load files by path only from directories that only trusted users can write to.
  • Run tools and services with -P or -I when they do not need the script directory on the path.
  • Treat installing a plugin as trusting its author: loading it runs its code with your privileges.

10Pitfalls

Catching too much when a dependency is optional

The usual “try the fast library, else fall back” code catches ModuleNotFoundError. But the same exception is raised when the module exists and one of its own imports fails, which hides a real bug. The exception's name attribute tells the two cases apart.

Importing a package does not import its submodules

Packages are modules with a __path__, and their submodules are only loaded when something imports them[1]. Code that imports "xml.etree" dynamically and then reaches for .ElementTree works only if something else happened to import it first.

A relative name without an anchor

Circular imports see half-built modules

Because a module is placed in sys.modules before its code runs[1], a module that is imported again while it is still executing is returned in its partly initialised state. Dynamic plugin systems hit this when a plugin imports the application module that is in the middle of loading it.

The fix is to finish defining what plugins need before loading them, or to have plugins import the module and read shop.app.VERSION when they are called rather than at import time.

Other traps

  • Name clashes when loading by path. The name you pass to spec_from_file_location() becomes the key in sys.modules. Two plugin files both called utils.py must get different names, such as "myapp_plugins.vendor_a.utils", or the second will replace the first.
  • find_spec() is not side-effect free for dotted names. Checking "pkg.sub" imports pkg first[2].
  • Reloading in threaded code. importlib.reload() is not thread-safe[2].
  • Mutating sys.path globally. Inserting a directory affects every later import in the process; prefer loading by path, or remove the entry when you are done.
  • Swallowed plugin errors. pkgutil.walk_packages() ignores ImportError from packages unless you pass onerror[10].

1. Resolve "module:attribute" yourselfBasic

Write load_object(ref) that accepts "package.module:obj.attr", imports the module part with importlib.import_module() and follows the dotted attribute path with getattr(). Raise ValueError if the colon or either part is missing. Check that your results match pkgutil.resolve_name().

2. Which optional dependencies are available?Basic

Write available(names) that returns a dictionary mapping each top-level module name to True or False without executing any of those modules. Prove it with a local module that prints a message when imported: the message must not appear.

Show solution

find_spec() only asks the finders for a spec, so no module code runs. For a dotted name it would import the parent package[2], which is why the exercise sticks to top-level names.

3. A plugin folderIntermediate

Write load_plugins(folder) that loads every *.py file in folder (skipping names that start with an underscore) by path, registers each one in sys.modules under a unique name "plugins.<stem>", and returns a dictionary of the plugins that define a register() function. A plugin that raises during loading should be reported and skipped, not crash the loader.

Show solution

4. A lazy package with a deprecated aliasIntermediate

Package units has submodules length and mass. Make both load lazily on attribute access, and keep an old name working: units.metric was renamed to units.length, so accessing units.metric should emit a DeprecationWarning and return the length module. Use only the PEP 562 hooks.

Show solution

Deprecation warnings for moved or renamed attributes are the other use case that PEP 562 was designed for[12]. Because metric is never stored in the module's globals, every access goes through __getattr__ and warns.

5. Accept only names you discoveredIntermediate

A command-line tool runs tool <command>, where each command is a module in the package tool.commands. Write load_command(name) that imports only modules that pkgutil.iter_modules() actually found in that package, so that input such as "os", "..secrets" or "commands.greet.extra" is rejected before any import happens.

Show solution

This is the “indirect selection” mitigation from CWE-470: the user picks from a set the program built itself[17].

6. An in-memory importerAdvanced

Write a class that acts as both a meta path finder and a loader for modules whose source code is held in a dictionary. Append an instance to sys.meta_path so that a plain import greetings works even though no file exists. Make tracebacks name the virtual file.
