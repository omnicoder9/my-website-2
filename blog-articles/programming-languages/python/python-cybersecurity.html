1Overview

Security work is full of small, specific jobs: check which services a host exposes, hash a suspicious file, pull the strings out of a binary, parse a thousand log lines, reconfigure a fleet of routers. Python suits these jobs because its standard library already covers sockets, hashing, binary parsing, regular expressions and process control, and because the security community maintains mature libraries for the rest. This article tours six disciplines and, for each one, shows the Python that does the routine part of the work.

The framing throughout is defensive and professional. Penetration testing follows the NIST technical testing guide, whose four phases are planning, discovery, attack and reporting, and whose planning phase is where rules are identified and management approval is documented before any test runs[1]. Incident response follows NIST SP 800-61 Revision 3, which organises the work around the six Functions of the NIST Cybersecurity Framework 2.0 (Govern, Identify, Protect, Detect, Respond and Recover)[2]. Forensics follows NIST SP 800-86, which divides the forensic process into collection, examination, analysis and reporting[3]. Adversary behaviour is named with MITRE ATT&CK, a globally accessible knowledge base of adversary tactics and techniques based on real-world observations[4].

2Authorisation, law and the lab

The code in this article is ordinary. What makes it legitimate or criminal is whether you have permission to point it at a system. In the United States, 18 U.S.C. § 1030 makes it an offence to intentionally access a computer without authorisation or in excess of authorised access and thereby obtain certain information[5]. In the United Kingdom, section 1 of the Computer Misuse Act 1990 covers unauthorised access to computer material, and section 3A covers making, supplying or obtaining articles for use in such offences[6]. Other countries have similar laws.

Professional practice turns that legal line into paperwork. NIST SP 800-115 places the rules of engagement and documented management approval in the planning phase, before any discovery or attack activity, and supplies a rules-of-engagement template in its appendix B[1]. In practice that means a signed scope listing the exact hosts, networks, dates and techniques allowed, and a named contact to call if something breaks.

How the examples stay safe
  • Scans and HTTP checks target 127.0.0.1 and services the script itself starts.
  • Example addresses come from the blocks reserved for documentation (192.0.2.0/24, 198.51.100.0/24 and 203.0.113.0/24)[7], example domains use the reserved .invalid top-level domain[8], and example MAC addresses come from the IANA documentation range 00-00-5E-00-53-00 to 00-00-5E-00-53-FF[9].
  • The "malware" is a 1.5 KB Windows program built in section 4 that does nothing but call ExitProcess(0). No real malware is used or needed.
  • Packets are built and written to a file, never sent.

When you move on to real samples, analyse them in an isolated virtual machine with no route to production networks, and follow your organisation's malware handling procedures; NIST SP 800-83 covers malware incident prevention and handling for desktops and laptops[10].

3Penetration testing

NIST describes penetration testing as a four-phase process: planning, discovery, attack and reporting. Discovery includes identifying network ports and services, and the guide notes that penetration testing "should be performed only after careful consideration, notification, and planning"[1]. Python is most useful in discovery and in checking configuration, where a short script can do in seconds what would take an hour by hand.

3.1 A scope-checked TCP connect scan

A TCP connection opens with a three-way handshake: SYN, then SYN plus ACK, then ACK[11]. If nothing is listening, the target answers the SYN with a reset[11]. A connect scan therefore just tries to connect to each port. Python's socket.connect_ex() is convenient for this because it returns an error indicator, 0 on success, instead of raising an exception[12]. Port scanning is the technique ATT&CK calls Network Service Discovery (T1046), which is why defenders watch for it[13].

The script below refuses any target outside its written scope. ipaddress.ip_network() builds a network object, and the in operator tests whether an address belongs to it[14]. A thread pool runs the probes concurrently, and Executor.map() returns results in input order[15]. Two toy services started by the script give it something to find; after connecting, the scanner reads the service's banner, the identifying text many services send first. NIST notes that banners are not proof of what is running, because an administrator can change them[1].

3.2 Checking HTTP security headers

Web application testing has its own methodology, the OWASP Web Security Testing Guide[16]. One small, repeatable check is whether responses carry the security headers OWASP recommends, such as Strict-Transport-Security, Content-Security-Policy, X-Content-Type-Options: nosniff, X-Frame-Options: DENY (or CSP frame-ancestors, which obsoletes it in supporting browsers) and an explicit Referrer-Policy[17]. The lab server is built from http.server, which the Python documentation says is not recommended for production because it implements only basic security checks[18].

Read the result with care. The lab server speaks plain HTTP, and browsers must ignore a Strict-Transport-Security header that arrives over an insecure connection[19], so that header only matters on an HTTPS site.

3.3 Auditing password storage

Password cracking recovers passwords from stored hashes, usually to find accounts with weak passwords; a dictionary attack simply tries every word in a list[1]. ATT&CK records online guessing as T1110.001[20]. The audit below shows why a plain hash is the wrong way to store passwords: identical passwords produce identical hashes, and a wordlist recovers them instantly. OWASP states that fast hashing algorithms such as SHA-256 are not suitable for password storage, that each password needs a unique random salt, and that scrypt, when Argon2id is unavailable, should use at least N = 217, r = 8 and p = 1[21]. Python provides scrypt as hashlib.scrypt()[22], and hmac.compare_digest() compares the results without content-dependent short-circuiting, which resists timing analysis[23].

4Malware analysis

Analysis usually starts static: describe the file without running it. You compute hashes to identify it, measure entropy to guess whether it is packed or encrypted, pull out readable strings, match it against detection rules and read its executable headers. Python covers each step.

4.1 Building a harmless sample

To practise without live malware, the script below writes a minimal 64-bit Windows Portable Executable (PE). Every field it sets is defined in Microsoft's PE format specification: the MZ header whose offset 0x3C points to the PE\0\0 signature, a COFF header with machine type 0x8664 (x64), an optional header with magic 0x20B (PE32+), and two sections[24]. The import table names one function, KERNEL32.dll!ExitProcess, and the read-only data section carries an update URL on the reserved .invalid domain so the later tools have something to find. The script uses struct.pack and struct.pack_into with the < prefix for little-endian, standard-size fields[25]. The file was built for analysis and was not run on Windows.

4.2 Hashes, entropy and strings

Hashes are the fingerprints analysts share. hashlib offers MD5, SHA-1 and SHA-256 behind one interface, and its documentation warns that MD5 and SHA-1 have known collision weaknesses[22]. NIST recommends moving away from SHA-1 for all applications and encourages SHA-256 at a minimum[26]. Analysts still record MD5 and SHA-1 because older threat reports and databases index samples by them; SHA-256 is the one to rely on.

Shannon entropy, measured in bits per byte, ranges from 0 for constant data to 8 for perfectly uniform data. Lyda and Hamrock showed that entropy analysis helps find encrypted and packed malware, because packing and encryption push entropy towards the maximum[27]. Malware authors pack and encode payloads precisely to hide them, the ATT&CK technique Obfuscated Files or Information (T1027)[28].

The sample's low entropy says it is neither packed nor encrypted, and the strings reveal the import and the URL in plain text.

4.3 Detection rules with YARA

YARA describes malware families as rules made of an optional meta section, an optional strings section and a required condition. Strings can be text, hexadecimal patterns or regular expressions, and conditions can test bytes at fixed offsets, for example uint16(0) == 0x5A4D for the MZ signature, or require n strings from a set[29]. The yara-python binding compiles rules from source and matches files or in-memory data; since version 4.3.0 each match exposes StringMatchInstance objects with offset and matched_data[30].

4.4 Reading the PE structure with pefile

pefile is a Python module for reading and working with PE files, giving access to headers and section data[31]. The script reads the fields that matter in triage. A DllCharacteristics value with bit 0x0100 set means the image is NX compatible, and bit 0x0040 means it can be relocated at load time (ASLR); section flags 0x40000000, 0x80000000 and 0x20000000 mean readable, writable and executable[24]. The imphash, an MD5 of the imported library and function names in table order, was introduced by Mandiant to cluster related samples and is implemented in pefile as get_imphash()[32]. The datetime.UTC alias used for the timestamp was added in Python 3.11[33].

Two details deserve attention. The compile timestamp is just a field the linker writes, so it can be forged, as this script did. And a section that is both writable and executable, or one with entropy near 8, is a classic sign of a packer and worth a closer look.

5Reverse engineering

Reverse engineering recovers what a program does from its compiled form. For native code that means disassembly; for Python malware distributed as bytecode it means reading CPython's instructions.

5.1 Disassembling the entry point with Capstone

Capstone is a disassembly framework with a small Python API: create a Cs object for an architecture and mode, call disasm(code, address), and iterate over the instructions. Setting detail = True exposes each instruction's operands[34]. The script below combines Capstone with pefile. It disassembles from the entry point, and when it sees an indirect call through a RIP-relative address it computes the target and looks it up in the Import Address Table, which is how disassemblers label API calls.

The four instructions reserve stack space, set the first argument register (ecx) to zero and call ExitProcess, so the program exits with status 0. That is the whole of its behaviour, which confirms the sample is harmless.

5.2 Reading Python bytecode with dis

The dis module disassembles CPython bytecode. Its documentation stresses that bytecode is an implementation detail of CPython that may change between versions, so the listing below is specific to Python 3.13[35]. The function hides its key behind an XOR. The constant folder has already computed that XOR at compile time, so the key sits in the function's constants as a single integer.

Decoding hidden strings by repeating the program's own decoding step is a routine part of malware analysis. Malware does the same at run time, which ATT&CK records as Deobfuscate/Decode Files or Information (T1140); its procedure examples include malware that decrypts strings with single-byte XOR keys[36]. Exercise 2 practises exactly that.

6Network automation

Security teams automate networks for two reasons: to see what is on the wire, and to change many devices consistently and auditably. The three tools below cover packets, device output and device sessions.

6.1 Building and parsing packets with Scapy

Scapy is a Python program that lets the user send, sniff, dissect and forge network packets[37]. Layers are stacked with the / operator, wrpcap() saves packets to a PCAP file, rdpcap() reads them back, and summary() gives a one-line description of a packet[38]. The script builds a short conversation offline, a DNS lookup, a TCP handshake and an HTTP request, then analyses the saved capture the way you would analyse one from a sensor. A beacon to a web server like this is the ATT&CK technique Application Layer Protocol: Web Protocols (T1071.001)[39].

6.2 Turning CLI output into data with TextFSM

Network devices answer in text tables meant for people. TextFSM is a template-based state machine that parses such semi-formatted text into records; Google originally built it to read the CLI output of network devices[40]. The ntc-templates project ships ready-made templates, and its parse_output(platform=..., command=..., data=...) function picks the right one[41].

6.3 Running commands over SSH with Netmiko

Netmiko wraps SSH sessions to network devices. You describe a device in a dictionary with device_type, host, username and password, pass it to ConnectHandler, and call send_command()[42]. Both cisco_ios and linux are in Netmiko's regularly tested platform list[43]. For this article the "device" is an SSH server on the test machine with a lab-only account, so the output below is real. Credentials come from environment variables so they never appear in source code or version control.

Against a router you would set device_type to cisco_ios and send commands such as show ip interface brief, then feed the output to the parser from section 6.2. Keep automation read-only until a change has been reviewed, and log every command you send.

7Incident response

NIST SP 800-61 Revision 3 supersedes the 2012 Computer Security Incident Handling Guide and replaces its four-phase life cycle with a model built on the CSF 2.0 Functions; it maps the old phases (preparation; detection and analysis; containment, eradication and recovery; post-incident activity) onto the new Functions and lets organisations use whichever model suits them[2]. Python earns its place in the Detect and Respond work, where responders need answers from large volumes of logs quickly.

7.1 Triage of SSH authentication logs

The script parses OpenSSH-style log lines with a regular expression that uses named groups, read back with m["name"] indexing, which match objects have supported since Python 3.6[44]. It counts failures per source and raises an alert when a source that failed repeatedly then logs in successfully. That sequence is the signature of password guessing (T1110.001)[20] ending in the use of a valid account (T1078)[45], and it is the most urgent line in the output.

7.2 Sweeping for indicators of compromise

Once one host is confirmed compromised, responders sweep the rest for its indicators: file hashes, domains, IP addresses. hashlib.file_digest(), added in Python 3.11, hashes an open file efficiently[22].

Hash matching ignores file names, so the copy disguised as invoice.exe is found as surely as the original. A hash match is exact, though: changing a single byte defeats it, which is why sweeps combine hashes with behavioural indicators such as the domain lookup.

8Digital forensics

NIST SP 800-86 divides forensics into collection, examination, analysis and reporting[3]. Evidence is only useful if you can show it has not changed since collection, so hashing runs through every phase.

8.1 An evidence manifest

The script records each file's SHA-256, size and modification time in a JSON manifest at collection, then re-hashes later to prove nothing changed, or to show exactly what did. Timestamps are stored in UTC with datetime.fromtimestamp(ts, tz)[33] so that examiners in different time zones read the same values.

On a real case, work from a verified forensic image rather than the original media, store the manifest separately from the evidence, and record who handled what and when.

8.2 Spotting disguised files by signature

A file's extension is only part of its name; its type is in its first bytes. A PNG file, for example, always begins with the eight bytes 89 50 4E 47 0D 0A 1A 0A[46], and a Windows executable begins with MZ[24]. Attackers exploit the gap by giving payloads a misleading extension or by changing the file's signature, the ATT&CK technique Masquerade File Type (T1036.008)[47].

8.3 Memory forensics with Volatility 3

Some evidence exists only in RAM: running processes, network connections, injected code and decrypted keys. Volatility 3 is an open-source memory forensics framework written in Python, and it can also be used as a library[48]. Its plugins are run against a memory image from the command line, for example python3 vol.py -f MemDump.DMP windows.pslist to list processes; for Windows images it can usually build the symbol tables it needs from PDB files downloaded automatically from Microsoft[49]. No memory image was available for this article, so that command is not run here.

Where Python fits in memory work

Volatility does the heavy parsing. Python is then the glue: run several plugins, collect their output, and correlate it with the log, hash and network findings from sections 6 and 7 into a single timeline.

9Writing safe security tools

Security tools read hostile input by design: banners, log lines, file names and samples written by attackers. A careless tool becomes the next vulnerability. Four habits from the standard library documentation prevent most problems.

  • Never let a shell parse untrusted text. subprocess does not call a shell unless you pass shell=True, so with a list of arguments every character, metacharacters included, reaches the program literally; if you must use a shell, quoting untrusted values with shlex.quote() is your responsibility[50].
  • Use secrets, not random, for tokens and keys. The random module is designed for modelling and simulation, not security or cryptography[51].
  • Compare secrets in constant time with hmac.compare_digest() or secrets.compare_digest()[23,51].
  • Never unpickle untrusted data. Malicious pickle data can execute arbitrary code during unpickling; use a format such as JSON instead[52].

10Exercises

Each exercise uses only the lab material from this article. Solutions were run on CPython 3.13 in the same folder as the examples, so sample.exe is present.

Exercise 1: Port specificationsPenetration testing

Scanners accept port lists like 22,80,8000-8002. Write parse_ports(spec) that returns a sorted list of unique ports, accepts spaces, and raises ValueError for non-numeric items, ports outside 1 to 65535, and reversed or open-ended ranges.

Show solution

str.partition("-") splits each item into at most three parts, so "1-" leaves an empty upper bound that the digit check rejects. Validating input this strictly matters in a scanner, because a typo can widen the scan beyond the authorised scope.

Exercise 2: Single-byte XORMalware analysis

A sample stores a URL XOR-encoded with one unknown byte. The encoded bytes in hex are 7b676763293c3c6663777267763d7a7d65727f7a773c7021. Try all 256 keys and print only decodings that are printable ASCII and contain ://.

Show solution

Filtering on printability and a known fragment ("crib") leaves one candidate. With longer keys the same idea works per key position, which is why simple XOR is obfuscation rather than encryption.

Exercise 3: Parse PE headers by handReverse engineering

Without using pefile's parsed fields, read sample.exe with struct: check the MZ and PE\0\0 signatures, then print the machine type, number of sections, section names, optional-header magic and entry-point RVA. Finally, confirm your values agree with pefile.

Show solution

The offsets come from the PE specification: the PE signature's offset is at 0x3C, the COFF header follows the four-byte signature, SizeOfOptionalHeader sits 16 bytes into the COFF header, and the section table starts right after the optional header[24].

Exercise 4: Detect a port scan in a captureNetwork automation

Write find_scanners(packets, threshold=10) that reports each source and destination pair where the source sent SYN-only TCP segments to at least threshold distinct ports. Test it on a capture you build with Scapy that contains one sweep of 20 ports and some normal connections.

Show solution

Counting distinct ports rather than packets keeps a busy but normal client, which may open many connections to port 443, below the threshold. This is the network-side view of the scan from section 3.1 (T1046)[13].

Exercise 5: Brute force in a time windowIncident response

Two sources each fail to log in five times, one within a minute and one over twelve minutes. Write bursts(events, limit=5, window=60) that flags only sources with at least limit failures inside any window-second span.

Show solution

A deque per source holds the failure times still inside the window; old entries drop off the left as new ones arrive, so each event is handled in amortised constant time. Totals alone would treat both sources the same.

Exercise 6: Carve PNG files from raw dataDigital forensics

File carving recovers files from raw data with no file system metadata. Given a byte string that holds junk, two PNG files and a truncated PNG header, find each PNG by its signature, end it after the IEND chunk, which is always the last chunk of a PNG datastream[46], and write each one out. Report and skip anything truncated.

Show solution

The fake PNGs carry only a signature and an IEND trailer, enough to test the carver. Real carving tools also validate chunk lengths and CRCs to reject false positives.
