1Threat model and scope

Django ships with defences against the most common classes of web attack, but most of them are either switched off by default for development convenience or can be bypassed by a single careless line of code. The framework's own security overview says as much: its protections cover cross-site scripting, cross-site request forgery, SQL injection, clickjacking and Host header attacks, provided the developer uses the framework's tools as intended [1].

This article follows one running example: a small document-sharing app called docs, where signed-in users upload files and write notes. Every control below is applied to that app. The snippets come from a companion project whose test suite (18 tests, reproduced in part in the exercises) passes on Django 6.1.2.

2Cross-Site Request Forgery (CSRF)

The threat

In a CSRF attack, a page on another site makes the victim's browser send a state-changing request to your site, and the browser attaches the victim's cookies automatically [5]. If your app relies only on the session cookie to decide who is acting, the forged request succeeds.

How Django defends

CsrfViewMiddleware (on by default in startproject) combines several checks [6]:

  • A secret is stored in the csrftoken cookie; each form carries a csrfmiddlewaretoken field rendered by {% csrf_token %}. The form value is masked differently on every response to defeat BREACH-style compression attacks.
  • Every request whose method is not GET, HEAD, OPTIONS or TRACE must present a token whose secret matches the cookie, or it is rejected with HTTP 403.
  • If the browser sends an Origin header, it must match the current host or an entry in CSRF_TRUSTED_ORIGINS. Over HTTPS without an Origin header, a strict Referer check applies instead.
  • The secret is rotated on every login.

The cookie also defaults to SameSite=Lax, which stops browsers from sending it on most cross-site subrequests [7,8]. OWASP treats SameSite as defence in depth, not as a replacement for a token [5].

Code

<form method="post" action="{% url 'document-delete' doc.pk %}">
  {% csrf_token %}
  <button type="submit">Delete</button>
</form>

For JavaScript clients, read the token from the cookie and send it in the X-CSRFToken header (the default value of CSRF_HEADER_NAME is HTTP_X_CSRFTOKEN) [6]:

function getCookie(name) {
  const m = document.cookie.match(new RegExp("(^|;\\s*)" + name + "=([^;]*)"));
  return m ? decodeURIComponent(m[2]) : null;
}

await fetch(`/docs/${id}/delete/`, {
  method: "POST",
  headers: { "X-CSRFToken": getCookie("csrftoken") },
  credentials: "same-origin",
});

State changes belong behind POST (or PUT/PATCH/DELETE). A GET that deletes data is not protected by any CSRF scheme, which is why OWASP says never to use GET for state-changing operations [5]. Django's require_POST decorator enforces this at the view:

from django.shortcuts import get_object_or_404, redirect
from django.views.decorators.http import require_POST

from .models import Document


@require_POST
def delete_document(request, pk):
    doc = get_object_or_404(Document, pk=pk, owner=request.user)
    doc.delete()
    return redirect("document-list")

Pitfalls

  • @csrf_exempt on a cookie-authenticated view. Exempt only endpoints that authenticate some other way, such as a webhook verified by an HMAC signature.
  • Setting Referrer-Policy: no-referrer site-wide. Over HTTPS, the strict Referer check then fails for browsers that omit Origin, breaking every POST; use rel="noreferrer" on individual links instead [6].
  • Trusting subdomains you do not control. Any subdomain can set cookies for the parent domain, so a hostile subdomain can plant a CSRF cookie [6].
  • Assuming CSRF tokens stop XSS. They do not. Script running in your origin can read the token, so XSS defeats all CSRF defences [5].

from django.http import JsonResponse
from django.shortcuts import get_object_or_404
from django.views.decorators.http import require_POST


@require_POST
def rename(request, pk):
    doc = get_object_or_404(Document, pk=pk, owner=request.user)
    title = request.POST.get("title", "").strip()[:200]
    if not title:
        return JsonResponse({"error": "title required"}, status=400)
    doc.title = title
    doc.save(update_fields=["title"])
    return JsonResponse({"ok": True})

The SPA sends the token in X-CSRFToken. A test that proves the protection is active uses Client(enforce_csrf_checks=True), because the test client skips CSRF checks by default:

def test_post_without_csrf_token_is_rejected(self):

3Cross-Site Scripting (XSS)

The threat

XSS happens when untrusted data reaches a browser in a context where it is interpreted as code. The OWASP prevention cheat sheet's central rule is to encode output for the exact context it lands in: HTML body, attribute, JavaScript, CSS or URL [9].

How Django defends

The Django template language escapes < > ' " & in every variable by default, which the documentation says protects against the majority of XSS attacks [1]. Protection is lost when you opt out: the safe filter, mark_safe(), is_safe on custom filters, or {% autoescape off %} [1]. Autoescaping also targets HTML only; other output formats need their own escaping [1].

Since Django 6.0 the framework also has built-in Content Security Policy support through ContentSecurityPolicyMiddleware and the SECURE_CSP setting, with per-request nonces [10]. CSP is a second line of defence: if an injection slips through, the browser refuses to run scripts the policy does not allow [9,11].

Code

Quote every attribute. An unquoted attribute lets a value containing a space add new attributes, even though it has been escaped [1]:

{# Vulnerable: value "x onmouseover=alert(1)" adds an event handler #}
<div class={{ css_class }}>

{# Safe #}
<div class="{{ css_class }}"></div>

Pass data to JavaScript with json_script, which escapes <, > and & as Unicode escapes, and read it with textContent rather than innerHTML [9]:

{{ doc.title|json_script:"doc-title" }}
<script nonce="{{ csp_nonce }}">
  const title = JSON.parse(document.getElementById("doc-title").textContent);
  document.querySelector("h1").textContent = title;
</script>

When Python code builds HTML, use format_html(), which escapes each argument before interpolation, instead of an f-string wrapped in mark_safe():

from django.utils.html import format_html

# Vulnerable: mark_safe(f'<b class="user">{name}</b>')
badge = format_html('<b class="user">{}</b>', name)
# name = '<img src=x onerror=alert(1)>' renders as
# <b class="user">&lt;img src=x onerror=alert(1)&gt;</b>

A strict nonce-based policy in settings.py. The csp context processor must be enabled for {{ csp_nonce }} to exist in templates [10]:

from django.utils.csp import CSP

MIDDLEWARE += ["django.middleware.csp.ContentSecurityPolicyMiddleware"]
TEMPLATES[0]["OPTIONS"]["context_processors"].append(
    "django.template.context_processors.csp"
)
SECURE_CSP = {
    "default-src": [CSP.SELF],
    "script-src": [CSP.SELF, CSP.NONCE],
    "style-src": [CSP.SELF, CSP.NONCE],
    "img-src": [CSP.SELF, "data:"],
    "object-src": [CSP.NONE],
    "base-uri": [CSP.NONE],
    "frame-ancestors": [CSP.NONE],
    "form-action": [CSP.SELF],
}

Roll a new policy out with SECURE_CSP_REPORT_ONLY first; the browser reports violations without blocking. Django does not collect the reports itself, so you need a report-uri endpoint [10]. Never cache whole responses that contain a nonce, because a reused nonce is no longer secret [10].

Pitfalls

  • Storing user HTML (rich-text editors) and rendering it with |safe. Sanitise it with an allow-list HTML sanitiser on input and output, and keep the sanitiser patched [1,9].
  • Putting template variables inside <script> blocks, inline event handlers or href="javascript:...". These are contexts where HTML escaping is not enough [9].
  • Escaping in an {% autoescape off %} email template and then reusing it for HTML.

Exercise 3.1

This custom filter highlights a search term. Find the XSS bug and fix it without losing the highlighting.

@register.filter
def highlight(text, term):
    return mark_safe(text.replace(term, f"<mark>{term}</mark>"))
Show solution

Both text and term are user-controlled, and mark_safe tells the template engine not to escape the result, so text = "<script>..." executes. Escape the inputs first, then add the only markup you trust:

from django import template
from django.utils.html import escape
from django.utils.safestring import mark_safe

register = template.Library()


@register.filter
def highlight(text, term):
    safe_text, safe_term = escape(text), escape(term)
    if not safe_term:
        return safe_text
    return mark_safe(safe_text.replace(safe_term, f"<mark>{safe_term}</mark>"))

Escaping both before replacing ensures the replacement works on the escaped form, and the only unescaped characters in the output are the <mark> tags the code itself wrote.

4SQL injection prevention

The threat

SQL injection occurs when user input is concatenated into a query string and changes the query's structure. OWASP's primary defence is parameterised queries; escaping input by hand is "strongly discouraged" [12].

How Django defends

QuerySets are built with query parameterisation: the SQL text and its parameters travel separately, and the database driver handles the parameters [1]. Risk returns when you write SQL yourself with raw(), cursor.execute(), extra() or RawSQL [1,13]. Django's security team treats reports that rely on unsanitised input passed to extra() or RawSQL as out of scope, because that is the developer's responsibility [3].

Code

# Safe: ORM lookups are parameterised
Document.objects.filter(owner=request.user, title__icontains=q)

# Vulnerable: string formatting builds the SQL
Document.objects.raw(f"SELECT * FROM docs_document WHERE title = '{q}'")

# Also vulnerable: quoted placeholder
Document.objects.raw("SELECT * FROM docs_document WHERE title = '%s'", [q])

# Safe: unquoted placeholder, value passed as a parameter
Document.objects.raw("SELECT * FROM docs_document WHERE title = %s", [q])

The Django documentation warns specifically against both string formatting and quoting the %s placeholder [13]. Use %s on every backend, including SQLite [13]. A safe raw-cursor helper:

from django.db import connection


def count_titles_raw(user_id, needle):
    with connection.cursor() as cursor:
        cursor.execute(
            "SELECT COUNT(*) FROM docs_document WHERE owner_id = %s AND title LIKE %s",
            [user_id, f"%{needle}%"],
        )
        return cursor.fetchone()[0]

Parameters cannot stand in for identifiers such as column names or ASC/DESC, so user-chosen sort orders must come from an allow-list [12]. A ChoiceField does this for free:

class SearchForm(forms.Form):
    q = forms.CharField(max_length=100)
    order = forms.ChoiceField(
        choices=[("title", "Title"), ("-created", "Newest")], required=False
    )


def search(request):
    form = SearchForm(request.GET)
    results = []
    if form.is_valid():
        order = form.cleaned_data["order"] or "title"  # only allow-listed values
        results = Document.objects.filter(
            owner=request.user, title__icontains=form.cleaned_data["q"]
        ).order_by(order)
    return render(request, "docs/search.html", {"form": form, "results": results})

Pitfalls

  • extra() is an old API that Django plans to deprecate and no longer fixes; use it only as a last resort, always with params [14].
  • Passing **request.GET.dict() straight into filter() lets a user choose lookups across relations (for example owner__password__startswith), which leaks data through timing or result counts. Map allowed filters explicitly.

5Clickjacking protection

The threat

A hostile page loads your site in a transparent frame and tricks the user into clicking buttons they cannot see [15,16].

How Django defends

XFrameOptionsMiddleware, enabled by startproject, sends X-Frame-Options: DENY on every response unless a view sets the header itself [15]. The header is described in RFC 7034, which is informational, not a standard [17]. The CSP frame-ancestors directive is the modern equivalent; when both are present, browsers that follow CSP Level 3 ignore X-Frame-Options, and OWASP recommends sending both [11,16]. Both must be HTTP headers; frame-ancestors does not work in a <meta> tag [11].

Code

# settings.py
X_FRAME_OPTIONS = "DENY"                       # Django's default
SECURE_CSP = {..., "frame-ancestors": [CSP.NONE]}

# views.py: one widget that partners may embed
from django.views.decorators.clickjacking import xframe_options_exempt
from django.views.decorators.csp import csp_override


@xframe_options_exempt
@csp_override({"default-src": [CSP.SELF],
               "frame-ancestors": ["https://partner.example"]})
def embeddable_widget(request):
    ...

The per-view decorators xframe_options_deny, xframe_options_sameorigin and xframe_options_exempt override the middleware for one view [15]. csp_override replaces the whole policy rather than merging with it, so restate every directive you need [10].

Pitfalls

  • JavaScript "frame-busting" code is bypassable (double framing, sandboxed iframes, onbeforeunload tricks) and is a last resort only [16].
  • SameSite cookies make a framed page load logged-out, which helps, but they do not stop framing by a same-site sibling subdomain [16].

6Secure password storage

The threat

Databases leak. When they do, the attacker tries to recover passwords offline at billions of guesses per second. The defence is a deliberately slow, salted, memory-hard or iterated hash [18,19].

What the standards say

  • NIST SP 800-63B-4 (2025): passwords must be salted (salt of at least 32 bits) and hashed with a scheme that resists offline attack, with the cost "as high as practical". Single-factor passwords must be at least 15 characters; passwords used only inside multi-factor authentication at least 8. Verifiers should accept at least 64 characters, must not impose composition rules or periodic changes, and must check new passwords against a blocklist of common or compromised values [19].
  • OWASP Password Storage Cheat Sheet: prefer Argon2id with at least 19 MiB memory, 2 iterations and parallelism 1; otherwise scrypt (N=217, r=8, p=1), bcrypt (cost ≥ 10, 72-byte input limit) or PBKDF2-HMAC-SHA256 with 600,000 iterations [18].
  • RFC 9106 specifies Argon2 and recommends Argon2id [20].

How Django defends

Django stores algorithm$iterations$salt$hash and uses PBKDF2-SHA256 by default [21]. Django 6.1 raised the default iteration count from 1,200,000 to 1,500,000 [22], well above OWASP's floor. Argon2 is supported but needs argon2-cffi (pip install django[argon2]); when you put it first in PASSWORD_HASHERS, existing hashes are upgraded transparently the next time each user logs in, as long as the old hasher stays in the list [21]. Django's Argon2 hasher defaults (time cost 2, memory 100 MiB, parallelism 8) exceed OWASP's minimum.

Code

PASSWORD_HASHERS = [
    "django.contrib.auth.hashers.Argon2PasswordHasher",   # new hashes
    "django.contrib.auth.hashers.PBKDF2PasswordHasher",   # verify + upgrade old ones
    "django.contrib.auth.hashers.PBKDF2SHA1PasswordHasher",
    "django.contrib.auth.hashers.ScryptPasswordHasher",
]

AUTH_PASSWORD_VALIDATORS = [
    {"NAME": "django.contrib.auth.password_validation.UserAttributeSimilarityValidator"},
    {"NAME": "django.contrib.auth.password_validation.MinimumLengthValidator",
     "OPTIONS": {"min_length": 15}},          # NIST 800-63B-4, single-factor
    {"NAME": "django.contrib.auth.password_validation.CommonPasswordValidator"},
    {"NAME": "django.contrib.auth.password_validation.NumericPasswordValidator"},
]

MinimumLengthValidator defaults to 8, and CommonPasswordValidator checks a built-in list of 20,000 common passwords, which partially covers NIST's blocklist requirement [19,21]. Validators run in Django's password forms and in createsuperuser/changepassword, but not in User.objects.create_user(); call validate_password() yourself in custom sign-up code [21].

from django.contrib.auth.password_validation import validate_password

def register(username, email, password):
    user = User(username=username, email=email)
    validate_password(password, user=user)   # raises ValidationError
    user.set_password(password)              # never assign user.password directly
    user.save()
    return user

Pitfalls

  • Removing an old hasher from PASSWORD_HASHERS before every user has logged in again locks those users out [21].
  • Rolling your own hashing with hashlib.sha256(password). Fast hashes are exactly what offline cracking hardware is built for [18].
  • Logging request bodies on the login view, which writes plaintext passwords to logs.

Exercise 6.1

Your legacy table stores unsalted MD5 hashes in legacy_hash. Design a migration that upgrades every account to Argon2 without waiting for users to log in and without ever knowing their passwords.

Show solution

Wrap the old hash: store argon2(md5(password)) now, and verify by computing md5 of the submitted password first. Django's documentation describes this "wrapped hasher" pattern for PBKDF2 [21]; the Argon2 version below also overrides verify(), because Argon2's verification does not go through encode().

# accounts/hashers.py
import hashlib
from django.contrib.auth.hashers import Argon2PasswordHasher


class Argon2WrappedMD5PasswordHasher(Argon2PasswordHasher):
    algorithm = "argon2_wrapped_md5"

    @staticmethod
    def _md5(password):
        return hashlib.md5(password.encode()).hexdigest()

    def encode_md5_hash(self, md5_hash, salt):
        return super().encode(md5_hash, salt)

    def encode(self, password, salt):
        return self.encode_md5_hash(self._md5(password), salt)

    def verify(self, password, encoded):
        # Argon2's verify() does not call encode(), so apply the MD5 step here too
        return super().verify(self._md5(password), encoded)


# migration RunPython function
def forwards(apps, schema_editor):
    User = apps.get_model("auth", "User")
    hasher = Argon2WrappedMD5PasswordHasher()
    for user in User.objects.exclude(legacy_hash="").iterator():
        user.password = hasher.encode_md5_hash(user.legacy_hash, hasher.salt())
        user.legacy_hash = ""
        user.save(update_fields=["password", "legacy_hash"])

Add the wrapped hasher to PASSWORD_HASHERS after Argon2. On each user's next login Django verifies against the wrapped hash and re-hashes with plain Argon2 [21]. Once the migration runs, no MD5 hash remains in the database.

7Session security and cookie settings

The threat

A stolen session identifier is as good as a password. Attackers steal it by sniffing plain HTTP, by XSS reading document.cookie, or by fixation: planting a known session ID before the victim logs in [23].

How Django defends

  • login() calls cycle_key(), issuing a new session key to prevent fixation; logout() calls flush(), deleting the session data and cookie [24].
  • Changing a password invalidates a user's other sessions, because each session stores an HMAC of the password hash; update_session_auth_hash() keeps the current session alive in custom password-change views [25].
  • Sessions are cookie-only; Django never puts session IDs in URLs, where they would leak through the Referer header [24].

The cookie attributes come from RFC 6265: Secure restricts a cookie to secure channels, and HttpOnly hides it from scripts [26]. The newer SameSite attribute is specified in the RFC 6265bis draft [8].

OWASP suggests idle timeouts of 2–5 minutes for high-value applications and 15–30 minutes for low-risk ones, plus an absolute timeout (4–8 hours for a full-day office application) [23]. Django's SESSION_COOKIE_AGE is measured from the last time the session was modified, not read, so an idle timeout needs SESSION_SAVE_EVERY_REQUEST = True or explicit tracking [24].

Code

SESSION_ENGINE = "django.contrib.sessions.backends.cached_db"
SESSION_COOKIE_SECURE = True
SESSION_COOKIE_HTTPONLY = True
SESSION_COOKIE_SAMESITE = "Lax"
SESSION_COOKIE_AGE = 60 * 60 * 8        # absolute ceiling: 8 hours
SESSION_COOKIE_DOMAIN = None            # host-only; never ".example.com" unless required

An idle-timeout middleware that complements the absolute ceiling:

import time
from django.contrib.auth import logout

IDLE_SECONDS = 30 * 60


class IdleTimeoutMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        if request.user.is_authenticated:
            now = int(time.time())
            last = request.session.get("last_seen", now)
            if now - last > IDLE_SECONDS:
                logout(request)           # flushes the session
            else:
                request.session["last_seen"] = now
        return self.get_response(request)

Pitfalls

  • The signed_cookies session backend stores data client-side, signed but not encrypted: users can read it, it can be replayed, and logging out does not invalidate a stolen cookie [24].
  • The pickle serializer turns a leaked SECRET_KEY into remote code execution; keep the default JSON serializer [24].
  • Database sessions are never purged automatically; schedule manage.py clearsessions daily [24].
  • A broad SESSION_COOKIE_DOMAIN sends your session cookie to every subdomain, including ones run by others [24].

Exercise 7.1

A custom login view authenticates with request.session["uid"] = user.pk. What attack does this enable, and what is the one-line fix?

Show solution

Session fixation. The session key is not rotated at login, so an attacker who planted a session ID in the victim's browser (for example from a sibling subdomain) now shares the victim's authenticated session [23,24]. Replace the hand-written assignment with django.contrib.auth.login(request, user), which rotates the key. If you must keep custom logic, call request.session.cycle_key() after authenticating [24]. The test:

def test_login_rotates_session(self):

8HTTPS, HSTS and TLS configuration

The threat

Without TLS, anyone on the network path can read credentials and session cookies or modify pages in transit. Django's deployment checklist calls for HTTPS on the whole site, not only the login page, because the same session cookie travels on every request [27].

Standards

  • TLS 1.3 was published as RFC 8446 (2018) and has been revised as RFC 9846 (2026), which also obsoletes the TLS 1.2 specification RFC 5246 [28].
  • RFC 8996 (BCP 195) says TLS 1.0 and 1.1 MUST NOT be used [29].
  • NIST SP 800-52 Rev. 2 requires TLS 1.2 support and required TLS 1.3 support by 1 January 2024 for US government systems [30]. OWASP says web applications must default to TLS 1.3 and may keep TLS 1.2 for compatibility, using AEAD cipher suites with forward secrecy [31].
  • HTTP Strict Transport Security (RFC 6797) makes the browser refuse plain HTTP for a host for max-age seconds; browsers ignore the header when it arrives over plain HTTP [32].

How Django fits in

TLS is terminated by your web server or load balancer, not by Django. Django's SecurityMiddleware redirects HTTP to HTTPS and sets the HSTS header [1,7]. Behind a proxy, Django sees plain HTTP unless you tell it which header carries the original scheme. The documentation warns that getting SECURE_PROXY_SSL_HEADER wrong can create CSRF vulnerabilities [1]: set it only if the proxy always overwrites that header.

Code

# settings.py
SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https")
SECURE_SSL_REDIRECT = True
SECURE_HSTS_SECONDS = 3600            # stage 1: one hour
# SECURE_HSTS_SECONDS = 31_536_000    # stage 2: one year, after a clean week
SECURE_HSTS_INCLUDE_SUBDOMAINS = True # only if every subdomain serves HTTPS
SECURE_HSTS_PRELOAD = False           # stage 3, see below
# nginx: terminate TLS, drop unknown hosts, overwrite the scheme header
server {
    listen 80 default_server;
    return 444;                                   # unknown Host: close
}
server {
    listen 80;
    server_name docs.example.com;
    return 301 https://$host$request_uri;
}
server {
    listen 443 ssl;
    http2 on;
    server_name docs.example.com;
    ssl_certificate     /etc/letsencrypt/live/docs.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/docs.example.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_prefer_server_ciphers off;
    client_max_body_size 10m;                     # cap uploads before Django
    location / {
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;   # overwrites client value
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_pass http://127.0.0.1:8000;
    }
}

The first server block follows Django's checklist advice to reject requests for unknown hosts at the web server as well as through ALLOWED_HOSTS [27].

HSTS preload

Preloading puts your domain in the browsers' built-in HSTS list, protecting even the first visit. Submission requires max-age of at least 31,536,000 seconds, includeSubDomains and preload, and every subdomain must serve HTTPS. Removal takes months to reach users [33]. Raise max-age in stages, as Django's documentation also cautions that careless HSTS can cause serious, irreversible problems [7].

9CORS configuration

What CORS is, and is not

The browser's same-origin policy stops a script on one origin from reading responses from another. Cross-Origin Resource Sharing, defined in the WHATWG Fetch Standard, lets a server relax that rule for chosen origins with Access-Control-Allow-* response headers [34,35]. An origin is the triple of scheme, host and port [36]. CORS is a relaxation, never a protection: adding CORS headers can only expose more data. It also does not stop requests from being sent, so it is no substitute for CSRF protection.

Requests that are not "simple" (for example JSON bodies or custom headers) trigger a preflight OPTIONS request first. The wildcard Access-Control-Allow-Origin: * is not allowed on credentialed requests; the server must name the origin and send Access-Control-Allow-Credentials: true [35].

Django configuration

Django has no built-in CORS support; the widely used package is django-cors-headers. Its middleware must sit as high as possible, before CommonMiddleware, so it can add headers to every response [37].

INSTALLED_APPS += ["corsheaders"]
MIDDLEWARE.insert(1, "corsheaders.middleware.CorsMiddleware")  # after SecurityMiddleware

CORS_ALLOWED_ORIGINS = ["https://app.example.com"]   # exact origins, with scheme
CORS_URLS_REGEX = r"^/api/.*$"                        # only the API, not the whole site
CORS_ALLOW_CREDENTIALS = False                        # token auth, no cookies

If the browser app must send cookies, set CORS_ALLOW_CREDENTIALS = True, list the SPA origin in CSRF_TRUSTED_ORIGINS too, and keep CSRF protection on [6,37].

Pitfalls

  • CORS_ALLOW_ALL_ORIGINS = True combined with cookie authentication lets any website read authenticated responses if credentials are also allowed.
  • Regexes such as r"https://.*example\.com" also match https://evilexample.com. Anchor them: r"^https://([a-z0-9-]+\.)?example\.com$".
  • Allowing the origin null, which sandboxed iframes and local files send [37].

10Secret management and environment variables

Why SECRET_KEY matters

SECRET_KEY signs sessions (for non-cache backends), cookie-stored messages, password-reset tokens and everything that uses django.core.signing; Django's settings reference warns that a leaked key can lead to privilege escalation and remote code execution [7,38]. Signing proves data was not tampered with, but it does not hide it: signed values remain readable [38].

Where secrets should live

The Twelve-Factor App argues for keeping configuration in environment variables, with the test that the codebase could be open-sourced at any moment without compromising credentials [39]. OWASP adds a caution: environment variables are visible to all processes and may end up in logs or crash dumps, so a mounted file or a secrets manager is preferable where available [40]. Django's checklist shows both forms: os.environ["SECRET_KEY"] or reading /etc/secret_key.txt [27].

Code

import os
from pathlib import Path
from django.core.exceptions import ImproperlyConfigured


def secret(name):
    """Read NAME from a mounted file (NAME_FILE) or the environment."""
    if path := os.environ.get(f"{name}_FILE"):
        return Path(path).read_text().strip()
    try:
        return os.environ[name]
    except KeyError:
        raise ImproperlyConfigured(f"Set {name} or {name}_FILE") from None


SECRET_KEY = secret("DJANGO_SECRET_KEY")
SECRET_KEY_FALLBACKS = [k for k in os.environ.get("DJANGO_SECRET_KEY_FALLBACKS", "").split(",") if k]
DATABASES = {"default": {
    "ENGINE": "django.db.backends.postgresql",
    "NAME": "docs", "USER": "docs_app",
    "PASSWORD": secret("DATABASE_PASSWORD"),
    "HOST": os.environ.get("DATABASE_HOST", "localhost"),
}}

Generate keys with a cryptographically secure generator. Python's secrets module exists for this, and its documentation says to prefer it over random, which is designed for simulation, not security [41]:

python -c "import secrets; print(secrets.token_urlsafe(50))"

Rotating the key

Set the new key as SECRET_KEY and move the old one to the front of SECRET_KEY_FALLBACKS. Fallbacks are used only to verify, never to sign, so existing sessions and tokens stay valid while new ones use the new key. Remove the old key once the tokens it signed have expired [7,38].

from django.core import signing

token = signing.dumps({"uid": 7}, salt="unsubscribe")      # signed with old key
# ...deploy: SECRET_KEY=new, SECRET_KEY_FALLBACKS=[old]
signing.loads(token, salt="unsubscribe", max_age=3600)     # {'uid': 7}
# ...after expiry: SECRET_KEY_FALLBACKS=[]  -> BadSignature

Pitfalls

  • Keys starting django-insecure-, or shorter than 50 characters, trigger security.W009 in check --deploy.
  • Committing .env files. Add them to .gitignore and run secret detection in pre-commit hooks and CI, as OWASP recommends [40].
  • Baking secrets into container images with ENV or ARG [40].
  • DEBUG = True in production shows settings and local variables on error pages [27].

11File-upload security

The threat

An upload is attacker-controlled bytes with an attacker-controlled name and an attacker-controlled Content-Type. Risks include stored XSS (an "image" that is really HTML), path traversal through the filename, server-side execution, resource exhaustion and malware distribution [42].

What Django does and does not do

Django streams uploads larger than FILE_UPLOAD_MAX_MEMORY_SIZE (2.5 MB) to temporary files and caps the number of files per request with DATA_UPLOAD_MAX_NUMBER_FILES (default 100) [7,43]. Its security guide is blunt about the rest: no framework-level technique can safely validate all uploaded content. A file with a valid PNG header followed by HTML passes Pillow's verification, so serve uploads from a separate top-level domain (a subdomain is not enough), cap body size at the web server, and make sure the server never executes uploaded files [1].

Code

The OWASP cheat sheet's core list: an extension allow-list, a file-type check that does not trust Content-Type, a generated filename, a size limit, storage outside the web root, and least-privilege permissions [42]:

# docs/validators.py
from pathlib import Path
from django.core.exceptions import ValidationError

MAX_UPLOAD_BYTES = 5 * 1024 * 1024
SIGNATURES = {
    ".pdf": [b"%PDF-"],
    ".png": [b"\x89PNG\r\n\x1a\n"],
    ".jpg": [b"\xff\xd8\xff"],
    ".jpeg": [b"\xff\xd8\xff"],
}


def validate_upload(f):
    ext = Path(f.name).suffix.lower()
    if ext not in SIGNATURES:
        raise ValidationError("Unsupported file type.")
    if f.size > MAX_UPLOAD_BYTES:
        raise ValidationError("File too large (max 5 MB).")
    head = f.read(16)
    f.seek(0)
    if not any(head.startswith(sig) for sig in SIGNATURES[ext]):
        raise ValidationError("File content does not match its extension.")
# docs/models.py
import uuid
from pathlib import Path


def upload_to(instance, filename):
    ext = Path(filename).suffix.lower()          # already allow-listed
    return f"uploads/{instance.owner_id}/{uuid.uuid4().hex}{ext}"


class Document(models.Model):
    owner = models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=models.CASCADE,
                              related_name="documents")
    title = models.CharField(max_length=200)
    file = models.FileField(upload_to=upload_to, blank=True)

Serve files through an authorizing view rather than a public MEDIA_URL, forcing download and sandboxing anything the browser might render:

def download(request, pk):
    doc = get_object_or_404(Document, pk=pk, owner=request.user)
    response = FileResponse(doc.file.open("rb"), as_attachment=True,
                            filename=f"document-{doc.pk}{Path(doc.file.name).suffix}")
    response["Content-Security-Policy"] = "default-src 'none'; sandbox"
    return response
# settings.py
MEDIA_ROOT = BASE_DIR / "private-media"     # outside the web server's document root
DATA_UPLOAD_MAX_NUMBER_FILES = 10
FILE_UPLOAD_PERMISSIONS = 0o640             # always use the 0o prefix
FILE_UPLOAD_DIRECTORY_PERMISSIONS = 0o750

Magic-byte checks are easy to defeat when used alone [42], which is why this design also renames, forces download and sandboxes. For higher-risk documents, add antivirus scanning or content disarm and reconstruction (CDR) as OWASP suggests [42].

Pitfalls

  • FILE_UPLOAD_PERMISSIONS = 644 (decimal, without 0o) sets the wrong mode [7].
  • Relying on DATA_UPLOAD_MAX_MEMORY_SIZE to limit uploads: file uploads are not counted against it, and under ASGI the whole body may be spooled to disk first. Set client_max_body_size (nginx) or LimitRequestBody (Apache) [1,7].
  • Using the user's filename in os.path.join(); ../../ sequences escape the target directory.

12Authentication versus authorization

Two different questions

Authentication establishes who the user is; authorization decides what that user may do. Django's auth system handles both, which is why its documentation calls them "somewhat coupled" [25]. Broken access control, the authorization failure, is the number one category in the OWASP Top 10:2025 [2].

Authentication in Django

Since Django 5.1, LoginRequiredMiddleware makes every view require login unless marked with @login_not_required [25,44]. That turns authentication into deny-by-default, which OWASP recommends [45].

MIDDLEWARE = [
    ...,
    "django.contrib.auth.middleware.AuthenticationMiddleware",
    "django.contrib.auth.middleware.LoginRequiredMiddleware",
    ...,
]

from django.contrib.auth.decorators import login_not_required

@login_not_required
def api_ping(request):
    return JsonResponse({"ok": True})

For multi-factor authentication, which OWASP calls by far the best defence against password attacks [46], use a maintained third-party package (for example django-otp or django-allauth's MFA support); Django core does not include MFA.

Authorization in Django

Model permissions (add, change, delete, view) are created automatically; check them with user.has_perm("app.codename"), @permission_required or PermissionRequiredMixin [25]. Model permissions are type-level: "may edit documents". Most real bugs are object-level: "may edit this document". OWASP's guidance is to check access to the specific object on every request, not to rely on unguessable IDs [45].

# Vulnerable (IDOR): any logged-in user can read any document by changing pk
def document_detail(request, pk):
    doc = get_object_or_404(Document, pk=pk)

# Fixed: scope the query to the owner; other users get 404, not 403
def document_detail(request, pk):
    doc = get_object_or_404(Document, pk=pk, owner=request.user)
    return render(request, "docs/detail.html", {"doc": doc})


@permission_required("docs.publish_document", raise_exception=True)
@require_POST
def publish(request, pk):
    doc = get_object_or_404(Document, pk=pk, owner=request.user)
    ...

Returning 404 rather than 403 for other users' objects avoids confirming that the object exists. For class-based views, override get_queryset() so every generic view inherits the scoping.

class OwnedQuerysetMixin:
    def get_queryset(self):
        return super().get_queryset().filter(owner=self.request.user)


class DocumentUpdate(OwnedQuerysetMixin, UpdateView):
    model = Document
    fields = ["title", "body"]

Pitfalls

  • Permission caching: ModelBackend caches permissions on the user object, so re-fetch the user after granting a permission in the same request [25].
  • Granting staff users "change user" in the admin effectively makes them superusers, because they can edit their own permissions [25].
  • Hiding a button in the template is not authorization; client-side checks never count [45].

13Rate limiting and brute-force protection

The threat

Online guessing comes in two shapes: many passwords against one account (brute force), and one leaked password against many accounts (credential stuffing). NIST SP 800-63B-4 requires verifiers to limit consecutive failed attempts on an account to no more than 100 [19]. OWASP's credential-stuffing guidance favours MFA first, then layered controls such as graduated throttling, CAPTCHA and breached-password checks, and warns that simple IP blocking alone is weak [46].

Django tools

Django core has no login throttling. Two maintained packages fill the gap:

  • django-ratelimit provides a decorator that limits by IP, user or a request field; it needs a shared cache backend with atomic increments, such as Redis or Memcached, not the database cache [47]. When a limit is exceeded with block=True it raises Ratelimited, a subclass of PermissionDenied, so the default response is 403.
  • django-axes records failed logins and locks out by IP, username, user agent or combinations, with cool-off periods [48].

HTTP 429 Too Many Requests, with an optional Retry-After header, is the standard status for rate limiting [49].

Code

from django.contrib.auth.views import LoginView
from django.utils.decorators import method_decorator
from django_ratelimit.decorators import ratelimit


@method_decorator(ratelimit(key="ip", rate="20/m", method="POST"), name="post")
@method_decorator(ratelimit(key="post:username", rate="5/m", method="POST"), name="post")
class RateLimitedLoginView(LoginView):
    template_name = "docs/login.html"

Keying by post:username slows guessing against one account even when the attacker rotates IP addresses; keying by IP slows one machine trying many accounts. Convert the exception into a proper 429:

from django.http import HttpResponse
from django_ratelimit.exceptions import Ratelimited


class RatelimitTo429Middleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        return self.get_response(request)

    def process_exception(self, request, exception):
        if isinstance(exception, Ratelimited):
            response = HttpResponse("Too many requests. Try again later.", status=429)
            response["Retry-After"] = "60"
            return response
        return None

Pitfalls

  • Behind a proxy, REMOTE_ADDR is the proxy's address, so every user shares one IP bucket. Configure RATELIMIT_IP_META_KEY to read the client IP from a header your proxy sets and overwrites [47].
  • LocMemCache is per-process; with four workers the effective limit is four times higher. Use a shared cache [47].
  • Locking accounts hard after a few failures lets an attacker lock out real users on purpose. Prefer short, growing delays and notify the user [46].
  • Password-reset and sign-up forms need limits too; they are used for account enumeration.

14Dependency vulnerability scanning

The threat

Most of a Django project's code is other people's code. "Software Supply Chain Failures" is A03 in the OWASP Top 10:2025 [2]. OWASP recommends automated dependency analysis from the very start of a project, because adding it late produces a backlog that is hard to clear [50]. 16GDPR and sensitive-data handling

What the regulation requires of the code

The General Data Protection Regulation, Regulation (EU) 2016/679, applies to personal data: any information relating to an identified or identifiable natural person (Article 4(1)) [55]. The obligations that translate most directly into Django code are:

  • Principles (Article 5(1)): data minimisation (collect only what is necessary), storage limitation (keep it no longer than necessary), and integrity and confidentiality (appropriate security) [55].
  • Special categories (Article 9): health, biometric, genetic and similar data are prohibited by default and need a specific legal condition [55].
  • Data subject rights: access (Article 15), erasure (Article 17), and data portability in a structured, commonly used, machine-readable format (Article 20) [55].
  • Data protection by design and by default (Article 25) [55,56].
  • Security of processing (Article 32), which names "the pseudonymisation and encryption of personal data" and regular testing of security measures as examples [55].
  • Breach notification (Article 33): notify the supervisory authority without undue delay and, where feasible, within 72 hours of becoming aware of a breach, unless it is unlikely to result in a risk to individuals [55].

The legal analysis (lawful basis, records of processing, processors) belongs with your data protection officer; this section covers the engineering.

Minimise and pseudonymise

# Keep identifiers out of logs: log a keyed hash instead of the email address
import hashlib, hmac
from django.conf import settings


def pseudonym(value: str) -> str:
    key = settings.PSEUDONYM_KEY.encode()          # separate from SECRET_KEY
    return hmac.new(key, value.lower().encode(), hashlib.sha256).hexdigest()[:16]

logger.info("password reset requested user=%s", pseudonym(email))

Pseudonymised data is still personal data under the GDPR, because it can be re-linked with the key, but it reduces exposure in logs and analytics [55]. Avoid putting personal data in URLs, which are recorded by proxies and sent in Referer headers; Django's default SECURE_REFERRER_POLICY = "same-origin" limits the latter [1,7].

Encrypt sensitive fields

Django has no built-in field encryption. The cryptography package's Fernet recipe provides authenticated symmetric encryption; keep the key out of the database, and use MultiFernet for rotation [57].

from cryptography.fernet import Fernet, MultiFernet
from django.conf import settings
from django.db import models

_fernet = MultiFernet([Fernet(k) for k in settings.FIELD_ENCRYPTION_KEYS])


class EncryptedTextField(models.TextField):
    def get_prep_value(self, value):
        if value is None:
            return value
        return _fernet.encrypt(value.encode()).decode()

    def from_db_value(self, value, expression, connection):
        if value is None:
            return value
        return _fernet.decrypt(value.encode()).decode()

Encrypted columns cannot be filtered or indexed by their plaintext. Encrypt the fields that are sensitive and rarely queried (national ID numbers, health notes), and rely on disk and backup encryption for the rest.

Storage limitation in practice

# management/commands/purge_stale_data.py
from datetime import timedelta
from django.core.management.base import BaseCommand
from django.utils import timezone


class Command(BaseCommand):
    help = "Delete data past its retention period."

    def handle(self, *args, **options):
        cutoff = timezone.now() - timedelta(days=365 * 2)
        stale = User.objects.filter(last_login__lt=cutoff, is_staff=False)
        self.stdout.write(f"Deleting {stale.count()} inactive accounts")
        for user in stale.iterator():
            for doc in user.documents.all():
                doc.file.delete(save=False)
            user.delete()

Schedule it with clearsessions. Remember that backups also hold personal data; document how long they are kept.
