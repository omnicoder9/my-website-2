Introduction: two different problems

"Async" in a Django project usually means one of two different things, and mixing them up leads to poor designs.

  • Concurrency inside a request. A single process waits on many slow I/O operations (HTTP calls to other services, long-lived WebSocket or streaming connections) without tying up one thread per connection. This is the job of asyncio, ASGI and async views.
  • Work outside the request. Sending email, generating a report, resizing images, or calling a flaky payment provider should not make the user wait or be lost when a web process restarts. This is the job of a task queue (Celery, or Django's own Tasks framework) backed by a durable broker such as Redis or RabbitMQ.

Async views do not replace a task queue: a coroutine started in a web process dies with that process, and nothing retries it. A task queue does not make a page faster to render either; it moves work elsewhere. Most production systems need both, and the sections below build up each in turn.

1ASGI versus WSGI

WSGI (PEP 3333) defines a synchronous interface: the application is a callable that takes two positional arguments, conventionally environ and start_response, and must return an iterable yielding zero or more bytestrings[1]. A request occupies its worker (process or thread) from start to finish, so concurrency equals the number of workers.

# The whole WSGI contract (PEP 3333)
def application(environ, start_response):
    start_response("200 OK", [("Content-Type", "text/plain")])
    return [b"Hello, WSGI"]

ASGI was designed because WSGI's "design is irrevocably tied to the HTTP-style request/response cycle", while protocols such as WebSocket do not follow that pattern[2]. An ASGI application is a coroutine application(scope, receive, send): scope describes the connection, receive is awaited for incoming events, and send is awaited to emit events[2].

# The ASGI contract: one coroutine per connection, events in and out
async def application(scope, receive, send):
    assert scope["type"] == "http"
    await send({"type": "http.response.start", "status": 200,
                "headers": [(b"content-type", b"text/plain")]})
    await send({"type": "http.response.body", "body": b"Hello, ASGI"})

Django supports both. startproject creates <project>/asgi.py with an application callable for any ASGI server; runserver does not use it[3]. Django's ASGI deployment guide documents Daphne, Granian, Hypercorn and Uvicorn[3], and the WSGI guide covers the traditional servers[4].

Hidden cost

Under ASGI, every synchronous middleware between the server and an async view forces a switch to a thread and back. Django's bundled middleware supports both modes, but third-party middleware may not, and the adaptation can be found by enabling debug logging for django.request and looking for "Asynchronous handler adapted for middleware …"[5].

2Synchronous and asynchronous views

Any view becomes async by returning a coroutine, usually via async def. For class-based views, the HTTP handler methods (get(), post()) are declared async def, not __init__() or as_view(). Django detects async views with inspect.iscoroutinefunction[5].

shop/views.py
import asyncio
import httpx                         # any asyncio-native HTTP client
from django.http import JsonResponse
from django.views import View

# Sync view: three upstream calls happen one after another.
def dashboard_sync(request):
    with httpx.Client(timeout=2) as client:
        a = client.get("https://pricing.internal/api").json()
        b = client.get("https://stock.internal/api").json()
        c = client.get("https://reviews.internal/api").json()
    return JsonResponse({"pricing": a, "stock": b, "reviews": c})

# Async view: the three calls overlap, so latency ~= the slowest one.
async def dashboard(request):
    async with httpx.AsyncClient(timeout=2) as client:
        a, b, c = await asyncio.gather(
            client.get("https://pricing.internal/api"),
            client.get("https://stock.internal/api"),
            client.get("https://reviews.internal/api"),
        )
    return JsonResponse({"pricing": a.json(), "stock": b.json(), "reviews": c.json()})

# Class-based: only the handlers are async.
class HealthView(View):
    async def get(self, request):
        return JsonResponse({"ok": True})

Decorators such as never_cache, csrf_exempt and require_GET work on async views; when a decorator is applied through method_decorator on dispatch, dispatch itself must be async def[5].

When the client goes away

If a client disconnects during a long-lived request, Django raises asyncio.CancelledError inside the view. Catch it only to clean up, then re-raise[5]:

async def report_preview(request):
    try:
        data = await expensive_upstream_query()
    except asyncio.CancelledError:
        await release_upstream_slot()
        raise                       # never swallow cancellation
    return JsonResponse(data)

Choosing between sync and async views

  • Use async for views that mostly wait on network I/O that has an async client, and for streaming responses served over ASGI.
  • Keep views sync when they are mostly ORM work inside transactions, or CPU-bound. Django adapts between modes for you, but each switch has a cost: tens of microseconds per request on the ASGI path and a few hundred microseconds in the cold-start path[5].
  • Never do slow work inline just because the view is async. If it must survive a restart or be retried, enqueue it (§7).

3async and await

PEP 492 (Python 3.5) introduced native coroutines declared with async def, the await expression, and the async with and async for statements; using await outside an async def function is a SyntaxError[6]. PEP 525 (Python 3.6) added asynchronous generators: async def functions containing yield, which are what streaming responses consume[7].

The key mental model is cooperative multitasking: a coroutine runs until it reaches an await on something not yet ready, and only then can the event loop run something else. A blocking call (synchronous ORM query, time.sleep, requests.get) stalls every coroutine on that loop.

Structured concurrency and timeouts

Python 3.11 added asyncio.TaskGroup and the asyncio.timeout() family[8]. A task group waits for all its children and cancels the rest if one fails, which is safer than loose create_task calls.

import asyncio

async def fetch_all(client, urls):
    results = {}
    async with asyncio.timeout(3):              # deadline for the whole batch
        async with asyncio.TaskGroup() as tg:
            tasks = {u: tg.create_task(client.get(u)) for u in urls}
    # Leaving the TaskGroup block means every task finished (or all were cancelled).
    for url, task in tasks.items():
        results[url] = task.result().status_code
    return results
Fire-and-forget pitfall

The event loop only keeps weak references to tasks, so "a task that isn't referenced elsewhere may get garbage collected at any time, even before it's done"[8]. Keep a strong reference (or use a TaskGroup). In a web process, prefer a real task queue for fire-and-forget work: it survives restarts and can retry.

Calling blocking code from async code

asyncio.to_thread() (Python 3.9+) runs a blocking function in a thread[8]. Inside Django, use asgiref.sync.sync_to_async instead, because it is aware of Django's thread-sensitive components. Its default thread_sensitive=True runs the function in the same thread as other thread-sensitive calls; async_to_sync goes the other way and preserves thread-locals and contextvars[5].

from asgiref.sync import sync_to_async, async_to_sync

def legacy_pdf_render(order_id):          # blocking library
    ...

async def invoice_view(request, order_id):
    pdf = await sync_to_async(legacy_pdf_render)(order_id)
    ...

# From sync code (e.g. a management command) calling an async API:
result = async_to_sync(fetch_all)(client, urls)

Django warns against wrapping each row or operation of a tight loop; move the whole loop inside one sync_to_async() call[5].

4Async-compatible database access

Every QuerySet method that might block, such as get() or delete(), has an a-prefixed variant (aget(), adelete()), and results can be iterated with async for. Methods that only build a query (filter(), exclude()) do not run SQL and can be chained freely[9]. Model methods have async forms too, such as asave() and acreate()[5].

library/views.py
from django.http import JsonResponse, Http404
from .models import Author, Book

async def author_detail(request, pk):
    try:
        author = await Author.objects.aget(pk=pk)
    except Author.DoesNotExist:
        raise Http404
    books = [b.title async for b in Book.objects.filter(author=author).order_by("title")]
    count = await Book.objects.filter(author=author).acount()
    return JsonResponse({"name": author.name, "books": books, "count": count})

async def add_book(request, pk):
    book = await Book.objects.acreate(author_id=pk, title=request.POST["title"])
    return JsonResponse({"id": book.pk}, status=201)

The three rules that bite

  1. No sync ORM calls on the event loop. Django's async-unsafe parts raise SynchronousOnlyOperation when called from a thread with a running event loop[5]. Forgetting await produces errors like "coroutine object has no attribute x"[9].
  2. No implicit lazy loading. Relations are deferred by default; touching entry.blog without having prefetched it during async evaluation attempts a blocking query and raises SynchronousOnlyOperation. Use select_related() or prefetch_related()[9].
  3. No async transactions yet. Transactions are not supported with async queries; put transactional code in a synchronous function and call it with sync_to_async[5,9].
from asgiref.sync import sync_to_async
from django.db import transaction
from django.db.models import F

def _transfer(src_id, dst_id, amount):
    with transaction.atomic():
        src = Account.objects.select_for_update().get(pk=src_id)
        if src.balance < amount:
            raise InsufficientFunds
        Account.objects.filter(pk=src_id).update(balance=F("balance") - amount)
        Account.objects.filter(pk=dst_id).update(balance=F("balance") + amount)

async def transfer_view(request):
    await sync_to_async(_transfer)(request.POST["src"], request.POST["dst"], int(request.POST["amount"]))
    return JsonResponse({"ok": True})

# Avoid lazy-loading in async code: fetch the relation up front.
async def latest_entry(request):
    entry = await Entry.objects.select_related("blog").alatest("pub_date")
    return JsonResponse({"blog": entry.blog.name})
Connections and pooling

Django advises disabling persistent connections (CONN_MAX_AGE) in async mode and using the database's pooling or a third-party pooler; concurrent requests in one process share that pool, so size it for the in-flight query concurrency you expect[5]. Django 6.0 also added AsyncPaginator and AsyncPage[10].

The environment variable DJANGO_ALLOW_ASYNC_UNSAFE disables the safety check, but Django warns it risks data loss or corruption under concurrent access and should not be used in production[5]; it exists mainly for notebooks.

5Django Channels and WebSockets

WebSocket (RFC 6455) starts as an HTTP Upgrade request that the server accepts with 101 Switching Protocols; browsers send an Origin header that servers use to protect against unauthorised cross-origin use, and the ws/wss schemes default to ports 80 and 443[11]. Plain Django views cannot hold such a connection; Django Channels adds ASGI routing for WebSockets, consumers (the WebSocket equivalent of views) and channel layers for cross-process messaging.

Setup

Install with python -m pip install -U 'channels[daphne]', put daphne first in INSTALLED_APPS, and point ASGI_APPLICATION at your routing object[12].

mysite/asgi.py
import os
from channels.auth import AuthMiddlewareStack
from channels.routing import ProtocolTypeRouter, URLRouter
from channels.security.websocket import AllowedHostsOriginValidator
from django.core.asgi import get_asgi_application

os.environ.setdefault("DJANGO_SETTINGS_MODULE", "mysite.settings")
# Initialise Django first so the app registry is ready before importing consumers/models.
django_asgi_app = get_asgi_application()

from notifications.routing import websocket_urlpatterns  # noqa: E402

application = ProtocolTypeRouter({
    "http": django_asgi_app,
    "websocket": AllowedHostsOriginValidator(
        AuthMiddlewareStack(URLRouter(websocket_urlpatterns))
    ),
})

This mirrors the official tutorial, including initialising the Django ASGI app before importing routing, and AllowedHostsOriginValidator, which checks the WebSocket Origin against ALLOWED_HOSTS[13].

A per-user notification consumer

notifications/consumers.py
from channels.generic.websocket import AsyncJsonWebsocketConsumer

class NotificationConsumer(AsyncJsonWebsocketConsumer):
    async def connect(self):
        user = self.scope["user"]                # set by AuthMiddlewareStack
        if not user.is_authenticated:
            await self.close()
            return
        self.group = f"user.{user.pk}"
        await self.channel_layer.group_add(self.group, self.channel_name)
        await self.accept()

    async def disconnect(self, code):
        if hasattr(self, "group"):
            await self.channel_layer.group_discard(self.group, self.channel_name)

    async def receive_json(self, content):
        if content.get("type") == "ping":
            await self.send_json({"type": "pong"})

    # Handles events whose "type" is "notify.message" (dots become underscores).
    async def notify_message(self, event):
        await self.send_json({"type": "notification", "text": event["text"]})
notifications/routing.py
from django.urls import path
from .consumers import NotificationConsumer

websocket_urlpatterns = [path("ws/notifications/", NotificationConsumer.as_asgi())]

as_asgi() plays the role of as_view() and creates a consumer instance per connection[13]. An event's type selects the handler method, with periods replaced by underscores[14]. Inside async consumers, access the ORM with the async query API or the database_sync_to_async adapter, and read the authenticated user from scope["user"][15].

Pushing from anywhere (views, Celery tasks)

The channel layer is async-only, so synchronous code calls it through async_to_sync[14]:

from asgiref.sync import async_to_sync
from channels.layers import get_channel_layer

def notify_user(user_id: int, text: str) -> None:
    async_to_sync(get_channel_layer().group_send)(
        f"user.{user_id}", {"type": "notify.message", "text": text}
    )

Groups are pure broadcast; you cannot list their members[14]. Treat the channel layer as a real-time fan-out mechanism, not as a durable queue: if delivery must be guaranteed, store the notification in the database first and use the WebSocket only to signal that something new exists.

6Server-Sent Events (SSE) integration

SSE is a one-way, server-to-browser stream over ordinary HTTP. The format's MIME type is text/event-stream; streams are always UTF-8; the fields are event, data, id and retry; lines starting with a colon are comments, which can be sent "every 15 seconds or so" to keep proxies from dropping idle connections; browsers resend the last seen id in a Last-Event-ID header on reconnect; and a 204 No Content response tells the client to stop reconnecting[16]. For dashboards, progress bars and notifications, SSE is simpler than WebSockets and needs no Channels.

In Django, use StreamingHttpResponse with an async iterator under ASGI. Under WSGI the iterator should be synchronous; a mismatched iterator is fully consumed with a warning, which defeats streaming. If the client disconnects, Django cancels the coroutine, and you can catch asyncio.CancelledError to clean up[17].

progress/views.py
import asyncio, json
from django.http import StreamingHttpResponse, HttpResponse
from django.views.decorators.http import require_GET
from .models import Job

def sse(data: dict, *, event: str | None = None, id: str | None = None) -> str:
    lines = []
    if event: lines.append(f"event: {event}")
    if id: lines.append(f"id: {id}")
    lines.append(f"data: {json.dumps(data)}")
    return "\n".join(lines) + "\n\n"      # blank line terminates the event

async def job_events(job_id):
    last = None
    yield "retry: 5000\n\n"                   # ask the browser to wait 5 s before reconnecting
    try:
        while True:
            job = await Job.objects.only("status", "progress").aget(pk=job_id)
            state = (job.status, job.progress)
            if state != last:
                last = state
                yield sse({"status": job.status, "progress": job.progress},
                          event="progress", id=str(job.progress))
            else:
                yield ": keep-alive\n\n"
            if job.status in ("SUCCESS", "FAILURE"):
                return
            await asyncio.sleep(1)
    except asyncio.CancelledError:
        raise                                 # client went away; nothing to clean up here

@require_GET
async def job_stream(request, job_id):
    if not await Job.objects.filter(pk=job_id, owner_id=request.user.pk).aexists():
        return HttpResponse(status=204)        # tells EventSource to stop reconnecting
    resp = StreamingHttpResponse(job_events(job_id), content_type="text/event-stream")
    resp["Cache-Control"] = "no-cache"
    resp["X-Accel-Buffering"] = "no"         # disable nginx proxy buffering for this response
    return resp
client
const es = new EventSource(`/jobs/${jobId}/stream/`);
es.addEventListener("progress", (e) => {
  const { status, progress } = JSON.parse(e.data);
  bar.value = progress;
  if (status === "SUCCESS" || status === "FAILURE") es.close();
});

Notes: request.user in an async view is resolved lazily from the session, so in code that must stay fully async prefer await request.auser(). Streaming responses cannot carry ETag or Content-Length, and many middleware cannot inspect them[17]. Polling the database every second per client is fine for modest traffic; at scale, have the worker publish to Redis and have the stream subscribe (§8), or use a Channels AsyncHttpConsumer, which supports SSE through send_headers/send_body[15]. The X-Accel-Buffering header is an nginx-specific convention; consult your proxy's documentation.

7Background job processing with Celery

Celery is the most widely used task queue for Django: the web process publishes a message describing a function call to a broker, and separate worker processes execute it. Django 6.0 also introduced a built-in Tasks framework (django.tasks) with a @task decorator and .enqueue(), but Django ships no worker: its two built-in backends are for development and testing, and production needs a third-party backend[10,18]. This article uses Celery, which provides workers, retries, scheduling and monitoring today.

Wiring Celery into Django

With the CELERY namespace every Celery option is written in uppercase with a CELERY_ prefix; @shared_task lets reusable apps define tasks without importing the project's app; and a development worker is started with celery -A proj worker -l INFO[19].

Defining and calling tasks

orders/tasks.py
from celery import shared_task
from django.core.mail import send_mail
from .models import Order

@shared_task
def send_order_confirmation(order_id: int) -> None:
    order = Order.objects.select_related("customer").get(pk=order_id)
    send_mail(f"Order #{order.pk} confirmed", "Thanks!", None, [order.customer.email])
orders/views.py
from django.db import transaction

def checkout(request):
    with transaction.atomic():
        order = Order.objects.create(customer=request.user.customer, total=cart_total(request))
        # Publish only after COMMIT, so the worker can see the row.
        send_order_confirmation.delay_on_commit(order.pk)
    return redirect("order-done", order.pk)

# With execution options (delay() does not accept them):
send_order_confirmation.apply_async(args=[order.pk], countdown=60, expires=3600, queue="email")
Four habits that prevent most Celery bugs
  1. Enqueue after commit. delay_on_commit() (Celery 5.4+) defers publishing until the transaction commits; on older versions wrap the call in transaction.on_commit(functools.partial(task.delay, ...))[19,20]. Callbacks registered in a transaction that is rolled back are discarded[21].
  2. Pass identifiers, not objects. The default serializer is JSON[22]; send primary keys and reload fresh state in the worker, as the Celery task guide recommends for Django model objects[20].
  3. Never wait on a subtask inside a task. Calling .get() inside a task can deadlock when the pool is exhausted; use chains or callbacks[20].
  4. Design every task to run more than once (§11).

Composing work: chains, groups and chords

Celery's canvas primitives describe workflows: a signature wraps one task invocation (add.s(2, 2); .si() makes it immutable), a chain runs signatures one after another, a group runs tasks in parallel, and a chord runs a body after its header group finishes[23].

from celery import chain, chord

# Resize all images in parallel, then build the gallery, then notify.
workflow = chain(
    chord([resize.s(img_id) for img_id in image_ids], build_gallery.s(album_id)),
    notify_owner.si(album_id),
)
workflow.apply_async()

8Redis as a broker or cache

Redis can play three distinct roles in a Django stack, and they have conflicting requirements.

As a Celery broker

The URL format is redis://:password@hostname:port/db_number[24]. The Redis transport emulates acknowledgements with a visibility timeout, 1 hour by default: a task not acknowledged within that window is redelivered. Consequently, tasks with an ETA or countdown longer than the visibility timeout can be executed "again, and again in a loop", and Celery advises against raising the timeout to fit long ETAs[24]. Redis must also not evict broker keys: set maxmemory-policy to noeviction or allkeys-lru if you see InconsistencyErrors[24].

CELERY_BROKER_URL = "redis://redis:6379/0"
CELERY_BROKER_TRANSPORT_OPTIONS = {"visibility_timeout": 3600}  # must exceed your longest task
CELERY_RESULT_BACKEND = "redis://redis:6379/1"

As Django's cache

Django ships a native Redis cache backend, django.core.cache.backends.redis.RedisCache, which uses redis-py (with hiredis recommended)[25]. The cache API has a-prefixed async methods such as aset() and ahas_key(), but Django notes that truly asynchronous cache backends are not yet supported[25].

CACHES = {
    "default": {
        "BACKEND": "django.core.cache.backends.redis.RedisCache",
        "LOCATION": "redis://cache-redis:6379",
    }
}
Separate broker and cache

A cache is expected to evict data under memory pressure; a broker must not lose messages. Because the broker needs an eviction policy that keeps its keys[24] while a cache is usually run with LRU eviction, use separate Redis instances (not merely separate database numbers, since maxmemory-policy is per instance) for the two roles.

As a pub/sub or stream bus

Redis Pub/Sub "exhibits at-most-once message delivery semantics": offline subscribers miss messages. Redis Streams persist entries and support at-least-once delivery through consumer groups (XADD, XREADGROUP, XACK), with a pending entries list for unacknowledged messages and XAUTOCLAIM to take over a dead consumer's work[26,27]. Pub/Sub is fine for live progress updates; use Streams (or a broker) for events that must not be lost.

# Worker publishes progress; an async SSE view relays it (redis-py asyncio API).
import redis.asyncio as aioredis

async def progress_events(job_id):
    r = aioredis.from_url("redis://redis:6379/2")
    async with r.pubsub() as ps:
        await ps.subscribe(f"job:{job_id}")
        async for msg in ps.listen():
            if msg["type"] == "message":
                yield f"data: {msg['data'].decode()}\n\n"

9RabbitMQ as a message broker

RabbitMQ implements AMQP 0-9-1: publishers send messages to exchanges, which route copies to queues according to bindings; consumers receive from queues. Exchange types are direct, fanout, topic and headers, and a nameless default exchange routes to the queue whose name equals the routing key[28]. With explicit acknowledgements the broker removes a message only after the consumer acknowledges it and redelivers if the consumer dies; durable queues survive a restart, but messages must also be published as persistent; and prefetch limits unacknowledged messages per channel[28].

RabbitMQ is Celery's default broker and uses amqp://user:password@host:5672/vhost URLs. A dedicated user and virtual host are created with rabbitmqctl add_user, add_vhost and set_permissions[29].

$ rabbitmqctl add_user app secret
$ rabbitmqctl add_vhost app
$ rabbitmqctl set_permissions -p app app ".*" ".*" ".*"

Quorum queues

Quorum queues are "a durable, replicated queue based on the Raft consensus algorithm" and RabbitMQ recommends them as the default for replicated, highly available queues; since RabbitMQ 4.0 they apply a default delivery limit of 20, after which poison messages are dropped or dead-lettered[30]. Celery supports them from 5.5 via task_default_queue_type, with caveats: global QoS is disabled, autoscaling does not work, and ETA/countdown tasks rely on native delayed delivery[29].

CELERY_TASK_DEFAULT_QUEUE_TYPE = "quorum"
CELERY_BROKER_TRANSPORT_OPTIONS = {"confirm_publish": True}
CELERY_TASK_ROUTES = {
    "orders.tasks.send_order_confirmation": {"queue": "email"},
    "reports.tasks.*": {"queue": "reports"},
}

Celery recommends task_routes over hard-coding queue names at call sites; workers subscribe with -Q[22], for example celery -A proj worker -Q reports --concurrency 2.

Either way, delivery is at-least-once: redeliveries carry a redeliver flag and RabbitMQ says consumers "must be prepared to handle redeliveries"[31].

11Retries, timeouts and idempotency

Distributed systems fail partially. A worker can crash after charging a card but before recording it; a broker can redeliver a message that was already processed. The defence has three parts: retry transient failures, bound every operation in time, and make every effect idempotent so that retries and redeliveries are harmless.

Retries

Celery offers manual retries with bind=True and self.retry() (default max_retries 3, default delay 180 s) and automatic retries with autoretry_for; retry_backoff=True produces delays of 1 s, 2 s, 4 s and so on, capped by retry_backoff_max (default 600 s), and retry_jitter (default True) randomises them[20]. Jitter matters because synchronised retries from many clients hammer a recovering service at the same moment[34]. Publishing itself is also retried by default according to retry_policy[22].

Timeouts

A task may have a hard time_limit, after which the worker kills and replaces the process, and a soft_time_limit, which raises SoftTimeLimitExceeded so the task can clean up; time limits do not work on platforms without SIGUSR1[35,36]. Celery recommends setting explicit timeouts on operations such as HTTP requests and treating time limits as a safety net[20]. In async code, use asyncio.timeout()[8].

Idempotency

RFC 9110 defines a method as idempotent when the intended effect of several identical requests is the same as for a single one[37]. Celery says "ideally task functions should be idempotent"[20], and late acknowledgement (acks_late=True), which redelivers a task if the worker dies mid-execution, is only safe when they are[20]. For HTTP APIs that trigger jobs, the IETF Idempotency-Key header draft standardises a client-supplied key that lets servers recognise retried POSTs[38].

payments/tasks.py
import httpx
from celery import shared_task
from celery.exceptions import SoftTimeLimitExceeded
from django.db import transaction
from .models import Payment

class TransientGatewayError(Exception):
    pass

@shared_task(
    bind=True,
    acks_late=True,                    # redeliver if the worker dies mid-task ...
    autoretry_for=(TransientGatewayError, httpx.TransportError),
    retry_backoff=True, retry_backoff_max=300, retry_jitter=True,
    retry_kwargs={"max_retries": 6},
    soft_time_limit=30, time_limit=45,
)
def capture_payment(self, payment_id: int) -> str:
    # ... so the task must be idempotent. Step 1: claim the work atomically.
    with transaction.atomic():
        p = Payment.objects.select_for_update().get(pk=payment_id)
        if p.status == Payment.CAPTURED:
            return "already-captured"        # duplicate delivery: no-op

    # Step 2: call the provider with a stable idempotency key, so a retry after
    # an ambiguous failure (timeout) cannot charge twice.
    try:
        r = httpx.post(
            "https://psp.example/captures",
            json={"intent": p.provider_intent_id, "amount": p.amount_cents},
            headers={"Idempotency-Key": f"capture-{p.pk}"},
            timeout=10,
        )
    except SoftTimeLimitExceeded:
        raise TransientGatewayError("soft time limit")
    if r.status_code >= 500 or r.status_code == 429:
        raise TransientGatewayError(r.status_code)
    r.raise_for_status()                 # 4xx: permanent, do not retry

    # Step 3: record the outcome with a conditional update (safe to repeat).
    Payment.objects.filter(pk=p.pk).exclude(status=Payment.CAPTURED).update(
        status=Payment.CAPTURED, provider_ref=r.json()["id"]
    )
    return "captured"

Deduplication with a short-lived lock

Where no natural idempotency exists, a Redis key set with NX (only if absent) and EX (expiry) can suppress concurrent duplicates. Redis documents this pattern but recommends a random token released only by its owner, and notes that the Redlock algorithm gives stronger guarantees[39]. A lock is an optimisation; a database uniqueness constraint is the real guarantee.

import uuid
import redis
r = redis.Redis.from_url("redis://redis:6379/3")

RELEASE = "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end"

@shared_task
def rebuild_search_index(shard: int):
    key, token = f"lock:reindex:{shard}", uuid.uuid4().hex
    if not r.set(key, token, nx=True, ex=600):
        return "skipped: already running"
    try:
        do_reindex(shard)
    finally:
        r.eval(RELEASE, 1, key, token)
Late acks have sharp edges

With acks_late, a message is still acknowledged if the child process is killed; task_reject_on_worker_lost requeues it instead, but Celery warns this "can cause message loops"[20,36]. Pair it with a delivery limit (quorum queues default to 20[30]) and idempotent code.

12Event-driven processing

In an event-driven design, code announces that something happened ("order placed") and independent handlers react (send email, reserve stock, update analytics) without the producer knowing them.

In-process: Django signals

Signals decouple code inside one process, but they are synchronous function calls: send() returns only after every receiver has run, and an exception in a receiver can stop the others unless send_robust() is used[40]. Async receivers are supported, asend() must be awaited, and since Django 6.1 async receivers run concurrently in an asyncio.TaskGroup[40]. Django itself recommends direct calls where possible because signals can make code hard to follow[40]. Use a signal to enqueue work, not to do it.

from django.db.models.signals import post_save
from django.dispatch import receiver

@receiver(post_save, sender=Order, dispatch_uid="order-placed-email")
def on_order_saved(sender, instance, created, **kwargs):
    if created:
        send_order_confirmation.delay_on_commit(instance.pk)

Across processes: the transactional outbox

Writing to the database and publishing to a broker are two separate systems, so one can succeed while the other fails. on_commit narrows the window[21], but a crash between commit and publish still loses the event. The transactional outbox pattern stores the event in an outbox table in the same transaction as the business change; a separate relay publishes it, and because the relay may publish twice, consumers must be idempotent[41].

events/models.py and events/tasks.py
class OutboxEvent(models.Model):
    id = models.UUIDField(primary_key=True, default=uuid.uuid4)
    topic = models.CharField(max_length=100)       # e.g. "order.placed"
    payload = models.JSONField()
    created = models.DateTimeField(auto_now_add=True, db_index=True)
    published = models.DateTimeField(null=True, db_index=True)

def place_order(cart):
    with transaction.atomic():
        order = Order.objects.create(...)
        OutboxEvent.objects.create(topic="order.placed", payload={"order_id": order.pk})
    return order

HANDLERS = {"order.placed": ["orders.tasks.send_order_confirmation_evt",
                            "inventory.tasks.reserve_stock_evt"]}

@shared_task
def relay_outbox(batch_size=200):         # run every few seconds via beat
    with transaction.atomic():
        events = list(OutboxEvent.objects.select_for_update(skip_locked=True)
                      .filter(published__isnull=True).order_by("created")[:batch_size])
        for evt in events:
            for task_name in HANDLERS.get(evt.topic, []):
                current_app.send_task(task_name, kwargs={"event_id": str(evt.id), **evt.payload})
            evt.published = timezone.now()
        OutboxEvent.objects.bulk_update(events, ["published"])

class ProcessedEvent(models.Model):          # consumer-side idempotency ledger
    event_id = models.UUIDField()
    handler = models.CharField(max_length=100)
    class Meta:
        constraints = [models.UniqueConstraint(fields=["event_id", "handler"], name="uniq_evt_handler")]

A consumer inserts into ProcessedEvent inside the same transaction as its own effect; an IntegrityError means "already handled". For fan-out to other services, publish to a RabbitMQ topic exchange[28] or a Redis Stream with consumer groups[27]; for fan-out to browsers, forward to a Channels group[14].

13Long-running tasks and task monitoring

Making long tasks behave

  • Prefetch. worker_prefetch_multiplier defaults to 4 messages per process; for long tasks Celery suggests 1 so short tasks are not stuck behind a reserved long one[36]. Route long tasks to their own queue and workers (§9).
  • Visibility timeout. On Redis, a task running longer than the visibility timeout is redelivered to another worker[24].
  • Memory. worker_max_tasks_per_child recycles prefork processes after N tasks, which contains leaks[35].
  • Chunking. Split huge jobs into a group/chord of smaller tasks[23]; each piece can retry independently.
  • Cancellation. Revoking skips a queued task; terminate=True kills a running one but is a last resort that should never be called programmatically[35]. Prefer a cooperative "cancel requested" flag that the task checks between chunks.

Reporting progress

With task_track_started a task reports STARTED; built-in states also include PENDING (also used for unknown ids), RETRY, SUCCESS, FAILURE and REVOKED, and custom states can be set with self.update_state(state="PROGRESS", meta={...})[20,36]. Results expire after one day by default[36].

reports/tasks.py
import csv, io
from celery import shared_task
from django.core.files.base import ContentFile

@shared_task(bind=True, acks_late=True, soft_time_limit=1800, time_limit=1900)
def export_orders(self, export_id: int):
    export = Export.objects.get(pk=export_id)
    qs = Order.objects.filter(created__date__range=(export.start, export.end)).order_by("pk")
    total = qs.count() or 1
    buf = io.StringIO()
    writer = csv.writer(buf)
    for i, order in enumerate(qs.iterator(chunk_size=2000), start=1):
        writer.writerow([order.pk, order.total, order.created.isoformat()])
        if i % 2000 == 0:
            export.refresh_from_db(fields=["cancel_requested"])
            if export.cancel_requested:
                Export.objects.filter(pk=export_id).update(status="CANCELLED")
                return "cancelled"
            pct = int(i * 100 / total)
            self.update_state(state="PROGRESS", meta={"done": i, "total": total})
            Export.objects.filter(pk=export_id).update(progress=pct)   # durable copy for the UI
            notify_user(export.owner_id, f"Export {pct}% done")      # §5 channel layer push
    export.file.save(f"orders-{export_id}.csv", ContentFile(buf.getvalue()), save=False)
    Export.objects.filter(pk=export_id).update(status="SUCCESS", progress=100, file=export.file.name)
    return export.file.name

What to alert on

Queue depth and age of the oldest message per queue; task failure and retry rates by task name; task runtime percentiles against the soft time limit; worker count and restarts; and a beat heartbeat task (like the one in §10) whose absence pages someone. Exercise 3: Concurrency with a deadline

Write async def first_quote(urls) that requests all URLs concurrently and returns the body of the first successful response, cancelling the rest, with an overall 2-second deadline that raises TimeoutError.

Show solution 
import asyncio, httpx

async def first_quote(urls):
    async with httpx.AsyncClient(timeout=2) as client, asyncio.timeout(2):
        pending = {asyncio.create_task(client.get(u)) for u in urls}
        try:
            while pending:
                done, pending = await asyncio.wait(pending, return_when=asyncio.FIRST_COMPLETED)
                for t in done:
                    if not t.exception() and t.result().is_success:
                        return t.result().text
            raise RuntimeError("all upstreams failed")
        finally:
            for t in pending:
                t.cancel()

asyncio.timeout() raises TimeoutError when the deadline passes[8]; the finally block cancels stragglers, and the pending set holds strong references so tasks are not garbage-collected early[8]. A TaskGroup is less convenient here because a "first wins" race is not an all-must-succeed pattern.

Exercise 5: Chat room consumer

class RoomConsumer(AsyncJsonWebsocketConsumer):
    async def connect(self):
        self.user = self.scope["user"]
        if not self.user.is_authenticated:
            return await self.close()
        self.slug = self.scope["url_route"]["kwargs"]["slug"]
        self.group = f"room.{self.slug}"
        await self.channel_layer.group_add(self.group, self.channel_name)
        await self.accept()

    async def disconnect(self, code):
        if hasattr(self, "group"):
            await self.channel_layer.group_discard(self.group, self.channel_name)

    async def receive_json(self, content):
        text = str(content.get("text", ""))[:2000]
        if not text:
            return
        await Message.objects.acreate(room_slug=self.slug, author=self.user, text=text)
        await self.channel_layer.group_send(self.group, {
            "type": "room.message", "user": self.user.get_username(), "text": text})

    async def room_message(self, event):
        await self.send_json({"user": event["user"], "text": event["text"]})

# routing: re_path(r"ws/rooms/(?P<slug>[-\w]+)/$", RoomConsumer.as_asgi())

Exercise 7: A safe webhook sender

Write a Celery task deliver_webhook(delivery_id) that POSTs a stored payload to a customer URL. Requirements: 10 s request timeout; retry on network errors and 5xx with exponential backoff and jitter up to 8 attempts; never retry on 4xx; never deliver the same delivery_id successfully twice even if the message is redelivered.

Show solution 
class Retryable(Exception): pass

@shared_task(bind=True, acks_late=True, autoretry_for=(Retryable, httpx.TransportError),
             retry_backoff=True, retry_backoff_max=600, retry_jitter=True,
             retry_kwargs={"max_retries": 7}, soft_time_limit=20, time_limit=30)
def deliver_webhook(self, delivery_id):
    d = WebhookDelivery.objects.get(pk=delivery_id)
    if d.delivered_at:
        return "duplicate"
    r = httpx.post(d.url, json=d.payload, timeout=10,
                   headers={"Idempotency-Key": str(d.uuid)})   # lets receivers dedupe too
    if r.status_code >= 500:
        raise Retryable(r.status_code)
    WebhookDelivery.objects.filter(pk=d.pk, delivered_at__isnull=True).update(
        delivered_at=timezone.now(), status_code=r.status_code, attempts=self.request.retries + 1)
    return r.status_code

max_retries=7 gives eight attempts in total; backoff and jitter options are Celery's[20]; jitter avoids synchronised retry storms[34]. A 4xx is recorded and not retried. The delivered_at check plus the conditional update make redelivery harmless, though a crash between the POST and the update can still cause one duplicate POST, which is why the Idempotency-Key header is sent[38]. True exactly-once delivery to an external system is not possible; "at-least-once plus idempotent receiver" is the practical goal[31,41].

Summary checklist

  • Deploy with ASGI only when you have async code, and keep the middleware stack async-capable[5].
  • In async code, use a-prefixed ORM methods, prefetch relations, and wrap transactions in sync_to_async[9].
  • Use Channels for bidirectional real-time, SSE for one-way streams; persist anything that must not be lost[14,16].
  • Enqueue after commit, pass ids, never block on subtasks[20].
  • Keep broker and cache Redis separate; prefer RabbitMQ quorum queues when you need replication and rich routing[24,30].
  • Run exactly one beat; avoid long ETAs[22,32].
  • Retry with backoff and jitter, bound every call in time, and make every task idempotent[20,34].
  • Use an outbox for events that must survive crashes, and idempotent consumers[41].
  • Track progress in your own models; monitor queue depth, failures and runtimes with Flower or Prometheus[42,43].
