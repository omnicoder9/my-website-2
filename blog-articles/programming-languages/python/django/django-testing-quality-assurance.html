Django Testing and Quality Assurance

A working guide to testing a Django and Django REST framework application, from fast unit tests to a real browser, plus the static checks that catch bugs before any test runs. Every code listing below comes from one small project, and every listing was run.

$ pytest --cov=shop tests solutions
77 passed in 4.8s · TOTAL 158 stmts, 14 branches · 100.00%
$ ruff check . && ruff format --check . && mypy shop config
All checks passed! · 28 files already formatted · Success: no issues found in 14 source files

Tested on 28 October 2026 with Python 3.13.17, Django 6.1.2, Django REST framework 3.18.3, pytest 9.2.0, pytest-django 4.14.0, pytest-cov 7.1.0, factory_boy 3.3.3, Hypothesis 6.170.12, responses 0.26.3, coverage.py 7.17.0, Ruff 0.17.3, mypy 2.4.0, django-stubs 6.1.2 and Playwright 1.64.1.

Tests are only useful if they are fast enough to run constantly, precise enough to point at the broken line, and trustworthy enough that a green run means something. This article builds that kind of suite for a small bookshop application. Each section introduces one technique, shows the real code, and cites the documentation that defines the behaviour being relied on. Sources are numbered in the order they are first cited, following the Vancouver system, and listed in full at the end.

1The example project

The application is a bookshop with three models (Author, Book, Order), a few HTML views, a REST API, an order service that reserves stock inside a database transaction, and a client for an external exchange-rate API. That mix gives every kind of test something real to do.

The test settings module changes only one thing. Django's documentation notes that the default password hasher is slow by design and recommends a faster hasher in test settings when many users are created or authenticated 1.

Email in Django 6.1. Django 6.1 introduced the MAILERS setting and deprecated EMAIL_BACKEND. The test runner automatically replaces every configured mailer with the in-memory backend, so tests can inspect django.core.mail.outbox without sending anything 2. The project's settings.py therefore defines MAILERS = {"default": {"BACKEND": "django.core.mail.backends.console.EmailBackend"}}.

2Unit, integration, and end-to-end tests

Tests are usually grouped by how much of the system they exercise. The test pyramid gives the standard advice: write lots of small, fast unit tests, some coarser-grained tests, and very few high-level tests that drive the application from end to end. The higher a test sits, the slower and more brittle it tends to be. An inverted shape, with many end-to-end tests and few unit tests, is sometimes called the "ice-cream cone" 3.

Counts are the 64 tests in tests/, grouped by whether each test needs the database or a browser.

A unit test

Unit tests for pure functions need no database and no Django test case. pytest's parametrize marker runs one test body over a table of inputs 4, which suits boundary values such as rounding at half a cent.

An end-to-end test

An end-to-end test needs a running server. Django's LiveServerTestCase launches a live server in the background for the duration of the test 5, and pytest-django exposes the same thing as the live_server fixture, which depends on transactional_db 6. Playwright's pytest plugin supplies a fresh browser page per test and runs headless unless you pass --headed 7.

Why the environment variable? Playwright's synchronous API keeps an event loop running in the test thread. Django raises SynchronousOnlyOperation when its ORM is called from a thread with a running event loop, and DJANGO_ALLOW_ASYNC_UNSAFE disables that check. Django's documentation warns that doing so can cause data loss under concurrent access and must never be used in production 8. It is acceptable here only because the test process is single-purpose.

Keep end-to-end tests for the few journeys that would cost real money if they broke, such as sign-in and checkout. The marker e2e is registered in pyproject.toml, so pytest -m "not e2e" gives a fast loop during development.

3Django TestCase and the test client

Django's test framework is built on Python's standard unittest module, which provides test cases, fixtures, suites and runners 9. Tests that need a database never touch the real one: Django creates a separate blank test database (named by prefixing test_, or in memory for SQLite) and destroys it afterwards unless you pass --keepdb 1.

Choosing a base class

The summary above follows Django's testing-tools reference 5. Because TestCase rolls back instead of truncating, it is much faster, and the runner orders the suite so that all TestCase subclasses run first, then other Django tests, then plain unittest tests that might leave the database dirty 1.

setUpTestData: create once, use many times

TestCase.setUpTestData() runs once per class inside a class-level atomic block. Objects created there are shared across the class's tests, and Django gives each test a fresh copy (they must support copy.deepcopy()), so mutations do not leak. This is faster than recreating the data in setUp() 5. Section 4 uses it for model tests.

The test client

The test client acts as a dummy browser: it resolves URLs, runs middleware and views, renders templates, and returns the response with extra attributes such as response.context and, with follow=True, response.redirect_chain 5. Two ways to log in matter:

  • client.login(username=..., password=...) goes through the authentication backends and returns True on success.
  • client.force_login(user) skips authentication. It is faster because the password hash is never computed, and it even works for inactive users 5.

Use force_login in nearly every test and keep one or two login tests that prove real credentials work.

Running the suite

--parallel runs one process per core by default, --keepdb skips creating and destroying the test database, and --shuffle randomises order with a printed seed so that tests which depend on each other are exposed and the failing order can be replayed 10. The bookshop suite passes under --shuffle.

4Model and view testing

Models

Test the behaviour you wrote, not Django itself: custom save() logic, properties, querysets, __str__, URL generation and validators. Note that validators run in full_clean(), not in save(), so a validation test must call full_clean() explicitly.

BookFactory.build() creates an unsaved instance, which is enough for testing a property and avoids a database write. Factories are covered in section 8.

Views

View tests sit at the integration level. They check status codes, templates, context, rendered content and redirects. The helpers assertContains, assertTemplateUsed and assertRedirects make the intent explicit and produce clearer failure messages than comparing raw bytes 5.

assertNumQueries pins the number of SQL queries a block may run 5. Here it protects the select_related("author") call: if someone removes it, the template's {{ book.author }} triggers one extra query per book, and the test fails with the list of queries that ran.

RequestFactory for isolated views. When you want to call a view function directly, RequestFactory builds a request without running middleware. Session and authentication attributes such as request.user must then be set by the test 11. pytest-django exposes it as the rf fixture 6.

5API tests using Django REST framework

DRF ships its own test helpers. APIClient has the same interface as Django's client but understands DRF content negotiation, and format="json" encodes the request body as JSON instead of the default multipart. response.data holds the data the response was built from, so assertions do not need to parse response.content. APITestCase and its siblings mirror Django's test case classes but use APIClient 12.

Shared pytest fixtures live in conftest.py, where every test module in the directory can request them by naming them as arguments 13. force_authenticate sets request.user directly, bypassing authentication 12.

pytest-django blocks database access by default. A test must opt in with the django_db marker or the db fixture, which keeps accidental queries out of unit tests 14. Setting pytestmark at module level applies the marker to every test in the file.

The last test checks visibility rather than permissions: a draft owned by someone else returns 404, not 403, because get_queryset() never includes it. Returning 404 avoids revealing that the object exists.

6Authentication and permission tests

Security rules deserve exhaustive, table-driven tests, because a missing check rarely shows up in normal use. Two facts from DRF's documentation shape these tests.

  • 401 or 403? An authenticated request that is denied gets 403 Forbidden. An unauthenticated request gets 401 Unauthorized only if the first authentication class sends a WWW-Authenticate header; otherwise it gets 403 15. TokenAuthentication sends WWW-Authenticate: Token; SessionAuthentication sends no header and so produces 403 16. The bookshop lists token authentication first, so anonymous writes get 401.
  • Object permissions. has_object_permission() runs only after the view-level checks pass and only when the view calls check_object_permissions(), which generic views do in get_object(). Read-only methods are listed in SAFE_METHODS 15.

The file tests the permission at two levels. The parametrised API tests prove that the permission is actually wired into the view. The unit test against IsOwnerOrReadOnly covers every method and ownership combination without routing, which is where it is cheapest to be thorough. The CSRF test matters because session-authenticated API requests must carry a CSRF token. DRF only enforces CSRF for authenticated session requests 16, and APIClient skips the check unless it is created with enforce_csrf_checks=True 12.

7Mocking external services

Tests must never depend on a third-party server: it makes them slow and flaky, and it can cost money. The bookshop's exchange-rate client wraps every failure in a domain exception, so callers handle one error type.

There are three common ways to replace the dependency, each at a different layer.

  1. unittest.mock.patch replaces a Python object. Patch the name where it is looked up, not where it is defined 17. Here that is shop.rates.requests.get. autospec=True makes the mock enforce the real signature, so calling it with wrong arguments raises TypeError just as the real code would 17.
  2. responses intercepts the requests library at the transport layer 18, so your real request-building and error-handling code runs. Matchers assert on the query string or body.
  3. pytest's monkeypatch swaps attributes and environment variables and undoes every change when the test finishes 19. pytest-django's settings fixture does the same for Django settings 6.

Mock at the boundary. Mock the thing you do not own (the HTTP call), not your own functions. A test that mocks get_rate while testing get_rate proves nothing. Prefer responses or autospec mocks, so that a change to the real API breaks the test instead of passing silently.

8Factories, fixtures, and test data

Every test needs data, and how you create it decides how readable and how fragile the suite is. There are three main options.

ApproachStrengthsWeaknesses
Django JSON/YAML fixtures (fixtures = [...])Realistic reference data; produced by dumpdataBreak when models change; hide what a test depends on
Factories (factory_boy)Each test states only the fields it cares about; valid defaults for the restNeed maintaining alongside models
pytest fixturesCompose and share setup through conftest.py; scopes from function to sessionCan become a hidden dependency web if overused

Factories with factory_boy

DjangoModelFactory saves through Model.objects.create(), and django_get_or_create reuses an existing row instead of failing on a unique field 20. Sequence generates unique values, SubFactory builds related objects, and Trait bundles a named variation such as sold_out=True 21.

Tests then read like specifications: BookFactory(sold_out=True) says exactly which detail the test cares about. create_batch(10) makes ten books for the query-count test in section 4.

Django fixtures

Fixtures are files of serialised data, written by hand or with manage.py dumpdata, and loaded with loaddata or a test case's fixtures attribute. Django looks for them in each app's fixtures/ directory and in FIXTURE_DIRS 22. With TestCase they are loaded once per class; with TransactionTestCase they are reloaded before every test because the tables are flushed 5.

Use fixtures for stable reference data such as countries or currency codes, and factories for everything a test manipulates.

pytest fixtures

pytest fixtures are functions that tests request by name. They can have function, class, module, package or session scope, and a fixture that yields runs its teardown code after the test 13. The bookshop's auth_client fixture composes api_client and user, and pytest resolves the chain automatically.

9Database transaction testing

place_order() must either reserve stock and create the order, or do neither. It also sends a confirmation email, which must happen only if the order really commits.

Django's atomic() commits a block if it completes and rolls it back if an exception escapes. transaction.on_commit() callbacks run only after a successful commit and are discarded on rollback 23.

There is a catch for tests. TestCase wraps every test in a transaction that it never commits, so on_commit() callbacks never run. Django's fix is captureOnCommitCallbacks(), which collects the callbacks and, with execute=True, runs them when the block exits 23,5. To test real commit and rollback, or code that must run inside a transaction such as select_for_update(), use TransactionTestCase 5. In pytest, the equivalents are @pytest.mark.django_db(transaction=True) 14 and the django_capture_on_commit_callbacks fixture 6.

test_failure_after_order_rolls_back_stock is the important one. It makes Order.objects.create raise after the stock UPDATE has run, and proves that the update is rolled back with it. Without atomic(), the shop would lose stock every time order creation failed.

Database realism. These tests run on SQLite, which accepts select_for_update() but has no row locks to take. Concurrency tests that rely on row locking need the production database engine, usually PostgreSQL, in CI.

10Coverage measurement

coverage.py records which lines and branches run during the tests. With branch measurement on, it also compares the transitions that actually happened with the ones static analysis says are possible. An if whose condition was always true is reported as a partial branch 24. Django's documentation shows the plain workflow, coverage run --source='.' manage.py test followed by coverage report 11. With pytest, the pytest-cov plugin does both 25.

coverage.py reads [tool.coverage.*] tables from pyproject.toml 26. This is the real report for the 64 tests in tests/:

Read the Missing column as a to-do list. Line 79 of models.py is Order.__str__. Line 29 of services.py is the quantity < 1 guard, and the partial branch shows that its condition was never true. Lines 39 to 44 of views.py are the error paths of the order view. Exercises 1 and 2 close these gaps and bring the total to 100%.

What coverage cannot tell you. Coverage shows what ran, not what was checked. A test with no assertions still raises the number. Treat a coverage floor (fail_under) as a ratchet that stops untested code from slipping in, not as proof of quality. A real bug in the order view (exercise 7) sat on lines that already had coverage.

11Regression testing

A regression test pins down a bug that has been fixed so it cannot quietly return. Django's own contribution checklist asks of every bug fix whether there is "a proper regression test (the test should fail before the fix is applied)" 27. The workflow is:

  1. Reproduce the bug in a test and watch the test fail for the reason in the bug report.
  2. Fix the code.
  3. Watch the test pass, then keep it in the suite permanently, named after the issue.

Issue 42 was a real failure mode of a naive slugify(title). Two books with the same title collided on the unique slug column. The fix is unique_slug() in models.py, and the test documents both the bug and the expected suffixes. Exercise 7 walks through the full cycle for a new bug, including the failing output before the fix.

The whole suite is a regression suite for every previous change. Running it on every push, as section 14 sets up, and occasionally with --shuffle, catches regressions in behaviour and in test isolation 10.

12Property-based testing with Hypothesis

Example-based tests check the inputs you thought of. Hypothesis is a property-based testing library: you describe a range of inputs with strategies and state a property that should hold for all of them, and @given generates the inputs 28,29. By default it tries 100 examples per test 30. When a test fails, Hypothesis reports a minimal failing example, shrunk from whatever input first failed 31, and saves it to a local .hypothesis database so it is replayed first on the next run. @example adds an explicit input that runs every time 32.

Good properties for apply_discount are not "the answer is X" but invariants: the result is never negative and never more than the price, a larger discount never costs more, and a zero discount changes nothing.

Tests that touch the database must use hypothesis.extra.django.TestCase (or TransactionTestCase) so that each generated example, not just each test method, runs in its own transaction. from_model() builds a strategy for model instances from the field definitions 30. The Django extra is installed with pip install "hypothesis[django]" 33.

13Linting, formatting, and type checking

Static checks find whole classes of defects without running anything: unused imports, bare except, unsafe defaults, type mismatches. They also end arguments about style. PEP 8 is the shared style baseline for Python code 34, and PEP 484 defines the type-hint syntax that type checkers read 35.

Ruff: linter and formatter

Ruff is a linter and formatter written in Rust. Its documentation describes it as 10 to 100 times faster than tools like Flake8 and Black, with over 900 built-in rules, able to replace Flake8 and its plugins, isort, pyupgrade and others, and configured from pyproject.toml 36. ruff format is designed as a drop-in replacement for Black: on Black-formatted projects such as Django, more than 99.9% of lines come out identical. ruff format --check exits non-zero without rewriting files, which is what CI needs 37.

The rule prefixes select pycodestyle (E, W), Pyflakes (F), import sorting (I), bugbear (B), pyupgrade (UP), Django-specific checks (DJ), pytest style (PT), Bandit security checks (S) and simplifications (SIM) 38. On its first run against the project, Ruff reported 37 findings, including a model without __str__ (DJ008), an unused import (F401), nested with statements that could be combined (SIM117) and many PT009 warnings. PT009 prefers bare assert to self.assertEqual. That conflicts with Django's TestCase, whose assertion methods give better messages, so the configuration ignores it in test files. Configuration should encode decisions like that one.

mypy with django-stubs

mypy is a static type checker for Python designed for gradual typing, so annotations can be added a module at a time 39. Django's metaprogramming (managers, related fields, settings) needs help, which django-stubs provides as type stubs plus a mypy plugin enabled in pyproject.toml 40. djangorestframework-stubs does the same for DRF 41.

Continuous integration

A minimal GitHub Actions workflow runs the static checks first, because they are fastest, then the tests with a coverage floor. The action versions follow GitHub's Python guide 45. makemigrations --check exits non-zero when a model change has no migration 10.

Run the browser tests in a separate job after playwright install --with-deps chromium, so a slow or flaky browser never blocks the fast feedback.
