Caching and Performance in Django

A practical technical article for Python and Django engineers · Written against Django 6.1, Python 3.13+ and PostgreSQL 18 · October 2026

Most slow Django applications are not slow because Python is slow. They are slow because they repeat work: the same query on every request, the same template fragment rendered a thousand times, the same bytes sent to a browser that already has them, or a fresh database connection opened for every page. This article works through the main tools for removing that repeated work, then shows how to measure whether a change helped.

1. Principles: measure first

Django's own performance guide is blunt: "It's no good just guessing or assuming where the inefficiencies lie in your code" [1]. Its database guide gives the same order of operations: profile first, apply a change, then profile again to confirm that it helped [2]. The reason is arithmetic. Amdahl's argument about parallel speed-up applies to any optimization: the total gain is bounded by the fraction of time spent in the part you improved [3]. If template rendering takes 5% of a request, making it infinitely fast saves 5%. If one query takes 70%, a better index may save most of the request.

A useful mental model is the request's latency budget. A typical dynamic page spends time in roughly these places, and every section of this article targets one of them:

2. The Django cache framework

Django ships a cache framework with a common API in front of several storage backends. Caches are configured in the CACHES setting, a dictionary of named aliases; django.core.cache.cache is a shortcut for caches["default"] [4]. If you configure nothing, Django uses the local-memory backend [4].

2.1 Configuration

# settings.py
CACHES = {
    "default": {
        "BACKEND": "django.core.cache.backends.redis.RedisCache",
        "LOCATION": "redis://127.0.0.1:6379/1",
        "TIMEOUT": 300,            # seconds; the default is 300
        "KEY_PREFIX": "catalog",   # keeps keys from different apps/deployments apart
        "VERSION": 1,
    },
    "local": {
        "BACKEND": "django.core.cache.backends.locmem.LocMemCache",
        "LOCATION": "per-process-hot-keys",
    },
}

The arguments that matter most are these [4]:

  • TIMEOUT defaults to 300 seconds. None means keys never expire, and 0 means they expire immediately (effectively "do not cache").
  • KEY_PREFIX is prepended to every key, and VERSION is the default key version. The final key is built by KEY_FUNCTION, which by default joins prefix, version and key as "prefix:version:key".
  • OPTIONS passes backend-specific settings, such as MAX_ENTRIES and CULL_FREQUENCY for the local-memory, filesystem and database backends.

2.2 The low-level API

The low-level API is the most flexible way to cache, because you choose exactly what to store. The core methods are get, set, add (stores only if the key is absent and returns True only when it stored), get_or_set (whose default may be a callable), get_many/set_many/delete_many, touch, incr/decr, and clear, which removes everything in the cache, not just your application's keys [4]. Each method also has an a-prefixed async variant such as aget and aset [4].

# catalog/services.py
from django.core.cache import cache

from .models import Book


def top_rated_books(limit=10):
    """Return the top-rated books as plain dicts, cached for ten minutes."""
    key = f"top-rated:{limit}"
    return cache.get_or_set(
        key,
        # A callable is only evaluated on a cache miss.
        lambda: list(
            Book.objects.order_by("-rating", "pk")
            .values("pk", "title", "rating")[:limit]
        ),
        timeout=600,
    )

Three habits make cached values safer:

  1. Cache plain data, not lazy objects. A QuerySet is lazy and does no database work until it is evaluated [2]; wrapping it in list(...) or using values() forces the query before the result is stored.
  2. Distinguish "missing" from "cached None". cache.get(key) returns None (or the default you pass) on a miss [4], so if None is a legitimate value, pass a unique sentinel as the default.
  3. Keep keys short and clean. Memcached rejects keys longer than 250 characters or containing whitespace or control characters, and the other built-in backends emit CacheKeyWarning for such keys so that code stays portable [4]. Hash long or user-supplied inputs.

2.3 Invalidation strategies

There are three common ways to keep cached data correct. Which one fits depends on how stale a value is allowed to be.

StrategyHowGood for
Time-based expirySet a timeout and accept staleness up to that ageAggregates, listings, data where a few minutes of staleness is fine
Explicit deletionDelete keys when the source data changes (for example from a signal)Detail pages that must update promptly
Key-based (generational) expiryPut a version or timestamp in the key, so a change produces a new key and old entries simply age outFragments of objects with an updated_at; whole namespaces
 
# catalog/signals.py  (import this module from AppConfig.ready())
from django.core.cache import cache
from django.db.models.signals import post_delete, post_save
from django.dispatch import receiver

from .models import Book

NAMESPACE_KEY = "books:generation"


def books_generation():
    # add() only writes if the key is absent, so this initialises the counter once.
    cache.add(NAMESPACE_KEY, 1, timeout=None)
    return cache.get(NAMESPACE_KEY, 1)


def book_list_key(page):
    return f"books:list:g{books_generation()}:p{page}"


@receiver([post_save, post_delete], sender=Book)
def invalidate_book_caches(sender, instance, **kwargs):
    cache.delete(f"book:{instance.pk}")
    try:
        cache.incr(NAMESPACE_KEY)          # every list key changes at once
    except ValueError:                     # incr() raises if the key is missing
        cache.set(NAMESPACE_KEY, 1, timeout=None)

Atomicity. Django documents that incr() and decr() are atomic on Memcached, while other backends implement them as a two-step read and update [4]. For counters that must be exact under concurrency, use the backend's native operations or the database.

2.4 Preventing a cache stampede

When a popular key expires, every concurrent request misses at the same moment and recomputes the value. This is called a stampede (or dog-piling). A common mitigation is to let one request recompute while the others wait briefly for the new value. Because add() only stores a key that does not already exist [4], it can act as a lightweight lock on a shared backend.

import time

from django.core.cache import cache

_MISSING = object()


def get_or_compute_locked(key, compute, timeout=300, lock_ttl=30, wait=0.05, attempts=40):
    value = cache.get(key, _MISSING)
    if value is not _MISSING:
        return value

    lock_key = f"lock:{key}"
    if cache.add(lock_key, "1", lock_ttl):          # we won the race
        try:
            value = compute()
            cache.set(key, value, timeout)
            return value
        finally:
            cache.delete(lock_key)

    for _ in range(attempts):                       # someone else is computing
        time.sleep(wait)
        value = cache.get(key, _MISSING)
        if value is not _MISSING:
            return value
    return compute()                                # degrade gracefully, never fail

The lock has a TTL so that a crashed worker cannot hold it forever. The pattern only coordinates processes that share the backend: with the per-process local-memory cache, each worker has its own lock (see section 3).

from django.core.cache import cache
from django.db.models import Avg, Count
from django.db.models.signals import post_save
from django.dispatch import receiver

from .models import Book

_MISSING = object()


def _stats_key(publisher_id):
    return f"publisher-stats:{publisher_id}"


def publisher_stats(publisher_id):
    key = _stats_key(publisher_id)
    stats = cache.get(key, _MISSING)
    if stats is _MISSING:
        stats = Book.objects.filter(publisher_id=publisher_id).aggregate(
            books=Count("pk"), avg_rating=Avg("rating")
        )
        # The dict itself is never None, so even {"books": 0, "avg_rating": None}
        # is a real cached value and will not be recomputed on every request.
        cache.set(key, stats, timeout=15 * 60)
    return stats


@receiver(post_save, sender=Book)
def _invalidate_publisher_stats(sender, instance, **kwargs):
    cache.delete(_stats_key(instance.publisher_id))

Note the use of instance.publisher_id rather than instance.publisher.id: the former reads the foreign-key value already on the instance, while the latter may trigger a query [2]. The aggregation runs in the database rather than in Python, which the database guide also recommends [2].

3. Local-memory, filesystem and Redis caching

Django's built-in backends are Memcached (via pymemcache or pylibmc), Redis, database, filesystem, local-memory and a dummy backend for development [4]. The built-in Redis backend arrived in Django 4.0 [5]. This section compares the three most commonly chosen ones.

3.1 Local-memory cache

CACHES = {
    "default": {
        "BACKEND": "django.core.cache.backends.locmem.LocMemCache",
        "LOCATION": "unique-snowflake",
        "OPTIONS": {"MAX_ENTRIES": 1000, "CULL_FREQUENCY": 3},
    }
}

The local-memory cache is per-process and thread-safe. It uses an LRU culling strategy, with MAX_ENTRIES defaulting to 300 and CULL_FREQUENCY defaulting to 3 (one third of entries are culled when the limit is reached). Django notes it is not particularly memory-efficient and is a reasonable choice for development rather than production [4].

The per-process property has an important consequence. A production server running several worker processes (for example Gunicorn's recommended starting point of (2 × cores) + 1 workers [6]) has several independent caches. Deleting a key in one worker does not remove it from the others, so explicit invalidation silently fails. Use local memory only for data that is safe to be stale per process, such as rarely changing configuration, or as a tiny "L1" in front of a shared cache.

3.2 Filesystem cache

CACHES = {
    "default": {
        "BACKEND": "django.core.cache.backends.filebased.FileBasedCache",
        "LOCATION": "/var/tmp/django_cache",   # absolute path, writable by the server user
        "TIMEOUT": 3600,
        "OPTIONS": {"MAX_ENTRIES": 10_000},
    }
}

The filesystem backend stores each value as a separate file. LOCATION must be an absolute path that the web server's user can read and write, and performance can degrade when the cache holds a large number of files [4]. It is shared between processes on one machine but not across machines.

Security. Values are serialized with pickle. Django warns that if LOCATION sits inside MEDIA_ROOT, STATIC_ROOT or a static-files finder directory, sensitive data may be exposed, and an attacker who can write cache files could falsify content or execute arbitrary code [4]. Keep the directory private.

3.3 Redis

import os

CACHES = {
    "default": {
        "BACKEND": "django.core.cache.backends.redis.RedisCache",
        # One URL, or a list: the first server is used for writes,
        # the others serve reads.
        "LOCATION": os.environ.get("REDIS_URL", "redis://127.0.0.1:6379/1"),
        "KEY_PREFIX": "catalog",
        "TIMEOUT": 300,
    }
}

Redis is a shared, networked, in-memory store, so every worker on every machine sees the same keys and invalidation works. Configure Redis itself as a cache too: set a maxmemory limit and an eviction policy. The Redis documentation recommends allkeys-lru as a good starting point, suggests allkeys-lfu when a small hot set should stay resident, and warns that noeviction makes writes fail with an error once memory is full [7].

# redis.conf (cache-only instance)
maxmemory 512mb
maxmemory-policy allkeys-lru

Redis reports keyspace_hits, keyspace_misses and evicted_keys in INFO stats, from which you can compute the hit ratio hits / (hits + misses); a low hit ratio with high evictions suggests the cache is too small or the policy is evicting the wrong keys [7].

The local-memory cache is per-process [4]. The editor's save request ran in one worker, whose signal handler deleted the key from that worker's memory. The other three workers still hold the old value until the default 300-second timeout expires [4]. Subsequent requests are distributed across workers, so users see old and new versions at random.

Fixes: (1) switch the default cache to a shared backend such as Redis, so one delete() is visible to all workers; or (2) if a shared cache is not available, use key-based expiry, for example including book.updated_at in the key, so a changed book naturally maps to a new key in every process. Option 2 still needs the database read of updated_at, which is cheap if it is the only column read.

4. Per-site, per-view and fragment caching

On top of the low-level API, Django provides three ready-made caching granularities [4]. From coarsest to finest:

4.1 Per-site cache

MIDDLEWARE = [
    "django.middleware.cache.UpdateCacheMiddleware",     # must be FIRST
    "django.middleware.security.SecurityMiddleware",
    "django.contrib.sessions.middleware.SessionMiddleware",
    "django.middleware.common.CommonMiddleware",
    # ...
    "django.middleware.cache.FetchFromCacheMiddleware",  # must be LAST
]

CACHE_MIDDLEWARE_ALIAS = "default"
CACHE_MIDDLEWARE_SECONDS = 600
CACHE_MIDDLEWARE_KEY_PREFIX = "site"

The ordering is not arbitrary. Response middleware runs in reverse order, so UpdateCacheMiddleware must run after anything that adds to the Vary header on the way out (for example SessionMiddleware adds Cookie, GZipMiddleware adds Accept-Encoding and LocaleMiddleware adds Accept-Language), while FetchFromCacheMiddleware must come after middleware that updates Vary on the way in [4,8]. The middleware also sets Expires and Cache-Control: max-age from CACHE_MIDDLEWARE_SECONDS [4].

The per-site cache is the easiest to turn on and the hardest to keep correct. Any page that differs per user must either vary on Cookie (which, with sessions, means effectively per-user entries) or be excluded. It suits mostly anonymous, content-heavy sites.

4.2 Per-view cache

# catalog/views.py
from django.shortcuts import render
from django.views.decorators.cache import cache_page
from django.views.decorators.vary import vary_on_headers

from .services import top_rated_books


@cache_page(60 * 15, key_prefix="top")
@vary_on_headers("Accept-Language")
def top_books(request):
    return render(request, "catalog/top.html", {"books": top_rated_books()})


# Or in the URLconf, leaving the view undecorated:
# path("top/", cache_page(60 * 15)(top_books))

cache_page(timeout, *, cache=None, key_prefix=None) caches the whole response of one view. The key includes the full URL, so /books/?page=2 and /books/?page=3 are cached separately. Its timeout takes precedence over any max-age in Cache-Control. Importantly, cache_page does not automatically vary by authentication, session or cookies; use vary_on_cookie or vary_on_headers if the output depends on them [4].

Personalised and CSRF-protected pages. Never cache a page that contains user-specific data or a CSRF token without varying appropriately; otherwise one user's page is served to another. The cache documentation calls out CSRF-protected forms specifically [4].

4.3 Template fragment caching

{% load cache %}
<h1>{{ book.title }}</h1>

{# Cache the expensive sidebar for 10 minutes, one entry per book version. #}
{% cache 600 book_sidebar book.pk book.updated_at.isoformat %}
  <aside>
    <h2>Readers also liked</h2>
    <ul>
      {% for other in book.similar_books %}
        <li>{{ other.title }}</li>
      {% endfor %}
    </ul>
  </aside>

The syntax is {% cache timeout fragment_name [vary_on ...] [using="alias"] %}. The fragment name is taken literally, and the extra arguments are converted to strings and included in the key, so do not pass model instances (use their primary key) and beware that None and the string "None" collide [4]. Including updated_at as shown gives key-based invalidation for free. To delete a fragment explicitly, rebuild its key [4]:

from django.core.cache import cache
from django.core.cache.utils import make_template_fragment_key

key = make_template_fragment_key("book_sidebar", [book.pk, book.updated_at.isoformat()])
cache.delete(key)

Fragment caching is often the best trade-off for logged-in pages: the personalised header stays dynamic while the expensive shared parts are cached. Django also recommends the cached template loader, which avoids recompiling templates on every render [1].

5. HTTP caching and ETags

The cheapest request is the one that never reaches your server. HTTP caching is defined by RFC 9111 [9], with the validators (ETag, Last-Modified) and conditional requests defined in RFC 9110 [10].

The difference between no-cache and no-store is a frequent source of confusion: no-cache means "check with me first", not "do not cache". MDN's guidance is to send no-cache for HTML documents, whose URLs cannot change, and long-lived max-age plus immutable for versioned assets whose URLs change when their content changes [12]. For personalised HTML, add private [12].

Django sets these headers with decorators [4]:

from django.views.decorators.cache import cache_control, never_cache


@cache_control(public=True, max_age=60, s_maxage=600)   # CDN keeps it longer than browsers
def catalogue_home(request): ...


@cache_control(private=True, no_cache=True)              # personalised, always revalidate
def my_reading_list(request): ...


@never_cache                                             # e.g. checkout pages
def checkout(request): ...

5.2 Validators and conditional requests

An ETag is an opaque identifier for a particular representation of a resource [10]. A client that has a cached copy sends it back in If-None-Match; if it still matches, the server replies 304 Not Modified with no body [10]. A strong ETag changes whenever the bytes change; a weak ETag (prefixed W/) promises only semantic equivalence (RFC 9110 section 8.8.1) [10]. If-None-Match uses the weak comparison function, while If-Match uses strong comparison (RFC 9110 sections 13.1.1 and 13.1.2) [10].

5.3 ETags in Django

Django offers two approaches. ConditionalGetMiddleware adds an ETag to responses that lack one and turns matching conditional GETs into 304 responses [8]. It is global and easy, but the view still runs and builds the full response, so it saves bandwidth, not server time [13]. The condition, etag and last_modified decorators are better when the validator is cheap to compute, because Django can return 304 before the view runs [13].

# catalog/views.py
import hashlib

from django.shortcuts import get_object_or_404, render
from django.views.decorators.cache import cache_control
from django.views.decorators.http import condition

from .models import Book


def _book_updated_at(request, pk):
    # One indexed primary-key lookup reading a single column.
    return Book.objects.filter(pk=pk).values_list("updated_at", flat=True).first()


def book_etag(request, pk):
    updated = _book_updated_at(request, pk)
    if updated is None:
        return None
    return hashlib.sha256(f"book:{pk}:{updated.isoformat()}".encode()).hexdigest()[:32]


def book_last_modified(request, pk):
    return _book_updated_at(request, pk)


# cache_control (and vary_on_*) must be ABOVE condition(): RFC 9110 requires
# those headers on 304 responses too.
@cache_control(private=True, no_cache=True)
@condition(etag_func=book_etag, last_modified_func=book_last_modified)
def book_detail(request, pk):
    book = get_object_or_404(Book.objects.select_related("author", "publisher"), pk=pk)
    return render(request, "catalog/book_detail.html", {"book": book})

Two details come straight from Django's documentation. First, use condition() when you have both validators; chaining @etag and @last_modified is incorrect, because the outer decorator cannot see the inner one's result [13]. Second, place cache_control and vary_on_* above condition() so their headers also appear on 304 responses [13]. In production you would usually cache the updated_at lookup itself, so that a validation request touches only the cache.

5.4 Optimistic concurrency with If-Match

The same decorator protects writes. For methods such as PUT or DELETE, if the client's If-Match no longer matches the current ETag, Django returns 412 Precondition Failed, signalling that the resource changed since the client read it [13]. This prevents the "lost update" problem in APIs without database locks.

5.5 Vary and compression

The Vary header lists request headers that select between stored responses (RFC 9110 section 12.5.5) [10]. A response compressed for one client must not be served to a client that cannot decompress it, which is why GZipMiddleware adds Accept-Encoding to Vary [4]. GZipMiddleware also converts an existing strong ETag to a weak one, because the compressed bytes differ from the uncompressed ones (RFC 9110 section 8.8.1) [8]. Every header you vary on multiplies the number of cache entries, so vary on as little as possible.

6. Query optimization and N+1 problems

The single most common Django performance bug is the N+1 query: one query fetches a list, then one more query runs for each item to fetch something related. It happens because related objects are loaded lazily on attribute access. Django caches a non-callable relation such as book.author after the first access, but a callable such as book.tags.all() queries again each time [2].

6.1 Seeing the queries

6.3 The fixes

select_related() follows foreign-key and one-to-one relations with a SQL join, in the same query. prefetch_related() runs one extra query per relation and joins the results in Python, which is what many-to-many and reverse foreign-key relations need [2,17].

from django.db.models import Avg, Count, Prefetch

from .models import Book, Review


def book_list(request):
    books = (
        Book.objects
        .select_related("author", "publisher")            # JOIN: 0 extra queries
        .prefetch_related(
            "tags",                                        # +1 query for all tags
            Prefetch(                                      # +1 query, filtered
                "reviews",
                queryset=Review.objects.filter(stars__gte=4).order_by("-created_at"),
                to_attr="good_reviews",
            ),
        )
        .annotate(                                         # aggregated in SQL
            review_count=Count("reviews", distinct=True),
            avg_stars=Avg("reviews__stars"),
        )
        .order_by("-published")[:50]
    )
    return render(request, "catalog/book_list.html", {"books": books})

The result is three queries regardless of how many books are listed. Prefetch(..., to_attr=...) stores the filtered list on a new attribute; the QuerySet reference recommends to_attr over filtering the related manager's cache [17]. annotate() performs the aggregation in the database rather than in Python [2]. In the template, use book.good_reviews and book.review_count instead of calling .all or |length on a related manager.

New in Django 6.1: fetch modes. QuerySet.fetch_mode(models.FETCH_PEERS) makes the first lazy access to a foreign key or deferred field on one instance load it for all instances from the same queryset in a batch [17]. The database guide describes it as an easier option when access patterns are hard to predict [2]. Explicit select_related/prefetch_related remains the more predictable choice for hot paths. Also note that calling select_related() with no arguments is deprecated in 6.1 [17].

6.5 Other ways to fetch less

The database optimization guide lists several more techniques [2]:

  • values() / values_list() return dicts or tuples instead of model instances when you only need data.
  • defer() / only() skip loading large columns, but accessing a deferred field later costs another query, so use them carefully.
  • count() instead of len(qs), exists() instead of if qs, and contains(obj) instead of obj in qs, but only when you do not need the rows anyway; if you will iterate the queryset, evaluate it once and reuse its result cache.
  • entry.blog_id instead of entry.blog.id.
  • update(), delete(), bulk_create() and bulk_update() act on many rows in one statement. update() and delete() skip each instance's save()/delete() methods and per-object signals.
  • F() expressions perform comparisons and updates in SQL, for example Book.objects.filter(pk=pk).update(rating=F("rating") + 1).
  • iterator() streams large result sets to save memory.

7. Database indexes and query plans

After the number of queries, the cost of each query matters. Django's guide recommends adding indexes to fields you frequently filter, exclude or order by, once profiling shows the need, and reminds you that indexes have a maintenance cost on writes [2].

7.1 Declaring indexes

from django.db import models
from django.db.models import Q
from django.db.models.functions import Lower


class Book(models.Model):
    # ... fields as before ...

    class Meta:
        indexes = [
            # Composite: "this author's books, newest first".
            models.Index(fields=["author", "-published"], name="book_author_pub_idx"),
            # Supports keyset pagination over the whole catalogue (section 8).
            models.Index(fields=["-published", "-id"], name="book_pub_id_idx"),
            # Partial: only the small set of featured rows is indexed.
            models.Index(fields=["published"], condition=Q(is_featured=True),
                         name="book_featured_pub_idx"),
            # Covering: filter on title, read rating from the index alone (PostgreSQL).
            models.Index(fields=["title"], include=["rating"], name="book_title_cov_idx"),
            # Functional: case-insensitive lookups.
            models.Index(Lower("title"), name="book_lower_title_idx"),
        ]

The model index reference documents each option: a leading hyphen for descending order; condition for partial indexes (supported on PostgreSQL and SQLite, ignored on MySQL and MariaDB); include for covering indexes (PostgreSQL only); and positional expressions for functional indexes. A name is required for the latter three [18]. Foreign keys already get an index by default, so the composite index above is about the combination with ordering.

Column order in a composite B-tree index matters. PostgreSQL's documentation explains that a multicolumn B-tree index is most efficient when there are constraints on the leading (leftmost) columns: equality on leading columns plus an inequality on the first column without an equality constraint limit the portion of the index scanned [19]. It also advises using multicolumn indexes sparingly, noting that indexes with more than three columns are unlikely to help except in very stylized usage [19].

7.2 Building indexes without blocking writes

7.3 Reading query plans

QuerySet.explain() shows how the database will execute a query, including which indexes and joins it uses [2]. On PostgreSQL, keyword options are passed through to EXPLAIN [17]:

qs = Book.objects.filter(author_id=7).order_by("-published")[:20]
print(qs.explain(analyze=True, buffers=True))

Illustrative output before and after adding book_author_pub_idx (numbers will differ on your data):

-- Before
Limit  (cost=2113.40..2113.45 rows=20 width=96) (actual time=18.9..18.9 rows=20 loops=1)
  ->  Sort  (cost=2113.40..2115.90 rows=1000 width=96) (actual time=18.9..18.9 rows=20 loops=1)
        Sort Key: published DESC
        ->  Bitmap Heap Scan on catalog_book  (... rows=1000 ...)
              Recheck Cond: (author_id = 7)
              ->  Bitmap Index Scan on catalog_book_author_id_...  (... rows=1000 ...)

-- After
Limit  (cost=0.43..18.20 rows=20 width=96) (actual time=0.04..0.09 rows=20 loops=1)
  ->  Index Scan using book_author_pub_idx on catalog_book  (... rows=20 loops=1)
        Index Cond: (author_id = 7)

How to read it, following PostgreSQL's Using EXPLAIN chapter [21]:

  • Cost is in arbitrary planner units (by convention a sequential page fetch costs 1.0); the first number is the start-up cost and the second is the total.
  • rows is the planner's estimate of rows the node emits. With ANALYZE, compare it with the actual count: large gaps usually mean stale or insufficient statistics.
  • Scan types: a Seq Scan reads the whole table; a Bitmap Heap Scan suits moderately selective conditions; an Index Scan suits few rows or an ORDER BY that matches the index; an Index Only Scan answers from the index without visiting the table.
  • actual time is in milliseconds per loop; multiply by loops for the total. BUFFERS shows pages hit in cache versus read from disk.

In the "before" plan the database finds all 1,000 of the author's books, sorts them, then keeps 20. In the "after" plan the index already stores them in the right order, so the scan stops after 20 rows. A sort that disappears under a LIMIT is one of the most valuable things an index can do.

EXPLAIN ANALYZE executes the statement. For INSERT, UPDATE, DELETE or MERGE, wrap it in BEGIN; ... ROLLBACK; to avoid keeping the changes [21].

8. Pagination for large datasets

8.1 Django's Paginator

from django.core.paginator import Paginator
from django.shortcuts import render


def book_index(request):
    qs = Book.objects.select_related("author").order_by("-published", "-id")
    paginator = Paginator(qs, per_page=25)
    page_obj = paginator.get_page(request.GET.get("page"))
    return render(request, "catalog/index.html", {"page_obj": page_obj})

Paginator(object_list, per_page, orphans=0, allow_empty_first_page=True, error_messages=None) accepts a list or queryset, and the queryset should be ordered for consistent results [22]. To find the total, it calls count() when available and falls back to len() [23]. get_page() is lenient: a non-integer returns the first page and an out-of-range number returns the last [22]. Django 6.0 added AsyncPaginator with aget_page() and related coroutine methods for async views [22]. Class-based ListView does the same through paginate_by [23].

8.2 Why OFFSET gets slow

Page-number pagination becomes LIMIT 25 OFFSET 250000 in SQL. As Markus Winand explains, OFFSET gives the database only a count of rows to skip, so it must still produce and discard all of them; large offsets are therefore expensive, and results drift (duplicates or gaps) when rows are inserted between page requests [24]. On top of that, the page links usually need COUNT(*) over the whole filtered set, which is itself a full scan on large tables.

8.3 Keyset (cursor) pagination

Keyset pagination, also called the seek method, filters for rows that come after the last row seen in a fixed sort order, instead of skipping a count [24]. With a matching index (here book_pub_id_idx on (-published, -id) from section 7) each page costs about the same no matter how deep you go. The trade-off is that users cannot jump to an arbitrary page number [24].

# catalog/pagination.py
import base64
import datetime as dt
import json

from django.db.models import Q


def encode_cursor(book):
    raw = json.dumps([book.published.isoformat(), book.pk]).encode()
    return base64.urlsafe_b64encode(raw).decode()


def decode_cursor(cursor):
    published, pk = json.loads(base64.urlsafe_b64decode(cursor.encode()))
    return dt.date.fromisoformat(published), int(pk)


def keyset_page(queryset, cursor=None, size=25):
    """Return (rows, next_cursor). Order is newest first, ties broken by pk."""
    qs = queryset.order_by("-published", "-pk")
    if cursor:
        published, pk = decode_cursor(cursor)
        # "Strictly after (published, pk)" in descending order:
        qs = qs.filter(Q(published__lt=published) | Q(published=published, pk__lt=pk))
    rows = list(qs[: size + 1])          # fetch one extra row to learn if there is a next page
    has_next = len(rows) > size
    rows = rows[:size]
    return rows, (encode_cursor(rows[-1]) if has_next and rows else None)
# catalog/views.py
from django.core.exceptions import BadRequest
from django.http import JsonResponse

from .pagination import keyset_page


def book_feed(request):
    try:
        rows, next_cursor = keyset_page(Book.objects.all(), request.GET.get("cursor"))
    except (ValueError, TypeError):
        raise BadRequest("invalid cursor")
    return JsonResponse({
        "results": [{"id": b.pk, "title": b.title, "published": b.published.isoformat()} for b in rows],
        "next": next_cursor,
    })

The tie-breaker (pk) is essential: without a unique final sort column, rows that share a published date could be skipped or repeated across pages.

For management commands and exports, do not load the whole table into memory. QuerySet.iterator() streams rows instead of caching them, and when it is combined with prefetch_related(), the prefetch is only honoured if you pass a chunk_size [2,17]. On PostgreSQL, iterator() uses a server-side cursor, which has implications for connection poolers (section 9) [25].

9. Connection pooling

Opening a PostgreSQL connection involves a network handshake, authentication and a new backend process, and Django's performance guide notes that connecting can account for a significant part of request processing time [1]. By default Django closes the connection at the end of each request (CONN_MAX_AGE = 0) [25]. There are three ways to avoid reconnecting.

9.1 Persistent connections

DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": "catalog",
        # ...
        "CONN_MAX_AGE": 60,          # reuse a connection for up to 60 s
        "CONN_HEALTH_CHECKS": True,  # check a reused connection once per request
    }
}

With a positive CONN_MAX_AGE, each thread keeps its connection between requests. CONN_HEALTH_CHECKS verifies a reused connection once per request before use, which avoids errors when the server has closed it [25]. Django advises disabling persistent connections under ASGI and using the backend's pooling instead [25,26].

9.2 Django's built-in PostgreSQL pool

Django 5.1 added connection pool support for PostgreSQL, "as the time to establish a new connection can be relatively long" [27]. It requires psycopg 3 with the pool extra (pip install "psycopg[pool]"), keeps a separate pool per database alias per process, and accepts either True or a dict of ConnectionPool options. CONN_MAX_AGE must be 0 when pooling is on; connection lifetime is set with the pool's max_lifetime instead [25].

DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": "catalog",
        # ...
        "CONN_MAX_AGE": 0,
        "OPTIONS": {
            "pool": {
                "min_size": 2,
                "max_size": 8,
                "timeout": 10,        # seconds to wait for a free connection
                "max_lifetime": 1800, # recycle connections every 30 minutes
            },
        },
    }
}

psycopg's own documentation says the right pool size is "probably not as large as you imagine": start small, watch get_stats(), and tune min_size and max_size from what you see [28].

9.3 Sizing: do the multiplication

Because each process has its own pool [25], the worst case number of server connections is:

hosts × processes per host × max_size ≤ PostgreSQL max_connections − reserved

Four hosts running nine Gunicorn workers each with max_size = 8 could open 288 connections. A sync worker serves one request at a time [6], so it rarely needs more than one or two connections; a threaded or ASGI worker needs roughly as many as its concurrent requests that touch the database. Django's async guide adds that, because thread-sensitive sync calls serialize on a request's worker thread, you should increase the pool size to support more concurrent requests rather than disable thread_sensitive [26].

9.4 External poolers: PgBouncer

When many processes or services share one database, an external pooler multiplexes them onto fewer server connections. PgBouncer offers three modes: session pooling (a server connection per client connection, all features work), transaction pooling (a server connection only for the duration of a transaction) and statement pooling (which disallows multi-statement transactions). Transaction pooling breaks session-level features such as SET, LISTEN, WITH HOLD cursors, SQL-level PREPARE and session advisory locks [29].

For Django, the important consequence is server-side cursors. QuerySet.iterator() opens one on PostgreSQL, and such a cursor only exists on the connection that created it; under transaction pooling, the next statement may run on another connection and fail. Django's documented fix is "DISABLE_SERVER_SIDE_CURSORS": True for that database, or wrapping each streaming queryset in atomic() [25].

10. Compression and static asset optimization

10.1 Response compression

GZipMiddleware compresses responses for clients that send Accept-Encoding: gzip. It skips bodies under 200 bytes and responses that already have a Content-Encoding [8]. It should sit after UpdateCacheMiddleware and before any middleware that reads or changes the response body, and ConditionalGetMiddleware should come after it so that ETags are not computed on compressed bytes [8].

MIDDLEWARE = [

    "whitenoise.middleware.WhiteNoiseMiddleware",       # see 10.3
    "django.middleware.gzip.GZipMiddleware",

    "django.middleware.http.ConditionalGetMiddleware",
    "django.middleware.common.CommonMiddleware",
    # ...
]

Compression and secrets (BREACH). Django's performance guide warns that GZip compression of responses is considered a security risk because it is vulnerable to attacks that can nullify the protection of TLS [1]. To mitigate this, GZipMiddleware implements "Heal The Breach", adding up to 100 random bytes (max_random_bytes) to each response [8]. A common recommendation is to let the reverse proxy or CDN compress, and to avoid compressing responses that reflect attacker-controlled input next to secrets such as CSRF tokens.

Brotli (Content-Encoding: br) is a newer format specified in RFC 7932 [30]; it is usually applied to static files ahead of time (10.3) or by the proxy. Measure on your own payloads, as in Exercise 10.1.

10.2 Hashed filenames for long-lived caching

The best static file request is the one the browser never makes. ManifestStaticFilesStorage appends an MD5 hash of each file's content to its name (css/styles.css becomes css/styles.55e7cbb9ba48.css), rewrites references inside CSS and JavaScript, and records the mapping in staticfiles.json when you run collectstatic, so no hashing happens at request time [31]. It is active when DEBUG = False [31]. Because a changed file gets a new URL, the old one can be cached "forever", the pattern MDN recommends with max-age=31536000, immutable [11,12].

STATIC_URL = "/static/"
STATIC_ROOT = BASE_DIR / "staticfiles"

11. Profiling and benchmarking

Profiling answers "where does the time go?"; benchmarking answers "is version B faster than version A?". Both need care to produce numbers you can trust.

11.1 Two kinds of profiler

A deterministic (tracing) profiler records every function call, return and exception, which gives exact call counts but adds overhead. A statistical (sampling) profiler periodically samples the call stack; it usually has less overhead but gives relative indications of where time goes [33]. In Python 3.15 the standard library organizes these as profiling.tracing and profiling.sampling; cProfile remains available as an alias of profiling.tracing, and the old pure-Python profile module is deprecated [33]. The examples below use cProfile, which works on every supported version.

11.2 Profiling a single request

# catalog/middleware.py: development only
import cProfile
import io
import pstats

from django.conf import settings
from django.http import HttpResponse


class ProfileMiddleware:
    """Append ?prof to any URL (with DEBUG=True) to get a cProfile report instead of the page."""

    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        if not (settings.DEBUG and "prof" in request.GET):
            return self.get_response(request)
        profiler = cProfile.Profile()
        profiler.runcall(self.get_response, request)
        out = io.StringIO()
        stats = pstats.Stats(profiler, stream=out)
        stats.sort_stats(pstats.SortKey.CUMULATIVE).print_stats(30)
        return HttpResponse(out.getvalue(), content_type="text/plain")

Sort by cumulative time to find the expensive call trees, then by tottime to find the functions that are expensive themselves. Pair this with Django Debug Toolbar, which shows SQL queries with their timings for the same page [1,15].

py-spy is a sampling profiler that runs outside the target process and attaches to it by PID, so it needs no code changes or restart, and its authors describe its overhead as low enough for production use. 11.4 Micro-benchmarks with timeit

timeit runs a snippet many times, disables garbage collection during timing by default, and with repeat() returns several measurements [35]. Its documentation advises against reporting the mean and standard deviation of those measurements: the lowest value gives a lower bound for how fast the machine can run the snippet, and higher values are usually caused by other processes interfering [35].

$ python -m timeit -s "ids = list(range(10_000)); wanted = list(range(0, 10_000, 7))" \
    "[i for i in ids if i in wanted]"
$ python -m timeit -s "ids = list(range(10_000)); wanted = set(range(0, 10_000, 7))" \
    "[i for i in ids if i in wanted]"

11.5 Benchmarking discipline

  1. Benchmark with production-like data volumes. A query that is instant on 100 rows can be a sequential scan on 10 million, and query plans change with table statistics [21].
  2. Change one thing at a time, and re-measure after each change, as Django's guide recommends [2].
  3. Separate cold-cache and warm-cache runs; report both.
  4. Keep the load generator off the machine under test.
  5. Check that a change helps in the real application: Django notes that changes can make real-world performance worse rather than better [1].

This helper is called from a template tag on every book page and is slow for authors with many books. Profile it, explain the cost, and fix it.

def similar_titles(book, all_books):
    words = book.title.lower().split()
    result = []
    for other in all_books:
        if other.pk != book.pk and other not in result:

Show solution

Run it under cProfile (or the middleware above) and sort by tottime. Three costs appear: other not in result is a linear scan of a list, so the loop is quadratic; other.title.lower().split() is recomputed for every word; and the loop never stops early even though only five results are needed. A rewrite:

def similar_titles(book, all_books, limit=5):
    words = set(book.title.lower().split())
    result, seen = [], {book.pk}
    for other in all_books:
        if other.pk in seen:
            continue
        if words.intersection(other.title.lower().split()):   # set lookup, split once
            result.append(other)
            seen.add(other.pk)
            if len(result) == limit:                          # stop early
                break
    return result

Confirm with timeit.repeat on a realistic list (say 5,000 books) and compare the minimum times [35]. Then ask whether the result should be computed per request at all: it depends only on the catalogue, so it is a good candidate for the low-level cache or for a fragment cache keyed on book.updated_at (sections 2 and 4).

12. Load testing and latency analysis

12.1 Little's Law

Little's Law states that in a stable system the average number of items in the system equals the arrival rate times the average time each spends there: L = λW [36]. For a web service, concurrency = throughput × latency. At 200 requests per second with a 250 ms average response time, about 50 requests are in flight at any moment. If each sync worker handles one request at a time [6], fewer than 50 workers means requests queue, and queueing inflates latency, which raises concurrency further. This is why latency climbs steeply once a service passes its capacity.

12.2 Percentiles, not averages

Averages hide the slow requests users notice. Report percentiles (p50, p95, p99) and the maximum. Dean and Barroso show why the tail matters more as systems grow: if a request fans out to 100 servers and each is slow 1% of the time, 63% of user requests will see at least one slow response [37]. The same applies inside one Django view that makes many sequential cache, database and API calls.

# analyse.py: summarise latencies (ms), one value per line
import statistics
import sys

samples = [float(line) for line in open(sys.argv[1]) if line.strip()]
q = statistics.quantiles(samples, n=100, method="inclusive")   # 99 cut points
print(f"n={len(samples)}  mean={statistics.fmean(samples):.1f}  "
      f"p50={q[49]:.1f}  p95={q[94]:.1f}  p99={q[98]:.1f}  max={max(samples):.1f}")

Locust describes user behaviour in Python. Each HttpUser has a client, @task methods define actions, wait_time sets think time, and the name argument groups URLs with different IDs under one statistics entry [38].

12.5 Running a useful load test

  1. Define the question. "Can we serve 300 req/s with p95 under 300 ms?" is testable; "is it fast?" is not.
  2. Ramp up in steps and find the knee where latency percentiles start rising faster than throughput.
  3. Watch the server side at the same time: CPU per worker, database connections and slow queries, cache hit ratio [7].
  4. Look for the bottleneck, fix it, and repeat. A load test that does not end with a named bottleneck has not finished.

By Little's Law, in-flight requests ≈ 600 × 0.08 s = 48 on average [36]. 13. CPU-bound versus I/O-bound workloads

The right fix for a slow request depends on what the request is waiting for. A request is I/O-bound when it spends most of its time waiting on the database, cache, disk or another service, and CPU-bound when it spends most of its time executing Python code. A quick test is to compare CPU time with wall-clock time: timeit uses time.perf_counter() (wall clock) by default and time.process_time() (CPU time) with -p [35]. If they are close, the work is CPU-bound; if wall time is much larger, it is waiting.

13.1 The GIL

The Python glossary defines the global interpreter lock as "the mechanism used by the CPython interpreter to assure that only one thread executes Python bytecode at a time". It also notes that some extension modules release the GIL during computationally intensive tasks such as compression or hashing, and that "the GIL is always released when doing I/O" [40]. Since Python 3.13 CPython can be built with the GIL disabled, following PEP 703 [40,41]; whether your dependencies and workload benefit from a free-threaded build is something to measure, not assume.

The practical rule follows directly:

WorkloadThreadsProcessesasyncio
I/O-boundGood: the GIL is released while waiting [40]Works, more memoryBest for very high concurrency
CPU-bound (pure Python)No speed-up on a GIL buildGood: each process has its own interpreter [42]No help; blocks the event loop

concurrent.futures mirrors this: ThreadPoolExecutor is often used to overlap I/O, ProcessPoolExecutor side-steps the GIL using separate processes (arguments and results must be picklable), and Python 3.14 adds InterpreterPoolExecutor, where each worker has its own interpreter and GIL [42].

13.2 I/O-bound: overlap the waiting

A view that calls three external services one after another pays the sum of their latencies; issued concurrently it pays roughly the maximum. Under ASGI, async views let one process serve many such connections without a thread each; under WSGI, an async view runs in its own one-off event loop, so concurrent calls inside the view still work but you lose the benefits of an async stack [26].

# catalog/views.py: async view, served by an ASGI server
import asyncio

import httpx                       # third-party async HTTP client
from django.http import JsonResponse

from .models import Book


async def book_enriched(request, pk):
    book = await Book.objects.select_related("author").aget(pk=pk)
    async with httpx.AsyncClient(timeout=2.0) as client:
        prices, stock, reviews = await asyncio.gather(
            client.get(f"https://prices.internal/books/{pk}"),
            client.get(f"https://stock.internal/books/{pk}"),
            client.get(f"https://reviews.internal/books/{pk}/summary"),
            return_exceptions=True,                       # one slow service must not break the page
        )
    def ok(r):
        return r.json() if isinstance(r, httpx.Response) and r.status_code == 200 else None
    return JsonResponse({
        "title": book.title, "author": book.author.name,
        "price": ok(prices), "stock": ok(stock), "reviews": ok(reviews),
    })

Every QuerySet method that runs SQL has an a-prefixed async variant, but transactions do not yet work in async mode [26]. Crossing between sync and async code with sync_to_async() costs tens of microseconds per call on the in-request ASGI path, so restructure tight loops so that the loop runs inside a single crossing [26]. Under WSGI, Gunicorn's documentation lists long blocking calls to external services as a reason to use async (gevent or eventlet) workers instead of sync ones [6].

13.3 CPU-bound: move it off the request path

No amount of async helps a request that spends 2 seconds rendering a PDF or resizing images in Python. The options, in order of preference:

  1. Do less. Profile (section 11), use a better algorithm, or cache the result (section 2).
  2. Do it later. Django 6.0 added a Tasks framework: decorate a function with @task and call .enqueue(). Django defines and queues tasks, but does not provide a production worker, so you configure a third-party backend; the built-in backends are for development and tests [43].
  3. Do it in parallel with processes, for batch jobs.
# catalog/tasks.py
from django.tasks import task


@task(queue_name="reports")
def build_sales_report(publisher_id, year):
    # Arguments and return value must be JSON-serialisable: pass IDs, not model instances.
    from .reports import render_report_pdf
    return render_report_pdf(publisher_id, year)

# catalog/management/commands/rebuild_thumbnails.py
from concurrent.futures import ProcessPoolExecutor

from django.core.management.base import BaseCommand

from catalog.models import Book
from catalog.images import make_thumbnail   # pure function: path in, path out


class Command(BaseCommand):
    def handle(self, *args, **options):
        paths = list(Book.objects.values_list("cover_path", flat=True))
        with ProcessPoolExecutor() as pool:           # one process per CPU by default
            for done in pool.map(make_thumbnail, paths, chunksize=64):

Amdahl's argument sets the expectation: if 10% of the job is serial (reading the list, writing results), no number of processes can make it more than about ten times faster [3].

Exercise 13.1: threads versus processes

Write a script that runs (a) a CPU-bound function (counting primes below 200,000) and (b) an I/O-bound function (time.sleep(0.2), standing in for a network call) eight times each, using a ThreadPoolExecutor and a ProcessPoolExecutor with four workers. Predict the results first.

import time
from concurrent.futures import ProcessPoolExecutor, ThreadPoolExecutor


def count_primes(limit=200_000):
    count = 0
    for n in range(2, limit):
        if all(n % d for d in range(2, int(n ** 0.5) + 1)):
            count += 1
    return count


def fake_io(_=None):
    time.sleep(0.2)          # sleeping releases the GIL, like real I/O
    return 1


def run(executor_cls, fn, jobs=8, workers=4):
    t0 = time.perf_counter()
    with executor_cls(max_workers=workers) as ex:
        list(ex.map(fn, [200_000] * jobs if fn is count_primes else range(jobs)))
    return time.perf_counter() - t0


if __name__ == "__main__":       # required for ProcessPoolExecutor
    t0 = time.perf_counter(); count_primes(); single = time.perf_counter() - t0
    print(f"one CPU job: {single:.2f}s")
    for name, cls in (("threads", ThreadPoolExecutor), ("processes", ProcessPoolExecutor)):
        print(f"{name:9} CPU x8: {run(cls, count_primes):.2f}s   I/O x8: {run(cls, fake_io):.2f}s")

Expected pattern on a standard (GIL) build with at least four cores:

  • CPU, threads: about 8 × the single-job time. Only one thread runs bytecode at a time [40].
  • CPU, processes: about 2 × the single-job time (8 jobs over 4 processes), plus start-up cost, because each process has its own interpreter [42].
  • I/O, threads: about 0.4 s (two rounds of 0.2 s), because the GIL is released while waiting [40].
  • I/O, processes: also about 0.4 s plus process start-up: correct but heavier than needed.

On a free-threaded build, the CPU-with-threads result may approach the process result; that is exactly the kind of claim to verify with this script on your own hardware [41].
