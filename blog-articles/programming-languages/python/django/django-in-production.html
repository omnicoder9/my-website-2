Introduction and reference architecture

Running Django in production is mostly about the parts around Django. The framework's own deployment checklist is short: turn off debug mode, keep the secret key secret, set allowed hosts, serve over HTTPS, and use a real application server instead of runserver, which "is not designed for a production setting" [1]. Everything else in this article is about the processes, proxies, databases, pipelines and runbooks that keep those settings true under load, during deploys and after failures.

The examples target Django 6.x on Python 3.12 or later. At the time of writing, the latest official Django release is 6.1, and 5.2 is the supported long-term-support (LTS) release, with extended support until April 2028 [2]. Django 6.0 supports Python 3.12, 3.13 and 3.14 [3]. The settings shown here also work on 5.2 unless a note says otherwise. All code is written for an imaginary online shop called acme-shop, with the Django project package named config.

The architecture used throughout looks like this. Each layer gets its own section.

Two ideas from the Twelve-Factor App methodology run through every section: configuration lives in the environment, not in code [4], and application processes are stateless and share nothing, so anything that must persist lives in a backing service such as a database [5]. Those two rules are what make horizontal scaling, rolling deploys and disaster recovery tractable.

1 Production settings and environment variables

Split settings into a shared base module and small environment-specific modules. Keep anything that differs between deploys, or that is secret, out of the repository and read it from the environment at startup [4]. The Django checklist gives the canonical example: SECRET_KEY = os.environ["SECRET_KEY"], and stresses that the key "must be a large random value and it must be kept secret" [1].

A settings layout that fails fast

A missing variable should crash the process at boot with a clear message, not surface as a confusing error on the first request. The helper below also supports the NAME_FILE convention, where a secret is mounted as a file by Docker or Kubernetes instead of placed in the environment (see §11).

Verifying the configuration

Run the deployment checks against the production settings module in CI. check --deploy "activates some additional checks that are only relevant in a deployment setting", and --fail-level WARNING makes warnings fail the build (the default level is ERROR) [10].

Django 6.0 also added built-in Content Security Policy support through ContentSecurityPolicyMiddleware and the SECURE_CSP and SECURE_CSP_REPORT_ONLY settings [3]. Start in report-only mode, read the reports, then enforce.

Exercise 1

A teammate proposes DEBUG = os.environ.get("DEBUG", False) so that staging can turn debugging on. Find the bug, then explain why the article's settings module does not read DEBUG from the environment at all.

Show solution

os.environ.get returns a string when the variable is set, and every non-empty string is truthy. DEBUG=False or DEBUG=0 in the environment therefore turns debug mode on. Even with correct parsing, the setting is a single typo away from leaking source code and settings on every error page [1]. Keeping DEBUG = False hard-coded in production.py and using a separate staging.py module (with its own error tracking) removes the failure mode entirely.

2 WSGI servers: Gunicorn

WSGI, defined in PEP 3333, is the standard interface between Python web servers and synchronous applications [11]. Django's startproject generates wsgi.py exposing an application callable, and Gunicorn is the most common server for it. Gunicorn is "a pure-Python WSGI server for UNIX" with no dependencies; gunicorn myproject.wsgi starts one process with one thread on 127.0.0.1:8000 [12]. That default is for trying it out, not for production.

Process model

Gunicorn uses a pre-fork model: a master (arbiter) process manages a pool of worker processes. The default sync worker handles one request at a time and assumes the application avoids indefinite blocking; async or threaded workers suit long blocking calls, streaming and long polling [13]. The design page suggests starting from (2 × CPU cores) + 1 workers and adjusting under load [13].

Because sync workers handle one request at a time, Gunicorn must sit behind a buffering proxy. Without one, slow clients tie up workers and the server becomes vulnerable to denial-of-service; Gunicorn's deployment guide "strongly recommends" a proxy and prefers Nginx [14].

A production configuration file

Start it with gunicorn config.wsgi:application --config gunicorn.conf.py. Gunicorn reads WEB_CONCURRENCY for workers by default as well [15].

Gunicorn defaults worth knowing [15]

Signals

The master reacts to signals: TERM is a graceful shutdown in which workers finish in-flight requests up to graceful_timeout; INT and QUIT are a quick shutdown; HUP reloads configuration and replaces workers gracefully; TTIN and TTOU add or remove a worker [13,16]. Container platforms send SIGTERM on stop, which is exactly what you want (§13).

Exercise 2

A 4-vCPU VM runs Gunicorn with gthread, 9 workers and 4 threads each, and Django's connection pool has max_size = 4. How many requests can be in progress at once, and what is the maximum number of PostgreSQL connections this VM can open? What happens if you raise threads to 8 without changing the pool?

Show solution

Concurrency is 9 × 4 = 36 requests. The pool is per process, so the VM can open up to 9 × 4 = 36 database connections. With 8 threads, 72 requests can run, but each worker still has only 4 pooled connections; threads beyond that wait up to the pool's timeout and then fail. Size max_size to at least the thread count, then check that replicas × workers × max_size stays under PostgreSQL's max_connections (§5, §16).

3 ASGI servers: Uvicorn or Daphne

ASGI is the asynchronous successor to WSGI. It supports long-lived connections such as WebSockets and an optional lifespan protocol for startup and shutdown events [17,18]. Django ships an asgi.py with an application object, and documents Daphne, Hypercorn and Uvicorn as servers [19].

Use ASGI when you have async views that wait on I/O, streaming responses, or WebSockets through Django Channels. A purely synchronous app gains nothing: Django's ASGI handler runs sync code in a thread, and Django's docs warn against calling blocking synchronous code from async code [19].

Database connections under ASGI

Django's database docs are explicit: "When using ASGI, persistent connections should be disabled. Instead, use your database backend's built-in connection pooling if available" [9]. With PostgreSQL that means CONN_MAX_AGE = 0 plus the "pool" option shown in §1, or an external pooler such as PgBouncer.

Uvicorn

Uvicorn can manage its own worker processes or run under Gunicorn as a process manager. Its docs note that the old uvicorn.workers module is deprecated in favour of the separate uvicorn-worker package, and that --reload and --workers are mutually exclusive [20].

--forwarded-allow-ips accepts addresses and networks; the docs warn "Only trust clients you can actually trust!" and allow * only when every proxy strips incoming forwarded headers first [20,21].

Daphne and Channels

Daphne is the server built for Django Channels. Channels' deployment guide shows daphne -b 0.0.0.0 -p 8001 myproject.asgi:application, describes running Daphne for all traffic or only for WebSockets behind a path-routing proxy, and recommends a supervisor or orchestrator to restart and scale processes [22,23]. Initialise Django's ASGI app before importing consumers so the app registry is populated [22]:

With more than one Daphne process, consumers in different processes can only message each other through a shared channel layer, usually Redis, configured with CHANNEL_LAYERS [22].

Exercise 3

After switching from Gunicorn (WSGI) to Uvicorn, a team keeps CONN_MAX_AGE = 600. Under load PostgreSQL reports "too many connections". Explain why and give the fix.

Show solution

Under ASGI, Django runs sync ORM code in a thread pool, and persistent connections are tied to threads that come and go, so connections accumulate instead of being reused. Django's docs say persistent connections should be disabled under ASGI [9]. Set CONN_MAX_AGE = 0 and enable "pool" in OPTIONS (requires psycopg[pool]), or put PgBouncer in transaction mode in front of the database (§5).

4 Reverse proxies: Nginx

The reverse proxy terminates TLS, buffers slow clients, serves static files, rejects unknown hosts and upgrades WebSocket connections. Uvicorn's docs call a proxy "not necessary" but "recommended for additional resilience" [20], and for Gunicorn's sync workers it is required in practice [14].

Proxy defaults you need to override

By default Nginx rewrites Host to $proxy_host and sends Connection: close upstream [24], so Django would see the upstream name instead of the public hostname. Buffering is on by default, which is what protects sync workers; proxy_read_timeout defaults to 60 s between two reads [24]. Upstream keepalive needs HTTP/1.1 and a cleared Connection header [25]. WebSockets need the Upgrade and Connection headers passed explicitly, because they are hop-by-hop [26].

The catch-all server with return 444 is the pattern from Django's own checklist [1]. HSTS is left to Django's SecurityMiddleware here; set it in one place only, or browsers receive duplicate headers.

Forwarded headers and trust

X-Forwarded-For and X-Forwarded-Proto are de facto headers; RFC 7239 standardises the same information in a single Forwarded header [27]. Whichever you use, the rule is the same: the first proxy must overwrite, not append to, the scheme header it receives, and the application must trust forwarded headers only from known proxy addresses. That is what Django's SECURE_PROXY_SSL_HEADER warning and Gunicorn's forwarded_allow_ips are about [6,15].

Exercise 4

Users report that the order-tracking WebSocket disconnects every minute when nothing happens. The /ws/ location has the Upgrade headers but no other settings. What is the cause, and what are two fixes?

Show solution

proxy_read_timeout defaults to 60 s and applies between two reads from the upstream [24]; an idle WebSocket sends nothing, so Nginx closes it. Nginx's WebSocket guide gives two remedies: raise proxy_read_timeout for that location, or have the backend send periodic ping frames so the connection is never idle that long [26]. Doing both is common: a longer timeout plus application-level heartbeats every 20–30 s.

5 PostgreSQL production configuration

Recent Django releases support PostgreSQL 15 and later [9]. Production configuration has three layers: the server's resource settings, the connection path between Django and the server, and the roles and timeouts that keep one bad query from hurting everyone.

Server resources

For a dedicated server with at least 1 GB of RAM, the PostgreSQL manual calls 25% of memory "a reasonable starting value" for shared_buffers, and says more than 40% is unlikely to help because PostgreSQL also relies on the OS cache [28]. work_mem defaults to 4 MB and applies per sort or hash operation, so one complex query can use several multiples of it, and many sessions can do so at once [28]. Size it with your connection count in mind.

Managed services (Amazon RDS, Cloud SQL, Azure Database for PostgreSQL) set most of these through parameter groups or flags rather than a file, but the reasoning is the same.

Timeouts per role, not globally

statement_timeout and idle_in_transaction_session_timeout default to 0, meaning disabled [29]. Set them on the application role so they apply to every session that role opens, including sessions opened through a pooler. Migrations run under a separate role (§14), so long index builds are not cut off.

Connection pooling

Every PostgreSQL connection is a server process, so connection count is a real cost. There are two pooling options, and you usually want one of them, not both.

  • Django's built-in pool. Set "pool" in OPTIONS to True or to a dict of ConnectionPool arguments. It requires psycopg 3 with psycopg[pool], and CONN_MAX_AGE must be 0; connection lifetime is then controlled with the pool's max_lifetime [9]. The pool lives inside each worker process.
  • PgBouncer. An external pooler shared by every process and replica. Its default pool_mode is session; in transaction mode a server connection returns to the pool when each transaction finishes [30]. Django's docs say transaction pooling "requires disabling server-side cursors", via DISABLE_SERVER_SIDE_CURSORS = True [9].

Encrypt and verify the connection

libpq's sslmode=require encrypts traffic but does not check who is on the other end. verify-full also checks that the server certificate is signed by a trusted CA and that its name matches the host you asked for [31]. Use verify-full with the provider's CA bundle in sslrootcert, as in §1.

Isolation level
Django, like PostgreSQL, defaults to READ COMMITTED. Higher levels can be set with OPTIONS["isolation_level"], but then the application must handle serialization failures [9]. Most Django apps should stay on the default and use select_for_update() where they need row locks.

Exercise 5

Six app replicas each run 3 Gunicorn workers, and each worker uses Django's pool with max_size=8. PostgreSQL has max_connections = 100, of which you reserve 10 for admin and migration sessions. Does this fit? If not, give two ways to make it fit.

Show solution

Worst case is 6 × 3 × 8 = 144 connections, which exceeds the 90 available. Options: (1) shrink the per-worker pool, for example max_size=5 gives 90, but only if threads per worker are 5 or fewer, or requests will queue on the pool; (2) remove in-process pooling and put PgBouncer in transaction mode in front of PostgreSQL with default_pool_size around 40–80, so thousands of client connections share a small number of server connections [9,30]. Raising max_connections is a third option, but each connection costs server memory, and work_mem multiplies with it [28].

6 Static and media storage

Django separates static files (CSS, JavaScript and images that ship with the code) from media files (files users upload at runtime) [32,33]. They have different lifecycles and different security properties, and should be stored differently.

Static files: hashed names and long caching

collectstatic gathers files from every app and from STATICFILES_DIRS into STATIC_ROOT [34]. ManifestStaticFilesStorage appends an MD5 content hash to each filename (for example css/styles.55e7cbb9ba48.css), rewrites references inside CSS, and records the mapping in staticfiles.json, which makes far-future cache headers safe [34]. Run collectstatic once, at image build time, so every replica serves identical files.

WhiteNoise lets the app server serve these files itself with correct caching and compression, which removes the need for a separate static file server on platforms such as ECS or Cloud Run. Place its middleware directly after SecurityMiddleware and select its compressed manifest storage [35]:

Put a CDN in front for global users; the hashed names mean the CDN never serves a stale file after a deploy.

Media files: object storage, private by default

WhiteNoise is explicitly not for user uploads: it only scans files at startup, and serving uploads from the main domain is a security risk [35]. In a multi-replica deployment, local disk is also wrong because each replica would see different files. Use object storage through django-storages. Its S3 backend keeps files private by default (default_acl is None), signs URLs with query-string authentication by default, and overwrites same-named files unless file_overwrite is False [36]. If no keys are configured it falls back to the boto3 default session [36], which is how an IAM role on ECS, EKS or EC2 supplies credentials without any secret in settings (§11).

Django's security guide adds two rules for uploads: limit upload size at the web server, and serve user content from a separate registrable domain (for example usercontent-example.com, not a subdomain), because a file can be a valid image and valid HTML at the same time [7].

Exercise 6

After a deploy, some users see an unstyled page for a few minutes. The site uses plain StaticFilesStorage, Nginx sends expires 1y for /static/, and a CDN sits in front. Explain what happened and how the article's setup prevents it.

Show solution

With unhashed names, styles.css keeps the same URL across deploys. Browsers and the CDN hold the old file for up to a year, so new HTML can be paired with old CSS, or, during a rolling deploy, old HTML with new CSS. Manifest storage gives each version a unique name and keeps old hashed files available, so cached pages still find the files they reference, and long cache lifetimes become safe [34]. Running collectstatic in the image build keeps the manifest identical on every replica.

7 Docker and Docker Compose

A container image is the unit you build once in CI and promote unchanged through staging to production. Docker's guidance is to use multi-stage builds so the final image holds only what it needs, choose a small trusted base image, pin its version, exclude irrelevant files with .dockerignore, and rebuild regularly to pick up patched dependencies [37,38].

A multi-stage Dockerfile

Three details matter for operations. CMD uses the exec (JSON array) form, which the Dockerfile reference recommends for the main process; the shell form wraps the command in /bin/sh -c, so the shell, not Gunicorn, becomes PID 1 and receives the stop signal [39]. The process runs as an unprivileged user. And the build stage's compilers never reach the runtime image [38].

Compose for a single host or a production-like local stack

Compose's depends_on supports three conditions: service_started, service_healthy (based on the dependency's healthcheck) and service_completed_successfully [40]. The last one is how a one-shot migration service gates the web service. Compose secrets are mounted as files under /run/secrets/ rather than exposed as environment variables [41].

The $$ in the healthcheck escapes Compose interpolation so the variables are expanded inside the container, as in Docker's own example [40]. Nginx reaches the app through the service name, web:8000, in its upstream block.

Exercise 7

A container takes the full 10 seconds to stop on every docker compose down, and in-flight requests are cut off. Its Dockerfile ends with CMD gunicorn config.wsgi:application -c gunicorn.conf.py. What is wrong?

Show solution

That is the shell form, so the container runs /bin/sh -c "gunicorn ..." and the shell is PID 1 [39]. The stop signal goes to the shell, which does not forward it, so Gunicorn never starts its graceful shutdown; after the timeout Docker kills everything. Switch to the exec form, CMD ["gunicorn", "config.wsgi:application", "-c", "gunicorn.conf.py"], so Gunicorn receives SIGTERM and drains requests up to graceful_timeout [16]. Also make sure stop_grace_period is longer than that timeout.

ECS task definition

Each container definition can inject secrets through a secrets list whose valueFrom is the ARN of a Secrets Manager secret or an SSM parameter; the value arrives as an environment variable when the task starts [51]. stopTimeout is how long ECS waits before forcefully killing a container that does not exit on its own; without it, the default is 30 seconds [51].

The execution role is used by ECS itself to pull the image and read the secrets; the task role is what the Django code assumes when it calls AWS APIs, for example S3 for media. Keep them separate so the application cannot read secrets it was not given [51] (§11).

Load balancer target group

The ALB health check should call /readyz/. By default, ELB waits 300 seconds when deregistering a target so in-flight requests can finish [52]; for a Django app with a 30-second request timeout, lowering deregistration_delay.timeout_seconds to 30–60 seconds makes rolling deploys much faster. Slow start mode ramps traffic to new targets linearly, which helps when fresh workers have cold caches [52].

Exercise 9

The team stores the database password as a plain environment entry in the task definition so it "works the same as locally". List two concrete risks and the change you would make.

Show solution

Plain environment values are part of the task definition, so anyone with permission to describe task definitions can read the password, and it is copied into every revision and often into CI logs or infrastructure-as-code state. Rotation also requires a new task definition revision. Move it to Secrets Manager and reference it with secrets[].valueFrom [51]; grant only the execution role secretsmanager:GetSecretValue on that one ARN. Secrets Manager can then rotate the credential on a schedule [53], and a redeploy picks up the new value.

10 Kubernetes deployment

On Kubernetes, the Django web tier is a Deployment: a controller that keeps a set of identical Pods running and replaces them gradually during a rolling update, bounded by maxSurge and maxUnavailable [54]. Migrations run as a Job, which retries failed Pods up to backoffLimit [55]. Probes tell the kubelet when to restart a container and when to send it traffic [56].

Configuration and secrets

Kubernetes Secrets are, by default, stored unencrypted in etcd, and anyone who can create a Pod in a namespace can read every Secret in it. The docs list the minimum steps: enable encryption at rest, restrict access with least-privilege RBAC, limit which containers see each Secret, and consider an external secret store provider [57]. In practice that means the Secret below is created by a controller that syncs it from your cloud secret manager, not committed as YAML.

Deployment

The PodDisruptionBudget limits how many Pods voluntary disruptions such as node drains can take down at once [58,59]. preStop hooks run before the container receives its termination signal, and their time counts against the grace period [60,61].

Exercise 10

A team's liveness probe calls /readyz/, which checks PostgreSQL. During a 2-minute database failover, every web Pod in the cluster restarts repeatedly, and recovery takes 10 minutes after the database is back. Explain the chain of events and the fix.

Show solution

A failing liveness probe makes the kubelet restart the container [56]. Because the probe depends on the database, a database outage fails liveness everywhere at once; all Pods restart, enter crash back-off, and then reconnect at the same moment, adding load just as the database recovers. Liveness should only answer "is this process wedged?" and so should call /healthz/, which touches no dependencies. Dependency checks belong in the readiness probe, which only removes the Pod from Service endpoints without restarting it [56].

11 Secrets management and IAM

OWASP's secrets management guidance comes down to a few rules: keep secrets in a dedicated store rather than in code, images or configuration files; give each workload only the secrets it needs; prefer short-lived, automatically rotated credentials; and log access to secrets [62]. Cloud IAM guidance says the same from the identity side: use temporary credentials through roles instead of long-term access keys, and grant least privilege [63].

Exercise 11

Plan a zero-downtime rotation of SECRET_KEY after a laptop holding it was lost. What do you deploy, in what order, and what will users notice?

Show solution

Generate a new key and store it. Deploy with SECRET_KEY set to the new key and the compromised key at the front of SECRET_KEY_FALLBACKS [6]. Existing sessions and signed tokens keep validating against the fallback, so nobody is logged out, and everything newly signed uses the new key. Because the old key is compromised, keep the fallback window short: once you accept that sessions signed with it are invalidated, deploy again with the fallback removed. At that point users with old sessions must log in again, and password-reset links issued before the rotation stop working. Django's checklist asks you to remove old fallbacks "in a timely manner" [1].

12 Logging, metrics, tracing and alerting

Google's SRE book names four "golden signals" for user-facing systems: latency, traffic, errors and saturation [66]. Logs explain individual events, metrics show the four signals over time, traces show where time went inside one request, and alerts turn metrics into pages. Each needs a deliberate design.

Logs as JSON on stdout

The Twelve-Factor App treats logs as an event stream: the app writes unbuffered to stdout and the platform routes it [67]. Django's logging is configured with Python's dictConfig schema through the LOGGING setting [68,69]. Structured JSON with a request ID makes logs searchable and lets you join them with traces.

A ContextVar works for both WSGI threads and ASGI tasks, unlike a thread-local. Django's checklist asks you to review logging before launch and to consider an error-tracking service, since email error reports "don't scale very well" [1].

Metrics with Prometheus

Prometheus naming practice: use base units such as seconds, suffix counters with _total, and never put unbounded values such as user IDs in labels [70]. Label by the URL route pattern, not the raw path. Because Gunicorn runs several processes, the Python client must run in multiprocess mode: point PROMETHEUS_MULTIPROC_DIR at an empty directory before start, collect with MultiProcessCollector, and mark dead workers in Gunicorn's child_exit hook, as in §2 [71].

Expose metrics_view on an internal port or protect it; it should not be reachable from the internet.

Distributed tracing with OpenTelemetry

OpenTelemetry's Python distribution provides zero-code instrumentation through opentelemetry-instrument, which monkey-patches supported libraries [72]. Pre-fork servers such as Gunicorn need care, because exporters and background threads created before fork() do not work in the workers; the troubleshooting guide's workarounds include programmatic instrumentation in Gunicorn's post_fork hook [73]. Trace context travels between services in the W3C traceparent header [74].

Add the trace ID to the JSON log payload and you can jump from a log line to its trace.

Alerting on symptoms, against an SLO

The SRE book says every page should be actionable and that it is better to alert on symptoms than causes [66]. The SRE workbook's recommended set-up for a 99.9% SLO uses multiwindow burn rates: page when the 1-hour and 5-minute error rates both exceed 14.4× the budget rate (2% of the monthly budget gone), or the 6-hour and 30-minute rates exceed 6× (5% gone); open a ticket at 1× over 3 days [75]. Prometheus alerting rules express this with an expression and an optional for duration [76].

Exercise 12

A developer adds a path label containing request.path to the request counter. Within a day Prometheus memory doubles. Why, and how does the article's middleware avoid it?

Show solution

Every distinct label value creates a new time series. Raw paths include IDs, slugs and query-like segments (/orders/18231/, /orders/18232/, ...), plus whatever bots request, so the number of series grows without limit. Prometheus's naming guide warns against high-cardinality labels such as user IDs for exactly this reason [70]. The middleware labels by request.resolver_match.route, the URL pattern (orders/<int:pk>/), which has one value per route, and uses "unmatched" for 404s.

13 Health checks and graceful shutdown

Health endpoints answer two different questions. Liveness: is this process able to make progress, or should it be restarted? Readiness: should this instance receive traffic right now? Kubernetes maps them to separate probes, and adds a startup probe that holds the other two off until a slow-starting app is up [56].

Endpoints that bypass host validation

Probes from the kubelet or a load balancer usually connect by IP address, so their Host header is not in ALLOWED_HOSTS and Django would answer 400. The middleware below sits first in MIDDLEWARE (§6) and answers before anything calls request.get_host(). A failing readiness check returns 503, the status RFC 9110 defines for a server that is temporarily unable to handle the request, optionally with Retry-After [77].

Keep the readiness check cheap: it runs every few seconds on every replica. Do not expose error details in the response body; log them instead.

The shutdown sequence

Graceful shutdown means no request is cut off when an instance stops, whether for a deploy, a scale-in or a node drain. The Twelve-Factor App calls this disposability: fast startup and graceful shutdown on SIGTERM [78]. On Kubernetes, when a Pod is deleted it is removed from Service endpoints while the preStop hook runs; then the container receives SIGTERM; if it is still running when terminationGracePeriodSeconds (default 30 s) expires, it is killed with SIGKILL [60,61]. Gunicorn responds to SIGTERM by finishing in-flight requests for up to graceful_timeout [16].

Shutdown time budget for the Kubernetes manifest in §10
PhaseDurationWhat happens
preStop sleep10 sEndpoint removal reaches kube-proxy and the ingress; the Pod still serves stragglers.
Gunicorn drain≤ 25 sSIGTERM → workers stop accepting and finish in-flight requests.
Margin10 sExporters flush spans and logs.
terminationGracePeriodSeconds45 sAnything still running gets SIGKILL.

On ECS, the equivalent knobs are the target group's deregistration delay and the container's stopTimeout [51,52]. In Compose, it is stop_grace_period [79]. The rule is the same everywhere: the platform's grace period must be longer than the server's drain time, which must be longer than your slowest legitimate request.

Exercise 13

During every rolling deploy on Kubernetes, the ingress logs a burst of 502 errors lasting about a second per Pod, even though Gunicorn drains correctly. There is no preStop hook. Explain the race and the fix.

Show solution

Endpoint removal and SIGTERM happen at roughly the same time, and endpoint removal takes a moment to reach every proxy [61]. Gunicorn closes its listening socket as soon as it gets SIGTERM, so for a short window the ingress still routes new connections to a Pod that refuses them, producing 502s. A preStop hook that sleeps a few seconds delays SIGTERM until routing has caught up [60]; then raise terminationGracePeriodSeconds so that the sleep plus graceful_timeout still fits.

14 Database migration strategy

During a rolling deploy, old and new code run against the same database at the same time. Every migration must therefore be compatible with both the release before it and the release after it. The usual way to achieve that is expand and contract: first add new structures that old code ignores, deploy code that uses them, and only in a later release remove what is no longer used.

When and how migrations run

  • Run migrate once per release as a separate one-off step (a CI step, an ECS task or a Kubernetes Job), before the new code rolls out. The Twelve-Factor App calls these admin processes and asks that they run in an identical environment to the app [80]. Do not run it in each container's entrypoint, where several replicas start it at once.
  • On PostgreSQL, each migration runs in a transaction by default because PostgreSQL supports transactional DDL [81]. A failed migration rolls back cleanly unless you set atomic = False.
  • Review the SQL before merging with sqlmigrate app 0042 [81], and gate deploys on migrate --check, which exits non-zero when unapplied migrations exist [10].

Locks are the real risk

Most ALTER TABLE forms take an ACCESS EXCLUSIVE lock [82], which conflicts with every other lock mode, including plain SELECT [83]. The statement itself may be instant, but if it waits behind a long transaction, every query that arrives after it queues too. Setting lock_timeout for the migration role (§5) makes the migration fail fast instead of freezing the site; retry it later.

ChangeSafe approach on PostgreSQL
Add a nullable column, or one with a constant defaultSafe. A non-volatile default is stored in metadata, so no table rewrite is needed [82].
Add an indexAddIndexConcurrently in a migration with atomic = False [84,85]. Concurrent builds avoid blocking writes but cannot run in a transaction and leave an INVALID index on failure, which you drop and retry [86].
Add NOT NULL to an existing columnAdd CHECK (col IS NOT NULL) NOT VALID, then VALIDATE CONSTRAINT (weaker lock), then SET NOT NULL, which skips the scan because the valid check proves it [82].
Add a foreign keyAdd with NOT VALID, then validate separately [82].
Rename a column or tableAvoid. Add the new column, write to both, backfill, switch reads, then drop the old one in a later release.
Drop a columnRelease 1: remove the field from the model and from Django's migration state only. Release 2: drop it from the database.
Backfill a large tableNon-atomic data migration in batches, each batch in its own transaction [85].

Examples

Before release 1, give the column a database default or make it nullable so that inserts from the new code, which no longer sends a value, do not fail. In release 2, a RunSQL("ALTER TABLE orders_order DROP COLUMN legacy_status") removes it.

Data migrations must use apps.get_model(); importing the model directly "may work initially" but breaks when old migrations are re-run later [81].

Exercise 14

A migration adds an index with plain AddIndex to a 200-million-row orders table, and checkout is down for 18 minutes. Rewrite it safely, and say what to do if the concurrent build fails halfway.

Show solution

A plain CREATE INDEX blocks writes on the table until it finishes [86], so every checkout insert waited. Use AddIndexConcurrently from django.contrib.postgres.operations in a migration with atomic = False, as in the 0042 example [84]. If the build fails (for example on a deadlock or a uniqueness violation), PostgreSQL leaves an INVALID index that is ignored for queries but still costs write overhead; drop it and run the concurrent build again, or use REINDEX INDEX CONCURRENTLY [86].

15 Backups and disaster recovery

Two numbers drive the design. The recovery point objective (RPO) is how much data, measured in time, you can afford to lose; the recovery time objective (RTO) is how long the service can be down. AWS describes four strategies in increasing cost and decreasing RTO and RPO: backup and restore, pilot light, warm standby, and multi-site active/active [87]. NIST SP 800-34 frames the same work as contingency planning, including regular testing of the plan [88].

Database: physical backups plus WAL for point-in-time recovery

A base backup combined with a continuous archive of WAL files lets PostgreSQL restore to any moment since the base backup [89]. pg_dump output is a logical backup: useful for copies and migrations between versions, but it "cannot be used as part of a continuous-archiving solution" [89,90]. Managed services do this for you: RDS automated backups let you restore to any point within the retention period you configure [91].

Logical backup and an automated restore test

An untested backup is a hope, not a plan. Record how long the drill took: that is your measured RTO for this path.

Exercise 15

At 14:05 a faulty data migration sets every order's status to cancelled. You have nightly pg_dump files and RDS automated backups with 7-day retention. Which do you use, and how do you limit the damage to other data written since 14:05?

Show solution

Use point-in-time recovery from the automated backups to a new instance at 14:04, just before the migration [91]. The nightly dump would lose up to a day of data. PITR always creates a new database, so do not cut over blindly: orders, payments and users written after 14:05 exist only in the damaged database. Either copy the correct status values from the restored instance back into production with a targeted UPDATE ... FROM, or switch to the restored instance and replay later writes from the damaged one. The first is usually smaller and safer. Afterwards, add the incident to your restore drills, and require RunPython migrations to be reversible or tested against a production-sized copy.

16 Horizontal scaling and load balancing

Horizontal scaling means adding identical app instances behind a load balancer. It only works if instances are stateless: anything that must outlive a request goes to a backing service [5]. For Django, that checklist is short.

  • Sessions in the database or cache (cached_db), never in local files or local memory [92].
  • Cache shared, such as Redis, so invalidation is seen by every instance [1,93].
  • Media in object storage (§6). Static files baked into the image.
  • Background work in a queue processed by separate workers. Django 6.0's django.tasks framework defines tasks and enqueues them, but "does not provide a worker mechanism"; execution needs external infrastructure [3].
  • WebSockets with Channels need a shared channel layer to reach clients connected to other instances [22].

Load balancing algorithms

Nginx balances round-robin by default, and also offers least_conn and ip_hash for session persistence [94]. With stateless Django, prefer round-robin or least-connections; sticky sessions hide state bugs and unbalance load. Passive health checks (max_fails, fail_timeout) take a failing server out of rotation [25]. Managed load balancers such as the ALB combine active health checks with slow start for new targets [52,95].

Autoscaling

Kubernetes' Horizontal Pod Autoscaler changes the replica count of a Deployment to match demand, and needs resource requests on the containers to compute CPU utilization [96]. Scale on CPU for CPU-bound apps, or on request rate or latency through custom metrics for I/O-bound ones.

The database is the ceiling

Web replicas scale out easily; the primary database does not. Write the connection budget down and let it set maxReplicas:

Connection budget for maxReplicas: 12
Replicas × workers × pool size12 × 3 × 4 = 144 client connections
Through PgBouncer (transaction mode)→ default_pool_size 40 server connections
Plus migrations, admin, monitoring+ 15
PostgreSQL max_connections200 (comfortable headroom)

Beyond that, scale reads with replicas and Django's database routers, cache aggressively, and move slow work to background workers. Without a pooler, the same 12 replicas would need 144 server connections and would hit the limit during a deploy surge, when old and new Pods overlap.

Exercise 16

After scaling from 2 to 6 replicas, some users are logged out at random, and a "recently viewed" list flickers between two versions. Settings show SESSION_ENGINE = "django.contrib.sessions.backends.file" and the default cache. Explain both symptoms and fix them.

Show solution

File sessions live on each instance's own disk, so a request routed to a different replica cannot find the session and the user appears logged out. The default cache is per-process local memory [1], so each worker on each replica has its own "recently viewed" list. Both break the stateless-process rule [5]. Use a shared Redis cache for CACHES and SESSION_ENGINE = "django.contrib.sessions.backends.cached_db" [92]. Sticky sessions at the load balancer would hide the symptom but not fix the design, and would break again on every deploy.

Go-live checklist

  1. check --deploy --fail-level WARNING passes against production settings (§1).
  2. Gunicorn or Uvicorn runs behind a buffering proxy; forwarded headers trusted only from the proxy (§2–4).
  3. Unknown hosts are rejected at the proxy; HSTS starts with a short max-age (§1, §4).
  4. Database connections are pooled and budgeted; app role has timeouts and no DDL rights (§5).
  5. Static files are hashed and baked into the image; media is in private object storage on a separate domain (§6).
  6. Image runs as non-root with an exec-form command and a health check (§7).
  7. CI fails on missing migrations; deploys use OIDC and immutable image tags (§8).
  8. Secrets come from a secret store; workloads use roles, not keys (§9, §11).
  9. Liveness has no dependencies; readiness does; grace periods exceed drain time (§10, §13).
  10. JSON logs with request IDs, golden-signal metrics, traces, and SLO burn-rate alerts with runbooks (§12).
  11. Migrations are backward compatible, run once per release, with lock_timeout (§14).
  12. PITR is enabled, an independent copy exists, and a restore drill ran this month (§15).
  13. Instances are stateless and the connection budget caps autoscaling (§16).
