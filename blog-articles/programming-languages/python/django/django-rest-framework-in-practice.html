00Why DRF, and the sample API

Django REST framework (DRF) is a toolkit for building Web APIs on top of Django. It adds a serialization layer that turns model instances into JSON and validates incoming data, class-based and function-based API views, pluggable authentication, permission and throttling policies, and a browsable HTML interface for every endpoint [1]. The current release at the time of writing is 3.18.3, published on 6 October 2026, and the framework supports Django 5.2, 6.0 and 6.1 on Python 3.10 and later [1,2].

The vocabulary of DRF comes from HTTP and from REST. Resources are identified by URLs, clients manipulate them through representations, and each message describes how to process itself [3]. The HTTP specification then fixes what methods and status codes mean: GET is safe, PUT and DELETE are idempotent, 201 Created announces a new resource, and so on [4]. Most DRF defaults are those rules written as code, which is why this article cites RFC 9110 alongside the DRF documentation.

How to read this article

Every section builds on one Django project: a small library catalogue with authors, books and reviews. All code shown here was copied by a build script from that project, and the project's 53 tests (unit, integration, exercise solutions and schema-driven contract tests) pass against Django 6.1.2 and DRF 3.18.3. Where a statement comes from running that code rather than from documentation, the text says so.

References use the Vancouver system: sources are numbered in the order they are first cited, and the numbered list at the end follows the National Library of Medicine's Citing Medicine format for Internet sources [5].

01Serializers and model serializers

A serializer does two jobs. In one direction it converts complex data, such as model instances and querysets, into Python primitives that a renderer can turn into JSON. In the other it parses and validates incoming primitives and turns them back into objects [7]. The same class handles both, so validation rules and output shape stay in one place.

A plain Serializer

A Serializer declares every field explicitly and, if it should save data, implements create() and update(). Calling save() on a validated serializer calls create() when no instance was passed and update() when one was [7].

ModelSerializer

ModelSerializer is the shortcut you will use most. It generates fields from the model, generates validators such as those for unique constraints, and provides default create() and update() implementations [7]. Since DRF 3.3 you must list fields or exclude explicitly [7]. That rule is also a security control: an explicit allow-list stops a client from setting fields it should not touch, the mass-assignment problem that OWASP files under broken object property level authorization [8].

Fields that the model does not have, such as book_count, are declared on the serializer. Here the value comes from a queryset annotation in the view, so the serializer only declares it read_only. Field options such as read_only, write_only, required, source and allow_null are listed on the serializer fields page [9].

Field-level and object-level validation

A method named validate_<field> validates one field and returns the cleaned value. A method named validate() receives all the attributes and checks rules that span fields [7]. Partial updates. With partial=True (a PATCH request), attrs holds only the fields that were sent, so the object-level check falls back to self.instance for the publication date [7].

02API views and APIView

APIView subclasses Django's View. The differences are what make it an API view: handlers receive DRF Request objects, they can return DRF Response objects that are rendered after content negotiation, APIException subclasses are turned into error responses, and authentication, permission and throttle checks run before the handler is dispatched [10].

Each policy can be set per view through class attributes: renderer_classes, parser_classes, authentication_classes, throttle_classes and permission_classes. When they are not set, the defaults from REST_FRAMEWORK apply [10].

Two details in this view are easy to get wrong. First, the view uses get_object_or_404; DRF converts Django's Http404 into a 404 response just as it converts its own exceptions [11]. Second, every handler accepts version=None. The project uses URL path versioning (section 14), and the captured version URL argument is passed to the handler as a keyword argument, so a handler without it raises TypeError. The test suite caught exactly that before the signatures were fixed.

Object permissions in APIView. A plain APIView does not run object-level permission checks for you. If a permission class implements has_object_permission(), you must call self.check_object_permissions(request, obj) after fetching the object. Generic views do this inside get_object() [12].

03Function-based API views

The @api_view decorator gives a plain function the same request handling as APIView. It takes the list of allowed methods; with no list only GET is allowed, and any other method gets 405 Method Not Allowed [10]. Policy decorators such as @permission_classes and @throttle_classes go below it [10].

Function views suit small, one-off endpoints such as health checks or webhooks. Once an endpoint needs pagination, filtering or several methods on the same resource, the generic classes in the next section remove most of the code. DRF's own tutorial makes the same progression, from functions to classes to generics [13]. The @extend_schema decorators are for OpenAPI generation and are explained in section 15.

05ViewSets and routers

A ViewSet groups the actions for one resource in one class. Instead of handler methods named after HTTP methods, it defines actions: list, create, retrieve, update, partial_update and destroy. ModelViewSet provides all six through the mixins above, and ReadOnlyModelViewSet provides only list and retrieve [15]. Extra endpoints are added with the @action decorator, where detail=True acts on one object and detail=False on the collection [15].

During dispatch self.action names the current action, so methods such as get_serializer_class() and get_permissions() can branch on it [15]. Exercise 4 uses this to make deletion staff-only.

@action overrides only existing attributes. Keyword arguments to @action are applied as view attributes, and DRF raises TypeError: BookViewSet() received an invalid keyword 'throttle_scope' at URL-loading time if the class does not already define the attribute. That is why the class declares throttle_scope = None. This was observed when building the sample project.

Routers

A router generates the URL patterns for a ViewSet. register(prefix, viewset, basename) needs an explicit basename when the ViewSet has no queryset attribute, as here, because the router normally derives the name from the queryset's model [16]. Generated URL names follow the pattern {basename}-list and {basename}-detail, and @action routes get {basename}-{action name} [16].

07Request parsing and response rendering

DRF's Request wraps Django's HttpRequest. request.data holds the parsed body for any content type and any method, and request.query_params is a clearer name for request.GET [20]. When request.data is first accessed, DRF reads the Content-Type header and picks a parser that matches it [21]. The defaults are JSONParser, FormParser and MultiPartParser [6].

ParserMedia typerequest.data
JSONParserapplication/jsondict or list
FormParserapplication/x-www-form-urlencodedQueryDict
MultiPartParsermultipart/form-dataQueryDict, files in request.FILES
FileUploadParser*/*dict with a single 'file' key

The table follows the parsers guide, which also advises that FileUploadParser should usually be the only parser on its view [21].

On the way out, Response takes unrendered Python data plus an optional status and headers [22]. Content negotiation then chooses a renderer from the client's Accept header: more specific media types win over less specific ones, ties go to the order of renderer_classes, and a client that sends */* or no header gets the first renderer [23,24]. The defaults are JSONRenderer and BrowsableAPIRenderer [6]. The browsable renderer is what serves an HTML page with forms when you open an endpoint in a browser [24].

When negotiation fails in either direction, DRF answers with the matching HTTP status. The sample project's tests check both:

An XML body with no XML parser gets 415 Unsupported Media Type, and Accept: application/xml with no XML renderer gets 406 Not Acceptable. These come from DRF's UnsupportedMediaType and NotAcceptable exceptions and match RFC 9110 §15.5.16 and §15.5.7 [4,11].

08Authentication and permissions

DRF separates two questions. Authentication decides who sent the request and sets request.user and request.auth. Permissions decide whether that caller may do what they asked [12,25]. Both run before the handler.

Choosing between 401 and 403

RFC 9110 says a 401 response must carry a WWW-Authenticate header that tells the client how to authenticate, while 403 means the server understood the request and refuses it [4]. DRF follows this. If the request was not authenticated and the first authentication class can produce a WWW-Authenticate header, the response is 401; otherwise it is 403. A request that authenticated but lacks permission always gets 403 [25]. In the sample project JWT authentication comes first, so anonymous writes get 401 with WWW-Authenticate: Bearer realm="api".

The built-in authentication classes are SessionAuthentication, BasicAuthentication, TokenAuthentication and RemoteUserAuthentication; the default is session plus basic [6,25]. Session authentication enforces Django's CSRF protection on unsafe methods (POST, PUT, PATCH, DELETE) for authenticated users [25], which matters when a browser front end shares the session cookie.

Permission classes

Built in are AllowAny, IsAuthenticated, IsAdminUser, IsAuthenticatedOrReadOnly, DjangoModelPermissions, DjangoModelPermissionsOrAnonReadOnly and DjangoObjectPermissions [12]. The project default if you configure nothing is AllowAny [6], so set DEFAULT_PERMISSION_CLASSES deliberately. A custom class overrides has_permission() for view-level checks, has_object_permission() for per-object checks, or both [12]:

Permission classes compose with &, | and ~, for example permission_classes = [IsAuthenticated & (IsOwner | IsAdminUser)] [12].

Object permissions do not filter lists. Generic views check object permissions only when retrieving a single instance. They are not applied to each row of a list, and they do not run on create [12]. Restrict list visibility in get_queryset(), as the mine action does, and check create-time rules in the serializer or perform_create().

09Token and JWT authentication

DRF's built-in tokens

TokenAuthentication stores one random key per user in the database. Add rest_framework.authtoken to INSTALLED_APPS, run migrations, and expose obtain_auth_token, which returns {"token": "..."} when a username and password are posted to it [25]. Clients then send the header Authorization: Token <key>. The documentation describes the implementation as fairly simple, points to django-rest-knox for multiple tokens per user and expiry, and requires that APIs using it be served only over HTTPS [25].

JSON Web Tokens with Simple JWT

A JSON Web Token is a compact, URL-safe set of claims, signed (JWS) or encrypted (JWE) [26]. A signed token is only base64url-encoded, so anyone holding it can read the claims; the signature proves integrity, not secrecy. Because the server can check the signature without a database lookup, JWTs suit stateless services and short-lived credentials.

The common DRF package is Simple JWT. Setup adds rest_framework_simplejwt.authentication.JWTAuthentication to DEFAULT_AUTHENTICATION_CLASSES and routes TokenObtainPairView, TokenRefreshView and, optionally, TokenVerifyView [27]:

Clients exchange a username and password for an access token and a refresh token, send the access token as Authorization: Bearer <token>, and post the refresh token to get a new access token when it expires. The Bearer scheme and its WWW-Authenticate challenge come from RFC 6750 [28].

The defaults are from the Simple JWT settings reference [29]. Some consequences follow directly. With HS256 the signing key is the Django SECRET_KEY, so leaking it lets an attacker mint tokens for any user. A JWT cannot be revoked before it expires unless you keep server-side state; Simple JWT's optional blacklist app stores outstanding and blacklisted refresh tokens for that purpose [30]. RFC 8725 adds general rules for JWT consumers: pin the algorithms you accept, validate every token's issuer and audience where they apply, and do not accept unsigned tokens [31]. Bearer tokens of either kind must travel only over TLS, because whoever holds one can use it [28].

Which to choose. For a first-party browser front end on the same domain, session authentication with CSRF protection needs no token storage in JavaScript. For mobile apps, command-line clients and service-to-service calls, use tokens: DRF tokens are simplest to revoke (delete the row), and JWTs avoid the database lookup at the cost of harder revocation.

10Filtering, searching, ordering

The simplest filter is get_queryset() itself: filtering on request.user gives each user only their own records [32]. For client-controlled filters DRF uses filter backends, set globally with DEFAULT_FILTER_BACKENDS or per view with filter_backends [32].

Field filters with django-filter

DjangoFilterBackend comes from the django-filter package. Setting filterset_fields on a view generates equality filters; a FilterSet class supports lookups such as ranges [32,33].

With filterset_class = BookFilter on the ViewSet, GET /api/v1/books/?author=2&max_price=15 returns that author's books costing 15 or less.

Search

SearchFilter reads the search query parameter and matches it against search_fields, which can follow relations with double underscores. A prefix changes the match: ^ starts with, = exact, $ regular expression and @ full-text search on PostgreSQL. With no prefix the match is case-insensitive containment [32]. The ViewSet's search_fields = ["title", "=isbn", "author__name"] therefore finds books by partial title or author name, and by exact ISBN only.

Ordering

OrderingFilter reads the ordering parameter; a leading - reverses the order and commas combine fields. If you omit ordering_fields, clients may sort by any readable serializer field, which the documentation warns can leak data, so list the allowed fields explicitly [32]. A request to order by a field that is not allowed is ignored rather than rejected, as the test below shows.

11Pagination

DRF provides three styles. PageNumberPagination takes ?page=, LimitOffsetPagination takes ?limit= and ?offset=, and CursorPagination returns opaque cursors that only move forward or backward [34]. Pagination is applied automatically only by generic views and ViewSets; a plain APIView must call the paginator itself [34]. To enable it globally, set both DEFAULT_PAGINATION_CLASS and PAGE_SIZE, which default to None [34].

page_size_query_param lets clients choose a page size, and max_page_size caps it [34]. A paginated list response looks like this:

Page-number and limit-offset pagination both run a COUNT query and an OFFSET query, which slow down on large tables and can skip or repeat rows when data changes between requests. Cursor pagination avoids both, but needs an ordering on a field that is unique or nearly unique, does not change after creation, and is indexed. Its default ordering is -created [34], which is why the Book model has a created timestamp. Always paginate over an ordered queryset; the test run printed an UnorderedObjectListWarning until Review got a default ordering.

12Throttling and rate limiting

Throttles are like permissions, but they depend on how often a client has made requests. AnonRateThrottle limits anonymous clients by IP address, UserRateThrottle limits authenticated users by user id, and ScopedRateThrottle applies a named rate to views that declare a throttle_scope [35]. Rates are written as a number per period, where the period is s, m, h or d (only the first character counts, so minute works too) [35]. This project uses "anon": "100/hour", "user": "1000/hour" and "reviews": "10/minute".

When a request is throttled DRF raises Throttled, which produces 429 Too Many Requests, and includes a Retry-After header when the throttle can compute the wait [11,35]. Status 429 and its Retry-After hint are defined in RFC 6585 [36], and Retry-After itself in RFC 9110 §10.2.3 [4].

Throttle history is stored in Django's cache [35]. The default local-memory cache is per process [37], so with several worker processes each one counts separately; point throttles at a shared cache such as Redis in production. Clear the cache between tests, as the project's conftest.py does, or counts leak from one test into the next.

Throttling is not a security boundary. The DRF documentation says application-level throttling should not be treated as protection against brute-force or denial-of-service attacks, and notes that the built-in throttles use non-atomic operations that can let a few extra requests through under heavy concurrency [35]. Client identity comes from X-Forwarded-For or REMOTE_ADDR; behind a proxy, set NUM_PROXIES so the client address is not spoofable [35]. Put hard limits at the proxy or gateway and use DRF throttles for fair-use quotas.

13Validation and exception handling

Validation happens in layers. Field types reject malformed values, field options such as max_length constrain them, validate_<field>() and validate() add your own rules, and ModelSerializer adds validators generated from model constraints [7,9]. The isbn field is unique=True on the model, so a duplicate fails with the error code unique before the database is touched (see test_unique_validator_from_model above). is_valid(raise_exception=True) raises ValidationError, which becomes a 400 response [7,11].

What DRF handles

DRF's exception handler turns three kinds of exception into responses: subclasses of APIException, Django's Http404, and Django's PermissionDenied. Anything else propagates and becomes a 500 [11]. Most error bodies have a single detail key; validation errors are keyed by field, with cross-field errors under non_field_errors by default [6,11].

A custom handler for RFC 9457 problem details

RFC 9457 defines a standard JSON error format, application/problem+json, with the members type, title, status, detail and instance [38]. A custom handler set through EXCEPTION_HANDLER receives (exc, context), can call the default handler first, and returns a Response, or None to let the exception propagate [11].

Set content_type, not the header. In testing with DRF 3.18.3, assigning response["Content-Type"] inside the handler was overwritten when the response was rendered, and the client received application/json. Setting response.content_type keeps the media type.

14API versioning

DRF offers five versioning schemes: AcceptHeaderVersioning, URLPathVersioning, NamespaceVersioning, HostNameVersioning and QueryParameterVersioning [39]. Whichever is active sets request.version; with no scheme it is None [39]. DEFAULT_VERSION applies when the request carries none, ALLOWED_VERSIONS rejects anything else, and VERSION_PARAM (default "version") names the parameter [39].

15OpenAPI schemas and Swagger documentation

Fixing what introspection cannot see

The first run on the sample project reported 23 errors and a warning, and they are typical. Generic views and ViewSets are introspected from serializer_class and queryset. Function views and plain APIViews have neither, so drf-spectacular reported "unable to guess serializer" and skipped them. The nested ReviewList failed because get_queryset() reads self.kwargs["book_pk"], which does not exist during schema generation. Three fixes cleared all of them, using the tools described in the customization guide [45]:

  • @extend_schema(request=..., responses=...) on function views, with inline_serializer for one-off response shapes (see author_list and health in section 03).
  • A serializer_class attribute on AuthorDetail, which drf-spectacular reads even on a plain APIView.
  • A swagger_fake_view guard in get_queryset() that returns Review.objects.none() while the schema is generated (see ReviewList in section 04).

16Nested serializers and relationship handling

DRF represents relations in several ways [46]:

FieldRepresentationExample
PrimaryKeyRelatedFieldThe target's primary key"author": 2
SlugRelatedFieldA unique field on the target"author": "octavia-butler"
StringRelatedField__str__(), read-only"author": "Octavia E. Butler"
HyperlinkedRelatedFieldA URL to the target"author": "https://…/authors/2/"
Nested serializerThe target's full representation"author": {"id": 2, "name": "…"}

A writable relation needs either a queryset, which DRF uses to look up the instance from the input, or read_only=True [46]. BookSerializer combines the two common patterns: a read-only nested AuthorSummarySerializer for output, and a write-only PrimaryKeyRelatedField named author_id for input. Clients read a useful object and write a simple id.

Writable nested serializers

Nested serializers are read-only by default. To accept nested input you must write create() and/or update() that save the children explicitly, because DRF cannot know whether nested data should create, update or replace related rows [7,46].

The N+1 query problem

Nested output is where APIs get slow. DRF does not optimize querysets for you [46], so serializing a page of books with nested authors and reviews runs one query for the page and then one more per book for each relation. select_related() follows foreign keys with a SQL join, and prefetch_related() fetches many-valued relations in one extra query per relation [47,48]. 17API testing and contract testing

DRF's test tools

APIRequestFactory and APIClient extend Django's RequestFactory and Client, and APITestCase mirrors Django's TestCase with self.client set to an APIClient [50,51]. Three features do most of the work. force_authenticate(user=...) skips credentials so a test can focus on behaviour. format="json" encodes the body as JSON; the default test format is multipart unless TEST_REQUEST_DEFAULT_FORMAT changes it, as this project does. And response.data holds the data before rendering, which is easier to assert on than parsed bytes [51]. APIClient skips CSRF checks unless created with enforce_csrf_checks=True [51].

The project uses pytest with pytest-django. The django_db marker gives a test database access inside a transaction that is rolled back afterwards [49]. Shared fixtures live in conftest.py:

A good API test suite covers each endpoint's success path, every documented error status, permission boundaries between users, and query counts for list endpoints. The tests shown in earlier sections are all from tests/test_api.py.

Contract testing

Unit tests check that code does what its author intended. Contract tests check that the API does what its published description promises, which is what clients actually depend on. There are two common approaches.

Provider-side, schema-driven. Schemathesis reads an OpenAPI document, generates requests from it with property-based testing, and checks the responses against the schema. It can call a Django WSGI application in-process, so no server is needed; database access then needs pytest-django's db fixture and a Hypothesis health-check suppression, and localhost must be in ALLOWED_HOSTS [52].

The first test fails when someone changes the API without regenerating and committing schema.yml, so schema changes show up in code review. The second generated hundreds of requests and found three real problems while this article was written: the URL ordering bug in section 14, the integer-overflow 500 in section 04, and missing schema information for function views in section 15. It also flagged behaviour that is deliberate, such as 400 for an unknown ?author= id, which the schema does not declare. The test therefore runs an explicit set of checks; declaring 4xx responses in the schema would let you turn on the stricter ones.

Consumer-driven. Pact takes the opposite direction. Each consumer records the requests it makes and the responses it expects, and the provider replays those contracts in its own build, so the provider learns which changes would break a real client before deploying [53]. Use schema-driven tests to keep an API honest to its documentation, and consumer-driven contracts when several teams depend on it and you need to know which fields they actually use.

Exercise 1 serializers

Add read-only average_rating and review_count fields to a book serializer without running one query per book.

Show solution

Compute both values in the database with annotate(Avg(...), Count(..., distinct=True)) [47] and declare them as read-only fields. distinct=True matters once more than one join is involved.

The annotation is in BookStatsViewSet.get_queryset() (exercise 3's listing).

Exercise 4 permissions

Owners may edit their books, staff may edit any book, and only staff may delete. What status should a non-staff owner get on DELETE?

Show solution

get_permissions() in the ViewSet above returns [IsAdminUser()] when self.action == "destroy". The owner is authenticated but not permitted, so the answer is 403, not 401 [4,25].

A FilterSet field can target an annotation by name, because the filter runs on the annotated queryset. max_limit caps whatever the client sends [33,34].

Exercise 6 throttling

Allow 5 requests a minute in bursts and 100 a day overall per user. Write a test proving the sixth request in a minute gets 429.

Show solution

Subclass UserRateThrottle twice with different scopes, add rates "burst": "5/minute" and "sustained": "100/day", and list both throttles on the view. Every throttle must allow the request [35].
