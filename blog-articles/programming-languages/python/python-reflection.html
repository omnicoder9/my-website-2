Reflection in Python

1Reflection, introspection, intercession

Pattie Maes, in the 1987 paper that gave the field much of its vocabulary, defined computational reflection as "the activity performed by a computational system when doing computation about (and by that possibly affecting) its own computation"[1]. A reflective system is one that "incorporates structures representing (aspects of) itself", and those structures are causally connected to the system: change one and the other changes with it[1].

Bobrow, Gabriel and White split the idea in two, and the split is the one this article uses[2,3]:

  • Introspection is "the ability for a program to observe and therefore reason about its own state". In Python that means asking an object for its type, its attributes or its signature.
  • Intercession is "the ability for a program to modify its own execution state or alter its own interpretation or meaning". In Python that means setting an attribute whose name arrived at runtime, creating a class from a dictionary, or overriding how attribute lookup itself works.

Python is reflective all the way down because everything it manipulates is an object: "All data in a Python program is represented by objects or by relations between objects"[4]. Classes, functions, modules and methods are objects too, so the same small set of tools works on all of them. And the structures are causally connected in Maes's sense: a class's namespace is a real dictionary, and an attribute reference such as C.x is translated to a lookup in C.__dict__["x"][4]. Changing the namespace changes the class.

Scope of this article

Examining objects in depth (the inspect module, dir and vars, type checks, docstrings, sys, gc and dis) is the subject of the companion article on introspection in this series. Section 2 recaps just enough of it to support the rest. Decorators, descriptors, metaclasses, monkey patching and dynamic imports also have their own articles, so they appear here only where reflection leans on them.

3Attributes by name

Four built-ins turn a string into an attribute operation. getattr(x, 'foobar') is equivalent to x.foobar, setattr(x, 'foobar', 123) to x.foobar = 123, and delattr(x, 'foobar') to del x.foobar[5]. hasattr answers whether the name exists, and it does so by calling getattr and checking whether an AttributeError is raised[5].

Three details in that output come straight from the specification of these functions:

  • With a third argument, getattr returns it instead of raising AttributeError[5].
  • The name "need not be a Python identifier"; an attribute such as "not an identifier!" cannot be reached with dot notation but works through getattr and friends[5].
  • Private name mangling happens at compile time, so getattr and setattr need the mangled name (_Config__secret), not the one written in the class body[5].

Without a default, a missing name raises:

hasattr only knows about AttributeError

Because hasattr is implemented as "call getattr and see whether it raises AttributeError"[5], it runs any code behind the attribute. A property that raises some other exception makes hasattr raise too, and a property with a bug that raises AttributeError makes the attribute look absent. When you need to look without running anything, inspect.getattr_static retrieves attributes "without triggering dynamic lookup via the descriptor protocol, __getattr__ or __getattribute__"[6].

attrgetter and methodcaller

When the same name is applied to many objects, the operator module builds the function for you. attrgetter('name.first', 'name.last') returns a callable that fetches (b.name.first, b.name.last) from its argument, so it follows dotted paths, and methodcaller('name', 'foo', bar=1) returns a callable that performs b.name('foo', bar=1)[9]. Both are ideal key= functions when the sort field is chosen at runtime.

4Calling by name: dispatch

Since methods are attributes, getattr plus a call is a complete dispatch mechanism. A common convention is a name prefix that marks which methods are commands, so that a user can only reach methods meant for them. The standard library's own cmd module works this way: an interpreter "will recognize a command name foo if and only if it has a method do_foo"[10].

A home-grown dispatcher can go one step further with inspect.signature. Signature.bind(*args, **kwargs) maps arguments to parameters and raises TypeError if they do not match[6], so the dispatcher can reject a bad command line before calling anything, and each parameter's annotation can double as its converter.

Note that inspect.signature on a bound method leaves out self, which is why bind only sees the user's arguments.

Dispatching on type instead of name

When the choice depends on the type of a value rather than a string, functools.singledispatch already does the bookkeeping: it turns a function into a generic function whose implementation is picked by "the type of the first argument"[11]. Section 8 uses it in a serializer.

5Creating classes and objects at runtime

type(name, bases, dict)

Called with three arguments, type "is essentially a dynamic form of the class statement": name becomes __name__, bases becomes __bases__ (with object added if it is empty), and dict supplies the class body[5]. So a class can be assembled from data, for example one class per table in a schema file.

Keyword arguments given to the three-argument form are passed on to the class-creation machinery, usually __init_subclass__, just as keywords in a class header would be[5]. What it does not do is call a metaclass's __prepare__; for that the documentation points to types.new_class, which "creates a class object dynamically using the appropriate metaclass" and fills the namespace through an exec_body callback[5,12]. Metaclasses themselves are covered in their own article.

Look closely at the MRO in that output: the class made by types.new_class reports itself as types.Echo, not __main__.Echo, so its __module__ is wrong for anything that relies on it, such as repr, pickling or documentation tools. Setting ns["__module__"] = __name__ inside exec_body fixes it. The class made by type() picks up __main__ correctly, as the last line shows.

__init_subclass__ was added by PEP 487 so that a base class can customise its subclasses without a metaclass[13]; the data model reference describes it as "called whenever the containing class is subclassed"[4].

make_dataclass

If the class you are building is mostly fields, dataclasses.make_dataclass takes a list of name, (name, type) or (name, type, Field) entries plus the usual dataclass options, and a namespace for extra methods[14].

SimpleNamespace for ad-hoc objects

Sometimes you need an object, not a class. types.SimpleNamespace is "a simple object subclass that provides attribute access to its namespace", and unlike a bare object it lets you add and remove attributes[12]. Used as a JSON object_hook, it turns nested dictionaries into dot-accessible objects.

6Changing objects and classes at runtime

Classes are mutable objects, and instances find methods by looking in their class, so a function assigned to a class becomes a method of every instance at once, including instances that already exist. A function assigned to a single instance is different: functions only turn into bound methods when they are found in a class dictionary[15], so the instance must be bound by hand with types.MethodType[12,15].

Replacing an existing function on a module or class while a program runs is monkey patching, which has its own article in this series.

A class's __dict__ is read-only; setattr is not

Modules and instances have an updateable __dict__, but classes expose theirs through a types.MappingProxyType "to prevent direct dictionary updates"[5]. The supported way to change a class is setattr, which also keeps the interpreter's internal caches consistent.

Special methods must live on the type

Setting __len__ or __repr__ on an instance looks as if it works, because a direct call such as obj.__len__() finds it. But implicit invocations of special methods (by len(), operators, repr() and so on) "are only guaranteed to work correctly if defined on an object's type, not in the object's instance dictionary"[4].

__slots__ closes the door

A class that defines __slots__ gets no per-instance __dict__, and "attempts to assign to an unlisted variable name raises AttributeError"[4]. setattr obeys the same rule, and vars() raises TypeError[5]. Reflective code that assumes every object has a __dict__ breaks on such classes; Exercise 2 shows a version that does not.

7Intercepting attribute access

Intercession can also go the other way: instead of your code poking at an object, the object takes control of what a dot means. Four special methods do it[4]:

  • __getattr__(self, name) is called only "when the default attribute access fails with an AttributeError". That asymmetry is intentional and makes it the safe hook for fallbacks and proxies.
  • __getattribute__(self, name) is called "unconditionally" for every attribute access on instances; to avoid infinite recursion it must fetch anything it needs through object.__getattribute__(self, name).
  • __setattr__(self, name, value) is called for every assignment, instead of storing in the instance dictionary; to really store a value it should call object.__setattr__.
  • __dir__(self) is called by dir(); the result is converted to a list and sorted.

The example below is a recording proxy. It stores its own state with object.__setattr__ so that its __setattr__ does not catch those assignments, forwards everything else to the wrapped object, and reports a sensible dir().

Properties, classmethod and bound methods are all built on descriptors, which decide what a class-level attribute turns into when it is looked up. They are the subject of the descriptors article; for reflection the practical consequence is the one in Section 3: getattr runs descriptor code and inspect.getattr_static does not.

8Practical uses

A generic serializer for dataclasses

A serializer has to answer "which fields does this object have, and what type is each one?" without being told. dataclasses.fields returns the Field objects of a dataclass or instance[14], and getattr reads each value by its name. For loading, the declared types matter, and here typing.get_type_hints earns its place: with from __future__ import annotations every annotation is stored as a string, and get_type_hints evaluates those forward references into real types[8]. singledispatch handles the per-type encoding[11].

Real libraries add validation, aliases and generics on top, but the core loop of "list the fields, read each by name, convert by declared type" is the same. Exercise 6 extends it to list[Address] with typing.get_origin and get_args.

A command-line interface from a function signature

A function's signature already says which arguments are required, which have defaults and what types they expect. Reading it with inspect.signature[6] is enough to build an argparse parser[16], and calling the function with **vars(namespace) closes the loop.

A plugin registry

Plugin systems combine two reflective steps: loading code whose name is only known at runtime, and finding the classes it defines. importlib.import_module imports a module from a string name and returns it[17], and __init_subclass__ lets the base class record every subclass as it is created[4,13]. The "module:attribute" strings below follow the same shape as packaging entry points, which importlib.metadata.entry_points() lists for installed distributions and which load with EntryPoint.load()[18]. Import machinery in depth belongs to the dynamic imports article.

9Security

Reflection turns strings into behaviour, so a string from outside the program is input that can choose behaviour. Three rules cover most of the risk.

Never pass an untrusted name straight to getattr

Attribute chains reach much further than they look. Every Python function carries __globals__, "a reference to the dictionary that holds the function's global variables"[4], and every bound method exposes its function. So a path an attacker chooses can walk from a harmless object to the module's secrets. str.format has the same reach, because a replacement field such as {0.attr} is resolved with getattr[19], which makes user-supplied format strings an attribute-walking tool too.

An explicit allowlist (or a dictionary of handlers) is the fix. Refusing names that start with an underscore is a useful second layer but not a substitute, because a public method can still be something the caller should not run. The prefix convention from Section 4 is a form of allowlist: only cmd_ methods are reachable.

eval and exec are not reflection tools

The documentation for both eval and exec warns: "This function executes arbitrary code. Calling it with untrusted user-supplied input will lead to security vulnerabilities"[5]. Almost everything people reach for eval to do has a reflective alternative: getattr for a name, a dictionary for a choice, importlib.import_module for a module. To read a Python literal from text, ast.literal_eval accepts only literal structures (strings, bytes, numbers, tuples, lists, dicts, sets, booleans, None and Ellipsis) and "is specifically designed not to execute Python code"[20]. It is still "not free from attack": a relatively small input can exhaust memory or the C stack and crash the process, so the same page says calling it on untrusted data "is thus not recommended"[20]. Parse untrusted data with a data format such as JSON instead.

Deserialization that constructs objects by name

Pickle stores objects by recording which class or function to call to rebuild them, which is reflection on load. That is why the pickle documentation states that "the pickle module is not secure" and that malicious data can "execute arbitrary code during unpickling"[21]. A reflective serializer like the one in Section 8 is safer only if it, too, refuses to build types the caller did not list.

Audit hooks are not a sandbox

CPython raises auditing events for some sensitive attribute reads and writes[4], and sys.addaudithook lets a program observe them. The sys documentation is explicit that hooks "are not suitable for implementing a 'sandbox'" and that "malicious code can trivially disable or bypass" Python-level hooks[22]. Use them for logging, not for confinement.

10Performance

Reflection costs something, but less than its reputation suggests for simple attribute access and more than you might expect for the heavier inspect calls. The measurements below use timeit, taking the best of several repeats as the documentation recommends, since higher values are usually caused by other processes rather than the code itself[23]. Absolute numbers depend on the machine; the ratios are what matter.

On the run shown, getattr with a variable name and attrgetter stay within a small factor of plain dot access, all in the tens of nanoseconds, so attribute reflection by itself is rarely a bottleneck. Misses are where the style matters: hasattr and getattr(obj, name, default) stay cheap, while raising and catching AttributeError is more than ten times slower. The EAFP style, which the glossary describes as assuming attributes exist and catching exceptions "if the assumption proves false"[24], is therefore the right default when misses are rare, and a default argument is better when they are common. inspect.signature takes around ten microseconds, so a dispatcher that calls it on every request should compute signatures once and cache them, for example with functools.cache[11].

11Pitfalls

  • hasattr runs code. It hides AttributeError raised by bugs inside properties and lets every other exception through[5]. Prefer getattr(obj, name, sentinel), or inspect.getattr_static when you only want to look[6].
  • Mangled names. getattr(obj, "__secret") does not find an attribute written as self.__secret inside a class; mangling happened at compile time[5].
  • Not every object has a __dict__. Slotted classes and many built-in types have none, and vars() raises TypeError[4,5]. Use dataclasses.fields, __slots__ or dir() as appropriate.
  • dir() is not a contract. It aims to be useful at the prompt rather than "rigorously or consistently defined", and it leaves out metaclass attributes when called on a class[5]. Don't build an allowlist from it.
  • Special methods on instances are ignored by syntax. Put __len__, __eq__ and friends on the class[4].
  • Functions on instances are not methods. Bind them with types.MethodType or assign them to the class[15].
  • Raw annotations can be strings. Under from __future__ import annotations, __annotations__ and Field.type hold text; use typing.get_type_hints, which evaluates them and merges base-class annotations along the MRO[8].
  • Recursion in __getattribute__ and __setattr__. Any self.x inside them calls them again; go through object.__getattribute__ and object.__setattr__[4].
  • Classes built with types.new_class can carry the wrong __module__. Set it explicitly in exec_body (Section 5).
  • Classes built at runtime are harder to read and to type-check. A class made with type() or make_dataclass is invisible to static tools until it exists. Prefer a plain class statement unless the shape really is data-driven.

12Annotations in Python 3.14

The examples above were run on CPython 3.13. Python 3.14 changes how annotations are stored: following PEP 649 and PEP 749, they are evaluated lazily, only when something asks for them[25–27]. A new annotationlib module provides annotationlib.get_annotations, which can return annotations in three formats: VALUE (evaluated, may raise for undefined names), FORWARDREF (unresolvable names come back as ForwardRef objects) and STRING (source-like text)[27]. The annotations HOWTO recommends annotationlib.get_annotations on 3.14 and later as the best way to read an object's annotations, while typing.get_type_hints remains the higher-level tool when you want resolved types[28]. The annotationlib page also cautions that most of its functions can execute arbitrary code, which puts reading annotations in the same category as getattr from the security section[27].

13Exercises

Each solution was run and its output is shown. Try the exercise before opening it.

1. Safe deep get Beginner

Write deep_get(obj, path, default=None) that follows a dotted path such as "owner.address.city" with getattr and returns default as soon as any link is missing. It must not catch exceptions other than a missing attribute.

Show solution

Use a private sentinel object so that an attribute whose value is legitimately None is not mistaken for a missing one.

2. Update from a dictionary Beginner

Write apply_updates(obj, data) that sets each key of data on obj only if the object already has a public attribute of that name, and returns a sorted list of the keys it rejected. It must also work on a class with __slots__.

Show solution

Checking vars(obj) would fail on the slotted class, and a slot that has never been assigned is not yet visible to hasattr, so the solution asks the class through dir(type(obj)), which lists both ordinary class attributes and slot descriptors.

The callable check stops a caller from replacing a method such as delete, which dir() would otherwise allow.

3. A record class factory with type() Intermediate

Without using dataclasses or namedtuple, write record(name, field_names) that returns a new class whose instances take the fields positionally, compare equal when all fields are equal, and print as Name(a=1, b=2). The class should also have __slots__.

Show solution

Defining __eq__ without __hash__ makes the class unhashable, the same choice a mutable dataclass makes.

4. An event router Intermediate

Write a base class Router whose dispatch(event, **payload) calls the subclass method on_<event>, falls back to on_default(event, **payload) when there is none, and refuses event names that are not identifiers or start with an underscore. Add an events() class method that lists the events a subclass handles.

Show solution

5. Call a function with string arguments Intermediate

Write call_with_strings(func, values) where values maps parameter names to strings (as from a web form). Convert each value using the parameter's annotation (bool should accept "true"/"false"), fill in defaults, report all unknown or missing parameters in one TypeError, and call the function.

Show solution

Signature.bind checks the arguments[6]; BoundArguments.apply_defaults fills in the defaults so that every parameter is present for display. Resolving annotations through get_type_hints keeps the solution working even if the module uses string annotations[8].

6. Load nested lists and optional fields Advanced

Extend from_plain from Section 8 so that it handles fields typed list[SomeDataclass] and SomeDataclass | None. Use typing.get_origin and typing.get_args, which return the unsubscripted type (X for X[Y, Z]) and its arguments ((Y, Z))[8].

Show solution

The trick is to make conversion a recursive function of the type rather than of the field. A union such as Address | None has origin types.UnionType[12]; for None the value passes through, otherwise the non-None member is used.

7. A read-only view Advanced

Write ReadOnly(obj), a proxy that forwards attribute reads to obj, wraps any non-callable attribute that is itself an object with a __dict__ in another ReadOnly (so view.a.b = 1 also fails), raises AttributeError on any assignment or deletion, and makes dir(view) show the target's attributes.

Show solution

__getattr__ is enough for reads because the proxy has almost no attributes of its own; __setattr__ and __delattr__ intercept every write[4]. The proxy stores its target with object.__setattr__, the one write it allows itself.
