Who Keeps the Promise Once It Is Bytecode?

Java, Kotlin, Scala, Groovy and Clojure compile to the same class-file format and run on the same virtual machine. What really separates them is not what they let you write but who is still enforcing it after compilation: the JVM, the emitted bytecode, a runtime library, or nobody at all.

1One machine, five sets of promises

Every language in this article ends in the same place: a file that begins with the four bytes CA FE BA BE, followed by a version number, a constant pool and a list of methods written in the instruction set of the Java Virtual Machine 1. The verifier that loads such a file neither knows nor cares which compiler produced it. It checks that the operand stack is used consistently, that each instruction receives values of compatible types, and that the class respects the access rules written into its own flags 1. Everything else a source language promised has to be carried some other way, or not at all.

That observation is the organising question here. A programming language is, among other things, a set of promises about programs: this value is never null, this hierarchy is closed, this list cannot change, this call reaches that method. Java makes some of those promises, and the JVM was designed to keep precisely those. Kotlin, Scala, Groovy and Clojure make others. Some the machine has since learned to keep; many it has not. A feature checklist is therefore the wrong comparison, because the checklists have largely converged. The useful comparison is a question asked promise by promise: once the program is bytecode, who keeps the promise?

The answer comes in six grades, which this article calls the holder ladder. At the bottom rung, H5, the platform itself (the JVM and the java.base module) enforces the promise for every caller, whatever language compiled the caller. At H4 the compiler wrote instructions into the class file that decide the matter. At H3 a runtime library shipped with the language decides it, call by call, for as long as the library is on the class path and callers go through it. At H2 the promise survives as a standard class-file attribute that any tool may read and none is obliged to honour. At H1 it survives only in metadata private to the language’s own compiler. At H0 nothing records it at all. §3 defines the ladder precisely; §§6–9 place 23 promises on it, one plate per promise, for every language that makes the promise: 92 placements in all.

Three kinds of evidence support the placements. The first is history and specification: what each language’s designers wrote and what its documentation says. The second is source code: the same four small programs are written in all five languages, and every listing below is the exact file that was compiled. The third is a laboratory. A script compiled those programs with JDK 25.0.4.1, Kotlin 2.4.20, Scala 3.9.0, Groovy 4.0.26 and Clojure 1.11.1; ran them; required byte-identical output from all five; disassembled every class file; and then attacked each language’s promises from a plain Java caller, by passing null where null was forbidden, mutating lists that were meant to be read-only, and loading a subclass that a sealed type had never permitted. Every number in the prose and the figures is printed by that script, whose full output closes the article.

The headline result, stated here so that the rest can be read against it, is that the platform keeps the promises Java made, and almost nothing else. Of the 21 placements at H5 outside Java, 19 sit on promises that Java itself keeps at H5; the remaining two are string interpolation, which Kotlin and Scala lower onto Java’s own string-concatenation bootstrap. Every promise Java does not make (non-null parameters, tail calls, default and named arguments, extension methods, zero-cost wrappers) is kept, when it is kept at all, by whoever made it: in emitted checks and private metadata for Kotlin, in TASTy for Scala, in the runtime for Groovy and Clojure. The mean rung barely distinguishes the four alternative languages, which run from 3.10 to 3.27. The place where each keeps its promises distinguishes them completely.

2How five languages arrived on one machine

Java and its virtual machine were designed together at Sun Microsystems in the first half of the 1990s and published as a pair: a language specification in 1996 2 and a machine whose instructions, invokevirtual, getfield, checkcast, presupposed Java’s object model. James Gosling later described Java as deliberately conservative, built from ideas that had already proven themselves elsewhere 3. The conservatism extended to the machine. The JVM had classes, single inheritance, interfaces, access flags, final fields and monitors because Java had them, and it had nothing that Java lacked.

The first languages to target the machine anyway treated the class file as an assembly format. Groovy began in 2003 as James Strachan’s effort to bring the dynamism of Python and Ruby to the Java platform while keeping Java’s syntax within reach 4. It was put through the Java Community Process as JSR 241 in 2004 5 and reached 1.0 in January 2007 4. Its wager was that a language could look like Java while deferring almost every decision (which method a call reaches, what a property is, whether a class has a given method at all) to a meta-object protocol running inside a library 6. Groovy is now an Apache Software Foundation project 7. Groovy 4.0, released in 2022, made invokedynamic the default call mechanism and added native records and sealed types 8; 5.0 followed in August 2025 with compatibility for JDK 11 through 25 9,10, and 5.1 is the current stable line 11,12.

Scala came from the other direction. Martin Odersky had co-designed the generics proposal whose erasure strategy still shapes the platform 13, and in 2004 his group at EPFL released a language that unified object-oriented and functional programming within one static type system 14. Scala brought case classes and pattern matching, traits with concrete members, local type inference and first-class functions to the JVM long before Java adopted versions of each 15. Scala 3, a redesign founded on the calculus of dependent object types 16, was released in May 2021 17. Its new long-term-support line, 3.9, was released on 3 September 2026 and succeeds 3.3 LTS as the recommended baseline for library authors 18,19.

Clojure, released by Rich Hickey in 2007, is a Lisp designed from the outset to be hosted: rather than wrap the JVM it embraces it, borrowing its garbage collector, its just-in-time compiler and its libraries, while replacing the Java default of mutable objects with persistent immutable data structures and explicit reference types for managed change 20. Its persistent vectors and maps descend from Bagwell’s hash array mapped tries 21. Clojure is dynamically typed and compiles each top-level form to bytecode as it is loaded, which means the compiler is part of the runtime 22. The current release is 1.12.6, published on 2 September 2026 23; the 1.12 line still emits Java 8 bytecode and is expected to be the last to do so 24.

Kotlin arrived last and was the most deliberately pragmatic. JetBrains unveiled it in July 2011 and released 1.0 on 15 February 2016, when its lead designer summed up the design in one word, pragmatism 25,26. Kotlin’s promises were chosen to be the ones Java programmers most wanted and could adopt a file at a time: null-safe types, data classes, extension functions and default arguments. Google announced first-class support for Kotlin on Android in May 2017 27. Kotlin 2.0, released in May 2024, replaced the compiler front end with K2 28; 2.4.0 stabilised context parameters in June 2026 29,30, and 2.4.20 followed in September 31.

The machine did not stand still while this happened. JSR 292 added the invokedynamic instruction in Java 7 specifically to serve such languages 32: a compiler can leave the linkage of a call site to a bootstrap method that runs once, on first execution 33. Java 8 then used the same instruction for its own lambdas 34, and later releases kept adding bootstraps that any compiler may reuse: string concatenation in Java 9 35, record equality 36 and type switches 37. Since 2018 the JDK has shipped every six months 38; JDK 25 is the current long-term-support release, and JDK 27 reached general availability on 15 September 2026 39. Figure 1 lays the five histories side by side.

The timeline carries a pattern that §11 returns to. Again and again a feature ships first in one of the alternative languages and reaches Java years later. At that point the JVM or java.base begins to keep a promise that some other compiler had until then kept by itself, and each of those compilers must decide whether to hand the promise over.

3The holder ladder

The ladder ranks holders by what has to be present at run time for the promise to hold, from least to most. Figure 2 gives the six rungs; the definitions below are the ones the lab applies.

H5, the platform. The JVM or java.base enforces the promise for every caller in every language. A final field, a PermittedSubclasses check at class loading, a monitor. Nothing but a JDK needs to be present. H4, emitted bytecode. The compiler wrote instructions into the class file that decide the matter: a null check at method entry, a goto that replaces a tail call. Those instructions may call a small helper, as Kotlin’s null checks call Intrinsics, but the decision is fixed in the class file and holds against any caller. H3, the language runtime. A library decides the matter each time the code runs: which method a Groovy call reaches, whether a Clojure vector accepts an element. The promise holds while the library is on the class path and callers route through it; a Java caller that bypasses the library bypasses the promise. H2, an advisory attribute. A standard attribute such as Signature or Exceptions, which javac and reflection read and the JVM ignores. H1, the language’s own compiler. Metadata that only one language understands, principally Kotlin’s @Metadata annotation 40 and Scala’s TASTy files 41. The same compiler honours it when it compiles against the class; the JVM and every other compiler see something weaker. H0, nobody. The promise was checked during compilation and left no trace.

Three coding rules keep the placements honest. First, placements use default compiler settings. A flag that adds a promise, such as Scala’s explicit nulls 42 or Groovy’s static compilation 43, is noted on the plate but not coded, because the question is what an ordinary build keeps. Second, when two records of a promise survive, the more independent one counts: Scala generics are placed at H2 because the Signature attribute carries them, even though TASTy carries more. When a promise needs two mechanisms together, the less independent one counts: Scala case-class equality is emitted inline, but its hash code is computed by scala.runtime.Statics, so it sits at H3. Third, a dash is not a zero. A dash means the language makes no such promise (Java has no default arguments). H0 means the language makes the promise and nothing after compilation keeps it.

Why rank holders this way rather than by how strict the promise is? Because the ladder predicts what happens at language boundaries, which is where JVM languages actually meet. A promise at H5 survives a mixed build with no cooperation from anyone. A promise at H4 survives any caller but only at the points where a compiler chose to emit a check. At H3 and below, the promise holds among code written in the promising language and weakens, sometimes to nothing, the moment Java, or another JVM language, becomes the caller.

4Four programs in five languages

The shared programs are small on purpose, so that every difference in the class files traces back to a language’s choices rather than to a program’s. P1 counts word frequencies in a fixed sentence and prints the top five, ordered by count and then alphabetically. P2 declares a closed hierarchy of three shapes and computes areas with an exhaustive match. P3 puts six points into a set and relies on value equality to find the four distinct ones. P4 sums the integers from one to a million by self-recursion. Java has no tail-call elimination, so its P4 is a loop; the other four each use their own mechanism: tailrec, @tailrec, @TailRecursive and recur. Gate.java
import java.util.*;
import java.util.stream.*;

public class Gate {
    static final String TEXT = "the class file is the contract the verifier reads the class file "
        + "and the verifier trusts nothing the compiler said unless the class file says it too "
        + "a promise the class file does not carry is a promise someone else must keep";

    sealed interface Shape permits Circle, Rect, Tri {}
    record Circle(double r) implements Shape {}
    record Rect(double w, double h) implements Shape {}
    record Tri(double b, double h) implements Shape {}

    static double area(Shape s) {
        return switch (s) {
            case Circle c -> Math.PI * c.r() * c.r();
            case Rect r -> r.w() * r.h();
            case Tri t -> 0.5 * t.b() * t.h();
        };
    }

    static String kind(Shape s) {
        return switch (s) {
            case Circle c -> "circle";
            case Rect r -> "rect";
            case Tri t -> "tri";
        };
    }

    record Point(int x, int y) {}

    public static void main(String[] args) {
        // P1 word frequency
        Map<String, Long> freq = Arrays.stream(TEXT.split(" "))
            .collect(Collectors.groupingBy(w -> w, Collectors.counting()));
        freq.entrySet().stream()
            .sorted(Map.Entry.<String, Long>comparingByValue().reversed()
                    .thenComparing(Map.Entry.comparingByKey()))
            .limit(5)
            .forEach(e -> System.out.println("P1 " + e.getKey() + " " + e.getValue()));

        // P2 a closed hierarchy, matched exhaustively
        List<Shape> shapes = List.of(new Circle(1.0), new Rect(2.0, 3.0), new Tri(4.0, 5.0),
                                     new Circle(0.5), new Rect(1.5, 1.5), new Tri(3.0, 2.0));
        double total = 0.0;
        for (Shape s : shapes) {
            double a = area(s);
            total += a;
            System.out.println("P2 " + kind(s) + " " + String.format("%.4f", a));
        }
        System.out.println("P2 total " + String.format("%.4f", total));

        // P3 value equality
        List<Point> pts = List.of(new Point(3, 1), new Point(1, 2), new Point(3, 1),
                                  new Point(0, 0), new Point(1, 2), new Point(2, 9));
        Set<Point> distinct = new HashSet<>(pts);
        System.out.println("P3 distinct " + distinct.size());
        distinct.stream()
            .sorted(Comparator.comparingInt(Point::x).thenComparingInt(Point::y))
            .forEach(p -> System.out.println("P3 (" + p.x() + "," + p.y() + ")"));
        System.out.println("P3 equal " + new Point(1, 2).equals(new Point(1, 2)));

        // P4 sum 1..1_000_000 (no tail-call elimination on the JVM: a loop)
        long acc = 0;
        for (long n = 1_000_000; n > 0; n--) acc += n;
        System.out.println("P4 " + acc);
    }
}

5What the compilers leave behind

Before any promise is tested, the class files themselves say a good deal. The same four programs produced 6 class files from javac, 11 from Kotlin, 12 from Scala (plus 7 TASTy files), 13 from Groovy and 39 from Clojure. In bytes the range is more than tenfold, from 11,313 for Java to 120,723 for Clojure (Figure 3). The class-file versions also differ. javac and Kotlin, told to target JDK 25, wrote version 69. Scala 3.9 wrote 61 (Java 17) by default. Groovy was told to target 17. Clojure 1.11 wrote 52, Java 8, as the 1.12 line still does 24.

More revealing than size is where the emitted code sends its calls. Figure 4 classifies every invoke instruction by the owner of its target. Java’s program calls the platform, itself and invokedynamic sites, and never a language runtime, because it has none. Kotlin sends 18.8% of its calls into kotlin-stdlib, most of them collection helpers and the 6 parameter checks discussed under plate A3. Groovy sends 39.5% to its runtime and routes most of the rest through 99 invokedynamic sites. Scala’s 51.6% reflects the shared program’s heavy use of Scala collections rather than any dynamic dispatch. Clojure sends 84% of 1,084 calls into clojure.lang, and its class files contain 601 checkcast instructions against Java’s 9: the signature of a dynamically typed language talking to a statically typed machine.

The bootstrap methods behind those invokedynamic sites are the clearest evidence of the platform absorbing other languages’ work (Figure 5). Java’s program uses four JDK bootstraps: 5 lambda sites, 12 record-method sites, 7 string-concatenation sites and 2 type switches. Kotlin, targeting JDK 25, compiled its when over a sealed interface into the JDK’s own SwitchBootstraps 37, and its string templates into StringConcatFactory 35. Groovy’s records use the JDK’s ObjectMethods bootstrap exactly as Java’s do 36, while its 87 dynamic call sites are linked by Groovy’s own IndyInterface. Clojure emits no invokedynamic at all. Its calls go through IFn interfaces and the vars that hold functions 50.

Finally, the metadata. All 11 of Kotlin’s class files carry a kotlin.Metadata annotation, which records nullability, properties, default values and the difference between read-only and mutable collection types, none of which the JVM’s own descriptors can express 40. 7 of Scala’s classes carry a TASTY attribute pointing to a .tasty file that holds the fully typed syntax tree 41. These two mechanisms are where H1 lives, and they are why a Kotlin library and a Scala library each look richer to their own compiler than to javac.

6Calls and types

The first family of promises concerns what a call means and what a type guarantees. It is also where the dynamic and static languages part company most visibly, because the question of which method a call reaches is settled in the constant pool for three of the five languages and in a library for the other two.

The dispatch probe makes the difference concrete. Over.f has an Object overload and a String overload, and each language’s pick passes it a String whose static type is Object. Java, Kotlin and Scala chose the overload at compile time from the static type, wrote f(Ljava/lang/Object;) into the call instruction, and returned f(Object). Groovy returned f(String), because its runtime selects among overloads by the arguments’ run-time types, a behaviour its documentation calls multi-methods 51. Clojure returned f(Object), but for a Clojure reason. Its compiler resolves a Java call statically when it can, and with no type hint on the argument it resolved this one to the Object overload. The same probe file’s len, which calls .length on an unhinted argument, compiled instead to a reflective call through clojure.lang.Reflector, the case Clojure’s reflection warnings exist to flag 52.

The null probe asks where a forbidden null is caught (Figure 6). Only Kotlin makes the promise, and it keeps it with emitted code: calling len(null) from Java failed before the body ran, with the message Parameter specified as non-null is null: method ProbeKt.len, parameter s. Kotlin’s documentation says it generates such checks for public functions precisely because nothing stops a Java caller from passing null 53. Java and Scala failed at the dereference, with the JDK’s helpful message naming the variable 54. Groovy and Clojure failed inside their runtimes, in NullObject.invokeMethod and Reflector respectively.

Three further probes complete the family. bump(Long.MAX_VALUE) returned −9223372036854775808 in Java, Kotlin, Scala and Groovy, which is the two’s-complement wrap the JVM specifies for ladd 1. Groovy, though, reached that answer through an invokedynamic call into its own arithmetic, so its runtime decided and happened to agree. Clojure threw ArithmeticException: long overflow, raised by Math.addExact inside clojure.lang.Numbers; Clojure’s arithmetic checks overflow by design and offers promoting operators for when you want big integers instead 55. A boom function that threw java.io.IOException without declaring it reached the Java harness from Kotlin, Scala, Groovy and Clojure alike. Checked exceptions are a compile-time analysis in the Java language, not a JVM rule 56. Finally, each language’s narrowest visibility was tested with reflection that did not call setAccessible. Java’s private produced IllegalAccessException. Kotlin’s internal and Scala’s private[vis] compiled to public methods and were simply called 53. Groovy’s private was ACC_PRIVATE, and the JVM stopped the Java caller, yet a second Groovy class called it without complaint and printed secret. Clojure’s defn- var was reachable from Java through the var API, while Clojure’s own compiler refused the reference: var: #'lab.probe/secret is not public 50.

7Data

The data family is where Java has caught up fastest (records in 2021, sealed types the same year, pattern switches in 2023) and therefore where the question of handing promises over to the platform is most live.

Sealing is the cleanest test (Figure 7). The harness compiled a class Evil that implements each language’s Shape interface against a stub, then loaded it beside the real classes. For Java, Kotlin and Groovy the JVM refused at class-load time with Failed listed permitted subclass check, because all three compilers had written a PermittedSubclasses attribute listing exactly 3 classes 44,8,47. Scala 3.9 wrote no such attribute; Class.isSealed() returned false and the foreign subclass loaded. Scala’s sealing is fully enforced by the Scala compiler, which reads it from TASTy 41, and by nothing else. The same feature, on the same JVM, sits at H5 for three languages and H1 for the fourth. That is a compiler’s choice, not a platform constraint.

Read-only lists tell a subtler story (Figure 8). Java’s List.of returned java.util.ImmutableCollections$ListN, which rejected both set and add 58. Kotlin’s listOf returned java.util.Arrays$ArrayList, a fixed-size view over an array, so add failed but set(0, "z") succeeded and changed the list. Kotlin’s read-only List is a compile-time view onto java.util.List, and its read-only-ness exists only in Kotlin’s type checker and metadata 59,60. Scala’s list is not a java.util.List at all, so there was nothing to mutate. Clojure’s persistent vector implements java.util.List and rejected both mutators 55. Groovy’s list literal is a plain ArrayList by design 61 and makes no read-only promise.

The remaining data promises are quieter. Every language made the declared fields of its data type final: two of two in Java, Kotlin, Scala and Groovy, and the two declared fields among 6 in Clojure’s record, whose extra fields include two mutable hash caches. Structural equality was lowered five ways. Java and Groovy records call the JDK’s ObjectMethods bootstrap; Kotlin writes equals and hashCode inline; Scala writes equals inline but computes the hash in scala.runtime.Statics; Clojure delegates to APersistentMap. An unmatched case throws MatchException in Java, NoWhenBranchMatchedException in Kotlin and scala.MatchError in Scala, each thrown by a default branch the compiler emitted. Finally, a Kotlin value class and a Scala opaque type both vanished into a double. Kotlin’s twice(Meters) became twice-ZF1rqJE(double), name-mangled so that overloads cannot collide 62, while Scala’s became twice(double) 63. Java has no such promise yet. JEP 401 value classes are integrated as a preview for JDK 28 64,65.

8Functions

The function family holds most of the promises Java does not make, which is why it is where the alternative languages keep the most promises by themselves.

Lambdas show the platform absorbing, then being adopted. A capturing x -> x + k compiled to an invokedynamic site linked by LambdaMetafactory in Java, Kotlin and Scala, so no class was generated at compile time. Scala has done this since 2.12 66, and Kotlin by default since 2.0 28. Groovy compiled the closure to its own class, ProbeG$_adder_closure1, a subclass of groovy.lang.Closure 67. Clojure generated 2 classes, one for adder and one for the function it returns, each extending the runtime’s function base class 20.

Tail calls show the opposite: a promise the platform has never taken up. Every compiler that offers self-tail-recursion rewrote the call into a jump, and the lab found zero remaining self-calls in the compiled sumTo of Kotlin, Scala, Groovy and Clojure 68,69,70,71. Java makes no such promise. A plain recursive sum to a million threw StackOverflowError; with a 1 MB stack in the interpreter the deepest successful call was 7,869 frames. That depth is a property of that configuration, not of Java.

Default and named arguments divide cleanly by rung. Defaults are emitted code. Kotlin generated sumTo$default(long, long, int, java.lang.Object), whose int is a bitmask of the omitted arguments; Scala generated a getter sumTo$default$2(); Groovy generated an extra overload taking one argument 72. Named arguments are compile-time bookkeeping in Kotlin and Scala. Kotlin’s documentation notes that they cannot be used when calling Java functions, because Java bytecode does not always preserve parameter names 68. In Groovy and Clojure they are run-time maps 72,73. Extension methods follow the same split. Kotlin and Scala resolve them statically to ordinary static methods and record the receiver in metadata 74,75; Groovy’s extension modules and Clojure’s protocols attach behaviour to existing classes at run time 6,48.

String interpolation is the instructive exception. Kotlin and Scala lowered "hello $name #$n" to Java’s own StringConcatFactory bootstrap 35, which lands them at H5 on a promise Java itself does not make. Groovy built a GStringImpl, a lazily rendered object that is not a java.lang.String and does not share its hash code 61. Clojure called clojure.core/str. Java previewed string templates in JDK 21 and 22 and then withdrew them before JDK 23, because the design was judged unsuitable in its current form 76,77.

9Runtime and metaprogramming

The last family asks what a running program can change and what it can learn about itself. Here the two dynamic languages are not a weaker version of the static ones. For them, keeping promises at H3 is the design: a Groovy or Clojure program can change what a call does while it runs, because the runtime, not the constant pool, decides.

Lightweight concurrency arrived in four different places. Java’s virtual threads live in the JDK 78. Kotlin compiles a suspend function into a state machine that takes an extra Continuation parameter, so suspension is emitted code and scheduling is a library matter 79. Scala’s standard concurrency abstraction is the library’s Future 80. Clojure provides futures, agents and software-transactional refs in its core runtime 81. Groovy makes no language-level concurrency promise of its own. Mutual exclusion, by contrast, converged completely. All five compile a lock to the JVM’s monitors; Clojure’s locking expands to the monitor-enter and monitor-exit special forms 71.

Metaprogramming splits by time. Java annotation processors 82, Kotlin compiler plugins and symbol processors 83, and Groovy AST transformations 6 all run during compilation and leave only their output behind. Scala 3 keeps the bodies of inline methods and macros in TASTy, so that later compilations can expand them 84,41. Clojure macros are ordinary functions stored in vars, and the compiler that expands them ships inside clojure.jar 85. Run-time redefinition splits the same way. The JVM permits a running class to be redefined only within narrow limits, changing method bodies but not adding or removing methods or fields 86, so a Java, Kotlin or Scala call means what it meant at compile time. Groovy’s ExpandoMetaClass can add or replace methods on a live class 6, and redefining a Clojure var changes every call that goes through it 50.

Reflection, finally, shows the price of H1. java.lang.reflect sees everything Java declares. It cannot see Kotlin’s nullability, Scala’s opaque types or either language’s default arguments. Kotlin’s reflection library recovers them by decoding @Metadata 40, and Scala’s TASTy inspector by reading TASTy 41. Groovy and Clojure need neither, because their structure is runtime data to begin with.

10What keeping your own promises costs

A promise kept at H3 needs a runtime, and runtimes have weight. Beside the JDK, the shared program needed 1.85 MB of kotlin-stdlib (995 classes), 9.82 MB of Scala library (3,662 classes), 7.62 MB of Groovy core (4,570 classes) and 4.75 MB of Clojure with its two spec libraries (4,087 classes). The loaded-class log is more telling than the jar sizes (Figure 9). Running the same four programs, Kotlin loaded 52 classes from its runtime, 5.23% of it; Scala loaded 339; Groovy 451; and Clojure 1,493, 36.53% of its runtime, because loading clojure.core initialises the compiler and the whole standard namespace before the first line of the program runs 22.

Start-up time follows the loaded-class counts (Figure 10). The medians of nine runs were 167 ms for Java, 144 ms for Kotlin, 338 ms for Scala, 982 ms for Clojure and 1,728 ms for Groovy. These are whole-process wall-clock times on one container, and they are the only non-deterministic numbers in the lab. The gap between Kotlin and Java is within run-to-run noise. One candidate explanation, which the lab did not isolate, is that Java’s program links 26 invokedynamic sites at start-up against Kotlin’s 13. The order-of-magnitude gap for Groovy and Clojure is not noise: it is the price of initialising a runtime that is going to decide things later.

11The platform absorbs, and the compilers choose

The history in §2 has a regular shape, and the lab turns it into numbers (Figure 11). The lab tracks 10 features that shipped first in one of the four alternative languages. 7 of them later reached Java: closures (Groovy 1.0 in 2007, Java 8 in 2014 4,34), concrete trait members, which became default methods 14,34, local type inference 87, multi-line strings 88, data carriers with generated equality 45, pattern matching in switch 46, and lightweight concurrency (Kotlin coroutines, stable in 1.3 in 2018 89; virtual threads in Java 21 78). The lag from first appearance to absorption had a median of 13 years and ranged from 5 to 19. Three have not been absorbed: persistent collections, null-safe types, and string interpolation, which Java previewed and withdrew 76.

Absorption does not by itself move a promise to H5. It offers a platform mechanism, and each compiler decides whether to use it. The lab caught several such decisions. Kotlin and Groovy emit PermittedSubclasses, and Scala 3.9 does not (plate B4). Groovy records use Java’s ObjectMethods bootstrap, while Kotlin data classes and Scala case classes still generate their own equality (B2). Kotlin moved lambdas onto LambdaMetafactory in 2.0 and Scala in 2.12 (C1), and Kotlin compiles when over sealed types to SwitchBootstraps when it targets a new enough JDK. Each adoption trades independence for compatibility. A class that relies on a JDK 21 bootstrap cannot run on JDK 17. Clojure has kept a Java 8 bytecode baseline through the whole 1.12 line 24, and Scala 3.9 still emits Java 17 class files by default, so each of them has chosen reach over adoption for now.

The next offer is already visible. JEP 401 value classes were integrated as a preview for JDK 28, due in March 2027, disabled by default 64,65. If they become final, Kotlin value classes and Scala opaque types, today at H1 (plate B6), will have a platform rung to move to, and the choice will once more be the compilers’.

Five findings follow from the ledger. Each is computed by the lab.

1. The platform keeps Java’s promises. Of the 21 non-Java placements at H5, 19 are on promises Java itself keeps at H5. Among promises Java keeps at H5, the other languages reach H5 42.2% of the time (19 of 45). Among promises Java does not make, they reach it 9.1% of the time (2 of 22), and both of those are string interpolation riding Java’s concatenation bootstrap (Figure 12). The JVM is not a neutral substrate that happens to favour Java. It is Java’s promise-keeper, extended over the years to lend its mechanisms to anyone who asks.

2. Averages hide the languages; distributions reveal them. The four alternatives have mean rungs between 3.10 and 3.27, but they keep their promises in different places (Figure 13). Kotlin keeps 27.3% at H4 and 31.8% at H1 or H0, with none at H3: a compiler that writes checks and metadata rather than relying on a runtime. Scala keeps 33.3% at H1, the largest share of any language, in TASTy. Groovy keeps 47.1% at H3 and Clojure 75%. Java keeps 75% at H5.

3. Where the JVM has a word, everyone converges. Four plates show a single rung across every language that makes the promise: A2 (generic type arguments), B1 (immutable fields), C2 (tail calls), D2 (mutual exclusion). Two are things the JVM has had from the start, final fields and monitors. One is erasure, which every typed language inherited when the platform adopted the GJ design for generics 13. The fourth, tail calls, is the one technique every language that offers it implements the same way, and the platform has never taken it over.

4. The widest disagreement is over visibility. Plate A6 spans 5 rungs, from Java’s JVM-enforced private to Groovy’s private that Groovy callers ignore. The mean spread across plates is 1.81 rungs. The same English word, private, names five different guarantees.

5. Rungs are chosen, not imposed. Sealing sits at H5 for Java, Kotlin and Groovy and at H1 for Scala on the same JVM (plate B4); equality is lowered four ways (B2). Where a platform mechanism exists, a language’s rung reflects its compiler’s priorities: compatibility with older JDKs, independence from the platform, or fidelity to its own type system.

13Choosing among them

The ledger does not rank the languages. It says what each one costs at a boundary, which is where most real JVM systems live.

Java is the language whose promises survive every boundary, because the platform keeps them. It makes fewer promises than the others: no null safety, no default or named arguments, no tail calls. Where it does make them, nothing downstream can quietly break them. Kotlin is the strongest choice when Java callers are in the picture, because its most important promise, non-null parameters, is kept by emitted checks that hold against them. Its read-only collections, internal visibility and value classes are Kotlin-only guarantees, and an API meant for Java callers should not rely on them. Scala offers the richest static promises and keeps a larger share of them than any other language in its own metadata. That is excellent within Scala and weakest at a Java boundary, where sealing, opaque types and qualified privacy all disappear. Its new 3.9 LTS line is a publishing decision for library authors, since artifacts built with 3.9 cannot be consumed by 3.3 projects 18.

Groovy and Clojure keep their promises at run time on purpose. That buys what the static languages cannot offer: programs that change their own behaviour while running, dispatch on run-time types, and in Clojure’s case immutable data that stays immutable even when Java holds it. It costs start-up time and a runtime that must travel with the program, and it means a promise is kept only while calls go through the runtime. Groovy offers static compilation for code that wants the other trade 43; Clojure offers type hints and reflection warnings 52.

The practical rule is the ladder’s own. For any promise your design depends on, find its rung in the language you are using, then ask who will call the code. If the caller is written in the same language, anything from H1 up will do. If the caller might be Java, or another JVM language, only H4 and H5 are promises; everything else is a convention.

14Method and limitations

Toolchains. JDK 25.0.4.1 compiled and ran Java. Kotlin 2.4.20 and Scala 3.9.0 came from their GitHub releases; Kotlin was given -jvm-target 25, and Scala used its default target. Maven Central was unreachable from the build container. Groovy 4.0.26 therefore came from the jars bundled in an npm package, and Clojure 1.11.1 from the Ubuntu archive. Both are older than the current releases (Groovy 5.1 and Clojure 1.12.6 11,23). Groovy 4.0.26 cannot read JDK 25 class files, so it compiled on JDK 21 with a Java 17 target and ran on JDK 25; Groovy 5 supports JDK 25 10. Clojure 1.11 and 1.12 both emit Java 8 bytecode 24, but 1.12 changed Java interop, for example by adding qualified method values, and could resolve some probes differently.

What was measured. Class-file facts come from javap -v -p -c on every emitted class. Promise tests ran from a Java harness that loaded each language’s classes through its own class loader, so the Java compiler never saw them. Loaded-class counts come from -Xlog:class+load. All outputs except start-up time were byte-identical across runs with different Python hash seeds, and the build refuses to proceed unless the five gate outputs match.

What was judged. The 23 promises were chosen to cover each language’s headline features, not sampled, and the placements are judgements applying the three rules in §3 to that evidence. Where the lab tested a promise directly (A1, A3 to A6, B1 to B6, C1 to C3, C6), the plate cites the experiment. The remaining placements rest on the cited documentation. Different default flags, particularly Scala’s explicit nulls and Groovy’s static compilation, would move several placements. A promise can also be kept at a rung without being kept well: Kotlin’s checks cover public entry points, not every path a null can travel.
