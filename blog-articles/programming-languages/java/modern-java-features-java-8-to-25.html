1. Orientation: “modern Java” is several different evolutions

Java 8 was not the end of Java's modernization; it was the beginning of a sustained redesign of APIs, language constructs, runtime packaging, data modeling, and concurrency.

JDK 25 became generally available on 16 September 2025 and is the reference implementation of Java SE 25. The OpenJDK release page identifies it as a long-term-support release from most vendors. Java 25 made Scoped Values permanent, while Structured Concurrency was still in its fifth preview and primitive types in patterns were in their third preview. [1][2]

The features in this article are not all the same kind. Lambdas, records, sealed classes, and switch expressions are language features. Streams, Optional, virtual threads, Scoped Values, and Structured Concurrency are library or runtime-facing APIs. The module system changes both compilation and run-time configuration. Preview features are fully specified and implemented for evaluation but are impermanent: they can change or disappear in a later release. [3][4]

Version discipline: examples marked “Java 25 preview” require --enable-preview --release 25 at compilation and --enable-preview when run. Code using withdrawn String Templates does not compile on JDK 25 at all.

Four design movements

Behavior as data

Lambdas, method references, default methods, and streams made functional-style library design practical without replacing Java's object model.

Data-oriented programming

Records, sealed hierarchies, record patterns, and pattern switches let code state the shape of data and exhaustively describe alternatives.

Explicit architecture

The module system added named dependencies, exported packages, service declarations, and strong encapsulation to deployment units.

Direct-style scalable concurrency

Virtual threads, Scoped Values, and Structured Concurrency seek scalable request handling without forcing application logic into callback graphs.

3. Lambda expressions

Java 8 · Permanent A concise syntax for instances of functional interfaces, integrated with target typing and method references.

Project Lambda delivered lambda expressions and “virtual extension methods,” the design that became default interface methods, for Java 8. A lambda is compatible with a target functional interface—an interface whose function type is determined by a single abstract method. Standard interfaces such as Function, Predicate, Consumer, and Supplier form the vocabulary used by streams and many later APIs. [5][6]

Java 8+Functions are objects with declared contracts 
import java.math.BigDecimal;
import java.util.List;
import java.util.function.Function;
import java.util.function.Predicate;

record Invoice(String id, BigDecimal total, boolean paid) {}

public final class LambdaExample {
    private static final Predicate<Invoice> UNPAID =
            invoice -> !invoice.paid();

    private static final Function<Invoice, String> TO_ID =
            Invoice::id;

    public static List<String> unpaidInvoiceIds(List<Invoice> invoices) {
        return invoices.stream()
                .filter(UNPAID)
                .map(TO_ID)
                .toList(); // toList() itself was added after Java 8.
    }
}

Lexical scope and capture

Lambda bodies use lexical scoping rather than introducing the anonymous-class meaning of this. Local variables captured by a lambda must be final or effectively final. Capturing a mutable object is legal, but it does not make mutation thread-safe. [5]

Java 8+Captured local is effectively final 
int minimumLength = 8;

var longEnough = (java.util.function.Predicate<String>)
        text -> text.length() >= minimumLength;

// minimumLength++; // Compilation error: captured local is no longer effectively final.

Overload and readability hazards

Because lambdas are target-typed, overloaded methods accepting unrelated functional interfaces can become ambiguous. Public APIs should avoid overload sets that differ only by function type when a lambda could match more than one target. Method references are useful when the method name communicates intent; a lambda is often clearer when adaptation, validation, or argument reordering is involved.

4. Streams

Java 8 · Library API Lazy pipelines over data sources, with intermediate operations and terminal reductions.

A stream is a sequence of elements supporting aggregate operations. Stream pipelines consist of a source, zero or more intermediate operations such as filter and map, and a terminal operation such as collect, reduce, or forEach. Streams are consumable and generally cannot be reused after a terminal operation. Behavioral parameters are expected to be non-interfering and, in most cases, stateless. [7]

Java 16+Declarative aggregation 
import java.math.BigDecimal;
import java.util.List;
import java.util.Map;
import java.util.stream.Collectors;

record Sale(String region, BigDecimal amount, boolean completed) {}

static Map<String, BigDecimal> revenueByRegion(List<Sale> sales) {
    return sales.stream()
            .filter(Sale::completed)
            .collect(Collectors.groupingBy(
                    Sale::region,
                    Collectors.reducing(
                            BigDecimal.ZERO,
                            Sale::amount,
                            BigDecimal::add)));
}

Laziness and short-circuiting

Intermediate operations are lazy: they construct a pipeline rather than traversing the source immediately. Short-circuiting terminal operations such as findFirst, anyMatch, and limit can avoid processing all elements when the pipeline permits it. [7]

Java 8+Short-circuiting search 
Optional<User> administrator = users.stream()
        .filter(User::active)
        .filter(user -> user.roles().contains("ADMIN"))
        .findFirst();

Parallel streams are not a free speed switch

Streams may be sequential or parallel, but correctness still requires associative reduction and non-interfering operations. Performance depends on data size, splittability, per-element cost, memory locality, and contention. Blocking I/O inside a parallel stream is usually a poor match because stream parallelism is data parallelism, whereas virtual threads target large numbers of mostly waiting tasks. [7][23]

Avoid side-effect accumulation: items.parallelStream().forEach(results::add) is unsafe when results is an ordinary ArrayList. Prefer a collector whose combination semantics are defined.

5. Optional

Java 8 · Library API An explicit return value for a computation that may have no result.

The Java API describes Optional as primarily intended for method return types where absence must be represented and null is likely to cause errors. It is a value-based class, so code should not depend on object identity. Its operations include conditional mapping, filtering, fallback, exception production, and stream conversion. [8]

Java 9+Compose absence rather than inspect it repeatedly 
Optional<URI> avatarUri(UserRepository users, String userId) {
    return users.findById(userId)
            .filter(User::active)
            .map(User::profile)
            .map(Profile::avatarPath)
            .map(path -> URI.create("https://cdn.example.com/" + path));
}

String displayName(User user) {
    return Optional.ofNullable(user.nickname())
            .filter(name -> !name.isBlank())
            .orElseGet(user::legalName);
}

orElse versus orElseGet

The argument to orElse is evaluated before the method call; the supplier passed to orElseGet is invoked only when the optional is empty. Use the supplier form when the fallback is expensive or has side effects. [8] 

// fetchFromRemoteService() is called even when cached is present:
Value a = cached.orElse(fetchFromRemoteService());

// Called only when empty:
Value b = cached.orElseGet(this::fetchFromRemoteService);

Boundaries and anti-patterns

  • Do not call get() without first proving presence; prefer orElseThrow, mapping, or pattern-specific logic.
  • Do not use Optional merely to hide a mandatory invariant; reject invalid state at construction.
  • Avoid Optional<List<T>> when an empty list already expresses “no elements,” unless absence and emptiness are genuinely different domain states.
  • Be cautious with Optional fields, parameters, and serialization models; the API's primary documented intent is return values.

6. Default interface methods

Java 8 · Permanent Interface methods with implementations, originally introduced to evolve core collection APIs for lambdas.

Default methods let an interface add an implementation without requiring every existing implementation class to provide one. This mechanism supported library evolution for operations such as collection traversal and stream creation while maintaining source compatibility for many existing implementors. [5]

Java 8+Behavioral extension point 
interface Identified {
    String id();

    default String diagnosticLabel() {
        return getClass().getSimpleName() + "[" + id() + "]";
    }
}

record Job(String id) implements Identified {}

System.out.println(new Job("j-42").diagnosticLabel());
// Job[j-42]

Conflict rules remain explicit

interface JsonNamed {
    default String name() { return "json"; }
}

interface XmlNamed {
    default String name() { return "xml"; }
}

final class Codec implements JsonNamed, XmlNamed {
    @Override
    public String name() {
        return JsonNamed.super.name() + "+" + XmlNamed.super.name();
    }
}

When unrelated interfaces provide the same default signature, the implementing class must resolve the conflict. A concrete class method takes precedence over an interface default. Default methods should preserve the semantic contract of the interface; they are not a substitute for stateful mixins or multiple implementation inheritance.

7. The Java Platform Module System

Java 9 · Permanent Named modules, explicit dependencies, exported packages, service use/provision, and strong encapsulation.

JEP 261 implemented the Java Platform Module System specified by JSR 376. A module descriptor declares the module name, required modules, exported packages, opened packages, and service relationships. Packages not exported by a named module are not generally accessible to other modules, even when their public classes exist on the module path. [9]

Java 9+module-info.java 
module com.example.billing {
    requires java.sql;
    requires java.net.http;

    exports com.example.billing.api;

    uses com.example.billing.spi.TaxProvider;
    provides com.example.billing.spi.TaxProvider
        with com.example.billing.internal.DefaultTaxProvider;
}

API visibility versus reflection

exports grants normal compile-time and run-time access to public types in a package. opens grants reflective access, commonly needed by serialization, dependency-injection, persistence, or testing frameworks. A qualified export or open targets specific modules. These declarations should be as narrow as the framework contract permits. [9] 

module com.example.customer {
    exports com.example.customer.api;

    // Reflective access only for a named persistence implementation:
    opens com.example.customer.persistence to org.hibernate.orm.core;
}

Compilation and execution

# Compile two modules from a conventional module source tree:
javac -d out --module-source-path src \
      -m com.example.billing,com.example.app

# Run the main class from a named module:
java --module-path out \
     -m com.example.app/com.example.app.Main

Modules are not merely dependency metadata

Build tools resolve artifacts; the module system resolves named modules and enforces readability and package boundaries in the Java compiler and runtime. They solve related but distinct problems. Modularization can expose split packages, illegal reflective access, reliance on JDK internals, and cyclic architecture that class-path builds previously tolerated.

Adoption tactic: begin by removing internal-JDK dependencies and split packages, then modularize cohesive libraries. Automatic modules can support transitions, but stable public module names should be treated as compatibility commitments.

8. Local-variable type inference with var

Java 10 · Permanent Compiler inference for local variables with initializers; Java remains statically typed.

JEP 286 introduced local-variable type inference. The compiler derives the static type from the initializer, after which the variable behaves as if that type had been written explicitly. var is restricted to local variables with initializers, enhanced-for variables, and traditional-for loop locals; it is not a general placeholder for fields, method parameters, or return types. [10][11]

Java 10+Static type is inferred, not dynamic 
var names = new java.util.ArrayList<String>();
names.add("Ada");

// names.add(42); // Compilation error: names is ArrayList<String>.

var entry = Map.entry("retries", 3);
// entry has the inferred type Map.Entry<String, Integer>.

Use names to carry the information the type no longer shows

// Clear: initializer and name reveal the abstraction.
var activeCustomers = customerRepository.findActive();

// Less clear: concrete type and purpose are both hidden.
var x = service.execute(request);

OpenJDK's style guidance recommends using var to improve readability, not merely to reduce character count. Good cases include obvious constructors, verbose generic types, loop variables, and APIs where the variable's role is more important than its implementation class. Explicit types remain useful when they expose an important abstraction or prevent an initializer from dominating the line. [11]

Lambda parameters and annotations

Java 11 allowed var in implicitly typed lambda parameters, chiefly so annotations and modifiers can be applied uniformly. All parameters in one lambda must use a consistent form. [12] 

BiFunction<String, String, String> join =
        (@Deprecated var left, var right) -> left + ":" + right;

9. Switch expressions

Java 14 · Permanent switch can produce a value; arrow rules avoid accidental fall-through.

Switch expressions were previewed in Java 12 and 13 and finalized by JEP 361 in Java 14. Both switch statements and expressions can use arrow labels. A switch expression must be exhaustive, and a block arm produces a value with yield. [13]

Java 14+Expression-oriented branching 
enum Tier { FREE, STANDARD, ENTERPRISE }

static int concurrentJobs(Tier tier) {
    return switch (tier) {
        case FREE -> 1;
        case STANDARD -> 5;
        case ENTERPRISE -> 50;
    };
}
Java 14+Block arm with yield 
static Duration timeout(Environment environment) {
    return switch (environment) {
        case DEVELOPMENT -> Duration.ofSeconds(30);
        case TEST -> Duration.ofSeconds(5);
        case PRODUCTION -> {
            audit("Production timeout selected");
            yield Duration.ofSeconds(2);
        }
    };
}

Arrow rules do not fall through. Traditional colon labels remain available when legacy fall-through semantics are intentionally required. Prefer exhaustive enum switches without a default when the compiler should identify newly added constants that need handling.

10. Text blocks

Java 15 · Permanent Multiline string literals with predictable incidental-indentation handling.

Text blocks were previewed in Java 13 and 14 and finalized in Java 15. They reduce escape noise for multiline text while still producing ordinary String values. Compilation removes incidental indentation according to the closing delimiter and surrounding content, normalizes line terminators, and processes escape sequences. [14][15]

Java 15+JSON fixture 
String json = """
        {
          "event": "order.created",
          "version": 2,
          "items": [
            {"sku": "A-17", "quantity": 3}
          ]
        }
        """;
Java 15+SQL remains parameterized 
String sql = """
        SELECT id, customer_id, total
          FROM purchase_order
         WHERE status = ?
           AND created_at >= ?
         ORDER BY created_at DESC
        """;

try (PreparedStatement statement = connection.prepareStatement(sql)) {
    statement.setString(1, "OPEN");
    statement.setObject(2, since);
    // Execute...
}
Security boundary: text blocks improve source readability; they do not make concatenated SQL, HTML, shell commands, or JSON safe. Continue to use prepared statements, encoders, serializers, and domain-specific APIs.

Whitespace controls

The \s escape can preserve trailing spaces, and a backslash at the end of a source line suppresses the corresponding newline in the resulting string. Use these controls sparingly because invisible formatting can be hard to review. [14]

11. Records

Java 16 · Permanent Nominal classes that make a transparent data-carrier commitment.

Records were previewed in Java 14 and 15 and finalized in Java 16. A record declaration defines a fixed state description—the record components—and receives corresponding private final fields, public accessors, a canonical constructor, and implementations of equals, hashCode, and toString. Records are implicitly final and cannot extend another class, though they can implement interfaces. [16]

Java 16+Compact constructor enforces invariants 
import java.math.BigDecimal;
import java.util.Currency;
import java.util.Objects;

public record Money(BigDecimal amount, Currency currency) {
    public Money {
        Objects.requireNonNull(amount, "amount");
        Objects.requireNonNull(currency, "currency");

        if (amount.scale() > currency.getDefaultFractionDigits()) {
            throw new IllegalArgumentException(
                    "Too many fractional digits for " + currency);
        }
    }

    public Money add(Money other) {
        if (!currency.equals(other.currency)) {
            throw new IllegalArgumentException("Currency mismatch");
        }
        return new Money(amount.add(other.amount), currency);
    }
}

Shallow immutability is not deep immutability

Record component fields are final, but referenced objects can still be mutable. Defensive copying may be necessary both when constructing the record and when exposing components. The automatically generated accessor returns the stored reference unless it is overridden. [16] 

public record Team(String name, List<String> members) {
    public Team {
        members = List.copyOf(members);
    }
}

Records are not universal DTO replacements

Use records when identity is derived from the whole declared state and the API benefits from transparent accessors. Entities with lifecycle identity, mutable aggregates, lazy-loading requirements, or framework proxy constraints may be better represented by ordinary classes. Record serialization and framework compatibility should be tested with the exact library versions used by the application.

12. Pattern matching

Java 16 and 21 · Permanent core Type patterns for instanceof, record patterns, and pattern matching for switch.

Java 25 · Third preview Primitive types in patterns, instanceof, and switch are an additional preview feature.

12.1 Type patterns for instanceof

Pattern matching for instanceof was finalized in Java 16. A successful type pattern both tests the runtime type and introduces a pattern variable. Flow scoping makes the variable available only where the compiler can prove the pattern matched. [17] 

static int normalizedLength(Object value) {
    if (value instanceof String text && !text.isBlank()) {
        return text.strip().length();
    }
    return 0;
}

12.2 Pattern matching for switch

Pattern switches were previewed from Java 17 through Java 20 and finalized in Java 21. Case labels can contain type patterns, null, and guarded patterns using when. Pattern switches are checked for dominance and exhaustiveness. [18] 

static String describe(Object value) {
    return switch (value) {
        case null -> "null";
        case String s when s.isBlank() -> "blank text";
        case String s -> "text of length " + s.length();
        case Integer i when i < 0 -> "negative integer";
        case Integer i -> "integer " + i;
        default -> value.getClass().getSimpleName();
    };
}

12.3 Record patterns

Record patterns, finalized in Java 21, destructure record values by matching their component structure. Patterns can nest, allowing validation and extraction to be expressed near the control flow that depends on it. [19] 

record Point(int x, int y) {}
record Segment(Point start, Point end) {}

static int manhattanLength(Segment segment) {
    if (segment instanceof Segment(
            Point(int x1, int y1),
            Point(int x2, int y2))) {
        return Math.abs(x2 - x1) + Math.abs(y2 - y1);
    }
    throw new AssertionError("Unreachable for a non-null Segment");
}

12.4 Primitive patterns in Java 25

JEP 507 extends pattern contexts and switch to primitive types in its third preview in Java 25. Because it is preview, production adoption should account for possible source and API changes in later releases. [20]

Java 25 previewCompile with --enable-preview --release 25 
static String classify(long value) {
    return switch (value) {
        case 0L -> "zero";
        case long n when n < 0L -> "negative";
        case long n -> "positive: " + n;
    };
}

13. Sealed classes and interfaces

Java 17 · Permanent A controlled set of permitted direct subclasses or implementations.

Sealed classes were previewed in Java 15 and 16 and finalized in Java 17. A sealed class or interface restricts direct extension or implementation to a declared permitted set. A permitted subtype must be final, sealed, or non-sealed, explicitly declaring how the hierarchy continues. [21]

Java 21+Sealed algebraic-style model with record patterns 
sealed interface Expression
        permits Constant, Add, Multiply, Negate {}

record Constant(double value) implements Expression {}
record Add(Expression left, Expression right) implements Expression {}
record Multiply(Expression left, Expression right) implements Expression {}
record Negate(Expression operand) implements Expression {}

static double evaluate(Expression expression) {
    return switch (expression) {
        case Constant(double value) -> value;
        case Add(var left, var right) ->
                evaluate(left) + evaluate(right);
        case Multiply(var left, var right) ->
                evaluate(left) * evaluate(right);
        case Negate(var operand) -> -evaluate(operand);
    };
}

The compiler can prove the switch exhaustive because the selector type is sealed and every permitted alternative is handled. Omitting a broad default is valuable here: when a new permitted subtype is introduced, existing exhaustive switches become compilation points that identify logic requiring review. [18][21]

Closed-world modeling, not universal inheritance control

Sealing is appropriate when the domain owns and understands the complete set of alternatives: syntax trees, protocol outcomes, commands, states, and bounded result types. Extensible plugin APIs generally need open interfaces or an explicitly non-sealed branch.

14. Virtual threads

Java 21 · Permanent Lightweight Thread instances scheduled by the JDK rather than one-to-one for their entire lifetime with operating-system threads.

Virtual threads were previewed in Java 19 and 20 and finalized by JEP 444 in Java 21. Their goal is to let thread-per-request server code scale to large numbers of concurrent, mostly waiting tasks while preserving ordinary blocking control flow, stack traces, exceptions, interruption, and thread-oriented tools. They improve throughput for high-concurrency waiting workloads; they do not make CPU-bound computation faster. [22][23]

Java 21+One virtual thread per task 
import java.net.URI;
import java.net.http.*;
import java.util.List;
import java.util.concurrent.Executors;

static List<String> fetchAll(List<URI> uris) throws Exception {
    HttpClient client = HttpClient.newHttpClient();

    try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
        var futures = uris.stream()
                .map(uri -> executor.submit(() -> {
                    HttpRequest request = HttpRequest.newBuilder(uri).GET().build();
                    return client.send(
                            request,
                            HttpResponse.BodyHandlers.ofString()).body();
                }))
                .toList();

        return futures.stream()
                .map(future -> {
                    try {
                        return future.get();
                    } catch (Exception e) {
                        throw new RuntimeException(e);
                    }
                })
                .toList();
    }
}

Do not pool virtual threads

JEP 444 explicitly advises creating a new virtual thread for each task rather than pooling virtual threads. Pools historically ration expensive platform threads; virtual threads are intended to be plentiful. Scarce external resources—database connections, API quotas, file descriptors, or service capacity—must still be bounded with semaphores, connection pools, rate limiters, or domain-specific controls. [22] 

private final Semaphore outboundLimit = new Semaphore(50);

Response callPartner(Request request) throws Exception {
    outboundLimit.acquire();
    try {
        return partnerClient.call(request);
    } finally {
        outboundLimit.release();
    }
}

Pinning and JDK evolution

A virtual thread normally unmounts from its carrier when it blocks. Earlier implementations could remain pinned in some synchronized or native situations; JDK 24 delivered JEP 491 to allow virtual threads to synchronize without pinning in most synchronized cases. Native calls and other special operations can still require measurement and diagnosis with current JDK tooling. [24]

Migration pattern: begin with I/O-bound request handlers written in direct style. Replace fixed worker pools with a virtual-thread-per-task executor, retain existing timeouts and cancellation, and separately limit each scarce downstream resource.

15. String Templates: an important withdrawn preview

Java 21–22 preview only · Withdrawn Not present in Java 23, 24, or 25.

String Templates were introduced by JEP 430 in Java 21 and re-previewed by JEP 459 in Java 22. The design coupled literal text and embedded expressions with a template processor, allowing a template expression to produce a String or another domain-specific result. After two preview rounds, OpenJDK withdrew the feature before Java 23 because the design was judged unsuitable in its current form; Java 23 and Java 25 do not provide the syntax, even with preview enabled. [25][26][27]

Historical Java 22 previewDoes not compile on JDK 25 
// Historical syntax from the withdrawn preview:
String user = "Duke";
int messages = 4;

String summary = STR."""
        User: \{user}
        Messages: \{messages}
        """;

Why this history matters

Preview is a feedback mechanism, not a promise that syntax will become permanent. Shipping a long-lived library or persisted source generator around a preview feature creates migration risk. Preview use belongs behind deliberate build configuration, test coverage, and an explicit upgrade plan. [4][27]

Java 25 alternatives

String user = "Duke";
int messages = 4;

// Ordinary formatting:
String summary = """
        User: %s
        Messages: %d
        """.formatted(user, messages);

// For SQL, use PreparedStatement rather than interpolation.
// For JSON, use a JSON serializer.
// For HTML, use contextual escaping or a template engine.
Do not teach withdrawn syntax as current Java. It is useful historically and as a case study in the preview process, but production Java 25 source must use another mechanism.

16. Scoped Values

Java 25 · Permanent Dynamically scoped, bounded, one-way sharing of context with callees and structured child threads.

Scoped Values incubated in Java 20, previewed in Java 21 through 24, and became permanent through JEP 506 in Java 25. A ScopedValue acts like an implicit method parameter available to code within a bounded dynamic scope. Unlike ThreadLocal, a binding is established for an operation, cannot be mutated through the key, and automatically ceases to be bound when the operation completes normally or exceptionally. [28][29]

Java 25+Bound request context 
import java.lang.ScopedValue;
import java.util.UUID;

public final class RequestContext {
    private static final ScopedValue<Context> CURRENT =
            ScopedValue.newInstance();

    public static void serve(String userId, Runnable handler) {
        var context = new Context(
                UUID.randomUUID().toString(),
                userId);

        ScopedValue.where(CURRENT, context)
                .run(handler);
    }

    public static Context current() {
        return CURRENT.orElseThrow(
                () -> new IllegalStateException("No request context"));
    }

    public record Context(String requestId, String userId) {}
}
RequestContext.serve("user-17", () -> {
    audit(RequestContext.current().requestId());
    applicationService.execute();
});

Capability discipline

The Java 25 API documentation advises treating the ScopedValue object itself as a capability: only code with access to the key can retrieve the bound value. Keys are commonly private, static, and final. Values shared into child threads should be immutable or otherwise synchronized. [29]

When Scoped Values replace ThreadLocal—and when they do not

Scoped Values are preferred for one-way transmission of unchanging contextual data such as request identity, tenant, security context, or trace metadata. A ThreadLocal remains conceptually different: it allows mutation and can persist for a thread's lifetime. Code that uses ThreadLocal as a mutable back-channel or per-thread cache cannot be mechanically translated into a Scoped Value. [28][29]

17. Structured Concurrency

Java 25 · Fifth preview Related concurrent subtasks are created, joined, failed, canceled, and observed as one lexical unit.

Structured Concurrency incubated in Java 19 and 20, previewed in Java 21, and was re-previewed through Java 25. JEP 505 changed the Java 25 API to open scopes through static factory methods and introduced joiner-based completion policies. The default scope starts each forked subtask in a virtual thread, waits for all subtasks to succeed or one to fail, and confines child-thread lifetimes to the scope. [30][31]

Java 25 previewCompile and run with --enable-preview 
import java.util.concurrent.StructuredTaskScope;
import java.util.concurrent.StructuredTaskScope.Subtask;

record Dashboard(User user, List<Order> orders) {}

Dashboard loadDashboard(String userId) throws InterruptedException {
    try (var scope = StructuredTaskScope.open()) {
        Subtask<User> user =
                scope.fork(() -> userClient.fetch(userId));

        Subtask<List<Order>> orders =
                scope.fork(() -> orderClient.fetchFor(userId));

        scope.join(); // Propagates failure under the default policy.

        return new Dashboard(user.get(), orders.get());
    }
}

Why ordinary futures are often unstructured

With independent executor submissions, the parent task can lose lexical ownership of child tasks. A failure may leave sibling work running, cancellation can be incomplete, and thread dumps show a flat collection rather than a task tree. A structured scope gives the parent a single place to fork, join, handle failure, and close; closing prevents unfinished children from outliving the scope. [30][31]

Joiner policies

Java 25's preview API includes joiners for policies such as “all successful or throw,” “any successful result or throw,” “await all successful or throw,” and “await all.” Custom joiners can define completion and result policies. Because this API is preview, names and signatures can change in later Java releases. [31]

Java 25 previewFirst successful result wins 
import static java.util.concurrent.StructuredTaskScope.Joiner
        .anySuccessfulResultOrThrow;

<T> T race(List<Callable<T>> alternatives)
        throws InterruptedException {

    try (var scope = StructuredTaskScope.open(
            anySuccessfulResultOrThrow())) {

        alternatives.forEach(scope::fork);
        return scope.join();
    }
}
Preview boundary: the concept is mature enough for evaluation, but the Java 25 API is not permanent. Isolate direct references to StructuredTaskScope behind a small internal abstraction if an application must reduce upgrade impact.

18. How the features compose

18.1 Data-oriented domain model

Records describe products, sealed interfaces describe a closed sum of alternatives, and pattern switches destructure and exhaustively process the model. This combination can replace visitors, tag fields, unsafe casts, and “impossible” default branches in bounded domains. [16][18][19][21] 

sealed interface PaymentResult permits Approved, Declined, Failed {}

record Approved(String authorizationCode) implements PaymentResult {}
record Declined(String reason) implements PaymentResult {}
record Failed(Throwable cause) implements PaymentResult {}

static HttpResponse toResponse(PaymentResult result) {
    return switch (result) {
        case Approved(var code) -> HttpResponse.ok(
                Map.of("authorizationCode", code));
        case Declined(var reason) -> HttpResponse.status(
                422, Map.of("reason", reason));
        case Failed(var cause) -> {
            log.error("Payment failed", cause);
            yield HttpResponse.serverError();
        }
    };
}

18.2 Direct-style request concurrency

Virtual threads provide inexpensive task threads; Scoped Values carry immutable request context through call stacks and structured child threads; Structured Concurrency binds the lifetime of forked operations to the request. The three features address different concerns and are designed to work together. [22][28][30]

Java 25 preview because of StructuredTaskScopeContext + concurrency 
private static final ScopedValue<TraceContext> TRACE =
        ScopedValue.newInstance();

Response handle(Request request) {
    TraceContext trace = TraceContext.from(request);

    return ScopedValue.where(TRACE, trace).call(() -> {
        try (var scope = StructuredTaskScope.open()) {
            var profile = scope.fork(
                    () -> profileClient.fetch(request.userId()));

            var recommendations = scope.fork(
                    () -> recommendationClient.fetch(request.userId()));

            scope.join();

            return Response.ok(new Page(
                    profile.get(),
                    recommendations.get(),
                    TRACE.get().traceId()));
        }
    });
}

18.3 Lambdas are the connective tissue

The callback passed to ScopedValue.run, the tasks forked by a structured scope, stream operations, executor submissions, and Optional transformations all use functional interfaces. Java 8's lambda work therefore underlies many APIs introduced a decade later. [5][6]

19. Adoption and migration strategy

  1. Choose a release baseline. Java 17 and 21 are common migration waypoints; Java 25 adds permanent Scoped Values and newer language changes. Confirm vendor support, framework certification, and deployment images.
  2. Separate source level from runtime level. Set toolchains and --release explicitly so developers do not accidentally compile against APIs absent from the deployment target.
  3. Modernize behavior before syntax. Add tests, remove obsolete libraries, and clarify domain boundaries before replacing classes with records or visitors with pattern switches.
  4. Use records and sealed types together selectively. Model closed, data-centered domains; do not force entities, framework proxies, or open plugin APIs into closed hierarchies.
  5. Adopt virtual threads at I/O boundaries. Preserve blocking code, remove pools that only ration threads, and retain explicit bounds for scarce downstream resources.
  6. Replace ThreadLocal context only when semantics align. Scoped Values suit immutable, one-way context; mutable caches and bidirectional communication require another design.
  7. Isolate preview APIs. Keep Java 25 Structured Concurrency behind a small internal layer and compile preview code in dedicated modules or source sets.
  8. Delete withdrawn experiments. String Template source from Java 21–22 previews must be rewritten before compiling on JDK 23–25.
  9. Benchmark representative workloads. Streams, parallelism, virtual threads, and data-model changes should be measured with realistic contention, I/O, allocation, and warm-up.

Final perspective

Modern Java is not one stylistic shift. Java 8 made behavior composable; Java 9 made architecture visible; Java 10–17 reduced ceremony around local code and data carriers; Java 21 completed a major pattern-matching and virtual-thread milestone; Java 25 made bounded contextual data sharing permanent while continuing to refine structured concurrency. The withdrawal of String Templates demonstrates that preview features are genuine experiments rather than inevitable additions. [1][3][27][28][30]

Practical conclusion: write new Java in the oldest release that supplies the permanent features your system actually needs; use newer runtime features after measurement; and treat preview features as versioned experiments with an exit plan.
