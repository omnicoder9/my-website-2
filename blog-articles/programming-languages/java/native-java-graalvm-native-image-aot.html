1. What “Native Java” means

“Native Java” is an informal phrase, not one precise Java specification term. It commonly refers to three related but technically different ideas.

Java calling native code

A JVM application can invoke C or other platform libraries through JNI or the Foreign Function and Memory API. The Java application still runs on a JVM.

A native executable from Java

GraalVM Native Image analyzes Java bytecode ahead of time and emits a platform-specific executable or shared library containing application code and required runtime components.

AOT code used by a JVM

JDK 9 introduced the experimental jaotc tool, which generated native shared libraries loaded by HotSpot. That experiment was removed in JDK 17.

GraalVM as a JDK

GraalVM can also run ordinary Java bytecode on HotSpot with the Graal JIT compiler. Using GraalVM does not automatically mean using Native Image.

GraalVM Native Image is the focus of this article. It compiles Java bytecode ahead of time into a native executable for a specific operating system and architecture. The executable does not run on HotSpot, but it still contains a Java runtime substrate providing services such as memory management, thread scheduling, exception handling, and garbage collection. [1][2]

Essential distinction: a native executable is not “Java without a runtime.” It is Java compiled with a different deployment and runtime model. The JIT compiler and general class-loading environment are absent, but required runtime services remain in the binary.

As of 30 July 2026, the official GraalVM download page lists Oracle GraalVM 25.1 as an innovation release, Oracle GraalVM 25.0 as an LTS release, and supported JDK 21 and JDK 17 lines. Native Image is available through GraalVM distributions and official container images. [3]

2. Historical development

Original Java model Java source is compiled to class-file bytecode. A JVM loads, verifies, links, interprets, and may dynamically compile methods to machine code.
JDK 9 · JVMCI JEP 243 introduced a Java-level JVM Compiler Interface so a compiler written in Java can inspect VM metadata and install machine code as a dynamic compiler.
JDK 9 · jaotc JEP 295 added an experimental AOT tool using Graal as its backend to produce native libraries consumed by HotSpot.
GraalVM Graal evolved as a Java-written optimizing compiler used as a HotSpot JIT compiler and as the compiler at the heart of Native Image.
JDK 17 JEP 410 removed the experimental jaotc AOT tool and the JDK-bundled experimental Graal compiler, while retaining JVMCI for external compilers.
Modern Native Image Native Image became the principal GraalVM mechanism for producing standalone Java executables and native shared libraries.

The Java Virtual Machine Specification defines the class-file and JVM execution model, while javac translates Java source to class files. The portability boundary is normally bytecode: the same application artifact can run wherever a compatible JVM and dependencies are available. [4][5]

JEP 243 delivered JVMCI in JDK 9. JVMCI lets a compiler written in Java access VM structures, receive compilation requests, and install generated machine code into HotSpot. Graal is the primary demonstration of that architecture. [6]

JEP 295 also arrived in JDK 9, but its jaotc model was not a standalone executable. It generated an AOT shared library—for example, libHelloWorld.so—that the java launcher could load into HotSpot with -XX:AOTLibrary. The feature was explicitly experimental. [7] 

# Historical JDK 9 experimental AOT flow — not Native Image:
jaotc --output libHelloWorld.so HelloWorld.class
java -XX:AOTLibrary=./libHelloWorld.so HelloWorld

JEP 410 removed jaotc, the jdk.aot module, and the JDK-bundled experimental Graal JIT modules in JDK 17 because they saw little use and imposed maintenance cost. JVMCI remained so externally built compilers could still integrate with HotSpot. [8]

Historical trap: tutorials that describe jaotc as the current way to compile Java natively are obsolete. Modern standalone AOT deployment uses GraalVM Native Image, framework-specific integrations built on it, or another external technology—not the removed JDK tool.

3. JIT versus AOT execution models

Dimension HotSpot JVM with JIT GraalVM Native Image AOT
Deployment unit JARs/modules plus a compatible JVM OS- and architecture-specific executable or shared library
Compilation timing Bytecode is interpreted and compiled during execution Reachable bytecode is compiled before deployment
Runtime profiling JIT observes actual branches, call sites, and hot methods Default AOT compilation relies on static analysis and heuristics; PGO can supply representative profiles
Startup Must initialize a JVM, load classes, and warm selected code paths Machine code and part of the initial heap are already present
Dynamic loading General class loading, reflection, proxies, and instrumentation are runtime capabilities All runtime code must be known at build time; dynamic features may require metadata
Peak adaptation JIT can recompile according to observed behavior No general application JIT; profile-guided builds recover some profile information
Build cost Ordinary Java compilation and packaging Whole-program analysis, image-heap construction, native compilation, and linking
Operational fit Long-lived services, adaptive peak throughput, broad compatibility Fast-starting services, serverless, CLIs, scale-to-zero, constrained containers

The JIT compiler's major advantage is access to live profiles. It can learn which branches are common, which receiver types appear at a call site, and which methods become hot. A conventional AOT compiler lacks that runtime history unless the build is supplied with a representative profile. GraalVM's PGO workflow exists to bring selected runtime profile data into a subsequent Native Image build. [9]

Native Image's documented advantages include fast startup, lower runtime memory overhead, immediate availability of AOT-compiled code, compact packaging, and elimination of unreachable code. Those are workload-dependent engineering claims, not universal benchmark results; the correct comparison is the same application under production-like load, memory limits, and deployment conditions. [1][10]

4. GraalVM architecture

JVM mode GraalVM can run ordinary bytecode on HotSpot, using the Graal compiler as a high-tier JIT compiler.

Native Image mode Graal compiles a closed set of reachable Java code into a native executable backed by Native Image runtime components.

The Graal compiler is written in Java and transforms bytecode into machine code. Through JVMCI, it can operate as a HotSpot JIT compiler. GraalVM also includes Truffle, a framework for implementing languages whose interpreters can be partially evaluated and optimized by Graal. Native Image reuses Graal for ahead-of-time compilation but does not run the resulting application on HotSpot. [6][11][12]

Graal JIT compiler

Runs inside or alongside HotSpot through JVMCI and compiles hot bytecode during application execution.

Native Image builder

Runs as a build-time JVM process, analyzes the application's closed world, constructs an image heap, compiles code, and links a binary.

Native Image runtime

Supplies garbage collection, threads, exceptions, synchronization, safepoints, diagnostics, and other services needed by the executable.

Truffle

Provides a language-implementation framework; it is related to GraalVM but not required for an ordinary Java Native Image application.

Native Image's older documentation calls its runtime substrate “Substrate VM.” Current documentation more often describes Native Image runtime components directly. The architectural point remains: the executable includes a specialized runtime rather than embedding the full HotSpot JVM and its JIT compilation infrastructure. [2][13]

5. The Native Image build pipeline

Bytecode inputApplication, dependencies, JDK classes, metadata.
Class loadingBuilder loads the build-time universe.
Reachability analysisFind types, methods, fields, resources, and call paths.
Image heapPersist selected initialized objects and static state.
AOT compilationGenerate target machine code.
Native linkingCreate executable or shared library.

The builder starts from application entry points and statically analyzes reachable program elements. It includes the application classes, required dependency and JDK classes, resources, runtime components, and native code needed for the selected platform. The builder then compiles the reachable code and links a platform-specific binary. [1][14]

This is a whole-program build relative to the supplied class path, module path, metadata, and entry points. The builder itself runs on a JVM and can require substantial memory and CPU because it creates a representation of the application and analyzes its reachable graph. GraalVM documents builder heap controls through -J JVM arguments and parallelism through --parallelism. [15]

Build tuningArguments for the builder JVM 
# Limit builder heap to 8 GiB and use eight build threads:
native-image \
  -J-Xmx8g \
  --parallelism=8 \
  -jar target/application.jar

Build-time and runtime are separate semantic phases

Native Image may execute class initializers and framework build-time code while constructing the binary. Objects reachable from build-time static state can be serialized into the image heap. At runtime, the executable begins with that pre-populated state plus a normal runtime Java heap for newly allocated objects. [16][17]

Reproducibility consequence: the native build is not merely “compile every method.” Build environment, initialization policy, included resources, metadata, target architecture, compiler options, and native linker inputs can all affect the output.

6. Building a first native executable

The native-image tool accepts a main class, an executable JAR, or a Java module. It requires a local native toolchain appropriate to the operating system, including C compiler and development libraries documented for the platform. [1][14]

src/main/java/com/example/HelloNative.javaJava 25 
package com.example;

import java.time.Instant;
import java.util.HexFormat;
import java.util.random.RandomGenerator;

public final class HelloNative {
    private HelloNative() {}

    public static void main(String[] args) {
        byte[] nonce = new byte[8];
        RandomGenerator.getDefault().nextBytes(nonce);

        System.out.printf(
                "Native Java at %s; nonce=%s%n",
                Instant.now(),
                HexFormat.of().formatHex(nonce));
    }
}

Class-directory build

mkdir -p out
javac --release 25 -d out \
  src/main/java/com/example/HelloNative.java

native-image \
  -cp out \
  -o hello-native \
  com.example.HelloNative

./hello-native

Executable-JAR build

jar --create \
  --file hello-native.jar \
  --main-class com.example.HelloNative \
  -C out .

native-image \
  --no-fallback \
  -jar hello-native.jar \
  hello-native

--no-fallback requires a true native executable and makes the build fail rather than producing a fallback artifact that depends on a JVM. This is useful in CI because a successful build then proves that the selected native deployment model was actually produced. [18][19]

Modular build

native-image \
  --module-path mods \
  --module com.example.app/com.example.HelloNative \
  hello-native

Native Image accepts standard module-oriented options such as --module, --module-path, --add-opens, and --add-exports. [20]

9. The closed-world assumption

Native Image assumes that every class and method that can execute is known at image build time. The reachability analysis begins at entry points and follows discoverable references. Code that is not reachable is omitted, while code that becomes reachable only through runtime data may be invisible to static analysis unless metadata or build-time registration makes it explicit. [18][25]

Usually straightforward

  • Direct constructor and method calls.
  • Ordinary inheritance and interface dispatch where implementations are present in the build.
  • Lambdas and string concatenation emitted by javac in supported forms.
  • Resources referenced by constant calls that Native Image can prove.
  • Libraries that publish their own reachability metadata.

Often requires special treatment

  • Class names read from configuration and passed to Class.forName.
  • Reflective constructor, method, field, record-component, or method-handle access.
  • Dynamic proxies selected from runtime interface lists.
  • JNI lookups initiated by native code.
  • Foreign Function and Memory API signatures generated from runtime data.
  • Classpath scanning and runtime bytecode generation.
  • Resources whose paths are computed from external data.
  • Java serialization types not otherwise reachable.

Native Image supports many dynamic Java features, but their reachable targets must be describable before deployment. General loading of brand-new classes from arbitrary bytecode at runtime is not compatible with the closed-world model. GraalVM documents limited predefined-class mechanisms for legacy cases, but calls them a best-effort approach rather than a substitute for an AOT-aware architecture. [25][26]

Design implication: Native Image rewards explicit wiring, generated registries, service indexes, build-time code generation, and libraries that publish metadata. It penalizes architectures that discover their executable universe only after startup.

10. Reachability metadata

Reachability metadata tells the builder which dynamically accessed types, members, resources, proxy interfaces, JNI elements, serialization types, and foreign-call signatures must remain in the binary. Current GraalVM documentation uses a unified reachability-metadata.json format under META-INF/native-image/<groupId>/<artifactId>/. [26]

10.1 Reflection example

PluginLoader.javaRuntime class name 
package com.example.plugins;

import java.lang.reflect.InvocationTargetException;

public final class PluginLoader {
    private PluginLoader() {}

    public static PricingPlugin load(String className) {
        try {
            Class<?> rawType = Class.forName(className);
            Class<? extends PricingPlugin> pluginType =
                    rawType.asSubclass(PricingPlugin.class);

            return pluginType.getDeclaredConstructor().newInstance();
        } catch (ClassNotFoundException
                 | NoSuchMethodException
                 | InstantiationException
                 | IllegalAccessException
                 | InvocationTargetException exception) {
            throw new IllegalArgumentException(
                    "Cannot load pricing plugin " + className,
                    exception);
        }
    }
}
package com.example.plugins;

import java.math.BigDecimal;

public interface PricingPlugin {
    BigDecimal adjust(BigDecimal subtotal);
}

public final class FivePercentDiscount implements PricingPlugin {
    public FivePercentDiscount() {}

    @Override
    public BigDecimal adjust(BigDecimal subtotal) {
        return subtotal.multiply(new BigDecimal("0.95"));
    }
}

The plugin type cannot be inferred when its class name comes from runtime configuration. Metadata must make the type and reflectively invoked constructor available. Missing metadata can cause Native Image registration errors at runtime. [27]

src/main/resources/META-INF/native-image/com.example/native-demo/reachability-metadata.jsonMinimal reflection registration 
{
  "reflection": [
    {
      "condition": {
        "typeReached": "com.example.plugins.PluginLoader"
      },
      "type": "com.example.plugins.FivePercentDiscount",
      "methods": [
        {
          "name": "<init>",
          "parameterTypes": []
        }
      ]
    }
  ]
}

Metadata entries should be as narrow as possible. The format also supports conveniences such as allDeclaredConstructors and allPublicMethods, but broad registration increases binary contents and can conceal an imprecise plugin contract. [26]

10.2 Resource example

package com.example.config;

import java.io.IOException;
import java.nio.charset.StandardCharsets;

public final class Banner {
    public static String load() {
        try (var stream =
                     Banner.class.getResourceAsStream("/banner.txt")) {
            if (stream == null) {
                throw new IllegalStateException("Missing banner.txt");
            }
            return new String(
                    stream.readAllBytes(),
                    StandardCharsets.UTF_8);
        } catch (IOException exception) {
            throw new IllegalStateException("Cannot read banner", exception);
        }
    }
}
reachability-metadata.jsonInclude a classpath resource 
{
  "resources": [
    {
      "glob": "banner.txt"
    }
  ]
}

Native Image automatically detects some constant resource lookups, but explicit resource metadata is appropriate when paths are dynamic or a library contract requires a pattern. Build reports can show which resources were embedded. [26][28]

10.3 Metadata repository

GraalVM's Reachability Metadata Repository distributes configuration for third-party libraries that do not publish sufficient metadata themselves. Native Build Tools can discover and apply repository entries according to dependency coordinates. Library authors should prefer shipping metadata in their own artifacts so compatibility evolves with the library release. [22][29]

11. Collecting metadata with the Tracing Agent

The Native Image Tracing Agent runs the application on a JVM and records observed uses of reflection, resources, JNI, proxies, and other dynamic features. Its output can seed reachability metadata. The agent sees only paths exercised by the workload, so complete tests and representative scenarios remain essential. [30]

Direct command-line workflow

# Run JVM tests or an application scenario while collecting metadata:
java \
  -agentlib:native-image-agent=\
config-output-dir=src/main/resources/META-INF/native-image/com.example/native-demo \
  -jar target/native-demo.jar

# Build using the collected metadata:
native-image \
  --no-fallback \
  -jar target/native-demo.jar \
  native-demo

Gradle workflow

# Run the application on the JVM with agent instrumentation:
./gradlew -Pagent=standard run

# Copy and merge generated metadata into source resources:
./gradlew metadataCopy \
  --task run \
  --dir src/main/resources/META-INF/native-image

# Build the native executable:
./gradlew nativeCompile

Native Build Tools supports standard, conditional, and direct agent modes. Standard mode is aimed at a concrete application executable, while conditional mode is useful for library metadata that should apply only when a relevant type is present. [23][29]

Agent limitation: metadata collection is coverage-dependent. If an integration test never exercises a serializer subtype, plugin, locale bundle, proxy, JNI callback, or security provider, the agent cannot register it. Review generated metadata and add targeted native tests.

12. Build-time class initialization and the image heap

Native Image can initialize classes while building the executable. Static fields and reachable objects created by those initializers may be stored in the image heap and become immediately available at runtime. This can reduce startup work, but it changes when code executes and can freeze environment-dependent state into the binary. [16][17]

HazardousInitializer.javaUnsafe to freeze at build time 
package com.example.runtime;

import java.net.InetAddress;
import java.security.SecureRandom;
import java.time.Instant;

public final class HazardousInitializer {
    public static final Instant STARTED_AT = Instant.now();
    public static final byte[] SECRET_NONCE =
            new SecureRandom().generateSeed(32);
    public static final String HOSTNAME = resolveHostname();

    private static String resolveHostname() {
        try {
            return InetAddress.getLocalHost().getHostName();
        } catch (Exception exception) {
            return "unknown";
        }
    }
}

If this class is initialized during image construction, the timestamp, random bytes, and build machine hostname can be persisted into the binary. GraalVM's security guidance specifically warns that build-time initializers can embed secrets or fix values such as random seeds that should be obtained when the executable starts. [31] 

native-image \
  --initialize-at-run-time=com.example.runtime.HazardousInitializer \
  -jar target/native-demo.jar

Safe build-time initialization

package com.example.lookup;

import java.util.Map;

public final class HttpStatusText {
    public static final Map<Integer, String> VALUES = Map.of(
            200, "OK",
            400, "Bad Request",
            404, "Not Found",
            500, "Internal Server Error");

    private HttpStatusText() {}
}

Immutable lookup data with no environmental dependency may be an appropriate build-time candidate, while time, locale, host identity, credentials, random state, file contents, network access, and external configuration generally belong at runtime. GraalVM recommends explicit initialization at the class level rather than broad package-wide settings unless the package semantics are fully understood. [17][32] 

native-image \
  --initialize-at-build-time=com.example.lookup.HttpStatusText \
  --initialize-at-run-time=com.example.runtime.HazardousInitializer \
  -H:+PrintClassInitialization \
  -jar target/native-demo.jar
Do not use --initialize-at-build-time= globally as a generic speed switch. It can persist incorrect state, violate library assumptions, enlarge the image heap, and embed sensitive data.

13. Native Image runtime and memory management

At runtime, Java objects allocated by a native executable live on a Java heap managed by the Native Image runtime. The heap can grow and shrink within configured limits, and garbage collection reclaims unreachable runtime objects. The default collector is Serial GC, optimized for low memory footprint and smaller heaps. [33]

Collector Purpose Availability and caution
Serial GC Default, low footprint, smaller heaps Single-collector design favors footprint over large-heap parallelism
G1 GC Lower pause goals and high throughput on supported Linux architectures Not available in GraalVM Community Edition; select with --gc=G1
Epsilon GC No-op collector for very short, tightly bounded allocation lifetimes Never reclaims memory; unsuitable for ordinary long-running services 
# Explicit default:
native-image --gc=serial -jar application.jar

# G1 where supported:
native-image --gc=G1 -jar application.jar

# Only for short-lived, allocation-bounded workloads:
native-image --gc=epsilon -jar application.jar

Native Image supports ordinary runtime heap sizing options on the produced executable. Build-time memory and runtime memory are separate: -J-Xmx configures the builder JVM, while -Xmx passed to the executable configures its runtime heap. [15][33] 

# Builder heap:
native-image -J-Xmx8g -jar application.jar

# Runtime heap:
./application -Xms64m -Xmx256m

Image heap versus runtime heap

The image heap contains objects captured during the build and mapped into the executable's initial state. The runtime heap contains new allocations and mutable runtime state. An image can therefore start with a rich object graph without reconstructing it, but that graph contributes to binary size and may retain objects unexpectedly if build-time roots are too broad. [16][17]

14. Performance engineering: startup is not the whole benchmark

Native Image is designed to avoid JVM startup, class-loading, and JIT warmup costs, and its binaries can offer materially lower startup latency and runtime memory use for suitable applications. A HotSpot JVM, however, can adapt to live profiles and recompile hot code over time. The winner therefore depends on whether the workload is dominated by cold start, steady-state throughput, tail latency, memory, deployment density, or build cost. [1][9]

Measure at least six dimensions

  1. Cold start. Process creation to readiness, not merely time to enter main.
  2. Warm throughput. Requests, events, or operations per second after stabilization.
  3. Tail latency. P95, P99, and worst-case behavior under realistic concurrency.
  4. Memory. Heap, RSS, native memory, shared pages, and container memory limits.
  5. Artifact and image size. Executable, shared libraries, debug symbols, and container layers.
  6. Build cost. Native build time, builder peak memory, CI capacity, and metadata maintenance.

Reproducible launch benchmark

#!/usr/bin/env bash
set -euo pipefail

runs="${1:-30}"
binary="${2:-./target/native-demo}"

for ((i = 1; i <= runs; i++)); do
  /usr/bin/time \
    -f '%e,%M' \
    "$binary" \
    >/dev/null
done 2>&1

The script records wall-clock seconds and peak resident memory from the operating system's perspective, but it is not a complete server benchmark. A service comparison should include readiness probes, dependency initialization, realistic traffic, equal heap/container limits, repeated clean starts, and steady-state load.

Optimization levels

Native Image supports optimization levels including quick-build mode, size optimization, and higher performance settings. The default is -O2. Faster development builds can use -Ob, size-sensitive artifacts can use -Os, and supported Oracle GraalVM builds can use advanced -O3 behavior. [34] 

# Fast local iteration:
native-image -Ob -jar application.jar

# Optimize for binary size:
native-image -Os -jar application.jar

# Default production tradeoff:
native-image -O2 -jar application.jar
Benchmark rule: compare a native executable against a well-configured JVM deployment—not an untuned default. Include current JDKs, representative garbage collectors, realistic warmup, container awareness, and equivalent application features.

15. Profile-guided optimization

PGO addresses a fundamental AOT disadvantage: the compiler ordinarily lacks runtime branch and call-frequency information. GraalVM's workflow builds an instrumented executable, runs it under a representative workload to create an .iprof profile, and rebuilds using that profile. Official GraalVM documentation states that PGO is not available in GraalVM Community Edition. [9][34]

Three-stage PGO workflow

# 1. Build an instrumented executable:
native-image \
  --pgo-instrument \
  -jar target/application.jar \
  application-instrumented

# 2. Run representative traffic.
# The program writes default.iprof when it exits normally.
./application-instrumented \
  --load-test-scenario=production-like

# 3. Build the optimized executable:
native-image \
  --pgo=default.iprof \
  -jar target/application.jar \
  application

Profile quality determines optimization quality

A profile should include representative endpoints, payload sizes, exceptional paths, serialization types, database result shapes, and concurrency. A narrowly trained profile can bias code layout and optimization toward a benchmark path that is unimportant—or harmful—in production.

Operational PGO lifecycle

  • Version the profile with the source revision and dependency graph that generated it.
  • Regenerate after major framework, JDK, or workload changes.
  • Compare PGO and non-PGO binaries under the same benchmark.
  • Keep instrumented binaries out of production unless the profiling deployment is intentional.
  • Record the workload and environment used to create the profile.

16. Dynamic, mostly-static, and static linking

Native Image builds dynamically linked executables by default. On Linux, it can also build a mostly-static executable that leaves libc dynamic, or a fully static executable linked with musl. Fully static glibc linking is not supported by the documented Native Image workflow. [35] 

# Default dynamically linked executable:
native-image -jar application.jar

# Mostly static; libc remains dynamically linked:
native-image --static-nolibc -jar application.jar

# Fully static with musl:
native-image --static --libc=musl -jar application.jar

Minimal container image

DockerfileMulti-stage native build 
FROM container-registry.oracle.com/graalvm/native-image:25.1 AS build

WORKDIR /workspace
COPY . .
RUN ./mvnw -Pnative \
    -DskipTests \
    --batch-mode \
    clean package

FROM gcr.io/distroless/base-debian12:nonroot

COPY --from=build \
  /workspace/target/native-demo \
  /app/native-demo

USER nonroot:nonroot
ENTRYPOINT ["/app/native-demo"]

A distroless runtime still needs the libraries expected by a dynamically or mostly-statically linked executable. A truly static musl binary can run in a scratch image, but TLS certificates, time-zone data, locale data, DNS behavior, and files required by the application must still be supplied deliberately. [35]

Build for the target

Native executables are platform-specific. A Linux x64 image is not a Windows x64 or Linux AArch64 image. Build in a target-compatible environment or use a supported cross-compilation and container workflow; test the final artifact on the actual base image and architecture. [1][18]

17. Diagnostics and observability

Native Image supports build reports, static-analysis reports, debug information, heap dumps, JDK Flight Recorder, native memory tracking, Linux perf, JMX in supported configurations, and selected jcmd operations. These facilities are not all enabled automatically; monitoring support can increase the executable's size and attack surface, so it is selected at build time. [36]

Build report

native-image \
  --emit=build-report \
  -jar application.jar

The HTML build report helps inspect included code, resources, image-heap contents, and build decisions. It is useful when a binary unexpectedly grows or metadata retains more of a dependency than intended. [28]

JDK Flight Recorder

# Enable JFR in the executable:
native-image \
  --enable-monitoring=jfr \
  -jar application.jar

# Record at runtime:
./application \
  -XX:StartFlightRecording=filename=recording.jfr,duration=60s

Native Image supports many JFR events and custom events, but its event set and platform behavior are not identical to HotSpot. The official documentation lists available events and current limitations. [37]

jcmd, heap dumps, and native memory

# Build the required monitoring features:
native-image \
  --enable-monitoring=jcmd,jvmstat,jfr,heapdump,nmt \
  -jar application.jar

# Discover and inspect:
jcmd -l
jcmd <pid> VM.uptime
jcmd <pid> Thread.print
jcmd <pid> VM.native_memory
jcmd <pid> GC.heap_dump /tmp/application.hprof
jcmd <pid> JFR.start name=diagnostic duration=60s filename=/tmp/app.jfr

Current Native Image documentation describes supported jcmd commands including thread dumps, heap dumps, JFR control, system properties, native memory, uptime, and version information. The feature is not currently available on Windows. [38]

Production practice: decide diagnostic capabilities before an incident. A tiny binary without heap dumps, JFR, or useful symbols may reduce footprint but make rare production failures materially harder to investigate.

18. Native-code interoperability

“Native Java” can also mean crossing the Java/native boundary. Native Image supports JNI for Java-to-native and native-to-Java calls, and can compile Java code into a shared library callable from C or C++. JNI-accessed classes and members must be known at image build time because wrapper code and metadata have to be generated before runtime. [39][40]

Native Image C API shared library

NativeMath.javaJava exported as a C function 
package com.example.nativeapi;

import org.graalvm.nativeimage.IsolateThread;
import org.graalvm.nativeimage.c.function.CEntryPoint;

public final class NativeMath {
    private NativeMath() {}

    @CEntryPoint(name = "native_add")
    public static int add(
            IsolateThread thread,
            int left,
            int right) {
        return Math.addExact(left, right);
    }
}
javac -d out NativeMath.java

native-image \
  --shared \
  -cp out \
  -o native_math \
  com.example.nativeapi.NativeMath

A shared-library build generates platform library files and C headers. A method exposed with @CEntryPoint must be static, have a unique exported name, receive an isolate or isolate-thread context, and use supported non-object parameter and return types for the Native Image C API. [40]

main.cCall Java-implemented native function 
#include <stdio.h>
#include "native_math.h"

int main(void) {
    graal_isolate_t *isolate = NULL;
    graal_isolatethread_t *thread = NULL;

    if (graal_create_isolate(NULL, &isolate, &thread) != 0) {
        fprintf(stderr, "Could not create Native Image isolate\n");
        return 1;
    }

    int result = native_add(thread, 20, 22);
    printf("Result: %d\n", result);

    graal_tear_down_isolate(thread);
    return 0;
}

JNI inside a native executable

JNI itself is supported, but native lookups by string—such as FindClass or GetMethodID—cannot be inferred from Java call paths. Reachability metadata must register JNI-visible types, fields, methods, constructors, and wrapper entry points. [39][26]

Portability consequence: once an application depends on native libraries or emits a native shared library, ABI, compiler, operating system, architecture, C library, symbol visibility, packaging, and security updates become part of the Java application's lifecycle.

19. Testing and continuous integration

JVM tests remain the fastest development feedback, but they cannot prove that reachability metadata, initialization policy, native linking, platform resources, and runtime diagnostics work in the final executable. Native Build Tools therefore supports compiling and executing JUnit Platform tests as native code. [21][23]

Test pyramid for a native target

  1. JVM unit tests: business logic, edge cases, and fast feedback.
  2. JVM integration tests with the tracing agent: exercise dynamic features and collect candidate metadata.
  3. Native tests: serializers, dependency injection, proxies, resource loading, JNI, locale, security providers, and startup paths.
  4. Artifact smoke tests: run the exact binary inside its final container/base image.
  5. Performance tests: compare cold start, load, memory, and failure behavior.

20. Security considerations

Native Image can reduce deployed code by excluding unreachable elements and removing the general JIT infrastructure, which can reduce attack surface. It does not automatically make an application secure: application vulnerabilities, unsafe dependencies, native libraries, exposed protocols, weak configuration, and container privileges remain. [10][31]

Build-time execution is a trust boundary

The builder executes class initializers and framework features. A malicious or compromised build dependency can therefore execute with builder privileges. Native builds should run in isolated, reproducible environments with controlled dependencies, minimal credentials, and audited network access.

Prevent sensitive image-heap state

  • Initialize credential, random, host, time, and environment-dependent classes at runtime.
  • Inspect Native Image security and build reports.
  • Do not expose production secrets to build jobs.
  • Scan the final binary and container, not just Maven or Gradle dependencies.
  • Track native C libraries and C-library security updates.

Metadata is capability retention

Reflection metadata asks the build to preserve types and members that static analysis might otherwise remove. Broad registrations such as all fields, constructors, and methods retain more behavior and introspection surface than narrow method signatures. Treat metadata as security- and footprint-relevant configuration. [26]

Never embed secrets during the build: environment variables, generated tokens, private keys, hostnames, and random seeds accessed by build-time initializers can become part of the native executable's image heap.

21. When to choose Native Image

Use Native Image when Prefer a JVM deployment when
Cold start directly affects cost, latency, or scale-to-zero behavior. The process is long-lived and adaptive peak throughput dominates startup.
Memory density limits the number of replicas or functions. The application uses large heaps and benefits from a broader range of mature HotSpot collectors.
The application is a CLI, short-lived worker, build tool, or serverless function. The system depends heavily on runtime class generation, agents, plugins, or arbitrary class loading.
The framework and dependencies publish tested Native Image support. Critical libraries have poor metadata, unsupported native behavior, or unstable integrations.
A platform-specific artifact is acceptable. One portable JAR must run unchanged across diverse operating systems and architectures.
The team can afford longer native builds and maintain native CI matrices. Rapid iteration and minimal build infrastructure are more valuable than startup savings.

Hybrid deployment is often correct

One codebase can retain JVM tests and a JVM artifact while also producing a native deployment profile. A command-line utility might ship natively, while a continuously busy analytics service remains on HotSpot. The choice belongs to each workload rather than to an organization-wide slogan.

Decision experiment

  1. Select one representative service or CLI. Avoid the most reflection-heavy legacy application as the first experiment.
  2. Build both artifacts. Preserve the same application behavior, dependencies, configuration, and tests.
  3. Resolve metadata honestly. Do not disable features merely to make the native build pass unless the production design also changes.
  4. Measure production constraints. Startup to readiness, P99 latency, throughput, memory, container density, and build cost.
  5. Test operations. Logs, metrics, traces, JFR, heap dumps, graceful shutdown, signals, DNS, TLS, and incident procedures.
  6. Calculate lifecycle cost. Include native CI, architecture matrix, framework upgrades, metadata maintenance, and debugging skills.

22. Production checklist

Build and reproducibility

  • Pin GraalVM, Native Build Tools, Maven/Gradle wrapper, compiler, and container base versions.
  • Build in a controlled environment matching the target OS, architecture, and C library.
  • Use --no-fallback or equivalent plugin configuration.
  • Archive the build report and exact build command.
  • Budget builder memory and parallelism explicitly in CI.

Compatibility

  • Check every direct dependency for built-in or repository reachability metadata.
  • Exercise reflection, proxies, serialization, resources, JNI, security providers, and locale behavior in native tests.
  • Audit runtime bytecode generation, agents, classpath scanning, and plugin discovery.
  • Keep metadata narrow, conditional, versioned, and reviewed.

Initialization and security

  • Review build-time initialized application classes.
  • Force sensitive, random, environmental, network, and time-dependent state to runtime.
  • Do not expose secrets to the native build.
  • Track native-library and base-image vulnerabilities.

Performance and operations

  • Benchmark native and JVM deployments under equivalent production limits.
  • Select GC and heap settings according to measured workload.
  • Evaluate PGO only with representative profiles.
  • Enable JFR, heap dumps, jcmd, NMT, or debug symbols required by incident response.
  • Smoke-test the final container on every target architecture.
Bottom line: GraalVM Native Image is not a drop-in “make Java faster” switch. It is a different compilation and deployment model. It is strongest when fast startup, low footprint, compact packaging, and direct-style Java programming matter more than unrestricted runtime dynamism and JIT adaptation.
