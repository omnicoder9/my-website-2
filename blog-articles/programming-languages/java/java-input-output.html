1. I/O is a protocol between memory and an external system

Input/output code coordinates byte or character representation, framing, buffering, resource lifetime, partial progress, concurrency, filesystem semantics, durability, error recovery, and trust boundaries. A successful write normally means only that data advanced to the next layer—not necessarily that it reached durable storage.

Representation

Bytes, Unicode characters, primitive values, object graphs, or application records.

Transport/storage

Files, sockets, memory, pipes, channels, devices, archives, and provider-defined file systems.

Lifecycle

Open, read/write, flush, close, cancellation, replacement, and recovery after partial failure.

Policy

Size limits, charset rules, permissions, symbolic-link behavior, atomicity, durability, and trust.

The java.io package provides byte streams, character streams, primitive/object serialization, and legacy filesystem abstractions. Java NIO adds buffers, channels, charsets, and selectable/asynchronous I/O. NIO.2, centered on java.nio.file, provides paths, file operations, attributes, file-system providers, directory traversal, and change notification.[1][2][3]

Choose the data model before the API. Binary data belongs in byte streams or channels; text belongs in readers/writers with an explicit charset; filesystem identity belongs in Path; durable application interchange normally belongs in a documented schema rather than Java native serialization.

Decorator composition

try (InputStream input =
        new BufferedInputStream(
            new GZIPInputStream(
                Files.newInputStream(path)))) {

    byte[] content =
        input.readAllBytes();
}

Classic stream classes are designed for composition: a source/sink stream is wrapped with buffering, compression, checksums, encryption, data conversion, or object framing. Ownership must be clear because closing the outer stream normally closes the wrapped stream.

3. Resource ownership and try-with-resources

Most Java I/O handles implement AutoCloseable or Closeable. Try-with-resources closes resources in reverse declaration order and preserves close failures as suppressed exceptions when the body already failed.[4]

try (InputStream input =
        Files.newInputStream(source);
     OutputStream output =
        Files.newOutputStream(target)) {

    input.transferTo(output);
}

Layered ownership

try (OutputStream file =
        Files.newOutputStream(path);
     BufferedOutputStream buffered =
        new BufferedOutputStream(file);
     DataOutputStream data =
        new DataOutputStream(buffered)) {

    data.writeInt(
        MAGIC);

    data.writeLong(
        recordCount);
}

Declaring every layer is not mandatory when only the outermost object is used and its close contract closes the delegate. Declaring layers separately can improve clarity when each is referenced, but avoid closing a shared underlying stream owned elsewhere.

Do not close borrowed streams

static void writeReport(
        Writer destination,
        Report report)
        throws IOException {

    // Caller owns destination.
    destination.write(
        render(report));

    destination.flush();
}
  • A method that opens a resource should usually close or return ownership explicitly.
  • A method receiving a resource should not close it unless its contract says ownership transfers.
  • Closing System.in, System.out, or shared servlet/framework streams can break unrelated code.

4. Partial progress, EOF, and failure semantics

Many I/O methods can complete partially before failing. A stream or channel may return fewer bytes than requested; channel writes can consume only part of a buffer; a failed copy can leave a partially written target.[5][6]

Read until a fixed record is complete

static byte[] readExactly(
        InputStream input,
        int length)
        throws IOException {

    byte[] result =
        input.readNBytes(length);

    if (result.length != length) {
        throw new EOFException(
            "Expected "
                + length
                + " bytes; received "
                + result.length);
    }

    return result;
}

Channel write loop

static void writeFully(
        WritableByteChannel channel,
        ByteBuffer source)
        throws IOException {

    while (source.hasRemaining()) {
        int written =
            channel.write(source);

        if (written == 0) {
            Thread.onSpinWait();
        }
    }
}

EOF conventions

  • InputStream.read() returns -1 at end of stream.
  • Reader.read() returns -1 at end of character input.
  • Channel reads return -1 at end of stream, possibly 0 when no bytes are transferred.
  • readNBytes(n) can return fewer than n bytes at EOF.
  • EOF in the middle of a framed record is a protocol error, not a normal end condition.

5. InputStream

Byte input InputStream is the abstract superclass for reading byte sequences. Its main operations read one byte, an array region, a bounded number of bytes, all remaining bytes, skip bytes, transfer data, report an estimate of immediately available bytes, and close the stream.[5]

Bounded stream copy

static long copyBounded(
        InputStream input,
        OutputStream output,
        long maximum)
        throws IOException {

    byte[] buffer =
        new byte[16 * 1024];

    long total = 0;

    for (int count;
            (count = input.read(buffer))
                != -1;) {

        total =
            Math.addExact(
                total,
                count);

        if (total > maximum) {
            throw new IOException(
                "Input exceeds "
                    + maximum
                    + " bytes");
        }

        output.write(
            buffer,
            0,
            count);
    }

    return total;
}

available() is not total length

available() estimates bytes readable without blocking. It must not be used to size an entire message or determine EOF; many streams legitimately return zero while more data can arrive later.

Mark and reset

if (input.markSupported()) {
    input.mark(8);

    byte[] signature =
        input.readNBytes(8);

    input.reset();
}

Mark/reset support and read-limit semantics depend on the concrete stream. BufferedInputStream adds mark/reset support even when the wrapped stream lacks it.

6. OutputStream

Byte output OutputStream is the abstract superclass for writing bytes. write(int) writes the low eight bits of its argument; array overloads write byte sequences; flush() pushes buffered output toward the underlying destination; close() releases resources.[7]

try (OutputStream output =
        Files.newOutputStream(
            path,
            StandardOpenOption.CREATE,
            StandardOpenOption.TRUNCATE_EXISTING,
            StandardOpenOption.WRITE)) {

    output.write(
        header);

    output.write(
        payload);

    output.flush();
}

Flush is not physical durability

Flushing a stream ensures buffered data is passed to the underlying stream or operating-system layer according to the implementation. It does not generally guarantee that the data has reached stable physical storage. File durability requires filesystem/channel-specific synchronization and remains subject to operating-system and hardware semantics.[8]

Do not ignore close failures

Buffered, compressed, encrypted, and archive streams can emit final bytes during close. A close failure may indicate incomplete output even when all write calls returned successfully.

7. Buffered byte streams

BufferedInputStream and BufferedOutputStream reduce calls to an underlying stream by staging bytes in memory. Buffering is useful for many small reads/writes, but unnecessary double buffering can waste memory and add copies.[1]

try (InputStream input =
        new BufferedInputStream(
            Files.newInputStream(
                source),
            64 * 1024);
     OutputStream output =
        new BufferedOutputStream(
            Files.newOutputStream(
                target),
            64 * 1024)) {

    input.transferTo(output);
}

Buffer sizing

  • Start with defaults unless profiling shows a bottleneck.
  • Choose sizes that match record sizes and workload, not filesystem block sizes by folklore.
  • Large per-connection buffers multiply across concurrency.
  • Some APIs—such as Files.readAllBytes—already materialize the entire content, making another buffer irrelevant.

8. In-memory byte streams

ByteArrayInputStream reads from an existing byte array without external resources. ByteArrayOutputStream accumulates bytes in a growable memory buffer and can expose a copy with toByteArray() or write its contents to another stream.[1]

static byte[] encodeMessage(
        Message message)
        throws IOException {

    try (ByteArrayOutputStream bytes =
            new ByteArrayOutputStream();
         DataOutputStream output =
            new DataOutputStream(bytes)) {

        output.writeInt(
            1);

        output.writeUTF(
            message.id());

        output.writeInt(
            message.payload().length);

        output.write(
            message.payload());

        output.flush();

        return bytes.toByteArray();
    }
}

Bound growth

ByteArrayOutputStream can grow until memory is exhausted. Do not use it for untrusted or unbounded inputs without enforcing a maximum before accumulation.

9. Primitive binary I/O with data streams

DataInput and DataOutput define binary encodings for Java primitive types and strings. DataInputStream and DataOutputStream implement these interfaces over streams.[9]

Versioned record

static void writeRecord(
        DataOutput output,
        Record record)
        throws IOException {

    byte[] name =
        record.name()
            .getBytes(
                StandardCharsets.UTF_8);

    if (name.length > 65_535) {
        throw new IOException(
            "Name too long");
    }

    output.writeInt(
        0x52454331);

    output.writeShort(
        1);

    output.writeLong(
        record.id());

    output.writeShort(
        name.length);

    output.write(name);
}
static Record readRecord(
        DataInput input)
        throws IOException {

    int magic =
        input.readInt();

    if (magic != 0x52454331) {
        throw new StreamCorruptedException(
            "Bad magic");
    }

    int version =
        input.readUnsignedShort();

    if (version != 1) {
        throw new StreamCorruptedException(
            "Unsupported version");
    }

    long id =
        input.readLong();

    int nameLength =
        input.readUnsignedShort();

    byte[] name =
        new byte[nameLength];

    input.readFully(name);

    return new Record(
        id,
        new String(
            name,
            StandardCharsets.UTF_8));
}

Encoding notes

  • Data streams use defined big-endian encodings for multibyte primitive values.
  • writeUTF/readUTF use modified UTF-8 with a 65,535-byte encoded-length limit; they are not a general UTF-8 file format.
  • Application binary formats still need magic values, versions, limits, checksums/authentication, and compatibility rules.

10. Reader

Character input Reader is the abstract superclass for reading character streams. It exposes single-character, array, CharBuffer, bounded, skip, transfer, readiness, mark/reset, and close operations.[10]

Bounded character read

static String readTextBounded(
        Reader reader,
        int maximumCharacters)
        throws IOException {

    StringBuilder result =
        new StringBuilder(
            Math.min(
                maximumCharacters,
                8_192));

    char[] buffer =
        new char[4_096];

    int total = 0;

    for (int count;
            (count = reader.read(buffer))
                != -1;) {

        total =
            Math.addExact(
                total,
                count);

        if (total
                > maximumCharacters) {
            throw new IOException(
                "Text exceeds character limit");
        }

        result.append(
            buffer,
            0,
            count);
    }

    return result.toString();
}

Characters are not Unicode code points

A Java char is a UTF-16 code unit. Supplementary Unicode characters use surrogate pairs, so character counts and string indices are not necessarily user-perceived character counts.

11. Writer

Character output Writer is the abstract superclass for character output. It supports appending and writing characters, arrays, strings, and CharSequence values, plus flushing and closing.[8]

static void writeCsvRow(
        Writer writer,
        List<String> columns)
        throws IOException {

    for (int index = 0;
            index < columns.size();
            index++) {

        if (index > 0) {
            writer.write(',');
        }

        writer.write(
            escapeCsv(
                columns.get(index)));
    }

    writer.write(
        System.lineSeparator());
}

Text protocols should define line endings explicitly. System.lineSeparator() is appropriate for host-native human files, while wire formats and reproducible build artifacts often require a fixed \n.

12. Bridging bytes and characters

InputStreamReader decodes bytes from an InputStream into characters using a charset. OutputStreamWriter encodes characters into bytes for an OutputStream. These bridges maintain decoder/encoder state across calls, which is necessary for multibyte encodings.[11][12]

Explicit UTF-8

try (Reader reader =
        new BufferedReader(
            new InputStreamReader(
                Files.newInputStream(path),
                StandardCharsets.UTF_8))) {

    process(reader);
}
try (Writer writer =
        new BufferedWriter(
            new OutputStreamWriter(
                Files.newOutputStream(path),
                StandardCharsets.UTF_8))) {

    writer.write(
        content);
}

Never decode chunks independently

// Wrong: a UTF-8 sequence can span reads.
String chunk =
    new String(
        bytes,
        0,
        count,
        StandardCharsets.UTF_8);

Use one reader/decoder over the complete byte stream so incomplete multibyte sequences are retained between input chunks.

13. Buffered text and line-oriented I/O

BufferedReader and BufferedWriter buffer characters. BufferedReader.readLine() removes the line terminator and returns null at EOF. lines() returns a lazily populated stream whose underlying reader must remain open during use.[1]

Read bounded lines

try (BufferedReader reader =
        Files.newBufferedReader(
            path,
            StandardCharsets.UTF_8)) {

    for (String line;
            (line = reader.readLine())
                != null;) {

        if (line.length()
                > MAX_LINE_CHARS) {
            throw new IOException(
                "Line too long");
        }

        processLine(line);
    }
}

Write lines

try (BufferedWriter writer =
        Files.newBufferedWriter(
            path,
            StandardCharsets.UTF_8,
            StandardOpenOption.CREATE,
            StandardOpenOption.TRUNCATE_EXISTING)) {

    for (String line : lines) {
        writer.write(line);
        writer.newLine();
    }
}
readLine() has no built-in line-length bound. A hostile file can force very large allocation before the application validates the returned string. Use a bounded parser/reader when line size is a security boundary.

14. PrintWriter and formatted text

PrintWriter provides formatted text output and optional automatic flushing. Unlike most writers, its printing methods do not throw IOException; they record an internal error state that callers must test with checkError().[1]

try (PrintWriter writer =
        new PrintWriter(
            Files.newBufferedWriter(
                path,
                StandardCharsets.UTF_8))) {

    writer.printf(
        Locale.ROOT,
        "%s,%d,%.2f%n",
        product.sku(),
        product.quantity(),
        product.price());

    if (writer.checkError()) {
        throw new IOException(
            "Failed to write report");
    }
}

Choose deliberately

Use PrintWriter for convenient human-readable formatting when checked error propagation is not essential or is explicitly checked. Use Writer/BufferedWriter directly when failures must immediately propagate as IOException.

15. Charsets, malformed input, and unmappable output

The java.nio.charset package defines named charsets, decoders, encoders, error results, and actions for malformed byte sequences or unmappable characters.[13]

Strict UTF-8 decoder

CharsetDecoder decoder =
    StandardCharsets.UTF_8
        .newDecoder()
        .onMalformedInput(
            CodingErrorAction.REPORT)
        .onUnmappableCharacter(
            CodingErrorAction.REPORT);

try (Reader reader =
        new InputStreamReader(
            Files.newInputStream(path),
            decoder)) {

    process(reader);
}

Strict encoder

CharsetEncoder encoder =
    StandardCharsets.US_ASCII
        .newEncoder()
        .onMalformedInput(
            CodingErrorAction.REPORT)
        .onUnmappableCharacter(
            CodingErrorAction.REPORT);

try (Writer writer =
        new OutputStreamWriter(
            Files.newOutputStream(path),
            encoder)) {

    writer.write(content);
}

Default convenience decoding can replace malformed input rather than rejecting it, depending on API and decoder configuration. For signed, parsed, canonical, or security-sensitive text, choose and test an explicit error policy.[14][15]

16. NIO and NIO.2

NIO Java NIO defines buffers, channels, charsets, selectors, asynchronous channels, and related abstractions. NIO.2 adds provider-based file-system access through Path, Files, file attributes, traversal, and watch services.[2][16]

Streams versus channels

StreamsChannels
Sequential byte or character abstractionByte transfer through explicit buffers
Usually one direction per objectCan be read-only, write-only, or bidirectional
Natural decorator compositionSeek, positional I/O, scatter/gather, mapping, selectors
Simple blocking loopsBlocking, non-blocking, or asynchronous depending on channel type

NIO does not automatically mean non-blocking. FileChannel operations are generally blocking; network channels can be configured non-blocking and registered with selectors.

17. Path

Filesystem path Path represents a path in a specific FileSystem. It exposes name elements, roots, parents, resolution, relativization, normalization, comparison, conversion, and watch registration. A Path is not proof that the referenced file exists.[17]

Path relative =
    Path.of(
        "var",
        "data",
        "orders.json");

Path absolute =
    relative.toAbsolutePath()
        .normalize();

Path parent =
    absolute.getParent();

Path sibling =
    absolute.resolveSibling(
        "orders.backup.json");

Resolve and relativize

Path root =
    Path.of(
        "/srv/application");

Path configuration =
    root.resolve(
        "config/application.yaml");

Path relativeToRoot =
    root.relativize(
        configuration);

Paths from different providers generally cannot be resolved or relativized together. String separators, roots, case sensitivity, and validity are file-system/provider dependent.

18. Path normalization and containment

Lexical normalization removes redundant . elements and resolves .. where possible, but it does not access the filesystem and does not resolve symbolic links. toRealPath resolves an existing path under provider rules and, by default, follows symbolic links.[17]

Lexical containment

static Path resolveUnderRoot(
        Path root,
        String userName) {

    Path normalizedRoot =
        root.toAbsolutePath()
            .normalize();

    Path candidate =
        normalizedRoot.resolve(
                userName)
            .normalize();

    if (!candidate.startsWith(
            normalizedRoot)) {
        throw new SecurityException(
            "Path escapes root");
    }

    return candidate;
}

This prevents straightforward lexical traversal but does not defeat a symbolic-link race or mount/reparse-point change between validation and use.

Existing-path containment

Path realRoot =
    root.toRealPath();

Path realCandidate =
    candidate.toRealPath();

if (!realCandidate.startsWith(
        realRoot)) {
    throw new SecurityException(
        "Resolved file escapes root");
}

High-assurance design

  • Use operating-system sandboxing and directory permissions as the primary boundary.
  • Do not allow attackers to modify directories traversed during validation/use.
  • Use provider/platform APIs with directory-relative handles when available through specialized libraries.
  • Specify whether symbolic links are accepted, rejected, or treated as leaf objects.
  • Avoid using filenames as authorization identities.

19. The Files utility class

Files provides static operations for opening streams/channels, creating and deleting files/directories, copying and moving, reading/writing content, inspecting and modifying attributes, traversing trees, and comparing file content.[18]

Path directory =
    Files.createDirectories(
        Path.of(
            "var",
            "data"));

Path file =
    directory.resolve(
        "orders.bin");

boolean exists =
    Files.exists(
        file);

long size =
    Files.size(
        file);

FileTime modified =
    Files.getLastModifiedTime(
        file);

Avoid check-then-act races

// Racy:
if (!Files.exists(path)) {
    Files.createFile(path);
}

// Atomic create-if-absent request:
try {
    Files.createFile(path);
} catch (FileAlreadyExistsException exists) {
    // Handle existing file.
}

Existence tests can be immediately stale. Prefer the operation itself and handle its defined exceptions.

20. Convenience methods for text and bytes

String configuration =
    Files.readString(
        path,
        StandardCharsets.UTF_8);

Files.writeString(
    target,
    configuration,
    StandardCharsets.UTF_8,
    StandardOpenOption.CREATE,
    StandardOpenOption.TRUNCATE_EXISTING);
byte[] content =
    Files.readAllBytes(path);

    target,

    StandardOpenOption.CREATE_NEW);

Use whole-file methods only for bounded content

readAllBytes, readString, and readAllLines materialize content in memory. Check file metadata where useful, but still enforce a streaming limit because metadata can be stale, misleading, compressed, sparse, or changed concurrently.

Lazy lines

try (Stream<String> lines =
        Files.lines(
            path,
            StandardCharsets.UTF_8)) {

    long errors =
        lines.filter(
                line ->
                    line.startsWith(
                        "ERROR"))
            .count();
}

The stream owns an open file resource and must be closed.

21. Copy, move, and atomic replacement

Files.copy(
    source,
    target,
    StandardCopyOption
        .REPLACE_EXISTING,
    StandardCopyOption
        .COPY_ATTRIBUTES);

Copying a directory creates an empty target directory; it does not recursively copy entries. Attribute-copy support and precision are provider dependent.[18]

Atomic publish pattern

static void replaceAtomically(
        Path target,
        byte[] content)
        throws IOException {

    Path directory =
        target.toAbsolutePath()
            .getParent();

    Files.createDirectories(
        directory);

    Path temporary =
        Files.createTempFile(
            directory,
            target.getFileName()
                .toString(),
            ".tmp");

    boolean moved = false;

    try {
        try (FileChannel channel =
                FileChannel.open(
                    temporary,
                    StandardOpenOption.WRITE,
                    StandardOpenOption
                        .TRUNCATE_EXISTING)) {

            ByteBuffer buffer =
                ByteBuffer.wrap(content);

            while (buffer.hasRemaining()) {
                channel.write(buffer);
            }

            channel.force(true);
        }

        Files.move(
            temporary,
            target,
            StandardCopyOption
                .ATOMIC_MOVE,
            StandardCopyOption
                .REPLACE_EXISTING);

        moved = true;
    } catch (AtomicMoveNotSupportedException unsupported) {
        Files.move(
            temporary,
            target,
            StandardCopyOption
                .REPLACE_EXISTING);

        moved = true;
    } finally {
        if (!moved) {
            Files.deleteIfExists(
                temporary);
        }
    }
}

ATOMIC_MOVE requests an atomic filesystem move; support depends on source/target provider and filesystem. Atomic replacement does not automatically guarantee crash durability of directory metadata.

22. Directory iteration and file-tree traversal

Directory stream

try (DirectoryStream<Path> entries =
        Files.newDirectoryStream(
            directory,
            "*.csv")) {

    for (Path entry : entries) {
        process(entry);
    }
}

DirectoryStream is resource-backed and must be closed. It is useful when a directory can contain many entries and a materialized list is undesirable.

Walk a tree

Files.walkFileTree(
    root,
    new SimpleFileVisitor<>() {
        @Override
        public FileVisitResult visitFile(
                Path file,
                BasicFileAttributes attributes)
                throws IOException {

            if (attributes.isRegularFile()) {
                process(file, attributes);
            }

            return FileVisitResult.CONTINUE;
        }

        @Override
        public FileVisitResult visitFileFailed(
                Path file,
                IOException failure)
                throws IOException {

            failures.record(
                file,
                failure);

            return FileVisitResult.CONTINUE;
        }
    });

By default, walkFileTree does not follow symbolic links and visits all levels. Following links requires explicit FOLLOW_LINKS and introduces cycle/race concerns.[18]

Delete a tree bottom-up

Files.walkFileTree(
    root,
    new SimpleFileVisitor<>() {
        @Override
        public FileVisitResult visitFile(
                Path file,
                BasicFileAttributes attributes)
                throws IOException {

            Files.delete(file);
            return FileVisitResult.CONTINUE;
        }

        @Override
        public FileVisitResult postVisitDirectory(
                Path directory,
                IOException failure)
                throws IOException {

            if (failure != null) {
                throw failure;
            }

            Files.delete(directory);
            return FileVisitResult.CONTINUE;
        }
    });

23. File attributes

The file-attribute APIs expose basic, POSIX, DOS, owner, ACL, user-defined, and provider-specific views. Supported views vary by file store.[19]

BasicFileAttributes attributes =
    Files.readAttributes(
        path,
        BasicFileAttributes.class,
        LinkOption.NOFOLLOW_LINKS);

System.out.printf(
    "size=%d directory=%s symlink=%s modified=%s key=%s%n",
    attributes.size(),
    attributes.isDirectory(),
    attributes.isSymbolicLink(),
    attributes.lastModifiedTime(),
    attributes.fileKey());

POSIX permissions

Set<PosixFilePermission> permissions =
    PosixFilePermissions.fromString(
        "rw-------");

FileAttribute<
    Set<PosixFilePermission>> attribute =
        PosixFilePermissions
            .asFileAttribute(
                permissions);

Path secret =
    Files.createFile(
        path,
        attribute);

Creation attributes can be applied atomically where the provider supports them, avoiding a window where a sensitive file exists with broader default permissions.

24. Symbolic links and hard links

Most Files operations follow symbolic links by default. LinkOption.NOFOLLOW_LINKS requests operations on the link itself where supported. Deleting or moving a symbolic link affects the link entry, not its target.[3]

if (Files.isSymbolicLink(path)) {
    Path target =
        Files.readSymbolicLink(
            path);

    System.out.println(target);
}
Path symbolic =
    Files.createSymbolicLink(
        link,
        target);

Path hard =
    Files.createLink(
        hardLink,
        existingFile);

Security questions

  • Should traversal follow links?
  • Can an attacker replace an ancestor with a link?
  • Are link targets allowed outside the root?
  • Does deletion operate on the link or target?
  • Can hard links expose the same file through another authorized path?

Path temporaryDirectory =
    Files.createTempDirectory(
        "import-");

Path temporaryFile =
    Files.createTempFile(
        temporaryDirectory,
        "payload-",
        ".bin");

try {
    processTemporaryFile(
        temporaryFile);
} finally {
    Files.deleteIfExists(
        temporaryFile);

    Files.deleteIfExists(
        temporaryDirectory);
}

Security guidance

  • Let the platform generate unpredictable names; do not probe random names manually.
  • Create temporary files in a controlled directory with appropriate permissions.
  • Do not assume deleteOnExit is timely, bounded, or suitable for long-running services.
  • Clean up after partial failure.
  • Do not expose temporary paths to untrusted clients unless required.

26. Watching directories

WatchService allows a directory to register for create, delete, modify, and overflow events. Events are hints and can be coalesced, duplicated, or lost; OVERFLOW signals that events may have been discarded.[17]

try (WatchService watcher =
        FileSystems.getDefault()
            .newWatchService()) {

    directory.register(
        watcher,
        StandardWatchEventKinds
            .ENTRY_CREATE,
        StandardWatchEventKinds
            .ENTRY_MODIFY,
        StandardWatchEventKinds
            .ENTRY_DELETE);

    while (!Thread.currentThread()
            .isInterrupted()) {

        WatchKey key =
            watcher.take();

        for (WatchEvent<?> event
                : key.pollEvents()) {

            if (event.kind()
                    == StandardWatchEventKinds
                        .OVERFLOW) {

                rescan(directory);
                continue;
            }

            Path name =
                (Path) event.context();

            handle(
                event.kind(),
                directory.resolve(name));
        }

        if (!key.reset()) {
            break;
        }
    }
}

Watch services are not a durable event log. Reconcile against actual filesystem state after startup, overflow, errors, and periodically when correctness matters.

27. Channels

Channels A channel is a connection to an entity capable of I/O. Readable channels transfer bytes into buffers; writable channels transfer bytes from buffers. Seekable channels add position, size, and truncation; scattering/gathering channels operate on buffer arrays.[6]

try (ReadableByteChannel input =
        Channels.newChannel(
            Files.newInputStream(source));
     WritableByteChannel output =
        Channels.newChannel(
            Files.newOutputStream(target))) {

    ByteBuffer buffer =
        ByteBuffer.allocate(
            32 * 1024);

    while (input.read(buffer) != -1) {
        buffer.flip();

        while (buffer.hasRemaining()) {
            output.write(buffer);
        }

        buffer.clear();
    }
}

Channels adapts streams to channels and channels to streams/readers/writers. Adapters do not erase the underlying blocking behavior or ownership semantics.

28. FileChannel

FileChannel is a seekable channel for reading, writing, mapping, locking, forcing, truncating, querying size, and transferring file data. It can be opened directly or obtained from file streams and RandomAccessFile.[20]

try (FileChannel channel =
        FileChannel.open(
            path,
            StandardOpenOption.READ,
            StandardOpenOption.WRITE,
            StandardOpenOption.CREATE)) {

    ByteBuffer header =
        ByteBuffer.allocate(
            16);

    int count =
        channel.read(header);

    if (count == -1) {
        return;
    }

    header.flip();
    parseHeader(header);
}

Shared position

Relative reads and writes use and update the channel's current position. Concurrent operations that share that position require coordination. Positional operations avoid changing the shared position.

Interruption

FileChannel is interruptible. Interrupting a thread blocked in a channel operation can close the channel and throw ClosedByInterruptException, affecting other users of the same channel.

29. Positional and random-access I/O

static ByteBuffer readBlock(
        FileChannel channel,
        long position,
        int length)
        throws IOException {

    ByteBuffer buffer =
        ByteBuffer.allocate(length);

    long offset = position;

    while (buffer.hasRemaining()) {
        int count =
            channel.read(
                buffer,
                offset);

        if (count == -1) {
            break;
        }

        if (count == 0) {
            continue;
        }

        offset += count;
    }

    buffer.flip();
    return buffer;
}

Positional read(buffer, position) and write(buffer, position) do not modify the channel's current position. Multiple positional operations can proceed concurrently subject to channel/provider/filesystem behavior and application record consistency.[20]

Do not mix append and positional writes

The effect of positional writes on a channel opened in append mode is unspecified. Use one deliberate access model.

30. Scattering reads and gathering writes

ByteBuffer header =
    ByteBuffer.allocate(
        HEADER_SIZE);

ByteBuffer payload =
    ByteBuffer.allocate(
        payloadLength);

long count =
    channel.read(
        new ByteBuffer[] {
            header,
            payload
        });
ByteBuffer header =
    encodeHeader(record);

ByteBuffer payload =
    ByteBuffer.wrap(
        record.payload());

while (header.hasRemaining()
        || payload.hasRemaining()) {

    channel.write(
        new ByteBuffer[] {
            header,
            payload
        });
}

Scattering distributes sequential file bytes across buffers in order; gathering consumes remaining bytes from buffers in order. One call can still transfer fewer bytes than the aggregate remaining amount.[21]

31. Channel-to-channel transfer

static void copy(
        FileChannel source,
        FileChannel target)
        throws IOException {

    long position = 0;
    long size =
        source.size();

    while (position < size) {
        long transferred =
            source.transferTo(
                position,
                size - position,
                target);

        if (transferred == 0) {
            break;
        }

        position += transferred;
    }

    if (position != size) {
        source.position(position);

        ByteBuffer buffer =
            ByteBuffer.allocateDirect(
                64 * 1024);

        while (source.read(buffer) != -1) {
            buffer.flip();
            writeFully(target, buffer);
            buffer.clear();
        }
    }
}

transferTo and transferFrom can use efficient platform transfer paths, but a call is not guaranteed to move the entire requested range. Loop and provide a fallback when zero progress is possible.

32. File size, truncation, forcing, and durability

try (FileChannel channel =
        FileChannel.open(
            path,
            StandardOpenOption.WRITE)) {

    channel.truncate(
        desiredSize);

    channel.force(true);
}

truncate(size) reduces a file if it is larger and leaves it unchanged if smaller. force(metadata) requests that file-content updates—and optionally metadata updates—be forced to the storage device. Guarantees remain dependent on the operating system, filesystem, storage stack, and device.[20]

Crash-consistent replacement

  1. Write a temporary file in the same target directory/filesystem.
  2. Force the temporary file's contents.
  3. Atomically move it over the target if supported.
  4. On systems requiring stronger guarantees, force the containing directory using platform-specific facilities.
  5. Design recovery for old, new, or temporary states.
Atomic visibility and durable persistence are different properties. An atomic rename can prevent readers from seeing a half-written file while still not guaranteeing survival after sudden power loss.

33. File locks

FileChannel.lock and tryLock acquire a lock on all or part of a file and return FileLock. Locks can be shared or exclusive where supported. They are ultimately operating-system facilities and are advisory on many systems.[20]

try (FileChannel channel =
        FileChannel.open(
            path,
            StandardOpenOption.READ,
            StandardOpenOption.WRITE);
     FileLock lock =
        channel.lock()) {

    updateFile(channel);
}

Cautions

  • Not every filesystem supports shared locks as requested.
  • Locks held by the same JVM can overlap only under defined restrictions; overlapping requests can throw OverlappingFileLockException.
  • Closing the channel releases its locks.
  • Locks do not protect against programs that ignore advisory locking.
  • Network filesystems can have different reliability and failure semantics.

34. Memory-mapped files

FileChannel.map maps a file region into a MappedByteBuffer, a direct buffer whose bytes correspond to file content. The mapping remains valid until the buffer becomes unreachable and is reclaimed.[22]

try (FileChannel channel =
        FileChannel.open(
            path,
            StandardOpenOption.READ)) {

    long size =
        channel.size();

    if (size > Integer.MAX_VALUE) {
        throw new IOException(
            "Map in smaller windows");
    }

    MappedByteBuffer mapped =
        channel.map(
            FileChannel.MapMode.READ_ONLY,
            0,
            size);

    int magic =
        mapped.getInt();
}

Mapped-I/O hazards

  • Mapping lifetime is not lexical and there is no standard deterministic unmap operation.
  • Truncating or replacing a mapped file can make regions inaccessible and produce unspecified exceptions.
  • Changes by another process may become visible at unspecified times.
  • Mapping consumes virtual address space and native-memory bookkeeping.
  • force() requests propagation of modified mapped pages but is not a universal transactional guarantee.

Use mapping for measured workloads such as large random-access indexes, not as a reflexive replacement for ordinary buffered I/O.

35. ByteBuffer

Buffer ByteBuffer is a finite sequence of bytes with a fixed capacity, mutable position and limit, optional mark, byte order, relative/absolute access, bulk operations, primitive accessors, slicing, duplication, compaction, and typed views.[23]

ByteBuffer buffer =
    ByteBuffer.allocate(
        1_024);

buffer.putInt(
    0x4A494F31);

buffer.putLong(
    recordId);

buffer.put(
    payload);

buffer.flip();

int magic =
    buffer.getInt();

long id =
    buffer.getLong();

byte[] remaining =
    new byte[
        buffer.remaining()];

buffer.get(remaining);

Relative versus absolute

byte next =
    buffer.get();
// Advances position.

byte first =
    buffer.get(0);
// Does not alter position.

Slices and duplicates share content

ByteBuffer header =
    buffer.slice(
        0,
        HEADER_SIZE);

ByteBuffer payload =
    buffer.slice(
        HEADER_SIZE,
        buffer.limit()
            - HEADER_SIZE);

A slice or duplicate has independent position/limit/mark state but shares underlying content. Mutation through one view is visible through the others.

36. Buffer state transitions

new / clear() position = 0 limit = capacity │ put / channel.read ▼ filled region: [0, position) │ flip() ▼ position = 0 limit = old position │ get / channel.write ▼ remaining unread bytes ├─ clear(): discard them └─ compact(): move them to front

Standard blocking loop

ByteBuffer buffer =
    ByteBuffer.allocate(
        16 * 1024);

while (channel.read(buffer) != -1) {
    buffer.flip();

    parseCompleteRecords(buffer);

    buffer.compact();
}

buffer.flip();
parseFinalRecords(buffer);

if (buffer.hasRemaining()) {
    throw new EOFException(
        "Truncated final record");
}

clear does not erase data

clear() resets position and limit for writing; it does not zero the underlying bytes. rewind() resets position to zero while keeping the limit. compact() preserves unread bytes and places the position after them.[24]

Secrets

Clearing buffer state does not remove secrets. Overwrite sensitive content where practical and understand that copies can remain in heap/native memory, caches, OS buffers, crash dumps, and storage.

37. Byte order and typed views

ByteBuffer translates primitive values according to its current ByteOrder. New buffers default to big-endian order. Application binary formats must specify byte order explicitly.[23]

ByteBuffer littleEndian =
    ByteBuffer.allocate(16)
        .order(
            ByteOrder.LITTLE_ENDIAN);

littleEndian.putInt(
    0x01020304);

littleEndian.flip();

int value =
    littleEndian.getInt();

Typed view

ByteBuffer bytes =
    ByteBuffer.allocateDirect(
            4 * 1_024)
        .order(
            ByteOrder.nativeOrder());

IntBuffer integers =
    bytes.asIntBuffer();

for (int index = 0;
        index < integers.capacity();
        index++) {

    integers.put(
        index,
        index * 2);
}

A typed view interprets shared bytes as another primitive type. Its position/limit are measured in that primitive type and are independent of the original byte buffer's position.

38. Heap and direct buffers

A non-direct buffer is backed by ordinary Java heap storage, often an array. A direct buffer is allocated outside the normal garbage-collected heap, and the JVM makes a best effort to perform native I/O directly on it without an intermediate copy. Direct buffers usually cost more to allocate and reclaim.[23]

ByteBuffer heap =
    ByteBuffer.allocate(
        64 * 1024);

ByteBuffer direct =
    ByteBuffer.allocateDirect(
        64 * 1024);

System.out.println(
    heap.isDirect());

System.out.println(
    direct.isDirect());

Selection

  • Use heap buffers for ordinary short-lived application transformations and easy array access.
  • Consider reusable direct buffers for measured channel-I/O hot paths.
  • Bound direct-buffer pooling; direct memory contributes to process footprint outside -Xmx.
  • Do not allocate a new large direct buffer per request.
  • Benchmark the complete pipeline, including copies and allocation lifetime.

39. Designing a versioned binary file format

fixed header ┌─────────┬─────────┬─────────┬──────────────┐ │ magic │ version │ flags │ record count │ └─────────┴─────────┴─────────┴──────────────┘ records ┌─────────┬──────────────┬─────────────┬──────┐ │ type │ payload len │ payload │ CRC │ └─────────┴──────────────┴─────────────┴──────┘
public final class RecordFile {
    private static final int MAGIC =
        0x52464331;

    private static final short VERSION =
        1;

    public static void write(
            Path path,
            List<Record> records)
            throws IOException {

        try (FileChannel channel =
                FileChannel.open(
                    path,
                    StandardOpenOption.CREATE_NEW,
                    StandardOpenOption.WRITE)) {

            ByteBuffer header =
                ByteBuffer.allocate(16)
                    .order(
                        ByteOrder.BIG_ENDIAN);

            header.putInt(MAGIC);
            header.putShort(VERSION);
            header.putShort((short) 0);
            header.putLong(
                records.size());
            header.flip();

            writeFully(
                channel,
                header);

            for (Record record : records) {
                writeRecord(
                    channel,
                    record);
            }

            channel.force(true);
        }
    }
}

Format requirements

  • Magic identifier and explicit version.
  • Defined byte order and character encoding.
  • Maximum file, record, string, collection, and nesting sizes.
  • Forward-compatible unknown-record/field rules.
  • Checksums for corruption detection or cryptographic authentication for adversarial modification.
  • Atomic publication and recovery semantics.
  • Test vectors independent of the implementation.

40. Java object serialization

Serialization Java Object Serialization encodes primitive values and graphs of objects into a byte stream. ObjectOutputStream writes class descriptors, serializable field state, arrays, strings, and shared references; ObjectInputStream reconstructs the graph using classes available in the receiving JVM.[25][26]

Deserialization of untrusted data is inherently dangerous and should be avoided. Native serialization can instantiate classes, invoke serialization callbacks, allocate deep/large graphs, and exercise code paths not designed as an input protocol. Filtering reduces risk but does not turn arbitrary native serialization into a safe public format.[27]

Object graph semantics

try (ObjectOutputStream output =
        new ObjectOutputStream(
            Files.newOutputStream(path))) {

    output.writeObject(
        object);
}

try (ObjectInputStream input =
        new ObjectInputStream(
            Files.newInputStream(path))) {

    Object restored =
        input.readObject();
}

Only values whose classes implement Serializable or Externalizable can be serialized, except that non-serializable superclass state is initialized through its accessible no-argument constructor under the serialization rules.[28]

41. A serializable class

public final class UserPreferences
        implements Serializable {

    @Serial
    private static final long serialVersionUID =
        1L;

    private final String theme;
    private final int pageSize;

    public UserPreferences(
            String theme,
            int pageSize) {

        this.theme =
            Objects.requireNonNull(theme);

        if (pageSize < 1
                || pageSize > 1_000) {
            throw new IllegalArgumentException();
        }

        this.pageSize = pageSize;
    }

    public String theme() {
        return theme;
    }

    public int pageSize() {
        return pageSize;
    }
}

Round trip

static byte[] serialize(
        Serializable value)
        throws IOException {

    try (ByteArrayOutputStream bytes =
            new ByteArrayOutputStream();
         ObjectOutputStream output =
            new ObjectOutputStream(bytes)) {

        output.writeObject(value);
        output.flush();

        return bytes.toByteArray();
    }
}

The @Serial annotation lets compilers check declarations that participate in the serialization mechanism, including serialVersionUID and custom callback methods.[29]

42. serialVersionUID and class evolution

Serialization uses a stream class descriptor and serial-version UID to determine compatibility between the writer's and reader's class versions. If a serializable class does not declare an explicit UID, one is computed from structural details and can change unexpectedly when the class evolves.[30]

@Serial
private static final long serialVersionUID =
    3L;

Compatible and incompatible evolution

  • Adding fields can be compatible; missing fields receive default values.
  • Removing fields can be compatible for readers that no longer require them.
  • Changing field types, hierarchy, or serialization contract can be incompatible.
  • Compatibility of the stream does not guarantee semantic validity of the object.
  • Long-lived persisted data requires explicit migration/version tests.

Use serialver for legacy classes

serialver \
  -classpath build/classes/java/main \
  com.example.UserPreferences

For new durable formats, prefer explicit schemas and application-level versioning over relying on Java class evolution rules.

43. Custom serialization callbacks

A serializable class can define precisely named private writeObject, readObject, and readObjectNoData methods. Deserialization bypasses ordinary serializable-class constructors, so readObject must re-establish invariants and reject invalid state.[26]

public final class ApiCredential
        implements Serializable {

    @Serial
    private static final long serialVersionUID =
        1L;

    private String keyId;

    private transient SecretKey secretKey;

    private void writeObject(
            ObjectOutputStream output)
            throws IOException {

        throw new NotSerializableException(
            "Credentials must not be serialized");
    }

    private void readObject(
            ObjectInputStream input)
            throws IOException {

        throw new InvalidObjectException(
            "Credentials must not be deserialized");
    }
}

Validated custom read

@Serial
private void readObject(
        ObjectInputStream input)
        throws IOException,
               ClassNotFoundException {

    input.defaultReadObject();

    if (theme == null
            || pageSize < 1
            || pageSize > 1_000) {

        throw new InvalidObjectException(
            "Invalid preferences");
    }
}

transient

Static and transient fields are omitted by default serialization. transient is not encryption: secrets reachable through other non-transient fields can still be serialized, and previously serialized copies remain.

44. Serialization of records and enums

Serializable records are deserialized through their canonical constructor, which provides a natural place for component validation. Several ordinary serialization callbacks are ignored for records. Enum constants are serialized by name and have special fixed serialization behavior.[26]

public record PageSettings(
        String theme,
        int pageSize)
        implements Serializable {

    @Serial
    private static final long serialVersionUID =
        1L;

    public PageSettings {
        Objects.requireNonNull(theme);

        if (pageSize < 1
                || pageSize > 1_000) {
            throw new IllegalArgumentException();
        }
    }
}

Enums

enum Mode
        implements Serializable {
    DEVELOPMENT,
    PRODUCTION
}

Renaming an enum constant breaks streams containing its former name. Treat serialized enum names as persisted schema values.

45. Object graphs, identity handles, and stream reset

Object streams preserve sharing and cycles by assigning handles to objects already written. Writing the same object reference again normally writes a back-reference rather than a fresh snapshot.[31]

MutableState state =
    new MutableState();

output.writeObject(state);

state.update();

output.writeObject(state);
// Usually writes a back-reference,
// not a second updated copy.

Reset or unshared values

output.writeObject(state);
output.reset();
output.writeObject(state);

reset() clears object-handle state so subsequent objects are written anew. It can also prevent the output stream from retaining every object ever written in a long-lived stream.

Do not build indefinite object streams

Long-lived object streams retain handles, couple sender and receiver class paths, complicate recovery after corruption, and create framing/versioning problems. Use bounded messages with explicit schemas for durable queues and network protocols.

46. Deserialization filters

Java serialization filters can inspect classes and graph metrics before objects are created. Filters can limit allowed classes/modules, array length, graph depth, reference count, and stream bytes. Filtering is not enabled unless configured globally, selected by a filter factory, or set on an input stream.[32][33]

Stream-specific allowlist

ObjectInputFilter filter =
    ObjectInputFilter.Config.createFilter(
        "maxdepth=10;"
            + "maxrefs=1000;"
            + "maxbytes=1048576;"
            + "java.base/*;"
            + "com.example.dto.*;"
            + "!*");

try (ObjectInputStream input =
        new ObjectInputStream(
            Files.newInputStream(path))) {

    input.setObjectInputFilter(
        filter);

    Object value =
        input.readObject();

    if (!(value
            instanceof TransferDocument document)) {

        throw new InvalidObjectException(
            "Unexpected root type");
    }

    validate(document);
}

JVM-wide pattern

java \
  -Djdk.serialFilter=\
maxarray=100000\;maxdepth=20\;maxrefs=5000\;maxbytes=10485760\;!* \
  -jar application.jar

Filter limitations

  • A filter does not validate business invariants.
  • Allowed classes can still contain dangerous callbacks or huge data within permitted limits.
  • Filters must be tested with every expected graph and rejection case.
  • A stream-specific filter should be composed with applicable JVM-wide policy under the configured filter-factory rules.
  • Reject-by-default allowlists are safer than broad package acceptance.

JEP 290 introduced serialization filtering in Java 9; JEP 415 added context-specific filter-factory selection in Java 17.[34][35]

Fault-oriented cases

  • Truncated header, payload, multibyte text, and serialized stream.

  • Malformed and unmappable charset input.
  • Partial channel writes through a test channel wrapper.
  • Permission denied, read-only filesystem, full disk/quota, and file already exists.

Partial-write test channel

final class ChunkedChannel
        implements WritableByteChannel {

    private final ByteArrayOutputStream output =
        new ByteArrayOutputStream();

    private final int maximumChunk;
    private boolean open = true;

    ChunkedChannel(int maximumChunk) {
        this.maximumChunk =
            maximumChunk;
    }

    @Override
    public int write(
            ByteBuffer source) {

        int count =
            Math.min(
                source.remaining(),
                maximumChunk);

        byte[] bytes =
            new byte[count];

        source.get(bytes);
        output.writeBytes(bytes);

        return count;
    }

    @Override
    public boolean isOpen() {
        return open;
    }

    @Override
    public void close() {
        open = false;
    }
}

49. I/O performance engineering

Measure the full path

  • System calls, page cache, storage latency, compression, encryption, decoding, parsing, allocation, and downstream processing.
  • Throughput, p95/p99 latency, bytes per operation, CPU, allocation rate, direct memory, file descriptors, and queueing.
  • Cold-cache and warm-cache behavior.

Common improvements

  • Use buffered streams/readers for many small operations.
  • Batch records and gather writes when protocol permits.
  • Stream bounded data rather than materializing entire files.
  • Use transferTo/transferFrom for measured bulk-copy paths.
  • Reuse direct buffers only when native-I/O profiling justifies them.
  • Use memory mapping for measured random-access workloads with controlled file lifecycle.
  • Reduce duplicate encoding/decoding and byte-array copies.

Concurrency

More concurrent I/O can improve device/network utilization until queues, descriptors, memory bandwidth, storage IOPS, or downstream systems saturate. Bound concurrency and measure queue wait. Virtual threads simplify blocking I/O concurrency but do not create more storage bandwidth.

Observability

java \

filename=io.jfr,dumponexit=true \
  -jar application.jar

  --events \

51. Production I/O checklist

Representation

  • Binary and text data are not confused.
  • Text charset and coding-error policy are explicit.
  • Binary formats specify byte order, version, lengths, and limits.
  • Wire and durable formats are documented independently of code.

Resources and failure

  • Every opened resource has one owner and deterministic close path.
  • Partial reads/writes and mid-record EOF are handled.
  • Close/flush failures are observed.
  • Whole-file operations are used only for bounded content.
  • Cancellation and interruption behavior is tested.

Filesystem

  • Path/Files replace legacy File for new code.
  • Check-then-act races are avoided.
  • Root containment and symbolic-link policy are explicit.
  • Sensitive files receive restrictive creation attributes.
  • Atomic replacement and durability requirements are distinguished.
  • Temporary files are unpredictable, controlled, and cleaned up.
  • Watch events are reconciled with actual state.

Channels and buffers

  • Channel loops handle partial progress.
  • Buffer flip/compact/clear transitions are correct.
  • Shared channel positions are synchronized or avoided with positional I/O.
  • Direct and mapped memory is included in the process-memory budget.
  • Mapped-file lifetime and concurrent modification are controlled.
  • File-lock portability assumptions are tested.

Serialization

  • Native serialization is not accepted from untrusted clients.
  • Legacy deserialization has reject-by-default filters and graph limits.
  • Root type and business invariants are validated after reading.
  • serialVersionUID and evolution tests exist.
  • Secrets and runtime resources are excluded.
  • New long-lived formats use explicit schemas instead.

Operations

  • File descriptor, direct-memory, I/O latency, bytes, and errors are monitored.
  • Storage-full, permission, filesystem, and crash-recovery cases are rehearsed.
  • Tests run on supported operating systems and filesystems.
  • Performance decisions are based on end-to-end profiling.
Final principle: Java I/O APIs provide transfer mechanisms, not a complete storage protocol. Correct systems make ownership, encoding, framing, size, path trust, atomic visibility, durability, compatibility, and recovery explicit.
