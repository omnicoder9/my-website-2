1. A temporal model before an API type

A date, a wall-clock time, a local date-time, an offset date-time, a regional zoned date-time, and an instant answer different questions. Correct code begins by deciding whether the domain describes a calendar value, a point on the global time-line, or an amount between values.

Calendar value

“The invoice is due on 2026-08-31” or “the store opens at 09:00.” No global instant is implied.

Local appointment

“The meeting is at 09:00 in New York.” A region zone is required to map it to an instant.

Timeline event

“The message was accepted at this exact moment.” Store an Instant or equivalent offset timestamp.

Amount

“Wait 30 seconds” is a Duration; “bill one month later” is a Period or calendar operation.

The java.time package provides immutable ISO-calendar dates and times, instants, offsets, regional zones, clocks, durations, and periods. Supporting packages provide formatting/parsing, temporal fields/units/adjusters, alternate chronologies, and zone rules.[1]

Do not use LocalDateTime as a universal timestamp. It contains no offset or zone and therefore may identify zero, one, or two instants in a regional time zone.

3. Immutability, value semantics, and thread safety

The principal java.time types are immutable and thread-safe. Arithmetic and adjustment methods return new values rather than mutating existing instances. They are value-based classes: equal instances should be treated as interchangeable, and their object identity should not be used for synchronization.[2][3][4]

LocalDate original =
    LocalDate.of(
        2026,
        Month.JULY,
        30);

LocalDate nextWeek =
    original.plusWeeks(1);

assert original.equals(
    LocalDate.of(2026, 7, 30));

assert nextWeek.equals(
    LocalDate.of(2026, 8, 6));

Safe sharing

public static final DateTimeFormatter
    LOG_TIMESTAMP =
        DateTimeFormatter.ISO_INSTANT;

DateTimeFormatter is also immutable and thread-safe, so reusable formatters can be stored in static final fields.[5]

4. LocalDate

Date LocalDate represents a date in the ISO-8601 calendar without a time or zone. It exposes year, month, day, day-of-week, day-of-year, leap-year rules, arithmetic, queries, adjustment, and streams of dates.[2]

Creation and validation

LocalDate release =
    LocalDate.of(
        2026,
        Month.OCTOBER,
        15);

LocalDate parsed =
    LocalDate.parse(
        "2026-10-15");

LocalDate fromEpochDay =
    LocalDate.ofEpochDay(
        20_000);

Factory methods validate field ranges and calendar validity; creating 30 February throws DateTimeException.

Useful operations

boolean leap =
    release.isLeapYear();

DayOfWeek day =
    release.getDayOfWeek();

LocalDate monthEnd =
    release.with(
        TemporalAdjusters
            .lastDayOfMonth());

Stream<LocalDate> days =
    release.datesUntil(
        release.plusDays(7));

Start of day in a zone

ZonedDateTime start =
    release.atStartOfDay(
        ZoneId.of(
            "America/New_York"));

atStartOfDay(zone) returns the earliest valid local time for the date. Because a zone transition can make midnight invalid, the result is not guaranteed to be 00:00.[6]

5. LocalTime

Time of day LocalTime stores a wall-clock time from 00:00 through 23:59:59.999999999 at nanosecond precision, without a date, offset, or zone. It cannot identify an instant by itself.[3]

LocalTime opens =
    LocalTime.of(
        9,
        0);

LocalTime closes =
    LocalTime.of(
        17,
        30);

boolean open =
    !now.isBefore(opens)
    && now.isBefore(closes);

Truncation and fields

LocalTime timestamp =
    LocalTime.of(
        14,
        37,
        42,
        918_273_645);

LocalTime minutePrecision =
    timestamp.truncatedTo(
        ChronoUnit.MINUTES);

long nanosOfDay =
    timestamp.toNanoOfDay();

Overnight windows

static boolean withinWindow(
        LocalTime value,
        LocalTime start,
        LocalTime end) {

    if (start.equals(end)) {
        return true;
    }

    if (start.isBefore(end)) {
        return !value.isBefore(start)
            && value.isBefore(end);
    }

    // Window crosses midnight.
    return !value.isBefore(start)
        || value.isBefore(end);
}

A time-only overnight interval is a recurring clock rule, not an elapsed interval. Attach dates and a zone before measuring actual elapsed time.

6. LocalDateTime

Local date-time LocalDateTime combines LocalDate and LocalTime without an offset or zone. It is suitable when the local fields themselves are the domain value or when the zone will be supplied separately.[4]

LocalDateTime appointment =
    LocalDate.of(
            2026,
            Month.NOVEMBER,
            1)
        .atTime(
            1,
            30);

LocalDate date =
    appointment.toLocalDate();

LocalTime time =
    appointment.toLocalTime();

It is not a unique timestamp

ZoneId zone =
    ZoneId.of(
        "America/New_York");

List<ZoneOffset> validOffsets =
    zone.getRules()
        .getValidOffsets(
            appointment);

// Can be 0, 1, or 2 offsets.

Local date-times in a regional zone can fall in a gap with no valid offset or an overlap with two valid offsets. Normal local times have one valid offset.[7]

Current local time needs an explicit clock/zone

LocalDateTime current =
    LocalDateTime.now(
        clock);

The now(Clock) overload makes the source of current time testable and avoids an implicit dependency on the system default zone.

7. Instant, OffsetDateTime, and OffsetTime

Timeline Instant represents a point on the Java time-line using epoch seconds and nanoseconds. It is usually the best core type for machine events, ordering, expiry, and transport-independent timestamps.[8]

Instant acceptedAt =
    clock.instant();

Instant expiresAt =
    acceptedAt.plus(
        Duration.ofMinutes(15));

boolean expired =
    !clock.instant()
        .isBefore(expiresAt);

Offset date-time

OffsetDateTime observed =
    OffsetDateTime.parse(
        "2026-07-30T23:13:00-04:00");

Instant sameInstant =
    observed.toInstant();

OffsetDateTime stores local date-time fields plus a fixed UTC offset. It identifies an instant but does not retain the region rules that produced the offset.[9]

Offset time

OffsetTime combines a time of day and offset without a date. It can compare positions within an abstract day but does not contain regional rules or a complete instant.[10]

Java time-scale

The Java time-scale divides each civil day into exactly 86,400 conceptual seconds and uses UTC-SLS semantics around leap seconds; clock implementations document their actual accuracy and mapping.[11]

8. ZoneId and ZoneOffset

Zones A ZoneOffset is a fixed offset such as -04:00. A region ZoneId such as America/New_York refers to a set of historical and future offset rules. Region IDs are normally preferable for civil scheduling because offsets can change.[12][13]

ZoneId newYork =
    ZoneId.of(
        "America/New_York");

ZoneOffset fixed =
    ZoneOffset.of(
        "-04:00");

ZoneId utc =
    ZoneOffset.UTC;

Avoid three-letter abbreviations

Short identifiers such as EST, CST, or IST are ambiguous and can represent fixed offsets rather than regional daylight-saving behavior. Store canonical region IDs or explicit offsets.

System default

ZoneId systemZone =
    ZoneId.systemDefault();

The system default is deployment configuration and can differ across hosts and containers. Business logic should use an explicitly configured zone rather than assuming the server's default.

9. ZonedDateTime

Regional date-time ZonedDateTime combines local date-time fields, an offset, and a zone ID. The offset is resolved from zone rules for the local date-time, with defined behavior for daylight-saving gaps and overlaps.[14]

ZonedDateTime meeting =
    ZonedDateTime.of(
        LocalDate.of(
            2026,
            9,
            15),
        LocalTime.of(
            9,
            30),
        ZoneId.of(
            "Europe/Paris"));

Instant meetingInstant =
    meeting.toInstant();

ZoneOffset meetingOffset =
    meeting.getOffset();

Same instant in another zone

ZonedDateTime inTokyo =
    meeting.withZoneSameInstant(
        ZoneId.of(
            "Asia/Tokyo"));

Same local fields in another zone

ZonedDateTime similarLocal =
    meeting.withZoneSameLocal(
        ZoneId.of(
            "Asia/Tokyo"));

withZoneSameInstant preserves the timeline point and changes displayed local fields. withZoneSameLocal preserves local fields where possible and therefore usually changes the instant.

10. Daylight-saving gaps and overlaps

When clocks move forward, a range of local times does not exist: a gap. When clocks move backward, a range occurs twice: an overlap. Government decisions can also create non-hour transitions and permanent changes.[15]

Gap resolution

ZoneId zone =
    ZoneId.of(
        "America/New_York");

LocalDateTime missing =
    LocalDateTime.of(
        2026,
        3,
        8,
        2,
        30);

ZonedDateTime resolved =
    missing.atZone(zone);

// Default behavior shifts forward by
// the gap length into a valid time.

Overlap resolution

LocalDateTime repeated =
    LocalDateTime.of(
        2026,
        11,
        1,
        1,
        30);

ZonedDateTime earlier =
    repeated.atZone(zone);

ZonedDateTime later =
    earlier.withLaterOffsetAtOverlap();

For an overlap, the default resolver normally chooses the earlier offset. For a gap, it shifts the local date-time forward by the length of the gap. withEarlierOffsetAtOverlap and withLaterOffsetAtOverlap make the overlap choice explicit.[14]

Strict construction

ZonedDateTime strict =
    ZonedDateTime.ofStrict(
        repeated,
        requestedOffset,
        zone);

ofStrict rejects a gap or an offset that is not valid for the supplied local date-time and zone.

11. Inspecting ZoneRules

ZoneRules maps instants to offsets and local date-times to zero, one, or two valid offsets. It also exposes transitions, daylight-saving information, standard offsets, and recurring transition rules.[7]

ZoneId zone =
    ZoneId.of(
        "America/New_York");

ZoneRules rules =
    zone.getRules();

LocalDateTime local =
    LocalDateTime.of(
        2026,
        11,
        1,
        1,
        30);

List<ZoneOffset> offsets =
    rules.getValidOffsets(local);

switch (offsets.size()) {
    case 0 -> {
        ZoneOffsetTransition transition =
            rules.getTransition(local);

        System.out.println(
            "Gap: " + transition);
    }

    case 1 ->
        System.out.println(
            "Normal: " + offsets.getFirst());

    case 2 ->
        System.out.println(
            "Overlap: " + offsets);

    default ->
        throw new AssertionError();
}

Find upcoming transitions

Instant cursor =
    clock.instant();

for (int index = 0;
        index < 4;
        index++) {

    ZoneOffsetTransition next =
        rules.nextTransition(cursor);

    if (next == null) {
        break;
    }

    System.out.printf(
        "%s: %s -> %s%n",
        next.getInstant(),
        next.getOffsetBefore(),
        next.getOffsetAfter());

    cursor =
        next.getInstant()
            .plusNanos(1);
}

A transition is a discontinuity in the local time-line, normally represented as a gap or overlap. Transition sizes are not required to be exactly one hour.[15]

12. Converting local, offset, zoned, and instant values

Instant to regional local time

Instant event =
    Instant.parse(
        "2026-07-31T03:13:00Z");

ZonedDateTime newYork =
    event.atZone(
        ZoneId.of(
            "America/New_York"));

ZonedDateTime tokyo =
    event.atZone(
        ZoneId.of(
            "Asia/Tokyo"));

assert newYork.toInstant()
    .equals(tokyo.toInstant());

Local value to instant

LocalDateTime local =
    LocalDateTime.of(
        2026,
        12,
        15,
        9,
        0);

ZonedDateTime zoned =
    local.atZone(
        ZoneId.of(
            "Europe/London"));

Instant instant =
    zoned.toInstant();

Offset is enough for a past instant, not future civil rules

OffsetDateTime transmitted =
    OffsetDateTime.parse(
        "2026-07-30T23:13:00-04:00");

Instant exact =
    transmitted.toInstant();

// The region cannot be reconstructed from -04:00.
ZoneId region =
    ZoneId.of(
        "America/New_York");

Preserve the right invariant

  • Use withZoneSameInstant to display one event in another region.
  • Use withZoneSameLocal only when retaining wall-clock fields is the business requirement.
  • Use toInstant for ordering and global comparison.
  • Store the region ID separately when future recurrence or original scheduling intent matters.

13. Calendar arithmetic with dates

Date-based arithmetic applies calendar rules. Adding one month adjusts invalid end-of-month results to the last valid day, rather than adding a fixed number of seconds.[2]

LocalDate januaryEnd =
    LocalDate.of(
        2026,
        1,
        31);

LocalDate oneMonthLater =
    januaryEnd.plusMonths(1);

// 2026-02-28

Repeated billing dates

static LocalDate billingDate(
        YearMonth month,
        int preferredDay) {

    int actualDay =
        Math.min(
            preferredDay,
            month.lengthOfMonth());

    return month.atDay(
        actualDay);
}

LocalDate next =
    billingDate(
        YearMonth.of(
            2026,
            Month.FEBRUARY),
        31);

Do not chain adjusted dates when the anchor matters

// Drifts after February if repeated:
date = date.plusMonths(1);

// Preserve original billing-day policy:
YearMonth nextMonth =
    YearMonth.from(date)
        .plusMonths(1);

date =
    billingDate(
        nextMonth,
        preferredDay);

YearMonth represents a year and month without a day and provides month length and end-of-month operations.[16]

14. Time and local date-time arithmetic

LocalTime wraps within the day

LocalTime result =
    LocalTime.of(
            23,
            30)
        .plusHours(2);

// 01:30; no date was retained.

LocalDateTime carries into the date

LocalDateTime result =
    LocalDateTime.of(
            2026,
            7,
            30,
            23,
            30)
        .plusHours(2);

// 2026-07-31T01:30

Zoned arithmetic depends on unit category

Date-based units such as days and months operate on the local time-line and then resolve the zone. Time-based units such as hours operate on the instant time-line for ZonedDateTime.[14]

ZonedDateTime start =
    ZonedDateTime.of(
        2026,
        3,
        7,
        9,
        0,
        0,
        0,
        ZoneId.of(
            "America/New_York"));

ZonedDateTime nextLocalDay =
    start.plusDays(1);

ZonedDateTime twentyFourHours =
    start.plusHours(24);

Across a daylight-saving transition, “same local time tomorrow” and “24 elapsed hours later” can produce different local clock readings.

15. Duration

Time-based amount Duration stores a directed amount in seconds and nanoseconds. Its day unit is exactly 86,400 seconds and therefore ignores daylight-saving variation.[17]

Duration timeout =
    Duration.ofSeconds(
        2,
        500_000_000);

Duration cacheTtl =
    Duration.ofMinutes(15);

Duration elapsed =
    Duration.between(
        startedAt,
        finishedAt);

Parts versus totals

Duration value =
    Duration.ofSeconds(
        3_661,
        250_000_000);

long totalSeconds =
    value.getSeconds();

long hoursPart =
    value.toHoursPart();

int minutesPart =
    value.toMinutesPart();

int secondsPart =
    value.toSecondsPart();

int nanosPart =
    value.toNanosPart();

Overflow-aware conversions

try {
    long nanos =
        duration.toNanos();
} catch (ArithmeticException tooLarge) {
    // Duration cannot fit in a long nanosecond count.
}

Parsing ISO duration text

Duration parsed =
    Duration.parse(
        "PT2H30M15.5S");

Duration text uses an ISO-8601-based representation beginning with P, with a T before time components.

16. Period

Date-based amount Period represents an ISO-calendar amount in years, months, and days. It preserves these components rather than converting them to a fixed number of seconds.[18]

Period trial =
    Period.ofDays(30);

Period subscription =
    Period.ofMonths(1);

Period age =
    Period.between(
        birthDate,
        today);

Component semantics

Period value =
    Period.of(
        1,
        15,
        10);

Period normalized =
    value.normalized();

// 2 years, 3 months, 10 days

normalized() normalizes years and months using a 12-month year but does not convert days to months because month lengths vary.

Apply to a date

LocalDate renewal =
    currentDate.plus(
        Period.ofMonths(1));

Parsing

Period parsed =
    Period.parse(
        "P1Y2M10D");

17. Duration versus Period

RequirementUse
Expire exactly 24 hours after creationDuration.ofHours(24)
Run at the same local time tomorrowPeriod.ofDays(1) or plusDays(1)
Renew one calendar month laterPeriod.ofMonths(1)
Measure request latencyDuration, preferably monotonic timing
Calculate age in calendar years/months/daysPeriod.between

DST example

ZoneId zone =
    ZoneId.of(
        "America/New_York");

ZonedDateTime start =
    ZonedDateTime.of(
        2026,
        3,
        7,
        9,
        0,
        0,
        0,
        zone);

ZonedDateTime calendarDay =
    start.plus(
        Period.ofDays(1));

ZonedDateTime exactDay =
    start.plus(
        Duration.ofDays(1));

The calendar period aims to retain 09:00 local time. The duration advances exactly 86,400 seconds, which can display as 10:00 after a one-hour spring transition.[14][17]

18. Measuring between values and using units

ChronoUnit defines standard units and can calculate whole units between compatible temporal objects. Date-based units are estimated in duration; time-based units are exact under the API's unit definitions.[19]

long days =
    ChronoUnit.DAYS.between(
        startDate,
        endDate);

long minutes =
    ChronoUnit.MINUTES.between(
        startInstant,
        endInstant);

Period calendarDifference =
    Period.between(
        startDate,
        endDate);

Duration elapsed =
    Duration.between(
        startInstant,
        endInstant);

Whole-unit truncation

LocalDateTime start =
    LocalDateTime.of(
        2026,
        7,
        30,
        10,
        45);

LocalDateTime end =
    LocalDateTime.of(
        2026,
        7,
        31,
        10,
        44);

long wholeDays =
    ChronoUnit.DAYS.between(
        start,
        end);

// 0 complete days.

Elapsed timing

long start =
    System.nanoTime();

operation.run();

long elapsedNanos =
    System.nanoTime()
        - start;

System.nanoTime() is intended for measuring elapsed time and is not related to wall-clock epoch time. Use Instant/Clock for timestamps and monotonic time for in-process latency measurement.[20]

19. TemporalAdjuster and business-date rules

TemporalAdjusters supplies reusable date adjustment strategies including first/last day of a month or year, next/previous weekdays, and ordinal weekdays in a month.[21]

LocalDate firstMonday =
    date.with(
        TemporalAdjusters
            .firstInMonth(
                DayOfWeek.MONDAY));

LocalDate nextFriday =
    date.with(
        TemporalAdjusters.next(
            DayOfWeek.FRIDAY));

LocalDate monthEnd =
    date.with(
        TemporalAdjusters
            .lastDayOfMonth());

Custom next-business-day adjuster

static TemporalAdjuster
nextBusinessDay(
        Set<LocalDate> holidays) {

    Set<LocalDate> immutableHolidays =
        Set.copyOf(holidays);

    return TemporalAdjusters.ofDateAdjuster(
        date -> {
            LocalDate candidate =
                date.plusDays(1);

            while (candidate.getDayOfWeek()
                        == DayOfWeek.SATURDAY
                    || candidate.getDayOfWeek()
                        == DayOfWeek.SUNDAY
                    || immutableHolidays
                        .contains(candidate)) {

                candidate =
                    candidate.plusDays(1);
            }

            return candidate;
        });
}
LocalDate settlement =
    tradeDate.with(
        nextBusinessDay(
            holidays));

A holiday calendar is jurisdiction- and product-specific. Treat it as versioned business data rather than assuming weekends alone define business days.

20. Clock and deterministic current time

Current time Clock supplies the current instant together with a zone and exists primarily to make current-time access injectable and testable. Oracle recommends avoiding an implicit dependency on the system default zone when a specific zone or UTC is intended.[11]

Inject a clock

public final class TokenService {
    private final Clock clock;
    private final Duration lifetime;

    public TokenService(
            Clock clock,
            Duration lifetime) {

        this.clock =
            Objects.requireNonNull(clock);

        this.lifetime =
            Objects.requireNonNull(lifetime);
    }

    public Token issue() {
        Instant issuedAt =
            clock.instant();

        return new Token(
            issuedAt,
            issuedAt.plus(lifetime));
    }
}

Fixed clock test

Clock clock =
    Clock.fixed(
        Instant.parse(
            "2026-07-31T03:13:00Z"),
        ZoneOffset.UTC);

TokenService service =
    new TokenService(
        clock,
        Duration.ofMinutes(15));

Token token =
    service.issue();

assertEquals(
    Instant.parse(
        "2026-07-31T03:28:00Z"),
    token.expiresAt());

Other clocks

Clock shifted =
    Clock.offset(
        Clock.systemUTC(),
        Duration.ofDays(30));

Clock secondPrecision =
    Clock.tickSeconds(
        ZoneOffset.UTC);

Use InstantSource instead of Clock when code needs only instants and should not carry a zone dependency.[22]

21. Formatting with DateTimeFormatter

Formatting DateTimeFormatter formats and parses temporal values using predefined ISO/RFC formatters, patterns, localized styles, or a builder. A formatter can carry a locale, chronology, decimal style, resolver policy, and override zone.[5]

Prefer predefined wire formats

String instantText =
    DateTimeFormatter.ISO_INSTANT
        .format(instant);

String zonedText =
    DateTimeFormatter
        .ISO_ZONED_DATE_TIME
        .format(zoned);

String offsetText =
    DateTimeFormatter
        .ISO_OFFSET_DATE_TIME
        .format(offsetDateTime);

Override display zone

DateTimeFormatter utcLogFormatter =
    DateTimeFormatter
        .ofPattern(
            "uuuu-MM-dd'T'HH:mm:ss.SSSXXX",
            Locale.ROOT)
        .withZone(
            ZoneOffset.UTC);

String text =
    utcLogFormatter.format(
        instant);

Format the type that matches the fields

A formatter requiring a zone cannot format a LocalDateTime unless it has an override zone. A date-only value cannot supply hour fields. Let such mismatches fail rather than inventing implicit values.

23. Localized user-facing formatting

Localized formatters choose locale-specific ordering, names, punctuation, and styles. The exact output is locale data, not a stable machine protocol.[23]

DateTimeFormatter dateFormatter =
    DateTimeFormatter
        .ofLocalizedDate(
            FormatStyle.LONG)
        .withLocale(
            Locale.US);

String us =
    dateFormatter.format(
        LocalDate.of(
            2026,
            7,
            30));

String france =
    dateFormatter
        .withLocale(
            Locale.FRANCE)
        .format(
            LocalDate.of(
                2026,
                7,
                30));

Localized date and time need a zone where required

DateTimeFormatter display =
    DateTimeFormatter
        .ofLocalizedDateTime(
            FormatStyle.FULL)
        .withLocale(
            Locale.UK)
        .withZone(
            ZoneId.of(
                "Europe/London"));

String text =
    display.format(
        instant);

Machine versus human formats

  • Use explicit ISO/RFC-style contracts for storage, APIs, and logs.
  • Use localized formatters at the presentation boundary.
  • Do not parse localized free-form user text as though it were a stable wire format.

24. DateTimeFormatterBuilder

DateTimeFormatterBuilder constructs complex formatters from numeric fields, fractions, text, literals, offsets, zones, chronology, optional sections, padding, case sensitivity, and strictness controls.[24]

Optional seconds and fractional seconds

DateTimeFormatter flexibleTime =
    new DateTimeFormatterBuilder()
        .parseCaseSensitive()
        .appendValue(
            ChronoField.HOUR_OF_DAY,
            2)
        .appendLiteral(':')
        .appendValue(
            ChronoField.MINUTE_OF_HOUR,
            2)
        .optionalStart()

Defaulting fields is a protocol decision. A sentinel leap year such as 2000 can permit 29 February for recurring month-day parsing, but it should not be mistaken for the user's real year.

25. Parsing

Parsing converts text into temporal fields and then resolves those fields into a date/time type. The target type determines which fields are required; parsing a zone-bearing string as LocalDateTime intentionally discards neither zone nor offset—it fails unless the query extracts only supported fields.[5]

Direct parsing

LocalDate date =
    LocalDate.parse(
        "2026-07-30");

LocalTime time =
    LocalTime.parse(
        "23:13:45.123");

OffsetDateTime offset =
    OffsetDateTime.parse(
        "2026-07-30T23:13:45-04:00");

ZonedDateTime zoned =
    ZonedDateTime.parse(
        "2026-07-30T23:13:45-04:00"
            + "[America/New_York]");

Parse with an explicit formatter

DateTimeFormatter formatter =
    DateTimeFormatter
        .ofPattern(
            "uuuuMMdd-HHmmss",
            Locale.ROOT)
        .withResolverStyle(
            ResolverStyle.STRICT);

LocalDateTime value =
    LocalDateTime.parse(
        "20260730-231345",
        formatter);

Handle parse diagnostics

try {
    return LocalDate.parse(
        input,
        formatter);
} catch (DateTimeParseException failure) {
    throw new InvalidDateInput(
        input,
        failure.getErrorIndex(),
        failure);
}

DateTimeParseException records the parsed text and error index. Avoid returning low-level parser messages directly to untrusted clients; map them to stable validation errors.[25]

26. Strict, smart, and lenient resolution

Formatter parsing occurs in two phases: lexical field extraction followed by resolution into coherent dates/times. ResolverStyle controls the second phase. Pattern formatters default to SMART.[5][26]

StyleBehaviorUse
STRICTRequires field combinations valid for the date/timeMachine input, contractual user input
SMARTApplies field-specific sensible adjustmentsConvenient presentation parsing when adjustment is intended
LENIENTAllows arithmetic overflow such as month 15Specialized normalization/import tools

Invalid day behavior

DateTimeFormatter strict =
    DateTimeFormatter
        .ofPattern(
            "uuuu-MM-dd",
            Locale.ROOT)
        .withResolverStyle(
            ResolverStyle.STRICT);

LocalDate.parse(
    "2026-02-30",
    strict);
// throws DateTimeParseException

In SMART ISO resolution, a day from 1 through 31 beyond the month's actual end can be adjusted to the last valid day. Strict mode rejects the invalid year-month-day combination.[26]

Validation should not silently normalize user mistakes. Use strict parsing unless the product explicitly defines normalization behavior.

Accept zoned, offset, or local date-time

29. Intervals, ranges, and boundary semantics

The core API provides points and amounts rather than one universal interval class. Domain ranges should define whether endpoints are inclusive or exclusive and whether they are local-calendar or timeline ranges.

Half-open instant range

public record InstantRange(
        Instant startInclusive,
        Instant endExclusive) {

    public InstantRange {
        Objects.requireNonNull(
            startInclusive);

        Objects.requireNonNull(
            endExclusive);

        if (endExclusive.isBefore(
                startInclusive)) {
            throw new IllegalArgumentException();
        }
    }

    public boolean contains(
            Instant value) {

        return !value.isBefore(
                startInclusive)
            && value.isBefore(
                endExclusive);
    }

    public Duration length() {
        return Duration.between(
            startInclusive,
            endExclusive);
    }

    public boolean overlaps(
            InstantRange other) {

        return startInclusive.isBefore(
                other.endExclusive)
            && other.startInclusive
                .isBefore(
                    endExclusive);
    }
}

Local date range

record DateRange(
    LocalDate startInclusive,
    LocalDate endExclusive) {

    Stream<LocalDate> dates() {
        return startInclusive.datesUntil(
            endExclusive);
    }
}

Half-open ranges compose cleanly: adjacent ranges share a boundary without overlapping, and their length is computed directly from start to end.

}

A fixed offset cannot express future political changes. A region ID enables recalculation with the runtime's current zone rules, while storing a previously resolved instant preserves what was scheduled under earlier rules.

Precision contract

Java types can represent nanoseconds, but databases and protocols may store fewer fractional digits. Define whether persistence rejects, truncates, or rounds excess precision, and test the round trip.

32. JSON and API contracts

RFC 3339 defines a widely used Internet profile of ISO 8601 for date-time interchange with a required numeric offset or Z. It does not encode an IANA region zone ID.[29]

Timeline event

{
  "occurredAt": "2026-07-31T03:13:00.123456Z"
}

Scheduled regional appointment

{
  "localDateTime": "2026-11-01T01:30:00",
  "zoneId": "America/New_York",
  "overlapPolicy": "LATER_OFFSET",
  "resolvedInstant": "2026-11-01T06:30:00Z"
}

Contract rules

  • Require an offset for event timestamps.
  • Use Z/UTC as a canonical form when preserving the original offset is unnecessary.
  • Send a separate region ID when regional rules matter.
  • Specify accepted fractional precision.
  • Specify whether leap-second text is accepted and how it is normalized.
  • Reject timestamps without offsets when the field claims to be a global event time.

Convert at the system boundary, then keep java.time types throughout application logic. Do not mix mutable Calendar/DateFormat state with immutable modern values.

34. Time-zone database lifecycle

The JDK's default region zones are based on the IANA Time Zone Database. Governments change offsets, daylight-saving schedules, and zone boundaries, so time-zone data is versioned operational data rather than a timeless constant.[12][32]

As of 30 July 2026, IANA TZDB 2026c is the latest published release; it was released on 8 July 2026. A particular JDK build may contain an earlier TZDB version, so applications must inspect and update their deployed runtime rather than assuming the latest IANA rules are bundled.[33]

Inspect available versions

NavigableMap<String, ZoneRules> versions =
    ZoneRulesProvider.getVersions(
        "America/New_York");

System.out.println(
    versions.lastKey());

Available region IDs

Set<String> zones =
    ZoneId.getAvailableZoneIds();

Upgrade strategy

  • Track government changes and JDK/TZDB releases.
  • Update all scheduling nodes consistently.
  • Recalculate future occurrences after a rule update.
  • Do not rewrite historical event instants.
  • Record which rule version produced critical future schedules when auditability requires it.
  • Test zones affected by current rule changes before deployment.

ZoneRulesProvider supplies rules and version maps; custom providers are an advanced integration mechanism and must preserve thread safety and unique zone IDs.[32]

36. Performance and thread safety

The core values and formatters are immutable and safe to share. Prefer reusable formatters and prevalidated ZoneId constants for hot paths, but optimize only after profiling.[5]

Reuse formatters

            .appendInstant(6)
            .toFormatter(
                Locale.ROOT);

Avoid needless string round trips

    Instant.parse(
        instant.toString());

// Use the immutable value directly:

    instant;

Allocation and parsing

  • Arithmetic returns new objects; short-lived allocation is usually inexpensive but can matter in massive pipelines.
  • Parsing and localized formatting are more expensive than field access.
  • Zone-rule lookup is optimized but regional scheduling remains more work than fixed-offset arithmetic.
  • Measure with JMH when micro-level performance is material.

Cache policy

Cache stable formatters and business calendars. Do not cache “today” or the current offset indefinitely: those values depend on time, zone rules, and the configured clock.

38. Complete example: DST-aware daily scheduling

A daily civil schedule requires a local time, region zone, and policies for gaps and overlaps. Persisting only the next instant loses the recurrence's human intent.

enum GapPolicy {
    SHIFT_FORWARD,
    REJECT
}

enum OverlapPolicy {
    EARLIER_OFFSET,
    LATER_OFFSET
}

public record DailySchedule(
        LocalTime localTime,
        ZoneId zone,
        GapPolicy gapPolicy,
        OverlapPolicy overlapPolicy) {

    public DailySchedule {
        Objects.requireNonNull(localTime);
        Objects.requireNonNull(zone);
        Objects.requireNonNull(gapPolicy);
        Objects.requireNonNull(overlapPolicy);
    }

    public ZonedDateTime nextAfter(
            Instant afterExclusive) {

        LocalDate candidateDate =
            afterExclusive.atZone(zone)
                .toLocalDate();

        for (;;) {
            ZonedDateTime candidate =
                resolve(candidateDate);

            if (candidate.toInstant()
                    .isAfter(afterExclusive)) {
                return candidate;
            }

            candidateDate =
                candidateDate.plusDays(1);
        }
    }

    private ZonedDateTime resolve(
            LocalDate date) {

        LocalDateTime local =
            date.atTime(localTime);

        ZoneRules rules =
            zone.getRules();

        List<ZoneOffset> offsets =
            rules.getValidOffsets(local);

        if (offsets.size() == 1) {
            return ZonedDateTime.ofStrict(
                local,
                offsets.getFirst(),
                zone);
        }

        if (offsets.isEmpty()) {
            if (gapPolicy
                    == GapPolicy.REJECT) {

                ZoneOffsetTransition transition =
                    rules.getTransition(local);

                throw new DateTimeException(
                    "Scheduled local time is in gap: "
                        + transition);
            }

            // Standard atZone behavior shifts the
            // local value forward by the gap length.
            return local.atZone(zone);
        }

        ZoneOffset selected =
            overlapPolicy
                    == OverlapPolicy
                        .EARLIER_OFFSET
                ? offsets.getFirst()
                : offsets.getLast();

        return ZonedDateTime.ofStrict(
            local,
            selected,
            zone);
    }
}

Usage

DailySchedule schedule =
    new DailySchedule(
        LocalTime.of(
            1,
            30),
        ZoneId.of(
            "America/New_York"),
        GapPolicy.SHIFT_FORWARD,
        OverlapPolicy.LATER_OFFSET);

ZonedDateTime next =
    schedule.nextAfter(
        clock.instant());

Operational design

  • Store the recurrence rule and zone ID.
  • Store the next resolved instant for efficient dispatch.
  • After execution, calculate the next occurrence from the recurrence—not by adding 24 hours to the prior instant.
  • Recalculate future occurrences after TZDB updates.
  • Use idempotency when scheduler failover can dispatch the same occurrence twice.
  • Record the resolved local date-time, offset, zone ID, and instant in execution history.

39. Production checklist

Type selection

  • LocalDate is used for date-only domain values.
  • LocalTime is used for recurring wall-clock times.
  • LocalDateTime is never mistaken for a unique instant.
  • Instant is used for globally ordered events and expiry.
  • ZoneId is retained for regional civil schedules.
  • Duration and Period are selected by elapsed versus calendar intent.

Zones and DST

  • Business zones are explicit configuration, not server defaults.
  • Gap and overlap behavior is specified and tested.
  • Same-instant versus same-local conversion is intentional.
  • TZDB/JDK versions are tracked and updated.
  • Future schedules can be recalculated after rule changes.

Formatting and parsing

  • Machine contracts use stable ISO/RFC-style formats.
  • Presentation uses locale-specific formatting.
  • Strict parsing validates contractual input.
  • Pattern letters use u/M/m/H/h correctly.
  • Input length, range, zone, and precision are bounded.
  • Formatters are immutable and reused.

Persistence and APIs

  • Timeline timestamps include an offset or use UTC.
  • Regional schedules store local fields and region IDs separately.
  • Database precision and driver mappings are integration-tested.
  • Original offset is retained only when the domain needs it.
  • Localized strings are not used as durable storage.

Testing and operation

  • Clock/InstantSource is injected.
  • Leap days, month ends, gaps, and overlaps are covered.
  • Elapsed measurements use a monotonic source.
  • Rule/version changes are part of deployment testing.
  • Recurring dispatch is idempotent and auditable.
Final principle: model the meaning first. Local values describe calendars and clocks; instants describe the global time-line; zones are mutable political rule sets; durations measure exact elapsed time; periods express calendar movement. Formatting and storage must preserve that meaning rather than erase it.
