1. Exceptions are non-local control transfer with typed diagnostic state

An exception transfers control from the point of failure to the nearest compatible handler, potentially crossing expressions, statements, methods, constructors, and initialization code. The thrown object carries a type, message, cause, stack trace, and possibly suppressed failures.

Signal

A JVM-detected condition, explicit throw, assertion failure, loading/linking failure, or resource limitation.

Contract

Checked exception declarations expose recoverable failure modes in method and constructor APIs.

Propagation

Frames unwind until a compatible catch clause is selected or the thread terminates.

Cleanup

finally and try-with-resources execute cleanup during normal and abrupt completion.

Every Java exception is represented by an instance of Throwable or one of its subclasses. Java exceptions are precise: effects before the throw point remain visible, while later expressions and statements must not appear to have executed.[1]

Exceptions are part of API design. The useful question is not merely “can this fail?” but “what can callers reasonably do, what context must cross the boundary, and who owns cleanup?”

2. The Throwable hierarchy

Object └── Throwable ├── Exception │ ├── RuntimeException │ │ ├── IllegalArgumentException │ │ ├── IllegalStateException │ │ ├── NullPointerException │ │ └── ... │ ├── IOException │ ├── SQLException │ ├── InterruptedException │ └── ... └── Error ├── AssertionError ├── LinkageError ├── VirtualMachineError └── ...

Throwable is the superclass of all errors and exceptions. For compile-time checking, subclasses that are not also subclasses of RuntimeException or Error are checked exceptions.[2]

Generic throwable classes are prohibited

// Illegal:
class Problem<T>
        extends Exception {
}

The Java language does not permit generic subclasses of Throwable.[1]

3. Checked exceptions

Compile-time checked A checked exception must be caught or declared when it can escape a method or constructor. Checked exception types in a throws clause form part of the API contract between implementation and caller.[1]

public Configuration load(
        Path path)
        throws IOException,
               ConfigurationFormatException {

    String text =
        Files.readString(
            path,
            StandardCharsets.UTF_8);

    return parser.parse(text);
}

Good candidates

  • External I/O, networking, and database operations where callers can retry, choose another source, report failure, or compensate.
  • Domain workflows with an expected exceptional branch that should remain explicit at each calling layer.
  • Library boundaries where hiding the failure would remove useful recovery choices.

Cost of checked contracts

Checked exceptions propagate through signatures and functional interfaces, so a checked type should represent information that callers can use rather than implementation detail.

4. Unchecked exceptions

Runtime exception RuntimeException and its subclasses are unchecked: the compiler does not require catch or declaration. They commonly represent invalid arguments, illegal object state, violated preconditions, unsupported operations, and programming errors, although recovery is still possible in some contexts.[3]

public Money divide(
        BigDecimal divisor) {

    Objects.requireNonNull(
        divisor,
        "divisor");

    if (divisor.signum() == 0) {
        throw new IllegalArgumentException(
            "divisor must be non-zero");
    }

    return new Money(
        amount.divide(divisor),
        currency);
}

Unchecked does not mean undocumented

Public APIs should document important runtime exceptions when callers can prevent them or when they express a meaningful precondition.

Do not convert everything automatically

Wrapping every checked exception in one generic runtime exception can destroy recovery information and make failure handling less precise.

5. Error

Serious failure Error is the superclass of failures from which ordinary programs are not ordinarily expected to recover. Examples include linkage failures and virtual-machine resource failures.[4]

try {
    runApplication();
} catch (Exception failure) {
    reportRecoverableFailure(
        failure);
}
// Error is not caught here.

Do not use Error for application validation

// Wrong:
throw new Error(
    "Customer was not found");

// Use a domain exception or result type.

Rare boundaries

Infrastructure may catch Throwable only to record diagnostics or perform minimal containment before rethrowing or terminating. It must not pretend that every Error leaves the process or subsystem in a reliable state.

6. Message, cause, stack trace, and suppressed failures

Throwable stores an optional detail message, an optional cause, a stack trace, and a list of suppressed exceptions. Stack traces are normally captured when a throwable is created, subject to constructor configuration and VM behavior.[2]

Throwable failure =
    new IllegalStateException(
        "Cannot transition order "
            + orderId
            + " from "
            + current
            + " to "
            + requested,
        cause);

String message =
    failure.getMessage();

Throwable root =
    failure.getCause();

StackTraceElement[] frames =
    failure.getStackTrace();

Throwable[] suppressed =
    failure.getSuppressed();

Cause and suppression are different

  • A cause represents a lower-level failure that explains the current failure.
  • A suppressed exception represents another sibling failure that could not be propagated as the primary one, commonly a cleanup failure.

7. The throw statement

Control transfer A throw statement evaluates a reference assignable to Throwable and immediately transfers control outward until a compatible handler is found. Throwing null causes a NullPointerException.[5]

if (quantity < 0) {
    throw new IllegalArgumentException(
        "quantity must be non-negative: "
            + quantity);
}

Throw an existing failure

catch (IOException failure) {
    auditFailure(failure);
    throw failure;
}

Throw expression type

throw new CustomerNotFoundException(
    customerId);

The thrown object's dynamic type controls handler selection; its static type participates in compile-time exception analysis.

8. The throws clause

A method or constructor throws clause declares checked exception types that can escape. It does not throw anything by itself and does not require callers to catch unchecked exceptions.[6]

public Report generate(
        ReportRequest request)
        throws DataAccessException,
               ReportTemplateException {

    // ...
}

Declare useful abstraction-level failures

// Leaks implementation detail:
public User load(UserId id)
        throws SQLException;

// Better repository abstraction:
public User load(UserId id)
        throws RepositoryException;

Avoid overbroad declarations

// Weak contract:
public void execute()
        throws Exception {
}

Broad declarations force callers to handle failures that may be unrelated and make API evolution harder to understand.

9. Checked exceptions and overriding

An overriding method may not add checked exception types that the overridden method does not permit. It may omit checked exceptions or narrow them to subclasses. Unchecked exceptions are not restricted by this rule.[1]

interface Loader {
    Data load()
        throws IOException;
}

final class FileLoader
        implements Loader {

    @Override
    public Data load()
            throws FileNotFoundException {

        // Narrower checked exception.
        // ...
    }
}

Library design implication

A functional interface or callback that declares no checked exception cannot be implemented by a lambda that throws an unrelated checked exception without handling or adapting it.

10. The try statement

A try statement executes a block and can be followed by catch clauses, a finally clause, or a resource specification. A plain try statement must have catches or finally; try-with-resources can stand alone.[5]

try {
    process(request);
} catch (ValidationException failure) {
    return badRequest(
        failure.getMessage());
} finally {
    metrics.requestFinished();
}

Keep the protected region narrow

byte[] bytes;

try {
    bytes =
        Files.readAllBytes(path);
} catch (IOException failure) {
    throw new DocumentReadException(
        path,
        failure);
}

return parse(bytes);

A narrow try block reduces the chance of catching an exception from an operation that the handler did not intend to handle.

11. Catch-clause selection

When a value is thrown from a try block, catch clauses are examined in source order. Control transfers to the first catch parameter whose type can receive the thrown object's type.[5]

try {
    repository.save(order);
} catch (DuplicateOrderException failure) {
    return conflict(
        failure.orderId());
} catch (RepositoryException failure) {
    return serviceUnavailable(
        failure);
}

Handler responsibility

  • Recover and continue with a valid state.
  • Translate to the current abstraction.
  • Add context and rethrow.
  • Perform boundary reporting and terminate the operation.

A catch clause should not merely make the compiler quiet.

12. Catch specific types before general types

try {
    parse(input);
} catch (SpecificFormatException failure) {
    handleSpecific(failure);
} catch (FormatException failure) {
    handleGeneral(failure);
}

Unreachable catch

try {
    parse(input);
} catch (Exception failure) {
    handle(failure);
} catch (IOException failure) {
    // Compile-time error:
    // already caught by Exception.
}

A catch clause is unreachable when an earlier clause catches every throwable it could receive. The compiler rejects such ordering.[1]

13. Multi-catch

Multi-catch handles several unrelated exception types with one handler. Alternatives are separated with |; no alternative may be a subtype of another alternative. The catch parameter is implicitly final.[5]

try {
    importDocument(path);
} catch (MalformedDocumentException
         | UnsupportedDocumentException
         failure) {

    return reject(
        path,
        failure.getMessage());
}

Use when handling is genuinely identical

If the response, logging severity, retry policy, or context differs by type, separate catch clauses communicate the distinction better.

14. Precise rethrow

Java's exception analysis can infer a narrower set of checked exception types when a catch parameter is rethrown without reassignment and the try block can throw only specific alternatives.[1]

public void copy(
        Path source,
        Path target)
        throws FileNotFoundException,
               AccessDeniedException {

    try {
        performCopy(
            source,
            target);
    } catch (IOException failure) {
        audit(failure);
        throw failure;
    }
}

The declaration can remain narrower than the catch parameter's apparent static superclass when the compiler proves the actual escaping alternatives.

15. finally

Under ordinary Java execution, a finally block executes after the try/catch computation whether it completes normally or abruptly, including return and thrown exception.[5]

Lock lock =
    this.lock;

lock.lock();

try {
    updateState();
} finally {
    lock.unlock();
}

Appropriate uses

  • Release a lock or permit.
  • Restore temporary thread or process state.
  • Record completion metrics.
  • Run cleanup not represented by an AutoCloseable.

Prefer try-with-resources for closeable resources

Manual close logic in finally is verbose and can accidentally hide the primary failure.

16. Abrupt completion inside finally

If a finally block itself completes abruptly—by throwing or returning—its reason for completion replaces the pending return value or exception from the try/catch computation.[5]

Never return from finally

static int broken() {
    try {
        throw new IllegalStateException(
            "primary");
    } finally {
        return 42;
        // Suppresses the exception.
    }
}

Cleanup failure can mask the primary failure

try {
    operation();
} finally {
    resource.close();
    // If both fail, close failure can replace
    // the operation failure.
}
A finally block should normally complete normally. Try-with-resources exists partly to preserve the primary failure while recording close failures as suppressed.

17. Try-with-resources

Resource safety A try-with-resources statement declares or references one or more final/effectively-final resources whose types implement AutoCloseable. Resources are closed automatically after the try block, before any associated catch or finally completes.[7]

try (BufferedReader reader =
        Files.newBufferedReader(
            path,
            StandardCharsets.UTF_8)) {

    return reader.lines()
        .map(String::strip)
        .filter(
            Predicate.not(
                String::isEmpty))
        .toList();
}

Existing effectively-final variable

InputStream input =
    openInput();

try (input) {
    return input.readAllBytes();
}

Catch and finally remain available

try (Connection connection =
        dataSource.getConnection()) {

    return query(connection);
} catch (SQLException failure) {
    throw translate(failure);
} finally {
    metrics.queryFinished();
}

18. Resource initialization and close order

Resources are initialized from left to right and closed in reverse order. If a later initializer fails, resources that initialized successfully are still closed. A close failure does not prevent attempts to close earlier resources.[5]

try (InputStream file =
        Files.newInputStream(path);
     BufferedInputStream buffered =
        new BufferedInputStream(file);
     DataInputStream data =
        new DataInputStream(buffered)) {

    return data.readInt();
}
// Close order:
// data, buffered, file.

Declare ownership once

Closing an outer decorator usually closes its delegate. Declaring every layer is legal, but application contracts should make resource ownership clear and avoid independently closing a borrowed resource.

19. Suppressed exceptions

If the try body or a resource initializer has already thrown, later close failures are attached to the primary throwable with addSuppressed. They are available through getSuppressed and normally appear in printed stack traces.[2]

try {
    useResource();
} catch (Exception failure) {
    LOGGER.log(
        System.Logger.Level.ERROR,
        "Primary failure: "
            + failure);

    for (Throwable suppressed
            : failure.getSuppressed()) {

        LOGGER.log(
            System.Logger.Level.ERROR,
            "Suppressed close failure: "
                + suppressed);
    }

    throw failure;
}

Manual sibling suppression

Throwable primary =
    firstFailure;

for (Throwable sibling
        : additionalFailures) {

    primary.addSuppressed(
        sibling);
}

throw primary;

Do not confuse suppressed failures with the causal chain: both can coexist.

20. Designing an AutoCloseable resource

AutoCloseable.close() may declare Exception, though implementations are encouraged to declare more specific exceptions or none. The API warns that suppressing InterruptedException can interact badly with thread interruption, so close methods should not throw it when suppression would be harmful.[7]

public final class Transaction
        implements AutoCloseable {

    private boolean committed;
    private boolean closed;

    public void commit()
            throws TransactionException {

        ensureOpen();
        writeCommitRecord();
        committed = true;
    }

    @Override
    public void close()
            throws TransactionException {

        if (closed) {
            return;
        }

        closed = true;

        if (!committed) {
            rollback();
        }
    }

    private void ensureOpen() {
        if (closed) {
            throw new IllegalStateException(
                "Transaction is closed");
        }
    }
}

Close design goals

  • Document idempotence or single-close behavior.
  • Make partial initialization safe to close.
  • Keep close bounded and avoid surprising blocking where possible.
  • Preserve the resource's primary domain failure.

21. Custom checked exceptions

Domain contract A custom checked exception extends Exception or another checked exception class. Provide constructors that preserve detail messages and causes, and include structured fields when callers need machine-readable context.[8]

public final class
ConfigurationFormatException
        extends Exception {

    private final Path source;
    private final int line;

    public ConfigurationFormatException(
            Path source,
            int line,
            String message) {

        super(message);
        this.source =
            Objects.requireNonNull(
                source);
        this.line = line;
    }

    public ConfigurationFormatException(
            Path source,
            int line,
            String message,
            Throwable cause) {

        super(message, cause);
        this.source =
            Objects.requireNonNull(
                source);
        this.line = line;
    }

    public Path source() {
        return source;
    }

    public int line() {
        return line;
    }
}

When checked is appropriate

Use a checked domain exception when callers at the immediate boundary are expected to distinguish, recover, retry, prompt, or select an alternative.

22. Custom unchecked exceptions

A custom unchecked exception extends RuntimeException or one of its subclasses. Use it for violated preconditions, invalid state, unsupported application operations, or abstraction-level failures that callers generally cannot recover from locally.[3]

public final class
UnknownOrderStateException
        extends IllegalStateException {

    private final OrderId orderId;
    private final String state;

    public UnknownOrderStateException(
            OrderId orderId,
            String state) {

        super(
            "Unknown state "
                + state
                + " for order "
                + orderId);

        this.orderId =
            Objects.requireNonNull(
                orderId);

        this.state =
            Objects.requireNonNull(
                state);
    }

    public OrderId orderId() {
        return orderId;
    }

    public String state() {
        return state;
    }
}

Avoid one class per sentence

Create a distinct exception type when handlers need to distinguish it, when it marks an abstraction boundary, or when it carries a stable contract—not merely to rephrase a message.

23. Exception messages and structured context

Actionable message

throw new IllegalArgumentException(
    "maximumRetries must be between "
        + "0 and 10; was "
        + maximumRetries);

Parameter null checks

this.repository =
    Objects.requireNonNull(
        repository,
        "repository");

Objects.requireNonNull is designed for parameter and constructor validation and returns the validated reference, allowing assignment and checking in one expression.[9]

Structured data beats message parsing

catch (RateLimitException failure) {
    scheduleRetry(
        failure.retryAfter());
}
  • State what operation failed.
  • Include stable identifiers, bounds, and relevant non-secret values.
  • Avoid credentials, tokens, personal data, and full payloads.
  • Do not require callers to parse prose to recover structured data.

24. Exception chaining

Exception chaining preserves a lower-level throwable as the cause of a higher-level one. Standard throwable constructors support message-and-cause and cause-only forms.[2]

try {
    return parser.parse(text);
} catch (LowLevelParseException failure) {
    throw new ConfigurationFormatException(
        path,
        failure.line(),
        "Invalid configuration in "
            + path,
        failure);
}

Preserve the original cause

// Wrong:
throw new ConfigurationException(
    failure.getMessage());

// Correct:
throw new ConfigurationException(
    "Unable to read configuration",
    failure);

The causal chain preserves original type, message, and stack frames for diagnosis.

25. Exception translation at abstraction boundaries

Translate an exception when a lower-layer type would leak an implementation detail or provide the wrong abstraction to callers. Throwable explicitly supports wrapping to preserve flexibility in upper-layer APIs.[2]

public Customer load(
        CustomerId id)
        throws RepositoryException {

    try {
        return jdbcLoad(id);
    } catch (SQLException failure) {
        throw new RepositoryException(
            "Unable to load customer "
                + id,
            failure);
    }
}

Do not translate repeatedly without value

Every wrapper should add a meaningful abstraction, stable context, or handler distinction. Deep chains of generic “service failed” exceptions add noise.

26. Do not swallow failures

Empty catch

try {
    save();
} catch (IOException ignored) {
    // Failure disappears.
}

At minimum, decide explicitly

try {
    deleteTemporaryFile();
} catch (NoSuchFileException ignored) {
    // Idempotent cleanup: already absent.
} catch (IOException failure) {
    cleanupFailures.add(
        failure);
}

Legitimate ignoring requires a contract

Ignoring an exception can be correct when the failure is explicitly irrelevant, such as deleting an already absent temporary file. Narrow the caught type, comment the reason, and preserve unexpected alternatives.

27. Catching Exception or Throwable

Application boundary

try {
    requestHandler.handle(request);
} catch (Exception failure) {
    LOGGER.log(
        System.Logger.Level.ERROR,
        "Unhandled request failure",
        failure);

    return internalServerError(
        correlationId);
}

Catching Exception can be appropriate at a request, job, event-loop, or command boundary that must isolate one operation. It should not replace specific handling inside the application.

Throwable boundary

try {
    plugin.run();
} catch (Throwable failure) {
    recordFatalPluginFailure(
        failure);

    throw failure;
}

Catch Throwable only for minimal diagnostics, containment, or mandatory cleanup and normally rethrow it. Catching it also receives serious errors whose recovery assumptions may be invalid.

28. Validation exceptions

Null argument

Objects.requireNonNull(
    request,
    "request");

Invalid argument value

if (pageSize < 1
        || pageSize > 1_000) {

    throw new IllegalArgumentException(
        "pageSize must be 1..1000; was "
            + pageSize);
}

Invalid object state

if (closed) {
    throw new IllegalStateException(
        "Session is closed");
}

Batch validation result

When multiple user-correctable validation errors should be reported together, a typed result containing all violations is usually better than throwing at the first field.

29. I/O exception boundary

IOException is the general checked superclass for failures during I/O operations, with more specific subclasses for EOF, filesystem, networking, character coding, and other conditions.[10]

public Document readDocument(
        Path path)
        throws DocumentAccessException {

    try {
        byte[] bytes =
            Files.readAllBytes(path);

        return decoder.decode(bytes);
    } catch (NoSuchFileException failure) {
        throw new DocumentNotFoundException(
            path,
            failure);
    } catch (AccessDeniedException failure) {
        throw new DocumentPermissionException(
            path,
            failure);
    } catch (IOException failure) {
        throw new DocumentAccessException(
            path,
            failure);
    }
}

Specific translation preserves distinctions that callers can use while hiding filesystem implementation details.

30. InterruptedException

InterruptedException is a checked signal used by blocking operations when a thread is interrupted. Many methods clear the thread's interrupted status when throwing it, so code that cannot propagate the exception should usually restore the status with Thread.currentThread().interrupt().[11]

Propagate when possible

public Result waitForResult()
        throws InterruptedException {

    return queue.take();
}

Restore when translating

try {
    return queue.take();
} catch (InterruptedException failure) {
    Thread.currentThread()
        .interrupt();

    throw new OperationCancelledException(
        "Interrupted while waiting",
        failure);
}
Do not log and continue as though nothing happened. Interruption is a cooperative cancellation/request signal, not an ordinary transient error.

31. Exceptions from Future

Future.get() reports a task's thrown exception through checked ExecutionException; its cause is the original task failure.[12]

try {
    return future.get(
        timeout.toMillis(),
        TimeUnit.MILLISECONDS);
} catch (ExecutionException failure) {
    Throwable cause =
        failure.getCause();

    if (cause
            instanceof DomainException domain) {
        throw domain;
    }

    throw new TaskFailedException(
        "Background task failed",
        cause);
} catch (InterruptedException failure) {
    Thread.currentThread()
        .interrupt();

    throw new OperationCancelledException(
        failure);
}

Unwrap at the boundary

Do not discard the wrapper blindly; translate the cause according to the API contract of the waiting layer.

32. Exceptional completion in CompletionStage

CompletionException is an unchecked wrapper used when a completion encounters an exception or error. Completion stages propagate exceptional completion to dependent stages; exceptionally, handle, and whenComplete provide different recovery and observation semantics.[13][14]

CompletableFuture<Profile> profile =
    client.loadProfile(userId)
        .exceptionally(failure -> {
            Throwable cause =
                unwrapCompletion(
                    failure);

            if (cause
                    instanceof NotFoundException) {
                return Profile.empty(
                    userId);
            }

            throw new CompletionException(
                new ProfileLoadException(
                    userId,
                    cause));
        });

Observe without replacing

stage.whenComplete(
    (value, failure) -> {
        if (failure != null) {
            metrics.failed();
        } else {
            metrics.succeeded();
        }
    });

Side effects from already-started asynchronous work are not rolled back when a dependent stage fails.

33. Uncaught exception handlers

When a thread is about to terminate because of an uncaught throwable, the JVM invokes its configured Thread.UncaughtExceptionHandler, or falls back through its thread group and default handler.[15]

ThreadFactory factory =
    Thread.ofPlatform()
        .name(
            "worker-",
            0)
        .uncaughtExceptionHandler(
            (thread, failure) ->
                LOGGER.log(
                    System.Logger.Level.ERROR,
                    "Uncaught failure in "
                        + thread.getName(),
                    failure))
        .factory();

An uncaught handler is a final diagnostic boundary, not a recovery mechanism for continuing the failed thread's operation.

34. Helpful NullPointerException messages

JEP 358, delivered in JDK 14, added JVM-generated null-detail messages that identify which expression was null for many JVM-thrown NullPointerExceptions. Explicitly constructed NPEs do not receive the same bytecode-derived detail.[16]

// A JVM-thrown NPE can identify
// which dereference in the chain was null.
String city =
    order.customer()
        .address()
        .city();

Still validate public preconditions

public Service(
        Repository repository) {

    this.repository =
        Objects.requireNonNull(
            repository,
            "repository");
}

Helpful diagnostics do not replace explicit domain validation or nullness design.

35. Exceptions versus result types

SituationPrefer
Invariant violation or programmer errorUnchecked exception
Recoverable external operation failureChecked/domain exception when callers act on it
Ordinary absenceOptional, empty collection, or null-free domain model
Several expected validation errorsTyped validation result
High-frequency branch in parsing/probingStatus/result value rather than exceptions as control flow
Asynchronous failureExceptional completion plus typed cause

Sealed result example

sealed interface PaymentResult {
    record Approved(
        Receipt receipt)
        implements PaymentResult {
    }

    record Declined(
        DeclineReason reason)
        implements PaymentResult {
    }
}

A declined card may be an expected business result rather than an exceptional software failure.

36. Logging exceptions once, at the right boundary

Log the throwable, not only its message

LOGGER.log(
    System.Logger.Level.ERROR,
    "Unable to process order "
        + orderId,
    failure);

Avoid log-and-rethrow duplication

// Usually noisy:
catch (RepositoryException failure) {
    LOGGER.log(
        System.Logger.Level.ERROR,
        "Repository failed",
        failure);

    throw failure;
}

If an upstream boundary will log the same failure with adequate context, add context through exception translation and let that boundary log once. Duplicate logging inflates incident counts and obscures the causal chain.

Use appropriate severity

  • Expected validation rejection is not necessarily an error log.
  • A retryable dependency outage may be warning or error depending on exhaustion.
  • An uncaught operation failure at a boundary normally deserves the full throwable.
  • Do not log secrets, access tokens, raw credentials, or sensitive payloads.

37. Stack traces and stack inspection

Each StackTraceElement represents one frame in a throwable's stack trace, with class, method, source file, line, module, and class-loader information where available.[17]

for (StackTraceElement frame
        : failure.getStackTrace()) {

    System.err.println(
        frame.getClassName()
            + "."
            + frame.getMethodName()
            + ":"
            + frame.getLineNumber());
}

Inspect the current thread without creating an exception

StackWalker provides lazy, configurable traversal of the current thread's stack and hides reflection implementation frames by default.[18]

String caller =
    StackWalker
        .getInstance()
        .walk(frames ->
            frames.skip(1)
                .findFirst()
                .map(frame ->
                    frame.getClassName()
                        + "#"
                        + frame.getMethodName())
                .orElse(
                    "<unknown>"));

Do not rewrite stack traces casually

Removing or replacing frames can make diagnosis misleading. Translate with a cause rather than manufacturing a new root failure without provenance.

38. Exception performance and allocation

Creating a normal throwable typically captures stack-trace state, and throwing requires stack unwinding and handler search. Exact costs depend on JVM optimization, stack depth, exception type, and whether stack traces are writable.[2]

Do not use exceptions for ordinary hot-path branching

// Avoid when invalid input is common:
try {
    return Integer.parseInt(text);
} catch (NumberFormatException failure) {
    return fallback;
}

Exception is appropriate when invalid input is exceptional

static int requirePort(
        String text) {

    int port =
        Integer.parseInt(text);

    if (port < 1
            || port > 65_535) {
        throw new IllegalArgumentException(
            "Port out of range: "
                + port);
    }

    return port;
}

Do not disable stack traces globally for convenience

Custom no-stack exceptions can be justified for carefully measured internal control transfer, but they remove essential production diagnostics and should not be default public failures.

Test interruption

  • The method propagates InterruptedException, or restores interrupted status when translating.
  • Locks, permits, resources, and partial state are released.
  • Cancellation completes within a bound.

Test every catch branch

Inject failures at the dependency boundary rather than relying on unstable operating-system conditions. Include primary failure, cleanup failure, both together, empty causes, and unexpected runtime failures.

Parser boundary

public final class DocumentParser {
    public Document parse(
            BufferedReader reader)
            throws DocumentFormatException,
                   IOException {

        String header =
            reader.readLine();

        if (header == null) {
            throw new DocumentFormatException(
                1,
                "Missing header",
                null);
        }

        try {
            return parseBody(
                header,
                reader);
        } catch (NumberFormatException failure) {
            throw new DocumentFormatException(
                currentLine(),
                "Invalid numeric field",
                failure);
        }
    }
}

Repository transaction

public interface ImportTransaction
        extends AutoCloseable {

    boolean exists(DocumentId id)
        throws RepositoryException;

    void insert(Document document)
        throws RepositoryException;

    void commit()
        throws RepositoryException;

    @Override
    void close()
        throws RepositoryException;
}

Service implementation

public final class DocumentImportService {
    private final DocumentParser parser;
    private final ImportRepository repository;

    public DocumentImportService(
            DocumentParser parser,
            ImportRepository repository) {

        this.parser =
            Objects.requireNonNull(parser);

        this.repository =
            Objects.requireNonNull(
                repository);
    }

    public Document importFile(
            Path path)
            throws DocumentImportException,
                   InterruptedException {

        Objects.requireNonNull(
            path,
            "path");

        if (Thread.interrupted()) {
            throw new InterruptedException(
                "Import interrupted before start");
        }

        Document document;

        try (BufferedReader reader =
                Files.newBufferedReader(
                    path,
                    StandardCharsets.UTF_8)) {

            document =
                parser.parse(reader);
        } catch (DocumentFormatException failure) {
            throw failure;
        } catch (IOException failure) {
            throw new DocumentAccessException(
                path,
                failure);
        }

        try (ImportTransaction transaction =
                repository.begin()) {

            if (transaction.exists(
                    document.id())) {

                throw new DuplicateDocumentException(
                    document.id());
            }

            transaction.insert(document);
            transaction.commit();

            return document;
        } catch (DuplicateDocumentException failure) {
            throw failure;
        } catch (RepositoryException failure) {
            throw new DocumentPersistenceException(
                document.id(),
                failure);
        }
    }
}

Boundary handler

try {
    Document imported =
        service.importFile(path);

    return ImportResponse.success(
        imported.id());
} catch (DuplicateDocumentException failure) {
    return ImportResponse.conflict(
        failure.id());
} catch (DocumentFormatException failure) {
    return ImportResponse.invalid(
        failure.line(),
        failure.getMessage());
} catch (DocumentAccessException failure) {
    return ImportResponse.unavailable(
        failure.path());
} catch (InterruptedException failure) {
    Thread.currentThread()
        .interrupt();

    return ImportResponse.cancelled();
} catch (DocumentImportException failure) {
    LOGGER.log(
        System.Logger.Level.ERROR,
        "Import failed for "
            + path,
        failure);

    return ImportResponse.failed();
}

Design properties

  • Checked domain types expose recoverable import outcomes.
  • I/O and repository exceptions are translated at boundaries with causes preserved.
  • Try-with-resources owns the reader and transaction.
  • Transaction close failures are suppressed when a primary body failure exists.
  • Interruption is propagated and restored at the outer boundary.
  • Structured exception fields prevent message parsing.
  • The handler logs only the unexpected generic domain failure.

42. Production checklist

Exception taxonomy

  • Checked exceptions represent failures immediate callers can reasonably handle.
  • Unchecked exceptions represent precondition, state, or non-local unrecoverable failures.
  • Error is not used for application-domain conditions.
  • Expected absence and validation aggregation use result types where clearer.

Throwing and declaring

  • Messages include operation, stable identifiers, and relevant bounds.
  • Sensitive information is excluded.
  • Public checked declarations are narrow and abstraction-appropriate.
  • Overriding methods obey checked-exception narrowing rules.
  • Causes are preserved through translation.

Handling

  • Try blocks are narrow enough to avoid accidental catches.
  • Specific catches precede general catches.
  • Multi-catch is used only for identical policy.
  • Handlers recover, translate, add context, or terminate the operation.
  • Broad catches exist only at deliberate isolation boundaries.
  • Failures are logged once with the full throwable.

Cleanup and resources

  • Every owned closeable resource uses try-with-resources.
  • Resource initialization and reverse close order are understood.
  • Suppressed cleanup failures remain observable.
  • Finally blocks complete normally and do not return.
  • Locks and permits are released in finally.
  • Close methods have bounded, documented behavior.

Concurrency

  • InterruptedException is propagated or interrupted status is restored.
  • ExecutionException and CompletionException causes are unwrapped at the right boundary.
  • Asynchronous exceptional completion is not mistaken for rollback.
  • Uncaught handlers are treated as diagnostic last resorts.

Testing and operation

  • Exception type, cause, structured fields, and suppression are tested.
  • Cleanup failures and combined body/close failures are covered.
  • Helpful stack traces are preserved.
  • High-frequency invalid inputs do not rely on exceptions without measurement.
  • Microbenchmarks use JMH and production tests include failure injection.
Final principle: exception handling is the design of failure ownership. Reliable Java code signals a precise type, preserves causes, cleans up deterministically, respects interruption, handles only what it can make valid, and reports failures once at the boundary that owns the outcome.
