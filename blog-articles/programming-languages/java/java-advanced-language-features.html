1. Three levels of Java program structure

Advanced Java design operates simultaneously at the type level, package level, and module level. Classes and interfaces model values and behavior; packages organize names and package-private collaboration; modules define readable dependencies, exported API packages, reflective openness, and service-provider relationships.

module: com.example.orders ├── exports com.example.orders.api ├── opens com.example.orders.internal.dto to framework.json └── packages ├── com.example.orders.api │ ├── Order.java │ └── OrderService.java └── com.example.orders.internal ├── DefaultOrderService.java └── SqlOrderRepository.java

A compilation unit can declare a package, import names, and declare top-level classes or interfaces. A modular compilation unit declares a named module. Imports affect simple-name resolution; they do not grant access that package or module rules deny.[1]

Names, access, and readability are separate. A type can be found by a fully qualified name yet remain inaccessible; a public type can remain hidden because its package is not exported; a package can be opened for reflection without being exported for ordinary source access.

2. Packages

Namespace A package groups top-level classes and interfaces under a qualified name. A package declaration, when present, must precede imports and top-level declarations.

package com.example.billing.api;

public interface InvoiceService {
    Invoice issue(
        InvoiceRequest request);
}

Packages are not nested access scopes

com.example and com.example.billing are distinct packages. A parent-looking name does not grant access to package-private members in a child package, nor vice versa.[2]

Unnamed package

A compilation unit without a package declaration belongs to an unnamed package. It is suitable for small exploratory programs but not for maintainable libraries or named modules.[1]

Reverse-domain naming

com.example.product.feature
org.example.library.spi
io.example.tooling.cli

Package naming conventions are not enforced by the language, but globally distinctive names reduce collision risk across independently produced libraries.

3. Source and package structure

The compiler expects source and class files to be arranged according to package-oriented search paths. A public top-level type is conventionally stored in a source file whose name matches the type.[3]

src/main/java/ └── com/example/catalog/ ├── package-info.java ├── Product.java ├── ProductRepository.java └── internal/ └── InMemoryProductRepository.java
javac \
  -d build/classes \
  src/main/java/com/example/catalog/Product.java

Package cohesion

  • Group types that collaborate around one stable responsibility.
  • Keep internal implementation packages separate from exported API packages.
  • Avoid “util” packages that become unrelated dumping grounds.
  • Prefer package-private collaboration over making every implementation type public.

4. Package documentation and annotations

A package-info.java compilation unit is the conventional location for package documentation and package annotations.

/**
 * Public API for invoice creation and lookup.
 *
 * <p>Implementations are not part of the
 * compatibility contract.
 */
@NullMarked
package com.example.invoice.api;

import org.jspecify.annotations.NullMarked;

One annotated package declaration

The language permits package annotations but requires at most one annotated package declaration for a package.[1]

Use package documentation for architecture

Document ownership, nullness policy, threading assumptions, extension points, and which subpackages are internal.

5. Imports

Imports let code use simple names for types and static members. They do not load classes, copy declarations, create dependencies by themselves, or override access control.[1]

package com.example.report;

import java.time.Instant;
import java.util.List;
import static java.util.Comparator.comparing;
import static java.util.Objects.requireNonNull;

Import forms

FormExample
Single typeimport java.util.List;
Type on demandimport java.util.*;
Single static memberimport static java.lang.Math.PI;
Static on demandimport static java.lang.Math.*;

On-demand imports do not recurse

import java.util.*; does not import java.util.concurrent. Subpackages are separate packages.

Name ambiguity

import java.awt.List;
import java.util.List;
// Compile-time ambiguity.

Resolve collisions with one fully qualified name or narrower imports.

6. Java 25 module import declarations

Java 25 Java 25 finalized module import declarations. import module M; imports, on demand, public top-level types from packages exported by module M to the current module, including appropriate transitive exports.[4]

import module java.base;

public class WordCount {
    public static void main(
            String[] arguments) {

        Map<String, Long> counts =
            Stream.of(arguments)
                .collect(
                    Collectors.groupingBy(
                        Function.identity(),
                        Collectors.counting()));

        counts.forEach(
            System.out::println);
    }
}

It is still only an import

A module import does not add a requires directive to a named module and does not bypass exports, readability, or ordinary access control.

Ambiguity remains possible

If imported modules export types with the same simple name, use a single-type import or qualified type name to disambiguate.

7. Visibility and access control

Java access control restricts references to top-level types and members. The four member-access levels are public, protected, package access (no modifier), and private.[2]

ModifierSame top-level class/nestSame packageSubclass elsewhereOther code
privateYesNoNoNo
Package accessYesYesNoNo
protectedYesYesQualified subclass rulesNo
publicYesYesYesYes, subject to module export/readability

Top-level declarations

A top-level class or interface is either public or package-access; it cannot be protected or private.

Package-private implementation

package com.example.cache;

final class SegmentedCache
        implements Cache {
    // Visible only within this package.
}

8. The subtleties of protected

Protected members are accessible throughout the declaring package. Outside the package, access must occur from subclass code and is constrained by the qualifying expression.

package api;

public class Base {
    protected int value;
}
package extension;

public class Derived extends api.Base {
    void update(Derived other) {
        other.value = 10;
        this.value = 20;
    }

    void invalid(api.Base other) {
        // other.value = 30;
        // Not permitted across packages:
        // qualifier is merely Base.
    }
}

Protected access is not “public to all subclasses everywhere.” It exists to support inheritance while retaining package collaboration rules.[2]

9. Visibility across module boundaries

A public type in a named module is ordinarily accessible to another named module only when the first module exports its package and the second module reads the first. Reflection requiring access beyond public exported members additionally depends on package openness.

public member + public top-level type + package exported by module A + module B reads module A = ordinary cross-module access
module com.example.library {
    exports com.example.library.api;
    // com.example.library.internal
    // remains strongly encapsulated.
}

Core reflection enforces language access plus module readability, exports, and opens rules unless access can legitimately be enabled under AccessibleObject.[5]

10. Enumeration classes

Closed value set An enum class defines a fixed set of named instances. Every enum class extends java.lang.Enum implicitly and cannot explicitly extend another class.[6]

public enum DeploymentState {
    PENDING,
    RUNNING,
    SUCCEEDED,
    FAILED
}

Compiler-provided members

DeploymentState state =
    DeploymentState.valueOf(
        "RUNNING");

DeploymentState[] values =
    DeploymentState.values();

String stableName =
    state.name();

int ordinal =
    state.ordinal();

name() is the declared identifier. ordinal() is the zero-based declaration position and should not be persisted as a stable external protocol value.

Switch exhaustiveness

String label =
    switch (state) {
        case PENDING -> "Waiting";
        case RUNNING -> "Running";
        case SUCCEEDED -> "Complete";
        case FAILED -> "Failed";
    };

External representation

Define an explicit wire/database code when names may evolve.

enum Status {
    ACTIVE("A"),

12. EnumSet and EnumMap

EnumSet and EnumMap are specialized collections for enum keys/elements. They are compact, type-safe, and iterate in enum declaration order.

EnumSet<Permission> writePermissions =
    EnumSet.of(
        Permission.READ,
        Permission.WRITE);

EnumMap<DeploymentState, Duration>
    timeoutByState =
        new EnumMap<>(
            DeploymentState.class);

timeoutByState.put(
    DeploymentState.RUNNING,
    Duration.ofMinutes(30));

Use them instead of integer bit masks or general-purpose hash collections when the domain key is an enum.[7]

13. Record classes

Data carrier A record class declares a fixed state description. For each record component, the compiler derives a private final field, public accessor, canonical constructor participation, and state-based equals, hashCode, and toString behavior.[8]

public record Coordinate(
    double latitude,
    double longitude) {
}

Usage

Coordinate point =
    new Coordinate(
        35.7796,
        -78.6382);

double latitude =
    point.latitude();

Coordinate same =
    new Coordinate(
        35.7796,
        -78.6382);

assert point.equals(same);

Records are classes

Records can implement interfaces, declare static members, instance methods, nested types, and validation constructors. They are implicitly final and extend java.lang.Record.[9]

14. Canonical and compact record constructors

Compact canonical constructor

public record Percentage(
        int value) {

    public Percentage {
        if (value < 0
                || value > 100) {
            throw new IllegalArgumentException(
                "value must be 0..100");
        }
    }
}

Defensive copying

public record Team(
        String name,
        List<Member> members) {

    public Team {
        name =
            Objects.requireNonNull(name)
                .strip();

        members =
            List.copyOf(members);
    }
}

Additional constructor

public Team(
        String name) {

    this(
        name,
        List.of());
}

A non-canonical record constructor must delegate, directly or indirectly, to the canonical constructor.

15. Record semantics and limitations

A record's API is deliberately coupled to its component list. Record components define nominal state, so changing that list is an API and serialization-shape change.

Shallow immutability

public record UnsafeRecord(
    List<String> values) {
}

// The field is final, but the list can mutate
// unless copied by the constructor.

Custom behavior without breaking the contract

public record Rectangle(
        double width,
        double height) {

    public Rectangle {
        if (width < 0 || height < 0) {
            throw new IllegalArgumentException();
        }
    }

    public double area() {
        return width * height;
    }
}

Not every DTO should be a record

Use an ordinary class when the public abstraction should be decoupled from representation, supports staged mutation, requires identity semantics, or needs subclassing.

16. Reflecting over record components

Class.isRecord() identifies record classes; getRecordComponents() returns their declared component metadata. RecordComponent exposes the component name, type, generic type, annotations, and accessor.[10]

static Map<String, Object>
recordValues(
        Record record)
        throws ReflectiveOperationException {

    Class<?> type =
        record.getClass();

    if (!type.isRecord()) {
        throw new IllegalArgumentException();
    }

    Map<String, Object> result =
        new LinkedHashMap<>();

    for (RecordComponent component
            : type.getRecordComponents()) {

        Object value =
            component.getAccessor()
                .invoke(record);

        result.put(
            component.getName(),
            value);
    }

    return Map.copyOf(result);
}

17. Sealed classes and interfaces

Restricted hierarchy A sealed class or interface restricts which types may directly extend or implement it. Each permitted direct subtype must be declared final, sealed, or non-sealed.[11]

public sealed interface PaymentResult
        permits Approved,
                Declined,
                ReviewRequired {
}

public record Approved(
        Receipt receipt)
        implements PaymentResult {
}

public record Declined(
        DeclineReason reason)
        implements PaymentResult {
}

public non-sealed class ReviewRequired
        implements PaymentResult {
    // Open to further subclasses.
}

Location rule

Permitted direct subtypes must belong to the same named module as the sealed supertype; in the unnamed module, they must be in the same package.

Inferred permits

The permits clause can be omitted when all direct permitted subtypes are declared in the same compilation unit and can be inferred by the compiler.

18. Modeling exhaustive alternatives

static String describe(
        PaymentResult result) {

    return switch (result) {
        case Approved(
                Receipt receipt) ->
            "Approved: "
                + receipt.number();

        case Declined(
                DeclineReason reason) ->
            "Declined: "
                + reason;

        case ReviewRequired review ->
            "Review: "
                + review;
    };
}

Sealed hierarchies work especially well with final classes and records because the compiler can reason about a closed set of direct alternatives. A non-sealed branch reopens that part of the hierarchy.

Reflection

Class<?> type =
    PaymentResult.class;

boolean sealed =
    type.isSealed();

Class<?>[] permitted =
    type.getPermittedSubclasses();

The class-file representation records permitted subclasses, and core reflection exposes them at run time.

19. Nested-class taxonomy

A nested class is declared within another class or interface. It can be a member class, local class, or anonymous class. An inner class is a nested class that is not explicitly or implicitly static.[12]

nested classes ├── member classes │ ├── static nested class │ └── non-static member class (inner) ├── local class │ ├── ordinary local class (inner) │ ├── local enum (implicitly static) │ └── local record (implicitly static) └── anonymous class (inner)

Implicitly static nested types

Nested interfaces, enum classes, record classes, annotation interfaces, and member classes declared in interfaces are implicitly static.

20. Static nested classes

No enclosing instance A static nested class is a member of its enclosing class but has no implicit reference to an enclosing instance.

public final class Graph {
    private final List<Node> nodes;

    public static final class Node {
        private final String name;

        public Node(String name) {
            this.name =
                Objects.requireNonNull(name);
        }

        public String name() {
            return name;
        }
    }

    public Graph(
            List<Node> nodes) {

        this.nodes =
            List.copyOf(nodes);
    }
}

Use cases

  • Builders and factories tightly coupled to one public type.
  • Implementation helpers that need access to private members but not an enclosing object.
  • Namespacing related value types.

Instantiation

Graph.Node node =
    new Graph.Node("A");

21. Non-static member inner classes

Enclosing instance An inner member class is associated with an instance of its enclosing class and can access that instance's members, including private members.

public final class Counter {
    private int value;

    public final class IncrementCommand {
        private final int amount;

        public IncrementCommand(
                int amount) {
            this.amount = amount;
        }

        public int execute() {
            value += amount;
            return value;
        }

        public Counter owner() {
            return Counter.this;
        }
    }
}

Construction

Counter counter =
    new Counter();

Counter.IncrementCommand command =
    counter.new IncrementCommand(5);

Retention hazard

An inner-class instance retains its enclosing instance. Long-lived callbacks, iterators, or cache entries can therefore retain a much larger object graph than intended.

22. Local classes

A local class is declared inside a block, commonly within a method. It has a lexical scope and can capture final or effectively final local variables.

static Comparator<Path>
byExtensionThenName(
        boolean ignoreCase) {

    class PathComparator
            implements Comparator<Path> {

        @Override
        public int compare(
                Path left,
                Path right) {

            String first =
                extension(left);

            String second =
                extension(right);

            int result =
                ignoreCase
                    ? first.compareToIgnoreCase(
                        second)
                    : first.compareTo(second);

            return result != 0
                ? result
                : left.compareTo(right);
        }
    }

    return new PathComparator();
}

When useful

Use a local class when behavior needs multiple methods, named state, or a recursive self-reference but is meaningful only inside one method.

Local records

record IndexedValue<T>(
    int index,
    T value) {
}

A local record is implicitly static and therefore does not capture enclosing local variables.

23. Anonymous classes

An anonymous class is declared and instantiated in one class-instance-creation expression. It has no source-level name, cannot declare explicit constructors, and extends one class or implements one interface.[13]

Comparator<String> byLength =
    new Comparator<>() {
        @Override
        public int compare(
                String left,
                String right) {

            return Integer.compare(
                left.length(),
                right.length());
        }
    };

With state and several methods

Iterator<Integer> iterator =
    new Iterator<>() {
        private int next;

        @Override
        public boolean hasNext() {
            return next < limit;
        }

        @Override
        public Integer next() {
            if (!hasNext()) {
                throw new NoSuchElementException();
            }

            return next++;
        }
    };

Prefer lambdas for functional interfaces

Comparator<String> byLength =
    Comparator.comparingInt(
        String::length);

Anonymous classes remain useful when an object needs identity, mutable fields, several overridden methods, or a distinct this.

24. Captured variables and object lifetime

static Runnable task(
        Path path,
        System.Logger logger) {

    String description =
        path.toAbsolutePath()
            .toString();

    return new Runnable() {
        @Override
        public void run() {
            logger.log(
                System.Logger.Level.INFO,
                description);
        }
    };
}

Local and anonymous inner classes can capture only final or effectively final local variables. Captured references can still point to mutable objects.

Concurrency hazard

List<String> output =
    new ArrayList<>();

Runnable task =
    () ->
        output.add("value");
// Effective-final reference,
// mutable non-thread-safe object.

Minimize capture

Capture only the values the object needs. Avoid accidentally retaining request contexts, UI trees, class loaders, or large service graphs.

25. Generics: compile-time parametric polymorphism

Type parameterization Generics allow classes, interfaces, methods, and constructors to operate over types while preserving compile-time type checking. Type arguments are reference types or wildcards; primitive types are not valid type arguments.[14]

List<String> names =
    new ArrayList<>();

names.add("Ada");

String name =
    names.getFirst();

Invariance

List<Integer> integers =
    List.of(1, 2, 3);

// Illegal:
// List<Number> numbers = integers;

List<? extends Number> numbers =
    integers;

Why invariant?

If List<Integer> were a subtype of List<Number>, code could insert a Double into a list promised to contain integers.

26. Generic classes and interfaces

public final class Box<T> {
    private T value;

    public Box(T value) {
        this.value = value;
    }

    public T get() {
        return value;
    }

    public void set(T value) {
        this.value = value;
    }
}

Multiple parameters

public record Pair<L, R>(
    L left,
    R right) {
}

Static members cannot use the class parameter

class Registry<T> {
    // Illegal:
    // static T shared;

    static <T> Registry<T> empty() {
        return new Registry<>();
    }
}

Generic interfaces

public interface Decoder<S, T> {
    T decode(S source)
        throws DecodeException;
}

27. Generic methods and constructors

A generic method declares its own type parameters before the return type. Its type variables are independent of any enclosing generic class.

static <T> T requireOne(
        Collection<T> values) {

    if (values.size() != 1) {
        throw new IllegalArgumentException(
            "Expected exactly one value");
    }

    return values.iterator()
        .next();
}

Generic factory

static <K, V> Map<K, V>
mapOf(
        K key,
        V value) {

    return Map.of(
        key,
        value);
}

Generic constructor

class Snapshot {
    private final List<Object> values;

    <T> Snapshot(
            Iterable<T> source) {

        List<Object> result =
            new ArrayList<>();

        source.forEach(result::add);

        values =
            List.copyOf(result);
    }
}

28. Upper bounds and intersection bounds

static <T extends Comparable<? super T>>
T maximum(
        Collection<? extends T> values) {

    return values.stream()
        .max(
            Comparator.naturalOrder())
        .orElseThrow();
}

Multiple bounds

static <T extends AutoCloseable
        & Runnable>
void runAndClose(
        T resource)
        throws Exception {

    try (resource) {
        resource.run();
    }
}

At most one class bound is permitted and, if present, it must appear first. The erasure of a type variable is based on its leftmost bound.[14]

Recursive bound

interface Node<N extends Node<N>> {
    N parent();
}

F-bounded forms express operations returning or comparing a more precise self type, but they can make APIs difficult to read. Use them only when the precision has practical value.

PECS

static <T> void copy(
        Collection<? extends T> source,
        Collection<? super T> target) {

    target.addAll(source);
}

Unbounded wildcard

static int sizeOf(
        Collection<?> values) {

    return values.size();
}

Wildcards express the variance relationship required by one API use without introducing a new named type variable.

30. Wildcard capture and helper methods

Problem

static void reverseFirstTwo(
        List<?> values) {

    // Cannot call set safely with Object
    // because the element type is unknown.
}

Capture helper

static void reverseFirstTwo(
        List<?> values) {

    reverseFirstTwoCaptured(values);
}

private static <T> void
reverseFirstTwoCaptured(
        List<T> values) {

    if (values.size() < 2) {
        return;
    }

    T first =
        values.get(0);

    values.set(
        0,
        values.get(1));

    values.set(
        1,
        first);
}

The helper method lets type inference capture the unknown wildcard as one consistent type variable.

31. Type inference and the diamond operator

The compiler infers generic method and constructor type arguments from arguments, target types, bounds, and invocation context.[15]

Map<String, List<Integer>> values =
    new HashMap<>();

List<String> names =
    List.of(
        "Ada",
        "Grace");

Optional<String> first =
    Optional.of("value");

Explicit type witness

List<Number> numbers =
    List.<Number>of(
        1,
        2.5);

var is not dynamic typing

var map =
    new HashMap<String, Integer>();
// Static inferred type:
// HashMap<String,Integer>.

Use explicit type arguments or variable types when inference produces an overly narrow type or obscures the public contract.

32. Type erasure

Runtime translation Java implements most generics through erasure. The erasure of G<T...> is raw type G; a type variable erases to its leftmost bound; method signatures are erased for JVM-level linkage.[14]

source class Box<T> { T get(); } conceptual erased form class Box { Object get(); } casts/checks are inserted at typed use sites

No overload by type argument alone

// Illegal: same erased signature.
void process(
    List<String> values) {
}

void process(
    List<Integer> values) {
}

No class literal for parameterized type

// Illegal:
// Class<List<String>> c =
//     List<String>.class;

Class<List> raw =
    List.class;

33. Reifiable and non-reifiable types

A reifiable type is fully represented at run time. Examples include primitives, non-generic classes, raw types, arrays of reifiable components, and parameterized types whose arguments are all unbounded wildcards.[14]

if (value
        instanceof List<?> list) {

    System.out.println(
        list.size());
}

Illegal parameterized test

// Illegal:
// value instanceof List<String>

Generic arrays

// Illegal:
// T[] values = new T[10];

// Legal with a class token:
static <T> T[] newArray(
        Class<T> type,
        int length) {

    @SuppressWarnings("unchecked")
    T[] result =
        (T[]) Array.newInstance(
            type,
            length);

    return result;
}

34. Heap pollution, raw types, and generic varargs

Heap pollution occurs when a variable of parameterized type refers to an object that is not of that parameterized type. Raw types, unchecked casts, and arrays of non-reifiable component types are common causes.

List raw =
    new ArrayList<Integer>();

raw.add("not an integer");

@SuppressWarnings("unchecked")
List<Integer> integers =
    raw;

Integer value =
    integers.getFirst();
// ClassCastException.

Generic varargs hazard

static void corrupt(
        List<String>... lists) {

    Object[] array = lists;

    array[0] =
        List.of(42);

    String value =
        lists[0].getFirst();
}

@SafeVarargs

@SafeVarargs is a programmer assertion that a constructor or eligible method does not perform unsafe operations on its non-reifiable varargs parameter. It suppresses warnings; it does not make an unsafe body safe.[16]

@SafeVarargs
static <T> List<T> concatenate(
        List<? extends T>... lists) {

    return Arrays.stream(lists)
        .flatMap(List::stream)
        .toList();
}

35. Bridge methods

Erasure can change overriding signatures. The compiler may generate synthetic bridge methods so polymorphism continues to work at the JVM level.

class Parent<T> {
    T value() {
        return null;
    }
}

class Child
        extends Parent<String> {

    @Override
    String value() {
        return "child";
    }
}
source Child: String value() compiler may add bridge: Object value() { return value(); }

Reflection consequence

for (Method method
        : Child.class
            .getDeclaredMethods()) {

    System.out.printf(
        "%s bridge=%s synthetic=%s%n",
        method,

}

Frameworks that enumerate methods must account for bridge and synthetic members rather than treating every reflected method as a separate source declaration.

36. Annotations as structured program metadata

Metadata An annotation is an instance of an annotation interface associated with a declaration or type use. The language defines normal, marker, and single-element annotation syntax.[17]

@Deprecated(
    since = "3.0",
    forRemoval = true)
public void legacyOperation() {
}

Annotation element types

Annotation elements may return primitives, String, Class, enum types, annotation types, or one-dimensional arrays of these forms. Elements cannot accept parameters, type parameters, or checked exceptions.

Metadata needs a consumer

An annotation by itself does not execute behavior. Its meaning comes from the compiler, JVM, annotation processor, framework, test engine, documentation tool, or application code that reads it.

39. @Target, @Retention, and documentation

@Target restricts the declaration and type contexts in which an annotation may appear.[19] @Retention selects whether annotation information is discarded after source processing, retained in the class file, or made available to core reflection at run time. Without @Retention, the default is CLASS.[20]

Public-contract metadata

@Documented tells tools such as Javadoc to include annotations of that annotation interface in generated API documentation.[21]

Inheritance is narrow

@Inherited applies only to annotation lookup on class declarations through the superclass chain. It does not cause annotations to be inherited from interfaces, methods, fields, or constructors.

An annotation targeted at TYPE_USE can appear wherever a type is used, including generic arguments, array components, casts, receiver types, bounds, and throws clauses.

Declaration versus type annotation

Core reflection distinguishes declaration metadata through AnnotatedElement methods and type-use metadata through AnnotatedType structures.

Semantics are external

The JVM does not automatically enforce a custom nullness, taint, unit, or validation annotation. A compiler plugin, static analyzer, bytecode agent, or framework must implement that meaning.

42. Core reflection

Runtime inspection Core reflection consists of Class and the java.lang.reflect package. It exposes loaded classes, fields, methods, constructors, parameters, generic signatures, annotations, record components, arrays, proxies, and access metadata.[23]

Class<?> type =
    Class.forName(
        "com.example.Plugin");

    type.getName());

System.out.println(
    type.getModule()
        .getName());

Reflection models JVM entities

Core reflection fundamentally presents the run-time/JVM model, which can include synthetic and bridge members not written directly in source.

Appropriate uses

  • Dependency injection and serialization frameworks.
  • Testing and inspection tools.
  • Plugin metadata and service adaptation.
  • Debuggers, object browsers, and language runtimes.

48. The Java Platform Module System

JPMS JPMS adds named modules, reliable configuration, strong encapsulation, service declarations, and run-time module layers. It was delivered in Java 9 by JEP 261.[28]

module graph com.example.app │ requires ▼ com.example.api ▲ │ requires com.example.provider service relation app: uses com.example.api.Plugin provider: provides Plugin with JsonPlugin

Module concepts

  • Readability: whether one module can refer to public types in another.
  • Exports: which packages form ordinary public APIs.
  • Opens: which packages allow deep reflective access.
  • Services: decoupled provider discovery.
  • Layers: additional resolved module graphs at run time.

At run time, a named module is represented by java.lang.Module and belongs to a module layer.[29]

49. module-info.java

A normal module descriptor names dependencies, exported and opened packages, consumed services, and service providers. Its compiled form is module-info.class at the root of the modular output or JAR.[30]

module com.example.orders {
    requires java.sql;
    requires transitive
        com.example.money;

    exports com.example.orders.api;

    opens com.example.orders.internal.dto
        to framework.json;

    uses com.example.orders.api.TaxProvider;

    provides
        com.example.orders.api.TaxProvider
        with
        com.example.orders.internal
            .DefaultTaxProvider;
}

Implicit dependence

Every named module reads java.base; an explicit ordinary requires java.base is not normally written.

Descriptor location

src/ └── com.example.orders/ ├── module-info.java └── com/example/orders/ ├── api/ └── internal/

50. requires, requires transitive, and requires static

Ordinary dependence

module com.example.app {
    requires com.example.orders;
}

The module reads the required module, subject to successful resolution.

Transitive dependence

module com.example.orders.api {
    requires transitive
        com.example.money;
}

A module that reads com.example.orders.api also reads com.example.money. Use this when exported API signatures expose types from the depended-on module.

Static dependence

module com.example.integration {
    requires static
        annotations.nullness;
}

A static dependence is mandatory at compile time but optional at run time. It is useful for source/class metadata or optional integrations whose code is not executed unless the module is present.

Do not overuse transitivity

Transitive dependencies enlarge downstream readable graphs and become part of API architecture.

Opening a package permits reflective frameworks to access all types and members using APIs that support suppression of normal access checks. It does not make the package an ordinary source-level API.[29]

Export API; open implementation only where required. An open module is convenient during migration but gives every package broad reflective exposure.

53. Automatic modules and the unnamed module

Unnamed module

Code loaded from the class path belongs to an unnamed module associated with its class loader. It retains class-path compatibility but does not provide an explicit module descriptor or strong package encapsulation.

Automatic module

A non-modular JAR placed on the module path can be treated as an automatic module with a derived or manifest-specified name. Automatic modules ease migration but expose a broad surface and express no precise dependencies.[28]

Migration strategy

  1. Give stable library JARs an Automatic-Module-Name manifest entry before full modularization.
  2. Eliminate split packages and internal cross-package coupling.
  3. Add a descriptor with explicit dependencies and exports.
  4. Replace command-line encapsulation overrides with real module directives.

Split packages

A named module owns complete packages. Designing the same package across several modules causes resolution and class-loading problems and should be eliminated.

Compile a multi-module source tree

javac \

Package a modular JAR

jar \
  --create \

Launch a main class in a module

java \

The java launcher supports -m/--module for selecting a module and main class.[32]

Inspect a modular JAR

jar \
  --describe-module \
  --file dist/com.example.application.jar

Modular JARs store the module descriptor as module-info.class at the archive root; multi-release and automatic-module metadata follow the JAR specification.[33]

55. Dynamic module layers

A ModuleLayer is a run-time layer of modules created from a resolved Configuration and a mapping from modules to class loaders. The boot layer contains the initial application graph.[34]

ModuleFinder finder =
    ModuleFinder.of(
        pluginDirectory);

ModuleLayer parent =
    ModuleLayer.boot();

Configuration configuration =
    parent.configuration()
        .resolve(
            finder,
            ModuleFinder.of(),
            Set.of(
                "com.example.plugin.json"));

ModuleLayer pluginLayer =
    parent.defineModulesWithOneLoader(
        configuration,
        ClassLoader.getSystemClassLoader());

ServiceLoader<Plugin> plugins =
    ServiceLoader.load(
        pluginLayer,
        Plugin.class);

Isolation limits

A layer can use one loader, one loader per module, or a custom mapping. Module layers organize readability and loading, but they are not a security sandbox and do not automatically unload while classes, objects, threads, or caches remain reachable.

56. Complete example: modular command-plugin architecture

API module

module com.example.command.api {
    exports com.example.command.api;
}
package com.example.command.api;

public sealed interface CommandResult
        permits Success,
                Failure {
}

public record Success(
        String message)
        implements CommandResult {

    public Success {
        message =
            Objects.requireNonNull(message);
    }
}

public record Failure(
        String code,
        String message)
        implements CommandResult {

    public Failure {
        code =
            Objects.requireNonNull(code);

        message =
            Objects.requireNonNull(message);
    }
}

public interface Command {
    String name();

    CommandResult execute(
        List<String> arguments);
}

Built-in provider module

module com.example.command.echo {
    requires com.example.command.api;

    provides com.example.command.api.Command
        with com.example.command.echo.EchoCommand;
}
package com.example.command.echo;

public final class EchoCommand
        implements Command {

    public EchoCommand() {
    }

    @Override
    public String name() {
        return "echo";
    }

    @Override
    public CommandResult execute(
            List<String> arguments) {

        return new Success(
            String.join(
                " ",
                arguments));
    }
}

Application module

module com.example.command.app {
    requires com.example.command.api;

    uses com.example.command.api.Command;
}

Registry using generics and annotations

@Documented
@Retention(
    RetentionPolicy.RUNTIME)
@Target(
    ElementType.TYPE)
public @interface CommandMetadata {
    String description();

    boolean experimental()
        default false;
}
public final class CommandRegistry {
    private final Map<String, Command>
        byName;

    private CommandRegistry(
            Map<String, Command> byName) {

        this.byName =
            Map.copyOf(byName);
    }

    public static CommandRegistry load() {
        Map<String, Command> result =
            new TreeMap<>();

        for (Command command
                : ServiceLoader.load(
                    Command.class)) {

            Command previous =
                result.putIfAbsent(
                    command.name(),
                    command);

            if (previous != null) {
                throw new IllegalStateException(
                    "Duplicate command: "
                        + command.name());
            }
        }

        return new CommandRegistry(
            result);
    }

    public Optional<Command> find(
            String name) {

        return Optional.ofNullable(
            byName.get(name));
    }

    public List<String> names() {
        return List.copyOf(
            byName.keySet());
    }
}

Execution with exhaustive sealed-result handling

CommandResult result =
    registry.find(commandName)
        .map(command ->
            command.execute(arguments))
        .orElseGet(() ->
            new Failure(
                "unknown-command",
                commandName));

int exitCode =
    switch (result) {
        case Success(
                String message) -> {
            System.out.println(message);
            yield 0;
        }

        case Failure(
                String code,
                String message) -> {
            System.err.printf(
                "%s: %s%n",
                code,
                message);
            yield 1;
        }
    };

Architecture properties

  • Packages expose only the service API; provider implementation packages stay unexported.
  • Records represent immutable command results.
  • A sealed result hierarchy enables exhaustive handling.
  • ServiceLoader discovers providers without reflection over implementation packages.
  • Generics preserve registry key/value types.
  • Runtime annotations add optional metadata without changing the service interface.
  • Additional providers can be loaded in child module layers.

57. Testing advanced language features

Compile-time tests

  • Inaccessible package-private and protected members fail compilation from the wrong context.
  • Sealed hierarchies reject unauthorized direct subtypes.
  • Generic APIs reject unsafe calls without raw-type escape hatches.
  • Annotations reject invalid targets and missing required elements.
  • Named modules fail resolution when dependencies or service types are missing.

60. Production checklist

Packages and access

  • Packages represent cohesive responsibilities and use globally distinctive names.
  • Package-private types and members keep implementations out of public APIs.
  • Protected access is used with its cross-package qualifier rules understood.
  • Imports are treated as name-resolution tools, not dependency or access declarations.
  • Module imports are used deliberately and ambiguities are controlled.

Advanced types

  • Enum external values use stable explicit codes rather than ordinals.
  • Records are used for transparent state carriers and defensively copy mutable components.
  • Sealed hierarchies model genuinely closed alternatives.
  • Every permitted subtype chooses final, sealed, or non-sealed intentionally.
  • Static nested classes are preferred when no enclosing instance is required.
  • Local and anonymous classes capture only minimal state.

Generics

  • Public APIs avoid raw types and unchecked casts.
  • Bounds express actual required operations.
  • Wildcards follow producer-extends/consumer-super semantics.
  • Wildcard capture helpers isolate complex inference.
  • Erasure restrictions are considered for overloads, arrays, tests, and reflection.
  • @SafeVarargs is applied only after a real safety audit.

Annotations and reflection

  • Retention and target match the annotation consumer.
  • Public metadata uses @Documented where appropriate.
  • Repeatable annotations use valid container definitions and by-type lookup.
  • Reflection handles synthetic, bridge, generic, record, and sealed metadata.
  • Deep reflection uses narrowly opened packages.
  • Reflection caches do not retain unloadable class loaders.

Modules

  • Module descriptors declare minimal dependencies.
  • requires transitive is limited to dependencies exposed through public API.
  • API packages are exported; implementation packages remain encapsulated.
  • opens is qualified to known framework modules where possible.
  • Services separate provider implementations from consumers.
  • Automatic modules are treated as migration tools, not final architecture.
  • Compilation, launch, service discovery, and reflection are tested on the module path.
Final principle: advanced Java features are mechanisms for expressing architectural constraints. Packages define collaboration boundaries, generics preserve type relationships, records and sealed types model data and alternatives, annotations describe metadata, reflection interprets runtime structure, and JPMS turns dependency and encapsulation rules into enforceable configuration.
