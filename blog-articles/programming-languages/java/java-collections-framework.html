1. A unified framework for groups, sequences, sets, queues, and mappings

The Java Collections Framework is a set of interfaces, implementations, algorithms, wrappers, and traversal abstractions. Correct selection begins with semantic requirements—duplicates, encounter order, key equality, priority, range queries, concurrency, mutation, and access pattern—not with memorizing a favorite concrete class.

Interface contract

Defines operations, equality semantics, optional mutation, ordering, and element restrictions.

Implementation

Chooses array, linked node, hash table, tree, heap, or concurrent representation.

Algorithm

Operates polymorphically through interfaces: sorting, searching, reversing, rotating, copying, and aggregation.

View

Presents backed or reversed/subrange/key/value/entry access without necessarily copying storage.

The framework is a unified architecture for representing and manipulating collections independently of representation details. It includes more than a dozen interfaces, general-purpose and special-purpose implementations, and polymorphic algorithms.[1]

Program to the narrowest useful interface. A parameter that only iterates should accept Iterable or Collection; indexed algorithms need List; uniqueness needs Set; key lookup needs Map; double-ended scheduling needs Deque.

2. Core interface hierarchy

Iterable<E> └── Collection<E> ├── SequencedCollection<E> │ ├── List<E> │ └── Deque<E> ├── Set<E> │ └── SequencedSet<E> │ └── SortedSet<E> │ └── NavigableSet<E> └── Queue<E> └── Deque<E> Map<K,V> (not a Collection) ├── SequencedMap<K,V> ├── SortedMap<K,V> │ └── NavigableMap<K,V> └── ConcurrentMap<K,V>

Collection is the root of the element-container hierarchy. Map belongs to the framework but does not extend Collection because it models key–value mappings rather than a group of homogeneous elements.[2][3]

Interfaces describe behavior

  • List: ordered sequence with positional access and duplicates.
  • Set: no duplicate elements under its equality/order semantics.
  • Queue: elements held before processing, usually head-oriented.
  • Deque: insertion/removal at both ends.
  • Map: unique keys mapped to values.

4. Collection<E>

Root interface Collection represents a group of elements. Some implementations allow duplicates, some do not; some define encounter order, some do not. The JDK provides implementations of more specific subinterfaces rather than a direct general-purpose Collection implementation.[2]

static <T> boolean replaceAll(
        Collection<T> target,
        Collection<? extends T> values) {

    boolean changed =
        !target.equals(values);

    target.clear();
    target.addAll(values);

    return changed;
}

Optional operations

Mutating methods such as add, remove, and clear are optional. Unsupported implementations throw UnsupportedOperationException.

5. List<E>

Sequence A list is an ordered collection with positional access. It typically permits duplicates and can allow multiple null elements depending on implementation. Lists are sequenced collections and expose first, last, and reversed views in Java 21 and later.[4]

List<String> steps =
    new ArrayList<>();

steps.add("compile");
steps.add("test");
steps.add(1, "lint");

String first =
    steps.getFirst();

String last =
    steps.getLast();

List<String> reversed =
    steps.reversed();

Indexed versus iterator access

for (int index = 0;
        index < list.size();
        index++) {

    process(
        list.get(index));
}

Indexed traversal is efficient for random-access lists such as ArrayList but can become quadratic for sequential-access lists such as LinkedList. Enhanced for or iterators are representation-neutral.

6. Set<E>

Uniqueness A set contains no duplicate elements: it contains no two elements that are equal under the set's equality semantics. General-purpose sets define equality by membership, independent of encounter order.[5]

8. Deque<E>

Double ended A deque supports insertion, removal, and examination at both ends. It can represent FIFO queues and LIFO stacks. Deque implementations are generally preferable to legacy Stack for stack behavior.[7]

Deque<String> history =
    new ArrayDeque<>();

history.addLast("page-1");
history.addLast("page-2");

String current =
    history.removeLast();

String previous =
    history.peekLast();

Stack vocabulary

Deque<Frame> stack =
    new ArrayDeque<>();

stack.push(frame);

Frame top =
    stack.peek();

Frame removed =
    stack.pop();

Most deque implementations prohibit null because poll and peek use null to indicate emptiness.

9. Map<K,V>

Key–value mapping A map associates each unique key with at most one value. It exposes backed views of keys, values, and entries. The map's encounter order is the order of iteration through these views and is implementation-specific unless guaranteed.[3]

Mutable keys are dangerous

Changing a key in a way that affects equals, hashCode, or ordering while it is stored can make the mapping unreachable or violate tree invariants.

10. Sequenced collections, sets, and maps

Encounter order Java 21 introduced SequencedCollection, SequencedSet, and SequencedMap to model collections with a defined encounter order and uniform first, last, and reversed operations.[8]

SequencedCollection<String> sequence =
    new ArrayList<>();

sequence.addFirst("first");
sequence.addLast("last");

String first =
    sequence.getFirst();

SequencedCollection<String> reverseView =
    sequence.reversed();

Reversed views are backed

List<String> list =
    new ArrayList<>(
        List.of("a", "b", "c"));

List<String> reversed =
    list.reversed();

reversed.removeFirst();
// Removes "c" from list.

A reversed view changes encounter-order presentation and writes through when mutation is supported; it is not necessarily a copy.

11. Backed views, copies, and snapshots

Many collection-returning operations create views rather than independent storage. Changes to the backing collection are visible in the view, and permitted changes through the view write through to the backing collection.[2]

Sublist view

    new ArrayList<>(
        List.of("a", "b", "c", "d"));

List<String> middle =
    values.subList(1, 3);

middle.clear();

assert values.equals(
    List.of("a", "d"));

Map views

Set<CustomerId> keys =
    map.keySet();

Collection<Customer> values =
    map.values();

Set<Map.Entry<CustomerId, Customer>>
    entries =
        map.entrySet();

Snapshot copy

Do not confuse “unmodifiable” with “immutable snapshot.” An unmodifiable view can still reflect mutations to its backing collection; a copy can still contain mutable elements.

12. Equality, hashing, and membership

Collection operations are generally specified in terms of equals, while hash-based implementations also use hashCode to locate candidate buckets. Equal objects must have equal hash codes.[2][9]

public record CustomerId(
    String value) {

    public CustomerId {
        value =
            Objects.requireNonNull(value)
                .strip();

        if (value.isEmpty()) {
            throw new IllegalArgumentException();
        }
    }
}

List equality

Lists compare equal when they contain equal elements in the same order.

Set equality

Sets compare equal when they contain the same members, regardless of encounter order.

Map equality

Maps compare equal when they contain the same key–value mappings.

14. ArrayList

Resizable array ArrayList implements List, RandomAccess, and SequencedCollection. Positional access is constant time; append is amortized constant time; insertion/removal away from the end shifts later elements. It permits nulls and is not synchronized.[10]

Backed byObject[] elementDataDefault capacity10, allocated on first addGrowth×1.5Thread safetyNone

Under the hoodHow it is built

size = 4, capacity = 10 elementData: [ A | B | C | D | · | · | · | · | · | · ] 0 1 2 3 4 add(E) → write to elementData[size++] O(1) amortized get(i) → bounds check, read elementData[i] O(1) add(1, X) → System.arraycopy shifts B..D right one slot O(n − i) [ A | X | B | C | D | · | · | · | · | · ] remove(0) → shift everything left, null out last slot O(n) array full → allocate old + old/2 (10 → 15 → 22 → 33 …), copy, discard old

An ArrayList is a thin wrapper around a plain object array and a size counter. A no-argument constructor shares an empty sentinel array, so no storage is allocated until the first add, which allocates ten slots. When the array is full, grow allocates a new array 50% larger (oldCapacity + (oldCapacity >> 1)) and copies everything across; because the size grows geometrically, the total copying cost averages out to a constant per append.[27]

Insertions and removals anywhere but the end use System.arraycopy to slide the tail of the array, which is a fast memory move but still linear in the number of elements moved. Removed slots are set to null so the garbage collector can reclaim the element. The array never shrinks on its own; call trimToSize() after building a large, long-lived list. Every structural change increments modCount, which iterators compare against to detect concurrent modification (the fail-fast behavior in §36).

Because the references sit next to each other in memory, iteration walks memory linearly and is very friendly to CPU caches and prefetchers. That locality is why ArrayList beats LinkedList in practice even for many workloads that look like they favor a linked list on paper.

Use it when

  • You need a general-purpose list; this is the default.
  • You read by index or iterate far more than you insert in the middle.
  • You mostly append at the end, then sort, filter, or stream.
  • You know the approximate size up front (pre-size it).

Avoid it when

  • You repeatedly insert or remove at the front: use ArrayDeque.
  • You need uniqueness or fast contains: a Set is O(1) where ArrayList.contains is O(n).
  • Many threads mutate it: use a concurrent structure or external locking.
  • You store millions of primitives: boxing costs ~16 bytes per Integer; use an int[] or a primitive-collection library.

    new ArrayList<>(

Remove by index versus value

    new ArrayList<>(
        List.of(10, 20, 30));

// Removes element at index 1.

// Removes the value 30.

15. LinkedList

Doubly linked nodes LinkedList implements both List and Deque. Indexed operations traverse from the nearer end, while insertion/removal through a known iterator position or at either end is constant time. It permits nulls and is not synchronized.[11]

Backed byDoubly linked Node objectsFieldsfirst, last, sizePer element costone extra 24-byte nodeThread safetyNone

Under the hoodHow it is built

first last │ │ ▼ ▼ ┌────────────┐ ┌────────────┐ ┌────────────┐ │ prev: null │◄───│ prev │◄───│ prev │ │ item: A │ │ item: B │ │ item: C │ │ next │───►│ next │───►│ next: null │ └────────────┘ └────────────┘ └────────────┘ addFirst / addLast / removeFirst / removeLast → relink 2–4 pointers O(1) get(i) → walk from first if i < size/2, otherwise from last O(n) iterator.add / iterator.remove → relink around the cursor O(1)

Each element lives in its own Node object holding the item and pointers to the previous and next nodes; the list keeps references to the first and last node. Linking and unlinking at either end, or next to an iterator's cursor, only rewires a few pointers. Reaching position i by index, however, means following links one at a time; node(index) halves the worst case by starting from whichever end is closer.[27]

The hidden cost is memory and locality. On a typical 64-bit JVM with compressed references, every node is a separate 24-byte object (header plus three references), compared with 4 bytes per slot in an ArrayList. Nodes are scattered across the heap, so traversal chases pointers and misses cache. Even "O(1) insert in the middle" requires first finding the middle, which is O(n).

Use it when

  • You make a single pass with a ListIterator and insert or remove many elements at the cursor.
  • You genuinely need one object that is both a List and a Deque.
  • You need a deque that accepts null elements (rare, and usually a smell).

Avoid it when

  • You want a queue or stack: ArrayDeque is faster and smaller.
  • You access elements by index: every get(i) is a walk.
  • Memory or iteration speed matters: nodes cost several times more than array slots.
  • You think it is "better for inserts" without having measured; it usually is not.
LinkedList<Task> tasks =
    new LinkedList<>();

tasks.addFirst(
    urgent);

tasks.addLast(
    normal);

Task next =
    tasks.removeFirst();

Quadratic indexed traversal

// Poor for LinkedList:

        index < list.size();
        index++) {

    process(
        list.get(index));
}

Use an iterator

    process(task);
}

Linked nodes add object and pointer overhead and generally have poor cache locality. For queues and stacks, ArrayDeque is usually preferable; use LinkedList when its combined list/deque contract or iterator-position mutation is specifically useful.

16. ArrayDeque

Circular array ArrayDeque is a resizable-array implementation of Deque with no capacity limit. Most operations run in amortized constant time, it is not thread-safe, and it prohibits null elements. The JDK documents it as likely faster than Stack when used as a stack and faster than LinkedList when used as a queue.[28]

Backed byCircular Object[] elementsDefault capacity16 usable slotsGrowth≈×2 below 64, then ×1.5NullsRejectedThread safetyNone

Under the hoodHow it is built

capacity 8, head = 6, tail = 2 (tail = index of the next free slot) index: 0 1 2 3 4 5 6 7 elements: [ C | D | · | · | · | · | A | B ] ▲tail ▲head logical order: A, B, C, D (wraps around the end of the array) addFirst(x) → head = dec(head); elements[head] = x O(1) addLast(x) → elements[tail] = x; tail = inc(tail) O(1) pollFirst() → read elements[head], null it, head = inc(head) head == tail after an add → array is full: grow and unwrap into the new array

The deque is a single array treated as a ring. Two indexes mark where the logical sequence starts (head) and where the next element will be appended (tail); both wrap around modulo the array length, so adding or removing at either end never shifts other elements. When an add makes the ring full, grow enlarges it (roughly doubling while it is smaller than 64 slots, then by 50%) and copies the wrapped segments so they are contiguous again.[27]

Null is forbidden because an empty slot is null: pollFirst and peekFirst return null to mean "empty", and the implementation reads null slots to detect the boundaries. There is no index-based access; this is a deque, not a list.

Use it when

  • You need a stack (push/pop/peek); prefer it over legacy Stack.
  • You need a FIFO queue for breadth-first search, work lists, or buffering.
  • You need a sliding window or undo/redo history that adds and removes at both ends.
  • A single thread owns the structure.

Avoid it when

  • You need index access or removal from the middle: use ArrayList.
  • You need priority ordering: use PriorityQueue.
  • Several threads produce and consume: use a BlockingQueue or ConcurrentLinkedDeque.
  • You must store nulls.
// Stack (LIFO): are the brackets balanced?
static boolean balanced(String text) {
    Deque<Character> open = new ArrayDeque<>();

    for (char c : text.toCharArray()) {
        if (c == '(') {
            open.push(c);
        } else if (c == ')' && open.pollFirst() == null) {
            return false;   // ')' with nothing open
        }
    }
    return open.isEmpty();
}

// Queue (FIFO) for breadth-first search
Deque<Node> frontier = new ArrayDeque<>();
frontier.offer(start);

while (!frontier.isEmpty()) {
    Node node = frontier.poll();
    node.neighbours().forEach(frontier::offer);
}

Note that pop throws NoSuchElementException on an empty deque; use pollFirst when emptiness is an expected outcome rather than an error.

17. Vector

Legacy synchronized list Vector is a growable-array list whose methods are synchronized. It predates the Collections Framework and also exposes legacy capacity and Enumeration APIs.[12]

Backed byObject[] elementDataGrowth×2, or + capacityIncrementThread safetyEvery public method synchronized

Under the hoodHow it is built

Vector = ArrayList-style array + synchronized(this) on every method Stack extends Vector → push/pop/peek are also synchronized thread 1: synchronized get(0) ─┐ thread 2: synchronized get(1) ─┴─ serialized on the same monitor, even for reads

Internally Vector is nearly the same growable array as ArrayList, with two differences: every public method acquires the vector's own monitor, and growth doubles the capacity unless a positive capacityIncrement was supplied.[27] The legacy Stack class extends Vector, which is why it also exposes index-based methods that break the stack abstraction.

Use it when

  • You maintain legacy code or an API that requires Vector or Enumeration.

Avoid it when

  • Writing new code: use ArrayList, or ArrayDeque instead of Stack.
  • You need thread safety: per-method locking does not make check-then-act sequences atomic and serializes all readers.
Vector<String> vector =
    new Vector<>();

vector.add("legacy");

Enumeration<String> elements =
    vector.elements();

Method synchronization is not workflow atomicity

    String last =
        vector.remove(
            vector.size() - 1);
}

Another thread can change the vector between calls. Compound operations still require external synchronization.

Modern alternatives

  • ArrayList for thread-confined or externally synchronized use.
  • Collections.synchronizedList for one-lock wrapper semantics.
  • CopyOnWriteArrayList for small read-mostly shared lists.
  • Concurrent queues/deques for producer–consumer workflows.

18. HashSet

Hash set HashSet is backed by a HashMap, permits one null element, and makes no encounter-order guarantee. Basic operations are expected constant time when hash codes disperse elements well.[13]

Backed byHashMap<E, Object>Membershipkey present in the mapOrderUnspecifiedThread safetyNone

Under the hoodHow it is built

HashSet<E> ──wraps──► HashMap<E, Object> add(e) ≡ map.put(e, PRESENT) == null PRESENT is one shared dummy Object contains(e) ≡ map.containsKey(e) remove(e) ≡ map.remove(e) == PRESENT iterator() ≡ map.keySet().iterator()

A HashSet stores its elements as the keys of a private HashMap; every key maps to the same shared placeholder object. All of its performance characteristics, including hashing, buckets, tree bins, resizing, and the load factor, are therefore exactly those of HashMap. Read that section to understand why a poor hashCode slows the set down.

Use it when

  • You need fast contains/add/remove and order does not matter.
  • You are deduplicating, tracking "seen" items, or doing set algebra.
  • Elements have a good, stable hashCode/equals (records, strings, boxed numbers).

Avoid it when

  • Output order must be reproducible: use LinkedHashSet.
  • You need sorted order or range queries: use TreeSet.
  • Elements are enum constants: EnumSet is far smaller and faster.
  • Elements are mutated in ways that change hashCode while stored.
Set<CustomerId> seen =
    new HashSet<>();

        customer.id())) {

    throw new DuplicateCustomer(
        customer.id());
}

Iteration cost is proportional to the set's size plus backing-table capacity. Excessive initial capacity or a very low load factor can make traversal unnecessarily expensive.

19. LinkedHashSet

Insertion order LinkedHashSet combines hash-based membership with a well-defined encounter order, normally insertion order. Re-adding an existing element does not change its position.[14]

Backed byLinkedHashMap<E, Object>OrderInsertionOverheadtwo extra references per elementThread safetyNone

Under the hoodHow it is built

hash table (for O(1) contains) + doubly linked list (for order) head ⇄ [beta] ⇄ [alpha] ⇄ [gamma] ⇄ tail add("beta") again → already present, list unchanged

LinkedHashSet extends HashSet but calls a package-private constructor that makes the backing map a LinkedHashMap. Lookups use the hash table; iteration follows the linked list threaded through the entries, so it visits elements in the order they were first inserted and costs time proportional to the size, not the table capacity.[27]

Use it when

  • You need deduplication that keeps first-seen order.
  • Output must be deterministic (logs, reports, tests, JSON) without paying for sorting.
  • You need getFirst/getLast/reversed on a set.

Avoid it when

  • You need sorted order: use TreeSet.
  • Order truly does not matter and memory is tight: HashSet saves two references per element.

22. PriorityQueue

Binary heap PriorityQueue is an unbounded priority heap ordered by natural ordering or a comparator. Its head is a least element; ties are resolved arbitrarily. It prohibits nulls.[16]

A binary heap is a complete binary tree stored level by level in an array, so no node objects or pointers are needed: the children of slot i are at 2i + 1 and 2i + 2. The only ordering guarantee is that each parent is no greater than its children, which puts the minimum at index 0 but leaves the rest only partially ordered. Ties are broken arbitrarily, so the queue is not stable: two jobs with equal priority are not guaranteed to come out in submission order. Use it when

  • You repeatedly need the smallest (or, with a reversed comparator, largest) element.

  • Top-k: keep a size-k min-heap and evict the head when a larger item arrives (O(n log k)).

Avoid it when

  • You need to iterate in sorted order: sort a list or use a TreeSet.
  • You frequently update or remove arbitrary elements: use a TreeSet with a unique tie-breaker.
  • You need FIFO among equal priorities without adding a tie-breaker.
  • Several threads share it: use PriorityBlockingQueue.

23. HashMap

Hash table HashMap permits one null key and null values, makes no encounter-order guarantee, and provides expected constant-time get and put under a well-distributed hash function. It is not synchronized.[17]

Under the hoodHow it is built

hash(key) = h ^ (h >>> 16) where h = key.hashCode(); null key → 0 index = hash & (table.length − 1) table length is always a power of two table (length 16) threshold = 16 × 0.75 = 12 mappings [0] ─► null [1] ─► (k1,v1) ─► (k9,v9) collision: singly linked chain of Nodes [2] ─► null [3] ─► TreeNode bin chain reached 8 and table ≥ 64 → red-black tree ⋮ [15] ─► (k4,v4) size > threshold → resize to 32; each chain splits in place into "lo" (stays at i) and "hi" (moves to i + 16) — no rehashing

A HashMap is an array of buckets. To find a key it calls hashCode(), mixes the high 16 bits into the low 16 bits (h ^ (h >>> 16)) so that keys differing only in their upper bits still spread out, and masks the result with length − 1 to pick a bucket. Each bucket holds a singly linked chain of Node objects (hash, key, value, next); a lookup walks the chain comparing cached hashes first and calling equals only on a hash match.[27]

When the number of mappings exceeds capacity × loadFactor the table doubles. Because capacities are powers of two, each node either stays at the same index or moves exactly oldCapacity slots up, decided by one bit of its stored hash, so resizing never calls hashCode again. If a single chain grows to 8 nodes (TREEIFY_THRESHOLD) while the table has at least 64 buckets, that bucket is converted to a red-black tree of TreeNodes, ordered by hash and then by compareTo when keys are Comparable. This caps worst-case lookups in a heavily colliding bucket at O(log n) instead of O(n); a tree shrinks back to a list at 6 nodes. Smaller tables simply resize instead of treeifying.

The practical consequences: a constant or badly distributed hashCode collapses the map into a few long buckets; a key whose hash changes after insertion is filed under the wrong bucket and becomes unreachable; and iteration visits every bucket, so it costs size plus capacity.

  • Keys are immutable with good hashCode implementations (records, strings, IDs).

Avoid it when

  • You need predictable iteration order: LinkedHashMap.
  • You need sorted keys or nearest-key queries: TreeMap.
  • Keys are enum constants: EnumMap.
  • Several threads write: ConcurrentHashMap, not a HashMap behind ad hoc locks.

25. TreeMap

Navigable map TreeMap is a red-black-tree-based NavigableMap ordered by natural key order or a comparator. It guarantees logarithmic containsKey, get, put, and remove operations.[19]

Backed byRed-black tree of Entry nodesOrderSorted by keyCostO(log n) guaranteedThread safetyNone

Under the hoodHow it is built

(30)B / \ (20)R (40)B / \ \ (10)B (25)B (50)R Entry: key, value, left, right, parent, color get(k) → start at root; go left if k < node, right if k > node O(log n) put(k, v) → descend, attach a red leaf, then recolor / rotate upward ceiling(k) → descend, remembering the last node ≥ k subMap(a,b) → a view that bounds-checks against a and b, no copy

A red-black tree is a binary search tree in which every node is colored red or black, with two rules: a red node never has a red child, and every path from the root to a leaf passes through the same number of black nodes. Together these keep the tree within about twice the minimum possible height (at most 2·log₂(n + 1)), so every lookup, insert, and delete touches O(log n) nodes. After an insert or delete, fixAfterInsertion/fixAfterDeletion restore the rules with recoloring and at most a few rotations.[27]

Keys are located only by compareTo or the supplied comparator; equals and hashCode are never consulted. Each entry is an object with six fields, so a tree map typically uses more memory per mapping than a hash map, and each step costs a comparison, which can be expensive for long strings or composite comparators.

  • You need keys in sorted order (reports, leaderboards, time series).

  • You need range views: events between two instants, prices within a band.
  • You need a guaranteed O(log n) worst case rather than expected O(1).

Avoid it when

  • You only do exact-key lookups: HashMap is faster.
  • Keys lack a total ordering consistent with equals.
  • Several threads share it: use ConcurrentSkipListMap.

27. Special-purpose maps: IdentityHashMap and WeakHashMap

Two maps intentionally break the usual Map rules and are worth knowing so you can recognize when you need them.

IdentityHashMap

Open addressing Compares keys with == and hashes them with System.identityHashCode instead of equals/hashCode. Internally it is a single array holding keys and values in alternating slots, using linear probing on collision, so there are no entry objects.[31] Use it for graph traversal "visited" sets, object-copying and serialization bookkeeping, or proxies where two equal-but-distinct objects must be tracked separately. Do not use it as a general map; it deliberately violates the Map contract.

Set<Object> visited =
    Collections.newSetFromMap(
        new IdentityHashMap<>());

WeakHashMap

Weak keys A hash table whose entries hold their keys through WeakReferences. Once a key is no longer strongly reachable elsewhere, the garbage collector may clear it, and the map drops the entry the next time it is touched by draining a ReferenceQueue.[32] Use it to attach metadata to objects whose lifetime you do not control. Beware: a value that refers back to its own key keeps the key alive forever, keys that are interned strings or boxed small integers never become unreachable, and it is not a size- or time-bounded cache.

28. ConcurrentHashMap

Concurrent map ConcurrentHashMap supports fully concurrent retrievals and high expected concurrency for updates. Retrievals generally do not block, and neither keys nor values may be null.[20]

Backed byvolatile Node<K,V>[] tableWritesCAS on empty bins, lock on bin head otherwiseReadsLock-freeNullsRejected

Under the hoodHow it is built

Since Java 8, ConcurrentHashMap uses the same bucket-array layout as HashMap but coordinates threads per bucket. Inserting into an empty bucket is a single compare-and-set with no lock. Inserting into an occupied bucket synchronizes on that bucket's first node, so threads writing to different buckets never contend. Reads use volatile semantics and never lock.[27]

Resizing is cooperative: the table is transferred in chunks, moved buckets are replaced by ForwardingNode markers that redirect lookups to the new table, and any thread that tries to write during a resize helps move buckets instead of waiting. The element count is spread across striped counter cells to avoid a single hot counter, which is why size() is only an estimate under concurrent updates. Nulls are banned because get returning null must unambiguously mean "absent"; a caller cannot follow up with containsKey atomically.

Avoid it when

  • You need an atomic update across several keys or several maps: use a lock.
  • Only one thread uses it: HashMap is simpler.
  • You need sorted keys: ConcurrentSkipListMap.
  • You need nulls as keys or values.

  • Single-threaded use: TreeMap uses less memory.

41. Comparable<T> and natural ordering

Natural order Comparable imposes a total ordering on instances of a class through compareTo. Naturally ordered objects can be sorted and used as keys/elements in sorted maps and sets without an explicit comparator.[25]

public record Version(
        int major,
        int minor,
        int patch)
        implements Comparable<Version> {

    @Override
    public int compareTo(
            Version other) {

        int result =
            Integer.compare(
                major,
                other.major);

        if (result != 0) {
            return result;
        }

        result =
            Integer.compare(
                minor,
                other.minor);

        if (result != 0) {
            return result;
        }

        return Integer.compare(
            patch,
            other.patch);
    }
}

Orders and indexes

private static final
Comparator<Job> DISPATCH_ORDER =
    Comparator.comparingInt(
            Job::priority)
        .reversed()
        .thenComparing(
            Job::deadline)
        .thenComparing(
            Job::submittedAt)
        .thenComparing(
            Job::id);

private final Map<JobId, Job> byId =
    new HashMap<>();

private final PriorityQueue<Job> ready =
    new PriorityQueue<>(
        DISPATCH_ORDER);

private final NavigableMap<Instant,
    LinkedHashSet<JobId>> byDeadline =
        new TreeMap<>();

private final Map<String,
    LinkedHashSet<JobId>> byTag =
        new HashMap<>();

Add a job atomically under one lock

public synchronized void add(
        Job job) {

    if (byId.putIfAbsent(
            job.id(),
            job) != null) {

        throw new IllegalArgumentException(
            "Duplicate job: "
                + job.id());
    }

    boolean committed = false;

    try {
        if (job.state()
                == JobState.READY) {
            ready.add(job);
        }

        byDeadline
            .computeIfAbsent(
                job.deadline(),
                ignored ->
                    new LinkedHashSet<>())
            .add(job.id());

        for (String tag : job.tags()) {
            byTag.computeIfAbsent(
                    tag,
                    ignored ->
                        new LinkedHashSet<>())
                .add(job.id());
        }

        committed = true;
    } finally {
        if (!committed) {
            removeFromIndexes(job);
            byId.remove(job.id());
        }
    }
}

Dispatch next job

public synchronized Optional<Job>
pollReady() {

    while (!ready.isEmpty()) {
        Job queued =
            ready.remove();

        Job current =
            byId.get(
                queued.id());

        if (current == null
                || current.state()
                    != JobState.READY) {
            continue;
        }

        Job running =
            current.withState(
                JobState.RUNNING);

        byId.put(
            running.id(),
            running);

        return Optional.of(
            running);
    }

    return Optional.empty();
}

Deadline range query

public synchronized List<Job>
dueBetween(
        Instant startInclusive,
        Instant endExclusive) {

    return byDeadline
        .subMap(
            startInclusive,
            true,
            endExclusive,
            false)
        .values()
        .stream()
        .flatMap(Set::stream)
        .map(byId::get)
        .filter(
            Objects::nonNull)
        .sorted(DISPATCH_ORDER)
        .toList();
}

Design choices

  • HashMap provides primary-key lookup.
  • PriorityQueue provides efficient next-job selection but not arbitrary sorted iteration.
  • TreeMap provides deadline range queries.
  • LinkedHashSet deduplicates IDs while preserving deterministic insertion order.
  • Immutable job records avoid mutable-key/index corruption.
  • One lock protects the multi-collection invariant; replacing individual fields with concurrent collections would not make the compound transaction atomic.

53. Production checklist

Interface and semantics

  • The declared type is the narrowest interface needed.
  • Duplicate, order, null, and mutation policies are explicit.
  • Map key and set element equality are stable while stored.
  • Sequenced and reversed operations are understood as views where applicable.
  • Range-query requirements use navigable collections rather than ad hoc filtering.

Implementation

  • ArrayList is the default list unless a measured requirement suggests otherwise.
  • ArrayDeque is preferred for ordinary stacks and deques.
  • Enum keys and elements use EnumMap and EnumSet.
  • The chosen structure's internal cost model (array shift, hash, tree descent, heap sift, copy-on-write) matches the dominant operation.
  • Hash, linked-hash, tree, and priority structures match ordering requirements.
  • Capacity is estimated without gross over-allocation.
  • Legacy Vector is retained only for compatibility or a deliberate synchronization contract.

Ordering and comparison

  • Comparable defines one sensible natural order.
  • Alternative orders use reusable comparators.
  • Comparators are antisymmetric, transitive, and complete.
  • Comparator ties are intentional and compatible with set/map uniqueness.
  • Null ordering is explicit.

Iteration and views

  • Iterator mutation uses iterator methods or bulk operations.
  • Fail-fast behavior is not relied upon for correctness.
  • Concurrent traversal uses the implementation's consistency model.
  • Backed views and independent copies are not confused.
  • Resource and lifecycle ownership of views is clear.

Concurrency

  • Unsynchronized collections are thread-confined or externally protected.
  • Synchronized wrappers are traversed under their monitor.
  • Concurrent collections are used for scalable shared access.
  • Multi-collection and multi-key invariants still use explicit coordination.
  • Mapping functions are short, side-effect-aware, and non-recursive.

Algorithms and performance

  • Sorting and binary searching use the same ordering.
  • Destructive algorithms are applied only to modifiable lists.
  • Iteration order assumptions are documented and tested.
  • Big-O, memory layout, cache locality, and workload shape are all considered.
  • Performance claims use JMH or representative end-to-end tests.
Final principle: the Collections Framework separates semantic contracts from data-structure choices. Reliable Java code selects an interface by meaning, an implementation by workload, an ordering by domain law, and a concurrency model by ownership—not by habit.

Exercise 4: Keep the five largest readings

A stream supplies millions of integer readings. Retain only the five largest values without sorting or storing the full input. Duplicate readings count separately.

Show solution
static List<Integer> fiveLargest(
        Iterable<Integer> readings) {

    PriorityQueue<Integer> top =
        new PriorityQueue<>(5);

    for (int reading : readings) {
        if (top.size() < 5) {
            top.offer(reading);
        } else if (reading > top.peek()) {
            top.poll();
            top.offer(reading);
        }
    }

    List<Integer> result =
        new ArrayList<>(top);

    result.sort(Comparator.reverseOrder());
    return List.copyOf(result);
}

The min-heap root is the smallest retained value, so each new reading can be compared with the cutoff in constant time. Each replacement costs O(log 5), and storage remains bounded.

    }
}

ConcurrentHashMap coordinates key insertion, while LongAdder spreads heavily contended increments across internal cells. A read during active updates is a useful current total, not an atomic snapshot of every concurrent increment.

Extension challenge: add tests for empty inputs, duplicate values, comparator ties, invalid ranges, capacity boundaries, and concurrent updates. Then justify every concrete implementation in terms of required semantics and dominant operations.
