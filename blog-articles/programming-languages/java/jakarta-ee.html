1. Jakarta EE as a standardized platform

Jakarta EE is a family of specifications defining interoperable APIs, component lifecycles, container services, packaging rules, and compatibility requirements for server-side Java applications.

Jakarta EE 11 is the current final platform release. It requires Java SE 17 or later and includes standards for HTTP handling, dependency injection, persistence, validation, REST, messaging, transactions, security, concurrency, JSON, and other enterprise concerns.[1][2]

Specifications

Normative contracts define public APIs and required behavior. Applications use jakarta.* types instead of server internals.

Containers

Runtime containers create components, inject dependencies, associate scopes, manage transactions, and supply resources.

TCKs

Technology Compatibility Kits test whether implementations conform to a specification or profile.

Portable applications

WAR, JAR, and EAR archives can be deployed to compatible products, subject to documented external resources and extensions.

Compatibility listings identify products and exact releases certified for Jakarta EE 11 profiles. Certification is version- and profile-specific; a server name alone does not establish support for every Jakarta EE API.[3]

Jakarta EE is not one framework. It is a standardized platform implemented by multiple products. Implementations may differ internally while preserving application-facing contracts.

2. From J2EE to Jakarta EE

1999: J2EE 1.2 consolidated enterprise APIs including Servlets, JSP, JDBC, and EJB into a certifiable application-server platform.

2006: Java EE 5 simplified enterprise programming through annotations, dependency injection, POJO-style components, and the redesigned persistence model.

2017–2018: Oracle contributed Java EE technologies to the Eclipse Foundation, and the community selected the Jakarta EE name.

2019: Jakarta EE 8 reproduced the Java EE 8 baseline under the Eclipse specification process.

2020: Jakarta EE 9 moved enterprise APIs from javax.* to jakarta.*.

2022: Jakarta EE 10 delivered major post-migration feature updates and introduced the Core Profile.

2025: Jakarta EE 11 added Jakarta Data, modernized several specifications, and removed obsolete platform elements.

The initial enterprise platform grew from the application-server ecosystem and standard APIs such as Servlets, JSP, JDBC, and EJB. J2EE 1.2 arrived in late 1999, while subsequent Java EE generations progressively reduced deployment-descriptor and component boilerplate.[4]

Jakarta EE initially used Java EE 8 as its baseline. The Eclipse Foundation's open, vendor-neutral process now governs the platform, specifications, implementations, and compatibility tests.[5]

The namespace boundary

Jakarta EE 9 replaced the enterprise javax.* packages with jakarta.*. Package names are part of Java type identity, so Jakarta EE 9 is not source- or binary-compatible with the corresponding Java EE 8 APIs. Java SE APIs such as javax.sql and javax.naming did not move.[6][7]

// Java EE 8
import javax.servlet.http.HttpServlet;
import javax.persistence.Entity;
import javax.ws.rs.Path;

// Jakarta EE 9+
import jakarta.servlet.http.HttpServlet;
import jakarta.persistence.Entity;
import jakarta.ws.rs.Path;

// Java SE remains javax.sql
import javax.sql.DataSource;
Migration is broader than imports. Dependencies, descriptors, provider files, generated code, reflective strings, serialized types, test tooling, and server configuration must all target the same namespace generation.

3. Platform, Web Profile, and Core Profile

Jakarta EE profiles define coherent subsets for different runtime sizes and application styles.[8][9]

ProfilePurposeTechnologies relevant here
Core Profile 11Smaller runtimes and foundational servicesJakarta REST 4.0, CDI Lite 4.1, JSON-P, JSON-B, Interceptors
Web Profile 11Web applications and web enterprise servicesServlet 6.1, Pages 4.0, Persistence 3.2, CDI 4.1, Validation 3.1, REST, Transactions
Platform 11Complete enterprise platformEverything above plus Messaging 3.1, Connectors, Batch, Mail, full Enterprise Beans, and more

Jakarta Messaging is part of the full Platform, not the Web or Core Profile. Jakarta Pages is part of the Web Profile. An application requiring container-managed JMS and JSP therefore needs a full Platform product or an extended runtime that explicitly supplies both.

API dependency

<dependency>
  <groupId>jakarta.platform</groupId>
  <artifactId>jakarta.jakartaee-api</artifactId>
  <version>11.0.0</version>
  <scope>provided</scope>
</dependency>

The API is normally provided because the runtime supplies implementations. Bundling the platform API classes in a WAR can create classloading conflicts and does not transform a Servlet-only container into a Jakarta EE Platform server.

4. Container programming model

Jakarta EE containers provide component lifecycle, dependency and resource injection, naming, connection pooling, persistence-context association, security, transactions, and managed concurrency. Components are ordinarily Java classes plus annotations or deployment metadata.[10]

@ApplicationScoped
public class OrderService {
    @Inject
    OrderRepository orders;

    @PersistenceContext(unitName = "orders")
    EntityManager entityManager;

    @Inject
    JMSContext messaging;

    @Resource(lookup =
        "java:comp/DefaultManagedExecutorService")
    ManagedExecutorService executor;
}

CDI resolves beans by type and qualifiers. @PersistenceContext requests a container-managed persistence context. @Resource injects resources from the component environment. These are distinct services coordinated by the container.[11][12]

Managed concurrency

Application components should use Jakarta Concurrency or specification-managed asynchronous facilities instead of creating unmanaged executors. Managed tasks preserve container lifecycle and context rules and can be stopped when the application is undeployed.

Lifecycle is part of correctness. Request objects, responses, persistence contexts, transactions, sessions, and scoped CDI references must not be retained or used beyond their defined lifecycle.

6. Jakarta Servlet

Jakarta Servlet 6.1 defines server-side HTTP request and response handling, filters, sessions, listeners, multipart processing, asynchronous processing, dispatch, and web-application lifecycle for Jakarta EE 11.[14][15]

Servlet controller

@WebServlet("/orders")
public final class OrdersServlet extends HttpServlet {
    @Inject
    OrderQueryService queries;

    @Override
    protected void doGet(
            HttpServletRequest request,
            HttpServletResponse response)
            throws ServletException, IOException {

        String customerId =
                request.getParameter("customerId");

        request.setAttribute(
                "orders",
                queries.findForCustomer(customerId));

        request.getRequestDispatcher(
                "/WEB-INF/views/orders.jsp")
                .forward(request, response);
    }
}

A container can invoke one Servlet instance concurrently. Request state belongs in local variables and request attributes; mutable instance fields must be thread-safe.

Filter

@WebFilter(urlPatterns = "/*", asyncSupported = true)
public final class CorrelationFilter implements Filter {
    public static final String HEADER =
            "X-Correlation-ID";

    @Override
    public void doFilter(
            ServletRequest request,
            ServletResponse response,
            FilterChain chain)
            throws IOException, ServletException {

        HttpServletRequest incoming =
                (HttpServletRequest) request;
        HttpServletResponse outgoing =
                (HttpServletResponse) response;

        String id = normalize(
                incoming.getHeader(HEADER));

        incoming.setAttribute(
                CorrelationFilter.class.getName(),
                id);
        outgoing.setHeader(HEADER, id);

        chain.doFilter(request, response);
    }

    private static String normalize(String value) {
        if (value == null
                || value.length() > 128
                || !value.matches("[A-Za-z0-9._-]+")) {
            return UUID.randomUUID().toString();
        }
        return value;
    }
}

Asynchronous processing

AsyncContext lets a request release the initial container thread while managed work continues. Every Servlet and filter in the path must support asynchronous processing, and the application must complete or dispatch the context after success, error, or timeout.[16]

@WebServlet(
    value = "/reports/export",
    asyncSupported = true)
public final class ExportServlet extends HttpServlet {
    @Resource(lookup =
        "java:comp/DefaultManagedExecutorService")
    ManagedExecutorService executor;

    @Inject
    ExportService exports;

    @Override
    protected void doPost(
            HttpServletRequest request,
            HttpServletResponse response) {

        AsyncContext async = request.startAsync();
        async.setTimeout(30_000);

        executor.submit(() -> {
            try {
                byte[] csv = exports.create(
                        request.getParameter("customerId"));
                HttpServletResponse target =
                        (HttpServletResponse) async.getResponse();
                target.setContentType("text/csv");
                target.getOutputStream().write(csv);
            } catch (Exception failure) {
                // Record and map failure according to policy.
            } finally {
                async.complete();
            }
        });
    }
}
Async Servlet is not a durable job queue. Work that must survive restart or run for minutes belongs in Jakarta Messaging, Batch, or another durable workflow.

7. Jakarta Pages (JSP)

Jakarta Pages 4.0 is the Jakarta EE 11 specification for the technology historically known as JavaServer Pages or JSP. A page combines textual content with Expression Language, standard actions, and custom tags and is translated into a Jakarta Servlet by the container. Version 4.0 removes several long-deprecated features, including the obsolete jsp:plugin action and the isThreadSafe page directive.[17]

Presentation-only page

<%@ page contentType="text/html;charset=UTF-8"
         pageEncoding="UTF-8"
         session="false" %>
<%@ taglib prefix="c"
           uri="jakarta.tags.core" %>
<%@ taglib prefix="fmt"
           uri="jakarta.tags.fmt" %>

Jakarta Tags 3.0 uses URIs such as jakarta.tags.core, jakarta.tags.fmt, and jakarta.tags.functions. The core library supplies iteration, conditionals, output, URL handling, and scoped-variable operations.[18][19]

Jakarta Expression Language resolves scoped variables, bean properties, collection elements, operators, and method expressions. CDI can expose contextual beans to EL, but substantial business logic should be executed before rendering and represented through a dedicated view model.[20]

Avoid scriptlets

<%-- Avoid Java database and control-flow code in JSP --%>
<%
    List<OrderEntity> orders =
        entityManager.createQuery(
            "select o from Order o",
            OrderEntity.class)
        .getResultList();

    for (OrderEntity order : orders) {
        out.println(order.getId());
    }
%>

Scriptlets mix persistence, control flow, escaping, and presentation in one translated Servlet. Servlet controllers, CDI services, JPA repositories, EL, and tags provide clearer boundaries and are easier to test.

Keep JSP files under WEB-INF. External requests cannot invoke them directly, so the Servlet controller can consistently prepare data and enforce workflow before forwarding.

8. Jakarta Persistence (JPA)

Jakarta Persistence 3.2 standardizes object-relational mapping, entity lifecycle, persistence contexts, JPQL, Criteria queries, metadata, and provider integration. The specification descends from the EJB 3.0 persistence model and the Java Persistence 2.x line. Version 3.2 adds support for record embeddables and record composite keys, more Java time mappings, and query-language enhancements.[21]

Entity rules

An entity must be a top-level or static nested non-final class with a public or protected no-argument constructor. A record cannot be an entity. Every entity must have a primary key. Persistence 3.2 can use records as embeddables and composite key classes under the specified rules.

@Entity(name = "Order")
@Table(
    name = "customer_order",
    indexes = @Index(
        name = "order_customer_created_idx",
        columnList = "customer_id, created_at"))
public class OrderEntity {
    @Id
    @GeneratedValue(strategy = GenerationType.UUID)
    private UUID id;

    @Version
    private long version;

    @NotBlank
    @Column(name = "customer_id", nullable = false)
    private String customerId;

    @NotNull
    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 32)
    private OrderStatus status;

    @NotNull
    @Column(
        name = "total_amount",
        nullable = false,
        precision = 19,
        scale = 4)
    private BigDecimal totalAmount;

    @NotBlank
    @Size(min = 3, max = 3)
    @Column(nullable = false, length = 3)
    private String currency;

    @NotNull
    @Column(name = "created_at", nullable = false)
    private Instant createdAt;

    @Valid
    @ElementCollection
    @CollectionTable(
        name = "order_item",
        joinColumns =
            @JoinColumn(name = "order_id"))
    private List<OrderItemEmbeddable> items =
            new ArrayList<>();

    protected OrderEntity() {
        // Required by Jakarta Persistence.
    }

    public OrderEntity(
            String customerId,
            BigDecimal totalAmount,
            String currency,
            Instant createdAt) {
        this.customerId =
                Objects.requireNonNull(customerId);
        this.totalAmount =
                Objects.requireNonNull(totalAmount);
        this.currency =
                Objects.requireNonNull(currency);
        this.createdAt =
                Objects.requireNonNull(createdAt);
        this.status = OrderStatus.PENDING;
    }

    public void addItem(
            OrderItemEmbeddable item) {
        items.add(Objects.requireNonNull(item));
    }

    public void confirm() {
        if (status != OrderStatus.PENDING) {
            throw new IllegalStateException(
                "Only pending orders may be confirmed");
        }
        status = OrderStatus.CONFIRMED;
    }

    public UUID getId() { return id; }
    public long getVersion() { return version; }
    public String getCustomerId() { return customerId; }
    public OrderStatus getStatus() { return status; }
    public BigDecimal getTotalAmount() { return totalAmount; }
    public String getCurrency() { return currency; }
    public Instant getCreatedAt() { return createdAt; }
    public List<OrderItemEmbeddable> getItems() {
        return List.copyOf(items);
    }
}
@Embeddable
public record OrderItemEmbeddable(
        @NotBlank String sku,
        @Positive int quantity,
        @NotNull @Positive
        BigDecimal unitPrice) {
}

GenerationType.UUID requests an RFC 4122 UUID generator for supported key types. @Version defines the optimistic lock field used to detect conflicting updates rather than silently accepting a lost update.[22][23]

Persistence unit

<persistence
    xmlns="https://jakarta.ee/xml/ns/persistence"
    xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
    xsi:schemaLocation="
      https://jakarta.ee/xml/ns/persistence
      https://jakarta.ee/xml/ns/persistence/persistence_3_2.xsd"
    version="3.2">

  <persistence-unit
      name="orders"
      transaction-type="JTA">

    <jta-data-source>
      java:app/jdbc/Orders
    </jta-data-source>

    <class>
      com.example.orders.persistence.OrderEntity
    </class>

    <properties>
      <property
        name="jakarta.persistence.schema-generation.database.action"
        value="none" />
    </properties>
  </persistence-unit>
</persistence>

Production schemas are usually managed through reviewed migrations rather than destructive automatic creation. The persistence unit still defines the JTA data source, mappings, and provider behavior.

Repository

@ApplicationScoped
public class OrderRepository {
    @PersistenceContext(unitName = "orders")
    EntityManager entityManager;

    public void add(OrderEntity order) {
        entityManager.persist(order);
    }

    public Optional<OrderEntity> find(UUID id) {
        return Optional.ofNullable(
            entityManager.find(OrderEntity.class, id));
    }

    public OrderEntity require(UUID id) {
        OrderEntity result =
            entityManager.find(OrderEntity.class, id);

        if (result == null) {
            throw new OrderNotFound(id);
        }
        return result;
    }

    public List<OrderEntity> findByCustomer(
            String customerId,
            int limit) {
        return entityManager.createQuery("""
            select distinct o
            from Order o
            left join fetch o.items
            where o.customerId = :customerId
            order by o.createdAt desc
            """, OrderEntity.class)
            .setParameter("customerId", customerId)
            .setMaxResults(limit)
            .getResultList();
    }
}

A container-managed transaction-scoped EntityManager is typically an injected proxy resolving the persistence context associated with the active transaction. Do not share entities or raw provider sessions across threads.[24]

Query design

  • Use fetch joins, entity graphs, batch fetching, or DTO projections to avoid N+1 access.
  • Use pagination and stable ordering for large result sets.
  • Index columns used by predicates, joins, and ordering.
  • Keep remote calls outside database transactions whenever possible.
  • Do not expose mutable entities as REST response DTOs.

9. Contexts and Dependency Injection

CDI 4.1 provides typesafe injection, lifecycle scopes, producers, qualifiers, alternatives, interceptors, decorators, events, and extension mechanisms. CDI Lite defines a smaller subset; CDI Full adds facilities including decorators, a conversation scope, and portable extensions. Jakarta EE integrates CDI with component classes, EL, persistence, transactions, and resources.[11][25]

ScopeLifecycleTypical use
@DependentFollows injection targetStateless helpers and produced values
@RequestScopedOne requestRequest models and request-local state
@SessionScopedOne HTTP session; passivatingSmall user-session state when necessary
@ApplicationScopedApplication lifetimeThread-safe services and registries
@ConversationScopedExplicit multi-request conversationCDI Full web workflows

Normal scopes use client proxies, allowing a longer-lived bean to inject a contextual reference whose actual instance varies by request, session, or conversation. Bean classes and methods must remain proxyable according to CDI rules.

Constructor injection and qualifiers

@Retention(RetentionPolicy.RUNTIME)
@Target({
    ElementType.TYPE,

        CARD,

        implements PaymentGateway {

}

public class PaymentService {
    private final PaymentGateway gateway;

            @PaymentChannel(

Qualifiers participate in typesafe resolution and avoid string-based service locators. Alternatives support deployment substitutions, while producers adapt resources or construct values not represented by ordinary bean classes.

        return Clock.systemUTC();
    }
}

Interceptor binding

@InterceptorBinding
@Retention(RetentionPolicy.RUNTIME)
@Target({ElementType.TYPE, ElementType.METHOD})
public @interface Audited {
}

@Audited
@Interceptor
@Priority(Interceptor.Priority.APPLICATION)
public class AuditInterceptor {
    @AroundInvoke
    public Object invoke(
            InvocationContext context)
            throws Exception {
        long started = System.nanoTime();

        try {
            return context.proceed();
        } finally {
            long elapsed =
                System.nanoTime() - started;

            System.getLogger(
                context.getTarget()
                    .getClass()
                    .getName())
                .log(
                    System.Logger.Level.INFO,
                    "{0} completed in {1} ns",
                    context.getMethod().getName(),
                    elapsed);
        }
    }
}

Jakarta Interceptors standardizes bindings and invocation contexts. Interceptors are useful for consistent cross-cutting behavior, but they should not conceal major business semantics such as retries or remote calls.[26]

10. Jakarta Validation

Jakarta Validation 3.1 defines declarative constraints and metadata for JavaBeans, records, container elements, constructor parameters, method parameters, and return values. It clarifies record support and is included in Jakarta EE 11.[27]

Request records

@ConsistentOrder
public record CreateOrderRequest(
        @NotBlank
        @Size(max = 64)
        String customerId,

        @NotEmpty
        @Size(max = 100)
        List<@Valid CreateOrderItemRequest> items,

public record CreateOrderItemRequest(
        @NotBlank

        String sku,

        @Positive

        int quantity) {
}

Container-element constraints validate generic contents, and @Valid cascades recursively into contained objects.[28]

Custom cross-field constraint

@Documented
@Constraint(validatedBy =
    ConsistentOrderValidator.class)
@Target({
    ElementType.TYPE,
    ElementType.ANNOTATION_TYPE
})
@Retention(RetentionPolicy.RUNTIME)
public @interface ConsistentOrder {
    String message()
        default "Order values are inconsistent";

    Class<?>[] groups() default {};

    Class<? extends Payload>[] payload()
        default {};
}
public final class ConsistentOrderValidator
        implements ConstraintValidator<
            ConsistentOrder,
            CreateOrderRequest> {

    @Override
    public boolean isValid(
            CreateOrderRequest request,
            ConstraintValidatorContext context) {

        if (request == null) {
            return true;
        }

        long distinct =
            request.items().stream()
                .map(CreateOrderItemRequest::sku)
                .map(String::toUpperCase)
                .distinct()
                .count();

        if (distinct == request.items().size()) {
            return true;
        }

        context.disableDefaultConstraintViolation();
        context.buildConstraintViolationWithTemplate(
                "Duplicate SKU entries are not allowed")
            .addPropertyNode("items")
            .addConstraintViolation();

        return false;
    }
}

The standalone Validator API validates objects and exposes constraint metadata. The executable-validation API validates method and constructor parameters and results. Implementations of Validator and ExecutableValidator must be thread-safe.[29][30]

11. Jakarta RESTful Web Services (JAX-RS)

Jakarta REST 4.0 defines Java APIs for RESTful services and clients. The technology was historically called JAX-RS and is included in Jakarta EE 11 Core, Web, and full Platform profiles.[31][32]

@ApplicationPath("/api")
public class OrdersRestApplication
        extends Application {
}

Resource class

@Path("/orders")
@Consumes(MediaType.APPLICATION_JSON)
@Produces(MediaType.APPLICATION_JSON)
public class OrderResource {
    @Inject
    OrderApplicationService orders;

    @POST
    public Response create(
            @Valid CreateOrderRequest request,
            @HeaderParam("Idempotency-Key")
            String idempotencyKey,
            @Context UriInfo uriInfo) {

        if (idempotencyKey == null
                || idempotencyKey.isBlank()) {
            throw new BadRequestException(
                "Idempotency-Key is required");
        }

        CreatedOrder created =
            orders.create(
                idempotencyKey,
                request);

        URI location =
            uriInfo.getAbsolutePathBuilder()
                .path(created.id().toString())
                .build();

        return Response.created(location)
            .tag(new EntityTag(
                Long.toString(created.version())))
            .entity(created)
            .build();
    }

    @GET
    @Path("/{id}")
    public Response find(
            @PathParam("id") UUID id,
            @Context Request request) {

        OrderView order =
            orders.find(id)
                .orElseThrow(NotFoundException::new);

        EntityTag tag =
            new EntityTag(
                Long.toString(order.version()));

        Response.ResponseBuilder preconditions =
            request.evaluatePreconditions(tag);

        if (preconditions != null) {
            return preconditions.tag(tag).build();
        }

        return Response.ok(order)
            .tag(tag)
            .build();
    }

    @POST
    @Path("/{id}/confirm")
    public Response confirm(
            @PathParam("id") UUID id,
            @HeaderParam("If-Match")
            String ifMatch) {

        if (ifMatch == null) {
            throw new ClientErrorException(
                "If-Match is required",
                Response.Status.PRECONDITION_REQUIRED);
        }

        long expectedVersion =
            EntityTags.version(ifMatch);

        ConfirmedOrder result =
            orders.confirm(id, expectedVersion);

        return Response.ok(result)
            .tag(new EntityTag(
                Long.toString(result.version())))
            .build();
    }
}

12. Jakarta Messaging (JMS)

Jakarta Messaging 3.1 standardizes point-to-point and publish/subscribe messaging, message types, destinations, producers, consumers, selectors, delivery modes, acknowledgements, transactions, and integration with Jakarta EE. A full Jakarta EE Platform implementation includes a messaging provider; the Web and Core profiles do not require one.[37]

Destination and producer

@JMSDestinationDefinition(
    name = "java:app/jms/OrderCommands",
    interfaceName = "jakarta.jms.Queue",
    destinationName = "OrderCommands")
public class MessagingConfiguration {
}
@ApplicationScoped
public class FulfillmentPublisher {
    @Inject
    JMSContext context;

    @Resource(lookup =
        "java:app/jms/OrderCommands")
    Queue destination;

    public void submit(FulfillOrder command) {
        context.createProducer()
            .setDeliveryMode(
                DeliveryMode.PERSISTENT)
            .setTimeToLive(
                Duration.ofHours(24).toMillis())
            .setProperty(
                "messageType",
                "FulfillOrder")
            .setProperty(
                "schemaVersion",
                1)
            .send(
                destination,
                JsonSupport.toJson(command));
    }
}

Persistent delivery asks the provider to retain the message according to its reliability and destination-retention policy. It does not remove the need for idempotent business processing when a transaction rolls back and the provider redelivers the message.[38]

Message-driven bean

@MessageDriven(
    activationConfig = {
        @ActivationConfigProperty(
            propertyName = "destinationLookup",
            propertyValue =
                "java:app/jms/OrderCommands"),
        @ActivationConfigProperty(
            propertyName = "destinationType",
            propertyValue =
                "jakarta.jms.Queue"),
        @ActivationConfigProperty(
            propertyName = "messageSelector",
            propertyValue =
                "messageType = 'FulfillOrder'")
    })
public class FulfillmentConsumer
        implements MessageListener {

    @Inject
    FulfillmentService fulfillment;

    @Override
    public void onMessage(Message message) {
        try {
            String body =
                message.getBody(String.class);

            fulfillment.processOnce(
                message.getJMSMessageID(),
                JsonSupport.fromJson(
                    body,
                    FulfillOrder.class));
        } catch (JMSException failure) {
            throw new MessageHandlingException(failure);
        }
    }
}

Message-driven beans are container-managed asynchronous components. Their instances, concurrency, resource injection, transaction association, and message delivery are controlled by the container and provider.[39]

Idempotent consumer

@ApplicationScoped
public class FulfillmentService {
    @PersistenceContext(unitName = "orders")
    EntityManager entityManager;

    @Transactional
    public void processOnce(
            String messageId,
            FulfillOrder command) {

        ProcessedMessage existing =
            entityManager.find(
                ProcessedMessage.class,
                messageId);

        if (existing != null) {
            return;
        }

        createShipment(command);

        entityManager.persist(
            new ProcessedMessage(

Poison-message policy

  • Validate message type, schema version, content type, and size before domain processing.
  • Distinguish transient provider or database failure from permanently invalid data.
  • Bound redelivery and configure a dead-letter or quarantine destination.
  • Preserve message ID, correlation ID, original destination, delivery count, and diagnostic details.
  • Make replay an explicit administrative operation and keep consumers idempotent.
CDI events and JMS are not substitutes. CDI events are local object notifications. Jakarta Messaging crosses transaction, process, and host boundaries through a provider and can support durable redelivery.

13. Transactions and integration

Jakarta Transactions defines transaction demarcation and coordination contracts. In a Jakarta EE environment, container-managed transactions can associate JPA persistence contexts and enlist capable messaging and database resources.[40]

@ApplicationScoped
public class OrderApplicationService {
    @Inject
    OrderRepository orders;

    @Inject
    FulfillmentPublisher fulfillment;

    @Transactional
    public CreatedOrder create(
            @NotBlank String idempotencyKey,
            @Valid @NotNull
            CreateOrderRequest request) {

        OrderEntity order =
            mapToEntity(request);

        orders.add(order);

        fulfillment.submit(
            new FulfillOrder(
                order.getId(),
                idempotencyKey));

        return CreatedOrder.from(order);
    }
}

If the configured data source and messaging provider are enlisted in the same JTA transaction, the database update and send can commit or roll back together. Distributed transaction support depends on resource capabilities and server configuration. When an external broker cannot or should not participate, a transactional outbox is often the clearer design.

Rollback policy

@Transactional(
    rollbackOn = {
        PaymentException.class,
        InventoryException.class
    },
    dontRollbackOn = {
        CustomerNotificationException.class
    })
public ConfirmedOrder confirm(UUID orderId) {
    // ...
}

Do not assume every checked exception marks a transaction for rollback. Define rollback behavior deliberately and verify it in an in-container test.

Transactional observers

public void afterCommit(
        @Observes(
            during = TransactionPhase.AFTER_SUCCESS)
        OrderConfirmed event) {

    cache.invalidate(event.orderId());
}

Transactional CDI observers can react before completion or after a particular outcome. They remain process-local and non-durable, so cross-process guarantees still require a broker or outbox.

14. Integrated order application

The same application service can serve a Servlet/JSP user interface, a Jakarta REST API, and messaging entry points. This keeps protocol translation separate from business transactions.

@ApplicationScoped
@Audited
public class OrderApplicationService {
    private final OrderRepository orders;
    private final PricingService pricing;
    private final FulfillmentPublisher fulfillment;
    private final Clock clock;

    @Inject
    public OrderApplicationService(
            OrderRepository orders,
            PricingService pricing,
            FulfillmentPublisher fulfillment,
            Clock clock) {
        this.orders = orders;
        this.pricing = pricing;
        this.fulfillment = fulfillment;
        this.clock = clock;
    }

    @Transactional
    public CreatedOrder create(
            String idempotencyKey,
            CreateOrderRequest request) {

        BigDecimal total =
            pricing.calculate(
                OrderDraft.from(request),
                request.currency());

        OrderEntity order =
            new OrderEntity(
                request.customerId(),
                total,
                request.currency(),
                clock.instant());

        request.items().stream()
            .map(item ->
                new OrderItemEmbeddable(
                    item.sku(),
                    item.quantity(),
                    pricing.unitPrice(item.sku())))
            .forEach(order::addItem);

        orders.add(order);

        fulfillment.submit(
            new FulfillOrder(
                order.getId(),
                idempotencyKey));

        return CreatedOrder.from(order);
    }

    @Transactional
    public ConfirmedOrder confirm(
            UUID id,
            long expectedVersion) {

        OrderEntity order = orders.require(id);

        if (order.getVersion()
                != expectedVersion) {
            throw new OrderConflict(
                id,
                expectedVersion,
                order.getVersion());
        }

        order.confirm();
        return ConfirmedOrder.from(order);
    }
}

Security rules

  • Authenticate at a trusted boundary and preserve validated identity.
  • Authorize the requested domain object and action, not only a path or role.
  • Use parameterized JPQL or Criteria instead of concatenating untrusted input.
  • Escape user-controlled output in JSP.
  • Use CSRF defenses for cookie-authenticated state-changing browser requests.
  • Protect JNDI resources, server consoles, JMS destinations, and management endpoints.
  • Store credentials in deployment secret systems or server credential stores, not the WAR.
  • Bound JSON depth, message size, multipart uploads, collections, and decompression.

16. Deployment and portability

The platform specification defines module composition, deployment descriptors, naming, visibility, and component environments. A simple application often needs only a WAR; an EAR is useful when modules require explicit boundaries or coordinated deployment.[1]

Portable naming

  • java:comp — component environment
  • java:module — module scope
  • java:app — application scope
  • java:global — server-wide portable global namespace

Data sources, queues, connection factories, mail sessions, and security resources can be created through portable annotations or descriptors and through product-specific administration. Keep vendor-specific configuration outside business code.

Compatible implementations

Confirm the exact Jakarta EE version, profile, product release, and Java version in the compatibility listing. A Servlet container may implement Servlet and Pages without supplying JPA, CDI Full, JMS, JTA integration, or the full Platform.[3]

Delivery models

  • Deploy a thin WAR or EAR into an independently managed application server.
  • Build a container image containing both server and application.
  • Use vendor tooling to create an optimized or bootable runtime distribution.

The application programming model can remain Jakarta EE in each case; operational packaging is a deployment choice.

19. Performance and operations

Resource pools

Database connections, messaging connections, HTTP clients, executors, and request queues are finite concurrency controls. Size them from measured service time, throughput, and downstream capacity. Increasing a pool can worsen database or broker contention.

Persistence

  • Inspect generated SQL and query counts.
  • Use projections, pagination, fetch plans, and indexes.
  • Keep transactions short and avoid remote calls while holding locks.
  • Measure optimistic conflicts and retry only when domain semantics permit.
  • Use reviewed schema migrations rather than destructive startup generation.

Web requests

  • Set connection, request, and downstream deadlines.
  • Limit body sizes, multipart uploads, and collection counts.
  • Use ETags and cache headers where representations allow them.
  • Stream large content instead of materializing it entirely.
  • Use managed concurrency and virtual-thread-aware server features without removing downstream limits.

Messaging

  • Monitor depth, oldest message age, processing duration, redelivery, and dead-letter rate.
  • Set TTL only when expiration has domain meaning.
  • Scale consumers within database and external-service capacity.
  • Preserve idempotency during rollback and replay.

Observability

Collect runtime metrics for HTTP pools, threads, transactions, data sources, persistence, and messaging, plus application metrics for order outcomes, validation failures, optimistic conflicts, queue latency, and message redelivery. Propagate trace context from HTTP into database and messaging work.

Graceful shutdown

Fail readiness, stop accepting new work, allow bounded in-flight requests and message deliveries to complete, stop application-owned clients, and flush telemetry. Leave container-owned resource destruction to the container.

21. Production checklist

Platform and build

  • Target one explicit Jakarta EE version and profile.
  • Mark the platform API as provided.
  • Verify exact server and Java compatibility.
  • Pin server, JDBC driver, persistence provider, and messaging-provider versions.

Servlet and JSP

  • Servlet fields are immutable or thread-safe.
  • Filters call the chain exactly once or terminate intentionally.
  • Async requests always complete or dispatch.
  • JSP is under WEB-INF, uses EL and tags, and contains no persistence logic.
  • User-controlled output is escaped.

Persistence

  • Entities satisfy constructor and proxyability rules.
  • Optimistic locking protects concurrent updates.
  • N+1 behavior, pagination, indexes, and transaction length are measured.
  • Entities and persistence contexts are not shared across threads.

CDI and Validation

  • Bean discovery and scopes are intentional.
  • Application-scoped beans are thread-safe.
  • Qualifiers replace string service locators.
  • Validation covers boundaries but is not mistaken for authorization.
  • Interceptor ordering and transactional effects are tested.

REST and messaging

  • HTTP status, media types, ETags, errors, and idempotency are explicit.
  • DTOs are separate from mutable entities.
  • JMS consumers tolerate duplicate delivery.
  • Poison messages have bounded redelivery and quarantine.
  • Queue age, depth, throughput, and failure rates are monitored.

Security and operations

  • Authentication, domain authorization, TLS, and secret management are configured.
  • Administrative and JNDI resources are protected.
  • Logs and traces correlate requests, transactions, and messages.
  • Rolling deployment and graceful shutdown are rehearsed.
  • Backup, restore, schema migration, and broker recovery are tested.
Final principle: Jakarta EE is not primarily a collection of annotations. It is a set of behavioral contracts between applications and containers. Correct design depends on understanding lifecycle, scope, threading, transactions, persistence contexts, HTTP semantics, and message delivery.
