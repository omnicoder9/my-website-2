1. What a design pattern is

A design pattern is a named, reusable description of a recurring design problem, its context and forces, a general arrangement of collaborating elements, and the consequences of applying that arrangement.

Patterns are not finished code, algorithms, frameworks, or mandatory class diagrams. The Gang of Four catalog describes patterns through intent, motivation, applicability, structure, participants, collaborations, consequences, implementation guidance, examples, known uses, and related patterns.[3]

Problem

A recurring design pressure, not merely a desire to use a familiar class shape.

Context

The circumstances in which the pattern solves more problems than it creates.

Forces

Competing concerns such as extensibility, identity, coupling, lifecycle, latency, or testability.

Consequences

The new indirection, objects, state, failure modes, and maintenance obligations introduced by the solution.

Pattern literacy is diagnostic vocabulary. Saying “this wrapper is a decorator” communicates composition and transparent behavioral extension. It does not prove that the decorator is necessary or correctly implemented.

2. Historical development

1977: Christopher Alexander and collaborators published A Pattern Language, presenting named, connected solutions to recurring architectural problems.[1]

1987: Kent Beck and Ward Cunningham described applying pattern languages to object-oriented program design at an OOPSLA workshop.[2]

1994: Gamma, Helm, Johnson, and Vlissides published Design Patterns: Elements of Reusable Object-Oriented Software, cataloging 23 object-oriented patterns in creational, structural, and behavioral groups.[3]

1995 onward: Java's interfaces, garbage collection, reflection, class loading, and standard libraries made many GoF structures natural, while later lambdas, records, sealed classes, modules, and concurrency APIs reduced boilerplate or changed preferred implementations.

The original catalog was written primarily in C++ and Smalltalk. Java lacks multiple class inheritance, has interfaces and automatic memory management, and now has functional interfaces, records, and sealed hierarchies. The pattern intent remains useful, but literal translations of 1994 class diagrams are often unnecessarily ceremonial in modern Java.[3][4]

4. Selecting a pattern

  1. Name the change axis. What is expected to vary: construction, implementation family, algorithm, state, interface, policy, transport, or processing sequence?
  2. Identify ownership. Who creates, selects, wraps, observes, invokes, or transitions the object?
  3. Choose the smallest stable abstraction. A lambda or method reference may be enough; an inheritance hierarchy may be justified only when shared state or protected hooks are real.
  4. Specify lifecycle and concurrency. Patterns involving shared state, observers, caches, or queues need thread-safety and cleanup rules.
  5. Test the consequence. Verify substitution, composition order, error propagation, resource closure, and evolution—not only the happy-path result.
Start from forces, not pattern names. “We need a Factory” is weaker than “the caller must not depend on provider classes, providers are selected from configuration, and adding one must not edit the caller.”

5. Creational patterns

Creational Creational patterns separate object construction, representation, or concrete type selection from clients that use the resulting objects. They are useful when constructors alone expose too many details, when object families must vary together, or when creation policy needs testing and substitution.[3]

6. Singleton

IntentEnsure one logical instance and provide a controlled access point.
Use whenIdentity is a real invariant, not merely convenience.
Main costGlobal state, hidden dependencies, lifecycle coupling, and testing difficulty.

The canonical pattern makes a class responsible for controlling its own sole instance.[3] In Java, class initialization is synchronized by the JVM, which makes static initialization and the initialization-on-demand holder idiom safe without hand-written double-checked locking.[7]

Enum singleton

public enum AuditClock {
    INSTANCE;

    private final Clock clock = Clock.systemUTC();

    public Instant now() {
        return clock.instant();
    }
}

// Usage:
Instant timestamp = AuditClock.INSTANCE.now();

Enum constants are instances of the enum class; enum constructors are inaccessible to clients, and enum serialization has special handling in the Java platform.[6][8] An enum singleton is compact and resistant to accidental reflective construction through ordinary enum rules, but it cannot extend another class and is awkward when tests need a different clock.

Initialization-on-demand holder

public final class SchemaRegistry {
    private SchemaRegistry() {
    }

    private static final class Holder {
        private static final SchemaRegistry INSTANCE =
                new SchemaRegistry();
    }

    public static SchemaRegistry instance() {
        return Holder.INSTANCE;
    }
}

The nested holder is initialized when first actively used, and class initialization is coordinated by the JVM.[7]

Prefer dependency injection when identity is not the requirement

public final class InvoiceService {
    private final Clock clock;
    private final TaxPolicy taxPolicy;

    public InvoiceService(
            Clock clock,
            TaxPolicy taxPolicy) {
        this.clock = Objects.requireNonNull(clock);
        this.taxPolicy =
                Objects.requireNonNull(taxPolicy);
    }
}

Most “singletons” are actually application-scoped services. Passing them explicitly preserves one configured instance while avoiding a hidden global access point. Effective Java recommends enum types as a robust singleton technique while also emphasizing dependency injection for resource-dependent classes.[4]

Failure modes

  • Mutable global state creates test-order dependence and cross-request interference.
  • One instance per class loader is not necessarily one instance per process.
  • Distributed systems cannot obtain cluster-wide uniqueness from a Java Singleton.
  • Lazy initialization can defer configuration failure until production traffic.

7. Factory

IntentEncapsulate concrete object creation behind a stable creation interface.
VariantsStatic/simple factory, Factory Method, Abstract Factory, provider registry.
Main costAnother abstraction and potentially opaque selection logic.

The GoF Factory Method delegates creation to subclasses, while Abstract Factory creates related product families without naming their concrete classes.[3] Java also commonly uses static factories and functional suppliers.

Static factory with exhaustive enum selection

public interface Compressor {
    byte[] compress(byte[] input);
}

public enum Compression {
    GZIP,
    ZSTD,
    NONE
}

public final class Compressors {
    private Compressors() {
    }

    public static Compressor create(
            Compression compression) {

        return switch (compression) {
            case GZIP -> new GzipCompressor();
            case ZSTD -> new ZstdCompressor();
            case NONE -> input -> input.clone();
        };
    }
}

A static factory can return cached objects, subtype instances, or objects whose concrete classes are not public. It should communicate ownership and failure clearly and should not grow into a switch edited for every third-party extension.

Functional factory

public final class RetryExecutor {
    private final Supplier<Backoff> backoffFactory;

    public RetryExecutor(
            Supplier<Backoff> backoffFactory) {
        this.backoffFactory = backoffFactory;
    }

    public <T> T execute(Callable<T> operation)
            throws Exception {
        Backoff backoff = backoffFactory.get();
        // ...
        return operation.call();
    }
}

RetryExecutor executor =
    new RetryExecutor(
        () -> new ExponentialBackoff(
            Duration.ofMillis(50),
            Duration.ofSeconds(2)));

Supplier<T> is the standard functional interface for obtaining a result and does not require that each invocation return a new object.[9]

Service-provider factory

public interface PaymentProvider {
    String name();
    PaymentGateway create(PaymentConfiguration configuration);
}

public final class PaymentProviders {
    private final Map<String, PaymentProvider> providers;

    public PaymentProviders(ModuleLayer layer) {
        this.providers =
            ServiceLoader
                .load(layer, PaymentProvider.class)
                .stream()
                .map(ServiceLoader.Provider::get)
                .collect(Collectors.toUnmodifiableMap(
                    provider ->
                        provider.name()
                            .toLowerCase(Locale.ROOT),
                    Function.identity()));
    }

    public PaymentGateway create(
            String providerName,
            PaymentConfiguration configuration) {

        PaymentProvider provider =
            Optional.ofNullable(
                providers.get(
                    providerName.toLowerCase(
                        Locale.ROOT)))
                .orElseThrow(() ->
                    new UnknownPaymentProvider(
                        providerName));

        return provider.create(configuration);
    }
}
// Provider module:
module com.example.payment.stripe {
    requires com.example.payment.api;

    provides com.example.payment.api.PaymentProvider
        with com.example.payment.stripe.StripeProvider;
}

// Consumer module:
module com.example.checkout {
    requires com.example.payment.api;

    uses com.example.payment.api.PaymentProvider;
}

ServiceLoader discovers implementations of a known service interface at runtime and supports providers on class paths or module layers through the appropriate loading method.[10]

Factory pitfalls

  • A factory that merely calls one public constructor adds little value.
  • Returning null for an unsupported type hides failure; use a typed exception or Optional.
  • Configuration parsing, secret access, and network validation should not be silently repeated on every creation.
  • Factories should not become service locators that hide all dependencies.

8. Builder

IntentSeparate stepwise construction from the resulting representation.
Use whenConstruction has many optional values, invariants, or representations.
Main costBoilerplate and duplicated defaults.

The GoF Builder separates construction steps from the representation being built.[3] In Java, the term also commonly describes a fluent constructor alternative for immutable value objects.

Immutable configuration builder

public record HttpClientConfig(
        URI baseUri,
        Duration connectTimeout,
        Duration requestTimeout,
        int maxConnections,
        Map<String, String> defaultHeaders) {

    public HttpClientConfig {
        Objects.requireNonNull(baseUri);
        Objects.requireNonNull(connectTimeout);
        Objects.requireNonNull(requestTimeout);
        defaultHeaders = Map.copyOf(defaultHeaders);

        if (!baseUri.isAbsolute()) {
            throw new IllegalArgumentException(
                "baseUri must be absolute");
        }
        if (connectTimeout.isNegative()
                || connectTimeout.isZero()) {
            throw new IllegalArgumentException(
                "connectTimeout must be positive");
        }
        if (maxConnections < 1) {
            throw new IllegalArgumentException(
                "maxConnections must be positive");
        }
    }

    public static Builder builder(URI baseUri) {
        return new Builder(baseUri);
    }

    public static final class Builder {
        private final URI baseUri;
        private Duration connectTimeout =
                Duration.ofSeconds(1);
        private Duration requestTimeout =
                Duration.ofSeconds(3);
        private int maxConnections = 100;
        private final Map<String, String> headers =
                new LinkedHashMap<>();

        private Builder(URI baseUri) {
            this.baseUri = baseUri;
        }

        public Builder connectTimeout(
                Duration value) {
            connectTimeout = value;
            return this;
        }

        public Builder requestTimeout(
                Duration value) {
            requestTimeout = value;
            return this;
        }

        public Builder maxConnections(int value) {
            maxConnections = value;
            return this;
        }

        public Builder header(
                String name,
                String value) {
            headers.put(name, value);
            return this;
        }

        public HttpClientConfig build() {
            return new HttpClientConfig(
                baseUri,
                connectTimeout,
                requestTimeout,
                maxConnections,
                headers);
        }
    }
}
HttpClientConfig config =
    HttpClientConfig
        .builder(URI.create(
            "https://inventory.example.com"))
        .connectTimeout(
            Duration.ofMillis(500))
        .requestTimeout(
            Duration.ofSeconds(2))
        .maxConnections(200)
        .header("Accept", "application/json")
        .build();

Records provide compact nominal aggregates with generated accessors, equality, hashing, and a canonical constructor; their components can be defensively copied and validated in a compact constructor.[11]

Builder design rules

  • Keep required values explicit in the builder constructor or an initial stage.
  • Validate the complete invariant in build() or the target constructor.
  • Defensively copy mutable inputs.
  • Do not allow the built object to retain the mutable builder's collections.
  • Consider a plain constructor or record when there are only a few parameters.

9. Prototype

IntentCreate new objects by copying a configured exemplar.
Use whenConstruction is expensive or variants differ from a baseline.
Main costDefining correct shallow/deep copy and identity semantics.

The Prototype pattern delegates creation to an existing object that produces a copy of itself.[3] Java's Object.clone() performs field assignment and therefore a shallow copy; mutable referenced objects are not recursively cloned.[12]

Explicit copy constructor

public final class ReportTemplate {
    private final String name;
    private final List<Section> sections;
    private final Map<String, String> metadata;

    public ReportTemplate(
            String name,
            List<Section> sections,
            Map<String, String> metadata) {
        this.name = Objects.requireNonNull(name);
        this.sections = sections.stream()
            .map(Section::copy)
            .toList();
        this.metadata = Map.copyOf(metadata);
    }

    public ReportTemplate(
            ReportTemplate source) {
        this(
            source.name,
            source.sections,
            source.metadata);
    }

    public ReportTemplate copy() {
        return new ReportTemplate(this);
    }
}

Record “with” copy

public record RenderOptions(
        Locale locale,
        ZoneId zone,
        boolean includeDiagnostics,
        int maxRows) {

    public RenderOptions withLocale(
            Locale replacement) {
        return new RenderOptions(
            replacement,
            zone,
            includeDiagnostics,
            maxRows);
    }

    public RenderOptions withMaxRows(int replacement) {
        return new RenderOptions(
            locale,
            zone,
            includeDiagnostics,
            replacement);
    }
}

Why Cloneable is often avoided

Cloneable is a marker interface with no clone method; it changes the behavior of the protected Object.clone() method. Classes conventionally expose a public override if they support cloning.[13] Copy constructors and named copy methods make the result type, validation, and deep-copy policy explicit.

// Use only when compatibility requires Cloneable.
@Override
public MutableGraph clone() {
    try {
        MutableGraph copy =
            (MutableGraph) super.clone();

        copy.nodes = new ArrayList<>(
            this.nodes.stream()
                .map(Node::copy)
                .toList());

        return copy;
    } catch (CloneNotSupportedException impossible) {
        throw new AssertionError(impossible);
    }
}

Prototype pitfalls

  • Copied database IDs, lock objects, file handles, listeners, and caches may need reset rather than duplication.
  • Cycles and shared subgraphs require an identity map during deep copy.
  • Copying immutable objects is unnecessary; references can safely be shared.
  • Serialization round-trips are a costly and risky substitute for a defined copy contract.

10. Structural patterns

Structural Structural patterns organize classes and objects into larger compositions. They change how existing capabilities are exposed, combined, simplified, or controlled without necessarily changing the core implementation.[3]

11. Adapter

IntentConvert one interface into another interface expected by a client.
Use whenA useful component has an incompatible contract.
Main costSemantic translation, error mapping, and possible information loss.

Adapter preserves an existing implementation while presenting the interface required by another part of the system.[3] The difficult part is rarely method renaming; it is reconciling units, blocking behavior, lifecycle, errors, nullability, and transactional meaning.

Legacy payment adapter

// New domain-facing port.
public interface PaymentGateway {
    Authorization authorize(
        PaymentRequest request)
        throws PaymentFailure;
}

// Legacy library contract.
public final class LegacyCardClient {
    public int charge(
            String account,
            long amountInCents) {
        // 0 = approved, positive = decline code,
        // negative = transport or protocol failure.
        return 0;
    }
}

public final class LegacyCardAdapter
        implements PaymentGateway {

    private final LegacyCardClient client;

    public LegacyCardAdapter(
            LegacyCardClient client) {
        this.client = Objects.requireNonNull(client);
    }

    @Override
    public Authorization authorize(
            PaymentRequest request)
            throws PaymentFailure {

        long cents =
            request.amount()
                .movePointRight(2)
                .longValueExact();

        int result =
            client.charge(
                request.accountToken(),
                cents);

        if (result == 0) {
            return Authorization.approved();
        }
        if (result > 0) {
            return Authorization.declined(
                "LEGACY-" + result);
        }

        throw new PaymentTransportFailure(
            "Legacy provider failed: " + result);
    }
}

Object adapter versus class adapter

An object adapter composes the adaptee and is the normal Java form. The GoF class-adapter variant relies on multiple inheritance, which Java classes do not support. Interfaces and delegation usually provide a more flexible substitute.[5]

Adapter rules

  • Define the target interface from client and domain needs, not from the legacy API.
  • Normalize units, encodings, time zones, and error types at the boundary.
  • Document whether operations block, retry, cache, or own resources.
  • Do not leak legacy status codes or mutable data structures unless they are part of the target contract.
  • Write contract tests against both the adapter and a test double of the target interface.

12. Decorator

IntentAdd responsibilities to an object dynamically while preserving its interface.
Use whenBehavior must be combined independently and in different orders.
Main costWrapper chains, order sensitivity, and identity confusion.

A decorator implements the same abstraction as the wrapped component and forwards operations while adding behavior before, after, or around delegation.[3] Java I/O is a canonical library example: FilterInputStream wraps another stream and subclasses transform data or add functionality while preserving the InputStream contract.[14]

Interface decorator

public interface CustomerRepository {
    Optional<Customer> find(CustomerId id);
    void save(Customer customer);
}

public final class CachingCustomerRepository
        implements CustomerRepository {

    private final CustomerRepository delegate;
    private final ConcurrentMap<CustomerId, Customer> cache =
        new ConcurrentHashMap<>();

    public CachingCustomerRepository(
            CustomerRepository delegate) {
        this.delegate = Objects.requireNonNull(delegate);
    }

    @Override
    public Optional<Customer> find(CustomerId id) {
        Customer cached = cache.get(id);

        if (cached != null) {
            return Optional.of(cached);
        }

        Optional<Customer> loaded =
            delegate.find(id);

        loaded.ifPresent(
            value -> cache.put(id, value));

        return loaded;
    }

    @Override
    public void save(Customer customer) {
        delegate.save(customer);
        cache.put(customer.id(), customer);
    }
}

Composable timing decorator

public final class TimedCustomerRepository
        implements CustomerRepository {

    private final CustomerRepository delegate;
    private final BiConsumer<String, Duration> recorder;
    private final Clock clock;

    public TimedCustomerRepository(
            CustomerRepository delegate,
            BiConsumer<String, Duration> recorder,
            Clock clock) {
        this.delegate = delegate;
        this.recorder = recorder;
        this.clock = clock;
    }

    @Override
    public Optional<Customer> find(CustomerId id) {
        Instant started = clock.instant();

        try {
            return delegate.find(id);
        } finally {
            recorder.accept(
                "find",
                Duration.between(
                    started,
                    clock.instant()));
        }
    }

    @Override
    public void save(Customer customer) {
        Instant started = clock.instant();

        try {
            delegate.save(customer);
        } finally {
            recorder.accept(
                "save",
                Duration.between(
                    started,
                    clock.instant()));
        }
    }
}
CustomerRepository repository =
    new TimedCustomerRepository(
        new CachingCustomerRepository(
            new JdbcCustomerRepository(dataSource)),
        metrics::recordRepositoryTime,
        Clock.systemUTC());

Decorator order is observable. Timing outside caching measures cache hits and misses; timing only the JDBC delegate measures database access. Authorization outside caching prevents unauthorized data from being returned from the cache.

Decorator pitfalls

  • Do not break substitution by changing documented return, exception, transaction, or closure semantics.
  • Define who closes a wrapped resource; try-with-resources should still work.
  • Do not compare wrappers by object identity when logical identity belongs to the underlying component.
  • A large fixed stack may be clearer as one purpose-built component than twelve tiny wrappers.

13. Facade

IntentProvide a simpler, cohesive interface to a complex subsystem.
Use whenClients should depend on a small use-case API instead of many internal components.
Main costA facade can become an oversized god object.

Facade defines a higher-level interface that makes a subsystem easier to use without necessarily hiding all lower-level interfaces.[3]

Checkout facade

public final class CheckoutFacade {
    private final CartRepository carts;
    private final InventoryGateway inventory;
    private final PaymentGateway payments;
    private final OrderRepository orders;
    private final DomainEventPublisher events;

    public CheckoutFacade(
            CartRepository carts,
            InventoryGateway inventory,
            PaymentGateway payments,
            OrderRepository orders,
            DomainEventPublisher events) {
        this.carts = carts;
        this.inventory = inventory;
        this.payments = payments;
        this.orders = orders;
        this.events = events;
    }

    public CheckoutResult checkout(
            CustomerId customerId,
            CartId cartId,
            PaymentMethod paymentMethod) {

        Cart cart = carts.require(cartId);

        Reservation reservation =
            inventory.reserve(cart.items());

        try {
            Authorization authorization =
                payments.authorize(
                    PaymentRequest.from(
                        customerId,
                        cart,
                        paymentMethod));

            if (!authorization.approved()) {
                reservation.release();
                return CheckoutResult.declined(
                    authorization.reason());
            }

            Order order =
                Order.from(
                    customerId,
                    cart,
                    reservation,
                    authorization);

            orders.save(order);
            events.publish(
                new OrderPlaced(order.id()));

            return CheckoutResult.created(order.id());
        } catch (RuntimeException failure) {
            reservation.release();
            throw failure;
        }
    }
}

Facade versus application service

In layered systems, a use-case-oriented application service often plays the facade role. Its value is not the name Facade, but that clients depend on cohesive operations while internal repositories, gateways, and workflow details remain replaceable.

Facade pitfalls

  • Do not expose every subsystem operation through one enormous interface.
  • Group methods by cohesive use case or bounded context.
  • Keep transport DTOs outside a reusable domain facade.
  • Do not hide essential transaction, latency, or failure semantics from callers.

14. Proxy

IntentProvide a surrogate controlling access to another object.
VariantsRemote, virtual/lazy, protection, caching, smart-reference, tracing.
Main costHidden I/O, latency, failures, and identity differences.

Proxy presents the same interface as a subject while controlling creation, location, security, or invocation of the real subject.[3]

Static protection proxy

public interface DocumentStore {
    Document load(DocumentId id);
    void replace(DocumentId id, Document document);
}

public final class AuthorizedDocumentStore
        implements DocumentStore {

    private final DocumentStore target;
    private final AuthorizationService authorization;
    private final Supplier<Principal> principal;

    public AuthorizedDocumentStore(
            DocumentStore target,
            AuthorizationService authorization,
            Supplier<Principal> principal) {
        this.target = target;
        this.authorization = authorization;
        this.principal = principal;
    }

    @Override
    public Document load(DocumentId id) {
        authorization.require(
            principal.get(),
            Action.READ,
            id);

        return target.load(id);
    }

    @Override
    public void replace(
            DocumentId id,
            Document document) {
        authorization.require(
            principal.get(),
            Action.WRITE,
            id);

        target.replace(id, document);
    }
}

Dynamic proxy

java.lang.reflect.Proxy creates runtime objects implementing interfaces and dispatches interface method calls to an InvocationHandler.[15][16]

public final class TimingProxy {
    private TimingProxy() {
    }

    public static <T> T create(
            Class<T> contract,
            T target,
            BiConsumer<Method, Duration> recorder) {

        InvocationHandler handler =
            (proxy, method, arguments) -> {
                long started = System.nanoTime();

                try {
                    return method.invoke(
                        target,
                        arguments);
                } catch (InvocationTargetException failure) {
                    throw failure.getCause();
                } finally {
                    recorder.accept(
                        method,
                        Duration.ofNanos(
                            System.nanoTime() - started));
                }
            };

        Object proxy =
            Proxy.newProxyInstance(
                contract.getClassLoader(),
                new Class<?>[] { contract },
                handler);

        return contract.cast(proxy);
    }
}
PaymentGateway gateway =
    TimingProxy.create(
        PaymentGateway.class,
        new HttpPaymentGateway(client),
        metrics::record);

Proxy versus Decorator

Both can share the same interface and delegate. A decorator is primarily chosen to add composable responsibilities; a proxy is primarily chosen to control access to another subject. The same wrapper can technically exhibit both intents, so name it by the force it addresses.

Proxy pitfalls

  • A remote proxy does not make a network call equivalent to a local call; document latency, timeout, and retry behavior.
  • Dynamic proxies work through interfaces. Class-based proxying requires bytecode generation or subclassing and has final-method constraints.
  • Handle equals, hashCode, toString, default methods, and checked exceptions deliberately.
  • Lazy proxies must define thread-safe initialization and failure caching.

15. Behavioral patterns

Behavioral Behavioral patterns distribute algorithms, requests, state transitions, and communication among objects. Java's functional interfaces often let behavior be passed directly as values instead of requiring one concrete class per variation.[3][17]

16. Observer

IntentDefine a one-to-many dependency so observers are notified when a subject changes.
Use whenProducers should not know concrete consumers.
Main costLifecycle leaks, reentrancy, ordering, backpressure, and failure isolation.

The classic Observer pattern lets a subject maintain subscribers and notify them of changes.[3] Java's old java.util.Observable and Observer types have been deprecated since Java 9 because their event model is limited and notification ordering is unspecified; the Java API points to richer event models, concurrent data structures, or Flow for reactive streams.[21]

Synchronous typed observer

@FunctionalInterface
public interface OrderListener {
    void onOrderEvent(OrderEvent event);
}

public final class OrderEventSource {
    private final CopyOnWriteArrayList<OrderListener>
        listeners = new CopyOnWriteArrayList<>();

    public AutoCloseable subscribe(
            OrderListener listener) {
        listeners.add(
            Objects.requireNonNull(listener));

        return () -> listeners.remove(listener);
    }

    public void publish(OrderEvent event) {
        List<Throwable> failures =
            new ArrayList<>();

        for (OrderListener listener : listeners) {
            try {
                listener.onOrderEvent(event);
            } catch (Throwable failure) {
                failures.add(failure);
            }
        }

        if (!failures.isEmpty()) {
            throw new ObserverNotificationException(
                failures);
        }
    }
}

CopyOnWriteArrayList is thread-safe and copies its backing array on mutation, making it appropriate when subscription changes are rare and iteration is frequent.[22] It is a poor choice when observers are added and removed at high frequency or the list is large.

Reactive observer with Flow

The Flow interfaces define Publisher, Subscriber, Subscription, and Processor roles and include demand signaling. A publisher invokes each subscriber's callbacks in strictly ordered happens-before order for a subscription.[19]

public final class OrderPublisher
        implements AutoCloseable {

    private final SubmissionPublisher<OrderEvent>
        publisher =
            new SubmissionPublisher<>();

    public void subscribe(
            Flow.Subscriber<OrderEvent> subscriber) {
        publisher.subscribe(subscriber);
    }

    public int publish(OrderEvent event) {
        return publisher.offer(
            event,
            Duration.ofMillis(100),
            (subscriber, dropped) -> {
                metrics.incrementDroppedEvents();
                return false;
            });
    }

    @Override
    public void close() {
        publisher.close();
    }
}

SubmissionPublisher is a standard asynchronous Flow publisher with buffering and submission methods; production policy still must define executors, capacity, drops, subscriber failures, and shutdown.[20]

Observer pitfalls

  • Unsubscribe or use lifecycle ownership to prevent retained observers.
  • Specify synchronous versus asynchronous delivery.
  • Define ordering, duplicate handling, replay, and error policy.
  • A process-local Observer is not durable messaging.
  • A slow subscriber must not silently block unrelated work unless that is the intended backpressure policy.

17. Strategy

IntentEncapsulate interchangeable algorithms behind one contract.
Use whenOne operation varies independently from the context using it.
Main costSelection logic and proliferation of tiny implementations.

Strategy defines a family of algorithms, encapsulates each one, and makes them interchangeable.[3] A stateless one-method strategy maps naturally to a Java functional interface and lambda.

Named strategy interface

@FunctionalInterface
public interface DiscountPolicy {
    Money discount(
        Customer customer,
        Cart cart);
}

public final class CheckoutPricing {
    private final DiscountPolicy discounts;

    public CheckoutPricing(
            DiscountPolicy discounts) {
        this.discounts =
            Objects.requireNonNull(discounts);
    }

    public Money total(
            Customer customer,
            Cart cart) {
        return cart.subtotal()
            .minus(
                discounts.discount(
                    customer,
                    cart));
    }
}
DiscountPolicy noDiscount =
    (customer, cart) -> Money.zero(
        cart.currency());

DiscountPolicy loyalty =
    (customer, cart) ->
        customer.loyaltyYears() >= 5
            ? cart.subtotal()
                .multiply(new BigDecimal("0.10"))
            : Money.zero(cart.currency());

CheckoutPricing pricing =
    new CheckoutPricing(loyalty);

Function, Predicate, Consumer, Supplier, and operator specializations are standard functional interfaces. Use a domain-named interface when method names, checked exceptions, documentation, or multiple related operations matter.[17][18]

Strategy registry

public final class TaxPolicies {
    private final Map<CountryCode, TaxPolicy> policies;

    public TaxPolicies(
            Map<CountryCode, TaxPolicy> policies) {
        this.policies = Map.copyOf(policies);

Strategy pitfalls

  • Do not pass a large context object merely to avoid defining the strategy's real inputs.
  • Keep selection outside the algorithm implementation.
  • Use immutable or thread-safe strategy instances when shared.
  • If algorithms require coordinated mutable state and transitions, State may be the better model.

18. Command

IntentEncapsulate a request as an object.
Use whenRequests need queuing, logging, retries, scheduling, undo, or composition.
Main costCommand classes, captured state, serialization, and execution policy.

Command turns an operation and its parameters into a value that can be stored, passed, scheduled, retried, or audited independently of the invoker.[3] Java's Runnable is a minimal command that returns no result; Callable<V> returns a result and may throw a checked exception.[23][24]

Domain command records

public final class OrderCommandHandler {

Records are useful for immutable command envelopes, while a sealed interface makes the permitted command set explicit and allows exhaustive switching.[11][25]

Undoable command

public interface UndoableCommand {
    void execute();
    void undo();
}

public final class RenameDocument
        implements UndoableCommand {

    private final Document document;
    private final String replacement;
    private String previous;
    private boolean executed;

    public RenameDocument(
            Document document,
            String replacement) {
        this.document = document;
        this.replacement = replacement;
    }

    @Override
    public void execute() {
        if (executed) {
            throw new IllegalStateException(
                "Command already executed");
        }

        previous = document.name();
        document.rename(replacement);
        executed = true;
    }

    @Override
    public void undo() {
        if (!executed) {
            throw new IllegalStateException(
                "Command has not executed");
        }

        document.rename(previous);
        executed = false;
    }
}

Command pitfalls

  • A queued command needs stable identity and idempotent processing.
  • Do not serialize arbitrary implementation objects as a long-lived wire contract.
  • Undo is a domain operation, not reversal of time; external effects may require compensation.
  • Separate the command payload from execution concerns such as retry and authorization.
  • Captured lambdas can unintentionally retain large object graphs.

19. State

IntentChange an object's behavior when its internal state changes.
Use whenBehavior and allowed transitions vary by a finite lifecycle state.
Main costTransition ownership, persistence, and state-object proliferation.

State represents state-specific behavior in separate objects, making the context appear to change class as its state changes.[3] Sealed hierarchies and pattern-matching switches make closed Java state machines explicit and exhaustive.[25]

Sealed state machine

Transition table alternative

public enum Status {
    DRAFT,
    SUBMITTED,
    PAID,
    SHIPPED,
    CANCELLED
}

public enum Action {
    SUBMIT,
    PAY,
    SHIP,
    CANCEL
}

public final class Transitions {
    private static final Map<
            Status,
            Map<Action, Status>> TABLE =
        Map.of(
            Status.DRAFT,
            Map.of(
                Action.SUBMIT,
                Status.SUBMITTED,
                Action.CANCEL,
                Status.CANCELLED),
            Status.SUBMITTED,
            Map.of(
                Action.PAY,
                Status.PAID,
                Action.CANCEL,
                Status.CANCELLED),
            Status.PAID,
            Map.of(
                Action.SHIP,
                Status.SHIPPED));

    public static Status apply(
            Status state,
            Action action) {
        return Optional.ofNullable(TABLE.get(state))
            .map(row -> row.get(action))
            .orElseThrow(() ->
                new InvalidTransition(
                    state,
                    action));
    }
}

Use state objects when states own substantial behavior or data. A table or switch may be clearer when the machine is small and transitions are mostly declarative.

State pitfalls

  • Persist state and version together when concurrent transitions are possible.
  • Keep transition side effects atomic with the state update or use an outbox.
  • Do not expose setters that bypass transition rules.
  • Separate current state from historical events when auditability matters.

20. Template Method

IntentDefine an algorithm skeleton while allowing selected steps to vary.
Use whenSeveral workflows share invariant sequencing and extension hooks.
Main costInheritance coupling and fragile hook contracts.

Template Method places the invariant algorithm in a base class and delegates variable steps to protected operations implemented or overridden by subclasses.[3]

Abstract-class template

public abstract class ImportJob<R> {
    public final ImportResult run(
            InputStream input)
            throws IOException {

        Objects.requireNonNull(input);

        Instant started = Instant.now();
        List<ImportError> errors =
            new ArrayList<>();

        try (input) {
            validateHeader(input);
            Stream<R> records = parse(input);

            long accepted =
                records
                    .map(this::normalize)
                    .filter(record ->
                        validateRecord(
                            record,
                            errors))
                    .peek(this::persist)
                    .count();

            afterCommit(accepted);

            return new ImportResult(
                accepted,
                List.copyOf(errors),
                Duration.between(
                    started,
                    Instant.now()));
        }
    }

    protected abstract void validateHeader(
            InputStream input)
            throws IOException;

    protected abstract Stream<R> parse(
            InputStream input)
            throws IOException;

    protected R normalize(R record) {
        return record;
    }

    protected abstract boolean validateRecord(
            R record,
            List<ImportError> errors);

    protected abstract void persist(R record);

    protected void afterCommit(long accepted) {
        // Optional hook.
    }
}

The template method is final so subclasses cannot reorder resource closure, validation, persistence, and result construction. Protected hooks form a subclass API and require the same care as public interfaces.

Composition alternative

public record ImportPipeline<R>(
        HeaderValidator headerValidator,
        Parser<R> parser,
        UnaryOperator<R> normalizer,
        Predicate<R> validator,
        Consumer<R> persister,
        LongConsumer completion) {

    public ImportResult run(InputStream input)
            throws IOException {

        headerValidator.validate(input);

        long accepted =
            parser.parse(input)
                .map(normalizer)
                .filter(validator)
                .peek(persister)
                .count();

        completion.accept(accepted);
        return ImportResult.success(accepted);
    }
}

Composition can express the same fixed sequencing with Strategy functions and avoids subclass coupling. Template Method remains useful when subclasses share protected state, construction rules, or a mature extension lifecycle.

Default-method templates

Interfaces may declare default methods, allowing shared algorithm fragments without class inheritance. Default methods are inherited according to Java interface rules and must preserve compatibility with implementors.[26]

public interface RetriableOperation<T> {
    T attempt() throws Exception;

    default T execute(
            int maxAttempts)
            throws Exception {

        Exception last = null;

        for (int attempt = 1;
                attempt <= maxAttempts;
                attempt++) {
            try {
                return attempt();
            } catch (Exception failure) {
                last = failure;
            }
        }

        throw last;
    }
}

Template pitfalls

  • Do not invoke overridable methods from constructors.
  • Document hook order, transaction state, nullability, and exception behavior.
  • Prefer composition when callers need runtime combination of steps.
  • Keep the skeleton small; a base class with dozens of hooks is a framework that needs formal compatibility discipline.

21. Chain of Responsibility

IntentPass a request through potential handlers until one handles it or all participate.
Use whenHandler selection or processing order should be configurable.
Main costOrder dependence, lost requests, and unclear error policy.

Chain of Responsibility decouples a sender from a specific receiver by giving multiple objects an opportunity to handle a request.[3] Chains appear in servlet filters, middleware, validation pipelines, logging handlers, authentication, and message processors. Java logging Handler objects receive and export log records and are expected to be thread-safe because arbitrary threads may invoke them.[27]

First-handler-wins chain

@FunctionalInterface
public interface SupportHandler {
    Optional<Resolution> handle(
        SupportRequest request);
}

public final class SupportChain
        implements SupportHandler {

    private final List<SupportHandler> handlers;

    public SupportChain(
            List<SupportHandler> handlers) {
        this.handlers = List.copyOf(handlers);
    }

    @Override
    public Optional<Resolution> handle(
            SupportRequest request) {

        for (SupportHandler handler : handlers) {
            Optional<Resolution> result =
                handler.handle(request);

            if (result.isPresent()) {
                return result;
            }
        }

        return Optional.empty();
    }
}
SupportChain chain =
    new SupportChain(
        List.of(
            new PasswordResetHandler(),
            new BillingHandler(),
            new TechnicalSupportHandler()));

Around-invocation middleware chain

@FunctionalInterface
public interface Middleware {
    Response invoke(
        Request request,
        Next next)
        throws Exception;
}

@FunctionalInterface
public interface Next {
    Response invoke(Request request)
        throws Exception;
}

public final class MiddlewareChain {
    private final Next entry;

    public MiddlewareChain(
            List<Middleware> middleware,
            Next terminal) {

        Next current = terminal;

        ListIterator<Middleware> iterator =
            middleware.listIterator(
                middleware.size());

        while (iterator.hasPrevious()) {
            Middleware layer =
                iterator.previous();

            Next downstream = current;

            current = request ->
                layer.invoke(
                    request,
                    downstream);
        }

        this.entry = current;
    }

    public Response invoke(Request request)
            throws Exception {
        return entry.invoke(request);
    }
}
Middleware authentication =
    (request, next) -> {
        Principal principal =
            authenticate(request);
        return next.invoke(
            request.withPrincipal(principal));
    };

Middleware timing =
    (request, next) -> {
        long started = System.nanoTime();
        try {
            return next.invoke(request);
        } finally {
            metrics.record(
                "request",
                System.nanoTime() - started);
        }
    };

MiddlewareChain chain =
    new MiddlewareChain(
        List.of(timing, authentication),
        controller::handle);

Chain semantics to specify

  • Does every handler run, or does the first match terminate the chain?
  • Can a handler modify the request or response?
  • What happens when no handler accepts the request?
  • How are exceptions, retries, and compensation handled?
  • Is order fixed, configured, or priority-based?
  • Can a handler invoke the remainder more than once?

22. Closely related patterns

PatternsKey distinction
Adapter vs DecoratorAdapter changes the interface; Decorator preserves it and adds responsibility.
Decorator vs ProxyDecorator emphasizes composable behavior; Proxy emphasizes controlled access to a subject.
Facade vs AdapterFacade simplifies a subsystem for new clients; Adapter translates an incompatible existing interface.
Factory vs BuilderFactory selects or creates a product; Builder coordinates stepwise construction, often of one complex product.
Prototype vs BuilderPrototype starts from an existing exemplar; Builder starts from construction inputs and defaults.
Strategy vs StateStrategy is usually selected by the client; State changes as the context evolves and controls allowed behavior.
Strategy vs CommandStrategy represents an algorithm; Command represents a request, often carrying identity and parameters.
Observer vs messagingObserver is often in-process and immediate; a broker adds durability, delivery policy, and process boundaries.
Template Method vs StrategyTemplate Method varies steps through inheritance; Strategy varies behavior through composition.
Chain vs DecoratorA Chain selects or sequences handlers; a Decorator wraps one component while preserving its abstraction.

public abstract class DocumentImportTemplate {

            InputStream input,
            ProcessingOptions options)

                parser(options).parse(input);

                    options);

            return id;
        }

    }

Factory tests

  • Verify every supported discriminator maps to the correct contract implementation.
  • Verify unsupported values fail explicitly.
  • For ServiceLoader, test module descriptors and duplicate provider names.
  • Verify factories do not return shared mutable objects unless documented.

  • Subscribe, publish, unsubscribe, then prove no further notification occurs.
  • Define behavior when one observer throws.
  • Test reentrant publication and concurrent subscription changes.
  • For Flow, test demand, completion, cancellation, overflow, and subscriber failure.

Concurrency rules

Pattern structure does not imply thread safety. Singleton only controls instance count. Observer collections need safe iteration. Lazy proxies need safe publication. Decorator stacks must preserve synchronization requirements. Commands submitted to executors may run concurrently. The Java concurrency library provides standard executors, queues, synchronization aids, concurrent collections, and task abstractions intended as building blocks.[28][30]

  • Prefer immutable pattern participants and constructor injection.
  • Document whether objects are thread-safe, confined, or externally synchronized.
  • Never hold a lock while invoking unknown observers or chain handlers.
  • Bound executor queues and define rejection behavior.
  • Make cancellation and interruption part of Command and Proxy contracts when operations block.

25. Pattern overuse and common mistakes

MistakeConsequenceSimpler correction
Singleton for every serviceGlobal coupling and difficult testsConstruct one instance in composition root and inject it
Factory for one stable constructorIndirection without variabilityCall the constructor or use a clear static factory
Builder for a three-field valueMore code than the objectUse a record constructor
Deep inheritance for Template MethodFragile hook ordering and subclass couplingCompose strategies or functions
Observer as durable integrationLost events on crash and hidden synchronous couplingUse a transactionally integrated message system
Decorator that changes the contractBroken substitutabilityCreate an Adapter or a new abstraction
Proxy hiding remote I/OUnexpected latency and retry ambiguityName remote operations and expose deadlines
State represented by booleansImpossible combinations and scattered transitionsUse enum, sealed state, or transition table
Chain with undocumented orderSecurity and correctness vary by registration orderMake order explicit and test it

Patterns should reduce the cost of expected change. If a pattern introduces more concepts than the anticipated variation, it is speculative generality rather than reusable design. Refactoring literature recommends introducing abstractions in response to observed duplication, coupling, and change pressure rather than building elaborate flexibility without evidence.[31]

26. Pattern review checklist

Problem and intent

  • The recurring problem and expected variation are stated without naming the pattern.
  • The chosen pattern directly addresses that variation.
  • A simpler constructor, function, record, enum, or composition was considered.

Contracts

  • Interfaces define behavior, errors, lifecycle, blocking, ownership, and nullability.
  • Adapters, decorators, and proxies preserve or deliberately translate contracts.
  • Builders and prototypes define defensive-copy and validation semantics.

Lifecycle and concurrency

  • Singleton scope is defined: class loader, process, application, tenant, or cluster.
  • Observers can unsubscribe and cannot leak owners.
  • Lazy proxies and caches publish values safely.
  • Commands define cancellation, idempotency, retry, and persistence boundaries.
  • State transitions are atomic and versioned when concurrent.
  • Chains define order, termination, and failure behavior.

Evolution

  • Factories can add providers without editing unrelated clients when extensibility is required.
  • Sealed hierarchies are used only when the subtype set should be closed.
  • Template hooks are minimal, documented, and compatibility-tested.
  • Wire commands and events do not serialize arbitrary implementation classes.

Testing

  • Contract tests run against concrete, adapted, decorated, and proxied implementations.
  • Composition order is tested.
  • Observer failures, duplicate commands, invalid transitions, and no-handler chains are tested.
  • Concurrent access and cleanup are tested where applicable.
Final principle: the best pattern implementation is the least elaborate structure that makes the real variation explicit, preserves the contract, and leaves consequences visible. Modern Java often retains the GoF intent while replacing a hierarchy with a lambda, record, enum, sealed type, or library facility.
