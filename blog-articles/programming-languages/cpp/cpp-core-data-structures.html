Core Data Structures and Language Features in C++

Arrays, strings, pointers, references, dynamic memory, enumerations, type aliases, namespaces, structs and unions, and the preprocessor: how each works, where it comes from in the standard, and how to use it well in modern C++.

1. Introduction

C++ is defined by an International Standard, ISO/IEC 14882, maintained by the ISO working group JTC1/SC22/WG21. The edition published in December 2020 (C++20) was superseded in October 2024 by ISO/IEC 14882:2024 (C++23) [1,2]. The committee's working draft is publicly available and is the most convenient way to read the normative wording; this article cites its sections by their stable names in square brackets, for example [dcl.array], which do not change between editions the way clause numbers do [3].

The features covered here are the building blocks C++ inherited from C (arrays, pointers, struct, union, enum, typedef, and the preprocessor) together with the facilities C++ added to make them safer and more expressive (references, std::string, scoped enumerations, using aliases, namespaces, and owning smart pointers) [4,5]. Throughout, the recommendations follow the C++ Core Guidelines, edited by Bjarne Stroustrup and Herb Sutter, which codify modern best practice [6].

Each section gives the concept, the relevant rules, a complete compilable program, and that program's actual output.

2. Arrays

2.1 Fixed-size built-in arrays

A declaration T a[N] declares an array of N elements of type T. The bound N must be a constant expression greater than zero, and it is part of the type: int[5] and int[6] are different types. An array object consists of N contiguously allocated subobjects of type T [7,8]. When the bound is omitted, it is deduced from the initialiser, so char word[] = "abc" has type char[4] because a string literal includes a terminating null character [7,9].

Built-in arrays have two well-known pitfalls. First, in most expressions an array is implicitly converted to a pointer to its first element (array-to-pointer conversion, often called decay), which loses the size [10]. A function parameter declared as int a[] is in fact a pointer. Second, built-in arrays cannot be copied or assigned as a whole [8]. Passing an array by reference, as in const T (&)[N], preserves the bound, and std::size uses that technique.

The standard library class template std::array<T, N> is an aggregate with the same semantics as a struct holding a built-in array T[N] as its only data member, so it costs nothing extra at run time, while adding value semantics (copy, assignment, comparison), size(), iterators, and bounds-checked access through at() [11,12]. The Core Guidelines recommend std::array or std::vector over C-style arrays and advise never passing an array as a lone pointer [13,14].

2.2 Multidimensional arrays

C++ has no separate multidimensional array type: int grid[3][4] is an array of 3 arrays of 4 int. Because each element of the outer array is itself a contiguous array, the elements of each row are adjacent in memory (row-major order) [7,8]. All bounds except the first must be known when such an array is passed to a function, since they are part of the element type.

3. Strings

3.1 Character arrays (C strings)

A string literal such as "Hello" has type "array of n const char", where n is the number of characters plus one for the terminating '\0' [9,15]. The C library functions in <cstring> (strlen, strcpy, strcat, strcmp and so on) operate on such null-terminated byte strings. They trust the caller to provide enough space and a terminator: std::strlen has undefined behaviour if its argument does not point to a null-terminated array [16]. This is a classic source of buffer overflows, which is why the bounded variants such as strncat are used with an explicitly computed remaining capacity in the listing below.

3.2 std::string and std::string_view

std::string is an alias for std::basic_string<char>, a class template that owns a contiguous, dynamically sized sequence of characters and manages its own memory [17,18]. It provides concatenation (+, +=, append), searching (find, rfind, with npos meaning "not found"), extraction (substr), modification (insert, erase, replace), lexicographic comparison operators, numeric conversions (std::stoi, std::to_string), and c_str() to obtain a null-terminated pointer for C APIs [18]. C++20 added starts_with and ends_with, and C++23 added contains [18].

std::string_view (C++17) is a non-owning view of a contiguous character sequence: essentially a pointer and a length [19,20]. It is the idiomatic type for read-only string parameters because it binds cheaply to string literals, character arrays and std::string alike. Because it does not own its characters, a view must not outlive the data it refers to [20]. The Core Guidelines summarise the division of labour: use std::string to own character sequences and std::string_view to refer to them [21,22].

4. Pointers

4.1 Addresses and dereferencing

A pointer is an object whose value is the address of another object (or function), or a null pointer value [23,24]. The unary & operator yields the address of its operand, and the unary * operator performs indirection, producing an lvalue that refers to the pointed-to object [25]. const can apply to the pointer, to the pointee, or to both: const int* p is a pointer to a constant int, while int* const p is a constant pointer to a modifiable int [4,23].

4.2 Pointer arithmetic

Adding an integer j to a pointer to element i of an array of n elements yields a pointer to element i + j, provided 0 ≤ i + j ≤ n. The value n is allowed: a pointer may point one past the end of an array, but it may not be dereferenced. Any result outside that range is undefined behaviour. Subtracting two pointers into the same array gives the number of elements between them as a std::ptrdiff_t, not a number of bytes [26,27]. The subscript expression E1[E2] is defined to be identical to *((E1)+(E2)), which is why p[2] and *(p + 2) are interchangeable [28].

4.3 Null pointers

The keyword nullptr is the pointer literal; its type is std::nullptr_t, and it converts to the null pointer value of any pointer type [29–31]. Unlike 0 or the macro NULL, nullptr is not an integer, so it cannot accidentally select an integer overload [32]. Dereferencing a null (or otherwise invalid) pointer is undefined behaviour, so any pointer that may be null must be checked before use [33]. The Guidelines recommend nullptr over 0 and NULL, and simple, straightforward pointer use [34,35]. In modern code a raw pointer T* should be treated as non-owning; ownership is expressed with smart pointers (Section 6) [36].

5. References

5.1 Lvalue references

A reference is an alias for an existing object or function. It must be initialised when declared and cannot later be made to refer to something else; there are no null references, arrays of references, or pointers to references [37,38]. An lvalue reference T& binds to an lvalue of type T. Non-const lvalue references are the usual way to express "in-out" parameters [39]. A const T& can also bind to a temporary, which makes it a common way to pass large read-only arguments without copying [40].

5.2 Value categories and rvalue references

Every expression has a value category: it is an lvalue, an xvalue, or a prvalue; lvalues and xvalues together are glvalues, and prvalues and xvalues together are rvalues [41,42]. An rvalue reference T&&, introduced in C++11, binds only to rvalues, which identify objects whose resources may be reused. This enables move semantics: a move constructor T(T&&) can transfer ownership of a resource instead of copying it [5,38].

std::move does not move anything by itself; it is an unconditional cast to an rvalue reference (an xvalue), which makes the move overload eligible [43,44]. A moved-from standard library object is left in a valid but unspecified state [43]. When a reference to a temporary is bound directly, the temporary's lifetime is extended to that of the reference [45].

5.3 Forwarding references

In a function template, a parameter of the form T&& where T is deduced is a forwarding reference (Meyers calls it a "universal reference"). It binds to both lvalues and rvalues, and std::forward<T> passes the argument on with its original value category preserved. This is perfect forwarding [38,46,47].

6. Dynamic memory

6.1 new and delete

Objects with dynamic storage duration are created by a new-expression and live until destroyed by a delete-expression, independent of scope [48,49]. A new-expression obtains storage by calling an allocation function (operator new) and then initialises the object; a delete-expression calls the destructor and then releases the storage [48,50]. The single-object and array forms must be matched: memory from new T must be released with delete, and memory from new T[n] with delete[]; mixing them is undefined behaviour [50,51]. If allocation fails, the default allocation function throws std::bad_alloc; the new (std::nothrow) form returns a null pointer instead [49,52].

Manual new/delete is error-prone. Forgetting the delete leaks memory, deleting twice or using memory after deleting it is undefined behaviour, and an exception thrown between allocation and deallocation skips the cleanup entirely [53].

6.2 RAII and smart pointers

The C++ solution is Resource Acquisition Is Initialisation (RAII): tie each resource to the lifetime of an object whose destructor releases it, so cleanup happens automatically, including during exception propagation [5,54]. std::unique_ptr expresses sole ownership and, with the default deleter, is typically the same size as a raw pointer [55]. std::shared_ptr expresses shared ownership through a reference count and destroys the object when the last owner goes away [56,57]. The factory functions std::make_unique and std::make_shared avoid writing new at all [58]. The Core Guidelines state the rules plainly: avoid calling new and delete explicitly, and use unique_ptr or shared_ptr to represent ownership [59,60]. For dynamically sized sequences, a container such as std::vector is usually the right answer.

Note that local objects are destroyed in reverse order of construction, which is why shared is destroyed before unique in the output above [61].

7. Enumerations

An enumeration is a distinct type whose values are named constants called enumerators [62,63].

7.1 Unscoped enum

A traditional (unscoped) enumeration, inherited from C, places its enumerators in the enclosing scope and converts implicitly to an integer type through integral promotion [62,63]. Both properties cause trouble: enumerator names can clash with other names, and comparisons between unrelated enumerations or with plain integers compile silently.

7.2 Scoped enum class

A scoped enumeration (enum class or enum struct, C++11) keeps its enumerators inside its own scope, so they must be qualified (Direction::North), and it has no implicit conversion to integers; a static_cast is required. If no underlying type is specified, the underlying type of a scoped enumeration is int [62,63]. An explicit underlying type, as in enum class Status : std::uint8_t, fixes the size and permits opaque (forward) declarations [62]. C++20's using enum declaration brings the enumerators into a local scope when repetition gets tedious [63,64].

The Core Guidelines recommend enumerations over macros for sets of named constants, prefer class enums over plain enums, and advise specifying an underlying type only when necessary [65–67]. Meyers gives the same advice [68].

8. Type aliases: using and typedef

A typedef declaration, inherited from C, introduces a name that is a synonym for an existing type. It does not create a new type [69,70]. C++11 added the alias-declaration, using Name = type;, which has exactly the same semantics as the corresponding typedef [69,71]. The using form has two advantages. It reads left to right, with the new name first, which makes function-pointer and array types far easier to read. It can also be templated: an alias template such as template<class V> using Dictionary = std::map<std::string, V>; is impossible with typedef [71,72]. For these reasons both the Core Guidelines and Meyers prefer using [73,74].

Because an alias is not a distinct type, using Celsius = double; documents intent but does not stop a Celsius being mixed with any other double. When that safety matters, define a small struct or a scoped enumeration instead.

9. Namespaces

A namespace is a named declarative region. Names declared inside it are qualified by the namespace name, so independently developed libraries can each define, say, area without colliding [75–77]. Namespaces are open: a namespace may be extended by further definitions, even across files. Since C++17, nested namespaces may be declared compactly as namespace a::b::c { } [75,76].

  • Namespace aliases (namespace util = company::project::util;) give a long name a short local synonym [78].
  • Using-declarations (using std::cout;) introduce a single name into the current scope [79].
  • Using-directives (using namespace std;) make all names of a namespace visible for unqualified lookup [80]. At global scope in a header, a using-directive silently affects every file that includes it, which the Guidelines forbid; even in source files they recommend using-directives only for transition, for foundation libraries such as std, or within a local scope [81,82].
  • Unnamed namespaces give their members internal linkage, making them private to the translation unit. This is the C++ replacement for file-scope static [76,83].
  • Inline namespaces make their members available as members of the enclosing namespace, which libraries use for versioning [75,76].

The Guidelines also recommend using namespaces to express logical structure [84].

10. Structs and unions: custom data layouts

10.1 Structs

In C++ a struct is a class whose members are public by default, whereas those of a class are private by default; apart from such defaults the two keywords define the same kind of type [85,86]. A struct with no user-declared constructors, no private or protected direct non-static data members, and no virtual functions is an aggregate and can be initialised with braces, member by member. C++20 adds designated initialisers such as {.x = 3.0, .y = 4.0}, which must appear in declaration order [87,88]. Default member initialisers supply values for members that are not explicitly initialised, and structured bindings (C++17) unpack a struct into named variables [89,90].

10.2 Layout, alignment and padding

Non-static data members of a class are allocated so that later-declared members have higher addresses within the object, but each type has an alignment requirement, and the implementation may insert padding between members and after the last one to satisfy it [91,92]. The order of members therefore affects the object's size. In the listing, Padded occupies 12 bytes and Packed 8 on the test platform, although exact sizes are implementation-defined. offsetof reports a member's byte offset and is only guaranteed to work for standard-layout classes [93,94]. Bit-fields pack members into a specified number of bits; their allocation within the object is implementation-defined, so they should not be relied upon for exact external layouts [95,96].

10.3 Unions

In a union, all non-static data members share the same storage, so the union is at least as large as its largest member. At most one member is active at any time: the one most recently written [97,98]. Reading a member other than the active one is undefined behaviour in C++ (with a narrow exception for common initial sequences of standard-layout structs), so unions must not be used for type punning [98,99]. A union should be paired with a tag recording which member is active. An anonymous union inside a struct makes this pattern convenient [100]. The Guidelines warn against such "naked" unions, and in most code the type-safe std::variant (C++17), which tracks the active alternative itself and throws std::bad_variant_access on a wrong access, is the better tool [101,102].

11. The preprocessor

Before compilation proper, each source file is processed by the preprocessor, which handles lines beginning with #: file inclusion, macro replacement and conditional inclusion [103]. The preprocessor works on tokens and knows nothing about C++ scopes, types or namespaces, which explains both its power and its hazards [104].

11.1 #include

#include <header> and #include "file" replace the directive with the entire contents of the named header or source file. The search locations are implementation-defined. Conventionally the quoted form searches the including file's directory first and then falls back to the angle-bracket search [105,106]. Because a header may be included more than once in a translation unit, every header should have an include guard (#ifndef/#define/#endif) or the widely supported but non-standard #pragma once [106,107]. C++20 modules (import) offer a structured alternative to textual inclusion.

11.2 Macros

#define creates object-like macros (#define BUFFER_SIZE 256) and function-like macros (#define SQUARE(x) ((x) * (x))) [108,109]. Replacement is purely textual. Without parentheses, BAD_SQUARE(1 + 2) expands to 1 + 2 * 1 + 2, which is 5. Arguments with side effects may also be evaluated more than once. The # operator turns a macro argument into a string literal, and ## pastes two tokens together [110,111]. Predefined macros such as __FILE__, __LINE__ and __cplusplus describe the translation environment. __cplusplus is 201703L for C++17, 202002L for C++20 and 202302L for C++23 [109].

For constants and functions, modern C++ has better tools (constexpr variables, inline and constexpr functions, templates and enumerations), which respect scope and type. The Core Guidelines say not to use macros for constants or "functions", nor for program text manipulation [112,113].

11.3 Conditional compilation

#if, #ifdef, #ifndef, #elif, #else and #endif include or exclude blocks of source based on constant expressions evaluated by the preprocessor, using the defined operator and, since C++17, __has_include [114,115]. C++23 adds #elifdef and #elifndef [115]. Typical uses are include guards, platform-specific code, debug-only diagnostics controlled by NDEBUG (the same macro that disables assert), and testing for language or library features with feature-test macros [115,116].
