1Introduction: what OOP means in C++

Object-oriented programming (OOP) organises a program around objects: units that bundle state with the operations that act on it, are described by classes, and are related to one another through hierarchies and references. Booch characterises the object model by four major elements, abstraction, encapsulation, modularity and hierarchy[4], and C++ supports each of them directly.

C++ inherited its class concept from Simula 67, the language in which Dahl and Nygaard introduced classes, objects and subclassing[5]; Stroustrup's original goal for “C with Classes” was to combine Simula's program-organisation facilities with C's efficiency[6]. The result is a multi-paradigm language: object-oriented programming is one supported style among several, alongside procedural, generic and functional styles[7]. This shapes idiomatic C++ OOP in three ways that distinguish it from languages such as Java or C#:

  • Value semantics by default. Objects are values that live on the stack, inside other objects, or in containers; they are not implicitly heap-allocated references. Run-time polymorphism is opt-in, through virtual functions accessed via pointers or references[7,8].
  • Deterministic lifetime. A destructor runs at a precisely defined point, which makes “resource acquisition is initialisation” (RAII) the central resource-management technique[9 R.1; 10].
  • You pay only for what you use. A class with no virtual functions carries no dispatch overhead, and much polymorphism in C++ is resolved at compile time through overloading and templates[6,8].

2Classes and objects: fields, methods, constructors, destructors

A class is a user-defined type; an object is a region of storage of that type with a lifetime. A class definition declares members: non-static data members (fields), member functions (methods), nested types, and static members[1 §class.mem.general; 11]. The keywords class and struct both define classes; the only difference is the default access (private for class, public for struct) and the default base-class access[1 §class.access.general, §class.access.base]. The C++ Core Guidelines recommend class when the type has an invariant and struct when the data members can vary independently (rule C.2), and class whenever any member is non-public (C.8)[9].

Member functions

A non-static member function is called on an object and receives an implicit pointer to it, this. Declaring a member function const makes this a pointer to const, so the function can be called on const objects and cannot modify the non-mutable members of the object it is called on[1 §class.mfct.non.static; 7]. A static member belongs to the class rather than any one object: a static data member has a single instance shared by all objects, and a static member function has no this[1 §class.static; 12].

Constructors

A constructor is a special member function, named after the class, that initialises an object; its job is to establish the class invariant so that every member function can rely on it (Core Guideline C.41, “A constructor should create a fully initialized object”)[9,7]. Members are initialised in the member initialiser list (: owner_{...}, balance_{...}) or by default member initialisers written at the point of declaration. Initialising rather than assigning in the body is preferred (C.49), and single-argument constructors should usually be explicit to prevent unintended implicit conversions (C.46)[9,13].

Destructors

A destructor, ~ClassName(), is invoked implicitly when an object's lifetime ends: at the end of its scope for automatic objects, at delete for dynamically allocated ones, and when the enclosing object is destroyed for members[1 §class.dtor; 14]. Destructors should release every resource the object owns (C.31), must not fail (C.36) and are implicitly noexcept unless declared otherwise[9; 1 §except.spec].

3Encapsulation: access control with public, private and protected

Encapsulation is the separation of a type's contractual interface from its implementation; it hides the representation so that the object's invariants can be enforced in one place[4]. The idea derives from Parnas's information hiding: each module should hide a design decision that is likely to change[15]. C++ provides three access specifiers[1 §class.access.general; 16]:

SpecifierMember is accessible from
publicAnywhere the name is visible.
protectedMembers and friends of the class, and members and friends of classes derived from it (in a derived class, only through objects of the derived type[1 §class.protected]).
privateMembers and friends of the class only.

Access control applies to names, not to objects: any member function of X may access the private members of any other X object, and a friend declaration grants a named function or class the same access as a member[1 §class.access.general, §class.friend; 7]. Access control is a compile-time check; it does not change object layout or prevent deliberate circumvention, and it is meant to prevent accidents rather than fraud[7].

The Core Guidelines advise minimising the exposure of members (C.9) and avoiding protected data (C.133): protected data is visible to an open-ended set of derived classes, so the base can no longer maintain its invariant on its own[9]. Protected member functions, by contrast, are a useful way to offer services to derived classes.

4Abstraction: exposing interfaces while hiding implementation

Abstraction denotes the essential characteristics of an object that distinguish it from all other kinds of object, from the viewpoint of its user[4]. Where encapsulation hides how, abstraction decides what is shown. Stroustrup describes two main tools: concrete types, whose representation is part of their definition but whose use is through a well-defined set of operations, and abstract types, which insulate users completely from the implementation[8]. Core Guideline C.3 says to “represent the distinction between an interface and an implementation using a class”, and C.4 says to make a function a member only if it needs direct access to the representation[9].

C++ adds a physical dimension to abstraction: header files are textually included into every client, so private members still appear in the header, and changing them forces clients to recompile. The pimpl (“pointer to implementation”) idiom moves the representation into a separately compiled class, giving a stable interface and ABI and shorter build times at the cost of an extra allocation and indirection[17,18]. The destructor and move operations are defined in the implementation file because std::unique_ptr needs the complete type at the point where its deleter is instantiated[17]. Abstract base classes, the other main abstraction tool, are covered in section 7.

5Inheritance: single, multiple, multilevel, hierarchical

A class may be derived from one or more base classes; each base becomes a base-class subobject of the derived object, and the derived class inherits the base's members[1 §class.derived.general; 19]. Public inheritance models an is-a relationship: everything true of the base must be true of the derived class[20]. The access specifier on the base controls how inherited members are exposed[1 §class.access.base]:

Base member: public B: protected B: private B
publicpublicprotectedprivate
protectedprotectedprotectedprivate
privatenot accessible in the derived class

Non-public inheritance expresses is-implemented-in-terms-of rather than is-a; composition is usually the clearer way to express that[20; 9 C.129].

The four shapes of a hierarchy

  • Single: a class has exactly one direct base (Car : Vehicle).
  • Multilevel: a chain of derivations (ElectricCar : Car : Vehicle). Construction runs from the most basic class downward and destruction runs in reverse[1 §class.base.init, §class.dtor].
  • Hierarchical: several classes derive from the same base (Truck and Bus from Vehicle).
  • Multiple: a class has more than one direct base[1 §class.mi]. If two bases themselves share a base, the derived object contains two copies of it unless the shared base is declared virtual; a virtual base is shared, and it is initialised by the most-derived class's constructor, before any non-virtual base[1 §class.mi, §class.base.init; 21]. This is the “diamond” shape.

The Core Guidelines recommend multiple inheritance mainly to represent multiple distinct interfaces (C.135), using virtual bases to avoid overly general base classes (C.137), and creating class hierarchies only for concepts with inherent hierarchical structure (C.120)[9]. Inheriting constructors with using Base::Base; avoids writing forwarding constructors by hand[1 §namespace.udecl; 19].

6Polymorphism: overloading, overriding and virtual functions

Cardelli and Wegner distinguish ad hoc polymorphism (overloading and coercion) from universal polymorphism (parametric polymorphism and inclusion, that is, subtype, polymorphism)[22]. C++ supports all of them. Overloading and templates are resolved at compile time (static polymorphism); virtual functions are resolved at run time (dynamic polymorphism)[7].

Function overloading (compile time)

Several functions in the same scope may share a name if their parameter lists differ. At each call the compiler performs overload resolution, ranking the implicit conversions each candidate needs and choosing the unique best match; if there is no unique best match the call is ambiguous[1 §over.match; 23]. Return types do not take part in overload resolution[1 §over.match].

Virtual functions and overriding (run time)

A member function declared virtual may be overridden in a derived class by a function with the same name and parameter list. A call through a pointer or reference to the base then invokes the final overrider for the object's dynamic type[1 §class.virtual; 24; 25]. The override specifier (C++11) makes the compiler reject a function that does not in fact override anything, which catches signature mismatches; final prevents further overriding of a function or derivation from a class[1 §class.virtual; 24]. Core Guideline C.128 says a virtual function should specify exactly one of virtual, override or final[9].

The standard does not prescribe how dispatch is implemented. In practice, compilers following the Itanium C++ ABI (GCC and Clang on most platforms) give each polymorphic object a hidden pointer to a per-class table of function pointers (the vtable), so a virtual call costs an indirect call and usually prevents inlining[26,7].

Overriding is not overloading: name hiding

A name declared in a derived class hides every base-class member with the same name, whatever their parameters, because name lookup stops at the first scope that contains the name and overload resolution happens afterwards[1 §class.member.lookup]. A using-declaration brings the base overloads into the derived scope (Core Guideline C.138)[9,27].

Two classic pitfalls

During construction and destruction, an object's dynamic type is the class whose constructor or destructor is running, so a virtual call made from a constructor does not reach the derived override[1 §class.cdtor; 27]; calling a pure virtual function this way is undefined behaviour[1 §class.abstract]. Core Guideline C.82 therefore says not to call virtual functions in constructors and destructors[9]. Passing a derived object by value as a base copies only the base subobject, which is called slicing; polymorphic types should be passed by reference or pointer, and a polymorphic class should suppress public copying (C.67)[9,7]. 7Abstract classes and interfaces: pure virtual functions

A virtual function declared with the pure-specifier = 0 is a pure virtual function. A class with at least one pure virtual function, declared or inherited without a final overrider, is an abstract class: no objects of it can be created except as base subobjects of a derived class[1 §class.abstract; 28]. A derived class that does not override every pure virtual function is itself abstract, as Widget is in Listing 6. A pure virtual function may nevertheless have a definition, and a pure virtual destructor must have one, because derived destructors always call it[1 §class.abstract, §class.dtor].

C++ has no interface keyword. By convention an interface is an abstract class with no data, only pure virtual functions and a virtual destructor (Core Guideline C.121: “If a base class is used as an interface, make it a pure abstract class”)[9,8]. Interfaces of this kind combine safely through multiple inheritance (C.135), and stable interfaces are preferred to deep class hierarchies (I.25)[9]. Making the interface's copy operations protected is one way to satisfy C.67 and prevent slicing through the interface type[9].

8Object lifetime: initialisation, copying, destruction

An object's lifetime begins when its storage is obtained and its initialisation is complete, and ends when its destructor call starts (or its storage is released or reused)[1 §basic.life; 29]. Using an object outside its lifetime is undefined behaviour.

Initialisation order

In a non-delegating constructor, virtual bases are initialised first (by the most-derived class only), then direct bases in declaration order, then non-static data members in the order they are declared in the class, regardless of the order in the member initialiser list; finally the constructor body runs. Destruction happens in exactly the reverse order[1 §class.base.init, §class.dtor]. Core Guideline C.47 says to declare and initialise members in the same order so the code reads as it executes[9]; both GCC (with -Wall) and Clang (by default) warn about a mismatch with -Wreorder.

The special member functions

Six member functions may be generated implicitly by the compiler: the default constructor, copy constructor, copy assignment operator, move constructor, move assignment operator and destructor[1 §special]. Whether each is generated depends on what the class declares. For example, the move constructor is implicitly declared only if the class has no user-declared copy constructor, copy assignment operator, move assignment operator or destructor[1 §class.copy.ctor]. Three practical rules follow[30,9]:

  • Rule of zero. If members manage their own resources (std::string, std::vector, std::unique_ptr), declare none of the special members and let the compiler generate correct ones (C.20).
  • Rule of three / five. If you must write a destructor, copy or move operation because the class owns a raw resource, define or =delete all five (C.21). Writing only some of them is the classic source of double deletion and resource leaks.
  • Move operations should be noexcept (C.66), so that containers such as std::vector can move rather than copy elements when they reallocate, and copy assignment must be safe for self-assignment (C.62)[9].

The copy-and-swap idiom used in Listing 7 builds the new state in a temporary and then swaps it in. It gives the strong exception guarantee and is safe for self-assignment, at the cost of an extra allocation compared with reusing existing storage[18,31].

Copy elision

Since C++17, initialising an object from a prvalue of the same type, such as returning Buffer{n} from a function, constructs the object directly in its final location; no copy or move constructor is called, and none needs to exist[32; 1 §class.copy.elision; 33]. That is why make(5) in Listing 7 prints only ctor(5) before the move assignment into c.

9Operator overloading: custom behaviour for operators

An operator function is a function named operator@. When at least one operand has class or enumeration type, the expression a @ b is resolved by overload resolution among member, non-member and built-in candidates[1 §over.oper, §over.match.oper; 34]. The rules are:

  • The operators ., .*, :: and ?: cannot be overloaded, and neither can the preprocessor operators # and ##[1 §over.oper.general].
  • Precedence, associativity and the number of operands are fixed by the grammar and cannot be changed, and new operator symbols cannot be invented[1 §over.oper.general; 7].
  • operator=, operator(), operator[] and operator-> must be non-static member functions (C++23 relaxes this for operator() and operator[], which may be static)[1 §over.assign, §over.call, §over.sub, §over.ref; 35].
  • Postfix ++/-- are distinguished from prefix by a dummy int parameter[1 §over.inc].

Guidelines

Operators should mimic conventional usage (C.160) and be used only for operations with their conventional meaning (C.167)[9,31]. Symmetric binary operators such as + and == should be non-members (C.161), so that implicit conversions apply equally to both operands; this is why 1 + a compiles in Listing 8[9]. Defining them as hidden friends, friends defined inside the class, keeps them out of ordinary lookup so they are found only by argument-dependent lookup when a Fraction is involved[1 §class.friend, §basic.lookup.argdep]. A common idiom implements + in terms of +=, which keeps the arithmetic in one place[18,34].

C++20 comparisons

C++20 introduced the three-way comparison operator <=> and rewritten candidates: given == and <=>, the compiler rewrites !=, <, >, <= and >= (including with the operands reversed) in terms of them, and both may be defaulted to compare members in declaration order[36; 1 §over.match.oper, §class.compare.default; 37]. Listing 8 defaults ==, which is correct because fractions are kept normalised, and writes <=> by hand because member-wise ordering would be wrong for fractions.

10Composition and aggregation: relationships between objects

UML distinguishes a plain association (objects that know about each other), aggregation (a whole–part association) and composition, a strong form of aggregation in which each part belongs to at most one whole at a time and the whole is responsible for the parts' lifetime[38]. In C++ the distinction is made concrete by ownership[7; 9 R.1]:

RelationshipTypical C++ representationLifetime
CompositionMember by value (Engine engine_;) or std::unique_ptr<T> Part created and destroyed with the whole
Aggregation / associationNon-owning reference, raw pointer, or std::span/view Part exists independently and must outlive the whole
Shared ownershipstd::shared_ptr<T> Part lives until its last owner is gone

The Core Guidelines state that a raw pointer (T*) is non-owning (R.3) and recommend unique_ptr or shared_ptr to represent ownership (R.20), preferring unique_ptr unless ownership really is shared (R.21)[9].

11Design principles: SOLID, separation of concerns, composition over inheritance

SOLID

The SOLID principles are five class-design principles collected by Robert C. Martin[39]; the acronym itself was suggested to him by Michael Feathers around 2004[40].

S — Single Responsibility Principle
“A class should have only one reason to change”[39]. Martin later restated it as: a module should be responsible to one, and only one, actor[40]. In Listing 10, persistence, notification and pricing are separate classes, so a change in one does not ripple into the others.
O — Open–Closed Principle
Software entities should be open for extension but closed for modification. The principle is due to Meyer[41]; Martin's formulation achieves it through abstraction and polymorphism[39]. A new DiscountPolicy can be added without editing OrderService.
L — Liskov Substitution Principle
Objects of a subtype must be usable wherever objects of the supertype are expected, without altering the desirable properties of the program[42,43]. Liskov and Wing make this precise in terms of preserved invariants, preconditions that may not be strengthened and postconditions that may not be weakened[43]. In C++ this is a semantic obligation on every public derivation; the compiler checks only signatures[20].
I — Interface Segregation Principle
“Clients should not be forced to depend on methods that they do not use”[39]. Prefer several small abstract classes to one broad one; compare the separate Drawable and Serializable interfaces in Listing 6.
D — Dependency Inversion Principle
High-level modules should not depend on low-level modules; both should depend on abstractions, and abstractions should not depend on details[39]. OrderService receives its collaborators through its constructor (dependency injection), so it can be tested with in-memory fakes.

Separation of concerns

Dijkstra introduced the phrase “separation of concerns” for the discipline of studying one aspect of a problem in isolation while knowing the others exist[44]. In class design it means each class, and each layer, addresses one concern, such as domain rules, persistence, presentation or transport, and communicates with the others through narrow interfaces. Parnas's criterion of decomposing a system by the design decisions it hides is the module-level form of the same idea[15].

Composition over inheritance

Gamma and colleagues' second principle of object-oriented design is “Favor object composition over class inheritance”: inheritance is “white-box” reuse that exposes a parent's implementation to its subclasses and is fixed at compile time, whereas composition is “black-box” reuse through interfaces that can be changed at run time[45]. The same advice appears in C++ guidance as “Prefer composition to inheritance”[18], and the Core Guidelines warn against using implementation inheritance where interface inheritance is meant (C.129)[9]. In Listing 10, pricing behaviour is composed into OrderService as a DiscountPolicy (the Strategy pattern[45]) rather than produced by subclassing OrderService, and it is replaced at run time.

12Looking ahead: C++23 additions

C++23 (ISO/IEC 14882:2024[3]) adds several features relevant to class design:

  • Explicit object parameters (“deducing this”). A member function may declare its object parameter explicitly, as this Self&& self. One template can then replace the const/non-const/&& overload set, and a base class can call into the derived class without the Curiously Recurring Template Pattern[46].
  • Multidimensional subscript. operator[] may take any number of arguments, so m[i, j] is valid[47].
  • static operator() for stateless function objects, which removes the unused this parameter[35].

13Summary checklist

  1. Give each class a clear invariant, establish it in the constructor, and keep data private[9 C.2, C.9, C.41].
  2. Mark single-argument constructors explicit and query functions const[9 C.46; 7].
  3. Prefer the rule of zero; if you own a raw resource, apply the rule of five and make moves noexcept[9 C.20, C.21, C.66].
  4. Give polymorphic base classes a public virtual destructor (or a protected non-virtual one)[9 C.35].
  5. Write override or final on every overrider, and never call virtuals from constructors or destructors[9 C.128, C.82].
  6. Handle polymorphic objects by reference or (smart) pointer to avoid slicing[9 C.67].
  7. Use pure abstract classes as interfaces, and keep them small[9 C.121, I.25; 39].
  8. Overload operators only with their conventional meaning; make symmetric ones non-members; use <=> in C++20[9 C.160, C.161; 37].
  9. Express ownership in types: values or unique_ptr for composition, non-owning pointers or references for aggregation[9 R.3, R.20].
  10. Favour composition over inheritance and depend on abstractions[45,39].
