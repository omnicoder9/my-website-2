Memory Management and Resource Ownership in C++

C++ series, part 3 · Targets C++17/C++20, with C++23 notes · 12 October 2026

C++ gives the programmer direct control over where objects live and when they die. That control is the source of the language's performance and predictability, and also of its most dangerous bugs. This article explains the model the standard actually defines (storage duration and object lifetime), the low-level tools (new and delete), the errors they invite, and the idioms that make those errors structurally unlikely: RAII, smart pointers, explicit ownership, correct copy and move semantics, and the Rules of Zero, Three and Five. It ends with how objects are laid out in memory.

Every listing is a complete program. Each was compiled with GCC 13.3 and Clang 18.1 using -std=c++20 -Wall -Wextra -pedantic (without warnings, except the deliberately broken Listing 4), and run under AddressSanitizer and UndefinedBehaviorSanitizer; the outputs shown are the real outputs on x86-64 Linux (glibc 2.39, libstdc++ 13). Layout numbers are platform-specific and are labelled as such. Normative statements are taken from the ISO C++20 standard [1] and cited by clause label through the public working draft [2], whose wording can differ in detail from C++20; changes made after C++20 that affect this article are noted where they arise.

1Stack and heap: automatic versus dynamic storage

Programmers talk about "the stack" and "the heap", but the C++ standard uses neither word for this purpose. It classifies objects by storage duration, the minimum potential lifetime of the storage that holds them, and defines four kinds: static, thread, automatic and dynamic [2 (basic.stc); 3]. "Stack" is the usual implementation of automatic storage, and "heap" (Stroustrup's preferred term is free store) is the usual home of dynamic storage [4,5].

Storage durationWhich objectsStorage lastsTypical implementation
AutomaticBlock-scope variables not declared static, thread_local or extern; function parametersUntil the enclosing block exitsCall stack
DynamicObjects created by a new-expression (and some implicitly created objects)Until explicitly deallocatedHeap / free store, via operator new
StaticNamespace-scope variables; variables declared static or externThe whole programData/BSS segments
ThreadVariables declared thread_localThe lifetime of the creating threadThread-local storage blocks

The first three columns follow the standard [2 (basic.stc); 3]; the last describes common practice, not a requirement.

Automatic storage is cheap: allocation and release amount to adjusting a stack pointer as functions are entered and left, and release is tied to scope, so it cannot be forgotten. Its limits are a fixed size decided when the program is compiled and a bounded total (on the Linux system used here, ulimit -s reports a default stack of 8192 KiB). Dynamic storage lets an object's size be chosen at run time and its lifetime be independent of any scope, at the cost of an allocator call and, crucially, an obligation to release it exactly once. The C++ Core Guidelines therefore advise: "Prefer scoped objects, don't heap-allocate unnecessarily" (R.5) [6].

Note in Listing 1 that the distinction is per object, not per variable name: heap is an automatic object holding the address of a dynamic one. Modern C++ code keeps almost all dynamic objects behind automatic "handles" like this, so that the handle's scope controls the dynamic object's lifetime (section 5).

2Object lifetime and storage duration

Storage duration describes the memory; lifetime describes the object in it, and the two are not the same. The lifetime of an object of type T begins when storage with the proper alignment and size for T has been obtained and its initialization is complete. It ends when the object is destroyed (for class types, when the destructor call starts) or when its storage is released or reused by another object [2 (basic.life); 7]. Storage can therefore exist without a live object in it (before a constructor finishes, after a destructor starts) and using an object outside its lifetime is undefined behaviour in most cases [2 (basic.life)].

Four rules account for nearly all lifetime reasoning in day-to-day code:

  1. Scope. An automatic object is destroyed when control leaves its block, by any route: falling off the end, return, break, or an exception [2 (stmt.jump); 4].
  2. Reverse order. Automatic objects in a block are destroyed in the reverse order of their construction; class members are destroyed in the reverse order of their declaration, after the destructor body runs [2 (stmt.jump); 2 (class.dtor)].
  3. Temporaries. A temporary object is destroyed as the last step in evaluating the full-expression that created it, roughly "at the semicolon" [2 (class.temporary)].
  4. Lifetime extension. Binding a temporary directly to a const T& or T&& extends the temporary's lifetime to that of the reference. There are exceptions; notably, a temporary bound to a reference parameter lives only until the end of the full-expression containing the call [2 (class.temporary)].

Since C++17, returning a prvalue such as Trace{n} from make is guaranteed not to create an intermediate temporary: the result object is initialised directly. This is why Listing 2 shows exactly one constructor call per make [8,9].

Static initialisation order. A block-scope static (like calls in Listing 1) is initialised the first time control passes through its declaration, and that initialisation is thread-safe since C++11 [2 (stmt.dcl); 3]. The relative order of dynamic initialisation of namespace-scope variables in different translation units is not specified, which is the source of the "static initialisation order fiasco" [10].

Implicit object creation (C++20) and std::start_lifetime_as (C++23)

Low-level code that obtains raw bytes (from std::malloc, a memory-mapped file or a network buffer) and then treats them as objects historically had no defined lifetime story. C++20 adopted P0593, under which certain operations, including std::malloc, operator new and starting the lifetime of an array of unsigned char or std::byte, implicitly create objects of implicit-lifetime types when that gives the program defined behaviour [2 (intro.object); 11]. C++23 added std::start_lifetime_as<T>(p) to do the same explicitly for existing bytes [12].

3Manual memory management: new, delete, arrays, allocation errors

A new-expression does two things: it calls an allocation function (operator new or operator new[]) to obtain raw storage, then initialises an object in it. If that initialisation throws, the matching deallocation function is called automatically, so a failing constructor does not leak [2 (expr.new); 13]. A delete-expression reverses the steps: it runs the destructor, then calls operator delete [2 (expr.delete); 14].

Rules that the compiler will not check

  • Match the forms. Memory from new must be released with delete; memory from new[] with delete[]. Mixing them, or calling delete on anything not obtained from the corresponding new, is undefined behaviour [2 (expr.delete); 5].
  • Exactly once. After delete p, the storage is gone and p holds an invalid pointer value; dereferencing it or deleting it again is undefined [2 (basic.stc); 2 (expr.delete)].
  • Null is safe. delete or delete[] on a null pointer does nothing harmful: no destructor runs [2 (expr.delete)].
  • Polymorphic deletion needs a virtual destructor. Deleting a derived object through a base-class pointer is undefined unless the base class has a virtual destructor [2 (expr.delete)]. Core Guideline C.35: "A base class destructor should be either public and virtual, or protected and non-virtual" [6].
  • Don't mix allocators. Never free() what new allocated or delete what malloc() allocated. malloc also runs no constructors; Core Guideline R.10 says "Avoid malloc() and free()" [5,6].

Allocation failure

When the global allocation function cannot satisfy a request, it first calls the installed new-handler (if any, see std::set_new_handler) and, if there is none or it gives up, throws std::bad_alloc [2 (new.delete.single); 15]. The new (std::nothrow) form returns a null pointer instead. An array bound that is invalid (for example negative, or so large the size computation overflows) throws std::bad_array_new_length, which derives from std::bad_alloc [2 (expr.new); 13]. In Listing 3 the request is well-formed but far larger than the address space, so the allocator throws.

Platform note. On systems that overcommit memory, such as Linux in its default configuration, a large but plausible allocation can "succeed" and the process can be killed later when the pages are first touched, so a bad_alloc handler is not a complete defence against memory exhaustion. Treat it as a way to fail cleanly on obviously impossible requests, not as a memory budget.

Alignment-aware allocation (C++17)

Before C++17, new ignored alignments stricter than the allocator's default. P0035 added overloads taking std::align_val_t, which a new-expression selects automatically for a type whose alignment exceeds __STDCPP_DEFAULT_NEW_ALIGNMENT__ [15,16]. Listing 11 shows this working.

The modern advice is that application code should almost never write new or delete at all. Core Guideline R.11 reads "Avoid calling new and delete explicitly", and ES.60 "Avoid new and delete outside resource management functions" [6]. The reasons are in the next section.

4Memory errors: leaks, dangling pointers, double frees, use-after-free

All four classic memory errors have the same root cause: the code that uses a pointer has no reliable knowledge of whether the object it points to is still alive, or of who is responsible for ending its life. Except for leaks, each results in undefined behaviour, meaning the standard places no requirements on what happens [2 (defns.undefined)]; the program may appear to work, crash, or corrupt data silently. Core Guideline ES.65 states the rule simply: "Don't dereference an invalid pointer" [6].

The realloc case deserves attention because no delete appears in the source. push_back on a full vector allocates a larger buffer, moves the elements and frees the old one, invalidating all pointers, references and iterators into it [2 (vector.modifiers)]. Every container documents its own invalidation rules, and views such as std::string_view and std::span do not own their data, so they dangle as soon as the data's owner dies [19].

Tooling. Sanitizers find errors on the paths a test actually executes, so they complement, not replace, the structural fixes below. Compiler warnings help too: GCC warns by default when a function returns the address of a local variable (-Wreturn-local-addr), and its -Wall set includes -Wdangling-pointer [20], which flagged the scope case of Listing 4 in an unoptimised GCC 13 build ("using dangling pointer 'p' to 'x'"). Neither catches the other four cases.

The structural cure is to make ownership explicit in the type system, so that exactly one well-defined thing is responsible for releasing each resource, and that release happens automatically. That is RAII.

5RAII: Resource Acquisition Is Initialization

RAII binds the life cycle of a resource that must be acquired before use (heap memory, a file, a socket, a mutex lock, a database transaction) to the lifetime of an object. The constructor acquires the resource and establishes the class invariant, or throws if it cannot; the destructor releases it and never throws [4,21]. Because C++ guarantees that destructors of fully constructed automatic objects run when their scope is left, including during stack unwinding after an exception, the release cannot be skipped [2 (except.ctor)]. The technique is also called Scope-Bound Resource Management (SBRM) [21]. Stroustrup describes it in The Design and Evolution of C++ as the basis for exception-safe resource management [22], and Core Guideline R.1 makes it the first rule of resource management: "Manage resources automatically using resource handles and RAII" [6].

Three properties of Listing 5 generalise:

  • "file closed" is printed before "caught". The destructor ran during unwinding, before the handler. No try/finally is needed, and none exists in C++.
  • The constructor throws rather than producing a half-valid object. If the constructor of File throws, no File object exists and its destructor is not called [2 (except.ctor)], so the destructor may assume f_ is valid.
  • Copying is deleted. A copied File would close the same FILE* twice, a double free in another guise. Section 8 shows how to give such a type move semantics instead.

The standard library is built on RAII: containers and std::string own their buffers; std::lock_guard, std::scoped_lock and std::unique_lock own mutex locks (Core Guideline CP.20: "Use RAII, never plain lock()/unlock()"); std::fstream owns a file; std::jthread joins in its destructor; and the smart pointers own dynamic objects [6,23].

6Smart pointers: std::unique_ptr, std::shared_ptr, std::weak_ptr

The <memory> header provides RAII handles for dynamic objects. Core Guideline R.20: "Use unique_ptr or shared_ptr to represent ownership"; R.21: "Prefer unique_ptr over shared_ptr unless you need to share ownership" [6].

std::unique_ptr: exclusive ownership

A unique_ptr<T, D> owns at most one object and destroys it with its deleter D (by default delete, or delete[] for unique_ptr<T[]>) when the unique_ptr is destroyed or reset. It is move-only: the copy constructor and copy assignment are deleted, so ownership can be transferred only by an explicit std::move and is never accidentally duplicated [2 (unique.ptr); 24]. If the stored pointer is null, the deleter is not called [2 (unique.ptr.single.dtor)]. Create one with std::make_unique (C++14), which never exposes a raw owning pointer (Core Guideline R.23) [6,24].

With a stateless deleter, unique_ptr has no space overhead in mainstream implementations, as the last line of Listing 6 confirms for libstdc++, though the standard does not require it [25]. It is the right default for a dynamically allocated object with a single owner, for polymorphic objects held in containers, and, with a custom deleter, for C resources such as FILE*. C++20 added std::make_unique_for_overwrite, which default-initialises (leaves trivially constructible elements uninitialised) when the buffer will be overwritten anyway [24]. C++23 added std::out_ptr and std::inout_ptr for passing a smart pointer to a C API that returns a resource through a T** parameter [26].

std::shared_ptr: shared ownership

A shared_ptr shares ownership of an object among all its copies; "the last remaining owner of the pointer is responsible for destroying the object" [2 (util.smartptr.shared.general)]. Implementations keep a separately allocated control block holding a strong count (owners), a weak count (observers) and the deleter. std::make_shared allocates the object and the control block together; the standard says implementations should perform no more than one allocation (Core Guideline R.22) [2 (util.smartptr.shared.create); 6].

The reference-count updates are thread-safe: different shared_ptr objects that share ownership can be copied and destroyed concurrently without a data race [2 (util.smartptr.shared.general)]. That does not make the pointed-to object, or a single shared_ptr object written by several threads, thread-safe; for the latter C++20 provides std::atomic<std::shared_ptr<T>> [27]. Shared ownership also costs more than unique ownership: a second allocation (unless make_shared is used), atomic increments on every copy, and a lifetime that is harder to reason about [25].

std::weak_ptr: observing without owning

A weak_ptr refers to an object managed by shared_ptr without contributing to its strong count. To use the object, call lock(), which atomically returns a shared_ptr that keeps the object alive, or an empty one if it has already been destroyed; expired() reports the latter [2 (util.smartptr.weak); 28]. Its main jobs are caches and observers that must not prolong lifetime, and breaking reference cycles: two objects that hold shared_ptrs to each other keep each other's count above zero forever, which is a leak (Core Guideline R.24: "Use std::weak_ptr to break cycles of shared_ptrs") [6,28].

In Listing 7, the Leaky objects are never destroyed (no ~Leaky line appears; LeakSanitizer reports them if the program is built with ASan), whereas the Node chain is cleaned up because its back link is a weak_ptr. A class that needs to hand out shared_ptrs to itself must inherit from std::enable_shared_from_this and call shared_from_this(); creating a second shared_ptr from this directly would start a second, independent count and lead to a double delete [2 (util.smartptr.enab); 27].

7Ownership semantics: moving, sharing, borrowing

Ownership is a design property: the owner of a resource is the entity responsible for releasing it. Modern C++ expresses ownership through types, so that a function signature tells the reader, and the compiler, what happens to the resource [6,23]. Three relationships cover almost every case.

  • Unique ownership, transferred by move. Exactly one owner at a time; ownership passes explicitly with std::move. Types: std::unique_ptr, containers, std::string, std::fstream, and any well-written resource handle.
  • Shared ownership. Several owners; the last one releases. Type: std::shared_ptr. Appropriate only when lifetime genuinely cannot be tied to a single owner.
  • Borrowing. Using a resource without owning it, for a period during which an owner is known to keep it alive. Types: T&, const T&, T*, std::string_view, std::span<T>. Core Guideline R.3: "A raw pointer (a T*) is non-owning"; I.11: "Never transfer ownership by a raw pointer (T*) or reference (T&)" [6].

Choosing parameter types

The Core Guidelines (R.30 to R.36) and Herb Sutter's guidance on smart pointer parameters give a consistent convention [6,29]. Most functions merely use an object, so most functions should borrow; F.7 says "For general use, take T* or T& arguments rather than smart pointers" [6].

Borrowing is a promise the compiler does not check. A reference or view is only valid while its owner keeps the object alive. 8Copy and move operations

Whenever an object is initialised from, or assigned from, another object of the same type, one of four special member functions runs [2 (class.copy.ctor); 2 (class.copy.assign)]:

OperationSignatureRuns for
Copy constructorT(const T&)T b = a;, pass/return by value from an lvalue
Move constructorT(T&&) noexceptT b = std::move(a);, initialising from an xvalue
Copy assignmentT& operator=(const T&)b = a;
Move assignmentT& operator=(T&&) noexceptb = std::move(a);

Together with the destructor these are the five operations that determine how a type manages a resource [30].

Copying must produce an independent object with equal value: for a resource-owning class that usually means a deep copy. Moving, introduced in C++11, transfers the resource from a source that the caller has declared it no longer needs (std::move is only a cast to an rvalue reference; it moves nothing by itself) [25,31]. The moved-from object must remain valid, meaning it can still be destroyed and assigned to; for standard library types, unless otherwise specified, it is left in "a valid but unspecified state" [2 (lib.types.movedfrom)]. Core Guideline C.64: "A move operation should move and leave its source in a valid state" [6].

Points of technique in Listing 9

  • Copy-and-swap. Copy assignment copies into a temporary first and then swaps. If the copy throws, *this is untouched (the strong exception guarantee), and self-assignment is handled correctly without a special case (Core Guideline C.62: "Make copy assignment safe for self-assignment") [4,6].
  • std::exchange reads the source member and resets it in one expression, leaving the source empty but valid.
  • noexcept moves. Core Guideline C.66: "Make move operations noexcept" [6]. This is not cosmetic. When a std::vector grows, it must preserve the strong exception guarantee of push_back, so it moves elements into the new buffer only if the move constructor cannot throw (or the type cannot be copied); otherwise it copies them [2 (vector.modifiers); 32]. The last two lines of output show the effect: seven moves for Buffer, but seven deep copies for RiskyMove, whose move constructor lacks noexcept [25].

Copy elision

The compiler can often avoid copies and moves altogether. Since C++17, initialising an object from a prvalue of the same type (including return T{...};) constructs it directly in its final location: no copy or move constructor is called and none needs to exist [8,9]. Returning a named local variable allows, but does not require, the elision known as NRVO; if it is not elided, the variable is moved rather than copied [9]. Writing return std::move(local); is therefore usually counter-productive, because it inhibits NRVO [25].

9The Rules of Zero, Three and Five

The compiler generates special member functions when they are not declared, but the rules for when it does so are subtle, and declaring one can suppress others [2 (class.copy.ctor); 2 (class.copy.assign); 30]:

  • An implicit move constructor or move assignment operator is declared only if the class has no user-declared copy constructor, copy assignment operator, move operation of the other kind, or destructor [2 (class.copy.ctor); 2 (class.copy.assign)].
  • If the class declares a move constructor or move assignment operator, the implicit copy constructor and copy assignment are defined as deleted [2 (class.copy.ctor); 2 (class.copy.assign)].
  • Otherwise the copy operations are still generated, but generating them for a class that has a user-declared destructor (or the other copy operation) is deprecated [2 (class.copy.ctor)].

Three rules of thumb follow from this [30].

Rule of Three (C++98)

If a class needs a user-defined destructor, copy constructor or copy assignment operator, it almost certainly needs all three. A destructor that releases a resource implies the implicitly generated memberwise copy would duplicate the handle and cause a double release [4,30].

Rule of Five (C++11)

Because a user-declared destructor or copy operation suppresses the implicit moves, a resource-owning class that should be movable must declare all five: destructor, copy constructor, copy assignment, move constructor and move assignment [30]. Core Guideline C.21: "If you define or =delete any copy, move, or destructor function, define or =delete them all" [6]. Buffer in Listing 9 is a Rule-of-Five class. Writing = default or = delete counts as declaring, and makes the intent explicit.

Rule of Zero

Classes that are not themselves resource managers should declare none of the five, and let members such as std::string, std::vector and std::unique_ptr handle resources; the compiler-generated memberwise operations then do the right thing (Core Guideline C.20: "If you can avoid defining default operations, do") [6,30]. This confines the hard code to a small number of resource-handle classes, most of which the standard library already provides.

Legacy in Listing 10 shows why the rules matter. Adding an empty destructor (perhaps for logging or a breakpoint) silently removed its move operations; std::move(l1) still compiles, because an rvalue can bind to the copy constructor's const Legacy& parameter, but it now performs a full copy, and the type is no longer noexcept-movable, so containers of it copy on reallocation. The static_asserts document and enforce the intended properties at compile time [2 (class.copy.ctor); 30].

10Alignment and object representation: padding, layout, alignment requirements

Object representation

An object of type T occupies sizeof(T) bytes. The standard calls that sequence of unsigned char objects the object representation; the bits that actually determine the value form the value representation, and any others are padding bits [2 (basic.types.general); 33]. Bytes of any object may be examined through char, unsigned char or std::byte glvalues; accessing an object through an unrelated type otherwise is undefined behaviour (the "strict aliasing" rule) [2 (basic.lval)]. C++20's std::bit_cast copies the object representation of one trivially copyable type into another of the same size, and is the safe replacement for type-punning through reinterpret_cast or unions [2 (bit.cast)].

Alignment requirements

Every object type has an alignment requirement: "an implementation-defined integer value representing the number of bytes between successive addresses at which a given object can be allocated". Every alignment is a power of two. Alignments up to alignof(std::max_align_t) are fundamental and supported everywhere; larger ones are extended and may not be supported in all contexts [2 (basic.align)]. alignof(T) yields a type's requirement and the alignas specifier strengthens it; an alignas that would make the alignment weaker than the type's natural alignment is ill-formed [2 (dcl.align); 34].

Padding and layout

To give every member its required alignment, compilers insert unnamed padding between members and at the end of a class. Non-static data members are allocated so that later members have higher addresses [2 (class.mem.general)]; before C++23 that was guaranteed only among members with the same access control, and P1847 made declaration order mandatory for all [35]. Tail padding makes sizeof a multiple of the alignment, so that every element of an array is correctly aligned [33]. The macro offsetof gives a member's byte offset; it is only conditionally supported for types that are not standard-layout [2 (support.types.layout)].

What Listing 11 demonstrates:

  • Member order matters. The same three members occupy 12 or 8 bytes depending on declaration order. The compiler may not reorder them for you [2 (class.mem.general)].
  • Padding bytes are not part of the value. std::has_unique_object_representations_v<Padded> is false, so hashing or comparing Padded objects byte-by-byte (for example with memcmp) is unreliable; TwoInts has no padding and is true [36].
  • Over-aligned types work on the heap. CacheLine requires 64-byte alignment, more than __STDCPP_DEFAULT_NEW_ALIGNMENT__ (16 here), and make_unique returns correctly aligned storage because C++17 new uses the align_val_t overloads [15,16]. Aligning independently written data to separate cache lines avoids "false sharing" between threads; C++17 provides std::hardware_destructive_interference_size as a portable hint for the distance needed [37].
  • Empty types. A complete object, even of an empty class, has non-zero size, so sizeof(Empty) is 1 and an Empty member costs 4 bytes here after padding. An empty base class may occupy no space (the empty base optimisation), and C++20's [[no_unique_address]] lets an empty member do the same [2 (intro.object); 2 (dcl.attr.nouniqueaddr); 38]. This is how standard containers and unique_ptr store stateless allocators and deleters for free.
  • Byte order is a property of the platform. std::bit_cast exposes the bytes of 0x01020304 as 4 3 2 1 on a little-endian machine; C++20's std::endian reports it portably [2 (bit.cast); 39].

Avoid packing pragmas for in-memory data. Compiler extensions such as #pragma pack or __attribute__((packed)) remove padding but produce misaligned members, which are slower on some architectures and can fault on others; references to such members are not portable. Reorder members, or serialise explicitly, instead. (These extensions are outside the standard [40].)

11Summary

  1. Think in terms of storage duration and lifetime, not "stack" and "heap". Prefer automatic objects; allocate dynamically only when size or lifetime require it (R.5).
  2. Every resource needs exactly one clearly identified owner, and that owner should be an object whose destructor releases it (RAII, R.1).
  3. Do not write new and delete in application code (R.11). Use std::make_unique by default and std::make_shared when ownership is genuinely shared; break cycles with std::weak_ptr.
  4. Express ownership in function signatures: borrow with references, pointers and views; transfer with unique_ptr by value; share with shared_ptr by value.
  5. Follow the Rule of Zero; when a class must manage a resource directly, follow the Rule of Five and make moves noexcept.
  6. Test with AddressSanitizer and treat compiler warnings as errors; both find what the type system cannot.
  7. Know your layout: order members by alignment, never compare padding, use alignas and std::bit_cast rather than casts and pragmas.
