1. A unified framework for groups, sequences, sets, queues, and mappings

The Java Collections Framework is a set of interfaces, implementations, algorithms, wrappers, and traversal abstractions. Correct selection begins with semantic requirements—duplicates, encounter order, key equality, priority, range queries, concurrency, mutation, and access pattern—not with memorizing a favorite concrete class.

Interface contract

Defines operations, equality semantics, optional mutation, ordering, and element restrictions.

Implementation

Chooses array, linked node, hash table, tree, heap, or concurrent representation.

Algorithm

Operates polymorphically through interfaces: sorting, searching, reversing, rotating, copying, and aggregation.

View

Presents backed or reversed/subrange/key/value/entry access without necessarily copying storage.

The framework is a unified architecture for representing and manipulating collections independently of representation details. It includes more than a dozen interfaces, general-purpose and special-purpose implementations, and polymorphic algorithms.[1]

Program to the narrowest useful interface. A parameter that only iterates should accept Iterable or Collection; indexed algorithms need List; uniqueness needs Set; key lookup needs Map; double-ended scheduling needs Deque.

2. Core interface hierarchy

Iterable<E> └── Collection<E> ├── SequencedCollection<E> │ ├── List<E> │ └── Deque<E> ├── Set<E> │ └── SequencedSet<E> │ └── SortedSet<E> │ └── NavigableSet<E> └── Queue<E> └── Deque<E> Map<K,V> (not a Collection) ├── SequencedMap<K,V> ├── SortedMap<K,V> │ └── NavigableMap<K,V> └── ConcurrentMap<K,V>

Collection is the root of the element-container hierarchy. Map belongs to the framework but does not extend Collection because it models key–value mappings rather than a group of homogeneous elements.[2][3]

Interfaces describe behavior

  • List: ordered sequence with positional access and duplicates.
  • Set: no duplicate elements under its equality/order semantics.
  • Queue: elements held before processing, usually head-oriented.
  • Deque: insertion/removal at both ends.
  • Map: unique keys mapped to values.

3. Generics, PECS, and type-safe collection APIs

List<String> names =
    new ArrayList<>();

names.add("Ada");

// Compile-time type safety:
String first =
    names.getFirst();

Producer extends, consumer super

static <T> void copy(
        Collection<? extends T> source,
        Collection<? super T> destination) {

    destination.addAll(source);
}

Invariant generic types

List<Integer> integers =
    List.of(1, 2, 3);

// Not legal:
// List<Number> numbers = integers;

List<? extends Number> numbers =
    integers;

Wildcard capture

Use ? extends T when reading values as T, ? super T when inserting values of type T, and an exact type when both reading and writing are required.

4. Collection<E>

Root interface Collection represents a group of elements. Some implementations allow duplicates, some do not; some define encounter order, some do not. The JDK provides implementations of more specific subinterfaces rather than a direct general-purpose Collection implementation.[2]

static <T> boolean replaceAll(
        Collection<T> target,
        Collection<? extends T> values) {

    boolean changed =
        !target.equals(values);

    target.clear();
    target.addAll(values);

    return changed;
}

Optional operations

Mutating methods such as add, remove, and clear are optional. Unsupported implementations throw UnsupportedOperationException.

General operations

boolean contains =
    collection.contains(value);

collection.removeIf(
    this::expired);

Object[] objects =
    collection.toArray();

String[] strings =
    collection.toArray(
        String[]::new);

5. List<E>

Sequence A list is an ordered collection with positional access. It typically permits duplicates and can allow multiple null elements depending on implementation. Lists are sequenced collections and expose first, last, and reversed views in Java 21 and later.[4]

List<String> steps =
    new ArrayList<>();

steps.add("compile");
steps.add("test");
steps.add(1, "lint");

String first =
    steps.getFirst();

String last =
    steps.getLast();

List<String> reversed =
    steps.reversed();

Indexed versus iterator access

for (int index = 0;
        index < list.size();
        index++) {

    process(
        list.get(index));
}

Indexed traversal is efficient for random-access lists such as ArrayList but can become quadratic for sequential-access lists such as LinkedList. Enhanced for or iterators are representation-neutral.

6. Set<E>

Uniqueness A set contains no duplicate elements: it contains no two elements that are equal under the set's equality semantics. General-purpose sets define equality by membership, independent of encounter order.[5]

Set<String> permissions =
    new HashSet<>();

boolean added =
    permissions.add(
        "READ");

boolean duplicate =
    permissions.add(
        "READ");

assert added;
assert !duplicate;

Set algebra

Set<String> intersection =
    new HashSet<>(left);

intersection.retainAll(right);

Set<String> union =
    new HashSet<>(left);

union.addAll(right);

Set<String> difference =
    new HashSet<>(left);

difference.removeAll(right);

7. Queue<E>

Processing order A queue holds elements before processing. Each insertion, removal, and examination operation has an exception-throwing form and a special-value form.[6]

PurposeThrows on failureSpecial value
Insertadd(e)offer(e)
Remove headremove()poll()
Examine headelement()peek()
Queue<Task> queue =
    new ArrayDeque<>();

queue.offer(task);

Task next =
    queue.poll();

if (next != null) {
    execute(next);
}

Queue order is implementation-specific: FIFO queues, priority queues, delay queues, and synchronous handoff queues implement different processing policies.

8. Deque<E>

Double ended A deque supports insertion, removal, and examination at both ends. It can represent FIFO queues and LIFO stacks. Deque implementations are generally preferable to legacy Stack for stack behavior.[7]

Deque<String> history =
    new ArrayDeque<>();

history.addLast("page-1");
history.addLast("page-2");

String current =
    history.removeLast();

String previous =
    history.peekLast();

Stack vocabulary

Deque<Frame> stack =
    new ArrayDeque<>();

stack.push(frame);

Frame top =
    stack.peek();

Frame removed =
    stack.pop();

Most deque implementations prohibit null because poll and peek use null to indicate emptiness.

9. Map<K,V>

Key–value mapping A map associates each unique key with at most one value. It exposes backed views of keys, values, and entries. The map's encounter order is the order of iteration through these views and is implementation-specific unless guaranteed.[3]

Map<CustomerId, Customer> byId =
    new HashMap<>();

Customer previous =
    byId.put(
        customer.id(),
        customer);

Customer found =
    byId.get(
        customerId);

Customer required =
    byId.getOrDefault(
        customerId,
        anonymousCustomer);

Entry iteration

for (Map.Entry<CustomerId, Customer>
        entry : byId.entrySet()) {

    process(
        entry.getKey(),
        entry.getValue());
}

Mutable keys are dangerous

Changing a key in a way that affects equals, hashCode, or ordering while it is stored can make the mapping unreachable or violate tree invariants.

10. Sequenced collections, sets, and maps

Encounter order Java 21 introduced SequencedCollection, SequencedSet, and SequencedMap to model collections with a defined encounter order and uniform first, last, and reversed operations.[8]

SequencedCollection<String> sequence =
    new ArrayList<>();

sequence.addFirst("first");
sequence.addLast("last");

String first =
    sequence.getFirst();

SequencedCollection<String> reverseView =
    sequence.reversed();

Reversed views are backed

List<String> list =
    new ArrayList<>(
        List.of("a", "b", "c"));

List<String> reversed =
    list.reversed();

reversed.removeFirst();
// Removes "c" from list.

A reversed view changes encounter-order presentation and writes through when mutation is supported; it is not necessarily a copy.

11. Backed views, copies, and snapshots

Many collection-returning operations create views rather than independent storage. Changes to the backing collection are visible in the view, and permitted changes through the view write through to the backing collection.[2]

Sublist view

List<String> values =
    new ArrayList<>(
        List.of("a", "b", "c", "d"));

List<String> middle =
    values.subList(1, 3);

middle.clear();

assert values.equals(
    List.of("a", "d"));

Map views

Set<CustomerId> keys =
    map.keySet();

Collection<Customer> values =
    map.values();

Set<Map.Entry<CustomerId, Customer>>
    entries =
        map.entrySet();

Snapshot copy

List<String> snapshot =
    List.copyOf(values);
Do not confuse “unmodifiable” with “immutable snapshot.” An unmodifiable view can still reflect mutations to its backing collection; a copy can still contain mutable elements.

12. Equality, hashing, and membership

Collection operations are generally specified in terms of equals, while hash-based implementations also use hashCode to locate candidate buckets. Equal objects must have equal hash codes.[2][9]

public record CustomerId(
    String value) {

    public CustomerId {
        value =
            Objects.requireNonNull(value)
                .strip();

        if (value.isEmpty()) {
            throw new IllegalArgumentException();
        }
    }
}

List equality

Lists compare equal when they contain equal elements in the same order.

Set equality

Sets compare equal when they contain the same members, regardless of encounter order.

Map equality

Maps compare equal when they contain the same key–value mappings.

14. ArrayList

Resizable array ArrayList implements List, RandomAccess, and SequencedCollection. Positional access is constant time; append is amortized constant time; insertion/removal away from the end shifts later elements. It permits nulls and is not synchronized.[10]

List<Order> orders =
    new ArrayList<>(
        expectedOrders);

orders.add(order);

Order first =
    orders.getFirst();

Order tenth =
    orders.get(9);

Pre-sizing

ArrayList<Record> records =
    new ArrayList<>(
        expectedCount);

records.ensureCapacity(
    expectedCount);

Remove by index versus value

List<Integer> values =
    new ArrayList<>(
        List.of(10, 20, 30));

values.remove(1);
// Removes element at index 1.

values.remove(
    Integer.valueOf(30));
// Removes the value 30.

Default choice for lists

ArrayList is usually the best general-purpose list because it has low per-element overhead, cache-friendly contiguous storage, efficient iteration, and fast indexed access.

15. LinkedList

Doubly linked nodes LinkedList implements both List and Deque. Indexed operations traverse from the nearer end, while insertion/removal through a known iterator position or at either end is constant time. It permits nulls and is not synchronized.[11]

LinkedList<Task> tasks =
    new LinkedList<>();

tasks.addFirst(
    urgent);

tasks.addLast(
    normal);

Task next =
    tasks.removeFirst();

Quadratic indexed traversal

// Poor for LinkedList:
for (int index = 0;
        index < list.size();
        index++) {

    process(
        list.get(index));
}

Use an iterator

for (Task task : tasks) {
    process(task);
}

Linked nodes add object and pointer overhead and generally have poor cache locality. For queues and stacks, ArrayDeque is usually preferable; use LinkedList when its combined list/deque contract or iterator-position mutation is specifically useful.

16. Vector

Legacy synchronized list Vector is a growable-array list whose methods are synchronized. It predates the Collections Framework and also exposes legacy capacity and Enumeration APIs.[12]

Vector<String> vector =
    new Vector<>();

vector.add("legacy");

Enumeration<String> elements =
    vector.elements();

Method synchronization is not workflow atomicity

if (!vector.isEmpty()) {
    String last =
        vector.remove(
            vector.size() - 1);
}

Another thread can change the vector between calls. Compound operations still require external synchronization.

Modern alternatives

  • ArrayList for thread-confined or externally synchronized use.
  • Collections.synchronizedList for one-lock wrapper semantics.
  • CopyOnWriteArrayList for small read-mostly shared lists.
  • Concurrent queues/deques for producer–consumer workflows.

17. HashSet

Hash set HashSet is backed by a HashMap, permits one null element, and makes no encounter-order guarantee. Basic operations are expected constant time when hash codes disperse elements well.[13]

Set<CustomerId> seen =
    new HashSet<>();

if (!seen.add(
        customer.id())) {

    throw new DuplicateCustomer(
        customer.id());
}

Iteration cost includes capacity

Iteration cost is proportional to the set's size plus backing-table capacity. Excessive initial capacity or a very low load factor can make traversal unnecessarily expensive.

Mutable element hazard

Set<MutableKey> set =
    new HashSet<>();

MutableKey key =
    new MutableKey("a");

set.add(key);

key.setValue("b");

// Lookup behavior is now unspecified
// relative to the changed hash/equality.

18. LinkedHashSet

Insertion order LinkedHashSet combines hash-based membership with a well-defined encounter order, normally insertion order. Re-adding an existing element does not change its position.[14]

Set<String> uniqueInOrder =
    new LinkedHashSet<>(
        List.of(
            "beta",
            "alpha",
            "beta",
            "gamma"));

assert uniqueInOrder.equals(
    Set.of(
        "alpha",
        "beta",
        "gamma"));

assert List.copyOf(
        uniqueInOrder)
    .equals(
        List.of(
            "beta",
            "alpha",
            "gamma"));

First, last, and reverse

String first =
    uniqueInOrder.getFirst();

String last =
    uniqueInOrder.getLast();

SequencedSet<String> reversed =
    uniqueInOrder.reversed();

Use it for stable deduplication, reproducible output, and deterministic iteration where sorted order is unnecessary.

19. TreeSet

Sorted set TreeSet is a NavigableSet backed by TreeMap. Elements use natural ordering or a constructor-supplied comparator. Basic add, remove, and contains operations have guaranteed logarithmic cost.[15]

NavigableSet<Instant> deadlines =
    new TreeSet<>();

deadlines.add(
    firstDeadline);

deadlines.add(
    secondDeadline);

Instant next =
    deadlines.ceiling(
        clock.instant());

Range views

NavigableSet<Integer> scores =
    new TreeSet<>(
        List.of(
            10, 20, 30, 40, 50));

NavigableSet<Integer> middle =
    scores.subSet(
        20,
        true,
        40,
        false);

Comparator equality

Tree sets treat elements as duplicates when comparison returns zero, even if equals returns false. The ordering should be consistent with equals to preserve the general Set contract.

20. PriorityQueue

Binary heap PriorityQueue is an unbounded priority heap ordered by natural ordering or a comparator. Its head is a least element; ties are resolved arbitrarily. It prohibits nulls.[16]

PriorityQueue<Job> jobs =
    new PriorityQueue<>(
        Comparator.comparing(
                Job::priority)
            .thenComparing(
                Job::submittedAt));

jobs.offer(job);

Job next =
    jobs.poll();

Iteration is not priority order

// Does not guarantee sorted traversal:
for (Job job : jobs) {
    process(job);
}

Drain in priority order

while (!jobs.isEmpty()) {
    process(
        jobs.remove());
}

Offer and poll are logarithmic, while peek is constant time. Removing or locating an arbitrary object is linear.

21. HashMap

Hash table HashMap permits one null key and null values, makes no encounter-order guarantee, and provides expected constant-time get and put under a well-distributed hash function. It is not synchronized.[17]

Map<CustomerId, Customer> customers =
    new HashMap<>();

customers.put(
    customer.id(),
    customer);

Customer value =
    customers.get(
        customerId);

Presence versus null value

Customer value =
    customers.get(id);

if (value == null
        && !customers.containsKey(id)) {
    // No mapping.
}

Iteration and capacity

Iteration over entries is proportional to size plus table capacity. Oversizing can degrade traversal even when lookup remains fast.

22. LinkedHashMap

Sequenced hash map LinkedHashMap maintains a doubly linked list through entries, providing a defined encounter order. It can use insertion order or access order.[18]

Insertion order

SequencedMap<String, Integer> counts =
    new LinkedHashMap<>();

counts.put("first", 1);
counts.put("second", 2);

Map.Entry<String, Integer> first =
    counts.firstEntry();

Access-order LRU cache

public final class LruCache<K, V>
        extends LinkedHashMap<K, V> {

    private final int maximumSize;

    public LruCache(
            int maximumSize) {

        super(
            16,
            0.75f,
            true);

        this.maximumSize =
            maximumSize;
    }

    @Override
    protected boolean
    removeEldestEntry(
            Map.Entry<K, V> eldest) {

        return size()
            > maximumSize;
    }
}

This simple cache is not thread-safe and does not provide expiration, weight limits, loading coordination, or production cache metrics.

23. TreeMap

Navigable map TreeMap is a red-black-tree-based NavigableMap ordered by natural key order or a comparator. It guarantees logarithmic containsKey, get, put, and remove operations.[19]

NavigableMap<Instant, Event> events =
    new TreeMap<>();

events.put(
    event.occurredAt(),
    event);

Map.Entry<Instant, Event> next =
    events.ceilingEntry(
        clock.instant());

Range queries

NavigableMap<Instant, Event> window =
    events.subMap(
        startInclusive,
        true,
        endExclusive,
        false);

Comparator determines key identity

Keys compare as the same mapping when the comparator returns zero. Comparator consistency with equals is strongly recommended.

24. ConcurrentHashMap

Concurrent map ConcurrentHashMap supports fully concurrent retrievals and high expected concurrency for updates. Retrievals generally do not block, and neither keys nor values may be null.[20]

ConcurrentHashMap<String, LongAdder>
    counts =
        new ConcurrentHashMap<>();

counts.computeIfAbsent(
        route,
        ignored ->
            new LongAdder())
    .increment();

Atomic per-key update

sessions.compute(
    sessionId,
    (id, current) -> {
        if (current == null
                || current.expired()) {
            return createSession(id);
        }

        return current.renew();
    });

Weakly consistent traversal

counts.forEach(
    10_000,
    (route, counter) ->
        publish(
            route,
            counter.sum()));

Concurrent traversals may reflect some updates that occur during traversal but do not throw ConcurrentModificationException. Aggregate methods such as size can be transient under concurrent mutation.[21]

25. Capacity, load factor, and growth

Array-backed structures

ArrayList and Vector maintain capacity beyond logical size. Growth allocates and copies a larger backing array. Pre-size when a reliable estimate is available, but avoid retaining grossly oversized arrays.

ArrayList<Result> results =
    new ArrayList<>(
        input.size());

Hash tables

Hash maps and sets balance table capacity against load factor. A higher load factor uses less table space but can increase collision work; a lower load factor uses more memory and increases iteration over empty buckets.[17]

HashMap<Key, Value> map =
    HashMap.newHashMap(
        expectedMappings);

HashSet<Key> set =
    HashSet.newHashSet(
        expectedElements);

Java 19 added sizing factories that accept expected element/mapping counts and choose implementation capacity appropriately.

26. Null policies differ by interface implementation

TypeTypical null policy
ArrayList, LinkedList, VectorPermit null elements
HashSet, LinkedHashSetPermit one null element
HashMap, LinkedHashMapPermit one null key and null values
TreeSet, TreeMapDepends on comparator; natural order generally rejects null keys/elements
PriorityQueueRejects null
ConcurrentHashMapRejects null keys and values
List.of, Set.of, Map.ofReject nulls

Null acceptance is part of the concrete implementation contract. Domain collections are usually easier to reason about when null elements/keys are prohibited at the boundary.

27. Iterator<E>

Traversal Iterator replaces legacy Enumeration and supports element traversal plus optional removal of the last returned element.[22]

Iterator<Session> iterator =
    sessions.iterator();

while (iterator.hasNext()) {
    Session session =
        iterator.next();

    if (session.expired()) {
        iterator.remove();
    }
}

Remove only after next

Iterator<String> iterator =
    values.iterator();

// IllegalStateException:
iterator.remove();

forEachRemaining

iterator.forEachRemaining(
    this::process);

Mutation outside the iterator during traversal is implementation-dependent and commonly invalid for ordinary collections.

28. ListIterator<E>

ListIterator extends iterator traversal with bidirectional movement, index reporting, replacement, and insertion at the cursor.[23]

ListIterator<String> iterator =
    values.listIterator();

while (iterator.hasNext()) {
    String value =
        iterator.next();

    if (value.isBlank()) {
        iterator.set(
            "<blank>");
    }

    if (value.equals("marker")) {
        iterator.add(
            "inserted-after-marker");
    }
}

Reverse traversal

ListIterator<String> iterator =
    values.listIterator(
        values.size());

while (iterator.hasPrevious()) {
    process(
        iterator.previous());
}

29. Fail-fast, snapshot, and weakly consistent traversal

ModelExamplesBehavior
Fail-fast, best effortArrayList, HashMap, TreeSetMay throw ConcurrentModificationException after unexpected structural modification
SnapshotCopyOnWriteArrayListIterator sees immutable snapshot from iterator creation
Weakly consistentConcurrentHashMap, concurrent queuesProceeds during updates; may reflect some later changes; no fail-fast exception

Fail-fast detection is a bug detector, not a synchronization guarantee. It operates on a best-effort basis and must never be used for program correctness.[10]

Unsafe concurrent modification

for (String value : values) {
    if (value.isBlank()) {
        values.remove(value);
    }
}

Use bulk removal

values.removeIf(
    String::isBlank);

30. Bulk collection and map operations

Collection bulk operations

target.addAll(source);

target.removeAll(rejected);

target.retainAll(allowed);

target.removeIf(
    this::expired);

List replacement

names.replaceAll(
    String::strip);

names.sort(
    String.CASE_INSENSITIVE_ORDER);

Map bulk update

balances.replaceAll(
    (account, balance) ->
        balance.max(
            BigDecimal.ZERO));

settings.forEach(
    this::publishSetting);

Default interface methods do not automatically add synchronization. Implementations with a synchronization protocol must override them appropriately.[2]

31. Sorting lists

Sorting List.sort and Collections.sort sort a modifiable list according to natural order or a comparator. The specified sort is stable: equal elements retain their relative order.[24]

employees.sort(
    Comparator.comparing(
            Employee::department)
        .thenComparing(
            Employee::lastName)
        .thenComparing(
            Employee::firstName));

Natural ordering

List<Instant> instants =
    new ArrayList<>(values);

Collections.sort(instants);

Unmodifiable lists

List<String> immutable =
    List.of("b", "a");

// UnsupportedOperationException:
immutable.sort(
    Comparator.naturalOrder());

Copy before sorting

List<String> sorted =
    new ArrayList<>(source);

sorted.sort(
    Comparator.naturalOrder());

32. Binary searching sorted lists

Collections.binarySearch searches a list using natural order or a comparator. The list must already be sorted according to the same ordering; otherwise the result is undefined.[24]

employees.sort(
    BY_EMPLOYEE_ID);

int index =
    Collections.binarySearch(
        employees,
        target,
        BY_EMPLOYEE_ID);

if (index >= 0) {
    Employee found =
        employees.get(index);
} else {
    int insertionPoint =
        -index - 1;
}

Random versus sequential access

Binary search uses indexed access efficiently on random-access lists. On large sequential-access lists it uses iterator-based traversal but still performs many link traversals; an array-backed sorted list is usually a better search structure.

Use maps for repeated exact-key lookup

If exact lookup is frequent and sorted traversal is not the primary requirement, a HashMap or TreeMap usually communicates intent better than repeatedly binary-searching a list.

34. Comparable<T> and natural ordering

Natural order Comparable imposes a total ordering on instances of a class through compareTo. Naturally ordered objects can be sorted and used as keys/elements in sorted maps and sets without an explicit comparator.[25]

public record Version(
        int major,
        int minor,
        int patch)
        implements Comparable<Version> {

    @Override
    public int compareTo(
            Version other) {

        int result =
            Integer.compare(
                major,
                other.major);

        if (result != 0) {
            return result;
        }

        result =
            Integer.compare(
                minor,
                other.minor);

        if (result != 0) {
            return result;
        }

        return Integer.compare(
            patch,
            other.patch);
    }
}

Never subtract to compare

// Wrong: can overflow.
return left - right;

// Correct:
return Integer.compare(
    left,
    right);

Comparable laws

  • Sign symmetry between x.compareTo(y) and y.compareTo(x).
  • Transitivity.
  • If comparison is zero, comparisons against every third value have the same sign.
  • Consistency with equals is strongly recommended.

35. Comparator<T>

Explicit order A comparator imposes an ordering externally, allowing several orderings for one type. It is a functional interface and supports composition, reversal, key extraction, null policy, and natural/reverse order factories.[26]

Comparator<Employee> bySalary =
    Comparator.comparing(
        Employee::salary);

Comparator<Employee> byName =
    Comparator.comparing(
            Employee::lastName)
        .thenComparing(

Tie-breakers matter

A sorted set or map treats comparison-zero values as equivalent. Add a stable unique tie-breaker when distinct domain values must coexist.

37. Ordering consistency with equals

Natural and explicit ordering are consistent with equals when comparison returns zero exactly when equality returns true. Inconsistent ordering can make a sorted set appear to reject unequal values or a sorted map replace an unequal key's mapping.[25]

BigDecimal first =
    new BigDecimal("4.0");

BigDecimal second =
    new BigDecimal("4.00");

assert first.compareTo(second) == 0;
assert !first.equals(second);

Set<BigDecimal> values =
    new TreeSet<>();

values.add(first);
values.add(second);

assert values.size() == 1;

Comparator for distinct representations

Comparator<BigDecimal> numericalThenScale =
    BigDecimal::compareTo;

numericalThenScale =
    numericalThenScale.thenComparingInt(
        BigDecimal::scale);

Document intentionally inconsistent orderings and avoid them for general-purpose sorted collections unless the equivalence relation is a deliberate part of the domain.

Mapping-function guidance

  • Keep mapping functions short and non-recursive.
  • Avoid external side effects unless retries/reinvocation are acceptable.
  • For ConcurrentHashMap, do not block unrelated progress with slow I/O inside compute.
  • Atomicity is normally per key, not across several keys or maps.

Factory values

An unmodifiable collection can still contain mutable elements. Deep immutability requires immutable reachable state or defensive copying.

40. Synchronized wrappers and concurrent alternatives

List<Event> synchronizedList =
    Collections.synchronizedList(
        new ArrayList<>());

Map<Key, Value> synchronizedMap =
    Collections.synchronizedMap(
        new HashMap<>());

Synchronized wrappers serialize method access through the wrapper. All access must use the wrapper, and traversal must be performed while manually holding the wrapper's monitor.[24]

synchronized (synchronizedMap) {
    for (Map.Entry<Key, Value> entry
            : synchronizedMap.entrySet()) {

        process(entry);
    }
}

Prefer concurrent collections for scalable shared access

ConcurrentHashMap is usually preferable to a synchronized HashMap when many threads access the map and no single global lock is required. Concurrent collections use weakly consistent traversal and atomic operations rather than one exclusion lock.[21]

41. Implementing custom collections

Abstract skeletal classes such as AbstractCollection, AbstractList, AbstractSet, and AbstractMap reduce the methods required to implement a custom collection. The collection interfaces still require precise equality, iterator, mutation, ordering, and exception contracts.

Read-only computed list

public final class Squares
        extends AbstractList<Long>
        implements RandomAccess {

    private final int size;

    public Squares(int size) {
        if (size < 0) {
            throw new IllegalArgumentException();
        }

        this.size = size;
    }

    @Override
    public Long get(int index) {
        Objects.checkIndex(
            index,
            size);

        long value = index;

        return value * value;
    }

    @Override
    public int size() {
        return size;
    }
}

Document characteristics

  • Whether nulls are permitted.
  • Encounter order and comparator.
  • Supported mutations.
  • Iterator consistency.
  • Thread-safety policy.
  • Complexity of key operations.
  • Whether views are backed or copied.

42. Complete example: in-memory job scheduler index

Domain model

public enum JobState {
    READY,
    RUNNING,
    COMPLETED,
    FAILED
}

public record JobId(
        UUID value)
        implements Comparable<JobId> {

    public JobId {
        Objects.requireNonNull(value);
    }

    @Override
    public int compareTo(
            JobId other) {

        return value.compareTo(
            other.value);
    }
}

public record Job(
        JobId id,
        int priority,
        Instant submittedAt,
        Instant deadline,
        Set<String> tags,
        JobState state) {

    public Job {
        Objects.requireNonNull(id);
        Objects.requireNonNull(submittedAt);
        Objects.requireNonNull(deadline);
        Objects.requireNonNull(tags);
        Objects.requireNonNull(state);

        tags =
            Set.copyOf(tags);
    }

    public Job withState(
            JobState next) {

        return new Job(
            id,
            priority,
            submittedAt,
            deadline,
            tags,
            next);
    }
}

Orders and indexes

private static final
Comparator<Job> DISPATCH_ORDER =
    Comparator.comparingInt(
            Job::priority)
        .reversed()
        .thenComparing(
            Job::deadline)
        .thenComparing(
            Job::submittedAt)
        .thenComparing(
            Job::id);

private final Map<JobId, Job> byId =
    new HashMap<>();

private final PriorityQueue<Job> ready =
    new PriorityQueue<>(
        DISPATCH_ORDER);

private final NavigableMap<Instant,
    LinkedHashSet<JobId>> byDeadline =
        new TreeMap<>();

private final Map<String,
    LinkedHashSet<JobId>> byTag =
        new HashMap<>();

Add a job atomically under one lock

public synchronized void add(
        Job job) {

    if (byId.putIfAbsent(
            job.id(),
            job) != null) {

        throw new IllegalArgumentException(
            "Duplicate job: "
                + job.id());
    }

    boolean committed = false;

    try {
        if (job.state()
                == JobState.READY) {
            ready.add(job);
        }

        byDeadline
            .computeIfAbsent(
                job.deadline(),
                ignored ->
                    new LinkedHashSet<>())
            .add(job.id());

        for (String tag : job.tags()) {
            byTag.computeIfAbsent(
                    tag,
                    ignored ->
                        new LinkedHashSet<>())
                .add(job.id());
        }

        committed = true;
    } finally {
        if (!committed) {
            removeFromIndexes(job);
            byId.remove(job.id());
        }
    }
}

Dispatch next job

public synchronized Optional<Job>
pollReady() {

    while (!ready.isEmpty()) {
        Job queued =
            ready.remove();

        Job current =
            byId.get(
                queued.id());

        if (current == null
                || current.state()
                    != JobState.READY) {
            continue;
        }

        Job running =
            current.withState(
                JobState.RUNNING);

        byId.put(
            running.id(),
            running);

        return Optional.of(
            running);
    }

    return Optional.empty();
}

Deadline range query

public synchronized List<Job>
dueBetween(
        Instant startInclusive,
        Instant endExclusive) {

    return byDeadline
        .subMap(
            startInclusive,
            true,
            endExclusive,
            false)
        .values()
        .stream()
        .flatMap(Set::stream)
        .map(byId::get)
        .filter(
            Objects::nonNull)
        .sorted(DISPATCH_ORDER)
        .toList();
}

Design choices

  • HashMap provides primary-key lookup.
  • PriorityQueue provides efficient next-job selection but not arbitrary sorted iteration.
  • TreeMap provides deadline range queries.
  • LinkedHashSet deduplicates IDs while preserving deterministic insertion order.
  • Immutable job records avoid mutable-key/index corruption.
  • One lock protects the multi-collection invariant; replacing individual fields with concurrent collections would not make the compound transaction atomic.

Comparator law tests

@Test
void comparatorIsTransitive() {
    for (Job first : jobs) {
        for (Job second : jobs) {
            for (Job third : jobs) {
                if (DISPATCH_ORDER.compare(
                            first,
                            second) <= 0
                        && DISPATCH_ORDER.compare(
                            second,
                            third) <= 0) {

                    assertTrue(
                        DISPATCH_ORDER.compare(
                            first,
                            third) <= 0);
                }
            }
        }
    }
}

Required cases

  • Empty, singleton, duplicate, and maximum-size inputs.
  • Null acceptance/rejection under the selected implementation.
  • Equal hash codes for equal keys.
  • Mutable-key attempts and immutable snapshots.
  • Comparator ties and consistency with equals.
  • Backed view mutations in both directions.
  • Iterator removal and unexpected concurrent modification.
  • Concurrent-map compute, replacement, and traversal behavior.
  • Priority-queue ties and draining order.
  • Binary search for found and insertion-point results.

Use randomized differential tests

For a custom collection, run the same operation sequence against a trusted reference implementation and compare state, return values, exceptions, iterator order, and views.

Big-O is not enough

  • Array locality often outweighs linked-list asymptotics for practical traversal.
  • Per-entry node/link/tree overhead can dominate small payloads.
  • Hash quality affects collision work.
  • Comparator cost is paid throughout tree and heap operations.
  • Ordering and synchronization constraints can dominate algorithmic cost.

46. Production checklist

Interface and semantics

  • The declared type is the narrowest interface needed.
  • Duplicate, order, null, and mutation policies are explicit.
  • Map key and set element equality are stable while stored.
  • Sequenced and reversed operations are understood as views where applicable.
  • Range-query requirements use navigable collections rather than ad hoc filtering.

Implementation

  • ArrayList is the default list unless a measured requirement suggests otherwise.
  • ArrayDeque is preferred for ordinary stacks and deques.
  • Hash, linked-hash, tree, and priority structures match ordering requirements.
  • Capacity is estimated without gross over-allocation.
  • Legacy Vector is retained only for compatibility or a deliberate synchronization contract.

Ordering and comparison

  • Comparable defines one sensible natural order.
  • Alternative orders use reusable comparators.
  • Comparators are antisymmetric, transitive, and complete.
  • Comparator ties are intentional and compatible with set/map uniqueness.
  • Null ordering is explicit.

Iteration and views

  • Iterator mutation uses iterator methods or bulk operations.
  • Fail-fast behavior is not relied upon for correctness.
  • Concurrent traversal uses the implementation's consistency model.
  • Backed views and independent copies are not confused.
  • Resource and lifecycle ownership of views is clear.

Concurrency

  • Unsynchronized collections are thread-confined or externally protected.
  • Synchronized wrappers are traversed under their monitor.
  • Concurrent collections are used for scalable shared access.
  • Multi-collection and multi-key invariants still use explicit coordination.
  • Mapping functions are short, side-effect-aware, and non-recursive.

Algorithms and performance

  • Sorting and binary searching use the same ordering.
  • Destructive algorithms are applied only to modifiable lists.
  • Iteration order assumptions are documented and tested.
  • Big-O, memory layout, cache locality, and workload shape are all considered.
  • Performance claims use JMH or representative end-to-end tests.
Final principle: the Collections Framework separates semantic contracts from data-structure choices. Reliable Java code selects an interface by meaning, an implementation by workload, an ordering by domain law, and a concurrency model by ownership—not by habit.
