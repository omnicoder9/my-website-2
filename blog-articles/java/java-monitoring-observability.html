1. Monitoring and observability

Monitoring asks whether known conditions are healthy. Observability asks whether the telemetry emitted by a system is sufficient to investigate behavior—including failure modes that were not predicted when dashboards and alerts were designed.

OpenTelemetry defines traces, metrics, logs, and baggage as distinct telemetry signals. Metrics represent measurements captured at runtime; traces describe the path and timing of work across components; logs record events; baggage carries contextual key-value data across process boundaries. The signals are complementary rather than interchangeable. [1]

Monitoring

Predefined queries, thresholds, health checks, dashboards, and notifications answer recurring operational questions efficiently.

Observability

Consistent dimensions, trace context, structured events, exemplars, and deep JVM diagnostics allow engineers to form and test new hypotheses during an incident.

Telemetry

The raw and derived data—metrics, spans, log records, profiles, events, and management attributes—used to observe the system.

Operations

Ownership, objectives, runbooks, escalation, retention, access control, and reliable delivery turn telemetry into an incident-response capability.

Engineering principle: telemetry is part of the product contract. Instrumentation should be reviewed, tested, versioned, and operated like any other production interface.

Questions each signal answers well

Signal Best questions Weakness when used alone
Metrics How much? How often? Is the rate, saturation, latency, or error ratio changing? Aggregates normally omit individual request detail.
Traces Where did one request spend time? Which dependency failed? What was the causal path? Sampling can omit rare events; storage cost grows with span volume and attributes.
Logs What discrete event occurred? Which decision, exception, or state transition was recorded? Unstructured logs are difficult to aggregate and correlate.
JMX What are the current JVM and application management attributes? Can a managed operation be invoked? Remote exposure can be operationally and security-sensitive.
JFR Which code, allocations, locks, GC events, threads, or operating-system events explain a performance problem? Diagnostic recordings require specialized analysis and are not a replacement for service-level metrics.

OpenTelemetry separates instrumentation APIs from SDK configuration and exporters. In Java, the stable API can be used by libraries, while the application owner installs and configures an SDK or Java agent. The SDK provides tracer, meter, and logger providers; processors and exporters control how recorded telemetry leaves the process. [2][3]

The OpenTelemetry Collector organizes data flow into receivers, processors, and exporters. Components become active only when included in a service pipeline. Separate pipelines can be configured for traces, metrics, and logs, allowing a deployment to batch, filter, enrich, sample, and route signals outside application processes. [4]

Pull and push are transport choices, not signal definitions

Prometheus commonly pulls metrics by scraping an HTTP endpoint. OTLP exporters push batches of traces, metrics, or logs to a Collector or backend. A Java service can legitimately expose Micrometer metrics for Prometheus while exporting traces through OTLP and writing structured logs to standard output. [5][6]

Avoid duplicate pipelines: if logs are tailed from stdout, do not also send the same records through an OTLP appender unless the backend deduplicates them. If Micrometer exposes Prometheus metrics, disable an automatic OTLP metrics exporter unless both copies are intentional.

3. Java platform monitoring: JMX and Java Flight Recorder

JMX Current management attributes and operations through MBeans.

JFR Time-oriented diagnostic and profiling events generated by the JVM, operating system, and application.

JMX is a standard Java API for monitoring and managing resources such as applications, services, devices, and the JVM. The JVM exposes platform MXBeans for memory, threads, garbage collectors, class loading, operating-system data, and other runtime state through the platform MBean server. Applications can register their own MBeans. [7][8]

QueueMonitorMXBean.javaApplication-specific JMX state 
package com.example.checkout;

public interface QueueMonitorMXBean {
    int getDepth();
    long getProcessedTotal();
    boolean isPaused();
    void pause();
    void resume();
}
package com.example.checkout;

import java.util.concurrent.atomic.AtomicBoolean;
import java.util.concurrent.atomic.LongAdder;
import java.util.function.IntSupplier;

public final class QueueMonitor implements QueueMonitorMXBean {
    private final IntSupplier depth;
    private final LongAdder processed = new LongAdder();
    private final AtomicBoolean paused = new AtomicBoolean();

    public QueueMonitor(IntSupplier depth) {
        this.depth = depth;
    }

    @Override
    public int getDepth() {
        return depth.getAsInt();
    }

    @Override
    public long getProcessedTotal() {
        return processed.sum();
    }

    @Override
    public boolean isPaused() {
        return paused.get();
    }

    @Override
    public void pause() {
        paused.set(true);
    }

    @Override
    public void resume() {
        paused.set(false);
    }

    public void recordProcessed() {
        processed.increment();
    }
}
import java.lang.management.ManagementFactory;
import javax.management.ObjectName;

var monitor = new QueueMonitor(queue::size);

ManagementFactory.getPlatformMBeanServer().registerMBean(
        monitor,
        new ObjectName("com.example.checkout:type=QueueMonitor"));

Local JMX monitoring is available through the Attach API without opening a remote management port. Remote JMX requires explicit configuration and security. Oracle's Java 25 management guide recommends authentication and TLS for production and warns that disabling them permits unauthorized users to monitor or control the application. [9]

Java Flight Recorder

JFR records structured events about the JVM, application, and operating system. The Java 25 Flight Recorder API supports custom events and continuous event streaming. JDK Mission Control analyzes recordings for code performance, allocation, locks, garbage collection, latency, and other runtime behavior. [10][11]

CheckoutJfrEvent.javaCustom diagnostic event 
package com.example.checkout;

import jdk.jfr.Category;
import jdk.jfr.Event;
import jdk.jfr.Label;
import jdk.jfr.Name;
import jdk.jfr.StackTrace;
import jdk.jfr.Threshold;

@Name("com.example.Checkout")
@Label("Checkout operation")
@Category({"Application", "Checkout"})
@Threshold("20 ms")
@StackTrace(false)
public final class CheckoutJfrEvent extends Event {
    @Label("Route")
    String route;

    @Label("Outcome")
    String outcome;

    @Label("Item count")
    int itemCount;
}
CheckoutJfrEvent event = new CheckoutJfrEvent();
event.begin();

try {
    checkout(command);
    event.outcome = "success";
} catch (RuntimeException failure) {
    event.outcome = "error";
    throw failure;
} finally {
    event.route = "checkout";
    event.itemCount = command.items().size();

    if (event.shouldCommit()) {
        event.commit();
    }
}
# Start a recording at JVM startup:
java \
  -XX:StartFlightRecording=filename=checkout.jfr,duration=5m,settings=profile \
  -jar checkout.jar

# Inspect from the command line:
jfr summary checkout.jfr
jfr print --events com.example.Checkout checkout.jfr

Oracle's JFR guide demonstrates extending jdk.jfr.Event, setting fields, and committing the event. Custom JFR events are appropriate for diagnostic detail that would be too expensive or high-cardinality as always-on metrics. [12]

4. Metric design

Prometheus and Micrometer model metrics as named measurements with dimensions—called labels in Prometheus and tags in Micrometer. Each unique metric name and label-value combination creates a distinct time series. High-cardinality labels therefore increase memory, storage, network, and query cost. [13][14]

Metric type Meaning Java examples Typical PromQL
Counter Monotonically increasing event total, except reset on process restart Requests, failures, messages, retries, bytes processed rate(counter_total[5m])
Gauge Current value that can rise or fall Queue depth, active requests, pool usage, temperature Direct value, max_over_time, comparisons
Histogram Distribution of observations across buckets plus count and sum Latency, payload size, batch size histogram_quantile, SLO bucket ratios
Summary Client-calculated quantiles and count/sum Local percentile approximation Read quantile series; cannot aggregate quantiles correctly across instances
Long-task timer Current duration and count of tasks still running Import jobs, migrations, long batch stages Active count, maximum active duration

Prometheus recommends counters for accumulating totals and gauges for values that can decrease. Raw counters are normally converted to rates. Histograms allow server-side aggregation and percentile approximation, while client-side summary quantiles cannot be meaningfully aggregated across label dimensions or instances. [15][16]

Names and units

Prometheus recommends a domain prefix, one quantity and unit per metric, base units such as seconds and bytes, and unit suffixes. Counters conventionally end in _total. Micrometer uses backend-aware naming conventions, so an instrumentation name such as checkout.http.server.requests is translated into Prometheus-style series. [17]

Cardinality policy

Dimension Metric label? Trace/log field? Reason
HTTP route template Yes Yes Bounded and operationally useful
Status class or outcome Yes Yes Bounded error analysis
Deployment environment Yes Resource attribute Bounded operational partition
User ID No Only when permitted and protected Unbounded and potentially sensitive
Raw URL No Usually sanitized; use route template Path parameters create unbounded series
Exception message No Log or span event Messages often contain variable data
Order ID No Log/trace under data policy Per-request identifier, unsuitable for aggregation
Never label metrics with unbounded values: user IDs, request IDs, UUIDs, email addresses, stack traces, exception messages, full URLs, and SQL text belong in controlled logs or traces—not time-series labels.

5. Micrometer: portable Java metrics

Micrometer 1.17 A JVM instrumentation facade supporting counters, gauges, timers, distribution summaries, long-task timers, and backend registries.

Observation API One lifecycle can produce metrics, spans, and contextual events through registered handlers.

Micrometer provides a facade over monitoring-system instrumentation clients. A MeterRegistry owns meters; each meter is identified by name and tags. 5.2 Cohesive application metrics

CheckoutMetrics.javaBounded tags and aggregable latency 
package com.example.checkout;

import io.micrometer.core.instrument.Counter;
import io.micrometer.core.instrument.Gauge;
import io.micrometer.core.instrument.MeterRegistry;
import io.micrometer.core.instrument.Timer;

import java.time.Duration;
import java.util.Objects;
import java.util.concurrent.atomic.AtomicInteger;
import java.util.function.Supplier;

public final class CheckoutMetrics {
    private final MeterRegistry registry;
    private final Counter rejected;
    private final Timer checkoutLatency;
    private final AtomicInteger queueDepth = new AtomicInteger();

    public CheckoutMetrics(MeterRegistry registry) {
        this.registry = Objects.requireNonNull(registry);

        this.rejected = Counter.builder("checkout.orders.rejected")
                .description("Orders rejected before payment")
                .tag("reason", "validation")
                .register(registry);

        this.checkoutLatency = Timer.builder("checkout.operation")
                .description("End-to-end checkout duration")
                .publishPercentileHistogram()
                .serviceLevelObjectives(
                        Duration.ofMillis(100),
                        Duration.ofMillis(250),
                        Duration.ofMillis(500),
                        Duration.ofSeconds(1))
                .minimumExpectedValue(Duration.ofMillis(5))
                .maximumExpectedValue(Duration.ofSeconds(5))
                .register(registry);

        Gauge.builder(
                        "checkout.queue.depth",
                        queueDepth,
                        AtomicInteger::get)
                .description("Orders waiting for checkout processing")
                .register(registry);
    }

    public <T> T timeCheckout(
            String outcome,
            Supplier<T> operation) {

        Timer.Sample sample = Timer.start(registry);
        try {
            return operation.get();
        } finally {
            sample.stop(Timer.builder("checkout.operation.by.outcome")
                    .tag("outcome", normalizeOutcome(outcome))
                    .publishPercentileHistogram()
                    .serviceLevelObjectives(
                            Duration.ofMillis(100),
                            Duration.ofMillis(500),
                            Duration.ofSeconds(1))
                    .register(registry));
        }
    }

    public void rejectedValidation() {
        rejected.increment();
    }

    public void setQueueDepth(int value) {
        queueDepth.set(value);
    }

    private static String normalizeOutcome(String outcome) {
        return switch (outcome) {
            case "success", "client_error", "server_error" -> outcome;
            default -> "unknown";
        };
    }
}

Micrometer timers already publish event counts, so a separate request counter is often redundant. Percentile histograms are aggregable in Prometheus; client-side percentile values are not. Service-level objective boundaries add explicit cumulative buckets that support direct compliance calculations. [20][21]

5.3 Avoid repeated meter creation on a hot path

Micrometer registries cache meters by name and tags, but looking up a meter for every event still adds work. Cache meter instances when the tag set is fixed. For bounded dynamic tags, maintain an enum-keyed or otherwise bounded cache rather than constructing arbitrary tag values from input. [22] 

enum Outcome {
    SUCCESS("success"),
    CLIENT_ERROR("client_error"),
    SERVER_ERROR("server_error");

    final String tag;

    Outcome(String tag) {
        this.tag = tag;
    }
}

final class OutcomeCounters {
    private final EnumMap<Outcome, Counter> counters =
            new EnumMap<>(Outcome.class);

    OutcomeCounters(MeterRegistry registry) {
        for (Outcome outcome : Outcome.values()) {
            counters.put(
                    outcome,
                    Counter.builder("checkout.completed")
                            .tag("outcome", outcome.tag)
                            .register(registry));
        }
    }

    void increment(Outcome outcome) {
        counters.get(outcome).increment();
    }
}

5.4 Observation API

Micrometer Observation represents an operation lifecycle with start, stop, error, event, and scope callbacks. Observation handlers can create metrics, spans, or logs from the same instrumentation. Low-cardinality key-values are suitable for metrics and traces; high-cardinality values are intended for traces but must still obey privacy and cost policies. [23][24] 

Observation.createNotStarted(
            "checkout.process",
            observationRegistry)
        .lowCardinalityKeyValue("outcome", "success")
        .highCardinalityKeyValue("order.id", orderId)
        .observe(() -> checkout(order));
Portable does not mean identical: Micrometer maps common meter concepts to each backend's data model. Naming, temporality, histograms, base units, and export behavior still differ, so validate the actual series and queries in the selected backend.

6. Prometheus: scrape-based metrics collection

Prometheus is configured with scrape jobs and targets. It periodically fetches metric exposition from application instances and stores labeled time series. Micrometer's current micrometer-registry-prometheus module uses the Prometheus Java Client 1.x and exposes registry data through PrometheusMeterRegistry.scrape(). [5][25]

6.1 Plain Java metrics endpoint

MetricsEndpoint.javaJDK HTTP server 
package com.example.checkout;

import com.sun.net.httpserver.HttpExchange;
import com.sun.net.httpserver.HttpServer;
import io.micrometer.prometheusmetrics.PrometheusConfig;
import io.micrometer.prometheusmetrics.PrometheusMeterRegistry;

import java.io.IOException;
import java.net.InetSocketAddress;
import java.nio.charset.StandardCharsets;
import java.util.concurrent.Executors;

public final class MetricsEndpoint implements AutoCloseable {
    private static final String OPEN_METRICS =
            "application/openmetrics-text; version=1.0.0; charset=utf-8";

    private final PrometheusMeterRegistry registry;
    private final HttpServer server;

    public MetricsEndpoint(int port) throws IOException {
        this.registry =
                new PrometheusMeterRegistry(PrometheusConfig.DEFAULT);

        this.server = HttpServer.create(
                new InetSocketAddress("0.0.0.0", port),
                0);

        server.createContext("/metrics", this::scrape);
        server.createContext("/live", exchange ->
                respond(exchange, 200, "live\n", "text/plain"));
        server.createContext("/ready", exchange ->
                respond(exchange, 200, "ready\n", "text/plain"));

        server.setExecutor(Executors.newVirtualThreadPerTaskExecutor());
    }

    public PrometheusMeterRegistry registry() {
        return registry;
    }

    public void start() {
        server.start();
    }

    private void scrape(HttpExchange exchange) throws IOException {
        String body = registry.scrape(OPEN_METRICS);
        respond(exchange, 200, body, OPEN_METRICS);
    }

    private static void respond(
            HttpExchange exchange,
            int status,
            String body,
            String contentType) throws IOException {

        byte[] bytes = body.getBytes(StandardCharsets.UTF_8);
        exchange.getResponseHeaders().set("Content-Type", contentType);
        exchange.sendResponseHeaders(status, bytes.length);

        try (var output = exchange.getResponseBody()) {
            output.write(bytes);
        }
    }

    @Override
    public void close() {
        server.stop(0);
        registry.close();
    }
}

Micrometer can emit Prometheus text or OpenMetrics exposition. Exemplars that link metric samples to trace and span identifiers require OpenMetrics exposition and a configured span-context source. [25]

6.3 Scrape health is itself a signal

Prometheus creates the up series for scrape targets. A value of zero means the scrape failed, but the cause can be the application, network, service discovery, TLS, authentication, timeout, or metric endpoint. A page should identify user-visible impact; scrape failure is often an important supporting alert or diagnostic condition rather than the only service-health signal.

7. PromQL, histograms, and recording rules

PromQL operates on instant vectors, range vectors, scalars, and strings. The rate() function calculates the per-second rate of a counter and accounts for resets. Prometheus recommends applying rate() before aggregation so resets can be detected per time series. [28][29]

Request rate

sum by (route) (
  rate(checkout_operation_by_outcome_seconds_count[5m])
)

Error ratio

sum(
  rate(checkout_operation_by_outcome_seconds_count{
    outcome="server_error"
  }[5m])
)
/
clamp_min(
  sum(rate(checkout_operation_by_outcome_seconds_count[5m])),
  0.001
)

P95 latency from a classic histogram

histogram_quantile(
  0.95,
  sum by (le, route) (
    rate(checkout_operation_by_outcome_seconds_bucket[5m])
  )
)

Classic histogram buckets are cumulative and carry the le label, which must be retained during aggregation for histogram_quantile(). Native histograms simplify aggregation because they store a histogram sample rather than one series per explicit bucket. Current Prometheus guidance recommends native histograms when the instrumentation and operational environment support them. [16][29]

SLO bucket ratio

# Fraction of requests completed within 500 ms.
sum(rate(checkout_operation_by_outcome_seconds_bucket{
  le="0.5"
}[5m]))
/
sum(rate(checkout_operation_by_outcome_seconds_count[5m]))

            0.95,

              rate(
                checkout_operation_by_outcome_seconds_bucket[5m]
              )
            )
          )

      - record: checkout:within_500ms_ratio5m
        expr: |
          sum(
            rate(
              checkout_operation_by_outcome_seconds_bucket{
                le="0.5"
              }[5m]
            )

Recording rules evaluate expressions at configured intervals and persist their results as new time series. They reduce repeated dashboard and alert query cost and centralize important aggregations. Rule files should be syntax-checked with promtool and tested with representative input series. [27]

9. Distributed tracing

A trace is a tree or graph of spans representing related operations. A span has a name, timestamps, trace and span identifiers, a parent, attributes, events, links, status, and a kind. The OpenTelemetry tracing API is stable. Span names should describe a bounded operation such as checkout.process or an HTTP route template, not a specific user or resource identifier. [35]

Span kind Meaning Example
SERVER Handling an incoming request HTTP POST /checkout
CLIENT Synchronous outgoing request HTTP call to payment service
PRODUCER Publishing deferred work Sending order.created
CONSUMER Receiving or processing deferred work Handling a Kafka message
INTERNAL In-process operation Pricing calculation

Trace context

W3C Trace Context standardizes the traceparent and tracestate HTTP headers. OpenTelemetry span contexts conform to this model, carrying a trace ID, span ID, trace flags, and trace state. Propagators inject context into outbound carriers and extract it from inbound carriers. [36][35] 

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01

Sampling

Sampling controls which traces are recorded or exported. Head sampling decides near trace creation and is inexpensive but lacks knowledge of the final outcome. Tail sampling can evaluate completed traces in a Collector or backend and retain errors or slow traces, but requires buffering and operational capacity. Metrics should still quantify all requests because sampled traces are not a reliable denominator for service rates.

Span attributes, events, and links

  • Use attributes for searchable properties with controlled size and cardinality.
  • Use events for timestamped points within a span, such as a retry or queue wait.
  • Record exceptions and set error status according to semantic conventions.
  • Use links for causal relationships that are not a single parent-child edge, such as batch consumers.
  • End every span; unfinished spans can consume memory and never reach exporters.

10. OpenTelemetry Java agent: zero-code instrumentation

The OpenTelemetry Java agent attaches to Java 8 or later and injects bytecode instrumentation for supported libraries and frameworks. It commonly captures inbound HTTP, outbound HTTP, database, messaging, and framework operations. Manual API instrumentation can extend the automatically generated trace with business spans and attributes. [37]

When auto-instrumentation is insufficient

  • Business operations are invisible behind one framework span.
  • Queue time and processing time need separate spans or events.
  • Domain outcomes need bounded attributes.
  • Custom protocols require explicit propagators or instrumentation.
  • Instrumentation creates noisy or sensitive attributes that must be suppressed.
Do not instrument every method: spans should represent operations useful for causal analysis. Method-level tracing creates excessive volume and hides meaningful boundaries among thousands of implementation spans.

11.2 Business span with correct lifecycle

TracedCheckoutService.javaChild span, error event, bounded attributes 
package com.example.checkout;

import io.opentelemetry.api.OpenTelemetry;
import io.opentelemetry.api.common.AttributeKey;
import io.opentelemetry.api.trace.Span;
import io.opentelemetry.api.trace.StatusCode;
import io.opentelemetry.api.trace.Tracer;
import io.opentelemetry.context.Scope;

import java.util.Objects;

public final class TracedCheckoutService {
    private static final AttributeKey<String> OUTCOME =
            AttributeKey.stringKey("checkout.outcome");

    private static final AttributeKey<Long> ITEM_COUNT =
            AttributeKey.longKey("checkout.item.count");

    private final Tracer tracer;
    private final PaymentGateway paymentGateway;

    public TracedCheckoutService(
            OpenTelemetry openTelemetry,
            PaymentGateway paymentGateway) {

        this.tracer = openTelemetry.getTracer(
                "com.example.checkout",
                "1.0.0");

        this.paymentGateway =
                Objects.requireNonNull(paymentGateway);
    }

    public Receipt checkout(Order order) {
        Span span = tracer.spanBuilder("checkout.process")
                .setAttribute(ITEM_COUNT, order.items().size())
                .startSpan();

        try (Scope ignored = span.makeCurrent()) {
            Receipt receipt = paymentGateway.pay(order);

            span.setAttribute(OUTCOME, "success");
            span.addEvent("payment.authorized");
            return receipt;
        } catch (PaymentDeclinedException declined) {
            span.setAttribute(OUTCOME, "declined");
            span.setStatus(StatusCode.ERROR, "payment declined");
            span.recordException(declined);
            throw declined;
        } catch (RuntimeException failure) {
            span.setAttribute(OUTCOME, "error");
            span.setStatus(StatusCode.ERROR, "checkout failed");
            span.recordException(failure);
            throw failure;
        } finally {
            span.end();
        }
    }
}

A new span is not automatically made current by the OpenTelemetry API; opening a Scope establishes it as the current context for child instrumentation and must be closed. Every started span must be ended. Attributes known at span creation should be set before starting when a sampler may need them. [35]

Baggage

OpenTelemetry baggage is a separate key-value store propagated with context. It is not automatically copied into span, metric, or log attributes. Baggage travels in headers and can reach unintended downstream services; sensitive or untrusted values require strict allowlists. [38]

package com.example.checkout;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public final class CheckoutLogger {
    private static final Logger LOG =
            LoggerFactory.getLogger(CheckoutLogger.class);

    public void completed(
            String orderId,
            int itemCount,
            long durationMillis) {

        LOG.atInfo()
                .setMessage("checkout completed")
                .addKeyValue("event.name", "checkout.completed")
                .addKeyValue("order.id", orderId)

                .setMessage("checkout failed")
                .addKeyValue("event.name", "checkout.failed")
                .addKeyValue("order.id", orderId)
                .setCause(failure)
                .log();

}

package com.example.telemetry;

import io.opentelemetry.api.trace.Span;
import io.opentelemetry.api.trace.SpanContext;
import org.slf4j.MDC;

public final class TraceLogScope implements AutoCloseable {
    private final MDC.MDCCloseable trace;
    private final MDC.MDCCloseable span;

    private TraceLogScope(
            MDC.MDCCloseable trace,
            MDC.MDCCloseable span) {
        this.trace = trace;
        this.span = span;
    }

    public static TraceLogScope open() {
        SpanContext context =
                Span.current().getSpanContext();

        if (!context.isValid()) {
            return new TraceLogScope(null, null);
        }

        return new TraceLogScope(
                MDC.putCloseable(
                        "trace_id",
                        context.getTraceId()),
                MDC.putCloseable(
                        "span_id",
                        context.getSpanId()));
    }

    @Override
    public void close() {
        if (span != null) {
            span.close();
        }
        if (trace != null) {
            trace.close();
        }
    }
}

13.5 Asynchronous logging tradeoffs

Logback's AsyncAppender buffers events in a blocking queue. By default it can discard TRACE, DEBUG, and INFO events when the queue is near capacity, while WARN and ERROR are retained. Shutdown must stop the logging context so queued events can flush. Queue size, discarding behavior, blocking, caller data, and flush timeout are reliability decisions—not mere performance tuning. [46]

Logging is not free: verbose payloads, stack traces, caller lookup, synchronous network appenders, and saturated async queues can affect latency or lose evidence. Measure the configured path under failure and shutdown conditions.

15. Alerting design

Page Immediate human action is required to protect users or a near-term objective.

Ticket Work is required, but interruption is not justified.

Dashboard Useful context that does not independently demand notification.

Prometheus alerting guidance recommends few alerts, alerts on symptoms associated with user pain, useful diagnostic consoles, slack for brief fluctuations, and pages only when an operator can take action. For online services, latency and error rate should generally be evaluated high in the stack. [48]

An alert contract

  • Condition: a query expressing a user-visible or objective-threatening symptom.
  • Duration: enough persistence to exclude harmless transients.
  • Severity: page, ticket, or informational.
  • Owner: team and escalation path.
  • Impact: what users or objectives are affected.
  • Runbook: first checks, safe mitigations, and rollback information.
  • Context: dashboard, deploy, trace, and log links.

Bad and better alert conditions

Bad page Why Better approach
Heap above 70% May be normal managed-heap behavior and does not prove user impact Page on sustained latency/error symptoms; show heap and GC as cause context
One exception logged Expected business exceptions and retries may be harmless Alert on error ratio, failed operations, or exhausted retry outcomes
CPU above 80% for one minute High utilization can be efficient and transient Combine sustained saturation with queue growth, latency, or dropped work
Every instance restart Deployments and autoscaling cause expected restarts Alert on crash loops, unavailable capacity, or failed readiness
Alert ownership: select one authoritative alert rule for a symptom. Duplicating the same condition in Prometheus, Grafana, a cloud monitor, and a log platform creates multiple pages for one incident and inconsistent silencing.

18.5 Native incident drills

  • Force a dependency timeout and confirm one error span, correlated logs, and metric changes.
  • Drop Collector connectivity and observe exporter queue and application behavior.
  • Fill an asynchronous log queue and confirm the documented loss or blocking policy.
  • Break the metrics endpoint and confirm scrape-health diagnostics.
  • Trigger the alert expression long enough to verify routing, grouping, and resolution.
  • Capture a JFR recording during load and verify custom events and JVM evidence.

19. Performance, cardinality, and telemetry cost

Instrumentation consumes CPU, memory, network bandwidth, storage, query capacity, and human attention. Prometheus warns that every label set is another time series, and Micrometer meters are identified by name and tags. OpenTelemetry spans and logs similarly grow with attributes, events, stack traces, and sampling rate. [14][13]

Control points

Signal Primary cost controls
Metrics Label allowlists, histogram buckets, scrape interval, retention, recording rules, aggregation
Traces Head/tail sampling, span limits, attribute limits, route normalization, batch export
Logs Level policy, structured fields, sampling repetitive events, retention tiers, stack-trace policy
JFR Event settings, thresholds, stack traces, recording duration, disk limits
Dashboards Query interval, time range, recording rules, variable scope, panel count
Alerts Symptom focus, duration, grouping, inhibition, repeat interval, ownership review

Histogram budget

A classic histogram creates one time series per bucket plus count and sum for every tag combination. Micrometer's minimum and maximum expected values constrain its generated bucket set, while explicit service-level objective boundaries add operationally meaningful buckets. Enable distributions only for selected timers rather than every library meter. [21]

Exporter failure behavior

Telemetry export must not silently exhaust application memory when a backend is unavailable. Batch queues, timeouts, retries, dropping policies, and Collector memory limits must be bounded. Monitor the telemetry pipeline itself: dropped spans, failed exports, scrape failures, rule evaluation errors, Collector queue saturation, and notification errors.

Observability can fail during the incident it is meant to explain. Backends, collectors, DNS, certificates, and network paths need their own monitoring, capacity, redundancy, and tested failure modes.

20. Security and privacy

Telemetry often contains URLs, headers, database statements, user identifiers, host data, stack traces, and business events. OpenTelemetry baggage is transmitted in request headers; logs and traces can cross organizational or regional boundaries; remote JMX can expose management operations. Treat observability data as production data with an explicit classification and access policy. [38][9]

Data-minimization rules

  • Record route templates rather than raw paths containing identifiers.
  • Never collect authorization, cookie, session, password, or secret headers.
  • Prefer error type and bounded code to raw exception messages as metric dimensions.
  • Redact or omit SQL text and bind values unless an approved diagnostic mode requires them.
  • Hashing is not automatically anonymization; small or known input spaces can be reversed.
  • Use trace and request identifiers for correlation instead of copying full payloads.
  • Apply retention and access tiers according to signal sensitivity.

Secure JMX

Remote JMX uses management capabilities, not a read-only metrics protocol by default. Oracle recommends TLS and authentication for production. An HTTP metrics endpoint should expose only measurements and be protected by network policy, authentication proxy, or service-mesh controls appropriate to the environment. [9]

Log injection

Structured encoders escape output, but applications should still validate external values, preserve field boundaries, and avoid allowing untrusted input to determine logger names, event names, metric names, or alert labels. Newlines and control characters in plain-text formats can forge apparent records if not encoded.

21. Incident investigation workflow

  1. Confirm user impact. Check request rate, error ratio, latency objective, availability, and affected environments.
  2. Establish the time window. Include the alert's pending period, deployment events, and preceding baseline.
  3. Partition the symptom. Compare route, region, version, dependency, and outcome—only across bounded dimensions.
  4. Open a representative trace. Use an exemplar or filtered trace search to find the critical path and failed dependency.
  5. Correlate logs. Search by trace ID and span ID; inspect structured events and exceptions near the failing span.
  6. Inspect JVM evidence. Check heap, allocation, GC, threads, locks, pools, and capture JFR when aggregates cannot explain the behavior.
  7. Mitigate safely. Roll back, shed load, disable a feature, increase capacity, or isolate a dependency according to the runbook.
  8. Verify recovery. Confirm the user-facing metric recovers, the alert resolves, queues drain, and no hidden saturation remains.
  9. Preserve evidence. Save trace links, logs, dashboards, JFR recordings, versions, and the incident timeline.
  10. Improve the system. Add or refine telemetry only when it would have shortened detection, diagnosis, or mitigation.

22. Production checklist

Metrics

  • Every service exposes rate, error, latency, and saturation signals appropriate to its workload.
  • Metric names, units, descriptions, and bounded dimensions are documented.
  • No metric label contains user, request, order, raw URL, exception message, or arbitrary input values.
  • Histogram boundaries include operational objectives and have an explicit series budget.
  • Prometheus rules are validated and unit-tested with promtool.

Traces

  • Inbound, outbound, database, and messaging boundaries propagate W3C trace context.
  • Business spans are named generically and ended on every path.
  • Sampling preserves required errors and slow paths without treating traces as a request denominator.
  • Baggage is allowlisted and contains no secrets or uncontrolled personal data.
  • Representative traces can be reached from dashboards or exemplars.

Logs

  • Logs are structured, escaped, and carry trace and span identifiers.
  • Event names and fields are stable; messages do not require brittle parsing.
  • Exceptions preserve stack traces without duplicating the same failure at every layer.
  • Async queue loss, blocking, and shutdown behavior are deliberately configured and tested.
  • One collection path prevents duplicate log ingestion.

JVM diagnostics

  • JVM runtime metrics are collected through Micrometer, JMX, or OpenTelemetry.
  • Remote JMX is disabled or strongly authenticated and encrypted.
  • JFR recording and analysis procedures are documented and rehearsed.
  • Custom JFR events capture expensive, high-detail diagnostic transitions that do not belong in metrics.

Dashboards and alerts

  • Dashboards begin with user-visible symptoms and link to causes, traces, logs, deploys, and runbooks.
  • Alerts are actionable, owned, grouped, inhibited, and tested end to end.
  • Every page identifies impact, duration, severity, dashboard, and runbook.
  • Alert noise, stale dashboards, unused metrics, and old suppressions are reviewed regularly.

Pipeline and governance

  • Collector queues, failed exports, dropped telemetry, and backend health are monitored.
  • Resource attributes and semantic conventions are versioned across services.
  • Retention, residency, access, and redaction policies are enforced.
  • Dependencies and collector images are pinned and upgraded in reviewed changes.
  • Telemetry cost is measured per service and signal.
Final principle: the goal is not maximum telemetry. The goal is the smallest, reliable, privacy-conscious set of signals that detects meaningful failure and lets an engineer explain and mitigate it quickly.
