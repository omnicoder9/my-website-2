1. A stream is a computation, not a container

A Java stream is a sequence of elements supporting aggregate operations. It does not own storage; it conveys elements from a source through a pipeline. The same source can often create several streams, but each individual stream pipeline is consumed at most once.

Source

A collection, array, generator, range, file, custom spliterator, or other producer.

Intermediate stages

Lazy transformations such as filtering, mapping, sorting, deduplication, slicing, flattening, and gathering.

Terminal stage

A result or effect such as reduction, collection, matching, finding, counting, iteration, or materialization.

Execution mode

Sequential or parallel, with source order and splitting characteristics affecting behavior and cost.

The java.util.stream package defines object streams and the primitive specializations IntStream, LongStream, and DoubleStream. Streams are lazy, consumable, and potentially unbounded; their operations are designed for functional-style bulk processing.[1]

Model the result, not the loop. Streams are strongest when the computation can be stated as a transformation and reduction without observable mutation during traversal.

2. Pipeline architecture and lazy evaluation

source │ ▼ filter(predicate) ┐ │ │ intermediate, lazy ▼ │ map(function) │ │ │ ▼ ┘ collect(collector) ───── terminal, triggers traversal
List<String> names =
    people.stream()
        .filter(Person::active)
        .map(Person::name)
        .sorted()
        .toList();

A pipeline has one source, zero or more intermediate operations, and one terminal operation. Traversal begins only when the terminal operation runs, and elements are normally processed vertically through fused stages rather than by materializing every intermediate result.[2]

Short-circuiting

Optional<Order> firstLarge =
    orders.stream()
        .filter(order ->
            order.total()
                .compareTo(threshold) > 0)
        .findFirst();

A short-circuiting operation can complete without consuming all input. This permits finite answers from some infinite pipelines when a bounding or matching operation appears downstream.

Optimization latitude

The implementation may elide stages or behavioral-parameter invocations when it can prove that the result is unchanged. Side effects inside intermediate operations must therefore not be used as required program behavior.[2]

3. Streams versus collections

CollectionStream
Owns and manages elementsDescribes traversal and computation
Can normally be traversed repeatedlySingle-use pipeline
Eagerly contains its current stateIntermediate operations are lazy
Supports access according to collection typeNo random-access API
May be mutableDoes not mutate its source by design
List<Order> orders =
    repository.loadOrders();

long openCount =
    orders.stream()
        .filter(order ->
            order.status() == Status.OPEN)
        .count();

Collection.stream() creates a sequential stream, while parallelStream() creates a possibly parallel stream. Collection implementations expose spliterators whose characteristics help the stream framework preserve order and divide work.[3]

4. Single use, ownership, and closing

After a terminal operation, a stream is consumed. Reusing it can throw IllegalStateException, although implementations are not required to detect every form of reuse.[2]

Stream<String> stream =
    Stream.of("alpha", "beta");

long count = stream.count();

// Invalid reuse:
List<String> values =
    stream.toList();

Use a supplier for repeatable pipelines

Supplier<Stream<Order>> openOrders =
    () ->
        orders.stream()
            .filter(order ->
                order.status() == Status.OPEN);

long count =
    openOrders.get().count();

BigDecimal total =
    openOrders.get()
        .map(Order::total)
        .reduce(
            BigDecimal.ZERO,
            BigDecimal::add);

Most streams need no explicit close

Streams implement AutoCloseable, but streams backed only by in-memory collections or arrays normally hold no closeable resource. Resource-backed streams—such as Files.lines—must be closed. Close handlers can be attached with onClose.[4]

5. Non-interference, statelessness, and side effects

Behavioral parameters should be non-interfering and usually stateless. Non-interference means they do not modify the stream source during pipeline execution unless the source explicitly supports concurrent modification. Statelessness means an element's result does not depend on mutable state that changes while processing other elements.[1]

Incorrect shared mutation

List<String> result =
    new ArrayList<>();

names.parallelStream()
    .filter(name -> !name.isBlank())
    .forEach(result::add);
// Data race and possible corruption.

Correct reduction

List<String> result =
    names.parallelStream()
        .filter(name -> !name.isBlank())
        .toList();

Source interference

// Do not modify 'orders' while traversing it.
orders.stream()
    .filter(Order::expired)
    .forEach(orders::remove);

Use collection operations such as removeIf, collect a replacement, or isolate mutation outside the stream traversal.

9. Infinite and generated streams

Iterative sequence

List<Integer> powersOfTwo =
    Stream.iterate(
            1,
            value -> value <= 1_024,
            value -> value * 2)
        .toList();

Infinite iteration with a bound

List<LocalDate> nextSevenDays =
    Stream.iterate(
            startDate,
            date -> date.plusDays(1))
        .limit(7)
        .toList();

Generated values

List<UUID> identifiers =
    Stream.generate(UUID::randomUUID)
        .limit(100)
        .toList();

iterate(seed, function) produces an ordered infinite stream. generate(supplier) produces an unordered infinite stream. Infinite pipelines require a short-circuiting terminal or a finite intermediate bound to complete.[2]

10. I/O-backed streams

try (Stream<String> lines =
        Files.lines(
            path,
            StandardCharsets.UTF_8)) {

    long warnings =
        lines.filter(line ->
                line.startsWith("WARN"))
            .count();
}

Files.lines lazily reads lines and returns a stream that owns an open file. The stream must be closed, and deferred I/O failures are wrapped in UncheckedIOException during pipeline execution.[6]

Directory entries

try (Stream<Path> entries =
        Files.list(directory)) {

    List<Path> regularFiles =
        entries.filter(
                Files::isRegularFile)
            .toList();
}

Do not return an open stream casually

An API returning a resource-backed stream transfers closing responsibility to its caller. Prefer a callback, a materialized result, or a clearly documented closeable stream when lifetime is not obvious.

11. Spliterators: traversal plus partitioning

A Spliterator traverses elements and can split its remaining elements into another spliterator for possible parallel processing. It reports characteristics such as ORDERED, DISTINCT, SORTED, SIZED, NONNULL, IMMUTABLE, CONCURRENT, and SUBSIZED.[7]

Spliterator<Order> spliterator =
    orders.spliterator();

long estimated =
    spliterator.estimateSize();

boolean ordered =
    spliterator.hasCharacteristics(
        Spliterator.ORDERED);

Spliterator<Order> prefix =
    spliterator.trySplit();

Parallel quality depends on splitting

A source that splits into balanced, sized partitions can parallelize effectively. A source that cannot split, splits only one item at a time, or has expensive sequential traversal may perform poorly in parallel.

Encounter order

If a spliterator reports ORDERED, traversal and splitting preserve the source's defined encounter order. Lists are ordered by index; hash-based collections generally have no guaranteed order.[7]

12. Creating a custom stream source

StreamSupport is a low-level facility primarily for library authors exposing stream views over custom data structures. It creates sequential or parallel streams from spliterators or suppliers of spliterators.[8]

Iterator-backed source

static <T> Stream<T> stream(
        Iterator<T> iterator) {

    Spliterator<T> spliterator =
        Spliterators
            .spliteratorUnknownSize(
                iterator,
                Spliterator.ORDERED);

    return StreamSupport.stream(
        spliterator,
        false);
}

Late-binding supplier

Stream<Event> stream =
    StreamSupport.stream(
        () -> eventLog.spliterator(),
        Spliterator.ORDERED
            | Spliterator.NONNULL,
        false);

The supplier form is invoked at most once and only after terminal evaluation begins, reducing the window for source interference. Reported characteristics must match the supplied spliterator.[8]

Spliterators.AbstractSpliterator can provide limited splitting when implementing only tryAdvance; custom sources should override splitting when they can partition more accurately and cheaply.[9]

13. Intermediate operations

Intermediate Intermediate operations return another stream and are lazy. They are commonly classified as stateless or stateful and as short-circuiting or non-short-circuiting.[1]

CategoryExamplesImplication
Statelessfilter, map, flatMap, peekEach element can normally be processed independently
Statefuldistinct, sorted, ordered limitMay buffer or coordinate across elements
Short-circuitinglimit, takeWhileCan produce a finite result from infinite input
One-to-manyflatMap, mapMulti, gatherOutput cardinality can differ from input

Pipeline order matters: filtering before expensive mapping usually reduces work, while sorting before filtering can sort elements that will later be discarded.

14. filter, map, and primitive mappings

List<String> normalized =
    users.stream()
        .filter(User::enabled)
        .map(User::email)
        .map(email ->
            email.strip()
                .toLowerCase(Locale.ROOT))
        .distinct()
        .toList();

Map to primitive streams

long totalBytes =
    files.stream()
        .mapToLong(
            FileMetadata::size)
        .sum();

map is a one-to-one transformation. mapToInt, mapToLong, and mapToDouble avoid wrapper allocation and expose numeric terminal operations.[2]

15. flatMap and mapMulti

Flatten nested streams

List<LineItem> items =
    orders.stream()
        .flatMap(order ->
            order.items().stream())
        .toList();

Flatten optionals

List<User> found =
    ids.stream()
        .map(repository::find)
        .flatMap(Optional::stream)
        .toList();

Emit zero or more values without a stream per input

List<String> tokens =
    lines.stream()
        .<String>mapMulti(
            (line, downstream) -> {
                for (String token
                        : line.split("\\s+")) {

                    if (!token.isBlank()) {
                        downstream.accept(token);
                    }
                }
            })
        .toList();

flatMap maps each element to a stream and concatenates the mapped streams. mapMulti gives the mapper a downstream consumer and is useful when each input emits a small number of results without needing an intermediate stream object.[2]

16. distinct and sorted

List<String> uniqueSorted =
    names.stream()
        .map(String::strip)
        .filter(name -> !name.isEmpty())
        .distinct()
        .sorted(
            String.CASE_INSENSITIVE_ORDER)
        .toList();

distinct uses Object.equals for object streams. sorted() requires natural ordering; sorted(comparator) accepts explicit ordering. Both are stateful operations that may need to retain many or all elements.[2]

Sort after reducing cardinality

List<Order> recentLargest =
    orders.stream()
        .filter(order ->
            order.createdAt()
                .isAfter(cutoff))
        .sorted(
            Comparator.comparing(
                    Order::total)
                .reversed())
        .limit(100)
        .toList();

17. Slicing and prefix operations

List<Event> page =
    events.stream()
        .skip(offset)
        .limit(pageSize)
        .toList();
List<Reading> healthyPrefix =
    readings.stream()
        .takeWhile(
            Reading::healthy)
        .toList();

List<Reading> afterWarmup =
    readings.stream()
        .dropWhile(
            Reading::warmingUp)
        .toList();

For ordered streams, takeWhile and dropWhile operate on the longest matching prefix. For unordered streams, their selected subset is nondeterministic within the documented constraints. Ordered parallel slicing can require substantial coordination.[2]

Pagination warning

skip still traverses skipped elements in many sources. Database or remote pagination should normally be pushed into the source query rather than performed after loading everything.

18. peek is mainly a diagnostic stage

List<Invoice> invoices =
    orders.stream()
        .peek(order ->
            LOGGER.log(
                System.Logger.Level.DEBUG,
                "received " + order.id()))
        .filter(Order::billable)
        .peek(order ->
            metrics.billableSeen()
                .increment())
        .map(billing::createInvoice)
        .toList();

peek performs an action as elements are consumed downstream, but its action may not run for every source element when optimization or short-circuiting avoids traversal. In parallel pipelines it can execute in arbitrary worker threads.[2]

Do not place required writes in peek. Use an explicit terminal operation, a separate loop, or a collector whose result captures the required work.

19. Stream gatherers

Stream.gather applies a Gatherer, a reusable custom intermediate operation. Gatherers can be stateless or stateful, short-circuit, emit zero or more outputs, maintain state, and support parallel evaluation when they define a combiner.[10]

Fixed windows

List<List<Integer>> windows =
    Stream.of(
            1, 2, 3, 4, 5, 6, 7, 8)
        .gather(
            Gatherers.windowFixed(3))
        .toList();

// [[1,2,3], [4,5,6], [7,8]]

Prefix scan

List<Integer> runningTotals =
    Stream.of(2, 4, 6, 8)
        .gather(
            Gatherers.scan(
                () -> 0,
                Integer::sum))
        .toList();

// [2, 6, 12, 20]

Bounded concurrent mapping

List<Profile> profiles =
    userIds.stream()
        .gather(
            Gatherers.mapConcurrent(
                20,
                profileClient::load))
        .toList();

The predefined gatherers include fixed/sliding windows, scans, folds, and bounded concurrent mapping with virtual threads.[11] Stream gatherers were finalized in JDK 24 by JEP 485.[12]

21. Immutable reduction with reduce

reduce combines stream elements using an associative accumulation function. Associativity is essential because parallel execution may group elements differently from sequential execution.[2]

Identity reduction

BigDecimal total =
    invoices.stream()
        .map(Invoice::amount)
        .reduce(
            BigDecimal.ZERO,
            BigDecimal::add);

Optional reduction

Optional<Order> largest =
    orders.stream()
        .reduce(
            BinaryOperator.maxBy(
                Comparator.comparing(
                    Order::total)));

Three-argument reduction

long totalBytes =
    files.parallelStream()
        .reduce(
            0L,
            (subtotal, file) ->
                subtotal + file.size(),
            Long::sum);

Broken non-associative reduction

// Sequential and parallel grouping differ.
int result =
    values.parallelStream()
        .reduce(
            0,
            (left, right) ->
                left - right);

Subtraction, string prefixing with position-dependent state, and floating-point transformations that assume one grouping are common reduction errors. Use an associative operation or keep execution sequential under an explicit contract.

22. Matching and finding

boolean hasOverdue =
    invoices.stream()
        .anyMatch(
            invoice ->
                invoice.dueDate()
                    .isBefore(today)
                && !invoice.paid());

boolean allValid =
    records.stream()
        .allMatch(
            validator::isValid);

boolean noneRejected =
    records.stream()
        .noneMatch(
            Record::rejected);

Match operations are short-circuiting. For empty streams, allMatch and noneMatch return true, while anyMatch returns false, following vacuous-truth semantics.[2]

findFirst versus findAny

Optional<Server> deterministic =
    servers.parallelStream()
        .filter(Server::healthy)
        .findFirst();

Optional<Server> fastestChoice =
    servers.parallelStream()
        .filter(Server::healthy)
        .findAny();

findFirst respects encounter order when one exists. findAny is explicitly nondeterministic and can permit greater freedom in parallel execution.

Optional result

Search and extrema operations use Optional because an empty stream has no result. Avoid immediate get(); use orElse, orElseGet, orElseThrow, ifPresent, or further transformations.[13]

23. min, max, and count

Optional<Employee> highestPaid =
    employees.stream()
        .max(
            Comparator.comparing(
                Employee::salary));
long active =
    users.stream()
        .filter(User::active)
        .count();

min and max return optionals for object streams. Primitive streams return OptionalInt, OptionalLong, or OptionalDouble. count returns a long.[2]

Count can skip traversal

long count =
    list.stream()
        .peek(
            System.out::println)
        .count();

If the source size is known and intermediate stages do not change cardinality, the implementation may compute the count without traversing elements, so the peek action might not run.[2]

24. Materialization with toList and toArray

List<CustomerId> identifiers =
    customers.stream()
        .map(Customer::id)
        .toList();

Stream.toList() returns an unmodifiable list. The implementation type and serializability are not specified, and the result can contain null elements if the stream contains them.[2]

Collectors may have different contracts

List<CustomerId> identifiers =
    customers.stream()
        .map(Customer::id)
        .collect(
            Collectors.toCollection(
                ArrayList::new));

Typed array

Customer[] array =
    customers.stream()
        .filter(Customer::active)
        .toArray(
            Customer[]::new);

Primitive array

int[] lengths =
    words.stream()
        .mapToInt(
            String::length)
        .toArray();

25. forEach, forEachOrdered, and effects

orders.stream()
    .forEach(
        order ->
            audit.write(
                order.id()));

forEach is explicitly nondeterministic for parallel streams and may invoke actions in any worker thread without respecting encounter order. If the action accesses shared state, the action must provide synchronization.[2]

Ordered effect

values.parallelStream()
    .forEachOrdered(
        System.out::println);

forEachOrdered preserves encounter order but can reduce parallel scalability by imposing ordering constraints.

Prefer returning data

A stream that computes a result is easier to test, retry, and parallelize than one that performs database writes, network calls, or mutation in each element action. Use streams to prepare commands, then execute the commands under explicit error and transaction policy.

26. The Collector model

Collector A collector is a mutable reduction described by a supplier, accumulator, combiner, optional finisher, and a set of characteristics. Parallel collection creates isolated partial containers for non-concurrent collectors and merges them after accumulation.[14]

supplier() ──► empty accumulation A │ ▼ accumulator(A, T) repeated │ parallel: combiner(A, A) │ ▼ finisher(A) ──► R
List<String> names =
    people.stream()
        .map(Person::name)
        .collect(
            Collectors.toList());

Collector functions must satisfy identity and associativity constraints so sequential and parallel evaluation are equivalent.[14]

27. Collection-producing collectors

List<String> list =
    names.stream()
        .collect(
            Collectors.toList());

Set<String> set =
    names.stream()
        .collect(
            Collectors.toSet());

TreeSet<String> sorted =
    names.stream()
        .collect(
            Collectors.toCollection(
                TreeSet::new));

List<String> unmodifiable =
    names.stream()
        .collect(

28. Map collectors and duplicate keys

Unique keys

Map<CustomerId, Customer> byId =
    customers.stream()
        .collect(
            Collectors.toMap(
                Customer::id,
                Function.identity()));

The two-argument toMap throws IllegalStateException when duplicate keys occur. A domain with possible duplicates must define an explicit merge policy.[15]

Merge duplicates

Map<String, Order> latestByNumber =
    orders.stream()
        .collect(
            Collectors.toMap(
                Order::number,
                Function.identity(),
                BinaryOperator.maxBy(
                    Comparator.comparing(
                        Order::updatedAt))));

Choose map implementation

Map<String, Product> sortedBySku =
    products.stream()
        .collect(
            Collectors.toMap(
                Product::sku,
                Function.identity(),
                (left, right) -> left,
                TreeMap::new));

Concurrent map

ConcurrentMap<String, Product> concurrent =
    products.parallelStream()
        .unordered()
        .collect(
            Collectors.toConcurrentMap(
                Product::sku,
                Function.identity(),
                (left, right) -> left));

29. Grouping and partitioning

Group by one key

Map<Department, List<Employee>>
    byDepartment =
        employees.stream()
            .collect(
                Collectors.groupingBy(
                    Employee::department));

Nested grouping

Map<Region, Map<Department,
    List<Employee>>> grouped =
        employees.stream()
            .collect(
                Collectors.groupingBy(
                    Employee::region,
                    Collectors.groupingBy(
                        Employee::department)));

Boolean partition

Map<Boolean, List<Invoice>>
    byOverdue =
        invoices.stream()
            .collect(
                Collectors.partitioningBy(
                    invoice ->
                        invoice.dueDate()
                            .isBefore(today)));

groupingBy produces a map keyed by a classifier and can cascade a downstream collector. partitioningBy always partitions on a boolean predicate and produces entries for both boolean keys.[15]

30. Downstream collectors

Count per group

Map<Status, Long> counts =
    orders.stream()
        .collect(
            Collectors.groupingBy(
                Order::status,
                Collectors.counting()));

Map values before collection

Map<Department, Set<String>>
    namesByDepartment =
        employees.stream()
            .collect(
                Collectors.groupingBy(
                    Employee::department,
                    Collectors.mapping(
                        Employee::name,
                        Collectors.toSet())));

Filter inside groups

Map<Department, Set<Employee>>
    highEarners =
        employees.stream()
            .collect(
                Collectors.groupingBy(
                    Employee::department,
                    Collectors.filtering(
                        employee ->
                            employee.salary()
                                .compareTo(limit) > 0,
                        Collectors.toSet())));

Flatten group members

Map<Team, Set<Skill>> skills =
    employees.stream()
        .collect(
            Collectors.groupingBy(
                Employee::team,
                Collectors.flatMapping(
                    employee ->
                        employee.skills()
                            .stream(),
                    Collectors.toSet())));

Downstream composition keeps classification separate from each group's reduction and avoids post-processing maps with extra mutable loops.[15]

Join text

String csv =

IntSummaryStatistics statistics =

Maximum by group

Map<Department, Optional<Employee>>
    topPaid =

Two reductions in one pass

record PriceSummary(
    long count,
    BigDecimal total) {
}

PriceSummary summary =
    orders.stream()
        .collect(
            Collectors.teeing(
                Collectors.counting(),

Collectors includes joining, counting, summing, averaging, summarizing, reducing, min/max, and teeing combinators.[15]

32. Building a custom collector

Immutable result with mutable accumulation

record ErrorSummary(
    long total,
    Map<String, Long> byCode) {
}

final class ErrorAccumulator {
    long total;
    final Map<String, Long> byCode =
        new HashMap<>();

    void add(ErrorEvent event) {
        total++;

        byCode.merge(
            event.code(),
            1L,
            Long::sum);
    }

    ErrorAccumulator combine(
            ErrorAccumulator other) {

        total += other.total;

        other.byCode.forEach(
            (code, count) ->
                byCode.merge(
                    code,
                    count,
                    Long::sum));

        return this;
    }

    ErrorSummary finish() {
        return new ErrorSummary(
            total,
            Map.copyOf(byCode));
    }
}
Collector<ErrorEvent,
    ErrorAccumulator,
    ErrorSummary> collector =
        Collector.of(
            ErrorAccumulator::new,
            ErrorAccumulator::add,
            ErrorAccumulator::combine,
            ErrorAccumulator::finish);

ErrorSummary summary =
    events.parallelStream()
        .collect(collector);

The supplier must create a fresh container, the accumulator must incorporate one input, the combiner must merge complete partial states associatively, and the finisher must not expose an unsafe mutable intermediate container.[14]

33. Collector characteristics and concurrent reduction

CharacteristicMeaning
IDENTITY_FINISHAccumulation and result types are effectively the same; finisher can be treated as identity
UNORDEREDResult equivalence does not depend on encounter order
CONCURRENTAccumulator can be called concurrently on one result container

A concurrent collector permits shared concurrent accumulation, but a concurrent reduction is performed only when the stream is unordered or the collector is also unordered. Non-concurrent collectors remain safe in parallel because each partial container is thread-confined until combination.[14]

Do not mark a collector concurrent casually

// Incorrect if ArrayList is the shared container:
Collector.of(
    ArrayList::new,
    ArrayList::add,
    (left, right) -> {
        left.addAll(right);
        return left;
    },
    Collector.Characteristics.CONCURRENT);

The accumulator container and every mutation performed on it must actually support concurrent calls before declaring CONCURRENT.

34. Primitive streams

Primitive streams IntStream, LongStream, and DoubleStream specialize pipelines for primitive values and avoid boxing each element into Integer, Long, or Double.[16][17][18]

int totalLength =
    words.stream()
        .mapToInt(
            String::length)
        .sum();

double average =
    measurements.stream()
        .mapToDouble(
            Measurement::value)
        .average()
        .orElse(
            Double.NaN);

35. Ranges, boxing, and cross-type conversion

Half-open and closed ranges

IntStream indexes =
    IntStream.range(
        0,
        values.size());

    IntStream.rangeClosed(
        1,
        10);

Index-based mapping

List<IndexedValue> indexed =
    IntStream.range(
            0,
            values.size())
        .mapToObj(index ->
            new IndexedValue(
                index,
                values.get(index)))
        .toList();

Boxing and unboxing

Stream<Integer> boxed =
    IntStream.range(0, 100)
        .boxed();

IntStream unboxed =
    boxed.mapToInt(
        Integer::intValue);

Primitive conversions

DoubleStream doubles =
    LongStream.range(
            1,
            1_000)
        .asDoubleStream();

IntStream.range excludes the upper bound, while rangeClosed includes it. Boxing is available when object APIs are needed, but repeated boxing/unboxing adds allocation and indirection.[16]

36. Numeric reductions and statistical precision

Built-in reductions

IntSummaryStatistics statistics =
    orders.stream()
        .mapToInt(
            Order::itemCount)
        .summaryStatistics();

long count =
    statistics.getCount();

int minimum =
    statistics.getMin();

int maximum =
    statistics.getMax();

long sum =
    statistics.getSum();

double average =
    statistics.getAverage();

Primitive streams provide sum, min, max, average, count, and summary-statistics terminals. Empty averages and extrema use primitive optional types.[16]

Integer overflow

// Can overflow int:
int total =
    values.sum();

// Promote before summing:
long safeTotal =
    values.mapToLong(
            Integer::longValue)
        .sum();

Floating-point grouping

double total =
    measurements.parallelStream()
        .mapToDouble(
            Measurement::value)
        .sum();

Floating-point addition is not mathematically associative. Different traversal or parallel grouping can produce small rounding differences. Use domain-specific decimal arithmetic or compensated algorithms when reproducibility or financial exactness matters.[18]

Average without a second pass

DoubleSummaryStatistics summary =
    readings.stream()
        .mapToDouble(
            Reading::value)
        .summaryStatistics();

OptionalDouble average =
    summary.getCount() == 0
        ? OptionalDouble.empty()
        : OptionalDouble.of(
            summary.getAverage());

37. How parallel streams execute

Parallel A parallel pipeline divides the source through its spliterator, evaluates partitions concurrently, and combines partial results. The Stream API originated in Java 8 as the collections bulk-data facility, with parallelism built on fork/join-style decomposition.[19]

source spliterator │ trySplit ┌────┴────┐ ▼ ▼ partition A partition B │ │ pipeline pipeline │ │ partial A partial B └────┬────┘ ▼ combine / reduce
long checksum =
    records.parallelStream()
        .filter(Record::valid)
        .mapToLong(
            Record::checksum)
        .reduce(
            0L,
            (left, right) ->
                left ^ right);

Execution mode is pipeline state

Stream<Record> stream =
    records.stream()
        .parallel()
        .filter(Record::valid)
        .sequential()
        .map(this::normalize);

boolean parallel =
    stream.isParallel();
// false: the final mode applies to the pipeline.

parallel() and sequential() change the mode of the pipeline; execution does not begin until a terminal operation.[4]

38. Encounter order and unordered()

Encounter order originates in the source: a list has index order, an array has element order, a sorted set has sorted order, and a typical hash set has no defined order. Ordered streams preserve that order where operations require it.[7]

Release unnecessary ordering

Set<String> unique =
    names.parallelStream()
        .unordered()
        .map(
            String::strip)
        .filter(
            name -> !name.isEmpty())
        .collect(
            Collectors.toSet());

unordered() does not randomly shuffle elements. It declares that downstream computation need not preserve the previous encounter-order constraint, allowing more efficient parallel implementations for operations such as distinct, grouping, and limiting.

Order-sensitive result

List<String> firstTen =
    names.parallelStream()
        .filter(
            this::acceptable)
        .limit(10)
        .toList();

For an ordered source, “first ten” is a stronger requirement than “any ten” and can require cross-partition coordination.

39. Parallel streams are not automatically faster

FactorFavors parallelismFavors sequential execution
Input sizeLargeSmall
Per-element workSubstantial CPU workCheap mapping/filtering
Source splittingBalanced array/list/rangeIterator, linked structure, sequential I/O
Stateful stagesFew and unorderedOrdered sort/distinct/limit
CombiningCheap associative reductionExpensive map/list merging
EnvironmentIdle cores availableShared saturated server

Expensive combination example

Map<CustomerId, List<Order>> grouped =
    orders.parallelStream()
        .collect(
            Collectors.groupingBy(
                Order::customerId));

Parallel groupingBy can spend substantial time merging maps and per-key lists. If result order is unnecessary and concurrent accumulation is appropriate, groupingByConcurrent can reduce combining costs, but only measurement can establish a benefit.[15]

Do not benchmark with one invocation

JIT compilation, allocation, GC, fork/join warmup, source size, and surrounding system load can dominate results. Use a proper benchmark harness and realistic application-level tests.

40. ForkJoinPool common-pool interactions

Parallel stream implementations normally execute tasks using the common ForkJoinPool in the standard JDK implementation. The common pool is process-wide and is also used by other facilities, including many asynchronous CompletableFuture operations.[20]

Blocking work can reduce shared progress

List<Profile> profiles =
    userIds.parallelStream()
        .map(
            profileClient::blockingLoad)
        .toList();

Blocking network or database calls can occupy common-pool workers, couple unrelated workloads, and create unpredictable latency. Prefer virtual-thread task execution, asynchronous APIs, or a dedicated bounded executor when work is primarily blocking.

Library design

Libraries should not silently call parallel() on caller data. Parallel policy depends on the whole application's CPU budget, workload, source characteristics, and resource isolation.

Dedicated pool caveat

try (ForkJoinPool pool =
        new ForkJoinPool(8)) {

    Result result =
        pool.submit(() ->
                values.parallelStream()
                    .map(this::compute)
                    .reduce(
                        identity,
                        this::combine))
            .join();
}

Current JDK behavior commonly uses the invoking fork/join pool for a nested parallel pipeline, but code needing durable, explicit execution control should use fork/join tasks or another concurrency abstraction directly rather than relying on incidental implementation behavior.

41. Side effects, shared state, and visibility

Unsafe accumulator

int[] total = {0};

values.parallelStream()
    .forEach(
        value ->
            total[0] += value);

Correct reduction

int total =
    values.parallelStream()
        .mapToInt(
            Integer::intValue)
        .sum();

Concurrent side effect does not guarantee useful ordering

ConcurrentLinkedQueue<String> queue =
    new ConcurrentLinkedQueue<>();

names.parallelStream()
    .forEach(
        queue::add);

This avoids structural corruption but the resulting order is not guaranteed by forEach. Thread safety is only one aspect of semantic correctness.

Stateful lambda

AtomicInteger index =
    new AtomicInteger();

List<IndexedValue> indexed =
    values.parallelStream()
        .map(value ->
            new IndexedValue(
                index.getAndIncrement(),
                value))
        .toList();

The indices depend on scheduling, not encounter order. Use IntStream.range over an indexed source or collect sequentially when stable positions matter.

42. Exceptions, checked failures, and null elements

Checked exceptions need an explicit boundary

static String readUnchecked(
        Path path) {

    try {
        return Files.readString(
            path,
            StandardCharsets.UTF_8);
    } catch (IOException failure) {
        throw new UncheckedIOException(
            failure);
    }
}

List<String> contents =
    paths.stream()
        .map(
            StreamGuide::readUnchecked)
        .toList();

Prefer result values when partial failure is expected

sealed interface ReadResult {
    record Success(
        Path path,
        String content)
        implements ReadResult {
    }

    record Failure(
        Path path,
        IOException cause)
        implements ReadResult {
    }
}
List<ReadResult> results =
    paths.stream()
        .map(
            this::tryRead)
        .toList();

Null handling

List<String> normalized =
    values.stream()
        .filter(
            Objects::nonNull)
        .map(
            String::strip)
        .toList();

Many stream operations can carry null object elements, but operations such as sorting, method references, findFirst/optional-producing terminals, and unmodifiable collectors can reject or fail on nulls. Prefer null-free domain collections and use Optional for optional single values.

Parallel failure

When one parallel task fails, other partitions may already have executed effects. A thrown exception does not roll back side effects. Keep parallel functions pure or make effects idempotent and transactionally controlled.

44. Performance engineering and JMH

Use JMH for microbenchmarks of stream pipelines. It handles warmup, forks, iteration control, dead-code elimination hazards, and result consumption more reliably than ad hoc System.nanoTime() loops.[21]

Benchmark stream versus loop

@State(Scope.Thread)
public class SumBenchmark {
    int[] values =
        IntStream.range(
                0,
                1_000_000)
            .toArray();

    @Benchmark
    public long streamSum() {
        return Arrays.stream(values)
            .mapToLong(
                value ->
                    (long) value * value)
            .sum();
    }

    @Benchmark
    public long loopSum() {
        long result = 0;

        for (int value : values) {
            result +=
                (long) value * value;
        }

        return result;
    }
}

Optimization guidelines

  • Use primitive streams for numeric hot paths.
  • Filter before expensive mapping or sorting when semantics permit.
  • Avoid repeated boxing, nested tiny streams, and accidental materialization.
  • Prefer mapMulti when each input emits a few outputs.
  • Do not parallelize small or cheaply processed collections.
  • Use source-level filtering and aggregation for databases and remote systems.
  • Measure collector combination costs.

Loops remain valid

A loop can be clearer and faster for index-sensitive algorithms, early multi-level exits, complex exception handling, mutable state machines, and very small hot operations. The Stream API is not a replacement for every loop.

45. Complete example: sales analytics pipeline

Domain model

record Sale(
    String region,
    String product,
    int quantity,
    BigDecimal unitPrice,
    Instant occurredAt) {

    BigDecimal revenue() {
        return unitPrice.multiply(
            BigDecimal.valueOf(
                quantity));
    }
}

record ProductSummary(
    long transactions,
    long units,
    BigDecimal revenue) {
}

Custom downstream collector

final class ProductAccumulator {
    long transactions;
    long units;
    BigDecimal revenue =
        BigDecimal.ZERO;

    void add(Sale sale) {
        transactions++;
        units += sale.quantity();
        revenue =
            revenue.add(
                sale.revenue());
    }

    ProductAccumulator combine(
            ProductAccumulator other) {

        transactions +=
            other.transactions;

        units +=
            other.units;

        revenue =
            revenue.add(
                other.revenue);

        return this;
    }

    ProductSummary finish() {
        return new ProductSummary(
            transactions,
            units,
            revenue);
    }
}

static Collector<Sale,
    ProductAccumulator,
    ProductSummary>
productSummaryCollector() {

    return Collector.of(
        ProductAccumulator::new,
        ProductAccumulator::add,
        ProductAccumulator::combine,
        ProductAccumulator::finish);
}

Analysis

static Map<String,
    Map<String, ProductSummary>>
summarizeSales(
        Stream<Sale> sales,
        Instant startInclusive,
        Instant endExclusive) {

    return sales
        .filter(sale ->
            !sale.occurredAt()
                .isBefore(startInclusive))
        .filter(sale ->
            sale.occurredAt()
                .isBefore(endExclusive))
        .filter(sale ->
            sale.quantity() > 0)
        .collect(
            Collectors.groupingBy(
                Sale::region,
                TreeMap::new,
                Collectors.groupingBy(
                    Sale::product,
                    TreeMap::new,
                    productSummaryCollector())));
}

File-backed execution

try (Stream<String> lines =
        Files.lines(
            csvPath,
            StandardCharsets.UTF_8)) {

    Map<String,
        Map<String, ProductSummary>>
        report =
            summarizeSales(
                lines.skip(1)
                    .map(
                        SalesCsv::parse),
                start,
                end);

    publish(report);
}

Design properties

  • The input stream is owned and closed by the caller.
  • Parsing is separated from aggregation.
  • Time boundaries are half-open.
  • The collector is associative and creates isolated partial state.
  • Tree maps make output ordering explicit.
  • The same pipeline can be tested sequentially and in parallel.

46. Production checklist

Pipeline semantics

  • The source, transformation, and result are clearer than an equivalent loop.
  • Every stream has exactly one terminal operation.
  • Resource-backed streams are closed with try-with-resources.
  • Behavioral parameters are non-interfering and stateless.
  • Required effects are not hidden in peek.

Intermediate operations

  • Cheap cardinality-reducing filters appear early when legal.
  • Stateful operations have bounded memory requirements.
  • Infinite streams are bounded by short-circuiting operations.
  • flatMap, mapMulti, and gatherers are selected by cardinality and state needs.
  • Ordering requirements are explicit.

Terminal operations and collectors

  • Reduction operations are associative and have correct identities.
  • Duplicate map keys have an explicit merge policy.
  • Result mutability and implementation requirements are explicit.
  • Custom collectors satisfy identity, associativity, confinement, and finishing rules.
  • Concurrent collector characteristics match the actual container.

Primitive streams

  • Numeric pipelines avoid unnecessary boxing.
  • Integer overflow is considered.
  • Floating-point tolerance and reproducibility are specified.
  • Empty extrema and averages are handled through optionals.

Parallel execution

  • Parallelism is enabled only after representative measurement.
  • The source splits efficiently and per-element work is substantial.
  • Stateful ordered stages and expensive combining are accounted for.
  • Blocking I/O is not placed casually in common-pool parallel pipelines.
  • Functions are pure or side effects are safe, idempotent, and order-independent.
  • Libraries do not silently impose parallel policy.

Testing and operation

  • Empty, duplicate, null, ordered, unordered, and failure cases are tested.
  • Sequential and parallel results are compared for custom reductions.
  • Resource closure is tested.
  • Performance claims use JMH or end-to-end load tests.
  • Loops are retained where they are clearer or more efficient.
Final principle: a stream pipeline is a declarative query over a source. Correctness comes from pure transformations, explicit ordering, associative reductions, bounded state, and well-owned resources; speed comes only when the source, workload, and execution mode align.
