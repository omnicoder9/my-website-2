1. The Java data-access landscape

Java database code sits between two independent models: Java objects and SQL database state. Correctness depends on preserving SQL semantics—transactions, constraints, nulls, types, ordering, isolation, and set-oriented operations—while managing Java resource lifecycles and object identity.

JDBC

A standard, low-level API for connections, SQL statements, parameters, result sets, metadata, transactions, and vendor drivers.

DataSource and pooling

A factory abstraction for connections, usually backed by a bounded pool in servers and long-running applications.

ORM / Jakarta Persistence

Maps domain classes and relationships to relational tables and coordinates entity lifecycle, identity, queries, dirty checking, locking, and caches.

Database-native behavior

SQL dialect, indexes, constraints, query plans, isolation, locking, replication, and server-specific types remain decisive even behind an ORM.

The JDBC 4.3 API consists of the core java.sql package and the server-side/data-source facilities in javax.sql. It includes driver discovery, connections, statements, prepared and callable statements, result sets, metadata, savepoints, batch updates, large update counts, and sharding-related APIs.[1]

An ORM does not eliminate SQL. It generates and executes SQL, so schema design, query shape, indexes, transaction boundaries, and database diagnostics remain part of application design.

2. Historical development

1997: JDBC 1.0 standardized Java access to relational databases through drivers, connections, statements, and result sets.

JDBC 2.x: Added data sources, pooling interfaces, distributed transactions, scrollable/updatable result sets, and batch updates.

JDBC 3.0: Added savepoints, generated keys, parameter metadata, pooled statements, and result-set holdability.[1]

JDBC 4.0: Added service-provider driver discovery, richer SQLException types, SQL XML, ROWID, and wrapper APIs.[1]

JDBC 4.1–4.3: Added try-with-resources compatibility, typed getObject, schema and network timeout APIs, large update counts, SQLType, request boundaries, and sharding hints.[1]

2006 onward: The Java Persistence API standardized ORM concepts first under Java EE and now as Jakarta Persistence. Version 3.2 is the Jakarta EE 11 generation used in this guide.[19]

DataSource for applications

DataSource is the preferred connection-factory abstraction. It permits pooling, naming-service integration, wrappers, and configuration without coupling application code to DriverManager or a concrete driver.[7]

public final class JdbcOrderRepository {
    private final DataSource dataSource;

    public JdbcOrderRepository(
            DataSource dataSource) {
        this.dataSource =
            Objects.requireNonNull(dataSource);
    }

    public Optional<OrderRecord> find(
            UUID id)
            throws SQLException {

        try (Connection connection =
                dataSource.getConnection()) {

            return find(connection, id);
        }
    }
}
Acquire late, release early. A pooled connection is a scarce concurrency permit. Do not hold it while performing unrelated HTTP calls, waiting on user input, or doing CPU-heavy transformation.

7. Connection pooling

DataSource Opening a physical database connection may require DNS, TCP, TLS, authentication, and server-session setup. A pool retains physical connections and returns logical wrappers whose close() normally returns the connection to the pool rather than closing the socket.[8]

HikariCP exposes JDBC DataSource behavior and configurable acquisition timeout, pool size, lifetime, idle, and keepalive policies. Its project documentation warns that database connections should not simply be maximized and that network keepalive configuration matters for connection reliability.[11]

Pool-size reasoning

  • Bound the pool below the database's safe session capacity.
  • Account for every application replica, migration job, administrative tool, and background worker.
  • Measure connection wait time, active/idle counts, timeout rate, transaction duration, and database saturation.
  • A larger pool can increase lock contention, memory, and context switching while reducing throughput.
  • Set acquisition timeout below the request deadline so failures are controlled rather than cascading.

Reset connection state

Pool implementations must restore relevant connection state—auto-commit, isolation, read-only, catalog, schema, and warnings—before reuse. Application code should still restore any changed state or use one well-defined transaction helper.

8. Resource lifecycle and try-with-resources

Connection, Statement, and ResultSet implement AutoCloseable. Try-with-resources closes them in reverse declaration order even when an exception occurs.[1][9]

private Optional<OrderRecord> find(
        Connection connection,
        UUID id)
        throws SQLException {

    String sql = """
        select
            id,
            customer_id,
            status,
            total_amount,
            currency,
            version,
            created_at,
            confirmed_at
        from customer_order
        where id = ?
        """;

    try (PreparedStatement statement =
            connection.prepareStatement(sql)) {

        statement.setObject(
            1,
            id,
            JDBCType.OTHER);

        try (ResultSet results =
                statement.executeQuery()) {

            if (!results.next()) {
                return Optional.empty();
            }

            OrderRecord order =
                mapOrder(results);

            if (results.next()) {
                throw new SQLException(
                    "Primary-key query returned "
                        + "multiple rows");
            }

            return Optional.of(order);
        }
    }
}

Do not return a live ResultSet

A result set depends on its statement and connection. Map rows inside the resource scope and return immutable domain or DTO values. Streaming abstractions must own and close their database resources explicitly.

10. PreparedStatement

Security PreparedStatement represents parameterized SQL with ? placeholders. Values are bound through typed setter methods rather than embedded into SQL text. A driver may precompile the statement immediately or defer preparation until execution.[13]

Insert with typed parameters

private static final String INSERT_ORDER = """
    insert into customer_order (
        id,
        customer_id,
        status,
        total_amount,
        currency,
        version,
        created_at,
        confirmed_at
    )
    values (?, ?, ?, ?, ?, ?, ?, ?)
    """;

public void insert(
        Connection connection,
        OrderRecord order)
        throws SQLException {

    try (PreparedStatement statement =
            connection.prepareStatement(
                INSERT_ORDER)) {

        statement.setObject(
            1,
            order.id());

        statement.setString(
            2,
            order.customerId());

        statement.setString(
            3,
            order.status().name());

        statement.setBigDecimal(
            4,
            order.totalAmount());

        statement.setString(
            5,
            order.currency());

        statement.setLong(
            6,
            order.version());

        statement.setObject(
            7,
            order.createdAt());

        if (order.confirmedAt() == null) {
            statement.setNull(
                8,
                Types.TIMESTAMP_WITH_TIMEZONE);
        } else {
            statement.setObject(
                8,
                order.confirmedAt());
        }

        int changed =
            statement.executeUpdate();

        if (changed != 1) {
            throw new SQLException(
                "Expected one inserted row, got "
                    + changed);
        }
    }
}

Typed setters should be compatible with the SQL parameter type. Where conversion is necessary, setObject accepts a target SQLType; explicit setNull is the most portable way to send SQL NULL.[13]

Identifiers cannot be parameters

// Invalid concept: '?' is a value placeholder, not an identifier.
select * from ? order by ?

// Whitelist structural SQL instead.
String orderBy =
    switch (sort) {
        case CREATED_ASC -> "created_at asc";
        case CREATED_DESC -> "created_at desc";
        case TOTAL_DESC -> "total_amount desc";
    };

String sql = """
    select id, customer_id, total_amount
    from customer_order
    where customer_id = ?
    order by %s
    limit ?
    """.formatted(orderBy);

Table names, column names, operators, and sort directions are SQL structure, not parameter data. Choose them from a fixed allowlist or a query builder; never insert arbitrary request strings.

Driver-side preparation

pgJDBC uses the extended query protocol for prepared statements and can promote frequently executed statements to named server-prepared statements after a configurable threshold. Prepared-statement caches consume memory per connection, so configuration must reflect query diversity and pool size.[14]

11. ResultSet mapping

A ResultSet cursor initially points before the first row. next() advances it and reports whether a row exists. Column values may be retrieved by index or label; labels are generally clearer and less fragile when projections change.[15]

public record OrderRecord(
        UUID id,
        String customerId,
        OrderStatus status,
        BigDecimal totalAmount,
        String currency,
        long version,
        OffsetDateTime createdAt,
        OffsetDateTime confirmedAt) {
}

private static OrderRecord mapOrder(
        ResultSet results)
        throws SQLException {

    return new OrderRecord(
        results.getObject(
            "id",
            UUID.class),

        results.getString(
            "customer_id"),

        OrderStatus.valueOf(
            results.getString(
                "status")),

        results.getBigDecimal(
            "total_amount"),

        results.getString(
            "currency"),

        results.getLong(
            "version"),

        results.getObject(
            "created_at",
            OffsetDateTime.class),

        results.getObject(
            "confirmed_at",
            OffsetDateTime.class));
}

12. SQL NULL and type handling

Primitive getters such as getInt and getLong return zero when the SQL value is NULL; call wasNull() immediately afterward to distinguish NULL from a real zero. Typed getObject(label, Class) can return a nullable wrapper or temporal type when supported.[15]

long rawValue =
    results.getLong("retry_count");

Integer retryCount =
    results.wasNull()
        ? null
        : Math.toIntExact(rawValue);

// Often clearer:
Integer typedRetryCount =
    results.getObject(
        "retry_count",
        Integer.class);

Temporal values

OffsetDateTime createdAt =
    results.getObject(
        "created_at",
        OffsetDateTime.class);

LocalDate businessDate =
    results.getObject(
        "business_date",
        LocalDate.class);

JDBC 4.2 added standard mappings for java.time through typed setObject and getObject, but exact database mappings and time-zone semantics depend on the SQL type and driver.[1]

Money

Use BigDecimal for exact decimal columns. Define scale and rounding in the domain and schema rather than relying on implicit conversion.

BigDecimal total =

        .setScale(
            4,
            RoundingMode.UNNECESSARY);

Enums

Mapping an enum by textual name is usually more stable than persisting ordinal position. Reject unknown values explicitly so schema and application drift is visible.

13. Generated keys

JDBC can request automatically generated columns when preparing or executing an insert. Support and the set of statements that return keys are database-specific.[6]

String sql = """
    insert into shipment (
        order_id,
        created_at
    )
    values (?, ?)
    """;

try (PreparedStatement statement =
        connection.prepareStatement(
            sql,
            new String[] {"id"})) {

    statement.setObject(1, orderId);
    statement.setObject(
        2,
        OffsetDateTime.now(clock));

    int changed =
        statement.executeUpdate();

    if (changed != 1) {
        throw new SQLException(
            "Expected one row");
    }

    try (ResultSet keys =
            statement.getGeneratedKeys()) {

        if (!keys.next()) {
            throw new SQLException(
                "No generated shipment ID");
        }

        long shipmentId =
            keys.getLong(1);
    }
}

Application-generated UUIDs can simplify idempotency and allow related rows to be constructed before the insert, while database-generated identity or sequence values centralize key generation. Choose based on storage, ordering, replication, and domain requirements.

15. Local JDBC transactions

Transactions Auto-commit is enabled by default, so each statement commits as an individual transaction when it completes. Disable auto-commit to group statements into one atomic unit and call commit() or rollback() explicitly.[6]

public <T> T inTransaction(
        SqlWork<T> work)
        throws SQLException {

    try (Connection connection =
            dataSource.getConnection()) {

        boolean previousAutoCommit =
            connection.getAutoCommit();

        int previousIsolation =
            connection.getTransactionIsolation();

        boolean previousReadOnly =
            connection.isReadOnly();

        try {
            connection.setAutoCommit(false);
            connection.setReadOnly(false);
            connection.setTransactionIsolation(
                Connection.TRANSACTION_READ_COMMITTED);

            T result =
                work.execute(connection);

            connection.commit();
            return result;
        } catch (Throwable failure) {
            try {
                connection.rollback();
            } catch (SQLException rollbackFailure) {
                failure.addSuppressed(
                    rollbackFailure);
            }

            if (failure instanceof SQLException sql) {
                throw sql;
            }

            if (failure instanceof RuntimeException runtime) {
                throw runtime;
            }

            throw new SQLException(
                "Transactional work failed",
                failure);
        } finally {
            try {
                connection.setReadOnly(
                    previousReadOnly);
                connection.setTransactionIsolation(
                    previousIsolation);
                connection.setAutoCommit(
                    previousAutoCommit);
            } catch (SQLException resetFailure) {
                // A pool should evict a connection that
                // cannot be safely reset.
                connection.abort(
                    Runnable::run);
            }
        }
    }
}

@FunctionalInterface
public interface SqlWork<T> {
    T execute(Connection connection)
        throws Exception;
}

Transaction boundary

OrderResult result =
    transactions.inTransaction(connection -> {
        OrderRecord order =
            orders.require(
                connection,
                orderId);

        reservations.reserve(
            connection,
            order);

        orders.confirm(
            connection,

        return OrderResult.confirmed(

Keep the transaction aligned with one consistency boundary. The outbox row is inserted in the same transaction as the domain state, allowing a separate relay to publish after commit without attempting an unsafe database-plus-broker dual write.

16. Isolation levels and concurrency anomalies

JDBC defines constants for READ_UNCOMMITTED, READ_COMMITTED, REPEATABLE_READ, and SERIALIZABLE, plus TRANSACTION_NONE. Database implementations may provide stronger behavior, map one level to another, or reject unsupported levels.[6]

LevelConceptual protectionTypical trade-off
READ UNCOMMITTEDWeakest standard level; may permit dirty readsRarely useful for transactional application logic
READ COMMITTEDEach statement sees committed data according to database rulesRepeated reads may observe change
REPEATABLE READStronger stable-read behaviorMore conflicts or retained versions/locks
SERIALIZABLEOutcome equivalent to some serial executionTransactions may abort and require retry
connection.setAutoCommit(false);
connection.setTransactionIsolation(
    Connection.TRANSACTION_SERIALIZABLE);

try {
    executeBusinessTransaction(connection);
    connection.commit();
} catch (SQLException failure) {
    connection.rollback();
    throw failure;
}

PostgreSQL documents the standard isolation levels and states that serialization failures require aborting and retrying the whole transaction from the beginning.[17]

Isolation does not replace constraints

Use unique constraints and atomic conditional updates for invariants. “Check then insert” at a weak isolation level is vulnerable to a concurrent writer unless protected by a constraint, lock, or serializable transaction.

update customer_order
set
    status = 'CONFIRMED',
    confirmed_at = ?,
    version = version + 1
where id = ?
  and status = 'PENDING'
  and version = ?

Checking the update count makes the expected state and version part of one atomic database operation.

17. Savepoints

A savepoint marks a point within a transaction to which the application may roll back without necessarily aborting the entire transaction. Savepoints require auto-commit to be disabled and driver/database support.[18]

connection.setAutoCommit(false);

try {
    insertOrder(connection, order);

    Savepoint beforeOptionalAudit =
        connection.setSavepoint(
            "before_optional_audit");

    try {
        insertDetailedAudit(
            connection,
            order);
    } catch (SQLException auditFailure) {
        connection.rollback(
            beforeOptionalAudit);

        insertMinimalAudit(
            connection,
            order,
            auditFailure.getSQLState());
    } finally {
        connection.releaseSavepoint(
            beforeOptionalAudit);
    }

    connection.commit();
} catch (SQLException failure) {
    connection.rollback();
    throw failure;
}
Savepoints are not nested independent transactions. A final rollback still undoes work before and after the savepoint, and external side effects cannot be rolled back by JDBC.

18. SQL failures, classification, and retry

Retry whole transactions

public <T> T serializable(
        int maximumAttempts,
        SqlWork<T> work)
        throws SQLException {

    SQLException last = null;

    for (int attempt = 1;
            attempt <= maximumAttempts;
            attempt++) {

        try {
            return executeSerializable(work);
        } catch (SQLException failure) {
            last = failure;

            if (!isRetryableTransactionFailure(
                    failure)
                    || attempt == maximumAttempts) {
                throw failure;
            }

            sleepWithJitter(attempt);
        }
    }

    throw last;
}

Retry rules

  • Retry the complete transaction with a new connection or clean transaction state.
  • Only retry errors documented as transient by the target database/driver.
  • Make operations idempotent or use stable command IDs.
  • Bound attempts and total deadline; add jitter.
  • Do not blindly retry syntax errors, constraint violations, authentication failures, or unknown commit outcomes.
  • After a connection failure during commit, the outcome may be ambiguous; reconcile by idempotency key or durable operation status.

19. Batch operations

Batching JDBC batch APIs send multiple update commands or parameter sets through one statement. They can reduce network round trips and allow driver/database optimizations. A batch is not inherently atomic; transaction handling determines atomicity.[1][12]

Prepared batch insert

public void insertItems(
        Connection connection,
        UUID orderId,
        List<OrderItemRecord> items)
        throws SQLException {

    String sql = """
        insert into order_item (
            order_id,
            line_number,
            sku,
            quantity,
            unit_price
        )
        values (?, ?, ?, ?, ?)
        """;

    try (PreparedStatement statement =
            connection.prepareStatement(sql)) {

        int pending = 0;

        for (OrderItemRecord item : items) {
            statement.setObject(
                1,
                orderId);

            statement.setInt(
                2,
                item.lineNumber());

            statement.setString(
                3,
                item.sku());

            statement.setInt(
                4,
                item.quantity());

            statement.setBigDecimal(
                5,
                item.unitPrice());

            statement.addBatch();
            pending++;

            if (pending == 500) {
                verifyBatch(
                    statement.executeBatch());
                pending = 0;
            }
        }

        if (pending > 0) {
            verifyBatch(
                statement.executeBatch());
        }
    }
}

private static void verifyBatch(
        int[] counts)
        throws SQLException {

    for (int count : counts) {
        if (count == Statement.EXECUTE_FAILED) {
            throw new SQLException(
                "Batch element failed");
        }
    }
}

Large batch counts

executeLargeBatch() returns long[] for update counts that may exceed integer range.[12]

Partial failure

BatchUpdateException carries update counts for commands processed before or around the failure. Drivers may stop at the first error or continue. If the batch must be all-or-nothing, execute it inside a transaction and roll back on any failure.[1]

try {
    long[] counts =
        statement.executeLargeBatch();

    verifyLargeBatch(counts);
} catch (BatchUpdateException failure) {
    connection.rollback();

    long[] counts =
        failure.getLargeUpdateCounts();

    throw new BatchPersistenceFailure(
        counts,
        failure);
}

Batch size

Choose batch size by measurement. Very small batches leave round-trip savings unused; very large batches consume memory, create long transactions, hold locks longer, and complicate failure diagnosis.

A repository should expose domain-oriented persistence operations while keeping SQL, row mapping, and JDBC resources internal. Transaction ownership belongs above repositories when one use case spans several repositories.

public boolean confirm(
        Connection connection,
        UUID id,
        long expectedVersion,
        OffsetDateTime confirmedAt)
        throws SQLException {

    String sql = """
        update customer_order
        set
            status = 'CONFIRMED',
            confirmed_at = ?,
            version = version + 1
        where id = ?
          and status = 'PENDING'
          and version = ?
        """;

    try (PreparedStatement statement =
            connection.prepareStatement(sql)) {

        statement.setObject(
            1,
            confirmedAt);

        statement.setObject(
            2,
            id);

        statement.setLong(
            3,
            expectedVersion);

        return statement.executeUpdate() == 1;
    }
}

Do not hide transaction scope

A repository method that silently opens and commits its own connection prevents atomic composition with other repository calls. Offer connection-accepting internal methods or execute repositories within a container-managed transaction.

Cascade versus database cascade

  • ORM cascade controls propagation of entity operations such as persist, merge, remove, refresh, and detach.
  • Database ON DELETE CASCADE controls referential actions in SQL.
  • They are independent and must be designed together.
  • CascadeType.REMOVE on broad many-to-many relationships can delete shared entities and is usually inappropriate.

Fetch type is not a query plan

Lazy or eager mapping is a default contract, not a complete use-case query. Use query-specific fetch joins, entity graphs, or projections so each transaction loads the graph it requires.

28. Dirty checking and flush

Flush synchronizes persistence-context changes with the database by generating SQL INSERT, UPDATE, and DELETE statements. Hibernate describes the persistence context as a transactional write-behind cache.[23][30]

transaction.begin();

OrderEntity order =
    entityManager.find(
        OrderEntity.class,
        orderId);

order.confirm(
    OffsetDateTime.now(clock));

// No explicit update call.
// Provider detects managed-state change.

entityManager.flush();

// SQL has been sent, but the transaction
// has not necessarily committed.
transaction.commit();

Flush is not commit

A successful flush does not make the transaction durable. A later statement or commit can still fail, and rollback undoes the flushed database changes.

Flush modes

  • AUTO permits the provider to flush before queries when needed for correct results and at commit.
  • COMMIT defers synchronization toward commit, but query visibility details must follow specification/provider rules.
  • Explicit flush() is useful for early constraint detection or bounded batch processing.

Bulk DML bypasses managed state

int changed =

31. Persistence context / first-level cache

Cache Every EntityManager has a persistence context that acts as an identity map and first-level cache. It is mandatory and cannot be disabled for a stateful entity manager.[19][30]

Benefits

  • One managed instance per entity identity within the context.
  • Repeated find can avoid a database lookup when the entity is already managed.
  • Dirty checking compares managed state and produces updates.
  • Associations can point to consistent managed instances.

Memory risk in bulk work

transaction.begin();

for (int index = 0;
        index < orders.size();
        index++) {

    entityManager.persist(
        orders.get(index));

    if (index > 0
            && index % 50 == 0) {

        entityManager.flush();
        entityManager.clear();
    }
}

transaction.commit();

Managed entities remain reachable from the persistence context until it is cleared or closed. Large loops should periodically flush and clear, or use bulk SQL/StatelessSession when entity lifecycle behavior is unnecessary.[28]

Staleness

If another transaction modifies a row, an already-managed entity does not automatically refresh. Use transaction boundaries, refresh, lock modes, or cache bypass options when current database state is required.

33. Query cache

Hibernate's query cache is separate from the second-level entity cache. It typically caches query result identifiers or scalar results, not complete managed object graphs. It is disabled by default and should be enabled only for specific stable, repeatedly executed queries.[30]

    entityManager.createQuery("""
        select o
        from CustomerOrder o
        where o.status = :status
        order by o.createdAt
        """, OrderEntity.class)

            OrderStatus.PENDING)

Risks

  • High-cardinality parameters create many low-reuse cache entries.
  • Frequent writes invalidate result regions.
  • Identifier hits still require entity-cache or database lookups.
  • Pagination and ordering increase key diversity.
  • Cached query results can become an expensive coordination mechanism in a cluster.

Measure hit rate, miss cost, invalidation rate, memory, and end-to-end latency. A database index or query rewrite is often more reliable than a query cache.

  • Can stale data cause money loss, authorization failure, or overselling?
  • How is cache consistency tested during rolling deployment?
Never add a cache without a stale-data policy. A cache hit is only valuable if returning that version of the data is correct enough for the use case.

35. Batching with ORM

Hibernate can group entity INSERT, UPDATE, and DELETE statements into JDBC batches. Effective batching depends on identifier generation, SQL shape, flush boundaries, and provider configuration.[30]

Map<String, Object> properties =
    Map.of(
        "hibernate.jdbc.batch_size",
        50,
        "hibernate.order_inserts",
        true,
        "hibernate.order_updates",
        true,
        "hibernate.jdbc.batch_versioned_data",
        true);

Batch persist loop

transaction.begin();

for (int index = 0;
        index < commands.size();
        index++) {

    entityManager.persist(
        map(commands.get(index)));

    if ((index + 1) % 50 == 0) {
        entityManager.flush();
        entityManager.clear();
    }
}

transaction.commit();

Identity generation caveat

Some identity-column strategies require executing each insert immediately to obtain its generated identifier and may inhibit batching. Sequences, pooled optimizers, or application-generated identifiers can offer better batching, depending on database/provider support.

Verify generated SQL

Enable bounded SQL/batch diagnostics in a non-production or controlled environment and inspect network round trips, prepared-statement reuse, update counts, and transaction duration. Hibernate documents a dedicated batch logging category for verification.[28]

37. Performance and observability

Measure at every layer

  • Pool acquisition wait and timeout.
  • Transaction duration and rollback rate.
  • Statement count per request.
  • Query latency distribution and rows returned/changed.
  • Database CPU, I/O, locks, deadlocks, temp files, and connection count.
  • ORM flush time, entity load count, collection fetches, and cache hit/miss rate.
  • Result-set and object allocation for large reads.

Query timeout

try (PreparedStatement statement =
        connection.prepareStatement(sql)) {

    statement.setQueryTimeout(5);

    try (ResultSet results =
            statement.executeQuery()) {
        // ...
    }
}

JDBC query timeout asks the driver to cancel after a number of seconds and may throw SQLTimeoutException. Cancellation behavior depends on driver and server support; also enforce request deadlines and database-side statement timeouts.[12]

Network timeout

connection.setNetworkTimeout(
    networkTimeoutExecutor,
    10_000);

Connection.setNetworkTimeout bounds waits for database replies at the connection level. It is distinct from connection acquisition and statement execution timeout.[6]

Explain plans

explain (analyze, buffers, format json)
select
    id,
    customer_id,
    total_amount
from customer_order
where customer_id = ?
order by created_at desc
limit 100;

Use representative parameter values and production-like statistics. An ORM-generated query should be copied with bound values into database diagnostics to inspect its actual plan.

Avoid common performance failures

  • N+1 lazy loading.
  • Unbounded result sets.
  • Long transactions holding connections and locks.
  • Missing or misordered indexes.
  • Overwide entity loads for read-only projections.
  • Flush inside tight loops without batching.
  • Oversized pools overwhelming the database.
  • Caching low-reuse, rapidly changing data.

39. Database security

Security Prepared statements separate SQL code from values and are the primary defense against SQL injection in data parameters. Structural SQL still requires allowlisting or a safe query builder.

Least privilege

  • Use a dedicated application database role.
  • Grant only required tables, views, sequences, and procedures.
  • Separate migration credentials from runtime credentials.
  • Restrict destructive administration to controlled jobs.
  • Rotate credentials and avoid storing them in source or JDBC URLs.

TLS and authentication

jdbc:postgresql://db.example.com:5432/orders\
?sslmode=verify-full\
&ApplicationName=orders-service

Validate the server certificate and host identity. Database-specific SSL properties must be taken from current driver documentation; insecure modes can encrypt traffic without authenticating the server.[31]

Safe logging

  • Do not log connection passwords, access tokens, or full URLs containing secrets.
  • Log parameterized query names or fingerprints rather than sensitive parameter values.
  • Redact personal and financial data.
  • Record SQLState, vendor code, operation, and correlation ID for failures.

Driver updates

JDBC drivers parse server messages, implement authentication, and handle TLS. Track vendor security advisories and update promptly; pgJDBC maintains a dedicated security page and release channel.[32]

40. Schema migration discipline

Versioned migrations

db/migration/
├── V001__create_orders.sql
├── V002__add_order_version.sql
├── V003__create_order_items.sql
└── V004__add_customer_created_index.sql

Expand and contract

  1. Add new nullable column/table/index compatible with old code.
  2. Deploy code that writes both old and new forms where needed.
  3. Backfill in bounded batches.
  4. Deploy code that reads the new form.
  5. Enforce new constraints after data is valid.
  6. Remove the old representation in a later release.

Do not rely on automatic destructive schema update

ORM schema generation is useful for tests, prototypes, and validation, but production changes need reviewable ordering, data migration, locking analysis, rollback/forward-fix strategy, and operational monitoring.

Index creation

Adding an index can consume I/O, CPU, disk, and locks. Use the database's online/concurrent facilities where appropriate and understand their transactional restrictions.

41. Production checklist

Drivers and connections

  • Driver version is current, pinned, and security-reviewed.
  • DataSource is injected rather than global DriverManager use.
  • Pool size respects database capacity across all replicas.
  • Acquisition, validation, lifetime, and network timeouts are explicit.
  • Connections, statements, and result sets use try-with-resources.

SQL and mapping

  • All data parameters use PreparedStatement.
  • Dynamic identifiers and ordering use allowlists.
  • Queries select explicit columns.
  • NULL, decimal, enum, and temporal semantics are tested.
  • Update counts and generated keys are validated.
  • Large reads use bounded pagination or verified streaming.

Transactions

  • Auto-commit behavior is intentional.
  • Transaction boundary matches one consistency unit.
  • Remote calls do not occur while holding database locks.
  • Isolation level is chosen from anomaly requirements.
  • Retries are limited to classified transient failures and rerun the whole transaction.
  • Unknown commit outcomes use idempotency/reconciliation.

Batching

  • Batch size is measured and bounded.
  • Batch failure rolls back when atomicity is required.
  • ORM identifier strategy permits batching.
  • Persistence context is flushed and cleared during large entity loops.

ORM

  • Entity identity, equality, and no-arg constructor rules are satisfied.
  • Relationships have explicit ownership and helper methods.
  • Fetch plans are use-case-specific.
  • Optimistic versioning protects concurrent updates.
  • Bulk DML is followed by context clear/refresh.
  • DTO projections are used for wide read-only queries.

Caching

  • First-level cache lifetime is bounded by transaction/context scope.
  • Second-level cached entities are selected deliberately.
  • External writers participate in invalidation or caching is avoided.
  • Query cache is enabled only for measured high-reuse queries.
  • Hit, miss, eviction, stale-read, and memory metrics are monitored.

Operations and security

  • Database constraints enforce invariants.
  • Application and migration roles use least privilege.
  • TLS verifies the server identity.
  • Secrets and sensitive parameters are not logged.
  • Schema migrations are versioned and tested from the previous release.
  • Database plans, locks, pool metrics, and transaction latency are observable.
Final principle: database programming is transaction and data-model programming first, API programming second. JDBC gives precise control; ORM coordinates object lifecycle and mapping. Both succeed only when SQL, constraints, isolation, resource ownership, and cache staleness are explicit.
