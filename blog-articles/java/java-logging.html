1. Logging as an event pipeline

A logging call creates a diagnostic event. The logging system decides whether to accept it, enriches it with context, formats or encodes it, and exports it to one or more destinations.

API

The types application code calls: JUL Logger, SLF4J Logger, or Log4j API Logger.

Event

Timestamp, severity, logger name, message template, arguments, exception, markers, key-value fields, and execution context.

Backend

The implementation that filters, buffers, routes, formats, rotates, and writes events.

Transport and storage

Console, file, socket, collector agent, journal, message system, or observability platform.

The Java platform logging package defines Logger, LogRecord, Handler, Formatter, Filter, Level, and a global LogManager. Loggers create records; handlers export them to destinations.[1][2]

Logging is not a debugger, profiler, metric system, or durable audit ledger by default. It can support each use case only when the event schema, delivery guarantees, access controls, retention, and failure behavior are designed for that purpose.

2. Historical development

2002: Java 1.4 introduced java.util.logging as a standard JDK logging facility.

2003: Log4j 1.x popularized hierarchical loggers, appenders, layouts, and external configuration in Java applications.

2005: SLF4J emerged as a facade so libraries and applications could log through one API while choosing a provider at deployment time.

2006: Logback began as a successor in the same project lineage and later became the native SLF4J implementation commonly paired with the facade.

2014: Log4j 2 replaced the Log4j 1 architecture with a separate API/Core design, plugin configuration, asynchronous loggers, richer messages, and low-allocation features.

2022 onward: SLF4J 2 introduced a fluent API, key-value pairs, multiple markers, and provider discovery through ServiceLoader.[8][10]

2026: Current stable lines used in this article are SLF4J 2.0.18, Logback 1.6.1, and Log4j 2.26.1.[9][18][26]

3. Severity levels and event semantics

Severity should describe the operational consequence of an event, not the amount of text desired. The exact level names differ: JUL uses SEVERE, WARNING, INFO, CONFIG, FINE, FINER, and FINEST; SLF4J, Logback, and Log4j commonly expose ERROR, WARN, INFO, DEBUG, and TRACE.[3][19]

Operational intentTypical levelExample
Request or subsystem failed and requires investigationERROR / SEVEREOrder persistence failed after retries; user operation did not complete
Unexpected condition but service continuedWARN / WARNINGFallback configuration used; queue nearing capacity
Important lifecycle or business milestoneINFOApplication ready; deployment version; order accepted
Developer-focused decision detailDEBUG / FINESelected pricing strategy; cache miss and lookup path
Fine-grained execution traceTRACE / FINER / FINESTProtocol frames, parser transitions, per-item processing

Event naming

// Weak: no stable event meaning.
logger.info("Done");

// Better human-readable message.
logger.info(
    "Order accepted: orderId={}, itemCount={}",
    order.id(),
    order.items().size());

// Strong structured event.
logger.atInfo()
    .addKeyValue("event.action", "order.accepted")
    .addKeyValue("order.id", order.id())
    .addKeyValue("order.item_count", order.items().size())
    .log("Order accepted");

A stable action name lets operators query the semantic event even if the human message changes. Use a bounded vocabulary for field names and event actions; avoid turning arbitrary user data into field names.

Log once at the ownership boundary

Lower layers should normally return or throw enough context for the layer that owns recovery or user impact. Logging the same exception at repository, service, controller, and global handler levels produces duplicate events and can obscure the causal chain.

4. API, provider, bridge, and implementation

ComponentRoleExamples
Logging APICompile-time calls made by application or library codeJUL, SLF4J API, Log4j API
Provider/backendRuntime implementation receiving events from its primary APIJUL implementation, Logback, Log4j Core
Binding/provider moduleConnects a facade API to a backendLogback's SLF4J provider, log4j-slf4j2-impl
BridgeReceives calls from one API and forwards them to anotherjul-to-slf4j, log4j-to-slf4j, log4j-jul

SLF4J is a facade that allows the deployment to select a logging provider. Its 2.x line discovers providers with the Java service-provider mechanism. A library should normally depend on slf4j-api only, while an application selects one provider.[7][10]

Never install bridges in both directions. For example, sending Log4j API to SLF4J while also binding SLF4J back to Log4j creates a routing cycle. Draw one directed graph from every API in the dependency tree to one final backend.

5. java.util.logging (JUL)

JDK API JUL is available in the java.logging module and requires no external dependencies. Logger names form a hierarchy, records can propagate to parent handlers, and the global LogManager owns shared configuration and logger state.[1][4]

Basic logging

package com.example.orders;

import java.util.logging.Level;
import java.util.logging.Logger;

public final class OrderService {
    private static final Logger LOGGER =
        Logger.getLogger(
            OrderService.class.getName());

    public Order create(CreateOrder command) {
        LOGGER.log(
            Level.FINE,
            () -> "Creating order for customer "
                + command.customerId());

        try {
            Order order = doCreate(command);

            LOGGER.log(
                Level.INFO,
                "Order created: orderId={0}, itemCount={1}",
                new Object[] {
                    order.id(),
                    order.items().size()
                });

            return order;
        } catch (RuntimeException failure) {
            LOGGER.log(
                Level.SEVERE,
                "Order creation failed for customer "
                    + command.customerId(),
                failure);

            throw failure;
        }
    }
}

JUL overloads accepting Supplier<String> evaluate the supplier only when the effective level is enabled, avoiding unnecessary message construction.[3]

Check a level around expensive argument computation

if (LOGGER.isLoggable(Level.FINE)) {
    LOGGER.fine(
        "Graph snapshot: "
            + graph.renderDiagnosticSnapshot());
}

Handlers and formatters

A Handler receives LogRecord objects and exports them. Built-in handlers include console, file, stream, socket, and memory buffering handlers. A Formatter converts records to an output representation; handlers may also apply levels and filters.[5]

Logger logger =
    Logger.getLogger("com.example.orders");

FileHandler file =
    new FileHandler(
        "logs/orders-%g.log",
        10 * 1024 * 1024,
        5,
        true);

file.setLevel(Level.ALL);
file.setFormatter(new SimpleFormatter());

logger.addHandler(file);
logger.setLevel(Level.FINE);
logger.setUseParentHandlers(false);

Programmatic configuration can be useful in small tools and tests, but application servers and shared runtimes may own the JUL LogManager. Library code should not reset global logging configuration.

7. Structured JSON with JUL

JUL has no built-in JSON formatter, but its Formatter extension point can encode each LogRecord as one JSON object. A production formatter must escape strings, format parameters consistently, preserve exceptions, and avoid introducing invalid JSON through untrusted values.

package com.example.logging;

import java.time.Instant;
import java.util.*;
import java.util.logging.*;

public final class JsonFormatter extends Formatter {
    @Override
    public String format(LogRecord record) {
        StringBuilder json =
            new StringBuilder(512);

        json.append('{');
        field(
            json,
            "timestamp",
            Instant.ofEpochMilli(
                record.getMillis()).toString());
        comma(json);
        field(
            json,
            "severity",
            record.getLevel().getName());
        comma(json);
        field(
            json,
            "logger",
            record.getLoggerName());
        comma(json);
        field(
            json,
            "message",
            formatMessage(record));
        comma(json);
        field(
            json,
            "thread.id",
            Long.toString(
                record.getLongThreadID()));

        if (record.getSourceClassName() != null) {
            comma(json);
            field(
                json,
                "source.class",
                record.getSourceClassName());
        }

        if (record.getSourceMethodName() != null) {
            comma(json);
            field(
                json,
                "source.method",
                record.getSourceMethodName());
        }

        Throwable thrown = record.getThrown();

        if (thrown != null) {
            comma(json);
            field(
                json,
                "error.type",
                thrown.getClass().getName());
            comma(json);
            field(
                json,
                "error.message",
                thrown.getMessage());
            comma(json);
            field(
                json,
                "error.stack_trace",
                stackTrace(thrown));
        }

        json.append('}')
            .append(System.lineSeparator());

        return json.toString();
    }

    private static void field(
            StringBuilder output,
            String name,
            String value) {

        quote(output, name);
        output.append(':');
        quote(output, Objects.toString(value, ""));
    }

    private static void comma(StringBuilder output) {
        output.append(',');
    }

    private static void quote(
            StringBuilder output,
            String value) {

        output.append('"');

        for (int index = 0;
                index < value.length();
                index++) {

            char character = value.charAt(index);

            switch (character) {
                case '"' -> output.append("\\\"");
                case '\\' -> output.append("\\\\");
                case '\b' -> output.append("\\b");
                case '\f' -> output.append("\\f");
                case '\n' -> output.append("\\n");
                case '\r' -> output.append("\\r");
                case '\t' -> output.append("\\t");
                default -> {
                    if (character < 0x20) {
                        output.append(
                            "\\u%04x".formatted(
                                (int) character));
                    } else {
                        output.append(character);
                    }
                }
            }
        }

        output.append('"');
    }

    private static String stackTrace(
            Throwable thrown) {

        java.io.StringWriter buffer =
            new java.io.StringWriter();

        thrown.printStackTrace(
            new java.io.PrintWriter(buffer));

        return buffer.toString();
    }
}
A custom encoder becomes infrastructure code. Fuzz-test escaping, cap field lengths, benchmark it, and keep its schema stable. Mature backends offer more complete JSON facilities and should be preferred when available.

8. SLF4J

Facade API The Simple Logging Facade for Java provides one API over providers such as Logback, Log4j, JUL, the simple provider, and the no-operation provider. SLF4J 2.0.18 is the current stable release and requires Java 8 or later.[7][9]

Library dependency

<dependency>
  <groupId>org.slf4j</groupId>
  <artifactId>slf4j-api</artifactId>
  <version>2.0.18</version>
</dependency>

A reusable library should normally publish only the SLF4J API dependency and leave provider selection to the final application. Shipping a provider from a library can create multiple-provider warnings or override the application's logging policy.

Classic API

package com.example.orders;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public final class OrderService {
    private static final Logger LOGGER =
        LoggerFactory.getLogger(
            OrderService.class);

    public Order confirm(Order order) {
        LOGGER.debug(
            "Confirming order {} at version {}",
            order.id(),
            order.version());

        try {
            Order confirmed = order.confirm();

            LOGGER.info(
                "Order {} confirmed",
                confirmed.id());

            return confirmed;
        } catch (RuntimeException failure) {
            LOGGER.error(
                "Unable to confirm order {}",
                order.id(),
                failure);

            throw failure;
        }
    }
}

Parameterized logging delays string formatting until the backend accepts the event. Arguments should be passed separately rather than concatenated into the template. The trailing Throwable overload preserves exception structure when the number of placeholders does not consume it.[8][11]

Provider selection

9. SLF4J fluent logging and key-value fields

SLF4J 2.0 introduced a fluent API through LoggingEventBuilder. It supports message templates, arguments, suppliers, exceptions, multiple markers, and key-value pairs while preserving the disabled-level behavior of the classic API.[11][12]

LOGGER.atInfo()
    .setMessage("Order accepted")
    .addKeyValue("event.action", "order.accepted")
    .addKeyValue("order.id", order.id())
    .addKeyValue(
        "order.item_count",
        order.items().size())
    .addKeyValue(
        "order.total",
        () -> order.total().toPlainString())
    .log();

Exception and marker

Marker audit =
    MarkerFactory.getMarker("AUDIT");

LOGGER.atWarn()
    .addMarker(audit)
    .addKeyValue(
        "event.action",
        "permission.denied")
    .addKeyValue(
        "principal.id",
        principal.id())
    .addKeyValue(
        "resource.id",
        resource.id())
    .setCause(failure)
    .log("Permission denied");

Markers are backend-interpreted tags that can influence routing, filtering, or formatting. The fluent API can add multiple markers to one event.[13]

Do not omit the terminal call

// No event is emitted because log() is never called.
LOGGER.atInfo()
    .addKeyValue("order.id", order.id())
    .setMessage("Order accepted");

// Correct:
LOGGER.atInfo()
    .addKeyValue("order.id", order.id())
    .log("Order accepted");

LoggingEventBuilder builds an event only when its terminal log method is called.[12]

Supplier boundaries

LOGGER.atDebug()
    .setMessage("Route candidates: {}")
    .addArgument(
        () -> routeGraph.expensiveSnapshot())
    .log();

Use a supplier for values whose construction is materially expensive. A supplier that captures a large object graph may extend object lifetime until the event is processed by an asynchronous backend, so capture only what is required.

10. MDC, Thread Context, and propagation

Mapped Diagnostic Context associates key-value context with the current execution thread. SLF4J exposes a provider-neutral MDC; Logback and Log4j supply their own implementations. MDC is useful for request, trace, tenant, user, job, and correlation identifiers that should appear on many events.[14][21]

Scoped MDC cleanup

public Response handle(Request request) {
    try (MDC.MDCCloseable requestId =
            MDC.putCloseable(
                "request.id",
                request.id());
         MDC.MDCCloseable tenantId =
            MDC.putCloseable(
                "tenant.id",
                request.tenantId())) {

        LOGGER.info("Request received");

        return service.process(request);
    }
}

Always restore or clear context in a finally block or scoped closeable. Thread pools reuse threads, so leaked MDC values can be attached to unrelated requests.

Explicit executor propagation

public final class ContextAwareExecutor
        implements Executor {

    private final Executor delegate;

    public ContextAwareExecutor(
            Executor delegate) {
        this.delegate =
            Objects.requireNonNull(delegate);
    }

    @Override
    public void execute(Runnable command) {
        Map<String, String> captured =
            MDC.getCopyOfContextMap();

        delegate.execute(() -> {
            Map<String, String> previous =
                MDC.getCopyOfContextMap();

            try {
                if (captured == null) {
                    MDC.clear();
                } else {
                    MDC.setContextMap(captured);
                }

                command.run();
            } finally {
                if (previous == null) {
                    MDC.clear();
                } else {
                    MDC.setContextMap(previous);
                }
            }
        });
    }
}

Logback's MDC is thread-local and child threads do not automatically inherit a copy. Context must be propagated explicitly across executors, asynchronous callbacks, reactive pipelines, and message boundaries.[20]

Log4j Thread Context scoped values

try (CloseableThreadContext.Instance ignored =
        CloseableThreadContext
            .put("request.id", requestId)
            .put("tenant.id", tenantId)
            .push("checkout")) {

    LOGGER.info("Processing request");
}

Log4j Thread Context combines a map, commonly called MDC, and a stack, commonly called NDC. Its closeable API helps restore both after a scope exits.[36]

Context design

  • Use stable identifiers, not entire request or user objects.
  • Prefer pseudonymous internal IDs over email addresses or names.
  • Do not place credentials, access tokens, session IDs, or payment data in context.
  • Keep the key set bounded and document ownership.
  • Propagate trace identifiers through protocol headers and message metadata, then copy them into logging context.

11. Logging bridges and routing graphs

Bridges allow dependencies using different logging APIs to converge on one backend. SLF4J supplies bridges for JUL, Commons Logging, and Log4j 1.x; Log4j supplies bridges from SLF4J and JUL into the Log4j API and bridges from Log4j API to other systems.[15][32]

JUL to SLF4J

<dependency>
  <groupId>org.slf4j</groupId>
  <artifactId>jul-to-slf4j</artifactId>
  <version>2.0.18</version>
  <scope>runtime</scope>
</dependency>
import org.slf4j.bridge.SLF4JBridgeHandler;

public final class LoggingBootstrap {
    public static void routeJulToSlf4j() {
        SLF4JBridgeHandler.removeHandlersForRootLogger();
        SLF4JBridgeHandler.install();
    }
}

The JUL bridge installs a JUL Handler that forwards records into SLF4J. Because JUL classes in java.* cannot be replaced, this bridge incurs JUL record creation and handler forwarding; align JUL levels with the backend to avoid needless disabled-event work.[15][16]

SLF4J to Log4j 2

<dependency>
  <groupId>org.apache.logging.log4j</groupId>
  <artifactId>log4j-slf4j2-impl</artifactId>
  <scope>runtime</scope>
</dependency>

For SLF4J 2.x, Log4j's provider module is log4j-slf4j2-impl. It forwards SLF4J calls to the Log4j API and then to Log4j Core.[32]

JUL to Log4j 2

12. Logback

SLF4J backend Logback Classic natively implements SLF4J and uses Logback Core for appenders, encoders, rolling policies, and infrastructure. The current stable Logback release is 1.6.1; the 1.6.x line uses SLF4J 2.0.x and runs on Java 11 or later.[18][19]

Maven dependencies

<dependencies>
  <dependency>
    <groupId>org.slf4j</groupId>
    <artifactId>slf4j-api</artifactId>
    <version>2.0.18</version>
  </dependency>

  <dependency>
    <groupId>ch.qos.logback</groupId>
    <artifactId>logback-classic</artifactId>
    <version>1.6.1</version>
    <scope>runtime</scope>
  </dependency>
</dependencies>

logback-classic depends on logback-core. Keep Logback modules and SLF4J API versions aligned with the compatibility documented by the release line.

Architecture

Logback loggers are hierarchical. Accepted events flow to appenders attached to the logger and, by default, to ancestor appenders; this cumulative behavior is called additivity. A logger with a local appender can set additivity="false" to prevent duplicate propagation.[17][24]

logback.xmlLocal console and production rolling file 
<configuration>
  <property
      name="LOG_DIR"

      name="CONSOLE"

  <appender
      name="FILE"

    <file>${LOG_DIR}/application.log</file>

    <rollingPolicy
        class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">
      <fileNamePattern>
        ${LOG_DIR}/archive/application.%d{yyyy-MM-dd}.%i.log.gz
      </fileNamePattern>
      <maxFileSize>100MB</maxFileSize>
      <maxHistory>14</maxHistory>
      <totalSizeCap>10GB</totalSizeCap>
    </rollingPolicy>

    <encoder>
      <pattern>
        %date{ISO8601,UTC} %-5level
        [%thread] %logger{36}
        %kvp %mdc %msg %ex%n
      </pattern>
    </encoder>
  </appender>

  <logger
      name="com.example.orders.sql"
      level="DEBUG"
      additivity="false">
    <appender-ref ref="FILE" />
  </logger>

  <root level="${ROOT_LOG_LEVEL:-INFO}">
    <appender-ref ref="CONSOLE" />
    <appender-ref ref="FILE" />
  </root>
</configuration>

Logback appenders export events, encoders convert events to bytes, and rolling policies control archive naming, rollover, retention, and size caps.[22][23]

Configuration diagnostics

<configuration debug="true">
  ...
</configuration>

Configuration diagnostics should be enabled only when investigating startup or reconfiguration problems; they can generate additional output. Keep configuration files read-only to the application identity and never treat untrusted input as executable configuration.

15. Logback asynchronous appenders

Logback's AsyncAppender places events on a blocking queue and delegates output to one attached appender from a worker thread. Its default queue capacity is 256. By default, when 20% capacity remains, TRACE, DEBUG, and INFO events are discardable; discardingThreshold=0 retains them. neverBlock=false causes producers to block when the queue is full, while true permits event loss instead.[22]

<appender
    name="JSON_FILE"
    class="ch.qos.logback.core.rolling.RollingFileAppender">

  <file>logs/application.json</file>

  <rollingPolicy
      class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">
    <fileNamePattern>
      logs/archive/application.%d{yyyy-MM-dd}.%i.json.gz
    </fileNamePattern>
    <maxFileSize>100MB</maxFileSize>
    <maxHistory>14</maxHistory>
    <totalSizeCap>10GB</totalSizeCap>
  </rollingPolicy>

  <encoder
      class="ch.qos.logback.classic.encoder.JsonEncoder" />
</appender>

<appender
    name="ASYNC_JSON"
    class="ch.qos.logback.classic.AsyncAppender">

  <queueSize>8192</queueSize>
  <discardingThreshold>0</discardingThreshold>

Caller location is excluded by default because obtaining it is expensive and must occur before the event leaves the originating thread. Shutdown must stop the logger context or otherwise allow the asynchronous queue to flush within its configured limit.[22]

19. Log4j asynchronous logging

Log4j offers queue-based Async Appenders and Disruptor-based asynchronous loggers. Asynchronous logging moves output I/O to another thread and can absorb bursts, but the application still performs event capture, context copying, queue publication, and any eagerly evaluated argument work.[33]

Mixed asynchronous logger configuration

Async loggers use LMAX Disruptor and require its runtime dependency. Log4j recommends evaluating synchronous and asynchronous choices against the actual application; synchronous logging is simpler when the measured difference is not meaningful.[33]

Location information

Class, method, file, and line location require stack inspection. Log4j documents this as expensive, and asynchronous components disable location capture by default because it must occur on the originating thread.[29]

Queue saturation

  • Define whether producers block, discard, or fall back synchronously.
  • Count dropped events and expose queue utilization.
  • Do not route compliance audit events through a lossy queue unless the control design explicitly permits loss.
  • Exercise shutdown and abrupt termination; asynchronous buffers are not durable storage.
  • Benchmark burst behavior, not only steady-state throughput.

Schema rules

  • Use stable lowercase dotted or snake-case names consistently.
  • Document units in the field name or schema; do not mix milliseconds and nanoseconds under one key.
  • Use a fixed event-action vocabulary and version incompatible semantic changes.
  • Avoid high-cardinality field names; cardinality belongs in values.
  • Cap untrusted strings, collection sizes, and stack trace depth.
  • Represent absent values consistently—omit, null, or explicit sentinel—according to the storage schema.
  • Keep one JSON object per record and use UTF-8.

21. Exception logging

Pass the throwable separately

// Bad: discards stack, cause, and suppressed exceptions.
LOGGER.error(
    "Checkout failed: " + failure);

// Correct SLF4J classic API.
LOGGER.error(
    "Checkout failed for order {}",
    orderId,
    failure);

// Correct fluent API.
LOGGER.atError()
    .addKeyValue("order.id", orderId)
    .setCause(failure)
    .log("Checkout failed");

A Java Throwable can contain a message, cause chain, suppressed exceptions, and stack frames. Passing it as a throwable allows the backend to preserve and structure these elements.[41]

Log at one recovery boundary

public Order load(OrderId id) {
    try {
        return repository.require(id);
    } catch (SQLException failure) {
        // Add domain context, but do not log here if the
        // controller-level owner will record the final failure.
        throw new OrderLoadFailure(id, failure);
    }
}

public Response handle(OrderId id) {
    try {
        return Response.ok(service.load(id));
    } catch (OrderLoadFailure failure) {
        LOGGER.atError()
            .addKeyValue("order.id", id)
            .setCause(failure)
            .log("Unable to load order");

        return Response.serverError();
    }
}

Expected exceptions

Not every exception is an error event. Validation rejection, optimistic concurrency conflict, client cancellation, or a normal cache miss may belong at INFO, DEBUG, or no log at all. Severity should follow operational impact and whether action is required.

Stack trace size

  • Preserve full traces for unexpected failures in a controlled error stream.
  • Use root-cause and frame truncation only when the storage and incident requirements justify it.
  • Record exception type and a stable error code separately from the mutable message.
  • Do not expose internal stack traces to clients merely because they were logged.

22. Logging security, privacy, and integrity

Security boundary Logs commonly contain operationally sensitive data and are attractive targets for credential theft, privacy breaches, evidence destruction, and injection. OWASP recommends excluding or masking secrets and sensitive identifiers, sanitizing event data to prevent log injection, protecting transmission and storage, and monitoring access to logs.[42][43]

Data that should normally not be logged

  • Passwords, password reset tokens, API keys, private keys, bearer tokens, and authorization headers.
  • Session identifiers and authentication cookies.
  • Full payment card or bank details.
  • Unnecessary personal, health, legal, or confidential business data.
  • Complete request/response bodies without an explicit approved schema and redaction layer.
  • Database connection strings containing credentials.

Redaction at the boundary

public final class SafeHeaders {
    private static final Set<String> SECRET_HEADERS =
        Set.of(
            "authorization",
            "cookie",
            "set-cookie",
            "proxy-authorization",
            "x-api-key");

    private SafeHeaders() {
    }

    public static Map<String, String> forLogging(
            Map<String, String> headers) {

        return headers.entrySet().stream()
            .collect(Collectors.toUnmodifiableMap(
                entry ->
                    entry.getKey()
                        .toLowerCase(Locale.ROOT),
                entry ->
                    SECRET_HEADERS.contains(
                        entry.getKey()
                            .toLowerCase(Locale.ROOT))
                        ? "[REDACTED]"
                        : limitAndNeutralize(
                            entry.getValue(),
                            500)));
    }

    private static String limitAndNeutralize(
            String value,
            int maximumCharacters) {

        String normalized =
            value.replace('\r', ' ')
                .replace('\n', ' ')
                .replace('\u0000', ' ');

        return normalized.length()
                <= maximumCharacters
            ? normalized
            : normalized.substring(
                0,
                maximumCharacters)
                + "…";
    }
}

Structured encoders escape control characters for JSON syntax, but that does not decide whether the data is permissible to retain. Redaction and minimization are policy decisions before encoding.

Log injection

When untrusted values are written into line-oriented text without neutralization, carriage returns, line feeds, and delimiters can forge apparent records or corrupt downstream parsing. JSON encoding with correct escaping reduces framing risk, while input limits and field allowlists reduce abuse.[42]

Configuration security

  • Keep logging configuration and plugin paths writable only by deployment administrators.
  • Do not download logging configuration from an unauthenticated or untrusted location.
  • Upgrade promptly; logging backends process configuration, formats, network output, and exceptions on privileged application paths.
  • Prefer current supported release lines. Logback 1.6.x is the current stable line, while older 1.2, 1.3, and 1.4 lines are end-of-life.[18]
  • Maintain dependency locks and software bills of materials for logging artifacts.

Audit logging

Security and compliance audit records require stronger controls than ordinary diagnostics: authenticated actor identity, action, target, outcome, event time, source, policy decision, tamper resistance, access review, retention, and delivery monitoring. Separate audit-event policy from debug-level configuration so an operator cannot silently disable required evidence.

23. Logging performance

Logging cost includes level checks, argument construction, event allocation, context copying, caller-location capture, message formatting, exception rendering, queue publication, encoding, synchronization, I/O, flushing, rotation, compression, and downstream backpressure.

Avoid eager work

// Eager string and snapshot creation even when DEBUG is disabled.
LOGGER.debug(
    "Cache contents: "
        + cache.expensiveSnapshot());

// Parameterized but still eager snapshot construction.
LOGGER.debug(
    "Cache contents: {}",
    cache.expensiveSnapshot());

// Lazy SLF4J fluent argument.

    .setMessage("Cache contents: {}")
    .addArgument(
        cache::expensiveSnapshot)
    .log();

// JUL supplier.
JUL_LOGGER.log(
    Level.FINE,
    () -> "Cache contents: "
        + cache.expensiveSnapshot());

Do not log inside extreme hot loops by default

// High-volume per-item logging can dominate the operation.
for (Record record : records) {
    LOGGER.debug(
        "Processing record {}",
        record.id());
    process(record);
}

// Aggregate and sample.
long failures = 0;
long processed = 0;

for (Record record : records) {
    try {
        process(record);
        processed++;
    } catch (RuntimeException failure) {
        failures++;

        if (failures <= 10) {
            LOGGER.atWarn()
                .addKeyValue("record.id", record.id())
                .setCause(failure)
                .log("Record processing failed");
        }
    }
}

LOGGER.atInfo()
    .addKeyValue("records.processed", processed)
    .addKeyValue("records.failed", failures)
    .log("Batch completed");

Caller location and stack traces

Log4j documents source location as expensive because the runtime must inspect the call stack. Logback likewise excludes caller data from asynchronous events by default. Enable file and line fields only where incident value exceeds the measured cost.[29][22]

Async is a queue, not free performance

Asynchronous logging can reduce application-thread I/O and absorb bursts. It introduces queue memory, context snapshots, worker scheduling, shutdown flushing, reordering relative to external effects, and a saturation policy. Log4j recommends benchmarking async versus sync behavior in the actual application and retaining synchronous logging when the difference is not significant.[33][44]

25. Deployment architecture

Libraries

  • Depend on one neutral API—commonly SLF4J—or use JUL when zero dependencies and JDK integration are primary.
  • Do not set global levels, replace handlers, or package a provider.
  • Do not assume MDC keys or backend-specific marker behavior unless part of the library contract.

Standalone services

Application and dependencies
  ├── SLF4J API calls
  ├── JUL dependency calls
  └── Log4j API dependency calls
          │
          ├── jul-to-slf4j

Containerized applications often write structured events to standard output and let the platform's agent handle rotation, shipping, retries, and storage. File appenders remain appropriate when local durability, regulated retention, or platform constraints require them, but the application and collector must not compete to rotate the same file.

Application servers

Jakarta EE and other managed containers may provide server-wide logging integration, JUL managers, class-loader isolation, and administrative level control. Follow the server's supported bridge architecture rather than replacing global logging from application code.

Its backend is selected by the platform LoggerFinder, allowing early platform and modular code to log without a direct dependency on JUL classes. It is relevant for JDK-facing libraries but is less feature-rich than SLF4J or Log4j for application structured logging.[46]

Log4j distinguishes logging APIs, implementations, and bridges in its migration documentation. A backend can be changed without recompiling code only when API compatibility and the correct bridge/provider modules are maintained.[32][47]

Configuration migration

  • Translate levels and logger hierarchy.
  • Recreate appender destinations, filters, additivity, rollover, and retention.
  • Map pattern fields or JSON schemas explicitly.
  • Verify MDC, markers, key-value pairs, caller data, and exception rendering.
  • Test overload behavior and parameter formatting.
  • Exercise queue saturation and shutdown.
  • Remove the old implementation and opposite-direction bridges from the runtime.

Never migrate by copying a pattern only

Equivalent-looking conversion patterns can differ in escaping, timestamps, exception placement, MDC formatting, caller lookup, and line framing. Treat stored log schemas and alert queries as downstream compatibility contracts.

27. Selection guide

ChoiceStrengthsTrade-offs
JULNo external dependency, JDK integration, handlers and managementLess ergonomic structured data and application ecosystem integration
SLF4J APIProvider-neutral library API, parameterized and fluent logging, MDC and markersRequires one correctly selected provider; backend capabilities vary
LogbackNative SLF4J implementation, mature configuration, rolling, async appender, built-in JSON encoderBackend-specific configuration and lifecycle; async overload must be designed
Log4j API + CoreRich message model, JSON Template Layout, plugins, Thread Context, async loggers, low-allocation facilitiesMore modules and configuration surface; version alignment and bridge design matter
SLF4J + Log4j CoreNeutral application API with Log4j backend facilitiesSome Log4j API-specific message capabilities are not directly exposed through classic SLF4J calls

Practical defaults

  • Reusable library: SLF4J API only, or JUL when dependency-free JDK integration is a stated requirement.
  • Conventional application: SLF4J with current Logback.
  • Advanced structured and asynchronous needs: Log4j API/Core or SLF4J with Log4j Core.
  • Existing managed runtime: use its supported logging integration and bridge dependencies into it.

The best backend is the one whose schema, routing, overload, patching, deployment, and operational behavior the team can test and maintain. Raw disabled-call nanoseconds should not outweigh reliability and incident usability.

28. Production logging checklist

Dependency graph

  • One intended API is used by new application code.
  • One provider/backend wins at runtime.
  • Bridges form a directed acyclic route to that backend.
  • All backend modules are version-aligned and on a supported release.

Event design

  • Severity reflects operational consequence.
  • Events have stable action names and typed fields.
  • Messages remain concise and readable without being the only query surface.
  • Exceptions are passed separately.
  • Duplicate logging at every layer is avoided.

Context

  • Request, trace, span, tenant, and job IDs use documented keys.
  • MDC is restored after every scope.
  • Context is propagated explicitly across executors and messages.
  • Context values contain no credentials or unnecessary personal data.

Structured output

  • One valid UTF-8 JSON object is emitted per record.
  • Field names, types, units, and absent-value policy are stable.
  • Control characters and Unicode are tested.
  • Values and stack traces have practical size limits.
  • Storage mappings and alerts are versioned with schema changes.

Delivery and performance

  • Async queue capacity and block/drop policy are explicit.
  • Dropped events and queue utilization are observable.
  • Shutdown and rotation are tested.
  • Caller location is enabled only when justified.
  • Expensive arguments use suppliers or level checks.
  • High-volume loops use aggregation or sampling.

Security and operations

  • Secrets, session IDs, payment data, and unnecessary PII are excluded.
  • Untrusted values are length-limited and safely encoded.
  • Configuration and log storage have least-privilege access.
  • Audit logging has separate reliability and retention controls.
  • Runtime level changes are authenticated, time-bounded, and recorded.
  • Dependency security updates are part of the normal patch process.
Final principle: useful logging is a designed event system. Choose one API route, preserve structured context, make overload behavior explicit, protect sensitive data, and test the complete path from call site to storage. More log lines are not more observability; well-defined, correlated, trustworthy events are.
