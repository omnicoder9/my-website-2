1. A useful performance model

Java performance is not one number. It is a set of workload-dependent outcomes produced by application algorithms, data representation, concurrency, the JIT compiler, garbage collection, operating-system scheduling, storage, networking, and hardware.

Latency

Time from request or operation start to completion. Report a distribution—especially percentiles and maxima—not only an average.

Throughput

Completed work per unit time under a defined load, concurrency level, and correctness criterion.

Resource efficiency

CPU time, allocated bytes, live heap, native memory, network, storage, and energy per unit of useful work.

Capacity and stability

The maximum sustainable load before queues grow, deadlines fail, GC dominates, or the system becomes unstable.

The HotSpot VM interprets and compiles Java bytecode, profiles executing methods, optimizes hot paths, and may later deoptimize code when assumptions become invalid. Consequently, startup behavior, warmup behavior, and steady-state behavior can differ materially.[2]

Performance is a contract with a workload. A claim such as “method A is faster” is incomplete without input distribution, JVM version, flags, hardware, warmup state, concurrency, GC, and statistical uncertainty.

2. Historical context

1990s: Java introduced managed memory, bytecode portability, interpretation, and increasingly capable just-in-time compilation.

1999: HotSpot became central to Sun's Java runtime strategy, using runtime profiles to focus optimization on hot methods and paths.

2000s: Tiered compilation, escape analysis, generational collectors, and serviceability tooling matured.

2018: JDK Flight Recorder was open-sourced and made generally available as a low-overhead event collection framework.[5]

JDK 11: Low-overhead sampled heap allocation profiling was delivered through JVMTI.[10]

JDK 25: JFR gained experimental CPU-time profiling, cooperative sampling, and method timing/tracing; AOT caches gained simpler ergonomics and method profiles; compact object headers became a product feature.[1]

JDK 25 reached general availability on 16 September 2025 and is the Java SE 25 reference implementation. Performance results must name the exact JDK build because compiler, collector, library, and serviceability behavior changes across releases.[1]

3. A disciplined optimization workflow

  1. Define the user-visible objective. Example: p99 checkout latency below 200 ms at 2,000 requests per second with an error rate below 0.1%.
  2. Capture a representative workload. Preserve payload sizes, key distributions, concurrency, cache state, database behavior, and deployment limits.
  3. Measure the whole system. Record latency distributions, throughput, CPU, allocation rate, live heap, GC pauses, queue depth, I/O, and saturation.
  4. Profile before editing. Locate hot code, blocked time, allocations, locks, GC pressure, and external waits.
  5. Form one falsifiable hypothesis. “JSON field-name canonicalization allocates 1.4 GB/s and causes young collections every 180 ms.”
  6. Change one material factor. Preserve correctness tests and observability.
  7. Benchmark and load test. Use JMH for isolated code and a representative system test for end-to-end impact.
  8. Compare confidence intervals and operational trade-offs. Retain the change only if the relevant metric improves without unacceptable regressions.
Do not tune from folklore. Heap flags copied from another workload, replacing every stream with a loop, pooling every object, or setting thread counts to CPU count can make the actual system slower or less reliable.

A CPU profile and a wall-clock profile answer different questions. CPU sampling attributes time while threads execute; wall-clock sampling also captures waiting and blocked stacks. Allocation profiling identifies creation sites, while a heap dump identifies retained objects. One cannot substitute for the other.

async-profiler is an open-source sampling profiler supporting CPU, wall-clock, allocation, lock, native-memory, and other profiling modes, with outputs including interactive flame graphs and JFR files.[13]

# Allocation profile

# Wall-clock profile for latency investigation

5. Java Flight Recorder and JDK Mission Control

Java Flight Recorder is a low-overhead event recording framework integrated with HotSpot. It records JVM, operating-system, and application events into a binary stream or file. JDK Mission Control analyzes recordings and provides automated rules, timelines, stack traces, allocation views, lock analysis, and GC diagnostics.[4][6]

Start at JVM launch

java \
  -XX:StartFlightRecording=\
name=prod,settings=profile,duration=10m,filename=app.jfr \
  -jar application.jar

Attach to a running process

jcmd 4217 JFR.start \
  name=incident \
  settings=profile \
  duration=5m \
  filename=/var/tmp/incident.jfr

jcmd 4217 JFR.check

jcmd 4217 JFR.dump \
  name=incident \
  filename=/var/tmp/incident-now.jfr

jcmd 4217 JFR.stop name=incident

The JDK troubleshooting guide recommends JFR for production-time profiling and jcmd for starting, checking, dumping, and stopping recordings on a running JVM.[3][7]

Custom domain event

package com.example.performance;

import jdk.jfr.*;

@Name("com.example.Checkout")
@Label("Checkout")
@Category({"Application", "Commerce"})
@Description("End-to-end checkout execution")
@StackTrace(false)
public final class CheckoutEvent extends Event {
    @Label("Order ID")
    public String orderId;

    @Label("Item Count")
    public int itemCount;

    @Label("Outcome")
    public String outcome;

    @DataAmount(DataAmount.BYTES)
    @Label("Response Bytes")
    public long responseBytes;
}
public CheckoutResult checkout(
        CheckoutRequest request) {

    CheckoutEvent event = new CheckoutEvent();
    event.orderId = request.orderId();
    event.itemCount = request.items().size();
    event.begin();

    try {
        CheckoutResult result =
            checkoutService.execute(request);

        event.outcome = result.outcome().name();
        event.responseBytes = result.estimatedBytes();

        return result;
    } catch (RuntimeException failure) {
        event.outcome = "ERROR";
        throw failure;
    } finally {
        event.commit();
    }
}

Application events subclass jdk.jfr.Event; fields become event data, and begin()/commit() record duration when enabled by the active configuration.[4][30]

JDK 25 profiling additions

JDK 25 includes experimental JFR CPU-time profiling, which samples threads according to consumed CPU time on supported Linux systems; cooperative sampling improves stability of stack sampling; and method timing/tracing can instrument selected methods for duration and invocation evidence. These features are opt-in and should be evaluated for overhead under the target workload.[8][9][12]

Out-of-memory evidence

java \
  -XX:+HeapDumpOnOutOfMemoryError \
  -XX:HeapDumpPath=/var/crash/java \
  -XX:ErrorFile=/var/crash/java/hs_err_pid%p.log \
  -jar application.jar

A heap-space OutOfMemoryError does not by itself prove a leak: the live set may simply exceed the configured heap, allocation may spike, or the application may retain data intentionally. A rising post-GC live set under stable load is stronger leak evidence. Heap dumps and old-object sampling help find retained objects and paths to GC roots.[22]

Thread-dump interpretation

  • Repeatedly RUNNABLE stacks at the same method suggest CPU work or native I/O reported as runnable.
  • Many BLOCKED threads identify monitor contention and the lock owner.
  • WAITING or TIMED_WAITING can be healthy queueing, parking, sleep, or synchronization; correlate with latency and queue depth.
  • One dump is a snapshot. Collect multiple dumps several seconds apart to distinguish persistent from transient stacks.

7. Reading CPU and latency profiles

Flame graph interpretation

  • Width represents sampled resource consumption, not call duration of one invocation.
  • The top edge shows code directly consuming the sampled resource.
  • Wide lower frames aggregate the work of callees.
  • Compare profiles captured under the same load and duration; absolute sample counts vary.

Common profile signatures

SignatureLikely causeNext evidence
Wide JSON parsing/encoding stacksPayload volume, reflection, copying, field lookup, encodingAllocation profile, payload distribution, parser configuration
Hash map and equality stacksPoor key distribution, repeated lookups, oversized object graphKey cardinality, collision data, data-layout benchmark
Regex engine dominatesRepeated compilation or pathological pattern/inputCompile-site profile, input examples, timeout/fuzz test
Lock/park stacks dominate wall timeContention or undersized poolJFR monitor/park events, queue depth, owner stacks
GC and allocation dominateHigh allocation rate or large live setAllocation profile, GC logs, heap occupancy after GC
Kernel networking/file stacksExternal I/O or syscall pressureSocket latency, disk metrics, request tracing
A hotspot is not automatically waste. A method may dominate because it performs the application's essential work. Optimize the algorithm or reduce how often the work is required; moving cost behind another method does not improve performance.

8. Benchmarking: what JMH solves

JMH is the OpenJDK Java Microbenchmark Harness for constructing, running, and analyzing nano-, micro-, milli-, and macrobenchmarks on the JVM. It generates benchmark infrastructure that helps control warmup, measurement iterations, forking, state scope, concurrency, parameterization, result consumption, and common compiler pitfalls.[14][15]

OpenJDK recommends a standalone JMH project with generated benchmark code rather than casually timing a loop inside an application or IDE. JMH 1.37 remains the current artifact published in Maven Central as of 30 July 2026.[15][16]

Microbenchmark versus system test

QuestionApproach
Which parser implementation consumes fewer nanoseconds and bytes for one document?JMH with representative inputs
Does the checkout service meet p99 latency at production load?End-to-end load test with real dependencies or realistic substitutes
Did a JDK upgrade change startup and warmup?Process-level benchmark over many fresh JVM launches
Does a GC flag reduce pauses without throughput loss?Representative long-running load test plus GC/JFR analysis

10. A defensible JMH benchmark

package com.example.benchmarks;

import org.openjdk.jmh.annotations.*;
import org.openjdk.jmh.infra.Blackhole;

import java.nio.charset.StandardCharsets;
import java.util.concurrent.TimeUnit;

@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.NANOSECONDS)
@Warmup(iterations = 5, time = 1)
@Measurement(iterations = 8, time = 1)
@Fork(value = 3)
public class OrderEncodingBenchmark {

    @State(Scope.Thread)
    public static class Input {
        @Param({"4", "32", "256"})
        int lineCount;

        Order order;
        OrderEncoder encoder;

        @Setup(Level.Trial)
        public void setup() {
            order = OrderFixtures.order(lineCount);
            encoder = new OrderEncoder(
                StandardCharsets.UTF_8);
        }
    }

    @Benchmark
    public byte[] encode(
            Input input) {
        return input.encoder.encode(input.order);
    }

    @Benchmark
    public void encodeIntoBlackhole(
            Input input,
            Blackhole blackhole) {
        input.encoder.encodeTo(
            input.order,
            blackhole::consume);
    }
}
WarmupAllows interpretation, profiling, compilation, class loading, and caches to approach the intended phase.
ForkRuns fresh JVM processes, reducing contamination from earlier benchmarks and JVM state.
State scopeDefines whether benchmark state is per thread, per group, or shared across the benchmark.

Benchmark modes

  • AverageTime: average time per operation.
  • Throughput: operations per unit time.
  • SampleTime: sampled latency distribution.
  • SingleShotTime: time for one invocation, useful for cold or expensive operations when configured carefully.

Allocation metrics

The JMH GC profiler reports metrics such as normalized bytes allocated per operation and collection activity. These are especially valuable because a time result can appear unchanged while one version allocates significantly more and will degrade under sustained load.

java -jar target/benchmarks.jar \
  OrderEncodingBenchmark \
  -prof gc \
  -jvmArgsAppend '-Xms2g -Xmx2g'

11. Common benchmarking traps

Dead-code elimination

// Bad: result is unused and may be optimized away.
@Benchmark
public void bad() {
    Math.log(input);
}

// Better: return it.
@Benchmark
public double good() {
    return Math.log(input);
}

Constant folding

// Risk: compiler can know all values.
@Benchmark
public int folded() {
    return 42 * 17;
}

// State value is opaque to benchmark compilation.
@State(Scope.Thread)
public static class Values {
    int value = 42;
}

@Benchmark
public int measured(Values values) {
    return values.value * 17;
}

Looping inside a benchmark

// Misleading: loop optimizations and one-time setup
// are mixed into the measured operation.
@Benchmark
public long manualLoop() {
    long sum = 0;
    for (int i = 0; i < 1_000_000; i++) {
        sum += operation(i);
    }
    return sum;
}

// Prefer one logical operation per invocation.
@Benchmark
public long operation(Values values) {
    return operation(values.next());
}

Other threats

  • Benchmark input is too small, uniform, or cache-friendly compared with production.
  • Setup work is accidentally included or excluded.
  • Only one fork is used, hiding process-to-process variance.
  • Benchmarks run on a thermally throttled laptop with background processes.
  • The benchmark measures a local operation while production is dominated by I/O or contention.
  • Results from different JDKs use different flags, CPU frequency policy, or container limits.
  • A statistically significant result is too small to matter operationally.
JMH prevents many harness errors, not experimental-design errors. Representative data, correct operation boundaries, enough forks, controlled machines, and system-level verification remain the engineer's responsibility.

12. Java memory: heap is only one category

A Java process consumes more memory than the object heap. HotSpot also reserves or commits memory for class metadata, code cache, garbage-collector structures, thread stacks, JIT compiler data, direct buffers, JNI and native libraries, mapped files, and the JVM itself. Native Memory Tracking groups HotSpot-owned native memory by subsystem but does not account for every allocation made by third-party native code.[20]

CategoryTypical contentsDiagnostic evidence
Java heapObjects and arrays managed by the collectorJFR, GC logs, histogram, heap dump
Metaspace/class spaceLoaded-class metadataNMT Class category, class-loading events
Code cacheJIT-compiled machine code and metadataJFR compilation events, Compiler.codecache
ThreadsNative stacks and JVM thread structuresNMT Thread category, thread count
Direct/native buffersOff-heap I/O buffers and native library allocationsBufferPool MXBeans, NMT partial view, OS tools
GC structuresRemembered sets, marking structures, regions, barriersNMT GC categories and collector logs

Reserved virtual address space is not the same as committed physical memory. A large reserved heap can coexist with a much smaller committed heap; operational limits should be evaluated against committed memory, resident set size, container limits, and worst-case growth.[20]

13. Memory optimization

Memory Effective memory optimization reduces the live set, allocation rate, object graph depth, duplication, or native footprint while preserving correctness. “Use fewer objects” is not a universal rule: short-lived allocation can be cheap, whereas retained objects determine required heap capacity and tracing work.

Start with retention and cardinality

  • Measure object count, shallow size, retained size, and paths to GC roots.
  • Find unbounded maps, queues, listeners, caches, thread locals, class loaders, and request histories.
  • Define cache maximum size, weight, expiration, invalidation, and observability.
  • Do not retain complete payloads when identifiers or compact summaries are sufficient.
  • Use streaming or pagination instead of materializing entire result sets.

Replace duplicate representation

// Wasteful: stores the same normalized value and repeatedly
// retains source strings in many Customer objects.
public final class Customer {
    private final String rawEmail;
    private final String normalizedEmail;
    private final String emailDomain;
    // ...
}

// Compact boundary: normalize once and store the representation
// actually required by the domain.
public record EmailAddress(
        String localPart,
        String domain) {

    public EmailAddress {
        localPart = normalizeLocal(localPart);
        domain = IDN.toASCII(
            domain.toLowerCase(Locale.ROOT));
    }

    public static EmailAddress parse(String text) {
        int separator = text.lastIndexOf('@');
        if (separator <= 0
                || separator == text.length() - 1) {
            throw new IllegalArgumentException(
                "Invalid email address");
        }

        return new EmailAddress(
            text.substring(0, separator),
            text.substring(separator + 1));
    }
}

Use primitive storage when density matters

// Each boxed Long is a separate reference object unless
// optimized away or reused; the collection stores references.
List<Long> timestamps = new ArrayList<>();

// Dense primitive representation.
long[] timestamps = new long[count];

Boxing converts primitive values to wrapper references, and unboxing converts wrappers back to primitives. Generic collections require reference types, so high-cardinality numeric data can introduce wrapper allocations and pointer-heavy layouts.[26]

String deduplication

HotSpot can enable G1 string deduplication with -XX:+UseStringDeduplication. The JVM attempts to make equal strings share backing character storage. It is disabled by default and introduces its own tracking and processing cost, so evaluate it using a workload containing meaningful duplicate strings.[17]

java \
  -XX:+UseG1GC \
  -XX:+UseStringDeduplication \
  -Xlog:stringdedup=info \
  -jar application.jar

Compact object headers in JDK 25

JDK 25 makes compact object headers a product feature, enabled with -XX:+UseCompactObjectHeaders. It is not the default layout in JDK 25. The feature can reduce per-object overhead and improve locality for object-dense workloads, but compatibility and performance must be tested with the chosen collector, libraries, and tooling.[25]

java \
  -XX:+UseCompactObjectHeaders \
  -Xms4g -Xmx4g \
  -jar application.jar

14. Object allocation

Allocation HotSpot normally allocates small objects rapidly from thread-local allocation buffers. The performance cost of allocation includes initialization, memory bandwidth, later tracing/copying/reclamation, and the live references that survive. Allocation rate is therefore often more actionable than raw allocation count.

Measure bytes per operation

java -jar target/benchmarks.jar \
  '.*ParsingBenchmark.*' \
  -prof gc

Use allocation profiling to identify sites, then JMH normalized allocation to compare isolated alternatives. JEP 331 added a sampled allocation event to JVMTI so profilers can sample allocations with low overhead rather than instrumenting every allocation.[10][31]

Accidental temporary collections

// Allocates intermediate lists and boxed values.
public static long sumPositive(
        List<Integer> values) {

    return values.stream()
        .filter(value -> value > 0)
        .map(value -> value.longValue())
        .toList()
        .stream()
        .reduce(0L, Long::sum);
}

// One pass, no intermediate collection.
public static long sumPositive(
        int[] values) {

    long sum = 0;

    for (int value : values) {
        if (value > 0) {
            sum += value;
        }
    }

    return sum;
}

This example is not a rule that loops always outperform streams. The relevant change combines primitive storage, removal of an intermediate list, and one-pass aggregation. Benchmark the actual operation and retain the more maintainable form when the difference is immaterial.

Repeated immutable concatenation

// Quadratic copying risk as the result grows.
String result = "";

for (String token : tokens) {
    result = result + token + ',';
}

// Mutable accumulation with one final String.
StringBuilder result =
    new StringBuilder(estimatedLength);

for (String token : tokens) {
    result.append(token).append(',');
}

return result.toString();

The Java compiler can translate a single concatenation expression efficiently, but concatenation across loop iterations repeatedly constructs growing results. Pre-sizing the builder can avoid capacity expansions when a reliable estimate is available.

Regex compilation

// Avoid compiling the pattern for every request.
public final class CustomerIds {
    private static final Pattern VALID =
        Pattern.compile("[A-Z]{3}-[0-9]{8}");

    public static boolean isValid(String value) {
        return VALID.matcher(value).matches();
    }
}

Object reuse: use selectively

Pooling ordinary short-lived Java objects can increase retention, synchronization, cache misses, and stale-state bugs. Reuse is more likely to help when construction owns an external or native resource, objects are very large, initialization is expensive, or a measured allocation hotspot cannot be eliminated. Buffers, parsers, and compressors require explicit ownership and size caps.

public final class BufferPool {
    private final ArrayBlockingQueue<byte[]> buffers;
    private final int bufferSize;

    public BufferPool(
            int capacity,
            int bufferSize) {
        this.buffers =
            new ArrayBlockingQueue<>(capacity);
        this.bufferSize = bufferSize;
    }

    public byte[] acquire() {
        byte[] buffer = buffers.poll();
        return buffer != null
            ? buffer
            : new byte[bufferSize];
    }

    public void release(byte[] buffer) {
        if (buffer.length == bufferSize) {
            Arrays.fill(buffer, (byte) 0);
            buffers.offer(buffer);
        }
    }
}
A pool is a retained cache. Bound its count and object size, clear sensitive state, define ownership, and prove with allocation and latency measurements that it improves the workload.

15. Escape analysis and scalar replacement

Escape analysis allows the HotSpot server compiler to analyze how a newly created object is used. The official JVM guide describes global escape, argument escape, and no escape. Objects classified as scalar replaceable may have their allocation removed, and locks on non-escaping objects may be eliminated. HotSpot does not generally implement this as “put the object on the stack”; it can replace the aggregate with scalar values in optimized code.[2][24]

Allocation that may disappear

public record Point(int x, int y) {
}

public static int squaredDistance(
        int x,
        int y) {

    Point point = new Point(x, y);

    return point.x() * point.x()
        + point.y() * point.y();
}

After inlining, the compiler may represent x and y directly and eliminate the Point allocation. This is an optimization opportunity, not a source-level guarantee.

Escaping result

public static Point createPoint(
        int x,
        int y) {

    return new Point(x, y);
}

The returned reference escapes the method, so callers can observe object identity and lifetime. Further inlining into a caller may still expose a larger optimization scope, but the method alone does not guarantee allocation elimination.

Publication prevents local scalar replacement

private static volatile Point latest;

public static void publishPoint(
        int x,
        int y) {

    latest = new Point(x, y);
}

Controlled differential experiment

# Escape analysis is enabled by default.
java -jar target/benchmarks.jar \
  EscapeAnalysisBenchmark \
  -prof gc

# Diagnostic comparison only:
java -XX:-DoEscapeAnalysis \
  -jar target/benchmarks.jar \
  EscapeAnalysisBenchmark \
  -prof gc

-XX:+DoEscapeAnalysis is enabled by default in HotSpot and can be disabled for a controlled experiment.[17] A difference between enabled and disabled runs is evidence that escape analysis matters to that benchmark, but disabling a global optimization changes more than one local allocation and is not a production recommendation.

Help the compiler without contorting the design

  • Keep hot methods small enough to inline, but do not split or merge methods solely by guesswork.
  • Avoid publishing temporary objects through fields, arrays, or global collections.
  • Prefer immutable local aggregates when they clarify code.
  • Measure allocation in the optimized steady state; debugger and profiler modes can affect compilation.
  • Do not replace readable records with parallel primitive locals unless profiling proves a material benefit.

16. CPU optimization

CPU CPU optimization starts with algorithms and data movement. Small instruction-level changes rarely compensate for unnecessary sorting, repeated parsing, poor asymptotic complexity, lock contention, or cache-unfriendly object graphs.

Remove repeated work

// Recomputes normalization for every comparison.
customers.sort(
    Comparator.comparing(
        customer ->
            normalize(customer.displayName())));

// Decorate-sort-undecorate: normalize once.
record SortableCustomer(
        String key,
        Customer value) {
}

List<Customer> sorted =
    customers.stream()
        .map(customer ->
            new SortableCustomer(
                normalize(
                    customer.displayName()),
                customer))
        .sorted(
            Comparator.comparing(
                SortableCustomer::key))
        .map(SortableCustomer::value)
        .toList();

The second form trades temporary allocation for fewer expensive normalizations. A profile and representative benchmark determine which cost dominates.

Fuse passes over data

public static Statistics analyze(
        double[] values) {

    long count = 0;
    double sum = 0;
    double min =
        Double.POSITIVE_INFINITY;
    double max =
        Double.NEGATIVE_INFINITY;

    for (double value : values) {
        if (!Double.isFinite(value)) {
            continue;
        }

        count++;
        sum += value;
        min = Math.min(min, value);
        max = Math.max(max, value);
    }

    return count == 0
        ? Statistics.empty()
        : new Statistics(
            count,
            sum / count,
            min,
            max);
}

Batch boundary crossings

// Chatty: one database round trip per ID.
for (CustomerId id : ids) {
    customers.add(repository.find(id));
}

// Batched contract: one query or bounded groups.
customers.addAll(
    repository.findAll(ids));

Reducing database, network, filesystem, JNI, or synchronization boundary crossings often produces larger gains than local arithmetic tuning.

Avoid boxing in hot numeric paths

// Boxing and generic dispatch.
long sum =
    values.stream()
        .map(Long::valueOf)
        .reduce(0L, Long::sum);

// Primitive specialization.
long sum =
    LongStream.of(values)
        .sum();

Primitive streams avoid wrapper values in the stream's element type. The JLS defines boxing and unboxing conversions between primitives and wrapper references.[26]

Use branch and lookup structure deliberately

// Repeated linear scan.
Handler find(String code) {
    for (Handler handler : handlers) {
        if (handler.code().equals(code)) {
            return handler;
        }
    }
    throw new UnknownHandler(code);
}

// Precomputed lookup for repeated queries.
private final Map<String, Handler> byCode =
    handlers.stream()
        .collect(Collectors.toUnmodifiableMap(
            Handler::code,
            Function.identity()));

The map improves repeated lookup complexity but consumes more memory and build time. The number of handlers and lookup frequency determine whether it is worthwhile.

Inlining and polymorphism

HotSpot uses runtime type profiles and class hierarchy information when compiling calls. Highly polymorphic call sites can be harder to optimize than stable monomorphic or bimorphic sites, but manual type switches can worsen design and performance. Use JFR compilation evidence or compiler diagnostics before restructuring interfaces solely for inlining.

17. Concurrency costs and scalability

Throughput can stop scaling because of locks, atomics, cache-line contention, queues, memory bandwidth, external-resource limits, or oversubscription. More threads increase available concurrency only until a limiting resource saturates.

Measure contention

  • Use JFR monitor-enter, park, thread, socket, and file events.
  • Compare runnable thread count with available processors and CPU utilization.
  • Measure executor queue delay separately from task execution time.
  • Record database connection acquisition and remote-service concurrency.

High-update statistics

public final class RequestCounters {
    private final LongAdder successes =
        new LongAdder();
    private final LongAdder failures =
        new LongAdder();

    public void success() {
        successes.increment();
    }

    public void failure() {
        failures.increment();
    }

    public Snapshot snapshot() {
        return new Snapshot(
            successes.sum(),
            failures.sum());
    }
}

Adder classes are designed for frequently updated summary statistics where exact atomic snapshots are not required for every read. Under contention, they spread updates across internal variables and combine values when read.[27] Use AtomicLong when one linearizable value and compare-and-set semantics are required.

Bound work instead of creating unlimited parallelism

public final class BoundedProcessor
        implements AutoCloseable {

    private final ExecutorService executor;
    private final Semaphore permits;

    public BoundedProcessor(
            int maxConcurrentTasks) {

        this.executor =
            Executors.newVirtualThreadPerTaskExecutor();

        this.permits =
            new Semaphore(maxConcurrentTasks);
    }

    public <T> Future<T> submit(
            Callable<T> task) {

        return executor.submit(() -> {
            permits.acquire();
            try {
                return task.call();
            } finally {
                permits.release();
            }
        });
    }

    @Override
    public void close() {
        executor.close();
    }
}

Virtual threads make blocking-style concurrency inexpensive in thread-management terms, but they do not increase CPU, database connections, memory bandwidth, or downstream capacity. Explicit concurrency limits remain necessary.

False sharing and cache contention

Independent fields updated by different cores can still contend if they occupy the same cache line. Diagnose with scalability curves and hardware-counter tools before adding padding or internal annotations. Layout is an implementation detail and can change with VM options such as compact object headers.

Optimize coordinated omission and queues, not only service time. A task can execute in 1 ms after waiting 500 ms in an executor queue. Measure arrival-to-completion latency and queue delay.

18. Garbage-collection fundamentals

Garbage collection reclaims objects that are no longer reachable. Collector performance depends on allocation rate, object lifetime distribution, live-set size, reference processing, heap capacity, CPU availability, and pause-time requirements. The official JDK 25 GC tuning guide recommends first allowing the VM to select a collector and then tuning from observed behavior.[18][19]

Important metrics

  • Allocation rate: bytes allocated per second or operation.
  • Live set: memory retained after collection under stable load.
  • Headroom: free capacity needed for allocation bursts and concurrent collection.
  • Pause distribution: individual stop-the-world duration and total paused time.
  • GC CPU: processor time consumed by collector threads.
  • Promotion: objects surviving young collections into older regions.
  • Concurrent-cycle health: whether marking and reclamation keep pace with allocation.

Unified GC logging

java \
  -Xms4g \
  -Xmx4g \
  -Xlog:gc*,safepoint:file=/var/log/app-gc.log:\
time,uptime,level,tags:filecount=10,filesize=50m \
  -jar application.jar

Unified JVM logging uses -Xlog selectors, levels, decorators, and output rotation. GC logs expose collection causes, phases, heap occupancy, pause durations, and collector-specific events.[17]

Heap sizing

A heap that is too small can cause frequent collection, promotion pressure, and allocation failure. A heap that is much larger than necessary can increase footprint, recovery cost, and the amount of memory touched or committed. Size from the stable live set plus measured headroom, not from host memory alone.

19. Collector selection

CollectorPrimary objectiveTypical starting useEnable
SerialSmall footprint and simplicitySmall heaps, constrained or single-processor workloads-XX:+UseSerialGC
ParallelHigh throughputBatch and compute workloads tolerating longer pauses-XX:+UseParallelGC

Oracle's JDK 25 guide describes G1 as the default on most hardware and operating-system configurations, Parallel as a throughput collector, Serial as appropriate for small/simple applications, and ZGC as a fully concurrent low-latency collector. Collector choice is a starting point; workload measurements decide the result.[19]

In JDK 25, -XX:+UseZGC selects generational ZGC because the non-generational mode was removed in JDK 24.[23]

20. JVM tuning: principles before flags

JVM JVM tuning should begin with the smallest explicit configuration that enforces operational limits and captures evidence. HotSpot ergonomics already choose compiler, heap, and collector parameters from the runtime environment; every additional flag becomes an assumption that must be revalidated after JDK, hardware, container, and workload changes.

A conservative production baseline

java \
  -Xms2g \
  -Xmx2g \
  -XX:+UseG1GC \
  -XX:+HeapDumpOnOutOfMemoryError \
  -XX:HeapDumpPath=/var/crash/java \
  -XX:ErrorFile=/var/crash/java/hs_err_pid%p.log \
  -Xlog:gc*,safepoint:file=/var/log/java/gc.log:\
time,uptime,level,tags:filecount=10,filesize=50m \
  -XX:StartFlightRecording=\
name=continuous,settings=default,maxage=6h,maxsize=1g,\
disk=true,filename=/var/log/java/continuous.jfr \
  -jar application.jar

What to tune first

  1. Application behavior: algorithms, allocation, caching, database calls, concurrency, and payload size.
  2. Heap maximum: enough for live data and collection headroom while respecting process/container memory.
  3. Collector: choose based on throughput and pause objectives.
  4. One collector goal: for example, a G1 pause target—not dozens of internal region and tenuring flags.
  5. Startup mechanisms: CDS or AOT cache only when startup/warmup is a measured objective.

Do not blindly copy legacy flags

  • Removed or obsolete flags may prevent startup or be ignored.
  • Manual young-generation sizing can interfere with G1's adaptive behavior.
  • Fixed compiler thresholds can improve one phase and harm another.
  • Large thread stacks multiply native memory by platform-thread count.
  • -XX:+AlwaysPreTouch shifts page commitment to startup; it can improve runtime predictability but increases startup work and committed memory.
  • -XX:+DisableExplicitGC changes the behavior of System.gc() requests and can surprise libraries that use them for a documented purpose.

The JDK 25 java tool specification documents current, deprecated, obsolete, and removed options and is the authoritative source for flag availability.[17]

Record the effective configuration

java -XshowSettings:vm -version

jcmd 4217 VM.flags
jcmd 4217 VM.command_line
jcmd 4217 VM.system_properties
A flag is not a fix. If a larger heap hides an unbounded cache or a shorter pause target consumes all available CPU, the underlying capacity problem remains.

21. G1 tuning

G1 is a generational, regional, evacuating collector that performs part of its work concurrently and attempts to meet pause-time goals while retaining useful throughput. Oracle recommends starting with G1 defaults, setting a maximum heap, and optionally selecting a different pause-time goal before changing low-level controls.[21]

Minimal G1 experiment

java \
  -Xms8g \
  -Xmx8g \
  -XX:+UseG1GC \
  -XX:MaxGCPauseMillis=100 \
  -Xlog:gc*,safepoint:file=g1.log:\
time,uptime,level,tags \
  -jar application.jar

MaxGCPauseMillis is a goal rather than a hard real-time guarantee. A tighter goal can make G1 collect young regions more frequently, use more GC CPU, or reduce throughput.

Interpret common G1 symptoms

SymptomEvidencePotential response
Frequent young collectionsHigh allocation rate; low time between pausesReduce allocation or increase heap/headroom before forcing generation sizes
Long evacuation pausesLarge copied live set, many regions, reference processingReduce retained young data, inspect object lifetimes, reconsider pause goal
Full GC or evacuation failureHeap nearly full; concurrent cycle too late; fragmentation or humongous pressureAdd headroom, reduce live set, inspect large objects, review concurrent-cycle timing
High concurrent GC CPUMarking/cleanup active oftenReduce allocation/live set or evaluate larger heap/another collector
Humongous allocation pressureLarge arrays/objects occupy special regionsStream, chunk, compress, or cap payloads; avoid speculative region-size tuning

Why low-level flags are last

Flags such as region size, initiating occupancy, refinement threads, reserve percentage, and tenuring controls affect multiple interacting collector heuristics. Change them only when logs identify a specific failure mode and an A/B load test confirms improvement across latency, throughput, CPU, and footprint.

22. ZGC, Parallel, and Serial collectors

Generational ZGC

java \
  -Xms16g \
  -Xmx16g \
  -XX:+UseZGC \
  -Xlog:gc*,safepoint:file=zgc.log:\
time,uptime,level,tags \
  -jar latency-sensitive-service.jar

ZGC performs most collection work concurrently and is designed for very low pause times. In JDK 25 only the generational mode remains. Lower pauses can require additional concurrent CPU and memory headroom, so compare service throughput and host saturation rather than considering pause duration alone.[19][23]

Parallel GC

java \
  -Xms12g \
  -Xmx12g \
  -XX:+UseParallelGC \
  -Xlog:gc:file=parallel-gc.log:\
time,uptime,level,tags \
  -jar batch-processor.jar

Parallel GC uses multiple GC threads and is intended for high-throughput workloads where longer stop-the-world pauses are acceptable. It is often a useful baseline for batch processing and bounded jobs.[19]

Serial GC

java \
  -Xms128m \
  -Xmx128m \
  -XX:+UseSerialGC \
  -jar small-command-line-tool.jar

Serial GC uses one collector thread and can minimize complexity and auxiliary footprint for small heaps or constrained applications. It is not automatically best for every small service; process-level benchmarks should include startup, throughput, and peak memory.

Shenandoah and vendor distributions

Some OpenJDK distributions provide Shenandoah. JDK 25 integrated Generational Shenandoah, but availability, enablement, support, and maturity depend on the specific JDK build and vendor. Verify the chosen distribution rather than assuming every Java SE implementation ships identical collectors.[1]

23. Native memory and container limits

Enable Native Memory Tracking at startup

java \
  -XX:NativeMemoryTracking=summary \
  -Xms2g -Xmx2g \
  -jar application.jar
# Establish a baseline after startup and warmup.
jcmd 4217 VM.native_memory baseline

# Current summary.
jcmd 4217 VM.native_memory summary scale=MB

# Difference from baseline.
jcmd 4217 VM.native_memory summary.diff scale=MB

NMT is off by default and supports summary and detail modes. It must be enabled at JVM startup; jcmd can then print, baseline, diff, or stop tracking. Oracle documents an approximate 5–10% performance overhead when NMT is enabled and notes that it tracks HotSpot/JVM allocations rather than all third-party native allocations.[20]

Frequent native-memory causes

  • Too many platform threads or oversized -Xss thread stacks.
  • Direct byte buffers retained by caches or delayed cleanup.
  • Unbounded class loading, generated classes, or class-loader leaks.
  • Large code cache caused by application size, generated methods, or compilation activity.
  • Native libraries, compression, TLS, database drivers, and JNI allocations outside NMT coverage.
  • Memory-mapped files and shared libraries contributing to resident set size.

Container budget

# Illustrative budget for a 4 GiB container:
#   Java heap maximum       2.5 GiB
#   Metaspace/code/GC       0.5 GiB
#   Threads/direct/native   0.5 GiB
#   Safety margin           0.5 GiB

java \
  -Xms2500m \
  -Xmx2500m \
  -XX:MaxDirectMemorySize=256m \
  -Xss512k \
  -jar application.jar

This budget is illustrative, not a universal ratio. Measure committed heap, resident memory, thread count, direct buffers, class loading, and native categories under peak load before assigning limits. Setting -Xms equal to -Xmx can improve predictability but reserves a fixed maximum and may commit more aggressively depending on other flags and collector behavior.

24. Startup, warmup, and ahead-of-time caches

Startup performance includes process creation, class loading, linking, verification, configuration, dependency initialization, and initial compilation. Warmup includes runtime profiling and JIT compilation toward optimized code. Measuring only steady state misses serverless, CLI, autoscaling, and short-lived workloads.

Measure fresh processes

for run in $(seq 1 30); do
  /usr/bin/time \
    -f '%e,%M' \
    java -jar application.jar \
    --benchmark-startup \
    2>> startup-results.csv
done

Process-level tests should randomize or control filesystem cache state, CPU frequency, background work, and network dependencies. Report distributions across fresh JVM launches.

JDK 25 AOT cache workflow

JDK 25 simplifies creation and use of ahead-of-time caches and can store method-execution profiles from a training run. These profiles help the JIT compiler optimize hot code sooner in subsequent runs. The cache is workload- and application-specific; the training run must exercise representative startup and early traffic.[32][33]

# JDK 25 one-step training and cache creation.
# The application arguments must exercise representative
# initialization and early hot methods.
java -XX:AOTCacheOutput=app.aot \
  -jar application.jar --training

# Production run using the cache.
java -XX:AOTCache=app.aot \
  -jar application.jar

The one-step workflow launches a second JVM to assemble the cache after the training run. In memory-constrained build environments, use the explicit two-step AOTMode=record and AOTMode=create workflow instead. Recreate caches when application classes, dependencies, relevant command-line configuration, or the JDK build change.[32]

Startup anti-patterns

  • Eagerly loading every plugin, schema, tenant, or remote connection before readiness.
  • Scanning huge class paths when a generated index or module provider list is available.
  • Performing network discovery serially in one startup thread.
  • Running migrations, cache preloads, and health checks without separate deadlines.
  • Optimizing startup at the expense of the first real request without measuring both.

25. Case study: reducing p99 latency and allocation

Initial evidence

A Java HTTP service processes batches of pricing records. At 1,500 requests per second, p99 latency is 420 ms, CPU is 78%, allocation is 2.8 GB/s, and G1 performs a young collection roughly every 240 ms. JFR shows wide stacks in string splitting, regex compilation, boxed stream aggregation, and JSON tree construction.

Original code

public PriceSummary summarize(
        List<String> lines) {

    Pattern delimiter = Pattern.compile(",");

    List<BigDecimal> prices =
        lines.stream()
            .map(delimiter::split)
            .map(parts -> parts[3])
            .map(BigDecimal::new)
            .filter(price ->
                price.signum() >= 0)
            .toList();

    BigDecimal total =
        prices.stream()
            .reduce(
                BigDecimal.ZERO,
                BigDecimal::add);

    return new PriceSummary(
        prices.size(),
        total);
}

Hypotheses

  1. Compiling the same regular expression for every request is unnecessary.
  2. split() creates arrays and substrings for fields that are discarded.
  3. The intermediate price list retains every parsed value until the request completes.
  4. BigDecimal is required for decimal correctness, but aggregation can occur in one pass.

Revised parser

public final class PriceSummarizer {
    public PriceSummary summarize(
            List<String> lines) {

        int count = 0;
        BigDecimal total = BigDecimal.ZERO;

        for (String line : lines) {
            String priceText =
                fourthCsvField(line);

            BigDecimal price =
                new BigDecimal(priceText);

            if (price.signum() < 0) {
                continue;
            }

            count++;
            total = total.add(price);
        }

        return new PriceSummary(count, total);
    }

    private static String fourthCsvField(
            String line) {

        int start = 0;
        int field = 0;

        for (int index = 0;
                index <= line.length();
                index++) {

            boolean boundary =
                index == line.length()
                || line.charAt(index) == ',';

            if (!boundary) {
                continue;
            }

            if (field == 3) {
                return line.substring(start, index);
            }

            field++;
            start = index + 1;
        }

        throw new IllegalArgumentException(
            "Expected at least four CSV fields");
    }
}

Benchmark

@OutputTimeUnit(TimeUnit.MICROSECONDS)

@Measurement(iterations = 8)

    @State(Scope.Thread)
    public static class Data {
        @Param({"10", "100", "1000"})
        int rows;

        List<String> input;
        PriceSummarizer optimized;
        OriginalPriceSummarizer original;

        @Setup(Level.Trial)
        public void setup() {
            input = PriceFixtures.lines(rows);
            optimized = new PriceSummarizer();

                new OriginalPriceSummarizer();

Verification plan

  • Property-test the parser against quoted fields and malformed input; the simple parser above is valid only for the explicitly supported CSV subset.
  • Compare JMH time and bytes/op for all batch sizes.
  • Run production-shaped load with the same JDK, heap, collector, and payload distribution.
  • Compare p50, p95, p99, throughput, CPU, allocation, GC pause sum, and error rate.
  • Re-profile to confirm the original stacks disappear and no new hotspot dominates.
The case-study principle: optimize the represented work, not syntax. The gain comes from removing repeated compilation, unused parsed fields, and an intermediate retained list—not from declaring that loops are inherently faster than streams.

Regression policy

  • Run on dedicated or strongly isolated machines.
  • Pin JDK build, JVM arguments, CPU allocation, and benchmark data.
  • Use multiple forks and retain raw JMH JSON.
  • Compare effect size and uncertainty rather than one score.
  • Use broad thresholds for noisy microbenchmarks and investigate trends over time.
  • Require system-level validation for changes intended to affect production latency or capacity.
  • Track allocation and footprint regressions even when time is stable.

JDK upgrade testing

For a JDK upgrade, compare startup, warmup, steady-state throughput, tail latency, allocation rate, GC pauses, native memory, code cache, and failure behavior. Begin with default or minimal flags; legacy tuning can suppress improvements in newer JVM ergonomics.

27. Production performance checklist

Objectives and workload

  • Latency, throughput, footprint, and capacity objectives are numeric.
  • Input and key distributions match production.
  • Warm, cold, burst, and steady-state phases are distinguished.
  • Correctness and error-rate constraints are part of the benchmark.

Profiling

  • CPU and wall-clock profiles are not confused.
  • Allocation sites and retained objects are analyzed separately.
  • JFR is captured long enough to represent the incident.
  • Thread, lock, I/O, GC, and compilation events are correlated on one timeline.
  • Native memory is measured when RSS exceeds heap expectations.

JMH

  • Benchmarks run in a standalone generated harness.
  • Warmup, measurement, forks, state scope, and parameters are explicit.
  • Results cannot be folded or eliminated.
  • Representative inputs and allocation metrics are included.
  • Raw results and environment metadata are retained.

Memory and allocation

  • Caches, queues, listeners, and histories have bounds and ownership.
  • Heap dumps or old-object samples identify retention paths.
  • Boxing and intermediate collections are removed only from measured hot paths.
  • Object pools are bounded and justified by evidence.
  • Escape-analysis benefits are measured rather than assumed.

CPU and concurrency

  • Algorithmic complexity and repeated work are addressed before micro-operations.
  • Queue delay is measured separately from execution time.
  • Thread and connection counts respect downstream capacity.
  • Lock contention and atomic hot spots are profiled.
  • Remote and database calls are batched when semantics permit.

JVM and GC

  • The exact JDK build and effective flags are recorded.
  • Heap is sized from live set plus measured headroom.
  • The collector matches latency and throughput objectives.
  • GC logs and JFR validate every tuning change.
  • Low-level GC flags are used only for a diagnosed failure mode.
  • Container memory includes native and safety margins, not only -Xmx.
  • Startup and AOT caches are tested with representative training.
Final principle: Java performance engineering is an empirical control loop. Observe the real workload, identify the limiting resource, isolate a hypothesis, change the smallest relevant factor, and verify the result at both micro and system scale. The JVM is an adaptive optimizer; give it representative work and evidence before overriding it.
