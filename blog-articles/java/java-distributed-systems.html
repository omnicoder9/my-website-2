1. Foundations and historical development

A distributed system is not simply a program whose classes happen to run on different machines. Communication becomes delayed and fallible, state is replicated or partitioned, clocks disagree, and one component can fail while every other component continues running.

1978 Lamport formalized the “happened-before” relation and logical clocks, showing how a partial ordering of events can be constructed without assuming a perfectly synchronized global clock.
1983–1985 Fischer, Lynch, and Paterson proved that a deterministic consensus protocol in a fully asynchronous system can fail to terminate when even one process may crash.
2000 Fielding described REST as an architectural style for distributed hypermedia systems, built from constraints including client-server separation, statelessness, caching, uniform interfaces, layered systems, and optional code-on-demand.
2002 Gilbert and Lynch formalized Brewer's conjecture: during a network partition, the asynchronous model cannot guarantee both availability and atomic consistency.
2010s Cloud infrastructure, containers, service meshes, event streaming, GraphQL, and gRPC made independently deployed services and polyglot communication mainstream.
2023+ Java virtual threads restored a scalable direct-style thread-per-request model for high-concurrency, mostly waiting server workloads.

Lamport's logical-clock work distinguished physical time from causal order: if event a can influence event b, then a happened before b. Concurrent events need not have a total causal ordering. This distinction underlies distributed logs, vector clocks, conflict detection, tracing, and replicated-state reasoning. [1]

The FLP result does not say that consensus systems are impossible in practice. It states that deterministic consensus cannot guarantee termination in the fully asynchronous crash-failure model. Real systems make additional timing assumptions, use failure detectors, randomization, leases, quorums, or partially synchronous models. [2]

CAP is likewise conditional rather than a three-way menu for normal operation. Its impossibility result concerns executions in which communication is partitioned: a system cannot simultaneously guarantee that every request receives a non-error response and that every operation appears atomically consistent across the partition. [3]

Operational translation: a remote call has no outcome called “the network failed before anything happened.” The caller may be unable to distinguish “the server never received the request” from “the server committed it and the response was lost.” Idempotency, deduplication, reconciliation, and observability exist because this ambiguity is fundamental.

2. Failure, time, and consistency models

2.1 Failure is multidimensional

Failure Example Required design response
Crash-stop Process exits and does not recover during the observation window Redundancy, restart, replay, ownership transfer
Crash-recovery Process restarts with some durable state and lost memory state Durable journals, idempotent recovery, epoch or fencing tokens
Omission Message or response is lost Timeouts, retries, deduplication
Delay Response arrives after caller timeout Deadlines, cancellation, late-result policy
Duplication Retry delivers the same command or event twice Idempotency keys, inbox tables, natural idempotence
Reordering Version 3 is observed before version 2 Sequence numbers, partition keys, causal metadata
Partition Two healthy regions cannot communicate Explicit consistency/availability decision
Byzantine Component sends arbitrary or contradictory data Authentication, validation, signatures, specialized consensus

2.2 Timeouts are local conclusions

A timeout states that the caller is no longer willing to wait. It does not prove the server stopped, rolled back, or never received the request. gRPC explicitly distinguishes a deadline from successful remote cancellation: when a deadline expires, the client stops waiting, while server application work must still cooperate with cancellation. [17][21]

2.3 Consistency vocabulary

  • Linearizability: operations appear to occur atomically between invocation and response while respecting real-time order.
  • Sequential consistency: all operations fit one total order preserving each process's program order, without requiring real-time order.
  • Read-your-writes: a client sees its own completed updates.
  • Monotonic reads: a client does not move backward to an older observed version.
  • Eventual convergence: replicas that receive the same updates eventually agree when updates stop.

These properties are not interchangeable. “Eventually consistent” does not define how long convergence takes, which anomalies are allowed, or what clients observe during conflict. A useful API states the consistency scope and recovery semantics in domain language. [3][42]

2.4 Idempotency

HTTP defines GET, HEAD, PUT, DELETE, OPTIONS, and TRACE as idempotent methods: multiple identical requests have the same intended effect as one request, although each request can still produce side effects such as logging. POST is not inherently idempotent, but an application can provide idempotency-key semantics. [5] 

public interface IdempotencyStore {
    Optional<StoredResponse> find(String key);
    void reserve(String key, String requestHash);
    void complete(String key, StoredResponse response);
}

public Response createOrder(
        String idempotencyKey,
        CreateOrder command) {

    String requestHash = hashCanonical(command);

    Optional<StoredResponse> existing =
            idempotencyStore.find(idempotencyKey);

    if (existing.isPresent()) {
        return existing.get().toResponse();
    }

    return transactionRunner.required(() -> {
        idempotencyStore.reserve(
                idempotencyKey,
                requestHash);

        Order order = orders.create(command);

        StoredResponse response =
                StoredResponse.created(order.id(), order.version());

        idempotencyStore.complete(
                idempotencyKey,
                response);

        return response.toResponse();
    });
}

Do not choose by payload syntax: JSON versus Protobuf is less important than interaction semantics. Request/response creates temporal coupling. Messaging introduces replay and duplicate-delivery concerns. GraphQL centralizes query planning. Streaming introduces ordering, partitioning, and long-lived flow control.

4. REST APIs

Synchronous REST is an architectural style; HTTP supplies standardized method, representation, caching, conditional-request, and status semantics.

REST was defined by Fielding as a set of architectural constraints for network-based software. HTTP is a stateless application-level protocol whose semantics include resources, methods, representations, conditional requests, authentication, caching, and intermediaries. An HTTP JSON endpoint is not automatically RESTful merely because it uses nouns in URLs. [4][5]

4.1 Jakarta REST resource

Jakarta REST 4.0 maps HTTP-centric resource semantics to Java annotations and POJOs and is the final Jakarta EE 11 release of the specification. It supports resource classes, URI templates, media types, providers, filters, interceptors, clients, server-sent events, and Java SE bootstrap. [8]

OrderResource.javaConditional reads and idempotent creation 
package com.example.orders.api;

import jakarta.ws.rs.*;
import jakarta.ws.rs.core.*;

import java.net.URI;

@Path("/orders")
@Consumes(MediaType.APPLICATION_JSON)
@Produces(MediaType.APPLICATION_JSON)
public final class OrderResource {
    private final OrderService orders;
    private final IdempotencyStore idempotency;

    public OrderResource(
            OrderService orders,
            IdempotencyStore idempotency) {
        this.orders = orders;
        this.idempotency = idempotency;
    }

    @GET
    @Path("/{id}")
    public Response get(
            @PathParam("id") String id,
            @Context Request request) {

        OrderView order = orders.find(id)
                .orElseThrow(NotFoundException::new);

        EntityTag tag =
                new EntityTag(Long.toString(order.version()));

        Response.ResponseBuilder precondition =
                request.evaluatePreconditions(tag);

        if (precondition != null) {
            return precondition.tag(tag).build();
        }

        return Response.ok(order)
                .tag(tag)
                .build();
    }

    @POST
    public Response create(
            @HeaderParam("Idempotency-Key") String key,
            CreateOrder command,
            @Context UriInfo uriInfo) {

        if (key == null || key.isBlank()) {
            throw new BadRequestException(
                    "Idempotency-Key is required");
        }

        CreatedOrder created =
                idempotency.executeOnce(
                        key,
                        command,
                        () -> orders.create(command));

        URI location = uriInfo.getAbsolutePathBuilder()
                .path(created.id())
                .build();

        return Response.created(location)
                .tag(new EntityTag(
                        Long.toString(created.version())))
                .entity(created)
                .build();
    }
}

Conditional requests use validators such as ETags to avoid transferring unchanged representations and to prevent lost updates. HTTP status, cache, and method semantics should be preserved rather than tunneled through a universal 200 OK response body. [5][6]

4.3 JDK HTTP client

Java's HttpClient supports HTTP/1.1 and HTTP/2, synchronous and asynchronous requests, connection reuse, redirects, proxies, authentication, and per-request timeouts. A client should normally be reused rather than created for every call so connections can be pooled. [9]

InventoryHttpClient.javaDeadline, cancellation, and explicit status handling 
package com.example.inventory;

import java.io.IOException;
import java.net.URI;
import java.net.http.*;
import java.time.Duration;
import java.util.Objects;

public final class InventoryHttpClient implements AutoCloseable {
    private final URI baseUri;
    private final HttpClient client;

    public InventoryHttpClient(URI baseUri) {
        this.baseUri = Objects.requireNonNull(baseUri);
        this.client = HttpClient.newBuilder()
                .connectTimeout(Duration.ofSeconds(1))
                .version(HttpClient.Version.HTTP_2)
                .build();
    }

    public Availability reserve(
            String sku,
            int quantity,
            String idempotencyKey)
            throws IOException, InterruptedException {

        String body = """
                {"sku":"%s","quantity":%d}
                """.formatted(sku, quantity);

        HttpRequest request = HttpRequest.newBuilder(
                        baseUri.resolve("/reservations"))
                .timeout(Duration.ofSeconds(2))
                .header("Content-Type", "application/json")
                .header("Accept", "application/json")
                .header("Idempotency-Key", idempotencyKey)
                .POST(HttpRequest.BodyPublishers.ofString(body))
                .build();

        HttpResponse<String> response = client.send(
                request,
                HttpResponse.BodyHandlers.ofString());

        return switch (response.statusCode()) {
            case 201 -> Availability.RESERVED;
            case 409 -> Availability.UNAVAILABLE;
            case 429, 502, 503, 504 ->
                    throw new RetryableInventoryException(
                            response.statusCode(),
                            response.body());
            default ->
                    throw new InventoryProtocolException(
                            response.statusCode(),
                            response.body());
        };
    }

    @Override
    public void close() {
        client.close();
    }
}

4.4 REST compatibility

  • Add optional fields before removing or changing existing fields.
  • Do not repurpose status codes or resource identifiers.
  • Make enum expansion safe for clients or represent open sets as strings.
  • Use media-type or URI versioning only when semantic compatibility cannot be preserved.
  • Publish OpenAPI descriptions as testable contracts, not as the sole source of behavior.

5. GraphQL

Client-selected graph GraphQL defines a typed schema, validation, execution, introspection, and a response model that can contain both data and errors.

GraphQL was created internally in 2012, opened for standardization in 2015, and is maintained as an open specification. The September 2025 specification defines a query language and execution system for client-server applications. A GraphQL operation selects fields from a schema; the response mirrors the requested shape. [10]

5.1 Schema

schema.graphqlsTyped public contract 
type Query {
  order(id: ID!): Order
  orders(customerId: ID!, first: Int = 20): OrderConnection!
}

  createOrder(input: CreateOrderInput!): CreateOrderPayload!
}

  id: ID!

}

  id: ID!

}

  sku: String!

}

  amount: String!
  currency: String!
}

  PENDING
  CONFIRMED
  CANCELLED
}

  customerId: ID!
  items: [CreateOrderItemInput!]!
  idempotencyKey: ID!
}

  sku: String!

}

  order: Order
  userErrors: [UserError!]!

  code: String!

}

  nodes: [Order!]!
  nextCursor: String
}

GraphQL nullability controls error propagation. If a resolver fails for a nullable field, that field can become null while an error is added to the response. If a non-null field resolves to null, the error propagates to the nearest nullable parent. Schema authors should therefore use non-null to express real invariants, not optimism. [10]

5.2 GraphQL Java wiring

GraphQL Java can build a schema programmatically or parse Schema Definition Language and attach DataFetcher and TypeResolver implementations. Its execution engine can return synchronous values or CompletableFuture results. [11][12]

GraphQlFactory.javaSDL and runtime wiring 
package com.example.graphql;

import graphql.GraphQL;
import graphql.schema.GraphQLSchema;
import graphql.schema.idl.*;

import java.io.Reader;

public final class GraphQlFactory {
    public static GraphQL create(
            Reader schemaReader,
            OrderQueries orderQueries,
            OrderMutations orderMutations) {

        TypeDefinitionRegistry registry =
                new SchemaParser().parse(schemaReader);

        RuntimeWiring wiring = RuntimeWiring.newRuntimeWiring()
                .type("Query", builder -> builder
                        .dataFetcher(
                                "order",
                                environment ->
                                        orderQueries.find(
                                                environment.getArgument("id")))
                        .dataFetcher(
                                "orders",
                                environment ->
                                        orderQueries.findByCustomer(
                                                environment.getArgument("customerId"),
                                                environment.getArgument("first"))))
                .type("Mutation", builder -> builder
                        .dataFetcher(
                                "createOrder",
                                environment ->
                                        orderMutations.create(
                                                environment.getArgument("input"))))
                .build();

        GraphQLSchema schema =
                new SchemaGenerator()
                        .makeExecutableSchema(registry, wiring);

        return GraphQL.newGraphQL(schema)
                .build();
    }
}

5.3 N+1 queries and DataLoader

A field resolver that loads one customer for every order can issue N additional calls after loading N orders. GraphQL Java supports batching through DataLoader so keys encountered during an execution can be combined into fewer backend calls and results can be cached within the request. [13] 

MappedBatchLoader<String, Customer> customerLoader =
        customerIds ->
                CompletableFuture.supplyAsync(
                        () -> customerRepository.findAllById(customerIds));

DataLoaderRegistry loaders = new DataLoaderRegistry();
loaders.register(
        "customers",
        DataLoaderFactory.newMappedDataLoader(customerLoader));

DataFetcher<CompletableFuture<Customer>> customerFetcher =
        environment -> {
            Order order = environment.getSource();
            DataLoader<String, Customer> loader =
                    environment.getDataLoader("customers");
            return loader.load(order.customerId());
        };

5.4 Query cost and authorization

  • Limit depth, field count, aliases, list sizes, and total estimated complexity.
  • Authorize the field and object being resolved, not only the top-level operation.
  • Use persisted or allowlisted operations for tightly controlled clients.
  • Set end-to-end deadlines on resolver I/O.
  • Expose resolver timing and batching behavior through GraphQL Java instrumentation.

GraphQL Java's instrumentation interface can observe or alter parsing, validation, execution, field fetching, and result handling. It is the appropriate extension point for complexity analysis, tracing, metrics, and policy enforcement. [14]

6. gRPC and Protocol Buffers

Typed RPC gRPC defines services and messages in an interface definition language and generates Java client and server code.

HTTP/2 Unary, server-streaming, client-streaming, and bidirectional-streaming RPCs share channels and transport facilities.

gRPC models remote operations as service methods. Protocol Buffers commonly serve as both the interface definition language and wire format. Java code generation supplies message types, service base classes, and client stubs. [15][16]

6.1 Service definition

inventory.protoUnary and server-streaming methods

  rpc Reserve(ReserveRequest) returns (ReserveResponse);

    OUTCOME_UNSPECIFIED = 0;
    RESERVED = 1;
    UNAVAILABLE = 2;

  Outcome outcome = 1;

  repeated string sku = 1;
}

  string sku = 1;

6.2 Schema evolution

Protocol Buffer field numbers identify fields on the wire and must not be reused after removal. New fields are generally compatible when old readers can ignore them and new readers can use defaults or explicit presence. Enum zero values should represent an unspecified state. Generated code and runtime versions have documented compatibility constraints and should be upgraded deliberately. [18][19] 

message ReserveRequest {
  string request_id = 1;
  string sku = 2;
  int32 quantity = 3;

  reserved 4;              // Removed field number is never reused.
  reserved "warehouse";    // Removed field name is reserved.

  optional string region = 5;
}

6.3 Java server

InventoryGrpcService.javaMap domain outcomes to protocol outcomes 
package com.example.inventory.grpc;

import com.example.inventory.v1.*;
import io.grpc.Status;
import io.grpc.stub.StreamObserver;

public final class InventoryGrpcService
        extends InventoryServiceGrpc.InventoryServiceImplBase {

    private final InventoryApplicationService inventory;

    public InventoryGrpcService(
            InventoryApplicationService inventory) {
        this.inventory = inventory;
    }

    @Override
    public void reserve(
            ReserveRequest request,
            StreamObserver<ReserveResponse> observer) {

        try {
            ReservationResult result =
                    inventory.reserve(
                            request.getRequestId(),
                            request.getSku(),
                            request.getQuantity());

            ReserveResponse response =
                    switch (result) {
                        case Reserved reserved ->
                                ReserveResponse.newBuilder()
                                        .setOutcome(
                                                ReserveResponse.Outcome.RESERVED)
                                        .setReservationId(reserved.id())
                                        .build();

                        case Unavailable ignored ->
                                ReserveResponse.newBuilder()
                                        .setOutcome(
                                                ReserveResponse.Outcome.UNAVAILABLE)
                                        .build();
                    };

            observer.onNext(response);
            observer.onCompleted();
        } catch (IllegalArgumentException invalid) {
            observer.onError(
                    Status.INVALID_ARGUMENT
                            .withDescription(invalid.getMessage())
                            .withCause(invalid)
                            .asRuntimeException());
        } catch (RuntimeException failure) {
            observer.onError(
                    Status.INTERNAL
                            .withDescription("Reservation failed")
                            .withCause(failure)
                            .asRuntimeException());
        }
    }
}

gRPC defines a standard health service with unary Check and streaming Watch methods. 7. Microservices

Microservices organize a system as independently deployable services aligned to business capabilities, with decentralized data ownership and automation around deployment and operation. The style gained broad attention in the early 2010s, but it builds on earlier service-oriented, Unix-process, and distributed-object traditions. [40][43]

7.1 A service boundary is more than a package boundary

Property In-process module Microservice boundary
Call failure Usually immediate exception Timeout, duplication, partition, partial response
Versioning One build graph Independent deployment and compatibility window
Data Shared memory or transaction Owned persistence and asynchronous consistency
Security Language visibility Network identity, authentication, authorization, encryption
Observability Stack trace Metrics, distributed tracing, correlated logs
Cost Nanoseconds to microseconds Serialization, queues, network, proxies, retries, storage

7.2 When a modular monolith is the stronger choice

  • The domain boundaries are still being discovered.
  • One team owns the system and deploys it together.
  • Transactions commonly span proposed service boundaries.
  • Independent scaling or security isolation is not required.
  • Operational maturity for distributed tracing, gateways, messaging, and incident response is limited.

7.3 Request fan-out

ProductPageService.javaVirtual-thread aggregation with one overall deadline 
package com.example.product;

import java.time.Duration;
import java.util.concurrent.*;

public final class ProductPageService {
    private final CatalogClient catalog;
    private final PriceClient pricing;
    private final ReviewClient reviews;

    public ProductPage load(String productId)
            throws InterruptedException {

        long deadline =
                System.nanoTime()
                        + Duration.ofSeconds(1).toNanos();

        try (var executor =
                     Executors.newVirtualThreadPerTaskExecutor()) {

            Future<Product> product =
                    executor.submit(
                            () -> catalog.find(productId));

            Future<Price> price =
                    executor.submit(
                            () -> pricing.find(productId));

            Future<ReviewSummary> review =
                    executor.submit(
                            () -> reviews.summary(productId));

            try {
                return new ProductPage(
                        getBeforeDeadline(product, deadline),
                        getBeforeDeadline(price, deadline),
                        getBeforeDeadline(review, deadline));
            } catch (ExecutionException
                     | TimeoutException failure) {

                product.cancel(true);
                price.cancel(true);
                review.cancel(true);
                throw new ProductPageUnavailable(failure);
            }
        }
    }

    private static <T> T getBeforeDeadline(
            Future<T> future,
            long deadline)
            throws ExecutionException,
                   InterruptedException,
                   TimeoutException {

        long remaining =
                Math.max(0L, deadline - System.nanoTime());

        return future.get(remaining, TimeUnit.NANOSECONDS);
    }
}

Virtual threads, finalized in Java 21, allow thread-per-request code to scale for high-concurrency workloads that spend much of their time waiting. They do not increase CPU capacity and should not replace explicit connection limits, deadlines, bulkheads, or downstream quotas. [25][26]

Fan-out amplifies tail latency: if one response requires ten independent remote calls, its success and latency depend on all ten. Reduce unnecessary hops, parallelize only independent work, use partial-result policy deliberately, and keep one end-to-end deadline budget.

8. Service discovery

Service discovery maps a logical service identity to one or more changing network endpoints. Client-side discovery returns endpoints to the client, which selects a destination. Server-side discovery sends the client to a stable proxy or virtual address that chooses a backend.

8.1 Kubernetes Services and DNS

Kubernetes Service objects define a stable abstraction over dynamic Pod endpoints. EndpointSlices represent the backing addresses. Cluster DNS creates records so workloads can resolve Services by name rather than tracking Pod IP addresses. [27][28]

inventory-service.ymlStable service identity

inventory:8080

# Fully qualified:
inventory.default.svc.cluster.local:8080

# gRPC target URI:
dns:///inventory.default.svc.cluster.local:50051

A normal ClusterIP Service gives clients one virtual address. A headless Service sets clusterIP: None and publishes endpoint addresses directly through DNS, allowing clients or stateful protocols to select individual backends. [27]

8.2 Discovery is not health

DNS resolution proves that an address was published, not that the instance can serve the current request. Readiness, active health checking, connection failure, and application-specific availability remain separate concerns. Remove unready endpoints promptly and make clients tolerate stale DNS and connection pools.

8.3 Client behavior

  • Reuse channels and HTTP clients so connection pools adapt to endpoint changes.
  • Honor DNS TTL and resolver update behavior.
  • Use bounded connection attempts and deadlines.
  • Prefer logical service names in configuration, not instance IPs.
  • Report resolved endpoints and load-balancer state in diagnostics.

gRPC Java's NameResolver is a pluggable component that resolves target URIs and can provide continuously updated address sets. The channel combines name resolution, connectivity, health, service configuration, and a load-balancing policy. [24]

9. API gateways

An API gateway presents a common external interface and can centralize TLS termination, authentication integration, routing, rate limits, request normalization, observability, and protocol translation. It should not become a second business-logic monolith.

Kubernetes Gateway API is an official SIG-Network project for L4 and L7 routing. Its role-oriented model separates GatewayClass, Gateway, and protocol-specific Route resources. HTTPRoute and GRPCRoute map incoming traffic to Services, with attachment controlled by both route and listener configuration. [29][30]

10. Circuit breakers and resilience patterns

Circuit breaker Stops repeatedly calling a dependency whose recent outcomes exceed configured failure or slow-call thresholds.

Bulkhead Limits concurrent work so one dependency cannot consume all capacity.

Retry Repeats selected transient failures with a bounded policy.

Resilience4j 2 requires Java 17 and provides circuit breaker, retry, rate limiter, bulkhead, time limiter, cache, and integrations. Its circuit breaker uses a sliding window and transitions among closed, open, and half-open states according to configured failure and slow-call rates. [31][32]

10.1 Circuit breaker

ResilientInventoryClient.javaTimeout first, breaker around remote outcome 
package com.example.inventory;

import io.github.resilience4j.circuitbreaker.*;
import io.github.resilience4j.retry.*;
import io.github.resilience4j.bulkhead.*;

import java.io.IOException;
import java.time.Duration;
import java.util.function.Supplier;

public final class ResilientInventoryClient {
    private final InventoryHttpClient delegate;
    private final CircuitBreaker breaker;
    private final Retry retry;
    private final Bulkhead bulkhead;

    public ResilientInventoryClient(
            InventoryHttpClient delegate) {

        this.delegate = delegate;

        this.breaker = CircuitBreaker.of(
                "inventory",
                CircuitBreakerConfig.custom()
                        .slidingWindowType(
                                CircuitBreakerConfig.SlidingWindowType.COUNT_BASED)
                        .slidingWindowSize(50)
                        .minimumNumberOfCalls(20)
                        .failureRateThreshold(50.0f)
                        .slowCallRateThreshold(50.0f)
                        .slowCallDurationThreshold(
                                Duration.ofMillis(500))
                        .waitDurationInOpenState(
                                Duration.ofSeconds(10))
                        .permittedNumberOfCallsInHalfOpenState(5)
                        .recordException(
                                this::isDependencyFailure)
                        .build());

        this.retry = Retry.of(
                "inventory",
                RetryConfig.custom()
                        .maxAttempts(3)
                        .waitDuration(Duration.ofMillis(50))
                        .retryOnException(
                                this::isRetryable)
                        .build());

        this.bulkhead = Bulkhead.of(
                "inventory",
                BulkheadConfig.custom()
                        .maxConcurrentCalls(50)
                        .maxWaitDuration(Duration.ZERO)
                        .build());
    }

    public Availability reserve(
            String sku,
            int quantity,
            String idempotencyKey) {

        Supplier<Availability> operation = () -> {
            try {
                return delegate.reserve(
                        sku,
                        quantity,
                        idempotencyKey);
            } catch (IOException io) {
                throw new InventoryTransportException(io);
            } catch (InterruptedException interrupted) {
                Thread.currentThread().interrupt();
                throw new InventoryTransportException(interrupted);
            }
        };

        Supplier<Availability> protectedCall =
                Bulkhead.decorateSupplier(
                        bulkhead,
                        CircuitBreaker.decorateSupplier(
                                breaker,
                                Retry.decorateSupplier(
                                        retry,
                                        operation)));

        return protectedCall.get();
    }

    private boolean isRetryable(Throwable failure) {
        return failure instanceof RetryableInventoryException
                || failure instanceof InventoryTransportException;
    }

    private boolean isDependencyFailure(Throwable failure) {
        return isRetryable(failure)
                || failure instanceof InventoryProtocolException;
    }
}

10.2 Order of policies

Policy ordering changes semantics. A circuit breaker outside retry observes one logical operation after retries; a breaker inside retry observes each attempt. A bulkhead outside retry limits the whole operation, while a bulkhead inside can release capacity between attempts. Document the intended unit being counted.

10.3 Retry rules

  • Retry transient transport and availability failures, not validation or permanent authorization failures.
  • Set a maximum attempt count and one overall deadline.
  • Use exponential backoff with jitter across many clients.
  • Retry only idempotent operations or commands carrying deduplication identity.
  • Respect server signals such as Retry-After when semantics permit.
  • Expose attempts and final outcomes as metrics and traces.

10.4 Circuit breakers are local memory

A Resilience4j circuit breaker is local to one process. Ten replicas can have ten different breaker states. This is often desirable because they observe different connections and load, but it is not a globally coordinated dependency-health decision. [32]

Never stack resilience blindly: gateway retries, service-mesh retries, client retries, library retries, and broker redelivery can multiply one user request into a retry storm. Assign retry ownership at one layer and budget the maximum total attempts.

11.4 Poison messages and retries

  • Separate transient transport failures from invalid payloads and permanent domain rejection.
  • Bound retries and add delay to avoid hot loops.
  • Quarantine irrecoverable messages with original payload, headers, failure, and schema metadata.
  • Preserve ordering requirements when moving one record around a failed predecessor.
  • Expose consumer lag, retry count, processing latency, and quarantine rate.
“Exactly once” has a boundary: Kafka transactions can provide exactly-once semantics for supported Kafka read-process-write workflows. An email, payment API, filesystem, or ordinary database outside that transaction still needs idempotency or another atomicity design.

12. Event-driven architecture

Event A statement that something relevant occurred.

Command A request that one logical handler perform an action.

Reply A result correlated to a prior request or command.

Event-driven architecture connects components through events rather than direct temporal coordination. Producers publish facts without knowing every consumer. Consumers build projections, trigger processes, integrate systems, or derive further events.

12.1 Event naming and semantics

package com.example.events;

import java.time.Instant;

        String specVersion,
        String id,
        URI source,
        String type,
        String subject,
        Instant time,
        String dataContentType,
        URI dataSchema,
        T data) {

        if (!"1.0".equals(specVersion)) {

        Objects.requireNonNull(source);

12.4 Event evolution

  • Events are contracts and remain observable after the producing code changes.
  • Add optional fields before removing or changing existing fields.
  • Do not change the meaning of an existing event type.
  • Create a new major event type for incompatible semantic changes.
  • Keep producer implementation details out of the public envelope.
  • Publish schema and compatibility policy with ownership and retention assumptions.

12.5 Event notification versus event-carried state

A notification event can contain only an identifier and require consumers to call the producer, preserving strong coupling to producer availability and current state. An event-carried-state transfer includes the data consumers need, increasing payload size and schema responsibility but reducing synchronous coupling. Choose deliberately per consumer and data-governance requirement.

13. Distributed data, outbox, and sagas

13.1 Avoid shared-database microservices

When independently deployed services write the same tables, database schema and transaction behavior become an undocumented shared API. Prefer one service owning writes to a data set and expose read models, APIs, events, or replicated projections to others.

13.2 The dual-write problem

@Transactional
public Order confirm(OrderId id) {
    Order order = orders.confirm(id);
    kafkaProducer.send(toEvent(order)); // Different transactional resource.
    return order;
}

The database commit and broker publish do not share one ordinary local transaction. A crash can occur after either side succeeds. Retrying can then duplicate the successful side. The transactional outbox pattern records the business update and an outbox row in one database transaction, then a relay or change-data-capture connector publishes the outbox event. [38][39]

13.6 Sagas

A saga coordinates a long-running business transaction as local transactions plus compensating actions. Choreography distributes coordination through events; orchestration gives one process manager explicit state and command responsibility. Compensation is a business action, not a database rollback: a refund does not erase the historical charge. [43]

public List<Command> react(
        OrderSagaState state,
        DomainEvent event) {

    return switch (state) {
        case AwaitingInventory waiting
                when event instanceof InventoryReserved reserved ->
                List.of(
                        new CapturePayment(
                                waiting.orderId(),
                                reserved.reservationId(),
                                stablePaymentRequestId(waiting.orderId())));

        case AwaitingInventory waiting
                when event instanceof InventoryRejected rejected ->
                List.of(
                        new RejectOrder(
                                waiting.orderId(),
                                rejected.reason()));

        case AwaitingPayment waiting
                when event instanceof PaymentCaptured ->
                List.of(
                        new CompleteOrder(waiting.orderId()));

        case AwaitingPayment waiting
                when event instanceof PaymentFailed failed ->
                List.of(

                                waiting.reservationId()),
                        new RejectOrder(
                                waiting.orderId(),
                                failed.reason()));

        default -> List.of();
    };
}
Persist saga state before sending commands. Every command needs stable identity; every reply needs correlation; timeouts need durable schedules; and repeated events must be safe.

14. Java concurrency for distributed services

Java virtual threads are lightweight Thread instances managed by the JDK. They allow server applications to keep straightforward blocking code while supporting large numbers of concurrent, mostly waiting operations. JDK 24 removed nearly all synchronized-block pinning cases, improving compatibility with existing libraries. [25][26]

14.1 One virtual thread per request—not one unlimited dependency call per request

public final class BoundedRemoteClient {
    private final Semaphore permits;
    private final InventoryHttpClient client;

    public BoundedRemoteClient(
            int maxConcurrentCalls,
            InventoryHttpClient client) {

        this.permits = new Semaphore(maxConcurrentCalls);
        this.client = client;
    }

    public Availability reserve(
            String sku,
            int quantity,
            String idempotencyKey) throws Exception {

        if (!permits.tryAcquire(
                25,
                TimeUnit.MILLISECONDS)) {
            throw new DependencyOverloadedException();
        }

        try {
            return client.reserve(
                    sku,
                    quantity,
                    idempotencyKey);
        } finally {
            permits.release();
        }
    }
}

14.2 Cancellation and interruptibility

Timeouts and canceled requests should propagate through Java interruption, HTTP future cancellation, gRPC context cancellation, database statement timeouts, and child-task ownership. Code that catches InterruptedException should restore interrupt status unless it is deliberately translating or completing the cancellation. 

try {
    return queue.take();
} catch (InterruptedException interrupted) {
    Thread.currentThread().interrupt();
    throw new RequestCancelled(interrupted);
}

14.3 Backpressure

A system needs a bounded policy at every queue: reject, shed, block, spill to durable storage, reduce producer rate, or degrade quality. An unbounded executor or in-memory queue transforms temporary downstream slowness into heap exhaustion and long tail latency.

15. Observability across service boundaries

Distributed systems require correlation across HTTP, gRPC, messaging, databases, gateways, and background processes. OpenTelemetry Java supports automatic and manual instrumentation for traces, metrics, and logs, including a Java agent and library integrations. [41]

15.1 Minimum service telemetry

  • Request or message rate by bounded operation.
  • Error and rejection ratio by stable outcome category.
  • Latency distribution and deadline-exceeded count.
  • Concurrency, queue depth, pool saturation, and consumer lag.
  • Retry attempts, circuit-breaker state, bulkhead rejection, and fallback use.
  • Trace context propagated through synchronous and asynchronous boundaries.
  • Structured logs carrying trace, span, message, and idempotency identifiers.

15.3 Unknown-outcome dashboards

Track operations whose callers timed out but whose final state was later reconciled. A high unknown outcome rate indicates deadline mismatch, overloaded downstreams, or responses lost after commit, even when final business state is correct.

16. Security

16.1 Authenticate workloads, authorize domain actions

Gateways and service meshes can authenticate a workload identity or validate a bearer token. The service must still authorize access to the requested resource, tenant, account, field, command, or event. GraphQL field resolvers and asynchronous consumers need the same domain authorization rigor as REST controllers.

16.2 Transport security

  • Use TLS for external and sensitive internal traffic.
  • Verify service identity; do not disable hostname or certificate validation.
  • Rotate credentials and certificates without requiring global restarts.
  • Separate client identity from end-user identity and preserve delegation context explicitly.
  • Restrict gateway route attachment and cross-namespace backend references through platform authorization.

Gateway API was designed with distinct infrastructure-provider, cluster-operator, and application developer roles and relies on Kubernetes RBAC and attachment controls to prevent one actor from exposing another actor's service without agreement. [29][30]

16.3 Message security

  • Authorize producers and consumers per topic or destination.
  • Validate event type, schema version, source, and size before deserialization.
  • Avoid Java native object serialization as an interoperability format.
  • Encrypt or tokenize sensitive event fields and set retention accordingly.
  • Sign high-integrity events when broker authorization alone is insufficient.

16.4 Prevent amplification

Bound GraphQL query complexity, gRPC message sizes, HTTP bodies, decompression ratios, pagination, batch sizes, streaming concurrency, retry counts, and event fan-out. A valid authenticated request can still exhaust the system.

ClientREST or GraphQL request with identity and idempotency key.

18.1 Interaction choices

  • REST: public order commands and resources.
  • GraphQL: client-specific read composition over projections.
  • gRPC: typed low-latency internal inventory and pricing calls.
  • Kafka: order lifecycle events, fan-out, replay, and projections.
  • Outbox: atomic order-state and event intent persistence.
  • Saga: durable coordination of inventory, payment, and fulfillment.

18.2 Request flow

  1. Gateway authenticates the client and forwards a bounded identity context.
  2. Order service validates the command and claims the idempotency key.
  3. Service performs necessary deadline-bounded synchronous checks.
  4. Order state and an order.created outbox event commit atomically.
  5. The client receives 201 Created or the stored prior response.
  6. CDC or an outbox relay publishes the event to a topic keyed by order ID.
  7. Consumers process idempotently and emit replies or further domain events.
  8. The saga advances durable state and issues stable command IDs.
  9. GraphQL reads denormalized projections rather than fan-out calling every write service.

            requests:
              cpu: "250m"
              memory: "256Mi"
            limits:
              memory: "512Mi"
Keep the synchronous critical path short. Accept the command, commit authoritative state, and move nonessential fan-out to durable events. Synchronous calls remain appropriate when the response cannot be correct without the result.

19. Decision guide

  1. Define the business invariant. State what must never be duplicated, lost, reordered, or observed inconsistently.
  2. Choose temporal coupling. Does the producer require an immediate result, or can work continue asynchronously?
  3. Choose the contract model. Resource semantics, client-selected graph, typed RPC, command queue, or event log.
  4. Define identity. Resource ID, idempotency key, event ID, correlation ID, partition key, and trace ID serve different purposes.
  5. Set the deadline budget. Allocate time across gateway, service, dependency, retries, and cleanup.
  6. Assign retry ownership. Select one layer and define retryable outcomes, attempts, backoff, and idempotency.
  7. Define consistency. Specify authoritative state, replica lag, read-your-writes behavior, and reconciliation.
  8. Design compatibility. HTTP representation, GraphQL schema, Protobuf fields, and event schemas evolve independently.
  9. Bound every queue. Threads, connections, requests, broker buffers, consumer work, and dead letters need limits.
  10. Test ambiguity. Simulate commit-before-response-loss, duplicate delivery, stale discovery, and partial completion.

Requirement Likely starting point
Broad public interoperability and caching REST over HTTP
Flexible client-specific read graph GraphQL over read models
Strongly typed internal RPC and streaming gRPC with Protocol Buffers

20. Production checklist

Protocols and contracts

  • REST methods, status codes, ETags, caching, and errors follow HTTP semantics.
  • GraphQL depth, complexity, batching, nullability, and field authorization are controlled.
  • gRPC clients set deadlines; servers stop canceled work; retry policy is explicit.
  • Protobuf field numbers and removed names are never reused.
  • Event schemas, ownership, partition keys, and compatibility policy are published.

Resilience

  • One overall deadline is propagated through every call.
  • Retries are bounded, jittered, observable, and limited to replay-safe operations.
  • Circuit breakers and bulkheads have measured thresholds and dashboards.
  • Every queue, executor, connection pool, and batch is bounded.
  • Overload behavior is explicit: reject, shed, degrade, or persist.

Messaging and data

  • Consumers tolerate duplicate delivery and crash recovery.
  • Poison-message and quarantine policy is tested.
  • Database plus broker dual writes use an outbox, transaction, or reconciliation design.
  • Saga state, timers, commands, and compensations are durable and idempotent.
  • Replays produce stable projections and do not repeat external side effects.

Discovery and gateways

  • Clients use stable logical service names and tolerate endpoint churn.
  • Readiness and protocol health are separate from DNS publication.
  • Gateway route ownership and cross-namespace attachment are controlled.
  • Rate limits, body limits, TLS, and authentication policy are tested at the edge.
  • Gateway and mesh retries do not duplicate application-level retry ownership.

Observability and security

  • Metrics expose rate, error, latency, saturation, retries, breaker state, and lag.
  • Trace context crosses HTTP, gRPC, outbox, broker, and consumer boundaries.
  • Logs carry stable operation, trace, event, and idempotency identifiers.
  • Credentials and personal data are excluded from metric labels and event envelopes unless required and protected.
  • Runbooks cover unknown outcomes, duplicate commands, stalled sagas, and consumer backlog.
Final principle: distributed-systems reliability is not produced by adding microservices, Kafka, retries, or a service mesh. It comes from making uncertainty explicit: bounded waiting, stable identity, replay-safe behavior, compatible contracts, durable state, controlled load, and evidence that explains what happened.
