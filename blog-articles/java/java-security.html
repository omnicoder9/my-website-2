1. A security model before an API call

Security code is correct only relative to an asset, attacker, trust boundary, protocol, and failure policy. Cryptographic primitives protect specific properties; they do not automatically authenticate users, authorize actions, secure keys, or make a protocol replay-resistant.

Confidentiality

Unauthorized parties cannot recover protected plaintext.

Integrity and authenticity

Unauthorized modification is detected and the origin is authenticated under an appropriate key.

Authentication

A claimant proves control of one or more authenticators bound to an identity.

Authorization

An authenticated subject is permitted or denied an operation on a resource under policy.

The Java Cryptography Architecture (JCA) provides provider-based APIs for secure random generation, message digests, signatures, encryption, MACs, key generation, key derivation, key encapsulation, key storage, certificates, and certificate-path validation.[1] JSSE builds TLS/DTLS secure communication on the same provider architecture, while JAAS supplies pluggable authentication and a subject/principal model.[2][3]

Do not invent a cryptographic protocol. Use a standardized protocol or a reviewed high-level construction. Correct calls to Cipher, Signature, or MessageDigest can still form an insecure protocol when nonces, context, canonicalization, replay protection, or key separation are wrong.

2. Current platform context

Java 1.1–1.4: JCA, signed code, JAAS, JSSE, and PKIX certification-path APIs became core platform facilities.

Java 9: PKCS #12 became the default keystore type, and the JDK added configurable NIST SP 800-90A DRBG implementations.[4][5]

Java 15: The JDK added Ed25519 and Ed448 EdDSA signatures standardized by RFC 8032.[6]

Java 18: Subject.current() and Subject.callAs() provided a modern subject-propagation model.

Java 24: The Security Manager was permanently disabled. Policy-file and permission-based JAAS authorization ceased to be supported.[7]

Java 25: JAAS authentication, JCA, PKIX, KeyStore, JSSE, and application-managed authorization remain available; old Subject.doAs/getSubject and AccessControlContext-related APIs are deprecated for removal.[3][8]

4. Algorithm names, restrictions, and policy

Java standard algorithm names define portable identifiers such as SHA-256, HmacSHA256, AES/GCM/NoPadding, Ed25519, RSASSA-PSS, PKIX, and PKCS12. Required support depends on the engine and Java version.[9]

Do not infer security from availability

An installed provider may expose legacy algorithms for compatibility. The JDK security-properties file independently restricts algorithms for certificate validation, TLS, signed JARs, and XML signatures through properties including jdk.certpath.disabledAlgorithms, jdk.tls.disabledAlgorithms, and jdk.jar.disabledAlgorithms.[10]

System.out.println(
    Security.getProperty(
        "jdk.certpath.disabledAlgorithms"));

System.out.println(
    Security.getProperty(
        "jdk.tls.disabledAlgorithms"));

Selection rules

  • Use approved, standardized algorithms and complete transformations.
  • Specify algorithm parameters and key sizes; provider defaults can differ and change.[11]
  • Use authenticated encryption for application data, not bare AES modes that provide confidentiality alone.
  • Use a KDF/password hashing function for passwords, not a fast digest.
  • Use a MAC when parties share a secret; use a digital signature when verification must use a public key.
  • Version encrypted and signed data so algorithms and keys can rotate.

5. SecureRandom

Randomness SecureRandom is the JCA engine for cryptographically strong random values. Many implementations are deterministic random bit generators seeded from entropy sources. JDK DRBG support implements mechanisms described by NIST SP 800-90A.[5][12]

General-purpose instance

public final class RandomSource {
    private static final SecureRandom RANDOM =
        new SecureRandom();

    private RandomSource() {
    }

    public static byte[] bytes(int length) {
        if (length < 1) {
            throw new IllegalArgumentException(
                "length must be positive");
        }

        byte[] value = new byte[length];
        RANDOM.nextBytes(value);
        return value;
    }
}

A long-lived SecureRandom instance is appropriate for ordinary token, nonce, salt, and key-generation support. Do not seed it with timestamps, process IDs, usernames, or other low-entropy values.

Explicit DRBG

byte[] personalization =
    "orders-service/session-token/v1"
        .getBytes(StandardCharsets.UTF_8);

SecureRandom random =
    SecureRandom.getInstance(
        "DRBG",
        DrbgParameters.instantiation(
            256,
            DrbgParameters.Capability.RESEED_ONLY,
            personalization));

Explicit DRBG parameters can document security strength, reseeding capability, and personalization. Availability and provider configuration must be tested in the deployment environment.[5]

getInstanceStrong()

SecureRandom.getInstanceStrong() follows the securerandom.strongAlgorithms security property. It can select an implementation with different latency or blocking characteristics; use it only when the application has measured and accepted those operational semantics.

Never use java.util.Random, ThreadLocalRandom, or predictable counters for secrets. They are suitable for simulation, sampling, or load distribution—not authentication tokens, keys, salts, password reset links, or nonce generation.

6. Tokens, salts, nonces, and identifiers

URL-safe opaque token

public final class OpaqueTokens {
    private static final SecureRandom RANDOM =
        new SecureRandom();

    private static final Base64.Encoder ENCODER =
        Base64.getUrlEncoder()
            .withoutPadding();

    public static String generate(
            int randomBytes) {

        byte[] value =
            new byte[randomBytes];

        RANDOM.nextBytes(value);

        return ENCODER.encodeToString(value);
    }
}

// 32 random bytes; encoding is not entropy.
String resetToken =
    OpaqueTokens.generate(32);

Hashing a high-entropy opaque token permits lookup and verification without retaining the bearer credential in plaintext. A stolen database verifier should not itself authorize the request.

Nonce discipline

A nonce is not necessarily secret, but its uniqueness requirements are algorithm-specific. AES-GCM requires nonce uniqueness under one key; accidental reuse can destroy confidentiality and authentication. NIST specifies GCM and its IV construction requirements in SP 800-38D.[13]

  • Generate a fresh nonce for every encryption under a key.
  • Store/transmit the nonce with ciphertext; do not derive it from a timestamp alone.
  • Rotate the key before nonce-generation limits are approached.
  • Never accept caller-selected nonces without a protocol that guarantees uniqueness.

7. MessageDigest

Hashing A message digest maps arbitrary input to a fixed-length output. SHA-256 produces a 256-bit digest and SHA-512 a 512-bit digest. NIST's Secure Hash Standard specifies SHA-2 family algorithms used to detect message modification.[1][14]

Hash bytes

public static byte[] sha256(
        byte[] input)
        throws NoSuchAlgorithmException {

    MessageDigest digest =
        MessageDigest.getInstance(
            "SHA-256");

    return digest.digest(input);
}

Hash a file without loading it all

public static byte[] sha256(
        Path path)
        throws IOException,
               NoSuchAlgorithmException {

    MessageDigest digest =
        MessageDigest.getInstance(
            "SHA-256");

    try (InputStream input =
            new BufferedInputStream(
                Files.newInputStream(path))) {

        byte[] buffer =
            new byte[64 * 1024];

        for (int count;
                (count = input.read(buffer)) != -1;) {

            digest.update(
                buffer,
                0,
                count);
        }
    }

    return digest.digest();
}

Constant-time digest comparison

boolean accepted =
    MessageDigest.isEqual(
        expectedDigest,
        actualDigest);

MessageDigest.isEqual is intended for digest comparison without early return based on the first differing byte. Comparison still belongs inside a protocol that validates lengths, encoding, key use, freshness, and context.

What a digest does not provide

  • No secret-key authentication: anyone can recompute the digest.
  • No encryption: the input is not concealed.
  • No password-hardening: fast hashes aid offline guessing.
  • No canonicalization: equivalent structured values can produce different bytes.

8. Message authentication codes

A MAC is a keyed integrity/authenticity primitive. HMAC combines a cryptographic hash with a secret key and is appropriate when all verifiers may possess the same secret. Unlike a signature, HMAC does not provide public verification.[1]

public static byte[] hmacSha256(
        SecretKey key,
        byte[] message)
        throws GeneralSecurityException {

    Mac mac =
        Mac.getInstance(
            "HmacSHA256");

    mac.init(key);

    return mac.doFinal(message);
}

9. Password verification

Passwords must be stored in a form resistant to offline attacks: a unique salt, a password-hashing/key-derivation scheme, and a cost factor high enough for the verifier's environment. Store the algorithm, cost, salt, and result so policy can evolve. NIST SP 800-63B-4 requires salted password hashing and recommends increasing the cost over time; SP 800-132 specifies PBKDF-based derivation for storage applications.[15][16]

MessageDigest alone is not password storage. SHA-256 and SHA-512 are intentionally fast, which also makes large-scale password guessing fast.

Versioned PBKDF2 verifier

public record PasswordVerifier(
        String algorithm,
        int iterations,
        byte[] salt,
        byte[] hash) {

    public PasswordVerifier {
        salt = salt.clone();
        hash = hash.clone();
    }

    @Override
    public byte[] salt() {
        return salt.clone();
    }

    @Override
    public byte[] hash() {
        return hash.clone();
    }
}
public final class PasswordHashing {
    private static final String ALGORITHM =
        "PBKDF2WithHmacSHA256";

    private static final int SALT_BYTES = 16;
    private static final int OUTPUT_BITS = 256;

    private final SecureRandom random;
    private final int iterations;

    public PasswordHashing(
            SecureRandom random,
            int iterations) {

        if (iterations < 1) {
            throw new IllegalArgumentException(
                "iterations must be positive");
        }

        this.random =
            Objects.requireNonNull(random);
        this.iterations = iterations;
    }

    public PasswordVerifier create(
            char[] password)
            throws GeneralSecurityException {

        byte[] salt =
            new byte[SALT_BYTES];

        random.nextBytes(salt);

        byte[] hash =
            derive(
                password,
                salt,
                iterations);

        return new PasswordVerifier(
            ALGORITHM,
            iterations,
            salt,
            hash);
    }

    public boolean verify(
            char[] password,
            PasswordVerifier verifier)
            throws GeneralSecurityException {

        if (!ALGORITHM.equals(
                verifier.algorithm())) {
            return false;
        }

        byte[] candidate =
            derive(
                password,
                verifier.salt(),
                verifier.iterations());

        try {
            return MessageDigest.isEqual(
                verifier.hash(),
                candidate);
        } finally {
            Arrays.fill(
                candidate,
                (byte) 0);
        }
    }

    private static byte[] derive(
            char[] password,
            byte[] salt,
            int iterations)
            throws GeneralSecurityException {

        PBEKeySpec specification =
            new PBEKeySpec(
                password,
                salt,
                iterations,
                OUTPUT_BITS);

        try {
            SecretKeyFactory factory =
                SecretKeyFactory.getInstance(
                    ALGORITHM);

            return factory
                .generateSecret(specification)
                .getEncoded();
        } finally {
            specification.clearPassword();
        }
    }
}

The iteration value above is configuration, not a timeless constant. Benchmark the verifier on deployment hardware, set the highest practical cost consistent with authentication capacity, rate-limit failed attempts, and rehash after successful authentication when stored parameters are obsolete.[15]

10. Authenticated encryption with AES-GCM

AES is a NIST-standard block cipher with 128-, 192-, and 256-bit keys. GCM is an authenticated-encryption mode that protects both confidentiality and integrity and can authenticate additional unencrypted data.[17][13]

public record EncryptedValue(
        int version,
        String keyId,
        byte[] nonce,
        byte[] ciphertext) {

    public EncryptedValue {
        nonce = nonce.clone();
        ciphertext = ciphertext.clone();
    }

    @Override
    public byte[] nonce() {
        return nonce.clone();
    }

    @Override
    public byte[] ciphertext() {
        return ciphertext.clone();
    }
}
public final class AesGcm {
    private static final int NONCE_BYTES = 12;
    private static final int TAG_BITS = 128;

    private final SecureRandom random;

    public AesGcm(SecureRandom random) {
        this.random =
            Objects.requireNonNull(random);
    }

    public EncryptedValue encrypt(
            String keyId,
            SecretKey key,
            byte[] plaintext,
            byte[] associatedData)
            throws GeneralSecurityException {

        byte[] nonce =
            new byte[NONCE_BYTES];

        random.nextBytes(nonce);

        Cipher cipher =
            Cipher.getInstance(
                "AES/GCM/NoPadding");

        cipher.init(
            Cipher.ENCRYPT_MODE,
            key,
            new GCMParameterSpec(
                TAG_BITS,
                nonce));

        cipher.updateAAD(
            associatedData);

        byte[] ciphertext =
            cipher.doFinal(
                plaintext);

        return new EncryptedValue(
            1,
            keyId,
            nonce,
            ciphertext);
    }

    public byte[] decrypt(
            EncryptedValue value,
            SecretKey key,
            byte[] associatedData)
            throws GeneralSecurityException {

        Cipher cipher =
            Cipher.getInstance(
                "AES/GCM/NoPadding");

        cipher.init(
            Cipher.DECRYPT_MODE,
            key,
            new GCMParameterSpec(
                TAG_BITS,
                value.nonce()));

        cipher.updateAAD(
            associatedData);

        return cipher.doFinal(
            value.ciphertext());
    }
}

Associated data

byte[] aad =
    canonicalEncode(
        Map.of(
            "purpose", "customer-tax-id",
            "tenantId", tenantId,
            "recordId", customerId,
            "schemaVersion", "3"));

Associated data remains readable but is authenticated. Binding purpose, tenant, record identity, and schema version prevents ciphertext from being moved to another record or semantic field without detection.

Operational rules

  • Never reuse a GCM nonce with the same key.
  • Store key ID, algorithm/version, nonce, ciphertext/tag, and required context.
  • Reject authentication-tag failures without returning partial plaintext.
  • Do not compress attacker-controlled and secret data together before encryption in an interactive protocol.
  • Use a key-management service or protected keystore; do not hard-code keys.

12. KeyStore concepts

Key storage KeyStore is an engine for storing cryptographic keys and certificates. Standard entry types are private-key entries with certificate chains, secret-key entries, and trusted-certificate entries.[18]

EntryContentsTypical use
PrivateKeyEntryPrivate key plus corresponding certificate chainTLS server/client identity, document or artifact signing
SecretKeyEntrySymmetric keyAES encryption, HMAC, local key wrapping
TrustedCertificateEntryTrusted public certificateTrust anchor or explicitly trusted peer

Every Java implementation must support the PKCS12 keystore type, and the default type is pkcs12 unless overridden by the keystore.type security property.[18] JDK 9 changed the default from JKS to PKCS #12 for stronger standard interoperability and storage of private, trusted-certificate, and secret-key entries.[4]

Keystore versus truststore

“Keystore” describes the format/API. “Truststore” describes how its certificate entries are used. The same KeyStore class can hold local identity keys or trust anchors, but separating files, permissions, ownership, and rotation is usually clearer.

File storage limitations

A password-protected PKCS #12 file improves protection at rest, but an application that can unlock a private key can use it. File permissions, process isolation, secret delivery, audit, key rotation, and hardware-backed non-exportable keys remain part of the design.[19]

14. keytool

keytool creates and manages keystores, key pairs, secret keys, certificate requests, certificates, certificate chains, and trusted certificates. Its output and defaults are provider- and release-sensitive, so production commands should specify store type, algorithms, sizes, validity, extensions, aliases, and files explicitly.[20]

Generate an RSA TLS identity

keytool -genkeypair \
  -alias orders-tls-2026-01 \
  -keystore orders-identity.p12 \
  -storetype PKCS12 \
  -keyalg RSA \
  -keysize 3072 \
  -sigalg SHA384withRSA \
  -validity 365 \
  -dname "CN=orders.internal.example,O=Example,C=US" \
  -ext "SAN=dns:orders.internal.example,dns:orders" \
  -ext "KU=digitalSignature,keyEncipherment" \
  -ext "EKU=serverAuth"

Create a certificate signing request

keytool -certreq \
  -alias orders-tls-2026-01 \
  -keystore orders-identity.p12 \

15. Key lifecycle and protected key services

Key security includes generation, registration, distribution, storage, activation, use, rotation, revocation, archival, recovery, destruction, and audit. NIST SP 800-57 describes lifecycle and management considerations for cryptographic keying material.[19]

Use keys for one purpose

  • Separate encryption, MAC, signing, TLS identity, and wrapping keys.
  • Separate tenants, environments, and security domains where compromise boundaries differ.
  • Give every active key a stable key ID and lifecycle state.
  • Retain old decryption or verification keys for the required data-retention window, but stop new use after rotation.
  • Destroy retired key material according to storage technology and policy.

Hardware-backed keys

The JCA provider model permits private keys to remain inside PKCS #11 tokens, hardware security modules, smart cards, or cloud key-management services. Such keys may be represented by Java PrivateKey objects whose encoded material is unavailable; applications request cryptographic operations rather than exporting the secret.[21]

16. Digital signatures

Signatures A digital signature uses a private key to sign and a public key to verify. It can detect unauthorized modification and authenticate the signer under the key-to-identity binding. NIST FIPS 186-5 specifies approved digital-signature algorithms and their intended integrity and signer-authentication properties.[22]

Ed25519 signing and verification

public static byte[] sign(
        PrivateKey privateKey,
        byte[] message)
        throws GeneralSecurityException {

    Signature signature =
        Signature.getInstance(
            "Ed25519");

    signature.initSign(
        privateKey);

    signature.update(
        message);

    return signature.sign();
}

public static boolean verify(
        PublicKey publicKey,
        byte[] message,
        byte[] signatureBytes)
        throws GeneralSecurityException {

    Signature signature =
        Signature.getInstance(
            "Ed25519");

    signature.initVerify(
        publicKey);

    signature.update(
        message);

    return signature.verify(
        signatureBytes);
}

EdDSA support entered the JDK in Java 15 and implements Ed25519/Ed448 according to RFC 8032.[6]

RSA-PSS with explicit parameters

PSSParameterSpec parameters =
    new PSSParameterSpec(
        "SHA-256",
        "MGF1",
        MGF1ParameterSpec.SHA256,
        32,
        1);

Signature signature =
    Signature.getInstance(
        "RSASSA-PSS");

signature.setParameter(
    parameters);

signature.initSign(
    privateKey,
    secureRandom);

signature.update(message);

byte[] value =

Signature algorithm parameters must be identical during verification. Do not rely on ambiguous “RSA signature” terminology: key type, padding/signature scheme, digest, MGF digest, salt length, and canonical message format all matter.

Signature is not encryption

Anyone with the public key can verify a signature, but the signed message remains visible. Encrypt separately when confidentiality is required, and specify whether the protocol signs plaintext, ciphertext, or a canonical envelope.

17. Canonical signed envelopes and replay resistance

Signing arbitrary object serialization, mutable JSON text, locale-sensitive formatting, or a Java Serializable byte stream creates brittle or ambiguous verification. Define one canonical byte representation and include protocol context.

        String commandId,

public static byte[] canonicalBytes(
        SignedCommand command)
        throws IOException {

    ByteArrayOutputStream bytes =
        new ByteArrayOutputStream();

    try (DataOutputStream output =
            new DataOutputStream(bytes)) {

        output.writeInt(
            command.version());

        writeUtf8(
            output,
            command.keyId());

        writeUtf8(
            output,
            command.commandId());

        output.writeLong(
            command.issuedAt()
                .toEpochMilli());

        output.writeLong(
            command.expiresAt()
                .toEpochMilli());

        writeUtf8(
            output,
            command.action());

        writeUtf8(
            output,
            command.resourceId());

        output.writeInt(
            command.payload().length);

        output.write(
            command.payload());
    }

    return bytes.toByteArray();
}

private static void writeUtf8(
        DataOutputStream output,
        String value)
        throws IOException {

    byte[] encoded =
        value.getBytes(
            StandardCharsets.UTF_8);

    output.writeInt(
        encoded.length);

    output.write(
        encoded);
}

Verification order

  1. Parse using bounded lengths and a supported version.
  2. Resolve the key ID from a trusted key registry.
  3. Verify the signature over canonical bytes.
  4. Validate issue/expiry time with bounded clock skew.
  5. Atomically reject previously used command IDs/nonces.
  6. Authorize the authenticated signer for the requested action and resource.
  7. Execute idempotently and record outcome.
A valid signature proves possession of a signing key for those bytes. It does not prove freshness, human intent, current authorization, certificate validity, or that the key was uncompromised.

A certification path links an end-entity certificate through zero or more intermediate CA certificates to a configured trust anchor. Validation checks signatures, validity, constraints, policies, algorithm restrictions, and—when configured—revocation status.[25]

22. JAAS architecture

JAAS JAAS authentication is a Java implementation of a pluggable authentication framework. An application creates a LoginContext; the context reads a Configuration, invokes configured LoginModules, and produces a Subject populated with principals and credentials after successful authentication.[3][31]

24. Implementing a LoginModule

A login module has two phases. login() gathers and verifies evidence, storing temporary state privately. If the overall stack succeeds, commit() adds principals and credentials to the subject; otherwise abort() removes temporary state. logout() removes committed state.[32]

public final class UserPrincipal
        implements Principal,
                   Serializable {

    private final String name;

    public UserPrincipal(String name) {
        this.name =
            Objects.requireNonNull(name);
    }

    @Override
    public String getName() {
        return name;
    }

    @Override
    public boolean equals(Object other) {
        return other instanceof UserPrincipal value
            && name.equals(value.name);
    }

    @Override
    public int hashCode() {
        return name.hashCode();
    }
}
public final class PasswordLoginModule
        implements LoginModule {

    private Subject subject;
    private CallbackHandler callbacks;
    private PasswordVerifierService verifier;

    private UserPrincipal authenticated;
    private boolean succeeded;
    private boolean committed;

    @Override
    public void initialize(
            Subject subject,
            CallbackHandler callbacks,
            Map<String, ?> sharedState,
            Map<String, ?> options) {

        this.subject =
            Objects.requireNonNull(subject);

        this.callbacks =
            Objects.requireNonNull(callbacks);

        this.verifier =
            Services.passwordVerifier(
                Objects.toString(
                    options.get(
                        "passwordVerifier")));
    }

    @Override
    public boolean login()
            throws LoginException {

        NameCallback name =
            new NameCallback(
                "Username");

        PasswordCallback password =
            new PasswordCallback(
                "Password",
                false);

        try {
            callbacks.handle(
                new Callback[] {
                    name,
                    password
                });

            char[] candidate =
                password.getPassword();

            try {
                boolean valid =
                    verifier.verify(
                        name.getName(),
                        candidate);

                if (!valid) {
                    throw new FailedLoginException(
                        "Invalid credentials");
                }

                authenticated =
                    new UserPrincipal(
                        name.getName());

                succeeded = true;
                return true;
            } finally {
                password.clearPassword();

                if (candidate != null) {
                    Arrays.fill(
                        candidate,
                        '\0');
                }
            }
        } catch (IOException
                 | UnsupportedCallbackException failure) {

            throw new LoginException(
                "Credential callback failed")
                .initCause(failure);
        }
    }

    @Override
    public boolean commit()
            throws LoginException {

        if (!succeeded) {
            return false;
        }

        subject.getPrincipals()
            .add(authenticated);

        committed = true;
        return true;
    }

    @Override
    public boolean abort()
            throws LoginException {

        clear();

        return succeeded
            || committed;
    }

    @Override
    public boolean logout()
            throws LoginException {

        if (authenticated != null) {
            subject.getPrincipals()
                .remove(authenticated);
        }

        clear();
        return true;
    }

    private void clear() {
        authenticated = null;
        succeeded = false;
        committed = false;
    }
}

Module rules

  • Do not retry or sleep inside login(); the application owns rate limiting and retry policy.[32]
  • Do not add principals in login(); wait for commit().
  • Clear passwords and temporary credentials on every path.
  • Return generic authentication failures to callers while recording safe diagnostic reasons internally.
  • Do not trust module options from an attacker-writable configuration file.

26. Authentication design beyond JAAS

Authentication Authentication establishes that a claimant controls one or more authenticators bound to an identity. NIST SP 800-63B-4 defines authentication assurance levels and requirements for passwords, one-time codes, cryptographic authenticators, phishing resistance, recovery, and session management.[15]

JAAS is a framework, not an Internet protocol

JAAS can coordinate Kerberos, operating-system, smart-card, password, or custom modules inside a Java application. Web and distributed systems usually authenticate through standardized external protocols and identity providers, then construct trusted application principals from validated assertions.

Authentication controls

  • Use authenticated protected channels for credential submission.
  • Prefer phishing-resistant cryptographic authenticators where risk justifies them.
  • Rate-limit failed authentication and recovery attempts.
  • Bind authenticators and recovery methods through verified account workflows.
  • Do not use security questions as an authentication factor.
  • Invalidate sessions and credentials after compromise indicators.
  • Record authentication events without secrets.

Password policy

NIST SP 800-63B-4 requires at least 15 characters for a password used as a single factor, permits a lower minimum of eight when it is only part of multifactor authentication, discourages composition rules and periodic changes, and requires comparison against common/expected/compromised password blocklists.[15]

27. Authorization after the Security Manager

Authorization The old JAAS authorization mechanism depended on policy files, permissions, AccessControlContext, and the Security Manager. Because the Security Manager is permanently disabled, this mechanism is no longer supported. Applications must perform authorization explicitly.[3][7]

Authorization inputs

  • Subject: authenticated user/service principals and trusted attributes.
  • Action: the exact operation requested.
  • Resource: object identity, tenant, owner, classification, and state.
  • Environment: time, network zone, authentication strength, risk, and transaction context.
  • Policy: explicit rules with deny-by-default semantics.

NIST defines attribute-based access control as evaluating subject, object, operation, and possibly environmental attributes against policy rules and relationships.[35]

Enforce at the service boundary

Authorization rules

  • Deny by default and fail closed when policy data is unavailable.
  • Authorize every request, including object identity—not only route names.
  • Do not rely on hidden UI controls or possession of an identifier.
  • Separate authentication strength from authorization role.
  • Keep policy decisions pure where possible and audit the decision inputs safely.
  • Perform checks in the transaction when resource state affects authorization.

public final class OrderAuthorization {
    public Decision decide(
            AuthorizationRequest request) {

        Set<String> roles =
            request.subject()
                .getPrincipals(
                    RolePrincipal.class)
                .stream()
                .map(
                    RolePrincipal::getName)
                .collect(
                    Collectors.toUnmodifiableSet());

        OrderAttributes order =
            request.resource();

        return switch (request.action()) {
            case READ_ORDER ->
                canRead(
                    request.subject(),
                    roles,
                    order);

            case CANCEL_ORDER ->
                canCancel(
                    request.subject(),
                    roles,
                    order,
                    request.environment());

            case REFUND_ORDER ->
                canRefund(
                    roles,
                    order,
                    request.environment());
        };
    }

    private Decision canRead(
            Subject subject,
            Set<String> roles,
            OrderAttributes order) {

        String userId =
            Subjects.requireUser(subject)
                .getName();

        boolean allowed =
            roles.contains(
                "ORDER_SUPPORT")
            || order.customerId()
                .equals(userId);

        return Decision.of(
            allowed,
            allowed
                ? "READ_ALLOWED"
                : "NOT_OWNER_OR_SUPPORT");
    }

    private Decision canCancel(
            Subject subject,
            Set<String> roles,
            OrderAttributes order,
            Environment environment) {

        boolean owner =
            order.customerId().equals(
                Subjects.requireUser(subject)
                    .getName());

        boolean cancellable =
            order.status()
                == OrderStatus.PENDING;

        boolean strongAuthentication =
            environment.authenticationLevel()
                .atLeast(
                    AuthenticationLevel.MULTI_FACTOR);

        boolean allowed =
            cancellable
            && strongAuthentication
            && (owner
                || roles.contains(
                    "ORDER_SUPPORT"));

        return Decision.of(
            allowed,
            allowed
                ? "CANCEL_ALLOWED"
                : "CANCEL_POLICY_FAILED");
    }
}

  • Keep privileged bypasses narrow, explicit, and audited.

            "key-1",
            key,
            plaintext,
            aad);

    byte[] altered =
        encrypted.ciphertext();

    altered[altered.length / 2] ^= 1;

    EncryptedValue corrupted =
        new EncryptedValue(
            encrypted.version(),
            encrypted.keyId(),
            encrypted.nonce(),
            altered);

    assertThrows(
        AEADBadTagException.class,
        () ->
            encryption.decrypt(
                corrupted,
                key,
                aad));
}

Signature tests

  • Valid signature and exact bytes succeed.
  • Changed payload, action, resource, key ID, time, or version fails.
  • Wrong public key fails.
  • Expired and replayed envelopes fail even when the signature is valid.
  • Malformed length fields are rejected before allocation.

Certificate tests

  • Valid chain to intended trust anchor succeeds.
  • Expired/not-yet-valid leaf fails at a fixed test clock.
  • Wrong EKU, basic constraints, name, or key usage fails where required.
  • Untrusted root and missing intermediate fail.
  • Revocation behavior is tested for responder success, revoked status, unknown status, and outage.

  • Test cross-tenant identifiers and ownership changes.

Testability through interfaces

Inject a Clock, key resolver, nonce repository, and policy service. Keep the real cryptographic primitive; replace environment and persistence boundaries, not AES, SHA, or signature verification with fake algorithms.

JDK providers

The JDK reference implementation ships multiple providers for core hashes, signatures, ciphers, TLS, SASL, GSS/Kerberos, XML signatures, and platform/hardware integration. The exact algorithms and restrictions are documented by the JDK Providers guide and security-properties file.[37]

FIPS and validated modules

Using an algorithm named in a FIPS publication is not the same as operating inside a validated cryptographic module. Compliance can depend on provider/module validation, approved mode, operating environment, configuration, key generation, entropy, boundaries, and operational procedures.

  • Select a provider/module approved by the organization's compliance authority.
  • Pin and verify provider version and configuration.
  • Prevent fallback to unapproved providers.
  • Test every required algorithm, keystore, TLS path, and hardware error condition.
  • Record module/provider identity in deployment evidence, not secret material.

PKCS #11 deployment

The SunPKCS11 provider connects JCA/JCE engine calls to a native PKCS #11 library. Token slots, mechanisms, session limits, login behavior, key attributes, and failover are device-specific and require vendor integration testing.[38]

33. Cryptographic agility and rotation

Cryptographic agility is the ability to change algorithms, parameters, providers, and keys without losing protected data or creating an uncontrolled downgrade path. It is primarily a data-format and operational design problem.

Versioned envelope

record ProtectedPayload(
    int formatVersion,
    String algorithm,
    String keyId,
    byte[] parameters,
    byte[] associatedDataDigest,
    byte[] ciphertext) {
}

Registry, not arbitrary algorithm input

public final class CryptoRegistry {
    private final Map<
        Integer,
        PayloadCryptography> versions =
            Map.of(
                1,
                new AesGcmV1(),
                2,
                new AesGcmV2());

    public PayloadCryptography require(
            int version) {

        return Optional.ofNullable(
                versions.get(version))
            .orElseThrow(
                UnsupportedCryptoVersion::new);
    }
}

Do not call Cipher.getInstance() or Signature.getInstance() with an algorithm name supplied by an untrusted message. Map a supported version to a locally controlled implementation and parameter policy.

Rotation workflow

  1. Create and register the new key under a unique key ID.
  2. Enable verification/decryption using both old and new keys.
  3. Switch new signing/encryption to the new key.
  4. Re-encrypt, rewrap, or allow old data to age out according to policy.
  5. Revoke old signing/authentication keys and distribute revocation state.
  6. Remove old private/secret material only after the last required use.
  7. Retain safe audit evidence of lifecycle actions.

Algorithm retirement

JDK algorithm restrictions evolve as cryptographic guidance changes. Test upgrades against existing certificate chains, signed JARs, TLS peers, and stored data rather than disabling new restrictions globally to restore compatibility.[10]

34. Integrated example: authenticated administrative command

This design combines JAAS authentication, explicit authorization, an Ed25519 signature, freshness/replay checks, and an audit event. The signature protects a command crossing an untrusted transport; it does not replace the operator's authenticated session or policy check.

Command service

public final class AdministrativeCommandService {
    private final PublicKeyRegistry keys;
    private final ReplayRepository replays;
    private final AuthorizationService authorization;
    private final AuditLog audit;
    private final Clock clock;

    public CommandResult execute(
            Subject operator,
            SignedCommand command)
            throws GeneralSecurityException,
                   IOException {

        Instant now =
            clock.instant();

        validateEnvelope(
            command,
            now);

        PublicKey key =
            keys.requireActive(
                command.keyId(),
                now);

        byte[] bytes =
            canonicalBytes(
                command);

        if (!verify(
                key,
                bytes,
                command.signature())) {

            audit.failure(
                "ADMIN_SIGNATURE_INVALID",
                command.commandId(),
                command.keyId());

            throw new InvalidCommandException();
        }

        if (!replays.acceptOnce(
                command.keyId(),
                command.commandId(),
                command.expiresAt())) {

            audit.failure(
                "ADMIN_COMMAND_REPLAY",
                command.commandId(),
                command.keyId());

            throw new InvalidCommandException();
        }

        AuthorizationRequest request =
            AuthorizationRequest.forCommand(
                operator,
                command.action(),
                command.resourceId(),
                now);

        Decision decision =
            authorization.decide(
                request);

        if (!decision.allowed()) {
            audit.denied(
                operator,
                command,
                decision.reasonCode());

            throw new AccessDeniedException();
        }

        CommandResult result =
            dispatch(command);

        audit.success(
            operator,
            command,
            result.code());

        return result;
    }

    private static void validateEnvelope(
            SignedCommand command,
            Instant now) {

        if (command.version() != 1) {
            throw new InvalidCommandException();
        }

        if (command.issuedAt()
                .isAfter(
                    now.plusSeconds(30))) {
            throw new InvalidCommandException();
        }

        if (!now.isBefore(
                command.expiresAt())) {
            throw new InvalidCommandException();
        }

        if (command.expiresAt()
                .isAfter(
                    command.issuedAt()
                        .plusSeconds(300))) {
            throw new InvalidCommandException();
        }
    }
}

Security properties

  • Authentication identifies the operator separately from the command signer.
  • The key registry controls active key IDs and validity.
  • The signature binds action, resource, payload, and time.
  • The replay repository makes command IDs single-use across replicas.
  • Authorization evaluates the current operator and resource state.
  • The audit record stores identifiers and outcomes, not private keys or bearer credentials.

35. Production security checklist

Threat model and design

  • Assets, attackers, trust boundaries, and failure policy are documented.
  • Standard protocols and authenticated constructions replace custom cryptography.
  • Authentication, authorization, confidentiality, integrity, and replay protection are treated separately.

Cryptography

  • Algorithms use standard names and explicit parameters.
  • Authenticated encryption protects application ciphertext.
  • GCM nonces are unique per key and generated by controlled code.
  • MAC/signature input includes protocol context and canonical encoding.
  • Fast message digests are not used for password storage.
  • Constant-time comparison is used for secret-derived fixed-length values where appropriate.
  • Security-property algorithm restrictions are not bypassed casually.

Randomness and keys

  • SecureRandom generates keys, tokens, nonces, salts, and challenges.
  • Keys are generated with explicit algorithms and parameters.
  • Key purposes, tenants, and environments are separated.
  • Every protected record contains a controlled key ID and format version.
  • Private/secret keys are stored in protected keystores, HSMs, or KMSs.
  • Rotation, revocation, recovery, and destruction are tested.

Certificates and TLS

  • Certificate parsing is not confused with PKIX validation.
  • Trust anchors are minimal and domain-specific.
  • Names, key usage, EKU, constraints, validity, and algorithm restrictions are enforced.
  • Revocation behavior is explicit.
  • No trust-all manager or disabled hostname verifier exists.
  • TLS and code-signing keys are separate.

JAAS and authentication

  • LoginModule temporary state is committed or aborted correctly.
  • Passwords are cleared and failures are generic.
  • Subject.callAs/current replace deprecated AccessControlContext patterns.
  • Asynchronous identity propagation is explicit.
  • Rate limiting, recovery, MFA, session rotation, and revocation are designed outside the login module.

Authorization

  • Application policy replaces removed Security Manager authorization.
  • Every operation is denied by default and checks the actual resource.
  • Tenant, ownership, state, authentication strength, and environment attributes are validated.
  • Privileged bypasses are narrow and audited.
  • Cross-tenant and object-level denial tests exist.

Operations

  • Secrets never appear in logs, command lines, source, heap dumps, or build artifacts.
  • Provider and keystore configurations are versioned and access-controlled.
  • Dependency/JDK security updates are tested promptly.
  • Security events identify key IDs, principals, actions, and outcomes without sensitive material.
  • Known-answer, tamper, replay, expiry, trust, and negative authorization tests run in CI.
Final principle: Java supplies mature cryptographic and identity primitives, but the application owns protocol semantics, key custody, trust policy, authentication assurance, authorization decisions, and operational recovery. Secure code makes each of those boundaries explicit and testable.
