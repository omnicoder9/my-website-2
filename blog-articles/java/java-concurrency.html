1. Concurrency is coordination under partial ordering

Concurrency allows several tasks to make progress during overlapping periods. Parallelism is the simultaneous execution of work on multiple processors. Java provides both, but correctness depends on task lifetime, shared-state ownership, ordering, visibility, atomicity, cancellation, bounded resource use, and failure propagation.

Thread

An execution context with a call stack, interruption state, and scheduling identity.

Task

A unit of work represented by a Runnable, Callable, completion stage, or fork/join task.

Synchronization

Mechanisms that establish ordering, visibility, mutual exclusion, or coordinated waiting.

Resource policy

Limits on threads, queues, downstream calls, memory, deadlines, retries, and task lifetime.

The Java concurrency APIs are centered in java.lang, java.util.concurrent, java.util.concurrent.locks, and java.util.concurrent.atomic. They provide threads, task execution, futures, queues, synchronizers, concurrent collections, locks, atomics, fork/join, virtual threads, and preview structured-concurrency facilities.[1]

Prefer ownership over synchronization. Immutable values, thread confinement, message passing, bounded queues, and transaction boundaries reduce the amount of shared mutable state that must be made correct.

2. Platform and virtual threads

Threads Every Java thread is represented by an instance of java.lang.Thread. Java 25 has two thread kinds: platform threads, which are closely associated with operating-system threads, and virtual threads, which are scheduled by the Java runtime over a smaller set of carrier platform threads.[2]

Virtual threads provide scale rather than faster execution. They are most effective when tasks spend substantial time blocked in supported I/O or synchronization operations and are not intended to accelerate long-running CPU-bound computation.[3]

3. The Thread class

The Thread API creates, starts, names, interrupts, joins, and inspects threads. A Thread object can be started at most once. Calling run() directly executes the task in the current thread; calling start() schedules a new thread that invokes run().[2]

Platform thread

Thread worker =
    Thread.ofPlatform()
        .name("inventory-reconciler")
        .uncaughtExceptionHandler(
            (thread, failure) ->
                LOGGER.log(
                    System.Logger.Level.ERROR,
                    "Worker failed: "
                        + thread.getName(),
                    failure))
        .unstarted(
            () ->
                reconcileInventory());

worker.start();
worker.join();

Virtual thread

Thread request =
    Thread.ofVirtual()
        .name("request-", 0)
        .start(
            () ->
                handleRequest(command));

Thread.Builder creates unstarted or started platform/virtual threads and thread factories. Builders themselves are not thread-safe; factories created from them are thread-safe.[4]

Prefer task submission in applications

Direct thread creation is appropriate for dedicated lifecycle-managed runtime threads or simple programs. Application business work is usually easier to manage through an executor or structured scope that owns shutdown, failures, cancellation, and resource policy.

4. Runnable and Callable

Runnable represents an operation that returns no result. Callable<V> returns a value and may throw a checked exception. Both are functional interfaces and can be represented by lambdas or method references.[5][6]

Runnable auditTask =
    () ->
        audit.flush();

Callable<OrderSummary> loadTask =
    () ->
        orders.loadSummary(
            orderId);

Separate task from execution policy

public final class RebuildIndex
        implements Callable<IndexStatistics> {

    private final DocumentRepository documents;
    private final SearchIndex index;

    public RebuildIndex(
            DocumentRepository documents,
            SearchIndex index) {

        this.documents =
            Objects.requireNonNull(documents);

        this.index =
            Objects.requireNonNull(index);
    }

    @Override
    public IndexStatistics call()
            throws IOException {

        return index.rebuild(
            documents.streamAll());
    }
}

The task does not choose its own thread, queue, retry policy, timeout, or scheduling priority. Those belong to its caller or executor configuration.

5. Thread lifecycle and states

Thread.State exposes six diagnostic states: NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, and TERMINATED. They are JVM-level states and do not map one-to-one to operating-system scheduler states.[2]

Start and join form memory-ordering edges

final class ResultBox {
    int value;
}

ResultBox result =
    new ResultBox();

Thread worker =
    Thread.startVirtualThread(
        () ->
            result.value = 42);

worker.join();

// The worker's actions happen-before
// successful return from join().

A call to Thread.start() happens-before actions in the started thread. All actions in a thread happen-before another thread successfully returns from join() on that thread.[7]

6. Interruption and cooperative cancellation

Interruption is a cooperative cancellation signal represented by a thread's interrupted status. Many blocking methods respond by throwing InterruptedException and clearing that status. Application code must decide whether to propagate, restore, or translate interruption.[2]

Interruptible worker loop

public void runWorker() {
    try {
        while (!Thread.currentThread()
                .isInterrupted()) {

            WorkItem item =
                queue.take();

            process(item);
        }
    } catch (InterruptedException cancelled) {
        Thread.currentThread()
            .interrupt();
    } finally {
        releaseResources();
    }
}

Propagate when possible

public Order loadOrder(
        OrderId id)
        throws InterruptedException {

    return queue.take()
        .load(id);
}

Restore when translating

try {
    future.get();
} catch (InterruptedException cancelled) {
    Thread.currentThread()
        .interrupt();

    throw new OperationCancelledException(
        cancelled);
}
Do not swallow interruption. Catching InterruptedException and continuing normally can prevent executor shutdown, scope cancellation, request deadlines, and application termination.

7. Daemon threads and uncaught exceptions

The JVM begins shutdown when all started non-daemon threads have terminated. Daemon status therefore expresses whether a thread keeps the process alive; it is not a resource-cleanup mechanism.[2]

ThreadFactory factory =
    Thread.ofPlatform()
        .name("metrics-", 0)
        .daemon(true)
        .uncaughtExceptionHandler(
            (thread, failure) ->
                fatalErrors.record(
                    thread.getName(),
                    failure))
        .factory();

Executor exception visibility

  • An exception escaping a thread's top-level run reaches its uncaught-exception handler.
  • An exception from a task submitted with submit is normally captured in its Future.
  • An exception from periodic scheduled execution suppresses later executions.
  • Ignoring returned futures can silently discard failures.

Shutdown hooks are not guaranteed cleanup

Use explicit lifecycle methods, try-with-resources, and orderly executor shutdown. Abrupt process termination, host failure, or forced container kill may prevent hooks from completing.

8. The Java Memory Model

JMM The Java Memory Model specifies which values reads of shared variables may observe and which reorderings are legal. It defines actions, program order, synchronization order, synchronizes-with relations, happens-before, data races, and special semantics for final fields.[8]

Data-race example

final class BrokenCounter {
    int value;

    void increment() {
        value++;
    }
}

value++ is a read-modify-write sequence, not one atomic action. Concurrent calls can read the same old value and overwrite one another. Without a happens-before relationship, reads may also observe stale values or effects in surprising orders.

Correct synchronization gives sequentially consistent reasoning

The JLS provides a strong guarantee for correctly synchronized programs: if all conflicting shared-memory accesses are ordered by synchronization, programmers can reason as though thread actions were interleaved in a sequentially consistent order.[8]

Compiler and CPU reordering

Implementations may reorder operations when the resulting execution remains legal under the JMM. Source order in one thread is not by itself a cross-thread visibility guarantee.

9. Happens-before relationships

If action A happens-before action B, A's effects are visible to B and ordered before B for JMM reasoning. Important edges include monitor unlock/lock, volatile write/read, thread start/join, executor submission/task execution, future completion/result retrieval, concurrent collection transfer, and synchronizer release/acquire operations.[7]

10. Safe publication and immutability

Construction alone does not safely publish an object to another thread. Publication needs a happens-before edge such as initialization of a static field, storing into a volatile field, releasing a lock, submitting through an executor, or inserting into a concurrent collection.

Immutable value

public final class RoutingTable {
    private final Map<String, URI> routes;

    public RoutingTable(
            Map<String, URI> routes) {

        this.routes =
            Map.copyOf(routes);
    }

    public URI require(
            String service) {

        return Optional.ofNullable(
                routes.get(service))
            .orElseThrow();
    }
}

Volatile snapshot publication

public final class RoutingRegistry {
    private volatile RoutingTable current =
        new RoutingTable(
            Map.of());

    public RoutingTable current() {
        return current;
    }

    public void replace(
            RoutingTable next) {
        current =
            Objects.requireNonNull(next);
    }
}

Final fields receive special initialization safety when an object does not escape during construction, but final-field semantics do not make referenced mutable objects immutable or make later mutations automatically visible.[8]

11. Intrinsic locks and synchronized

Synchronization Every object has an associated monitor. A synchronized instance method locks this; a synchronized static method locks the declaring Class object; a synchronized statement locks the evaluated object. Monitor locks are reentrant.[8]

public final class BankAccount {
    private long balance;

    public BankAccount(long initial) {
        if (initial < 0) {
            throw new IllegalArgumentException();
        }

        balance = initial;
    }

    public synchronized long balance() {
        return balance;
    }

    public synchronized void withdraw(
            long amount) {

        if (amount < 0
                || amount > balance) {
            throw new IllegalArgumentException();
        }

        balance -= amount;
    }
}

Compound invariants need one lock

private final Object lock =
    new Object();

private int queued;
private int running;

public void moveQueuedToRunning() {
    synchronized (lock) {
        if (queued == 0) {
            throw new IllegalStateException();
        }

        queued--;
        running++;
    }
}

Lock-object rules

  • Use a private final lock object rather than externally accessible strings, class literals, or caller-owned objects.
  • Keep critical sections small but complete for the invariant.
  • Do not invoke slow or unknown external code while holding a lock.
  • Use a globally consistent lock order when several locks are required.

12. Monitor wait sets: wait, notify, and notifyAll

Object.wait() atomically releases the object's monitor and suspends the current thread in that monitor's wait set. Before returning, the thread must re-acquire the monitor. Waits may return because of notification, interruption, timeout, or a spurious wakeup, so condition predicates must be tested in a loop.[9]

public final class OneSlot<T> {
    private T value;
    private boolean full;

    public synchronized void put(
            T next)
            throws InterruptedException {

        while (full) {
            wait();
        }

        value =
            Objects.requireNonNull(next);

        full = true;
        notifyAll();
    }

    public synchronized T take()
            throws InterruptedException {

        while (!full) {
            wait();
        }

        T result = value;
        value = null;
        full = false;

        notifyAll();
        return result;
    }
}

High-level queues and synchronizers are usually preferable. The example demonstrates monitor semantics; production producer-consumer code should normally use BlockingQueue.

13. The explicit lock framework

The Lock interface separates lock acquisition and release from lexical blocks and adds interruptible acquisition, timed attempts, polling attempts, and multiple condition variables. A successful lock/unlock pair has the same memory-synchronization effects as monitor lock/unlock.[10]

Lock lock =
    new ReentrantLock();

lock.lock();

try {
    updateSharedState();
} finally {
    lock.unlock();
}

When explicit locks help

  • The acquisition must be interruptible or time-bounded.
  • Several condition queues are needed for one protected state.
  • Lock acquisition and release cannot be represented by one lexical block.
  • Read and write access have distinct policies.
  • Diagnostics or fairness controls are required.
Every successful acquisition needs a guaranteed release. Put unlock() in the finally block immediately after acquisition succeeds.

14. ReentrantLock

ReentrantLock implements a reentrant mutual-exclusion lock with semantics similar to a synchronized monitor and adds fairness, condition variables, interruptible/timed acquisition, and inspection methods. A fair lock favors the longest-waiting thread under contention, but fairness can reduce throughput and does not guarantee scheduler fairness.[11]

public final class Inventory {
    private final ReentrantLock lock =
        new ReentrantLock();

    private final Map<String, Integer> stock =
        new HashMap<>();

    public boolean reserve(
            String sku,
            int quantity,
            Duration timeout)
            throws InterruptedException {

        if (!lock.tryLock(
                timeout.toNanos(),
                TimeUnit.NANOSECONDS)) {
            return false;
        }

        try {
            int available =
                stock.getOrDefault(
                    sku,
                    0);

            if (available < quantity) {
                return false;
            }

            stock.put(
                sku,
                available - quantity);

            return true;
        } finally {
            lock.unlock();
        }
    }
}

Interruptible acquisition

lock.lockInterruptibly();

try {
    criticalOperation();
} finally {
    lock.unlock();
}

Interruptible and timed acquisition support bounded shutdown and deadlock avoidance strategies that intrinsic monitor entry does not directly expose.

15. Condition

A Condition factors monitor-style waiting into a distinct wait set associated with a Lock. Calling await() atomically releases the lock, waits, and re-acquires the lock before returning. Predicates must still be checked in a loop because of spurious wakeups and competing consumers.[12]

public final class BoundedBuffer<E> {
    private final ReentrantLock lock =
        new ReentrantLock();

    private final Condition notEmpty =
        lock.newCondition();

    private final Condition notFull =
        lock.newCondition();

    private final Object[] elements;
    private int head;
    private int tail;
    private int size;

    public BoundedBuffer(int capacity) {
        if (capacity < 1) {
            throw new IllegalArgumentException();
        }

        elements =
            new Object[capacity];
    }

    public void put(E element)
            throws InterruptedException {

        lock.lockInterruptibly();

        try {
            while (size
                    == elements.length) {
                notFull.await();
            }

            elements[tail] =
                Objects.requireNonNull(element);

            tail =
                (tail + 1)
                    % elements.length;

            size++;
            notEmpty.signal();
        } finally {
            lock.unlock();
        }
    }

    @SuppressWarnings("unchecked")
    public E take()
            throws InterruptedException {

        lock.lockInterruptibly();

        try {
            while (size == 0) {
                notEmpty.await();
            }

            E result =
                (E) elements[head];

            elements[head] = null;

            head =
                (head + 1)
                    % elements.length;

            size--;
            notFull.signal();

            return result;
        } finally {
            lock.unlock();
        }
    }
}

ArrayBlockingQueue already provides this bounded-buffer behavior. Custom condition code is justified only when the state machine differs materially from existing synchronizers.

16. Read/write and stamped locks

ReentrantReadWriteLock

A read/write lock permits multiple readers when no writer holds the write lock and one exclusive writer otherwise. It helps only when read sections are sufficiently long, writes are uncommon, and contention is measurable; lock coordination can cost more than a short synchronized section.[13]

public final class Catalog {
    private final ReadWriteLock lock =
        new ReentrantReadWriteLock();

    private final Map<String, Product> products =
        new HashMap<>();

    public Product find(String sku) {
        Lock read =
            lock.readLock();

        read.lock();

        try {
            return products.get(sku);
        } finally {
            read.unlock();
        }
    }

    public void replace(Product product) {
        Lock write =
            lock.writeLock();

        write.lock();

        try {
            products.put(
                product.sku(),
                product);
        } finally {
            write.unlock();
        }
    }
}

StampedLock

StampedLock has write, read, and optimistic-read modes. It is not reentrant and its optimistic reads are valid only when a subsequent validate succeeds; code inside an unvalidated optimistic section must tolerate inconsistent intermediate observations.[14]

public final class Position {
    private final StampedLock lock =
        new StampedLock();

    private double x;
    private double y;

    public double distanceFromOrigin() {
        long stamp =
            lock.tryOptimisticRead();

        double currentX = x;
        double currentY = y;

        if (!lock.validate(stamp)) {
            stamp =
                lock.readLock();

            try {
                currentX = x;
                currentY = y;
            } finally {
                lock.unlockRead(stamp);
            }
        }

        return Math.hypot(
            currentX,
            currentY);
    }

    public void move(
            double deltaX,
            double deltaY) {

        long stamp =
            lock.writeLock();

        try {
            x += deltaX;
            y += deltaY;
        } finally {
            lock.unlockWrite(stamp);
        }
    }
}

Visibility A volatile write happens-before every subsequent volatile read of the same field. Volatile accesses provide visibility and ordering but do not provide mutual exclusion for compound operations.[15]

18. Atomic classes

The java.util.concurrent.atomic package provides lock-free thread-safe updates to individual values and arrays through operations corresponding to VarHandle access modes. It includes atomic booleans, integers, longs, references, arrays, field updaters, accumulators, and adders.[16]

Sequence number

public final class Sequence {
    private final AtomicLong next =
        new AtomicLong(1);

    public long next() {
        return next.getAndIncrement();
    }
}

State machine with compare-and-set

enum State {
    NEW,
    RUNNING,
    TERMINATED
}

public final class Lifecycle {
    private final AtomicReference<State> state =
        new AtomicReference<>(
            State.NEW);

    public void start() {
        if (!state.compareAndSet(
                State.NEW,
                State.RUNNING)) {
            throw new IllegalStateException();
        }
    }

    public void terminate() {
        state.set(
            State.TERMINATED);
    }
}

Atomic update functions may be retried

AtomicInteger limit =
    new AtomicInteger(100);

limit.updateAndGet(
    current ->
        Math.max(
            1,
            current / 2));

The update function can be invoked more than once when contention causes a failed compare-and-set retry. It must therefore be side-effect-free.[17]

LongAdder for contended statistics

private final LongAdder requests =
    new LongAdder();

void record() {
    requests.increment();
}

long approximateTotal() {
    return requests.sum();
}

LongAdder distributes updates across internal variables under contention and is often preferable for high-update statistics. Its sum() is not an atomic snapshot relative to concurrent updates and is unsuitable for sequence numbers or exact transactional state.[18]

19. Compare-and-set, contention, and the ABA problem

Compare-and-set atomically changes a value when its current value equals an expected value. Lock-free algorithms build progress through retry loops, but contention can produce repeated failed retries and wasted CPU.

public int decrementUnlessZero(
        AtomicInteger value) {

    for (;;) {
        int current =
            value.get();

        if (current == 0) {
            return 0;
        }

        if (value.compareAndSet(
                current,
                current - 1)) {
            return current - 1;
        }

        Thread.onSpinWait();
    }
}

ABA

A compare-and-set can succeed after a value changes from A to B and back to A, even if that intermediate transition matters. Solutions include immutable nodes with identity, version numbers, AtomicStampedReference, or algorithm-specific reclamation/version schemes.

record VersionedState(
    State state,
    long version) {
}

AtomicReference<VersionedState> current =
    new AtomicReference<>(
        new VersionedState(
            State.NEW,
            0));

Lock-free is not wait-free

Lock-free algorithms guarantee system-wide progress under their assumptions, not bounded progress for every thread. A repeatedly losing thread can starve.

20. VarHandle and memory-access modes

VarHandle is a strongly typed handle to a field, array element, static variable, or supported off-heap location. It supports plain, opaque, acquire/release, volatile, compare-and-set, compare-and-exchange, and atomic update modes.[19]

public final class Flag {
    private static final VarHandle READY;

    static {
        try {
            READY =
                MethodHandles.lookup()
                    .findVarHandle(
                        Flag.class,
                        "ready",
                        boolean.class);
        } catch (ReflectiveOperationException failure) {
            throw new ExceptionInInitializerError(
                failure);
        }
    }

    private boolean ready;

    public void publish() {
        READY.setRelease(
            this,
            true);
    }

    public boolean isPublished() {
        return (boolean)
            READY.getAcquire(this);
    }
}

21. The Executor abstraction

Executors Executor separates task submission from the mechanics of thread creation, scheduling, and execution. An executor may run a task in a new thread, pooled thread, virtual thread, calling thread, or another implementation-defined context.[20]

public final class DirectExecutor
        implements Executor {

    @Override
    public void execute(
            Runnable command) {
        command.run();
    }
}

Submission establishes visibility

Order order =
    buildOrder();

executor.execute(
    () ->
        persist(order));

Actions before submission happen-before execution of the submitted task. This safely publishes task state through a compliant executor.[7]

Do not assume asynchronous execution

The base Executor interface does not promise a different thread or concurrent execution. APIs that require non-blocking submission or a particular execution context must document and enforce that contract.

22. ExecutorService lifecycle

ExecutorService adds result-bearing submission, bulk invocation, controlled shutdown, and termination management. shutdown() rejects new tasks but allows submitted tasks to finish; shutdownNow() prevents queued tasks from starting and attempts to interrupt executing tasks.[21]

Try-with-resources

try (ExecutorService executor =
        Executors.newFixedThreadPool(4)) {

    Future<Report> report =
        executor.submit(
            () ->
                generateReport());

    publish(
        report.get());
}

ExecutorService implements AutoCloseable. Its default close() performs an orderly shutdown and waits for termination, responding to interruption by escalating to shutdownNow() and restoring interruption.[21]

Explicit bounded shutdown

static void stop(
        ExecutorService executor,
        Duration timeout) {

    executor.shutdown();

    try {
        if (!executor.awaitTermination(
                timeout.toMillis(),
                TimeUnit.MILLISECONDS)) {

            executor.shutdownNow();

            if (!executor.awaitTermination(
                    timeout.toMillis(),
                    TimeUnit.MILLISECONDS)) {

                LOGGER.log(
                    System.Logger.Level.ERROR,
                    "Executor did not terminate");
            }
        }
    } catch (InterruptedException cancelled) {
        executor.shutdownNow();

        Thread.currentThread()
            .interrupt();
    }
}

24. Pool sizing, saturation, and backpressure

CPU-bound work

For compute-heavy independent tasks, a starting pool size near the number of processors is reasonable; measure cache behavior, vectorization, GC, and other process activity before increasing it.

Blocking work

Platform-thread pools can use more threads than processors when tasks wait, but the right size depends on blocking fraction and downstream capacity. Virtual threads often remove the need to size threads for blocking, but downstream concurrency still needs explicit limits.

Little's Law as a capacity lens

concurrency ≈ arrival_rate × average_latency

If a service receives 500 requests per second and each occupies a worker for 100 ms, the average required concurrency is approximately 50 before accounting for variability and tail latency. This is a capacity relationship, not a universal pool-size formula.

Caller-runs backpressure

CallerRunsPolicy executes a rejected task in the submitting thread unless the executor is shut down. It can slow producers naturally, but it is inappropriate when the submitting thread must remain non-blocking or has a sensitive role such as an event loop.

Expose saturation

    executor.getQueue().size();

    executor.getCompletedTaskCount();

    rejectionCounter.sum();

  • Reject before memory and latency become unbounded.
  • Propagate deadlines to queued work.
  • Remove or cancel obsolete queued requests when possible.
  • Measure queue wait separately from execution time.

25. Scheduled executors

ScheduledExecutorService schedules one-shot, fixed-rate, and fixed-delay tasks using relative delays. Scheduled execution has no real-time guarantee; a task starts no earlier than its enablement time and may start later because of scheduler or worker contention.[24]

Future<V> represents a pending or completed asynchronous result. It supports cancellation, completion inspection, blocking result retrieval, timed retrieval, and immediate state/result inspection methods. 27. Cancellation is a protocol

Future.cancel(true) requests interruption if a task is already running; it does not forcibly terminate arbitrary Java code. The task, libraries, and blocking operations must respond cooperatively.

Cancellation-aware task

public ImportResult importFile(
        Path path)
        throws IOException,
               InterruptedException {

    long rows = 0;

    try (BufferedReader reader =
            Files.newBufferedReader(path)) {

                (line = reader.readLine())
                    != null;) {

                throw new InterruptedException();

            rows++;
        }
    }

}

Non-interruptible work

CPU loops that never test interruption, blocking native calls, and libraries that swallow interruption can delay cancellation indefinitely. Design cancellation points and bound non-interruptible sections.

Side effects

Cancelling the local future does not roll back database commits, HTTP requests, file writes, or messages already sent. Use transactional boundaries, idempotency keys, compensation, or operation-status reconciliation.

public final class ProcessingPipeline
        implements AutoCloseable {

    private static final WorkItem STOP =
        WorkItem.stopMarker();

    private final BlockingQueue<WorkItem> queue;
    private final List<Thread> workers;

    public ProcessingPipeline(
            int capacity,
            int workerCount) {

        queue =
            new ArrayBlockingQueue<>(
                capacity);

        workers =
            IntStream.range(
                    0,
                    workerCount)
                .mapToObj(index ->
                    Thread.ofPlatform()
                        .name(
                            "processor-"
                                + index)
                        .start(
                            this::workerLoop))
                .toList();
    }

    public boolean submit(
            WorkItem item,
            Duration timeout)
            throws InterruptedException {

        return queue.offer(
            item,
            timeout.toNanos(),
            TimeUnit.NANOSECONDS);
    }

    private void workerLoop() {
        try {
            for (;;) {
                WorkItem item =
                    queue.take();

                if (item == STOP) {
                    return;
                }

                process(item);
            }
        } catch (InterruptedException cancelled) {
            Thread.currentThread()
                .interrupt();
        }
    }

    @Override
    public void close()
            throws InterruptedException {

        for (int index = 0;
                index < workers.size();
                index++) {

            queue.put(STOP);
        }

        for (Thread worker : workers) {
            worker.join();
        }
    }
}

ArrayBlockingQueue is a fixed-capacity FIFO queue backed by an array. Its optional fairness setting can reduce starvation but generally lowers throughput.[33]

Capacity is a service-level decision

A bounded queue limits memory and queueing delay. When full, the system must block producers, reject work, shed load, or route it elsewhere. An unbounded queue merely postpones overload until latency or memory becomes unacceptable.

36. The Fork/Join Framework

Fork/join ForkJoinPool is an executor optimized for tasks that recursively create subtasks. Worker threads use work stealing: a worker processes its own tasks and steals tasks from other workers when idle.[37]

worker A deque: [ A1 A2 A3 ] <─ owner pops worker B deque: [ B1 ] <─ owner pops worker C idle ──────────────► steals from opposite end

Task model

  • RecursiveTask<V> returns a result.
  • RecursiveAction returns no result.
  • CountedCompleter supports completion-triggered graphs.
  • ForkJoinTask is a lightweight future-like task designed for fork/join pools.[38]

Use for decomposable CPU work

Fork/join performs best when tasks split into enough independent CPU-bound subtasks, blocking is rare, and task sizes are large enough to amortize scheduling overhead.

Fork one branch, compute one directly

LeftTask left =
    new LeftTask(...);

left.fork();

Result rightResult =
    new RightTask(...)
        .compute();

Result leftResult =
    left.join();

return combine(
    leftResult,
    rightResult);

Computing one branch directly keeps the current worker productive and reduces queued task overhead.

37. RecursiveTask example

public final class ParallelLongSum
        extends RecursiveTask<Long> {

    private static final int THRESHOLD =
        50_000;

    private final long[] values;
    private final int start;
    private final int end;

    public ParallelLongSum(
            long[] values,
            int start,
            int end) {

        this.values = values;
        this.start = start;
        this.end = end;
    }

    @Override
    protected Long compute() {
        int length =
            end - start;

        if (length <= THRESHOLD) {
            long sum = 0;

            for (int index = start;
                    index < end;
                    index++) {

                sum += values[index];
            }

            return sum;
        }

        int middle =
            start
                + length / 2;

        ParallelLongSum left =
            new ParallelLongSum(
                values,
                start,
                middle);

        ParallelLongSum right =
            new ParallelLongSum(
                values,
                middle,
                end);

        left.fork();

        long rightValue =
            right.compute();

        long leftValue =
            left.join();

        return leftValue
            + rightValue;
    }
}
try (ForkJoinPool pool =
        new ForkJoinPool(
            Runtime.getRuntime()
                .availableProcessors())) {

    long total =
        pool.invoke(
            new ParallelLongSum(
                values,
                0,
                values.length));
}

RecursiveTask is the result-bearing recursive fork/join base class. Threshold selection is workload- and hardware-dependent and should be benchmarked.[39]

Avoid shared mutation

Return partial results and combine them. Shared counters, synchronized accumulation, or writes to adjacent shared memory can erase parallel speedup through contention and cache-coherence traffic.

39. Virtual threads (Project Loom)

Virtual threads Virtual threads are lightweight Thread instances implemented by the JDK. When a virtual thread blocks in supported operations, it can unmount from its carrier platform thread so that the carrier executes other virtual threads. They were finalized in Java 21.[40][41]

Thread-per-request style

public void acceptLoop(
        ServerSocket listener)
        throws IOException {

    while (!Thread.currentThread()
            .isInterrupted()) {

        Socket socket =
            listener.accept();

        Thread.startVirtualThread(
            () ->
                handle(socket));
    }
}

Why they scale

  • Virtual-thread stacks are represented in heap-managed chunks rather than one permanently reserved large native stack.
  • Blocking Java I/O generally parks the virtual thread without monopolizing a carrier.
  • Ordinary stack traces, exceptions, interruption, locks, thread locals, and debugging concepts remain available.
  • One virtual thread can represent one request or task for its entire lifetime.

What they do not change

  • CPU-bound work is still limited by processors.
  • Databases, remote services, file descriptors, sockets, and memory remain finite.
  • Data races and lock-order bugs remain bugs.
  • Cancellation is still cooperative.
  • Long-lived queues can still create unbounded latency.

Oracle's adoption guidance emphasizes that virtual threads increase throughput for highly concurrent blocking applications, not single-request speed, and should not be pooled.[40]

41. Pinning, monitors, and blocking behavior

Before Java 24, a virtual thread could remain mounted to its carrier while blocked inside a synchronized method or statement, reducing scalability. JEP 491 changed HotSpot so virtual threads can normally unmount when blocked on monitors or while waiting inside synchronized code. In Java 25, the principal remaining pinning cases are execution in native methods and foreign-function calls.[43][40]

synchronized is no longer a virtual-thread anti-pattern

public synchronized void update(
        Snapshot next) {

    snapshot =
        Objects.requireNonNull(next);
}

Use synchronized when it clearly protects a short invariant. Choose ReentrantLock for its own semantic features—timed or interruptible acquisition, several conditions, fairness, or lock inspection—not merely to avoid historical pinning.

Serialization still limits throughput

public synchronized Response callRemote() {
    return remoteClient.fetch();
}

Even when the virtual thread unmounts during I/O, the monitor remains held and other callers cannot enter. Do not hold a lock across network calls, database operations, callbacks, sleeps, or other slow/unknown work unless that serialization is explicitly required.

Native pinning

Frequent long native or foreign-function calls can occupy carrier threads. Measure them with JFR, isolate them behind bounded platform-thread executors when necessary, or use non-blocking/native integration designed for the workload.

44. Deadlock, livelock, starvation, and priority inversion

Deadlock

private final Object accountsLock =
    new Object();

private final Object ledgerLock =
    new Object();

void first() {
    synchronized (accountsLock) {
        synchronized (ledgerLock) {
            updateBoth();
        }
    }
}

void second() {
    synchronized (ledgerLock) {
        synchronized (accountsLock) {
            updateBoth();
        }
    }
}

If two threads enter the methods in opposite order, each can hold one monitor while waiting indefinitely for the other.

Consistent lock ordering

static void transfer(
        Account first,
        Account second,
        long amount) {

    Account lower =
        first.id().compareTo(
            second.id()) < 0
            ? first
            : second;

    Account higher =
        lower == first
            ? second
            : first;

    synchronized (lower.lock()) {
        synchronized (higher.lock()) {
            first.debit(amount);
            second.credit(amount);
        }
    }
}

Other progress failures

  • Livelock: threads repeatedly react to each other but no operation completes.
  • Starvation: one task continually loses access to CPU, locks, permits, or queue capacity.
  • Priority inversion: high-priority work waits for lower-priority work holding a needed resource.
  • Thread-pool starvation deadlock: all workers block waiting for tasks queued to the same saturated pool.

Avoid waiting on the same bounded pool

// Dangerous in a one-thread executor:
Future<Result> outer =
    executor.submit(() -> {
        Future<Part> inner =
            executor.submit(
                this::loadPart);

        return combine(
            inner.get());
    });

Use direct composition, a different execution resource, enough independently justified capacity, or structured concurrency/virtual threads with explicit downstream limits.

45. Testing concurrent code

Coordinate, do not sleep

@Test
void incrementsAreNotLost()
        throws Exception {

    int threads = 8;
    int increments = 100_000;

    AtomicInteger counter =
        new AtomicInteger();

    CountDownLatch ready =
        new CountDownLatch(
            threads);

    CountDownLatch start =
        new CountDownLatch(1);

    try (ExecutorService executor =
            Executors.newFixedThreadPool(
                threads)) {

        List<Future<?>> futures =
            IntStream.range(
                    0,
                    threads)
                .mapToObj(index ->
                    executor.submit(() -> {
                        ready.countDown();
                        start.await();

                        for (int count = 0;
                                count < increments;
                                count++) {

                            counter.incrementAndGet();
                        }

                        return null;
                    }))
                .toList();

        assertTrue(
            ready.await(
                2,
                TimeUnit.SECONDS));

        start.countDown();

        for (Future<?> future
                : futures) {

            future.get(
                5,
                TimeUnit.SECONDS);
        }
    }

    assertEquals(
        threads * increments,
        counter.get());
}

Test properties, not one interleaving

  • Invariants remain true after concurrent operations.
  • No item is lost, duplicated, or processed after cancellation.
  • Shutdown terminates within a bound.
  • Queue capacity and rejection policy behave under saturation.
  • Interrupted tasks restore or propagate interruption correctly.
  • Timeouts do not leak tasks, locks, permits, or threads.

Stress and repetition

@RepeatedTest(1_000)
void publicationIsSafe() {
    // Small targeted race scenario.
}

Repetition can expose races but cannot prove absence. Combine deterministic coordination, targeted stress, static analysis, model checking where practical, and production telemetry.

Never depend on Thread.sleep for readiness

Sleep-based tests are slow and flaky because they depend on scheduler timing. Use latches, barriers, phasers, futures, fake clocks for scheduled logic, and explicit test hooks.

Platform-thread deadlock detection

ThreadMXBean threads =
    ManagementFactory
        .getThreadMXBean();

long[] deadlocked =
    threads.findDeadlockedThreads();

if (deadlocked != null) {
    ThreadInfo[] information =
        threads.getThreadInfo(

ThreadMXBean monitors platform threads and can detect monitor and ownable-synchronizer deadlocks among them. It does not provide general management of virtual threads, and its deadlock methods do not find cycles involving virtual threads.[49]

Operational metrics

  • Active, queued, completed, rejected, and oldest-queued task counts.
  • Executor queue wait and execution duration.
  • Lock acquisition time and contention count.
  • Semaphore utilization and wait time.
  • Scheduled-task drift and suppressed failures.
  • Virtual-thread count, pin events, and downstream permit saturation.
  • Cancellation and interruption latency.

47. Performance engineering

Measure with JMH

Java concurrency microbenchmarks are vulnerable to dead-code elimination, constant folding, warmup effects, false sharing, timer noise, and accidental serialization. JMH is the OpenJDK benchmark harness for constructing and running JVM benchmarks.[52]

@State(Scope.Group)
public class CounterBenchmark {
    private final AtomicLong atomic =
        new AtomicLong();

    private final LongAdder adder =
        new LongAdder();

    @Benchmark
    @Group("atomic")
    @GroupThreads(8)
    public long atomicIncrement() {
        return atomic.incrementAndGet();
    }

    @Benchmark
    @Group("adder")
    @GroupThreads(8)
    public void adderIncrement() {
        adder.increment();
    }
}

Contention is a workload property

An atomic counter can outperform a lock at low contention and collapse under cache-line contention at high update rates. LongAdder spreads updates but sacrifices exact atomic snapshots. Read/write locks help only when their access pattern and critical-section duration justify their coordination cost.

False sharing

Independent hot variables that occupy the same cache line can invalidate one another across cores even without a logical data race. Detect the symptom through hardware/JFR/performance profiling and redesign data ownership before relying on VM-specific padding annotations.

Parallel speedup has limits

  • Sequential work limits maximum speedup.
  • Task creation, coordination, memory bandwidth, and cache misses add overhead.
  • Too-fine fork/join tasks spend more time scheduling than computing.
  • Too many platform threads increase context switching and stack memory.
  • Too many simultaneous virtual-thread operations can overload external systems.

Prefer end-to-end metrics

Measure throughput, p50/p95/p99 latency, queue wait, CPU, allocation, downstream saturation, and failure behavior under realistic load. A faster isolated primitive can make the complete service slower by increasing contention elsewhere.

48. Production concurrency checklist

State and memory model

  • Shared mutable state has one documented owner or synchronization policy.
  • Every cross-thread publication has a happens-before edge.
  • Compound invariants use one atomic operation or lock boundary.
  • Final fields and immutable snapshots are preferred.
  • Volatile fields are not used for compound increments or multi-field transactions.

Locks and waiting

  • Lock order is globally consistent.
  • Every explicit lock and permit is released in finally.
  • Condition predicates are tested in loops.
  • No slow I/O or unknown callback executes while holding a lock.
  • Timed or interruptible acquisition is used where shutdown/deadlines require it.

Executors and pools

  • Every executor has an owner and shutdown path.
  • Platform-thread pools use bounded queues and explicit rejection policy.
  • Queue wait and saturation are observable.
  • Tasks submitted with submit have their futures observed.
  • Scheduled periodic tasks catch/report expected failures.
  • The common fork/join pool is not burdened with uncontrolled blocking work.

Futures and cancellation

  • Every wait has an overall deadline where appropriate.
  • Cancellation is propagated and tasks respond to interruption.
  • Remote side effects are not assumed to roll back after cancellation.
  • CompletableFuture stages use explicit executors when isolation matters.
  • Timeout completion is not confused with cancellation of underlying work.

Collections and synchronizers

  • The collection's consistency model matches the workflow.
  • Compound map operations use compute, merge, or explicit locking.
  • Copy-on-write collections are limited to small read-mostly data.
  • Producer–consumer queues are bounded.
  • Semaphores limit the actual scarce resource.

Virtual threads and Loom

  • Virtual threads represent tasks and are never pooled.
  • CPU-bound concurrency remains bounded near processor capacity.
  • Database, network, and memory concurrency is explicitly limited.
  • Long native/foreign calls and pin events are measured.
  • synchronized is used according to invariant needs, not avoided because of obsolete pinning guidance.
  • Scoped values carry bounded immutable context.
  • Structured-concurrency preview usage is isolated and compiled/run with preview enabled.

Testing and operations

  • Tests coordinate with latches/barriers rather than sleeps.
  • Deadlock, saturation, cancellation, and shutdown paths are tested.
  • Thread dumps, JFR, and executor metrics are available during incidents.
  • Benchmarks use JMH and representative contention.
  • Changes are validated under overload, not only nominal traffic.
Final principle: concurrency is primarily a lifecycle and ownership problem. Threads and atomic instructions are implementation tools; reliable systems make task trees, state ownership, ordering, cancellation, deadlines, saturation, and failure propagation explicit.
