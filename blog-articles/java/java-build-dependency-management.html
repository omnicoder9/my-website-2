1. A build system is a reproducible transformation graph

A Java build transforms versioned source, resources, metadata, generated code, dependencies, toolchains, and configuration into tested, packaged, and publishable artifacts.

Project model

Identity, modules, source sets, packaging, language level, metadata, and publication coordinates.

Work graph

Lifecycle phases or tasks that compile, test, package, verify, document, and publish.

Dependency graph

Direct and transitive modules, variants, scopes/configurations, repositories, constraints, exclusions, and selected versions.

Execution environment

Build-tool version, JDK/toolchain, operating system, environment variables, credentials, network repositories, and caches.

Maven describes the build through a Project Object Model and conventional lifecycle. Gradle describes projects and tasks through Kotlin or Groovy build scripts and constructs a task directed acyclic graph for each invocation.[1][24]

The build is production code. It executes third-party plugins, controls compiler and test behavior, chooses dependencies, accesses credentials, and creates artifacts that other systems trust. Review, test, version, and secure it accordingly.

2. History and current tool lines

2002–2005: Maven established the POM, repository coordinates, standard directory layout, lifecycle phases, and convention-over-configuration model that shaped the Java ecosystem.

2010: Maven 3 retained the Maven 2 project model while modernizing the core, repository resolution, embedding, and parallel-build infrastructure.

2008 onward: Gradle combined dependency management and conventions familiar from Maven with a programmable task model, incremental execution, plugins, and Groovy—later Kotlin—build scripts.

2025: Gradle 9.0 began the 9.x line and adopted three-component version numbers.

2026: Maven 3.9.16 is the current stable Maven 3 release; Maven 3.10.0 was still at release-candidate status on 30 July 2026. Gradle 9.6.1 is the current Gradle release and is recommended over 9.6.0 because it contains patch fixes.[2][23]

Maven 3.9.16 requires Java 8 or later to run, while Gradle 9.x requires a modern JVM and its current installation guidance uses Java 17 for the Gradle daemon. Both tools can build code for a different Java version through toolchains.[2][29][49]

Separate the build JVM from the target JVM. The JDK that launches Maven or Gradle is not automatically the JDK that should compile, test, or generate documentation for the project.

4. Maven architecture

Maven Maven reads pom.xml, builds an effective model through the Super POM, parent inheritance, profiles, interpolation, and defaults, resolves dependencies and plugins from repositories, and invokes plugin goals bound to lifecycle phases.[3][5]

ModelPOM XML with coordinates, dependencies, build configuration, and metadata.
WorkPlugins expose goals; packaging types bind goals to lifecycle phases.
CompositionParent inheritance, aggregation modules, imported BOMs, and profiles.

Basic commands

# Compile production sources
./mvnw compile

# Run tests
./mvnw test

# Produce the artifact and run tests
./mvnw package

# Run all verification through verify
./mvnw clean verify

# Install the artifact into the local repository
./mvnw install

# Publish to the configured remote repository
./mvnw deploy

Invoking a lifecycle phase runs that phase and every earlier phase in the same lifecycle. A direct plugin goal such as dependency:tree runs that goal, not the complete default lifecycle.[5]

5. Maven Wrapper

The Maven Wrapper commits launcher scripts and configuration to the project so contributors and CI use a declared Maven distribution without a preinstalled matching Maven version. The wrapper downloads and caches the distribution when necessary.[9]

# Generate or update wrapper files.
mvn wrapper:wrapper -Dmaven=3.9.16

# Build through the project-owned launcher.
./mvnw --version
./mvnw clean verify

# Windows
mvnw.cmd clean verify
.mvn/wrapper/maven-wrapper.propertiesPin distribution and checksums 
wrapperVersion=3.3.4
distributionType=only-script
distributionUrl=https://repo.maven.apache.org/maven2/org/apache/maven/apache-maven/3.9.16/apache-maven-3.9.16-bin.zip
distributionSha256Sum=<official-sha256>

The wrapper supports SHA-256 verification for the wrapper JAR and Maven distribution through wrapperSha256Sum and distributionSha256Sum. Verify wrapper changes as supply-chain-sensitive code because the wrapper executes before project plugins and tests.[50]

6. POM anatomy

The POM is Maven's fundamental project model. A minimal Maven 3 POM contains the project root, modelVersion 4.0.0, groupId, artifactId, and version. Most projects also declare packaging, name, properties, dependencies, and build plugins.[3]

7. Maven lifecycle, phases, and goal bindings

Maven defines three built-in lifecycles: default for building and deploying, clean for removing build outputs, and site for project documentation. Each lifecycle is an ordered sequence of phases.[5]

Default lifecycle phaseTypical purpose
validateCheck project and environment prerequisites
generate-sourcesGenerate source code
process-resourcesCopy/filter main resources
compileCompile main sources
testRun unit tests
packageCreate JAR, WAR, or other primary artifact
verifyRun additional quality and integration checks
installInstall artifacts and POM into the local repository
deployPublish artifacts and metadata to a remote repository

Packaging controls default bindings. For a JAR project, the compiler goal is bound to compilation, Surefire to testing, and the JAR plugin to packaging. The JAR plugin's jar:jar goal binds by default to package.[15][16][17]

Do not invoke compile:compile as a normal build

# Runs the lifecycle and required preceding work.
./mvnw test

# Runs only one plugin goal directly.
./mvnw compiler:compile

Use phases for normal builds so resources, generated sources, tests, checks, and packaging remain coordinated. Invoke a direct goal for inspection or a deliberately isolated operation.

8. Artifact coordinates and repositories

Maven repositories store artifacts and metadata using a coordinate-derived path. The local repository caches downloaded artifacts and stores locally installed outputs; remote repositories provide released and snapshot components.[7][8]

# Coordinate:
com.example:money:1.0.0

# Repository path:
com/example/money/1.0.0/money-1.0.0.jar
com/example/money/1.0.0/money-1.0.0.pom

Repository policy

  • Prefer Maven Central and an authenticated organizational repository manager.
  • Centralize mirrors and credentials in settings.xml, not project POMs.
  • Avoid system-scoped dependencies and arbitrary local JAR paths.
  • Do not depend on mavenLocal()-style developer state in CI or published metadata.
  • Use immutable release versions; treat snapshots as changing development artifacts.

Maven settings can define local-repository location, mirrors, proxies, authentication servers, and environment-specific profiles. The user settings file normally lives at ~/.m2/settings.xml and should not be committed with credentials.[10]

9. Maven dependencies and scopes

Dependency graph Maven reads dependency POMs and includes transitive dependencies automatically. Scope determines the classpaths on which a dependency appears and how it propagates to consumers.[6]

compileYesYesYesYes
providedYesNoYesNo
runtimeNoYesYesYes at runtime
testNoNoYesNo

  <!-- Public library API and implementation classpath -->
  <dependency>
    <groupId>org.slf4j</groupId>
    <artifactId>slf4j-api</artifactId>
    <version>2.0.18</version>
  </dependency>

  <!-- Runtime provider, not required to compile source -->
  <dependency>
    <groupId>ch.qos.logback</groupId>
    <artifactId>logback-classic</artifactId>
    <version>1.6.1</version>
    <scope>runtime</scope>
  </dependency>

  <!-- Test only -->
  <dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <scope>test</scope>
  </dependency>
</dependencies>

Directly declare what source code uses

Even when a class is available transitively, declare its component directly if production or test source imports it. This makes the classpath contract explicit and prevents a transitive dependency from disappearing when an unrelated direct dependency changes.

10. Dependency mediation, optional dependencies, and exclusions

When multiple dependency paths request different versions of one artifact, Maven uses dependency mediation: the nearest definition in the dependency tree wins, and declaration order breaks ties at the same depth. A version managed in the current project's dependencyManagement can override transitive versions.[6]

application
├── library-a
│   └── codec:1.8
└── library-b
    └── helper
        └── codec:1.6

Selected: codec:1.8
because it is nearer to application.

Inspect before overriding

./mvnw dependency:tree

./mvnw dependency:tree \
  -Dincludes=commons-codec:commons-codec

./mvnw dependency:analyze

The Maven Dependency Plugin can render the graph and analyze used-but-undeclared or declared-but-unused dependencies.[18]

Exclusion

<dependency>
  <groupId>com.example</groupId>
  <artifactId>legacy-client</artifactId>
  <version>4.2.0</version>

  <exclusions>
    <exclusion>
      <groupId>commons-logging</groupId>
      <artifactId>commons-logging</artifactId>
    </exclusion>
  </exclusions>
</dependency>

An exclusion removes one dependency path, not every occurrence in the graph. Use it when the upstream metadata is wrong, the dependency is genuinely unnecessary for the selected feature, or another implementation is intentionally supplied. Run tests that cover the affected code path.

Optional dependency

<dependency>
  <groupId>com.example</groupId>
  <artifactId>metrics-integration</artifactId>
  <version>1.0.0</version>
  <optional>true</optional>
</dependency>

An optional dependency remains on the current project's classpath but is not automatically included when another project depends on it. Consumers that use the optional feature must declare the dependency themselves.

Convergence enforcement

The Maven Enforcer dependencyConvergence rule fails the build when different versions of an artifact occur in the dependency tree, forcing explicit alignment instead of silent nearest-wins selection.[14]

BOM imports are designed to keep related components on compatible versions and are particularly useful for libraries distributed as a coordinated family.[6]

Parent POM and BOM solve different problems. A parent shares build configuration and metadata through inheritance. A BOM shares dependency-version constraints through import and can be consumed without inheriting the build.

12. Maven plugins, goals, and executions

A Maven plugin contains one or more goals. A goal can be invoked directly or bound to a lifecycle phase through an execution. Maven core and plugin releases are independent, so production POMs should pin plugin versions.[2][21]

pom.xmlGenerate source metadata during the lifecycle 
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-resources-plugin</artifactId>
  <version>3.5.0</version>

  <executions>
    <execution>
      <id>copy-filtered-build-info</id>
      <phase>generate-resources</phase>

      <goals>
        <goal>copy-resources</goal>
      </goals>

      <configuration>
        <outputDirectory>
          ${project.build.outputDirectory}
        </outputDirectory>

        <resources>
          <resource>
            <directory>src/build-info</directory>
            <filtering>true</filtering>
          </resource>
        </resources>
      </configuration>
    </execution>
  </executions>
</plugin>

Execution identity

Give executions stable IDs. Parent and child plugin configuration merges by plugin coordinates and execution ID, so clear IDs make inheritance and override behavior understandable.

Current example plugin line

  • Maven Compiler Plugin 3.15.0 compiles Java sources and recommends setting release explicitly.[15]
  • Maven JAR Plugin 3.5.1 creates the main JAR.[17]
  • Maven Dependency Plugin 3.11.0 inspects, analyzes, copies, and unpacks dependencies.[18]
  • Maven Source Plugin 3.4.0 creates source archives.[19]

13. pluginManagement versus plugins

pluginManagement defines default versions and configuration for matching plugin declarations in the current POM or descendants. It does not generally activate a new plugin execution. The plugins section declares active build plugins and executions.

<build>
  <pluginManagement>
    <plugins>
      <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <artifactId>maven-compiler-plugin</artifactId>
        <version>3.15.0</version>

        <configuration>
          <release>${maven.compiler.release}</release>
          <parameters>true</parameters>
        </configuration>
      </plugin>

      <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <artifactId>maven-surefire-plugin</artifactId>
        <version>3.5.5</version>
      </plugin>
    </plugins>
  </pluginManagement>

  <plugins>
    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-compiler-plugin</artifactId>
    </plugin>

    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-surefire-plugin</artifactId>
    </plugin>
  </plugins>
</build>

Put organization-wide versions and defaults in a parent POM's management section. Activate only the plugins required by each packaging or module, unless the parent intentionally enforces a check in every child.

14. Profiles and environment-specific settings

Maven profiles conditionally modify the effective POM based on explicit profile selection or activation conditions. They can add properties, dependencies, repositories, plugins, and configuration.[20]

  <profile>
    <id>integration-tests</id>

    <activation>
      <property>
        <name>runITs</name>
      </property>
    </activation>

    <build>
      <plugins>
        <plugin>
          <groupId>org.apache.maven.plugins</groupId>
          <artifactId>maven-failsafe-plugin</artifactId>
          <version>3.5.5</version>

            <execution>
              <goals>

      </plugins>

./mvnw verify -DrunITs
./mvnw help:active-profiles

Profile guidance

  • Prefer explicit activation to machine-specific file or JDK heuristics.
  • Do not use profiles to produce semantically different release artifacts from the same coordinates.
  • Keep credentials and repository mirrors in settings, not project profiles.
  • Use CI matrices for supported environments rather than hiding all variation in one enormous POM.

15. Maven multi-module builds and the reactor

Maven distinguishes aggregation from inheritance. An aggregator POM lists modules in <modules>; a parent POM supplies inherited model content. One POM commonly plays both roles, but the relationships are independent.[3][11]

The reactor collects modules, sorts them according to project, plugin, plugin-dependency, and extension relationships, then builds them in dependency order. dependencyManagement alone does not create reactor ordering because it is not an instantiated dependency.[11]

commerce/
├── pom.xml
├── commerce-bom/
│   └── pom.xml
├── commerce-domain/
│   ├── pom.xml
│   └── src/...
├── commerce-service/
│   ├── pom.xml
│   └── src/...
└── commerce-app/
    ├── pom.xml
    └── src/...
# Build every module.
./mvnw clean verify

# Build one selected module plus required reactor dependencies.
./mvnw -pl commerce-app -am verify

# Build one module and modules that depend on it.
./mvnw -pl commerce-domain -amd test

# Resume after a failed module.
./mvnw -rf :commerce-service verify

# Continue independent modules and report failures at the end.
./mvnw --fail-at-end verify

Module-boundary rules

  • Keep dependencies acyclic.
  • Do not share source directories across modules.
  • Expose stable APIs from lower-level modules and keep application wiring at the top.
  • Avoid splitting modules so finely that every change rebuilds and releases the entire reactor anyway.
  • Use separate repositories/builds when components truly have independent versioning and release cadence.

24. A custom cacheable Gradle task

Gradle's incremental execution and build cache require complete, stable task inputs and outputs. Lazy Property, RegularFileProperty, and DirectoryProperty values also carry producer information so Gradle can infer task dependencies.[33][46]

build.gradle.ktsTyped generated metadata 
import org.gradle.api.DefaultTask
import org.gradle.api.file.RegularFileProperty
import org.gradle.api.provider.Property
import org.gradle.api.tasks.*

@CacheableTask
abstract class GenerateBuildInfo : DefaultTask() {

    @get:Input
    abstract val artifactName: Property<String>

    @get:Input
    abstract val artifactVersion: Property<String>

    @get:Input
    abstract val revision: Property<String>

    @get:OutputFile
    abstract val outputFile: RegularFileProperty

    @TaskAction
    fun generate() {
        val destination =
            outputFile.get().asFile

        destination.parentFile.mkdirs()

        destination.writeText(
            """
            name=${artifactName.get()}
            version=${artifactVersion.get()}
            revision=${revision.get()}
            """.trimIndent() + "\n"
        )
    }
}

val generateBuildInfo =
    tasks.register<GenerateBuildInfo>(
        "generateBuildInfo"
    ) {
        artifactName.set(project.name)
        artifactVersion.set(
            provider { project.version.toString() }
        )
        revision.set(
            providers.environmentVariable(
                "GIT_COMMIT"
            ).orElse("unknown")
        )

        outputFile.set(
            layout.buildDirectory.file(
                "generated-resources/build-info.properties"
            )
        )
    }

sourceSets.main {
    resources.srcDir(
        generateBuildInfo.map {
            it.outputFile.get().asFile.parentFile
        }
    )
}

Task rules

  • Perform file or process work in @TaskAction, not during configuration.
  • Declare every semantic input and output.
  • Use relative path sensitivity when absolute paths do not affect output.
  • Do not read ambient environment values inside the task action without declaring them as inputs.
  • Make output deterministic before marking a task cacheable.

Gradle platforms align versions through dependency constraints. A platform can import a Maven BOM or be produced by a java-platform project and published as Gradle Module Metadata and a Maven BOM.[39][40]

Consume a platform

Create a platform

    `java-platform`
    `maven-publish`
}

    allowDependencies()
}

    api(
        platform("org.junit:junit-bom:5.13.4")

        api(
            "org.slf4j:slf4j-api:2.0.18"

A dependency constraint contributes a version requirement only when the module appears in the graph. It does not add the module. Gradle constraints can be preferred, strict, ranged, or rejected; strictness should be used deliberately because it can make a graph unsatisfiable.[41]

Conflict resolution

When different paths request versions of one module, Gradle considers the requested versions and by default selects the highest version that satisfies the active constraints. Capability conflicts identify multiple components that claim the same functionality and may require an explicit choice.[36]

configurations.configureEach {
    resolutionStrategy {
        failOnVersionConflict()
    }
}

failOnVersionConflict() converts implicit version selection into a build failure, which can be useful in tightly controlled applications. Published libraries should normally express constraints rather than force internal resolution rules on consumers.

28. Gradle dependency locking, verification, and repository control

Dependency locking

Dependency locking records the resolved versions of selected configurations and fails later resolution when the graph differs from the committed lock state. It is especially useful when ranges or dynamic selectors are unavoidable; it is not a substitute for immutable artifacts and should not be used to pretend changing snapshots are stable.[42]

dependencyLocking {
    lockAllConfigurations()
}
# Resolve configurations and write lock files.
./gradlew dependencies --write-locks

# Update only selected modules.
./gradlew dependencies \
  --update-locks org.slf4j:slf4j-api

# Normal builds verify the lock state.
./gradlew build

Commit Gradle lock files. Update them in a reviewed dependency-upgrade change so the graph modification is visible independently of the build script.

Gradle dependency verification can validate checksums and signatures for dependency artifacts and metadata across the complete build, including subprojects and buildSrc. A mismatch requires investigation rather than automatic acceptance.[43]

31. Gradle incremental builds, build cache, and configuration cache

Up-to-date checks

When a task declares complete inputs and outputs, Gradle can skip execution when its outputs are already valid. This is local incremental build avoidance and does not require the build cache.

Build cache

The Gradle build cache stores outputs of cacheable tasks and can reuse them locally or from a remote cache when the cache key matches. Cache keys incorporate task implementation and declared normalized inputs; incomplete input declarations can produce incorrect reuse.[46]

gradle.propertiesBuild performance defaults 
org.gradle.caching=true
org.gradle.parallel=true

# Enable only after plugins and custom tasks are compatible.
org.gradle.configuration-cache=true
# One invocation without persistent configuration.
./gradlew build --build-cache

# Explain task outcomes.
./gradlew build --info

Configuration cache

The configuration cache stores the result of the configuration phase so a later compatible invocation can skip re-evaluating build scripts and reconstruct the task graph from cached state. It is disabled by default in Gradle 9.6.1 and requires compatible build logic and plugins.[48]

# Trial run and diagnostic report.
./gradlew build --configuration-cache

# Temporarily surface incompatibilities as warnings
# during migration, not as permanent policy.
./gradlew build \
  --configuration-cache \
  --configuration-cache-problems=warn

Cache correctness rules

  • Declare environment variables, system properties, files, tool versions, and classpaths that affect output.
  • Do not write outside declared output locations.
  • Do not let two tasks own overlapping output files.
  • Normalize absolute paths when output should be relocatable.
  • Do not cache tasks that publish, deploy, sign with nondeterministic material, or mutate external systems.
  • Treat a remote cache as trusted artifact infrastructure with authentication, integrity, and access policy.

Publication contract

  • Coordinate changes are API changes for consumers.
  • Publish source and documentation artifacts for libraries.
  • Validate generated POM or Gradle Module Metadata before release.
  • Do not publish test fixtures or internal implementation dependencies accidentally.
  • Release artifacts should be immutable; never replace bytes at an existing release coordinate.
  • Sign and attest releases according to repository and organizational policy.

34. Maven versus Gradle

ConcernMavenGradle
Primary modelDeclarative XML POM and conventional lifecycleProject/task model configured through Kotlin or Groovy DSL
Work definitionPlugin goals bound to ordered phasesTasks connected in a DAG
Project layoutStandard layout is central to conventionsJava plugins use Maven-compatible conventions
Dependency scopesFixed scopes such as compile, runtime, provided, testPlugin-created configurations, attributes, capabilities, and variants
Version alignmentdependencyManagement and imported BOMsPlatforms, constraints, catalogs, locking
Multi-project modelAggregator modules and reactor orderingSubprojects, project dependencies, composite builds
Shared build policyParent POMs and plugin managementConvention plugins and included build logic
IncrementalityPrimarily plugin-specific and lifecycle-orientedTask inputs/outputs, up-to-date checks, local/remote build cache
CustomizationPrefer existing plugins; custom plugin development for new behaviorBuild scripts can register tasks; plugins are preferred for reusable logic
DebuggingEffective POM, lifecycle, dependency treeTask graph, dependency insight, build/configuration cache reports

Choose Maven when

  • Uniform conventions and a predictable lifecycle are more important than custom task modeling.
  • The organization has mature parent POMs, BOMs, and Maven repository governance.
  • The project is a conventional Java library or application with well-supported plugins.
  • Build readability for broad Java ecosystem contributors is a priority.

Choose Gradle when

  • The build has complex generated artifacts, custom pipelines, variant-aware components, or non-Java tasks.
  • Incremental execution and local/remote task-output reuse materially affect developer throughput.
  • The project needs reusable typed convention plugins and composite build logic.
  • Android or other Gradle-native ecosystems determine the build tool.
Both tools can produce excellent or fragile builds. The decisive factors are dependency policy, plugin quality, model clarity, reproducibility, security, and the team's ability to maintain the build—not XML versus Kotlin syntax alone.

35. Migrating between Maven and Gradle

Inventory semantics before translating syntax

  • Source sets and generated-source directories.
  • Compiler release, annotation processors, test engines, JVM arguments, and fork behavior.
  • Resource filtering and encoding.
  • Dependency scopes/configurations, optional dependencies, exclusions, and BOM imports.
  • Integration-test lifecycle, quality checks, packaging, manifest, shading, signing, and publication metadata.
  • Profiles, environment variables, repository mirrors, credentials, and CI parameters.
  • Multi-module boundaries and release ordering.

Parallel validation

./gradlew clean build

  | sort > maven-jar.txt

Migration rules

  • Do not delete the old build until dependency graphs, tests, artifacts, manifests, and publication metadata match intended semantics.
  • Do not call Maven from Gradle or Gradle from Maven as a permanent architecture.
  • Replace plugins by behavior, not by similar names.
  • Rebaseline reproducible hashes only after explaining every artifact difference.
  • Update IDE and CI entry points to use the new wrapper.

CI principles

  • Run only the committed wrapper.
  • Use clean, ephemeral workers for release verification.
  • Cache downloaded dependencies and verified task outputs—not unreviewed final release artifacts.
  • Keep repository credentials scoped to publishing jobs, not pull-request builds.
  • Use read-only repository credentials for ordinary builds.
  • Retain dependency reports, test reports, SBOMs, checksums, provenance, and effective build configuration for releases.
  • Test offline or through a controlled mirror to expose undeclared repository dependencies.

37. Production build and dependency-management checklist

Toolchain and wrappers

  • Maven or Gradle version is pinned by the committed wrapper.
  • Wrapper JAR and distribution checksums are verified.
  • Build JVM and Java compilation/test toolchain are explicit.
  • Local development and CI invoke the same wrapper commands.

Project structure

  • Production, test, generated, fixture, and integration-test sources have explicit ownership.
  • Generated outputs live under target or build.
  • Modules form an acyclic dependency graph.
  • Module boundaries match stable API, ownership, or release boundaries.

Maven

  • Plugin versions are pinned.
  • dependencyManagement manages versions without being confused with declarations.
  • pluginManagement supplies defaults without being confused with activation.
  • Profiles are explicit and do not create different releases under identical coordinates.
  • Effective POM and dependency tree are inspected in CI for policy checks.
  • Reactor selection commands are documented.

Gradle

  • Tasks are registered lazily.
  • Custom tasks declare complete typed inputs and outputs.
  • api is used only for dependencies exposed in the public ABI.
  • Version catalogs are paired with platforms or constraints where enforcement is required.
  • Lock files and verification metadata are committed.
  • Shared policy lives in convention plugins.
  • Build and configuration caches are enabled only after correctness validation.

Dependency graph

  • Every imported type has a direct declared dependency.
  • Transitive conflicts are visible and intentionally resolved.
  • Exclusions have tests covering the affected functionality.
  • Dynamic and changing versions are prohibited in releases.
  • Snapshots are restricted to development channels.
  • Repository sources are centralized and approved.
  • Dependency checksums/signatures and SBOMs are part of release evidence.

Reproducibility and publication

  • Build timestamps and generated ordering are deterministic.
  • Artifacts can be rebuilt in a clean environment and hash-compared.
  • Published POM/metadata correctly represents API and runtime dependencies.
  • Release coordinates are immutable.
  • Sources, Javadoc, license, SCM, and provenance metadata are published where required.
  • Signing and credentials are isolated to release jobs.
Final principle: a good Java build makes inputs, dependency selection, toolchains, work ordering, and outputs explicit. Maven achieves this primarily through a stable model and lifecycle; Gradle achieves it through typed project and task graphs. In either system, reproducibility and supply-chain integrity come from deliberate policy—not from the tool name.
