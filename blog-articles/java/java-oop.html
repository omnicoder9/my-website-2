1. Object-oriented programming as collaboration among typed objects

Object-oriented design organizes a program around objects that expose behavior through types while controlling access to their representation. Java combines class-based single inheritance, multiple interface inheritance, reference semantics, static typing, dynamic dispatch for overridden instance methods, and a universal root class named Object.

Encapsulation

Keep state and invariants behind a coherent behavioral boundary.

Abstraction

Expose the operations clients need while omitting irrelevant representation detail.

Inheritance

Define a subtype by extending one class or implementing one or more interfaces.

Polymorphism

Use a supertype reference to invoke subtype-specific behavior through dynamic dispatch.

Java classes support single class inheritance; variables of a class or interface type can refer to compatible subclass or implementing-class objects. Instance methods operate on a current object, while class methods operate without a current instance.[1]

OOP is not “put every field behind getters and setters.” Its central task is to define stable responsibilities, valid state transitions, substitutable types, and explicit ownership.

2. Classes and objects

Class A class declaration defines a class and describes its implementation. An object is a dynamically created class instance or array; reference values point to objects or contain the special null reference.[2][3]

public final class Account {
    private final AccountId id;
    private BigDecimal balance;

    public Account(
            AccountId id,
            BigDecimal openingBalance) {

        this.id =
            Objects.requireNonNull(id);

        this.balance =
            requireNonNegative(
                openingBalance);
    }

    public AccountId id() {
        return id;
    }

    public BigDecimal balance() {
        return balance;
    }

    public void deposit(
            BigDecimal amount) {

        balance =
            balance.add(
                requirePositive(amount));
    }
}
Account account =
    new Account(
        accountId,
        new BigDecimal("100.00"));

3. Identity, state, and behavior

AspectJava manifestation
IdentityA particular object reference; reference equality uses ==
StateValues stored in instance fields and reachable owned objects
BehaviorInstance methods that observe or change state
TypeCompile-time class/interface type and runtime object class
Account firstReference =
    account;

Account secondReference =
    account;

assert firstReference
    == secondReference;

Many references can point to the same object. A mutation through one alias is observable through every alias that reaches that object.[3]

Value objects versus entities

A value object is normally identified by its attributes, while an entity has continuity or identity independent of its current attributes. The choice affects equality, mutation, persistence, and copying.

4. Class declarations

public sealed abstract class Shape
        permits Circle,
                Rectangle {

    private final String label;

    protected Shape(
            String label) {

        this.label =
            Objects.requireNonNull(label);
    }

    public final String label() {
        return label;
    }

    public abstract double area();
}

A class body can declare fields, methods, member classes and interfaces, instance and static initializers, and constructors. Every class except Object extends one direct superclass and may implement interfaces.[2]

Class modifiers

  • abstract: incomplete and not directly instantiable.
  • final: cannot be subclassed.
  • sealed: restricts direct subclasses.
  • static: available for member classes, indicating no enclosing instance.

5. Fields

A field declaration creates either an instance variable, freshly present in each object, or a static class variable, present once per class. A final field can be assigned only once.[2]

public final class Sensor {
    private static long createdCount;

    private final SensorId id;
    private double lastReading;
    private volatile boolean active;

    public Sensor(
            SensorId id) {

        this.id =
            Objects.requireNonNull(id);

        createdCount++;
    }
}

Do not expose mutable fields

// Fragile public representation:
public List<LineItem> items =
    new ArrayList<>();

Public mutable fields let any caller violate ordering, validation, synchronization, and lifecycle policies.

6. Field defaults and explicit initialization

Instance and static fields receive default values before explicit initializers run: numeric zero, false, '\u0000', or null. Local variables do not receive automatic default initialization and must be definitely assigned before use.[3]

final class Defaults {
    int count;          // 0
    boolean ready;      // false
    Object value;       // null
}

Prefer valid construction over temporary invalid defaults

public final class Endpoint {
    private final URI uri;
    private final Duration timeout;

    public Endpoint(
            URI uri,
            Duration timeout) {

        this.uri =
            Objects.requireNonNull(uri);

        this.timeout =
            requirePositive(timeout);
    }
}

7. Methods

Methods declare executable behavior. Instance methods are invoked relative to an object and can use this; static methods are invoked relative to a class and have no current instance.[2]

public final class Cart {
    private final List<LineItem> items =
        new ArrayList<>();

    public void add(
            Product product,
            int quantity) {

        items.add(
            new LineItem(
                product,
                requirePositive(quantity)));
    }

    public BigDecimal subtotal() {
        return items.stream()
            .map(LineItem::total)
            .reduce(
                BigDecimal.ZERO,
                BigDecimal::add);
    }
}

Commands and queries

Commands change state; queries return information. Separating them often makes side effects and invariants easier to reason about.

8. Method signatures, overloading, and resolution

A method signature consists of its name and parameter types after relevant adaptation; return type alone does not distinguish overloads. Overload selection is performed at compile time from the argument and target types.[2]

void send(
    String message) {
}

void send(
    byte[] payload) {
}

void send(
    Message message) {
}

Not a legal overload

// Illegal: return type alone differs.
int size() {
    return 0;
}

// long size() { return 0L; }

Overloading is not overriding

Overloading selects among declarations at compile time; overriding selects an implementation at runtime for an already selected instance-method signature.

9. Constructors

Constructors initialize new class instances. They have the class name, no return type, are not members, are not inherited, and cannot be overridden.[2]

public final class ConnectionPolicy {
    private final Duration timeout;
    private final int retries;

    public ConnectionPolicy(
            Duration timeout,
            int retries) {

        this.timeout =
            requirePositive(timeout);

        if (retries < 0) {
            throw new IllegalArgumentException(
                "retries must be non-negative");
        }

        this.retries = retries;
    }
}

Default constructor

If a class declares no constructor, the compiler can provide a default constructor whose accessibility matches the class and which invokes the superclass no-argument constructor.

10. Constructor chaining with this and super

public final class RetryPolicy {
    private final int attempts;
    private final Duration delay;

    public RetryPolicy() {
        this(
            3,
            Duration.ofSeconds(1));
    }

    public RetryPolicy(
            int attempts,
            Duration delay) {

        this.attempts =
            requirePositive(attempts);

        this.delay =
            requireNonNegative(delay);
    }
}

Superclass construction

public class Employee
        extends Person {

    private final EmployeeId employeeId;

    public Employee(
            String name,
            EmployeeId employeeId) {

        super(name);

        this.employeeId =
            Objects.requireNonNull(
                employeeId);
    }
}

An explicit constructor invocation calls another constructor of the same class with this(...) or a direct-superclass constructor with super(...).[2]

11. Object creation

A class-instance creation expression uses new, a class type, constructor arguments, and optionally an anonymous-class body. The selected constructor initializes the new instance.[4]

Order order =
    new Order(
        OrderId.random(),
        customerId,
        clock.instant());

Factory methods

Order order =
    Order.create(
        customerId,
        clock);

A factory can name construction intent, return cached or subtype objects, enforce canonicalization, and hide the concrete class.

Object allocation is not a constructor call alone

Creation includes allocation, default initialization, superclass initialization, instance field/initializer execution, and constructor-body execution.

12. Instance initialization order

allocate object ↓ default-initialize all instance fields ↓ invoke direct superclass constructor ↓ run this class's field initializers and instance initializer blocks in textual order ↓ run remaining constructor body

Superclass construction precedes subclass instance initializers. Field and instance initializer execution follows textual order within each class.[5]

class Base {
    Base() {
        System.out.println(
            "Base constructor");
    }
}

class Child extends Base {
    private int value =
        initializeValue();

    Child() {
        System.out.println(
            "Child constructor");
    }

    private int initializeValue() {
        System.out.println(
            "Child field");
        return 42;
    }
}

13. Reference variables

A variable of class type T can hold null or a reference to an instance of T or a subclass. A variable of interface type can refer to any object whose class implements that interface.[3]

Shape shape =
    new Circle(
        10.0);

Renderable renderable =
    new SvgCircle(
        10.0);

Object anything =
    shape;

References are copied by value

Account first =
    account;

Account second =
    first;

// Both variables now contain references
// to the same Account object.

Java does not pass objects “by reference” in the language-parameter sense; method arguments copy reference values.

14. Aliasing and ownership

List<String> source =
    new ArrayList<>();

Holder holder =
    new Holder(source);

source.add("later");
// Whether holder changes depends on whether
// Holder copied or retained source.

Defensive copy

public final class Holder {
    private final List<String> values;

    public Holder(
            Collection<String> values) {

        this.values =
            List.copyOf(values);
    }

    public List<String> values() {
        return values;
    }
}

Ownership policy should answer who may mutate, who retains references, whether inputs are copied, and whether returned collections are views or snapshots.

15. The null reference

The null reference points to no object and can be assigned or cast to any reference type. Dereferencing it generally throws NullPointerException.[3]

Customer customer =
    repository.findNullable(id);

if (customer == null) {
    return Optional.empty();
}

return Optional.of(customer);

Validate required collaborators

this.repository =
    Objects.requireNonNull(
        repository,
        "repository");

Use null-free internal invariants where practical. Optional return types, empty collections, sealed results, and explicit sentinel objects can model absence more safely.

16. Static members

Class-level A static field exists once per class rather than once per object. A static method has no current object and cannot directly access instance fields, instance methods, this, or super.[2]

public final class OrderIds {
    private static final AtomicLong
        SEQUENCE =
            new AtomicLong();

    private OrderIds() {
    }

    public static long next() {
        return SEQUENCE
            .incrementAndGet();
    }
}

Call through the declaring type

long id =
    OrderIds.next();

Although Java permits some static members to be referenced through an expression, doing so obscures that no dynamic dispatch occurs.

Static mutable state

Global mutable static fields create hidden dependencies, test interference, and synchronization requirements. Prefer immutable constants and explicitly injected stateful services.

17. Static initialization

A class is initialized before its first active use, including certain static field accesses, static method invocations, and instance creation. Static field initializers and static blocks execute in textual order.[5]

public final class Configuration {
    private static final Map<String, String>
        DEFAULTS;

    static {
        Map<String, String> values =
            new HashMap<>();

        values.put(
            "timeout",
            "30");

        DEFAULTS =
            Map.copyOf(values);
    }

    private Configuration() {
    }
}

Initialization failure

If class initialization fails, active use can produce ExceptionInInitializerError, and later attempts can fail because the class remains erroneous for that class loader.

18. Encapsulation

Boundary Encapsulation groups state with the operations that preserve its invariants and restricts uncontrolled access to implementation details.

public final class BankAccount {
    private BigDecimal balance;

    public BankAccount(
            BigDecimal openingBalance) {

        balance =
            requireNonNegative(
                openingBalance);
    }

    public BigDecimal balance() {
        return balance;
    }

    public void withdraw(
            BigDecimal amount) {

        requirePositive(amount);

        if (balance.compareTo(amount) < 0) {
            throw new InsufficientFunds();
        }

        balance =
            balance.subtract(amount);
    }
}

Encapsulation is behavioral

A class with private fields but unrestricted setters can remain poorly encapsulated if callers can place it into invalid states.

Access control applies to types, fields, methods, constructors, and member types. Top-level classes are public or package-access; member declarations can also be protected or private.[6]

Minimize visibility

Begin with private or package access and widen only for a real client or extension contract.

20. Getters and setters

Simple accessor

public String name() {
    return name;
}

Validated mutator

public void rename(
        String requestedName) {

    String normalized =
        Objects.requireNonNull(
                requestedName)
            .strip();

    if (normalized.isEmpty()) {
        throw new IllegalArgumentException(
            "Name must not be blank");
    }

    name = normalized;
}

Do not expose representation mechanically

// Weak domain API:
order.setStatus(
    OrderStatus.SHIPPED);

// Stronger transition:
order.markShipped(
    shipmentId,
    shippedAt);

Behavioral methods can express prerequisites, side effects, and domain vocabulary better than generic setters.

21. Information hiding

Information hiding protects design decisions likely to change: data representation, caching, algorithms, persistence, synchronization, validation, and external integration.

public interface CustomerDirectory {
    Optional<Customer> find(
        CustomerId id);
}
final class JdbcCustomerDirectory
        implements CustomerDirectory {

    private final DataSource dataSource;

    // SQL and mapping remain hidden.
}

Encapsulation versus information hiding

Encapsulation bundles data and behavior; information hiding minimizes which implementation decisions clients can depend upon. The two reinforce each other but are not identical.

22. Immutable objects

public final class Money {
    private final BigDecimal amount;
    private final Currency currency;

    public Money(
            BigDecimal amount,
            Currency currency) {

        this.amount =
            Objects.requireNonNull(amount);

        this.currency =
            Objects.requireNonNull(currency);
    }

    public Money add(
            Money other) {

        requireSameCurrency(other);

        return new Money(
            amount.add(
                other.amount),
            currency);
    }
}

Requirements

  • Do not expose mutators.
  • Initialize all state during construction.
  • Prevent or control subclassing.
  • Defensively copy mutable input and output.
  • Ensure reachable components cannot mutate unexpectedly.

Immutable objects simplify sharing, hashing, reasoning, and concurrency, but may require persistent data structures or controlled builders for large updates.

23. Composition and delegation

public final class AuditedRepository<T, ID>
        implements Repository<T, ID> {

    private final Repository<T, ID>
        delegate;

    private final AuditSink audit;

    public AuditedRepository(
            Repository<T, ID> delegate,
            AuditSink audit) {

        this.delegate =
            Objects.requireNonNull(
                delegate);

        this.audit =
            Objects.requireNonNull(
                audit);
    }

    @Override
    public Optional<T> find(
            ID id) {

        audit.record(
            "find",
            id);

        return delegate.find(id);
    }
}

Why composition often scales better

  • No dependence on protected representation.
  • Behavior can be selected or replaced at runtime.
  • Several collaborators can be combined without multiple class inheritance.
  • The wrapper controls exactly which operations it exposes.

Inheritance is appropriate for genuine substitutable subtypes; composition is appropriate for assembling capabilities.

24. Class inheritance

Subtype relation Every class except Object has one direct superclass. A subclass inherits accessible members subject to Java's overriding, hiding, and access rules.[2]

public class Message {
    private final Instant createdAt;

    protected Message(
            Instant createdAt) {

        this.createdAt =
            Objects.requireNonNull(
                createdAt);
    }

    public final Instant createdAt() {
        return createdAt;
    }
}

public final class EmailMessage
        extends Message {

    private final EmailAddress recipient;

    public EmailMessage(
            Instant createdAt,
            EmailAddress recipient) {

        super(createdAt);

        this.recipient =
            Objects.requireNonNull(
                recipient);
    }
}

Inheritance carries contracts

A subclass must honor all promises clients rely upon through the superclass type, not merely compile successfully.

25. The extends clause

public class SavingsAccount
        extends Account {
    // ...
}

The extends clause specifies the direct superclass. If omitted for an ordinary class other than Object, the direct superclass is Object.[2]

Generic superclass

public final class StringRepository
        extends AbstractRepository<String> {
}

Restrictions

  • A final class cannot be extended.
  • A sealed superclass restricts its permitted direct subclasses.
  • Inheritance cycles are illegal.
  • A class cannot extend multiple classes.

26. The super keyword

Invoke a superclass constructor

public PremiumAccount(
        AccountId id,
        BigDecimal balance) {

    super(
        id,
        balance);
}

Invoke an overridden superclass method

@Override
public void close() {
    flushPremiumMetrics();
    super.close();
}

Access a hidden field

int total =
    super.count
        + this.count;

super selects the direct-superclass member implementation and bypasses ordinary virtual dispatch for that selected invocation.

27. Inherited, hidden, and non-inherited declarations

DeclarationSubclass behavior
Accessible instance methodInherited and possibly overridden
Static methodInherited but can be hidden, not overridden
FieldInherited if accessible; same-named field hides it
Private memberNot inherited as accessible member; still part of superclass object state/behavior
ConstructorNever inherited

Class members include declared and inherited members, but constructors are not members and are never inherited.[2]

28. Method overriding

Overriding occurs when a subclass declares an instance method with an override-equivalent signature and compatible return/access/throws contract. The @Override annotation asks the compiler to verify intent.[2]

public class Notification {
    public String channel() {
        return "generic";
    }
}

public final class SmsNotification
        extends Notification {

    @Override
    public String channel() {
        return "sms";
    }
}

Restrictions

  • A final method cannot be overridden.
  • A private method is not overridden.
  • An overriding method cannot reduce accessibility.
  • Static methods are hidden rather than overridden.

29. Covariant returns and checked exceptions

Covariant result

class Document {
    Document copy() {
        return new Document();
    }
}

class PdfDocument extends Document {
    @Override
    PdfDocument copy() {
        return new PdfDocument();
    }
}

An overriding method can return a subtype of the overridden reference return type.

Narrower checked failure

interface Loader {
    Data load()
        throws IOException;
}

final class FileLoader
        implements Loader {

    @Override
    public Data load()
            throws FileNotFoundException {
        // ...
        return data;
    }
}

An overriding declaration cannot introduce broader checked exceptions than the overridden contract.

30. Static method hiding and field hiding

class Base {
    static String type() {
        return "base";
    }

    String label = "base";
}

class Child extends Base {
    static String type() {
        return "child";
    }

    String label = "child";
}
Base reference =
    new Child();

System.out.println(
    Base.type());        // base

System.out.println(
    reference.label);   // base

Static methods and fields are selected from the compile-time qualifying type, not by runtime dynamic dispatch. Hiding can confuse readers and should generally be avoided in public hierarchies.

31. Subtype polymorphism

One interface, many implementations A variable of a superclass or interface type can refer to objects of compatible runtime subclasses, allowing common code to invoke specialized behavior.[1]

List<Shape> shapes =
    List.of(
        new Circle(10),
        new Rectangle(4, 5));

double total =
    shapes.stream()
        .mapToDouble(
            Shape::area)
        .sum();

Client code depends on abstraction

static void publish(
        Report report,
        ReportRenderer renderer,
        OutputStream output)
        throws IOException {

    renderer.render(
        report,
        output);
}

New renderer implementations can participate without changing the publishing algorithm.

32. Dynamic method dispatch

For an overridden instance method, compile-time method resolution identifies the signature, then runtime dispatch selects the most specific applicable implementation from the object's runtime class.[4]

Notification notification =
    new SmsNotification();

String channel =
    notification.channel();
// "sms"
compile-time type: Notification selected signature: channel() runtime class: SmsNotification invoked body: SmsNotification.channel()

What is not dynamically dispatched

  • Fields.
  • Static methods.
  • Private methods.
  • Constructors.
  • Overload selection.

33. Dynamic dispatch during construction

Overridden instance methods can dispatch to a subclass implementation even while a superclass constructor is running, before subclass field initializers have executed.[5]

class Base {
    Base() {
        initialize();
    }

    void initialize() {
    }
}

class Child extends Base {
    private String value =
        "ready";

    @Override
    void initialize() {
        System.out.println(
            value);
        // null during Base construction
    }
}
Do not invoke overridable methods from constructors. The subclass can observe partially initialized state, publish this, or violate invariants.

34. Upcasting

Upcasting converts a subclass reference to a superclass or implemented-interface type. It is widening and normally requires no explicit cast.[7]

Circle circle =
    new Circle(10);

Shape shape =
    circle;

Object object =
    circle;

Capabilities are restricted by the reference type

Shape shape =
    new Circle(10);

double area =
    shape.area();

// Not available through Shape:
// shape.radius()

The object remains a Circle; only the compile-time operations visible through the variable change.

35. Downcasting

A downcast converts a supertype reference to a more specific subtype. It requires an explicit cast and a runtime compatibility check; failure throws ClassCastException.[7]

Shape shape =
    loadShape();

Circle circle =
    (Circle) shape;

double radius =
    circle.radius();

Unsafe assumption

Shape shape =
    new Rectangle(4, 5);

Circle circle =
    (Circle) shape;
// ClassCastException.

Frequent downcasts indicate a design smell

Move common behavior into a polymorphic method, visitor, sealed-type switch, or capability interface rather than repeatedly inspecting concrete types.

36. Pattern matching with instanceof

static double diameter(
        Shape shape) {

    if (shape
            instanceof Circle circle) {

        return circle.radius()
            * 2.0;
    }

    throw new IllegalArgumentException(
        "Shape has no diameter");
}

Flow-scoped variable

if (value
        instanceof String text
        && !text.isBlank()) {

    process(text);
}

Null handling

null instanceof T evaluates to false, so successful pattern matching also establishes a non-null reference.

37. Abstraction

Abstraction defines a client-facing model in terms of relevant operations and guarantees while omitting representation, storage, algorithm, and integration detail.

public interface ClockSource {
    Instant now();
}
public final class SystemClockSource
        implements ClockSource {

    private final Clock clock;

    public SystemClockSource(
            Clock clock) {
        this.clock =
            Objects.requireNonNull(clock);
    }

    @Override
    public Instant now() {
        return clock.instant();
    }
}

Abstractions should be cohesive, stable, and expressed in domain vocabulary rather than merely mirroring one implementation.

38. Abstract classes

An abstract class is incomplete or intentionally treated as incomplete. It cannot be instantiated directly but can define fields, constructors, concrete methods, abstract methods, protected extension hooks, and implemented interfaces.[2]

public abstract class ReportExporter {
    private final Charset charset;

    protected ReportExporter(
            Charset charset) {
        this.charset =
            Objects.requireNonNull(charset);
    }

    public final void export(
            Report report,
            OutputStream output)
            throws IOException {

        Objects.requireNonNull(report);
        Objects.requireNonNull(output);

        writeHeader(output);
        writeBody(
            report,
            output);
        writeFooter(output);
    }

    protected final Charset charset() {
        return charset;
    }

    protected abstract void writeBody(
        Report report,
        OutputStream output)
        throws IOException;

    protected void writeHeader(
            OutputStream output)
            throws IOException {
    }

    protected void writeFooter(
            OutputStream output)
            throws IOException {
    }
}

Template method

A final public algorithm can call protected hooks, centralizing invariant ordering while allowing controlled specialization.

39. Interfaces

Contract inheritance An interface declares a reference type implemented by otherwise unrelated classes. A class can implement multiple interfaces, and an interface can extend multiple interfaces.[8]

public interface Payable {
    Money amountDue();

    void markPaid(
        PaymentId paymentId,
        Instant paidAt);
}
public final class Invoice
        implements Payable,
                   Comparable<Invoice> {
    // ...
}

No interface instances

A variable of interface type refers to an object whose class implements the interface; interfaces themselves are not instantiated.

40. Interface members

MemberRole
Abstract instance methodRequired behavior for implementations
Default methodInherited instance implementation
Static methodInterface-level utility/factory; not inherited as instance behavior
Private methodImplementation helper for default/static methods
FieldImplicitly public static final constant field

public interface Identified<ID> {
    ID id();

    default boolean sameId(
            Identified<ID> other) {

        return Objects.equals(
            id(),
            other.id());
    }

    static <ID> Comparator<Identified<ID>>
    comparingIds(
            Comparator<? super ID>
                comparator) {

        return Comparator.comparing(
            Identified::id,
            comparator);
    }
}

41. Multiple interface inheritance

An interface can directly extend several interfaces, and a class can implement several interface types. This provides multiple behavioral contracts without multiple class-state inheritance.[8]

public interface Timestamped {
    Instant timestamp();
}

public interface Named {
    String name();
}

public interface NamedEvent
        extends Timestamped,
                Named {
}
public final class UserCreated
        implements NamedEvent,
                   Serializable {
    // ...
}

One object, several views

Named named = event;
Timestamped timestamped = event;
Object object = event;

42. Default-method conflict resolution

Class method wins

A concrete method inherited from a superclass takes precedence over an interface default method with the same signature.

More specific interface wins

A default from a subinterface can override a default from its superinterface.

Unrelated defaults require resolution

interface JsonNamed {
    default String format() {
        return "json";
    }
}

interface XmlNamed {
    default String format() {
        return "xml";
    }
}

final class Formatter
        implements JsonNamed,
                   XmlNamed {

    @Override
    public String format() {
        return JsonNamed.super
            .format();
    }
}

Java rejects ambiguous inherited defaults unless the class explicitly overrides and resolves them.[8]

An API can combine both: expose an interface for clients and provide an optional abstract skeletal implementation for implementers.

44. The Object class

Universal root Object is the root of the class hierarchy. Every class has Object as a superclass, and all objects, including arrays, support its methods.[9]

45. The equals() contract

Object.equals implements reference equality by default. An override defines logical equality and must be reflexive, symmetric, transitive, consistent, and false for null.[9]

public final class CustomerId {
    private final String value;

    public CustomerId(
            String value) {

        this.value =
            normalize(value);
    }

    @Override
    public boolean equals(
            Object other) {

        return this == other
            || other
                instanceof CustomerId id
            && value.equals(
                id.value);
    }

    @Override
    public int hashCode() {
        return value.hashCode();
    }
}

Choose equality fields carefully

Use stable fields that represent the type's logical identity or value. Mutable equality fields are dangerous in sets, maps, caches, and deduplication.

46. Equality and inheritance

The symmetry trap

class Point {
    final int x;
    final int y;

    // equals accepts any Point subtype
}

class ColoredPoint extends Point {
    final Color color;

    // Adding color to equality can break
    // symmetry or transitivity.
}

Extensible value classes make equality difficult because a subclass may add equality-relevant state while the superclass cannot anticipate it.

Strategies

  • Make value classes final.
  • Use records for transparent component-based values.
  • Use composition rather than extending an equality-bearing value class.
  • Use exact-class equality only when that is the documented domain relation.

Entity equality

Entities commonly compare by a stable identifier rather than every mutable attribute.

47. The hashCode() contract

Repeated calls must return the same integer while equality-relevant information is unchanged. Equal objects must have equal hash codes; unequal objects may collide.[9]

@Override
public int hashCode() {
    return Objects.hash(
        customerId,
        effectiveDate);
}

Objects provides null-safe equality and hashing helpers, though direct field hashing can avoid varargs allocation in hot paths.[10]

Hash collection invariant

Set<CustomerId> ids =
    new HashSet<>();

ids.add(id);

// Do not mutate fields used by
// id.equals/hashCode while stored.

Identity hash code

System.identityHashCode(object) returns the default identity-oriented hash code even if the class overrides hashCode.[11]

48. The toString() contract

Object.toString returns a non-null string formed from the runtime class name, @, and an unsigned hexadecimal hash code. Subclasses are recommended to provide concise, informative representations.[9]

@Override
public String toString() {
    return "Order[id=%s,status=%s,total=%s]"
        .formatted(
            id,
            status,
            total);
}

Do not treat toString() as a stable protocol

  • Format may evolve.
  • Locale and nested representations may vary.
  • Secrets can leak into logs.
  • Parsing it couples code to diagnostics.

Identity representation

String identity =
    Objects.toIdentityString(
        object);

49. clone() and Cloneable

Object.clone() creates a field-for-field copy of an object. If the runtime class does not implement the marker interface Cloneable, the method throws CloneNotSupportedException. Arrays support cloning regardless of this marker.[9][12]

public final class LegacyPoint
        implements Cloneable {

    private int x;
    private int y;

    @Override
    public LegacyPoint clone() {
        try {
            return (LegacyPoint)
                super.clone();
        } catch (
                CloneNotSupportedException
                    impossible) {

            throw new AssertionError(
                impossible);
        }
    }
}

Shallow copy

class Document
        implements Cloneable {

    List<Section> sections;
    // super.clone() copies the list reference,
    // not the list and its elements.
}

The cloning protocol is awkward because Cloneable declares no clone method, Object.clone is protected, constructors are bypassed, and deep-copy policy is unspecified.

50. Prefer explicit copying alternatives

Copy constructor

public Document(
        Document source) {

    this.title =
        source.title;

    this.sections =
        source.sections.stream()
            .map(Section::new)
            .toList();

Copy factory

public static Document copyOf(
        Document source) {

    return new Document(source);
}

Immutable update

public Customer withEmail(
        EmailAddress nextEmail) {

    return new Customer(
        id,

        nextEmail);
}

Serialization is not a general cloning API

Round-tripping through serialization is slow, couples copying to wire-format concerns, and can create security and compatibility problems.

51. finalize(): historical mechanism

Deprecated for removal In Java 25, Object.finalize() still exists but is deprecated for removal. Finalization has unpredictable latency, no guaranteed execution before process termination, ordering hazards, resurrection risks, and security/performance problems.[9]

// Historical only — do not write:
@Override
protected void finalize()
        throws Throwable {

    try {
        releaseNativeResource();
    } finally {
        super.finalize();
    }
}

JEP 421 deprecated finalization for removal in JDK 18 and established a staged path toward disabling and eventually removing it. Applications and libraries should migrate to explicit resource management.[13]

Garbage collection is memory management, not deterministic resource management. File descriptors, sockets, locks, native handles, and transactions require explicit ownership and release.

52. Modern resource cleanup

AutoCloseable and try-with-resources

public final class NativeBuffer
        implements AutoCloseable {

    private long address;
    private boolean closed;

    @Override
    public void close() {
        if (!closed) {
            closed = true;
            free(address);
            address = 0;
        }
    }
}
try (NativeBuffer buffer =
        NativeBuffer.allocate(size)) {

    process(buffer);
}

AutoCloseable integrates with try-with-resources for deterministic cleanup.[14]

Cleaner as a safety net

Cleaner can register an at-most-once cleanup action after phantom reachability, but explicit clean/close remains the efficient and predictable path. The cleaning action must not retain the registered object.[15]

private static final Cleaner
    CLEANER =
        Cleaner.create();

private static final class State
        implements Runnable {

    private long address;

    @Override
    public void run() {
        if (address != 0) {
            free(address);
            address = 0;
        }
    }
}

53. Complete example: polymorphic order fulfillment

Domain abstractions

public interface FulfillmentMethod {
    FulfillmentQuote quote(
        Order order,
        FulfillmentContext context);

    FulfillmentResult fulfill(
        Order order,
        FulfillmentContext context)
        throws FulfillmentException;
}
public record FulfillmentContext(
    Clock clock,
    Inventory inventory,
    EventPublisher events) {

    public FulfillmentContext {
        Objects.requireNonNull(clock);
        Objects.requireNonNull(inventory);
        Objects.requireNonNull(events);
    }
}

Encapsulated entity

public final class Order {
    private final OrderId id;
    private final CustomerId customerId;
    private final List<LineItem> items;
    private OrderStatus status;
    private FulfillmentReceipt receipt;

    public Order(
            OrderId id,
            CustomerId customerId,
            Collection<LineItem> items) {

        this.id =
            Objects.requireNonNull(id);

        this.customerId =
            Objects.requireNonNull(
                customerId);

        this.items =
            List.copyOf(items);

        if (this.items.isEmpty()) {
            throw new IllegalArgumentException(
                "Order must contain items");
        }

        this.status =
            OrderStatus.PENDING;
    }

    public OrderId id() {
        return id;
    }

    public List<LineItem> items() {
        return items;
    }

    public OrderStatus status() {
        return status;
    }

    public void markFulfilled(
            FulfillmentReceipt receipt) {

        if (status
                != OrderStatus.PENDING) {
            throw new IllegalStateException(
                "Order is not pending");
        }

        this.receipt =
            Objects.requireNonNull(
                receipt);

        status =
            OrderStatus.FULFILLED;
    }
}

Abstract base implementation

public abstract class
AbstractFulfillmentMethod
        implements FulfillmentMethod {

    @Override
    public final FulfillmentResult fulfill(
            Order order,
            FulfillmentContext context)
            throws FulfillmentException {

        Objects.requireNonNull(order);
        Objects.requireNonNull(context);

        validate(
            order,
            context);

        context.inventory()
            .reserve(order.items());

        boolean committed = false;

        try {
            FulfillmentReceipt receipt =
                performFulfillment(
                    order,
                    context);

            order.markFulfilled(
                receipt);

            context.events()
                .publish(
                    new OrderFulfilled(
                        order.id(),
                        context.clock()
                            .instant()));

            committed = true;

            return new FulfillmentResult(
                order.id(),
                receipt);
        } finally {
            if (!committed) {
                context.inventory()
                    .release(
                        order.items());
            }
        }
    }

    protected void validate(
            Order order,
            FulfillmentContext context)
            throws FulfillmentException {
    }

    protected abstract
    FulfillmentReceipt
    performFulfillment(
        Order order,
        FulfillmentContext context)
        throws FulfillmentException;
}

Polymorphic service

public final class FulfillmentService {
    private final Map<FulfillmentKind,
        FulfillmentMethod> methods;

    public FulfillmentService(
            Map<FulfillmentKind,
                FulfillmentMethod> methods) {

        this.methods =
            Map.copyOf(methods);
    }

    public FulfillmentResult fulfill(
            Order order,
            FulfillmentKind kind,
            FulfillmentContext context)
            throws FulfillmentException {

        FulfillmentMethod method =
            Optional.ofNullable(
                    methods.get(kind))
                .orElseThrow(() ->
                    new UnsupportedFulfillment(
                        kind));

        return method.fulfill(
            order,
            context);
    }
}

Design properties

  • The service depends on the FulfillmentMethod abstraction rather than concrete classes.
  • Dynamic dispatch selects digital or shipment behavior.
  • The abstract base class centralizes reservation, compensation, validation hooks, and event publication.
  • The entity exposes meaningful state transitions rather than generic setters.
  • Collections are defensively copied.
  • Constructors establish valid collaborators and state.
  • Subtype-specific dependencies remain encapsulated.
  • New fulfillment implementations can be added without changing the service algorithm.

55. OOP performance and runtime considerations

Allocation

Objects consume header, field, alignment, and reachable-object storage. Exact layouts are JVM implementation details. The JIT may eliminate some allocations through escape analysis, but code should not depend on that optimization.

Dynamic dispatch

Virtual calls can often be inlined when runtime type profiles are stable. Highly polymorphic call sites can be harder to optimize, but design clarity should precede speculative devirtualization.

Indirection and locality

Deep object graphs, linked nodes, and wrapper layers can reduce cache locality. Data-oriented layouts may outperform rich object graphs in numerical or high-volume hot paths.

Measure rather than guess

Use the OpenJDK Java Microbenchmark Harness for isolated JVM microbenchmarks, and use realistic load tests for architecture decisions.[16]

@Benchmark
public Money virtualDispatch(
        BenchmarkState state) {

    return state.method.quote(
            state.order,
            state.context)
        .cost();
}

Compatibility

Changing inheritance, member accessibility, method signatures, abstract/default methods, or field shapes can affect source and binary compatibility. The Java Language Specification defines binary compatibility separately from source compatibility.[17]

57. Production OOP checklist

Classes and construction

  • Each class has one cohesive responsibility.
  • Constructors establish a valid state or fail.
  • Required dependencies are non-null and explicit.
  • Mutable inputs are defensively copied when ownership is retained.
  • Factories are used where construction intent or implementation hiding matters.
  • Constructors do not invoke overridable methods.

Encapsulation

  • Fields are private unless a stronger reason exists.
  • Visibility is minimized.
  • Getters do not expose mutable internals.
  • Setters are replaced by meaningful state transitions where possible.
  • Invariants are enforced inside the owning object.
  • Static mutable state is avoided or rigorously synchronized.

Inheritance and polymorphism

  • Inheritance represents a true substitutable “is-a” relationship.
  • Composition is preferred for assembling behavior.
  • Overridden methods preserve superclass contracts.
  • Static methods and fields are not mistaken for dynamically dispatched members.
  • Downcasts are rare and guarded.
  • Interfaces are small, cohesive capabilities.
  • Default-method conflicts are resolved explicitly.
  • Abstract classes centralize shared state or invariant algorithms.

Object contracts

  • Equality semantics are documented and stable.
  • equals satisfies equivalence laws.
  • hashCode is consistent with equality.
  • toString is informative but excludes secrets.
  • Copy behavior is explicit: shallow, deep, immutable update, or prohibited.
  • New code does not rely on clone without a compelling compatibility need.
  • New code never overrides finalize.

Testing and evolution

  • Every implementation passes shared supertype contract tests.
  • Invalid construction and state transitions are tested.
  • Aliasing and defensive-copy behavior are tested.
  • Equality works across collection and inheritance scenarios.
  • Performance is measured under realistic polymorphism and allocation patterns.
  • Source and binary compatibility are evaluated before evolving public hierarchies.
Final principle: Java OOP is the disciplined design of objects that own valid state, expose stable behavior, and remain substitutable through abstractions. Inheritance is one tool; encapsulation, composition, explicit contracts, and deterministic lifecycle ownership are more fundamental.
