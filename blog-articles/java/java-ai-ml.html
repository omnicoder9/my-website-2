1The question under the language war

The usual way to ask about Java and artificial intelligence is as a contest with Python, and the usual answer is that Python won the notebook and Java kept the server. That answer is true and not very useful. It says nothing about the choice a Java team actually makes when it adds a model to a system, which is not a choice of language at all. The call site is Java whichever way you go. The choice is where the arithmetic will run, and what has to cross a boundary to get there.

Every library in this article answers that question differently. Weka runs its learners as ordinary bytecode on the heap. The Vector API keeps the arithmetic in Java but hands it to the CPU's vector lanes. The Foreign Function and Memory API reaches native code through memory the JVM still polices. ONNX Runtime, TensorFlow Java and Deeplearning4j cross through the Java Native Interface into C++ engines the JVM cannot see into. A local model server moves the work into another process, and Spring AI and LangChain4j move it to a provider on the other side of the network. Each move buys speed, reach or model quality, and each one pays for it in the same currency: guarantees the JVM used to give you for free and now does not.

So the question the article asks of every library is the one in its title. What does the JVM still vouch for once the arithmetic has moved? Five guarantees are tracked throughout: that static types describe the data, that no access can corrupt memory, that lifetimes are managed, that the work is visible to Java's own profiling and tracing, and that the same inputs give the same bits. The first four are what most Java developers think of as the platform's promise. The fifth has been part of the language since JDK 17 restored strict floating-point semantics everywhere 1, and it turns out to be the first thing machine learning gives away.

The answer is not the one the language-war framing predicts. The weakest place to put the arithmetic, measured by these five guarantees, is not the remote API. It is the native engine linked into your own process, which scores 4.00 of 10 against 5.86 for a model across the network and 6.00 for one in a separate local process. Memory safety is lost at exactly one rung and returns as soon as the model runs in another process. Types are lost only when data leave the JVM, and come back only per call, when a validator checks them. Bit-determinism is kept by 3 of 27 libraries, all of them plain bytecode, and a lab experiment shows that even those pay for it in accuracy.

The rest of the article is built on that ladder. Section 2 is a short history of how Java got onto each rung. Section 3 defines the rungs and the five guarantees. Sections 4 to 9 take the rungs in order, with 27 numbered plates, one per library or mechanism, each recording the same four facts and a small gauge. Section 10 collects the plates into a census and a ledger, Section 11 turns the census into advice, and Section 12 says what the lab behind the numbers can and cannot show. Three of the code listings are compiled and run as part of this build; the framework listings are checked against their published documentation and marked as such.

2Thirty years, six rungs

Java was not designed for numerical work, and for most of its life it did not pretend to be. Sun shipped Java 1.0 on 23 January 1996 as a language for networked applications, with an applet viewer, a compiler, a prototype debugger and class libraries for graphics, audio, animation and networking 2. The first serious machine learning on the platform came from a university that chose Java for portability rather than speed: the Waikato Environment for Knowledge Analysis, rewritten from scratch in Java, placed on SourceForge in April 2000, and downloaded more than 1.4 million times by 2009 3. Weka's maintainers later described what a decade of running a Java research project had involved, from licensing to the maintenance cost of a large plugin ecosystem 4.

The 2000s and early 2010s filled the bottom rung. Statistical NLP arrived in Stanford CoreNLP and Apache OpenNLP, whose annotator pipelines became the text-processing layer of enterprise search 5. Distributed learning arrived with Hadoop and then Spark, whose MLlib gave the JVM a way to train over data too large for one machine 6. All of this ran as bytecode, and all of it could be debugged, profiled and serialised like any other Java.

Deep learning broke that pattern. The computation that mattered now happened in dense linear algebra on GPUs, and the fastest implementations were C++ and CUDA. Java's answer was to bind to them. Deeplearning4j built its own C++ core, libnd4j, and reached it through JavaCPP 7. TensorFlow and ONNX Runtime published official or community Java bindings 8,9. Amazon's Deep Java Library put one Java API over several native engines so that code would not have to choose 10. Oracle Labs' Tribuo, open-sourced in 2020, went the other way for classical models, staying in Java and adding provenance as a first-class output 11. For deep learning, though, the centre of gravity had moved to D3: in-process native code, reached through JNI.

The platform then spent five years building the rungs in between. The Vector API began incubating in JDK 16 so that Java code could ask for SIMD instructions directly 12. The Foreign Function and Memory API began as a foreign-memory incubator in JDK 14 13 and became final in JDK 22 14, giving Java a supported way to call native code without writing JNI glue. Lucene adopted the Vector API for its nearest-neighbour search in 2023, with a scalar fallback for runtimes that lack the incubator module 15. Pure-Java LLM inference followed, in Jlama and llama3.java 16,17. Project Babylon was proposed in September 2023 to let Java code be translated into foreign programming models, GPUs and machine learning graphs among them 18.

The top of the ladder arrived last and fastest. Spring AI was launched at SpringOne in 2023 and LangChain4j appeared the same year; both reached 1.0 in May 2025 19,20. By September 2026 Spring AI was at 2.0 21, LangChain4j at 1.20 22, Rod Johnson's Embabel at 1.0 23 and Google's Agent Development Kit for Java past 1.10 24. An industry survey by a Java vendor reported that 62% of organisations were using Java to code AI functionality in 2026, up from 50% a year earlier 25; its list of the libraries respondents used mixes Java-ML, DJL and Spring AI with OpenCL and PyTorch 26, which is itself a fair picture of how the rungs are used together in practice.

The newest platform work still points at the middle of the ladder. JDK 27, released on 15 September 2026, carries the Vector API's twelfth incubation 27, and the API will not move to preview until Valhalla's value classes are available as a preview feature 28. In March 2026 the JEP was still at Submitted status when Oracle presented value classes to the JCP Executive Committee 29. The dependency started to resolve five months later, in August 2026, when JEP 401 was integrated into the JDK 28 mainline as a preview 30,31, in a change reported at about 197,000 lines across 1,816 files 32. 3The ladder and the five guarantees

The rungs are defined by where the arithmetic runs relative to the JVM, and so by what has to cross to reach it. At D0 the work is ordinary bytecode and nothing crosses. At D1 it is still Java, but compiled into vector instructions whose lanes the program addresses explicitly. At D2 it runs in native code reached through the Foreign Function and Memory API, with data in off-heap segments the JVM still bounds-checks. At D3 it runs in a native engine linked into the process through JNI, where the JVM's knowledge stops at the handle. At D4 it runs in another process on the same machine, and data cross as bytes on a pipe or a local socket. At D5 it runs at a provider across the network, and data cross as text inside HTTP.

The five guarantees are scored 2 when the JVM keeps them, 1 when they survive partly or only through a library's discipline, and 0 when they are gone.

Types (TY). Does the compiler describe the data at the boundary? A float vector of a known species is typed. A tensor whose shape is checked when the session runs is partly typed. A string of JSON that will become a record if it parses is not typed at all until it does.

Bounds (BD). Can a mistake corrupt memory? Bytecode cannot, and neither can a second process. JNI code can: a bad pointer in a native engine brings the whole JVM down, which is why the platform now warns about JNI use unless the application opts in 33 and is deprecating the raw memory access in sun.misc.Unsafe 34.

Lifetime (LT). Who frees what? The collector, a scoped arena that throws on use after close, or you, remembering to call close() on every native tensor.

Observability (OB). Can Java's own tools see the work? JDK Flight Recorder and ordinary stack traces see bytecode and vector code. They see only a call into native code or a client-side span around a remote request.

Determinism (DT). Do the same inputs give the same bits, on every run and every machine? Strict floating point makes scalar Java deterministic by specification 1. Vector reductions, native BLAS, GPU kernels and sampled model outputs do not promise it.

Each plate records four fields in a fixed order: where the arithmetic runs, what crosses, what the JVM still vouches for, and what you now have to check yourself. The gauge beside each plate is a boundary map. Six cells run left to right from the heap to the network; the plate's rung is filled in its colour, and a line runs from the call site at the left edge to it. Below, five pips show the guarantees: solid for kept, half for partial, open for gone, with the total out of ten at the right. Figure 2 shows the whole ladder with the mean score at each rung.

The coding is a judgement about each library's default path, recorded in the lab source so that every statistic in Section 10 is computed from one table. Where a library straddles rungs (Smile's native BLAS routines, Tribuo's optional ONNX interface) the plate records the main path and the note records the exception.

4D0: in the bytecode

The bottom rung is where Java machine learning started, and it still holds the strongest guarantees on the ladder: a mean of 9.20 out of 10. Everything is on the heap, everything is typed, and a debugger can step into the learner itself. The cost is speed on dense linear algebra, which is why the rung is now occupied by classical learners, NLP pipelines and distributed training rather than neural networks.

The University of Waikato's workbench of classic learners, rewritten from scratch in Java and distributed through SourceForge from April 2000.

Nothing. Datasets are Instances objects and stay on the heap.

Its lasting design point is that a model, its data and its evaluation are all ordinary Java objects you can serialise, inspect and step through.

Distributed machine learning on Spark, written in Scala and callable from Java, running across a cluster of executor JVMs.

Bytecode, on many JVMs at once.

Serialised partitions and aggregates between executors.

Determinism at D0 is not quite free, and experiment E1 in Section 5 measures the price. The scalar loop that strict floating point makes reproducible adds its terms one at a time in a single accumulator, and that is the least accurate order available.

5D1: on the vector lanes

The Vector API lets Java code say what the JIT compiler would otherwise have to guess: that a loop should run eight or sixteen floats at a time. Listing 1 is the kernel used in the lab. It is ordinary, type-checked Java, and it keeps four of the five guarantees. The fifth is traded away in one line.

The trade is in reduceLanes(ADD). The specification says the order of the scalar additions that combine the lanes is intentionally not defined, so that the JVM can use whatever instruction sequence is fastest, and that the result may therefore vary for the same inputs 37. Fused multiply-add is a second source of difference: it rounds once where sum += a[i]*b[i] rounds twice.

B01

Vector API

The incubating API for explicit SIMD. First incubated in JDK 16; JDK 27, released on 15 September 2026, carries the twelfth incubation.

Arithmetic runs
On the CPU's vector lanes, through intrinsics the JIT compiles into vector instructions.
Crosses as
Nothing leaves Java. Arrays are loaded into species-typed vectors.
JVM still vouches for
Types (a vector's species is part of its type), bounds (loads are checked), collected lifetime and profiler visibility. Not bit-determinism.
You now check
With tolerances, not equality. The specification deliberately leaves the order of floating-point cross-lane additions and multiplications undefined.

The API has been incubating since JDK 16 12 and will keep incubating until Valhalla's value classes are available as a preview, at which point it moves to preview itself 28,38. The operator documentation states the determinism trade in so many words: the order of a float ADD or MUL reduction is intentionally not defined, so the result may vary for the same inputs 37. B04

llama3.java

Llama 3 inference in a single Java source file with no dependencies: a GGUF parser, a tokenizer and the model, with matrix-vector products on the Vector API.

Arithmetic runs
On vector lanes.
Crosses as
Nothing.
JVM still vouches for
Types, bounds, lifetime and visibility.
You now check
Quantisation format and sampling settings, as for any local model.

The project supports F16, BF16 and F32 weights and the Q4_0, Q4_1, Q4_K, Q5_K, Q6_K and Q8_0 quantisations 17, and it became the starting point for GPULlama3.java 42. Its value is pedagogical as much as practical: an entire inference path you can read in one sitting and step through with an ordinary Java debugger.

Experiment E1 asks how much this matters. It computes 10,000 random 768-element float dot products seven legal ways, varying the number of lanes, the use of fused multiply-add and the order of the final lane sum, and compares each with a reference that sums the exact products in double-double and rounds once. All seven variants agreed bit-for-bit on 0.03% of pairs. The plain scalar loop and a 16-lane fused tree differed on 94.70%.

The more useful result is the direction of the error. The scalar loop, the only variant Java makes deterministic, was the least accurate: its mean distance from the correctly rounded answer was 19.17 units in the last place, and it hit the correctly rounded value on 6.24% of pairs. The 32-lane tree was off by 6.78 units on average and correct on 22.62%. More accumulators mean shorter chains of additions and less accumulated rounding. Determinism and accuracy are different properties, and D0 buys the first at the cost of the second.

On this machine, after warm-up, the real 8-lane kernel in Listing 1 matched an 8-lane fused multiply-add with a sequential lane sum in 3,000 of 3,000 pairs and a pairwise lane tree in 1,232. The JIT chose the sequential order, which the specification permits but does not require; another CPU or another JDK could choose differently. It matched the plain scalar loop in only 162 pairs.

For retrieval, the differences are usually too small to reorder anything. Over 20,000 independent 384-dimension documents and 200 queries, switching from the scalar loop to the 16-lane tree changed neither the top-10 set nor its order for any query. In a corpus built like a real chunked index, with near-duplicate chunks, it changed the order of the top 10 for 5 queries and the set for 0. The practical rule is the one Lucene follows: test rankings with tolerance for near-ties, and never assert exact float equality across code paths.

Pure-Java inference engines such as Jlama and llama3.java rely on a second trade at this rung, quantisation. Experiment E2 applies the symmetric block-32 formats used in GGUF files, with an fp16 scale per block of 32 weights, to a 1024 by 1024 matrix with realistic outliers.

At 8.5 bits per weight (Q8_0) one matrix-vector product carried a relative error of 0.64%; at 4.5 bits (Q4_0) it was 11.14%, seventeen times larger for about half the memory again. Applied to document embeddings instead of weights, Q8_0 kept 99.3% of the float32 top-10 results and Q4_0 kept 86.0%. None of these trades involves the JVM's guarantees; they are the same whichever rung the model runs on. They matter here because D1 is where a Java team is most likely to make them itself.

6D2: across the arena

The Foreign Function and Memory API is the platform's replacement for JNI, and its design choice is to keep two guarantees that JNI gives away. Memory lives in segments that know their own size, allocated from arenas that know when they are closed. Listing 2 is the lab's experiment E6. It calls the C library's strlen through a downcall handle, fills a 64-byte off-heap buffer, reads one element past its end, and reads again after the arena is closed.

On JDK 21 with preview features enabled, the downcall returned 5, the read past the end threw IndexOutOfBoundsException, and the read after close threw IllegalStateException. Under JNI, either mistake would have been undefined behaviour in the process. The listing uses the JDK 21 preview names (allocateUtf8String, allocateArray); in the final API of JDK 22 and later they are allocateFrom and allocate, and nothing else changes.

C01

FFM API

The Foreign Function and Memory API, final in JDK 22 after incubating from JDK 14, which replaces JNI for calling native code and managing off-heap memory.

Arithmetic runs
Wherever the native function you link to runs; data sit in arena-managed memory outside the heap.
Crosses as
Memory segments described by layouts, passed through downcall handles.
JVM still vouches for
Bounds and lifetime of every segment: an out-of-range read throws, and a read after the arena closes throws. Not the behaviour of the native function you call.
You now check
That each function descriptor matches the real C signature. A mismatch is trusted, not detected.

The API took eight releases to finish, from the foreign-memory incubator of JDK 14 13 to the final form in JDK 22 14. Its restricted methods warn unless native access is enabled, and JDK 24 put JNI under the same regime, so the platform now treats both as integrity decisions the application owner makes explicitly 33. Experiment E6 and Listing 2 exercise both guarantees.

C02

Project Babylon's code reflection, which lets a library obtain a symbolic model of a Java method or lambda and translate it into a foreign programming model.

Arithmetic runs
In whatever runtime the code model is translated for; in the machine learning demonstrations, ONNX Runtime reached through FFM.
Crosses as
A code model, lowered into the foreign program (for example an ONNX graph).

The project was proposed in September 2023 to extend Java to SQL, differentiable programming, machine learning models and GPUs, with the GPU programming model explicitly kept out of the JDK itself 18. Its talks and articles since then include ONNX-based generative models written in Java and linked to ONNX Runtime through FFM 43.

C03

HAT

The Heterogeneous Accelerator Toolkit, built on Babylon, which translates Java kernels into CUDA or OpenCL and manages their data.

Arithmetic runs
On the GPU.
Crosses as
Buffers in FFM-managed memory; kernels as generated source.
JVM still vouches for
Types of kernel code; bounds and lifetime of buffers on the host side.
You now check
Kernel correctness on the device and the distance to vendor libraries.

A matrix-multiplication case study moves from about 7 GFLOP/s on CPUs to about 14 TFLOP/s on an NVIDIA A10 by tuning from the Java side 44. A later tensor-core API raised a naive kernel from 240 GFLOP/s to 7.3 TFLOP/s while cuBLAS reached 42 TFLOP/s on the same card, a gap the authors attribute to shared-memory tiling and double buffering they had not yet done 45. An independent comparison warns that an integrated GPU did not beat the parallel Vector API on the CPU for the same workload 46.

What FFM does not vouch for is the native function itself. A function descriptor is a promise the programmer makes about a C signature, and the linker takes it on trust. That is why D2 scores 5.67 rather than something close to D1: the rung keeps bounds and lifetime on the Java side and loses them on the other.

Babylon and HAT use this rung as a foundation rather than an end. Their pitch is that Java code, not a separately written kernel, becomes the thing that runs on the accelerator, with FFM carrying the data. The numbers so far are promising and honest about the gap: a Java-authored matrix multiplication reaching 14 TFLOP/s on an A10 44, and a tensor-core version at 7.3 TFLOP/s against cuBLAS's 42 on the same device 45.

7D3: through JNI into a native engine

This is where most Java deep learning has lived for a decade, and it is the lowest-scoring rung on the ladder at 4.00 of 10. The engines are excellent; the boundary is the problem. JNI was designed in the 1990s as an escape hatch whose native side is trusted completely 47, and a native engine loaded through it shares the JVM's address space. A buffer overrun in a kernel, a mismatched library version or a double free is a crash of the whole process, with no Java stack trace to explain it.

8D4: in another process

Moving the model into a separate process looks like a step further away. By the JVM's guarantees it is a step back towards safety: D4 scores 6.00, two points above D3. A local model server can crash, leak or corrupt its own memory without touching the Java heap, because the operating system's process boundary does what JNI never could. The price is the other guarantee the plates track most closely, types. What crosses now is bytes, and whatever structure they have is a convention the two sides share.

Three lab experiments look at what crosses this boundary and how.

Numbers as text. Embeddings travel to and from vector stores and model APIs as JSON arrays. Experiment E3 serialised 1,000 unit-length 384-dimension vectors four ways. Binary float32 is 1,536 bytes and base64 2,048. Java's shortest round-trip form, which is what Float.toString produces, averaged 4,687.6 bytes, 3.05 times the binary size, and round-tripped all 384,000 values exactly. Fixed six-decimal formatting was smaller at 3,649.7 bytes and changed no top-10 results over 200 queries. Four decimals, a common shortcut, saved more (2,881.7 bytes) and changed the top-10 set for 2 queries and the order for 9. At D5 even precision is a formatting decision someone made.

Validation and retry. Structured output recovers a type by parsing and validating the reply, and Spring AI 2.0's validation advisor retries when that fails 21. Experiment E4 simulates 200,000 requests under two failure models with the same average. If every reply fails the schema independently with probability 0.05, two retries cut failures to 0.0125%, matching the exact value of 0.0125%, at an average of 1.052 calls per request. If instead 3% of inputs are hard, failing nine times in ten, retries flatten out: after four, failures are still 1.73% in simulation against an exact 1.77%, and 1.77 points of that come from the hard 3% alone. A retry loop helps with noise and does little for a systematic weakness, and it cannot see a reply that is valid and wrong: in the same simulation, a 4% rate of schema-valid wrong answers came through at 3.99% for every retry budget.

Waiting. A model call holds its thread for seconds. With a fixed pool, the pool becomes the capacity limit long before the provider does. Experiment E5 models requests with a median service time of 1.5 seconds (mean 1.80 s) arriving at rising rates. A pool of 200 platform threads saturates at 111.4 requests per second: at 120 requests per second its p99 latency is 28.0 s, and at 200 it is 158.6 s. With a virtual thread per call and a semaphore of 512 standing in for the provider's concurrency limit, p99 stays at 6.01 s through 250 requests per second. Virtual threads, final since JDK 21 59 and no longer pinned by synchronized blocks since JDK 24 60, move the limit to where it belongs. Listing 7 is the pattern, compiled and run for this build.

Finally, a Java service can itself be the tool. Listing 8 exposes a Spring method as an MCP tool with one annotation, the programming model Spring AI 2.0 moved into its core 21. At that point the ladder turns around: the JVM is the far side of someone else's D5, and every guarantee the method's types give is one that a remote model's arguments must pass through before they reach it.

11Choosing where the arithmetic runs

The census suggests a way of choosing that starts from guarantees rather than from libraries. Ask first which guarantee the system cannot do without, then find the highest rung that keeps it, then check the ones the rung gives up.

If the requirement is reproducibility and audit, as in credit scoring or anything a regulator may ask you to rerun, the bottom rung is the only one that keeps bit-determinism by specification. Tribuo adds provenance on top. E1 is a reminder that deterministic is not the same as accurate; if you also need the most accurate sum, compute it in double or with compensated summation, and do it on purpose.

If the requirement is throughput on the CPU without native dependencies, D1 is the rung. The Vector API is still an incubator module after twelve releases 28, which means command-line flags and API churn, but Lucene has shipped on it since 2023 with a scalar fallback 15, and that pattern is the right one to copy. Write equality tests with tolerances from the start.

If the requirement is a model only a native engine can run well, prefer a library that manages lifetimes for you (DJL's managers, LangChain4j's embedding wrappers) over one that hands you raw native objects. Treat engine upgrades as you would a JVM upgrade, because a mismatch fails the same way: as a crash. Consider whether the same model could run in a separate process instead; D4 costs a serialisation step and gives back memory safety.

If the requirement is the best available model, D5 is unavoidable, and the work moves from computing to checking. Put a typed target on every reply, validate it, and budget retries for noise rather than for systematic failure (E4). Treat tool calls as authorisation decisions, because the JVM vouches only that a method can run. Run the waiting on virtual threads with an explicit cap that matches the provider's limit (E5). Pin model identifiers, and store the embedding model's name with every vector you index.

Two cautions apply at every rung. First, the incubating and preview features this ladder depends on (the Vector API, structured concurrency, value classes) are still moving 27,31, and code that uses them should isolate them behind a small interface. Second, the frameworks at the top move faster still. A mistaken release that cannot be withdrawn 22, two main frameworks targeting different MCP revisions within one summer 21,22, and integrations removed between milestones 56 all happened in 2026. Pin versions, read release notes, and let a build fail when a dependency moves.

        for (; i < S256.loopBound(a.length); i += S256.length()) {
            FloatVector va = FloatVector.fromArray(S256, a, i);
            FloatVector vb = FloatVector.fromArray(S256, b, i);
            acc = va.fma(vb, acc);                 // one rounding per lane per step
        }
        float sum = acc.reduceLanes(VectorOperators.ADD); // order of the 8 adds: unspecified
        for (; i < a.length; i++) sum += a[i] * b[i];      // scalar tail
        return sum;
    }

    /** The plain scalar loop: two roundings per element, strictly left to right (JEP 306). */
    static float dotScalar(float[] a, float[] b) {
        float sum = 0f;
        for (int i = 0; i < a.length; i++) sum += a[i] * b[i];
        return sum;
    }

    /** k partial accumulators; fma or mul+add per lane; final lane sum sequential or pairwise tree. */
    static float dotLanes(float[] a, float[] b, int k, boolean fma, boolean tree) {
        float[] acc = new float[k];
        for (int i = 0; i < a.length; i++) {
            int j = i % k;
            acc[j] = fma ? Math.fma(a[i], b[i], acc[j]) : acc[j] + a[i] * b[i];
        }
        if (!tree) { float s = acc[0]; for (int j = 1; j < k; j++) s += acc[j]; return s; }
        int m = k;
        while (m > 1) { for (int j = 0; j < m / 2; j++) acc[j] = acc[j] + acc[j + m / 2]; m /= 2; }
        return acc[0];
    }

    /** Reference: products are exact in double; sum them in double-double; round once to float. */
    static float dotExact(float[] a, float[] b) {
        double hi = 0, lo = 0;
        for (int i = 0; i < a.length; i++) {
            double x = (double) a[i] * (double) b[i];
            double s = hi + x, bb = s - hi, err = (hi - (s - bb)) + (x - bb);
            hi = s; lo += err;
        }
        return (float) (hi + lo);
    }

    static float[] gauss(SplittableRandom r, int n) {
        float[] v = new float[n];
        for (int i = 0; i < n; i++) v[i] = (float) r.nextGaussian();
        return v;
    }
    static void normalise(float[] v) {
        double s = 0; for (float x : v) s += (double) x * x;
        float inv = (float) (1.0 / Math.sqrt(s));
        for (int i = 0; i < v.length; i++) v[i] *= inv;
    }
    static int ulpDist(float x, float y) {
        int a = Float.floatToRawIntBits(x), b = Float.floatToRawIntBits(y);
        if (a < 0) a = 0x80000000 - a; if (b < 0) b = 0x80000000 - b;
        return Math.abs(a - b);
    }

    static int[] rankFlips(float[][] docs, float[][] qs, int K) {

            if (!Arrays.equals(t1, t2)) orderChanged++;

    static int[] topK(float[][] docs, float[] q, int K, boolean lanes) {
        int[] idx = new int[K]; float[] sc = new float[K]; Arrays.fill(sc, Float.NEGATIVE_INFINITY); Arrays.fill(idx, -1);
        for (int i = 0; i < docs.length; i++) {

                sc[j] = s; idx[j] = i;
            }
        }
        return idx;
    }

        for (int s = 0; s < v.length; s += 32) {

            for (int i = s; i < e; i++) { int q = Math.round(v[i] / d); q = Math.max(-qmax - 1, Math.min(qmax, q)); o[i] = q * d; }
        }
        return o;
    }
