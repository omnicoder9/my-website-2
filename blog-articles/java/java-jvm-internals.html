1. Specification versus HotSpot implementation

“The JVM” can mean either the abstract Java Virtual Machine defined by the specification or a concrete implementation such as HotSpot. The distinction is essential: the specification defines observable execution structures and class-file semantics, while HotSpot chooses object headers, Metaspace allocation, compilers, barriers, code-cache organization, and collectors.

JVMS Required abstraction

Class files, instructions, run-time data areas, frames, loading, linking, initialization, exceptions, and verification rules.

HotSpot Concrete machinery

Template interpreter, C1/C2 compilers, tiered policy, object layout, compressed references, Metaspace, code heaps, safepoints, GC barriers, and serviceability.

The Java Virtual Machine Specification explicitly leaves memory layouts, garbage-collection algorithms, and internal optimizations such as machine-code translation to implementors. A conforming JVM need not use HotSpot's organization even though it must preserve JVMS semantics.[1][2]

Rule for reading JVM documentation: statements about the heap, stacks, frames, loading, and bytecode may be specification-level. Statements about generations, regions, Metaspace, TLABs, colored pointers, compact headers, C1/C2, or code heaps are HotSpot-specific.

2. JVM architecture at a glance

Source language │ ▼ compiler / generator │ ▼ .class files ──► class loader subsystem │ ├─ load ├─ verify ├─ prepare ├─ resolve └─ initialize │ ▼ run-time data areas ┌──────────────┬───────────────┐ │ shared │ per-thread │ │ heap │ pc register │ │ method area │ JVM stack │ │ runtime CPs │ native stack │ └──────────────┴───────────────┘ │ ▼ execution engine interpreter ─► C1/C2 JIT ─► native code │ ▼ GC, native runtime, OS, CPU

The JVMS defines a heap and method area shared by all JVM threads and per-thread program-counter registers, JVM stacks, and optionally native-method stacks. Each method invocation creates a frame containing local variables, an operand stack, and a reference to the current class's run-time constant pool.[2]

HotSpot augments these abstractions with native subsystems including Metaspace, compressed-class space, code heaps, compiler arenas, thread stacks, GC data structures, synchronization machinery, JNI handles, JFR buffers, and internal C-heap allocations.[3][4]

3. From launcher to termination

  1. The native launcher starts the VM, parses options, selects ergonomic defaults, initializes core runtime subsystems, and creates the initial thread.
  2. The VM creates and initializes foundational platform classes and the boot module layer.
  3. The initial application class is loaded, linked, initialized, and its selected main method is invoked.
  4. Application threads execute interpreted, compiled, or native code while class loading, compilation, GC, and service threads run concurrently.
  5. The VM terminates after the last non-daemon thread exits, System.exit is invoked, or an external/native fatal event ends the process.[5]

4. The class-file format

JVMS The class-file format is a hardware- and operating-system-independent binary representation of a class or interface. A class file begins with the magic value 0xCAFEBABE, version numbers, and a constant pool, followed by access flags, hierarchy information, fields, methods, and attributes.[7]

ClassFile {
    u4             magic;
    u2             minor_version;
    u2             major_version;
    u2             constant_pool_count;
    cp_info        constant_pool[constant_pool_count-1];
    u2             access_flags;
    u2             this_class;
    u2             super_class;
    u2             interfaces_count;
    u2             interfaces[interfaces_count];
    u2             fields_count;
    field_info     fields[fields_count];
    u2             methods_count;
    method_info    methods[methods_count];
    u2             attributes_count;
    attribute_info attributes[attributes_count];
}

Java 25 class-file version

Java SE 25 uses class-file major version 69. Preview class files use minor version 65535 and require preview-enabled execution for the matching release.[7]

Constant pool

The constant pool stores literals and symbolic references to classes, fields, methods, method handles, method types, dynamic constants, and invokedynamic call sites. Most cross-class references remain symbolic in the file and are resolved during linking or on first use.[7][5]

Attributes

  • Code: bytecode, operand-stack/local limits, exception table, and nested attributes.
  • StackMapTable: verification type states at control-flow points.
  • LineNumberTable and LocalVariableTable: debugging metadata.
  • BootstrapMethods: bootstrap methods for dynamic constants and invokedynamic.
  • RuntimeVisibleAnnotations: reflection-visible annotations.
  • Module: module descriptor information for module-info.class.

5. JVM bytecode

Bytecode JVM instructions are typed opcodes operating primarily on local-variable slots, an operand stack, the heap, and the run-time constant pool. Many opcodes encode their operand type in the mnemonic: iadd for int, ladd for long, fadd for float, and dadd for double.[8]

Source

public final class PriceMath {
    public static int discounted(
            int price,
            int percent) {

        int reduction =
            price * percent / 100;

        return price - reduction;
    }
}

7. Frames, locals, and the operand stack

Each JVM method invocation creates a frame. The frame stores an array of local variables, an operand stack, and information needed for dynamic linking and method completion. Frame sizes are determined from method class-file metadata and are implementation-independent abstractions even though physical stack representation is implementation-specific.[2]

frame for discounted(price, percent) ┌──────────────────────────────┐ │ local 0: price │ │ local 1: percent │ │ local 2: reduction │ ├──────────────────────────────┤ │ operand stack │ │ ... push/load/operate ... │ ├──────────────────────────────┤ │ current runtime constant pool│ │ return/exception state │ └──────────────────────────────┘

Category 1 and category 2 values

Most values occupy one local-variable or operand-stack unit; long and double are category-2 values and occupy two consecutive local-variable slots. The specification does not require 64-bit alignment in the local-variable array.[2]

Exception handling

Bytecode exception handlers are represented by protected instruction ranges and handler targets in the Code attribute. Abrupt completion clears the current operand stack and transfers control to a matching handler with the thrown reference on the new operand stack; otherwise the frame is unwound.[2][7]

8. Loading, linking, and initialization

The JVM dynamically loads, links, and initializes classes and interfaces. Loading locates or generates a binary representation and creates the runtime class; linking verifies and prepares it and may resolve symbolic references; initialization executes its class initialization method <clinit> when required.[5]

binary name + defining loader │ ▼ loading │ ▼ linking ┌─────┼─────┐ verify prepare resolve │ ▼ initialization <clinit>

Class identity

At runtime, a class or interface is identified by both its binary name and defining class loader. Two loaders can define classes from identical bytes and names that are nevertheless distinct and not assignment-compatible.[5]

Class<?> first =
    loaderA.loadClass(
        "com.example.Plugin");

Class<?> second =
    loaderB.loadClass(
        "com.example.Plugin");

System.out.println(
    first.getName()
        .equals(second.getName())); // true

System.out.println(
    first == second);               // false

9. Built-in class loaders and delegation

The Java runtime has a bootstrap loader, a platform loader, and a system/application loader. The bootstrap loader is VM-internal and typically represented as null; the platform loader defines platform classes; the system loader normally defines application classes from the class path, module path, and tools.[10]

System.out.println(
    Object.class.getClassLoader());
// null: bootstrap-defined

System.out.println(
    java.sql.Driver.class
        .getClassLoader());
// commonly platform loader

System.out.println(
    Main.class.getClassLoader());
// commonly application/system loader

System.out.println(
    ClassLoader
        .getPlatformClassLoader());

System.out.println(
    ClassLoader
        .getSystemClassLoader());

Parent-first algorithm

The default loadClass(name, resolve) checks whether the class is already loaded, delegates to the parent or bootstrap loader, then invokes findClass. Subclasses are encouraged to override findClass, not the delegation algorithm itself.[10]

Modules and layers

A module layer associates resolved modules with class loaders. The boot layer is created at JVM startup and contains java.base; additional layers may map all modules to one loader or assign different loaders.[11]

10. A bounded custom class loader

public final class DirectoryClassLoader
        extends ClassLoader
        implements AutoCloseable {

    static {
        registerAsParallelCapable();
    }

    private final Path root;

    public DirectoryClassLoader(
            String name,
            Path root,
            ClassLoader parent) {

        super(name, parent);

        this.root =
            root.toAbsolutePath()
                .normalize();
    }

    @Override
    protected Class<?> findClass(
            String binaryName)
            throws ClassNotFoundException {

        String relative =
            binaryName.replace(
                '.',
                File.separatorChar)
                + ".class";

        Path classFile =
            root.resolve(relative)
                .normalize();

        if (!classFile.startsWith(root)) {
            throw new ClassNotFoundException(
                binaryName);
        }

        try {
            byte[] bytes =
                Files.readAllBytes(
                    classFile);

            if (bytes.length
                    > 10 * 1024 * 1024) {
                throw new ClassNotFoundException(
                    "Class file too large: "
                        + binaryName);
            }

            return defineClass(
                binaryName,
                bytes,
                0,
                bytes.length);
        } catch (IOException failure) {
            throw new ClassNotFoundException(
                binaryName,
                failure);
        }
    }

    @Override
    public void close() {
        // Release any loader-owned resources.
    }
}

defineClass converts valid class-file bytes into a Class associated with the defining loader. Parallel-capable subclasses register during class initialization so loading different names can use finer-grained locks and avoid deadlocks in non-hierarchical loading arrangements.[10]

Isolation guidance

  • Expose shared APIs from a parent loader so plugin objects cross the boundary through one common type identity.
  • Close JAR/file handles, executors, native registrations, and thread locals owned by an unloadable loader.
  • Never load untrusted bytecode as a sandbox: the Security Manager is no longer available as a containment mechanism.
  • Use process/container isolation for adversarial code.

11. Verification, preparation, and resolution

Verification

Verification checks that class-file structure and bytecode satisfy safety and consistency constraints: valid formats, type-correct instruction usage, legal control flow, correct stack states, and compatible symbolic references. Modern class files provide StackMapTable frames to support type checking at control-flow joins.[7][5]

Preparation

Preparation creates static fields and initializes them to JVM default values. Source-level constant variables may receive their ConstantValue values during preparation; ordinary static initializer expressions run later in <clinit>.[5]

Resolution

Resolution converts symbolic references in the run-time constant pool into direct runtime references after access, type, and compatibility checks. A JVM may resolve eagerly or lazily as long as specified errors occur at permitted points.[5]

java \
  -Xlog:class+load=info \
  -Xlog:class+resolve=debug \

12. Class initialization

A class or interface is initialized immediately before certain active uses, including first execution of a declared static method, first access or assignment of a non-constant static field, and reflective invocation that requires initialization. Class initialization is synchronized so only one thread executes <clinit> while others observe its result or failure.[5]

final class InitializationDemo {
    static final int COMPILE_TIME = 42;

    static final Integer RUNTIME =
        initialize();

    static {
        System.out.println(
            "class initializer");
    }

    private static int initialize() {
        System.out.println(
            "field initializer");
        return 7;
    }
}
// May not initialize InitializationDemo because
// COMPILE_TIME can be inlined as a constant value.
System.out.println(
    InitializationDemo.COMPILE_TIME);

// Requires active use and initialization.
System.out.println(
    InitializationDemo.RUNTIME);

Initialization failure

If <clinit> completes abruptly, initialization fails and the class is marked erroneous. The initiating use receives an initialization-related error; later uses receive NoClassDefFoundError for the failed class.[5]

13. Class unloading and loader leaks

A class can be unloaded only when its defining loader is reclaimable; loader reachability therefore retains all classes, metadata, static fields, constant pools, and related runtime structures for that loader. Exact unloading timing is implementation- and collector-dependent.[5][12]

Common loader-retention paths

  • Thread context class loaders on long-lived threads.
  • Thread-local values whose classes or values come from the plugin loader.
  • Static caches in parent-loaded libraries keyed by plugin classes.
  • JDBC drivers, MBeans, logging appenders, shutdown hooks, or service registries not deregistered.
  • Native/JNI global references.
  • Executors and timers created by the plugin.

Unloadable plugin lifecycle

try (URLClassLoader loader =
        new URLClassLoader(

            new URL[] {
                pluginJar.toUri().toURL()
            },
            Plugin.class.getClassLoader())) {

        loader.loadClass(
            descriptor.implementationClass());

    Plugin plugin =
        Plugin.class.cast(
            implementation
                .getConstructor()
                .newInstance());

    try {
        plugin.start(context);
    } finally {
        plugin.stop();
    }
}

14. Run-time data areas

The JVMS defines run-time data areas with different lifetimes and sharing rules. The heap and method area are created at VM startup and shared; each JVM thread has a program-counter register and JVM stack created with the thread; an implementation may provide native-method stacks.[2]

AreaSharingContents / roleSpecified failure
HeapSharedObjects and arraysOutOfMemoryError
Method areaSharedPer-class structures, method/field data, code, runtime constant poolsOutOfMemoryError
Run-time constant poolPer class/interface, method-area residentLiterals and symbolic/direct referencesOutOfMemoryError
JVM stackPer threadFrames for Java method invocationsStackOverflowError or OutOfMemoryError
PC registerPer threadCurrent JVM instruction address for non-native executionNot specified independently
Native method stackPer thread / implementation-definedNative execution supportStackOverflowError or OutOfMemoryError

These are logical areas, not a promise of one contiguous operating-system mapping per area. HotSpot may reserve address space separately from committing physical backing and may represent frames differently in interpreted and compiled execution.[2][4]

15. The Java heap

Heap The JVM heap is the shared run-time area from which storage for all class instances and arrays is allocated. It may be fixed or dynamically expanded and contracted; its memory need not be contiguous. The JVMS requires automatic storage management but does not mandate a collector.[2]

HotSpot sizing

java \
  -Xms2g \
  -Xmx2g \
  -XX:+AlwaysPreTouch \
  -Xlog:gc+heap=info \
  -jar application.jar
  • -Xms sets the initial heap size.
  • -Xmx sets the maximum heap size.
  • Equal values remove heap resizing as a runtime variable but commit/physical-backing behavior still depends on platform and options.
  • -XX:+AlwaysPreTouch asks HotSpot to touch heap pages at startup, shifting page-fault cost earlier.[6]

Reserved, committed, and used

maximum / reserved virtual range ┌───────────────────────────────────────┐ │ committed to JVM use │ │ ┌───────────────────────┐ │ │ │ live + garbage + free │ uncommitted │ │ └───────────────────────┘ │ └───────────────────────────────────────┘

“Reserved” is address space the VM has set aside; “committed” is memory available for VM use under OS rules; “used” is the portion currently occupied by allocated heap content. Resident set size can differ from all three due to paging, shared mappings, native allocations, and OS accounting.[4]

16. HotSpot object layout

HotSpot A HotSpot object typically contains an object header, instance fields, and alignment padding. Arrays additionally store a length. Field layout, header size, compressed references, and alignment are implementation details rather than Java-language or JVMS contracts.[3][13]

ordinary object (conceptual) ┌────────────────────────────┐ │ mark / locking / GC bits │ │ class metadata reference │ ├────────────────────────────┤ │ instance fields │ ├────────────────────────────┤ │ alignment padding │ └────────────────────────────┘ array adds: │ array length │

Compressed references

On many 64-bit HotSpot configurations, compressed ordinary object pointers and compressed class pointers encode heap and class-metadata references in narrower forms to reduce footprint and improve cache density. Their availability and addressing range depend on heap layout, alignment, platform, and VM options.[3]

Compact object headers in JDK 25

JDK 25 makes HotSpot compact object headers a product feature, but not the default layout. The feature combines class information with other header state to reduce object-header size on supported configurations and is enabled explicitly with -XX:+UseCompactObjectHeaders.[13]

java \
  -XX:+UseCompactObjectHeaders \
  -Xlog:gc+init=info \
  -jar application.jar
Do not encode business logic around measured object offsets or header bytes. Instrumentation libraries that inspect layout must treat it as VM/version/configuration-specific and test every supported runtime.

17. Java Virtual Machine stacks

Stack Each platform thread has a JVM stack that stores frames for active method invocations. JVM stacks can be fixed or dynamically extensible; the implementation controls representation. Excessive recursion can throw StackOverflowError, while inability to create or expand a stack can throw OutOfMemoryError.[2]

Stack overflow experiment

public final class StackDepth {
    private static long depth;

    public static void main(String[] args) {
        try {
            recurse();
        } catch (StackOverflowError failure) {
            System.out.println(
                "depth ≈ " + depth);
        }
    }

    private static void recurse() {
        depth++;

        long a = depth;
        long b = a + 1;
        long c = b + 1;

        if (c == Long.MIN_VALUE) {
            System.out.println(c);
        }

        recurse();
    }
}
java -Xss256k StackDepth
java -Xss1m   StackDepth
java -Xss4m   StackDepth

-Xss controls platform-thread stack size. Observed recursion depth also depends on method shape, compilation, inlining, architecture, and guard pages, so it is not a portable frame-size measurement.[6]

18. Virtual-thread stacks

Virtual threads are Java threads scheduled by the runtime rather than permanently tied to one operating-system thread. Their stacks are represented in heap-managed stack chunks and can grow and shrink as execution mounts and unmounts, rather than reserving one large native stack per virtual thread.[14]

try (ExecutorService executor =
        Executors
            .newVirtualThreadPerTaskExecutor()) {

    List<Future<Integer>> work =
        IntStream.range(0, 100_000)
            .mapToObj(index ->
                executor.submit(() -> {
                    Thread.sleep(
                        Duration.ofSeconds(1));

                    return index;
                }))
            .toList();
}

Virtual threads make thread-per-task code practical for blocking workloads but do not remove heap, scheduler, file-descriptor, connection, or downstream limits. Their frames still obey Java/JVM invocation semantics even though physical storage differs from platform-thread native stacks.[14]

19. Method area and run-time constant pools

The method area is the shared logical area containing per-class structures such as the run-time constant pool, field and method data, and code for methods and constructors. The JVMS does not prescribe its physical location or GC policy.[2]

From constant pool to resolved target

class-file constant pool Methodref #42 │ load class / link ▼ run-time constant pool entry │ resolve ▼ HotSpot metadata + entry point / dispatch data

Resolution can produce direct references to runtime classes, fields, methods, method handles, method types, dynamic constants, and call sites. The VM may cache linkage results while preserving specified linkage and initialization behavior.[5]

String constants

String literals and dynamically computed constants interact with heap objects and intern tables, even though symbolic entries originate in class-file/run-time constant pools. “Constant pool memory” is therefore not synonymous with one isolated byte array or with the Java string pool.[7][5]

20. HotSpot Metaspace

Metaspace HotSpot stores class metadata in native memory called Metaspace rather than in the Java heap. Metadata allocation is associated with class-loader data structures, allowing bulk reclamation when a loader and its classes unload.[15][12]

Elastic Metaspace

JEP 387 redesigned Metaspace in JDK 16 to return unused class-metadata memory to the operating system more promptly and reduce fragmentation/footprint through smaller allocation granules and a buddy-based allocator.[15]

Compressed class space

When compressed class pointers are enabled, HotSpot reserves a separate address range for class structures that must be addressable by compressed encodings. It is related to, but separately reported from, general Metaspace.[15][4]

Controls and diagnostics

java \
  -XX:MaxMetaspaceSize=512m \
  -XX:CompressedClassSpaceSize=256m \
  -Xlog:gc+metaspace=info \
  -jar application.jar

jcmd <pid> VM.metaspace basic scale=MB

MaxMetaspaceSize caps class-metadata allocation and can cause OutOfMemoryError: Metaspace. Leaving it uncapped does not make Metaspace free: it still competes for process/container native memory.[6][4]

21. The HotSpot code cache

Code cache HotSpot stores generated native code in the code cache: JIT-compiled methods, runtime stubs, adapters, interpreter-related code, and other VM-generated machine code. With tiered compilation and a sufficiently large cache, HotSpot uses segmented code heaps for non-method, profiled, and non-profiled code.[6][3]

segmented code cache ┌────────────────────────────┐ │ non-method code heap │ │ interpreter / adapters │ ├────────────────────────────┤ │ profiled method code heap │ │ C1/profiled compilations │ ├────────────────────────────┤ │ non-profiled method heap │ │ optimized C2 code │ └────────────────────────────┘

Inspect it

jcmd <pid> Compiler.codecache

jcmd <pid> Compiler.codelist

jstat -compiler <pid> 1s

java \
  -XX:+PrintCodeCache \
  -jar application.jar

If the code cache fills, compilation can be constrained or disabled until code sweeping reclaims space, degrading performance. Causes include very large applications, extensive dynamic code generation, aggressive compilation, and undersized cache configuration.[6][16]

22. Native memory beyond the Java heap

Native memory Process memory includes much more than the Java heap: Metaspace, compressed-class space, code cache, thread stacks, GC structures, compiler memory, symbols, arenas, direct buffers, mapped files, JNI/native libraries, JFR buffers, and the JVM executable/shared libraries.[17][4]

NMT reports HotSpot/JVM subsystem allocations at summary or detail level and must be enabled at startup. It does not account for every third-party native allocation or all JDK-library/native-library memory, so unexplained RSS growth may require OS tools, allocator profiling, or native debuggers.[17][4]

Direct buffers

ByteBuffer direct =
    ByteBuffer.allocateDirect(
        64 * 1024 * 1024);

direct.putInt(0, 42);

Direct byte buffers are allocated outside the normal garbage-collected heap and the JVM makes a best effort to perform native I/O directly on them. Their reclamation depends on object reachability and cleaner processing, not lexical scope; bounded pooling or explicit Foreign Memory API lifetimes are preferable for large deterministic native allocations.[18]

23. The execution engine

HotSpot executes methods through a combination of bytecode interpretation, runtime stubs, native methods, and dynamically compiled machine code. Method entry points can change as code is compiled, invalidated, deoptimized, or recompiled.[3][19]

method first invoked │ ▼ interpreted execution │ profile counters ▼ C1 compilation (fast) │ richer profile ▼ C2 compilation (optimized) │ assumption invalidated ▼ deoptimization → interpreter / recompile

Compiled code preserves Java semantics through metadata describing safepoints, oop locations, exception handling, deoptimization states, inlined frames, and stack walking. Native stack traces can therefore show one compiled machine frame that logically contains several inlined Java calls.[19]

24. The bytecode interpreter

The interpreter begins executing methods without waiting for machine-code compilation and collects execution profiles used by tiered compilers. It dispatches JVM opcodes, manages frames and operand stacks, performs runtime checks, and transfers control to resolved methods, stubs, native code, or compiled entries.[3]

Why retain an interpreter?

  • Low startup cost for cold methods.
  • Execution and profiling before compilation thresholds are reached.
  • A target for deoptimization when speculative compiled assumptions fail.
  • Support for debugging, instrumentation, and unusual control transfers.

Mixed mode

java -version
# Typical HotSpot output includes:
# "mixed mode, sharing"

“Mixed mode” indicates that the VM can execute both interpreted and compiled code. “Sharing” indicates class-data-sharing support is active for eligible archived metadata.

25. Tiered JIT compilation

JIT HotSpot tiered compilation combines the interpreter, the fast client compiler (C1), and the optimizing server compiler (C2). C1 can quickly generate instrumented code that gathers profiles; C2 uses profile information for more expensive optimizations. Tiered compilation is enabled by default in normal server operation.[6][3]

jcmd <pid> Compiler.codecache
jstat -compiler <pid> 1000

Compilation is method- and profile-specific

A method may exist in multiple compiled forms at different tiers. On-stack replacement can compile and enter a hot loop while the enclosing method is already running. Profiles include branch frequencies, receiver types, call counts, and other observations used to specialize code.

Warmup

Startup and steady-state performance differ because classes load, profiles accumulate, methods compile, code caches fill, and GC ergonomics adapt. Microbenchmarks must use a harness such as JMH that isolates warmup, forks, dead-code elimination, and constant folding rather than timing one loop with System.nanoTime().

26. JIT optimizations

HotSpot compilers can apply inlining, constant folding, common-subexpression elimination, loop transformations, range-check elimination, lock optimizations, escape analysis, scalar replacement, vectorization, and hardware intrinsics when legality and profitability conditions are met.[6]

Escape-analysis example

record Point(int x, int y) {
}

static int squaredDistance(
        int x,
        int y) {

    Point point =
        new Point(x, y);

    return point.x() * point.x()
        + point.y() * point.y();
}

If the allocation does not escape the compiled scope and all uses are visible, HotSpot may replace the object with scalar values and eliminate the allocation and associated field loads. This is a compiler optimization, not a language promise that the object is “allocated on the stack.”[6]

Inlining unlocks optimization

static int calculate(Order order) {
    return order.total()
        .subtract(order.discount())
        .intValueExact();
}

Inlining exposes callee operations to the caller's optimization graph, enabling constant propagation, allocation elimination, and branch simplification. Excessive polymorphism, large methods, unstable profiles, or code-cache pressure can prevent or reverse inlining decisions.

Intrinsics

HotSpot can replace selected library methods with architecture-specific machine instructions or highly optimized stubs, including cryptographic, array, string, checksum, and mathematical operations when supported.[6]

27. Speculation, uncommon traps, and deoptimization

Profile-guided compilation can speculate that observed receiver types, branch behavior, or class hierarchy conditions will continue. HotSpot records enough state to reconstruct interpreter frames if an assumption becomes invalid, then deoptimizes and may recompile with broader assumptions.[3][19]

Monomorphic to polymorphic

interface PriceRule {
    int apply(int value);
}

static int compute(
        PriceRule rule,
        int value) {

    return rule.apply(value);
}

If one implementation dominates during profiling, compiled code may inline that target behind a type guard. Loading or observing other implementations can make the call site polymorphic, trigger uncommon traps, and cause less specialized recompilation.

Consequences

  • Latency spikes during deoptimization and recompilation.
  • Temporary return to interpreted/lower-tier execution.
  • Different inlining and allocation behavior after workload phase changes.
  • Benchmark instability when warmup input is not representative.

29. Garbage-collection foundations

Garbage collection An object becomes reclaimable when it is no longer reachable through the collector's root set and object graph under the JVM's reference-processing rules. Collectors discover live objects, reclaim dead storage, and often move or compact live objects while preserving all observable Java references.[20]

Typical GC roots in HotSpot

  • References in active interpreted and compiled Java frames.
  • Static fields and other class-loader-associated roots.
  • JNI local/global handles and VM internal handles.
  • References embedded in compiled code and runtime data structures.
  • Active monitors, system dictionaries, interned strings, JVMTI/JFR/serviceability roots, and selected native structures.

Exact root organization is implementation-specific and collector/serviceability dependent. Compiled code includes metadata that identifies reference locations at safe traversal points.[21][19]

Core collector techniques

TechniqueMechanismTrade-off
MarkTrace reachable objects from rootsWork proportional to roots/live graph
SweepReturn unmarked blocks to free structuresCan fragment without compaction
Copy / evacuateMove live objects to new spaceCompacts but needs destination headroom and reference updates
CompactRelocate live objects to eliminate holesMovement and updating can be expensive
Concurrent mark/relocatePerform major work while mutators runBarriers, CPU, memory, and coordination overhead

Stop-the-world does not mean single-threaded

A stop-the-world phase suspends application mutator execution, but the collector can use many GC worker threads during that pause. Conversely, a concurrent phase runs alongside mutators and competes for CPU and memory bandwidth.

30. Generational collection

Generational collectors exploit the empirical tendency for many newly allocated objects to die quickly. They concentrate frequent collections on a young generation and move surviving objects toward an old generation, reducing the amount of memory examined in common collections.[20]

young generation ┌──────────┬──────────┬──────────┐ │ Eden │ Survivor │ Survivor │ └──────────┴──────────┴──────────┘ allocation → copy survivors │ age / pressure ▼ old generation ┌────────────────────────────────┐ │ longer-lived objects │ └────────────────────────────────┘

HotSpot's exact young/old layout differs by collector. Serial and Parallel use more traditional contiguous generation spaces; G1 and low-latency collectors use region-based or otherwise specialized layouts. Generational ZGC is the only ZGC mode in JDK 25, and JDK 25 makes Generational Shenandoah a product mode where included by the JDK distribution.[22][23][24]

Remembered sets and barriers

A young collection must find references from older memory into young memory without scanning the entire old generation. Collectors use write barriers, card tables, remembered sets, remembered edges, or related structures to record cross-generation or cross-region references.[25]

Young-generation sizing

A larger young generation usually reduces collection frequency but can increase pause work and leaves less space for the old generation in a fixed heap. The best balance depends on allocation rate, object survival, live-set size, and latency objectives.[20]

31. Serial GC

Serial Serial GC uses one GC thread for collection work. It avoids parallel coordination overhead and is appropriate for small heaps, single-processor environments, small utilities, and workloads where stop-the-world pauses are acceptable.[26]

java \
  -XX:+UseSerialGC \
  -Xms128m \
  -Xmx128m \
  -Xlog:gc*=info \
  -jar application.jar

Behavioral profile

  • Generational heap with copying-style young collection and compacting old/full collection in HotSpot.
  • Application threads stop during collection.
  • Low collector-thread footprint and simple ergonomics.
  • Pause duration grows with live data and work because one GC thread performs it.

Good fit

  • Command-line tools and short-lived jobs.
  • Small container limits where GC worker overhead matters.
  • Small live sets and infrequent allocation bursts.
  • Environments intentionally constrained to one active processor.

Oracle's JDK 25 guidance describes Serial GC as suitable for small data sets—approximately 100 MB as a starting point—and explicitly enables it with -XX:+UseSerialGC. Actual suitability must be measured against the workload.[26]

32. Parallel GC

Parallel Parallel GC, also called the throughput collector, is a stop-the-world generational collector that uses multiple GC worker threads to accelerate collection. It is intended for medium-to-large heaps on multiprocessor systems where throughput is more important than short tail-latency pauses.[26]

java \
  -XX:+UseParallelGC \
  -Xms4g \
  -Xmx4g \
  -XX:MaxGCPauseMillis=500 \
  -XX:GCTimeRatio=19 \
  -Xlog:gc*=info \
  -jar batch-job.jar

Adaptive sizing

Parallel GC can adapt generation sizes and related parameters toward pause-time, throughput, and footprint goals. A goal is not a hard real-time guarantee; the collector balances objectives based on observed behavior and available heap.[20]

Strengths

  • High application throughput when pauses are acceptable.
  • Parallel collection uses available processors effectively.
  • Good fit for batch computation, offline processing, and jobs with natural pause tolerance.

Risks

  • Old/full collections stop all mutators and can be long for large live sets.
  • Large heaps can trade fewer collections for larger individual pauses.
  • Overcommitted hosts reduce the value of many GC threads.
  • Latency-sensitive request services can experience unacceptable outliers.

33. Garbage-First (G1)

G1 G1 is HotSpot's default collector on most server-class configurations. It is generational, incremental, parallel, mostly concurrent, evacuating, and stop-the-world for selected phases. It partitions the heap into equal-sized regions that can be assigned to Eden, Survivor, old, or humongous roles.[25][27]

G1 heap: equal-sized regions, roles change ┌────┬────┬────┬────┬────┬────┬────┐ │ E │ O │ S │free│ H │ E │ O │ └────┴────┴────┴────┴────┴────┴────┘ E=Eden S=Survivor O=Old H=Humongous

Cycle outline

  1. Young-only evacuation pauses collect Eden and Survivor regions.
  2. Concurrent marking discovers old-region liveness.
  3. Remark/cleanup complete marking and prepare reclamation.
  4. Mixed collections evacuate young regions plus selected old regions with favorable garbage density.
  5. Full compaction is a fallback when normal evacuation/concurrent progress cannot keep up.

G1 selects collection sets and predicts pause cost from prior behavior. Evacuation copies live objects out of selected regions, compacting them while immediately freeing complete source regions.[25]

Remembered sets

Per-region remembered information tracks references into collection-set regions from outside the set. Write barriers and concurrent refinement maintain this information, trading mutator/concurrent CPU for avoiding whole-heap scans during young and mixed collections.[25][28]

Humongous objects

Objects at least half a G1 region are treated as humongous and occupy one or more contiguous old-generation regions. High humongous allocation can waste region tails, increase marking pressure, and contribute to fragmentation or full collections.[25][28]

Baseline configuration

java \
  -XX:+UseG1GC \
  -Xms4g \
  -Xmx4g \
  -XX:MaxGCPauseMillis=200 \
  -Xlog:gc*,safepoint:file=gc.log:\
time,uptime,level,tags \
  -jar application.jar

Oracle recommends beginning with G1 defaults, maximum heap, and—if required—a pause-time goal. Fixing young-generation size with -Xmn or related options interferes with G1's primary mechanism for meeting its pause target.[28]

34. Z Garbage Collector (ZGC)

ZGC ZGC is a scalable low-latency collector that performs expensive marking and relocation work concurrently and targets sub-millisecond maximum pauses largely independent of heap size. Oracle documents operation from a few hundred megabytes to 16 TB, with throughput cost relative to less concurrent collectors.[22]

Generational-only in JDK 25

JDK 24 removed non-generational ZGC. In JDK 25, -XX:+UseZGC selects generational ZGC; the former ZGenerational option was removed/obsoleted as described by JEP 490.[22][23]

java \
  -XX:+UseZGC \
  -Xms8g \
  -Xmx8g \
  -XX:+AlwaysPreTouch \
  -Xlog:gc*=info \
  -jar latency-service.jar

Concurrent relocation and barriers

ZGC uses load barriers and metadata encoded with references/associated structures to allow application threads to access objects while marking and relocation progress concurrently. The collector remaps references without requiring a heap-size-proportional stop-the-world compaction pause.[22]

Headroom is the primary tuning resource

ZGC dynamically adapts generation sizes, GC thread counts, and tenuring thresholds. The primary tuning action is giving it enough maximum heap that concurrent cycles complete before allocation exhausts available memory.[22]

Trade-offs

  • Very low pauses for latency-critical heaps.
  • Concurrent GC consumes CPU and memory bandwidth during application execution.
  • Barriers add per-access/mutation overhead.
  • Insufficient headroom can produce allocation stalls or failure despite short reported pauses.

35. Shenandoah GC

Shenandoah Shenandoah is an upstream OpenJDK low-pause collector that performs marking, evacuation/compaction, and reference updating largely concurrently with application threads. Its pause durations are designed not to scale directly with heap size, though roots and other pause work still matter.[21][29]

Distribution availability

Shenandoah is part of upstream OpenJDK, but binary inclusion and support vary by vendor and platform. The Oracle JDK collector guide does not list it; verify the actual runtime with java -XX:+UseShenandoahGC -version and vendor documentation.[21]

JDK 25 modes

JEP 521 changed Generational Shenandoah from an experimental feature to a product feature in JDK 25. The established SATB/single-generation mode remains available; the generational mode must be selected explicitly in JDK 25 builds that include it.[24]

# Established mode
java \
  -XX:+UseShenandoahGC \
  -Xms8g \
  -Xmx8g \
  -Xlog:gc*=info \
  -jar latency-service.jar

# Generational product mode in JDK 25
java \
  -XX:+UseShenandoahGC \
  -XX:ShenandoahGCMode=generational \
  -Xms8g \
  -Xmx8g \
  -Xlog:gc*=info \
  -jar latency-service.jar

Cycle and failure modes

Shenandoah's regular cycle includes short initial/final marking coordination, concurrent marking, concurrent evacuation, and concurrent reference updates/cleanup. Under allocation pressure it can pace mutators, enter a stop-the-world degenerated cycle, or fall back to a full collection.[21]

Trade-offs

  • Low pauses through concurrent compaction.
  • Barrier and concurrent-thread overhead affects throughput.
  • Root-set size can influence pause duration.
  • Enough free heap is required while concurrent phases run.
  • Vendor/build support must be verified operationally.

36. Choosing a collector

CollectorPrimary objectiveMain cost / riskStarting use case
SerialSmall footprint and simplicitySingle-threaded stop-the-world workSmall heaps, utilities, constrained CPUs
ParallelMaximum throughputLonger stop-the-world pausesBatch and offline jobs
G1Balanced throughput and bounded-ish pausesRemembered-set/concurrent overhead; evacuation failuresGeneral server workloads
ZGCExtremely low pausesConcurrent/barrier throughput and headroom costStrict latency, large heaps
ShenandoahLow pauses with concurrent compactionBarrier/concurrent overhead; distribution availabilityLatency-sensitive OpenJDK distributions

Collector choice should follow measurable service objectives: throughput, p99/p999 latency, footprint, CPU limit, live-set size, allocation rate, startup, and operational support. Oracle recommends allowing ergonomics to choose unless requirements justify a different collector, then adjusting heap size before extensive low-level tuning.[26]

Compare correctly

  • Use the same JDK build, hardware/container limits, load, duration, and heap budget.
  • Measure end-to-end latency, not only GC pause lines.
  • Include warmup, class loading, JIT, and steady-state phases.
  • Track CPU consumed by mutators and concurrent GC.
  • Record live set after major/concurrent cycles and allocation rate.
  • Test overload and memory-pressure behavior, not only nominal throughput.

37. Object allocation and TLABs

HotSpot commonly gives each mutator thread a thread-local allocation buffer (TLAB) carved from the current allocation region/space. Most small allocations then advance a thread-local pointer without global synchronization; refill and slow-path allocation coordinate with the heap/collector.[6]

Allocation-pressure program

public final class AllocationPressure {
    private static volatile Object sink;

    public static void main(String[] args) {
        int retainedEvery =
            Integer.parseInt(args[0]);

        List<byte[]> retained =
            new ArrayList<>();

        for (long index = 0;; index++) {
            byte[] value =
                new byte[8 * 1024];

            value[0] =
                (byte) index;

            if (index % retainedEvery == 0) {
                retained.add(value);
            } else {
                sink = value;
            }

            if (retained.size() > 20_000) {
                retained.subList(
                    0,
                    10_000)
                    .clear();
            }
        }
    }
}
java \
  -Xms512m \
  -Xmx512m \
  -Xlog:gc*,gc+tlab=debug \
  AllocationPressure 100

Fast allocation is not free

Allocation consumes heap bandwidth, zeroing, TLAB refills, GC scanning/copying, cache capacity, and eventual reference processing. Eliminating temporary objects can improve performance even when allocation itself is a pointer bump.

Large objects

Large arrays and objects can bypass ordinary TLAB paths. G1 treats objects at least half a region as humongous; collector-specific large-object paths have different fragmentation and reclamation characteristics.[25]

38. Strong, soft, weak, phantom, and cleaner processing

Java reference objects let applications interact with reachability beyond ordinary strong references. The collector atomically clears and enqueues references according to the specified reachability category and collector progress.[30]

ReferenceUseWarning
StrongNormal object graphRetains object
SoftMemory-sensitive cachesCollection policy and latency are unsuitable for correctness or precise capacity
WeakCanonical maps/listeners keyed without ownershipCan disappear after reachability transition
PhantomPost-mortem notification with reference queueReferent cannot be retrieved
CleanerFallback cleanup action based on phantom reachabilityNondeterministic; explicit close remains primary

Weak-key registry

Map<ClassLoader, PluginMetrics> metrics =
    Collections.synchronizedMap(
        new WeakHashMap<>());

Cleaner fallback

public final class NativeHandle
        implements AutoCloseable {

    private static final Cleaner CLEANER =
        Cleaner.create();

    private final State state;
    private final Cleaner.Cleanable cleanable;

    public NativeHandle(long address) {
        state = new State(address);
        cleanable =
            CLEANER.register(
                this,
                state);
    }

    @Override
    public void close() {
        cleanable.clean();
    }

    private static final class State
            implements Runnable {

        private long address;

        State(long address) {
            this.address = address;
        }

        @Override
        public synchronized void run() {
            if (address != 0) {
                nativeFree(address);
                address = 0;
            }
        }
    }
}

Cleaner uses phantom reachability and should provide only a safety net. The cleaning action must not strongly capture the registered object. Finalization is deprecated for removal; prefer explicit resource management, try-with-resources, and bounded ownership.[31][32]

39. Safepoints and thread-local handshakes

HotSpot needs points where thread state and reference locations are known well enough for global VM operations such as selected GC phases, deoptimization, class redefinition, stack walking, biased/runtime transitions, and some diagnostics. A safepoint coordinates all relevant Java threads; a thread-local handshake can execute certain callbacks on individual threads without globally stopping every thread.[19][33]

Safepoint logging

java \
  -Xlog:safepoint=info \
  -Xlog:safepoint+stats=debug \
  -jar application.jar

Time to safepoint

Pause duration includes both the time required to bring threads to a safe state and the VM operation itself. Long native calls, page faults, scheduling delays, and unusual generated-code behavior can contribute to synchronization latency even when GC work is short.

Polling and metadata

Compiled methods contain safepoint polls or implicit safe points plus oop maps and deoptimization metadata. This lets HotSpot identify references in registers/stack slots and reconstruct logical Java frames when needed.

44. JVM internals checklist

Class loading

  • Binary name plus defining loader is treated as class identity.
  • Custom loaders preserve parent delegation unless isolation explicitly requires otherwise.
  • Plugin lifecycle removes threads, thread locals, registries, native handles, and caches.
  • Initialization side effects are minimal and failures are tested.
  • Class-loading and Metaspace trends are monitored in dynamic systems.

Memory

  • -Xmx leaves room for Metaspace, code cache, stacks, direct memory, GC, JNI, and OS overhead.
  • Platform-thread count and -Xss fit the native-memory budget.
  • Direct/mapped/native allocations have bounded ownership.
  • NMT is enabled in diagnostic environments where native growth matters.
  • Object-layout assumptions are isolated and tested by runtime/version.

Execution and JIT

  • Benchmarks include separate warmup and forked steady-state measurement.
  • Production profiles use JFR rather than guesswork.
  • Compiler directives are temporary, method-specific, and version-tested.
  • Code-cache usage and compilation failures are observable.
  • Workload phase changes are considered when interpreting deoptimization.

Garbage collection

  • Collector choice follows latency, throughput, CPU, footprint, and support objectives.
  • Heap has room above the live set for allocation and concurrent collection.
  • GC logs include causes, phases, heap/region information, and timestamps.
  • End-to-end latency is correlated with GC rather than inferred from pause time alone.
  • Allocation rate, promotion/tenuring, humongous objects, and reference processing are measured.
  • Low-latency collector stalls/degenerated cycles are treated as failures even when pauses are short.

Operations

  • JDK vendor and exact build are recorded with incident artifacts.
  • Heap dump, fatal-error log, JFR, and GC-log paths are writable and capacity-managed.
  • jcmd commands and impact levels are documented for responders.
  • Container CPU/memory limits are visible to both VM and monitoring.
  • Changes are validated under representative load and failure pressure.
Final principle: the JVM is an adaptive runtime. Class loading, allocation, compilation, and collection continuously change execution state. Reliable conclusions come from separating specification from implementation, measuring the exact JDK build, and correlating bytecode, profiles, memory ownership, GC activity, native resources, and application latency.
