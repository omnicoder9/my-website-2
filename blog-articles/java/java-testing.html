1What a test is for

A test is a small program that makes a claim about a larger one. When it passes, it tells you that the claim held on this run. The question that decides whether the test was worth writing is the counterfactual one: if the code were wrong, would the test have noticed? Dijkstra put the limit plainly half a century ago: testing can show the presence of bugs, never their absence 1. Everything in this article is about making the first half of that sentence as strong as possible for the effort spent.

The organising question is therefore what would make this test fail? It is a sharper question than "is this code tested?", because it can be asked of every assertion, every mock, every integration test and every coverage number, and it has a measurable answer. Change the program in a small, plausible way and see which tests go red. That procedure is called mutation analysis. It was proposed in the 1970s 2, surveyed at length since 3, and it is the closest thing the field has to a direct measurement of a test suite's ability to detect faults 4,5.

To make the argument concrete rather than rhetorical, this article is built around a lab. A small Java invoicing module, about 240 lines, is tested by six suites written in six different styles. Every suite is run against 24 deliberately faulty versions of the module, and every suite's code coverage is measured with JaCoCo. Every listing in the article that is marked compiled and run was compiled and executed at build time. Every number quoted in the text or drawn in a figure comes from that run. The toolchain is the current one: JUnit 6.1.2 6, Mockito 5.23.0 7 and JaCoCo 0.8.15 8 on a Java 21 runtime, with H2 2.2.220 as the SQL engine for the integration tests.

The figure above is the article in one picture. The suite that asserts nothing covers 94.2% of executable lines and detects 1 of 24 of the 24 faults. The suite that concentrates on boundaries covers only 56.7% and detects 14 of 24. The combination of three focused suites detects 23 of 24. Coverage tells you where tests have been; it says very little about what they would notice. The rest of the article works through the four subjects in turn, JUnit and its assertions, mocking with Mockito, integration testing and coverage, and asks of each the same question.

2The system under test

The module computes invoices. An InvoiceService takes a customer id and a list of line items, looks the customer up, sums the quantities, applies a volume and membership discount, adds regional sales tax, dates the invoice from an injected Clock, saves it and notifies the customer. Money is held as whole cents in an immutable record, which removes an entire class of floating-point bugs before a single test is written 9. Rounding is half-to-even, the banker's rounding defined by java.math.RoundingMode.HALF_EVEN 10.

The discount rule is where boundaries live. A total quantity of 10 or more earns 5 per cent, 50 or more earns 10 per cent, members get another 5 per cent, and the total is capped at 12.

The service depends on four collaborators, each behind an interface: a customer repository, an invoice repository, a tax-rate lookup and a notifier. It also takes the discount policy, a clock and an id generator. Every one of those constructor parameters is a seam: a place where a test can substitute something it controls. This is the design move that makes the rest of the article possible, and it is also the move most often skipped in code that turns out to be hard to test 11,12.

The two repositories have a real implementation, JdbcStore, which issues SQL through plain JDBC. Its correctness depends on column names, bind positions and an ORDER BY clause, none of which exist until a database parses them. Keep that in mind; it matters a great deal in the section on mocking.

The 24 faults

The faulty versions, called mutants, were seeded by hand in the operator families that PIT, the standard mutation tool for Java, applies automatically 13,14. There are four boundary changes, two logic changes and four arithmetic changes. There are two rounding-mode swaps, four interaction faults (a missing call, a wrong argument, a reversed order), one exception-handling fault, two time faults and five SQL faults. Each mutant is a one-line, plausible mistake. A mutant is killed by a suite if at least one of the suite's tests fails when run against it. The full list, with which suites killed each, is in the table in the coverage section.

3Unit testing with JUnit 6

JUnit descends from Kent Beck's SUnit for Smalltalk 15 and from the Java port Beck and Erich Gamma wrote in 1997, introduced to most programmers by their article "Test infected" 16. The xUnit pattern it established, a test method, a fixture, assertions, a runner, is now the common vocabulary of the field 17.

Platform, engine, API

Since version 5, JUnit has been three things rather than one. The JUnit Platform discovers and launches tests and reports results to IDEs and build tools through a Launcher API. A test engine plugs into the Platform and knows how to run one programming model. JUnit Jupiter is the engine and API for the modern model: @Test, @BeforeEach, @ParameterizedTest, the extension model 18. JUnit Vintage runs JUnit 3 and 4 tests on the same Platform. Other frameworks ship their own engines, which is why a single build can run Jupiter, Spock and Cucumber tests side by side.

JUnit 6.0.0, released on 30 September 2025, raised the minimum Java version to 17. It gave Platform, Jupiter and Vintage a single version number, which ended the old Platform 1.x / Jupiter 5.x pairing. It also annotated the whole API with JSpecify nullability annotations 19,20. It switched CSV parsing for parameterised tests to FastCSV, added support for Kotlin suspend test methods and introduced a cancellation API 19. For Java test code written against Jupiter 5 the migration is usually a version bump. The APIs used in this article are unchanged between 5.x and 6.x.

The anatomy of a test

The simplest useful test arranges an input, acts once and asserts one outcome. Suite S3 is exactly that: one realistic order and one exact expected total.

Three details are worth pausing on. The test class and method are package-private. Jupiter does not require public, and the convention is to omit it. The expected value is written out as a literal, with the arithmetic in a comment, rather than computed by the test. A test that recomputes its expected value with the same formula as the code will agree with the code's bugs. And the assertion compares Money values, not raw longs, which matters for the failure message, as the next section shows.

S3 executes about half the module and kills 3 of 24 mutants: a negated membership test, subtraction of tax instead of addition, and truncation instead of rounding. Each of those changes the one total it checks. It cannot see a boundary shift, because its order of three items is nowhere near a threshold, and it cannot see anything about saving or notifying, because it never looks.

Lifecycle: a new instance for every test

By default Jupiter creates a new instance of the test class for every test method 18. Fields are therefore fresh for each test, and one test cannot leak state into another through them. @BeforeEach and @AfterEach run around each test on that instance. @BeforeAll and @AfterAll run once per class and must be static unless the class opts into @TestInstance(Lifecycle.PER_CLASS).

Per-method instances are the framework's first defence against order-dependent tests, which Luo and colleagues found among the three leading causes of flaky tests in their study of 201 flaky-test fixes across 51 open-source projects 21. They are not a complete defence. Static fields, shared databases, files and system properties all survive from one test to the next. In JUnit 6 the order in which methods run is deterministic, but intentionally not obvious, precisely so that nobody relies on it 19.

Parameterised tests and boundaries

The discount rule changes behaviour at quantities 10 and 50 and at the cap. A test that samples one quantity per region, say 5, 25 and 75, passes against a version where >= 10 has become > 10. The mutant only differs at exactly 10. Boundary-value analysis, the classical technique catalogued in ISO/IEC/IEEE 29119-4 22 and in every testing textbook since Myers 23, says to test on both sides of each edge and on the edge itself.

@ParameterizedTest with a @CsvSource turns that table into one test method with one invocation per row, each reported separately 18. Suite S4 does that for the discount policy and for rounding. It also uses @Nested classes to group tests by subject, assertAll to report several related checks together and assertThrows for the error paths.

The fixtures it uses are hand-written fakes: working, in-memory implementations of the four ports. A fake is the most realistic kind of test double. It has real behaviour, only simpler.

It runs against fakes rather than SQL, so all five SQL mutants survive too.

What counts as a unit

There are two schools. The classical or Detroit school treats a unit as a unit of behaviour and uses real collaborators wherever they are fast and deterministic, substituting only for shared or slow resources. The mockist or London school, associated with Freeman and Pryce 11, treats a unit as a class and replaces every collaborator with a test double, so each test isolates one object's responsibilities 24,25. S4 is classical: the real DiscountPolicy and Money run inside every service test. S5, in the mocking section, is mockist. The lab does not settle the argument, but it does show what each style can and cannot see.

Running tests in a build

Build tools run tests through the Platform. In Maven, the Surefire plugin runs unit tests in the test phase. The Failsafe plugin runs integration tests, named *IT by convention, in the integration-test and verify phases, so that environment teardown still happens when a test fails 26. The dependency block for the libraries used here is short, because JUnit publishes a bill of materials that aligns every module's version.

Failure messages are part of the test

When a test fails, its message is the first and often the only diagnostic anyone reads. The seven tests below were written to fail. The service was given a zero tax rate, so every total comes out at 65.00 instead of the expected 68.09. The output is JUnit's own, captured verbatim at build time.

The boolean form, assertTrue(a == b), reports only that true was expected and false was received: the information that would explain the failure has been thrown away before the assertion saw it. assertEquals reports both values. Comparing value objects rather than primitives reports them in the domain's own notation, 68.09 against 65.00, because JUnit prints each object's toString(). A message supplier adds context without cost on the passing path, because the lambda is evaluated only on failure 18.

assertAll runs every check in its group and reports all the failures together. The three-failure report above is more useful than the first failure alone, because the pattern (tax zero, total short by exactly the tax, date a day off) points at two independent causes. The third failure is a deliberate trap: the fixed clock is 03:30 UTC on 1 March, which is still 28 February in the clock's zone, and the test author forgot. We come back to that in the integration section.

assertThrows returns the exception it caught, so the test can inspect it. Checking only the type is weaker than it looks. The one mutant that survived every suite in the lab removes the service's empty-order guard. With the guard gone, an empty order still throws IllegalArgumentException, because DiscountPolicy independently rejects a total quantity of 0. The type matches, the test passes and the mutant lives. Asserting the message as well, "an invoice needs at least one line", kills it. That was verified at build time and is recorded in the method section. It also exposes something about the code: the guard is redundant with a check one layer down, which is a design observation a coverage report would never have produced.

Floating point, deltas and the assert keyword

assertEquals(0.3, 0.1 + 0.2) fails, as the last demo shows, because neither 0.1 nor 0.2 is exactly representable in binary floating point 9,27. For double values, use the overload with a tolerance, assertEquals(expected, actual, delta). For money, use integer cents or BigDecimal and avoid the problem entirely. Note that BigDecimal.equals compares scale, so 2.0 and 2.00 are unequal, while compareTo does not 10.

Java's own assert statement is not a testing tool. Assertions of that kind are disabled at run time unless the JVM is started with -ea 28, so a check written with assert in a test silently does nothing in a default run. Use the framework's assertions in tests and reserve the keyword for internal invariants in production code.

Fluent assertion libraries

Jupiter's Assertions class is deliberately small. Many teams add AssertJ or Hamcrest for richer comparisons of collections, maps, exceptions and object graphs, and for failure messages that describe the whole structure 29,30. The choice is a matter of taste and consistency. What matters, per the lab, is not which library is used but whether the assertion constrains the answer enough that a wrong one fails.

5Mocking with Mockito

A vocabulary for test doubles

Gerard Meszaros named the family of stand-ins that tests use in place of real collaborators test doubles, and distinguished five kinds 17. A dummy is passed but never used. A stub returns canned answers. A spy is a stub that also records how it was called. A mock is pre-programmed with expectations and verifies them. A fake has a working, simplified implementation, such as the in-memory repositories in the fixtures above. Martin Fowler's essay "Mocks aren't stubs" draws the consequential distinction between the kinds of verification they support. State verification checks what the system produced. Behaviour verification checks what the system did to its collaborators 25.

Mock objects came out of the London extreme-programming community. Mackinnon, Freeman and Craig described them in 2000 as a way to test an object from the inside by replacing its environment 32. Freeman, Mackinnon, Pryce and Walnes later sharpened the idea into "mock roles, not objects": mocks are for discovering and specifying the interfaces an object needs from its neighbours, not for replacing arbitrary classes 33. That origin explains the most-quoted rule of thumb in the area, don't mock types you don't own. Replace your own interfaces, and test your adapters to third-party code against the real thing 11.

Mockito in practice

Mockito is the dominant mocking library for Java. It is a mock-then-verify design: you create a mock, stub the calls you need, run the code, then verify the interactions you care about 31. Mockito 5 made the inline mock maker the default, which uses the Java instrumentation API to redefine classes in place. Final classes and methods can therefore be mocked without configuration, and the minimum Java version became 11 34. The current release is 5.23.0, published on 11 March 2026 7.

Suite S5 tests the service in the mockist style. Every port is a Mockito mock. The discount policy and Money stay real, because they are value-like domain logic with no side effects. That matches what developers report doing in practice: Spadini and colleagues found that developers mock dependencies that make testing hard, such as databases and web services, and avoid mocking classes that hold domain rules 35,36.

The features in that listing are, in order of appearance, these. @ExtendWith(MockitoExtension.class) creates the @Mock and @Captor fields before each test and checks stubbing hygiene after it. when(...).thenReturn(...) stubs a call. An ArgumentCaptor catches the invoice passed to save so the test can make state assertions about it. inOrder(...) verifies that saving happened before notifying. same(returned) checks identity rather than equality. verifyNoInteractions asserts that the failure path produced no side effects at all.

What mocks cannot see

JaCoCo's per-class report for S5 shows that it executed 0 of 44 lines of JdbcStore. Of course it did: the store was mocked. All five SQL mutants survive S5. A mock of a repository encodes the test author's belief about what the repository does. If the belief is wrong, the mock and the code agree with each other and the suite stays green. The stub when(customers.find("c2")).thenReturn(Optional.of(BRUNO)) would be equally satisfied by a repository whose SQL queried the wrong column. Spadini's interviewees named this exact problem as the main cost of mocking: keeping a mock's behaviour compatible with the class it replaces 35.

Two further costs follow. Mock-heavy tests couple to how the code does something, so a refactoring that preserves behaviour can break them. And a mock can be arranged to return anything, including values the real collaborator could never produce. Google's guidance is to prefer real implementations where they are fast and deterministic, then fakes, and to reserve stubbing and interaction testing for cases where the interaction is itself the requirement 12. The lab's numbers support a narrower version of the same advice. Mocks were the only way to see the four interaction faults, and useless for the five SQL faults. Both suites were needed.

6Integration testing

What is being integrated

ISO/IEC/IEEE 29119 and the ISTQB syllabus define integration testing as testing that focuses on the interactions between integrated components or systems 39,40. In practice, for a Java service, the interesting integrations are the ones where Java code meets something that is not Java: a SQL engine, a message broker, an HTTP API, a file system, the system clock. Those are exactly the places where a unit test's doubles encode an assumption about the outside world, and where the assumption can be wrong.

The test pyramid, popularised by Mike Cohn, recommends many fast unit tests, fewer integration tests and fewer still end-to-end tests 41–43. The shape is an economic argument about speed and cost of maintenance, not a claim that the upper layers catch less. In the lab, the integration suite caught five faults that no unit test could.

A database in the test

Suite S6 runs JdbcStore against a real SQL engine. Each test gets a fresh, named in-memory H2 database, created in @BeforeEach and closed in @AfterEach. Every test therefore starts from the same known state, and no data leaks between tests. One test wires the real store into the real service, the smallest end-to-end slice the module allows.

Fidelity: H2 is not your production database

An in-memory engine is fast and needs no infrastructure, which is why the lab uses one. It is also a different SQL dialect from PostgreSQL, MySQL or Oracle, with its own type coercions, locking behaviour and error codes 44. An integration test against H2 verifies your SQL against H2. The standard remedy is to run the integration suite against the production engine in a disposable container. Testcontainers for Java does this from inside a JUnit test. Its 2.0 release removed JUnit 4 support, prefixed every module's artifact id with testcontainers- and moved the container classes into per-module packages such as org.testcontainers.postgresql 45,46. Spring's TestContext framework offers the same idea at the level of a whole application context, caching it across test classes 47.

The clock is an integration too

Suite S4's datesComeFromTheInjectedClock pins the date by injecting Clock.fixed(...), the approach the java.time API was designed to support 48. The time mutant that replaces LocalDate.now(clock) with LocalDate.now() is killed with a message that names whatever day the build happened to run:

Injecting a clock only helps if the test and the code agree about which clock. The demo test in the assertions section expected 1 March and got 28 February, because the fixed instant was 03:30 UTC and the clock's zone was New York. How often does that class of mistake, a test computing "today" in UTC while the code uses a local zone, actually fail? The lab swept every minute of two days, one in January and one in July, for seven zones.

For a New York service the test is wrong for 300 minutes of the day in January and 240 in July: 20.8% and 16.7% of runs, all in the evening, local time. A London service passes every run all winter and fails for an hour a night in summer. An Auckland service fails more often than it passes in January. A test like that passes on the developer's machine in the morning and fails on the overnight build, and becomes one of the time-dependent flaky tests in the studies. Luo and colleagues found that 78 per cent of the flaky tests they studied were flaky from the moment they were written 21. Eck and colleagues' interviews with Mozilla developers show how much time such tests cost to diagnose after the fact 49. The fix is always the same: make the test construct its expected value from the same injected clock, or better, fix both the instant and the zone and write the expected date as a literal.

7Test coverage

What JaCoCo measures

JaCoCo instruments bytecode, either on the fly through a Java agent attached to the test JVM or offline, and records which probes executed 50. From those probes it derives six counters 51. Instructions are bytecode instructions executed. Branches are the outcomes of if and switch decisions. Lines are source lines with at least one instruction executed. Methods are methods with at least one instruction executed. Cyclomatic complexity and classes complete the set. Line coverage is the number most dashboards show. Branch coverage is the stronger of the two cheap measures, because a line containing a condition counts as covered as soon as either outcome runs. JaCoCo 0.8.15, released on 5 June 2026, officially supports Java 26 and has experimental support for Java 27 class files 8.

S1, which asserts nothing, has 94.2% line coverage but only 63.6% branch coverage. It ran almost every line and took less than two-thirds of the decisions both ways. The gap between the two numbers is a quick, free signal that a suite follows happy paths.

Coverage against detection

The scatter below puts the two measures side by side for all seven suites.

Across the seven suites the rank correlation between line coverage and mutants killed is +0.04. Using branch coverage instead it is +0.17. With seven points neither number deserves more than one significant figure of trust. The pattern behind them is the robust part. Three suites (S1, S2 and S6) sit above 90 per cent line coverage and kill between one and six mutants. The two suites that kill the most among the single suites, S4 and S5, sit near 55 per cent.

The lab agrees with the literature. Inozemtseva and Holmes generated 31,000 test suites for five large Java systems and found that, once suite size is controlled for, the correlation between coverage and mutant detection is low to moderate. Stronger forms of coverage gave no better insight 52. The paper received the ICSE Most Influential Paper award ten years later 53. Gopinath, Jensen and Groce, working with hundreds of open-source projects, found statement coverage the best of the cheap criteria at predicting mutation score, but still a proxy 54. Kochhar, Thung and Lo, using real rather than seeded bugs, found coverage only moderately related to bug detection 55. Mutants themselves are a defensible stand-in for real faults. Just and colleagues found a statistically significant correlation between mutant detection and real-fault detection that coverage alone did not explain 4, and Papadakis and colleagues reached a similar, more qualified conclusion at larger scale 5.

Stronger criteria: MC/DC

Aviation software is the one domain where the choice of coverage criterion is written into certification. DO-178C requires modified condition/decision coverage for the most critical software level 56. MC/DC requires that each condition in a decision be shown to affect the decision's outcome independently, by a pair of tests that differ only in that condition and produce different outcomes 57,58. The lab computed the minimum number of tests each criterion needs by brute force over every subset of the truth table.

For a chain of n conditions joined by &&, branch coverage always needs two tests, MC/DC needs n + 1 and exhaustive multiple-condition coverage needs 2n. That linear rather than exponential growth is the whole reason MC/DC exists: it is the strongest condition-level criterion that stays affordable 57. Zhu, Hall and May's survey remains the standard map of the other adequacy criteria 59. For ordinary business code, branch coverage plus boundary-value tests like S4's usually captures what MC/DC would.

What to do with the number

Google's published guidance offers 60 per cent as acceptable, 75 as commendable and 90 as exemplary. It warns against top-down mandates, and against engineers treating a target as a checkbox 60. At Google's scale, coverage is computed daily for a billion lines of code in seven languages. Its main use is at the level of the changeset in code review, where a reviewer can see which new lines no test executed 61. A later refinement, productive coverage, weights uncovered code by how likely it is to matter, so that reviewers are not asked to cover trivia 62.

That is the right use of the number: coverage is good at telling you what is not tested. An uncovered line is certainly unverified. A covered line may or may not be verified; the lab's S1 covered 98 lines and verified none. The measurement that answers the article's question is mutation analysis. PIT makes it practical for Java by generating mutants at bytecode level and running only the tests that cover each mutated line 13. At Google, surviving mutants are surfaced in code review as suggestions rather than as a score, and developers act on a substantial share of them 63.

8The ledger

The seven suites, collected. Each row is one plate from the sections above.

Four practical conclusions follow from the lab, each tied to a number above.

First, assertions are the test. A suite that asserts nothing, or asserts only that something happened, can reach any coverage figure you like and detect almost nothing: S1 and S2 cover more than 92 per cent of lines and kill 1 of 24 and 2 of 24 faults. Write exact expected values, compare domain values rather than primitives, check exception messages as well as types, and use assertAll where several facts belong together.

Second, put examples where behaviour changes. S4's boundary rows killed every boundary mutant with the lowest coverage of any focused suite. @ParameterizedTest makes the edges cheap to enumerate.

Third, mock roles, and only where the interaction is the requirement. Mockito's InOrder verification was the only thing in the lab that saw a notification sent before the save. The same mocks made the suite blind to every SQL fault, because a mocked repository cannot disagree with its author.

Fourth, test the seams against the real thing. Only the integration suite saw SQL faults, and it saw all of them. Inject the clock and fix its zone. Run the database suite against the production engine when fidelity matters.

Coverage belongs underneath all four, as a map of where no test has looked, not as a score. The question to ask of every test, and of every number about tests, is still the one this article began with: what would make it fail?

9Method and limits

The lab ran in a Linux container on OpenJDK 21.0.12.1. Neither Maven Central nor a prebuilt JUnit or Mockito distribution was reachable from it. JUnit 6.1.2 and Mockito 5.23.0, including mockito-junit-jupiter, were therefore compiled from their tagged release sources.

Two build-level substitutions were needed for JUnit, both outside anything the tests exercise. The single Kotlin-coroutine helper class in junit-platform-commons was replaced by a stub that throws, because no Kotlin runtime was present. One sealed modifier in junit-jupiter-api was removed, because it is only legal across packages inside a named module and the build used the class path. The JRE enum, which JUnit generates from a template at build time, was rendered from that template.

Mockito ran on Byte Buddy 1.14.13 from the operating system's package repository rather than the newer release it ships with. JaCoCo 0.8.15 was the official release distribution. Tests were launched through the JUnit Platform Launcher API from a 40-line runner, not through Maven.

Each mutant was applied as an exact, single-occurrence text substitution to a copy of the source. The copy was compiled, and all six suites were run against it in one JVM. Coverage for S7 comes from running S4, S5 and S6 together under one JaCoCo agent. Kills for S7 are the union of the three suites' kills, which is exact because a mutant is killed by a suite if any of its tests fails.

The mutation results, coverage figures, failure messages and sweep counts are deterministic. The one exception is the date inside the T1 failure message, which is whatever day the build ran. The surviving mutant L2 was re-run against a copy of S4 whose empty-order test also asserts the exception message. That run reported the check passing on the original code and failing on the mutant, with AssertionFailedError: expected: <an invoice needs at least one line> but was: <quantity must be positive: 0>.

The lab is small by design. It has 24 hand-seeded mutants in one 240-line module, and it demonstrates mechanisms rather than estimating effect sizes; the correlations in the coverage section are across seven points. The empirical studies cited alongside each claim are where the effect sizes come from.
