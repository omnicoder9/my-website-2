PostgreSQL Indexing

An expert guide to PostgreSQL index access methods and design: B-tree, Hash, GiST, SP-GiST, GIN and BRIN; multicolumn, unique, partial, expression and covering indexes; operator classes; selectivity and cardinality; read/write tradeoffs; maintenance; over-indexing; and query-driven index design.

Technical article • PostgreSQL 18.6 baseline • Updated 16 September 2026 • Vancouver-style references

Abstract

Indexes are secondary data structures that trade additional storage and write work for faster access to selected query patterns. PostgreSQL provides several built-in access methods rather than one universal index: B-tree for ordered scalar search and ordering, Hash for equality, GiST and SP-GiST as extensible search-tree frameworks, GIN as an inverted index for multi-component values, and BRIN as a compact block-range summary index for physically correlated data. The planner chooses whether to use an index from estimated selectivity, cardinality, ordering, heap-access cost, and complete plan cost—not merely because an index exists.[1]-[3]

Advanced index design is primarily about matching real query predicates. Multicolumn B-tree indexes are most effective when their leading columns constrain the searchable range, although PostgreSQL 18 can use skip scan in more cases. Partial indexes intentionally index only rows satisfying a predicate; expression indexes index computed values; unique indexes enforce uniqueness; and covering indexes use INCLUDE columns to make index-only scans possible without changing search-key semantics.[4]-[8]

Indexes are not free. Every extra index consumes disk, creates WAL, increases insert/delete maintenance, can make updates more expensive, and can reduce opportunities for heap-only tuple (HOT) updates when indexed attributes change. Wide or redundant indexes also enlarge working sets and lengthen maintenance operations. The correct question is therefore not “Which columns should have indexes?” but “Which recurring query paths justify an additional physical structure after accounting for write, storage, concurrency, and maintenance cost?”[1][9][10]

1. PostgreSQL indexing model

PostgreSQL indexes are separate relations from the table heap. An ordinary index scan finds index entries and then fetches corresponding heap tuples, where MVCC visibility is checked and any non-indexed columns are obtained. This separation explains both index advantages and costs: index traversal can avoid scanning most heap pages, but a selective index can still generate many random heap fetches if matching rows are physically scattered.[8][11]

table heap +-----------------------------+ | page 0: rows ... | | page 1: rows ... | | page 2: rows ... | +-----------------------------+ secondary index +-------------------------------------+ | key -> TID(block, offset) | | key -> TID(block, offset) | | ... | +-------------------------------------+ | v index scan finds TIDs | v heap fetch + MVCC visibility check

1.1 CREATE INDEX

CREATE INDEX orders_customer_idx
ON app.orders (customer_id);

B-tree is the default access method. Other methods are selected explicitly with USING.[2][12]

CREATE INDEX event_payload_gin
ON app.event
USING gin (payload);

2. How the planner decides whether to use an index

An index is only useful if its complete execution path is expected to be cheaper than alternatives such as a sequential scan, bitmap scan, another index, or an index combination. PostgreSQL estimates predicate selectivity using planner statistics, estimates the number of rows that will qualify, and then prices index traversal, index tuple processing, heap I/O, CPU filtering, ordering benefits, and parent-plan requirements.[13]-[15]

WHERE customer_id = 42 | v statistics -> selectivity estimate | v estimated rows | +--> Seq Scan cost +--> Index Scan cost +--> Bitmap Heap Scan cost +--> alternative index costs | v lowest estimated complete-plan cost wins

2.1 An index is not a directive

EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM app.orders
WHERE status = 'complete';

If nearly every row has status='complete', an index on status may be less efficient than scanning the heap. Low-cardinality values can still be worth indexing when a rare value is queried frequently, especially with a partial index; cardinality alone never determines usefulness.[6][14]

3. Built-in index types

PostgreSQL 18 provides B-tree, Hash, GiST, SP-GiST, GIN and BRIN as built-in index access methods. The supplied bloom module provides an additional index access method as an extension. Each access method defines different storage/search semantics and relies on operator classes to determine which operators and data types it can accelerate.[2]

4. B-tree indexes

B-tree is PostgreSQL's default and general-purpose ordered index. It supports data types with a well-defined linear order and is considered for comparisons using <, <=, =, >=, and >, plus constructs reducible to those comparisons such as BETWEEN and many IN cases. It is also the only built-in index type that can directly produce sorted output for ORDER BY and the only built-in access method that can currently enforce ordinary unique indexes.[2][7][16]

CREATE INDEX orders_created_idx
ON app.orders (created_at);

SELECT *
FROM app.orders
WHERE created_at >= timestamp '2026-09-01'
  AND created_at <  timestamp '2026-10-01';

4.1 Ordering

CREATE INDEX orders_created_desc_idx
ON app.orders (created_at DESC);

SELECT *
FROM app.orders
ORDER BY created_at DESC
LIMIT 100;

A B-tree can normally be scanned forward or backward, so one simple ascending single-column B-tree can satisfy both ascending and descending order (with corresponding null ordering). Explicit per-column direction becomes more important in multicolumn indexes where mixed directions are required.[16]

4.2 Pattern matching

B-tree can support prefix pattern matching such as LIKE 'foo%' when the operator class/collation semantics allow it; PostgreSQL also provides pattern operator classes such as text_pattern_ops for cases where locale-aware ordering otherwise prevents the desired prefix behavior.[17]

4.3 B-tree implementation considerations

B-tree index tuples have size limits; PostgreSQL's implementation requires an index entry to fit within roughly one-third of an index page after applicable compression. Very wide values or covering payloads can therefore make index creation/insertion fail even when the heap column itself can store the value.[18]

5. Hash indexes

Hash indexes support simple equality comparisons through =. They do not provide range ordering, ORDER BY output, multicolumn keys, or uniqueness enforcement. PostgreSQL's own documentation recommends B-tree for typical concurrently accessed scalar data because B-tree has broader functionality and strong concurrency behavior; Hash remains a specialized equality structure.[2][9]

CREATE INDEX session_token_hash_idx
ON auth.session
USING hash (session_token);

SELECT *
FROM auth.session
WHERE session_token = $1;

Hash index access uses bucket-level locking internally, while B-tree, GiST, SP-GiST and GIN generally use shorter page-level locks. This implementation difference is one reason B-tree is normally the preferred scalar index unless a measured workload demonstrates a Hash advantage.[9]

6. GiST

GiST (Generalized Search Tree) is an extensible balanced-tree framework rather than one fixed data structure. Operator classes supply the semantics needed to map a data type and its predicates into the GiST framework. Built-in and supplied operator classes support geometric types, range types, nearest-neighbor searches, and many extension-defined domains.[2][19]

CREATE INDEX places_location_gist
ON geo.place
USING gist (location);

SELECT *
FROM geo.place
ORDER BY location <-> point(-78.6382, 35.7796)
LIMIT 10;

Nearest-neighbor search is an important GiST capability when the selected operator class defines an ordering operator such as distance. GiST also underlies common exclusion-constraint designs, where equality on one dimension and overlap on another can be combined using appropriate operator classes.[19][20]

6.1 btree_gist

The supplied btree_gist extension provides GiST operator classes with B-tree-like comparison behavior for many scalar types. They do not generally outperform native B-tree and do not provide ordinary B-tree uniqueness, but are useful when scalar comparisons need to participate in a multicolumn GiST structure, especially exclusion constraints.[20]

7. SP-GiST

SP-GiST (Space-Partitioned GiST) is an extensible framework for search structures that recursively partition a search space. Unlike GiST's balanced-tree abstraction, SP-GiST is designed to accommodate partitioning structures such as tries, radix trees, quadtrees and k-d trees through suitable operator classes. Supported operators depend on the chosen operator class.[2][21]

CREATE INDEX point_spgist_idx
ON geo.sample
USING spgist (location);

SP-GiST can support nearest-neighbor ordering when its operator class implements the relevant distance semantics. It is attractive when the data's natural partitioning structure matches an available SP-GiST operator class.[2][21]

8. GIN

GIN (Generalized Inverted Index) is designed for values containing many component values. Rather than indexing one scalar key per row, a GIN operator class extracts keys from each indexed value, stores an inverted mapping from key to matching heap rows, and supports queries based on component membership. Arrays, full-text tsvector, and JSONB are canonical uses.[2][22]

CREATE INDEX article_search_gin
ON content.article
USING gin (search_vector);

SELECT *
FROM content.article
WHERE search_vector @@ websearch_to_tsquery('english', 'postgres indexing');
CREATE INDEX event_payload_gin
ON app.event
USING gin (payload);

SELECT *
FROM app.event
WHERE payload @> '{"type":"purchase"}'::jsonb;

8.1 Write amplification and fast update

A single row can generate many GIN key entries, so GIN inserts are often substantially more expensive than scalar B-tree inserts. GIN's fast-update mechanism can accumulate pending entries for later consolidation; it is configurable through GIN storage parameters and maintenance behavior.[9][12][22]

8.2 PostgreSQL 18 parallel GIN build

PostgreSQL 18 added support for parallel creation of GIN indexes, reducing build time when the planner/build infrastructure can use parallel workers.[23]

9. BRIN

BRIN (Block Range INdex) stores summaries for ranges of consecutive heap blocks instead of one entry per indexed row. For min/max operator classes, each range records summary boundaries; if a query's predicate cannot match a block range's summary, PostgreSQL can skip that range. BRIN is therefore exceptionally compact and effective when column values correlate with physical row order.[2][24]

CREATE INDEX telemetry_recorded_brin
ON telemetry.sample
USING brin (recorded_at)
WITH (pages_per_range = 128);

SELECT *
FROM telemetry.sample
WHERE recorded_at >= now() - interval '1 hour';
heap physical order blocks 0..127 time 2026-01-01 .. 2026-01-03 blocks 128..255 time 2026-01-03 .. 2026-01-05 blocks 256..383 time 2026-01-05 .. 2026-01-07 BRIN summaries: range 0 -> [min Jan 1, max Jan 3] range 1 -> [min Jan 3, max Jan 5] range 2 -> [min Jan 5, max Jan 7] query Jan 6: range 0/1 can be skipped range 2 must be checked

BRIN does not prove which individual rows match; it identifies ranges that might contain matches and therefore produces lossy candidates for heap rechecking. Its advantage is a tiny index and low maintenance cost on massive physically correlated tables.[24]

9.1 Correlation is the key

A BRIN on a randomly distributed UUID usually summarizes nearly the whole value domain in every block range and cannot prune much. An append-only timestamp or increasing identifier often has excellent physical correlation and is a much better candidate.

10. Advanced indexing

Advanced PostgreSQL indexing is mostly about controlling which values become keys, which rows receive entries, which extra values are stored as payload, and which operators give those keys meaning. The CREATE INDEX grammar supports expressions, per-key collations, operator classes, direction/null ordering, included columns, storage parameters, tablespaces and partial-index predicates.[12]

CREATE INDEX orders_lookup_idx
ON app.orders
USING btree (
    tenant_id,
    lower(email) text_pattern_ops,
    created_at DESC
)
INCLUDE (order_id, total_amount)
WHERE state = 'open'
WITH (fillfactor = 90);

No single “advanced” feature should be added just because PostgreSQL supports it. Every extra predicate, expression and payload column should map to stable query behavior and a measurable access requirement.

11. Composite and multicolumn indexes

A multicolumn index stores multiple key columns in one index entry. PostgreSQL 18 allows multicolumn key indexes for B-tree, GiST, GIN and BRIN; Hash and SP-GiST do not support multiple key columns. The compile-time limit is normally 32 total columns including INCLUDE columns.[4]

CREATE INDEX orders_tenant_customer_created_idx
ON app.orders (
    tenant_id,
    customer_id,
    created_at DESC
);

11.1 B-tree leading-column behavior

For multicolumn B-tree, equality constraints on leading columns plus an inequality on the first non-equality column most directly narrow the range of index entries that must be scanned. Restrictions on later columns can still be checked in the index, and PostgreSQL 18 can sometimes use skip scan to reposition through leading-key groups, but leading-column design remains central.[4]

-- Excellent fit:
SELECT *
FROM app.orders
WHERE tenant_id = 7
  AND customer_id = 42
  AND created_at >= current_date - 30
ORDER BY created_at DESC;

11.2 Column order is query order, not “most selective first”

The blanket rule “put the most selective column first” is incomplete. For B-tree, column order should reflect equality/range predicates, required ordering, skip-scan opportunities, and actual query shapes. An equality-constrained tenant key often belongs before a timestamp range even if the timestamp has more distinct values, because doing so isolates the relevant tenant's ordered subrange.

11.3 GiST, GIN and BRIN differ

Multicolumn GiST can use conditions on any indexed column, but its first column is especially important to how much of the index must be searched. GIN and BRIN can use any subset of their indexed columns without the same leading-column search-effectiveness rule. This is one reason “leftmost prefix” folklore should not be generalized from B-tree to every access method.[4]

Keep multicolumn indexes purposeful. PostgreSQL's documentation recommends using them sparingly and notes that indexes with more than three key columns are unlikely to help unless the workload is highly stylized.[4]

12. PostgreSQL 18 B-tree skip scan

PostgreSQL 18 added broader B-tree skip-scan support. When useful restrictions exist on later index columns but an earlier column lacks an equality condition, the planner can sometimes perform repeated index searches over distinct values/groups of the earlier key rather than scan the entire index. Whether this is profitable depends strongly on the number of distinct leading values and the selectivity of later conditions.[4][23]

CREATE INDEX people_region_email_idx
ON app.person(region, email);

-- PostgreSQL 18 may use skip scan when region has
-- relatively few distinct values:
SELECT *
FROM app.person
WHERE email = 'alice@example.com';
index order: (region, email) APAC: a... b... alice... EU: a... b... alice... US: a... b... alice... skip scan conceptually: search APAC + alice reposition search EU + alice reposition search US + alice instead of reading every entry between groups

Skip scan improves index reuse but does not make column order irrelevant. If the leading column has millions of distinct values, repeated repositioning can be more expensive than another path. Use EXPLAIN against production-like cardinalities instead of assuming PostgreSQL 18 makes every reversed predicate efficient.

13. Unique indexes

Unique indexes enforce uniqueness of the indexed key values. PostgreSQL automatically creates a unique B-tree index for ordinary UNIQUE and PRIMARY KEY constraints, so manually creating a duplicate index on the same key is unnecessary. By default, SQL nulls are considered distinct for unique-index purposes; NULLS NOT DISTINCT requests that nulls compare as equal for uniqueness enforcement.[5][25]

CREATE UNIQUE INDEX account_email_uq
ON auth.account (lower(email))
NULLS NOT DISTINCT;

Only B-tree can currently be declared as an ordinary unique index. Included columns do not participate in uniqueness enforcement: the uniqueness key is formed from key columns only.[5][26]

13.1 Unique constraint versus unique index

ALTER TABLE auth.account
ADD CONSTRAINT account_username_uq
UNIQUE (username);

Use a constraint when uniqueness is part of the logical data model because constraints communicate schema semantics and can be referenced by other features. Use an explicitly created unique index when the uniqueness rule is expression-based or partial, since those forms cannot be expressed as an ordinary simple unique constraint in the same way.

13.2 MVCC uniqueness

Unique-index enforcement is MVCC-aware. Physically duplicated index keys can temporarily refer to different row versions, but PostgreSQL ensures that no valid snapshot can observe two live rows that violate the uniqueness rule.[26]

14. Partial indexes

A partial index stores entries only for rows satisfying its predicate. This can dramatically shrink an index and reduce update overhead when applications repeatedly query a small, stable subset of a much larger table.[6][12]

CREATE INDEX orders_unbilled_customer_idx
ON billing.orders (customer_id, created_at)
WHERE billed IS NOT TRUE;
SELECT *
FROM billing.orders
WHERE billed IS NOT TRUE
  AND customer_id = 42
ORDER BY created_at;

14.1 Planner predicate implication

For PostgreSQL to use a partial index, the query's conditions must imply the index predicate. PostgreSQL recognizes straightforward logical implication patterns, but it is not a general theorem prover. Critically, parameterized clauses can prevent proof at planning time: an index predicate such as x < 2 cannot generally be proven from a generic prepared clause x < $1 for all possible parameter values.[6]

14.2 Partial unique indexes

CREATE UNIQUE INDEX one_active_subscription_per_user
ON billing.subscription(user_id)
WHERE status = 'active';

This enforces uniqueness only within the indexed subset and is a powerful way to encode conditional uniqueness.[12]

14.3 Avoid pseudo-partitioning with many partial indexes

Do not create dozens or hundreds of mutually exclusive partial indexes as a substitute for table partitioning. The planner must reason about each candidate index, and the design becomes hard to maintain. Use declarative partitioning when the logical/storage unit is genuinely partitioned.

15. Expression indexes

An index key can be a scalar expression over table columns. PostgreSQL computes the expression when a row is inserted or when the indexed expression's source columns change, then stores the result in the index. Queries using the same indexable expression can search that precomputed value.[7][12]

CREATE INDEX account_lower_email_idx
ON auth.account (lower(email));

SELECT account_id
FROM auth.account
WHERE lower(email) = lower($1);

15.1 Functions must be immutable

Functions and operators appearing in index expressions or partial-index predicates must be immutable: the result for the same arguments must not depend on time, table contents, configuration or other outside state. Otherwise the stored index key could cease to represent the row correctly.[12]

15.2 Expression indexes and case-insensitive uniqueness

CREATE UNIQUE INDEX account_email_ci_uq
ON auth.account (lower(email));

This is a common technique when normalized/case-folded values should be unique, assuming the chosen normalization semantics are stable and appropriate for the application's locale requirements.

15.3 Cost on writes

Expression evaluation occurs during index maintenance, so a computationally expensive expression can increase insertion and update cost even if reads become faster. Store or generate a normalized column instead when the expression is central to the data model and needs reuse across many constraints/queries.

16. Covering indexes and included columns

INCLUDE stores non-key payload columns in an index. Included columns do not participate in search-key semantics or B-tree ordering and do not affect uniqueness enforcement, but their values can be returned by an index-only scan when all other requirements are met.[8][12]

CREATE INDEX orders_customer_cover_idx
ON app.orders (customer_id, created_at DESC)
INCLUDE (order_id, status, total_amount);
SELECT
    order_id,
    created_at,
    status,
    total_amount
FROM app.orders
WHERE customer_id = 42
ORDER BY created_at DESC
LIMIT 50;

16.1 Key versus payload

B-tree key: (customer_id, created_at DESC) -> searchable -> ordered -> affects tree comparisons INCLUDE payload: (order_id, status, total_amount) -> stored with leaf entry -> not a search key -> can satisfy output for index-only scan

16.2 Wider is not automatically better

Payload columns enlarge the index, increase cache pressure and write cost, and can cause tuple-size-limit failures if entries become too wide. Covering indexes work best when payload columns are relatively narrow and the target query is important enough to justify duplication.[8][18]

17. Index-only scans

An index-only scan can return query results without fetching each matching heap tuple when two conditions hold: the index physically stores all values required by the query, and PostgreSQL can determine MVCC visibility without consulting the heap page. Visibility is checked through the table's visibility map; when a page is marked all-visible, the executor can trust the index entry without a heap visibility visit.[8]

EXPLAIN (ANALYZE, BUFFERS)
SELECT
    order_id,
    created_at,
    total_amount
FROM app.orders
WHERE customer_id = 42
ORDER BY created_at DESC
LIMIT 50;

In an actual index-only plan, Heap Fetches shows how often the executor still had to visit the heap. A covering index on a frequently updated table can have limited benefit because modifications clear all-visible bits until VACUUM re-establishes them.[8]

17.1 Access method capability matters

B-tree indexes always support index-only retrieval of stored values. Whether GiST or SP-GiST can do so depends on the operator class. GIN fundamentally stores component keys rather than complete original values and therefore cannot generally reconstruct arbitrary original column values for index-only scans in the same way.[8]

18. Operator classes and operator families

An index access method alone does not define what a data type means inside that index. An operator class binds a data type to an index method and identifies the operators and support functions that implement the method's required semantics. Operator families group compatible operator classes and can add cross-data-type operators/support routines so the planner understands comparisons across related types.[27]-[29]

index method: B-tree | +-- operator family: integer_ops | +-- int2_ops +-- int4_ops +-- int8_ops | +-- cross-type comparisons/support

18.1 Default versus alternate semantics

CREATE INDEX customer_name_pattern_idx
ON app.customer (name text_pattern_ops);

A data type can have multiple operator classes for the same index method when different index semantics are useful. One class can be marked default; an index definition names a non-default class explicitly when needed.[17][28]

18.2 Why this matters for extensibility

GiST, SP-GiST, GIN and BRIN derive much of their usefulness from operator classes. Their access methods provide generic mechanics while operator classes define domain-specific strategies such as overlap, containment, nearest-neighbor distance, component extraction or block-range summary semantics.[19][22][24]

18.3 Inspect operator classes

SELECT
    am.amname AS method,
    opc.opcname,
    opc.opcintype::regtype AS indexed_type,
    opc.opcdefault
FROM pg_opclass AS opc
JOIN pg_am AS am
  ON am.oid = opc.opcmethod
ORDER BY am.amname, indexed_type::text, opc.opcname;

19. Indexes and ORDER BY

Only B-tree among PostgreSQL's built-in index types directly returns rows in a defined sorted key order. The planner compares scanning an ordered B-tree against retrieving rows another way and performing an explicit sort. For a large fraction of a table, sequential scan plus sort can be cheaper; for ORDER BY ... LIMIT n, a matching B-tree can be especially powerful because execution can stop after the first n qualifying entries.[16]

CREATE INDEX feed_tenant_time_idx
ON social.feed_item (
    tenant_id,
    published_at DESC,
    item_id DESC
);

SELECT *
FROM social.feed_item
WHERE tenant_id = 9
ORDER BY published_at DESC, item_id DESC
LIMIT 25;

19.1 Mixed directions

CREATE INDEX ranking_idx
ON scoring.result (
    competition_id ASC,
    score DESC,
    participant_id ASC
);

A multicolumn index with explicitly mixed directions can satisfy an ordering that cannot be obtained simply by reversing a uniformly ascending index.[16]

20. Combining multiple indexes

PostgreSQL can combine index results through bitmap operations such as BitmapAnd and BitmapOr. This lets independent single-column indexes jointly serve some AND/OR predicates, although bitmap heap access loses the individual index's ordering and adds bitmap construction/recheck work.[30]

CREATE INDEX orders_status_idx
ON app.orders(status);

CREATE INDEX orders_created_idx
ON app.orders(created_at);

EXPLAIN
SELECT *
FROM app.orders
WHERE status = 'open'
  AND created_at >= current_date - 7;

A multicolumn index can still be better when the combination is frequent, highly selective, or needs key order for ORDER BY. Bitmap combination is valuable flexibility, not evidence that every multicolumn index is redundant.[30]

21. Selectivity and cardinality

Selectivity is the estimated fraction of input rows satisfying a predicate; cardinality is the resulting estimated number of rows. PostgreSQL's planner derives these values from statistics collected by ANALYZE, including null fractions, distinct counts, most-common values, histograms, and optional extended statistics. The resulting row estimate is a major determinant of whether index access appears cheaper than scanning.[13]-[15]

10,000,000 rows | WHERE tenant_id = 7 estimated selectivity 0.001 | v ~10,000 candidate rows | +-- index access may be attractive WHERE active = true estimated selectivity 0.97 | v ~9,700,000 candidate rows | +-- sequential scan often more attractive

21.1 Cardinality is not the same as selectivity

A column can have only two distinct values yet still be a good index candidate if one value is extremely rare and frequently queried. Conversely, a unique column is highly selective but may not justify an index if no workload queries or joins on it and no uniqueness constraint is needed.

21.2 Statistics must match expression/query semantics

If a query filters on an expression or correlated column combination, ordinary per-column statistics may misestimate it. Expression statistics, higher statistics targets or extended statistics can improve planner evidence; otherwise a perfectly good index can remain unused because the optimizer believes the predicate is unselective.[13][15]

22. Index design principles

22.1 Start from query shapes

List recurring predicates, joins, ordering/grouping requirements and projected columns before creating indexes. The index key should encode the access path the query needs, not simply mirror the table schema.

22.2 Equality, then range, then ordering—when that matches the workload

For many multicolumn B-tree queries, a useful pattern is equality-constrained keys first, then a range/order key. This follows how B-tree narrows contiguous ranges. It is a pattern, not a universal formula: skip scan, multiple query families and desired output order can change the best sequence.[4][16]

22.3 Prefer one index that serves a query family

-- Query family:
WHERE tenant_id = $1
  AND customer_id = $2
ORDER BY created_at DESC
LIMIT 50

-- Strong candidate:
CREATE INDEX orders_lookup_idx
ON app.orders(
    tenant_id,
    customer_id,
    created_at DESC
)
INCLUDE(order_id, status, total_amount);

This can be more valuable than three independent indexes because it constrains the exact ordered key range and may cover output. But if each column is also independently searched by important queries, additional indexes can still be justified.

22.4 Keep index predicates stable

Partial-index predicates should represent durable categories such as deleted_at IS NULL or state='open', not sliding time windows like “last 30 days” based on now(), which is not immutable and is therefore invalid in an index definition.[12]

23. Read/write tradeoffs

Every index must be maintained when relevant rows are inserted, deleted or updated. Maintenance can include computing expressions, extracting GIN component keys, updating tree pages or block-range summaries, checking uniqueness, generating WAL, dirtying additional buffers, and later vacuuming dead index entries. Larger index portfolios therefore increase write latency and storage even if many indexes are never chosen for reads.[1][9]

BenefitCost
Faster selective readsInsert/update/delete index maintenance
Avoided sort via B-tree orderLarger disk/cache working set

Specialized JSON/text/spatial searchPotentially high GIN/GiST maintenance cost

23.1 Write amplification is workload-specific

Updating a column not referenced by any index can sometimes be cheap enough to remain HOT. Updating an indexed key normally requires new index entries. GIN can require several key insertions for one row because one indexed value can decompose into many components.[9][10]

24. Indexes and HOT updates

Heap-only tuple (HOT) updates allow PostgreSQL to create a new row version on the same heap page without creating new ordinary index entries when the update does not modify indexed attributes and enough same-page space exists. Consequently, indexing a frequently updated column can disable HOT for updates that change that column and increase write amplification.[10]

SELECT
    relname,
    n_tup_upd,
    n_tup_hot_upd,
    round(
        100.0 * n_tup_hot_upd
        / NULLIF(n_tup_upd, 0),
        2
    ) AS hot_pct
FROM pg_stat_user_tables
WHERE n_tup_upd > 0
ORDER BY hot_pct;

PostgreSQL's index access-method interface distinguishes summarizing indexes such as BRIN: because they summarize blocks rather than point to every individual tuple, some changes can remain HOT-compatible in ways ordinary tuple-pointing indexes cannot, although index-predicate columns still matter.[31]

25. Index maintenance

VACUUM removes or marks reclaimable dead index entries as part of normal MVCC maintenance, while each access method manages reusable pages according to its implementation. Indexes can still become physically inefficient after sustained churn. PostgreSQL specifically documents B-tree patterns where pages become sparsely populated but remain allocated, making periodic REINDEX worthwhile in some workloads.[32]

25.1 REINDEX

REINDEX INDEX app.orders_customer_idx;

A standard rebuild takes stronger locks. In production, concurrent rebuilding is often preferable where supported.[32][33]

25.2 B-tree fillfactor

CREATE INDEX orders_created_idx
ON app.orders(created_at)
WITH (fillfactor = 80);

B-tree fillfactor controls initial leaf-page fullness. Lower values reserve room for future insertions/updates and can reduce page splits for some insertion patterns, at the cost of a larger initial index. The best setting depends on key distribution and write behavior.[12]

25.3 GIN maintenance

GIN's pending-list fast-update path changes the shape of maintenance: inserts can first accumulate pending entries and later merge them into the main GIN structure. Monitor index size, write behavior and VACUUM/autovacuum rather than treating GIN like a scalar B-tree.[22]

25.4 BRIN summarization

BRIN ranges may need summarization after new pages are populated. PostgreSQL exposes BRIN maintenance functions such as brin_summarize_new_values(), brin_summarize_range(), and brin_desummarize_range() for specialized maintenance/diagnosis.[34]

26. Concurrent index builds and rebuilds

A normal CREATE INDEX permits reads but blocks writes to the target table while the build runs. CREATE INDEX CONCURRENTLY performs more work and takes longer, including multiple table scans and transaction waits, but allows normal inserts, updates and deletes to continue for most of the build. It is therefore often required for large production tables.[12]

CREATE INDEX CONCURRENTLY orders_customer_idx
ON app.orders(customer_id);

If a concurrent build fails, PostgreSQL can leave an invalid index behind. The planner will not use the incomplete index, but the invalid structure can still impose update overhead; drop it or rebuild it rather than ignoring it.[12]

26.1 Rebuild concurrently

REINDEX INDEX CONCURRENTLY
app.orders_customer_idx;

Concurrent REINDEX reduces write blocking compared with ordinary REINDEX, but it requires additional work/time and has operational restrictions. Use it when maintaining production availability is more important than the fastest possible rebuild.[32][33]

27. Monitoring index usage

PostgreSQL explicitly recommends examining index usage against the real workload rather than assuming that every created index is useful. Start with current statistics and production-representative data, then inspect individual plans with EXPLAIN/EXPLAIN ANALYZE and aggregate usage with the cumulative statistics views.[35]

27.1 Index-level usage statistics

SELECT
    schemaname,
    relname AS table_name,
    indexrelname AS index_name,
    idx_scan,
    last_idx_scan,
    idx_tup_read,
    idx_tup_fetch,
    pg_size_pretty(
        pg_relation_size(indexrelid)
    ) AS index_size
FROM pg_stat_user_indexes
ORDER BY idx_scan ASC, pg_relation_size(indexrelid) DESC;

idx_scan counts index searches rather than necessarily one executor node per query; PostgreSQL 18 skip scan and some multi-value search patterns can perform several index searches during one scan node. idx_tup_read counts index entries returned, while idx_tup_fetch counts live heap rows fetched by simple index scans and can be smaller because of dead tuples or index-only scans.[36]

27.2 Usage counts are evidence, not deletion commands

An index with zero scans might still be critical for a unique constraint, a rarely executed incident/reconciliation query, foreign-key-related application paths, seasonal reports, or a newly deployed query. Statistics reset events and server restarts also change the observation window. Before dropping an index, inspect dependencies, constraints, query history and a sufficiently long workload period.

27.3 Workload-level query statistics

SELECT
    queryid,
    calls,
    mean_exec_time,
    total_exec_time,
    rows,
    query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 25;

The supplied pg_stat_statements extension tracks normalized planning/execution statistics for query shapes, making it useful for identifying the queries whose cumulative latency justifies index work. It requires server-side loading and per-database extension installation.[37]

27.4 Verify with EXPLAIN

EXPLAIN (
    ANALYZE,
    BUFFERS,
    SETTINGS,
    TIMING OFF
)
SELECT ...;

Use estimated-versus-actual cardinalities and buffer activity to determine whether the index solves the intended problem. If the index is never chosen, PostgreSQL's documentation recommends checking ANALYZE/statistics first, then experimentally comparing alternative plan types rather than immediately forcing index usage.[35][38]

28. Over-indexing

Over-indexing means maintaining more or wider index structures than the workload justifies. It is especially common when teams add one index per slow-query incident without periodically consolidating overlapping structures. PostgreSQL does not automatically merge or drop redundant indexes because apparently overlapping indexes can have different ordering, predicates, operator classes, included payloads, uniqueness semantics or workload roles.

28.1 Common redundancy pattern

-- Existing:
CREATE INDEX orders_tenant_idx
ON app.orders(tenant_id);

CREATE INDEX orders_tenant_customer_idx
ON app.orders(tenant_id, customer_id);

CREATE INDEX orders_tenant_customer_created_idx
ON app.orders(tenant_id, customer_id, created_at DESC);

For B-tree, the longer indexes can often support predicates on their leading subsets, which may make a shorter index redundant. But smaller indexes can be cheaper to scan/cache and might support different workloads better. Test actual plans and usage before consolidation.[4]

28.2 Costs of excess indexes

Cost areaEffect of more indexes
INSERTEvery relevant index receives a new entry.
UPDATEChanged indexed attributes generate index maintenance and can prevent HOT.
DELETEDead index entries remain until maintenance/reuse.
WALIndex changes generate additional logged modifications.
Buffer/cacheLarger total index footprint competes for memory/cache residency.
VACUUMMore indexes create more cleanup work.
Backup/replicationLarger physical database affects backups and physical-replication/storage volume.
DDLSchema migrations/builds/rebuilds take longer and require more space.

28.3 Duplicate constraint indexes

A primary key or unique constraint already creates its enforcing unique index. Creating a second ordinary index on exactly the same key is usually pure duplication.[5][25]

29. Query-driven indexing

Query-driven indexing starts with the workload rather than the schema. PostgreSQL's own index-usage guidance recommends real data, current ANALYZE statistics, experimentation and measured plans because small synthetic datasets and unrealistic distributions can make the planner choose entirely different access paths.[35]

1. Observe workload pg_stat_statements / traces / slow queries | v 2. Identify expensive recurring query family | v 3. Inspect EXPLAIN ANALYZE predicates, joins, ordering, rows, buffers | v 4. Design candidate index type + keys + order + predicate + INCLUDE | v 5. Test on realistic cardinality/distribution | v 6. Measure read improvement + write/storage cost | v 7. Deploy (CONCURRENTLY if needed) | v 8. Re-measure and prune obsolete indexes

29.1 Normalize query families

Index for recurring shapes such as “tenant + customer + newest 50,” not for one literal execution. Parameterized application SQL, normalized query IDs and repeated workload observations help reveal these stable families.

29.2 Design from predicates inward

For each high-value query, classify conditions into exact equality, range, membership/containment, spatial/distance, prefix text, full-text, ordering, and output payload. That classification usually reveals both the appropriate access method and key order.

29.3 Validate planner estimates

If actual rows differ dramatically from estimates, an index change may not be the first fix. Improve statistics or extended statistics so PostgreSQL can price existing and candidate indexes correctly.[13][15]

29.4 Measure the write side

Benchmark inserts/updates at representative concurrency after adding an index. A 10× faster dashboard query may be a poor trade if the index makes the primary write path 2× slower and the dashboard runs once per hour; the reverse may also be true.

30. Index design patterns

30.1 Tenant-scoped newest-first lookup

CREATE INDEX event_tenant_created_idx
ON app.event(
    tenant_id,
    created_at DESC,
    event_id DESC
)
INCLUDE(event_type);

Supports tenant equality plus stable newest-first pagination. The final unique-ish tie-breaker produces deterministic keyset ordering, and the included type can help covering reads.

30.2 Soft-delete active-row index

CREATE INDEX customer_active_email_idx
ON app.customer(lower(email))
WHERE deleted_at IS NULL;

Useful when most historical/deleted rows are rarely queried and active records dominate lookup traffic. The query must contain a condition that allows the planner to prove the partial predicate.[6]

30.3 Conditional uniqueness

CREATE UNIQUE INDEX team_one_primary_owner
ON app.team_member(team_id)
WHERE role = 'owner'
  AND is_primary;

30.4 JSONB containment

CREATE INDEX asset_metadata_gin
ON asset.item
USING gin(metadata);

SELECT *
FROM asset.item
WHERE metadata @> '{"color":"blue"}'::jsonb;

GIN is usually the natural starting point when searching component values inside JSONB, though the exact JSONB operator class should be chosen around the operators the workload actually uses.[2][22]

30.5 Time-series BRIN

CREATE INDEX metrics_time_brin
ON metrics.sample
USING brin(sample_time);

Strong candidate when rows arrive approximately in timestamp order and the table is enormous. Compare index size and heap blocks visited against a B-tree for the actual time-window workload.

30.6 Range overlap with GiST

CREATE INDEX booking_period_gist
ON scheduling.booking
USING gist(period);

SELECT *
FROM scheduling.booking
WHERE period && tstzrange($start, $end, '[)');

30.7 Queue partial B-tree

CREATE INDEX job_ready_idx
ON queue.job(priority DESC, job_id)
WHERE state = 'ready';

A small partial index can make FOR UPDATE SKIP LOCKED worker claims efficient when only a small fraction of all historical jobs remain ready.

30.8 Case-insensitive exact lookup

CREATE UNIQUE INDEX user_email_lower_uq
ON auth.user_account(lower(email));

31. Common pitfalls

31.1 Indexing every foreign-key column “because it is a foreign key”

PostgreSQL automatically indexes the referenced side of a primary/unique key, but it does not automatically create an index on each referencing foreign-key column. A referencing-side index is often valuable for joins and parent deletes/updates, but should still reflect actual workload and constraint-maintenance needs rather than a reflexive rule.[25]

31.2 Putting range columns before equality columns by “selectivity”

In a multicolumn B-tree, leading equality conditions usually narrow the searchable range more effectively than putting a frequently ranged column first. Design around B-tree search semantics and query order, not a single distinct-count ranking.[4]

31.3 Assuming PostgreSQL can always use a partial index with parameters

Parameterized predicates may not imply a partial-index predicate at planning time because a generic parameter can take values for which the implication is false.[6]

31.4 Making every index covering

INCLUDE columns enlarge leaf entries, indexes, writes and cache footprint. Index-only scans also depend on visibility-map state, so volatile tables may still perform heap fetches.[8]

31.5 Expecting GIN to behave like B-tree

GIN is an inverted index whose values can generate many keys. It has different build/write/maintenance characteristics and does not provide B-tree ordering.[22]

31.6 Using BRIN without physical correlation

BRIN summarizes block ranges. If each range contains nearly the entire logical value domain, few ranges can be excluded and the index provides little pruning.[24]

31.7 Rebuilding indexes on a calendar without evidence

B-tree indexes can sometimes become inefficiently sparse, but REINDEX consumes I/O, disk and locking/concurrent-build resources. Monitor physical size and workload performance rather than scheduling universal weekly rebuilds.[32]

31.8 Dropping an “unused” index after a short statistics window

Usage statistics may have been reset, and rare business-critical queries can be absent from a short observation period. Check constraints, dependencies, historical query data and deployment timing first.[35][36]

31.9 Forcing index scans instead of fixing estimates

Disabling sequential scans is useful as a diagnostic experiment, but PostgreSQL recommends first checking real data and ANALYZE statistics. If the forced index is genuinely faster, investigate selectivity/cost estimates rather than permanently disabling a plan type.[35]

31.10 Assuming a multicolumn index replaces all prefix indexes

The longer B-tree can often serve leading-prefix queries, but it is physically larger and can be more expensive to scan/cache. Keep or drop the shorter index based on measured query and write behavior.

32. Production checklist

  1. Start with query shapes, not columns.
  2. Use B-tree by default for scalar equality/range/order workloads.
  3. Use Hash only for a measured equality-specific reason.
  4. Use GiST/SP-GiST when the operator class matches spatial, range, nearest-neighbor or partitioned-search semantics.
  5. Use GIN for multi-component values such as arrays, JSONB and full-text search.
  6. Use BRIN for very large physically correlated tables.
  7. Order multicolumn B-tree keys around equality, range and ordering semantics.
  8. Remember PostgreSQL 18 skip scan, but do not use it as an excuse for careless key order.
  9. Use unique constraints/indexes to enforce real invariants.
  10. Use partial indexes for stable, frequently queried subsets.
  11. Use expression indexes only with immutable semantics.
  12. Add INCLUDE payload only when index-only access has meaningful value.
  13. Inspect Heap Fetches before assuming a covering index is truly index-only.
  14. Understand the operator class behind specialized behavior.
  15. Keep ANALYZE statistics current.
  16. Validate selectivity/cardinality estimates with EXPLAIN ANALYZE.
  17. Measure write amplification and HOT impact after adding indexes.
  18. Use CREATE INDEX CONCURRENTLY for production builds where write availability is required.
  19. Monitor invalid concurrent builds and remove/rebuild them.
  20. Use REINDEX because evidence justifies it, not because a calendar says so.
  21. Observe pg_stat_user_indexes across a representative workload window.
  22. Use pg_stat_statements to prioritize index work by real query cost.
  23. Periodically look for overlapping and duplicate indexes.
  24. Retest after PostgreSQL upgrades. Planner and access-method capabilities evolve; PostgreSQL 18's B-tree skip scan and parallel GIN builds are examples.
Index design principle: an index is a physical implementation of a query-access contract. Choose the smallest structure that makes an important, recurring query family cheap enough—then verify that its read benefit exceeds its permanent write, storage, cache and maintenance cost.
