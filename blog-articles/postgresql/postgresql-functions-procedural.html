PostgreSQL Functions & Procedural Programming

A technical guide to SQL functions, PL/pgSQL, procedures, variables, control flow, loops, exception handling, dynamic SQL, cursors, volatility categories, planner contracts, transaction management, and secure SECURITY DEFINER design.

Technical article • PostgreSQL 18.6 baseline • Updated 15 September 2026 • Vancouver-style references

Abstract

PostgreSQL supports database-resident programming at several levels. Simple logic can be expressed as SQL-language functions. More procedural logic can be implemented with PL/pgSQL, which adds variables, blocks, conditionals, loops, exception handling, dynamic SQL, and cursors. Procedures, invoked with CALL, are distinct from functions and can perform transaction control in specific top-level call contexts. PostgreSQL also supports additional procedural languages such as PL/Python, PL/Perl, and PL/Tcl, as well as C-language functions for lower-level extension work.[1]-[4]

Server-side programming is tightly integrated with the PostgreSQL optimizer and security model. Function attributes such as IMMUTABLE, STABLE, VOLATILE, STRICT, execution cost, parallel safety, and SECURITY DEFINER are not documentation-only annotations; they alter planning, snapshot visibility, invocation frequency, and privilege boundaries. Correct classification is therefore part of correctness, not merely performance tuning.[5][6]

1. PostgreSQL's server-side programming model

PostgreSQL supports user-defined functions written in SQL, procedural languages, internal server functions, and C. Procedural languages are implemented through language handlers loaded by PostgreSQL. The standard distribution includes PL/pgSQL, PL/Tcl, PL/Perl, and PL/Python, while additional languages can be supplied by extensions.[1][7]

application SQL | v PostgreSQL parser / analyzer / planner | +---------------------+ | | v v SQL function PL/pgSQL function/procedure | | | +--> variables / control flow | +--> static SQL | +--> EXECUTE dynamic SQL | +--> cursors | +--> exception blocks | +-----------> PostgreSQL executor | v tables / indexes / MVCC

Functions are expressions from SQL's point of view: they have a return type and may be invoked in expressions, queries, indexes, generated expressions subject to restrictions, and other database objects. Procedures are invoked with CALL and do not participate as ordinary SQL expression values. Their main semantic distinction is that procedures can perform transaction control when invoked in the permitted context.[2][8]

2. SQL functions

SQL-language functions execute SQL statements and return a value or set of values according to the declared return type. In the classic string-body form, a function body can contain multiple SQL statements and returns the result of the final query; the final statement must produce a value compatible with the function's declared return type unless the function returns void. SQL functions cannot use transaction-control commands such as COMMIT or SAVEPOINT.[2]

2.1 Scalar SQL function

CREATE FUNCTION app.net_price(
    gross numeric,
    discount_rate numeric
)
RETURNS numeric
LANGUAGE SQL
IMMUTABLE
STRICT
PARALLEL SAFE
RETURN gross * (1 - discount_rate);
SELECT app.net_price(125.00, 0.15);
-- 106.2500

The RETURN expression SQL-function form is concise for a single expression. STRICT is shorthand for RETURNS NULL ON NULL INPUT, allowing PostgreSQL to return null without invoking the function whenever any argument is null. IMMUTABLE and PARALLEL SAFE are valid here because this function depends only on its arguments and has no side effects.[5]

2.2 Table-reading SQL function

CREATE FUNCTION app.customer_order_total(p_customer_id bigint)
RETURNS numeric
LANGUAGE SQL
STABLE
AS $$
    SELECT COALESCE(sum(o.total), 0)
    FROM app.orders AS o
    WHERE o.customer_id = p_customer_id;
$$;

A function that reads database tables should generally not be labeled IMMUTABLE because its result can change as table contents change. STABLE is appropriate when the function performs reads and returns a value that is consistent for the same arguments throughout one statement snapshot.[9]

2.3 Data-modifying SQL function

CREATE FUNCTION app.close_order(p_order_id bigint)
RETURNS app.orders
LANGUAGE SQL
VOLATILE
AS $$
    UPDATE app.orders
    SET status = 'closed',
        closed_at = statement_timestamp()
    WHERE order_id = p_order_id
    RETURNING *;
$$;

A function that changes database state must be marked VOLATILE. VOLATILE is PostgreSQL's default if no volatility category is specified.[5][9]

3. Arguments, output parameters, sets, and table functions

PostgreSQL functions can accept base, composite, array, domain, range, polymorphic, and other supported SQL types. They can return one scalar value, a composite row, SETOF a type, output parameters, or RETURNS TABLE. Named arguments can be called positionally, by name, or with mixed notation subject to PostgreSQL's argument rules.[1][10]

3.1 Named and default arguments

CREATE FUNCTION app.calculate_tax(
    subtotal numeric,
    tax_rate numeric DEFAULT 0.07
)
RETURNS numeric
LANGUAGE SQL
IMMUTABLE
STRICT
RETURN subtotal * tax_rate;
SELECT app.calculate_tax(100);
SELECT app.calculate_tax(
    tax_rate => 0.0825,
    subtotal => 100
);

3.2 RETURNS TABLE

CREATE FUNCTION app.recent_orders(
    p_customer_id bigint,
    p_limit integer DEFAULT 20
)
RETURNS TABLE (
    order_id bigint,
    created_at timestamptz,
    total numeric
)
LANGUAGE SQL
STABLE
AS $$
    SELECT
        o.order_id,
        o.created_at,
        o.total
    FROM app.orders AS o
    WHERE o.customer_id = p_customer_id
    ORDER BY o.created_at DESC
    LIMIT p_limit;
$$;
SELECT *
FROM app.recent_orders(42, 10);

RETURNS TABLE is effectively a set-returning function with named output columns. SQL functions returning sets return all rows from the final query rather than only the first row.[2]

3.3 Output parameters

CREATE FUNCTION app.order_stats(
    p_customer_id bigint,
    OUT order_count bigint,
    OUT order_total numeric
)
LANGUAGE SQL
STABLE
AS $$
    SELECT
        count(*),
        COALESCE(sum(total), 0)
    FROM app.orders
    WHERE customer_id = p_customer_id;
$$;
SELECT *
FROM app.order_stats(42);

4. PL/pgSQL

PL/pgSQL is PostgreSQL's built-in SQL procedural language. A PL/pgSQL routine consists of blocks containing an optional label, an optional DECLARE section, a BEGIN/END body, and an optional EXCEPTION section. Blocks can be nested, which provides lexical scope for variables and supports localized exception handling.[11]

4.1 Basic function

CREATE OR REPLACE FUNCTION app.account_status(
    p_balance numeric,
    p_credit_limit numeric
)
RETURNS text
LANGUAGE plpgsql
IMMUTABLE
STRICT
AS $$
BEGIN
    IF p_balance < 0 THEN
        RETURN 'credit';

    ELSIF p_balance > p_credit_limit THEN
        RETURN 'over-limit';

    ELSE
        RETURN 'normal';
    END IF;
END;
$$;

4.2 PL/pgSQL still executes SQL through PostgreSQL

PL/pgSQL expressions and static SQL statements are processed by PostgreSQL's SQL engine. Variables used inside optimizable statements are converted to query parameters, and PL/pgSQL can cache and reuse execution plans. This means PL/pgSQL is not a separate query engine layered over PostgreSQL; its SQL statements still use the standard parser, optimizer, executor, indexes, MVCC, and privileges.[12][13]

5. Variables and declarations

PL/pgSQL variables are declared in a block's DECLARE section and can use SQL data types. PostgreSQL provides %TYPE to copy the type of a table column or other variable and %ROWTYPE to declare a row matching a table or composite type. Record variables can adapt dynamically to query row structures.[14] 

CREATE FUNCTION app.describe_customer(p_customer_id bigint)
RETURNS text
LANGUAGE plpgsql
STABLE
AS $$
DECLARE
    v_customer app.customer%ROWTYPE;
    v_order_count bigint := 0;
    v_total app.orders.total%TYPE;
    v_summary text;
BEGIN
    SELECT *
    INTO STRICT v_customer
    FROM app.customer
    WHERE customer_id = p_customer_id;

    SELECT
        count(*),
        COALESCE(sum(total), 0)
    INTO
        v_order_count,
        v_total
    FROM app.orders
    WHERE customer_id = p_customer_id;

    v_summary :=
        format(
            '%s: %s orders, total %s',
            v_customer.display_name,
            v_order_count,
            v_total
        );

    RETURN v_summary;
END;
$$;

5.1 Constants and defaults

DECLARE
    c_max_attempts CONSTANT integer := 5;
    v_attempt integer := 0;
    v_started_at timestamptz := clock_timestamp();

PL/pgSQL declarations can initialize variables with expressions. Initialization occurs each time control enters the block, not at function-definition time.[14]

5.2 Scope and labels

CREATE FUNCTION app.scope_demo()
RETURNS integer
LANGUAGE plpgsql
AS $$
DECLARE
    x integer := 1;
BEGIN
    <<inner_block>>
    DECLARE
        x integer := 2;
    BEGIN
        RAISE NOTICE 'inner x = %', x;
        RAISE NOTICE 'outer x = %', scope_demo.x;
    END;

    RETURN x;
END;
$$;

Nested blocks can shadow outer names. Explicit naming conventions such as p_ for parameters and v_ for local variables reduce ambiguity between PL/pgSQL variables and SQL column names.[11][13]

6. Executing SQL inside PL/pgSQL

6.1 Static SQL

UPDATE app.orders
SET status = 'closed'
WHERE order_id = p_order_id;

Optimizable SQL statements written directly in PL/pgSQL can reference PL/pgSQL variables. PostgreSQL substitutes their values as query parameters and may cache a plan for later executions.[12]

6.2 SELECT ... INTO

SELECT
    status,
    total
INTO
    v_status,
    v_total
FROM app.orders
WHERE order_id = p_order_id;

PL/pgSQL's SELECT ... INTO assigns query output to variables; it is distinct from SQL's table-creating SELECT INTO. Without STRICT, the first row is assigned and zero rows produce nulls. With STRICT, exactly one row is required; otherwise PostgreSQL raises NO_DATA_FOUND or TOO_MANY_ROWS.[12] 

SELECT *
INTO STRICT v_order
FROM app.orders
WHERE order_id = p_order_id;

6.3 FOUND

UPDATE app.orders
SET status = 'closed'
WHERE order_id = p_order_id
  AND status <> 'closed';

IF FOUND THEN
    RAISE NOTICE 'order % closed', p_order_id;
ELSE
    RAISE NOTICE 'order % unchanged or missing', p_order_id;
END IF;

PL/pgSQL maintains a special Boolean variable FOUND for many statements. Its meaning depends on the most recently executed relevant PL/pgSQL statement, so read it immediately when its value matters.[12]

6.4 GET DIAGNOSTICS

UPDATE app.orders
SET status = 'archived'
WHERE created_at < current_date - interval '2 years';

GET DIAGNOSTICS v_rows = ROW_COUNT;

RAISE NOTICE 'archived % rows', v_rows;

7. Control flow

PL/pgSQL provides IF, ELSIF, ELSE, searched and simple CASE, block labels, EXIT, and CONTINUE. These constructs operate around ordinary SQL statements executed by PostgreSQL.[15]

7.1 IF

IF v_balance < 0 THEN
    v_state := 'credit';
ELSIF v_balance = 0 THEN
    v_state := 'empty';
ELSE
    v_state := 'positive';
END IF;

7.2 CASE

CASE v_status
    WHEN 'pending' THEN
        v_priority := 10;
    WHEN 'processing' THEN
        v_priority := 20;
    WHEN 'failed' THEN
        v_priority := 100;
    ELSE
        v_priority := 0;
END CASE;

7.3 Early return

IF p_amount <= 0 THEN
    RETURN false;
END IF;

8. Loops

PL/pgSQL supports unconditional LOOP, WHILE, integer-range FOR, query FOR, array FOREACH, and cursor loops. EXIT leaves a loop or labeled block, while CONTINUE advances to the next iteration.[15]

8.1 Integer loop

FOR i IN 1..10 LOOP
    RAISE DEBUG 'i=%', i;
END LOOP;

8.2 Query loop

FOR v_order IN
    SELECT order_id, total
    FROM app.orders
    WHERE customer_id = p_customer_id
    ORDER BY created_at
LOOP
    v_running_total := v_running_total + v_order.total;
END LOOP;

8.3 Prefer set-based SQL when possible

-- Procedural loop:
FOR v_order IN
    SELECT order_id
    FROM app.orders
    WHERE status = 'pending'
LOOP
    UPDATE app.orders
    SET status = 'expired'
    WHERE order_id = v_order.order_id;
END LOOP;

-- Usually better:
UPDATE app.orders
SET status = 'expired'
WHERE status = 'pending';

A loop is appropriate when each iteration genuinely needs procedural branching or a different operation. When one relational statement expresses the same transformation, set-based SQL generally gives the optimizer more freedom and reduces per-row interpreter and execution overhead.

8.4 FOREACH arrays

FOREACH v_tag IN ARRAY p_tags LOOP
    INSERT INTO app.order_tag(order_id, tag)
    VALUES (p_order_id, v_tag)
    ON CONFLICT DO NOTHING;
END LOOP;

9. Exceptions and error handling

By default, an error inside a PL/pgSQL function aborts the function and propagates outward. A block with an EXCEPTION section catches specified errors. PostgreSQL implements such a block using a subtransaction: when an error is caught, database changes made inside the block are rolled back, while PL/pgSQL variables retain their values as they stood when the error occurred.[15]

9.1 Catch a uniqueness violation

CREATE FUNCTION app.create_customer(
    p_email text,
    p_name text
)
RETURNS bigint
LANGUAGE plpgsql
AS $$
DECLARE
    v_customer_id bigint;
BEGIN
    BEGIN
        INSERT INTO app.customer(email, display_name)
        VALUES (p_email, p_name)
        RETURNING customer_id
        INTO v_customer_id;

    EXCEPTION
        WHEN unique_violation THEN
            SELECT customer_id
            INTO STRICT v_customer_id
            FROM app.customer
            WHERE email = p_email;
    END;

    RETURN v_customer_id;
END;
$$;
Prefer declarative conflict handling when it fits. For ordinary insert conflicts, INSERT ... ON CONFLICT is usually clearer than using exceptions for expected control flow. Exception blocks have additional overhead because they establish subtransaction machinery.[15]

9.2 Raise application errors

IF p_amount <= 0 THEN
    RAISE EXCEPTION
        'amount must be positive: %',
        p_amount
        USING
            ERRCODE = '22023',
            HINT = 'Pass an amount greater than zero.';
END IF;

RAISE supports severity levels DEBUG, LOG, INFO, NOTICE, WARNING, and EXCEPTION. It can assign SQLSTATE codes and structured fields such as DETAIL, HINT, table name, column name, and constraint name.[16]

9.3 Inspect an exception

EXCEPTION
    WHEN OTHERS THEN
        GET STACKED DIAGNOSTICS
            v_sqlstate = RETURNED_SQLSTATE,
            v_message  = MESSAGE_TEXT,
            v_detail   = PG_EXCEPTION_DETAIL,
            v_hint     = PG_EXCEPTION_HINT;

        RAISE LOG
            'operation failed state=% message=% detail=% hint=%',
            v_sqlstate,
            v_message,
            v_detail,
            v_hint;

        RAISE;  -- rethrow original error
END;

10. Dynamic SQL

PL/pgSQL's EXECUTE executes a command constructed at runtime. Unlike static SQL in PL/pgSQL, an EXECUTE command is planned each time it runs rather than using PL/pgSQL's normal plan cache. Dynamic SQL is necessary when identifiers or statement structure vary at runtime, such as changing the target table or column.[12]

10.1 Parameterize values

EXECUTE
    'SELECT count(*) FROM app.orders
     WHERE customer_id = $1
       AND created_at >= $2'
INTO v_count
USING p_customer_id, p_since;

The USING clause binds data values without converting them to SQL text. PostgreSQL's documentation specifically recommends this approach because it avoids quoting problems, unnecessary text conversion, and SQL-injection risk.[12]

10.2 Quote identifiers with format()

CREATE FUNCTION admin.count_rows(
    p_schema name,
    p_table name
)
RETURNS bigint
LANGUAGE plpgsql
AS $$
DECLARE
    v_count bigint;
BEGIN
    EXECUTE format(
        'SELECT count(*) FROM %I.%I',
        p_schema,
        p_table
    )
    INTO v_count;

    RETURN v_count;
END;
$$;

Parameters cannot substitute SQL identifiers. Use format('%I', ...) or quote_ident() for identifiers and USING for values. %L can quote a literal when textual insertion is truly required.[12][17]

10.3 Dynamic DDL

EXECUTE format(
    'CREATE INDEX %I ON %I.%I (%I)',
    p_index_name,
    p_schema,
    p_table,
    p_column
);

Utility commands generally cannot accept query parameters for identifiers or structural elements, so runtime-varying DDL must be constructed as SQL text. Validate authorization and allowed object names before exposing such functionality to untrusted callers.[12]

11. Cursors

PL/pgSQL cursor variables use the refcursor type and represent portal names. Cursors allow incremental retrieval from a query rather than immediately transferring all rows to the client or procedural code. PL/pgSQL supports bound and unbound cursors, explicit OPEN/FETCH/MOVE/CLOSE, and cursor FOR loops.[18]

11.1 Return a cursor to a client

CREATE FUNCTION app.open_customer_orders(
    p_customer_id bigint
)
RETURNS refcursor
LANGUAGE plpgsql
AS $$
DECLARE
    v_cursor refcursor := 'customer_orders';
BEGIN
    OPEN v_cursor FOR
        SELECT
            order_id,
            created_at,
            total
        FROM app.orders
        WHERE customer_id = p_customer_id
        ORDER BY created_at DESC;

    RETURN v_cursor;
END;
$$;
BEGIN;

SELECT app.open_customer_orders(42);

FETCH FORWARD 50 FROM customer_orders;

CLOSE customer_orders;

COMMIT;

A regular cursor exists within a transaction, so callers normally keep the transaction open while fetching. PostgreSQL also converts certain cursor loops in procedures into holdable cursors automatically if the procedure commits during the loop, with important consequences for locking and materialization.[18][19]

11.2 Dynamic cursor

OPEN v_cursor FOR EXECUTE format(
    'SELECT * FROM %I.%I
     WHERE customer_id = $1
     ORDER BY created_at DESC',
    p_schema,
    p_table
)
USING p_customer_id;

11.3 Prefer ordinary queries when streaming is handled by the driver

Many application drivers already provide fetch-size or streaming APIs. Returning a PostgreSQL cursor is most useful when server-side procedural logic itself needs cursor behavior or when a client explicitly wants a named portal protocol. It should not be added solely because a result set is large without considering the driver's normal streaming facilities.

12. Procedures

Procedures are created with CREATE PROCEDURE and invoked with CALL. They can have input and output parameters but do not return values as ordinary SQL expressions. In simple cases, a procedure and a function returning void may look similar, but procedures have distinct transaction-control capabilities and SQL-standard semantics.[2][3]

12.1 Simple procedure

CREATE PROCEDURE app.archive_orders(
    p_before timestamptz
)
LANGUAGE plpgsql
AS $$
BEGIN
    UPDATE app.orders
    SET status = 'archived'
    WHERE created_at < p_before
      AND status = 'closed';
END;
$$;

CALL app.archive_orders(
    current_timestamp - interval '2 years'
);

12.2 Output parameters

CREATE PROCEDURE app.archive_orders(
    p_before timestamptz,
    OUT archived_rows bigint
)
LANGUAGE plpgsql
AS $$
BEGIN
    UPDATE app.orders
    SET status = 'archived'
    WHERE created_at < p_before
      AND status = 'closed';

    GET DIAGNOSTICS archived_rows = ROW_COUNT;
END;
$$;
CALL app.archive_orders(
    current_timestamp - interval '2 years',
    NULL
);

When calling a procedure from ordinary SQL, arguments are supplied for output parameters as required by CALL; PostgreSQL documentation notes that writing NULL is customary for pure OUT parameters.[3][20]

13. Transaction control in procedures

PL/pgSQL procedures invoked with top-level CALL, and anonymous DO blocks invoked at the top level, can execute COMMIT and ROLLBACK. PostgreSQL automatically starts a new transaction after each such transaction-ending command. Transaction control is restricted by call-stack context: nested procedures can do it when the chain consists of CALL/DO invocations without an intervening ordinary SQL command.[19]

13.1 Batch procedure

CREATE PROCEDURE admin.process_work_queue()
LANGUAGE plpgsql
AS $$
DECLARE
    v_job record;
BEGIN
    FOR v_job IN
        SELECT job_id
        FROM admin.work_queue
        WHERE state = 'ready'
        ORDER BY job_id
    LOOP
        UPDATE admin.work_queue
        SET state = 'processed',
            processed_at = clock_timestamp()
        WHERE job_id = v_job.job_id;

        COMMIT AND CHAIN;
    END LOOP;
END;
$$;

COMMIT AND CHAIN starts the next transaction with the same transaction characteristics as the previous transaction. In a cursor loop, the first transaction end can convert the cursor to a holdable cursor, fully evaluating it and releasing locks that its query had held; this must be considered for large or concurrency-sensitive loops.[19]

13.2 Exception blocks and transaction control

PL/pgSQL exception blocks use subtransactions internally. PostgreSQL does not allow ending the transaction with COMMIT or ROLLBACK while such a subtransaction is active. PL/pgSQL also does not expose SQL savepoint commands directly; ordinary savepoint-style recovery is represented by nested blocks with exception handlers.[19]

Functions cannot commit. If a workflow needs multiple independently committed units of work, use a top-level procedure or move transaction orchestration to the client. Do not attempt to hide transaction boundaries inside an ordinary function.

14. Function volatility: IMMUTABLE, STABLE, and VOLATILE

Every PostgreSQL function has a volatility classification. It is a contract with the optimizer about how results and side effects behave. If omitted, the default is VOLATILE. PostgreSQL recommends selecting the strictest category that is actually valid.[9]

CategoryPromiseTypical examplesPlanner consequence
IMMUTABLE Same arguments produce the same result indefinitely; no database modification. Pure arithmetic, deterministic parsing independent of session settings. Constant calls can be folded during planning.
STABLE Same arguments produce the same result within one statement; no database modification. Table lookups, current_timestamp, functions depending on session configuration. Can be reused within a scan and used in index scan conditions.
VOLATILE Result may change between calls; side effects permitted. random(), sequence operations, data-modifying functions. Must be evaluated where required; optimizer cannot assume repeatability.

14.1 Immutable example

CREATE FUNCTION app.celsius_to_fahrenheit(c numeric)
RETURNS numeric
LANGUAGE SQL
IMMUTABLE
STRICT
PARALLEL SAFE
RETURN (c * 9 / 5) + 32;

14.2 Stable example

CREATE FUNCTION app.product_price(p_product_id bigint)
RETURNS numeric
LANGUAGE SQL
STABLE
AS $$
    SELECT price
    FROM app.product
    WHERE product_id = p_product_id;
$$;

14.3 Volatile example

CREATE FUNCTION app.next_external_id()
RETURNS bigint
LANGUAGE SQL
VOLATILE
AS $$
    SELECT nextval('app.external_id_seq');
$$;

14.4 Snapshot semantics

For SQL and standard procedural-language functions, volatility also affects snapshot visibility. STABLE and IMMUTABLE functions use the calling query's established snapshot, while VOLATILE functions obtain a fresh snapshot for each SQL query they execute. This is why a supposedly stable function should not be used to observe changes made earlier by the same calling command.[9]

14.5 The danger of false immutability

-- Incorrect if result depends on TimeZone.
CREATE FUNCTION app.bad_local_date(ts timestamptz)
RETURNS date
LANGUAGE SQL
IMMUTABLE
RETURN ts::date;

A cast from timestamptz to date can depend on the session's TimeZone. PostgreSQL explicitly warns that functions depending on configuration parameters should not be labeled immutable. Mislabeling can cause a value to be folded into a prepared/cached plan and then reused after the environment changes.[9]

15. Parallel safety, strictness, cost, and row estimates

Volatility is not the same as parallel safety. User-defined functions are PARALLEL UNSAFE by default. Authors may mark a function PARALLEL SAFE if it can execute safely in parallel worker processes, or PARALLEL RESTRICTED if it may run only in the parallel group leader.[5][21]

15.1 Parallel safety

CREATE FUNCTION app.square(x numeric)
RETURNS numeric
LANGUAGE SQL
IMMUTABLE
STRICT
PARALLEL SAFE
RETURN x * x;

Functions that modify database state, alter transaction state, access sequences, or persistently modify settings must be marked parallel unsafe. Functions using temporary tables, cursors, prepared statements, or other backend-local state are generally parallel restricted. Incorrectly marking a function safe can lead to errors or incorrect behavior in parallel plans.[5]

15.2 Function cost

CREATE FUNCTION app.expensive_score(p jsonb)
RETURNS numeric
LANGUAGE plpgsql
IMMUTABLE
PARALLEL SAFE
COST 500
AS $$
BEGIN
    -- Expensive deterministic computation...
    RETURN 0;
END;
$$;

COST tells the optimizer the estimated execution cost relative to cpu_operator_cost. PostgreSQL's default is 1 for C/internal functions and 100 for other languages. A realistic cost can influence join order and how often the planner is willing to invoke a function.[5]

15.3 Set-returning row estimate

CREATE FUNCTION app.customer_recent_orders(
    p_customer_id bigint
)
RETURNS SETOF app.orders
LANGUAGE SQL
STABLE
ROWS 20
AS $$
    SELECT *
    FROM app.orders
    WHERE customer_id = p_customer_id
    ORDER BY created_at DESC
    LIMIT 20;
$$;

For set-returning functions, ROWS provides the planner with an expected result cardinality. The default estimate is 1000 rows if no value is supplied.[5]

16. SECURITY DEFINER functions

Functions run as SECURITY INVOKER by default, meaning object access is checked using the privileges of the calling user. SECURITY DEFINER instead executes the function with the privileges of its owner. This can create a narrow capability API around protected tables, but it also creates a privilege-escalation boundary that must be hardened carefully.[5][22]

16.1 Unsafe design

CREATE FUNCTION app_private.lookup_token(p_user_id bigint)
RETURNS text
LANGUAGE SQL
SECURITY DEFINER
AS $$
    SELECT token
    FROM user_token
    WHERE user_id = p_user_id;
$$;

If an untrusted user can create a table, view, operator, or function in a schema earlier on the function's search_path, unqualified object references can resolve to malicious objects. PostgreSQL's documentation specifically warns that the temporary schema is normally writable and searched early unless a safe search_path is fixed.[5][22]

16.2 Hardened design

BEGIN;

CREATE FUNCTION api.lookup_token(p_user_id bigint)
RETURNS text
LANGUAGE SQL
STABLE
SECURITY DEFINER
SET search_path = pg_catalog, app_private, pg_temp
AS $$
    SELECT t.token
    FROM app_private.user_token AS t
    WHERE t.user_id = p_user_id;
$$;

ALTER FUNCTION api.lookup_token(bigint)
OWNER TO token_service_owner;

REVOKE ALL
ON FUNCTION api.lookup_token(bigint)
FROM PUBLIC;

GRANT EXECUTE
ON FUNCTION api.lookup_token(bigint)
TO support_api;

COMMIT;

A secure SECURITY DEFINER function should use a minimally privileged owner, schema-qualify sensitive objects, set a trusted search_path with pg_temp last, and revoke the default PUBLIC execute privilege before selectively granting access. PostgreSQL recommends creating the function and changing privileges in one transaction to avoid a window of public exposure.[5]

16.3 Security-definer procedures

Procedures can also be declared SECURITY DEFINER, but PostgreSQL does not allow transaction-control statements inside a security-definer procedure. A procedure with a SET clause attached to its definition is likewise restricted from transaction control.[3]

17. Practical programming patterns

17.1 Encapsulate one atomic business operation

CREATE FUNCTION app.transfer_credit(
    p_from bigint,
    p_to bigint,
    p_amount numeric
)
RETURNS void
LANGUAGE plpgsql
VOLATILE
AS $$
DECLARE
    v_from_balance numeric;
BEGIN
    IF p_amount <= 0 THEN
        RAISE EXCEPTION 'amount must be positive'
            USING ERRCODE = '22023';
    END IF;

    SELECT balance
    INTO STRICT v_from_balance
    FROM app.account
    WHERE account_id = p_from
    FOR UPDATE;

    IF v_from_balance < p_amount THEN
        RAISE EXCEPTION 'insufficient balance'
            USING ERRCODE = '23514';
    END IF;

    UPDATE app.account
    SET balance = balance - p_amount
    WHERE account_id = p_from;

    UPDATE app.account
    SET balance = balance + p_amount
    WHERE account_id = p_to;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'destination account does not exist';
    END IF;
END;
$$;

The function executes inside the caller's transaction and is atomic with that transaction. It does not independently commit. Row locking through FOR UPDATE can serialize conflicting balance changes under PostgreSQL's normal transaction semantics.[23]

17.2 Use RETURN QUERY for sets

CREATE FUNCTION app.orders_over(
    p_min_total numeric
)
RETURNS TABLE (
    order_id bigint,
    customer_id bigint,
    total numeric
)
LANGUAGE plpgsql
STABLE
AS $$
BEGIN
    RETURN QUERY
    SELECT
        o.order_id,
        o.customer_id,
        o.total
    FROM app.orders AS o
    WHERE o.total > p_min_total;
END;
$$;

17.3 Dynamic set-returning query

CREATE FUNCTION admin.sample_table(
    p_schema name,
    p_table name,
    p_limit integer
)
RETURNS SETOF jsonb
LANGUAGE plpgsql
AS $$
BEGIN
    RETURN QUERY EXECUTE format(
        'SELECT to_jsonb(t)
         FROM %I.%I AS t
         LIMIT $1',
        p_schema,
        p_table
    )
    USING p_limit;
END;
$$;

RETURN QUERY EXECUTE combines set-returning behavior with runtime-generated SQL and supports USING parameters.[15]

17.4 One-off maintenance with DO

DO $$
DECLARE
    r record;
BEGIN
    FOR r IN
        SELECT schemaname, tablename
        FROM pg_tables
        WHERE schemaname = 'staging'
    LOOP
        RAISE NOTICE 'found %.%', r.schemaname, r.tablename;
    END LOOP;
END;
$$ LANGUAGE plpgsql;

DO executes an anonymous code block as though it were the body of a function returning void. It is useful for migrations and ad hoc administrative scripts that do not justify a permanent database routine.[24]

18. Performance and query planning

18.1 Static SQL can reuse plans

PL/pgSQL can cache plans for static SQL and expressions. PostgreSQL chooses between custom and generic cached plans according to its normal prepared-plan strategy. This reduces repeated parsing/planning overhead but means plan behavior can depend on parameter distributions and schema changes.[12][13]

18.2 Dynamic SQL forces replanning

EXECUTE is planned on every execution. This is necessary for varying identifiers and can also be useful when a query's optimal plan depends strongly on current parameter values, but it imposes planning overhead. Do not replace static SQL with dynamic SQL without a concrete reason.[12]

18.3 SQL functions may be easier for the optimizer

For simple relational expressions, an SQL-language function is often preferable to PL/pgSQL because it avoids unnecessary procedural machinery and may be eligible for optimizer transformations such as SQL-function inlining when PostgreSQL's documented conditions are satisfied. Procedural code should be introduced for actual procedural requirements rather than as a default abstraction mechanism.[2]

18.4 Avoid row-by-row work when one query suffices

-- Procedural:
FOR r IN SELECT order_id FROM app.orders WHERE status = 'pending'
LOOP
    UPDATE app.orders
    SET status = 'expired'
    WHERE order_id = r.order_id;
END LOOP;

-- Relational:
UPDATE app.orders
SET status = 'expired'
WHERE status = 'pending';

18.5 Inspect routine metadata

SELECT
    n.nspname AS schema_name,
    p.proname,
    pg_get_function_identity_arguments(p.oid) AS arguments,
    l.lanname AS language,
    p.provolatile,
    p.proparallel,
    p.prosecdef,
    p.proisstrict,
    p.procost,
    p.prorows
FROM pg_proc AS p
JOIN pg_namespace AS n ON n.oid = p.pronamespace
JOIN pg_language AS l ON l.oid = p.prolang
WHERE n.nspname NOT IN ('pg_catalog', 'information_schema')
ORDER BY schema_name, p.proname;

The pg_proc catalog stores routine metadata including volatility, parallel-safety, strictness, security-definer status, estimated cost, and set-return row estimate. Periodic review can catch routines left with defaults that no longer reflect their implementation.[25]

19. Testing, diagnostics, and observability

19.1 Use deterministic test fixtures

Function tests should cover normal results, null behavior, empty result sets, duplicate rows under INTO STRICT, concurrency where rows are locked or modified, exception paths, privilege context, search-path behavior, and any volatility assumptions.

19.2 Development reload loop

CREATE OR REPLACE FUNCTION app.example(...)
RETURNS ...
LANGUAGE plpgsql
AS $$
...
$$;
-- psql:
\i functions.sql
SELECT app.example(...);

PostgreSQL's PL/pgSQL development guidance recommends using CREATE OR REPLACE FUNCTION during iterative development and reloading function-definition files with psql or equivalent tooling.[26]

19.3 Compile/runtime checks

SET plpgsql.extra_warnings = 'all';
SET plpgsql.extra_errors = 'shadowed_variables';

PL/pgSQL provides additional compile-time checks for issues such as shadowed variables and other suspicious constructs. Enabling warnings in CI or development environments can catch errors that are syntactically legal but likely unintended.[26]

19.4 Instrument with messages carefully

RAISE DEBUG
    'processing customer %, batch %',
    p_customer_id,
    v_batch_id;

Message visibility is controlled by PostgreSQL's client and server logging thresholds. Avoid emitting secrets or high-cardinality sensitive values into logs from routines.[16]

19.5 Observe workload-level cost

A function can hide expensive SQL from application source code but not from PostgreSQL execution. Use EXPLAIN, pg_stat_statements, wait events, locks, and application traces to measure routines as part of the complete query path. When a routine contains several SQL statements, investigate the individual statements as well as the outer function call.

20. Production guidelines

ConcernRecommended practice
Simple relational logicPrefer SQL functions over procedural code where possible.
VolatilityUse the strictest valid category, never a more aggressive category for speed alone.
ParallelismMark user-defined functions parallel safe/restricted only after auditing their behavior.
Dynamic SQLUse USING for values and format('%I', ...) for identifiers.
ExceptionsReserve exception blocks for exceptional paths; prefer SQL conflict handling when available.
LoopsPrefer set-based SQL when one statement expresses the operation.
ProceduresUse them when transaction control or procedure semantics are actually required.
Security definerMinimal owner, trusted search_path, revoke PUBLIC execute, grant narrowly.
OwnershipDo not make application runtime roles owners of privileged routines.
Schema changesVersion routine definitions alongside migrations and test dependent objects.

20.1 Review checklist

  1. Language: Is SQL sufficient, or is PL/pgSQL genuinely needed?
  2. Return contract: Are scalar, composite, set, and output-parameter semantics explicit?
  3. Null semantics: Should the function be STRICT?
  4. Volatility: Does the category match database access, session settings, and side effects?
  5. Snapshot behavior: Is the function expected to see changes made by the calling statement?
  6. Parallel safety: Can it really run in a worker?
  7. Plan behavior: Should SQL stay static and cacheable, or is runtime replanning required?
  8. Dynamic SQL: Are identifiers quoted and values parameterized?
  9. Exceptions: Are subtransaction semantics and performance understood?
  10. Transactions: Is transaction control in the client/function/procedure layer where it belongs?
  11. Security: Are owner, search_path, execute grants, and called objects trusted?
  12. Performance: Is procedural row-by-row work replacing a simpler relational statement?
Programming principle: treat a PostgreSQL routine as part of the query planner, transaction engine, and privilege model—not merely as stored application code. The best routine is usually the smallest routine whose semantics PostgreSQL can understand accurately.
