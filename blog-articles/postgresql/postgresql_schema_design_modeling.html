PostgreSQL Schema Design & Modeling

An expert guide to relational modeling in PostgreSQL: entities and relationships, primary/candidate/natural/surrogate keys, normalization through BCNF, deliberate denormalization, declarative constraints, generated and identity columns, sequences, cascading referential actions, exclusion/temporal constraints, and partitioning strategy.

Technical article • PostgreSQL 18.6 baseline • Updated 16 September 2026 • Vancouver-style references

Abstract

Schema design turns domain rules into relations whose rows have stable identities, whose relationships are explicit, and whose invalid states are rejected as close to the data as practical. Relational theory supplies entities, relationships, candidate keys, functional dependencies and normalization; PostgreSQL supplies concrete enforcement mechanisms such as PRIMARY KEY, UNIQUE, NOT NULL, CHECK, FOREIGN KEY, EXCLUDE, generated columns, identity columns and declarative partitioning.[1]-[5]

A candidate key is a minimal set of attributes that uniquely identifies a tuple; the primary key is one candidate key selected as the relation's designated identifier. Other candidate keys should normally still be enforced with UNIQUE and suitable nullability rules. PostgreSQL primary keys imply uniqueness and non-nullability and create an enforcing unique index; foreign keys enforce referential integrity against primary/unique keys.[4][6][7]

Normalization uses functional dependencies to reduce redundancy and modification anomalies. 1NF removes repeating/multivalued groups from the relational representation; 2NF removes partial dependencies of non-prime attributes on composite candidate keys; 3NF removes problematic transitive dependencies; BCNF strengthens the rule so every nontrivial functional dependency has a superkey as determinant. Denormalization should therefore be an explicit performance/operational choice with a consistency mechanism, not an accidental by-product of modeling.[8]-[12]

Partitioning is a physical data-management strategy rather than a normal form. PostgreSQL range, list and hash partitioning splits one logical table into physical partitions and can improve pruning, bulk data removal and locality for very large tables, but poor partition-key choice or excessive partition counts can increase planning and operational complexity.[13]

1. Relational modeling

Relational modeling represents a domain as relations whose tuples describe facts and whose attributes draw values from defined domains/types. Keys identify tuples, foreign keys connect facts across relations, and functional dependencies describe semantic determination between attribute sets. Entity-relationship modeling is commonly used as a conceptual precursor: entity sets become relations and relationship sets become foreign keys or associative relations according to cardinality and attributes.[6][14]

Customer -------- places -------- Order | | | customer_id | order_id | email | created_at | | +----------- 1 : N -------------+ Order -------- contains -------- Product \----------- N : M -----------/ | OrderLine (order_id, product_id, quantity, unit_price)

The key modeling question is the grain of each relation: what exactly does one row mean? Mixing facts with different lifecycles in one table usually creates redundancy or ambiguous update rules.

2. Entities and relationships

A one-to-many relationship is normally represented by a foreign key on the “many” side. A one-to-one relationship can use a foreign key with uniqueness, often making the foreign key itself the primary key of the dependent table. A many-to-many relationship becomes an associative relation, especially when the relationship has attributes of its own.[14][4]

CREATE TABLE commerce.customer (
    customer_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email text NOT NULL UNIQUE,
    display_name text NOT NULL
);

CREATE TABLE commerce.orders (
    order_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id bigint NOT NULL
        REFERENCES commerce.customer(customer_id),
    created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE commerce.order_line (
    order_id bigint NOT NULL
        REFERENCES commerce.orders(order_id) ON DELETE CASCADE,
    product_id bigint NOT NULL
        REFERENCES catalog.product(product_id),
    quantity integer NOT NULL CHECK (quantity > 0),
    unit_price numeric(12,2) NOT NULL CHECK (unit_price >= 0),
    PRIMARY KEY (order_id, product_id)
);

3. Keys and functional dependencies

A superkey is an attribute set that uniquely identifies a tuple. A candidate key is a minimal superkey: no proper subset still uniquely identifies the tuple. If a relation has several candidate keys, one is designated as primary; the others remain alternate candidate keys. Functional dependencies are semantic constraints of the modeled domain, not accidental properties of today's sample rows.[6][15]

Functional dependency X → Y: if two valid tuples agree on X, they must agree on Y.

4. Candidate and primary keys

PostgreSQL PRIMARY KEY combines uniqueness and non-nullability and automatically creates an enforcing unique B-tree index. A table can have only one primary key but can have many other candidate keys represented with UNIQUE plus suitable nullability rules.[4][16]

CREATE TABLE auth.user_account (
    user_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    account_no text NOT NULL UNIQUE,
    email text NOT NULL UNIQUE,
    display_name text NOT NULL
);

Choosing user_id as the primary key does not make account_no or email stop being business candidate keys if the domain requires them to be unique.

5. Natural versus surrogate keys

A natural key uses attributes that already have domain meaning; a surrogate key introduces an identifier primarily for row identity. Candidate-key theory does not require the primary key to be natural, so the decision is architectural. Surrogate keys are often chosen for stability and narrow foreign keys, while natural candidate keys should still be enforced when they express real uniqueness rules.[6][17]

QuestionNatural keySurrogate key
Business meaningYesUsually none
Change riskDepends on business rule stabilityCan be designed immutable
WidthMay be wide/compositeOften compact scalar
Business uniquenessCan enforce directlyStill needs separate UNIQUE on natural candidate key
A surrogate does not normalize a relation. Adding an id column does not remove functional dependencies among the remaining attributes.

6. Normalization

Normalization decomposes relation schemas to reduce redundancy and insertion/update/deletion anomalies using keys and functional dependencies. The goal is to store each independent fact in a relation where its determinant is represented correctly, while preserving the ability to reconstruct the intended information through joins.[8][10]

Enrollment( student_id, student_name, course_id, course_title, instructor_id, instructor_name, grade ) student_id -> student_name course_id -> course_title, instructor_id instructor_id -> instructor_name (student_id, course_id) -> grade

7. First Normal Form (1NF)

Practical 1NF guidance requires single relation values rather than spreadsheet-style repeating groups. Cornell describes the design goal as atomic values, no repeating groups and uniquely identifiable rows. “Atomic” is domain-relative: PostgreSQL arrays, ranges, JSON and composites are still single typed values, so 1NF is not a blanket prohibition on structured types.[8][18]

-- Avoid fixed repeating columns:
CREATE TABLE bad_order (
    order_id bigint PRIMARY KEY,
    product_1 bigint,
    product_2 bigint,
    product_3 bigint
);

-- Model arbitrary cardinality:
CREATE TABLE order_line (
    order_id bigint NOT NULL REFERENCES orders(order_id),
    line_no integer NOT NULL,
    product_id bigint NOT NULL REFERENCES product(product_id),
    PRIMARY KEY (order_id, line_no)
);

8. Second Normal Form (2NF)

A relation is in 2NF when it is in 1NF and every non-prime attribute is fully functionally dependent on every candidate key rather than on only part of a composite key. Partial-dependency problems therefore arise around composite candidate keys.[9][10]

Inventory( warehouse_id, product_id, warehouse_address, quantity ) key: (warehouse_id, product_id) warehouse_id -> warehouse_address violation (warehouse_id, product_id) -> quantity
CREATE TABLE inventory.warehouse (
    warehouse_id bigint PRIMARY KEY,
    address text NOT NULL
);

CREATE TABLE inventory.stock (
    warehouse_id bigint NOT NULL REFERENCES inventory.warehouse,
    product_id bigint NOT NULL REFERENCES catalog.product,
    quantity integer NOT NULL CHECK (quantity >= 0),
    PRIMARY KEY (warehouse_id, product_id)
);

9. Third Normal Form (3NF)

Third Normal Form refines schemas so non-key facts are not stored through inappropriate transitive dependencies. A standard formal definition states that for every nontrivial functional dependency X → A, either X is a superkey or A is a prime attribute (belongs to some candidate key). This allows some dependencies that BCNF rejects, which is why BCNF is strictly stronger.[10][11]

Employee( employee_id, department_id, department_name ) employee_id -> department_id department_id -> department_name therefore: employee_id -> department_name transitively department_name describes Department, not Employee.
CREATE TABLE org.department (
    department_id bigint PRIMARY KEY,
    department_name text NOT NULL UNIQUE
);

CREATE TABLE org.employee (
    employee_id bigint PRIMARY KEY,
    department_id bigint NOT NULL
        REFERENCES org.department(department_id)
);

This decomposition avoids storing the same department name once per employee and makes a department-name change one row update rather than many synchronized updates.

10. Boyce-Codd Normal Form (BCNF)

A relation is in BCNF when every nontrivial functional dependency X → Y has a superkey on the left side. BCNF therefore rejects any non-key determinant, even some cases that satisfy 3NF because the dependent attribute happens to be prime.[11][12]

BCNF: for every nontrivial FD X → Y, X must be a superkey.

BCNF is useful when overlapping candidate keys create subtle redundancy. However, a BCNF decomposition can fail to preserve every functional dependency as a local constraint, while a 3NF synthesis can often preserve dependencies. Schema design therefore balances stronger normalization with enforceability and practical query structure.[12]

11. Denormalization

Denormalization deliberately duplicates or precomputes information to reduce joins, aggregate work or remote reads. It is not the same as failing to normalize: a denormalized design should begin with a known source-of-truth model and explicitly define how redundant copies remain synchronized.

TechniqueBenefitConsistency burden
Snapshot customer name/address on invoicePreserves historical facts and avoids reconstructing old stateOften intentional independence, not synchronized duplication
Store cached total on orderFaster readsMust match order lines; trigger/application/generated design needed
Materialized summary table/viewFaster analyticsRefresh/update latency
Duplicate lookup labelAvoid join in hot pathMust propagate changes or accept staleness

PostgreSQL gives several alternatives before duplicating ordinary columns: indexes improve join/access cost, generated columns derive same-row values, materialized views store derived query results, and partitioning changes physical layout. Denormalization is most defensible when profiling shows a real bottleneck and the consistency contract is explicit.

12. Constraints as executable schema semantics

PostgreSQL constraints let the database reject invalid states regardless of which application or client submits the write. PostgreSQL 18 stores CHECK, NOT NULL, PRIMARY KEY, UNIQUE, FOREIGN KEY, and EXCLUDE constraints in pg_constraint.[4][19]

CREATE TABLE booking.reservation (
    reservation_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id bigint NOT NULL
        REFERENCES commerce.customer(customer_id),
    party_size integer NOT NULL CHECK (party_size > 0),
    confirmation_code text NOT NULL UNIQUE
);

Constraints should express invariant facts, not merely current UI assumptions. If the database must never contain a negative party size, that rule belongs in the schema even when every application form already validates it.

13. NOT NULL

NOT NULL states that a column must contain a non-null value. PostgreSQL's documentation recommends marking columns non-null whenever null is not a meaningful domain state; in PostgreSQL 18 not-null constraints are represented in pg_constraint as well as column metadata.[4][19]

CREATE TABLE catalog.category (
    category_id bigint PRIMARY KEY,
    name text NOT NULL
);

Do not use nullable columns as a generic “future flexibility” mechanism. Null should have a modeled meaning such as unknown/not-applicable/not-yet-known, and those meanings may need to be distinguished explicitly when they matter operationally.

14. UNIQUE

A unique constraint guarantees that constrained column combinations are unique. PostgreSQL implements it with a unique index. By default, nulls are treated as distinct for uniqueness; NULLS NOT DISTINCT changes this so nulls collide for the constraint.[4][20]

CREATE TABLE auth.login_name (
    user_id bigint PRIMARY KEY,
    username text UNIQUE NULLS NOT DISTINCT
);

A partial uniqueness rule cannot be expressed as a normal UNIQUE constraint, but can be enforced with a unique partial index, for example “only one active subscription per user.”[4]

CREATE UNIQUE INDEX one_active_subscription
ON billing.subscription(user_id)
WHERE status = 'active';

15. CHECK

A CHECK constraint requires its Boolean expression to be true or null for each row. PostgreSQL assumes the expression is effectively immutable with respect to database state: it does not continuously re-evaluate existing rows when an external function changes. Cross-row/table rules therefore generally should not be implemented as ordinary CHECK expressions.[4]

CREATE TABLE payroll.employee (
    employee_id bigint PRIMARY KEY,
    salary numeric(12,2) NOT NULL,
    bonus numeric(12,2) NOT NULL DEFAULT 0,

    CONSTRAINT salary_positive CHECK (salary > 0),
    CONSTRAINT bonus_nonnegative CHECK (bonus >= 0)
);

16. PRIMARY KEY

A primary key is the schema's designated row identifier. PostgreSQL enforces it as UNIQUE plus NOT NULL and creates an index automatically. There is no need to create a duplicate index over exactly the same key merely because the primary key exists.[4][20]

CREATE TABLE school.enrollment (
    student_id bigint NOT NULL,
    course_id bigint NOT NULL,
    term text NOT NULL,
    grade text,

    PRIMARY KEY (student_id, course_id, term)
);

17. FOREIGN KEY

Foreign keys ensure that referencing values correspond to existing referenced keys and define the response when referenced rows are updated or deleted. Referenced columns must form a primary key, unique constraint, or qualifying non-partial unique index. PostgreSQL does not automatically index the referencing columns.[4]

CREATE TABLE support.ticket (
    ticket_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    requester_id bigint NOT NULL,

    CONSTRAINT ticket_requester_fk
        FOREIGN KEY (requester_id)
        REFERENCES auth.user_account(user_id)
        ON UPDATE CASCADE
        ON DELETE RESTRICT
);

18. EXCLUDE constraints

An exclusion constraint ensures that for any two rows, not all specified operator comparisons can be true simultaneously. PostgreSQL enforces exclusion constraints using an index of the chosen access method, commonly GiST. They are especially useful for non-overlap rules such as time/range bookings that ordinary equality-based uniqueness cannot express.[4][21]

CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE booking.room_reservation (
    reservation_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    room_id bigint NOT NULL,
    during tstzrange NOT NULL,

    EXCLUDE USING gist (
        room_id WITH =,
        during WITH &&
    )
);

The example prevents two reservations for the same room whose time ranges overlap.

19. Cascading referential actions

Foreign keys support actions including NO ACTION, RESTRICT, CASCADE, SET NULL, and SET DEFAULT for referenced deletes/updates. PostgreSQL documents a meaningful distinction between NO ACTION and RESTRICT: NO ACTION can be deferred when the constraint is deferrable, while RESTRICT prevents the operation immediately and also differs for some equality/collation scenarios.[4]

CREATE TABLE blog.comment (
    comment_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    post_id bigint NOT NULL
        REFERENCES blog.post(post_id)
        ON DELETE CASCADE,
    author_id bigint
        REFERENCES auth.user_account(user_id)
        ON DELETE SET NULL
);

Use CASCADE when the child fact has no independent meaning after the parent disappears. Use RESTRICT/NO ACTION when deletion should require explicit business handling. Use SET NULL only when “no referenced parent” is a valid modeled state.

20. Generated columns

A generated column is always computed from other columns. PostgreSQL 18 supports stored and virtual generated columns, with virtual now the default. Stored generated values are computed on write and occupy storage; virtual values are computed when read. Generation expressions can use only immutable behavior and cannot contain subqueries or reference other generated columns; generated columns cannot also have defaults or identity definitions and cannot be partition keys.[3][22]

CREATE TABLE commerce.order_line_calc (
    order_id bigint NOT NULL,
    quantity integer NOT NULL CHECK (quantity > 0),
    unit_price numeric(12,2) NOT NULL CHECK (unit_price >= 0),

    line_total numeric(14,2)
        GENERATED ALWAYS AS (quantity * unit_price) STORED
);

Generated columns are appropriate when a value is a deterministic function of the same row. They are not a replacement for aggregate/cross-row derived data such as an order total across many line rows.

21. Identity columns

An identity column automatically obtains values from an implicit sequence. PostgreSQL supports GENERATED ALWAYS and GENERATED BY DEFAULT. Identity columns are automatically NOT NULL, but identity alone does not guarantee uniqueness; declare PRIMARY KEY or UNIQUE when uniqueness is required.[2]

CREATE TABLE app.event (
    event_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    occurred_at timestamptz NOT NULL DEFAULT now(),
    payload jsonb NOT NULL
);

ALWAYS rejects ordinary explicit values unless the statement uses an override clause; BY DEFAULT allows an explicit value to replace sequence generation. The former is often useful when application code should never assign identifiers directly.[2][16]

22. Sequences

A sequence is an independent number generator implemented as a special single-row relation. nextval() atomically returns distinct sequence values across concurrent sessions. Sequence calls such as nextval and setval are not rolled back, so gaps are normal and sequences are unsuitable for requirements demanding gapless assignment.[23]

CREATE SEQUENCE billing.invoice_number_seq
    AS bigint
    START WITH 100000
    CACHE 50;

SELECT nextval('billing.invoice_number_seq');

Use an identity column when the sequence exists specifically to generate one table column's identifiers. Use a standalone sequence when several operations/tables need explicit access to the generator or the sequence itself is part of the domain/integration contract.

23. PostgreSQL 18 temporal/non-overlap constraints

PostgreSQL 18 adds non-overlapping forms of PRIMARY KEY and UNIQUE constraints using WITHOUT OVERLAPS, plus temporal foreign-key semantics using PERIOD. The last key column must be a range or multirange type. Conceptually, a temporal key identifies an entity together with a validity range while preventing overlapping validity intervals for the same entity key.[16][24]

CREATE TABLE pricing.product_price (
    product_id bigint NOT NULL,
    valid_during daterange NOT NULL,
    price numeric(12,2) NOT NULL CHECK (price >= 0),

    PRIMARY KEY (
        product_id,
        valid_during WITHOUT OVERLAPS
    )
);

These features can make bitemporal/valid-time style modeling more declarative, but they do not eliminate the need to define semantics such as whether adjacent intervals are allowed, how corrections are represented, or how application queries select the valid version.

24. Partitioning strategy

Declarative partitioning divides one logical table into physical partitions. PostgreSQL supports range, list and hash partitioning. The partitioned parent is virtual: storage belongs to its partitions, and inserted rows are routed to a partition according to the partition key.[13]

StrategyGood fitExample
RangeOrdered/time-oriented lifecycleMonthly event partitions by occurred_at
ListDiscrete known categoriesRegion/tenant class
HashEven distribution without natural rangesHash of customer/tenant ID

24.1 Partition for pruning and lifecycle, not merely table size

PostgreSQL recommends choosing partition keys that commonly appear in query WHERE clauses so partition pruning can eliminate irrelevant partitions. Data-retention operations are another strong reason: dropping or detaching an old partition can be far cheaper than deleting millions of old rows and then vacuuming the dead tuples.[13]

CREATE TABLE telemetry.event (
    event_id bigint NOT NULL,
    occurred_at timestamptz NOT NULL,
    device_id bigint NOT NULL,
    payload jsonb NOT NULL,
    PRIMARY KEY (event_id, occurred_at)
) PARTITION BY RANGE (occurred_at);

CREATE TABLE telemetry.event_2026_09
PARTITION OF telemetry.event
FOR VALUES FROM ('2026-09-01')
         TO   ('2026-10-01');

CREATE TABLE telemetry.event_2026_10
PARTITION OF telemetry.event
FOR VALUES FROM ('2026-10-01')
         TO   ('2026-11-01');

24.2 Primary/unique keys on partitioned tables

PostgreSQL 18 requires a partitioned table's primary/unique key to include every partition-key column, with restrictions on expression partition keys, because uniqueness is enforced by indexes on individual partitions rather than one global index spanning the whole partition tree.[13][16]

24.3 Too many partitions can hurt

More partitions are not inherently better. Large partition counts consume metadata and increase planning/management work; poorly chosen boundaries can leave queries touching many partitions anyway. Partition count should reflect data volume, pruning selectivity, retention operations, index sizes and operational automation.[13]

24.4 Partitioning is not sharding

Native declarative partitions remain tables within one PostgreSQL database and are managed by the same database instance unless foreign tables or external systems are deliberately introduced. Partitioning alone does not distribute write ownership or compute across independent PostgreSQL servers.

25. Worked schema: normalized commerce model

The following example combines candidate-key modeling, surrogate identifiers, relationship tables, constraints, generated columns and partitioning without mixing their responsibilities.

CREATE SCHEMA commerce;
CREATE SCHEMA catalog;

CREATE TABLE commerce.customer (
    customer_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    account_no text NOT NULL,
    email text NOT NULL,
    display_name text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),

    CONSTRAINT customer_account_no_uq UNIQUE (account_no),
    CONSTRAINT customer_email_uq UNIQUE (email)
);

CREATE TABLE catalog.product (
    product_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    sku text NOT NULL,
    name text NOT NULL,
    current_price numeric(12,2) NOT NULL,

    CONSTRAINT product_sku_uq UNIQUE (sku),
    CONSTRAINT product_price_nonnegative
        CHECK (current_price >= 0)
);

CREATE TABLE commerce.orders (
    order_id bigint GENERATED ALWAYS AS IDENTITY,
    customer_id bigint NOT NULL,
    order_date date NOT NULL DEFAULT current_date,
    status text NOT NULL,
    shipping_name text NOT NULL,
    shipping_address text NOT NULL,

    PRIMARY KEY (order_id, order_date),

    CONSTRAINT orders_customer_fk
        FOREIGN KEY (customer_id)
        REFERENCES commerce.customer(customer_id)
        ON DELETE RESTRICT,

    CONSTRAINT orders_status_ck
        CHECK (status IN (
            'draft','submitted','paid','shipped','cancelled'
        ))
) PARTITION BY RANGE (order_date);

CREATE TABLE commerce.orders_2026
PARTITION OF commerce.orders
FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');

CREATE TABLE commerce.order_line (
    order_id bigint NOT NULL,
    order_date date NOT NULL,
    line_no integer NOT NULL,
    product_id bigint NOT NULL,
    quantity integer NOT NULL,
    unit_price numeric(12,2) NOT NULL,

    line_total numeric(14,2)
        GENERATED ALWAYS AS (
            quantity * unit_price
        ) STORED,

    PRIMARY KEY (order_id, order_date, line_no),

    CONSTRAINT order_line_order_fk
        FOREIGN KEY (order_id, order_date)
        REFERENCES commerce.orders(order_id, order_date)
        ON DELETE CASCADE,

    CONSTRAINT order_line_product_fk
        FOREIGN KEY (product_id)
        REFERENCES catalog.product(product_id),

    CONSTRAINT order_line_quantity_ck
        CHECK (quantity > 0),

    CONSTRAINT order_line_price_ck
        CHECK (unit_price >= 0)
);

25.1 Why snapshot shipping data?

The customer table stores current customer identity and contact state. An order's shipping name/address can intentionally be copied into the order if the requirement is to preserve what was used for that transaction even after the customer edits their profile. That is not accidental denormalization: it models a distinct historical fact with a different lifecycle.

25.2 Why copy unit price into the order line?

catalog.product.current_price is current catalog state, whereas order_line.unit_price is the agreed transaction-time price. They may begin equal, but they represent different facts. Keeping only a foreign key to product price would make historical orders change meaning when catalog prices change.

25.3 Why generated line_total?

Line total is a deterministic same-row function of quantity and unit price, which fits a generated column. By contrast, an order-wide total is an aggregate across several rows and cannot be expressed as a generated column under PostgreSQL's generated-column rules.[22]

26. Schema evolution and constraint rollout

Production schema design includes how invariants are introduced to existing data. PostgreSQL validates ordinary newly added constraints immediately unless a supported constraint form is added with deferred validation semantics. Large migrations often need staged backfills, concurrent indexes and final constraint validation rather than one blocking rewrite.

26.1 Add a constraint after cleaning data

ALTER TABLE commerce.customer
ADD CONSTRAINT customer_email_nonempty
CHECK (email <> '') NOT VALID;

-- Clean/verify legacy rows.

ALTER TABLE commerce.customer
VALIDATE CONSTRAINT customer_email_nonempty;

NOT VALID is useful for supported CHECK/foreign-key deployment paths because new writes are constrained while validation of historical rows can be performed separately. Exact locking/validation behavior should be reviewed for the PostgreSQL version and command being deployed.[25]

26.2 Preserve candidate keys through migrations

When replacing a natural primary key with a surrogate key, do not automatically drop the old natural uniqueness rule. If the natural identifier remains a domain candidate key, migrate it to UNIQUE NOT NULL rather than allowing duplicates after the primary-key change.

27. Common schema-design antipatterns

27.1 Comma-separated IDs in a text column

-- Hard to constrain and join correctly:
product_ids text  -- '12,44,98'

Use an associative table when values represent relationships requiring referential integrity, independent querying or unbounded cardinality.

27.2 “Everything JSONB”

JSONB is valuable for genuinely document-like, sparse or evolving attributes, but core relational keys and invariants are easier to enforce when important attributes are typed columns with constraints. Use semi-structured storage deliberately rather than to avoid modeling decisions.

27.3 Surrogate key plus no business uniqueness

An auto-generated id prevents duplicate IDs but does nothing to prevent duplicate usernames, SKUs, account numbers or other candidate keys. Encode those invariants separately.

27.4 Nullable-by-default schemas

Leaving every column nullable weakens the data model and pushes mandatory-state rules into application code. Use null where absence/unknown is a legitimate state, and NOT NULL otherwise.[4]

27.5 Cascading deletes without lifecycle analysis

ON DELETE CASCADE is appropriate when child rows have no meaning without the parent. Using it on independently valuable audit, financial or historical facts can make a single deletion unexpectedly destructive.

27.6 Storing derived aggregates without synchronization

If order.total duplicates the sum of lines, define who updates it, under what transaction boundary, and how inconsistencies are detected/repaired. Otherwise it is not a cache; it is a second competing source of truth.

27.7 Partitioning every table

Partitioning adds DDL, planning, index and operational complexity. PostgreSQL notes that benefits are generally most relevant for otherwise very large tables and workloads that can prune partitions or exploit partition-level lifecycle operations.[13]

27.8 Using a mutable business attribute as a primary key without considering propagation

A natural key can be an excellent primary key when stable. If it changes frequently, every referencing foreign key may need updates, possibly making a surrogate relationship key operationally simpler while retaining a unique constraint on the business value.

27.9 Assuming 3NF/BCNF automatically means fastest

Normal forms reason about dependencies and redundancy, not latency. A normalized design can require joins; whether a measured workload benefits from materialized/duplicated data is a separate physical-design question.

28. Production checklist

  1. Define the grain of every table. One row should represent one clearly stated fact.
  2. Identify all candidate keys before choosing the primary key.
  3. Enforce alternate candidate keys with UNIQUE and appropriate NOT NULL constraints.
  4. Choose natural versus surrogate primary keys based on stability, width, propagation and domain semantics.
  5. Do not treat a surrogate ID as a substitute for normalization.
  6. Model many-to-many relationships with associative tables when the relationship is queryable/constrained.
  7. Normalize repeated facts at least through the level justified by known functional dependencies.
  8. Use BCNF analysis for schemas with overlapping candidate keys or subtle determinants.
  9. Denormalize only with an explicit source of truth and synchronization contract.
  10. Use NOT NULL for mandatory facts.
  11. Use CHECK for same-row invariant expressions.
  12. Use UNIQUE/PRIMARY KEY for candidate-key constraints.
  13. Use FOREIGN KEY for referential integrity.
  14. Index referencing foreign-key columns when joins/deletes/updates justify it; PostgreSQL does not add that index automatically.
  15. Choose ON DELETE/ON UPDATE actions from entity lifecycle semantics, not convenience.
  16. Use EXCLUDE or PostgreSQL 18 temporal constraints for non-overlap rules.
  17. Use generated columns for immutable same-row derivations.
  18. Remember PostgreSQL 18 generated columns are virtual by default.
  19. Use identity columns for table-local generated identifiers.
  20. Do not assume identity implies uniqueness; add PRIMARY KEY or UNIQUE.
  21. Do not require gapless numbering from sequences.
  22. Partition only when pruning, lifecycle operations, locality or very large table/index sizes justify it.
  23. Choose partition keys from actual query predicates and retention operations.
  24. Account for PostgreSQL's requirement that partitioned primary/unique keys include partition-key columns.
  25. Test schema migrations and constraints against production-scale data and concurrent workloads.
Schema-design principle: model facts once, identify them explicitly, constrain relationships declaratively, and separate logical correctness from physical optimization. PostgreSQL's strongest schemas use the database not merely as storage, but as an executable specification of valid data.
