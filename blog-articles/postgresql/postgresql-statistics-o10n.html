PostgreSQL Statistics & Optimization

An expert guide to PostgreSQL's statistical query-planning model: relation cardinality, column distributions, histograms, most-common values, physical correlation, selectivity and cardinality estimation, extended multivariate statistics, ANALYZE and VACUUM ANALYZE, planner cost constants, prepared-plan behavior, and systematic diagnosis of unstable or badly estimated plans.

Technical article • PostgreSQL 18.6 baseline • Updated 15 September 2026 • Vancouver-style references

Abstract

PostgreSQL is a cost-based optimizer: it enumerates plausible execution strategies, estimates how many rows each operation will produce, estimates the cost of those operations, and selects a plan with the lowest estimated total cost. Statistics are therefore not incidental metadata. They are the evidence from which PostgreSQL estimates scan selectivity, join cardinality, number of groups, index locality, row width, and ultimately whether an index scan, sequential scan, nested loop, hash join, merge join, sort, hash aggregate, or other strategy appears cheapest.[1]-[3]

The core statistics model has two levels. Relation-level statistics such as pg_class.reltuples and relpages approximate the size of tables and indexes. Per-column statistics in pg_statistic, exposed more safely through pg_stats, describe null fractions, average widths, numbers of distinct values, most-common values (MCVs), equal-population histograms, and correlation between logical value ordering and physical heap ordering. PostgreSQL combines these summaries with operator-specific selectivity functions to estimate how many rows satisfy predicates.[2][4][5]

Single-column statistics have a fundamental weakness: they usually treat conditions on separate columns as independent. PostgreSQL's extended statistics objects address selected forms of cross-column dependence through functional dependencies, multivariate distinct counts, multivariate MCV lists, and expression statistics. They can radically improve estimates for correlated predicates and group counts, although PostgreSQL 18 still does not use extended statistics for join selectivity estimation.[2][6]

Query-plan instability often reflects changing evidence rather than arbitrary optimizer behavior. ANALYZE samples large tables, so repeated samples can differ slightly; rapidly changing or skewed data can make statistics stale between analyses; and prepared statements may switch between parameter-sensitive custom plans and parameter-independent generic plans. Diagnosing instability means comparing estimated and actual row counts, understanding the statistics behind the estimates, and separating estimator problems from cost-model or plan-cache problems before resorting to planner method switches.[7]-[9]

1. How statistics drive optimization

The optimizer's most important intermediate quantity is often cardinality: the estimated number of rows emitted by a plan node. Costs for joins, sorts, hashes, repeated parameterized scans, aggregation, materialization, and parallel operations all depend on the number of input/output rows. A cardinality error near the bottom of a plan can therefore propagate upward and change join order, join algorithm, memory assumptions, and scan method.[1][10]

SQL | v parse / rewrite | v candidate access paths and join orders | +--> relation cardinality: reltuples / current size | +--> predicate selectivity: | null_frac | n_distinct | MCV frequencies | histogram | cross-column statistics | +--> estimated rows at every node | +--> cost model: page I/O tuple/index CPU operators/functions parallel overhead cache assumptions | v lowest-estimated-cost plan | v executor | v actual rows / time / buffers | +--> compare actual vs estimated with EXPLAIN ANALYZE

The planner's cost numbers are intentionally abstract rather than millisecond predictions. Their role is comparison among alternative plans. PostgreSQL conventionally anchors the scale with seq_page_cost=1.0 and expresses CPU, random-I/O, parallel, and other costs relative to that baseline.[11]

2. Table and index statistics

The planner needs a base cardinality before applying predicates. PostgreSQL stores approximate row and page counts in pg_class: reltuples estimates live rows and relpages estimates pages. These fields are not updated continuously; VACUUM, ANALYZE, and some DDL commands update them. When the current physical page count differs from the stored page count, the planner scales the row estimate to reflect the table's current size.[2][12] 

SELECT
    c.oid::regclass AS relation,
    c.relkind,
    c.reltuples,
    c.relpages,
    pg_size_pretty(pg_relation_size(c.oid)) AS relation_size
FROM pg_class AS c
WHERE c.oid IN (
    'app.orders'::regclass,
    'app.orders_customer_created_idx'::regclass
);

2.1 Approximate by design

reltuples is an estimate, not a transactionally maintained row counter. Maintaining an exact count on every write would itself impose concurrency and write overhead. For planning, a sufficiently accurate estimate is more useful than an exact but expensive count.[2]

2.2 Row width matters too

The planner also estimates row width, because wider rows affect sequential-scan I/O, sort/hash memory, tuple-transfer costs, and join execution. Per-column average widths in pg_stats.avg_width contribute to these estimates.[4]

3. Column statistics and pg_stats

ANALYZE stores detailed statistics in the internal pg_statistic catalog. PostgreSQL recommends examining the readable pg_stats view instead: it exposes only statistics for tables the current user may read and presents the internal statistic slots as named columns.[2][4] 

SELECT
    schemaname,
    tablename,
    attname,
    null_frac,
    avg_width,
    n_distinct,
    most_common_vals,
    most_common_freqs,
    histogram_bounds,
    correlation
FROM pg_stats
WHERE schemaname = 'app'
  AND tablename = 'orders'
ORDER BY attname;

4. Distinct-value estimates

n_distinct has two encodings. A positive number estimates a fixed absolute count of distinct values. A negative number represents the negative fraction of table rows expected to be distinct. Thus -1 means approximately unique, while -0.1 means distinct values are expected to number roughly 10% of the current row count.[4][13]

4.1 Why proportional values matter

-- Suppose reltuples ~= 10,000,000
-- n_distinct = -0.20
-- estimated distinct values ~= 2,000,000

A proportional encoding lets the estimate grow as the table grows, which is appropriate for identifier-like or high-cardinality attributes. A positive fixed count is more appropriate for stable domains such as a finite set of status codes.[4]

4.2 Manual override

ALTER TABLE app.orders
ALTER COLUMN external_id
SET (
    n_distinct = -1
);

ANALYZE app.orders;

PostgreSQL permits manual n_distinct overrides when sampling cannot estimate cardinality reliably. The ANALYZE documentation recommends this only where an independently known value is more accurate, because a wrong override can systematically poison estimates.[7][14]

5. Most-common values (MCVs)

A histogram alone is a poor description of strongly skewed values. PostgreSQL therefore stores selected high-frequency values separately in most_common_vals with parallel frequencies in most_common_freqs. When an equality predicate's constant is present in the MCV list, the planner can use its recorded frequency directly.[5] 

SELECT
    most_common_vals,
    most_common_freqs
FROM pg_stats
WHERE schemaname = 'app'
  AND tablename = 'orders'
  AND attname = 'status';

5.1 Equality on an MCV

selectivity(status = 'open') ≈ frequency stored for 'open' in most_common_freqs estimated_rows ≈ relation_cardinality × selectivity

This is why skewed columns often benefit from a larger statistics target: the planner can record more important values explicitly instead of forcing them into a coarse residual model.[5][7]

5.2 Equality on a value outside the MCV list

For a non-null equality constant that is not an MCV, PostgreSQL estimates the remaining non-MCV probability mass as approximately uniform across the remaining distinct values. In simplified form:[5]

selectivity(non_MCV_value) ≈ (1 - null_frac - Σ MCV_frequencies) / (n_distinct - number_of_MCVs)

This assumption is necessarily approximate. If the “tail” is itself very skewed, raising the statistics target may move more high-frequency tail values into the MCV list and improve estimates.

6. Histograms

For orderable data types, histogram_bounds divides the non-MCV population into intervals containing approximately equal numbers of rows. Unlike equal-width histograms, dense value regions therefore get narrower value ranges and sparse regions get wider ones. Values represented in the MCV list are excluded from the histogram population.[4][5]

values --------------------------------------------> 0 10 12 13 14 30 100 |--------|---|-|--|------|--------------| bucket1 b2 b3 b4 bucket5 Each bucket aims for roughly equal POPULATION, not equal numerical width.

6.1 Range selectivity

For a predicate such as amount < 100, PostgreSQL locates the constant within the histogram, counts complete buckets below it, estimates a fraction of the containing bucket, and combines that result with any MCV values satisfying the predicate. The final estimate is multiplied by the base relation cardinality to derive estimated rows.[5] 

EXPLAIN
SELECT *
FROM app.orders
WHERE total_amount < 100;

6.2 Histogram resolution

The per-column statistics target bounds both MCV-list length and histogram resolution. More buckets reduce approximation error for irregular distributions, at the cost of a larger ANALYZE sample, more analysis time, additional catalog storage, and slightly more planning work.[2][7]

7. Correlation: physical locality, not column dependence

The pg_stats.correlation value ranges from -1 to +1 and measures how closely a column's logical ordering follows the table's physical row ordering. Values near +1 or -1 tell the planner that an index scan following that column tends to visit heap pages in an ordered/local pattern, reducing the effective penalty of random page access compared with a column whose correlation is near zero.[4] 

SELECT
    attname,
    correlation
FROM pg_stats
WHERE schemaname = 'app'
  AND tablename = 'orders'
ORDER BY abs(correlation) DESC NULLS LAST;
Do not confuse this with cross-column statistical correlation. pg_stats.correlation is about physical heap order versus the value ordering of one column. Cross-column dependencies belong to extended statistics.

7.1 Naturally correlated columns

An append-mostly table whose created_at increases with insertion order often has strong positive physical correlation on that column. An index range scan over recent timestamps may therefore be costed more favorably than an equally selective index on a randomly distributed UUID-like value.[4][11]

7.2 CLUSTER can alter correlation

CLUSTER app.orders
USING orders_customer_created_idx;

ANALYZE app.orders;

CLUSTER physically rewrites a table according to an index order; a subsequent ANALYZE lets the planner observe the resulting correlation. PostgreSQL does not maintain clustered order automatically as future updates/inserts arrive.[15]

8. Selectivity estimation

Selectivity is the planner's estimated fraction of rows satisfying a predicate. PostgreSQL associates operators with restriction and join selectivity estimator functions. Those estimators consult available statistics and apply type/operator-specific logic; the built-in equality and scalar range estimators are documented through PostgreSQL's row-estimation examples.[5][16]

estimated_rows = estimated_input_rows × predicate_selectivity

8.1 AND conditions and independence

When multiple predicates concern columns for which PostgreSQL has no applicable multivariate statistics, it commonly approximates them as independent and multiplies their selectivities. If two conditions each appear to match 1% independently, their conjunction is estimated near 0.01%. If the columns are actually strongly correlated, that multiplication can be wildly wrong.[2][17]

S(A AND B) ≈ S(A) × S(B) when the estimator assumes independence

8.2 OR and NOT

Boolean combinations require corresponding probability logic and safeguards against overlap. The important operational point is not to hand-reproduce every estimator, but to recognize that a poor primitive selectivity estimate can contaminate higher-level Boolean estimates and eventually alter the chosen plan.[10]

9. Cardinality estimation

Cardinality estimation turns relation size and selectivity into predicted row counts at each plan node. Those row counts affect whether repeated nested-loop probes seem cheap, how large a hash table is expected to be, how many groups an aggregate will produce, whether parallelism appears worthwhile, and how much work a sort is expected to perform.[1][10]

9.1 Diagnose estimation ratios

EXPLAIN (
    ANALYZE,
    BUFFERS,
    SETTINGS,
    SUMMARY,
    TIMING OFF
)
SELECT ...
FROM ...;

The most useful comparison is often actual rows versus estimated rows at the earliest node where they diverge materially. Later nodes can inherit error from their children, so fixing the first major misestimate is usually more effective than tuning the final join directly.[3][18]

9.2 A simple error factor

estimation_factor = actual_rows / estimated_rows 1.0 = exact 10 = 10× underestimate 0.1 = 10× overestimate

Use the ratio as a diagnostic aid rather than a universal alarm threshold. A tenfold error from 1 row to 10 rows may be irrelevant, while a twofold error from 50 million to 100 million rows can dominate memory and join strategy.

10. Join-cardinality errors

Join estimates are especially consequential because they control join ordering and method. An underestimated outer input can make a nested loop appear cheap even though it will execute its inner scan far more times than expected. Conversely, an overestimated join can make PostgreSQL choose a hash/merge strategy with unnecessary startup/memory work.[1][18]

estimated: customers filter -> 10 rows | v nested loop | +--> 10 index probes into orders actual: customers filter -> 100,000 rows | v same nested loop | +--> 100,000 probes Root cause may be the FILTER estimate, not the nested-loop implementation.

10.1 Extended-statistics limitation

In PostgreSQL 18, extended statistics are not currently used for selectivity estimates made for table joins. They can improve restriction clauses and group cardinalities within a relation, but they do not directly solve every join-correlation problem.[6]

10.2 Schema design can expose stronger information

Primary keys, unique constraints, foreign keys, NOT NULL constraints, partition bounds, and usable indexes provide structural information separate from sampled distribution statistics. Where a relationship is truly invariant, expressing it declaratively is generally preferable to hoping the statistical model infers it from sampled data.

11. Extended statistics

PostgreSQL does not automatically compute statistics for every column combination because the combinatorial cost would be prohibitive. Instead, administrators define targeted statistics objects for combinations that matter to real queries. Creating the object records the definition; a subsequent manual or automatic ANALYZE computes its data.[2][6] 

CREATE STATISTICS app.orders_customer_state_stats
    (dependencies, ndistinct, mcv)
ON customer_id, state
FROM app.orders;

ANALYZE app.orders;

11.1 Inspect extended statistics

SELECT
    statistics_schemaname,
    statistics_name,
    attnames,
    exprs,
    kinds,
    n_distinct,
    dependencies,
    most_common_vals,
    most_common_freqs,
    most_common_base_freqs
FROM pg_stats_ext
WHERE schemaname = 'app'
  AND tablename = 'orders';

The pg_stats_ext view exposes extended-statistics information in a readable form, while pg_statistic_ext stores definitions and pg_statistic_ext_data stores collected values. The underlying data catalogs are access-restricted because MCV contents can reveal data distributions.[19]-[21]

12. Functional-dependency statistics

Functional dependencies model cases where one column strongly determines another. A canonical example is ZIP code and city: a ZIP code may determine one city nearly perfectly, while a city can contain many ZIP codes. Without dependency knowledge, predicates on both columns can be multiplied as if independent, producing severe underestimation.[2][17] 

CREATE STATISTICS app.customer_geo_dep
    (dependencies)
ON postal_code, city, state
FROM app.customer;

ANALYZE app.customer;
EXPLAIN (ANALYZE, TIMING OFF)
SELECT *
FROM app.customer
WHERE postal_code = '27601'
  AND city = 'Raleigh';

Dependency statistics are applied to supported equality and constant-IN conditions. PostgreSQL 18 does not use them for arbitrary range predicates, LIKE clauses, or equality joins between columns, and dependencies do not encode which combinations are impossible strongly enough to guarantee a zero-row estimate for contradictory constant combinations.[2]

13. Multivariate n-distinct statistics

Single-column distinct counts cannot reliably predict the number of distinct combinations in GROUP BY a, b. If a and b are correlated, multiplying or otherwise combining their individual cardinalities can drastically overestimate the number of groups. The ndistinct statistics kind records observed distinct counts for column combinations to improve grouping estimates.[2][17] 

CREATE STATISTICS app.order_group_ndistinct
    (ndistinct)
ON tenant_id, customer_id, state
FROM app.orders;

ANALYZE app.orders;
EXPLAIN (ANALYZE, TIMING OFF)
SELECT
    tenant_id,
    customer_id,
    state,
    count(*)
FROM app.orders
GROUP BY tenant_id, customer_id, state;

Use multivariate distinct statistics for combinations actually used in grouping/distinct estimation and where bad group-count estimates affect plan quality; unnecessary objects add ANALYZE and planning overhead.[2]

14. Multivariate MCV lists

Multivariate MCV lists capture specific combinations of values that occur together more or less frequently than independent single-column frequencies suggest. They are more detailed than functional dependencies because they store actual common combinations, but this also makes them more expensive to collect, store, and consult.[17] 

CREATE STATISTICS app.orders_state_channel_mcv
    (mcv)
ON state, sales_channel
FROM app.orders;

ANALYZE app.orders;

14.1 Inspect MCV items

SELECT
    m.index,
    m.values,
    m.nulls,
    m.frequency,
    m.base_frequency
FROM pg_statistic_ext AS se
JOIN pg_statistic_ext_data AS sed
  ON sed.stxoid = se.oid
CROSS JOIN LATERAL
    pg_mcv_list_items(sed.stxdmcv) AS m
WHERE se.stxname = 'orders_state_channel_mcv'
ORDER BY m.frequency DESC;

frequency represents the observed frequency of the combination in the statistics sample, while base_frequency represents what the planner would expect from the individual frequencies under independence. Large differences are exactly the kind of cross-column skew multivariate MCVs are intended to model.[17][20]

15. Statistics on expressions

A query can filter on an expression for which ordinary column statistics say little—for example date_trunc('month', created_at), lower(email), or a computed category. PostgreSQL supports statistics objects containing expressions; univariate expression statistics are collected automatically for each complex expression in such an object, without requiring the index-maintenance cost of an expression index.[6] 

CREATE STATISTICS app.orders_created_month_stats
ON (
    date_trunc('month', created_at)
)
FROM app.orders;

ANALYZE app.orders;
EXPLAIN
SELECT count(*)
FROM app.orders
WHERE date_trunc('month', created_at)
      = timestamp '2026-09-01 00:00:00';

15.1 Statistics are not an access path

Expression statistics improve estimates, not execution access. If the expression itself is selective and frequently filtered, an expression index may still be appropriate; expression statistics can improve planning without providing index lookup capability.[6][22]

16. ANALYZE

ANALYZE samples table contents, computes planner statistics, and stores them in PostgreSQL's statistics catalogs. For large tables it uses a random sample rather than reading every row, which bounds maintenance cost but makes the resulting estimates approximate and slightly variable from one run to another.[7] 

ANALYZE app.orders;

ANALYZE (VERBOSE)
app.orders;

ANALYZE app.orders (
    customer_id,
    state,
    total_amount
);

16.1 Sampling can move a borderline plan

PostgreSQL explicitly notes that repeated ANALYZE runs can produce slightly different statistics even when the underlying data has not changed. Estimated costs can therefore move, and in rare cases a plan near a cost crossover can switch from one strategy to another. Increasing the statistics target increases the sample and can reduce this sampling-driven instability.[7][5]

16.2 Locks and concurrency

ANALYZE requires only a read lock on the target table and normally runs concurrently with ordinary non-DDL activity. PostgreSQL 18 also supports SKIP_LOCKED and BUFFER_USAGE_LIMIT options for operational control.[7]

16.3 ANALYZE after bulk change

COPY app.orders
FROM '/staging/orders.csv'
WITH (FORMAT csv, HEADER true);

ANALYZE app.orders;

After a large import, restore, or distribution-changing update, a manual ANALYZE can be appropriate instead of waiting for autoanalyze to reach its threshold. PostgreSQL's EXPLAIN documentation recommends ensuring statistics are current before diagnosing apparently poor planner behavior.[18][7]

17. Statistics targets

default_statistics_target is 100 by default. A column-specific target can override it with ALTER TABLE ... SET STATISTICS. The target limits MCV entries and histogram bins, and the largest target among analyzed columns influences the sample size. Higher values improve detail at the cost of longer ANALYZE, more statistics storage, and some additional planning work.[7][11] 

SHOW default_statistics_target;

ALTER TABLE app.orders
ALTER COLUMN customer_id
SET STATISTICS 1000;

ALTER TABLE app.orders
ALTER COLUMN state
SET STATISTICS 500;

ANALYZE app.orders;

17.1 Raise targets selectively

Good candidates are columns that are heavily used in filters/grouping and have irregular distributions or estimation problems. Raising the global target to thousands because one column is skewed makes every ANALYZE more expensive and is usually inferior to targeted changes.[23]

17.2 Extended-statistics target

ALTER STATISTICS
app.orders_state_channel_mcv
SET STATISTICS 1000;

ANALYZE app.orders;

PostgreSQL 18 permits an extended statistics target from 0 through 10000; DEFAULT returns to the object's normal defaulting behavior. A higher target can increase MCV detail for the statistics object.[24]

18. VACUUM ANALYZE

VACUUM and ANALYZE address different problems. VACUUM reclaims obsolete MVCC storage, advances freeze/visibility state, and performs related maintenance; ANALYZE samples live data and refreshes planner statistics. VACUUM (ANALYZE) runs both operations in one command but does not merge their semantics into one algorithm.[23][25] 

VACUUM (
    ANALYZE,
    VERBOSE
) app.orders;

18.1 When ANALYZE alone is sufficient

If the issue is stale cardinality/distribution statistics after a bulk load and dead tuples are not a concern, ANALYZE alone is cheaper and more targeted. Conversely, a vacuum operation without ANALYZE can reclaim space while leaving old planner distributions intact.

18.2 CLI wrapper

vacuumdb \
  --analyze \
  --verbose \
  appdb

vacuumdb is a client wrapper around the server's VACUUM/ANALYZE commands. Its --analyze-in-stages mode can quickly produce coarse statistics first on a freshly restored/upgraded database and then build fuller statistics in later stages.[26]

19. Autoanalyze

Autovacuum also schedules automatic ANALYZE runs. For ordinary tables, PostgreSQL compares the number of inserted, updated, or deleted tuples since the last analysis with a threshold consisting of a fixed base plus a scale factor multiplied by the estimated table row count.[23]

analyze_threshold = autovacuum_analyze_threshold + autovacuum_analyze_scale_factor × reltuples

19.1 Per-table tuning

ALTER TABLE app.orders
SET (
    autovacuum_analyze_threshold = 5000,
    autovacuum_analyze_scale_factor = 0.01
);

Large rapidly changing tables may need lower scale factors so a meaningful distribution change is observed earlier. Tiny frequently changing tables can usually tolerate defaults because the absolute threshold remains small.[23][27]

19.2 Distribution change can matter before row-count change

A table can keep roughly the same row count while a critical distribution changes dramatically—for example, millions of orders move from pending to complete. Autoanalyze counts tuple modifications, so such updates eventually trigger it, but latency between a sudden distribution change and the next analysis can temporarily produce stale selectivity estimates.

20. Partitioned-table statistics

Explicit ANALYZE on a partitioned table samples rows across its partitions and can build parent/inherited statistics. Autovacuum processes the leaf partitions but does not process the storage-less partitioned parent itself, so parent-level statistics can become stale when only the partitions change. PostgreSQL recommends running manual ANALYZE on partitioned parents when their data distribution changes significantly.[7][23] 

ANALYZE analytics.events;

20.1 Local versus inherited statistics

pg_stats.inherited distinguishes statistics for only the relation from statistics covering its inheritance/partition tree. This distinction matters when diagnosing a query on the parent versus a query using ONLY parent.[2][4]

21. Planner cost parameters

Cost parameters model relative work, not absolute elapsed time. PostgreSQL documentation explicitly warns that there is no universally correct formula for choosing them and that tuning them from a few isolated experiments is risky; they should approximate the overall workload and hardware environment.[11]

ParameterPostgreSQL 18 defaultPlanner interpretation
seq_page_cost1.0Relative cost of a sequential page fetch
random_page_cost4.0Relative cost of a non-sequential page fetch
cpu_tuple_cost0.01Processing one row
cpu_index_tuple_cost0.005Processing one index entry
cpu_operator_cost0.0025Executing one operator/function
parallel_setup_cost1000Launching parallel workers
parallel_tuple_cost0.1Moving a tuple from a parallel worker
effective_cache_size4 GB*Planner estimate of cache available to one query; does not allocate memory

*The documentation notes that the default scales with block size if PostgreSQL was built with a nonstandard BLCKSZ.[11]

21.1 Random versus sequential I/O

SHOW seq_page_cost;
SHOW random_page_cost;

Reducing random_page_cost relative to seq_page_cost makes index-driven access look cheaper. PostgreSQL's default of 4.0 already assumes substantial caching; systems whose active database is mostly memory-resident may justify a smaller gap, while rotational or uncached storage can justify a larger one. Measure representative workload behavior before changing global values.[11]

21.2 effective_cache_size is not cache allocation

SHOW effective_cache_size;

This setting is only a planner assumption about likely cache availability from PostgreSQL shared buffers plus OS cache, adjusted mentally for competing concurrent queries. Increasing it does not allocate or reserve memory; it changes cost estimates, especially for index access.[11]

21.3 Tablespace-specific I/O costs

ALTER TABLESPACE fast_nvme
SET (
    random_page_cost = 1.2,
    seq_page_cost = 1.0
);

PostgreSQL permits tablespace-specific overrides for page cost parameters, allowing physically distinct storage classes to be modeled differently without changing the entire cluster's cost assumptions.[11]

21.4 Planner method switches are diagnostic tools

SET LOCAL enable_seqscan = off;

EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;

The enable_*scan/enable_*join settings are deliberately described as crude planner influence controls. They are useful to test whether an alternative plan could be faster, but PostgreSQL recommends fixing statistics/cost/index/schema problems rather than permanently disabling plan types as the primary tuning strategy.[11]

22. Using EXPLAIN to diagnose estimates

EXPLAIN exposes the planner's estimated costs, row counts, and widths. EXPLAIN ANALYZE actually executes the statement and adds runtime row counts and timings. With BUFFERS, WAL, SETTINGS, and PostgreSQL 18's MEMORY option, it can expose additional resource/planner context.[3][18] 

EXPLAIN (
    ANALYZE,
    BUFFERS,
    WAL,
    SETTINGS,
    MEMORY,
    TIMING OFF,
    SUMMARY
)
SELECT
    o.customer_id,
    sum(o.total_amount)
FROM app.orders AS o
WHERE o.state = 'paid'
  AND o.created_at >= current_date - interval '30 days'
GROUP BY o.customer_id;

22.1 A practical reading order

  1. Start at the lowest node where estimated rows and actual rows diverge materially.
  2. Identify the predicate/join/group estimate responsible.
  3. Inspect the relevant pg_stats/pg_stats_ext data.
  4. Check whether statistics are stale or sampled too coarsely.
  5. Only then evaluate indexes, cost constants, join settings, or query rewrites.

22.2 EXPLAIN ANALYZE has overhead

Because it executes the query and instruments plan nodes, EXPLAIN ANALYZE can make execution slower than a normal run. Timing instrumentation can be particularly expensive on some platforms; TIMING OFF retains actual row counts while reducing per-node clock-call overhead.[18]

22.3 Do not run destructive statements accidentally

BEGIN;

EXPLAIN (ANALYZE, BUFFERS)
DELETE FROM app.orders
WHERE created_at < date '2020-01-01';

ROLLBACK;

Because ANALYZE in EXPLAIN means “execute,” wrap mutating tests in a rollbackable transaction when safe and remember that some external side effects (for example, certain function behavior) may not be reversible merely because the SQL transaction rolls back.

23. Query-plan instability

A plan is “unstable” operationally when small changes in data, statistics, parameter values, configuration, or planner state cause materially different execution plans or runtimes. This is not one PostgreSQL feature; several distinct mechanisms can produce it.[7][8]

23.1 Sampling instability

Large-table ANALYZE samples are randomized. PostgreSQL explicitly notes that a fresh sample can slightly change estimated costs and, in rare borderline cases, change the selected plan. If a critical decision depends on a poorly represented tail of a distribution, increasing the relevant target is more direct than globally forcing a scan type.[7]

23.2 Cost crossover

estimated cost ^ | sequential scan | / | / |---------X------------------> selectivity | / | / index scan | +--------------------------------------------> Near X, a small estimate change can legitimately flip plans. The real question is whether both cost curves model reality accurately.

23.3 Plan change is not automatically regression

A changing plan can be appropriate when the data distribution, parameter value, cache/storage assumptions, or relation size changes. Stabilizing a plan at all costs can freeze a strategy that is optimal only for today's data.

24. Prepared statements: generic versus custom plans

Parameterized prepared statements can use custom plans—planned with the actual supplied values—or generic plans that are reusable across parameter values. PostgreSQL's default plan_cache_mode=auto initially uses custom plans, calculates their average estimated cost, then compares a generic plan against that history and can switch to the generic plan when repeated replanning does not appear worthwhile.[8][11]

24.1 Skew makes parameters matter

PREPARE orders_by_customer(bigint) AS
SELECT *
FROM app.orders
WHERE customer_id = $1
ORDER BY created_at DESC;

If customer 1 owns 30% of all orders while most customers own 20 rows, an index plan suitable for a typical customer may be poor for customer 1, and a generic plan cannot use the actual parameter value to choose differently. Accurate MCV statistics help custom plans estimate this skew; they cannot make a generic plan parameter-specific.[8]

24.2 Inspect custom and generic behavior

EXPLAIN EXECUTE orders_by_customer(42);

EXPLAIN (GENERIC_PLAN)
SELECT *
FROM app.orders
WHERE customer_id = $1::bigint
ORDER BY created_at DESC;

PostgreSQL 18's EXPLAIN (GENERIC_PLAN) can display a parameter-independent plan without executing it. For an already prepared statement, a generic plan retains $n placeholders while a custom plan displays the supplied constants.[3][8]

24.3 Count plan types

SELECT
    name,
    generic_plans,
    custom_plans,
    statement
FROM pg_prepared_statements;

The session-local pg_prepared_statements view reports how many generic and custom plans have been used for each prepared statement.[28]

24.4 Diagnostic override

SET LOCAL plan_cache_mode = force_custom_plan;
-- compare

SET LOCAL plan_cache_mode = force_generic_plan;
-- compare

Use this to prove that parameter sensitivity is the issue before changing application prepare behavior. PostgreSQL also forces reanalysis/replanning of prepared statements after relevant DDL or planner-statistics updates, so an ANALYZE can legitimately alter a cached statement's subsequent plan.[8]

25. Workload-level plan monitoring

25.1 pg_stat_statements

The supplied pg_stat_statements extension aggregates planning and execution metrics for normalized query shapes. With planning tracking enabled it records plan counts and planning-time statistics; execution metrics include min/max/mean/standard deviation, block activity, rows, WAL, and parallel-worker information. Large execution-time variance for one normalized query can be a signal of parameter skew, plan changes, cache effects, lock waits, or changing input cardinality.[29] 

SELECT
    queryid,
    calls,
    plans,
    round(mean_plan_time::numeric, 3) AS mean_plan_ms,
    round(mean_exec_time::numeric, 3) AS mean_exec_ms,
    round(stddev_exec_time::numeric, 3) AS exec_stddev_ms,
    round(min_exec_time::numeric, 3) AS min_exec_ms,
    round(max_exec_time::numeric, 3) AS max_exec_ms,
    rows,
    query
FROM pg_stat_statements
WHERE calls > 20
ORDER BY max_exec_time DESC
LIMIT 25;

25.2 Planning tracking overhead

# postgresql.conf
shared_preload_libraries = 'pg_stat_statements'
pg_stat_statements.track_planning = on

Planning tracking is optional because planning statistics add overhead, especially in workloads with many structurally identical concurrent queries that contend on the same statistics entry. Enable it intentionally when the diagnostic value justifies the cost.[29]

25.3 auto_explain

auto_explain can log execution plans for slow statements automatically, which is valuable when the bad plan appears only under production parameter values. log_analyze can include actual row counts, but PostgreSQL warns that enabling per-node timing for all candidate statements can impose substantial overhead; auto_explain.log_timing=off can reduce that cost when row counts are the main goal.[30] 

# Example only:
session_preload_libraries = 'auto_explain'
auto_explain.log_min_duration = '1s'
auto_explain.log_analyze = on
auto_explain.log_timing = off
auto_explain.log_buffers = on
auto_explain.log_settings = on
auto_explain.sample_rate = 0.10

26. A statistics-first optimization workflow

slow / unstable query | v capture exact SQL + parameters | v EXPLAIN (ANALYZE, BUFFERS, SETTINGS, TIMING OFF) | v find earliest major estimate error | +-----+---------------------------------------+ | | estimate wrong? estimates good? | | v v inspect pg_stats / pg_stats_ext investigate cost model, | I/O, work_mem, indexes, +--> stale? -> ANALYZE join algorithms, cache, +--> sample too coarse? -> raise target parallelism, locking +--> correlated columns? -> ext stats +--> expression? -> expression stats +--> partition parent stale? -> ANALYZE parent +--> parameter skew? -> custom/generic test | v re-ANALYZE / reproduce | v measure actual workload again

26.1 Step 1: preserve the problematic context

Record the SQL shape, parameter values, PostgreSQL settings relevant to planning, schema/index definitions, and time/data-distribution context. Reproducing only the SQL text can miss the parameter skew or prepared-plan state that caused the incident.

26.2 Step 2: compare estimates to actuals

EXPLAIN (
    ANALYZE,
    BUFFERS,
    SETTINGS,
    TIMING OFF,
    SUMMARY
)
SELECT ...;

26.3 Step 3: inspect exact statistics used by the suspect predicate

SELECT *
FROM pg_stats
WHERE schemaname = 'app'
  AND tablename = 'orders'
  AND attname IN (
      'customer_id',
      'state',
      'created_at'
  );

26.4 Step 4: fix the smallest statistical model that explains the error

-- Example: one skewed column.
ALTER TABLE app.orders
ALTER COLUMN customer_id
SET STATISTICS 1000;

-- Example: cross-column skew.
CREATE STATISTICS app.orders_customer_state_mcv (mcv)
ON customer_id, state
FROM app.orders;

ANALYZE app.orders;

26.5 Step 5: verify, then revisit cost/index choices

If cardinalities become accurate but PostgreSQL still chooses a slower plan, the problem has moved from selectivity estimation toward cost assumptions, missing access paths, memory, or execution behavior. That is the right time to examine cost constants or index design.[11]

27. Common pitfalls

27.1 “The planner should know the exact row count”

PostgreSQL deliberately uses approximate relation and sampled distribution statistics. Exact continuously maintained counts would be expensive and still would not solve predicate-distribution estimation.[2][7]

27.2 Raising every statistics target to 10,000

Higher targets increase sample size, ANALYZE time, statistics storage, and planning work. Raise targets selectively where estimation error matters.[7]

27.3 Misreading correlation as “customer_id correlates with state”

The pg_stats value is physical ordering correlation for one column. Use extended statistics for relationships between columns.[4][2]

27.4 Creating extended statistics but forgetting ANALYZE

CREATE STATISTICS defines what to collect; it does not populate statistical values. ANALYZE performs collection.[2][6]

27.5 Expecting extended statistics to fix join selectivity

PostgreSQL 18 does not currently apply them to table-join selectivity estimation.[6]

27.6 Changing random_page_cost to fix one query

Planner cost constants affect the whole workload (or tablespace). PostgreSQL explicitly warns against choosing them based on a few experiments. First verify the query's cardinality estimates and access-path design.[11]

27.7 Disabling sequential scans permanently

A sequential scan can be the correct plan when a query returns a large fraction of a table. enable_seqscan=off is useful for comparison but does not repair bad estimates or create a truly efficient index path.[11]

27.8 Blaming PostgreSQL for parameter-sensitive workloads without inspecting generic plans

A plan optimal for a rare value can be disastrous for a very common value. Prepared statements can intentionally choose a generic plan to save repeated planning work. Compare custom and generic behavior before changing SQL/indexes.[8]

27.9 Forgetting parent statistics on partitioned tables

Autovacuum handles leaf partitions but not the partitioned parent itself; manual parent ANALYZE may be needed for parent-level statistics.[7][23]

27.10 Treating plan changes after ANALYZE as inherently bad

ANALYZE exists so the optimizer can adapt to data. Sampling can cause small changes, while real distribution changes should change plans. The objective is robust performance, not a permanently identical plan tree.[7]

27.11 Looking only at total runtime

A slow plan's root cause often appears as an early row-estimation error. Node-level estimated-versus-actual cardinalities are usually more diagnostic than the final execution time alone.[18]

28. Production checklist

  1. Keep statistics current. Let autoanalyze work and run manual ANALYZE after major distribution-changing loads.
  2. Inspect pg_stats, not just EXPLAIN. Understand the evidence behind the row estimate.
  3. Monitor reltuples/relpages. Base cardinality errors contaminate all higher estimates.
  4. Use MCVs for skew. Raise per-column targets when important common values are underrepresented.
  5. Use histograms for ranges. Increase resolution only where it improves real estimates.
  6. Interpret correlation correctly. It models physical ordering locality, not cross-column dependence.
  7. Create extended statistics deliberately. Use dependencies, n-distinct, MCV, or expression statistics for demonstrated problems.
  8. Remember extended-statistics limits. PostgreSQL 18 does not use them for join selectivity.
  9. Compare estimated and actual rows. Find the earliest material divergence in the plan.
  10. Tune statistics before planner switches. enable_* settings are diagnostic levers, not first-choice permanent fixes.
  11. Tune cost constants workload-wide. Do not optimize random_page_cost around one anecdotal query.
  12. Set effective_cache_size realistically. It is a planner estimate, not allocated memory.
  13. Investigate parameter skew. Compare custom and generic plans for prepared statements.
  14. Monitor plan/execution variance. Use pg_stat_statements and selectively use auto_explain.
  15. Analyze partitioned parents explicitly.
  16. Retest after data growth. A plan that was correct at 10 million rows may not remain correct at 500 million.
  17. Prefer declarative schema information. Constraints and proper data modeling complement statistical estimation.
  18. Optimize from evidence. Cardinality estimates explain many “mysterious” plan choices.
Optimization principle: PostgreSQL chooses plans from a model of the data, not from the data itself. When a plan looks irrational, first ask which cardinality estimate made it rational to the optimizer—and then improve the evidence or assumptions behind that estimate.
