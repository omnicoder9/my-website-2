PostgreSQL Installation & Administration

A production-oriented guide to installing and operating PostgreSQL on Linux, Windows, macOS, containers, and managed cloud platforms; initializing clusters; controlling services; configuring postgresql.conf, pg_hba.conf, and pg_ident.conf; managing roles and tablespaces; using psql and libpq environment variables; and operating the core PostgreSQL administrative utilities.

Technical article • PostgreSQL 18.6 baseline • Updated 16 September 2026 • Vancouver-style references

Abstract

PostgreSQL administration has two layers that should be kept distinct. PostgreSQL itself defines the cluster layout, initdb, the postgres server process, configuration files, SQL role model, tablespaces, client protocol and command-line utilities. Operating-system packages and managed services add a second layer that decides binary locations, service-unit names, data-directory conventions, automatic initialization, patching workflows, backups and which server settings are exposed. A reliable runbook separates those layers rather than treating one distribution's paths or service names as universal PostgreSQL behavior.[1]-[5]

A self-managed PostgreSQL instance begins with binaries plus a database cluster. initdb creates the cluster directory, shared catalogs, the postgres database and template databases, as well as default postgresql.conf, pg_hba.conf and related state. The server is then started either through an OS service manager such as systemd/Windows Services or directly through pg_ctl/postgres. PostgreSQL configuration settings differ in when they take effect: some reload on SIGHUP, some can change per session, and others—including listen_addresses, port, max_connections, shared_buffers and logging_collector—require server start/restart.[6]-[10]

Client authentication is separate from SQL privileges. pg_hba.conf determines whether a connection attempt is permitted and which authentication method applies; database roles determine what an authenticated session may own or access. pg_ident.conf is an optional mapping layer for external identities such as operating-system/GSSAPI names that differ from PostgreSQL role names. Roles exist cluster-wide, can own objects, and can have attributes such as LOGIN, CREATEDB, CREATEROLE, REPLICATION and BYPASSRLS.[11]-[15]

Operational utilities cover different failure and maintenance domains. pg_dump/pg_restore perform logical, database/object-level backup and restore; pg_basebackup takes a physical base backup of an entire running cluster for recovery/replication; vacuumdb wraps SQL VACUUM/ANALYZE; and reindexdb wraps SQL REINDEX. These tools are complementary rather than interchangeable and should be tied to tested restore, maintenance and disaster-recovery procedures.[16]-[21]

1. Installation model: binaries, cluster, service

Installing PostgreSQL binaries does not necessarily create or start a database cluster. PostgreSQL's upstream model separates executable installation from initdb, which creates a cluster. OS packages may automate some or all of initialization and service registration, while other packages intentionally leave those steps to the administrator.[1][6]

install PostgreSQL software | v postgres / psql / initdb / pg_ctl / utilities | v initialize cluster (initdb) | +--> data directory +--> shared catalogs +--> postgres + template databases +--> postgresql.conf +--> pg_hba.conf +--> pg_ident.conf | v start server (systemd / Windows service / pg_ctl / container runtime) | v connect and administer with psql/libpq

PostgreSQL's download site recommends using integrated package management on Linux when available because packaging supplies OS integration and update management. PostgreSQL also publishes links to Windows/macOS installers and source code for custom builds.[1][2]

2. Linux installation

Linux distributions commonly ship PostgreSQL through their native package repositories, while the PostgreSQL project also maintains the PGDG package repositories for several major distributions. Package names, data directories, service units, initialization commands and supported versions are packaging decisions; always consult the repository page for the distribution being deployed.[2]-[4]

2.1 Debian/Ubuntu using the PGDG repository

The official PostgreSQL Debian/Ubuntu repository documentation provides an automated repository-configuration helper and versioned packages. A PostgreSQL 18 installation can be performed with the versioned server package after configuring the repository.[3][4]

sudo apt install -y postgresql-common
sudo /usr/share/postgresql-common/pgdg/apt.postgresql.org.sh

sudo apt update
sudo apt install postgresql-18
Packaging-specific behavior: Debian-family packages use their own multi-cluster tooling and directory/service conventions. Do not infer those paths from upstream initdb examples or copy them onto RHEL-family systems.

2.2 RHEL/Rocky/AlmaLinux/Fedora family

The PostgreSQL download page for Red Hat-family systems notes that some packages do not initialize or automatically enable PostgreSQL after installation. Its post-installation example uses a setup utility followed by systemd service enable/start operations.[5]

postgresql-setup --initdb
systemctl enable postgresql.service
systemctl start postgresql.service

The exact service/package name varies by repository and version. Use systemctl list-unit-files | grep -i postgres, package documentation, or the repository's supplied instructions rather than assuming one universal unit name.

2.3 Verify binaries and server

psql --version
postgres --version
pg_config --version

psql -d postgres -c 'SELECT version();'

3. Windows installation

The PostgreSQL project links to an EDB interactive installer for Windows. The installer includes the PostgreSQL server and pgAdmin and can run in graphical or silent modes. Windows can run PostgreSQL as a system service; upstream pg_ctl also supports register and unregister service operations.[22][7]

3.1 Service registration with pg_ctl

pg_ctl register ^
  -N PostgreSQL18 ^
  -D "C:\PostgreSQL\18\data" ^
  -S auto

pg_ctl unregister -N PostgreSQL18

On Windows, PostgreSQL also supports the eventlog logging destination. Changes to pg_hba.conf are applied to subsequent new connections immediately on Windows, unlike Unix-like systems where an HBA reload is normally required.[7][11][23]

3.2 PowerShell client example

$env:PGHOST = "localhost"
$env:PGPORT = "5432"
$env:PGUSER = "postgres"
$env:PGDATABASE = "postgres"

psql -c "SELECT version();"

4. macOS installation

The PostgreSQL project lists several macOS distribution options: the EDB installer, Postgres.app, Homebrew, MacPorts and Fink. The EDB installer bundles the server, pgAdmin and StackBuilder; Postgres.app provides a self-contained app; Homebrew and other package managers integrate PostgreSQL with their own package/service conventions.[24]

4.1 Homebrew-style workflow

# Exact formula version depends on what Homebrew currently ships.
brew search postgresql
brew install postgresql@18

# Package-manager service control is Homebrew-specific.
brew services list

For source builds on macOS, upstream PostgreSQL documents installing Apple's command-line developer tools with xcode-select --install. Source-build/extension ABI details depend on the SDK/sysroot used to build PostgreSQL.[25]

5. Containers

The Docker Official Image for PostgreSQL provides versioned images including PostgreSQL 18.6. The image entrypoint initializes PostgreSQL when the configured data directory is empty, using environment variables such as POSTGRES_PASSWORD, POSTGRES_USER, POSTGRES_DB and POSTGRES_INITDB_ARGS. Those initialization variables do not retroactively reconfigure an already initialized persistent volume.[26]

5.1 Minimal Docker run

docker volume create pg18-data

docker run -d \
  --name pg18 \
  -e POSTGRES_PASSWORD='change-me' \
  -p 5432:5432 \
  -v pg18-data:/var/lib/postgresql \
  postgres:18.6

The official image changed its volume/data layout for PostgreSQL 18 and later: the image-level volume is /var/lib/postgresql, while the default version-specific PGDATA resides below it. This differs from PostgreSQL 17-and-earlier Docker-image conventions, so volume mounts should follow the image documentation for the selected major version.[26]

5.2 Compose example

services:
  db:
    image: postgres:18.6
    restart: unless-stopped
    shm_size: 256mb
    environment:
      POSTGRES_USER: app_admin
      POSTGRES_PASSWORD_FILE: /run/secrets/postgres_password
      POSTGRES_DB: appdb
      POSTGRES_INITDB_ARGS: "--data-checksums"
    secrets:
      - postgres_password
    volumes:
      - pg18-data:/var/lib/postgresql
    ports:
      - "127.0.0.1:5432:5432"

secrets:
  postgres_password:
    file: ./postgres_password.txt

volumes:
  pg18-data:

5.3 Initialization scripts

The official image executes *.sql, *.sql.gz and shell initialization files in /docker-entrypoint-initdb.d after initial initdb, but only when the database directory is empty. Treat these as first-boot/bootstrap scripts, not as a migration system for existing databases.[26]

# docker-entrypoint-initdb.d/10-app.sql
CREATE ROLE app_runtime LOGIN;
CREATE DATABASE appdb OWNER app_runtime;

5.4 Containers do not remove database administration

A container image packages processes and files; it does not make the database stateless. Persistent storage, backup/restore, major-version upgrade, resource limits, shared memory, replication, WAL retention, monitoring and security still require deliberate design.

6. Managed cloud PostgreSQL

Managed PostgreSQL services replace some host-level administration with provider APIs. Amazon RDS for PostgreSQL, Azure Database for PostgreSQL Flexible Server, and Google Cloud SQL for PostgreSQL manage the underlying VM/service lifecycle and provide platform-integrated backup, networking, monitoring and availability features, but they expose only a controlled subset of PostgreSQL/OS capabilities.[27]-[29]

Self-managedManaged cloud
Root/administrator access to hostUsually no host access
Edit postgresql.conf directlyProvider parameter/flag interface
Superuser role under your controlProvider-managed elevated role; full superuser often unavailable
Choose filesystem/tablespace pathsStorage exposed through provider abstractions
Run pg_ctl/systemctlStart/stop/restart via provider control plane
Design backups manuallyAutomated backups/PITR often integrated, but restore testing remains your responsibility

Azure documents that its managed superuser role remains controlled by the service and that only a subset of PostgreSQL parameters can be configured through the service. Cloud SQL likewise documents itself as fully managed PostgreSQL. RDS exposes PostgreSQL through RDS controls rather than host-level administration.[27]-[30]

Cloud administration changes responsibility, not correctness requirements. You still need role design, connection security, query/index tuning, restore testing, schema migrations, capacity planning and monitoring. Provider backups are not a substitute for proving your RTO/RPO through restores.

7. Database initialization with initdb

initdb creates a new PostgreSQL database cluster: the data-directory structure, shared catalog tables, postgres, template1 and template0 databases, and initial configuration/authentication files. The cluster must be initialized by the operating-system account that will own/run the server, not by root.[6]

install -d -m 0700 -o postgres -g postgres /srv/postgresql/18/data

sudo -u postgres initdb \
  -D /srv/postgresql/18/data \
  --encoding=UTF8 \
  --locale=C.UTF-8 \
  --auth-host=scram-sha-256 \
  --auth-local=peer \
  --data-checksums

initdb can select locale/provider/encoding, configure initial HBA authentication, enable data checksums, choose WAL segment size, and place WAL in another directory. These choices are not all equally easy to change later; initialization should therefore be part of the infrastructure specification, not an improvised first boot.[6]

Do not use trust casually. Upstream initdb permits trust authentication for convenience, but explicitly warns against it unless all users with access to the relevant host/network are trusted.[6]

8. Cluster and configuration layout

By default, upstream PostgreSQL expects configuration files in the data directory referenced by -D/PGDATA. PostgreSQL can separate the physical data directory from configuration files by setting data_directory and can independently point to hba_file and ident_file. Linux packages often use this flexibility to place configuration under /etc while storing database files elsewhere.[31]

SHOW data_directory;
SHOW config_file;
SHOW hba_file;
SHOW ident_file;

Use SQL to ask a running server where its files are rather than guessing package paths.

9. Starting and stopping PostgreSQL

The server can be started by an OS service manager, pg_ctl, or the postgres executable directly. Production package installs normally use the platform service manager because it provides boot integration, process supervision and centralized logs; pg_ctl remains the portable PostgreSQL-level control utility.[7]

service manager direct PostgreSQL control systemd / Windows Services pg_ctl | | +-------------> postgres <----------+ | cluster | shared memory / files

10. systemctl on Linux

systemd is not a PostgreSQL feature, but many Linux packages install PostgreSQL service units. Unit names vary by package family/version, so inspect the installed units instead of hard-coding a name from another distribution.

systemctl list-unit-files | grep -i postgres
systemctl list-units --type=service | grep -i postgres

sudo systemctl status postgresql.service
sudo systemctl start postgresql.service
sudo systemctl stop postgresql.service
sudo systemctl restart postgresql.service
sudo systemctl reload postgresql.service
sudo systemctl enable postgresql.service

The Red Hat-family PostgreSQL download instructions explicitly show enabling and starting a postgresql.service after initialization for the referenced package setup, while Debian-derived packaging can expose cluster-specific units/tooling. Treat those service names as package contracts, not upstream PostgreSQL constants.[5]

10.1 Logs with journald

journalctl -u postgresql.service
journalctl -u postgresql.service -f

Whether server logs appear in journald, PostgreSQL log files, syslog or several destinations depends on the service wrapper and PostgreSQL log_destination/logging_collector configuration.[23]

11. pg_ctl

pg_ctl initializes, starts, stops, restarts, reloads, promotes and reports the status of a PostgreSQL server. On Windows it also registers/unregisters a service. It uses -D or PGDATA to find the cluster configuration.[7]

export PGDATA=/srv/postgresql/18/data

pg_ctl status
pg_ctl start -l /var/log/postgresql/pg18.log
pg_ctl reload
pg_ctl restart
pg_ctl stop

11.1 Shutdown modes

ModeBehaviorUse
smartRejects new connections and waits for existing clients to disconnect.Gentlest planned shutdown when waiting is acceptable.
fastDefault; disconnects clients, rolls back active transactions, performs clean shutdown.Normal operational shutdown/restart.
immediateAborts server processes without clean shutdown; next start performs crash recovery.Emergency only.

Upstream pg_ctl stop defaults to fast mode. Immediate mode deliberately creates crash-recovery work and should not be a routine service-control choice.[7]

12. postgresql.conf

postgresql.conf is the main server-parameter configuration file. It is generated during initialization. Each parameter is generally specified as name = value; comments start with #, and when the same parameter occurs repeatedly the last active value wins. Settings can also come from command-line -c, ALTER SYSTEM, per-database/role settings and session SET, with precedence defined by PostgreSQL's configuration system.[8]

# postgresql.conf — illustrative, not universal tuning values

listen_addresses = '127.0.0.1,10.20.0.15'
port = 5432
max_connections = 200

shared_buffers = '8GB'
work_mem = '16MB'
maintenance_work_mem = '1GB'

wal_level = 'replica'
max_wal_size = '8GB'

log_destination = 'stderr,jsonlog'
logging_collector = on
log_min_duration_statement = '500ms'
log_checkpoints = on

12.1 Inspect effective settings

SHOW shared_buffers;
SHOW work_mem;

SELECT
    name,
    setting,
    unit,
    context,
    source,
    sourcefile,
    sourceline,
    pending_restart
FROM pg_settings
WHERE name IN (
    'listen_addresses',
    'port',
    'max_connections',
    'shared_buffers',
    'work_mem',
    'maintenance_work_mem'
)
ORDER BY name;

12.2 ALTER SYSTEM

ALTER SYSTEM SET log_min_duration_statement = '500ms';
SELECT pg_reload_conf();

ALTER SYSTEM writes settings to postgresql.auto.conf, which PostgreSQL reads in addition to the main configuration. It is useful for automation, but teams should avoid splitting configuration ownership across manual files, configuration management and ad hoc ALTER SYSTEM without a defined source of truth.[8]

13. Reload versus restart

Every setting has a context that determines when and by whom it can change. A configuration reload causes the server to reread reloadable files/settings, while postmaster-context parameters require a complete server restart. Examples that require server start include listen_addresses, port, max_connections, shared_buffers and logging_collector.[9][23][32]

SELECT
    name,
    context,
    pending_restart
FROM pg_settings
WHERE pending_restart
ORDER BY name;
SELECT pg_reload_conf();
Admin rule: let pg_settings.context and pending_restart answer “reload or restart?” rather than memorizing every parameter.

14. pg_hba.conf: client authentication policy

pg_hba.conf controls client authentication. Rules are evaluated in order; PostgreSQL uses the first matching record, and there is no fallback to later records if authentication fails. Rules match connection type, database, user and client address, then select an authentication method/options.[11]

# TYPE  DATABASE   USER          ADDRESS          METHOD

local   all        postgres                       peer
local   all        all                            scram-sha-256

host    appdb      app_runtime   10.20.0.0/16     scram-sha-256
hostssl appdb      reporting     10.30.4.0/24     scram-sha-256
host    replication repl_user    10.40.0.0/24     scram-sha-256

14.1 Reload and validate

SELECT *
FROM pg_hba_file_rules
WHERE error IS NOT NULL;
SELECT pg_reload_conf();

On Unix-like systems, PostgreSQL rereads HBA rules at start and SIGHUP/reload. On Windows, edits are applied to subsequent new connections immediately. The pg_hba_file_rules view is useful for syntax/interpretation checks before relying on a change.[11]

14.2 Authentication is not authorization

A successful HBA/authentication check establishes a PostgreSQL role identity. Object privileges, role membership, row-level security and ownership then determine what that session can do. Do not use HBA rules as a replacement for SQL privilege design.[12][14]

15. pg_ident.conf: user-name mapping

pg_ident.conf maps external authenticated user names to PostgreSQL role names. It is used when an authentication mechanism supplies an external identity—such as Ident, peer/GSSAPI/SSPI scenarios—and the requested database role name differs from that identity. The selected mapping is referenced with map=... in the matching pg_hba.conf record.[13]

# pg_ident.conf
# MAPNAME       SYSTEM-USERNAME              PG-USERNAME

corp            alice@EXAMPLE.COM            alice_db
corp            bob@EXAMPLE.COM              reporting_user
# pg_hba.conf
hostgssenc appdb all 10.0.0.0/8 gss map=corp

15.1 Validate mappings

SELECT *
FROM pg_ident_file_mappings
WHERE error IS NOT NULL;

pg_ident.conf supports repeated map names, include directives and regular-expression mapping. It reloads on SIGHUP on Unix-like systems and can be moved by setting ident_file.[13][33]

16. Network configuration

listen_addresses decides which network interfaces accept TCP connection attempts. Its default is localhost, so an upstream server normally does not accept remote TCP connections until configured. port defaults to 5432. Authentication/network firewall rules are separate controls: widening listen_addresses does not by itself authorize a user, and adding HBA access does not help if the server is not listening on the relevant interface.[9]

# postgresql.conf
listen_addresses = '10.20.0.15'
port = 5432
# pg_hba.conf
hostssl appdb app_runtime 10.20.50.0/24 scram-sha-256
client | v network/firewall permits traffic? | v PostgreSQL listening on interface/port? | v pg_hba.conf first matching rule? | v authentication succeeds? | v role privileges permit SQL operation?

17. Users and roles

PostgreSQL uses one unified role model: roles can own objects, receive privileges, be members of other roles and optionally have LOGIN. CREATE USER is effectively CREATE ROLE ... LOGIN, while a role without LOGIN is commonly used as a permission group. Roles exist across the entire cluster rather than separately in each database.[14][15]

17.1 Separate ownership, runtime and human access

CREATE ROLE app_owner NOLOGIN;

CREATE ROLE app_runtime
    LOGIN
    NOSUPERUSER
    NOCREATEDB
    NOCREATEROLE
    PASSWORD 'replace-via-secure-secret-flow';

GRANT CONNECT ON DATABASE appdb TO app_runtime;
GRANT USAGE ON SCHEMA app TO app_runtime;

ALTER SCHEMA app OWNER TO app_owner;

17.2 Role attributes

AttributeMeaning
LOGINRole can be used as initial session user.
SUPERUSERBypasses nearly all database permission checks; reserve tightly.
CREATEDBCan create databases.
CREATEROLECan create/manage roles within documented limits.
REPLICATIONAllows replication protocol operations where authentication permits.
BYPASSRLSBypasses row-level security policies.
CONNECTION LIMITLimits simultaneous connections for the role.

PostgreSQL explicitly warns that superuser is dangerous and should not be used for normal work. Prefer least privilege and purpose-specific login/group/owner roles.[15]

18. Tablespaces

A tablespace registers another filesystem location in which PostgreSQL can place relation files. Tablespaces are cluster-wide objects and can be selected for databases, tables, indexes and some constraints. The target directory must already exist, be owned by the PostgreSQL OS account and be usable by the server.[34][35]

# As root/administrator:
mkdir -p /mnt/fastssd/pg_ts_fast
chown postgres:postgres /mnt/fastssd/pg_ts_fast
chmod 700 /mnt/fastssd/pg_ts_fast
CREATE TABLESPACE fastssd
OWNER app_owner
LOCATION '/mnt/fastssd/pg_ts_fast';

CREATE INDEX orders_created_idx
ON app.orders(created_at)
TABLESPACE fastssd;
Tablespaces are not portable independent disks. A tablespace belongs to one PostgreSQL cluster; filesystem backups/restores and cluster moves must preserve the cluster's tablespace relationships.[34]

19. Environment variables

libpq-based clients and most PostgreSQL utilities accept environment variables that provide default connection parameters. Core variables include PGHOST, PGPORT, PGDATABASE, PGUSER, PGSERVICE, PGPASSFILE and many SSL/authentication options. Server-side administration also commonly uses PGDATA for the cluster directory.[36][7]

export PGHOST=db.internal.example
export PGPORT=5432
export PGDATABASE=appdb
export PGUSER=app_admin

psql

19.1 Avoid PGPASSWORD in routine environments

Although PGPASSWORD exists, PostgreSQL's documentation discourages using it for security reasons on systems where process environments can be inspected. Prefer a protected password file, a secrets mechanism or stronger authentication.[36]

19.2 Password file

# ~/.pgpass
db.internal.example:5432:appdb:app_admin:secret
chmod 600 ~/.pgpass

On Unix, an overly permissive .pgpass is ignored. On Windows, the conventional file is under %APPDATA%\postgresql\pgpass.conf. PGPASSFILE can point to another password file.[37]

19.3 Connection service files

# ~/.pg_service.conf
[prod-app]
host=db.internal.example
port=5432
dbname=appdb
user=app_admin
sslmode=verify-full
PGSERVICE=prod-app psql

Service files make connection endpoints centrally configurable and are especially useful for scripts and utilities. A direct connection-string parameter overrides the corresponding service-file value.[38]

20. psql

psql is PostgreSQL's interactive terminal and scripting client. It can execute SQL from standard input/files, expose metadata through backslash meta-commands, format output, manage variables and connect using standard libpq connection parameters.[39]

psql -h db.internal.example -p 5432 -U app_admin -d appdb

20.1 Essential meta-commands

\conninfo
\l
\dn
\dt app.*
\d+ app.orders
\du
\dx
\x auto
\timing on
\watch 5

20.2 Safer scripting

psql \
  -X \
  -v ON_ERROR_STOP=1 \
  -d appdb \
  -f migration.sql

-X avoids loading a user's psqlrc, helping make automation deterministic, while ON_ERROR_STOP causes psql scripts to stop on errors instead of silently continuing. For transactionally safe migrations, combine these client behaviors with explicit transaction handling where the involved DDL permits it.

20.3 Connection URI

psql \
  'postgresql://app_admin@db.internal.example:5432/appdb?sslmode=verify-full'

21. createdb

createdb is a shell wrapper around SQL CREATE DATABASE; there is no semantic difference between creating a database through the utility and issuing the SQL command with equivalent options. The executing role normally becomes owner unless another owner is specified and the caller has sufficient privilege.[40]

createdb \
  -h localhost \
  -U postgres \
  -O app_owner \
  appdb
# SQL equivalent:
CREATE DATABASE appdb OWNER app_owner;

22. createuser

createuser is a wrapper around CREATE ROLE and creates a role with login by default. The caller needs appropriate role-management privilege; creating superuser, replication or bypass-RLS roles requires superuser authority according to PostgreSQL's role rules.[41]

createuser \
  --login \
  --no-superuser \
  --no-createdb \
  --no-createrole \
  --pwprompt \
  app_runtime

For infrastructure-as-code and repeatable privilege design, SQL CREATE ROLE/ALTER ROLE is often clearer because the resulting desired state lives beside other schema/security DDL.

23. pg_dump: logical backup

pg_dump creates a consistent logical export of one PostgreSQL database. It can dump plain SQL or archive formats. Custom (-Fc) and directory (-Fd) formats are intended for pg_restore and allow selective/parallel restore capabilities that a plain SQL script does not.[16]

23.1 Custom-format database backup

pg_dump \
  -h db.internal.example \
  -U backup_user \
  -Fc \
  -f appdb_2026-09-16.dump \
  appdb

23.2 Directory format with parallel dump

pg_dump \
  -Fd \
  -j 8 \
  -f appdb_dir \
  appdb

23.3 Schema/data selection

pg_dump --schema=app --format=custom appdb > app.dump

pg_dump --table='app.orders*' --data-only appdb > orders.sql

A logical dump is not a physical image of the cluster. It is excellent for object-level restore, migration and version-flexible logical backups, but it does not by itself capture cluster-wide roles/tablespaces; use pg_dumpall --globals-only or separately managed role/tablespace DDL for global objects.[16][42]

24. pg_restore

pg_restore restores archive files produced by non-plain pg_dump formats. It can list/select archive contents, remap ownership behavior, clean existing objects, create a target database and perform parallel restore for supported archive formats.[17]

createdb -O app_owner appdb_restore

pg_restore \
  -d appdb_restore \
  --no-owner \
  --exit-on-error \
  -j 8 \
  appdb_2026-09-16.dump

24.1 Inspect archive contents

pg_restore --list appdb_2026-09-16.dump > restore.list

Restore testing should be automated. A backup that has never been restored and validated is evidence that files exist, not evidence that recovery objectives can be met.

25. pg_basebackup: physical base backup

pg_basebackup takes a physical base backup of a running PostgreSQL cluster through the replication protocol. The result contains cluster-level physical files suitable for point-in-time recovery, standby creation and other physical recovery workflows. It backs up the entire cluster, not selected databases/tables.[18]

pg_basebackup \
  -h primary.internal.example \
  -U repl_backup \
  -D /backups/base/2026-09-16 \
  -Fp \
  -Xs \
  -P

25.1 Standby bootstrap

pg_basebackup \
  -h primary.internal.example \
  -U repl_user \
  -D /srv/postgresql/18/data \
  -R \
  -Xs \
  -P

-R writes standby connection/recovery configuration for convenient replica setup. The server must permit a replication connection and the connecting role must have the required replication/base-backup privileges.[18]

26. vacuumdb

vacuumdb is a command-line wrapper around SQL VACUUM and ANALYZE. It is useful for scripts, post-restore statistics refresh, maintenance jobs and operating across databases without embedding SQL directly.[19]

vacuumdb --analyze appdb

vacuumdb \
  --all \
  --analyze \
  --jobs=4

26.1 After a large logical restore

vacuumdb \
  --dbname=appdb_restore \
  --analyze-in-stages \
  --jobs=8

Autovacuum remains the normal ongoing maintenance mechanism. vacuumdb is not a replacement for correctly configured autovacuum; it is an explicit/manual/scheduled interface to the same maintenance commands.

27. reindexdb

reindexdb is a wrapper around SQL REINDEX. It rebuilds indexes when corruption, collation changes or measured bloat/structural inefficiency justifies a rebuild. It can operate on individual indexes/tables/schemas/databases and supports concurrent reindexing where PostgreSQL supports REINDEX CONCURRENTLY.[20][21]

reindexdb --table=app.orders appdb

reindexdb \
  --index=app.orders_created_idx \
  --concurrently \
  appdb

Do not schedule blanket reindexing merely because indexes exist. Rebuilds consume I/O, WAL, disk space and lock/concurrent-maintenance resources; trigger them from actual corruption/upgrade/collation/performance evidence.

28. Administrative operating patterns

28.1 Find the real configuration source

SELECT name, setting, source, sourcefile, sourceline
FROM pg_settings
WHERE name IN (
  'data_directory',
  'hba_file',
  'ident_file',
  'listen_addresses',
  'port'
);

28.2 Validate auth/config before disconnecting yourself

SELECT * FROM pg_hba_file_rules WHERE error IS NOT NULL;
SELECT * FROM pg_ident_file_mappings WHERE error IS NOT NULL;

SELECT pg_reload_conf();

28.3 Keep an emergency administrative path

Reserve a controlled way to connect when ordinary application connection pools exhaust the server. PostgreSQL supports reserved/superuser connection slots, and production systems should avoid consuming every available connection with application pools.[9]

28.4 Prefer role separation

NOLOGIN owner role | +-- owns schemas/tables/functions runtime login role | +-- receives only app privileges migration/deployer role | +-- elevated DDL rights backup/replication role | +-- minimum required backup/replication privileges human DBA login | +-- uses SET ROLE / approved elevation

28.5 Treat restart-required settings as change events

Changes to shared_buffers, max_connections, network listeners and other postmaster-context settings should go through normal change-control/HA procedures because a restart affects availability. Use replicas/failover or maintenance windows according to the deployment architecture.

28.6 Test restores, not only backups

For logical backups, restore into a clean database and run integrity/application checks. For physical backups, test recovery—including the required WAL and recovery target logic—in an isolated environment. Backup success logs alone do not validate recoverability.

29. Security baseline

29.1 Do not expose PostgreSQL directly unless required

Keep listen_addresses, host firewalls/security groups and HBA networks as narrow as the architecture permits. Exposing port 5432 on all interfaces plus a broad HBA rule significantly increases attack surface even when passwords are strong.

29.2 Prefer SCRAM for password authentication

PostgreSQL supports SCRAM-SHA-256 and other authentication methods. New deployments using password authentication should use SCRAM rather than legacy password approaches where client compatibility permits.[12][43]

29.3 Protect secrets

Do not commit database passwords to source repositories, container images or world-readable shell scripts. Prefer secret stores, protected password files, workload identities/Kerberos/certificates where appropriate, and short-lived credentials.

29.4 Minimize superuser

Superuser bypasses almost all database permission checks. Routine applications should never connect as superuser, and DBA workflows should prefer controlled elevation over permanently broad login roles.[15]

29.5 TLS is separate from authentication

Encrypted transport and identity authentication solve different problems. Configure ssl/hostssl and client verification as needed, while still selecting an appropriate user authentication method and SQL privilege model.[9][12]

30. Production checklist

  1. Use a supported PostgreSQL major/minor release and a documented package source.
  2. Separate package-specific paths/service units from upstream PostgreSQL behavior.
  3. Record initdb decisions: locale/provider, encoding, checksums, authentication, WAL/data locations.
  4. Run the server as a dedicated non-root OS account.
  5. Ask the server for data_directory, config_file, hba_file and ident_file; do not guess.
  6. Keep configuration under one controlled source of truth.
  7. Use pg_settings to inspect effective values, source and pending restart.
  8. Keep listen_addresses and network/firewall scope narrow.
  9. Order pg_hba.conf rules intentionally; first match wins.
  10. Validate HBA and ident files through their system views before relying on changes.
  11. Prefer SCRAM-SHA-256 for password authentication on modern deployments.
  12. Separate authentication from authorization/role privileges.
  13. Use owner, runtime, migration, backup and human roles separately where practical.
  14. Avoid application superusers.
  15. Use tablespaces only for a clear storage-placement reason and include them in backup/DR planning.
  16. Use service files or protected password files instead of hard-coded credentials.
  17. Use deterministic psql scripting such as -X and ON_ERROR_STOP.
  18. Use pg_dump/pg_restore for logical/object-level backup and migration.
  19. Capture cluster-global roles/tablespaces separately from single-database pg_dump.
  20. Use pg_basebackup plus required WAL for physical recovery/standby workflows.
  21. Automate restore tests.
  22. Keep autovacuum healthy; use vacuumdb for explicit maintenance, not as a substitute.
  23. Reindex from evidence, not on an arbitrary calendar.
  24. In containers, persist the documented PostgreSQL 18 volume path and do not confuse initialization variables with runtime reconfiguration.
  25. In managed cloud, understand which PostgreSQL privileges/settings are provider-controlled.
  26. Patch minor releases and rehearse major upgrades.
  27. Monitor disk/WAL growth, connections, locks, replication, autovacuum, checkpoints and backups.
Administration principle: keep PostgreSQL state explicit. Know which binary version is running, which cluster it owns, where configuration comes from, which identity is authenticating, which role owns data, how the service is supervised, and exactly how a backup becomes a tested restore.
