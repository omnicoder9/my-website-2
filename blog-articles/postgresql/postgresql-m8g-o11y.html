PostgreSQL Monitoring and Observability

A production-oriented guide to PostgreSQL statistics views, query observability, locks, replication lag, WAL, connections, cache behavior, disk usage, logs, Prometheus, Grafana, and OpenTelemetry.

Technical article • PostgreSQL 18.6 baseline • Updated 15 September 2026 • Vancouver-style references

Abstract

PostgreSQL observability is the process of turning database state, cumulative counters, logs, query execution data, replication state, and application traces into evidence about availability, latency, saturation, correctness, and capacity. PostgreSQL 18 exposes a rich cumulative statistics system through views such as pg_stat_activity, pg_stat_database, pg_stat_user_tables, pg_stat_user_indexes, pg_stat_replication, pg_stat_wal, and pg_stat_io. The supplied pg_stat_statements extension adds normalized query-level statistics across the server.[1][2]

Database observability should not be reduced to a single dashboard. Metrics are best for trend and alert detection; logs preserve event detail; traces connect database calls to application request paths; and direct SQL inspection remains essential during incidents. Prometheus, Grafana, and OpenTelemetry can integrate these signals, but they do not replace understanding the semantics of the PostgreSQL statistics themselves.[3]-[7]

1. An observability model for PostgreSQL

A useful PostgreSQL observability stack has four signal classes. Current-state views answer questions such as “what is running or waiting now?” Cumulative statistics show counters since a reset point. Logs preserve server events and selected statement information. Application telemetry connects database operations to request traces and service-level latency. No single class is sufficient by itself.[1][8][6]

Application request | | trace/span v PostgreSQL client call | v PostgreSQL backend process | | | | | | | +--> logs | | +-----------> pg_stat_statements | +--------------------> pg_stat_activity / pg_locks +----------------------------> cumulative pg_stat_* views | v exporter / scraper | v Prometheus | +--------+--------+ | | Grafana alerts Infrastructure metrics (CPU, RAM, disk, network) should be correlated with the database and application signals rather than viewed separately.

2. PostgreSQL statistics views

PostgreSQL's cumulative statistics system tracks server activity and exposes it through pg_stat_* and pg_statio_* views. PostgreSQL also documents ordinary operating-system tools such as ps, top, iostat, and vmstat as useful complements, because the server's own views do not replace OS-level CPU, memory, storage, and scheduler telemetry.[1]

2.1 Current versus cumulative values

Not every column has the same time semantics. For example, pg_stat_database.numbackends reflects current connections, while most other columns in that view are accumulated values since the last reset. Monitoring code should retain the reset timestamp or derive rates over time rather than treating cumulative counters as instantaneous load.[1]

2.2 Statistics visibility inside transactions

PostgreSQL can cache statistics reads inside a transaction according to stats_fetch_consistency. PostgreSQL 18 documents none, cache, and snapshot; the default is cache, while none is especially suitable for monitoring systems that want a fresh read on each access. pg_stat_clear_snapshot() clears cached statistics state in the current transaction.[9] 

SHOW stats_fetch_consistency;

-- In an interactive troubleshooting transaction, force the next
-- statistics read to refresh.
SELECT pg_stat_clear_snapshot();

2.3 Monitoring privileges

A monitoring identity does not need to be a superuser. PostgreSQL provides predefined roles including pg_monitor and pg_read_all_stats; pg_monitor includes pg_read_all_settings, pg_read_all_stats, and pg_stat_scan_tables. These roles expose privileged operational information and should still be granted deliberately.[10] 

CREATE ROLE monitoring LOGIN PASSWORD 'managed-outside-source-code';
GRANT CONNECT ON DATABASE postgres TO monitoring;
GRANT pg_monitor TO monitoring;

3. pg_stat_activity

pg_stat_activity has one row per server process associated with a database session and exposes session identity, state, current query, timestamps, wait events, transaction state, client information, and other runtime metadata. It is the primary first-response view for “what is PostgreSQL doing now?”[1]

3.1 Active sessions

SELECT
    pid,
    datname,
    usename,
    application_name,
    client_addr,
    state,
    wait_event_type,
    wait_event,
    now() - xact_start  AS transaction_age,
    now() - query_start AS query_age,
    left(query, 220) AS query
FROM pg_stat_activity
WHERE pid <> pg_backend_pid()
ORDER BY
    xact_start NULLS LAST,
    query_start NULLS LAST;

3.2 Interpret state and wait separately

The state column describes session state, while wait_event_type and wait_event explain whether the process is waiting on a lock, I/O, client interaction, WAL, IPC, timeout, or another class of event. An “active” query can still be waiting rather than consuming CPU. This distinction is crucial during latency incidents.[1]

3.3 Idle in transaction

SELECT
    pid,
    usename,
    application_name,
    client_addr,
    now() - xact_start AS xact_age,
    now() - state_change AS idle_age,
    left(query, 200) AS last_query
FROM pg_stat_activity
WHERE state = 'idle in transaction'
ORDER BY xact_start;

“Idle in transaction” sessions are especially important because a session is not executing a query but still owns an open transaction. Depending on what it previously did, that transaction may retain locks or an old snapshot and interfere with vacuum cleanup or schema changes. Monitoring should track transaction age, not only statement age.[1]

4. pg_stat_database

pg_stat_database aggregates database-wide statistics such as transactions, block reads/hits, tuples processed, temporary-file usage, conflicts, deadlocks, checksum failures, and session counts. It is a high-value source for throughput and health trends because its counters can be converted into rates by a time-series system.[1] 

SELECT
    datname,
    numbackends,
    xact_commit,
    xact_rollback,
    blks_read,
    blks_hit,
    temp_files,
    pg_size_pretty(temp_bytes) AS temp_bytes,
    deadlocks,
    checksum_failures,
    stats_reset
FROM pg_stat_database
WHERE datname IS NOT NULL
ORDER BY datname;

4.1 Derived rates

The absolute value of xact_commit rarely matters by itself; the rate of change matters. A Prometheus-like system computes transactions per second from counter deltas. The same applies to block reads, temporary bytes, deadlocks, and many other cumulative counters. 

transactions_per_second
  = rate(xact_commit + xact_rollback)

rollback_fraction
  = rate(xact_rollback)
    / rate(xact_commit + xact_rollback)

5. pg_stat_user_tables

pg_stat_user_tables is the user-table subset of the table statistics views. It exposes estimated live/dead tuple counts, sequential/index scan activity, tuple modifications, vacuum/analyze timestamps and counts, and related maintenance statistics. PostgreSQL 18 also reports time spent in manual and automatic vacuum/analyze activity.[1][11]

5.1 Dead tuples and maintenance

SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    n_mod_since_analyze,
    last_vacuum,
    last_autovacuum,
    last_analyze,
    last_autoanalyze,
    vacuum_count,
    autovacuum_count,
    analyze_count,
    autoanalyze_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 40;

5.2 Tables relying heavily on sequential scans

SELECT
    schemaname,
    relname,
    seq_scan,
    seq_tup_read,
    idx_scan,
    n_live_tup
FROM pg_stat_user_tables
WHERE seq_scan > 0
ORDER BY seq_tup_read DESC
LIMIT 40;

A high sequential-scan count is not automatically a problem: small tables and scans that return a large fraction of rows can be efficient. The statistics identify candidates for investigation; EXPLAIN (ANALYZE, BUFFERS) determines whether a specific plan is appropriate.[1][12]

6. pg_stat_user_indexes

pg_stat_user_indexes exposes user-index scan counts and tuple activity. It helps answer whether an index is being used, but usage count alone is not enough to decide that an index is useless: indexes may exist for rare critical queries, uniqueness enforcement, foreign-key-related access paths, or maintenance windows outside the observation period.[1] 

SELECT
    schemaname,
    relname,
    indexrelname,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch
FROM pg_stat_user_indexes
ORDER BY idx_scan ASC, indexrelname;

6.1 Candidate unused indexes with size

SELECT
    s.schemaname,
    s.relname,
    s.indexrelname,
    s.idx_scan,
    pg_size_pretty(pg_relation_size(s.indexrelid)) AS index_size
FROM pg_stat_user_indexes AS s
JOIN pg_index AS i
  ON i.indexrelid = s.indexrelid
WHERE s.idx_scan = 0
  AND NOT i.indisprimary
  AND NOT i.indisunique
ORDER BY pg_relation_size(s.indexrelid) DESC;
Do not automate index deletion from idx_scan = 0. Statistics can be reset, observation windows may miss periodic workloads, and an index can have correctness or operational value not visible from scan count alone.

7. pg_stat_statements

The pg_stat_statements extension tracks planning and execution statistics for SQL statements across the server. It requires shared memory, so the module must be listed in shared_preload_libraries and the server restarted when first enabled. Query identifiers must also be available; PostgreSQL automatically enables this behavior when compute_query_id is auto or on and the module is active.[2] 

# postgresql.conf
shared_preload_libraries = 'pg_stat_statements'
compute_query_id = auto
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

7.1 Top SQL by total execution time

SELECT
    queryid,
    calls,
    total_exec_time,
    mean_exec_time,
    rows,
    shared_blks_hit,
    shared_blks_read,
    temp_blks_read,
    temp_blks_written,
    wal_bytes,
    left(query, 240) AS query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 30;

7.2 Top SQL by mean latency

SELECT
    queryid,
    calls,
    mean_exec_time,
    stddev_exec_time,
    rows,
    left(query, 240) AS query
FROM pg_stat_statements
WHERE calls >= 20
ORDER BY mean_exec_time DESC
LIMIT 30;

7.3 PostgreSQL 18 additions

PostgreSQL 18 added pg_stat_statements columns for planned/launched parallel workers and for WAL-buffer-full events, making it easier to relate specific query fingerprints to parallel execution behavior and WAL pressure.[11]

7.4 Query fingerprints versus individual requests

pg_stat_statements aggregates normalized query forms; it is excellent for finding expensive query classes but does not tell you which user request experienced a particular latency spike. Application tracing fills that gap by associating an individual database call with its parent request and service context.[2][6]

8. Locks and blocking

pg_locks exposes outstanding locks from PostgreSQL's lock manager. PostgreSQL documents it as a tool for identifying ungranted locks, lock concentration on relations, and the contribution of lock contention to database performance.[13]

8.1 Waiting locks

SELECT
    pid,
    locktype,
    relation::regclass AS relation,
    mode,
    granted,
    waitstart
FROM pg_locks
WHERE NOT granted
ORDER BY waitstart NULLS LAST;

8.2 Blocking sessions

SELECT
    a.pid AS waiting_pid,
    a.usename AS waiting_user,
    a.application_name,
    pg_blocking_pids(a.pid) AS blocking_pids,
    a.wait_event_type,
    a.wait_event,
    now() - a.query_start AS waiting_for,
    left(a.query, 220) AS waiting_query
FROM pg_stat_activity AS a
WHERE cardinality(pg_blocking_pids(a.pid)) > 0
ORDER BY a.query_start;

8.3 Blocker detail

WITH waits AS (
    SELECT
        pid AS waiting_pid,
        unnest(pg_blocking_pids(pid)) AS blocking_pid
    FROM pg_stat_activity
)
SELECT
    w.waiting_pid,
    w.blocking_pid,
    ba.usename AS blocker_user,
    ba.application_name AS blocker_app,
    now() - ba.xact_start AS blocker_xact_age,
    left(ba.query, 220) AS blocker_query
FROM waits AS w
JOIN pg_stat_activity AS ba
  ON ba.pid = w.blocking_pid
ORDER BY blocker_xact_age DESC NULLS LAST;

9. Long-running queries and transactions

A long statement and a long transaction are different operational problems. query_start identifies when the current query began, while xact_start identifies the transaction's start. A transaction can remain open between statements and continue to influence locking, visibility horizons, or maintenance even when no SQL is actively executing.[1] 

SELECT
    pid,
    datname,
    usename,
    application_name,
    state,
    now() - query_start AS query_age,
    now() - xact_start AS transaction_age,
    wait_event_type,
    wait_event,
    left(query, 240) AS query
FROM pg_stat_activity
WHERE pid <> pg_backend_pid()
  AND (
      (state = 'active'
       AND query_start < now() - interval '30 seconds')
      OR
      (xact_start IS NOT NULL
       AND xact_start < now() - interval '5 minutes')
  )
ORDER BY xact_start NULLS LAST, query_start NULLS LAST;

9.1 Cancellation and termination

-- Prefer cancel when the immediate problem is one statement.
SELECT pg_cancel_backend(12345);

-- Terminate the entire session only when necessary.
SELECT pg_terminate_backend(12345);

PostgreSQL exposes server signaling functions for canceling a backend's current query or terminating the session. A monitoring account that must take such actions can be granted pg_signal_backend, though that role is operationally powerful and does not permit signaling superuser-owned backends.[10][14]

10. Replication lag

On a primary server, pg_stat_replication shows one row per directly connected WAL sender. It exposes sent, written, flushed, and replayed WAL locations and time-based lag estimates. Replication is asynchronous by default unless synchronous replication is configured, so some lag is inherent in ordinary streaming replication.[1][15]

10.1 Primary-side replication status

SELECT
    application_name,
    client_addr,
    state,
    sync_state,
    sent_lsn,
    write_lsn,
    flush_lsn,
    replay_lsn,
    write_lag,
    flush_lag,
    replay_lag
FROM pg_stat_replication
ORDER BY application_name;

10.2 Byte lag

SELECT
    application_name,
    pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS replay_lag_bytes,
    pg_size_pretty(
        pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)
    ) AS replay_lag_pretty
FROM pg_stat_replication
WHERE replay_lsn IS NOT NULL
ORDER BY replay_lag_bytes DESC;

10.3 Standby-side replay delay

SELECT
    pg_is_in_recovery() AS in_recovery,
    pg_last_wal_receive_lsn() AS receive_lsn,
    pg_last_wal_replay_lsn() AS replay_lsn,
    now() - pg_last_xact_replay_timestamp() AS replay_delay;
Timestamp lag can mislead on an idle primary. If the primary has not committed a transaction recently, the age of the last replayed commit can grow even when the standby is fully caught up. Combine timestamp-based delay with WAL-position/byte lag and replication state.

10.4 Replication-slot retention

SELECT
    slot_name,
    slot_type,
    active,
    restart_lsn,
    confirmed_flush_lsn,
    wal_status,
    safe_wal_size
FROM pg_replication_slots
ORDER BY active, slot_name;

Replication slots can intentionally retain WAL required by consumers. PostgreSQL allows max_slot_wal_keep_size to limit the amount retained by slots at checkpoint time; inactive or lagging slots should be monitored because they can create severe pg_wal growth.[15]

11. WAL statistics

pg_stat_wal reports cluster-wide WAL activity, including WAL record count, full-page images, bytes generated, WAL buffer full events, writes, syncs, and timing when WAL I/O timing is tracked. These statistics help separate query-level latency from WAL-generation and durability pressure.[1] 

SELECT
    wal_records,
    wal_fpi,
    pg_size_pretty(wal_bytes) AS wal_bytes,
    wal_buffers_full,
    wal_write,
    wal_sync,
    wal_write_time,
    wal_sync_time,
    stats_reset
FROM pg_stat_wal;

11.1 WAL generation rate

For dashboards, plot the rate of change of wal_bytes rather than the cumulative total. A sharp increase may correspond to bulk loads, index builds, mass updates, full-page-image generation after checkpoints, or simply legitimate traffic growth. Correlate WAL rate with deployment events and pg_stat_statements.wal_bytes to find SQL fingerprints responsible for the write volume.[2]

11.2 Archiver health

SELECT
    archived_count,
    last_archived_wal,
    last_archived_time,
    failed_count,
    last_failed_wal,
    last_failed_time,
    stats_reset
FROM pg_stat_archiver;

12. Connection counts

Each ordinary PostgreSQL client session is represented by a backend process, and connection capacity is finite. Monitoring should distinguish total sessions from active, idle, idle-in-transaction, waiting, and reserved administrative capacity rather than alerting on one undifferentiated count.[1] 

SELECT
    count(*) AS total_sessions,
    count(*) FILTER (WHERE backend_type = 'client backend') AS client_sessions,
    count(*) FILTER (WHERE state = 'active') AS active,
    count(*) FILTER (WHERE state = 'idle') AS idle,
    count(*) FILTER (WHERE state = 'idle in transaction') AS idle_in_transaction,
    count(*) FILTER (WHERE wait_event_type IS NOT NULL) AS waiting
FROM pg_stat_activity;

12.1 Compare with limits

SELECT
    current_setting('max_connections')::int AS max_connections,
    current_setting('superuser_reserved_connections')::int
        AS superuser_reserved_connections,
    count(*) FILTER (WHERE backend_type = 'client backend') AS used
FROM pg_stat_activity;

Connection saturation should be interpreted with pool metrics from the application tier. A database with 80% of its connection limit used might be healthy if the pool is stable and queries are short, or it might already be in trouble if pool checkout latency is rising and most sessions are blocked.

13. Cache hit ratio

A common PostgreSQL cache-hit ratio is calculated from pg_stat_database.blks_hit and blks_read. PostgreSQL explicitly states that blks_hit counts hits in the PostgreSQL shared-buffer cache only; it does not include the operating system's filesystem cache. Therefore a low or changing value is an investigation signal, not a direct measurement of physical disk misses.[1] 

SELECT
    datname,
    blks_hit,
    blks_read,
    round(
      100.0 * blks_hit
      / NULLIF(blks_hit + blks_read, 0),
      2
    ) AS shared_buffer_hit_pct
FROM pg_stat_database
WHERE datname IS NOT NULL
ORDER BY shared_buffer_hit_pct;

13.1 Table-level I/O views

SELECT
    schemaname,
    relname,
    heap_blks_read,
    heap_blks_hit,
    idx_blks_read,
    idx_blks_hit,
    toast_blks_read,
    toast_blks_hit
FROM pg_statio_user_tables
ORDER BY heap_blks_read DESC
LIMIT 30;

A better workflow than alerting on an arbitrary 99% threshold is to correlate cache ratios with read latency, pg_stat_io, storage metrics, and application performance. Large analytical scans may legitimately reduce a database-wide ratio without representing an outage.

14. Disk usage

PostgreSQL provides size functions including pg_database_size, pg_table_size, pg_indexes_size, pg_relation_size, pg_total_relation_size, and pg_tablespace_size. These report database-object storage but do not replace filesystem-level monitoring of the data directory, pg_wal, logs, temporary files, archives, and free disk space.[16][1]

14.1 Database sizes

SELECT
    datname,
    pg_size_pretty(pg_database_size(datname)) AS database_size
FROM pg_database
WHERE datallowconn
ORDER BY pg_database_size(datname) DESC;

14.2 Largest user relations

SELECT
    schemaname,
    relname,
    pg_size_pretty(pg_table_size(relid)) AS table_size,
    pg_size_pretty(pg_indexes_size(relid)) AS indexes_size,
    pg_size_pretty(pg_total_relation_size(relid)) AS total_size
FROM pg_statio_user_tables
ORDER BY pg_total_relation_size(relid) DESC
LIMIT 40;

14.3 Tablespace usage

SELECT
    spcname,
    pg_size_pretty(pg_tablespace_size(oid)) AS size
FROM pg_tablespace
ORDER BY pg_tablespace_size(oid) DESC;

A production alert should normally be based on filesystem free bytes and growth rate, not solely on SQL object totals, because WAL retention or logs can fill a disk even if ordinary table sizes are stable.[1]

15. PostgreSQL logs

PostgreSQL logging can record startup/shutdown events, errors, checkpoints, connections, lock waits, temporary files, autovacuum behavior, slow statements, and other operational events depending on configuration. log_min_duration_statement logs completed statements whose duration exceeds a configured threshold; log_min_duration_sample allows sampling to reduce volume at high traffic levels.[8]

15.1 Example logging configuration

# postgresql.conf

logging_collector = on
log_destination = 'stderr'

# Correlate log lines by time, PID, user, database, application, and client.
log_line_prefix = '%m [%p] user=%u db=%d app=%a client=%h '

# Slow statements.
log_min_duration_statement = '500ms'

# Operational events.
log_checkpoints = on
log_lock_waits = on
log_temp_files = '100MB'

# Connection lifecycle if required for the environment.
log_connections = on
log_disconnections = on

PostgreSQL recommends including a process ID or session identifier in log_line_prefix when correlating statement and duration messages. PostgreSQL 18 expanded connection logging granularity and added a %L prefix escape for client IP information.[8][11]

15.2 Logging tradeoffs

Logging every statement on a high-throughput system can create substantial volume and can expose sensitive SQL text. Prefer targeted duration thresholds, sampling, and structured application traces. Query parameters and secrets should not be intentionally collected unless there is a justified and secured operational need.

16. Prometheus

Prometheus scrapes HTTP metrics endpoints on a configured interval and stores time series identified by labels. A common PostgreSQL pattern uses prometheus-community/postgres_exporter to query PostgreSQL statistics and expose them at an HTTP /metrics endpoint. The current exporter project lists PostgreSQL 13 through 18 in its CI-tested versions and includes collectors for database, locks, replication, replication slots, activity, archiver, table statistics, WAL, and optional pg_stat_statements metrics.[3]

16.1 Exporter monitoring role

CREATE ROLE postgres_exporter LOGIN PASSWORD 'managed-secret';
GRANT CONNECT ON DATABASE postgres TO postgres_exporter;
GRANT pg_monitor TO postgres_exporter;

The exporter documentation recommends pg_monitor or pg_read_all_stats for non-superuser monitoring on supported modern PostgreSQL releases.[3][10]

16.2 Exporter example

docker run --rm \
  --network host \
  -e DATA_SOURCE_URI="localhost:5432/postgres?sslmode=require" \
  -e DATA_SOURCE_USER="postgres_exporter" \
  -e DATA_SOURCE_PASS_FILE="/run/secrets/postgres_exporter_password" \
  -v /run/secrets:/run/secrets:ro \
  quay.io/prometheuscommunity/postgres-exporter

The exporter listens on port 9187 by default and exposes metrics at /metrics. Its documentation recommends file-based password input as an alternative to putting the password directly in an environment variable.[3]

16.3 Prometheus scrape configuration

global:
  scrape_interval: 15s
  evaluation_interval: 15s

rule_files:
  - /etc/prometheus/rules/postgres.yml

scrape_configs:
  - job_name: postgres
    static_configs:
      - targets:
          - db01-exporter.internal:9187
          - db02-exporter.internal:9187

Prometheus configuration uses scrape_configs for targets and rule_files for recording and alerting rules; valid configuration can be reloaded at runtime.[4]

16.4 PromQL examples

# Transactions per second by database.
sum by (datname) (
  rate(pg_stat_database_xact_commit[5m])
  +
  rate(pg_stat_database_xact_rollback[5m])
)

# Rollbacks per second.
sum by (datname) (
  rate(pg_stat_database_xact_rollback[5m])
)

# Current PostgreSQL sessions.
sum by (datname) (
  pg_stat_database_numbackends
)

# Shared-buffer hit ratio over a moving interval.
sum by (datname) (rate(pg_stat_database_blks_hit[5m]))
/
clamp_min(
  sum by (datname) (
    rate(pg_stat_database_blks_hit[5m])
    +
    rate(pg_stat_database_blks_read[5m])
  ),
  1
)

Prometheus rate() calculates a per-second average rate for counters and accounts for counter resets; its documentation recommends applying rate() before aggregating so resets can be detected correctly.[17]

16.5 Recording rules

groups:
  - name: postgres-recording
    interval: 30s
    rules:
      - record: postgres:transactions_per_second:5m
        expr: |
          sum by (instance, datname) (
            rate(pg_stat_database_xact_commit[5m])
            +
            rate(pg_stat_database_xact_rollback[5m])
          )

      - record: postgres:shared_buffer_hit_ratio:5m
        expr: |
          sum by (instance, datname) (
            rate(pg_stat_database_blks_hit[5m])
          )
          /
          clamp_min(
            sum by (instance, datname) (
              rate(pg_stat_database_blks_hit[5m])
              +
              rate(pg_stat_database_blks_read[5m])
            ),
            1
          )

Recording rules precompute expressions at regular intervals and store the result as new time series. Prometheus provides promtool check rules for syntax validation.[18]

17. Grafana

Grafana can query Prometheus as a data source and render PostgreSQL telemetry as dashboards, panels, tables, and alerts. Grafana variables can make one dashboard reusable across environments, clusters, instances, databases, and applications by replacing hard-coded labels with selectable values.[5][19]

17.1 Recommended dashboard rows

Storage/cacheshared-buffer hit ratio, disk reads/writes, I/O latency, DB size, filesystem free space

17.2 Template variable example

# Grafana query variable:
label_values(pg_stat_database_numbackends, instance)

# Dashboard query:
sum by (datname) (
  pg_stat_database_numbackends{instance=~"$instance"}
)

Grafana's Prometheus variable support can populate values from Prometheus labels and supports regex matching for multi-value selections.[19]

17.3 Grafana alerting

Grafana can create Grafana-managed alerts that query Prometheus, while Prometheus-native alert rules can also be displayed in Grafana. The Grafana documentation recommends pending periods to avoid alerting on brief spikes and recording rules for expensive repeated expressions.[20]

18. OpenTelemetry

OpenTelemetry complements PostgreSQL server monitoring by instrumenting application database calls. Its database semantic conventions define client spans for database operations; for PostgreSQL, db.system.name is set to postgresql, and database calls normally use span kind CLIENT. This lets a trace show how much of an HTTP request's latency was spent waiting on PostgreSQL and which service issued the call.[6][21]

HTTP request span | +--> validation | +--> PostgreSQL CLIENT span | db.system.name = postgresql | db.namespace = appdb.public (when available) | db.operation = SELECT/INSERT/... (when available) | +--> downstream HTTP span | +--> response

18.1 OTLP export

# Common OpenTelemetry environment configuration.
export OTEL_SERVICE_NAME="orders-api"
export OTEL_EXPORTER_OTLP_ENDPOINT="http://otel-collector:4318"
export OTEL_EXPORTER_OTLP_PROTOCOL="http/protobuf"

OpenTelemetry defines OTLP environment variables for shared and signal-specific endpoints. With the common HTTP endpoint, exporters derive paths such as /v1/traces, /v1/metrics, and /v1/logs according to the OTLP exporter specification.[22][23]

receivers:

The OpenTelemetry Collector is designed to receive telemetry, process it, and forward it to one or more backends through signal pipelines. The exact production configuration depends on the chosen backend and security model.[24]

18.3 Java zero-code JDBC instrumentation

export JAVA_TOOL_OPTIONS="-javaagent:/opt/otel/opentelemetry-javaagent.jar"
export OTEL_SERVICE_NAME="orders-api"
export OTEL_EXPORTER_OTLP_ENDPOINT="http://otel-collector:4318"

java -jar orders-api.jar

The OpenTelemetry Java agent instruments many common libraries without application source changes. Its supported-library documentation includes JDBC database client spans and metrics. Database-statement sanitization is enabled by default in the Java agent so literal values are replaced rather than exported verbatim in captured SQL text.[25][26]

18.4 What traces add that pg_stat_statements cannot

A query fingerprint might have an acceptable average in pg_stat_statements yet be slow only for a specific API endpoint, tenant, or request fan-out path. Traces provide per-request causality and service context. Conversely, traces are sampled and application-scoped, while pg_stat_statements supplies server-wide aggregate query evidence. The signals are strongest when correlated rather than substituted for one another.

19. Alert design

An alert should identify an actionable symptom or risk, use a persistence window where brief spikes are harmless, and link to a runbook. Prometheus supports alert rules with an optional for duration so a condition must remain active before firing; Alertmanager adds notification routing, grouping, silencing, and inhibition.[27][28]

19.1 Example Prometheus rules

groups:
  - name: postgres-alerts
    rules:

      - alert: PostgreSQLExporterScrapeFailing
        expr: pg_exporter_last_scrape_error == 1
        for: 2m
        labels:
          severity: warning
        annotations:
          summary: "PostgreSQL exporter scrape is failing on {{ $labels.instance }}"

      - alert: PostgreSQLTooManyConnections
        expr: |
          sum by (instance) (pg_stat_database_numbackends)
          > 0.85 * pg_settings_max_connections
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "PostgreSQL connections exceed 85% of max"

      - alert: PostgreSQLDeadlocksIncreasing
        expr: |
          sum by (instance) (
            increase(pg_stat_database_deadlocks[10m])
          ) > 0
        labels:
          severity: warning
        annotations:
          summary: "PostgreSQL deadlocks detected"

      - alert: PostgreSQLSharedBufferHitRatioDrop
        expr: |
          postgres:shared_buffer_hit_ratio:5m < 0.90
        for: 15m
        labels:
          severity: info
        annotations:
          summary: "Shared-buffer hit ratio dropped; investigate I/O and workload"
Thresholds above are examples, not universal targets. Production thresholds should come from workload baselines and service objectives. A cache-hit ratio or connection percentage is only useful when it correlates with a real capacity or latency risk.

19.2 Alert on absence too

Monitoring should detect missing telemetry as well as bad values. Prometheus alert expressions can use target-level up or absent()-style checks so the loss of an exporter does not silently look like a healthy zero rate.[20][27]

20. Dashboard design principles

20.1 Put service symptoms first

The first row should answer whether users are affected: application database error rate, request latency, transaction throughput, and database availability. CPU, buffer hits, and WAL are diagnostic signals and belong below the symptom row.

20.2 Show rates for counters

Cumulative counters such as commits, block reads, WAL bytes, deadlocks, and temp bytes should usually be graphed as rates or interval increases. Raw cumulative values are still useful for reset detection and accounting but are poor visualizations of current load.[17]

20.3 Keep reset context visible

If PostgreSQL statistics are reset, counter rates can temporarily change and long-term totals lose continuity. Include stats_reset-derived context or exporter/process uptime panels so operators know whether a sudden drop to zero is a workload change or a counter reset.

20.4 Avoid high-cardinality labels

Do not export full SQL text, arbitrary user IDs, request IDs, or other unbounded values as Prometheus labels. Keep high-cardinality query/request detail in logs and traces; use bounded labels such as instance, database, environment, service, or query ID for metrics.

21. Incident investigation workflow

21.1 Scenario: database latency spike

  1. Confirm user impact: application p95/p99 and error rate.
  2. Check sessions: active count, pool checkout pressure, idle-in-transaction count.
  3. Check waits: pg_stat_activity.wait_event_type and blocking chains.
  4. Check expensive SQL: pg_stat_statements recent rates and top total/mean time.
  5. Check I/O: pg_stat_io, cache behavior, filesystem/storage latency.
  6. Check WAL/checkpoints: WAL generation, sync time, checkpoint activity.
  7. Check replication: if reads are routed to replicas, inspect lag and recovery conflicts.
  8. Check traces: identify which endpoints and request paths correlate with slow DB spans.
  9. Check logs: lock waits, slow statements, temp files, errors, autovacuum/checkpoint events.

21.2 Compact incident SQL

-- 1. What is active?
SELECT pid, application_name, wait_event_type, wait_event,
       now()-query_start AS age, left(query,160)
FROM pg_stat_activity
WHERE state='active'
ORDER BY query_start;

-- 2. Who is blocked?
SELECT pid, pg_blocking_pids(pid), left(query,160)
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;

-- 3. Long transactions?
SELECT pid, application_name, state, now()-xact_start AS xact_age,
       left(query,160)
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;

-- 4. Top cumulative SQL?
SELECT calls, total_exec_time, mean_exec_time,
       shared_blks_read, temp_blks_written, wal_bytes,
       left(query,160)
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;

-- 5. Replication?
SELECT application_name, state, sync_state,
       write_lag, flush_lag, replay_lag
FROM pg_stat_replication;
Observability principle: use metrics to find the time window, SQL views to inspect current database state, logs to recover event detail, and traces to explain which application operations generated the database work.
