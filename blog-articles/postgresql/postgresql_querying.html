PostgreSQL SQL & Querying

A comprehensive guide to PostgreSQL query construction and data manipulation: SELECT, INSERT, UPDATE, DELETE, MERGE, filtering, sorting, limiting, aggregation, joins, subqueries, CTEs, recursive queries, windows, set operations, LATERAL, VALUES, RETURNING, and PostgreSQL-specific DISTINCT ON.

Technical article • PostgreSQL 18.6 baseline • Updated 16 September 2026 • Vancouver-style references

Abstract

PostgreSQL implements the SQL relational query model through a composable set of statements and clauses. SELECT derives result relations from source relations; INSERT, UPDATE, DELETE, and MERGE change persistent rows; and RETURNING can expose modified rows without issuing a separate query. The same expression, subquery, join, common-table-expression, and set-operation machinery is reused across both reading and data modification.[1]-[7]

The logical processing model of a SELECT begins with CTEs and FROM sources, filters rows with WHERE, forms groups and applies HAVING, computes the output list, removes duplicates when requested, applies set operations, orders results, limits output, and finally applies row-locking clauses where present. This logical order explains common rules such as why aliases defined in the select list are unavailable in WHERE, why aggregate filters usually belong in HAVING, and why window functions must be filtered from an outer query rather than directly in WHERE.[1][8][9]

PostgreSQL adds several practically important capabilities beyond basic SQL examples: DISTINCT ON for “first row per group” queries, LATERAL for row-dependent FROM items, data-modifying CTEs, recursive WITH with standard SEARCH/CYCLE clauses, ON CONFLICT upserts, MERGE with multiple conditional actions, and explicit old/new row references in PostgreSQL 18 RETURNING lists.[1][3][6][10]

1. SELECT

SELECT retrieves rows from zero or more table-like sources and computes an output list. FROM items can be base tables, views, subqueries, CTEs, VALUES, functions, joins and LATERAL items. PostgreSQL's syntax also supports grouping sets, window definitions, set operations, ordering, limiting and row-locking clauses.[1][8]

SELECT
    o.order_id,
    o.customer_id,
    o.created_at,
    o.total_amount
FROM app.orders AS o
WHERE o.status = 'paid'
  AND o.created_at >= timestamptz '2026-09-01 00:00:00+00'
ORDER BY o.created_at DESC, o.order_id DESC
LIMIT 100;

1.1 Output expressions

SELECT
    order_id,
    total_amount,
    total_amount * 0.07 AS estimated_tax,
    upper(status) AS status_upper
FROM app.orders;

The select list consists of arbitrary value expressions, not only raw columns. Aliases label the result columns and can be used by later logical stages such as ORDER BY, subject to name-resolution rules.[11]

2. Logical processing order

The SQL text is not evaluated strictly top-to-bottom. PostgreSQL documents the conceptual processing order as CTEs, FROM sources, WHERE filtering, grouping/aggregation and HAVING, output expressions, DISTINCT, set operations, ORDER BY, LIMIT/OFFSET and row locking.[1]

WITH ↓ FROM / JOIN / LATERAL ↓ WHERE ↓ GROUP BY + aggregate calculation ↓ HAVING ↓ SELECT output expressions ↓ DISTINCT / DISTINCT ON ↓ UNION / INTERSECT / EXCEPT ↓ ORDER BY ↓ LIMIT / OFFSET / FETCH ↓ row-locking clauses

This is a semantic model; the optimizer is free to transform the physical plan while preserving query meaning.[12]

3. Filtering with WHERE

WHERE retains rows whose condition evaluates to SQL true. False and null/unknown conditions are removed. Because SQL uses three-valued logic, comparisons with null normally yield null rather than true or false; use IS NULL/IS NOT NULL when testing nullness.[8][13]

SELECT *
FROM app.orders
WHERE customer_id = 42
  AND status IN ('open', 'paid')
  AND cancelled_at IS NULL
  AND total_amount BETWEEN 50 AND 500;

3.1 Predicate placement matters with outer joins

-- Preserve customers with no paid orders:
SELECT c.customer_id, o.order_id
FROM app.customer AS c
LEFT JOIN app.orders AS o
  ON o.customer_id = c.customer_id
 AND o.status = 'paid';

Putting o.status='paid' in WHERE instead would reject the null-extended rows produced for customers with no match, changing the effective semantics toward an inner join.[8]

4. Sorting with ORDER BY

SQL does not guarantee result order unless ORDER BY is specified. PostgreSQL permits ordering by expressions, output names or select-list ordinal numbers, with per-key ASC/DESC and NULLS FIRST/NULLS LAST options.[14]

SELECT order_id, customer_id, created_at
FROM app.orders
ORDER BY
    created_at DESC,
    order_id DESC;

Multiple ordering keys are important when deterministic pagination or “first row” semantics are required. A non-unique ordering such as timestamp alone can leave peer rows in an unspecified relative order.

5. Limiting and pagination

LIMIT, OFFSET, and standard FETCH FIRST/NEXT restrict the output subset. PostgreSQL warns that a limit without a unique deterministic ORDER BY can return unpredictable subsets, and a large OFFSET can be inefficient because skipped rows still have to be computed.[15]

SELECT *
FROM app.orders
ORDER BY created_at DESC, order_id DESC
LIMIT 50 OFFSET 1000;

5.1 Keyset pagination

SELECT *
FROM app.orders
WHERE (created_at, order_id)
      < ($last_created_at, $last_order_id)
ORDER BY created_at DESC, order_id DESC
LIMIT 50;

Keyset pagination avoids repeatedly computing and discarding a growing offset and is typically better for deep, stable pagination when a suitable ordered key exists.

6. INSERT

INSERT creates rows from explicit values, DEFAULT VALUES, or a query result. Missing target columns receive their declared defaults or null if no default exists. PostgreSQL also supports ON CONFLICT for unique/exclusion-conflict handling.[3]

INSERT INTO app.customer(email, display_name)
VALUES
    ('alice@example.com', 'Alice'),
    ('bob@example.com',   'Bob')
RETURNING customer_id, email;

6.1 INSERT ... SELECT

INSERT INTO archive.orders (
    order_id,
    customer_id,
    created_at,
    total_amount
)
SELECT
    order_id,
    customer_id,
    created_at,
    total_amount
FROM app.orders
WHERE created_at < date '2024-01-01';

6.2 Upsert with ON CONFLICT

INSERT INTO app.user_setting(user_id, setting_name, setting_value)
VALUES ($1, 'theme', 'dark')
ON CONFLICT (user_id, setting_name)
DO UPDATE
SET setting_value = EXCLUDED.setting_value
RETURNING *;

ON CONFLICT DO UPDATE provides deterministic insert-or-update behavior based on a unique/exclusion conflict target.[3]

7. UPDATE

UPDATE changes column values for rows satisfying its condition. New expressions can use old row values, scalar subqueries, defaults, and columns from relations listed in PostgreSQL's FROM extension.[4]

UPDATE app.product
SET price = price * 1.05,
    updated_at = clock_timestamp()
WHERE category_id = 10
RETURNING product_id, price;

7.1 UPDATE ... FROM

UPDATE inventory.stock AS s
SET quantity = s.quantity + d.delta
FROM inventory.adjustment AS d
WHERE d.stock_id = s.stock_id
  AND d.batch_id = $1
RETURNING s.stock_id, s.quantity;
Join multiplicity matters. Ensure the FROM join produces at most one relevant source row per target row unless nondeterministic source-row choice is acceptable. Pre-aggregate or constrain the source when necessary.

8. DELETE

DELETE removes rows satisfying its condition. Omitting WHERE deletes every row. PostgreSQL supports USING to join other relations into the delete condition and RETURNING to expose deleted rows.[5]

DELETE FROM queue.job
WHERE state = 'complete'
  AND finished_at < now() - interval '90 days'
RETURNING job_id, finished_at;

8.1 DELETE ... USING

DELETE FROM app.session AS s
USING app.user_account AS u
WHERE u.user_id = s.user_id
  AND u.disabled
RETURNING s.session_id;

9. MERGE

MERGE compares a source relation with a target table and conditionally executes INSERT, UPDATE, DELETE, or DO NOTHING actions. PostgreSQL determines each candidate row's match status, then evaluates WHEN clauses in order; at most one action is taken for each candidate change row.[6]

MERGE INTO inventory.product AS p
USING staging.product_feed AS s
ON p.sku = s.sku

WHEN MATCHED
 AND s.discontinued THEN
    UPDATE SET active = false

WHEN MATCHED THEN
    UPDATE SET
        name = s.name,
        price = s.price,
        active = true

WHEN NOT MATCHED BY TARGET THEN
    INSERT (sku, name, price, active)
    VALUES (s.sku, s.name, s.price, true)

WHEN NOT MATCHED BY SOURCE
 AND p.source = 'supplier-x' THEN
    UPDATE SET active = false

RETURNING
    merge_action() AS action,
    p.product_id,
    p.sku;

MERGE is useful when several target actions depend on match status. For simple unique-key upsert, INSERT ... ON CONFLICT is often shorter and expresses conflict-driven semantics directly; MERGE is broader because it can include deletes, source-missing actions, and several ordered conditions.[3][6]

10. RETURNING

INSERT, UPDATE, DELETE, and MERGE can return rows directly from the modification. This avoids a follow-up query and makes it easy to obtain identity/default/generated values or the rows that were actually changed. PostgreSQL 18 can explicitly expose old and new row versions in supported RETURNING lists.[7]

INSERT INTO app.customer(email, display_name)
VALUES ('ada@example.com', 'Ada')
RETURNING customer_id, created_at;
UPDATE app.product
SET price = price * 1.10
WHERE product_id = 42
RETURNING
    OLD.price AS old_price,
    NEW.price AS new_price;
DELETE FROM app.session
WHERE expires_at < now()
RETURNING OLD.session_id, OLD.user_id;

The RETURNING list has select-list-like expression syntax, so computed expressions can be returned as well.[7]

11. Aggregation

Aggregate functions reduce sets of input rows to one result per group. Common examples include count, sum, avg, min, max, array_agg, jsonb_agg, and string_agg. Except for count, most built-in aggregates return null when no input rows are selected unless the query applies a fallback such as COALESCE.[16]

SELECT
    count(*) AS orders,
    sum(total_amount) AS revenue,
    avg(total_amount) AS average_order
FROM app.orders
WHERE status = 'paid';

11.1 Aggregate FILTER

SELECT
    customer_id,
    count(*) AS all_orders,
    count(*) FILTER (WHERE status = 'paid') AS paid_orders,
    sum(total_amount) FILTER (WHERE status = 'paid') AS paid_revenue
FROM app.orders
GROUP BY customer_id;

FILTER lets several differently filtered aggregates share one grouped input instead of requiring separate subqueries.[8][17]

11.2 Ordering inside aggregates

SELECT
    customer_id,
    array_agg(order_id ORDER BY created_at DESC) AS newest_first
FROM app.orders
GROUP BY customer_id;

Order-sensitive aggregates should specify ORDER BY inside the aggregate when ordering affects the result.[16]

12. GROUP BY

GROUP BY condenses rows sharing the same grouping values into one group and computes aggregate functions over each group. PostgreSQL also supports GROUPING SETS, ROLLUP, and CUBE for multiple grouping levels in one statement.[8]

SELECT
    customer_id,
    date_trunc('month', created_at) AS month,
    count(*) AS order_count,
    sum(total_amount) AS revenue
FROM app.orders
WHERE status = 'paid'
GROUP BY customer_id, date_trunc('month', created_at);

12.1 ROLLUP

SELECT
    region,
    category,
    sum(revenue) AS revenue
FROM reporting.sales
GROUP BY ROLLUP (region, category);

ROLLUP produces hierarchical subtotals, while CUBE produces combinations of grouping dimensions. GROUPING() can distinguish subtotal-generated nulls from ordinary null values.[18]

13. HAVING

WHERE filters input rows before grouping; HAVING filters group rows after grouping and aggregate computation. PostgreSQL also treats a query containing HAVING but no explicit GROUP BY as a grouped query with one implicit group.[8]

SELECT
    customer_id,
    count(*) AS orders,
    sum(total_amount) AS revenue
FROM app.orders
WHERE status = 'paid'
GROUP BY customer_id
HAVING sum(total_amount) > 10000;

If a condition can be applied before aggregation and does not depend on aggregate results, place it in WHERE so fewer rows need to participate in grouping.

14. Joins

A join combines two FROM items according to a relationship between their rows. PostgreSQL supports inner, left outer, right outer, full outer, and cross joins. Join conditions can be written with ON, USING, or NATURAL, although explicit ON/USING is generally safer for evolving schemas.[8]

JoinRows preservedTypical use
INNEROnly matching combinationsRequire relationship match
LEFTAll left rows + matchesOptional child/right data
RIGHTAll right rows + matchesEquivalent to reversed LEFT in many cases
FULLAll rows from both sidesReconciliation/difference reports
CROSSAll combinationsCartesian generation

15. Inner joins

SELECT
    o.order_id,
    c.email,
    o.total_amount
FROM app.orders AS o
JOIN app.customer AS c
  ON c.customer_id = o.customer_id
WHERE o.status = 'paid';

An inner join returns only combinations satisfying the join condition. USING is shorthand when both inputs use the same join-column names and also returns one merged copy of each named join column.[8]

SELECT *
FROM app.orders
JOIN app.customer
USING (customer_id);

16. Left, right, and full outer joins

16.1 LEFT JOIN

SELECT
    c.customer_id,
    c.email,
    o.order_id
FROM app.customer AS c
LEFT JOIN app.orders AS o
  ON o.customer_id = c.customer_id
 AND o.status = 'open';

A left join includes every matching pair plus one null-extended row for each unmatched left row. Right join mirrors this behavior with the right input preserved, while full join preserves unmatched rows from both sides.[8]

16.2 FULL JOIN reconciliation

SELECT
    a.external_id AS source_a_id,
    b.external_id AS source_b_id,
    a.amount AS a_amount,
    b.amount AS b_amount
FROM source_a.transaction AS a
FULL JOIN source_b.transaction AS b
  ON b.external_id = a.external_id
WHERE a.external_id IS NULL
   OR b.external_id IS NULL
   OR a.amount IS DISTINCT FROM b.amount;

17. Cross joins

CROSS JOIN returns the Cartesian product: every left row combined with every right row. It is equivalent to an inner join with an always-true condition. Cross joins are useful when generating combinations deliberately, but accidental Cartesian products can explode row counts.[8]

SELECT
    r.region,
    d.day
FROM reporting.region AS r
CROSS JOIN generate_series(
    date '2026-09-01',
    date '2026-09-30',
    interval '1 day'
) AS d(day);

18. Self joins

A self join is ordinary join syntax in which the same relation appears more than once under different aliases. Aliases are essential because each occurrence represents a different logical role.[1]

SELECT
    e.employee_id,
    e.name AS employee_name,
    m.name AS manager_name
FROM org.employee AS e
LEFT JOIN org.employee AS m
  ON m.employee_id = e.manager_id;

19. Subqueries

A subquery is a query embedded inside another SQL expression or FROM item. PostgreSQL supports scalar subqueries, row subqueries, derived tables, EXISTS, IN, ANY/SOME, and ALL constructs.[19]

19.1 Scalar subquery

SELECT
    p.product_id,
    p.price,
    (
        SELECT avg(price)
        FROM app.product
    ) AS average_price
FROM app.product AS p;

A scalar subquery must return at most one row and one value; zero rows produce null.

19.2 EXISTS

SELECT c.*
FROM app.customer AS c
WHERE EXISTS (
    SELECT 1
    FROM app.orders AS o
    WHERE o.customer_id = c.customer_id
      AND o.status = 'open'
);

EXISTS depends only on whether the subquery returns at least one row, so its select list is normally irrelevant and PostgreSQL can stop once existence has been established.[19]

19.3 NOT IN and nulls

NOT IN (subquery) can evaluate to null rather than true when the subquery contains null values and no equal row exists. NOT EXISTS is often easier to reason about for anti-join logic when nullability is possible.[19]

20. Correlated subqueries

A correlated subquery references columns from an outer query level. Conceptually, those outer values act as parameters for the inner query during evaluation. The optimizer can often transform correlated constructs into joins or semijoins, but the SQL semantics remain row-dependent.[19]

SELECT
    c.customer_id,
    c.email
FROM app.customer AS c
WHERE EXISTS (
    SELECT 1
    FROM app.orders AS o
    WHERE o.customer_id = c.customer_id
      AND o.total_amount > 1000
);

20.1 Correlated scalar aggregate

SELECT
    c.customer_id,
    (
        SELECT count(*)
        FROM app.orders AS o
        WHERE o.customer_id = c.customer_id
    ) AS order_count
FROM app.customer AS c;

For bulk reports, an explicit grouped join can be easier for humans to analyze and sometimes gives the planner a more obvious global aggregation opportunity. Measure both forms rather than assuming correlation is inherently slow.

21. Common table expressions (CTEs)

A WITH clause defines named query results that can be referenced by the primary statement. CTEs improve compositional readability and can also contain data-modifying statements whose RETURNING output becomes the CTE relation.[10][1]

WITH paid_orders AS (
    SELECT
        customer_id,
        total_amount
    FROM app.orders
    WHERE status = 'paid'
)
SELECT
    customer_id,
    count(*) AS orders,
    sum(total_amount) AS revenue
FROM paid_orders
GROUP BY customer_id;

21.1 CTE materialization

PostgreSQL can fold a side-effect-free, nonrecursive CTE into its parent query when it is referenced once, allowing joint optimization. MATERIALIZED can force a separate CTE result, while NOT MATERIALIZED can request folding when semantically allowed. A CTE is therefore not automatically an optimization fence in modern PostgreSQL.[10]

WITH recent AS NOT MATERIALIZED (
    SELECT *
    FROM app.orders
    WHERE created_at >= current_date - 30
)
SELECT *
FROM recent
WHERE customer_id = 42;

21.2 Data-modifying CTE

WITH moved AS (
    DELETE FROM queue.job
    WHERE state = 'complete'
      AND finished_at < now() - interval '90 days'
    RETURNING *
)
INSERT INTO archive.job
SELECT *
FROM moved;

Data-modifying CTEs execute once even if their output is not fully consumed, and sibling data-modifying CTEs conceptually share the same command snapshot. Avoid designs where several modifying CTEs target the same row because PostgreSQL documents the result as unspecified.[10]

22. Recursive CTEs

WITH RECURSIVE allows a CTE to reference itself. PostgreSQL evaluates a nonrecursive seed term, then repeatedly evaluates the recursive term using rows produced by the previous iteration until no new rows remain. Although written recursively, the implementation is iterative.[10]

WITH RECURSIVE org_tree AS (
    SELECT
        employee_id,
        manager_id,
        name,
        0 AS depth
    FROM org.employee
    WHERE employee_id = $root

    UNION ALL

    SELECT
        e.employee_id,
        e.manager_id,
        e.name,
        t.depth + 1
    FROM org.employee AS e
    JOIN org_tree AS t
      ON e.manager_id = t.employee_id
)
SELECT *
FROM org_tree
ORDER BY depth, employee_id;

22.1 Hierarchical paths

WITH RECURSIVE tree AS (
    SELECT
        employee_id,
        manager_id,
        ARRAY[employee_id] AS path
    FROM org.employee
    WHERE manager_id IS NULL

    UNION ALL

    SELECT
        e.employee_id,
        e.manager_id,
        t.path || e.employee_id
    FROM org.employee AS e
    JOIN tree AS t
      ON e.manager_id = t.employee_id
)
SELECT *
FROM tree
ORDER BY path;

22.2 SEARCH and CYCLE

PostgreSQL supports SQL-standard SEARCH DEPTH FIRST/SEARCH BREADTH FIRST clauses that synthesize an ordering column, and CYCLE clauses that mark and stop recursive paths that revisit specified keys.[1][10]

WITH RECURSIVE graph_walk(id, link, depth) AS (
    SELECT id, link, 0
    FROM graph
    WHERE id = $start

    UNION ALL

    SELECT g.id, g.link, w.depth + 1
    FROM graph AS g
    JOIN graph_walk AS w
      ON g.id = w.link
)
SEARCH DEPTH FIRST BY id SET traversal_order
CYCLE id SET is_cycle USING cycle_path
SELECT *
FROM graph_walk
ORDER BY traversal_order;

23. Window functions

A window function computes over rows related to the current output row while preserving each row's identity. The OVER clause defines partitioning, ordering, and optionally the window frame. Ordinary aggregates can become window functions when followed by OVER.[9][20]

SELECT
    customer_id,
    order_id,
    total_amount,
    sum(total_amount) OVER (
        PARTITION BY customer_id
        ORDER BY created_at, order_id
        ROWS BETWEEN UNBOUNDED PRECEDING
             AND CURRENT ROW
    ) AS running_spend
FROM app.orders;

23.1 Ranking

SELECT
    customer_id,
    order_id,
    total_amount,
    row_number() OVER (
        PARTITION BY customer_id
        ORDER BY total_amount DESC, order_id
    ) AS position,
    rank() OVER (
        PARTITION BY customer_id
        ORDER BY total_amount DESC
    ) AS amount_rank
FROM app.orders;

row_number assigns sequential numbers; rank assigns equal peer values the same rank and leaves gaps; dense_rank does not leave gaps.[20]

23.2 LAG and LEAD

SELECT
    recorded_at,
    reading,
    reading - lag(reading) OVER (
        ORDER BY recorded_at
    ) AS change_from_previous
FROM telemetry.sample;

23.3 Frame semantics

first_value, last_value, and aggregate windows operate over the current frame, not automatically the whole partition. With window ORDER BY, the default frame can end at the current row's last peer, which is frequently surprising for last_value. Specify an explicit frame when whole-partition or rolling-window semantics are intended.[20]

last_value(total_amount) OVER (
    PARTITION BY customer_id
    ORDER BY created_at
    ROWS BETWEEN UNBOUNDED PRECEDING
         AND UNBOUNDED FOLLOWING
)

23.4 Filtering window output

Window functions are logically evaluated after WHERE, GROUP BY, and HAVING, and PostgreSQL permits window calls only in the select list and ORDER BY. To filter by a window result, use a subquery or CTE.[9]

SELECT *
FROM (
    SELECT
        o.*,
        row_number() OVER (
            PARTITION BY customer_id
            ORDER BY created_at DESC, order_id DESC
        ) AS rn
    FROM app.orders AS o
) AS ranked
WHERE rn <= 3;

24. Set operations: UNION, INTERSECT, EXCEPT

Set operations combine the results of two compatible queries. The two inputs must produce the same number of columns and corresponding columns must resolve to compatible data types.[21][22]

24.1 UNION

SELECT email FROM app.customer
UNION
SELECT email FROM crm.lead;

UNION removes duplicates; UNION ALL preserves them and normally avoids duplicate-elimination work.[21]

24.2 INTERSECT

SELECT customer_id
FROM app.orders
WHERE created_at >= current_date - 30

INTERSECT

SELECT customer_id
FROM app.support_ticket
WHERE created_at >= current_date - 30;

24.3 EXCEPT

SELECT customer_id FROM app.customer
EXCEPT
SELECT customer_id FROM app.orders;

EXCEPT returns rows present in the first result but not the second. All three operators support ALL variants. INTERSECT binds more tightly than UNION and EXCEPT; parentheses should be used whenever compound-query intent could be ambiguous.[21]

25. LATERAL

LATERAL allows a FROM subquery to reference columns from FROM items to its left. PostgreSQL evaluates the lateral item for each relevant left-side row or row set, then joins the generated rows back into the query. Table functions can already reference earlier FROM columns without writing the keyword explicitly, so LATERAL is optional for function calls.[8]

25.1 Top-N child rows per parent

SELECT
    c.customer_id,
    c.email,
    recent.order_id,
    recent.created_at,
    recent.total_amount
FROM app.customer AS c
LEFT JOIN LATERAL (
    SELECT
        o.order_id,
        o.created_at,
        o.total_amount
    FROM app.orders AS o
    WHERE o.customer_id = c.customer_id
    ORDER BY o.created_at DESC, o.order_id DESC
    LIMIT 3
) AS recent
ON true;

With an index such as (customer_id, created_at DESC, order_id DESC), this form can express a very efficient bounded lookup for each selected customer.

25.2 LATERAL with set-returning functions

SELECT
    e.event_id,
    kv.key,
    kv.value
FROM app.event AS e
CROSS JOIN LATERAL
jsonb_each_text(e.payload) AS kv(key, value);

26. VALUES

VALUES creates a constant table without creating a stored table. Every row must have the same number of expressions and each result column resolves to a common compatible type using the same family of type-resolution rules as set operations.[23][22]

SELECT *
FROM (
    VALUES
        (1, 'low'),
        (2, 'medium'),
        (3, 'high')
) AS priority(code, label)
ORDER BY code;

26.1 Join application-supplied small sets

SELECT
    p.product_id,
    p.name,
    requested.quantity
FROM (
    VALUES
        (101::bigint, 2),
        (205::bigint, 1),
        (999::bigint, 5)
) AS requested(product_id, quantity)
JOIN catalog.product AS p
USING (product_id);

VALUES can be used anywhere a select-like table expression is allowed and is particularly convenient as an INSERT source or small inline lookup relation.[23]

27. PostgreSQL DISTINCT ON

DISTINCT ON (expr...) is a PostgreSQL extension that keeps the first row for each equal group of the specified expressions. The “first” row is unpredictable unless ORDER BY establishes the desired ordering, and the DISTINCT ON expressions must match the leftmost ORDER BY expressions.[1][11]

27.1 Latest row per customer

SELECT DISTINCT ON (customer_id)
    customer_id,
    order_id,
    created_at,
    total_amount
FROM app.orders
ORDER BY
    customer_id,
    created_at DESC,
    order_id DESC;

This is often the most concise PostgreSQL solution for one row per group when a deterministic ordering defines which row should win. A window-function solution is more portable and easier to extend when the requirement becomes top-N rather than top-1.

27.2 Equivalent window pattern

SELECT *
FROM (
    SELECT
        o.*,
        row_number() OVER (
            PARTITION BY customer_id
            ORDER BY created_at DESC, order_id DESC
        ) AS rn
    FROM app.orders AS o
) AS x
WHERE rn = 1;

28. Practical query patterns

28.1 Anti-join with NOT EXISTS

SELECT c.*
FROM app.customer AS c
WHERE NOT EXISTS (
    SELECT 1
    FROM app.orders AS o
    WHERE o.customer_id = c.customer_id
);

28.2 Conditional aggregation

SELECT
    customer_id,
    count(*) FILTER (WHERE status = 'open') AS open_orders,
    count(*) FILTER (WHERE status = 'paid') AS paid_orders,
    sum(total_amount) FILTER (WHERE status = 'paid') AS revenue
FROM app.orders
GROUP BY customer_id;

28.3 Top-N per group

WITH ranked AS (
    SELECT
        o.*,
        row_number() OVER (
            PARTITION BY customer_id
            ORDER BY total_amount DESC, order_id
        ) AS rn
    FROM app.orders AS o
)
SELECT *
FROM ranked
WHERE rn <= 5;

28.4 Hierarchical ancestry

WITH RECURSIVE ancestry AS (
    SELECT employee_id, manager_id, name, 0 AS level
    FROM org.employee
    WHERE employee_id = $1

    UNION ALL

    SELECT m.employee_id, m.manager_id, m.name, a.level + 1
    FROM org.employee AS m
    JOIN ancestry AS a
      ON m.employee_id = a.manager_id
)
SELECT *
FROM ancestry
ORDER BY level;

28.5 Batch delete

WITH doomed AS (
    SELECT ctid
    FROM app.event
    WHERE created_at < now() - interval '2 years'
    ORDER BY created_at
    FOR UPDATE
    LIMIT 10000
)
DELETE FROM app.event AS e
USING doomed AS d
WHERE e.ctid = d.ctid;

PostgreSQL's DELETE has no direct LIMIT. The documentation demonstrates a bounded CTE pattern for batch deletion; ctid is safe here only as a transient physical locator within the statement/batch pattern, not as persistent identity.[5]

28.6 Atomic change plus returned result

UPDATE inventory.product
SET quantity = quantity - 1
WHERE product_id = $1
  AND quantity > 0
RETURNING product_id, quantity;

The affected-row count or empty RETURNING result becomes the application-visible success test without a preceding read-then-write race.

29. Common querying pitfalls

29.1 Assuming row order without ORDER BY

Heap order, index order, parallel execution and changed plans can all alter output order. PostgreSQL explicitly documents unspecified order without ORDER BY.[1][14]

29.2 LIMIT without deterministic order

A limit over an unordered/non-unique result can return different subsets across executions or plans. Add enough ordering keys to define the result you actually mean.[15]

29.3 Large OFFSET pagination

The server must still compute rows that are skipped. Prefer keyset/cursor pagination for deep interactive result sets when possible.[15]

29.4 Turning LEFT JOIN into INNER JOIN accidentally

A right-side condition in WHERE rejects null-extended unmatched rows. Put match-specific optional-side predicates in the join's ON clause when unmatched left rows must remain.[8]

29.5 NOT IN with nullable subquery output

A null on the right can make NOT IN evaluate to unknown. Use NOT EXISTS, enforce non-nullability, or explicitly handle null semantics.[19]

29.6 Using HAVING for row filters

Filters that do not depend on grouped/aggregate values usually belong in WHERE, allowing rows to be eliminated before grouping.[8]

29.7 Assuming CTEs always materialize

Modern PostgreSQL can fold eligible single-use CTEs into the parent query. Use MATERIALIZED/NOT MATERIALIZED only when the semantic/performance tradeoff is understood.[10]

29.8 Forgetting window-frame semantics

last_value over the default ordered frame often returns the current peer group's last value rather than the partition's final value. Specify the intended frame explicitly.[20]

29.9 Using UNION when duplicates do not need removal

UNION performs duplicate elimination. Use UNION ALL when duplicate preservation is semantically correct; it can avoid unnecessary deduplication work.[21]

29.10 Ambiguous UPDATE ... FROM matches

If several source rows join to one update target row, do not rely on whichever source row happens to be chosen. Make source cardinality one-to-one by constraint, aggregation or a deterministic subquery.

29.11 Treating DISTINCT as a fix for a bad join

If a join unexpectedly multiplies rows, adding DISTINCT can hide the symptom while preserving wrong semantics and extra work. Diagnose the relationship cardinality and join predicate first.

29.12 Using MERGE when ON CONFLICT states the rule more directly

MERGE is broader, but simple unique-key upsert logic can be clearer with INSERT ... ON CONFLICT. Choose the construct that maps most directly to the concurrency/business rule.[3][6]

30. Production checklist

  1. Always define deterministic ORDER BY when result order matters.
  2. Use keyset pagination for deep/high-traffic pagination when a stable ordered key exists.
  3. Filter rows in WHERE before GROUP BY whenever the condition is row-level.
  4. Use HAVING for conditions on groups/aggregates.
  5. Use FILTER for multiple conditional aggregates over the same grouping.
  6. Place optional-side predicates carefully in outer joins.
  7. Use EXISTS/NOT EXISTS when the requirement is existence rather than returning joined rows.
  8. Handle NOT IN null semantics explicitly.
  9. Use CTEs for clarity, but understand folding/materialization behavior.
  10. Use recursive CTEs for graphs/hierarchies and protect against cycles.
  11. Specify window frames when defaults do not exactly match the requirement.
  12. Filter window results from an outer query.
  13. Prefer UNION ALL when duplicate elimination is not required.
  14. Use LATERAL for per-row dependent subqueries/functions.
  15. Use VALUES for small inline relations and bulk literal input.
  16. Use DISTINCT ON with deterministic ORDER BY for concise top-1-per-group PostgreSQL queries.
  17. Use RETURNING instead of follow-up SELECTs when you need modified row values.
  18. Use INSERT ... ON CONFLICT for conflict-driven upsert and MERGE for broader match-state workflows.
  19. Ensure UPDATE ... FROM and MERGE source cardinality matches intended target cardinality.
  20. Parameterize application queries rather than interpolating values into SQL text.
  21. Validate expensive queries with EXPLAIN (ANALYZE, BUFFERS) on representative data.
Query-design principle: SQL is declarative. Express the exact relational result and modification semantics first—rows, groups, matches, windows, set membership, and ordering—then let PostgreSQL optimize that expression. Clear cardinality and deterministic semantics are usually better optimization inputs than clever but ambiguous SQL.
