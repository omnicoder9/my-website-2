PostgreSQL Transactions & Concurrency

An expert guide to PostgreSQL transaction semantics and multiuser concurrency: ACID, transaction blocks and savepoints, isolation levels, MVCC snapshots, transaction IDs and tuple visibility, row/table/advisory locks, deadlocks, serialization failures and retry design, and distributed two-phase commit.

Technical article • PostgreSQL 18.6 baseline • Updated 16 September 2026 • Vancouver-style references

Abstract

PostgreSQL transactions group one or more SQL operations into an atomic unit that either commits as a whole or is rolled back as a whole. Statements issued outside an explicit transaction block are still transactional: PostgreSQL implicitly executes each such statement in its own transaction. Explicit blocks created with BEGIN or START TRANSACTION allow applications to coordinate multiple reads and writes under one transaction boundary and one set of transaction characteristics.[1]-[3]

Concurrency is built primarily on multiversion concurrency control (MVCC), not on read locks that exclude writers. PostgreSQL retains multiple physical tuple versions and evaluates their visibility against a snapshot. Readers normally do not block writers and writers normally do not block readers merely because they access the same rows. Explicit row/table locks remain available where applications need stronger coordination, while Serializable isolation adds Serializable Snapshot Isolation (SSI) to detect dangerous read/write dependency structures without turning ordinary reads into blocking locks.[4][5]

PostgreSQL implements three distinct isolation behaviors: Read Committed, Repeatable Read, and Serializable; a request for Read Uncommitted behaves as Read Committed. Read Committed obtains a new snapshot for each command, Repeatable Read holds a stable transaction snapshot and provides snapshot-isolation behavior, and Serializable adds conflict tracking so only executions consistent with some serial order can commit. Repeatable Read and Serializable applications must be designed to retry transactions that fail with serialization error SQLSTATE 40001.[5][6]

Locks and retries are application-level concurrency tools, not failures of MVCC. Row locks serialize modifications to specific rows; table locks protect broader resources and DDL interactions; advisory locks represent application-defined resources. Deadlocks can arise whenever transactions acquire mutually incompatible resources in inconsistent order, in which case PostgreSQL detects the cycle and aborts one participant. Two-phase commit extends transaction atomicity to external transaction managers by allowing a transaction to enter a durable prepared state before a later global commit/rollback decision.[7]-[10]

1. Transactions

A transaction bundles database operations into a single logical unit. Intermediate states are not made visible to other transactions as committed states, and an aborted transaction's database changes are discarded. PostgreSQL starts an implicit transaction around every command that is not already inside an explicit transaction block, so transactional behavior exists even when an application never writes BEGIN itself.[1][11] 

BEGIN;

UPDATE bank.account
SET balance = balance - 100
WHERE account_id = 10;

UPDATE bank.account
SET balance = balance + 100
WHERE account_id = 20;

INSERT INTO bank.transfer(
    from_account_id,
    to_account_id,
    amount
)
VALUES (10, 20, 100);

COMMIT;

If any required operation fails and the application rolls back instead of committing, the database changes made by the block do not become permanent. PostgreSQL additionally puts a transaction block into an aborted state after most statement errors; subsequent commands are rejected until the application executes ROLLBACK or rolls back to a valid savepoint.[1][12]

1.1 Transaction boundaries are semantic boundaries

Keeping a transaction open is not merely a syntactic choice. The boundary controls snapshot lifetime, row/table lock lifetime, transaction-ID horizons, resource retention, and when other sessions can observe committed effects. Transactions should cover one coherent unit of work and should generally not remain idle while waiting for human input, HTTP calls, or other unpredictable external work.

2. ACID in PostgreSQL

ACID is a conventional model for transaction guarantees: atomicity, consistency, isolation, and durability. PostgreSQL implements these properties through transaction state, constraints and SQL semantics, MVCC/isolation and locking, and WAL/crash recovery respectively. “Consistency” deserves special care: PostgreSQL can enforce constraints and transactional semantics, but it cannot infer arbitrary application business rules that were never encoded in the schema or protected by a correct concurrency protocol.[1][13][14]

PropertyOperational meaningRepresentative PostgreSQL mechanism
AtomicityA transaction's database effects commit together or are aborted together.Transaction state, WAL, rollback, subtransactions/savepoints.
ConsistencyCommitted state obeys declared database rules; application invariants require appropriate constraints/protocols.Constraints, triggers, Serializable transactions, explicit locking.
IsolationConcurrent transactions observe controlled views and interactions.MVCC snapshots, isolation levels, row/table/predicate locks.
DurabilityUnder durable settings, a successfully committed transaction survives server/system failure according to the configured commit contract.WAL, flush/fsync ordering, crash recovery.

3. Atomicity

Atomicity means the transaction boundary is all-or-nothing with respect to committed database effects. PostgreSQL does not expose a partially committed transaction merely because the transaction contains many SQL statements. ROLLBACK aborts the active transaction and discards its updates.[1][15] 

BEGIN;

UPDATE inventory.product
SET quantity = quantity - 1
WHERE product_id = 501;

INSERT INTO sales.order_line(order_id, product_id, quantity)
VALUES (9001, 501, 1);

-- application discovers an invariant violation
ROLLBACK;

3.1 Savepoints provide nested partial recovery, not partial commit

A savepoint lets an application undo work back to a point inside the transaction and continue. Releasing a savepoint merges its surviving effects into the enclosing transaction; those effects still do not become durable/visible as a committed transaction until the top-level transaction commits.[12][16]

4. Consistency

PostgreSQL can enforce declarative integrity rules such as NOT NULL, CHECK, uniqueness, primary keys, foreign keys and exclusion constraints. Such constraints prevent transactions from committing states that violate their defined rules. However, ACID consistency is not a magical inference engine: if the application requires “there must always be at least one on-call physician” or “credits must equal debits across several relations,” the application must encode and enforce that rule using an appropriate combination of constraints, Serializable isolation, locks, triggers or other well-designed transactional logic.[13][17] 

CREATE TABLE ledger.entry (
    entry_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    account_id bigint NOT NULL,
    amount numeric(18,2) NOT NULL,
    CHECK (amount <> 0)
);
Read Committed is not sufficient for every business-rule check. Two statements in one Read Committed transaction can see different committed worlds, and a “check then write” sequence can race with another transaction. Use a unique/exclusion constraint when the invariant maps to one, or use Serializable/explicit locking for broader invariants.[5][17]

5. Isolation

Isolation defines which effects of concurrent transactions a transaction may observe and how conflicting writes are handled. PostgreSQL's MVCC architecture means ordinary reads operate from snapshots rather than acquiring locks that conflict with ordinary writers. Explicit row/table locks are layered on top for coordination that MVCC snapshots alone do not provide.[4]

The SQL standard describes dirty reads, nonrepeatable reads, phantom reads and serialization anomalies. PostgreSQL's implemented isolation behavior is stronger than the minimum standard in some places: Read Uncommitted behaves as Read Committed, and PostgreSQL Repeatable Read prevents phantom reads even though the standard permits them at that level.[5]

6. Durability

PostgreSQL uses write-ahead logging to make committed changes recoverable. Under normal synchronous durable settings, the WAL records needed to represent a transaction—including the commit—are flushed to durable storage before success is returned to the client. Dirty table/index pages can be written later because crash recovery can redo the changes from WAL.[14]

transaction changes heap/index pages | v WAL records | v WAL flush through commit record | +--> COMMIT success | v data pages may be flushed later crash after acknowledged durable commit: replay WAL -> reconstruct committed changes

Durability is configurable. For example, synchronous_commit=off can acknowledge transactions before their WAL is durably flushed, risking loss of recent acknowledged transactions after a crash while preserving database consistency. More radical non-durable settings such as fsync=off have much stronger corruption risks and change the durability contract for the whole instance.[18][19]

7. BEGIN, COMMIT, and ROLLBACK

7.1 Start explicitly

BEGIN;

-- equivalent style:
START TRANSACTION;

BEGIN starts a transaction block; PostgreSQL otherwise wraps individual statements in implicit transactions.[3]

7.2 Commit

COMMIT;

COMMIT makes the current transaction's successful effects permanent according to the configured durability contract and releases transaction-level locks/resources.[1]

7.3 Roll back

ROLLBACK;

ROLLBACK aborts the current transaction and discards its updates.[15]

7.4 Transaction characteristics

BEGIN
    ISOLATION LEVEL SERIALIZABLE
    READ WRITE;

-- or early in the block:
SET TRANSACTION
    ISOLATION LEVEL REPEATABLE READ,
    READ ONLY;

Transaction isolation, read/write mode and deferrability are transaction characteristics. Serializable read-only transactions can optionally be DEFERRABLE, allowing PostgreSQL to delay snapshot acquisition until it can obtain a snapshot that is safe from serialization failures under defined conditions.[5][20]

8. Savepoints and subtransactions

Savepoints divide a transaction into recoverable subunits. ROLLBACK TO SAVEPOINT discards commands executed after the savepoint and establishes a new subtransaction at the same nesting level while retaining the named savepoint. RELEASE SAVEPOINT removes the savepoint and merges surviving changes into its enclosing transaction context.[12][16] 

BEGIN;

INSERT INTO billing.invoice(customer_id, amount)
VALUES (42, 150.00);

SAVEPOINT optional_audit;

INSERT INTO audit.event(event_type, payload)
VALUES ('invoice-created', '{"customer_id":42}');

-- Suppose this optional portion must be abandoned:
ROLLBACK TO SAVEPOINT optional_audit;

-- Continue the outer transaction.
UPDATE billing.customer
SET last_invoice_at = clock_timestamp()
WHERE customer_id = 42;

COMMIT;

8.1 Error recovery

After an error aborts the current subtransaction, rolling back to a savepoint is the mechanism for regaining a usable state without abandoning the entire outer transaction. This behavior is why client libraries and ORMs sometimes implement nested transactional scopes with savepoints.[12]

8.2 Internal subtransactions

PostgreSQL internally calls these nested units subtransactions or subxacts. They can be created explicitly through SAVEPOINT and implicitly by procedural-language exception handling. Deep or extremely numerous subtransactions have bookkeeping costs, so savepoints should represent real recovery boundaries rather than wrap every trivial statement unnecessarily.[21]

PostgreSQL implements only three distinct isolation behaviors because Read Uncommitted maps to Read Committed. PostgreSQL's Repeatable Read is stronger than the minimum SQL-standard requirement because it does not permit phantom reads.[5]

10. Read Committed

Read Committed is PostgreSQL's default isolation level. A normal SELECT sees rows committed before that statement began plus the transaction's own prior changes. A later statement in the same transaction obtains a new snapshot and may therefore see transactions that committed since the prior statement.[5]

Session A Session B --------- --------- BEGIN; SELECT balance; -- 100 UPDATE ... SET balance=150; COMMIT; SELECT balance; -- 150 COMMIT; Read Committed: each SELECT can obtain a newer snapshot.

10.1 Writes can wait and then re-evaluate

Read Committed modification commands have behavior that cannot be reduced to “everything comes from the statement's initial snapshot.” If a target row is concurrently updated, an UPDATE, DELETE, SELECT FOR UPDATE, or related command can wait for the first updater. If that updater commits, PostgreSQL re-evaluates the search condition against the updated version before deciding whether to proceed.[5]

10.2 Good default, but not universal

Read Committed is effective for many OLTP operations where each statement can be reasoned about independently or where atomic constraints/row locks enforce conflicts. It is much harder to use correctly for business rules that depend on a stable multi-statement view of changing data.[17]

11. Repeatable Read

A Repeatable Read transaction uses a stable snapshot established at its first non-transaction-control statement. Successive queries see the same committed database state, together with the transaction's own changes. Concurrent transactions can continue committing, but their later commits are not added to this transaction's snapshot.[5] 

BEGIN ISOLATION LEVEL REPEATABLE READ;

SELECT count(*)
FROM app.orders
WHERE status = 'open';

-- Other sessions can commit new open orders here.

SELECT count(*)
FROM app.orders
WHERE status = 'open';
-- same snapshot result, absent this transaction's own changes

COMMIT;

PostgreSQL implements this level as snapshot isolation. It prevents dirty reads, nonrepeatable reads and phantom reads, but it can still permit serialization anomalies where several transactions each act on a logically consistent snapshot that cannot all be placed into a single serial execution order.[5]

11.1 Updating concurrently changed rows

An updating Repeatable Read transaction can receive a serialization failure if a row it attempts to update was changed by a concurrent transaction after the Repeatable Read transaction's snapshot was established. The correct response is to abort and retry the complete transaction against a new snapshot.[5][6]

12. Serializable isolation

Serializable provides PostgreSQL's strictest isolation. Committed Serializable transactions are guaranteed to have an effect consistent with executing those transactions one at a time in some order. PostgreSQL achieves this using Serializable Snapshot Isolation: transactions use snapshot-style reads and PostgreSQL additionally tracks read/write dependencies that could form dangerous structures. When a safe serial order cannot be guaranteed, one transaction is aborted with serialization_failure rather than allowing an anomalous commit.[5] 

BEGIN ISOLATION LEVEL SERIALIZABLE;

SELECT count(*)
FROM scheduling.doctor
WHERE on_call;

-- Make a decision based on the invariant.

UPDATE scheduling.doctor
SET on_call = false
WHERE doctor_id = 101;

COMMIT;

12.1 Predicate locks are not normal blocking locks

Serializable transactions can acquire predicate locks represented in pg_locks as SIReadLock. These track read dependencies for SSI and generally do not block normal concurrent access. PostgreSQL can promote multiple fine-grained predicate locks to coarser page/relation locks to bound predicate-lock memory use.[5]

12.2 Serializable still requires retries

Serializable is not “execute with no concurrency.” It permits high concurrency but may abort a participant to preserve serializability. Applications must treat SQLSTATE 40001 as a transaction-level retry signal.[6]

12.3 Read-only deferrable transactions

BEGIN
    ISOLATION LEVEL SERIALIZABLE
    READ ONLY
    DEFERRABLE;

-- Long report using a safe snapshot.
SELECT ...;

COMMIT;

A Serializable, read-only, deferrable transaction may wait before its first query until PostgreSQL can obtain a snapshot that is safe from serialization failures, after which it can run without the normal SSI predicate-lock/retry risk described for such reporting workloads.[5]

13. MVCC

PostgreSQL's concurrency foundation is Multi-Version Concurrency Control. Updating a logical row normally creates a new physical tuple version rather than overwriting the prior committed version in place. Transactions read the tuple version that is visible to their snapshot. Once no transaction can need an old version, vacuum/pruning can reclaim it.[4][22]

logical row id=42 V1: xmin=100 xmax=125 balance=500 | +------ update by XID 125 | v V2: xmin=125 xmax=0 balance=600 older snapshot -> V1 may be visible newer snapshot -> V2 visible future cleanup -> V1 reclaimed when globally dead

The key concurrency benefit is that readers can usually continue reading an older visible version while another transaction writes a newer version. This avoids the read/write lock conflict pattern used by traditional lock-based concurrency schemes.[4]

14. Snapshots

A snapshot represents the set/horizon of transactions relevant to visibility decisions. PostgreSQL exposes snapshot values using the pg_snapshot type, which contains lower and upper transaction-ID bounds plus an array of transactions that were in progress when the snapshot was taken.[23] 

SELECT pg_current_snapshot();

SELECT
    pg_snapshot_xmin(pg_current_snapshot()) AS xmin,
    pg_snapshot_xmax(pg_current_snapshot()) AS xmax;

14.1 Snapshot lifetime depends on isolation

IsolationTypical snapshot scope
Read CommittedNew snapshot for each ordinary command.
Repeatable ReadTransaction snapshot established at first non-control statement.
SerializableStable snapshot plus SSI dependency tracking.

14.2 Exporting a snapshot

-- Session A:
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT pg_export_snapshot();
-- e.g. 00000003-0000001B-1

-- Session B, before doing work:
BEGIN ISOLATION LEVEL REPEATABLE READ;
SET TRANSACTION SNAPSHOT '00000003-0000001B-1';

PostgreSQL supports exporting/importing snapshots so separate sessions can operate against the same database view, subject to restrictions on when a snapshot may be imported and the exporting transaction remaining open.[24]

15. Transaction IDs

Every PostgreSQL transaction has a virtual transaction identifier. A normal transaction ID (XID) is assigned from a cluster-wide sequence when a transaction first needs to write. A read-only transaction can therefore have a virtual XID without having been assigned a normal XID.[11][25] 

BEGIN;

SELECT pg_current_xact_id_if_assigned();
-- NULL in a transaction that has not needed a normal XID yet

CREATE TEMP TABLE xid_demo(id integer);
INSERT INTO xid_demo VALUES (1);

SELECT pg_current_xact_id_if_assigned();

ROLLBACK;

Normal on-disk transaction identifiers have finite wraparound semantics, which is why VACUUM/freezing must eventually make very old tuple versions safe from XID wraparound. Long-running transactions, abandoned prepared transactions, and some replication slots can hold back those horizons.[11]

16. Tuple visibility

Heap tuples include transaction metadata such as the inserting transaction ID (xmin) and deleting/updating transaction state (xmax). Whether a tuple is visible depends on those fields, transaction commit/abort status, the active snapshot, and tuple status bits. An XID value alone is not enough to decide visibility without transaction state and snapshot context.[22] 

SELECT
    ctid,
    xmin,
    xmax,
    *
FROM app.account
WHERE account_id = 42;
To see tuple T, conceptually PostgreSQL asks: Was T's creating transaction visible to this snapshot? | +-- no -> tuple not visible | yes | Was T deleted/updated by a transaction visible to this snapshot? | +-- yes -> old tuple not visible | no | v tuple is visible

The actual visibility rules include many optimizations and states, but this model captures the core MVCC reasoning. System columns are useful for diagnostics but should not be used as durable application-level identity or concurrency tokens without careful semantics.[26]

17. Tuple versions and concurrent updates

An UPDATE normally produces a new heap tuple version and marks the old version as updated; a DELETE marks the prior version deleted. PostgreSQL must retain the previous version while some snapshot may still see it. This physical versioning is why long-running snapshots can contribute to dead-tuple retention and bloat.[22]

17.1 Lost-update style operations

Use atomic SQL expressions where possible rather than application read-modify-write sequences. For example, a balance increment should typically be expressed as one UPDATE balance = balance + ... statement or protected by an appropriate row lock/isolation strategy rather than reading the value into application memory and later writing an independently computed replacement.[5] 

-- Prefer an atomic database-side change:
UPDATE counter
SET value = value + 1
WHERE counter_id = 7
RETURNING value;

18. Row-level locking

PostgreSQL provides four explicit row-lock strengths through SELECT ... FOR ...: FOR UPDATE, FOR NO KEY UPDATE, FOR SHARE, and FOR KEY SHARE. Row locks block conflicting row-level writers/lockers but do not block ordinary snapshot reads. They are held until transaction end, though locks acquired after a savepoint are released if PostgreSQL rolls back to that savepoint.[7]

Locking clauseTypical purposeRelative strength
FOR UPDATEStrong row lock for planned update/delete or exclusive ownership.Strongest row lock.
FOR NO KEY UPDATEUpdate row without changing key values referenced by foreign keys.Weaker than FOR UPDATE.
FOR SHAREShared row lock preventing conflicting writes while permitting other share locks.Shared.
FOR KEY SHAREWeak shared lock protecting key/reference stability.Weakest listed row lock.

18.1 Pessimistic claim pattern

BEGIN;

SELECT *
FROM inventory.product
WHERE product_id = 501
FOR UPDATE;

-- Decide/update while the row is locked.
UPDATE inventory.product
SET quantity = quantity - 1
WHERE product_id = 501
  AND quantity > 0;

COMMIT;

18.2 Work queue with SKIP LOCKED

BEGIN;

WITH next_job AS (
    SELECT job_id
    FROM queue.job
    WHERE state = 'ready'
    ORDER BY priority DESC, job_id
    FOR UPDATE SKIP LOCKED
    LIMIT 1
)
UPDATE queue.job AS j
SET
    state = 'running',
    started_at = clock_timestamp()
FROM next_job
WHERE j.job_id = next_job.job_id
RETURNING j.*;

COMMIT;

SKIP LOCKED is useful for queue-like consumers because it avoids waiting on rows already claimed by other workers, but it intentionally provides an inconsistent view of locked rows and is not appropriate as a general substitute for normal isolation.[27]

19. Table-level locking

PostgreSQL automatically obtains table-level locks appropriate to each command, and applications can explicitly request table locks using LOCK TABLE. There are eight table lock modes, ranging from ACCESS SHARE to ACCESS EXCLUSIVE. Conflicts are defined by the lock compatibility matrix, not simply by a numeric ordering.[7]

ACCESS SHAREPlain SELECTConflicts only with ACCESS EXCLUSIVE.

ROW EXCLUSIVEINSERT, UPDATE, DELETE, MERGECommon writer table lock.
SHARE UPDATE EXCLUSIVEVACUUM (without FULL), ANALYZE, some CREATE INDEX/ALTER TABLE operationsSelf-conflicting maintenance/DDL coordination.
SHARECREATE INDEX (non-concurrent)Allows readers, conflicts with row writers.

BEGIN;

LOCK TABLE accounting.ledger
IN SHARE MODE;

-- Perform cross-table/current-state validation.

COMMIT;

Explicit table locking can enforce application consistency where non-Serializable transactions need a current globally stable view, but it reduces concurrency. Serializable transactions can often avoid such broad blocking by detecting dangerous dependency patterns instead.[17]

20. Advisory locks

Advisory locks are application-defined locks identified by either one 64-bit key or two 32-bit keys. PostgreSQL does not attach an advisory lock key to a particular row/table meaning; the application defines the resource convention. Locks can be shared or exclusive, and either session-scoped or transaction-scoped.[7][28]

20.1 Transaction-scoped advisory lock

BEGIN;

SELECT pg_advisory_xact_lock(9001);

-- Exactly one transaction at a time performs
-- application-defined work for resource 9001.

UPDATE app.resource
SET refreshed_at = clock_timestamp()
WHERE resource_id = 9001;

COMMIT;
-- lock automatically released

20.2 Try-lock pattern

SELECT pg_try_advisory_lock(42);

Try-lock functions return immediately with a Boolean result instead of waiting. Session-level advisory locks persist until explicitly unlocked or the session ends; transaction-level advisory locks automatically release at transaction end and cannot be manually released early.[28]

Advisory means cooperative. PostgreSQL will not stop another code path from modifying the underlying data unless that code path follows the same advisory-lock convention. Use row/table constraints and locks when the database itself must enforce conflict semantics.

21. Monitoring locks

The pg_locks view exposes locks known to PostgreSQL's lock manager, including relation locks, transaction/virtual-transaction locks, advisory locks and Serializable predicate locks. Row-level locks are primarily recorded in tuples and therefore do not appear as one pg_locks row per locked row; waits can appear as transaction-ID locks, and the supplied pgrowlocks extension can inspect row-lock information directly.[25][29] 

SELECT
    l.pid,
    a.usename,
    a.state,
    l.locktype,
    l.mode,
    l.granted,
    l.relation::regclass AS relation,
    l.transactionid,
    l.virtualxid,
    a.wait_event_type,
    a.wait_event,
    left(a.query, 120) AS query
FROM pg_locks AS l
LEFT JOIN pg_stat_activity AS a
  ON a.pid = l.pid
ORDER BY l.granted, l.pid;

21.1 Find blockers

SELECT
    a.pid,
    pg_blocking_pids(a.pid) AS blocking_pids,
    a.wait_event_type,
    a.wait_event,
    a.query
FROM pg_stat_activity AS a
WHERE cardinality(pg_blocking_pids(a.pid)) > 0;

pg_blocking_pids() is preferable to trying to infer every blocker by manually self-joining pg_locks, because PostgreSQL can account for lock-manager queue ordering and parallel-worker relationships.[24]

22. Deadlocks

A deadlock occurs when transactions wait in a cycle such that none can proceed without another releasing a resource. PostgreSQL automatically detects deadlock cycles and aborts one transaction so the others can continue. Deadlocks can involve row locks, table locks, advisory locks or combinations of resources.[7]

Transaction A Transaction B ------------- ------------- locks row 1 locks row 2 | | wants row 2 wants row 1 | | +---------- waits <------------+ cycle PostgreSQL detects cycle and aborts one participant.

22.1 Reproduce a row-lock deadlock

-- Session A
BEGIN;
UPDATE account SET balance = balance + 10 WHERE id = 1;
-- wait

-- Session B
BEGIN;
UPDATE account SET balance = balance + 20 WHERE id = 2;
UPDATE account SET balance = balance + 20 WHERE id = 1;
-- waits for A

-- Session A
UPDATE account SET balance = balance + 10 WHERE id = 2;
-- cycle: PostgreSQL aborts one transaction

22.2 Prevention: consistent lock order

-- Every transfer locks lower account_id first.
SELECT *
FROM account
WHERE id IN (10, 20)
ORDER BY id
FOR UPDATE;

The standard defense is to acquire multiple resources in a consistent global order and use the strongest lock mode needed as the first lock on an object when practical. Deadlocks can still occur in complex systems, so applications should also be ready to retry transactions aborted with SQLSTATE 40P01 when retry is semantically safe.[7][6]

22.3 Detection timing

PostgreSQL does not run an expensive deadlock search the instant every lock wait begins. deadlock_timeout controls how long PostgreSQL waits before checking for a deadlock; the PostgreSQL 18 default is one second. The same interval is used by log_lock_waits to decide when to log lock waits.[30]

23. Serialization failures

A serialization failure is not a deadlock. It is PostgreSQL deliberately aborting a transaction because the concurrent execution cannot safely commit under the requested isolation semantics. Both Repeatable Read and Serializable can return SQLSTATE 40001; Serializable uses this specifically to prevent serialization anomalies detected by SSI dependency tracking.[6] 

ERROR:  could not serialize access due to concurrent update
SQLSTATE: 40001

Applications should retry the complete transaction, not merely the statement that received the error. The decisions that selected which rows to read, which values to compute, and which SQL statements to issue may all have depended on the old snapshot.[6]

24. Retry architecture

Transaction retry logic belongs around the entire unit of work. PostgreSQL does not automatically retry Serializable transactions because the server cannot reproduce arbitrary application-side decisions or external interactions correctly.[6] 

# Pseudocode

for attempt in range(MAX_ATTEMPTS):
    try:
        begin_transaction(isolation="serializable")

        # All decision-making and SQL for the unit of work
        # occur inside this retry attempt.
        perform_business_transaction()

        commit()
        break

    except DatabaseError as e:
        rollback()

        if e.sqlstate not in {"40001", "40P01"}:
            raise

        sleep(backoff_with_jitter(attempt))
else:
    raise TransactionRetryExhausted()

24.1 Idempotency and external side effects

If a retried transaction triggers external effects—payment requests, emails, message publishing—the application must design those effects for idempotency or move them behind a transactional outbox/coordination mechanism. A database rollback cannot undo a remote HTTP request that has already completed.

24.2 Retry more carefully for constraint errors

PostgreSQL notes that some unique-violation (23505) and exclusion-violation (23P01) cases can reflect concurrency patterns similar to serialization conflicts, but these SQLSTATEs can also represent permanent invalid input. Unlike 40001, they should not be blindly retried without application knowledge.[6]

25. Application-level consistency patterns

25.1 Prefer constraints for local invariants

CREATE TABLE app.username (
    user_id bigint PRIMARY KEY,
    normalized_username text NOT NULL UNIQUE
);

A unique constraint lets PostgreSQL serialize conflicting insertions correctly without an application-side “SELECT then INSERT if absent” race.

25.2 Use row locking for current-row decisions

BEGIN;

SELECT quantity
FROM inventory.product
WHERE product_id = 501
FOR UPDATE;

UPDATE inventory.product
SET quantity = quantity - 1
WHERE product_id = 501
  AND quantity >= 1;

COMMIT;

25.3 Use Serializable for broad predicate invariants

When a rule depends on a set of rows or the absence of rows and cannot be represented directly as a constraint, Serializable can be simpler than manually locking every potentially relevant row/range. The application then accepts transaction retries as the concurrency-control mechanism.[17]

25.4 Broad explicit locking is sometimes appropriate

If non-Serializable writes can occur and an application must verify a global invariant against a current stable state, PostgreSQL documents explicit row or table locking as a valid strategy. Such locks trade concurrency for certainty and should be scoped narrowly.[17]

26. Two-phase commit (2PC)

PostgreSQL supports two-phase commit for coordination by an external distributed transaction manager. The local transaction performs its work, then executes PREPARE TRANSACTION. PostgreSQL persists enough state for a later COMMIT PREPARED or ROLLBACK PREPARED from any session. The transaction is no longer associated with the session after prepare.[9][10]

global transaction manager | +-------------------------+ | | v v PostgreSQL A PostgreSQL B BEGIN BEGIN changes changes PREPARE 'g-123-A' PREPARE 'g-123-B' | | +-----------+-------------+ | all participants prepared? / \ yes no | | v v COMMIT PREPARED ROLLBACK PREPARED on every system on every system

26.1 Example

-- Phase 1
BEGIN;

UPDATE finance.account
SET balance = balance - 100
WHERE account_id = 10;

PREPARE TRANSACTION 'global-payment-8f0c';

-- Later, after external coordinator decision:
COMMIT PREPARED 'global-payment-8f0c';

-- Or:
-- ROLLBACK PREPARED 'global-payment-8f0c';

26.2 Inspect prepared transactions

SELECT
    transaction,
    gid,
    prepared,
    owner,
    database
FROM pg_prepared_xacts
ORDER BY prepared;

26.3 Prepared transactions are operational liabilities if abandoned

A prepared transaction keeps its locks and can hold back vacuum/XID horizons. PostgreSQL explicitly warns that prepared transactions should normally remain prepared only briefly and recommends keeping the feature disabled unless an external transaction manager reliably resolves them. max_prepared_transactions controls how many can exist; a value of zero disables transaction preparation.[9][10]

Short-lived prepared state can remain in shared memory and WAL; prepared transactions that survive checkpoints are represented in pg_twophase state files so the decision can survive restart/crash recovery.[10][31]

27. Production concurrency patterns

27.1 Atomic inventory decrement without an explicit SELECT lock

UPDATE inventory.product
SET quantity = quantity - 1
WHERE product_id = $1
  AND quantity > 0
RETURNING quantity;

This expresses the test and write in one atomic SQL statement. Under Read Committed, concurrent updaters are coordinated through row-level update locking and PostgreSQL rechecks the qualification after relevant waits.[5]

27.2 Optimistic version column

UPDATE app.document
SET
    body = $new_body,
    version = version + 1
WHERE document_id = $id
  AND version = $expected_version
RETURNING version;

If zero rows are updated, another transaction changed the row first. This application-level optimistic concurrency pattern is often convenient for APIs, but it is separate from PostgreSQL's internal MVCC transaction IDs and avoids depending on implementation system columns.

27.3 Worker queue

BEGIN;

WITH claimed AS (
    SELECT job_id
    FROM job
    WHERE state = 'ready'
    ORDER BY priority DESC, job_id
    FOR UPDATE SKIP LOCKED
    LIMIT 10
)
UPDATE job AS j
SET state = 'running'
FROM claimed AS c
WHERE j.job_id = c.job_id
RETURNING j.*;

COMMIT;

27.4 Read-consistent reporting

BEGIN
    ISOLATION LEVEL REPEATABLE READ
    READ ONLY;

SELECT ...;
SELECT ...;
SELECT ...;

COMMIT;

This provides a stable database snapshot across a multi-query report. If the report requires protection from every serialization anomaly relative to concurrent business transactions, use Serializable semantics instead.[5]

27.5 Serializable invariant

BEGIN ISOLATION LEVEL SERIALIZABLE;

SELECT count(*) AS active_admins
FROM app.user_role
WHERE role = 'admin'
  AND active;

-- remove one only if the invariant remains valid
DELETE FROM app.user_role
WHERE user_id = $user
  AND role = 'admin';

COMMIT;

Concurrent transactions making related decisions can trigger 40001; the application retries from the beginning rather than adding broad blocking locks around all reads.[5][6]

28. Common pitfalls

28.1 Leaving transactions idle

An idle transaction can retain locks and, at snapshot-holding isolation levels or after certain activity, hold back cleanup horizons. Keep transactions short and configure idle_in_transaction_session_timeout where appropriate for application roles.[32]

28.2 Assuming Read Committed means one transaction snapshot

It does not. Read Committed normally takes one snapshot per command, so consecutive reads can legitimately see different committed results.[5]

28.3 Using Repeatable Read as though it were Serializable

PostgreSQL Repeatable Read prevents phantoms and provides a stable snapshot, but concurrent snapshot-isolation transactions can still produce a serialization anomaly. Business-rule enforcement across predicates may require Serializable or explicit locking.[5][17]

28.4 Retrying only the failed statement

For SQLSTATE 40001, retry the complete transaction including application decisions, not only the statement that failed.[6]

28.5 Inconsistent lock ordering

Locking the same set of objects in different orders across code paths is a classic deadlock generator. Define canonical ordering rules for multi-row/multi-resource operations.[7]

28.6 Assuming row locks block normal readers

A row-level lock blocks incompatible writers/lockers, not ordinary MVCC reads. A normal SELECT can still read the row version visible to its snapshot.[4][7]

28.7 Treating advisory locks as enforced data constraints

Advisory locks work only when every cooperating code path obeys the same application convention. They do not automatically protect underlying SQL rows from unconstrained operations.[28]

28.8 Leaving prepared transactions unresolved

A forgotten 2PC transaction continues holding locks and can interfere with VACUUM and transaction-ID maintenance. Monitor pg_prepared_xacts if 2PC is enabled.[9]

28.9 Treating sequences as fully transactional counters

PostgreSQL documents that sequence changes are immediately visible to other transactions and are not rolled back when the transaction that called the sequence aborts. Sequence gaps are therefore normal and should not be used as proof of transaction rollback or business-event continuity.[5]

28.10 Confusing deadlocks and serialization failures

Deadlock detection breaks a blocking wait cycle and reports 40P01; a serialization failure reports 40001 because PostgreSQL cannot allow that concurrent execution to commit under the requested isolation semantics. Both may be retryable, but they are different mechanisms.[6][7]

29. Production checklist

  1. Make transaction boundaries intentional. One transaction should represent one coherent unit of database work.
  2. Keep transactions short. Do not hold database transactions open around slow external calls or user think time.
  3. Use constraints before application “check then write” logic when an invariant maps cleanly to a database constraint.
  4. Know the snapshot model. Read Committed is statement-scoped; Repeatable Read and Serializable use stable transaction snapshots.
  5. Choose Serializable when a multi-row/predicate invariant must behave as a serial execution and transaction retry is acceptable.
  6. Build retry handling for 40001 whenever Repeatable Read or Serializable writes are used.
  7. Consider 40P01 retry handling for semantically retryable deadlocks.
  8. Retry the entire transaction.
  9. Acquire multiple locks in a consistent order.
  10. Use the weakest lock that correctly protects the invariant without relying on accidental behavior.
  11. Use SKIP LOCKED for queue-style workloads, not as a general consistency primitive.
  12. Monitor blockers with pg_stat_activity, pg_locks, and pg_blocking_pids().
  13. Distinguish advisory locks from database-enforced locks.
  14. Use savepoints for genuine partial-recovery boundaries.
  15. Remember that sequence increments are not rolled back.
  16. Use two-phase commit only with a real external transaction manager.
  17. Monitor prepared transactions and resolve them quickly.
  18. Keep durability settings aligned with business consequences. An acknowledged financial transaction should not use a durability mode intended for disposable telemetry.
  19. Test concurrency, not only single-session correctness. Important invariants should be stress-tested with concurrent sessions and deliberate failure/retry scenarios.
Concurrency principle: PostgreSQL maximizes concurrency by separating visibility from conflict. MVCC decides which tuple version a transaction may see; locks serialize operations that must not proceed together; Serializable isolation detects dependency structures that snapshots alone cannot make safe. Correct applications choose the narrowest mechanism that actually protects their invariant.
