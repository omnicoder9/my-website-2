PostgreSQL Backup & Recovery

A production-oriented guide to logical dumps, pg_dump, pg_dumpall, physical and incremental base backups, pg_basebackup, pg_restore, continuous WAL archiving, point-in-time recovery, recovery targets and timelines, disaster recovery, backup verification, and recurring recovery tests.

Technical article • PostgreSQL 18.6 baseline • Updated 15 September 2026 • Vancouver-style references

Abstract

PostgreSQL documents three fundamental backup approaches: SQL dumps, file-system-level backups, and continuous archiving. They solve different recovery problems. Logical dumps reconstruct database objects and data through SQL-level operations and are portable/selective. Physical backups copy the database cluster's files and are the normal starting point for fast whole-cluster recovery. Continuous archiving combines a physical base backup with an unbroken WAL archive so PostgreSQL can replay changes after the base backup and stop at a selected point in time, transaction, restore point, or WAL position.[1]

A backup system is defined by the recovery result it can actually produce, not by successful completion of a backup command. A pg_dump of one database does not include cluster-wide roles and tablespaces; an incremental pg_basebackup is not independently restorable; a base backup without required WAL cannot perform PITR; and a checksum/manifest verification does not prove that applications can start and operate after recovery. PostgreSQL's own pg_verifybackup documentation explicitly states that successful verification is not a substitute for test restores.[2]-[6]

A production strategy therefore begins with recovery objectives. Recovery point objective (RPO) determines how much committed data may be lost, while recovery time objective (RTO) determines how long restoration may take. Those objectives drive backup frequency, WAL archival latency, full/incremental cadence, retention, restore parallelism, off-site copies, and how often recovery exercises must be performed.

1. Backup and recovery model

Use more than one layer. A common production design keeps logical dumps for object-level portability and physical/PITR backups for whole-cluster disaster recovery. Each covers failure and recovery modes the other handles poorly.

2. RPO, RTO, and failure classes

Before choosing tools, define what must survive. An RPO of 24 hours can be satisfied by a daily snapshot if that amount of data loss is acceptable. An RPO measured in minutes or seconds normally requires frequent/off-host WAL archival or another continuously captured change stream. RTO then determines whether recovery can spend hours replaying WAL/importing dumps or needs a recent physical base backup and heavily practiced automation.

2.1 Think in failure classes

FailureLikely recovery mechanism
Accidentally dropped one tableRestore table from logical dump or restore physical/PITR copy elsewhere and extract table.
Bad deployment at 14:06PITR to just before the damaging transaction if rolling forward is not feasible.
Entire data volume lostPhysical base backup + WAL archive, or logical rebuild if dataset/RTO permit.
Primary and replicas corrupted by replicated mistakeIndependent backup/PITR repository.
Need cross-major migrationpg_dump/pg_restore, pg_upgrade, or logical replication—not raw physical restore into a different major release.
Need one user's row from yesterdayRecover backup/PITR to isolated server, extract data, reconcile selectively.

3. Logical backups

A logical backup represents database objects and data independently of PostgreSQL's on-disk page layout. pg_dump exports one database; pg_dumpall can export every database plus cluster-wide global objects. Logical dumps are consistent while the database is in use and do not block ordinary readers or writers, although they take locks that protect dumped objects from conflicting DDL while the dump is running.[2][3]

3.1 Strengths

Logical backups are selective, inspectable, and useful for migrations. Archive-format dumps let pg_restore select and reorder objects and can restore data/index creation in parallel. They are particularly valuable when one schema/table must be recovered without replacing the whole cluster.[2][4]

3.2 Limitations

Large logical restores can take substantially longer than physical recovery because PostgreSQL must create objects, load rows, build indexes, and validate constraints. pg_dump covers one database and does not include cluster-global roles/tablespaces. PostgreSQL's pg_dump documentation also cautions that it is generally not the right primary mechanism for regular production backups except in simpler cases.[2]

4. pg_dump

4.1 Plain SQL dump

pg_dump \
  --host=db.internal \
  --username=backup_user \
  --dbname=appdb \
  --file=appdb-2026-09-15.sql
# Restore with psql, not pg_restore:
createdb -T template0 appdb_restore

psql \
  -X \
  --dbname=appdb_restore \
  --file=appdb-2026-09-15.sql

Plain-text output contains SQL commands and is restored through psql. PostgreSQL recommends psql -X for plain dump restoration so local psqlrc settings do not interfere with the restore.[2]

4.2 Custom archive

pg_dump \
  --format=custom \
  --compress=zstd:6 \
  --dbname=appdb \
  --file=appdb-2026-09-15.dump

Custom-format archives are consumed by pg_restore, support selective restore, and permit parallel restore.[2][4]

4.3 Directory archive with parallel dump

pg_dump \
  --format=directory \
  --jobs=8 \
  --dbname=appdb \
  --file=/backup/appdb-2026-09-15

Parallel dump is supported by directory format. PostgreSQL opens the leader connection plus worker connections, so the connection limit and production load must be considered.[2]

4.4 Selective logical backup

# Schema:
pg_dump -Fc -n billing appdb > billing.dump

# Table and its matching patterns:
pg_dump -Fc -t 'audit.*' appdb > audit.dump

# Schema only:
pg_dump -Fc --schema-only appdb > appdb-schema.dump

# Data only:
pg_dump -Fc --data-only appdb > appdb-data.dump
Selective dumps can omit dependencies. PostgreSQL does not guarantee that a schema/table-only dump can restore into an empty database by itself because objects outside the selection may be required.[2]

4.5 Version rules

A newer pg_dump can generally dump older PostgreSQL servers, but pg_dump refuses to dump a server newer than its own major version. Dump output is intended to load into newer server versions; loading into an older major version is not guaranteed and can require manual changes.[2]

5.1 Parallel restore

createdb -T template0 appdb_restore

pg_restore \
  --dbname=appdb_restore \
  --jobs=8 \
  --exit-on-error \
  appdb-2026-09-15.dump

For custom/directory archives, pg_restore -j parallelizes time-consuming data loads, index creation, and constraint creation using multiple database sessions. PostgreSQL advises tuning job count to CPU, disk, client/server placement, and workload; excessive concurrency can cause contention.[4]

6. pg_dumpall and cluster-global objects

pg_dumpall generates a SQL script for all databases and includes global objects that pg_dump does not: database roles, tablespaces, and grants for configuration parameters. Internally it invokes pg_dump for each database.[3]

6.1 Full cluster logical script

pg_dumpall \
  --file=cluster-2026-09-15.sql
psql -X \
  --dbname=postgres \
  --file=cluster-2026-09-15.sql

6.2 Globals-only companion backup

pg_dumpall \
  --globals-only \
  --file=globals-2026-09-15.sql

A practical design is to dump each large application database in custom/directory format for parallel restore and separately dump cluster globals with pg_dumpall --globals-only.

6.3 Role-password sensitivity

pg_dumpall \
  --globals-only \
  --no-role-passwords \
  --file=globals-no-passwords.sql

By default, a complete globals dump can contain password verifiers for roles. PostgreSQL provides --no-role-passwords when those should not be included, but restored roles then require passwords to be set before password authentication can succeed.[3]

7. Logical restore workflow

archive | +--> restore cluster globals (if needed) | +--> create empty database from template0 | +--> restore pre-data schema | +--> load table data (parallel where possible) | +--> create indexes / constraints / triggers | +--> restore grants / comments / statistics (when present) | +--> ANALYZE as needed | +--> application validation

7.1 Restore into a truly empty database

createdb \
  --template=template0 \
  appdb_restore

pg_restore \
  --dbname=appdb_restore \
  --jobs=8 \
  --exit-on-error \
  appdb.dump

PostgreSQL recommends template0 when an empty destination is required so local additions to template1 do not collide with objects from the dump.[4]

7.2 Restore roles first when ownership matters

psql -X \
  --dbname=postgres \
  --file=globals.sql

createdb -T template0 appdb_restore

pg_restore \
  --dbname=appdb_restore \
  appdb.dump

Object ownership and ACL recreation can fail if referenced roles do not exist. Restoring required roles before database objects avoids that class of failure.

8. pg_restore

pg_restore restores non-plain pg_dump archives. It can restore directly to a database or emit an equivalent SQL script, selectively include/exclude objects, reorder archive entries, and parallelize data/index/constraint work for custom and directory archives.[4]

8.1 Recreate original database

pg_restore \
  --clean \
  --if-exists \
  --create \
  --dbname=postgres \
  appdb.dump

With --create, the database specified to --dbname is used only as the initial connection from which the database embedded in the archive is dropped/created; restore then reconnects to that database.[4]

8.2 Inspect archive before restore

pg_restore \
  --list \
  appdb.dump \
  > appdb.list
# Edit appdb.list, comment/reorder items, then:
pg_restore \
  --use-list=appdb.list \
  --dbname=appdb_restore \
  appdb.dump

8.3 Restore one schema/table

pg_restore \
  --schema=billing \
  --dbname=appdb_restore \
  appdb.dump

pg_restore \
  --table=invoice \
  --dbname=appdb_restore \
  appdb.dump

Selective restore does not automatically restore every dependency of the selected object. Validate the target schema and dependency graph rather than assuming a table-only restore is self-contained.[4]

8.4 Transaction strategies

# Atomic all-or-nothing restore:
pg_restore \
  --single-transaction \
  --dbname=appdb_restore \
  appdb.dump

# PostgreSQL 18: bounded object batches:
pg_restore \
  --transaction-size=2000 \
  --dbname=appdb_restore \
  appdb.dump

PostgreSQL 18 supports --transaction-size, which offers a middle ground between one transaction per command and one enormous restore transaction. The latter can consume large amounts of lock-table space in large schemas.[4]

9. Physical backups

A physical backup copies the PostgreSQL cluster's storage files in a form usable by the PostgreSQL server. It includes all databases in that cluster and is tied to PostgreSQL's physical storage format. Physical backups are therefore ideal for rapid cluster recovery but are not the mechanism for selectively restoring one table or moving arbitrarily between major server versions.[1][5]

9.1 What must be consistent

PostgreSQL data spans the main data directory plus any tablespace directories. A naive live filesystem copy can capture mutually inconsistent pages unless PostgreSQL's online backup protocol/base-backup tooling or a filesystem snapshot strategy satisfying PostgreSQL's consistency requirements is used. Stopping the server and copying every required file is conceptually simple, while pg_basebackup is the normal online physical backup tool.[1][12]

10. pg_basebackup

pg_basebackup takes an online physical backup of a running PostgreSQL cluster using the replication protocol. A full backup is an exact cluster copy; PostgreSQL 18 also supports incremental base backups. The utility automatically manages PostgreSQL backup mode and can include/stream the WAL needed to make the resulting backup internally recoverable.[5]

10.1 Replication role and HBA

CREATE ROLE backup_repl
LOGIN
REPLICATION
PASSWORD 'managed-out-of-band';
# pg_hba.conf
hostssl replication backup_repl 10.20.30.0/24 scram-sha-256

10.2 Plain full backup

pg_basebackup \
  --host=pg-primary.internal \
  --username=backup_repl \
  --pgdata=/backup/full/2026-09-15 \
  --format=plain \
  --wal-method=stream \
  --checkpoint=fast \
  --progress

The replication account must have REPLICATION or superuser rights, HBA must permit the replication connection, and max_wal_senders must have capacity for the backup connection plus an extra sender when WAL is streamed concurrently.[5]

10.3 Tar-format backup

pg_basebackup \
  --host=pg-primary.internal \
  --username=backup_repl \
  --pgdata=/backup/tar/2026-09-15 \
  --format=tar \
  --compress=zstd:6 \
  --wal-method=stream \
  --progress

10.4 Take backup from a standby

pg_basebackup can run against a suitably configured standby, which can offload backup I/O from the primary. PostgreSQL documents limitations: the primary must use full_page_writes, backup may wait for needed WAL under some modes, and the backup fails if the standby is promoted while the backup is running.[5]

10.5 Monitor base-backup progress

SELECT
    pid,
    phase,
    backup_total,
    backup_streamed,
    tablespaces_total,
    tablespaces_streamed
FROM pg_stat_progress_basebackup;

PostgreSQL exposes active base-backup progress through pg_stat_progress_basebackup on the server.[13]

11. Incremental physical backups

PostgreSQL 18 can take an incremental base backup relative to the manifest of an earlier backup from the same cluster. For relation files, the incremental can store only blocks changed since the reference backup; non-relation files are generally included in full. PostgreSQL determines changed blocks from WAL summary files under pg_wal/summaries.[6][14]

11.1 Enable WAL summarization

# postgresql.conf
summarize_wal = on

Incremental backup requires suitable WAL summaries to exist for the needed interval. If required summaries are unavailable, the incremental backup fails.[6]

11.2 Take an incremental backup

pg_basebackup \
  --host=pg-primary.internal \
  --username=backup_repl \
  --pgdata=/backup/incr/2026-09-16 \
  --incremental=/backup/full/2026-09-15/backup_manifest \
  --wal-method=stream \
  --progress

11.3 Backup dependency graph

Full F0 | +--> Incremental I1 | +--> Incremental I2 | +--> Incremental I3 To recover I3 state: F0 + I1 + I2 + I3 | v pg_combinebackup | v synthetic/reconstructed full backup

PostgreSQL does not maintain an external backup catalog that knows which older backups remain required by future incrementals. Operators must track chain dependencies and avoid deleting an ancestor needed to reconstruct a retained descendant.[6]

11.4 When incremental backups help

They are most useful for large clusters where only a modest fraction of relation blocks changes between backups. For small databases or highly rewritten data sets, full backups can be simpler and may provide little additional storage cost relative to incrementals.[6]

12. pg_combinebackup

An incremental base backup cannot be used directly as a PostgreSQL data directory. pg_combinebackup combines a full backup and all dependent incremental backups into a reconstructed full backup suitable for recovery. Input backups must be specified in chronological order.[7] 

pg_combinebackup \
  /backup/full/2026-09-15 \
  /backup/incr/2026-09-16 \
  /backup/incr/2026-09-17 \
  --output=/restore/full-2026-09-17

12.1 Verify the reconstructed backup

pg_verifybackup \
  /restore/full-2026-09-17

By default, pg_combinebackup creates a new backup manifest for the reconstructed backup, which allows subsequent integrity verification.[7]

13. WAL archiving

Continuous archiving relies on preserving completed WAL segment files outside pg_wal. Once PostgreSQL successfully archives a segment, the local segment can eventually be recycled or removed; the external archive must retain every WAL segment required to recover retained base backups through their desired recovery windows.[6]

13.1 Enable archiving

# postgresql.conf
wal_level = replica
archive_mode = on

archive_command =
  'test ! -f /mnt/postgres-wal/%f && cp %p /mnt/postgres-wal/%f'

%p expands to the source WAL path and %f to its file name. The command must return zero only after successful archival. PostgreSQL repeatedly retries a failed archive command, so archive destinations/scripts should be idempotent and must not silently overwrite an existing segment with different contents.[6][15]

13.2 Archive module alternative

# Example module supplied by PostgreSQL:
archive_mode = on
archive_library = 'basic_archive'
basic_archive.archive_directory = '/mnt/postgres-wal'

PostgreSQL supports archive_library modules as an alternative to shell-based archive_command. The documentation notes that an archive module can be more robust and performant than invoking a shell command for each archived segment; basic_archive is supplied as a working example rather than a complete remote backup product.[16][17]

13.3 Force a WAL switch

SELECT pg_switch_wal();

Archiving normally occurs after a segment completes. pg_switch_wal() forces PostgreSQL to begin a new WAL segment so a partially used current segment becomes archivable.[18]

13.4 Archive timeout

# Example only; choose from RPO and WAL volume:
archive_timeout = '5min'

archive_timeout can force WAL segment switches when workload is quiet, reducing how long committed WAL waits in the current segment before archiving. PostgreSQL warns against excessively short values because prematurely closed segments still consume full segment-sized archive storage.[15]

Archive-command failure is a storage incident. If archiving cannot succeed, PostgreSQL retains WAL in pg_wal. Persistent archival failure can consume the filesystem and eventually threaten database availability.

14. Continuous archiving

The continuous-archive model combines two artifacts: a base backup and all archived WAL needed after that backup. During recovery, PostgreSQL restores the physical files from the base backup, then repeatedly obtains archived WAL and replays it forward. This can reconstruct the database to a much later point than the base backup itself.[6]

time ------------------------------------------------------------> Base backup B0 | v [cluster files] \ + WAL 001 + WAL 002 + WAL 003 + WAL 004 + WAL 005 + ... Restore: B0 + WAL 001 + 002 + 003 + 004 ^ | recovery target here

14.1 Why base-backup age matters

An older retained base backup can still be used if every required WAL segment remains available, but recovery then has more WAL to replay. Base-backup cadence therefore affects RTO even when the WAL archive can satisfy the RPO.[6]

14.2 Keep the chain complete

A missing required WAL file can make an otherwise intact base backup unrecoverable to later points. Retention policies must consider the oldest retained recoverable base/incremental chain and retain the WAL required from that backup through the end of its advertised recovery window.

15. Point-in-time recovery (PITR)

PITR restores a physical backup and replays WAL until a configured recovery target. In PostgreSQL 12 and later, recovery settings live in normal server configuration and archive recovery is requested by creating recovery.signal in the data directory. The old recovery.conf mechanism has been removed.[8]

15.1 Typical restore procedure

# 1. Stop PostgreSQL.
systemctl stop postgresql

# 2. Move damaged/current data directory aside.
mv /var/lib/postgresql/18/main \
   /var/lib/postgresql/18/main.failed

# 3. Restore a full/reconstructed base backup.
cp -a /restore/full-2026-09-15 \
      /var/lib/postgresql/18/main

# 4. Ensure ownership.
chown -R postgres:postgres \
    /var/lib/postgresql/18/main

# 5. Request archive recovery.
touch /var/lib/postgresql/18/main/recovery.signal
# postgresql.conf / postgresql.auto.conf in restored cluster
restore_command =
  'cp /mnt/postgres-wal/%f %p'

recovery_target_time =
  '2026-09-15 14:05:59-04'

recovery_target_action = 'promote'
# 6. Start in isolated/restricted environment and watch recovery logs.
systemctl start postgresql

The precise filesystem/service commands are environment-specific. The PostgreSQL semantics are that restore_command must retrieve requested archived WAL, recovery.signal enables targeted archive recovery, and the recovery target controls where replay stops.[6][8][9]

15.2 Prefer isolation during forensic recovery

When recovering from operator error or compromise, start the restored cluster away from normal application traffic. Validate the target point before exposing it, because choosing a target after the damaging transaction simply reconstructs the damaged state.

16. Recovery targets

PostgreSQL supports several mutually exclusive recovery targets. At most one of recovery_target, recovery_target_lsn, recovery_target_name, recovery_target_time, or recovery_target_xid may be configured. If none is set, archive recovery normally replays to the end of available WAL.[9]

TargetExampleUse
Earliest consistent pointrecovery_target = 'immediate'Recover only to the point where the restored online backup becomes consistent.
Timerecovery_target_time = '2026-09-15 14:05:59-04'Common operator-error recovery target.
Named restore pointrecovery_target_name = 'before_release_2026_09_15'Recover to an application/deployment marker.
Transaction IDrecovery_target_xid = '123456789'Stop around a known transaction ID.
WAL LSNrecovery_target_lsn = '5A/12345678'Precise WAL-position recovery.

16.1 Inclusive target

recovery_target_time = '2026-09-15 14:06:00-04'
recovery_target_inclusive = off

For time, XID, and LSN targets, recovery_target_inclusive controls whether recovery includes transactions exactly at the target boundary. The default is on.[9]

16.2 Action at the target

# Default:
recovery_target_action = 'pause'

# Or:
recovery_target_action = 'promote'

# Or:
recovery_target_action = 'shutdown'

Pausing is useful when an operator wants to inspect the recovered state before promotion. A disaster-recovery automation may use promote after an already validated target policy.[9]

17. Named restore points

A restore point writes a named marker into WAL. It is useful before risky deployments, schema migrations, bulk jobs, or other known operational boundaries.[18] 

SELECT pg_create_restore_point(
    'before_billing_release_2026_09_15'
);

During recovery:

restore_command =
  'cp /mnt/postgres-wal/%f %p'

recovery_target_name =
  'before_billing_release_2026_09_15'

recovery_target_action = 'pause'
A restore point is only a WAL marker. It does not create a backup. Recovery to the marker still requires a suitable earlier base backup and an uninterrupted WAL chain through that marker.

18. Recovery timelines

PostgreSQL creates a new timeline when archive recovery completes and the server begins a new history. Timeline history files allow recovery to follow branches and later recover to points after previous PITR operations without confusing WAL from divergent histories.[6]

timeline 1: ----A----B----C----D | PITR/promote | timeline 2: +----E----F | later PITR | timeline 3: +----G
# Usually appropriate:
recovery_target_timeline = 'latest'

latest is PostgreSQL's default and follows the latest timeline found in the archive. Explicit timeline selection is mainly needed in more complex re-recovery scenarios.[9]

19. File-system-level backups

A cold filesystem backup made while PostgreSQL is cleanly shut down is straightforward: copy the complete cluster data directory and every tablespace. A live raw file copy without PostgreSQL's backup protocol or a sufficiently coordinated filesystem snapshot is unsafe because files can be captured at inconsistent points.[1][12]

19.1 Cold backup shape

systemctl stop postgresql

rsync -aHAX \
  /var/lib/postgresql/18/main/ \
  /backup/cold/main/

# Repeat for every external tablespace location.

systemctl start postgresql

This is operationally simple but imposes downtime and must include all tablespaces and required configuration/secrets according to the deployment architecture.

19.2 Snapshot-based backup

Storage snapshots can provide an efficient physical backup when the snapshot mechanism captures all PostgreSQL storage consistently. Multi-volume/tablespace designs require particular care: a snapshot of only the main data directory while a tablespace is captured at another instant can be unusable.

20. Backup verification

20.1 Base-backup manifests

pg_basebackup normally produces a backup_manifest. The manifest records files/checksums, the originating cluster system identifier in current manifest versions, required WAL ranges, and a checksum of the manifest itself. It is primarily intended for pg_verifybackup.[10][19]

20.2 Verify a plain physical backup

pg_verifybackup \
  --progress \
  /backup/full/2026-09-15

Verification checks manifest integrity, expected files, file sizes/checksums, and required WAL readability when supported. PostgreSQL stresses that this cannot detect every problem and must be followed by actual recovery tests.[10]

20.3 Verify WAL stored separately

pg_verifybackup \
  --wal-directory=/mnt/postgres-wal \
  /backup/full/2026-09-15

20.4 Tar-format limitation

PostgreSQL 18's pg_verifybackup can verify tar-format backup files, including supported compression, but WAL parsing verification is currently supported only for plain-format backups. For tar format, use --no-parse-wal and validate recoverability through restore testing.[10]

20.5 Verify logical archives structurally

# Confirm archive is readable and inspect its TOC.
pg_restore --list appdb.dump > /tmp/appdb.toc

# Generate SQL without executing it.
pg_restore \
  --file=/tmp/appdb-restore.sql \
  appdb.dump

This catches archive-read problems and enables review but still does not prove successful restoration or application correctness.

21. Recovery testing

A backup test should execute the recovery path, not merely read backup metadata. PostgreSQL explicitly states that pg_verifybackup does not replace test restores.[10]

21.1 Logical restore test

createdb -T template0 restore_test

pg_restore \
  --dbname=restore_test \
  --jobs=8 \
  --exit-on-error \
  appdb.dump

vacuumdb \
  --analyze \
  restore_test

21.2 Physical/PITR test

1. Provision isolated host/container/VM 2. Select retained base/full reconstructed backup 3. Restore data directory + tablespaces 4. Configure restore_command 5. Set a representative recovery target 6. Create recovery.signal 7. Start PostgreSQL 8. Wait for target and promote/pause 9. Run database integrity/application checks 10. Record achieved RPO/RTO and cleanup

21.3 Validate application semantics

-- Examples only; choose domain-specific invariants.
SELECT count(*) FROM app.customer;
SELECT count(*) FROM app.orders;

SELECT min(created_at), max(created_at)
FROM app.orders;

SELECT *
FROM pg_constraint
WHERE NOT convalidated;

SELECT extname, extversion
FROM pg_extension
ORDER BY extname;

Recovery tests should also confirm authentication, extensions, sequences/identity behavior, scheduled jobs, external integrations, ownership/grants, tablespace paths, and representative application queries.

21.4 Measure recovery, do not estimate it

Record restore download/copy time, decompression time, WAL replay time, index/data import time for logical restores, validation time, and client cutover time. RTO is an observed operational metric, not the theoretical speed of the backup tool.

22. Disaster recovery architecture

production PostgreSQL | +--------------+---------------+ | | v v scheduled base backup WAL archive full/incremental continuous segments | | +---------------+--------------+ | v backup repository A (local/site) | +------ replicated/copied -------+ | v repository B independent failure domain | v isolated restore test | v DR PostgreSQL + validation

22.1 Separate failure domains

A backup stored only on the same host, filesystem, storage array, cloud account/credential boundary, or administrative path as production can fail with production. Disaster recovery requires copies that survive the failures in the stated threat model.

22.2 Backup catalog

Track at least: backup ID, PostgreSQL system identifier/version, start/end time, full/incremental parent chain, manifest location/checksum, tablespaces, encryption/storage metadata from the surrounding system, required WAL range, retention expiry, verification status, last restore-test result, and achieved recovery time.

22.3 Keep configuration outside the database backup plan too

Database files alone may not reproduce production service. Recovery automation also needs versioned configuration for PostgreSQL, HBA/authentication, TLS certificates/issuance process, extensions/packages, service units, storage mounts, backup credentials, DNS/load-balancer behavior, monitoring, and application secrets. Protect secrets through the organization's secret-management mechanism rather than embedding them in backup scripts.

23. Monitoring backup and archive health

23.1 WAL archiver status

SELECT
    archived_count,
    last_archived_wal,
    last_archived_time,
    failed_count,
    last_failed_wal,
    last_failed_time,
    stats_reset
FROM pg_stat_archiver;

pg_stat_archiver reports successful/failed archival statistics and recent WAL file/timestamps. It should be correlated with archive-repository observations and free space in pg_wal.[20]

23.2 Current WAL generation

SELECT
    wal_records,
    wal_fpi,
    wal_bytes,
    wal_buffers_full,
    stats_reset
FROM pg_stat_wal;

Backup/archive capacity must account for peak WAL generation, not average database growth. Bulk loads, index builds, VACUUM-related full-page writes, and maintenance can change WAL volume significantly.

23.3 Backup progress

SELECT *
FROM pg_stat_progress_basebackup;

23.4 Operational alerts

Alert on stale last-successful full/incremental backup, missing expected backup manifests, archive failure count increases, time since last archived WAL, repository free space, pg_wal free space, verification failure, broken incremental dependency chains, and overdue restore exercises.

24. Backup security and trust

24.1 Backups contain production data

A logical or physical backup can contain the same sensitive data as the live database, and cluster-global logical dumps can include role password verifiers unless explicitly omitted. Repository access should therefore be treated as production-data access.[3]

24.2 Restore is code execution

PostgreSQL warns that restoring logical dumps executes SQL originating from the source cluster, including code chosen by source superusers. If the source or supplied dump is not trusted, inspect it before restoration. For archive-format dumps, pg_restore --file can render the SQL for review.[2][4] 

pg_restore \
  --file=/tmp/review.sql \
  untrusted.dump

24.3 Dedicated backup credentials

Use a dedicated role and narrow network access for physical backup connections. Logical dump privileges depend on what must be read/exported. Avoid embedding passwords directly in scripts or shell command history; use supported secure credential mechanisms.

25. Recovery runbooks

25.1 Restore one database from custom dump

# Preconditions:
# - PostgreSQL version/extension packages prepared
# - global roles restored where needed
# - target DB absent or disposable

dropdb --if-exists appdb_restore
createdb -T template0 appdb_restore

pg_restore \
  --dbname=appdb_restore \
  --jobs=8 \
  --exit-on-error \
  /backup/appdb.dump

vacuumdb --analyze appdb_restore

25.2 Restore cluster with PITR

# Pseudocode/runbook shape:
stop_postgres
quarantine_old_data_directory
restore_latest_valid_full_or_combined_backup
restore_tablespace_layout
write_restore_command
write_recovery_target
touch_recovery.signal
start_postgres_isolated
monitor_recovery_logs
validate_target_state
promote_if_paused
run_database_checks
switch_clients_only_after_validation

25.3 Recover a table without rolling back the entire production cluster

production remains online | +--> build isolated PITR restore to desired time | +--> pg_dump -t damaged_table recovered_db | v review/reconcile | v import selected rows/table into production

This pattern is often safer than rolling the whole cluster back when only one logical object needs historical recovery.

27. Common pitfalls

27.1 Calling replication a backup

A replica normally replays accidental deletes and corrupt application writes. Replication improves availability; independently retained backups provide historical recovery.

27.2 Running pg_dump but forgetting globals

Per-database dumps do not contain cluster roles or tablespaces. Back up globals separately with pg_dumpall when a full logical rebuild must reproduce them.[2][3]

27.3 Restoring a plain dump with pg_restore

Plain SQL scripts are restored with psql. pg_restore is for custom, directory, and tar archives created by pg_dump.[4]

27.4 Keeping a base backup but deleting required WAL

PITR depends on an unbroken WAL chain from the selected base backup through the recovery target. A base backup alone cannot reconstruct later database state.[6]

27.5 Keeping incrementals but deleting their ancestors

Incrementals are dependency chains. PostgreSQL does not manage the external retention graph for you.[6]

27.6 Trusting pg_verifybackup as a restore test

The utility detects many file/manifest/WAL problems but explicitly cannot reproduce every check performed by a running database and cannot verify application semantics. Restore and query the backup.[10]

27.7 Archive command that overwrites existing WAL

Archive naming is based on WAL segment names. A robust archival system must refuse or safely verify collisions rather than silently replacing existing content with a different file.[6]

27.8 Never measuring restore time

A backup can meet storage-retention goals and still fail the RTO because data transfer, decompression, replay, index creation, validation, or human coordination takes too long.

27.9 Recovering directly over the only production copy

When practical, preserve the failed/current data directory and recover into an isolated replacement. The old state can be invaluable for investigation or extracting transactions not present at the chosen recovery target.

27.10 Leaving recovery credentials/configuration undocumented

A perfect database backup is not sufficient if the team cannot recreate extensions, TLS, authentication, tablespaces, service configuration, storage mounts, or application connectivity during a site-level incident.

28. Production checklist

  1. Write down RPO and RTO. Backup cadence must trace to explicit business objectives.
  2. Use multiple recovery layers. Logical dumps and physical/PITR backups solve different problems.
  3. Dump cluster globals. Roles/tablespaces are not included in per-database pg_dump.
  4. Choose archive formats deliberately. Custom/directory formats give pg_restore selective and parallel restore capabilities.
  5. Use template0 for clean logical restore tests.
  6. Archive WAL continuously for PITR. Alert immediately on archival failure.
  7. Make archive writes collision-safe and idempotent.
  8. Track incremental dependencies. Never expire a required ancestor backup.
  9. Generate and retain backup manifests.
  10. Run pg_verifybackup on physical backups.
  11. Test restores regularly. Verification is not recovery.
  12. Measure actual recovery time. Record restore, replay, validation, and cutover durations.
  13. Test PITR targets. Time, restore-point, and timeline behavior should be familiar before an incident.
  14. Keep copies in independent failure domains.
  15. Secure backups like production data.
  16. Monitor repository and pg_wal capacity.
  17. Version recovery infrastructure. PostgreSQL packages/extensions/configuration and automation must be reproducible.
  18. Practice object-level recovery. Know how to restore one table without rolling back the whole cluster.
  19. Practice full disaster recovery. Include people, routing, credentials, monitoring, and application validation—not only PostgreSQL startup.
Backup principle: a backup is trustworthy only when its dependencies are retained, its integrity is checked, and the organization has repeatedly demonstrated that it can restore the required data within the promised recovery window.
