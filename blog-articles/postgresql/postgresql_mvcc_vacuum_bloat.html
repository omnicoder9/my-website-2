PostgreSQL MVCC, VACUUM & Bloat

An expert guide to PostgreSQL's multiversion storage model: tuple visibility, snapshots, transaction IDs, dead tuples, pruning, HOT updates, autovacuum, ordinary and full vacuuming, ANALYZE, freezing and wraparound protection, visibility/free-space maps, table and index bloat, and production diagnostics.

Technical article • PostgreSQL 18.6 baseline • Updated 15 September 2026 • Vancouver-style references

Abstract

PostgreSQL implements multiversion concurrency control (MVCC) by keeping multiple physical row versions when data changes. Each statement evaluates tuple visibility against a snapshot, allowing ordinary readers and writers to proceed without blocking one another merely because they access the same rows. This concurrency model shifts work into storage maintenance: an UPDATE normally creates a new row version, and a DELETE marks an existing version obsolete rather than immediately erasing it. Once no transaction can still see an old version, PostgreSQL can reclaim its space.[1]-[4]

VACUUM is the maintenance mechanism that turns obsolete MVCC versions into reusable storage, cleans corresponding index references when appropriate, advances freezing horizons, and updates visibility metadata. Ordinary VACUUM operates in place and normally returns reusable space to the relation rather than the operating system. VACUUM FULL, by contrast, rewrites the table into a compact new file and requires an ACCESS EXCLUSIVE lock; PostgreSQL therefore recommends ordinary vacuuming as routine maintenance and reserves full rewrites for exceptional cases where physical shrinkage is worth the blocking and extra disk usage.[5][6]

Bloat is best understood as inefficient physical allocation, not as a synonym for “dead tuples.” A relation may have many dead versions that ordinary vacuum can soon recycle, substantial reusable free space that is not harmful, or genuinely poor page/index utilization that imposes extra I/O and storage cost. Diagnosing bloat therefore requires combining activity statistics, physical size, tuple/free-space inspection, workload behavior, vacuum history, long-running transaction horizons, and index structure rather than relying on one percentage alone.[7]-[10]

1. MVCC architecture

PostgreSQL uses multiversion concurrency control so each SQL statement operates against a logically consistent snapshot rather than reading whatever tuple happens to be newest in storage at every instant. Under normal MVCC reads, row-level writers do not block readers merely because they modify rows a query might read, and readers do not block writers merely by reading those rows. Explicit table/row locks still exist, and isolation-level rules can require waiting or serialization failure, but snapshot visibility—not a global read lock—is the foundation.[1][11]

logical row: account_id = 42 time ---------------------------------------------------------> T1 INSERT heap version V1 xmin=100, xmax=0 balance=100 | | T2 UPDATE v V1: xmin=100, xmax=125 --------+ | +--> V2: xmin=125, xmax=0 balance=125 Concurrent snapshots: Snapshot before XID 125 committed: sees V1 does not see V2 Snapshot after XID 125 committed: V1 obsolete to that snapshot sees V2 Storage may temporarily contain BOTH versions.

The physical persistence of multiple versions is what enables an old snapshot to continue seeing an earlier row state while a newer transaction sees a later one. It is also why update/delete workloads create maintenance work even when the logical row count stays constant.[3][5]

2. Tuple versions and heap tuple headers

The built-in heap table access method stores rows on fixed-size pages, normally 8 KiB. Each heap row has a tuple header containing MVCC metadata including the inserting transaction ID (t_xmin), deleting/updating transaction information (t_xmax), command identifiers, status bits, and a t_ctid pointer that can identify this row version or a newer version in an update chain.[3]

heap page +------------------------------------------------------+ | PageHeaderData | +------------------------------------------------------+ | item pointers -> [tuple V1] [tuple V2] [...] | | | | tuple header: | | t_xmin inserting XID | | t_xmax deleting/updating XID or related state | | t_ctid self/newer tuple pointer | | infomask cached visibility/tuple-state bits | | ... | | tuple user columns | +------------------------------------------------------+

2.1 System columns are observable

SELECT
    ctid,
    xmin,
    xmax,
    *
FROM app.account
WHERE account_id = 42;

The SQL-visible system columns expose useful low-level information, but they are not suitable application identifiers. ctid is a physical tuple location and can change after updates or table rewrites; transaction IDs wrap and are implementation-level metadata.[12]

2.2 UPDATE is logically replacement

In the heap implementation, an update generally means creating a new tuple version and marking the old version as updated. The old row cannot be reclaimed until PostgreSQL can prove no relevant snapshot can still see it.[5][13]

3. Tuple visibility and snapshots

A PostgreSQL snapshot describes transaction visibility at a point in time. The pg_snapshot representation contains xmin, xmax, and a list of transactions that were in progress. Roughly, transactions older than the snapshot horizon may be visible if committed, transactions at or beyond the upper horizon are too new, and transactions specifically listed as in progress are not visible to the snapshot.[14] 

SELECT pg_current_snapshot();

SELECT
    pg_snapshot_xmin(pg_current_snapshot()),
    pg_snapshot_xmax(pg_current_snapshot());

3.1 Visibility depends on both tuple metadata and transaction status

A tuple's xmin/xmax alone do not fully answer visibility without knowing whether those transactions committed, aborted, or remain in progress and how they relate to the current snapshot. PostgreSQL maintains transaction commit status and caches visibility outcomes in tuple hint/status bits to avoid repeatedly performing expensive status lookups.[3][15]

3.2 Snapshot timing follows isolation semantics

At PostgreSQL's default Read Committed isolation, each command obtains a new snapshot at command start, so two successive queries inside one transaction can see different committed data. Repeatable Read and Serializable use a transaction-level snapshot, subject to their additional isolation rules.[11]

4. Transaction IDs

PostgreSQL distinguishes virtual transaction IDs from normal transaction IDs. Every transaction has a virtual identity, but a normal 32-bit XID is generally assigned only when the transaction first needs to write. XIDs come from a cluster-wide sequence across databases and are fundamental to MVCC visibility and recovery.[4] 

SELECT
    pg_current_xact_id_if_assigned();

CREATE TEMP TABLE xid_demo(id integer);

INSERT INTO xid_demo VALUES (1);

SELECT
    pg_current_xact_id_if_assigned();

PostgreSQL also exposes 64-bit xid8 interfaces for monitoring/SQL functions. The on-disk/internal normal XID used for tuple visibility remains 32-bit and therefore requires wraparound management.[4][14]

4.1 Age

SELECT
    relname,
    age(relfrozenxid) AS xid_age
FROM pg_class
WHERE relkind IN ('r', 'm')
ORDER BY xid_age DESC
LIMIT 20;

The age() function is commonly used to express how old an XID is relative to the current XID counter using PostgreSQL's wraparound-aware arithmetic.[14]

5. UPDATE and DELETE lifecycle

5.1 UPDATE

Before: page [V1 xmin=100 xmax=0, value='A'] UPDATE commits as XID 125: page [V1 xmin=100 xmax=125, value='A'] [V2 xmin=125 xmax=0, value='B'] Eventually: - V1 no longer visible to any relevant snapshot - V1 becomes dead - pruning/VACUUM can reclaim its storage - V2 remains live

5.2 DELETE

Before: [V1 xmin=100 xmax=0] DELETE by XID 150: [V1 xmin=100 xmax=150] After XID 150 commits: old snapshots may still see V1 new snapshots do not Once no snapshot can see V1: V1 is dead and reclaimable

PostgreSQL does not immediately overwrite or erase the old row because another transaction may have a snapshot under which that version is still valid. This is the fundamental reason vacuuming exists.[5]

6. Dead tuples

A dead tuple is a row version that is no longer visible to any transaction that PostgreSQL must preserve. Updated/deleted versions can transition through states where they are invisible to some newer snapshots but still potentially visible to older transactions. Only after the global visibility horizon advances far enough can they be safely removed/reused.[5]

6.1 Estimated dead tuples

SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    n_mod_since_analyze,
    last_vacuum,
    last_autovacuum,
    vacuum_count,
    autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 25;

n_live_tup and n_dead_tup are statistics estimates, not exact physical counts. They are useful for trend monitoring and autovacuum diagnosis, not as a byte-accurate bloat measurement.[16]

6.2 Exact/approximate physical tuple statistics

CREATE EXTENSION IF NOT EXISTS pgstattuple;

SELECT *
FROM pgstattuple_approx('app.orders'::regclass);

The supplied pgstattuple extension can inspect physical tuple/free-space statistics. pgstattuple() performs a full relation scan for exact data, while pgstattuple_approx() avoids scanning all pages where possible and returns exact dead-tuple statistics with approximations for live tuples/free space.[7]

7. Page pruning and tuple reuse

VACUUM is not the only mechanism that can remove obsolete heap tuple versions. PostgreSQL can perform page pruning during normal access when a page is visited and the page header indicates pruning may be useful. Pruning can remove tuple versions that are safely dead and compact free space within the page. HOT chains make this particularly powerful because some intermediate versions can be removed without immediately involving index cleanup.[3][13]

same heap page index entry | v [V1] -> [V2] -> [V3] -> [V4] dead dead live newest HOT/pruning can collapse obsolete chain members: index entry | v redirect -------> [V3] -> [V4] freed tuple slots/page bytes become reusable

7.1 Reusable does not mean file shrinks

Pruning or VACUUM can make internal page space available for future inserts/updates, but that normally does not reduce the relation's file size. PostgreSQL can truncate completely empty pages from the physical end of a heap under ordinary vacuum when it can obtain the needed lock; otherwise physical shrinkage generally requires a rewrite.[6]

8. Heap-Only Tuple (HOT) updates

HOT reduces the cost of MVCC updates. PostgreSQL can use HOT when the update does not modify columns referenced by ordinary indexes (BRIN, a summarizing index type, is treated differently) and when there is enough free space on the same heap page to store the new row version.[13]

8.1 Normal update versus HOT

NON-HOT UPDATE heap: V1 -> V2 index A: old entry + new entry index B: old entry + new entry ... later VACUUM removes dead heap/index entries HOT UPDATE heap same page: V1 -> V2 index entry still points to HOT chain root no new entries in ordinary indexes pruning can remove intermediate versions earlier

8.2 Monitor HOT rate

SELECT
    schemaname,
    relname,
    n_tup_upd,
    n_tup_hot_upd,
    n_tup_newpage_upd,
    round(
        100.0 * n_tup_hot_upd
        / NULLIF(n_tup_upd, 0),
        2
    ) AS hot_pct
FROM pg_stat_user_tables
WHERE n_tup_upd > 0
ORDER BY hot_pct ASC, n_tup_upd DESC;

pg_stat_all_tables/pg_stat_user_tables expose total updates, HOT updates, and updates that placed the new tuple on another page. A low HOT ratio on a heavily updated table can be caused by indexed-column changes, lack of page free space, or both.[13][16]

8.3 Index design affects update cost

Adding an index to a frequently changed column can make updates non-HOT even when the index has modest read value. Index portfolio design is therefore also write-amplification and bloat design.

9. Fillfactor and update-heavy tables

The table fillfactor storage parameter determines how fully PostgreSQL initially packs heap pages during insertion/rewrite operations. Leaving deliberate free space can increase the chance that future updated versions fit on the same page, enabling HOT updates. The default heap fillfactor is 100; lowering it trades larger initial table size for update headroom.[13][17] 

ALTER TABLE app.account
SET (fillfactor = 80);

Changing the parameter affects future page filling; it does not automatically rewrite all existing pages to 80% occupancy. A later rewrite such as VACUUM FULL or CLUSTER can physically lay out the table according to the new storage behavior, but such operations have significant locking and I/O consequences.[17][18]

9.1 Not every update-heavy table wants 80%

Wide rows, update frequency, indexed columns, page locality, storage cost, and read workload all affect the optimum. Measure HOT rates, relation growth, and query I/O before and after changing fillfactor.

10. Ordinary VACUUM

Ordinary VACUUM scans a relation to reclaim space from row versions that are provably dead, perform index cleanup as needed, update the free-space and visibility maps, freeze eligible old tuple transaction metadata, and update relation-level vacuum statistics. It operates in place and normally permits concurrent SELECT, INSERT, UPDATE, and DELETE operations.[5][6] 

VACUUM app.orders;

VACUUM (VERBOSE) app.orders;

VACUUM (ANALYZE) app.orders;

10.1 What ordinary VACUUM does to space

Dead heap space becomes available for future tuples in that table. It normally remains allocated to the relation rather than returning to the operating system. If completely empty pages occur at the physical end of the table, vacuum can attempt to truncate them and return that tail space, which requires a brief ACCESS EXCLUSIVE lock.[6]

10.2 Index cleanup

VACUUM removes dead index entries when index cleanup is useful/needed. PostgreSQL 18's default INDEX_CLEANUP=AUTO permits skipping a complete index vacuum when the number of dead tuples is so small that scanning the index would cost more than the expected benefit. Persistently suppressing index cleanup on frequently modified tables can allow index and heap line-pointer cleanup debt to accumulate.[6] 

VACUUM (
    VERBOSE,
    INDEX_CLEANUP ON
) app.orders;

10.3 Parallel VACUUM

Ordinary VACUUM can use parallel workers for eligible index-vacuum/index-cleanup phases. It does not parallelize the heap scan itself. The requested worker count is further constrained by eligible indexes and max_parallel_maintenance_workers.[6] 

VACUUM (
    PARALLEL 4,
    ANALYZE
) app.orders;

11. VACUUM FULL

VACUUM FULL is not “more thorough ordinary vacuum.” It rewrites the entire table into a new compact file and rebuilds its indexes, returning unused physical space to the operating system. The rewrite requires extra disk space during execution and an ACCESS EXCLUSIVE lock that blocks other table access.[5][6] 

VACUUM (FULL, ANALYZE, VERBOSE)
app.orders;
PropertyVACUUMVACUUM FULL

Routine operation?YesNo; exceptional remediation

11.1 Alternatives

CLUSTER also rewrites a table (while physically ordering it by an index), and certain ALTER TABLE operations perform rewrites. For index-only bloat, REINDEX may be the right remedy without rewriting the heap.[5][18][19]

12. ANALYZE

ANALYZE samples table contents and updates planner statistics used to estimate row counts, selectivity, value distributions, and query costs. Vacuuming and statistics maintenance are related operationally but solve different problems; VACUUM ANALYZE simply runs both operations for convenience.[5][20] 

ANALYZE app.orders;

ANALYZE (VERBOSE)
app.orders(customer_id, status, created_at);

12.1 More statistics for skewed columns

ALTER TABLE app.orders
ALTER COLUMN status
SET STATISTICS 500;

ANALYZE app.orders;

Increasing a column's statistics target can give the planner a finer sample/model for skewed distributions at the cost of more ANALYZE work and catalog space.[20][21]

12.2 Partitioned parents

PostgreSQL's autovacuum daemon does not automatically issue ANALYZE for partitioned parent tables based on child modifications. If query planning depends on parent-level inheritance statistics, PostgreSQL documentation recommends running manual ANALYZE on the parent as needed.[5]

13. Autovacuum

Autovacuum automates both VACUUM and ANALYZE. An autovacuum launcher periodically visits databases and starts workers for relations whose activity or anti-wraparound age meets configured thresholds. Autovacuum is enabled by default and requires statistics collection (track_counts) for ordinary threshold-based decisions. Even if autovacuum is disabled globally or per table, PostgreSQL can still launch anti-wraparound vacuum work when necessary.[5][22] 

SHOW autovacuum;
SHOW autovacuum_max_workers;
SHOW autovacuum_naptime;

13.1 Why autovacuum is part of normal operation

Autovacuum is not an optional “cleanup utility” for an MVCC PostgreSQL database. It is responsible for maintaining reusable storage, planner statistics, visibility-map coverage, and XID/MultiXact safety. Disabling it without a replacement maintenance system accumulates operational debt and can eventually cause transaction-ID safety shutdowns.[5]

13.2 Per-table tuning

ALTER TABLE app.event_log
SET (
    autovacuum_vacuum_scale_factor = 0.01,
    autovacuum_vacuum_threshold = 5000,
    autovacuum_analyze_scale_factor = 0.02,
    autovacuum_analyze_threshold = 5000
);

Large/high-churn tables often need table-specific thresholds because a percentage-based default can allow too many obsolete tuples to accumulate before vacuum begins. PostgreSQL supports most autovacuum thresholds as per-table storage parameters.[22][17]

14. Autovacuum trigger formulas

For ordinary update/delete cleanup, PostgreSQL computes a vacuum threshold from a fixed threshold plus a fraction of the estimated table size, capped by PostgreSQL 18's autovacuum_vacuum_max_threshold when configured. PostgreSQL 18 added this fixed maximum threshold specifically to prevent percentage scaling from allowing extremely large absolute dead-tuple counts on very large tables.[5][23] 

vacuum threshold =
  min(
    autovacuum_vacuum_max_threshold,
    autovacuum_vacuum_threshold
      + autovacuum_vacuum_scale_factor * reltuples
  )

When autovacuum_vacuum_max_threshold=-1, the cap is disabled. Insert-heavy tables also have an insert-triggered vacuum formula that includes the fraction of the table not yet frozen, allowing vacuum to maintain visibility/freeze state even when rows are mostly inserted rather than updated or deleted.[5][22]

14.1 Why 20% can be too late

-- Conceptual example:
table size = 1,000,000,000 rows
scale factor = 0.20

percentage component = 200,000,000 tuples

A threshold that is reasonable for a 10,000-row table may be unsuitable for a billion-row table. Tune based on acceptable dead-tuple accumulation, vacuum duration, update rate, and storage headroom—not merely the default percentage.

14.2 Analyze threshold

analyze threshold =
  autovacuum_analyze_threshold
    + autovacuum_analyze_scale_factor * reltuples

Autoanalyze counts inserts, updates, and deletes because all can change planner statistics.[5][22]

15. Vacuum cost control, buffers, and memory

VACUUM can generate significant I/O. PostgreSQL provides cost-based delay controls that assign costs to buffer hits, misses, and dirtying; once a worker exceeds its cost budget it sleeps briefly. Autovacuum workers have separate cost settings and dynamically balance their global cost limit among active workers unless per-table limits override that behavior.[22] 

SHOW autovacuum_vacuum_cost_delay;
SHOW autovacuum_vacuum_cost_limit;
SHOW vacuum_cost_page_hit;
SHOW vacuum_cost_page_miss;
SHOW vacuum_cost_page_dirty;

15.1 Vacuum buffer access strategy

SHOW vacuum_buffer_usage_limit;

VACUUM (
    BUFFER_USAGE_LIMIT '512MB'
) app.large_fact;

PostgreSQL uses a Buffer Access Strategy ring for VACUUM/ANALYZE so large maintenance scans need not evict the whole working set from shared buffers. PostgreSQL 18's default vacuum_buffer_usage_limit is 2 MiB; larger values can improve maintenance throughput but can displace more useful cache pages.[24][6]

15.2 Maintenance memory

Vacuum/index cleanup can use maintenance_work_mem; autovacuum can use autovacuum_work_mem per worker. Since multiple autovacuum workers run concurrently, per-worker memory settings should be sized with aggregate memory pressure in mind.[24]

16. Freezing old tuple transaction IDs

Because normal XIDs are finite and wrap, PostgreSQL must eventually mark sufficiently old committed row versions as permanently old. This process is called freezing. Modern PostgreSQL normally preserves the original tuple xmin and marks frozen status in tuple metadata rather than literally replacing every XID with the special frozen XID.[5]

16.1 Ordinary versus aggressive vacuum

Ordinary VACUUM can skip all-visible pages even when they contain old but not-yet-frozen tuples. When a relation approaches its freeze-age thresholds, PostgreSQL performs an aggressive vacuum that visits pages needed to advance the table's frozen-XID horizon, including all-visible but not all-frozen pages.[5][25] 

SELECT
    c.oid::regclass AS relation,
    age(c.relfrozenxid) AS xid_age,
    c.relminmxid,
    mxid_age(c.relminmxid) AS mxid_age
FROM pg_class AS c
WHERE c.relkind IN ('r', 'm')
ORDER BY xid_age DESC
LIMIT 30;

16.2 Manual aggressive freeze

VACUUM (
    FREEZE,
    VERBOSE
) app.archive_2024;

VACUUM FREEZE effectively lowers the freeze-age thresholds for that invocation and aggressively freezes eligible tuples. It is useful in controlled cases such as static archival tables but is not a routine substitute for correctly configured autovacuum.[6]

17. Transaction-ID wraparound

Normal transaction IDs are 32-bit and cycle every roughly four billion transactions. PostgreSQL's wraparound-aware ordering can distinguish approximately two billion “past” from two billion “future” XIDs around the current position. If a very old tuple remains unfrozen beyond the safe horizon, its old XID could otherwise be interpreted as being in the future. PostgreSQL prevents this through freezing and aggressive anti-wraparound vacuuming.[4][5]

32-bit XID space (conceptual ring) future <----------+ / \ | | | current XID | | | \ / +----------> past A tuple cannot retain an ordinary insertion XID indefinitely. Before it crosses the safety horizon, VACUUM freezes it.

17.1 Database-level monitoring

SELECT
    datname,
    age(datfrozenxid) AS xid_age,
    mxid_age(datminmxid) AS mxid_age
FROM pg_database
ORDER BY xid_age DESC;

17.2 Table-level monitoring

SELECT
    n.nspname,
    c.relname,
    age(c.relfrozenxid) AS xid_age
FROM pg_class AS c
JOIN pg_namespace AS n
  ON n.oid = c.relnamespace
WHERE c.relkind IN ('r', 'm')
ORDER BY xid_age DESC
LIMIT 50;

17.3 Emergency protection

PostgreSQL begins warning well before wraparound and eventually refuses commands that allocate new transaction IDs when the cluster approaches the hard safety boundary. The correct response is to remove horizon blockers such as very old transactions/prepared transactions/obsolete replication slots and run ordinary vacuum on affected databases/tables. PostgreSQL 18 specifically warns against using VACUUM FULL as an anti-wraparound emergency response.[5]

18. MultiXact IDs and wraparound

When multiple transactions hold row-level locks on the same tuple, PostgreSQL can represent that shared locking state using a MultiXact ID. MultiXact IDs also wrap and have their own freeze/age thresholds, so vacuum maintenance protects against both normal XID and MultiXact exhaustion.[5][26] 

SELECT
    datname,
    age(datfrozenxid) AS xid_age,
    mxid_age(datminmxid) AS multixact_age
FROM pg_database
ORDER BY multixact_age DESC;

Workloads with heavy concurrent row locking can consume MultiXact IDs much faster than ordinary applications. Monitor both age systems rather than assuming XID health alone proves wraparound safety.

19. Visibility map

Every heap relation has a visibility-map fork (_vm). It stores two bits per heap page: all-visible means every tuple on the page is visible to all active and future transactions until the page is modified, and all-frozen means every tuple is frozen. Vacuum sets these bits; data modification clears them conservatively.[8]

heap page 42 +----------------------------------+ | all tuples globally visible? YES | | all tuples frozen? YES | +----------------------------------+ visibility map: page 42 -> [all-visible=1][all-frozen=1] Consequences: - ordinary vacuum can skip appropriate page work - index-only scan can avoid heap visibility fetch - anti-wraparound vacuum can skip all-frozen page

19.1 Index-only scans

PostgreSQL indexes generally do not store enough MVCC visibility information to prove a referenced heap tuple is visible. An index-only scan therefore checks the visibility map; if the heap page is all-visible, PostgreSQL can return values directly from the index without fetching the heap page for visibility confirmation.[5][8] 

EXPLAIN (ANALYZE, BUFFERS)
SELECT order_id
FROM app.orders
WHERE customer_id = 42;

In an index-only plan, a low Heap Fetches count is often evidence that visibility-map coverage is effective.

19.2 Inspect visibility metadata

CREATE EXTENSION IF NOT EXISTS pg_visibility;

SELECT *
FROM pg_visibility_map_summary(
    'app.orders'::regclass
);

The supplied pg_visibility extension can inspect visibility-map state and compare it with heap contents. Low-level correction functions are intended for corruption-recovery situations, not routine tuning.[27]

20. Free-space map

The free-space map (FSM) tracks available reusable space in heap and index relations (except hash indexes) in a separate _fsm fork. For heap pages, PostgreSQL records an approximate amount of free space so insert/update placement can locate pages with enough room without scanning the entire relation.[9]

heap pages: page 0 almost full page 1 2 KB free page 2 4 KB free page 3 500 B free FSM tree: max / \ max max / \ / \ p0 p1 p2 p3 Need ~3 KB? FSM directs insertion toward page 2.

20.1 Inspect the FSM

CREATE EXTENSION IF NOT EXISTS pg_freespacemap;

SELECT
    blkno,
    avail
FROM pg_freespace('app.orders')
ORDER BY avail DESC
LIMIT 20;

FSM values are approximate and intentionally quantized. For heap relations they describe reusable free bytes per page; for indexes the representation indicates empty-page availability rather than meaningful byte-level free space.[9][28]

20.2 VACUUM and FSM

When vacuum/pruning frees tuple storage, the relation can advertise that space through the FSM so later inserts/updates reuse existing pages. This is why a relation can remain physically large after cleanup without necessarily remaining inefficient: its pages may contain valuable reusable capacity.

21. Table bloat

“Table bloat” is an operational term rather than a single PostgreSQL catalog field. It generally describes a heap occupying substantially more physical space/pages than its useful live data and intended free-space reserve require. Causes include sustained update/delete churn, vacuum falling behind, long-lived visibility horizons, non-HOT updates, workload shifts after mass deletion, and page-layout fragmentation.[5][7]

21.1 Dead tuples versus reusable free space versus bloat

StateMeaningTypical action
Dead tuplesObsolete row versions not needed by snapshotsLet/force ordinary VACUUM reclaim them
Reusable free spaceAlready reclaimed page capacity available to future rowsOften healthy; no shrink needed
Physical bloatRelation remains inefficiently large for current/live workloadFix cause; consider rewrite if space/I/O cost justifies it
Expected fillfactor headroomDeliberately unused page space reserved for updatesDo not “fix” as bloat without measuring benefit

21.2 Size inventory

SELECT
    c.oid::regclass AS relation,
    pg_size_pretty(pg_relation_size(c.oid)) AS heap_size,
    pg_size_pretty(pg_indexes_size(c.oid)) AS indexes_size,
    pg_size_pretty(pg_total_relation_size(c.oid)) AS total_size
FROM pg_class AS c
JOIN pg_namespace AS n
  ON n.oid = c.relnamespace
WHERE c.relkind = 'r'
  AND n.nspname NOT IN ('pg_catalog', 'information_schema')
ORDER BY pg_total_relation_size(c.oid) DESC
LIMIT 30;

21.3 Mass deletion

DELETE FROM app.audit_event
WHERE occurred_at < current_date - interval '2 years';

VACUUM app.audit_event;

Ordinary VACUUM makes the freed space reusable but will not generally shrink a table from, say, 500 GB to 50 GB simply because 90% of rows were deleted. If the table is expected to regrow, retaining reusable capacity may be beneficial; if not, a rewrite or partition-drop strategy may be appropriate.[5]

22. Index bloat

Indexes have their own lifecycle. Updating/deleting heap tuples can leave index entries that later vacuum must remove. B-tree pages that become completely empty can be reclaimed for reuse, but sparsely populated pages can remain allocated, leading to inefficient space use under some delete/update patterns. PostgreSQL recommends periodic monitoring and REINDEX where this becomes significant.[10][19]

22.1 Inspect B-tree physical statistics

CREATE EXTENSION IF NOT EXISTS pgstattuple;

SELECT *
FROM pgstatindex(
    'app.orders_customer_id_idx'::regclass
);

pgstatindex exposes B-tree metrics such as tree level, index size, leaf density, and fragmentation indicators. Interpret these in context; no universal percentage automatically means an index must be rebuilt.[7]

22.2 Rebuild online where appropriate

REINDEX INDEX CONCURRENTLY
app.orders_customer_id_idx;

Standard REINDEX rebuilds an index with stronger write blocking. REINDEX CONCURRENTLY uses more work and time but permits normal inserts/updates/deletes during most of the operation and is often preferable for production remediation.[19]

22.3 Deduplication and index behavior

Modern B-tree indexes can apply internal optimizations such as deduplication in suitable cases, but bloat remains workload-dependent. Monitor physical size and query behavior instead of applying periodic rebuilds blindly.

23. Diagnosing bloat and vacuum health

23.1 First-pass table statistics

SELECT
    relid::regclass AS relation,
    n_live_tup,
    n_dead_tup,
    n_tup_ins,
    n_tup_upd,
    n_tup_hot_upd,
    n_tup_newpage_upd,
    n_tup_del,
    last_autovacuum,
    autovacuum_count,
    last_autoanalyze,
    autoanalyze_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 30;

23.2 Compare statistics to physical size

SELECT
    s.relid::regclass AS relation,
    s.n_live_tup,
    s.n_dead_tup,
    pg_size_pretty(pg_relation_size(s.relid)) AS heap,
    pg_size_pretty(pg_indexes_size(s.relid)) AS indexes,
    pg_size_pretty(pg_total_relation_size(s.relid)) AS total
FROM pg_stat_user_tables AS s
ORDER BY pg_total_relation_size(s.relid) DESC
LIMIT 30;

23.3 Physical sampling with pgstattuple_approx

SELECT
    table_len,
    approx_tuple_count,
    dead_tuple_count,
    dead_tuple_percent,
    approx_free_space,
    approx_free_percent
FROM pgstattuple_approx('app.orders'::regclass);

23.4 Visibility coverage

SELECT *
FROM pg_visibility_map_summary(
    'app.orders'::regclass
);

23.5 FSM distribution

SELECT
    width_bucket(avail, 0, current_setting('block_size')::int, 10) AS bucket,
    count(*) AS pages
FROM pg_freespace('app.orders')
GROUP BY 1
ORDER BY 1;

23.6 Index sizes

SELECT
    i.indexrelid::regclass AS index_name,
    pg_size_pretty(pg_relation_size(i.indexrelid)) AS index_size,
    s.idx_scan,
    s.idx_tup_read,
    s.idx_tup_fetch
FROM pg_index AS i
LEFT JOIN pg_stat_user_indexes AS s
  ON s.indexrelid = i.indexrelid
WHERE i.indrelid = 'app.orders'::regclass
ORDER BY pg_relation_size(i.indexrelid) DESC;
Avoid a single-number “bloat threshold.” A large free-space percentage can be desirable on an update-heavy table, while a low dead-tuple count can coexist with poor index density after historical churn. Diagnose behavior, size, reuse, and workload together.

24. Long-running transactions and vacuum horizons

VACUUM cannot remove a row version if some still-relevant transaction/snapshot might need it. Long-running transactions can therefore pin the visibility horizon and cause dead tuples to accumulate across tables that transaction could observe. An “idle in transaction” connection can create this problem even while executing no query.[5][29]

24.1 Find old transaction horizons

SELECT
    pid,
    usename,
    application_name,
    state,
    xact_start,
    backend_xid,
    backend_xmin,
    age(backend_xid) AS xid_age,
    age(backend_xmin) AS xmin_age,
    left(query, 120) AS query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;

24.2 Idle transaction timeout

ALTER ROLE app_user
SET idle_in_transaction_session_timeout = '5min';

PostgreSQL explicitly notes that open idle transactions can prevent vacuum from removing recently dead tuples and thereby contribute to bloat. Apply the timeout with awareness of connection pool/application behavior.[29]

24.3 Prepared transactions and replication slots

Old prepared transactions and logical replication slots with old xmin/catalog_xmin can also pin horizons. PostgreSQL's wraparound recovery guidance explicitly calls out prepared transactions, long-running backends, and stale replication slots as blockers that may need to be resolved before vacuum can advance database age.[5] 

SELECT
    gid,
    prepared,
    owner,
    database,
    transaction,
    age(transaction) AS xid_age
FROM pg_prepared_xacts
ORDER BY xid_age DESC;

SELECT
    slot_name,
    slot_type,
    active,
    xmin,
    catalog_xmin,
    age(xmin) AS xmin_age,
    age(catalog_xmin) AS catalog_xmin_age
FROM pg_replication_slots
ORDER BY greatest(
    coalesce(age(xmin), 0),
    coalesce(age(catalog_xmin), 0)
) DESC;

25. Monitoring VACUUM and ANALYZE

25.1 VACUUM progress

SELECT
    pid,
    datname,
    relid::regclass AS relation,
    phase,
    heap_blks_total,
    heap_blks_scanned,
    heap_blks_vacuumed,
    index_vacuum_count,
    num_dead_item_ids,
    max_dead_item_ids
FROM pg_stat_progress_vacuum;

PostgreSQL exposes one row per running ordinary VACUUM/autovacuum worker in pg_stat_progress_vacuum. VACUUM FULL is a table rewrite and reports through pg_stat_progress_cluster instead.[30]

25.2 VACUUM FULL progress

SELECT
    pid,
    command,
    relid::regclass AS relation,
    phase,
    heap_tuples_scanned,
    heap_tuples_written
FROM pg_stat_progress_cluster
WHERE command = 'VACUUM FULL';

25.3 ANALYZE progress

SELECT
    pid,
    datname,
    relid::regclass AS relation,
    phase,
    sample_blks_total,
    sample_blks_scanned,
    ext_stats_total,
    ext_stats_computed
FROM pg_stat_progress_analyze;

25.4 Autovacuum worker activity

SELECT
    pid,
    datname,
    state,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE backend_type = 'autovacuum worker'
ORDER BY datname, pid;

PostgreSQL 18 introduced asynchronous I/O infrastructure that can improve operations including VACUUM, but vacuum throughput remains sensitive to storage, cost delay, buffer strategy, index work, and tuple horizon blockers.[23]

26. Production tuning patterns

26.1 Large high-churn OLTP table

ALTER TABLE app.session_state
SET (
    fillfactor = 80,

    autovacuum_vacuum_scale_factor = 0.005,
    autovacuum_vacuum_threshold = 10000,
    autovacuum_analyze_scale_factor = 0.01,
    autovacuum_analyze_threshold = 10000,

    autovacuum_vacuum_cost_limit = 4000,
    autovacuum_vacuum_cost_delay = 2
);

The values are examples, not universal recommendations. The goal is to begin cleanup before dead versions become operationally expensive, preserve page headroom for HOT, and give workers enough throughput to keep pace with mutation rate.

26.2 Append-mostly table

ALTER TABLE app.event_log
SET (
    autovacuum_vacuum_insert_scale_factor = 0.02,
    autovacuum_vacuum_insert_threshold = 10000,
    autovacuum_analyze_scale_factor = 0.01
);

Insert-triggered vacuum can maintain visibility/freeze coverage even on tables that do not generate many dead versions through updates/deletes.[5][22]

26.3 Static historical partition

VACUUM (FREEZE, ANALYZE)
analytics.fact_2024_12;

For a partition that will become immutable, one aggressive vacuum can freeze old tuple metadata and mark pages all-visible/all-frozen, reducing future anti-wraparound work and improving index-only-scan opportunities. Do this only when the partition is genuinely stable.

26.4 Guard against old idle transactions

ALTER ROLE web_app
SET idle_in_transaction_session_timeout = '2min';

26.5 PostgreSQL 18 absolute dead-tuple cap

# Global example:
autovacuum_vacuum_max_threshold = 10000000

PostgreSQL 18's maximum threshold is useful when very large tables make pure percentage scaling operationally unsafe. Tune the cap based on vacuum throughput and acceptable dead-version inventory.[23]

27. Bloat remediation decision tree

relation is large / slow | v Are dead tuples accumulating NOW? | +----+----+ | | yes no | | v v Why isn't Is space already reusable? vacuum / index sparse? keeping up? | | +-------------------------+ | | fix thresholds/workers/ future growth will reuse? long transactions/slots | | +---+---+ VACUUM yes no | | | v v v reusable space leave it remediation | +--------------+--------------+ | | heap bloat index bloat | | VACUUM FULL / CLUSTER REINDEX [CONCURRENTLY] or online external tool* / recreate index * external tooling not covered by PostgreSQL core docs

27.1 Start with the cause

Rewriting a bloated table without fixing an autovacuum deficit, long transaction, update pattern, or inappropriate index/fillfactor will often reproduce the bloat. Remediation should begin with the mechanism generating or retaining dead space.

27.2 Use ordinary VACUUM when reuse is enough

VACUUM (
    VERBOSE,
    ANALYZE
) app.orders;

27.3 Use REINDEX for index-only problems

REINDEX INDEX CONCURRENTLY
app.orders_status_idx;

27.4 Use VACUUM FULL only for justified heap shrinkage

-- Requires outage/strong locking planning:
VACUUM FULL app.orders;

27.5 Partition lifecycle can eliminate chronic bulk-delete bloat

If bloat repeatedly comes from retention deletes on time-series data, range partitioning may be structurally superior: dropping or detaching an expired partition removes its storage as a unit instead of creating millions of dead versions that need vacuuming.[31]

28. Common pitfalls

28.1 Treating dead tuples as permanent bloat

Dead versions may be normal short-lived MVCC debris that the next vacuum will recycle. Measure whether vacuum is keeping up and whether relation pages are actually poorly utilized before scheduling a rewrite.

28.2 Expecting ordinary VACUUM to shrink a 500 GB file

Ordinary vacuum normally makes space reusable inside the relation. It returns OS space only when empty pages at the physical tail can be truncated. Use a rewrite only if physical shrinkage is truly required.[6]

28.3 Using VACUUM FULL as routine maintenance

It blocks table access with ACCESS EXCLUSIVE, requires extra disk, and treats the symptom by rewriting storage. PostgreSQL recommends ordinary vacuum as the routine path.[5][6]

28.4 Increasing autovacuum workers without enough throughput/memory planning

More workers can improve concurrency across many hot tables but also multiply I/O and potentially autovacuum_work_mem consumption. Tune worker count, per-worker cost, memory, and storage capacity as one system.[22][24]

28.5 Long transactions hidden in connection pools

An application that opens a transaction and then waits on the client can pin old snapshots while appearing idle. Monitor xact_start/backend_xmin, not only currently executing queries.[16][29]

28.6 Indexing every mutable attribute

Every ordinary index referencing a changed column can prevent HOT for that update and adds new index entries/work. Indexes must justify their read benefit against update amplification.[13]

28.7 Confusing ANALYZE with cleanup

ANALYZE updates planner statistics; it does not reclaim dead tuple storage. VACUUM cleans storage; VACUUM ANALYZE does both.[6][20]

28.8 Disabling autovacuum on an active table

Doing so removes routine cleanup/statistics work while anti-wraparound vacuum can still occur. If maintenance must be managed manually, it must explicitly replace every relevant autovacuum responsibility.[22]

28.9 Ignoring index cleanup debt

Forcing INDEX_CLEANUP OFF can be useful during an urgent anti-wraparound situation, but regular suppression can allow dead index entries and dead line pointers to accumulate and harm performance.[6]

28.10 Monitoring only database-level XID age

Database age tells you urgency but not which table is responsible. Drill into pg_class.relfrozenxid and also inspect MultiXact age and horizon blockers.

29. Production checklist

  1. Keep autovacuum enabled. Treat it as part of normal MVCC operation.
  2. Monitor both table churn and cleanup. Track dead tuples, vacuum frequency, update rates, and physical size.
  3. Tune large hot tables individually. Percentage defaults can allow excessive absolute dead-tuple counts.
  4. Use PostgreSQL 18's autovacuum_vacuum_max_threshold where a fixed upper trigger is useful.
  5. Monitor XID and MultiXact age. Check both databases and individual relations.
  6. Find old transaction horizons. Long transactions, prepared transactions, and replication slots can block cleanup.
  7. Consider idle_in_transaction_session_timeout for application roles that should never idle in a transaction.
  8. Measure HOT efficiency. Index only columns whose read benefit justifies update cost.
  9. Use fillfactor intentionally. Reserve update headroom on hot tables when measurements support it.
  10. Let ordinary VACUUM create reusable space. Do not require OS shrinkage unless storage/I/O economics demand it.
  11. Reserve VACUUM FULL for exceptional rewrites. Plan locks, disk space, WAL, and downtime.
  12. Use REINDEX for index-specific bloat. Prefer CONCURRENTLY when production write availability matters.
  13. Keep planner statistics fresh. Analyze manually where autovacuum does not cover parent-table needs.
  14. Monitor visibility-map coverage. It affects vacuum skipping and index-only-scan efficiency.
  15. Understand FSM free space. Reusable pages are an asset, not automatically waste.
  16. Use pgstattuple/pg_visibility/pg_freespacemap selectively for physical diagnosis.
  17. Monitor active vacuum progress. Use the progress views before concluding maintenance is hung.
  18. Fix the cause before rewriting bloat. Otherwise the relation will grow again.
  19. Consider partitioning for bulk-retention workloads. Lifecycle DDL can avoid recurring mass-delete bloat.
MVCC maintenance principle: PostgreSQL buys concurrency by retaining history. Healthy systems make that history short-lived: snapshots advance, HOT/pruning avoid unnecessary index churn, autovacuum reclaims versions early, and freezing turns truly old live tuples into permanent history-safe state.
