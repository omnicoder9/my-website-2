PostgreSQL Query Processing

An expert guide to PostgreSQL’s complete query-processing pipeline: SQL parsing, raw parse trees, semantic analysis, query rewriting, planner paths and cost optimization, statistics and cardinality estimation, execution plans, the demand-pull executor, scan and join algorithms, sorting and aggregation, materialization, and evidence-driven optimization with EXPLAIN.

Technical article • PostgreSQL 18.6 baseline • Updated 16 September 2026 • Vancouver-style references

Abstract

PostgreSQL transforms SQL through several distinct internal representations before execution. The raw parser validates SQL syntax and constructs a parse tree; semantic transformation resolves database objects, operators, functions, aggregates, and types into a query tree; the rewrite system applies view and rule transformations; the planner/optimizer searches physically different ways to compute the same result; and the executor recursively runs the selected plan tree to produce rows.[1]-[4]

The optimizer is cost based. It does not follow simple rules such as “use an index whenever possible.” It estimates relation and intermediate cardinalities using statistics, generates candidate scan and join paths, estimates startup and total costs, tracks useful ordering and parameterization properties, and converts the cheapest suitable path into an executor plan. For join-heavy queries, exhaustive search itself can become expensive, so PostgreSQL can switch to the Genetic Query Optimizer (GEQO).[5]-[8]

The executor follows a demand-pull model: each plan node is repeatedly asked for its next row and requests input from child nodes as needed. Some nodes stream naturally, while blocking nodes perform substantial work before returning their first row. Understanding these runtime behaviors—together with cardinality estimates, memory limits, physical locality, MVCC visibility, and I/O—is central to reading plans correctly.[4][9]

EXPLAIN exposes the optimizer’s estimates and chosen node tree. EXPLAIN ANALYZE executes the statement and adds actual row counts and runtime evidence. The most productive performance question is often not “Why did PostgreSQL choose a hash join?” but “Which estimate made that hash join look cheapest?”[9][10]

1. The query-processing pipeline

PostgreSQL documents a staged path from client SQL to result rows: parse the text, semantically transform it, rewrite query trees using rules, optimize the rewritten query into a physical plan, then recursively execute that plan.[1][2]

client SQL text | v lexer + grammar parser | v raw parse tree | v semantic transformation / parse analysis | v Query tree | v query rewriter (views/rules) | v rewritten Query tree(s) | v planner / optimizer (paths, cardinalities, costs) | v Plan tree | v executor | v result rows

These boundaries are diagnostically useful. A syntax error belongs to parsing; an unknown or ambiguous column is discovered during semantic analysis; a view changes the query through rewriting; scan/join choices are planner decisions; disk spills and repeated loops are execution behavior.

2. SQL parsing and lexical analysis

The raw parser checks syntactic validity. PostgreSQL’s lexer recognizes identifiers, SQL keywords and other tokens; the grammar parser builds the raw parse tree. The internals documentation identifies scan.l and gram.y as the source definitions processed by flex and bison.[2]

SELECT
    c.customer_id,
    c.name,
    sum(o.total_amount) AS revenue
FROM app.customer AS c
JOIN app.orders AS o
  ON o.customer_id = c.customer_id
WHERE o.created_at >= date '2026-09-01'
  AND o.status = 'paid'
GROUP BY c.customer_id, c.name
ORDER BY revenue DESC
LIMIT 20;

At this stage PostgreSQL can recognize the grammatical structures. It has not yet completed the catalog-backed work needed to establish the actual relation OIDs, function/aggregate identities, operator implementations, expression data types, coercions, and column bindings.[2]

3. Raw parse tree

The raw parse tree is syntax oriented. For example, syntax that resembles a function call is represented as such before semantic analysis decides whether it denotes an ordinary function, aggregate, window function, or another semantically specialized expression form.[2]

SELECT sum(total_amount) FROM app.orders WHERE status = 'paid'; conceptual raw tree: SelectStmt ├── targetList │ └── ResTarget │ └── FuncCall "sum" │ └── ColumnRef "total_amount" ├── fromClause │ └── RangeVar app.orders └── whereClause └── A_Expr "=" ├── ColumnRef "status" └── String "paid"

This representation describes what the user wrote, not yet the fully resolved meaning of the statement.

4. Semantic analysis / transformation

The transformation phase performs semantic interpretation using system catalogs. It resolves relations and columns, looks up functions and operators, determines actual expression types, inserts required coercions, identifies aggregate references, establishes query namespaces, and creates the semantically rich Query representation.[2]

raw: FuncCall("sum", ColumnRef("total_amount")) transformation: resolve app.orders resolve total_amount -> numeric resolve SUM(numeric) mark aggregate semantics determine result type query-tree expression: Aggref(resolved aggregate OID, typed Var ...)

PostgreSQL’s documentation uses this exact class of distinction: a raw FuncCall can transform to FuncExpr or Aggref once catalog lookup determines what the referenced name means.[2]

4.1 Semantic errors can follow valid syntax

SELECT nonexistent_column
FROM app.orders;

The statement is grammatical, but semantic analysis cannot bind the referenced column.

5. Query tree

The transformed query tree is PostgreSQL’s semantic representation of a statement before cost-based planning. It contains command type, range-table entries, target expressions, qualifications, grouping and sorting information, subqueries, modification targets, and other analyzed details. Query rewrite rules are themselves represented in the catalogs as query trees.[3]

# Developer diagnostics; use cautiously.
debug_print_parse = on
debug_print_rewritten = on
debug_print_plan = on

PostgreSQL documents these developer settings as mechanisms for emitting internal trees to server logs. They are useful for backend development but EXPLAIN is the normal way to inspect optimizer output.[3][11]

Parse/query trees and plans are different artifacts. A query tree describes SQL semantics. A plan describes one selected physical program for realizing those semantics.

6. Query rewriting

The rewrite system sits between parse analysis and planning. It consumes query trees, applies rewrite rules stored in PostgreSQL catalogs, and emits zero or more query trees. Rewriting is a semantic transformation system, not the physical cost-based optimizer.[3][12]

analyzed Query | v rewrite system | +-- view _RETURN rule expansion +-- applicable INSERT/UPDATE/DELETE rules | v rewritten Query tree(s) | v planner

It is possible for rules to generate additional statements or suppress a statement entirely. The planner sees the rewritten result rather than the original SQL text.[12]

7. Views and the rule system

Ordinary views are implemented through the rewrite system. A query against a view is rewritten to incorporate the view’s defining query. The planner can then flatten suitable subqueries and optimize the resulting base-table query much as if the underlying SQL had been written directly.[13]

CREATE VIEW app.paid_orders AS
SELECT order_id, customer_id, total_amount, created_at
FROM app.orders
WHERE status = 'paid';

EXPLAIN
SELECT *
FROM app.paid_orders
WHERE customer_id = 42;

A materialized view differs: its result is physically stored and queried like a table; its defining query is used to populate or refresh that stored result rather than expanded on every read.[14]

8. Planner / optimizer

The planner/optimizer searches alternative execution strategies that are semantically equivalent. It considers access paths for individual relations, then joins, ordering requirements, aggregation, parallelism, and other operations. PostgreSQL seeks the plan expected to have the lowest cost according to its statistics and cost model.[5]

same relational result orders Seq Scan -----+ +-- Hash Join -- HashAggregate -- Sort customer Seq Scan ---+ customer Index Scan -+ +-- Nested Loop -- GroupAggregate orders Index Scan ---+ orders Sort ----------+ +-- Merge Join -- Aggregate customer Sort --------+ planner compares cardinalities, costs, ordering, parameterization, parallel safety and other properties.

The optimizer must also limit its own search expense. When the number of joins becomes large enough that exhaustive join-order enumeration is impractical, PostgreSQL can use GEQO’s genetic search instead.[15]

9. Paths versus plans

PostgreSQL’s optimizer works primarily with paths while searching. Paths are compact candidate representations containing the properties needed to compare alternatives. Once the final path is chosen, PostgreSQL constructs the complete plan tree required by the executor.[5]

candidate paths SeqScanPath IndexPath BitmapHeapPath ParallelPath ... | v cheapest paths + useful ordered paths | v join paths NestedLoopPath / HashPath / MergePath | v selected final Path | v executor Plan tree

The cheapest unordered path is not always the only candidate worth preserving. A more expensive relation path that already produces useful order can eliminate a later sort or enable a merge join, making the complete query cheaper.[5][9]

10. Join-order search and GEQO

The number of possible join orders grows rapidly with the number of joined relations, compounded by multiple join methods and access paths. PostgreSQL’s normal planner performs a broad dynamic search for manageable queries; GEQO provides a bounded genetic search for sufficiently large join problems.[15]

SHOW geqo;
SHOW geqo_threshold;

Optimization time is itself latency. For large analytical join graphs, finding a very good plan quickly can be preferable to exhausting resources trying to prove the globally cheapest plan.

11. Statistics and cardinality estimation

Row-count estimates are core optimizer inputs. PostgreSQL uses relation-level estimates such as pg_class.reltuples/relpages, single-column statistics collected by ANALYZE, and optionally extended multivariate statistics. Most-common values, histograms, null fractions, distinct-value estimates and physical correlation help estimate predicate selectivity and group cardinality.[7][8]

SELECT reltuples, relpages
FROM pg_class
WHERE oid = 'app.orders'::regclass;

SELECT
    attname,
    null_frac,
    n_distinct,
    most_common_vals,
    most_common_freqs,
    histogram_bounds,
    correlation
FROM pg_stats
WHERE schemaname = 'app'
  AND tablename = 'orders';
estimated output rows ≈ estimated input rows × estimated selectivity

A cardinality error at a leaf can cascade upward. If PostgreSQL expects 10 outer rows and actually gets 100,000, a nested loop’s repeated inner work can become thousands of times larger than costed.

12. Cost estimation

Planner costs are abstract comparative units, not elapsed milliseconds. A node has startup cost (work before first output) and total cost (work if consumed to completion), as well as estimated rows and row width. Upper-node costs include child costs. PostgreSQL conventionally sets seq_page_cost=1.0 and expresses other I/O/CPU costs relative to it.[9][16]

SHOW seq_page_cost;
SHOW random_page_cost;
SHOW cpu_tuple_cost;
SHOW cpu_index_tuple_cost;
SHOW cpu_operator_cost;
SHOW effective_cache_size;
PropertyMeaning
Startup costCost incurred before the first output row can be produced.
Total costEstimated cost if all output is consumed.
RowsEstimated output cardinality.
WidthEstimated average output-row size in bytes.
OrderingCan satisfy ORDER BY/group/merge requirements without an extra sort.
ParameterizationCan consume values supplied by an outer plan, e.g. nested-loop inner index probes.

Memory-sensitive nodes use settings such as work_mem; hash-based operations derive their limit using hash_mem_multiplier. One query can contain several such operations and parallel workers can multiply resource use.[17]

13. Execution-plan structure

An execution plan is a tree of plan nodes. Leaf nodes obtain rows from tables, indexes, values lists, functions, or other sources. Internal nodes filter, join, sort, aggregate, cache, limit, or otherwise transform child output. Text EXPLAIN expresses tree structure with indentation.[9]

Limit
  -> Sort
        Sort Key: (sum(o.total_amount)) DESC
        -> HashAggregate
              Group Key: c.customer_id, c.name
              -> Hash Join
                    Hash Cond: (o.customer_id = c.customer_id)
                    -> Bitmap Heap Scan on orders o
                    -> Hash
                          -> Seq Scan on customer c

Conditions appear at the plan node that can execute them. Index Cond limits index access; Filter rejects rows after retrieval; Recheck Cond verifies bitmap/index matches where required; join nodes expose Hash Cond, Merge Cond, or join filters. This distinction is often more important than the predicate text itself because early filtering reduces downstream work.[9]

14. Executor architecture

The executor recursively evaluates the chosen plan using a demand-pull mechanism. A parent repeatedly asks a child for its next row. The child may request rows from its own children, producing a pipeline from leaf scans upward to the root.[4]

client consumes result | v root.next() | v parent node.next() | +--> child.next() | +--> grandchild.next() | v heap/index access

Some nodes return rows incrementally. Others are blocking. A Sort consumes all of its child input before it can return the first correctly sorted row. A hash join must build its hash table before probing. A Materialize node stores child output so it can satisfy later rescans without re-running the child.[4][9]

14.1 Data-modifying plans

The same executor infrastructure handles SELECT, INSERT, UPDATE, DELETE, and MERGE. PostgreSQL uses a top-level ModifyTable node for data modifications. For update/delete processing, plans carry tuple identifiers and required values up to that node so the executor can modify the target rows.[4]

15. Sequential scan

A sequential scan reads the relation heap in physical order, checks MVCC visibility, evaluates filters, and emits qualifying tuples. It is often optimal when much of the relation must be examined, when no useful index exists, or when indexed random heap access would cost more than a linear scan.[9][16]

EXPLAIN
SELECT *
FROM app.orders;
Seq Scan on orders
  (cost=0.00..125000.00 rows=5000000 width=128)

15.1 Why an available index can lose

If a predicate matches a large fraction of a table, an index plan can require traversing the index plus many heap fetches, while a sequential scan touches heap pages in simple physical order. PostgreSQL chooses based on estimated complete cost rather than the existence of an index.[9]

15.2 Parallel sequential scan

In a parallel sequential scan, table block ranges are shared among cooperating processes. Parallel plans require special partial paths so workers collectively produce the required rows once rather than each executing the whole plan independently.[18]

16. Index scan

An ordinary index scan traverses an index to identify candidate heap tuple locations and then fetches heap tuples for visibility checking and requested values. PostgreSQL indexes are secondary structures stored separately from the heap, so an index scan generally combines index and table access.[19]

CREATE INDEX orders_customer_created_idx
ON app.orders(customer_id, created_at DESC);

EXPLAIN
SELECT *
FROM app.orders
WHERE customer_id = 42
ORDER BY created_at DESC
LIMIT 20;
Limit
  -> Index Scan using orders_customer_created_idx on orders
        Index Cond: (customer_id = 42)

This plan can both find one customer's rows and produce them in descending timestamp order, avoiding a separate sort.

16.1 Parameterized index access

Nested-loop joins can feed values from the current outer row into the inner index scan. This is a key reason nested loops remain extremely competitive when the outer side is small and the inner relation has a selective index.[9]

17. Index-only scan

An index-only scan can return values directly from an index if the index access method can supply the referenced data and all query columns are available in the index. PostgreSQL still must verify MVCC visibility. It uses the heap page's visibility-map all-visible bit to determine when the heap access can safely be skipped; if that bit is not set, a heap visit is still required.[19]

CREATE INDEX orders_customer_cover_idx
ON app.orders(customer_id, created_at DESC)
INCLUDE (order_id, total_amount, status);

EXPLAIN (ANALYZE, BUFFERS)
SELECT order_id, created_at, total_amount, status
FROM app.orders
WHERE customer_id = 42
ORDER BY created_at DESC
LIMIT 20;

Actual EXPLAIN output can report Heap Fetches. A physically possible index-only scan is most beneficial when a large fraction of referenced heap pages are all-visible.[19]

17.1 Covering-index trade-off

INCLUDE payload columns can make index-only scans possible without making the payload part of the search key, but they enlarge and duplicate data in the index. Wide covering indexes can increase storage and write cost, so PostgreSQL recommends conservative use.[19]

18. Bitmap scans

A bitmap strategy separates index lookup from heap retrieval. Bitmap index scans identify matching tuple locations and build bitmaps. Multiple bitmaps can be combined with BitmapAnd or BitmapOr. A Bitmap Heap Scan then visits matching heap blocks in physical order, reducing random access compared with fetching each index hit immediately.[9][20]

CREATE INDEX orders_status_idx ON app.orders(status);
CREATE INDEX orders_created_idx ON app.orders(created_at);

EXPLAIN
SELECT *
FROM app.orders
WHERE status = 'paid'
  AND created_at >= date '2026-09-01';
Bitmap Index Scan(status) ----+ +-- BitmapAnd -- Bitmap Heap Scan Bitmap Index Scan(date) ------+ | v heap pages in physical order

Bitmap combination can exploit separate indexes, but scanning more indexes has its own cost. The planner can choose one bitmap index plus a filter, combine several, use a multicolumn index, or use another scan type depending on selectivity and cost.[20]

18.1 Ordering is lost

Because the bitmap is consumed in physical heap order, the ordering of an underlying B-tree is not preserved. A query with ORDER BY can therefore require a separate sort.[20]

19. Nested-loop join

A nested-loop join iterates over rows from its outer child and executes or rescans its inner child for each outer row. The inner scan can be parameterized with values from the current outer tuple. This algorithm is excellent for small outer inputs and cheap indexed probes, but repeated inner work can explode when the outer cardinality was underestimated.[9]

outer row A -> inner lookup(A) -> matches outer row B -> inner lookup(B) -> matches outer row C -> inner lookup(C) -> matches ...
approximate nested-loop cost ≈ outer cost + estimated outer rows × inner rescan cost + CPU join cost
EXPLAIN
SELECT c.customer_id, o.order_id
FROM app.customer AS c
JOIN app.orders AS o
  ON o.customer_id = c.customer_id
WHERE c.customer_id IN (42, 77, 101);

If PostgreSQL estimates three outer rows, a nested loop with inner index probes is natural. If the actual outer result is hundreds of thousands of rows, the multiplicative work can dominate runtime.

20. Hash join

A hash join builds a hash table from one input, usually the smaller estimated side, then scans the other input and probes the hash table by equality join keys. PostgreSQL's EXPLAIN documentation describes this as a build Hash node feeding a Hash Join probe.[9]

build input | v Hash | v +------------------+ | key -> hash rows | +------------------+ ^ | | probes | outer input scan
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM app.orders AS o
JOIN app.customer AS c
  ON c.customer_id = o.customer_id
WHERE o.created_at >= current_date - 30;

20.1 Memory and batches

Hash operations use a memory allowance based on work_mem and hash_mem_multiplier. If a hash table cannot fit in the usable memory, PostgreSQL can divide processing into batches involving temporary storage. EXPLAIN ANALYZE reports buckets, batches, and memory usage.[9][17]

20.2 Parallel hash

Parallel hash joins allow cooperating processes to build a shared hash table. This differs from a non-parallel hash join inside a parallel plan, where each process can build its own hash state.[18]

21. Merge join

A merge join requires compatible ordering on the join keys. It advances through the sorted inputs, comparing key values and emitting matching combinations. The required order can come from indexes or explicit sorts.[9]

left: 1 2 2 5 9 ... ^ right: 1 2 3 5 5 ... ^ equal -> emit matching combinations left lower -> advance left right lower -> advance right

PostgreSQL notes that sequential scan plus sort can beat an ordered index scan for large inputs because the latter may require substantial nonsequential heap access. The optimizer compares complete input-generation costs, not just the merge operation itself.[9]

22. Sort

A conventional Sort node is blocking. On first demand, it consumes its child input, performs the sort, stores the result, and then returns rows in requested order. That is why sorts have startup cost before producing their first tuple.[4]

EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM app.orders
WHERE created_at >= date '2026-09-01'
ORDER BY total_amount DESC;

Sorts use work_mem as their base memory limit. If the data does not fit, PostgreSQL can use external sorting and temporary files. EXPLAIN ANALYZE reports the sort method and memory/disk space used.[9][17]

22.1 Avoiding sorts with order-preserving paths

B-tree indexes can deliver ordered rows. The optimizer weighs ordered index access against an unordered scan plus explicit sort. For many returned rows, sequential access plus sort can still be cheaper.[21]

22.2 Incremental sort

If the child is already ordered by a prefix of the desired key list, PostgreSQL can sometimes use Incremental Sort, sorting smaller groups on the remaining keys. This can reduce memory usage and allow earlier output, which is particularly useful with LIMIT.[9]

23. Aggregate

Aggregate nodes implement aggregate-function and grouping semantics. A query with no GROUP BY has one logical aggregate group. Grouped queries can use order-based aggregation or hashing depending on input order, group estimates, memory, aggregate capabilities, and complete path cost.[22]

EXPLAIN
SELECT sum(total_amount)
FROM app.orders
WHERE customer_id = 42;
Aggregate
  -> Index Scan using orders_customer_created_idx on orders
        Index Cond: (customer_id = 42)

Some aggregates support Partial Mode, which allows parallel plans to compute partial transition states in workers and combine/finalize them higher in the plan.[22][18]

24. Hash aggregate

HashAggregate stores aggregate transition state in a hash table keyed by the grouping columns. This avoids sorting when hashing is suitable but makes memory requirements depend heavily on the number and size of groups. PostgreSQL can batch hash aggregation when required by memory pressure.[17][10]

EXPLAIN (ANALYZE, BUFFERS)
SELECT
    customer_id,
    count(*) AS order_count,
    sum(total_amount) AS revenue
FROM app.orders
GROUP BY customer_id;
HashAggregate
  Group Key: customer_id
  Batches: 1
  Memory Usage: ...
  -> Seq Scan on orders

Bad group-cardinality estimates can make the planner underestimate hash memory requirements or miscompare hash and sorted aggregation. PostgreSQL's multivariate ndistinct statistics can improve estimates for correlated multicolumn group keys.[23]

25. Materialization

A Materialize node saves the output of a child plan so repeated rescans can consume the stored result instead of executing the child again. PostgreSQL's EXPLAIN documentation demonstrates a nested-loop case in which an inner index scan is run once, materialized, then replayed for each outer tuple.[9]

Nested Loop +-- outer scan | +-- Materialize | +-- child scan (performed once) | v cache each rescan reads cached rows

This is an executor-plan technique and should not be conflated with SQL CTE MATERIALIZED/NOT MATERIALIZED, which affects whether suitable common-table expressions are folded into the surrounding query during planning.[24]

26. Parallel query plans

PostgreSQL constructs special parallel-aware partial plans rather than simply running an ordinary plan independently in every worker. Gather combines worker output without guaranteeing order; Gather Merge preserves a required sorted order while merging worker streams.[18][25]

Finalize Aggregate | Gather / | \ worker worker worker | | | Partial Aggregate | Parallel Seq Scan

Parallel workers are separate processes and can multiply CPU, memory, and I/O usage. Settings such as work_mem apply to operations in workers as well, so plan-level memory can substantially exceed one session's nominal setting.[17]

27. EXPLAIN

EXPLAIN shows the execution plan that PostgreSQL’s planner selected without running the statement unless the ANALYZE option is requested. PostgreSQL 18 supports text, JSON, XML, and YAML plan formats and options including VERBOSE, SETTINGS, GENERIC_PLAN, MEMORY, BUFFERS, WAL, and output serialization measurement in applicable modes.[10]

EXPLAIN (
    VERBOSE,
    SETTINGS,
    MEMORY,
    FORMAT TEXT
)
SELECT
    c.customer_id,
    count(*)
FROM app.customer AS c
JOIN app.orders AS o
  ON o.customer_id = c.customer_id
WHERE o.status = 'paid'
GROUP BY c.customer_id;

27.1 The four fundamental estimates

Index Scan ...
(cost=0.43..48.72 rows=16 width=64)
      ^       ^       ^        ^
      |       |       |        +-- average output row width
      |       |       +----------- estimated output rows
      |       +------------------- total cost
      +--------------------------- startup cost

The first line—the root node—contains the estimated total cost of the selected complete plan. Do not sum every node’s total cost: parent cost already includes the cost of child nodes plus the parent’s own work.[9]

27.2 Startup cost matters when execution can stop early

For LIMIT, EXISTS, and other contexts where the parent might consume only a small prefix, a plan with higher full-run cost can still be preferred because its startup cost is lower. PostgreSQL interpolates expected consumption for LIMIT when comparing paths.[10][9]

27.3 Machine-readable plans

EXPLAIN (FORMAT JSON)
SELECT *
FROM app.orders
WHERE order_id = 42;

Use JSON, XML, or YAML rather than parsing text output when implementing plan-analysis automation.[10]

28. EXPLAIN ANALYZE

EXPLAIN ANALYZE runs the command and adds actual execution statistics. This is how an engineer validates the planner’s assumptions rather than merely inspecting them. Compare estimated rows with actual rows, examine loops, buffer activity, sort/hash spill behavior, index searches, heap fetches, rows removed by filters/rechecks, planning time, and execution time.[9][10]

EXPLAIN (
    ANALYZE,
    BUFFERS,
    WAL,
    SETTINGS,
    TIMING OFF,
    SUMMARY
)
SELECT
    customer_id,
    count(*)
FROM app.orders
WHERE status = 'paid'
  AND created_at >= current_date - 30
GROUP BY customer_id;

28.1 Find the earliest major estimation error

estimation factor = actual rows / estimated rows 1.0 roughly exact 10 10× underestimate 0.1 10× overestimate

An error at a scan node can propagate through every join and aggregate above it. Correcting the leaf predicate’s statistics, expression, or data model is usually more robust than forcing the final join algorithm.

28.2 Loops change interpretation

Index Scan ... (actual rows=3 loops=10000)

Actual per-loop rows must be interpreted together with loops. A nested-loop inner path returning only three rows at a time may still produce 30,000 rows of work when called 10,000 times.

28.3 Profiling overhead

PostgreSQL documents that EXPLAIN ANALYZE can run slower than ordinary execution because of instrumentation. TIMING OFF avoids most per-node clock measurements while retaining actual row/loop information and total execution timing.[10]

28.4 Data-changing statements really execute

BEGIN;

EXPLAIN (
    ANALYZE,
    BUFFERS,
    WAL
)
UPDATE app.orders
SET status = 'archived'
WHERE created_at < date '2024-01-01';

ROLLBACK;

ANALYZE causes execution, so side effects occur. A transaction/rollback is useful for testing DML where appropriate, although external side effects of called functions are not necessarily undone merely because the SQL transaction rolls back.[10]

29. Query optimization workflow

Query optimization is most reliable when it follows the dependency chain used by PostgreSQL itself: semantics → cardinality → access paths → costs → execution resources. Starting by forcing a join type or globally lowering a cost constant skips the evidence that explains why the current plan was chosen.

slow query | v capture SQL + parameter values + planning settings | v EXPLAIN (ANALYZE, BUFFERS, SETTINGS, TIMING OFF) | v find earliest material estimate/runtime problem | +------------------------------+ | | bad cardinality? estimates good? | | v v ANALYZE inspect: statistics target - missing/poor index path extended statistics - memory spill predicate expression - I/O/cache behavior parameter skew - ordering/sort partition parent stats - parallel overhead - cost-model assumptions | | +---------------+--------------+ | v test alternative strategy experimentally | v deploy only measured, workload-safe changes

29.1 Reproduce the real parameter case

The same SQL text can need different plans for different constants. A highly skewed customer, tenant, date range, or status value may invalidate conclusions drawn from a “typical” value. Capture the parameters that made the production execution slow.

29.2 Ensure statistics are current

ANALYZE app.orders;

PostgreSQL’s EXPLAIN documentation explicitly recommends current pg_statistic data before judging planner decisions. Autovacuum normally maintains statistics, but a recent bulk load or distribution-changing update can justify immediate manual analysis.[10]

29.3 Improve statistics selectively

ALTER TABLE app.orders
ALTER COLUMN customer_id
SET STATISTICS 1000;

CREATE STATISTICS app.orders_customer_status_stats
    (dependencies, mcv)
ON customer_id, status
FROM app.orders;

ANALYZE app.orders;

Cross-column correlation is a common cause of misestimation because ordinary statistics are mostly single-column. Extended statistics can capture selected dependencies and multivariate MCV distributions.[7][23]

29.4 Inspect where filtering occurs

Index Scan using orders_status_idx on orders
  Index Cond: (status = 'paid')
  Filter: (lower(source) = 'web'::text)
  Rows Removed by Filter: 500000

If an access path retrieves huge numbers of tuples only to discard them in a filter, a better index might move that predicate into index qualification. Depending on the workload, possibilities include multicolumn, partial, or expression indexes—or accepting a sequential/bitmap plan when the result set is broad.

29.5 Use plan-method switches as experiments

BEGIN;

SET LOCAL enable_hashjoin = off;

EXPLAIN (ANALYZE, BUFFERS, TIMING OFF)
SELECT ...;

ROLLBACK;

PostgreSQL describes the enable_* parameters as crude planner controls. They are valuable for measuring an alternative plan, but a permanent fix should usually correct the statistics, index design, query form, resource settings, or cost assumptions that caused the wrong comparison.[16]

29.6 Distinguish execution from client time

The optimizer does not include every possible end-to-end cost in plan costs, such as all client transmission and result-formatting work. PostgreSQL 18’s EXPLAIN can optionally measure serialization cost, which helps distinguish server executor time from conversion of output values for delivery.[10]

30. Common misconceptions and pitfalls

30.1 “An index exists, so PostgreSQL should use it”

An index has lookup cost and often heap-fetch cost. For broad predicates, sequential access can be cheaper; for intermediate selectivity a bitmap scan can be better; an ordinary index scan often wins for selective predicates or useful ordering.[9][20]

30.2 “The parser chooses the plan”

Parsing checks syntax. Semantic analysis resolves meaning. Rewriting transforms query trees. The planner chooses the physical strategy. Conflating these stages makes internal explanations and performance diagnoses confusing.[2][3][5]

30.3 “EXPLAIN cost is milliseconds”

Costs are relative units used to compare plans. Use EXPLAIN ANALYZE for measured runtime and remember that cache state and concurrent workload can make actual execution vary from one run to another.[9]

30.4 Adding every node’s cost

Upper-node cost already contains child costs. Summing the tree double-counts the work.[9]

30.5 “Hash join is faster than nested loop”

Algorithm quality depends on input cardinality, selectivity, indexes, memory, ordering, and data distribution. Nested loops with selective parameterized index probes can outperform hashing by orders of magnitude on small outer inputs; hash joins can dominate when large equality-join inputs must be matched.

30.6 “Index-only scan never reads the heap”

MVCC visibility may still require heap fetches when the visibility map cannot prove the page all-visible. Heap Fetches in actual plans reveals this behavior.[19]

30.7 Raising work_mem globally for one spill

work_mem is generally per sort/hash operation, not a server-wide pool. Multiple nodes, sessions, and parallel workers can multiply memory consumption. Test targeted changes first.[17]

30.8 Permanently disabling sequential scans or join types

Planner method settings are diagnostic/influence controls, not substitutes for accurate statistics and cost models. A forced plan may fix one query/parameter case while harming others.[16]

30.9 Assuming an ordinary view is materialized

An ordinary view is query rewriting; a materialized view stores data. They have different runtime behavior.[13][14]

30.10 Looking only at root execution time

The earliest large estimated-versus-actual row difference often explains the rest of the plan. Diagnose bottom-up rather than treating the final node as the root cause.

30.11 Ignoring PostgreSQL-version changes

Planner capabilities evolve. PostgreSQL 18, for example, added B-tree skip-scan improvements and substantial planner/runtime enhancements; even with identical schema and SQL, the chosen strategy can differ between releases.[26]

31. Production checklist

  1. Think in pipeline stages. Parsing, semantic analysis, rewriting, planning, and execution solve different problems.
  2. Keep statistics current. Cardinality estimates drive most cost comparisons.
  3. Read the plan as a tree. Parent nodes pull from children and inherit their costs.
  4. Understand condition placement. Index conditions, filters, rechecks, and join conditions execute at different stages.
  5. Compare scan alternatives. Sequential, index, index-only, and bitmap scans each have a workload niche.
  6. Watch nested-loop multiplication. Multiply inner work by actual outer loops.
  7. Inspect hash batches and sort methods. They expose memory pressure and spilling.
  8. Exploit useful ordering. It can avoid sorts and enable merge processing.
  9. Use covering indexes selectively. Index-only potential must justify write/storage cost.
  10. Use extended statistics for demonstrated cross-column estimation errors.
  11. Run EXPLAIN ANALYZE knowingly. It executes the query.
  12. Use TIMING OFF when cardinality/buffer evidence is the main goal.
  13. Find the earliest significant estimate error. Later errors often inherit from it.
  14. Use planner switches as experiments. Do not use them as the first permanent remedy.
  15. Tune work_mem with total concurrency in mind.
  16. Use machine-readable EXPLAIN formats for automation.
  17. Test representative parameter values. Skew can make one SQL shape need different custom plans.
  18. Retest after major upgrades. Optimizer behavior legitimately changes across PostgreSQL releases.
Query-processing principle: SQL specifies a result, not an algorithm. PostgreSQL performance comes from translating that declarative request through increasingly semantic representations until the optimizer can select a concrete physical program; the most durable tuning improves the evidence and access paths that make that selection accurate.
