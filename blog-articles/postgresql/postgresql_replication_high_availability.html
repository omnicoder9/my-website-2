PostgreSQL Replication & High Availability

A production-oriented guide to physical and streaming replication, primary/standby architecture, WAL sender and receiver processes, replication slots, synchronous and asynchronous durability, logical replication and decoding, failover-capable logical slots, read replicas, connection routing, Patroni, etcd/Consul, HAProxy, failover, switchover, fencing, and load balancing.

Technical article • PostgreSQL 18.6 baseline • Patroni 4.1.x context • Updated 15 September 2026 • Vancouver-style references

Abstract

PostgreSQL provides two fundamentally different replication families. Physical replication reproduces the PostgreSQL cluster's physical changes by shipping and replaying write-ahead log (WAL); it is the native basis for warm/hot standby, streaming replication, read replicas, and fast primary/standby failover. Logical replication decodes WAL into table-level changes identified by logical row identity and applies selected publications to subscribing databases. Physical replication preserves an entire compatible PostgreSQL cluster; logical replication can select tables, columns, rows, and change types and can operate across major PostgreSQL versions and operating-system platforms.[1]-[4]

Replication alone is not high availability. PostgreSQL deliberately leaves primary-failure detection, leader election, fencing, endpoint movement, and automatic client routing to surrounding infrastructure. A complete HA system needs an authoritative decision about which node may accept writes, a mechanism to prevent the former primary from becoming a second writer after failover, and a routing layer that sends write traffic only to the current primary. Frameworks such as Patroni combine PostgreSQL streaming replication with a distributed configuration store (DCS), while load balancers such as HAProxy can use Patroni's REST health endpoints to route clients to the current primary or eligible replicas.[5]-[9]

The durability/availability trade-off remains explicit. Asynchronous streaming replication minimizes commit latency but can lose the most recent acknowledged transactions if the primary fails before their WAL reaches the promoted standby. Synchronous replication makes selected commits wait for one or more standby acknowledgements, reducing the data-loss window in exchange for latency and the possibility that commits wait when insufficient synchronous standbys are available. PostgreSQL exposes several acknowledgement levels—from remote operating-system write through remote flush to remote replay—through synchronous_commit.[1][10]

1. Replication and HA model

clients | +-------------+-------------+ | | v v write endpoint read endpoint HAProxy HAProxy | | Patroni /primary check Patroni /replica check | | v v +----------------+ +----------------+ | PostgreSQL pg1 |------->| PostgreSQL pg2 | | PRIMARY | WAL | STANDBY | +----------------+ +----------------+ | | | WAL | optional cascading WAL v v +----------------+ +----------------+ | PostgreSQL pg3 | | PostgreSQL pg4 | | STANDBY | | STANDBY | +----------------+ +----------------+ Each Patroni node | +------ leader lock / cluster state ------+ | +-------------------+------------------+ | distributed consensus store | | etcd OR Consul (quorum-based DCS) | +--------------------------------------+

There are several independent questions in this architecture: where database changes are copied, which copies are durable enough to promote, who decides the writer, how the old writer is fenced, and how applications discover the new writer. Treating those as separate control planes makes failures easier to reason about.

1.1 Replication is not backup

Replication rapidly copies good changes and bad changes alike. An accidental DELETE, logical corruption, or compromised session can be replicated immediately. PostgreSQL documents backup/restore and continuous archiving as separate reliability mechanisms, including point-in-time recovery (PITR). HA therefore complements rather than replaces tested backups and WAL archives.[11]

2. WAL as the replication substrate

PostgreSQL's write-ahead log records changes before the corresponding data pages need to reach durable storage. Each WAL position is identified by an LSN (pg_lsn), a monotonically increasing byte position that can be compared to quantify replication progress and lag. WAL normally lives in pg_wal as fixed-size segment files; 16 MiB is the normal default segment size unless another size was chosen at initdb time.[12] 

SELECT
    pg_current_wal_lsn() AS current_lsn;

SELECT
    pg_size_pretty(
        pg_wal_lsn_diff(
            pg_current_wal_lsn(),
            '0/0'::pg_lsn
        )
    );

Physical replication transports WAL itself. Logical replication uses WAL too, but decodes relevant records into logical row/table changes before transmission.[2][13]

3. Physical replication

Physical standby replication continuously replays WAL generated by an upstream PostgreSQL instance. It reproduces the entire cluster at the storage/recovery level rather than selecting individual tables. PostgreSQL's log-shipping and streaming-standby architecture therefore has stricter compatibility requirements than logical replication: physical primary/standby systems normally use the same PostgreSQL major release and compatible hardware architecture and tablespace paths.[1]

3.1 Warm standby versus hot standby

A standby continuously applying WAL is a warm standby in the HA sense. When hot_standby=on and recovery has reached a consistent state, PostgreSQL also permits read-only SQL connections during recovery, making the server useful as a read replica.[14]

3.2 Physical replication copies almost everything at cluster scope

Because recovery replays WAL describing physical database changes, DDL, indexes, catalog changes, and all databases in the cluster are reproduced as part of the standby's state. This simplicity is one reason physical replication is the natural mechanism for a byte-compatible HA standby.

4. Streaming replication

Streaming replication sends WAL records across a live network connection as PostgreSQL generates them rather than waiting for complete WAL segments to be archived. It is asynchronous by default, usually giving a much smaller lag/data-loss window than file-at-a-time log shipping. A standby can also combine streaming with a WAL archive, allowing it to recover missing segments from the archive after an outage or large lag.[1]

PRIMARY STANDBY backend transaction | v WAL inserted | +--> WAL flushed on primary | v WAL sender ===============================> WAL receiver | v write WAL locally | v flush WAL | v recovery replay | v read-only visibility

Streaming replication begins with primary_conninfo on a server in standby mode. PostgreSQL enters standby mode when a standby.signal file is present at startup; pg_basebackup -R can create that file and write connection settings automatically.[1][15]

5. WAL sender and WAL receiver

On a physical replication connection, the upstream PostgreSQL backend enters WAL-sender mode. A corresponding WAL receiver on the standby receives the stream, writes/flushed WAL locally, reports progress, and recovery replays those records. The streaming protocol carries receiver status messages containing write, flush, and apply LSNs, which are also exposed through PostgreSQL monitoring views.[16]

5.1 Primary-side WAL senders

SELECT
    pid,
    application_name,
    client_addr,
    state,
    sync_state,
    sent_lsn,
    write_lsn,
    flush_lsn,
    replay_lsn,
    write_lag,
    flush_lag,
    replay_lag
FROM pg_stat_replication
ORDER BY application_name;

5.2 Standby-side WAL receiver

SELECT
    pid,
    status,
    sender_host,
    sender_port,
    slot_name,
    written_lsn,
    flushed_lsn,
    latest_end_lsn,
    latest_end_time
FROM pg_stat_wal_receiver;

The primary's pg_stat_replication view represents connected WAL senders, while the standby's pg_stat_wal_receiver describes its receiving process.[17]

6. Building a physical streaming standby

6.1 Primary configuration

# postgresql.conf on all nodes that may become primary
wal_level = replica
max_wal_senders = 10
max_replication_slots = 10

# Optional extra retention safety, not a replacement for slot monitoring.
wal_keep_size = '2GB'

# Cap physical/logical slot WAL retention according to operational policy.
# Example value only:
max_slot_wal_keep_size = '50GB'

wal_level=replica or higher is required for physical standby connections, and max_wal_senders controls concurrent WAL sender/base-backup connections. Replication slots require max_replication_slots capacity. PostgreSQL 18 also provides max_slot_wal_keep_size to bound WAL retained by slots at checkpoint time.[18]

6.2 Dedicated replication role

CREATE ROLE physical_repl
LOGIN
REPLICATION
PASSWORD 'managed-out-of-band';
# pg_hba.conf
hostssl replication physical_repl 10.20.10.0/24 scram-sha-256

Physical standbys authenticate to the replication pseudo-database using a superuser or a role with REPLICATION; PostgreSQL recommends a dedicated replication account rather than a superuser.[1]

6.3 Seed the standby with pg_basebackup

pg_basebackup \
  --host=pg1.internal \
  --username=physical_repl \
  --pgdata=/var/lib/postgresql/18/main \
  --wal-method=stream \
  --write-recovery-conf \
  --create-slot \
  --slot=pg2_physical \
  --progress

pg_basebackup creates a cluster-wide physical base backup using the replication protocol. -R/--write-recovery-conf writes standby.signal and connection settings; -C -S slot can create/use a physical slot and persist that slot name for the future standby connection.[15]

6.4 Standby connection identity

# Typically written into postgresql.auto.conf by pg_basebackup -R.
primary_conninfo =
  'host=pg1.internal port=5432 user=physical_repl application_name=pg2 sslmode=verify-full'

primary_slot_name = 'pg2_physical'

The standby's application_name is important when it is named in synchronous_standby_names.[18]

7. Replication slots

A replication slot records how far a replication consumer has progressed so PostgreSQL retains resources the consumer still needs. For physical replication, this principally protects required WAL. Logical slots additionally retain WAL/catalog visibility required for logical decoding. Slots survive disconnects, which is precisely why an abandoned slot can consume unbounded disk space unless retention/inactivity safeguards and monitoring are configured.[1][19]

7.1 Create a physical slot

SELECT *
FROM pg_create_physical_replication_slot(
    'pg3_physical'
);

7.2 Inspect all slots

SELECT
    slot_name,
    slot_type,
    active,
    active_pid,
    restart_lsn,
    confirmed_flush_lsn,
    wal_status,
    safe_wal_size,
    inactive_since,
    invalidation_reason,
    failover,
    synced
FROM pg_replication_slots
ORDER BY slot_name;

PostgreSQL 18 exposes slot WAL status, remaining safe WAL size under configured limits, inactivity, invalidation reason, and logical failover/synchronization state. A slot can become unusable if required WAL is removed or other invalidation conditions occur.[19]

7.3 PostgreSQL 18 idle-slot invalidation

# Example operational safety net.
idle_replication_slot_timeout = '24h'

PostgreSQL 18 added idle_replication_slot_timeout, which can invalidate slots that remain inactive longer than the configured duration. This helps contain abandoned-slot risk but must be set long enough for legitimate outages and maintenance windows.[18][20]

A replication slot is a retention promise. If the consumer is offline, the producer can keep generating WAL while the slot prevents deletion. Monitor slot lag and disk space as one failure mode.

8. Asynchronous replication

Physical streaming replication is asynchronous by default. The primary can acknowledge a transaction commit before a standby has durably received the commit WAL. If the primary is then lost and the standby is promoted, transactions present only on the old primary can disappear from the promoted history. The amount of potential loss depends on the replication delay at failure time.[1]

8.1 Why asynchronous replication is attractive

The primary does not add the standby network/storage round trip to ordinary commit latency. This works well for geographically distant read replicas, workloads willing to tolerate a small failover loss window, and replicas whose principal purpose is read scaling rather than zero-data-loss HA.

8.2 Measure byte lag, not just “connected” state

SELECT
    application_name,
    state,
    sync_state,
    pg_size_pretty(
        pg_wal_lsn_diff(
            pg_current_wal_lsn(),
            replay_lsn
        )
    ) AS replay_byte_lag
FROM pg_stat_replication;

A standby can be connected and streaming but still be too far behind to satisfy a particular failover loss objective.

9. Synchronous replication

Synchronous replication makes selected write transactions wait for confirmation from one or more synchronous replication consumers. In ordinary physical streaming replication, this improves durability because the application does not receive commit success until the configured remote acknowledgement has occurred. The trade-off is commit latency and write availability if PostgreSQL cannot obtain enough required acknowledgements.[1][10]

9.1 Priority-based synchronous standbys

# primary postgresql.conf
synchronous_standby_names =
  'FIRST 1 (pg2, pg3)'

With FIRST 1, PostgreSQL chooses the highest-priority currently eligible standby from the listed names; another candidate can take over synchronous responsibility if the preferred standby disconnects.[1]

9.2 Quorum-based synchronous standbys

synchronous_standby_names =
  'ANY 2 (pg2, pg3, pg4)'

ANY 2 requires acknowledgements from any two of the listed synchronous candidates, avoiding a fixed priority ordering.[1]

9.3 synchronous_commit acknowledgement levels

SettingCommit waits forImplication
offDoes not wait for local WAL flushAsynchronous commit; transaction can be lost after server/OS crash.
localLocal primary flushNo synchronous-replica wait.
remote_writeStandby has received and written commit WAL to its OSLower remote durability than flush-to-disk, potentially less latency.
onRequired synchronous standby has flushed commit WAL durablyStandard synchronous durability mode.
remote_applyRequired synchronous standby has replayed commitChange is visible to new standby queries; highest acknowledgement latency.

PostgreSQL documents remote_apply as useful in simple cases for load balancing with causal consistency because commit does not return until the synchronous standby has replayed the transaction.[1][10]

9.4 Per-transaction durability policy

BEGIN;

SET LOCAL synchronous_commit = 'remote_apply';

INSERT INTO finance.payment(...);

COMMIT;

Because synchronous_commit can be changed per transaction/session/user/database, a workload can reserve strongest remote durability for business-critical transactions without imposing it on every write.[1]

Synchronous replication can reduce write availability. If commits require acknowledgements that no eligible standby can provide, write transactions can wait indefinitely until configuration changes, a suitable standby returns, or shutdown intervenes. Design the synchronous quorum and failure domains together.

10. Hot standby and read replicas

With hot_standby=on, a physical standby accepts read-only connections after reaching a consistent recovery point. Replicas are useful for reporting, expensive reads, backup offload, and geographical read locality. Because WAL must be replayed after it is generated and transferred, an asynchronous read replica is eventually consistent with the primary rather than immediately identical at every wall-clock instant.[14]

10.1 Is this server a standby?

SELECT pg_is_in_recovery();

10.2 Receive versus replay progress

SELECT
    pg_last_wal_receive_lsn() AS received,
    pg_last_wal_replay_lsn()  AS replayed,
    pg_last_xact_replay_timestamp() AS last_replay_time;

10.3 Query/recovery conflicts

A standby must replay the primary's WAL, including cleanup records. Long-running read queries can conflict with replay. max_standby_streaming_delay and max_standby_archive_delay determine how long replay can wait before conflicting standby queries are canceled. hot_standby_feedback=on can reduce cleanup conflicts by reporting standby visibility needs upstream, but PostgreSQL warns that it can increase bloat on the primary.[14][18] 

# Reporting-oriented standby example; values are workload-specific.
max_standby_streaming_delay = '5min'
hot_standby_feedback = on

10.4 Delayed replica

# Example disaster-recovery/read-replica safety window.
recovery_min_apply_delay = '15min'

A delayed standby intentionally postpones replay of transaction commit records, providing a time window against some operator mistakes. This increases WAL accumulation and is not a replacement for PITR backups.[18]

11. Cascading replication

A physical standby can itself accept replication connections and relay WAL to downstream standbys. Cascading reduces direct WAL sender load on the primary and can reduce cross-site bandwidth when one regional relay feeds several local replicas. PostgreSQL currently treats cascading streaming as asynchronous; synchronous standby settings on the primary do not make downstream cascaded replicas synchronous with the primary.[1]

primary (region A) | +==== streaming ====> standby-a (region B) | +=====> standby-b1 | +=====> standby-b2

A downstream standby points its primary_conninfo to the upstream standby. The upstream must be configured to send WAL (max_wal_senders, authentication, and hot-standby-compatible settings).[1]

12. Monitoring physical replication

12.1 Primary-side lag dimensions

SELECT
    application_name,
    client_addr,
    state,
    sync_state,
    pg_size_pretty(
        pg_wal_lsn_diff(
            pg_current_wal_lsn(),
            sent_lsn
        )
    ) AS sender_backlog,
    pg_size_pretty(
        pg_wal_lsn_diff(
            sent_lsn,
            write_lsn
        )
    ) AS network_or_receiver_backlog,
    pg_size_pretty(
        pg_wal_lsn_diff(
            write_lsn,
            flush_lsn
        )
    ) AS standby_flush_backlog,
    pg_size_pretty(
        pg_wal_lsn_diff(
            flush_lsn,
            replay_lsn
        )
    ) AS replay_backlog
FROM pg_stat_replication;

LSN differences help locate the bottleneck: WAL generation/sender, network/receive, standby disk flush, or replay. Time lag columns are useful but represent recent synchronous-feedback timings rather than a universal prediction of “seconds behind.”[1][17]

12.2 Slot retention pressure

SELECT
    slot_name,
    active,
    wal_status,
    pg_size_pretty(
        pg_wal_lsn_diff(
            pg_current_wal_lsn(),
            restart_lsn
        )
    ) AS retained_wal,
    pg_size_pretty(safe_wal_size) AS safe_wal_remaining,
    invalidation_reason
FROM pg_replication_slots
WHERE slot_type = 'physical';

12.3 Standby conflict statistics

SELECT *
FROM pg_stat_database_conflicts
ORDER BY datname;

A read replica that repeatedly cancels queries or delays replay is not simply “healthy because streaming is connected.” Monitor replay lag and recovery conflicts together.[17]

13. Logical replication

Logical replication sends changes to database objects based on logical row identity rather than copying physical blocks. PostgreSQL's built-in logical replication uses a publish/subscribe model: a publisher exposes one or more publications, and subscribers connect, perform optional initial table synchronization, then continuously apply decoded changes in transactional order.[2][21]

PUBLISHER SQL DML | v WAL | v walsender | v logical decoding + pgoutput | +--> publication filtering | tables / schemas | columns | row filters | INSERT UPDATE DELETE TRUNCATE | v logical replication protocol | v SUBSCRIBER apply worker | v ordinary target tables

PostgreSQL explicitly lists cross-version, cross-platform, subset replication, consolidation, and access isolation among logical replication use cases.[2]

14. Publications

A publication is a set of changes from one PostgreSQL database. Tables can belong to multiple publications, and publications can select DML operation types. PostgreSQL also supports publication column lists, row filters, and whole-schema publication forms.[22]

14.1 Basic publication

CREATE PUBLICATION app_changes
FOR TABLE
    app.customer,
    app.orders
WITH (
    publish = 'insert, update, delete'
);

14.2 Row filter and column list

CREATE PUBLICATION fulfillment_changes
FOR TABLE app.orders (
    order_id,
    customer_id,
    status,
    total,
    updated_at
)
WHERE (
    status IN ('paid', 'packed', 'shipped')
)
WITH (
    publish = 'insert, update, delete'
);

When publishing UPDATE or DELETE, the publisher needs a replica identity that lets the subscriber identify the target row—usually the primary key. Publication column lists and row-filter expressions are subject to additional replica-identity rules for these operations.[22]

14.3 Replica identity

ALTER TABLE app.orders
REPLICA IDENTITY USING INDEX orders_pkey;

-- Last resort for tables without a suitable key:
ALTER TABLE legacy_table
REPLICA IDENTITY FULL;

REPLICA IDENTITY FULL can allow updates/deletes without a suitable replica-identity index but transmits/compares more old-row information and is generally less efficient than a proper key.[22]

15. Subscriptions

A subscription defines the downstream connection and publications to consume. By default, PostgreSQL creates a logical replication slot on the publisher and initially copies pre-existing table data before continuously applying subsequent changes. Additional temporary synchronization slots can exist during initial table synchronization.[23]

15.1 Subscriber setup

CREATE SUBSCRIPTION reporting_sub
CONNECTION
  'host=publisher.internal port=5432 dbname=appdb user=logical_repl sslmode=verify-full'
PUBLICATION app_changes
WITH (
    copy_data = true,
    streaming = parallel,
    failover = true
);

Logical replication publishers need wal_level=logical, sufficient WAL sender/slot capacity, and appropriate authentication. Subscriber worker settings such as max_logical_replication_workers and max_worker_processes must accommodate apply, table-sync, and optional parallel apply workers.[24]

15.2 Monitor subscribers

SELECT
    subname,
    worker_type,
    pid,
    leader_pid,
    relid::regclass,
    received_lsn,
    latest_end_lsn,
    last_msg_send_time,
    last_msg_receipt_time
FROM pg_stat_subscription
ORDER BY subname, worker_type;

15.3 Conflict monitoring

SELECT *
FROM pg_stat_subscription_stats
ORDER BY subname;

A logical subscriber can also receive local writes. If incoming replicated changes violate constraints or encounter divergent local data, conflicts can occur; PostgreSQL records defined conflict categories and statistics for logical subscriptions.[25]

16. Logical decoding

Logical decoding is the lower-level infrastructure that extracts logical changes from WAL and feeds an output plugin. It is useful for custom CDC pipelines, audit/event systems, and replication products. Changes are consumed through logical replication slots, and the output plugin controls wire/content format.[13]

16.1 Create an example logical slot

SELECT *
FROM pg_create_logical_replication_slot(
    'cdc_demo',
    'test_decoding'
);

16.2 Consume changes with SQL

SELECT *
FROM pg_logical_slot_get_changes(
    'cdc_demo',
    NULL,
    NULL
);

16.3 Stream through the replication protocol

pg_recvlogical \
  --dbname='host=publisher.internal dbname=appdb user=cdc_user' \
  --slot=cdc_demo \
  --start \
  --file=-

The streaming replication protocol supports logical slot creation and START_REPLICATION ... LOGICAL; pg_recvlogical implements these operations for clients. The built-in logical replication system normally uses the standard pgoutput plugin instead of the human-oriented test_decoding example.[26][16]

Logical slots also retain WAL. A stopped CDC connector can fill producer storage just like an abandoned physical slot. Monitor every slot as a durable consumer obligation.

17. Replication origins

Replication origins track how far changes from an external logical source have been replayed and provide an origin identity for changes. PostgreSQL designed them to support safe logical replication progress tracking and to help replication systems distinguish locally generated changes from changes replayed from another origin, which is important in loop-prevention designs.[27]

17.1 Create and inspect an origin

SELECT pg_replication_origin_create(
    'mycdc/upstream-east'
);

SELECT *
FROM pg_replication_origin;

SELECT *
FROM pg_replication_origin_status;

Built-in logical subscriptions use replication-origin infrastructure internally to track apply progress; custom logical replication implementations can use the same facilities through the replication-origin functions.[27]

18. Logical replication through physical failover

A historically difficult topology is a physical HA publisher that also feeds logical subscribers: promoting the physical standby changes the publisher server, but downstream logical replication also depends on logical slots. PostgreSQL 18 supports failover-capable logical slots that can be synchronized to physical standbys, allowing subscriptions to continue from the promoted publisher when the topology is configured correctly.[28]

18.1 Subscription requests a failover slot

CREATE SUBSCRIPTION analytics_sub
CONNECTION
  'host=publisher-vip.internal dbname=appdb user=logical_repl sslmode=verify-full'
PUBLICATION analytics_pub
WITH (
    failover = true
);

18.2 Primary coordinates physical and logical progress

# primary postgresql.conf
synchronized_standby_slots = 'pg2_physical'
# physical standby postgresql.conf
sync_replication_slots = on

# Slot synchronization also requires a dbname in primary_conninfo.
primary_conninfo =
  'host=pg1.internal dbname=postgres user=physical_repl application_name=pg2'

PostgreSQL's failover documentation emphasizes that logical slot synchronization is asynchronous, so operators must verify the synchronized slots are ready before a planned switch. synchronized_standby_slots ensures logical WAL sending waits until the designated physical standby has received the WAL needed to preserve those failover slots.[18][28]

18.3 Inspect failover readiness

SELECT
    slot_name,
    slot_type,
    failover,
    synced,
    active,
    confirmed_flush_lsn,
    restart_lsn,
    invalidation_reason
FROM pg_replication_slots
WHERE slot_type = 'logical';

19. Failover and fencing

Failover is an unplanned transition after the current primary becomes unavailable or unsuitable. Native PostgreSQL can promote a standby with pg_ctl promote or pg_promote(), but it does not itself provide the external failure detector, cluster-wide leader election, client endpoint update, or fencing mechanism needed for safe automatic HA.[5] 

SELECT pg_promote(
    wait_seconds => 60,
    wait         => true
);

19.1 Split brain is the central safety failure

network partition | +-------------------------+ | | old primary standby still writable promoted | | v v accepts writes accepts writes \ / \---- divergent WAL ----/ Result: two primaries, conflicting histories, possible data loss.

PostgreSQL's failover documentation explicitly requires a mechanism to ensure that a former primary cannot simply restart as primary after another standby has been promoted. This class of mechanism is often called fencing or STONITH. The exact implementation may be power fencing, hypervisor/cloud fencing, network isolation, storage fencing, or another authoritative mechanism.[5]

19.2 Promotion changes the timeline

When a standby is promoted, PostgreSQL creates a new recovery timeline. Other standbys can follow the new timeline when configured with recovery_target_timeline='latest' (the default). The old primary's divergent timeline must be reconciled before it can safely rejoin.[1]

20. Switchover

A switchover is a planned role transition performed while the cluster is healthy—for example, to patch the current primary, change infrastructure, or regularly test HA. A controlled system verifies the target standby is suitably caught up, prevents new writes on the old primary, promotes the target, redirects clients, and converts/rebuilds the old primary as a standby.[5][29]

20.1 Patroni switchover

patronictl -c /etc/patroni.yml switchover \
  postgres-ha \
  --primary pg1 \
  --candidate pg2

Patroni documents switchover as the preferred operation for a healthy cluster and failover as the operation intended for unhealthy situations. Forced/manual failover can cause data loss if the candidate is behind the former primary.[29]

20.2 Rejoin the old primary

PostgreSQL's pg_rewind can often synchronize a former primary with the new primary much faster than taking a full new base backup, provided the cluster was configured to preserve the information pg_rewind requires and the histories are suitable.[5][30]

21. Connection routing

After failover, applications should not need to know which host was promoted. A routing layer provides a stable endpoint and uses an authoritative health/leadership signal—not merely “TCP port 5432 accepts connections”—to distinguish the writer from replicas.

application | +--> db-write.internal:5432 | | | v | HAProxy | | | +--> Patroni /primary == 200 ? pg1 : no | +--> Patroni /primary == 200 ? pg2 : yes ---> PostgreSQL pg2 | +--> Patroni /primary == 200 ? pg3 : no | +--> db-read.internal:5432 | v HAProxy | +--> /replica?lag=64MB -> pg1/pg3 eligible +--> balance read traffic

21.1 DNS, virtual IPs, proxies, and service discovery

Common patterns include a floating virtual IP, a TCP proxy/load balancer, service discovery, or application drivers that can try multiple endpoints. A proxy usually gives the cleanest separation between database topology and application connection strings, but the proxy itself must be deployed redundantly so it does not become the new single point of failure.

22. Patroni

Patroni is an HA orchestration framework for PostgreSQL. It uses PostgreSQL streaming replication for data movement and a distributed configuration store for cluster coordination/leader state. Patroni exposes a REST API used internally for leader races, by patronictl for operational actions, and by load balancers such as HAProxy for role-aware health checks.[6][31]

22.1 Minimalized Patroni configuration shape

scope: postgres-ha
namespace: /service/
name: pg1

restapi:
  listen: 0.0.0.0:8008
  connect_address: 10.20.10.11:8008

etcd3:

22.2 Leader lock and timing

Patroni stores dynamic configuration in the DCS. Its ttl is the lifetime of the leader lock, loop_wait controls its HA loop interval, and retry_timeout bounds retries for DCS/PostgreSQL operations. Patroni documents a relationship between these values and also provides maximum_lag_on_failover to exclude excessively lagged asynchronous replicas from automatic leader election.[32]

22.3 Patroni health endpoints

# HTTP 200 only when node is PostgreSQL primary and holds leader lock:
GET /primary

# HTTP 200 only for an eligible replica:
GET /replica

# Include a lag threshold:
GET /replica?lag=64MB

Patroni's current REST API documents /primary//read-write for leader-primary health checks and /replica for load-balancer-eligible replicas, including optional lag thresholds.[31]

22.4 Synchronous mode

Patroni can manage PostgreSQL synchronous-replication settings to trade write availability for stronger durability. This does not eliminate the fundamental distributed-systems trade-off: a cluster that refuses writes without a synchronous copy is choosing data durability over availability during some failures; a cluster that promotes an asynchronous replica may lose acknowledged transactions if it is behind.[1][32]

23. Distributed coordination with etcd or Consul

The DCS does not carry PostgreSQL table data; it carries coordination metadata such as leader state and cluster configuration. It must therefore provide a consistent, quorum-backed mechanism for leader coordination under node and network failures.

23.1 etcd

etcd is a distributed consistent key-value store widely used for metadata and coordination. Its v3 API exposes key/value operations, watches, and leases; leases have TTLs and attached keys are deleted when the lease expires. etcd uses a Raft-based replicated consensus design and provides revision metadata useful for ordered distributed coordination.[7][33]

Patroni pg1 ----+ Patroni pg2 ----+----> etcd quorum Patroni pg3 ----+ etcd1 etcd2 etcd3 \ | / Raft consensus

23.2 Consul

Consul's server agents use Raft consensus for authoritative cluster state. Consul provides a KV store and sessions that bind node/health/TTL state to keys and can be used to implement distributed locks. Patroni can use Consul as an alternative DCS backend.[8][34][35]

23.3 Keep DCS failure domains independent

Placing every DCS voting member on the same host, rack, or failure domain as one database node undermines the point of quorum coordination. A three-member DCS is normally spread across independent failure domains so the loss of one member does not eliminate quorum; exact topology should reflect infrastructure failure modes and latency.

The DCS is part of the database HA control plane. Back it up where supported, monitor quorum and latency, secure client/peer traffic, and test database behavior when the DCS becomes unavailable or partitioned.

24. HAProxy routing with Patroni health checks

HAProxy provides active health checking and removes servers from load-balancing rotation when checks fail, restoring them after configured successful checks. Patroni's role-aware HTTP endpoints make it possible to check the Patroni control plane on port 8008 while sending PostgreSQL client connections to port 5432.[9][31]

24.1 Writer endpoint

global
    log stdout format raw local0

defaults
    mode tcp
    timeout connect 5s
    timeout client  1m
    timeout server  1m

frontend postgres_write
    bind *:5432
    default_backend postgres_primary

backend postgres_primary
    mode tcp
    option httpchk GET /primary
    http-check expect status 200

    server pg1 10.20.10.11:5432 check port 8008 inter 2s fall 3 rise 2
    server pg2 10.20.10.12:5432 check port 8008 inter 2s fall 3 rise 2
    server pg3 10.20.10.13:5432 check port 8008 inter 2s fall 3 rise 2

Only the Patroni node that is PostgreSQL primary and holds the leader lock returns success from /primary, so the writer backend converges on a single eligible server.[31]

24.2 Read-replica endpoint

frontend postgres_read
    bind *:5433
    default_backend postgres_replicas

backend postgres_replicas
    mode tcp
    balance leastconn

    option httpchk GET /replica?lag=64MB
    http-check expect status 200

    server pg1 10.20.10.11:5432 check port 8008 inter 2s fall 3 rise 2
    server pg2 10.20.10.12:5432 check port 8008 inter 2s fall 3 rise 2
    server pg3 10.20.10.13:5432 check port 8008 inter 2s fall 3 rise 2

Patroni's replica endpoint can exclude nodes with a configured noloadbalance-style tag/state and can apply a byte-lag limit supplied in the request. The HAProxy health check then keeps only eligible replicas in rotation.[31]

Make the routing tier HA too. Two redundant HAProxy instances behind a virtual IP, cloud/network load balancer, or another resilient front end are preferable to one proxy that turns a three-node PostgreSQL cluster into a single-endpoint single point of failure.

25. Load balancing and consistency

25.1 Writes go to one authoritative primary

In a standard physical-replication HA cluster, all ordinary writes go to the primary. A generic round-robin proxy must not send write connections across primary and standbys indiscriminately.

25.2 Reads can be distributed—but may be stale

Asynchronous replicas can lag. Sending a user to a replica immediately after a successful write can produce a read that does not yet observe that write. Applications can tolerate this, pin consistency-sensitive reads to the primary, enforce lag thresholds, or use stronger synchronous acknowledgement such as remote_apply in workflows where the latency trade-off is acceptable.[1][14]

25.3 Separate pools

# Application connection strings conceptually:
DATABASE_WRITE_URL=postgresql://app@db-write.internal:5432/appdb
DATABASE_READ_URL=postgresql://app_ro@db-read.internal:5433/appdb

Separate credentials can reinforce the routing contract: the read pool can use a role whose database privileges are read-only even if it accidentally reaches a writable server.

25.4 Existing connections do not teleport

A load balancer redirects new connections after failover; existing TCP sessions to the failed/demoted primary break and applications must reconnect. Connection pools should have bounded connection lifetimes/health checking and robust retry behavior at safe transaction boundaries.

26. HA operations, rewind, backups, and testing

26.1 Rebuild the failed former primary

After promotion, the old primary's timeline can diverge. It must not simply reconnect as though nothing happened. PostgreSQL recommends recreating a standby and notes that pg_rewind can accelerate reconciliation for suitable clusters.[5][30]

26.2 Backups from a standby

pg_basebackup can take a backup from a standby when required replication/hot-standby configuration is present, which can offload work from the primary. PostgreSQL documents several limitations, including failure if that standby is promoted during the backup.[15]

26.3 Regular switchovers are HA tests

PostgreSQL explicitly recommends regular primary/standby switching as both a maintenance technique and a test that the failover mechanism will function when needed. Runbooks should cover the database nodes, DCS, routing layer, application reconnection, logical slots, backups, monitoring, and rejoin procedure.[5]

28. Common pitfalls

28.1 “Streaming” does not mean synchronous

PostgreSQL streaming replication is asynchronous unless synchronous standby configuration and a waiting synchronous_commit level make commits wait.[1]

28.2 Slots without alerts

An inactive slot can retain WAL until pg_wal fills. Configure retention limits/timeouts deliberately and alert on restart_lsn lag, safe_wal_size, inactivity, and invalidation.[18][19]

28.3 Two-node automatic failover without authoritative fencing

If a network partition makes each database side believe the other has failed, both can accept writes unless an external consensus/fencing mechanism prevents it. PostgreSQL specifically warns about the returning old primary and the need for STONITH-like protection.[5]

28.4 Treating read replicas as immediately consistent

Asynchronous hot standbys can lag and return older snapshots. Choose the read endpoint based on the consistency requirement of each request.[14]

28.5 Making hot_standby_feedback a universal fix

It reduces some standby query cancellations but can delay cleanup and create bloat on the primary. Monitor both replica usability and primary vacuum health.[18]

28.6 Forgetting logical slots during physical failover

A physical promotion can be perfect while downstream CDC/logical subscribers fail because their logical slots did not move. Use PostgreSQL's failover-slot synchronization when logical subscribers must survive publisher failover.[28]

28.7 Health checking only port 5432

A PostgreSQL process can accept TCP connections while being a standby or while the HA manager considers it ineligible for leadership. Route writes using role/leader-aware health state such as Patroni's /primary endpoint.[31]

28.8 One load balancer in front of three database nodes

Database redundancy does not help if the only client entry point is a single failed proxy. The routing layer needs its own redundancy strategy.

28.9 Promoting the most convenient replica instead of the safest one

With asynchronous replication, promotion candidate lag determines potential lost transactions. Patroni's maximum_lag_on_failover exists specifically to exclude replicas beyond an operator-defined lag threshold from automatic elections.[32]

28.10 Assuming HA replaces disaster recovery

Replication protects availability from node failures. PITR/backups protect different failure classes, including replicated human/application mistakes and corruption scenarios.[11]

29. Production checklist

  1. Define durability and availability targets. Decide how much acknowledged-write loss is acceptable and how much commit latency/unavailability is acceptable.
  2. Use dedicated replication identities. Protect replication connections with narrow HBA rules and TLS.
  3. Capacity WAL senders and slots. Include physical replicas, base backups, logical subscriptions, and synchronization workers.
  4. Monitor slot retention. Alert before WAL disk space becomes critical.
  5. Choose asynchronous vs synchronous deliberately. Do not infer it from the word “streaming.”
  6. Design synchronous quorum across failure domains.
  7. Monitor receive, flush, and replay progress separately.
  8. Tune read replicas for their purpose. HA replicas and long-query reporting replicas often need different conflict policies.
  9. Fence the former primary. Promotion without fencing is not safe automatic HA.
  10. Use a quorum-backed DCS for Patroni. Monitor DCS quorum, latency, and certificates/credentials.
  11. Route by authoritative role state. Use Patroni-aware health checks rather than TCP-only writer checks.
  12. Make routing redundant. HAProxy/load-balancer infrastructure needs its own HA design.
  13. Separate writer and reader endpoints. Make replica staleness an explicit application contract.
  14. Plan logical replication through failover. Synchronize failover slots before promotion.
  15. Practice switchovers. Include application reconnect behavior and old-primary rejoin.
  16. Test destructive/network failures. A diagram is not evidence that failover is safe.
  17. Retain backups and WAL archives. HA is not PITR.
  18. Document the degenerate state. After failover, rebuild redundancy promptly.
HA principle: replication moves data; consensus chooses authority; fencing prevents two authorities; routing exposes the chosen authority to clients. A PostgreSQL HA design is correct only when all four behaviors agree during failures.
