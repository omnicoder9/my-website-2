PostgreSQL Security

A production-oriented guide to authentication, authorization, roles, role inheritance, privileges, row-level security, TLS, pg_hba.conf, password authentication, SCRAM, LDAP, Kerberos/GSSAPI, client certificates, auditing, SECURITY DEFINER functions, and SQL-injection prevention.

Technical article • PostgreSQL 18.6 baseline • Updated 15 September 2026 • Vancouver-style references

Abstract

PostgreSQL security is layered. Network reachability and transport protection determine who can reach the server and whether traffic is protected in transit. pg_hba.conf selects the authentication mechanism for a matching connection. Authentication proves an identity, while PostgreSQL roles, role memberships, object ownership, privileges, and row-level security determine what that identity can do after login. Server logs and audit extensions record activity, and application-side parameter binding prevents untrusted input from becoming executable SQL syntax.[1]-[5]

The security model is powerful because PostgreSQL separates these layers. A client may authenticate with SCRAM, LDAP, GSSAPI/Kerberos, or a certificate yet still receive no access to application data. Conversely, a perfectly designed privilege model is ineffective if a broad trust HBA rule lets arbitrary network clients impersonate privileged roles. Secure deployments therefore treat authentication, authorization, encryption, database ownership, application query construction, auditing, and operating-system/network controls as one system.[1][6]

1. PostgreSQL security model

client | | network ACL / firewall / security group v PostgreSQL listener | | TLS or GSSAPI transport protection v pg_hba.conf | | authentication: | SCRAM / GSS / LDAP / certificate / peer / ... v session identity (role) | +--> role memberships / SET ROLE | +--> database CONNECT | +--> schema USAGE / CREATE | +--> table / sequence / function privileges | +--> row-level security policies | +--> SECURITY DEFINER privilege boundaries | v SQL execution | +--> logs / pgAudit / monitoring | +--> application parameter binding prevents injection

PostgreSQL uses roles as its database identity and authorization primitive. A role may have LOGIN and act as a login user, may have NOLOGIN and act as a privilege group, may own objects, and may be granted membership in other roles. Roles are cluster-wide rather than scoped to a single database.[7][8]

Authentication and authorization are distinct. The authentication chapter describes how a connection proves the PostgreSQL role name it requested; database roles and object privileges determine what the session may access once authentication succeeds.[1][7]

2. Authentication

PostgreSQL 18 supports multiple client authentication methods, including trust, password authentication, GSSAPI, SSPI on Windows, Ident/peer, LDAP, RADIUS, certificate authentication, PAM, BSD authentication, and OAuth. The appropriate choice depends on whether identity is local or centralized, whether single sign-on is required, and what security infrastructure—certificate authority, Kerberos realm, LDAP directory, or OAuth provider—is available.[6]

2.1 Authentication does not create roles

External authentication methods validate an external identity but generally do not create PostgreSQL roles automatically. LDAP authentication, for example, verifies a username/password pair through LDAP, but the corresponding PostgreSQL database role must already exist. GSSAPI and certificate identities can be transformed through username maps when the external name differs from the PostgreSQL role name.[9][10]

3. pg_hba.conf

Client authentication is controlled by the host-based authentication file, traditionally pg_hba.conf. PostgreSQL evaluates HBA records in order. The first record matching connection type, database, user, and client address determines the authentication method; if authentication using that record fails, PostgreSQL does not fall through to later matching records. If no record matches, the connection is denied.[2]

3.1 Secure example

# TYPE      DATABASE       USER             ADDRESS          METHOD

# Local administrative login from operating-system identity.
local       all            postgres                          peer

# Application traffic: TLS + SCRAM, restricted subnet and role.
hostssl     appdb          app_login        10.20.10.0/24    scram-sha-256

# Read-only service group.
hostssl     appdb          +app_readers     10.20.20.0/24    scram-sha-256

# Physical replication.
hostssl     replication    replicator       10.20.30.15/32   scram-sha-256

# Explicitly reject anything else.
host        all            all              0.0.0.0/0        reject
host        all            all              ::0/0            reject

hostssl matches only SSL-encrypted TCP connections. A role name prefixed by + matches direct or indirect members of that role. CIDR prefixes limit client networks, and explicit reject records can document a deny policy. Access also requires the role to have CONNECT privilege on the target database.[2]

3.2 Validate before reload

SELECT
    line_number,
    type,
    database,
    user_name,
    address,
    auth_method,
    options,
    error
FROM pg_hba_file_rules
ORDER BY line_number;

pg_hba_file_rules can reveal syntax/configuration errors before or after a change. On Unix-like systems, HBA changes take effect after a configuration reload; PostgreSQL documents pg_reload_conf(), pg_ctl reload, or SIGHUP as reload mechanisms.[2] 

SELECT pg_reload_conf();

3.3 Order is policy

HBA rules are ordered. Put narrow, deliberate rules before broad ones. A permissive early rule can make stricter later rules unreachable because PostgreSQL does not “try the next method” after a matched record fails.[2]

4. Password authentication

PostgreSQL 18 supports scram-sha-256, md5, and clear-text password HBA methods. SCRAM is the preferred password method. MD5-encrypted password support is deprecated and scheduled for removal in a future PostgreSQL release. The clear-text password method transmits the password as clear text at the PostgreSQL protocol layer and should only be considered when the transport itself is securely encrypted; SCRAM is preferable in ordinary deployments.[11][12]

4.1 Password storage algorithm

SHOW password_encryption;
-- PostgreSQL 18 default: scram-sha-256

password_encryption controls the format used when a new password is assigned. PostgreSQL 18 defaults this parameter to scram-sha-256. Older clients that lack SCRAM support may require upgrades before an MD5-to-SCRAM migration.[12]

4.2 Set passwords without exposing them in shell history

-- In psql:
\password app_login

PostgreSQL warns that putting a clear-text password directly in CREATE ROLE or ALTER ROLE commands can expose it through client history or logging. The psql \password command prompts interactively and avoids embedding the clear-text value in SQL text.[13]

4.3 Password expiration

ALTER ROLE temporary_vendor
PASSWORD 'generated-out-of-band'
VALID UNTIL '2026-10-01 00:00:00+00';

VALID UNTIL applies to password authentication, not to the role itself. A role whose password is expired can still authenticate through a non-password method if the applicable HBA rules permit it.[8]

5. SCRAM-SHA-256

SCRAM-SHA-256 is PostgreSQL's modern password challenge-response mechanism. It prevents the password from being sent directly during authentication and stores a cryptographic verifier instead of a reusable clear-text password. PostgreSQL also supports SCRAM-SHA-256-PLUS when TLS channel binding is available.[14]

5.1 Configure SCRAM

# postgresql.conf
password_encryption = 'scram-sha-256'

# pg_hba.conf
hostssl appdb app_login 10.20.10.0/24 scram-sha-256

5.2 Channel binding

SCRAM channel binding mixes information derived from the TLS server certificate into authentication, which helps prevent a man-in-the-middle server from transparently forwarding the SCRAM exchange. PostgreSQL's libpq security documentation recommends verified TLS and notes that channel_binding=require can strengthen SCRAM against server-spoofing attacks.[14][15] 

psql "host=db.example.com \
dbname=appdb \
user=app_login \
sslmode=verify-full \
sslrootcert=/etc/postgresql/root.crt \
channel_binding=require"

6. LDAP authentication

PostgreSQL LDAP authentication uses an LDAP server to validate the presented username/password. LDAP does not replace PostgreSQL authorization: the requested PostgreSQL role must already exist, and its memberships and object privileges remain PostgreSQL-managed. PostgreSQL supports both simple-bind and search-plus-bind configurations.[9]

6.1 Search-plus-bind HBA example

# Example only: adapt TLS, directory base, service account,
# and attribute names to the actual directory.

hostssl appdb all 10.30.0.0/16 ldap \
    ldapserver=ldap.example.com \
    ldapscheme=ldaps \
    ldapport=636 \
    ldapbasedn="ou=People,dc=example,dc=com" \
    ldapbinddn="cn=postgres-search,ou=Service,dc=example,dc=com" \
    ldapbindpasswd="loaded-through-secure-config-management" \
    ldapsearchattribute="uid"

In search-plus-bind mode PostgreSQL first searches the directory to find the user's DN and then binds as that DN to validate the user's password. The search service account's password becomes a server-side secret and should be protected through file permissions and secret-management processes.[9]

6.2 Directory membership is not database privilege membership

LDAP authentication validates identity; it does not by itself map LDAP groups to PostgreSQL privileges. Role creation and membership still need to be provisioned in PostgreSQL (or synchronized by external identity automation). This separation is important when designing deprovisioning workflows.

7. Kerberos and GSSAPI

PostgreSQL supports GSSAPI for authentication, connection encryption, or both. In common enterprise deployments the GSSAPI mechanism is Kerberos, giving users single sign-on based on Kerberos tickets instead of database passwords. PostgreSQL must be built with GSSAPI support, and the server normally uses a Kerberos service principal such as postgres/hostname@REALM stored in a keytab readable by the PostgreSQL server account.[16][17]

7.1 HBA example

# Require GSSAPI-encrypted connections and GSS authentication.
hostgssenc appdb all 10.40.0.0/16 gss \
    include_realm=1 \
    map=corp_users

7.2 Username map

# pg_ident.conf
# MAPNAME       SYSTEM-USERNAME                  PG-USERNAME
corp_users      /^(.*)@EXAMPLE\.COM$             \1

PostgreSQL username maps can translate an external principal into a PostgreSQL role name. The GSSAPI documentation recommends retaining realm information during authentication and performing explicit mappings rather than simply stripping realms in multi-realm environments.[10][16]

7.3 GSSAPI encryption

GSSAPI can also encrypt the database connection. PostgreSQL warns that optional GSS encryption can be subject to downgrade if the client does not require it; use hostgssenc server rules and gssencmode=require client settings when GSS encryption is a security requirement.[17][15]

8. Certificate authentication

PostgreSQL certificate authentication requires an SSL connection and uses a client X.509 certificate as the authentication credential. With the cert HBA method, PostgreSQL validates the client certificate chain and maps certificate identity—by default the certificate common name—to a PostgreSQL username, optionally through pg_ident.conf.[18][19]

8.1 Server setup

# postgresql.conf
ssl = on
ssl_cert_file = '/etc/postgresql/tls/server.crt'
ssl_key_file  = '/etc/postgresql/tls/server.key'
ssl_ca_file   = '/etc/postgresql/tls/client-ca.crt'
# pg_hba.conf
hostssl appdb app_machine 10.50.10.0/24 cert clientname=CN

8.2 Certificate plus another authentication method

PostgreSQL also allows a hostssl rule to require a trusted client certificate with clientcert=verify-ca or clientcert=verify-full while using another HBA authentication method such as SCRAM. verify-full additionally requires the certificate identity to match the requested username or username mapping.[2][19] 

hostssl appdb sensitive_app 10.50.20.0/24 scram-sha-256 \
    clientcert=verify-full

9. SSL/TLS

PostgreSQL uses SSL/TLS to encrypt TCP client/server traffic. Server-side TLS requires SSL support in the PostgreSQL build, a server certificate, and a matching private key. Client-side security depends on verification settings: encryption alone is not sufficient to prevent server impersonation if the client does not verify certificate trust and hostname.[19][20]

9.1 Client verification

postgresql://app_login@db.example.com:5432/appdb\
?sslmode=verify-full\
&sslrootcert=/etc/postgresql/root.crt

libpq's verify-full mode validates the certificate chain and verifies that the server certificate matches the requested host name. PostgreSQL's spoofing guidance recommends verify-ca or, preferably for identity verification, verify-full rather than encryption without certificate verification.[15][20]

9.2 Require encrypted HBA records

# Only encrypted TCP connections can match.
hostssl appdb all 10.20.0.0/16 scram-sha-256

A plain host rule can match encrypted and unencrypted TCP connections. Use hostssl where TLS is mandatory, and ensure ssl=on and valid server key/certificate configuration are in place.[2]

10. Authorization

After authentication, PostgreSQL evaluates authorization from role attributes, role memberships, object ownership, explicit object privileges, schema privileges, default privileges, row-level security, and—in special cases—security-definer code. Superusers bypass normal permission checks and should be reserved for administrative operations that truly require unrestricted access.[7][8][21]

10.1 Prefer capability roles

-- Group/capability roles: cannot log in.
CREATE ROLE app_ro NOLOGIN;
CREATE ROLE app_rw NOLOGIN;
CREATE ROLE app_migrator NOLOGIN;

-- Login identity.
CREATE ROLE orders_api
LOGIN
NOSUPERUSER
NOCREATEDB
NOCREATEROLE
NOREPLICATION
NOBYPASSRLS;

Separating login identities from capability roles simplifies least-privilege management. Privileges can be granted to stable group roles, while memberships can be changed as services, operators, or duties change.[7][22]

11. Roles and users

Since PostgreSQL 8.1, “users” and “groups” are both represented as roles. A role with LOGIN can be selected as the initial session authorization identity and acts like a traditional database user. A NOLOGIN role is useful as a group or privilege bundle. Roles exist across the entire PostgreSQL cluster rather than per database.[7][8]

11.1 Inspect roles

SELECT
    rolname,
    rolsuper,
    rolinherit,
    rolcreaterole,
    rolcreatedb,
    rolcanlogin,
    rolreplication,
    rolbypassrls,
    rolconnlimit,
    rolvaliduntil
FROM pg_roles
ORDER BY rolname;

pg_roles is a publicly readable view over the role catalog that hides password verifiers. It is useful for reviewing potentially dangerous attributes such as SUPERUSER, CREATEROLE, REPLICATION, and BYPASSRLS.[23]

11.2 Avoid giving application roles administrative attributes

Ordinary application roles rarely require SUPERUSER, CREATEDB, CREATEROLE, REPLICATION, or BYPASSRLS. These attributes bypass or expand important authorization boundaries and should be treated as privileged administration capabilities.[8]

12. Role membership and inheritance

Role membership lets one role receive or assume privileges associated with another. In modern PostgreSQL, each membership edge has separate ADMIN, INHERIT, and SET options. INHERIT determines whether ordinary privileges of the granted role are automatically usable; SET determines whether the member can explicitly SET ROLE; ADMIN determines whether the member can grant membership in that role to others.[22][24]

12.1 Automatic inheritance

GRANT app_ro TO orders_api
WITH INHERIT TRUE, SET FALSE, ADMIN FALSE;

Here orders_api can immediately use ordinary privileges granted to app_ro, but cannot switch its current role to app_ro and cannot grant app_ro membership to other roles.

12.2 Explicit privilege elevation

CREATE ROLE release_operator LOGIN;
CREATE ROLE app_migrator NOLOGIN;

GRANT app_migrator TO release_operator
WITH INHERIT FALSE, SET TRUE, ADMIN FALSE;

-- Normal session does not automatically use app_migrator privileges.
SET ROLE app_migrator;

-- Perform migration...

RESET ROLE;

This pattern creates an explicit privilege-elevation step within the database. It can be useful for human operators because privileged activity is distinct from normal session identity and can be combined with auditing.

12.3 Inspect membership edges

SELECT
    granted.rolname AS granted_role,
    member.rolname  AS member_role,
    m.admin_option,
    m.inherit_option,
    m.set_option,
    grantor.rolname AS grantor
FROM pg_auth_members AS m
JOIN pg_roles AS granted ON granted.oid = m.roleid
JOIN pg_roles AS member  ON member.oid  = m.member
JOIN pg_roles AS grantor ON grantor.oid = m.grantor
ORDER BY granted_role, member_role;

pg_auth_members records role membership and all three options, making it suitable for privilege-path auditing.[24]

13. Privileges, GRANT, and REVOKE

PostgreSQL objects have owners and access-control lists. Depending on object type, privileges include SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER, CREATE, CONNECT, TEMPORARY, EXECUTE, USAGE, SET, ALTER SYSTEM, and MAINTAIN. Ownership itself confers powerful control and is not equivalent to an ordinary grant.[21]

13.1 Least-privilege application schema

CREATE SCHEMA app AUTHORIZATION app_migrator;

-- Remove public ability to create in this application schema.
REVOKE ALL ON SCHEMA app FROM PUBLIC;

-- Read capability.
GRANT USAGE ON SCHEMA app TO app_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA app TO app_ro;

-- Write capability inherits read capability.
GRANT app_ro TO app_rw;
GRANT INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA app TO app_rw;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA app TO app_rw;

-- Application login.
GRANT app_rw TO orders_api;

13.2 Database access

REVOKE CONNECT ON DATABASE appdb FROM PUBLIC;

GRANT CONNECT ON DATABASE appdb TO app_ro;
GRANT CONNECT ON DATABASE appdb TO app_rw;
GRANT CONNECT ON DATABASE appdb TO app_migrator;

PostgreSQL grants CONNECT and TEMPORARY on databases to PUBLIC by default. Security-sensitive installations often explicitly review and, where appropriate, revoke defaults instead of assuming that creating a role automatically restricts database reachability.[21]

13.3 Column-level privileges

REVOKE ALL ON app.customer FROM support_agent;

GRANT SELECT (
    customer_id,
    display_name,
    status
)
ON app.customer
TO support_agent;

Table privileges can be granted at column granularity for operations such as SELECT and UPDATE. Column privileges can reduce exposure when a role only needs a subset of fields, though views or application APIs may provide clearer interfaces for complex access rules.[21][25]

13.4 Grant option

GRANT SELECT ON app.reporting_view
TO analytics_lead
WITH GRANT OPTION;

WITH GRANT OPTION lets the recipient grant that object privilege onward. This is an administrative delegation and should not be confused with ordinary use of the privilege. Revoking a grant option can cascade to grants that depended on it.[21][26][27]

14. Default privileges

A common least-privilege failure occurs after a deployment: existing tables have correct grants, but a newly created table is inaccessible because permissions were never assigned. ALTER DEFAULT PRIVILEGES sets privileges that will be applied to objects created in the future by a particular creating role. It does not retroactively alter existing objects.[28] 

ALTER DEFAULT PRIVILEGES
FOR ROLE app_migrator
IN SCHEMA app
GRANT SELECT
ON TABLES
TO app_ro;

ALTER DEFAULT PRIVILEGES
FOR ROLE app_migrator
IN SCHEMA app
GRANT INSERT, UPDATE, DELETE
ON TABLES
TO app_rw;

ALTER DEFAULT PRIVILEGES
FOR ROLE app_migrator
IN SCHEMA app
GRANT USAGE, SELECT
ON SEQUENCES
TO app_rw;

Default privileges are tied to the role that actually creates the future object. PostgreSQL explicitly notes that they are not inherited from the creating role's own role memberships at object-creation time. Migration ownership should therefore be designed deliberately.[28]

15. Row-level security

Row-level security (RLS) restricts which rows a role may read or modify after ordinary SQL privileges have already allowed access to the table. After RLS is enabled, normal access must be permitted by a policy; if no applicable policy exists, PostgreSQL uses a default-deny policy. Superusers and roles with BYPASSRLS bypass row security, and table owners normally bypass it unless FORCE ROW LEVEL SECURITY is used.[5]

15.1 Multi-tenant policy

CREATE TABLE app.order_data (
    order_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id bigint NOT NULL,
    customer_id bigint NOT NULL,
    total numeric(12,2) NOT NULL
);

ALTER TABLE app.order_data ENABLE ROW LEVEL SECURITY;
ALTER TABLE app.order_data FORCE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation
ON app.order_data
USING (
    tenant_id =
    current_setting('app.tenant_id', true)::bigint
)
WITH CHECK (
    tenant_id =
    current_setting('app.tenant_id', true)::bigint
);
BEGIN;

SET LOCAL app.tenant_id = '1042';

SELECT *
FROM app.order_data;

INSERT INTO app.order_data(tenant_id, customer_id, total)
VALUES (1042, 55, 125.00);

COMMIT;

The USING expression controls which existing rows are visible/targetable, while WITH CHECK controls which new row versions are permitted by data-modification commands. The application must ensure that the tenant context itself cannot be freely forged by an untrusted session; RLS is only as strong as the trusted identity/context used by its policy expression.[5]

15.2 Command-specific policies

CREATE POLICY order_read
ON app.order_data
FOR SELECT
TO app_ro
USING (tenant_id = current_setting('app.tenant_id')::bigint);

CREATE POLICY order_write
ON app.order_data
FOR ALL
TO app_rw
USING (tenant_id = current_setting('app.tenant_id')::bigint)
WITH CHECK (tenant_id = current_setting('app.tenant_id')::bigint);

Policies may target specific commands and roles. Multiple permissive policies combine using OR, while restrictive policies combine using AND according to PostgreSQL's row-security rules.[5]

15.3 Verify policy activation

SELECT row_security_active('app.order_data');

The row_security_active() information function tells whether row security is active for a table under the current user/environment, which is useful when testing ownership and BYPASSRLS behavior.[29]

16. SECURITY DEFINER functions

Functions normally run with the privileges of the caller (SECURITY INVOKER). A SECURITY DEFINER function instead runs with the privileges of its owner, allowing it to expose a narrow privileged operation to callers who do not have direct access to the underlying objects. That makes such functions an authorization boundary and a high-value attack surface.[30][31]

16.1 Unsafe pattern

-- Dangerous if search_path includes schemas writable by untrusted roles.
CREATE FUNCTION app.get_secret(p_id bigint)
RETURNS text
LANGUAGE plpgsql
SECURITY DEFINER
AS $$
DECLARE
    v text;
BEGIN
    SELECT secret INTO v
    FROM sensitive_data
    WHERE id = p_id;
    RETURN v;
END;
$$;

If an attacker can create objects in a schema searched before the intended objects, names inside a security-definer function can resolve to attacker-controlled objects. PostgreSQL's function-security guidance therefore recommends excluding untrusted writable schemas from search_path.[30][31]

16.2 Hardened pattern

CREATE FUNCTION app.get_secret(p_id bigint)
RETURNS text
LANGUAGE sql
SECURITY DEFINER
SET search_path = pg_catalog, app_private, pg_temp
AS $$
    SELECT secret
    FROM app_private.sensitive_data
    WHERE id = p_id
$$;

ALTER FUNCTION app.get_secret(bigint)
OWNER TO security_function_owner;

REVOKE ALL
ON FUNCTION app.get_secret(bigint)
FROM PUBLIC;

GRANT EXECUTE
ON FUNCTION app.get_secret(bigint)
TO support_agent;

A safe design uses an owner that has only the privileges the function requires, schema-qualifies sensitive objects, fixes a safe search_path, places pg_temp last, and revokes the default PUBLIC execute privilege before granting execution to intended roles. PostgreSQL explicitly documents the search-path requirement for security-definer functions.[21][30]

Do not make a SECURITY DEFINER function owned by a superuser unless it genuinely requires superuser powers. The function executes with the owner's privileges, so least privilege applies to function ownership just as it applies to application roles.

17. Auditing and logging

17.1 Native PostgreSQL logging

PostgreSQL can emit logs to destinations including stderr, CSV, JSON, syslog, and Windows event log. Logging controls can record connections, disconnections, authentication-related failures, statements, statement duration, lock waits, and other server events. JSON/CSV output can simplify ingestion into centralized log-analysis systems.[32] 

# postgresql.conf

logging_collector = on
log_destination = 'jsonlog'

log_connections = on
log_disconnections = on
log_lock_waits = on

# Log DDL plus data-changing statements.
log_statement = 'mod'

# Alternatively/additionally, duration-driven logging:
log_min_duration_statement = '1000ms'

log_line_prefix =
    '%m [%p] user=%u db=%d app=%a client=%h session=%c '

Verbose statement logging can capture sensitive SQL or parameters and can generate substantial volume. Security logging should balance evidentiary requirements with data minimization, storage controls, and performance overhead.[32]

17.2 pgAudit

pgAudit is an open-source PostgreSQL extension for detailed session and object audit logging through PostgreSQL's standard logging facility. Its project documentation distinguishes audit logging from generic log_statement=all monitoring and maintains PostgreSQL-major-specific branches; pgAudit 18.x targets PostgreSQL 18.[33] 

# postgresql.conf
shared_preload_libraries = 'pgaudit'

# After restart, in the database:
CREATE EXTENSION pgaudit;

# Example session audit classes.
pgaudit.log = 'write, ddl, role'
pgaudit.log_relation = on

Because pgAudit depends on preload hooks, deployment includes a PostgreSQL restart when first enabling it. Audit requirements should define retention, immutability, centralized shipping, privileged log access, clock synchronization, and how sensitive statement contents are handled—not only which SQL statements are emitted.[33]

17.3 Audit role changes

Changes involving role creation, membership, GRANT/REVOKE, RLS policies, schema ownership, and security-definer functions are particularly important because they can change authorization without touching application tables. A security monitoring program should detect these control-plane changes in addition to data-plane reads/writes.

18. SQL injection prevention

SQL injection occurs when untrusted data is merged into SQL syntax rather than transmitted as a data value. The primary defense is parameter binding through the database driver. Parameterization separates the SQL statement structure from values, so data such as quotes or SQL keywords is encoded as a value instead of becoming executable query text.[34][35]

18.1 Unsafe Python

# DO NOT DO THIS.
email = request.args["email"]

sql = (
    "SELECT user_id, email "
    "FROM app_user "
    "WHERE email = '" + email + "'"
)

cursor.execute(sql)

18.2 Safe Psycopg

email = request.args["email"]

cursor.execute(
    """
    SELECT user_id, email
    FROM app_user
    WHERE email = %s
    """,
    (email,),
)

Psycopg's documentation explicitly warns against Python string concatenation/interpolation for query values and instructs callers to supply values separately to execute().[34]

18.3 Safe Java / pgJDBC

String sql = """
    SELECT user_id, email
    FROM app_user
    WHERE email = ?
    """;

try (PreparedStatement ps = connection.prepareStatement(sql)) {
    ps.setString(1, email);

    try (ResultSet rs = ps.executeQuery()) {
        // consume result
    }
}

JDBC PreparedStatement binds parameter values through the driver rather than by concatenating them into SQL. pgJDBC uses the extended PostgreSQL query protocol for prepared statements and can promote repeated executions to named server-side prepared statements for performance; injection safety comes from parameter binding itself, not from whether the server caches the plan.[35][36]

18.4 Values are not identifiers

Bind parameters represent values, not table names, column names, sort directions, SQL keywords, or arbitrary query fragments. Dynamic identifiers must be selected from a trusted allowlist or composed with a driver API that safely quotes SQL identifiers.[34] 

# Bad idea:
# cursor.execute("SELECT * FROM %s WHERE id = %s", (table_name, id))

# Better:
ALLOWED_TABLES = {
    "customers": "app.customer",
    "orders": "app.orders",
}

qualified_table = ALLOWED_TABLES[user_selected_table]

# Then compose the identifier through a trusted library/allowlist,
# while continuing to bind id as a data parameter.

18.5 Dynamic ORDER BY

sort_columns = {
    "created": "created_at",
    "total": "total",
}

sort_directions = {
    "asc": "ASC",
    "desc": "DESC",
}

column = sort_columns.get(requested_sort)
direction = sort_directions.get(requested_direction)

if column is None or direction is None:
    raise ValueError("unsupported sort option")

sql = f"""
    SELECT order_id, total, created_at
    FROM app.orders
    ORDER BY {column} {direction}
    LIMIT %s
"""

cursor.execute(sql, (limit,))

The string composition above is safe only because both SQL fragments come from fixed application-controlled allowlists. Untrusted input is never inserted directly. The numeric limit remains a bound value.

18.6 Least privilege limits injection impact

Parameterization prevents injection, but application-role privileges are a second line of defense. A service account that can read/write only its own schema cannot use an application bug to create superusers, modify unrelated databases, or read privileged catalogs in the same way a superuser-backed application could. SQL-injection prevention and database least privilege should be deployed together.

19. Production security hardening blueprint

19.1 Server network and TLS

# postgresql.conf
listen_addresses = '10.20.0.15'

ssl = on
ssl_cert_file = '/etc/postgresql/tls/server.crt'
ssl_key_file = '/etc/postgresql/tls/server.key'
ssl_ca_file = '/etc/postgresql/tls/client-ca.crt'

password_encryption = 'scram-sha-256'

The database listener should be exposed only on interfaces and networks that require access. Firewalls/security groups should enforce the same principle outside PostgreSQL. TLS protects traffic but does not replace network minimization or database authorization.

19.2 Application role design

-- Owner/migrator is not the runtime login.
CREATE ROLE app_owner NOLOGIN;
CREATE ROLE app_ro NOLOGIN;
CREATE ROLE app_rw NOLOGIN;

CREATE ROLE orders_api
LOGIN
NOSUPERUSER
NOCREATEDB
NOCREATEROLE
NOREPLICATION
NOBYPASSRLS;

CREATE SCHEMA app AUTHORIZATION app_owner;

REVOKE ALL ON SCHEMA app FROM PUBLIC;

GRANT USAGE ON SCHEMA app TO app_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA app TO app_ro;

GRANT app_ro TO app_rw;
GRANT INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA app TO app_rw;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA app TO app_rw;

GRANT app_rw TO orders_api;

19.3 Future objects

ALTER DEFAULT PRIVILEGES
FOR ROLE app_owner
IN SCHEMA app
GRANT SELECT ON TABLES TO app_ro;

ALTER DEFAULT PRIVILEGES
FOR ROLE app_owner
IN SCHEMA app
GRANT INSERT, UPDATE, DELETE ON TABLES TO app_rw;

ALTER DEFAULT PRIVILEGES
FOR ROLE app_owner
IN SCHEMA app
GRANT USAGE, SELECT ON SEQUENCES TO app_rw;

19.4 Restrict public defaults where needed

REVOKE CONNECT ON DATABASE appdb FROM PUBLIC;
GRANT CONNECT ON DATABASE appdb TO app_ro, app_rw, app_owner;

-- If applications do not need temp objects:
REVOKE TEMPORARY ON DATABASE appdb FROM PUBLIC;

-- Review function EXECUTE grants as functions are created.
-- New functions normally receive PUBLIC EXECUTE unless defaults are changed.
ALTER DEFAULT PRIVILEGES
FOR ROLE app_owner
REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC;

PostgreSQL grants some privileges to PUBLIC by default, including database CONNECT/TEMPORARY and function/procedure EXECUTE. A hardened environment should review these defaults explicitly rather than assuming “not granted” means “not accessible.”[21][28]

19.5 Connection rule

# pg_hba.conf
hostssl appdb orders_api 10.20.10.0/24 scram-sha-256
# Client
postgresql://orders_api@db.example.com/appdb\
?sslmode=verify-full\
&sslrootcert=/run/secrets/postgres-ca.crt\
&channel_binding=require

19.6 Security checklist

  1. Network: PostgreSQL is reachable only from required networks and hosts.
  2. TLS: remote clients verify the server certificate and hostname.
  3. HBA: rules are narrow, ordered deliberately, and validated through pg_hba_file_rules.
  4. Password auth: SCRAM is used; deprecated MD5 verifiers are being removed.
  5. Roles: applications are non-superuser, non-CREATEROLE, non-REPLICATION, and non-BYPASSRLS.
  6. Ownership: runtime application logins do not own application tables.
  7. Membership: INHERIT/SET/ADMIN edges are reviewed explicitly.
  8. Privileges: database, schema, table, sequence, function, and default privileges are intentionally assigned.
  9. RLS: tenant/user policies are tested under real runtime roles, including owner/bypass behavior.
  10. Definer code: privileged functions pin a safe search_path and have minimal owners.
  11. Injection: applications bind values through driver parameters; dynamic identifiers come from allowlists.
  12. Auditing: role/privilege/DDL changes and required data activity are retained in protected centralized logs.
  13. Secrets: passwords, LDAP bind credentials, keytabs, and private keys are managed outside source code.
  14. Lifecycle: PostgreSQL, drivers, TLS libraries, and security extensions are kept on supported releases.

20. Security review queries

20.1 Dangerous role attributes

SELECT
    rolname,
    rolsuper,
    rolcreaterole,
    rolcreatedb,
    rolreplication,
    rolbypassrls,
    rolcanlogin
FROM pg_roles
WHERE rolsuper
   OR rolcreaterole
   OR rolcreatedb
   OR rolreplication
   OR rolbypassrls
ORDER BY rolname;

20.2 Role membership graph

SELECT
    granted.rolname AS granted_role,
    member.rolname AS member_role,
    m.admin_option,
    m.inherit_option,
    m.set_option
FROM pg_auth_members AS m
JOIN pg_roles granted ON granted.oid = m.roleid
JOIN pg_roles member  ON member.oid  = m.member
ORDER BY granted_role, member_role;

20.3 Public schema privileges

SELECT
    n.nspname,
    has_schema_privilege('PUBLIC', n.oid, 'USAGE') AS public_usage,
    has_schema_privilege('PUBLIC', n.oid, 'CREATE') AS public_create
FROM pg_namespace AS n
WHERE n.nspname !~ '^pg_'
ORDER BY n.nspname;

20.4 Database privileges

SELECT
    datname,
    has_database_privilege('PUBLIC', datname, 'CONNECT') AS public_connect,
    has_database_privilege('PUBLIC', datname, 'TEMP') AS public_temp
FROM pg_database
WHERE datallowconn
ORDER BY datname;

20.5 Tables with RLS state

SELECT
    n.nspname AS schema_name,
    c.relname AS table_name,
    c.relrowsecurity AS rls_enabled,
    c.relforcerowsecurity AS rls_forced
FROM pg_class AS c
JOIN pg_namespace AS n ON n.oid = c.relnamespace
WHERE c.relkind IN ('r','p')
  AND n.nspname NOT IN ('pg_catalog','information_schema')
ORDER BY schema_name, table_name;

20.6 RLS policies

SELECT
    schemaname,
    tablename,
    policyname,
    permissive,
    roles,
    cmd,
    qual,
    with_check
FROM pg_policies
ORDER BY schemaname, tablename, policyname;

20.7 SECURITY DEFINER inventory

SELECT
    n.nspname AS schema_name,
    p.proname,
    pg_get_userbyid(p.proowner) AS owner,
    p.prosecdef AS security_definer,
    p.proconfig AS function_settings,
    pg_get_function_identity_arguments(p.oid) AS arguments
FROM pg_proc AS p
JOIN pg_namespace AS n ON n.oid = p.pronamespace
WHERE p.prosecdef
ORDER BY schema_name, p.proname;

20.8 HBA validation

SELECT
    line_number,
    type,
    database,
    user_name,
    address,
    auth_method,
    options,
    error
FROM pg_hba_file_rules
ORDER BY line_number;
Security principle: authenticate strongly, authorize minimally, encrypt and verify network identities, treat privileged code as a security boundary, parameterize application SQL, and continuously inspect the role/privilege graph rather than assuming it remains correct after deployment.
