PostgreSQL Full-Text Search

An expert-level guide to PostgreSQL’s native text-search pipeline: tokenization, lexemes, tsvector, tsquery, configurations, dictionaries, stemming, phrase and prefix search, ranking, highlighting, GIN/GiST indexing, generated search columns, multilingual designs, and production search applications.

Technical article • PostgreSQL 18.6 baseline • Updated 15 September 2026 • Vancouver-style references

Abstract

PostgreSQL includes a native full-text-search subsystem that converts natural-language documents into normalized searchable lexemes and user queries into Boolean/proximity query trees. The two central data types are tsvector, which represents a document as sorted lexemes with optional positions and weights, and tsquery, which represents a search expression. The match operator @@ evaluates whether a vector satisfies a query. Text-search configurations connect parsers to dictionaries so token normalization can reflect language-specific stemming, stop words, synonyms, thesauri, or custom rules.[1]-[4]

PostgreSQL also provides relevance functions (ts_rank, ts_rank_cd), query-to-snippet highlighting (ts_headline), document/query manipulation functions, and specialized GIN and GiST index operator classes. For conventional full-text document search, PostgreSQL identifies GIN as the preferred index type; GiST text-search indexes are lossy signature indexes and require row rechecks. A production search system therefore usually combines an explicit search configuration, a persistent or indexed document vector, a GIN index, a query-construction strategy suitable for user input, relevance ranking, and application-specific filters and business ranking signals.[5]-[8]

1. PostgreSQL full-text-search architecture

Full-text search is not substring search. PostgreSQL parses text into typed tokens, maps tokens through dictionaries into normalized lexemes, and stores those lexemes in a searchable vector. The same normalization pipeline is applied to user query terms. This lets language-aware search match related surface forms—for example, an English stemmer can normalize grammatical variants to a common stem—rather than requiring byte-for-byte equality between the document and query text.[1][3]

DOCUMENT "title + body" | v text-search parser | +--> token type: word / asciiword / url / email / ... | v configured dictionary chain | +--> lowercasing +--> stop-word removal +--> stemming +--> synonym/thesaurus mapping | v lexemes + positions + optional weights | v tsvector -------------------------+ \ \ @@ match \ USER QUERY v | tsquery v ^ plainto_tsquery / to_tsquery / | phraseto_tsquery / websearch_to_tsquery-+ | +--> same configuration/dictionaries Matched rows | +--> ts_rank / ts_rank_cd +--> application ranking factors +--> ts_headline on final result set

The selected text-search configuration is part of the semantics. A configuration chooses a parser and specifies which dictionaries are tried, in order, for each token type. PostgreSQL can host multiple configurations in one database, and callers can pass an explicit configuration to to_tsvector and query-construction functions rather than relying on the session's default_text_search_config.[9]

2. Documents, tokens, and lexemes

A text-search document can be a single text value or a structured combination of fields. PostgreSQL's parser divides a document into tokens and assigns token types such as ASCII word, word, host, URL, email, integer, floating-point number, and hyphenated-word forms. The configuration then maps each token type to one or more dictionaries. The first dictionary in that chain that recognizes a token determines the emitted lexeme or lexemes; a stop word can be recognized and intentionally emit nothing.[3][10] 

SELECT alias, description, token
FROM ts_debug(
    'english',
    'PostgreSQL 18 supports full-text search at docs.example.com.'
);

ts_debug exposes how a configuration parses and normalizes a sample document, including parser token types and dictionary decisions. It is one of the most useful tools for diagnosing “why did this word not match?” problems.[10]

2.1 Normalization changes the indexed representation

SELECT to_tsvector(
    'english',
    'The databases are searching documents efficiently'
);

The resulting vector does not necessarily contain the original words. English stop words can disappear and inflected words can be reduced by stemming. Full-text search therefore compares normalized lexical representations rather than the raw original text.[3]

3. tsvector

tsvector stores a sorted list of distinct lexemes. A lexeme can also carry one or more positional locations and one of four optional weight labels—A, B, C, or D. Positions enable phrase/proximity behavior and cover-density ranking; weights let an application distinguish structurally important fields such as a title from a body.[2][3]

3.1 Construct a vector

SELECT to_tsvector(
    'english',
    'PostgreSQL databases support database text searching.'
);

3.2 Match a vector

SELECT
    to_tsvector(
        'english',
        'PostgreSQL databases support database text searching.'
    )
    @@
    to_tsquery(
        'english',
        'database & search'
    ) AS matched;

3.3 Positional information

Positions encode where lexemes occur in the processed document and make phrase and proximity queries possible. PostgreSQL's strip(tsvector) function can remove positions and weights to reduce information, but stripped vectors cannot support the positional logic required by ts_rank_cd and lose information needed by some query restrictions.[11]

3.4 Concatenating vectors

SELECT
    to_tsvector('english', 'postgresql search')
    ||
    to_tsvector('english', 'index design');

The || operator combines two vectors and offsets positions in the right operand so positional information remains meaningful in the concatenated document.[11]

4. tsquery

tsquery represents a Boolean/proximity search expression over normalized lexemes. Its principal operators are & (AND), | (OR), ! (NOT), and phrase/proximity operators such as <-> (“followed immediately by”) and <N> (“followed at distance N”). Lexemes can also carry weight restrictions and prefix matching.[2][3]

4.1 Boolean queries

SELECT to_tsquery(
    'english',
    'postgres & (index | search) & !mysql'
);

4.2 Phrase query

SELECT to_tsquery(
    'english',
    'full <-> text <-> search'
);

4.3 Prefix query

SELECT to_tsquery(
    'english',
    'postgr:*'
);

The :* label changes a lexeme to prefix matching, so it can match lexemes beginning with the specified prefix. Prefix matching is lexical-prefix matching after query normalization; it is not arbitrary substring search inside words.[2]

4.4 Weight-restricted query

SELECT to_tsquery(
    'english',
    'postgres:A & search'
);

A query lexeme can be restricted to document lexemes carrying selected weights, such as only title-weight A occurrences. GIN full-text indexes do not store weight labels, so weight-restricted matches require row rechecks even when the GIN index identifies candidate rows.[5]

5. Query-building functions

PostgreSQL exposes several functions for turning user text into a tsquery. They differ primarily in how much query syntax they expect and how forgiving they are of arbitrary input.[3]

FunctionInput styleTypical use
to_tsqueryExplicit operators and valid tsquery syntaxAdvanced/programmatically generated search expressions.
plainto_tsqueryPlain textImplicit AND between normalized terms.
phraseto_tsqueryPlain phrase textTerms must occur in phrase order, accounting for stop words.
websearch_to_tsquerySearch-engine-like textHuman-facing search boxes with quotes, OR, and minus-style negation.

5.1 Plain text

SELECT plainto_tsquery(
    'english',
    'PostgreSQL full text search'
);

5.2 Phrase text

SELECT phraseto_tsquery(
    'english',
    'full text search'
);

5.3 Web-search syntax

SELECT websearch_to_tsquery(
    'english',
    '"full text search" OR postgres -mysql'
);

websearch_to_tsquery is designed for simplified web-search-like syntax and is deliberately more tolerant of raw user input than to_tsquery. It is often the best native front end for a human search box, while applications that need exact Boolean trees can build a tsquery more explicitly.[3]

SQL parameterization still matters. Query-builder functions make text-search syntax safer to accept, but the search string should still be sent to PostgreSQL as a bound SQL parameter rather than concatenated into SQL source.

6. Text-search configurations

A text-search configuration defines the complete token-to-lexeme pipeline: which parser breaks input into typed tokens and which ordered dictionary list handles each token type. The configuration is referenced by the catalog type regconfig. PostgreSQL ships predefined configurations for multiple languages and permits application-defined configurations.[9]

6.1 Inspect the default

SHOW default_text_search_config;

6.2 Make search semantics explicit

SELECT to_tsvector(
    'pg_catalog.english',
    body
)
FROM app.article;

Specifying a configuration explicitly is particularly important for indexes and generated search columns. It makes document normalization independent of per-session changes to default_text_search_config and gives the planner a stable expression that matches the indexed definition.[4]

6.3 Create a configuration from an existing one

CREATE TEXT SEARCH CONFIGURATION app.product_search (
    COPY = pg_catalog.english
);

6.4 Change token mappings

ALTER TEXT SEARCH CONFIGURATION app.product_search
ALTER MAPPING FOR
    asciiword,
    asciihword,
    hword_asciipart
WITH
    app.product_synonym,
    pg_catalog.english_stem;

Dictionary ordering is meaningful: PostgreSQL tries dictionaries in the order configured for the token type and stops when a dictionary recognizes the token. Specialized synonym or domain dictionaries therefore normally appear before a broad stemmer that recognizes nearly every word.[9][12]

7. Dictionaries

A text-search dictionary is responsible for recognizing a token and returning zero, one, or multiple normalized lexemes. Dictionaries are parameterized instances of dictionary templates. PostgreSQL ships templates for simple normalization, Snowball stemming, Ispell, synonyms, and thesauri, and extensions can supply additional templates.[12]-[14]

Dictionary/templatePurposeTypical position in chain
simpleLowercase; optionally eliminate stop wordsExact-ish normalized tokens or fallback.
snowballLanguage-specific stemming + optional stop wordsUsually late because it broadly recognizes words.
ispellMorphological dictionary based on affix/dictionary filesBefore broad fallback stemmers.
synonymReplace a word with configured synonymBefore stemmer when domain mapping is desired.
thesaurusPhrase-aware substitution using a subdictionaryFor domain-specific multiword concepts.

7.1 Test one dictionary

SELECT ts_lexize(
    'pg_catalog.english_stem',
    'databases'
);

7.2 Dictionary catalog

SELECT
    n.nspname AS schema_name,
    d.dictname,
    d.dictinitoption
FROM pg_ts_dict AS d
JOIN pg_namespace AS n
  ON n.oid = d.dictnamespace
ORDER BY schema_name, d.dictname;

The pg_ts_dict catalog records the dictionary, owner, template, schema, and template-specific initialization options. The implementation functions themselves are defined by the dictionary template.[15]

8. Stemming and stop words

Stemming reduces variant word forms to a language-specific stem. PostgreSQL's Snowball dictionary template is based on the Snowball stemming algorithms and is available for numerous languages. A Snowball dictionary can also use a stop-word list to eliminate high-frequency terms that are considered unhelpful for search.[12] 

SELECT to_tsvector(
    'english',
    'The searchable databases were searching database documents'
);

The key engineering consequence is that search semantics are linguistic rather than exact-text semantics. Stemming can intentionally increase recall, while stop words reduce index/query noise. However, both are domain-sensitive: a term considered common in ordinary prose might carry meaning in legal, medical, product-code, or source-code corpora.

8.1 Simple versus stemmed search

SELECT
    to_tsvector('simple',  'running runners ran') AS simple_vector,
    to_tsvector('english', 'running runners ran') AS english_vector;

The simple dictionary lowercases words and can apply stop words but does not perform language stemming. It is useful when preserving lexical forms is more important than matching morphological variants.[12]

8.2 Custom Snowball dictionary

CREATE TEXT SEARCH DICTIONARY app.english_domain (
    TEMPLATE = snowball,
    Language = english,
    StopWords = english
);

Dictionary options are template-specific. Custom stop-word files and synonym/thesaurus rule files are server-side text-search resources, so packaging and deployment of those files becomes part of the database deployment process.[14]

9. Synonyms and thesauri

A synonym dictionary maps one lexical form to another, while a thesaurus can recognize phrases and substitute normalized concepts. These are useful for domain vocabularies where different surface terms should match a shared concept—for example, “postgres” and “postgresql”, or a product abbreviation and its full name.[12]

9.1 Example synonym rule file

# postgres.syn (server-side dictionary file)
postgres     postgresql
pgsql        postgresql
dbms         database
CREATE TEXT SEARCH DICTIONARY app.product_synonym (
    TEMPLATE = synonym,
    SYNONYMS = postgres
);

CREATE TEXT SEARCH CONFIGURATION app.tech_search (
    COPY = pg_catalog.english
);

ALTER TEXT SEARCH CONFIGURATION app.tech_search
ALTER MAPPING FOR asciiword, word
WITH app.product_synonym, pg_catalog.english_stem;

9.2 Test the pipeline

SELECT *
FROM ts_debug(
    'app.tech_search',
    'Postgres is a DBMS'
);
Synonym policy changes search semantics. Treat dictionary files/configuration changes like application code: version them, test representative queries, deploy consistently across primary/standby nodes, and re-evaluate persisted vectors when normalization rules change.

10. Weighted structured documents

Most search documents are structured. A title match is often more important than a body match, while tags, author names, or product categories may fall between them. PostgreSQL lets applications label lexemes with weights A through D using setweight(), concatenate vectors, and supply corresponding numeric weights to ranking functions.[3] 

setweight(
    to_tsvector(
        'english',
        coalesce(title, '')
    ),
    'A'
)
||
setweight(
    to_tsvector(
        'english',
        coalesce(tags_text, '')
    ),
    'B'
)
||
setweight(
    to_tsvector(
        'english',
        coalesce(summary, '')
    ),
    'C'
)
||
setweight(
    to_tsvector(
        'english',
        coalesce(body, '')
    ),
    'D'
)

Using coalesce matters because to_tsvector(NULL) is null and PostgreSQL's vector concatenation would otherwise allow a nullable field to disrupt construction of the structured vector.[3]

10.1 Weight-aware query

SELECT *
FROM app.article
WHERE search_vector
      @@ to_tsquery(
             'english',
             'postgres:A | postgres'
         );

11. Ranking search results

The @@ operator answers whether a document matches a query; it does not define how matches should be ordered. PostgreSQL provides ts_rank, which primarily considers matching lexeme frequency and weights, and ts_rank_cd, which implements cover-density ranking and uses proximity information from lexeme positions. Relevance is application-specific, so built-in rank should often be combined with business signals such as recency, popularity, authority, tenancy, or product availability.[3]

11.1 Basic ranking

WITH q AS (
    SELECT websearch_to_tsquery(
        'english',
        $1
    ) AS query
)
SELECT
    a.article_id,
    a.title,
    ts_rank(
        a.search_vector,
        q.query
    ) AS rank
FROM app.article AS a
CROSS JOIN q
WHERE a.search_vector @@ q.query
ORDER BY rank DESC, a.article_id DESC
LIMIT 20;

11.2 Weight customisation

ts_rank(
    ARRAY[
        0.05,  -- D
        0.20,  -- C
        0.60,  -- B
        1.00   -- A
    ]::real[],
    a.search_vector,
    q.query
)

The weight array is ordered D, C, B, A. Custom values can make title/tag hits dominate body-only matches while retaining the same vector and query.[3]

11.3 Cover-density rank

SELECT
    article_id,
    title,
    ts_rank_cd(
        search_vector,
        websearch_to_tsquery('english', $1),
        32
    ) AS rank
FROM app.article
WHERE search_vector
      @@ websearch_to_tsquery('english', $1)
ORDER BY rank DESC
LIMIT 20;

ts_rank_cd uses positional proximity, so stripped vectors without positions cannot contribute to cover-density ranking. Normalization option 32 maps rank through rank/(rank+1), which bounds the value below 1 but does not create a globally calibrated relevance probability.[3]

11.4 Hybrid application ranking

WITH q AS (
    SELECT websearch_to_tsquery('english', $1) AS query
)
SELECT
    a.article_id,
    a.title,
    (
        ts_rank_cd(a.search_vector, q.query, 32) * 0.80
        +
        LEAST(a.popularity_score / 100.0, 1.0) * 0.15
        +
        exp(
            -EXTRACT(EPOCH FROM (now() - a.published_at))
            / 86400.0
            / 180.0
        ) * 0.05
    ) AS score
FROM app.article AS a
CROSS JOIN q
WHERE a.search_vector @@ q.query
ORDER BY score DESC
LIMIT 20;

PostgreSQL explicitly notes that relevance is vague and application-specific and that its built-in ranking functions do not use corpus-wide information. Combining lexical rank with domain signals is therefore a normal application-layer design rather than a workaround.[3]

12. Highlighting with ts_headline

ts_headline returns an excerpt from the original document with query terms marked. It supports controls for fragment count, fragment length, delimiters, and start/stop markers. It operates on the original document text, not just the vector, so it can be relatively expensive and is normally best applied only to the small final page of results.[3] 

WITH q AS (
    SELECT websearch_to_tsquery(
        'english',
        $1
    ) AS query
)
SELECT
    a.article_id,
    a.title,
    ts_headline(
        'english',
        a.body,
        q.query,
        'StartSel=<mark>, StopSel=</mark>,
         MaxFragments=2, MinWords=8, MaxWords=24,
         FragmentDelimiter= … '
    ) AS snippet
FROM app.article AS a
CROSS JOIN q
WHERE a.search_vector @@ q.query
ORDER BY ts_rank_cd(a.search_vector, q.query) DESC
LIMIT 20;
ts_headline is not an HTML sanitizer. PostgreSQL warns that its output is not guaranteed safe for direct insertion into a web page when the source text is untrusted. Strip unsafe markup before search or sanitize/escape the final rendered output according to the application's HTML policy.[3]

12.1 Rank first, headline second

WITH
q AS (
    SELECT websearch_to_tsquery('english', $1) AS query
),
top_hits AS (
    SELECT
        a.article_id,
        a.title,
        a.body,
        ts_rank_cd(a.search_vector, q.query) AS rank,
        q.query
    FROM app.article AS a
    CROSS JOIN q
    WHERE a.search_vector @@ q.query
    ORDER BY rank DESC
    LIMIT 20
)
SELECT
    article_id,
    title,
    rank,
    ts_headline(
        'english',
        body,
        query,
        'StartSel=<mark>, StopSel=</mark>, MaxFragments=2'
    ) AS snippet
FROM top_hits
ORDER BY rank DESC;

This shape avoids generating snippets for every candidate match before the top result page is known.

13. GIN indexes

GIN—Generalized Inverted Index—is designed for composite values whose component keys need to be searched independently. For full-text search, the indexed keys are document lexemes and the posting lists identify rows containing each lexeme. PostgreSQL identifies GIN as the preferred text-search index type in ordinary full-text workloads.[5][6]

13.1 Basic GIN index

CREATE INDEX article_search_gin
ON app.article
USING GIN (search_vector);

13.2 Expression GIN index

CREATE INDEX article_body_search_gin
ON app.article
USING GIN (
    to_tsvector(
        'english',
        body
    )
);

When indexing to_tsvector as an expression, use the two-argument version with an explicit configuration. A query must use a compatible expression/configuration for PostgreSQL to match it to the index.[4]

13.3 Query using the expression index

SELECT
    article_id,
    title
FROM app.article
WHERE to_tsvector('english', body)
      @@ websearch_to_tsquery('english', $1);

13.4 GIN write behavior

One row's vector typically contains many lexemes, so inserting one table row can create many index-key insertions. GIN supports a pending-list mechanism controlled by the fastupdate storage parameter and maintenance thresholds such as gin_pending_list_limit. This improves many write workloads by batching index maintenance, but pending-list growth and cleanup can create latency patterns worth monitoring on heavily updated search tables.[6] 

ALTER INDEX app.article_search_gin
SET (fastupdate = on);

ALTER INDEX app.article_search_gin
SET (gin_pending_list_limit = 8388608);

The numerical setting above is an example, not a universal recommendation. GIN tuning depends on write rate, autovacuum behavior, query latency objectives, available memory, and index size.

13.5 PostgreSQL 18 index builds

PostgreSQL 18 added support for parallel GIN index creation. This can reduce build time where the planner/build process can use parallel workers and sufficient CPU/I/O capacity is available.[16]

14. GiST indexes

GiST—Generalized Search Tree—is an extensible balanced-tree framework supporting many operator classes, including text-search operator classes. A full-text GiST vector index stores a fixed-length signature rather than every lexeme/posting list exactly. The signature can produce false positive candidates, so the heap row must be rechecked. PostgreSQL performs these rechecks automatically.[5][7] 

CREATE INDEX article_search_gist
ON app.article
USING GIST (search_vector);

14.1 Signature length

CREATE INDEX article_search_gist_256
ON app.article
USING GIST (
    search_vector tsvector_ops(siglen=256)
);

Increasing the GiST text-search signature length can reduce false matches at the cost of a larger index. GIN is generally preferred when the primary workload is full-text matching; GiST becomes interesting when its size/update behavior or broader GiST ecosystem fits the application better.[5]

15. Schema patterns for search vectors

15.1 Stored generated tsvector column

For a document derived entirely from fields in the same row under a fixed configuration, a stored generated column is often the cleanest design. PostgreSQL's text-search documentation recommends generated columns over the older built-in tsvector_update_trigger approach for automatically maintained search vectors.[11][17] 

CREATE TABLE app.article (
    article_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title text NOT NULL,
    summary text,
    body text NOT NULL,
    published_at timestamptz NOT NULL DEFAULT now(),

    search_vector tsvector
    GENERATED ALWAYS AS (
        setweight(
            to_tsvector(
                'english',
                coalesce(title, '')
            ),
            'A'
        )
        ||
        setweight(
            to_tsvector(
                'english',
                coalesce(summary, '')
            ),
            'B'
        )
        ||
        setweight(
            to_tsvector(
                'english',
                coalesce(body, '')
            ),
            'D'
        )
    ) STORED
);

CREATE INDEX article_search_vector_gin
ON app.article
USING GIN (search_vector);

Generated expressions must use immutable functions and may refer only to the current row rather than querying other tables. A stored generated column is recomputed when the row changes and occupies storage. These restrictions fit fixed-configuration to_tsvector(regconfig,text) pipelines well.[17]

15.2 Expression index

CREATE INDEX article_body_search_gin
ON app.article
USING GIN (
    to_tsvector(
        'english',
        coalesce(body, '')
    )
);

An expression index avoids storing a visible vector column, but queries and ranking logic often become more repetitive because the vector expression must be reproduced. A stored vector is usually convenient when the application needs weighting, ranking, inspection, and many repeated searches.

15.3 Trigger-maintained vector

PostgreSQL still provides tsvector_update_trigger and tsvector_update_trigger_column for cases that need trigger-based maintenance, including a configuration name stored in another column. PostgreSQL 18's documentation describes the basic trigger approach as obsoleted for straightforward cases by stored generated columns.[11] 

CREATE TABLE app.localized_document (
    document_id bigint PRIMARY KEY,
    search_config regconfig NOT NULL,
    title text,
    body text,
    search_vector tsvector
);

CREATE TRIGGER localized_document_tsv
BEFORE INSERT OR UPDATE
ON app.localized_document
FOR EACH ROW
EXECUTE FUNCTION tsvector_update_trigger_column(
    search_vector,
    search_config,
    title,
    body
);

16. Production search-query patterns

16.1 Filter first-class business dimensions with ordinary columns

WITH q AS (
    SELECT websearch_to_tsquery(
        'english',
        $1
    ) AS query
)
SELECT
    p.product_id,
    p.name,
    p.price,
    ts_rank_cd(
        p.search_vector,
        q.query,
        32
    ) AS relevance
FROM catalog.product AS p
CROSS JOIN q
WHERE p.store_id = $2
  AND p.active
  AND p.search_vector @@ q.query
ORDER BY relevance DESC, p.product_id
LIMIT $3;

Full-text search should complement ordinary relational filtering, not replace it. Tenant IDs, availability, dates, prices, permissions, workflow state, and other exact attributes belong in typed columns and ordinary predicates. PostgreSQL's planner can combine the text-search index with other indexes through bitmap operations when advantageous.

16.2 Phrase search

SELECT *
FROM app.article
WHERE search_vector
      @@ phraseto_tsquery(
             'english',
             $1
         );

16.3 Explicit proximity

SELECT *
FROM app.article
WHERE search_vector
      @@ to_tsquery(
             'english',
             'postgres <3> indexing'
         );

16.4 Prefix-autocomplete style query

SELECT
    product_id,
    name
FROM catalog.product
WHERE search_vector
      @@ to_tsquery(
             'simple',
             $1 || ':*'
         )
LIMIT 20;

If prefix text comes from a user, construct the tsquery carefully. Arbitrarily appending text into to_tsquery syntax can produce syntax errors or unintended operators. Applications often normalize/validate a single lexical prefix or construct queries with explicit query-combination functions rather than accepting raw advanced syntax.

16.5 Build a query with operators

SELECT
    plainto_tsquery('english', $1)
    &&
    to_tsquery('english', $2 || ':*');

PostgreSQL supplies operators and functions for combining existing tsquery values, which can be safer and clearer than generating one large textual query expression.[11]

17. Multilingual search

Language-specific stemming requires a language-appropriate configuration. A corpus containing multiple languages should not blindly run all documents through one English stemmer. Designs include partitioning/searching by language, storing a regconfig alongside each document and maintaining its vector with a trigger, or maintaining separate language-specific searchable fields.[9][11]

17.1 Configuration per row

CREATE TABLE app.document (
    document_id bigint PRIMARY KEY,
    language_code text NOT NULL,
    search_config regconfig NOT NULL,
    title text NOT NULL,
    body text NOT NULL,
    search_vector tsvector
);
INSERT INTO app.document(
    document_id,
    language_code,
    search_config,
    title,
    body
)
VALUES
    (1, 'en', 'pg_catalog.english', 'Database indexing', '...'),
    (2, 'es', 'pg_catalog.spanish', 'Índices de bases de datos', '...');

17.2 Search with matching language

SELECT
    document_id,
    title
FROM app.document
WHERE language_code = $1
  AND search_vector
      @@ websearch_to_tsquery(
             search_config,
             $2
         );

This design avoids comparing a query normalized under one language to vectors normalized under an incompatible language. It also makes the selected linguistic policy explicit in the row schema.

18. Architecture of a search application

Browser / API client | | query="postgres indexing" v Application | +--> validate tenant/filter parameters +--> bind search text as SQL parameter | v PostgreSQL | +--> websearch_to_tsquery(config, $query) | +--> GIN candidate lookup with @@ | +--> relational filters: | tenant / permissions / state / date / category | +--> ts_rank_cd + business-ranking signals | +--> LIMIT top N | +--> ts_headline only for final N | v Search results title + metadata + sanitized snippet + score

18.1 Example API query

WITH
q AS (
    SELECT websearch_to_tsquery(
        'english',
        $1
    ) AS query
),
ranked AS (
    SELECT
        a.article_id,
        a.title,
        a.summary,
        a.body,
        a.published_at,
        q.query,
        ts_rank_cd(
            a.search_vector,
            q.query,
            32
        ) AS lexical_score
    FROM app.article AS a
    CROSS JOIN q
    WHERE a.tenant_id = $2
      AND a.published
      AND a.search_vector @@ q.query
    ORDER BY
        lexical_score DESC,
        a.published_at DESC,
        a.article_id DESC
    LIMIT $3
)
SELECT
    article_id,
    title,
    published_at,
    lexical_score,
    ts_headline(
        'english',
        body,
        query,
        'StartSel=<mark>, StopSel=</mark>,
         MaxFragments=2, MinWords=6, MaxWords=22'
    ) AS snippet
FROM ranked
ORDER BY
    lexical_score DESC,
    published_at DESC,
    article_id DESC;

18.2 Stable pagination

Search relevance scores can tie and can change as document data changes. Add deterministic secondary keys such as publication time and primary key. For deep result sets, keyset-style pagination is often preferable to large OFFSET values, but keyset predicates must include all ordering keys used by the ranking query.

18.3 Security and tenancy

Do not search globally and filter sensitive rows in application memory. Permission and tenant predicates should be enforced in the SQL query—and, where appropriate, reinforced with PostgreSQL row-level security—so unauthorized documents are never returned from the database search.[18]

19. Performance engineering

19.1 Avoid recomputing vectors for every row at query time

-- Functional but potentially expensive on a large table without
-- a matching expression index:
WHERE to_tsvector('english', title || ' ' || body)
      @@ websearch_to_tsquery('english', $1)

A stored vector plus GIN index, or an exactly matching expression index, moves document parsing out of the hot read path and provides an indexable search representation.[4]

19.2 Explain the search plan

EXPLAIN (
    ANALYZE,
    BUFFERS
)
SELECT
    article_id,
    title
FROM app.article
WHERE search_vector
      @@ websearch_to_tsquery(
             'english',
             'postgres indexing'
         );

Use EXPLAIN (ANALYZE, BUFFERS) to verify that the intended text-search index is actually used and to quantify candidate rows, rechecks, heap access, and buffer traffic. Plan choice remains cost-based; an index is not necessarily chosen when a query matches a very large fraction of the table.[19]

19.3 Ranking can dominate after matching

A GIN index can find matching candidate rows efficiently, but sorting a huge match set by ts_rank still requires computing rank over those candidates and finding the top results. Narrow relational filters, selective queries, reasonable result limits, and application search syntax that discourages extremely broad queries can matter as much as index lookup latency.

19.4 Headline generation comes last

Because ts_headline reparses the original document and can be relatively expensive, generate it after candidate filtering, ranking, and limiting rather than for every match.[3]

19.5 Monitor GIN write costs

Search indexes increase write amplification because document changes require lexeme-index maintenance. Monitor table/index size, autovacuum, WAL, I/O, and query latency. On write-heavy systems, inspect GIN pending-list behavior and test whether default fastupdate behavior fits the workload.[6]

19.6 Statistics for vocabulary exploration

PostgreSQL's ts_stat function gathers statistics about lexemes contained in tsvector results. It can help inspect vocabulary frequency, diagnose corpus quality, and identify terms that dominate a search collection.[11] 

SELECT *
FROM ts_stat(
    'SELECT search_vector
     FROM app.article'
)
ORDER BY nentry DESC
LIMIT 50;

20.5 Regression-test search semantics

-- Example assertions to keep in migration/application tests:
SELECT
    to_tsvector('app.tech_search', 'Postgres indexing')
    @@ plainto_tsquery('app.tech_search', 'PostgreSQL index')
    AS expected_match;

SELECT
    to_tsvector('english', 'full text search')
    @@ phraseto_tsquery('english', 'full text search')
    AS expected_phrase_match;

Search behavior can change intentionally when dictionary rules, stop-word files, configuration mappings, or source text change. Treat representative query/document pairs as regression fixtures so search-semantic changes are visible before deployment.

21. Limitations and complementary techniques

21.1 Full-text search is not typo tolerance

Stemming handles morphological variation, but native full-text search does not inherently turn a misspelling into the intended lexeme. PostgreSQL's pg_trgm extension provides trigram similarity and GIN/GiST indexing for fuzzy string matching and can complement full-text search for spelling suggestions, names, identifiers, or partial-string behavior.[21]

21.2 Ranking is not corpus-trained relevance

ts_rank and ts_rank_cd do not use global corpus statistics such as inverse document frequency. PostgreSQL explicitly describes relevance as application-specific and encourages custom ranking logic when built-in lexical/proximity ranking is insufficient.[3]

21.3 Search configuration is linguistic policy

A stemmer, stop-word list, synonym map, or thesaurus can create false positives or false negatives in specialized domains. Search quality engineering should measure relevance on representative queries, not only index performance.

21.4 Full-text search is not semantic vector search

Native text search matches normalized lexical concepts encoded by dictionaries and query operators. Embedding/vector similarity solves a different problem: numerical semantic-neighborhood search. Applications can use both approaches, but they should not be treated as interchangeable.

21.5 Very large search products may need specialized engines

PostgreSQL full-text search is attractive when search must stay transactionally close to relational data, permissions, filters, and application writes. Dedicated search engines can provide additional distributed indexing, analyzers, faceting, typo correction, relevance-learning, and operational scaling features. The decision is architectural: compare required search semantics and scale against the value of keeping search inside PostgreSQL.

22. Production checklist

  1. Choose a configuration deliberately. Do not rely accidentally on whatever default_text_search_config happens to be.
  2. Test tokenization and dictionaries. Use ts_debug for representative domain text.
  3. Choose query syntax for the user interface. websearch_to_tsquery is often appropriate for human-facing search boxes.
  4. Bind search strings as SQL parameters. Do not build SQL statements by string concatenation.
  5. Persist or index the document vector. Avoid full-table reparsing in the read path.
  6. Prefer GIN for conventional full-text matching. Use GiST only with a clear workload reason.
  7. Weight fields intentionally. Titles, tags, summaries, and bodies normally have different relevance.
  8. Separate lexical matching from business ranking. Add recency/popularity/authority explicitly.
  9. Generate headlines only for final results. Sanitize/escape output before HTML rendering.
  10. Keep exact filters relational. Tenant, state, price, date, permissions, and IDs are not text-search concerns.
  11. Plan for multilingual data. Use language-appropriate configurations and query normalization.
  12. Version dictionaries/configurations. Changes can alter both indexed vectors and query behavior.
  13. Benchmark write cost. GIN indexes increase index maintenance and WAL.
  14. Measure broad-query behavior. Index lookup can be fast while ranking/sorting huge match sets is expensive.
  15. Regression-test relevance. Keep known document/query/expected-result fixtures alongside application tests.
Search-design principle: PostgreSQL full-text search works best when lexical normalization, indexing, ranking, and relational filtering are treated as one query-planning problem. Build a stable document representation, use the same configuration for documents and queries, let GIN narrow candidates, then spend expensive ranking and highlighting work only on the rows that matter.
