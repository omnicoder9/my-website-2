PostgreSQL JSON & Semi-Structured Data

An expert guide to json, jsonb, JSON operators, SQL/JSON path, nested documents, containment, GIN indexing, expression indexes, document mutation, JSON-to-relational projection, hybrid schema design, and deciding when JSONB should—or should not—replace normalized tables.

Technical article • PostgreSQL 18.6 baseline • Updated 15 September 2026 • Vancouver-style references

Abstract

PostgreSQL treats JSON as a first-class part of the relational database rather than as a separate storage engine. It provides two principal JSON storage types: json, which preserves the original JSON text, and jsonb, which stores a parsed binary representation designed for efficient processing and indexing. PostgreSQL also implements SQL/JSON facilities, a jsonpath type, JSON construction and decomposition functions, SQL/JSON query functions, and JSON_TABLE for projecting nested JSON data into relational rows and columns.[1][2]

For most application data that must be queried, filtered, updated, or indexed, PostgreSQL recommends jsonb. The trade-off is semantic: jsonb normalizes the representation, discarding insignificant whitespace, object-key ordering, and duplicate keys, while json preserves the original textual form. jsonb adds containment/existence operators and GIN index support, enabling document-oriented access patterns while retaining PostgreSQL transactions, joins, constraints, row security, and ordinary relational indexes.[1][3]

The strongest PostgreSQL schemas usually do not choose between “relational” and “JSON” globally. Instead, they normalize stable identifiers, relationships, constraints, and frequently queried scalar dimensions while using JSONB for attributes whose keys genuinely vary by entity, source, or version. PostgreSQL's own design guidance recommends keeping JSON documents reasonably structured and notes that large JSON documents remain subject to row-level concurrency: changing any part of a document updates and locks the containing row.[1]

1. Semi-structured data in PostgreSQL

Relational tables describe a stable schema through typed columns, keys, constraints, and relationships. Semi-structured data instead carries some of its schema inside each value: one document may contain optional keys, nested arrays, variable objects, or source-specific properties that another document omits. PostgreSQL supports both models in the same transaction and query plan. JSON values can be joined to relational tables, filtered with ordinary predicates, converted to records, aggregated into JSON responses, protected by row-level security, and indexed using both scalar and GIN strategies.[1][2]

PostgreSQL row +-----------------------------------------------------------+ | product_id bigint <- relational primary key | | tenant_id bigint <- relational security/filter | | sku text <- relational uniqueness | | name text <- stable searchable scalar | | price numeric <- typed/range queries | | attributes jsonb <- variable product attributes | +-----------------------------------------------------------+ | | | B-tree / constraints | GIN / JSON path v v relational query model document query model \ / +-------- JOIN ----------+ | v one SQL query

This coexistence is central to effective PostgreSQL JSON design. JSONB is not an escape from relational modeling; it is another data type with specialized operators and indexes. The design question is therefore usually which fields belong in JSON, not whether the entire application should be “relational” or “document-oriented.”[1]

2. json versus jsonb

Both json and jsonb validate JSON input, but they store it differently. json stores an exact copy of the input text and must reparse that text for processing operations. jsonb parses input into a decomposed binary representation, making insertion somewhat more expensive but processing substantially faster and enabling indexing.[1]

Object-key order preservationYesNo
Duplicate object keysPreserved in stored textOnly the last value is retained

Containment/existence operatorsNo JSONB-style containment familyYes
GIN indexingNo native JSON GIN opclassYes
Typical application choiceExact textual preservation/interchangeQueryable application documents

2.1 Representation differences

SELECT
    '{"b": 2, "a": 1, "a": 3}'::json  AS as_json,
    '{"b": 2, "a": 1, "a": 3}'::jsonb AS as_jsonb;

The json value preserves the source ordering and duplicate keys. The jsonb value canonicalizes the object representation and keeps only the last value for duplicate keys. Applications that depend on exact serialization, duplicate-key retention, or original key order should not silently change that payload to jsonb.[1]

2.2 JSON null is not SQL NULL

SELECT
    NULL::jsonb             AS sql_null,
    'null'::jsonb           AS json_null,
    '{"x": null}'::jsonb    AS object_with_json_null;

SQL NULL represents absence/unknown at the SQL value level. JSON null is a JSON scalar stored inside a JSON value. Confusing them can produce subtle API and filtering bugs.[1]

Default choice: use jsonb when the database needs to query or index the contents. Use json when preserving the exact incoming JSON representation is itself a requirement.

3. Constructing JSON safely

PostgreSQL provides JSON constructors that convert typed SQL values into correctly escaped JSON values. Prefer these functions to hand-concatenating JSON strings. to_jsonb recursively converts SQL arrays and composite rows, while jsonb_build_object and jsonb_build_array build objects and arrays from SQL expressions.[2]

3.1 Build an object

SELECT jsonb_build_object(
    'product_id', 42,
    'name', 'Mechanical Keyboard',
    'price', 129.99,
    'active', true,
    'tags', jsonb_build_array('keyboard', 'usb-c', 'wireless')
);

3.2 Convert a row

SELECT to_jsonb(p)
FROM catalog.product AS p
WHERE p.product_id = 42;

3.3 Aggregate relational rows into JSON

SELECT jsonb_build_object(
    'customer_id', c.customer_id,
    'name', c.display_name,
    'orders',
        COALESCE(
            jsonb_agg(
                jsonb_build_object(
                    'order_id', o.order_id,
                    'total', o.total,
                    'created_at', o.created_at
                )
                ORDER BY o.created_at DESC
            ) FILTER (WHERE o.order_id IS NOT NULL),
            '[]'::jsonb
        )
)
FROM app.customer AS c
LEFT JOIN app.orders AS o
  ON o.customer_id = c.customer_id
WHERE c.customer_id = $1
GROUP BY c.customer_id, c.display_name;

JSON aggregation is often an excellent API-output pattern: the database keeps normalized relational storage but returns a nested response shape. PostgreSQL provides json_agg/jsonb_agg and object aggregates specifically for this purpose.[2][4]

3.4 SQL/JSON constructors

SELECT json_object(
    'code' VALUE 'P-100',
    'active' VALUE true,
    'description' VALUE NULL
    ABSENT ON NULL
    RETURNING jsonb
);

PostgreSQL 18 implements SQL/JSON constructors that support options such as ABSENT ON NULL, uniqueness rules for object keys, and explicit return types.[2]

4. JSON extraction and operators

The extraction operators -> and #> preserve JSON/JSONB values, while ->> and #>> convert the extracted value to SQL text. Array indexes are zero-based for JSON access, and negative indexes count from the end. If the requested path does not match the structure, extraction operators return SQL NULL instead of raising an error.[2]

4.1 Sample document

{
  "name": "Workstation",
  "manufacturer": {
    "name": "Acme",
    "country": "US"
  },
  "dimensions": {
    "width_mm": 420,
    "height_mm": 460
  },
  "tags": ["computer", "workstation", "linux"],
  "variants": [
    {"sku": "WS-32", "ram_gb": 32, "price": 1899.00},
    {"sku": "WS-64", "ram_gb": 64, "price": 2299.00}
  ]
}

4.2 Extract JSON values

SELECT
    attributes -> 'manufacturer' AS manufacturer_object,
    attributes -> 'tags'         AS tags_array,
    attributes -> 'variants' -> 0 AS first_variant
FROM catalog.product;

4.3 Extract SQL text

SELECT
    attributes ->> 'name' AS name,
    attributes #>> '{manufacturer,country}' AS country,
    attributes #>> '{variants,0,sku}' AS first_sku
FROM catalog.product;

4.4 Cast after extraction

SELECT *
FROM catalog.product
WHERE (attributes #>> '{dimensions,width_mm}')::integer >= 400;

Because ->>/#>> return text, numeric/date semantics require an explicit cast. If that field is frequently filtered or joined, moving it to a typed relational/generated column can improve validation, statistics, and indexing clarity.

5. Modeling nested documents

PostgreSQL allows JSON arrays and objects to nest arbitrarily. The important modeling question is whether the nested element is an inseparable part of one atomic datum or an independently identifiable entity that should participate in relational constraints and concurrent updates. PostgreSQL's documentation explicitly recommends keeping JSON documents to a manageable size and treating a JSON document as an atomic datum where possible because an update locks the whole containing row.[1]

5.1 Good nested use case: immutable source payload

CREATE TABLE integrations.webhook_event (
    event_id uuid PRIMARY KEY,
    source text NOT NULL,
    event_type text NOT NULL,
    received_at timestamptz NOT NULL DEFAULT now(),
    payload jsonb NOT NULL
);

Third-party webhook payloads naturally vary by event version and provider and often need to be preserved as one source record. Stable routing fields such as source, event_type, and received_at remain relational for filtering and operational queries.

5.2 Risky nested use case: independent child entities

-- Tempting, but usually problematic if line items are independently
-- updated, constrained, referenced, or aggregated:
{
  "order_id": 123,
  "items": [
    {"product_id": 10, "quantity": 2, "unit_price": 12.50},
    {"product_id": 11, "quantity": 1, "unit_price": 99.00}
  ]
}

If each line needs a foreign key to a product, independent updates, per-line uniqueness, reporting, or joins, an order_item table usually provides stronger guarantees and better statistics than embedding the lines in JSONB.

6. Updating JSONB documents

Because jsonb is a value, JSON update operations conceptually produce a new JSONB value for the column. PostgreSQL provides concatenation/deletion operators, jsonb_set, jsonb_set_lax, jsonb_insert, and subscripting assignment for targeted document changes.[2][1]

6.1 Replace or add a nested value

UPDATE catalog.product
SET attributes = jsonb_set(
    attributes,
    '{manufacturer,country}',
    to_jsonb('CA'::text),
    true
)
WHERE product_id = 42;

jsonb_set replaces the target path and, by default, creates the final item when it is missing. Earlier path steps must already exist; otherwise the target value is returned unchanged.[2]

6.2 Subscript assignment

UPDATE catalog.product
SET attributes['dimensions']['width_mm'] = '440'::jsonb
WHERE product_id = 42;

JSONB subscripting can create missing intermediate object/array structures where traversal is possible. If an existing intermediate value is a scalar that cannot be traversed, PostgreSQL raises an error.[1]

6.3 Delete a top-level key

UPDATE catalog.product
SET attributes = attributes - 'legacy_code'
WHERE product_id = 42;

6.4 Delete a nested path

UPDATE catalog.product
SET attributes = attributes #- '{manufacturer,legacy_id}'
WHERE product_id = 42;

6.5 Merge is top-level, not recursive

SELECT
    '{"a": {"x": 1}, "b": 2}'::jsonb
    ||
    '{"a": {"y": 3}}'::jsonb;

The || operator merges only at the top level; it does not recursively merge nested objects. When duplicate object keys occur, the right operand wins.[2]

7. JSONB containment and existence

Containment is one of the defining advantages of jsonb. A @> B asks whether JSONB value A contains JSONB value B according to PostgreSQL's structural containment rules. Object containment matches key/value subsets recursively; array containment ignores array order and duplicate elements for containment purposes. The related ?, ?|, and ?& operators test top-level keys or string array elements.[1][2]

7.1 Object containment

SELECT *
FROM catalog.product
WHERE attributes @> '{
  "manufacturer": {
    "country": "US"
  }
}'::jsonb;

7.2 Array containment

SELECT *
FROM catalog.product
WHERE attributes @> '{
  "tags": ["linux", "workstation"]
}'::jsonb;

7.3 Top-level key existence

SELECT *
FROM catalog.product
WHERE attributes ? 'warranty';

7.4 Any/all top-level keys

SELECT *
FROM catalog.product
WHERE attributes ?| ARRAY['warranty', 'dimensions'];

SELECT *
FROM catalog.product
WHERE attributes ?& ARRAY['manufacturer', 'tags'];
Containment is structural; existence is top-level. The ? operator does not recursively search nested objects. Use containment, extraction, an expression index, or JSON path for nested conditions.[1]

8. SQL/JSON path and the jsonpath type

PostgreSQL's jsonpath type stores parsed SQL/JSON path expressions. Path expressions navigate nested structures using member access (.), array access ([]), wildcards, filters, variables, predicates, methods, and arithmetic. JSON path array indexes are zero-based.[1][2]

8.1 Find nested variants by numeric condition

SELECT *
FROM catalog.product
WHERE attributes @? '$.variants[*] ? (@.ram_gb >= 64)';

8.2 Boolean predicate with @@

SELECT *
FROM catalog.product
WHERE attributes @@ '$.dimensions.width_mm >= 400';

@? asks whether a SQL-standard path expression returns any item. @@ evaluates a predicate-check expression and expects a single Boolean-like result. Both operators suppress several structural/type/numeric errors by design, which makes them useful across heterogeneous document collections.[2]

8.3 Variables instead of string-building

SELECT jsonb_path_query(
    attributes,
    '$.variants[*] ? (@.price >= $min && @.price <= $max)',
    jsonb_build_object(
        'min', to_jsonb($1::numeric),
        'max', to_jsonb($2::numeric)
    )
)
FROM catalog.product;

Passing path variables separately avoids embedding application values into the path expression text and makes dynamic filters easier to reason about.[2]

8.4 Lax versus strict mode

SELECT jsonb_path_query(
    '{"groups":[{"values":[1,2]},{"values":[3,4]}]}'::jsonb,
    'lax $.groups.values'
);

SELECT jsonb_path_query(
    '{"groups":[{"values":[1,2]},{"values":[3,4]}]}'::jsonb,
    'strict $.groups[*].values'
);

Lax mode can automatically unwrap arrays and adapt some structural mismatches, while strict mode requires the path to match structure explicitly. PostgreSQL warns that automatic unwrapping can produce surprising results in some paths—particularly recursive descent—so strict mode is valuable when exact document shape matters.[2]

9. SQL/JSON query functions

PostgreSQL implements SQL/JSON facilities for querying JSON values with explicit behavior for empty/error cases, wrappers, and return types. These complement PostgreSQL-specific functions such as jsonb_path_query and operators such as @?/@@.[2]

9.1 Path query family

SELECT jsonb_path_query(
    '{"a":[1,2,3,4,5]}'::jsonb,
    '$.a[*] ? (@ >= $min && @ <= $max)',
    '{"min":2,"max":4}'::jsonb
);

SELECT jsonb_path_query_array(
    '{"a":[1,2,3,4,5]}'::jsonb,
    '$.a[*] ? (@ >= 2)'
);

SELECT jsonb_path_query_first(
    '{"a":[1,2,3]}'::jsonb,
    '$.a[*] ? (@ > 1)'
);

9.2 Test input JSON text

SELECT
    payload_text IS JSON AS is_json,
    payload_text IS JSON OBJECT AS is_object,
    payload_text IS JSON WITH UNIQUE KEYS AS unique_keys
FROM staging.ingest;

The SQL/JSON IS JSON predicate can validate generic text/byte input and optionally test whether the value is a scalar, object, or array and whether object keys are unique.[2]

10. JSON_TABLE: project documents into relational rows

JSON_TABLE is an SQL/JSON facility that turns JSON data into a relational table expression. A row path selects source items, the COLUMNS clause assigns typed SQL columns, and NESTED PATH can expand nested arrays. PostgreSQL permits JSON_TABLE in the FROM clause of SELECT, UPDATE, and DELETE, and as a source for MERGE.[5]

10.1 Flatten product variants

SELECT
    p.product_id,
    jt.variant_no,
    jt.sku,
    jt.ram_gb,
    jt.price
FROM catalog.product AS p,
JSON_TABLE(
    p.attributes,
    '$.variants[*]'
    COLUMNS (
        variant_no FOR ORDINALITY,
        sku text PATH '$.sku',
        ram_gb integer PATH '$.ram_gb',
        price numeric(12,2) PATH '$.price'
    )
) AS jt;

10.2 Nested projection

SELECT
    e.event_id,
    jt.order_no,
    jt.line_no,
    jt.sku,
    jt.quantity
FROM integrations.webhook_event AS e,
JSON_TABLE(
    e.payload,
    '$.orders[*]'
    COLUMNS (
        order_no text PATH '$.orderNumber',
        NESTED PATH '$.lines[*]'
        COLUMNS (
            line_no FOR ORDINALITY,
            sku text PATH '$.sku',
            quantity integer PATH '$.quantity'
        )
    )
) AS jt
WHERE e.event_type = 'batch.orders';

This is particularly useful for ETL/staging workflows: ingest a source payload as JSONB, project it into typed rows, validate it, then load stable application entities into normalized tables.[5]

11. Expanding arrays and objects

PostgreSQL also provides set-returning functions for decomposing documents. jsonb_array_elements expands a top-level array, jsonb_each expands an object into key/value rows, and record-population functions map objects into existing PostgreSQL composite types.[2]

11.1 Array elements with LATERAL

SELECT
    p.product_id,
    v.variant ->> 'sku' AS sku,
    (v.variant ->> 'price')::numeric AS price
FROM catalog.product AS p
CROSS JOIN LATERAL
    jsonb_array_elements(
        p.attributes -> 'variants'
    ) AS v(variant);

11.2 Object key/value expansion

SELECT
    p.product_id,
    kv.key,
    kv.value
FROM catalog.product AS p
CROSS JOIN LATERAL
    jsonb_each(
        p.attributes -> 'specifications'
    ) AS kv(key, value);

11.3 Populate a typed record

CREATE TYPE staging.variant_input AS (
    sku text,
    ram_gb integer,
    price numeric(12,2)
);

SELECT *
FROM jsonb_populate_record(
    NULL::staging.variant_input,
    '{"sku":"WS-64","ram_gb":64,"price":2299}'::jsonb
);

Typed projection is useful because PostgreSQL conversion then enforces the target SQL type. PostgreSQL 18 also exposes jsonb_populate_record_valid for checking whether a document can populate a composite value without raising a conversion error.[2]

12. GIN indexes for JSONB

GIN is an inverted index access method suited to values containing multiple searchable components. PostgreSQL provides two built-in JSONB GIN operator classes: jsonb_ops (default) and jsonb_path_ops. A single JSONB GIN index can accelerate containment and JSON-path searches over many keys/values inside documents.[3][6]

12.1 Default JSONB GIN index

CREATE INDEX product_attributes_gin
ON catalog.product
USING GIN (attributes);

The default jsonb_ops operator class supports the key-existence operators ?, ?|, ?&, containment @>, and JSON-path match operators @? and @@.[3][6]

12.2 Indexed containment

SELECT
    product_id,
    name
FROM catalog.product
WHERE attributes @> '{
  "manufacturer": {"country": "US"},
  "tags": ["linux"]
}'::jsonb;

12.3 Indexed JSON path

SELECT
    product_id,
    name
FROM catalog.product
WHERE attributes @? '$.variants[*] ? (@.ram_gb >= 64)';

For indexable JSON-path patterns, PostgreSQL extracts equality clauses involving accessor chains and constants and uses those keys/values for GIN lookup. The exact path forms supported differ between JSONB GIN operator classes.[3]

12.4 GIN write amplification

One JSONB value can contribute many index entries, so a single row insert/update can require substantial GIN work. PostgreSQL's index-locking documentation explicitly notes that GIN insertion can produce several index-key insertions for one row. Benchmark write-heavy document tables with realistic payload sizes before indexing every JSONB column indiscriminately.[7]

13.1 Path-optimized index

CREATE INDEX product_attributes_path_gin
ON catalog.product
USING GIN (attributes jsonb_path_ops);

PostgreSQL documents jsonb_path_ops indexes as typically much smaller and more specific for supported containment/path searches, especially when keys appear frequently. The trade-off is reduced operator coverage and inability to index value-less structures effectively.[3]

13.2 Choose from the actual query workload

If the application frequently asks whether arbitrary keys exist, use jsonb_ops. If the dominant workload is containment and path/value search and key-existence is unimportant, test jsonb_path_ops. It is also possible to create targeted expression indexes rather than indexing every key/value in a large document.

14. Targeted expression and scalar indexes

A whole-document GIN index is flexible but stores search information for every indexed key/value. When one nested field is queried frequently, an expression index can be smaller and more precise. PostgreSQL supports indexes over scalar expressions, and the JSON documentation specifically demonstrates indexing nested JSON expressions.[3][8]

14.1 GIN index on one nested array

CREATE INDEX product_tags_gin
ON catalog.product
USING GIN ((attributes -> 'tags'));

SELECT *
FROM catalog.product
WHERE attributes -> 'tags' ? 'linux';

14.2 B-tree index on extracted scalar

CREATE INDEX product_country_idx
ON catalog.product (
    (attributes #>> '{manufacturer,country}')
);

SELECT *
FROM catalog.product
WHERE attributes #>> '{manufacturer,country}' = 'US';

14.3 Typed numeric expression index

CREATE INDEX product_width_idx
ON catalog.product (
    ((attributes #>> '{dimensions,width_mm}')::integer)
);

SELECT *
FROM catalog.product
WHERE (attributes #>> '{dimensions,width_mm}')::integer
      BETWEEN 400 AND 500;

Expression indexes move expression computation to writes and index maintenance rather than indexed reads. PostgreSQL notes that this improves retrieval at the cost of extra insertion/non-HOT-update work.[8]

14.4 Partial expression index

CREATE INDEX product_active_warranty_idx
ON catalog.product (
    (attributes ->> 'warranty_code')
)
WHERE active
  AND attributes ? 'warranty_code';

Partial indexes contain only rows satisfying a predicate. They can reduce index size and write maintenance when the indexed condition is selective, but PostgreSQL can use them only when it can prove the query predicate implies the index predicate at planning time.[9]

15. Relational + JSON hybrid modeling

A hybrid model keeps stable semantics in normal columns and reserves JSONB for variable or source-specific structure. This makes primary keys, foreign keys, uniqueness, typed comparisons, statistics, and common indexes straightforward while preserving document flexibility where it is genuinely useful.[1][10]

15.1 Product catalog

CREATE TABLE catalog.product (
    product_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id bigint NOT NULL
        REFERENCES app.tenant(tenant_id),

    sku text NOT NULL,
    name text NOT NULL,
    category_id bigint NOT NULL
        REFERENCES catalog.category(category_id),

    price numeric(12,2) NOT NULL
        CHECK (price >= 0),

    active boolean NOT NULL DEFAULT true,

    -- Manufacturer/category-specific optional attributes.
    attributes jsonb NOT NULL DEFAULT '{}'::jsonb,

    UNIQUE (tenant_id, sku)
);

Stable business identity and integrity are relational: tenant, SKU, category, price, active state. JSONB stores variable product characteristics such as dimensions, connector lists, material properties, or manufacturer metadata that differ widely by category.

15.2 Why price should not be JSON here

Putting price inside JSONB would make type validation, range checks, statistics, sorting, ordinary indexes, and application-wide consistency less direct. If almost every row has a field with the same meaning and type and it drives common predicates or constraints, that is strong evidence it belongs in a normal column.

15.3 Event envelope pattern

CREATE TABLE app.event (
    event_id uuid PRIMARY KEY,
    tenant_id bigint NOT NULL,
    aggregate_type text NOT NULL,
    aggregate_id text NOT NULL,
    event_type text NOT NULL,
    schema_version integer NOT NULL,
    occurred_at timestamptz NOT NULL,
    payload jsonb NOT NULL
);

CREATE INDEX event_aggregate_time_idx
ON app.event (
    tenant_id,
    aggregate_type,
    aggregate_id,
    occurred_at
);

CREATE INDEX event_payload_gin
ON app.event
USING GIN (payload jsonb_path_ops);

The envelope remains relational for ordering, partitioning, tenancy, routing, and event identity; the event-specific payload remains JSONB.

16. Constraining JSON documents

JSONB validates JSON syntax but does not automatically enforce an application-level schema. PostgreSQL recommends keeping documents reasonably predictable, and ordinary CHECK constraints can enforce selected invariants that matter to database correctness.[1][10]

16.1 Require an object

ALTER TABLE catalog.product
ADD CONSTRAINT product_attributes_object
CHECK (
    jsonb_typeof(attributes) = 'object'
);

16.2 Require a nested key when another condition applies

ALTER TABLE catalog.product
ADD CONSTRAINT product_dimensions_if_hardware
CHECK (
    category_id <> 10
    OR (
        attributes ? 'dimensions'
        AND jsonb_typeof(
            attributes -> 'dimensions'
        ) = 'object'
    )
);

16.3 Constrain scalar type and range

ALTER TABLE catalog.product
ADD CONSTRAINT product_optional_weight_valid
CHECK (
    NOT (attributes ? 'weight_kg')
    OR (
        jsonb_typeof(attributes -> 'weight_kg') = 'number'
        AND (attributes ->> 'weight_kg')::numeric > 0
    )
);

16.4 What checks should not become

A large JSON schema reimplemented as dozens of complicated SQL checks can become harder to maintain than normalized columns or application/ingestion validation. Use database constraints for invariants whose violation would make persisted state invalid; use application/domain validation for richer presentation and workflow rules.

17. Promote important JSON fields with generated columns

PostgreSQL 18 supports stored and virtual generated columns. A stored generated column is computed on write and stored like a normal column; a virtual generated column is computed on read. Generated expressions are constrained to immutable logic and cannot query other rows. This makes generated columns useful for surfacing stable scalar values from JSONB while retaining the original document.[11]

17.1 Extract a stable scalar

CREATE TABLE integrations.partner_record (
    record_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    payload jsonb NOT NULL,

    external_id text
    GENERATED ALWAYS AS (
        payload ->> 'id'
    ) STORED,

    event_type text
    GENERATED ALWAYS AS (
        payload ->> 'type'
    ) STORED
);

CREATE INDEX partner_record_external_id_idx
ON integrations.partner_record(external_id);

This pattern can simplify frequently used predicates and gives the planner normal column statistics. It also makes it easier to constrain the extracted value without discarding the original source document.

17.2 Generated numeric field

ALTER TABLE catalog.product
ADD COLUMN width_mm integer
GENERATED ALWAYS AS (
    (attributes #>> '{dimensions,width_mm}')::integer
) STORED;

CREATE INDEX product_width_generated_idx
ON catalog.product(width_mm);

If a generated field becomes fundamental to application identity or integrity, consider eventually migrating it to an ordinary relational column instead of preserving JSONB as its authoritative source.

18.1 Normalize when the database needs to understand the field deeply

A value usually deserves a relational column when PostgreSQL must understand it as a stable concept: enforce its type, reference it with a foreign key, make it unique, build multicolumn indexes around it, collect useful statistics, partition by it, grant column-specific privileges, or update it independently under concurrency.

18.2 Use JSONB when variation is intrinsic

JSONB is strongest for polymorphic attributes, third-party source payloads, sparse optional metadata, versioned event bodies, per-category specifications, configuration documents, and data whose nested structure is itself part of the domain.

18.3 Avoid the EAV trap in either direction

An entity-attribute-value table can turn every field into rows and lose straightforward typing; an undisciplined JSONB blob can turn every field into invisible schema. A hybrid model usually provides a better boundary: stable semantics become relational, variable semantics remain in JSONB.

Rule of thumb: if a property is important enough that you regularly join, sort, constrain, group, partition, or authorize by it, strongly consider making it relational.

19. Application patterns

19.1 Flexible product specifications

SELECT
    product_id,
    sku,
    name,
    attributes #>> '{dimensions,width_mm}' AS width_mm,
    attributes -> 'ports' AS ports
FROM catalog.product
WHERE category_id = $1
  AND attributes @> $2::jsonb;

19.2 Third-party API response cache

CREATE TABLE integrations.api_response (
    provider text NOT NULL,
    cache_key text NOT NULL,
    fetched_at timestamptz NOT NULL,
    expires_at timestamptz NOT NULL,
    response jsonb NOT NULL,
    PRIMARY KEY (provider, cache_key)
);

The cache key, provider, and expiration are stable operational dimensions; provider-specific response content remains JSONB.

19.3 User preferences

CREATE TABLE app.user_preferences (
    user_id bigint PRIMARY KEY
        REFERENCES app.user_account(user_id)
        ON DELETE CASCADE,
    preferences jsonb NOT NULL DEFAULT '{}'::jsonb,
    CHECK (jsonb_typeof(preferences) = 'object')
);

Preferences are often a good JSONB use case because optional UI settings evolve rapidly and are usually updated/retrieved as one logical unit. Security-sensitive authorization state should generally remain in normal roles/columns rather than being hidden inside a preferences document.

19.4 API response from normalized data

SELECT jsonb_build_object(
    'id', o.order_id,
    'status', o.status,
    'total', o.total,
    'customer', jsonb_build_object(
        'id', c.customer_id,
        'name', c.display_name
    ),
    'lines', (
        SELECT jsonb_agg(
            jsonb_build_object(
                'sku', p.sku,
                'quantity', oi.quantity,
                'unit_price', oi.unit_price
            )
            ORDER BY oi.order_item_id
        )
        FROM app.order_item AS oi
        JOIN catalog.product AS p
          ON p.product_id = oi.product_id
        WHERE oi.order_id = o.order_id
    )
)
FROM app.orders AS o
JOIN app.customer AS c
  ON c.customer_id = o.customer_id
WHERE o.order_id = $1;

Generating nested JSON at the query boundary lets storage remain normalized while serving JSON APIs efficiently.

20. Performance engineering

20.1 Measure the actual predicates

A “JSONB table” is not one workload. A query testing arbitrary containment has different indexing needs from one filtering a known scalar path, expanding large arrays, or sorting by a nested numeric value. Capture production SQL with pg_stat_statements and examine representative plans with EXPLAIN (ANALYZE, BUFFERS) before choosing indexes.[12][13] 

EXPLAIN (
    ANALYZE,
    BUFFERS
)
SELECT product_id
FROM catalog.product
WHERE attributes @> '{"tags":["linux"]}'::jsonb;

20.2 Whole-document GIN versus targeted indexes

A broad GIN index buys query flexibility but indexes many keys/values that might never be searched. PostgreSQL's JSON documentation notes that targeted expression indexes can be smaller and faster when a particular nested path is frequently queried.[3]

20.3 Row size and update contention

Updating one nested property still updates the JSONB column value in the containing row. PostgreSQL documentation warns that large documents can increase lock contention because the entire row is locked for update. Separate independently changing entities into their own rows when concurrency requires it.[1]

20.4 Planner visibility

The PostgreSQL planner relies on statistics to estimate selectivity. Stable frequently queried scalar columns typically expose clearer single-column statistics than arbitrary paths inside heterogeneous JSONB. Generated columns or expression indexes can help when a nested scalar becomes operationally important.[14]

20.5 Avoid repeated expansion of large arrays

SELECT ...
FROM events e
CROSS JOIN LATERAL jsonb_array_elements(e.payload->'items') AS item
WHERE ...;

Set-returning expansion creates one SQL row per JSON element. If an embedded array is routinely exploded for reporting across millions of parent rows, that nested collection is behaving like a relation and may belong in a child table or materialized derived structure.

20.6 Index write cost

Expression indexes must recompute indexed expressions on inserts and non-HOT updates, while GIN can generate many key insertions per JSONB datum. Do not build every plausible JSON index; index the workload that actually exists.[7][8]

20.7 Keep indexes compatible with predicates

-- This expression index:
CREATE INDEX product_country_idx
ON catalog.product (
    (attributes #>> '{manufacturer,country}')
);

-- naturally supports this predicate:
WHERE attributes #>> '{manufacturer,country}' = 'US'

Index design and query expression shape must align. A semantically similar query that invokes different operators or casts may not match the intended expression index.

21. Schema evolution and JSON migrations

JSONB permits documents of different versions to coexist, but versionless semi-structured data can become difficult to interpret. External payloads and long-lived documents benefit from an explicit schema/version marker plus migration logic that can distinguish old and new structures.

21.1 Version documents explicitly

{
  "schema_version": 3,
  "manufacturer": {
    "id": "m-42",
    "name": "Acme"
  },
  "dimensions": {
    "width_mm": 420
  }
}

21.2 Backfill one version

UPDATE catalog.product
SET attributes =
    jsonb_set(
        attributes,
        '{schema_version}',
        '3'::jsonb,
        true
    )
WHERE COALESCE(
    (attributes ->> 'schema_version')::integer,
    0
) < 3;

21.3 Promote a JSON property to a real column

ALTER TABLE catalog.product
ADD COLUMN manufacturer_id bigint;

UPDATE catalog.product
SET manufacturer_id =
    (attributes #>> '{manufacturer,id}')::bigint
WHERE attributes #> '{manufacturer,id}' IS NOT NULL;

ALTER TABLE catalog.product
ADD CONSTRAINT product_manufacturer_fk
FOREIGN KEY (manufacturer_id)
REFERENCES catalog.manufacturer(manufacturer_id);

A pragmatic JSON architecture allows the boundary to move. Early variable fields can live in JSONB; fields that later become core business dimensions can be migrated into typed relational columns without abandoning the rest of the document.

22. Common pitfalls

22.1 Storing identifiers as inconsistent JSON types

{"customer_id": 42}
{"customer_id": "42"}

JSON distinguishes numbers from strings. Mixed representations make containment and typed extraction inconsistent. Define a document contract even when the database does not enforce every field.

22.2 Forgetting duplicate-key semantics

SELECT '{"role":"user","role":"admin"}'::jsonb;

Only the last duplicate object-key value survives in JSONB. If duplicate keys carry semantic meaning in an upstream format, preserve the raw input separately or model the data differently.[1]

22.3 Treating JSON values as text too early

-- Preserves JSON type:
attributes -> 'price'

-- Becomes text:
attributes ->> 'price'

Use JSON-returning operators while navigating documents and convert to text/typed SQL values at the boundary where relational comparison is required.

22.4 Using string LIKE instead of JSON semantics

-- Avoid:
WHERE attributes::text LIKE '%"country":"US"%'

-- Prefer:
WHERE attributes @> '{"country":"US"}'::jsonb

Text formatting is not JSON structure. JSONB containment or JSON path expresses structural intent and can use appropriate indexes.[3]

22.5 Putting an entire relational graph into one document

A large document may look convenient initially but weakens foreign-key enforcement, independent concurrency, targeted statistics, and relational querying. PostgreSQL's JSON design guidance specifically recommends atomic/manageable documents rather than uncontrolled document growth.[1]

22.6 Assuming GIN makes every JSON expression fast

GIN indexes support defined operators/opclasses. A predicate that extracts a value, casts it, and performs a range comparison usually needs a scalar expression index or generated column rather than expecting a whole-document GIN index to act as a universal JSON accelerator.

22.7 Storing authorization rules in opaque JSON

If authorization depends on a field, make sure PostgreSQL can enforce that rule reliably through relational columns, role privileges, or row-level security. Application-only interpretation of an opaque document is a weak substitute for database authorization controls.

23. Production checklist

  1. Choose the storage type deliberately. Prefer jsonb for queryable documents; use json only when preserving source representation matters.
  2. Define a document contract. Flexible does not mean structureless.
  3. Keep stable identity relational. Primary keys, tenant IDs, foreign keys, status, timestamps, and other core fields usually belong in columns.
  4. Keep independently changing entities separate. Large nested arrays can become concurrency and reporting liabilities.
  5. Use containment for structural subset search. Use JSON path for more expressive nested predicates.
  6. Select the GIN opclass from workload needs. jsonb_ops is flexible; jsonb_path_ops can be smaller/faster for containment/path queries.
  7. Use targeted expression indexes for frequently queried nested paths.
  8. Promote hot scalar fields to generated or ordinary columns when range/sort/join/statistics behavior matters.
  9. Use CHECK constraints for document invariants whose violation would corrupt persistent state.
  10. Use JSON_TABLE or record expansion for controlled JSON-to-relational projection.
  11. Generate API JSON from relational rows instead of denormalizing storage solely to match response shape.
  12. Parameterize SQL and JSON path variables. Never concatenate untrusted values into SQL source.
  13. Benchmark write cost. JSONB GIN and expression indexes amplify updates.
  14. Version long-lived document formats. Plan migrations from JSON fields into relational columns when semantics stabilize.
  15. Verify plans. Use EXPLAIN (ANALYZE, BUFFERS) on representative containment, path, extraction, and expansion queries.
Modeling principle: JSONB is most valuable when variability is intrinsic to the data. Normalize what the database must understand strongly; keep flexible what the domain truly allows to vary.
