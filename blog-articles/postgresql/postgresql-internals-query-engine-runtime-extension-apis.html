PostgreSQL Internals: Query Engine, Runtime, and Extension APIs

A source-oriented tour of PostgreSQL's query engine, runtime subsystems, logical decoding, and extension interfaces, with storage and buffer internals summarized where they affect execution.

Technical article • PostgreSQL 18.6 documentation baseline • Source-tree details are version-sensitive • Updated 15 September 2026

Abstract

PostgreSQL is simultaneously a relational database engine and a framework of cooperating subsystems. A SQL statement enters through the backend process, is parsed and rewritten, is transformed into paths and then a plan, and is interpreted by an executor whose nodes obtain tuples through table and index access-method APIs. Beneath that layer, PostgreSQL coordinates relation storage, a shared buffer cache, write-ahead logging (WAL), transaction status, snapshots, locking, and background processes. The same architecture is deliberately extensible: functions, types, operators, foreign data wrappers (FDWs), table and index access methods, background workers, logical-decoding output plugins, and other server modules can be added without modifying core SQL syntax or rebuilding the server in many cases.[1]-[3]

This article uses PostgreSQL 18.6 documentation as the stable behavioral baseline and refers to PostgreSQL's generated source documentation for implementation examples. Internal C functions and structures outside documented extension interfaces are not guaranteed to remain source- or binary-compatible across major releases; PostgreSQL explicitly distinguishes well-established plugin APIs from the much larger body of internal server symbols.[21]

Companion article: for a bottom-up treatment of process architecture, shared memory, relation files, heap pages, tuple layout, TOAST, FSM/VM, catalogs, and object-to-file mapping, see PostgreSQL Internals: Process Architecture and Storage Layout.

1. PostgreSQL source code

The PostgreSQL source is maintained in Git, and the official documentation links to the public repository and describes how to obtain it. The source tree separates major concerns into directories such as src/backend/access, executor, optimizer, parser, replication, storage, and utils, while public and internal headers live primarily under src/include.[3]

A practical way to read PostgreSQL source is to follow one behavior vertically rather than trying to understand the tree directory by directory. For example, follow a page read from ReadBuffer() in the buffer manager down to the storage-manager layer, then follow a tuple visibility decision from heap access code into snapshot and transaction-state facilities. The official internals chapter deliberately presents query processing as a sequence of stages rather than a catalog of files, which mirrors this approach.[2]

Version boundary. Code examples in this article illustrate PostgreSQL 18-era interfaces and the current generated source documentation. Re-check headers and documentation when targeting another major release; internal APIs are not an ABI promise across major versions.[21]

2. The path of a query

At a high level, PostgreSQL receives SQL in a backend process, parses it into a parse tree, performs parse analysis and rewriting, invokes the planner/optimizer to generate an executable plan, and finally runs that plan through the executor. The executor returns result tuples to the client or applies data-modifying operations as specified by the plan.[2]

client SQL | v backend / traffic-cop | +--> raw parser | +--> parse analysis / transformation | +--> rewrite system | +--> planner / optimizer | | | +--> RelOptInfo / Paths / costs | +--> chosen Path | +--> Plan tree | +--> ExecutorStart() +--> ExecutorRun() +--> ExecutorFinish() +--> ExecutorEnd() | +--> table/index AMs +--> buffers +--> WAL / locks / transactions / snapshots +--> result or modified rows

The top-level executor interface in src/backend/executor/execMain.c is explicitly organized around ExecutorStart, ExecutorRun, ExecutorFinish, and ExecutorEnd. The planner's external interface is implemented in src/backend/optimizer/plan/planner.c. These functions are useful landmarks when tracing a statement in a debugger.[12][13]

3. Storage manager

PostgreSQL's built-in heap and index access methods store relations as files divided into blocks/pages. Ordinary tables and indexes have a main fork; relations can also have free-space-map and visibility-map forks, and unlogged relations have an initialization fork. Large relation files are segmented when they exceed the configured segment size. TOAST tables provide out-of-line storage for values that do not fit efficiently in ordinary heap tuples.[4]

The storage manager, commonly abbreviated smgr, is the layer through which relation file operations are dispatched. In the PostgreSQL source, src/backend/storage/smgr/smgr.c describes itself as the public interface to the storage-manager switch; an SMgrRelation represents the physical on-disk relation files opened for reads and writes. Buffer flushing, recovery, checkpoints, and DDL-related physical file operations can use this layer even when they are not going through the ordinary relation cache path.[5]

3.1 Relation forks and page-oriented I/O

The smgr layer does not understand SQL rows in the way the executor does. Its job is closer to relation-fork and block I/O: create or unlink storage, read/write/extend blocks, determine relation size, synchronize storage, and mediate the concrete storage implementation. Higher layers decide what page contents mean.[4][5] 

-- Inspect physical relation identity and fork sizes from SQL.
SELECT
    c.oid::regclass AS relation,
    pg_relation_filenode(c.oid) AS filenode,
    pg_size_pretty(pg_relation_size(c.oid, 'main')) AS main,
    pg_size_pretty(pg_relation_size(c.oid, 'fsm'))  AS fsm,
    pg_size_pretty(pg_relation_size(c.oid, 'vm'))   AS vm
FROM pg_class AS c
WHERE c.oid = 'public.orders'::regclass;

Functions such as pg_relation_size expose the sizes of relation forks at SQL level, while the physical-storage chapter documents the file layout and the meaning of the main, FSM, VM, and initialization forks.[4]

4. Buffer manager in the execution path

The shared buffer manager matters to this article because executor nodes, table access methods, index access methods, WAL, and checkpoint activity all meet at page access. In source terms, the runtime path repeatedly asks for relation blocks, pins the selected buffer while using it, acquires content locks when page contents must be examined or changed, marks modified pages dirty, and relies on WAL-before-data ordering before dirty pages reach durable storage.[6][7]

This query/runtime article treats buffers as execution plumbing: what the executor and extension code need to know when they cause page reads, writes, or instrumentation. For the deeper physical view--buffer identity, replacement behavior, buffer-access strategy rings, pg_buffercache queries, and the mapping from cached blocks back to relation files--see PostgreSQL Internals: Process Architecture and Storage Layout.[23]

5. WAL subsystem

Write-ahead logging is PostgreSQL's crash-recovery foundation. The core rule is that the WAL describing a change must reach durable storage before the corresponding modified data page is allowed to reach durable storage. This allows recovery to redo committed changes whose data pages had not yet been written when a crash occurred, and means a commit can usually force sequential WAL rather than every changed heap and index page.[7]

WAL positions are represented by Log Sequence Numbers (LSNs), monotonically increasing byte positions in the WAL stream. WAL is stored under pg_wal in segment files. In the source tree, xlog.c coordinates startup/checkpointing and WAL-buffer management; record construction is largely in xloginsert.c, recovery in xlogrecovery.c, record reading in xlogreader.c, and redo helpers in xlogutils.c.[7]

5.1 A simplified write path

backend modifies page | | construct WAL record v WAL insertion buffers ----> WAL segment files | | | +--> durable flush required by commit policy | +--> page receives page LSN | v dirty shared buffer | +--> later checkpoint / bgwriter / eviction write (must not violate WAL-before-data rule)

The page LSN connects page state to WAL progress: before a dirty page is written, the WAL required to redo that page state must already be durable. The buffer manager and WAL manager therefore interact directly; PostgreSQL's buffer-manager source includes WAL-related headers and uses page LSNs during writeback decisions.[6][7]

5.2 Observing WAL

-- Current insertion position.
SELECT pg_current_wal_lsn();

-- Byte distance between two LSNs.
SELECT pg_size_pretty(
    pg_wal_lsn_diff(pg_current_wal_lsn(), '0/0'::pg_lsn)
);

-- From the shell, inspect WAL records (requires appropriate access).
pg_waldump --start=0/16B6C50 --limit=20 /path/to/pg_wal

PostgreSQL documents pg_lsn values as byte positions in WAL and ships pg_waldump for low-level WAL inspection.[7]

5.3 WAL for extensions

Extensions that implement crash-sensitive storage structures can use PostgreSQL's generic WAL facility or a custom WAL resource manager. Generic WAL is simpler but is not decoded by logical decoding; custom resource managers are more flexible and can participate in logical decoding but require a larger amount of implementation and operational care.[17]

6. Lock manager

PostgreSQL has multiple synchronization mechanisms with different scopes. The heavyweight lock manager handles database-object locks and lock modes visible conceptually through SQL locking behavior; lightweight locks (LWLocks) protect shared-memory data structures and short critical sections; spinlocks are used for still shorter low-level mutual exclusion. These mechanisms complement MVCC rather than replacing it.[8][21]

The primary heavyweight lock implementation is in src/backend/storage/lmgr/lock.c. Its source describes the shared lock table as a shared-memory hash table; when a process requests an incompatible lock, the backend is placed to sleep by process-management code until the lock can be granted. The main interface includes operations such as LockAcquire() and LockRelease().[8]

6.1 MVCC and locks solve different problems

MVCC allows ordinary readers and writers to operate without treating every read/write overlap as a blocking conflict. PostgreSQL still needs explicit table locks, tuple-level locking, relation-extension locks, internal metadata locks, and predicate locking for serializable isolation. The concurrency-control documentation defines table- and row-level lock modes and documents deadlock detection and advisory locks.[8] 

-- See heavyweight locks currently known to PostgreSQL.
SELECT
    pid,
    locktype,
    relation::regclass,
    mode,
    granted,
    waitstart
FROM pg_locks
ORDER BY granted, pid;

-- Find sessions waiting on another backend.
SELECT
    pid,
    pg_blocking_pids(pid) AS blockers,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;

7. Transaction manager

PostgreSQL's transaction-processing internals cover transaction identifiers, locking relationships, subtransactions, and two-phase transactions. The source file src/backend/access/transam/xact.c contains top-level transaction-system routines and coordinates with commit status, subtransactions, WAL, two-phase commit, snapshots, replication, invalidation, and resource cleanup.[9]

7.1 Transaction IDs and command IDs

PostgreSQL uses 32-bit transaction identifiers (xid) in on-disk tuple metadata and manages wraparound through vacuum/freezing mechanisms. User-facing snapshot inspection uses the non-wrapping xid8 type where appropriate. A transaction can execute multiple commands, so command identifiers participate in distinguishing visibility among changes made within the same transaction.[9][10]

7.2 Transaction state is more than BEGIN/COMMIT

Internally, a backend tracks top-level transaction state, subtransaction nesting, resource ownership, transaction characteristics, command counters, snapshots, pending invalidations, and callbacks. Successful commit must coordinate durability and visibility; abort must release or unwind resources safely. This is why transaction code touches a broad set of subsystems in xact.c rather than being isolated in a narrow module.[9] 

-- View the current transaction identifier only when one is assigned.
SELECT pg_current_xact_id_if_assigned();

BEGIN;
SELECT pg_current_xact_id();  -- forces/returns an xid8
SAVEPOINT s1;
UPDATE accounts SET balance = balance - 10 WHERE id = 1;
ROLLBACK TO s1;
COMMIT;

8. MVCC in the runtime

PostgreSQL's multiversion concurrency control (MVCC) gives each statement or transaction a visibility snapshot and lets ordinary reads avoid blocking ordinary writes under the documented isolation model. For the planner and executor, the important contract is not the byte layout of a tuple header; it is that every scan node returns only tuple versions visible to the snapshot and lock mode under which that node runs.[8][10]

Snapshots also shape extension code. Server-side functions, SPI users, custom scan providers, access methods, FDWs, and logical-decoding plugins must respect the snapshot, command-counter, transaction, and memory-lifetime rules of the backend they run inside. Code that bypasses those rules can produce rows that SQL semantics would not permit, leak memory across statements, or observe state at the wrong transactional moment.[9][10][21]

For heap tuple header fields, xmin/xmax, HOT chains, visibility-map effects, free-space reuse, and raw-page inspection, use the companion storage article's heap storage and low-level inspection sections.[4]

9. Query planner internals

The planner/optimizer transforms a rewritten query tree into a physical plan. PostgreSQL considers alternative scan methods, join orders, join algorithms, aggregation strategies, parallel alternatives, sort strategies, and other paths, attaches cost estimates, and selects a cheapest path according to the cost model. The internals documentation calls out the planner as the stage that generates possible plans before the executor begins.[2]

The planner's external interface lives in src/backend/optimizer/plan/planner.c. Much of the optimizer works with Paths: candidate execution strategies carrying properties such as estimated rows, startup cost, total cost, parameterization, pathkeys (ordering), and parallel-safety information. Only after path selection are plan nodes constructed for the executor.[12]

9.1 Statistics drive cardinality estimates

PostgreSQL uses statistics from ANALYZE and related system catalogs to estimate selectivity and row counts. Cardinality mistakes propagate into downstream cost decisions: a severe underestimate can cause the planner to choose nested loops or undersized hashes; an overestimate can make useful indexes appear too expensive. PostgreSQL documents both single-column and multivariate statistics as inputs to planner estimation.[11] 

EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT c.id, count(*)
FROM customers c
JOIN orders o ON o.customer_id = c.id
WHERE c.region = 'east'
GROUP BY c.id
ORDER BY count(*) DESC
LIMIT 20;

For internals work, compare estimated rows= with actual row counts at each node and then inspect the statistics assumptions that produced the discrepancy. EXPLAIN (ANALYZE, BUFFERS) is often the fastest bridge from a high-level performance symptom to planner and buffer behavior.[11]

9.2 Join search and GEQO

Join-order optimization becomes combinatorial as the number of joined relations increases. PostgreSQL contains both its ordinary dynamic-programming-style join search and a genetic query optimizer (GEQO) intended for sufficiently large join problems. GEQO is documented as an alternative search strategy for complex join ordering rather than a different executor.[1]

10. Executor internals

The executor interprets the selected plan tree. Each plan-node type has executor support that initializes node-specific state, requests tuples from child nodes, applies expressions or join logic, and produces tuples upward. At the top level, ExecutorStart, ExecutorRun, ExecutorFinish, and ExecutorEnd form the external executor lifecycle.[13]

Limit | Sort | Hash Join | \ Seq Scan Hash (customers) | Seq Scan (orders)

Execution is demand-driven for many plan nodes: a parent asks a child for the next tuple or batch of work, and the child recursively pulls from its own children. Materialization, hashing, sorting, aggregation, parallel exchange, and modification nodes introduce node-specific state and buffering. Executor state, expression contexts, tuple slots, snapshots, and instrumentation are allocated and released around the query lifecycle.[13]

10.1 TupleTableSlot

Executor nodes generally exchange tuples through TupleTableSlot-style abstractions rather than by assuming one fixed physical tuple representation. This indirection allows executor code to handle heap tuples, minimal tuples, virtual tuples, foreign tuples, and other representations through slot operations, which is important for extensibility and avoiding unnecessary materialization.[13]

10.2 Hooks

The executor exposes hook variables around its top-level lifecycle, including start/run/finish/end hooks, allowing extensions to observe or wrap execution. Hooks are powerful but live in the server plugin API space, so extension authors must follow PostgreSQL's API/ABI stability guidance rather than assuming every internal executor symbol is stable forever.[13][21]

11. Memory contexts

PostgreSQL avoids pervasive manual lifetime tracking by allocating most backend memory inside hierarchical memory contexts. Allocations made with palloc() belong to the current context. Resetting or deleting a context releases all allocations owned by it, making context lifetime the primary unit of memory management in server code.[14]

The implementation in src/backend/utils/mmgr/mcxt.c provides operations common to context types and dispatches allocator-specific work through a MemoryContextMethods table. PostgreSQL has multiple context implementations optimized for different allocation patterns, while the context tree supplies ownership and lifetime semantics above them.[14]

11.1 Typical C pattern

MemoryContext old;
MemoryContext workctx;

workctx = AllocSetContextCreate(CurrentMemoryContext,
                                "my extension work",
                                ALLOCSET_DEFAULT_SIZES);

old = MemoryContextSwitchTo(workctx);

/* These allocations belong to workctx. */
char *buf = palloc(4096);
/* ... do work ... */

MemoryContextSwitchTo(old);

/* Frees everything allocated in workctx at once. */
MemoryContextDelete(workctx);

When using SPI, SPI_connect() creates a new memory context and makes it current; SPI_finish() destroys that SPI context and restores the previous one. Therefore, return values that must outlive SPI_finish() need to be allocated in an appropriate upper context, for example with SPI_palloc() where documented.[14][21] 

-- Inspect this backend's memory-context tree.
SELECT
    name,
    type,
    level,
    total_bytes,
    free_bytes,
    used_bytes
FROM pg_backend_memory_contexts
ORDER BY path;

PostgreSQL exposes pg_backend_memory_contexts for inspecting the current backend's context hierarchy and allocation totals; access is restricted because this is server-internal diagnostic information.[14]

12. Background workers

PostgreSQL lets extensions register code to run in server-managed background processes. Background workers are started, stopped, and monitored by the server, share PostgreSQL's shared-memory environment, and can optionally establish database connections. Static background workers are commonly registered from _PG_init() when the module is loaded through shared_preload_libraries; dynamic workers can be requested later from a backend or another worker.[15]

The implementation is centered in src/backend/postmaster/bgworker.c, which maintains registered-worker metadata and shared-memory worker slots. PostgreSQL's own features also use background-worker infrastructure, including logical replication and parallel query components.[15]

12.1 Minimal registration skeleton

#include "postgres.h"
#include "fmgr.h"
#include "postmaster/bgworker.h"

PG_MODULE_MAGIC;

void _PG_init(void);
void my_worker_main(Datum main_arg);

void
_PG_init(void)
{
    BackgroundWorker worker = {0};

    snprintf(worker.bgw_name, BGW_MAXLEN, "my_worker");
    snprintf(worker.bgw_type, BGW_MAXLEN, "my_worker");

    worker.bgw_flags =
        BGWORKER_SHMEM_ACCESS | BGWORKER_BACKEND_DATABASE_CONNECTION;

    worker.bgw_start_time = BgWorkerStart_RecoveryFinished;
    worker.bgw_restart_time = 10;

    snprintf(worker.bgw_library_name, MAXPGPATH, "my_extension");
    snprintf(worker.bgw_function_name, BGW_MAXLEN, "my_worker_main");

    RegisterBackgroundWorker(&worker);
}

Background workers execute C code inside PostgreSQL's process and memory environment, so a bug can corrupt server state or crash a process. The official documentation explicitly warns administrators to load only carefully audited worker modules.[15]

13. Parallel execution

When the optimizer selects a parallel plan, the plan contains a Gather or Gather Merge node above a parallel portion. The leader requests worker processes, and each successfully launched worker executes the parallel plan fragment. The leader can also participate in the parallel work while simultaneously consuming worker output.[16]

Gather does not preserve ordering from workers; Gather Merge merges already ordered streams while preserving the required sort order. Parallel execution is constrained by configuration such as max_worker_processes, max_parallel_workers, and max_parallel_workers_per_gather, so a plan may receive fewer workers than the planner requested.[16] 

EXPLAIN (ANALYZE, VERBOSE)
SELECT count(*)
FROM large_fact
WHERE event_date >= current_date - interval '30 days';

-- Typical shape:
-- Finalize Aggregate
--   -> Gather
--        Workers Planned: N
--        -> Partial Aggregate
--             -> Parallel Seq Scan ...

13.1 Parallel safety

A parallel plan cannot freely call arbitrary code. Functions and plan operations are classified with respect to parallel safety, and custom server code must not assume process-local state is automatically shared among workers. Parallel infrastructure uses dynamic shared memory and explicit shared data structures where cooperation is necessary.[16][21]

14. Logical decoding

Logical decoding converts physical WAL changes into a logical stream that external consumers can understand without reconstructing raw page modifications. PostgreSQL associates logical streams with replication slots and uses output plugins to transform decoded changes into a chosen representation.[17]

The source file src/backend/replication/logical/logical.c coordinates logical-decoding contexts and interaction among WAL reading, snapshot building, reorder buffers, decoding, and output. It is designed so consumers can create and consume change streams without directly orchestrating every internal decoding component.[17]

14.1 Replication slots

A logical replication slot identifies a persistent change stream for one database and preserves the resources needed for a consumer to continue from its confirmed position. This durability has an operational consequence: a stalled or abandoned slot can retain WAL, so slot lag must be monitored.[17] 

-- For experimentation only; requires logical WAL configuration.
SELECT *
FROM pg_create_logical_replication_slot('demo_slot', 'test_decoding');

CREATE TABLE ld_demo(id int primary key, v text);
INSERT INTO ld_demo VALUES (1, 'hello');
UPDATE ld_demo SET v = 'world' WHERE id = 1;

SELECT *
FROM pg_logical_slot_get_changes('demo_slot', NULL, NULL);

SELECT pg_drop_replication_slot('demo_slot');

14.2 Output plugin skeleton

#include "postgres.h"
#include "fmgr.h"
#include "replication/output_plugin.h"

PG_MODULE_MAGIC;

static void startup(LogicalDecodingContext *ctx,
                    OutputPluginOptions *opt,
                    bool is_init);
static void begin_txn(LogicalDecodingContext *ctx, ReorderBufferTXN *txn);
static void change(LogicalDecodingContext *ctx,
                   ReorderBufferTXN *txn,
                   Relation rel,
                   ReorderBufferChange *chg);
static void commit_txn(LogicalDecodingContext *ctx,
                       ReorderBufferTXN *txn,
                       XLogRecPtr commit_lsn);

void
_PG_output_plugin_init(OutputPluginCallbacks *cb)
{
    cb->startup_cb = startup;
    cb->begin_cb   = begin_txn;
    cb->change_cb  = change;
    cb->commit_cb  = commit_txn;
}

An output plugin must export _PG_output_plugin_init and fill callback pointers. PostgreSQL ships contrib/test_decoding as an example implementation.[17]

15. Custom data types

PostgreSQL's extensibility is catalog-driven: system catalogs describe types, functions, operators, access methods, and related metadata. A user-defined base type can therefore become a first-class SQL type when the required support functions and catalog entries are created. For a base type, input and output functions are mandatory; binary send/receive, typmod, analysis, subscripting, and other support functions are optional depending on the type.[18]

15.1 Example: fixed-size 2D point type

/* point2d.c */
#include "postgres.h"
#include "fmgr.h"
#include "utils/builtins.h"

PG_MODULE_MAGIC;

typedef struct Point2D
{
    double x;
    double y;
} Point2D;

PG_FUNCTION_INFO_V1(point2d_in);
PG_FUNCTION_INFO_V1(point2d_out);

Datum
point2d_in(PG_FUNCTION_ARGS)
{
    char *str = PG_GETARG_CSTRING(0);
    Point2D *p = (Point2D *) palloc(sizeof(Point2D));

    if (sscanf(str, "(%lf,%lf)", &p->x, &p->y) != 2)
        ereport(ERROR,
                (errcode(ERRCODE_INVALID_TEXT_REPRESENTATION),
                 errmsg("invalid point2d value: \"%s\"", str)));

    PG_RETURN_POINTER(p);
}

Datum
point2d_out(PG_FUNCTION_ARGS)
{
    Point2D *p = (Point2D *) PG_GETARG_POINTER(0);
    PG_RETURN_CSTRING(psprintf("(%g,%g)", p->x, p->y));
}
-- SQL installation script
CREATE TYPE point2d;

CREATE FUNCTION point2d_in(cstring)
RETURNS point2d
AS 'MODULE_PATHNAME', 'point2d_in'
LANGUAGE C IMMUTABLE STRICT;

CREATE FUNCTION point2d_out(point2d)
RETURNS cstring
AS 'MODULE_PATHNAME', 'point2d_out'
LANGUAGE C IMMUTABLE STRICT;

CREATE TYPE point2d (
    INTERNALLENGTH = 16,
    INPUT = point2d_in,
    OUTPUT = point2d_out,
    ALIGNMENT = double
);

The shell-type pattern is required because the I/O functions refer to the type before its final definition exists. PostgreSQL documents this bootstrap sequence for user-defined base types. Real production types must also address alignment, binary representation, pass-by-value/reference rules, TOAST behavior where relevant, error handling, binary I/O if desired, and portability of any on-disk representation.[18]

16. Custom operators

A PostgreSQL operator delegates execution to an underlying function, but operator catalog metadata also informs the optimizer. Operator definitions can declare commutators, negators, selectivity functions, and whether the operator participates in hash or merge semantics. Operators are overloadable by operand types.[18] 

CREATE FUNCTION point2d_distance(point2d, point2d)
RETURNS double precision
AS 'MODULE_PATHNAME', 'point2d_distance'
LANGUAGE C IMMUTABLE STRICT PARALLEL SAFE;

-- A made-up distance operator.
CREATE OPERATOR <-> (
    LEFTARG = point2d,
    RIGHTARG = point2d,
    FUNCTION = point2d_distance,
    COMMUTATOR = <->
);

The operator itself does not automatically make an index usable. Indexability requires an appropriate operator class/family and access-method strategy/support functions. PostgreSQL separates operator semantics from index access-method integration so that the same SQL type can support different indexing strategies.[18][19]

17. Custom access methods

17.1 Table access methods

The table access method API defines the boundary between core PostgreSQL and a table's physical storage behavior. Each table AM is represented in pg_am and is created through CREATE ACCESS METHOD. Its handler returns a TableAmRoutine containing callbacks for scans, tuple operations, index interaction, vacuuming, relation sizing, and other table behaviors.[19] 

PG_FUNCTION_INFO_V1(my_tableam_handler);

Datum
my_tableam_handler(PG_FUNCTION_ARGS)
{
    static const TableAmRoutine routine = {
        .type = T_TableAmRoutine,

        /* Required callbacks would be filled here:
         * slot_callbacks,
         * scan_begin / scan_getnextslot / scan_end,
         * tuple_insert / tuple_delete / tuple_update,
         * relation_size,
         * relation_vacuum,
         * index_fetch_*,
         * ...
         */
    };

    PG_RETURN_POINTER(&routine);
}
CREATE FUNCTION my_tableam_handler(internal)
RETURNS table_am_handler
AS 'MODULE_PATHNAME'
LANGUAGE C;

CREATE ACCESS METHOD my_tableam
TYPE TABLE
HANDLER my_tableam_handler;

A real table AM is a large implementation, not a handful of callbacks. It must integrate correctly with MVCC, WAL/crash recovery as applicable, indexes, vacuum, relation lifecycle, scans, locking, statistics, and executor expectations. The table-AM chapter should therefore be treated as the contract, while built-in heap code is an implementation reference rather than a minimal template.[19]

17.2 Index access methods

Index access methods implement independent index relation types. The core server calls an IndexAmRoutine containing callbacks for build, insertion, scans, uniqueness checks where supported, vacuum, costing, parallel behaviors, and other capabilities. PostgreSQL's built-in B-tree, GiST, SP-GiST, GIN, BRIN, and hash indexes are separate access methods behind this interface.[19] 

PG_FUNCTION_INFO_V1(my_indexam_handler);

Datum
my_indexam_handler(PG_FUNCTION_ARGS)
{
    IndexAmRoutine *am = makeNode(IndexAmRoutine);

    am->amstrategies = 1;
    am->amsupport = 1;

    /* Supply ambuild, ambuildempty, aminsert,
       ambeginscan, amrescan, amgettuple/amgetbitmap,
       amendscan, amcostestimate, vacuum callbacks, etc. */

    PG_RETURN_POINTER(am);
}

Index methods are also tied to operator classes and operator families, which map SQL operators and support functions to access-method strategy numbers. That mapping is how the planner knows that a predicate can be implemented by a particular custom index.[18][19]

18. Foreign data wrappers

An FDW makes an external data source look like a PostgreSQL foreign table. The FDW supplies a handler returning an FdwRoutine of planner, executor, update, explain, analyze, import, parallel, and optional asynchronous callbacks. The core planner asks the FDW to estimate and generate foreign paths; the executor later invokes callbacks to start, iterate, rescan, and end the foreign scan.[20]

18.1 Minimal structural skeleton

#include "postgres.h"
#include "fmgr.h"
#include "foreign/fdwapi.h"

PG_MODULE_MAGIC;
PG_FUNCTION_INFO_V1(my_fdw_handler);

Datum
my_fdw_handler(PG_FUNCTION_ARGS)
{
    FdwRoutine *r = makeNode(FdwRoutine);

    r->GetForeignRelSize  = myGetForeignRelSize;
    r->GetForeignPaths    = myGetForeignPaths;
    r->GetForeignPlan     = myGetForeignPlan;
    r->BeginForeignScan   = myBeginForeignScan;
    r->IterateForeignScan = myIterateForeignScan;
    r->ReScanForeignScan  = myReScanForeignScan;
    r->EndForeignScan     = myEndForeignScan;

    PG_RETURN_POINTER(r);
}

The planner callbacks are where an FDW reports row estimates, costs, parameterization, pushdown opportunities, path ordering, and other information. A sophisticated FDW can push filters, joins, aggregation, ordering, or limits to the remote system when semantics permit, reducing data transfer and local execution work.[20] 

CREATE FUNCTION my_fdw_handler()
RETURNS fdw_handler
AS 'MODULE_PATHNAME'
LANGUAGE C STRICT;

CREATE FOREIGN DATA WRAPPER my_fdw
HANDLER my_fdw_handler;

CREATE SERVER remote_system
FOREIGN DATA WRAPPER my_fdw
OPTIONS (endpoint 'https://example.internal');

CREATE FOREIGN TABLE remote_orders(
    id bigint,
    total numeric
)
SERVER remote_system
OPTIONS (resource 'orders');

19. Extension development

An extension packages related SQL objects and optional shared-library code into a unit that can be installed with CREATE EXTENSION. PostgreSQL uses an extension control file, one or more versioned SQL scripts, and optional dynamically loadable libraries. PGXS provides makefile infrastructure for building many server extensions against an installed PostgreSQL development environment.[18][22]

19.1 Small complete extension layout

my_math/
├── Makefile
├── my_math.control
├── my_math--1.0.sql
└── my_math.c

my_math.c

#include "postgres.h"
#include "fmgr.h"

PG_MODULE_MAGIC;

PG_FUNCTION_INFO_V1(int8_square);

Datum
int8_square(PG_FUNCTION_ARGS)
{
    int64 x = PG_GETARG_INT64(0);

    if (x != 0 && (x > PG_INT64_MAX / x || x < PG_INT64_MIN / x))
        ereport(ERROR,
                (errcode(ERRCODE_NUMERIC_VALUE_OUT_OF_RANGE),
                 errmsg("bigint square overflow")));

    PG_RETURN_INT64(x * x);
}

my_math--1.0.sql

CREATE FUNCTION int8_square(bigint)
RETURNS bigint
AS 'MODULE_PATHNAME', 'int8_square'
LANGUAGE C
IMMUTABLE
STRICT
PARALLEL SAFE;

my_math.control

comment = 'Small C extension example'
default_version = '1.0'
module_pathname = '$libdir/my_math'
relocatable = true

Makefile

EXTENSION = my_math
MODULES = my_math
DATA = my_math--1.0.sql

PG_CONFIG = pg_config
PGXS := $(shell $(PG_CONFIG) --pgxs)
include $(PGXS)

Build and install

make
sudo make install

psql -d postgres -c "CREATE EXTENSION my_math"
psql -d postgres -c "SELECT int8_square(12)"

PGXS standardizes common extension build/install rules but is not intended as a universal build system. PostgreSQL also supports regression-test integration through PGXS variables and versioned update scripts so extension upgrades can be expressed as catalog changes instead of destructive reinstallations.[22]

19.2 Safety model

A C extension executes in the PostgreSQL server's address space and privileges. Memory corruption, invalid pointers, incorrect varlena handling, unsafe signal behavior, or broken lock/WAL protocols can crash a backend or the server and can corrupt data. That power is precisely why base-type creation, background workers, access methods, and similar facilities are treated as privileged extension points.[18][15][21]

20. PostgreSQL C APIs

20.1 Function manager (fmgr)

Dynamically loaded SQL-callable C functions use PostgreSQL's version-1 function-manager convention. A function has the C signature Datum name(PG_FUNCTION_ARGS), is announced with PG_FUNCTION_INFO_V1(name), reads arguments through PG_GETARG_* macros, and returns through PG_RETURN_* macros. Datum is the generic server value carrier used by this interface.[21] 

PG_FUNCTION_INFO_V1(add_one);

Datum
add_one(PG_FUNCTION_ARGS)
{
    int32 arg = PG_GETARG_INT32(0);
    PG_RETURN_INT32(arg + 1);
}

20.2 PG_MODULE_MAGIC

Loadable PostgreSQL modules normally declare PG_MODULE_MAGIC. The magic block allows the server to reject modules compiled for an incompatible PostgreSQL server interface rather than loading arbitrary incompatible code.[21]

20.3 SPI: call SQL from server C code

The Server Programming Interface (SPI) lets C functions and server modules invoke PostgreSQL's parser, planner, and executor. Typical code connects to SPI, executes or prepares SQL, inspects returned tuple tables, and then disconnects. SPI also establishes memory-lifetime rules for allocations made while connected.[21] 

#include "executor/spi.h"

if (SPI_connect() != SPI_OK_CONNECT)
    elog(ERROR, "SPI_connect failed");

int rc = SPI_execute(
    "SELECT id, total FROM orders WHERE total > 1000",
    true,   /* read_only */
    0       /* no row limit */
);

if (rc != SPI_OK_SELECT)
    elog(ERROR, "SPI_execute failed: %d", rc);

/* SPI_processed rows are available through SPI_tuptable. */

SPI_finish();

20.4 Error reporting

Server C code uses PostgreSQL's error-reporting infrastructure rather than ordinary application-level error handling. ereport()/elog() can abort the current transaction through PostgreSQL's non-local error machinery, so C extensions must use PostgreSQL cleanup patterns and resource owners rather than assuming a normal C return path after an error.[21]

20.5 Hooks and callbacks

PostgreSQL exposes hooks at selected planner, executor, utility, authentication, shared-memory, and other integration points. Hooks are commonly implemented as global function-pointer variables; extensions save the previous hook, install their own, and optionally chain. Because the server contains many symbols that were not designed as stable plugin contracts, PostgreSQL 18's API/ABI guidance recommends favoring established interfaces and planning for major-version recompilation and adaptation when using deeper internals.[21]

20.6 Shared memory and LWLocks

Extensions loaded early enough can request shared-memory space and named lightweight locks, then attach to that shared state in server processes. Correct shared-memory code must define initialization ownership, concurrency protocols, process lifetime, error behavior, and versioning carefully; ordinary process-local globals are not a substitute for explicitly shared state.[21]

21. Runtime inspection lab

PostgreSQL exposes query/runtime internals through EXPLAIN, system views, memory-context views, WAL tooling, and supplied inspection modules. In this article, the useful first pass is to correlate a plan tree with executor timing, buffer counters, locks, memory contexts, and WAL position; raw heap-page decoding belongs in the companion storage article.[11][14][23]

21.1 Trace a plan through runtime subsystems

EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT c.id, count(*) AS orders
FROM customers AS c
JOIN orders AS o ON o.customer_id = c.id
WHERE c.region = 'east'
GROUP BY c.id
ORDER BY orders DESC
LIMIT 20;

SELECT pid, locktype, relation::regclass, mode, granted
FROM pg_locks
WHERE pid = pg_backend_pid()
ORDER BY locktype, mode;

Read the plan twice: first as a planner artifact, where estimated row counts and costs explain why this shape was chosen, and then as an executor trace, where actual rows, timing, and buffer counters show what happened when each node ran. Lock and memory views give the same experiment a backend-runtime dimension.[8][11][14]

21.2 Keep page inspection in the storage lane

Use pageinspect, pg_buffercache, pg_walinspect, pg_freespacemap, and pg_visibility when the question is about physical pages, buffer residency, WAL records, or heap-storage side structures. The companion article demonstrates that workflow directly so this article can stay focused on planner, executor, extension, and runtime APIs.[23]

21.3 Build PostgreSQL for source-level debugging

git clone https://git.postgresql.org/git/postgresql.git
cd postgresql
git checkout REL_18_STABLE

./configure --enable-debug --enable-cassert
make -j"$(nproc)"
make check

The official source repository documentation explains obtaining PostgreSQL with Git. Debug and assertion-enabled builds are appropriate for development and source tracing rather than production benchmarking because assertions and debug options alter runtime behavior and overhead.[3]

Suggested reading path: start with the official “Overview of PostgreSQL Internals,” then read execMain.c and planner.c, then use the companion storage article when you need to trace heap pages through bufmgr.c, smgr.c, WAL, and tuple visibility. After that, move into access-method or logical-decoding extension APIs.
