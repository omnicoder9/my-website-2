PostgreSQL Database Objects

A technical guide to PostgreSQL’s object model: tables, views, materialized views, indexes, sequences, schemas, functions, procedures, triggers, types, domains, operators, aggregates, collations, extensions, foreign-data wrappers, publications and subscriptions—with catalogs, dependencies, ownership, namespaces, and practical DDL examples.

Technical article • PostgreSQL 18.6 baseline • Updated 16 September 2026 • Vancouver-style references

Abstract

PostgreSQL is more than a collection of tables. A database contains a graph of named objects—relations, executable routines, type-system objects, operators, collations, extensions, foreign-data wrappers and replication definitions—linked through ownership, schema namespaces, privileges and dependency metadata. Understanding those object boundaries is essential for safe schema evolution, privilege design, extension packaging and automated deployment.[1]-[4]

Several object kinds are relation-like and share one schema namespace: tables, sequences, indexes, views, materialized views and foreign tables cannot reuse the same name within a schema. Functions and procedures are represented in pg_proc and can be overloaded by argument signature; types and domains are represented in pg_type; schemas themselves live in pg_namespace. PostgreSQL's system catalogs make this object model inspectable through ordinary SQL.[2][5]-[8]

Many higher-level objects are definitions over other objects rather than standalone storage. A normal view stores a query definition and is rewritten into underlying relations at planning time; a materialized view stores query results and can be refreshed; an index stores an auxiliary access structure; a sequence stores independent state for number generation; a trigger binds event timing to a trigger function; an aggregate composes transition/combine/final functions; and an extension packages multiple dependent objects as one installable/upgradable unit.[9]-[15]

PostgreSQL also treats data federation and logical replication as database objects. A foreign-data wrapper defines the API implementation for an external source, servers and user mappings supply endpoint/credential metadata, and foreign tables expose remote objects through SQL. Publications define sets of table changes to emit; subscriptions define downstream connections to one or more publications and normally create replication-slot state on the publisher.[16]-[21]

1. The PostgreSQL object model

PostgreSQL stores object definitions in system catalogs and connects those definitions through OIDs and dependency records. Most DDL is catalog manipulation plus any necessary physical work: CREATE TABLE creates relation/type metadata and storage; CREATE VIEW creates relation metadata plus a rewrite rule; CREATE FUNCTION creates a pg_proc entry and associated dependencies; CREATE EXTENSION records an extension object and associates its member objects with it.[4][5][22]

database | +-- schemas (pg_namespace) | +-- relation namespace | tables / indexes / sequences / views / | materialized views / foreign tables | +-- routines | functions / procedures | +-- type system | base/composite/enum/range types / domains | +-- executable semantics | operators / aggregates / triggers | +-- locale semantics | collations | +-- extensibility | extensions / FDWs / servers / user mappings | +-- logical replication publications / subscriptions

Some objects are database-local while a few object types such as roles are cluster-wide. A client connection operates inside one database, and schemas organize names within that database rather than crossing database boundaries.[2]

2. Schemas, namespaces and naming rules

A schema is PostgreSQL's principal namespace container. The same name can exist in different schemas, and qualified names such as billing.invoice remove ambiguity. Schemas cannot be nested.[2]

CREATE SCHEMA billing;

CREATE TABLE billing.invoice (...);
CREATE TABLE archive.invoice (...);

PostgreSQL has multiple logical namespaces inside each schema. Tables, sequences, indexes, views, materialized views and foreign tables share the relation namespace and therefore cannot collide by name. Types have another namespace; routines can be overloaded; operators are distinguished by name and operand types.[2][23]

2.1 search_path

SHOW search_path;

SET search_path = app, shared, pg_catalog;

When an object name is not schema-qualified, PostgreSQL searches schemas according to search_path. The first existing schema in the effective path where the user has appropriate privilege is also the default creation location for many unqualified objects. Because adding a schema to search_path implicitly trusts users who can create objects there, secure environments should control CREATE privileges carefully.[2]

3. Dependency tracking

PostgreSQL records dependencies so that objects cannot normally be dropped while dependent objects still require them. The default drop behavior is effectively RESTRICT; CASCADE recursively removes dependent objects or dependent subobjects such as constraints.[3]

DROP TABLE products;
-- ERROR: cannot drop table because other objects depend on it

DROP TABLE products CASCADE;

3.1 Function-body dependency nuance

Dependency discovery depends on how an SQL routine body is defined. If an SQL-language function/procedure body is supplied as a string literal, PostgreSQL tracks dependencies visible from the routine signature and other catalog-level properties but cannot necessarily discover table references hidden inside the string. SQL-standard BEGIN ATOMIC bodies are parsed when the routine is defined, allowing parser-visible dependencies to be recorded.[3]

CREATE FUNCTION app.lookup_note(app.color)
RETURNS text
LANGUAGE SQL
BEGIN ATOMIC
    SELECT note
    FROM app.color_note
    WHERE color = $1;
END;
Schema refactoring implication: do not assume every routine dependency is tracked if routine bodies are stored as opaque strings. For strongly managed schemas, parsed SQL-standard bodies can provide better dependency metadata.

4. Ownership and privileges

Most PostgreSQL objects have an owner. The creating role generally becomes owner unless DDL allows or specifies another owner. Ownership conveys implicit authority to alter/drop the object and grant privileges, while object-specific privileges determine what other roles can do. Schema USAGE controls name lookup/access and schema CREATE controls creation in that namespace.[2][24]

ALTER TABLE app.orders OWNER TO app_owner;

GRANT SELECT, INSERT, UPDATE
ON app.orders
TO app_runtime;

Extensions complicate ownership slightly because an extension object owns membership of its contained objects from PostgreSQL's dependency perspective, while the contained objects still have their ordinary SQL owners. Dropping an extension normally drops its member objects as an extension-level operation.[14][22]

5. Tables

A table is PostgreSQL's primary persistent row-storage object. CREATE TABLE defines columns, data types, defaults/generated expressions, constraints, optional partitioning, storage method, tablespace and persistence class. Ordinary, temporary and unlogged tables have different durability/lifetime semantics.[25]

CREATE TABLE app.orders (
    order_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id bigint NOT NULL
        REFERENCES app.customer(customer_id),
    status text NOT NULL
        CHECK (status IN ('open','paid','cancelled')),
    total_amount numeric(14,2) NOT NULL
        CHECK (total_amount >= 0),
    created_at timestamptz NOT NULL DEFAULT now()
);

5.1 Table creates a composite type

Creating a table also creates a composite row type with the same name in the type namespace. That row type can be used as a routine argument/result or as a field type in other constructs, which is one reason the table and type namespaces interact even though they are not the same namespace.[25]

CREATE FUNCTION app.order_total(o app.orders)
RETURNS numeric
LANGUAGE SQL
IMMUTABLE
RETURN o.total_amount;

5.2 Temporary and unlogged tables

Temporary tables live in a session-specific temporary schema and are automatically dropped at session end (or earlier according to ON COMMIT). Unlogged tables bypass normal WAL logging for table data, making them faster for some workloads but not crash-safe and not replicated to physical standbys in the same way as ordinary logged relations.[25]

6. Views

A normal view stores a query definition rather than materialized rows. PostgreSQL implements views through the rewrite system: a query referencing the view is transformed so the underlying relations and predicates can be planned together with the outer query.[9][26]

CREATE VIEW reporting.open_orders AS
SELECT
    o.order_id,
    o.customer_id,
    o.total_amount,
    o.created_at
FROM app.orders AS o
WHERE o.status = 'open';
SELECT *
FROM reporting.open_orders
WHERE customer_id = 42;

6.1 Security and API boundary

Views are frequently used to expose stable interfaces over underlying tables, hide columns, encapsulate joins, or apply security boundaries. PostgreSQL supports options such as security_barrier and security_invoker for cases where evaluation order or invoker privileges matter.[27]

6.2 Updatable views

Simple views can be automatically updatable when PostgreSQL can map modifications unambiguously to one base relation. More complex view-write behavior can be implemented with rules or INSTEAD OF triggers.[27]

7. Materialized views

A materialized view stores the result of a query in table-like physical storage while retaining the defining query so the contents can be regenerated with REFRESH MATERIALIZED VIEW. Unlike a normal view, querying a materialized view reads its stored rows directly rather than rerunning the defining query.[10][28]

CREATE MATERIALIZED VIEW reporting.daily_sales AS
SELECT
    date_trunc('day', created_at) AS sales_day,
    count(*) AS orders,
    sum(total_amount) AS revenue
FROM app.orders
WHERE status = 'paid'
GROUP BY 1
WITH DATA;
CREATE UNIQUE INDEX daily_sales_day_uq
ON reporting.daily_sales(sales_day);

REFRESH MATERIALIZED VIEW CONCURRENTLY
reporting.daily_sales;

REFRESH ... CONCURRENTLY permits concurrent reads during refresh but requires a qualifying unique index over ordinary columns and has additional restrictions. Materialized views are useful when recomputation cost is high and some staleness is acceptable.[29]

8. Indexes

An index is a relation-like object that stores an auxiliary access structure for a table or materialized view. PostgreSQL supports B-tree, Hash, GiST, SP-GiST, GIN and BRIN built-in access methods. Indexes can also enforce uniqueness, implement exclusion constraints, provide ordered access and support index-only scans.[30][31]

CREATE INDEX orders_customer_created_idx
ON app.orders(customer_id, created_at DESC)
INCLUDE(order_id, total_amount)
WHERE status = 'open';

Indexes share the relation namespace with tables/views/sequences and are represented in pg_class with relation kind i (ordinary index) or I (partitioned index), while index-specific metadata is in pg_index.[5][32]

9. Sequences

A sequence is a special single-row relation that generates numeric values independently of ordinary transactional rollback semantics. CREATE SEQUENCE controls start, increment, minimum/maximum, cycling, cache and data type. Sequence state is commonly consumed through nextval, currval, and setval.[11][33]

CREATE SEQUENCE app.invoice_no_seq
    AS bigint
    START WITH 100000
    INCREMENT BY 1
    CACHE 100;

SELECT nextval('app.invoice_no_seq');

9.1 Identity columns

GENERATED ... AS IDENTITY is normally preferable to manually wiring a sequence when the requirement is “this table column receives generated numeric identities,” because PostgreSQL creates/manages the associated sequence relationship as part of the column definition.[25]

9.2 Gaps are normal

Sequence values are designed for concurrent number allocation, not gapless transactional numbering. Values consumed by transactions that later abort are not automatically returned to the sequence; cached values and crashes can also create gaps. Do not use a normal sequence as an audit requirement for gapless legal numbering without a separate concurrency design.[33]

10. Schemas

A schema is a named namespace inside one database. Schemas organize objects, separate third-party/application namespaces and provide privilege boundaries. The same object name can exist in different schemas, and the search_path controls resolution of unqualified names.[2][34]

CREATE SCHEMA app AUTHORIZATION app_owner;

GRANT USAGE ON SCHEMA app TO app_runtime;
GRANT CREATE ON SCHEMA app TO app_deployer;

The public schema exists by default in new databases unless template/customization changes that. Modern privilege defaults and deployment policies should still be reviewed explicitly rather than assuming every role should be able to create objects in shared namespaces.[2]

10.1 Schema-qualified DDL

CREATE TABLE app.customer (...);
CREATE VIEW reporting.customer_summary AS ...;
CREATE FUNCTION app.normalize_email(text) RETURNS text ...;

Schema qualification improves migration determinism and security by reducing dependence on session-specific search_path configuration.

11. Functions

A PostgreSQL function is a routine invoked in expressions, queries, defaults, indexes, constraints and other SQL contexts. Functions can return scalar, composite, set or table-shaped results, and can be implemented in SQL, PL/pgSQL, C, trusted/untrusted procedural languages and extension-provided languages.[12][35]

CREATE FUNCTION app.net_amount(
    gross numeric,
    discount numeric
)
RETURNS numeric
LANGUAGE SQL
IMMUTABLE
STRICT
RETURN gross - discount;

11.1 Volatility

Function volatility categories—IMMUTABLE, STABLE and VOLATILE—tell the optimizer what assumptions it may make about repeated calls. Volatility is a semantic promise and must be declared correctly; expression indexes require immutable functions because stored index keys must remain valid.[35][36]

11.2 Security definer

CREATE FUNCTION admin.rotate_api_key(p_user_id bigint)
RETURNS void
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = pg_catalog, admin, pg_temp
AS $$
BEGIN
    UPDATE admin.api_key
    SET revoked_at = clock_timestamp()
    WHERE user_id = p_user_id
      AND revoked_at IS NULL;
END
$$;

SECURITY DEFINER functions execute with the function owner's privileges rather than the caller's. PostgreSQL documents the need to secure search_path and privileges carefully because malicious objects placed in writable schemas can otherwise alter name resolution.[35]

11.3 Overloading

Functions can share a name when argument signatures differ. PostgreSQL resolves a call by schema search, argument count/types, implicit casts and type-resolution rules. This is powerful but can make ambiguous calls or unsafe search-path exposure more likely when overloaded APIs are designed carelessly.[37]

12. Procedures

Procedures resemble functions but are invoked with CALL rather than used as expression values. A key distinction is transaction control: procedures invoked by CALL in the appropriate top-level context can execute COMMIT and ROLLBACK; ordinary functions cannot end the surrounding transaction.[13][38]

CREATE PROCEDURE maintenance.archive_old_orders(
    cutoff timestamptz
)
LANGUAGE plpgsql
AS $$
BEGIN
    INSERT INTO archive.orders
    SELECT *
    FROM app.orders
    WHERE created_at < cutoff;

    DELETE FROM app.orders
    WHERE created_at < cutoff;
END
$$;

CALL maintenance.archive_old_orders(
    now() - interval '2 years'
);

Choose a function when the routine naturally behaves like a value-producing SQL operation and must compose in queries. Choose a procedure when command-style invocation and, where appropriate, internal transaction control better match the API.

13. Triggers

A trigger binds a trigger function to table/view events such as INSERT, UPDATE, DELETE or TRUNCATE. PostgreSQL supports BEFORE, AFTER and view-only INSTEAD OF triggers, at row or statement granularity where applicable. Constraint triggers provide deferrable timing semantics for specialized integrity checks.[14][39]

CREATE FUNCTION audit.capture_order_change()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    INSERT INTO audit.order_event(
        operation,
        order_id,
        changed_at
    )
    VALUES (
        TG_OP,
        COALESCE(NEW.order_id, OLD.order_id),
        clock_timestamp()
    );

    RETURN COALESCE(NEW, OLD);
END
$$;

CREATE TRIGGER orders_audit_trg
AFTER INSERT OR UPDATE OR DELETE
ON app.orders
FOR EACH ROW
EXECUTE FUNCTION audit.capture_order_change();

13.1 Transition tables

Statement-level triggers can use transition relations through REFERENCING OLD TABLE/NEW TABLE in supported cases, allowing one trigger invocation to inspect all rows affected by a statement instead of firing row-by-row logic.[14]

Trigger design principle: triggers are powerful for invariants/auditing close to the data, but hidden side effects make write behavior less obvious. Keep them small, deterministic and documented, and avoid synchronous remote calls from trigger execution paths.

14. User-defined types

CREATE TYPE supports several type families: composite types, enumerated types, range types, multirange-related definitions and fully custom base types implemented with input/output functions. PostgreSQL's extensible type system is central to its ability to add operators, index operator classes and domain-specific semantics.[15][40]

14.1 Enum

CREATE TYPE app.order_state AS ENUM (
    'open',
    'paid',
    'cancelled'
);

14.2 Composite type

CREATE TYPE app.money_amount AS (
    amount numeric(18,2),
    currency char(3)
);

14.3 Range type

CREATE TYPE scheduling.float8range_custom AS RANGE (
    subtype = float8,
    subtype_diff = float8mi
);

Table row types are automatically generated composite types, while standalone composite types define structure without creating storage of their own.[15][25]

15. Domains

A domain creates a distinct named type based on an existing underlying type plus optional default, NOT NULL and CHECK constraints. Domains are useful when the same scalar validation rule should be reused across many columns and routine signatures.[16]

CREATE DOMAIN app.email_address AS text
CHECK (
    VALUE = lower(VALUE)
    AND position('@' in VALUE) > 1
);
CREATE TABLE app.contact (
    contact_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email app.email_address NOT NULL
);

15.1 Domain versus table constraint

A domain constraint applies wherever a domain value is formed, while a table constraint applies in the context of one table row. Cross-column rules therefore belong on tables rather than domains. Domain checks should depend only on the input value and immutable behavior so existing stored values do not silently become invalid after external state changes.[16]

16. Operators

PostgreSQL operators are named syntactic objects backed by functions. CREATE OPERATOR associates an operator token with argument/result types, an implementation procedure and optional optimizer metadata such as commutator, negator and selectivity functions. Operators are a major extension point used by custom types and index operator classes.[17][41]

CREATE FUNCTION app.int_distance(integer, integer)
RETURNS integer
LANGUAGE SQL
IMMUTABLE STRICT
RETURN abs($1 - $2);

CREATE OPERATOR app.<-> (
    LEFTARG = integer,
    RIGHTARG = integer,
    FUNCTION = app.int_distance
);

Creating an operator does not automatically make it indexable. Index use requires an appropriate operator class/family that tells a particular access method how the operator fits its strategy/support-function semantics.[41]

17. Aggregates

An aggregate is a routine-like object that reduces many input rows to one result per group. PostgreSQL implements aggregates from component functions: a transition function maintains state, an optional final function converts state to output, and optional combine/serialization/deserialization functions enable partial and parallel aggregation. Ordered-set and hypothetical-set aggregates have additional direct/ordered argument semantics.[18][42]

CREATE FUNCTION app.sum_squares_sfunc(
    state numeric,
    value numeric
)
RETURNS numeric
LANGUAGE SQL
IMMUTABLE
RETURN state + value * value;

CREATE AGGREGATE app.sum_squares(numeric) (
    SFUNC = app.sum_squares_sfunc,
    STYPE = numeric,
    INITCOND = '0'
);
SELECT customer_id,
       app.sum_squares(total_amount)
FROM app.orders
GROUP BY customer_id;

Aggregate definitions live in pg_proc as routine objects plus aggregate-specific rows in pg_aggregate that reference transition/final/combine functions and state types.[6][43]

18. Collations

A collation defines locale-dependent ordering and character-classification/comparison behavior for collatable data types. PostgreSQL can use libc and ICU providers (depending on build/platform), plus built-in collations. Collation choice affects comparisons, sorting and indexes over collatable strings, so changing collation semantics can require index rebuilds.[19][44]

CREATE COLLATION app.en_ci (
    provider = icu,
    locale = 'en-u-ks-level2',
    deterministic = false
);
CREATE TABLE app.person (
    display_name text COLLATE app.en_ci
);

18.1 Deterministic versus nondeterministic

Deterministic collations require byte-identical strings for equality after provider comparison, while nondeterministic ICU collations can support comparison semantics such as case- or accent-insensitivity. Nondeterministic collations have restrictions/behavioral tradeoffs and should be chosen intentionally for the application's equality semantics.[44]

19. Extensions

An extension packages a set of SQL objects so PostgreSQL can install, version, update and remove them as one logical unit. CREATE EXTENSION executes the extension's installation script and records membership/version/schema metadata in pg_extension. Extensions can contain SQL objects, C functions, custom types, operators, access methods and many other object kinds.[20][22][45]

CREATE EXTENSION IF NOT EXISTS pg_trgm;

SELECT extname, extversion, extnamespace::regnamespace
FROM pg_extension
ORDER BY extname;

19.1 Upgrade path

ALTER EXTENSION my_extension
UPDATE TO '2.0';

Extension authors provide control files and update scripts describing valid version transitions. Member objects should generally be managed through the extension rather than individually dropped or altered in ways that break extension expectations.[45]

19.2 Trusted extensions

Extensions can be marked trusted by their control metadata, allowing non-superusers with appropriate database privileges to install them under PostgreSQL's trusted-extension rules. Whether an extension is safe to trust is a packaging/security decision, not merely a SQL syntax property.[20]

20. Foreign-data wrappers

A foreign-data wrapper (FDW) is a database object representing code that knows how PostgreSQL should access an external data source. The SQL/MED object model then layers foreign servers, user mappings and foreign tables on top of the wrapper. PostgreSQL ships postgres_fdw as an extension for accessing remote PostgreSQL databases.[21][46]

CREATE EXTENSION postgres_fdw;

CREATE SERVER reporting_remote
FOREIGN DATA WRAPPER postgres_fdw
OPTIONS (
    host 'db.internal',
    port '5432',
    dbname 'reporting'
);

The FDW object itself names handler/validator functions that implement the wrapper. Server options describe a remote endpoint, and user mappings associate local PostgreSQL roles with remote authentication options.[21][47]

21. Servers, user mappings and foreign tables

21.1 User mapping

CREATE USER MAPPING FOR app_runtime
SERVER reporting_remote
OPTIONS (
    user 'report_reader',
    password 'secret'
);

21.2 Foreign table

CREATE FOREIGN TABLE integration.remote_customer (
    customer_id bigint NOT NULL,
    name text,
    created_at timestamptz
)
SERVER reporting_remote
OPTIONS (
    schema_name 'public',
    table_name 'customer'
);

A foreign table has local PostgreSQL column/type metadata but no local heap storage for its remote rows. The FDW decides how scans, joins, filters, aggregates and writes can be pushed down or executed remotely. With postgres_fdw, matching local/remote data types and collations is strongly recommended to avoid semantic differences in remotely evaluated expressions.[46][48]

21.3 Import foreign schema

IMPORT FOREIGN SCHEMA public
LIMIT TO (customer, invoice)
FROM SERVER reporting_remote
INTO integration;

IMPORT FOREIGN SCHEMA lets an FDW generate local foreign-table definitions from a remote schema when the wrapper supports it.[49]

22. Publications

A publication is a logical-replication object in one database that defines a set of table changes intended for subscribers. A publication can include named tables, all tables in named schemas, or all tables in the database. It can publish selected operation types—INSERT, UPDATE, DELETE, and TRUNCATE—and PostgreSQL 18 supports row filters and column lists for eligible publication definitions.[50][52]

CREATE PUBLICATION sales_pub
FOR TABLE app.orders (
    order_id,
    customer_id,
    status,
    total_amount,
    created_at
)
WHERE (status IN ('open', 'paid'))
WITH (
    publish = 'insert,update,delete'
);

Creating a publication does not start data movement. It defines what changes a future subscriber can request. A table can participate in multiple publications, and publications are not schemas—they do not change normal query visibility or table access.[50]

22.1 Replica identity

For published UPDATE and DELETE, PostgreSQL needs a replica identity that lets the subscriber identify the target row. A primary key is the default replica identity when present; tables without an appropriate identity may need REPLICA IDENTITY USING INDEX or FULL, with different overhead/semantic tradeoffs.[50]

ALTER TABLE app.orders
REPLICA IDENTITY USING INDEX orders_pkey;

22.2 Publication scope restrictions

Publications contain persistent base tables and partitioned tables, not ordinary views, materialized views, foreign tables, temporary tables, or unlogged tables. Schema-level publications dynamically include eligible existing and future tables in the schema.[52]

23. Subscriptions

A subscription is the downstream logical-replication object. It specifies a connection to a publisher and one or more publication names. Creating a subscription normally creates a replication slot on the publisher and, when committed, starts logical-replication worker activity unless the subscription is disabled.[51][53]

CREATE SUBSCRIPTION sales_sub
CONNECTION 'host=publisher.internal port=5432 dbname=sales user=repl'
PUBLICATION sales_pub
WITH (
    copy_data = true,
    create_slot = true,
    enabled = true
);

Subscriptions are database-local and stored in pg_subscription; connection information can contain sensitive credentials and catalog visibility is restricted accordingly. One subscriber database can have multiple subscriptions and can itself publish data onward.[51][55]

23.1 Schema is not replicated automatically

Built-in logical replication primarily replicates table data changes, not arbitrary DDL. Subscriber tables must normally exist with compatible schemas before data synchronization/apply. Production logical-replication designs therefore require a separate schema-migration discipline.[51]

23.2 Operational object lifecycle

ALTER SUBSCRIPTION sales_sub DISABLE;

ALTER SUBSCRIPTION sales_sub
REFRESH PUBLICATION;

DROP SUBSCRIPTION sales_sub;

Dropping or disabling subscriptions has replication-slot implications. Operators should understand slot ownership and cleanup so abandoned subscriptions do not retain WAL indefinitely on publishers.

24. Inspecting database objects through system catalogs

PostgreSQL's system catalogs make the object model queryable. While information_schema offers standards-oriented views, PostgreSQL-specific catalogs expose richer implementation metadata needed for administration, extensions, dependency analysis and replication inspection.[4]

24.1 Relation-like objects

SELECT
    n.nspname AS schema_name,
    c.relname,
    c.relkind,
    c.relpersistence,
    c.relowner::regrole AS owner,
    c.relpages,
    c.reltuples
FROM pg_class AS c
JOIN pg_namespace AS n
  ON n.oid = c.relnamespace
WHERE n.nspname NOT IN ('pg_catalog', 'information_schema')
ORDER BY n.nspname, c.relkind, c.relname;
pg_class.relkindRepresentative object

pg_class covers relation-like object kinds, which is why several apparently different SQL objects share relation naming and many relation-oriented system functions.[5]

24.2 Functions, procedures and aggregates

SELECT
    n.nspname,
    p.proname,
    p.prokind,
    pg_get_function_identity_arguments(p.oid) AS identity_args,
    pg_get_function_result(p.oid) AS result,
    p.provolatile,
    p.proparallel,
    p.prosecdef
FROM pg_proc AS p
JOIN pg_namespace AS n
  ON n.oid = p.pronamespace
WHERE n.nspname = 'app'
ORDER BY p.proname, identity_args;

pg_proc.prokind distinguishes ordinary functions, procedures, aggregates and window functions, demonstrating that these SQL-level object families share core routine catalog infrastructure.[6]

24.3 Types and domains

SELECT
    n.nspname,
    t.typname,
    t.typtype,
    t.typcategory,
    t.typbasetype::regtype AS base_type
FROM pg_type AS t
JOIN pg_namespace AS n
  ON n.oid = t.typnamespace
WHERE n.nspname = 'app'
ORDER BY t.typname;

pg_type.typtype distinguishes base, composite, domain, enum, pseudo and range-related type categories, while domains reference their underlying type in typbasetype.[7]

24.4 Extensions

SELECT
    extname,
    extversion,
    extnamespace::regnamespace AS schema,
    extowner::regrole AS owner
FROM pg_extension
ORDER BY extname;

24.5 Publications and subscriptions

SELECT
    pubname,
    pubowner::regrole,
    puballtables,
    pubinsert,
    pubupdate,
    pubdelete,
    pubtruncate
FROM pg_publication
ORDER BY pubname;

SELECT
    subname,
    subowner::regrole,
    subenabled,
    subslotname,
    subpublications
FROM pg_subscription
ORDER BY subname;

24.6 Dependency graph

SELECT
    d.classid::regclass AS dependent_catalog,
    d.objid,
    d.refclassid::regclass AS referenced_catalog,
    d.refobjid,
    d.deptype
FROM pg_depend AS d
WHERE d.objid = 'reporting.open_orders'::regclass;

pg_depend records many inter-object dependencies used by DDL to enforce RESTRICT/CASCADE behavior and automatic dependency rules. Extension membership is also represented through dependency machinery.[3][56]

25. Object lifecycle: create, alter, rename, move, drop

Most PostgreSQL object types follow a common lifecycle: CREATE, object-specific ALTER, optional rename/schema/owner changes, privilege grants/revokes, and DROP. Dependency tracking ensures operations that would invalidate dependent objects are either rejected or made explicit with CASCADE.[3]

25.1 Move an object between schemas

ALTER TABLE public.orders
SET SCHEMA app;

25.2 Rename without breaking OID dependencies

ALTER TABLE app.orders
RENAME TO customer_order;

Many dependencies are recorded by internal object identity rather than textual name, so rename operations preserve dependency links. Application SQL that hard-codes old names still needs to be migrated.

25.3 RESTRICT before CASCADE

DROP TYPE app.order_state;
-- inspect DETAIL

-- only after reviewing consequences:
DROP TYPE app.order_state CASCADE;

A useful operational practice is to attempt destructive DDL without CASCADE first and inspect PostgreSQL's dependency details before deciding whether cascading removal is actually intended.[3]

25.4 Transactional DDL

Most PostgreSQL catalog DDL participates in transactions, enabling groups of schema changes to commit or roll back atomically. Some commands—particularly certain concurrent index and replication operations—have transaction-block restrictions and need dedicated migration handling.

26. Object-design guidelines

26.1 Use schemas as stable module boundaries

Organize application, reporting, integration and extension namespaces intentionally. Prefer schema-qualified references in deployment/security-sensitive code and avoid granting arbitrary users CREATE in schemas that appear on privileged roles' search_path.[2]

26.2 Put invariants at the lowest appropriate object layer

Use table constraints for row/cross-column integrity, domains for reusable scalar constraints, unique/exclusion indexes for set-level uniqueness/exclusion, and triggers only when declarative constraints cannot express the rule cleanly.

26.3 Separate logical interfaces from physical optimizations

Views/functions can present stable APIs while indexes/materialized views provide physical performance strategies beneath them. This separation allows physical redesign without forcing every application to know storage details.

26.4 Make routine semantics explicit

Declare function volatility, strictness, parallel safety and security mode accurately. Routine attributes are optimizer/security contracts, not documentation comments.[35]

26.5 Package reusable infrastructure as extensions

If a feature consists of many related functions, types, operators, casts and views that must be installed/upgraded together, an extension can provide versioning and membership boundaries that ad hoc migration snippets cannot.[45]

26.6 Treat replication objects as configuration in schema management

Publication filters/column lists and subscription settings are part of data architecture. Track them in infrastructure/migration workflows alongside tables and indexes rather than managing them only through manual operational commands.

27. Common pitfalls

27.1 Treating every object as if it had independent naming

Tables, indexes, sequences, views, materialized views and foreign tables share the relation namespace. An index named customer prevents a table/view/sequence of the same name in that schema.[2]

27.2 Relying on mutable search_path in privileged code

Unqualified names can resolve to attacker-controlled objects if writable schemas precede trusted schemas. Security-definer functions should set a safe path explicitly and application migrations should prefer qualified names.[2][35]

27.3 Assuming views store results

Ordinary views store query definitions. Materialized views store results. Their freshness, storage and performance characteristics are fundamentally different.[9][10]

27.4 Assuming sequences are transactional counters

Sequence allocation intentionally does not promise gaplessness after rollbacks/crashes/caching. Use a separate locked transactional numbering mechanism when legal/business rules require gapless issuance.[33]

27.5 Using domains for cross-column rules

Domains validate one value. Rules involving multiple columns or rows belong in table constraints, exclusion/unique structures, triggers or transactional logic.

27.6 Creating custom operators without planner/index semantics

A user-defined operator works as syntax around a function, but index acceleration requires an operator class/family and correct planner semantics. Creating the token alone does not make it searchable by an index.[41]

27.7 Hiding large business workflows in triggers

Triggers run inside the modifying transaction, so expensive or remote work increases lock/transaction duration and makes failure behavior harder to reason about. Prefer triggers for tight data-local behavior and move external effects to explicit application/outbox workflows.

27.8 Installing extension member objects manually

Manually recreating objects that should belong to an extension can break upgrade/membership assumptions. Use CREATE EXTENSION/ALTER EXTENSION and the extension's supported scripts.[20][45]

27.9 Assuming a foreign table is a cached copy

A foreign table is local metadata for external data access. Unless the FDW specifically implements caching, querying it invokes wrapper-defined remote/external access semantics.[48]

27.10 Assuming logical replication sends DDL

Publications/subscriptions replicate eligible data changes, not general schema migrations. Keep publisher/subscriber schemas compatible through a separate migration process.[50][51]

27.11 Using CASCADE reflexively

CASCADE can remove an entire dependency tree. Use it only after examining the dependent objects that PostgreSQL reports under the default restrictive behavior.[3]

28. Production checklist

  1. Use schemas deliberately as namespace, security and module boundaries.
  2. Schema-qualify deployment and security-sensitive references.
  3. Remember the shared relation namespace for tables, indexes, sequences, views, materialized views and foreign tables.
  4. Use tables for durable row storage and constraints for declarative integrity.
  5. Use views as logical interfaces, not as caches.
  6. Use materialized views when persisted derived results and controlled staleness are acceptable.
  7. Use indexes as workload-driven physical access structures.
  8. Use identity columns for table-local generated identities unless independent sequence semantics are specifically needed.
  9. Never assume normal sequences are gapless.
  10. Choose functions versus procedures based on SQL composability and transaction-control needs.
  11. Declare routine volatility/security/search_path correctly.
  12. Keep triggers small and data-local.
  13. Use domains for reusable scalar constraints; table constraints for row/cross-column rules.
  14. Treat custom types/operators/aggregates as an integrated extensibility system.
  15. Choose collations intentionally and plan for reindexing when collation semantics/version changes require it.
  16. Package multi-object reusable features as extensions.
  17. Model FDW deployments as wrapper → server → mapping → foreign table.
  18. Keep FDW local/remote types and collations semantically compatible.
  19. Track publication/subscription definitions in deployment configuration.
  20. Ensure replica identity supports published UPDATE/DELETE.
  21. Manage logical-replication schema changes separately from data replication.
  22. Inspect pg_class, pg_proc, pg_type and object-specific catalogs when debugging.
  23. Review dependencies before destructive DDL.
  24. Prefer RESTRICT-first thinking; use CASCADE intentionally.
Object-model principle: PostgreSQL's power comes from composing many small first-class objects—storage, names, types, executable semantics, access methods, federation and replication—through cataloged dependencies. Good database architecture chooses the object whose semantics match the requirement instead of forcing every concern into tables and application code.
