PostgreSQL in Production

A production engineering guide to provisioning, configuration, schema change, deployment, backup and recovery, high availability, monitoring, capacity, connection management, security, upgrades, compatibility, and operational runbooks.

Technical article • PostgreSQL 18.6 documentation baseline • Updated 15 September 2026 • Vancouver-style references

Abstract

Running PostgreSQL in production is a reliability discipline rather than a single configuration exercise. A production system must provision durable infrastructure, manage server configuration as controlled state, deploy application and schema changes without unsafe lock amplification, maintain independently testable backups, define high-availability and disaster-recovery objectives, observe database behavior, plan resource growth, manage connection pressure, enforce least privilege, and upgrade before a major version leaves support. PostgreSQL supplies the mechanisms for these tasks—including physical and logical replication, continuous WAL archiving and point-in-time recovery, statistics views, TLS, role-based access control, configuration views, pg_upgrade, checksums, and administration utilities—but the operator must combine those mechanisms into a tested operating model.[1]-[5]

This article uses PostgreSQL 18.6 as the current stable documentation baseline. As of September 2026, PostgreSQL 18, 17, 16, 15, and 14 are supported; the PostgreSQL project normally supports each major release for five years and recommends running the current minor release for the chosen major version.[1][2]

1. Production operating model

The database should be operated against explicit service objectives. At minimum, define a recovery point objective (RPO), recovery time objective (RTO), availability target, expected peak throughput, maximum acceptable query latency for important workloads, retention obligations, and maintenance windows. PostgreSQL's backup, replication, failover, and monitoring facilities provide the building blocks, but the values of those objectives determine which building blocks are required.[5][17][18]

┌──────────────────────────┐ │ Applications / jobs │ └────────────┬─────────────┘ │ TLS + authentication │ ┌────────────▼─────────────┐ │ pool / routing endpoint │ └───────┬─────────┬───────┘ │ │ writes stale-tolerant reads │ │ ┌───────▼───┐ ┌──▼──────────┐ │ primary │ │ hot standby │ └───────┬───┘ └──┬──────────┘ │ WAL │ replay └───────────┘ │ WAL archive │ ┌────────────▼─────────────┐ │ backups / PITR / offsite │ └──────────────────────────┘ Observability spans every layer: app latency, pool state, PostgreSQL statistics, OS/storage metrics, replication lag, archiver state, and backups.

High availability and disaster recovery should not be conflated. A local hot standby can reduce downtime after a server failure, while a geographically separate backup or replica addresses a different failure domain. Similarly, a replica is not a substitute for a backup: replication can faithfully reproduce accidental deletes or destructive DDL, whereas point-in-time recovery can return to an earlier state if the required base backup and WAL remain available.[5][17][20]

2. Database provisioning

2.1 Provision from requirements, not defaults

Provisioning should start from workload characteristics: dataset size and growth, working-set size, write rate, WAL generation rate, read/write mix, expected connection concurrency, maintenance workload, RPO/RTO, and the storage system's latency and durability properties. PostgreSQL exposes separate memory and connection parameters, and its resource-consumption documentation notes that many memory settings apply per operation or per worker rather than once per server; consequently, a configuration that looks safe in isolation can overcommit memory under concurrency.[11][22]

2.2 Initialize deliberately

initdb creates a PostgreSQL database cluster and fixes choices such as the initial locale provider and cluster-level checksum state. In PostgreSQL 18, data checksums are enabled by default and can be disabled explicitly with --no-data-checksums. When enabled, checksums are stored on data pages and verified when pages are read; temporary files and some internal structures are outside that protection.[3][4] 

# Example: explicit cluster initialization.
# Run as the operating-system account dedicated to PostgreSQL.

initdb \
  -D /var/lib/postgresql/18/main \
  --encoding=UTF8 \
  --locale-provider=icu \
  --locale=en-US

# Confirm the checksum state after startup.
psql -Atqc "SHOW data_checksums"

The production rule is to make cluster initialization reproducible. Locale, encoding, checksum state, filesystem layout, service user, directory permissions, and binary version should be recorded in infrastructure code or a build procedure rather than inferred from whatever defaults happen to exist on a host.[3][4]

2.3 Storage layout

PostgreSQL relies on its write-ahead log for crash recovery and requires a storage stack that correctly implements the durability behavior expected by fsync and related synchronization methods. Settings such as disabling fsync or full_page_writes are explicitly documented as non-durable optimizations and should not be used for ordinary production systems that require committed data to survive host or power failure.[23]

2.4 Provisioning verification

-- Cluster identity and version.
SELECT version();
SHOW server_version;
SHOW server_version_num;

-- Fundamental durability/physical settings.
SHOW data_checksums;
SHOW wal_level;
SHOW fsync;
SHOW full_page_writes;
SHOW synchronous_commit;

-- Core sizing.
SHOW max_connections;
SHOW shared_buffers;
SHOW work_mem;
SHOW maintenance_work_mem;
SHOW max_wal_size;

-- Where configuration came from.
SELECT name, setting, unit, context, source, sourcefile, sourceline, pending_restart
FROM pg_settings
WHERE name IN (
  'max_connections','shared_buffers','work_mem','maintenance_work_mem',
  'max_wal_size','wal_level','archive_mode','ssl'
)
ORDER BY name;

pg_settings reports each setting's context, source, and whether a file change is awaiting restart; this is useful for proving that the provisioned server is actually running the intended configuration rather than merely having the intended text in a file.[9]

3. Configuration management

3.1 Treat PostgreSQL configuration as controlled state

PostgreSQL reads configuration from postgresql.conf and optionally included files. ALTER SYSTEM writes settings to postgresql.auto.conf, which overrides values from postgresql.conf. A configuration change may be session-settable, reloadable with SIGHUP, or require a server restart depending on the parameter's context.[7][8]

Production teams should choose one authoritative configuration path. If an external configuration manager owns the files, uncontrolled ALTER SYSTEM use can create drift because postgresql.auto.conf may override managed values. PostgreSQL 18 includes allow_alter_system specifically to help environments where an external tool is intended to control configuration, though the documentation states that disabling ALTER SYSTEM is not itself a security boundary.[7]

3.2 Example managed configuration fragment

# 00-production.conf
# Example only: values must be sized for the actual workload.

listen_addresses = '10.20.0.15'
port = 5432

max_connections = 200

shared_buffers = '8GB'
work_mem = '16MB'
maintenance_work_mem = '1GB'

wal_level = replica
max_wal_size = '16GB'
min_wal_size = '2GB'

archive_mode = on
archive_command = '/usr/local/sbin/archive-wal "%p" "%f"'

log_checkpoints = on
log_lock_waits = on
log_min_duration_statement = '500ms'

ssl = on
ssl_min_protocol_version = 'TLSv1.2'

shared_preload_libraries = 'pg_stat_statements'

The fragment demonstrates categories, not universal values. PostgreSQL's memory documentation warns that work_mem can be consumed by multiple query operations and multiple concurrent sessions, while parallel query can multiply resource use across workers. Therefore static “percentage of RAM” recipes are insufficient for sizing a busy production system.[11]

3.3 Validate before reload

-- Check file parsing and identify ignored/error lines.
SELECT
    sourcefile,
    sourceline,
    name,
    setting,
    applied,
    error
FROM pg_file_settings
WHERE error IS NOT NULL
   OR applied IS FALSE
ORDER BY sourcefile, sourceline;

-- Reload valid SIGHUP settings.
SELECT pg_reload_conf();

-- Identify settings changed in files that still require restart.
SELECT name, setting, pending_restart
FROM pg_settings
WHERE pending_restart;

pg_file_settings reports configuration-file entries and parsing/application errors, while pg_reload_conf() requests a server configuration reload. pg_settings.pending_restart identifies file changes that cannot take effect until restart.[9][10]

4. Schema migrations

4.1 The production problem is locking, not SQL syntax

Many ALTER TABLE forms acquire an ACCESS EXCLUSIVE lock unless the command's documentation specifies a weaker level. An operation that completes instantly in a development database can wait behind an old transaction in production, and the queued exclusive lock can then block subsequent queries. Production migrations must therefore be designed around both the work the command performs and the lock it must acquire.[12]

4.2 Use bounded lock acquisition

BEGIN;

-- Do not let a deployment wait indefinitely behind a blocker.
SET LOCAL lock_timeout = '3s';

-- Bound the statement itself.
SET LOCAL statement_timeout = '5min';

ALTER TABLE orders
    ADD COLUMN fulfillment_state text;

COMMIT;

lock_timeout aborts a statement that waits too long to acquire a lock, while statement_timeout bounds total statement execution. PostgreSQL recommends against indiscriminately setting these globally in postgresql.conf because different workloads require different limits; deployment sessions are a natural place to set migration-specific values.[13]

4.3 Expand/contract migration pattern

For application-visible changes, prefer an expand/contract sequence: first add backward-compatible schema, then deploy application code that can operate with old and new representations, backfill or dual-write as required, switch reads, and only later remove the old representation. This approach is an application deployment strategy built on PostgreSQL's transactional DDL and ALTER facilities; it reduces the need for a schema change and code change to become globally visible at exactly the same instant.[12][14]

Phase 1: expand

BEGIN;
SET LOCAL lock_timeout = '2s';

ALTER TABLE users
    ADD COLUMN display_name_v2 text;

COMMIT;

Phase 2: backfill in bounded batches

-- Repeat in batches from application/maintenance code.
WITH batch AS (
  SELECT id
  FROM users
  WHERE display_name_v2 IS NULL
  ORDER BY id
  LIMIT 5000
  FOR UPDATE SKIP LOCKED
)
UPDATE users AS u
SET display_name_v2 = u.display_name
FROM batch
WHERE u.id = batch.id;

Phase 3: enforce without a long initial validation scan

ALTER TABLE users
  ADD CONSTRAINT users_display_name_v2_nn
  NOT NULL display_name_v2 NOT VALID;

ALTER TABLE users
  VALIDATE CONSTRAINT users_display_name_v2_nn;

PostgreSQL 18 permits foreign-key, check, and not-null constraints to be added as NOT VALID. The initial command skips validating old rows while still enforcing the constraint for subsequent writes; VALIDATE CONSTRAINT later scans existing data using a weaker SHARE UPDATE EXCLUSIVE lock than the usual exclusive schema-change path.[12]

4.4 Create indexes concurrently

CREATE INDEX CONCURRENTLY idx_orders_customer_created
ON orders(customer_id, created_at DESC);

A regular CREATE INDEX blocks writes while the index is built. CREATE INDEX CONCURRENTLY permits inserts, updates, and deletes to continue, at the cost of extra scans, waits, and total work. It cannot run inside a transaction block, and a failed concurrent build can leave an invalid index that should be inspected and removed or rebuilt.[15]

4.5 Unique constraints with reduced write blocking

CREATE UNIQUE INDEX CONCURRENTLY users_email_uq_new
ON users(lower(email));

-- If the index is suitable for a constraint, attach it with ALTER TABLE.
-- Expression indexes cannot become ordinary UNIQUE constraints;
-- for simple columns, the documented USING INDEX route applies.

PostgreSQL documents a production-oriented technique for ordinary unique/primary-key constraints: build an eligible unique B-tree index concurrently, then attach it to the constraint with ALTER TABLE ... ADD CONSTRAINT ... USING INDEX. This avoids the long write-blocking phase of building that index under the constraint operation itself.[12][15]

4.6 Migration preflight

-- Long-running transactions can hold old snapshots or locks.
SELECT
  pid,
  usename,
  application_name,
  state,
  now() - xact_start AS transaction_age,
  wait_event_type,
  wait_event,
  left(query, 200) AS query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;

-- Observe a concurrent index build.
SELECT *
FROM pg_stat_progress_create_index;

PostgreSQL exposes live backend and progress views for schema operations. Concurrent index builds can spend time waiting for writers, validating the index, or waiting for old snapshots; those phases are surfaced through pg_stat_progress_create_index.[24][16]

5. Deployment strategies

5.1 Separate application compatibility from migration completion

A robust application deployment is compatible with the database both before and after the migration step. This is especially important when deployments are rolling, because old and new application instances may overlap. Expand/contract schema changes, tolerant readers, versioned application behavior, and delayed destructive cleanup reduce coupling between database DDL and process replacement.[12][14]

5.2 Recommended release sequence

StageGoalRollback posture

5.3 Deployment preflight example

#!/usr/bin/env bash
set -euo pipefail

: "${DATABASE_URL:?must be set}"

# Is PostgreSQL accepting connections?
pg_isready -d "$DATABASE_URL"

# Verify exact server version.
psql "$DATABASE_URL" -X -v ON_ERROR_STOP=1 -Atqc \
  "SELECT current_setting('server_version');"

# Refuse to deploy if a transaction has been open too long.
psql "$DATABASE_URL" -X -v ON_ERROR_STOP=1 -Atqc "
SELECT CASE WHEN EXISTS (
  SELECT 1
  FROM pg_stat_activity
  WHERE xact_start IS NOT NULL
    AND now() - xact_start > interval '15 minutes'
    AND pid <> pg_backend_pid()
) THEN 1 ELSE 0 END;
"

# Optional: application-specific migration/version table check.
psql "$DATABASE_URL" -X -v ON_ERROR_STOP=1 -Atqc \
  "SELECT max(version) FROM app_schema_migrations;"

pg_isready reports whether a PostgreSQL server is accepting, rejecting, or not responding to connection attempts through distinct exit codes, making it suitable for scripted readiness checks. A successful transport readiness test should still be complemented by application-level checks that exercise the actual database, role, schema, and critical query paths.[25]

5.4 Do not use database restore as the first-line deployment rollback

A database restore is a recovery operation with an RPO/RTO cost, not an ordinary code rollback mechanism. For reversible application releases, design migrations so application rollback can occur without restoring the database. Reserve PITR or backup restoration for situations where data itself must be returned to an earlier state.[5][17]

6. Backup strategy

6.1 PostgreSQL has three fundamental backup approaches

The PostgreSQL documentation groups backups into SQL dumps, filesystem-level backups, and continuous archiving. Production systems commonly combine logical dumps for selective portability with physical base backups plus WAL archiving for fast whole-cluster restoration and point-in-time recovery.[5]

6.2 Define backup policy in RPO/RTO terms

MechanismPrimary useKey limitation
pg_dump/pg_dumpallLogical portability, selective databases/objects, migrations, archival.Restore time can be high for very large datasets; not a continuous PITR stream.
pg_basebackupWhole-cluster physical base backup; seed standbys/PITR.Not selective at database/table level.
WAL archiveReplay changes after a base backup; PITR.Requires complete, durable archive coverage and retention discipline.
ReplicaHA/read scaling; can be a backup source.Replicates logical mistakes; not historical recovery by itself.

6.3 Continuous archiving

# postgresql.conf
wal_level = replica
archive_mode = on
archive_command = '/usr/local/sbin/archive-wal "%p" "%f"'
#!/usr/bin/env bash
# /usr/local/sbin/archive-wal
# Simplified local example. Production systems normally copy to
# independently durable/off-site storage and verify persistence.

set -euo pipefail

src="$1"
name="$2"
dest="/srv/postgres-wal-archive/$name"

if [[ -e "$dest" ]]; then
  cmp --silent "$src" "$dest"
  exit $?
fi

tmp="${dest}.tmp.$$"
cp "$src" "$tmp"
sync "$tmp"
mv "$tmp" "$dest"

PostgreSQL retries archiving until the configured archive_command or archive module reports success. The documentation recommends that archival logic not overwrite a pre-existing WAL file with different contents, because archive-name collisions can otherwise destroy recoverability. Archived WAL contains effectively all database changes and must be protected accordingly.[17]

6.4 Base backups

# Full physical backup, streamed from a running server.
pg_basebackup \
  --host=db-primary.internal \
  --username=backup \
  --pgdata=/backup/base/2026-09-15 \
  --format=plain \
  --wal-method=stream \
  --checkpoint=fast \
  --progress \
  --verbose

pg_basebackup takes a physical backup of the entire cluster over the replication protocol and can be used as the base for PITR or a standby. It can also back up from a properly configured standby. PostgreSQL 17 and later support incremental base backups; an incremental backup must be combined with its predecessor chain using pg_combinebackup before it can be used directly for restore.[18]

Incremental backup example

# Assuming full/backup_manifest is retained:
pg_basebackup \
  -h db-primary.internal \
  -U backup \
  -D /backup/inc/2026-09-16 \
  --incremental=/backup/full/backup_manifest \
  --progress

# Restore preparation requires combining the chain:
pg_combinebackup \
  /backup/full \
  /backup/inc/2026-09-16 \
  -o /restore/combined

6.5 Backup verification

A backup policy is incomplete without automated restore tests. The test should restore into isolated infrastructure, replay WAL to a chosen recovery point, start PostgreSQL, run structural and application-level validation, and measure the elapsed time. Backup age, WAL-archive age, restore success, and restore duration should be monitored as production signals.[5][17][18] 

-- Monitor the archiver.
SELECT
  archived_count,
  last_archived_wal,
  last_archived_time,
  failed_count,
  last_failed_wal,
  last_failed_time
FROM pg_stat_archiver;

-- Monitor a running base backup.
SELECT *
FROM pg_stat_progress_basebackup;

7. High-availability architecture

7.1 Physical streaming replication

PostgreSQL physical streaming replication sends WAL from a primary to a standby, which replays the changes. Streaming replication is asynchronous by default: a transaction can commit on the primary before its changes are durable on a standby. If the primary fails during that lag window, transactions acknowledged to clients can be absent after failover.[19]

7.2 Synchronous replication

Synchronous replication can make a commit wait for confirmation from one or more synchronous standbys according to the configured policy. This reduces the acknowledged-data-loss window but adds commit latency and availability dependencies: if the required synchronous standby cannot respond, commits that require it can wait. The topology must therefore be selected from RPO, latency, and failure-domain requirements rather than from a generic rule that “synchronous is safer.”[19]

7.3 Example physical standby configuration

Primary

# postgresql.conf
wal_level = replica
max_wal_senders = 10
max_replication_slots = 10

# Example only; synchronous replication is a business/SLO choice.
# synchronous_standby_names = 'FIRST 1 (db_standby_1)'
-- Create a dedicated replication login.
CREATE ROLE replicator
WITH LOGIN REPLICATION
PASSWORD 'use-a-secret-manager-generated-value';

-- Optional physical slot to protect WAL needed by this standby.
SELECT pg_create_physical_replication_slot('db_standby_1');

HBA entry

# pg_hba.conf
hostssl replication replicator 10.20.2.15/32 scram-sha-256

Build the standby

pg_basebackup \
  -h db-primary.internal \
  -U replicator \
  -D /var/lib/postgresql/18/main \
  -R \
  --slot=db_standby_1 \
  --wal-method=stream \
  --progress

With -R, pg_basebackup writes standby.signal and appends connection settings to postgresql.auto.conf so the copied data directory can start as a standby. Replication slots can prevent required WAL from being removed before a consumer receives it, but an inactive or lagging slot can therefore retain large volumes of WAL and must be monitored.[18][19]

7.4 Failover requires an external decision mechanism

PostgreSQL can promote a standby with pg_ctl promote or pg_promote(), but the PostgreSQL project documentation explicitly states that the server does not provide the system software that detects primary failure and notifies the standby to fail over. Production automatic failover therefore requires an external control system or managed service that performs health assessment, leader election/fencing, endpoint routing, and promotion.[20][10]

Split-brain prevention is mandatory. After a standby is promoted, the old primary must not be allowed to rejoin as a writable primary. PostgreSQL's failover documentation explicitly calls out the need for a fencing/STONITH mechanism to prevent both systems from believing they are primary, a condition that can lead to data loss.[20]

7.5 HA monitoring

-- Primary: connected standbys and their WAL positions.
SELECT
    application_name,
    client_addr,
    state,
    sync_state,
    sent_lsn,
    write_lsn,
    flush_lsn,
    replay_lsn,
    write_lag,
    flush_lag,
    replay_lag
FROM pg_stat_replication;

-- Primary: retained WAL risk from slots.
SELECT
    slot_name,
    slot_type,
    active,
    restart_lsn,
    confirmed_flush_lsn,
    wal_status,
    safe_wal_size
FROM pg_replication_slots;

-- Standby:
SELECT
    pg_is_in_recovery() AS is_standby,
    pg_last_wal_receive_lsn(),
    pg_last_wal_replay_lsn(),
    pg_last_xact_replay_timestamp();

PostgreSQL's cumulative statistics system includes views for physical replication, replication slots, WAL receivers, archiving, WAL generation, database activity, locks, I/O, and recovery conflicts. Those server views should be correlated with external checks on process health, storage, network reachability, endpoint routing, and application success.[16][10]

8. Disaster recovery

8.1 Design DR for independent failure domains

A disaster-recovery copy should survive the failures that the production primary and its local HA standby are intended to tolerate. That normally means independent storage and, for site-level disaster recovery, a separate failure domain or region. PostgreSQL provides streaming/log-shipping and continuous WAL archiving mechanisms, but geographic placement, object-storage durability, credentials, DNS, network routing, and orchestration are infrastructure responsibilities.[17][19]

8.2 PITR recovery configuration

Modern PostgreSQL configures archive recovery using ordinary server parameters plus a recovery.signal file; the old recovery.conf mechanism was removed in PostgreSQL 12. Recovery can target time, transaction, LSN, or a named restore point depending on the recovery requirement.[17][26] 

# postgresql.conf / postgresql.auto.conf on the recovery host
restore_command = '/usr/local/sbin/restore-wal "%f" "%p"'
recovery_target_time = '2026-09-15 18:42:10-04'
recovery_target_action = 'promote'
# Signal archive recovery.
touch "$PGDATA/recovery.signal"

# Start PostgreSQL through the normal service manager.
systemctl start postgresql-18

8.3 Named restore points before dangerous operations

SELECT pg_create_restore_point('before_billing_migration_20260915');

pg_create_restore_point() inserts a named WAL marker that can be selected later through recovery_target_name. A restore point is useful only if the backup/WAL archive needed to reach it is retained and recoverable.[10][17]

8.4 Recovery rehearsal

A DR test should exercise the entire dependency chain: retrieve backup media, retrieve archived WAL, restore permissions and configuration, recover to a declared target, bring the database online in isolation, validate consistency, restore application secrets and network routes, run application smoke tests, and measure RTO. A test that only verifies that backup files exist does not validate recovery.[5][17]

9. Monitoring

9.1 Monitor symptoms and causes

PostgreSQL provides a broad statistics system covering sessions, replication, WAL, archiving, I/O, tables, indexes, checkpointer behavior, background writer activity, locks, subscriptions, and progress of maintenance operations. Production monitoring should combine these internal signals with OS/storage metrics and application service-level indicators such as request latency and error rate.[16]

9.2 Session and wait monitoring

SELECT
    pid,
    usename,
    application_name,
    client_addr,
    state,
    wait_event_type,
    wait_event,
    now() - xact_start  AS xact_age,
    now() - query_start AS query_age,
    left(query, 220) AS query
FROM pg_stat_activity
WHERE pid <> pg_backend_pid()
ORDER BY xact_start NULLS LAST, query_start NULLS LAST;

9.3 Blocking chains

SELECT
    a.pid AS waiting_pid,
    a.usename AS waiting_user,
    pg_blocking_pids(a.pid) AS blocking_pids,
    a.wait_event_type,
    a.wait_event,
    now() - a.query_start AS wait_age,
    left(a.query, 180) AS waiting_query
FROM pg_stat_activity AS a
WHERE cardinality(pg_blocking_pids(a.pid)) > 0
ORDER BY a.query_start;

9.4 Database-level health

SELECT
    datname,
    numbackends,
    xact_commit,
    xact_rollback,
    blks_read,
    blks_hit,
    temp_files,
    pg_size_pretty(temp_bytes) AS temp_bytes,
    deadlocks,
    checksum_failures
FROM pg_stat_database
WHERE datname IS NOT NULL
ORDER BY datname;

9.5 Table/vacuum health

SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    n_mod_since_analyze,
    last_autovacuum,
    last_autoanalyze,
    autovacuum_count,
    autoanalyze_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 30;

Vacuuming is not optional maintenance in an MVCC system. PostgreSQL documents vacuum as necessary to reuse space from updated/deleted tuples, update planner statistics, update the visibility map, and prevent transaction-ID and multixact wraparound problems. The autovacuum subsystem is enabled by default and is strongly recommended for ordinary production systems.[21]

9.6 Query workload: pg_stat_statements

# postgresql.conf
shared_preload_libraries = 'pg_stat_statements'
compute_query_id = auto
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

SELECT
    calls,
    total_exec_time,
    mean_exec_time,
    rows,
    shared_blks_hit,
    shared_blks_read,
    temp_blks_written,
    wal_bytes,
    left(query, 200) AS query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 25;

The supplied pg_stat_statements module tracks normalized planning/execution statistics across statements. It requires shared memory and is therefore loaded through shared_preload_libraries; access to other users' query text is restricted to appropriately privileged roles.[27]

10. Capacity planning

10.1 Capacity is multi-dimensional

PostgreSQL capacity should be tracked across storage bytes and growth, WAL volume, IOPS/throughput/latency, CPU, memory, query concurrency, connections, replica lag, temporary-file generation, maintenance time, and checkpoint behavior. Capacity problems often appear first in an adjacent resource: for example, memory pressure can become storage I/O, a slow replica can become WAL-disk growth, or long transactions can become vacuum backlog.[11][16][21]

10.2 Storage inventory

-- Database sizes.
SELECT
    datname,
    pg_size_pretty(pg_database_size(datname)) AS size
FROM pg_database
ORDER BY pg_database_size(datname) DESC;

-- Largest relations including indexes and TOAST.
SELECT
    schemaname,
    relname,
    pg_size_pretty(pg_total_relation_size(relid)) AS total_size,
    pg_size_pretty(pg_relation_size(relid)) AS heap_size,
    pg_size_pretty(pg_indexes_size(relid)) AS index_size
FROM pg_catalog.pg_statio_user_tables
ORDER BY pg_total_relation_size(relid) DESC
LIMIT 40;

10.3 Connection capacity

SELECT
    count(*) AS total,
    count(*) FILTER (WHERE state = 'active') AS active,
    count(*) FILTER (WHERE state = 'idle') AS idle,
    count(*) FILTER (WHERE state = 'idle in transaction') AS idle_in_xact
FROM pg_stat_activity;

SHOW max_connections;

max_connections sets the upper bound on concurrent server connections and influences the sizing of server resources, including shared memory. Raising it is therefore not a free way to handle application connection storms; connection pooling and workload concurrency control are usually safer tools for reducing backend count.[28]

10.4 Memory envelope

shared_buffers is cluster-wide, whereas work_mem can be used separately by multiple sort/hash operations within a single query and by many simultaneous sessions. Parallel workers can further multiply operation-level memory. Capacity planning should therefore model a realistic concurrency envelope instead of multiplying work_mem by only the connection count or treating the value as a per-query hard ceiling.[11]

10.5 Growth forecast

-- A simple schema for recording daily database size snapshots.
CREATE TABLE IF NOT EXISTS ops.database_size_history (
    captured_at timestamptz NOT NULL DEFAULT now(),
    database_name name NOT NULL,
    bytes bigint NOT NULL,
    PRIMARY KEY (captured_at, database_name)
);

INSERT INTO ops.database_size_history(database_name, bytes)
SELECT current_database(), pg_database_size(current_database());

-- Approximate recent average daily growth.
WITH d AS (
  SELECT
    date_trunc('day', captured_at) AS day,
    max(bytes) AS bytes
  FROM ops.database_size_history
  WHERE database_name = current_database()
    AND captured_at >= now() - interval '30 days'
  GROUP BY 1
),
delta AS (
  SELECT day, bytes - lag(bytes) OVER (ORDER BY day) AS growth
  FROM d
)
SELECT pg_size_pretty(avg(growth)::bigint) AS avg_daily_growth
FROM delta
WHERE growth IS NOT NULL;

10.6 Plan maintenance capacity too

Capacity planning includes the ability to vacuum, analyze, create/rebuild indexes, take backups, and replay or archive WAL while normal workload continues. PostgreSQL notes that vacuum creates I/O traffic and that autovacuum may need parameter adjustment for heavily updated tables; a production system that runs acceptably only when maintenance is absent is under-provisioned operationally.[21]

11. Connection management

11.1 PostgreSQL uses a backend per connection

PostgreSQL's server process model gives client sessions dedicated backend processes. The configured max_connections also causes PostgreSQL to size certain resources in proportion to that limit. Production services should therefore avoid opening unbounded direct connections as application replicas or serverless workers scale.[28]

11.2 Pool at the application or proxy layer

A pool limits simultaneous database backends while allowing a larger number of application requests to share them over time. PostgreSQL itself supplies libpq and server connection controls, but external poolers are separate products; whichever pool is used, its maximum database-side concurrency should be chosen from measured database capacity, not from the maximum number of application threads.[28][29]

11.3 Put useful metadata in the connection string

postgresql://app_user@db.internal:5432/appdb\
?sslmode=verify-full\
&sslrootcert=/etc/postgresql/root.crt\
&application_name=orders-api\
&connect_timeout=5\
&keepalives=1\
&keepalives_idle=30\
&keepalives_interval=10\
&keepalives_count=3

libpq supports application_name, connection timeouts, TCP keepalive controls, TLS modes, and other connection parameters. Supplying a meaningful application name makes workload ownership visible in pg_stat_activity, which materially improves incident diagnosis.[29]

11.4 Timeouts are part of connection hygiene

-- Role-specific defaults for an application.
ALTER ROLE orders_app SET statement_timeout = '30s';
ALTER ROLE orders_app SET idle_in_transaction_session_timeout = '60s';
ALTER ROLE orders_app SET lock_timeout = '5s';

PostgreSQL exposes statement, lock, transaction, idle-session, and idle-in-transaction timeout controls. Long idle transactions are especially dangerous operationally because they can retain snapshots and locks and delay vacuum cleanup; timeouts should be tuned to application behavior and not applied blindly across workloads with intentionally long operations.[13]

11.5 Readiness versus liveness

pg_isready answers whether the server is accepting connections, rejecting them, or not responding. A production application's readiness check should usually go further by connecting with the actual application identity and executing a lightweight query, while avoiding expensive checks that themselves increase load during an incident.[25]

12. Security hardening

12.1 Minimize network exposure

listen_addresses controls which network interfaces accept PostgreSQL TCP connections, while pg_hba.conf controls host-based authentication rules. Restrict listener interfaces and network firewalls/security groups to required paths, then use narrowly scoped HBA records rather than broad allow rules.[28][30]

12.2 Require TLS and verify identity

# postgresql.conf
ssl = on
ssl_cert_file = '/etc/postgresql/tls/server.crt'
ssl_key_file  = '/etc/postgresql/tls/server.key'
ssl_min_protocol_version = 'TLSv1.2'
# pg_hba.conf
hostssl appdb orders_app 10.20.10.0/24 scram-sha-256
# Client
psql "host=db.internal dbname=appdb user=orders_app \
sslmode=verify-full sslrootcert=/etc/postgresql/root.crt"

PostgreSQL supports TLS for client/server traffic. libpq's verify-full mode verifies both certificate trust and host identity and is recommended by the PostgreSQL documentation for most security-sensitive deployments. A server-side hostssl HBA rule ensures that the matching authentication rule only applies to TLS connections.[31][32]

12.3 Prefer SCRAM over legacy MD5 password authentication

PostgreSQL 18 defaults password_encryption to scram-sha-256, and MD5-encrypted password support is deprecated for removal in a future release. SCRAM also supports TLS channel binding where client/server capabilities permit it.[33][34]

12.4 Separate login identities from authorization roles

-- No-login capability role.
CREATE ROLE orders_rw NOLOGIN;

GRANT CONNECT ON DATABASE appdb TO orders_rw;
GRANT USAGE ON SCHEMA app TO orders_rw;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA app TO orders_rw;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA app TO orders_rw;

-- Ensure future objects get the expected grants.
ALTER DEFAULT PRIVILEGES IN SCHEMA app
GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO orders_rw;

ALTER DEFAULT PRIVILEGES IN SCHEMA app
GRANT USAGE, SELECT ON SEQUENCES TO orders_rw;

-- Login identity.
CREATE ROLE orders_app LOGIN;
GRANT orders_rw TO orders_app;

PostgreSQL roles can represent users, groups, or both, and role membership composes privileges. ALTER DEFAULT PRIVILEGES defines grants for future objects created by a role, preventing the common production failure where existing tables work but newly deployed tables are inaccessible to the application.[35][36]

12.5 Keep applications away from superuser

An application role normally does not need SUPERUSER, CREATEDB, CREATEROLE, REPLICATION, or BYPASSRLS. PostgreSQL also provides predefined roles such as pg_monitor and pg_maintain to grant narrower operational capabilities than superuser where appropriate; the documentation warns that predefined role permissions can evolve and should be reviewed across upgrades.[35][37]

12.6 Secure operational secrets

Database passwords, replication credentials, client private keys, and backup/archive credentials should not be stored in application source code or world-readable configuration. PostgreSQL requires restrictive permissions on the server private key for TLS on Unix systems and provides mechanisms such as client certificates, GSSAPI, SCRAM, and OAuth depending on deployment requirements.[31][34]

13. Upgrade planning

13.1 Minor and major upgrades are different

PostgreSQL publishes new major versions roughly annually and supports a major version for five years. Minor releases contain fixes, including security and corruption fixes, and the project recommends running the current minor release. Minor upgrades within a major do not require dump/reload; major upgrades can require pg_upgrade, dump/restore, or a replication-based migration because data-directory compatibility is not promised between major versions.[2]

13.2 Minor release process

  1. Read the release notes for every target minor release.
  2. Verify extensions, packaging, OS libraries, and automation in staging.
  3. Confirm current backup and recovery health.
  4. Drain or fail over traffic according to the HA design.
  5. Install the new minor binaries/packages and restart as required.
  6. Run smoke tests, replication checks, query/error-rate checks, and extension validation.

The PostgreSQL versioning policy explicitly notes that minor updates normally require stopping the server, installing updated binaries, and restarting, while still advising operators to read release notes for any additional actions.[2]

13.3 Major upgrade with pg_upgrade

# Preflight compatibility check using the NEW pg_upgrade binary.
 /usr/lib/postgresql/18/bin/pg_upgrade \
  --check \
  --old-bindir=/usr/lib/postgresql/17/bin \
  --new-bindir=/usr/lib/postgresql/18/bin \
  --old-datadir=/var/lib/postgresql/17/main \
  --new-datadir=/var/lib/postgresql/18/main

pg_upgrade upgrades a cluster to a later major version without the full logical dump/reload usually required for a major upgrade. It validates compatibility requirements and requires external modules to be available in a compatible form. PostgreSQL 18 can preserve optimizer statistics during pg_upgrade, reducing one traditional post-upgrade warm-up burden, although extended statistics are not preserved in the same way.[38][39]

13.4 Upgrade with logical replication

Logical replication can replicate between different PostgreSQL major versions and therefore provides a path to a low-downtime major upgrade: provision the target cluster, replicate selected data, validate it, quiesce or tightly control writes for cutover, allow the subscriber to catch up, redirect application traffic, and preserve a rollback plan. Logical replication has feature restrictions and operational complexity, so it is not a transparent substitute for pg_upgrade.[40]

13.5 Extension compatibility is part of the upgrade

A major-version plan must inventory installed extensions, procedural languages, preload libraries, custom C modules, collations/locales, client drivers, and replication topology. pg_upgrade cannot prove arbitrary third-party modules are binary-compatible; operators must obtain or build extension versions for the target PostgreSQL release and follow each extension's upgrade instructions.[38]

14. Version compatibility

14.1 Supported major versions

As of 15 September 2026, the PostgreSQL project lists PostgreSQL 18.6, 17.11, 16.15, 15.19, and 14.24 as supported branches. PostgreSQL 14 is scheduled to reach its final release in November 2026, so an organization still running 14 should already have a tested major-upgrade plan rather than treating its remaining support window as long-term runway.[1][2]

These dates come from the PostgreSQL project's versioning policy and are time-sensitive. Production lifecycle management should alert well before EOL so operating-system packaging, extensions, applications, and DR environments can be upgraded while the source major still receives security and bug fixes.[2]

14.2 Client/server compatibility

PostgreSQL's wire protocol and libpq are designed for broad compatibility, but individual features and authentication methods have version requirements. For example, older clients might not support SCRAM, and newer SQL syntax or server functions are obviously unavailable on older servers. Deployment pipelines should test the exact driver major/minor versions that production applications use against the target server version rather than assuming “PostgreSQL-compatible” is sufficient.[29][33]

14.3 Replication compatibility

Physical streaming replication operates between compatible server binaries and is used for same-major HA topologies; logical replication is the PostgreSQL-native mechanism explicitly intended for use cases that include replication between different major versions. Upgrading a logical-replication topology has additional documented prerequisites, including special handling for logical slots and subscriptions.[19][40][41]

15. Operational runbooks

A runbook should be executable by an operator who did not design the system. It should contain trigger conditions, safety checks, commands, decision points, expected outputs, escalation criteria, rollback/forward-recovery steps, and post-incident verification. PostgreSQL's own failover documentation recommends written administration procedures and regular switching tests so the failover mechanism is exercised before an emergency.[20]

15.1 Runbook: suspected primary failure

  1. Confirm scope. Check application failures, pg_isready, host/process health, network path, and storage.
  2. Avoid premature failover. Determine whether the primary is truly unavailable or only unreachable from part of the network.
  3. Fence the old primary. Ensure it cannot accept writes if a standby will be promoted.
  4. Check standby health. Verify recovery state, received/replayed WAL, and expected data-loss window.
  5. Promote. Use the approved orchestrator or pg_promote()/pg_ctl promote.
  6. Move the write endpoint. Update routing/DNS/VIP/service discovery according to the architecture.
  7. Validate. Run application writes/reads and check replication/archive/backup systems.
  8. Rebuild redundancy. Rewind or rebuild the former primary/new standby before declaring the incident resolved.
-- On the candidate standby:
SELECT pg_is_in_recovery(),
       pg_last_wal_receive_lsn(),
       pg_last_wal_replay_lsn(),
       pg_last_xact_replay_timestamp();

-- After fencing and approval:
SELECT pg_promote(wait => true, wait_seconds => 60);

PostgreSQL documents promotion and explicitly requires a mechanism to prevent the old primary from returning as a simultaneous writer. pg_rewind can help resynchronize a diverged former primary in suitable configurations rather than taking a complete new base backup.[20][10][42]

15.2 Runbook: restore to a point in time

  1. Identify the target time/LSN/transaction/restore point and freeze further destructive activity.
  2. Select a base backup old enough to precede the target.
  3. Restore into isolated infrastructure, never over the only surviving production copy.
  4. Configure restore_command and the recovery target.
  5. Create recovery.signal and start PostgreSQL.
  6. Monitor recovery until the target is reached.
  7. Validate business data and application invariants.
  8. Choose cutover procedure and preserve the former environment for forensic comparison until explicitly released.

PITR works by restoring a physical base backup and replaying archived WAL until the chosen target. Recovery timelines preserve branches of WAL history created by recovery/promotions, allowing later recovery operations to distinguish divergent histories.[17]

15.3 Runbook: runaway query or blocking transaction

-- Identify old active statements and transactions.
SELECT
  pid, usename, application_name, state,
  now() - xact_start AS xact_age,
  now() - query_start AS query_age,
  wait_event_type, wait_event,
  left(query, 240) AS query
FROM pg_stat_activity
WHERE pid <> pg_backend_pid()
ORDER BY xact_start NULLS LAST, query_start NULLS LAST;

-- Identify blockers.
SELECT pid, pg_blocking_pids(pid), left(query, 200)
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;

-- Cancel the current query first when appropriate.
SELECT pg_cancel_backend(12345);

-- Escalate to session termination only when required.
SELECT pg_terminate_backend(12345);

PostgreSQL provides server signaling functions for canceling a backend's current query or terminating a session. Termination is more disruptive because it aborts the session and its transaction; incident procedures should identify the owning service and business operation before killing a blocker whenever time permits.[10][16]

15.4 Runbook: rapidly growing pg_wal

  1. Check archiver failures in pg_stat_archiver.
  2. Check inactive/lagging physical and logical replication slots.
  3. Check standby connectivity and replication state.
  4. Check backup/replication consumers that may retain WAL.
  5. Measure current WAL generation rate and recent workload changes.
  6. Restore the failed consumer/archive path or intentionally remove an obsolete slot only after proving it is no longer required.
SELECT * FROM pg_stat_archiver;

SELECT
  slot_name,
  slot_type,
  active,
  restart_lsn,
  confirmed_flush_lsn,
  wal_status,
  safe_wal_size
FROM pg_replication_slots;

Replication slots exist specifically to retain resources a consumer still needs, so deleting a required slot can force replica rebuild or lose logical-decoding continuity. PostgreSQL's routine-vacuuming documentation also notes that abandoned slots can hold old horizons and should be identified when investigating wraparound or retention problems.[19][21]

15.5 Runbook: disk nearing full

  1. Determine whether growth is tables/indexes, WAL, temporary files, logs, or backup/archive data.
  2. Protect service first: add capacity if possible before attempting risky reclamation.
  3. Investigate abnormal WAL retention, abandoned slots, failed archiving, or large transactions.
  4. Inspect largest relations and growth history.
  5. Avoid impulsive VACUUM FULL on busy large tables; it takes an exclusive lock and requires extra working disk space during rewrite.
  6. Correct the growth cause and revise alerts/capacity forecast.

PostgreSQL warns that VACUUM FULL requires an ACCESS EXCLUSIVE lock and generally recommends regular standard vacuuming instead. Disk-space incidents should therefore be solved by understanding what is consuming storage rather than treating VACUUM FULL as a universal emergency command.[21]

15.6 Runbook: suspected corruption

  1. Preserve logs and avoid repeatedly restarting or rewriting the affected objects without a plan.
  2. Check checksum-failure statistics and storage/OS errors.
  3. Run targeted integrity checks against a replica or maintenance window where possible.
  4. Determine whether the problem is isolated to an index or affects heap data.
  5. Use restore/replica/reindex options appropriate to the damaged object; do not use destructive low-level repair tools without expert review and backups.
SELECT datname, checksum_failures, checksum_last_failure
FROM pg_stat_database
WHERE checksum_failures IS NOT NULL;

# Targeted logical/physical consistency checks:
pg_amcheck --database=appdb --table=public.orders

When checksums are enabled, PostgreSQL verifies data-page checksums during reads and reports failures. pg_amcheck invokes the supplied amcheck facilities to check supported relations and B-tree indexes and is designed for database corruption checks.[4][43]

15.7 Runbook: production schema change

  1. Classify the DDL lock level and whether it rewrites or scans the table.
  2. Check long transactions and blockers.
  3. Set deployment-local lock_timeout and statement_timeout.
  4. Use CONCURRENTLY, NOT VALID/VALIDATE, or expand/contract where applicable.
  5. Monitor progress and database load.
  6. Validate application compatibility before destructive cleanup.

The safety details are command-specific: ALTER TABLE generally takes ACCESS EXCLUSIVE unless documented otherwise, while concurrent index creation preserves writes but performs additional scans and transaction waits. A runbook should cite the exact target PostgreSQL major-version command documentation for every high-impact DDL step.[12][15]

15.8 Runbook: major-version upgrade

  1. Confirm source and target versions are supported and read all intervening release notes.
  2. Inventory extensions, preload libraries, client drivers, locales/collations, replication slots, and logical replication.
  3. Test the chosen path—pg_upgrade, dump/restore, or logical-replication cutover—on a production-sized copy.
  4. Measure downtime and post-upgrade performance, not just upgrade command runtime.
  5. Take/verify backups before the production change.
  6. Run pg_upgrade --check if using pg_upgrade.
  7. Execute the change under the approved traffic/failover plan.
  8. Validate application behavior, extensions, query performance, replicas, backup/archive jobs, and observability.
  9. Retain rollback assets until the explicit rollback window closes.

The PostgreSQL project permits skipping intervening major versions with pg_upgrade, but recommends reading the release notes for all intervening majors. Logical-replication cluster upgrades have their own documented prerequisites and non-transactional steps, so they require separate backup and rollback planning.[2][38][41]

16. Production readiness checklist

  1. Lifecycle: PostgreSQL major version is supported; current minor release is scheduled or installed.[2]
  2. Provisioning: initialization settings, checksums, locale, storage, OS account, and filesystem permissions are reproducible.[3][4]
  3. Configuration: one authoritative configuration workflow exists; drift and pending-restart settings are detectable.[7]-[10]
  4. Schema: migrations are reviewed for lock level, scans/rewrites, rollback behavior, and live-data volume.[12][15]
  5. Backups: base backups and WAL retention satisfy the defined RPO; automated restores demonstrate RTO.[5][17][18]
  6. HA: replica lag is monitored; failover and fencing are tested; endpoint cutover is documented.[19][20]
  7. DR: an independent recovery copy exists and has been restored in a separate environment.
  8. Monitoring: sessions, waits, locks, queries, I/O, vacuum, WAL, archive state, replicas, and storage growth are observable.[16][27]
  9. Capacity: growth, WAL, memory/concurrency, connection count, and maintenance headroom are forecast rather than watched only at failure thresholds.
  10. Connections: application connection concurrency is bounded; timeouts and application names are configured.[13][28][29]
  11. Security: network reachability is narrow, TLS identity is verified, SCRAM or stronger integrated authentication is used, and applications use least-privilege roles.[30]-[37]
  12. Upgrades: extensions and clients are inventoried; major upgrade rehearsals use production-sized data; EOL dates generate advance work.[2][38]
  13. Runbooks: failover, restore, blocking sessions, disk/WAL growth, corruption, migrations, and upgrades have tested procedures.
Core operating principle: a production PostgreSQL system is healthy only when it can be changed and recovered safely—not merely when queries are succeeding right now.
