PostgreSQL Scaling

A technical guide to scaling PostgreSQL vertically and horizontally: CPU, RAM, storage and IOPS, read replicas, routing, caching, partitioning, application sharding, Citus, YugabyteDB, CockroachDB, and the distributed-systems concepts behind scale-out SQL.

Technical article • PostgreSQL 18.6 baseline • Updated 15 September 2026 • Vancouver-style references

Abstract

PostgreSQL scaling is best treated as a sequence of increasingly expensive architectural choices. A single PostgreSQL server can use many CPU cores across concurrent sessions and selected parallel plans, can use large amounts of memory for shared buffers and query workspaces, and can drive high-performance storage; read-heavy systems can add physical hot standbys; very large tables can be partitioned; and applications can shard data across independent PostgreSQL clusters. Beyond that point, systems such as Citus, YugabyteDB, and CockroachDB provide different forms of distributed SQL, but they make different architectural and compatibility tradeoffs.[1]-[5]

The central engineering principle is to identify the constrained resource before adding architecture. CPU saturation, memory pressure, random I/O latency, WAL/checkpoint pressure, connection saturation, lock contention, a single hot key, replica lag, and total dataset size are different bottlenecks and require different remedies. Horizontal distribution introduces network communication, data-placement decisions, distributed failure modes, and cross-shard transaction costs that a single-node database avoids.[6][25][26]

1. The PostgreSQL scaling ladder

Scaling should normally progress from the least distributed solution that meets the requirement to more distributed designs only when the measured workload demands them. Native PostgreSQL already supplies mechanisms for query optimization, parallel execution, large-memory operation, partitioning, physical and logical replication, and connection failover. None of those mechanisms requires converting the database into a horizontally sharded distributed transaction system.[1][2][7][8]

complexity / operational cost / distributed coordination ↑ | distributed SQL | Citus / YugabyteDB / CockroachDB | application sharding | multiple independent PostgreSQL shards | partitioning | one PostgreSQL cluster, many table partitions | read scaling | primary + physical/logical replicas | vertical scaling | more CPU / RAM / faster storage | query/schema optimization | indexes / plans / batching / fewer round trips +----------------------------------------------→ scale requirement

This ladder is not a maturity ranking. A large single-node PostgreSQL system with replicas can be a better design than a distributed system when the workload fits on one writer, because local transactions and joins avoid distributed coordination. Conversely, a workload that requires write throughput or data volume beyond one machine, or low-latency writes in many regions, may justify a distributed architecture despite the additional complexity.[25][26]

2. Measure the bottleneck first

PostgreSQL 18 exposes cumulative statistics for sessions, tables, indexes, WAL, replication, checkpoints, background writing, and I/O. EXPLAIN (ANALYZE, BUFFERS) adds plan-level runtime and buffer information, while pg_stat_statements can aggregate planning/execution behavior by normalized statement. These surfaces are more useful for scaling decisions than CPU percentage alone because they identify where time and resource consumption occur.[6][9][10]

2.1 Baseline workload inventory

-- Active sessions and wait classes.
SELECT
    pid,
    application_name,
    state,
    wait_event_type,
    wait_event,
    now() - query_start AS query_age,
    left(query, 180) AS query
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY query_start;

-- Database-level workload.
SELECT
    datname,
    numbackends,
    xact_commit,
    xact_rollback,
    blks_read,
    blks_hit,
    temp_files,
    pg_size_pretty(temp_bytes) AS temp_bytes,
    deadlocks
FROM pg_stat_database
WHERE datname IS NOT NULL
ORDER BY datname;

2.2 Find expensive SQL

CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

SELECT
    calls,
    total_exec_time,
    mean_exec_time,
    rows,
    shared_blks_hit,
    shared_blks_read,
    temp_blks_written,
    wal_bytes,
    left(query, 220) AS query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 30;

Before adding replicas or shards, optimize statements that consume a disproportionate share of total runtime, I/O, temporary space, or WAL. A missing index or poor cardinality estimate remains a bad query after scale-out; distribution can multiply the cost if the same inefficient operation is executed on every shard.[9][10]

2.3 Inspect one critical query

EXPLAIN (ANALYZE, BUFFERS, WAL, VERBOSE)
SELECT
    customer_id,
    sum(total)
FROM orders
WHERE created_at >= now() - interval '30 days'
GROUP BY customer_id
ORDER BY sum(total) DESC
LIMIT 100;

EXPLAIN with buffer reporting distinguishes shared-buffer hits from physical reads and can report I/O timing when timing collection is enabled. PostgreSQL's planner cost model historically expresses costs relative to page fetches; the actual bottleneck should be validated from runtime measurements rather than inferred from cost alone.[9][11]

3. Vertical scaling

Vertical scaling means increasing the capacity of one PostgreSQL server: faster or more CPU cores, more RAM, faster storage, higher IOPS/throughput, or a platform with better network and memory bandwidth. This preserves the simplest data model and transaction topology because all rows remain under one PostgreSQL primary.[6]

3.1 What vertical scaling preserves

  • Local ACID transactions across all tables.
  • Local joins without cross-node data movement.
  • One authoritative write endpoint.
  • Ordinary PostgreSQL extensions and server semantics.
  • Simple uniqueness, foreign keys, sequences, and locking across the full dataset.

The limit is that one primary eventually has finite CPU, memory bandwidth, storage bandwidth, WAL generation/flush capacity, and lock/concurrency capacity. Vertical scaling can also become economically inefficient at the largest machine sizes. The point at which this occurs is workload-specific and should be measured rather than assumed.[6][12]

4. CPU scaling

4.1 PostgreSQL can use multiple cores in two ways

First, separate PostgreSQL backend processes can execute concurrent sessions on separate CPU cores. Second, selected individual queries can use parallel plans containing Gather or Gather Merge and parallel workers. Parallel workers are limited by max_worker_processes, max_parallel_workers, and max_parallel_workers_per_gather; the workers requested by a plan are not guaranteed to be available at execution time.[12][13] 

SHOW max_worker_processes;
SHOW max_parallel_workers;
SHOW max_parallel_workers_per_gather;

EXPLAIN (ANALYZE, VERBOSE)
SELECT count(*)
FROM events
WHERE occurred_at >= current_date - interval '30 days';

Parallel query is not available for every statement. PostgreSQL does not generate a parallel plan for queries that write data or lock rows, and functions marked PARALLEL UNSAFE prevent parallel execution. Parallel workers are separate processes and can multiply CPU, memory, and I/O consumption; PostgreSQL specifically notes that per-worker resource settings such as work_mem can make a parallel query consume substantially more total resources than a serial query.[12][13]

4.2 CPU-bound scaling checklist

  1. Use pg_stat_statements to identify statements consuming aggregate CPU time.
  2. Fix unnecessary work: poor joins, row-by-row queries, excessive parsing, functions, and avoidable sorting.
  3. Confirm indexes and planner row estimates.
  4. Measure whether critical analytical queries can use parallel plans.
  5. Increase cores only if the workload has enough independent or parallelizable work to consume them.
  6. Watch run-queue/load and database latency together; higher CPU utilization is acceptable until it degrades latency or throughput objectives.

5. RAM scaling

PostgreSQL uses both its shared buffer cache and the operating system's filesystem cache. The PostgreSQL 18 documentation gives roughly 25% of system memory as a reasonable initial value for shared_buffers on a dedicated server with at least 1 GB of RAM and notes that allocations beyond roughly 40% are unlikely to outperform a smaller value in many environments because the OS cache also matters.[6]

5.1 Memory is not one pool

shared_buffers is cluster-wide, while work_mem is a base limit applied to individual sort/hash operations. A complex query can use several such operations, many sessions can run concurrently, and parallel workers can each receive their own work-memory budget. Hash operations can use work_mem × hash_mem_multiplier. Therefore, raising work_mem globally based only on total RAM can create intermittent memory exhaustion under concurrency.[6] 

SHOW shared_buffers;
SHOW work_mem;
SHOW hash_mem_multiplier;
SHOW maintenance_work_mem;

-- Temp spill by database.
SELECT
    datname,
    temp_files,
    pg_size_pretty(temp_bytes) AS temp_bytes
FROM pg_stat_database
ORDER BY temp_bytes DESC;

5.2 What additional RAM can improve

More RAM can increase the effective cache available to frequently accessed table/index pages and can permit larger query working sets before sorts and hashes spill to temporary storage. It can also support larger maintenance operations. The benefit depends on the working set and concurrency; once the hot working set is already cached, more memory may provide less benefit than faster CPU or storage.[6][10]

6. Storage, throughput, latency, and IOPS

PostgreSQL performance depends on both data-file I/O and WAL durability. Random table/index reads, temporary-file spills, checkpoints, vacuum, index creation, WAL generation, and WAL flushes can all compete for storage bandwidth or latency. PostgreSQL exposes I/O statistics in pg_stat_io, checkpoint statistics in pg_stat_checkpointer, WAL statistics in pg_stat_wal, and per-query block/I/O statistics through EXPLAIN and pg_stat_statements.[10][14]

6.1 Inspect server I/O

SELECT
    backend_type,
    object,
    context,
    reads,
    read_bytes,
    read_time,
    writes,
    write_bytes,
    write_time,
    fsyncs,
    fsync_time
FROM pg_stat_io
ORDER BY (read_time + write_time + fsync_time) DESC NULLS LAST;

6.2 Inspect WAL and checkpoints

SELECT
    wal_records,
    wal_fpi,
    pg_size_pretty(wal_bytes) AS wal_bytes,
    wal_buffers_full,
    wal_write,
    wal_sync,
    wal_write_time,
    wal_sync_time
FROM pg_stat_wal;

SELECT *
FROM pg_stat_checkpointer;

Larger shared_buffers settings can require a larger max_wal_size so dirty-page writes are spread over a longer interval. This illustrates an important scaling principle: memory, WAL, checkpoints, and storage are coupled rather than independent knobs.[6]

6.3 IOPS versus throughput

“More IOPS” is not automatically the answer. Small random reads can be latency/IOPS sensitive, while sequential scans, base backups, checkpoint writeback, and bulk operations can be bandwidth-sensitive. Determine the dominant I/O context from PostgreSQL and operating-system/storage metrics, then test storage changes against application latency and throughput.[9][10]

Scaling rule: do not buy storage characteristics from a generic PostgreSQL recipe. Measure read latency, write latency, WAL flush latency, queue depth, temporary I/O, cache-hit behavior, and the workload's block-access pattern.

7. Read scaling

Read scaling removes read work from the primary by serving eligible queries elsewhere. PostgreSQL's native physical streaming replication produces standby servers that continuously receive and replay WAL. With hot standby enabled, those standbys can accept read-only queries while recovery continues.[2][15]

┌───────────────┐ writes / consistency reads ──►│ primary │ └───────┬───────┘ │ WAL streaming ┌─────────────────────┼─────────────────────┐ v v v ┌────────────┐ ┌────────────┐ ┌────────────┐ │ replica A │ │ replica B │ │ replica C │ │ read-only │ │ read-only │ │ read-only │ └────────────┘ └────────────┘ └────────────┘ ▲ ▲ ▲ └──── stale-tolerant/read-only traffic ───┘

Read scaling is effective only when the workload contains enough reads that can tolerate replica semantics. Writes still converge on the primary in ordinary physical streaming replication, and reads that require immediate read-after-write consistency may need to stay on the writer because replication is asynchronous by default.[2][15]

8. Read replicas

8.1 Physical hot standby

A hot standby replays the primary's physical WAL stream and exposes a read-only database. There is measurable delay between primary and standby. Recovery can also conflict with queries running on the standby; PostgreSQL documents cases where standby queries may be canceled so WAL replay can continue, for example when replaying an ACCESS EXCLUSIVE lock or vacuum cleanup that conflicts with the standby snapshot.[15]

8.2 Monitor lag

-- Primary.
SELECT
    application_name,
    client_addr,
    state,
    sync_state,
    sent_lsn,
    write_lsn,
    flush_lsn,
    replay_lsn,
    write_lag,
    flush_lag,
    replay_lag
FROM pg_stat_replication
ORDER BY application_name;

-- Standby.
SELECT
    pg_is_in_recovery(),
    pg_last_wal_receive_lsn(),
    pg_last_wal_replay_lsn(),
    now() - pg_last_xact_replay_timestamp() AS replay_delay;

8.3 Application consistency policy

function executeQuery(request):
    if request.isWrite:
        return writer.execute(request.sql)

    if request.requiresReadYourWrites:
        return writer.execute(request.sql)

    if request.maxStalenessAllowsReplica:
        return replicas.pickHealthy().execute(request.sql)

    return writer.execute(request.sql)

Applications should classify queries by consistency requirement rather than route every SELECT to a replica. A query that reads an order immediately after the same request created it, for example, may require the writer; a dashboard aggregate that tolerates seconds of lag may be a good replica candidate.

8.4 Logical replicas

PostgreSQL logical replication can replicate a subset of tables or rows to a subscriber and can consolidate multiple databases or provide data to separate user groups. It works at logical row-change level rather than by making a byte-for-byte physical standby. Subscriber schemas must be managed separately, and writes to the same replicated data on the subscriber can create conflicts.[16][17] 

-- Publisher
CREATE PUBLICATION reporting_pub
FOR TABLE orders, customers;

-- Subscriber
CREATE SUBSCRIPTION reporting_sub
CONNECTION 'host=writer.internal dbname=appdb user=repuser'
PUBLICATION reporting_pub;

9. Connection routing

Routing can occur in the application, in a connection pool/proxy, through DNS/service discovery, or using client-library host selection. libpq supports multiple hosts in one connection string and target_session_attrs values such as read-write, read-only, primary, standby, and prefer-standby. PostgreSQL 18 also documents load_balance_hosts=random, which randomizes host/address trial order for new connections.[18]

9.1 Writer routing

postgresql://db1,db2,db3/appdb\
?target_session_attrs=read-write\
&connect_timeout=3

With target_session_attrs=read-write, libpq only accepts a session whose default transaction mode permits writes. When multiple hosts are listed, hosts are tried until an acceptable connection is found.[18]

9.2 Standby routing

postgresql://replica1,replica2,primary/appdb\
?target_session_attrs=prefer-standby\
&load_balance_hosts=random\
&connect_timeout=3

This can spread new connections among suitable hosts, but each established connection remains attached to one server; libpq does not route each SQL statement independently after connection establishment. Fine-grained read/write splitting therefore belongs in the application or a proxy/router that understands connection role and transaction state.[18]

Read routing is a consistency feature, not merely load balancing. A router needs a policy for replica lag, read-after-write behavior, transaction pinning, failover, and what happens when no sufficiently fresh replica exists.

10. Caching

10.1 PostgreSQL already has multiple cache layers

PostgreSQL caches table and index pages in shared_buffers and also benefits from the operating system's filesystem cache. Application caching adds a separate semantic layer: it caches query results or domain objects and can avoid executing PostgreSQL work entirely. These layers solve different problems and should not be conflated.[6][9]

10.2 Cache-aside pattern

function getProduct(productId):
    key = "product:" + productId

    cached = cache.get(key)
    if cached exists:
        return decode(cached)

    row = db.query(
        "SELECT id, name, price, version FROM product WHERE id = $1",
        productId
    )

    cache.set(key, encode(row), ttl = 60 seconds)
    return row

10.3 Invalidation matters more than lookup speed

A cache can reduce read load only if its consistency semantics are acceptable. TTL-based caching deliberately permits staleness until expiration. Write-through or explicit invalidation can improve freshness but creates a dual-system consistency problem: database commit and cache mutation are not ordinarily one atomic transaction. Designing cache keys, TTLs, version fields, and invalidation behavior is therefore part of data correctness, not just performance.

10.4 Good cache candidates

  • Reference data that changes rarely.
  • Expensive aggregates whose freshness tolerance is known.
  • Public objects with a high read-to-write ratio.
  • Derived representations that can be recomputed.

Do not cache merely because a query is slow. First determine whether the query should be indexed or rewritten. Caching an inefficient query may hide a capacity problem until cache misses, restarts, or invalidations create a sudden database load spike.

11. Write scaling

Write scaling is harder than read scaling because concurrent writers must preserve database invariants. In ordinary PostgreSQL physical replication, the primary is the write authority and standbys replay its WAL, so adding replicas does not multiply write throughput. Logical replication can distribute selected change streams but does not turn a set of independent PostgreSQL publishers/subscribers into a transparent multi-writer distributed database.[2][16]

11.1 Scale the writer before distributing it

Before sharding, reduce avoidable write work: batch inserts, avoid unnecessary indexes, keep transactions short, remove redundant updates, tune autovacuum, and ensure storage can sustain WAL and data-file write volume. Native PostgreSQL can often handle much larger workloads after schema and query optimization than an application initially demonstrates.

11.2 Why horizontal write scale changes the data model

Once rows are split among independent writers, a unique constraint or transaction that spans shards can no longer be enforced by one local PostgreSQL lock manager and transaction manager. The system needs either an application-level protocol or a distributed database layer to locate data and coordinate cross-shard operations. This is the fundamental architectural difference between partitioning inside one PostgreSQL server and sharding across servers.[25][26]

12. PostgreSQL table partitioning

Declarative partitioning divides one logical PostgreSQL table into smaller physical tables according to a range, list, or hash partition key. The partitioned parent itself has no storage; rows are routed into child partitions. Partition pruning can remove irrelevant partitions during planning or execution, reducing scanned data when predicates constrain the partition key.[7]

12.1 Range partitioning example

CREATE TABLE events (
    id           bigint GENERATED ALWAYS AS IDENTITY,
    tenant_id    bigint NOT NULL,
    occurred_at  timestamptz NOT NULL,
    payload      jsonb NOT NULL,
    PRIMARY KEY (occurred_at, id)
) PARTITION BY RANGE (occurred_at);

CREATE TABLE events_2026_09
PARTITION OF events
FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');

CREATE TABLE events_2026_10
PARTITION OF events
FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');

CREATE INDEX events_2026_09_tenant_time_idx
ON events_2026_09 (tenant_id, occurred_at DESC);

12.2 Hash partitioning example

CREATE TABLE account_event (
    account_id bigint NOT NULL,
    event_id   uuid NOT NULL,
    created_at timestamptz NOT NULL,
    payload    jsonb NOT NULL,
    PRIMARY KEY (account_id, event_id)
) PARTITION BY HASH (account_id);

CREATE TABLE account_event_p0 PARTITION OF account_event
FOR VALUES WITH (MODULUS 8, REMAINDER 0);

CREATE TABLE account_event_p1 PARTITION OF account_event
FOR VALUES WITH (MODULUS 8, REMAINDER 1);

-- Repeat remainders 2..7.

12.3 Partitioning is not horizontal server sharding

Native PostgreSQL partitions are ordinary PostgreSQL relations managed by the same cluster and, unless tablespaces/storage placement are deliberately changed, typically by the same server/storage system. Partitioning can improve pruning, maintenance, archival, and certain access patterns, but it does not create independent write nodes or distribute a transaction across a network. The PostgreSQL documentation also warns that excessive partition counts can increase planning time and per-session memory use; “more partitions” is not automatically better.[7]

12.4 Operational benefit: drop data instead of deleting it

-- Retention for time-partitioned data can become metadata-oriented.
ALTER TABLE events DETACH PARTITION events_2025_09;
DROP TABLE events_2025_09;

For time-series retention, removing an old partition can be operationally much cheaper than issuing a massive row-by-row DELETE against a monolithic table. Partitioning can therefore be a scalability feature even when it does not add servers.[7]

13. Application-level sharding

Application sharding places subsets of rows on independent PostgreSQL clusters and makes the application responsible for mapping each request to the correct shard. This can scale writes because different shards have different PostgreSQL primaries, but it moves data-placement, cross-shard query, migration, rebalancing, and global-constraint responsibilities into the application/platform layer.

13.1 Simple hash router

SHARDS = [
    "postgresql://shard0/app",
    "postgresql://shard1/app",
    "postgresql://shard2/app",
    "postgresql://shard3/app"
]

function shardForTenant(tenantId):
    return stableHash(tenantId) mod length(SHARDS)

function executeForTenant(tenantId, sql, params):
    shard = shardForTenant(tenantId)
    return pools[shard].execute(sql, params)

13.2 Directory-based routing

A fixed hash is simple but awkward when adding/removing shards because many keys can remap. A directory service or shard map adds a level of indirection: tenant_id → shard_id. The application can migrate one tenant at a time and update the directory after data is synchronized, at the cost of maintaining a highly available routing metadata service. 

CREATE TABLE shard_directory (
    tenant_id bigint PRIMARY KEY,
    shard_id  integer NOT NULL,
    state     text NOT NULL CHECK (state IN ('active', 'moving'))
);

13.3 Choose a shard key from access patterns

A good shard key distributes storage and write load while keeping common transactions and joins inside one shard. Multi-tenant systems often use tenant_id because most operations naturally belong to one tenant; Citus documentation makes the same locality point for distribution columns, emphasizing that colocating related rows reduces distributed transaction and join cost.[20][21]

13.4 Problems the application must solve

  • Global uniqueness: use UUIDs, shard-prefixed IDs, or a separate global service instead of a sequence local to one shard.
  • Cross-shard transactions: avoid them, redesign ownership, or implement a distributed coordination/saga protocol.
  • Cross-shard analytics: query all shards and merge results, replicate to an analytical store, or use a distributed query layer.
  • Rebalancing: copy a key range/tenant while handling ongoing writes and then switch routing safely.
  • Schema changes: apply migrations consistently to every shard and handle partial deployment failure.
  • Hot shards: a perfectly even tenant count does not guarantee even write or storage load.
Sharding is a data-model commitment. The shard key becomes part of routing, operational tooling, data migration, and often primary/foreign key design. Changing it later can require moving a large fraction of the dataset.

14. Distributed SQL concepts

Distributed SQL systems attempt to preserve a relational SQL interface and transactions while partitioning data across multiple nodes. The general problem combines database concerns—schemas, indexes, SQL planning, transactions—with distributed-systems concerns—sharding, replica placement, consensus, quorum, network partitions, clocks, rebalancing, and partial failures. Systems differ substantially in where they place these responsibilities.[25][26]

14.1 Shards, tablets, and ranges

A distributed table is divided into independently placeable units. Citus calls the physical pieces of distributed tables shards; YugabyteDB calls them tablets; CockroachDB's distributed key-value layer divides the keyspace into ranges. These units let the system spread storage and work across nodes.[20][23][28]

14.2 Replication and consensus

Horizontal partitioning increases capacity but does not itself provide high availability, so distributed databases commonly replicate each shard. Raft is a replicated-log consensus algorithm based on leader election, log replication, and majority agreement. YugabyteDB uses Raft groups for tablets; CockroachDB uses Raft for replicated ranges.[25][27][28]

logical table | +---- shard A ---- replicas A1 A2 A3 ---- Raft / quorum | +---- shard B ---- replicas B1 B2 B3 ---- Raft / quorum | +---- shard C ---- replicas C1 C2 C3 ---- Raft / quorum A distributed transaction may need to coordinate operations that touch more than one independently replicated shard.

14.3 Local versus distributed transactions

A transaction whose rows all belong to one shard can often be processed with less network coordination than a transaction spanning several shards. This is why distribution keys and data locality matter so much. Citus explicitly encourages colocating related tenant data; YugabyteDB and CockroachDB distribute transactional work across tablet/range groups when a transaction touches multiple partitions.[20][23][29]

14.4 Quorum has a latency cost

Strongly consistent replicated writes require communication among replicas. Raft commits replicated log entries based on majority agreement, so placing voting replicas across distant regions can put inter-region network latency on the write path. Multi-region distributed databases therefore expose data-locality and replication-placement controls so operators can trade write latency, read locality, and failure tolerance deliberately.[25][26][30]

14.5 Distributed SQL is not identical to PostgreSQL

PostgreSQL compatibility has layers: wire protocol, SQL syntax, types, functions, extensions, transaction semantics, catalog behavior, operational tools, and internals. Citus is a PostgreSQL extension and runs PostgreSQL on coordinator/worker nodes. YugabyteDB's YSQL reuses PostgreSQL query-layer code and is wire-format compatible with PostgreSQL while using a different distributed storage layer. CockroachDB implements a separate distributed database that speaks the PostgreSQL wire protocol and supports much PostgreSQL syntax, but it is not the PostgreSQL server implementation.[20][22][31]

14.6 Spanner as a foundational distributed-SQL design

Google's Spanner paper describes a globally distributed, synchronously replicated, multi-version database supporting externally consistent distributed transactions and automatic data movement. Its architecture influenced later distributed SQL systems and formalized many of the design tensions around global replication, placement, time, consistency, and transaction coordination.[26]

15. Citus

Citus is a PostgreSQL extension that turns multiple PostgreSQL servers into a distributed cluster. Current Citus documentation describes a coordinator node and worker nodes in a shared-nothing architecture. Applications normally connect to the coordinator, which uses distribution metadata to route a query to one worker or parallelize it across workers and combine the results.[20]

15.1 Table types and distribution

Citus supports distributed tables, reference tables, and ordinary local PostgreSQL tables. Distributed table rows are assigned to shards based on a distribution column. Reference tables are useful for relatively small data that must be available alongside distributed data across workers. Related distributed tables can be colocated so rows with the same distribution-key value are stored on the same worker placement, reducing the need for network data movement during tenant-local joins and transactions.[20][21]

15.2 Multi-tenant Citus example

CREATE EXTENSION IF NOT EXISTS citus;

CREATE TABLE tenant (
    tenant_id bigint PRIMARY KEY,
    name text NOT NULL
);

CREATE TABLE customer (
    tenant_id bigint NOT NULL,
    customer_id bigint NOT NULL,
    name text NOT NULL,
    PRIMARY KEY (tenant_id, customer_id)
);

CREATE TABLE orders (
    tenant_id bigint NOT NULL,
    order_id bigint NOT NULL,
    customer_id bigint NOT NULL,
    total numeric(12,2) NOT NULL,
    PRIMARY KEY (tenant_id, order_id),
    FOREIGN KEY (tenant_id, customer_id)
      REFERENCES customer(tenant_id, customer_id)
);

SELECT create_reference_table('tenant');
SELECT create_distributed_table('customer', 'tenant_id');
SELECT create_distributed_table('orders', 'tenant_id');

The tenant ID is intentionally included in keys and common query predicates. Citus documentation recommends choosing distribution columns so related data is colocated and common operations can be executed on one worker; distributing on the wrong key can force cross-node repartitioning or reduce which constraints can be enforced efficiently.[20][21]

15.3 Query routing

-- Tenant-local: typically targets one shard/worker.
SELECT order_id, total
FROM orders
WHERE tenant_id = 1042
ORDER BY order_id DESC
LIMIT 50;

-- Cross-tenant aggregation: can be parallelized across shards.
SELECT tenant_id, sum(total)
FROM orders
GROUP BY tenant_id
ORDER BY sum(total) DESC
LIMIT 100;

15.4 Scale out and rebalance

Adding workers increases the hardware pool, but existing shards may need to move so the new capacity receives data and work. Citus supplies rebalancing functions that plan and execute shard movement; current documentation exposes functions such as citus_rebalance_start() and planning helpers for reviewing moves before execution.[32]

15.5 Where Citus fits

Citus is particularly attractive when retaining PostgreSQL itself is important and the workload has a strong distribution key such as tenant, customer, device, or another dimension that allows most transactions to remain colocated. Cross-shard joins and transactions are possible in many cases, but their cost and feature behavior differ from single-node PostgreSQL, so distribution-key design is the central architectural decision.[20][21]

16. YugabyteDB

YugabyteDB is a distributed SQL database with a PostgreSQL-compatible YSQL API. The YSQL query layer reuses PostgreSQL query-layer code and is wire-format compatible with PostgreSQL, while the storage layer is YugabyteDB's DocDB rather than PostgreSQL heap/index storage. YugabyteDB divides tables into tablets and distributes those tablets across tablet servers.[22][23]

16.1 Architecture

YugabyteDB separates a query layer from a distributed storage layer. YB-TServers serve application data and host tablet peers; each tablet has replicas that form a Raft group. YugabyteDB supports hash and range sharding and automatically distributes tablets across nodes. Its master service manages cluster metadata and background orchestration.[22]-[24]

16.2 Ordinary SQL, distributed storage

CREATE TABLE account_event (
    tenant_id   bigint NOT NULL,
    account_id  bigint NOT NULL,
    event_id    uuid NOT NULL,
    created_at  timestamptz NOT NULL,
    payload     jsonb NOT NULL,
    PRIMARY KEY (tenant_id, account_id, event_id)
);

CREATE INDEX account_event_time_idx
ON account_event (tenant_id, account_id, created_at DESC);

From the application perspective, YSQL exposes familiar PostgreSQL-like tables and SQL while the storage layer maps rows into tablets. The product documentation emphasizes that applications interact with the table as one logical unit even though its rows can be distributed across multiple nodes.[23][24]

16.3 Horizontal write scale

Tablet leaders are spread across YB-TServers, allowing different shards to accept writes through different leaders. Replication factor determines the number of peers for each tablet; writes requiring strong consistency are replicated through the tablet's Raft group. As nodes are added, YugabyteDB can rebalance tablet leaders and replicas across the cluster.[24][33]

16.4 Compatibility boundary

Because YSQL is not backed by PostgreSQL's ordinary storage manager, compatibility should be evaluated at the application feature level. YugabyteDB documents broad PostgreSQL feature support together with limitations/deviations. Applications relying on unusual extensions, low-level PostgreSQL storage behavior, superuser operations, or exact planner/runtime behavior need explicit validation rather than assuming wire compatibility implies identical PostgreSQL semantics.[22][34]

17. CockroachDB

CockroachDB is a distributed SQL database that implements the PostgreSQL wire protocol and supports much PostgreSQL syntax and client tooling, but it is an independent database implementation. Every CockroachDB node can act as a SQL gateway; SQL operations are translated into operations over a distributed key-value layer whose keyspace is divided into replicated ranges.[29][31]

17.1 Ranges and Raft

CockroachDB splits key-value data into ranges and replicates ranges across nodes. Raft is used to keep range replicas consistent. Because many ranges exist across a cluster, work and storage can be distributed across nodes and rebalanced rather than requiring one PostgreSQL-style primary to own every write.[28][29]

17.2 Transaction behavior

CockroachDB's developer documentation states that SERIALIZABLE is the default isolation level. Under contention, some transactions can require retries; CockroachDB can retry certain cases internally, while other cases return a retry error to the client. This is an application-visible distributed database behavior that PostgreSQL-compatible clients must handle correctly.[31] 

function runTransactionWithRetry(work):
    for attempt in 1..MAX_ATTEMPTS:
        begin transaction
        try:
            result = work()
            commit
            return result
        catch retryable_serialization_error:
            rollback
            sleep(backoffWithJitter(attempt))
    throw "retry budget exhausted"

17.3 Multi-region locality

CockroachDB provides multi-region table locality abstractions, including regional tables, regional-by-row tables, and global tables. For regional-by-row tables, rows are associated with a region and CockroachDB manages the underlying placement configuration. This lets application architects trade local access latency, write latency, and resilience through database-level locality settings rather than hand-managing independent PostgreSQL shards.[30] 

CREATE TABLE users (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    username STRING NOT NULL UNIQUE
) LOCALITY REGIONAL BY ROW;

17.4 PostgreSQL compatibility boundary

PostgreSQL drivers often connect successfully because of the wire-protocol compatibility, but CockroachDB documentation explicitly frames compatibility as support for the PostgreSQL wire protocol and most PostgreSQL syntax/features rather than identity with PostgreSQL. Transaction retry semantics, supported extensions, types/functions, operational tooling, and performance behavior should all be validated for the application.[31]

19. Scaling decision framework

19.1 If CPU is the bottleneck

First optimize SQL and indexes, then use concurrency/parallelism effectively, then scale CPU. Add read replicas only if a meaningful fraction of CPU work is from reads that can move off the writer. Sharding is justified only when one writer's compute remains the limiting factor after simpler measures.[12][13]

19.2 If memory is the bottleneck

Identify whether the problem is cache misses, query workspaces, connection count, or another process. Add RAM and tune shared_buffers/work_mem with concurrency in mind. A larger machine is normally less disruptive than distributing data merely to obtain more aggregate RAM.[6]

19.3 If storage/IOPS is the bottleneck

Measure pg_stat_io, pg_stat_wal, checkpoints, query buffer reads, and temporary I/O. Improve indexes/query shapes, cache effectiveness, storage latency/throughput, and checkpoint/WAL configuration before adding architectural layers. Replicas can absorb read I/O but not primary WAL generation.[9][10][14]

19.4 If reads dominate

Physical replicas are the native PostgreSQL scale-out mechanism. Define which reads tolerate lag, route them deliberately, monitor replay lag and conflicts, and keep strict read-after-write paths on the writer when required.[15][18]

19.5 If one large table is operationally painful

Use native declarative partitioning if pruning, retention, archival, loading, or maintenance can be organized around a natural key such as time or tenant. Partitioning can be highly valuable without adding servers, but it should not be mistaken for distributed write scale-out.[7]

19.6 If writes exceed one primary

Choose among application sharding, Citus, or a distributed SQL database based on transaction locality and PostgreSQL-compatibility requirements. If nearly every transaction belongs to one tenant/account, a tenant shard key can keep operations local. If transactions frequently span arbitrary keys, distributed transaction cost becomes central and should be benchmarked directly.[20][23][31]

19.7 If multi-region writes are required

The speed of light and quorum placement become application constraints. A strongly consistent write replicated across distant regions necessarily involves network communication. Distributed systems offer placement controls and locality strategies, but no topology can provide synchronous intercontinental replication without paying some inter-region latency on operations that require those remote replicas.[25][26][30]

19.8 Practical checklist

  1. Profile first: identify CPU, memory, I/O, lock, connection, WAL, or dataset limits.
  2. Optimize SQL/schema: bad work scales badly.
  3. Scale up: preserve single-node semantics while they remain economical.
  4. Add read replicas: only for reads with an explicit staleness policy.
  5. Add caching: only with a defined freshness/invalidation contract.
  6. Partition: for pruning, lifecycle, and maintenance—not as a substitute for sharding.
  7. Choose a shard/distribution key carefully: optimize for transaction locality and even load.
  8. Benchmark cross-shard work: joins, uniqueness, transactions, and fan-out aggregates.
  9. Model skew: average load can hide one hot tenant/key.
  10. Model failure: replica loss, node loss, region loss, network partition, rebalance, and retry behavior.
  11. Validate PostgreSQL compatibility: test required extensions, SQL behavior, drivers, migrations, and tooling.
  12. Measure end-to-end: distributed database scaling is constrained by application latency, not only database throughput.
Scaling principle: use distribution to solve a measured distribution problem. A larger or better-tuned PostgreSQL primary is simpler than a distributed database; a distributed database becomes valuable when the workload genuinely requires resources, writes, or geographic placement that one primary cannot provide.
