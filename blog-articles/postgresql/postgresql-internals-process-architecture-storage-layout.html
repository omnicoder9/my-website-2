PostgreSQL Internals: Process Architecture and Storage Layout

A bottom-up technical guide to PostgreSQL's process and memory architecture, buffer manager, WAL buffers, backend memory, physical relation files, heap pages and tuples, TOAST, visibility and free-space maps, system catalogs, object identifiers, and the mapping from SQL objects to on-disk storage.

Technical article • PostgreSQL 18.6 baseline • Updated 16 September 2026 • Vancouver-style references

Abstract

PostgreSQL is a multiprocess client/server database. A supervisor process accepts connections and starts one backend process per client session. Those backend processes do not share ordinary private address space, but they coordinate through operating-system shared memory, semaphores and other IPC mechanisms. Shared state includes the shared buffer pool, WAL buffers, lock-related structures and many internal caches/control structures; query-local executor state and most temporary working memory remain private to each backend process.[1]-[3]

Persistent table storage is relation oriented. Built-in heap tables and indexes are stored in relation files identified by filenode numbers and split into fixed-size pages, normally 8 KiB. Heap pages contain a page header, stable line pointers, free space, tuple data and optionally access-method-specific special space. Heap tuples carry MVCC transaction metadata such as inserting/deleting transaction IDs and a physical tuple identifier (ctid). Large variable-length values use TOAST, which transparently compresses and/or moves values out of the main heap row when necessary.[4]-[7]

Several side structures make heap storage practical. The free-space map records which pages have reusable capacity so inserts do not scan the whole relation looking for room. The visibility map records pages known to be all-visible or all-frozen, enabling index-only scans and reducing vacuum work. System catalogs—ordinary PostgreSQL tables with specially known schemas—describe relations, columns, functions, types, operators, access methods and most other database objects. OIDs serve as internal catalog identifiers, while relation filenodes identify the current physical storage files; the two must not be assumed to be identical.[8]-[12]

Companion article: for planner, executor, logical decoding, background workers, foreign data wrappers, access methods, extension packaging, and PostgreSQL C APIs, see PostgreSQL Internals: Query Engine, Runtime, and Extension APIs.

1. Client/server architecture

PostgreSQL implements a process-per-connection client/server model. A client process communicates with exactly one backend process for a session. A supervisor process traditionally called the postmaster (the primary postgres server process) listens for connection requests and starts backend processes as connections arrive.[1]

application / psql / JDBC / libpq | PostgreSQL protocol | v +-----------------+ | postmaster / | | primary postgres| +--------+--------+ | accepts/spawns +-------+--------+---------+ | | | v v v backend A backend B backend C session A session B session C \ | / \ | / +--------------+-------+ | v shared-memory state shared buffers / WAL buffers / locks / internal shared control

The wire protocol carries SQL text and protocol messages between the client and backend. Query parsing, planning, execution, transaction management and most SQL semantics occur inside the server backend rather than in the client library.[1]

2. Connection lifecycle

When the server detects a new connection request, it creates a backend process dedicated to that client. Backend processes coordinate with the rest of the instance using shared memory and semaphores. Once established, the client sends requests to that backend and receives results over the same session connection.[1]

SELECT
    pid,
    backend_type,
    usename,
    datname,
    client_addr,
    state,
    query
FROM pg_stat_activity
ORDER BY backend_type, pid;

On Unix-like systems, process titles visible through ps identify both server background processes and per-client backends. Client backends typically expose user, database, client host and activity in the process title.[13]

$ ps -ef | grep '[p]ostgres'

postgres ... postgres: checkpointer
postgres ... postgres: background writer
postgres ... postgres: walwriter
postgres ... postgres: autovacuum launcher
postgres ... postgres: appuser appdb 10.0.1.15 idle

3. Process architecture

A PostgreSQL instance contains several categories of processes: the primary supervisor, client backends, auxiliary processes, autovacuum workers, WAL sender processes, parallel workers, logical-replication workers and optional extension-defined background workers. The exact set varies with configuration and workload.[14][15]

4. Backend processes

A backend process is the server-side process acting for one client session. It owns session-local state such as temporary-table buffers, prepared statements/cursors, many caches, private memory contexts and executor state. It attaches to the instance’s shared memory so it can access the shared buffer pool, locks and global coordination structures.[1][16]

4.1 Inspect your backend

SELECT
    pg_backend_pid() AS pid,
    current_database(),
    current_user;

4.2 Session memory contexts

SELECT

PostgreSQL 18’s pg_backend_memory_contexts exposes the context hierarchy for the current backend, including context type and path information.[17]

5. Background and auxiliary processes

5.1 Background writer

The background writer periodically writes dirty shared-buffer pages so backends are less likely to face bursts of dirty-buffer writes when they need replacement buffers. It is deliberately rate controlled so it smooths I/O rather than simply flushing everything aggressively.[2]

5.2 Checkpointer

The checkpointer executes checkpoints, synchronizing modified database pages according to PostgreSQL’s WAL/checkpoint protocol and establishing recovery starting points.[14]

5.3 WAL writer

The WAL writer periodically writes WAL buffers, reducing the amount of WAL-writing work individual foreground backends must perform.[18]

5.4 Autovacuum

The autovacuum subsystem has a persistent launcher and worker processes. The launcher schedules work across databases, while workers run VACUUM and/or ANALYZE on tables that cross activity or anti-wraparound thresholds.[15]

5.5 Startup, archiver and replication processes

During recovery, the startup process replays WAL. A configured WAL archiver copies completed WAL to an archive. WAL receiver and sender processes participate in physical streaming replication. Logical replication and parallel query use PostgreSQL’s worker infrastructure.[14]

6. Shared memory

Because PostgreSQL backends are separate operating-system processes, common state is placed in shared memory. PostgreSQL requires IPC facilities such as shared memory and semaphores. On modern Unix-like systems the main shared memory region is typically backed by anonymous mmap, while additional dynamic shared memory can be allocated for features such as parallel query.[2][19]

SHOW shared_memory_type;
SHOW dynamic_shared_memory_type;
SHOW min_dynamic_shared_memory;

6.1 Inspect shared-memory allocations

SELECT
    name,
    pg_size_pretty(size) AS size,
    pg_size_pretty(allocated_size) AS allocated
FROM pg_shmem_allocations
ORDER BY size DESC NULLS LAST;

The pg_shmem_allocations view reports allocations within the server’s main shared memory segment, including PostgreSQL and extension allocations. It does not include dynamic shared memory allocations.[20]

server startup | +--> main shared-memory area | shared buffers | WAL buffers | lock/control structures | fixed shared caches | +--> dynamic shared memory (on demand) parallel query coordination/data extension/background-worker needs other transient shared structures

7. Shared buffers

shared_buffers is PostgreSQL’s shared database-page cache. A buffer slot normally holds one database block, typically 8 KiB. Every backend can access the shared cache, while PostgreSQL also benefits from the operating system’s filesystem cache underneath it.[2]

SHOW shared_buffers;
SHOW block_size;

PostgreSQL 18 documents 128 MiB as the typical default. For a dedicated server with at least 1 GiB of RAM, the documentation suggests 25% of system memory as a reasonable starting point while noting that PostgreSQL also relies on the OS cache and allocations above roughly 40% are unlikely to be generally superior.[2]

relation block requested | +-- already in shared_buffers? -- yes --> pin + use | no | v choose reusable buffer | +-- dirty? --> write as required | v read block from filesystem | v buffer becomes valid/pinned | v backend reads/modifies page | +-- write operation --> mark dirty | v later background/checkpoint/backend write

7.1 Inspect the buffer cache

CREATE EXTENSION IF NOT EXISTS pg_buffercache;

SELECT *
FROM pg_buffercache_summary();

SELECT
    usage_count,
    buffers,
    dirty,
    pinned
FROM pg_buffercache_usage_counts()
ORDER BY usage_count;

The supplied pg_buffercache extension can inspect buffer identities, dirty/pinned state and clock-sweep usage counts. PostgreSQL 18 also adds NUMA-aware buffer inspection when built with NUMA support.[21][22]

8. WAL buffers

WAL buffers are shared memory used to stage WAL records that have not yet been written to WAL segment files. The default wal_buffers=-1 selects approximately 1/32 of shared_buffers, bounded below by 64 KiB and above by one WAL segment, normally 16 MiB.[18]

SHOW wal_buffers;

SELECT
    wal_records,
    wal_fpi,
    pg_size_pretty(wal_bytes) AS wal_bytes,
    wal_buffers_full
FROM pg_stat_wal;

WAL buffers are not a second copy of shared table pages. They contain serialized WAL records used for crash recovery, replication and archiving. The write-ahead rule requires relevant WAL to become durable before protected dirty data pages may be flushed to durable storage.[23]

9. Backend/private memory

Not all PostgreSQL memory is shared. Each backend process has its own private address space for parser/planner state, executor state, per-query memory contexts, tuple slots, expression evaluation, caches, network buffers and temporary working data. This private memory is where settings such as work_mem and much of maintenance_work_mem become operationally important.

A common sizing mistake is to add shared_buffers + work_mem and treat the result as maximum PostgreSQL memory. work_mem is a per-operation base limit, not one fixed allocation per server or even per connection, so one complex plan can use several independent work areas and several backends can do so concurrently.[2]

10. work_mem

work_mem sets the base maximum memory available to an individual query operation such as a sort or hash table before PostgreSQL uses temporary files. PostgreSQL 18 defaults it to 4 MiB. Sorts used by ORDER BY, DISTINCT and merge joins can consume work memory, while hash joins, hash aggregates, Memoize nodes and some IN processing use hash memory derived from work_mem and hash_mem_multiplier.[2]

SHOW work_mem;
SHOW hash_mem_multiplier;

SET LOCAL work_mem = '128MB';

EXPLAIN (ANALYZE, BUFFERS)
SELECT customer_id, sum(total_amount)
FROM app.orders
GROUP BY customer_id;
one backend | +-- Sort A ---------- up to work_mem +-- Sort B ---------- up to work_mem +-- Hash Join ------- up to work_mem × hash_mem_multiplier +-- HashAggregate --- up to work_mem × hash_mem_multiplier several concurrent backends/parallel workers => aggregate RAM can greatly exceed one work_mem value

When an operation exceeds its in-memory allowance, PostgreSQL can spill to temporary files under base/pgsql_tmp or the selected temporary tablespace. EXPLAIN can report temporary block I/O and sort/hash spill behavior.[4][24]

11. maintenance_work_mem

maintenance_work_mem is the memory limit used by maintenance commands such as VACUUM, CREATE INDEX and ALTER TABLE ADD FOREIGN KEY. PostgreSQL 18 defaults it to 64 MiB and documents that it can normally be set higher than work_mem because fewer maintenance operations are usually concurrent.[2]

SHOW maintenance_work_mem;
SHOW autovacuum_work_mem;
SHOW vacuum_buffer_usage_limit;

Autovacuum workers can each consume autovacuum_work_mem (or fall back to maintenance_work_mem when it is -1), so aggregate maintenance memory still needs capacity planning. PostgreSQL also treats parallel utility memory differently from parallel query: supported parallel maintenance commands apply maintenance_work_mem to the utility operation as a whole rather than independently multiplying it for each worker.[2]

12. Memory contexts

Internally, PostgreSQL manages private allocations through hierarchical memory contexts. Instead of tracking and individually freeing every allocation, code allocates objects into a context associated with a particular lifetime—query, transaction, cache, executor node, error handling and so on—and can reset or delete the context as a unit. This design simplifies cleanup on success and error paths.[16]

TopMemoryContext ├── CacheMemoryContext │ ├── catalog/cache allocations │ └── long-lived session caches ├── TopTransactionContext │ └── transaction-lifetime allocations ├── MessageContext │ └── current protocol/query message └── Executor / query contexts ├── plan-node state ├── expression state └── tuple / temporary allocations

12.1 Inspect current backend memory

SELECT
    repeat('  ', level - 1) || name AS context,
    type,
    pg_size_pretty(total_bytes) AS total,
    pg_size_pretty(used_bytes)  AS used,
    pg_size_pretty(free_bytes)  AS free
FROM pg_backend_memory_contexts
ORDER BY path;

12.2 Request another backend's context dump

SELECT pg_log_backend_memory_contexts(12345);

pg_log_backend_memory_contexts() asks another backend or auxiliary process to log its memory-context hierarchy. PostgreSQL cautions against frequent use because it can generate many log messages.[25]

13. Physical storage overview

PostgreSQL’s built-in heap table access method stores tables as relations composed of fixed-size blocks/pages. Index access methods use relation files too, usually with the same basic page framework but index-specific page content. The physical-storage chapter explicitly notes that PostgreSQL is extensible: custom table or index access methods are not required to use every detail of the built-in heap/index storage format.[5]

SQL object | v system catalog metadata (pg_class / pg_attribute / ...) | v relation identity OID + relfilenode + tablespace + database | v relation forks/files main / fsm / vm / init | v file segments relfilenode relfilenode.1 relfilenode.2 ... | v fixed-size pages (usually 8 KiB) | v line pointers + heap/index tuples

14. PostgreSQL data-directory layout

The PostgreSQL data directory contains configuration/state files plus subdirectories for databases, WAL and specialized transactional metadata. The built-in pg_default tablespace is stored under PGDATA/base; cluster-wide relations such as pg_database live under PGDATA/global; WAL segment files live under PGDATA/pg_wal.[4]

A database directory under base is named by the database’s OID, not by its SQL name. User-defined tablespaces add another layer: a link under pg_tblspc points to the external tablespace location, which then contains a version-specific directory and per-database OID subdirectories.[4]

15. Relation files, filenodes and forks

Each ordinary table and index is stored in its own relation files. The main file is named after the relation’s current filenode. Additional relation forks store supporting structures: _fsm for the free-space map, _vm for heap visibility maps, and _init for the initialization fork of unlogged relations.[4]

SELECT
    c.oid,
    c.oid::regclass AS relation,
    c.relfilenode,
    pg_relation_filenode(c.oid) AS actual_filenode,
    pg_relation_filepath(c.oid) AS filepath
FROM pg_class AS c
WHERE c.oid = 'app.orders'::regclass;

For some system catalogs pg_class.relfilenode is zero and PostgreSQL resolves the actual lower-level filenode through internal mapping; pg_relation_filenode() handles this correctly.[4]

15.1 File segmentation

By default, a relation file larger than 1 GiB is split into segments. The first segment uses the bare filenode name, then .1, .2 and so on. The 1 GiB segment size is a build-time default and can differ in a custom PostgreSQL build.[4]

base/16384/ 24576 first main-fork segment 24576.1 second segment 24576.2 third segment 24576_fsm free-space map fork 24576_vm visibility map fork

15.2 Temporary relations/files

Temporary relations have backend-qualified filenames. Temporary files produced by operations such as sorts that exceed memory appear in pgsql_tmp directories and contain the owning backend PID in their filename.[4]

16. Pages and blocks

PostgreSQL tables and indexes are arrays of fixed-size pages, normally 8 KiB. “Block” and “page” are commonly used for this unit in PostgreSQL. A heap page contains five logical regions: a 24-byte page header, an array of 4-byte item identifiers (line pointers), free space, the actual tuple items, and special space used by some index access methods. Ordinary heap pages do not use special space.[6]

lower addresses +------------------------------------+ | PageHeaderData (24 bytes) | +------------------------------------+ | ItemIdData / line pointers | grows downward | [lp1][lp2][lp3]... | +------------------------------------+ | | | FREE SPACE | | | +------------------------------------+ | tuple/item data | grows upward | [tuple3][tuple2][tuple1] | +------------------------------------+ | special space (indexes may use it) | +------------------------------------+ higher addresses

The page header includes pd_lsn (the WAL position of the latest page change), an optional checksum field, flag bits, offsets describing free/special space, a page-size/version field and pd_prune_xid, which helps identify pages where pruning might be useful.[6]

16.1 Stable line pointers

A tuple can move within a page when free space is compacted without changing its line-pointer index. PostgreSQL’s physical tuple identifier (ctid) is a pair of block number and line-pointer index, so the line-pointer stability permits intra-page compaction without breaking every reference to that tuple location.[6][12]

17. Heap tuple layout

Heap rows use a fixed header—23 bytes on most machines—followed by an optional null bitmap, alignment padding and user attribute data. The header stores transaction visibility metadata and tuple-state flags. Large variable-length attributes can be represented by compact TOAST pointers rather than inline values.[6]

t_cidCommand identifier information.
t_ctidPhysical TID of this tuple or a newer row version.
t_infomask, t_infomask2Attribute count and tuple/MVCC state flags.
t_hoffOffset where user attributes begin.
SELECT
    ctid,
    xmin,
    xmax,
    *
FROM app.orders
LIMIT 10;

The SQL-visible system columns expose some of the same underlying concepts, but ctid is not a durable application key: UPDATEs and table rewrites can change physical tuple locations.[12]

18. Heap storage and MVCC versions

The default table access method is called heap. Rows do not have to be stored in logical key order; any heap page with sufficient free space can accept a tuple. An UPDATE normally creates a new tuple version rather than overwriting the old version in place, allowing older snapshots to continue seeing prior versions until they become globally obsolete.[5][6]

logical row id=7 page 100: line 4 -> V1 xmin=400 xmax=425 value='old' ctid=(100,7) line 7 -> V2 xmin=425 xmax=0 value='new' ctid=(100,7) older snapshot may see V1 newer snapshot sees V2 VACUUM/pruning eventually reclaims V1

Heap-only tuple (HOT) updates can avoid creating new index entries when indexed columns are unchanged and the new row version fits on the same heap page, reducing update amplification and allowing more efficient pruning.[26]

19. TOAST

PostgreSQL pages have fixed size and heap tuples are not allowed to span pages. Large variable-length attributes therefore need another representation. TOAST—the Oversized-Attribute Storage Technique—compresses and/or moves large values out of line into a separate TOAST table, leaving a small pointer datum in the main row.[7]

TOAST processing normally begins when a row exceeds roughly 2 KiB (TOAST_TUPLE_THRESHOLD). PostgreSQL tries compression and/or out-of-line storage until the row is reduced toward the target size or no further useful reduction is possible. The on-disk TOAST pointer is a compact fixed-size representation containing enough metadata to locate and reconstruct the external value.[7]

main heap row +-------------------------------+ | id | title | body TOAST ptr | +-------------------------------+ | v associated TOAST table +--------------------------+ | chunk 0 of large value | | chunk 1 | | chunk 2 | | ... | +--------------------------+

19.1 Inspect a table's TOAST relation

SELECT
    c.oid::regclass AS table_name,
    c.reltoastrelid,
    c.reltoastrelid::regclass AS toast_table
FROM pg_class AS c
WHERE c.oid = 'app.documents'::regclass;

19.2 Column storage strategies

TOAST-capable data types use per-column storage strategies such as PLAIN, MAIN, EXTERNAL, and EXTENDED, controlling whether compression and/or out-of-line storage are allowed or preferred. Variable-length types participate because their varlena representation can encode inline, compressed and external forms.[7]

SELECT
    attname,
    attstorage,
    attcompression
FROM pg_attribute
WHERE attrelid = 'app.documents'::regclass
  AND attnum > 0
  AND NOT attisdropped
ORDER BY attnum;

19.3 TOAST and update behavior

If an UPDATE does not change an already out-of-line attribute, PostgreSQL normally preserves the existing external value rather than detoasting and rewriting it. This is one reason very wide rows can still be practical when updates usually touch only small columns.[7]

20. Free-space map (FSM)

Heap and most index relations have a free-space map stored in a separate _fsm fork. The FSM tracks approximately how much reusable space is available on each relation page, allowing PostgreSQL to find a page likely to fit a new tuple without linearly scanning the entire relation.[8]

heap pages: block 0: 800 B free block 1: 3200 B free block 2: 1200 B free block 3: 5000 B free FSM tree summarizes maxima [5000] / \ [3200] [5000] / \ / \ 800 3200 1200 5000 need ~4 KiB? search descends toward block 3

The FSM is itself organized as a tree of FSM pages. Bottom-level entries encode free space for relation pages, and upper levels store maxima for lower subtrees so searches can descend efficiently.[8]

20.1 Inspect free space

CREATE EXTENSION IF NOT EXISTS pg_freespacemap;

SELECT
    blkno,
    avail
FROM pg_freespace('app.orders')
ORDER BY avail DESC
LIMIT 20;

The supplied pg_freespacemap extension exposes the free-space values PostgreSQL currently records. The values are approximate management metadata, not an exact byte-level fragmentation analysis.[27]

21. Visibility map (VM)

Every heap relation has a visibility-map fork named with the _vm suffix. It stores two bits per heap page. The all-visible bit means all tuples on the page are known visible to all active/future transactions and need no vacuum cleanup at that point; the all-frozen bit means all tuples are frozen for transaction-ID purposes.[9]

heap page N | +-- all-visible bit | enables index-only scan | to skip heap visibility visit | +-- all-frozen bit lets aggressive anti-wraparound VACUUM skip the page

The map is conservative: a set bit must be true, while a cleared bit does not prove that the condition is false. VACUUM sets visibility bits and data-modifying operations clear them as needed.[9]

21.1 Inspect visibility coverage

CREATE EXTENSION IF NOT EXISTS pg_visibility;

SELECT *
FROM pg_visibility_map_summary(
    'app.orders'::regclass
);

Visibility coverage matters directly to query execution because ordinary secondary indexes do not contain heap MVCC visibility state. An index-only scan can avoid a heap fetch when the VM says the page is all-visible.[9]

22. System catalogs

PostgreSQL stores schema metadata and internal bookkeeping in system catalogs. These catalogs are themselves regular PostgreSQL tables from a storage perspective, but backend code knows their schemas and depends on their semantics. PostgreSQL therefore strongly discourages manual structural manipulation of catalog tables; ordinary SQL DDL should be used instead.[10][11][28]

CatalogRepresentative purpose

22.1 Catalog-driven extensibility

PostgreSQL is unusually catalog driven: its catalogs describe not just tables and columns but types, operators, functions, access methods, casts and other extensible behavior. Extensions add catalog rows plus executable code, which is a central part of PostgreSQL’s extensibility model.[29]

22.2 Example: reconstruct table metadata

SELECT
    c.oid,
    n.nspname AS schema_name,
    c.relname,
    c.relkind,
    c.relpersistence,
    c.reltuples,
    c.relpages,
    c.reltoastrelid
FROM pg_class AS c
JOIN pg_namespace AS n
  ON n.oid = c.relnamespace
WHERE c.oid = 'app.orders'::regclass;
SELECT
    a.attnum,
    a.attname,
    a.atttypid::regtype AS data_type,
    a.attnotnull,
    a.attstorage,
    a.attcompression
FROM pg_attribute AS a
WHERE a.attrelid = 'app.orders'::regclass
  AND a.attnum > 0
  AND NOT a.attisdropped
ORDER BY a.attnum;

23. Object identifiers (OIDs)

PostgreSQL uses OIDs as internal primary keys in many system catalogs. The oid type is an unsigned four-byte identifier, so PostgreSQL does not promise global uniqueness across every possible object over arbitrarily large lifetimes. OIDs identify catalog objects within the scopes where the system uses them.[12]

23.1 reg* alias types

Alias types such as regclass, regtype, regprocedure, regnamespace, and regrole provide convenient name-aware input/output for OID references. They make catalog queries safer and more readable than hand-writing name-to-OID subqueries.[12]

SELECT
    'app.orders'::regclass::oid AS relation_oid,
    'numeric'::regtype::oid     AS numeric_type_oid;

SELECT *
FROM pg_attribute
WHERE attrelid = 'app.orders'::regclass;

23.2 Early binding

A stored constant of a reg-type such as regclass is really an OID reference and creates dependency-aware early binding: if the object is renamed, the reference continues to identify that object. A text name resolved later has different semantics.[12]

23.3 OID is not filenode

Do not derive filenames from table OIDs. Relation OID and filenode frequently start equal, but operations such as TRUNCATE, REINDEX, CLUSTER, and some ALTER TABLE operations can replace physical storage and change the filenode while preserving the logical object OID.[4]

24. Mapping an SQL object to physical files

The safe way to map a relation to storage is to combine catalogs with PostgreSQL’s file-mapping functions rather than assuming a name or OID corresponds directly to a file.[4]

SELECT
    c.oid,
    c.oid::regclass AS relation,
    c.reltablespace,
    pg_relation_filenode(c.oid) AS filenode,
    pg_relation_filepath(c.oid) AS main_fork_path,
    pg_relation_size(c.oid, 'main') AS main_bytes,
    pg_relation_size(c.oid, 'fsm')  AS fsm_bytes,
    pg_relation_size(c.oid, 'vm')   AS vm_bytes
FROM pg_class AS c
WHERE c.oid = 'app.orders'::regclass;

24.1 Conceptual mapping

app.orders | v pg_namespace + pg_class | +-- relation OID = logical catalog identity +-- tablespace +-- relfilenode / pg_relation_filenode() | v database OID directory | v main relation path base/<db_oid>/<filenode> | +-- <filenode> main +-- <filenode>_fsm FSM +-- <filenode>_vm VM +-- .1, .2 ... large-file segments

24.2 Find the current database directory

SELECT oid, datname
FROM pg_database
WHERE datname = current_database();

25. Low-level inspection tools

PostgreSQL ships several extensions specifically for inspecting storage internals. They are excellent for learning and diagnosis but some require superuser-level access because they expose raw page content or internal state.

25.1 pageinspect

CREATE EXTENSION IF NOT EXISTS pageinspect;

SELECT *
FROM page_header(
    get_raw_page('app.orders', 0)
);

SELECT
    lp,
    t_xmin,
    t_xmax,
    t_ctid,
    t_infomask,
    t_infomask2,
    t_hoff
FROM heap_page_items(
    get_raw_page('app.orders', 0)
);

pageinspect can read a time-consistent copy of a raw page and decode heap line pointers and tuple headers. It returns tuples regardless of whether they are visible to the current MVCC snapshot because it is inspecting the physical page image directly.[30]

25.2 pg_buffercache

SELECT
    c.oid::regclass AS relation,
    count(*) AS cached_buffers
FROM pg_buffercache AS b
JOIN pg_class AS c
  ON pg_relation_filenode(c.oid) = b.relfilenode
WHERE b.reldatabase IN (
    0,
    (SELECT oid
     FROM pg_database
     WHERE datname = current_database())
)
GROUP BY c.oid
ORDER BY cached_buffers DESC
LIMIT 20;

26. PostgreSQL 18 internals notes

PostgreSQL 18 adds several internals/observability improvements relevant to this topic. It can be compiled with NUMA awareness and exposes pg_shmem_allocations_numa plus pg_buffercache_numa for shared-memory placement inspection. It also added buffer-cache eviction helpers intended for testing, expanded memory-context reporting, and added a TOAST relation to pg_index so very large expression-index metadata can be supported.[22][31]

These are diagnostic capabilities, not reasons to make routine manual cache-management decisions. PostgreSQL and the operating system manage caching dynamically; explicit cache eviction functions are documented for developer/testing scenarios.[21]

27. Operational implications of the internals

27.1 Connections consume processes and private memory

Because PostgreSQL normally uses one backend process per client session, thousands of idle or lightly active application connections still create process and memory overhead. Connection pooling is therefore a capacity tool, not merely a latency optimization.

27.2 Shared buffers are only one layer of caching

PostgreSQL reads/writes relation pages through its shared buffer cache, while the operating system can also cache filesystem pages. Sizing shared_buffers to nearly all RAM can therefore deprive the OS and backend private memory of useful capacity.[2]

27.3 Per-operation memory multiplies

work_mem is not reserved globally. Concurrent sorts, hash joins, hash aggregates and parallel workers can each consume separate work areas. A setting that is safe for a ten-connection analytics server can be unsafe for hundreds of concurrent OLTP sessions.[2]

27.4 MVCC creates physical versions

Logical UPDATEs and DELETEs translate into physical tuple-version lifecycle. Heap pages, line pointers, HOT chains, visibility maps, free-space maps and vacuum are all consequences of supporting concurrent MVCC snapshots without overwriting history immediately.

27.5 TOAST can hide large physical I/O

A table whose visible heap rows look compact can have substantial associated TOAST storage. Use pg_total_relation_size() or inspect reltoastrelid when investigating storage size rather than looking only at the main fork.

27.6 Logical object stability differs from physical file stability

Applications should reference SQL objects through names/OIDs/dependencies, never their filenodes or filesystem paths. PostgreSQL is free to replace a relation’s physical storage during maintenance/DDL while keeping the logical object intact.[4]

28. Production checklist

  1. Understand the process model. One client session normally maps to one backend process.
  2. Use connection pooling where connection counts would create excessive backend/process memory overhead.
  3. Distinguish shared and private memory. Shared buffers and WAL buffers are instance-wide; most query work areas are per backend/operation.
  4. Size work_mem for concurrency, not one query.
  5. Remember hash_mem_multiplier. Hash operations can exceed the base work_mem value.
  6. Size maintenance/autovacuum memory separately.
  7. Inspect memory contexts for unexplained backend growth.
  8. Use pg_buffercache diagnostically rather than trying to micromanage the cache.
  9. Remember PostgreSQL’s normal block size is 8 KiB. Pages are the core unit of heap/index buffer I/O.
  10. Understand tuple headers and MVCC versions. UPDATE is normally version creation, not in-place logical overwrite.
  11. Account for TOAST storage. Large text/JSON/bytea values may live outside the main heap.
  12. Use the FSM/VM concepts when reasoning about inserts, VACUUM and index-only scans.
  13. Query catalogs instead of parsing filesystem names.
  14. Never assume object OID equals filenode.
  15. Use pg_relation_filepath() and pg_relation_filenode() for current physical mapping.
  16. Use pageinspect, pg_freespacemap, and pg_visibility only when low-level diagnosis is actually needed.
  17. Treat catalog writes as internal surgery. Prefer supported SQL DDL/API operations.
  18. Retest internals assumptions after major upgrades. Internal catalogs, observability fields and implementation details evolve.
Internals principle: PostgreSQL separates logical identity, process-local execution state, instance-wide shared state and physical storage. Good operational reasoning follows those boundaries: know which process owns a resource, which structures are shared, which identifiers are logical versus physical, and which storage metadata is authoritative.
