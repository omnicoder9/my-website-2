PostgreSQL Triggers

A technical guide to BEFORE, AFTER, and INSTEAD OF triggers; row-level and statement-level execution; transition tables; event triggers; auditing; automatic data maintenance; deferred constraint triggers; trigger ordering; recursion; replication behavior; and production design.

Technical article • PostgreSQL 18.6 baseline • Updated 15 September 2026 • Vancouver-style references

Abstract

A PostgreSQL trigger is a database object that automatically invokes a trigger function when a specified database event occurs. Ordinary triggers attach to a table, partitioned table, view, or foreign table and respond to data-modification events such as INSERT, UPDATE, DELETE, and, for statement-level triggers, TRUNCATE. Event triggers operate at database scope and respond to supported DDL and database events rather than to row changes.[1]-[3]

Triggers are useful when logic must execute regardless of which application issued a statement: maintaining timestamps or derived state, implementing updatable views, recording transactional audit history, enforcing specialized cross-row invariants, and governing schema changes. Their power also makes them easy to misuse. Trigger logic is implicit from the perspective of the calling SQL statement, executes inside database transactions, can multiply work per affected row, can recursively cause more triggers, and can introduce ordering and concurrency dependencies. Good trigger engineering therefore requires explicit knowledge of timing, granularity, data visibility, transaction semantics, and failure behavior.[2][4]

1. Trigger execution model

PostgreSQL classifies ordinary triggers along two independent dimensions: timing and granularity. Timing determines whether the function runs before, after, or instead of an operation. Granularity determines whether it runs once per affected row or once per SQL statement. Not every combination is legal: INSTEAD OF triggers exist only on views and are always row-level, while TRUNCATE triggers are statement-level only.[1][5]

TimingRow-levelStatement-levelMain use
BEFORETables and foreign tablesTables, views, foreign tablesValidate, normalize, alter or suppress a row before storage; pre-statement setup.
AFTERTables and foreign tablesTables, views, foreign tablesObserve final changes, audit, maintain dependent data, run set-wise postprocessing.
INSTEAD OFViews onlyNot supportedImplement writes against a view by redirecting them to base tables.
SQL statement | +--> BEFORE STATEMENT trigger(s) | +--> for each affected row: | BEFORE ROW trigger(s) | | | +-- may modify NEW | +-- may return NULL and skip this row | v | physical row operation / constraints | +--> AFTER ROW trigger events | (executed after row changes; ordinary AFTER events complete | before AFTER STATEMENT) | +--> AFTER STATEMENT trigger(s) | +--> deferred constraint-trigger events, if any, may wait until transaction end

For triggers of the same kind on the same event and relation, PostgreSQL fires them in alphabetical order by trigger name. For BEFORE and INSTEAD OF row triggers, the row returned by one trigger becomes the input to the next. A BEFORE or INSTEAD OF trigger can return NULL to suppress the operation for that row.[2][5]

2. CREATE TRIGGER

PostgreSQL 18 supports CREATE TRIGGER and CREATE OR REPLACE TRIGGER. A trigger specifies its name, timing, event or events, target relation, granularity, optional condition, optional transition relations, and the trigger function to execute.[5] 

CREATE [ OR REPLACE ] [ CONSTRAINT ] TRIGGER trigger_name
{ BEFORE | AFTER | INSTEAD OF }
{ INSERT | UPDATE [ OF column [, ...] ] | DELETE | TRUNCATE [ OR ... ] }
ON relation
[ DEFERRABLE | NOT DEFERRABLE ]
[ INITIALLY IMMEDIATE | INITIALLY DEFERRED ]
[ REFERENCING OLD TABLE AS old_rows NEW TABLE AS new_rows ]
[ FOR EACH { ROW | STATEMENT } ]
[ WHEN ( condition ) ]
EXECUTE FUNCTION trigger_function(arguments);

If FOR EACH is omitted, statement-level execution is the default. The user creating the trigger requires TRIGGER privilege on the target relation and EXECUTE privilege on the trigger function. A trigger function is declared with no ordinary function arguments and returns the pseudo-type trigger; literal arguments from CREATE TRIGGER are exposed through language-specific trigger metadata such as PL/pgSQL's TG_ARGV.[5][6]

2.1 Multi-event trigger

CREATE TRIGGER orders_audit_row
AFTER INSERT OR UPDATE OR DELETE
ON app.orders
FOR EACH ROW
EXECUTE FUNCTION app.audit_order_row();

PostgreSQL permits multiple DML events in one trigger using OR. The trigger function can inspect TG_OP to distinguish INSERT, UPDATE, and DELETE.[5][6]

3. PL/pgSQL trigger functions

PL/pgSQL automatically creates special trigger variables. NEW contains the proposed row for row-level INSERT and UPDATE; OLD contains the previous row for row-level UPDATE and DELETE. Other variables include TG_OP, TG_WHEN, TG_LEVEL, TG_TABLE_SCHEMA, TG_TABLE_NAME, TG_NAME, TG_NARGS, and TG_ARGV.[6] 

CREATE OR REPLACE FUNCTION app.example_trigger()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    RAISE DEBUG
        'trigger=% op=% when=% level=% table=%.%',
        TG_NAME,
        TG_OP,
        TG_WHEN,
        TG_LEVEL,
        TG_TABLE_SCHEMA,
        TG_TABLE_NAME;

    IF TG_OP = 'DELETE' THEN
        RETURN OLD;
    END IF;

    RETURN NEW;
END;
$$;

3.1 Return-value semantics

The return value is critical for row-level BEFORE and INSTEAD OF triggers. A BEFORE INSERT or BEFORE UPDATE trigger normally returns NEW, potentially after modifying it. A BEFORE DELETE trigger normally returns OLD. Returning NULL suppresses that row's operation. The return value of an ordinary row-level AFTER trigger and of statement-level triggers is ignored, so those functions conventionally return NULL.[6]

4. BEFORE triggers

A row-level BEFORE trigger executes before PostgreSQL performs the row operation. It can change NEW for an INSERT or UPDATE, reject the statement by raising an exception, or return NULL to suppress that row without necessarily aborting the entire statement. Because the row has not yet been written, a BEFORE trigger is generally the natural choice for normalization or automatic values that belong to the row being stored.[2][6]

4.1 Automatic updated_at

CREATE TABLE app.customer (
    customer_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email text NOT NULL,
    display_name text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT statement_timestamp(),
    updated_at timestamptz NOT NULL DEFAULT statement_timestamp()
);

CREATE OR REPLACE FUNCTION app.set_updated_at()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    NEW.updated_at := statement_timestamp();
    RETURN NEW;
END;
$$;

CREATE TRIGGER customer_10_set_updated_at
BEFORE UPDATE
ON app.customer
FOR EACH ROW
WHEN (OLD.* IS DISTINCT FROM NEW.*)
EXECUTE FUNCTION app.set_updated_at();

The WHEN predicate avoids invoking the function for an update where the complete old/new row images are not distinct at the point PostgreSQL evaluates the condition. The trigger changes NEW in memory before storage rather than issuing a second UPDATE against the same row.[2][5]

4.2 Normalizing data

CREATE OR REPLACE FUNCTION app.normalize_customer()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    NEW.email := lower(trim(NEW.email));
    NEW.display_name := trim(NEW.display_name);

    IF NEW.display_name = '' THEN
        RAISE EXCEPTION 'display_name must not be empty'
            USING ERRCODE = '23514';
    END IF;

    RETURN NEW;
END;
$$;

CREATE TRIGGER customer_05_normalize
BEFORE INSERT OR UPDATE
ON app.customer
FOR EACH ROW
EXECUTE FUNCTION app.normalize_customer();
Prefer declarative constraints where they fit. NOT NULL, CHECK, UNIQUE, foreign keys, generated columns, domains, and defaults are more visible to schema tools and the optimizer than custom trigger code. Use triggers for behavior that cannot be expressed cleanly with declarative features.[7]

5. AFTER triggers

An AFTER trigger executes after PostgreSQL has completed the row operation and checked relevant constraints. By the time a row-level AFTER trigger executes, the effects of the outer command are visible to SQL run from the trigger. Because the stored row can no longer be replaced by the trigger's return value, AFTER triggers are a natural fit for auditing, dependent-table maintenance, notifications inside the database, and validation that needs to observe final row state.[2][4]

5.1 Audit row after change

CREATE TABLE audit.order_change (
    audit_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    changed_at timestamptz NOT NULL DEFAULT clock_timestamp(),
    changed_by name NOT NULL,
    operation text NOT NULL,
    order_id bigint,
    old_row jsonb,
    new_row jsonb
);

CREATE OR REPLACE FUNCTION audit.log_order_change()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN
        INSERT INTO audit.order_change(
            changed_by, operation, order_id, new_row
        )
        VALUES (
            session_user, TG_OP, NEW.order_id, to_jsonb(NEW)
        );

    ELSIF TG_OP = 'UPDATE' THEN
        INSERT INTO audit.order_change(
            changed_by, operation, order_id, old_row, new_row
        )
        VALUES (
            session_user, TG_OP, NEW.order_id,
            to_jsonb(OLD), to_jsonb(NEW)
        );

    ELSIF TG_OP = 'DELETE' THEN
        INSERT INTO audit.order_change(
            changed_by, operation, order_id, old_row
        )
        VALUES (
            session_user, TG_OP, OLD.order_id, to_jsonb(OLD)
        );
    END IF;

    RETURN NULL;
END;
$$;

CREATE TRIGGER orders_90_audit
AFTER INSERT OR UPDATE OR DELETE
ON app.orders
FOR EACH ROW
EXECUTE FUNCTION audit.log_order_change();

The audit insert participates in the same transaction as the original data change. If the transaction later rolls back, the audit row rolls back too. This makes the pattern useful for committed data history but insufficient as a tamper-resistant record of failed or rolled-back attempts; server/audit logging is a separate concern.[6][8]

6. INSTEAD OF triggers

INSTEAD OF triggers are row-level triggers defined on views. Rather than allowing PostgreSQL to perform the original INSERT, UPDATE, or DELETE against the view, the trigger function performs the intended changes against underlying tables. Its return value tells PostgreSQL whether the row operation was handled and affects RETURNING behavior.[1][6]

6.1 Updatable API-style view

CREATE TABLE app.person (
    person_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    first_name text NOT NULL,
    last_name text NOT NULL
);

CREATE TABLE app.person_contact (
    person_id bigint PRIMARY KEY
        REFERENCES app.person(person_id) ON DELETE CASCADE,
    email text NOT NULL UNIQUE
);

CREATE VIEW api.person AS
SELECT
    p.person_id,
    p.first_name,
    p.last_name,
    c.email
FROM app.person AS p
JOIN app.person_contact AS c USING (person_id);
CREATE OR REPLACE FUNCTION api.write_person_view()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN
        INSERT INTO app.person(first_name, last_name)
        VALUES (NEW.first_name, NEW.last_name)
        RETURNING person_id INTO NEW.person_id;

        INSERT INTO app.person_contact(person_id, email)
        VALUES (NEW.person_id, NEW.email);

        RETURN NEW;

    ELSIF TG_OP = 'UPDATE' THEN
        UPDATE app.person
        SET first_name = NEW.first_name,
            last_name = NEW.last_name
        WHERE person_id = OLD.person_id;

        UPDATE app.person_contact
        SET email = NEW.email
        WHERE person_id = OLD.person_id;

        NEW.person_id := OLD.person_id;
        RETURN NEW;

    ELSIF TG_OP = 'DELETE' THEN
        DELETE FROM app.person
        WHERE person_id = OLD.person_id;

        RETURN OLD;
    END IF;

    RETURN NULL;
END;
$$;

CREATE TRIGGER person_view_write
INSTEAD OF INSERT OR UPDATE OR DELETE
ON api.person
FOR EACH ROW
EXECUTE FUNCTION api.write_person_view();

This pattern can expose a stable relational interface while hiding underlying normalization. It should not be used merely to make ordinary automatically updatable views more complicated; PostgreSQL can automatically rewrite many simple views without an INSTEAD OF trigger.[1][9]

7. Row-level triggers

A FOR EACH ROW trigger runs once per row affected by the statement. A statement that updates one million rows can therefore invoke a row trigger one million times. This gives the function direct OLD/NEW access but makes per-row SQL, network operations, expensive JSON processing, or repeated scans potentially costly.[5]

7.1 Row filtering without exceptions

CREATE OR REPLACE FUNCTION app.skip_empty_event()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    IF NEW.payload = '{}'::jsonb THEN
        RETURN NULL;
    END IF;

    RETURN NEW;
END;
$$;

CREATE TRIGGER event_10_skip_empty
BEFORE INSERT
ON app.event
FOR EACH ROW
EXECUTE FUNCTION app.skip_empty_event();

Returning NULL from a row-level BEFORE trigger suppresses the current row and prevents subsequent triggers for that row from firing. This behavior is materially different from raising an exception, which normally aborts the statement and transaction unless handled in a surrounding PL/pgSQL exception context.[2][6]

8. Statement-level triggers

A FOR EACH STATEMENT trigger fires once for the statement, even if the statement affects zero rows. Statement-level triggers reduce invocation overhead and are useful for logging statement occurrence, refreshing a coarse-grained status, or performing set-based work through transition tables. TRUNCATE triggers are always statement-level.[5]

8.1 Track bulk operation occurrence

CREATE TABLE audit.table_operation (
    event_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    occurred_at timestamptz NOT NULL DEFAULT clock_timestamp(),
    actor name NOT NULL,
    table_schema name NOT NULL,
    table_name name NOT NULL,
    operation text NOT NULL
);

CREATE OR REPLACE FUNCTION audit.log_table_operation()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    INSERT INTO audit.table_operation(
        actor, table_schema, table_name, operation
    )
    VALUES (
        session_user, TG_TABLE_SCHEMA, TG_TABLE_NAME, TG_OP
    );

    RETURN NULL;
END;
$$;

CREATE TRIGGER orders_95_statement_audit
AFTER INSERT OR UPDATE OR DELETE OR TRUNCATE
ON app.orders
FOR EACH STATEMENT
EXECUTE FUNCTION audit.log_table_operation();

This records that the statement occurred but not which rows changed. For set-level access to row images, use transition relations on supported AFTER triggers.[5]

9. Transition tables

The REFERENCING clause can expose the set of rows changed by one SQL statement as read-only transition relations. OLD TABLE holds before-images for UPDATE/DELETE, and NEW TABLE holds after-images for INSERT/UPDATE. In PostgreSQL 18, transition tables are available only for AFTER triggers on plain tables; they are not available to constraint triggers, and an UPDATE trigger using transition tables cannot specify an UPDATE OF column list.[5]

9.1 Set-wise audit for updates

CREATE TABLE audit.order_price_change (
    audit_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    changed_at timestamptz NOT NULL DEFAULT clock_timestamp(),
    changed_by name NOT NULL,
    order_id bigint NOT NULL,
    old_total numeric(12,2) NOT NULL,
    new_total numeric(12,2) NOT NULL
);

CREATE OR REPLACE FUNCTION audit.log_order_price_changes()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    INSERT INTO audit.order_price_change(
        changed_by,
        order_id,
        old_total,
        new_total
    )
    SELECT
        session_user,
        n.order_id,
        o.total,
        n.total
    FROM old_orders AS o
    JOIN new_orders AS n USING (order_id)
    WHERE o.total IS DISTINCT FROM n.total;

    RETURN NULL;
END;
$$;

CREATE TRIGGER orders_90_price_audit
AFTER UPDATE
ON app.orders
REFERENCING
    OLD TABLE AS old_orders
    NEW TABLE AS new_orders
FOR EACH STATEMENT
EXECUTE FUNCTION audit.log_order_price_changes();

This approach can be much more efficient than issuing one audit INSERT from every affected row because the trigger function runs once and processes the changed set relationally. It also gives the function a statement-wide perspective that an isolated row trigger does not naturally have.[2][5]

9.2 Set-wise summary maintenance

CREATE TABLE app.daily_sales (
    sales_date date PRIMARY KEY,
    gross numeric(18,2) NOT NULL
);

CREATE OR REPLACE FUNCTION app.apply_inserted_sales()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    INSERT INTO app.daily_sales(sales_date, gross)
    SELECT
        sold_at::date,
        sum(total)
    FROM inserted_sales
    GROUP BY sold_at::date
    ON CONFLICT (sales_date)
    DO UPDATE SET gross =
        app.daily_sales.gross + EXCLUDED.gross;

    RETURN NULL;
END;
$$;

CREATE TRIGGER sale_90_summary_insert
AFTER INSERT
ON app.sale
REFERENCING NEW TABLE AS inserted_sales
FOR EACH STATEMENT
EXECUTE FUNCTION app.apply_inserted_sales();
Summary maintenance must handle every mutation path. If inserts increase a summary, updates that move rows across groups and deletes that remove rows also need correct inverse/delta logic. Missing one path silently corrupts derived data.

10. WHEN conditions and UPDATE OF

A trigger can include a Boolean WHEN condition. For row triggers the condition can reference OLD and/or NEW as appropriate. For an AFTER trigger, PostgreSQL evaluates the condition immediately after the row change and queues the trigger event only when the condition is true, which can materially reduce overhead when only a small fraction of rows require trigger execution.[2][5] 

CREATE TRIGGER invoice_90_notify_paid
AFTER UPDATE
ON app.invoice
FOR EACH ROW
WHEN (
    OLD.status IS DISTINCT FROM NEW.status
    AND NEW.status = 'paid'
)
EXECUTE FUNCTION app.invoice_became_paid();

10.1 UPDATE OF is syntactic targeting

CREATE TRIGGER product_20_recalculate
BEFORE UPDATE OF quantity, unit_price
ON app.line_item
FOR EACH ROW
EXECUTE FUNCTION app.recalculate_line_total();

An UPDATE OF trigger fires when a listed column appears as a target of the UPDATE, not only when its value changes. For example, SET quantity = quantity still qualifies. Conversely, a listed value can be changed indirectly by an earlier BEFORE trigger even if the original statement did not target that column. Use WHEN (OLD.column IS DISTINCT FROM NEW.column) when actual value change is the intended condition.[5]

11. Trigger ordering and interactions

When multiple triggers of the same kind apply to the same event on a relation, PostgreSQL fires them alphabetically by trigger name rather than by creation time. Naming can therefore encode ordering intentionally, but hidden order dependencies are a maintainability risk.[2][5] 

customer_10_normalize
customer_20_validate_business_rule
customer_90_audit

For row-level BEFORE triggers, each trigger sees the row returned by earlier BEFORE triggers. If one returns NULL, the row operation and remaining row triggers are skipped. An INSERT ... ON CONFLICT DO UPDATE statement can execute both insert and update trigger paths when rows encounter conflicts, so functions shared between those events must be safe under that control flow.[2][5]

11.1 Avoid accidental recursion

-- Risky design:
-- An UPDATE trigger on app.account issues UPDATE app.account ...
-- which invokes the trigger again.

A trigger that writes to its own table can recursively fire itself. PostgreSQL does not prohibit such recursion. Prefer modifying NEW in a BEFORE trigger when the goal is to change the current row. When recursive cross-row updates are genuinely required, design a termination condition and consider the concurrency implications explicitly.[2]

12. Visibility of data changes

Trigger timing changes which effects are visible to SQL executed inside the trigger. Statement-level BEFORE triggers see none of the modifications of the triggering statement; statement-level AFTER triggers see all of them. A row-level BEFORE trigger does not see its own not-yet-performed row modification, although it can see modifications already made to previously processed rows of the same statement. The order in which a multi-row command processes rows is not generally predictable, so depending on those partial effects is unsafe. A row-level AFTER trigger sees the command's completed changes.[4]

Do not enforce cross-row invariants by assuming row-processing order in a BEFORE ROW trigger. For set-wide logic, use declarative constraints, statement-level transition tables, explicit locking, or an appropriate deferred constraint trigger.

13. Audit logging with triggers

13.1 What trigger-based auditing is good at

A data-change trigger can capture old/new row images, the database user, operation type, transaction-visible application context, and timestamps independently of which application code path performed the write. PostgreSQL's PL/pgSQL documentation includes row-level auditing as a canonical trigger use case.[6]

13.2 Generic JSONB audit design

CREATE SCHEMA audit;

CREATE TABLE audit.row_history (
    audit_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    occurred_at timestamptz NOT NULL DEFAULT clock_timestamp(),
    txid bigint NOT NULL DEFAULT pg_current_xact_id()::text::bigint,
    session_user_name name NOT NULL DEFAULT session_user,
    current_user_name name NOT NULL DEFAULT current_user,
    application_name text DEFAULT current_setting('application_name', true),
    schema_name name NOT NULL,
    table_name name NOT NULL,
    operation text NOT NULL,
    old_row jsonb,
    new_row jsonb
);
CREATE OR REPLACE FUNCTION audit.capture_row()
RETURNS trigger
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = pg_catalog, audit
AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN
        INSERT INTO audit.row_history(
            schema_name, table_name, operation, new_row
        )
        VALUES (
            TG_TABLE_SCHEMA, TG_TABLE_NAME, TG_OP, to_jsonb(NEW)
        );
        RETURN NULL;

    ELSIF TG_OP = 'UPDATE' THEN
        INSERT INTO audit.row_history(
            schema_name, table_name, operation, old_row, new_row
        )
        VALUES (
            TG_TABLE_SCHEMA, TG_TABLE_NAME, TG_OP,
            to_jsonb(OLD), to_jsonb(NEW)
        );
        RETURN NULL;

    ELSIF TG_OP = 'DELETE' THEN
        INSERT INTO audit.row_history(
            schema_name, table_name, operation, old_row
        )
        VALUES (
            TG_TABLE_SCHEMA, TG_TABLE_NAME, TG_OP, to_jsonb(OLD)
        );
        RETURN NULL;
    END IF;

    RAISE EXCEPTION 'unsupported trigger operation: %', TG_OP;
END;
$$;
REVOKE ALL ON FUNCTION audit.capture_row() FROM PUBLIC;

CREATE TRIGGER customer_90_audit
AFTER INSERT OR UPDATE OR DELETE
ON app.customer
FOR EACH ROW
EXECUTE FUNCTION audit.capture_row();

A SECURITY DEFINER audit function can let application roles write audit records without granting direct write access to the audit table, but it becomes a privileged code boundary and must use a safe, controlled search_path and minimal owner privileges. PostgreSQL's security guidance for security-definer functions applies to trigger functions as it does to ordinary callable functions.[10]

13.3 Limitations

Trigger-based audit rows are transactional. They record committed database state changes well, but a transaction rollback removes both the original data changes and its trigger-written audit rows. Privileged users can also alter or disable triggers. When an audit requirement includes failed statements, administrator activity, DDL, or tamper-resistant evidence, combine data triggers with protected server/audit logs and external log retention rather than treating the audit table as the sole security record.[4][11]

14. Automatic data maintenance

Triggers can maintain derived state when an invariant needs to hold immediately inside the same database transaction. PostgreSQL's own PL/pgSQL documentation includes automatic row stamping and summary-table maintenance as canonical examples.[6]

14.1 Maintain a denormalized count

CREATE TABLE app.project (
    project_id bigint PRIMARY KEY,
    open_task_count bigint NOT NULL DEFAULT 0
);

CREATE TABLE app.task (
    task_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    project_id bigint NOT NULL REFERENCES app.project(project_id),
    status text NOT NULL
        CHECK (status IN ('open', 'closed'))
);
CREATE OR REPLACE FUNCTION app.maintain_open_task_count()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN
        IF NEW.status = 'open' THEN
            UPDATE app.project
            SET open_task_count = open_task_count + 1
            WHERE project_id = NEW.project_id;
        END IF;

    ELSIF TG_OP = 'DELETE' THEN
        IF OLD.status = 'open' THEN
            UPDATE app.project
            SET open_task_count = open_task_count - 1
            WHERE project_id = OLD.project_id;
        END IF;

    ELSIF TG_OP = 'UPDATE' THEN
        -- Handle project moves and status changes.
        IF OLD.project_id = NEW.project_id THEN
            IF OLD.status = 'closed' AND NEW.status = 'open' THEN
                UPDATE app.project
                SET open_task_count = open_task_count + 1
                WHERE project_id = NEW.project_id;
            ELSIF OLD.status = 'open' AND NEW.status = 'closed' THEN
                UPDATE app.project
                SET open_task_count = open_task_count - 1
                WHERE project_id = NEW.project_id;
            END IF;
        ELSE
            IF OLD.status = 'open' THEN
                UPDATE app.project
                SET open_task_count = open_task_count - 1
                WHERE project_id = OLD.project_id;
            END IF;

            IF NEW.status = 'open' THEN
                UPDATE app.project
                SET open_task_count = open_task_count + 1
                WHERE project_id = NEW.project_id;
            END IF;
        END IF;
    END IF;

    RETURN NULL;
END;
$$;

CREATE TRIGGER task_80_maintain_project
AFTER INSERT OR UPDATE OR DELETE
ON app.task
FOR EACH ROW
EXECUTE FUNCTION app.maintain_open_task_count();

This provides transactionally consistent derived data, but it also introduces write amplification and lock contention on popular parent rows. For high-write workloads, set-wise transition-table maintenance, query-time aggregation, materialized views, asynchronous processing, or another architecture may be preferable depending on freshness requirements.

14.2 Built-in trigger functions

PostgreSQL also supplies a small number of reusable built-in trigger functions, including suppress_redundant_updates_trigger() and tsvector_update_trigger(). The latter exists for automatic text-search vector maintenance, although generated columns are another design option for derived values where the expression rules permit them.[12]

15. Constraint triggers

A constraint trigger is a special AFTER ROW trigger on a plain table whose firing can be immediate or deferred. If it is DEFERRABLE, SET CONSTRAINTS can switch its timing between immediate and deferred; an initially deferred constraint trigger can wait until transaction end. PostgreSQL expects constraint triggers to raise an exception when the invariant they implement is violated.[5][13]

15.1 Deferred cross-row invariant

Suppose allocations may be inserted or updated in any order inside one transaction, but the committed total for a project must never exceed its budget. A deferred constraint trigger can check the final transactional state. The example locks the parent project row to serialize concurrent budget checks for the same project.

CREATE TABLE finance.project_budget (
    project_id bigint PRIMARY KEY,
    budget numeric(14,2) NOT NULL CHECK (budget >= 0)
);

CREATE TABLE finance.allocation (
    allocation_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    project_id bigint NOT NULL
        REFERENCES finance.project_budget(project_id),
    amount numeric(14,2) NOT NULL CHECK (amount >= 0)
);
CREATE OR REPLACE FUNCTION finance.check_project_budget()
RETURNS trigger
LANGUAGE plpgsql
AS $$
DECLARE
    v_project_id bigint;
    v_budget numeric(14,2);
    v_allocated numeric(14,2);
BEGIN
    v_project_id := COALESCE(NEW.project_id, OLD.project_id);

    -- Serialize checks/changes for this project.
    SELECT budget
    INTO v_budget
    FROM finance.project_budget
    WHERE project_id = v_project_id
    FOR UPDATE;

    SELECT COALESCE(sum(amount), 0)
    INTO v_allocated
    FROM finance.allocation
    WHERE project_id = v_project_id;

    IF v_allocated > v_budget THEN
        RAISE EXCEPTION
            'project % allocation % exceeds budget %',
            v_project_id, v_allocated, v_budget
            USING ERRCODE = '23514';
    END IF;

    RETURN NULL;
END;
$$;

CREATE CONSTRAINT TRIGGER allocation_budget_check
AFTER INSERT OR UPDATE OR DELETE
ON finance.allocation
DEFERRABLE
INITIALLY DEFERRED
FOR EACH ROW
EXECUTE FUNCTION finance.check_project_budget();
BEGIN;

INSERT INTO finance.allocation(project_id, amount)
VALUES (7, 3000), (7, 2000);

-- Force deferred checks now instead of waiting for COMMIT:
SET CONSTRAINTS allocation_budget_check IMMEDIATE;

COMMIT;

Constraint triggers are useful when an invariant genuinely needs deferred evaluation and cannot be represented by PostgreSQL's declarative constraint types. They are not a substitute for ordinary CHECK, UNIQUE, exclusion, primary-key, or foreign-key constraints where those features can express the rule. Also, because a constraint trigger is row-level, a bulk statement can queue many deferred events; functions should be designed with that cost in mind.[5][7]

16. Event triggers

Event triggers are database-wide hooks for supported database/DDL events. Unlike ordinary triggers, they are not attached to one table and do not process DML row changes. PostgreSQL 18 event-trigger events include ddl_command_start, ddl_command_end, sql_drop, table_rewrite, and login. Event trigger functions return the pseudo-type event_trigger.[3][14]

16.1 DDL audit table

CREATE TABLE audit.ddl_history (
    audit_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    occurred_at timestamptz NOT NULL DEFAULT clock_timestamp(),
    actor name NOT NULL,
    command_tag text NOT NULL,
    object_type text,
    schema_name text,
    object_identity text
);
CREATE OR REPLACE FUNCTION audit.capture_ddl()
RETURNS event_trigger
LANGUAGE plpgsql
AS $$
DECLARE
    cmd record;
BEGIN
    FOR cmd IN
        SELECT *
        FROM pg_event_trigger_ddl_commands()
    LOOP
        INSERT INTO audit.ddl_history(
            actor,
            command_tag,
            object_type,
            schema_name,
            object_identity
        )
        VALUES (
            session_user,
            cmd.command_tag,
            cmd.object_type,
            cmd.schema_name,
            cmd.object_identity
        );
    END LOOP;
END;
$$;

CREATE EVENT TRIGGER audit_ddl_end
ON ddl_command_end
EXECUTE FUNCTION audit.capture_ddl();

pg_event_trigger_ddl_commands() is available inside ddl_command_end event-trigger functions and returns information about base DDL commands performed by the user action. If a ddl_command_end event trigger raises an error, the DDL statement is rolled back with the transaction.[14][15]

16.2 Capture dropped objects

CREATE TABLE audit.drop_history (
    audit_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    occurred_at timestamptz NOT NULL DEFAULT clock_timestamp(),
    actor name NOT NULL,
    object_type text,
    schema_name text,
    object_identity text,
    original boolean,
    normal boolean
);

CREATE OR REPLACE FUNCTION audit.capture_drops()
RETURNS event_trigger
LANGUAGE plpgsql
AS $$
BEGIN
    INSERT INTO audit.drop_history(
        actor,
        object_type,
        schema_name,
        object_identity,
        original,
        normal
    )
    SELECT
        session_user,
        object_type,
        schema_name,
        object_identity,
        original,
        normal
    FROM pg_event_trigger_dropped_objects();
END;
$$;

CREATE EVENT TRIGGER audit_sql_drop
ON sql_drop
EXECUTE FUNCTION audit.capture_drops();

16.3 Governing DDL

CREATE OR REPLACE FUNCTION admin.block_drop_table()
RETURNS event_trigger
LANGUAGE plpgsql
AS $$
BEGIN
    RAISE EXCEPTION
        'DROP TABLE is disabled in this database; use the deployment pipeline';
END;
$$;

CREATE EVENT TRIGGER guard_drop_table
ON ddl_command_start
WHEN TAG IN ('DROP TABLE')
EXECUTE FUNCTION admin.block_drop_table();

Event-trigger WHEN TAG IN (...) filters let an administrator apply a trigger only to selected command tags. Multiple event triggers for the same event fire in alphabetical name order. Because a broken event trigger can interfere with essential DDL—and login event triggers can affect connections—event triggers require particularly careful testing and operational recovery planning.[14][16]

17. Triggers and partitioned tables

Creating a row-level trigger on a partitioned table causes PostgreSQL to create corresponding clone triggers on existing partitions, and matching clones are created for partitions attached or created later. When a partition is detached, its clone triggers are removed. Statement-level triggers behave differently: when a statement targets a partitioned parent, statement triggers attached to the explicitly named parent fire, while statement triggers on individual partitions do not automatically fire just because their rows were modified through the parent.[5][17]

17.1 Inspect cloned triggers

SELECT
    c.oid::regclass AS relation,
    t.tgname,
    t.tgparentid,
    t.tgenabled
FROM pg_trigger AS t
JOIN pg_class AS c
  ON c.oid = t.tgrelid
WHERE NOT t.tgisinternal
ORDER BY relation::text, t.tgname;

The pg_trigger.tgparentid column identifies a trigger cloned from a parent trigger. This is useful when diagnosing trigger behavior across partition hierarchies.[17]

18. Triggers and replication behavior

PostgreSQL's session_replication_role setting controls whether replication-related triggers and rules fire for a session. The default is origin. Logical replication apply processes can use replica, under which triggers in their default configuration do not fire. Individual triggers can be configured through ALTER TABLE ... ENABLE TRIGGER variants to fire in origin, replica, or always modes.[18][19] 

ALTER TABLE app.orders ENABLE REPLICA TRIGGER orders_replica_hook;
ALTER TABLE app.orders ENABLE ALWAYS  TRIGGER orders_always_hook;
ALTER TABLE app.orders ENABLE         TRIGGER orders_normal_hook;
ALTER TABLE app.orders DISABLE        TRIGGER orders_disabled_hook;
Replication semantics must be designed, not assumed. A trigger that maintains local derived tables or audit state may need different behavior on a logical subscriber than it has on the publisher. Test the actual replication mode and trigger-enable state.

19. Trigger performance engineering

19.1 Invocation count is multiplicative

A row trigger runs once per affected row, so its cost multiplies with statement cardinality. If a function performs another indexed lookup, JSON conversion, or write for each row, a bulk statement can turn one SQL operation into millions of additional operations. Statement-level transition tables can often convert that procedural loop into a set-based query.[5]

19.2 Use WHEN to avoid needless AFTER events

CREATE TRIGGER account_90_balance_audit
AFTER UPDATE
ON app.account
FOR EACH ROW
WHEN (OLD.balance IS DISTINCT FROM NEW.balance)
EXECUTE FUNCTION audit.capture_balance_change();

For an AFTER trigger, PostgreSQL evaluates the WHEN condition before queuing the trigger event. A selective predicate can therefore avoid later event processing for rows that do not matter.[5]

19.3 Prefer set-oriented SQL inside triggers

Transition tables make it possible to aggregate, join, and write all affected rows in one invocation. This usually gives PostgreSQL's planner more opportunity to optimize the work than repeatedly running the same statement from a row trigger.

19.4 Watch lock amplification

Triggers can touch tables not named in the caller's statement, so they can expand the lock footprint and create deadlock paths that are not obvious from application SQL. Use consistent lock/update ordering across trigger code and application code, keep transactions short, and monitor blocking through pg_stat_activity and pg_locks.[20][21]

19.5 Avoid synchronous external side effects

A database trigger executes inside the SQL transaction. Calling external HTTP services or other unreliable remote systems from trigger code couples transaction latency and correctness to network behavior, while PostgreSQL cannot atomically commit the remote side effect with the database transaction. A safer pattern is often to write an outbox/event row transactionally and have a separate worker deliver the external side effect after commit. 

CREATE TABLE app.outbox (
    event_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    event_type text NOT NULL,
    aggregate_id bigint NOT NULL,
    payload jsonb NOT NULL,
    created_at timestamptz NOT NULL DEFAULT clock_timestamp(),
    published_at timestamptz
);

-- Trigger performs only a local transactional INSERT.
INSERT INTO app.outbox(event_type, aggregate_id, payload)
VALUES ('invoice.paid', NEW.invoice_id, to_jsonb(NEW));

20. Inspecting and operating triggers

20.1 Information schema

SELECT
    trigger_schema,
    trigger_name,
    event_manipulation,
    event_object_schema,
    event_object_table,
    action_timing,
    action_orientation,
    action_condition
FROM information_schema.triggers
ORDER BY event_object_schema,
         event_object_table,
         action_order;

The SQL-standard information_schema.triggers view exposes ordinary triggers visible to the current user, including event, timing, orientation, condition, and transition-table metadata. PostgreSQL's reported action order reflects its alphabetical trigger-name firing order.[22]

20.2 Catalog-level inspection

SELECT
    c.oid::regclass AS relation,
    t.tgname,
    t.tgenabled,
    t.tgisinternal,
    p.oid::regprocedure AS trigger_function,
    pg_get_triggerdef(t.oid, true) AS definition
FROM pg_trigger AS t
JOIN pg_class AS c ON c.oid = t.tgrelid
JOIN pg_proc  AS p ON p.oid = t.tgfoid
WHERE NOT t.tgisinternal
ORDER BY relation::text, t.tgname;

20.3 Event-trigger inventory

SELECT
    e.evtname,
    e.evtevent,
    e.evtenabled,
    e.evttags,
    p.oid::regprocedure AS function_name
FROM pg_event_trigger AS e
JOIN pg_proc AS p ON p.oid = e.evtfoid
ORDER BY e.evtevent, e.evtname;

Ordinary triggers are stored in pg_trigger; event triggers are stored in pg_event_trigger. Internal triggers also exist—for example, PostgreSQL uses trigger mechanisms internally for some constraints—so operational queries often filter tgisinternal when inventorying application-defined triggers.[17][23]

20.4 Temporarily disabling triggers

ALTER TABLE app.orders DISABLE TRIGGER orders_90_audit;

-- ... controlled maintenance ...

ALTER TABLE app.orders ENABLE TRIGGER orders_90_audit;

Disabling triggers changes correctness behavior and should be tightly controlled. DISABLE TRIGGER ALL can include internally generated constraint triggers and normally requires elevated privileges for system constraint triggers. Bulk-load procedures should prefer designs that preserve constraints and maintenance logic unless bypass is explicitly safe.[19]

21.1 Production checklist

  1. Prefer declarative schema features when they express the rule directly.
  2. Name triggers intentionally because equal-kind triggers fire alphabetically.
  3. Use BEFORE triggers to modify NEW rather than issuing a second update to the same row.
  4. Use AFTER triggers for observation of final row changes.
  5. Use statement-level transition tables when logic is naturally set-oriented.
  6. Make every mutation path explicit: INSERT, UPDATE, DELETE, TRUNCATE, conflict updates, cascades, and partition routing where relevant.
  7. Test bulk statements, not only single-row operations.
  8. Test concurrency for cross-row/cross-table invariants and derived counters.
  9. Test rollback behavior so transactional audit/maintenance semantics are understood.
  10. Review replication behavior and session_replication_role implications.
  11. Avoid hidden remote side effects from inside database transactions.
  12. Inventory triggers during schema review so behavior does not become invisible institutional knowledge.
Trigger design principle: keep the trigger small, deterministic, transactionally appropriate, and close to the invariant it protects. The more hidden work a trigger performs, the more important it becomes to document, benchmark, and test it as part of the schema itself.
