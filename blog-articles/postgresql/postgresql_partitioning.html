PostgreSQL Partitioning

A production-oriented guide to declarative range, list, and hash partitioning; subpartitioning; partition pruning; partition-wise joins and aggregates; partition maintenance; time-series retention; partitioned indexes and constraints; and the architectural boundary between partitioning and sharding.

Technical article • PostgreSQL 18.6 baseline • Updated 15 September 2026 • Vancouver-style references

Abstract

PostgreSQL partitioning divides one logical table into smaller physical relations called partitions. In declarative partitioning, the parent is a virtual partitioned table with no row storage of its own; rows are stored in leaf partitions and PostgreSQL automatically routes inserts and partition-key-changing updates to the correct partition. PostgreSQL supports range, list, and hash strategies, and any partition can itself be partitioned to form a multi-level hierarchy.[1][2]

Partitioning is most useful when the partition boundary matches actual workload boundaries. PostgreSQL can prune partitions whose bounds cannot satisfy a query, both during planning and—in supported parameterized cases—during execution. Partitioning can also make retention and bulk lifecycle operations much cheaper because entire partitions can be attached, detached, or dropped instead of deleting rows individually. However, partitioning is not a general-purpose accelerator: excessive partition counts increase planning and memory overhead, poorly chosen keys prevent pruning, and every partition still resides inside the same PostgreSQL cluster unless an external/distributed system places data on multiple nodes.[1][3]

PostgreSQL 18 improves planning efficiency for queries involving many partitions and expands cases in which partition-wise joins can be applied while reducing their memory usage. These improvements do not remove the need for conservative partition counts and workload-driven design; partition-wise join and aggregate planning remain disabled by default because they can multiply plan nodes and memory consumption across partitions.[4][5]

1. Why partition a table?

Partitioning is a physical data-management technique. It can improve query performance when pruning reduces a query to a small subset of the data, improve cache locality by keeping hot partitions and their indexes small, enable sequential scans of appropriately sized partitions, and make bulk lifecycle operations such as retention much cheaper. PostgreSQL also allows different partitions to use different tablespaces, so cold data can be placed on slower storage while recent data remains on faster storage.[1]

logical table: telemetry +-----------------------------------------------------------+ | Jan | Feb | Mar | Apr | May | Jun | Jul | Aug | ... | +-----------------------------------------------------------+ | | | | | v v v v v physical partition relations Query: WHERE observed_at >= '2026-09-10' AND observed_at < '2026-09-11' Planner/executor: old partitions X X X X X X X X September partition -> scan only relevant leaf

1.1 What partitioning does not automatically solve

Partitioning does not automatically make every query faster. A query that cannot constrain the partition key may still scan many or all partitions. It does not eliminate the need for indexes inside partitions, and it does not create additional database servers or distribute writes across independent PostgreSQL nodes. It should be justified by measured query, maintenance, retention, or storage-placement needs.[1]

Good partition keys align with real boundaries: common WHERE predicates, retention intervals, lifecycle operations, or naturally isolated data groups.

2. Declarative partitioning architecture

A declaratively partitioned table is defined with PARTITION BY. The parent relation stores partition metadata but no table rows; storage belongs to its partitions. Each partition has bounds defining the subset it accepts, and PostgreSQL automatically routes rows inserted through the parent. Partitions are otherwise table-like relations and may have their own indexes, tablespaces, and additional constraints.[1][2] 

CREATE TABLE telemetry.reading (
    observed_at timestamptz NOT NULL,
    device_id bigint NOT NULL,
    metric_id integer NOT NULL,
    value double precision NOT NULL
)
PARTITION BY RANGE (observed_at);

The partition key can use columns or expressions. Range and hash partition keys may contain multiple columns or expressions; list partitioning uses one column or expression. Range/list keys rely on B-tree operator classes, while hash partitioning uses a hash operator class.[2]

2.1 Parent, intermediate, and leaf relations

telemetry.reading -- partitioned parent | +-- reading_2026_08 -- leaf table | +-- reading_2026_09 -- leaf table | +-- reading_2026_10 -- leaf table Multi-level hierarchy: events -- RANGE by month | +-- events_2026_09 -- HASH by tenant_id | +-- events_2026_09_h0 -- leaf | +-- events_2026_09_h1 -- leaf | +-- events_2026_09_h2 -- leaf | +-- events_2026_09_h3 -- leaf | +-- events_2026_10 +-- ...

3. Range partitioning

Range partitioning divides values into non-overlapping intervals. Bounds are inclusive on the lower side and exclusive on the upper side. A monthly partition declared from 2026-09-01 to 2026-10-01 therefore contains September but not midnight at the start of October.[1] 

CREATE TABLE telemetry.reading_2026_09
PARTITION OF telemetry.reading
FOR VALUES FROM ('2026-09-01 00:00:00+00')
             TO ('2026-10-01 00:00:00+00');

CREATE TABLE telemetry.reading_2026_10
PARTITION OF telemetry.reading
FOR VALUES FROM ('2026-10-01 00:00:00+00')
             TO ('2026-11-01 00:00:00+00');

3.1 Why range partitioning dominates time-series designs

A time predicate naturally maps to ordered intervals, old intervals can be detached/dropped as one unit, and new future partitions can be created predictably. Daily, weekly, monthly, or quarterly partitions are common choices; the correct interval depends on ingestion volume, retention operations, query windows, and acceptable partition count.

3.2 Multi-column range keys

CREATE TABLE finance.ledger (
    business_date date NOT NULL,
    account_id bigint NOT NULL,
    entry_id bigint NOT NULL,
    amount numeric(18,2) NOT NULL
)
PARTITION BY RANGE (business_date, account_id);

Multi-column ranges use row-comparison semantics and can express complex ordered regions. They should be used only when application predicates and lifecycle boundaries actually benefit from the extra dimension; subpartitioning can sometimes be clearer.

3.3 MINVALUE and MAXVALUE

CREATE TABLE finance.ledger_old
PARTITION OF finance.ledger
FOR VALUES FROM (MINVALUE, MINVALUE)
             TO ('2024-01-01', MINVALUE);

MINVALUE and MAXVALUE provide open-ended range bounds. Their ordering follows the partition key definition and is subject to PostgreSQL's range-bound rules.[2]

4. List partitioning

List partitioning assigns explicit values to partitions. It is useful when the number of data groups is relatively small and semantically stable—for example geographic region, data source, or a small set of tenant tiers.[1] 

CREATE TABLE commerce.order_event (
    event_id bigint NOT NULL,
    region_code text NOT NULL,
    occurred_at timestamptz NOT NULL,
    payload jsonb NOT NULL
)
PARTITION BY LIST (region_code);

CREATE TABLE commerce.order_event_us
PARTITION OF commerce.order_event
FOR VALUES IN ('US');

CREATE TABLE commerce.order_event_ca
PARTITION OF commerce.order_event
FOR VALUES IN ('CA');

CREATE TABLE commerce.order_event_eu
PARTITION OF commerce.order_event
FOR VALUES IN ('DE', 'FR', 'ES', 'IT', 'NL');

4.1 NULL in list partitioning

CREATE TABLE commerce.order_event_unknown
PARTITION OF commerce.order_event
FOR VALUES IN (NULL);

List partitioning can route null partition-key values explicitly when NULL is included in a partition bound.[2]

4.2 Avoid one-partition-per-entity explosions

A list partition per customer can seem attractive with tens of customers and become operationally expensive with tens of thousands. PostgreSQL's best-practice guidance specifically warns that future growth can make such a design impractical and suggests hash partitioning with a reasonable fixed number of partitions when entity count may grow substantially.[1]

5. Hash partitioning

Hash partitioning assigns rows using a hash of the partition key and partitions described by a modulus/remainder pair. It is useful when the goal is relatively even distribution rather than semantic ranges or explicit value groups.[1][2] 

CREATE TABLE app.session_event (
    tenant_id bigint NOT NULL,
    session_id uuid NOT NULL,
    occurred_at timestamptz NOT NULL,
    payload jsonb NOT NULL
)
PARTITION BY HASH (tenant_id);

CREATE TABLE app.session_event_h0
PARTITION OF app.session_event
FOR VALUES WITH (MODULUS 8, REMAINDER 0);

CREATE TABLE app.session_event_h1
PARTITION OF app.session_event
FOR VALUES WITH (MODULUS 8, REMAINDER 1);

CREATE TABLE app.session_event_h2
PARTITION OF app.session_event
FOR VALUES WITH (MODULUS 8, REMAINDER 2);

CREATE TABLE app.session_event_h3
PARTITION OF app.session_event
FOR VALUES WITH (MODULUS 8, REMAINDER 3);

CREATE TABLE app.session_event_h4
PARTITION OF app.session_event
FOR VALUES WITH (MODULUS 8, REMAINDER 4);

CREATE TABLE app.session_event_h5
PARTITION OF app.session_event
FOR VALUES WITH (MODULUS 8, REMAINDER 5);

CREATE TABLE app.session_event_h6
PARTITION OF app.session_event
FOR VALUES WITH (MODULUS 8, REMAINDER 6);

CREATE TABLE app.session_event_h7
PARTITION OF app.session_event
FOR VALUES WITH (MODULUS 8, REMAINDER 7);

5.1 Hash partitioning does not distribute across servers

These eight partitions are still relations inside the same PostgreSQL database cluster. Hash partitioning can spread data across partitions/tablespaces and improve local data management, but it is not the same thing as distributed sharding across independent nodes.[1][24]

6. Multi-level partitioning

A partition can itself be a partitioned table. This enables hierarchical strategies such as range-by-time followed by hash-by-tenant, or list-by-region followed by range-by-date. PostgreSQL does not verify that a subpartitioning definition is logically constrained to the parent partition's bounds, so administrators must define consistent subpartition ranges themselves.[1]

6.1 Range by month, then hash by tenant

CREATE TABLE app.event (
    tenant_id bigint NOT NULL,
    occurred_at timestamptz NOT NULL,
    event_id uuid NOT NULL,
    payload jsonb NOT NULL
)
PARTITION BY RANGE (occurred_at);

CREATE TABLE app.event_2026_09
PARTITION OF app.event
FOR VALUES FROM ('2026-09-01')
             TO ('2026-10-01')
PARTITION BY HASH (tenant_id);

CREATE TABLE app.event_2026_09_h0
PARTITION OF app.event_2026_09
FOR VALUES WITH (MODULUS 4, REMAINDER 0);

CREATE TABLE app.event_2026_09_h1
PARTITION OF app.event_2026_09
FOR VALUES WITH (MODULUS 4, REMAINDER 1);

CREATE TABLE app.event_2026_09_h2
PARTITION OF app.event_2026_09
FOR VALUES WITH (MODULUS 4, REMAINDER 2);

CREATE TABLE app.event_2026_09_h3
PARTITION OF app.event_2026_09
FOR VALUES WITH (MODULUS 4, REMAINDER 3);

6.2 Partition-count multiplication

Hierarchies multiply quickly. Thirty-six monthly partitions each split into 32 hash partitions produce 1,152 leaf partitions. PostgreSQL can handle large trees, but planning time, memory consumption, metadata management, autovacuum activity, and schema operations all grow with partition count. PostgreSQL's best-practice guidance explicitly recommends restraint in subpartitioning designs.[1]

7. Tuple routing and partition-key updates

Rows inserted through a partitioned parent are routed automatically according to the partition key. If no partition accepts the row and there is no default partition, the insert fails. Updating a partition key can move the row from one leaf partition to another.[1][2] 

INSERT INTO telemetry.reading(
    observed_at,
    device_id,
    metric_id,
    value
)
VALUES (
    '2026-09-15 18:00:00+00',
    101,
    7,
    42.5
);

The application does not need to name reading_2026_09; PostgreSQL performs tuple routing internally.

7.1 Partition movement on UPDATE

UPDATE telemetry.reading
SET observed_at = '2026-10-01 00:00:00+00'
WHERE device_id = 101
  AND observed_at = '2026-09-30 23:59:59+00';

If the target key now belongs to October, PostgreSQL moves the row to the October partition. A limitation is that a BEFORE ROW trigger on INSERT cannot rewrite a row in a way that changes its final partition destination after routing semantics are determined.[1]

8. Partition pruning

Partition pruning eliminates partitions whose bounds cannot satisfy a query predicate. It relies on partition bounds, not indexes. A table can therefore benefit from pruning even without an index on the partition key; whether each surviving partition also needs an index depends on how much of that partition the query will scan.[1]

8.1 A pruning-friendly query

SET enable_partition_pruning = on;

EXPLAIN (ANALYZE, BUFFERS)
SELECT
    device_id,
    avg(value)
FROM telemetry.reading
WHERE observed_at >= timestamptz '2026-09-10 00:00:00+00'
  AND observed_at <  timestamptz '2026-09-11 00:00:00+00'
GROUP BY device_id;

If the table is partitioned monthly by observed_at, PostgreSQL can eliminate every partition except September before scanning tuples.

8.2 Predicate shape matters

-- Direct key predicate: pruning-friendly.
WHERE observed_at >= $1
  AND observed_at <  $2

-- Potentially less directly provable depending on expression/partition key:
WHERE date_trunc('day', observed_at) = $1::date

Partitioning works best when common query predicates line up with the partition-key expression and bounds. PostgreSQL recommends choosing partition columns that frequently appear in compatible WHERE clauses.[1]

8.3 Pruning versus constraint exclusion

Declarative partition pruning uses partition bounds and can occur at planning and execution time. Constraint exclusion examines CHECK constraints and is primarily useful for legacy inheritance partitioning; it applies only at plan time and is slower to plan because it examines constraints rather than specialized partition metadata.[1]

9. Execution-time partition pruning

PostgreSQL can prune partitions after planning when parameter values become available only during execution. This includes prepared-statement parameters, values from subqueries, and parameterized inner scans of nested-loop joins. Pruning can happen during plan initialization or repeatedly during execution when a relevant parameter changes.[1][5]

9.1 Prepared query

PREPARE reading_window(timestamptz, timestamptz) AS
SELECT
    device_id,
    observed_at,
    value
FROM telemetry.reading
WHERE observed_at >= $1
  AND observed_at <  $2;

EXPLAIN (ANALYZE, BUFFERS)
EXECUTE reading_window(
    '2026-09-01',
    '2026-09-02'
);

In EXPLAIN, partitions eliminated during initialization can be reflected by a Subplans Removed count. Partitions eliminated dynamically during execution can appear with differing loop counts or as (never executed) in EXPLAIN ANALYZE.[1]

9.2 Important locking detail

PostgreSQL notes that partitions removed during initialization-time pruning are still locked at the beginning of query execution. Pruning reduces scan work; it does not necessarily eliminate every partition-related lock acquisition.[1]

10. Partition-wise joins

Partition-wise join allows PostgreSQL to replace one large join between partitioned tables with joins between corresponding partitions. PostgreSQL 18's planner setting enable_partitionwise_join is disabled by default. It currently applies when join conditions include all partition keys, the key types match, and child partitions have one-to-one compatible bounds.[5]

10.1 Compatible partition layouts

CREATE TABLE analytics.orders (
    tenant_id bigint NOT NULL,
    order_id bigint NOT NULL,
    total numeric NOT NULL
)
PARTITION BY HASH (tenant_id);

CREATE TABLE analytics.customers (
    tenant_id bigint NOT NULL,
    customer_id bigint NOT NULL,
    name text NOT NULL
)
PARTITION BY HASH (tenant_id);

-- Both hierarchies use the same MODULUS and REMAINDER layout.
SET enable_partitionwise_join = on;

EXPLAIN (ANALYZE, BUFFERS)
SELECT
    o.tenant_id,
    count(*),
    sum(o.total)
FROM analytics.orders AS o
JOIN analytics.customers AS c
  ON c.tenant_id = o.tenant_id
WHERE o.tenant_id BETWEEN 100 AND 200
GROUP BY o.tenant_id;

10.2 Memory/planning trade-off

Partition-wise joining can create a separate join subtree for many partitions. PostgreSQL warns that this can increase planning CPU/memory and can multiply the number of execution nodes whose memory is limited independently by work_mem. It is therefore disabled by default and should be enabled/tested for workloads where compatible partition layouts create a measurable benefit.[5]

10.3 PostgreSQL 18 improvements

PostgreSQL 18 expanded the situations in which partition-wise joins can be used and reduced their memory usage, alongside improvements to planning queries that access many partitions. These are planner improvements, not a reason to ignore partition-count discipline.[4]

11. Partition-wise aggregation

With enable_partitionwise_aggregate, PostgreSQL can perform grouping or aggregation independently in partitions before combining results. When GROUP BY includes the partition keys, aggregation can often be fully partition-local; otherwise PostgreSQL may perform partial aggregation per partition followed by finalization above the partitioned scans.[5] 

SET enable_partitionwise_aggregate = on;

EXPLAIN (ANALYZE, BUFFERS)
SELECT
    observed_at::date AS day,
    device_id,
    avg(value)
FROM telemetry.reading
WHERE observed_at >= '2026-09-01'
  AND observed_at <  '2026-10-01'
GROUP BY observed_at::date, device_id;

Like partition-wise joins, partition-wise aggregation can create many plan nodes and increase total memory consumption. The setting is therefore off by default.[5]

12. Partitioned indexes

An index declared on a partitioned table is itself a partitioned or “virtual” index. The actual index data lives in indexes on leaf partitions. Creating an index on the parent normally recurses through current partitions, attaches equivalent existing indexes where possible, and creates missing child indexes. Future partitions automatically receive/attach corresponding indexes.[1][6] 

CREATE INDEX reading_device_time_idx
ON telemetry.reading (
    device_id,
    observed_at DESC
);

12.1 The CREATE INDEX CONCURRENTLY limitation

PostgreSQL does not allow CREATE INDEX CONCURRENTLY directly on a partitioned parent. For large production tables, PostgreSQL documents a staged pattern: create the parent index with ON ONLY so it remains invalid, build child indexes concurrently, then attach each child index. When every required child index is attached, the parent index becomes valid automatically.[1] 

-- 1. Create invalid parent index without recursively building children.
CREATE INDEX reading_device_time_idx
ON ONLY telemetry.reading (
    device_id,
    observed_at DESC
);

-- 2. Build each leaf index concurrently.
CREATE INDEX CONCURRENTLY reading_2026_09_device_time_idx
ON telemetry.reading_2026_09 (
    device_id,
    observed_at DESC
);

-- 3. Attach it to the parent index.
ALTER INDEX telemetry.reading_device_time_idx
ATTACH PARTITION telemetry.reading_2026_09_device_time_idx;

-- Repeat for all leaves.

12.2 Per-partition indexes

Partitions may also have indexes not present on the parent. This can be useful when old/cold partitions have different access patterns from recent/hot partitions, although asymmetric index portfolios increase operational complexity.

13. Unique constraints and primary keys

Global uniqueness is constrained by physical partition boundaries. To create a UNIQUE or PRIMARY KEY constraint on a partitioned table, the constraint must include every partition-key column, and partition keys participating in such a constraint cannot be partition expressions. For multi-level hierarchies, PostgreSQL 18 requires the constraint to include partition-key columns of the target partitioned table and all descendant partitioned tables.[1][2]

13.1 Time-partitioned primary key

CREATE TABLE app.event (
    occurred_at timestamptz NOT NULL,
    event_id uuid NOT NULL,
    tenant_id bigint NOT NULL,
    payload jsonb NOT NULL,
    PRIMARY KEY (occurred_at, event_id)
)
PARTITION BY RANGE (occurred_at);

A primary key on event_id alone cannot be declared globally on this parent, because leaf indexes can only enforce uniqueness inside their own partitions and the partition layout would not prevent the same event_id from appearing in two time partitions.[1]

13.2 Application implication

If the logical identity must be globally unique independent of the partition key, options include changing the partition key, making the partition key part of the identity, maintaining a separate unpartitioned key registry, or using application-level/global coordination. Partitioning strategy and key design therefore cannot be decided independently.

14. Partition maintenance

The ability to manipulate entire partitions is one of partitioning's largest operational advantages. Dropping or detaching a partition avoids deleting rows one at a time and avoids the subsequent vacuum work caused by mass deletion.[1]

14.1 Drop expired data

DROP TABLE telemetry.reading_2024_09;

Dropping a partition is fast relative to deleting its rows, but it requires an ACCESS EXCLUSIVE lock on the parent partitioned table.[1][2]

14.2 Detach before archiving

ALTER TABLE telemetry.reading
DETACH PARTITION telemetry.reading_2024_09;

After detachment, the former partition remains as an independent table. It can be backed up, aggregated, exported, moved, or dropped later.

14.3 Concurrent detach

ALTER TABLE telemetry.reading
DETACH PARTITION telemetry.reading_2024_09
CONCURRENTLY;

PostgreSQL documents DETACH PARTITION ... CONCURRENTLY as requiring only a SHARE UPDATE EXCLUSIVE lock on the parent rather than the stronger lock used by ordinary detach, subject to the command's restrictions.[1][7]

15. Low-lock partition attachment workflow

Creating a new partition directly with CREATE TABLE ... PARTITION OF requires an ACCESS EXCLUSIVE lock on the parent. A production-friendly alternative is to create a standalone table, load and validate it independently, add a matching CHECK constraint, then attach it. ATTACH PARTITION needs a weaker SHARE UPDATE EXCLUSIVE lock on the parent.[1][2]

15.1 Create a staging partition

CREATE TABLE telemetry.reading_2026_11
(
    LIKE telemetry.reading
    INCLUDING DEFAULTS
    INCLUDING CONSTRAINTS
);

ALTER TABLE telemetry.reading_2026_11
ADD CONSTRAINT reading_2026_11_bounds
CHECK (
    observed_at >= timestamptz '2026-11-01 00:00:00+00'
    AND observed_at < timestamptz '2026-12-01 00:00:00+00'
);

15.2 Load and index independently

COPY telemetry.reading_2026_11
FROM '/staging/reading_2026_11.csv'
WITH (FORMAT csv, HEADER true);

CREATE INDEX CONCURRENTLY reading_2026_11_device_time_idx
ON telemetry.reading_2026_11 (
    device_id,
    observed_at DESC
);

15.3 Attach

ALTER TABLE telemetry.reading
ATTACH PARTITION telemetry.reading_2026_11
FOR VALUES FROM ('2026-11-01')
             TO ('2026-12-01');

If PostgreSQL cannot prove from a valid CHECK constraint that every row satisfies the proposed partition bound, it scans the table while holding an ACCESS EXCLUSIVE lock on the table being attached. A matching constraint allows PostgreSQL to avoid that validation scan. After successful attachment, the redundant check can be dropped.[1]

15.4 DEFAULT-partition caveat

If the parent has a DEFAULT partition, attaching a new explicit partition can require PostgreSQL to scan the default partition to prove it contains no rows that belong in the new range. Adding a matching exclusion CHECK constraint to the default partition can avoid that scan and its associated ACCESS EXCLUSIVE lock.[1]

16. Time-series partitioning

Time-series workloads are a natural fit for range partitioning because data arrives in time order, queries frequently constrain time, and retention is typically time-based. Partition interval selection should be driven by workload shape rather than a fixed rule.[1]

16.1 Monthly time-series table

CREATE TABLE metrics.sample (
    ts timestamptz NOT NULL,
    tenant_id bigint NOT NULL,
    series_id bigint NOT NULL,
    value double precision NOT NULL,
    tags jsonb
)
PARTITION BY RANGE (ts);

CREATE INDEX sample_tenant_series_ts_idx
ON metrics.sample (
    tenant_id,
    series_id,
    ts DESC
);

16.2 Pre-create future partitions

CREATE TABLE metrics.sample_2026_10
PARTITION OF metrics.sample
FOR VALUES FROM ('2026-10-01')
             TO ('2026-11-01');

CREATE TABLE metrics.sample_2026_11
PARTITION OF metrics.sample
FOR VALUES FROM ('2026-11-01')
             TO ('2026-12-01');

PostgreSQL does not automatically create missing declarative partitions when a row falls outside all explicit bounds. Production systems commonly automate future partition creation ahead of the ingest frontier.[1]

16.3 Retention as metadata operations

ALTER TABLE metrics.sample
DETACH PARTITION metrics.sample_2024_09 CONCURRENTLY;

-- Archive/export if needed, then:
DROP TABLE metrics.sample_2024_09;

16.4 Choosing daily vs monthly

FactorSmaller intervalsLarger intervals
Retention precisionMore preciseCoarser
Partition countHigherLower
Index size per partitionSmallerLarger
Planning overheadHigher if many partitions survive planning metadataLower
Typical broad scansMore child scansFewer child scans
Detach/drop granularityFineCoarse

The right interval balances query locality, retention operations, data volume, index size, and partition-count overhead.

17. DEFAULT partitions

A default partition catches rows that do not fit any explicit partition bound. It can be useful as an operational safety net when new values or unexpected timestamps arrive, but it should not become a silent dumping ground that masks partition-management failures.[2] 

CREATE TABLE telemetry.reading_default
PARTITION OF telemetry.reading
DEFAULT;

17.1 Monitor it

SELECT count(*)
FROM telemetry.reading_default;

For strict time-series ingestion, many teams prefer failing fast when a future partition is missing, because the failure exposes an operational defect immediately. Where a default partition is used, alert on unexpected row growth and periodically migrate rows into the correct explicit partitions.

18. Inspecting partition trees

PostgreSQL provides partition-information functions that expose the relation hierarchy. pg_partition_tree() lists the root, intermediate partitions, and leaves with depth information; pg_partition_ancestors() and pg_partition_root() navigate upward.[8]

18.1 Tree inventory

SELECT
    relid,
    parentrelid,
    isleaf,
    level
FROM pg_partition_tree('telemetry.reading')
ORDER BY level, relid::text;

18.2 Partition sizes

SELECT
    relid,
    pg_size_pretty(
        pg_total_relation_size(relid)
    ) AS total_size
FROM pg_partition_tree('telemetry.reading')
WHERE isleaf
ORDER BY pg_total_relation_size(relid) DESC;

18.3 Total leaf-table data size

SELECT
    pg_size_pretty(
        sum(pg_relation_size(relid))
    ) AS total_heap_size
FROM pg_partition_tree('telemetry.reading')
WHERE isleaf;

PostgreSQL's documentation demonstrates this partition-tree technique for measuring the physical data contained by a partitioned table.[8]

18.4 Catalog metadata

SELECT
    c.oid::regclass AS partitioned_table,
    CASE p.partstrat
        WHEN 'r' THEN 'range'
        WHEN 'l' THEN 'list'
        WHEN 'h' THEN 'hash'
    END AS strategy,
    p.partnatts,
    p.partattrs
FROM pg_partitioned_table AS p
JOIN pg_class AS c
  ON c.oid = p.partrelid;

pg_partitioned_table stores metadata for partitioned tables, including strategy and partition-key information.[9]

19. Partitioning performance engineering

19.1 Pruning must eliminate meaningful work

Partitioning has the highest query value when typical predicates remove most partitions. If almost every query scans all partitions, the design may add planning overhead without reducing execution work.

19.2 Index each surviving partition for its real access path

-- Partition key drives pruning:
WHERE observed_at >= $1
  AND observed_at <  $2

-- Device key narrows rows inside the surviving partitions:
AND device_id = $3
CREATE INDEX reading_device_time_idx
ON telemetry.reading (
    device_id,
    observed_at DESC
);

Pruning and indexing solve different problems. Pruning decides which relations can be ignored; indexes decide how to access tuples inside the remaining relations.[1]

19.3 Too many partitions

PostgreSQL warns that excessive partition counts increase planning time and memory use in both planning and execution. Large partition counts are most tolerable when typical queries prune down to a small subset. PostgreSQL 18 improves planning for many-partition queries, but this overhead remains a real design constraint.[1][4]

19.4 Plan with EXPLAIN

EXPLAIN (
    ANALYZE,
    BUFFERS,
    SETTINGS
)
SELECT *
FROM telemetry.reading
WHERE observed_at >= '2026-09-15'
  AND observed_at <  '2026-09-16'
  AND device_id = 101;

Look for the expected child relations, Subplans Removed, (never executed) subplans in runtime-pruning scenarios, and whether each surviving leaf uses an appropriate scan method.[1][10]

19.5 Statistics remain per relation

Partitions are physical relations and require normal ANALYZE/autovacuum attention. High-churn recent partitions may have different maintenance needs from historical partitions. PostgreSQL's automatic statistics and vacuum infrastructure applies to partition leaf tables like other relations.[11]

19.6 Do not partition small tables for aesthetics

Partitioning introduces additional relations, indexes, planner work, DDL automation, monitoring, backups, and migration complexity. PostgreSQL's documentation notes that the benefit generally appears only when tables are large enough for locality/maintenance gains to matter.[1]

20. Partitioning versus sharding

Partitioning and sharding both horizontally divide rows, but they operate at different architectural scopes. Native PostgreSQL declarative partitioning divides one logical table into physical relations managed by one PostgreSQL cluster. Sharding distributes subsets of data across multiple database servers/nodes and therefore introduces distributed query routing, placement, network communication, rebalancing, and distributed transaction concerns.[1][24]

20.1 Citus as a concrete distributed example

Current Citus documentation describes distributed tables as horizontally partitioned into shards placed across PostgreSQL worker nodes. A coordinator tracks the distribution metadata and routes or parallelizes queries to workers. That is fundamentally different from a native hash-partitioned PostgreSQL table whose partitions are still local relations inside one cluster.[24]

Partitioning is not a prerequisite for sharding, and sharding is not a stronger form of local partition pruning. They solve related but distinct problems: local physical organization versus distributed capacity.

21. Practical partitioning patterns

21.1 Time-series retention

PARTITION BY RANGE (ts)
-- monthly leaves
-- detach/drop leaves at retention boundary

Use when: most queries contain time predicates and retention is time-based.

21.2 Fixed-count tenant spreading

PARTITION BY HASH (tenant_id)
-- 16 or 32 stable hash partitions

Use when: tenant count is large/unbounded but distributing local table/index size across a fixed number of relations is helpful.

21.3 Region + time hierarchy

PARTITION BY LIST (region_code)
-- each region partition:
PARTITION BY RANGE (occurred_at)

Use when: region is a stable operational/storage boundary and queries/retention are also time-oriented.

21.4 Time + hash hierarchy

PARTITION BY RANGE (occurred_at)
-- each time partition:
PARTITION BY HASH (tenant_id)

Use when: retention is time-oriented but single time partitions become too large or too hot. Verify that the multiplied partition count is operationally justified.

21.5 Sliding window table

future: [Oct] [Nov] [Dec] current: [Sep] recent: [Jun][Jul][Aug] expired: detach May -> archive -> drop Automation: 1. create N future partitions 2. monitor default/no-match errors 3. detach oldest partition 4. archive/aggregate 5. drop according to retention policy

22. Common pitfalls

22.1 Partitioning by a column queries do not filter

A partition key that rarely appears in predicates provides little pruning benefit. Choose keys from actual query and lifecycle behavior rather than from abstract data taxonomy.[1]

22.2 Partition explosion

365 daily partitions/year
× 100 tenant-list subpartitions
= 36,500 new leaf partitions/year

This creates substantial catalog, DDL, planning, autovacuum, monitoring, and backup complexity. Hashing tenants into a fixed number of subpartitions or using only the time dimension may be better.

22.3 Assuming the partition key must be indexed

Partition pruning uses partition metadata, not the presence of a partition-key index. Index the partition key when queries inside surviving partitions benefit from it—not merely because it is the partition key.[1]

22.4 Forgetting uniqueness restrictions

-- This cannot be a global PK on a table partitioned only by occurred_at:
PRIMARY KEY (event_id)

-- This can:
PRIMARY KEY (occurred_at, event_id)

22.5 Missing future partitions

An insert with no matching partition fails unless a default partition exists. Time-based systems should create future partitions proactively and monitor the partition horizon.[1]

22.6 Treating a DEFAULT partition as permanent storage

A default partition can hide missed maintenance and can complicate later attachments because PostgreSQL may need to validate that the default partition contains no rows belonging to a new explicit partition.[1]

22.7 Expecting CREATE INDEX CONCURRENTLY on the parent

Build the parent index with ON ONLY, create child indexes concurrently, then attach them.[1]

22.8 Enabling partition-wise join globally without measuring

The setting is off by default because plan size, planning work, and per-node memory can multiply with the number of partitions. Test per session/workload first.[5]

22.9 Confusing partitioning with distributed write scaling

Native partitions remain inside one PostgreSQL cluster. If one server's CPU, storage, or write throughput is the hard bottleneck, local partitioning does not create additional machines.[1][24]

23. Production checklist

  1. Define the problem. Is partitioning solving query pruning, retention, storage placement, index size, or maintenance?
  2. Choose a key from workload predicates. Partition bounds should align with common filters.
  3. Choose a sustainable partition count. Model several years of growth before selecting granularity.
  4. Prefer declarative partitioning. Use inheritance-based designs only for requirements declarative partitioning cannot meet.
  5. Test pruning with real SQL. Inspect EXPLAIN and runtime pruning behavior.
  6. Index surviving partitions. Partitioning and indexing are complementary.
  7. Design primary/unique keys with partition constraints in mind.
  8. Pre-create future partitions. Do not let ingestion discover missing partitions first.
  9. Automate retention. Detach/archive/drop entire partitions when time/data boundaries permit.
  10. Use matching CHECK constraints before ATTACH. Avoid validation scans and long locks.
  11. Account for DEFAULT partitions during ATTACH.
  12. Plan index rollout. Use child CREATE INDEX CONCURRENTLY plus ATTACH PARTITION for low-lock builds.
  13. Evaluate partition-wise joins/aggregates deliberately. They can multiply planning and memory costs.
  14. Monitor partition counts and sizes. Use pg_partition_tree() and relation-size functions.
  15. Review autovacuum/statistics on hot leaves.
  16. Keep partitioning and sharding decisions separate. Local data organization is not distributed capacity.
Partitioning principle: partition around a boundary the workload already understands—time, a stable category, or a controlled hash domain. The best partitioning scheme removes work from queries and operations; the worst merely multiplies tables.
