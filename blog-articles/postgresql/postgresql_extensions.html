PostgreSQL Extensions

How PostgreSQL turns database features into installable packages: extension architecture, lifecycle and security, PostGIS, pgvector, pg_stat_statements, foreign-data wrappers, TimescaleDB, pg_trgm, hstore, citext, uuid-ossp, and custom C extension development.

Technical article • PostgreSQL 18.6 baseline • Updated 15 September 2026 • Vancouver-style references

Abstract

One of PostgreSQL's defining strengths is that the server is designed to be extended. Its behavior is catalog-driven: PostgreSQL stores metadata not only about tables and columns but also about data types, functions, operators, access methods, casts, aggregates, operator classes, and other programmable database objects. User-defined SQL objects and dynamically loaded native code can therefore add capabilities that participate in PostgreSQL's parser, type system, planner, executor, indexes, transactions, and storage-facing APIs without maintaining a private fork of the PostgreSQL server.[1][2]

The extension mechanism packages a related set of objects under one versioned database object. CREATE EXTENSION executes an extension's installation script and records which objects belong to that extension, enabling coordinated ownership, upgrades, dumps, and removal. The ecosystem ranges from small supplied modules such as pg_trgm and citext, through observability extensions such as pg_stat_statements, to substantial systems such as PostGIS, pgvector, TimescaleDB, and foreign-data wrappers.[3]-[5]

1. Extension architecture

1.1 PostgreSQL is catalog-driven

PostgreSQL's extensibility begins with its system catalogs. The server stores definitions for types, functions, operators, casts, access methods, operator classes, aggregates, and many other objects in catalogs that the parser, planner, executor, and type system consult at runtime. This allows a newly installed object to participate in ordinary SQL resolution and planning rather than existing as an isolated plugin API outside the database language.[1]

SQL statement | v parser / analyzer | +---- system catalogs -----------------------------+ | | | types functions operators casts | | access methods operator classes aggregates | +--------------------------------------------------+ | v planner / optimizer | v executor | +--> built-in implementation | +--> extension SQL / PL function | +--> dynamically loaded C shared library | +--> extension index/operator/access-method APIs

PostgreSQL's server-programming interfaces go far beyond scalar functions. The official “Extending SQL” documentation covers user-defined functions, procedures, aggregates, types, operators, optimizer information, index operator classes, and packaging; later internals chapters define APIs for foreign-data wrappers, custom scans, table access methods, index access methods, WAL integration, and other deeper facilities.[2]

1.2 An extension is a package, not a separate process

A PostgreSQL extension is principally a package of database objects with lifecycle metadata. A pure-SQL extension may contain only a control file and SQL scripts. A native extension commonly adds a shared library containing C/C++ code. CREATE EXTENSION executes the installation SQL while marking created objects as members of the extension so PostgreSQL understands that they belong together.[3][6]

1.3 Typical extension files

my_extension/
├── Makefile
├── my_extension.control
├── my_extension--1.0.sql
├── my_extension--1.0--1.1.sql    # optional upgrade path
├── my_extension.c                # optional native code
├── sql/                           # optional regression-test SQL
└── expected/                      # optional expected test output

PostgreSQL's packaging convention uses a primary .control file and versioned installation scripts named extension--version.sql. Update scripts use names such as extension--1.0--1.1.sql. Native extensions normally install a dynamically loadable shared library as well.[6]

2. CREATE EXTENSION and extension lifecycle

2.1 Installation has two levels

An extension must first be installed at the PostgreSQL software/server level so its control, SQL, and any library files are available to the server. CREATE EXTENSION then installs that extension into one specific database. Consequently, a package can exist on the host while not being enabled in a particular database, and an extension normally needs to be created separately in each database where its objects are required.[3][4] 

-- What the server could install:
SELECT
    name,
    default_version,
    installed_version,
    comment
FROM pg_available_extensions
ORDER BY name;

-- Enable one extension in the current database:
CREATE EXTENSION pg_trgm;

2.2 Syntax

CREATE EXTENSION [ IF NOT EXISTS ] extension_name
    [ WITH ]
    [ SCHEMA schema_name ]
    [ VERSION version ]
    [ CASCADE ];

The SCHEMA option controls the target schema when the extension supports relocation or otherwise permits schema choice. VERSION chooses a non-default install version. CASCADE recursively installs missing prerequisite extensions. PostgreSQL records extension membership so DROP EXTENSION can remove the package's member objects as a unit.[3]

2.3 Extension catalog

SELECT
    e.extname,
    e.extversion,
    n.nspname AS extension_schema,
    e.extrelocatable,
    pg_get_userbyid(e.extowner) AS owner
FROM pg_extension AS e
JOIN pg_namespace AS n
  ON n.oid = e.extnamespace
ORDER BY e.extname;

The pg_extension catalog stores each installed extension's name, owner, schema, relocatability flag, version, and optional configuration-table metadata. Extension names themselves are not schema-qualified; the extension schema identifies where most or all schema-qualifiable member objects reside.[7]

2.4 PostgreSQL 18: extension_control_path

PostgreSQL 18 added extension_control_path, allowing administrators to configure where PostgreSQL searches for extension control files. The default $system location resolves to the compiled-in PostgreSQL shared-data directory. Nonstandard library paths may also require corresponding dynamic_library_path configuration.[8] 

# postgresql.conf
extension_control_path =
    '/opt/company/postgresql/share:/usr/local/share/postgresql:$system'

dynamic_library_path =
    '/opt/company/postgresql/lib:/usr/local/lib/postgresql:$libdir'

3. Extension security and trust

3.1 Native extensions execute inside the server

C extension code is dynamically loaded into the PostgreSQL server process. It is therefore trusted native code from the database server's perspective: memory-safety bugs, unsafe signal behavior, or malicious code can crash a backend, disclose process-accessible data, or compromise database integrity. Extension installation should be treated like installation of server software, not like importing an ordinary application library.[1][9]

3.2 Trusted extensions

By default, installing an extension requires the privileges needed to create all objects in its script, often including superuser-only operations. PostgreSQL also supports extensions marked trusted in their control file. A trusted extension can be installed by a non-superuser that has CREATE privilege on the current database. PostgreSQL's supplied trusted extensions include citext, hstore, pg_trgm, and uuid-ossp.[4]

3.3 Search-path attacks during installation

The CREATE EXTENSION documentation warns that extension installation scripts can become vulnerable to Trojan-horse objects if untrusted users can create objects in schemas searched during installation. For extensions whose scripts have not been thoroughly audited, PostgreSQL recommends installing into schemas in which untrusted users do not have CREATE privilege, and applying the same care to prerequisite extensions.[3] 

CREATE SCHEMA extensions AUTHORIZATION postgres;

REVOKE CREATE ON SCHEMA extensions FROM PUBLIC;

CREATE EXTENSION hstore SCHEMA extensions;
Extension governance matters. Before production deployment, review the extension's source/provenance, PostgreSQL-version support, update path, backup/restore behavior, replication behavior, privileges, native-code surface, and operational requirements.

4. Extension inventory and version management

4.1 Installed extensions

SELECT
    extname,
    extversion
FROM pg_extension
ORDER BY extname;

4.2 Available versions and upgrade candidates

SELECT
    name,
    version,
    installed,
    superuser,
    trusted,
    relocatable,
    schema,
    requires,
    comment
FROM pg_available_extension_versions
ORDER BY name, version;

pg_available_extension_versions reports versions discoverable from installed control/script files together with privilege, trust, schema, relocatability, and prerequisite metadata. It is useful for detecting whether a newly installed extension package has exposed an upgrade path to a database.[10]

4.3 Updating

ALTER EXTENSION vector UPDATE;
ALTER EXTENSION postgis UPDATE;
ALTER EXTENSION my_extension UPDATE TO '1.2';

An extension can be updated only through update paths supplied by its installed extension files. PostgreSQL runs the selected update scripts and automatically adds new objects created by those scripts to the extension's membership.[6]

5. PostGIS

PostGIS extends PostgreSQL with spatial data types, spatial functions, coordinate-system support, and spatial index integration. The core PostGIS extension includes geometry, geography, the spatial reference system catalog, and a large set of spatial functions; raster and topology facilities are packaged separately.[11]

5.1 Installation

CREATE EXTENSION postgis;

-- Optional modules when installed on the host:
CREATE EXTENSION postgis_raster;
CREATE EXTENSION postgis_topology;

5.2 Geometry versus geography

PostGIS geometry values use coordinates in the geometry's spatial reference system; distance units therefore depend on that SRID. The geography type represents geodetic coordinates and provides distance operations in meters for functions such as ST_DWithin.[11][12] 

CREATE TABLE store (
    store_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name text NOT NULL,
    location geography(Point, 4326) NOT NULL
);

INSERT INTO store(name, location)
VALUES (
    'Downtown',
    ST_SetSRID(ST_MakePoint(-78.6382, 35.7796), 4326)::geography
);

5.3 Spatial indexes

CREATE INDEX store_location_gix
ON store
USING GIST (location);

PostGIS documents GiST as the standard spatial indexing mechanism for geometry/geography workloads and also supports other spatial indexing strategies for relevant types. Spatial indexes implement bounding-box-aware access paths so predicates such as ST_DWithin can use index-assisted filtering.[11][12]

5.4 Radius query

SELECT
    store_id,
    name
FROM store
WHERE ST_DWithin(
    location,
    ST_SetSRID(ST_MakePoint(-78.64, 35.78), 4326)::geography,
    5000
);

For geography, the distance parameter to ST_DWithin is expressed in meters and the function performs an index-aware bounding-box comparison when suitable indexes exist.[12]

6. pgvector

pgvector adds vector data types and vector similarity operators to PostgreSQL. The project supports exact nearest-neighbor search and approximate search through HNSW and IVFFlat indexes. Its primary dense vector type supports single-precision vectors; the extension also provides half-precision, binary, and sparse representations.[13]

6.1 Installation and exact search

CREATE EXTENSION vector;

CREATE TABLE document_embedding (
    document_id bigint PRIMARY KEY,
    embedding vector(3) NOT NULL
);

INSERT INTO document_embedding(document_id, embedding)
VALUES
    (1, '[1,2,3]'),
    (2, '[4,5,6]'),
    (3, '[1,1,1]');

-- L2 nearest neighbors:
SELECT
    document_id,
    embedding <-> '[3,1,2]' AS distance
FROM document_embedding
ORDER BY embedding <-> '[3,1,2]'
LIMIT 5;

pgvector defines operators for L2 distance (<->), negative inner product (<#>), cosine distance (<=>), L1 distance, and binary-vector distances. Without an approximate index, nearest-neighbor queries are exact.[13]

6.2 HNSW

CREATE INDEX document_embedding_hnsw_cosine
ON document_embedding
USING hnsw (embedding vector_cosine_ops);

BEGIN;
SET LOCAL hnsw.ef_search = 100;

SELECT
    document_id,
    1 - (embedding <=> '[3,1,2]') AS cosine_similarity
FROM document_embedding
ORDER BY embedding <=> '[3,1,2]'
LIMIT 10;

COMMIT;

HNSW builds a multilayer graph. pgvector documents HNSW as generally providing a stronger speed/recall tradeoff than IVFFlat, at the cost of slower builds and greater memory use. hnsw.ef_search controls the candidate list used during search; increasing it can improve recall while increasing query cost.[13]

6.3 IVFFlat

CREATE INDEX document_embedding_ivf_l2
ON document_embedding
USING ivfflat (embedding vector_l2_ops)
WITH (lists = 100);

BEGIN;
SET LOCAL ivfflat.probes = 10;

SELECT document_id
FROM document_embedding
ORDER BY embedding <-> '[3,1,2]'
LIMIT 10;

COMMIT;

IVFFlat partitions vectors into lists and searches selected lists. It requires data for its clustering/training step, and its recall depends materially on list and probe configuration. Approximate indexes deliberately trade perfect recall for lower query cost; production evaluation should therefore measure recall against exact search as well as latency.[13]

6.4 Versioning

SELECT extversion
FROM pg_extension
WHERE extname = 'vector';

ALTER EXTENSION vector UPDATE;

The official pgvector project documents PostgreSQL 13+ support for its current 0.8.x line and instructs database users to update installed metadata with ALTER EXTENSION vector UPDATE after installing a newer extension package.[13]

7. pg_stat_statements

pg_stat_statements is a PostgreSQL-supplied extension that records planning and execution statistics for normalized SQL statements. It tracks across all databases at the shared-memory level, but its views and management functions are installed separately into each database where they need to be queried.[14]

7.1 Preload requirement

# postgresql.conf
shared_preload_libraries = 'pg_stat_statements'
compute_query_id = auto
-- After server restart:
CREATE EXTENSION pg_stat_statements;

The extension must be included in shared_preload_libraries because it requires shared memory allocated at server startup. Query identifiers must also be enabled; compute_query_id=auto activates query-ID generation when the module needs it.[14]

7.2 Performance analysis

SELECT
    queryid,
    calls,
    total_exec_time,
    mean_exec_time,
    rows,
    shared_blks_hit,
    shared_blks_read,
    temp_blks_written,
    wal_bytes,
    left(query, 220) AS query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 25;

Because statements are normalized and aggregated, pg_stat_statements is well suited to workload-level performance analysis: it identifies query classes that consume large amounts of time, I/O, temporary space, or WAL without requiring every execution to be logged individually.[14]

8. Foreign-data wrappers

The SQL/MED-inspired foreign-data-wrapper architecture lets PostgreSQL represent external data as foreign tables. A wrapper supplies planner and executor callbacks that PostgreSQL uses to estimate remote relations, create foreign paths/plans, begin scans, fetch rows, push operations to the remote source where supported, and optionally implement modification, import, join, aggregate, asynchronous, and parallel behaviors.[15]

8.1 postgres_fdw

PostgreSQL ships postgres_fdw for accessing tables on external PostgreSQL servers. The documented setup consists of installing the extension, defining a foreign server, creating per-user mappings, and defining or importing foreign tables.[16] 

CREATE EXTENSION postgres_fdw;

CREATE SERVER analytics_cluster
FOREIGN DATA WRAPPER postgres_fdw
OPTIONS (
    host 'analytics.internal',
    port '5432',
    dbname 'warehouse'
);

CREATE USER MAPPING FOR app_user
SERVER analytics_cluster
OPTIONS (
    user 'remote_reader',
    password 'managed-secret'
);

CREATE SCHEMA foreign_analytics;

IMPORT FOREIGN SCHEMA public
LIMIT TO (daily_sales, customer_rollup)
FROM SERVER analytics_cluster
INTO foreign_analytics;

8.2 Querying a foreign table

EXPLAIN (VERBOSE)
SELECT
    region,
    sum(revenue)
FROM foreign_analytics.daily_sales
WHERE day >= current_date - 30
GROUP BY region;

A capable FDW can push filters, joins, aggregation, or ordering to the remote source, reducing transferred data. Pushdown capability is wrapper-specific and should be verified from EXPLAIN VERBOSE and runtime measurements rather than assumed.[15][16]

9. TimescaleDB

TimescaleDB is a PostgreSQL extension focused on time-series and analytical workloads. Its central abstraction is the hypertable, a PostgreSQL-visible table whose data is automatically partitioned into chunks according to a time-oriented dimension. SQL issued against the hypertable is routed to the relevant chunks by the extension's planner/executor integration.[17]

9.1 Enable the extension

CREATE EXTENSION IF NOT EXISTS timescaledb;

9.2 Current hypertable creation syntax

Current TimescaleDB documentation (v2.20+) supports creating a hypertable directly through an extended CREATE TABLE syntax. Older/self-hosted deployments and conversions of existing ordinary tables can use create_hypertable().[18][17] 

CREATE TABLE metric (
    time timestamptz NOT NULL,
    device_id text NOT NULL,
    value double precision
)
WITH (
    tsdb.hypertable,
    tsdb.partition_column = 'time',
    tsdb.chunk_interval = '1 day'
);

9.3 Convert an existing table

CREATE TABLE sensor_reading (
    time timestamptz NOT NULL,
    sensor_id bigint NOT NULL,
    temperature double precision
);

SELECT create_hypertable(
    'sensor_reading',
    by_range('time', INTERVAL '1 day')
);

TimescaleDB documents hypertables as PostgreSQL tables automatically partitioned by time. The extension keeps standard SQL operations such as SELECT and ALTER TABLE available on the logical table while managing the underlying chunks.[17][18]

Compatibility note: TimescaleDB is a substantial extension with its own version compatibility, planner hooks, background jobs, storage features, and upgrade procedures. Treat PostgreSQL major upgrades and TimescaleDB upgrades as a coordinated lifecycle rather than upgrading the server binaries independently.

10. pg_trgm

pg_trgm supplies trigram-based text-similarity functions, operators, and GiST/GIN operator classes. A trigram is a sequence of three consecutive characters; similarity is derived from the trigrams shared by strings. This makes the extension useful for fuzzy matching and index-assisted LIKE/ILIKE-style search patterns.[19]

10.1 Similarity search

CREATE EXTENSION pg_trgm;

SELECT
    similarity('PostgreSQL', 'Postgres') AS score;

SELECT
    name,
    similarity(name, 'postgress') AS score
FROM product
WHERE name % 'postgress'
ORDER BY score DESC
LIMIT 20;

10.2 GIN trigram index

CREATE INDEX product_name_trgm_gin
ON product
USING GIN (name gin_trgm_ops);

SELECT *
FROM product
WHERE name ILIKE '%postgres%';

The extension's trigram operator classes allow GiST and GIN indexes to accelerate supported similarity and pattern-matching operations. This can provide indexed substring-like searches that ordinary B-tree indexes generally cannot support for patterns beginning with an unrestricted wildcard.[19]

10.3 Upgrade note for PostgreSQL 18

PostgreSQL 18 changed some collation/lowercasing behavior, and its release notes recommend reindexing pg_trgm-related indexes after pg_upgrade when relevant collation-provider behavior differs from the prior cluster. This is an example of why extension-specific release notes belong in every major-version upgrade plan.[20]

11. hstore

hstore adds a key/value type in which keys and values are text strings. It is useful for semi-structured attributes when a row may contain many optional textual properties. PostgreSQL's supplied hstore extension includes operators, functions, GiST/GIN indexing support, and language transforms for selected procedural languages.[21] 

CREATE EXTENSION hstore;

CREATE TABLE asset (
    asset_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    attributes hstore NOT NULL DEFAULT ''::hstore
);

INSERT INTO asset(attributes)
VALUES ('manufacturer=>Acme, color=>blue, voltage=>240');

SELECT
    asset_id,
    attributes -> 'manufacturer' AS manufacturer
FROM asset
WHERE attributes @> 'color=>blue';

11.1 GIN indexing

CREATE INDEX asset_attributes_gin
ON asset
USING GIN (attributes);

SELECT *
FROM asset
WHERE attributes ? 'voltage';

SELECT *
FROM asset
WHERE attributes @> 'manufacturer=>Acme';

hstore supports GiST and GIN indexes for containment and key-existence operators. It also supports B-tree/hash equality indexes, although ordering of key/value collections is usually less useful than containment/search indexes.[21]

11.2 hstore versus JSONB

hstore is deliberately limited to text key/value pairs. JSONB supports nested JSON structures and typed JSON scalar values, so it is generally the richer representation when nested documents are required. hstore remains useful when its simpler flat text-map model is exactly the desired schema.

12. citext

citext defines a case-insensitive character-string type. Comparisons behave broadly as though values were lowercased before comparison, allowing case-insensitive equality and uniqueness without writing lower() in every query. The extension is trusted.[22] 

CREATE EXTENSION citext;

CREATE TABLE app_user (
    user_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email citext NOT NULL UNIQUE
);

INSERT INTO app_user(email)
VALUES ('Alice@example.com');

-- Matches:
SELECT *
FROM app_user
WHERE email = 'alice@EXAMPLE.COM';

-- Fails because uniqueness is case-insensitive:
INSERT INTO app_user(email)
VALUES ('ALICE@example.com');

12.1 Modern collation alternative

PostgreSQL 18's citext documentation explicitly recommends considering nondeterministic collations instead. They can support combinations such as case-insensitive and accent-insensitive comparison and handle more Unicode special cases than the extension's lowercasing approach. citext remains useful, but its locale and Unicode limitations should be evaluated for international text.[22]

13. uuid-ossp

uuid-ossp provides functions implementing several standard UUID generation algorithms, historically including UUID versions 1, 3, 4, and 5, plus namespace constants. It is a trusted extension.[23] 

CREATE EXTENSION "uuid-ossp";

SELECT uuid_generate_v4();

SELECT uuid_generate_v5(
    uuid_ns_url(),
    'https://example.com/customer/42'
);

13.1 PostgreSQL 18 often does not need it

PostgreSQL 18 provides native generation for UUIDv4 and UUIDv7. The PostgreSQL documentation therefore states that uuid-ossp is needed only for special requirements beyond core UUID facilities. For a new application that simply needs random UUIDv4 or time-ordered UUIDv7 values, prefer the built-in functions and avoid an unnecessary extension dependency.[23][24] 

-- Built into PostgreSQL 18:
SELECT uuidv4();
SELECT uuidv7();

14. Building a custom extension

PostgreSQL's PGXS build infrastructure automates common build/install rules for extensions against an already installed PostgreSQL development environment. PGXS is especially useful for C extensions but can also package pure-SQL extensions. The extension package typically installs a control file and SQL scripts into PostgreSQL's extension directory and native shared libraries into the server library directory.[25]

14.1 Complete minimal C extension: pg_clamp

Directory

pg_clamp/
├── Makefile
├── pg_clamp.control
├── pg_clamp--1.0.sql
└── pg_clamp.c

pg_clamp.c

#include "postgres.h"
#include "fmgr.h"
#include "utils/errcodes.h"

PG_MODULE_MAGIC;

PG_FUNCTION_INFO_V1(clamp_int4);

Datum
clamp_int4(PG_FUNCTION_ARGS)
{
    int32 value = PG_GETARG_INT32(0);
    int32 minimum = PG_GETARG_INT32(1);
    int32 maximum = PG_GETARG_INT32(2);

    if (minimum > maximum)
        ereport(ERROR,
                (errcode(ERRCODE_INVALID_PARAMETER_VALUE),
                 errmsg("minimum must not exceed maximum")));

    if (value < minimum)
        PG_RETURN_INT32(minimum);

    if (value > maximum)
        PG_RETURN_INT32(maximum);

    PG_RETURN_INT32(value);
}

pg_clamp.control

comment = 'Small example extension providing integer clamping'
default_version = '1.0'
module_pathname = '$libdir/pg_clamp'
relocatable = true

pg_clamp--1.0.sql

CREATE FUNCTION clamp_int4(integer, integer, integer)
RETURNS integer
AS 'MODULE_PATHNAME', 'clamp_int4'
LANGUAGE C
IMMUTABLE
STRICT
PARALLEL SAFE;

COMMENT ON FUNCTION clamp_int4(integer, integer, integer)
IS 'Clamp a 32-bit integer to an inclusive minimum/maximum range';

Makefile

EXTENSION = pg_clamp
MODULES = pg_clamp
DATA = pg_clamp--1.0.sql

PG_CONFIG = pg_config
PGXS := $(shell $(PG_CONFIG) --pgxs)
include $(PGXS)

Build and install

make
sudo make install

psql -d appdb -c "CREATE EXTENSION pg_clamp"
psql -d appdb -c "SELECT clamp_int4(150, 0, 100)"

PGXS obtains PostgreSQL-specific build flags and installation directories through pg_config --pgxs. The EXTENSION, MODULES, and DATA variables identify the extension, shared-library module, and extension scripts respectively.[25]

15. PostgreSQL C APIs used by extensions

15.1 Function manager

SQL-callable C functions use PostgreSQL's version-1 function-manager convention. The function has a C signature based on Datum, declares metadata with PG_FUNCTION_INFO_V1(), retrieves arguments through PG_GETARG_*, and returns values through PG_RETURN_*. PG_MODULE_MAGIC embeds compatibility information used when loading the shared library.[9] 

PG_MODULE_MAGIC;
PG_FUNCTION_INFO_V1(example);

Datum
example(PG_FUNCTION_ARGS)
{
    int32 x = PG_GETARG_INT32(0);
    PG_RETURN_INT32(x + 1);
}

15.2 PostgreSQL memory management

Server extension code normally allocates memory with PostgreSQL memory-context APIs such as palloc() rather than ordinary application-lifetime assumptions. Errors raised through PostgreSQL's error machinery can unwind execution non-locally; using PostgreSQL resource ownership and memory contexts is essential for safe cleanup.[9]

15.3 Server Programming Interface (SPI)

Extensions that need to issue SQL from server-side C code can use the Server Programming Interface (SPI). SPI connects a C function to PostgreSQL's parser, planner, executor, and tuple-table facilities, allowing the extension to prepare and execute SQL inside the server.[26] 

#include "executor/spi.h"

if (SPI_connect() != SPI_OK_CONNECT)
    elog(ERROR, "SPI_connect failed");

int rc = SPI_execute(
    "SELECT count(*) FROM pg_catalog.pg_class",
    true,
    1
);

if (rc != SPI_OK_SELECT)
    elog(ERROR, "SPI_execute failed");

SPI_finish();

16. Custom extension upgrades

The extension mechanism tracks a version name. Extension authors can provide update scripts named extension--old--new.sql, after which ALTER EXTENSION ... UPDATE applies the path. Updates run in the extension installation environment, and newly created objects are automatically associated with the extension.[6]

16.1 Example 1.0 → 1.1 update

-- pg_clamp--1.0--1.1.sql

CREATE FUNCTION clamp_numeric(numeric, numeric, numeric)
RETURNS numeric
LANGUAGE SQL
IMMUTABLE
STRICT
PARALLEL SAFE
RETURN greatest($2, least($1, $3));

COMMENT ON FUNCTION clamp_numeric(numeric, numeric, numeric)
IS 'Clamp a numeric value to an inclusive minimum/maximum range';
ALTER EXTENSION pg_clamp UPDATE TO '1.1';

SELECT extversion
FROM pg_extension
WHERE extname = 'pg_clamp';

16.2 Do not edit extension-owned objects casually

Extension upgrade scripts expect the extension's object graph to be in a known state. Manual changes to extension-owned functions, types, operators, or tables can make upgrades fail or silently invalidate vendor assumptions. Put local wrappers and application-specific objects outside the vendor extension whenever possible.

17. Testing extensions

PostgreSQL's supplied and third-party extensions commonly use the PostgreSQL regression-test infrastructure. PGXS supports regression tests through makefile variables, while the PostgreSQL contrib tree uses commands such as make check before installation and make installcheck against a running server. The pgvector project likewise documents make installcheck and TAP tests for its development workflow.[4][13][25]

17.1 PGXS regression test

# Makefile
EXTENSION = pg_clamp
MODULES = pg_clamp
DATA = pg_clamp--1.0.sql
REGRESS = clamp

PG_CONFIG = pg_config
PGXS := $(shell $(PG_CONFIG) --pgxs)
include $(PGXS)
-- sql/clamp.sql
SELECT clamp_int4(5, 0, 10);
SELECT clamp_int4(-5, 0, 10);
SELECT clamp_int4(15, 0, 10);
# Run against installed extension/server environment.
make install
make installcheck

17.2 Test upgrade paths too

An extension that supports multiple deployed versions should test fresh installation and every supported upgrade path. Tests should also cover dump/restore, PostgreSQL major upgrades, replica behavior, failure/recovery behavior for persistent extension state, and concurrent use when the extension participates in planner or background-worker hooks.

18. Extensions in production

18.1 Extension state belongs in infrastructure inventory

SELECT
    current_database() AS database_name,
    extname,
    extversion
FROM pg_extension
ORDER BY extname;

Record installed extension versions alongside the PostgreSQL server version. PostgreSQL package upgrades can place newer extension binaries/scripts on disk without automatically updating every database's extension catalog; an explicit ALTER EXTENSION UPDATE may still be required according to the extension's documentation.

18.2 Backups

Extension objects are represented in PostgreSQL catalogs and are handled by logical dump mechanisms according to extension membership and extension configuration-table declarations. Physical backups include the database's physical state but a restore environment must also provide compatible extension binaries and supporting libraries before PostgreSQL can successfully use native extension objects.[6]

18.3 PostgreSQL major upgrades

A major PostgreSQL upgrade should include an extension compatibility matrix. Native modules are compiled against PostgreSQL server headers and frequently require target-major-version packages or recompilation. Extension release notes can also require post-upgrade actions, as demonstrated by PostgreSQL 18's pg_trgm reindex guidance for affected collation changes.[20][25]

18.4 Managed PostgreSQL

Hosted PostgreSQL platforms typically expose an allowlist rather than arbitrary native-library installation because server extensions execute privileged code inside the database process. Availability and versions therefore vary by provider. An application that depends on a nonstandard extension should treat extension availability as a portability requirement before selecting a managed platform.

18.5 Preload libraries

Some extensions need startup-time hooks or shared memory and must be placed in shared_preload_libraries. pg_stat_statements is a canonical example. Changing this parameter requires a server restart, which means adding or removing such an extension has infrastructure-level deployment implications rather than being a pure database migration.[14]

19. Selecting the right extension

Need Extension / mechanism Key capability Important caveat
Spatial/GIS PostGIS Geometry, geography, spatial predicates and indexes Coordinate systems and spatial-index semantics must be understood.
Vector similarity / embeddings pgvector Exact search, HNSW, IVFFlat, multiple vector representations Approximate indexes trade recall for speed.
SQL workload profiling pg_stat_statements Normalized query performance statistics Requires shared_preload_libraries and restart to enable initially.
Remote/external data FDW / postgres_fdw Foreign tables integrated with PostgreSQL planner/executor Pushdown and transaction semantics vary by wrapper/source.
Time-series data TimescaleDB Hypertables/chunks and time-series features Substantial PostgreSQL-version and extension-version lifecycle.
Fuzzy text pg_trgm Trigram similarity and GIN/GiST search Index size and similarity thresholds need workload tuning.
Flat key/value attributes hstore Text key/value map with GIN/GiST support JSONB is richer for nested or typed JSON data.
Case-insensitive string type citext Case-insensitive comparison/uniqueness Nondeterministic collations may be better for Unicode/collation needs.
Special UUID algorithms uuid-ossp UUID v1/v3/v4/v5 generation and namespaces Core PostgreSQL 18 already supplies UUIDv4 and UUIDv7.
Domain-specific server behavior Custom extension Functions, types, operators, access methods, hooks, workers, etc. Native code becomes part of the trusted database server.

19.1 Evaluation checklist

  1. Necessity: is the feature already present in core PostgreSQL?
  2. Maintenance: is the extension actively maintained and compatible with your PostgreSQL major version?
  3. Upgrade path: are tested extension update scripts available?
  4. Security: does it execute native code, contact external systems, or require superuser/preload access?
  5. Replication: how does it behave on physical and logical replicas?
  6. Backup/restore: what must be installed before restoration?
  7. Portability: is it available on every environment and managed provider you require?
  8. Planner impact: does it add hooks, operators, custom scans, or access methods that alter plans?
  9. Operational state: does it create background workers, jobs, internal schemas, or persistent metadata?
  10. Observability: what views, logs, and metrics expose extension health?
Architectural principle: extensions are powerful because PostgreSQL lets them participate deeply in database semantics. That same depth means an extension should be managed as part of the database platform's software supply chain, version lifecycle, security model, and recovery plan—not merely as an optional SQL package.
