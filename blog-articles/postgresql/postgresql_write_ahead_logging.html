PostgreSQL Write-Ahead Logging

An expert guide to PostgreSQL WAL: the write-ahead rule, WAL records and resource managers, segments and LSNs, WAL buffers and the WAL writer, durability and group commit, crash recovery, checkpoints and restartpoints, full-page images, WAL compression and archiving, wal_level, fsync, synchronous_commit, retention, replication slots, and production monitoring.

Technical article • PostgreSQL 18.6 baseline • Updated 15 September 2026 • Vancouver-style references

Abstract

Write-ahead logging (WAL) is the durability and recovery substrate of PostgreSQL. Its core rule is simple: PostgreSQL must make the log record describing a database-page change durable before the corresponding modified data page is allowed to reach durable storage. That ordering means a transaction can commit after forcing a comparatively small sequential WAL stream rather than synchronously flushing every table and index page it changed. If the server later crashes with data files only partially updated, PostgreSQL replays WAL from the last checkpoint's redo position to reconstruct a consistent state.[1][2]

WAL is also the common substrate for physical replication, continuous archiving and point-in-time recovery, logical decoding, and several maintenance/recovery mechanisms. The amount and lifetime of WAL are therefore affected not only by transaction volume but by wal_level, checkpoints, full-page images, base backups, archiving, replication lag, wal_keep_size, and replication slots. A configuration that performs well under ordinary writes can still exhaust pg_wal when an archive destination fails or a slot consumer stops advancing.[3]-[6]

Durability settings must be understood as distinct contracts. fsync=off disables PostgreSQL's normal efforts to ensure ordered durable writes and can produce unrecoverable corruption after an operating-system or hardware crash. By contrast, synchronous_commit=off leaves the WAL machinery crash-safe but permits PostgreSQL to report a transaction committed before its commit record is durably flushed; a crash can therefore lose some recently acknowledged transactions without leaving the database internally inconsistent.[3][7]

1. The WAL concept

PostgreSQL's write-ahead rule requires the WAL describing a data-file change to be flushed to durable storage before that changed data page is flushed. Commit durability then requires the commit record to satisfy the configured WAL synchronization contract before success is returned to the client. The result is a separation between logical durability and immediate data-file persistence: dirty table/index pages may remain in shared buffers after commit because recovery can reconstruct them from WAL.[1]

transaction modifies row | v buffer page becomes dirty | +-----------------------+ | | v v construct WAL record data page still only | in shared buffers v WAL buffers | v write / flush WAL | +------ durable commit boundary | v client may receive COMMIT success | | later v checkpointer / background writer / backend writes dirty data page | v data file durable Invariant: required WAL must reach durable storage BEFORE the data page it protects.

This ordering has two major performance consequences. First, commit generally needs to force a sequential log rather than every random data page modified by the transaction. Second, multiple concurrent transactions can share one WAL flush, so the cost of one durability synchronization can commit several transactions together.[1][8]

1.1 REDO, not a general UNDO log

Crash recovery is primarily roll-forward recovery: PostgreSQL starts from a checkpoint and replays WAL records needed to redo physical changes. PostgreSQL's MVCC data representation and transaction status mechanisms handle the visibility of transactions that did not commit; recovery does not need a traditional transaction-by-transaction rollback pass over every uncommitted update before opening the database.[1][2]

2. End-to-end WAL lifecycle

SQL execution | v heap/index/catalog change | v resource manager builds WAL record | v WAL insert into shared WAL buffers | +--> record assigned LSN | v WAL writer/backend writes WAL pages | v OS page cache | +--> fsync/fdatasync/O_DSYNC/etc. | v durable WAL storage | +-----------------------+----------------------+-------------------+ | | | | v v v v crash recovery physical replica WAL archive logical decode REDO replay WAL sender/receiver PITR change stream | v old segments: recycle/remove ONLY when no retention requirement still needs them

A WAL file can remain in pg_wal for several independent reasons: ordinary checkpoint/recycling policy, wal_keep_size, an archive backlog, a physical or logical replication slot, a backup/recovery requirement, or replication/recovery state. max_wal_size is not therefore a hard ceiling on pg_wal size.[3][4]

3. WAL records

PostgreSQL appends WAL records as changes occur. Every record has common WAL metadata plus content interpreted by a resource manager responsible for a subsystem such as heap operations, B-tree indexes, transaction control, checkpoints, or other storage components. The exact record payload depends on the operation being logged.[2][9]

3.1 Conceptual record shape

+---------------------------------------------------------+ | common WAL record header | | - total length | | - transaction-related metadata where applicable | | - previous-record linkage / record metadata | | - resource-manager id + operation info | | - record checksum / integrity metadata | +---------------------------------------------------------+ | optional block references | | relation/fork/block identity | | optional full-page image | | operation-specific block data | +---------------------------------------------------------+ | resource-manager-specific main data | +---------------------------------------------------------+

The exact binary format is PostgreSQL-internal and can change between releases. Applications should use supported SQL views/functions or utilities such as pg_waldump rather than parsing WAL bytes directly unless they are implementing a PostgreSQL-version-specific extension or replication component.[2][10]

3.2 Resource managers

SELECT
    rm_id,
    rm_name,
    rm_builtin
FROM pg_get_wal_resource_managers()
ORDER BY rm_id;

PostgreSQL 18 exposes currently loaded WAL resource managers through pg_get_wal_resource_managers(), including whether each manager is built in or supplied by an extension.[11]

3.3 WAL for extensions

Extensions implementing custom storage/access methods can participate in crash safety through PostgreSQL's generic WAL facility or by registering a custom WAL resource manager. Generic WAL is simpler and describes page modifications generically; custom resource managers provide more control and can integrate with logical decoding, but are substantially more complex.[9][12]

4. Log sequence numbers (LSNs)

Every WAL insertion position is identified by a log sequence number. An LSN is a byte position in the WAL stream represented by PostgreSQL's pg_lsn type. LSNs increase monotonically as WAL is generated and are widely used to measure replication, recovery, and archival progress.[2][13]

4.1 Current write-ahead positions

SELECT
    pg_current_wal_insert_lsn() AS insert_lsn,
    pg_current_wal_lsn()        AS write_lsn,
    pg_current_wal_flush_lsn()  AS flush_lsn;

The positions represent different stages: insertion into WAL buffers, writing WAL, and flushing WAL durably. On a busy server they can differ temporarily.[11]

4.2 Measure WAL volume

SELECT pg_size_pretty(
    pg_wal_lsn_diff(
        '4A/90000000'::pg_lsn,
        '4A/10000000'::pg_lsn
    )
) AS wal_distance;

4.3 Map LSN to segment

SELECT
    pg_walfile_name(pg_current_wal_lsn()),
    pg_walfile_name_offset(pg_current_wal_lsn());

These functions are useful when correlating SQL-visible positions with archive files, replication lag, or pg_waldump analysis.[11]

5. WAL segments and pg_wal

PostgreSQL stores WAL under PGDATA/pg_wal as fixed-size segment files. The normal segment size is 16 MiB, although it can be chosen at cluster initialization with initdb --wal-segsize. Segments are internally divided into WAL pages, normally 8 KiB.[2][14]

5.1 Segment names

000000010000000A000000FE
^^^^^^^^
timeline

        ^^^^^^^^
        high-order log component

                ^^^^^^^^
                segment component

The hexadecimal file name encodes the timeline and WAL position. Administrators should treat the name as an opaque WAL identity and use PostgreSQL functions/utilities for position conversion rather than implementing archive logic that assumes an undocumented binary layout.[2]

5.2 Recycle versus remove

At checkpoints, PostgreSQL can recycle no-longer-required WAL segments by renaming them for future positions instead of repeatedly creating new files. wal_recycle=on is the default; copy-on-write filesystems are one scenario where creating new files can sometimes be preferable.[3]

5.3 Segment preallocation

With wal_init_zero=on (the default), PostgreSQL initializes new WAL files with zeroes, which can preallocate space on some filesystems. Copy-on-write filesystems may not benefit and can be configured differently.[3]

Never manually delete files from pg_wal to free space. PostgreSQL's recovery, replication, and archive state determines which WAL is safe to recycle/remove. Manual deletion can make the cluster unrecoverable or break replicas and slots.

6. WAL buffers and the WAL writer

Before WAL reaches files, records are staged in shared WAL buffers. wal_buffers controls the shared memory available for WAL not yet written. PostgreSQL's default -1 auto-sizes the buffer to approximately 1/32 of shared_buffers, with a lower bound of 64 KiB and an upper bound of one WAL segment (normally 16 MiB). The default is intended to be reasonable for most installations.[3] 

SHOW wal_buffers;
SHOW wal_writer_delay;
SHOW wal_writer_flush_after;

6.1 What fills WAL buffers?

Backends insert WAL records into the shared WAL buffers while modifying protected data. If buffers fill, backends must help write WAL, increasing foreground latency. A few megabytes can help on highly concurrent write workloads, but extremely large WAL buffers usually do not help because commit and the WAL writer still cause frequent writes/flushes.[3]

6.2 WAL writer

The WAL writer periodically writes WAL buffers and may flush them according to wal_writer_delay and wal_writer_flush_after. In PostgreSQL 18, the default delay is 200 ms and the default volume threshold is 1 MiB. Asynchronously committing transactions can wake the WAL writer sooner.[3]

6.3 Detect buffer pressure

SELECT
    wal_records,
    wal_fpi,
    pg_size_pretty(wal_bytes) AS wal_bytes,
    wal_buffers_full,
    stats_reset
FROM pg_stat_wal;

A rapidly increasing wal_buffers_full value means WAL generation has repeatedly exhausted the available WAL buffers. PostgreSQL 18 also exposes per-statement wal_buffers_full, WAL records, full-page images, and WAL bytes in pg_stat_statements when that extension is enabled.[15][16]

7. Commit durability

Under ordinary durable settings, PostgreSQL makes the transaction's commit WAL durable before returning success. This does not require the transaction's table/index pages to be on disk yet. If a crash occurs afterward, recovery can replay the durable WAL and reproduce those data-page changes.[1]

Transaction T UPDATE heap page UPDATE index page write commit record | v WAL flushed through T's commit LSN | +--> COMMIT success returned | | data pages may still be dirty v later checkpoint/background writes Crash after COMMIT: WAL has T -> REDO can reconstruct missing page writes. Crash before commit WAL durable: T may be absent after recovery.

7.1 Group commit

Concurrent committers can share WAL synchronization. If several transactions need WAL flushed to nearby positions, one process's durable flush can satisfy others waiting behind it. This is one reason PostgreSQL can sustain transactional throughput even though durable commits involve storage synchronization.[1][8]

7.2 Commit delay knobs

SHOW commit_delay;
SHOW commit_siblings;

commit_delay can intentionally delay a synchronous WAL flush when enough concurrent transactions are active, attempting to gather more commits behind one flush. This is workload- and storage-dependent and should be benchmarked rather than enabled by rule of thumb.[8]

8. fsync and storage correctness

With fsync=on, PostgreSQL issues operating-system synchronization requests so writes are forced to durable storage in the required order. The exact mechanism is controlled by wal_sync_method and can use facilities such as fdatasync(), fsync(), O_DSYNC, or platform-specific alternatives.[3] 

SHOW fsync;
SHOW wal_sync_method;

8.1 Why fsync=off is dangerous

Turning fsync off disables PostgreSQL's normal attempts to force and order durable writes. An abrupt operating-system or hardware failure can then leave data files and WAL in an ordering/state that cannot be repaired by ordinary crash recovery, resulting in unrecoverable corruption. PostgreSQL states that high-quality hardware by itself is not a sufficient reason to disable fsync.[3]

8.2 Legitimate non-durable scenarios

PostgreSQL documents limited cases where fsync=off can make sense: disposable databases, initial loading of a cluster that can be recreated from another source, or frequently recreated read-only clones not used for failover. These are explicitly non-durable designs.[3][17]

8.3 Returning from fsync=off

Simply changing the setting back to on does not retroactively guarantee that previously dirty kernel buffers have reached persistent storage. PostgreSQL documents methods such as shutting down and synchronizing storage, sync, reboot/unmount, or initdb --sync-only to establish a durable baseline.[3][18]

8.4 Storage must tell the truth

WAL durability depends on the storage stack honoring flush requests. A controller or drive that reports a flush complete while retaining volatile write-cache data can violate PostgreSQL's assumptions. Battery-backed/persistent caches or correctly configured write barriers/flush semantics are part of database durability, not an implementation detail.[2][19]

9. synchronous_commit

synchronous_commit determines how far WAL processing must progress before PostgreSQL reports transaction success. The valid values are off, local, remote_write, on, and remote_apply. Without configured synchronous standbys, the meaningful local distinction is primarily on versus off; the remote modes gain their distinct behavior when synchronous replication is configured.[3]

ValueLocal durability before successRemote synchronous behavior
offDoes not wait for local WAL flushDoes not wait for synchronous standby acknowledgement
localWaits for local WAL flushDoes not wait for remote synchronous standby
remote_writeWaits for local WAL flushWaits for remote OS-level write acknowledgement
onWaits for local WAL flushWaits for remote durable flush when synchronous replication applies
remote_applyWaits for local WAL flushWaits until synchronous standby replays the commit

9.1 Per-transaction durability

BEGIN;

SET LOCAL synchronous_commit = off;

INSERT INTO analytics.page_view(...);

COMMIT;
BEGIN;

SET LOCAL synchronous_commit = remote_apply;

INSERT INTO finance.payment(...);

COMMIT;

The setting can be applied selectively by transaction/session/user/database. This allows noncritical telemetry to use asynchronous commit while financially significant transactions preserve stronger acknowledgement semantics.[3]

10. Asynchronous commit

With synchronous_commit=off, PostgreSQL can acknowledge a transaction once it is logically complete without waiting for that transaction's WAL to reach persistent storage. A crash can therefore lose recent acknowledged transactions. PostgreSQL nevertheless guarantees that recovery will leave the database in a consistent state—as if those lost transactions had aborted cleanly—because fsync and write-ordering protections remain active.[7][3]

PostgreSQL documents the maximum local durability delay for asynchronous commit as three times wal_writer_delay. This is an upper-bound behavior under the WAL writer mechanism, not a promise that every asynchronous transaction waits that long.[3]

Safe performance trade-off: if an application can lose a small number of recent noncritical transactions after a host crash, synchronous_commit=off is far safer than fsync=off. The former risks recent transaction loss; the latter risks structural corruption.

11. Checkpoints

A checkpoint establishes a WAL position such that database files have been brought forward sufficiently for recovery to begin from that checkpoint's REDO location rather than from the beginning of time. Checkpoints write dirty buffers, synchronize files, emit checkpoint WAL information, and update control information used to find the recovery starting point.[20][2]

11.1 Why checkpoints exist

Without checkpoints, crash recovery could require replaying an ever-growing history. A newer checkpoint shortens the amount of WAL that must be scanned/replayed. The trade-off is checkpoint I/O and full-page-image generation after the checkpoint.[21]

11.2 Main checkpoint settings

# Illustrative values, not universal recommendations:
checkpoint_timeout = '15min'
checkpoint_completion_target = 0.9
max_wal_size = '8GB'
min_wal_size = '2GB'

checkpoint_timeout sets the maximum time between automatic checkpoints; PostgreSQL 18 defaults to 5 minutes. max_wal_size can trigger checkpoints based on WAL volume and is a soft rather than absolute limit. checkpoint_completion_target (default 0.9) spreads checkpoint write activity across most of the available checkpoint interval to reduce I/O spikes.[3]

11.3 Forced checkpoints

CHECKPOINT;

The SQL CHECKPOINT command forces an immediate checkpoint and is not intended for routine normal operation. Frequent forced checkpoints increase I/O and full-page-write generation.[20]

11.4 Checkpoint frequency and WAL volume

More frequent checkpoints tend to increase full-page images because each checkpoint resets the “first modification since checkpoint” condition. Increasing checkpoint intervals can therefore reduce full-page-write overhead, but it allows more WAL to accumulate and can lengthen crash recovery.[3]

12. Restartpoints during recovery

A server in archive recovery or standby recovery cannot create ordinary checkpoints in the same way as a primary. Instead, it creates restartpoints at suitable checkpoint records encountered in the replay stream. Restartpoints establish points from which recovery could restart if the standby itself crashes.[21] 

-- On a server in recovery this requests a restartpoint.
CHECKPOINT;

PostgreSQL's CHECKPOINT command documentation explicitly notes that during recovery it forces a restartpoint rather than an ordinary checkpoint.[20]

13. Full-page writes

A database page is normally written in a storage-block-sized operation, but an operating-system or power failure can interrupt that write and leave a torn page: part old contents, part new contents. The ordinary logical delta in a WAL record might not contain enough information to repair arbitrary torn bytes. PostgreSQL's default full_page_writes=on protects against this by logging the entire page image the first time a page is modified after each checkpoint.[3]

checkpoint | v page P first modified | +--> WAL includes full-page image (FPI) + change information | page P modified again | +--> usually only change WAL, no second FPI needed | next checkpoint | v page P next first modification | +--> FPI again

13.1 Why only the first change?

Crash recovery starts from a checkpoint. Once the first post-checkpoint change replays a full valid page image, subsequent WAL deltas for that page have a known consistent base. Logging the page image on every modification would therefore be unnecessary overhead.[3][2]

13.2 Do not disable casually

SHOW full_page_writes;

PostgreSQL warns that disabling full_page_writes can produce unrecoverable or silent data corruption after a system failure. It should be treated with the same caution as other non-durable settings.[3][17]

13.3 Hint bits and wal_log_hints

SHOW wal_log_hints;

When wal_log_hints=on, PostgreSQL logs full-page images on the first post-checkpoint change even for otherwise noncritical hint-bit modifications. Data checksums cause hint-bit updates to receive the necessary WAL protection regardless of this setting. wal_log_hints is also relevant to tooling such as pg_rewind on clusters without data checksums.[3][22]

14. WAL compression

Full-page images can dominate WAL volume in workloads that dirty many distinct pages soon after checkpoints. wal_compression compresses full-page images before they are written to WAL and decompresses them during replay. PostgreSQL 18 supports pglz, and builds compiled with the corresponding libraries can also support lz4 and zstd.[3] 

# Example:
wal_compression = zstd

Compression can reduce WAL bandwidth, archive storage, and replication traffic at the cost of CPU during generation and replay. The correct choice depends on CPU headroom, storage/network bottlenecks, compression availability in the PostgreSQL build, and the proportion of WAL made up of full-page images.[3]

14.1 Measure before deciding

SELECT
    wal_records,
    wal_fpi,
    pg_size_pretty(wal_bytes) AS wal_bytes
FROM pg_stat_wal;

A high wal_fpi count relative to total WAL activity is one signal that full-page images are significant enough for compression/checkpoint tuning to matter.[15]

15. Crash recovery

After an unclean shutdown, PostgreSQL reads cluster control information to locate the latest usable checkpoint, reads the checkpoint record, and replays WAL forward from the checkpoint's REDO location. Because WAL is durable before protected data pages, replay can reconstruct changes that committed but had not yet reached the data files.[2]

pg_control | v latest checkpoint location | v read checkpoint record | v REDO start LSN | v scan WAL forward | +--> restore full-page images where needed +--> redo heap/index/catalog operations +--> apply transaction state records | v consistent end of WAL | v database opens for normal operation

15.1 Recovery time is partly a WAL-volume problem

Larger intervals between checkpoints can reduce steady-state checkpoint/FPI overhead but can increase the volume of WAL recovery may need to scan and replay after a crash. max_wal_size and checkpoint_timeout therefore participate in both performance and recovery-time design.[3]

15.2 WAL does not replace data checksums

WAL protects the write ordering and reconstructs logged changes. Data checksums detect some forms of on-disk page corruption. The mechanisms address different reliability problems and are complementary.[23]

16. wal_level

wal_level controls how much information PostgreSQL writes to WAL. PostgreSQL 18 supports minimal, replica (the default), and logical. Each higher level contains the information required by lower levels plus additional information for its use case. It can only be changed at server start.[3]

LevelPurposeTypical use
minimalEnough for crash recovery, with reduced logging for certain create/rewrite operationsSpecialized non-replication/non-archiving configurations
replicaAdds information needed for WAL archiving and physical replication, including standby readsDefault production setting for backups/HA
logicalAdds information required for logical decodingLogical replication, CDC, output plugins
 
SHOW wal_level;

16.1 Higher WAL levels can increase volume

Additional logical/replication information is not free. If logical decoding is not required, replica is normally sufficient for physical replication and continuous archiving. When logical replication or a CDC tool requires logical decoding, use logical and size WAL/network/storage accordingly.[3][24]

17. WAL archiving

Continuous archiving copies completed WAL segments to durable external storage. Combined with a physical base backup, archived WAL enables point-in-time recovery: restore the backup, fetch archived WAL, and replay it forward to a target. PostgreSQL can archive through a shell archive_command or an archive_library module.[5][25]

17.1 Command-based archiving

wal_level = replica
archive_mode = on

archive_command =
  'test ! -f /srv/wal-archive/%f && cp %p /srv/wal-archive/%f'

%p is replaced by the path to the WAL file to archive and %f by the file name. The command must return success only when the WAL has been stored safely. PostgreSQL retries failed archival and will not recycle/remove the segment merely because the command was attempted.[5][3]

17.2 Archive modules

archive_mode = on
archive_library = 'basic_archive'
basic_archive.archive_directory = '/srv/wal-archive'

PostgreSQL's archive-module API avoids launching a shell command per segment and allows modules to implement more robust archiving behavior. The supplied basic_archive module is an example implementation, not a complete off-site disaster-recovery product.[25][26]

17.3 Archive lag on low-write systems

archive_timeout = '5min'

A WAL segment is normally archived after it completes. archive_timeout can force a segment switch so low-volume systems do not leave recent WAL unarchived for too long. Very small values waste archive space because switched segments still occupy full segment-sized files.[3]

17.4 Force a segment switch

SELECT pg_switch_wal();

This can be useful before a backup/recovery test or when an operator wants the current partly filled segment to become archivable promptly.[11]

18. WAL retention

The amount of WAL retained in pg_wal is determined by the maximum requirement among several independent mechanisms. A segment cannot safely disappear simply because the normal checkpoint size budget has been reached if an archive, standby, or slot still requires it.[3][4]

Reasons a WAL segment may remain in pg_wal: normal checkpoint/recycle budget --------+ min_wal_size ----------------------------+ wal_keep_size ---------------------------+ archive not yet successful --------------+--> effective retention physical slot restart_lsn ---------------+ logical slot restart_lsn ----------------+ backup/recovery requirements ------------+ standby/recovery state ------------------+

18.1 max_wal_size is a soft limit

SHOW max_wal_size;
SHOW min_wal_size;

max_wal_size influences automatic checkpoint behavior but is explicitly a soft limit. Heavy load, a failing archive command/library, high wal_keep_size, and replication-slot requirements can cause pg_wal to grow beyond it.[3]

18.2 wal_keep_size

# Example:
wal_keep_size = '2GB'

wal_keep_size retains at least a specified amount of older WAL in pg_wal for streaming standbys, giving lagging replicas some protection even without slots. Unlike a replication slot, it does not track a specific consumer's exact progress.[4]

18.3 Capacity formula

approximate WAL storage runway
    = free pg_wal bytes
      / peak WAL generation bytes per second

Use peak—not average—generation. Index builds, bulk loads, maintenance, checkpoints/full-page images, and write bursts can drastically change WAL generation.

19. Replication slots

A replication slot is a durable promise that PostgreSQL will retain WAL (and, for logical slots, catalog visibility state) required by a specific replication consumer. Physical slots protect WAL for physical standbys; logical slots protect WAL and decoding state for logical replication/CDC. Slots survive disconnects, so they protect consumers from short outages but can also retain large amounts of WAL during long outages.[4][27]

19.1 Create a physical slot

SELECT *
FROM pg_create_physical_replication_slot(
    'standby_a'
);

19.2 Create a logical slot

SELECT *
FROM pg_create_logical_replication_slot(
    'cdc_orders',
    'pgoutput'
);

19.3 Inspect slot retention

SELECT
    slot_name,
    slot_type,
    active,
    active_pid,
    restart_lsn,
    confirmed_flush_lsn,
    wal_status,
    pg_size_pretty(safe_wal_size) AS safe_wal_remaining,
    inactive_since,
    invalidation_reason
FROM pg_replication_slots
ORDER BY slot_name;

restart_lsn is the oldest WAL position the slot may still require. For logical slots, confirmed_flush_lsn records how far the consumer has confirmed receipt. PostgreSQL 18 exposes wal_status and safe_wal_size to show whether a slot's required WAL remains safely retained under configured limits.[27]

19.4 Bound slot retention

# Examples only:
max_slot_wal_keep_size = '50GB'
idle_replication_slot_timeout = '24h'

With the default max_slot_wal_keep_size=-1, a slot can retain unlimited WAL. A finite limit can prevent unbounded growth but may invalidate a slot if the consumer falls too far behind. PostgreSQL 18's idle_replication_slot_timeout can invalidate slots inactive longer than a configured interval. Both settings trade consumer continuity for storage safety and must be aligned with legitimate outage windows.[4]

Inactive slot + active workload = growing disk obligation. Every production slot should have an owner, purpose, lag alert, retirement process, and explicit retention policy.

20. WAL and physical replication

Streaming replication sends WAL from the primary's WAL sender to a standby WAL receiver. The standby writes/flushed WAL and recovery replays it. Replication positions are therefore WAL LSNs, and replication lag can be split into send, receive/write, flush, and replay stages.[28][29] 

SELECT
    application_name,
    state,
    sync_state,
    sent_lsn,
    write_lsn,
    flush_lsn,
    replay_lsn,
    pg_size_pretty(
        pg_wal_lsn_diff(
            pg_current_wal_lsn(),
            replay_lsn
        )
    ) AS replay_byte_lag
FROM pg_stat_replication;

The same WAL stream can simultaneously support crash recovery, physical replication, and archiving. That is why changing WAL generation or retention settings often affects backup and HA behavior together.

21. WAL and logical decoding

Logical decoding reads WAL and reconstructs logical row/change information through an output plugin. This requires wal_level=logical and logical replication slots. The standard logical replication implementation uses the built-in pgoutput plugin, while test_decoding is supplied for testing and illustration.[24][30] 

wal_level = logical
max_replication_slots = 10
max_wal_senders = 10

21.1 Logical retention can also block vacuum

Logical slots can expose both restart_lsn and catalog_xmin. The former retains WAL; the latter can prevent vacuum from removing older catalog tuples required for decoding. Slot monitoring is therefore both a WAL-storage and database-bloat concern.[27]

22. Monitoring WAL in PostgreSQL 18

22.1 Cluster-wide generation

SELECT
    wal_records,
    wal_fpi,
    pg_size_pretty(wal_bytes) AS wal_bytes,
    wal_buffers_full,
    stats_reset
FROM pg_stat_wal;

In PostgreSQL 18, WAL I/O timing has been moved out of pg_stat_wal into pg_stat_io; PostgreSQL 18 also adds WAL I/O rows and per-backend WAL/I/O observability improvements.[15][31]

22.2 WAL I/O

SELECT *
FROM pg_stat_io
WHERE object = 'wal'
ORDER BY backend_type, context;

Exact row combinations depend on server activity and PostgreSQL's statistics model. Enable track_wal_io_timing when WAL I/O timing itself must be measured, recognizing that timing instrumentation can add overhead on some systems.[31]

22.3 Checkpointer health

SELECT
    num_timed,
    num_requested,
    num_done,
    write_time,
    sync_time,
    buffers_written,
    slru_written,
    stats_reset
FROM pg_stat_checkpointer;

PostgreSQL 18 adds num_done and slru_written to checkpointer statistics. A high rate of requested/WAL-driven checkpoints relative to expected timed checkpoints can indicate that max_wal_size is too small for the workload.[31]

22.4 Archive health

SELECT
    archived_count,
    last_archived_wal,
    last_archived_time,
    failed_count,
    last_failed_wal,
    last_failed_time,
    stats_reset
FROM pg_stat_archiver;

22.5 Per-statement WAL

SELECT
    query,
    calls,
    wal_records,
    wal_fpi,
    pg_size_pretty(wal_bytes) AS wal_bytes,
    wal_buffers_full
FROM pg_stat_statements
ORDER BY wal_bytes DESC
LIMIT 20;

This is especially useful for finding statements whose runtime seems acceptable but whose WAL amplification is expensive for replication, archiving, storage, and recovery.[16]

22.6 Estimate WAL rate

-- Capture at t1:
SELECT clock_timestamp(), pg_current_wal_lsn();

-- Capture again at t2 and calculate:
SELECT
    pg_wal_lsn_diff($lsn2::pg_lsn, $lsn1::pg_lsn)
    / EXTRACT(EPOCH FROM ($time2 - $time1))
    AS bytes_per_second;

23. Inspecting WAL with pg_waldump

pg_waldump renders PostgreSQL WAL records in human-readable form. It is a diagnostic/internal utility and is most useful for database engineers investigating WAL composition, resource-manager activity, recovery behavior, or extension logging. It should generally be run against files while the server is stopped or against copied WAL rather than used as an ordinary application interface.[10]

23.1 Display records

pg_waldump \
  --path="$PGDATA/pg_wal" \
  --limit=100

23.2 Filter by resource manager

pg_waldump \
  --path="$PGDATA/pg_wal" \
  --rmgr=Btree \
  --limit=50

23.3 Summary mode

pg_waldump \
  --path="$PGDATA/pg_wal" \
  --stats=record

The output can reveal which resource managers and record types dominate a captured WAL range. Combine this with workload-level statistics rather than inferring application causality from WAL alone.

24. WAL performance tuning

24.1 Start with the bottleneck

SymptomLikely areaInvestigate
Commit latency tracks storage latencyWAL durable flushpg_stat_io, storage cache/flush behavior, wal_sync_method, group commit
wal_buffers_full rises rapidlyWAL buffer pressureWAL rate, wal_buffers, concurrent writers
Very high wal_fpiFull-page-image volumeCheckpoint frequency, max_wal_size, wal_compression
Frequent requested checkpointsCheckpoint/WAL sizingpg_stat_checkpointer, max_wal_size
pg_wal grows despite checkpointsRetention obligationarchive failure, slots, wal_keep_size, replica lag
Replication/archive bandwidth saturatedWAL volumeWAL-generating SQL, FPI ratio, compression, bulk operations

24.2 Increase checkpoint interval carefully

# Example baseline to benchmark, not a generic prescription:
checkpoint_timeout = '15min'
checkpoint_completion_target = 0.9
max_wal_size = '8GB'
min_wal_size = '2GB'

Larger checkpoint intervals can reduce checkpoint churn and FPIs, but require more pg_wal space and can extend crash-recovery work. The right values are workload- and RTO-dependent.[3]

24.3 Use asynchronous commit selectively

ALTER ROLE telemetry_ingest
SET synchronous_commit = off;

This can reduce latency for expendable event streams while leaving default durable commit semantics for critical application roles. Do not disable fsync to solve a commit-latency problem that can be addressed at the transaction durability layer.[3]

24.4 Compress FPIs if CPU is available

wal_compression = lz4

Benchmark CPU cost against reduced WAL bytes, archive bandwidth, and replica traffic. Compression helps primarily the full-page-image component of WAL rather than every record equally.[3]

24.5 Measure SQL WAL amplification

EXPLAIN (
    ANALYZE,
    BUFFERS,
    WAL
)
UPDATE app.account
SET last_seen_at = clock_timestamp()
WHERE account_id BETWEEN 1 AND 100000;

Modern PostgreSQL EXPLAIN can report WAL records, full-page images, and bytes generated by the executed plan, helping compare alternative write strategies.[32]

25. WAL failure modes

25.1 Archive destination failure

WAL generation continues | archive command fails | completed WAL cannot be recycled | pg_wal grows | filesystem fills | database may be unable to continue safely

Monitor pg_stat_archiver, archive-side freshness, and filesystem free space. The failure of a remote backup service can become a primary-database storage incident if the backlog is allowed to grow indefinitely.[5]

25.2 Abandoned replication slot

A disconnected consumer with a slot can create the same disk-growth pattern. With unlimited slot retention, the cluster continues retaining old WAL until the consumer advances or the slot is removed. A finite max_slot_wal_keep_size protects disk at the cost of potentially invalidating the consumer.[4][27]

25.3 Misconfigured durability

Disabling fsync or full_page_writes can transform an ordinary abrupt failure into unrecoverable corruption. Disabling only synchronous_commit has a different, narrower failure mode: loss of some recent acknowledged transactions.[3][17]

25.4 Storage lying about flush completion

Even correct PostgreSQL settings cannot compensate for storage that violates flush semantics. Test and configure storage controllers, hypervisors, cloud/block devices, filesystems, and write caches according to their durability guarantees.[19]

25.5 WAL retention policy too small for replica outage

Without enough wal_keep_size, archive coverage, or a healthy physical slot, a standby that falls too far behind can lose access to required WAL and need a new base backup. Retention policy must reflect realistic repair/outage durations rather than normal steady-state lag.

25.6 Manually invoking pg_resetwal

pg_resetwal is an emergency last-resort utility for control/WAL corruption scenarios and can leave the database inconsistent. It is not a disk-space cleanup tool and should never be substituted for repairing archive or slot retention problems.[33]

26. Production configuration patterns

26.1 Durable standalone database with PITR

wal_level = replica
fsync = on
full_page_writes = on
synchronous_commit = on

checkpoint_completion_target = 0.9
max_wal_size = '8GB'

archive_mode = on
archive_command = '/usr/local/bin/archive-wal %p %f'

The archival helper should atomically upload/store WAL, refuse unsafe collisions, return success only after durability criteria are satisfied, and export observable failure state.

26.2 Primary with physical standbys

wal_level = replica
fsync = on
full_page_writes = on

max_wal_senders = 10
max_replication_slots = 10
wal_keep_size = '2GB'

# Protect local disk from an indefinitely abandoned slot.
max_slot_wal_keep_size = '100GB'

26.3 Primary with CDC/logical replication

wal_level = logical

max_wal_senders = 20
max_replication_slots = 20

# Operational safety policy example:
max_slot_wal_keep_size = '100GB'
idle_replication_slot_timeout = '48h'

The slot limits above are examples, not recommendations. They must be sized from peak WAL rate, maximum expected connector outage, resynchronization cost, and disk capacity.

26.4 Mixed durability by workload

-- Default:
ALTER DATABASE appdb
SET synchronous_commit = on;

-- Noncritical fire-and-forget telemetry:
ALTER ROLE telemetry_writer
SET synchronous_commit = off;

26.5 Observability query

WITH wal AS (
    SELECT
        wal_records,
        wal_fpi,
        wal_bytes,
        wal_buffers_full
    FROM pg_stat_wal
),
slots AS (
    SELECT
        count(*) FILTER (WHERE NOT active) AS inactive_slots,
        max(
            pg_wal_lsn_diff(
                pg_current_wal_lsn(),
                restart_lsn
            )
        ) FILTER (WHERE restart_lsn IS NOT NULL)
            AS max_slot_retained_bytes
    FROM pg_replication_slots
)
SELECT
    wal.wal_records,
    wal.wal_fpi,
    pg_size_pretty(wal.wal_bytes) AS total_wal,
    wal.wal_buffers_full,
    slots.inactive_slots,
    pg_size_pretty(slots.max_slot_retained_bytes)
        AS max_slot_retention
FROM wal
CROSS JOIN slots;

27. Production checklist

  1. Keep fsync=on for durable production data unless the entire database is intentionally disposable.
  2. Keep full_page_writes=on for crash safety against torn page writes.
  3. Use synchronous_commit=off selectively when losing recent noncritical transactions is acceptable.
  4. Choose wal_level from actual requirements. Use replica for archiving/physical replication and logical when logical decoding is required.
  5. Size pg_wal capacity for failure modes. Include peak WAL rate, archive outages, standby lag, and slot retention.
  6. Do not treat max_wal_size as a disk-usage cap.
  7. Monitor replication slots. Alert on inactivity, retained bytes, wal_status, and safe_wal_size.
  8. Monitor archiving. Archive failure is eventually a local storage failure.
  9. Monitor checkpoint behavior. Frequent requested/WAL-driven checkpoints often indicate under-sized WAL/checkpoint configuration.
  10. Measure full-page-image volume. Use pg_stat_wal, pg_stat_statements, and EXPLAIN (WAL).
  11. Consider WAL compression when FPIs dominate and CPU is available.
  12. Measure WAL I/O in PostgreSQL 18 through pg_stat_io.
  13. Test storage flush semantics. PostgreSQL durability assumes the storage stack honors synchronization requests.
  14. Archive WAL off-host when PITR/disaster recovery is required.
  15. Test crash and PITR recovery. Settings are not a durability guarantee until the recovery path is exercised.
  16. Never manually delete pg_wal files.
  17. Treat pg_resetwal as last-resort recovery tooling.
  18. Correlate WAL tuning with HA and backups. The same WAL stream drives crash recovery, replication, and continuous archiving.
WAL design principle: optimize the log only after preserving its ordering contract. PostgreSQL performance depends on making WAL cheap to generate and flush; PostgreSQL correctness depends on never allowing protected data to outrun the WAL needed to recover it.
