PostgreSQL Data Types

A technical guide to PostgreSQL's scalar and specialized type system: integers and exact/inexact numerics, strings, date/time, Boolean and binary data, arrays, JSON/JSONB, XML, UUID, enums, ranges and multiranges, composite and domain types, network and geometric types, and full-text-search types.

Technical article • PostgreSQL 18.6 baseline • Updated 16 September 2026 • Vancouver-style references

Abstract

PostgreSQL has a rich, extensible type system. Built-in scalar types cover exact and approximate numerics, strings, temporal values, Boolean values and raw bytes; specialized types represent UUIDs, network addresses, geometric objects, JSON/XML, arrays, ranges and full-text-search structures. PostgreSQL also lets users define enum, composite, range, domain and fully custom base types, and its operator/index infrastructure is strongly type-directed.[1][2]

Type choice is part of schema semantics. numeric/decimal provide exact decimal arithmetic where floating-point rounding would be inappropriate; text and unconstrained varchar avoid arbitrary string limits; timestamptz represents instants and is stored internally in UTC while displaying in the session time zone; bytea stores arbitrary octets; and network/range/full-text types supply validation and operators that plain strings cannot.[3]-[7]

Structured types are not interchangeable. json preserves the original JSON text, including whitespace and duplicate keys, whereas jsonb stores a decomposed representation, normalizes object representation, keeps only the last duplicate key, supports containment semantics and can be indexed effectively with GIN. Arrays are strongly typed homogeneous collections. Composite values are typed rows. Domains restrict an underlying type with reusable constraints. Range and multirange types encode contiguous and non-contiguous ordered intervals and integrate with GiST/SP-GiST and exclusion/temporal constraints.[8]-[12]

1. PostgreSQL's type system

Every PostgreSQL value has a data type. Types determine valid input syntax, binary representation, comparison/arithmetic semantics, casts, operators, functions, statistics behavior and available index operator classes. Built-in and user-defined types are cataloged in pg_type; auxiliary catalogs such as pg_range add type-specific metadata.[1][13][14]

SELECT
    n.nspname AS schema_name,
    t.typname,
    t.typtype,
    t.typcategory,
    t.typlen
FROM pg_type AS t
JOIN pg_namespace AS n
  ON n.oid = t.typnamespace
WHERE n.nspname IN ('pg_catalog', 'app')
ORDER BY n.nspname, t.typname;

2. Numeric types

PostgreSQL numeric types include two-, four- and eight-byte integers, exact arbitrary-precision numeric/decimal, and four-/eight-byte inexact floating-point types. Integer overflow raises an error rather than silently wrapping. numeric is recommended where exactness matters, while floating-point arithmetic trades exact decimal representation for hardware-friendly approximate computation.[3]

3. smallint, integer, and bigint

These types store signed whole numbers. PostgreSQL describes integer as the usual choice because it balances storage, range and performance; smallint saves two bytes where ranges are truly small, and bigint is required when a four-byte integer might overflow.[3]

CREATE TABLE metrics.counter (
    shard_id smallint NOT NULL,
    event_count bigint NOT NULL DEFAULT 0,
    retry_count integer NOT NULL DEFAULT 0
);

Choose integer width from maximum lifetime values, not current sample values. Changing a key type after billions of rows and foreign-key references exist is operationally much harder than choosing sufficient range initially.

4. numeric and decimal

numeric and decimal are equivalent exact types. Declaring numeric(p,s) constrains precision and scale; unconstrained numeric can store values up to PostgreSQL's implementation limits. Exact arithmetic is especially appropriate for money, accounting, exact ratios and other domains where binary floating-point rounding is unacceptable.[3]

CREATE TABLE billing.invoice (
    invoice_id bigint PRIMARY KEY,
    subtotal numeric(14,2) NOT NULL,
    tax      numeric(14,2) NOT NULL,
    total    numeric(14,2) NOT NULL
);
SELECT
    0.1::numeric + 0.2::numeric AS exact_decimal;

PostgreSQL numeric also supports special values such as Infinity, -Infinity and NaN in supported declarations; constrained application domains may still reject these through explicit checks when they are not meaningful.[3]

5. real and double precision

real and double precision are inexact floating-point types based on the platform's IEEE 754 implementation. Many decimal fractions cannot be represented exactly in binary floating point, so direct equality expectations can be inappropriate after computation. Use them for measurements, simulation and numerical workloads where approximation is part of the domain rather than for exact currency arithmetic.[3]

CREATE TABLE telemetry.sensor_reading (
    sensor_id bigint NOT NULL,
    measured_at timestamptz NOT NULL,
    temperature double precision NOT NULL
);

6. Character types

PostgreSQL's general-purpose character types are fixed-length character(n)/char(n), bounded variable-length character varying(n)/varchar(n), unbounded varchar, and text. Length limits are measured in characters, not bytes. Character-set validity is enforced according to the database encoding, and the NUL code point cannot be stored in PostgreSQL character strings.[4]

7. char, varchar, and text

char(n) blank-pads stored values to the declared length and treats trailing spaces as insignificant in ordinary comparisons. varchar(n) enforces a maximum character count without padding. text and unconstrained varchar accept arbitrary-length strings up to PostgreSQL's value-size limits. PostgreSQL documents no general performance advantage for char(n); it is commonly slower/larger because of padding, so text or varchar are normally preferred.[4]

CREATE TABLE app.customer (
    customer_id bigint PRIMARY KEY,
    country_code char(2) NOT NULL,
    display_name text NOT NULL,
    external_label varchar(80)
);
A length limit is a domain rule, not a storage optimization. Use varchar(n) when “at most n characters” is actually an invariant. Do not add arbitrary lengths merely because another DBMS historically required them.

8. Date/time types

PostgreSQL supports date, time-of-day types, timestamp types and interval. The timestamp/time/interval types accept fractional-second precision from 0 through 6. PostgreSQL uses the proleptic Gregorian calendar for dates, including years before the calendar's historical adoption.[5]

9. date and time

date represents a calendar date without time of day. time without time zone represents a time of day without a date. PostgreSQL also implements time with time zone for SQL compatibility, but its documentation discourages it for most applications because a fixed time-of-day plus offset lacks the date context needed to apply daylight-saving rules reliably.[5]

CREATE TABLE scheduling.office_hours (
    weekday smallint NOT NULL CHECK (weekday BETWEEN 1 AND 7),
    opens_at time NOT NULL,
    closes_at time NOT NULL,
    CHECK (opens_at < closes_at)
);

10. timestamp and timestamptz

SQL timestamp means timestamp without time zone. PostgreSQL's timestamptz abbreviation means timestamp with time zone. A timestamptz value represents an instant: PostgreSQL converts input to UTC internally and renders it in the current session TimeZone at output. The original zone name is not retained as part of the value.[5]

SET TIME ZONE 'America/New_York';

SELECT
    timestamptz '2026-09-16 09:00:00-04' AS instant,
    timestamp   '2026-09-16 09:00:00'    AS local_wall_time;

11. interval

interval represents a span of time using separate month, day and microsecond components internally, preserving calendar-aware distinctions such as “1 month” versus a fixed number of seconds. Arithmetic involving months/days and timestamptz can therefore interact with month lengths and daylight-saving transitions differently from adding a fixed number of seconds.[5][15]

SELECT
    timestamptz '2026-03-07 12:00 America/New_York'
      + interval '1 day'  AS next_calendar_day,
    interval '2 years 3 months 4 days 05:06:07' AS duration;

12. boolean

PostgreSQL implements the SQL boolean type. Logical values are TRUE and FALSE; SQL null represents an unknown/missing state rather than a third stored Boolean value. The type occupies one byte and accepts several textual input spellings, though SQL literals TRUE/FALSE are clearest in application SQL.[6]

CREATE TABLE feature.flag (
    flag_name text PRIMARY KEY,
    enabled boolean NOT NULL DEFAULT false
);

SELECT *
FROM feature.flag
WHERE enabled;

13. Binary data with bytea

bytea stores arbitrary variable-length binary strings. Unlike character types, it permits zero bytes and other non-printable octets and treats the value as raw bytes rather than encoded text. PostgreSQL supports hexadecimal and historical escape input/output forms; hex is the default output and the preferred modern representation.[7]

CREATE TABLE file.chunk (
    chunk_id bigint PRIMARY KEY,
    payload bytea NOT NULL,
    sha256 bytea NOT NULL
);

INSERT INTO file.chunk(chunk_id, payload, sha256)
VALUES (
    1,
    decode('48656c6c6f', 'hex'),
    digest('Hello', 'sha256')
);

Binary-string functions such as encode/decode, get_byte, set_byte, and SHA-2 hash functions operate directly on bytea values.[16]

14. Arrays

PostgreSQL supports variable-length multidimensional arrays of built-in and user-defined base, enum, composite, range and domain element types. Array bounds are part of the value, and the declared dimensionality in ordinary table DDL is mainly documentation: PostgreSQL does not generally enforce a fixed declared dimension count/length.[8]

CREATE TABLE app.article (
    article_id bigint PRIMARY KEY,
    tags text[] NOT NULL DEFAULT '{}',
    quarterly_views integer[]
);

INSERT INTO app.article(article_id, tags, quarterly_views)
VALUES (
    1,
    ARRAY['postgresql', 'database', 'sql'],
    ARRAY[120, 180, 250, 300]
);

14.1 Access and search

SELECT
    tags[1],
    quarterly_views[2:4]
FROM app.article
WHERE article_id = 1;

SELECT *
FROM app.article
WHERE tags @> ARRAY['postgresql'];

Arrays have containment/overlap operators and can be indexed with suitable GIN operator classes. They work well when a collection is genuinely one atomic row attribute; if elements have independent identities, constraints, relationships, or frequent per-element updates, a child relation is usually a better relational design.[17]

15. json and jsonb

Both types validate JSON syntax. json stores an exact copy of the input text, preserving insignificant whitespace, object-key order and duplicate object keys. jsonb stores a decomposed binary representation, discards whitespace and key ordering, and retains only the last value for duplicate keys. Processing is generally faster with jsonb because reparsing is unnecessary, and jsonb supports GIN indexing and containment/existence operations.[9]

CREATE TABLE app.event (
    event_id bigint PRIMARY KEY,
    payload jsonb NOT NULL
);

INSERT INTO app.event(event_id, payload)
VALUES (
    1,
    '{"type":"purchase","amount":19.95,"tags":["web","promo"]}'
);

SELECT
    payload->>'type' AS type,
    (payload->>'amount')::numeric AS amount
FROM app.event
WHERE payload @> '{"type":"purchase"}';

15.1 Indexing JSONB

CREATE INDEX event_payload_gin
ON app.event
USING gin(payload);

CREATE INDEX event_payload_path_gin
ON app.event
USING gin(payload jsonb_path_ops);

The default jsonb_ops GIN class supports key-existence, containment and JSONPath operators. jsonb_path_ops supports a narrower operator set but can produce smaller/more specific containment-oriented indexes.[9]

15.2 SQL null versus JSON null

SQL NULL means absence/unknown at the SQL level. JSON null is a JSON value inside a non-null JSON document. They are not interchangeable and should be modeled deliberately.[9]

JSON is not a schema-avoidance mechanism. PostgreSQL's documentation recommends keeping JSON document structure reasonably predictable even in flexible applications. Core keys and invariants are usually easier to constrain and join when represented as typed relational columns.

16. xml

The xml type stores XML while validating input for XML well-formedness and enabling XML-specific functions/operators. It can store full XML documents or XML content fragments. PostgreSQL does not automatically validate values against DTDs or XML Schema, and XML support requires a PostgreSQL build with libxml support.[10][18]

CREATE TABLE integration.message (
    message_id bigint PRIMARY KEY,
    document xml NOT NULL
);

INSERT INTO integration.message
VALUES (
    1,
    XMLPARSE(
        DOCUMENT
        '<order id="42"><status>paid</status></order>'
    )
);
SELECT xpath(
    '/order/status/text()',
    document
)
FROM integration.message;

17. uuid

The uuid type stores 128-bit universally unique identifiers. PostgreSQL accepts standard and several alternative textual input forms and emits the canonical hyphenated form. PostgreSQL 18 natively provides UUIDv4 and timestamp-ordered UUIDv7 generation functions; the type itself can store UUIDs of any version.[11][19]

CREATE TABLE app.object (
    object_id uuid PRIMARY KEY DEFAULT uuidv7(),
    created_at timestamptz NOT NULL DEFAULT now()
);

UUIDs are useful where identifiers must be generated independently across nodes or exposed externally without a centralized sequence. UUIDv7 additionally incorporates time ordering, which can improve locality relative to purely random UUIDv4 identifiers in some index/write patterns.[19]

18. Enumerated types (ENUM)

An enum type is a static, ordered set of labels. Values have the ordering declared at type creation, and each enum type is type-safe and distinct from every other enum type even if labels overlap. New enum values can be added with ALTER TYPE; removing/reordering existing enum labels is intentionally more restrictive because enum values become durable type semantics.[20][21]

CREATE TYPE app.order_state AS ENUM (
    'draft',
    'submitted',
    'paid',
    'shipped',
    'cancelled'
);

CREATE TABLE app.orders (
    order_id bigint PRIMARY KEY,
    state app.order_state NOT NULL
);
SELECT enum_range(NULL::app.order_state);

18.1 Enum versus lookup table/domain

Enums fit small, stable, strongly typed vocabularies whose ordering is part of the type. Use a lookup/reference table when labels need rich metadata, independent lifecycle, localization, frequent changes or foreign-key relationships from many systems. A domain plus a check can be useful when the value should retain the underlying type's broader operator behavior.

19. Range types

A range type represents a contiguous interval over an ordered subtype. PostgreSQL supplies int4range, int8range, numrange, tsrange, tstzrange and daterange. Bounds can be inclusive/exclusive and independently unbounded; empty ranges are first-class values. Specialized operators express containment, overlap, adjacency and relative position.[12][22]

CREATE TABLE booking.reservation (
    reservation_id bigint PRIMARY KEY,
    room_id bigint NOT NULL,
    during tstzrange NOT NULL
);

SELECT *
FROM booking.reservation
WHERE during &&
      tstzrange(
        timestamptz '2026-09-16 13:00Z',
        timestamptz '2026-09-16 15:00Z',
        '[)'
      );

19.1 Range constraints

CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE booking.reservation
ADD CONSTRAINT room_no_overlap
EXCLUDE USING gist (
    room_id WITH =,
    during WITH &&
);

Range semantics integrate naturally with GiST/SP-GiST indexing, exclusion constraints and PostgreSQL 18 temporal WITHOUT OVERLAPS/PERIOD constraints.[12][23]

20. Multirange types

Every PostgreSQL range type has a corresponding multirange type. A multirange is an ordered list of non-null, nonempty, non-overlapping/non-adjacent ranges that represents a set of disjoint intervals. Built-in examples include int4multirange, nummultirange, tsmultirange, tstzmultirange, and datemultirange.[12]

SELECT datemultirange(
    daterange(date '2026-01-01', date '2026-01-10', '[)'),
    daterange(date '2026-02-01', date '2026-02-05', '[)')
);

Multiranges are useful for availability calendars, non-contiguous validity windows and compact set-of-interval representations where arrays of ranges would lack canonical multirange semantics and specialized operators.

21. Composite types

A composite type is a typed row structure: a named list of fields and their data types. Every table automatically has an associated composite row type, and standalone composites can be created with CREATE TYPE ... AS (...). They can be used as function arguments/results, table columns, arrays and nested structured values.[24][2]

CREATE TYPE app.money_amount AS (
    amount numeric(18,2),
    currency char(3)
);

CREATE TABLE app.payment (
    payment_id bigint PRIMARY KEY,
    charged app.money_amount NOT NULL
);

INSERT INTO app.payment
VALUES (
    1,
    ROW(19.95, 'USD')::app.money_amount
);

SELECT
    (charged).amount,
    (charged).currency
FROM app.payment;

Constraints attached to a table do not automatically become constraints of its standalone composite row type when that type is used elsewhere. If invariant enforcement must travel with the value, consider a domain or dedicated validation design.[24]

22. Domain types

A domain is a user-defined type layered over another type with optional constraints/default/nullability semantics. Operators/functions of the underlying type normally apply to domain values after implicit down-casting; assignment into the domain checks the domain's constraints. Domains are useful for reusable scalar/structured value contracts.[25][26]

CREATE DOMAIN app.positive_amount
AS numeric(18,2)
CHECK (VALUE > 0);

CREATE DOMAIN app.email_address
AS text
CHECK (
    VALUE = lower(VALUE)
    AND position('@' IN VALUE) > 1
);

CREATE TABLE app.invoice (
    invoice_id bigint PRIMARY KEY,
    amount app.positive_amount NOT NULL,
    customer_email app.email_address NOT NULL
);

Domain checks should depend only on the value and stable/immutable semantics. Cross-column and cross-row invariants belong in table constraints, exclusion constraints, triggers or transaction logic rather than a domain.

23. Network address types

PostgreSQL provides inet and cidr for IPv4/IPv6 data plus macaddr and macaddr8 for hardware addresses. The documentation recommends these specialized types instead of plain text because they validate input and provide network-aware containment, masking, arithmetic and formatting operations.[27][28]

23.1 inet

inet stores a host address plus an optional network prefix. Host bits to the right of the prefix can remain nonzero, so values such as 192.168.1.42/24 are valid.[27]

CREATE TABLE security.login_event (
    event_id bigint PRIMARY KEY,
    remote_addr inet NOT NULL,
    occurred_at timestamptz NOT NULL
);

SELECT *
FROM security.login_event
WHERE remote_addr <<= inet '10.0.0.0/8';

23.2 cidr

cidr represents network specifications rather than arbitrary host-with-prefix combinations. Host bits to the right of the mask must be zero. Use it when the stored value semantically denotes a subnet/network block.[27]

CREATE TABLE network.allowed_network (
    network cidr PRIMARY KEY,
    description text
);

23.3 macaddr and macaddr8

macaddr stores six-byte MAC addresses, while macaddr8 stores eight-byte EUI-64-style addresses. PostgreSQL accepts several common textual input formats and emits a standardized representation.[27]

24. Geometric types

PostgreSQL includes built-in two-dimensional geometric types: point, line, lseg, box, path, polygon, and circle. Specialized operators/functions implement containment, intersection, distance, translation and other geometry operations; suitable GiST/SP-GiST operator classes can index several geometric searches.[29][30]

CREATE TABLE map.marker (
    marker_id bigint PRIMARY KEY,
    location point NOT NULL
);

SELECT
    marker_id,
    location <-> point(-78.6382, 35.7796) AS distance
FROM map.marker
ORDER BY location <-> point(-78.6382, 35.7796)
LIMIT 10;

The built-in geometry model is a two-dimensional Cartesian plane. Applications requiring geographic coordinates, coordinate-reference systems, sophisticated topology, or GIS standards commonly use an extension such as PostGIS rather than assuming built-in point/polygon have geodetic semantics.

25. Full-text-search types: tsvector and tsquery

PostgreSQL provides two native types for full-text search. tsvector represents a document as a sorted set of normalized lexemes, optionally with positions and weights. tsquery represents a Boolean/proximity query over lexemes. Text search configuration determines parsing, stop-word handling, dictionaries and stemming before ordinary text is converted into these types.[31][32]

CREATE TABLE content.article (
    article_id bigint PRIMARY KEY,
    title text NOT NULL,
    body text NOT NULL,
    search_vector tsvector
        GENERATED ALWAYS AS (
            setweight(to_tsvector('english', coalesce(title, '')), 'A') ||
            setweight(to_tsvector('english', coalesce(body,  '')), 'D')
        ) STORED
);

CREATE INDEX article_search_gin
ON content.article
USING gin(search_vector);

SELECT
    article_id,
    title,
    ts_rank(
        search_vector,
        websearch_to_tsquery('english', 'postgres indexing')
    ) AS rank
FROM content.article
WHERE search_vector @@
      websearch_to_tsquery('english', 'postgres indexing')
ORDER BY rank DESC;

Do not build a production tsvector by simply casting arbitrary prose to tsvector; the type itself assumes lexemes are already normalized. Use to_tsvector with the correct text-search configuration to parse and normalize source text.[31][32]

25.1 tsquery constructors

SELECT plainto_tsquery('english', 'database systems');
SELECT phraseto_tsquery('english', 'database systems');
SELECT websearch_to_tsquery(
    'english',
    '"database systems" -oracle'
);

GIN is generally the preferred full-text-search index type for static/search-heavy workloads, while GiST provides an alternative with different lossy/index-size/update characteristics.[33]

26. Casts, literals, and type resolution

PostgreSQL can resolve many mixed-type expressions through implicit casts, preferred type categories, operator/function overload resolution and context. Explicit casts use either CAST(value AS type) or PostgreSQL's value::type syntax. Because implicit conversion can change operator selection and semantics, important boundaries should be typed explicitly rather than relying on ambiguous unknown string literals or accidental casts.[34][35]

SELECT
    '42'::integer,
    CAST('19.95' AS numeric(10,2)),
    '2026-09-16T15:30:00Z'::timestamptz,
    '{"active":true}'::jsonb;

26.1 Parameter typing matters

Client libraries should bind native typed parameters rather than building SQL by string interpolation. Besides security, typed binding avoids unnecessary text conversions and helps PostgreSQL select the intended function/operator overload and plan behavior.

26.2 Domains and casts

When an underlying-type value is assigned to a domain, PostgreSQL checks the domain constraints. When a domain value is passed to an operator/function defined for the underlying type, the domain can be treated as the underlying type; the resulting expression normally has the underlying type unless explicitly cast back to the domain.[25]

27. Storage, variable-length values, and TOAST

Fixed-width types such as integers and timestamps have compact inline representations. Many variable-length types—including text, bytea, arrays, JSONB, XML and composites containing wide fields—use PostgreSQL's varlena infrastructure and can participate in TOAST. PostgreSQL pages are normally 8 KiB and tuples cannot span pages, so large values can be compressed and/or moved into an associated TOAST relation transparently.[36]

heap row +-------------------------------------+ | id | small columns | TOAST pointer | +--------------------------+----------+ | v TOAST relation +-------------------+ | chunk 0 | | chunk 1 | | chunk 2 | +-------------------+

TOAST normally starts trying to shrink rows around a roughly 2 KiB threshold. Unchanged out-of-line fields are normally preserved across an update, so changing a small column does not necessarily rewrite a large TOASTed value. Column storage strategies can choose compression/out-of-line behavior for advanced workloads.[36]

27.1 Inspect per-column storage attributes

SELECT
    attname,
    atttypid::regtype AS type,
    attstorage,
    attcompression
FROM pg_attribute
WHERE attrelid = 'app.event'::regclass
  AND attnum > 0
  AND NOT attisdropped
ORDER BY attnum;

28.1 Model semantics before storage size

The smallest physical type is not automatically the best type. A two-byte integer can save space, but an overflow migration can be far more expensive. Conversely, numeric should not replace every integer/float merely because its range is large; exact arbitrary-precision arithmetic consumes more CPU/storage than fixed-width types.

28.2 Prefer semantic types over encoded text

Use date instead of 'YYYY-MM-DD' text, inet instead of IP strings, uuid instead of UUID-shaped text, and ranges instead of hand-parsed "start-end" strings. Native types validate input and expose correct comparison/operator/index semantics.

28.3 Separate identifier representation from generation

bigint and uuid describe value representation; identity/sequence/UUID generation functions describe how values are created. Do not conflate the type with the generation policy.

29. Common data-type pitfalls

29.1 Using floating point for exact money

Binary floating-point is intentionally inexact. Use numeric when exact decimal arithmetic is a requirement.[3]

29.2 Choosing char(n) for performance

PostgreSQL documents no performance advantage over text/varchar; blank padding can increase storage and CPU work.[4]

29.3 Storing instants in timestamp without a zone model

A zone-free timestamp does not identify an absolute instant. Use timestamptz for events on a global timeline; if the original named zone is semantically required, store that zone identifier separately.[5]

29.4 Treating timestamptz as “timestamp plus stored zone name”

PostgreSQL stores the instant internally in UTC and displays it using the current session time zone; the original zone label is not preserved.[5]

29.5 Storing binary data in text

Text must obey the database encoding and cannot contain zero octets. bytea exists for arbitrary bytes.[7]

29.6 Defaulting every flexible attribute to JSONB

JSONB is powerful but moves some structure away from ordinary SQL constraints and can make whole-document updates contend on one row. Keep stable relational keys/invariants as typed columns where practical.[9]

29.7 Expecting JSON to equal JSONB behavior

json preserves textual details and lacks the same containment/indexing facilities; jsonb normalizes representation. Choose deliberately.[9]

29.8 Arrays as replacement for relationships

An array is one value in one row. If elements need foreign keys, per-element attributes, joins, independent updates or relational cardinality, use a child/association table.

29.9 Comparing unrelated enum types

Enums are type-safe; two enum types with the same label text are still distinct types and cannot be directly compared without an explicit conversion/operator.[20]

29.10 Using inet when only canonical networks are valid

inet permits host bits after the netmask; cidr rejects them. Use the type that matches the domain rule.[27]

29.11 Persisting ctid or other implementation identifiers as business IDs

Physical/system identifiers are not substitutes for modeled identifiers. Use application primary-key types such as bigint/uuid and keep physical tuple identity internal.

29.12 Assuming tsvector itself normalizes text

Direct input to tsvector is treated as already-normalized lexemes. Use to_tsvector to apply parser/dictionary normalization to ordinary documents.[31]

30. Production checklist

  1. Choose types from domain semantics first, storage/performance second.
  2. Use integer widths with lifetime growth in mind.
  3. Use numeric/decimal for exact decimal arithmetic.
  4. Use real/double precision only when approximation is acceptable.
  5. Prefer text or unconstrained varchar for ordinary strings.
  6. Use varchar(n) only when n is a real business rule.
  7. Avoid char(n) unless blank-padding semantics are actually desired.
  8. Use date for calendar dates and timestamptz for absolute event instants.
  9. Store a named time zone separately when the original/local scheduling zone matters.
  10. Use interval for semantic calendar/time durations, not ad hoc seconds strings.
  11. Use boolean rather than text/integer flags.
  12. Use bytea for arbitrary binary data.
  13. Use arrays for truly atomic typed collections, not relational relationships.
  14. Prefer jsonb for query/index-heavy JSON; use json when preserving original representation matters.
  15. Distinguish SQL NULL from JSON null.
  16. Use uuid as a native 128-bit type rather than varchar.
  17. Use enums for small stable vocabularies; lookup tables for rich/evolving vocabularies.
  18. Use ranges/multiranges when interval algebra is part of the domain.
  19. Use composite types for typed row structures, not as a substitute for independent entities.
  20. Use domains for reusable value-level constraints.
  21. Use inet/cidr/macaddr types for network data.
  22. Use tsvector/tsquery and a text-search configuration for full-text search.
  23. Use explicit casts at ambiguous API/type boundaries.
  24. Account for TOAST and wide-value update/read patterns when storing large JSON, text, XML, arrays, or bytea.
  25. Verify index operator-class support for specialized types before assuming an operator is indexable.
Type-design principle: a data type is executable domain semantics. It defines which values are valid, how they compare, what operators mean, how values are represented, and which indexes/functions PostgreSQL can use. Prefer the most specific native or user-defined type that faithfully represents the data rather than encoding semantics into generic text.
