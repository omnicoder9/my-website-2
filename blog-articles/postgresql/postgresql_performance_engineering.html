PostgreSQL Performance Engineering

A production-oriented guide to query and index optimization, connection management, memory and CPU tuning, disk I/O, WAL and checkpoints, autovacuum, parallel query, JIT compilation, partitioning, PgBouncer, caching, benchmarking, and load testing.

Technical article • PostgreSQL 18.6 baseline • Updated 15 September 2026 • Vancouver-style references

Abstract

PostgreSQL performance engineering is the disciplined process of identifying the resource or execution path that limits application objectives, changing one layer of the system, and validating the result under representative load. PostgreSQL provides planner and runtime instrumentation through EXPLAIN, cumulative statistics views, pg_stat_statements, WAL and I/O statistics, autovacuum progress, and server configuration parameters. These mechanisms make it possible to separate query-planning errors, lock contention, connection saturation, memory pressure, CPU saturation, temporary-file spills, storage latency, WAL pressure, checkpoint bursts, and maintenance debt rather than treating all latency as one problem.[1]-[4]

Performance tuning is workload-specific. PostgreSQL's own documentation repeatedly frames values such as memory settings, planner cost constants, checkpoint configuration, and autovacuum thresholds as parameters to be selected for the actual system rather than universal best values. Accordingly, this article emphasizes measurement, controlled experimentation, and load testing instead of fixed “magic” configuration recipes.[5]-[8]

1. Performance engineering method

A database is fast only relative to a workload and an objective. The objective might be p99 API latency, sustained transactions per second, nightly batch completion time, replica freshness, maximum hardware cost, or a combination of these. An optimization that increases throughput while making tail latency unacceptable is not an improvement for a latency-sensitive service. Begin by defining workload shape and measurable service objectives before changing configuration.[1][33]

1. Define objective | v 2. Reproduce workload | v 3. Measure bottleneck SQL / locks / CPU / RAM / I/O / WAL / checkpoints / vacuum / connections | v 4. Form one hypothesis | v 5. Change one variable | v 6. Re-run controlled test | +---- no improvement ----> revert / new hypothesis | v 7. Validate under production-shaped concurrency and duration | v 8. Monitor regression over time

1.1 Build a performance baseline

-- Workload-level query fingerprints.
SELECT
    queryid,
    calls,
    total_exec_time,
    mean_exec_time,
    rows,
    shared_blks_hit,
    shared_blks_read,
    temp_blks_read,
    temp_blks_written,
    wal_bytes,
    left(query, 220) AS query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 30;

-- Current sessions and waits.
SELECT
    pid,
    application_name,
    state,
    wait_event_type,
    wait_event,
    now() - query_start AS query_age,
    left(query, 180) AS query
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY query_start;

pg_stat_statements gives cumulative planning/execution data for normalized SQL statements and can expose block, temporary-I/O, WAL, and parallel-worker behavior. pg_stat_activity supplies current session and wait state. Taken together, they answer different questions: which statements consume resources over time, and what sessions are doing at this instant.[2][3]

Highest-leverage rule: fix unnecessary work before tuning the server to perform unnecessary work faster.

2. Query optimization

PostgreSQL's planner evaluates alternative scans, joins, aggregates, sorts, and other plan shapes using estimated row counts and costs, then chooses the lowest-cost plan according to its model. EXPLAIN shows the selected plan, while EXPLAIN ANALYZE actually executes the statement and annotates the plan with observed row counts and timing. PostgreSQL 18 also supports options including BUFFERS, WAL, SETTINGS, and MEMORY for deeper analysis.[1][9]

2.1 Start with estimated versus actual rows

EXPLAIN (
    ANALYZE,
    BUFFERS,
    WAL,
    VERBOSE,
    SETTINGS,
    MEMORY
)
SELECT
    c.id,
    c.email,
    sum(o.total) AS lifetime_value
FROM customer AS c
JOIN orders AS o
  ON o.customer_id = c.id
WHERE c.status = 'active'
  AND o.created_at >= current_date - interval '90 days'
GROUP BY c.id, c.email
ORDER BY lifetime_value DESC
LIMIT 100;

Large differences between estimated and actual row counts often indicate stale/inadequate statistics, correlated predicates the ordinary single-column statistics do not model well, or expressions for which the planner lacks useful information. Estimation errors can propagate upward and cause incorrect join-method, scan-method, memory, or parallelism choices.[9][10]

2.2 Use buffers to distinguish CPU from data access

BUFFERS reports block accesses such as shared-buffer hits and reads. A plan with enormous buffer traffic can be slow even if every block is cached because repeatedly examining millions of tuples consumes CPU and memory bandwidth. Conversely, a small number of high-latency storage reads may dominate wall-clock time. Pair plan data with pg_stat_io and operating-system/storage metrics before attributing a query to one resource.[1][3]

2.3 Avoid accidental row multiplication

-- Potentially expensive if both detail tables contain many rows
-- for each customer, because the join can multiply rows before aggregation.
SELECT c.id, sum(o.total), count(t.id)
FROM customer c
JOIN orders o  ON o.customer_id = c.id
JOIN tickets t ON t.customer_id = c.id
GROUP BY c.id;

-- Often clearer and cheaper: aggregate independently, then join.
WITH order_totals AS (
  SELECT customer_id, sum(total) AS total
  FROM orders
  GROUP BY customer_id
),
ticket_counts AS (
  SELECT customer_id, count(*) AS tickets
  FROM tickets
  GROUP BY customer_id
)
SELECT c.id, o.total, t.tickets
FROM customer c
LEFT JOIN order_totals o USING (customer_id)
LEFT JOIN ticket_counts t USING (customer_id);

The second form is not universally faster, but it illustrates a general optimization technique: reduce cardinality before combining large relations when the semantics allow it. The correct plan should always be verified with actual data and EXPLAIN ANALYZE.[1]

2.4 Beware optimization by configuration forcing

Planner method settings such as enable_seqscan and enable_nestloop are valuable diagnostic tools, but permanently disabling plan methods is usually inferior to correcting statistics, indexing, cost assumptions, or query structure. If forcing an index scan makes a query faster, the useful question is why the planner believed the other plan was cheaper.[11]

2.5 DML and EXPLAIN ANALYZE

BEGIN;

EXPLAIN (ANALYZE, BUFFERS, WAL)
UPDATE orders
SET status = 'archived'
WHERE created_at < date '2024-01-01';

ROLLBACK;

EXPLAIN ANALYZE executes data-modifying statements. PostgreSQL's documentation recommends wrapping a diagnostic DML execution in a transaction and rolling it back when the data change itself should not persist.[9]

3. Planner statistics and cardinality estimation

PostgreSQL's optimizer depends heavily on statistics collected by ANALYZE, normally invoked automatically by autovacuum. These include null fractions, distinct-value estimates, most-common values, histograms, and other information in pg_statistic. Extended statistics can describe dependencies, multi-column distinct counts, and multi-column most-common values when predicates are correlated.[10][12]

3.1 Increase statistics where estimation is poor

ALTER TABLE orders
ALTER COLUMN customer_id
SET STATISTICS 1000;

ANALYZE orders;

Increasing a column's statistics target allows ANALYZE to collect a more detailed sample for that column, at the cost of additional statistics storage and planning overhead. It should be targeted to columns where better selectivity estimates materially affect plans rather than applied indiscriminately.[12]

3.2 Extended statistics for correlated predicates

CREATE STATISTICS orders_customer_region_stats
    (dependencies, ndistinct, mcv)
ON customer_id, region
FROM orders;

ANALYZE orders;

Extended statistics help the planner estimate predicates involving multiple related columns more accurately than assuming column independence. PostgreSQL documents functional dependencies, multivariate distinct counts, and multivariate most-common-value lists for this purpose.[10]

4. Index optimization

Indexes trade write cost and storage for faster access paths. PostgreSQL supports B-tree, Hash, GiST, SP-GiST, GIN, and BRIN index access methods in core, each suited to different operators and data distributions. B-tree remains the general choice for equality and ordered range access, while GIN, GiST, SP-GiST, and BRIN support specialized search patterns and data layouts.[13]

4.1 Index the predicates and orderings you actually execute

-- Workload:
SELECT id, customer_id, total, created_at
FROM orders
WHERE customer_id = $1
ORDER BY created_at DESC
LIMIT 50;

-- Index aligned to equality filter followed by required ordering.
CREATE INDEX orders_customer_created_idx
ON orders (customer_id, created_at DESC);

Multicolumn B-tree indexes are most effective when constraints apply to the leading columns. PostgreSQL can use later columns too, including through skip-scan optimizations in appropriate cases, but column order still affects how much of the index must be scanned.[14]

4.2 Covering indexes and index-only scans

CREATE INDEX orders_customer_created_cover_idx
ON orders (customer_id, created_at DESC)
INCLUDE (total, status);

INCLUDE columns can make required output values available directly from the index without changing the index's search key. PostgreSQL can perform index-only scans when the index contains all required columns and the visibility map shows that heap visibility checks can be skipped for the relevant pages. Index-only behavior therefore also depends on vacuum maintaining visibility-map information.[15]

4.3 Partial indexes

CREATE INDEX orders_open_customer_idx
ON orders (customer_id, created_at DESC)
WHERE status IN ('pending', 'processing');

A partial index stores entries only for rows satisfying its predicate. It can be smaller and cheaper to maintain when queries consistently target a selective subset, but the planner can use it only when the query predicate logically implies the index predicate.[16]

4.4 Expression indexes

CREATE UNIQUE INDEX customer_email_ci_uq
ON customer (lower(email));

Expression indexes precompute indexed expressions, allowing predicates on those expressions to use an index. They make writes more expensive because PostgreSQL must maintain the computed index entry when indexed data changes.[17]

4.5 Find large low-use index candidates

SELECT
    s.schemaname,
    s.relname,
    s.indexrelname,
    s.idx_scan,
    pg_size_pretty(pg_relation_size(s.indexrelid)) AS index_size,
    i.indisunique,
    i.indisprimary
FROM pg_stat_user_indexes AS s
JOIN pg_index AS i
  ON i.indexrelid = s.indexrelid
ORDER BY s.idx_scan ASC, pg_relation_size(s.indexrelid) DESC;
Do not drop an index from idx_scan = 0 alone. Statistics may have been reset, periodic workloads may be absent from the observation window, and uniqueness/constraint or rare incident-response queries may justify the index.

4.6 Write amplification

Every index that covers a modified row may require index maintenance. Excess or redundant indexes can therefore reduce insert/update throughput, increase WAL generation, enlarge backups, and add vacuum work. Performance engineering should evaluate the total index portfolio, not just whether each individual read query could be made faster by adding another index.[13][2]

5. Connection management

PostgreSQL uses a process-per-session architecture for ordinary client connections. max_connections determines the maximum concurrent connection count and affects allocation of server resources. Raising the limit can increase process and memory overhead and does not increase the amount of useful concurrent work the CPU and storage can sustain.[18]

5.1 Measure states, not only totals

SELECT
    count(*) AS total,
    count(*) FILTER (WHERE state = 'active') AS active,
    count(*) FILTER (WHERE state = 'idle') AS idle,
    count(*) FILTER (WHERE state = 'idle in transaction') AS idle_in_tx,
    count(*) FILTER (WHERE wait_event_type IS NOT NULL) AS waiting
FROM pg_stat_activity
WHERE backend_type = 'client backend';

A large number of idle sessions usually represents connection-management overhead rather than database throughput. A large number of simultaneously active sessions can create CPU scheduling and lock/I/O contention. The useful concurrency level is workload- and hardware-dependent, so application pools should bound concurrency rather than mirroring thread counts or request counts one-for-one.[3][18]

5.2 Protect against idle transactions

ALTER ROLE orders_app
SET idle_in_transaction_session_timeout = '60s';

ALTER ROLE orders_app
SET statement_timeout = '30s';

idle_in_transaction_session_timeout can terminate sessions that sit idle while holding an open transaction. Such sessions can retain locks and old snapshots and impede vacuum cleanup. Timeouts should be matched to the workload rather than applied blindly to legitimately long-running operations.[19]

6. Memory tuning

PostgreSQL memory tuning requires distinguishing shared memory from per-operation memory. shared_buffers is the server's shared page cache. work_mem is a base memory limit used independently by sort and hash operations, and a query can contain multiple such operations. Parallel workers can multiply that consumption. maintenance_work_mem applies to maintenance operations such as VACUUM and index creation, while autovacuum can use separate autovacuum_work_mem.[5]

6.1 shared_buffers

PostgreSQL's documentation suggests roughly 25% of system memory as a reasonable starting point for shared_buffers on a dedicated database server with at least 1 GB RAM, while noting that values much beyond roughly 40% are unlikely to outperform a smaller setting in many cases because PostgreSQL also depends on the operating system cache. These are starting points, not targets.[5]

6.2 work_mem is not “per connection”

SHOW work_mem;
SHOW hash_mem_multiplier;

EXPLAIN (ANALYZE, BUFFERS)
SELECT customer_id, sum(total)
FROM orders
GROUP BY customer_id
ORDER BY sum(total) DESC;

A single query can use multiple sort or hash nodes and can execute them concurrently. Hash operations can use work_mem × hash_mem_multiplier. Consequently, setting work_mem to a large fraction of RAM can cause memory exhaustion under concurrency even if no individual query looks excessive.[5]

6.3 Detect temporary spills

SELECT
    datname,
    temp_files,
    pg_size_pretty(temp_bytes) AS temp_bytes
FROM pg_stat_database
WHERE datname IS NOT NULL
ORDER BY temp_bytes DESC;
# Optional diagnostic logging.
log_temp_files = '64MB'

Temporary-file creation can indicate sorts, hashes, or other operations exceeding available memory. Increasing work_mem can help some statements, but query/index improvements can often eliminate much more work. Per-role or per-session values are safer than raising a global value for one analytical query class.[5][20]

6.4 Effective cache size

effective_cache_size does not allocate memory. It is a planner estimate of how much disk cache is likely to be available to one query, accounting for PostgreSQL and operating-system caching and sharing among concurrent queries. Higher estimates can make index scans appear cheaper; lower values can favor sequential scans.[11]

7. CPU utilization

PostgreSQL can use multiple CPU cores through concurrent backend processes and, for eligible queries, parallel workers. CPU saturation can come from efficient high throughput, poorly selective scans, excessive expression evaluation, sorting/hashing, contention-induced spinning, query planning, JIT compilation, or large numbers of runnable sessions. CPU percentage alone is therefore not a diagnosis.[3][21]

7.1 Find CPU-heavy query fingerprints

PostgreSQL does not directly assign host CPU time to each SQL statement in pg_stat_statements. However, high total_exec_time combined with low physical I/O and low wait evidence often identifies CPU-intensive SQL. Application/OS profilers and process metrics can confirm the hypothesis.

SELECT
    queryid,
    calls,
    total_exec_time,
    mean_exec_time,
    shared_blks_hit,
    shared_blks_read,
    temp_blks_written,
    left(query, 200) AS query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 25;

7.2 Reduce rows before expensive operations

CPU cost is often proportional to tuples processed rather than tuples returned. Applying selective predicates earlier, improving indexes, avoiding accidental join multiplication, and pre-aggregating where semantically valid can reduce CPU more effectively than adding cores.

8. Disk I/O

PostgreSQL 18 exposes cluster I/O activity through pg_stat_io, including reads, writes, writebacks, extends, fsyncs, byte counters, timing, and eviction/reuse information by backend type, object, and context. I/O timing requires the corresponding timing settings where applicable and can have platform-dependent overhead.[3]

8.1 Inspect I/O by context

SELECT
    backend_type,
    object,
    context,
    reads,
    read_bytes,
    read_time,
    writes,
    write_bytes,
    write_time,
    fsyncs,
    fsync_time,
    evictions,
    reuses
FROM pg_stat_io
ORDER BY
    coalesce(read_time,0)
  + coalesce(write_time,0)
  + coalesce(fsync_time,0) DESC;

8.2 Cache hit ratio is not disk hit ratio

SELECT
    datname,
    round(
        100.0 * blks_hit
        / NULLIF(blks_hit + blks_read, 0),
        2
    ) AS shared_buffer_hit_pct
FROM pg_stat_database
WHERE datname IS NOT NULL;

blks_hit measures hits in PostgreSQL's shared buffer cache, not the operating system page cache. A shared-buffer miss may still be served from RAM by the operating system. Treat the ratio as one database-cache signal and correlate it with I/O latency and storage telemetry.[3]

8.3 Storage benchmark versus database benchmark

A raw storage benchmark measures characteristics of the storage subsystem, while a PostgreSQL workload includes WAL, buffer management, locks, visibility checks, planning, transaction control, and data access. Storage microbenchmarks are useful for isolating device behavior, but capacity decisions should be validated with the actual database workload.[33]

9. WAL tuning

Write-ahead logging is the foundation of PostgreSQL crash recovery. WAL records describing page changes must be durable before the corresponding changed data pages can be safely written. Performance tuning must therefore preserve durability requirements unless the workload explicitly accepts weaker guarantees.[22][23]

9.1 Observe WAL first

SELECT
    wal_records,
    wal_fpi,
    pg_size_pretty(wal_bytes) AS wal_bytes,
    wal_buffers_full,
    wal_write,
    wal_sync,
    wal_write_time,
    wal_sync_time,
    stats_reset
FROM pg_stat_wal;

9.2 WAL volume by query

SELECT
    queryid,
    calls,
    pg_size_pretty(wal_bytes::bigint) AS wal_generated,
    left(query, 220) AS query
FROM pg_stat_statements
WHERE wal_bytes > 0
ORDER BY wal_bytes DESC
LIMIT 25;

9.3 WAL compression

wal_compression can compress full-page images using supported methods such as pglz, lz4, or zstd when PostgreSQL was built with the relevant libraries. PostgreSQL documents the tradeoff explicitly: compression can reduce WAL volume without reducing durability, but consumes additional CPU during WAL generation and replay.[23] 

# Example candidate for a write-heavy workload after measurement.
wal_compression = zstd

9.4 synchronous_commit

Changing synchronous_commit changes transaction durability/latency semantics rather than merely “making WAL faster.” PostgreSQL documents that turning it off can allow recently committed transactions to be lost after an operating-system crash, although it does not create the same database-corruption risk as disabling fsync. Any use of weaker commit durability must be a business-level durability decision, not a hidden tuning trick.[24]

Do not disable fsync or full_page_writes as routine production tuning. PostgreSQL documents these as non-durable settings for environments that explicitly accept the associated crash risks.[24]

10. Checkpoint tuning

A checkpoint ensures that dirty data pages are written such that recovery can begin from a known WAL position. Too-frequent checkpoints increase write pressure and full-page-image generation; very infrequent checkpoints can increase crash-recovery time and WAL-space requirements. PostgreSQL 18 schedules checkpoints based on checkpoint_timeout and WAL growth relative to max_wal_size.[23][25]

10.1 Important settings

SettingPostgreSQL 18 defaultEngineering effect
checkpoint_timeout5 minUpper time interval between automatic checkpoints; increasing can lengthen crash recovery.[23]
checkpoint_completion_target0.9Spreads checkpoint work over most of the checkpoint interval to smooth I/O.[23]
max_wal_size1 GBSoft WAL-size trigger for automatic checkpoints; increasing can reduce checkpoint frequency but lengthen recovery.[23]
min_wal_size80 MBControls how much WAL is kept for recycling during ordinary operation.[23]

10.2 Observe checkpoint behavior

SELECT *
FROM pg_stat_checkpointer;

If checkpoints are repeatedly triggered by WAL accumulation rather than the timeout, checkpoint_warning can log warnings suggesting that max_wal_size may be too small. Increasing shared_buffers can also justify increasing max_wal_size so dirty-page writeback can be spread over a longer interval.[5][23]

10.3 Example tuning experiment

# Example only; benchmark before/after with production-shaped load.
checkpoint_timeout = '15min'
max_wal_size = '16GB'
min_wal_size = '4GB'
checkpoint_completion_target = 0.9

This configuration is not a recommended universal baseline. Its suitability depends on write rate, available WAL disk space, crash-recovery objective, replication/archive behavior, and storage throughput.

11. Autovacuum tuning

Vacuum is required to reuse space left by updated/deleted tuples, update planner statistics, maintain the visibility map, and prevent transaction-ID/multixact wraparound. Autovacuum automates this work and should normally remain enabled. Standard VACUUM operates concurrently with ordinary reads/writes, whereas VACUUM FULL rewrites the table and takes an ACCESS EXCLUSIVE lock.[7]

11.1 Trigger formula

For ordinary update/delete-driven vacuuming, PostgreSQL describes the trigger as the minimum of a maximum threshold and the base threshold plus scale factor times estimated table tuples. PostgreSQL 18's default autovacuum_vacuum_scale_factor is 0.2, and its default maximum threshold is 100,000,000 tuples. Per-table storage parameters can override these values.[7][26]

11.2 Large hot table tuning

ALTER TABLE orders SET (
    autovacuum_vacuum_threshold = 10000,
    autovacuum_vacuum_scale_factor = 0.02,
    autovacuum_analyze_threshold = 5000,
    autovacuum_analyze_scale_factor = 0.01
);

These example values are intentionally illustrative. High-churn large tables often benefit from more frequent per-table vacuum/analyze than the cluster defaults, while small/static tables may not. Validate effectiveness using dead-tuple trends, vacuum duration, table/index growth, planner estimates, and I/O impact.[7][26]

11.3 Find maintenance lag

SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    n_mod_since_analyze,
    last_autovacuum,
    last_autoanalyze,
    autovacuum_count,
    autoanalyze_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 40;

11.4 Monitor vacuum progress

SELECT *
FROM pg_stat_progress_vacuum;

11.5 Cost-based throttling

PostgreSQL includes cost-based vacuum delay controls so maintenance can limit its resource impact. Making autovacuum excessively slow can allow dead tuples and visibility debt to accumulate; making it too aggressive can compete with foreground workload. Tune the cost settings and worker count using observed maintenance backlog and spare I/O capacity rather than simply maximizing workers.[26]

12. Parallel query

PostgreSQL can execute eligible plan fragments with multiple worker processes. Parallel plans contain a Gather or Gather Merge node. Gather collects rows without preserving worker ordering; Gather Merge merges sorted streams while preserving order. Parallel scans, joins, aggregates, and appends can reduce elapsed time when enough work exists to amortize worker startup and tuple-transfer overhead.[21][27]

12.1 Observe per-worker execution

EXPLAIN (ANALYZE, VERBOSE, BUFFERS)
SELECT
    customer_id,
    sum(total)
FROM orders
WHERE created_at >= current_date - interval '1 year'
GROUP BY customer_id;

PostgreSQL recommends EXPLAIN (ANALYZE, VERBOSE) to see per-worker statistics and judge whether work is evenly distributed.[27]

12.2 Worker limits

SHOW max_worker_processes;
SHOW max_parallel_workers;
SHOW max_parallel_workers_per_gather;

A plan can request workers that are unavailable at execution time because parallel workers come from finite server-wide pools. A plan intended to run with several workers can therefore execute with fewer workers or none, which is one reason benchmark results must include realistic concurrent load rather than isolated single-query tests.[21]

12.3 Parallelism is resource multiplication

Parallelism can reduce latency while increasing instantaneous CPU, memory, and I/O consumption. PostgreSQL notes that per-operation memory may be applied independently in workers, so a parallel query can consume substantially more aggregate memory than its serial equivalent.[5]

12.4 Do not force parallelism blindly

Planner settings such as parallel_setup_cost and parallel_tuple_cost influence whether parallel plans are selected. PostgreSQL's documentation notes that lowering them can be useful diagnostically if an expected parallel plan is not chosen, but the resulting plan can still be slower than the serial plan the optimizer originally preferred.[27]

13. JIT compilation

PostgreSQL can use LLVM-based just-in-time compilation for expression evaluation and tuple deforming when PostgreSQL was built with JIT support. JIT has compilation overhead, so it is primarily beneficial for long-running CPU-bound queries—often analytical queries—where the saved execution time outweighs code-generation cost.[28]

13.1 Cost thresholds

PostgreSQL decides at plan time whether estimated query cost exceeds jit_above_cost, and uses additional thresholds for inlining and expensive JIT optimization. Prepared statements using generic plans inherit these decisions from the settings effective when the plan was prepared.[28] 

SHOW jit;
SHOW jit_above_cost;
SHOW jit_inline_above_cost;
SHOW jit_optimize_above_cost;

EXPLAIN (ANALYZE, BUFFERS)
SELECT
    customer_id,
    sum(total * tax_rate)
FROM large_order_fact
GROUP BY customer_id;

13.2 OLTP versus analytical workloads

For short OLTP queries, JIT compilation overhead can exceed the time saved. For longer scans and aggregation-heavy CPU workloads, JIT may improve runtime. Test with identical warmed/cold-cache conditions and sufficient repetitions to separate compilation effects from ordinary run-to-run variation.[28]

14. Partitioning

Declarative partitioning divides one logical table into smaller physical relations using range, list, or hash partitioning. Partition pruning can eliminate irrelevant partitions during planning and execution. PostgreSQL documents performance benefits when heavily accessed rows fall into a small number of partitions or when retention/maintenance can operate on partitions rather than row-by-row across one very large table.[29]

14.1 Time-range example

CREATE TABLE events (
    event_id    bigint GENERATED ALWAYS AS IDENTITY,
    occurred_at timestamptz NOT NULL,
    tenant_id   bigint NOT NULL,
    payload     jsonb NOT NULL,
    PRIMARY KEY (occurred_at, event_id)
) PARTITION BY RANGE (occurred_at);

CREATE TABLE events_2026_09
PARTITION OF events
FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');

CREATE TABLE events_2026_10
PARTITION OF events
FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');

14.2 Pruning

EXPLAIN
SELECT *
FROM events
WHERE occurred_at >= timestamptz '2026-09-10'
  AND occurred_at <  timestamptz '2026-09-11';

Partitioning helps only when the partition key aligns with access and lifecycle patterns. PostgreSQL warns that excessive partition counts can increase planning time and per-session memory usage, especially when queries fail to prune most partitions. More partitions are not inherently better.[29]

14.3 Retention without mass DELETE

ALTER TABLE events
DETACH PARTITION events_2025_09;

DROP TABLE events_2025_09;

Partition detach/drop can make time-based retention substantially cheaper than deleting millions of old rows individually, and it can reduce vacuum/WAL work associated with such deletion patterns.[29]

Partitioning is not sharding. Native PostgreSQL partitioning organizes relations inside one PostgreSQL cluster; it does not create independent write servers.

15. Connection pooling

A connection pool separates application concurrency from PostgreSQL session count. This reduces connection setup overhead and, more importantly, places a hard limit on simultaneous database backends. Pool sizing should be based on the concurrency PostgreSQL can process efficiently, multiplied across application instances, not on the maximum number of application requests that can exist at once.[18]

15.1 Queueing is preferable to uncontrolled saturation

1000 application requests | v application pool / PgBouncer max 40 PostgreSQL sessions | +---- 40 executing or waiting in PostgreSQL | +---- remaining callers queue with bounded timeout

If 1000 callers each open a direct PostgreSQL connection, the server must schedule and maintain all of them even if the CPU can execute only a small subset usefully. A bounded pool converts uncontrolled database concurrency into an explicit queue with measurable checkout latency.

15.2 Monitor both sides

Database connection count by itself does not reveal pool saturation. Track application pool active/idle/waiting counts and checkout latency together with PostgreSQL session states. A database may appear to have a stable session count while callers are timing out in a saturated pool.

16. PgBouncer

PgBouncer is a lightweight external connection pooler for PostgreSQL. It accepts client connections and multiplexes them onto a smaller set of server connections. PgBouncer supports session, transaction, and statement pooling modes, which differ in when a PostgreSQL server connection is released for reuse.[30]

16.1 Pool modes

ModeServer connection releasedImplication
sessionWhen the client disconnectsHighest session-semantic compatibility; less multiplexing.
transactionAfter the transaction finishesStrong multiplexing; session-scoped state needs careful review.
statementAfter each queryMulti-statement transactions are disallowed.

PgBouncer's current configuration documentation lists session pooling as the default. Transaction pooling is commonly used to reduce PostgreSQL backend counts for stateless application traffic, but any feature relying on a stable server session must be evaluated against transaction-pool semantics.[30]

16.2 Example configuration

[databases]
appdb = host=postgres-primary.internal port=5432 dbname=appdb

[pgbouncer]
listen_addr = 0.0.0.0
listen_port = 6432

pool_mode = transaction

max_client_conn = 2000
default_pool_size = 50
reserve_pool_size = 10
reserve_pool_timeout = 2

max_db_connections = 120

auth_type = scram-sha-256
auth_file = /etc/pgbouncer/userlist.txt

server_reset_query = DISCARD ALL
ignore_startup_parameters = extra_float_digits

PgBouncer documents max_client_conn as the client-side limit and default_pool_size as the default maximum server connections per user/database pair. File-descriptor requirements can exceed max_client_conn because PgBouncer also holds server connections.[30]

16.3 Prepared statements in transaction pooling

Modern PgBouncer can track protocol-level named prepared statements in transaction and statement pooling when max_prepared_statements is non-zero. PgBouncer rewrites prepared-statement names and ensures the required statement is prepared on whichever server connection is assigned. SQL-level PREPARE/EXECUTE commands are not handled by that mechanism in the same way. The current documented default for max_prepared_statements is 200.[30]

16.4 Watch PgBouncer itself

-- Connect to PgBouncer's administrative database, then:
SHOW POOLS;
SHOW STATS;
SHOW CLIENTS;
SHOW SERVERS;

A database performance incident can originate in the pooler: client queues, pool exhaustion, authentication latency, server connection creation, or a too-small pool can all increase application latency while PostgreSQL itself appears underutilized.

17. Caching

PostgreSQL has a shared buffer cache and also benefits from the operating system's filesystem cache. Application-level caches add a separate semantic cache that can avoid database execution entirely. These layers should be considered independently because a database page cache stores physical data pages, while an application cache stores query results or domain objects with application-defined freshness semantics.[5][31]

17.1 Observe shared-buffer contents

CREATE EXTENSION IF NOT EXISTS pg_buffercache;

SELECT
    c.relname,
    count(*) AS buffers,
    pg_size_pretty(
      count(*) * current_setting('block_size')::int::bigint
    ) AS cached
FROM pg_buffercache AS b
JOIN pg_class AS c
  ON c.relfilenode = b.relfilenode
GROUP BY c.relname
ORDER BY buffers DESC
LIMIT 30;

The supplied pg_buffercache extension provides real-time information about shared-buffer occupancy. It is intended for operational inspection and does not include the operating-system cache.[31]

17.2 Prewarming

CREATE EXTENSION IF NOT EXISTS pg_prewarm;

SELECT pg_prewarm(
    'orders',
    mode => 'buffer'
);

The supplied pg_prewarm module can load relation blocks into the operating-system cache or PostgreSQL buffers. Prewarming can reduce cold-start latency for a known working set but consumes I/O and can evict other useful data, so it should be used intentionally.[32]

17.3 Application cache-aside

function getProduct(productId):
    key = "product:" + productId

    value = cache.get(key)
    if value exists:
        return value

    value = db.query(
        "SELECT id, name, price, version FROM product WHERE id = $1",
        productId
    )

    cache.set(key, value, ttl = 60 seconds)
    return value

An application cache reduces database work only at the cost of a freshness policy. TTL caching permits bounded staleness; explicit invalidation creates coordination between the database transaction and the cache. Cache invalidation and failure behavior must therefore be designed as part of correctness, not only performance.

18. Benchmarking

PostgreSQL ships pgbench, a benchmark client that executes SQL transaction scripts with configurable client concurrency, worker threads, duration, protocol mode, request rate, retries, and latency reporting. Its built-in workload is loosely based on TPC-B, but custom scripts are the more useful mode for application performance engineering.[33]

18.1 Initialize the built-in dataset

createdb perf_lab

pgbench -i \
  --scale=100 \
  perf_lab

18.2 Basic saturation benchmark

pgbench \
  --client=64 \
  --jobs=8 \
  --time=300 \
  --progress=5 \
  --report-per-command \
  --protocol=prepared \
  perf_lab

--protocol=prepared uses the extended query protocol with prepared statements and reuses parse analysis after the first iteration. pgbench reports processed and failed transactions, latency, connection setup time, and TPS; --report-per-command adds per-command latency/failure statistics.[33]

18.3 Custom application-shaped script

\set tenant_id random(1, 10000)
\set amount random(100, 25000)

BEGIN;

SELECT balance
FROM account
WHERE tenant_id = :tenant_id
  AND account_id = 1
FOR UPDATE;

UPDATE account
SET balance = balance - :amount
WHERE tenant_id = :tenant_id
  AND account_id = 1;

INSERT INTO ledger(tenant_id, account_id, amount, created_at)
VALUES (:tenant_id, 1, -:amount, clock_timestamp());

COMMIT;
pgbench \
  --file=transfer.sql \
  --client=100 \
  --jobs=8 \
  --time=600 \
  --protocol=prepared \
  --progress=10 \
  appdb

18.4 Control the test environment

  • Use production-like data volume and data distribution.
  • Match indexes, constraints, extensions, PostgreSQL parameters, and storage.
  • Separate client-generator capacity from database capacity.
  • Record CPU, RAM, I/O latency, WAL, checkpoints, vacuum, connections, and query metrics during the run.
  • Repeat runs and report variation rather than one best number.
  • Distinguish cold-cache, warm-cache, and steady-state tests.

18.5 TPS is not enough

A high TPS number can hide unacceptable tail latency or failed transactions. pgbench reports average latency and standard deviation and can log transactions for deeper percentile analysis. A benchmark should report throughput, latency distribution, errors/retries, saturation metrics, and resource use together.[33]

19. Load testing

A saturation benchmark asks “how fast can this system go?” A load test asks “what happens at the workload rate the application expects?” pgbench supports rate-limited execution with --rate, scheduling transaction starts on a Poisson-distributed timeline rather than simply starting the next transaction as soon as the previous one ends. This makes it useful for open-loop-style arrival-rate testing.[33]

19.1 Arrival-rate test

pgbench \
  --file=app_workload.sql \
  --client=200 \
  --jobs=16 \
  --time=900 \
  --rate=2500 \
  --latency-limit=100 \
  --progress=5 \
  --log \
  appdb

With --rate, pgbench reports schedule lag as clients fall behind the requested arrival rate. If --latency-limit is also set, transactions already too far behind schedule to meet the limit can be skipped rather than submitted, making overload visible rather than hiding it in an ever-growing queue.[33]

19.2 Test a concurrency curve

for c in 1 2 4 8 16 32 64 128 256; do
  echo "=== clients=$c ==="
  pgbench \
    --file=app_workload.sql \
    --client="$c" \
    --jobs=8 \
    --time=120 \
    --protocol=prepared \
    appdb
done

Plot throughput and p50/p95/p99 latency against concurrency. Healthy systems normally reach a region where additional concurrency no longer increases useful throughput and instead increases queueing, lock contention, CPU scheduling, or I/O wait. That “knee” is often a better input for connection-pool sizing than max_connections.

19.3 Soak tests

Short tests can miss vacuum lag, checkpoint patterns, WAL retention, cache churn, connection leaks, table/index growth, memory fragmentation, and thermal/credit throttling in infrastructure. Run long-duration soak tests when validating sustained production capacity, and observe maintenance behavior rather than disabling it for the benchmark.

19.4 Serialization/deadlock retries

pgbench can retry transactions that fail due to serialization anomalies or deadlocks using --max-tries; the default is one try, so retries are disabled unless explicitly configured. If a benchmark is intended to model an application that performs retries, configure pgbench accordingly and report both retried transactions and final failures.[33] 

pgbench \
  --file=serializable_workload.sql \
  --time=300 \
  --client=64 \
  --max-tries=5 \
  --failures-detailed \
  appdb

20. Integrated tuning workflow

20.1 Scenario: p99 latency rises under peak load

  1. Check application pool saturation. Is connection checkout latency rising?
  2. Inspect PostgreSQL waits. Are active sessions CPU-running, lock-waiting, I/O-waiting, or client-waiting?
  3. Inspect pg_stat_statements. Did one query class become dominant?
  4. Compare plan estimates with actual rows. Correct statistics/indexes before tuning global settings.
  5. Inspect temp I/O. Determine whether sorts/hashes spill.
  6. Inspect pg_stat_io. Determine which backend/object/context is creating I/O.
  7. Inspect WAL/checkpoints. Determine whether write bursts correspond to WAL sync or checkpoint pressure.
  8. Inspect dead tuples/autovacuum. Determine whether maintenance debt has inflated table/index work.
  9. Test one change. Re-run the same arrival-rate load and compare latency distribution and resource use.

20.2 Compact diagnostic pack

-- Sessions and waits.
SELECT pid, application_name, state, wait_event_type, wait_event,
       now()-query_start AS age, left(query,160)
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY query_start;

-- Top SQL.
SELECT calls, total_exec_time, mean_exec_time,
       shared_blks_read, temp_blks_written, wal_bytes,
       left(query,160)
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;

-- I/O.
SELECT backend_type, object, context,
       reads, read_bytes, read_time,
       writes, write_bytes, write_time,
       fsyncs, fsync_time
FROM pg_stat_io;

-- WAL.
SELECT * FROM pg_stat_wal;

-- Checkpoints.
SELECT * FROM pg_stat_checkpointer;

-- Vacuum debt.
SELECT schemaname, relname, n_live_tup, n_dead_tup,
       last_autovacuum, last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 30;

20.3 Performance anti-patterns

Anti-patternWhy it failsBetter approach
Raise max_connections whenever clients queueMoves queueing into PostgreSQL and increases backend/memory/scheduling pressureBound concurrency with pools/PgBouncer and size from measured knee
Set huge global work_memApplied to multiple operations and workers concurrentlyUse conservative global setting; raise per workload/session when justified
Add every possible indexIncreases writes, WAL, storage, vacuum and cache footprintDesign indexes from measured access paths and remove proven redundancy
Disable durability to fix write latencyChanges failure guarantees rather than solving root causeMeasure WAL sync/storage/checkpoints; weaken durability only by explicit requirement
Run VACUUM FULL as routine maintenanceRewrites table and takes ACCESS EXCLUSIVE lockTune autovacuum and use ordinary vacuum as normal mechanism
Partition every large table into thousands of partitionsAdds planning and metadata overhead if pruning is ineffectivePartition only around access/lifecycle boundaries
Benchmark only maximum TPSCan hide tail latency, failures, retries and overload queueingReport latency distribution, failures, saturation and resource usage

20.4 Final checklist

  1. Query plans: estimated and actual rows are reasonably aligned.
  2. Indexes: important predicates/orderings have appropriate indexes; write cost is understood.
  3. Connections: database concurrency is bounded and pool queueing is observable.
  4. Memory: global and per-operation settings fit peak concurrency.
  5. CPU: expensive SQL and parallelism are measured, not inferred.
  6. I/O: storage latency, temp spills, cache behavior, and PostgreSQL I/O context are visible.
  7. WAL: WAL volume and sync latency are monitored; durability tradeoffs are explicit.
  8. Checkpoints: checkpoints do not create avoidable I/O spikes and recovery objectives are preserved.
  9. Autovacuum: hot tables do not accumulate dead tuples or stale statistics faster than maintenance can keep up.
  10. JIT: enabled/disabled based on measured analytical/OLTP behavior.
  11. Partitioning: pruning and lifecycle benefits outweigh planning/metadata cost.
  12. Benchmarking: tests use production-shaped data, concurrency, transactions, and duration.
  13. Load testing: target arrival rates and latency objectives are tested before production peaks.
Performance engineering principle: optimize the path that dominates end-to-end latency or capacity, validate the change under controlled representative load, and preserve correctness and durability unless the requirements explicitly permit a tradeoff.
