1 The question

Every change to a running system is a claim that nothing short of production can settle. Staging environments do not carry production's inputs, its data, its scale, its neighbours or its odd clients, and so every release is observed for the first time by somebody. The engineering of deployment is, underneath its vocabulary of colours and birds, a set of rules for deciding who that somebody is, how much of them there is, what is learned from them, and how quickly the system can be put back if what is learned is bad.

The move that organises the last twenty years of practice is the separation of two acts that used to be one. To deploy is to install a version where it could run. To release is to let requests reach it 1,2. Once those are separate, the space between them can be filled with evidence: synthetic tests on an idle environment, copies of live requests whose answers nobody sees, a small share of real users compared against the rest. Each named pattern in this article is a particular way of filling that space, and each pays for its evidence in a particular currency.

The organising question is therefore not which pattern is safest but whose requests pay for the evidence. A canary spends a few real users' failures to learn whether the new version fails more often. Shadow traffic spends machine time and engineering effort instead, and learns nothing about anything a discarded response cannot show. Blue-green spends almost no evidence at all and buys a fast way back. A rolling update spends whatever the load balancer happens to hand it and gathers no verdict of its own.

The lab that accompanies the article turns the question into arithmetic, and its first result sets the tone. To detect that a new version has doubled the error rate, at the conventional 5% false-alarm rate and 80% power, a canary must accumulate about 8.0 excess failed requests, and that number barely moves whether the service fails one request in a hundred or one in ten thousand, and whether the canary takes one percent of traffic or a tenth of one percent (L1). The traffic split does not set the price of the verdict. It sets the clock. Small canaries are not safer than large ones; they are slower.

That result reframes the oldest image in the field. When John Scott Haldane recommended small animals to mine rescuers in the 1890s, the point was that a canary is more sensitive to carbon monoxide than a miner, so it collapses first 3; British pits used them until 1986 4. A software canary is not a more sensitive animal. It is the same animal as the fleet, running the same code on the same kind of traffic, and it only gives warning if the difference it shows can be told apart from chance. The metaphor quietly borrows an amplifier the practice does not have.

The article proceeds in five families of pattern, twenty-five plates in all, each read against the same fixed fields and drawn with the same small gauge. Eight experiments in a stdlib-only Python lab supply every number; their source and verbatim output close the article.

2 A short history

Systems that could not stop were the first to separate installing from switching. Erlang, built at Ericsson for telephone switches, loads a new version of a module beside the old one; calls already running finish on the old code, fully qualified calls enter the new, and the runtime keeps no more than two versions resident 5,6. OTP release handling adds explicit conversion of in-memory state during an upgrade 7. The web server nginx does the same for its whole executable: a signal starts a new master process beside the old one, and the old one can be told to resume if the new one misbehaves 8.

The web of the early 2000s mostly did not bother. Deploys were rare, scheduled and total: stop, replace, start, inside a maintenance window. Blue-green arrived as a response to the cut-over problem in that world. Fowler credits the name to Daniel Terhorst-North and Jez Humble at ThoughtWorks and describes it as a technique that had been around for a long time and was underused; Humble and Farley's Continuous Delivery made it canonical in 2010 9,2.

Frequency changed the problem. Flickr's 2009 talk on ten deploys a day recast deployment as a routine act rather than an event 10, and at that cadence a technique whose main virtue is a fast way back is no longer enough, because a team deploying ten times a day wants to learn from production, not merely survive it. Facebook had already launched Chat in 2008 after a period in which live pages generated chat traffic against the new servers without showing anything to users, a dark launch 11. Canary release was written down as a named pattern in 2014 12, the same year as the parallel-change recipe for splitting schema changes into reversible steps 13.

Two industrial threads then converged. One treated configuration as code: Facebook's Configerator put configuration through review and a canary before a full push 14, and its mobile pipeline staged binaries through internal and external tiers 15,16. The other treated infrastructure as disposable: servers rebuilt from images rather than patched, so that the way back is a previous artefact rather than an act of repair 17,18. Kubernetes gave that second thread its default strategy, the rolling update, which is still one of only two strategies a Deployment offers natively 19.

The years around 2018 turned judgement into software. Google's site reliability books devoted a chapter to canarying 20,21, and Davidovič and Beyer described Google's canary analysis service 22. Netflix and Google released Kayenta, a statistical judge that plugs into the Spinnaker delivery platform and scores a canary against a fresh baseline 23,24. RedMonk's James Governor gave the family its umbrella name, progressive delivery 25. Controllers such as Argo Rollouts and Flagger brought the same loop into Kubernetes 26,27, and the clouds exposed weights as ordinary settings: weighted target groups on load balancers, weighted aliases on functions, canary and linear presets in deployment services 28,29,30, and eventually blue-green switchover for managed databases 31.

The hyperscalers meanwhile wrote down their internal practice: one box, then waves with bake times and automatic rollback 32; canary regions, pilots and paired regions never updated together 33; cells as the unit of both failure and deployment 34; shuffle sharding to make any one failure touch few customers 35. Service meshes made copying live traffic cheap 36,37, and in 2025 the Kubernetes Gateway API promoted percentage-based request mirroring to its standard channel 38.

The incidents of the period push in one direction. Knight Capital lost $461.1 million in 2012 after a deploy reached seven of eight servers 39,40. Cloudflare in 2019, CrowdStrike in 2024, Google Cloud and Cloudflare again in 2025 all broke on changes that were configuration, content or data rather than code, pushed on channels that did not run the ladder the code pipeline ran 41,42,43,44. The frontier of the field has moved from how to deploy code to the recognition that every channel that changes production is a deployment. DORA's research programme, which measures delivery throughput and instability together 45, reported in 2025 that AI adoption now goes with higher throughput and still goes with higher instability 46; more change is arriving at the same gates. Kubernetes v1.37, released on 26 August 2026 47, still offers the same two native strategies.

3 Vocabulary, ladder and gauge

Seven words carry the rest of the article. A change is anything that alters what production does: code, configuration, content, schema, flag state. It is deployed when it could run and released when requests reach it. Exposure is the share of some unit that has been released to. Evidence is what is observed about the new version before exposure reaches everyone, and a verdict is the decision, made on that evidence, to continue. The way back is whatever returns exposure to zero.

Each plate is coded on three attributes. The first is a six-rung evidence ladder, which records the strongest kind of evidence that stands behind the decision to expose everyone, in the pattern's usual form.

RungEvidenceWhat it means
V0No evidenceNothing is observed before everyone is exposed; the first observation is a user's.
V1LivenessThe new version starts, answers a probe, boots its slot.
V2Synthetic inputScripted, replayed or test traffic against the deployed version; no user sees its output.
V3Live input, discarded outputReal production requests reach the new version; its responses never reach users.
V4Live exposure, judgedReal users are served; a threshold alarm, a dashboard or a person decides.
V5Live exposure, comparedReal users are served; a statistical test against a concurrent control decides.

The rungs are ordered by what the evidence can rule out, not by how sophisticated the tooling is. V3 is placed below V4 although it exposes nobody, because a discarded response cannot show what users do next, what gets written, or how a feature behaves when it is visible; V3 is the only rung paid for in something other than user failures, which is its value, and it is blind to state, which is its limit.

The second attribute is the exposure unit, the thing that one percent is one percent of: an instance, a request, a user, a cell of customers, a device, or stored state. The unit decides who is hurt and how. One percent of requests is a little of everyone's traffic; one percent of users is all of some people's. A cell holds a fixed set of customers; a device holds a copy nobody else can take back. Stored state is exposed to every version at once, because it is shared by definition.

The third attribute is the way back, in three kinds: a switch (a router weight, a flag, a boot slot: seconds, nothing reinstalled), a redeploy (minutes, the previous artefact installed again) and forward only (installed binaries and migrated data cannot be recalled, only superseded).

Every plate carries the same gauge, a ramp profile. The vertical strip at the left marks the rung. The plot shows exposure on a logarithmic scale from 0.1% to 100% against a rollout clock with no units, with a separate row at the bottom for zero. A hatched band on that bottom row is evidence gathered before anyone is exposed, teal for synthetic input and violet for live input. A diamond marks the verdict: filled canary yellow when it is a statistical comparison with a control, hollow when it is a threshold or a person. A grey hatched block is an outage. The chips beneath name the unit and the way back.

The codings are judgements about each pattern's canonical form, made with a written rule: code what the pattern needs to function, not what a mature team might add to it. A rolling update with an external metrics check is a rolling update with a canary bolted on, and the bolt is coded separately.

4 Replacing the old version

The first family decides how the old version leaves. None of its members gathers more than synthetic evidence, and most gather only liveness; what they differ in is the shape of the transition and the speed of the way back.

A1

Recreate

V0
Switched
Every instance, at once: the old set is stopped before the new set starts.
Exposed first
Everyone, after an outage window that is paid whether or not the release is good.
Evidence before 100%
None. The first observation of the new version is a user's.
Way back
Another recreate, with another outage.
Fails when
Anything at all is wrong; there is no smaller population to be wrong on.

Kubernetes still ships it as one of only two native Deployment strategies, for workloads that cannot tolerate two versions at once 19.

A2

Rolling update

V1
Switched
Instances in batches, bounded by how many extra may exist and how many may be missing.
Exposed first
Whatever requests the load balancer happens to send to the first ready replacements.
Evidence before 100%
Liveness and readiness: the process starts and answers a probe.
Way back
A rolling update in the other direction; the controller can halt on a deadline but cannot judge.
Fails when
The fault passes the readiness probe, which most faults do.

The default strategy is 25% surge and 25% unavailable, and progress is declared failed only after a deadline with no progress 19,48; Argo's own documentation lists what it cannot do: no traffic control, no external metrics, no automatic abort 26.

A3

Blue-green

V2
Switched
A whole second environment, then the router, in one move.
Exposed first
Test traffic on the idle environment; then every user at the switch.
Evidence before 100%
Synthetic checks against the idle environment before any user sees it.
Way back
Point the router back, in seconds, while the old environment still runs and the data still fits it.
Fails when
The fault needs real input or real load, or the schema has moved on.

Named at ThoughtWorks by Daniel Terhorst-North and Jez Humble and described in the Continuous Delivery book; Fowler's account adds that the database must first be made to serve both versions 9,2.

A4

Immutable replacement

V1
Switched
Whole machine images, never patched in place; each release is a new artefact.
Exposed first
Requests reaching the first new instances, as in a rolling update.
Evidence before 100%
The image builds and boots; drift between hosts is removed, not detected.
Way back
Redeploy the previous image, which still exists unchanged.
Fails when
The fault is in the release itself rather than in drift.

The phoenix-server and immutable-infrastructure arguments were about reproducibility, not about exposure: they make the way back trustworthy without making the way forward observed 17,18.

A5

In-place hot swap

V1
Switched
Code inside a running process: old calls finish on old code, new calls enter new code.
Exposed first
Every new call in the process, almost at once.
Evidence before 100%
The new module or binary loads and accepts work.
Way back
Reload the old code while it is still resident; Erlang keeps exactly two versions.
Fails when
The in-memory state format changed and the conversion is wrong.

Erlang/OTP loads a new module version beside the old one and purges the old one on the next load; release upgrades carry explicit state conversion 5,7,6. nginx does the same for its whole binary with a new master process 8.

A6

A/B partitions

V1
Switched
A device's system image, written to the inactive slot while the active one keeps running.
Exposed first
The device itself, at its next boot.
Evidence before 100%
The device boots the new slot and marks it successful.
Way back
The bootloader falls back to the other slot after failed boots.
Fails when
The device boots cleanly and then misbehaves.

Android's seamless updates keep two copies of the system partitions for exactly this fallback 49; the fleet-level exposure is then a separate decision (B4).

The rolling update is the default of a generation and deserves its arithmetic. With twenty replicas, thirty seconds to become ready and the default of 25% surge and 25% unavailable, the rollout takes 61 seconds, keeps at least 15 replicas ready (a 75% capacity floor) and briefly runs 25 pods (L4). Set surge to one and unavailable to zero and the same rollout takes 601 seconds with no loss of capacity; set both to the whole fleet in opposite directions and it becomes either a blue-green inside one Deployment (twice the pods for 31 seconds) or a recreate (zero capacity for 30 seconds). The two knobs trade time against headroom and nothing else. None of them trades anything for evidence, which is why Argo's documentation, introducing its own controller, lists the rolling update's limits so plainly: no control over traffic, no external metrics, no automatic abort 26.

Blue-green's real product is the way back, and the way back is only as fast as the switch actually is. The lab models two switches for the same flip (L6). With a load-balancer weight change, new connections go to green at once but keep-alive connections already open to blue carry on until they close 50; with lifetimes drawn from a lognormal with a thirty-second median, 63.9% of requests still reach blue a minute after the switch, and blue's share does not fall below 1% for 82 minutes or below 0.1% for 4.6 hours. A drain deadline of five minutes ends that tail by force, closing 28.3% of blue's connections, which is why graceful shutdown protocols such as HTTP/2's GOAWAY exist 51. A DNS switch behaves the other way round: a sixty-second TTL moves nearly everyone within a minute, leaving 1.98%, but if 2% of resolvers ignore the TTL and cache for up to a day, blue keeps more than 1% of traffic for 11.8 hours 52,53. A switch has a tail, and the tail is set by the slowest client, not the fastest mechanism.

The other members of the family trade differently. Immutable replacement removes drift between hosts, so that the version being rolled back to is exactly what it was; it gathers no more evidence than a rolling update. Hot swapping keeps the process alive and moves new calls to new code almost at once, and puts all of its risk into the conversion of in-memory state. A/B partitions give each device its own fast way back, the bootloader's fallback, and leave the fleet-wide exposure decision to a separate pattern (B4).

5 Choosing who sees it first

The second family is where evidence is bought with users' requests, and where the price can be computed.

Suppose the old version fails a fraction p0 of requests and the new one fails r·p0. A canary receives a share w of traffic and is compared with the rest, a one-sided two-proportion test at a 5% false-alarm rate and 80% power 54. The number of canary requests needed is roughly (zα√(1+kr) + zβ√(r+k))² / (p0(r−1)²), where k is the ratio of canary to control size. Multiply by the excess failure rate p0(r−1) to get the excess failures suffered on the way to a verdict, and p0 cancels. A doubling costs about 8.0 failed requests beyond the ordinary, a 25% increase about 26.7, a 10% increase about 63.9, and a five-fold increase about 3.1. The lab confirms the closed form by simulation: at p0 = 0.1%, r = 2 and w = 1%, 8,138 canary requests give an empirical power of 0.791 over 2,000 trials against a target of 0.80.

Two corollaries follow. The canary weight appears only through k, and for a canary against the whole remaining fleet k is close to zero, so a 0.1% canary and a 5% canary pay nearly the same number of failures. What the weight changes is time: at 2,000 requests a second and p0 = 0.1%, a 1% canary needs 6.8 minutes to see a doubling and a 0.1% canary needs 67.0. And the more reliable the service, the longer the wait: at p0 = 0.01% the 1% canary needs 67.9 minutes and the 0.1% canary 11.2 hours, because the same 8.0 excess failures take ten times as many requests to accumulate. Good services make slow canaries. The zero-numerator rule says the same thing from the other side: a canary that saw no failures in n requests can only say the rate is below about 3/n 55, so three thousand clean requests say only that the rate is below 0.1%.

Comparing against a freshly deployed baseline of the same size, as Kayenta does in order to avoid comparing new, cold instances with old, warm ones 23,56, sets k to one and costs 2.31 times the failures of a whole-fleet control (18.5 rather than 8.0 for a doubling). That is the price of removing the warm-up confound, and it is worth knowing that it is a price.

The second hazard is looking too often. A canary dashboard is watched continuously, and an automated judge is typically run at intervals. If a naive test at the 5% level is applied every minute to a release that is in fact identical to the old one, the chance of at least one false failure is 6.2% after one look, 20.5% after fifteen and 29.2% after sixty (L2). Watching ten independent metrics that way makes a false rollback of a perfectly good release a near certainty, 96.8%. The remedies are old: sequential tests whose boundaries account for repeated looks 57,58, or always-valid inference designed for continuously monitored online experiments 59. In the lab, a constant boundary of z = 2.633 holds the false-rollback rate at 5% across sixty looks, and z = 3.432 per metric holds it across ten metrics. Rank-based comparisons such as the Mann-Whitney test, used in canary judges for latency distributions 60, carry the same obligation. The simulation in section 9 shows the trap in practice: a stepped canary that restarts its comparison at each step spends its false-alarm budget three times and rolls back 12.2% of good releases.

Sato's definition is a subset of users or servers first, then the rest 12. The sentinel in the coal mine was chosen because it was more sensitive than a miner 3; a software canary is the same animal as the fleet and must get its sensitivity from statistics.

B2

Automated canary analysis

V5
Switched
A canary and a freshly deployed baseline of the same size, side by side.
Exposed first
The canary's share of requests.
Evidence before 100%
A statistical judge compares canary to baseline, metric by metric, and scores the result.
Way back
Automatic: a failing score rolls back without a human.

Kayenta scores each metric and aggregates to 0-100 with success, marginal and failure bands; it compares against a newly deployed baseline rather than the long-running fleet 23,56. Argo Rollouts and Flagger run the same loop as Kubernetes controllers 61,27.

Waves and rings

V4
Switched
Cells, zones and regions in a fixed order, each baking before the next.
Exposed first

Evidence before 100%
Each wave's own alarms over a bake time; the next wave waits on them.
Way back

Amazon describes one-box, then waves with bake times and automatic rollback on alarms 32; Azure's safe deployment practice runs canary regions, a pilot, then paired regions never at once 33.

B4

Phased mobile release

V4
Switched
Which devices are offered the new binary, over days.
Exposed first
A random 1% of devices with automatic updates on day one.

Way back

Apple's phased release runs 1, 2, 5, 10, 20, 50 then 100% over seven days and can be paused 62; Play staged rollouts are similar 63. Facebook's mobile pipeline pairs this with internal dog-fooding tiers 15.

B5

Feature flags

V4
Switched
A code path, switched per user at run time; the binary is already everywhere.
Exposed first
The users the flag selects, consistently.
Evidence before 100%
Whatever is watched for the flagged cohort; usually alarms, sometimes an experiment.
Way back
Turn the flag off, in seconds, with no deploy.
Fails when
Old flags are reused, untested combinations accumulate, or the flag service itself is a global push.

Hodgson separates release toggles, experiment toggles, ops toggles and permission toggles by lifetime and dynamism 1; OpenFeature standardises the evaluation API 64. Knight Capital's loss began with a reused flag 39.

B6

Dark launch

V3
Switched
Real user activity is made to call the new backend, with nothing shown to the user.
Exposed first
Nobody, visibly; the new system carries real load.
Evidence before 100%
Capacity, latency and error behaviour under production input.
Way back
Stop the hidden calls.
Fails when
The hidden path differs from what the visible feature will do, or has side effects.

Facebook Chat was exercised this way before its 2008 launch: live pages generated chat traffic with no visible interface 11.

B7

Controlled experiment

V5
Switched
Randomised users, held in their arm for the whole test.
Exposed first
Half, or a fixed share, of users.
Evidence before 100%
A randomised comparison on the metrics the business cares about.
Way back
End the treatment arm.
Fails when
The sample is too small, the analysis peeks, or assignment is not what it claims.

Kohavi and colleagues set out the method and its traps 65,66; variance reduction with pre-period data buys the same power with fewer users 67. A canary asks whether something broke; an experiment asks whether something improved.

The family's other members move the unit rather than the statistics. Waves and rings make the cell, zone or region the unit and add time, so that an effect too small to see in one wave's alarms still has several chances to be seen before it reaches everyone 32,33. Phased mobile releases make the device the unit, and because an installed binary cannot be recalled they have no way back at all, only a pause and a fix shipped forward 62,63. Browser vendors run the same idea as channels, with a nightly build called Canary at the front 68.

Feature flags make the user the unit and separate release from deploy entirely: the binary is everywhere and the flag decides who runs the new path 1. Their way back is the fastest in the article, and the simulation prices that: with the same schedule and the same statistical judge, a flag ramp whose way back is a flip rather than a five-minute redeploy suffers 239 excess failures from a loud fault rather than 955, a factor of 4.0 bought entirely by the speed of going back. Flags have their own failure mode, and it is the most expensive in this article: Knight Capital repurposed a flag that had once activated a function it had stopped using in 2003, and the one server that did not receive the new code ran the old function when the flag was set 39.

A controlled experiment shares the canary's machinery and differs in the question. A canary asks whether the new version is worse, one-sidedly, on operational metrics, and wants an answer in minutes. An experiment asks whether it is better on business metrics, needs randomised and consistent assignment, and runs for days 65,66; variance reduction with pre-period data can shorten it 67. Both are V5. Confusing them produces canaries run for a week and experiments stopped at the first good-looking day.

6 Evidence without exposure

The third family is the only one that pays in something other than users' failures. A shadow receives copies of real requests, or runs beside the real code path, and whatever it answers is thrown away. The cost is capacity, since every mirrored request is served twice, and engineering, since the copy must be kept from writing anything real. Istio documents mirroring as fire-and-forget with responses discarded 36; Envoy's route configuration carries the mirror policy 37; the Gateway API's percentage-based mirroring exists precisely so that the capacity cost can be dialled 69,38.

V3

Exposed first
Nobody.
Evidence before 100%
Errors, latency and outputs of the candidate on production input.
Way back
Nothing to undo, unless the candidate wrote somewhere.
Fails when
The fault lives on a write path the shadow must be kept away from.

Istio mirrors in fire-and-forget mode and discards the responses 36; Envoy exposes request mirror policies 37, and Gateway API made percentage-based mirroring a standard feature in v1.3.0 38,69.

A shadow's evidence is a comparison of outputs, and real outputs are full of legitimate difference: request identifiers, timestamps, orderings that depend on hashing, recommendations that depend on randomness. Diffy's answer was to run a second copy of the old version and treat any field on which two correct copies disagree as noise 71. The lab reproduces that scheme on fifty thousand mirrored requests with eight fields and two planted regressions, a price error on 0.5% of requests and a 2% change on a recommendation list that already differs 30% of the time between correct runs (L5). Every single response differs from the primary in some field, so a raw diff rate says nothing. A naive rule that flags any field with any difference flags 6 of 8 fields. Subtracting the secondary's noise and testing the excess flags exactly 2, the two planted regressions, with z-scores of 16.30 for the price field and 3.47 for the noisy one.

That last number is the family's limit in miniature. A regression on a noisy field is visible, but only just, and only because fifty thousand requests were mirrored: seeing a 2% change on top of 30% noise needs about 13,421 requests, against 1,309 to see a 0.5% change on a field that is otherwise always equal, 10.3 times as many. Nondeterminism is not an annoyance in shadow testing; it is the exchange rate between mirrored traffic and evidence.

The other limit is structural. A shadow sees what shows in a response to a request whose side effects have been suppressed. It cannot see a write that goes wrong, a message published twice, or a user who behaves differently when a feature is visible. In the section-9 simulation, a shadow phase ahead of a blue-green switch catches both planted faults before anyone is exposed, and pays nothing; when the same fault lives on a write path the shadow cannot exercise, the combination degrades exactly to blue-green, and a loud fault then costs 47,760 failed requests, because no smoke test stood in front of it. GitHub's Scientist makes the same trade inside a single process, running the candidate beside the control and returning the control's result 70; preview stacks do it with synthetic input rather than copies 26.

7 State that does not roll back

Code can be replaced; data outlives it. Every pattern in the first three families assumes that the old version can be put back and will find the world as it left it. The fourth family exists because that assumption fails at the database. Fowler's account of blue-green already says so: make the schema serve both versions first, deploy the application second, and remove support for the old version only after the new one has settled 9.

The family's defining feature shows in the census. No pattern whose unit is stored state rises above V2, because stored state is shared by every version at once: there is no control group for a schema, and nothing to compare a migrated table against except the table it replaced. The patterns respond by changing the question. Expand-and-contract turns one irreversible change into a sequence of reversible ones, each of which is an ordinary code deploy that can be canaried: add the new column, write both, read the new, stop writing the old, and only then drop it 13,72. Online schema change tools build the new table off to the side and make the irreversible moment as short as a rename 73,74; managed database blue-green does the same for the whole instance 31. The strangler fig moves the unit from the database to the route, so that each route can be exposed and judged on its own, and fails exactly where two systems come to own the same data 75.

The way back is itself a deployment, and it runs into the same state. The SEC's order on Knight Capital records that, with erroneous orders flowing, the firm removed the new code from the seven servers where it had been correctly installed, and that this made things worse, because the repurposed flag was still set and now activated the old function on those servers too 39. A rollback is safe only if the world it returns to is the one the old version expects, and the flag state was part of that world.

At fleet sizes in the hundreds a per-host miss rate that looks negligible leaves some host stale on almost every deploy (L7); Amazon's S3 outage came from an operational command whose effect was not bounded before it ran 77.

Cells make blast radius a design parameter. The lab stages a release over 64 cells in waves of 1, 1, 2, 4, 8, 16 and 32, with a thirty-minute bake and a statistical comparison in each wave (L8). For a service failing 0.1% of requests, a doubling is caught in the first cell every time, and the expected share of cells exposed is 1.56%. The same schedule leaks as the fault gets quieter or the service more reliable: a 25% increase at p0 = 0.1% exposes 3.02% on average, a doubling at 0.01% exposes 2.43%, and a 25% increase at 0.01% exposes 21.16%, because the first wave now detects it only 0.171 of the time. The price of evidence from L1 does not go away when the unit changes; it is paid per wave.

Shuffle sharding attacks the same problem from the assignment side. Give each customer a random set of k workers out of N, and a poisoned customer or a bad release on one shard touches few others entirely: with 100 workers and shards of five there are 75,287,520 distinct shards, and the chance that another customer shares all five is about 1 in 75 million, although 23.04% share at least one worker and so feel some degradation 35. With eight workers and pairs the numbers are 28 shards, 3.57% and 46.43%. The technique bounds total failure, not partial pain.

Staged configuration push is the pattern the recent incidents were missing, and it is not exotic. Facebook's Configerator sends a configuration change to test servers and compares them with control servers before a wider push 14. The same discipline applied to every channel that changes production is what the incidents in section 10 did without.

At scale, every deploy is a mixed-version deploy. If each host independently fails to receive a release with probability 0.5%, the chance that at least one host is left on the old build is 3.93% for a fleet of eight, 39.42% for a hundred and 99.33% for a thousand; even at 0.1% per host, a thousand-host fleet is left mixed 63.23% of the time (L7). A version census that asks each host what it runs and catches 99% of stragglers cuts the eight-host case to 0.040% but leaves the thousand-host case at 4.877%. Version skew is therefore not an anomaly to be prevented but a state every design must tolerate, which is the strongest argument for making every change backward-compatible with at least one previous version.

11 Choosing a rollout

The lab and the census suggest an order in which to make the decisions, and the order matters more than any single choice.

Start with the unit, because it is fixed by the system rather than chosen. If a user must see one version consistently, the unit is the user and the mechanism is a flag or a sticky route. If customers are isolated in cells, the unit is the cell. If the change is to shared state, the unit is stored state and no amount of traffic splitting will help; the change must first be converted into a sequence of code changes that can each be exposed on their own.

Choose the way back next, because it bounds the bill when detection is fast. A switch is worth more than any refinement of the analysis when faults are loud, and it is only available if the old version can still run against the world as it now is. Where the way back is forward only, as with devices and migrated data, buy time instead: more waves, longer bakes, a pause button.

Then price the evidence. The size of the smallest effect worth catching and the baseline failure rate give, through L1's formula, the number of requests the canary needs; the traffic share then gives the time. If that time is longer than the release can wait, there are three honest options: accept a coarser verdict (catch doublings, not 10% regressions), move part of the evidence to a shadow for read paths, or reduce variance in the metric. Shrinking the canary is not one of them, since it lengthens the wait without reducing the bill.

Make every look count. Use a sequential boundary for any comparison that is checked repeatedly, divide the false-alarm budget among the metrics being watched, and do not restart the comparison at every step of a ramp without accounting for it 58,59.

Finally, govern every channel. Configuration, content, feature-flag state, schema and operational commands are all deployments. Each should have an exposure unit, a verdict and a way back, and each should be checked by a census of what is actually running rather than by the tool's belief about what it installed. Chaos experiments, which deliberately inject failure in production, are the complementary practice for testing whether the ways back work when they are needed 79.

12 Method and limits

Rung, unit and way back were assigned to each plate by the rule stated in section 3: code the pattern's canonical form, not the best form a mature team might give it. Several plates would move with different conventions; a feature-flag system connected to an experimentation platform is V5 rather than V4, and a rolling update gated by an external analysis is a canary. The census counts that follow are properties of this coding and should be read as such.

The lab is deliberately small. L1 uses the normal approximation to a one-sided pooled two-proportion test and checks it by simulation. L2 and L3 use binomial draws per minute with a fixed seed per run, so that patterns in L3 see identical random numbers and differ only in their rules. L4 is a second-resolution model of the Kubernetes surge and availability bounds, not the controller itself. L6 draws the connections open at the switch from the length-biased form of the lifetime distribution. L8 computes detection power analytically for each wave. The whole lab runs in a few seconds, uses only the Python standard library, and produces byte-identical output under different hash seeds; its complete source and output are reproduced below so that every number in the text can be traced.

What it does not model is at least as important: latency rather than errors, correlated faults that appear only under particular traffic, the time a human takes to notice and act, the cost of duplicate capacity, and faults that change user behaviour rather than server responses. Each of those would move some numbers; none of them would restore the intuition that a smaller canary is a safer one.

def n_canary(p0, r, k):
    """Canary requests needed to detect p1 = r*p0 with a one-sided pooled
    two-proportion z-test (alpha .05, power .80).  k = n_canary/n_control;
    k -> 0 means the control is the whole remaining fleet."""
    p1 = r * p0
    pbar = (k * p1 + p0) / (k + 1)
    a = Z_A * math.sqrt(pbar * (1 - pbar) * (1 + k))
    b = Z_B * math.sqrt(p1 * (1 - p1) + k * p0 * (1 - p0))
    return (a + b) ** 2 / (p1 - p0) ** 2


def excess_limit(r, k):
    """Small-p limit of n_canary * (p1 - p0): independent of p0."""
    return (Z_A * math.sqrt(k * r + 1) + Z_B * math.sqrt(r + k)) ** 2 / (r - 1)

def z_two(x1, n1, x0, n0):
    pp = (x1 + x0) / (n1 + n0)
    se = math.sqrt(max(pp * (1 - pp), 1e-18) * (1 / n1 + 1 / n0))
    return ((x1 / n1) - (x0 / n0)) / se

BASE_P = 0.001
RPS = 2000
FAULTS = {"good": 1.0, "loud": 200.0, "quiet": 2.0}   # multiplier on p0
# loud = 20% errors on the new version, still passing readiness probes


def fleet_alarm(win_err, win_req):
    """V4 threshold alarm: 5-minute fleet error rate above 1.5x p0 and at
    least 30 errors in the window (typical 'burn' style guard)."""
    return win_req > 0 and win_err >= 30 and win_err / win_req > 1.5 * BASE_P


def run_pattern(name, fault, rng, cfg):
    """Minute-resolution simulation. Returns dict with harmed requests
    (excess failures attributable to the new version, as expected value on
    realised exposure), minute of detection (or None), minute at which 100%
    of traffic is on the new version (or None if rolled back)."""
    mult = FAULTS[fault]
    p_new = min(BASE_P * mult, 1.0)
    per_min = RPS * 60
    sched = cfg["sched"]                 # list of (minute, share)
    horizon = cfg.get("horizon", 180)
    mode = cfg["detect"]                 # 'alarm' | 'compare' | 'none'
    back = cfg["back"]                   # minutes to return to 0% after detection
    down = cfg.get("downtime", 0)        # minutes of full outage at t0
    smoke = cfg.get("smoke", 0)          # synthetic requests before exposure
    shadow = cfg.get("shadow", None)     # (minutes, share) mirrored before exposure
    harmed = 0.0
    detect_at = None
    full_at = None
    t0 = 0
    # pre-exposure evidence
    if smoke:
        x = rng.binomialvariate(smoke, p_new)
        # smoke passes if error count consistent with baseline (<= 3/1000 of runs)
        if x > max(3, 3 * smoke * BASE_P):
            return {"harmed": 0.0, "detect": 0, "full": None, "stage": "smoke"}
    if shadow:
        mins, share = shadow
        n1 = n0 = x1 = x0 = 0
        for t in range(1, mins + 1):
            a = int(per_min * share)
            n1 += a
            x1 += rng.binomialvariate(a, p_new)
            n0 += per_min
            x0 += rng.binomialvariate(per_min, BASE_P)
            if cfg.get("shadow_visible", True) and z_two(x1, n1, x0, n0) > OUT["L2"]["pocock_c"]:
                return {"harmed": 0.0, "detect": -mins + t, "full": None, "stage": "shadow"}
        t0 = 0
    share_now = 0.0
    si = 0
    cn1 = cn0 = cx1 = cx0 = 0
    win = []
    rolling_back = False
    rb_start = rb_share = None
    for t in range(0, horizon):
        if not rolling_back:
            while si < len(sched) and sched[si][0] <= t:
                share_now = sched[si][1]
                if mode == "compare":           # new comparison window per step
                    cn1 = cn0 = cx1 = cx0 = 0
                si += 1
        else:
            el = t - rb_start
            share_now = 0.0 if back == 0 else max(0.0, rb_share * (1 - el / back))
        if full_at is None and share_now >= 1.0 and not rolling_back:
            full_at = t
        if down and t < down:
            err = per_min
            harmed += per_min * (1 - BASE_P)   # outage: every request fails
            continue                          # alarms are suppressed in the window
        a = int(round(per_min * share_now))
        b = per_min - a
        xa = rng.binomialvariate(a, p_new) if a else 0
        xb = rng.binomialvariate(b, BASE_P) if b else 0
        harmed += a * (p_new - BASE_P)
        win.append((xa + xb, per_min))
        if len(win) > 5:
            win.pop(0)
        if detect_at is not None:
            if share_now <= 0.0:
                break
            continue
        if mode == "alarm" and share_now > 0:
            e = sum(x for x, _ in win)
            n = sum(y for _, y in win)
            if fleet_alarm(e, n):
                detect_at = t
        elif mode == "ring_alarm" and share_now > 0:
            # alarm on the exposed ring's own rate
            cn1 += a
            cx1 += xa
            if cx1 >= 30 and cx1 / cn1 > 1.5 * BASE_P:
                detect_at = t
        elif mode == "compare" and 0 < share_now < 1.0:
            cn1 += a
            cx1 += xa
            cn0 += b
            cx0 += xb
            if cn1 and cn0 and z_two(cx1, cn1, cx0, cn0) > OUT["L2"]["pocock_c"]:
                detect_at = t
        if detect_at is not None:
            rolling_back = True
            rb_start = t + 1
            rb_share = share_now
            full_at = None
    return {"harmed": harmed, "detect": detect_at, "full": full_at, "stage": "live"}

def median(xs):
    s = sorted(xs)
    n = len(s)
    if n == 0:
        return None
    return s[n // 2] if n % 2 else 0.5 * (s[n // 2 - 1] + s[n // 2])

# L4  Rolling update arithmetic

def rolling_sim(N, surge, unavail, ready_s=30):
    """Second-resolution model of a Deployment rollout.  Old pods are
    removed while ready capacity stays >= N - maxUnavailable; new pods are
    created while total pods stay <= N + maxSurge.  Returns (duration s,
    minimum ready pods, peak total pods)."""
    old = N
    pend = []            # seconds until each pending new pod is ready
    newr = 0
    t = 0
    minr = N
    peak = N
    while newr < N or old > 0:
        while old > 0 and old + newr - 1 >= N - unavail:
            old -= 1
        while newr + len(pend) < N and old + newr + len(pend) < N + surge:
            pend.append(ready_s)
        peak = max(peak, old + newr + len(pend))
        minr = min(minr, old + newr)
        t += 1
        pend = [s - 1 for s in pend]
        newr += sum(1 for s in pend if s <= 0)
        pend = [s for s in pend if s > 0]
    return t, minr, peak

# L6  A switch is not an instant
# ---------------------------------------------------------------------------
def lab6():
    hdr("L6", "A switch is not an instant: share of requests still reaching blue")
    rng = random.Random(SEED + 6)
    # (a) load-balancer flip; keep-alive connections persist until they end.
    # Connections open at the switch are length-biased: for lognormal(mu, s)
    # lifetimes the length-biased law is lognormal(mu + s^2, s), and the
    # remaining life is a uniform fraction of it.
    mu, s = math.log(30.0), 1.5
    conns = sorted(rng.random() * rng.lognormvariate(mu + s * s, s)
                   for _ in range(200000))
    tot = len(conns)
    def lb_share(t):
        lo, hi = 0, tot
        while lo < hi:
            mid = (lo + hi) // 2
            if conns[mid] <= t:
                lo = mid + 1
            else:
                hi = mid
        return (tot - lo) / tot
    # (b) DNS weighted record with TTL 60 s; 2% of resolvers pin for up to 24 h
    clients = []
    for _ in range(200000):
        if rng.random() < 0.02:
            clients.append(rng.random() * 86400.0)
        else:
            clients.append(rng.random() * 60.0)
    clients.sort()
    nc = len(clients)
    def dns_share(t):
        lo, hi = 0, nc
        while lo < hi:
            mid = (lo + hi) // 2
            if clients[mid] <= t:
                lo = mid + 1
            else:
                hi = mid
        return (nc - lo) / nc
    grid = [1, 5, 10, 30, 60, 120, 300, 600, 1800, 3600, 21600, 86400]
    dense = [10 ** (i / 12) for i in range(0, 60)]
    res_dense = {"t": dense, "lb": [lb_share(t) for t in dense], "dns": [dns_share(t) for t in dense]}
    res = {"grid": grid, "dense": res_dense, "lb": [lb_share(t) for t in grid],
           "dns": [dns_share(t) for t in grid], "reach": {}}
    print("   t (s)    LB flip + keep-alive     DNS TTL 60 s (+2% pinned)")
    for t, a, b in zip(grid, res["lb"], res["dns"]):
        print(f"  {t:>6}    {a*100:>18.3f}%     {b*100:>20.3f}%")
    for label, fn in [("lb", lb_share), ("dns", dns_share)]:
        for target in [0.01, 0.001, 0.0001]:
            lo, hi = 0.0, 200000.0
            for _ in range(80):
                mid = (lo + hi) / 2
                if fn(mid) > target:
                    lo = mid
                else:
                    hi = mid
            res["reach"][f"{label}_{target}"] = hi
    print("\n  seconds until blue's share falls below:   1%        0.1%       0.01%")
    for label in ["lb", "dns"]:
        r = res["reach"]
        print(f"  {label:<5}{'':>35}{r[label+'_0.01']:>9.0f} {r[label+'_0.001']:>10.0f} {r[label+'_0.0001']:>10.0f}")
    # a graceful drain timeout of 300 s cuts how many LB connections?
    res["lb_cut_300"] = lb_share(300)
    print(f"\n  a 300 s drain deadline closes {res['lb_cut_300']*100:.3f}% of blue's connections forcibly")
    OUT["L6"] = res

def lab8():
    hdr("L8", "Containment: waves over cells, and shuffle-shard overlap")
    cells = 64
    waves = [1, 1, 2, 4, 8, 16, 32]
    R = 2000.0
    bake_s = 30 * 60.0
    res = {"cells": cells, "waves": waves, "cases": []}
    print(f"  {cells} cells, waves {waves}, 30 min bake per wave, 2000 req/s, V5 comparison per wave")
    print("  p0       r      P(detect) by wave (conditional)                     expected exposed")
    for p0 in [1e-3, 1e-4]:
        for r in [2.0, 1.25]:
            cum = 0
            p_reach = 1.0
            exp_frac = 0.0
            pds = []
            for wv in waves:
                cum += wv
                share = wv / cells
                if cum >= cells:
                    exp_frac += p_reach * 1.0
                    pds.append(None)
                    break
                n_c = R * share * bake_s
                k = share / (1 - share)
                p1 = r * p0
                pbar = (k * p1 + p0) / (k + 1)
                se0 = math.sqrt(pbar * (1 - pbar) * (1 + k) / n_c)
                se1 = math.sqrt((p1 * (1 - p1) + k * p0 * (1 - p0)) / n_c)
                pd = 1 - N01.cdf((Z_A * se0 - (p1 - p0)) / se1)
                pds.append(pd)
                exp_frac += p_reach * pd * (cum / cells)
                p_reach *= (1 - pd)
            res["cases"].append({"p0": p0, "r": r, "pd": pds, "exposed": exp_frac})
            txt = " ".join("  -  " if x is None else f"{x:.3f}" for x in pds)
            print(f"  {p0:<7g}  {r:<5}  {txt:<50}  {exp_frac*100:6.2f}%")
    res["shuffle"] = []
    print("\n  shuffle sharding: workers N, shard size k -> distinct shards, overlap with one poisoned tenant")
    for N, k in [(8, 2), (16, 4), (100, 5), (1000, 5)]:
        c = math.comb(N, k)
        p_any = 1 - math.comb(N - k, k) / c
        res["shuffle"].append({"N": N, "k": k, "shards": c, "p_all": 1 / c, "p_any": p_any})
        print(f"  N={N:<5} k={k}  shards={c:>18,}  P(identical)={1/c:.2e}  P(share >=1 worker)={p_any*100:.2f}%")
    OUT["L8"] = res
