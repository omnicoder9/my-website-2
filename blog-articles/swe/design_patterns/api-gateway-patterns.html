/s01-the-question-at-the-door

1The question at the door

Every request that enters a system of services passes something first. Sometimes it is a load balancer that sees only an address and a port. Sometimes it is a proxy that terminates TLS, reads the path, checks a token, validates the body against a schema, calls six services, and stitches their answers into the exact shape one mobile screen wants. All of these are called gateways, and the catalogues that name their patterns (gateway routing, gateway aggregation, gateway offloading, backends for frontends, the strangler fig) describe them one at a time 1-5. Read side by side, the catalogues hide the variable that matters most, which is how far into the request the edge has to read before it can do its job.

This article organises the whole family around that single question. A request is a set of nested layers: bytes, a protocol envelope, an address, a caller, a payload that obeys a contract, and a purpose the caller has in mind. A pattern that decides from the outer layers can be generic, shared, and left alone for years. A pattern that decides from the inner layers has to know things that belong to other teams, and so it changes whenever they change. Depth is not a defect. Aggregation at the edge exists because reading all the way to purpose saves a mobile client hundreds of milliseconds, and the lab below measures exactly when that is true. But depth is always paid for, and the payment arrives as coupling, as state, and as a new place for failures to meet.

The argument runs through three claims, each checked against a small deterministic lab whose output is reproduced in full at the end.

The first is that the benefit of a deep pattern is narrower than its reputation. Gateway aggregation saves the client round trips that a dependency chain would otherwise force. With twelve independent calls over HTTP/2 it saves nothing and costs 3.0 ms for the extra hop; with three dependent levels on a 100 ms link it saves 195.0 ms at the median. The depth of the call graph and the length of the link decide, not the number of calls.

The second is that depth is paid for in change coupling, and that the most celebrated remedy, backends for frontends, does not reduce the payment. In a modelled estate of 24 services and four clients, a shared aggregating edge absorbs 100.2 deployments a year originating from 26 teams, and only 4.0% of them are caused by the team that owns it. Splitting it into one backend per client raises total edge deployments by a factor of 1.58, but puts 37.8% of each backend's changes in the hands of the team that operates it. The split moves ownership; it does not remove work.

The third is historical. The discipline's recurring move, from gRPC's method-in-the-path to the 2026 Model Context Protocol headers to body-based routing in inference gateways, is to promote whatever the edge needs out of the payload and into the envelope, so that the edge can stay shallow while still routing on meaning 6-8. Much of the history of this field is the history of that promotion.

/s02-from-facade-to-gateway-api-a

2From façade to Gateway API: a short history

The idea of putting one simplified interface in front of a set of subsystems is older than services. The façade pattern in the 1994 catalogue of design patterns gives a subsystem a single higher-level interface so that clients need not know its parts 9. Parnas had already argued in 1972 that modules should be divided by the decisions they hide, which is the same instinct at a different scale: an edge is useful exactly in proportion to what it hides from the client 10.

The enterprise-integration literature of the early 2000s supplied most of the vocabulary the gateway patterns still use. Hohpe and Woolf's catalogue names the content-based router, the aggregator, scatter-gather, the message translator and the messaging gateway, all as components of messaging systems rather than HTTP proxies 11. The enterprise service bus, described at book length in 2004, put routing, transformation and orchestration into shared middleware between applications 12. SOAP, published as a W3C note in 2000, gave that middleware an envelope to read 13. In the same year Fielding's dissertation defined REST and made layered systems and intermediaries a first-class constraint: a component should not be able to see beyond the layer it interacts with, which is what lets a cache or a gateway stand in the middle at all 14. HTTP's own semantics still use the word in this sense: a gateway, or reverse proxy, is an intermediary that acts as the origin server for the outbound connection while translating requests to the servers behind it 15.

Two strands of experience then pulled in opposite directions. Amazon's service-oriented platform, as described by its CTO in 2006, composed pages from many small services; in a later interview he put the number of services called to construct the gateway page at between 100 and 150 16,17. Composition at that scale had to happen somewhere, and the obvious place was a tier close to the services. At the same time, the ESB's habit of accumulating business logic in shared middleware became the thing the microservice style defined itself against. Lewis and Fowler's 2014 description of microservices contrasted smart endpoints and dumb pipes with a bus that does sophisticated routing, choreography and transformation 18. The gateway patterns of the following decade are, in large part, an argument about how smart the pipe at the front door is allowed to be.

Netflix supplied the reference implementation of the modern edge. Its Zuul service had accepted all of the Netflix API's traffic since May 2012 and was described in 2013 as an edge service for dynamic routing, monitoring, resiliency and security, built from filters for authentication, canary testing, load shedding, stress testing and multi-region routing 19,20. In parallel, the Netflix API team found that its generic, granular REST resources forced every device to make many calls and assemble one experience itself, and redesigned the API so that device teams could write their own server-side endpoints to cut chattiness 21,22. By 2013 that API served more than two billion requests a day from more than 800 device types 23. Zuul 2, rebuilt on asynchronous non-blocking I/O, was open-sourced in 2018 24,25.

The name backends for frontends came from SoundCloud. Phil Calçado described the pattern in 2015 as one backend per user experience, owned by the team that builds the frontend, and Sam Newman's article later that year made it widely known 26,27. The same year saw the managed and open-source gateway products that dominate today's landscape begin in earnest: Amazon API Gateway launched in July 2015 28, Google open-sourced gRPC in February 29, and Facebook published GraphQL in September 30. Lyft open-sourced Envoy in September 2016 as a proxy and communication bus designed to sit at the edge and beside every service 31, and the Cloud Native Computing Foundation graduated it in 2018 32. When Netflix put Hystrix into maintenance, Spring Cloud moved its Netflix integrations, Zuul 1 included, into maintenance mode in December 2018 and pointed users to Spring Cloud Gateway 33,34. Microsoft released YARP, a reverse proxy supplied as a .NET library rather than a product, in November 2021 35.

In Kubernetes, the edge acquired a standard API twice. Ingress gave clusters a minimal routing resource, and its documentation now describes the API as frozen, with new work going to Gateway API instead 36. Gateway API reached general availability in October 2023 with a deliberately role-oriented model: infrastructure providers own GatewayClass, cluster operators own Gateway, and application developers own routes 37,38. In November 2025 the Kubernetes project announced the retirement of Ingress NGINX, with best-effort maintenance ending in March 2026; the announcement singles out the snippets annotations, which let users inject arbitrary NGINX configuration, as flexibility that had become an unacceptable security risk 39. Gateway API v1.6 followed on 30 June 2026 and moved TCPRoute and UDPRoute to the Standard channel, completing a stable model that runs from pure layer 4 to layer 7 40. The migration path was tooled as well: Ingress2Gateway, a tool for converting Ingress resources into Gateway API resources, reached 1.0 in March 2026 41.

The newest chapter concerns traffic whose routing key has always lived inside the body. OpenAI-compatible inference APIs name the model in a JSON field, and the Gateway API Inference Extension adds model-aware scheduling behind a standard gateway 42,43. The Model Context Protocol's 2026-07-28 revision made its method and target names mandatory HTTP headers so that gateways can route without parsing JSON-RPC bodies 7. Both are the same move the history keeps repeating, and section 5 returns to it.

3Six depths and four kinds of memory

A second, independent axis records what the pattern must remember between requests. Most confusion about gateway scaling comes from treating these as the same thing. A pattern can read very deep and remember nothing (aggregation holds partial results only for the life of one request), and a pattern can read very shallow and hold shared state that every replica must agree on (a circuit breaker reads only the route and the last few outcomes, but its state is what makes it work).

A note on terms. Microsoft's catalogue splits the single-gateway idea into routing, aggregation and offloading 1-3; Richardson's pattern language treats the API gateway and backends for frontends as one pattern with a variant 44; Newman treats the gateway, the BFF and GraphQL as alternative ways of aggregating calls for a user interface 45. The ladder cuts across all three: routing and offloading sit on the outer rungs, aggregation and BFF on the innermost, and the variants differ in who owns the rung, not in which rung it is.

/s04-where-the-edge-sits-five

4Where the edge sits: five topologies

Before the patterns, the places they run. Five arrangements account for almost everything in production.

In the first, there is no gateway: clients call services directly. It is the arrangement Taibi and Lenarduzzi list as a microservice bad smell, because every client must then know every service's location, protocol and security model, and every cross-cutting concern is re-implemented per service 46. In the second, a single gateway fronts everything; this is the classic API gateway, and it is where the god-gateway failure lives, when one shared tier accretes the composition logic of every client. In the third, each client experience has its own backend, and those backends may themselves sit behind a thin shared edge that does only the outer-rung work. In the fourth, a federated graph router reads a query and plans it across subgraphs owned by different teams. In the fifth, a mesh of proxies beside every service handles east-west traffic, and the north-south edge becomes one more proxy in the same control plane; Burns and Oppenheimer named the per-service variant the ambassador pattern 47,48.

The topologies are not exclusive, and mature systems usually layer them: an outer edge at E1 to E3 run by a platform team, and composition at E5 run by the teams that own clients. The lab's coupling experiment, reported in section 10, gives a reason for that layering that has nothing to do with performance.

Routing is the pattern most people mean by gateway. The gateway reads the host, path, method and perhaps a header, and chooses a service 1. The decision looks trivial and is not, because route tables overlap. A request for /api/orders/export can match a prefix route for /api, another for /api/orders, and an exact route for the full path. Configuration languages that evaluate routes in file order give the first match; Gateway API instead specifies precedence: an exact path match wins, then the longest prefix, then method matches, then the number of header matches and of query-parameter matches, with ties broken by creation time and name 53.

The difference is measurable. The lab builds random route sets over a small path vocabulary, shuffles their order, and compares the route chosen by first-match with the route chosen by specificity. With 8 overlapping routes, 1.96% of requests are misrouted by a random reordering; with 32 routes the figure is 12.3%, and 98.0% of route sets contain at least one misrouted path. Specificity rules give the same answer for every permutation by construction. The value of a precedence rule is that it removes a dependency on an ordering nobody reviews.

Discovery-backed routing deserves a separate word because it is where routing becomes stateful. A static route table names addresses; a dynamic one names services and receives endpoints and health from a control plane. Envoy's xDS protocols are the most widespread form, streaming route, cluster and endpoint configuration to proxies 58, and registry-driven gateways of the Netflix and Spring generation did the same with client-side registries 33,59. The lab's coupling model shows why this matters: with static pools an address-level edge must be redeployed for every service move, 35.5 times a year in the modelled estate, while discovery removes all but the structural changes and brings the figure to 15.0.

Promotion: keeping the edge shallow on purpose

The most consequential routing pattern is not usually listed as a pattern at all. It is the protocol-design decision to put the routing key in the envelope. gRPC carries the fully qualified service and method in the HTTP/2 :path pseudo-header, so any layer-7 proxy can route individual RPCs without decoding a protobuf body 6. GraphQL, by contrast, identifies what a client wants by a query document rather than by a resource address 60; in the common single-endpoint deployment the operation travels in the request body, so anything that wants to route, cache or rate-limit per operation has to read to E4.

Two recent designs show the promotion happening deliberately. The Model Context Protocol's 2026-07-28 revision requires Mcp-Method and Mcp-Name headers, carrying information already present in the JSON-RPC body, precisely so that gateways and load balancers can route and apply policy without parsing the body; the same revision retired its session handshake and session header, making each request self-describing 7. Inference gateways do the promotion inside the edge: a body-based routing extension reads the model field from an OpenAI-compatible request, copies it into an X-Gateway-Model-Name header, and ordinary HTTPRoute header matches then select the model pool, with the extension deliberately failing closed if it cannot parse the body 8,61.

Promotion has a price the plate records: once the same fact is in two places, the two can disagree. An edge that routes on a header the client controls must either verify it against the body or ensure the service re-checks what it acts on. That is a small, explicit cost in exchange for keeping every other edge component at E2.

Two cautions follow from the rung. The first is architectural: if services trust anything that reached them because the gateway checked, then any path around the gateway is an unauthenticated path. Token formats designed for this layer make the trust explicit rather than implicit. JWTs carry signed claims a service can verify itself 62, introspection lets an edge or service ask the authorisation server about an opaque token 64, token exchange lets an edge swap an external credential for an internal one scoped to the downstream call 65, and sender-constrained tokens bind a token to a TLS client certificate or a proof-of-possession key so that a copied token is useless on its own 51,66. The OWASP API Security Top 10 still ranks broken object-level authorisation first, a reminder that the edge can check who is asking but rarely knows enough about the object to decide whether they may touch it 56.

The second caution is about counting. Rate limiting is the canonical per-principal pattern, and the standard vocabulary for it is settling: 429 Too Many Requests has existed since 2012 67, and the IETF httpapi working group's RateLimit and RateLimit-Policy header fields, which let a server advertise quota policy and remaining allowance, reached draft 11 in May 2026 68. Architecture guidance also describes the other side of the exchange: in the rate limiting pattern a caller paces its own requests so that it stays under a downstream service's throttling limits rather than discovering them through errors 72. The algorithms behind the headers differ in a way the headers do not reveal. The lab drives four limiters, each nominally 100 requests per 60 seconds, with four attacker strategies and records the most requests admitted in any 60-second interval.

Only the sliding log, which stores a timestamp for every admitted request, holds the line at 100. The fixed window admits 200 across a window boundary, the token bucket admits 199 (a full bucket plus a minute of refill), and the sliding-window counter admits 198 to an attacker who idles for a window and then bursts. None of this contradicts Cloudflare's measurement that its sliding-window counter wrongly allowed or limited only 0.003% of 400 million real requests 69: real traffic is not adversarial, and the approximation is excellent on it. The point is that a limit is a statement about typical admission unless the algorithm is the log, and a quota meant as a hard bound on an expensive backend needs either the log or a limit set at half the true capacity.

Distribution adds a second error in the opposite direction. The cheapest way to run a limiter on many gateway replicas is to divide the global limit by the replica count and enforce it locally, which is what per-node counting policies do. With random load balancing the replicas do not see equal shares. The lab splits a limit of 960 per window across N replicas and sends a well-behaved client exactly at the limit: at 8 replicas 3.41% of its requests are refused, at 32 replicas 7.12%, and even a client at 80% of its quota loses 1.16% at 32 replicas. The error falls on the honest client, not the attacker. Cloudflare's own design avoided it by sharing counters within a point of presence and relying on anycast to keep one client's traffic in one place 69.

Transcoding is the cleanest example of legitimate E4 work. Google's API design guidance defines how an annotation on an RPC maps a path template, query parameters and body onto request fields, so that one service definition serves both JSON over HTTP and gRPC 75. Envoy implements the mapping as a filter and gRPC-Gateway generates a reverse proxy from the same annotations 76,77. The edge reads the contract but does not invent it: the mapping lives in the service's own descriptor, versioned with the service.

Schema validation is the opposite case. Rejecting malformed input before it reaches a service sounds like pure gain, but a shared edge that validates strictly turns every additive change in any service into an edge change. Fowler's tolerant reader, which ignores what it does not understand, is the older advice for exactly this reason 74. In the lab's coupling model a strict validator at a shared edge changes 111.0 times a year against 52.2 for a tolerant one, more than a shared aggregation edge, because every service's contract passes through it.

Caching and collapsing are where E4 meets shared state. HTTP caching keys a stored response on the method and target and on every request header the response names in Vary 78, and an edge that under-specifies that key will serve one caller's representation to another. Collapsing and stale-while-revalidate address a different problem: what happens when a popular entry expires under load 79. The lab replays 600,004 requests over 10,000 Zipf-distributed keys with a 30-second lifetime and an 80 ms origin fetch.

The result corrects a common intuition. Collapsing concurrent misses barely changes aggregate origin load, which falls from 208.7 to 203.7 requests a second, because most misses are for cold keys in the long tail that never have two requests in flight. What collapsing changes is the hot key: without it, every expiry of the most popular entry (about 204.3 requests a second) sends 14.8 requests to the origin shard that owns it; with it, exactly 1.0. Stale-while-revalidate changes the client's view instead, lifting the hit ratio from 89.6% to 98.3% at the same origin load. Collapsing protects a shard; serving stale protects the user.

Federated GraphQL routers sit on this rung too, and they are instructive because they are the one widely deployed composition layer that stays at E4. The router reads a query document against a composed schema and plans which subgraphs answer which fields; the purpose, the shape of the response a screen needs, is supplied by the client in the query rather than coded into the edge 60. Apollo introduced federation in 2019, and in 2024 the GraphQL Foundation's working groups started a Composite Schemas effort to specify composition and distributed execution across implementations 82,83. The trade is visible in the plate: the edge no longer changes when a screen changes, but it can no longer bound how far a single query fans out, so cost analysis and persisted operations move to the edge instead.

The lab's first experiment asks when aggregation actually pays. A screen needs twelve backend calls whose service times are log-normal with a 15 ms median. The client either calls services directly or makes one call to a gateway that sits a millisecond from the services and adds 2 ms of processing. Two things vary: the client's round-trip time, from 20 ms to 400 ms, and the dependency structure, from twelve independent calls (one level) to three dependent levels of four.

Three regimes appear. With independent calls over HTTP/2, the client can issue all twelve at once and pays one round trip either way; aggregation saves nothing and adds 3.0 ms. With independent calls over HTTP/1.1, where clients limit concurrent connections per origin 87,88, twelve calls need two waves, and aggregation saves one round trip: 123.8 ms at a 100 ms RTT. With dependent calls, aggregation saves one client round trip per extra level regardless of protocol: 195.0 ms at 100 ms RTT and 795.0 ms at 400 ms. The saving is (levels − 1) × RTT, plus any connection-limit waves, minus the hop. The number of calls is irrelevant once they can run concurrently.

That is the latency case. The cost side has two parts, both independent of where the composer runs. The first is the tail. When a response waits for n parts, it is as slow as the slowest. Dean and Barroso's example, a 1% chance of a one-second call, becomes a 63% chance that a response fanning out to 100 servers is slow 89; the lab reproduces it at 63.4%. Their remedy, hedging, sends a second copy of any call that exceeds a high percentile of normal latency. With the hedge threshold at the single-call 95th percentile (20.1 ms), the lab cuts the probability that a 100-way fan-out waits on a slow call from 63.4% to 1.06%, for 5.02% extra calls; at ten-way fan-out the 99th-percentile response falls from 1,128.9 ms to 37.5 ms. Dean and Barroso report a production result of the same shape: hedging after 10 ms cut the 99.9th-percentile latency of a 1,000-key read from 1,800 ms to 74 ms while sending about 2% more requests 89.

The second cost is availability. An aggregate that fails whenever any part fails has availability equal to the product of its parts. Twenty parts at three nines leave the aggregate down 14.3 hours a month. Declaring all but two parts optional, so that the response degrades by omitting them, brings the figure back to 1.4 hours. The pattern that makes this possible in code is unglamorous: settle all calls, fail only on the required ones, and mark the response partial.

The third plate on this rung, orchestration at the edge, marks the boundary the catalogues warn about without always drawing. Composition reads data for a screen; orchestration decides the order of business steps and what to undo when one fails. Once a gateway runs multi-step writes it holds compensation logic that belongs to a domain, and it has become the smart pipe that the microservice style defined itself against 18,86. SoundCloud's later retrospective on its BFFs reported the adjacent failure: complex logic migrating from clients into the BFFs, and cross-cutting concerns such as authentication being implemented separately in each and diverging over time 85.

Retries are the sharpest case. Each layer that retries on failure multiplies the attempts that reach the layer below, and the multiplication is worst exactly when the backend is down. Google's SRE guidance on cascading failures makes the point, advises against issuing retries at multiple levels, and recommends a per-request retry limit and a server-wide retry budget 90; Amazon's guidance adds backoff with jitter and warns against retrying at every layer of a deep stack 91. The lab computes the amplification for stacks of one to four layers, each allowed two retries.

With independent failures the picture is mild: at a 50% failure rate two layers produce 2 backend attempts per request. With a correlated outage, the only kind that matters, four layers produce 81.0. A budget that allows retries only up to 10% of first attempts at each layer holds four layers to 1.46. Envoy implements the budget idea in its circuit-breaker thresholds, capping active retries as a percentage of active requests 92; the Google handling-overload chapter describes the client-side counterpart, adaptive throttling, in which clients start rejecting requests locally once the backend's acceptance rate falls 95.

Circuit breakers, named for this use by Nygard and popularised by Fowler and by Netflix's Hystrix library, stop calling a backend that is failing and give it time to recover 34,93,94; Azure's catalogue lists the pattern alongside retry and throttling 97-99. Load shedding decides which work to refuse when capacity runs out, and both the Google and Amazon accounts stress that the choice should follow request value and cost rather than arrival order 95,96. The rung matters here: a gateway that sheds by priority must read the caller or the request class, which moves shedding from E2 to E3.

/s10-what-depth-costs

10What depth costs

Every pattern in the set can be run well. The question the ladder answers is what each costs to keep running as the system around it changes. The lab's coupling experiment makes that concrete with a modelled estate: 24 services, four client applications each using 12 of them, and yearly rates of change by kind: platform envelope changes, service address changes, caller and credential changes, contract changes (30% of them breaking), and changes to what each client's screens need. An edge must be redeployed whenever a change occurs at or above its depth in something it serves.

Three results stand out. Discovery is the single largest reduction available at the outer rungs, cutting an address-level edge from 35.5 to 15.0 deployments a year, because it converts address changes into data. Contract depth is where the curve steepens, and strictness is the multiplier: a tolerant edge at E4 changes 52.2 times a year, a strict one 111.0. And a shared aggregating edge, at 100.2 deployments from 26 teams, is a coordination problem before it is a performance problem.

Splitting that edge into backends for frontends is often presented as a way to make it simpler. The model says otherwise. Each BFF changes 39.7 times a year and involves 14.0 teams on average, but the four together change 158.8 times, 1.58 times the shared edge, because every service change now has to be absorbed by each BFF that uses the service. What the split buys is ownership: the share of a deployable's changes caused by the team that runs it rises from 4.0% to 37.8%. Conway's observation that system structure mirrors communication structure is the right frame 100: the BFF puts the most frequent change, the client's own, inside the team that makes it, and leaves the service-driven changes to be absorbed in several places instead of one. Whether that is a good trade depends on how often screens change relative to services, which is exactly the number an organisation should measure before choosing.

/s11-a-field-guide-to-the

11A field guide to the implementations

The same patterns appear, under different names, in every major implementation. The listings that follow show one pattern each in a different technology; they are deliberately short and use only documented configuration.

Gateway API is the most explicit about roles and precedence. A single HTTPRoute can express header-matched canary traffic and a weighted split, and its precedence rules, not the order of its rules, decide which match wins 53.

Envoy expresses the protection family directly. Retry policy sits on the route; the retry budget sits on the upstream cluster's circuit-breaker thresholds, as a percentage of active requests with a floor on concurrency 92.

NGINX's request-limiting module, which Cloudflare took as its starting point, implements a leaky bucket per key in shared memory on one server 69,70. Kong's rate-limiting plugin offers a local policy that counts per node, which is the split-limit arrangement measured in section 6 101.

Spring Cloud Gateway, the successor Spring recommended for Zuul 1, composes routes from predicates and filters in Java or configuration 33,102. YARP takes the library approach further: the proxy is an ASP.NET application, configured by routes and clusters and extended in ordinary code 35.

At E4, the contract itself carries the edge's instructions. An HTTP annotation on an RPC is all a transcoding gateway needs 75; a federation key directive is all a graph router needs to join an entity across subgraphs 82.

At E5, the composer is ordinary application code, which is the point of backends for frontends. The listing applies the section 8 rules: a deadline for the whole screen, settled rather than failed-fast parallel calls, and failure only on the part the screen cannot render without.

Managed gateways package the same rungs as products. Amazon API Gateway launched in 2015 with API keys, throttling and response caching as managed features, and AWS now documents two API styles that differ in which of those features they include 28,71. The practical reading of the ladder for any product is the same: find out which rungs it implements as configuration, which as code you write, and which it leaves to you, and choose the product whose configuration covers the outer rungs you want shared.

Two error-reporting conventions complete the picture. The Forwarded header standardises what an intermediary records about the client and the path it came through 103, and Problem Details gives a machine-readable body for errors an edge generates on a service's behalf 104. Both exist because the edge speaks for the service, and the service's clients need to know when it did.

What the ledger says

Read down the depth column and the structure of the field is plain. The outer three rungs hold 12 of the 26 patterns and almost all the generic, product-shaped functionality: TLS, routing, splitting, discovery, retries and breakers. These are the patterns a platform team can own for everyone. E3 and E4 hold the patterns that make the edge a party to someone else's decisions, identity and contract, and they are where the lab found the sharpest surprises: limits that admit twice their nominal value, split limits that refuse honest clients, strict validation that couples the edge to every contract. E5 holds only three patterns, and they are the ones the gateway is famous for.

Read across the state column and a second structure appears. The deepest patterns remember the least: every E5 plate holds state only for the life of a request. The shallowest routing patterns become the most stateful as soon as they remember backends: discovery, retry budgets, breakers and shedding all hold shared state, and all sit at E2 or E3. Scaling an edge horizontally is therefore hardest not where it reads most, but where it remembers most.

The recommendations follow from the two axes. Keep the shared edge at the outer rungs, and make it stateful only where the state is about backends it protects. Promote routing keys into the envelope rather than teaching the shared edge to read bodies. When composition is needed, measure the dependency depth and the client's round-trip time before building it, because those two numbers set its value. Put composition where the team that causes its changes can make them, accepting that this raises the total amount of edge work. And prefer rules, such as route precedence and retry budgets, that stay correct when the configuration around them is reordered or scaled out.

        row = []
        for L in (1, 2, 3, 4):
            F, E = f, 1.0
            for _ in range(L):
                calls = sum(F ** i for i in range(R + 1))
                E *= calls
                F = F ** (R + 1)
            row.append(E)
            rec(f"e4_f{f}_L{L}", E, 3)
        print(f"{f:>5} " + " ".join(f"{v:>9.3f}" for v in row))
    # budgeted retries, correlated full outage, simulated
    print("with a per-layer retry budget (retries <= 10% of first attempts), full outage f=1.0, simulated 20,000 requests:")
    for L in (1, 2, 3, 4):
        n_top = 20000
        arrivals = n_top
        for _ in range(L):
            first, retries, sent = 0, 0, 0
            for _ in range(int(arrivals)):
                first += 1; sent += 1
                for _ in range(R):
                    if retries + 1 <= 0.10 * first:
                        retries += 1; sent += 1
                    else:
                        break
            arrivals = sent
        amp = arrivals / n_top
        rec(f"e4_budget_L{L}", amp, 3)
        print(f"   L={L}: unbudgeted {(R + 1) ** L:>3}x   budgeted {amp:.3f}x")

def max_in_window(ts, W):
    best, j = 0, 0
    for i in range(len(ts)):
        while ts[i] - ts[j] >= W:
            j += 1
        best = max(best, i - j + 1)
    return best

def e5_rate_limits():
    hdr("E5  Rate limiters: worst case admitted in any 60 s, and split local limits")
    L, W, DT, T = 100, 60.0, 0.01, 600.0
    ticks = int(T / DT)

    class Fixed:
        def __init__(s): s.win, s.c = -1, 0
        def admit(s, t):
            w = int(t // W)
            if w != s.win: s.win, s.c = w, 0
            if s.c < L: s.c += 1; return True
            return False
    class Log:
        def __init__(s): s.q = []; s.h = 0
        def admit(s, t):
            while s.h < len(s.q) and t - s.q[s.h] >= W: s.h += 1
            if len(s.q) - s.h < L: s.q.append(t); return True
            return False
    class Counter:
        def __init__(s): s.win, s.c, s.prev = -1, 0, 0
        def admit(s, t):
            w = int(t // W)
            if w != s.win:
                s.prev = s.c if w == s.win + 1 else 0
                s.win, s.c = w, 0
            frac = (t - w * W) / W
            if s.prev * (1 - frac) + s.c + 1 <= L: s.c += 1; return True
            return False
    class Bucket:
        def __init__(s): s.tok, s.last = float(L), 0.0
        def admit(s, t):
            s.tok = min(L, s.tok + (t - s.last) * L / W); s.last = t
            if s.tok >= 1: s.tok -= 1; return True
            return False

    def strategies():
        yield "greedy", lambda k: True
        yield "boundary", lambda k: (k * DT) % W >= W - 0.02 or (k * DT) % W < 0.02
        yield "idle-burst", lambda k: int(k * DT / W) % 2 == 1 or (k * DT) % W >= W - 1.0
        yield "late-half", lambda k: (k * DT) % W >= W / 2
    print(f"limit {L} per {W:.0f} s; attacker offers up to 1000 requests per 10 ms tick under four strategies")
    print(f"{'algorithm':>18} {'worst 60 s':>11} {'x limit':>8} {'strategy':>11}")
    for name, cls in (("fixed window", Fixed), ("sliding log", Log), ("sliding counter", Counter), ("token bucket", Bucket)):
        worst, wname = 0, ""
        for sname, fire in strategies():
            lim, ts = cls(), []
            for k in range(ticks):
                if fire(k):
                    t = round(k * DT, 2)
                    for _ in range(1000):
                        if lim.admit(t): ts.append(t)
                        else: break
            m = max_in_window(ts, W)
            if m > worst: worst, wname = m, sname
        key = name.split()[0] + ("_" + name.split()[1] if len(name.split()) > 1 else "")
        rec(f"e5_{key}", worst)
        print(f"{name:>18} {worst:>11} {worst / L:>8.2f} {wname:>11}")
    # split limits across replicas with random load balancing
    rng = random.Random(SEED + 5)
    LG, WINS = 960, 3000
    print(f"global limit {LG}/window split as {LG}/N per replica; random load balancing; client below or at the limit")
    print(f"{'N':>3} {'per-replica':>12} {'reject @80%':>12} {'reject @100%':>13}")
    for N in (1, 2, 4, 8, 16, 32):
        cap = LG // N
        res = []
        for load in (0.8, 1.0):
            m = int(LG * load); rej = 0
            for _ in range(WINS):
                cnt = [0] * N
                for _ in range(m):
                    cnt[rng.randrange(N)] += 1
                rej += sum(max(0, c - cap) for c in cnt)
            res.append(100.0 * rej / (m * WINS))
        rec(f"e5_split_N{N}_80", res[0], 3); rec(f"e5_split_N{N}_100", res[1], 3)
        print(f"{N:>3} {cap:>12} {res[0]:>11.3f}% {res[1]:>12.3f}%")

def e6_coupling():
    hdr("E6  Change coupling: edge deployments a year, and whose changes they are")
    rng = random.Random(SEED + 6)
    S, C, USE = 24, 4, 12
    uses = [sorted(rng.sample(range(S), USE)) for _ in range(C)]
    ENV, ADDR, CALLER, CONTRACT, BREAK, PURPOSE, STRUCT = 4.0, 1.5, 3.0, 4.0, 0.3, 12.0, 0.35
    print(f"{S} services, {C} clients each using {USE}; per year: envelope {ENV} (platform), address {ADDR}/service,")
    print(f"caller {CALLER}/client, contract {CONTRACT}/service ({BREAK:.0%} breaking), purpose {PURPOSE}/client; {STRUCT:.0%} of address changes are structural")
    def scen(depth, dynamic=False, tolerant=False, clients=None):
        cl = list(range(C)) if clients is None else clients
        svcs = sorted(set(s for c in cl for s in uses[c]))
        rate, teams = 0.0, set()
        if depth >= 1: rate += ENV; teams.add("platform")
        a = ADDR * (STRUCT if dynamic else 1.0)
        rate += a * len(svcs); teams.update(f"s{s}" for s in svcs)
        if depth >= 3: rate += CALLER * len(cl); teams.update(f"c{c}" for c in cl)
        if depth >= 4: rate += CONTRACT * (BREAK if tolerant else 1.0) * len(svcs)
        if depth >= 5: rate += PURPOSE * len(cl); teams.update(f"c{c}" for c in cl)
        return rate, len(teams)
    e0d, e1d = scen(0, dynamic=True), scen(1, dynamic=True)
    rec("e6_e0d_rate", e0d[0], 1); rec("e6_e1d_rate", e1d[0], 1); rec("e6_e0d_teams", e0d[1], 1); rec("e6_e1d_teams", e1d[1], 1)
    print(f"dynamic-discovery variants: E0 L4 pool {e0d[0]:.1f}/yr ({e0d[1]} teams), E1 TLS offload {e1d[0]:.1f}/yr ({e1d[1]} teams)")
    rows = [
        ("A  E0 L4 pool, static", "e0", scen(0)),
        ("B  E1 TLS offload, static", "e1", scen(1)),
        ("C  E2 routes, static pools", "e2s", scen(2)),
        ("D  E2 routes, dynamic discovery", "e2d", scen(2, dynamic=True)),
        ("E  E3 + identity and quota", "e3", scen(3, dynamic=True)),
        ("F  E4 tolerant reader", "e4t", scen(4, dynamic=True, tolerant=True)),
        ("G  E4 strict validation", "e4s", scen(4, dynamic=True)),
        ("H  E5 shared aggregation edge", "e5sh", scen(5, dynamic=True, tolerant=True)),
    ]
    bffs = [scen(5, dynamic=True, tolerant=True, clients=[c]) for c in range(C)]
    print(f"{'edge':>34} {'deploys/yr':>11} {'teams':>6}")
    for label, key, (r, t) in rows:
        rec(f"e6_{key}_rate", r, 1); rec(f"e6_{key}_teams", t)
        print(f"{label:>34} {r:>11.1f} {t:>6}")
    tot = sum(b[0] for b in bffs)
    mean_rate = tot / C; mean_teams = sum(b[1] for b in bffs) / C
    rec("e6_bff_rate", mean_rate, 1); rec("e6_bff_teams", mean_teams, 1); rec("e6_bff_total", tot, 1)
    print(f"{'I  E5 BFF, per client (mean of 4)':>34} {mean_rate:>11.1f} {mean_teams:>6.1f}")
    print(f"{'J  E5 BFF, all four together':>34} {tot:>11.1f}")
    sh = rows[-1][2]
    own_shared = ENV / sh[0]
    own_bff = (PURPOSE + CALLER) / mean_rate
    rec("e6_ratio_total", tot / sh[0], 2)
    rec("e6_own_shared", 100 * own_shared, 1); rec("e6_own_bff", 100 * own_bff, 1)
    print(f"BFF split multiplies total deployments by {tot / sh[0]:.2f} and cuts teams per deployable {sh[1]} -> {mean_teams:.1f};")
    print(f"share of deployments caused by the deployable's own team: shared edge (platform) {own_shared:.1%}, BFF (client team) {own_bff:.1%}")

def e7_collapse():
    hdr("E7  Edge cache on expiry: thundering herd, request collapsing, stale-while-revalidate")
    rng = random.Random(SEED + 7)
    K, LAM, TTL, FETCH, T = 10000, 2000.0, 30.0, 0.080, 300.0
    w = [1.0 / (k + 1) for k in range(K)]
    cum, s = [], 0.0
    for x in w:
        s += x; cum.append(s)
    arrivals, t = [], 0.0
    while True:
        t += rng.expovariate(LAM)
        if t >= T: break
        arrivals.append((t, bisect.bisect_left(cum, rng.random() * s)))
    rec("e7_requests", len(arrivals))
    print(f"{len(arrivals)} requests over {T:.0f} s, {K} keys Zipf(1.0), TTL {TTL:.0f} s, origin fetch {FETCH * 1000:.0f} ms")
    print(f"{'mode':>22} {'hit %':>7} {'origin req/s':>13} {'top-key origin/expiry':>22} {'waited %':>9}")
    for mode in ("no collapsing", "collapsing", "stale-while-revalidate"):
        exp_at, pending, origin, hits, waited = {}, {}, 0, 0, 0
        top_fetch, top_expiries = 0, 0
        for (t, k) in arrivals:
            if k in pending and pending[k] <= t:
                exp_at[k] = pending.pop(k) + TTL
                if k == 0: top_expiries += 1
            fresh = k in exp_at and t < exp_at[k]
            if fresh:
                hits += 1; continue
            if mode == "stale-while-revalidate" and k in exp_at:
                hits += 1
                if k not in pending:
                    pending[k] = t + FETCH; origin += 1
                    if k == 0: top_fetch += 1
                continue
            if mode == "no collapsing":
                origin += 1; waited += 1
                if k == 0: top_fetch += 1
                if k not in pending: pending[k] = t + FETCH
            else:
                waited += 1
                if k not in pending:
                    pending[k] = t + FETCH; origin += 1
                    if k == 0: top_fetch += 1
        per = top_fetch / max(1, top_expiries)
        n = len(arrivals)
        key = mode.split()[0].replace("-", "_")
        rec(f"e7_{key}_hit", 100 * hits / n, 2); rec(f"e7_{key}_origin", origin / T, 1)
        rec(f"e7_{key}_top", per, 1); rec(f"e7_{key}_wait", 100 * waited / n, 2)
        print(f"{mode:>22} {100 * hits / n:>7.2f} {origin / T:>13.1f} {per:>22.1f} {100 * waited / n:>9.2f}")
    print(f"top key rate = {LAM / s:.0f} req/s, so an uncollapsed expiry sends ~{1 + LAM / s * FETCH:.0f} requests to origin")
    rec("e7_topkey_rate", LAM / s, 1)

def e8_precedence():
    hdr("E8  Route precedence: first-match in config order vs Gateway API specificity rules")
    rng = random.Random(SEED + 8)
    L1 = ["api", "admin", "static", "v1", "v2"]
    L2 = ["users", "orders", "items", "search", "health"]
    L3 = ["id", "list", "export"]
    paths = []
    for a in L1:
        paths.append("/" + a)
        for b in L2:
            paths.append(f"/{a}/{b}")
            for c in L3:
                paths.append(f"/{a}/{b}/{c}")
    def matches(route, p):
        kind, v = route
        if kind == "exact": return p == v
        return p == v or p.startswith(v + "/")
    def spec_key(route):
        kind, v = route
        return (1 if kind == "exact" else 0, len(v))
    print(f"{len(paths)} distinct request paths; routes are random prefixes (depth 1-3) and ~25% exact matches")
    print(f"{'routes':>7} {'misrouted %':>12} {'sets w/ any':>12} {'reorder-safe':>13}")
    for R in (4, 8, 16, 32):
        mis_tot, anyset, SETS = 0.0, 0, 300
        for _ in range(SETS):
            routes = []
            while len(routes) < R:
                p = rng.choice(paths)
                r = ("exact" if rng.random() < 0.25 else "prefix", p)
                if r not in routes: routes.append(r)
            order = routes[:]; rng.shuffle(order)
            mis, cand = 0, 0
            for p in paths:
                m = [r for r in routes if matches(r, p)]
                if not m: continue
                cand += 1
                best = max(m, key=spec_key)
                first = next(r for r in order if matches(r, p))
                if first != best: mis += 1
            if cand:
                mis_tot += mis / cand
                if mis: anyset += 1
        rec(f"e8_R{R}_mis", 100 * mis_tot / SETS, 2); rec(f"e8_R{R}_any", 100 * anyset / SETS, 1)
        print(f"{R:>7} {100 * mis_tot / SETS:>11.2f}% {100 * anyset / SETS:>11.1f}% {'yes':>13}")
    print("reading: specificity ordering gives the same answer for every permutation of the config (0% by construction);")
    print("first-match depends on an order that nobody reviews.")
