01The question behind the catalogue

Every data design pattern with a name puts a fact in two places. A cache holds a copy of a row. A replica holds a copy of a database. A materialized view holds a copy of a query result, an index table a copy of a lookup, a search cluster a copy of a catalogue, and a system built on polyglot persistence holds the same customer in a relational store, a document store and a search engine at once. The second copy is the whole point: it is closer, cheaper, shaped differently or owned by someone else. It is also the source of nearly every failure these patterns are famous for, because two copies of a fact can disagree and one copy cannot.

The usual way to teach the patterns is as a menu, with a diagram and a list of pros and cons for each. This article takes a different line. It treats every pattern as an answer to a single question, who writes the second copy?, and asks two things of each answer. First, what mechanism actually carries a change from the authoritative copy to the derived one: a clock, the calling code, a component in the data path, a scheduled job, an ordered log, or the commit itself. Second, what is left behind when that mechanism fails: a copy that heals on its own, a write that is refused, a copy that stays silently wrong, or acknowledged writes that are lost.

Meta's engineers, describing how they took the consistency of the TAO cache from six nines to ten, put the premise plainly: invalidation is an action that something other than the cache has to perform, whether a client or a publish-subscribe system, and a cache that relies on time alone is a different design1. That observation is the spine of this article. The pattern names describe where the copy lives. The engineering lives in who is responsible for keeping it true.

The answer the census in section 10 gives is sharper than expected. Across 28 patterns, healing is never supplied by the writer. Of the 14 patterns whose copy is carried asynchronously by something other than the calling code (a clock, a schedule or a log), 12 heal by themselves. Of the 4 patterns in which the calling code writes the copy as a separate step, 3 leave it silently wrong when that step fails, and the fourth, cache-aside, heals only because a time-to-live is standing behind it. Synchronous carriers mostly buy consistency by refusing writes instead. The rest of the article is the evidence: a history, a coding scheme, 28 numbered plates with a small gauge each, eight experiments whose output is embedded verbatim, and worked examples in Python, Java, C#, Go, SQL and configuration for Redis, JCache, Spring, HybridCache, Hazelcast, PostgreSQL, SQL Server, Debezium and Kafka.

02A short history of the second copy

The first second copy was hardware. In 1965 Maurice Wilkes proposed a small, fast "slave memory" that would hold copies of words from a larger, slower main store and be consulted first2. IBM's System/360 Model 85, described by Liptay in 1968, put that structure into a commercial machine3. The theory arrived at the same time. Belady showed in 1966 that the optimal replacement policy evicts the item whose next use lies furthest in the future, a bound no real policy can reach because it needs the future4. Denning's working-set model of 1968 explained why caches work at all: programs revisit a small set of pages over any short window5. Mattson and colleagues showed in 1970 that for a large class of policies, including least-recently-used, a single pass over a reference trace yields the hit ratio for every cache size at once6. Hardware caches had one advantage that every later design envied: the processor that wrote a word was the only writer, so coherence was an engineering problem inside one box.

Codd's relational model, published in 1970, already named the software version of the problem. His paper separated the relations a user sees from their storage and discussed redundancy, where one relation can be derived from others, and the consistency obligations that follow when derivable data is stored rather than computed7. The transaction, set out by Gray in 1981, gave databases a way to change several stored facts atomically8, and with it the cleanest possible carrier for a second copy: change it inside the same commit. Blakeley, Larson and Tompa showed in 1986 how to update a stored view incrementally rather than recompute it9, and by 1995 Gupta and Mumick could survey a mature literature on materialized view maintenance10. Garcia-Molina and Salem's sagas of 1987 addressed the opposite case, a long-lived activity that cannot hold locks, by breaking it into local transactions with compensating actions11.

Replication forced the question into the open. Gray, Helland, O'Neil and Shasha's 1996 paper on the dangers of replication showed that update-anywhere schemes become unstable as they grow: in their model a tenfold increase in nodes and traffic produces roughly a thousandfold increase in deadlocks or reconciliations12. The web supplied the next wave. Breslau and colleagues found in 1999 that web request popularity follows a Zipf-like distribution with an exponent below one, which set realistic expectations for how much a cache of a given size can absorb13. Karger and colleagues' consistent hashing of 1997 let a cluster of caches grow without reshuffling every key14, and Thaler and Ravishankar's highest-random-weight mapping gave an alternative with no ring at all15. Che, Tung and Wang's approximation of 2002 made LRU hit ratios computable in closed form from popularity alone16, later shown to be accurate across a wide range of conditions17.

The pattern names this article uses mostly date from the 2000s. Memcached, written by Brad Fitzpatrick for LiveJournal and described in 2004, made the application-managed look-aside cache the default architecture of the dynamic web18. Tangosol's Coherence documentation of the same era already distinguished read-through, write-through, write-behind and refresh-ahead caching by name19, vocabulary that the Java standard caching API, JSR 107, finally codified in 201420. Amazon's Dynamo paper of 2007 showed a production store that accepted temporary divergence between replicas and handed conflicting versions back to the application21, and the CAP argument, stated by Brewer in 2000 and proved in a restricted form by Gilbert and Lynch in 2002, gave the trade a name22,23. Vogels popularised eventual consistency in 200924, and Abadi's PACELC formulation of 2012 pointed out that the more common trade is between consistency and latency when nothing is partitioned at all25.

The second copy then left the single database. Stonebraker and Çetintemel argued in 2005 that the era of one general-purpose engine for every workload was over26. Neal Ford coined "polyglot programming" in 200627, Scott Leberknight began using "polyglot persistence" around 200828, and Martin Fowler's 2011 note, which credits Leberknight with the term, predicted that any decent-sized enterprise would soon run a variety of storage technologies chosen by how each kind of data is manipulated29,30. Fowler had written up event sourcing in 200531; Greg Young's CQRS documents followed in 2010, building on Meyer's command-query separation32,33. Pat Helland argued in 2007 that systems at scale would give up distributed transactions altogether34, and Jay Kreps's 2013 essay on the log recast replication, integration and derived data as consumers of one ordered record of changes35. Nishtala and colleagues published the operational detail of Facebook's memcache the same year, including the lease mechanism that prevents stale sets36, alongside the TAO paper37. Helland later compressed the whole idea into a sentence: the truth is the log, and the database a cache of a subset of it38.

The recent history is mostly industrial. Chris Richardson's catalogue made the transactional outbox, database per service and the saga standard vocabulary for microservices39, and change data capture tools such as Debezium turned a database's own replication log into a general-purpose carrier40. Redis, the most widely deployed cache server, moved from the BSD licence to source-available terms with version 7.4 in March 2024, prompting the Linux Foundation-backed Valkey fork from Redis 7.2.4, and then added the AGPLv3 as an open-source option with Redis 8 in May 202541. Microsoft made HybridCache, a two-level cache for .NET with built-in stampede protection and tag-based invalidation, generally available in March 202542. EventStoreDB, the best-known database built for event sourcing, was renamed KurrentDB, with version 25.0 the first release under the new name43,44. 03Six carriers and four residues

The coding scheme has two axes. The first is the carrier: the mechanism that moves a change from the authoritative copy (the source) to the derived copy. There are six, ordered from the weakest coupling to the strongest, shown in Figure 2.

Time (P0). Nothing carries the change. The copy is given a lifetime and discarded when it expires, and the next reader fetches a fresh one. Read-through caching, HTTP caching and negative caching live here. Caller (P1). The code that wrote the source also writes or deletes the copy, as a separate operation that can fail or interleave independently. Component (P2). A cache provider, proxy or server performs the update synchronously on the caller's behalf, inside the call the caller is making. Schedule (P3). A job recomputes the copy from the source at intervals. Log (P4). The copy is produced by a consumer of an ordered, durable record of changes, and a consumer that stops can resume from its position. Commit (P5). The copy changes inside the same atomic commit as the source, or, for a replicated store, inside the same quorum write.

The second axis is the residue: what a broken carrier leaves behind. A copy that heals (H) returns to agreement without anyone noticing the fault, because it expires, is recomputed, or its consumer resumes. A carrier that refuses (B) preserves agreement by failing or blocking the write, so the cost is paid in availability or latency. A copy that is silent (S) stays wrong until someone detects the divergence and repairs it. A carrier that loses (W) can make acknowledged writes disappear, because at the moment of failure the copy that held them was ahead of the authority or was about to become it.

Each pattern was coded to the carrier that moves a change from the source into the copy, which is not always the component that fills the copy. Read-through is the instructive case: the cache fills itself on a miss, so the fill is carried by a component, but no mechanism tells the cache that the source has changed, so the change is carried only by expiry, and read-through is coded P0. Where a pattern combines carriers, the code is the one that bounds the copy's disagreement in normal operation, and the combination is noted on the plate.

Each plate below carries a two-rail gauge. The strip along the top marks the carrier. Beneath it, the upper rail is the source and the lower rail the copy, on a logarithmic time axis from a tenth of a millisecond to a day. The write lands as a black dot; a curve in the carrier's colour runs to the moment the copy is first updated; and the hatched band on the copy rail marks the interval during which the copy can still be wrong, from the typical best case to the design's bound. A band that runs off the right edge with an open arrow has no upper bound. A thick bar joining the rails means the copy changes in the same commit and there is no window. When the copy is written first and the source later, as in write-behind, the rails swap roles and the curve climbs instead of falling. 04Caching on the read path

Read-path caches exist because access is skewed. If every key were equally popular, a cache holding one per cent of the keys would absorb one per cent of the reads. Real traffic is closer to Zipf's law, where the i-th most popular item is requested in proportion to 1/iα13, and the payoff of a cache depends almost entirely on the exponent. Experiment E1 simulated an LRU cache over 20,000 keys and compared it with Che's approximation16. At α = 0.8, a cache holding 1% of the keys serves 17.5% of reads, 10% of the keys serves 44.6%, and 20% serves 57.7%. At α = 1.0 the same 1% cache serves 43.5%; at α = 0.6 it serves 4.6%. The approximation never strayed more than 0.4 percentage points from the simulation, which is why capacity planning for a cache can start from a popularity estimate and a spreadsheet (Figure 3).

The curve also shows the economics of growth. Doubling the cache from 10% to 20% of the keys at α = 0.8 cuts the miss rate from 55.4% to 42.3%, a reduction of 23.6%. Replacement policy moves these numbers at the margin: LRU-K45, ARC46 and the W-TinyLFU admission policy used by the Caffeine library for Java47,48 all beat plain LRU on skewed and scan-polluted traffic. But the choice of policy never changes the carrier. Every read-path pattern still has to answer who tells the cache that its copy is wrong.

Cache-aside

In cache-aside, which Amazon's guidance calls lazy loading49, the application checks the cache, falls back to the database on a miss, and puts what it found into the cache with a time-to-live. The pattern's reputation for subtlety comes from two races between those few lines. In the first, a reader misses, reads the old row, pauses, and writes the old value into the cache after a writer has already committed the new row and deleted the entry. In the second, the writer deletes the entry before committing, and a reader that arrives in the gap reads the old row and re-caches it. Facebook's memcache team chose deletion over updating the cache because deletes are idempotent, and closed the first race with leases: on a miss the cache hands the reader a token, a delete invalidates any outstanding token, and a set carrying an invalid token is refused36.

Experiment E2 put numbers on both races. It simulated one key read 100 times a second with a 600-second TTL, a read path whose latency is usually a few milliseconds but occasionally stalls for hundreds (a garbage-collection pause or a slow query), and five write-side strategies. With one write every 5 seconds, deleting after commit produced 1.05 stale episodes lasting more than a second per thousand writes; deleting before commit produced 240.217, about 229 times as many, with 288,859.6 parts per million of reads served stale. A second, delayed delete 500 ms after the first cut the after-commit rate by 68% but not to zero, because a few read-path stalls outlast any fixed delay. Leases produced no stale episode in any configuration (Figure 5). Updating the cache instead of deleting it did better than deletion in this model (0.067 per thousand writes), because a cache that is never emptied invites fewer racing fills, but it reintroduces a race between concurrent writers and computes values for writes nobody may read.

Read-through, and why it is coded as time

Read-through moves the fill into the cache. The application asks only the cache, and a loader registered with the cache fetches missing entries. JCache expresses this with a CacheLoader and a read-through flag, and the same configuration can enable write-through with a CacheWriter20:

Coherence, Hazelcast's MapLoader and Amazon's DynamoDB Accelerator work the same way52–54. The benefit is real: one component owns loading, serialisation and miss coalescing, and application code cannot forget to populate the cache. But a loader only acts on a miss. When the source changes behind the cache's back, nothing tells the cache, and the entry stays wrong until it expires. That is why read-through is coded P0 here even though a component does the filling. It is also why read-through almost always appears paired with write-through, which gives the cache a carrier for changes made through it, while changes made to the database by anything else still wait for the clock.

Stampedes

A popular entry that expires invites every concurrent reader to recompute it at once. Experiment E3 modelled a hot key with a 200 ms recomputation and a 60-second TTL. With no protection, the number of recomputations per expiry grows in proportion to the request rate: 3.06 at 10 requests a second and 1,007.75 at 5,000. A single-flight lock holds recomputation at exactly one per expiry, but at 5,000 requests a second it leaves 993.95 callers blocked behind the recomputation each time. Vattani, Chierichetti and Lowenstein's probabilistic early expiration (XFetch) lets each reader decide to recompute with a probability that rises as expiry approaches, scaled by how long recomputation takes55. With β = 1 it held the average at 2.75 recomputations per expiry at 5,000 requests a second, 366 times fewer than the unprotected cache, firing on average 1.525 seconds before expiry, so nobody waited (Figure 6). Go's singleflight package is the lock in library form56; memcache leases double as a stampede limiter because the cache hands out only one token per key at a time36.

Refresh-ahead

Refresh-ahead reloads an entry in the background when it is read after a set fraction of its lifetime. Coherence configures this as a refresh-ahead factor: at 0.5 with a 20-second expiry, an entry read in its last 10 seconds is refreshed asynchronously while the current value is returned52. Caffeine offers the same behaviour through refreshAfterWrite48. Experiment E5 ran it over 10,000 keys at 1,000 requests a second with a 60-second TTL. A factor of 0.5 cut the share of requests that had to wait for a load from 11.199% to 5.077% (54.7% fewer) at the cost of 55.1% more loads in total; a factor of 0.75 cut waiting misses by 40.2% for 21% more load (Figure 7). Refresh-ahead only helps keys read inside their refresh window, so the long tail of rarely read keys still misses, and every refresh spent on a key nobody reads again is load bought for nothing. It also shortens the average age of what is served. It does not change the carrier: staleness is still bounded by a clock.

Negative caching, near caches and the HTTP cache

Three more read-path patterns complete the family. Negative caching stores the fact that a key does not exist, protecting the database from repeated lookups for missing keys; a Bloom filter does the same in less space at the price of occasional false positives, each costing one unnecessary lookup57. A near cache keeps an in-process copy in front of a remote cache. Redis 6 introduced server-assisted client-side caching, in which the server remembers which keys each client has read and pushes invalidation messages when they change, and a client that loses its invalidation connection is expected to flush its local copies58. That last rule is what makes the near cache heal rather than go silent. The HTTP cache is the largest deployment of time as a carrier: RFC 9111 governs freshness lifetimes for browsers, proxies and content delivery networks59, and RFC 5861's stale-while-revalidate extension lets a cache serve a stale response while it fetches a fresh one, which is refresh-ahead expressed as a header60.

05Caching on the write path

Write-path patterns decide what happens to the cache when data changes through it. In write-through, a put does not return until the cache's writer has stored the value in the backing store. Coherence describes exactly this52; Hazelcast treats a MapStore with write-delay-seconds of zero as write-through, and propagates any exception from the store to the original caller53. DynamoDB Accelerator writes through to DynamoDB and updates its item cache on success54. The cache and the store agree whenever the call succeeds, and when the store is unavailable the write fails. That is the refusal residue: nothing diverges, and availability pays.

Write-behind reverses the order. The cache acknowledges the write immediately and a queue stores it later, usually in batches. Any positive write-delay-seconds turns a Hazelcast map store into write-behind, and by default Hazelcast coalesces updates so that only the latest value for each key is written53,62:

Write-behind is the only caching pattern in which the copy is ahead of its authority. During the delay, the cache is the sole holder of acknowledged writes. Experiment E4 measured both sides of that bargain with 1,000 writes a second over 100,000 Zipf-distributed keys. Flushing every second saved 36.4% of database writes through coalescing and exposed a mean of 504.7 acknowledged writes to a crash. Flushing every 120 seconds saved 76.3%, only 39.9 percentage points more, while the mean exposure grew to 61,879.3, 122.6 times as many (Figure 8). Relief grows with the logarithm of the delay, because coalescing only helps keys that are written more than once per interval and the Zipf tail is written rarely; exposure grows linearly. Replicating the write-behind queue to other members narrows the window to the failure of the whole grid rather than one member, but it does not change the residue: whatever is in the queue when the last copy dies is gone.

Write-around sends writes straight to the store and lets the cache fill only on reads, which keeps write-once data that is rarely reread from displacing useful entries. On its own it gives the cache no way to learn of a change, so it relies on expiry; add an invalidation and it becomes cache-aside.

06Derived views

A materialized view is a query result kept as a table. The carrier question splits the family in two. PostgreSQL's materialized views are recomputed on demand: REFRESH MATERIALIZED VIEW replaces the contents, and the CONCURRENTLY option, which requires a unique index on the view, lets readers keep querying the old contents while the new ones are computed63. The carrier is a schedule, typically a cron job, and a failed refresh leaves the view stale until the next one succeeds. Microsoft's Materialized View pattern describes the same trade for stores without native support: pre-computed, query-shaped data, regenerated by a process that runs when the source changes or on a schedule64.

SQL Server's indexed views take the other branch. A view created WITH SCHEMABINDING and given a unique clustered index is stored, and the engine maintains it as part of every statement that modifies its base tables65. Oracle offers the same through fast refresh on commit66. The copy cannot disagree with its source because it changes in the same transaction, which is the incremental maintenance that Blakeley, Larson and Tompa described in 19869. The price is paid by writers: every insert into the base table also updates the aggregate row, and concurrent writers to the same group contend for it.

Between those poles sit the denormalised copies that non-relational stores encourage. Microsoft's Index Table pattern creates tables keyed by a secondary attribute and pointing back to the primary data, maintained by the application, and warns that keeping them consistent with the base data is the application's job67. DynamoDB's global secondary indexes move that work into the database but support only eventually consistent reads68. Apache Cassandra's materialized views are the cautionary tale. Introduced to let the server maintain a table keyed differently from its base, they were marked experimental in 3.0.16 and 3.11.2 and gained a configuration flag to disable them69. Microsoft's guidance for its managed Cassandra service lists the reasons plainly: there is no way to tell whether a view is out of sync with its base table, no upper bound on how long synchronisation takes, and no repair other than dropping and recreating the view70. A server-side carrier without an ordered, resumable record is still a silent one.

A search index fed from the database is the log-carried version. A change data capture connector reads committed changes from the database's replication log, PostgreSQL's logical decoding for example71, and a consumer writes them to the index. Elasticsearch itself adds a second, bounded delay because newly indexed documents become searchable only at the next refresh, by default once a second72. If the consumer stops, it resumes from its recorded position and the index catches up. 07Replicas, shards and quorums

Replication is the second copy at database scale, and the choice between synchronous and asynchronous replication is the carrier choice in its purest form. PostgreSQL replicates asynchronously by default. With synchronous_commit set to remote_apply, a commit waits until a synchronous standby has applied it, so a read on that standby sees the commit; if no synchronous standby is available, commits wait74. Google's Spanner commits through Paxos groups across replicas and pays for it in commit latency75. The asynchronous replica is the other residue. Reads from it can miss the reader's own recent writes, the session guarantee that Terry and colleagues named read-your-writes in 199476, and if the primary fails and a lagging replica is promoted, writes the old primary acknowledged but had not shipped are gone. That is the second of only two patterns in the census that can lose acknowledged writes, and for the same structural reason as write-behind: authority can move to a copy that is behind.

Leaderless replication, as in Dynamo, writes to N replicas and considers a write successful when W acknowledge; reads consult R; stragglers are repaired by hinted handoff, read repair and anti-entropy, and concurrent writes can produce sibling versions that the application must reconcile21. Bailis and colleagues' probabilistically bounded staleness showed how to quantify, for partial quorums, the probability that a read returns a value older than the latest write77.

Sharding partitions data rather than copying it, but it still depends on a copy: every router and client holds a copy of the placement map that says which shard owns which key. Microsoft's Sharding pattern describes lookup, range and hash strategies for that map78; MongoDB keeps it on config servers and routes queries through mongos processes, while a balancer moves ranges between shards79. The carrier for the map is a component, and a request routed with an outdated map is caught by version checks on the shard and retried after a refresh, so the residue is refusal rather than a wrong answer. How much data moves when the map changes depends on the placement function. Experiment E7 placed 60,000 keys on 10 nodes and added an eleventh. Modulo placement moved 91.05% of the keys. Consistent hashing14 with a single point per node moved 22.25% here, 2.45 times the ideal, and left the busiest node carrying 3.365 times the mean load; with 500 virtual nodes per server the imbalance fell to 1.123. Rendezvous hashing15 moved 9.07% against an ideal of 9.09% with a maximum-to-mean load of 1.03. In every hashing scheme, no key moved between two of the original nodes (Figure 9).

08Polyglot persistence and the integration patterns

Polyglot persistence is the decision to use several storage technologies inside one system, each chosen for how its data is manipulated: relational tables for orders, a document store for catalogues, a graph for recommendations, a search engine for text29,30. The decision itself says nothing about how the stores stay consistent. That is left to a family of integration patterns, and the carrier axis ranks them sharply.

The simplest is the dual write: the application writes to the database and then to the second store. Kleppmann, Beresford and Svingen showed why this goes wrong even without crashes: two clients updating the same record can have their writes applied in one order by the first store and the opposite order by the second, leaving the stores permanently inconsistent with no error anywhere81. Lamport's 1978 analysis of event ordering is the underlying reason: without a shared ordering mechanism, independent processes have no agreed order to apply82. Experiment E6 measured the effect on 1,000 Zipf-distributed keys. With no crashes at all, dual writes left 0.75 divergent keys per 10,000 updates at 100 updates a second, 4.25 at 1,000 and 19.6 at 5,000, a 26.1-fold rise that tracks concurrency. Adding a crash between the two writes once in every 10,000 updates changed these figures by less than their run-to-run noise (4.3 at 1,000 a second). Ordering, not crashing, produces nearly all the divergence (Figure 10).

The transactional outbox removes the second independent write. The service writes its business change and an event row into an outbox table in the same local transaction, and a relay publishes the outbox rows in commit order83. Debezium's outbox event router reads the outbox table from the database's change stream and routes each row to a Kafka topic named by its aggregate type40. In E6 the outbox relay produced zero divergent keys at every rate, at the cost of a lag set by the relay's polling interval: a median of 49.9 ms and a 99th percentile of 99.1 ms in the model. Delivery is at least once, so consumers must be idempotent, which the model reproduced by delivering duplicates and applying them by version.

Change data capture generalises the outbox by treating the database's own replication log as the carrier for every derived copy35,71. Kafka's log compaction, which retains at least the latest record for each key, lets such a log double as a durable snapshot from which a new consumer can build its copy from scratch84. The saga handles the case where a business operation must change several services' own data. It runs a sequence of local transactions and, when one fails, executes compensating transactions for the steps already completed11,85. Its messages are usually carried by a log, so the individual steps resume after a crash, but the copies it coordinates are not guaranteed to converge: compensations are semantic rather than rollbacks, intermediate states are visible to other transactions because sagas give up isolation, and a compensation that cannot be performed leaves the services disagreeing until someone intervenes39. It is the one log-carried pattern in the census coded silent.

09Ownership, the log and CQRS

The last family concerns who owns data at all. A shared database used by several services gives them transactional consistency across each other's data for free, and Richardson lists the cost as coupling: schema changes need coordination and one service's load can block another's86. Database per service makes each service the only writer of its data; others see it through its API or keep local copies built from its events87. That trades refusal for healing: a consumer that falls behind catches up from the event stream.

Event sourcing inverts the authority. The append-only sequence of events is the source, and the current state of an entity is derived by folding over its events31,88. Appending is the commit, and stores built for the purpose, such as KurrentDB, reject an append whose expected stream version no longer matches, so a concurrent writer is refused rather than silently overwritten43. CQRS separates the model that accepts commands from the models that answer queries32,89, and in the common event-sourced form the query models are projections built by consumers of the event log. Fowler's warning that CQRS adds risky complexity for most systems is worth repeating before anyone adopts it90.

The characteristic CQRS failure is not divergence but delay: a user submits a change and the next page, read from a projection, does not show it. Experiment E8 modelled projection lag as log-normal with a median of 40.1 ms and a rare multi-second stall. A read issued immediately after the write misses it 100% of the time by construction; after 50 ms, 41.191% of the time; after 200 ms, 5.572%; after one second, 0.268% (Figure 11). Returning a version token with each command and having the query side wait until its projection has reached that version, capped at one second, cost a median wait of 40.1 ms and a 99th percentile of 444.4 ms, and fell back to reading the write model for the 0.268% of requests that hit the cap. This is read-your-writes implemented on top of a log76.

The Lambda architecture keeps two copies of every derived view, one recomputed by batch jobs over the complete dataset and one maintained by a stream processor to cover the gap until the next batch run91. Kreps's Kappa proposal of 2014 argued for dropping the batch layer and reprocessing by replaying the log through a new version of the stream job92. On the carrier axis that is a move from a schedule to a log, and both heal.

10What the census shows

Figure 12 places all 28 plates on the two axes. Three regularities stand out, and the first is the headline.

The writer never supplies healing. Every pattern in which the calling code writes the copy as a separate step (cache-aside, the application-maintained index table, polyglot persistence left to the application, and the dual write) is caller-carried, and 3 of those 4 are silent when the step fails. Cache-aside is the exception only because a time-to-live stands behind it; take the TTL away and it joins the others. By contrast, of the 14 patterns carried asynchronously by something other than the caller (a clock, a scheduled job or a log), 12 heal. The two exceptions are instructive: the asynchronous replica can lose writes when authority moves to it, and the saga coordinates compensations that can themselves fail.

Synchronous carriers mostly refuse. Of the 10 patterns carried synchronously by a component or by the commit, 6 protect agreement by failing or blocking writes. This is the consistency-for-availability and consistency-for-latency trade that CAP and PACELC describe23,25, visible here at the level of individual patterns. The exceptions are the near cache, which heals because its protocol flushes on disconnect; write-behind, which loses; and the server-maintained view and the leaderless quorum, which are silent.

Loss requires the copy to lead. Only 2 patterns can lose acknowledged writes, write-behind and the asynchronous replica, and in both the copy that holds the latest acknowledged writes is, for a moment, not the one that survives.

The two axes together separate 91.8% of the 378 pairs of plates, against 85.7% for the conventional grouping by family, and 13 of the 24 possible cells are occupied. The coding is the author's, made from the cited documentation, and a different reader could reasonably move a plate or two. The regularities above do not depend on any single borderline case.

11Choosing a pattern by its carrier

The census suggests an order of questions that is more useful than a list of pros and cons. Start with the residue you can afford. If a stale value is acceptable for a known interval, time is the cheapest carrier there is, and the only engineering is choosing the interval and protecting the expiry moment from stampedes. If stale values are not acceptable but occasional refusals are, put the copy in the commit, or behind a component that fails the write when it cannot update both. If neither staleness nor refusal is acceptable at scale, the honest answer is that no pattern delivers that, and the requirement needs to be negotiated.

Then look for any place where the calling code is the carrier. Every such place is a silent-failure site, and the census says it will stay one. The standard repairs all replace the caller with something else: leases or a transaction-aware cache manager for cache-aside, an outbox or change data capture for the dual write, and a log-fed consumer instead of an application-maintained index. Where a caller-carried copy remains, give it a clock as a backstop, as cache-aside does, and a reconciliation job that compares copy and source, as Meta's work on cache consistency shows is necessary even at ten nines1.

Finally, check which copy holds acknowledged writes at every instant. Wherever it is not the durable authority, as in write-behind and asynchronous failover, the loss window is a design parameter and should be written down as one: E4's flush interval and the replication lag at failover are the numbers to put in the runbook.

13Method and limitations

The lab. Every number quoted in this article comes from a single Python script that uses only the standard library, with a fixed seed of 20260928. It runs eight experiments and the census, prints the output reproduced below, and writes the same values to a results file that the build reads when it assembles the page, so no figure in the prose was typed by hand. The script avoids any iteration over unordered sets, and its output was byte-identical when run under different hash seeds. E1 simulates an LRU cache over 20,000 keys with Zipf popularity and compares it with Che's approximation16,17. E2 is an event-driven model of a single key read 100 times a second, with a time-to-live of 600 seconds and heavy-tailed pauses between a reader's database read and its cache fill; it counts stale intervals longer than one second after each write under five write-side strategies. E3 models expiry of a hot key whose recomputation takes 200 ms under naive recomputation, a single-flight lock and probabilistic early expiration55. E4 replays 1,000 Zipf-distributed writes a second against a write-behind queue and counts coalesced writes and the writes held in the queue at a random crash. E5 measures synchronous misses and background loads for refresh-ahead factors. E6 applies the same writes to two stores with independent, exponentially distributed apply delays, with and without dropped second writes, and compares an outbox relay that applies changes in commit order. E7 places 60,000 keys with MD5-derived hashes on 10 and then 11 nodes. E8 draws projection lag from a log-normal distribution with a median of 40 ms plus a rare multi-second tail, and asks how often a user's own write is invisible on the next read.

What the models leave out. These are models, chosen to isolate one mechanism each, and the absolute values depend on their parameters. E2 has one key and a single pause distribution; real stale rates depend on how often readers stall between reading and filling, which is rarely measured. E4 assumes a crash at a uniformly random moment and ignores replication of the queue. E6's divergence comes only from reordering between two stores, the most benign way a dual write fails; network partitions and partial failures would add to it. E8's tail is invented to show the effect of a tail, not estimated from any system. The relationships the article relies on (orders of magnitude between strategies, the growth of divergence with write rate, logarithmic relief against linear exposure) are more robust than the individual values.

Coding the plates. The carrier and residue codes are judgements, made by one author against the definitions in section 3 and the cited documentation, and a different reader could code a few plates differently. Near cache, leaderless quorum and write-around are the least certain; recoding any one of them moves the census tallies by one without changing the regularities in section 10. The census is a count of named patterns, not of deployments, and the families were chosen to cover the patterns the request named, not sampled from a population. Gauge windows are illustrative ranges for typical configurations and are drawn on a shared logarithmic axis so that plates can be compared; they are not measurements. def zipf_cdf(n, a):
    w = [1.0 / (i + 1) ** a for i in range(n)]
    s = sum(w)
    c, acc = [], 0.0
    for x in w:
        acc += x / s
        c.append(acc)
    c[-1] = 1.0
    return c, [x / s for x in w]

def draw(cdf, rng):
    return bisect.bisect_left(cdf, rng.random())

def e1():
    log("E1  Cache-aside capacity: LRU hit ratio under Zipf popularity, simulated and by Che's approximation")
    rng = random.Random(SEED + 1)
    N, R, WARM = 20000, 240000, 60000
    fracs = [0.005, 0.01, 0.02, 0.05, 0.10, 0.20]
    alphas = [0.6, 0.8, 1.0]
    table = {}
    maxdiff = 0.0
    for a in alphas:
        cdf, p = zipf_cdf(N, a)
        row = []
        for f in fracs:
            C = int(N * f)
            cache = OrderedDict()
            hits = n = 0
            for i in range(R):
                k = draw(cdf, rng)
                if k in cache:
                    cache.move_to_end(k)
                    if i >= WARM:
                        hits += 1
                else:
                    cache[k] = 1
                    if len(cache) > C:
                        cache.popitem(last=False)
                if i >= WARM:
                    n += 1
            sim = hits / n
            lo, hi = 0.0, 25.0
            for _ in range(48):
                T = math.exp((lo + hi) / 2)
                occ = sum(1 - math.exp(-q * T) for q in p)
                if occ > C:
                    hi = (lo + hi) / 2
                else:
                    lo = (lo + hi) / 2
            T = math.exp((lo + hi) / 2)
            che = sum(q * (1 - math.exp(-q * T)) for q in p)
            maxdiff = max(maxdiff, abs(che - sim))
            row.append((f, round(sim, 4), round(che, 4)))
            log(f"    alpha={a:.1f} cache={f*100:5.1f}% of keys  sim={sim*100:6.2f}%  che={che*100:6.2f}%")
        table[str(a)] = row
    put("E1.table", table)
    put("E1.maxdiff_pts", round(maxdiff * 100, 2))
    a08 = {r[0]: r[1] for r in table["0.8"]}
    put("E1.a08_1pct", round(a08[0.01] * 100, 1))
    put("E1.a08_10pct", round(a08[0.10] * 100, 1))
    put("E1.a08_20pct", round(a08[0.20] * 100, 1))
    a10 = {r[0]: r[1] for r in table["1.0"]}
    a06 = {r[0]: r[1] for r in table["0.6"]}
    put("E1.a10_1pct", round(a10[0.01] * 100, 1))
    put("E1.a06_1pct", round(a06[0.01] * 100, 1))

def e2_run(strat, WRITE_GAP, NW, TTL=600000.0, READ_RATE=0.1):
    rng = random.Random(SEED + 2)
    ev = []
    seq = [0]
    def push(t, kind, data=None):
        seq[0] += 1
        heapq.heappush(ev, (t, seq[0], kind, data))
    def db_read_latency():
        base = rng.lognormvariate(math.log(4.0), 0.5)
        if rng.random() < 0.02:
            base += min(5000.0, 50.0 * rng.paretovariate(1.2))
        return base
    st = {"db": 0, "cache": None, "lease": None, "lease_ctr": 0, "pending": False, "stale_start": None}
    episodes = []
    tw = 0.0
    for i in range(NW):
        tw += rng.expovariate(1.0 / WRITE_GAP)
        push(tw, "write_start")
    horizon = tw + 1000.0
    def schedule_reader(now):
        if not st["pending"]:
            st["pending"] = True
            push(now + rng.expovariate(READ_RATE), "read")
    def check_stale(now):
        c = st["cache"]
        stale = c is not None and c[1] > now and c[0] != st["db"]
        if stale and st["stale_start"] is None:
            st["stale_start"] = now
        if not stale and st["stale_start"] is not None:
            episodes.append(now - st["stale_start"])
            st["stale_start"] = None
    def set_cache(v, now):
        st["cache"] = (v, now + TTL)
        push(now + TTL, "tick")
        check_stale(now)
    def invalidate(now):
        st["cache"] = None
        st["lease"] = None
        check_stale(now)
        schedule_reader(now)
    schedule_reader(0.0)
    t = 0.0
    while ev:
        t, _, kind, data = heapq.heappop(ev)
        if t > horizon:
            break
        c = st["cache"]
        if c is not None and c[1] <= t:
            st["cache"] = None
            check_stale(t)
            schedule_reader(t)
        if kind == "read":
            st["pending"] = False
            c = st["cache"]
            if c is None or c[1] <= t:
                tok = None
                if strat == "lease":
                    if st["lease"] is None:
                        st["lease_ctr"] += 1
                        st["lease"] = st["lease_ctr"]
                        tok = st["lease"]
                    else:
                        schedule_reader(t)
                        continue
                push(t + db_read_latency(), "db_read_done", (st["db"], tok))
                schedule_reader(t)
        elif kind == "db_read_done":
            push(t + rng.expovariate(1.0 / 0.5), "cache_set", data)
        elif kind == "cache_set":
            v, tok = data
            if strat == "lease":
                if tok is not None and tok == st["lease"]:
                    st["lease"] = None
                    set_cache(v, t)
            else:
                set_cache(v, t)
        elif kind == "write_start":
            if strat == "delete_before":
                invalidate(t)
            push(t + rng.expovariate(1.0 / 5.0), "commit")
        elif kind == "commit":
            st["db"] += 1
            check_stale(t)
            if strat in ("delete_after", "double_delete", "lease"):
                push(t + rng.expovariate(1.0), "delete")
                if strat == "double_delete":
                    push(t + 500.0, "delete")
            elif strat == "update_after":
                push(t + rng.expovariate(1.0), "set_new", st["db"])
        elif kind == "delete":
            invalidate(t)
        elif kind == "set_new":
            set_cache(data, t)
    if st["stale_start"] is not None:
        episodes.append(t - st["stale_start"])
    longs = [e for e in episodes if e > 1000.0]
    return {
        "long_per_1000w": round(len(longs) / NW * 1000, 3),
        "mean_long_s": round(statistics.mean(longs) / 1000, 1) if longs else 0.0,
        "stale_time_ppm": round(sum(longs) / horizon * 1e6, 1),
    }

def e3():
    log("E3  Stampede at expiry: naive recompute, single-flight lock, probabilistic early expiry (XFetch, beta=1)")
    delta, T = 0.2, 60.0
    out = {}
    for lam, cycles in [(10, 400), (100, 300), (1000, 120), (5000, 40)]:
        rng = random.Random(SEED + 3 + lam)
        naive, locked_wait, xf, xf_early, lock_frac = [], [], [], [], []
        for c in range(cycles):
            E = 0.0
            # naive: requests after expiry until first recompute lands
            t = E + rng.expovariate(lam)
            first = t
            cnt = 0
            while t < first + delta:
                cnt += 1
                t += rng.expovariate(lam)
            naive.append(cnt)
            # lock: one recompute; count waiters
            t = first
            w = 0
            while t < first + delta:
                w += 1
                t += rng.expovariate(lam)
            locked_wait.append(w - 1)
            # xfetch over window [E - 25*delta, E + ...]
            t = E - 25 * delta + rng.expovariate(lam)
            trig = None
            n = 0
            while True:
                if trig is not None and t >= trig + delta:
                    break
                if t >= E and trig is None:
                    trig = t   # fell through to a true miss
                    n += 1
                    t += rng.expovariate(lam)
                    continue
                u = rng.random()
                if t - delta * math.log(u) >= E and (trig is None or t < trig + delta):
                    if trig is None:
                        trig = t
                    n += 1
                t += rng.expovariate(lam)
            xf.append(n)
            xf_early.append(E - trig)
        # requests per cycle ~ lam*T
        out[str(lam)] = {
            "naive": round(statistics.mean(naive), 2),
            "lock": 1.0,
            "lock_waiters": round(statistics.mean(locked_wait), 2),
            "xfetch": round(statistics.mean(xf), 3),
            "xfetch_early_s": round(statistics.mean(xf_early), 3),
            "lock_wait_share_ppm": round(statistics.mean(locked_wait) / (lam * T) * 1e6, 1),
        }
        o = out[str(lam)]
        log(f"    rate={lam:5d}/s  naive={o['naive']:8.2f} recomputes/expiry  lock=1 with {o['lock_waiters']:7.2f} blocked callers   "
            f"xfetch={o['xfetch']:6.3f} recomputes, fired {o['xfetch_early_s']:.3f} s early")
    put("E3", out)
    log("")

def e4():
    log("E4  Write-behind: database relief from coalescing against acknowledged writes exposed to a crash")
    rng0 = random.Random(SEED + 4)
    K, lam, H = 100000, 1000.0, 600.0
    cdf, _ = zipf_cdf(K, 0.99)
    times, keys = [], []
    t = 0.0
    while True:
        t += rng0.expovariate(lam)
        if t > H:
            break
        times.append(t)
        keys.append(draw(cdf, rng0))
    NWR = len(times)
    out = {}
    for F in [0.1, 1.0, 5.0, 30.0, 120.0]:
        flushed = 0
        dirty = {}
        nxt = F
        for tt, k in zip(times, keys):
            while tt >= nxt:
                flushed += len(dirty)
                dirty = {}
                nxt += F
            dirty[k] = 1
        flushed += len(dirty)
        rng = random.Random(SEED + 40)
        lost = []
        for _ in range(400):
            crash = rng.uniform(F, H)
            last = math.floor(crash / F) * F
            lo = bisect.bisect_left(times, last)
            hi = bisect.bisect_left(times, crash)
            lost.append(hi - lo)
        out[str(F)] = {
            "db_writes_per_update": round(flushed / NWR, 4),
            "relief_pct": round((1 - flushed / NWR) * 100, 1),
            "mean_lost": round(statistics.mean(lost), 1),
            "p99_lost": sorted(lost)[int(0.99 * len(lost)) - 1],
        }
        o = out[str(F)]
        log(f"    flush={F:6.1f} s  db writes per update={o['db_writes_per_update']:.4f} (relief {o['relief_pct']:5.1f}%)  "

    r1, r120 = out["1.0"], out["120.0"]
    put("E4.loss_ratio_1_120", round(r120["mean_lost"] / r1["mean_lost"], 1))
    log("")

    cdf, _ = zipf_cdf(N, 0.9)

            t += rng.expovariate(lam)
            if t > H:
                break

            if t < 120.0:
                warm = True
            else:
                warm = False

            if e is not None and e[1] is not None and t >= e[1]:
                e[0] = e[1]
                e[1] = None
            if e is None or t - e[0] >= T:
                if not warm:
                    miss += 1
                store[k] = [t + load_lat, None]
                if not warm:
                    n += 1
                    age_sum += 0.0
                continue
            if f is not None and e[1] is None and t - e[0] >= f * T:
                e[1] = t + load_lat
                if not warm:
                    bg += 1
            if not warm:
                n += 1
                age_sum += t - e[0]
        dur = H - 120.0
        key = "none" if f is None else str(f)
        out[key] = {
            "miss_pct": round(miss / n * 100, 3),

    log("")

                    total += 1
                # dual write: final value per key = last by apply time in each store
                def final(evs):
                    d = {}
                    for tt, k, v in sorted(evs):
                        d[k] = v
                    return d
                fa, fb = final(a_ev), final(b_ev)
                for k in range(K):
                    if fa.get(k) != fb.get(k):
                        div_dual += 1
                # outbox: relay applies in A-commit order, at least once
                a_sorted = sorted(a_ev)
                relay_t = 0.0
                fo = {}
                for tt, k, v in a_sorted:
                    relay_t = max(relay_t, tt) + rng.expovariate(1 / 0.05)
                    apply_t = relay_t + rng.uniform(0, 100.0)  # poll interval
                    lags.append(apply_t - tt)
                    fo[k] = v
                    if rng.random() < 0.01:   # duplicate delivery, idempotent by version
                        fo[k] = v
                for k in range(K):
                    if fa.get(k) != fo.get(k):
                        div_outbox += 1
            lags.sort()
            key = f"{int(lam)}_{pfail}"
            out[key] = {
                "dual_per_10k": round(div_dual / total * 10000, 2),
                "outbox_per_10k": round(div_outbox / total * 10000, 2),
                "lag_p50_ms": round(lags[len(lags) // 2], 1),
                "lag_p99_ms": round(lags[int(len(lags) * 0.99)], 1),
            }
            o = out[key]
            log(f"    rate={int(lam):5d}/s  crash between writes p={pfail:g}  dual-write divergent keys per 10k updates={o['dual_per_10k']:7.2f}  "
                f"outbox={o['outbox_per_10k']:.2f}  outbox lag p50={o['lag_p50_ms']} ms p99={o['lag_p99_ms']} ms")
    put("E6", out)
    log("")

def h64(s):
    return int.from_bytes(hashlib.md5(s.encode()).digest()[:8], "big")

def e7():
    log("E7  Resharding 10 -> 11 nodes: modulo placement, consistent hashing with virtual nodes, rendezvous hashing")
    NK = 60000
    kh = [h64(f"key:{i}") for i in range(NK)]
    out = {}
    def mod_assign(n):
        return [x % n for x in kh]
    a10, a11 = mod_assign(10), mod_assign(11)
    moved = sum(1 for x, y in zip(a10, a11) if x != y) / NK
    loads = [0] * 10
    for x in a10:
        loads[x] += 1
    out["modulo"] = {"moved_pct": round(moved * 100, 2), "max_over_mean": round(max(loads) / (NK / 10), 3)}
    for v in [1, 10, 100, 500]:
        def ring(n):
            pts = sorted((h64(f"node{j}#{r}"), j) for j in range(n) for r in range(v))
            hs = [p[0] for p in pts]
            own = [p[1] for p in pts]
            res = []
            for x in kh:
                i = bisect.bisect_left(hs, x)
                res.append(own[i % len(hs)])
            return res
        r10, r11 = ring(10), ring(11)
        moved = sum(1 for x, y in zip(r10, r11) if x != y) / NK
        wrong = sum(1 for x, y in zip(r10, r11) if x != y and y != 10)
        loads = [0] * 10
        for x in r10:
            loads[x] += 1
        out[f"ring_v{v}"] = {"moved_pct": round(moved * 100, 2), "max_over_mean": round(max(loads) / (NK / 10), 3),
                             "moved_not_to_new": wrong}
    # rendezvous
    def hrw(n, keys):
        res = []
        for i in keys:
            best, bj = -1, -1
            for j in range(n):
                s = h64(f"{i}|node{j}")
                if s > best:
                    best, bj = s, j
            res.append(bj)
        return res
    ks = list(range(NK))
    w10, w11 = hrw(10, ks), hrw(11, ks)
    moved = sum(1 for x, y in zip(w10, w11) if x != y) / NK
    wrong = sum(1 for x, y in zip(w10, w11) if x != y and y != 10)
    loads = [0] * 10
    for x in w10:
        loads[x] += 1
    out["rendezvous"] = {"moved_pct": round(moved * 100, 2), "max_over_mean": round(max(loads) / (NK / 10), 3),
                         "moved_not_to_new": wrong}
    for k, o in out.items():
        log(f"    {k:11s} keys moved={o['moved_pct']:6.2f}%  max/mean load at 10 nodes={o['max_over_mean']:.3f}"
            + (f"  moved between old nodes={o['moved_not_to_new']}" if 'moved_not_to_new' in o else ""))
    put("E7", out)
    put("E7.ideal_moved_pct", round(100 / 11, 2))
    put("E7.nkeys", NK)
    log(f"    ideal minimum moved = 1/11 = {100/11:.2f}%")
    log("")

def e8():
    log("E8  CQRS read model: probability a user's own write is invisible on the next read")
    rng = random.Random(SEED + 8)
    S = 200000
    lags = []
    for _ in range(S):
        L = rng.lognormvariate(math.log(40.0), 1.0)
        if rng.random() < 0.002:
            L += rng.uniform(2000, 20000)
        lags.append(L)
    lags_sorted = sorted(lags)
    out = {"lag_p50_ms": round(lags_sorted[S // 2], 1), "lag_p99_ms": round(lags_sorted[int(S * .99)], 1),
           "lag_p999_ms": round(lags_sorted[int(S * .999)], 1)}
    gaps = [0.0, 50.0, 200.0, 1000.0, 5000.0]
    tab = {}
    for g in gaps:
        stale = sum(1 for L in lags if L > g) / S
        tab[str(int(g))] = round(stale * 100, 3)
        log(f"    read {int(g):5d} ms after the write: stale with probability {stale*100:7.3f}%")
    out["stale_pct"] = tab
    # version-token wait capped at 1 s
    cap = 1000.0
    waits = sorted(min(L, cap) for L in lags)
    fall = sum(1 for L in lags if L > cap) / S
    out["token_wait_p50_ms"] = round(waits[S // 2], 1)
    out["token_wait_p99_ms"] = round(waits[int(S * .99)], 1)
    out["token_fallback_pct"] = round(fall * 100, 3)
    log(f"    version token, wait capped at 1 s: wait p50={out['token_wait_p50_ms']} ms p99={out['token_wait_p99_ms']} ms, "
        f"falls back to the write model {out['token_fallback_pct']}% of the time")
    log(f"    lag p50={out['lag_p50_ms']} p99={out['lag_p99_ms']} p99.9={out['lag_p999_ms']} ms")
    put("E8", out)
    log("")

def census():
    log("C   Census of the plates: carrier rung x what a broken carrier leaves behind")
    d = json.load(open("census.json"))
    P = d["plates"]
    rungs, fails = d["rungs"], d["failures"]

    for p in P:
        grid[p[3]][p[4]].append(p[0])
    for r in rungs:
        log("    " + r + "  " + "  ".join(f"{f}:{len(grid[r][f])}" for f in fails))

    rc = {r: sum(1 for p in P if p[3] == r) for r in rungs}
    caller = [p for p in P if p[3] == "P1"]
    caller_S = [p[0] for p in caller if p[4] == "S"]
    heal = [p for p in P if p[4] == "H"]

    async_nc_H = sum(1 for p in async_nc if p[4] == "H")
    sync = [p for p in P if p[3] in ("P2", "P5")]
    sync_B = sum(1 for p in sync if p[4] == "B")
    W = [p[0] for p in P if p[4] == "W"]
    S = [p[0] for p in P if p[4] == "S"]
    # separation of pairs
    pairs = sep_rf = sep_fam = 0
    for i in range(n):
        for j in range(i + 1, n):
            pairs += 1
            if (P[i][3], P[i][4]) != (P[j][3], P[j][4]):
                sep_rf += 1
            if P[i][1] != P[j][1]:
                sep_fam += 1
    occ = sum(1 for r in rungs for f in fails if grid[r][f])
    res = {"n": n, "fail_counts": fc, "rung_counts": rc, "grid": grid,
           "caller_n": len(caller), "caller_S": caller_S, "caller_S_n": len(caller_S),

           "sync_n": len(sync), "sync_B": sync_B, "W": W, "S": S,
           "pairs": pairs, "sep_rf_pct": round(sep_rf / pairs * 100, 1), "sep_fam_pct": round(sep_fam / pairs * 100, 1),
           "cells_occupied": occ, "cells": len(rungs) * len(fails)}
    log(f"    plates={n}  heal={fc['H']} refuse={fc['B']} silent={fc['S']} lose={fc['W']}")

    log(f"    synchronous carriers (P2,P5): {sync_B} of {len(sync)} refuse")

    put("C", res)
    log("")
