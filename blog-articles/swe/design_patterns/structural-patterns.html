1The question

Four of the seven structural patterns in the 1994 catalogue have the same class diagram. A client holds a reference typed to some interface; behind that interface sits an object that holds a reference to another object and passes calls along to it. Draw Adapter, Bridge, Decorator and Proxy with the names rubbed off and they cannot be told apart. The authors knew this. Their own discussion of the structural patterns concedes the resemblance and separates the patterns by what each is for rather than by how it is built1. Three decades later, tools that try to find patterns in source code inherit the same difficulty: a detector that looks only at structure has to fall back on names, call sequences or behaviour to decide which of several look-alikes it is looking at2,3.

This article takes the difficulty as its subject. It proposes that the structural patterns are best read not as shapes but as contracts about ignorance. Each one places something between a client and the thing the client uses, and each licenses the client to stay ignorant of one specific fact. An adapter lets the client ignore that the capability comes from a class with a foreign interface. A facade lets it ignore how a subsystem is assembled. A bridge lets it ignore which implementation stands behind an abstraction; a composite, whether it holds one thing or a tree; a decorator, that responsibilities have been added; a proxy, where the subject lives, when it is created, or whether the caller may touch it; and a flyweight, that the instance it holds is shared with thousands of others.

Framed that way the organising question becomes empirical. What is the client allowed not to know, and does the ignorance hold? A contract about ignorance can be tested, because every interposed object exposes channels through which a client could, if it tried, tell that it is not holding the thing itself: the object's class, its identity, how it compares for equality, how it prints, which attributes it carries, which language protocols it honours, and what calling it does to the world. Section 4 turns those channels into a battery of eight tell-tale lamps and runs it against 26 concrete interposed objects in Python, eight of them built directly from standard-library objects. Sections 5 to 11 go through the seven patterns in turn, each with its history, its appearances across Java, C#, C++, Go, Rust, Kotlin, TypeScript and Python, a set of plates carrying the battery's reading for each variant, and a measurement of the quantity that the pattern hides.

Three findings organise what follows. First, the lamps sort by mechanism, not by name. Two interposed objects from the same pattern differ on 2.88 of eight channels on average; two from different patterns differ on 3.38, barely more. Two of the three pairs with identical readings cross pattern boundaries: an object adapter reads exactly like weakref.proxy, and a transparent composite exactly like a subclass extension. The pattern name records intent; what the client can observe is fixed by lower-level choices about whether a second object exists, whether calls are forwarded by name or by protocol, and whether anyone wrote an equality method. Second, two channels resist every technique of concealment. A proxy that forwards every special method its target's type defines, unwraps its arguments and lies about its class still lights exactly two lamps, type() and is; the one plate in the battery that goes fully dark is a handle-and-body pair, which hides a relationship behind an object rather than an object behind another. Third, what the patterns hide is usually a quantity, not a name: cost, time, order and location. The lab puts numbers on each. Lazy loading through proxies overtakes an eager join once 1.2% of rows are touched; a caching proxy with a 98.95% hit rate serves stale data on 83.03% of reads; and the same four stream decorators stacked in different orders produce outputs that differ in size by a factor of 5.65.

2Where the patterns came from

The word came from architecture. Christopher Alexander and his colleagues published A Pattern Language in 1977, a set of 253 patterns for towns, buildings and construction, each naming a recurring problem, the forces in tension around it and a solution that resolves them, and each linked to larger and smaller patterns so that the whole could be read as a language4. The Timeless Way of Building (1979) supplied the theory behind it5. Software borrowed the idea a decade later. At OOPSLA in 1987 Kent Beck and Ward Cunningham reported an experiment in which a small pattern language guided novice users to design Smalltalk window interfaces6.

The individual structural patterns predate their names. Smalltalk-80 already had the two primitives on which most of them depend: doesNotUnderstand:, which lets an object receive any message it does not implement and forward it elsewhere, and become:, which swaps the identities of two objects wholesale7. Geoffrey Pascoe's encapsulators (1986) used the first to wrap arbitrary objects with pre- and post-actions8. Henry Lieberman's paper on prototypes the same year distinguished delegation, in which the receiver of a forwarded message still sees the original object as self, from plain forwarding, in which it does not9; that distinction returns in Section 3 as the source of several leaks. Smalltalk's model-view-controller framework nested views inside views, a composite in all but name10.

Proxy has the clearest origin. Marc Shapiro's 1986 paper on the proxy principle, written for distributed systems, argued that a client should first acquire a local object representing a remote service and direct all its communication to it, so that the proxy and the servers behind it form one distributed object that the client cannot decompose11. The remote procedure call had been given its classic implementation two years earlier12. Flyweight has an equally specific birthplace. At Stanford, Paul Calder and Mark Linton made every character in a WYSIWYG document editor an object in the InterViews toolkit, and made that affordable by sharing one object per distinct glyph and passing position in from outside; their 1990 paper called these shared objects flyweights13,14. John Vlissides, who would become the fourth author of the catalogue, had built the Unidraw framework in the same group15. Jim Coplien's 1991 book on C++ idioms supplied handle-and-body, envelope-and-letter and the counted pointer, which became Bridge and the smart-reference kind of Proxy16. Erich Gamma's doctoral thesis on the ET++ framework, completed at Zürich the same year, is the other direct ancestor17.

Gamma, Richard Helm, Ralph Johnson and Vlissides presented a first version of the catalogue at ECOOP in 199318 and published the book at OOPSLA in October 1994, with a 1995 copyright date1. It named 23 patterns and classified them on two axes: purpose (creational, structural or behavioural) and scope (whether the relationships are fixed between classes at compile time or between objects at run time). Seven patterns are structural, and Adapter is the only one that appears in both scopes, as a class adapter built by inheritance and an object adapter built by composition. The first Pattern Languages of Programs conference met the same year and its proceedings followed in 199519. Pattern-Oriented Software Architecture (1996) extended the vocabulary up to architectural scale and gave Proxy its own list of variants20; Vlissides' Pattern Hatching (1998) recorded what the authors had learned from applying their own catalogue21.

The patterns then moved outwards. Martin Fowler's Patterns of Enterprise Application Architecture (2002) recast several of them at the boundary between an application and its data: Gateway is an adapter for an external resource, Remote Facade coarsens an interface for the network, and Lazy Load comes in four variants of which virtual proxy is one22. Eric Evans' anti-corruption layer (2003) is a facade and a set of adapters placed deliberately between one model and another23, and Alistair Cockburn's hexagonal architecture (2005) put the word adapter into the name of an architectural style24. Dissent arrived early. In 1996 Peter Norvig showed that 16 of the 23 patterns have qualitatively simpler implementations in Lisp or Dylan than in C++, at least for some of their uses25, and Paul Graham later suggested that a program full of patterns is a sign that its author is using abstractions that are not powerful enough26. Section 12 returns to both claims, because the structural patterns are exactly where languages have since absorbed the most.

3One skeleton, seven intents

Two principles from the catalogue's first chapter carry the whole structural family: program to an interface, not an implementation, and favour object composition over class inheritance1. Both descend from David Parnas's 1972 argument that a module should be defined by the design decision it hides rather than by a step in the processing27, and both depend on Barbara Liskov's substitution requirement that an object of a subtype be usable wherever the supertype is expected without the program noticing28,29. Composition matters because inheritance exposes a subclass to its parent's implementation, which Alan Snyder identified in 1986 as a breach of encapsulation30 and which later work formalised as the fragile base class problem31.

Composition has its own hazard, and it is the root of most tell-tales in this article. When a wrapper forwards a call to an inner object, the inner object runs with self or this bound to itself, not to the wrapper. Lieberman's delegation binds self to the original receiver; forwarding does not9. So any callback the inner object makes to itself escapes the wrapper. Joshua Bloch calls this the self problem and uses it to explain why wrapper classes do not suit callback frameworks32. Spring's documentation describes the same effect for its proxy-based aspects: a method that calls another method on this bypasses the proxy, so transactional or security advice on the second method silently does not apply33. The client was allowed not to know that a proxy was there, and so, it turns out, was the object behind it.

With the skeleton fixed, the seven intents differ along a small number of dimensions. The first is the relation between the interface the client sees and the interface of the thing behind it. An adapter translates one interface into another. A facade presents a new, narrower interface over many objects. Bridge, Composite, Decorator, Proxy and Flyweight all present the same interface as the thing they stand for, sometimes widened (a buffered stream adds peek) or narrowed (a read-only view removes assignment). The second is the number of things behind the interposed object: one for an adapter, decorator or proxy, many for a facade or composite, and for a flyweight, the reverse, one object behind many logical references. The third is when the structure is bound: at class-definition time for a class adapter or a subclass, at construction for most wrappers, at first use for a virtual proxy or a flyweight factory, and continuously for a composite whose children are added over its lifetime.

The catalogue's own discussion of the structural patterns draws two of these distinctions explicitly. Adapter and Bridge both introduce a level of indirection, but an adapter is applied after two incompatible designs already exist, while a bridge is chosen up front so that an abstraction and its implementations can evolve apart. Composite, Decorator and Proxy share a recursive structure, but a composite exists to aggregate, a decorator to add responsibilities without subclassing, and a proxy to control access to an object that it does not change1. Neither distinction is visible in the code. Both are statements about what the designer intended the client to be able to ignore.

4An instrument for ignorance

If a pattern is a licence to ignore something, the obvious test is to try to find out. The lab in Appendix A builds, for each interposed object, a reference: an object that natively offers the interface the client is written against, with no pattern involved. For a decorator the reference is the undecorated component; for an adapter, a class written directly against the target interface; for a composite, a single leaf of the same total size; for a flyweight, a freshly constructed instance with the same value. The battery then asks, channel by channel, whether a client could observe a difference. A lamp is lit when it could.

Across 26 plates the battery lit 101 of 208 lamps, a mean of 3.88. The most frequently lit channels are name (21 plates), type (20) and identity (15); the least frequently lit is kind (2), which is to say that nominal conformance is the easiest thing to fake and almost every implementation manages it. Equality is lit on 11 plates, nearly always for the same reason: a wrapper that does not define its own equality falls back to identity, so two wrappers around equal subjects compare unequal. That one missing method is the commonest leak in the battery and the cheapest to fix.

The more important result is how little the pattern name predicts. The 23 distinct lamp signatures across 26 plates separate 99.1% of all pairs, so the battery discriminates finely; but within a family the spread is wide. Proxies range from 2 to 7 lamps, adapters from 3 to 7, facades from 2 to 6. The mean Hamming distance between two plates of the same family is 2.88 channels, against 3.38 for plates of different families. Three pairs of plates have identical signatures (A1 and P7, C1 and D5, P2 and P6), and two of those pairs cross family lines. What the client can observe is decided by the mechanism: whether a second object exists, whether calls are forwarded by name or through the language's protocols, whether value semantics were carried across, whether the printed form was considered. The pattern name decides none of these.

Two caveats bound the result. The channels are Python's, and other languages expose different ones: Java has reference equality, getClass() and equals/hashCode; JavaScript has strict equality, instanceof through the prototype chain and property enumeration; C++ has addresses and typeid. The two channels that turn out to be irreducible in Python, type and identity, have counterparts in every one of them, and later sections show that the same leaks recur. And a lit lamp is not a defect. Most decorators light effect because adding an effect is their purpose; a buffered reader lights effect because reducing device reads is its purpose. The battery measures what the client could observe. Whether it should be allowed to is the pattern's business, and the plates say which lamps are intended.

5Adapter: the foreign interface

The catalogue's intent for Adapter is to convert the interface of a class into another interface that clients expect, so that classes with incompatible interfaces can work together1. It is the only structural pattern offered in two scopes. The class adapter inherits from the adaptee and implements the target, so a single object plays both roles; the object adapter holds the adaptee and implements the target by forwarding. The battery makes the difference concrete. The object adapter (plate A1) lights identity because it is a second object standing for the same probe, and it lights equality because nobody thought to define it. The class adapter (A2) keeps identity and equality dark, since there is only one object and it inherits the adaptee's value semantics, but it lights surface: a client holding a class adapter can call the adaptee's own methods and bypass the translation entirely.

The JDK is full of adapters that are not called adapters. Its documentation describes InputStreamReader as a bridge from byte streams to character streams34, a reminder that the vocabulary was never enforced even inside a single library; in the catalogue's terms it translates one interface into another over a single object, which makes it an adapter. Arrays.asList presents an array as a fixed-size list backed by the array, so writes through the list land in the array35. C++ standardises the idea as container adaptors: std::stack, std::queue and std::priority_queue wrap an underlying sequence and deliberately offer less than it does, so a stack cannot be iterated36. An adapter can narrow as well as translate.

Languages change the cost of adapting. Go's interfaces are satisfied implicitly: a type implements an interface by having the methods, with no declaration37. An adapter in Go is therefore needed only when the method names or signatures actually differ, and never merely to add an implements clause. Rust goes the other way. Its coherence rules forbid implementing a foreign trait on a foreign type, and the standard remedy is a newtype, a one-field tuple struct that makes the type local so the trait can be implemented on it38. That is an object adapter whose only job is to satisfy a rule about where implementations may live.

At architectural scale the adapter becomes a boundary. Cockburn's hexagonal architecture puts the application's own interfaces, its ports, at the centre and requires every technology on the outside to meet them through an adapter24. Evans' anti-corruption layer places facades, adapters and translators between a model and a legacy or external model so that the foreign concepts do not leak inward23. Both designs are ignorance contracts in the sense of this article. They specify what the application may stay ignorant of: which database, which message broker, which vendor's vocabulary.

Plates A3 and A4 show that adaptation is not only about method names. The iterator adapter over a paged API lights seven of eight lamps, and the one that matters is effect. The client sees a sequence; the adaptee is a service that serves pages. Iterate twice and every page is fetched twice; ask for the length and the adapter cannot answer without fetching everything. functools.partial adapts a signature rather than a name, and lights signature and surface because frameworks that introspect callables see a different object from a hand-written function39. An adapter hides the foreign interface. It does not hide the foreign semantics, and the plates record where those differ.

6Facade: the assembly

A facade provides a unified interface to a set of interfaces in a subsystem, making the subsystem easier to use1. Its promise is the least demanding of the seven. The client is not asked to believe that it holds any particular object; it is simply spared the knowledge of which objects exist behind the call and in what order they run. The subsystem facade in plate F1 lights only type and name, the minimum any new class must light. Nothing about its behaviour differs from a hand-written monolith with the same method. The module facade (F2) lights more, because a module is a singleton: two requests return the same object, and it passes no nominal type check.

The Simple Logging Facade for Java puts the pattern in its name. Application code logs through SLF4J's interfaces and a binding chosen at deployment connects them to Logback, java.util.logging or another back end, so a library can log without choosing the application's logging system40. Sam Newman's backend-for-frontend and the API gateway pattern apply the same idea at service scale: one coarse endpoint per client type, assembling calls to many services behind it41,42. Fowler's strangler fig application puts a facade in front of a legacy system so that functionality can be moved out from behind it piece by piece while clients keep calling the same interface43. In each case the facade is valuable precisely because the client can stay ignorant of the assembly, which is therefore free to change.

How much assembly does a facade hide? Experiment E7 instruments four standard-library facades with Python's profiler and counts what one call touches after a warm-up call has performed any lazy imports. The results, in Figure 5, are uneven in an instructive way. shutil.make_archive reaches 42 distinct Python functions across 7 source files; email.message_from_string reaches 30 across 6. json.dumps with indentation reaches only 8 distinct functions but calls them 628 times, because indented output takes a pure-Python encoder that recurses through the structure; textwrap.fill reaches 8 functions and spends most of its effort in C, with 520 calls into compiled regular-expression and string code. Fan-out, the breadth of what is hidden, and depth, the amount of work hidden, are different quantities, and a facade's interface reveals neither.

The failure mode of a facade is erosion. A facade designed for the common case eventually meets a client that needs one more capability from the subsystem, and the client reaches around the facade to get it. From then on that client depends on both the facade and the assembly, and the assembly is no longer free to change. The catalogue anticipated this and recommended that a facade not prevent access to the subsystem classes when clients need them1. That keeps the escape hatch open, and a door that is open will be used.

7Bridge: the implementation

Bridge decouples an abstraction from its implementation so that the two can vary independently1. Its pedigree is Coplien's handle-and-body idiom, in which a handle class that clients see holds a pointer to a body class that does the work16. The motivating arithmetic is simple. If m abstractions must each run on n implementations, inheritance produces m×n classes, while a bridge produces m+n. Experiment E3 tabulates the difference: 3 abstractions on 4 implementations need 12 subclasses against 7 bridged classes; 8 on 10 need 80 against 18. Figure 6 plots it beside the corresponding count for decorators.

JDBC is the most widely deployed bridge in enterprise software. Applications program against the java.sql interfaces, and a driver supplied by each database vendor implements them; the application can be moved to another database by changing the driver and the connection URL44. AWT's early peer classes bridged Java components to native toolkits in the same way. In C++ the handle-and-body idiom survives as pimpl, the pointer-to-implementation idiom, whose main purpose is to keep private details out of a header so that clients need not recompile when they change45. The listing in Section 5 compiles the idiom: the header declares struct Impl and never defines it, so no client can depend on its layout.

Bridge is the only family in which a plate goes completely dark. Plate B1 swaps the implementor from one that computes πr² to one that computes r²π, which for r = 2 produce the same double, and the battery finds a single difference: the generated representation prints the implementor's class name. Plate B2 is a handle-and-body pair with a private body, equality defined on the handle and a representation that does not mention the body, and it lights nothing. The reason is structural. A bridge does not put a second object between the client and the thing it uses; the client holds the abstraction itself, and the implementation is a relationship behind it. There is no second object whose identity could show and no forwarding layer whose gaps could leak. The one caveat is observational equivalence. The dark reading depends on the two implementations agreeing on every input the client will present; for r = 3 the two formulas differ in the last bit, and a client that compares floating-point results would see the bridge.

8Composite: the multiplicity

Composite composes objects into tree structures to represent part-whole hierarchies and lets clients treat individual objects and compositions uniformly1. Its ancestors are the nested views of Smalltalk's model-view-controller framework10 and the glyph and scene trees of InterViews14. It is now the default structure of every user interface: the DOM is a tree of nodes in which a document, an element and a text node share one interface for traversal46, and component frameworks describe a page as a tree of components that render children they do not inspect.

The catalogue recognised a tension in the pattern and named its two resolutions. The transparent form declares child-management operations such as add on the common interface, so a client never needs to know whether it holds a leaf; the price is that a leaf must do something when asked to add a child, usually throw. The safe form declares child management only on the composite, so a leaf cannot be misused; the price is that a client wanting to add must first find out what it holds1. Plates C1 and C2 put a number on the trade-off. Both light type, name and effect. The safe form additionally lights surface, which is exactly the knowledge the pattern was meant to remove, returned to the client as a type test. The transparent form trades that lamp for a runtime exception.

The effect lamp is the composite's real tell. A folder of two files reports the same size as a single file of ten bytes, but it reads both leaves to do so: the operation count scales with the multiplicity the client was told it could ignore. In a user interface that is a layout pass that grows with the tree; in a file system it is a recursive walk; in a bill of materials it is a query per level. The DOM's design reflects the cost: a document can be traversed uniformly, but anything that touches every node is visibly expensive, and the standard's own operations distinguish between those that act on a node and those that act on its subtree46.

The standard library's ChainMap is a composite of mappings that presents several dictionaries as one, searched in order47. Plate C3 found a leak that its documentation states but most users do not expect: iteration scans the mappings from last to first, so the keys come back in a different order from those of a merged dictionary with the same contents. The client was allowed to ignore that it held several mappings, and the iteration order tells it anyway.

9Decorator: the added responsibility

Decorator attaches additional responsibilities to an object dynamically and offers a flexible alternative to subclassing for extending functionality1. The argument for it is combinatorial. If a stream may be buffered, compressed, encrypted, checksummed or encoded, in any combination, subclassing needs a class for every subset, 2n of them for n features; decorators need n classes, one per responsibility, composed at run time. Experiment E3 tabulates the counts. For six optional features that is 64 subclasses against 6 decorators.

The Java I/O library is the canonical instance. FilterInputStream holds another input stream and passes calls through, and its subclasses add buffering, decompression, checksums and typed reads48. .NET's streams follow the same design, with BufferedStream and CryptoStream wrapping any other stream49,50. Go writes the same thing with interfaces: io.Reader is one method, and the standard library supplies readers that wrap readers, while net/http handlers are wrapped by handlers such as StripPrefix and TimeoutHandler to form middleware chains51,52.

The count of decorators hides a second count. With n decorators there are not 2n distinct stacks but many more, because order matters: the number of ordered stacks is the sum over k of n!/(n−k)!, which is 65 for four transforms, 1,957 for six and 9,864,101 for ten. Experiment E3 builds all 65 ordered stacks of four real transforms (zlib compression, a toy keystream cipher, base64 encoding and a CRC-32 trailer) over 24,806 bytes of deterministic log text. Every one of the 65 produces a different output, and none of the six pairs of transforms commutes. The sizes, in Figure 7, fall into two bands. Every ordering that compresses before it encrypts ends near 23.6% of the input; every ordering that encrypts first ends between 101% and 133.5%, because ciphertext is indistinguishable from random data and random data does not compress. The worst ordering is 5.65 times the size of the best.

Order is not only a matter of size. Compressing before encrypting is right for size and, in some protocols, wrong for secrecy: John Kelsey showed in 2002 that the length of compressed-then-encrypted output leaks information about the plaintext to an attacker who can influence part of it53, the principle behind later attacks on compressed TLS. A decorator stack encodes decisions that its client was allowed to ignore and its designer was not. The zlib and base64 formats used in the experiment are the ones specified in RFC 1950 and RFC 464854,55.

Python gave the word a second meaning. PEP 318 introduced the @decorator syntax for functions and methods in Python 2.4 and recorded the objection that the name is not consistent with its use in the pattern catalogue56. A Python decorator is any callable applied to a function at definition time; it may register the function and return it unchanged, or return a wrapper. When it wraps, it is a decorator in the catalogue's sense too, and functools.wraps exists to make the wrapper look like the original by copying its name, docstring and other metadata and recording the original as __wrapped__39.

Plates D3 and D4 compare the two options, and the comparison is a small lesson in the economics of concealment. Without wraps (D4) the wrapper leaks its name and its signature: it prints as wrapper and takes (*args, **kwargs). With wraps (D3) both lamps go dark, and a new one lights: surface, because the wrapper now carries __wrapped__. That attribute is how inspect.signature recovers the original signature, so the leak is the mechanism of the concealment. React's documentation for higher-order components, the same idea applied to components, lists the equivalent leaks: static methods of the wrapped component are not copied over and refs are not passed through unless forwarded explicitly57. TypeScript 5.0 implemented the ECMAScript decorators proposal and brought the Python sense of the word to the JavaScript ecosystem58.

Kotlin goes furthest. Its by clause makes a class implement an interface by forwarding every member to a named object, overriding only what it chooses, so the boilerplate of a decorator disappears; the documentation presents delegation as a good alternative to implementation inheritance, supported natively59. The forwarding is still forwarding in Lieberman's sense: the inner object's calls to itself do not come back through the decorator, so the self problem remains9,32.

10Proxy: location, lifetime and access

Proxy provides a surrogate or placeholder for another object in order to control access to it1. The catalogue lists four kinds: a remote proxy stands for an object in another address space, a virtual proxy creates an expensive object only when it is needed, a protection proxy checks access rights, and a smart reference does extra bookkeeping on every access, such as counting references or locking. A proxy has the same interface as its subject, which is what separates it from an adapter, and it controls access rather than adding responsibilities, which is what separates it from a decorator. The class diagram is the one in Figure 2; only the intent is new.

The remote proxy is older than the catalogue: Section 2 traced it to Shapiro's proxy principle and to the stubs that made a remote procedure call look like a local one11,12. In 1994 Waldo and colleagues at Sun argued that this transparency is a mistake. Latency, memory access, partial failure and concurrency differ irreducibly between local and remote objects, so a design that hides location invites clients to rely on local semantics they will not get61. In the vocabulary of this article, location is something a client is not allowed not to know. Plate P6 makes the point with a by-copy wire: the stub hides where the subject lives and lights effect, because a list returned by the stub is a copy, and a client that edits it edits nothing on the server.

In Python the cheapest proxy is four lines long, and it does not work. A class that defines __getattr__ forwards every attribute lookup that fails on the proxy itself, so named methods reach the target. But the language looks up special methods such as __len__ and __iter__ on the type, bypassing both the instance and __getattr__62, so every builtin and operator that relies on them fails.

Experiment E2 measures the damage. It applies 22 operations to a list and to a proxy for the same list. The naive proxy gives a different outcome on 18 of them while getting 3 of 3 named methods right. A hardened proxy, which defines a forwarding method for each of the 37 special methods that list defines, unwraps proxied arguments, reports the target's class through __class__ and forwards dir, differs on only 2: type(x) is list, and json.dumps(x), whose C encoder checks the concrete type and rejects the proxy. Figure 8 shows both columns. The wrapt library is the production form of the hardened proxy, and its documentation keeps a separate CallableObjectProxy because forwarding __call__ unconditionally would make every proxied object appear callable63. Objective-C built the same idea into its runtime: NSProxy is a root class, not a subclass of NSObject, and a subclass forwards messages it does not implement to its subject64.

Java generates proxies at run time. Proxy.newProxyInstance creates a class that implements a given list of interfaces and routes every call, including equals, hashCode and toString, to an InvocationHandler65. The mechanism covers interfaces only, and it has an exception leak of its own: if the handler throws a checked exception that the interface method does not declare, the caller receives an UndeclaredThrowableException instead65. .NET's DispatchProxy has the same shape, an interface type and a single Invoke method that receives every call66.

Spring's declarative transactions, security and caching are built from such proxies, generated from the interface or, for classes, by subclassing33. The virtual proxy hides when work happens. Hibernate represents a lazily fetched association with a proxy that loads the associated entity on first access71; .NET packages the same idea as Lazy<T>72; Fowler's Lazy Load pattern describes the trade and warns of ripple loading, in which a loop over lazily loaded objects issues one query per object22. Experiment E5 prices that under an assumed cost model of 0.5 ms per round trip and 0.01 ms per returned row, with 500 orders belonging to 107 of 150 customers. An eager join costs one query and 8.50 ms whatever the client does. Lazy loading through proxies costs more once 6 orders are touched (1.2%); touching all of them costs 108 queries and 60.07 ms. Batching the proxies' loads 16 at a time moves the crossover to 142 orders (28.4%) and the full traversal to 8 queries and 10.07 ms (Figure 9). The absolute figures are the model's; the shape is the point. The virtual proxy is cheapest when the client touches almost nothing, and the client is exactly the party that has been told it need not know what touching costs.

A caching proxy hides cost and exposes freshness. Experiment E6 runs 20,000 operations over 200 keys with Zipf-distributed popularity, of which 5% are writes that go straight to the source, as writes from another process would. With room for every key and no expiry the proxy answers 98.95% of reads itself and 83.03% of reads are stale. A ten-entry cache hits 31.92% and is stale on 3.64%. A time-to-live trades one for the other: at capacity 100, expiry after 500 operations takes the stale share from 58.22% to 27.37% and the hit rate from 83.31% to 77.40%; expiry after 50 pins every cache of 50 entries or more at 45.75% hits and 4.44% stale (Figure 10). Without invalidation from the source, hit rate and staleness rise together, because both measure how long the proxy keeps an answer.

The protection proxy and the smart reference are the quiet majority. types.MappingProxyType gives a read-only view of a mapping73 and Collections.unmodifiableList a read-only view of a list74; both are live, so a reader who assumed a snapshot sees the owner's later writes. C++ lets a class overload -> and unary *, which is how unique_ptr and shared_ptr read like raw pointers while managing a lifetime75. Rust's Deref trait serves smart pointers the same way, and its documentation limits it to types that transparently behave like the target, dereference cheaply and will not surprise their users through automatic coercion76: a short statement of which lamps a smart reference must keep dark. weakref.proxy hides that a reference is weak until the referent is collected and every operation raises77; a Mock built with a spec passes isinstance and stands for an object that does not exist78.

Smalltalk-80 gave a proxy a way to disappear. Its become: exchanges the identities of two objects, so every reference to one becomes a reference to the other7; a proxy could load its subject and then become it, taking the identity lamp with it. None of the other languages in this article has that operation, which is one reason the identity lamp is lit on 15 of 26 plates.

11Flyweight: the sharing

Flyweight uses sharing to support large numbers of fine-grained objects efficiently1. Its origin is the most specific in the catalogue. Paul Calder and Mark Linton's glyphs for InterViews represented every character of a document in a WYSIWYG editor as an object, and made that affordable by sharing one object per distinct character13,14. The pattern's vocabulary comes from that design: intrinsic state, such as the character code and font, lives in the shared object; extrinsic state, such as position, is supplied by the context whenever the flyweight is used. Flyweight is the only structural pattern that inverts the skeleton, putting many logical references in front of one object rather than one reference in front of many.

Experiment E4 lays out a 50,000-character document over an alphabet of 80 symbols drawn with Zipf frequencies. One object per character, each carrying its own font and style, costs 202.6 bytes per character. Sharing one object per distinct symbol and keeping a small placed object per position for the extrinsic state costs 81.9, a saving of 59.6%. Moving the extrinsic state out of objects altogether, into packed arrays of positions and symbol indices, costs 6.6, a saving of 96.7%. Most of the saving comes from the second step: the per-position objects, not the per-symbol ones, are what the pattern has to eliminate.

Sharing is not free. The factory needs a table and each use needs a lookup, and the saving depends on how often each intrinsic state recurs. The sweep in E4 holds a population of 5,000 elements and varies the number of distinct states. With one state the shared layout costs 0.355 of the unshared one; with a thousand, 0.535; sharing stops paying at 3,540 distinct states (70.8% of the population, each state reused 1.41 times on average), and with every element distinct it costs 1.233 times as much (Figure 11).

Languages apply the pattern to their own values, and that is where the identity lamp becomes a trap. The Java language specification requires boxing to return the same object for int values between −128 and 127 and for a few other small values, and leaves larger values to the implementation79. CPython keeps preallocated objects for the integers from −5 to 25680: in the lab, int('256') is int('256') is True and int('257') is int('257') is False. sys.intern offers the same sharing for strings on request81. Code that compares with is or == on references passes every test that uses small values and fails in production.

The other failure is mutation. A flyweight must be immutable, or at least its intrinsic state must be, because every logical reference sees a change made through any of them. Rust's Cow makes the discipline explicit: it holds borrowed data and clones it into an owned value only when mutation is required82, so sharing lasts exactly as long as nobody writes. The two flyweight plates are the quietest in the battery after the bridge, lighting 1 to 2 lamps, and the lamp they both light is identity. Sharing is the one thing a flyweight cannot hide, because sharing is what it is.

12What the patterns became

The patterns did not stay in the catalogue. Section 2 quoted Norvig's finding that 16 of the 23 have simpler implementations in Lisp or Dylan25 and Graham's view that recurring patterns betray a missing abstraction26; the structural patterns are where mainstream languages have since supplied the abstraction. Python's decorator syntax, JavaScript's Proxy, Java's dynamic proxies, .NET's DispatchProxy, Kotlin's by clause and Rust's Deref are each a structural pattern turned into a feature56,59,65–67,76. Go promotes the methods of an embedded field to the outer struct37, which makes the forwarding half of a decorator free.

The battery suggests a qualification. Absorption removes the boilerplate; it does not remove the leak, because the leak belongs to the mechanism. Kotlin's delegation still forwards rather than delegates, JavaScript's proxy still has its own identity and cannot see private fields, functools.wraps trades a lit name for a lit surface, and Spring's proxies still miss self-calls. A feature decides which lamps are lit by default. It cannot decide that a second object does not exist.

Aspect-oriented programming carried the idea further. Kiczales and colleagues introduced aspects in 1997 to modularise concerns such as logging, synchronisation and error handling that cut across a program's decomposition83. In 2002 Hannemann and Kiczales implemented all 23 patterns in both Java and AspectJ and found modularity improvements in 17 of them, through better locality, reusability, composability and pluggability84. In most enterprise Java code the aspects arrive by a route that closes the circle: Spring implements them with proxies33.

Popularisation took a different path. Head First Design Patterns taught the catalogue to a generation through examples and pictures85, and the names became interview vocabulary. The evidence on whether the patterns help has stayed thinner than their reputation. Prechelt and colleagues ran controlled maintenance experiments on programs with and without patterns, including Decorator and Composite, and found effects that varied by pattern and task; their conclusion was that, unless there is a clear reason to prefer the simpler solution, the flexibility of a pattern is usually the wiser choice86. Zhang and Budgen's mapping study of the empirical literature found some support for patterns as a framework for maintenance and some qualitative indication that they do not help novices learn design87. Their follow-up survey of experienced users found only three patterns, Observer, Composite and Abstract Factory, clearly regarded as useful88. Ampatzoglou and colleagues' broader mapping study of research on the catalogue reports mixed findings on quality89, and Khomh and Guéhéneuc's survey of experts found that patterns can affect several quality attributes negatively as well as positively90.

None of this contradicts the catalogue, whose authors presented patterns as a vocabulary for design experience rather than as a guarantee of quality1. It does support the reading this article has taken. A structural pattern is a promise about what a client may ignore, and whether it helps depends on whether that promise holds for the channels the client actually uses.

So what is the client allowed not to know? Read down the ledger and the answer has two parts. A client may stay ignorant of almost everything behind an object: its implementation, the subsystem assembled under it, the interface it was translated from, how many parts it contains, where it lives, when it was loaded, what extra work each call does. Every one of those can be hidden well, and the plates that hide them best light only a lamp or two. What a client cannot be kept from knowing is that a second object is there. Type and identity are the two lamps that no forwarding extinguishes: the hardened proxy lights exactly those two, type is lit on 20 of 26 plates and identity on 15, and only the two bridge plates, where the client's handle is the object and not a stand-in for one, keep both dark. The one plate that goes dark, the handle-and-body pair, is the one in which the client holds the only object and the hiding happens entirely inside it.

The ignorance a pattern grants is also never free. What the client was allowed to forget comes back as a quantity: cost in the facade's fan-out and the lazy proxy's queries, time in the virtual proxy's first touch, order in the decorator stack, freshness in the cache, location in the remote stub, sharing in the flyweight. The lab put a number on each, and none of the numbers is small.

Four practical rules follow. Decide which lamps a wrapper must keep dark, and test those channels directly, as the battery does, rather than trusting the pattern's name. Forward equality and hashing, or document that the wrapper has identity semantics; it is the commonest leak and the cheapest to close. Keep proxies and flyweights out of identity-keyed contexts such as weak maps, identity sets and is comparisons, or hand clients only the wrapper, as Vue does. And write down the hidden quantity, the cost, time, order, freshness or location, where the next reader of the interface will see it. The patterns are contracts about ignorance, and a contract is only as good as the list of things it does not cover.

class HardenedProxy:
    """Forwards every special method the TARGET'S TYPE defines (no more, no
    fewer), unwraps proxied arguments, and spoofs __class__ -- the recipe
    used by wrapt.ObjectProxy and lazy-object-proxy."""
    __slots__ = ("_target",)

    def __getattr__(self, name): return getattr(self._target, name)

    @property
    def __class__(self): return type(self._target)

    def __dir__(self): return dir(self._target)


_SKIP = {"__class__", "__getattribute__", "__getattr__", "__setattr__",
         "__delattr__", "__init__", "__new__", "__init_subclass__",
         "__subclasshook__", "__dir__", "__reduce__", "__reduce_ex__",
         "__getstate__", "__sizeof__", "__class_getitem__", "__doc__"}
_PROXY_TYPES = {}


def _unwrap(v):
    return object.__getattribute__(v, "_target") if isinstance(
        type(v), type) and issubclass(type(v), HardenedProxy) else v


def _mk_fwd(n):
    def f(self, *a, **k):
        tgt = object.__getattribute__(self, "_target")
        return getattr(tgt, n)(*[_unwrap(x) for x in a], **k)
    f.__name__ = n
    return f


def hardened(target):
    t = type(target)
    cls = _PROXY_TYPES.get(t)
    if cls is None:
        ns = {"__slots__": ()}
        for n in dir(t):
            if (n.startswith("__") and n.endswith("__") and n not in _SKIP
                    and callable(getattr(t, n, None))):
                ns[n] = _mk_fwd(n)
        if getattr(t, "__hash__", None) is None:
            ns["__hash__"] = None
        cls = _PROXY_TYPES[t] = type("HardenedProxy", (HardenedProxy,), ns)
    p = object.__new__(cls)
    object.__setattr__(p, "_target", target)
    return p

def keystream_xor(data, key=b"lab-key-not-for-use"):
    """A TOY stream transform (SHA-256 in counter mode). Illustrative only."""
    out = bytearray(len(data))
    for block in range(0, len(data), 32):
        ks = hashlib.sha256(key + block.to_bytes(8, "big")).digest()
        for i, b in enumerate(data[block:block + 32]):
            out[block + i] = b ^ ks[i]
    return bytes(out)

class CharFull:
    __slots__ = ("char", "font", "size", "bitmap", "x", "y")

class GlyphFW:

    def __init__(self, char, font, size, bitmap):

class Placed:
    __slots__ = ("glyph", "x", "y")

    def __init__(self, glyph, x, y): self.glyph, self.x, self.y = glyph, x, y


def deep_size(roots):
    seen = set()
    total = 0
    stack = list(roots)
    while stack:
        o = stack.pop()
        if id(o) in seen:
            continue
        seen.add(id(o))
        total += sys.getsizeof(o)
        if isinstance(o, (list, tuple)):
            stack.extend(o)
        elif isinstance(o, dict):
            stack.extend(o.keys())
            stack.extend(o.values())
        elif hasattr(type(o), "__slots__"):
            for s in type(o).__slots__:
                stack.append(getattr(o, s))
    return total


def zipf_text(n, k, seed, s=1.1):
    rng = random.Random(seed)
    alphabet = [chr(0x21 + i) for i in range(k)]
    weights = [1 / (i + 1) ** s for i in range(k)]
    return rng.choices(alphabet, weights=weights, k=n)

    say("")
    say(f"{'touched':>8} {'distinct':>8} | {'eager q':>7} {'ms':>6} | {'lazy q':>6} {'ms':>6} | "
        f"{'batch q':>7} {'ms':>6}")
    order_idx = list(range(n_orders))
    rng.shuffle(order_idx)
    rows = []
    for f in [0, 0.01, 0.02, 0.05, 0.1, 0.2, 0.3, 0.5, 0.75, 1.0]:
        t = int(round(f * n_orders))
        touched = order_idx[:t]
        dist = len(set(owner[i] for i in touched))
        eager_q, eager_rows = 1, n_orders
        lazy_q, lazy_rows = 1 + dist, n_orders + dist
        batch_q, batch_rows = 1 + math.ceil(dist / BATCH), n_orders + dist
        ce = eager_q * RTT + eager_rows * ROW * 1.6    # joined rows are wider
        cl = lazy_q * RTT + lazy_rows * ROW
        cb = batch_q * RTT + batch_rows * ROW
        rows.append((f, t, dist, eager_q, ce, lazy_q, cl, batch_q, cb))
        say(f"{100 * f:7.0f}% {dist:8d} | {eager_q:7d} {ce:6.2f} | {lazy_q:6d} {cl:6.2f} | "
            f"{batch_q:7d} {cb:6.2f}")

    cross = None
    for t in range(0, n_orders + 1):
        dist = len(set(owner[i] for i in order_idx[:t]))
        ce = RTT + n_orders * ROW * 1.6
        cl = (1 + dist) * RTT + (n_orders + dist) * ROW

        cb = (1 + math.ceil(dist / BATCH)) * RTT + (n_orders + dist) * ROW
        if cb > ce:
            bcross = (t, dist)
            break
    say("")
    say(f"batched lazy loading costs more than the eager join once {bcross[0]} orders "
        f"({100 * bcross[0] / n_orders:.1f}%) are touched, i.e. {bcross[1]} distinct customers")
    say(f"lazy loading costs more than the eager join once {cross[0]} orders "
        f"({100 * cross[0] / n_orders:.1f}%) are touched, i.e. {cross[1]} distinct customers")
    JS["E5"] = {"orders": n_orders, "cust": n_cust, "owners": len(set(owner)),

def e6():
    rule("E6  Caching proxy: hit rate against stale reads")
    rng = random.Random(20260929)
    keys = 200
    w = [1 / (i + 1) for i in range(keys)]
    N = 20_000
    stream = []
    for _ in range(N):
        k = rng.choices(range(keys), weights=w)[0]
        stream.append(("w" if rng.random() < 0.05 else "r", k))
    say(f"{N} operations over {keys} keys (Zipf s=1); 5% are writes that go "
        f"straight to the source, bypassing the proxy")
    res = []
    say(f"{'capacity':>8} {'ttl':>6} {'hit %':>7} {'stale % of reads':>17} {'source reads':>13}")
    for cap in [10, 25, 50, 100, 200]:
        for ttl in [None, 500, 50]:
            source = [0] * keys
            cache = collections.OrderedDict()
            hits = stale = reads = misses = 0
            for t, (op, k) in enumerate(stream):
                if op == "w":
                    source[k] += 1
                    continue
                reads += 1
                ent = cache.get(k)
                if ent is not None and (ttl is None or t - ent[1] <= ttl):
                    hits += 1
                    cache.move_to_end(k)
                    if ent[0] != source[k]:
                        stale += 1
                else:
                    misses += 1
                    cache[k] = (source[k], t)
                    cache.move_to_end(k)
                    if len(cache) > cap:
