Six rungs of what the core may import. K0, the outer disc, licenses anything; K5, the centre, nothing that performs an effect.

The family of application architectures that runs from the layered stack through ports and adapters, the onion and clean architecture is usually taught as a sequence of diagrams. This article reads each of them as a single sentence about the dependency graph: what the code that carries business policy is permitted to import. Twenty-five patterns and precursors are coded on a six-rung import ladder and on an orthogonal axis recording what, if anything, keeps the rule true. A lab of seven deterministic experiments builds reference dependency graphs for eight architectures and measures propagation cost, blast radius, stability and role-level reachability. Three results carry the argument. Hexagonal, onion and clean architecture are the same graph at the level of roles, differing only in how many modules a feature costs. Inverting a dependency does not remove coupling but relocates it, from the infrastructure onto the core. And 18 of 25 patterns prescribe no mechanism at all for keeping their own rule, which is the part of the choice that decides whether the diagram survives contact with a year of commits.

Same graph, different names. At the level of roles, hexagonal, onion and clean architecture disagree on 0 of 30 reachability cells. Each differs from strict layering on 5. What separates them is cost: 3, 5 and 7 modules per feature.

Inversion relocates coupling. A driver swap reaches 24 of 24 modules in a layered design and 8 of 24 in a hexagonal one. A rule change in the most-used feature goes the other way, from 62.5% to 95.8% of modules.

The rule is rarely kept by anything. 18 of 25 patterns prescribe no mechanical enforcement. Among the 12 that make the strongest claims (K3 and above), 3 do. Separate build modules stop only one of four kinds of erosion.

01The question

Every architecture in this family is drawn as a picture, and every picture hides the same small fact. A layered stack, a hexagon, an onion and four concentric circles all encode a rule about which source files may name which others. The pictures differ a great deal; the rules differ much less. Read the canonical sources closely and each one reduces to a sentence of the form the code that holds the business policy may import X and nothing else, plus, sometimes, a sentence about how that is to be kept true.

That reduction is the organising question of this article: what is the core allowed to know? It is a sharper question than "which architecture is best", because it has an answer that can be checked by a tool. It also explains why the names multiplied. Once the answer moved from "the layer below" to "only interfaces the core itself declares", most of what remained to argue about was how many rings to draw inside the core and what to call them.

Figure 1 shows the single move on which the family turns. In a layered stack, control flows downward and source dependencies follow it: the business code calls the data access code and must therefore name it. In the inverted designs, control still flows outward to the database at run time, but the source dependency points back: the business code names an interface it owns, and the database code implements it. Martin put this as a principle in 1996 1; Cockburn drew it as a hexagon in 2005 2; Palermo as an onion in 2008 3; Martin again as circles in 2012 4. The runtime behaviour of the four is the same. What changes is which file has to be edited, rebuilt and retested when something changes.

The article proceeds in four movements. Sections 2 to 5 give the history, from the operating-system levels of the late 1960s to the modular monoliths of 2025, with code from Java, C#, Go, Python, TypeScript and Rust. Section 6 introduces the two instruments used throughout: an import ladder of six rungs, from K0 (the core may import anything) to K5 (the core may import nothing that performs an effect), and an enforcement axis recording what keeps the rule true, from convention to a network boundary. Section 7 is a lab of seven deterministic experiments on reference dependency graphs. Section 8 shows how each major platform can make the rule mechanical, and section 9 turns the findings into a way of choosing. The twenty-five coded patterns follow as plates, each with a small gauge, and a closing ledger collects them.

Two terms are used narrowly. Core means the code that carries business policy, whatever a given pattern calls it: domain layer, application, entities and use cases, the inner rings. Dependency means a compile-time or import-time reference from one unit of source to another, the relation Parnas called uses in its static form 5, not a runtime call. The distinction between the two is the whole subject.

02Levels, modules and the uses relation

The layered idea did not begin in business software. It began with the problem of convincing oneself that a program is correct. Dijkstra's account of the THE multiprogramming system, presented in 1967 and published in 1968, describes an operating system built as a hierarchy of levels 6. Level 0 allocated the processor and handled the real-time clock. Level 1 was the segment controller that managed memory against the drum. Level 2 interpreted messages to and from the operator console, level 3 buffered input and output streams, level 4 ran user programs, and the operator sat at level 5. Each level could use only the abstractions provided by the levels below it. The claim that made the paper famous was that this structure made the system testable: each level could be verified exhaustively on the assumption that the ones beneath it were correct, so the number of cases to consider stayed small.

Two things about THE are worth holding onto. The first is that the levels were justified by reasoning, not by change. Dijkstra's later name for the underlying discipline, the separation of concerns, is about being able to think about one aspect of a problem at a time 7. The second is that the levels ran in the same direction as the calls. Higher levels invoked lower ones and knew about them; lower levels knew nothing of what was built on them. Every layered architecture in this article inherits that alignment of control and dependency, and every inverted one is defined by breaking it.

Wirth's stepwise refinement proposed the complementary top-down habit of development in 1971 8. The following year Parnas changed the question. His paper on decomposing systems into modules compared two designs for the same small program, a keyword-in-context index, and showed that the obvious one, a module per processing step, spread every likely change across several modules 9. His alternative made each module the owner of a design decision, the format of the stored lines for example, hidden behind an interface. The criterion was change, not correctness. Stevens, Myers and Constantine gave the same instinct its lasting vocabulary two years later as coupling and cohesion 10.

Information hiding says nothing about direction. A module in Parnas's 1972 sense exposes an interface that it owns and that its clients adapt to; nothing forbids two modules from using each other. The missing piece arrived in stages. Habermann, Flon and Cooprider argued in 1976, from their work on a family of operating systems, that modularity and hierarchy are separate structuring decisions that had been conflated 11. Parnas's 1979 paper on designing software for extension and contraction then separated uses from invokes: a program uses another if its correctness depends on the other being present and correct 5. He asked that the uses relation be loop-free, so that the system could be delivered in useful subsets and extended without disturbing what already worked. Parnas, Clements and Weiss applied the approach to a large real system, the A-7E flight software, in 1985 12.

By 1980, then, the three ideas that the later diagrams recombine were on the table: levels of abstraction that make reasoning local, modules that hide decisions likely to change, and a loop-free uses relation that orders the modules. The same year Zimmermann published the seven-layer OSI reference model 13, which gave the whole industry a picture of layers so persuasive that it became the default drawing of any complex system. Saltzer, Reed and Clark's end-to-end argument followed in 1984 as the canonical caution against it: a function placed in a low layer may be redundant, or insufficient, when only the endpoints know what correctness means 14. Application architecture absorbed the picture more readily than the caution.

03The layered consensus

The first architecture in this family to reverse a dependency did so at the user interface. Reenskaug's notes at Xerox PARC in 1979 described models, views and controllers 15, and Krasner and Pope's cookbook made the arrangement standard Smalltalk-80 practice in 1988 16. The essential rule was that the model should know nothing about its views. A view registered itself as a dependent of the model and was notified of changes through Smalltalk's generic change-notification mechanism, so the model never named a view. That is, in the language of this article, a consumer-owned port at exactly one boundary. It is also why "MVC" came to mean very different things in later web frameworks, where the model was often the database row and the controller the place where everything else went.

Jacobson's use-case driven method of 1992 sorted analysis objects into three kinds: interface objects, later called boundary objects, that face actors; control objects that carry the behaviour of one use case; and entity objects that hold long-lived information 17. Entities knew nothing of boundaries or controllers. Viewed from 2026 this is remarkable: a core that imports nothing outside itself, twenty years before the concentric diagrams. It was an analysis discipline rather than a code-structure rule, but Martin's 2012 post lists it explicitly among the ideas that clean architecture unifies 4.

The early 1990s also gave software architecture its academic footing. Perry and Wolf defined architecture as elements, form and rationale, and named two ways in which it degrades: erosion, the violation of the architecture, and drift, insensitivity to it 18. Garlan and Shaw catalogued architectural styles, among them layered systems, pipes and filters, and event-based implicit invocation 19, and their 1996 book made the catalogue a discipline 20. Kruchten's 4+1 view model separated the logical, process, development and physical views of a system 21. That separation matters here: every rule in this article is a rule about the development view, the organisation of source into modules, even when the diagrams that express it look like runtime pictures. The current standard for architecture description, ISO/IEC/IEEE 42010:2022, formalises the point that one system has many views, each answering different concerns 22.

The Pattern-Oriented Software Architecture volume of 1996 gave the layered style its most-cited pattern form 23. Its Layers pattern states the strict version, in which each layer uses only the layer directly beneath, and names a relaxed variant in which a layer may use any layer below. The same volume describes the Microkernel pattern, which will reappear below as the plug-in architecture. Clements and colleagues later made the definition precise in Documenting Software Architectures: a layer diagram depicts an allowed-to-use relation, which is a permission, not a description of calls 24. That distinction is exactly the one this article turns on.

In enterprise systems the layers acquired a physical meaning. Two-tier client–server systems put the user interface on the desktop and the data on a shared server, and the difficulty of keeping domain logic out of the screens pushed many teams to a third tier 25. Three-tier architecture made the boundary between presentation, logic and data a process boundary. That is the strongest kind of enforcement on this article's axis, since the logic tier simply cannot reach a presentation class, but it changed nothing about direction. The logic tier called the data tier, knew its interfaces and usually its schema, and the rung stayed where Dijkstra had put it. Fielding's dissertation of 2000 wrote the same constraint into REST, where each component in a layered system cannot see beyond the layer it interacts with 26; the constraint is about visibility between neighbours, and says nothing about which neighbour owns the interface.

Fowler's Patterns of Enterprise Application Architecture of 2002 is the most influential statement of the resulting consensus 25. It organises an application into presentation, domain and data source, with one rule held firm: the domain and data source should never depend on the presentation. The domain may depend on the data source by default. Fowler also catalogues the ways to reverse that: a Data Mapper keeps domain objects ignorant of the database entirely, and a Separated Interface lets the domain declare an interface whose implementation lives elsewhere. The inversion is therefore present in the canonical layered book as an option, not as a rule.

Evans's Domain-Driven Design followed in 2003 27. His layered architecture stacks user interface, application, domain and infrastructure, and asks that all the code related to the domain model be concentrated in one layer isolated from the others. The diagram lets each layer use those below it, so the domain may use infrastructure. Yet his repositories point the other way: the domain works with a repository through an interface that speaks the language of the model, and the implementation belongs to infrastructure. Vernon's implementation guide a decade later made the consequence explicit by recommending the hexagonal arrangement for exactly this reason 28. The layered consensus contained its own successor.

The consensus is still alive, and not only in legacy code. Google's current guidance for Android applications describes a UI layer, a data layer that is the source of truth, and an optional domain layer between them that depends on the data layer's repositories 29. That is K1 on the ladder below, stated as recommended practice by a platform owner in the 2020s. The choice is defensible: on a phone, the data layer is often the most stable part of the application, and the inversion would buy little. It is a useful reminder that the ladder is a description, not a ranking.

04The inversion

Martin's 1996 column on the dependency inversion principle stated it in two clauses: high-level modules should not depend on low-level modules, both should depend on abstractions; and abstractions should not depend on details, details should depend on abstractions 1. The first clause is usually quoted. The second carries the weight. An interface published by the database layer and imported by the business layer satisfies the first clause and leaves the arrow exactly where it was, because the abstraction belongs to the detail. Only when the business layer owns the interface, declares it in its own package, names it in its own vocabulary and lets the database code implement it, does the source dependency reverse. Martin's later book gathered the principle with its siblings 30, and his Design principles and design patterns paper had earlier tied them to package structure 31.

Martin also supplied the metrics used in section 7. In a 1994 paper he defined afferent coupling (how many units depend on a package), efferent coupling (how many it depends on), and instability as the ratio of efferent to total coupling, and proposed that dependencies should run in the direction of stability 32. Lakos's book on large-scale C++ design, published in 1996, gave the physical counterpart: components should be levelisable, arranged so that each can be tested using only those below it, and the cumulative component dependency, the total number of components needed to test every component, measures how far a design falls short 33. Both are about the development view, and both reward the same move.

The move needed a mechanism for supplying the implementation at run time without the core naming it. The design-patterns book of 1995 had supplied the vocabulary of abstract factories and strategies 34, and Fowler's 2004 article gave the wiring its lasting name, dependency injection, distinguishing constructor, setter and interface injection and contrasting them with a service locator 35. Seemann's composition root later named the one place that is allowed to know everything: the entry point that constructs the object graph and hands implementations to the core 36. Every inverted architecture needs such a place, and every one of them draws it outside the core.

Ports and adapters

Cockburn's hexagonal architecture, discussed on the Portland Pattern Repository and written up in 2005, is the most direct statement of the inversion as an architecture 2. The application sits inside; everything else, users, tests, databases, message queues, other applications, sits outside and is reached through ports. A port is a purpose-named conversation, "for placing orders" or "for obtaining exchange rates", and an adapter translates between a port and a particular technology. Driving actors call into the application through its primary ports; the application calls out to driven actors through secondary ports that it declares. The book Cockburn wrote with Garrido de Paz, published in preview in 2024 and as an updated first edition in 2025, is explicit that the hexagon has no significance as a shape: it was chosen to leave room to draw ports and to break the habit of a one-dimensional stack 37.

The payoff Cockburn emphasised was testing. An application whose every external conversation goes through a port can be driven by a test harness and can talk to an in-memory database without modification. This is the hexagon's version of Dijkstra's claim for THE: the structure exists so that the core can be checked in isolation. Netflix's engineering team described adopting the pattern in 2020 for a set of studio applications whose data sources were expected to change, and reported that swapping a data source became a matter of writing a new adapter 38.

The listing shows the same driven port in three languages. The Java interface sits in the domain package and the JPA adapter implements it; the Python version uses a structural Protocol, introduced by PEP 544, so the adapter need not even import the port to satisfy it 39. The Go version is the most interesting, because the language's own guidance makes the inversion the default. The Go code review comments state that interfaces generally belong in the package that uses values of the interface type, not the package that implements them 40. A Go programmer who follows the style guide writes consumer-owned ports without having heard of hexagons.

The onion and the circles

Palermo's onion architecture of July 2008 kept the inversion and added structure inside the core 3. At the centre is the domain model; around it domain services; around those application services; and on the outside user interface, infrastructure and tests. The rule is stated flatly: code may depend on layers closer to the centre, never on layers further out, so the domain model is coupled only to itself. Palermo wrote for .NET teams and framed each ring as a project whose references point inward, which gives the pattern a mechanical enforcement that the hexagon lacks. Microsoft's own architecture guidance for ASP.NET Core applications describes the same arrangement, an application core with no dependency on infrastructure, and notes that it has gone by several names, hexagonal, ports and adapters, onion and clean 41.

Reenskaug and Coplien's DCI architecture of 2009 approached the same territory from a different concern 42. It separates what the system is, relatively dumb data objects, from what the system does, the roles those objects play in a use-case context. Its target was the readability of interactions, which in conventional object-oriented code are smeared across many classes. The data objects import nothing about any use case. Coplien and Bjørnvig built a method around it the following year 43.

Martin's clean architecture post of August 2012 presented itself as a unification 4. It named its precursors, hexagonal architecture, onion architecture, screaming architecture, DCI and BCE, and drew four circles: entities, use cases, interface adapters, and frameworks and drivers. The single rule, which Martin called the dependency rule, is that source code dependencies can only point inward; nothing in an inner circle can know anything at all about something in an outer circle, including names of functions, classes or variables declared there. The 2017 book develops the consequences at length 44. It treats a component as a unit of deployment, a jar or a DLL, and describes Main as the dirtiest, outermost component, merely a plugin to the application. It also insists that frameworks are details to be kept at arm's length, plugged in from outside rather than used as the base the entities are built on; a core that knows nothing of its framework at all is the difference between K3 and K4 on the ladder below.

That definition of a component is worth pausing on, because the architecture vocabulary does not agree with itself. The C4 model, the most widely used diagramming convention for software architecture today, defines a component as a grouping of functionality inside a container and states that components are not separately deployable; the container is the deployable unit 45. A reader moving between the two will find the same word naming units on opposite sides of the deployment boundary. Nothing in this article depends on either usage; the lab speaks only of modules, meaning units of compilation with declared dependencies.

Graça's widely read synthesis of 2017 drew hexagonal, onion, clean, CQRS and DDD into one diagram and argued that they compose rather than compete 46. The lab below reaches the same conclusion by a different route and puts a number on it.

The functional core

Bernhardt's 2012 talk on boundaries pushed the ladder to its top rung 47. His proposal was a core of pure functions over plain values, with no mutation and no input or output, wrapped in a thin imperative shell that performs every effect and holds almost no logic. A pure function cannot call a port, because calling a port is an effect. Seemann's 2016 essay made the resulting claim precise: functional architecture is ports and adapters, and more strictly so, because in a language that tracks effects the compiler rejects the impure call rather than a reviewer 48. Meszaros's humble object is the testing-side view of the same arrangement: move logic out of the object that is hard to test until what remains is too simple to need testing 49.

05Slicing the other way

Layers and rings cut an application horizontally, by technical role. A second line of thought cuts it vertically, by what the application is for, and it has run alongside the first for as long.

Fowler described event sourcing in 2005: capture every change to application state as an event, and rebuild state by replaying the events 50. Young's CQRS documents of 2010 separated the model that changes state from the model that answers queries, extending Meyer's command–query separation from individual methods to whole models 51,52. The two travel together often but need not. Both are orthogonal to the ring diagrams: they say how state is recorded and read, not what the core may import. Fowler's own note on CQRS is a caution, that for most systems it adds risky complexity 53. Chassaing's decider formulation of 2021 shows how far event sourcing can be pushed toward the functional core: an aggregate becomes a pure decide function from command and state to events, and a pure evolve function from state and event to state 54.

Martin's screaming architecture post of 2011 made the vertical argument about directory structure 55. A system's top-level folders should announce what it does, not which framework it uses. Fowler argued in 2015 that presentation, domain and data layers are a reasonable way to organise a small module but a poor way to organise the top of a large one, which should be divided by domain area first 56.

Bogard named vertical slice architecture in 2018 57. A slice contains everything one request needs, from endpoint to data access, and the stated aim is to minimise coupling between slices and maximise coupling within a slice. A handler is free to use the ORM context directly, so on the ladder the rung inside a slice is K1; the claim of the pattern is about the horizontal axis, what one slice may know of another, and there it is strict. The .NET ecosystem around slices leaned heavily on MediatR, Bogard's in-process mediator library; it is now a commercially licensed product of his company, Lucky Penny Software, with version 14.0.0 released in December 2025 58. An architecture's tooling is also one of its dependencies.

At the scale of a whole system the vertical cut becomes a module or a service. Lewis and Fowler's 2014 description of microservices organised them around business capabilities and made the boundary a network call 59. Newman's second edition of Building Microservices is candid that the boundary protects nothing if services share a database, and that a well-structured modular monolith is often the better starting point 60. The modular monolith is now supported by tooling that checks its boundaries. Spring Modulith treats each direct sub-package of an application's root package as a module, allows other modules to use only the types it exposes through named interfaces, and rejects cycles; ApplicationModules.verify() in a test fails the build on any violation 61. Version 2.0, released on 21 November 2025, moved to a Spring Boot 4 and Spring Framework 7 baseline 62.

The plug-in or microkernel architecture completes the set. POSA described the microkernel in 1996 23, and Richards's short catalogue of architecture patterns presents the plug-in form common in products, browsers and development environments: a minimal core defines contracts and plug-ins depend on it 63. It is the inverted arrangement applied to extension rather than to infrastructure, and it is one of the few in this set whose platforms usually make the rule impossible to break.

The vertical and horizontal cuts compose. A modular monolith can be hexagonal inside each module; a vertical slice can call a small domain model that owns its ports. Richards and Ford's textbook treats this as the normal state of affairs, with the top-level partitioning, technical or domain, as one of the most consequential early decisions 64, and Bass, Clements and Kazman's fourth edition frames all of these as tactics toward modifiability and testability rather than as styles to adopt whole 65.

06A ladder and an axis

The history suggests two instruments. The first is an ordinal scale for the rule itself: what may the code that carries policy import? The second is a nominal axis for what keeps the rule true. The plates at the end code twenty-five patterns and precursors on both, from each one's canonical source.

The ladder measures what is licensed, not what is wise. K1 is not a defect; for a small application whose database will outlive its business rules, the layer below is the right thing for the core to know, and Android's current guidance chooses it deliberately 29. The rung also measures only one boundary, the one between policy and the machinery that serves it. Two patterns at the same rung can partition the policy itself in completely different ways.

The coding rule is this: a plate sits on the rung that its canonical source states for the code it calls the core, and on the enforcement letter that source prescribes or clearly assumes. Evans's layered architecture is coded K1 because that is what its layer diagram permits, even though its repositories anticipate K3. Clean architecture is coded M because Martin defines components as separately deployable units with declared dependencies 44. Hexagonal architecture is coded N because Cockburn's article describes the structure without prescribing a mechanism 2.

The census has a clear shape. The rungs spread across the whole ladder, 1 at K0, 9 at K1, 3 at K2, 5 at K3, 6 at K4 and 1 at K5, and the families separate cleanly: the layered family averages rung 1.50, the inverted family 3.83. Enforcement does not spread. 14 of 25 plates rely on convention alone, and 18 of 25, 72%, prescribe nothing mechanical at all, only convention or review. The two axes are also close to independent. Plates with a mechanical enforcement average rung 2.43; plates without one average 2.33. Of the 12 plates at K3 or above, which make the strongest claims about what the core may not know, 3 are mechanically enforced, and those three are the onion, clean architecture and the microkernel. Only 14 of the 36 rung-by-enforcement cells are occupied, and the empty column for architecture tests has one entry, the modular monolith, which is also the most recent pattern in the set.

That is the first finding and the frame for the rest. The patterns that are most often compared to one another differ mainly in the rung they claim. The property that decides whether a codebase actually sits on that rung a year later is on the other axis, and the patterns are mostly silent about it.

07The lab

The lab is a single Python program using only the standard library, run at build time; its complete output is reproduced at the end of this section, and every number in the prose and figures is read from it. It builds reference dependency graphs for eight architectures at a chosen number of features F. Feature i uses features ⌊(i−1)/2⌋ and ⌊i/3⌋, which gives a small acyclic web in which feature 0 is the most depended upon. Every graph contains a web framework, a SQL driver and a composition root (main).

The architectures are generated from their canonical descriptions. Strict layered: per feature, a UI module that uses a service module that uses a data-access module that uses the driver, with entities in the data-access module; services use the services of features they depend on. Relaxed layered: the same, plus UI-to-data-access skips and cross-feature reads into other features' data access. Big ball of mud: relaxed layered plus random edges between any two application modules with probability 0.06, fixed seed. Hexagonal: per feature, a core, a web adapter and a SQL adapter, both adapters depending on the core. Onion: domain model, domain services and application services rings, with UI and infrastructure outside. Clean: entities, use cases, controllers, presenters, gateways, and web and database framework modules. Vertical slice: one module per feature using a shared ORM context. Functional core: a pure module and a shell per feature, with the shell holding all effects. Each module is tagged with one or more roles, ENTRY, POLICY, STORE, SQL, WEB or MAIN, so that the architectures can be compared role by role.

The program iterates only ordered lists, and its output is byte-identical under several values of Python's hash seed. Two metrics come from the literature. Propagation cost is MacCormack, Rusnak and Baldwin's measure: the density of the visibility matrix, the transitive closure of the dependency matrix with the diagonal set, or the share of module pairs in which a change to one could reach the other 66. It grew from the design-structure matrices of Baldwin and Clark 67 and Sangal and colleagues' use of them to manage layered software 68. NCCD is Lakos's cumulative component dependency normalised by that of a balanced binary tree of the same size, (n+1)log₂(n+1)−n 33.

E2 and E4: structure

At F = 8 the big ball of mud has a propagation cost of 83.26%, one strongly connected component containing 22 of its modules, and an NCCD of 5.641. Every other architecture is acyclic. Strict layering has a propagation cost of 23.18%, hexagonal 17.83%, onion 16.66% and clean 12.64%.

Two results in this table deserve attention. The first is that strict and relaxed layering have identical propagation cost, 23.18% each, although the relaxed graph has 66 edges against 49. Every skip that relaxed layering adds connects two modules that were already connected transitively, so the visibility matrix does not change. A metric built on reachability cannot see the difference between strict and open layering, which is precisely the difference the POSA pattern and Richards's advice are about 23,63. What changes is the number of direct couplings, each of which is a place where a change must be made rather than merely checked.

The second is that the lower propagation cost of the ringed architectures is bought with modules. Figure 4 plots the sweep of E4. Hexagonal architecture costs 3 modules per feature, the onion 5, clean architecture 7, the functional core 2 and vertical slices 1. Propagation cost falls as features are added for every architecture except the mud, which rises from 43.2% at two features to 97.0% at thirty-two, because its random edges grow with the square of the module count. NCCD, by contrast, rises slowly with size for the ringed designs, from 1.34 to 2.04 for clean architecture, while the vertical slices fall from 1.32 to 1.07: independent slices are the one arrangement whose testing cost per module shrinks as it grows.

E3: where the coupling goes

The blast radius of a change is the number of application modules that transitively depend on the changed one, and so must at least be rebuilt and retested. The lab measures it for four changes: replacing the SQL driver, replacing the web framework, changing a business rule in the most depended-upon feature, and adding a field to that feature's central entity.

The expected result is there. Replacing the SQL driver reaches 24 of 24 application modules in the strict layered design, every module in the system, and 8 of 24 in the hexagonal one, only the SQL adapters. In every layered variant all 8 policy modules can reach the driver; in hexagonal, onion, clean and functional-core designs none can. A unit test of one hexagonal core loads 2.88 application modules on average against 5.75 in the layered design.

The less advertised result is the other half of the table. A change to the business rule of the most-used feature reaches 15 of 24 modules in the layered design, 62.5%, and 23 of 24 in the hexagonal one, 95.8%. In clean architecture it reaches 55 of 56. Inversion does not reduce coupling. It moves it. In the layered design the most depended-upon thing is the data layer; after inversion it is the core, because every adapter now depends on the port it implements and therefore on the core that declares it. That is precisely the intent of the pattern, which bets that business policy changes less often than the technology around it, and Martin's stable-dependencies argument says the same thing in other words 32. But it is a bet, not a free improvement, and the lab makes its terms visible. Where the business rules are the volatile part, where they change weekly and the database never does, the inverted designs put the most frequent change at the point of widest impact.

The vertical slices show the third possible shape. A rule change in one slice reaches 0 other modules, because slices do not depend on one another, but an entity change in the shared ORM context reaches every slice, 8 of 9, and every slice's policy can reach the driver. Slicing buys isolation along the feature axis by giving up the isolation along the technology axis that the rings provide. The two cuts are complementary, which is why they compose.

E6: what stability metrics see

Martin's instability metric points the same way as the blast radius. Mean instability of the policy modules is 0.531 in the strict layered design and 0.281 in the hexagonal one; the stable-dependencies principle is violated on 5 edges of the strict layered graph, three of them service-to-data-access edges in the most depended-upon features, and on none of the hexagonal or clean graph's edges. Two cautions come with this. The relaxed layered graph has fewer violations, 2, than the strict one, because the extra skips give the data-access modules more dependents and so make them look more stable: the metric rewards adding coupling. And the onion graph has 4 violations, all between the application-services and domain-services rings of leaf features whose domain services happen to fan out to other features; the arrows point inward, as the pattern requires, and the metric flags them anyway. The metrics are useful signals and poor verdicts.

E7: are they different architectures?

The last structural experiment asks the question the names invite. For each architecture the lab builds a six-by-six matrix recording whether any module of one role can reach any module of another, and counts the cells, of thirty, on which two architectures disagree.

Hexagonal, onion and clean architecture are at distance 0 from each other. At the level of roles they are the same graph: the entry points and the stores depend on the policy, the policy reaches neither the store nor the driver, and only the composition root sees everything. They differ from strict layering on 5 of 30 cells, which are exactly the cells that express the inversion. The functional core is at distance 2 from them, because its shell merges the entry and store roles; the vertical slices are at distance 2 from layered and 7 from hexagonal. Strict and relaxed layering are at distance 0, which is E2's point again from another angle.

The differences among the three named inverted patterns are real, but they are differences inside the core: how many rings, which ring holds the use cases, whether framework annotations may touch the entities. Those are decisions about the horizontal axis of figure 6, 3, 5 or 7 modules per feature, not about which way the arrows point.

E5: how long a rung lasts

The final experiment is analytic and its parameters are illustrative, not measured, and it should be read that way. It asks how long a codebase stays on its rung under different enforcement. Suppose 3% of commits add an import that breaks the dependency rule, in four kinds: an inner ring importing an outer one within the same build module (40%); the core importing an adapter module, which would create a cycle (15%); the core declaring a new dependency on a framework (25%); and a framework annotation or type appearing in the domain (20%). Which mechanism catches which kind is by construction. Review is assumed to catch half of everything. A module graph catches only the cycle, because declaring a new dependency in a build file is permitted and moves within one module are invisible to it. An architecture test catches the three kinds for which rules were written; the fourth needs its own rule.

With convention alone the rung has a half-life of 23 commits. Review doubles it to 46. A module graph alone barely helps, 27, and adds nothing once architecture tests are present: tests alone and tests with modules both give 115. Tests with review give 231. Only a rule set that covers every kind of violation stops the leak entirely. The particular numbers are artefacts of the assumptions; the ordering is not, because it follows from what each mechanism can see. Separate build modules, the enforcement most often recommended for onion and clean architecture, prevent exactly one kind of erosion, the cycle. The real protection is a written rule for each kind of violation, run on every build.

The empirical literature supports the premise, if not the parameters. Perry and Wolf named erosion in 1992 18; Lehman's laws of software evolution predicted increasing complexity unless work is done to reduce it 69; Eick and colleagues found statistical evidence of code decay in a large telephone switching system 70; de Silva and Balasubramaniam's survey of controls for architecture erosion found the problem pervasive and the remedies mostly partial 71; and Le and colleagues found architectural decay across the versions of the open-source systems they studied 72. Murphy, Notkin and Sullivan's reflexion models of 1995 were an early attempt at the fix the lab points to: compare the intended module structure with the one extracted from source, and report the divergences 73.

08Keeping the rule

If the rung is decided by the pattern and kept by the mechanism, the useful question for any platform is which mechanisms it offers. Every mainstream ecosystem now has at least one, and several have three.

Java. ArchUnit checks architecture rules as ordinary unit tests over compiled bytecode, and ships ready-made rule builders for layered and onion architectures 74. Because it analyses bytecode it sees annotations and types in method signatures, the fourth kind of violation in E5, as easily as imports. The Java Platform Module System, delivered in JDK 9 through JEP 261, adds language-level enforcement: a module must declare what it requires and what it exports, and unexported packages cannot be accessed from outside 75. jMolecules offers annotations that name architectural roles, such as ports, adapters and layers, in code, with matching ArchUnit rules 76, and Spring Modulith verifies module boundaries in a test and can run jMolecules rules alongside 61.

C# and .NET. The conventional solution layout, visible in Jason Taylor's widely used clean architecture template, is one project per ring with project references pointing inward 77. That makes direction a property of the build, the M of the enforcement axis, and the E5 result applies: the project graph prevents cycles but not a new package reference in the domain project. NetArchTest supplies the test-level rules, with a fluent API modelled on ArchUnit 78.

Go. Go has two relevant language rules. The consumer-side interface convention described in section 4 makes K3 the idiomatic default 40. And the internal directory, introduced in Go 1.4 in December 2014, makes a package importable only by code rooted at the parent of the internal directory 79. Adapters placed under internal/ cannot be imported by another module at all.

Python. Python has no compile-time module boundary, so the mechanism must be a test. Import Linter checks contracts over the import graph: a layers contract forbids lower layers from importing higher ones, a forbidden contract bans particular imports, and an independence contract keeps sibling packages apart 80. Percival and Gregory's Architecture Patterns with Python is the fullest treatment of the inverted architectures in the language, built around repositories, a service layer and a unit of work, with the domain model free of any ORM import 81.

TypeScript and JavaScript. dependency-cruiser validates the module graph against rules written as data, and can express the strictest form of the dependency rule directly: nothing under src/domain may import anything outside it 82.

Rust. A Cargo workspace makes each ring a crate with its own dependency list, and the language's visibility rules, pub, pub(crate) and module privacy, decide what one crate can see of another 83. A domain crate whose manifest does not list the database or web crates cannot name them; the port is a trait in the domain crate and the adapter crate implements it.

None of these tools decides what the rule should be. They make a written rule cheap to keep, which E5 suggests is the larger part of the problem. The written rule can itself be recorded: Nygard's architecture decision records, short documents with a context, a decision and its consequences, are the lightest-weight way to say which rung a codebase is meant to occupy and why 84. The masthead of this article is written in that form.

09Choosing

The lab and the census suggest a way of choosing that starts from the two axes rather than the names.

First, decide what changes most. E3 showed that inversion moves the widest blast radius from the infrastructure to the core. If the database, the message broker, the delivery channel or a third-party API is likely to be replaced or multiplied, and the business rules are comparatively stable, an inverted design puts the frequent change where it is cheapest. If the rules are the volatile part and the infrastructure is settled, a layered design is not a compromise; it is the design whose most-depended-upon part is the one that changes least. Conway's observation that systems mirror the communication structure of the organisations that build them 85 adds a second input: a team that owns a database schema used by many applications will experience it as the stable centre whatever the diagram says.

Second, choose the rung, not the name. If the goal is to keep policy testable without infrastructure, K3 is sufficient and ports and adapters is the least ceremonious way to reach it, at 3 modules per feature in the lab. Onion and clean architecture reach K4 by adding rings inside the core; they are worth their 5 and 7 modules per feature when the core itself is large enough that its internal structure needs its own rules. K5, a functional core, is the strongest guarantee and the cheapest in modules, but it asks the team to express policy as pure computation, which is a larger change of habit than any directory layout.

Third, choose the cut. Rings and slices are complementary. A system with many loosely related features and thin logic in each benefits most from slices; a system with a rich shared model benefits most from rings; most real systems have both regions. The modular monolith with hexagonal modules is the combination the current tooling supports best 61.

Fourth, choose the mechanism before writing the first line. The rung a codebase is on after a year is decided on the enforcement axis. A rule written as an architecture test on day one costs a few lines; the same rule retrofitted after erosion costs a migration. E5's ordering holds under any parameters: convention decays fastest, separate build modules stop only cycles, and a test per kind of violation is what actually holds the line.

Richards and Ford state the first law of software architecture as the claim that everything in it is a trade-off 64. The contribution of the ladder is to make one of those trade-offs explicit and measurable: each rung up buys isolation of policy from infrastructure, and pays for it with modules, with indirection, and with a larger blast radius for changes to the policy itself.

12Limits

The reference graphs are generated from canonical descriptions, not extracted from real systems, and the feature web is small and regular. Real codebases have far more modules per feature, many more cross-feature edges, and shared kernels that none of the generators include. The results that depend only on the shape of the rules, the identity of the three inverted patterns at role level, the relocation of blast radius, the blindness of propagation cost to open layering, are robust to that. The specific percentages are not claims about any real system.

E5 is explicitly illustrative. Its catch matrix follows from how each mechanism works; its violation rate, mix and review effectiveness are assumptions chosen to be plausible, and a different mix would change every half-life. Only the ordering of mechanisms should be taken from it.

The plate codings are judgements about canonical sources. Several patterns are practised at a different rung from the one their source states, most obviously DDD's layered architecture, which in practice is usually implemented with inverted repositories, and hexagonal architecture, which is often enforced with architecture tests even though the pattern does not require them. The ledger records the source, not the practice.
