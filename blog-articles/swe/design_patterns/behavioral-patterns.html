When is it decided what runs?

Behavioral design patterns, from Strategy to Observer, read as a single move: taking a decision out of a conditional and making it later. How late, and who then gets to make it, predicts what each pattern costs and where it lives today.

§1 The question

Every behavioral pattern in the 1994 catalogue by Erich Gamma, Richard Helm, Ralph Johnson and John Vlissides starts from the same place: a piece of code that asks a question and branches on the answer. Which algorithm? Which handler? Which state am I in? Who needs to hear about this? The Gang of Four describe the behavioral family as concerned with algorithms and the assignment of responsibilities between objects, and they sort its eleven members, alongside five creational and seven structural patterns, by purpose and by whether the relationship is fixed through classes or through objects 1. That classification is useful for finding a pattern. It says little about what a pattern does to a program.

This article proposes a different organising question: when is it decided what runs? Each behavioral pattern takes a decision that was written into a conditional and moves it somewhere later. Template Method moves it to the moment a subclass is defined. Strategy moves it to the moment an object is built. Command and Visitor move it to the moment of the call. State moves it into the object's own history. Observer and Chain of Responsibility move it out of the object altogether, into whichever other parts of the program have registered a receiver by the time the event fires. The refactoring literature names the first step of that journey directly: replace a conditional with polymorphism 2,3.

Moving a decision later buys flexibility, the ability to add a case without editing the code that dispatches on it, which is the open–closed principle Bertrand Meyer set out in 1988 4. It also costs something specific. The later the decision, the less the source text at the point of dispatch tells a reader about what will happen there. At the earliest rung the answer is in a class declaration. At the latest it depends on the order in which unrelated modules happened to subscribe.

The article places thirteen patterns on a six-rung ladder of decision time, the eleven from the catalogue plus Null Object and the reactive stream, and checks each placement by executing a canonical implementation and perturbing it. The result is a pattern in the patterns. Of the 8 that decide at the call or earlier, 6 now live inside languages or standard libraries as syntax or ordinary types: lambdas, generators, pattern matching, abstract base classes. None of them needed a framework. All 3 that decide by membership, the ones where a third party determines what runs, did acquire one, with its own rules about ordering, propagation and flow control. What late patterns defer is not a choice among alternatives but an ordering among many receivers, and ordering is semantics that a lambda cannot carry.

Along the way the article gives the history of the catalogue, a plate for each pattern in the catalogue's own spirit of fixed headings, worked examples in Java, Python, C++, JavaScript, TypeScript, Go and Rust, eight experiments that measure the costs each pattern trades in, and a review of what controlled studies have found. Every listing was compiled and run, and every number comes from the lab described in the final section.

§2 Where the catalogue came from

The word pattern came to software from architecture. Christopher Alexander and his colleagues published A Pattern Language in 1977: 253 named solutions to recurring problems of building, from the scale of regions down to window seats, each written in a fixed form and each linked to the larger and smaller patterns it completes 5. Its companion, The Timeless Way of Building, argued that such a language lets ordinary people make places that work 6. The form mattered as much as the content. A pattern named a problem, described the forces in tension, gave a solution and said what it led to next.

Software borrowed the form a decade later. At OOPSLA in 1987 Kent Beck and Ward Cunningham reported that a small pattern language of five patterns had let Smalltalk novices design usable window interfaces 7. Smalltalk had already been supplying the raw material. Its class library included a dependents mechanism through which any object could be told when another changed, which is the Observer pattern as a built-in facility 8. Trygve Reenskaug's 1979 note at Xerox PARC had described models, views and controllers 9, and Glenn Krasner and Stephen Pope's 1988 cookbook showed how Smalltalk-80 wired them together through that dependency mechanism 10. On the C++ side, James Coplien's 1992 book collected idioms that captured recurring design moves in the language's own terms 11.

Gamma, Helm, Johnson and Vlissides presented a first catalogue at ECOOP in 1993 12, and the book followed at OOPSLA in October 1994 with 23 patterns, sample code in C++ and Smalltalk, and a template of fixed headings (intent, motivation, applicability, structure, participants, collaborations, consequences, implementation, known uses and related patterns) that made every entry comparable 1. The first Pattern Languages of Programs conference met the same year, and its proceedings appeared in 1995 13. Architectural pattern systems followed within two years 14, and a second volume in 2000 added patterns for concurrent and networked objects such as Reactor, a demultiplexer that dispatches events to registered handlers and is Observer at the scale of an operating-system event loop 15. Bobby Woolf's Null Object appeared in the third PLoP volume in 1998 16.

The catalogue drew criticism almost at once, and the criticism is where this article's question begins. In 1996 Peter Norvig argued that 16 of the 23 patterns became invisible or much simpler in a dynamic language with first-class functions, types and generic dispatch 17. His point was that many patterns are workarounds for missing language features. The sharper version of that point, visible only with thirty years of hindsight, is that the features arrived for some patterns and not others. Figure 1 lines the two histories up. Left of the axis is the pattern literature. Right of it is the steady absorption of patterns into languages: CLU's iterators in 1977 18, Dan Ingalls's double dispatch in 1986 19, the STL's iterators 20, Python's generators 21, lambdas in Java 8 22, the iteration protocols of ECMAScript 2015 23, sealed types and pattern matching in Java 17 and 21 24,25. Observer followed a different road. Java deprecated its Observable class in version 9 26, the same release that adopted the Reactive Streams interfaces as java.util.concurrent.Flow 27,28.

A second line of criticism asked whether patterns belong in code at all. Jan Hannemann and Gregor Kiczales reimplemented all 23 in AspectJ and found modularity improvements in 17, largest where one object played several roles or many objects played one role, the crosscutting shape that Observer and Mediator have 29. The expression problem, named by Philip Wadler in 1998, gave Visitor a formal setting: a data type defined by cases should let you add new cases and new functions over it without recompiling existing code and without giving up static typing 30. John Reynolds had described the two halves of that tension in 1975 31, and William Cook sharpened it into the contrast between objects and abstract data types 32.

§3 A ladder of decision time

The ladder has six rungs, named for the latest moment that can change which code runs at the point of dispatch. Rung D0 is the conditional itself, the if or switch the pattern replaces, where the answer is written into the text. D1 is definition: the choice is made by which class you write. D2 is construction: the choice is fixed when an object is built, typically by passing in a collaborator. D3 is invocation: the caller supplies the choice with each call. D4 is own history: the object's earlier calls determine what a later call does. D5 is membership: parties other than the caller and the object, acting through a registration interface, determine what runs.

A placement on this ladder should be checkable rather than asserted, so the lab turns each rung into a test. For each pattern it builds a canonical Python implementation, records the set of functions executed during one key operation, and compares that set across pairs of fresh objects that differ in exactly one respect: a different class in the same role (T0), a different constructor argument (C), a different call argument (I), a different own history before the call (S), or a receiver registered by a third party (M). The rung is the latest test that changes the executed set. Figure 2 shows the result for all thirteen.

Twelve of the thirteen land where their definitions predict: Template Method alone at D1, Strategy, Null Object and Interpreter at D2, Command, Iterator, Visitor and Mediator at D3, State at D4, and Observer, Chain of Responsibility and the reactive stream at D5. The two patterns the Gang of Four classify as class-scoped, Template Method and Interpreter, are the two earliest on the ladder 1, which is what the ladder should say about relationships fixed through inheritance.

The thirteenth result is the most informative. Memento changes nothing under any perturbation: restoring a different snapshot runs exactly the same code, 2 functions in the lab's trace. Memento sits off the ladder because what it defers is data, not behaviour. It is the half of undo that remembers what the state was, where Command is the half that remembers what was done, and the Gang of Four pair them for that reason 1. The ladder's inability to place Memento is a check that it is measuring dispatch rather than anything that varies.

Two placements depend on the implementation, and the plates say so. Chain of Responsibility fires both the invocation and the membership tests, because which handler answers depends on the request and on who has joined the chain. A Strategy with a public setter would fire the membership test too; the canonical form in the lab is configured once, at construction. Rungs describe a pattern as usually built, not every program that uses the name.

§5 Deciding before the call

The four patterns at D1 and D2 fix the choice before any call is made. They are the patterns that most resemble a language feature, because they amount to passing a piece of behaviour as a value.

Strategy

Strategy is the clearest case of a pattern dissolving into syntax. In the catalogue it is a class hierarchy: an abstract strategy, concrete strategies, and a context holding a reference to one of them 1. In Java since version 8 it is a lambda or a method reference, and the standard Comparator interface ships combinators for composing strategies without naming a class at all 22. Python went further in the same direction. Its sorting functions take a key function, and Python 3 removed the older comparison-function parameter, leaving a helper to convert old comparison functions into key functions 35. Go shows the same arc inside one language: the original sort package required a type implementing an interface with three methods, Go 1.8 added a function taking a comparison closure, and Go 1.21's generic slices package made the closure the ordinary way to sort 51,52.

C++ adds a rung below. A policy class passed as a template parameter makes the strategy a compile-time choice, which Andrei Alexandrescu developed into policy-based design 36. In the ladder's terms that moves Strategy from D2 to D1: the choice is made by the type you instantiate, and the compiler can inline it. The pattern has not changed; the decision time has.

What survives from the catalogue's version is its stated cost. Clients must know the strategies exist in order to pick one 1. A lambda does not change that. It only makes the choice cheaper to express.

Template Method

Template Method is inheritance used as a hook mechanism: the base class owns the sequence and calls abstract or overridable steps that subclasses fill in. The Gang of Four connect it to the Hollywood principle, in which the parent calls the child rather than the reverse 1. Johnson and Foote had described the same inversion of control as the defining property of frameworks in 1988 33, and Martin Fowler's later account of inversion of control traces the idea through framework design 53. The pattern is so common in standard libraries that it rarely gets named. Java's AbstractList documentation tells an implementer that supplying two methods yields a working unmodifiable list, with iteration, search and sub-lists inherited from the template 34.

The lab places it at D1, the only pattern there. Two SalesReport objects with different titles execute the same five functions; only a different subclass changes them. That is its strength, since the order of steps is visible in one place and cannot be rearranged at run time, and its limit, since a live object cannot swap a step.

Null Object

Null Object replaces a null reference with an object that has the expected interface and does nothing 16. The lab's service executes three functions whether its logger records lines or discards them; only the construction argument differs. The price is that absence becomes invisible. A null reference fails loudly at the first use, where a null object succeeds quietly forever, which is exactly right for an optional logger and exactly wrong for a missing payment gateway.

Interpreter

Interpreter maps each grammar rule to a class and evaluates a sentence by walking the tree of instances 1. The program being interpreted is data, supplied when the tree is built, so the lab places Interpreter at D2: a different tree runs different code, a different context of variable bindings does not. The Gang of Four limit the pattern to simple grammars and recommend parser generators for anything larger 1. It remains hand-written because every little language is different, but its evaluation half is where the next rung's Visitor usually takes over.

§6 Deciding at the call

At D3 the caller supplies the decision with each call. All four patterns here make the choice an argument: a command to run, an aggregate to traverse, an operation to apply, an event to route.

Command and the price of undo

Command turns a request into an object so it can be stored, queued, logged, composed into macros and undone 1. The first half of that list is now a closure. The second half is still application code, because undo needs either an inverse for each command or a copy of the state it destroyed. Java's Swing toolkit has carried an undo framework of edit objects and an undo manager for decades 37; Redux makes every state change an action object applied by a pure function, which is what lets its tools replay history 38; event sourcing stores the commands, or rather the events they produced, as the system of record and rebuilds state by replaying them 44. Game engines use the same move for input handling and undo 54.

The storage side of that choice is measurable. The lab applies 3,000 random insertions and deletions to a document and keeps the history three ways: a full snapshot after every edit (pure Memento), only the inverse commands (pure Command), and snapshots every k edits with commands between. Replaying the inverses reconstructs all 3,001 states exactly. Full snapshots cost 23,577,838 bytes against 71,489 for commands alone, 329.8 times as much, but commands alone need a mean of 1,500 replay steps to reach an arbitrary point. Checkpoints every 64 edits cost 433,391 bytes with a mean replay of 16.2 steps. Figure 3 shows the whole trade. Event-sourced systems snapshot periodically for exactly this reason 44.

Iterator

Iterator is the most thoroughly absorbed pattern of all. The catalogue distinguishes external iterators, where the client asks for the next element, from internal ones, where the aggregate applies an operation to each element 1. CLU had iterators as a language construct in 1977, procedures that yield values to a loop body 18, and Barbara Liskov's history of the language describes how they came in 55. The STL made iterators the glue between generic algorithms and containers 20. Python added an iterator protocol in 2001 and generators the same year 21,56, C# has yield 39, ECMAScript 2015 standardised iteration protocols and generator functions 23, and Rust builds its for loop on an iterator trait 42.

The generator is not just shorter than a hand-written iterator class. It changes what the pattern costs, because a lazy pipeline only pulls what its consumer asks for. The lab builds a map-then-filter pipeline over a million-element source and asks for the first ten matches. At a selectivity of 0.5 the lazy pipeline draws 20 elements from the source, where an eager version touches 2,000,000; at 0.001 it draws 11,448, still 175 times fewer (Figure 4). An external iterator is a decision at invocation that the consumer, not the producer, controls how much work is done.

Visitor and the expression problem

Visitor lets you add operations over a fixed set of element classes without touching them. Each element's accept method calls back the visit method for its own type, a double dispatch that Ingalls had described for mixed-type arithmetic in Smalltalk 1,19. The catalogue states the cost plainly: adding a new element class is hard, because every visitor must change 1. That is one side of the expression problem 30; ordinary methods on each class are the other.

The lab measures the trade by generating real source for a growing system in three styles and counting how many pre-existing units each change edits. With 10 types and 6 operations, adding an operation to methods-on-classes edits all 10 classes; with Visitor it edits none. Adding a type edits 7 existing units under Visitor (the visitor interface and all 6 visitors) and none under methods-on-classes. The break-even share of type additions is (M+1)/(N+M+1), 0.412 for that shape. Over 60 randomly growing systems per mix, starting from four types and three operations, the curves cross at 0.509 (Figure 5).

Pattern matching over a closed hierarchy edits exactly the same units as Visitor in every one of those runs; its curve lies on top of Visitor's. That is the point. Java's sealed interfaces with exhaustive switch patterns, C++'s std::variant with std::visit, and Python's singledispatch are not a solution to the expression problem 24,25,40,41,57. They are Visitor's side of it with the boilerplate removed and, in the statically typed cases, with the compiler guaranteeing that a new case is not forgotten, the property the Java listing's comment points at. Python's own ast module still ships a NodeVisitor class that dispatches by method name, the pattern in its original shape 58. The research literature has pursued the other side, extensible visitors and generic walkers that loosen the fixed set of element types 59,60.

Mediator

Mediator makes colleagues talk through one object instead of to each other 1. The lab's font dialog routes a change in one widget to the others; which widgets are updated depends on who reported the change, so it sits at D3. The lab also counts where the interaction rules end up. With 40 colleagues each interacting with three others, direct references total 120 and no class holds more than 3 rules; with a mediator, references rise to 160 and a single class holds all 120. Adding a colleague edits one class instead of three. Mediator does not remove coupling. It moves the knowledge into one place, which is easier to find and harder to keep small, the monolith the catalogue warns about 1.

§7 Deciding by history

At D4 the object decides for itself, based on what has already happened to it. Only State sits here, and the lab confirms it is the only pattern whose executed code changes when nothing differs but the object's own earlier calls.

State

The catalogue's State example is a TCP connection whose open, close and acknowledge requests behave differently depending on whether it is closed, listening or established, implemented by delegating each request to a swappable state object 1. The pattern trades a conditional over the object's mode for one class per mode. What it does not supply is a rule for events a state was never taught to handle. In the canonical form, the abstract state class provides a default, usually doing nothing.

The lab takes that example at its word. It encodes the summary state diagram of RFC 793 61, which RFC 9293 now carries forward 62, as eleven State classes over ten events, with a base class that ignores anything not drawn. The diagram has 19 transitions among 110 state–event cells, so 91 cells, 82.7%, are handled by the default (Figure 6). The State implementation and a plain transition table produce identical traces over all 11,110 event sequences of length one to four; the pattern changes the code's shape, not its behaviour. Across those sequences 77.9% of steps land in a default cell, and in a uniform random walk of events 83.1% do. RFC 793 itself says its diagram is only a summary and not the total specification; the event-processing rules elsewhere in the document define responses, resets among them, for cases the diagram omits 61. A State implementation built from the diagram alone fills those cells with silence.

Two lines of work push the missing cells back into view. David Harel's statecharts added hierarchy, so a superstate can define what its substates do by default, along with orthogonal regions and broadcast events 63, and the W3C's SCXML gives statecharts a standard executable form 43. Typestate, introduced by Robert Strom and Shaula Yemini in 1986, moves the state into the type so an invalid call is rejected before the program runs 64. Rust's book teaches both: it first implements a blog post's workflow as State objects behind trait objects, then re-encodes the states as distinct types so that calling a method in the wrong state does not compile 42.

Typestate pulls State from D4 down to D1. The decision is still made by history, but the compiler tracks that history, and the reader of a call site can see from its type which behaviour runs. The cost is that the history must be linear enough for the type system to follow; a connection held in a collection alongside others in different states needs the run-time version back. Game programmers reach for the pushdown and hierarchical variants of State for the same reason statecharts exist 54.

Memento

Memento captures an object's internal state in an opaque token that a caretaker can hold and later hand back, preserving the object's encapsulation 1. As the ladder showed, it does not move any dispatch decision. Its cost is the one measured in the Command section, and its modern home is serialisation and periodic snapshots in event-sourced stores 44.

§8 Deciding by membership

At D5 neither the caller nor the object decides what runs. Other parts of the program do, by registering receivers. This is where the patterns acquired runtimes, and the lab's two experiments here show why.

Observer

Observer lets any number of dependants register with a subject and be notified when it changes 1. It is the oldest behavioral pattern in running code, present as Smalltalk's dependents mechanism before it had a name 8,10. The catalogue already lists its central hazard: because observers do not know about each other, one change can set off a cascade of updates whose cost and order nobody chose 1.

The hazard has a precise form. When two observers of a source are both observed by a third, the third can recompute after the first update and before the second, reading one fresh input and one stale one. Reactive-programming research calls that a glitch, and systems that avoid it propagate changes in topological order 65,66. The lab builds random dependency graphs and propagates a change two ways: naive observer push, where each node notifies its dependants depth-first as soon as it changes, and topological order. Both end with correct values. The naive version gets there by recomputing 1.75 to 3.52 times as many nodes as were affected, and 11.6% to 38.7% of its recomputations read a stale input; topological propagation recomputes each affected node once, with no glitches. On a chain of diamonds the growth is exponential. With twelve diamonds in series, naive push performs 16,380 recomputations against 36 and the final join runs 4,096 times for a single change (Figure 7).

That is why Observer did not become syntax. Java deprecated Observable in version 9, and its documentation gives the reasons: the event model is limited, the order of notifications delivered by Observable is unspecified, and state changes do not correspond one-for-one with notifications 26. The replacements are runtimes with defined semantics. The DOM's event dispatch defines capture, target and bubble phases and lets a listener stop propagation or register to run once 45. Node's EventEmitter warns when more than ten listeners attach to one event, a heuristic for the forgotten-listener leak 46. .NET defines the pattern through IObservable and IObserver interfaces 67. Erik Meijer's Reactive Extensions recast an observable as the mathematical dual of an enumerable, so the whole query vocabulary of collections applies to events 47, a line of work that goes back to functional reactive animation 68. Ingo Maier, Tiark Rompf and Martin Odersky titled their 2010 report Deprecating the Observer Pattern and catalogued the ways callback-based code resists composition and reasoning 69. The newest descendant, a TC39 proposal for signals backed by the authors of many JavaScript frameworks, is explicitly about the semantics of a dependency graph: it specifies automatic dependency tracking and evaluation that avoids glitches, and it remains at Stage 1 70.

Chain of Responsibility

Chain of Responsibility passes a request along a sequence of handlers until one accepts it. The catalogue names its two costs: receipt is not guaranteed, and the sender cannot tell which handler will act 1. In current code the pattern is the middleware pipeline. Servlet filters pass the request down a filter chain 48, ASP.NET Core documents that middleware order defines behaviour and that any component may short-circuit the rest 49, Express passes a next function to each layer 50, and in Go the idiom is a handler that wraps another handler from the standard net/http package 71. DOM events propagate through the tree the same way 45.

Order in a chain is behaviour, not decoration. The lab models eight handlers, one per request type, with request types following a Zipf distribution. Sorting handlers by frequency gives a mean of 2.796 handlers consulted per request; the reverse order gives 6.204; the average over all 40,320 orders is 4.500 (Figure 8). A single interceptor registered at the front by another module adds a hop to every request, 35.8% on the sorted chain, and removing the most frequent handler leaves 39.8% of requests traversing the whole chain to fall off its end. A catch-all registered first silences every handler behind it. None of these outcomes is visible at the call site; all of them are decided by registration.

Reactive streams

The reactive stream is Observer with the two missing rules added: composition, so a stream can be mapped, filtered and merged like a collection, and flow control, so a slow consumer can tell a fast producer how much it can take. The Reactive Streams specification, released in 2015, standardised four interfaces for asynchronous streams with non-blocking backpressure 28, and JDK 9 adopted them as java.util.concurrent.Flow 27. In the ladder's terms nothing moved: what runs is still decided by who subscribed. What changed is that the runtime now owns the questions of order and rate that the catalogue's Observer left to the application.

§9 What the evidence says

Controlled studies of patterns are fewer than the patterns' reputation would suggest, and their findings are mixed in a way that fits the ladder. Lutz Prechelt and colleagues gave professional engineers nine maintenance tasks on programs written with and without patterns. Most tasks showed a benefit or no cost from the pattern version, but one application of Observer that looked well justified produced a negative effect, and the authors concluded that the flexibility of a pattern is usually worth having unless there is a clear reason to prefer the simpler design 72. A replication with paid professionals working in a real development environment extended the result 73.

Marek Vokáč followed a commercial C++ product of about 500,000 lines through three years of weekly maintenance and compared defect rates for classes taking part in patterns with the code at large. Rates ranged from 63% to 154% of the average across patterns. Observer and Singleton tended to appear in the complex parts of the system and so marked code needing attention; Factory appeared in simpler code with fewer defects; Template Method showed no clear tendency 74. On the ladder, the latest-deciding pattern in that study is the one found in the hardest code.

Guido Salvaneschi and colleagues tested the reactive alternative to Observer directly. Subjects given reactive versions of programs understood them significantly better than subjects given Observer-based versions 75, and a larger follow-up with 127 subjects confirmed the effect 76. Other studies look at particular patterns, such as how the way a Visitor is drawn in a class diagram affects the effort of understanding it 77, or at quality attributes in general, where developers' ratings show patterns do not always improve them 78. Systematic reviews of the whole field find the evidence thin, uneven across patterns, and hard to generalise 79,80.

Read together, these studies say something narrower than either the enthusiasts or the critics of patterns. Patterns that decide early are rarely where the trouble is found. The pattern that decides by membership recurs as the one associated with complex code, surprising maintenance cost, and a measurable comprehension penalty against an alternative that adds ordering semantics.

The explanation the experiments support is that early patterns defer a choice, and a choice is a value. Once a language can pass behaviour as a value, whether a lambda, a generator or a case of a sealed type, the pattern becomes a way of writing that value. Late patterns defer an ordering among receivers that nobody at the call site controls. The practical reading is a question to ask before reaching for a behavioral pattern: when will the decision be made, and who will be able to see it? If the answer is at the call or earlier, the pattern is probably a language feature in your language already, and the idiomatic form is the one to use. If the answer is by whoever registers, use the ordering rules of an existing runtime rather than writing Observer from the catalogue.

_HARNESS = {"trace", "classify", "<lambda>", "Sample.__init__", "_tree", "<genexpr>"}


def trace(fn):
    seen = []
    this = __file__

    def prof(frame, event, arg):
        if event == "call" and frame.f_code.co_filename == this:
            q = frame.f_code.co_qualname
            if q not in _HARNESS and not q.startswith("<lambda>"):
                seen.append(q)
    sys.setprofile(prof)
    try:
        fn()
    finally:
        sys.setprofile(None)
    return frozenset(seen), len(seen)


def classify(s):
    a0, a1 = s.args
    res = {}
    oa, ob = s.make("a"), s.make("b")
    ca, _ = trace(lambda: s.op(oa, a0)); cb, _ = trace(lambda: s.op(ob, a0))
    res["C"] = ca != cb
    oa, ob = s.make("a"), s.make("a")
    ca, _ = trace(lambda: s.op(oa, a0)); cb, _ = trace(lambda: s.op(ob, a1))
    res["I"] = ca != cb
    oa, ob = s.make("a"), s.make("a")
    s.history(oa)

        oa, ob = s.make("a"), s.make("a")

def gen_units(style, types, ops):
    u = {}
    if style == "oo":
        for t in types:
            body = "".join(f"    def {o}(self): return '{o}:{t}'\n" for o in ops)
            u[f"class {t}"] = f"class {t}(Node):\n{body}"
    elif style == "visitor":
        u["interface Visitor"] = "class Visitor:\n" + "".join(
            f"    def visit_{t}(self, n): raise NotImplementedError\n" for t in types)
        for t in types:
            u[f"class {t}"] = f"class {t}(Node):\n    def accept(self, v): return v.visit_{t}(self)\n"
        for o in ops:
            u[f"visitor {o}"] = f"class {o.title()}(Visitor):\n" + "".join(
                f"    def visit_{t}(self, n): return '{o}:{t}'\n" for t in types)
    elif style == "match":
        u["sealed Node"] = "Node = " + " | ".join(types) + "\n"
        for t in types:
            u[f"record {t}"] = f"@dataclass(frozen=True)\nclass {t}: pass\n"
        for o in ops:
            u[f"fn {o}"] = f"def {o}(n):\n    match n:\n" + "".join(
                f"        case {t}(): return '{o}:{t}'\n" for t in types)
    return u


def edits(before, after):
    return sum(1 for k in before if k in after and before[k] != after[k])

def make_dag(n, rng):
    ns = max(2, n // 10)
    parents = {i: [] for i in range(ns)}
    for i in range(ns, n):
        parents[i] = sorted(rng.sample(range(i), 2))
    children = {i: [] for i in range(n)}
    for i, ps in parents.items():
        for p in ps: children[p].append(i)
    return ns, parents, children


def run_prop(n, parents, children, src, mode):
    val = {i: (i if not parents[i] else 0) for i in range(n)}
    for i in range(n):
        if parents[i]: val[i] = sum(val[p] for p in parents[i]) + 1
    # affected set and final values
    aff = set([src]); stack = [src]
    while stack:
        x = stack.pop()
        for c in children[x]:
            if c not in aff: aff.add(c); stack.append(c)
    final = dict(val); final[src] = val[src] + 1000
    for i in range(n):
        if parents[i] and i in aff: final[i] = sum(final[p] for p in parents[i]) + 1
    recomputes = 0; glitches = 0; per = {}
    val[src] += 1000
    def recompute(i):
        nonlocal recomputes, glitches
        recomputes += 1; per[i] = per.get(i, 0) + 1
        if any(val[p] != final[p] for p in parents[i]): glitches += 1
        val[i] = sum(val[p] for p in parents[i]) + 1
    if mode == "naive":
        sys.setrecursionlimit(100000)
        def push(x):
            for c in children[x]:
                recompute(c); push(c)
        push(src)
    else:
        for i in sorted(aff - {src}): recompute(i)
    ok = all(val[i] == final[i] for i in range(n))
    return recomputes, glitches, len(aff) - 1, max(per.values()) if per else 0, ok

    hdr("E3  Observer propagation: naive depth-first push vs topological order")
    rng = random.Random(SEED + 3)
    rows = []
    for n in (10, 20, 40, 80, 160):
        agg = {"naive": [0, 0, 0, 0], "topo": [0, 0, 0, 0]}; okall = True; trials = 40
        for t in range(trials):
            ns, par, ch = make_dag(n, rng)
            src = rng.randrange(ns)
            for mode in ("naive", "topo"):
                rc, gl, af, mx, ok = run_prop(n, par, ch, src, mode)
                a = agg[mode]; a[0] += rc; a[1] += gl; a[2] += af; a[3] = max(a[3], mx)
                okall &= ok
        r = dict(n=n,
                 naive_recompute=agg["naive"][0] / trials, naive_glitch=agg["naive"][1] / trials,
                 affected=agg["naive"][2] / trials, naive_max=agg["naive"][3],
                 topo_recompute=agg["topo"][0] / trials, topo_glitch=agg["topo"][1] / trials,
                 correct=okall)
        r["amplification"] = r["naive_recompute"] / max(r["affected"], 1e-9)

    # diamond chains: k diamonds in series
    chain = []
    for k in range(1, 13):
        n = 1 + 3 * k; parents = {0: []}; nxt = 1; top = 0

            l, r_, j = nxt, nxt + 1, nxt + 2

            top = j; nxt += 3
        children = {i: [] for i in range(n)}
        for i, ps in parents.items():
            for p in ps: children[p].append(i)
        rc, gl, af, mx, ok = run_prop(n, parents, children, 0, "naive")
        rt, gt, _, _, _ = run_prop(n, parents, children, 0, "topo")
        chain.append(dict(k=k, naive=rc, topo=rt, glitch=gl, last=mx, ok=ok))
    say("diamond chains (k diamonds in series): " + ", ".join(
        f"k={c['k']}:{c['naive']}/{c['topo']}" for c in chain))
    say(f"k=12: naive recomputes {chain[-1]['naive']} vs topological {chain[-1]['topo']}; "
        f"the last join node alone runs {chain[-1]['last']} times")
    OUT["E3"] = dict(rows=rows, chain=chain)

class TcpState:
    name = "?"
    def handle(self, ev):
        return self, "ignored"
def _mk_state(nm):
    def handle(self, ev, _nm=nm):
        tgt = DIAGRAM.get((_nm, ev))
        if tgt is None: return TcpState.handle(self, ev)
        return STATE_OBJ[tgt], "moved"
    return type(nm.replace("-", "_"), (TcpState,), {"name": nm, "handle": handle})
STATE_OBJ = {nm: _mk_state(nm)() for nm in STATES}


def run_table(seq):
    s = "CLOSED"; tr = []
    for ev in seq:
        t = DIAGRAM.get((s, ev))
        if t is None: tr.append((s, "ignored"))
        else: s = t; tr.append((s, "moved"))
    return tr


def run_states(seq):
    s = STATE_OBJ["CLOSED"]; tr = []
    for ev in seq:
        s, what = s.handle(ev); tr.append((s.name, what))
    return tr

def e6():
    hdr("E6  Chain of Responsibility: handlers consulted per request")
    n = 8; s = 1.1
    w = [1 / (i + 1) ** s for i in range(n)]; Z = sum(w); p = [x / Z for x in w]
    def mean_hops(order): return sum(p[t] * (order.index(t) + 1) for t in range(n))
    best = mean_hops(list(range(n))); worst = mean_hops(list(range(n))[::-1])
    perms = list(itertools.permutations(range(n)))
    avg = sum(mean_hops(list(o)) for o in perms) / len(perms)
    say(f"8 handlers, request types Zipf(s={s}): frequency-sorted {best:.3f}, reverse {worst:.3f}, "
        f"mean over all {len(perms):,} orders {avg:.3f}")
    # a third party registers an interceptor at the front
    say(f"interceptor added at the front by another module: every request +1 hop -> {best + 1:.3f} "
        f"(+{100 / best:.1f}% on the sorted chain)")
    # one request type loses its handler: those requests traverse everything
    rows = []
    for gone in range(n):
        order = [t for t in range(n) if t != gone]
        m = sum(p[t] * (order.index(t) + 1) for t in range(n) if t != gone) + p[gone] * (n - 1)
        rows.append(dict(gone=gone, hops=m, unhandled=p[gone]))
    say("one handler removed (type k now falls off the end): " +
        ", ".join(f"k={r['gone']}: {r['hops']:.3f} hops, {100 * r['unhandled']:.1f}% unhandled" for r in rows[:4]))
    # shadowing: a catch-all registered first silences all later handlers
    say("catch-all registered first: 100.0% of requests handled by it; specific handlers reached 0 times")
    OUT["E6"] = dict(n=n, s=s, p=p, best=best, worst=worst, avg=avg, perms=len(perms),
                     removed=rows, sorted_plus=best + 1)
