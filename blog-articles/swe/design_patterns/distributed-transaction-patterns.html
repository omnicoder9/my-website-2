Distributed transaction design patterns

Where Does the Doubt Go?

Distributed transaction design patterns, from two-phase commit to sagas, compensation and the transactional outbox, read as one problem: somebody has to hold the interval in which the outcome is not yet known.

Every pattern for keeping several systems consistent answers the same question in a different place. Between the moment the first system commits to a change and the moment every system agrees on the result, the outcome is in doubt. Two-phase commit keeps that doubt in a coordinator's log and makes everyone wait for it. A saga lets the world see it. An outbox turns it into a duplicate message. A compensation hands it to the business. This article catalogues twenty-six patterns by where the doubt waits, who pays for it, and whether anything bounds it, then tests the claims in a seven-experiment lab.

The interval nobody wants

A transaction on one database is easy to reason about because it has one moment of truth. The commit record reaches the log, and from that instant the change has happened; before it, the change has not 1,2. Split the same change across two databases, a database and a message broker, or three services owned by three teams, and that moment disappears. There is now an interval during which some participant has done its part and the others have not yet agreed. During that interval the outcome is in doubt.

Nothing about the network can remove this interval. Gray's 1978 notes on database operating systems frame the problem as the generals paradox: two parties exchanging messages over a channel that can lose them can never be certain together that both will act 3,4. Seven years later Fischer, Lynch and Paterson proved the stronger result that no deterministic protocol can guarantee agreement in an asynchronous system if even one process may crash 5. The CAP result and its later refinements say the same thing from the side of availability: during a partition, a system must either refuse to answer or answer without agreement 6–8.

So the doubt is not a defect to be engineered away. It is a quantity to be placed. Every distributed transaction pattern (two-phase commit, the saga, the compensating transaction, try–confirm/cancel, the transactional outbox, the idempotent consumer, change data capture, durable execution) is a decision about three things:

Custody: which component holds the in-doubt state, and therefore which component's failure prolongs it. Payer: who experiences the doubt while it lasts, whether that is someone waiting on a lock, someone reading a value that will be retracted, someone receiving a message twice, or the business writing off a loss. Bound: whether anything guarantees the doubt ends, whether it ends only because someone chose a timeout, or whether it can last for ever.

The organising question of this article is therefore not which pattern is best, but where each pattern sends the doubt. The answer turns out to be orderly. Doubt that stays low (in a single log or a coordinator) is paid for by waiting. Doubt that moves up into workflows, message channels and business processes is paid for by exposure, duplication and apology. And doubt is bounded in only two ways: by consensus, which confines it to a replicated log, or by commutativity, which arranges that there is nothing to decide.

Fifty years in one lineage

The patterns in this article are usually taught as two generations: the database generation of two-phase commit and XA, and the microservice generation of sagas and outboxes. The history is more continuous than that, and the continuity matters, because nearly every microservice pattern was first written down by database researchers solving a local problem.

The first decade built the transaction itself. The System R group at IBM defined consistency and predicate locking 9; Gray's notes and Lampson and Sturgis's report described two-phase commit and its recovery 3,10; Haerder and Reuter coined ACID 1. Almost immediately, the same researchers began asking what to do when a transaction was too long, too distributed or too important to hold locks. Gray's 1981 VLDB paper on the virtues and limitations of the transaction concept already names long-lived transactions and compensation as open problems 11. Skeen proposed three-phase commit to remove blocking 12; Moss proposed nested transactions 13; Garcia-Molina argued that many applications need only semantic atomicity, not isolation 14.

The middle of the 1980s produced most of the ideas this article's families B and D rest on. The R* project gave two-phase commit its presumed-abort and presumed-commit optimisations 15. O'Neil's escrow method let transactions share a quantity without locking it 16. Garcia-Molina and Salem's sagas broke a long transaction into committed steps with compensations 17. The following years generalised them into nested sagas, ConTracts and long-running activity models, and gave compensation a formal footing 18–21. The standard reference works of the period, by Bernstein, Hadzilacos and Goodman and by Gray and Reuter, treat all of this as one subject 22,23.

Industry standardised the atomic half. The X/Open XA specification of 1991 made two-phase commit an interface between transaction managers and resource managers 24, and it survives in Jakarta Transactions, .NET's System.Transactions and the WS-AtomicTransaction standard 25–27. The semantic half was standardised more loosely, in WS-BusinessActivity and in BPMN's compensation events 28,29, and more durably in the vocabulary of Enterprise Integration Patterns, whose process managers, idempotent receivers and guaranteed-delivery channels are the messaging world's names for the same mechanisms 30.

The 2000s changed which half was fashionable. Hohpe's short essay on why a coffee shop does not use two-phase commit 31, Pritchett's BASE 32, Vogels's account of eventual consistency at Amazon 33 and, above all, Helland's argument that scalable systems must be designed around entities that are updated atomically one at a time and coordinated by messages 34 made avoiding distributed transactions the default at internet scale. Helland and Campbell's follow-up recast the whole enterprise as memories, guesses and apologies 35.

The 2010s then did two things at once. The database side found ways to make atomic commitment scale: Percolator's transactions over Bigtable 36, Gray and Lamport's consensus-replicated commit 37 deployed by Spanner 38, Calvin's deterministic ordering 39 and, later, DynamoDB's transactions 40. The theory side mapped exactly how much consistency needs no coordination at all: highly available transactions, invariant confluence, CRDTs and the CALM theorem 41–44. Meanwhile the microservice movement, having split its databases, rediscovered the saga and gave it an operational vocabulary of orchestration, choreography, outboxes and idempotent consumers 45–48. A 2021 study of how practitioners manage data across microservices found cross-service consistency to be one of the central challenges they report, and one they often address in application code rather than with platform support 49.

The current decade has turned the orchestrated saga into a runtime. Durable-execution systems let a saga be written as ordinary code: Azure Durable Functions, given a formal semantics in 2021 50, and Temporal, founded in 2019 by the builders of Amazon's Simple Workflow Service and Uber's Cadence and begun as a fork of Cadence 51,52. And the circle is closing in an unexpected place. Kafka, the log that made outboxes and change data capture practical, added transactions of its own in 2017 53, and its KIP-939 proposes letting Kafka participate in an external two-phase commit 54. The pattern the industry spent twenty years avoiding is being rebuilt into the infrastructure that was supposed to replace it.

How to read a plate

Each pattern below is a plate with a fixed set of four fields (what it guarantees, where the doubt waits, who pays, and when it breaks), a short history with its sources, the technologies that implement it, and a gauge. The gauge is drawn as a miniature sequence diagram, because the sequence diagram is the one notation every reader of this subject already uses for commit protocols.

The custody ladder

The six lifelines of the gauge are the rungs of a custody ladder, ordered by how far from the data the in-doubt state is held. The activation bar sits on the lifeline of the component that holds custody.

K0, engine. The doubt is resolved inside one storage engine's log. Local transactions, inbox tables and idempotency-key tables live here. K1, coordinator. A protocol participant whose log decides the outcome: a two-phase commit coordinator, a Paxos group, Kafka's transaction coordinator. K2, reservation. A business resource explicitly marked tentative: a hold, an escrowed quantity, a PENDING status. K3, workflow. A persisted saga log or workflow history that knows which steps are done and which compensations remain. K4, channel. A log or queue that owes a delivery: an outbox, a change stream, an event log. K5, business. A human or business process that settles divergence by rule: compensation policy, reconciliation, write-off.

One plate, the dual write, has no custodian at all. Its gauge shows a hatched bar floating between lifelines.

Payer and bound

The glyph at the foot of each gauge names the payer. N, nobody outside the engine. W, waiters: requests that block on a lock or are refused a reserved resource. R, readers: anyone who can observe an intermediate state that may be retracted. C, consumers: receivers who must tolerate duplicates, replays or lag. B, the business: people and processes who absorb divergence as cost.

The shape of the activation bar gives the bound. A closed bar means the doubt is bounded by the protocol itself. A bar ending in a dashed segment and a cross-tick means it ends only because someone set a timeout that converts doubt into a unilateral decision (abort, cancel, forget). A bar ending in an open arrow means nothing bounds it: the doubt lasts until some party recovers or some compensation eventually succeeds.

Coding rules

A plate is coded by its dominant mechanism as usually deployed, not by its best or worst configuration. When a pattern's residual doubt is handed on to another pattern (the outbox hands duplicates to the idempotent consumer), the plate is coded by what it holds itself and the hand-off is stated in the fields. Custody, payer and bound are categorical codings made by the author from the cited sources; they are not measurements. Where a number appears in the text it comes from the lab, whose code and output are reproduced in full in the final section.

Family A: agreeing before acting

The first family resolves the doubt before any participant's change becomes visible. Every plate in it holds custody at K0 or K1, and every plate beyond the single-log case makes its payer wait. This is not a coincidence of coding. A participant that has promised to accept either outcome can do only one thing while it waits for the verdict, which is to keep other transactions away from the data it has promised about.

The question that separates the plates is what happens when the process holding custody disappears. Classic two-phase commit and its optimised descendants simply wait for it to come back. The lab's first experiment measures what that costs. Two hundred thousand transactions each had a 0.2% chance of losing their coordinator inside the decision window, and a lost coordinator took a mean of 10 minutes to restore. With classic two-phase commit, 99.67% of all lock-time was spent in those rare failures; the ninety-ninth percentile window was 4 milliseconds, but the 99.99th was 1,921 seconds. Replicating the decision across three acceptors, as Paxos Commit does, turned each single loss into a 2-second failover and cut the mean in-doubt time per transaction from 1,214 to 25.4 milliseconds. Counting requests that arrive at a hot row at fifty per second, that is the difference between 60,680 and 1,269 blocked bystanders per thousand transactions.

The distribution matters more than the mean. Two-phase commit is not slow; it is fast almost always and catastrophically slow rarely, and the rare case is the one that holds locks while a human is paged. The systems that have made atomic commitment work at scale attacked that tail rather than the median, either by replicating the coordinator (A06) or by removing the reason a participant would ever vote no (A07).

A01

Local ACID transaction

1976–1992
What it guarantees
All of the transaction's writes become durable together, or none do.
Where the doubt waits
In the log tail, between appending the commit record and forcing it to stable storage.
Who pays
Nobody outside the engine; concurrent transactions see isolation, not doubt.
When it breaks
The data spans two logs. Then this plate stops applying and one of the others takes over.

Everything else in this article is a way of recovering what this plate gives for free. A single write-ahead log makes commitment a single event: the transaction is committed at the instant its commit record is durable, and recovery replays or discards around that instant 1,2. The consistency-and-locking work at IBM gave the transaction its modern shape 9, and Haerder and Reuter named the four properties that every later pattern trades away one at a time 1. The doubt exists, but it lasts one forced write and it is held by the only party that could possibly resolve it.

In practice. PostgreSQL, MySQL/InnoDB, SQL Server, Oracle, SQLite; MongoDB multi-document transactions within one replica set 55.

A02

Two-phase commit

1976–1978
What it guarantees
Every participant commits or every participant aborts.
Where the doubt waits
In the coordinator's log. A participant that has voted yes is prepared, and may neither commit nor abort on its own.
Who pays
Whoever needs a row a prepared participant has locked.
When it breaks
The coordinator is lost after the votes are in. The prepared participants block until it returns.

Two-phase commit appears in Gray's 1978 notes and in Lampson and Sturgis's crash-recovery report, which circulated from 1976 3,10. Phase one asks each participant to make its part durable and promise not to change its mind; phase two broadcasts the verdict. The promise is the whole trick and the whole cost. Once a participant votes yes it has surrendered its right to decide, so it must hold its locks until someone tells it the outcome. Gray framed the underlying impossibility as the generals paradox, which Akkoyunlu, Ekanadham and Huber had described for network protocols 3,4: no finite exchange of messages over an unreliable channel makes two parties certain together. Two-phase commit does not escape that result; it concentrates the uncertainty in one log and makes everyone else wait for it.

In practice. PostgreSQL PREPARE TRANSACTION and COMMIT PREPARED 56; MySQL XA 57; DynamoDB TransactWriteItems uses an internal coordinator and two phases with timestamp ordering 40.

A03

Presumed abort and presumed commit

1986
What it guarantees
The same outcome as two-phase commit with fewer forced log writes and messages.
Where the doubt waits
Still in the coordinator's log; the optimisation is what the coordinator may forget.
Who pays
The same waiters as two-phase commit.
When it breaks
Exactly where two-phase commit breaks. The presumption changes the bookkeeping, not the blocking.

The R* project at IBM observed that a coordinator which finds no record of a transaction can safely answer abort, if it has promised to record every commit before telling anyone 15. Presumed abort lets aborts and read-only participants skip forced writes and acknowledgements; presumed commit inverts the bet for workloads where commits dominate. These are the variants most commercial transaction managers implement. They are worth knowing precisely because they show that half a century of engineering on the protocol has made the common path cheaper and left the failure path exactly as it was.

In practice. The default in XA-style transaction managers descended from R* and the X/Open model 23,24.

A04

Three-phase commit

1981
What it guarantees
No single failure can leave a participant blocked, provided failures can be detected reliably.
Where the doubt waits
In an extra pre-commit round that lets survivors elect a new coordinator and finish.
Who pays
The same waiters, for a shorter time.
When it breaks
The network partitions or delays messages past a timeout. Two sides can then decide differently.

Skeen showed that a protocol can be made nonblocking by adding a state in which every participant knows that everyone voted yes but nobody has committed 12. The survivors of a crash can then finish the transaction by themselves. The price is an assumption the internet does not honour: that a slow process can be told apart from a dead one. Fischer, Lynch and Paterson proved that no deterministic protocol reaches agreement in a fully asynchronous system with even one crash 5, and later work made the connection to atomic commit explicit: nonblocking commit in an asynchronous system needs failure detectors or partial synchrony 58,59. Three-phase commit is taught everywhere and deployed almost nowhere, because the timeout that makes it nonblocking is also what makes it unsafe under partition.

In practice. Mostly a textbook protocol 22; its idea survives inside consensus-based commit (A06).

A05

XA, JTA and the distributed transaction coordinator

1991
What it guarantees
Two-phase commit across heterogeneous resource managers through one standard interface.
Where the doubt waits
In the transaction manager's log; each resource manager keeps its prepared branches until told.
Who pays
Lock waiters, and eventually operators resolving in-doubt branches by hand.
When it breaks
A resource manager takes a heuristic decision. The outcome can then be mixed, and XA reports it rather than preventing it.

The X/Open XA specification fixed the calls between a transaction manager and its resource managers (xa_prepare, xa_commit, xa_rollback and xa_recover among them) and so turned two-phase commit into an interoperability contract 24. It lives on in Jakarta Transactions 25, in .NET's System.Transactions 26 and in the XA support of most relational databases 56,57. The specification is candid about its escape hatch. A resource manager that cannot wait any longer may commit or roll back a prepared branch on its own and report a heuristic outcome; if its guess disagrees with the coordinator the transaction is heuristically mixed. The doubt did not go away. It was handed to whoever reads the heuristic report. PostgreSQL's documentation goes as far as saying PREPARE TRANSACTION is not intended for use in applications, and ships with it disabled by default 56.

In practice. Jakarta Transactions (JTA) 25; .NET TransactionScope 26; WS-AtomicTransaction for SOAP services 27.

A06

Consensus-replicated commit (Paxos Commit, Spanner)

2006–2012
What it guarantees
Two-phase commit's outcome without a single coordinator whose loss blocks everyone.
Where the doubt waits
In a replicated log: the decision is chosen by a majority of acceptors, not written by one process.
Who pays
Lock waiters, for a failover rather than a repair.
When it breaks
A majority of the replicas holding the decision is lost at once.

Gray and Lamport showed that two-phase commit is the degenerate case of a more general protocol: with 2F+1 acceptors recording each participant's vote, the transaction survives F failures without blocking, and with F=0 it reduces to classic two-phase commit 37,60. Spanner deploys the idea at global scale, running two-phase commit across participant groups that are each replicated by Paxos, and adding a TrueTime commit wait so that timestamps order transactions externally 38. Consensus does not remove the doubt, and a transaction still waits for a majority. What it removes is the single process whose disappearance turns milliseconds into an operator's afternoon. In this plate's lab counterpart, the replicated coordinator cuts the average in-doubt time per transaction by a factor of 47.8.

In practice. Google Spanner 38; the same shape (two-phase commit over consensus-replicated groups) in Raft-based systems 37.

A07

Deterministic ordering (Calvin)

2012
What it guarantees
Serializable multi-partition transactions without a commit vote.
Where the doubt waits
Before execution, in a replicated sequencing layer that fixes the global order of transaction inputs.
Who pays
Every transaction, a little: it waits for its batch to be sequenced.
When it breaks
Transactions are interactive or nondeterministic, so their read and write sets cannot be known in advance.

Calvin asks why a participant would ever vote no. If the only reasons are nondeterministic (a deadlock, a crash, a timeout), then agreeing on the order of inputs first, and executing deterministically everywhere, removes the need to agree on the outcome afterwards 39. The doubt has not vanished; it has been moved to the front, where the sequencer batches requests into short epochs and replicates each batch before anyone executes it. This is the clearest demonstration in the collection that the question is not whether to pay for doubt but when.

In practice. Calvin and its deterministic-database successors 39.

Family B: acting, then agreeing

The second family lets each participant commit its step at once and resolves the doubt afterwards, by completing the remaining steps or by compensating the completed ones. Custody moves up the ladder to reservations (K2) and workflow logs (K3), and the payer changes from waiters to readers. The saga's founding paper said so in its first pages: it gains availability by giving up isolation 17.

Giving up isolation is not an abstract loss. It admits the anomalies that isolation levels exist to prevent (dirty reads, lost updates, non-repeatable reads) at the level of business entities rather than rows 45,61. The lab's fourth experiment shows two of them in a single inventory saga. Three thousand orders arrived for five hundred units; each order debited stock, then attempted payment, which failed one time in ten and triggered a compensation.

The compensation was written two ways. Written as restore the stock to the value I saw before my debit, a plausible reading of undo, it overwrote 271 concurrent debits, resurrected stock that had already been sold, and let the saga sell 2,411 units of a 500-unit inventory. Written as add back the one unit I took, a commutative increment, it sold exactly 500 with no error. That single difference is the whole of Korth, Levy and Silberschatz's point that a compensation must be defined against the current state, not the prior one 21, and it is why the cloud pattern catalogues insist on it 62. Even the correct saga exposed its doubt: for 25.8% of the run a reader could see a debit that would later be retracted, and 226 customers were turned away while a doomed debit was holding the last units.

The second structural question in this family is who owns the clock. A saga that is waiting for a step that will never report back is in doubt for as long as nobody notices. The fifth experiment sent a hundred thousand four-step sagas through services that silently dropped one message in a thousand.

Orchestration and choreography are usually compared on coupling. The lab compares them on ownership of the timeout, and the difference is categorical: an orchestrator knows it is waiting, so it retried and left 0 sagas stuck, while choreography left 417 stopped with nobody waiting. Adding a stale-saga sweeper fixed choreography, which is to say that choreography becomes safe once something orchestrates its failures.

B01

Saga

1987
What it guarantees
Either every step T1…Tn completes, or the completed prefix is undone by compensations Cj…C1.
Where the doubt waits
In the saga log that records which steps have committed and which compensations remain.
Who pays
Readers, who can see the effects of a saga that will later be compensated.
When it breaks
A compensation cannot succeed. The saga then has nowhere to go.

Garcia-Molina and Salem wrote the saga paper about a local problem: a long-lived transaction that held database locks for hours 17. Their answer was to break it into a sequence of ordinary transactions, each committing on its own, and to pair each with a compensating transaction to run if a later step failed. Nothing in the paper needs a network. The price was stated plainly: a saga gives up isolation, so other transactions may see its partial results. The same group later generalised sagas to nested and parallel structures 18, and the same years produced the ConTract model and the long-running activity model of Dayal, Hsu and Ladin 19,20. The saga's modern life began when microservice architectures rediscovered the long-lived transaction as the only transaction they had left 45,46.

In practice. Implemented through orchestration (B03) or choreography (B04); Azure's architecture guidance documents both 63.

B02

Compensating transaction

1983–1990
What it guarantees
A later transaction that semantically cancels an earlier, already committed one.
Where the doubt waits
In business meaning: what counts as undone is decided by the domain, not the database.
Who pays
The business, which must define an inverse and live with the gap when there is none.
When it breaks
The effect has escaped. An email is read, goods are shipped, a price is quoted.

A compensation is not a rollback. A rollback restores the state before the transaction; a compensation acts on the state as it is now, after other transactions have run, and tries to reach a state the business accepts as equivalent 21. Garcia-Molina's earlier work on semantic knowledge had already argued that many applications only need semantic atomicity, meaning an outcome that is acceptable, rather than an identical one 14. Microsoft's pattern catalogue puts the practical consequence bluntly: the compensation may not return the system to its original state, and it must itself be idempotent because it can fail and be retried 62. The lab shows how quickly the difference matters. A compensation written as restore the value I saw, instead of add back what I took, overwrote 271 concurrent writes and let the saga sell 2,411 units of a 500-unit stock.

In practice. Every saga framework; BPMN 2.0 models compensation as an explicit event and handler 29; WS-BusinessActivity standardised the protocol for SOAP services 28.

B03

Orchestrated saga

2005–2018
What it guarantees
One component drives the steps, awaits each reply, and runs the compensations.
Where the doubt waits
In the orchestrator's persisted state machine.
Who pays
Readers of the intermediate state, and the orchestrator's operators.
When it breaks
The orchestrator's own state is lost or its timeouts are set longer than the business can tolerate.

An orchestrator is a saga log with a scheduler attached. It sends a command, waits for the reply, advances or compensates, and it is the one component that knows how long it has been waiting. That makes it the natural owner of timeouts. In the lab's silent-loss scenario an orchestrator with a 30-second timeout and 3 retries left 0 of 100,000 sagas stuck, paying instead an average delay of 30.3 seconds on the 765 sagas that needed a retry. Richardson's pattern language and the cloud vendors' guidance both describe the shape 45,63.

In practice. Temporal 64; Azure Durable Functions 65; BPMN engines with compensation events 29; Seata's Saga mode 66.

B04

Choreographed saga

2010s
What it guarantees
Each service reacts to the previous service's event; no component sees the whole saga.
Where the doubt waits
In the event stream, spread across every participant's local state.
Who pays
Readers of intermediate state, and whoever eventually notices the saga has stopped.
When it breaks
An event is lost or mis-handled. No one is waiting for the next one, so no one times out.

Choreography removes the orchestrator and with it the single place where the saga's progress is known. The loose coupling is real; so is the gap. When the event that should trigger step three is silently dropped, step two's service believes its work is done and step three's service never heard of the saga. In the lab, 417 of 100,000 choreographed sagas stopped with nobody waiting, against an analytic expectation of 399. A periodic sweeper that looks for stale sagas found all of them, after 153 seconds on average. The sweeper is, of course, an orchestrator that only wakes up for failures.

In practice. Event-driven services over a broker 30,45.

B05

Try–Confirm/Cancel (TCC)

2007–2014
What it guarantees
Each participant first reserves (try), then either confirms or cancels the reservation.
Where the doubt waits
In the reservation itself: a resource explicitly marked tentative, with an expiry.
Who pays
Other customers, who find the reserved capacity unavailable until it is confirmed or released.
When it breaks
A confirm arrives after the reservation has expired and been cancelled.

TCC applies two-phase commit's structure to business resources instead of database locks. The try phase is the vote and the reservation is the prepared state, but the reservation belongs to the business, carries its own timeout, and is visible to everyone as reserved. Pardon and Pautasso gave the pattern a RESTful form in which each reservation is a resource with a lifetime and the confirm is a PUT to it 67. Because a reservation expires by itself, TCC gets something two-phase commit cannot: a participant that never hears back will cancel on its own schedule. The cost is a race that must be designed for, between a late confirm and an early expiry.

In practice. Apache Seata TCC mode 66; the RESTful reservation design 67.

B06

Escrow and reservation of quantities

1986
What it guarantees
Concurrent transactions may each take from a quantity, as long as every possible outcome stays within bounds.
Where the doubt waits
In a reserved amount set aside from the quantity, not in a lock on the whole record.
Who pays
Only transactions that would push the quantity past its bound, and they are refused at once.
When it breaks
The update is not a commutative increment. Setting a price cannot be escrowed.

O'Neil's escrow method treats an aggregate such as a stock count or a balance as a pool from which transactions draw 16. A transaction reserves its amount under a brief latch, checks that the worst case still respects the bound, and proceeds without holding a lock on the record. In the lab's hot-counter test, escrow completed 62 times faster than an exclusive lock held to commit, and when stock ran out both refused exactly 1,000 orders. Correctness was identical; only the waiting changed. Escrow is the first sign of the result family D makes explicit: when the operations commute, most of the doubt can be removed rather than moved.

In practice. Quantity fields such as stock and balances 16; the same idea underlies CRDT counters (D04).

B07

Semantic lock and pending state

2018
What it guarantees
A record carries an explicit PENDING or APPROVAL_PENDING marker while a saga that touched it is unfinished.
Where the doubt waits
In a status field that any reader can see and interpret.
Who pays
Readers, who must decide what to do with a pending record; the state tells them, it does not hide.
When it breaks
The saga dies and the marker is never cleared.

Richardson's countermeasures for missing isolation (semantic lock, commutative updates, pessimistic view, reread value, version file and by-value dispatch) are ways of making a saga's intermediate states less dangerous without restoring isolation 45. The semantic lock is the simplest: mark the record, and let readers see the mark. The lab tested exactly what it buys. With a pending state readers could act on, the number of orders refused while a doomed debit was outstanding fell from 226 to 0, and 7 parked orders were served after a mean wait of 0.91 seconds. The share of time a reader could see a debit that would later be retracted did not move: 25.80% either way. A semantic lock does not reduce exposure. It labels it, and labelled doubt can be reasoned about.

In practice. Status columns such as APPROVAL_PENDING in Richardson's order example 45.

B08

Pivot and retriable steps

1987–2018
What it guarantees
Steps before a go/no-go point can be compensated; steps after it are guaranteed to complete by retry.
Where the doubt waits
Before the pivot, in the compensation list; after it, in an obligation to retry until success.
Who pays
Readers, and the retry budget of every step after the pivot.
When it breaks
A step after the pivot can fail permanently. Then the saga is committed to something it cannot finish.

The original saga paper already distinguished backward recovery, which runs compensations, from forward recovery, which retries from a save point 17. Richardson turned this into a design rule by naming three kinds of step: compensatable, pivot and retriable 45. Put everything that can be undone before the pivot, put the irrevocable decision at the pivot, and put only steps that cannot fail for business reasons after it. The rule is a discipline for placing the unbounded part of the doubt where retrying is always safe, which is to say where every step is idempotent 68.

In practice. Retry policies in durable-execution runtimes implement the retriable tail 64.

Family C: the message is the transaction

The third family is about the most common distributed transaction of all, one that most developers do not recognise as one: changing a database and telling somebody about it. The database commit and the message send are two writes to two systems, and every possible ordering of them can fail between the writes.

The lab's second experiment ran a million operations through three strategies, with a one-in-a-thousand chance of a crash between writes, a two-in-a-thousand chance of an ambiguous acknowledgement from the broker, and a three-in-a-thousand chance that the database transaction would roll back after the event had been sent. Committing the database first lost 953 events and duplicated 937; publishing first sent 3,929 events for changes that never happened. The outbox lost and invented nothing, and it duplicated 1,934 events, almost exactly the database-first strategy's losses plus its duplicates. This is the clearest numerical statement in the article of its central claim. The outbox does not reduce the amount of doubt. It converts every silent loss into a visible duplicate, and moves custody from nowhere to a table that a relay must drain.

Duplicates are then the consumer's problem, and the consumer's answer is to remember what it has already processed. How long it remembers is a timeout on the doubt.

Brokers that offer transactions of their own, such as Kafka since KIP-98, pull the doubt back down to a coordinator and make read-committed consumers wait for it 53. The sixth experiment shows the stall that follows when one producer hangs inside a transaction: every read-committed consumer of the partition stops at the last stable offset until the transaction times out 69.

C01

Dual write

always
What it guarantees
Nothing. The database and the broker are written in sequence and hoped to agree.
Where the doubt waits
Nowhere. Between the two writes, no component records that the second is owed.
Who pays
The business, through divergence that is silent until someone reconciles.
When it breaks
Any crash, timeout or rollback between the two writes.

Dual write is the pattern everyone writes first: update the database, then publish the event (or the other way round). It is the only plate in the collection whose doubt has no custodian at all, which is why it earns a place. In a million simulated operations, writing the database first lost 953 events outright and duplicated 937 more through retries after ambiguous acknowledgements; publishing first produced 3,929 phantom events announcing changes that never committed. Neither ordering is safe, and the failures are silent: nothing in either system says anything is wrong 47,70.

In practice. Any handler that calls a database client and a message client in sequence 70.

C02

Transactional outbox

2010s
What it guarantees
An event is published if and only if the business change that produced it committed, at least once.
Where the doubt waits
In an outbox row written in the same local transaction as the change, until a relay has published it.
Who pays
Consumers, who must tolerate duplicates.
When it breaks
Consumers are not idempotent, or the relay's lag exceeds what readers of the events can tolerate.

The outbox collapses a dual write into a single local transaction (plate A01) plus a delivery obligation. The change and a row describing the event commit together; a separate relay reads unpublished rows, publishes them, and marks them sent 45,47. The relay can crash after publishing and before marking, so the guarantee is at-least-once. The lab makes the trade exact. The outbox lost nothing and invented nothing, and it produced 1,934 duplicates, which is 102.3% of the losses plus duplicates of the database-first dual write. The doubt was not destroyed; it was converted from silent loss into visible duplication and delivered to the one party equipped to handle it.

In practice. Hand-written relays polling an outbox table 47; Debezium's outbox event router over change data capture 71.

C03

Change data capture and log tailing

2010s
What it guarantees
Every committed change in the database becomes an event, in commit order, at least once.
Where the doubt waits
In the database's own replication log, read by a connector that tracks its position.
Who pays
Consumers, who see duplicates after connector restarts and must interpret row-level changes.
When it breaks
The log is pruned before the connector reads it, or the schema of the captured table changes under it.

Change data capture reads the write-ahead log or binlog that the database already keeps for recovery and replication, and republishes it as a stream 70. It is the purest version of the outbox idea because it adds no write at all: the database's own commit record is the event's custody. Paired with an outbox table, it lets the application choose the event's shape while the log supplies the delivery; that combination is what Debezium's outbox router implements 71. The obligation that remains is the consumer's: the connector records its offset after publishing, so a restart replays.

In practice. Debezium connectors 71; Percolator's observers were an in-database relative 36.

C04

Idempotent consumer and inbox

2003
What it guarantees
Processing a message twice has the same effect as processing it once.
Where the doubt waits
In a table of processed message identifiers, written in the same local transaction as the message's effect.
Who pays
Consumers, in storage for the identifiers and in the risk that one has expired.
When it breaks
A duplicate arrives after its identifier has been pruned.

Hohpe and Woolf named the idempotent receiver 30; Richardson's idempotent consumer records each message ID in the same transaction as the business update so that the check and the effect cannot disagree 48. The pattern pulls the doubt back down into a local transaction, which is why it sits at K0. What it cannot do is remember for ever. The lab gave duplicates a realistic mix of causes, from quick retries to operator replays days later, and measured how many slip past a dedupe table of each retention. At one minute, 20.1% escape; at twenty-four hours, 1.71%; at seven days, 0.39%, at the cost of holding 1,209,600,000 identifiers at a steady 2,000 messages per second. Retention is a timeout on the doubt, and every value of it is a decision about which late duplicates the business will absorb.

In practice. An inbox table keyed by message ID, inserted with INSERT … ON CONFLICT DO NOTHING in the same transaction as the effect (listing 5).

C05

Idempotency keys at the API boundary

2010s
What it guarantees
A client may retry a non-idempotent request (a POST) without the server acting twice.
Where the doubt waits
In a server-side record keyed by a client-chosen key, holding the first response.
Who pays
Clients, who must generate and keep the key, and who lose protection once the server forgets it.
When it breaks
The client retries with a new key, or after the server has pruned the old one.

An idempotency key is the idempotent consumer applied to the network edge. The client invents a unique key per logical operation; the server stores the key with the result of the first attempt and replays that result for any retry 68. Stripe's API stores the status code and body of the first attempt, replays them for every retry (including a 500 error), rejects a reused key sent with different parameters, and may prune keys once they are at least twenty-four hours old 72, and Leach's write-up shows how to implement it with atomic phases in PostgreSQL 73. The IETF HTTPAPI working group has been standardising an Idempotency-Key header since 2021; as of September 2026 it is still an Internet-Draft 74.

In practice. Stripe's API 72; the draft Idempotency-Key HTTP header, whose authors came from PayPal 74.

C06

Broker transactions (Kafka exactly-once)

2017
What it guarantees
Writes to several partitions, and the consumer offsets that caused them, commit or abort together.
Where the doubt waits
In the broker's transaction coordinator and its replicated transaction log.
Who pays
Read-committed consumers, who cannot read past the first offset of any open transaction.
When it breaks
A producer hangs inside a transaction. The partition stalls for readers until the timeout aborts it.

Kafka's KIP-98 added idempotent producers and transactions in 2017: a coordinator per transactional ID, a two-phase protocol with commit markers written into each partition, and a read_committed isolation level for consumers 53,75. It is two-phase commit inside one system, and it inherits the blocking. Read-committed consumers cannot pass the last stable offset, the first offset of the earliest open transaction, so one hung producer stalls everyone reading that partition until transaction.timeout.ms (sixty seconds by default) aborts it 69. In the lab, that single hang delayed 43.7% of all messages by more than a second. KIP-939 goes further and lets Kafka join an external two-phase commit by adding a prepared state, which requires disabling the timeout so that a prepared transaction can wait for its coordinator indefinitely 54. Joining a larger transaction means giving up the one bound Kafka had. With no timeout and a coordinator that took ten minutes to return, the lab's stall reached 82.6% of messages. The KIP has been accepted, but as of the 4.3 release line the transaction.version level it requires is not yet defined in Kafka's source 76.

In practice. Apache Kafka producers and Kafka Streams exactly-once processing 53,75; Flink's two-phase-commit sink motivates KIP-939 54.

C07

Event sourcing and listen-to-yourself

2005
What it guarantees
A change is recorded exactly once, as an event; all state, including the service's own, is derived from it.
Where the doubt waits
In the event log, which is the only write.
Who pays
Consumers, including the service itself, which reads its own writes late and must tolerate replay.
When it breaks
Something must be decided synchronously on state the log has not yet been folded into.

If the only write is the append of an event, there is no second write to get wrong. Event sourcing makes the log the system of record and derives every other store from it 70,77; the listen-to-yourself variant has a service publish an event and update its own state only when it consumes that event back. The dual write disappears by construction. What replaces it is a read-your-writes gap, because the service's own view lags its log. Event sourcing is the outbox taken to its conclusion, and it relocates the same doubt to the same payer: whoever consumes the log.

In practice. Event stores, or a Kafka topic used as the log of record 70.

Family D: runtimes, reconciliation, and doubt that never arises

The last family collects the three places the doubt can end up once the mechanisms above have done what they can. Durable-execution runtimes and process managers make the workflow log (K3) a managed service. Reconciliation makes the business (K5) an explicit participant. And coordination avoidance removes the doubt by construction, by restricting the operations to ones whose order does not matter.

The seventh experiment shows the last idea in its oldest form, O'Neil's escrow method 16. Two thousand decrements of a hot counter, each inside a transaction that does five milliseconds of other work, finished in 10 seconds when each held a row lock to commit and in 0.16 seconds when each reserved its unit under a 0.05-millisecond latch and let go. When stock ran short, both methods sold and refused exactly the same orders. Nothing about the outcome changed; only the waiting did. Decrements commute, so the doubt about their order never had to be held. The same observation, generalised, is the invariant-confluence and CALM results: coordination is necessary exactly for the operations that do not commute with the invariants you care about 42,44.

D01

Durable execution

2012–2019
What it guarantees
Ordinary code runs to completion across crashes, because each step's result is recorded and replayed.
Where the doubt waits
In the workflow's event history, persisted by the runtime.
Who pays
Readers of intermediate state in the systems the workflow calls, and those systems, which see at-least-once activities.
When it breaks
Workflow code is nondeterministic, or an activity is not idempotent, or no execution timeout is set and nobody notices.

Durable execution turns a saga log into a programming model. The runtime records each activity's result in an event history; after a crash, the workflow function is re-executed and completed steps are answered from the history instead of being run again 50,64. Temporal's founders built Amazon's Simple Workflow Service and then Uber's Cadence before starting Temporal in 2019 51, and the Temporal server began as a fork of Cadence 52; Azure Durable Functions has a formal semantics published at OOPSLA 50,65. The model makes an orchestrated saga look like a try/finally block, which is its great strength and the source of its specific risks: workflow code must be deterministic so that replay reproduces it, and activities run at least once.

In practice. Temporal and Cadence 52; Azure Durable Functions 65.

D02

Process manager

2003
What it guarantees
A stateful router that decides the next message to send based on the replies so far.
Where the doubt waits
In the process manager's correlation store.
Who pays
Readers of intermediate state in the downstream systems.
When it breaks
The correlation store and the messaging system disagree about which replies arrived.

Enterprise Integration Patterns gave the orchestrator its messaging-world name: a process manager maintains the state of each process instance and determines the next step from intermediate results 30. It is worth a plate of its own because it shows the orchestrated saga was not invented for microservices. The same book's catalogue of guaranteed delivery, idempotent receivers and correlation identifiers already contains most of the machinery this article describes.

In practice. Integration brokers and service buses that implement the EIP vocabulary 30.

D03

Reconciliation, write-off and apology

2005–2009
What it guarantees
Divergence between systems is found after the fact and settled by a business rule.
Where the doubt waits
In the business process: a reconciliation job, a write-off policy, a customer-service script.
Who pays
The business, in money written off and in apologies.
When it breaks
The divergence is large, frequent, or of a kind no rule prices.

Hohpe's coffee-shop essay observed that a café does not use two-phase commit with its customers; when a drink cannot be made it refunds the money, remakes the drink, or writes off the loss, choosing by cost 31. Helland and Campbell generalised the observation: systems built on memories, guesses and apologies make decisions on local knowledge and apologise when those decisions turn out wrong 35. This is the top of the custody ladder, and it is where every lower plate's unhandled residue eventually arrives. It is also, often, the correct place for it; a ledger that reconciles nightly and writes off pennies is cheaper than one that blocks on every transfer.

In practice. End-of-day reconciliation and settlement processes; the coffee shop 31.

D04

Coordination avoidance (CRDTs, I-confluence, CALM)

2011–2020
What it guarantees
Replicas accept updates independently and still converge, because the updates commute.
Where the doubt waits
Nowhere, because there is no outcome to decide: every order of the updates gives the same result.
Who pays
Nobody, within the class of invariants that are confluent under the operations.
When it breaks
An invariant requires coordination, as a non-negative balance does under concurrent withdrawals.

Three lines of work arrived at the same boundary. Conflict-free replicated data types make convergence a property of the data type 43. Bailis and colleagues' invariant confluence tells you, for a given invariant and set of operations, whether any coordination is needed at all 42, after showing how much isolation is achievable with high availability 41. The CALM theorem states that a program has a consistent, coordination-free implementation exactly when it is monotonic 44. This is the only plate other than A01 whose payer is nobody, and it earns that the same way: not by moving the doubt, but by arranging that there is no doubt to hold.

In practice. CRDT libraries for replicated counters, sets and text 43; escrow counters (B06).

The first result is that the payer is almost determined by the custody rung. All 9 plates whose payer is a waiter hold custody at K1 or K2. None of the 11 plates that hold custody at K3 or above makes anyone wait; every one of them charges readers, consumers or the business instead. The two plates whose payer is nobody, the local transaction and coordination avoidance, both sit at K0. Custody and payer are two codings made separately from the sources, and yet the custody rung alone predicts whether the payer waits for 25 of the twenty-six. The exception is the semantic lock (B07), a reservation whose whole purpose is to stop readers waiting by telling them what they are looking at. Moving the doubt away from the data does not make it cheaper. It changes the currency it is paid in.

The second result is about bounds. 12 of the twenty-six plates hold doubt that nothing bounds. Only 3 of those are members of the two-phase commit family that the industry left behind because it could block. The other 9 are the patterns adopted to escape it: the saga, the compensation, the choreographed saga, the post-pivot retry, the dual write, the outbox, change data capture, event sourcing and durable execution. Leaving two-phase commit removed the lock; it did not bound the doubt. It moved the unbounded part from a participant waiting on a coordinator to a reader seeing a state that may be undone, a consumer that may be sent the same message next week, or a business that finds the divergence in a reconciliation report.

The third result is about how doubt is bounded at all. 5 plates are bounded by construction, and they achieve it in exactly two ways. Three (the local transaction, consensus-replicated commit and deterministic ordering) confine the decision to a single log, replicated or not. Two (escrow and coordination avoidance) arrange that the operations commute, so there is no outcome to decide. Every other bound in the collection is a timeout: a place where someone decided how long to wait before acting on their own. The 9 timeout-bounded plates are where the lab spent most of its time, because a timeout is a price, not a guarantee. A one-day dedupe retention still lets 1.71% of duplicates through; a sixty-second transaction timeout still stalls 43.7% of a partition's messages when it fires; an orchestrator's thirty-second deadline still adds half a minute to every saga it rescues.

Put together, the three results answer the title. The doubt goes up the custody ladder, and as it rises it stops being paid for in waiting and starts being paid for in exposure, duplication and apology. It is never destroyed except by consensus or commutativity. Everywhere else it is either moved or timed out, and a timeout is only a decision about which residue someone else will pay for.

Choosing where the doubt goes

Read this way, choosing a distributed transaction pattern is a sequence of questions about the doubt rather than a comparison of frameworks.

First, ask whether there is any doubt to hold. If the operations commute with the invariant (counters, sets, append-only logs, balances allowed to go temporarily negative), coordination avoidance or escrow removes the problem 16,42,43. Second, ask whether the data can live in one log. Helland's advice to design around entities that are updated atomically one at a time is the most effective distributed transaction pattern there is, because it avoids needing one 34. A service boundary drawn through the middle of an invariant is a decision to hold doubt forever.

Third, if a decision must span several logs and the participants are few, fast and under one operator, atomic commitment is not the relic its reputation suggests. Replicate the coordinator (A06) and the blocking tail that discredited it shrinks from an outage to a failover, as the lab's first experiment shows. Spanner and DynamoDB are existence proofs that it scales when one team owns the whole protocol 38,40.

Fourth, if participants are independent services, the doubt will be exposed; decide to whom. Put reversible steps before an explicit pivot and retriable steps after it (B08). Give every intermediate state a name readers can see (B07). Write every compensation as a commutative correction against the current state, never as a restore of a remembered one (B02). Give the saga an owner that knows how long it has been waiting, whether that is an orchestrator, a durable-execution runtime or a sweeper (B03, D01).

Fifth, whenever a state change and a message must agree, never dual-write. Use an outbox or change data capture, and make every consumer idempotent with a retention chosen deliberately against the replay behaviour of the whole pipeline, not a round number (C02–C04). Sixth, decide in advance what the business will do with the residue: the duplicates that outlive the dedupe window, the compensation that cannot succeed, the reconciliation difference. Hohpe's coffee shop writes off the drink 31. A bank cannot, and should know that before choosing an architecture that will occasionally ask it to.

The lab

The seven experiments below are written in the Python standard library, seeded, and deterministic. They were run once for this build; every number quoted in the text and figures is read from their JSON output, and the text output is reproduced verbatim. Their output was checked byte-identical under three values of PYTHONHASHSEED. The constants are illustrative orders of magnitude, not measurements of any product; the experiments are meant to show the shape of each trade, and each result is a property of the model stated in its code.

Two limits are worth stating. The experiments simulate the patterns' logic, not real databases, brokers or networks, so they omit contention effects, fsync costs and correlated failures that would make most tails worse. And the codings of custody, payer and bound on which the ledger's results rest are the author's, made from the cited sources; another reader could reasonably code a borderline plate (the orchestrated saga's bound, for instance) differently. The results in the ledger section are stated as counts precisely so that a changed coding can be checked against them.

#!/usr/bin/env python3
"""Where Does the Doubt Go? -- companion lab.

Seven deterministic experiments on where the in-doubt interval of a
distributed transaction ends up, and who pays for it.  Standard library
only.  Every random stream is seeded from SEED plus the experiment number,
every collection whose iteration order is observable is a list, and the
output is byte-identical across PYTHONHASHSEED values.

Constants are illustrative, not fitted to any product.  They are chosen to
be plausible orders of magnitude so that the SHAPE of each result can be
inspected; the article quotes the numbers only as properties of this model.
"""
import json, math, sys
from random import Random

SEED = 20260925
OUT = {}

def pct(xs, q):
    xs = sorted(xs)
    if not xs:
        return 0.0
    k = min(len(xs) - 1, max(0, int(math.ceil(q * len(xs))) - 1))
    return xs[k]

def hdr(s):
    print()
    print(s)
    print("-" * len(s))

# ---------------------------------------------------------------- E1
def e1():
    hdr("E1  Who waits when the coordinator is lost: basic 2PC vs Paxos Commit (F=1)")
    rng = Random(SEED + 1)
    N = 200_000
    pc = 0.002          # P(a coordinator process crashes inside the window), per txn
    mean_rec = 600.0    # s, mean time to restart a lost coordinator (operator timescale)
    failover = 2.0      # s, election timeout when one of 2F+1 acceptors is lost
    base = 0.004        # s, prepare->decision window with nobody failing
    lam = 50.0          # other requests per second arriving at the same hot row
    res = {}
    for proto in ["basic_2pc", "paxos_commit"]:
        d = []
        for _ in range(N):
            if proto == "basic_2pc":
                x = base
                if rng.random() < pc:
                    x += rng.expovariate(1.0 / mean_rec)
            else:
                crashes = sum(1 for _ in range(3) if rng.random() < pc)
                x = base
                if crashes == 1:
                    x += failover
                elif crashes >= 2:
                    x += rng.expovariate(1.0 / mean_rec)
            d.append(x)
        tot = sum(d)
        tail = sum(x - base for x in d)
        r = {
            "mean_ms": 1000 * tot / N,
            "p99_ms": 1000 * pct(d, 0.99),
            "p9999_s": pct(d, 0.9999),
            "max_s": max(d),
            "gt1s": sum(1 for x in d if x > 1.0),
            "gt60s": sum(1 for x in d if x > 60.0),
            "tail_share": tail / tot,
            "lock_s_per_1000": 1000 * tot / N,
            "bystanders_per_1000": 1000 * lam * tot / N,
        }
        grid = [10 ** (k / 4.0) for k in range(-12, 17)]   # 1 ms .. 10^4 s
        ds = sorted(d); import bisect
        r["ccdf"] = [[g, (N - bisect.bisect_right(ds, g)) / N] for g in grid]
        res[proto] = r
        print(f"{proto:13s} mean {r['mean_ms']:9.3f} ms  p99 {r['p99_ms']:7.3f} ms  "
              f"p99.99 {r['p9999_s']:9.3f} s  max {r['max_s']:9.1f} s")
        print(f"{'':13s} txns in doubt >1 s: {r['gt1s']:4d}   >60 s: {r['gt60s']:4d}   "
              f"share of lock-time from failures: {100*r['tail_share']:6.2f}%")
        print(f"{'':13s} lock-seconds per 1000 txns {r['lock_s_per_1000']:8.3f}   "
              f"blocked bystanders per 1000 txns at {lam:.0f}/s: {r['bystanders_per_1000']:8.1f}")
    ratio = res["basic_2pc"]["mean_ms"] / res["paxos_commit"]["mean_ms"]
    res["mean_ratio"] = ratio
    res["params"] = {"N": N, "pc": pc, "mean_rec": mean_rec, "failover": failover,

def e2():
    hdr("E2  Dual write vs transactional outbox under crashes and ambiguous acks")
    N = 1_000_000
    p_crash = 0.001     # process crash between the two writes
    f_amb = 0.002       # broker publish returns an error or times out
    w_amb = 0.5         # ...but the record was in fact appended
    g_db = 0.003        # DB commit fails after publish (deadlock, constraint)
    res = {}
    for strat in ["db_then_publish", "publish_then_db", "outbox_relay"]:
        rng = Random(SEED + 2)
        lost = phantom = dup = 0
        for _ in range(N):
            if strat == "db_then_publish":
                if rng.random() < p_crash:
                    lost += 1            # row committed, event never sent
                    continue
                if rng.random() < f_amb:  # retry once on error
                    if rng.random() < w_amb:
                        dup += 1
            elif strat == "publish_then_db":
                if rng.random() < f_amb and rng.random() < w_amb:
                    dup += 1
                if rng.random() < p_crash:
                    phantom += 1         # event out, row never written
                    continue
                if rng.random() < g_db:
                    phantom += 1         # event out, transaction rolled back
            else:
                # business row + outbox row commit atomically; relay publishes,
                # then marks the row sent.  Crash between those two -> redelivery.
                if rng.random() < p_crash:
                    dup += 1
                if rng.random() < f_amb and rng.random() < w_amb:
                    dup += 1
        res[strat] = {"lost": lost, "phantom": phantom, "dup": dup,
                      "silent_per_million": (lost + phantom) * 1_000_000 / N}
        print(f"{strat:16s} lost {lost:6d}   phantom {phantom:6d}   duplicate {dup:6d}")
    a = res["db_then_publish"]; o = res["outbox_relay"]
    res["outbox_dup_over_dualwrite_lost"] = o["dup"] / max(1, a["lost"] + a["dup"])
    print(f"outbox duplicates / (db-first lost + db-first duplicates) = "
          f"{res['outbox_dup_over_dualwrite_lost']:.3f}")
    res["params"] = {"N": N, "p_crash": p_crash, "f_amb": f_amb, "w_amb": w_amb, "g_db": g_db}
    OUT["E2"] = res

def e4():
    hdr("E4  Saga without isolation: exposure, lost updates, and what a pending state buys")
    res = {}
    for variant in ["restore_saved_value", "increment_back", "pending_aware"]:
        rng = Random(SEED + 4)
        stock0 = 500; n_orders = 3000; rate = 40.0; mean_pay = 1.5; q = 0.10; park_max = 3.0
        t = 0.0; arrivals = []
        for i in range(n_orders):
            t += rng.expovariate(rate)
            dur = rng.expovariate(1.0 / mean_pay)
            fails = rng.random() < q
            arrivals.append((t, dur, fails))
        # event list: (time, kind, id)
        stock = stock0; pending = {}   # id -> (resolve_time, fails, saved)
        events = [(a[0], 0, i) for i, a in enumerate(arrivals)]
        events.sort()
        import heapq
        heap = list(events); heapq.heapify(heap)
        parked = []                    # order ids waiting on a pending resolution
        sold = refused = false_refused = lost_update_events = parked_ok = 0
        doomed_intervals = []
        waits = []
        def admit(i, now):
            nonlocal stock
            saved = stock
            stock -= 1
            dur, fails = arrivals[i][1], arrivals[i][2]
            pending[i] = (now + dur, fails, saved)
            heapq.heappush(heap, (now + dur, 1, i))
            if fails:
                doomed_intervals.append((now, now + dur))
        while heap:
            now, kind, i = heapq.heappop(heap)
            if kind == 0:              # order arrives
                if stock > 0:
                    admit(i, now)
                elif variant == "pending_aware" and pending:
                    parked.append((i, now))
                    heapq.heappush(heap, (now + park_max, 2, i))
                else:
                    refused += 1
                    if any(v[1] for v in pending.values()):
                        false_refused += 1
            elif kind == 1:            # payment resolves
                end, fails, saved = pending.pop(i)
                if fails:
                    if variant == "restore_saved_value":
                        if stock != saved - 1:
                            lost_update_events += 1
                        stock = saved
                    else:
                        stock += 1
                    if variant == "pending_aware" and parked and stock > 0:
                        j, t0 = parked.pop(0)
                        waits.append(now - t0); parked_ok += 1
                        admit(j, now)
                else:
                    sold += 1
                if variant == "pending_aware" and not pending:
                    while parked:
                        j, t0 = parked.pop(0); refused += 1
            else:                      # park timeout
                for k, (j, t0) in enumerate(parked):
                    if j == i:
                        parked.pop(k); refused += 1
                        break
        truth = stock0 - sold
        # dirty reads: a dashboard polling every 5 ms sees a value that includes a debit
        # that will later be compensated
        horizon = max(e for _, e in doomed_intervals) if doomed_intervals else 0.0
        iv = sorted(doomed_intervals); covered = 0.0; cs = ce = None
        for s, e in iv:
            if cs is None:
                cs, ce = s, e
            elif s <= ce:
                ce = max(ce, e)
            else:
                covered += ce - cs; cs, ce = s, e
        if cs is not None:
            covered += ce - cs
        last_arrival = arrivals[-1][0]
        r = {"sold": sold, "refused": refused, "false_refused": false_refused,
             "final_stock": stock, "true_stock": truth, "error": stock - truth,
             "lost_update_events": lost_update_events,
             "exposed_fraction": covered / max(horizon, last_arrival),
             "parked_ok": parked_ok,
             "mean_wait_s": (sum(waits) / len(waits)) if waits else 0.0}
        res[variant] = r
        print(f"{variant:20s} sold {sold:4d}  refused {refused:4d}  refused-while-a-doomed-debit-was-pending "
              f"{false_refused:4d}")
        print(f"{'':20s} final stock {stock:5d} vs true {truth:5d} (error {stock-truth:+d}); "
              f"compensations that clobbered a concurrent write {lost_update_events}")
        print(f"{'':20s} share of time a reader sees a to-be-retracted debit: "
              f"{100*r['exposed_fraction']:6.2f}%   parked then served {parked_ok} "
              f"(mean wait {r['mean_wait_s']:.2f} s)")
    OUT["E4"] = res

def e5():
    hdr("E5  Who owns the timeout: orchestration vs choreography with silent message loss")
    rng = Random(SEED + 5)
    S = 100_000; steps = 4; d = 0.001; T = 30.0; retries = 3; sweep = 300.0
    orch_stuck = 0; orch_detect = []; orch_comp = 0
    chor_stuck = 0; sweep_detect = []
    for _ in range(S):
        # orchestration: each command/reply pair can be lost; orchestrator retries
        ok = True; t_lost = 0.0
        for s in range(steps):
            tries = 0
            while True:
                lost = rng.random() < 2 * d      # command or reply lost
                if not lost:
                    break
                tries += 1; t_lost += T
                if tries > retries:
                    ok = False; break
            if not ok:
                break
        if not ok:
            orch_comp += 1
        if t_lost > 0:
            orch_detect.append(t_lost)
        # choreography: each hop is one event; a lost event halts the saga silently
        halted = any(rng.random() < d for _ in range(steps))
        if halted:
            chor_stuck += 1
            sweep_detect.append(rng.random() * sweep + rng.random() * 5.0)
    r = {"sagas": S, "steps": steps, "d": d, "T": T, "retries": retries,
         "orch_stuck": orch_stuck, "orch_compensated": orch_comp,
         "orch_retried": len(orch_detect),
         "orch_mean_delay_s": (sum(orch_detect) / len(orch_detect)) if orch_detect else 0.0,
         "chor_stuck": chor_stuck,
         "chor_expected": S * (1 - (1 - d) ** steps),
         "sweep_mean_s": (sum(sweep_detect) / len(sweep_detect)) if sweep_detect else 0.0,
         "sweep": sweep}
    print(f"orchestrated: stuck {orch_stuck}  retried {r['orch_retried']} (mean added delay "
          f"{r['orch_mean_delay_s']:.1f} s)  gave up and compensated {orch_comp}")
    print(f"choreographed: stuck with nobody waiting {chor_stuck} of {S} "
          f"(analytic {r['chor_expected']:.1f})")
    print(f"choreographed + {sweep:.0f} s stale-saga sweeper: all found, mean detection "
          f"{r['sweep_mean_s']:.1f} s")
    OUT["E5"] = r

def e6():
    hdr("E6  read_committed and the last stable offset: one open transaction stalls a partition")
    res = {}
    for scen, horizon in [("normal", 120.0), ("hung_60s_timeout", 120.0), ("hung_2pc_no_timeout", 700.0)]:
        rng = Random(SEED + 6)
        P = 5; gap_msg = 0.010
        txns = []  # (start, end, msgs[list of times], aborted)
        for p in range(P):
            t = rng.uniform(0, 0.05)
            while t < horizon:
                dur = rng.uniform(0.050, 0.250)
                msgs = []
                k = 0
                while k * gap_msg < dur:
                    msgs.append(t + k * gap_msg); k += 1
                end = t + dur; aborted = False
                if p == 0 and t <= 10.0 < t + dur + 0.1 and scen != "normal" and not any(x[4] for x in txns):
                    # producer 0 hangs mid-transaction at ~10 s
                    if scen == "hung_60s_timeout":
                        end = t + 60.0
                    else:
                        end = t + 600.0          # external coordinator restored after 10 min
                    aborted = True
                    msgs = [m for m in msgs if m <= t + dur / 2]
                    txns.append((t, end, msgs, aborted, True))
                    t = end + 0.5
                    continue
                txns.append((t, end, msgs, aborted, False))
                t = end + rng.uniform(0.0, 0.020)
        allm = []
        for ti, (s, e, ms, ab, hung) in enumerate(txns):
            for m in ms:
                allm.append((m, ti))
        allm.sort()
        first_off = {}
        for off, (m, ti) in enumerate(allm):
            if ti not in first_off:
                first_off[ti] = off
        # visible time of offset o = max end over txns whose first offset <= o
        order = sorted(first_off.items(), key=lambda kv: kv[1])
        vis = [0.0] * len(allm); j = 0; runmax = 0.0
        for off in range(len(allm)):
            while j < len(order) and order[j][1] <= off:
                runmax = max(runmax, txns[order[j][0]][1]); j += 1
            vis[off] = runmax
        lat = []; stalled = 0; aborted_seen_uncommitted = 0
        for off, (m, ti) in enumerate(allm):
            if txns[ti][3]:
                aborted_seen_uncommitted += 1
                continue                  # aborted records are filtered for read_committed
            L = vis[off] - m
            lat.append(L)
            if L > 1.0:
                stalled += 1
        r = {"messages": len(lat), "p50_ms": 1000 * pct(lat, 0.50), "p99_ms": 1000 * pct(lat, 0.99),
             "max_s": max(lat), "stalled_gt1s": stalled,
             "stalled_share": stalled / len(lat),
             "aborted_visible_to_read_uncommitted": aborted_seen_uncommitted}
        res[scen] = r
        print(f"{scen:20s} msgs {len(lat):7d}  p50 {r['p50_ms']:8.1f} ms  p99 {r['p99_ms']:10.1f} ms  "
              f"max {r['max_s']:7.1f} s  stalled >1 s {stalled:7d} ({100*r['stalled_share']:5.1f}%)  "
              f"aborted records a read_uncommitted consumer would see {aborted_seen_uncommitted}")
    OUT["E6"] = res

def e7():
    hdr("E7  Hot counter: exclusive lock held to commit vs escrow reservation")
    W = 64; n = 2000; work = 0.005; latch = 0.00005
    res = {}
    for stock in [1_000_000, 1000]:
        # exclusive: row lock held for the whole transaction, so decrements serialise
        lock_make = n * work
        # escrow: short latch to reserve, work proceeds concurrently, commit applies delta
        free = [0.0] * W; latch_free = 0.0; avail = stock; reserved = 0
        esc_ok = esc_ref = 0; end = 0.0
        for i in range(n):
            w = min(range(W), key=lambda k: (free[k], k))
            t = max(free[w], latch_free)
            latch_free = t + latch
            if avail - reserved >= 1:
                reserved += 1; esc_ok += 1
                done = latch_free + work
                avail -= 1; reserved -= 1   # confirm at end (bookkeeping only)
            else:
                esc_ref += 1; done = latch_free
            free[w] = done; end = max(end, done)
        lock_ok = min(n, stock); lock_ref = n - lock_ok
        r = {"stock": stock, "lock_makespan_s": lock_make, "lock_tps": n / lock_make,
             "escrow_makespan_s": end, "escrow_tps": n / end,
             "speedup": lock_make / end, "lock_ok": lock_ok, "lock_refused": lock_ref,
             "escrow_ok": esc_ok, "escrow_refused": esc_ref}
        res[str(stock)] = r
        print(f"stock {stock:9d}: lock {lock_make:6.3f} s ({r['lock_tps']:7.1f}/s)  escrow {end:6.3f} s "
              f"({r['escrow_tps']:8.1f}/s)  speedup {r['speedup']:6.1f}x  sold lock/escrow "
              f"{lock_ok}/{esc_ok}  refused {lock_ref}/{esc_ref}")
    res["params"] = {"workers": W, "txns": n, "work_ms": work * 1000, "latch_ms": latch * 1000}
    OUT["E7"] = res
