1The question

Every resilience pattern answers the same question: a request has arrived that the system cannot serve right now, so what should happen to it? A retry sends it again. A timeout stops waiting for it. A circuit breaker stops sending it. A bulkhead keeps it inside a partition. A fallback answers it from somewhere else. Load shedding refuses it. Catalogues usually present these as a toolbox of independent devices1–4. This article reads them instead as dispositions of demand, and asks of each one where the load goes when the answer is no.

The question matters because the patterns do not all move load in the same direction. Some multiply it, some spread it out in time, some confine it, some divert it and some remove it. The patterns that feel most defensive, retries above all, are the ones that add load to a component at the moment it has least capacity to spare. The result is a failure that is caused by the protection rather than by the fault. Google Cloud's global outage of 12 June 2025 had a null-pointer crash as its trigger, but the region that took longest to recover, us-central1, was held down for about two hours and forty minutes because restarting tasks all reached for the same Spanner table without randomised exponential backoff5. Amazon's us-east-1 event of October 2025 contained the same shape: after DynamoDB's DNS was restored, the EC2 subsystem that manages server leases could not finish re-establishing them before they timed out, queued the work again, and entered what Amazon called congestive collapse6.

The article catalogues twenty-six patterns as numbered plates in six families. Each plate records what triggers the pattern, what it does, what it spends, and when it fails, and carries a gauge placing it on a six-rung ladder of dispositions and one of four loci where it runs. A stdlib-only Python lab of nine deterministic experiments (seed 20260925) supplies every number in the prose and figures; its source and full output are reproduced at the end. The headline result is from experiment E3: after a two-second capacity dip, a service with three retries per request never recovered, and adding exponential backoff with full jitter did not rescue it. The only retrying policies that recovered within a few seconds were those that refused work (a retry budget, a circuit breaker) or discarded work nobody was still waiting for. Backoff moves load in time. Only refusal takes it away.

2Faults, errors and failures

The field's vocabulary comes from the dependability literature, and it is worth using precisely. Avižienis, Laprie, Randell and Landwehr define a failure as an event in which delivered service deviates from correct service, an error as the part of the system state that may lead to a failure, and a fault as the adjudged or hypothesised cause of an error7. The chain runs fault, error, failure, and a failure of one component is a fault for the component that depends on it. Fault tolerance, in their taxonomy, is the set of means that avoid service failure in the presence of faults: error detection, then recovery by rollback, rollforward, compensation or masking.

Distributed systems add a second axis: what a failed component is assumed to do. A crash failure stops and stays stopped. An omission failure drops some messages. A timing failure answers, but too late to be useful. A Byzantine failure does anything at all, including lying8. Almost every pattern in this article assumes crash, omission or timing faults. None of them defends against a component that returns confident, wrong answers.

Two results frame what the patterns can hope to achieve. Fischer, Lynch and Paterson proved that in an asynchronous system no deterministic protocol can guarantee consensus if even one process may crash, because a crashed process cannot be distinguished from a slow one9. Chandra and Toueg recast the problem in terms of unreliable failure detectors, oracles that may suspect correct processes and are allowed to be wrong10. Every timeout in production is such a detector. It guesses. The design question is never whether the guess is right but what the system does with a wrong one.

The second frame is empirical. Huang and colleagues at Microsoft named gray failure: a component that looks healthy to its own health checks while failing the requests that matter, so that the system's observers disagree about whether it is up11. Gunawi and colleagues read hundreds of public outage reports from dozens of cloud services and found cascades across dependent services and imperfect failure recovery among the recurring themes12. Yuan and colleagues, studying failures in Cassandra, HBase, HDFS, Hadoop MapReduce and Redis, found that 92% of catastrophic failures came from incorrect handling of non-fatal errors that the software had explicitly signalled13. The fault-handling code is where the failures live. That is the code these patterns are.

Finally, resilience is broader than fault tolerance. The resilience-engineering tradition defines it as a system's ability to adjust its functioning before, during and after disturbances so that it can sustain operations under both expected and unexpected conditions14, and Cook's short treatise reminds engineers that complex systems run in degraded mode as a matter of course15. The patterns here are the mechanised part of that ability: the reflexes, not the judgement.

3Seventy years of not trusting the parts

The idea that a reliable whole can be built from unreliable parts is older than software. John von Neumann's 1952 Caltech lectures, published in 1956, showed that majority voting over multiplexed unreliable components could drive the error probability of a whole network down as far as desired, at the price of redundancy16. Lyons and Vanderkulk at IBM turned the argument into triple modular redundancy for computer hardware in 1962: three copies and a voter, masking any single fault17. Masking by redundancy is still the pattern behind replicated state machines, whose general form Schneider set out in 1990 in a tutorial that remains the standard reference18.

Software fault tolerance followed in the 1970s. Randell's recovery blocks (1975) ran a primary routine, checked its result with an acceptance test, and on failure rolled back and tried an alternate, which is a fallback with a checkpoint19. Avižienis's N-version programming (1985) ran independently written versions and voted on their outputs20, and Knight and Leveson's 1986 experiment with 27 independently written versions rejected the hypothesis that independently developed programs fail independently21. Their result is the permanent warning over any fallback or replica that shares code, data or assumptions with what it backs up.

The commercial fault-tolerant machine arrived with Tandem. Jim Gray's 1985 report on Tandem field failures found that administration and software, not hardware, dominated outages, and argued for process pairs, transactions and fail-fast modules: a component should either work correctly or stop, never limp22. Fail-fast became crash-only software in Candea and Fox's 2003 formulation, where the only way to stop is to crash and the only way to start is to recover23, and it became Erlang's philosophy of letting processes crash under a supervisor that restarts them, set out in Armstrong's 2003 thesis24.

Retry and backoff came from networking. The ALOHA packet radio network (1970) had stations retransmit after a random delay when their packets collided25, and Metcalfe and Boggs's Ethernet (1976) doubled the range of that random delay after each successive collision, the binary exponential backoff that every retry library still implements26. Adaptive timeouts came from TCP: Karn and Partridge showed how to estimate round-trip time without being fooled by retransmissions27, and after the Internet's congestion collapses of 1986 Jacobson's 1988 paper added the estimator for round-trip variance, exponential backoff of the retransmission timer and the congestion window28. The RFC 6298 retransmission timer is a direct descendant29. Saltzer, Reed and Clark's end-to-end argument (1984) supplied the rule for where such checks belong: a function can be completely and correctly implemented only with knowledge held at the endpoints30.

The vocabulary most engineers use today is younger. Michael Nygard's Release It! (2007) named the circuit breaker, the bulkhead and the timeout as stability patterns for enterprise software and described the anti-patterns they counter31. Martin Fowler's 2014 description spread the circuit breaker's state machine widely32. Netflix built Hystrix around those patterns, with per-dependency thread pools and fallbacks, and later put it into maintenance mode, stating in its README that its focus had shifted to adaptive implementations such as concurrency limits and recommending Resilience4j for new work33. Dean and Barroso's "The tail at scale" (2013) made hedged requests a standard technique34, and Google's SRE book (2016) set out load shedding, criticality, client-side throttling and the anatomy of cascading failure35,36. Chaos engineering, from Chaos Monkey onward, made fault injection a routine test of all of it37.

The most recent turn is the recognition that the patterns interact. Bronson, Aghayev, Charapko and Zhu named metastable failures in 2021: states in which a trigger pushes a system into overload that persists after the trigger is removed, sustained by a feedback loop that is usually made of retries38. The follow-up study of real incidents found the pattern across many large operators and identified retry policy as the most common sustaining effect39. The patterns are protection against faults and, composed carelessly, the cause of the worst ones.

5Bounding the wait

A timeout is the only pattern that every remote call needs, because without one a caller waits forever for a peer that has crashed or partitioned away, and every resource it holds while waiting is lost to the rest of the system. Nygard lists the missing timeout among the most common causes of cascading failure in enterprise systems1. The difficulty is choosing the value. Amazon's Builders' Library describes the usual method: pick an acceptable false-timeout rate, such as 0.1%, and set the timeout at the corresponding percentile of the dependency's latency, measured on the caller's side40. A timeout set at the median fails half the calls. A timeout longer than the caller's own caller will wait does nothing useful.

A01

Timeout

D2 bound
Trigger
A call has not answered within a fixed interval.
Does
Abandons the call locally and releases the thread, socket or memory that was waiting on it.
Spends
Requests that would have succeeded just after the cut-off, which become errors.
Fails when
The value is copied from a default rather than derived from the dependency's latency distribution, or it is longer than the caller's own caller will wait.
In practice
Polly and Resilience4j timeout strategies41,42; context.WithTimeout in Go43.
A02

Deadline propagation

D2 bound
Trigger
A request enters a chain of services with a finite budget.
Does
Carries the absolute deadline with the request so every hop knows how much time is left and stops when it reaches zero.
Spends
Clock agreement between hops, and a protocol field to carry the remaining budget.
Fails when
One hop in the chain drops the deadline and starts a fresh one, after which everything below it works for a caller that has gone.
In practice
gRPC deadlines, sent on the wire as grpc-timeout44; Go's context package43.
A03

Adaptive timeout

D2 bound
Trigger
The latency of a dependency drifts over time.
Does
Sets the timeout from a running estimate of the latency mean and variance instead of a constant.
Spends
Estimator state, and ambiguity about which attempt a late reply belongs to.
Fails when
The estimator learns from samples taken during an incident and stretches the timeout exactly when it should hold.
In practice
TCP's retransmission timer with Karn's rule27,29.
A04

Failure detector

D4 divert
Trigger
Heartbeats from a peer stop arriving or arrive late.
Does
Converts silence into a level of suspicion, and past a threshold marks the peer as failed so traffic moves elsewhere.
Spends
Heartbeat traffic, and the certainty that some healthy peers will be suspected.
Fails when
The peer is alive but degraded (a gray failure), so it keeps answering heartbeats while failing real work.
In practice
φ accrual detection in Cassandra and Akka lineage45; Kubernetes liveness probes46.

Timeouts compose badly along a chain. If a request passes through four services and each enforces only its own timeout, a hop deep in the chain can still be working long after the user at the top has given up. Deadline propagation fixes this by sending the absolute deadline with the request: gRPC carries the remaining budget in a grpc-timeout header so that servers can stop work the client no longer wants44, and Go's context package exists to carry deadlines and cancellation across API boundaries43. Experiment E5 models a four-hop chain with a one-second budget. On a normal day (2.9% of requests failing) propagation saves only 0.7% of the total work. When every hop's latency doubles and 60.7% of requests fail, the work done after the deadline, which propagation would have avoided, is 19.2% of everything the chain does. At four times normal latency it is 56.6%. Deadline propagation is nearly worthless on a good day and saves most of the fleet's work on a bad one, which is exactly the day when the capacity is needed.

Adaptive timeouts are older than any of this. TCP's retransmission timer keeps a smoothed round-trip time and a mean deviation and sets the timeout at the mean plus four deviations, with a floor of one second in RFC 6298, and doubles it on each retransmission28,29. Karn's rule stops the estimator from sampling retransmitted segments, whose replies cannot be matched to an attempt27. The hazard in application code is the one the plate names: an estimator that keeps learning during an incident stretches the timeout just as it should stay short.

A failure detector is a timeout turned into a verdict about a peer. The φ accrual detector of Hayashibara and colleagues replaces the binary suspect-or-trust output with a continuous suspicion level computed from the distribution of heartbeat inter-arrival times, so that each application can choose its own threshold45. Kubernetes exposes three probe types with distinct consequences: a failing liveness probe restarts the container, a failing readiness probe removes it from service endpoints, and a startup probe holds the other two off while a slow container starts46. The gray-failure problem applies here directly: a probe that tests the process and not the work it does will report a healthy container that is failing every real request11.

6Trying again

A retry is the cheapest pattern to add and the most expensive to get wrong. Its value is real when faults are independent: if a transient error affects 10% of calls independently, one retry raises success from 90% to 99%, a gain of 9 percentage points, while a third retry adds only 0.09 points more (E1). When the fault is correlated, as it is in an outage, every attempt fails and retries add load and nothing else.

Retry

D0 multiply
Trigger
A call fails with an error believed to be transient.
Does
Sends the same request again, up to a fixed number of attempts.
Spends
Extra load on the dependency, and extra latency for the caller.
Fails when
The fault is correlated rather than transient, or retries are configured at several layers so their counts multiply.
In practice
gRPC retryPolicy47; AWS SDK standard retry mode48; Polly, Resilience4j41,42.
B02

Exponential backoff

D1 defer
Trigger
A retry is about to be sent.
Does
Waits a delay that grows geometrically with the attempt number, up to a cap.
Spends
Caller latency, and a longer tail before the caller gives up.
Fails when
Many clients failed at the same instant, so their growing delays stay aligned and they return together.

B03

Jitter

D1 defer
Trigger
Many clients are backing off from the same event.
Does
Randomises each delay so that retries that were synchronised become spread out.
Spends
Predictability of individual retry times.
Fails when
The randomisation window is small against the number of clients, or it is applied to the retry but not to the reconnection on restart.

Full, equal and decorrelated jitter49; Polly UseJitter41.
B04

Idempotency key

D0 multiply
Trigger
A request that changes state may have been received even though its reply was lost.
Does
Tags the request with a client-chosen key so the server can recognise a duplicate and return the first result.
Spends
Server-side storage of keys and results for a retention period.
Fails when
The key is regenerated on retry, or it expires before the last retry arrives, or two different requests share one key.
In practice
Stripe's Idempotency-Key50; IETF draft header51; AWS client tokens52.
B05

Hedged request

D0 multiply
Trigger
A request has been outstanding longer than a chosen latency percentile.
Does
Sends a second copy to another replica and uses whichever answers first, cancelling the other.
Spends
The fraction of requests that pass the hedge delay, sent twice.
Fails when
The slowness is shared by every replica (overload, a slow common dependency), so the hedge doubles load on a system that is already saturated.
In practice
Hedged and tied requests34; gRPC hedgingPolicy47; Polly hedging41.
B06

Retry budget

D5 refuse
Trigger
Retries are about to exceed a set share of recent traffic.
Does
Allows retries only while they stay under a ratio of first attempts, and fails fast once the ratio is spent.
Spends
Recovery from isolated transient faults during a broad incident.
Fails when
The budget is kept per process in a fleet of thousands, so each process stays under its ratio while the aggregate does not.
In practice
gRPC retryThrottling47; Envoy retry_budget53; Finagle RetryBudget54.

The worst property of retries is that they multiply across layers. If each of d layers retries r times, a single user request can arrive at the bottom layer (r+1)d times. Three retries at each of five layers gives 1,024 attempts for one request; retrying only at the top gives 4. Google's SRE book recommends retrying at a single layer for exactly this reason, together with a per-request retry limit and a server-wide retry budget36.

Retrying is safe only if repeating the request is safe. HTTP defines idempotent methods, those whose intended effect is the same whether the request is sent once or many times, and permits clients to retry them automatically55. POST is not idempotent, which is why Stripe introduced an Idempotency-Key header whose value the server uses to recognise a repeated request and return the saved result of the first50. The IETF HTTPAPI working group has been standardising the header since 2021; its latest version, draft 07 of October 2025, remains a work-in-progress Internet-Draft rather than an RFC51. Amazon's practice is similar, with a client-supplied token on mutating API calls52. The gRPC retry design is explicit that gRPC itself provides no way to mark a method as idempotent and leaves the choice of retryable status codes to the service owner47.

Backoff spreads retries in time and jitter spreads them across clients. Marc Brooker's 2015 simulation of clients contending for a shared resource showed exponential backoff without jitter still producing clustered calls, and compared full jitter (a delay drawn uniformly between zero and the exponential ceiling), equal jitter and decorrelated jitter49. Experiment E2 repeats the comparison in a slotted collision model: 100 clients starting within 100 slots, one call per slot, a collision failing every call in it, and a client giving up after fifteen attempts. Without jitter, 61% of the clients never succeeded, because clients that collided once stayed synchronised on every later attempt; the survivors spent 967 calls. Every jittered strategy brought every client through, with 312 (equal), 364 (full) and 299 (decorrelated) calls. The decisive variable is whether there is randomness at all. The ranking among the jittered variants differs from Brooker's, which found full jitter cheaper than equal jitter, and so depends on the contention model; the article does not claim a winner among them.

A retry budget caps retries as a share of traffic rather than per request. gRPC implements it as a token bucket per server name: each failure removes a token, each success adds tokenRatio, and retries and hedges stop when the count falls to half of maxTokens47. Envoy's circuit-breaker thresholds include a retry_budget expressed as a percentage of active requests, with a floor of concurrent retries53, and Finagle's clients carry a RetryBudget by default54. The SRE book's recommendation is a per-client budget that allows retries only while they are below 10% of requests35. In the canonical outage of E9, a 10% budget holds the hung dependency to 1.10× its normal arrivals, where three unbudgeted retries give 4.00×.

Hedging sends a second copy of a slow request instead of waiting for the first to fail. Dean and Barroso reported that in a BigTable benchmark, sending a hedged request after 10 ms cut the 99.9th-percentile latency for retrieving 1,000 keys from 1,800 ms to 74 ms while sending just 2% more requests34. Experiment E4 draws latencies from a log-normal body with a 2% slow tail. A single request has a p99 of 172.2 ms and a p99.9 of 727.0 ms. Hedging at the p95 delay (19.1 ms) costs 5.25% extra requests and cuts p99 to 29.2 ms and p99.9 to 37.9 ms, factors of 5.9 and 19.2. Hedging at p99 costs only 1.05% but leaves p99 at 177.2 ms, because the hedge fires only after the tail has already been paid. The model assumes the slowness is independent between replicas. When it is shared, as in an overload, every request passes the hedge delay and the pattern doubles load: its canonical load factor in E9 is 2.00×.

7Stopping asking

The circuit breaker is the pattern most identified with resilience engineering, and its logic is a small state machine. Closed, it passes calls through and counts failures. When the failure rate over a window crosses a threshold it opens, and calls fail immediately without touching the dependency. After a cool-down it goes half-open and admits a few trial calls; if they succeed it closes, and if they fail it opens again31,32. Resilience4j implements count-based and time-based sliding windows, a minimum number of calls before the failure rate is computed, and a slow-call rate threshold so that a breaker can trip on latency as well as errors42. Polly v8 uses a failure ratio over a sampling duration with a minimum throughput41, and Microsoft's standard HTTP resilience handler for .NET chains rate limiting, a total timeout, retry, a circuit breaker and a per-attempt timeout in that order56.

Circuit breaker

Adaptive throttling

D5 refuse
Trigger
Recent requests have outnumbered recent acceptances by more than a factor K.
Does
Rejects a proportion of new requests locally, with probability rising as acceptances fall.
Spends
A share of requests the backend could have served, while the history window catches up.
Fails when
The history window is long against the incident, so throttling engages late and releases late.

Client-side adaptive throttling35.
C03

Outlier ejection

D4 divert
Trigger
One host in a pool returns consecutive errors or has an error rate far from its peers.
Does
Removes that host from load balancing for an ejection time that grows with each repeat.
Spends
Capacity, since an ejected host serves nothing even if the fault was transient.
Fails when
Many hosts fail together, so ejection removes most of the pool; hence the cap on the ejected share.
In practice
Envoy outlier detection57; Istio outlierDetection58.

Every breaker faces a statistical trade-off between tripping on noise and noticing a real outage late. Experiment E7 computes it for a count-based window with a 50% threshold. With a baseline error rate of 20% (a noisy but working dependency), a ten-call window has a 3.3% probability that any given window trips, and when evaluated on every call it tripped 8,300 times per million calls. A fifty-call window has a trip probability of 2.1e-06 and did not trip once in 200,000 calls. The price is detection. When the error rate jumps to 60%, the ten-call window trips after a median of 8 calls and the fifty-call window after 40. Against a total outage the minimum is simply half the window. Knowing this in advance matters more than the specific numbers: the window should be sized in calls from the dependency's real traffic rate, and a low-traffic dependency will need a time-based window with a minimum call count, or it will never collect enough calls to decide.

A breaker that counts only errors has a further blind spot: a dependency that hangs produces no errors until the caller's timeouts fire, so the breaker's detection time is at least the timeout. In E9 the breaker holds the hung dependency to 0.025× its normal arrivals, but the first second's 100 requests all reach it before a single failure is recorded.

Client-side adaptive throttling, as described in the SRE book, needs no states at all. Each client keeps counts of requests attempted and requests accepted by the backend over the last two minutes, and rejects new requests locally with probability max(0, (requests − K × accepts) / (requests + 1)), with K = 2 as Google's usual setting35. It is smooth where the breaker is abrupt and it adapts to partial failure. Its weakness is its memory. E9 plays the formula against a total outage that begins after two minutes of healthy traffic: the accepted count must fall below half the attempted count before anything is rejected, which takes 61 seconds. Over the sixty-second canonical outage the throttle never engages, and the dependency receives 1.00× its normal load. Experiment E3 shows the other end of the same memory, in the section on metastable failure below.

Outlier ejection is the intermediary's version of the breaker, applied per host instead of per dependency. Envoy ejects a host after five consecutive 5xx responses by default, for a base ejection time of thirty seconds multiplied by the number of times it has been ejected, and never ejects more than a configured share of the cluster (10% by default)57. Istio exposes the same controls in a DestinationRule58. The cap on ejected hosts is the pattern's answer to correlated failure: if half the pool is returning errors, ejecting all of them would leave the survivors with twice the load.

8Confining the damage

Nygard took the bulkhead from shipbuilding, where watertight partitions keep a breach in one compartment from flooding the hull31. In software it means giving each dependency or class of work its own bounded share of the resources that would otherwise be shared: threads, connections, memory, or entire copies of the stack. Confinement does not reduce the damage. It chooses who bears it.

D01

Bulkhead

D3 confine
Trigger
Calls to one dependency slow down and start to accumulate.
Does
Gives each dependency its own capped pool of threads or permits, so a slow one cannot occupy the resources others need.
Spends
Utilisation, since reserved capacity sits idle when its dependency is quiet.
Fails when
The partitions are sized on nominal latency, not on the latency the dependency reaches when it is sick.
In practice
Hystrix thread-pool and semaphore isolation59; Resilience4j bulkhead42.
D02

Cell-based architecture

D3 confine
Trigger
A fault, bad deploy or poison request could affect every customer at once.
Does
Builds many independent copies of the whole stack and routes each customer to one, so a failure is bounded to a cell.
Spends
Duplicated fixed cost, a routing layer that must itself not fail, and cross-cell operations.
Fails when
A change is rolled out to every cell at once, or the cells share a dependency outside the cell boundary.

AWS cell-based architecture guidance60.

D3 confine

In practice
Erlang/OTP supervisors24,62; crash-only design23; Kubernetes restart policy46.

The quantitative case for bulkheads is Little's law: the average number of requests in a system equals the arrival rate multiplied by the average time each spends there63. A pool of threads is exhausted when the sum of rate times latency across its callers exceeds its size, and latency is the term that changes during an incident. Experiment E6 puts two dependencies behind a 200-thread pool: A takes 50 requests a second at 20 ms, B takes 150 a second. While B is healthy the pool needs a few threads. As B's latency rises, the shared pool saturates once B passes 1.33 seconds, and at a two-second hang A, which is perfectly healthy, has only 66.4% of its calls admitted. With a bulkhead of 40 threads for B and 20 reserved for A, A is untouched and B is admitted at 13.3%, calls that were going to time out anyway. Hystrix offered two forms of isolation: a separate thread pool per dependency, which also allows the caller to walk away from a blocked call, and a semaphore, which caps concurrency on the caller's own thread at lower overhead but cannot interrupt a blocked call59. A semaphore bulkhead is also a load reducer: in E9 a ten-permit bulkhead admits at most ten calls a second to a dependency that hangs for a second, a load factor of 0.10×.

At the scale of whole services, the bulkhead becomes the cell. AWS's guidance describes cell-based architecture as many independent replicas of a workload, each serving a subset of customers through a thin routing layer, so that a failure, a bad deployment or a poison request is confined to one cell60. Shuffle sharding goes further by giving each customer a random combination of workers rather than a fixed partition. MacCárthaigh's example uses eight workers and shards of two, giving 28 possible shards61. E8 computes the consequences. With eight workers and fixed pairs, a customer whose requests crash their workers takes out a quarter of all customers. With shuffle sharding, only 3.6% of other customers share both of its workers, though 46.4% share one of them, which is why shuffle sharding needs clients that retry across their shard. At Route 53's scale of 2,048 virtual name servers and shards of four there are 730,862,190,080 combinations, and the chance that another customer shares all four is 1.4e-12; the combinatorics are MacCárthaigh's61.

Supervision confines faults in time rather than space. An Erlang/OTP supervisor restarts a failed child according to a strategy (one-for-one, one-for-all, rest-for-one) and gives up, escalating to its own supervisor, if more than a set number of restarts occur within a set period62. Armstrong's argument was that it is safer to kill a process that has entered an unexpected state and restart it from a known one than to write defensive code for every possible error24. The restart-intensity limit is the part that matters for this article: without it, a deterministic fault becomes an endless restart loop, and every restart is a new burst of load on whatever the process connects to at start-up. The June 2025 recovery in us-central1 had this shape, with restarting tasks all loading from one database at once5.

9Refusing and shaping

Server-side patterns see what callers cannot: the server's own queue, CPU and latency. Their common principle is that a server should do less when it cannot do everything, and that doing less on purpose beats doing less by accident.

Rate limiting is the oldest of them. The token bucket admits a request when a token is available and refills tokens at a fixed rate up to a burst size; Turner's 1986 description of the leaky bucket for broadband packet networks is its best-known early statement, and Go's golang.org/x/time/rate package is a representative modern implementation64,65. Its limitation shows in E9: a rate limiter set at normal demand admits all of it to a dependency that has hung, a load factor of 1.00×, because the rate did not change. The constraint that matters during an incident is concurrency, and concurrency is what latency inflates.

Load shedding keeps a server at useful throughput past its capacity. Without it, throughput falls as load rises past saturation, because the server spends time on requests whose clients have already timed out. David Yanacek's account of Amazon's practice describes measuring and preserving goodput, rejecting early and cheaply, and prioritising requests67; the SRE book adds criticality classes so that batch work is shed before user-facing work35. Its caveat is the same as the SRE book's reason for client-side throttling: rejection is not free, and a server can be overloaded by the work of rejecting requests alone. HTTP gives servers two ways to say no: 503 Service Unavailable with an optional Retry-After header55, and 429 Too Many Requests66.

Adaptive concurrency limits replace the configured number with a measured one. Netflix's concurrency-limits library treats a service's limit on in-flight requests the way TCP treats its congestion window: its Vegas algorithm estimates queueing from the ratio of minimum to sampled round-trip time, and raises or lowers the limit accordingly68. The library's README makes the argument from Little's law that a limit expressed in requests per second goes stale as systems autoscale, while one expressed in concurrency does not. Envoy's adaptive concurrency filter applies the same idea at the proxy using a gradient controller69. In E9, a simple additive-increase, multiplicative-decrease limit falls quickly against a hang and holds the dependency to 0.014×.

Backpressure propagates a slow consumer's limits upstream instead of buffering. The Reactive Streams specification makes it the protocol: a subscriber calls request(n), and a publisher may send no more than it has been asked for70. SEDA had made the same argument for server architecture in 2001, with explicit queues between stages whose admission controllers keep each stage well-conditioned under overload71. Backpressure only works if it reaches the source; a single unbounded buffer anywhere turns it back into a queue that grows until memory runs out.

Deadline-aware queueing handles the requests that are already inside. CoDel, from Nichols and Jacobson, drops packets based on how long they have waited rather than how many are queued, distinguishing good queues that absorb bursts from bad queues that stand72. Facebook applied the same idea to server request queues: under a standing queue, switch from first-in-first-out to last-in-first-out, so that the newest requests, whose clients are still waiting, are served first, and bound the time a request may sit in the queue73. Experiment E3 shows how much this matters. With three retries per request, a server that simply discards queued requests whose client has already timed out recovered from the trigger faster than any other policy tried.

10Degrading and replacing

The D4 patterns send demand somewhere else: to a replica, a cache, a default answer or a smaller response. They are the patterns with the most dangerous hidden assumption, which is that the somewhere else is independent of whatever failed.

Fallback is the clearest case. Hystrix encouraged a getFallback for every command59, and a well-chosen default can keep a page rendering when a recommendation service is down. Amazon's Builders' Library argues the opposite position for most of its systems: fallback paths are exercised rarely, so they are poorly tested; they often behave differently under load from the primary path; and a fallback that shifts work onto another system can turn a partial failure into a total one74. Its preferred alternatives are to make the primary path more robust, to push data to where it is needed ahead of time, and to fail fast. Knight and Leveson's result on correlated faults in independently written software is the theoretical background: a fallback that shares assumptions with its primary will tend to fail on the same inputs21.

Serving stale data is the fallback that works best in practice, because its limitation is visible and bounded. RFC 5861 defines stale-if-error, which lets a cache serve a stale response when the origin returns an error, and stale-while-revalidate, which lets it serve stale content while fetching a fresh copy in the background, each within a stated number of seconds75. The staleness bound is the pattern's contract. Where a stale answer would be wrong, such as an account balance or an access decision, the pattern does not apply.

Redundancy with failover is the oldest D4 pattern and the one with the strongest theory, from triple modular redundancy through state machine replication17,18. Its practical weak point is the decision to fail over. A detector must declare the primary dead, and by the impossibility result it cannot be certain9. A detector that is too eager fails over from a slow but healthy primary and may end with two; one that is too cautious leaves traffic on a dead one. Replicas also fail together when they share a bug, a configuration or an input.

Brownout, from Klein and colleagues, dims optional content in a response when a controller sees latency rising, so that the essential part of the response still meets its deadline; they reported that it kept response times bounded under load spikes and failures while serving optional content whenever capacity allowed76. It is load shedding within a single request instead of across requests, and it depends on a product decision made in advance about what is optional.

Compensation deserves a mention though it has no plate. A saga splits a long transaction into steps, each with a compensating action that semantically undoes it if a later step fails77. It is fault tolerance for state rather than load: it answers the question the idempotency key raises, which is what to do when a sequence of changes is only partly applied.

11When the patterns compose: metastable failure

Every plate describes a pattern alone. Production systems run several at once, and the interactions are where outages come from. Bronson and colleagues define a metastable state as one in which a system stays in overload after the trigger that caused it has gone, because some sustaining effect keeps offered load above capacity; retries are the classic sustaining effect, but caches that go cold and slow-path fallbacks can do the same38. The system has two stable states for the same offered load, and a trigger moves it from the good one to the bad one.

Experiment E3 builds the smallest system that shows this. A server processes up to 10 requests per 10 ms tick in first-in-first-out order. Clients send 7 new requests per tick on average (70% utilisation) and time out after 200 ms. For two seconds, capacity drops to 4 per tick; then it returns to normal. Eight policies face the same trigger, with the same random arrivals, and the simulation runs for 180 seconds.

With timeouts alone, the backlog built during the dip drains in 2.30 seconds and goodput returns to 100%. With three retries per request, it never returns. The backlog makes fresh requests wait past their timeout, each timed-out request generates a retry, and offered load settles at 2.82× capacity while the queue grows to 305,418 requests by the end of the run. The server stays fully busy throughout, serving requests whose clients have already gone. Goodput is zero. Exponential backoff with full jitter makes no difference: offered load is 2.77× capacity and goodput is still zero, because backoff delays each retry without reducing the number of them. The same total demand arrives, only later.

Three retrying policies escape. gRPC-style retry throttling stops retrying once failures drain its token bucket and recovers in 2.31 seconds, the same as having no retries at all. A circuit breaker (100-call window, 50% threshold, half-second cool-down) recovers in 0.96 seconds with a peak queue of 231, because while open it sheds new requests as well as retries. The fastest recovery, 0.50 seconds, comes from the server discarding requests whose clients have already timed out, at a tenth of the cost of serving them. That policy does nothing to the clients; it stops the server from spending its capacity on work nobody will receive.

The SRE throttle, with its two-minute history, engages too late to prevent the storm and then locks in. By the time attempts outnumber acceptances by two to one, acceptances have fallen close to zero, so the rejection probability rises close to one, few requests are sent, and few acceptances are recorded to bring it down again. In the 180-second run it cut offered load to nearly nothing and goodput stayed at zero. A forty-minute run shows that it does recover, after 17.6 minutes; capping the rejection probability at 99% shortens that to 8.7 minutes. The SRE book presents the formula for rejections of the "out of quota" kind, where the backend is up and answering quickly35, and E3 uses it outside that setting, so this is a limitation of applying it to hangs and not a flaw in its stated purpose. The lesson generalises: any control loop whose input is its own output needs a floor of probe traffic, which is what a circuit breaker's half-open state provides.

The same shape appears in public incident reports. In December 2021, Amazon attributed a us-east-1 event to automated scaling that triggered a surge of connection activity from clients on its internal network, together with a latent issue that prevented those clients from adequately backing off78. In June 2025, Google's us-central1 region was held down by restarting Service Control tasks that all loaded policy from the same Spanner table without randomised exponential backoff; Google recovered by throttling task creation and moving traffic to multi-region databases5. In October 2025, Amazon's EC2 lease manager could not re-establish leases before they timed out, queued the work again, and made no forward progress until engineers throttled incoming work and restarted hosts to clear the queues6. In each case the trigger was fixed quickly and the sustaining loop was what held the system down. Huang and colleagues' study of metastable incidents at large operators found retry policy to be the most common sustaining effect39.

Two further points follow from queueing theory. Latency in a queue rises without limit as utilisation approaches one79, so any pattern that raises offered load near saturation has a disproportionate effect on the waiting time that drives timeouts, which drive retries. And the distinction between open and closed systems matters: in a closed system a client waits for a response before sending the next request, so load falls when latency rises; in an open system new requests arrive regardless of how the old ones are doing80. Internet services are mostly open, which is why they need patterns that refuse load, not merely ones that wait for it.

13Verifying that it works

Resilience patterns are code that runs rarely, under conditions that are hard to create on demand, which is the recipe for untested code. Yuan and colleagues found that the majority of catastrophic failures in the systems they studied could have been prevented by simple testing of error-handling code, and that in many cases the error handler was empty or only logged the error13. Chaos engineering, as Netflix described it, runs experiments against production by forming a hypothesis about steady-state behaviour, injecting realistic faults such as instance termination or added latency, and looking for differences37,81.

The lab suggests what those experiments should test. First, inject latency, not only errors: a breaker that counts errors never trips on a hang until the timeouts fire, and a bulkhead sized on healthy latency is exactly the size that a slow dependency exhausts (E6, E7). Second, test recovery, not only failure. The metastable runs in E3 are indistinguishable during the trigger; the difference appears only after it ends. A fault-injection experiment that stops measuring when the fault is removed will pass a system that never recovers. Third, test with realistic load. A system at 30% utilisation absorbs retries that would tip it over at 70%, and the incidents above all happened at scale. Polly v8 ships chaos strategies (fault, outcome, latency and behaviour injection) that run inside the same pipeline as the resilience strategies, which makes the second and third tests easier to run in pre-production41.

Configuration deserves its own review. Retry counts at every layer should be multiplied out (E1), timeout values checked against the caller's caller, breaker windows checked against real traffic rates (E7), and each fallback checked for dependencies it shares with its primary.

So where does the load go? The census answers in three parts.

It goes up when the caller tries again. The patterns above 1× are retry, exponential backoff, jitter, hedging and the retry budget, all at the caller. Backoff and jitter sit at 4.00× in the canonical outage, the same as a plain retry, because in a sixty-second outage every delayed attempt still arrives. They are essential against contention (E2) and useless against overload (E3). By rung, the geometric-mean factor is 2.00× at D0, 1.17× at D1 and 1.00× at D2, then falls below one: 0.56× at D3, 0.096× at D4 and 0.24× at D5. D4 is lowest because once a detector has declared a component dead, diversion takes all of its traffic away, while most D5 patterns still let a fraction through.

It stays where it is when the pattern bounds, confines or substitutes after the fact. Timeouts, deadlines, idempotency keys, cells, shuffle sharding, supervision, deadline-aware queueing, fallback, rate limiting and, over a sixty-second outage, adaptive throttling all leave the hung dependency's arrivals at 1×. That is not a criticism. Cells and shuffle sharding change who is hurt; timeouts free the caller's resources; deadline propagation frees the resources of every hop below. But none of them reduces the load on the part that is failing, and a system that relies only on them will carry a sick dependency's full load for as long as it stays sick.

It goes away only through patterns that cap concurrency or refuse. The ten patterns below 1× are the breaker, the concurrency limit, outlier ejection, failure detection with failover, the semaphore bulkhead, backpressure, request coalescing in a stale cache, load shedding and brownout. Each either limits how many requests may be outstanding or decides not to send them. Rate limiting by requests per second is not among them, because a hang does not change the request rate; it changes the concurrency.

The composition result sharpens this. In E3, the policies that recovered from a metastable retry storm were a retry budget, a breaker and server-side discarding of expired work; the policy that spread retries out in time did not. The practical rule is therefore to pair every D0 pattern with a D5 pattern at the same locus: no retry without a budget, no hedge without throttling, and on the server, no queue without deadlines. gRPC's retry design already does this by putting retry, hedging and throttling in the same configuration block47.

Limitations. The load factors in E9 are canonical, not measured: each depends on stated parameters, and different defaults would move them. The E3 simulation is a single-server, single-queue discrete-time model with Poisson arrivals and unit service slots; real metastable failures involve caches, connection pools and several services, and their recovery times would differ. The collision model in E2 simplifies contention to single-slot collisions, and its ranking of jitter variants disagrees with Brooker's, which is reported rather than reconciled. E5 assumes independent log-normal hop latencies. All nine experiments are deterministic under their seed and produce byte-identical output under different Python hash seeds.

def e1():

def e2():
    say("E2  Backoff and jitter under contention (slotted collision model)")
    say("    100 clients start within 100 slots; one slot serves one call; a collision fails every call in it; give up after 15")
    base, cap, N, runs, GIVEUP = 16, 20000, 100, 20, 15
    def run(strategy, rng):
        # next attempt time per client
        nxt = [rng.randint(0, 99) for _ in range(N)]
        attempt = [0] * N
        gave_up = 0
        sleep_prev = [base] * N
        done = [False] * N
        calls = 0
        t = 0
        last = 0
        remaining = N
        while remaining:
            # find earliest slot with pending attempts
            t = min(nxt[i] for i in range(N) if not done[i])
            who = [i for i in range(N) if not done[i] and nxt[i] == t]
            calls += len(who)
            if len(who) == 1:
                i = who[0]; done[i] = True; remaining -= 1; last = t
                continue
            for i in who:
                attempt[i] += 1
                a = attempt[i]
                if a >= GIVEUP:
                    done[i] = True; remaining -= 1; gave_up += 1
                    continue
                expo = min(cap, base * (2 ** a))
                if strategy == "none":
                    s = expo
                elif strategy == "full":
                    s = rng.randint(0, expo)
                elif strategy == "equal":
                    s = expo // 2 + rng.randint(0, expo // 2)
                elif strategy == "decorrelated":
                    s = min(cap, rng.randint(base, max(base, sleep_prev[i] * 3)))
                    sleep_prev[i] = s
                nxt[i] = t + 1 + s
        return calls, last, gave_up
    res = {}
    for strat in ["none", "equal", "full", "decorrelated"]:
        rng = random.Random(SEED)
        cs, ts, gs = [], [], []
        for _ in range(runs):
            c, l, g = run(strat, rng)
            cs.append(c); ts.append(l); gs.append(g)
        res[strat] = dict(calls=round(sum(cs) / runs, 1), time=round(sum(ts) / runs, 1),
                          gave_up=round(sum(gs) / runs / N, 6))
        say("    %-13s mean calls %8.1f   last success at slot %8.1f   clients giving up after 15 attempts %5.1f%%" % (
            strat, res[strat]["calls"], res[strat]["time"], 100 * res[strat]["gave_up"]))
    res["full_vs_none_calls"] = round(res["none"]["calls"] / res["full"]["calls"], 2)
    res["calls_floor"] = N
    say("    no-jitter backoff issues %.2fx the calls of full jitter" % res["full_vs_none_calls"])
    OUT["e2"] = res
    say()

def poisson(rng, lam):
    L = math.exp(-lam); k = 0; p = 1.0
    while True:
        p *= rng.random()
        if p <= L:
            return k
        k += 1

def e4():

        for _ in range(n):

def e5():
    say("E5  Deadline propagation versus hops that enforce only their own timeouts (4-hop chain, 1 s budget)")
    rng = random.Random(SEED)
    n = 50000
    budget = 1000.0
    hops = 4
    res = {}
    for slow in [1.0, 2.0, 4.0]:
        wasted_fixed = 0.0; wasted_prop = 0.0; total_fixed = 0.0; total_prop = 0.0; fails = 0
        for _ in range(n):
            lats = [math.exp(rng.gauss(math.log(120.0 * slow), 0.6)) for _ in range(hops)]
            # sequential chain: hop i starts when hop i-1's local work finishes
            t = 0.0
            # fixed per-hop timeout of 1000 ms each: every hop does its full work regardless
            starts = []
            for L in lats:
                starts.append(t); t += L
            end = t
            failed = end > budget
            if failed:
                fails += 1
            for s, L in zip(starts, lats):
                total_fixed += L
                if failed:
                    # work after the caller gave up is wasted, and work before it served nobody either
                    wasted_fixed += L
            # propagated deadline: each hop stops when the remaining budget reaches zero
            t = 0.0
            for L in lats:
                if t >= budget:
                    break
                w = min(L, budget - t)
                total_prop += w
                if failed:
                    wasted_prop += w
                t += L
        res[str(slow)] = dict(fail=round(fails / n, 6), wasted_fixed=round(wasted_fixed / total_fixed, 6),
                              wasted_prop=round(wasted_prop / total_prop, 6),
                              work_saved=round(1 - total_prop / total_fixed, 6))
        say("    latency x%.0f  requests failing %5.1f%%  work on failed requests: fixed %5.1f%%  propagated %5.1f%%  orphaned work (done after the deadline, saved by propagation) %5.1f%%" % (
            slow, 100 * fails / n, 100 * wasted_fixed / total_fixed, 100 * wasted_prop / total_prop, 100 * (1 - total_prop / total_fixed)))
    OUT["e5"] = res
    say()

def binom_tail(n, k, p):
    return sum(math.comb(n, i) * p ** i * (1 - p) ** (n - i) for i in range(k, n + 1))

def e7():
    say("E7  Circuit breaker: false trips against detection delay (count window, threshold 50%)")
    rng = random.Random(SEED)
    rows = []
    for N in [5, 10, 20, 50, 100]:
        k = int(math.ceil(0.5 * N))
        fp05 = binom_tail(N, k, 0.05)
        fp20 = binom_tail(N, k, 0.20)
        # sliding evaluation: fraction of calls at which the window trips, baseline 5% and 20%
        def slide(p, calls=200000):
            w = deque(maxlen=N); s = 0; trips = 0
            for _ in range(calls):
                x = 1 if rng.random() < p else 0
                if len(w) == N:
                    s -= w[0]
                w.append(x); s += x
                if len(w) == N and s >= k:
                    trips += 1; w.clear(); s = 0
            return trips / calls
        tr05 = slide(0.05); tr20 = slide(0.20)
        # detection: calls after fault onset (error rate 60%) until trip, window pre-filled at 5%
        det = []
        for _ in range(4000):
            w = deque(maxlen=N); s = 0
            for _ in range(N):
                x = 1 if rng.random() < 0.05 else 0
                if len(w) == N:
                    s -= w[0]
                w.append(x); s += x
            c = 0
            while True:
                c += 1
                x = 1 if rng.random() < 0.60 else 0
                s -= w[0]; w.append(x); s += x
                if s >= k:
                    break
            det.append(c)
        det.sort()
        rows.append(dict(N=N, fp_window_05=fp05, fp_window_20=fp20, trips_per_call_05=tr05, trips_per_call_20=tr20,
                         detect_median=quantile(det, 0.5), detect_p95=quantile(det, 0.95), outage_calls=k))
        say("    N=%3d  P(window trips) at 5%%: %.2e  at 20%%: %.2e  trips per 1e6 calls at 20%%: %8.1f  detect @60%%: median %3d p95 %3d calls  total outage: %d calls" % (
            N, fp05, fp20, 1e6 * tr20, quantile(det, 0.5), quantile(det, 0.95), k))
    OUT["e7"] = dict(rows=rows)
    say()
