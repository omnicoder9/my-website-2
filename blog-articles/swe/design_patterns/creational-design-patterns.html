1The trouble with new

Every object-oriented program contains a line like Shape s = new Circle(2.0). It reads as one act and is really two. It names a concrete class, Circle, at this exact spot in the source, so that nothing short of editing the line can make the program build something else here. And it commits to a policy: a brand-new object, distinct from every other, each time the line runs. The creational design patterns are the accumulated answers to the complaint that those two decisions should not have been made here, together, by this code.

The Gang of Four put the complaint more carefully in 1994. Creational patterns, they wrote, share two recurring themes: they encapsulate knowledge about which concrete classes a system uses, and they hide how instances of those classes are created and put together, so that the rest of the system knows its objects only through their interfaces1. That is the same pair of decisions seen from the other side. The first theme is about where the concrete class is named. The second is about how many objects answer to that name, and when they come into existence.

This article takes that pair literally and uses it as its organising question: where is the concrete class named, and who decides how many objects answer to it? Read that way, the five creational patterns in the 1994 catalogue are not five unrelated mechanisms. Factory Method, Abstract Factory, Builder and Prototype are four different addresses for the first decision, each one step further from the line that uses the object. Singleton is the only one of the five that is about the second decision, and it is also the one that aged worst, for a reason the census below makes precise: it welds the policy to the class, so that the type being used also decides its own lifetime. Most of what happened to creational design in the three decades since, including dependency injection, the retreat from Singleton and the arrival of language-level lazy constants, can be read as prising those two decisions apart and moving both of them outward, towards a single place that assembles the program.

The argument is carried by four devices. A ladder of six rungs, N0 to N5, records where the concrete class is named, from the call site itself to data read at run time. An instance policy axis records how many objects answer to the name: fresh, one, scoped, keyed or bounded. Twenty-two mechanisms, the classic five and seventeen of their relatives, are coded onto both axes as numbered plates, each with the same four fields and a small gauge, collected in a ledger at the end. And a lab of eight deterministic experiments, written in the Python standard library and run at build time, supplies every number the text quotes; its output is reproduced verbatim in the appendix. The code listings, 36 small programs across Java, C#, C++, Python, Go, Rust and TypeScript, were each compiled and executed for this article, and each listing is followed by the output it actually printed.

The scope is creation in class-based and prototype-based object-oriented languages. Structural and behavioural patterns appear only where they touch creation, as Flyweight does. Nothing here depends on a particular framework version, and where a platform feature is recent enough that its status may still be moving, the text says so.

2Where the patterns came from

The word pattern arrived in software from architecture. Christopher Alexander and his colleagues published A Pattern Language in 1977, a set of 253 connected solutions for towns and buildings, each stated as a problem that recurs in a context together with the core of a solution that can be used many times without ever being the same twice2. A companion volume argued that such languages, not individual designs, are how living places get made3. Richard Gabriel's later account of the software pattern community traces how directly its founders borrowed both the format and the ambition4.

The first borrowing was small and practical. At the OOPSLA workshop in 1987, Kent Beck and Ward Cunningham described a small Alexander-style pattern language for designing Smalltalk user-interface windows, written so that the people who would use the windows could take part in designing them5. The setting matters for creation. In Smalltalk-80, classes are themselves objects, and new is an ordinary message sent to a class object; any method that holds a class in a variable can create an instance of whatever class it holds6. Creation was already polymorphic in the language where the pattern movement grew up. The same was true, more radically, of the prototype-based languages that appeared at the same time: Henry Lieberman proposed in 1986 that objects be created by copying or delegating to existing exemplars rather than by instantiating classes7, and David Ungar and Randall Smith's Self, presented at OOPSLA in 1987, removed classes altogether8.

C++ was the opposite case. Its classes were compile-time entities that did not exist as objects at run time, so there was nothing to hold in a variable and send new to. James Coplien's 1992 catalogue of C++ idioms therefore included the workarounds that later became patterns: the exemplar, a prototypical instance that manufactures others, and the virtual constructor, a virtual function that creates an object whose type is decided by the object it is called on9. Bjarne Stroustrup's own answer to the question of whether C++ has a virtual constructor is that it does not, directly, and that a virtual clone() or create() function is the idiom that provides the effect10. Ralph Johnson and Brian Foote had meanwhile described how reusable classes grow into frameworks, distinguishing frameworks customised by subclassing, which they called white-box, from those customised by plugging in objects, which they called black-box11. Both styles need a way for the framework to create objects whose classes it cannot know, and the two styles correspond exactly to the Factory Method and Abstract Factory answers.

Erich Gamma, Richard Helm, Ralph Johnson and John Vlissides presented the idea of a design pattern catalogue at ECOOP in 199312, and the book followed in October 1994 with a 1995 copyright date. It catalogued 23 patterns in three groups: five creational, seven structural and eleven behavioural1. Two of its general principles bear directly on creation: program to an interface, not an implementation; and favour object composition over class inheritance. The first cannot be honoured at a line that says new Circle, which is why the creational chapter exists at all. The first Pattern Languages of Programs conference met the same year, and its proceedings appeared in 199513; the Siemens group's Pattern-Oriented Software Architecture followed in 199614 and later devoted a whole volume to resource management, where creation, pooling and lifetime are the main subject15.

Critique arrived almost at once, and it came from the Smalltalk and Lisp side of the argument. In a 1996 talk, Peter Norvig argued that 16 of the 23 patterns had qualitatively simpler implementations, or disappeared, in languages with first-class types, first-class functions and macros such as Lisp and Dylan16. Creational patterns were prominent among them, for the reason Smalltalk had already shown: when a class is a value, a factory is just a variable. The Gang of Four had said much the same about their own Prototype pattern, which they described as most useful in static languages like C++ where classes are not objects, and less important in Smalltalk or Objective-C, where a class object already plays the role of a prototype1.

The second strand of history is concurrency. Singleton and lazy initialisation look trivial until two threads call them at once. Douglas Schmidt and Tim Harrison published Double-Checked Locking as a pattern for making lazy initialisation cheap and thread-safe17. Within a few years a group of Java experts, including Joshua Bloch, Doug Lea and Bill Pugh, published a declaration that the idiom was broken under the Java memory model of the time, because a thread could observe the reference to a new object before observing the writes made by its constructor18. The repair came from the language, not from the pattern: JSR 133 revised the Java memory model for Java 5 in 2004, giving volatile the semantics that make the idiom correct19, and the formal model was published at POPL the following January20. Scott Meyers and Andrei Alexandrescu made the corresponding case for C++ in 200421, and C++11 then required that a block-scope static be initialised exactly once even when control reaches it from several threads22.

The third strand moved the naming decision out of the code altogether. Robert Martin's dependency inversion principle, published in 1996, argued that high-level modules should not depend on low-level ones, and that both should depend on abstractions23. Martin Fowler's 2004 essay gave the resulting technique its standard name, dependency injection, contrasted it with the service locator, and described the lightweight containers then emerging in Java24. Containers such as Spring, Guice and Dagger, and the one built into .NET, turned what had been a creational pattern into an infrastructure service25–28.

The last strand is absorption. Languages kept adding syntax for what had been patterns. Kotlin's object declaration is a singleton whose initialisation is thread-safe and happens on first access29. Rust added OnceLock in version 1.70 and LazyLock in 1.8030,31. Java has been previewing a platform construct for the same purpose: Stable Values in JDK 2532, renamed Lazy Constants in JDK 2633, and shipped as a third preview in JDK 27, released on 15 September 202634,35. Its stated aim is a value initialised at most once that the JVM can treat as a true constant, without the holder classes and double-checked locking that the pattern literature taught.

3Two decisions, six addresses

The ladder records where, in the program's text or configuration, the name of the concrete class last appears before an object of that class exists. The measurement is taken from the point of view of the client, the code that wants an object. Every factory eventually executes a constructor somewhere; what changes from rung to rung is how far that somewhere is from the client, and who is allowed to change it.

Three things stand out in the census. First, the Gang of Four's five sit only on the middle rungs: Factory Method (N2), Abstract Factory (N3), Builder (N3), Prototype (N3), Singleton (N1). None of them names the class at the call site, and none of them moves the name out of the program's code. Second, all 5 mechanisms at N4 and N5 belong to the assembly family, techniques that were named and popularised after the catalogue. Third, the policy axis is lopsided in a revealing way: 5 of the 22 mechanisms hand out a single object, and 4 of those are coded at N0 or N1, where the class being used is also the class that decides its own count. The most crowded rungs are N1 and N3, with 7 plates each: the rung where a type decides for its callers, and the rung where the client is handed an object that decides for it.

4Factory Method and its simpler cousins

The base case is the constructor call itself, and it deserves a plate because everything else is defined against it.

The smallest step away from N0 is to let the product's own type decide. Joshua Bloch's first item in Effective Java recommends considering static factory methods instead of constructors, for reasons that map cleanly onto the two decisions38. A static factory has a name, so BigInteger.probablePrime can say what a constructor cannot. It need not create a new object on each call, which moves the instance policy out of the client's hands; the Java language specification requires boxing conversion to return identical objects for small values such as int values between −128 and 127, and Integer.valueOf is the static factory through which that cache is reached39. It can return an object of any subtype of its return type. And the class of the returned object can vary from call to call: Bloch's example is EnumSet, whose static factories return one implementation for enum types of up to 64 constants and another for larger ones, a difference invisible to callers. The class need not even exist when the factory is written, which is how service provider frameworks such as JDBC let drivers arrive later. Python makes the same move through __new__: instantiating pathlib.Path produces either a PosixPath or a WindowsPath, chosen by the class on behalf of its caller40,41. In C++, std::make_unique, added in C++14, is a static factory in the same spirit, although its job is ownership rather than choice of class42.

The Gang of Four's Factory Method goes one rung further. Its intent is to define an interface for creating an object while letting subclasses decide which class to instantiate; the catalogue also records its older name, Virtual Constructor1. The canonical setting is a framework. The framework's code knows when an object is needed, for instance when a document is opened, and the application's code knows what that object should be. A method on the framework's class, overridden in the application's subclass, joins the two. The catalogue is candid about the cost: a creator subclass may exist only to override one method, and when products come in hierarchies the creators tend to form a parallel hierarchy that must be kept in step.

The listings below show the same shape in six languages. In Java, C# and C++ the factory method is an abstract or pure virtual member of the creator. In TypeScript it is an abstract method whose product only has to match an interface structurally. In Python the factory method has collapsed into data: because a class is a callable value, a subclass can override a class attribute holding the product class instead of overriding a method, which is Norvig's point about first-class types made concrete. Rust has no inheritance at all, so the creator becomes a trait: a provided method holds the fixed algorithm and calls a required method that each implementing type supplies, since a trait's default implementations may call its other methods43.

What does the move up the ladder actually buy? Experiment E3 in the lab generates a small multi-file Python code base in four styles, each creating one of three shapes at a number of call sites, then generates the same code base with a fourth shape added and diffs the two. The inline style writes the conditional at every call site (N0); the static-factory style centralises it on the product's module (N1); the injected style registers products at a composition root (N4); and the registry style lets each product register itself when its module is imported (N5). With 40 call sites, adding one product edits 41 existing files and 43 lines in the inline style, one file and 4 lines with a static factory, and 2 files with a composition root. The registry style edits no existing file at all: it adds one file of 5 lines.

The result is less trivial than it looks. Every rung above N0 makes the cost of a new product independent of the number of places that create one. What changes above N1 is not how much is edited but who must edit it. At N1 the product's own module must change for every new product, so a third party cannot extend it. At N4 only the assembly changes. At N5 nothing that already exists changes, which is the literal form of the open-closed principle and the reason plugin systems live there. The price of that last step appears later, in the plates for registries and provider discovery: a product that was named by a string can also be misnamed by one, and the error moves from the compiler to the run.

5Abstract Factory: choosing a family once

Abstract Factory provides an interface for creating families of related or dependent objects without specifying their concrete classes; the catalogue gives its alternative name as Kit1. The motivating example was a user-interface toolkit that must support several look-and-feel standards. A client that creates scroll bars, windows and buttons directly will sooner or later create a scroll bar from one standard and a window from another. A client that is handed a single factory object, and asks it for every widget, cannot.

The pattern is everywhere in platform libraries, often without the name. Java's AWT Toolkit is the abstract superclass through which the platform binds components to a particular native toolkit implementation45. ADO.NET's DbProviderFactory creates a provider's connections, commands, parameters and data adapters, so that code written against it works with any registered database provider46. The Gang of Four noted three implementation habits that have held up: concrete factories are usually singletons, since one per family is enough; they are often implemented with factory methods, one per product; and when the number of families is large, a factory can instead be configured with prototypes that it clones1.

The benefit the catalogue claims is consistency among products, and experiment E4 puts a number on how much consistency is at stake. With m families and p kinds of product, an uncontrolled client can assemble mp combinations, of which only m are consistent. Three families of five products already give 243 combinations and a consistent share of 1.23%. Uniform mixing is a caricature, so E4 also models hand wiring, in which each of p creation sites picks the intended family except for a small independent slip rate ε. At ε = 1% and 12 creation sites, 11.4% of assemblies contain at least one part from the wrong family; at 2% and 40 sites, 55.4% do.

With an abstract factory the family is chosen exactly once, so mixing is impossible by construction. The error that remains, choosing the wrong family, is a single decision that happens in one place and can be tested there. That is the general shape of a creational pattern's benefit: it does not remove a decision, it reduces many scattered instances of the decision to one.

The catalogue is equally clear about the cost. Supporting a new kind of product is difficult, because the abstract factory's interface fixes the set of products it can create, and adding one means changing that interface and every concrete factory that implements it1. The asymmetry is exact: adding a family is an addition of one class, while adding a kind of product is an edit to m + 1 of them. Designs that expect new kinds of product more often than new families usually pay for Abstract Factory without collecting.

6Builder: construction as a sequence

The name Builder now covers two patterns that share a word and little else. The Gang of Four's Builder separates the construction of a complex object from its representation, so that the same construction process can produce different representations1. Its example is a reader for rich-text documents that walks the document once and hands each token to a builder; one builder produces plain ASCII, another a TeX file, another an editable widget. The reader is the director: it knows the sequence of steps and nothing about the product. The concrete builder knows how to assemble one kind of product and nothing about the sequence.

The builder most programmers meet today is Bloch's, from the second item of Effective Java, and it solves a different problem38. A class with many optional parameters invites the telescoping constructor, a chain of overloads each adding one parameter, which is hard to write and harder to read; or the JavaBeans style, a no-argument constructor followed by setters, which lets the object be observed half-built and rules out immutability. Bloch's builder takes the required parameters in its own constructor, exposes each optional parameter as a named method, and creates the immutable product in a final build() call where cross-field validation can live. It is a way of simulating named optional arguments in a language that lacks them.

Experiment E5 quantifies the telescoping problem. With k optional parameters there are 2k subsets a caller might want to supply, but a telescoping chain provides only the k + 1 prefixes. With four optional parameters, as in Bloch's nutrition-facts example, it reaches 31.25% of the subsets; with ten it reaches 1.07%. Overloading cannot close the gap when the parameters share a type, because overloads are distinguished by type and arity, not by name. And positional construction invites a quieter error: with six int parameters there are 720 orderings of the arguments, and every one of the 719 wrong ones type-checks.

The language survey below shows how differently platforms have answered. Rust has neither overloading nor default arguments, so the builder is the idiom its API guidelines recommend for complex values48, and the standard library's own std::process::Command is one49; the listing's builder consumes and returns self so that calls chain, and puts validation in build(). Java's own recent APIs use the same form: HttpClient.newBuilder() returns a builder whose methods configure an immutable client50. Go took a different route. Rob Pike described self-referential option functions in 201451, and Dave Cheney popularised them as functional options later that year52: a constructor accepts a variadic list of functions, each of which mutates the value under construction, so the constructor's signature never changes as options are added. Python mostly does not need a builder class at all, since keyword arguments with defaults already provide named, optional, order-free construction, and dataclasses.replace derives a modified copy of a frozen instance53. C++20's designated initialisers give aggregates named fields at construction54, which leaves the fluent builder in the listing for the cases where construction must validate or assemble in steps. C# object initialisers do the same for settable members, naming each one at the point of construction55, so the C# listing keeps its builder for an immutable request whose settings must be checked against one another before it exists.

The plate for named and optional arguments sits at N1 with a fresh policy, the same cell as a static factory. That is the lesson of Bloch's builder read through the ladder: it never moved the naming decision at all. The client still names the product type, usually as NutritionFacts.Builder. What the builder relocates is when the object becomes complete, from a single expression to the end of a sequence, and it gives that moment a method in which to refuse. The Gang of Four's Builder is a genuine N3 pattern because the director is handed a builder it did not choose. The modern builder is a construction-time grammar.

7Prototype: the copy as a constructor

Prototype specifies the kinds of objects to create by means of a prototypical instance, and creates new objects by copying it1. The client holds an exemplar and asks it for a copy; the copy has the exemplar's run-time class, which the client never names. That makes Prototype the one classic pattern that can introduce a new kind of product while the program is running: install a newly configured exemplar in a registry, and every later request for that key produces copies of it. The Gang of Four's examples were a music editor whose palette tools clone notes and staves, and a prototype manager that keeps a registry of exemplars by key1.

Whether the pattern is needed depends on the language, which is why its history matters. The catalogue itself says Prototype is particularly useful in static languages like C++, where classes are not objects and little type information is available at run time1. In C++ the need is real: a copy constructor requires the static type, so copying through a base-class pointer needs a virtual function, the virtual constructor of Coplien's catalogue9 and Stroustrup's FAQ10. In Java the mechanism exists but is widely avoided. Bloch's thirteenth item explains why: Cloneable has no clone method, Object.clone copies fields shallowly, and the whole arrangement conflicts with final fields; his advice is to provide a copy constructor or copy factory instead38. Rust makes copying an explicit trait, Clone, that a type must implement or derive56, and ownership rules mean that a derived clone of a value holding String and Vec fields shares nothing mutable with the original. Python's copy module provides both shallow and deep copies of arbitrary objects, and its deep copy keeps a memo of objects already copied so that shared and recursive structures are reproduced faithfully57.

JavaScript is the case where Prototype stopped being a pattern and became the object model. Its inheritance is prototype-based: every object has a link to another object, its prototype, from which property reads fall through58. Object.create makes a new object whose prototype is a given existing object59, which is Lieberman's delegation and Self's design carried into the most widely deployed language in the world7,8. For an independent deep copy, the HTML standard's structured clone algorithm, exposed as structuredClone, copies a value graph including nested objects, arrays, maps and dates60.

The TypeScript listing's third line of output is the pattern's central hazard in miniature. A delegating copy looked like a copy, and its first write to a nested field rewrote the exemplar. Experiment E6 measures the same effect for the general case of a shallow clone. A small document template with 12 mutable containers (the document, its style, its tag list, four sections and their paragraph lists) was cloned both ways and then subjected to five ordinary edits. The shallow clone allocated 1 new container and shared the other 11 with the prototype; 4 of the 5 edits to the clone changed the prototype, and only the edit that rebound a top-level field was safe. The deep clone allocated all 12 containers anew and leaked 0.

This is a question about instance policy in disguise. A shallow prototype does not produce one fresh object per request; it produces one fresh shell per request around a set of shared parts, so its true policy is mixed, fresh at the top and singleton below. Every prototype-based design has to decide, part by part, which parts are shared on purpose, as Self's traits objects and JavaScript's method-bearing prototypes are, and which are shared by accident.

8Singleton, and the race it invites

Singleton ensures that a class has only one instance and provides a global point of access to it1. The catalogue lists its benefits candidly: controlled access to the sole instance, a reduced global namespace compared with global variables, the ability to subclass the singleton and choose the subclass at run time, and the freedom to change one's mind later and allow a fixed number of instances. It is the only creational pattern in the catalogue whose subject is the instance policy rather than the location of the class name, and it answers both questions in the same place: the class names itself and decides that there will be one.

That fusion is the source of nearly every objection that followed. Miško Hevery's widely read 2008 essay argued that singletons make an API lie about its dependencies: a method that silently consults a global instance has an input its signature does not show, which is why tests that pass alone fail together62. Joshua Kerievsky's Refactoring to Patterns includes a refactoring named Inline Singleton for removing one63. John Vlissides, one of the four authors, devoted an essay in Pattern Hatching to the problem the original text had left open, which is how and when a singleton should be destroyed64, and Andrei Alexandrescu's Modern C++ Design spends a chapter on singleton lifetimes, including singletons that must be resurrected after destruction because a later destructor still uses them65. In C++ the lifetime problem compounds the static initialisation order problem, in which one translation unit's global object is used by another's before it has been constructed66; Scott Meyers recommended replacing non-local static objects with function-local statics precisely to put construction under the control of first use67,68.

First use is where concurrency enters. Lazy initialisation defers construction until the first request, which saves start-up time for objects that may never be needed, and it creates a window in which two threads can both see that no instance exists yet.

Experiment E1 enumerates every possible interleaving of two and three threads through five versions of a lazily initialised accessor, and counts the schedules in which more than one object is constructed or in which some thread returns a reference to an object whose constructor has not finished. The naive check-then-create version constructs a duplicate in 18 of 20 two-thread schedules (90.0%) and in 98.82% of three-thread schedules. Adding a lock after the unsynchronised check, without checking again inside it, still duplicates in 57.14% and 87.39%. Double-checked locking with a racy publication, in which the reference to the new object may become visible before the constructor's writes, as the pre-2004 Java memory model permitted18, never duplicates in any schedule. Instead, in 27.27% of two-thread schedules and 33.33% of three-thread schedules, a thread returns an object that is not yet constructed. Double-checked locking with safe publication, and a fully synchronised accessor, are correct in every schedule.

The middle result is the one worth remembering. The broken form of double-checked locking did not make the bug rarer; it made it invisible. A duplicate singleton is at least a second object that a test can detect. A torn one is the right object, observed too early, and it can only be found by reasoning about the memory model. That is why the eventual fix was a change to the language specification rather than to the pattern: under the revised Java memory model a volatile write safely publishes the object20, and in C++11 a block-scope static is initialised exactly once, with concurrent callers waiting for completion22,71.

The idiomatic answers across platforms now mostly avoid writing the synchronisation at all. In Java the initialisation-on-demand holder relies on the fact that a class is initialised on first active use under a per-class initialisation lock69,70; the single-element enum goes further, because the language forbids creating enum instances by any means other than their constants, including reflection, and the serialisation mechanism restores enum constants by name rather than by construction38,72,73. In C# a static constructor runs at most once74, and Lazy<T> defaults to a mode in which the factory delegate runs on one thread only while every other caller waits for its result75,76. Go's sync.Once guarantees that no call to Do returns before the single call of its function has returned77. Rust's OnceLock and LazyLock provide the same guarantee for statics30,31. Kotlin's object and Swift's static stored properties are initialised lazily on first access and exactly once even under concurrent access29,78. Java's Lazy Constants, still in preview in JDK 27, are the platform's own version, with the additional promise that the JVM may constant-fold the value once it is set34.

Python deserves separate treatment, because it has several singleton idioms and they fail in different ways. A module is imported once per interpreter and cached in sys.modules, and the language documentation recommends a shared configuration module as the canonical way to share state across modules79,81. Class-based idioms are more fragile. Experiment E2 ran two of them against ordinary operations. The version that overrides __new__ to return a stored instance preserves identity everywhere, but Python calls __init__ on whatever __new__ returns41, so a second call with a different argument silently re-initialised the singleton: after two calls, __init__ had run 2 times and the level set by the first caller had been overwritten with the second caller's. The version that uses a metaclass to intercept the call runs __init__ once, but copy.copy, copy.deepcopy and a pickle round-trip each produced a second instance, because both copying and unpickling reconstruct an object through __new__ without going through the class's call57,82.

The language-level singletons are safer than the hand-written ones, and the plate records the price of the improvement honestly. They remove the race and the boilerplate, and with them the visible code in which a reviewer might have noticed that a global was being introduced. The rung and the policy are exactly those of the Gang of Four's Singleton.

9Keyed, shared and pooled

Between one instance and a fresh one per request lie three policies that are often left out of discussions of creational patterns, although between them they account for much of the creation code in real systems.

A keyed policy returns one object per distinct key. Java's logging API is the familiar example: Logger.getLogger(name) returns the existing logger for a name if one has been created and otherwise creates it83. The same documentation carries the warning that exposes the policy: a logger obtained this way may be garbage-collected if no strong reference to it is kept, so configuration applied to one may be lost when a fresh one is later created for the same name. Keyed factories must decide whether their registry owns its instances or merely remembers them.

Interning is a keyed policy in which the key is the object's own value. The Gang of Four catalogued the idea as Flyweight, a structural pattern whose flyweight factory returns an existing shared object when one with the requested intrinsic state exists1. Java's String.intern returns the pooled string equal to the receiver, adding the receiver to the pool if there is none84, and the boxing cache described earlier is interning made mandatory by the language39. The characteristic failure is identity comparison: == on two boxed integers is true for small values and false for larger ones, and code that happens to be tested only on small values passes.

A bounded policy lends objects from a fixed set and takes them back. The third volume of Pattern-Oriented Software Architecture describes Pooling as the management of multiple instances of one type of resource so that they can be reused rather than re-acquired, alongside related patterns for lazy and eager acquisition and for caching15. Real pools sit on a spectrum of strictness. Go's sync.Pool is explicitly a cache of temporary objects intended to relieve pressure on the garbage collector, and any item in it may be removed at any time without notice85; it bounds nothing. .NET's ArrayPool<T> lends arrays for reuse86, and its IHttpClientFactory pools the message handlers beneath HTTP clients and recycles them on a schedule, avoiding the problems that come from managing client lifetimes by hand87. Database connection pools are the strict case, with a hard maximum and callers that wait.

Experiment E7 simulates such a pool: 20,000 requests arriving at random at 400 per second, each holding a resource for 10 ms on average, where creating a resource costs 30 ms. Little's law gives the average number of resources in use as the arrival rate times the holding time88, here 4.0. Without a pool every request pays the creation cost, for a mean latency of 40.05 ms. A pool of exactly 4 resources has no slack at all and the queue grows without limit over the run: mean latency 263.65 ms, worse than no pool by a factor of six. One more resource changes everything; at 5 the mean is 16.03 ms, and by 8 it is 10.23 ms, within a quarter of a millisecond of the service time itself. Beyond that, larger pools buy nothing: 32 resources give 10.1 ms.

The shape is the general lesson. The benefit of a pool is fixed by the creation cost it avoids and is collected almost entirely by the first few members above the offered load, while the harm of a pool that is too small is unbounded. Sizing from Little's law and adding headroom is not a tuning detail; it decides whether the pattern helps or hurts.

Monostate is the last and strangest policy. Robert Martin describes it as the counterpart of Singleton: any number of objects may be constructed normally, but all of their fields are static, so they share one state89. It keeps construction at N0 and moves the singleton property from identity to data. Its gauge shows six distinct objects on the tape, which is accurate and misleading in exactly the way the pattern is.

10Assembly: moving the name out of the code

The rungs above N3 are where the naming decision leaves the classes that use objects and moves to a place whose only job is to assemble them. Martin's dependency inversion principle supplied the motive: policy-level code should depend on abstractions, and the details should depend on the same abstractions23. Fowler supplied the vocabulary. In dependency injection an assembler hands each object its collaborators, through a constructor, a setter or an interface method; in a service locator each object asks a well-known registry for what it needs. Fowler's own conclusion was that the choice between the two matters less than the principle they share, separating the configuration of services from their use24.

Constructor injection with no framework is the plainest form. Every class declares its collaborators as constructor parameters and never calls new on them; a single place near the program's entry point, which Mark Seemann named the composition root, constructs everything and decides every lifetime90,91. Bloch's fifth item in Effective Java recommends the same, and adds a variant in which the constructor receives a factory, a Supplier<? extends T>, rather than an instance, so that the class can create as many as it needs without naming their class38.

Containers automate the composition root and make the instance policy a declared property of each registration. The defaults reveal how differently the major containers think. Spring's default scope is singleton, and its documentation is careful to distinguish this from the Gang of Four's: the pattern hard-codes one instance per class loader, while a Spring singleton is one instance per container and per bean definition25. Guice's default is the opposite: unless told otherwise it returns a new instance each time it supplies a value26. Dagger resolves the whole graph at compile time, so that a missing binding is a build error rather than a start-up one27. The .NET container offers transient, scoped and singleton lifetimes, and in the development environment it validates that scoped services are neither resolved from the root provider nor injected into singletons28.

That last check exists because of a specific failure, which Seemann and van Deursen call a captive dependency: a longer-lived object holding a shorter-lived one, so that the short-lived object outlives its scope91. Experiment E8 implements a small container and resolves a request-handling graph in which a controller depends on an order service and an audit service, both of which depend on a repository, which depends on a database context. It resolves the controller three times in each of four scopes under four lifetime configurations. With everything transient the diamond is never shared, and 144 objects are constructed. In the typical configuration, with the repository and context scoped and the clock and logger singletons, 46 objects are constructed and both services see the same repository in 100.0% of requests. Change only the order service to a singleton and the container still resolves without complaint, constructing 35 objects; but the two services now share a repository in only 25.0% of requests, and 9 of the 12 resolutions hand the controller an order service holding a database context from a scope that has already ended. The container's static check found the problem in one line, naming the singleton and the scoped service it captured.

The experiment shows why lifetime belongs in the composition root and not in the classes. A class that declares itself a singleton cannot know what its dependencies' lifetimes will be; a composition root sees both ends of every edge and can check that no edge points from longer to shorter. The container's check is only possible because the policy was moved out of the classes.

A service locator keeps the container but moves the lookup back into the classes. Seemann's argument against it, that it hides a class's dependencies and turns a missing registration into a run-time failure at the point of use, is the same argument Hevery made against Singleton, and for the same reason62,92. On the ladder the locator is N4, because configuration decides the class; on the policy axis it inherits whatever the registry holds, usually one.

The top rung names the class with data. Go's database/sql is the cleanest example in a standard library. A driver package registers a constructor under a name in its init function, a program imports the driver for that side effect alone, and sql.Open selects a driver by the name string; registering the same name twice panics93,94. Fowler's Plugin pattern describes the same arrangement in general terms, linking classes during configuration rather than compilation95. Java's ServiceLoader locates providers of a service interface declared in module descriptors or on the class path96, and older factories such as DocumentBuilderFactory.newInstance() follow a documented lookup order through a system property, a configuration file and the service loader before falling back to the platform default97. Spring's XML configuration made the same step explicit, with a factory-method attribute that names a static factory to call by string98.

Finally, the patterns that languages absorbed sit at N3, because in each case the client is handed something that decides. When classes are values, as in Smalltalk and Python, a class passed as an argument is an abstract factory with one product6,41. When functions are values, a closure is one too. Norvig's 1996 observation that many patterns become invisible in such languages is, in the terms of this article, the observation that N3 costs nothing there16.

11What the evidence says, and how to choose

For a body of advice this widely taught, the direct empirical evidence is thin, and it is worth being exact about what it shows. The best-known controlled experiment, by Lutz Prechelt and colleagues, gave professional engineers maintenance tasks on programs written either with a design pattern or with a simpler alternative that provided only the flexibility actually needed99. In most of the nine tasks, the pattern version was neutral or helped: its extra flexibility cost no extra maintenance time, or it reduced the time. In a few tasks the simpler version was faster or less error-prone. The authors concluded that, unless there is a clear reason to prefer the simpler solution, choosing the flexibility of the pattern is probably wise, because unexpected requirements often arrive.

Later syntheses were more cautious. Zhang and Budgen's mapping study of the empirical literature found comparatively few studies, almost all concerned with the Gang of Four's catalogue100. The doctoral work behind it, which combined the mapping study with a survey of experienced users, rated Composite and Observer as generally useful and identified Singleton and Visitor as useful but with possible negative aspects101. A practitioner survey by Khomh and Guéhéneuc found, contrary to the common belief that patterns improve quality, that several quality attributes were judged to be harmed by them102. Hannemann and Kiczales, re-implementing all 23 patterns in AspectJ, found modularity improvements in 17 of them, a result that says as much about the scattering of pattern code in plain Java as about aspects103. None of this overturns the catalogue; it says that the benefit of a pattern depends on whether the variation it prepares for actually occurs, which is what the ladder is built to make visible. The widely adopted term for a solution that recurs and reliably makes things worse, anti-pattern, was popularised by Brown and colleagues in 1998104; Singleton is the creational pattern most often given that label, and the census suggests why.

The two axes make the practical choice fairly mechanical. The question to ask first is what is expected to vary, and who will change it.

The organising question was where the concrete class is named, and who decides how many objects answer to it. The census gives a plain answer to the first half. The five classic creational patterns occupy the middle of the ladder, from N1 to N3; everything above them, where a single place names classes for the whole program, arrived as named technique after the catalogue, through Martin's inversion principle, Fowler's essay and the containers that followed. The direction of travel over thirty years has been consistently outward and later: from the line that uses an object to the program's assembly, and from compile time towards start-up.

The second half has a sharper answer. Of the 5 mechanisms whose policy is to hand out a single object, 4 are coded at N0 or N1, where the product's own type decides, and they share one set of problems: hidden dependencies, test interference, initialisation order, and races on first use. The instance policy causes trouble exactly when the class that is being used is also the class that decides how many of it there are. The lab's two concurrency results, a broken fix that turned duplicates into invisible half-built objects and a lifetime mismatch that handed out context from a dead scope, are both consequences of deciding the policy somewhere that cannot see the whole graph.

So the advice the patterns add up to is narrower and more useful than any single pattern. Name concrete classes as far from their users as the expected variation justifies, and no further, since each rung up trades a compile-time error for a later one. Decide how many objects answer to each name in the same place that assembles the program, where both ends of every dependency are visible, and never inside the class itself. The modern platforms have mostly converged on that division of labour: containers that treat lifetime as a declared property of a registration, languages that supply once-only initialisation as a primitive, and a steady retreat from classes that decide their own count. The pattern that named the problem in 1994, Singleton, turned out to be the clearest case of solving it in the wrong place.

def diffstat(before, after):

    return touched_existing, added_files, lines

def simulate_pool(pool, lam, service_mean, create_cost, n_req, seed):
    """pool=0 means no pool: every request creates its own resource (no limit).
    Otherwise at most `pool` resources exist; the first use of each pays create_cost."""
    rng = random.Random(seed)
    t = 0.0; arrivals = []
    for _ in range(n_req):
        t += rng.expovariate(lam); arrivals.append((t, rng.expovariate(1 / service_mean)))
    if pool == 0:
        lat = [create_cost + s for _, s in arrivals]
        return sum(lat) / n_req, sorted(lat)[int(0.99 * n_req)], n_req
    free = [(0.0, i) for i in range(pool)]; heapq.heapify(free)
    warmed = set(); lat = []
    for at, s in arrivals:
        ready, i = heapq.heappop(free)
        start = max(at, ready)
        cost = s + (0 if i in warmed else create_cost); warmed.add(i)
        done = start + cost
        lat.append(done - at); heapq.heappush(free, (done, i))
    return sum(lat) / n_req, sorted(lat)[int(0.99 * n_req)], len(warmed)

class Container:

    def add(self, name, lifetime, deps): self.regs[name] = (lifetime, deps)
    def scope(self): return Scope(self)
    def captive(self):

        bad = []
        for name, (lt, deps) in sorted(self.regs.items()):
            for d in deps:
                if rank[self.regs[d][0]] < rank[lt]:

        return bad

class Scope:
    def __init__(self, c): self.c = c; self.cache = {}
    def resolve(self, name, path=()):
        if name in path: raise RuntimeError("cycle: " + " -> ".join(path + (name,)))
        lt, deps = self.c.regs[name]
        if lt == "singleton" and name in self.c.singletons: return self.c.singletons[name]
        if lt == "scoped" and name in self.cache: return self.cache[name]
        args = [self.resolve(d, path + (name,)) for d in deps]
        obj = (name, len(self.c.built.get(name, [])), tuple(id(a) for a in args))
        obj = type(name, (), {"deps": args})()
        self.c.built.setdefault(name, []).append(obj)
        if lt == "singleton": self.c.singletons[name] = obj
        if lt == "scoped": self.cache[name] = obj
        return obj
