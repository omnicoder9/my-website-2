pick a1f0e21 · 01The append that was not clipped

In the run-up to Go 1.26, the team building the language's automated modernisation tools wrote a transformation that any reviewer would wave through. It replaced the idiom append([]string{}, slice...) — a copy made by appending onto an empty slice — with a call to the standard library's slices.Clone(slice). Shorter, clearer, obviously the same thing.

It is not the same thing. When slice is empty, append([]string{}, slice...) yields an empty non-nil slice, and slices.Clone yields nil. In most Go programs that difference is invisible. In a few, it is the difference between a JSON document containing [] and one containing null, or between a caller's == nil check passing and failing. The Go team found the discrepancy, and rather than fix it, they removed the modernizer from the go fix suite entirely. It remains available as an advisory diagnostic. It is not permitted to edit your code.[1]

Hold that decision in mind, because it is the whole subject in miniature. A transformation that is right for every input a reasonable person would think of, wrong for one input nobody specified, applied by a tool whose entire value proposition is that you can accept its output without reading it. The engineering response was not to argue that the difference doesn't matter. It was to observe that somebody's program might be able to tell, and that "might be able to tell" is the criterion.

Refactoring is usually introduced as a hygiene practice: tidy your code, name things well, keep methods short. That framing is not wrong, but it buries the interesting part. Every refactoring is a proposition of the form this program and that program are the same program, advanced without proof, and underwritten by whatever evidence the engineer happens to have. The named moves in the catalogue — Extract Method, Move Method, Rename, Inline, Replace Inheritance with Delegation — are not really techniques for improving code. They are techniques for changing code whose preconditions for behaviour-preservation someone has already worked out, so that you do not have to work them out again from scratch every time.

That is the value the catalogue actually delivers. Fowler's book is often described as a list of tidying operations; read it as a list of proof obligations and it becomes a much stranger and more useful document.[2][3]

This article takes the claim seriously. It walks the history of the word, the family of moves the word names, the smells that motivate them, the debt metaphor that funds them, the harness that is supposed to check them, the scale at which they stop being editor operations and become infrastructure projects, and the empirical record on whether any of it works. Along the way it runs eight experiments, in a program you can run yourself, that try to break the claim in specific ways — because the useful question about refactoring is not does it help but under what conditions is the identity it asserts actually true, and how would you know.

pick b3c9d40 · 02What "observable" is doing in that sentence

The canonical definition is Fowler's: refactoring is a change to the internal structure of software that makes it easier to understand and cheaper to modify without changing its observable behaviour.[3] Opdyke, who coined the term in his 1992 dissertation, put it more formally: a refactoring is a program transformation that preserves behaviour, guarded by a set of preconditions which, if satisfied, guarantee that preservation.[4] Griswold's contemporaneous thesis worked the same territory from the compiler side, treating restructuring as a meaning-preserving transformation over a program dependence graph.[5]

All three definitions rest on the word observable, and none of them defines it. This is not an oversight; it cannot be defined in general. Observability is relative to an observer, and the set of observers of a running program is not knowable in advance.

Consider what a program can be observed doing. Its return values, plainly. The exceptions it throws, and their types — a change from IllegalArgumentException to IllegalStateException is a behaviour change, whatever the diff says. Its writes to durable stores, the messages it publishes, the order in which those messages become causally visible to a consumer. Beyond that, the field gets murky fast. Wall-clock timing is observable to anything with a timeout. Allocation count is observable to a benchmark and to a garbage-collection-sensitive latency SLO. Log line text is observable to the alerting rule that greps it. Iteration order over an unordered collection is observable to any consumer that accidentally came to depend on the ordering your particular hash function happened to produce.

Hyrum Wright's formulation of this — that with a sufficient number of users, every observable behaviour of your system will be depended upon by somebody, regardless of what you promised — is usually invoked about public APIs.[6] It applies with equal force inside a codebase. The set of behaviours you are permitted to change is not the set you documented. It is the set nobody happens to be relying on, and you find out which set that is by changing things.

So "behaviour-preserving" is always shorthand for something narrower: preserving those behaviours that are within the scope of the equivalence relation I have chosen, and about which I have some evidence. Different communities choose different relations. A compiler writer's notion of observable equivalence for C is set out in the standard's abstract machine and excludes timing and memory layout by fiat. A hard-real-time system's notion includes worst-case execution time. A financial reporting system's includes the exact decimal representation of a rounded value. The word "refactoring" is doing different work in each of those rooms, and most arguments about whether a change "counts as a refactoring" are really arguments about which equivalence relation is in force.[7]

The practical consequence

When a refactoring causes an incident, the post-mortem almost never finds that someone made a mistake in the transformation. It finds that a property which nobody had classified as behaviour turned out to be load-bearing. The useful discipline is therefore not "be careful"; it is "write down which observables are in scope before you start", which is also the only way to make a review of a refactoring mean anything.

pick c81a5f7 · 03The undecidable middle

Suppose you were willing to be rigorous. You have two programs and you want to know whether they are equivalent. This is not a hard problem in the sense that it takes a long time; it is a hard problem in the sense that there is no algorithm for it. Program equivalence for a Turing-complete language reduces to the halting problem, and Rice's theorem generalises the point: every non-trivial semantic property of programs is undecidable.[8][9]

This is not an academic aside. It is the reason every refactoring tool you have used behaves the way it does.

A sound tool cannot apply a transformation unless it can prove the preconditions hold — a proof obligation in the ordinary Hoare sense, discharged statically rather than at run time.[10] Since it cannot decide equivalence in general, it must choose a conservative approximation: refuse anything it cannot certify. That guarantees it never breaks your program, at the cost of refusing many transformations that are perfectly safe. Opdyke's contribution was precisely this — for each refactoring in his catalogue, a set of syntactic and type-level preconditions sufficient (not necessary) for behaviour preservation.[4] Roberts later showed how to make these preconditions composable and to compute the postconditions of a refactoring, so that a sequence of them could be checked without re-analysing the program at each step.[11]

Alan Donovan's account of Go's source-level inliner is the best modern description of what conservatism costs in practice. The inliner exists to replace a call with a copy of the callee's body; it is about seven thousand lines of dense, compiler-like logic, and the great bulk of that is hazard analysis rather than substitution.[12] When the analysis cannot prove that argument expressions are effect-free with respect to each other, it does not refuse — it emits an explicit parameter-binding declaration, producing code that a human expert would call fussy. Donovan's own summary is that an inliner is like an optimising compiler whose objective is tidiness rather than speed, and that such a compiler is, by Rice's theorem, never finished.[12]

An optimizing compiler is free to delete each call to a function with no effects, because it has no effects today. The inliner is not, because the function may become important tomorrow.

Paraphrasing the Go inliner's design rationale

That asymmetry is worth dwelling on. A compiler's output is ephemeral; it is regenerated from source on every build, so it may exploit facts that are true only at this instant. A refactoring's output is the source. It must remain correct across every future edit that the source will undergo. Refactoring tools are therefore held to a strictly stronger standard than optimisers, which is why they do less.

Human engineers, of course, are not bound by soundness. We routinely apply transformations we cannot prove, on the strength of having read the code and formed a belief about what it does. Peter Naur's characterisation of programming as theory-building is the right lens here: the artefact under-determines the theory that produced it, and a refactoring is an assertion made from inside that theory.[13] The assertion is usually right. When it is wrong, it is wrong in ways the code does not display, which is precisely why we build harnesses.

pick d02b4ac · 04Where the word came from

The practice long predates the noun. Structured programming made the shape of a program into something a person could choose rather than inherit, which is a precondition for the idea that you might change the shape without changing the meaning.[14][15] Parnas's criteria for decomposition gave the first principled account of why one shape might be better than another — modules should hide the decisions most likely to change — and thereby supplied refactoring with its objective function twenty years before it had a name.[16]

Lehman's laws, formulated from observation of OS/360 and refined through the 1970s and 1980s, supplied the pressure. A program embedded in a real environment must continually change or become progressively less useful; and as it changes, its complexity increases unless work is explicitly done to reduce it.[17][18] The second law is the entire economic argument for refactoring, stated before the word existed. Parnas's later essay on software ageing made the same point in more clinical language.[19] Brooks had already drawn the line refactoring depends on: some complexity is essential to the problem and cannot be removed by any amount of tooling, and some is accidental — an artefact of how the solution happens to be expressed.[20] Refactoring is a claim that a particular lump of complexity belongs to the second category, and the claim is frequently wrong.

The Smalltalk community supplied the culture. In a live image, restructuring is cheap enough to do casually, and the browser makes the shape of the system continuously visible. Ralph Johnson's group at Illinois turned that culture into research. William Opdyke's 1992 dissertation named the practice, defined it as a behaviour-preserving transformation, and catalogued twenty-six of them with explicit preconditions.[4] Bill Griswold's 1991 Washington thesis had independently formalised meaning-preserving restructuring in terms of program dependence graphs.[5] Opdyke and Johnson's earlier SOOPPA paper had already sketched the frame: refactoring as the thing you do to an application framework so that it can absorb the next application.[21]

Then, crucially, the tool. Don Roberts, John Brant and Ralph Johnson built the Refactoring Browser for Smalltalk, published in 1997.[22] It is the origin of essentially every refactoring feature you have used since: the idea that the transformation is initiated by selecting code and choosing a menu item, that the tool checks preconditions and refuses if they fail, and that the whole operation is atomic and undoable. Roberts's own thesis supplied the analysis that made a sequence of such operations tractable.[11]

Kent Beck brought the practice into Extreme Programming as one of the inner-loop activities, alongside testing, and contributed the two metaphorical hats: at any moment you are either adding function or refactoring, never both, and you should know which hat you have on.[23][24] Martin Fowler's 1999 book, with contributions from Beck, Brant, Opdyke and Roberts, made it a discipline with a vocabulary: seventy-two named moves, each with a motivation, a mechanics section, and worked examples; plus the chapter on "bad smells in code", written with Beck, which gave engineers a way to talk about design problems without committing to a metric.[2]

The 2010s were about tools catching up and evidence arriving. IntelliJ IDEA and Eclipse JDT made refactoring an expected IDE feature for Java. Michael Feathers wrote the book about the case the catalogue quietly assumed away — code with no tests — and gave the field the word seam and the technique of characterisation testing.[25] Joshua Kerievsky connected the catalogue to the design-patterns literature,[26] framing patterns as destinations you refactor toward rather than designs you choose upfront.[27] Demeyer, Ducasse and Nierstrasz worked the same problem from the reengineering side, treating a legacy system as something you negotiate with rather than replace.[28] Mens and Tourwé's survey mapped the research landscape.[29] Fowler's second edition, in 2018, moved the examples to JavaScript and dropped much of the object-oriented framing, acknowledging that the moves were never really about classes.[3]

The most recent turn is the one visible in Go 1.26, and it is a genuine shift in the locus of control. For thirty years, refactoring tools operated on code you owned, at your instigation. The //go:fix inline directive lets the author of a library express a migration once, in the library, and have every downstream user's toolchain apply it on demand.[12] Google's internal Java, Kotlin and C++ teams have worked this way for years, to the tune of millions of eliminated calls to deprecated functions; Go's inliner alone has prepared more than eighteen thousand changelists against the monorepo.[12] Rust's edition mechanism plays a related trick at language scale: breaking changes are allowed, but every one of them must ship with an automated migration in cargo fix.[30]

The through-line

Every generation of the tooling has moved the same boundary in the same direction: enlarging the set of transformations a machine can certify, so that the set requiring human judgement gets smaller and more interesting. Nothing about the fundamental limit has changed since 1953. The boundary just keeps moving.

pick e5518b3 · 05Debt, and what the metaphor charges

Ward Cunningham introduced the debt metaphor in an OOPSLA experience report on the WyCash portfolio management system in 1992 — the same year Opdyke named refactoring, by coincidence rather than coordination.[31] His formulation was narrow and precise: shipping code that does not quite match your current understanding of the domain is like going into debt; it lets you ship, and it is fine as long as you pay it back promptly by refactoring as your understanding improves. Interest accrues as the extra effort every subsequent change costs while the mismatch persists.

Cunningham was explicit for the rest of his life that this was not a licence for sloppiness. The debt he described is the gap between the code and what you have learned, not the gap between the code and what you knew all along. Fowler's technical debt quadrant is the standard clarification: debt can be deliberate or inadvertent, and prudent or reckless, and these are independent axes.[32]

The academic literature has since tried to convert the metaphor into something measurable, with mixed success. Kruchten, Nord and Ozkaya's framing — debt as the invisible part of the software, distinct from both visible features and visible defects — is the most durable contribution.[33] The Dagstuhl seminar on the subject produced a useful taxonomy and, more usefully, a warning that the term had already been stretched to cover everything anyone disliked about a codebase.[34] Potdar and Shihab's work on self-admitted technical debt — comments in which developers explicitly flag a shortcut — gave researchers a tractable proxy at the cost of measuring only the debt somebody bothered to confess.[35]

What the interest actually costs

The quantitative estimates converge on an uncomfortable number. Besker, Martini and Bosch surveyed forty-three developers twice weekly over seven weeks and found that, on average, 23% of development time was reported as wasted dealing with technical debt, with additional testing the most common sink.[36] Their replication and extension study, using an independent dataset, landed in the same region and identified additional code analysis — the work of figuring out what existing code does before you can safely change it — as most strongly associated with wasted time.[37]

Tornhill and Borg approached it from the other end, mining thirty-nine proprietary production codebases with CodeScene and joining the results to Jira. Across 30,737 files they found that low-quality code contained fifteen times more defects than high-quality code, that resolving an issue in low-quality code took on average 124% more time in development, and — the finding that matters most for planning — that maximum cycle times were about nine times longer, meaning the variance is worse than the mean.[38] You can schedule around a task that is reliably twice as slow. You cannot schedule around a task that is usually fine and occasionally takes a fortnight.

Martini and Bosch's work on architectural debt adds the compounding term: some debt items are contagious, in that new code written against a bad interface inherits the badness, so the interest is not fixed but grows.[39] That is the mechanism behind the familiar experience of a module that was annoying two years ago and is now untouchable.

None of these numbers should be treated as constants of nature. They are estimates from self-report and from proprietary tooling with its own opinionated quality model, over samples that are not random. What they support is the qualitative claim, which is strong and consistent across methods: the cost of not refactoring is not zero, is not small, and shows up mostly as schedule variance rather than as a line item.

A caution about the metaphor

The debt frame is persuasive to finance-literate stakeholders, which is why it spread. It also imports assumptions that do not hold: that the principal is knowable, that interest rates are stable, that you can choose to service the debt at a time of your choosing. In practice you discover the principal by trying to pay it, the rate depends on which module the next feature lands in, and the payment schedule is set by whoever files the next ticket. Use the metaphor to open the conversation, not to run the calculation.

pick f7d2c19 · 06Smells are hypotheses about the future

The "bad smells" chapter that Beck and Fowler wrote for the 1999 book is the most-copied piece of the refactoring literature and the most frequently misread.[2] A smell is deliberately not a rule. Fowler's own framing is that a smell is a hint, quick to spot, that may indicate a problem worth a closer look — and the reason it is not a rule is that no threshold on any metric captures what makes a long method bad. What makes a long method bad is that the next change to it will be expensive, and whether that is true depends on what the next change is.

Read that way, each smell is a bet on a distribution of future changes. Divergent change — one class that is modified for several unrelated reasons — is a bet that those reasons will continue to arrive independently, in which case splitting the class pays. Shotgun surgery — one conceptual change that requires edits in many places — is the dual bet, and the fix is the opposite move. If you are wrong about the distribution, the "fix" makes things worse: a class split along the wrong seam turns every future change into shotgun surgery.

Detection tooling has advanced considerably and agreement has not. Van Emden and Moonen's early work established the pattern of static detection from source.[40] Arcelli Fontana and colleagues assessed multiple detectors on the same corpora and found substantial disagreement about which entities were affected.[41] Palomba and colleagues showed that version history often detects smells that static analysis of a single snapshot cannot see, because the smell is a property of how the code changes rather than of how it looks.[42] Machine-learning approaches have been surveyed and meta-analysed, with the honest conclusion that reported performance depends heavily on how the ground truth was labelled.[43] Sharma and Spinellis's survey and Lacerda's tertiary review both note that the field lacks an agreed definition of most of the smells it detects.[44][45]

Six defensible measures, six different verdicts

The lab makes this concrete. Take eight classes with plausible characteristics and rank them by six standard measures — lines of code, weighted methods per class, number of methods, efferent coupling, LCOM4 cohesion, and Martin's instability.[46][47][48][49] Each is a defensible operationalisation of "this class needs attention".

The rankings agree at 0.29 on Kendall's tau — better than chance, nowhere near consensus. Three of the eight classes are "the worst class" depending on which metric you asked, and seven of the eight make some metric's top three. If your team runs one detector and mine runs another, we will schedule different work and both of us will be able to justify it with numbers.

Shepperd's critique of cyclomatic complexity as a metric — that it is strongly correlated with lines of code and adds little independent information — has been repeatedly confirmed, most thoroughly by Landman and colleagues over a large Java and C corpus.[50][51] That does not make it useless; it makes it a proxy for size wearing a lab coat.

Sjøberg and colleagues ran the experiment that ought to settle the question and found something more interesting than either camp wanted: after controlling for file size and churn, most individual smells had no statistically significant effect on maintenance effort in their sample.[52] Olbrich and colleagues found that smelly components changed more often — but the direction of causation is genuinely ambiguous, since the components you change most are the ones most likely to accumulate smells.[53]

How to use a smell anyway

Not as a work queue. As a prompt for a conversation with the change history: which files did we touch most in the last six months, and are any of them smelly? The intersection of high churn and low quality is the only prioritisation signal in this area with consistent empirical support, and it is the basis of behavioural code analysis as a practice.[54][38]

pick 0a3f61d · 07Extract Method

Extract Method is the most-performed refactoring in every study that has counted, and it is the one people are most confident about. Take a coherent fragment, give it a name, call it from where it was. Fowler's mechanics are four steps long. Every IDE has it bound to a keystroke.

It is also the refactoring with the largest gap between how simple it looks and how many things must hold for it to be sound. The extracted fragment must not contain a jump out of the enclosing scope — return, break, continue, a labelled goto, a yield. If it assigns to more than one variable that is read afterwards, you need a return tuple or an out-parameter or a mutable holder, each of which changes something. If it reads a variable that is later reassigned in the original scope, the read must move with it. If the enclosing method is inside a lock, an exception handler, a transaction, or a defer, the extracted call sits inside that context but the extracted body might one day be called from outside it. In a language with checked exceptions, the extracted method's signature acquires a throws clause that becomes part of an interface.

The lab's first experiment takes the textbook case: extract the body of a loop that contains an early return. Every statement survives, in order. The return, which used to leave the enclosing function, now leaves the extracted one. Enumerating all 85 input lists of length 0–3 over the alphabet {0,1,2,3}, the two programs disagree on 70 of them.

The interesting variant is the second one. A careful engineer, having extracted the body, notices that the result is being discarded and adds a check — written the way it reads most naturally:

Listing 1 — the version that ships
def _found(i, x, limit):
    return i if x > limit else None

def first_bad_index(xs, limit):
    for i, x in enumerate(xs):
        hit = _found(i, x, limit)
        if hit:                 # <-- index 0 is falsy
            return hit
    return -1

This version is correct for every index except zero. It disagrees with the original on 42 of the 85 enumerated inputs, and a six-case example suite catches it 1 times out of six. Index zero is the position a hand-written test is least likely to exercise, because "the first element" feels like a special case rather than the general one.

The industrial version of this problem is worth noting: extraction is easy to perform and hard to choose. Which fragment? Where should the seam be? A team at ING built a data-driven Extract Method recommender by learning from the extractions their own engineers had already made, on the reasoning that the metric-based recommenders in the literature were optimising quantities nobody in the building cared about.[55] That reframing — from "which extraction improves the metric" to "which extraction would our engineers have made" — is the honest one, because the objective was always tacit.

pick 1b7e4c2 · 08Inline Method

Inline is Extract run backwards, and it is instructive precisely because it is the refactoring for which we have the most detailed public account of what soundness costs. Go's source-level inliner, built from 2023 and shipped as an analyzer in go fix in Go 1.26, has published its hazard list.[12] Six categories, each of which sounds like an edge case and each of which occurs constantly in real code.

Parameter elimination. Substituting an argument for a parameter is trivial when the parameter occurs once. When it occurs several times and the argument is a magic value, naive substitution scatters copies of that value through the body and destroys the relationship between them.

Side-effect ordering. Given func add(x, y int) int { return y + x } and a call add(f(), g()), naive substitution yields g() + f() and swaps the order in which two side-effecting functions run. It is bad style to depend on argument evaluation order; the tool must nonetheless be correct for code that does.

Fallible constant expressions. This one is genuinely surprising. Inlining index("", 0) where index(s string, i int) byte { return s[i] } produces ""[0], which is a constant expression, evaluated at compile time, out of bounds — so the program that previously ran fine (because the call was never reached) now fails to build. The inliner maintains a constraint system over expressions that might become constant under substitution, and solves it.

Shadowing. Every identifier in the argument expression must still refer to the same symbol after substitution, and every identifier in the callee's body must refer to the same symbol at the call site — including imports that may need to be added.

Unused variables. Removing an argument expression can remove the last reference to a caller local, which in Go is a compile error. Worse, two independently valid inlines can each remove the second-to-last reference, so both are fine alone and neither is fine together.

Defer. If the callee uses defer, inlining the body would move the deferred call's execution to the caller's return, which is too late. The only safe transformation wraps the body in an immediately invoked function literal — acceptable interactively, so undesirable in batch that the go fix analyzer refuses to inline such calls at all.

Semantic conflict

The unused-variable case generalises into something the Go team names explicitly: a semantic conflict, where two edits are textually independent but their meanings are incompatible. Three-way merge detects syntactic conflicts and is blind to these. Semantic conflicts are rare, and they usually surface as compile errors, which makes them survivable in a statically typed language and considerably less so elsewhere.[1]

Inline's second life is as a migration mechanism, which is the more important use. Annotate a deprecated function with //go:fix inline and give it a body that forwards to the replacement; every downstream caller's go fix run then rewrites the call site. Renaming ioutil.ReadFile to os.ReadFile across the entire public Go corpus becomes a two-line change in the standard library.[12] Argument order can be corrected the same way, because the forwarding body can transpose them. Types and constants get the same treatment through aliases. What looks like a small IDE convenience is, at scale, a general mechanism for API evolution without breakage.

pick 2c8a903 · 09Extract Class

Extract Class is where refactoring stops being an editor operation and becomes design. The mechanical part — move some fields and methods to a new class, hold a reference to it, forward — is easy. The decision of where to cut is the whole job, and no tool can make it for you, because the cut is a claim about which responsibilities will change independently.

The formal handle is cohesion. If you draw a bipartite graph of methods and the fields they touch, a class with a single responsibility tends to be connected; a class with two tends to fall into two components joined by a few bridging methods. LCOM4 counts those components.[48] The lab's sixth experiment takes a ten-method invoice class with two genuine responsibilities and three bridging methods, enumerates all 511 two-way partitions, and picks the one that maximises mean within-part cohesion minus a penalty for cross-part coupling.

The result is a real improvement and a real bill. Cohesion rises from 0.47 to 0.80. Two fields — currency, customer — are touched from both sides, so they must now be passed as arguments or exposed through accessors, and 5 method pairs that previously communicated by sharing a field now communicate through an API. That API is a new thing to version, document, test and eventually deprecate.

This is the general shape of every decomposition. You are converting an implicit coupling — two methods happen to touch the same field — into an explicit one, and explicit couplings are visible, reviewable, and expensive. The trade is usually worth it. It is not free, and the metric will not tell you when it stops being worth it, because cohesion goes up monotonically as you keep splitting, all the way to the absurd limit of one method per class.

The serialisation risk deserves emphasis because it is the one that escapes the process. A class that is persisted, cached, or sent over a wire has a shape that other systems already hold copies of. Splitting it changes the shape. If the serialised form is derived automatically from the class — which is the default in most frameworks — then Extract Class is not a refactoring at all: it is a schema migration wearing a refactoring's clothes, and it needs the expand/contract discipline described in section 20.

pick 3d1b7f8 · 10Move Method

Move Method has the cleanest decision rule in the catalogue and one of the worst failure modes. The rule: if a method uses more of another object's data than its own, it belongs on the other object. Fowler calls the smell feature envy, and it is close to mechanically detectable. Tsantalis and Chatzigeorgiou's algorithm — the basis of JDeodorant's Move Method support — formalises exactly this, computing for each method the set of entities it accesses and proposing moves that reduce the distance between the method and the data it uses, subject to preconditions that preserve behaviour.[56][57]

The failure mode is that access counts are a proxy for a question about ownership, and proxies fail when the domain disagrees with the arithmetic. A tax calculation may read almost everything from an Address and still belong to Invoice, because it is the invoice that is legally responsible for the tax, and because moving it would make Address — a value type that is otherwise safe to share, cache and compare — depend on tax law.

Move Method also has a scale problem that Extract Method does not. Moving a method changes two classes' public surfaces at once, which means every caller compiles against a new arrangement. Within one repository that is a tool's job. Across a published API it is a breaking change, and the standard resolution — leave a forwarding method on the old class, deprecate it, remove it later — is the parallel-change pattern again.

A method migrates from one class to another; the source either forwards or drops it.
precondition
The target is reachable from every call site; the method's remaining references to the source are passable as arguments; no name collision on the target; visibility of everything the body touches is preserved at the new location.
at risk
Accessibility (a private field read becomes an accessor call, or forces a widening); dispatch, if the method was overridden; dependency direction between packages; and the serialised/reflective surface of both classes.

Accessibility is the subtle one and has an entire literature. Steimann and Thies showed that mainstream Java IDEs get accessibility wrong during moves and pull-ups, producing programs that compile but bind differently — a private member becomes package-private to make the move work, and suddenly a different overload is selected somewhere else.[58] Schäfer, Thies, Steimann and Tip's comprehensive treatment of naming and accessibility in Java refactoring is the reference work.[59] The recent turn is toward learned assistance: Batole and colleagues combine LLMs, IDE refactoring engines and semantic embeddings to propose Move Method candidates while delegating the actual transformation to the engine that knows the preconditions — which is the right division of labour.[60]

pick 4e6c210 · 11Rename

Rename is the refactoring everybody believes is trivial, and it is the one with the largest gap between the naive implementation and the correct one. The naive implementation is find-and-replace. JetBrains' survey of 1,183 users of IntelliJ-based IDEs found that Find and Replace remains a popular way to perform renames even among people who have a correct rename bound to a keystroke.[61]

The lab's second experiment builds a small module in which the identifier total appears as: the local being renamed, an attribute on an unrelated class, a module-level constant prefix, a word inside a string literal, a word inside a comment, and a same-named local in a different function. A word-boundary regular expression finds 11 matches. The binding actually occupies 4. Precision is 0.364.

The critical detail is the last line of the experiment's output: the incorrectly renamed module still compiles and still runs. It has silently changed a user-visible string, renamed a field on a class that has nothing to do with the change, and renamed a variable in an unrelated function. None of those produces an error. In a dynamically typed language the attribute rename is a runtime AttributeError waiting for the right code path; in a statically typed one it is a compile error only if the attribute is actually declared, which in Python it is not.

Doing it correctly requires resolving every identifier occurrence to the declaration it binds to, then rewriting exactly the occurrences that bind to the target — which is a name-resolution problem, i.e. a substantial fraction of a compiler front end. And that is only the easy half. The hard half is that renaming can change which declaration an occurrence binds to elsewhere: rename a local to a name that shadows a field, and every subsequent unqualified use of that field in the same scope now refers to your local. Schäfer, Ekman and de Moor's "sound and extensible renaming for Java" is the paper that laid out the problem properly and gave an algorithm that preserves binding structure rather than merely avoiding collisions.[62]

class Report {

The reflective hazard is the one no analysis can close. A field named total that is serialised to JSON by an annotation-driven mapper has its name in the wire format. Renaming it is an API change dressed as a rename, and the compiler will approve. Every mature system eventually grows a rule about this — an explicit @JsonProperty("total"), a protobuf field number, an explicit column mapping — which is precisely an act of decoupling the internal name from the observable one, so that Rename can go back to being a refactoring.

pick 5f9d38b · 12Encapsulate Field

Encapsulate Field is usually taught as an article of object-oriented faith, and taught badly. Getters and setters that do nothing but read and write a field are not encapsulation; they are a public field with extra syntax, and a fair amount of the industry's cynicism about the practice is earned.

The operational argument is better than the doctrinal one, and it is about where invariants can live. A public field has as many write sites as there are callers. An accessor has one. Everything you might ever want to do to a value on the way in or out — validate it, normalise it, make it lazy, log the change, notify observers, guard it with a lock, cache a derived quantity, deprecate it — requires exactly one place to put the code. Encapsulation is not about hiding data; it is about narrowing the set of places that can violate an invariant from n to one.

This is why Encapsulate Field is so often the first move in a longer campaign. You cannot change a field's representation, split its class, make it lazy, or move it to another object while fifty call sites read it directly. Encapsulating it does none of those things and enables all of them. Feathers's framing of a seam — a place where you can alter behaviour without editing in that place — is the same idea generalised: the accessor is a seam.[25]

Plate 06Encapsulate Field
the move
Direct reads and writes of a field are replaced by calls to an accessor pair; the field's visibility narrows.
precondition
Every access site is reachable and rewritable (including reflective and generated ones); the accessor's semantics match the field's exactly — no eager validation on a value that was previously permitted, no copy where an alias was assumed.
at risk
Aliasing (returning a mutable collection by reference vs by copy is a behaviour change either way you resolve it); atomicity, if a compound update was previously a single field write; performance in hot paths where the field was a struct member.
answers
Public fields; Temporary Field; the inability to perform any other refactoring on the field.
the tell
You want to add a log line, a null check, or a cache, and there is nowhere to put it.

The aliasing hazard is the one that bites. If order.items was a public List and callers mutated it in place, then a getter that returns the list preserves behaviour and preserves the problem; a getter that returns an unmodifiable view or a copy changes behaviour, correctly, and will break callers. There is no behaviour-preserving version of this refactoring that also achieves its purpose. Recognising that early — and doing the encapsulation as a deliberate, tested behaviour change rather than as a refactoring — is the difference between a two-hour task and a two-week mystery.

pick 6a2c47e · 13Simplify conditionals

The family here is large: Decompose Conditional, Consolidate Conditional Expression, Replace Nested Conditional with Guard Clauses, Introduce Special Case, Replace Conditional with Polymorphism, Replace Control Flag with a break. They share a purpose — reduce the amount of branching a reader must hold in their head at once — and a hazard, which is that branching is conserved.

The lab's fourth experiment takes one function in three shapes — nested conditionals, guard clauses, and table dispatch — and measures each. The predicates are identical in all three. Total cyclomatic complexity is 5, 5 and 11: flattening does not reduce it, and dispatch increases it, because the dispatch table introduces a classification function whose branches are the same branches plus the lookup. Maximum nesting depth goes 4 → 1 → 1. Mean complexity per function goes 5.0 → 5.0 → 1.57.

That last number is the whole point, and it is worth stating carefully, because "reduce complexity" is a phrase that hides the mechanism. Guard clauses do not reduce the amount of thinking; they reduce the amount of simultaneous thinking, by letting each precondition be discharged and forgotten before the next one is read. Dispatch goes further: it exports the branching into the structure of the module, so that a reader interested in one case need never see the others. In exchange it costs six extra functions and six extra decision points, plus the indirection of finding out which function actually runs.

Listing 3 — guard clauses discharge preconditions one at a time
# nested: every reader must hold four open conditions
def price(order):
    if order is not None:
        if order.items:
            if order.customer.active:
                if order.total > 0:
                    return charge(order)
                ...

# guarded: each condition is closed before the next is opened
def price(order):
    if order is None:            return None
    if not order.items:          return 0
    if not order.customer.active: return None
    if order.total <= 0:        return 0
    return charge(order)

Two hazards recur. The first is negation: flattening a nested conditional into guard clauses requires inverting every test, and inverting a test that involves <=, and, or a null-propagating comparison is where off-by-one and De Morgan errors live. Experiment E3's seeded slip S3 is exactly this — units <= 0 becomes units < 0 — and the seven-case example suite does not catch it.

The second is short-circuiting. Extracting a() and b() into two named booleans is a readability improvement that also evaluates b() unconditionally. If b() is a null-guarded dereference, the extraction is a crash; if it is a database call, it is a performance regression; if it is idempotent and cheap, it is genuinely nothing. The refactoring's safety depends on a property of a function you did not look at.

pick 7b4f9d1 · 14Remove duplication — and when not to

Duplication is the smell with the strongest reputation and the weakest theory. "Don't repeat yourself" is stated as a principle about knowledge — every piece of knowledge should have a single authoritative representation[63] — and applied as a principle about text, which is not the same thing at all. Two functions with identical bodies that encode two independent business rules are not duplication; they are a coincidence, and unifying them creates a coupling that the domain does not have.

The practical heuristic is Beck's Rule of Three: duplicate once without comment, and refactor on the third occurrence — by which point you have seen enough variation to know what actually varies. Sandi Metz's formulation of the failure mode is the one that stuck in the industry's memory: duplication is far cheaper than the wrong abstraction.[64] The mechanism is worth spelling out, because it is not obvious.

When three copies diverge, each divergence costs you one edit in one place. When three callers share an abstraction and one of them needs to differ, you add a parameter. The second divergence adds another. Within a few cycles the shared function has four boolean flags, a strategy object, and a comment explaining which combinations are valid. Every caller now depends on code paths it never executes, every change must be validated against all callers, and the function is harder to delete than the three copies would have been — because deleting a copy is a local decision and deleting a shared abstraction is a negotiation.

Experiment E3's seed S9 models the opposite failure: three sites unified into a shared helper, and the shared constant subsequently changed from 0.9 to 0.91 by someone fixing one caller's requirement. The example suite catches that one — it is a numeric change on a common path — but the general risk is that unification converts three independent, locally-reviewable decisions into one decision with three stakeholders who are not in the room.

The industrial tooling here is mature and worth using: clone detection that works on token streams or ASTs rather than lines, so that renamed-but-identical fragments are found. JDeodorant's clone refactoring support pairs detection with the actual transformation, which is the part usually missing.[65] But detection answers "are these fragments similar", and the question you need answered is "will these fragments change together", which only the version history can tell you — and Palomba's history-based smell detection is the closest thing the field has to an answer to it.[42]

pick 8c5e0a4 · 15Replace inheritance with delegation

Inheritance is the only relationship in most mainstream languages that cannot be renegotiated without editing every participant. It couples a subclass to the whole of the superclass's surface, including the parts the superclass author never intended to publish, and it does so transitively and permanently.

The standard demonstration is java.util.Stack, which extends Vector and therefore inherits indexed access. A Stack is supposed to be a LIFO discipline; because of the inheritance, callers can insert at position three. The class cannot be fixed without breaking compatibility, so it has shipped that way since 1996 and is now primarily useful as a teaching aid — which is the use Bloch puts it to in the canonical argument for preferring composition.[66] Fowler's smell for this is refused bequest: the subclass does not want most of what it inherited.

Delegation costs forwarding methods — real, tedious boilerplate — and buys the ability to change your mind. The delegate can be swapped, wrapped, mocked, made lazy, or replaced with a different implementation, none of which is possible with a superclass. Composition also composes: an object can hold three delegates, and cannot have three superclasses in most languages.

Plate 10Replace Inheritance with Delegation
the move
A subclass stops extending its superclass and holds an instance of it instead, forwarding the methods it actually needs.
precondition
No caller depends on the subtype relation — no instanceof, no assignment to a variable of the supertype, no collection of supertype elements containing instances; no protected member is used; no overridden method is invoked from within the superclass (which delegation cannot reproduce).
at risk
Substitutability itself. Every instanceof, cast, generic bound, and serialisation of the supertype breaks. Self-calls inside the superclass that used to dispatch to the override now do not — this is the "broken callback" or self-use problem, and it is invisible until runtime.
answers
Refused Bequest; inheritance used for code reuse rather than for substitutability in the behavioural sense.[67]
the tell
A subclass overrides a method to throw UnsupportedOperationException.

The self-use hazard is the one that makes this refactoring genuinely dangerous rather than merely tedious. If Vector.addAll is implemented by calling this.add in a loop, then a subclass that overrides add to count elements will count correctly under inheritance and incorrectly under delegation, because the delegate's internal call goes to its own add, not to yours. There is no way to read the subclass and discover this. You have to read the superclass's implementation, which is exactly the thing inheritance promised you would not have to do.

Bavota and colleagues found empirically what this argument predicts: inheritance-related refactorings are among the most likely to induce bugs.[68] That is a good reason to do them carefully. It is not a reason to avoid them, since the alternative is leaving the coupling in place — but it is a strong reason to do them with characterisation tests over the subclass's full surface, not just the methods you meant to keep.

pick 9d7a1c6 · 16The harness, and what it actually holds

Every practical account of refactoring says the same thing: you need tests. Fowler is explicit that refactoring without a self-checking test suite is not refactoring but hoping.[3] Beck's red-green-refactor cycle makes the harness a precondition of the practice rather than an accompaniment.[24] This is correct advice and it is routinely misapplied, because "you need tests" gets operationalised as "you need coverage", and coverage of the code you are changing is not coverage of the behaviour you are preserving.

The lab's third experiment makes the distinction sharp. Take a small pricing function with tiered rates, a bulk discount and a membership discount. Seed twelve variants, each one a plausible slip during a specific named refactoring: a boundary that drifts during Extract Method, an operand order swapped during Extract Variable, an inverted guard, a lookup table with the wrong default, a reordering, a double rounding after an inline, a dropped flag after Encapsulate Field, a threshold changed during Extract Class, a shared constant that drifts after unification, transposed operands after a move, a silent fallback that becomes an exception, and a folded zero case.

Then check them with three oracles. An example suite of seven cases, written the way a competent engineer would write it, achieving 100% statement coverage of the baseline. Twenty thousand uniform random draws. And seven metamorphic properties — relations that hold of the baseline by construction, such as membership never increases the price and an unknown band prices as the lowest band.

The example suite catches 3 of twelve. It has full statement coverage. Every line of the baseline executes; the suite simply does not distinguish the baseline from most of its neighbours, because the cases were chosen to demonstrate the function's intent rather than to pin its boundaries. Random input does better — 6 of twelve — because volume finds boundary values that a human would not enumerate. The metamorphic properties catch all twelve, because they encode relations that any correct implementation must satisfy, and a slip is precisely a violation of such a relation.

What this means operationally

If you are about to refactor, the question is not "is this code covered". It is "would my suite distinguish this code from a version of it that is subtly wrong". Mutation testing answers that question directly and is the only coverage-adjacent measure that does. If you cannot run a mutation tool, the cheap approximation is: pick two boundary values per predicate and one relation per invariant, and check that removing any one of them makes a test fail.

Refactoring breaks tests, and that is data

There is a second, less obvious harness problem: the tests themselves are code, and refactoring the production code frequently breaks them. Kashiwa and colleagues measured this directly and found that a non-trivial fraction of refactoring operations break existing tests — not because behaviour changed but because the tests were coupled to structure.[69] Rachatasumrit and Kim found that refactoring changes are often not covered by the existing regression suite at all, and that the tests which do exist are frequently the ones most affected.[70]

A test that breaks when you rename a private method was testing the private method. That is a signal about the test, not the refactoring — but it is a signal that arrives at exactly the moment when you are least inclined to act on it, because you are mid-refactor and the fastest path is to update the test to match. Doing so converts your harness into a mirror of the implementation, which is the state in which it stops being able to detect anything.

The disciplined alternative is to notice which tests broke and ask whether each one was asserting behaviour or structure, then delete the structural ones. That is unpopular because deleting tests feels like reducing safety. It is the opposite: a suite that fails on every restructuring is a suite that will be routinely updated without being read, which is the same as not having one.

pick ae3b820 · 17Code without tests

The catalogue assumes a harness. Most code does not have one. Michael Feathers's definition — legacy code is simply code without tests — is deliberately blunt and remains the most useful framing available, because it converts a vague complaint about inherited code into a specific problem with known moves.[25]

The bind is circular. You cannot safely refactor without tests; you often cannot write tests without refactoring, because the code under test constructs its own collaborators, reads global configuration, or does I/O in a constructor. Feathers's resolution is the seam: a place where you can change behaviour without editing at that place. An interface is a seam. A subclass override is a seam. A linker or classpath substitution is a seam. A function pointer, a dependency-injected constructor argument, a preprocessor macro — all seams. Finding one lets you get a test harness around the code with a minimal, low-risk edit, after which the real refactoring becomes possible.

Characterisation tests

The second technique is the characterisation test, and it inverts the normal purpose of testing. You are not asserting what the code should do; you do not know that, and finding out may take weeks. You are recording what it currently does, so that you can detect change. Write a test that calls the code, observe the output, and assert that output — including the parts that look wrong. Bugs preserved on purpose are still bugs, but they are bugs you have now pinned in place, which means you can refactor around them and fix them separately, as a visible behaviour change with its own review.

Listing 4 — a characterisation test asserts the present, not the ideal
def test_legacy_rounding_is_pinned():
    # NOT a specification. A record of what ships today.
    # The half-cent rounds down; finance says it should round
    # half-up. Ticket FIN-4412. Do not "fix" while refactoring.
    assert legacy_price(band="b", units=7, member=True) == 5.42

Approval testing generalises this: capture a large, structured output — a rendered report, a serialised object graph, an entire response — into a file, review it once, and thereafter diff against it. The technique scales to codebases where writing individual assertions would take longer than the refactoring. It also produces a specific failure mode worth naming: an approved file that nobody has ever read is a rubber stamp, and re-approving a diff without reading it is how behaviour changes get laundered into the baseline.

The Mikado method

The third technique addresses the structural problem: in a tangled codebase, the change you want to make requires another change, which requires another. The Mikado method's protocol is to attempt the change naively, observe what breaks, revert, record the prerequisite as a node on a graph, and recurse — building a dependency tree of prerequisites from the leaves inward, then executing it bottom-up with the codebase working at every step.[71] The counter-intuitive instruction is the revert. Most engineers, on discovering a prerequisite, start fixing it, and end up three levels deep with nothing compiling and no way back. The method's value is entirely in the discipline of throwing away the exploratory work and keeping only the knowledge.

pick bf1d675 · 18The engines have bugs

The advice to prefer automated refactoring over manual editing is sound and slightly overstated, because refactoring engines are large pieces of software that implement approximations to undecidable properties, and they get it wrong.

Daniel, Dig, Garcia and Marinov opened this line of work by generating Java programs automatically and applying refactorings to them, finding twenty-one previously unknown bugs in Eclipse and NetBeans within hours.[72] Soares, Gheyi and Massoni scaled the approach: 153,444 generated transformations across twenty-nine refactorings in Eclipse JDT, NetBeans and the JastAdd refactoring tools, using a behavioural oracle, yielding 57 bugs that produced compilation errors and 63 that produced behavioural changes — that is, sixty-three ways in which a refactoring engine silently changed what a program did.[73] Gligoric and colleagues took a complementary approach, applying refactorings systematically at many points in real open-source projects rather than generated ones, and reported 77 new bugs for Eclipse's Java engine and 43 for its C engine.[74]

Mongiovi and colleagues attacked the opposite failure: overly strong preconditions, where the engine refuses a transformation that would have been safe. These are invisible as defects — nothing breaks — but they are the reason engineers conclude the tool "doesn't work on our code" and go back to editing by hand.[75] Wang, Xu, Zhang, Tsantalis and Tan's 2024 study is the first systematic characterisation of refactoring engine bugs across Eclipse, IntelliJ IDEA and NetBeans, classifying them by refactoring type, symptom, root cause and trigger, and finding 130 new bugs in current versions in the process.[76]

What follows from this

Not "don't use the tools" — the tools are still far more reliable than hand-editing, and the same studies that find engine bugs find the engines broadly trustworthy on ordinary input. What follows is that the harness protects you from the tool as well as from yourself, and that a refactoring applied by an IDE deserves the same test run as one applied by hand. The common practice of skipping CI on a "pure refactoring" commit has this exactly backwards.

Why people don't use them anyway

Murphy-Hill, Parnin and Black's study — four datasets covering more than 13,000 developers, 240,000 tool-assisted refactorings and 2,500 developer hours — established several findings that the field has been absorbing ever since.[77] Refactoring is rarely announced in commit messages, which invalidates the methodology of a good deal of earlier mining research. It is usually interspersed with other changes rather than performed in dedicated sessions. And a large majority of refactorings are performed manually even by developers who have the tools available. Their earlier work argued that the tools were not fit for the purpose developers actually had: they were designed around single, named, complete operations, and the work consists of many small partial ones.[78] Xing and Stroulia had reached a compatible conclusion from the other direction, reconstructing Eclipse's own evolution history and finding that a large share of the structural changes developers actually made had no counterpart in any tool's menu.[79]

Vakilian and colleagues went further, observing developers directly and cataloguing use, disuse and misuse — including the finding that developers often invoke a refactoring, dislike the result, undo it, and do it by hand.[80] Negara and colleagues compared manual and automated refactorings from continuous IDE recordings and found that manual ones substantially outnumber automated ones even for refactorings the IDE supports.[81] JetBrains' own survey of 1,183 users found that developers frequently want to know more about what a refactoring feature does but lack a route to that knowledge, and that Find and Replace remains a common rename mechanism.[61]

The tactical distinction Murphy-Hill drew is the one worth carrying: floss refactoring, done continuously as part of other work to keep the code healthy, versus root canal refactoring, done as a dedicated remedial project.[77] The evidence and the economics both favour floss. The next section explains why.

pick c0e8f31 · 19Incremental improvement is a scheduling claim

"Refactor incrementally" is usually presented as a matter of temperament — small steps, keep it green, don't be a hero. It is better understood as a claim about scheduling, and it has an arithmetic. Beck makes the scheduling explicit — the question is not whether to tidy but whether to tidy before, after, or never, and each answer has a different option value.[82]

The lab's seventh experiment models a repository of 4,000 files with mainline churn of 120 files per day. A refactoring touches 300 of them. Two strategies: hold the work on a branch for d days and merge once, or slice it into d pieces and merge each as it is finished. The total work is identical; only the schedule differs.

The long-lived branch accumulates conflicts because its exposure window is the whole of its life: every file it touched that anyone else also touched, at any point, is a conflict. Slicing the work does not reduce the number of files touched; it reduces each slice's exposure window to one merge interval. That is why the incremental line is flat and the big-bang line climbs. The ratio reaches 34× at ninety days.

The model is crude in ways that all favour the branch: it ignores that conflicts in refactored code are unusually hard to resolve (because the resolver must understand both the refactoring and the change), and that a long-lived branch also blocks everyone else's refactoring of the same files. Mahmoudi, Nadi and Tsantalis measured the first effect directly and found that refactorings are involved in a disproportionate share of merge conflicts, and that the conflicts they cause are harder than average.[83] The continuous-delivery literature has been making the same argument from the other direction for fifteen years: long-lived branches are a form of inventory, and inventory hides problems.[84][85]

The debt arithmetic

The eighth experiment asks the complementary question: given that the work must happen, when? It simulates 200 changes across twelve modules, where the cost of a change scales with the accumulated debt in the module it lands in, under four policies — never refactor; repay a little in whatever module you touch (the Boy Scout Rule, as Uncle Bob named it: leave the campground cleaner than you found it[86]); a big clean-up every forty changes; and one heroic rewrite at the midpoint.

Two features of this toy are worth taking seriously. The first is the crossover: continuous repayment is more expensive for the first 103 changes. Any team measured on a quarterly horizon will observe this and conclude that refactoring is not paying. They will be right about the measurement and wrong about the policy.

The second is that the big-bang policies lose to never refactoring at all over this horizon. That is a consequence of the premium in the model — a large remedial project costs more per unit of debt repaid than the same repayment spread across the work — and the premium is real. It is the merge cost from experiment E7, plus the cost of re-learning code you are not currently changing, plus the risk of a large change landing at once, plus the fact that a remedial project fixes the modules that were worst rather than the modules you are about to touch.

Kim, Zimmermann and Nagappan's field study at Microsoft is the best industrial evidence on the other side, and it is more nuanced than either camp usually admits. Their survey found that practitioners' working definition of refactoring is not confined to semantics-preserving transformation, and that developers perceive refactoring as carrying substantial cost and risk. But their quantitative analysis of a multi-year, centrally-organised refactoring effort on Windows found measurable benefit: significant reductions in inter-module dependencies and in post-release defects in the refactored modules.[87][88] So a large deliberate campaign can pay. It pays when it is aimed at a specific structural problem with a specific measurable target, and it is not a substitute for the continuous kind.

pick d29c4b7 · 20Parallel change

Some restructurings cannot be done atomically. The callers are in other repositories, or other companies, or running in production against a version of the code you are about to delete. The general solution is the same one every time, and it has been rediscovered and renamed at every scale. Sato's name for it — expand, migrate, contract — is the one that travels.[89]

Expand. Add the new thing beside the old one. Both work. Nothing has moved. This commit is trivially safe and trivially revertible.

Migrate. Move callers across, at whatever rate their owners can manage. Each migration is independently reviewable and revertible. Instrument the old path so you can see who is still on it — this is the step people skip, and it is what turns "we think everyone has migrated" into "we know".

Contract. Delete the old thing. This is the step that realises the value, and the step organisations reliably fail to complete. A migration that stops at 97% has bought nothing: the old path still exists, still needs tests, still receives bug reports, and the codebase now contains two ways to do the thing instead of one — which is strictly worse than where you started.

At schema scale this is Ambler and Sadalage's database refactoring, and their book is still the most complete treatment: add the new column, write to both, backfill, migrate readers, stop writing the old, drop it — with a transition period during which both schemas are supported and the application is version-tolerant.[90] At module scale it is branch by abstraction: introduce an abstraction over the thing you want to replace, move callers to the abstraction, build the new implementation behind it, flip, delete.[91] At system scale it is the strangler fig: put a facade in front of the legacy system, route features to a new implementation one at a time, and let the old system shrink until it can be switched off.[92] At API scale it is //go:fix inline and Rust's edition mechanism.[12][30]

These are usually taught as four separate patterns. They are one pattern at four scales, and the invariant they share is that every intermediate state is shippable. That is what makes them safe, and it is also what makes them slow, and the slowness is the reason the contract step gets dropped.

pick e4a70d9 · 21Large-scale change

Beyond a certain size, refactoring stops being an editing activity and becomes a pipeline. The threshold is roughly where the change is too large to review as a unit and too large to land atomically, which in practice means a few hundred files.

Google's account is the most fully documented. ClangMR combined the Clang compiler frontend with MapReduce: compile the entire repository with a modified compiler that retains ASTs, run AST matchers across the resulting corpus in parallel, and emit edits. The published example migrated more than 35,000 call sites of an old string-splitting API to a new one.[93] The surrounding machinery — a monorepo, a global build graph, an automated change-management system that shards edits by ownership and routes each shard to its owner — is what makes the transformation deliverable rather than merely computable.[94][6] The organising principle in Software Engineering at Google is that the one-time cost of a migration must be amortised by the ongoing cost of not migrating, and that this calculation only comes out positive if the tooling makes migrations cheap enough to do routinely.[6]

The Linux kernel solved the same problem differently and earlier. Coccinelle's semantic patches let a maintainer express a transformation in a notation that looks like a unified diff with metavariables, matched against the C abstract syntax rather than against text — which is what makes it work across the kernel's thicket of macros and configurations.[95] Padioleau and colleagues coined the term collateral evolution for the phenomenon it addresses: a change to an internal kernel API forces mechanical changes in hundreds of drivers, none of which the API author can review individually. A decade of production use in the kernel followed.[96]

The JavaScript ecosystem's codemod culture came from the same pressure at a different company. jscodeshift wraps a JavaScript parser with a jQuery-like traversal API, and React's breaking changes have shipped with codemods since the mid-2010s, which is why an ecosystem with no monorepo and no central authority can move.[97] Instagram's LibCST solved a Python-specific version of the problem: Python's standard ast module discards comments and formatting, so a round-trip through it destroys the file. LibCST preserves a lossless concrete syntax tree, which is the difference between a codemod that can be merged and one that produces a 50,000-line whitespace diff.[98]

The reason this class of tooling exists at all is a finding of Dig and Johnson's: when they classified the breaking changes across five widely-used frameworks and libraries, the large majority turned out to be refactorings rather than genuine semantic redesigns.[99] Kim, Cai and Kim later quantified the other side of it, showing that API-level refactorings cluster sharply around releases and correlate with elevated bug-fix activity.[100] Breaking changes are, mostly, renames and moves that crossed an ownership boundary — which is precisely the case a codemod can discharge and a human cannot afford to.

Python's own 2-to-3 migration is the field's most instructive failure. 2to3 was a competent tool; the transformation was well-understood; and the migration still took over a decade, because the transformation was not the bottleneck. The bottleneck was that every library had to migrate before its dependents could, that the two versions could not coexist in one process, and that there was no forcing function short of end-of-life.[101] Contrast Rust's editions, where the language is allowed to make breaking changes precisely because each edition ships with an automated migration in cargo fix and crates of different editions interoperate in one binary.[30] The lesson is not about tooling quality. It is that a migration's cost is dominated by coordination, and the only way to reduce coordination cost is to make the old and new coexist.

pick f61b8e0 · 22The same problem in other materials

Everything so far has been about source code, which is the material with the best tooling and the most forgiving failure modes. The identical problem appears wherever a structure has both an internal shape and an external contract — and in most other materials the observables are harder to enumerate and the revert is not free.

Databases

A schema has a shape and a contract, and the contract's holders are every application, report, ETL job and analyst query in the organisation. Splitting a table is Extract Class with a migration; renaming a column is Rename with no compiler to check it; adding a not-null constraint is a behaviour change that will be discovered by the first insert that fails at 3 a.m. Ambler and Sadalage catalogued the moves — split table, merge column, introduce surrogate key, replace one-to-many with association table — each with the transition-period mechanics that make it survivable.[90] The invariant across all of them is the parallel-change discipline of section 20, because there is no atomic option: the database is shared, stateful, and cannot be reverted by git revert.

Infrastructure as code

Terraform's moved block exists for exactly one reason: renaming a resource in configuration would otherwise be interpreted as destroying one resource and creating another, which for a database instance is a materially different outcome from a rename.[102] The block is a refactoring primitive in the strict sense — it asserts that the new address and the old address denote the same real-world object, which is precisely a claim of behaviour preservation, and one that no static analysis could infer. Its existence is an admission that in infrastructure the mapping from text to observable is mediated by state, so refactoring requires an explicit statement of identity.

Embedded and safety-critical code

In a MISRA C or DO-178C context, the observable set is enormous: timing, stack depth, memory layout, interrupt latency, and the traceability links between requirements, code and tests. A refactoring that splits a function may change stack usage, which may violate a worst-case analysis; it certainly invalidates the structural coverage evidence for the original function and requires it to be regenerated. Refactoring is not prohibited in these domains, but the cost of re-establishing the evidence is high enough that it must be justified explicitly rather than done opportunistically — which is a rational response to a genuinely larger observable set, not conservatism.

Configuration and preprocessor thickets

C code under #ifdef is a family of programs, not a program. A transformation must preserve behaviour for every configuration, including combinations nobody has ever built. Medeiros and colleagues studied refactoring in this setting — "the #ifdef hell" — and found that discipline in how directives are used strongly predicts whether tools can handle the code at all.[103] The same structure appears in feature-flagged application code, where the flag combinations form a configuration space that the test suite samples rather than covers.

Concurrent code

This is the case where the standard tooling is most quietly unsafe. Automated refactorings in mainstream Java IDEs generally make no special provision for concurrency, so a transformation that is behaviour-preserving under sequential reasoning may permit new interleavings. Extracting a method from inside a synchronised block, or introducing a local variable that turns one read of a shared field into two, changes the set of executions the program admits without changing any test's result. The behaviour is preserved in every execution you observed and not in the ones you did not.

Data and ML pipelines

A pipeline's observable is the distribution of its output, not any single value. Refactoring a feature-engineering step can preserve the code's semantics exactly and still shift a downstream model's predictions, because floating-point associativity changed when you reordered a sum, or because a previously implicit ordering became explicit. The harness that works here is not unit tests but distributional comparison against a held-out reference run — a characterisation test whose assertion is statistical.

The generalisation

The difficulty of refactoring in any material is proportional to the size of the observable set and inversely proportional to the cost of reverting. Source code in a version-controlled repository with a fast test suite is the easiest case anyone has ever had. Every intuition calibrated there understates the cost everywhere else.

pick 0b93f52 · 23Does it work? The evidence, honestly

The practitioner literature treats refactoring's benefits as self-evident. The empirical literature does not, and the gap is worth understanding rather than papering over.

What the evidence supports

That code quality is associated with speed and defect rates, strongly. Tornhill and Borg's thirty-nine-codebase study is the clearest recent statement: fifteen times more defects, 124% more development time per issue, and nine times worse tail latency in low-quality code.[38] That technical debt consumes a large, measurable fraction of developer time — roughly a quarter by self-report in Besker's longitudinal studies.[36][37] That a large, deliberate, targeted refactoring campaign can produce measurable structural and defect improvements, as Kim and colleagues found for Windows.[87] That refactoring improves program comprehension for readers, which Sellitto and colleagues measured directly.[104] Moser and colleagues' agile-team case study is the small-scale analogue, tracking quality and productivity across iterations with and without deliberate refactoring effort.[105]

What the evidence complicates

The link from individual refactorings to quality outcomes is much weaker than the folklore. Cedrim and colleagues tracked twenty-three projects longitudinally and found that fewer than 10% of refactorings actually removed a code smell, while more than 30% introduced new ones.[106] Bavota and colleagues found that a substantial share of refactorings induce bugs, with inheritance-related ones the worst offenders.[68] Their later experimental work found the relationship between quality metrics and refactoring activity to be weaker and messier than the metric-driven recommendation literature assumes.[107] Chávez and colleagues' multi-project study found the picture attribute-dependent rather than uniformly good: root-canal refactoring tended to improve internal quality, floss refactoring — the kind done in passing, which is most of it — frequently did not.[108] Szőke and colleagues found that only large, systematic, bulk refactoring produced measurable quality improvement — small scattered fixes did not.[109] Al Dallal and Abdin's systematic review of the whole question concluded that effects vary substantially by attribute and by refactoring type, with no uniform positive result.[110]

Why developers actually refactor

Not, it turns out, to remove smells. Silva, Tsantalis and Valente asked GitHub contributors directly, immediately after their commits, and found that refactoring is overwhelmingly driven by the need to accommodate a change that is coming — to make the next feature possible — rather than by an aesthetic or metric-driven assessment of the existing code.[111] Pantiuchina and colleagues confirmed this at scale in a mining study.[112] Vassallo and colleagues' large-scale exploration of refactoring activity in open-source projects found the same opportunism in the timing: refactoring clusters around feature work and release pressure, not around quality reviews.[113] Their later work on why refactorings are rejected in code review found reviewers' most common objections to be that the change was not worth the risk, or was out of scope for the pull request — which is a review culture responding rationally to the tangling problem.[114] Kim's Microsoft survey found the same: practitioners associate refactoring with substantial cost and risk, and do not use a semantics-preserving definition.[87]

Reconciling this

The apparent contradiction — code quality clearly matters, individual refactorings clearly do not reliably improve metrics — dissolves once you stop treating metrics as the objective. Refactoring is not a process for maximising a cohesion score. It is a process for making a specific anticipated change cheap. Cedrim's finding that most refactorings do not remove smells is not evidence that refactoring fails; it is evidence that smell removal was never what developers were doing.

Which suggests the honest evaluation question. Not did the metrics improve but: did the change we were preparing for become cheaper, and did we ship it. That is harder to measure and it is the thing the work was for. It also implies a discipline that most teams skip — name the change you are enabling before you start, so that afterwards you can tell whether you enabled it.

pick 1c47a86 · 24Agents at the keyboard

The most recent development is that a large share of refactoring is now performed by systems that cannot check their own preconditions.

Horikawa and colleagues conducted the first large-scale study of agentic refactoring, analysing 15,451 refactoring instances across 12,256 pull requests and 14,998 commits in 1,613 open-source Java projects, detected with RefactoringMiner.[115] The findings are specific enough to plan around.

Refactoring is common in agent output: 26.1% of agentic commits explicitly target it, and 53.9% of detected refactoring instances occur in commits whose messages say nothing about refactoring at all — that is, tangled with feature work, which is exactly the pattern Murphy-Hill observed in humans a decade and a half earlier.[115][77] The distribution of types skews low: agents perform more low-level, block-scoped edits than humans (35.8% vs 24.4%) and fewer high-level signature changes (43.0% vs 54.9%), with Change Variable Type, Rename Parameter and Rename Variable alone accounting for 30.7% of all agentic refactoring instances.[115]

The stated motivations skew even harder. Maintainability (52.5%) and readability (28.1%) account for over 80% of agentic refactoring, against 11.7% and 25.7% for the human baseline from Kim's Microsoft study.[115][87] Meanwhile the motivations that dominate human refactoring — duplication (13.7% human, 1.1% agentic) and reuse (12.9% vs 4.6%) — are nearly absent. Agents are doing tidying. Humans are doing design.

And the measured effect on quality is small. Class-level lines of code drop by a median of 15.25 and weighted methods per class by 2.07 for medium-level refactorings, both statistically significant with negligible effect sizes; the count of detected design and implementation smells does not move at all (median Δ = 0.00).[115] Structural decomposition — Extract Subclass, Split Class — produces the real gains, and it is the category agents perform least.

The reviewing problem

The finding with the sharpest operational edge is the tangling one. A reviewer facing a pull request that implements a feature and performs thirty renames must verify a behaviour change and a behaviour preservation in the same diff. Humans are poor at this; the failure mode is to check the feature and skim the renames. Watanabe and colleagues found that 45.1% of agentic pull requests required post-review fixes, and Sergeyuk's survey found that 21.9% of developers avoid AI assistance specifically for refactoring tasks, citing the need for behaviour to remain unchanged.[116][117]

The constructive reading is that the division of labour is becoming clearer, and it recapitulates the argument of section 3. A language model is good at proposing transformations and bad at proving preconditions. A refactoring engine is the reverse. Batole and colleagues' Move Method work takes exactly this shape: use embeddings and a model to generate and rank candidate moves, then hand the actual transformation to the IDE's engine, which knows about accessibility and dispatch and will refuse an unsound move.[60] Dilhara and colleagues' fusion of LLMs with transformation-by-example follows the same pattern.[118] Liu and colleagues' evaluation of general-purpose LLMs on real refactorings found them substantially better at identifying opportunities than at producing correct transformations.[119] Cordeiro, Noei and Zou's assessment reached a compatible conclusion.[120]

Which is the same conclusion the field reached in 1997 with the Refactoring Browser, in a new register: the value of a refactoring tool is that it refuses. A system that will cheerfully apply any transformation you describe is not a refactoring tool; it is an editor with opinions. Put the proposal-generation and the precondition-checking in different components, and let the checker win.

Reading the results honestly

E7 and E8 are simulations with invented parameters, and their absolute numbers mean nothing. What they establish is a shape: conflict exposure is linear in branch lifetime and flat under continuous merging, and a compounding cost function makes continuous small repayment beat periodic large repayment even when the periodic policy repays more total debt. Both shapes are robust to the parameters; you can change the churn rate or the interest coefficient over a wide range and the ordering does not flip.

E1 through E6 are not simulations. They are enumerations and measurements over concrete programs, and their numbers are exact for those programs. They do not generalise to a claim about how often real Extract Methods are wrong; they establish that the failure mode exists, is invisible in the diff, and is missed by the kind of test suite people actually write.

exec · make verifyThe claim, restated

The Go team could have shipped the slices.Clone moderniser. The nil-versus-empty distinction is genuinely obscure; the vast majority of affected programs would never have noticed; and the transformation makes code better in every case where it applies. They pulled it because somebody's program might have been able to tell.

That is the standard, and it is a demanding one, and it is worth defending against the two directions in which it usually erodes. The first erosion is the one that says the distinction does not matter — that a change this obscure cannot really count as a behaviour change. That is a claim about your observers, and you do not have the list. The second erosion is the one that says, since preservation cannot be guaranteed, the discipline is theatre. That is a counsel of despair that ends with a codebase nobody dares touch, which is Lehman's second law with the brakes off.

The workable position is in between and it is unglamorous. Name the observables you are holding fixed, before you start. Prefer the moves whose preconditions someone else has already worked out, and use the tools that check them — not because the tools are infallible but because they refuse, and refusing is the valuable behaviour. Build a harness that would notice if you were wrong, which means boundary values and invariants rather than coverage. Keep the steps small enough that a reviewer can verify preservation by reading, and separate enough that a feature and a refactoring are never in the same diff. Merge continuously, because the only variable you actually control is how long the work sits away from the trunk. And do the work where the change is, in the module you are already touching, on the day you are touching it — because the alternative is a remedial project, and remedial projects lose to doing nothing.

Then, when the commit lands and someone asks what it changed, you get to say the thing the whole practice exists to make true. Nothing observable. Everything else.
