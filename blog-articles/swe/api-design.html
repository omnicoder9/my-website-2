The promise you cannot take back

Here is a way to tell whether a piece of software has an API. Change something inside it. If nobody outside has to be told, it does not have an API — it has an implementation. The moment a change to the inside forces a conversation with the outside, an interface exists, whether or not anyone designed one.

That definition is deliberately uncomfortable, because it locates the API not in the code but in the obligation. David Parnas made the point in 1972, in the paper that gave us information hiding: the value of a module boundary is measured by what it lets you change without telling anyone, and the design question is which decisions to hide behind it.[1] Everything this article covers — resource modelling, contracts, versioning, pagination, filtering, sorting, authentication, authorization, idempotency, errors, rate limiting, compatibility, documentation — is an answer to a narrower version of Parnas's question: which promises are we making, and what will it cost us to keep them?

The cost is not hypothetical. Once an interface has users, its behaviour stops being yours. Hyrum Wright's formulation is the one every platform team eventually quotes from memory: with a sufficient number of users of an API, it does not matter what you promise in the contract, because all observable behaviours of your system will be depended on by somebody.[2,3] The consequence is not that documentation is pointless. It is that your documented surface and your effective surface are different objects, and design is the practice of dragging the second one closer to the first.

This has a practical corollary that shapes the rest of the article. A well-designed API is not one that is elegant on the day it ships. It is one that can absorb five years of product change without forcing its callers to rewrite. Elegance that cannot survive a new required field, a new authorization dimension, a hundred-fold growth in collection size, or a regulator's demand for an audit trail is not elegance; it is a first draft that got lucky.

Three claims run through everything below, and it is worth stating them plainly before the detail arrives.

First: an API is a distributed-systems artefact, not a function call with punctuation. The 1994 Sun Labs note on distributed computing argued that the attempt to make remote calls look local is a category error, because latency, partial failure and concurrency are not implementation details you can paper over.[4] Three decades of RPC frameworks have not repealed it. Idempotency keys exist because of partial failure. Pagination exists because of latency and memory. Optimistic concurrency exists because two callers can write at once. Every one of those is a promise about failure, and failure is where interfaces are actually tested.

Second: the interface style matters far less than practitioners argue. REST, GraphQL, gRPC and event streams differ in who gets to decide the shape of a response and in what the wire looks like. They do not differ in whether you must decide how a client pages a large collection, what happens when a request is retried, how a caller learns that it is not allowed to see a field, or how you remove something. A team that has thought those through will ship a good gRPC API and a good GraphQL API. A team that has not will ship a bad one in every style available.

Third: the hard part is removal, not addition. Adding is easy and reversible in the sense that nobody depended on the thing yesterday. Removing is a migration project you are running on behalf of strangers, on their schedule, with no authority over their release calendar. Design choices should therefore be judged mainly by how cheaply they can be undone. That is the lens this article applies to every subtopic.

paths: /history

Fifty-eight years of the same argument

The term is older than the web by three decades. "Application program interface" appears in a 1968 AFIPS conference paper by Ira Cotton and Frank Greatorex on remote computer graphics, where it names a stable set of Fortran subroutine calls that insulates a graphics program from the idiosyncrasies of a particular display device — so that the display, or the computer, could be replaced without rewriting the application.[5] The first API in the literature was, in other words, invented to solve a compatibility problem. Nothing since has changed the assignment.

The line from there runs through remote procedure call, which Birrell and Nelson made practical in 1984 by working out stub generation, binding and the semantics of a call whose reply may be lost.[6] It runs through the reaction to RPC's transparency ambitions, articulated in the Sun Labs note, and then through the enterprise middleware era — CORBA's IDL and object references,[7] then XML-RPC's deliberately minimal alternative,[8] then SOAP and the WS-* stack, which specified almost everything and, in doing so, made the specification the integration cost.[9]

Roy Fielding's 2000 dissertation is the pivot. It is frequently cited and rarely read; what it actually does is derive an architectural style by adding constraints to a null style and observing what each constraint buys — client-server, statelessness, cacheability, uniform interface, layered system, code on demand — and it explains the design of HTTP and URIs as the result.[10,11] The constraint that generated the most argument, and the least compliance, is hypermedia as the engine of application state; Fielding said so explicitly in 2008, observing that an interface where clients construct URLs from out-of-band knowledge is not REST regardless of what its documentation claims.[12] Martin Fowler's write-up of the Richardson maturity model is the standard map of how far real APIs travel along that path[13] — and the honest summary is that most stop at level 2 and are none the worse for it, because the constraints that pay for themselves at internet scale are cacheability and statelessness, not link-driven discovery.

The commercial history matters as much as the architectural one. Salesforce launched an XML API in February 2000, eBay followed in November of that year with a developer programme, and Amazon opened Amazon.com Web Services in July 2002 so that third-party sites could search and display its catalogue.[14] What made Amazon consequential was not the public API but the internal discipline behind it: Werner Vogels, describing the architecture in 2006, defined service orientation as encapsulating data together with the business logic that operates on it, with the only access through a published service interface — and noted that prohibiting direct database access by clients is what made it possible to change storage without involving them.[15] That is Parnas, restated as an operating rule for a company.

The modern pluralism arrives in 2015: GraphQL is published by Facebook, gRPC by Google, and Swagger becomes the OpenAPI Initiative under the Linux Foundation. Each has kept evolving — OpenAPI reached 3.2.0 in September 2025, adding formal path-templating rules, support for streaming media types and a richer tag structure,[16,17] and the GraphQL specification received its September 2025 edition, the first since October 2021, adding schema coordinates, oneOf input objects and descriptions on executable documents.[18,19] The IETF has meanwhile been quietly standardising the parts of API design that everyone had been reinventing: problem details for error bodies in 2023,[20] a Deprecation response header in March 2025,[21] and rate-limit headers and an Idempotency-Key header still working their way through the HTTPAPI working group.[22,23]

For us service orientation means encapsulating the data with the business logic that operates on the data, with the only access through a published service interface. Werner Vogels, ACM Queue, 2006[15]
paths: /styles

Four grammars, one set of decisions

Before the subtopics, it is worth fixing what actually differs between interface styles, because the differences are narrower than the discourse suggests. The useful distinction is who decides the shape of the response.

In a resource interface, the client names a thing and the server decides what a representation of that thing contains. HTTP gives this style its vocabulary: methods with defined safety and idempotency properties, status codes, conditional requests, content negotiation.[24] The provider owns the shape, which makes caching tractable and over-fetching structural.

In a query interface such as GraphQL, the client names the fields and the server owns the graph rather than the payload.[18] Over-fetching disappears; in its place you inherit query cost as a first-class security and capacity problem, because a client can now compose a request whose expense you did not anticipate.[25] GraphQL also relocates several decisions rather than removing them: HTTP caching becomes harder and is being addressed by the GraphQL-over-HTTP work, which defines an application/graphql-response+json media type so intermediaries can trust status codes.[26]

In a procedure interface such as gRPC or JSON-RPC, the client names an action and the types come from an interface definition language rather than a URL.[27] Protobuf's field numbering makes wire compatibility a first-class, mechanically checkable property.[28,29] The cost is that the operation set is unconstrained: nothing stops a service accumulating four hundred verbs, and nothing in the protocol tells a caller which of them are safe to retry beyond the status code taxonomy.[30]

In an event interface, nobody calls anybody. The producer publishes facts and consumers decide when to read them; ordering and retention become part of the contract, and schema evolution is governed by reader/writer resolution rules rather than by request validation.[31,32] AsyncAPI and CloudEvents give this style the description apparatus that OpenAPI gives to HTTP.[33,34]

Zimmermann and colleagues' pattern catalogue is the most systematic treatment of these choices as a design space rather than a religious question, and it is organised, tellingly, around message structure and quality attributes rather than around protocols.[35] Pautasso, Zimmermann and Leymann made the same argument empirically in 2008, comparing REST and WS-* on architectural criteria rather than partisanship.[36] The practical reading: pick the style that matches your consumers' fetch patterns and your organisation's tolerance for schema governance, then do the thirteen pieces of design work anyway.

Resource modelling

Resource modelling is where most API design either succeeds quietly or fails expensively, because it is the only part of the contract you genuinely cannot change later. A field can be deprecated. A version can be pinned. A name, once it is in ten thousand lines of other people's code and a hundred saved Postman collections, is permanent in the way a road layout is permanent.

Start from the aggregate, not the table

The first mistake is exposing storage. If the resource tree is a mirror of the relational schema, every normalisation decision becomes a public commitment, and clients will start issuing the joins you were trying to avoid. Domain-driven design supplies the better unit: the aggregate, a cluster of objects with a single root that is the boundary of a transaction and of invariants.[37,38] An aggregate root is a good resource because it is exactly the thing about which you can make consistency promises. Objects inside it are not separately addressable; objects outside it are referenced by identifier, not embedded and edited in place.

Google's resource-oriented design guidance formalises the same instinct for RPC and REST alike: model a small set of named resources with a standard method set — List, Get, Create, Update, Delete — and reach for a custom method only when the standard five genuinely do not fit.[39–41] The discipline is not aesthetic. A standard method set means a client library, a permission model, an audit log format and a pagination convention can each be written once. Kubernetes takes the idea furthest: every object is a group/version/kind with the same verbs, the same metadata block, the same list semantics, and conversion between versions handled by the API machinery rather than by each controller.[42,43]

Identity is the first promise

Identifiers deserve more design attention than they usually get, because they are the part of the payload most likely to be stored by someone else. Three rules earn their keep. Make them opaque: a client that can parse structure out of an id will parse it, and you will never be able to change the format. Make them stable: an id that is reassigned or reused turns every consumer's cache and every foreign key into a silent corruption. And make them unguessable if the object is not public, because sequential integers convert an authorization bug into an enumeration attack — the mechanism behind the most common API vulnerability class of the last decade.[44]

Naming, and the cost of a good name

Resource names are a URI design problem governed by generic syntax rules[45] and, where clients need to construct them, by URI templates.[46] Beyond syntax, the conventions that survive contact with large surfaces are dull and worth adopting wholesale: plural collection nouns, identifiers as path segments, sub-collections for containment, and hierarchical names that read as a sentence about ownership.[47] Google's convention of full resource names such as publishers/123/books/456 is more than tidiness — it gives every object a single canonical string that can appear in a permission policy, a log line and a cross-service reference.

Two naming decisions are worth arguing about. The first is verbs. Purists insist that any action can be modelled as a state change; practitioners discover that cancel, publish and refund are not state changes but state transitions with preconditions, side-effects and their own authorization rules. A custom method — whether spelled POST /orders/42:cancel, a gRPC method, or a GraphQL mutation — is usually the honest model, and pretending otherwise produces a status field that is really an RPC with extra steps.[41] The second is nesting depth. Every level of nesting is a claim that the parent will always be knowable at call time; three levels is usually the point at which that claim starts costing clients more than it saves them.

Representations, projections and partial updates

A resource is not its representation. The same order may be rendered as a summary in a list, a full document on GET, a webhook payload and a report row, and treating these as one schema forces a false choice between over-fetching and a proliferation of endpoints. Field masks are the disciplined answer for reads: let the caller ask for a subset by name, and let the default be documented rather than incidental.[48] For writes, the corresponding problem is expressing "change only this". PUT means replace, which is why it is safe to retry;[24] partial update needs PATCH, and PATCH needs a defined patch document format, either JSON Patch for explicit operations or JSON Merge Patch for the simpler merge-with-null-deletes semantics.[49–51] Shipping PATCH with an undocumented body format is one of the more common ways to create a contract nobody can implement correctly twice.

Interface contracts

A contract is the artefact that lets two teams work without talking. It has to be precise enough to generate code from, loose enough to leave the provider room to change its implementation, and — the part that is usually missed — explicit about behaviour that no schema language can express.

What a schema can and cannot say

OpenAPI describes HTTP APIs: paths, operations, parameters, request and response schemas drawn from JSON Schema, security schemes, and since 3.2.0 also streaming media types and non-standard methods.[16,52] Protobuf's .proto files describe messages and services, with field numbers rather than names carrying wire identity.[28] GraphQL's SDL describes a type graph with nullability as a first-class property.[18] AsyncAPI does the equivalent job for event-driven interfaces.[33] All four are genuinely valuable, and all four share the same blind spot.

None of them can express: whether two requests with the same body are the same request; whether a list is stable under concurrent writes; how long a token is valid; which errors are worth retrying; what happens when a field is omitted versus sent as null; how much load you are allowed to generate; what the ordering guarantee is; or whether a 500 means the write happened. Those are the promises clients actually break on. A schema is the skeleton of the contract, and prose supplies the ligaments — which is one reason a good API's reference documentation cannot be fully generated, a point section 17 returns to.

Design-first, and why the arrow direction matters

There are two ways to end up with a specification. In design-first, the spec is written and reviewed before the handlers exist, and code is generated or validated against it. In code-first, annotations in the implementation emit a spec as a by-product. The distinction sounds procedural and is actually architectural: in code-first, the specification is a report on whatever the handlers happen to do this week, so an accidental change is indistinguishable from an intentional one, and the diff that should have blocked a release instead documents it after the fact.

The gate is where the value is concentrated. Two classes of check belong there. Style linting enforces the decisions you have stopped re-litigating — naming, pagination parameters, error media types — using a tool such as Spectral for OpenAPI or Google's API linter for AIP conformance.[53,54] Breaking-change detection compares the proposed spec against the published one; Buf does this for Protobuf, oasdiff and similar tools for OpenAPI.[55,56] Section 19 builds a small version of both, so the logic is visible rather than asserted.

Contract testing: the promise, verified from the other side

A specification says what should happen. A contract test checks that it does — and, crucially, checks it against what consumers actually rely on rather than against everything the spec permits. The consumer-driven contracts pattern, described by Ian Robinson in 2006, inverts the usual direction: each consumer publishes the subset of provider behaviour it depends on, and the provider's build runs all of them.[57] Pact is the widely used implementation.[58] The payoff is a precise answer to the question that otherwise requires a survey: if I change this, who breaks?

The complementary discipline is on the consumer side. Martin Fowler's tolerant reader pattern says to extract only what you need and ignore the rest, so that provider additions do not break you.[59] It is good advice with an important limit, set out at length by the IAB in RFC 9413: liberal acceptance applied as a blanket principle degrades interoperability over time, because it lets specification ambiguities calcify into bug-for-bug compatibility that nobody can subsequently fix.[60,61] Be tolerant about additions you were told to expect. Be strict about everything else, and report what you rejected.

Versioning

Versioning is the most over-discussed and under-decided topic in API design. The reason is that teams argue about syntax — path segment versus header versus media type — when the real decision is a policy question: how many behaviours are we willing to run simultaneously, and for how long? The syntax follows from the answer, and is close to irrelevant otherwise.

The four mechanisms

Version in the path. /v1/, /v2/. Visible, trivially routable, cacheable per version, and hostile to the purist reading of REST because two URLs now name the same resource. It is what Google's own guidance recommends for major versions,[62] and its practical drawback is that it encourages big-bang v2 rewrites — which are the versioning equivalent of a rewrite branch, and fail for the same reasons.

Version in a media type. Accept: application/vnd.acme.v2+json. Formally the most correct: one URL per resource, negotiated representations. Practically, it interacts badly with browser tooling, CDN caching configuration, and every developer's first curl. RFC 9205's guidance on building protocols with HTTP is worth reading before choosing it, because it is specific about which HTTP mechanisms carry which costs.[63]

Pin the caller to a date. Stripe's model: an account is pinned to a version at its first request, every request may override with a Stripe-Version header, and the provider maintains compatibility shims so that an integration written in 2015 still sees 2015 semantics. Since the 2024 change to a release-train model, major named releases — Acacia, Basil, Clover, Dahlia — arrive roughly twice a year and may break; monthly releases within a train are additive only and safe to adopt.[64,65] This is the most consumer-friendly option available and the most expensive to operate, because the provider now maintains an unbounded stack of translation layers.

Do not version at all. GraphQL's default position is that a schema evolves by addition, with @deprecated marking fields on the way out; GitHub's public GraphQL API follows this, publishing a schedule of breaking changes rather than a version number.[18,66,67] Kubernetes reaches the same destination by a different road: versions exist (v1alpha1, v1beta2, v1) but the deprecation policy is what does the work, guaranteeing that a stable API version is supported for at least twelve months or three releases after deprecation, and that beta versions get nine months or three releases.[68]

Choosing, and the thing everyone gets backwards

Semantic versioning is the right mental model for libraries, where the consumer chooses when to upgrade.[69] It is a poor model for a hosted API, where the provider deploys and the consumer finds out. That asymmetry is the whole game. A hosted API has, in effect, only two version numbers that matter: "the behaviour you are pinned to" and "the behaviour we would like you to move to". The useful design goal is to make the number of distinct pinned behaviours small and their lifetimes explicit.

Shopify's quarterly calendar versioning is a clean example of making that explicit: versions are named by date, released on a schedule, and supported for a fixed window, so consumers can plan migrations against a calendar rather than a rumour.[70] The general principle is that predictability is worth more to consumers than longevity. A version supported for nine months with a published end date is easier to build against than one supported indefinitely until it is not.

Backward compatibility

Compatibility is where API design becomes mechanical enough to automate, which is why it is worth being precise about the rules rather than relying on judgement under deadline pressure.

The direction rule

Every field travels in one direction. Request fields are written by the client and read by the server. Response fields are written by the server and read by the client. A change is breaking whenever it can make an existing reader fail on data an existing writer may still produce. That single sentence generates almost the whole table.

Making an optional request field required breaks every client that omits it. Removing a response field breaks every client that reads it. Narrowing an accepted enum breaks clients still sending the removed value; widening a returned enum breaks clients whose switch has no default branch. Tightening validation breaks whoever was relying on the looser rule. Avro's reader/writer schema resolution formalises exactly this asymmetry for data pipelines,[31] and Confluent's compatibility modes — backward, forward, full — make it a deployment-order question: backward compatibility lets you upgrade readers first, forward compatibility lets you upgrade writers first.[32] Protobuf encodes the same discipline in its rules about never reusing a field number and never changing a field's type.[28,29] Google's AIP-180 states the API-level version of the policy.[71]

What the table leaves out

Three categories of breakage never appear in a schema diff, and between them they account for a large share of real incidents.

Semantic drift. The field keeps its name and type and starts meaning something slightly different: total begins including tax, created_at switches from the request time to the commit time, status: "complete" starts being set a step earlier in the workflow. Nothing fails. Reports quietly become wrong, and the discovery latency is measured in quarters.

Performance as contract. An endpoint that returned in 40 ms and now returns in 900 ms has broken every caller with a 200 ms timeout, and no schema captures this. It is the purest form of Hyrum's law: the promise nobody wrote down but everybody's timeout configuration encodes.[2] The same applies to ordering that was incidentally stable, to a collection that happened to fit in one page, and to an error that used to arrive in 10 ms and now arrives after a 30-second upstream timeout.

Error changes. Moving a condition from 400 to 422, splitting one error code into three, or changing the text a client was regex-matching are all breaking for someone. This is a strong argument for enumerating stable machine-readable error codes early, so that clients have something legitimate to branch on — the subject of section 14.

Designing for change before you need it

A handful of choices dramatically widen the space of non-breaking changes later, and all of them are cheap on day one and expensive to retrofit.

  • Paginate every collection from the first release. Google's guidance is explicit that adding pagination to an existing method is itself a backwards-incompatible change, because existing callers silently start receiving a truncated result set.[72] This is the single highest-value pre-commitment in the list.
  • Wrap list responses in an object. A bare JSON array has nowhere to put next_page_token, a total, or a warning, and adding a wrapper later is breaking.
  • Return enums with a documented unknown-value policy, so that adding a value is merely risky rather than fatal, and say in writing what a client should do on encountering one.
  • Reserve the shape for growth: single-valued fields that might plausibly become multi-valued should arrive as objects, not scalars, because {"url": "..."} can grow and "https://..." cannot.
  • Never make silence meaningful. If an omitted field and an explicit null differ, document the difference; if they do not, say so, because clients will otherwise discover the answer empirically and depend on whichever one they found.

Pagination

Pagination looks like a convenience feature and is actually a correctness feature. The promise a paginated collection makes is not "you get results in chunks"; it is "if you follow the pages to the end, you will have seen every matching row exactly once". Offset pagination cannot keep that promise, and most APIs ship it anyway.

Why offsets drift

LIMIT 20 OFFSET 40 asks for a position in an ordering that is being mutated by other people while you read it. If a row is inserted ahead of your position between page two and page three, every subsequent row shifts and one is skipped; if a row is deleted, one is served twice. Neither failure produces an error. The client receives a plausible, complete-looking result set that is quietly wrong — which is exactly the kind of defect that survives to production and then to a reconciliation report.

The second problem with offsets is cost. OFFSET 500000 requires the database to locate and discard half a million rows before returning twenty, so page-load time grows linearly with depth. Deep pagination is therefore both a correctness bug and an availability risk, since any caller can generate an expensive query by incrementing a number.

Keyset and cursor pagination

Keyset pagination replaces "skip n rows" with "start after this row", expressed as a predicate over the sort key: WHERE (created_at, id) < (?, ?) ORDER BY created_at DESC, id DESC LIMIT 20. Because the predicate names a row rather than a position, concurrent inserts before it are irrelevant, and because it is an index seek, the cost is constant at any depth. The tuple comparison is not optional — a non-unique sort key needs a unique tie-break appended, or rows sharing a key can be skipped or repeated at page boundaries.

The cursor should be opaque: an encoded token whose contents are the provider's business. Google's pagination guidance specifies exactly this shape, with page_size and page_token on the request and next_page_token on the response.[40,72] The reason opacity matters is not obfuscation but evolution: an opaque token lets you change the sort key, add a tie-break, switch storage engines or embed a snapshot identifier without breaking any client, whereas a base64-encoded JSON blob that clients have learned to decode is a public schema you did not intend to publish. Sign or encrypt tokens if they encode anything a caller should not be able to forge, and give them a documented expiry.

Other traditions arrive at the same structure. GraphQL's Relay-style connections wrap edges with per-edge cursors and a pageInfo object carrying hasNextPage and endCursor;[73] the extra machinery buys the ability to page through nested collections within a single query. HTTP's own mechanism is the Link header with rel="next" and rel="prev", which has the pleasing property that the client follows a URL rather than assembling one.[74] GitHub's REST API is the best-known large deployment of that convention.

The total-count trap

Clients ask for a total so they can render "page 7 of 412". On a large filtered collection an exact count is a full scan of the matching set, executed on every page request. Options, in descending order of how often they are the right answer: don't return one; return an estimate and label it as one; return an exact count only when the filtered set is below a threshold; return it on request via a separate, explicitly expensive parameter. Google's guidance allows a total_size that may be an estimate, and requires that the field document itself as such.[40]

Filtering

Filtering is where API design and database physics collide most directly. Every filter you accept is an index you have promised to maintain, and every filter you accept without an index is a denial-of-service vector that any authenticated caller can trigger by accident.

Three designs, in ascending order of ambition

Named parameters. ?status=pending&created_after=2026-01-01. Trivial to validate, trivial to route to an index, trivially cacheable, and unable to express OR. For a large majority of APIs this is sufficient and should be the default. Its weakness is combinatorial growth: each new dimension is a new parameter and, eventually, a new page of documentation.

A declared expression grammar. Google's AIP-160 defines a filter string with a CEL-like syntax over a closed field set, chosen deliberately so that filtering requirements can evolve without a new API version and without a client library release.[75] OData's $filter is the standardised, considerably larger version of the same idea.[76] The design principle in both cases is that the grammar is published and the field set is closed. A filter language that accepts arbitrary field names is a promise to index every column you will ever add.

Query-shaped interfaces. GraphQL arguments, or a search endpoint that accepts a query DSL. Maximum expressiveness, and the point at which cost control must become explicit: depth limits, complexity scoring, per-field cost budgets and persisted queries are not optional extras but the mechanism that makes the interface safe to expose.[25] The OWASP API Top 10 files this under unrestricted resource consumption, and it applies just as sharply to a REST endpoint accepting an unbounded filter as to a GraphQL query.[77]

The rules that hold across all three

  • Close the field set and publish it. Filterable fields are a contract; an un-filterable field can become filterable later, but the reverse is breaking.
  • Never build SQL by string concatenation from a filter string. Parse to an AST, validate the fields against the allow-list, then bind parameters. This is injection defence and cost defence in one pass.
  • Give every filter a bound. Unbounded date ranges, unanchored substring matches and negations over large sets are the three shapes that turn a filter into a table scan.
  • Return filters as part of the response context where it aids debugging, so that a client can tell an empty result from a mis-parsed filter.
  • Decide what an unknown field does. Silently ignoring an unrecognised filter is the worst option: it returns more data than the caller asked for and looks like success. Reject it.

the promise

Sorting

Sorting is usually treated as a footnote to filtering, and it deserves its own short treatment because it interacts with pagination in a way that silently breaks correctness.

The interface shape is settled: a single order_by parameter taking a comma-separated list of fields with optional desc, drawn from an enumerated allow-list.[40] The substance is in three properties that must be true and are usually left implicit.

The ordering must be total. If a caller sorts by created_at and a thousand rows share a timestamp, the database is free to return them in any order, and it will return them in a different order on the next call — so a cursor placed in the middle of that block will skip or repeat rows. The fix is mandatory and cheap: append a unique tie-break, usually the primary key, to every sort specification, and say in the documentation that you do.

The ordering must be stated, including its collation. Sorting strings is a locale-dependent operation: whether "apple" precedes "Apple", where accented characters land, and how empty strings compare all depend on collation. Sorting by a nullable column requires an explicit nulls-first or nulls-last policy. These are contract terms because clients render them to users, and a change is visible even though no schema changed.

The sortable set must be closed, and for the same reason as filters. Every sortable field is an index; sorting by a non-indexed field on a large collection is a full sort, and combining it with a deep cursor makes the cost worse rather than better.

Sorting and cursors, stated precisely

A cursor encodes a position in a specific ordering. If the client changes order_by mid-iteration, the cursor is meaningless, and the correct response is to reject the request rather than to silently reinterpret it. If the provider changes the default ordering, every cursor outstanding at deploy time becomes invalid. Both cases argue for encoding the ordering inside the opaque token and validating it on use — the cheapest possible defence against a class of bug that is otherwise invisible.

Authentication

Authentication answers exactly one question — who is calling? — and the most common design error is letting it answer a second one. A valid credential is a claim about identity. It is never, by itself, a decision about access.

The mechanisms, and what each is actually for

API keys. A single bearer secret identifying an application. Appropriate for server-to-server calls where the caller is an organisation rather than a person, and adequate when paired with strict transport security, scoping, rotation and revocation. The failure mode is structural: a static secret that never expires, is copied into environment variables, CI systems and support tickets, and grants everything the account can do.

OAuth 2.0 and 2.1. Delegated authorization: a resource owner permits a client to act on their behalf without sharing credentials.[78,79] The 2025 security best current practice, RFC 9700, is now the operative document: it mandates PKCE for authorization code flows, requires exact redirect-URI matching, and deprecates the implicit grant and the resource-owner-password grant.[80,81] The in-progress OAuth 2.1 draft consolidates those changes into a single specification, and although it remains a draft, building to its defaults is the correct posture for anything new.[82] OpenID Connect layers authentication proper on top, supplying an ID token with verifiable claims about the end user.[83]

Bearer tokens and their limits. A JWT is a signed, self-describing token whose attraction is that a resource server can validate it without a network call.[84] That is also its weakness: a self-contained token cannot be revoked before it expires, which is why short lifetimes plus refresh, or token introspection against the authorization server, are the two workable patterns.[85] Anyone holding a bearer token can use it; sender-constrained tokens remove that property, either by binding the token to a mutual-TLS client certificate[86] or via DPoP, which requires the client to prove possession of a key on each request.[87] For high-value APIs this is now the expected posture rather than an exotic one.

Mutual TLS on its own remains the right answer inside a service mesh, where the caller is a workload rather than a person and certificate rotation is automated.

Design rules that survive contact with production

  • Validate the audience. A token minted for service A must be rejected by service B. Skipping this turns any service that receives tokens into a confused deputy for every other service.
  • Never put credentials in a URL. Query strings land in access logs, browser history, referrer headers and error reports. RFC 9700 is explicit on this point.[80]
  • Design rotation before you need it. An API that supports exactly one active key per account forces every rotation to be an outage; two active keys with independent expiry make it a routine operation.
  • Distinguish the application from the user. Most non-trivial APIs need both, and conflating them makes audit logs unusable and least privilege unenforceable.
  • Return 401 for "I do not know who you are" and 403 for "I know, and no". The distinction is in RFC 9110[24] and clients genuinely branch on it: one means re-authenticate, the other means stop retrying.

Authorization

Authorization is the most consequential API design topic and the one least served by frameworks, because the part frameworks can do for you is the part that rarely fails. Guarding a route is easy. Deciding whether this caller may touch this row is application logic, and it is the single most common serious vulnerability in production APIs.

Three depths

Route. May this caller invoke this operation at all? Handled by scopes, roles or middleware. Failures here are broken function level authorization — an admin endpoint reachable by a normal user.[77]

Object. May this caller act on this specific object? This is broken object level authorization, ranked first in the 2023 OWASP list, and the guidance is worth quoting closely: every endpoint that receives an object identifier and acts on that object should implement an object-level check, and comparing a session user id against an id parameter addresses only a small subset of cases.[44] The vulnerability is structural rather than exotic. It appears when authorization is implemented per handler, so one of forty handlers is written by someone in a hurry, and it appears identically in GraphQL, where a mutation taking a list of document identifiers deletes all of them without checking any.[44]

Property. May this caller read or write this field? Serialising a whole internal object exposes fields the caller should not see; accepting a whole object binds fields the caller should not set. OWASP merged what used to be excessive data exposure and mass assignment into one entry precisely because they are one bug with two directions, and the mitigation is the same in both: enumerate the fields you expose and the fields you accept rather than reflecting an internal object.[88]

Models, and where to put the decision

Role-based access control assigns permissions to roles and roles to users, which is well-understood and scales badly along the dimension that matters for multi-tenant APIs.[89] Attribute-based access control makes the decision a function of attributes of subject, object, action and environment, which is expressive and hard to audit.[90] Relationship-based access control — the model behind Google's Zanzibar, which stores relationship tuples and answers "may user U do action A on object O?" as a graph query at global scale[91] — has become the reference architecture for products whose sharing model looks like a document system rather than an org chart.

Whichever model, the architectural rule is the same: the authorization decision belongs at the object, not at the edge. A gateway can enforce that a token is valid and that a scope is present. It cannot know that order 42 belongs to tenant B, because that is a database fact. Policy engines such as OPA and Cedar are valuable for keeping policy declarative and testable, but they still need the resource's attributes to decide, which means the decision point sits next to the data.[92,93]

Scopes are not permissions

A frequent design confusion: OAuth scopes express what the user consented to let this application do. They are a ceiling, not a grant. A token with payments:write does not mean the caller may write any payment; it means the application is permitted to attempt payment writes on behalf of a principal whose own permissions still have to be checked. APIs that treat scope as the terminal authorization check are one org-chart change away from an incident.

Idempotency

Every network call has three outcomes, not two: it succeeded, it failed, or you do not know. The third is the common case in production and the one API design most often ignores. A client that sends a payment request and receives a timeout has no way to distinguish "the charge never happened" from "the charge happened and the response was lost". Whatever it does next — retry and risk a double charge, or not retry and risk a missing one — is wrong some of the time, and the provider is the only party that can fix this.

What HTTP already promises

HTTP defines two independent properties. A method is safe if it is essentially read-only, and idempotent if the intended effect of several identical requests is the same as that of a single one.[24] GET, HEAD and OPTIONS are both; PUT and DELETE are idempotent but not safe; POST and PATCH are neither. This is a statement about intent, not about implementation: a PUT handler that appends rather than replaces has broken the promise the method makes, and clients — and intermediaries — are entitled to retry on that assumption.

The distinction is also why PUT is worth preferring for full-replacement updates. It converts "did my write land?" from an unanswerable question into a re-send.

Idempotency keys

For genuinely non-idempotent operations — creating a charge, sending a message, placing an order — the mechanism is a client-generated key that the server uses to deduplicate. Stripe's implementation is the reference: the client supplies an Idempotency-Key header, the server stores the result of the first request under that key, and any repeat with the same key returns the stored result rather than performing the operation again.[94] The IETF has an in-progress draft standardising the header name and semantics.[23] Google's equivalent convention passes a request_id in the request message.[95]

The details are where implementations diverge, and each divergence is a promise the documentation must make explicit.

  • Fingerprint the request body. If the same key arrives with a different payload, the client has a bug — probably a reused key from a connection pool or a retried request whose body was regenerated. Answering with an error is correct; silently applying one of the two payloads is not.
  • Store the response, not just a marker. A retry must receive the same body and the same status code as the original, because the client's parsing logic runs against it either way.
  • Handle the in-flight case. A retry arriving while the original is still executing must not start a second execution. A conflict status telling the client to retry shortly is the usual answer.
  • Bound and publish the retention window. Keys cannot be stored forever. Whatever the window is — twenty-four hours is common — it belongs in the documentation, because a client retrying outside it will get a second execution and needs to know that.
  • Scope keys per credential. A global key namespace lets one tenant's key collide with another's, which is both a correctness bug and an information leak.

Idempotency is not exactly-once

Pat Helland's treatment is the clearest statement of the underlying constraint: in a distributed system you get at-least-once delivery and you build exactly-once effects on top of it, by making operations idempotent at the point where state changes.[96,97] The API-level key is one instance of a general pattern that also shows up as the idempotent receiver in messaging architectures.[98] What you are promising a client is not that the network delivered once; it is that the observable effect happened once.

The adjacent mechanism, for updates rather than creates, is optimistic concurrency: the server returns an ETag, the client sends it back in If-Match, and a mismatch yields 412 Precondition Failed.[24] This solves a different problem — lost updates from concurrent writers rather than duplicate writes from one — and an API doing serious write traffic generally needs both.

Error handling

Errors are the part of an API that clients spend the most code on and that providers spend the least design effort on. The asymmetry is worth correcting, because an error response is not an accident — it is a documented, versioned, machine-consumed part of the contract, and it changes what the caller does next.

Status codes: use the vocabulary, do not invent one

HTTP's status classes carry real semantics that intermediaries, libraries and humans already understand: 4xx means the request was wrong and repeating it unchanged will not help, 5xx means the server failed and the same request might succeed later.[24,99] Getting the class right is worth more than getting the specific code perfect. The specific codes that repay precision are 401 versus 403, 404 versus 403 for objects the caller may not know exist, 409 for state conflicts, 412 for failed preconditions, 422 for semantically invalid content, and 429 for rate limiting.[100]

Two anti-patterns are endemic. The first is returning 200 OK with an error in the body, which defeats every generic retry policy, every monitoring dashboard and every HTTP-aware intermediary in the path. The second is mapping every failure onto 400, which forces clients to parse prose to find out what happened. GraphQL sits awkwardly here by design, since a partial success returns data alongside errors; the GraphQL-over-HTTP work exists partly to make status codes meaningful again for GraphQL responses.[26] gRPC solves the same problem with its own sixteen-code status enumeration, which maps cleanly onto HTTP semantics.[30]

A structured body, in one shape

RFC 9457 defines application/problem+json with a small set of members: a type URI identifying the problem class, a short human-readable title, the status, a detail specific to this occurrence, and an instance.[20] It is deliberately extensible, and the extensions worth adding are consistent across every mature API: a stable machine-readable code, a request_id for support, a field-level error list for validation failures, and an explicit retryability signal. Google's error guidance and gRPC's status model arrive at the same structure.[101] Twilio's long-standing practice of assigning every error a permanent numeric code with its own documentation page is the same idea taken to its logical conclusion.[102]

Two rules make the difference between an error format and an error contract. First, the code is stable and enumerated: clients branch on it, so it is as much a part of the API as a field name, and changing it is breaking. Second, the detail is not stable: it is prose for humans, may be localised, may include specifics, and clients must be told in writing never to parse it. Without that instruction, someone will, and then you cannot improve your error messages.

What errors must not contain

Stack traces, SQL fragments, internal hostnames, upstream vendor errors passed through verbatim, and — the subtle one — the difference between "this object does not exist" and "this object exists and is not yours". The last is an enumeration oracle: returning 404 uniformly for both cases costs a little debuggability and removes a reconnaissance primitive.[77]

Rate limiting

Rate limiting is usually filed under operations. It is a contract term: it determines what a client is allowed to build, and a limit that is undocumented or unpredictable is indistinguishable, from the caller's side, from an unreliable API.

Algorithms and what they promise

Fixed window counters are cheap and permit a burst of up to twice the limit across a window boundary. Sliding window variants smooth that at the cost of more state. Token bucket is the usual production choice because its two parameters map onto things a client can understand: bucket depth is the burst you may take, refill rate is the sustained throughput you may assume. Concurrency limits — capping in-flight requests rather than request rate — are frequently the better control for expensive endpoints, because they bound resource consumption rather than call count. Stripe's engineering write-up on running several limiter types side by side, each protecting a different resource, remains the clearest practitioner account.[103,104]

Telling the client

A limit the caller cannot observe is a limit the caller will hit. The response to an exceeded limit is 429 Too Many Requests, defined in RFC 6585, and it should carry Retry-After.[24,100] For proactive shaping, the IETF's HTTPAPI working group has been standardising rate-limit fields; the current draft defines RateLimit and RateLimit-Policy as structured fields, consolidating the widely deployed X-RateLimit-* conventions from earlier drafts.[22,105] It remains work in progress, which is itself worth telling consumers, but the names are stable enough to adopt.

Four things belong in the documentation, and their absence is the usual cause of support load: the scope of the limit (per key, per account, per endpoint, per IP), the algorithm and window, what happens to a request that is rejected (dropped, queued, degraded), and whether limits differ between endpoints.

The client half of the contract

Server-side limiting without client-side discipline produces a retry storm: every rejected caller waits the same interval and returns simultaneously, so the recovery attempt is itself an overload event. The mitigation is exponential backoff with jitter, and the AWS analysis of the various jitter strategies is the canonical treatment — full jitter, randomising uniformly across the whole backoff interval, both reduces contention and completes work sooner than the naive scheme.[106,107] Retries also need a budget rather than a count, because a fixed retry count per request multiplies load exactly when the system can least afford it, and circuit breakers exist to stop calling a service that is failing at all.[108]

The provider's complement to all of this is load shedding: when saturated, rejecting work quickly and cheaply is better than accepting it and timing out, because a timed-out request has consumed resources and produced nothing.[109,110] Rejecting fast is a service to the caller, and saying so in the documentation is what turns it from an outage into a documented behaviour.

Deprecation and removal

Everything above is about making promises. This section is about the only legitimate way to stop keeping one.

The mechanism

HTTP now has purpose-built signalling for this. The Deprecation response header field, standardised as RFC 9745 in March 2025, tells consumers that a resource is or will be deprecated, and the accompanying deprecation link relation points to documentation about it.[21] The Sunset header, RFC 8594, names the point in time after which the resource is expected to become unresponsive.[111] The pairing matters: Deprecation without Sunset is a mood, and Sunset without prior Deprecation is an ambush. In schema languages the equivalents are GraphQL's @deprecated directive[18] and OpenAPI's deprecated flag,[16] both of which have the significant advantage of being visible in tooling and introspection rather than only in prose.

The policy

Kubernetes has the most rigorous published example. Its rules include that an API version must not be deprecated until a replacement of equal or greater stability exists, that stable API versions remain available for at least twelve months or three releases after deprecation, and that beta versions get at least nine months or three releases — with the corollary that objects already persisted to storage must remain decodable even after their serving endpoint is withdrawn.[68] The last clause is the sophisticated one: removing an API from the wire is not the same as removing it from the data, and conflating them is how upgrades corrupt clusters.

The operational sequence that works, in the order it works:

  1. Ship the successor first, and make migrating to it strictly better rather than merely different. Nobody migrates for your convenience.
  2. Announce with a date, in the changelog, in the reference documentation, and by direct message to identified consumers.
  3. Signal in-band on every response, so that a team who never reads changelogs but does read logs finds out.
  4. Instrument by consumer. Per-credential, per-endpoint, per-field usage telemetry is what converts "we think everyone has moved" into a list of four accounts and their contact addresses.
  5. Brown out. Scheduled short outages of the deprecated path, announced in advance, find the integrations that monitoring did not.
  6. Remove, and mean it, returning 410 Gone rather than a silent 404, so the failure is diagnosable.

The other tradition

Some interfaces never remove anything. The Linux kernel's userspace ABI, Win32 and POSIX all operate on the principle that breaking existing programs is not an available option, and each has accumulated compatibility machinery accordingly — the kernel documents its stable-ABI commitment explicitly,[112,113] and Raymond Chen's history of Windows compatibility work is an extended account of what honouring it actually costs.[114] The trade is real: infinite compatibility buys an ecosystem and pays for it in permanent constraint on the implementation. Most hosted APIs cannot afford that bargain, which is exactly why they need a deprecation policy instead.

Every consumer planning a roadmap; every partner with a quarterly release train; every customer who integrated once and moved on.

Documentation

Documentation is the interface. Not a description of it — the interface itself, because a capability nobody can find does not exist, and a promise nobody wrote down cannot be relied on. Postman's 2025 survey of more than 5,700 developers and architects found that 93% of API teams report collaboration blockers, with inconsistent, outdated or missing documentation heading the list of causes.[115]

Four kinds of document, doing four different jobs

The Diátaxis framework's distinction between tutorials, how-to guides, reference and explanation maps unusually well onto API documentation, and most API docs fail by attempting one artefact that does all four.[116]

  • Reference is exhaustive, generated where possible, and organised for lookup. This is the part OpenAPI, SDL and .proto files give you nearly for free, and the part that should never be hand-maintained separately from the code.
  • How-to guides are task-shaped: "charge a card", "handle a failed webhook", "migrate from v1". They cut across endpoints, which is precisely why they cannot be generated.
  • Tutorials get a newcomer to a first successful call, and their metric is time-to-first-200, which is worth measuring literally.
  • Explanation covers the model: what a "payment intent" is, why there are two kinds of identifier, what consistency you get. Its absence is why support queues fill with questions the reference technically answers.

What must be documented that schemas cannot express

This list is the practical summary of the whole article, and it is worth treating as a checklist for any API reaching general availability: idempotency semantics and the retention window; which errors are retryable; rate limits, their scope and their algorithm; the consistency model, including whether a read immediately after a write reflects it; ordering guarantees; pagination stability under concurrent modification; the unknown-enum-value policy; null versus absent; the deprecation policy and minimum support window; and the authorization model in terms of what a caller can and cannot see.

Beyond prose, three artefacts do disproportionate work. A changelog with an entry per change, classified as breaking or additive, is the single most valuable page on most API documentation sites. Runnable examples — real requests with real responses, generated from the test suite so they cannot rot — answer more questions than any amount of narrative. And a sandbox that behaves like production, including its errors and its rate limits, is what lets a consumer test the paths they most need to get right.

Every integration built without a call to your team — which, if the documentation is good, is nearly all of them.

Governance at scale

Everything above is tractable for one API designed by one team. The problems change shape at fifty APIs across twelve teams, where the dominant failure is no longer a bad design decision but the same decision being made forty different ways.

The published style guides, and what to take from them

Three organisations have published their internal guidance in full, and reading all three is a faster education than any book. Google's AIPs are the most granular, numbered like PEPs and covering everything from resource naming to long-running operations, with a companion linter that enforces the machine-checkable subset.[54,117,118] Microsoft's REST API guidelines are shorter and more prescriptive about HTTP semantics.[119] Zalando's RESTful API guidelines are the most explicitly rationalised, with each rule marked MUST, SHOULD or MAY and accompanied by the reason it exists.[120]

The transferable lesson is not any specific rule. It is that a style guide's value comes from removing decisions from the agenda, and that a rule which cannot be automatically checked will be followed inconsistently no matter how well argued. Write the guide, then ask of each rule: what tool enforces this, and what does it output when violated? The rules that survive that question are the ones worth having.

What a governance function actually owns

  • A catalogue. One place that knows every endpoint that exists, who owns it and who calls it. Its absence is the OWASP category of improper inventory management, and it is why shadow and zombie endpoints outlive the teams that built them.[77]
  • A gate, not a meeting: linting and breaking-change detection in CI, blocking.
  • Consumer-driven contract tests, so the blast radius of a change is computed rather than estimated.[57,58]
  • Per-field usage telemetry, which is what makes deprecation finishable.
  • A deprecation policy with numbers in it, published once and applied uniformly.

Design review still matters, but it should be reserved for the things a linter cannot see: whether the resource model matches the domain, whether an operation should exist at all, and whether the promises being made are ones the team can keep in three years. Newman's treatment of service boundaries in microservice architectures is the most useful companion here, because most bad API designs are downstream of a bad boundary.[121]

A checker that runs on this article

The arguments above are only as good as their enforceability, so the rest of this section is a working implementation. contractcheck.py is dependency-free Python that runs two passes over a trimmed OpenAPI-shaped description: a design linter encoding eight of the rules argued for above, and a compatibility differ encoding fifteen change classifications derived from the direction rule in section 7.

The worked case is a payments API with a published v1 and two proposed revisions expressing the same product intent. Revision A is what a competent team ships when nobody is diffing: a new required field, a tightened validation limit, a narrowed currency enum, a removed convenience field, a widened integer type, a changed default, a dropped endpoint, a re-ordered list and a new endpoint that forgot its authorization declaration. Revision B delivers the same features additively. Neither revision was written to produce a particular verdict; the findings below are the tool's output, captured at build time and pasted verbatim.

#!/usr/bin/env python3
"""contractcheck.py - a dependency-free API contract checker.

Two passes over a trimmed OpenAPI-shaped description:

  PASS 1  DESIGN LINT      does this interface make the promises a client needs
                           in order to write correct code? (pagination, sort
                           allow-lists, idempotency, problem+json, security,
                           deprecation signalling)

  PASS 2  COMPATIBILITY    given the previously published revision, which of
                           these changes withdraws a promise somebody may
                           already be relying on?

The compatibility rules follow the direction-of-travel logic used by Protobuf,
Avro reader/writer resolution and AIP-180: request fields are written by the
client and read by the server, response fields are written by the server and
read by the client, and a change is breaking whenever it can make an existing
reader fail on data an existing writer may still produce.

Run:  python3 contractcheck.py
"""

from __future__ import annotations

import json
import sys
from dataclasses import dataclass, field

# --------------------------------------------------------------------------
# severity
# --------------------------------------------------------------------------
BREAK, RISK, LINT, OK = "BREAKING", "RISKY", "LINT", "OK"
RANK = {BREAK: 0, RISK: 1, LINT: 2, OK: 3}


@dataclass
class Finding:
    severity: str
    rule: str
    where: str
    detail: str

    def line(self) -> str:
        return f"  {self.severity:<9} {self.rule:<22} {self.where}\n            {self.detail}"


@dataclass
class Report:
    revision: str
    findings: list = field(default_factory=list)

    def add(self, sev, rule, where, detail):
        self.findings.append(Finding(sev, rule, where, detail))

    def count(self, sev):
        return sum(1 for f in self.findings if f.severity == sev)

    def render(self) -> str:
        out = [f"revision {self.revision}"]
        if not self.findings:
            out.append("  OK        no findings")
        for f in sorted(self.findings, key=lambda f: (RANK[f.severity], f.where)):
            out.append(f.line())
        out.append(f"  -- {self.count(BREAK)} breaking, {self.count(RISK)} risky, "
                   f"{self.count(LINT)} lint")
        return "\n".join(out)


# --------------------------------------------------------------------------
# helpers over the trimmed spec shape
# --------------------------------------------------------------------------
SAFE_METHODS = {"get", "head", "options"}
IDEMPOTENT_METHODS = {"get", "head", "options", "put", "delete"}

NUMERIC_WIDTH = {"int32": 32, "int64": 64, "float": 32, "double": 64}


def ops(spec):
    for path, methods in sorted(spec["paths"].items()):
        for method, op in sorted(methods.items()):
            yield path, method, op


def op_key(path, method):
    return f"{method.upper()} {path}"


def schema_fields(schema, prefix=""):
    """Flatten an object schema into {dotted.name: node}."""
    out = {}
    if not schema:
        return out
    for name, node in schema.get("properties", {}).items():
        key = prefix + name
        out[key] = node
        if node.get("type") == "object":
            out.update(schema_fields(node, key + "."))
        if node.get("type") == "array" and node.get("items", {}).get("type") == "object":
            out.update(schema_fields(node["items"], key + "[]."))
    return out


def required_set(schema):
    return set((schema or {}).get("required", []))


# --------------------------------------------------------------------------
# PASS 1 - design lint
# --------------------------------------------------------------------------
def lint(spec, report):
    for path, method, op in ops(spec):
        where = op_key(path, method)
        params = {p["name"]: p for p in op.get("parameters", [])}
        resp = op.get("responses", {})

        # R1 - a collection read must be paginated from day one; adding
        #      pagination later truncates every existing client's result set.
        if method == "get" and op.get("returns") == "collection":
            missing = [p for p in ("page_size", "page_token") if p not in params]
            if missing:
                report.add(LINT, "R1 unbounded-collection", where,
                           f"list operation without {', '.join(missing)}; "
                           "adding pagination later is itself a breaking change")
            ok = resp.get("200", {}).get("schema", {}).get("properties", {})
            if "next_page_token" not in ok:
                report.add(LINT, "R1 unbounded-collection", where,
                           "response carries no next_page_token, so a client "
                           "cannot tell a last page from a truncated one")

        # R2 - sorting must be an allow-list, and must break ties on a unique
        #      key or cursors drift across pages.
        if "order_by" in params:
            allowed = params["order_by"].get("enum")
            if not allowed:
                report.add(LINT, "R2 open-sort", where,
                           "order_by accepts arbitrary fields; every value is an "
                           "index you have promised to maintain")
            elif not op.get("sort_tiebreak"):
                report.add(LINT, "R2 open-sort", where,
                           "sort has no declared unique tie-break, so paging over "
                           "equal keys can repeat or skip rows")

        # R3 - filtering must be a declared grammar over a closed field set.
        if "filter" in params and not params["filter"].get("grammar"):
            report.add(LINT, "R3 open-filter", where,
                       "filter is a free-form string with no published grammar; "
                       "clients will discover the real one by trial and error")

        # R4 - unsafe, non-idempotent writes need a retry story.
        if method not in IDEMPOTENT_METHODS and not op.get("idempotency_key"):
            report.add(LINT, "R4 no-retry-story", where,
                       "non-idempotent write accepts no Idempotency-Key; a client "
                       "that times out cannot safely retry")

        # R5 - errors must be machine-readable in one shape.
        for code, r in sorted(resp.items()):
            if code.startswith(("4", "5")) and r.get("media") != "application/problem+json":
                report.add(LINT, "R5 ad-hoc-errors", f"{where} {code}",
                           f"error body is {r.get('media', 'undeclared')}, not "
                           "application/problem+json")

        # R6 - every operation states what it needs, including public ones.
        if "security" not in op:
            report.add(LINT, "R6 undeclared-auth", where,
                       "operation declares no security requirement; silence is "
                       "read as 'inherits something' by humans and as 'none' by tools")

        # R7 - deprecation must carry a date, not a mood.
        if op.get("deprecated") and not op.get("sunset"):
            report.add(LINT, "R7 open-ended-deprecation", where,
                       "marked deprecated with no Sunset date; a deprecation "
                       "without a date is a comment")

        # R8 - error codes clients branch on must be enumerated.
        for code, r in sorted(resp.items()):
            if code.startswith("4") and r.get("media") == "application/problem+json":
                if not r.get("codes"):
                    report.add(LINT, "R8 unenumerated-codes", f"{where} {code}",
                               "problem response declares no stable code list, so "
                               "clients will branch on the human-readable detail")

# PASS 2 - compatibility diff
# --------------------------------------------------------------------------
def diff(old, new, report):
    old_ops = {op_key(p, m): o for p, m, o in ops(old)}
    new_ops = {op_key(p, m): o for p, m, o in ops(new)}

    for key in sorted(set(old_ops) - set(new_ops)):
        report.add(BREAK, "C1 operation-removed", key,
                   "operation withdrawn; every caller of it fails at once")

    for key in sorted(set(old_ops) & set(new_ops)):
        o, n = old_ops[key], new_ops[key]

        # --- request direction: the client writes, the server reads
        ob = (o.get("requestBody") or {}).get("schema", {})
        nb = (n.get("requestBody") or {}).get("schema", {})
        of, nf = schema_fields(ob), schema_fields(nb)
        oreq, nreq = required_set(ob), required_set(nb)

        for f in sorted(set(nreq) - set(oreq)):
            report.add(BREAK, "C2 field-now-required", f"{key} req.{f}",
                       "existing clients omit this field and will now be rejected")
        for f in sorted(set(of) - set(nf)):
            report.add(BREAK, "C3 request-field-removed", f"{key} req.{f}",
                       "clients still send it; silently ignoring an input is worse "
                       "than rejecting it")
        for f in sorted(set(of) & set(nf)):
            a, b = of[f], nf[f]
            if a.get("type") != b.get("type"):
                report.add(BREAK, "C4 type-changed", f"{key} req.{f}",
                           f"{a.get('type')} -> {b.get('type')}")
            if set(a.get("enum") or []) - set(b.get("enum") or []):
                gone = sorted(set(a["enum"]) - set(b.get("enum") or []))
                report.add(BREAK, "C5 request-enum-narrowed", f"{key} req.{f}",
                           f"values still sent by clients are now invalid: {', '.join(gone)}")
            if a.get("maxLength") and b.get("maxLength") and b["maxLength"] < a["maxLength"]:
                report.add(BREAK, "C6 validation-tightened", f"{key} req.{f}",
                           f"maxLength {a['maxLength']} -> {b['maxLength']}")
            if a.get("default") != b.get("default"):
                report.add(RISK, "C7 default-changed", f"{key} req.{f}",
                           f"default {a.get('default')!r} -> {b.get('default')!r}; "
                           "callers who omit the field change behaviour without "
                           "changing a line of code")

        # --- response direction: the server writes, the client reads
        for code in sorted(set(o.get("responses", {})) & set(n.get("responses", {}))):
            os_, ns_ = o["responses"][code], n["responses"][code]
            ofr, nfr = schema_fields(os_.get("schema", {})), schema_fields(ns_.get("schema", {}))
            for f in sorted(set(ofr) - set(nfr)):
                report.add(BREAK, "C8 response-field-removed", f"{key} {code}.{f}",
                           "a client that reads this field starts seeing null or a crash")
            for f in sorted(set(nfr) - set(ofr)):
                report.add(RISK, "C9 response-field-added", f"{key} {code}.{f}",
                           "safe for tolerant readers; strict schema validators "
                           "reject unknown properties")
            for f in sorted(set(ofr) & set(nfr)):
                a, b = ofr[f], nfr[f]
                if a.get("type") != b.get("type"):
                    report.add(BREAK, "C4 type-changed", f"{key} {code}.{f}",
                               f"{a.get('type')} -> {b.get('type')}")
                add = set(b.get("enum") or []) - set(a.get("enum") or [])
                if add:
                    report.add(RISK, "C10 response-enum-widened", f"{key} {code}.{f}",
                               f"new values {', '.join(sorted(add))} reach clients "
                               "whose switch statements have no default branch")
                if a.get("format") in NUMERIC_WIDTH and b.get("format") in NUMERIC_WIDTH:
                    if NUMERIC_WIDTH[b["format"]] > NUMERIC_WIDTH[a["format"]]:
                        report.add(BREAK, "C11 numeric-widened", f"{key} {code}.{f}",
                                   f"{a['format']} -> {b['format']}; values now exceed "
                                   "what existing clients can hold")

        for code in sorted(set(o.get("responses", {})) - set(n.get("responses", {}))):
            report.add(BREAK, "C12 status-code-removed", f"{key} {code}",
                       "a condition clients handle explicitly now arrives under "
                       "some other status")

        # --- promises that are not in any schema
        if o.get("returns") == "collection" and o.get("order") != n.get("order"):
            report.add(RISK, "C13 ordering-changed", key,
                       f"documented order {o.get('order')!r} -> {n.get('order')!r}; "
                       "cursors minted under the old order may now skip rows")
        if o.get("idempotency_key") and not n.get("idempotency_key"):
            report.add(BREAK, "C14 idempotency-withdrawn", key,
                       "retries that were deduplicated will now double-apply")
        if set(o.get("security", [])) - set(n.get("security", [])):
            gone = sorted(set(o.get("security", [])) - set(n.get("security", [])))
            report.add(BREAK, "C15 auth-scheme-removed", key,
                       f"clients authenticating with {', '.join(gone)} lose access")

The implementation is small enough to read in one sitting, which is the point. Real tools do this properly — Buf for Protobuf, oasdiff for OpenAPI, GraphQL Inspector for schemas[55,56] — and any of them beats a hand-rolled version in production. What the toy version demonstrates is that "is this change breaking?" is not a matter of taste. It is a decision procedure over a schema and a direction, and a team that treats it as taste is choosing to find out from its consumers instead.

The same problem in other worlds

The subtopics of this article were not invented by web API designers. They recur wherever an interface outlives the team behind it, and the solutions found in other domains are worth borrowing from.

Cluster orchestration: Kubernetes

Kubernetes is the most instructive large API in open source because it made every decision this article discusses explicitly and wrote them down. Resources are group/version/kind triples with a uniform metadata block; every collection is paginated with an opaque continue token; label and field selectors are the closed filter grammar; conflict detection uses resource versions as an ETag equivalent; and the deprecation policy is quantified in months and releases.[42,43,68] Its most transferable idea is version conversion as infrastructure: multiple API versions are served from one internal representation, so adding a version does not fork the controller logic.

Payments: Stripe and Twilio

Payment APIs face the sharpest version of the retry problem, because a duplicate is not an inconvenience but a financial event, and the idempotency-key pattern most of the industry now uses came from there.[94] They also demonstrate the expensive end of version management: per-account version pinning with server-side compatibility shims, organised since 2024 into biannual named release trains where monthly releases are additive only.[64,65] Twilio's contribution is the error catalogue — every failure has a permanent numeric code with its own documentation page, which is what makes support tractable at scale.[102]

Healthcare: FHIR

HL7's FHIR defines a RESTful API over clinical resources, and its constraints are unusual in ways that clarify the general problem: interoperability is the product, the consumers include systems that cannot be upgraded, and extension is unavoidable because every jurisdiction has local requirements.[122] Its answers — a strict core with a formal extension mechanism, profiles that constrain rather than fork the base resources, and explicit conformance statements — are the most developed treatment anywhere of how to let an API vary by deployment without fragmenting.

Banking: open banking mandates

Regulated financial APIs invert the usual incentive structure: the provider is compelled to expose data, the consumers are competitors, and the specification is written by neither.[123] The result is the clearest demonstration that API design is an economic instrument rather than a technical one — the same functional surface, specified with different rate limits and different consent lifetimes, produces materially different market outcomes.

Operating systems: the interfaces that never break

POSIX, Win32 and the Linux kernel's userspace ABI operate under a compatibility commitment stronger than anything a hosted API attempts, and their accumulated cost is instructive.[112–114] The lesson is not that you should copy them. It is that permanent compatibility is a purchasable property whose price is permanent constraint, and that pricing that trade honestly is the versioning decision in section 6.

Data platforms

The data world faced schema evolution earlier and more acutely than the API world, because a schema change propagates to years of stored records rather than to live callers. Avro's reader/writer resolution and the compatibility modes built on top of it are the most precise available formulation of what backward and forward compatibility mean, and they are directly applicable to request and response schemas.[31,32] Kleppmann's treatment of encoding and evolution is the standard synthesis.[124]

The conventions that tried to standardise the middle

Between "roll your own JSON" and "adopt a full framework" sit a set of conventions worth knowing even where you decline them: JSON:API standardises document structure, relationships, sparse fieldsets and pagination links in one media type;[125] JSON itself is specified by RFC 8259;[126] and HTTP caching semantics, which most API designers under-use, are worth reading in full before deciding that every response must be dynamic.[127]

paths: /machine-consumers

When the caller is not a person

One change since 2024 is worth treating separately, because it alters the weighting of everything above rather than adding a new topic. A growing share of API traffic is generated by systems that selected the endpoint themselves.

Postman's 2025 survey found that 89% of developers use generative AI in daily work while only about 24% design APIs with AI agents in mind as consumers — and that the leading security concerns had shifted accordingly, with roughly half of respondents citing unauthorised or excessive API calls from agents.[115,128] The Model Context Protocol has emerged as one standardisation attempt for how such callers discover and invoke tools;[129] the GraphQL community's September 2025 additions of schema coordinates and executable-document descriptions were motivated in part by the same pressure.[19,130]

The design implications are less novel than the framing suggests, and that is the useful observation. A machine consumer is simply a maximally literal client: it reads the description rather than the tutorial, it has no institutional memory of undocumented behaviour, it will call at machine speed and with perfect persistence, and it cannot infer from context that a field named status has six possible values when the schema says string. Every practice this article argues for on other grounds pays off harder under that consumer:

  • Precise, complete schemas, because they are now the entire interface, not a supplement to a human's judgement.
  • Enumerated error codes and explicit retryability, because a client that cannot tell retryable from terminal will retry everything.
  • Idempotency keys, because persistent automated retries turn a rare double-write into a routine one.
  • Rate limits that are legible in-band, because an agent will find the limit empirically otherwise.
  • Authorization at the object level with tight scopes, because the blast radius of an over-privileged automated caller is bounded only by your permission model.

The one genuinely new design question is identification: distinguishing an agent from the human on whose behalf it acts, so that limits, permissions and audit records can differ. That is a delegation problem, which OAuth's separation of resource owner from client was designed for — the mechanism exists, and what is new is the need to use it precisely rather than as a login flow.[78,82]

Read down the "withdrawn by" column and a pattern emerges that is worth ending on. Almost none of these promises is broken by a decision to break it. Normative specifications worth reading in full

  • RFC 9110, HTTP Semantics — the single most useful document for anyone designing an HTTP API, particularly the sections on method properties and conditional requests.[24]

  • OpenAPI 3.2.0, the GraphQL September 2025 edition, and the Protocol Buffers language guide.[16,18,28]

Style guides

  • Google API Improvement Proposals — granular, numbered, and the most complete public treatment of resource-oriented design.[117]
  • Microsoft REST API Guidelines and Zalando's RESTful API Guidelines — shorter, opinionated, and useful precisely because they disagree with Google in places.[119,120]

Books

  • Zimmermann, Stocker, Lübke, Zdun and Pautasso, Patterns for API Design — the most systematic catalogue available.[35]
  • Geewax, API Design Patterns — the practical companion to Google's AIP thinking.[131]
  • Higginbotham, Principles of Web API Design, and Lauret, The Design of Web APIs — both strong on the process of getting from use cases to an interface.[132,133]
  • Richardson and Ruby, RESTful Web Services, and Richardson and Amundsen, RESTful Web APIs — the historical and the hypermedia-serious treatments respectively.[134,135]
  • Amundsen, Design and Build Great Web APIs — the most hands-on of the set.[136]

  • Bloch's OOPSLA talk on API design remains the best forty minutes available on the general problem, and almost all of it transfers from libraries to services.[137]

Tools

  • Linting: Spectral for OpenAPI, Google's API Linter for AIP conformance.[53,54]
