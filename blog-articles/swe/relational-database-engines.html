1The question

The usual comparison of relational database systems is a feature matrix. Transactions: yes, yes, yes, yes, yes. Window functions: yes, yes, yes, yes, yes. JSON: yes, yes, yes, yes, yes. Replication, partitioning, full-text search, stored procedures, materialised views, foreign keys, check constraints, common table expressions, recursive queries: yes all the way down. The matrix was informative in 2005. It is now a list of things that stopped distinguishing anything a decade ago, and reading it leaves you with the impression that the choice is mostly about licensing and taste.

It is not. The five engines in this article disagree, right now, about whether an empty string is a value, about how many rows a UNIQUE constraint admits, about whether two concurrent transactions can both succeed and leave the database in a state no serial order could produce, about what a primary key does to your storage, and about whether COMMIT means the transaction survives a power cut. Those disagreements are not exotic. Every one of them is reachable from a first week of ordinary application code.

There is a reason the matrix stopped working. Codd's 1970 paper defined a data model, not a product, and left every implementation question open 1; SEQUEL, four years later, gave that model a language whose explicit design goal was that non-specialists could use it 2. Standardisation came afterwards and codified what vendors had already shipped, which is why the standard is in places a description of a disagreement rather than a resolution of one. Its framework part still defines conformance in terms of a core plus optional features 3, and the parts of the language that matter most to a working application — comparison semantics, isolation, physical design, error behaviour — are exactly the parts where the standard either permits a choice or is silent. Forty years of competition then closed the feature gaps and left the choices in place.

So the features converged and the defaults did not. That is the single fact this article is organised around.

This article compares SQLite, MySQL, PostgreSQL, Microsoft SQL Server and Oracle Database by asking a different question of each of them. Not what can it do, because the honest answer is nearly everything, but:

When your SQL does not say which behaviour you meant, what does this engine assume — and what tells you it assumed something else?

The second half of that question is the one that matters. A difference between engines that produces a parse error is an inconvenience: you find it in the first minute of the first test run and you fix it. A difference that produces a plausible wrong answer is a different kind of object entirely. It ships. It sits in production for two years. It is discovered by a customer, or by a reconciliation nobody wrote, or never.

So the organising device here is a six-rung ladder of loudness: how a given engine announces the answer it picked. The rungs run from the parser rejecting your text before anything runs, down through statement errors, transaction rollbacks and pure cost, to the bottom rung, where nothing at all distinguishes a different answer from the right one. Nineteen questions are put to all five engines, giving ninety-five cells, and every cell gets a rung. The finding that organises the rest of the article is that the rungs are not distributed the way intuition suggests, and that the questions on which the five engines agree most closely are, disproportionately, the quiet ones.

A note on what is measured and what is cited. Nine experiments run in the article's own laboratory section, and all of them execute against a real engine or a deterministic model: the Python standard library ships SQLite, so one of the five can be interrogated directly rather than described. Every number quoted in the prose and the figures comes from that run. Where a claim concerns MySQL, PostgreSQL, SQL Server or Oracle, it is cited to the vendor's own documentation or to published third-party testing, and it is never presented as measured. The distinction is kept explicit throughout, because an article about silent differences that quietly extrapolated from one engine to five would be a poor advertisement for its own argument.

2Five engines on one page

A brief orientation, in the order the article will keep. The five are not peers in any single dimension: two are open-source server engines, two are commercial enterprise platforms, and one is not a server at all.

SQLite

SQLite is a C library that reads and writes an ordinary file. There is no server, no separate process, no network protocol and no configuration; a connection is a file handle inside the calling program. Its authors claim, credibly, that it is the most widely deployed database engine in the world, on the grounds that it ships inside every Android and iOS device, every major browser, and a large fraction of desktop applications 4. Its own documentation is unusually direct about where it does not belong: it competes with fopen(), not with a client-server database, and the discriminator is concurrency and scale rather than data volume 5. It has a test suite with more lines than the library, including tests that simulate power loss and out-of-memory at every allocation 6. Version 3.53 is current at the time of writing; the 3.52 release was withdrawn because features in it were not compatible with earlier releases 7. The measurements in this article ran against 3.45.1.

MySQL

MySQL is the database of the LAMP stack and of a very large share of the web's content-management installations. It is owned by Oracle and distributed under the GPL with a commercial licence alongside. Its distinguishing architectural feature is the storage-engine layer: the SQL parser, optimiser and cache sit above a pluggable interface, with InnoDB as the transactional default 8, 9, 10. Much of MySQL's reputation for looseness dates to behaviour that has since been tightened: strict SQL mode and ONLY_FULL_GROUP_BY are defaults now, not options 11, 12. Some of it is still earned, as the isolation section below shows.

PostgreSQL

PostgreSQL descends from Stonebraker's POSTGRES at Berkeley, whose stated design goal was extensibility: user-defined types, operators and access methods, with the database's own catalogue as the mechanism 13, 14. That decision is still the differentiator. PostGIS, pgvector and the foreign-data-wrapper family are not products bolted on; they are the extension system working as designed 15. It is released annually under a permissive licence 16, with five years of support per major version 17; version 18 is current and 19 is in beta as this is written 18. It has also become the default answer for new projects: the 2025 Stack Overflow survey put it at 55.6% of all respondents and 58.2% of professional developers, roughly fifteen points clear of MySQL 19.

Microsoft SQL Server

SQL Server's differentiator has never been a single engine feature; it is the integration of the engine with a tool chain that most enterprises already own. The 2025 release, generally available in November 2025, continues that line and adds a native vector type, native JSON and change event streaming 20, 21, 22.

Oracle Database

Oracle is the heavyweight, and its distinguishing capabilities are operational rather than syntactic: Real Application Clusters, Data Guard, the undo tablespace, a mature partitioning implementation and a procedural language deeply woven into the engine 23, 24, 25. The naming has moved: Oracle Database 23ai was replaced by Oracle AI Database 26ai, which reports its version as 23.26 and became available in the cloud and on engineered systems in October 2025 and on-premises for Linux x86-64 in early 2026, Enterprise Edition first 26, 27. The installed base is elsewhere: 19c support was extended to 2029 for premier and 2032 for extended, which is why a great deal of production Oracle is still 19c 28. Oracle also remains first in the DB-Engines popularity ranking, a metric weighted towards enterprise mentions rather than developer adoption 29, which is why it and the Stack Overflow numbers appear to disagree: they are measuring different populations.

What the licence buys and what it costs

The commercial split is real and is worth stating plainly, because it drives more architecture decisions than any behaviour in this article. SQLite is in the public domain and has no licence to manage at all. PostgreSQL uses a permissive BSD-style licence with no commercial-use restriction 16. MySQL is dual-licensed: GPL v2 for open-source use, a commercial licence for embedding it in a closed product, with the thread pool and several management features reserved to the Enterprise edition 30. SQL Server and Oracle are licensed per core, with a feature ladder attached to the edition: what is available in Standard against Enterprise decides whether you can use several of the capabilities discussed below, and the SQL Server 2025 release discontinued the Web edition entirely 31.

The practical consequence is that on the two commercial engines a performance problem sometimes has a purchase order as its solution and sometimes does not, and knowing which is an engineering skill specific to those platforms. On the two open-source engines the equivalent skill is knowing which parts of the operational story are not in the box: PostgreSQL ships streaming replication but not automatic failover, and MySQL's answer to the same problem, Group Replication, is in the distribution but has its own consistency and topology rules 32, 33.

SQLite's position is different in kind. It has no server to license, no process to operate and no failover story, and its file format is a published, stable, long-term format that its authors recommend as an application file format in place of a bespoke one 34, 35. Its own documentation maintains a list of the surprising behaviours that follow from its design choices, which is a more useful document than most vendors' release notes 36.

Read that table the way you would read a specification sheet for five cars: it tells you which one to shortlist and nothing about how any of them behaves at the limit. The rest of this article is the limit.

3The ladder

The ladder has six rungs. A rung answers one question: if this engine's answer is not the one your SQL assumed, what tells you?

5the parserthe text is rejected before anything runs
4the statementthe statement fails at run time with an error naming the value or object
3a rollbackthe transaction is aborted and told so: serialization failure, deadlock victim, busy
2the clockthe answer is correct and the cost is paid in latency, space or blocking
1an audita later reconciliation, constraint or test can find it, if someone writes one
0nothinga different answer is returned and no signal distinguishes it from the right one

Two things about the ordering. First, it is not a severity scale, and the colours deliberately invert the usual traffic light. Rung 5 — a parse error — is the best place a difference can live, because it is found by the person who wrote the statement, in the minute they wrote it, at zero cost. Rung 0 is the worst, and it is worst precisely because nothing about the experience of using the engine distinguishes it from correct behaviour. Second, the rung is a property of a pair, not of an engine: it records how loudly this engine announces this answer. An engine can sit at rung 5 on one question and rung 0 on the next, and the interesting engines do.

Each of the nineteen plates below carries the same six fields and a strip of five cells, one per engine, each cell filled with its rung's colour and labelled with its rung number. Reading across a strip tells you how much the engines disagree. Reading its colours tells you whether you will find out.

4I. What a value is

Start with values, because a database is a machine for storing and comparing them, and because the disagreements here are the ones an application programmer meets first and recognises last.

The first plate is the deepest architectural split among the five. Four of them implement a static type system: a column has a type, values are checked against it, and a value that cannot be converted is an error. SQLite implements a dynamic one. A declared type is an affinity, a preference applied when a value arrives, and the value is stored in whatever type survives the attempt 37. The documentation is not coy about it; the behaviour is deliberate, and the STRICT table option exists precisely for authors who want the other semantics 38.

The laboratory measured the consequence. Nine literals were inserted into six declared column types, giving 54 cells. In 19 of them (35.19%) the type that came back out was not the type that went in, and in 16 (29.63%) the value itself changed — the string ' 42 ' becomes the integer 42, the string '3.5' becomes a float, the string '42x' stays text. No cell raised an error. Declaring the same column STRICT turns four of the nine literals into constraint failures, which is the same information delivered four rungs louder.

The practical effect is not that SQLite is wrong. It is that a schema moved from SQLite to any of the other four will encounter, on first load, rows whose stored type contradicts the column's declaration, and a schema moved the other way will silently start accepting them.

The comparison case is worse, because here the five engines split three ways rather than two, and two of the three splits are silent. Consider a product code stored as text and a query written by somebody who remembered it was numeric: WHERE code = 42.

Five engines; three semantics; one statement that is syntactically valid on all of them. Two return an answer with no complaint and the answers are different from each other.

Oracle stores a zero-length string assigned to a character type as NULL, and its own SQL reference states plainly both that this is the current behaviour and that Oracle does not guarantee it will continue 46. Everywhere else the empty string is an ordinary value distinct from the absence of one, which is what the standard requires 47. This single divergence quietly changes the meaning of NOT NULL, of COALESCE, of every WHERE s = '', and of any application logic that distinguishes “the user left the field blank” from “the user never saw the field”. It is not a bug. It is forty years of backward compatibility, and it is invisible until the day the schema moves.

Here, for once, the five agree completely — and the agreement is the trap. Three-valued logic is in the standard, and every engine implements it faithfully: a comparison with NULL is UNKNOWN, UNKNOWN is not TRUE, and so x NOT IN (SELECT y FROM s) returns no rows whenever s contains a single NULL, regardless of what else it contains 47, 48, 51.

The laboratory ran the obvious version of this. A table of ten rows was filtered against an exclusion list containing one NULL and between zero and five real values. NOT IN returned the intended answer in 0 of 6 cases; the identical query written as NOT EXISTS returned it in 6 of 6. Widening the test to twelve NULL-sensitive constructs, 6 of 12 returned something other than the two-valued reading, and none of the twelve raised an error.

Date's 1984 critique of SQL identified this as one of the language's structural defects, and forty years of implementation have made it universal rather than fixed 50. The mitigation is a habit, not a setting: write the exclusion as NOT EXISTS, or make the sub-query column NOT NULL, and know that the engine will never tell you which of the two you are running.

MySQL's default collation for utf8mb4 ignores both case and accents: utf8mb4_0900_ai_ci, where ai is accent-insensitive and ci is case-insensitive 22, 56, 57, 58. SQLite compares bytes, and its NOCASE collation folds the twenty-six ASCII letters and nothing else 37.

The laboratory built 138 distinct identifiers by varying case and diacritics over twenty stems and counted the equivalence classes each rule produces. Binary comparison sees 138 distinct values. ASCII-only case folding sees 61. Full Unicode case folding sees 59. Case- and accent-insensitive comparison sees 20. The same CREATE UNIQUE INDEX statement therefore admits 138 rows on one engine and 20 on another: a spread of 118 rows, 85.5% of the input, with no error raised anywhere in the process. The measurement also confirmed the ASCII limitation directly: of 78 non-ASCII case pairs tested against COLLATE NOCASE, it treated 2 as equal.

Migrating from a case-sensitive engine to a case-insensitive one fails loudly — the load aborts on a duplicate key, which is why this plate puts MySQL and SQL Server at rung 4. Migrating the other way succeeds quietly and leaves you with two accounts where the source system had one. Unicode's collation algorithm is the reason the problem is hard rather than the reason it is inconsistent: the standard defines the mechanism and leaves the tailoring to the implementer 59.

The failure is loud; the reason it happens in production rather than in development is that the two machines were never the same.

5II. What a transaction is

The value questions are about what one statement means. The transaction questions are about what happens when two of them run at once, and this is where the gap between the words in the standard and the behaviour of the products is widest.

Every one of the five supports transactions, and four of the five default to an isolation level that permits results no serial execution could produce. This is not a defect that has been overlooked. It is a deliberate and universal trade, and the 1995 critique that named it is thirty years old 65.

The laboratory implemented a small versioned store and ran six canonical schedules against five isolation policies modelled on the five engines' defaults. The results are unambiguous: read committed implemented with locks, and read committed implemented with snapshots, each leave 5 of the 6 anomalies intact. InnoDB's repeatable read leaves 2. Snapshot isolation as PostgreSQL implements REPEATABLE READ leaves 1, write skew, which is the anomaly snapshot isolation is famously unable to prevent 71. Full serializability leaves 0, at the cost of aborting transactions that would have committed.

Mapped onto defaults: SQL Server ships the first column, PostgreSQL and Oracle the second, MySQL the third, and SQLite the fifth 66, 67, 68, 69, 70. SQLite gets serializability by refusing concurrency: there is one writer at a time, and the second writer is told SQLITE_BUSY rather than being allowed to interleave. The laboratory verified that directly against a real SQLite in write-ahead-log mode: two connections running the classic read-modify-write schedule produced database is locked on the second writer and a final value of 1 rather than a lost update.

What makes this rung 0 for four of the five is that an anomaly is not an error. Nothing is logged. No status code differs. The application receives two successful commits, and the row that should hold 2 holds 1. Bailis and colleagues found, surveying widely used web frameworks, that applications overwhelmingly do not use database transactions to enforce their invariants at all, preferring application-level validations that are unsound under concurrency — which means the database's default is usually the only line of defence, and it is not defending 73.

If Q08 is about the gap between the standard and the products, Q09 is about the gap between the products. REPEATABLE READ is a phrase from the standard. On the five engines it denotes, respectively: nothing at all, because SQLite has no such setting; a hybrid in which plain reads see a transaction-lifetime snapshot and locking reads and updates see the latest committed row 76; genuine snapshot isolation with serialization failures at commit 66; shared locks held to the end of the transaction, with phantoms still permitted 68; and, on Oracle, an error, because the level is not implemented and only read committed and serializable are offered 69.

Jepsen's 2023 analysis of MySQL 8.0.34 is worth citing precisely here, because it went further than the documentation does. Testing with the Elle checker, it found MySQL's repeatable read exhibits G2-item, G-single and lost update, violates internal consistency and monotonic atomic view, and satisfies neither Adya's formal definition nor the ambiguous ANSI one; the same work reported that Amazon RDS MySQL clusters routinely violate serializability at the SERIALIZABLE level 72, 74, 77. The practical summary in that report is the sentence to remember: a MySQL repeatable-read transaction cannot safely read a value and then write it, which is exactly the shape of every object-relational mapper's load-modify-save cycle. A separate bug report from the same work documents a fractured read at the serializable level 78. Kleppmann's Hermitage suite, which predates it by nine years, reached compatible conclusions by hand 75.

The measured consequence in this article's own laboratory is narrower and cleaner: the two columns both entitled repeatable read differ on 2 of the 6 schedules. That is the whole plate. A name in the standard is not a specification of behaviour, and retry logic written against one engine's interpretation will either never fire or fire constantly against another's.

It is worth being precise about why the defaults are what they are, because ‘the vendors chose speed over correctness’ is too cheap an explanation. The vocabulary of degrees of consistency comes from Gray and colleagues in 1976, and it was framed from the start as a menu of trades between concurrency and guarantees rather than as a ladder with one correct rung 79, 80. Serializability at the engine level was expensive under two-phase locking, which is what the standard's authors had in mind, and it stayed expensive until snapshot isolation made a cheaper approximation available. Making that approximation genuinely serializable took another two decades of work: Fekete and colleagues characterised the dangerous structures 71, Cahill and colleagues turned that into a runtime test 81, and PostgreSQL shipped it as serializable snapshot isolation in 2011, which is why PostgreSQL's SERIALIZABLE is serializable and Oracle's, which is snapshot isolation, is not 82.

The generalisation of that literature is that weaker isolation buys availability and throughput, and that the cost is paid in invariants the application must then defend itself 83, 84. The engines have made that trade on your behalf, in a configuration file, using a word from a 1992 standard whose meaning they do not share.

A primary key is a logical constraint. On three of the five it is also a storage layout. InnoDB always clusters the table in primary-key order, and every secondary index stores the primary key as its row locator 99. SQL Server creates a clustered index for the primary key unless told otherwise, with the same consequence 100. Oracle's default is a heap, with index-organized tables as the opt-in 101. The consequence is measurable, and the laboratory measured it. Forty thousand identical rows were loaded into a clustered table with primary keys of five different widths, and one secondary index was built on each. The index costs 199 pages with an 8-byte key, 277 at 16 bytes, 356 at 24, 473 at 36 and 757 at 64 — a factor of 3.80 across that range, against 140 pages for the same index on a heap table whose locator is an 8-byte rowid. The slope is 1.020 index bytes per row per byte of key, which is the locator being stored verbatim, once per row, in every index.

This is the whole content of the widely repeated advice not to use a random 36-character UUID as a primary key on InnoDB or SQL Server. The measurement puts a number on it: 3.38 times the index size of the heap equivalent, per secondary index, before any consideration of insertion order. One caution about extrapolating: the laboratory also tested insertion order directly, loading the same keys ascending and shuffled, and found a difference of −1.02% — a null result. SQLite rebalances across three sibling pages, so the page-split fragmentation that InnoDB documents for random primary keys does not appear in this engine. The locator cost is measured here; the fragmentation cost is documented elsewhere and is not.

Every engine that lets a reader and a writer run at the same time must keep the old version of a row somewhere until no reader needs it. There are two places to put it, and the choice determines which resource runs out and what happens when it does.

PostgreSQL puts the new version in the table and leaves the old one there as a dead tuple, to be reclaimed by autovacuum once no snapshot requires it 85, 87. Oracle, InnoDB and SQL Server write the before-image to a separate structure — an undo tablespace, an undo log, a version store in tempdb — and update the row in place 25, 106, 107. The systematic comparison of these designs is Wu and colleagues' evaluation of multiversion concurrency control, which treats version storage as one of four independent design decisions 108.

The laboratory modelled both against the same workload: five thousand rows, one reporting transaction holding a snapshot, and a stream of single-row updates. The result is a clean equivalence and a sharp difference. The undo buffer must retain exactly one before-image per update since the oldest live snapshot, which is precisely the number of dead versions the append-based engine cannot reclaim: the space requirement is identical. What differs is the behaviour at the boundary. The append engine keeps growing — at a hundred thousand updates against five thousand rows, a full scan reads 21 times the live data. The undo engine fails the reader: at half the required capacity, 99.36% of the rows the reporting transaction asked for could no longer be reconstructed.

That is ORA-01555, snapshot too old, in one number, and it is the reason the two designs feel so different in operation despite storing the same quantity of history. One of them degrades; the other one stops. OpenAI's published account of running ChatGPT on a single unsharded PostgreSQL primary is candid about which side of that trade they are on: updating one field copies the whole row, producing write amplification, read amplification as queries scan dead tuples, table and index bloat and complex autovacuum tuning — and their response was to move write-heavy shardable workloads off PostgreSQL entirely rather than to fight it 104, 105.

All five default to durable commits, and all five expose a parameter that makes them not. The rung is 0 across the board because the parameter has no effect a client can observe: the commit returns success at the same speed either way, and the difference appears only when the machine loses power 109, 110, 111, 112, 113.

The laboratory quantified the exposure. At a workload committing 8,000 transactions per second, with twenty thousand simulated crashes at uniformly random instants: flushing at every commit loses nothing; flushing every 10 ms loses 40.1 acknowledged transactions on average and 88 at the 99th percentile; every 100 ms, 399.3 and 808; every second, 3,994.0 and 7,933. Every one of those transactions had already returned success to a client.

The reason the parameter exists at all is that the alternative is a synchronous write to stable storage per commit, and that write is the single most expensive operation in the system. At a 1 ms fsync a single-threaded committer is capped at 1,000 transactions per second, so reaching 8,000 requires batching 8 commits per flush; at 5 ms it requires 40. Group commit is how every one of these engines resolves it, and the real choice is not durability against speed but durability against batching latency. It is also worth knowing that the storage underneath may not honour the contract: fsync failures have historically been reported once and then forgotten by the kernel, a class of bug studied systematically by Rebello and colleagues, and power-fault behaviour of consumer drives has been shown to violate it outright 114, 115, 116.

Underneath all five sits the same recovery design. Write the change to a log before writing it to the data pages, flush the log at commit, and reconstruct after a crash by replaying committed transactions and undoing uncommitted ones. ARIES is the canonical description and the direct ancestor of the mechanism in every engine here 117. The differences between them are entirely in where the log lives, how often it is flushed and how far behind a copy of it is allowed to be — which is to say, in the two plates on either side of this paragraph.

The laboratory put twenty predicate forms to a real engine with five indexes and read the plan for each. Eleven reached an index; nine scanned the table. The nine are the familiar ones and the reason they fail is always the same: the index stores the column's value, and the predicate asks about something else. lower(name) = ..., name || '' = ..., qty + 0 = 42 and substr(ts,1,7) = '2026-01' all scan, while the equivalent restrictions written against the bare column all seek. Rewriting the substring test as a half-open range on the same column turns a full scan into an index search on identical data.

Two of the twenty deserve individual attention. The first is the type-mismatch case from Q02, which on SQLite produces an indexed search returning the wrong rows, on MySQL and SQL Server a correct answer obtained by a full scan and reported in the plan as an implicit conversion 128, and on PostgreSQL and Oracle an error. One predicate, three outcomes, and only the error is loud.

The second is the prefix LIKE. It scanned, which surprises people who know that a prefix pattern is normally indexable. The reason is collation: SQLite's LIKE ignores case for ASCII, and the index was built with the default binary collation, so the index ordering does not match the predicate's notion of equality 130. Adding a single index declared COLLATE NOCASE changed the plan for the identical query to an index search on a bounded range. The same interaction between collation and index usability exists on all five engines, and it is the reason Q06's quiet disagreement about string equality has a performance shadow as well as a correctness one.

There is a second half to this question that no single plate captures, because it is about reuse rather than about one statement. All five engines cache work between executions, and they cache different things. SQL Server caches the plan and, by default, reuses a plan compiled for the parameter values of the first execution — parameter sniffing, which is a large net win and an occasional catastrophe when the first execution was atypical 128, 129, 130.

The consequence for a comparison is that identical SQL over identical data can be fast on the first run and slow on the thousandth, on one engine only, for reasons that have nothing to do with the query. This is the single most common cause of the complaint that a database ‘got slow overnight’, and it is a rung 2 problem on every engine: correct, expensive, and visible only to somebody who reads plans.

The general problem — that the optimiser's estimate of a plan's cost is derived from statistics that may be stale, skewed or missing — is older than any of these products 125, 126, and the empirical position is not encouraging: Leis and colleagues, testing cardinality estimation on a real-world workload, found errors of several orders of magnitude routine and traced most bad plans to them 127. The practical consequence for a comparison article is that ‘which engine is faster’ is not a well-formed question, and ‘which engine tells me why it was slow’ is.

This is the pattern that runs through the whole article, and the dialect plate is its clearest instance because the two classes are so cleanly separated. Where engines disagree about form, the parser catches it. Where they disagree about meaning, nothing does.

9What is not in the comparison

Five engines is a working set, not a census. Four omissions are worth naming, because each occupies a position none of the five does.

MariaDB forked from MySQL in 2009 and has diverged steadily: different optimiser, different clustering story, different system-versioned tables, and a licence and governance model designed to be independent of Oracle. For the questions in this article it answers mostly as MySQL does, which is why it is not a sixth column; for a migration it is no longer a drop-in replacement, and treating it as one is a common error.

IBM Db2 belongs in the same conversation as Oracle and SQL Server on capability, mainframe lineage and cost, and remains widespread in banking and insurance. It is omitted because a fifth column of enterprise defaults would have added length without adding a distinct answer to most of the nineteen questions.

DuckDB is to analytics what SQLite is to transactions: an in-process library with no server, a columnar engine, and a deliberate focus on scanning rather than on concurrent writes. It is the clearest recent demonstration that the embedded model is not a compromise but a different design point, and the question it answers — what does one analyst's laptop do with ten gigabytes — is not one any of the five is optimised for.

Distributed SQL systems — CockroachDB, TiDB, YugabyteDB, Spanner and the cloud-native offerings such as Aurora and AlloyDB — keep the relational interface and replace the storage and transaction layer with a replicated, sharded one, generally at serializable or snapshot isolation and generally at the cost of a consensus round trip per commit 120, 134. They change the answers to Q15, Q16 and Q17 substantially and change the answers to the value questions hardly at all, because those are inherited from whichever dialect the system chose to be compatible with. A system that is wire-compatible with MySQL inherits MySQL's collation default; one compatible with PostgreSQL inherits its type strictness. The plates in group I travel with the dialect.

It is also worth noting that a managed service can change a default out from under the comparison. Azure SQL Database enables read-committed snapshot isolation by default where on-premises SQL Server does not 21; Jepsen found RDS MySQL clusters violating serializability at a level where the engine alone does not 74. The engine's documentation is the beginning of the answer, and the provider's documentation is the rest of it.

Three things fall out of the ledger, and none of them is the thing a feature matrix would have suggested.

First, the modal outcome is silence. Rung 0 is the largest single category, with 39 of the 95 cells, and it is larger than rungs 3, 4 and 5 combined. The engines are not reticent because they are badly built; they are reticent because in almost every one of these cases both behaviours are defensible, the standard either permits both or is silent, and there is no error to raise. Nobody is wrong. That is the problem.

Second, loudness rises with disagreement, and the exceptions are the whole problem. Counting distinct behaviours per question against the mean rung gives a correlation of +0.56: broadly, the more ways the engines differ, the more likely something says so. That is reassuring until you look at the residuals, and the cleanest pair is a controlled comparison. Q19, dialect coverage, has four distinct behaviours and a mean rung of 5.0: every difference is caught, immediately, by the parser. Q08, the default isolation level, also has four distinct behaviours and a mean rung of 0.6: almost nothing is caught by anything. The two questions disagree by the same amount. They differ in what the disagreement is about. A parser can check the form of a statement for free, so it does; no component checks whether the answer means what the author thought, so none does.

There is a fourth observation that the ledger does not show, because it sits between rows. Several of the quiet cells are quiet in one direction only, and the direction is set by which engine has the stricter rule. A stricter destination converts a silent difference into a loud one at load time: the case-insensitive collation rejects the duplicate, the static type system rejects the string, the one-NULL unique index rejects the second NULL. A looser destination accepts everything and defers the discovery indefinitely. Whenever there is a choice about which way to run a migration first, running it towards the stricter engine buys a cheap audit of the data you already have.

Third, the engine you are moving away from is the one that matters. Every rung in this article is directional. Case-folding collation errors loudly when you migrate towards it and silently when you migrate away. Oracle's empty string is invisible until it meets a NOT NULL written elsewhere. PostgreSQL's aborted-transaction state breaks code written for MySQL and not the reverse. A migration plan built from a feature matrix will list the features present at the destination; the risk is in the defaults that differ, and those do not appear on any matrix because they are not features.

12Choosing

The practical question underneath all of this is still which engine to use, so here is a direct answer, offered as one reading of the evidence rather than as a ranking.

For a new server-based application with no constraint pulling elsewhere, PostgreSQL is the default choice, and the reasons are the ones this article measured rather than the ones usually given. Its type system refuses rather than guesses. Its REPEATABLE READ is genuine snapshot isolation and it tells you, with a serialization failure, when it cannot proceed. Its DDL is transactional. Its dialect is the closest of the five to the standard. The costs are real and specific: heap-only storage means bloat under write-heavy update workloads, and a process per connection means a pooler is not optional 104, 105, 121.

Choose MySQL when the surrounding ecosystem is built on it — WordPress, a large existing estate, a team fluent in it — and then read the isolation section again and decide deliberately whether to run at READ COMMITTED with explicit locking reads, or at SERIALIZABLE, or to accept that a load-modify-save cycle needs SELECT ... FOR UPDATE 74.

Choose SQL Server when the organisation already runs on Active Directory, .NET and Power BI, in which case the integration is worth more than any engine-level difference in this article, and turn on read-committed snapshot isolation early, before an application has been written that depends on readers blocking writers 21.

Choose Oracle when the requirement is one of the things only Oracle does at that maturity: Real Application Clusters, Data Guard's protection modes, decades of partitioning and workload-management machinery, or an application that is certified against it and nothing else 23, 24. The cost is the licence and the expertise, and both are substantial.

Choose SQLite far more often than most teams do. Its own guidance is the right test: it is a competitor to fopen(), and the question is concurrency rather than size 5. For a single-writer workload, a desktop or mobile application, a test fixture, an on-disk cache or an application file format it is not a compromise but the correct engineering answer 35. Its defaults are the strictest of the five on isolation and the loosest on typing, and STRICT tables fix the second of those in one word.

Checking the six defaults

The assertion suggested below is short enough to be worth spelling out, because each of these is a one-line query and none of them is in anybody's test suite. Isolation level: SHOW TRANSACTION ISOLATION LEVEL on PostgreSQL, SELECT @@transaction_isolation on MySQL, DBCC USEROPTIONS on SQL Server. Collation: SHOW SERVER_COLLATION, SHOW VARIABLES LIKE 'collation%', SELECT SERVERPROPERTY('Collation'), SELECT * FROM nls_database_parameters. Durability: SHOW synchronous_commit, SELECT @@innodb_flush_log_at_trx_commit, PRAGMA synchronous. Read-committed snapshot on SQL Server: is_read_committed_snapshot_on in sys.databases. Replication mode: whether a synchronous standby is named, whether semi-synchronous is loaded, which Data Guard protection mode is in force 21, 24, 66, 67.

Two of the nineteen questions cannot be asserted this way and have to be tested with data instead. Whether the empty string is NULL, and whether a second NULL fits in a unique column, are answered by inserting one row and looking. A schema-validation test that does exactly that, once, at deployment, would have caught most of the migration failures this article describes.

Whichever you choose, the operational advice that follows from the ledger is short. Write down the six or seven defaults on which your application actually depends — isolation level, collation, durability, replication mode, DDL transactionality, statement-error behaviour — and assert them in a test rather than assuming them. They are all interrogable at run time. None of them will announce itself when it changes.
