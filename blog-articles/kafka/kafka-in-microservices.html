1The question: where is the commit?

Every account of Apache Kafka in a microservice architecture starts from the same picture: services that used to call one another now publish and consume events through a shared, durable log 1–3. The picture is right, and it hides the part that decides whether the system is correct. A log gives every service an ordered, replicated append and a position to read from 4,5. A microservice pattern nearly always needs something more: that an event and the state change it describes happen together, that a consumer’s side effect happens once, that a business process either finishes or is undone. None of those is an append. Each is bought from some atomic write, and the useful question to ask of any pattern is where that write is.

This article asks the question of the eleven ideas in its brief (event-driven architecture, asynchronous communication, service decoupling, event notification, event-carried state transfer, event sourcing, CQRS, the saga, the transactional outbox, idempotent consumers and distributed workflows) and of the thirteen Kafka mechanisms they are built from. Each of the twenty-four is set out as a numbered plate with the same four fields: what it promises, the write it rests on, where a repeated record dies, and how it breaks. Each plate carries a small gauge, the commit bracket, that draws the answer: a rung strip across the top, three lanes for the producing service’s database, the Kafka log and the consuming service’s database, a bracket over whichever lane the commit covers, and dashed red arrows for every crossing that the commit does not reach.

The answer is placed on a six-rung commit ladder. A rung is defined by the widest-scope atomic write that the pattern’s own canonical description relies on for its correctness claim. C0 is nothing at all. C1 is one append to a replicated partition. C2 is the producer session, inside which the broker deduplicates retries by sequence number. C3 is a Kafka transaction, which makes writes to several partitions and a consumer group’s offsets atomic. C4 is one service’s own database transaction. C5 is the absence of any commit spanning the work, with compensation in its place. C1 to C3 are inside Kafka; C4 and C5 are not.

A second axis records where a repeated record is neutralised, because every crossing between two systems is at-least-once unless something on the far side absorbs the repeat 6,7. The broker can absorb it (K), as the idempotent producer does. A keyed store can (S), by refusing a key it has already seen or by upserting on the key. A business process can (B), by compensating or by triage. Or nothing does (N), and the repeat, or the loss, passes through.

The census in the closing ledger, computed by lab experiment E9, gives a plain result. Of the eleven items of the brief, none rest on Kafka’s own exactly-once machinery and none rely on the broker to absorb a repeat. Six promise more than an ordered append, and all six buy their commit outside Kafka: five from one service’s local transaction, the saga from no commit at all. The four plates whose repeats the broker does absorb are Kafka’s own mechanisms. This is not a criticism of Kafka. Its design documentation states that exactly-once delivery to systems other than Kafka requires those systems to cooperate, and it recommends the simplest form of cooperation, which is to store the consumer’s position in the same place as its output 4. The patterns in the brief are, very nearly all of them, ways of doing exactly that.

Two cautions about the coding. The rung is a property of a pattern as it is canonically described, not of every implementation of it: event-carried state transfer can be fed from an outbox, which moves its producing side to C4, and its plate says so. The rule takes the pattern’s own promise and asks what that promise needs. And the absorber is where a repeat dies under the pattern, not where it could die if someone added a mechanism: the dual write is coded N because nothing in it catches a lost or phantom event. A reader who codes a plate differently can recompute the census from the lab script, which reads the same table this article is built from.

The numbers in the text come from a standard-library Python lab of nine deterministic experiments, printed in full in the final section. Its fault parameters are illustrative. The experiments compare mechanisms under one fault model, so the zeros and the ratios carry the argument, not the absolute rates. Version facts are stated as of October 2026, when Apache Kafka 4.3.1 is the newest release on the 4.3 line and 4.2.2 the newest patch on 4.2 8,9. The listings target the 4.3 Java clients, and the API names they use were checked against the 4.3 client sources.

2What the log gives you

Kafka’s unit of storage is the partition, an append-only sequence of records numbered by offset. A topic is a named set of partitions spread over brokers, and a record with a key is sent to the partition chosen by hashing the key, so every record for one key lands in one partition 5,10. Kafka promises that any consumer of a partition reads its records in exactly the order they were written 5. It promises nothing about order across partitions, which is the right promise for a distributed log: a total order over everything would require every write in the system to pass through one place 11.

The key therefore carries the architecture’s ordering decisions. A service that keys order events by order id gets per-order ordering and nothing more; one that keys them by customer id gets per-customer ordering and a different set of hot spots. Domain-driven design’s aggregate is the usual answer to which key to choose, because an aggregate is defined as the boundary inside which invariants hold and changes must be serialised 12,13. Lab experiment E4 ports Kafka’s murmur2 partitioner bit for bit and measures the two costs of that choice. With uniform traffic, 20,000 keys spread over 12 partitions with the busiest partition at 1.016 times the mean. With Zipf-distributed key popularity, the shape that real request streams usually take 14, the busiest partition carries 2.752 times its share at s = 1, and a consumer group can use only 4.36 of its twelve partitions however many consumers it runs. The second cost is permanence. Adding partitions changes the hash modulus, and growing from 12 to 16 partitions remapped 75.16% of the keys in the lab; doubling to 24 remapped 50.35%. Per-key order holds across that change only if producers are drained first.

Replication and what committed means

Each partition is replicated, and a record counts as committed only when every replica in the in-sync set has applied it. Kafka then guarantees that a committed record is not lost while at least one in-sync replica survives 4,15. The producer chooses how much of that to wait for with its acks setting, and the topic sets min.insync.replicas, the smallest in-sync set allowed to accept a write when the producer asks for acks=all 4,16. With three replicas and a minimum of two, a single broker failure costs neither availability nor durability. The documentation’s own estimate is that waiting for commit takes on the order of ten milliseconds 4.

Since Kafka 4.0 the cluster’s metadata lives in KRaft, a Raft-derived quorum inside Kafka itself, and ZooKeeper is gone 17–19. The same release previewed eligible leader replicas, a subset of the in-sync set guaranteed to hold everything up to the high watermark and therefore safe to elect 20. None of this changes the rung. Replication makes the append durable; it is still one append.

The producer listing spells out two defaults on purpose. Since Kafka 3.0 a producer enables idempotence and waits for all in-sync replicas unless a conflicting setting is given 21,22. Teams that copied older tuning advice still set acks=1, or turn idempotence off for throughput, and in doing so step the producer down from C2 to a weaker C1.

Consumer groups, offsets and rebalancing

Consumers that share a group id divide a topic’s partitions among themselves, one owner per partition, and record their progress as committed offsets in an internal topic 4. The order in which a consumer processes and commits decides its failure semantics, as the documentation sets out: commit before processing and a crash loses records; process before committing and a crash redelivers them 4. There is no third order. Kafka 4.0 made the consumer group protocol of KIP-848 generally available, moving assignment onto the broker and replacing stop-the-world rebalances with incremental ones; consumers opt in with group.protocol=consumer, and 4.3 logs a recommendation to leave the classic protocol behind 9,17,23,24. Faster rebalancing narrows the window in which partitions move, but a partition that moves after processing and before commit is still redelivered to its next owner. The group protocol is about availability. The commit is about correctness.

Compaction and retention

A topic can keep records by time or size, or it can keep them by key. Under compaction Kafka guarantees to retain at least the last record for every key, never to reorder records, and to show every record to a consumer that keeps up with the head of the log; a record with a null value is a tombstone that eventually deletes its key 4. Compaction turns a topic into a replicable table, which is what event-carried state transfer and Kafka Streams’ changelogs both need. It also absorbs repeats in a weak, delayed sense, since two writes of the same key eventually collapse into one. Tiered storage, which moves older segments to object storage, changes what retention costs rather than what it means 25.

3Making the append exact

Two kinds of failure turn one intended append into something else. A producer whose request times out does not know whether the write landed; if it retries, a write that did land is duplicated, and if several requests are in flight, a retried batch can land behind batches that were sent after it 4,22. Kafka 0.11 answered both with the idempotent producer. The broker assigns each producer an id and accepts a batch only if it carries the next sequence number for its partition, acknowledging duplicates without appending them and rejecting gaps 4,26,27. The producer configuration source still states the conditions that come with this: idempotence requires acks=all, retries enabled and at most five requests in flight per connection, and with it ordering is preserved for any allowed value 22.

Lab experiment E3 measures what that buys. Over 100,000 batches with a one per cent request failure rate, a non-idempotent producer with five requests in flight appended 484 duplicate batches and 402 batches out of order. With one request in flight it kept order but still appended 524 duplicates, since a lost acknowledgement looks exactly like a lost write. With idempotence on, both counts were zero, for 2.08% extra requests against 0.98% for plain retries.

The session is the limit. Sequence numbers belong to a producer id; a producer that restarts gets a new id unless it is transactional, and an application that sends the same business event twice, because its own caller retried, sends two records with two valid sequence numbers. The broker deduplicates the network’s retries, not the application’s.

Transactions

KIP-98 also introduced transactions. A producer with a transactional.id can write to several partitions atomically and can add the consumer group’s offsets to the same transaction, so that a read, the writes it causes and the advance of the read position commit or abort together 4,26. Consumers that read with isolation.level=read_committed see only committed transactional records 4. A new instance that registers the same transactional.id fences the old one, which is what stops a paused zombie from committing late, and KIP-447 tied that fencing to consumer group metadata so that one producer per instance suffices 4,28. Kafka Streams is built on this read-process-write cycle and enables it with a single setting, processing.guarantee=exactly_once_v2 29,30.

One detail in the listing is easy to miss and is stated in the documentation: aborting a transaction does not move the consumer back. The application has to seek to the last committed position itself, or it will skip the records whose output it just discarded 4.

The protocol has had a hard few years. Jepsen’s 2024 analysis of Bufstream, a Kafka-compatible system, reported write loss, aborted reads and torn transactions in Kafka’s transaction protocol itself, affecting Kafka and presumably every compatible implementation; the problems were unresolved when the analysis was published 31. The vendor reported that Kafka’s maintainers expected the fix to come through KIP-890 32, whose second phase shipped in 4.0. With transaction version 2 the producer epoch is bumped on every transaction, so that a delayed write from one transaction cannot be counted into the next 17,33,34, and 4.2 tightened epoch validation on transaction markers again 35. The lesson for an architect is not to avoid transactions. It is to know their scope.

Where exactly-once ends

That scope is the cluster. The design documentation says plainly that exactly-once delivery is available when reading, processing and writing Kafka topics, and that exactly-once delivery to any other destination needs that destination’s cooperation 4. A microservice is precisely a thing with another destination: its own database, an email gateway, a payment provider. Figure 5 draws the consequence. The middle of the picture can be one transaction. The two crossings, from a service’s database into Kafka and from Kafka into another service’s database, are at-least-once whatever Kafka does, and each is made safe by a transaction on the far side of the crossing.

4Event-driven, asynchronous, decoupled

The architectural case for Kafka in microservices is usually made with three words from the brief: event-driven, asynchronous, decoupled. Each names a real property. Each is easy to overstate.

In an event-driven architecture a service announces that something has happened and does not know who is listening 3,36. The inversion is the point. The producer of a fact stops owning the list of its consequences, so adding a consumer is a deployment rather than a change to the producer. Lewis and Fowler’s early description of microservices already argued for keeping intelligence in the services and the transport between them simple 37. Fowler’s 2017 essay then separated four things that travel under the event-driven name, namely event notification, event-carried state transfer, event sourcing and CQRS, and argued that running them together is the main source of confusion 36; this article keeps them apart for the same reason. As a commit question, event-driven architecture on its own claims only that a published fact is appended durably and can be read in order. It says nothing about whether the fact is true, which is the dual-write problem two sections on.

Asynchronous communication is a property of the conversation, not of the transport. A request sent as a record, with a correlation id and a reply topic, frees the caller’s thread but not its business logic: the caller still waits for an answer, now without a deadline enforced by a socket 38. Replies can arrive late, twice, or after the requester has given up, so the requester has to keep a table of open correlation ids and drop anything it does not recognise. That table is the keyed store that absorbs the repeat.

Decoupling has a measurable core, which is temporal. A service that must call five others synchronously to answer a request is up only when all six are. Experiment E5 puts that at 97.427% for dependencies that are each up 99.5 per cent of the time, against 99.9 per cent for the service alone, and the request’s 99th-percentile latency rises with the slowest member of the fan-out, from 79.8 ms with one dependency to 111.7 ms with five 39. A service that answers from a local replica kept current by events is up whenever it is. What it pays instead is staleness. In the same experiment the replica lagged its source by a median of 80 ms, but by more than a second for 0.261% of reads, nearly all of them during consumer pauses.

Decoupling in time is real. Decoupling in meaning is not: the consumer still depends on the producer’s schema, its choice of keys and the semantics of its fields, which is why schema evolution rules matter as much as broker configuration 40,41.

5What an event carries

What a record carries decides which of Fowler’s four patterns it serves. An event notification carries little more than the fact and an identifier, such as OrderPlaced for order 42, and consumers that need detail call back to the source 36. Notifications tolerate repeats in a way that is easy to overlook: the callback fetches current state, so handling a notification twice fetches the same state twice. They are also the pattern most often published by a dual write, since a thin message seems too cheap to deserve an outbox, and the callback quietly recouples the consumer’s availability to the source.

Event-carried state transfer puts the state in the record, so that consumers can keep their own replica and never call back 3,36. In Kafka the natural carrier is a compacted topic keyed by entity id, which a new consumer reads from the beginning to build its replica and then follows 4. Experiment E8 shows the scale of the saving: a state topic with 50,000 keys that had received 2,001,109 updates kept 2.50% of its records after compaction, so a new replica bootstraps 40.0 times faster than one that replays the full history. The replica absorbs repeats by upserting on the key. What it cannot do unaided is tell an old update from a new one when the two arrive in the wrong order, which brings in the plate on versions below.

6The dual write and its two cures

The most common correctness bug in Kafka-based microservices is a pair of statements: update the database, then publish the event. Each succeeds on its own. Between them is a window in which a crash, a deploy or a failed publish leaves the database changed and the event unsent, and no retry inside the service can reach that window, because the process that would have retried is gone. Reverse the order and the failure becomes a phantom: an event announcing a change that then rolled back 47–49. Laigner and colleagues’ study of open-source microservice systems and of practitioners found consistency logic of this kind written by hand in the application layer, and argued that the underlying problems cannot be solved by software engineering practice alone 50.

Experiment E1 runs both orders, and both cures, under one fault model. Committing and then publishing without retries lost 166.0 events per 100,000 operations. Adding idempotent retries removed 69.0% of those losses and left 51.5, which is the crash window itself. Publishing first produced 463.0 phantom events per 100,000. The outbox and log-based change data capture produced neither losses nor phantoms, only duplicates (113.5 and 141.0 per 100,000), which consumers downstream can absorb.

The transactional outbox

The outbox removes the second write. The service inserts the event into an outbox table in the same local transaction as the state change, and a separate relay moves committed rows into Kafka 47,48. The commit is the database’s. The relay is at-least-once, because it can publish a row and die before recording that it did, so every outbox event carries an id that consumers use to discard repeats. Debezium’s outbox router reads the table through change data capture, puts the row’s id into a record header for exactly that purpose, uses the aggregate id as the record key so that each aggregate’s events stay in order, and expects the table to be written by inserts only 44.

Change data capture

Log-based change data capture goes one step further and makes the database’s own commit log the source of events, with no application write at all 51,52. It is the cheapest way to obtain a perfectly consistent stream of changes, and the most dangerous way to publish an interface: a raw change event exposes a table’s columns, so a schema migration becomes a breaking change for every consumer. An outbox read through CDC is the usual compromise, with CDC as the transport and the outbox table as the contract. Kafka Connect source connectors can take part in exactly-once delivery into Kafka 53,54, which removes the connector’s own duplicates but not the need for consumers to tolerate replays after a restore.

7Idempotent consumers

Every pattern that crosses out of Kafka ends at a consumer that does something: writes a row, charges a card, sends an email. Because the crossing is at-least-once, the consumer will sometimes do it twice. An idempotent consumer is one for which doing it twice has the same result as doing it once 7,58. Hohpe and Woolf catalogued the idea as the Idempotent Receiver two decades ago 38, and what has changed since is mostly vocabulary.

The difficulty is that idempotence has to be recorded somewhere, and experiment E2 shows that where matters more than whether. A consumer that committed offsets after processing had on average 50.3 records redelivered per failure, half the commit interval, and every redelivery repeated its effect: 4,879 duplicate effects over 200,000 records. Committing before processing removed the duplicates by losing 4,168 records instead. A dedupe table written in its own transaction after the effect removed 99.12% of the duplicates and left 43, exactly the failures that landed between the effect and the key. Writing the dedupe key in the same transaction as the effect left none, and so did storing the consumed offset in the sink beside the effect.

Two practical rules follow. The dedupe key must live at least as long as a record can be redelivered, which in practice means the topic’s retention plus any replay the team might run, not the commit interval. And the effect must be inside the transaction: a database write qualifies, a call to a payment provider does not. For external effects the consumer passes an idempotency key to the provider and relies on the provider’s own store, which is the same pattern one hop further out.

The second zero in E2 is the arrangement the Kafka documentation itself recommends 4, and it deserves a listing of its own. The consumer stores its position in its own database, in the same transaction as the read model it maintains, and on assignment seeks to that position rather than trusting the group’s committed offset. Redelivery then shrinks to the single record that was in flight (48 records in the experiment, against 4,879 for offset-only commits), and a replay becomes a deliberate seek rather than an accident.

8Event sourcing and CQRS

Event sourcing stores events as the system of record and derives current state by replaying them 59,60. It is tempting to treat a Kafka topic as the event store, and for one reason it rarely works: appending to an aggregate’s history needs a conditional write, append only if the history is still at the version I read, and Kafka has no conditional append per key. Two instances that both loaded order 42 at version 7 can both append version 8. The usual answers are a database table whose primary key enforces the version, or a single writer per aggregate guaranteed by partition ownership 13,52. The first is a C4 commit. The second rests on an argument about consumer group ownership that has to hold through every rebalance and every zombie, which is the argument fencing exists to make.

CQRS separates the model that accepts commands from the models that answer queries, and lets the read models be rebuilt from events 60,61. CQRS’s characteristic failure is not loss but surprise. A user changes something and the screen does not show it, because the query read a projection that had not yet caught up. Kafka Streams is the one place in this census where state and output share a Kafka transaction. A Streams application keeps its state in local stores backed by changelog topics, and with exactly_once_v2 the changelog writes, the output records and the input offsets commit together 29,30. That is a genuine C3, and it stops at the edge of the topology. A processor that calls a web service or writes to a database is outside the transaction, and the dead-letter support that 4.2 added to Streams’ exception handlers routes such failures somewhere; it does not make them atomic 35,64.

9Sagas and distributed workflows

A business process that spans services cannot have one commit, so it has many. Garcia-Molina and Salem defined a saga in 1987 as a long-lived transaction written as a sequence of ordinary transactions, each paired with a compensating transaction that semantically undoes it, with the guarantee that either the whole sequence completes or its completed prefix is compensated 65. Microservice practice adopted the idea with little change 47,66,67. On the commit ladder a saga is C5: no atomic write spans the work, and failure is absorbed by business logic.

Sagas take two shapes 41,47. In a choreographed saga each participant reacts to the previous step’s event and publishes its own, and nobody holds the state of the whole process. In an orchestrated saga one service holds an explicit state machine, sends commands to the others and waits for their replies. Experiment E7 ran 100,000 order sagas with business rejections possible at the payment, stock and shipping steps. 88,466 (88.47 per cent) completed; each of the others needed on average 1.64 compensating transactions. Choreography used 4.916 messages per saga and orchestration 9.832, exactly twice as many by construction, since every event becomes a command and a reply. What orchestration buys with those messages is one place where the saga’s state is written down, which is where an operator looks when a saga is stuck.

The orchestrator sketch shows how much of a C5 pattern is made of C4 pieces. Every reply is handled in one local transaction that locks the saga row, ignores replies it has already seen, saves the new state and enqueues the next command through the outbox. Compensation is the only part of the saga that is not a local commit, and it is the part the business has to design.

The cost both shapes share is isolation. Between a step and its compensation, other transactions can see the intermediate state. In E7, 5.55% of all sagas exposed a payment hold that was later released, for a median of 39.7 ms each; for a credit check, that is a customer refused because of an order that never happened. Compensation is also not undo: an email cannot be unsent, and a refund is not the absence of a charge 68,69. Practice adds countermeasures, such as semantic locks that mark records as pending, commutative updates and rereading values before the step after which the saga cannot turn back, and each of them is a design decision rather than a mechanism 47. Because every message in a saga crosses a service boundary, every participant must also be an idempotent consumer: with duplicate delivery at one per cent per message, E7 counted 50.4 duplicate deliveries per thousand sagas, each a second reservation, refund or shipment if the participant is not idempotent.

Durable workflow execution

Durable execution engines such as Temporal take the orchestrator one step further. The workflow is ordinary code, and the engine records each decision and each activity result in an event history, so that a crashed workflow is rebuilt by replaying its code against that history, with recorded activity results reused rather than recomputed 70. The condition that makes replay work is that workflow code is deterministic. Activities, which perform the side effects, are retried on failure, so they must be idempotent. The commit is the engine’s own persistence of the history, a C4 commit inside a service built for the purpose, and the repeat dies in the activity’s keyed store. Kafka usually sits at the edges of such a system, starting workflows from events and publishing their outcomes, rather than inside it.

10When processing fails

Some records cannot be processed. A consumer that retries a poison record forever stops its whole partition, since order is per partition and nothing behind the record can be delivered. The established answer is to move the record aside, to a retry topic consumed after a delay and finally to a dead-letter topic for inspection, which are Hohpe and Woolf’s dead letter and invalid message channels 38. Kafka Streams gained built-in dead-letter support in its exception handlers in 4.2 35,64. The move has two costs. It breaks per-key order, because later records for the same key overtake the one set aside. And unless the move and the offset commit share a transaction, a crash can duplicate the record into the dead-letter topic or skip it. What finally absorbs a dead letter is a person or a business process, which is why the plate is coded B.

Kafka 4.2 declared share groups, the queue semantics of KIP-932, ready for production after early access in 4.0 17,35,71. A share group lets many consumers take records from the same partition, acknowledges each record individually and counts deliveries, so that a record released by a failing consumer returns to the pool and a record that fails too often can be rejected for good 71. The 4.2 release added a RENEW acknowledgement for records that need longer than the acquisition lock allows 35. Share groups give up per-key order in exchange for parallelism beyond the partition count, which experiment E4 shows to be the binding limit under skewed keys. They do not change the rung. An acknowledgement is not part of the consumer’s side effect, so a consumer that dies after the effect and before the acknowledgement has its record redelivered to another member. Making share-group acknowledgements part of a Kafka transaction is proposed in KIP-1289, which is still under discussion 72.

Read by rung, the census separates cleanly into what Kafka gives and what the brief asks for. The thirteen supporting mechanisms sit mostly at C1, with the idempotent producer at C2 and transactions and Streams at C3, and four of them absorb repeats in the broker. The eleven items of the brief sit at C0, C1, C4 and C5, and never at C2 or C3. Every item whose promise exceeds an ordered append, which is to say event sourcing, CQRS, the outbox, the idempotent consumer, durable workflows and the saga, finds its commit in a service’s own database or in compensation. Read by absorber, the brief relies on keyed stores for eight items, on business logic for one, and on nothing for two; those two, event-driven architecture and decoupling, are architectural properties rather than mechanisms, and inherit whatever their parts provide.

As a classification, rung and absorber together distinguish 243 (88.0%) of the 276 pairs of plates, against 227 (82.2%) for the five families the plates are grouped in, and they occupy ten of the 24 possible cells. The ladder is not a better taxonomy of Kafka than the usual one. It answers a different question, and the ten occupied cells are its answer.

Three consequences follow for design reviews. First, for every arrow in an architecture diagram that crosses out of Kafka, ask where the commit on the far side is; if the answer is that the consumer commits offsets, the arrow is at-least-once with nothing absorbing the repeat. Second, treat the service’s database, not the broker, as the place where exactly-once is achieved, and size it for the outbox, dedupe and offset tables that work adds. Third, put a version or source position into every record that carries state, so that a consumer can fence out anything stale whatever happened upstream.

What is changing

The boundary is not fixed. KIP-939 proposes that a Kafka producer take part in an externally coordinated two-phase commit, so that a database and Kafka could commit one write together; its motivating cases are the dual write and the outbox 73. In the 4.3 release the producer configuration already includes transaction.two.phase.commit.enable, documented as telling the broker that the client takes part in two-phase commit and that its transactions never expire, while the public prepare and complete calls that the proposal specifies are present on Kafka’s trunk branch but not in the 4.3 producer interface 22,74. If they ship, a new rung appears between C3 and C4: one commit spanning a database and Kafka, coordinated outside both. It would move the outbox’s commit without removing the need for idempotent consumers on the far side, and it would bring back the operational questions about in-doubt transactions that Helland’s argument was about 6,56.

Two smaller moves point the same way. KIP-1289 would let share-group acknowledgements join a Kafka transaction 72, and the 4.x transaction work continues to harden the protocol that Jepsen found wanting 31,35. Each extends what Kafka can commit. None removes the crossing.

Limits

The coding takes each pattern at its canonical description, and real systems mix patterns. The lab’s fault parameters are illustrative. Its zeros are structural, since an outbox cannot lose an event that its transaction committed, but its non-zero counts scale with the parameters chosen. The listings are excerpts written against the 4.3 Java clients, not a tested application. And the census counts mechanisms rather than systems: a system assembled from mechanisms that each hold their rung can still be wrong where they meet.
