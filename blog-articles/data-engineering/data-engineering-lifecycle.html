stage=00/framing

A discipline defined by its stages, not its tools

Data engineering has an unusual relationship with its own history. Every few years the tooling turns over completely — a warehouse appliance becomes a Hadoop cluster becomes a cloud warehouse becomes a lakehouse — and each turn arrives with the claim that everything before it is obsolete. Underneath the churn, the work has been remarkably stable. Data is produced somewhere you do not control. It has to be moved. It has to be kept. It has to be reshaped into something a person or a model can use. And then it has to be delivered, on time, to whoever is waiting.

That sequence — generation, ingestion, storage, transformation, serving — is what Reis and Housley named the data engineering lifecycle, and the reason the framing has stuck is that it is deliberately technology-neutral. The stages have not changed even as the specific products implementing them have risen and fallen.[1] A pipeline built on Informatica and Teradata in 2004 and a pipeline built on Fivetran, Iceberg and dbt in 2026 differ enormously in cost, latency and operational shape, but they answer the same five questions in the same order.

Treating the lifecycle as the unit of analysis has a practical payoff: it tells you where a problem actually lives. A dashboard that is wrong at 09:00 has a root cause in exactly one of five places, and the diagnostic questions differ sharply between them. Did the source system change a column? Did ingestion silently drop a partition? Did a storage compaction job rewrite files mid-query? Did a transformation double-count because a join fanned out? Or did serving hand a stale snapshot to a tool that cached it? Engineers who reason in terms of stages narrow that down in minutes. Engineers who reason in terms of tools tend to blame whichever tool they understand least.

This article walks the lifecycle end to end: the history that produced each stage, the concepts that govern it, and the concrete decisions an engineer makes inside it. It ends where the field actually is in mid-2026 — a period of consolidation rather than invention, in which the interesting arguments are about catalogues, contracts and cost rather than about whether to use Hadoop.

stage=00/history

How the five stages were discovered

The lifecycle was not designed. It accumulated, each stage crystallising around a constraint that the previous generation of systems could not absorb.

Separating the operational from the analytical (1970–1996)

Codd's relational model gave the industry a shared abstraction for structured data: relations, a declarative query language, and independence between the logical schema and the physical layout.[2] What it did not give was a way to run analysis without hurting the system of record. Reporting queries scanned wide, locked rows, and competed with the transactions that paid for the machine.

The formal answer came from IBM. In 1988, Devlin and Murphy published the architecture of the EMEA Business Information System, which proposed an integrated warehouse of company data held separately from the operational databases, reachable through a consistent set of end-user tools and described by a business data directory.[3] That paper is the origin point of the first stage boundary in the lifecycle: source systems on one side, analytical systems on the other, with a deliberate copy in between. Inmon codified the enterprise warehouse as a subject-oriented, integrated, time-variant, non-volatile collection built for decision support;[4] Kimball argued the opposite direction, building outward from business processes as dimensional star schemas designed for query legibility rather than normalisation.[5] Their disagreement is still live, and both models remain in production, frequently in the same company.

The distributed detour (2003–2012)

Web-scale data broke the assumption that the warehouse fits on one very expensive machine. Google's response was to build reliability out of unreliable parts: a distributed file system that assumed component failure was routine,[6] and a programming model that let ordinary engineers express a parallel computation as a map and a reduce without writing any distribution logic themselves.[7] The open-source reimplementation of both became Hadoop, whose distributed file system carried the same design premise into thousands of ordinary enterprises.[8]

Two consequences followed. First, storage got cheap enough that discarding data started to look like the more expensive option, which produced the idea of keeping everything raw — the data lake, named by James Dixon in 2010 as a contrast to the bottled, pre-packaged data mart.[9] Second, MapReduce's batch-only, disk-heavy execution made iterative and interactive work painful, which drove the next wave: resilient distributed datasets and in-memory execution in Spark,[10] and columnar, massively parallel SQL execution in Dremel, the engine underneath BigQuery.[11,12]

The cloud rearrangement (2006–2016)

Amazon S3 launched on 14 March 2006 with roughly a petabyte of capacity across about 400 storage nodes, a five-gigabyte object limit and a price of fifteen cents per gigabyte. Twenty years later it holds more than 500 trillion objects, serves more than 200 million requests per second, and charges a little over two cents per gigabyte — while the code written against it in 2006 still runs.[13] That combination of durability, an unchanging API and a collapsing price is the single most consequential fact in modern data engineering, because it made storage a utility and left compute as the only thing worth scheduling.

Cloud warehouses drew the obvious conclusion. Snowflake's design separated storage from compute entirely, running multiple independent virtual warehouses over one shared copy of the data, with elasticity, semi-structured types and time travel as first-class features.[14] Redshift had already argued that a simpler, managed, columnar warehouse beat a tunable one for most teams.[15] Stonebraker's earlier point that no single engine serves every workload well had been proven in both directions: specialised systems won on performance, but only a few of them were worth operating yourself.[16]

The lakehouse and the current settlement (2016–2026)

By the mid-2010s most large organisations ran two tiers: a lake holding everything and a warehouse holding the modelled subset, with ETL between them. That arrangement paid for storage twice, kept the warehouse copy stale, and left machine learning workloads reading files the warehouse could not govern.[17] Three projects attacked the same weakness from different companies. Uber built Hudi in 2016 to get upserts and incremental consumption onto Hadoop.[18,19] Netflix engineers Ryan Blue and Daniel Weeks started Iceberg in 2017 because Hive's directory-based table layout could not guarantee correctness or atomic change.[20] Databricks published Delta Lake, which put an ACID transaction log over Parquet files in cloud object storage.[21] In 2021 the same group named the resulting pattern the lakehouse and argued the two-tier architecture would not survive.[17]

What has happened since looks less like a new architecture and more like an industry agreeing on one. In June 2024 Databricks acquired Tabular, founded by Iceberg's original creators, explicitly to converge the two leading open table formats;[22] in the same week Snowflake announced Polaris, an open implementation of the Iceberg REST catalogue.[23] Databricks open-sourced Unity Catalog days later.[24] The competitive frontier moved from the file on disk up to the catalogue that governs it.[25] Fivetran and dbt Labs, the two poles of the ingestion-and-transformation stack, announced a merger in October 2025 and completed it on 1 June 2026.[26,27,28] The lifecycle stages are unchanged; the vendor map is being redrawn under them.

stage=00/model

The shape of the lifecycle

Five stages carry data forward. Six concerns run underneath all of them, belonging to no single stage and failing across several at once when neglected. Reis and Housley call these the undercurrents: security, data management, DataOps, data architecture, orchestration and software engineering.[1]

Three properties of this model are worth stating explicitly before walking through it.

The stages are not teams. A five-person startup may compress all five into one scheduled job and one warehouse. A bank may have separate organisations for source-system integration, platform storage, analytics engineering and machine learning, with formal interfaces between them. The stages describe work, not headcount, and one of the more reliable ways to build a bad platform is to draw the org chart directly onto the diagram.

The boundaries are where guarantees change. Each transition is a place where a guarantee is either preserved or quietly dropped: ordering, completeness, exactly-once delivery, referential integrity, freshness, access control. Most data quality incidents are traceable to a guarantee that one stage assumed and the previous stage never actually made.

The lifecycle runs backwards during design. You choose serving first, because that is where the requirement lives, and let it dictate the acceptable latency, granularity and correctness of everything upstream. Building forwards from whatever the source system happens to emit is how organisations end up with warehouses full of tables nobody queries.

stage=01/generation

Generation: the systems you do not control

The first stage of the lifecycle is the one data engineers own least. Source systems are built for their own purposes by people whose incentives point somewhere else entirely, and the defining skill of this stage is characterising a source accurately enough to build something that does not break when it changes.

Internal sources

Application databases. The OLTP store behind a service — PostgreSQL, MySQL, DynamoDB, MongoDB — is usually the highest-value and most fragile source. It is tuned for short transactions with strict latency budgets, so analytical reads against the primary are antisocial and often forbidden. Its schema belongs to the application team and changes on their release cadence, not yours. Crucially, it stores current state: when a row is updated, the prior value is gone unless something captured it. Analysis almost always wants history, so the mismatch between state-oriented sources and event-oriented analysis is a recurring cost throughout the lifecycle.

Application logs and events. Server logs, clickstream, and structured application events are append-only by nature, which makes them a much better fit for downstream processing — they arrive as facts about things that happened, with timestamps, rather than as mutable rows. The failure modes are different: unbounded volume, no schema enforcement unless someone imposes one, and instrumentation written by product engineers who will change an event name without telling anyone.

IoT and telemetry. Sensor fleets combine high volume with poor connectivity and unreliable clocks. Devices buffer while offline and flush in bursts, so records arrive minutes or days after the moment they describe. Device clocks drift and are sometimes badly wrong. Every downstream decision about time — which timestamp is authoritative, how late is too late — originates in the physical properties of these sources.

External sources

Third-party APIs impose rate limits, pagination models, and undocumented behaviour changes. They may or may not offer a reliable cursor for incremental extraction, and their definition of “updated” often excludes deletions, which is why records vanish silently from downstream tables. Partner data feeds typically arrive as files dropped into a bucket or SFTP endpoint on an agreed schedule: simpler to consume, but you inherit whatever inconsistency the partner's own pipeline produced, with no ability to inspect upstream. Public datasets — government statistics, reference geographies, market data — look easy and are the most common source of silent breakage, because their release cadences, revision policies and identifier schemes change without any commercial relationship obliging anyone to warn you.

What to characterise before writing any code

For each source, the answers to a short list of questions determine most of the pipeline design downstream: is it state or events; is there a reliable monotonic cursor; are deletes observable; what is the schema-change process and who owns it; what volume and what peak rate; what is the authoritative timestamp; is there an idempotency key; and what is the actual read budget against the source before someone's pager goes off.

The last decade's most useful answer to several of these at once is change data capture. Rather than polling a table for rows that look new, log-based CDC reads the database's own write-ahead log or binlog — the structures the database already maintains for recovery and replication — and emits every insert, update and delete as an ordered event stream. Debezium implements this as a set of Kafka Connect source connectors, taking an initial snapshot where the logs no longer reach back far enough and streaming from the log thereafter.[29,30] CDC turns a state-oriented source into an event-oriented one at the boundary, which is precisely the conversion the rest of the lifecycle wants. It is the reason a modern warehouse can reconstruct what a customer record looked like on any past date, from a source system that never stored that history.

stage=02/ingestion

Ingestion: moving data without losing its guarantees

Ingestion is data movement, and the whole difficulty is that movement is where guarantees go to die. Two independent axes describe most of the design space: whether data moves in bounded chunks or continuously, and whether the producer sends or the consumer fetches.

Batch

Batch ingestion moves data in bounded chunks on a schedule: a nightly extract, an hourly file sweep, a weekly reload. It remains the correct default for most workloads, and the reasons are unglamorous. A batch has a beginning and an end, so it can be counted, checksummed, retried and compared against the source. Failures are contained: a bad run affects one partition, and re-running it is a bounded operation. Costs are predictable because compute is only awake while the job runs.

The mechanics that matter are incremental extraction and idempotency. Full reloads are simple and correct but scale badly; incremental extraction uses a high-water mark — an auto-incrementing key, an updated_at column, a log sequence number — to fetch only what changed. Every high-water mark has a subtle failure: clock skew between application servers, transactions that commit out of timestamp order, and rows updated by a process that forgets to touch the modification column. The standard mitigation is to overlap windows deliberately, re-reading a margin of data already seen, and to make the write idempotent so re-reading is harmless.

def extract_window(conn, table, low, high):
    # Overlapping window: re-read a safety margin, then rely on an
    # idempotent MERGE downstream. Never trust a source clock exactly.
    low = low - LATE_ARRIVAL_MARGIN          # e.g. 15 minutes
    rows = conn.execute(
        "SELECT * FROM {} WHERE updated_at >= %s AND updated_at < %s".format(table),
        (low, high),
    )
    return rows, high                       # new high-water mark, committed only on success

Streaming

Streaming ingestion treats data as an unbounded, continuously arriving sequence. The substrate is almost always a durable, partitioned, replayable log: Kafka, originally built at LinkedIn to carry high-volume activity and operational events with the throughput that conventional message brokers could not sustain,[31] or a managed equivalent such as Kinesis or Pub/Sub. The insight that made the log the default abstraction is that a log is not a queue: consumers hold their own offsets, read at their own pace, and can rewind, which means the same durable history can feed a real-time consumer and a bulk reprocessing job without duplicating storage.[32]

Streaming also drags in the hardest concept in the lifecycle: time. There are two clocks. Event time is when something happened in the world. Processing time is when the pipeline saw it. They diverge because of network delay, buffering, retries, partition skew and offline devices, and the divergence is neither constant nor bounded. The Dataflow model gave the industry the vocabulary that streaming engines now share: windowing to divide unbounded data by event time, watermarks as a heuristic lower bound on the event times already processed, triggers to decide when to emit a result, and accumulation modes to decide what a late arrival does to a result already published.[33] Flink and Spark Structured Streaming both implement variations of this model.[34,35]

The practical consequence is that a streaming pipeline forces an explicit decision that a batch pipeline lets you avoid: what happens to a record that arrives after you already published the number. The options are to drop it, to admit it within an allowed-lateness bound and restate the result, or to route it to a side output for manual handling. All three are defensible. Not choosing means the framework chooses for you, usually by dropping silently.

Push, pull, and who owns the failure

In a pull pattern, the ingestion system initiates: it queries the database, calls the API, lists the bucket. Control over rate, retry and backfill sits with you, which is why most managed connectors work this way. The cost is load on the source and the need for credentials into someone else's system. In a push pattern, the producer sends: the application emits to a topic, the partner writes a file, the webhook fires. Latency is lower and the source is not interrogated, but you now depend on the producer's reliability, and a push you failed to receive leaves no trace on your side unless the protocol includes acknowledgement. This is the practical argument for landing pushed data in a durable log before processing it — the log becomes the receipt.

Delivery semantics

Three guarantees are on offer and only two are cheap. At-most-once delivery can lose records and is almost never acceptable for analytics. At-least-once can duplicate them and is what most systems provide by default. Exactly-once is achievable, but only as an end-to-end property of a specific pipeline, usually by combining at-least-once transport with either transactional writes or idempotent keys at the destination.[36] The pragmatic form of this in most warehouses is a natural or synthetic idempotency key plus a MERGE: the pipeline may deliver a record five times, and the table still holds it once. Designing for at-least-once transport with idempotent application is far more robust than pursuing exactly-once transport and assuming it holds.

Choosing a latency, honestly

The single most common architectural mistake in this stage is buying latency nobody asked for. Streaming infrastructure has real ongoing costs: a broker to operate, stateful jobs to keep alive, checkpoints to manage, and reprocessing semantics that are far more subtle than re-running a batch job. Those costs are worth paying when the decision downstream is genuinely time-critical — fraud scoring, dynamic pricing, routing, real-time inventory. They are not worth paying so that a daily report can be technically current at 03:00.

The historical version of this argument is instructive. Marz's lambda architecture proposed running batch and streaming layers side by side and merging their outputs, accepting duplicated logic as the price of both accuracy and low latency.[37] Kreps objected that maintaining two implementations of the same computation in two distributed systems is exactly as painful as it sounds, and proposed instead reprocessing by replaying the log through an updated streaming job — the kappa pattern.[38] Modern practice has largely converged on a third position: one processing framework with unified batch and streaming APIs, writing into transactional table formats that make incremental and full recomputation the same operation.[35]

stage=03/storage

Storage: five layers people call one thing

Storage sounds like the simplest stage and is the one where the most consequential architectural decisions get made, because it is the only stage whose choices are expensive to reverse. Almost every confused argument about lakes, warehouses and lakehouses is really an argument in which the participants are talking about different layers of the same stack.

Object storage as the floor

Cloud object stores are extraordinarily good at exactly two things: keeping bytes safe and charging very little for it. S3 is designed for eleven nines of durability, achieved through replication and continuous background auditing of every stored byte, with automated repair triggered on the first sign of degradation.[13] Objects are addressed by key through HTTP verbs.

What object stores deliberately do not provide is everything a database takes for granted. There is no atomic rename, so the classic trick of writing to a temporary directory and renaming it into place — the basis of correctness in HDFS-era pipelines — does not hold. There is no transaction spanning multiple keys, so a job writing 300 files makes each one visible as it lands and a reader can see a half-finished write. Listing a large prefix is slow and expensive, which is fatal when a query planner has to enumerate thousands of partition directories to decide what to read.[21] These are not defects; they are the trade that makes the durability and the price possible. But they mean raw object storage alone cannot host a table.

File formats

Analytical queries touch few columns of many rows, which is the exact inverse of the row-oriented layout that transactional databases use. Columnar storage puts values of the same column together, which improves compression dramatically because adjacent values share a type and often a distribution, and lets an engine read only the columns a query names.[39] Parquet implements this with a nested, self-describing layout: row groups, column chunks, pages, and footer metadata carrying per-column statistics such as minimum and maximum values.[40] Those statistics do most of the practical work — an engine can skip an entire file after reading its footer if the maximum value of the filter column falls below the predicate. Arrow serves the same columnar logic in memory and as an interchange format, which is why engines can now hand data to one another without serialising through text.[41]

Table formats

A table format is the layer that turns a pile of Parquet files into something with the properties of a table. All three major implementations share the same core idea: metadata files, not directory listings, are the source of truth about which files constitute the table right now, and a commit is an atomic swap of a single pointer.

Iceberg emerged at Netflix in 2017 because Hive's convention of describing a table as a set of directories could not guarantee correctness at scale: listing thousands of partitions took minutes, schema changes required careful coordination, and readers could observe a writer mid-flight. Blue and Weeks tracked individual files in metadata instead, and required every change to commit atomically.[20,42] Delta Lake independently arrived at an ordered transaction log over Parquet, using optimistic concurrency to serialise commits and log compaction as checkpoints to keep metadata reads cheap.[21] Hudi came out of Uber a year earlier, motivated less by correctness than by mutability: the requirement was record-level upserts and incremental consumption of only what changed, so ingestion pipelines would not rewrite entire partitions on every run.[18,43]

The capabilities this unlocks are the ones the two-tier lake-plus-warehouse architecture was missing. Snapshot isolation: a long-running read sees a consistent view even while a writer commits. Time travel and rollback: any past snapshot is queryable, and a bad load is undone by re-pointing rather than restoring from backup. Schema evolution: Iceberg assigns stable field identifiers, so renaming a column does not orphan the data files written before the rename. Partition evolution: the partitioning scheme can change without rewriting history. Row-level deletes and updates: essential not only for correctness but for compliance, since the right to erasure under GDPR Article 17 obliges a controller to delete specific personal data on request — an operation that is trivial in a database and was, for years, close to impossible in a lake.[44] Iceberg's version 3 specification, delivered across 2025 releases, added binary deletion vectors, a variant type for semi-structured data, geospatial types and row lineage tracking.[45]

Catalogues

The catalogue answers a question the table format cannot: what is this table called, who may read it, and where is its current metadata pointer. It is also the atomic-swap point, which makes it the component that determines whether two different engines can safely write the same table. That is why the strategic centre of gravity moved here: Snowflake's Polaris and Databricks' Unity Catalog were both released as open implementations within weeks of each other in mid-2024, and the Iceberg REST catalogue API became the interoperability contract between them.[23,24,46,25] The older literature anticipated this: Google's Goods system inferred a catalogue over billions of internally produced datasets because nobody was going to register them by hand,[47] and Ground argued for a general data context service holding lineage, versioning and usage alongside schema.[48]

So what is a lake, a warehouse, or a lakehouse?

A data lake is object storage plus files, with schema applied on read. It is cheap, accepts anything, and offers no guarantees. Its characteristic failure is the data swamp: a repository nobody can navigate because no metadata layer was ever imposed — a documented and recurring outcome rather than a hypothetical one.[49] A data warehouse is a managed system with schema on write, a query optimiser, transactions, and governance built in; you buy correctness and performance and accept a proprietary boundary. A lakehouse is the lake's storage economics with the warehouse's guarantees, achieved by inserting the table format and catalogue layers.[17] It is worth being honest that the lakehouse's advantage is largest for organisations running mixed SQL and machine learning workloads over the same data at meaningful scale. For a company whose analytical estate is a few terabytes, a well-run cloud warehouse is simpler and probably cheaper, and single-node engines like DuckDB have made small-to-mid analytics dramatically less demanding than the distributed default assumes.[50]

stage=04/transformation

Transformation: where data acquires meaning

Everything before this stage moves bytes. Transformation is where those bytes become a number someone will act on, which makes it the stage with the highest ratio of business risk to technical difficulty. A subtly wrong join produces a report that is confidently, plausibly incorrect for months.

ETL, ELT, and why the letters moved

Classical ETL transformed data before loading it, on dedicated infrastructure between source and warehouse. The pattern was not a mistake; it was a rational response to the economics of the time. Warehouse storage was expensive and capacity was provisioned years in advance, so only modelled, conformed data earned a place in it, and transformation ran on a separate machine because warehouse compute was the scarcest resource in the building. A substantial body of research and tooling grew up around exactly this problem of specifying and optimising the transformation stage.[51]

ELT inverts the last two steps: extract, load the raw data as it arrived, and transform inside the destination using its own engine. This became the default once separated storage and compute made warehouse capacity elastic and object storage made retaining raw history nearly free.[14,13] The change that matters is not performance but reprocessability. When raw history is retained, a change to a business definition is a re-run against data you already hold. Under ETL, the same change requires re-extracting from a source system that may have overwritten the state you needed.

The pattern has visible limits. Transforming inside the warehouse means paying warehouse compute prices for work that a cheaper engine could do, which is why cost control became a first-class concern. And regulated data frequently cannot be landed raw at all: if a field must be tokenised or masked before it crosses a boundary, the transformation happens in flight, producing the hybrid sometimes labelled ETLT — minimal in-flight transformation for compliance, followed by full modelling in place.

What the T actually contains

Structural conforming. Types are cast and made consistent; timestamps are normalised to UTC with the original offset retained; identifiers from different systems are mapped to a common key. This is unglamorous and it is where most silent corruption enters, usually through implicit casts and timezone assumptions.

Deduplication. At-least-once ingestion guarantees duplicates. The standard treatment is to define a business key and a version ordering, then keep one row per key. In SQL this is a window function; the important part is that the ordering column must be genuinely monotonic within a key, which source-system timestamps often are not.

-- Collapse a CDC stream into current state: one row per key, latest version wins.
-- The tie-break on log sequence number matters; two events can share a millisecond.
WITH ranked AS (
  SELECT *,
         ROW_NUMBER() OVER (
           PARTITION BY order_id
           ORDER BY committed_at DESC, log_sequence_number DESC
         ) AS rn
  FROM raw.orders_cdc
  WHERE committed_at >= DATE_TRUNC('day', CURRENT_DATE - INTERVAL '3 days')
)
SELECT order_id, customer_id, status, order_total, committed_at
FROM ranked
WHERE rn = 1
  AND op <> 'd';                       -- deletes drop out here, not silently upstream

Joining and aggregating. The two recurring hazards are fan-out, where a join against a non-unique key silently multiplies rows and inflates every downstream sum, and non-additivity, where a measure valid at one grain is aggregated at another. Declaring the intended grain of every model and testing uniqueness on its key catches most of both.

History and slowly changing dimensions. When an attribute changes — a customer's segment, a product's price tier — the model must decide whether history is overwritten or preserved. Kimball's type 2 pattern retains prior versions with effective-from and effective-to timestamps, so a historical fact joins to the attribute value that was true at the time.[5] Getting this wrong produces the most insidious class of error in analytics: last year's revenue silently reclassified under this year's org chart.

Validation. Transformation is the natural place to assert what must be true, because it is the last point before consumption. Google's production experience is the reference here: a data validation system running as part of TFX, checking each batch against an evolving schema, comparing training and serving distributions, and treating the schema itself as a versioned artefact that engineers review like code.[52,53] Amazon's Deequ made the same argument for general data pipelines with declarative unit tests over data.[54] The broader research on data cleaning has been consistent for a decade that errors are best caught by constraints declared close to the data rather than by inspection after the fact.[55]

Modelling and the DAG

Transformation logic is not a script; it is a directed acyclic graph of tables, each with a declared schema, a grain, tests, and dependencies on others. This shift — from procedural jobs to declarative models with inferred dependencies — is what tools such as dbt formalised, and it is why analytics engineering became a recognisable role.[56]

Layering conventions vary in name — raw/conformed/served, bronze/silver/gold, staging/ intermediate/marts — but they encode the same discipline: preserve arrival fidelity in the first layer so you can always rebuild; centralise cleaning in the second so it happens once; and put business definitions in the third so a metric has one definition rather than one per dashboard.

Two properties make the DAG operable. Idempotency: running a model twice produces the same result, which is what makes retries and backfills safe. Incrementality: processing only what changed, which is the difference between a five-minute run and a five-hour one — and the reason the table formats' merge-on-read and incremental-read capabilities matter so much at this stage.[18] Orchestration then schedules the graph, which is precisely the problem Airflow was built for at Airbnb in October 2014: expressing workflows as Python-defined DAGs with dependencies, retries and visibility, rather than as a wall of cron entries.[57,58]

stage=05/serving

Serving: four consumers, four different contracts

Serving is the stage that justifies the other four. It is also where a single set of tables must satisfy consumers whose requirements barely overlap.

Business intelligence

Dashboards in Tableau, Power BI or Looker are the oldest consumer and the one with the sharpest semantic requirement: a metric must mean the same thing everywhere. The classic failure is not technical but organisational — three teams each write their own definition of active customer, all three are defensible, and the executive meeting spends its time reconciling numbers rather than deciding anything. The response is a semantic layer: metric definitions expressed once, in version control, and served to every tool from the same place. This is a direct descendant of Kimball's conformed dimensions, where shared dimensions guarantee that facts from different processes can be compared at all.[5]

Machine learning and feature stores

Models need features, and features are transformations of the same underlying data — which means every feature exists twice: once computed over history to train, once computed over current state to serve. When those two computations drift apart you get training-serving skew, a class of bug that is notoriously hard to diagnose because nothing errors; the model simply performs worse in production than in evaluation.[52]

The feature store is the architectural answer. Uber's Michelangelo introduced a centralised store of curated features with dual offline and online storage, so the same definition produces training data and serving values, with transformation logic executed identically in both paths.[59,60] The other requirement is point-in-time correctness: a training row for an event on 3 March must contain feature values as they were on 3 March, not as they are today. Building training sets by joining current dimension tables to historical events leaks future information into the past and produces evaluation scores that cannot be reproduced in production. The lifecycle discipline here is unglamorous and decisive: history retained in storage, event-time semantics preserved through transformation, and served features versioned. Sculley and colleagues' warning that machine learning systems accumulate technical debt in their data dependencies rather than in their model code remains the best short statement of why this stage belongs to data engineering rather than to data science.[61]

Reverse ETL

Reverse ETL closes the loop by syncing modelled data from the warehouse back into the operational systems where work actually happens: a lead score into Salesforce, a churn-risk flag into a support tool, a customer segment into an ad platform.[62,63] It exists because the insight is useless where it is computed. A salesperson will not open a dashboard; they will look at the record in front of them.

It also inverts the risk profile of the entire lifecycle. Every other stage writes into systems the data team owns, where a mistake is embarrassing but contained. Reverse ETL writes into someone else's system of record, at their rate limits, under their validation rules, where a bad sync overwrites fields humans depend on and may be genuinely difficult to undo. The engineering requirements follow: diff-based syncs that send only changes, strict idempotency, dry-run modes, field-level ownership agreed with the operational team, and hard limits on write volume. The category has consolidated commercially — Fivetran acquired Census in 2025 before merging with dbt Labs — but the operational discipline is unchanged.[28]

Data and AI applications

The newest consumer class embeds analytical data directly into products: customer-facing analytics, in-product recommendations, and increasingly retrieval layers for language models and agents. The requirements are the strictest of the four, because the consumer is an end user rather than an analyst: low and predictable latency, row-level access control that cannot leak one tenant's data to another, and a schema versioned like a public API because something outside your control now depends on it. This is the requirement driving much of the current infrastructure investment, including storage-side features aimed squarely at it — managed Iceberg tables, native vector storage and centralised object metadata offered directly by the object store itself.[13]

stage=**/undercurrents

The undercurrents

The stages describe what moves. The undercurrents describe what must hold across all of them, and they are where mature platforms distinguish themselves from working ones.[1]

Data quality and observability

Quality is not a stage; it is a property asserted at every boundary. In practice five dimensions cover most real incidents: freshness (did the data arrive when it should), volume (did roughly the expected number of rows arrive), schema (did the shape change), distribution (are the values still plausible), and lineage (what breaks if this breaks). The most instructive published example is a Google outage in which an upstream remote procedure call began failing and returned an error code in place of a real value; the model trained on it, degraded, and the feedback loop reinforced the corruption — none of which any component reported as an error.[52] Schema-based validation with per-batch anomaly detection exists precisely because the damaging failures are the ones that do not throw exceptions.

Governance, security and privacy

Governance becomes tractable only when the platform can answer three questions mechanically: what data exists, where did it come from, and who is allowed to see it. Catalogue and lineage systems exist to make the first two answerable at scale without manual registration.[47,48] The third is access control, and its centre of gravity has moved to the catalogue layer, which is why the catalogue wars of 2024–2026 are strategically significant rather than merely technical.[24,23] Privacy regulation adds a hard functional requirement that shaped storage design: the right to erasure obliges deletion of specific personal data on request, which is exactly what append-only file layouts could not do before row-level deletes arrived in the table formats.[44,21] Security's default posture is least privilege and encryption everywhere, and the highest-leverage practice is not technical at all: not collecting personal data you have no defined use for.

Orchestration and DataOps

Orchestration is dependency management over time: run this when that finished and its data actually arrived, retry on this class of failure, alert if the window closed without a result. The DAG model has been the dominant abstraction since Airflow, with the industry gradually shifting from scheduling tasks to declaring assets and letting the system infer what must run.[57,58] DataOps is the surrounding practice: version control for transformation logic, code review, a development environment that is not production, automated tests on both code and data, continuous deployment, and monitoring with meaningful service-level objectives on freshness and completeness. None of this is novel — it is software engineering, arriving late to a discipline that spent a decade pretending SQL scripts were not code.

Architecture and organisation

The most consequential architectural question is centralisation. A single platform team owning every pipeline gives consistency and becomes a bottleneck. Dehghani's data mesh proposes the opposite: domain teams own their data as a product, with a self-serve platform underneath and federated computational governance across it.[64,65] In practice, few organisations implement the full model, and the durable contribution is narrower but real — the insistence that a dataset has an owner, an interface, a documented service level and a consumer, rather than being an incidental by-product of somebody's job. Data contracts are that idea made concrete at the stage boundary where it matters most: a producer commits to a schema and a guarantee, and a breaking change is a versioned event rather than a surprise at 03:00.

Cost

Cloud data platforms convert capital expenditure into a metered bill that engineers change with every commit, which makes cost an engineering property rather than a procurement one. The dominant line items are predictable: idle or oversized warehouse compute, full-table scans caused by unpartitioned or badly clustered tables, streaming infrastructure serving batch requirements, and data movement between regions or clouds. The corresponding levers are equally predictable — partitioning and clustering aligned to actual query predicates, incremental models rather than full rebuilds, compaction of small files, retention policies that expire snapshots, and honest audits of which tables anyone still reads.

stage=**/worked

A worked example, end to end

Concepts settle faster against a concrete case. Consider a mid-sized online retailer with three sources, four consumers, and one requirement that its metrics reconcile.

The brief

Sources: a PostgreSQL order service, a clickstream from the web and mobile apps, and a CRM accessed through a rate-limited API. Consumers: a finance dashboard reconciled to the general ledger; a churn model; a lead score pushed into the CRM; and an in-product “recently viewed” panel. Constraint: finance must be able to reproduce any historical figure exactly.

Generation. Orders are state, not events, so history exists only if something captures it. Clickstream is already event-shaped, at-least-once, and unreliable about time because mobile clients buffer offline. The CRM is a pull-only source with a cursor that does not expose deletes — so deletions must be detected by periodic reconciliation against a full list of identifiers, not inferred from the incremental feed.

Ingestion. Three sources, three answers. Orders use log-based CDC into a durable topic: it keeps ordering, captures deletes, avoids querying the primary, and yields the full history finance requires.[29] Clickstream is pushed to the same log directly from the applications. The CRM is pulled hourly with an overlapping window and an idempotent merge, because an hourly figure is more than the sales team needs and the rate limit forbids anything faster. Only the in-product panel genuinely needs sub-second freshness, and it is served from a small streaming job rather than by making the entire platform real-time.

Storage. Everything lands in object storage as Parquet under an open table format, partitioned by ingestion date, with the catalogue holding table identity and permissions. Raw snapshots are retained for the statutory period because finance's reproducibility requirement is a storage requirement, not a reporting one.

Transformation. A three-layer DAG: raw preserves arrival; conformed deduplicates the CDC stream into current-state orders, sessionises and bot-filters clickstream, and resolves CRM records to a surviving customer identity; served publishes fct_revenue_daily, dim_customer as a type 2 dimension, and a point-in-time-correct churn feature set. Tests assert uniqueness on every declared grain, non-negativity on monetary amounts, referential integrity between facts and dimensions, and freshness on every source.

Serving. The dashboard reads the served layer through a semantic layer holding the single definition of revenue. The churn model trains from the feature tables and serves from their online mirror, so the training and serving computations are the same code. The lead score goes back to the CRM by reverse ETL, diff-based and rate-limited, writing to fields the sales operations team has explicitly agreed the pipeline owns.

The script below implements the core of this in miniature — CDC collapse, an idempotent merge, point-in-time-correct feature assembly, and validation gates — using only the standard library so it runs anywhere.

#!/usr/bin/env python3
"""Miniature lifecycle: ingest -> store -> transform -> validate -> serve."""
from collections import defaultdict

# --- 02 INGESTION: an at-least-once CDC feed. Note the duplicate and the delete.
CDC = [
    {"op": "c", "order_id": 1, "customer_id": 7, "total": 40.0, "ts": "2026-07-01T10:00", "lsn": 11},
    {"op": "u", "order_id": 1, "customer_id": 7, "total": 45.0, "ts": "2026-07-01T10:05", "lsn": 12},
    {"op": "u", "order_id": 1, "customer_id": 7, "total": 45.0, "ts": "2026-07-01T10:05", "lsn": 12},  # redelivery
    {"op": "c", "order_id": 2, "customer_id": 9, "total": 12.5, "ts": "2026-07-02T09:00", "lsn": 20},
    {"op": "d", "order_id": 2, "customer_id": 9, "total": 12.5, "ts": "2026-07-03T08:00", "lsn": 31},
    {"op": "c", "order_id": 3, "customer_id": 7, "total": 99.0, "ts": "2026-07-03T11:30", "lsn": 33},
]

# --- 04 TRANSFORMATION: collapse to current state. Latest (ts, lsn) per key wins.
def collapse(events):
    latest = {}
    for e in events:
        k = e["order_id"]
        if k not in latest or (e["ts"], e["lsn"]) > (latest[k]["ts"], latest[k]["lsn"]):
            latest[k] = e
    return [e for e in latest.values() if e["op"] != "d"]      # deletes removed explicitly

# --- 04 TRANSFORMATION: an idempotent merge. Applying twice must change nothing.
def merge(target, incoming, key="order_id"):
    idx = {r[key]: r for r in target}
    for r in incoming:
        idx[r[key]] = r
    return sorted(idx.values(), key=lambda r: r[key])

# --- Type 2 dimension: the segment a customer was in AT THE TIME of the order.
SEGMENT_HISTORY = {
    7: [("1970-01-01", "2026-07-02", "standard"), ("2026-07-02", "9999-12-31", "vip")],
    9: [("1970-01-01", "9999-12-31", "standard")],
}

def segment_as_of(customer_id, ts):
    day = ts[:10]
    for valid_from, valid_to, seg in SEGMENT_HISTORY.get(customer_id, []):
        if valid_from <= day < valid_to:
            return seg
    return "unknown"

# --- Undercurrent: validation gates run BEFORE anything is published.
def validate(rows):
    failures = []
    if len({r["order_id"] for r in rows}) != len(rows):
        failures.append("grain violated: order_id is not unique")
    if any(r["total"] < 0 for r in rows):
        failures.append("negative order total")
    if any(segment_as_of(r["customer_id"], r["ts"]) == "unknown" for r in rows):
        failures.append("orphan fact: no matching customer dimension")
    return failures

# --- 05 SERVING: the daily fact table finance reconciles against.
def fct_revenue_daily(rows):
    agg = defaultdict(lambda: {"orders": 0, "revenue": 0.0})
    for r in rows:
        k = (r["ts"][:10], segment_as_of(r["customer_id"], r["ts"]))
        agg[k]["orders"] += 1
        agg[k]["revenue"] += r["total"]
    return sorted((d, s, v["orders"], round(v["revenue"], 2)) for (d, s), v in agg.items())

if __name__ == "__main__":
    current = collapse(CDC)
    table = merge([], current)
    assert merge(table, current) == table, "merge must be idempotent"

    problems = validate(table)
    if problems:
        raise SystemExit("pipeline halted: " + "; ".join(problems))

    print(f"orders after collapse: {len(table)}")          # 2: dup folded, delete applied
    for row in fct_revenue_daily(table):
        print("  {}  {:<9} orders={} revenue={}".format(*row))

Output

orders after collapse: 2
  2026-07-01  standard  orders=1 revenue=45.0
  2026-07-03  vip       orders=1 revenue=99.0

Two details carry the argument. The 1 July order is attributed to standard even though customer 7 is vip today, because the dimension is joined as of the event date — that is point-in-time correctness. And the deleted order contributes nothing, because the delete was represented explicitly in the stream rather than being inferred from an absence.

stage=**/failure

Recurring failure modes

The same handful of failures recur across organisations of very different sizes, and each maps cleanly onto a stage.

Generation

Building against undocumented source behaviour

A pipeline is tuned to a source's current quirks — a nullable field that is never null, an ordering that happens to hold — without either being agreed. It works until the application team ships. The fix is a data contract, and its value is mostly in the conversation required to write one.

Ingestion

Streaming a batch requirement

A team builds continuous infrastructure for a report read once a day, then carries the operational burden indefinitely. Latency requirements should come from the decision the data supports, not from the architecture diagram.[38]

Storage

The data swamp

Everything is retained, nothing is catalogued, and within two years nobody can say which of four similarly named tables is authoritative. This is the documented outcome of a lake without a metadata layer, not a hypothetical.[49]

Storage

The small-file problem

Streaming ingestion writes thousands of tiny objects an hour. Query planning degrades, per-request costs dominate, and metadata grows faster than data. Compaction is not an optimisation here; it is maintenance the platform must schedule.[21]

Transformation

The pipeline jungle

Scripts accumulate without a dependency graph or tests until nobody can predict what a change breaks. Sculley and colleagues named this as a dominant source of technical debt in data-dependent systems, and it long predates machine learning.[61]

Transformation

Silent fan-out

A join on a non-unique key multiplies rows. Nothing errors; every downstream sum is simply too large. Grain declarations plus uniqueness tests catch it on the first run instead of the first quarter-end.[54]

Serving

Metric drift

The same word means different things in different dashboards because the definition lives in each tool rather than in one modelled layer. Conformed dimensions and a semantic layer are the standing answer.[5]

Serving

Training-serving skew

Features computed one way for training and another for inference. No exception is raised; the model just underperforms. The feature store exists to make the two paths share one definition.[59,52]

stage=**/present

Where the field stands in mid-2026

The most useful thing to say about the current moment is that it is a consolidation phase rather than an invention phase. Four movements are visible.

Format convergence. The table-format contest has effectively resolved into interoperability rather than a winner. Databricks bought Iceberg's creators explicitly to converge the formats, and both major vendors shipped open catalogue implementations within days of each other in mid-2024.[22,23,24,66] The competitive question moved up a layer, to the catalogue and the governance it carries.[25,46] For practitioners this is straightforwardly good: the format choice that felt irreversible in 2021 is closer to reversible now.

Vendor consolidation. The unbundled modern data stack — a separate tool for ingestion, transformation, orchestration, quality, catalogue and activation — is rebundling. Fivetran acquired Census in 2025 and completed its merger with dbt Labs on 1 June 2026, producing a combined company spanning ingestion, transformation and activation and serving, by its own account, more than 100,000 data teams.[26,27,28] The practical consequence for engineers is renewed attention to lock-in at the layers where portability is cheap to preserve: open file formats, open table formats, and SQL that is not gratuitously dialect-specific.

The AI workload as a first-class consumer. Retrieval, agents and model training are now shaping storage and serving requirements directly, rather than sitting downstream of a platform built for BI. The object store itself now offers managed Iceberg tables, native vector storage and centralised object metadata — capabilities that were separate products two years ago.[13] The engineering substance behind the marketing is old, though: the thing that makes an AI system trustworthy is the same lineage, freshness and validation discipline that makes a financial report trustworthy, which is precisely the argument the merged ingestion-and-transformation vendors are now making.[27]

A correction on scale. A meaningful share of analytical workloads never needed a distributed cluster. Single-node columnar engines have made it entirely reasonable to process tens or hundreds of gigabytes on one machine, which changes the default answer for a large number of teams.[50] Choosing the smallest architecture that satisfies the requirement is not a lack of ambition; it is the same judgement that says a nightly batch is the right answer far more often than a streaming pipeline.

stage=**/close

What actually transfers

The specific systems named throughout this article will be replaced. Some already are being: the Hadoop stack that defined the 2010s is largely gone from new builds, and the neat separation between lake and warehouse that replaced it lasted about five years. Betting a career on any particular tool is a losing position in this field.

What transfers is the reasoning. Data is produced by systems you do not control, so characterise them before you build. Movement is where guarantees are lost, so decide explicitly which ones you need and design for at-least-once delivery with idempotent application. Storage decisions are the expensive ones to reverse, so keep raw history and put the guarantees in a layer you can swap. Transformation is where data acquires meaning, so declare the grain, test the assumptions, and layer the graph so a definition change touches one place. Serving is the only stage the business sees, so design the lifecycle backwards from it. And the undercurrents — quality, governance, orchestration, cost, plain software engineering discipline — are what separate a platform people trust from a collection of jobs that mostly run.

That framing is why the lifecycle has outlasted every technology it has been implemented in, and it is a reasonable bet that it will outlast the current one too.[1]
