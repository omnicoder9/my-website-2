A data platform is not a collection of products. It is a set of decisions about where computation happens, who owns the schema, what is allowed to be wrong, and how much idle capacity you are willing to pay for. The tools are how those decisions get written down.

The catalogue is genuinely large and genuinely confusing. In any given year an engineer is asked to choose between four orchestrators, three file formats, three table formats, five query engines, two streaming substrates and an infrastructure-as-code tool whose licence changed since the last time they read it. The confusion is not because the field is immature. It is because most of these tools are solving the same half-dozen problems at different points on a cost curve, and the marketing material rarely says which point.

This article is a map of that landscape organised by function rather than by vendor. It walks the stack from the bytes upward: storage engines and the physical layouts they impose, the file and table formats that turned object storage into a database, the warehouses and query engines that read them, the processing engines that write them, the orchestrators that decide when any of it runs, the streaming substrates that feed it, and the infrastructure tooling that makes the whole thing reproducible. Along the way it explains the concepts each category exists to implement — columnar projection, partition pruning, idempotence, watermarks, snapshot isolation, declarative state — because a tool you cannot explain in terms of a concept is a tool you cannot replace.

Two orienting facts before we start. First, almost every idea in the modern stack is older than the product selling it: columnar layout, the immutable log, the directed acyclic graph, and the relational model itself all predate the cloud. Second, the field is consolidating hard. The 2016–2022 pattern of one venture-funded SaaS product per layer has been giving way to fewer, wider platforms — most visibly in the June 2026 completion of the Fivetran–dbt Labs merger, which put ingestion and transformation, two of the defining layers of the so-called modern data stack, inside one company1. Knowing the concepts rather than the logos is what makes that survivable.

Section 01 · FoundationsSix eras, one recurring argument

The history of data infrastructure is a history of one boundary being moved back and forth: the boundary between where data sits and where it is processed. Each era answered that question differently, and each answer left behind a tool category we still use.

The relational era (1970s–1980s). Codd's 1970 paper proposed that applications should address data by its content rather than by its physical location, freeing programs from knowing how records were laid out on disk2. That single act of indirection produced the declarative query, the query optimiser, and eventually SQL — and it is why a data engineer in 2026 still writes SELECT against systems Codd would not recognise. The row-oriented transactional database that grew out of it, embodied today by PostgreSQL and MySQL, remains the default system of record for operational software3,4.

The warehouse era (1990s). Analysts querying production databases hurt production databases. The response was a physically separate analytical copy, loaded on a schedule. Bill Inmon argued for a normalised, enterprise-wide integrated repository fed by subject-specific marts5; Ralph Kimball argued for dimensional models — facts and conformed dimensions — built for query legibility rather than normalisation6. That debate is unresolved and still visible in every argument about how wide a table in the gold layer should be. The era also fixed the ETL habit: transform on a dedicated middle tier, because warehouse compute was expensive and fixed.

The Hadoop era (2004–2012). Google published the Google File System and MapReduce, describing how to run reliable computation across thousands of unreliable commodity machines7,8. The open-source reimplementation — HDFS plus MapReduce, later Hive — inverted the previous economics: instead of moving data to compute, you moved compute to data9. Storage and processing lived on the same nodes, so scaling one meant scaling both. This era gave us schema-on-read, the data lake, and the columnar file formats that outlived it.

The cloud MPP era (2012–2016). Amazon Redshift launched in October 2012 as a fully managed petabyte-scale warehouse billed by the hour, and the centre of gravity moved back to SQL10. Google's Dremel, published in 2010, had already demonstrated the combination that would define the era — a multi-level execution tree over columnar storage, answering aggregations across trillion-row tables in seconds11 — and became BigQuery. Snowflake's 2016 paper then named the architectural move explicitly: a multi-cluster, shared-data design in which immutable columnar files live in an object store and independently sized compute clusters read them12. Storage and compute, welded together by Hadoop, came apart again.

The modern-stack era (2016–2022). With an elastic warehouse in the middle, an ecosystem of specialised SaaS tools grew around it: managed connectors for ingestion, dbt for in-warehouse transformation, Airflow for scheduling, a BI tool on top. Tristan Handy dates the pattern's catalysis to Redshift's launch, and the argument is convincing — cheap elastic SQL is what made ELT viable, and ELT is what let transformation move out of a bespoke middle tier and into version-controlled SQL13. This is the era whose vocabulary most teams still use.

The lakehouse and consolidation era (2022–2026). Two things happened at once. Open table formats — Iceberg, Delta Lake, Hudi — put warehouse semantics (transactions, schema evolution, time travel) onto plain files in object storage, breaking the link between a table and the engine that owns it14,15. And the point-tool market began collapsing into platforms. The current fight is not about the table format, which Iceberg has largely won on paper; it is about the catalog, the component that decides who is allowed to commit16.

What survives across all six eras is worth noticing, because it tells you what to learn. SQL survives. The relational model survives. Columnar layout survives — invented for warehouse appliances, reintroduced by Dremel, standardised as Parquet, and now the physical substrate of nearly everything17. The append-only log survives. And the directed acyclic graph survives as the universal shape of a pipeline. Tools are rented; these are owned.

Section 02 · StructureThe stack as a set of contracts

The useful way to read the layer diagram is not as a product shopping list but as a series of interfaces. Each layer promises something to the layer above it, and the promise — not the implementation — is what your pipelines depend on.

Table 1. What each layer actually promises, and what breaks when the promise is weak.

Two spines cut vertically through all five layers. Orchestration decides what runs, in what order, on which slice of time, and what happens when a step fails. Platform tooling decides how the thing that runs got there. Both are cross-cutting because both are, at bottom, about dependency: one about data dependencies, the other about infrastructure dependencies.

There is also a third, less tidy cross-cutting concern: the metadata plane — catalog, lineage, data quality, access control and cost. It is drawn as a footnote in most stack diagrams and it is where most mature teams end up spending their attention, for a reason we will get to.

This layered framing is deliberately conventional; it follows the data engineering lifecycle as it is usually taught18, and the distributed-systems reasoning underneath it — why replication, ordering and consistency guarantees are hard to compose, and why "exactly once" is a claim about a whole path rather than a component — is treated at length elsewhere19. The value of the framing is that it makes substitution legible: if you can name the contract a component satisfies, you can replace the component.

Section 03 · StorageRow stores, column stores, and why the shape matters

Every storage decision descends from one question: does the workload read many attributes of few rows, or few attributes of many rows? Transactional systems do the first. Analytical systems do the second. The physical layout that makes one fast makes the other slow.

Row-oriented (OLTP). A page holds complete tuples. Fetching a customer record by primary key touches one block; updating it rewrites one block. PostgreSQL and MySQL are the reference implementations, and both have grown well past their original remit — PostgreSQL in particular now carries JSONB, full-text search, partitioning, logical replication and a large extension ecosystem, which is why an enormous number of small analytics workloads correctly never leave it3,4. Their relevance to a data engineer is usually as a source: the write-ahead log of a production database is the highest-fidelity change stream available, and change-data-capture tools such as Debezium exist to turn it into an event stream without polling the tables20.

Column-oriented (OLAP). Values of a single attribute are stored contiguously. Three consequences follow, and they compound. Projection: a query that names four columns reads four columns, not the whole row. Compression: adjacent values share a domain, so dictionary encoding, run-length encoding and delta encoding work far better than they would on interleaved tuples. Vectorisation: a tight loop over a typed array is what modern CPUs are good at, so predicate evaluation happens on batches rather than one row at a time.

The effect is not marginal. In the worked example later in this article, two million synthetic order rows occupy 90.04 MB as CSV and 6.06 MB as zstd-compressed Parquet — a factor of 14.9 — and an aggregate over one column reads a fraction of even that.

The categories are converging at the edges. Snowflake stores tables as immutable files in a hybrid columnar (PAX) layout, grouping rows into micro-partitions and columns within them12. PostgreSQL extensions add columnar storage. But the underlying trade-off has not moved: point mutation is cheap in rows and expensive in columns, and every analytical system in this article works around that fact rather than solving it.

Section 04 · StorageFile formats: Parquet, ORC, Avro, Arrow

A file format is a serialisation contract. It is the most durable decision in the stack — engines get replaced every few years, but the bytes on disk outlive several of them — and it is also the decision most often made by accident, by whatever the ingestion tool defaulted to.

Apache Parquet is the default for analytical data at rest. It emerged in 2013 from a collaboration between Twitter and Cloudera, adopting the record-shredding and assembly algorithm from the Dremel paper so that deeply nested structures could be stored columnwise without flattening21,11. Its internal geometry is hybrid rather than purely columnar: a file is divided into row groups, each row group holds one column chunk per column, and each chunk is divided into pages. Statistics — minimum, maximum, null count — are recorded per chunk and, in later versions, per page, and the footer at the end of the file carries the schema and the offsets22.

That footer is the whole trick. Because it is written last and describes everything, a reader can issue one range request to the end of an object, learn the schema and the statistics, and then fetch only the byte ranges it needs. Predicate pushdown and column projection stop being query-engine features and become HTTP range requests. This is precisely the property that let Amazon S3 substitute for HDFS: you do not need a filesystem with seek semantics, only an object store that honours partial GETs.

Apache ORC arrived the same year from the Hive side of the ecosystem, structured around stripes rather than row groups, with lightweight indexes and, historically, richer built-in statistics and native ACID support inside Hive23. Functionally the two formats have converged; the choice is now largely ecosystem gravity. Parquet is the default in Spark, Snowflake and most lakehouse tooling; ORC retains deep roots in Hive-era estates24.

Apache Avro is row-oriented and belongs to a different job. It carries its schema with the data, supports well-defined schema resolution between writer and reader, and is compact for whole-record writes — which is why it dominates message payloads and streaming ingestion rather than analytical storage25. Iceberg uses Avro for its own manifest files, which is a good hint about where it belongs: many small records, written once, read whole.

Apache Arrow is not a storage format at all. It specifies an in-memory columnar layout so that two processes — a Python client and a query engine, say — can share a buffer without serialising and deserialising it26. The practical payoff shows up as the disappearance of conversion cost: reading Parquet into Arrow into pandas into DuckDB, once a chain of expensive copies, is now largely pointer arithmetic.

The rule that saves the most time

Land raw data in whatever the source gives you, convert to Parquet at the first opportunity, and choose a partition scheme that matches how the data will be filtered — usually a date derived from event time, not ingestion time. Nearly every "our lake is slow" investigation ends at either the wrong partition key or several million files that should have been several thousand.

Section 05 · StorageTable formats: making a directory behave like a table

Parquet files in a directory are not a table. There is no way to add a file and remove another atomically, no way to know which files belong to the current version, no way to run a query that is not affected by a concurrent rewrite, and no way to change the schema without rewriting everything. The Hive convention — a directory per partition, tracked in a metastore — papered over this and broke in all the predictable ways at scale15.

Open table formats solve it by adding a metadata layer that is itself made of files, plus one atomic pointer swap. Delta Lake's approach is an ordered transaction log of JSON actions, periodically checkpointed into Parquet, which yields ACID transactions, time travel and fast metadata operations over object stores whose own consistency guarantees are weak14,27. Apache Iceberg uses a tree: the catalog points at a table-metadata file, which points at a manifest list for each snapshot, which points at manifests, which point at data files with per-file statistics28. Apache Hudi came at it from the incremental-upsert direction, with copy-on-write and merge-on-read tables and built-in indexes for record-level updates29.

The differences are real but narrower than vendor material suggests; a CIDR analysis comparing the three found their designs converging on similar trade-offs, differing mainly in how they handle row-level deletes and how much metadata they are willing to read at plan time30. What matters operationally is the shared consequence: because a commit is a compare-and-swap on a single pointer, several engines can write to the same physical table safely, and a reader that pinned a snapshot id cannot have its scan torn by a concurrent compaction.

Iceberg's v3 specification, ratified in 2025, added deletion vectors, new data types including variant and geospatial types, and row-level lineage fields31. That last item is the tell: the format is being pushed to answer questions — which rows changed, and when — that used to require a separate CDC pipeline.

The live argument is now one layer up. If the table is just files, the catalog is the only thing that knows what the current version is and who may change it, which makes it the natural place to enforce governance and the natural place to capture a customer. Snowflake and Dremio's Polaris, donated to the Apache Software Foundation, and Databricks' Unity Catalog both implement the Iceberg REST catalog specification, and both would like to be the one you standardise on16,32. For a platform team the practical guidance is simple: pick a catalog that speaks the REST spec, and treat the ability to repoint tables at a different catalog as a requirement rather than a nicety.

Section 06 · StorageSearch and observability stores

A third storage family sits beside rows and columns: the inverted index. Apache Lucene maps terms to the documents containing them, with positional information and relevance scoring, which makes text retrieval and high-cardinality filtering fast in a way neither a row store nor a column store manages33. Elasticsearch and OpenSearch are both distributed systems built on Lucene, and both have absorbed a second role — log and metrics analytics — that now often exceeds the search workload in volume34,35.

Their history is a useful case study in supply-chain risk. Elastic relicensed Elasticsearch away from Apache 2.0 in 2021; AWS forked the last Apache-licensed release as OpenSearch; in 2024 Elastic added AGPLv3 as a licence option, restoring the open-source designation36, and AWS transferred OpenSearch to the vendor-neutral OpenSearch Software Foundation under the Linux Foundation37. Both projects are now viable; they have diverged enough that migration is a project rather than a configuration change.

The engineering point for a data platform is scope discipline. These systems are excellent at "find the matching documents fast" and mediocre and expensive at "aggregate a year of history". Teams routinely discover this after their log cluster has become their most costly component. Keep the index for recent, queryable operational data; keep the history in Parquet on object storage where a query engine can reach it.

Section 07 · QueryWarehouses, lakehouses, and SQL engines

The cloud data warehouse is the component most organisations think of as "the data platform", and its defining feature is architectural rather than functional: storage and compute are separately scalable and separately billed.

Snowflake described the pattern most cleanly. Tables are horizontally partitioned into large immutable files in an object store, laid out in hybrid columnar form; "virtual warehouses" are independent compute clusters that each cache table data on local disk and can be created, resized, suspended and resumed on demand; and a shared service layer handles metadata, transactions, optimisation and security12. A later analysis of Snowflake's production workload quantified what this buys — the ability to isolate workloads without duplicating data, and to pay nothing for idle capacity38.

Google BigQuery descends from Dremel and takes disaggregation further: there is no cluster to size at all in its default mode. A serving tree decomposes a query into subqueries across thousands of leaf nodes reading columnar storage over Google's network fabric11,39. The decade retrospective on Dremel is candid that the principles now taken for granted across cloud analytics — disaggregated storage and compute, in-situ analysis, columnar storage for nested data — were assembled there first17.

Amazon Redshift started at the other end, as a shared-nothing MPP cluster with local storage, and has been progressively re-architected toward the same shape: Redshift Managed Storage backed by S3 with local SSD caching, elastic resize, concurrency scaling, cross-cluster data sharing, and AQUA as a pushdown acceleration layer40. Reading the 2015 and 2022 papers back to back is the fastest way to understand the decade's architectural direction10.

Databricks SQL approaches the same destination from the lake side. Rather than loading data into a proprietary store, it runs a vectorised C++ engine, Photon, directly over Delta and Iceberg tables in the customer's object storage, with the explicit argument that warehouse-class performance no longer requires warehouse-class ingestion41,32. This is the lakehouse thesis in product form15.

Two other categories deserve a place in any honest survey.

Federated and lake query engines. Trino executes distributed SQL across connectors — object storage, relational databases, Kafka, search indexes — without ingesting first, which makes it the standard tool for querying a lake in place and for the awkward join that spans two systems42. ClickHouse occupies a different niche: a column store optimised for extremely fast aggregation over large, mostly-append datasets, widely used for product analytics and observability where sub-second response on billions of rows is the requirement43.

The single-node renaissance. DuckDB was presented in 2019 as an embeddable analytical database — SQLite's ergonomics with a vectorised OLAP engine — running inside the host process with no server to operate44. Its significance to the field is larger than its technical novelty: a modern laptop with 32 GB of RAM will comfortably process datasets that in 2015 would have justified a cluster, and a great many "big data" workloads are, on inspection, tens of gigabytes45. Testing whether the working set fits on one machine before provisioning a distributed engine is now a legitimate and frequently decisive step.

Section 08 · ProcessingEngines: Spark, Flink, and dbt

Processing engines are where transformation logic executes. There are three architectural answers in common use, and they are not competitors so much as different assumptions about the shape of the input.

Apache Spark — the general-purpose batch engine

Spark's founding abstraction, the resilient distributed dataset, was a read-only collection partitioned across a cluster whose lineage — the sequence of operations that produced it — was retained so that a lost partition could be recomputed rather than replicated46. That decision made in-memory cluster computing affordable on unreliable hardware, and it is why Spark tolerates spot instances gracefully. Spark SQL then added a relational front end and the Catalyst optimiser, so DataFrame code and SQL compile to the same optimised plan47.

Execution splits a plan into stages at shuffle boundaries. Narrow transformations — map, filter, projection — stay within a partition. Wide transformations — joins, aggregations, repartitions — require records to be redistributed by key, which means writing to disk and pulling across the network. Almost all Spark performance work is shuffle work: reduce it, or make it less skewed.

Spark 4.0, released in May 2025, made ANSI SQL mode the default, added a VARIANT type for semi-structured data, string collation support, a Python data-source API and structured logging48; the 4.1 line followed at the end of 202549,50. The ANSI default matters more than it sounds: silent overflow and implicit truncation were a long-standing source of quiet data corruption51.

Apache Flink — the stream-first engine

Flink's design premise inverts Spark's: treat batch as a bounded special case of streaming rather than streaming as a sequence of small batches52. It provides genuine event-time semantics, managed keyed state, and exactly-once processing through distributed checkpointing of that state. For workloads where correctness under out-of-order arrival matters — sessionisation, fraud scoring, running aggregates — this is the difference between a system that is right and one that is approximately right.

Flink 2.0, released in March 2025, was its first major release in nine years and re-architected state management for cloud-native deployment: remote distributed storage as primary state store, local disk as cache, and an asynchronous execution model to hide the resulting latency53,54. The accompanying VLDB paper describes the motivation plainly — containerised deployments have limited local disk, and coupling state size to node-local capacity had become the scaling ceiling55. Flink 2.0 also removed the DataSet API and raised the minimum Java version, so migration from 1.x is real work56.

dbt — transformation as software engineering

dbt is not an execution engine. It is a compiler and a workflow: you write SELECT statements, it resolves dependencies between them through a ref() function, materialises each model as a table or view in your warehouse, and runs tests and documentation from the same project57. The insight was that once warehouse compute is elastic and cheap, the transformation tier does not need its own cluster — it needs version control, tests, code review, environments and a dependency graph. dbt supplied those, and in doing so created "analytics engineering" as a role.

Its recent history is also the clearest example of the consolidation reshaping the field. Fivetran and dbt Labs announced an all-stock merger in October 202558 and completed it on 1 June 2026, simultaneously open-sourcing the Rust-based dbt Fusion engine as dbt Core v2.0 under Apache 2.01. Ingestion and transformation — the two layers whose separation defined the modern data stack — are now sold by the same company.

Choosing between the three

If the transformation is expressible in SQL and the data is already in the warehouse, use dbt: you get testing, lineage and review for free. If it needs non-SQL logic, unusual file formats, or machine-learning libraries at scale, use Spark. If correctness depends on event ordering and results are needed in seconds, use Flink. Most platforms of any size run all three, and the mistake is not using several — it is using Spark for something dbt would have done in twenty lines, or Flink for a report nobody reads before 9 a.m.

Section 09 · OrchestrationThe glue: schedulers and asset graphs

An orchestrator answers four questions: what runs, in what order, over which slice of time, and what happens when a step fails. Everything else it does is convenience.

Apache Airflow is the category's default. DAGs are defined in Python, tasks are executed by pluggable operators, and the scheduler handles dependencies, retries and backfills parameterised by logical date59. Airflow 3.0, released in April 2025, was the largest change since 2.0: a service-oriented architecture in which tasks talk to a Task Execution API rather than the metadata database directly, a Task SDK, DAG versioning, scheduler-managed backfills, event-driven scheduling, an edge executor for remote execution, and a rewritten UI60,61. The security consequence is the important one: worker processes no longer need database credentials. Subsequent releases added asset partitioning and multi-team deployments in 3.262 and, in 3.3, a first-class state store plus a Language Task SDK allowing tasks to be written in Java and Go63. Managed offerings track the open-source line with a lag64.

Prefect reframes orchestration around ordinary Python functions decorated as flows and tasks, with dependencies inferred at runtime rather than declared up front — which suits dynamic workflows whose shape depends on data65. Dagster makes a sharper conceptual move: its unit is the software-defined asset — a declaration in code of a table, file or model that should exist, its upstream dependencies, and the function that computes it66,67. The difference is not cosmetic. A task-centric scheduler can tell you that a job succeeded; an asset-centric one can tell you whether the table is stale and which upstream partition is missing. The idea has proved influential enough that Airflow's own asset model has moved in the same direction.

AWS Step Functions belongs to a different lineage — a managed state machine defined in JSON or YAML, with built-in integrations to hundreds of AWS services and no infrastructure to run68. For AWS-native pipelines that are mostly service invocations rather than data-aware transformations, it is often the smaller answer, and it removes an entire component from the platform team's on-call rota.

Whichever you pick, the properties you must build yourself are the same. Tasks must be idempotent: re-running the same interval must not double-count, which in practice means writing with MERGE or a partition overwrite rather than INSERT. Tasks must be parameterised by logical time, not by now(), or backfills silently produce different answers than the original run. And failure must have a bounded blast radius, which means partitioning work so that one bad day can be reprocessed alone.

Section 10 · MovementStreaming substrates and message queues

The most consequential distinction in this layer is between a log and a queue, and it is routinely blurred by marketing.

Apache Kafka is a log. The original paper described it as a distributed messaging system built for high-throughput log processing, with a deliberately simple storage model: an append-only, offset-addressed file per partition69. Consumers hold a cursor rather than receiving a push; messages persist after delivery according to a retention policy; and independent consumer groups read the same topic at their own pace. Fan-out and replay are therefore free, which is what makes Kafka useful as a system of record for events rather than merely a transport70.

Kafka 4.0, released in March 2025, removed ZooKeeper entirely — KRaft, Kafka's own Raft-based metadata quorum, is now the only supported mode — and made the next-generation consumer rebalance protocol generally available71,72. Clusters running ZooKeeper mode must migrate to KRaft on a 3.x release before they can upgrade73. The release also shipped early access to share groups, which give Kafka queue-like semantics where consumption is not bounded by partition count73.

Amazon Kinesis Data Streams and Google Cloud Pub/Sub occupy the same functional slot with managed operations. Kinesis is shard-based with an ordering guarantee per shard and a bounded retention window74; Pub/Sub is a globally managed publish-subscribe service with push and pull delivery and per-subscription retention75. Both trade a measure of control for the disappearance of broker operations, which for most teams is a good trade.

RabbitMQ is a queue, and a good one. The broker owns routing through exchanges and bindings, tracks per-message acknowledgement, and supports priorities, dead-letter queues and per-message TTL — capabilities the log model deliberately lacks76. It implements AMQP, a standardised wire protocol77. If the workload is task distribution among workers with complex routing and per-message retry, a queue is the correct primitive and a log is an awkward substitute. If the workload is "many independent consumers need the same event history", the reverse is true.

Time, lateness, and the guarantee that is easiest to fake

Streaming's hard problem is not throughput; it is deciding when a window of time is complete. The Dataflow model gave the field its vocabulary: separate event time (when the thing happened) from processing time (when the system saw it), use watermarks to estimate completeness, and use triggers and accumulation modes to decide when and how to emit results78. Apache Beam is the portable expression of that model79; Flink and Spark Structured Streaming both implement it.

Exactly-once is where careful teams and careless ones diverge. It is a property of the whole path, not of the broker. Kafka provides idempotent producers and transactional writes; Flink provides checkpointed state with consistent recovery; and the sink must offer an atomic commit for the guarantee to survive to the destination — which is one of the strongest practical arguments for writing streaming output into an open table format rather than appending files28,14. Break any link in that chain and what you have is at-least-once with better documentation.

Section 11 · PlatformInfrastructure as code, containers, and orchestrated compute

Everything above runs somewhere, and how it got there determines whether it can be rebuilt. This layer is borrowed wholesale from software engineering, and the borrowing has been the single largest improvement in data reliability of the last decade.

Terraform made declarative infrastructure mainstream: describe the desired state of cloud resources in HCL, let the tool compute a diff against reality, and review that plan before applying80. For data platforms this covers warehouses, buckets, IAM roles, network paths, Kafka topics and orchestration environments. Its licensing history is now part of the decision: HashiCorp relicensed Terraform from MPL 2.0 to the Business Source License in August 2023, a coalition forked the last MPL release, and the fork moved to the Linux Foundation as OpenTofu81,82. OpenTofu remains command-compatible and has added features of its own, including state encryption. Teams building products on top of the tool have a real choice to make; teams simply provisioning their own infrastructure mostly do not.

Ansible occupies the imperative half of the same problem. Playbooks describe ordered steps executed over SSH with no agent to install, which suits host configuration, on-premises estates and the long tail of procedures that have no stable declarative end state83. The declarative/imperative split in the figure is the useful mental model: Terraform for what should exist, Ansible for what should happen.

Docker solved the dependency problem that made data pipelines notoriously irreproducible — a pinned image containing a specific Python, a specific driver and a specific JVM is a far stronger contract than a requirements file84. Kubernetes then supplied the scheduling layer. Its lineage is explicit: it is the third container-management system built at Google, after Borg and Omega, and the published retrospective on that decade is unusually frank about which ideas transferred and which were mistakes85,86. For data workloads, Kubernetes is what runs Spark executors, Flink task managers, Airflow workers and stateless services on shared, autoscaled capacity, with resource limits that stop one job from starving another87.

The pattern that ties these together is that a pipeline change should travel the same road as an application change: committed, tested in CI against a sampled schema, planned, built into an immutable artefact, deployed by a controller, and observed. Where data teams differ from application teams is that their "tests" must cover the data as well as the code — which is the subject of the next section.

Section 12 · Cross-cuttingThe metadata plane: catalog, lineage, quality, cost

The layers described so far move and store bytes. The metadata plane describes them, and it is where teams that have solved the mechanical problems find their remaining failures.

Lineage. OpenLineage is an open specification for emitting lineage events at run time — jobs, runs and datasets, extensible through facets — with integrations for Airflow, Spark, Flink and dbt, and Marquez as its reference implementation88,89. The design goal was explicitly an OpenTelemetry for data: a vendor-neutral emission format so that lineage is a property of the pipeline rather than a feature of one catalog product. The practical value appears the first time someone asks which dashboards break if a source column is dropped, and the answer is a query rather than a week.

Quality. Tests belong in the pipeline, not in a monitoring dashboard downstream of it. dbt ships assertion tests — uniqueness, non-null, accepted values, referential integrity — that run as part of a build and fail it57. Great Expectations offers a richer, framework-independent expectation suite with data docs and profiling90. The distinction that matters is between a check that blocks publication and an alert that notifies after publication. Most incident post-mortems trace to a check that existed but only warned.

Cost. Separating storage from compute converted infrastructure cost into a per-query variable, which quietly made cost a data-engineering concern rather than a finance one. The controls are technical: partitioning and clustering so scans read less, materialisation so expensive aggregates are computed once, warehouse auto-suspend so idle clusters are not billed, and file compaction so planning does not spend more than execution39,38. A useful institutional habit is to attribute spend per model or per team, because unattributed cost is never optimised.

Contracts. The recurring organisational failure is that upstream application teams change a schema without knowing who reads it. The tooling answer — schema registries for streams, dbt contracts for models, and CI checks that fail a producer's build on a breaking change — works only when paired with the social answer, which is that a published dataset has a named owner and a stated guarantee. No product supplies that part.

Section 13 · PracticeA worked example: the whole stack in one file

The concepts above are easier to trust when they are measurable. The following script builds a miniature platform — columnar storage, partitioning, an idempotent merge and a blocking quality gate — using DuckDB and Parquet, with no cluster and no cloud account45,22. It is complete and runnable; the output shown afterwards is from an actual execution.

pipeline_demo.py — install with pip install duckdb pyarrow
import os, shutil, time, duckdb

LAKE = "lake"
shutil.rmtree(LAKE, ignore_errors=True); os.makedirs(LAKE, exist_ok=True)
con = duckdb.connect()

# 1. GENERATE — stand in for an ingestion tool: 2M synthetic order events
con.execute("""
CREATE TABLE raw_orders AS
SELECT i                                             AS order_id,
       (i * 7919) % 50000                            AS customer_id,
       DATE '2026-01-01' + INTERVAL (i % 120) DAY    AS order_date,
       round(((i * 31) % 9973) / 100.0, 2)           AS amount,
       ['web','ios','android','partner'][1 + (i % 4)] AS channel
FROM range(1, 2000001) t(i);
""")

# 2. WRITE — Hive-partitioned, columnar, compressed
con.execute(f"""
COPY (SELECT *, date_trunc('month', order_date) AS month FROM raw_orders)
TO '{LAKE}/orders'
(FORMAT parquet, PARTITION_BY (month), COMPRESSION zstd, OVERWRITE_OR_IGNORE);
""")

# 3. READ — projection and partition pruning are byte-range decisions
scan = f"read_parquet('{LAKE}/orders/**/*.parquet', hive_partitioning = true)"
con.sql(f"SELECT sum(amount) FROM {scan} WHERE month = DATE '2026-03-01'")

# 4. MERGE — the property that makes a task safe to re-run
MERGE = """
INSERT INTO orders BY NAME
SELECT * FROM incoming
ON CONFLICT (order_id) DO UPDATE SET
    customer_id = excluded.customer_id, order_date = excluded.order_date,
    amount      = excluded.amount,      channel    = excluded.channel;
"""
con.execute(MERGE)   # first run
con.execute(MERGE)   # replay of the same batch — state must not change

# 5. GATE — a failing check must fail the run, not warn a channel
CHECKS = {
  "order_id is unique":     "SELECT count(*) FROM (SELECT order_id FROM orders "
                            "GROUP BY 1 HAVING count(*) > 1)",
  "amount is non-negative": "SELECT count(*) FROM orders WHERE amount < 0",
  "channel in known set":   "SELECT count(*) FROM orders WHERE channel NOT IN "
                            "('web','ios','android','partner')",
  "order_date is not null": "SELECT count(*) FROM orders WHERE order_date IS NULL",
}
failures = sum(con.sql(q).fetchone()[0] > 0 for q in CHECKS.values())
raise SystemExit(1 if failures else 0)

Four things in that output are the article in miniature. The 14.9× compression is columnar layout plus domain-local encoding. The 3× pruning speedup is metadata doing work that would otherwise be I/O — and it is a floor, not a ceiling, because on a real lake with two years of daily partitions the ratio is measured in hundreds. The identical totals after replay are idempotence: the same batch applied twice leaves the same state, which is what makes an orchestrator's retry safe. And the gate exits non-zero, which is what makes a broken pipeline stop rather than publish.

Scaling that script up is mostly substitution, not redesign. Replace the generator with Debezium or a managed connector; replace the local directory with an Iceberg table on object storage; replace the merge with a MERGE INTO against that table; replace the check dictionary with dbt tests or Great Expectations; and wrap the whole thing in an Airflow or Dagster asset parameterised by logical date. The concepts do not change. That is the point of the layer diagram.

Section 14 · JudgementChoosing, and the two axes that decide it

Most tool arguments are really disagreements about two numbers: how fresh the data has to be, and how large the working set is. Plotting the engines against those axes explains more of the landscape than any feature matrix.

The upper-left region — sub-second freshness — is the expensive one, in engineering time as much as in infrastructure. Before committing to it, the question worth asking is what decision changes if the number is four hours old. Genuine answers exist: fraud declines, inventory allocation, dynamic pricing, incident detection. But a great deal of streaming infrastructure has been built to serve dashboards that are read once a morning.

A few heuristics that hold up across organisations of different sizes:

  • Start with the warehouse, add engines when it stops fitting. The cheapest architecture is one system. Introduce Spark when SQL cannot express the work or the data does not belong in the warehouse; introduce Flink when correctness requires event-time semantics.
  • Choose the file and table format more carefully than the engine. Engines are swapped every few years; the physical layout of the last decade of data is not. Parquet plus an open table format keeps the exit door open28,14.
  • Prefer boring, well-instrumented components at the edges. The ingestion layer is where data quality is won or lost, and clever code there is rarely worth it.
  • Count the operational surface, not the licence cost. A self-hosted Kafka, Airflow and Spark estate is three distributed systems with three on-call rotas. Managed equivalents cost money; self-hosting costs people, and people are more expensive and harder to hire.
  • Measure the working set before assuming distribution. A meaningful share of workloads labelled "big data" fit in memory on one modern machine44.
  • Treat licences as an architectural property. Elasticsearch, Terraform and Redis all changed licence terms within four years; the fork is sometimes the safer default and sometimes not36,81.

Section 15 · DirectionWhere this is going

The catalog is the new battleground. With Iceberg effectively settled as the table format and every major vendor reading and writing it, differentiation has moved to the component that arbitrates commits and enforces access. Polaris and Unity Catalog both implement the same REST specification, which is the good news; the question for buyers is whether governance features remain portable across implementations16,31.

Consolidation is not finished. The Fivetran–dbt Labs merger folded two layers of the canonical modern stack into one vendor1, and the same logic — that a customer would rather buy a platform than integrate seven products — applies to observability, catalogs and reverse ETL. The counter-pressure is the open format: as long as the bytes and the table semantics are open, consolidation at the product layer is survivable in a way that consolidation at the storage layer would not be.

The distributed-by-default assumption is weakening. Single-node engines have improved faster than most datasets have grown, and the combination of an in-process engine with remote Parquet is now a serious architecture rather than a laptop convenience44,45. Expect more pipelines whose transformation steps are single containers rather than clusters.

Streaming and batch continue to merge. Flink 2.0's materialised tables and disaggregated state, and Spark's continued investment in structured streaming, both point at the same destination: one declarative definition, executed in whichever mode the freshness requirement demands53,48.

Data infrastructure is being rebuilt around machine consumers. The explicit framing of the recent platform announcements — governed, semantically described data as the substrate for autonomous agents1 — is a genuine shift in requirements rather than only a marketing one. A dashboard tolerates an ambiguous column name because a human interprets it. A system that queries without a human in the loop does not, which raises the value of exactly the metadata plane teams have historically deferred: contracts, definitions, lineage and quality guarantees.

None of that changes the discipline underneath. The stack in 2036 will still be moving bytes from where they are produced to where they are needed, arguing about who owns the schema, and deciding how much staleness is acceptable. The tools will have different names. The contracts will be the same ones.
